# Locking: Row-Level, Table-Level, Advisory Locks — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does locking solve — and what is the difference between concurrency anomalies that locks prevent?**

A: Without locking, concurrent transactions reading and writing the same rows produce incorrect results. PostgreSQL defines four anomalies, each requiring a stricter isolation level or explicit lock to prevent:

```
Four concurrency anomalies:

┌─────────────────────┬──────────────────────────────────────────────────────────────┐
│ Anomaly             │ What happens                                                 │
├─────────────────────┼──────────────────────────────────────────────────────────────┤
│ Dirty Read          │ T2 reads a row that T1 has modified but not yet committed.   │
│                     │ If T1 rolls back, T2 acted on data that never existed.       │
│                     │ PostgreSQL NEVER allows dirty reads — not even at READ       │
│                     │ UNCOMMITTED (it behaves as READ COMMITTED).                  │
├─────────────────────┼──────────────────────────────────────────────────────────────┤
│ Non-repeatable Read │ T1 reads row A. T2 updates and commits row A. T1 reads row A │
│                     │ again — gets a different value. Same query, different result. │
│                     │ Prevented by: REPEATABLE READ or higher, or FOR SHARE lock.  │
├─────────────────────┼──────────────────────────────────────────────────────────────┤
│ Phantom Read        │ T1 queries rows matching a condition. T2 inserts a new       │
│                     │ matching row and commits. T1 re-runs the query — sees the    │
│                     │ new row. Prevented by: SERIALIZABLE isolation.               │
├─────────────────────┼──────────────────────────────────────────────────────────────┤
│ Lost Update         │ T1 and T2 both read balance = 100. T1 writes 110 (+10).     │
│                     │ T2 writes 150 (+50). T1's update is silently overwritten.   │
│                     │ Final balance: 150 instead of 160.                           │
│                     │ Prevented by: FOR UPDATE lock or optimistic locking.         │
└─────────────────────┴──────────────────────────────────────────────────────────────┘

Timeline of a Lost Update (the most common production bug):

  Time │ Transaction A                  Transaction B
  ─────┼─────────────────────────────────────────────────────────
    1  │ BEGIN
    2  │ SELECT balance FROM accounts   BEGIN
       │ WHERE id = 1;
       │ → balance = 100
    3  │                                SELECT balance FROM accounts
       │                                WHERE id = 1;
       │                                → balance = 100
    4  │ UPDATE accounts
       │ SET balance = 110             -- A adds 10
       │ WHERE id = 1;
    5  │ COMMIT;
    6  │                                UPDATE accounts
       │                                SET balance = 150  -- B adds 50, but to OLD value!
       │                                WHERE id = 1;
    7  │                                COMMIT;
       │                                → balance is 150, should be 160
```

```sql
-- PostgreSQL isolation levels and what they prevent:
-- READ COMMITTED (default): prevents dirty reads only
-- REPEATABLE READ:          prevents dirty + non-repeatable reads
-- SERIALIZABLE:             prevents all anomalies including phantoms

-- Set for a single transaction:
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- ... your queries ...
COMMIT;

-- Set for a session:
SET default_transaction_isolation = 'repeatable read';
```

**Q2. What is MVCC and how does it change what locks are needed?**

A: PostgreSQL uses Multi-Version Concurrency Control (MVCC) — every row can have multiple versions simultaneously. Readers never block writers and writers never block readers because each transaction sees a consistent snapshot of the database:

```
MVCC: Multiple row versions co-exist

accounts table — physical storage:

  xmin  xmax  id  balance   ← xmin = tx that created this version
  ─────────────────────────   ← xmax = tx that deleted/updated this version (0 = live)
   100     0   1    100      ← Version created by tx 100, still live
   101     0   1    110      ← Version created by tx 101 (after T1's UPDATE), still live
                              ← Both versions exist simultaneously

Transaction A (snapshot taken at tx 100):
  SELECT balance FROM accounts WHERE id = 1;
  → Sees xmin=100 row → balance = 100   (old version)

Transaction B (snapshot taken at tx 101):
  SELECT balance FROM accounts WHERE id = 1;
  → Sees xmin=101 row → balance = 110   (new version)

Neither transaction blocks the other. Readers don't need locks.
Writers need locks only to coordinate with OTHER writers.

VACUUM later cleans up dead row versions (xmax is set, not visible to any tx).
```

```sql
-- Consequence: a plain SELECT never blocks in PostgreSQL.
-- Only write operations (INSERT, UPDATE, DELETE, SELECT FOR UPDATE) need locks.

-- You can observe this:
-- Session A:
BEGIN;
UPDATE accounts SET balance = 200 WHERE id = 1;
-- (do NOT commit yet)

-- Session B:
SELECT balance FROM accounts WHERE id = 1;
-- → Returns 100 (old version) immediately — not blocked
-- → If you do SELECT FOR UPDATE, it WILL block — waiting for A to commit.

-- This is the core trade-off:
-- Plain SELECT: never blocks, may see stale data
-- SELECT FOR UPDATE: blocks until writer commits, always sees current data
```

## Section 2: Row-Level Locks

**Q3. What are the four row-level lock modes — when do you use each?**

A: PostgreSQL provides four `SELECT ... FOR` lock strengths. They form a spectrum from "I want to read, don't let anyone change key fields" to "I'm about to update, block everyone else":

```sql
-- ── FOR KEY SHARE (weakest) ────────────────────────────────────────────────────
-- "I'm reading this row and I depend on its primary key not being deleted."
-- Blocks: FOR UPDATE, FOR NO KEY UPDATE (anything that would delete or change the PK).
-- Allows: other FOR KEY SHARE and FOR SHARE locks to coexist.
-- Use case: foreign key checks — Postgres uses this internally when you INSERT a row
--           that references another table via FK. It locks the parent row so it can't
--           be deleted while the FK check is in progress.

SELECT * FROM orders WHERE id = 42 FOR KEY SHARE;

-- ── FOR SHARE ─────────────────────────────────────────────────────────────────
-- "I'm reading this row and nothing should change it (keys OR values)."
-- Blocks: FOR UPDATE, FOR NO KEY UPDATE (any write lock).
-- Allows: other FOR SHARE and FOR KEY SHARE locks to coexist.
-- Use case: reading a row whose value you are about to use in a calculation,
--           where you want to ensure no concurrent update invalidates your read.

SELECT * FROM accounts WHERE id = 42 FOR SHARE;
-- → Other readers can still lock this row for share.
-- → Writers trying FOR UPDATE will block until we COMMIT.

-- ── FOR NO KEY UPDATE ─────────────────────────────────────────────────────────
-- "I'm about to update this row but NOT its primary key."
-- Blocks: FOR SHARE, FOR NO KEY UPDATE, FOR UPDATE (all write-compatible).
-- Allows: FOR KEY SHARE to coexist (FK checks can still proceed).
-- Use case: updating non-key columns. Postgres uses this for UPDATE statements
--           that don't touch the primary key — more permissive than FOR UPDATE.

SELECT * FROM accounts WHERE id = 42 FOR NO KEY UPDATE;
UPDATE accounts SET balance = 200 WHERE id = 42;

-- ── FOR UPDATE (strongest) ────────────────────────────────────────────────────
-- "I'm about to update or delete this row, including potentially its primary key."
-- Blocks: ALL other row locks (FOR KEY SHARE, FOR SHARE, FOR NO KEY UPDATE, FOR UPDATE).
-- Use case: pessimistic locking — check-then-act patterns where you cannot afford
--           any concurrent modification between your read and your write.

SELECT * FROM accounts WHERE id = 42 FOR UPDATE;
-- → ALL other transactions trying to lock this row in any mode will BLOCK.
-- → Plain SELECT (no FOR clause) still works — MVCC, returns the old version.
COMMIT; -- Releases the lock
```

```
Lock compatibility matrix (✓ = compatible, ✗ = blocks):

                  Held lock:
                  FOR KEY   FOR      FOR NO    FOR
Requested lock:   SHARE     SHARE    KEY UPD   UPDATE
─────────────────────────────────────────────────────
FOR KEY SHARE       ✓         ✓         ✓        ✗
FOR SHARE           ✓         ✓         ✗        ✗
FOR NO KEY UPDATE   ✓         ✗         ✗        ✗
FOR UPDATE          ✗         ✗         ✗        ✗
```

**Q4. What do `NOWAIT` and `SKIP LOCKED` do — and when are they essential in production?**

A: By default, a `SELECT FOR UPDATE` that hits a locked row will wait indefinitely (or until `lock_timeout` fires). `NOWAIT` and `SKIP LOCKED` change that blocking behaviour — they are critical for queue processors, rate limiters, and any high-throughput concurrent system:

```sql
-- ── Default behaviour: block until the lock is available ─────────────────────
BEGIN;
SELECT * FROM jobs WHERE status = 'pending' LIMIT 1 FOR UPDATE;
-- If another session holds a lock on the returned row, this BLOCKS here.
-- It waits until the other session commits or until lock_timeout expires.

-- ── NOWAIT: fail immediately if any row is already locked ─────────────────────
BEGIN;
SELECT * FROM jobs WHERE status = 'pending' LIMIT 1 FOR UPDATE NOWAIT;
-- If the row is locked by another session:
--   ERROR:  could not obtain lock on row in relation "jobs"
-- Your application must catch this error and retry with backoff.
-- Use case: interactive operations where blocking would feel like a hang.
--           User clicks "checkout" — if the cart item is being modified, fail fast.

-- ── SKIP LOCKED: silently skip rows that are already locked ───────────────────
BEGIN;
SELECT * FROM jobs WHERE status = 'pending' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED;
-- If row 1 is locked by worker A, this query skips it and returns row 2.
-- No blocking, no error — just moves on to the next available row.
-- COMMIT or ROLLBACK releases the lock on the row this session holds.
-- Use case: job queues — N workers each claim a different row simultaneously.

-- ── Job queue pattern (the canonical SKIP LOCKED use case) ───────────────────
-- N worker processes all run this concurrently — no worker claims the same job:

CREATE TABLE jobs (
    id          BIGSERIAL PRIMARY KEY,
    status      TEXT NOT NULL DEFAULT 'pending', -- pending, processing, done, failed
    payload     JSONB,
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    attempts    INT DEFAULT 0
);

-- Worker process (runs in a loop):
BEGIN;

-- Atomically claim exactly one pending job, skip any already claimed by other workers:
UPDATE jobs
SET    status = 'processing', attempts = attempts + 1
WHERE  id = (
    SELECT id
    FROM   jobs
    WHERE  status = 'pending'
    ORDER  BY created_at    -- FIFO ordering
    LIMIT  1
    FOR    UPDATE SKIP LOCKED
)
RETURNING *;

-- If no rows returned → no work available, sleep and retry.
-- If a row returned → process it, then:
UPDATE jobs SET status = 'done'   WHERE id = :claimed_id;  -- success
-- OR:
UPDATE jobs SET status = 'failed' WHERE id = :claimed_id;  -- failure

COMMIT; -- Lock released

-- ── SKIP LOCKED vs NOWAIT: which to use? ─────────────────────────────────────
--
-- SKIP LOCKED:
--   ✓ Ideal for queue consumers — work on any available item
--   ✓ No errors to handle — silently skips contested rows
--   ✗ Does NOT guarantee ordering — a FIFO queue with SKIP LOCKED can
--     process item 2 before item 1 if item 1 is being processed
--   ✗ Not suitable when you MUST process a specific row (use NOWAIT)
--
-- NOWAIT:
--   ✓ When you need a specific row or fail (user's own cart, specific order)
--   ✓ Makes lock contention visible as an application error (catchable)
--   ✗ Caller must implement retry logic
--   ✗ Under high contention, many retries degrade throughput

-- ── lock_timeout: time-limited waiting ───────────────────────────────────────
-- A middle ground between indefinite blocking and NOWAIT:
SET lock_timeout = '2s'; -- Wait up to 2 seconds, then error
SELECT * FROM accounts WHERE id = 42 FOR UPDATE;
-- → Blocks for up to 2s, then:
--   ERROR:  canceling statement due to lock timeout
```

**Q5. How do you implement pessimistic locking with TypeORM in a NestJS service?**

A: TypeORM exposes row-level locks through the `setLock()` query builder method and the `lock` option on `findOne`. The key is ensuring the lock acquisition and the subsequent write happen in the same transaction:

```typescript
import { Injectable }            from '@nestjs/common';
import { InjectRepository }      from '@nestjs/typeorm';
import { Repository, DataSource } from 'typeorm';
import { Account }               from './account.entity';

@Injectable()
export class AccountService {
    constructor(
        @InjectRepository(Account)
        private readonly accountRepo: Repository<Account>,
        private readonly dataSource:  DataSource,
    ) {}

    // ── FOR UPDATE via QueryBuilder ───────────────────────────────────────────
    async transferFunds(
        fromId: number,
        toId:   number,
        amount: number,
    ): Promise<void> {
        await this.dataSource.transaction(async (manager) => {
            // Lock BOTH rows in consistent order (lower ID first) to prevent deadlock:
            const [first, second] = fromId < toId
                ? [fromId, toId]
                : [toId, fromId];

            // Acquire FOR UPDATE locks — blocks until both are available:
            const accounts = await manager
                .createQueryBuilder(Account, 'a')
                .setLock('pessimistic_write')     // → FOR UPDATE
                .where('a.id IN (:...ids)', { ids: [first, second] })
                .orderBy('a.id', 'ASC')           // Consistent lock order
                .getMany();

            const from = accounts.find(a => a.id === fromId)!;
            const to   = accounts.find(a => a.id === toId)!;

            if (from.balance < amount) {
                throw new Error('Insufficient funds');
            }

            from.balance -= amount;
            to.balance   += amount;

            await manager.save([from, to]);
        });
    }

    // ── Lock modes available in TypeORM ──────────────────────────────────────
    async demonstrateLockModes(id: number): Promise<void> {
        await this.dataSource.transaction(async (manager) => {
            // 'pessimistic_read'        → FOR SHARE
            // Prevents concurrent writes, allows concurrent reads with the same lock.
            await manager
                .createQueryBuilder(Account, 'a')
                .setLock('pessimistic_read')
                .where('a.id = :id', { id })
                .getOne();

            // 'pessimistic_write'       → FOR UPDATE
            // Prevents all concurrent row locks.
            await manager
                .createQueryBuilder(Account, 'a')
                .setLock('pessimistic_write')
                .where('a.id = :id', { id })
                .getOne();

            // 'pessimistic_partial_write' → FOR NO KEY UPDATE
            // Prevents concurrent write locks but allows FOR KEY SHARE.
            await manager
                .createQueryBuilder(Account, 'a')
                .setLock('pessimistic_partial_write')
                .where('a.id = :id', { id })
                .getOne();

            // 'pessimistic_write_or_fail' → FOR UPDATE NOWAIT
            // Immediately throws if row is locked. Catch LockNotAvailableError.
            try {
                await manager
                    .createQueryBuilder(Account, 'a')
                    .setLock('pessimistic_write_or_fail')
                    .where('a.id = :id', { id })
                    .getOne();
            } catch (err) {
                // TypeORM wraps the PostgreSQL error in LockNotAvailableError:
                if (err.name === 'LockNotAvailableError') {
                    throw new ConflictException('Resource is being modified — try again');
                }
                throw err;
            }

            // 'skip_locked' → FOR UPDATE SKIP LOCKED
            // Returns null if the row is locked (skips it).
            const row = await manager
                .createQueryBuilder(Account, 'a')
                .setLock('skip_locked')
                .where('a.id = :id', { id })
                .getOne();
            // row is null if locked by another transaction.
        });
    }

    // ── findOne with lock (simpler syntax for single-row cases) ──────────────
    async withdraw(accountId: number, amount: number): Promise<Account> {
        return this.dataSource.transaction(async (manager) => {
            // Lock the account row before reading balance:
            const account = await manager.findOne(Account, {
                where: { id: accountId },
                lock:  { mode: 'pessimistic_write' }, // FOR UPDATE
            });

            if (!account) throw new NotFoundException('Account not found');
            if (account.balance < amount) throw new BadRequestException('Insufficient funds');

            account.balance -= amount;
            return manager.save(account);
            // Lock is released when the transaction commits (end of this callback).
        });
    }
}
```

**Q6. What is optimistic locking — how does it differ from pessimistic, and when do you choose each?**

A: Pessimistic locking acquires a database lock before reading, preventing any concurrent modification. Optimistic locking acquires no lock — it detects a conflict at write time using a version number, then rejects the write if someone else modified the row first:

```typescript
// ── Optimistic locking: entity with @VersionColumn ────────────────────────────
import { Entity, PrimaryGeneratedColumn, Column, VersionColumn } from 'typeorm';

@Entity()
export class Product {
    @PrimaryGeneratedColumn()
    id: number;

    @Column()
    name: string;

    @Column('decimal', { precision: 10, scale: 2 })
    price: number;

    @Column({ default: 0 })
    stock: number;

    @VersionColumn()       // TypeORM auto-manages this column
    version: number;       // Starts at 1, incremented on every UPDATE
}

// How @VersionColumn works at the SQL level:
-- First read:   SELECT id, name, price, stock, version FROM products WHERE id = 1;
--               → version = 5
--
-- TypeORM UPDATE with version check:
--   UPDATE products
--   SET    stock = 99, version = 6
--   WHERE  id = 1
--   AND    version = 5;   ← Only succeeds if version hasn't changed
--
-- If another transaction already updated the row (version is now 6):
--   UPDATE ... WHERE id = 1 AND version = 5 → 0 rows affected
--   TypeORM throws: OptimisticLockVersionMismatchError

// ── Optimistic locking in service ────────────────────────────────────────────
@Injectable()
export class ProductService {
    constructor(
        @InjectRepository(Product)
        private readonly productRepo: Repository<Product>,
        private readonly dataSource:  DataSource,
    ) {}

    async updatePrice(id: number, newPrice: number, knownVersion: number): Promise<Product> {
        return this.dataSource.transaction(async (manager) => {
            // Read the current state:
            const product = await manager.findOne(Product, { where: { id } });
            if (!product) throw new NotFoundException();

            // Client must provide the version they read:
            if (product.version !== knownVersion) {
                throw new ConflictException('Product was modified — please reload and retry');
            }

            product.price = newPrice;
            // TypeORM's save() uses the version column internally:
            // UPDATE products SET price = ?, version = version + 1
            // WHERE id = ? AND version = ?  ← if this fails, TypeORM throws
            return manager.save(product);
        });
    }

    // ── Retry wrapper for optimistic locking ──────────────────────────────────
    // Optimistic locking requires application-level retry on conflict:
    async updateWithRetry(
        id:       number,
        newPrice: number,
        maxRetries = 3,
    ): Promise<Product> {
        for (let attempt = 1; attempt <= maxRetries; attempt++) {
            try {
                const product = await this.productRepo.findOneOrFail({ where: { id } });
                product.price = newPrice;
                return await this.productRepo.save(product);
                // TypeORM throws OptimisticLockVersionMismatchError on conflict
            } catch (err) {
                if (err.name === 'OptimisticLockVersionMismatchError' && attempt < maxRetries) {
                    // Exponential backoff before retry:
                    await new Promise(r => setTimeout(r, 50 * Math.pow(2, attempt)));
                    continue;
                }
                throw err; // Max retries exceeded or non-recoverable error
            }
        }
        throw new ConflictException('Could not update product after retries');
    }
}
```

```
Pessimistic vs Optimistic: choosing the right one

┌──────────────────────────┬────────────────────────────┬────────────────────────────┐
│ Factor                   │ Pessimistic (FOR UPDATE)   │ Optimistic (@VersionColumn)│
├──────────────────────────┼────────────────────────────┼────────────────────────────┤
│ Lock timing              │ On read                    │ On write only              │
│ Conflict detection       │ Preventive (blocks writer) │ Reactive (writer fails)    │
│ DB connections held      │ Longer (lock held during   │ Shorter (no lock on read)  │
│                          │ processing)                │                            │
│ Retry logic needed       │ No (blocked, then proceed) │ Yes (must re-read + retry) │
│ Throughput under conflict│ Low (all block on one lock)│ High (no blocking)         │
│ Ideal conflict rate      │ High (conflicts are common)│ Low (conflicts are rare)   │
│ Risk of deadlock         │ Yes (must manage order)    │ No (no mutual blocking)    │
│ Suitable for             │ Financial transfers, stock │ CMS edits, profile updates,│
│                          │ deductions, seat booking   │ inventory reads, reports   │
└──────────────────────────┴────────────────────────────┴────────────────────────────┘
```

## Section 3: Table-Level Locks

**Q7. What are PostgreSQL table-level lock modes — when does each arise and how do they conflict?**

A: Table-level locks operate on the entire table, not individual rows. Most are acquired automatically by DML statements. Understanding them is critical when running `ALTER TABLE`, `VACUUM`, `CREATE INDEX`, and application writes concurrently:

```sql
-- ── The 8 table-level lock modes (weakest to strongest) ───────────────────────

-- 1. ACCESS SHARE
--    Acquired by: SELECT (plain read)
--    Conflicts with: ACCESS EXCLUSIVE only
--    Meaning: "I am reading the table structure — don't drop or rewrite the table."
SELECT * FROM orders;   -- Acquires ACCESS SHARE automatically

-- 2. ROW SHARE
--    Acquired by: SELECT FOR UPDATE, SELECT FOR SHARE
--    Conflicts with: EXCLUSIVE, ACCESS EXCLUSIVE
SELECT * FROM orders WHERE id = 1 FOR UPDATE;  -- Acquires ROW SHARE on the table

-- 3. ROW EXCLUSIVE
--    Acquired by: INSERT, UPDATE, DELETE
--    Conflicts with: SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE
UPDATE orders SET status = 'shipped' WHERE id = 1;  -- Acquires ROW EXCLUSIVE

-- 4. SHARE UPDATE EXCLUSIVE
--    Acquired by: VACUUM (non-FULL), ANALYZE, CREATE INDEX CONCURRENTLY,
--                 ALTER TABLE (some forms), REINDEX CONCURRENTLY
--    Conflicts with: itself and stronger modes
--    Important: allows concurrent reads AND writes — safe for online maintenance.
CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);
-- → Acquires SHARE UPDATE EXCLUSIVE — does NOT block INSERT/UPDATE/DELETE

-- 5. SHARE
--    Acquired by: CREATE INDEX (non-concurrent)
--    Conflicts with: ROW EXCLUSIVE and stronger
--    Critical: blocks ALL writes while the index is being built.
CREATE INDEX idx_orders_status ON orders(status);
-- → Acquires SHARE lock → all INSERT/UPDATE/DELETE on 'orders' BLOCK
-- → ALWAYS use CREATE INDEX CONCURRENTLY in production to avoid this.

-- 6. SHARE ROW EXCLUSIVE
--    Acquired by: CREATE TRIGGER, some ALTER TABLE forms
--    Conflicts with: ROW EXCLUSIVE and stronger (allows reads, blocks writes)

-- 7. EXCLUSIVE
--    Acquired by: REFRESH MATERIALIZED VIEW (non-concurrent)
--    Conflicts with: ROW SHARE and stronger
REFRESH MATERIALIZED VIEW my_view;
-- → Blocks queries against the materialized view during refresh.
-- → Use REFRESH MATERIALIZED VIEW CONCURRENTLY to avoid blocking readers.

-- 8. ACCESS EXCLUSIVE (strongest)
--    Acquired by: DROP TABLE, TRUNCATE, REINDEX (non-concurrent),
--                 ALTER TABLE (most forms), LOCK TABLE (default)
--    Conflicts with: EVERYTHING — even plain SELECT blocks.
--    This is the only lock that blocks readers.
ALTER TABLE orders ADD COLUMN notes TEXT;
-- → Acquires ACCESS EXCLUSIVE → ALL queries (even SELECT) on 'orders' BLOCK.
-- → On large tables with heavy traffic, this can cause catastrophic lock queues.

-- ── The lock queue problem ────────────────────────────────────────────────────
-- A single ACCESS EXCLUSIVE lock queues ALL subsequent lock requests:
--
-- Session A: long SELECT (holds ACCESS SHARE)
-- Session B: ALTER TABLE (wants ACCESS EXCLUSIVE — waits for A)
-- Sessions C, D, E: SELECTs — want ACCESS SHARE, BLOCKED behind B
--
-- Even though C,D,E are compatible with A, they queue behind B.
-- B "locks the queue" — a short ALTER TABLE can make an entire table inaccessible
-- for the duration of all in-flight queries PLUS the alter itself.
--
-- Mitigation: set lock_timeout before dangerous DDL:
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN notes TEXT;
-- → If the table is busy after 2s, the ALTER fails cleanly (not queue-blocking forever).
```

```sql
-- ── Explicit LOCK TABLE (rare in application code) ────────────────────────────
-- Used when you need to prevent any writes for the duration of a transaction —
-- for example, before a bulk export or a full-table rewrite.

BEGIN;
LOCK TABLE orders IN SHARE MODE;
-- → Blocks INSERT/UPDATE/DELETE on orders for the duration of this transaction.
-- → Other SELECTs (ACCESS SHARE) are still allowed.
-- → Use sparingly — this is a heavy operation.

-- Export all orders knowing nothing will change:
COPY (SELECT * FROM orders ORDER BY id) TO '/tmp/orders_export.csv' CSV HEADER;
COMMIT;  -- Lock released

-- ── Table-level lock compatibility matrix (simplified) ───────────────────────
-- ACCESS SHARE:     conflicts only with ACCESS EXCLUSIVE
-- ROW EXCLUSIVE:    conflicts with SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE
-- ACCESS EXCLUSIVE: conflicts with EVERYTHING

-- Rule of thumb for interviews:
-- Regular DML (INSERT/UPDATE/DELETE) → ROW EXCLUSIVE → compatible with each other
-- CREATE INDEX (non-concurrent)       → SHARE → blocks all writes (production danger)
-- ALTER TABLE                         → ACCESS EXCLUSIVE → blocks everyone (production danger)
-- CREATE INDEX CONCURRENTLY           → SHARE UPDATE EXCLUSIVE → safe for production
```

**Q8. How do you safely run schema migrations on a live production database without downtime?**

A: Most `ALTER TABLE` operations acquire `ACCESS EXCLUSIVE` locks, making the table completely inaccessible during the migration. The solution is a sequence of small, lock-minimal steps:

```sql
-- ── DANGEROUS: Adding a column with a DEFAULT (pre-PostgreSQL 11) ──────────────
-- In PostgreSQL < 11, this rewrites the ENTIRE table:
ALTER TABLE orders ADD COLUMN priority INT NOT NULL DEFAULT 0;
-- → ACCESS EXCLUSIVE for the entire table rewrite duration.
-- → On a 100M row table: minutes of downtime.

-- ── SAFE (PostgreSQL 11+): Constant defaults are instant ─────────────────────
-- PostgreSQL 11+ stores the default in the catalog, no table rewrite:
ALTER TABLE orders ADD COLUMN priority INT NOT NULL DEFAULT 0;
-- → ACCESS EXCLUSIVE held, but operation is near-instant (metadata only).

-- ── SAFE: Adding a nullable column (all versions) ────────────────────────────
-- Adding a nullable column with no default is always instant:
ALTER TABLE orders ADD COLUMN notes TEXT;   -- Near-instant, brief ACCESS EXCLUSIVE
-- Back-fill later in batches:
UPDATE orders SET notes = '' WHERE notes IS NULL AND id BETWEEN 1 AND 10000;
-- ... repeat in batches

-- ── SAFE: Adding a NOT NULL constraint without locking ────────────────────────
-- PostgreSQL 12+ supports NOT VALID constraints + VALIDATE separately:

-- Step 1: Add constraint but skip validation of existing rows (near-instant lock):
ALTER TABLE orders ADD CONSTRAINT chk_amount_positive
    CHECK (amount > 0) NOT VALID;
-- → ACCESS EXCLUSIVE but very brief — no row scanning.

-- Step 2: Validate existing rows (acquires SHARE UPDATE EXCLUSIVE — non-blocking):
ALTER TABLE orders VALIDATE CONSTRAINT chk_amount_positive;
-- → Scans existing rows without blocking writes.

-- ── SAFE: Creating an index without blocking writes ───────────────────────────
-- WRONG for production:
CREATE INDEX idx_orders_user ON orders(user_id);
-- → SHARE lock — all INSERT/UPDATE/DELETE block during index build.

-- CORRECT for production:
CREATE INDEX CONCURRENTLY idx_orders_user ON orders(user_id);
-- → SHARE UPDATE EXCLUSIVE — concurrent writes are allowed during build.
-- → Takes longer, uses more resources, but zero downtime.
-- → One risk: if the build fails, the index is left INVALID — drop and retry.

-- ── SAFE: Adding a foreign key without full-table lock ────────────────────────
-- Step 1: Add FK with NOT VALID (validates new rows, skips existing):
ALTER TABLE order_items ADD CONSTRAINT fk_order
    FOREIGN KEY (order_id) REFERENCES orders(id) NOT VALID;
-- → Brief ACCESS EXCLUSIVE.

-- Step 2: Validate existing rows (SHARE UPDATE EXCLUSIVE, non-blocking):
ALTER TABLE order_items VALIDATE CONSTRAINT fk_order;

-- ── lock_timeout as a safety net for all migrations ───────────────────────────
-- Always set lock_timeout before DDL in production:
SET lock_timeout = '5s';
SET statement_timeout = '30s';
ALTER TABLE orders ADD COLUMN metadata JSONB;
-- → If the table is busy for 5s, the statement fails (not blocks forever).
-- → Retry during a low-traffic window.
```

## Section 4: Advisory Locks

**Q9. What are advisory locks — what makes them fundamentally different from row and table locks?**

A: Advisory locks are application-defined locks stored by PostgreSQL but carrying no intrinsic meaning to the database engine. Unlike row and table locks (which prevent conflicting SQL operations), advisory locks only prevent other advisory locks on the same key. What "the key" means is entirely up to your application:

```sql
-- ── Advisory lock fundamentals ────────────────────────────────────────────────
-- An advisory lock is identified by a 64-bit integer (or two 32-bit integers).
-- PostgreSQL stores it in shared memory — no table, no row, no disk.
-- It has NO effect on DML — you can INSERT/UPDATE/DELETE freely even if an
-- advisory lock is held on the same key. It is purely cooperative.
-- Two transactions must BOTH check the same lock key to coordinate.

-- ── Two forms: session-level vs transaction-level ──────────────────────────────

-- SESSION-LEVEL: persists until explicitly released OR the session ends.
-- Survives COMMIT and ROLLBACK within the session.
SELECT pg_advisory_lock(12345);           -- Exclusive session lock on key 12345
SELECT pg_advisory_lock_shared(12345);    -- Shared session lock on key 12345
SELECT pg_advisory_unlock(12345);         -- Must be called to release
SELECT pg_advisory_unlock_all();          -- Release all session advisory locks

-- TRANSACTION-LEVEL: automatically released at the end of the transaction.
-- MUCH preferred in application code — no risk of leaking a lock.
BEGIN;
SELECT pg_advisory_xact_lock(12345);          -- Exclusive, released on COMMIT/ROLLBACK
SELECT pg_advisory_xact_lock_shared(12345);   -- Shared, released on COMMIT/ROLLBACK
COMMIT;   -- Lock released automatically here

-- ── Non-blocking variants ─────────────────────────────────────────────────────
-- pg_try_advisory_lock: returns TRUE if acquired, FALSE if already held.
SELECT pg_try_advisory_lock(12345);           -- session level, exclusive, non-blocking
SELECT pg_try_advisory_xact_lock(12345);      -- transaction level, exclusive, non-blocking
SELECT pg_try_advisory_lock_shared(12345);    -- session level, shared, non-blocking
SELECT pg_try_advisory_xact_lock_shared(12345); -- transaction level, shared, non-blocking

-- ── Two-integer form (avoids collisions between subsystems) ──────────────────
-- Instead of a single BIGINT key, use (class, id) — two INT4 values.
-- Namespace your locks to prevent accidental collisions:
SELECT pg_advisory_xact_lock(1, 42);     -- Class 1 = "user locks", ID 42
SELECT pg_advisory_xact_lock(2, 42);     -- Class 2 = "report locks", ID 42
-- These are DIFFERENT locks even though both have ID 42.
```

**Q10. What are the canonical use cases for advisory locks — how do you implement each?**

A: Advisory locks are the right tool when you need mutual exclusion over a logical concept (a user's action, a job type, a resource identifier) rather than a specific database row:

```sql
-- ── Use Case 1: Per-user rate limiting / one-at-a-time user action ─────────────
-- Problem: User 42 clicks "Generate Report" twice. Two concurrent requests
-- start generating the same expensive report — wasteful or incorrect.
-- Solution: Lock on the user ID before starting the report generation.

BEGIN;
-- Try to acquire an exclusive lock for user 42's report action:
SELECT pg_try_advisory_xact_lock(
    hashtext('report'),  -- Namespace: convert string to int
    42                   -- User ID
);
-- → Returns TRUE: we have the lock, proceed.
-- → Returns FALSE: another session is already generating a report for user 42.
--   Abort the duplicate request.

-- The lock is held for the duration of the transaction.
-- The second request fails fast without even starting the expensive work.
COMMIT; -- Lock released automatically.

-- ── Use Case 2: Distributed cron job — exactly-once execution ─────────────────
-- Problem: You run 3 application instances. A nightly job should run on exactly
-- one instance, not all three simultaneously.

BEGIN;
-- Use a well-known constant as the lock key (same on all instances):
SELECT pg_try_advisory_xact_lock(1234567890); -- Key = "nightly_cleanup"

-- → Instance A acquires: runs the job.
-- → Instances B and C: pg_try returns FALSE → skip this run.

-- Run the cleanup only if we got the lock:
-- (check the result of pg_try_advisory_xact_lock in application code)
DELETE FROM sessions WHERE expires_at < NOW();
DELETE FROM audit_logs WHERE created_at < NOW() - INTERVAL '90 days';
COMMIT; -- Lock released; next scheduled run will compete for the lock again.

-- ── Use Case 3: Long-running migration / background job coordination ───────────
-- SESSION-level lock is appropriate here because the work spans multiple transactions.

-- Worker process:
SELECT pg_advisory_lock(9999);   -- Blocks until acquired (session level)
-- → Only one worker holds key 9999 at a time.
-- → Do the long work across many transactions:
DO $$
DECLARE batch_id BIGINT;
BEGIN
    LOOP
        -- Process one batch per transaction:
        BEGIN;
        UPDATE products
        SET    price = price * 1.05
        WHERE  id IN (
            SELECT id FROM products WHERE migrated = FALSE LIMIT 1000
        );
        EXIT WHEN NOT FOUND;
        COMMIT;
    END LOOP;
END $$;
SELECT pg_advisory_unlock(9999); -- Release when done

-- ── Use Case 4: Inventory reservation without SELECT FOR UPDATE ───────────────
-- An advisory lock on a product ID ensures only one reservation at a time,
-- without locking the entire products row (allows reads to proceed freely).

-- Reservation service (pseudocode, runs in application):
BEGIN;
PERFORM pg_advisory_xact_lock(hashtext('inventory'), :product_id);
-- Lock acquired — check availability and reserve:
SELECT stock FROM products WHERE id = :product_id;
-- If stock > 0:
UPDATE products SET stock = stock - :quantity WHERE id = :product_id;
INSERT INTO reservations (...) VALUES (...);
COMMIT; -- Lock released; next reservation can proceed.

-- ── Use Case 5: Leader election across application instances ──────────────────
-- One application instance becomes the "leader" and does special work.
-- Use a session-level advisory lock — the lock is held as long as the session lives.
-- If the leader crashes (session ends), PostgreSQL automatically releases the lock.
-- Another instance can then acquire it.

-- Each instance runs on startup:
SELECT pg_try_advisory_lock(hashtext('leader_election'));
-- → TRUE: this instance is the leader. Do leader-only work.
-- → FALSE: another instance is the leader. Run as follower.
-- When the leader's DB connection drops: lock is auto-released.
-- Next instance to try pg_try_advisory_lock will acquire it.

-- ── Use Case 6: Generating a gapless sequence (invoice numbers) ───────────────
-- AUTO_INCREMENT leaves gaps on rollback. Advisory locks can create gapless sequences.

BEGIN;
SELECT pg_advisory_xact_lock(hashtext('invoice_number_sequence'));
-- Only one transaction at a time can generate an invoice number:
SELECT COALESCE(MAX(invoice_number), 0) + 1 AS next_number FROM invoices;
-- Use this number for the new invoice:
INSERT INTO invoices (invoice_number, ...) VALUES (:next_number, ...);
COMMIT;
-- Gapless because: (1) only one generator at a time (lock), and
--                  (2) we INSERT in the same transaction (or rollback both).
```

**Q11. How do you implement advisory locks in TypeORM / NestJS — and how do you handle lock leakage?**

A: Advisory locks require raw SQL in TypeORM since there is no built-in abstraction. The key engineering concern is ensuring every acquired lock is always released — even on error:

```typescript
import { Injectable }               from '@nestjs/common';
import { DataSource, QueryRunner }  from 'typeorm';

@Injectable()
export class AdvisoryLockService {
    constructor(private readonly dataSource: DataSource) {}

    // ── Transaction-level advisory lock (preferred) ───────────────────────────
    // Released automatically on COMMIT or ROLLBACK — impossible to leak.
    async withExclusiveLock<T>(
        lockKey:  number,
        callback: (queryRunner: QueryRunner) => Promise<T>,
    ): Promise<T> {
        const qr = this.dataSource.createQueryRunner();
        await qr.connect();
        await qr.startTransaction();

        try {
            // Acquire the transaction-level advisory lock (blocks if not available):
            await qr.query('SELECT pg_advisory_xact_lock($1)', [lockKey]);

            // Run the protected work:
            const result = await callback(qr);
            await qr.commitTransaction();
            return result;
            // Lock released automatically on commit.
        } catch (err) {
            await qr.rollbackTransaction();
            // Lock released automatically on rollback.
            throw err;
        } finally {
            await qr.release(); // Return connection to pool
        }
    }

    // ── Non-blocking try variant ──────────────────────────────────────────────
    async tryWithExclusiveLock<T>(
        lockKey:  number,
        callback: (queryRunner: QueryRunner) => Promise<T>,
    ): Promise<T | null> {
        const qr = this.dataSource.createQueryRunner();
        await qr.connect();
        await qr.startTransaction();

        try {
            const [{ pg_try_advisory_xact_lock: acquired }] = await qr.query(
                'SELECT pg_try_advisory_xact_lock($1)',
                [lockKey],
            );

            if (!acquired) {
                await qr.rollbackTransaction();
                return null; // Lock not available — caller decides what to do
            }

            const result = await callback(qr);
            await qr.commitTransaction();
            return result;
        } catch (err) {
            await qr.rollbackTransaction();
            throw err;
        } finally {
            await qr.release();
        }
    }

    // ── Namespaced lock key helper ────────────────────────────────────────────
    // Generates a stable integer from a namespace + ID pair.
    // Uses PostgreSQL's hashtext to avoid collisions between subsystems.
    async getLockKey(namespace: string, id: number | string): Promise<number> {
        const [{ key }] = await this.dataSource.query(
            `SELECT (hashtext($1) << 32) | (hashtext($2::text) & x'7fffffff'::int) AS key`,
            [namespace, String(id)],
        );
        return parseInt(key, 10);
    }

    // ── Session-level lock (use sparingly — risk of leak) ─────────────────────
    // Required when work spans multiple transactions.
    // MUST be explicitly released — ensure finally block always runs.
    async withSessionLock<T>(
        lockKey:  bigint,
        callback: () => Promise<T>,
    ): Promise<T> {
        const qr = this.dataSource.createQueryRunner();
        await qr.connect();

        try {
            await qr.query('SELECT pg_advisory_lock($1)', [lockKey.toString()]);
            // Lock acquired — NOT tied to any transaction.
            return await callback();
        } finally {
            // Release ALWAYS — even if callback throws.
            // Failure to release here means the lock persists until this session ends.
            await qr.query('SELECT pg_advisory_unlock($1)', [lockKey.toString()]);
            await qr.release();
        }
    }
}

// ── Usage in a service ────────────────────────────────────────────────────────
@Injectable()
export class ReportService {
    constructor(
        private readonly lockService: AdvisoryLockService,
        private readonly reportRepo:  ReportRepository,
    ) {}

    // Generate a report for a user — exactly once, even under concurrent requests:
    async generateReport(userId: number): Promise<Report> {
        const lockKey = await this.lockService.getLockKey('report:generate', userId);

        const result = await this.lockService.tryWithExclusiveLock(lockKey, async (qr) => {
            // Check if a recent report already exists (may have been generated
            // by another instance while we waited for the lock — shouldn't happen
            // with try, but defensive check is good practice):
            const existing = await this.reportRepo.findRecent(userId, qr);
            if (existing) return existing;

            return this.reportRepo.generate(userId, qr);
        });

        if (result === null) {
            throw new ConflictException('Report generation already in progress for this user');
        }
        return result;
    }
}

// ── Detecting lock leaks in development ───────────────────────────────────────
// Query pg_locks to see all advisory locks currently held:

}
```

## Section 5: Deadlocks

**Q12. What causes deadlocks and how do you prevent them?**

A: A deadlock occurs when two transactions each hold a lock the other needs, and both are waiting indefinitely. PostgreSQL detects deadlocks automatically (within `deadlock_timeout`, default 1s) and aborts one transaction:

```
Classic deadlock (two transactions, two rows):

  Time │ Transaction A                    Transaction B
  ─────┼──────────────────────────────────────────────────────────
    1  │ BEGIN
    2  │ SELECT * FROM accounts           BEGIN
       │ WHERE id = 1 FOR UPDATE;
       │ → Lock on row 1 acquired ✓
    3  │                                  SELECT * FROM accounts
       │                                  WHERE id = 2 FOR UPDATE;
       │                                  → Lock on row 2 acquired ✓
    4  │ SELECT * FROM accounts
       │ WHERE id = 2 FOR UPDATE;
       │ → Lock on row 2: BLOCKED
       │   (B holds it)
    5  │                                  SELECT * FROM accounts
       │                                  WHERE id = 1 FOR UPDATE;
       │                                  → Lock on row 1: BLOCKED
       │                                    (A holds it)
    6  │ (deadlock detected by PostgreSQL after deadlock_timeout)
       │ ERROR: deadlock detected
       │ DETAIL: Process N waits for ShareLock on transaction X;
       │         blocked by process M.
       │         Process M waits for ShareLock on transaction Y;
       │         blocked by process N.
       │ HINT: See server log for query details.
       │ → Transaction A is aborted (the "victim")
       │                                  → Transaction B proceeds ✓
```

```sql
-- ── Prevention strategy 1: consistent lock ordering (most important) ──────────
-- ALWAYS acquire locks in the same order across all transactions.
-- If A and B both lock rows in ascending ID order, a deadlock is impossible.

-- WRONG: Transaction A locks 1 then 2; Transaction B locks 2 then 1.
-- CORRECT:

-- Application code must sort IDs before locking:
-- TypeORM example: lockIds.sort((a, b) => a - b) before querying

-- SQL example:
BEGIN;
SELECT * FROM accounts
WHERE id IN (1, 2)
ORDER BY id ASC    -- ← Consistent order: lowest ID first
FOR UPDATE;
-- Both transactions now request row 1 first, then row 2.
-- One blocks waiting for row 1 — no circular dependency.

-- ── Prevention strategy 2: lock all rows in a single query ───────────────────
-- Instead of two separate SELECT FOR UPDATE, lock both rows in one query.
-- PostgreSQL acquires all locks atomically within a single statement.
SELECT * FROM accounts WHERE id IN (:id1, :id2) FOR UPDATE;
-- No intermediate state where A holds one and B holds the other.

-- ── Prevention strategy 3: short transactions ─────────────────────────────────
-- The longer a transaction holds locks, the more likely it overlaps with others.
-- Do not: open a transaction, call an external API, then write to the DB.
-- Do: prepare all data, then open a transaction, write, commit immediately.

-- ── Prevention strategy 4: SELECT FOR UPDATE with NOWAIT and retry ────────────
-- Instead of waiting (and potentially deadlocking), fail fast and retry:
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
-- If this fails: retry after brief backoff.
-- Contention is visible as errors rather than deadlocks.

-- ── Handling a deadlock in application code (TypeORM) ─────────────────────────
async function transferWithDeadlockRetry(
    dataSource: DataSource,
    fromId: number,
    toId: number,
    amount: number,
    maxRetries = 3,
): Promise<void> {
    const [first, second] = [fromId, toId].sort((a, b) => a - b); // Consistent order

    for (let attempt = 1; attempt <= maxRetries; attempt++) {
        try {
            await dataSource.transaction(async (manager) => {
                const accounts = await manager
                    .createQueryBuilder(Account, 'a')
                    .where('a.id IN (:...ids)', { ids: [first, second] })
                    .orderBy('a.id', 'ASC')          // Must match sort order above
                    .setLock('pessimistic_write')
                    .getMany();

                const from = accounts.find(a => a.id === fromId)!;
                const to   = accounts.find(a => a.id === toId)!;

                from.balance -= amount;
                to.balance   += amount;
                await manager.save([from, to]);
            });
            return; // Success
        } catch (err) {
            // PostgreSQL deadlock error code: 40P01
            const isDeadlock = err.code === '40P01'
                             || err.message?.includes('deadlock detected');

            if (isDeadlock && attempt < maxRetries) {
                const backoff = 50 * Math.pow(2, attempt) + Math.random() * 50;
                await new Promise(r => setTimeout(r, backoff)); // Jittered backoff
                continue;
            }
            throw err; // Non-deadlock error or max retries exceeded
        }
    }
}

-- ── Monitoring deadlocks in PostgreSQL ────────────────────────────────────────
-- Deadlocks are logged when log_lock_waits = on and deadlock_timeout is set.
-- In postgresql.conf:
--   deadlock_timeout = 1s          -- Default; detection interval
--   log_lock_waits = on            -- Log waits longer than deadlock_timeout
--   log_min_messages = 'WARNING'   -- Ensure deadlock messages are logged

-- Query current lock waits:
SELECT
    blocked.pid                       AS blocked_pid,
    blocked.query                     AS blocked_query,
    blocking.pid                      AS blocking_pid,
    blocking.query                    AS blocking_query,
    now() - blocked.query_start       AS wait_duration
FROM pg_stat_activity AS blocked
JOIN pg_stat_activity AS blocking
    ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.cardinality(pg_blocking_pids(blocked.pid)) > 0;
```

## Section 6: Observability and Debugging

**Q13. How do you observe and diagnose lock contention in a running PostgreSQL database?**

A: Lock contention is often invisible until it becomes a crisis. PostgreSQL exposes lock state through system views — knowing how to read them is essential in production:

```sql
-- ── pg_locks: all current locks ───────────────────────────────────────────────
SELECT
    pid,
    locktype,           -- relation | transactionid | tuple | advisory | etc.
    relation::regclass, -- Table name (for relation locks)
    mode,               -- Lock mode (AccessShareLock, RowExclusiveLock, etc.)
    granted,            -- TRUE = held, FALSE = waiting
    transactionid,      -- Transaction being locked (for transactionid locktype)
    classid, objid      -- Advisory lock key (for advisory locktype)
FROM pg_locks
WHERE NOT granted      -- Show only WAITING locks (the interesting ones)
ORDER BY pid;

-- ── pg_stat_activity + pg_locks: who is blocking whom ────────────────────────
SELECT
    blocking.pid                        AS blocking_pid,
    blocking.usename                    AS blocking_user,
    blocking.application_name           AS blocking_app,
    substring(blocking.query, 1, 80)    AS blocking_query,
    blocked.pid                         AS blocked_pid,
    blocked.usename                     AS blocked_user,
    now() - blocked.state_change        AS blocked_duration,
    substring(blocked.query, 1, 80)     AS blocked_query
FROM pg_stat_activity AS blocked
JOIN pg_stat_activity AS blocking
    ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.wait_event_type = 'Lock';
-- → Run this when applications report slowness — shows the blocking chain.

-- ── pg_stat_activity: idle transactions holding locks ─────────────────────────
-- An open transaction that is "idle in transaction" holds all its locks
-- even though it is not actively executing a query. Very common bug.
SELECT
    pid,
    state,                         -- 'idle in transaction' is dangerous
    usename,
    application_name,
    now() - xact_start AS tx_age,  -- How long the transaction has been open
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND xact_start < NOW() - INTERVAL '30 seconds'  -- Transactions open >30s
ORDER BY tx_age DESC;

-- Mitigation: set idle_in_transaction_session_timeout in postgresql.conf:
--   idle_in_transaction_session_timeout = '30s'
-- → PostgreSQL auto-terminates sessions idle in a transaction for >30s.
-- → In TypeORM/NestJS: ensure your transaction callbacks always commit or rollback.
--   A missing await, an unhandled Promise, or an exception without rollback
--   can leave transactions open indefinitely.

-- ── Terminating a blocking session ────────────────────────────────────────────
SELECT pg_cancel_backend(pid);    -- Send SIGINT — cancels current query, tx continues
SELECT pg_terminate_backend(pid); -- Send SIGTERM — terminates the session (last resort)

-- ── Setting statement and lock timeouts (defensive defaults) ──────────────────
-- In your TypeORM datasource options or at connection time:
-- These prevent runaway queries from holding locks indefinitely.
SET statement_timeout = '30s';    -- Kill queries running longer than 30s
SET lock_timeout     = '5s';      -- Fail if a lock cannot be acquired within 5s
SET idle_in_transaction_session_timeout = '60s'; -- Kill idle transactions after 60s

-- In TypeORM DataSource config:
// extra: {
//     options: `-c statement_timeout=30000 -c lock_timeout=5000`
// }
```

## Section 7: Advanced Patterns

**Q14. How do you implement a distributed rate limiter or single-flight pattern using advisory locks?**

A: Advisory locks are the building block for distributed mutual exclusion in a PostgreSQL-backed application — no Redis required:

```typescript
import { Injectable, Logger }        from '@nestjs/common';
import { DataSource }                from 'typeorm';
import { Cron, CronExpression }      from '@nestjs/schedule';

// ── Distributed cron job — exactly-once execution across N instances ──────────
@Injectable()
export class ScheduledJobService {
    private readonly logger = new Logger(ScheduledJobService.name);

    constructor(private readonly dataSource: DataSource) {}

    // Multiple instances run this, only one executes the job body:
    @Cron(CronExpression.EVERY_HOUR)
    async runHourlyCleanup(): Promise<void> {
        const LOCK_KEY = 7341892; // Arbitrary unique constant for this job

        const qr = this.dataSource.createQueryRunner();
        await qr.connect();
        await qr.startTransaction();

        try {
            const [{ pg_try_advisory_xact_lock: acquired }] = await qr.query(
                'SELECT pg_try_advisory_xact_lock($1)',
                [LOCK_KEY],
            );

            if (!acquired) {
                this.logger.debug('Hourly cleanup already running on another instance — skipping');
                await qr.rollbackTransaction();
                return;
            }

            this.logger.log('Acquired distributed lock — running hourly cleanup');
            await qr.query(`DELETE FROM sessions WHERE expires_at < NOW()`);
            await qr.query(`DELETE FROM temp_files WHERE created_at < NOW() - INTERVAL '24 hours'`);

            await qr.commitTransaction(); // Lock released here
            this.logger.log('Hourly cleanup complete');
        } catch (err) {
            await qr.rollbackTransaction();
            this.logger.error('Hourly cleanup failed', err);
        } finally {
            await qr.release();
        }
    }
}

// ── Single-flight pattern: coalesce duplicate concurrent requests ──────────────
// Problem: 100 requests arrive at the same time for the same expensive computation.
// Without this: 100 DB queries run, 100 identical results computed.
// With single-flight: 1 query runs, 99 requests wait and reuse the result.

@Injectable()
export class SingleFlightService {
    private readonly inFlight = new Map<number, Promise<any>>();

    constructor(private readonly dataSource: DataSource) {}

    async getWithSingleFlight<T>(
        lockKey:  number,
        compute:  () => Promise<T>,
    ): Promise<T> {
        // In-process deduplication first (cheapest):
        if (this.inFlight.has(lockKey)) {
            this.logger.debug(`Reusing in-flight computation for key ${lockKey}`);
            return this.inFlight.get(lockKey)!;
        }

        // Cross-process deduplication via advisory lock:
        const promise = this.computeWithLock(lockKey, compute);
        this.inFlight.set(lockKey, promise);

        try {
            return await promise;
        } finally {
            this.inFlight.delete(lockKey);
        }
    }

    private async computeWithLock<T>(lockKey: number, compute: () => Promise<T>): Promise<T> {
        const qr = this.dataSource.createQueryRunner();
        await qr.connect();
        await qr.startTransaction();

        try {
            // If another instance is computing, this blocks until it completes:
            await qr.query('SELECT pg_advisory_xact_lock($1)', [lockKey]);
            // We now have the lock — the other instance committed its result.
            // Check cache before computing (the other instance may have populated it):
            const cached = await this.cache.get(String(lockKey));
            if (cached) return cached;

            const result = await compute();
            await this.cache.set(String(lockKey), result, 300);
            await qr.commitTransaction();
            return result;
        } catch (err) {
            await qr.rollbackTransaction();
            throw err;
        } finally {
            await qr.release();
        }
    }
}

// ── Gapless invoice number generation ────────────────────────────────────────
@Injectable()
export class InvoiceService {
    private readonly SEQUENCE_LOCK = hashCode('invoice_sequence'); // stable integer

    constructor(private readonly dataSource: DataSource) {}

    async createInvoice(data: CreateInvoiceDto): Promise<Invoice> {
        return this.dataSource.transaction(async (manager) => {
            // Serialize invoice number generation — only one at a time:
            await manager.query(
                'SELECT pg_advisory_xact_lock($1)',
                [this.SEQUENCE_LOCK],
            );

            const [{ next }] = await manager.query(
                'SELECT COALESCE(MAX(invoice_number), 0) + 1 AS next FROM invoices'
            );

            const invoice = manager.create(Invoice, {
                ...data,
                invoiceNumber: parseInt(next),
            });
            return manager.save(invoice);
            // COMMIT releases the advisory lock AND persists the invoice atomically.
            // No gap is possible: if the INSERT fails, the COMMIT never runs,
            // the number is never recorded, and the lock is released.
        });
    }
}

function hashCode(str: string): number {
    let hash = 0;
    for (let i = 0; i < str.length; i++) {
        hash = ((hash << 5) - hash) + str.charCodeAt(i);
        hash |= 0; // Convert to 32-bit integer
    }
    return Math.abs(hash);
}
```

**Q15. How do you implement optimistic locking without TypeORM's `@VersionColumn` — using timestamps or custom ETags?**

A: `@VersionColumn` uses an integer counter. Sometimes you need timestamp-based or hash-based conflict detection — for API responses (ETags), or when integrating with external systems that track `updatedAt`:

```typescript
import { Entity, PrimaryGeneratedColumn, Column, UpdateDateColumn } from 'typeorm';

// ── Timestamp-based optimistic locking ───────────────────────────────────────
@Entity()
export class Document {
    @PrimaryGeneratedColumn('uuid')
    id: string;

    @Column('text')
    content: string;

    @UpdateDateColumn({ precision: 3 }) // Millisecond precision
    updatedAt: Date;
}

@Injectable()
export class DocumentService {
    async updateDocument(
        id:               string,
        content:          string,
        knownUpdatedAt:   Date,    // The updatedAt the client saw when they read the document
    ): Promise<Document> {
        return this.dataSource.transaction(async (manager) => {
            // Lock and read the current row:
            const doc = await manager.findOne(Document, {
                where: { id },
                lock: { mode: 'pessimistic_write' },
            });
            if (!doc) throw new NotFoundException();

            // Compare timestamps — if different, someone else updated it:
            if (doc.updatedAt.getTime() !== knownUpdatedAt.getTime()) {
                throw new ConflictException({
                    message:       'Document was modified by another user',
                    currentVersion: doc.updatedAt.toISOString(),
                    yourVersion:    knownUpdatedAt.toISOString(),
                });
            }

            doc.content = content;
            return manager.save(doc); // updatedAt auto-updates via @UpdateDateColumn
        });
    }
}

// ── ETag-based optimistic locking (HTTP API pattern) ──────────────────────────
// The client reads a document and receives an ETag in the response header.
// On update, the client sends the ETag in If-Match header.
// The server rejects updates where the ETag doesn't match the current state.

import * as crypto from 'crypto';

function computeEtag(document: Document): string {
    // ETag = hash of the document content + version
    return crypto
        .createHash('md5')
        .update(`${document.id}:${document.updatedAt.getTime()}:${document.content}`)
        .digest('hex');
}

@Controller('documents')
export class DocumentController {
    @Get(':id')
    async getDocument(
        @Param('id') id: string,
        @Res()          res: Response,
    ): Promise<void> {
        const doc  = await this.documentService.findById(id);
        const etag = computeEtag(doc);

        res.setHeader('ETag',          `"${etag}"`);
        res.setHeader('Last-Modified', doc.updatedAt.toUTCString());
        res.json(doc);
    }

    @Put(':id')
    async updateDocument(
        @Param('id')              id:      string,
        @Body()                   body:    UpdateDocumentDto,
        @Headers('if-match')      ifMatch: string,  // ETag from client
        @Res()                    res:     Response,
    ): Promise<void> {
        const doc         = await this.documentService.findById(id);
        const currentEtag = `"${computeEtag(doc)}"`;

        if (ifMatch && ifMatch !== currentEtag) {
            // 412 Precondition Failed — standard HTTP response for ETag mismatch:
            res.status(412).json({
                error:          'Precondition Failed',
                message:        'Document was modified. Please fetch the latest version.',
                currentETag:    currentEtag,
            });
            return;
        }

        const updated = await this.documentService.update(id, body.content, doc.updatedAt);
        res.setHeader('ETag', `"${computeEtag(updated)}"`);
        res.json(updated);
    }
}

// ── Raw SQL optimistic update (no ORM) ───────────────────────────────────────
// Sometimes a single atomic SQL statement is more efficient than lock + read + write:

async function updateIfUnchanged(
    dataSource: DataSource,
    id:         string,
    content:    string,
    updatedAt:  Date,
): Promise<boolean> {
    const result = await dataSource.query(
        `UPDATE documents
         SET    content    = $1,
                updated_at = NOW()
         WHERE  id         = $2
         AND    updated_at = $3
         RETURNING id`,
        [content, id, updatedAt],
    );
    // Returns 1 row if update succeeded, 0 rows if the row was modified meanwhile.
    return result.length > 0;
}
```

## Section 8: Scenario-Based Questions

**Q16. "Our inventory service has a race condition — we're occasionally selling items we don't have in stock."**

A: This is the canonical lost update / check-then-act race condition. The fix depends on the chosen locking strategy:

```sql
-- ── Diagnosing the bug ────────────────────────────────────────────────────────
-- BROKEN: read-check-write without a lock
-- Session A and B both see stock = 1:
-- A: SELECT stock FROM products WHERE id = 42;  → 1
-- B: SELECT stock FROM products WHERE id = 42;  → 1
-- A: UPDATE products SET stock = 0 WHERE id = 42;  (sells the last item)
-- B: UPDATE products SET stock = 0 WHERE id = 42;  (sells it again! stock goes to -1 or 0)
-- Depending on constraints: either -1 stock, or B's update silently succeeds.

-- ── Fix 1: Pessimistic lock (FOR UPDATE) ─────────────────────────────────────
-- Correct for high-conflict scenarios (flash sales, limited stock):
BEGIN;
SELECT stock FROM products WHERE id = 42 FOR UPDATE;
-- B now BLOCKS here until A commits.
-- A: if stock > 0, proceed; else abort.
UPDATE products SET stock = stock - 1 WHERE id = 42;
COMMIT;
-- B unblocks: re-reads stock = 0 → aborts cleanly.

-- ── Fix 2: Atomic UPDATE with constraint check ────────────────────────────────
-- Elegant: no explicit lock, use WHERE to make the update conditional.
UPDATE products
SET    stock = stock - 1
WHERE  id    = 42
AND    stock > 0  -- Guard inside the UPDATE
RETURNING stock;
-- If 0 rows returned: stock was 0, the sale is rejected.
-- PostgreSQL row-level lock is held only during the update (brief).
-- No explicit transaction needed for a single UPDATE.

-- ── Fix 3: CHECK constraint (database-level safety net) ───────────────────────
-- Even with application locking, add a constraint as a final guard:
ALTER TABLE products ADD CONSTRAINT stock_non_negative CHECK (stock >= 0);
-- Any UPDATE that would make stock negative raises a ConstraintViolationError.
-- The application catches this and returns "out of stock" to the user.

-- ── Fix 4: Optimistic locking + retry (for low-conflict scenarios) ────────────
-- With @VersionColumn on the Product entity:
-- T1 reads: { stock: 1, version: 5 }
-- T2 reads: { stock: 1, version: 5 }
-- T1 updates: UPDATE ... WHERE version = 5 → succeeds, version becomes 6
-- T2 updates: UPDATE ... WHERE version = 5 → 0 rows (version is now 6)
-- T2 catches OptimisticLockVersionMismatchError → retries → reads stock = 0 → rejects

-- ── TypeORM implementation of Fix 2 (atomic conditional update) ───────────────
async function sellItem(productId: number, quantity: number): Promise<boolean> {
    const result = await dataSource.query(
        `UPDATE products
         SET    stock = stock - $1
         WHERE  id    = $2
         AND    stock >= $1
         RETURNING id, stock`,
        [quantity, productId],
    );
    // result.length === 0 means not enough stock.
    return result.length > 0;
}

// The complete inventory service pattern (combines atomic update + advisory lock
// for multi-step reservation workflows):
@Injectable()
export class InventoryService {
    async reserveStock(productId: number, quantity: number, orderId: string): Promise<void> {
        await this.dataSource.transaction(async (manager) => {
            // Advisory lock: serialise reservations for this product.
            // Alternative to FOR UPDATE when multiple tables are involved.
            await manager.query(
                'SELECT pg_advisory_xact_lock($1)',
                [productId],
            );

            const [product] = await manager.query(
                'SELECT id, stock FROM products WHERE id = $1',
                [productId],
            );

            if (!product || product.stock < quantity) {
                throw new BadRequestException('Insufficient stock');
            }

            await manager.query(
                'UPDATE products SET stock = stock - $1 WHERE id = $2',
                [quantity, productId],
            );

            await manager.query(
                'INSERT INTO reservations (order_id, product_id, quantity) VALUES ($1, $2, $3)',
                [orderId, productId, quantity],
            );
        });
        // Advisory lock released on commit.
    }
}
```

**Q17. "Design the locking strategy for a seat reservation system where seats cannot be double-booked."**

A: Seat booking is the canonical pessimistic locking problem. Each seat is a contended resource; concurrent bookings for the same seat must be serialised:

```sql
-- ── Schema ────────────────────────────────────────────────────────────────────
CREATE TABLE seats (
    id         BIGSERIAL PRIMARY KEY,
    event_id   BIGINT NOT NULL,
    seat_label TEXT   NOT NULL,   -- e.g. 'A-12'
    status     TEXT   NOT NULL DEFAULT 'available',  -- available | reserved | booked
    UNIQUE (event_id, seat_label)
);

CREATE TABLE bookings (
    id         BIGSERIAL PRIMARY KEY,
    seat_id    BIGINT      NOT NULL REFERENCES seats(id),
    user_id    BIGINT      NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL DEFAULT NOW() + INTERVAL '15 minutes',
    confirmed  BOOLEAN     NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

```typescript
// ── Reservation service ───────────────────────────────────────────────────────
@Injectable()
export class SeatReservationService {
    constructor(private readonly dataSource: DataSource) {}

    // Step 1: Reserve a seat (holds it for 15 minutes while user completes payment):
    async reserveSeat(seatId: number, userId: number): Promise<Booking> {
        return this.dataSource.transaction(async (manager) => {
            // FOR UPDATE: lock the specific seat row.
            // NOWAIT: fail immediately if another transaction has it (UI shows "seat taken").
            const [seat] = await manager.query(
                `SELECT id, status, event_id, seat_label
                 FROM   seats
                 WHERE  id = $1
                 FOR    UPDATE NOWAIT`,
                [seatId],
            );

            if (!seat) throw new NotFoundException('Seat not found');

            if (seat.status !== 'available') {
                throw new ConflictException(`Seat ${seat.seatLabel} is already ${seat.status}`);
            }

            // Mark as reserved — the seat is held but not yet paid:
            await manager.query(
                `UPDATE seats SET status = 'reserved' WHERE id = $1`,
                [seatId],
            );

            const [booking] = await manager.query(
                `INSERT INTO bookings (seat_id, user_id, expires_at)
                 VALUES ($1, $2, NOW() + INTERVAL '15 minutes')
                 RETURNING *`,
                [seatId, userId],
            );

            return booking;
            // Transaction commits here — lock on seat released.
            // The seat is now 'reserved' in the DB; another SELECT FOR UPDATE
            // will see status='reserved' and reject the second attempt.
        });
    }

    // Step 2: Confirm after payment:
    async confirmBooking(bookingId: number, userId: number): Promise<void> {
        await this.dataSource.transaction(async (manager) => {
            const [booking] = await manager.query(
                `SELECT b.id, b.seat_id, b.user_id, b.expires_at, b.confirmed
                 FROM   bookings b
                 WHERE  b.id = $1
                 FOR    UPDATE`,
                [bookingId],
            );

            if (!booking)                     throw new NotFoundException();
            if (booking.userId !== userId)    throw new ForbiddenException();
            if (booking.confirmed)            throw new ConflictException('Already confirmed');
            if (new Date() > booking.expiresAt) {
                // Reservation expired — release the seat:
                await manager.query(
                    `UPDATE seats SET status = 'available' WHERE id = $1`,
                    [booking.seatId],
                );
                await manager.query(
                    `DELETE FROM bookings WHERE id = $1`,
                    [bookingId],
                );
                throw new GoneException('Reservation expired — please select the seat again');
            }

            await manager.query(
                `UPDATE bookings SET confirmed = TRUE WHERE id = $1`,
                [bookingId],
            );
            await manager.query(
                `UPDATE seats SET status = 'booked' WHERE id = $1`,
                [booking.seatId],
            );
        });
    }

    // Background job: release expired reservations (runs every minute):
    @Cron('* * * * *')
    async releaseExpiredReservations(): Promise<void> {
        // Advisory lock: prevent multiple instances running simultaneously:
        await this.dataSource.transaction(async (manager) => {
            await manager.query(
                'SELECT pg_advisory_xact_lock($1)',
                [hashCode('release_expired_seats')],
            );

            // Atomically find and release all expired reservations:
            await manager.query(`
                WITH expired AS (
                    DELETE FROM bookings
                    WHERE  confirmed = FALSE
                    AND    expires_at < NOW()
                    RETURNING seat_id
                )
                UPDATE seats
                SET    status = 'available'
                WHERE  id IN (SELECT seat_id FROM expired)
            `);
        });
    }

    // List available seats (no lock — MVCC handles concurrent reads):
    async getAvailableSeats(eventId: number): Promise<Seat[]> {
        return this.dataSource.query(
            `SELECT id, seat_label FROM seats
             WHERE  event_id = $1 AND status = 'available'
             ORDER  BY seat_label`,
            [eventId],
        );
        // No FOR UPDATE — this is a read. Available seats may change by the time
        // the user selects one; the reservation step (FOR UPDATE NOWAIT) handles
        // the race condition.
    }
}
```

## Quick Reference Tables

### Row-Level Lock Modes

| Lock mode | SQL syntax | Acquired by | Blocks | Allows |
|---|---|---|---|---|
| FOR KEY SHARE | `FOR KEY SHARE` | FK checks (internal) | FOR UPDATE, FOR NO KEY UPDATE | FOR KEY SHARE, FOR SHARE |
| FOR SHARE | `FOR SHARE` | Explicit only | FOR UPDATE, FOR NO KEY UPDATE | FOR KEY SHARE, FOR SHARE |
| FOR NO KEY UPDATE | `FOR NO KEY UPDATE` | `UPDATE` (non-PK columns) | FOR SHARE, FOR NO KEY UPDATE, FOR UPDATE | FOR KEY SHARE |
| FOR UPDATE | `FOR UPDATE` | `UPDATE`, `DELETE`, explicit | ALL lock modes | Nothing |

### Table-Level Lock Modes (Selected)

| Operation | Lock acquired | Blocks writes? | Blocks reads? | Production risk |
|---|---|---|---|---|
| `SELECT` | ACCESS SHARE | No | No | None |
| `INSERT`/`UPDATE`/`DELETE` | ROW EXCLUSIVE | Compatible with others | No | None |
| `CREATE INDEX` | SHARE | **Yes** | No | **High — use CONCURRENTLY** |
| `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | No | No | Low |
| `ALTER TABLE` (most) | ACCESS EXCLUSIVE | **Yes** | **Yes** | **Very high** |
| `TRUNCATE` | ACCESS EXCLUSIVE | **Yes** | **Yes** | Very high |
| `VACUUM FULL` | ACCESS EXCLUSIVE | **Yes** | **Yes** | Very high |
| `VACUUM` (regular) | SHARE UPDATE EXCLUSIVE | No | No | Low |

### Advisory Lock Functions

| Function | Level | Blocking? | Exclusive? |
|---|---|---|---|
| `pg_advisory_lock(key)` | Session | Yes (blocks) | Yes |
| `pg_advisory_lock_shared(key)` | Session | Yes (blocks) | No (shared) |
| `pg_try_advisory_lock(key)` | Session | No (returns bool) | Yes |
| `pg_try_advisory_lock_shared(key)` | Session | No (returns bool) | No |
| `pg_advisory_xact_lock(key)` | Transaction | Yes (blocks) | Yes |
| `pg_advisory_xact_lock_shared(key)` | Transaction | Yes (blocks) | No |
| `pg_try_advisory_xact_lock(key)` | Transaction | No (returns bool) | Yes |
| `pg_advisory_unlock(key)` | Session only | — | — |

### Choosing a Locking Strategy

| Scenario | Recommended approach |
|---|---|
| Transfer between accounts | Pessimistic `FOR UPDATE`, consistent lock order |
| Edit a document/profile | Optimistic `@VersionColumn` or `updatedAt` check |
| Job queue (N workers) | `FOR UPDATE SKIP LOCKED` |
| Interactive claim (user picks one item) | `FOR UPDATE NOWAIT` |
| Exactly-once distributed cron | `pg_try_advisory_xact_lock` |
| Long background migration | `pg_advisory_lock` (session-level) |
| Seat/ticket reservation | `FOR UPDATE NOWAIT` + status column |
| Gapless invoice numbering | `pg_advisory_xact_lock` on sequence key |
| Online schema migration | `CONCURRENTLY` + `NOT VALID` + `VALIDATE` |
| Preventing oversell | Atomic `UPDATE ... WHERE stock >= qty RETURNING id` |

---

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) understanding **MVCC** precisely — readers never block writers and writers never block readers in PostgreSQL; a plain `SELECT` never waits on a lock because it reads from a snapshot; only `SELECT FOR UPDATE/SHARE` and write operations need locks, because MVCC already handles the reader/writer problem; (2) knowing the **four row-level lock modes** (`FOR KEY SHARE`, `FOR SHARE`, `FOR NO KEY UPDATE`, `FOR UPDATE`) and their compatibility — `FOR UPDATE` conflicts with everything, `FOR KEY SHARE` conflicts with almost nothing; (3) being precise that **`SKIP LOCKED` and `NOWAIT` solve different problems** — `SKIP LOCKED` is for queue workers (skip contested rows, move on), `NOWAIT` is for exclusive claims (fail immediately if contested, let the client retry); (4) knowing that **`CREATE INDEX` without `CONCURRENTLY` acquires a SHARE lock** that blocks all writes for the entire build duration — always use `CONCURRENTLY` in production, and knowing that `ALTER TABLE` acquires `ACCESS EXCLUSIVE` which blocks even `SELECT`; (5) understanding **deadlock prevention through consistent lock ordering** — always acquire locks on multiple rows in ascending primary key order; the standard transfer pattern is to sort account IDs before locking; (6) knowing the **two advisory lock levels**: transaction-level (`pg_advisory_xact_lock`) is released automatically on commit/rollback and is the safe default; session-level (`pg_advisory_lock`) persists until `pg_advisory_unlock` is called or the session ends and requires a `finally` block; (7) being able to **read `pg_locks` and `pg_stat_activity`** to diagnose live lock contention — specifically `idle in transaction` state, which means a session holds locks without doing any work, often caused by a missing `await` or unhandled exception in a transaction callback; and (8) understanding the **optimistic vs pessimistic trade-off** in concrete terms — pessimistic is correct when conflicts are frequent (financial writes, seat booking) because retrying is expensive; optimistic is correct when conflicts are rare (document editing, profile updates) because lock overhead on the common path is wasteful.
