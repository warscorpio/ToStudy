# Query Optimization in PostgreSQL — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. How does PostgreSQL execute a query — what is the pipeline from SQL text to result rows?**
A: Understanding query execution is the foundation of optimization. PostgreSQL processes every query through four distinct stages before returning a single row:

```
SQL text → Parser → Rewriter → Planner → Executor → Result rows

Stage 1: Parser
  Input:  "SELECT id, name FROM users WHERE email = 'a@b.com' LIMIT 1"
  Output: Parse tree (abstract syntax tree)
  Work:   Lexical analysis, syntax validation
          Does NOT touch the database or statistics yet
          Fails here: syntax errors ("SELEKT", missing FROM)

Stage 2: Rewriter
  Input:  Parse tree
  Output: Rewritten parse tree
  Work:   Applies rules and view definitions
          Expands views into their underlying SELECT
          Applies row-level security policies
          Rarely visible to developers — mostly transparent

Stage 3: Planner (Query Optimizer)
  Input:  Rewritten parse tree
  Output: Execution plan (a tree of plan nodes)
  Work:   THE most important stage for performance
          Consults pg_statistics for row count estimates
          Evaluates all viable execution plans
          Assigns a cost to each plan
          Chooses the lowest-cost plan
          Key decisions:
            - Seq scan vs index scan vs index-only scan
            - Nested loop vs hash join vs merge join
            - Join order for multi-table queries
            - Whether to push filters down or apply them late

Stage 4: Executor
  Input:  Execution plan
  Output: Result rows
  Work:   Walks the plan tree, fetching rows from each node
          Applies remaining filters, projections, aggregations
          Streams rows to client (does not buffer entire result)
```

```sql
-- Inspecting each stage:

-- Parser output (parse tree):
-- No direct SQL command, but syntax errors come from here:
SELECT SELEKT 1;   -- ERROR: syntax error at or near "SELEKT"

-- Planner output (execution plan) — the most useful diagnostic:
EXPLAIN SELECT id, name FROM users WHERE email = 'a@b.com';
-- Index Scan using users_email_idx on users  (cost=0.43..8.45 rows=1 width=52)
--   Index Cond: (email = 'a@b.com'::text)

-- Full execution with actual timings:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, name FROM users WHERE email = 'a@b.com';
-- Index Scan ... (actual time=0.023..0.025 rows=1 loops=1)
-- Buffers: shared hit=3
-- Planning Time: 0.12 ms
-- Execution Time: 0.04 ms

-- The gap between estimated and actual rows is the key diagnostic:
-- rows=1 (estimate) vs actual rows=5000 → stale statistics → run ANALYZE
-- rows=5000 (estimate) vs actual rows=1 → planner chose wrong plan
```

**Q2. What does `EXPLAIN` output mean — how do you read a query plan?**
A: `EXPLAIN` outputs a tree of plan nodes, each representing one operation. Nodes are indented to show parent-child relationships. The executor pulls rows from child nodes into parent nodes, bottom-up:

```sql
-- A moderately complex plan:
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.name, count(o.id) AS order_count, sum(o.total) AS revenue
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.created_at > '2024-01-01'
  AND o.status = 'COMPLETED'
GROUP BY u.id, u.name
ORDER BY revenue DESC
LIMIT 10;
```

```
HashAggregate  (cost=12847.23..12847.33 rows=10 width=52)
               (actual time=89.3..89.4 rows=10 loops=1)
  Group Key: u.id, u.name
  Buffers: shared hit=2847 read=124
  ->  Sort  (cost=12847.23..12848.23 rows=400 width=44)
            (actual time=89.2..89.3 rows=400 loops=1)
        Sort Key: (sum(o.total)) DESC
        Sort Method: quicksort  Memory: 46kB
        ->  Hash Join  (cost=3241.00..12829.23 rows=400 width=44)
                       (actual time=22.1..88.9 rows=400 loops=1)
              Hash Cond: (o.user_id = u.id)
              Buffers: shared hit=2840 read=124
              ->  Seq Scan on orders o  (cost=0.00..9241.00 rows=45000 width=24)
                                        (actual time=0.02..55.3 rows=45000 loops=1)
                    Filter: (status = 'COMPLETED')
                    Rows Removed by Filter: 155000
                    Buffers: shared hit=2340 read=124
              ->  Hash  (cost=3191.00..3191.00 rows=4000 width=28)
                         (actual time=21.9..21.9 rows=4000 loops=1)
                    Buckets: 4096  Batches: 1  Memory Usage: 241kB
                    ->  Seq Scan on users u  (cost=0.00..3191.00 rows=4000 width=28)
                                             (actual time=0.01..21.7 rows=4000 loops=1)
                          Filter: (created_at > '2024-01-01'::date)
                          Rows Removed by Filter: 96000
```

```
Reading the plan — key fields:

  cost=startup..total
    startup: cost before first row can be returned (e.g. sort must complete)
    total:   cost to return ALL rows
    Units: arbitrary — relative costs, not milliseconds

  rows=N
    Estimated rows this node will return
    Compare to "actual rows" — large gap = stale statistics

  actual time=start..end
    Real milliseconds: start = first row, end = last row
    Multiply by loops= for nested loop iterations

  Buffers: shared hit=N read=M
    hit = pages found in shared_buffers (RAM cache) — fast
    read = pages read from disk (or OS cache) — slower
    High read count = consider more RAM or index to reduce page scans

  Rows Removed by Filter: N
    Rows the node READ but discarded — wasted work
    High number = filter should be pushed earlier (index, partition pruning)
```

```sql
-- Specific plan nodes and what they mean:

-- Seq Scan: reads every row in the table
--   Normal for small tables or low-selectivity filters
--   Alarming for large tables with high-selectivity filters → missing index

-- Index Scan: traverses B-tree, then fetches heap rows one at a time
--   Good for high-selectivity (<5% of rows)
--   Each fetch = random I/O to heap

-- Index Only Scan: all needed columns in the index (INCLUDE or key columns)
--   No heap access — fastest possible index access
--   Requires visible heap (autovacuum must keep visibility map current)

-- Bitmap Index Scan + Bitmap Heap Scan:
--   Batch fetch: build bitmap of matching pages, read in order
--   Good for moderate selectivity (1%-15%)
--   More efficient than Index Scan for many matches (sequential heap reads)

-- Hash Join: build hash table on smaller relation, probe with larger
--   Good for large unsorted datasets
--   Requires memory (work_mem) — spills to disk if exceeded

-- Nested Loop: for each row in outer, scan inner
--   Fast when inner has an index and outer is small
--   Catastrophic for large outer with large inner (N×M operations)

-- Merge Join: sort both sides, merge in order
--   Good when both sides already sorted (index on join column)
--   Better than hash join when result needs to be sorted anyway
```

## Section 2: Avoid `SELECT *`

**Q3. Why is `SELECT *` harmful — what are the concrete performance and correctness costs?**
A: `SELECT *` is not just a style issue. It has measurable performance costs and can silently break application code in ways that only surface in production:

```sql
-- The performance cost of SELECT *:

-- Scenario: users table with 20 columns including a TEXT essay field
-- and a BYTEA avatar column

CREATE TABLE users (
    id           UUID PRIMARY KEY,
    email        TEXT NOT NULL,
    name         TEXT NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL,
    -- ... 10 more small columns ...
    bio          TEXT,           -- Up to 10KB per user
    avatar       BYTEA,          -- Profile photo: up to 500KB per user
    preferences  JSONB           -- Nested config object
);

-- BAD: fetches all 20 columns including bio (10KB) and avatar (500KB):
SELECT * FROM users WHERE id = 'u-42';
-- Network transfer: up to 510KB for one row
-- Memory: PostgreSQL must serialize all columns

-- GOOD: fetches only what the caller needs:
SELECT id, name, email FROM users WHERE id = 'u-42';
-- Network transfer: ~100 bytes
-- 5000x less data transferred

-- At scale: 10,000 users listed per page
SELECT * FROM users LIMIT 10000;
-- Up to 5GB transferred if all avatars are loaded
SELECT id, name, email, created_at FROM users LIMIT 10000;
-- ~4MB — manageable
```

```sql
-- SELECT * prevents Index-Only Scans:

CREATE INDEX ON users (email) INCLUDE (name);
-- This index contains: email (key) + name (stored)

-- Index-Only Scan possible — no heap access needed:
SELECT email, name FROM users WHERE email = 'a@b.com';
-- Index Only Scan using users_email_name_idx

-- Index-Only Scan IMPOSSIBLE with SELECT *:
SELECT * FROM users WHERE email = 'a@b.com';
-- Index Scan + heap fetch: avatar, bio, preferences NOT in index
-- Must go to heap for every row — all the expensive random I/O
```

```sql
-- SELECT * breaks application code silently:

-- 1. Column order dependency:
-- Your ORM maps result columns by position, not name.
-- You add a column to the table: ALTER TABLE users ADD COLUMN score INT AFTER name;
-- SELECT * now returns columns in different order
-- ORM maps 'name' field to the value at position 3 — which is now 'score'
-- Application reads user.name and gets 0 (the score default)
-- Silent data corruption — no error, wrong data

-- 2. Unexpected data in the result:
-- You JOIN two tables both with a column named 'id':
SELECT * FROM orders o JOIN users u ON u.id = o.user_id;
-- Result has TWO 'id' columns — one overrides the other in most ORMs
-- Which 'id' you get depends on column ordering and ORM behaviour

-- The correct pattern:
SELECT
    o.id AS order_id,
    o.total,
    o.status,
    u.id AS user_id,
    u.name AS user_name
FROM orders o
JOIN users u ON u.id = o.user_id;
-- Explicit aliases: no ambiguity, no hidden columns

-- 3. Security: accidentally exposing sensitive columns:
-- A new column password_hash is added to users.
-- An API endpoint using SELECT * now returns password_hash in the response.
-- If the ORM serializes the result directly: password hashes are in the API.
-- Explicit column selection is a defence-in-depth measure.
```

```sql
-- When SELECT * is acceptable:

-- 1. Exploration / debugging in psql:
SELECT * FROM orders WHERE id = 'ord-123';  -- Ad-hoc inspection, not application code

-- 2. EXISTS checks — column list irrelevant:
SELECT EXISTS (SELECT * FROM orders WHERE user_id = 'u-42');
-- Planner optimises away the * — equivalent to SELECT 1
-- But prefer: SELECT EXISTS (SELECT 1 FROM orders WHERE user_id = 'u-42')
-- More explicit, same performance

-- 3. CTEs where you immediately project:
WITH recent AS (
    SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '1 day'
    -- * here is less harmful: columns immediately narrowed in outer query
)
SELECT id, total FROM recent WHERE status = 'COMPLETED';
-- Still better to be explicit in the CTE itself

-- Rule: never use SELECT * in application code that ships to production.
-- Always name the columns you need.
```

**Q4. How does column selection interact with TOAST and wide tables?**
A: PostgreSQL uses TOAST (The Oversized-Attribute Storage Technique) to store large column values out-of-line. `SELECT *` forces TOAST decompression and retrieval for every large column on every row, even when the application discards them:

```sql
-- TOAST storage: columns > ~2KB are stored out-of-line in a TOAST table
-- Each large column access = additional random I/O to TOAST table

-- Check which columns are TOASTed:
SELECT
    attname AS column_name,
    atttypid::regtype AS data_type,
    attstorage AS storage_strategy,
    pg_size_pretty(avg_width::bigint) AS avg_size
FROM pg_stats
JOIN pg_attribute ON pg_attribute.attname = pg_stats.attname
WHERE tablename = 'articles'
  AND attrelid = 'articles'::regclass
  AND attnum > 0
ORDER BY avg_width DESC;
-- storage_strategy:
--   p = plain (never TOAST, always inline)
--   e = external (TOAST, don't compress)
--   x = extended (TOAST, compress if beneficial) ← default for TEXT, BYTEA, JSONB
--   m = main (compress inline first, then TOAST)

-- The performance impact:
-- Table: articles with id (UUID), title (TEXT, ~100 bytes), body (TEXT, ~50KB)
-- 100,000 rows

-- BAD: SELECT * fetches body for every row (TOAST decompression × 100,000):
SELECT * FROM articles WHERE category = 'tech' LIMIT 100;
-- Actual I/O: 100 × (heap page + TOAST fetch) = 200+ random reads
-- Time: potentially seconds

-- GOOD: only fetch the columns needed for the list view:
SELECT id, title, created_at, excerpt FROM articles
WHERE category = 'tech'
LIMIT 100;
-- No TOAST access at all (title, created_at, excerpt are small, inline)
-- Time: milliseconds

-- Fetch body only for the detail view (one row at a time):
SELECT id, title, body FROM articles WHERE id = $1;
-- One TOAST fetch, acceptable for single-row detail
```

## Section 3: The `WHERE` Clause

**Q5. How does the planner use `WHERE` clause conditions — what is selectivity and why does column order in the clause not matter?**
A: A common misconception is that the order of conditions in a `WHERE` clause affects which index is used or how filters are applied. It does not. The planner is a cost-based optimizer that evaluates all conditions simultaneously and chooses the cheapest plan regardless of the order you wrote them in:

```sql
-- These three queries produce IDENTICAL execution plans:
SELECT * FROM orders WHERE user_id = 'u-42' AND status = 'COMPLETED';
SELECT * FROM orders WHERE status = 'COMPLETED' AND user_id = 'u-42';
SELECT * FROM orders WHERE status = 'COMPLETED'
                       AND user_id = 'u-42';

-- The planner picks the most selective condition for index access,
-- regardless of which came first in the SQL text.
-- EXPLAIN shows: the plan is identical for all three.

-- What DOES matter for filter performance:
-- 1. Whether an index exists for the condition
-- 2. The selectivity (how many rows the condition eliminates)
-- 3. Whether conditions can be pushed below a join (predicate pushdown)
-- 4. Whether statistics are up to date (ANALYZE)
```

```sql
-- Selectivity — the planner's key input:
-- Selectivity = fraction of rows that match the condition
-- Lower selectivity = fewer rows pass = index more beneficial

-- High selectivity (few rows match — good for indexes):
WHERE id = 'specific-uuid'           -- ~1 row out of millions: selectivity ≈ 0
WHERE email = 'user@example.com'     -- 1 row: selectivity ≈ 0
WHERE order_date = '2024-03-15'      -- Maybe 0.01% of rows

-- Low selectivity (many rows match — index may not help):
WHERE status = 'COMPLETED'           -- Maybe 60% of rows
WHERE created_at > '2020-01-01'      -- Maybe 90% of rows
WHERE is_active = true               -- Maybe 80% of rows

-- The planner uses statistics to estimate selectivity:
SELECT
    attname,
    n_distinct,
    most_common_vals,
    most_common_freqs,
    histogram_bounds
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
-- n_distinct = 4: four distinct status values
-- most_common_vals = {COMPLETED, PENDING, SHIPPED, CANCELLED}
-- most_common_freqs = {0.62, 0.21, 0.10, 0.07}
-- Planner knows: WHERE status = 'COMPLETED' matches 62% of rows → seq scan likely

-- Misleading statistics — when the planner gets it wrong:
-- If status was just added and most orders are still PENDING,
-- but ANALYZE hasn't run: planner assumes uniform distribution (25% each)
-- and may choose an index scan when seq scan is better (or vice versa)
-- Fix: ANALYZE orders; (or let autovacuum do it)
```

**Q6. What is predicate pushdown and how does it dramatically affect join performance?**
A: Predicate pushdown is the planner's ability to apply a filter condition as early as possible in the execution — before joining, before aggregating. This reduces the number of rows flowing through expensive operations:

```sql
-- The difference pushdown makes:

-- Query: get revenue by user, for users created after 2024-01-01
-- with completed orders

-- Version 1: filter after join (no pushdown — wrong way to think about it):
SELECT u.name, SUM(o.total) AS revenue
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.created_at > '2024-01-01'
  AND o.status = 'COMPLETED'
GROUP BY u.id, u.name;

-- The planner DOES push predicates down automatically here.
-- EXPLAIN shows filters applied before the join:
-- Seq Scan on users → Filter: (created_at > '2024-01-01') → 4,000 rows
-- Seq Scan on orders → Filter: (status = 'COMPLETED') → 45,000 rows
-- Hash Join: 4,000 × 45,000 probe → far fewer than 100,000 × 200,000 full join

-- Where pushdown FAILS: views and subqueries with certain patterns:
CREATE VIEW recent_users AS
    SELECT * FROM users WHERE created_at > '2024-01-01';

-- The planner CAN push predicates into simple views (since PG 9+):
SELECT * FROM recent_users WHERE email = 'a@b.com';
-- Equivalent to: SELECT * FROM users WHERE created_at > '2024-01-01' AND email = 'a@b.com'
-- Index on email used if available

-- The planner CANNOT push predicates through:
-- - DISTINCT
-- - GROUP BY (in a subquery)
-- - UNION / EXCEPT / INTERSECT
-- - Subqueries with LIMIT or OFFSET
-- - Functions marked VOLATILE in the FROM clause

-- Example of pushdown failure:
SELECT * FROM (
    SELECT DISTINCT user_id FROM orders
) active_users
WHERE user_id = 'u-42';
-- The DISTINCT prevents pushdown of user_id = 'u-42' into the subquery
-- PostgreSQL must compute all distinct user_ids, THEN filter
-- Fix: WHERE clause inside the subquery:
SELECT * FROM (
    SELECT DISTINCT user_id FROM orders WHERE user_id = 'u-42'
) active_users;
-- Now filter is inside — index on user_id can be used
```

```sql
-- Practical pushdown patterns:

-- Pattern 1: Filter before aggregate (always):
-- BAD — planner may not optimise this depending on query structure:
SELECT user_id, COUNT(*) FROM (
    SELECT * FROM orders
) all_orders
WHERE status = 'COMPLETED'
GROUP BY user_id;

-- GOOD — explicit:
SELECT user_id, COUNT(*)
FROM orders
WHERE status = 'COMPLETED'
GROUP BY user_id;

-- Pattern 2: Filter before JOIN:
-- The planner handles simple cases, but for complex queries,
-- pre-filtering in a CTE or subquery makes intent explicit:

-- 50M order_events table — only need last 7 days:
WITH recent_events AS (
    SELECT * FROM order_events
    WHERE occurred_at > NOW() - INTERVAL '7 days'   -- ← pushed early: 50M → 10K rows
)
SELECT o.id, COUNT(e.id) AS event_count
FROM orders o
JOIN recent_events e ON e.order_id = o.id
GROUP BY o.id;
-- Join is 10K × orders subset — not 50M × all orders

-- Pattern 3: Partition pruning via WHERE:
-- Partitioned table — WHERE on partition key eliminates entire partitions:
SELECT * FROM metrics                    -- Partitioned by month
WHERE recorded_at > '2024-03-01'        -- Partition pruning: only March+ partitions scanned
  AND device_id = 'device-42';
-- EXPLAIN shows: Append → only relevant partitions listed, others pruned
```

**Q7. What are the most common WHERE clause anti-patterns that prevent index use?**
A: Several common query patterns silently bypass indexes by transforming the indexed column in ways the planner cannot reverse. Recognising and fixing these is one of the highest-value optimisation skills:

```sql
-- ANTI-PATTERN 1: Function on the indexed column
-- Index exists on: created_at
-- BAD — function wrapping prevents index use:
SELECT * FROM orders WHERE DATE(created_at) = '2024-03-15';
-- → Seq Scan: planner cannot use index on created_at because it's inside DATE()
-- EXPLAIN: Seq Scan, Filter: (date(created_at) = '2024-03-15')

-- GOOD — rewrite to range on the indexed column:
SELECT * FROM orders
WHERE created_at >= '2024-03-15'
  AND created_at <  '2024-03-16';
-- → Index Scan on created_at (or Bitmap Index Scan)

-- BAD — other function wrapping examples:
WHERE UPPER(email) = 'USER@EXAMPLE.COM'    -- Function on indexed column
WHERE EXTRACT(YEAR FROM created_at) = 2024 -- Function prevents range use
WHERE CAST(user_id AS TEXT) = '42'         -- Type cast on indexed column
WHERE LENGTH(name) > 20                    -- Function on column

-- GOOD alternatives:
WHERE email = lower('USER@EXAMPLE.COM')    -- Function on the VALUE, not the column
    -- or: CREATE INDEX ON users (lower(email)); and query matches expression
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'
WHERE user_id = 42::uuid                   -- Cast the literal, not the column
```

```sql
-- ANTI-PATTERN 2: Leading wildcard in LIKE
-- Index on name (B-tree):
SELECT * FROM products WHERE name LIKE '%widget%';
-- → Seq Scan: B-tree cannot search for suffix patterns (no left anchor)
-- EXPLAIN: Seq Scan, Filter: (name ~~ '%widget%')

-- FIX A: Full-text search for word-level matching:
SELECT * FROM products WHERE to_tsvector('english', name) @@ to_tsquery('widget');
-- Requires GIN index on to_tsvector('english', name)

-- FIX B: trigram index for substring matching:
CREATE EXTENSION pg_trgm;
CREATE INDEX ON products USING GIN (name gin_trgm_ops);
SELECT * FROM products WHERE name ILIKE '%widget%';
-- → GIN Bitmap Index Scan: trigram index used for leading wildcard

-- FIX C: reverse-index for suffix patterns:
CREATE INDEX ON products (reverse(name));
SELECT * FROM products WHERE reverse(name) LIKE reverse('%ltd');
-- ← 'Ltd' suffix pattern → becomes prefix on reversed string
```

```sql
-- ANTI-PATTERN 3: OR conditions spanning different columns
-- Indexes on user_id and email separately:
SELECT * FROM users WHERE user_id = 'u-42' OR email = 'a@b.com';
-- → Bitmap Index Scan on user_id + Bitmap Index Scan on email + BitmapOr
-- This actually works! PostgreSQL can combine indexes via bitmap OR.
-- BUT: if either condition has low selectivity, performance degrades.

-- When OR is problematic — non-indexed column in OR:
SELECT * FROM users WHERE id = 'u-42' OR is_admin = true;
-- is_admin has no index → can't use index on id alone because
-- even rows where id ≠ 'u-42' must be checked for is_admin = true
-- → Seq Scan

-- FIX: UNION ALL if both branches are indexable:
SELECT * FROM users WHERE id = 'u-42'
UNION ALL
SELECT * FROM users WHERE is_admin = true AND id != 'u-42';
-- Each branch uses its own index; combined without double-counting

-- Or rewrite with a covering index for the common case:
CREATE INDEX ON users (is_admin) WHERE is_admin = true;  -- Partial index
-- Small: only indexes the is_admin=true rows (hopefully few)
```

```sql
-- ANTI-PATTERN 4: Implicit type coercion
-- Column: user_id UUID NOT NULL
-- Index on: user_id

-- BAD — passing wrong type forces a cast on the column:
SELECT * FROM orders WHERE user_id = 42;       -- INT literal, UUID column
-- PostgreSQL tries to cast user_id to int OR cast 42 to uuid
-- Depending on available casts: may → Seq Scan with CAST(user_id AS INT) = 42
-- Or: ERROR: operator does not exist: uuid = integer

-- GOOD — use the correct literal type:
SELECT * FROM orders WHERE user_id = '42'::uuid;
-- Or let the driver/ORM send the correct type in the prepared statement

-- Subtler case with VARCHAR vs TEXT:
-- Column: email VARCHAR(255), Index on email
-- Query: WHERE email = 'a@b.com'  ← text literal
-- PostgreSQL: VARCHAR and TEXT share the same operators — index used
-- This case is usually fine, but type mismatches can surprise with custom types

-- ANTI-PATTERN 5: Negation
SELECT * FROM orders WHERE status != 'CANCELLED';
-- B-tree cannot efficiently answer "not equal" — must scan all rows
-- (though it may use index + filter for high selectivity, e.g. 99% not cancelled)

-- FIX: rewrite as positive condition if possible:
SELECT * FROM orders WHERE status IN ('PENDING', 'COMPLETED', 'SHIPPED');
-- Planner: BitmapOr of three index scans → more efficient

-- ANTI-PATTERN 6: IS NOT NULL on a mostly-non-null column
SELECT * FROM orders WHERE shipped_at IS NOT NULL;
-- If 95% of rows have shipped_at, this is a low-selectivity scan
-- Index won't help — seq scan is cheaper
-- If few rows are NULL, add a partial index:
CREATE INDEX ON orders (shipped_at) WHERE shipped_at IS NOT NULL;
-- But even then: 95% selectivity means seq scan likely wins
```

## Section 4: Using `LIMIT`

**Q8. How does `LIMIT` interact with the query planner, and when does it change the execution plan?**
A: `LIMIT` is not just "fetch N rows then stop." It fundamentally changes the planner's cost model because the planner knows it only needs to return N rows — it can choose a plan that produces the first N rows cheaply rather than all rows cheaply:

```sql
-- LIMIT changes plan costs:

-- Without LIMIT — cheapest plan to return ALL matching rows:
EXPLAIN SELECT * FROM orders WHERE user_id = 'u-42' ORDER BY created_at DESC;
-- Index Scan Backward using orders_user_created_idx on orders
-- (cost=0.43..8250.00 rows=5000 width=120)
-- → Full index scan to return all 5000 matching rows

-- With LIMIT — cheapest plan to return FIRST 10 rows:
EXPLAIN SELECT * FROM orders WHERE user_id = 'u-42' ORDER BY created_at DESC LIMIT 10;
-- Limit  (cost=0.43..0.60 rows=10 width=120)   ← total cost much lower
--   ->  Index Scan Backward using orders_user_created_idx on orders
--         (cost=0.43..8250.00 rows=5000 width=120)
-- Planner knows: stop after 10 rows — startup cost of index scan is cheap
-- Total cost ≈ 0.60 vs 8250.00 — the planner can exploit early termination

-- Why LIMIT can change the join strategy:
-- Without LIMIT: Hash Join preferred (fast for large result sets)
-- With LIMIT 10: Nested Loop may be preferred (fast for small result sets)
EXPLAIN SELECT u.name, o.total
FROM users u JOIN orders o ON o.user_id = u.id
ORDER BY o.created_at DESC
LIMIT 10;
-- May show: Nested Loop (fast for first 10 rows)
-- Without LIMIT: Hash Join
-- Reason: Nested Loop has high startup cost but low per-row cost → wins for LIMIT
```

```sql
-- LIMIT without ORDER BY — undefined result set:
SELECT * FROM orders LIMIT 10;
-- Returns 10 rows — but WHICH 10?
-- No guarantee of ordering — different executions may return different rows
-- As data changes, inserts, vacuums, reordering: result is non-deterministic

-- ALWAYS pair LIMIT with ORDER BY for deterministic pagination:
SELECT * FROM orders
ORDER BY created_at DESC, id DESC  -- Tiebreak on id for uniqueness
LIMIT 10;

-- Why OFFSET-based pagination is problematic:
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10 OFFSET 990;
-- PostgreSQL must: sort all rows, skip 990, return 10
-- The SKIP 990 is not free — it scans 990 rows just to discard them
-- Page 100 of results: OFFSET 990 → scan 1000 rows, discard 990
-- Page 1000 of results: OFFSET 9990 → scan 10,000 rows, discard 9,990
-- Gets progressively slower with each page
```

```sql
-- Keyset pagination (cursor-based) — the correct alternative to OFFSET:
-- First page:
SELECT id, created_at, total
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 10;
-- Returns rows: (t10, id-a), (t9, id-b), ..., (t1, id-j)
-- Save the last row's values: last_created_at = t1, last_id = id-j

-- Next page — WHERE clause instead of OFFSET:
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (last_created_at, last_id)  -- Row comparison
ORDER BY created_at DESC, id DESC
LIMIT 10;
-- Index on (created_at DESC, id DESC) makes this O(log N) regardless of page number
-- Page 1000 is as fast as page 1 — uses index to seek directly to the cursor position

-- Why this works:
-- (created_at, id) < (t1, id-j) is a composite comparison:
--   created_at < t1 OR (created_at = t1 AND id < id-j)
-- PostgreSQL uses the (created_at, id) index to find the exact position

-- Row comparison syntax:
WHERE (col1, col2) < ($1, $2)
-- Equivalent to: (col1 < $1) OR (col1 = $1 AND col2 < $2)
-- PostgreSQL evaluates this efficiently with a composite index

-- Keyset limitations:
-- Cannot jump to arbitrary page (no OFFSET equivalent)
-- The "next page token" is the last row's values — must be passed back to client
-- Deletions during pagination: deleted rows are cleanly skipped (no gaps or duplicates)
-- This is actually better than OFFSET (which shifts all subsequent pages on deletion)
```

**Q9. What is the `LIMIT` and `ORDER BY` interaction with indexes — and what is the "sort avoidance" optimization?**
A: When a query has both `ORDER BY` and `LIMIT`, the planner tries to find an index that already provides rows in the required order, avoiding a sort step entirely. This is called sort avoidance and can turn O(N log N) into O(log N + K):

```sql
-- Sort avoidance — the planner uses an index to skip the sort:

-- Index: CREATE INDEX ON orders (user_id, created_at DESC);

-- Query:
SELECT id, total FROM orders
WHERE user_id = 'u-42'
ORDER BY created_at DESC
LIMIT 10;

-- Plan WITH sort avoidance (ideal):
-- Limit  (cost=0.43..2.53 rows=10)
--   ->  Index Scan Backward using orders_user_created_idx on orders
--         Index Cond: (user_id = 'u-42')
--         (no Sort node in plan!)
-- Reading the index in reverse order gives DESC order for free

-- Plan WITHOUT sort avoidance (no matching index):
-- Limit  (cost=125.30..125.33 rows=10)
--   ->  Sort  (cost=125.30..137.80 rows=5000)
--         Sort Key: created_at DESC
--         ->  Index Scan using orders_user_id_idx
-- Sort happens BEFORE Limit — must sort ALL 5000 rows to find the top 10

-- The Sort node is the smoking gun — it means:
-- 1. No suitable index for the ORDER BY
-- 2. All matching rows fetched, sorted in memory (or disk if large), then limited
-- Fix: create an index that matches the ORDER BY column and direction
```

```sql
-- Matching ORDER BY to index direction:

-- Index: orders(created_at)  ← ascending by default
-- Works for:
SELECT * FROM orders ORDER BY created_at ASC LIMIT 10;   -- Index Scan Forward
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;  -- Index Scan Backward
-- B-tree can be scanned in both directions — ASC and DESC both work with one index

-- Composite index direction matters when both columns are in ORDER BY:
CREATE INDEX ON orders (user_id ASC, created_at DESC);
-- Works for: ORDER BY user_id ASC, created_at DESC  ← exact match
-- Works for: ORDER BY user_id DESC, created_at ASC  ← reversed (B-tree reversal)
-- Does NOT match: ORDER BY user_id ASC, created_at ASC ← mixed, needs separate index

-- NULLS ordering:
CREATE INDEX ON orders (completed_at DESC NULLS LAST);
-- Matches: ORDER BY completed_at DESC NULLS LAST  ← sort avoidance
-- B-tree default: DESC = NULLS FIRST (they appear at the start)
-- If query uses NULLS LAST: index must also specify NULLS LAST

-- Practical check — does the index satisfy ORDER BY?
EXPLAIN SELECT id FROM orders ORDER BY created_at DESC LIMIT 10;
-- If you see Sort node: index doesn't match ORDER BY direction/columns
-- If no Sort node: sort avoidance achieved
```

```sql
-- TOP-N queries — a specific pattern combining LIMIT and ORDER BY:

-- "Find the 10 most recent orders for this user" — classic TOP-N:
SELECT id, total, status, created_at
FROM orders
WHERE user_id = 'u-42'
ORDER BY created_at DESC
LIMIT 10;

-- Optimal index for this pattern: (user_id, created_at DESC)
CREATE INDEX ON orders (user_id, created_at DESC)
INCLUDE (total, status);
-- user_id: equality filter — eliminates non-matching users
-- created_at DESC: sort order — enables sort avoidance, early termination
-- INCLUDE (total, status): covers the projection — enables index-only scan
-- Together: Index Only Scan + no Sort + LIMIT early termination
-- = O(log N) seek + O(K) rows = fastest possible for this pattern

-- "Find the N users with the highest total revenue" — aggregate TOP-N:
SELECT user_id, SUM(total) AS revenue
FROM orders
WHERE status = 'COMPLETED'
GROUP BY user_id
ORDER BY revenue DESC
LIMIT 10;
-- This requires computing the aggregate for ALL users before LIMIT applies
-- No index can avoid this — the planner must aggregate first
-- LIMIT helps after aggregation: sort the aggregated result, take top 10
-- Fix: materialise a summary table if this query runs frequently
```

## Section 5: Join Optimization

**Q10. How does join order affect performance, and when should you guide the planner?**
A: In a multi-table join, the planner considers many possible join orderings (N! orderings for N tables). The optimal order joins smallest-first, building up intermediate result sets that are as small as possible at each step:

```sql
-- Join order matters enormously:

-- Tables: users (1M rows), orders (10M rows), order_items (50M rows)
-- Filters: users WHERE region='EU' (10K match), orders WHERE status='COMPLETED'

-- BAD join order (largest tables joined first):
-- orders (10M) × order_items (50M) → 500M intermediate rows
-- Then filter and join to users

-- GOOD join order (most selective filters applied first):
-- users WHERE region='EU' → 10K rows
-- JOIN orders WHERE status='COMPLETED' → reduces to ~6K rows
-- JOIN order_items → reduces to ~30K rows
-- Planner reaches same result with tiny intermediate sets

-- The planner usually figures this out automatically.
-- When it doesn't (stale statistics, complex queries):

-- Check join order in EXPLAIN:
EXPLAIN SELECT u.name, COUNT(oi.id) AS items_ordered
FROM users u
JOIN orders o ON o.user_id = u.id
JOIN order_items oi ON oi.order_id = o.id
WHERE u.region = 'EU'
  AND o.status = 'COMPLETED'
  AND o.created_at > '2024-01-01';
-- Read EXPLAIN bottom-up: first node in plan = first table accessed
-- If you see the 50M table accessed first: join order is wrong

-- Force join order (last resort — investigate statistics first):
SET join_collapse_limit = 1;  -- Planner uses joins in the order written
SELECT ...
FROM users u    -- This will be the outer (first) table
JOIN orders o ...
JOIN order_items oi ...;
SET join_collapse_limit = 8;  -- Reset to default
```

```sql
-- Join type performance: nested loop vs hash join vs merge join

-- Nested Loop: for each outer row, scan inner
SELECT * FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.id = 'specific-order-id';  -- 1 outer row
-- Nested Loop is fast: 1 outer row × index scan on users → 1-2 I/Os total
-- Ideal when: outer is tiny (1-100 rows), inner has an index

-- Hash Join: build hash table on smaller side, probe with larger
SELECT u.name, COUNT(o.id)
FROM users u
JOIN orders o ON o.user_id = u.id
GROUP BY u.id;
-- Hash Join: hash all users (1M) into memory, scan all orders (10M) probing hash
-- Ideal for: large unsorted datasets, no index on join column
-- Memory: work_mem controls hash table size (spills to disk if exceeded)

-- Merge Join: sort both sides, merge in order
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id
ORDER BY u.id;
-- Merge Join if both sides have index on join column (already sorted)
-- Ideal when: result needs to be sorted by join key anyway

-- work_mem — the lever for hash join performance:
SET work_mem = '256MB';  -- Larger hash table: fewer batches, faster hash joins
-- Be careful: work_mem is per-sort, per-hash per query — a complex query
-- with 5 hash joins × 256MB = 1.25GB per connection
-- Set at session level for specific heavy queries, not globally
```

## Section 6: Aggregation and GROUP BY

**Q11. How do you optimize aggregation queries — when does the planner use indexes for GROUP BY?**
A: Aggregation is inherently an O(N) operation — every row must be read to compute the aggregate. But index-based optimisations can avoid reading from the heap at all, and partial aggregation can reduce the data volume before expensive operations:

```sql
-- Index-Only Scan for aggregates — avoid heap entirely:

-- Index on orders(user_id) INCLUDE (total):
SELECT user_id, SUM(total) AS revenue, COUNT(*) AS order_count
FROM orders
WHERE status = 'COMPLETED'
GROUP BY user_id;
-- Without covering index: heap access per row to get total
-- With INCLUDE (total): Index-Only Scan → SUM(total) from index directly

-- COUNT(*) vs COUNT(column):
-- COUNT(*): counts all rows including NULLs — can use index-only scan
-- COUNT(column): must check if column is NULL per row — subtly different
-- For non-nullable columns: COUNT(*) = COUNT(column), use COUNT(*)

-- Approximate count for dashboards (fast, not exact):
SELECT reltuples::bigint AS approximate_count
FROM pg_class WHERE relname = 'orders';
-- Updated by ANALYZE — accurate within autovacuum frequency
-- Returns instantly — useful for "showing ~50M orders" in a dashboard

-- For exact count on large tables with no WHERE:
SELECT COUNT(*) FROM orders;  -- Seq scan — always O(N), always slow for huge tables
-- Accept approximation, or maintain a counter table:
CREATE TABLE table_counts (
    table_name TEXT PRIMARY KEY,
    count      BIGINT NOT NULL DEFAULT 0
);
-- Increment on INSERT trigger, decrement on DELETE trigger
-- SELECT count FROM table_counts WHERE table_name = 'orders' → O(1)
```

```sql
-- Partial aggregation — filter before aggregate:
-- BAD: aggregate all orders, then filter users:
SELECT u.name, SUM(o.total) AS revenue
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE u.region = 'EU'
GROUP BY u.id, u.name
HAVING SUM(o.total) > 1000;

-- GOOD: pre-aggregate orders, then join to users:
WITH user_revenue AS (
    SELECT user_id, SUM(total) AS revenue
    FROM orders
    GROUP BY user_id
    HAVING SUM(total) > 1000      -- Filter BEFORE join
)
SELECT u.name, r.revenue
FROM user_revenue r
JOIN users u ON u.id = r.user_id
WHERE u.region = 'EU';
-- user_revenue: computed from orders only (no user join yet)
-- Then joined to users with region filter
-- Planner may do this automatically, but explicit CTE makes it clear

-- DISTINCT vs GROUP BY:
-- DISTINCT: remove duplicate rows from result
-- GROUP BY: group rows for aggregation
-- For "unique values" queries: both can work but may have different costs:
SELECT DISTINCT user_id FROM orders WHERE status = 'COMPLETED';
SELECT user_id FROM orders WHERE status = 'COMPLETED' GROUP BY user_id;
-- DISTINCT: often uses Sort + Unique
-- GROUP BY: often uses HashAggregate
-- HashAggregate is usually faster; DISTINCT is cleaner for the intent
-- But check EXPLAIN — planner may choose the same plan for both
```

## Section 7: CTEs and Subqueries

**Q12. How do CTEs interact with query optimization — when are they "optimization fences"?**
A: A CTE (Common Table Expression) in PostgreSQL 12+ is, by default, inlined into the parent query — the planner can optimise across the CTE boundary. But before PostgreSQL 12, and for CTEs marked `MATERIALIZED`, the CTE is evaluated once and its result stored, creating an optimization fence:

```sql
-- PostgreSQL 12+: CTEs are inlined by default (NOT materialized)
WITH recent_orders AS (
    SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '7 days'
)
SELECT * FROM recent_orders WHERE user_id = 'u-42';
-- PostgreSQL 12+: planner inlines the CTE
-- Effective query: SELECT * FROM orders WHERE created_at > ... AND user_id = 'u-42'
-- Index on (user_id, created_at) can be used

-- Pre-PostgreSQL 12: CTEs were ALWAYS materialized (optimization fence)
-- PostgreSQL 12+: you can force materialization:
WITH recent_orders AS MATERIALIZED (
    SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '7 days'
)
SELECT * FROM recent_orders WHERE user_id = 'u-42';
-- Materializes recent_orders first (all 7-day orders), THEN filters by user_id
-- Index on user_id NOT used — filters applied after materialization
-- This is the correct behaviour if you want to reuse the CTE result multiple times
-- without re-executing the CTE each time it's referenced

-- When to use MATERIALIZED (forcing the fence):
-- 1. CTE referenced multiple times and re-execution is expensive:
WITH expensive_aggregate AS MATERIALIZED (
    SELECT user_id, SUM(total) AS revenue
    FROM orders GROUP BY user_id
    -- Expensive: computed once, reused twice below
)
SELECT e.user_id, e.revenue, u.name
FROM expensive_aggregate e
JOIN users u ON u.id = e.user_id
WHERE e.revenue > (SELECT AVG(revenue) FROM expensive_aggregate);
--                                              ↑ Second reference — reuses materialized result

-- 2. CTE contains volatile functions that should run once:
WITH snapshot AS MATERIALIZED (
    SELECT *, NOW() AS snapshot_time FROM orders  -- NOW() called once
)
SELECT * FROM snapshot WHERE snapshot_time < created_at;

-- When NOT to use MATERIALIZED (default inline is better):
-- Simple filters/projections where pushdown improves performance
-- Queries where the outer WHERE narrows the CTE result significantly
```

```sql
-- Subquery vs JOIN — when does it matter?

-- Correlated subquery — re-executes for each outer row: O(N×M)
-- Can be catastrophic for large tables:
SELECT o.id, o.total,
    (SELECT name FROM users WHERE id = o.user_id) AS user_name  -- Correlated!
FROM orders o
WHERE o.status = 'COMPLETED';
-- For 100K orders: 100K subquery executions → 100K index seeks on users
-- But: PostgreSQL often optimises simple correlated subqueries to a join automatically

-- Verify by checking EXPLAIN:
EXPLAIN SELECT o.id,
    (SELECT name FROM users WHERE id = o.user_id) AS user_name
FROM orders o WHERE o.status = 'COMPLETED';
-- If plan shows: "InitPlan" or "SubPlan" per outer row → correlated, potentially slow
-- If plan shows: join node → planner converted to join automatically (good)

-- Safe rewrite as explicit JOIN (always efficient):
SELECT o.id, o.total, u.name AS user_name
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'COMPLETED';

-- EXISTS vs IN vs JOIN — for semi-joins:
-- BAD: IN with subquery (materializes subquery first):
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE total > 1000);
-- PostgreSQL often converts this to a hash semi-join anyway

-- BETTER: EXISTS (short-circuits on first match):
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.user_id = u.id AND o.total > 1000
);
-- Stops checking orders for a user as soon as one matching order found
-- PostgreSQL often plans IN and EXISTS identically — verify with EXPLAIN

-- BEST: explicit JOIN or JOIN LATERAL for complex cases:
SELECT DISTINCT u.id, u.name
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.total > 1000;
-- DISTINCT removes duplicates if user has multiple qualifying orders
-- Or: use a semi-join hint in newer PostgreSQL versions
```

## Section 8: Statistics and the Planner

**Q13. How do you diagnose and fix bad row count estimates — the root cause of most plan failures?**
A: The planner's cost estimates are only as good as the statistics it has. When estimates are wrong by orders of magnitude, the planner chooses wrong plans. Diagnosing and fixing statistics is often more impactful than rewriting the query:

```sql
-- Diagnosing estimate vs actual mismatch:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 'u-42' AND status = 'COMPLETED';

-- Look for large gaps:
-- rows=5 (estimate) vs actual rows=15000 → planner underestimates → wrong plan
-- rows=15000 (estimate) vs actual rows=5 → planner overestimates → wrong plan

-- Common causes and fixes:

-- 1. Stale statistics (ANALYZE not run recently):
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'orders';
-- If last_autoanalyze is hours/days old on a busy table: run ANALYZE
ANALYZE orders;

-- 2. Low statistics target (not enough samples for accurate estimates):
-- Default: statistics_target = 100 (100 sample values per column)
-- For high-cardinality columns or skewed distributions: increase target
ALTER TABLE orders ALTER COLUMN user_id SET STATISTICS 500;
ANALYZE orders;  -- Recompute with more samples
-- Higher target → more accurate estimates → better plans
-- Downside: ANALYZE takes longer, pg_statistic table grows

-- 3. Correlated column statistics (planner assumes independence):
-- Planner estimates P(A AND B) = P(A) × P(B) (independence assumption)
-- But: status='COMPLETED' and paid_at IS NOT NULL are highly correlated
-- → Planner underestimates rows matching both conditions

-- Fix: create extended statistics for correlated columns:
CREATE STATISTICS orders_status_paid_stats (dependencies)
    ON status, paid_at FROM orders;
ANALYZE orders;
-- Now planner knows about the correlation between status and paid_at
-- Better estimates for queries filtering on both columns

-- Check if extended statistics are being used:
SELECT * FROM pg_stats_ext WHERE tablename = 'orders';

-- 4. Highly skewed data:
-- status column: 95% COMPLETED, 3% PENDING, 2% CANCELLED
-- Default statistics may not capture this accurately:
SELECT most_common_vals, most_common_freqs
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';
-- If freqs don't match reality: run ANALYZE with higher statistics target
```

```sql
-- plan_cache_mode and prepared statements:

-- Prepared statements cache the plan — may use wrong plan after data changes:
PREPARE get_orders (uuid) AS
    SELECT * FROM orders WHERE user_id = $1;

-- First 5 executions: PostgreSQL uses a generic plan (parameterised, no constant folding)
-- After 5 executions: switches to custom plan if it's cheaper
-- Problem: if data distribution changes after the plan is cached,
--          the cached plan may be suboptimal

-- Force re-planning:
DEALLOCATE get_orders;
PREPARE get_orders (uuid) AS SELECT * FROM orders WHERE user_id = $1;

-- Or force always custom plans (recalculate per execution):
SET plan_cache_mode = 'force_custom_plan';
-- Slower planning, always optimal plan for current statistics
-- Useful for: parameters with highly skewed distributions where generic plan fails

-- pg_hint_plan extension — last resort for forcing specific plans:
-- /*+ IndexScan(orders orders_user_id_idx) */ SELECT ...
-- Not built-in — requires extension installation
-- Use only when statistics are correct and planner still picks wrong plan
```

## Section 9: Practical Patterns

**Q14. What is the N+1 query problem in application code and how do you fix it at the SQL level?**
A: The N+1 problem occurs when an application fetches a list of N records, then executes one additional query per record to fetch related data — resulting in N+1 database round trips instead of 1 or 2:

```typescript
// N+1 in application code:

// BAD — N+1 pattern:
const orders = await db.query('SELECT * FROM orders WHERE status = $1', ['COMPLETED']);
// → 1 query returns 1000 orders

for (const order of orders) {
    const user = await db.query('SELECT * FROM users WHERE id = $1', [order.userId]);
    // → 1 query per order = 1000 additional queries
    order.user = user.rows[0];
}
// Total: 1001 queries → catastrophic for large result sets

// GOOD — single JOIN:
const result = await db.query(`
    SELECT
        o.id,
        o.total,
        o.status,
        u.id AS user_id,
        u.name AS user_name,
        u.email AS user_email
    FROM orders o
    JOIN users u ON u.id = o.user_id
    WHERE o.status = 'COMPLETED'
`);
// Total: 1 query → orders + users fetched together

// GOOD — two queries with IN (when JOIN is too broad):
const orders = await db.query('SELECT * FROM orders WHERE status = $1', ['COMPLETED']);
const userIds = [...new Set(orders.rows.map(o => o.userId))];

const users = await db.query(
    'SELECT id, name, email FROM users WHERE id = ANY($1)',
    [userIds]   // One query for all users at once
);
const userMap = new Map(users.rows.map(u => [u.id, u]));
for (const order of orders.rows) {
    order.user = userMap.get(order.userId);
}
// Total: 2 queries → dramatically better than 1001
```

```sql
-- SQL-level batch loading with JSON aggregation:
-- Return orders with their items, nested as JSON — one query:
SELECT
    o.id,
    o.total,
    o.status,
    json_agg(
        json_build_object(
            'id',       oi.id,
            'quantity', oi.quantity,
            'price',    oi.unit_price,
            'product',  p.name
        ) ORDER BY oi.id
    ) AS items
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.user_id = 'u-42'
GROUP BY o.id, o.total, o.status;

-- Result: each row contains the full nested structure
-- Application can deserialise JSON directly — no N+1 needed
-- json_agg returns NULL if no items — use COALESCE(json_agg(...), '[]'::json)

-- array_agg for simple ID lists:
SELECT
    o.id,
    o.total,
    array_agg(oi.product_id ORDER BY oi.id) AS product_ids
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, o.total;
```

**Q15. How do you optimize a slow dashboard query that aggregates across millions of rows?**
A: Dashboard queries over large tables are a common performance bottleneck. The solutions form a hierarchy from low-effort to high-effort, and most production systems need multiple layers:

```sql
-- Scenario: daily revenue dashboard — sum of completed orders by day, last 90 days
-- Table: 500M rows in orders

-- Attempt 1: naive aggregate (slow — scans 90 days of 500M rows):
SELECT
    DATE_TRUNC('day', created_at) AS day,
    SUM(total) AS revenue,
    COUNT(*) AS order_count
FROM orders
WHERE status = 'COMPLETED'
  AND created_at > NOW() - INTERVAL '90 days'
GROUP BY 1
ORDER BY 1;
-- Index on (status, created_at): may help if status is selective
-- But: counting and summing still requires touching every row in range

-- Layer 1: partial index to narrow scan:
CREATE INDEX ON orders (created_at)
WHERE status = 'COMPLETED';
-- Smaller index (only completed orders), better scan efficiency

-- Layer 2: covering index to avoid heap:
CREATE INDEX ON orders (created_at, total)
WHERE status = 'COMPLETED';
-- Index-Only Scan: never touches heap pages for total column
-- Better: but still O(N) for 90 days of data

-- Layer 3: materialized view — pre-aggregate at write time:
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT
    DATE_TRUNC('day', created_at) AS day,
    SUM(total) AS revenue,
    COUNT(*) AS order_count
FROM orders
WHERE status = 'COMPLETED'
GROUP BY 1;

CREATE UNIQUE INDEX ON daily_revenue (day);

-- Dashboard query: O(90) instead of O(500M):
SELECT day, revenue, order_count
FROM daily_revenue
WHERE day > NOW() - INTERVAL '90 days'
ORDER BY day;

-- Refresh strategy:
-- Full refresh (simple, locks view briefly):
REFRESH MATERIALIZED VIEW daily_revenue;
-- Concurrent refresh (no lock, requires unique index):
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;

-- Schedule refresh: pg_cron, or application-level scheduler:
-- SELECT cron.schedule('refresh-revenue', '*/10 * * * *',
--     'REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue');
-- Every 10 minutes: dashboard is max 10 minutes stale
```

```sql
-- Layer 4: summary table with incremental updates:
-- For real-time accuracy without full refresh overhead:

CREATE TABLE daily_revenue_summary (
    day          DATE NOT NULL PRIMARY KEY,
    revenue      NUMERIC(15,2) NOT NULL DEFAULT 0,
    order_count  INT NOT NULL DEFAULT 0,
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Trigger: update summary on every order completion:
CREATE OR REPLACE FUNCTION update_daily_revenue()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO daily_revenue_summary (day, revenue, order_count)
    VALUES (DATE_TRUNC('day', NEW.created_at), NEW.total, 1)
    ON CONFLICT (day) DO UPDATE SET
        revenue      = daily_revenue_summary.revenue + EXCLUDED.revenue,
        order_count  = daily_revenue_summary.order_count + 1,
        updated_at   = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trig_daily_revenue
AFTER INSERT ON orders
FOR EACH ROW
WHEN (NEW.status = 'COMPLETED')
EXECUTE FUNCTION update_daily_revenue();

-- Dashboard: O(90) → instant, always up to date:
SELECT day, revenue, order_count
FROM daily_revenue_summary
WHERE day > NOW() - INTERVAL '90 days'
ORDER BY day;

-- Caveat: handle status changes (PENDING → COMPLETED):
-- Trigger on UPDATE as well, adjust delta based on OLD vs NEW status
```

## Section 10: Scenario-Based Questions

**Q16. "A query was fast last month but is now taking 30 seconds. The table has grown 10x. Walk through your diagnosis."**
A: Performance regression after table growth almost always traces to one of three causes: the planner switched from an index scan to a seq scan as the table grew past a threshold, the index has bloated, or the query is doing more work than it should be:

```sql
-- Step 1: Run EXPLAIN ANALYZE and compare plan to last month:
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE user_id = 'u-42' ORDER BY created_at DESC LIMIT 20;

-- Look for:
-- Was it Index Scan, now Seq Scan? → Table grew past the planner's crossover point
-- Is Sort node present that wasn't before? → Index not covering new ORDER BY
-- Are actual rows >> estimated rows? → Stale statistics

-- Step 2: Check when ANALYZE last ran:
SELECT relname, last_autoanalyze, last_analyze, n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'orders';
-- If table grew 10x and autoanalyze threshold (20% change) was crossed → should have run
-- If last_autoanalyze is old: autovacuum may be falling behind

-- Step 3: Force fresh statistics and re-check:
ANALYZE orders;
EXPLAIN (ANALYZE, BUFFERS) <same query>;
-- If plan improves: statistics were stale, autovacuum needs tuning

-- Step 4: Check index usage and bloat:
SELECT
    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY idx_scan DESC;
-- If index_size grew disproportionately: index bloat
-- If idx_scan dropped to 0 on a key index: planner stopped using it

-- Step 5: Check if the index is still appropriate:
-- At 10x data: the planner's break-even point shifts
-- A 5% selectivity index is used at 1M rows but skipped at 10M rows
-- because 5% of 10M = 500K rows = many random heap reads

-- Fix A: partial index (reduce index size to stay selective):
CREATE INDEX ON orders (user_id, created_at DESC)
WHERE status != 'ARCHIVED';
-- If 90% of 10M rows are archived: this index covers only 1M active rows
-- Planner uses it because it's selective again

-- Fix B: tuning work_mem for sort-heavy queries:
SET work_mem = '64MB';
-- If the Sort node was spilling to disk (Sort Method: external merge):
-- More work_mem keeps sort in RAM → faster

-- Fix C: partition the table (if growth is time-based):
-- 10M rows in one table → 10 monthly partitions of 1M each
-- Queries with date filters: only relevant partition scanned
-- Each partition has its own small indexes → stays efficient
```

**Q17. "Write an optimized query to paginate through 10 million orders for a user, showing 20 at a time, with filters on status and date range."**
A: This is a compound optimization problem combining index design, keyset pagination, sort avoidance, and covering indexes — each component builds on the others:

```sql
-- The optimal solution, step by step:

-- Step 1: Design the index for this exact query pattern:
CREATE INDEX ON orders (user_id, status, created_at DESC)
INCLUDE (id, total, shipping_address_id);
-- user_id:     equality filter — the leading column
-- status:      equality filter — second column (when filtered)
-- created_at:  range filter + ORDER BY — last key column, DESC matches query
-- INCLUDE:     columns needed by SELECT — enables Index-Only Scan

-- Step 2: First page query:
SELECT id, total, status, created_at
FROM orders
WHERE user_id    = $1                        -- $1 = 'u-42'
  AND status     = $2                        -- $2 = 'COMPLETED' (optional filter)
  AND created_at >= $3                       -- $3 = start of date range
  AND created_at <  $4                       -- $4 = end of date range
ORDER BY created_at DESC, id DESC            -- Tiebreak on id for stable pagination
LIMIT 20;
-- Plan: Index Only Scan (all columns in index), sort avoidance (index ordered DESC)
-- No Sort node, no heap access, stops after 20 rows

-- Step 3: Subsequent pages — keyset pagination:
SELECT id, total, status, created_at
FROM orders
WHERE user_id    = $1
  AND status     = $2
  AND created_at >= $3
  AND created_at <  $4
  AND (created_at, id) < ($5, $6)           -- $5 = last_created_at, $6 = last_id
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- Seek directly to the cursor position — O(log N) regardless of page number
-- Page 500,000 is as fast as page 1

-- Step 4: Handle optional status filter gracefully:
-- If status is optional (user can filter or not), one query won't satisfy both indexes:

-- Option A: two separate queries (simplest):
-- If status provided: WHERE user_id = $1 AND status = $2 AND created_at ...
-- If status omitted:  WHERE user_id = $1 AND created_at ...

-- Option B: index on (user_id, created_at DESC) without status:
CREATE INDEX ON orders (user_id, created_at DESC)
INCLUDE (id, total, status);
-- Filter status in application or as a post-index filter
-- Works when status is selective enough to not impact performance much

-- Option C: partial indexes per status:
CREATE INDEX ON orders (user_id, created_at DESC)
WHERE status = 'COMPLETED';
CREATE INDEX ON orders (user_id, created_at DESC)
WHERE status = 'PENDING';
-- Smaller indexes, used when status filter is present in query
-- Query without status filter: uses general index on (user_id, created_at)

-- Step 5: The full pagination function in application code:
async function getOrderPage(params: {
    userId: string;
    status?: string;
    startDate: Date;
    endDate: Date;
    cursor?: { createdAt: Date; id: string };
    pageSize: number;
}): Promise<{ orders: Order[]; nextCursor: string | null }> {

    const { userId, status, startDate, endDate, cursor, pageSize } = params;

    const rows = await db.query(`
        SELECT id, total, status, created_at
        FROM orders
        WHERE user_id    = $1
          AND ($2::text IS NULL OR status = $2)
          AND created_at >= $3
          AND created_at <  $4
          AND ($5::timestamptz IS NULL OR (created_at, id) < ($5, $6::uuid))
        ORDER BY created_at DESC, id DESC
        LIMIT $7
    `, [
        userId,
        status ?? null,
        startDate,
        endDate,
        cursor?.createdAt ?? null,
        cursor?.id ?? null,
        pageSize + 1,        // Fetch one extra to detect if there's a next page
    ]);

    const hasNextPage = rows.length > pageSize;
    const orders = hasNextPage ? rows.slice(0, pageSize) : rows;
    const last = orders[orders.length - 1];

    return {
        orders,
        nextCursor: hasNextPage
            ? JSON.stringify({ createdAt: last.created_at, id: last.id })
            : null,
    };
}
```

## Quick Reference Table

| Optimization | What it prevents | How to verify | Common mistake |
|---|---|---|---|
| Avoid `SELECT *` | Over-fetching columns, prevents Index-Only Scan, exposes sensitive data, breaks on schema changes | Check network transfer size; `EXPLAIN` should show `Index Only Scan` with explicit columns | Using `SELECT *` in ORMs with `findAll()` — always specify fields |
| Explicit column list | TOAST decompression of unneeded large columns, ambiguous column names in JOINs | `EXPLAIN (BUFFERS)` shows `shared hit` count — fewer hits with explicit columns | Selecting `body` or `avatar` in list queries — save for detail view only |
| WHERE on indexed column | Sequential scans on large tables | `EXPLAIN` shows `Seq Scan` with high row count → missing index or anti-pattern | Wrapping indexed column in function: `DATE(created_at)` — rewrite as range |
| Avoid function on column | Index bypass from wrapping column in function | `EXPLAIN` shows `Filter` instead of `Index Cond` | `WHERE UPPER(email)` — use expression index or rewrite |
| LIMIT + ORDER BY | Full table sort before returning small result | `EXPLAIN` should show no `Sort` node when index matches ORDER BY | `LIMIT` without `ORDER BY` — non-deterministic results |
| Keyset pagination | Offset pagination degrading O(page_number) | Page 100 should take same time as page 1 | `OFFSET 9900` — scans and discards 9900 rows per page |
| Sort avoidance | Explicit Sort node for ordered queries | `EXPLAIN`: no `Sort` node = sort avoidance achieved | Wrong index column order or direction doesn't match `ORDER BY` |
| Covering index (INCLUDE) | Heap access for indexed queries | `EXPLAIN` shows `Index Only Scan` (not `Index Scan`) | INCLUDE columns that are too wide — index becomes bloated |
| Predicate pushdown | Joins computed before filters narrow row set | Filters appear below join node in `EXPLAIN` tree | `LIMIT` or `DISTINCT` in subquery preventing pushdown |
| Fresh statistics (ANALYZE) | Wrong row estimates → wrong plan | Estimated vs actual rows gap in `EXPLAIN ANALYZE` | Running `EXPLAIN` without `ANALYZE` — sees estimates not actuals |
| Keyset over OFFSET | OFFSET performance degrades linearly with page number | `EXPLAIN ANALYZE` actual time should be flat across pages | Using OFFSET for APIs where clients request arbitrary pages |
| Avoid N+1 | Hundreds of queries per request | Check slow query log for many identical queries differing only in parameter | ORM lazy-loading associations in a loop |
| Materialized view | Repeated expensive aggregations over huge tables | Dashboard query: `O(days)` not `O(total_rows)` | Forgetting to refresh — stale data without `REFRESH MATERIALIZED VIEW` |
| JOIN vs correlated subquery | Per-row subquery execution (correlated subquery in SELECT) | `EXPLAIN` shows `SubPlan` or `InitPlan` per outer row | Scalar subquery in SELECT list for each row — replace with JOIN |

**Tip for interviews:** Five things separate strong candidates on PostgreSQL query optimization: (1) being able to **read an `EXPLAIN (ANALYZE, BUFFERS)` output fluently** — specifically knowing that the gap between estimated rows and actual rows is the root cause of most plan failures, that `Rows Removed by Filter` indicates wasted work that an index could prevent, and that `shared read` in Buffers means disk I/O while `shared hit` means cache — and knowing that fixing stale statistics with `ANALYZE` is often the highest-leverage single action; (2) explaining **why WHERE clause column order doesn't matter** but the nature of the condition does — that the planner evaluates all conditions together using statistics, so `WHERE a = 1 AND b = 2` produces the same plan regardless of order, but wrapping a column in a function (`DATE(col)`) or doing a leading-wildcard `LIKE` silently bypasses the index and forces a sequential scan; (3) articulating the **keyset pagination advantage over OFFSET** — that `OFFSET N` forces scanning and discarding N rows making page 1000 dramatically slower than page 1, while keyset pagination (`WHERE (created_at, id) < ($last_ts, $last_id)`) turns page navigation into a O(log N) index seek regardless of depth, and that this requires a composite index matching the ORDER BY columns and directions; (4) knowing the **three-way interaction between `LIMIT`, `ORDER BY`, and sort avoidance** — that `LIMIT` changes the planner's cost model (prefers plans with low startup cost over low total cost), that sort avoidance requires the index to match the ORDER BY columns and directions exactly, and that a `Sort` node in `EXPLAIN` above a `LIMIT` means you're sorting all N rows to find the top K — the most common avoidable performance issue in pagination queries; and (5) understanding **when to escalate from index optimization to materialization** — that some aggregate queries are fundamentally O(N) regardless of indexing and the right solution is a materialized view or summary table with incremental updates, and being able to describe `REFRESH MATERIALIZED VIEW CONCURRENTLY` (requires unique index, no lock) vs regular refresh (brief lock) as the operational tradeoff.
