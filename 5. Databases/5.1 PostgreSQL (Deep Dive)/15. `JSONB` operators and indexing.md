# PostgreSQL `JSONB` Operators and Indexing — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is JSONB, how does it differ from JSON, and when do you choose one over the other?**
A: PostgreSQL has two JSON storage types. `JSON` stores the raw text verbatim — it preserves whitespace, duplicate keys, and key ordering exactly as written. `JSONB` decomposes the JSON into a binary representation on write, discarding whitespace, deduplicating keys (last value wins), and sorting keys internally. The binary format makes reads dramatically faster and enables indexing:

```
JSON vs JSONB — storage and behaviour:

  Input: '{"b": 2, "a": 1, "a": 99}'

  JSON stores:  '{"b": 2, "a": 1, "a": 99}'   ← verbatim text preserved
  JSONB stores: {"a": 99, "b": 2}              ← parsed, deduped, keys sorted

  JSON characteristics:
    Write: fast (no parsing — raw text stored)
    Read:  slower (must parse text on every read)
    Index: not supported
    Duplicate keys: preserved (both "a": 1 and "a": 99 kept)
    Key order: preserved exactly

  JSONB characteristics:
    Write: slightly slower (parsing + binary conversion on write)
    Read:  much faster (binary already parsed)
    Index: GIN, B-tree on expressions, GiST
    Duplicate keys: last value wins ("a": 99 kept, "a": 1 discarded)
    Key order: alphabetical internally (not visible to queries)
```

```sql
-- The practical difference in action:
SELECT '{"b": 2, "a": 1, "a": 99}'::json;
-- {"b": 2, "a": 1, "a": 99}   ← verbatim

SELECT '{"b": 2, "a": 1, "a": 99}'::jsonb;
-- {"a": 99, "b": 2}            ← deduped, sorted

-- Key order in JSON is preserved (but meaningless for queries):
SELECT '{"z": 1, "a": 2}'::json->>'z';   -- '1'
SELECT '{"z": 1, "a": 2}'::jsonb->>'z';  -- '1' (same result, different internal representation)

-- JSONB equality ignores key order:
SELECT '{"a": 1, "b": 2}'::jsonb = '{"b": 2, "a": 1}'::jsonb;  -- true
SELECT '{"a": 1, "b": 2}'::json  = '{"b": 2, "a": 1}'::json;   -- false (text comparison)
```

```sql
-- When to choose JSON:
--   You need to preserve exact input format (audit logs, debugging)
--   You store JSON only to pass it through — never query inside it
--   You have a write-heavy workload where parse overhead matters
--   You need to preserve duplicate keys (unusual)

-- When to choose JSONB (almost always):
--   You query inside the JSON (key access, containment, path expressions)
--   You need to index the JSON column or fields within it
--   You compare or aggregate JSON values
--   You use any of the JSONB operators (@>, ?, ?|, ?&, @?)
--   Speed of reads matters more than speed of writes

-- Rule: default to JSONB. Use JSON only for specific verbatim-preservation needs.

-- Storage size comparison:
SELECT
    pg_column_size('{"name":"Alice","age":30,"active":true}'::json)  AS json_size,
    pg_column_size('{"name":"Alice","age":30,"active":true}'::jsonb) AS jsonb_size;
-- json_size:  42 bytes (raw text)
-- jsonb_size: 56 bytes (binary with metadata)
-- JSONB is slightly larger for small documents due to metadata overhead
-- For large documents (>200 bytes): JSONB often compresses to similar or smaller size
-- PostgreSQL TOAST compresses both types for large values
```

**Q2. What is the internal binary structure of JSONB and why does it enable fast operations?**
A: JSONB stores documents as a tree of typed nodes in a compact binary format. Each node records its type (object, array, string, number, boolean, null), its length, and for objects, an offset table that enables O(1) key lookup without scanning:

```
JSONB binary layout (simplified):

  Document: {"user": {"id": 42, "name": "Alice"}, "active": true}

  Binary tree:
    [Object: 2 keys]
      [Key: "active"] → [Boolean: true]
      [Key: "user"]   → [Object: 2 keys]
                          [Key: "id"]   → [Integer: 42]
                          [Key: "name"] → [String: "Alice"]

  Each object node contains an offset table:
    {"id": offset_of_id_value, "name": offset_of_name_value}
  → Key lookup: binary search on sorted keys → O(log K) where K = number of keys
  → No need to scan the entire document for each key access

  Contrast with JSON (text):
    To find "name" inside "user": parse char by char from the start
    → O(document_length) for every key access

  JSONB advantages:
    1. Key access: O(log K) via binary search on sorted key offsets
    2. Type information stored: no parsing needed (is it a string? number?)
    3. Numbers stored as numeric (not string) → direct comparison
    4. Enables containment check (@>) by tree traversal, not string matching
    5. Indexing: GIN can extract individual keys/values from binary structure
```

```sql
-- Observing JSONB's type system:
SELECT jsonb_typeof('{"a": 1}'::jsonb);          -- 'object'
SELECT jsonb_typeof('[1, 2, 3]'::jsonb);          -- 'array'
SELECT jsonb_typeof('"hello"'::jsonb);            -- 'string'
SELECT jsonb_typeof('42'::jsonb);                 -- 'number'
SELECT jsonb_typeof('true'::jsonb);               -- 'boolean'
SELECT jsonb_typeof('null'::jsonb);               -- 'null'

-- Per-field type:
SELECT jsonb_typeof('{"a": 1, "b": "hello", "c": true}'::jsonb -> 'a');  -- 'number'
SELECT jsonb_typeof('{"a": 1, "b": "hello", "c": true}'::jsonb -> 'b');  -- 'string'

-- Numbers are stored as numeric — direct comparison works:
SELECT '{"price": 99.99}'::jsonb -> 'price' > '{"price": 50}'::jsonb -> 'price';
-- true — numeric comparison, not string comparison
-- Contrast: '99.99' > '50' is false as text (lexicographic: '9' < '5' is false, '5' < '9')
-- JSONB stores 99.99 as a number — comparison is numeric
```

## Section 2: Core Operators

**Q3. What are the extraction operators — `->`, `->>`, `#>`, `#>>` — and when do you use each?**
A: PostgreSQL provides two axes of extraction: single-level vs path, and JSONB-typed vs text. The combination gives four operators. Choosing correctly determines whether downstream operations (comparison, casting, indexing) work correctly:

```sql
-- The four extraction operators:

-- -> (single key → JSONB): returns a JSONB value, preserving type
SELECT '{"name": "Alice", "age": 30}'::jsonb -> 'name';
-- "Alice"   ← JSONB string (note: includes quotes in display)
SELECT '{"name": "Alice", "age": 30}'::jsonb -> 'age';
-- 30        ← JSONB number

-- ->> (single key → TEXT): returns a text string, strips type information
SELECT '{"name": "Alice", "age": 30}'::jsonb ->> 'name';
-- Alice     ← TEXT (no quotes)
SELECT '{"name": "Alice", "age": 30}'::jsonb ->> 'age';
-- 30        ← TEXT "30", not number 30

-- #> (path → JSONB): traverses nested path, returns JSONB
SELECT '{"user": {"address": {"city": "NYC"}}}'::jsonb #> '{user,address,city}';
-- "NYC"     ← JSONB string

-- #>> (path → TEXT): traverses nested path, returns text
SELECT '{"user": {"address": {"city": "NYC"}}}'::jsonb #>> '{user,address,city}';
-- NYC       ← TEXT

-- Array indexing (0-based):
SELECT '["apple", "banana", "cherry"]'::jsonb -> 1;
-- "banana"  ← JSONB (index 1)
SELECT '{"items": ["a", "b", "c"]}'::jsonb #> '{items,2}';
-- "c"       ← JSONB (nested array, index 2)
SELECT '{"items": ["a", "b", "c"]}'::jsonb #>> '{items,2}';
-- c         ← TEXT

-- Negative array index (from the end):
SELECT '["a", "b", "c"]'::jsonb -> -1;
-- "c"       ← last element (PostgreSQL 14+)
```

```sql
-- Choosing between -> and ->>:

-- Use -> (JSONB) when:
--   1. You want to compare to another JSONB value:
SELECT data -> 'status' = '"active"'::jsonb    -- JSONB comparison
FROM users WHERE id = 'u-1';

--   2. You're doing containment or existence checks:
SELECT data -> 'tags'                           -- Returns JSONB array
FROM posts WHERE (data -> 'tags') @> '["postgresql"]'::jsonb;

--   3. You're aggregating JSONB values:
SELECT json_agg(data -> 'user')
FROM orders;

-- Use ->> (TEXT) when:
--   1. You compare to a text literal:
SELECT * FROM users WHERE data ->> 'email' = 'alice@example.com';
-- TEXT = TEXT: correct

--   2. You cast to a specific type:
SELECT * FROM orders WHERE (data ->> 'total')::numeric > 100;
-- Cast text to numeric for comparison

--   3. You use in a LIKE or pattern match:
SELECT * FROM users WHERE data ->> 'name' ILIKE '%alice%';

--   4. You display the value to end users:
SELECT data ->> 'name' AS display_name FROM users;

-- CRITICAL: never compare ->> to a non-text value without casting:
-- BAD: (data ->> 'score') > 90   ← text comparison: '9' > '8', but '85' > '9' is false!
-- GOOD: (data ->> 'score')::int > 90   ← cast first, then numeric comparison
```

```sql
-- Null handling — the JSONB null vs SQL NULL distinction:

-- JSONB null (the JSON value null):
SELECT '{"value": null}'::jsonb -> 'value';
-- Returns: null (JSONB null — not SQL NULL)
SELECT jsonb_typeof('{"value": null}'::jsonb -> 'value');
-- Returns: 'null' (the string "null" — it IS a value)
SELECT ('{"value": null}'::jsonb -> 'value') IS NULL;
-- Returns: false — JSONB null is NOT SQL NULL

-- SQL NULL (missing key):
SELECT '{"other": 1}'::jsonb -> 'value';
-- Returns: NULL (SQL NULL — key doesn't exist)
SELECT ('{"other": 1}'::jsonb -> 'value') IS NULL;
-- Returns: true — missing key returns SQL NULL

-- The difference matters for ->>:
SELECT '{"value": null}'::jsonb ->> 'value';
-- Returns: NULL (SQL NULL) — JSONB null converted to SQL NULL by ->>

-- So: both missing key and JSON null return SQL NULL from ->>
-- Use -> to distinguish them:
SELECT ('{"value": null}'::jsonb -> 'value') = 'null'::jsonb;
-- Returns: true — JSON null value (not missing key)
```

**Q4. What are the containment and existence operators — `@>`, `<@`, `?`, `?|`, `?&` — and how do they work?**
A: Containment and existence operators are the workhorses of JSONB querying. They test structural relationships between documents rather than extracting values — and crucially, they are the operators that GIN indexes can accelerate:

```sql
-- @> (contains): does the left JSONB contain all of the right JSONB?
-- "Contains" means: right is a subset of left (structurally)

-- Object containment: every key-value pair in right exists in left
SELECT '{"a": 1, "b": 2, "c": 3}'::jsonb @> '{"a": 1, "c": 3}'::jsonb;
-- true: left has both a=1 and c=3

SELECT '{"a": 1, "b": 2}'::jsonb @> '{"a": 2}'::jsonb;
-- false: left has a=1, not a=2 (value must match too)

-- Array containment: right array is a subset of left array (order doesn't matter)
SELECT '[1, 2, 3, 4]'::jsonb @> '[3, 1]'::jsonb;
-- true: left contains both 3 and 1

SELECT '[1, 2, 3]'::jsonb @> '[1, 2, 4]'::jsonb;
-- false: left doesn't contain 4

-- Nested containment:
SELECT '{"user": {"name": "Alice", "age": 30}}'::jsonb
    @> '{"user": {"name": "Alice"}}';
-- true: left's "user" object contains {name: "Alice"}

-- Practical use — find products with specific attributes:
SELECT * FROM products
WHERE metadata @> '{"category": "electronics", "in_stock": true}';
-- Returns products where metadata has BOTH category=electronics AND in_stock=true
-- GIN index on metadata makes this fast
```

```sql
-- <@ (contained by): inverse of @> (left is subset of right)
SELECT '{"a": 1}'::jsonb <@ '{"a": 1, "b": 2}'::jsonb;
-- true: left is contained in right

-- Useful for checking if a document fits within an allowed structure:
SELECT '{"role": "viewer"}'::jsonb <@ '{"role": "viewer", "permissions": []}'::jsonb;
-- true

-- ? (key/element exists): does the string exist as a top-level key (object) or element (array)?
SELECT '{"name": "Alice", "age": 30}'::jsonb ? 'name';
-- true: "name" is a top-level key

SELECT '{"name": "Alice"}'::jsonb ? 'email';
-- false: "email" key does not exist

SELECT '["apple", "banana"]'::jsonb ? 'apple';
-- true: "apple" is an element of the array

-- Important: ? only checks TOP-LEVEL keys — not nested:
SELECT '{"user": {"name": "Alice"}}'::jsonb ? 'name';
-- false: "name" is nested inside "user", not at top level
-- To check nested: use @> or jsonb_path_exists

-- ?| (any key exists): at least one of the keys exists
SELECT '{"a": 1, "b": 2}'::jsonb ?| ARRAY['b', 'c', 'd'];
-- true: 'b' exists (even though 'c' and 'd' don't)

SELECT '{"a": 1}'::jsonb ?| ARRAY['x', 'y', 'z'];
-- false: none of the keys exist

-- ?& (all keys exist): ALL of the specified keys exist
SELECT '{"a": 1, "b": 2, "c": 3}'::jsonb ?& ARRAY['a', 'b'];
-- true: both 'a' and 'b' exist

SELECT '{"a": 1, "b": 2}'::jsonb ?& ARRAY['a', 'b', 'c'];
-- false: 'c' does not exist
```

```sql
-- @? (jsonpath match): does the jsonpath expression return any result?
-- (PostgreSQL 12+)
SELECT '{"items": [{"price": 150}, {"price": 30}]}'::jsonb
    @? '$.items[*].price ? (@ > 100)';
-- true: at least one item has price > 100

-- @@ (jsonpath predicate): does the jsonpath predicate hold?
-- (PostgreSQL 12+)
SELECT '{"score": 95}'::jsonb @@ '$.score > 90';
-- true: score is greater than 90

-- The difference between @? and @@:
-- @?: "does this path return any matches?" (existence check on path result)
-- @@: "does this boolean jsonpath predicate evaluate to true?"
-- Use @? for "find documents where this path exists with some value"
-- Use @@ for "find documents where this predicate is true"

-- @? with filter:
SELECT * FROM products
WHERE metadata @? '$.variants[*] ? (@.color == "red" && @.stock > 0)';
-- Find products that have at least one red variant with stock > 0
-- GIN index with jsonb_path_ops can accelerate @? and @>
```

**Q5. What are the modification operators and functions — how do you update JSONB non-destructively?**
A: JSONB is immutable — you cannot modify a field in place. Every "update" creates a new JSONB value. PostgreSQL provides the `||` concatenation operator, the `#-` deletion operator, and the `jsonb_set` / `jsonb_insert` functions for surgical modification:

```sql
-- || (concatenate / merge): merge two JSONB objects (right overwrites left for duplicate keys)
SELECT '{"a": 1, "b": 2}'::jsonb || '{"b": 99, "c": 3}'::jsonb;
-- {"a": 1, "b": 99, "c": 3}
-- "b" from left (2) is overwritten by right (99)
-- New key "c" added

-- Practical: update a field in a JSONB column:
UPDATE users
SET metadata = metadata || '{"last_login": "2024-03-15T10:00:00Z"}'
WHERE id = 'u-42';
-- Adds/updates last_login key without disturbing other metadata fields

-- || on arrays: concatenates (does not merge uniquely):
SELECT '[1, 2]'::jsonb || '[2, 3]'::jsonb;
-- [1, 2, 2, 3]   ← duplicates preserved in array concatenation

-- - (delete key / element):
SELECT '{"a": 1, "b": 2, "c": 3}'::jsonb - 'b';
-- {"a": 1, "c": 3}   ← "b" removed

SELECT '["apple", "banana", "cherry"]'::jsonb - 1;
-- ["apple", "cherry"]  ← index 1 (banana) removed

-- #- (delete at path): remove a nested key
SELECT '{"user": {"name": "Alice", "password": "secret"}}'::jsonb #- '{user,password}';
-- {"user": {"name": "Alice"}}  ← nested key removed

-- Update a column by removing a field:
UPDATE users
SET metadata = metadata - 'deprecated_field'
WHERE metadata ? 'deprecated_field';
-- Removes 'deprecated_field' from all users that have it
```

```sql
-- jsonb_set — surgical update of a specific path:
-- jsonb_set(target, path, new_value, create_missing)

SELECT jsonb_set(
    '{"user": {"name": "Alice", "score": 50}}',
    '{user, score}',         -- path array
    '99'::jsonb,             -- new value (must be JSONB)
    false                    -- create_missing: false = don't create if path missing
);
-- {"user": {"name": "Alice", "score": 99}}

-- Create the key if it doesn't exist:
SELECT jsonb_set(
    '{"user": {"name": "Alice"}}',
    '{user, score}',
    '99'::jsonb,
    true   -- create_missing: true = create path if it doesn't exist
);
-- {"user": {"name": "Alice", "score": 99}}

-- Practical update with computation:
UPDATE products
SET metadata = jsonb_set(
    metadata,
    '{price}',
    to_jsonb((metadata->>'price')::numeric * 1.1),  -- 10% price increase
    false
)
WHERE metadata ? 'price';
-- to_jsonb() converts a PostgreSQL value to JSONB

-- jsonb_insert — insert into array at specific position:
SELECT jsonb_insert(
    '{"items": ["a", "b", "c"]}',
    '{items, 1}',          -- Insert at index 1
    '"x"'::jsonb,          -- Value to insert
    false                  -- false = insert BEFORE index, true = insert AFTER
);
-- {"items": ["a", "x", "b", "c"]}

-- Append to array:
UPDATE orders
SET metadata = jsonb_insert(
    metadata,
    '{history, -1}',      -- -1 = after the last element
    to_jsonb(NOW()::text),
    true
)
WHERE id = 'ord-123';
```

```sql
-- jsonb_strip_nulls — remove all null values (useful for cleaning up documents):
SELECT jsonb_strip_nulls('{"a": 1, "b": null, "c": {"d": null, "e": 2}}');
-- {"a": 1, "c": {"e": 2}}  ← nulls removed at all levels

-- jsonb_build_object — construct JSONB programmatically:
SELECT jsonb_build_object(
    'user_id', u.id,
    'name', u.name,
    'order_count', COUNT(o.id),
    'last_order', MAX(o.created_at)
)
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.id = 'u-42'
GROUP BY u.id, u.name;
-- {"user_id": "...", "name": "Alice", "order_count": 5, "last_order": "2024-03-15"}

-- jsonb_object_agg — aggregate rows into a JSONB object:
SELECT jsonb_object_agg(key, value)
FROM (VALUES ('a', 1), ('b', 2), ('c', 3)) AS t(key, value);
-- {"a": 1, "b": 2, "c": 3}

-- json_agg — aggregate JSONB values into an array:
SELECT json_agg(
    jsonb_build_object('id', o.id, 'total', o.total)
    ORDER BY o.created_at DESC
)
FROM orders o
WHERE user_id = 'u-42';
-- [{"id": "ord-1", "total": 99.99}, {"id": "ord-2", "total": 149.00}, ...]
```

## Section 3: Path Navigation

**Q6. How do JSONPath expressions work in PostgreSQL — `jsonb_path_query`, `jsonb_path_exists`, and `jsonb_path_match`?**
A: JSONPath (PostgreSQL 12+) is a path language for navigating and filtering JSONB structures. It goes beyond the `#>` path extraction operator by supporting filters, wildcards, recursive descent, and arithmetic expressions:

```sql
-- JSONPath syntax basics:
-- $              root of the document
-- .key           access object key
-- [N]            access array element N (0-based)
-- [*]            wildcard: all array elements
-- .*             wildcard: all object values
-- ..             recursive descent (all levels)
-- ?(expr)        filter: keep elements where expr is true
-- @              current element (inside a filter)

-- jsonb_path_query — returns all matching values:
SELECT jsonb_path_query(
    '{"items": [{"name": "laptop", "price": 999}, {"name": "mouse", "price": 29}]}',
    '$.items[*].price'
);
-- 999
-- 29   ← two rows, one per match

-- Filter with condition:
SELECT jsonb_path_query(
    '{"items": [{"name": "laptop", "price": 999}, {"name": "mouse", "price": 29}]}',
    '$.items[*] ? (@.price > 100)'
);
-- {"name": "laptop", "price": 999}  ← only expensive items

-- Multiple conditions:
SELECT jsonb_path_query(
    '{"products": [
        {"id": 1, "active": true, "price": 50},
        {"id": 2, "active": false, "price": 200},
        {"id": 3, "active": true, "price": 150}
    ]}',
    '$.products[*] ? (@.active == true && @.price > 100)'
);
-- {"id": 3, "active": true, "price": 150}  ← active AND price > 100

-- Recursive descent with ..**:
SELECT jsonb_path_query(
    '{"a": {"b": {"c": 42}}, "d": 99}',
    '$.**.c'         -- find 'c' at any depth
);
-- 42

-- jsonb_path_query_array — same as jsonb_path_query but returns a JSONB array:
SELECT jsonb_path_query_array(
    '{"items": [{"price": 10}, {"price": 20}, {"price": 30}]}',
    '$.items[*].price'
);
-- [10, 20, 30]   ← single row with array result (useful for application layer)

-- jsonb_path_query_first — returns only the first match:
SELECT jsonb_path_query_first(
    '{"items": [{"price": 10}, {"price": 20}]}',
    '$.items[*].price'
);
-- 10

-- jsonb_path_exists — does any match exist? (returns boolean):
SELECT jsonb_path_exists(
    '{"orders": [{"status": "PENDING"}, {"status": "COMPLETED"}]}',
    '$.orders[*] ? (@.status == "PENDING")'
);
-- true: at least one pending order

-- jsonb_path_match — evaluate a boolean predicate (returns boolean):
SELECT jsonb_path_match(
    '{"score": 95, "grade": "A"}',
    '$.score >= 90'
);
-- true
```

```sql
-- JSONPath in WHERE clauses:
-- @? operator (uses GIN index with jsonb_path_ops):
SELECT * FROM orders
WHERE metadata @? '$.items[*] ? (@.quantity > 10)';
-- Find orders where any item has quantity > 10
-- GIN index with jsonb_path_ops accelerates this

-- @@ operator for simple boolean predicates:
SELECT * FROM users
WHERE profile @@ '$.age >= 18 && $.verified == true';

-- Passing variables to JSONPath (avoid SQL injection in dynamic paths):
SELECT jsonb_path_query(
    document,
    '$.items[*] ? (@.price > $min_price)',
    '{"min_price": 100}'::jsonb    -- variables object
)
FROM product_catalogues;
-- $min_price in the path is replaced by the value from the variables object
-- Safe for user-supplied values — no SQL injection possible

-- Timezone-aware datetime operations in JSONPath:
SELECT jsonb_path_query(
    '{"events": [{"ts": "2024-03-15T10:00:00Z"}, {"ts": "2024-03-16T10:00:00Z"}]}',
    '$.events[*] ? (@.ts.datetime() > "2024-03-15T12:00:00Z".datetime())'
);
-- {"ts": "2024-03-16T10:00:00Z"}  ← event after noon March 15
-- .datetime() converts string to datetime for proper comparison
```

## Section 4: Indexing JSONB

**Q7. What GIN index options exist for JSONB — what is the difference between the default operator class and `jsonb_path_ops`?**
A: PostgreSQL provides two GIN operator classes for JSONB. They differ in what operators they support, how the index is built, and performance characteristics. Choosing the wrong one is a common mistake:

```sql
-- Default GIN operator class (jsonb_ops):
CREATE INDEX ON products USING GIN (metadata);
-- Equivalent to:
CREATE INDEX ON products USING GIN (metadata jsonb_ops);

-- What jsonb_ops indexes:
-- Every KEY at every level → {"user": {"name": "Alice"}} indexes "user" and "name"
-- Every VALUE at every level → indexes "Alice" as a value
-- Each key-value pair as a single entry → for @> operator

-- Supported operators with jsonb_ops:
--   @>   containment (supported)
--   ?    key exists  (supported)
--   ?|   any key     (supported)
--   ?&   all keys    (supported)
--   @?   jsonpath    (supported, but less efficiently)
--   <@   contained by (supported via @> on reversed args)

-- jsonb_path_ops operator class:
CREATE INDEX ON products USING GIN (metadata jsonb_path_ops);

-- What jsonb_path_ops indexes:
-- Only key-path-to-value entries (hashed paths)
-- Does NOT index individual keys separately
-- Much smaller index: fewer entries, tighter structure

-- Supported operators with jsonb_path_ops:
--   @>   containment (supported — primary use case)
--   @?   jsonpath    (supported — optimised)
--   @@   jsonpath predicate (supported)
-- NOT supported:
--   ?    key exists  (NOT supported — cannot check key alone)
--   ?|   any key     (NOT supported)
--   ?&   all keys    (NOT supported)
```

```sql
-- Size comparison — real impact:
-- Table: 1M products with metadata JSONB (avg 20 key-value pairs per document)

-- Default GIN (jsonb_ops):
CREATE INDEX idx_metadata_ops ON products USING GIN (metadata);
-- Index size: ~800MB (indexes every key and value individually)

-- jsonb_path_ops:
CREATE INDEX idx_metadata_path_ops ON products USING GIN (metadata jsonb_path_ops);
-- Index size: ~150MB (5x smaller — only indexes paths, not individual keys)

-- Query performance comparison on @> queries:
-- Both indexes support @> — which is faster?
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products WHERE metadata @> '{"category": "electronics"}';
-- With jsonb_ops:      Bitmap Index Scan: ~5ms, pages_read: 120
-- With jsonb_path_ops: Bitmap Index Scan: ~2ms, pages_read: 30
-- jsonb_path_ops wins for @> because:
--   Fewer index entries → smaller index → fits better in cache → fewer reads

-- But if you need ? (key existence):
SELECT * FROM products WHERE metadata ? 'discount_code';
-- With jsonb_ops:      Uses index → fast
-- With jsonb_path_ops: Seq Scan → slow (? not supported by jsonb_path_ops)
```

```sql
-- Decision guide — which GIN operator class?

-- Use jsonb_path_ops when:
--   Primary queries use @> (containment) or @? (jsonpath)
--   You don't need to query by key existence alone (?)
--   Index size matters (dataset is large)
--   You want maximum @> query performance

-- Use jsonb_ops (default) when:
--   You use ? (key exists), ?|, ?& operators
--   Your queries check if keys exist without caring about values
--   You have varied query patterns and need to cover all operators
--   You're uncertain (it covers more operators)

-- Can you have both? Yes — two indexes on same column:
CREATE INDEX ON products USING GIN (metadata jsonb_ops);       -- for ? queries
CREATE INDEX ON products USING GIN (metadata jsonb_path_ops);  -- for @> queries
-- But: two indexes = double write cost, double storage
-- Profile which operators you actually use before doubling up
```

**Q8. How do you index specific JSONB fields for scalar comparisons — expression indexes on JSONB?**
A: GIN indexes support `@>` and `?` but cannot accelerate scalar comparisons like `WHERE (data->>'price')::numeric > 100` or `WHERE data->>'status' = 'active'`. For these, you need expression indexes that extract the scalar value and index it with a B-tree:

```sql
-- Expression index on a JSONB field:
-- Indexes the extracted text value for exact equality and range comparisons

-- B-tree on extracted text:
CREATE INDEX ON products ((metadata->>'category'));
-- Supports: WHERE metadata->>'category' = 'electronics'
-- Supports: WHERE metadata->>'category' LIKE 'elect%'
-- Does NOT support: WHERE metadata->>'category' > 100 (text comparison of number)

-- B-tree on extracted and cast numeric value:
CREATE INDEX ON products (((metadata->>'price')::numeric));
-- CRITICAL: double parentheses required for cast inside index expression
-- Supports: WHERE (metadata->>'price')::numeric > 100  ← numeric comparison
-- Supports: WHERE (metadata->>'price')::numeric BETWEEN 50 AND 200
-- Query MUST use the SAME expression: ::numeric cast required in WHERE clause

-- B-tree on extracted date:
CREATE INDEX ON events (((metadata->>'occurred_at')::timestamptz));
-- Supports: WHERE (metadata->>'occurred_at')::timestamptz > '2024-01-01'
-- Supports: ORDER BY (metadata->>'occurred_at')::timestamptz  ← sort avoidance!

-- B-tree on nested path:
CREATE INDEX ON orders (((metadata #>> '{shipping,address,city}')::text));
-- Supports: WHERE metadata #>> '{shipping,address,city}' = 'New York'
```

```sql
-- Composite expression index for multi-field JSONB queries:
-- Query: WHERE metadata->>'category' = 'electronics' AND (metadata->>'price')::numeric < 500

-- Option A: two separate expression indexes (planner combines with BitmapAnd):
CREATE INDEX ON products ((metadata->>'category'));
CREATE INDEX ON products (((metadata->>'price')::numeric));

-- Option B: composite expression index (better if both filters are always present):
CREATE INDEX ON products (
    (metadata->>'category'),
    ((metadata->>'price')::numeric)
);
-- Index on (category_text, price_numeric)
-- Query must include BOTH conditions to use this index
-- Smaller than two separate indexes (one vs two index structures)

-- INCLUDE for covering index on JSONB expression:
CREATE INDEX ON products (
    (metadata->>'category')
) INCLUDE (id, (metadata->>'name'), (metadata->>'price'));
-- Can satisfy: SELECT id, metadata->>'name', metadata->>'price'
--              WHERE metadata->>'category' = 'electronics'
-- Via Index-Only Scan — no heap access needed
-- Note: INCLUDE expressions supported in PostgreSQL 13+
```

```sql
-- Partial expression index — only index rows matching a condition:
-- Most products are active — index only inactive ones (rare, high-value queries):
CREATE INDEX ON products (id)
WHERE metadata->>'status' = 'inactive';

-- Index only non-null JSONB fields:
CREATE INDEX ON users ((metadata->>'phone'))
WHERE metadata ? 'phone';
-- Smaller index: only users with phone numbers
-- Used when: WHERE metadata ? 'phone' AND metadata->>'phone' = '555-1234'

-- Functional index with lower() for case-insensitive JSONB queries:
CREATE INDEX ON users (lower(metadata->>'email'));
-- Supports: WHERE lower(metadata->>'email') = lower('Alice@Example.com')
-- Must use lower() in the query to match the index expression
```

**Q9. What is the `jsonb_to_record` / `jsonb_populate_record` approach and when does it help?**
A: When you frequently query JSONB fields as if they were relational columns — especially with complex filters, joins, or ordering — you can extract the JSONB into a typed row using `jsonb_to_record`, or better, project it in a view with computed columns:

```sql
-- jsonb_to_record — extract JSONB into typed columns:
SELECT *
FROM jsonb_to_record('{"name": "Alice", "age": 30, "active": true}'::jsonb)
    AS t(name TEXT, age INT, active BOOLEAN);
-- name  | age | active
-- Alice |  30 | true
-- Typed: age is INT, active is BOOLEAN — not text strings

-- Use in queries to unpack JSONB rows:
SELECT t.name, t.age, t.active
FROM products,
     jsonb_to_record(metadata) AS t(
         name     TEXT,
         price    NUMERIC,
         category TEXT,
         active   BOOLEAN
     )
WHERE t.category = 'electronics' AND t.active = true AND t.price < 500;
-- Cleaner syntax than multiple ->>'key' extractions
-- BUT: does not use indexes — each row must be unpacked (seq scan)

-- jsonb_to_recordset — unpack a JSONB array of objects into rows:
SELECT *
FROM jsonb_to_recordset('[
    {"id": 1, "name": "Alice"},
    {"id": 2, "name": "Bob"}
]'::jsonb) AS t(id INT, name TEXT);
-- id | name
--  1 | Alice
--  2 | Bob

-- Practical: unpack nested JSONB arrays within rows:
SELECT p.id, items.name, items.quantity
FROM orders p,
     jsonb_to_recordset(p.metadata->'items') AS items(
         name     TEXT,
         quantity INT,
         price    NUMERIC
     )
WHERE items.quantity > 5;
-- Each order's items array unpacked into separate rows
-- Filter on unpacked rows
-- Still seq scan — no index on items.quantity inside nested array
```

```sql
-- When to use generated columns instead:
-- If you query the same JSONB fields frequently, extract them as real columns:

ALTER TABLE products
    ADD COLUMN category TEXT GENERATED ALWAYS AS (metadata->>'category') STORED,
    ADD COLUMN price    NUMERIC GENERATED ALWAYS AS ((metadata->>'price')::numeric) STORED;

-- Now create regular B-tree indexes on real columns:
CREATE INDEX ON products (category);
CREATE INDEX ON products (price);
CREATE INDEX ON products (category, price);

-- Queries use regular column syntax and fast B-tree indexes:
SELECT id, category, price FROM products
WHERE category = 'electronics' AND price < 500;
-- Index Scan on (category, price) — fast, no JSONB overhead

-- Tradeoff:
-- Generated columns: real column → fast queries, fast indexes, type-safe
--                    requires schema change, duplicates data (storage overhead)
-- Expression index:  no schema change, query must match exact expression
--                    can be added without ALTER TABLE
-- Choose generated column when: the field is frequently queried,
--   types matter (numeric vs text comparison), or joins are needed on the field
```

## Section 5: Schema Design

**Q10. When should you use JSONB vs relational columns — what are the architectural tradeoffs?**
A: JSONB is not a replacement for relational design — it is a tool for specific situations. Overusing it leads to the "schemaless trap": you lose type safety, foreign keys, aggregation efficiency, and query clarity:

```
JSONB is the right choice when:

  1. Schema is genuinely unknown at design time:
     User-defined fields, custom attributes per product category,
     third-party API responses with evolving structure.
     Electronics have {voltage, wattage}; clothing has {size, material}.
     One JSONB column handles all categories without an EAV table.

  2. Document is always read/written as a whole:
     Configuration blobs, form responses, event payloads.
     You never query "find all users where config.notifications.email = true".
     You just store and retrieve the whole config.

  3. Schema evolves rapidly without downtime:
     Adding a JSONB key does not require ALTER TABLE (no lock, no migration).
     Adding a relational column on a 500M row table: hours-long migration.

  4. Variable-structure data with sparse attributes:
     1000 products, each with 0-50 optional attributes.
     As a relational table: 50 nullable columns, mostly NULL.
     As JSONB: only stores attributes that exist.

Relational columns are the right choice when:

  1. You query the field in WHERE clauses frequently:
     WHERE price < 500: B-tree on price column → O(log N)
     WHERE (metadata->>'price')::numeric < 500: requires cast, expression index

  2. You aggregate, sum, or group by the field:
     SELECT category, AVG(price) GROUP BY category
     On real columns: GroupAggregate or HashAggregate on indexed column
     On JSONB: must extract and cast every row → slower

  3. You need foreign key references:
     REFERENCES other_table(id) only works on real columns
     Cannot enforce FK constraint on a JSONB field

  4. Type safety is critical:
     Real column: INT is always an integer — constraint enforced by DB
     JSONB field: "price" could be "ninety-nine" — app must validate

  5. You join on the field:
     JOIN ON products.category_id = categories.id → fast hash join
     JOIN ON products.metadata->>'category' = categories.name → no FK, slower

JSONB and relational columns together — the hybrid pattern:
  Real columns: id, user_id, created_at, status (frequently queried)
  JSONB column: metadata (rarely queried, variable structure)
  Best of both: fast indexes on structured fields, flexibility for the rest
```

```sql
-- The EAV (Entity-Attribute-Value) anti-pattern that JSONB replaces:
-- BAD — EAV table (common before JSONB was practical):
CREATE TABLE product_attributes (
    product_id UUID REFERENCES products(id),
    key        TEXT NOT NULL,
    value      TEXT NOT NULL,       -- all values as text — no types!
    PRIMARY KEY (product_id, key)
);
-- Query: "find electronics under $500"
SELECT p.id, p.name
FROM products p
JOIN product_attributes pa_cat ON pa_cat.product_id = p.id AND pa_cat.key = 'category'
JOIN product_attributes pa_price ON pa_price.product_id = p.id AND pa_price.key = 'price'
WHERE pa_cat.value = 'electronics'
  AND pa_price.value::numeric < 500;
-- Two joins, type casting, index challenges, complex queries

-- GOOD — JSONB replaces EAV cleanly:
SELECT id, name
FROM products
WHERE metadata @> '{"category": "electronics"}'
  AND (metadata->>'price')::numeric < 500;
-- One table, GIN index for @>, expression index for price comparison
```

**Q11. How do you handle schema validation for JSONB — preventing invalid data at the database level?**
A: Unlike relational columns, JSONB accepts any valid JSON. If you need to enforce structure, you have several options ranging from CHECK constraints to trigger-based validation:

```sql
-- CHECK constraint with jsonb_typeof:
ALTER TABLE users ADD CONSTRAINT metadata_is_object
    CHECK (jsonb_typeof(metadata) = 'object');
-- Prevents: INSERT with metadata = '[1,2,3]' (arrays not allowed)
-- Prevents: INSERT with metadata = '"string"'

-- CHECK constraint for required fields:
ALTER TABLE products ADD CONSTRAINT required_fields
    CHECK (metadata ?& ARRAY['name', 'price', 'category']);
-- Every product must have name, price, and category in metadata

-- CHECK constraint for field type:
ALTER TABLE products ADD CONSTRAINT price_is_numeric
    CHECK (jsonb_typeof(metadata->'price') = 'number');
-- metadata->price must be a JSON number (not a string)

-- CHECK constraint for value range:
ALTER TABLE products ADD CONSTRAINT price_positive
    CHECK ((metadata->>'price')::numeric > 0);
-- price must be positive when present

-- Composite validation:
ALTER TABLE products ADD CONSTRAINT valid_product_metadata CHECK (
    jsonb_typeof(metadata) = 'object'
    AND metadata ?& ARRAY['name', 'price']
    AND jsonb_typeof(metadata->'price') = 'number'
    AND (metadata->>'price')::numeric > 0
    AND (metadata->>'category' IS NULL OR length(metadata->>'category') > 0)
);
```

```sql
-- Trigger-based validation for complex rules:
CREATE OR REPLACE FUNCTION validate_product_metadata()
RETURNS TRIGGER AS $$
DECLARE
    meta JSONB := NEW.metadata;
BEGIN
    -- Must be an object:
    IF jsonb_typeof(meta) != 'object' THEN
        RAISE EXCEPTION 'metadata must be a JSON object';
    END IF;

    -- Required fields:
    IF NOT (meta ?& ARRAY['name', 'price', 'category']) THEN
        RAISE EXCEPTION 'metadata must contain name, price, and category';
    END IF;

    -- Price must be a positive number:
    IF jsonb_typeof(meta->'price') != 'number' THEN
        RAISE EXCEPTION 'metadata.price must be a number';
    END IF;
    IF (meta->>'price')::numeric <= 0 THEN
        RAISE EXCEPTION 'metadata.price must be positive';
    END IF;

    -- Category must be one of the allowed values:
    IF meta->>'category' NOT IN ('electronics', 'clothing', 'books', 'food') THEN
        RAISE EXCEPTION 'Invalid category: %', meta->>'category';
    END IF;

    -- Optional: variants must be an array if present:
    IF meta ? 'variants' AND jsonb_typeof(meta->'variants') != 'array' THEN
        RAISE EXCEPTION 'metadata.variants must be an array';
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER validate_product_metadata_trigger
BEFORE INSERT OR UPDATE OF metadata ON products
FOR EACH ROW EXECUTE FUNCTION validate_product_metadata();
```

## Section 6: Advanced Patterns

**Q12. How do you aggregate and transform JSONB data — building JSON responses directly in SQL?**
A: PostgreSQL's JSONB aggregation functions let you build nested JSON structures directly in SQL, eliminating application-layer assembly loops and reducing round trips:

```sql
-- Build a nested response for an order with its items and user:
SELECT jsonb_build_object(
    'id',        o.id,
    'status',    o.status,
    'total',     o.total,
    'created_at', o.created_at,
    'user', jsonb_build_object(
        'id',    u.id,
        'name',  u.name,
        'email', u.email
    ),
    'items', COALESCE(
        jsonb_agg(
            jsonb_build_object(
                'id',         oi.id,
                'quantity',   oi.quantity,
                'unit_price', oi.unit_price,
                'product', jsonb_build_object(
                    'id',   p.id,
                    'name', p.name
                )
            ) ORDER BY oi.id
        ),
        '[]'::jsonb   -- COALESCE handles NULL from LEFT JOIN with no items
    )
) AS order_json
FROM orders o
JOIN users u ON u.id = o.user_id
LEFT JOIN order_items oi ON oi.order_id = o.id
LEFT JOIN products p ON p.id = oi.product_id
WHERE o.id = 'ord-123'
GROUP BY o.id, o.status, o.total, o.created_at, u.id, u.name, u.email;

-- Output: one row, one column — complete nested JSON for the API response
-- Application receives this and sends it directly — no assembly needed
```

```sql
-- Aggregating a list with JSONB:
SELECT jsonb_build_object(
    'user_id', u.id,
    'name', u.name,
    'order_summary', jsonb_build_object(
        'count',   COUNT(o.id),
        'total',   SUM(o.total),
        'statuses', jsonb_object_agg(o.status, COUNT(*))
    )
)
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.id = 'u-42'
GROUP BY u.id, u.name;

-- {"user_id": "u-42", "name": "Alice",
--  "order_summary": {"count": 5, "total": 450.00, "statuses": {"COMPLETED": 3, "PENDING": 2}}}
```

```sql
-- JSONB in GROUP BY and aggregation:

-- Count by a JSONB field:
SELECT
    metadata->>'category' AS category,
    COUNT(*) AS product_count,
    AVG((metadata->>'price')::numeric) AS avg_price
FROM products
WHERE metadata ? 'price'
GROUP BY metadata->>'category'
ORDER BY product_count DESC;

-- Merge JSONB across rows (union of all keys):
SELECT json_object_agg(key, value)
FROM (
    SELECT DISTINCT key, value
    FROM products,
         jsonb_each(metadata)  -- expand all key-value pairs into rows
    WHERE (metadata->>'category') = 'electronics'
) t;
-- Returns: all unique key-value pairs across all electronics products merged

-- jsonb_each — iterate over all key-value pairs:
SELECT key, value, jsonb_typeof(value) AS type
FROM jsonb_each('{"name": "Alice", "age": 30, "active": true}'::jsonb);
-- key    | value   | type
-- name   | "Alice" | string
-- age    | 30      | number
-- active | true    | boolean

-- jsonb_each_text — like jsonb_each but values as text:
SELECT key, value
FROM jsonb_each_text('{"name": "Alice", "age": 30}'::jsonb);
-- key  | value
-- name | Alice
-- age  | 30
```

```sql
-- Unnesting JSONB arrays with jsonb_array_elements:
SELECT element, jsonb_typeof(element) AS type
FROM jsonb_array_elements('[1, "hello", true, null, {"nested": "obj"}]'::jsonb) AS element;
-- 1               | number
-- "hello"         | string
-- true            | boolean
-- null            | null
-- {"nested":"obj"}| object

-- Practical: find all unique tags across all posts:
SELECT DISTINCT tag
FROM posts,
     jsonb_array_elements_text(metadata->'tags') AS tag
ORDER BY tag;
-- Expands tags array into one row per tag, then deduplicates

-- Find posts tagged with a specific tag (array contains element):
SELECT p.id, p.title
FROM posts p,
     jsonb_array_elements_text(p.metadata->'tags') AS tag
WHERE tag = 'postgresql';
-- Equivalent to: WHERE metadata @> '["postgresql"]'
-- But the GIN index version (@>) is much faster for large tables
```

**Q13. How do you migrate from JSONB to relational columns when JSONB has outgrown its usefulness?**
A: When JSONB fields become frequently queried, joined, or aggregated, the flexibility advantage disappears and the performance/correctness costs accumulate. Migration is a multi-step process that maintains zero downtime:

```sql
-- Step 1: Audit which JSONB fields are actually used and what types they hold:
SELECT
    key,
    COUNT(*) AS rows_with_key,
    COUNT(*) FILTER (WHERE jsonb_typeof(metadata->key) = 'string')  AS string_count,
    COUNT(*) FILTER (WHERE jsonb_typeof(metadata->key) = 'number')  AS number_count,
    COUNT(*) FILTER (WHERE jsonb_typeof(metadata->key) = 'boolean') AS bool_count,
    COUNT(*) FILTER (WHERE jsonb_typeof(metadata->key) = 'null')    AS null_count
FROM products,
     jsonb_object_keys(metadata) AS key
GROUP BY key
ORDER BY rows_with_key DESC;
-- Reveals: which keys exist, how often, and what types
-- "price": 950000 rows, all number → good candidate for numeric column
-- "notes": 12 rows, all string → leave in JSONB (rare, variable)

-- Step 2: Add new columns alongside JSONB (zero downtime):
ALTER TABLE products
    ADD COLUMN category TEXT,
    ADD COLUMN price    NUMERIC(10,2);
-- New columns are NULL for existing rows — no lock beyond the ALTER itself

-- Step 3: Backfill from JSONB:
UPDATE products
SET
    category = metadata->>'category',
    price    = (metadata->>'price')::numeric
WHERE category IS NULL;  -- Only rows not yet backfilled
-- Run in batches to avoid lock contention:
UPDATE products
SET
    category = metadata->>'category',
    price    = (metadata->>'price')::numeric
WHERE id IN (
    SELECT id FROM products WHERE category IS NULL LIMIT 10000
);
-- Repeat until no rows remain
```

```sql
-- Step 4: Create a trigger to keep columns in sync during transition:
CREATE OR REPLACE FUNCTION sync_product_columns()
RETURNS TRIGGER AS $$
BEGIN
    NEW.category := NEW.metadata->>'category';
    NEW.price    := (NEW.metadata->>'price')::numeric;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER sync_product_columns_trigger
BEFORE INSERT OR UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION sync_product_columns();
-- Now: any write to metadata automatically updates the real columns too

-- Step 5: Create indexes on new columns:
CREATE INDEX CONCURRENTLY ON products (category);
CREATE INDEX CONCURRENTLY ON products (price);
-- CONCURRENTLY: no write lock, safe for production

-- Step 6: Migrate queries one by one (deploy incrementally):
-- Old query: WHERE metadata->>'category' = 'electronics'
-- New query: WHERE category = 'electronics'  ← uses B-tree on real column

-- Step 7: Verify correctness:
SELECT COUNT(*) FROM products WHERE category != metadata->>'category';
-- Should return 0 — columns are in sync

-- Step 8: Remove the synced fields from JSONB (optional):
UPDATE products
SET metadata = metadata - 'category' - 'price'
WHERE metadata ? 'category' OR metadata ? 'price';
-- Smaller JSONB documents → less storage, faster reads

-- Step 9: Drop the trigger (no longer needed):
DROP TRIGGER sync_product_columns_trigger ON products;

-- Step 10: Remove expression indexes on JSONB (if they existed):
DROP INDEX IF EXISTS products_metadata_category_idx;
DROP INDEX IF EXISTS products_metadata_price_idx;
```

## Section 7: Testing and Debugging

**Q14. How do you debug and profile JSONB queries — diagnosing why an index is not being used?**
A: JSONB index usage failures are silent — PostgreSQL runs the query as a seq scan without error. Diagnosis requires checking the operator used, the index operator class, and whether the query expression matches the index expression exactly:

```sql
-- Step 1: Confirm the index exists and is valid:
SELECT indexname, indexdef, indisvalid
FROM pg_indexes
JOIN pg_class ON pg_class.relname = pg_indexes.tablename
JOIN pg_index ON pg_index.indrelid = pg_class.oid
    AND pg_index.indexrelid = (
        SELECT oid FROM pg_class WHERE relname = indexname
    )
WHERE tablename = 'products';

-- Step 2: Run EXPLAIN to see if the index is used:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products WHERE metadata @> '{"category": "electronics"}';

-- If showing Seq Scan instead of Bitmap Index Scan:
-- Check 1: Is there a GIN index on metadata?
SELECT indexdef FROM pg_indexes WHERE tablename = 'products';

-- Check 2: Is the operator supported by the index's operator class?
-- Problem: jsonb_path_ops index but querying with ?
EXPLAIN SELECT * FROM products WHERE metadata ? 'discount';
-- If index is jsonb_path_ops: ? is NOT supported → Seq Scan
-- Fix: add a jsonb_ops index for ? queries

-- Check 3: Is the table too small? (planner prefers seq scan for small tables)
SELECT reltuples FROM pg_class WHERE relname = 'products';
-- If < ~1000 rows: planner may skip index
-- Force for testing: SET enable_seqscan = off;

-- Check 4: Stale statistics:
SELECT last_analyze, last_autoanalyze FROM pg_stat_user_tables
WHERE relname = 'products';
ANALYZE products;
EXPLAIN ... -- Re-check after fresh statistics

-- Check 5: Expression index mismatch:
-- Index: CREATE INDEX ON products ((metadata->>'price'))  ← text
-- Query: WHERE (metadata->>'price')::numeric > 100       ← cast to numeric
-- Mismatch: index stores text, query uses numeric cast → different expression
-- Fix: index must match the query exactly:
CREATE INDEX ON products (((metadata->>'price')::numeric));
-- Now: WHERE (metadata->>'price')::numeric > 100 uses the index
```

```sql
-- Checking GIN index utilization statistics:
SELECT
    schemaname,
    tablename,
    indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan AS times_used,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE tablename = 'products'
ORDER BY idx_scan DESC;
-- If idx_scan = 0 for GIN index: never used
-- Likely: queries use operators not supported by the index's operator class
-- Or: all queries use the seq scan path (too selective or table too small)

-- Diagnosing GIN pending list issues (write-heavy tables):
SELECT
    relname AS table_name,
    indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE indexrelname LIKE '%gin%' OR indexrelname LIKE '%metadata%';

-- Check if GIN pending list is large (causing slow reads):
SELECT *
FROM pg_indexes
WHERE tablename = 'products'
  AND indexdef LIKE '%gin%';
-- Then check autovacuum is running:
SELECT last_autovacuum FROM pg_stat_user_tables WHERE relname = 'products';
-- If autovacuum hasn't run recently on a write-heavy table:
-- GIN pending list grows → reads must scan pending list too → slows down
VACUUM products;  -- Manually trigger to flush pending list
```

## Section 8: Scenario-Based Questions

**Q15. "Users report that searching products by metadata attributes is slow. You have a GIN index on the metadata column but `EXPLAIN` shows a sequential scan." Diagnose and fix it.**
A: This is the most common JSONB performance issue. The sequential scan despite a GIN index almost always traces to operator mismatch, expression mismatch, or a query pattern the GIN cannot serve:

```sql
-- Reproduce the issue:
EXPLAIN SELECT * FROM products
WHERE (metadata->>'price')::numeric > 100;
-- Seq Scan on products  (cost=0.00..25431.00 rows=...)
-- Filter: (((metadata->>'price')::numeric) > 100)
-- GIN index on metadata NOT used

-- Root cause: GIN indexes for JSONB do NOT support scalar comparison operators
-- (>, <, >=, <=, BETWEEN) on extracted values
-- GIN supports: @>, ?, ?|, ?&, @?, @@ (containment and existence)
-- GIN does NOT support: ->> extracted value comparisons

-- Fix 1: expression B-tree index (for scalar comparisons):
CREATE INDEX ON products (((metadata->>'price')::numeric));
EXPLAIN SELECT * FROM products WHERE (metadata->>'price')::numeric > 100;
-- Index Scan using products_..._idx  ← expression B-tree used

-- Fix 2: jsonpath with @? (uses GIN jsonb_path_ops):
DROP INDEX IF EXISTS gin_metadata;
CREATE INDEX ON products USING GIN (metadata jsonb_path_ops);
SELECT * FROM products WHERE metadata @? '$.price ? (@ > 100)';
EXPLAIN SELECT * FROM products WHERE metadata @? '$.price ? (@ > 100)';
-- Bitmap Index Scan using GIN index  ← GIN used with jsonb_path_ops

-- Fix 3 (best for frequently-queried fields): generated column + B-tree:
ALTER TABLE products
    ADD COLUMN price_extracted NUMERIC
    GENERATED ALWAYS AS ((metadata->>'price')::numeric) STORED;
CREATE INDEX ON products (price_extracted);
SELECT * FROM products WHERE price_extracted > 100;
-- Regular index scan, no JSONB overhead in the hot path

-- Additional check: was the query using a wrong operator for the GIN type?
-- If index was created with jsonb_path_ops but query uses ?:
EXPLAIN SELECT * FROM products WHERE metadata ? 'discount_code';
-- With jsonb_path_ops GIN: Seq Scan (? not supported)
-- Fix: create a separate jsonb_ops GIN for ? queries:
CREATE INDEX ON products USING GIN (metadata jsonb_ops);
-- Or: use @> to check key existence (supported by jsonb_path_ops):
SELECT * FROM products WHERE metadata @> '{"discount_code": null}'::jsonb;
-- @> with null value: checks that the key exists (any value matches)
-- Actually: @> checks value too — null only matches null
-- Correct way with jsonb_path_ops: @? '$.discount_code'
SELECT * FROM products WHERE metadata @? '$.discount_code';
```

**Q16. "Design the JSONB schema and indexing strategy for a product catalogue with 10 million products, each having 0-100 variable attributes, supporting faceted search (filter by category, price range, multiple attributes simultaneously)."**
A: Faceted search over JSONB requires combining multiple operators and indexes strategically. The key insight is that different query types need different index types, and the highest-frequency filters deserve real columns:

```sql
-- Schema design:
CREATE TABLE products (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- High-frequency filter columns (real columns → fast B-tree):
    category    TEXT NOT NULL,              -- Always filtered, always the same structure
    price       NUMERIC(10,2) NOT NULL,     -- Range filter, sort, aggregate
    brand       TEXT,                       -- Frequent equality filter
    in_stock    BOOLEAN NOT NULL DEFAULT true,

    -- Variable attributes (JSONB → flexible, indexed separately):
    attributes  JSONB NOT NULL DEFAULT '{}',

    -- Derived search column (GIN for full-text):
    search_vec  TSVECTOR GENERATED ALWAYS AS (
        setweight(to_tsvector('english', coalesce(name, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(attributes->>'description', '')), 'B')
    ) STORED
);

-- Index strategy:
-- 1. B-tree indexes on structured filter columns:
CREATE INDEX ON products (category, price);           -- Category + price range
CREATE INDEX ON products (category, brand);           -- Category + brand filter
CREATE INDEX ON products (price) WHERE in_stock = true; -- Price for in-stock only
CREATE INDEX ON products (brand) WHERE brand IS NOT NULL;

-- 2. GIN on attributes for @> containment queries:
CREATE INDEX ON products USING GIN (attributes jsonb_path_ops);
-- For: WHERE attributes @> '{"color": "red"}' (single attribute filter)
-- For: WHERE attributes @> '{"color": "red", "size": "M"}' (multiple)

-- 3. GIN for full-text search:
CREATE INDEX ON products USING GIN (search_vec);

-- 4. Expression indexes for numeric attribute ranges (top attributes only):
-- Profile: which attributes are most commonly range-filtered?
-- For electronics: voltage, wattage, screen_size
CREATE INDEX ON products (((attributes->>'voltage')::numeric))
WHERE category = 'electronics';  -- Partial: only electronics have voltage
```

```sql
-- Faceted search queries — combining the indexes:

-- Query 1: Category + price range (uses B-tree on category, price):
SELECT id, name, price, brand
FROM products
WHERE category = 'electronics'
  AND price BETWEEN 100 AND 500
  AND in_stock = true
ORDER BY price ASC
LIMIT 20;
-- Plan: Index Scan on (category, price) → fast, sort avoidance possible

-- Query 2: Category + attribute filter (uses B-tree + GIN BitmapAnd):
SELECT id, name, price
FROM products
WHERE category = 'electronics'
  AND attributes @> '{"color": "black", "wireless": true}'
ORDER BY price ASC
LIMIT 20;
-- Plan: BitmapAnd of (category B-tree) + (attributes GIN)

-- Query 3: Full-text + attribute filter:
SELECT id, name, price, ts_rank(search_vec, query) AS rank
FROM products,
     websearch_to_tsquery('english', 'noise cancelling headphones') query
WHERE search_vec @@ query
  AND category = 'electronics'
  AND attributes @> '{"bluetooth": true}'
  AND price < 300
ORDER BY rank DESC
LIMIT 10;
-- Plan: GIN (search_vec) + GIN (attributes) + B-tree (price) via BitmapAnd

-- Query 4: Facet counts — how many products per brand in a category:
SELECT
    attributes->>'brand' AS brand,
    COUNT(*) AS count,
    MIN(price) AS min_price,
    MAX(price) AS max_price
FROM products
WHERE category = 'electronics'
  AND price < 500
  AND in_stock = true
GROUP BY attributes->>'brand'
ORDER BY count DESC
LIMIT 20;
-- If brand is very frequently used: promote to real column (better aggregation)
-- For occasional facet queries: acceptable from JSONB with category+price index
```

## Quick Reference Table

| Operator | Name | Returns | Supports GIN | Example |
|---|---|---|---|---|
| `->` | Extract key | JSONB | No | `data->'name'` → `"Alice"` (JSONB) |
| `->>` | Extract key as text | TEXT | No | `data->>'name'` → `Alice` (TEXT) |
| `#>` | Extract path | JSONB | No | `data #> '{a,b}'` → nested JSONB |
| `#>>` | Extract path as text | TEXT | No | `data #>> '{a,b}'` → nested TEXT |
| `@>` | Contains | BOOLEAN | Yes (both ops) | `data @> '{"role":"admin"}'` |
| `<@` | Contained by | BOOLEAN | Yes (jsonb_ops) | `'{"a":1}' <@ data` |
| `?` | Key exists | BOOLEAN | Yes (jsonb_ops only) | `data ? 'email'` |
| `?|` | Any key exists | BOOLEAN | Yes (jsonb_ops only) | `data ?| ARRAY['a','b']` |
| `?&` | All keys exist | BOOLEAN | Yes (jsonb_ops only) | `data ?& ARRAY['a','b']` |
| `@?` | JSONPath match | BOOLEAN | Yes (both ops) | `data @? '$.price ? (@ > 100)'` |
| `@@` | JSONPath predicate | BOOLEAN | Yes (jsonb_path_ops) | `data @@ '$.active == true'` |
| `\|\|` | Merge / concatenate | JSONB | No | `data \|\| '{"k":"v"}'` |
| `-` | Delete key | JSONB | No | `data - 'key'` |
| `#-` | Delete at path | JSONB | No | `data #- '{a,b}'` |

| Index type | Operator class | Supported operators | Best for | Avoid when |
|---|---|---|---|---|
| GIN | `jsonb_ops` (default) | `@>`, `<@`, `?`, `?|`, `?&`, `@?`, `@@` | Mixed query patterns, key existence checks | Pure `@>` workloads (larger than needed) |
| GIN | `jsonb_path_ops` | `@>`, `@?`, `@@` | Containment-heavy workloads, smaller index | Need `?`, `?|`, `?&` operators |
| B-tree | expression | `=`, `<`, `>`, `BETWEEN`, `LIKE` | Scalar comparisons on extracted fields | Multi-key containment, array operations |
| B-tree | generated column | All B-tree operators | High-frequency scalar field queries | Rarely-queried or variable-structure fields |

---

**Tip for interviews:** Five things separate strong candidates on PostgreSQL JSONB: (1) explaining the **`->` vs `->>` distinction with the type consequence** — that `->` returns JSONB (numbers are numeric, booleans are boolean) while `->>` returns TEXT (numbers become strings), and that comparing `(data->>'price') > 100` is a text comparison where `'9' > '100'` is true because `'9' > '1'` lexicographically — you must cast: `(data->>'price')::numeric > 100`; (2) knowing **which operators GIN can and cannot accelerate** — that `@>`, `?`, `@?` use the GIN index but `->>'field' = 'value'` and `->>'field' > 100` do not, and that the fix for scalar comparisons is an expression B-tree index with the exact same cast expression as the query; (3) understanding the **`jsonb_ops` vs `jsonb_path_ops` tradeoff** — that `jsonb_path_ops` is 3-5x smaller and faster for `@>` and `@?` but cannot serve `?`, `?|`, `?&` queries at all, so the choice depends on which operators your queries actually use; (4) articulating **when JSONB becomes the wrong tool** — that once you frequently range-filter, aggregate, sort, or join on a JSONB field, a generated column with a real B-tree index outperforms expression indexes and avoids type ambiguity, and knowing the zero-downtime migration path (add column, backfill, add sync trigger, migrate queries, remove trigger); and (5) knowing the **SQL NULL vs JSONB null distinction** — that `data->>'key'` returns SQL NULL for both a missing key and a key with JSON null value (making them indistinguishable in text extraction), while `data->'key'` returns SQL NULL only for missing keys and returns the JSONB value `null` for JSON nulls, which is critical for queries that need to distinguish "field not set" from "field explicitly set to null."
