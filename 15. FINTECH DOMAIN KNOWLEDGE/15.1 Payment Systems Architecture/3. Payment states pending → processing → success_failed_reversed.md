# Payment Lifecycle: Payment States — pending → processing → success / failed / reversed — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the payment lifecycle, and what states does a payment transition through?**
A: The payment lifecycle is the ordered sequence of states a payment object moves through from initiation to final settlement. The canonical state machine:

```
INITIATED → PENDING → PROCESSING → SUCCESS
                              ↘ FAILED
                              ↘ REVERSED (post-success)
                              ↘ PARTIALLY_REFUNDED (post-success)
```

Each state represents a distinct phase with defined entry conditions, exit conditions, and allowed transitions:

| State | Meaning | Who sets it |
|---|---|---|
| **INITIATED** | Payment object created; validation not yet run | Your API (on request receipt) |
| **PENDING** | Validated; awaiting network/processor response | Your API (after pre-flight checks) |
| **PROCESSING** | Submitted to payment network; awaiting authorization | Payment gateway callback / webhook |
| **SUCCESS** | Authorized and captured; funds reserved/moved | Gateway webhook |
| **FAILED** | Declined, expired, or error — terminal | Gateway webhook / timeout handler |
| **REVERSED** | Fully refunded post-capture | Refund API / chargeback handler |
| **PARTIALLY_REFUNDED** | A portion of captured amount returned | Refund API |

In Indian fintech context (UPI, Razorpay, PayU), the PROCESSING state is especially important: UPI transactions can sit in PROCESSING for up to 48 hours (pending bank confirmation) while the customer's account is debited — creating reconciliation challenges if your system doesn't model the intermediate state explicitly.

**Q2. Why model payment state explicitly rather than inferring it from timestamps or boolean flags?**
A: Explicit state modeling — a `status` enum column on the `payments` table — is the correct approach for several reasons:

- **State machines encode business rules**: a boolean `is_paid` can't express "is this payment FAILED because of a decline, or PENDING because of network timeout?" — two states that require completely different handling (retry vs. abandon).
- **Prevents illegal transitions**: explicit state + a guard layer (state machine library or application-level check) makes invalid transitions (`SUCCESS → PROCESSING`) impossible to code accidentally.
- **Enables correct idempotency**: if a gateway sends a duplicate `payment.captured` webhook, your handler checks current state; if already `SUCCESS`, it's a no-op — not a double-credit.
- **Drives correct UX**: the frontend displays "Payment processing — please wait" for PROCESSING, "Payment failed — retry" for FAILED. Without explicit state, you'd need heuristic inference.
- **Audit trail**: every state transition is a row in `payment_events` — who triggered it, when, and what the previous state was. Regulators (RBI, PCI-DSS auditors) require this for dispute resolution.

**Q3. What is the difference between authorization and capture in card payments, and how does it affect state modeling?**
A: Authorization and capture are two distinct steps in card payment processing:

- **Authorization** — the issuing bank verifies the cardholder's account has sufficient funds and reserves the amount. The merchant gets an authorization code. Funds are held but not moved. This maps to the `PROCESSING → AUTHORIZED` transition.
- **Capture** — the merchant instructs the network to actually move the reserved funds. This is what triggers settlement. This maps to `AUTHORIZED → SUCCESS`.

Most payment APIs (Stripe, Razorpay) default to **auto-capture** — authorize and capture in one step. But e-commerce flows that ship physical goods often use **manual capture** (authorize at order time, capture at shipment), requiring an intermediate `AUTHORIZED` state.

The full state machine for auth+capture:
```
PENDING → PROCESSING → AUTHORIZED → CAPTURED (SUCCESS)
                    ↘ DECLINED (FAILED)
                    AUTHORIZED → VOIDED (pre-capture cancellation)
                    CAPTURED → REFUNDED / REVERSED (post-capture)
```

Mixing authorization and capture into a single state loses the ability to track holds, void uncaptured authorizations, or enforce capture time windows (Visa requires capture within 7 days of authorization or the hold drops).

**Q4. What is a terminal state, and why does it matter for payment processing?**
A: A terminal state is a state from which no further transitions are possible within the same payment object. For payments:

- **Terminal success states**: `SUCCESS`, `CAPTURED`
- **Terminal failure states**: `FAILED`, `DECLINED`, `EXPIRED`
- **Terminal post-success states**: `FULLY_REFUNDED`, `REVERSED`

Terminal states matter because:
- **Idempotency enforcement**: if a payment is in a terminal state, any incoming webhook or API call attempting to transition it should be silently ignored (idempotent no-op), not processed. Processing a `payment.captured` webhook on an already-`FAILED` payment would be a critical data corruption bug.
- **No retry allowed on terminal failure**: a `FAILED` payment cannot be retried — a new payment object must be created. Retrying the same payment ID risks double-charging if the original actually succeeded but the success webhook was delayed.
- **Ledger finality**: once a payment is in a terminal state, ledger entries are finalized. Partial modifications (update amount, change description) are prohibited. Any money movement requires a new object (refund, chargeback).

**Q5. What is the difference between a refund and a reversal, and when does each occur?**
A: Both return money to the customer but at different points in the payment lifecycle:

| Property | Reversal | Refund |
|---|---|---|
| **When** | Before settlement (same-day, often same batch) | After settlement (funds already moved) |
| **Mechanism** | Cancels the authorization/capture; no funds movement | New credit transaction to customer's account |
| **Settlement impact** | No debit/credit in settlement batch | Separate credit entry in a future settlement |
| **Interchange fees** | Not charged (transaction voided) | Already charged; may or may not be returned depending on network |
| **Time window** | Hours to 1 business day | Days to months |
| **State transition** | `AUTHORIZED → VOIDED` or `CAPTURED → REVERSED` | `SUCCESS → PARTIALLY_REFUNDED` or `FULLY_REFUNDED` |

In Indian payment context: UPI reversals (called "refunds" colloquially) are typically auto-triggered by NPCI within 48 hours for failed transactions — but the amount hasn't actually moved yet, so it's technically a reversal, not a post-settlement refund. Your state machine must distinguish these to reconcile correctly with the bank settlement file.

## Section 2: State Transitions In Depth

**Q6. How do you implement a payment state machine in code? What patterns apply?**
A: Three patterns, in increasing robustness:

**Pattern 1 — Enum + guard in application layer (minimum viable)**
```typescript
// payments.service.ts
const VALID_TRANSITIONS: Record<PaymentStatus, PaymentStatus[]> = {
  PENDING:    ['PROCESSING', 'FAILED'],
  PROCESSING: ['SUCCESS', 'FAILED'],
  SUCCESS:    ['REVERSED', 'PARTIALLY_REFUNDED'],
  FAILED:     [],      // terminal
  REVERSED:   [],      // terminal
};

async function transition(
  paymentId: string,
  targetStatus: PaymentStatus,
  reason: string,
): Promise<Payment> {
  return db.transaction(async (trx) => {
    const payment = await trx('payments')
      .where({ id: paymentId })
      .forUpdate()   // pessimistic lock — prevents concurrent transitions
      .first();

    const allowed = VALID_TRANSITIONS[payment.status] ?? [];
    if (!allowed.includes(targetStatus)) {
      throw new InvalidTransitionError(payment.status, targetStatus);
    }

    await trx('payments').where({ id: paymentId }).update({
      status: targetStatus,
      updated_at: new Date(),
    });

    await trx('payment_events').insert({
      payment_id: paymentId,
      from_status: payment.status,
      to_status: targetStatus,
      reason,
      occurred_at: new Date(),
    });

    return { ...payment, status: targetStatus };
  });
}
```

**Pattern 2 — State machine library (XState, `javascript-state-machine`)**
Define states and transitions declaratively; the library enforces guards and fires side-effect hooks on transitions. Better for complex machines with conditional transitions and parallel states.

**Pattern 3 — DB-level enforcement (most robust)**
Add a check constraint or a trigger that validates transitions at the DB layer — catches bugs that bypass the application layer (direct SQL updates, migration scripts, admin tooling).

```sql
-- PostgreSQL check constraint using a transition table
CREATE TABLE payment_valid_transitions (
  from_status payment_status NOT NULL,
  to_status   payment_status NOT NULL,
  PRIMARY KEY (from_status, to_status)
);

-- Trigger enforces valid transitions on every UPDATE
CREATE OR REPLACE FUNCTION enforce_payment_transition()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status = NEW.status THEN RETURN NEW; END IF;
  IF NOT EXISTS (
    SELECT 1 FROM payment_valid_transitions
    WHERE from_status = OLD.status AND to_status = NEW.status
  ) THEN
    RAISE EXCEPTION 'Invalid payment transition: % → %', OLD.status, NEW.status;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**Q7. What is the role of pessimistic locking in payment state transitions, and when is optimistic locking wrong?**
A: Race conditions in payment state transitions cause double-charges, double-refunds, and split-brain state — critical bugs in fintech. Two locking strategies:

**Pessimistic locking (`SELECT FOR UPDATE`)**
- Acquires a row-level lock before reading; blocks concurrent transactions until released.
- Correct for payment transitions because the cost of a conflict (double-charge) is higher than the cost of lock contention (latency).
- Required when: concurrent webhook deliveries (gateway retries), concurrent API calls (user clicks "Pay" twice), or concurrent background jobs (timeout handler + success webhook racing).

```sql
BEGIN;
SELECT * FROM payments WHERE id = $1 FOR UPDATE;  -- blocks concurrent updaters
-- validate transition
UPDATE payments SET status = 'SUCCESS' WHERE id = $1;
INSERT INTO payment_events ...;
COMMIT;
```

**Optimistic locking (version column)**
- Read with a `version` number; update only if `version` hasn't changed; retry on conflict.
- Appropriate for low-contention entities (user profile updates) where retrying is cheap and safe.
- **Wrong for payments**: if two concurrent webhook deliveries both read `version=1` and both attempt to set `version=2`, the loser retries — and may incorrectly re-apply the transition on the already-updated row.

The rule: use pessimistic locking for any financial state transition. Optimistic locking is fine for non-financial metadata (payment description, metadata tags).

**Q8. How do you handle gateway webhook delivery: out-of-order events, duplicates, and missed events?**
A: Gateway webhooks are unreliable by design — HTTP delivery is not guaranteed ordered or deduplicated. Three failure modes:

**Duplicate delivery**
- Gateways retry webhooks on non-2xx responses (Razorpay retries for 24 hours).
- Fix: idempotency on `event_id`. Before processing, check if `event_id` exists in `webhook_events` table. If yes, return 200 immediately — no-op.
```typescript
const existing = await db('webhook_events').where({ event_id }).first();
if (existing) return res.status(200).json({ status: 'already_processed' });
// ... process event
await db('webhook_events').insert({ event_id, processed_at: new Date() });
```

**Out-of-order delivery**
- A `payment.captured` webhook arriving before `payment.authorized` (gateway races).
- Fix: transition guard rejects illegal transitions. If payment is `PENDING` and you receive `payment.captured`, either buffer the event (store it, re-process later) or apply a reconciliation job that detects payments stuck in PENDING with a captured gateway state.
- Alternative: event sourcing — store all events; compute current state by replaying events sorted by `gateway_event_time`, not by delivery order.

**Missed delivery**
- Webhook never arrives (gateway bug, your endpoint was down during deploy).
- Fix: periodic reconciliation job that polls the gateway's payment status API for any payment that has been in `PROCESSING` for more than N minutes. This is the safety net; don't rely on it as the primary path.

```typescript
// Reconciliation job — runs every 5 minutes
async function reconcileStaleProcessingPayments() {
  const stale = await db('payments')
    .where({ status: 'PROCESSING' })
    .where('updated_at', '<', subMinutes(new Date(), 10));

  for (const payment of stale) {
    const gatewayStatus = await gatewayClient.getPayment(payment.gateway_payment_id);
    if (gatewayStatus === 'captured') {
      await transitionPayment(payment.id, 'SUCCESS', 'reconciliation_job');
    } else if (gatewayStatus === 'failed') {
      await transitionPayment(payment.id, 'FAILED', 'reconciliation_job');
    }
  }
}
```

## Section 3: Failure Modes

**Q9. What are the distinct failure reasons for a payment, and should they all map to the same FAILED state?**
A: `FAILED` as a single state hides operationally critical distinctions. Use a `failure_reason` (or `failure_code`) alongside the terminal `FAILED` status:

| Failure Reason | Cause | Customer-facing action | Retry-safe? |
|---|---|---|---|
| `INSUFFICIENT_FUNDS` | Card declined by issuer | "Use a different card or top up" | No — same card will fail again |
| `CARD_EXPIRED` | Card past expiry date | "Update card details" | No |
| `CVV_MISMATCH` | Wrong CVV entered | "Check card details" | Yes — if customer re-enters |
| `AUTHENTICATION_FAILED` | 3DS / OTP failure | "Re-authenticate" | Yes |
| `GATEWAY_TIMEOUT` | No response from gateway | Internal retry (silent) | Yes — may have succeeded |
| `FRAUD_BLOCKED` | Risk engine blocked | "Contact support" | No |
| `BANK_SERVER_ERROR` | Issuer technical error | "Try again shortly" | Yes — transient |
| `LIMIT_EXCEEDED` | UPI daily limit hit | "Use different payment method" | No |

The `GATEWAY_TIMEOUT` case is uniquely dangerous: the payment may have actually succeeded at the gateway before the timeout, meaning you must NOT show the customer "Payment Failed" without first reconciling via status API. Show "Payment status unknown — please wait" and reconcile asynchronously.

**Q10. What is the "payment unknown / ambiguous state" problem and how do you resolve it?**
A: The ambiguous state arises when your system doesn't know if a payment succeeded because the network failed *after* the gateway processed it but *before* the response arrived. This is the distributed systems "exactly-once" problem applied to payments.

Timeline:
```
Client → [POST /pay] → Your API → Gateway API → TIMEOUT ← Your API
                                    ↑ did the gateway process it?
```

If you immediately mark the payment as `FAILED` and let the customer retry, you risk:
- Customer retries → second payment succeeds → two charges for one order.

Correct resolution:
1. Mark payment as `UNKNOWN` (or leave in `PROCESSING`) — never `FAILED` on timeout.
2. Respond to customer: "Your payment is being processed. We'll confirm shortly."
3. Launch reconciliation: poll gateway status API with the payment's `gateway_payment_id`.
4. On confirmed success → transition to `SUCCESS`, fulfill order.
5. On confirmed failure → transition to `FAILED`, allow retry.
6. On continued ambiguity (gateway also doesn't know) → escalate to manual review queue.

This is why every payment must have an `idempotency_key` sent to the gateway: if you need to retry the gateway call, you submit the same key and the gateway guarantees it won't charge twice.

**Q11. How do you implement payment timeouts and expiry?**
A: Payments that remain in `PENDING` or `PROCESSING` beyond a threshold must be expired — otherwise the customer sees a spinner indefinitely, and your system has dangling records that interfere with retry logic.

**Strategy: TTL + background job**
```typescript
// On payment creation, set expiry timestamp
await db('payments').insert({
  id: paymentId,
  status: 'PENDING',
  expires_at: addMinutes(new Date(), 30),  // UPI: 10-30 min; cards: 15-60 min
});

// Background job — runs every minute
async function expireStalePayments() {
  const expired = await db('payments')
    .whereIn('status', ['PENDING', 'PROCESSING'])
    .where('expires_at', '<', new Date())
    .returning('*');

  for (const payment of expired) {
    // Must reconcile with gateway before expiring — it may have succeeded
    const gatewayStatus = await gatewayClient.getPayment(payment.gateway_payment_id);
    if (gatewayStatus === 'captured') {
      await transitionPayment(payment.id, 'SUCCESS', 'expiry_reconciliation');
    } else {
      await transitionPayment(payment.id, 'FAILED', 'expired');
    }
  }
}
```

**UPI-specific**: NPCI mandates a maximum payment validity of 24 hours for collect requests. After 24 hours, the UPI transaction reference is invalid and NPCI auto-reverses any pending debits. Your system must model this by transitioning the payment to `FAILED` (with reason `UPI_EXPIRED`) and triggering your reconciliation against the bank settlement file.

## Section 4: Indian Fintech & Regulatory Context

**Q12. How does the UPI payment lifecycle differ from card payment lifecycle?**
A: UPI (Unified Payments Interface) has a fundamentally different state machine than card payments because UPI operates on real-time gross settlement (RTGS-adjacent) — money moves directly between bank accounts, not through a card network's authorization/capture cycle.

**UPI state machine:**
```
INITIATED → PENDING (collect request sent to payer's VPA)
         → PROCESSING (payer approved; NPCI routing)
         → SUCCESS (both debit and credit confirmed by banks)
         → FAILED (bank declined / timeout / insufficient funds)
         → REVERSED (NPCI auto-reversal for failed credit-leg)
```

Key differences from card:
- **No authorization/capture split** — UPI is irrevocable once SUCCESS. There is no "void" step.
- **Reversal is NPCI-initiated** — if the debit leg succeeds but the credit leg fails (bank down), NPCI automatically triggers a reversal within 48 hours. Your system must handle this as a gateway-initiated `REVERSED` transition, not a customer-initiated refund.
- **PROCESSING is longer** — card authorization is milliseconds; UPI processing can be minutes to hours during bank outages or high-traffic periods (Diwali, month-end).
- **VPA resolution delay** — `INITIATED → PENDING` involves VPA (Virtual Payment Address) resolution and collect-request delivery to the payer's UPI app. This step can fail (`VPA_NOT_FOUND`, `PAYER_APP_UNAVAILABLE`) before any money movement.
- **Debit/credit legs** — UPI has two distinct legs: debit from payer's bank and credit to payee's bank. Success requires both. Your `SUCCESS` state should only be set on receiving confirmation of both legs (via NPCI callback).

**Q13. What is payment reconciliation, and why is it non-negotiable in fintech?**
A: Reconciliation is the process of comparing your internal payment records against the gateway's settlement file and the bank's debit/credit statements to detect and resolve discrepancies.

Why it's non-negotiable:
- Gateways settle in batches (typically T+1 or T+2); the settlement file is the source of truth for what actually moved.
- Webhooks can be lost, delayed, or duplicated — your DB state may diverge from the gateway's state.
- RBI regulations require payment aggregators (Razorpay, PayU, Cashfree) to reconcile daily and maintain audit trails.

**Three-way reconciliation:**
```
Your DB payments table
      ↕ compare
Gateway settlement file (CSV/API)
      ↕ compare
Bank statement (NEFT/IMPS/UPI settlement credits)
```

**Discrepancy types and resolution:**
| Discrepancy | Cause | Resolution |
|---|---|---|
| Gateway SUCCESS, DB PROCESSING | Webhook missed | Mark SUCCESS; trigger fulfillment |
| DB SUCCESS, Gateway FAILED | Gateway bug or data corruption | Flag for manual review; hold fulfillment |
| Gateway settled, Bank not credited | Settlement delay or bank error | Escalate to gateway support |
| DB SUCCESS, not in Gateway file | Payment ID mismatch or test mode | Investigate; may indicate fraud |

```typescript
async function dailyReconciliation(settlementDate: Date) {
  const gatewaySettlement = await gatewayClient.getSettlementFile(settlementDate);
  const gatewayIds = new Set(gatewaySettlement.map(r => r.gateway_payment_id));

  // Find DB SUCCESS payments not in gateway settlement
  const dbSuccessPayments = await db('payments')
    .where({ status: 'SUCCESS' })
    .whereBetween('updated_at', [startOfDay(settlementDate), endOfDay(settlementDate)]);

  for (const payment of dbSuccessPayments) {
    if (!gatewayIds.has(payment.gateway_payment_id)) {
      await flagForManualReview(payment.id, 'NOT_IN_SETTLEMENT_FILE');
    }
  }
}
```

**Q14. What are RBI regulations relevant to payment state management that a backend engineer should know?**
A: Key RBI mandates that affect your payment state machine and data model:

- **PA/PG guidelines (2020)** — Payment Aggregators must not hold funds beyond T+1 (next business day settlement). Your system must track settlement status separately from payment status and alert if funds are held beyond the window.
- **Nodal account requirement** — all customer payments must flow through an escrow/nodal account; the PA's own funds and customer funds must be segregated. This requires your ledger to model collections vs. merchant payouts separately from payment states.
- **Refund timelines** — RBI mandates refunds within 5–7 business days for card payments. Your `REVERSED` / `REFUNDED` state must carry a `refund_initiated_at` timestamp; SLA monitoring alerts if the gateway hasn't confirmed refund within the window.
- **Failed transaction data** — RBI circular on failed transactions (2019) requires that every failed payment's `failure_reason` be logged and reportable. Your `payment_events` table with `failure_code` satisfies this.
- **2FA requirement** — Additional Factor of Authentication (AFA) is mandatory for card-not-present transactions above ₹5,000. Your `PENDING → PROCESSING` transition must include AFA (OTP/3DS) completion as a gate — payment cannot proceed to `PROCESSING` without it.

## Section 5: Distributed Systems & Architecture

**Q15. How do you design the payment events table for an audit trail that satisfies both engineering and compliance needs?**
A: The `payment_events` table is the append-only ledger of every state transition. Schema:

```sql
CREATE TABLE payment_events (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id      UUID NOT NULL REFERENCES payments(id),
  from_status     payment_status NOT NULL,
  to_status       payment_status NOT NULL,
  triggered_by    TEXT NOT NULL,           -- 'webhook', 'api', 'reconciliation_job', 'user'
  actor_id        UUID,                    -- user_id or service_account_id
  gateway_event_id TEXT,                   -- gateway's event ID for cross-reference
  metadata        JSONB,                   -- failure_code, reversal_reason, amount_refunded, etc.
  occurred_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  gateway_time    TIMESTAMPTZ,             -- timestamp from gateway event (may differ from occurred_at)
  ip_address      INET,                    -- for customer-initiated transitions
  idempotency_key TEXT                     -- prevents duplicate event inserts
);

CREATE INDEX idx_payment_events_payment_id ON payment_events(payment_id);
CREATE INDEX idx_payment_events_occurred_at ON payment_events(occurred_at DESC);
CREATE UNIQUE INDEX idx_payment_events_idempotency ON payment_events(idempotency_key)
  WHERE idempotency_key IS NOT NULL;
```

Critical design decisions:
- **Append-only** — rows are never updated or deleted. `UPDATE payment_events` must not exist in your codebase. Past transitions are immutable; this is your audit trail.
- **`gateway_time` vs `occurred_at`** — gateway_time is when the event actually happened at the gateway (used for reconciliation); occurred_at is when your system recorded it (may be delayed by webhook processing lag). Both are needed.
- **JSONB metadata** — allows flexible storage of transition-specific data without schema changes. Keep the schema stable; add metadata fields over time.
- **No DELETE permission on events table** — service accounts that process payments should have `INSERT` and `SELECT` only on `payment_events`. Even admins should require a special role with audit logging to delete.

**Q16. How does event sourcing apply to payments, and when is it overkill?**
A: Event sourcing stores payment state as a sequence of immutable events rather than a mutable row. Instead of `UPDATE payments SET status = 'SUCCESS'`, you append `PaymentCaptured { payment_id, amount, gateway_ref, captured_at }`. Current state is derived by replaying events.

**When event sourcing fits payments:**
- You need full auditability with no possibility of state tampering (regulator requirement).
- Complex state machines with multiple parallel sub-states (authorization + 3DS + capture + settlement each having their own lifecycle).
- You need temporal queries: "what was this payment's state at 14:32:07 yesterday?"
- You're building event-driven downstream systems (fulfillment, notifications, ledger) that consume payment events natively.

**When it's overkill:**
- A simple e-commerce checkout with basic PENDING → SUCCESS / FAILED flow.
- Team is not familiar with event sourcing tradeoffs (projection lag, eventual consistency of read models).
- Your volume is low enough that a well-indexed `payment_events` table + `payments.status` column gives you everything you need.

**Practical middle ground** (recommended for most fintech startups): keep a mutable `payments.status` column for fast reads, and an append-only `payment_events` table for audit. This gives you 90% of event sourcing's benefits with none of the complexity.

**Q17. How do you design an idempotent payment creation endpoint?**
A: Without idempotency, a network timeout causes a client to retry, potentially creating duplicate payments. The pattern:

```typescript
// POST /payments
// Client sends X-Idempotency-Key: <uuid> header

async function createPayment(req: Request): Promise<Response> {
  const idempotencyKey = req.headers['x-idempotency-key'];
  if (!idempotencyKey) throw new BadRequestError('X-Idempotency-Key required');

  // Check for existing response stored against this key
  const cached = await redis.get(`idempotency:${idempotencyKey}`);
  if (cached) {
    return Response.json(JSON.parse(cached), { status: 200 });
  }

  // Acquire distributed lock — prevents two concurrent requests with same key
  const lock = await redlock.acquire(`lock:idempotency:${idempotencyKey}`, 10_000);
  try {
    // Re-check after acquiring lock (another request may have just completed)
    const cachedAfterLock = await redis.get(`idempotency:${idempotencyKey}`);
    if (cachedAfterLock) {
      return Response.json(JSON.parse(cachedAfterLock), { status: 200 });
    }

    // Create payment
    const payment = await paymentService.create(req.body);

    // Cache response for 24 hours
    await redis.setex(
      `idempotency:${idempotencyKey}`,
      86400,
      JSON.stringify(payment)
    );

    return Response.json(payment, { status: 201 });
  } finally {
    await lock.release();
  }
}
```

Key decisions:
- **Idempotency key is client-generated** (UUID) — the client is responsible for generating and storing the key before the request. If the request times out, client retries with the *same* key.
- **24-hour TTL** — matches typical payment session windows. After 24 hours, the same key can create a new payment (the old one would be expired/terminal).
- **Cache the response, not just the payment ID** — returning the full payment object on repeat calls means clients don't need special handling for "duplicate" vs "new" responses.
- **Distributed lock** — prevents two concurrent requests with the same idempotency key from both creating payments. Redis-based Redlock is the standard pattern.

## Section 6: Scenario / System Design Questions

**Q18. "Design the data model for a payment system that supports UPI, card, and net banking with a unified state machine."**
A: The key design challenge is that each payment method has a slightly different state machine, but your product layer needs a unified view. Use inheritance / polymorphism at the data layer:

```sql
-- Base payment table — unified state machine
CREATE TABLE payments (
  id                  UUID PRIMARY KEY,
  order_id            UUID NOT NULL REFERENCES orders(id),
  amount              BIGINT NOT NULL,         -- in paise (smallest unit)
  currency            CHAR(3) NOT NULL DEFAULT 'INR',
  status              payment_status NOT NULL DEFAULT 'PENDING',
  payment_method      payment_method_type NOT NULL,  -- 'UPI', 'CARD', 'NETBANKING'
  idempotency_key     TEXT UNIQUE NOT NULL,
  gateway             TEXT NOT NULL,           -- 'razorpay', 'cashfree', 'payu'
  gateway_payment_id  TEXT,                    -- gateway's reference
  failure_code        TEXT,
  failure_message     TEXT,
  expires_at          TIMESTAMPTZ NOT NULL,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- UPI-specific fields
CREATE TABLE payment_upi_details (
  payment_id      UUID PRIMARY KEY REFERENCES payments(id),
  vpa             TEXT NOT NULL,              -- payer's VPA (e.g., user@okicici)
  upi_txn_id      TEXT,                       -- NPCI transaction ID
  bank_ref_no     TEXT,                       -- issuing bank reference
  debit_confirmed_at  TIMESTAMPTZ,
  credit_confirmed_at TIMESTAMPTZ             -- set separately from debit
);

-- Card-specific fields
CREATE TABLE payment_card_details (
  payment_id          UUID PRIMARY KEY REFERENCES payments(id),
  card_last_four      CHAR(4) NOT NULL,
  card_network        TEXT NOT NULL,          -- 'VISA', 'MASTERCARD', 'RUPAY'
  authorization_code  TEXT,
  rrn                 TEXT,                   -- Retrieval Reference Number
  auth_at             TIMESTAMPTZ,
  captured_at         TIMESTAMPTZ
);
```

**Q19. "A payment is stuck in PROCESSING for 2 hours. Walk me through your debugging and resolution process."**
A: Systematic investigation:

**Step 1 — Establish facts (2 minutes)**
```sql
SELECT p.*, pe.* FROM payments p
JOIN payment_events pe ON pe.payment_id = p.id
WHERE p.id = '<payment_id>'
ORDER BY pe.occurred_at;
```
What's the last recorded event? When did it enter PROCESSING? Was there a webhook receipt?

**Step 2 — Check gateway (5 minutes)**
- Look up the `gateway_payment_id` in the gateway dashboard / API.
- What does the gateway show as the current status?
- Are there any webhook delivery failures logged (gateway dashboard → webhooks → failed deliveries)?

**Step 3 — Branch by gateway status**

*Gateway shows SUCCESS*: webhook was lost. Manually trigger `transitionPayment(id, 'SUCCESS', 'manual_recovery')`. Check webhook endpoint health (was the service restarted during that window?). Fix the missed webhook; trigger fulfillment.

*Gateway shows FAILED*: same — webhook lost. Transition to `FAILED`; notify customer to retry.

*Gateway shows PROCESSING*: genuinely stuck at gateway. This indicates a bank-side issue (NPCI timeout, issuer bank outage). Check NPCI status page. Wait for gateway SLA (Razorpay SLA: 30 min for UPI, then auto-reversal). If past SLA, raise a support ticket with the gateway.

*Gateway shows no record of payment*: `gateway_payment_id` was never created — the gateway call failed silently before your DB committed the PROCESSING state, or the gateway had a partial write. This payment needs to be expired and a new one created.

**Step 4 — Prevent recurrence**
- Was this a one-off or systematic? Query: how many payments have been in PROCESSING > 30 minutes in the last 7 days?
- If systematic: your reconciliation job isn't running, or the webhook endpoint was unhealthy. Fix the root cause.
- Add alerting: PagerDuty alert if any payment stays in PROCESSING for more than 15 minutes without a webhook receipt.

**Q20. "How would you implement partial refunds, and what state transitions does it require?"**
A: Partial refunds are common in e-commerce (return one item from a multi-item order). State machine extension:

```
SUCCESS → PARTIALLY_REFUNDED (first partial refund)
PARTIALLY_REFUNDED → PARTIALLY_REFUNDED (subsequent partial refunds, up to original amount)
PARTIALLY_REFUNDED → FULLY_REFUNDED (when sum of refunds = original amount)
SUCCESS → FULLY_REFUNDED (single full refund)
```

Data model for refunds as first-class objects:
```sql
CREATE TABLE refunds (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id      UUID NOT NULL REFERENCES payments(id),
  amount          BIGINT NOT NULL,             -- in paise
  status          refund_status NOT NULL DEFAULT 'PENDING',
  reason          TEXT,
  gateway_refund_id TEXT,
  initiated_by    UUID,                        -- user or service account
  initiated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  completed_at    TIMESTAMPTZ
);

CREATE TYPE refund_status AS ENUM ('PENDING', 'PROCESSING', 'SUCCESS', 'FAILED');
```

Transition logic with invariant enforcement:
```typescript
async function initiateRefund(paymentId: string, amount: bigint, reason: string) {
  return db.transaction(async (trx) => {
    const payment = await trx('payments').where({ id: paymentId }).forUpdate().first();

    if (!['SUCCESS', 'PARTIALLY_REFUNDED'].includes(payment.status)) {
      throw new Error(`Cannot refund payment in ${payment.status} state`);
    }

    const existingRefunds = await trx('refunds')
      .where({ payment_id: paymentId })
      .whereIn('status', ['PENDING', 'PROCESSING', 'SUCCESS'])
      .sum('amount as total');

    const totalRefunded = BigInt(existingRefunds[0].total ?? 0);
    const remaining = payment.amount - totalRefunded;

    if (amount > remaining) {
      throw new Error(`Refund amount ${amount} exceeds remaining refundable amount ${remaining}`);
    }

    const refund = await trx('refunds').insert({
      payment_id: paymentId,
      amount,
      reason,
      status: 'PENDING',
    }).returning('*');

    // Update payment status
    const newPaymentStatus = (totalRefunded + amount === payment.amount)
      ? 'FULLY_REFUNDED'
      : 'PARTIALLY_REFUNDED';

    await trx('payments').where({ id: paymentId }).update({ status: newPaymentStatus });

    return refund[0];
  });
}
```
