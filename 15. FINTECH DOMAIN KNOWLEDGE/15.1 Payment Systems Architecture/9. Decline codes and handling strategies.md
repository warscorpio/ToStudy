# Decline Codes and Handling Strategies — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a decline code, and at what point in the payment lifecycle does it appear?**
A: A decline code is a standardized response code returned by the issuing bank (via the card network and acquirer) during the **authorization phase** of the payment lifecycle. It signals that the issuer has refused to approve the transaction and provides a machine-readable reason. Decline codes do not appear during capture or settlement — by those phases, the authorization has already been approved.

The response travels back through the same chain that carried the auth request:

```
Merchant → PG → Acquirer → Card Network → Issuer
                                              │
                              Decline decision + response code
                                              │
Merchant ← PG ← Acquirer ← Card Network ← Issuer
```

The raw decline code (e.g., `05`, `51`, `54`) is defined by the **ISO 8583** standard, which governs the message format for financial transaction card-originated messages. Card networks (Visa, Mastercard, RuPay) extend this with network-specific codes. Payment gateways (Razorpay, Stripe, Cashfree) translate these into their own normalized error codes and human-readable messages before returning them to the merchant.

A 5 YOE engineer must know: the raw ISO code, the PG's abstraction over it, what it means for the cardholder's actual account state, and critically — whether the transaction is safe to retry or must not be retried.

**Q2. What is the fundamental distinction between a hard decline and a soft decline?**
A: This is the most operationally important classification in decline handling:

- **Hard decline** — the issuer has made a firm, permanent decision to reject this transaction for this card. Retrying will produce the same decline and — beyond one or two attempts — will trigger card network penalty programs for excessive retries. The merchant must not retry; they must prompt the cardholder to use a different payment method or contact their bank.

- **Soft decline** — the decline is transient. The issuer is not refusing the card permanently; a condition prevented this specific attempt from succeeding (insufficient funds at this moment, issuer system temporarily unavailable, velocity limit exceeded for the day). A retry after an appropriate delay — or after the underlying condition changes (e.g., customer tops up their account) — may succeed.

| Property | Hard Decline | Soft Decline |
|---|---|---|
| Retry permitted? | No (1 retry maximum in 30 days) | Yes — with delay and limit |
| Underlying cause | Permanent card state (blocked, stolen, expired) | Transient condition (funds, issuer availability) |
| Customer action required? | Yes — use different card or call bank | Sometimes — top up account, wait |
| Risk of retrying | Network penalty, account flagging | None if within retry rules |
| Examples | `05`, `14`, `41`, `43`, `54`, `57`, `62` | `51`, `61`, `65`, `91`, `96` |

**Q3. What is ISO 8583, and how do card networks and payment gateways build on top of it?**
A: ISO 8583 is the international standard that defines the message format, data elements, and response codes for card payment transactions. It was designed in the 1980s for interchange between financial institutions and remains the backbone of card network communication today.

The standard defines:
- **Message type indicators (MTI)** — four-digit codes identifying the message class (0100 = authorization request, 0110 = authorization response, 0200 = financial transaction request, etc.)
- **Data elements (DE)** — up to 128 fields covering amount (DE4), card number (DE2), expiry (DE14), merchant category code (DE18), response code (DE39), and authorization code (DE38).
- **Response code (DE39)** — a two-character field carrying the issuer's decision. `00` = approved; anything else is a decline or exception.

Card networks extend ISO 8583 with proprietary data elements and additional response codes beyond the base standard. Visa's VisaNet, Mastercard's Banknet, and NPCI's RuPayNet each have their own extended code sets.

Payment gateways receive the raw ISO 8583 response from the acquirer and translate it into developer-friendly representations:

```typescript
// Raw ISO 8583 DE39 from acquirer: "51"
// Razorpay normalized response:
{
  "error": {
    "code": "BAD_REQUEST_ERROR",
    "description": "Your payment has been declined as the account has insufficient funds.",
    "reason": "payment_failed",
    "source": "customer",
    "step": "payment_authentication",
    "metadata": {
      "issuer_error_code": "51",
      "network_error_code": "INSUFFICIENT_FUNDS"
    }
  }
}

// Stripe normalized response:
{
  "error": {
    "type": "card_error",
    "code": "insufficient_funds",
    "decline_code": "insufficient_funds",
    "message": "Your card has insufficient funds."
  }
}
```

Engineers working at the PG integration layer deal with the PG's abstraction. Engineers working at the acquirer integration layer (e.g., building a payment gateway themselves) deal with raw ISO codes.

**Q4. What are the most critical ISO 8583 decline codes that every payments engineer must know?**
A: Grouped by operational category:

**Do-not-retry (hard declines):**

| Code | Name | Meaning | Cardholder Implication |
|---|---|---|---|
| `05` | Do Not Honor | Issuer generic refusal; card may be flagged | Contact bank; try different card |
| `14` | Invalid Card Number | PAN fails Luhn check or is not on file at issuer | Card number entered incorrectly; use different card |
| `41` | Lost Card | Card reported lost; issuer will not approve | Card is blocked; use different card |
| `43` | Stolen Card | Card reported stolen; may trigger capture request | Card is blocked; use different card |
| `54` | Expired Card | Card past its expiry date | Card expired; use different or updated card |
| `57` | Transaction Not Permitted to Cardholder | Card not enabled for this transaction type (e.g., international, online) | Card restriction; contact bank to enable |
| `62` | Restricted Card | Card has a spend restriction (geography, MCC) | Contact bank; use different card |
| `78` | No Account / No Such Account | Account linked to card does not exist | Rare; contact bank |

**Retry-permitted (soft declines):**

| Code | Name | Meaning | Action |
|---|---|---|---|
| `51` | Insufficient Funds | Not enough balance/credit at this moment | Retry after customer tops up; prompt alternative |
| `61` | Exceeds Withdrawal Amount Limit | Single transaction exceeds card's per-transaction limit | Retry with lower amount or different card |
| `65` | Exceeds Withdrawal Frequency Limit | Too many transactions in a period | Retry after period resets |
| `91` | Issuer or Switch Inoperative | Issuer's system temporarily unavailable | Retry after delay (exponential backoff) |
| `96` | System Malfunction | Generic system error on network/issuer side | Retry after delay |
| `N7` | CVV2 Failure (Visa-specific) | CVV entered incorrectly | Prompt cardholder to re-enter CVV |

**Special codes:**

| Code | Name | Meaning | Action |
|---|---|---|---|
| `00` | Approved | Transaction approved | Proceed to capture |
| `01` | Refer to Card Issuer | Issuer wants voice authorization | Prompt cardholder to call bank |
| `04` | Pick Up Card | Issuer requests card seizure (POS only) | Applicable only at POS; do not retry |
| `13` | Invalid Amount | Zero or malformed amount | Fix amount in request; programming error |
| `30` | Format Error | Message format error in auth request | Engineering bug; fix request format |
| `55` | Invalid PIN | Incorrect PIN entered (debit card) | Prompt re-entry; lock after 3 failures |

**Q5. How do RuPay and UPI decline codes differ from Visa/Mastercard ISO codes in an Indian fintech context?**
A: RuPay follows ISO 8583 for card transactions but adds NPCI-specific codes for domestic routing, NACH mandates, and Aadhaar-linked accounts. UPI uses a completely different error code system — NPCI's UPI error codes — since UPI is not a card network.

**RuPay-specific considerations:**
- RuPay debit cards on government-linked accounts (PMJDY accounts) have lower transaction limits enforced by the issuer — code `61` (exceeds limit) is more frequent and does not indicate the same risk profile as on a premium credit card.
- RuPay credit cards may return `57` for international transactions since RuPay's international acceptance is still expanding; do not treat this identically to a Visa `57` (card fully restricted).
- RuPay NCMC (National Common Mobility Card) transactions return specific offline-capable codes not relevant to online payments.

**UPI-specific error codes (selected):**

| UPI Error Code | Meaning | Handling |
|---|---|---|
| `U16` | Risk threshold exceeded | Soft — retry after 24h; often velocity-based |
| `U30` | Debit failed — insufficient funds | Soft — customer must add funds |
| `U69` | Transaction not permitted | Hard — UPI ID or account restricted |
| `U28` | Remitter bank not available | Soft — retry with backoff |
| `B2` | VPA not found | Hard — VPA (UPI ID) does not exist |
| `XB` | Transaction declined by bank | Generic hard decline |
| `YG` | Account blocked | Hard — account blocked by bank |
| `ZM` | Invalid MPIN | Soft after first; hard after 3 failures |
| `ZA` | Transaction timed out | Soft — retry |

In a NestJS backend handling both card and UPI payments, the decline classification logic must be rail-aware:

```typescript
// payments/decline/decline-classifier.ts
export type PaymentRail = 'card' | 'upi' | 'netbanking';

export function classifyDecline(
  responseCode: string,
  rail: PaymentRail,
): 'hard' | 'soft' | 'unknown' {
  if (rail === 'upi') return classifyUpiDecline(responseCode);
  if (rail === 'card') return classifyCardDecline(responseCode);
  return 'unknown';
}

const CARD_HARD_DECLINES = new Set([
  '05', '14', '41', '43', '54', '57', '62', '78', '04',
]);
const CARD_SOFT_DECLINES = new Set(['51', '61', '65', '91', '96', 'N7']);

function classifyCardDecline(code: string): 'hard' | 'soft' | 'unknown' {
  if (CARD_HARD_DECLINES.has(code)) return 'hard';
  if (CARD_SOFT_DECLINES.has(code)) return 'soft';
  return 'unknown'; // treat unknown as hard — safer than risking network penalty
}

const UPI_HARD_DECLINES = new Set(['U69', 'B2', 'XB', 'YG']);
const UPI_SOFT_DECLINES = new Set(['U16', 'U30', 'U28', 'ZA', 'ZM']);

function classifyUpiDecline(code: string): 'hard' | 'soft' | 'unknown' {
  if (UPI_HARD_DECLINES.has(code)) return 'hard';
  if (UPI_SOFT_DECLINES.has(code)) return 'soft';
  return 'unknown';
}
```

## Section 2: Hard Decline Handling In Depth

**Q6. What is the card network retry penalty program, and what triggers it?**
A: Visa and Mastercard operate formal programs that fine acquirers (and by extension, merchants) for excessive retries on hard-declined transactions. These are not guidelines — they are enforced financially.

**Visa's Transaction Retry Program:**
- Tracks retries at the BIN (card) level per merchant.
- For a hard-declined authorization (`05`, `14`, `41`, `43`, `54`, `57`, `62`): **one retry** is permitted within 30 days. Any further retry counts as an "excessive retry" violation.
- For soft declines (`51`, `91`, `96`): up to **15 retries** within 30 days, with at least 1 day between each attempt.
- Violation: $0.10 per excessive retry attempt (as of the most recent program update). Merchants with high retry volume can accumulate thousands of dollars in penalties per month.

**Mastercard's Transaction Processing Excellence (TPE):**
- Similar structure: hard decline → maximum 1 retry in 30 days; soft decline → up to 10 retries with minimum 24h between attempts.
- Additional monitoring: if a BIN is declined more than 35% of the time, the merchant is placed in a monitoring program with additional fees.

Engineering consequence — retry tracking must be persisted and enforced in the payment service:

```typescript
// payments/retry/retry-tracker.service.ts
@Injectable()
export class RetryTrackerService {
  constructor(private readonly redis: Redis) {}

  private retryKey(cardFingerprint: string, merchantId: string): string {
    // Use card fingerprint (hashed PAN or network token), not raw PAN
    return `retry:${merchantId}:${cardFingerprint}`;
  }

  async canRetry(
    cardFingerprint: string,
    merchantId: string,
    declineType: 'hard' | 'soft',
  ): Promise<{ allowed: boolean; reason?: string }> {
    const key = this.retryKey(cardFingerprint, merchantId);
    const data = await this.redis.hgetall(key);

    const retryCount = parseInt(data?.retryCount ?? '0', 10);
    const lastRetryAt = data?.lastRetryAt ? new Date(data.lastRetryAt) : null;
    const maxRetries = declineType === 'hard' ? 1 : 15;
    const minIntervalHours = declineType === 'hard' ? 24 * 30 : 24; // 30 days for hard, 1 day for soft

    if (retryCount >= maxRetries) {
      return { allowed: false, reason: `Max retries (${maxRetries}) reached for this card` };
    }

    if (lastRetryAt) {
      const hoursSinceLast = (Date.now() - lastRetryAt.getTime()) / (1000 * 60 * 60);
      if (hoursSinceLast < minIntervalHours) {
        return {
          allowed: false,
          reason: `Minimum retry interval not elapsed. Next allowed in ${Math.ceil(minIntervalHours - hoursSinceLast)}h`,
        };
      }
    }

    return { allowed: true };
  }

  async recordRetry(cardFingerprint: string, merchantId: string): Promise<void> {
    const key = this.retryKey(cardFingerprint, merchantId);
    await this.redis
      .multi()
      .hincrby(key, 'retryCount', 1)
      .hset(key, 'lastRetryAt', new Date().toISOString())
      .expire(key, 60 * 60 * 24 * 31) // 31-day TTL — aligns with network's 30-day window
      .exec();
  }
}
```

**Q7. How should a payment system handle the `05` (Do Not Honor) decline code specifically?**
A: `05` is the most common hard decline and the most ambiguous — it is the issuer's catch-all refusal when no more specific code applies. It covers: the issuer's fraud model flagged the transaction, the card is in a restricted state the issuer won't disclose, the account has been closed, or a catch-all system decision.

Handling:
- **Never retry** — `05` is a hard decline. The issuer has made a deliberate decision. Retrying on the same card within 30 days is a network violation (one retry maximum).
- **Do not disclose internal code to cardholder** — telling the cardholder "Do Not Honor" reveals nothing useful and may alarm them. Show a generic "your payment was declined" message. PGs like Razorpay normalize `05` to "payment_declined" for exactly this reason.
- **Offer alternatives** — prompt the cardholder to use a different card, try UPI, or use net banking.
- **Log for fraud analysis** — a merchant seeing repeated `05` declines across different cards for the same customer (device fingerprint or IP) is a fraud signal. Log `responseCode`, `cardBin`, `ipAddress`, `deviceId` together.

```typescript
// payments/decline/decline-handler.ts
async function handleDecline(
  payment: Payment,
  responseCode: string,
  rail: PaymentRail,
): Promise<DeclineOutcome> {
  const declineType = classifyDecline(responseCode, rail);
  const message = buildUserFacingMessage(responseCode, rail); // never expose raw code

  await paymentsRepo.updateStatus(payment.id, 'failed', {
    responseCode,
    declineType,
    failedAt: new Date(),
  });

  await auditLogRepo.record({
    paymentId: payment.id,
    event: 'payment_declined',
    metadata: { responseCode, declineType, cardBin: payment.cardBin, rail },
  });

  if (declineType === 'hard') {
    await retryTrackerService.recordRetry(payment.cardFingerprint, payment.merchantId);
    await notificationService.notifyDecline(payment, message, { suggestAlternative: true });
    return { action: 'prompt_alternative', message };
  }

  // Soft decline — schedule retry if this is a subscription/standing instruction
  if (payment.type === 'recurring') {
    const canRetry = await retryTrackerService.canRetry(
      payment.cardFingerprint,
      payment.merchantId,
      'soft',
    );
    if (canRetry.allowed) {
      await retryQueue.enqueue({ paymentId: payment.id }, { delay: hours(24) });
    }
  }

  return { action: 'retry_scheduled_or_prompt', message };
}
```

**Q8. How do you handle `41` (Lost Card) and `43` (Stolen Card) — codes that carry legal and security implications?**
A: These codes require special handling beyond standard decline processing:

- **`41` (Lost Card)** and **`43` (Stolen Card)** indicate that the cardholder has reported the card to their bank. The issuer knows the card is compromised.
- At a **POS terminal**, networks permit (and sometimes mandate) the terminal to attempt physical card capture ("pick up the card") — the merchant is instructed to confiscate the physical card and return it to the bank. This is not applicable to card-not-present (online) transactions.
- For **online (CNP) transactions**: the merchant has no card to capture. Simply decline the transaction, do not retry (hard decline), and do not provide any success-like response that might indicate the transaction was processed.
- **Fraud reporting** — a `41` or `43` on a CNP transaction is a strong fraud signal: either a fraudster is attempting to use a reported card (common — thieves try cards immediately after theft, before the victim reports), or the cardholder has mistakenly reported it lost/stolen while still in possession. Log and route to your fraud team.
- **Do not log raw PANs** — when recording `41`/`43` events, use the tokenized card reference or card fingerprint, never the raw PAN. Storing PANs in application logs is a PCI DSS violation.

```typescript
const SECURITY_ALERT_CODES = new Set(['41', '43']);

if (SECURITY_ALERT_CODES.has(responseCode)) {
  // Route to fraud system — do not expose code to merchant dashboard in raw form
  await fraudService.recordSecurityDecline({
    paymentId: payment.id,
    code: responseCode,
    cardFingerprint: payment.cardFingerprint, // NOT raw PAN
    ipAddress: payment.ipAddress,
    deviceId: payment.deviceId,
    timestamp: new Date(),
  });
  // Standard hard decline flow continues — no special merchant-facing behavior
}
```

**Q9. How should the system handle `54` (Expired Card) in a subscription or recurring payment context?**
A: Expired card is one of the most operationally impactful hard declines for subscription businesses. Cards expire every 1–4 years, and recurring payments fail silently unless the system actively manages card lifecycle:

**Proactive handling — before the decline:**
- **Account Updater** — Visa's Account Updater (VAU) and Mastercard's Automatic Billing Updater (ABU) are services where issuers push updated card details (new expiry, replacement card number) to acquirers before the old card expires. Payment gateways like Razorpay and Stripe integrate these and can auto-update stored card tokens without cardholder action. Enable this for all subscription merchants.
- **Pre-expiry notification** — query stored card metadata for cards expiring in the next 60 days; notify the cardholder to update their payment method before the decline occurs.

```typescript
// Cron: runs monthly — identifies cards expiring in next 60 days
@Cron('0 9 1 * *') // 9am on the 1st of each month
async notifyExpiringCards(): Promise<void> {
  const threshold = addDays(new Date(), 60);
  const subscriptions = await subscriptionsRepo.findWithExpiringCards(threshold);

  for (const sub of subscriptions) {
    await notificationService.sendCardExpiryWarning({
      customerId: sub.customerId,
      lastFourDigits: sub.card.lastFour,
      expiryMonth: sub.card.expiryMonth,
      expiryYear: sub.card.expiryYear,
      updateCardUrl: `${baseUrl}/account/payment-methods`,
    });
  }
}
```

**Reactive handling — after the `54` decline:**
- Mark the subscription as `payment_failed` with sub-reason `card_expired`.
- Enter a dunning flow (see Q17) — do not retry the same expired card; it will always decline.
- Notify the cardholder to update their card; provide a secure card update link (hosted payment page or tokenized update form — never collect raw card data on your own domain unless PCI DSS Level 1 compliant).
- Apply a grace period (typically 7–14 days) before suspending the subscription.

## Section 3: Soft Decline Handling In Depth

**Q10. How do you implement a retry strategy for soft declines that is safe, compliant, and effective?**
A: A production retry strategy must balance three constraints: maximizing recovery rate (business goal), staying within network retry rules (compliance goal), and not creating a poor cardholder experience (UX goal).

```typescript
// payments/retry/retry-strategy.ts
export interface RetryConfig {
  maxAttempts: number;
  intervalHours: number;
  applicableStatuses: Set<string>;
}

export const RETRY_CONFIGS: Record<string, RetryConfig> = {
  // Insufficient funds — retry on a schedule (salary credit day, top-up cycle)
  '51': { maxAttempts: 4, intervalHours: 24, applicableStatuses: new Set(['recurring']) },
  // Issuer unavailable — retry quickly
  '91': { maxAttempts: 3, intervalHours: 4, applicableStatuses: new Set(['recurring', 'one_time']) },
  // System malfunction — retry quickly
  '96': { maxAttempts: 3, intervalHours: 4, applicableStatuses: new Set(['recurring', 'one_time']) },
  // Frequency limit — retry after period reset
  '65': { maxAttempts: 2, intervalHours: 48, applicableStatuses: new Set(['recurring']) },
  // Amount limit — retry with same amount after limit resets
  '61': { maxAttempts: 2, intervalHours: 24, applicableStatuses: new Set(['recurring']) },
};

@Injectable()
export class SoftDeclineRetryService {
  async scheduleRetry(payment: Payment, responseCode: string): Promise<void> {
    const config = RETRY_CONFIGS[responseCode];
    if (!config) return; // no retry config for this code

    if (!config.applicableStatuses.has(payment.type)) return;

    const canRetry = await this.retryTracker.canRetry(
      payment.cardFingerprint,
      payment.merchantId,
      'soft',
    );
    if (!canRetry.allowed) {
      await this.escalateToDunning(payment, responseCode);
      return;
    }

    const currentAttempt = payment.retryCount + 1;
    if (currentAttempt > config.maxAttempts) {
      await this.escalateToDunning(payment, responseCode);
      return;
    }

    const retryAt = addHours(new Date(), config.intervalHours);
    await this.paymentRetryRepo.create({
      originalPaymentId: payment.id,
      scheduledAt: retryAt,
      attemptNumber: currentAttempt,
      triggerCode: responseCode,
    });

    await this.retryQueue.enqueue(
      { originalPaymentId: payment.id, attemptNumber: currentAttempt },
      { delay: config.intervalHours * 60 * 60 * 1000 },
    );
  }

  private async escalateToDunning(payment: Payment, code: string): Promise<void> {
    await this.dunningService.initiateDunningFlow(payment.subscriptionId, {
      lastDeclineCode: code,
      exhaustedRetries: true,
    });
  }
}
```

**Q11. What is smart retry / intelligent retry, and how does it differ from naive scheduled retry?**
A: Naive retry fires at fixed intervals regardless of the underlying decline reason or the probability of success. Smart retry uses additional signals to predict the optimal retry window:

**Signals for smart retry:**

- **Decline code semantics** — `51` (insufficient funds) for a salary-linked debit card should be retried on the 1st and 15th of the month (typical salary credit dates in India) rather than at a fixed 24h interval.
- **Historical success patterns** — for a given BIN (bank + card type), track what time of day and day of month retries historically succeed. Issuers process batch credits at predictable times (NEFT settlement windows: 8am, 11am, 1pm, 3pm, 5pm, 7pm IST).
- **Account Updater signals** — if VAU/ABU indicates a card has been updated, retry immediately with the new card details rather than waiting for the next scheduled retry.
- **Cardholder activity** — if the cardholder logs into the platform after a decline (indicating they are aware and may have taken action), retry earlier than the schedule.
- **Alternate payment method availability** — if the cardholder has added a second card since the decline, skip the retry on the original card and attempt the new card directly.

```typescript
// smart-retry/retry-optimizer.ts
export class RetryOptimizer {
  async getOptimalRetryTime(
    payment: Payment,
    responseCode: string,
  ): Promise<Date> {
    // Base delay from config
    const baseConfig = RETRY_CONFIGS[responseCode];
    let retryAt = addHours(new Date(), baseConfig.intervalHours);

    if (responseCode === '51') {
      // Insufficient funds on Indian debit card — align with NEFT windows
      const cardCountry = await this.binService.getCountry(payment.cardBin);
      if (cardCountry === 'IN') {
        retryAt = this.getNextNeftWindow(retryAt);
      }

      // Check if it's near month-start — salary credit likely
      const dayOfMonth = retryAt.getDate();
      if (dayOfMonth >= 28 || dayOfMonth <= 3) {
        // Near month boundary — retry on the 1st at 10am IST
        retryAt = this.getNextFirstOfMonth(retryAt, 10);
      }
    }

    // Historical BIN success rate by hour
    const successRates = await this.analyticsRepo.getBinSuccessRateByHour(payment.cardBin);
    if (successRates.length) {
      const bestHour = successRates.reduce((a, b) => (a.rate > b.rate ? a : b)).hour;
      retryAt = setHours(retryAt, bestHour);
    }

    return retryAt;
  }

  private getNextNeftWindow(after: Date): Date {
    const neftWindows = [8, 11, 13, 15, 17, 19]; // IST hours
    const currentHour = getHours(after);
    const nextWindow = neftWindows.find(h => h > currentHour);
    if (nextWindow) return setHours(after, nextWindow);
    return setHours(addDays(after, 1), neftWindows[0]); // next day's first window
  }
}
```

**Q12. How do you handle `N7` (CVV2 Failure) specifically, and how does it differ from other soft declines?**
A: `N7` is a Visa-specific response code indicating the CVV2 (card verification value) entered by the cardholder does not match the issuer's record. It is a **conditionally soft** decline — the handling depends on attempt count:

- **First occurrence** — prompt the cardholder to re-enter their CVV carefully. The card itself is valid; only the security code was wrong. Do not classify as a hard decline; do not block the card.
- **Second occurrence on the same session** — still prompt re-entry but add a visual indicator ("Make sure you are entering the 3-digit code on the back of your card").
- **Third occurrence** — treat as a hard decline for this session. The cardholder either does not have the correct card or is entering incorrectly. Do not attempt further CVV retries — repeated CVV failures can trigger the issuer to flag the card as compromised.
- **Do not retry CVV failures in recurring/background flows** — CVV is a cardholder-present verification; it makes no sense in automated recurring payments. Recurring payments use network tokens or stored credentials without CVV re-verification. A `N7` in a recurring context indicates a system configuration error (CVV should not be sent for recurring transactions).

```typescript
const CVV_FAILURE_CODE = 'N7';
const MAX_CVV_RETRIES = 2;

async function handleCvvFailure(
  sessionId: string,
  paymentId: string,
): Promise<CvvDeclineOutcome> {
  const sessionKey = `cvv_failures:${sessionId}`;
  const failureCount = await redis.incr(sessionKey);
  await redis.expire(sessionKey, 3600); // 1h TTL — session scoped

  if (failureCount <= MAX_CVV_RETRIES) {
    return {
      action: 'prompt_retry',
      message: 'The security code you entered does not match. Please check the 3-digit CVV on the back of your card.',
      attemptsRemaining: MAX_CVV_RETRIES - failureCount + 1,
    };
  }

  // Exceeded max CVV retries — hard stop for this session
  await paymentsRepo.updateStatus(paymentId, 'failed', { responseCode: CVV_FAILURE_CODE });
  return {
    action: 'hard_stop',
    message: 'We were unable to verify your card. Please try a different payment method.',
    attemptsRemaining: 0,
  };
}
```

**Q13. What is the `91` (Issuer Inoperative) decline, and how do you build a resilient retry flow around it?**
A: `91` means the issuer's authorization system is temporarily unavailable — the card network could not reach the issuer to get a decision. This is a pure system availability failure, not a cardholder eligibility decision. The card may be perfectly valid with sufficient funds. `91` should almost always be retried.

However, there is a critical risk: if the merchant retries immediately and the original request is still in-flight (the issuer is processing but slow), a retry can cause a **duplicate authorization** — two auth holds on the cardholder's account. The correct retry strategy:

```
├── Auth request sent
├── Timeout (issuer not responding) or 91 received
│
├── Step 1: Query PG for status of original request (GET /payments/:id)
│   └── If status is 'authorized' — the original succeeded; proceed to capture
│   └── If status is 'failed'/'91' — safe to retry
│
├── Step 2: Wait minimum 30 seconds before retry
│   (allows in-flight request to complete or fail cleanly)
│
├── Step 3: Retry with same idempotency key
│   (PG deduplicates — if original arrived, returns existing auth; no duplicate)
│
└── Step 4: Apply exponential backoff for subsequent retries
```

```typescript
async function retryAfterIssuerUnavailable(
  originalPaymentId: string,
  attempt: number,
): Promise<void> {
  // Wait before retrying — exponential backoff: 30s, 60s, 120s
  const delaySeconds = 30 * Math.pow(2, attempt - 1);
  await sleep(delaySeconds * 1000);

  // Check if original request succeeded in the meantime
  const status = await gatewayService.getPaymentStatus(originalPaymentId);
  if (status === 'authorized') {
    // Original went through — no retry needed
    await paymentsRepo.updateStatus(originalPaymentId, 'authorized');
    return;
  }

  // Safe to retry
  const originalPayment = await paymentsRepo.findById(originalPaymentId);
  await gatewayService.createPayment({
    ...originalPayment,
    idempotencyKey: `${originalPayment.idempotencyKey}-retry-${attempt}`,
  });
}
```

## Section 4: User-Facing Messaging and PG Abstraction

**Q14. How do you translate raw decline codes into user-facing messages without exposing internal error details?**
A: The mapping from raw ISO code to user-facing message must satisfy two constraints: accurate enough to guide the cardholder to the correct action, but vague enough to not expose internal system state or assist fraudsters.

**Anti-patterns:**
- Showing raw codes ("Error: 05") — meaningless to cardholders, occasionally useful to fraudsters.
- Over-specific messages ("Your card is flagged as stolen") — alarms legitimate cardholders, confirms card status to fraudsters.
- Generic catch-all for all declines ("Payment failed. Try again.") — gives insufficient guidance; does not tell the cardholder what action will help.

**Q15. How do different payment gateways abstract decline codes, and what are the engineering implications of switching PGs?**
A: Each PG publishes its own normalized error taxonomy on top of ISO 8583. This creates a portability problem when switching PGs or running multi-PG routing.

**Razorpay:**
```json
{
  "error": {
    "code": "BAD_REQUEST_ERROR",
    "description": "Your payment has been declined...",
    "reason": "payment_failed",
    "source": "customer",
    "metadata": { "payment_id": "pay_xxx", "order_id": "ord_xxx" }
  }
}
```
Razorpay's `reason` field carries the normalized code; the raw issuer code is sometimes in `metadata`.

**Stripe:**
```json

  "error": {
    "type": "card_error",
    "code": "card_declined",
    "decline_code": "insufficient_funds",
    "message": "Your card has insufficient funds."
  }
}
```
Stripe's `decline_code` is the most useful field — it maps closely to ISO semantics with human-readable names.

**Cashfree:**
```json
{
  "status": "FAILED",
  "message": "Payment failed",
  "reason": "INSUFFICIENT_FUNDS",
  "bankReference": "xxx"
}
```

export interface NormalizedDecline {

  retryable: boolean;

}

export function normalizeRazorpayDecline(error: RazorpayError): NormalizedDecline {
  const rawCode = error.metadata?.issuer_error_code ?? 'unknown';
  const declineType = classifyDecline(rawCode, 'card');
  return {
    rawCode,
    normalizedCode: mapReasonToCanonical(error.reason),
    declineType,
    retryable: declineType === 'soft',
    pgSource: 'razorpay',
  };
}

export function normalizeStripeDecline(error: StripeError): NormalizedDecline {
  const declineCode = error.decline_code ?? error.code;
  const rawCode = STRIPE_TO_ISO_MAP[declineCode] ?? 'unknown';
  const declineType = classifyDecline(rawCode, 'card');
  return {
    rawCode,
    normalizedCode: declineCode,
    declineType,
    retryable: declineType === 'soft',
    pgSource: 'stripe',
  };
}

## Section 5: Dunning, Monitoring, and Advanced Scenarios

**Q16. What is a decline rate, and what metrics should a payments engineer track around declines?**
A: Decline rate is the percentage of authorization attempts that are declined. It is a primary health metric for a payment system, but must be disaggregated to be actionable:

**Key metrics:**

```
Overall decline rate = declined_auths / total_auth_attempts

Hard decline rate = hard_declined_auths / total_auth_attempts
Soft decline rate = soft_declined_auths / total_auth_attempts

By code: decline_rate[code] = declines_with_code / total_attempts
By BIN: decline_rate[bin] = declines_for_bin / attempts_for_bin
By merchant: decline_rate[merchant] = declines_for_merchant / attempts_for_merchant
By payment method: decline_rate[rail] = declines_for_rail / attempts_for_rail
```

**Alert thresholds (typical benchmarks):**
- Overall decline rate > 10%: investigate — industry average is 5–8% for card-not-present.
- Spike in `91`/`96` codes: issuer or network outage — alert on-call.
- `05` rate increase on a specific BIN: possible issuer-side fraud crackdown or card program change.
- Soft-to-hard ratio shift: if historically 70% of declines are soft and the ratio flips, something structural has changed (new card type in customer base, new market).

**CloudWatch/Datadog metrics to instrument:**

**Q17. What is a dunning process, and how does it integrate with decline code handling for subscription payments?**
A: Dunning is the systematic process of recovering failed subscription payments through a pre-defined sequence of retries, notifications, and escalations. It activates when initial soft-decline retries are exhausted or a hard decline is encountered on a recurring payment.

A production dunning flow for an Indian lending/subscription platform:

```
Day 0: Payment fails (decline code recorded)
  ├── Hard decline → Skip retries → Day 0 notification: "Update payment method"
  └── Soft decline → Schedule smart retries

Day 1: Retry 1 (soft decline only)
  └── Success → Resume subscription | Failure → Continue dunning

Day 3: Retry 2 + Email: "Your payment is failing — action required"

Day 7: Retry 3 + SMS + Email: "Service at risk — update payment method"

Day 10: Retry 4 (final auto-retry)
  └── Success → Resume | Failure → Grace period warning

Day 14: Grace period ends
  └── Subscription suspended (not cancelled — allows recovery)
  └── Final notification: "Your account has been suspended"

Day 30: Account cancellation if no recovery
  └── Cancellation notification
  └── Optionally: offer win-back incentive
```

```typescript
// subscriptions/dunning/dunning.service.ts
@Injectable()
export class DunningService {
  async initiateDunningFlow(
    subscriptionId: string,
    context: { lastDeclineCode: string; exhaustedRetries: boolean },
  ): Promise<void> {
    const subscription = await this.subscriptionsRepo.findById(subscriptionId);
    const declineType = classifyDecline(context.lastDeclineCode, subscription.paymentRail);

    await this.dunningRepo.create({
      subscriptionId,
      startedAt: new Date(),
      triggerCode: context.lastDeclineCode,
      declineType,
      status: 'active',
    });

    if (declineType === 'hard') {
      // No automatic retries — go straight to customer notification
      await this.notifyCardUpdateRequired(subscription, context.lastDeclineCode);
      await this.scheduleGracePeriodExpiry(subscriptionId, days(14));
    } else {
      // Schedule smart retries before falling back to notifications
      await this.softDeclineRetryService.scheduleRetry(
        subscription.lastPayment,
        context.lastDeclineCode,
      );
    }
  }

  private async notifyCardUpdateRequired(
    subscription: Subscription,
    declineCode: string,
  ): Promise<void> {
    const message = this.buildDunningMessage(declineCode);
    await this.notificationService.send({
      userId: subscription.customerId,
      channels: ['email', 'sms', 'push'],
      templateId: 'payment_method_update_required',
      data: {
        subscriptionName: subscription.planName,
        updateUrl: this.generateSecureUpdateUrl(subscription),
        declineReason: message.userFacingReason,
      },
    });
  }
}
```

**Q18. How do you build a decline intelligence system to detect issuer-side outages versus customer-side issues?**
A: A sudden spike in decline codes `91` and `96` across multiple different customers and merchants but concentrated in one card BIN or issuer — is not a customer behavior issue; it is an issuer outage. Treating it as a fraud signal or customer error wastes ops time and creates a poor cardholder experience.

Distinguishing issuer outage from customer-side declines:

| Signal | Issuer Outage | Customer Issue |
|---|---|---|
| Affected BINs | One or a few BINs (same issuer) | Spread across multiple BINs |
| Decline codes | `91`, `96` dominant | `05`, `51`, `54`, `57` |
| Time pattern | Spike starts at a specific time, recovers | Gradual, sustained |
| Geographic pattern | Specific bank's customers | Random distribution |
| Affected customers | Multiple distinct customers | Concentrated in a single account |

```typescript
// payments/analytics/issuer-health-monitor.ts
@Injectable()
export class IssuerHealthMonitor {
  // Runs every 5 minutes via cron
  @Cron('*/5 * * * *')
  async detectIssuerAnomalies(): Promise<void> {
    const window = subMinutes(new Date(), 15); // last 15 minutes

    const declinesByBin = await this.analyticsRepo.getDeclineRateByBin(window);

    for (const binStats of declinesByBin) {
      const outageCodeRate = binStats.declineCounts['91'] + binStats.declineCounts['96'];
      const totalDeclines = binStats.totalDeclines;
      const outageCodeProportion = outageCodeRate / (totalDeclines || 1);

      // If >60% of declines for a BIN are 91/96 — likely issuer outage
      if (outageCodeProportion > 0.6 && totalDeclines > 10) {
        await this.alertingService.raiseIssuerOutageAlert({
          bin: binStats.bin,
          issuerName: await this.binService.getIssuerName(binStats.bin),
          declineRate: binStats.declineRate,
          dominantCode: '91/96',
          windowMinutes: 15,
        });

        // Suspend automated retries for this BIN during outage — don't pile on the issuer
        await this.retryManager.pauseRetriesForBin(binStats.bin, minutes(30));
      }
    }
  }
}
```

## Section 6: Scenario / System Design Style Questions

**Q19. "Design a decline handling system for a lending platform that processes both one-time loan disbursements and recurring EMI collections."**
A: Loan disbursements and EMI collections have fundamentally different decline semantics and must be handled separately:

**Loan disbursement (outgoing — lender to borrower):**
Disbursement failures (failed NEFT/IMPS/UPI credit to borrower's account) are not card decline codes — they are bank transfer failure codes (NPCI return codes, NEFT rejection codes). Common reasons: incorrect account number, account dormant, account frozen. These are hard failures; the disbursement must be retried only after the borrower corrects their bank details.

**EMI collection (incoming — borrower to lender):**
EMI collections are recurring card charges or NACH debits. These are subject to card decline codes or NACH return codes.

```typescript
// lending/payments/emi-collection.service.ts
@Injectable()
export class EmiCollectionService {
  async collectEmi(emiId: string): Promise<EmiCollectionResult> {
    const emi = await this.emiRepo.findById(emiId);
    const mandate = await this.mandateRepo.findByLoanId(emi.loanId); // NACH mandate or e-mandate

    let result: CollectionAttemptResult;

    if (mandate.type === 'nach') {
      result = await this.nachService.presentDebit(mandate.id, emi.amount, emi.dueDate);
    } else if (mandate.type === 'recurring_card') {
      result = await this.cardService.chargeStoredCard(mandate.cardToken, emi.amount);
    }

    if (result.success) {
      await this.emiRepo.markPaid(emiId, result.referenceId);
      await this.loanLedgerService.recordRepayment(emi.loanId, emi.amount);
      return { status: 'collected' };
    }

    // EMI collection failed — classify and handle
    return this.handleEmiDecline(emi, mandate, result.declineCode);
  }

  private async handleEmiDecline(
    emi: Emi,
    mandate: Mandate,
    declineCode: string,
  ): Promise<EmiCollectionResult> {
    const declineType = mandate.type === 'nach'
      ? classifyNachReturn(declineCode)
      : classifyDecline(declineCode, 'card');

    await this.emiRepo.recordFailure(emi.id, declineCode, declineType);

    // RBI guidelines: EMI overdue triggers NPA classification timeline
    // Must notify borrower and initiate dunning within 24h of first failure
    await this.dunningService.initiateEmiDunning({
      emiId: emi.id,
      loanId: emi.loanId,
      borrowerId: emi.borrowerId,
      declineCode,
      declineType,
      dueDate: emi.dueDate,
    });

    // Penal interest starts accruing from due date — record in loan ledger
    await this.loanLedgerService.recordPenalInterestStart(emi.loanId, emi.dueDate);

    return { status: 'failed', declineCode, declineType };
  }
}
```

**NACH-specific return codes** (NPCI-defined, distinct from ISO 8583):

| NACH Code | Meaning | Classification |
|---|---|---|
| `01` | Account closed | Hard |
| `05` | Insufficient funds | Soft |
| `09` | Account blocked | Hard |
| `12` | Account does not exist | Hard |
| `13` | Frozen account | Hard |
| `22` | Mandate not registered | Hard — re-registration required |
| `24` | Mandate revoked by account holder | Hard — borrower has cancelled mandate |

**Q20. "A merchant's overall decline rate has increased from 6% to 18% over the past week. Walk through your investigation."**
A: A 3× increase in decline rate is a P1 incident. Systematic investigation:

**Step 1 — Segment the increase (first 30 minutes)**
```sql
-- Break down by decline code to find what changed
SELECT
  response_code,
  DATE_TRUNC('day', created_at) AS day,
  COUNT(*) AS decline_count,
  COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (PARTITION BY DATE_TRUNC('day', created_at)) AS pct
FROM payment_attempts
WHERE merchant_id = '<merchant_id>'
  AND status = 'failed'
  AND created_at > NOW() - INTERVAL '14 days'
GROUP BY 1, 2
ORDER BY 2 DESC, 4 DESC;
```

**Step 2 — Identify the dominant code and map to root cause**

| Dominant New Code | Likely Root Cause | Next Step |
|---|---|---|
| Spike in `91`/`96` | Issuer outage or network degradation | Check issuer status pages; check if spike is BIN-specific |
| Spike in `05` | Issuer changed fraud scoring (new rules) | Check if specific BIN or all BINs; contact acquirer |
| Spike in `14` | Card data corruption bug in update/migration | Check if code change deployed in the same window |
| Spike in `54` | Stored card expiry not updated | Check if Account Updater is running correctly |
| Spike in `57` | New MCC assignment or restriction policy | Check if merchant's MCC was recently changed |
| Broad increase across all codes | Acquirer routing issue; 3DS misconfiguration | Check acquirer dashboard; check 3DS pass rates |

**Step 3 — Cross-reference with deployment timeline**
```bash
# Check if a deployment happened in the same time window as the spike
git log --oneline --after="2026-08-13" --before="2026-08-20"
# Correlate deploy timestamps with the first spike in decline metrics
```

**Step 4 — Check 3DS pass rate separately**
A decline rate increase that is not explained by code analysis may be a 3DS authentication failure — the transaction never reaches the issuer for authorization. 3DS failures return before the ISO decline code is generated.

```sql
SELECT
  DATE_TRUNC('hour', created_at),
  COUNT(*) FILTER (WHERE threeds_status = 'authenticated') AS threeds_success,
  COUNT(*) FILTER (WHERE threeds_status = 'failed') AS threeds_failed,
  COUNT(*) AS total
FROM payment_attempts
WHERE merchant_id = '<merchant_id>'
  AND created_at > NOW() - INTERVAL '7 days'
GROUP BY 1
ORDER BY 1 DESC;
```

**Step 5 — Remediation by root cause**
- Issuer outage → pause retries for affected BINs; inform merchant; recover automatically when outage resolves.
- Code bug (`14` spike from card data corruption) → rollback or hotfix the deployment; re-process affected payments.
- Fraud scoring change from issuer → contact acquirer relationship manager; adjust checkout flow (add 3DS on more transactions, reduce pre-auth amounts).
- MCC misconfiguration → work with acquirer to correct MCC; process refunds for incorrectly declined legitimate transactions.
