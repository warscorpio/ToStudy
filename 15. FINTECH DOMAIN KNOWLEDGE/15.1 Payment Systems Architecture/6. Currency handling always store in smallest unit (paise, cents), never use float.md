# Payment Lifecycle: Currency Handling — Smallest Unit Storage, Float Avoidance & Precision Arithmetic — Interview Q&A (5 YOE Level)

> **Domain:** Fintech / Payment Systems Architecture

---

## Section 1: Fundamentals

**Q1. Why is currency handling a correctness problem, not just a style preference?**

A: In most software domains, a rounding error of 0.000001 is inconsequential. In payments, it is a regulatory defect, a reconciliation failure, and a customer trust issue.

Consider three consequences of incorrect currency handling:

- **Financial loss:** A rounding error of ₹0.01 per transaction at 10 million transactions/day is ₹100,000/day in unaccounted money — money that either disappears from the system or accumulates as an unreconciled surplus.
- **Regulatory non-compliance:** RBI, SEBI, and equivalent regulators require that every paisa in a payment system be accounted for. A system that loses precision in intermediate calculations cannot produce a clean audit trail.
- **Reconciliation failure:** Your system's ledger must match the payment gateway's settlement report to the last paisa. A float-induced rounding difference causes a mismatch that triggers manual investigation on every settlement cycle.

Currency handling is a correctness problem at the same level as idempotency or atomicity — not a cosmetic one.

---

**Q2. What is the floating-point problem, and why does it make floats categorically wrong for money?**

A: IEEE 754 floating-point (the standard behind JavaScript's `number`, Python's `float`, Java's `double`) represents numbers in base-2 (binary). Most decimal fractions — including nearly all currency values — cannot be represented exactly in binary. The decimal `0.1` in binary is `0.0001100110011...` repeating forever; the hardware stores a rounded approximation.

**Concrete demonstration in Node.js:**

```javascript
> 0.1 + 0.2
0.30000000000000004

> 1.005.toFixed(2)
'1.00'   // Expected '1.01' — the stored value is 1.00499999...

> 0.1 + 0.2 === 0.3
false
```

In a payment context:

```javascript
// Calculating GST at 18%
const price = 1999.99;  // float
const gst   = price * 0.18;
console.log(gst);  // 359.99820000000004 — not 360.00

// Summing line items
const items = [10.10, 20.20, 30.30];
const total = items.reduce((a, b) => a + b, 0);
console.log(total);  // 60.599999999999994 — not 60.60
```

These errors are not bugs in your code — they are the deterministic, specified behavior of IEEE 754. The only correct fix is to never use floating-point types for currency values. Floats are for scientific computation where approximate answers are acceptable. Money requires exact arithmetic.

**Q3. What does "store in the smallest unit" mean, and what is the smallest unit for common currencies?**

A: The **smallest unit** is the indivisible atomic unit of a currency — the unit below which no subdivision exists in that currency's official denomination. All monetary values are stored as integers representing a count of this unit.

| Currency | Smallest unit | Symbol | Multiplier from major unit |
|---|---|---|---|
| Indian Rupee | Paise | ₹ / INR | 1 rupee = 100 paise |
| US Dollar | Cent | $ / USD | 1 dollar = 100 cents |
| Euro | Euro cent | € / EUR | 1 euro = 100 cents |
| Japanese Yen | Yen | ¥ / JPY | 1 yen = 1 yen (zero decimal places) |
| Kuwaiti Dinar | Fils | KWD | 1 dinar = 1000 fils (3 decimal places) |
| Bitcoin | Satoshi | BTC | 1 BTC = 100,000,000 satoshis |

**Rule:** Never store `19.99`. Store `1999` (paise / cents). The display layer divides by the currency's subunit factor when rendering to a human, but the storage and computation layer never touches a decimal point.

This is not an internal convention — it is the standard used by every major payment gateway. JusPay, Razorpay, and Stripe all accept and return amounts in the smallest unit. Sending `amount: 1999` to Razorpay means ₹19.99. Sending `amount: 19.99` is a request to charge ₹0.1999 — a bug that is both a business loss and a gateway validation error.

**Q4. What is the difference between integer arithmetic and decimal arithmetic, and which do you use for money?**

A: **Integer arithmetic** operates on whole numbers with no fractional part. All four basic operations (`+`, `-`, `*`, `/`) are exact when the operands are integers and the result is also an integer. Division that produces a non-integer result must be handled explicitly (floor, ceiling, or banker's rounding). In JavaScript/Node.js, safe integers are in the range `-(2^53 - 1)` to `2^53 - 1` — sufficient for any realistic monetary value in paise.

**Decimal arithmetic** operates on numbers that maintain a fixed number of digits after a decimal point, using base-10 internally rather than base-2. Libraries like `decimal.js`, `big.js`, and Java's `BigDecimal` implement this. `0.1 + 0.2` in a decimal library returns exactly `0.3`.

**For money, the recommendation in order of preference:**

1. **Integers (paise/cents) + integer arithmetic** — the simplest and most performant. Use this for all storage and most computation. All arithmetic on stored values is integer arithmetic; the decimal point only appears at the display layer.
2. **BigInt in JavaScript** — for very large values (crypto, high-value wire transfers) where even integer multiplication of large paise amounts might approach `Number.MAX_SAFE_INTEGER`. `BigInt` arithmetic is always exact.
3. **Decimal library** — for intermediate calculations that inherently produce non-integer results (tax rates, FX conversions, pro-rata splits) before the final value is rounded back to paise. Use `decimal.js` or `big.js` in Node.js; `BigDecimal` in Java.
4. **Float** — never, for any monetary value, in any context, at any layer.

## Section 2: Storage Design

**Q5. How do you design a database schema for monetary values?**

A: Store monetary amounts as integers in the smallest unit, alongside an explicit currency code. Never infer currency from context.

**PostgreSQL schema:**

```sql
CREATE TABLE payments (
    payment_id    UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
    amount_paise  BIGINT        NOT NULL CHECK (amount_paise > 0),
    currency      CHAR(3)       NOT NULL DEFAULT 'INR',  -- ISO 4217
    status        TEXT          NOT NULL,
    created_at    TIMESTAMPTZ   NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
    item_id       UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id      UUID          NOT NULL REFERENCES orders(order_id),
    unit_price    BIGINT        NOT NULL CHECK (unit_price >= 0),  -- paise
    quantity      INT           NOT NULL CHECK (quantity > 0),
    currency      CHAR(3)       NOT NULL
);
```

**Column type choices:**

| Type | Max value | Notes |
|---|---|---|
| `INT` (32-bit) | ~21.47 crore paise = ~₹21.47 lakh | Sufficient for most consumer payments |
| `BIGINT` (64-bit) | ~922 lakh crore paise | Use for any system where large values are possible (B2B, wholesale, crypto) |
| `NUMERIC(19, 0)` | Arbitrary precision integer | Use when you need arbitrary precision without the risk of overflow; slower than `BIGINT` |
| `DECIMAL(19, 4)` | 15 digits before decimal, 4 after | Only if you have a genuine need for sub-paise precision (FX rates, interest accrual); requires explicit rounding policy |

**Never use:** `FLOAT`, `DOUBLE PRECISION`, `REAL` — all are IEEE 754 types and introduce the binary representation error described in Q2.

**Q6. Should you store currency alongside every monetary amount, or is it safe to assume a single currency per system?**

A: Always store the currency code alongside every monetary amount — even in a system that currently handles only INR. The currency column costs 3 bytes and prevents an entire class of bugs. Arguments against storing currency ("we only do INR") fail the following tests:

- **Regulatory requirement:** Any system that processes cross-border payments, NRI accounts, or foreign currency accounts must track currency per transaction. Adding the column retroactively to a large payments table is a painful migration.
- **Copy-paste errors:** If a developer sees `amount_paise BIGINT` with no currency column and copies a JPY amount (which uses no subunits) into the same field, the value is 100× wrong silently.
- **Multi-currency creep:** Most fintech products that start INR-only eventually add USD, AED, or SGD for international users. Retrofitting currency tracking into a schema that assumed a single currency requires a data migration, an API version bump, and weeks of testing.

**Currency codes:** Use ISO 4217 three-letter codes (`INR`, `USD`, `EUR`, `JPY`). Store as `CHAR(3)`, not as a free-text string, and validate against a known list at the application layer.

**Q7. How do you represent the "subunit exponent" for multi-currency systems, and why does it matter for arithmetic?**

A: Different currencies have different numbers of decimal places (subunit exponents):

| Currency | ISO 4217 exponent | Subunit factor |
|---|---|---|
| INR, USD, EUR | 2 | 100 (paise, cents) |
| JPY, KRW | 0 | 1 (no subunit) |
| KWD, BHD, OMR | 3 | 1000 (fils) |
| BTC (informal) | 8 | 100,000,000 (satoshis) |

**The exponent matters for arithmetic** because you cannot add `500 JPY` (stored as `500`) to `500 INR` (stored as `50000`) and get a meaningful result. You also cannot display `50000` as a monetary amount without knowing the currency's exponent — is it `₹500.00` or `¥50000`?

**Implementation pattern:**

```typescript
const CURRENCY_CONFIG: Record<string, { exponent: number; symbol: string }> = {
  INR: { exponent: 2, symbol: '₹' },
  USD: { exponent: 2, symbol: '$' },
  JPY: { exponent: 0, symbol: '¥' },
  KWD: { exponent: 3, symbol: 'KD' },
};

function toSmallestUnit(amount: number, currency: string): number {
  const { exponent } = CURRENCY_CONFIG[currency];
  return Math.round(amount * 10 ** exponent);
}

function fromSmallestUnit(amount: number, currency: string): string {
  const { exponent, symbol } = CURRENCY_CONFIG[currency];
  return `${symbol}${(amount / 10 ** exponent).toFixed(exponent)}`;
}

// Usage
toSmallestUnit(19.99, 'INR')  // → 1999 (paise)
toSmallestUnit(500,  'JPY')   // → 500  (no conversion)
toSmallestUnit(1.500, 'KWD')  // → 1500 (fils)
```

This config-driven approach is safer than hardcoding `/ 100` throughout the codebase — a currency added later with a different exponent works automatically.

**Q8. How do you safely convert between user-input (decimal) and storage (integer) representations?**

A: User input arrives as a decimal string from a form field or API payload (`"199.99"`). The conversion to storage units must handle:

1. **Input as string, not float** — parse the string directly; do not let JavaScript convert it to a float first.
2. **Explicit rounding** — the conversion must use a defined rounding mode, not implicit truncation.
3. **Validation before conversion** — reject inputs that exceed the currency's allowed decimal places.

```typescript
import Decimal from 'decimal.js';

function parseAmountToSmallestUnit(
  input: string,        // e.g., "199.99" or "200"
  currency: string,     // e.g., "INR"
): bigint {
  const { exponent } = CURRENCY_CONFIG[currency];

  // Validate: no more decimal places than the currency allows
  const decimalIndex = input.indexOf('.');
  if (decimalIndex !== -1) {
    const decimalPlaces = input.length - decimalIndex - 1;
    if (decimalPlaces > exponent) {
      throw new ValidationError(
        `${currency} supports at most ${exponent} decimal places; got ${decimalPlaces}`
      );
    }
  }

  // Use Decimal.js to avoid float representation errors during conversion
  const factor = new Decimal(10).pow(exponent);
  const smallestUnit = new Decimal(input).mul(factor).toDecimalPlaces(0);

  return BigInt(smallestUnit.toFixed(0));
}

// Safe:   parseAmountToSmallestUnit("199.99", "INR") → 19999n
// Safe:   parseAmountToSmallestUnit("200",    "INR") → 20000n
// Throws: parseAmountToSmallestUnit("199.999","INR") → ValidationError
// Unsafe: parseInt(parseFloat("199.99") * 100) → 19998 or 20000 depending on float error
```

**Why `parseInt(parseFloat(input) * 100)` is wrong:** `parseFloat("199.99")` returns `199.98999999999999` in IEEE 754. Multiplying by 100 gives `19998.999999...`. `parseInt` truncates to `19998` — 1 paise short. This is the canonical bug that appears in codebases that start handling money casually.

## Section 3: Arithmetic & Rounding

**Q9. What are the common rounding modes, and which is correct for payments?**

A: Rounding is required whenever division or multiplication produces a result that cannot be represented exactly in the smallest unit. The choice of rounding mode affects who gains and who loses the fractional unit.

| Rounding mode | Description | Example (2.5 → integer) |
|---|---|---|
| **Round half up** | .5 rounds to the next integer away from zero | 2.5 → 3, -2.5 → -2 |
| **Round half down** | .5 rounds toward zero | 2.5 → 2, -2.5 → -3 |
| **Round half even** (Banker's rounding) | .5 rounds to the nearest even integer | 2.5 → 2, 3.5 → 4 |
| **Round half away from zero** | .5 rounds away from zero in both directions | 2.5 → 3, -2.5 → -3 |
| **Truncate** (floor toward zero) | Fractional part is discarded | 2.9 → 2, -2.9 → -2 |

**For payments:**
- **Default:** Round half up (most intuitive, matches customer expectations, matches how most gateways round).
- **For interest / tax calculations:** Banker's rounding (round half even) is preferred because it is statistically unbiased — over many transactions, it does not systematically favor either the merchant or the customer. Mandated by some accounting standards.
- **Never truncate** for final amounts — truncation systematically favors one party and will cause reconciliation drift over time.

**In Node.js with `decimal.js`:**

```typescript
import Decimal from 'decimal.js';

Decimal.set({ rounding: Decimal.ROUND_HALF_UP }); // set globally

const tax = new Decimal('199.99').mul('0.18');  // 35.9982
const taxPaise = tax.toDecimalPlaces(2, Decimal.ROUND_HALF_UP); // 36.00
```

**Q10. How do you split an amount evenly across N parties without losing or gaining paise?**

A: Splitting `total` across `N` parties is a classic fintech problem — integer division always leaves a remainder, and distributing the remainder incorrectly causes the split to not sum back to the original total.

**Example:** Split ₹100.00 (10000 paise) among 3 parties.
- `10000 / 3 = 3333.33...` — each party gets 3333 paise.
- `3333 × 3 = 9999` — 1 paise disappears.

**Correct algorithm — "largest remainder" method:**

```typescript
function splitAmount(totalPaise: bigint, n: number): bigint[] {
  const base = totalPaise / BigInt(n);           // integer division (floor)
  const remainder = totalPaise % BigInt(n);      // leftover paise

  // Give 'remainder' extra parties 1 paise more
  return Array.from({ length: n }, (_, i) =>
    BigInt(i) < remainder ? base + 1n : base
  );
}

splitAmount(10000n, 3);
// → [3334n, 3333n, 3333n]  (sum = 10000 ✓)

splitAmount(10000n, 4);
// → [2500n, 2500n, 2500n, 2500n]  (sum = 10000 ✓)

splitAmount(10001n, 3);
// → [3334n, 3334n, 3333n]  (sum = 10001 ✓)
```

**The rule:** `sum(splits) === total` must be a hard invariant. Add a test that verifies this for every split function in your codebase — not as a nicety, but as a property test with randomized inputs.

**Q11. How do you calculate tax (GST) on a payment amount correctly?**

A: Tax calculation has three correctness requirements:
1. Use integer/decimal arithmetic — no floats.
2. Apply a defined rounding mode consistently.
3. Decide whether the displayed price is **inclusive** or **exclusive** of tax before computing.

**Tax-exclusive (price + GST):**

```typescript
import Decimal from 'decimal.js';

function addGST(amountPaise: bigint, gstRate: string): {
  base: bigint;
  gst: bigint;
  total: bigint;
} {
  const base = new Decimal(amountPaise.toString());
  const gst  = base.mul(gstRate).toDecimalPlaces(0, Decimal.ROUND_HALF_UP);
  const total = base.add(gst);

  return {
    base:  amountPaise,
    gst:   BigInt(gst.toFixed(0)),
    total: BigInt(total.toFixed(0)),
  };
}

addGST(10000n, '0.18');
// base: 10000n (₹100.00), gst: 1800n (₹18.00), total: 11800n (₹118.00)

addGST(9999n, '0.18');
// base: 9999n (₹99.99), gst: 1800n (₹18.00 rounded from 1799.82), total: 11799n
```

**Tax-inclusive (extract GST from a price that already includes it):**

```typescript
function extractGST(totalPaise: bigint, gstRate: string): {
  base: bigint;
  gst: bigint;
} {
  // base = total / (1 + rate)
  const total = new Decimal(totalPaise.toString());
  const divisor = new Decimal(1).add(gstRate);
  const base = total.div(divisor).toDecimalPlaces(0, Decimal.ROUND_HALF_UP);
  const gst  = total.sub(base);

  return {
    base: BigInt(base.toFixed(0)),
    gst:  BigInt(gst.toFixed(0)),
  };
}

extractGST(11800n, '0.18');
// base: 10000n, gst: 1800n  ✓
```

**Always verify:** `base + gst === total`. Add this as an assertion after every tax calculation.

**Q12. How do you handle FX conversion between currencies without accumulating errors?**

A: Foreign exchange conversion is where even a correctly designed integer-storage system can fail if the conversion step is careless. An FX rate like `1 USD = 83.4521 INR` has more precision than paise allows — the conversion produces a non-integer result that must be rounded.

**Rules for FX conversion:**

1. **Store FX rates as high-precision decimals, not floats.** Use `NUMERIC(18, 8)` in Postgres, or a `decimal.js` `Decimal` in Node.js. A rate stored as `83.45` instead of `83.4521` introduces an error of `0.0021` per dollar — at $10,000 that is ₹21 of drift per transaction.
2. **Apply the rate using decimal arithmetic**, not float multiplication.
3. **Round the result to the target currency's smallest unit** using a defined rounding mode.
4. **Store the rate used** alongside every converted amount — for audit, for reconciliation, and for dispute resolution.

```typescript
import Decimal from 'decimal.js';

interface FXConversion {
  sourceAmount:    bigint;   // in source currency's smallest unit
  sourceCurrency:  string;
  targetAmount:    bigint;   // in target currency's smallest unit
  targetCurrency:  string;
  rateUsed:        string;   // stored as a string for exact replay
  convertedAt:     Date;
}

function convertCurrency(
  sourceAmountSmallest: bigint,
  sourceCurrency: string,
  targetCurrency: string,
  fxRate: string,           // e.g., "83.4521" — string, not float
): FXConversion {
  const sourceConfig = CURRENCY_CONFIG[sourceCurrency];
  const targetConfig = CURRENCY_CONFIG[targetCurrency];

  // Convert source to major unit, apply rate, convert to target smallest unit
  const sourceMajor  = new Decimal(sourceAmountSmallest.toString())
                          .div(10 ** sourceConfig.exponent);
  const targetMajor  = sourceMajor.mul(fxRate);
  const targetSmallest = targetMajor
                          .mul(10 ** targetConfig.exponent)
                          .toDecimalPlaces(0, Decimal.ROUND_HALF_UP);

  return {
    sourceAmount:   sourceAmountSmallest,
    sourceCurrency,
    targetAmount:   BigInt(targetSmallest.toFixed(0)),
    targetCurrency,
    rateUsed:       fxRate,
    convertedAt:    new Date(),
  };
}

convertCurrency(100n, 'USD', 'INR', '83.4521');
// sourceAmount: 100n cents ($1.00)
// targetAmount: 8345n paise (₹83.45, rounded from 83.4521 paise)
```

## Section 4: Display & Serialization

**Q13. How do you format a paise/cents amount for display to users?**

A: The display layer is the only place where the integer value is divided by the subunit factor. The division must produce a string, not a float, for the same reasons as input parsing.

```typescript
function formatAmount(amountSmallest: bigint, currency: string): string {
  const { exponent, symbol } = CURRENCY_CONFIG[currency];

  if (exponent === 0) {
    return `${symbol}${amountSmallest.toString()}`;
  }

  const factor = BigInt(10 ** exponent);
  const major  = amountSmallest / factor;
  const minor  = amountSmallest % factor;

  // Pad minor unit to the correct number of digits (e.g., 5 paise → "05")
  const minorStr = minor.toString().padStart(exponent, '0');

  return `${symbol}${major}.${minorStr}`;
}

formatAmount(19999n, 'INR');  // → "₹199.99"
formatAmount(500n,   'JPY');  // → "¥500"
formatAmount(1500n,  'KWD');  // → "KD1.500"
formatAmount(5n,     'INR');  // → "₹0.05"   (not "₹5" or "₹.5")
```

**Locale-aware formatting:** For user-facing display (invoices, statements), use `Intl.NumberFormat` with the currency code — it handles locale-specific separators (`,` vs `.`), RTL currencies, and symbol placement automatically:

```typescript
function formatAmountLocale(
  amountSmallest: bigint,
  currency: string,
  locale = 'en-IN',
): string {
  const { exponent } = CURRENCY_CONFIG[currency];
  const majorValue = Number(amountSmallest) / 10 ** exponent;

  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency,
    minimumFractionDigits: exponent,
    maximumFractionDigits: exponent,
  }).format(majorValue);
}

formatAmountLocale(199999n, 'INR', 'en-IN');  // → "₹1,999.99"
formatAmountLocale(199999n, 'USD', 'en-US');  // → "$1,999.99"
```

Note: `Intl.NumberFormat` receives a `Number` (float) for formatting only — this is acceptable because the output is a display string, not a value used in further arithmetic. The float error at display precision is invisible to the user.

**Q14. How do you serialize monetary values in API responses? Should you return integers or decimal strings?**

A: A frequently debated design decision. The two options:

**Option A — Return integers (smallest unit):**
```json
{ "amount": 19999, "currency": "INR" }
```
- Client must know the currency's exponent to display the value.
- Consistent with how payment gateways (Razorpay, JusPay, Stripe) return amounts.
- No ambiguity: `19999` is always 19999 paise, regardless of JSON parser floating-point behavior.

**Option B — Return decimal strings:**
```json
{ "amount": "199.99", "currency": "INR" }
```
- Human-readable without knowing the exponent.
- Must be a **string** not a **number** — `"amount": 199.99` as a JSON number is subject to float representation in the client's JSON parser.
- Common in accounting APIs and internal microservice responses.

**Option C — Return both:**
```json
{ "amount_smallest": 19999, "amount_display": "199.99", "currency": "INR" }
```
- Most explicit. The consumer uses `amount_smallest` for computation and `amount_display` for rendering.
- Verbose but eliminates any ambiguity about which field to use for what purpose.

**Recommendation:** For payment gateway-style public APIs, use Option A (integers, consistent with industry convention). For internal microservice APIs where human readability matters, use Option B (decimal strings, never JSON numbers). Document the choice explicitly in your API spec — the worst outcome is an undocumented API where half the consumers assume integers and half assume floats.

**Never return JSON numbers for monetary values:** `{ "amount": 199.99 }` — some JSON parsers (particularly older ones, or environments using 32-bit floats) will deserialize this as `199.98999...`. The field type must be either integer or string.

**Q15. How do you handle monetary values in logs and audit trails?**

A: Logs and audit trails have two requirements that conflict: human readability (so engineers can debug without a converter) and exactness (so the audit trail is legally defensible).

**Rules:**

1. **Log both the integer (storage) value and the formatted display value:**
   ```typescript
   logger.info({
     payment_id:     paymentId,
     amount_paise:   1999,           // exact, for audit
     amount_display: '₹19.99',       // human-readable, for debugging
     currency:       'INR',
   }, 'Payment initiated');
   ```

2. **Never log floats derived from monetary amounts.** `amount_float: 19.99` in a log is a float — it may round-trip through the log aggregator as `19.989999...`. Log the integer.

3. **Audit tables should mirror the storage schema** — store paise integers, not formatted strings. The display is generated at query time.

4. **For financial audit trails (required by regulation), log:**
   - The raw amount in smallest units.
   - The currency code.
   - The rounding mode used (if any rounding occurred in the transaction).
   - The exchange rate (if FX conversion occurred).
   - Timestamp with timezone (not epoch, not local time — `TIMESTAMPTZ` in Postgres, ISO 8601 in logs).

## Section 5: Common Bugs & Anti-Patterns

**Q16. What are the most common currency-handling bugs in Node.js/TypeScript codebases, and how do you prevent each?**

A:

| Bug | Example | Prevention |
|---|---|---|
| **Float multiplication for tax** | `amount * 0.18` where `amount` is a float | Store as paise; use `decimal.js` for rate multiplication |
| **`parseFloat` in input parsing** | `parseFloat(req.body.amount) * 100` | Parse input string with `decimal.js`; never use `parseFloat` on monetary input |
| **`toFixed()` for rounding** | `(1.005).toFixed(2)` → `"1.00"` | Never use `toFixed()` for rounding arithmetic; use `decimal.js` `.toDecimalPlaces()` |
| **Implicit float coercion from DB** | Postgres `NUMERIC` returned as JS `number` | Use `pg` with `types.setTypeParser` for numeric types, or always pass through `BigInt`/`Decimal` |
| **Summing in the wrong layer** | `SELECT SUM(amount_float) FROM payments` | Store as `BIGINT`; sum at DB layer where arithmetic is exact |
| **Displaying paise as rupees** | Logging `amount_paise` without a label, displaying raw paise value to users | Strict naming convention: always suffix column/variable with `_paise`, `_cents`, `_smallest_unit` |
| **Inconsistent rounding across services** | Service A uses round-half-up, Service B uses truncate | Centralize rounding logic in a shared library/package; enforce via linting rules |
| **Currency mismatch in arithmetic** | Adding `amount_paise` (INR) to `amount_cents` (USD) | Carry currency code everywhere; add a runtime check before any arithmetic between two amounts |

**Q17. How do you prevent float amounts from entering the system at the API boundary?**

A: The API boundary is the last checkpoint before untrusted data enters the system. Validation must reject float-typed monetary values before they reach business logic.

**NestJS DTO validation pattern:**

```typescript
import { IsString, Matches, IsInt, IsPositive, Length } from 'class-validator';
import { Transform } from 'class-transformer';

export class CreatePaymentDto {
  // Option A: Accept string, validate format, parse in service
  @IsString()
  @Matches(/^\d+(\.\d{1,2})?$/, { message: 'amount must be a decimal string with at most 2 decimal places' })
  amount: string;  // "199.99"

  // Option B: Accept integer (smallest unit) directly
  @IsInt()
  @IsPositive()
  amountPaise: number;  // 19999

  @IsString()
  @Length(3, 3)
  @Matches(/^[A-Z]{3}$/)
  currency: string;  // "INR"
}
```

**At the service layer (Option A):**

```typescript
@Injectable()
export class PaymentsService {
  async create(dto: CreatePaymentDto): Promise<Payment> {
    const amountPaise = parseAmountToSmallestUnit(dto.amount, dto.currency);
    // All further logic uses amountPaise (bigint) — no floats
  }
}
```

**Additional guards:**
- Add a custom validation decorator `@IsMonetaryString(currency)` that validates the number of decimal places based on the currency's exponent — injectable from `CURRENCY_CONFIG`.
- In TypeScript, define a branded type `type Paise = bigint & { readonly __brand: 'Paise' }` to prevent accidentally passing a raw `bigint` that hasn't been validated through the conversion function.

**Q18. How does PostgreSQL handle arithmetic on `BIGINT` columns, and what should you watch for?**

A: PostgreSQL's `BIGINT` arithmetic is exact for all four operations. However, several edge cases require explicit handling:

**Integer division truncates:**
```sql
SELECT 10001 / 3;  -- Returns 3333, not 3333.67
```
For division that must preserve precision (splitting, FX), do the division in the application layer using `decimal.js`, not in SQL.

**SUM overflow:**
```sql
SELECT SUM(amount_paise) FROM payments;
-- Returns BIGINT (max ~9.2 × 10^18)
-- 9.2 × 10^18 paise = ₹9.2 × 10^16 — far beyond any realistic payment volume
```
`SUM` of `BIGINT` in Postgres returns `NUMERIC` (not `BIGINT`) to avoid overflow — this is correct behavior. Treat aggregate results as `NUMERIC`/`Decimal` in the application.

**Returning NUMERIC from Postgres in Node.js:**

By default, `node-postgres` (`pg`) returns `NUMERIC` columns as JavaScript strings (not numbers) — because JavaScript `number` cannot represent all `NUMERIC` values exactly. This is intentional and correct:

```typescript
import { Pool } from 'pg';
import Decimal from 'decimal.js';

const pool = new Pool({ ... });

const result = await pool.query('SELECT SUM(amount_paise) AS total FROM payments');
const total = new Decimal(result.rows[0].total); // string → Decimal, exact
```

Do **not** do `parseInt(result.rows[0].total)` — this silently loses precision for values larger than `Number.MAX_SAFE_INTEGER` (9,007,199,254,740,991 — about ₹90 trillion, within range of a national payment system's daily volume).

## Section 6: System Design Scenario Questions

**Q19. "Design the data model for a multi-currency wallet in a lending platform."**

A: A multi-currency wallet must track balances per currency, support credit and debit operations, and maintain an immutable ledger for audit.

**Schema:**

```sql
-- Wallet: one per user per currency
CREATE TABLE wallets (
    wallet_id     UUID    PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       UUID    NOT NULL REFERENCES users(user_id),
    currency      CHAR(3) NOT NULL,
    UNIQUE (user_id, currency)
);

-- Ledger: append-only; each row is a single debit or credit
CREATE TABLE ledger_entries (
    entry_id      UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    wallet_id     UUID        NOT NULL REFERENCES wallets(wallet_id),
    amount_paise  BIGINT      NOT NULL,    -- positive = credit, negative = debit
    balance_after BIGINT      NOT NULL,    -- running balance snapshot (denormalized for query speed)
    entry_type    TEXT        NOT NULL,    -- 'CREDIT' | 'DEBIT'
    reference_id  UUID        NOT NULL,    -- idempotency: payment_id, refund_id, etc.
    reference_type TEXT       NOT NULL,    -- 'PAYMENT' | 'REFUND' | 'TRANSFER'
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_ledger_wallet_created ON ledger_entries (wallet_id, created_at DESC);
CREATE UNIQUE INDEX idx_ledger_reference ON ledger_entries (reference_id, reference_type, entry_type);
```

**Balance derivation:**
```sql
-- Authoritative balance (sum of all entries — slow but always correct)
SELECT SUM(amount_paise) FROM ledger_entries WHERE wallet_id = $1;

-- Fast balance (last entry's balance_after — requires the ledger is append-only)
SELECT balance_after FROM ledger_entries
WHERE wallet_id = $1 ORDER BY created_at DESC LIMIT 1;
```

**Debit with balance check (pessimistic lock):**
```sql
BEGIN;
  SELECT balance_after
  FROM ledger_entries
  WHERE wallet_id = $1
  ORDER BY created_at DESC
  LIMIT 1
  FOR UPDATE;  -- row-level lock prevents concurrent debits

  -- application checks: balance_after >= debit_amount
  -- if not: ROLLBACK and raise InsufficientFundsException

  INSERT INTO ledger_entries (wallet_id, amount_paise, balance_after, entry_type, reference_id, reference_type)
  VALUES ($1, -$debit_amount, $new_balance, 'DEBIT', $payment_id, 'PAYMENT');
COMMIT;
```

**The `UNIQUE` index on `(reference_id, reference_type, entry_type)`** is the last-line-of-defense idempotency guard — a duplicate ledger entry for the same payment fails at the DB constraint level, not just at the application layer.

**Q20. "Your daily reconciliation report shows a ₹237 discrepancy between your internal ledger and the payment gateway's settlement. How do you diagnose and fix it?"**

A: A reconciliation discrepancy is almost always one of: a rounding difference, a currency mismatch, an unprocessed webhook, or a timing difference. Structured diagnosis:

**Phase 1 — Classify the discrepancy**

```sql
-- Find payments where your amount differs from the gateway's settled amount
SELECT
    p.payment_id,
    p.amount_paise          AS internal_amount,
    g.settled_amount_paise  AS gateway_amount,
    p.amount_paise - g.settled_amount_paise AS diff_paise
FROM payments p
JOIN gateway_settlements g USING (gateway_order_id)
WHERE p.amount_paise != g.settled_amount_paise
  AND p.created_at >= now() - interval '1 day';
```

**Phase 2 — Identify root causes by pattern**

| Pattern | Likely cause | Fix |
|---|---|---|
| Every diff is ±1 paise | Rounding mode mismatch | Align rounding mode with gateway's documented mode |
| All diffs are multiples of 100 | Paise/rupee unit confusion at one boundary | Audit conversion points; add unit tests |
| Diff only on FX payments | FX rate precision mismatch | Store 8 decimal places for rates; check which rate the gateway applies |
| A small number of payments with large diffs | Missing webhook / unprocessed status update | Check `payments` table for stuck `PENDING` payments; replay webhooks |
| Diff exactly equals service fee | Fee not being deducted from the correct side | Audit fee calculation logic; verify gateway fee pass-through setting |

**Phase 3 — Prevent recurrence**

- Run reconciliation not once daily but after every settlement batch (typically every 30 minutes from the gateway).
- Add a metric: `recon_diff_paise` — alert if non-zero.
- Add a DB constraint: a `CHECK` that `amount_paise > 0` and `amount_paise < 10000000000` (₹1 crore) — catches absurd values from unit bugs at write time, not discovery time.
- Write a property test: for any valid amount in rupees, `fromSmallestUnit(toSmallestUnit(amount, 'INR'), 'INR') === amount`. This catches round-trip errors in conversion functions.

**Q21. "A new engineer on your team opens a PR that computes loan EMI like this: `const emi = (principal * rate) / months`. What's wrong and how do you fix it?"**

A: Multiple issues:

**Issue 1 — `principal` and `emi` are likely floats**

If `principal` is `50000.00` (a JavaScript `number`) and `rate` is `0.01`, the multiplication is a float operation. The result may be `499.99999...` instead of `500`, and after further arithmetic, a sub-paise error is stored in the DB.

**Issue 2 — No rounding mode defined**

EMI calculation divides an integer by `months` — this almost always produces a non-integer result. The code has no explicit rounding, so JavaScript's implicit float truncation applies. One paise can be lost or gained per EMI installment; over 36 months that is ₹0.36 of unreconciled money per loan.

**Issue 3 — No total verification**

`emi * months` likely does not equal the original principal + interest due to accumulated rounding. The sum of all EMIs must exactly equal the total repayment amount.

**Correct implementation:**

```typescript
import Decimal from 'decimal.js';

interface EMISchedule {
  monthlyEMI:    bigint;   // paise — most installments
  lastEMI:       bigint;   // paise — absorbs the rounding remainder
  totalRepayable: bigint;  // paise — must equal sum of all EMIs
}

function calculateEMI(
  principalPaise: bigint,
  annualRatePercent: string,  // e.g., "12.5" — string to avoid float
  months: number,
): EMISchedule {
  const P = new Decimal(principalPaise.toString());
  const r = new Decimal(annualRatePercent).div(100).div(12);  // monthly rate
  const n = new Decimal(months);

  // Standard reducing-balance EMI formula: P * r * (1+r)^n / ((1+r)^n - 1)
  const onePlusR = r.add(1);
  const onePlusRPowN = onePlusR.pow(n);
  const emiDecimal = P.mul(r).mul(onePlusRPowN)
                      .div(onePlusRPowN.sub(1))
                      .toDecimalPlaces(0, Decimal.ROUND_HALF_UP);

  const regularEMI   = BigInt(emiDecimal.toFixed(0));
  const totalRegular = regularEMI * BigInt(months - 1);

  // Last EMI absorbs all rounding remainder
  const totalRepayable = BigInt(
    P.mul(r.add(1).pow(n)).toDecimalPlaces(0, Decimal.ROUND_HALF_UP).toFixed(0)
  );
  const lastEMI = totalRepayable - totalRegular;

  // Invariant: sum of all EMIs === totalRepayable
  console.assert(
    totalRegular + lastEMI === totalRepayable,
    'EMI schedule does not sum to total repayable'
  );

  return { monthlyEMI: regularEMI, lastEMI, totalRepayable };
}
```

The last EMI absorbs the rounding remainder — a common industry convention. This ensures `sum(all_EMIs) === totalRepayable` exactly, making the loan account reconcilable at close.

## Quick Reference Table

| Rule | Wrong | Right |
|---|---|---|
| **Storage type** | `FLOAT`, `DOUBLE`, `DECIMAL(10,2)` | `BIGINT` (paise/cents), `NUMERIC(19,0)` |
| **Input parsing** | `parseFloat("199.99") * 100` | `new Decimal("199.99").mul(100)` → `BigInt` |
| **Tax calculation** | `amount * 0.18` | `new Decimal(amountPaise).mul("0.18").toDecimalPlaces(0, ROUND_HALF_UP)` |
| **Splitting** | `total / n` (float division) | Integer quotient + largest-remainder for the diff |
| **FX rate storage** | `FLOAT` or `DOUBLE` | `NUMERIC(18, 8)` in DB; `string` in code → `Decimal` |
| **API input type** | `amount: number` (JSON number) | `amount: string` or `amountPaise: integer` |
| **API output type** | `"amount": 199.99` (JSON float) | `"amount": 19999` (integer) or `"amount": "199.99"` (string) |
| **Display** | `(paise / 100).toFixed(2)` | `BigInt` arithmetic for major/minor split; `Intl.NumberFormat` for locale |
| **Rounding** | `Math.round()`, `.toFixed()` | `decimal.js` with explicit `ROUND_HALF_UP` or `ROUND_HALF_EVEN` |
| **DB sum** | `SUM(amount_float)` | `SUM(amount_paise)` → treat result as `NUMERIC` / `Decimal`, not `number` |
| **Naming** | `amount`, `price`, `total` | `amount_paise`, `price_cents`, `total_smallest_unit` |

**Tip for the interview:** At the 5 YOE level in fintech, currency handling questions surface in three ways: (1) "show me your payment schema" — the interviewer is checking for `BIGINT` vs `DECIMAL` vs `FLOAT`; a `FLOAT` column ends the conversation early; (2) "debug this reconciliation discrepancy" — the answer almost always traces to a float somewhere in the pipeline; and (3) a code review of EMI / split / tax logic — they want to see you immediately flag `*`, `/`, and `parseFloat` on monetary values and propose `decimal.js` or integer arithmetic. Have the `0.1 + 0.2` example ready to explain why floats are fundamentally wrong — not just imprecise, but specified to behave the way they do. And always anchor the technical rule to the business consequence: a float in a payment system is not a style issue, it is a reconciliation failure waiting to happen.
