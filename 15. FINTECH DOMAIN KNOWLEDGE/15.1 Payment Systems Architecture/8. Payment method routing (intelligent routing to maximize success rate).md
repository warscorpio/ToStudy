# Payment Method Routing: Intelligent Routing to Maximize Success Rate — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is payment routing, and why does it matter beyond simply "sending a payment to a processor"?**
A: Payment routing is the decision engine that determines *which processor, acquirer, or payment rail* handles a given transaction. In a single-processor setup, there is no routing decision — every transaction goes to Stripe, or Adyen, or Braintree. Routing becomes a discipline the moment you have more than one option, which happens earlier than most engineers expect:

- A merchant adding a backup processor for redundancy.
- A global business that needs different acquirers in different regions.
- A platform that wants to route high-value transactions to a processor with lower interchange.
- A subscription business routing retries to a secondary processor after a primary failure.

The reason it matters: **authorization rate is revenue**. A 1% improvement in auth rate on a $1B GMV platform is $10M in recovered revenue. Routing is one of the highest-leverage levers in payment systems optimization — more impactful, dollar-for-dollar, than most product features.

Routing decisions affect five outcomes simultaneously:
- **Authorization rate** — does the issuer approve the charge?
- **Transaction cost** — interchange, processor fees, network fees.
- **Latency** — how quickly does the authorization response return?
- **Reliability** — what happens if the chosen processor is degraded?
- **Compliance** — is the transaction routed through a compliant entity for the cardholder's jurisdiction?

**Q2. What is the difference between processor routing, network routing, and payment method routing?**
A: These operate at different layers of the payment stack:

- **Network routing** (card scheme level) — choosing between Visa and Mastercard rails when a dual-network card (common with debit cards in the US) allows it. Example: a US debit card can route through Visa *or* the STAR/NYCE/Pulse network. Merchants choose based on interchange cost (debit network interchange is often lower). Regulated by the Durbin Amendment (US) — merchants *must* have the option to route to at least two unaffiliated networks.

- **Processor / acquirer routing** — choosing which processor or acquiring bank handles the transaction once the network is decided. Example: route European cards through Adyen's European acquiring entity, US cards through Stripe. This is the most common layer where intelligent routing logic lives.

- **Payment method routing** — choosing *which payment method* to present or prioritize for a given customer. Example: showing SEPA Direct Debit (low cost, high success in Germany) instead of card for a German customer, or routing a B2B buyer to ACH instead of card to avoid interchange. Sits at the UX and product layer, not purely infrastructure.

At the 5 YOE level, interviewers primarily care about **processor routing** — the infrastructure decision engine — with some coverage of payment method selection strategy.

**Q3. What signals determine whether a routing decision is "intelligent"?**
A: Naïve routing uses a single static rule ("always use Stripe"). Intelligent routing incorporates real-time and historical signals across multiple dimensions:

| Signal Category | Examples | Latency |
|--|--|--|
| **Card attributes** | BIN country, card type (credit/debit/prepaid), card network (Visa/MC/Amex), issuer | Per-request (BIN lookup) |
| **Transaction attributes** | Amount, currency, MCC (merchant category code), 3DS status | Per-request |
| **Customer attributes** | Repeat customer vs. new, historical success rate on this card, account age | Per-request (cache) |
| **Processor real-time health** | Auth rate in last 5 min, P99 latency, error rate | Real-time (streamed) |
| **Processor historical performance** | Auth rate by BIN range over last 30 days | Batch-updated (hourly) |
| **Cost signals** | Interchange rate for this card + processor, per-transaction fees | Config (updated daily) |
| **Compliance signals** | Cardholder country, data residency requirements, local acquiring mandate | Config |

"Intelligent" means the routing engine consults *multiple* of these signals simultaneously and has a principled way to resolve conflicts between them (e.g., the cheapest processor has the lowest auth rate for this BIN).

## Section 2: Routing Strategies

**Q4. What are the primary routing strategies, from simplest to most sophisticated?**
A: A spectrum from static to ML-driven:

**1. Static / Priority Routing**
A fixed ordered list of processors. All transactions go to Processor A; if A fails, fall back to B.
- Pros: simple to implement, easy to reason about, no data dependency.
- Cons: ignores all signal; Processor A may have a lower auth rate for European cards than B, but you'll never discover it.
- When appropriate: early-stage companies, single-region merchants, when data volume is insufficient to train a model.

**2. Rule-Based Routing**
An explicit decision tree: IF card_country == 'DE' AND amount < 100 THEN use Adyen ELSE use Stripe.
- Pros: deterministic, auditable, no ML required, fast to iterate.
- Cons: rules proliferate and conflict; maintaining 200 rules is an engineering burden; rules cannot capture subtle multi-dimensional patterns.
- Implementation: a rule engine (Drools, custom DSL, feature flags) evaluated in priority order. Requires a conflict resolution strategy when multiple rules match.

**3. Cost-Optimized Routing**
Route each transaction to the processor with the lowest effective cost (interchange + processor fee + network fee) for that card type and amount.
- Pros: directly reduces payment processing costs; relatively straightforward to implement with a cost matrix.
- Cons: ignores auth rate. A processor that saves $0.05/transaction but has a 2% lower auth rate costs far more than it saves on high-volume flows.
- When appropriate: when auth rates are roughly equal across processors (common for mature, low-fraud verticals).

**4. Auth-Rate-Optimized Routing**
Route to the processor with the highest historical authorization rate for the specific BIN range, card type, and currency combination.
- Pros: directly maximizes revenue.
- Cons: requires significant data (need enough volume per BIN × processor combination to get statistically valid auth rate estimates); cold-start problem for new processors.
- Implementation: maintain a `routing_stats` table keyed on `(bin_prefix, processor_id, currency, card_type)` with rolling auth rate; use a minimum sample size threshold before trusting the estimate.

**5. Multi-objective / Weighted Routing**
Combine auth rate, cost, and latency into a scoring function. Route to the processor with the highest score.
```
score = w1 * auth_rate + w2 * (1 - normalized_cost) + w3 * (1 - normalized_latency)
```
- Pros: balances competing objectives explicitly.
- Cons: weight tuning requires business judgment and ongoing calibration; a miscalibrated weight causes unexpected cost spikes or auth rate drops.

**6. ML-Based Routing**
A trained model predicts the probability of authorization per processor for a given transaction feature vector, and routes to the highest-probability processor.
- Pros: captures non-linear interactions between features (e.g., "Adyen has higher auth rates for Amex cards over €500 from French issuers, but only on weekdays") that rule systems cannot express.
- Cons: requires large training data (millions of transactions); model drift requires retraining; harder to debug a failure ("why did the model route this to Stripe?"); requires MLOps infrastructure.
- When appropriate: platforms processing >$100M GMV/year with sufficient BIN-level data density.

**Q5. What is BIN-based routing, and how do you build a BIN lookup system?**
A: BIN (Bank Identification Number) — now formally called IIN (Issuer Identification Number) — is the first 6–8 digits of a card number. It identifies the issuing bank, card network, card type (credit/debit/prepaid/corporate), and country of issuance. BIN-based routing uses these attributes to make routing decisions without knowing anything else about the transaction.

**Why BINs matter for routing:**
- Different issuers have different relationships with different acquirers. A UK Barclays card may authorize at a higher rate through a UK-based acquirer than a US-based one (local acquiring advantage).
- Card type determines interchange: debit cards processed through Visa have different interchange than through Mastercard or a PIN debit network.
- Corporate cards (identified by BIN) often fail on consumer merchant category codes — routing them to a processor with better corporate card support improves auth rate.

**Building a BIN lookup system:**

```
Data sources:
- BIN databases: Binlist.net (free, limited), CDRN/Mastercard MATCH (paid), Visa BIN API (for Visa partners)
- Your own transaction history: enrich BIN records from issuer responses in authorization data

Schema:
bin_records (
  bin_prefix    VARCHAR(8) PRIMARY KEY,   -- first 6 or 8 digits
  card_network  VARCHAR(16),              -- visa, mastercard, amex, discover
  card_type     VARCHAR(16),              -- credit, debit, prepaid, corporate
  issuer_name   VARCHAR(128),
  issuer_country CHAR(2),                 -- ISO 3166
  issuer_region VARCHAR(32),
  updated_at    TIMESTAMPTZ
)
```

**Lookup performance:**
- BIN lookup must be sub-millisecond — it's in the critical path of every authorization.
- Cache the full BIN table in Redis (< 2MB for 6-digit BINs, ~20MB for 8-digit). Refresh nightly.
- For 8-digit BINs (the industry is migrating to 8-digit): use a prefix trie or range lookup, since BIN ranges are not contiguous.

**Q6. What is local acquiring, and why does it improve authorization rates?**
A: Local acquiring means the merchant's acquiring bank is in the *same country* as the cardholder's issuing bank. Example: a German cardholder at a German issuer, processed through a German acquirer vs. a US acquirer.

**Why it matters:**
- **Reduced cross-border decline rates**: issuers flag cross-border transactions as higher fraud risk. A German issuer seeing a charge from a German acquirer (same country) treats it as domestic — lower fraud score, higher auth probability.
- **Interchange savings**: domestic interchange rates are typically lower than cross-border rates (20–50bps difference).
- **Regulatory compliance**: some countries require local data processing for certain transaction types (Russia's Federal Law 152-FZ, India's RBI data localization requirements).

**Routing implication:**
Your routing engine must know the cardholder's country (from BIN) and select an acquirer with a local entity in that country. This requires a `processor_capabilities` table:

```
processor_acquiring_regions (
  processor_id   VARCHAR(32),
  country_code   CHAR(2),
  is_local       BOOLEAN,
  currency       CHAR(3),
  supported_card_types VARCHAR[]
)
```

For a German cardholder: `SELECT processor_id FROM processor_acquiring_regions WHERE country_code = 'DE' AND is_local = TRUE ORDER BY auth_rate DESC`.

Processors with strong local acquiring networks: Adyen (broadest global coverage), Worldpay, Checkout.com. Stripe has expanded but still uses cross-border acquiring in some markets.

## Section 3: Auth Rate Optimization In Depth

**Q7. How do you measure authorization rate accurately, and what are the common measurement mistakes?**
A: Auth rate = (successful authorizations) / (total authorization attempts). Simple in definition, subtle in measurement.

**Common mistakes:**

1. **Including retries in the denominator** — if a declined transaction is retried 3 times, counting it as 4 attempts makes your auth rate look worse than it is. Measure *first-attempt auth rate* as the primary metric; retry-inclusive rate as a secondary operational metric.

2. **Not segmenting by card type** — a single blended auth rate hides that your prepaid card auth rate is 40% while your credit card rate is 92%. Segment by: `(card_type, card_network, issuer_country, currency, amount_bucket)`.

3. **Not accounting for intentional declines** — your own fraud model declining a transaction before it reaches the processor is not an issuer decline. Exclude risk-engine blocks from the auth rate denominator, or report them separately as `risk_decline_rate`.

4. **Short measurement windows** — auth rate fluctuates by time of day, day of week, and seasonality. A 5-minute window is too noisy; a 30-day window is too stale to catch processor degradation. Use a 24-hour rolling window for health monitoring, 7-day for routing decisions.

5. **Survivorship bias in routing** — if your routing engine sends all "risky" transactions to Processor A, A's measured auth rate will be lower than B's — not because B is better, but because it gets the easy transactions. Control for this by periodically sending a random sample of transactions to all processors ("exploration" in the explore/exploit framework).

**Q8. What is the explore/exploit tradeoff in routing, and how do you implement it?**
A: This is a classic multi-armed bandit problem applied to payment routing. The exploitation side: route to the processor with the highest known auth rate for this transaction type. The exploration side: occasionally route to other processors to keep your auth rate estimates fresh and discover if a processor has improved.

**Why exploration is non-negotiable:**
Without it, your routing model never learns that Processor B improved its auth rates after upgrading infrastructure, or that Processor A degraded after a configuration change. The model becomes stale, and your routing decisions are based on outdated statistics.

**Implementation: ε-greedy routing**
```python
def route_transaction(transaction):
    best_processor = argmax(auth_rate_estimates, transaction.features)
    
    if random() < EPSILON:                   # exploration branch
        # Choose a random processor (weighted by minimum volume requirements)
        return random_processor(eligible_processors)
    else:                                    # exploitation branch
        return best_processor
```
- `EPSILON = 0.05–0.10` (5–10% exploration rate) is typical. Higher epsilon = faster learning, lower average auth rate. Lower = slower learning but better short-term performance.
- Route exploration traffic proportionally across all eligible processors, not uniformly — a processor with 1% market share shouldn't get 33% of exploration traffic if you have 3 processors.

**More sophisticated approaches:**
- **Thompson Sampling** — maintain a Beta distribution over each processor's auth rate; sample from distributions and pick the highest sample. Naturally balances explore/exploit and handles uncertainty correctly.
- **Upper Confidence Bound (UCB)** — explicitly penalize processors with high uncertainty (low sample count) less than processors with low uncertainty, so new processors get explored more.

**Q9. How does 3DS (3D Secure) interact with routing decisions?**
A: 3DS is an authentication protocol (Verified by Visa, Mastercard Identity Check) that shifts fraud liability from the merchant to the issuing bank when the cardholder authenticates. Its interaction with routing is bidirectional:

**3DS status affects routing:**
- A transaction that has passed 3DS authentication carries a lower fraud risk signal — some processors offer better auth rates or lower fees for 3DS-authenticated transactions.
- Route 3DS-authenticated transactions preferentially to processors that recognize 3DS and apply the liability shift — not all processors handle 3DS equally.
- Frictionless 3DS (risk-based authentication, no customer challenge) has different processor support than challenge 3DS. Route accordingly.

**Routing affects 3DS decision:**
- Some processors have better issuer relationships for triggering frictionless 3DS flow (no customer challenge), which improves conversion.
- 3DS is required (or strongly recommended) for European transactions under PSD2 SCA (Strong Customer Authentication). Routing European cards to a processor with a 3DS2-compliant integration is a compliance requirement.

**Routing + 3DS decision tree:**
```
Is the transaction in a PSD2-regulated region?
  YES → Must use SCA-compliant processor with 3DS2 support
  NO  → Is amount above soft-decline risk threshold?
          YES → Consider triggering 3DS to improve auth rate
          NO  → Route without 3DS for lower friction
```

## Section 4: Cost Optimization In Depth

**Q10. How do interchange fees work, and how does routing influence them?**
A: Interchange is the fee paid by the merchant's acquiring bank to the cardholder's issuing bank on every transaction. It is set by the card networks (Visa, Mastercard) and varies by: card type, merchant category code (MCC), transaction entry mode (card present vs. card not present), and geography.

**Interchange tiers (US examples, approximate):**
| Card Type | Interchange Rate |
|--|--|
| Consumer credit (CNP) | 1.65% + $0.10 |
| Consumer debit (CNP, regulated) | 0.05% + $0.21 (Durbin cap) |
| Consumer debit (CNP, unregulated) | 0.80% + $0.15 |
| Corporate/business credit | 2.20% + $0.10 |
| Rewards credit (CNP) | 1.95% + $0.10 |
| Prepaid | 1.15% + $0.15 |

**How routing influences interchange:**

1. **Debit network routing (Durbin Amendment)** — for US debit cards, routing through a PIN debit network (STAR, Pulse, NYCE) instead of Visa/Mastercard gives access to regulated interchange ($0.21 + 0.05% cap). For a $100 debit transaction: Visa interchange ≈ $0.95; PIN debit interchange ≈ $0.26. The merchant saves $0.69 per transaction — material at scale.

2. **Card type detection** — accurately identifying whether a card is regulated debit, unregulated debit, or credit (via BIN lookup) allows routing to the optimal network. Misclassifying a regulated debit card as credit and routing to Visa costs $0.69 per transaction unnecessarily.

3. **Level 2 / Level 3 data** — for B2B transactions (corporate cards), submitting additional data fields (purchase order number, line-item detail) qualifies for lower interchange rates. Some processors support L2/L3 data; routing B2B transactions to those processors and submitting the enriched data reduces interchange by 40–100bps.

**Q11. How do processor fees differ, and how do you build a cost model for routing decisions?**
A: Processor fees layer on top of interchange. Structures vary:

- **Interchange-plus (cost-plus)** — merchant pays actual interchange + a fixed markup (e.g., interchange + 0.20% + $0.10). Transparent; favorable for large merchants who negotiate low markups.
- **Flat rate** — one rate regardless of card type (e.g., Stripe's 2.9% + $0.30). Simple; favorable for small merchants; expensive for merchants with high debit or low-value transactions.
- **Blended / tiered** — processor groups cards into tiers (qualified, mid-qualified, non-qualified) and charges different rates per tier. Opaque; hard to optimize routing against.

**Building a cost model:**
```python
def effective_cost(transaction, processor):
    bin_info = lookup_bin(transaction.card_bin)
    interchange = get_interchange_rate(
        card_type=bin_info.card_type,
        card_network=bin_info.network,
        mcc=transaction.mcc,
        entry_mode='CNP',
        region=bin_info.issuer_country
    )
    processor_markup = get_processor_rate(processor, transaction.amount, bin_info.card_type)
    network_fee = get_network_fee(bin_info.network, transaction.amount)
    
    return interchange + processor_markup + network_fee
```

**Routing decision with cost:**
```python
def route_by_cost_and_auth_rate(transaction):
    candidates = get_eligible_processors(transaction)
    
    scored = []
    for p in candidates:
        cost = effective_cost(transaction, p)
        auth_rate = get_auth_rate_estimate(transaction, p)
        # Expected net revenue = (1 - cost_rate) * amount * auth_rate
        expected_value = (transaction.amount - cost) * auth_rate
        scored.append((p, expected_value))
    
    return max(scored, key=lambda x: x[1])[0]
```
This converts the multi-objective problem (minimize cost, maximize auth rate) into a single expected-value maximization.

## Section 5: Reliability & Failover Routing

**Q12. How do you detect processor degradation in real time and reroute traffic?**
A: A processor health monitor runs continuously alongside the routing engine. It must distinguish between:

- **Processor outage** — processor is returning 5xx errors or timing out; reroute all traffic immediately.
- **Auth rate degradation** — processor is healthy (returning 2xx) but auth rates have dropped (issuer relationship issue, network problem); reroute specific card types or BIN ranges.
- **Latency degradation** — processor response times have increased; reroute latency-sensitive flows.

**Architecture:**

```
Transaction Stream
      │
      ▼
┌─────────────────┐       ┌──────────────────────┐
│  Routing Engine  │◄──────│ Processor Health Feed │
└────────┬────────┘       └──────────┬───────────┘
         │                           │
         │               ┌───────────▼──────────┐
         │               │  Health Aggregator    │
         │               │  - Auth rate (5min)   │
         │               │  - Error rate (1min)  │
         │               │  - P99 latency (1min) │
         │               │  - Sample size check  │
         │               └──────────────────────┘
         │
    Route to healthy processor
```

**Health signal computation:**
```python
class ProcessorHealthMonitor:
    def is_degraded(self, processor_id, segment=None):
        window = self.get_window(processor_id, segment, minutes=5)
        
        if window.total_attempts < MIN_SAMPLE_SIZE:
            return False  # insufficient data; don't falsely flag
        
        if window.error_rate > ERROR_RATE_THRESHOLD:        # e.g., > 5%
            return True
        if window.auth_rate < BASELINE_AUTH_RATE * 0.95:   # > 5% drop from baseline
            return True
        if window.p99_latency > LATENCY_SLA_MS:            # e.g., > 3000ms
            return True
        
        return False
```

**Rerouting triggers:**
- Error rate > 5% in 1-minute window → immediate failover to secondary processor.
- Auth rate drops > 5% below 7-day rolling baseline in 5-minute window → segment-level reroute (e.g., stop routing UK cards to this processor).
- P99 latency > 3s in 1-minute window → reroute latency-sensitive flows; keep low-value async flows.

**Q13. What is the split-traffic / canary pattern in payment routing, and when do you use it?**
A: Split-traffic routing sends a percentage of transactions to a new processor (or new configuration) while keeping the majority on the proven path. It is analogous to a canary deployment, but for payment infrastructure.

**Use cases:**
- **Onboarding a new processor** — start with 1–5% of traffic, measure auth rate and latency, scale up if metrics are favorable.
- **Migrating from one processor to another** — gradually shift traffic from old to new over days/weeks, reversing immediately if degradation is detected.
- **A/B testing routing algorithms** — compare ML-based routing vs. rule-based on a live traffic split.
- **Regional expansion** — route 5% of transactions from a new country to a local acquirer before committing fully.

**Implementation:**
```python
def split_route(transaction, splits):
    # splits = [('stripe', 0.90), ('adyen', 0.10)]
    r = random()
    cumulative = 0
    for processor, weight in splits:
        cumulative += weight
        if r < cumulative:
            return processor
    return splits[-1][0]  # fallback
```

**Measurement discipline:**
- Tag every transaction with `routing_experiment_id` and `routing_variant` in your `payment_attempts` table.
- Use a holdout group (fully random sample) as a control — never compare experiment variants against historical baselines, only against the concurrent holdout.
- Statistical significance before declaring a winner: minimum 10,000 transactions per variant, p-value < 0.05 on auth rate difference.

## Section 6: Advanced Routing Patterns

**Q14. What is cascade routing, and how does it differ from primary/backup failover?**
A: Both involve multiple processors, but the trigger and design philosophy differ:

- **Primary/backup failover** — the secondary processor activates only when the primary is *down* or returns a system-level error. Under normal operation, 100% of traffic goes to the primary. Binary switch.

- **Cascade routing** — the transaction is attempted on the first processor; if it declines (for any reason — issuer decline, not just system failure), it is automatically retried on a second processor. The cascade is a *per-transaction* retry across processors, not a *per-processor-health* switch.

**When cascade routing recovers revenue:**
A card declined by Processor A may succeed on Processor B because:
- Different acquirer BIN → different issuer relationship → different fraud scoring.
- Processor A used a weak authentication signal; Processor B triggers 3DS, which the issuer accepts.
- Processor A's MCC mapping is slightly off for this merchant type; Processor B has a corrected mapping.

**Real-world authorization rate improvement from cascade:** typically 2–8% recovery rate on soft-declined transactions, depending on the card mix and processor diversity.

**Cascade routing constraints:**
- Only cascade on soft declines — never on hard declines (code `05`, `41`, `43`, `54`). The issuer's decision won't change based on which processor submits the request.
- Use the *same* idempotency key scoped to `(order_id, processor_id)` — a cascade to Processor B is a new charge attempt, not a retry of the Processor A attempt.
- Visa/Mastercard retry rules apply per card per 30 days across all processors — cascade attempts count toward the network limit.
- Latency cost: a cascade adds the latency of a second authorization round trip (typically 200–800ms). Acceptable for high-value transactions; may not be acceptable for in-person retail.

**Q15. How does payment method routing differ from processor routing, and what factors drive method selection?**
A: Payment method routing is the upstream decision: *which payment instrument* to offer or prioritize, before processor routing kicks in. This operates at the product/UX layer.

**Payment method taxonomy by region:**

| Region | Popular Methods | Typical Cost | Auth Rate |
|--|--|--|--|
| US | Card (Visa/MC), ACH, Buy Now Pay Later | Card: 1.5–3%; ACH: $0.20–$1.50 flat | Card: 85–95%; ACH: 92–98% |
| EU | Card, SEPA Direct Debit, iDEAL (NL), Sofort/Klarna | SEPA: €0.20–€0.35 flat | SEPA: 94–99% |
| UK | Card, Bacs Direct Debit, Open Banking | Bacs: £0.20 flat | Bacs: 95%+ |
| India | UPI, Card, Netbanking, Wallets | UPI: 0% (regulated) | UPI: 85–95% |
| LATAM | Card, Boleto (BR), OXXO (MX), PSE (CO) | Local methods: 1–2.5% | Varies widely |
| SEA | Card, GoPay, OVO, GrabPay, PromptPay | Wallets: 1–2% | 80–90% |

**Routing decision factors:**

1. **Customer geography** (from BIN country or billing address) → determines which methods are available and relevant.
2. **Transaction size** — for large B2B amounts (>$10K), ACH/SEPA is strongly preferred over card (lower cost, no interchange).
3. **Recurring vs. one-time** — recurring subscriptions prefer direct debit methods (ACH, SEPA, Bacs) for cost and stability. Card numbers expire; bank accounts don't.
4. **Customer segment** — consumer vs. business affects which methods they trust and use.
5. **Cost optimization** — local payment methods are almost always cheaper than international cards. A German SEPA payment costs €0.25; a Visa credit card costs 1.5–2%.
6. **Conversion optimization** — some methods have higher completion rates in specific markets. iDEAL has near-100% market penetration in the Netherlands; offering it first improves conversion for Dutch customers.

**Smart method ordering:**
```python
def rank_payment_methods(customer, transaction):
    available = get_available_methods(customer.country, transaction.currency)
    
    scored = []
    for method in available:
        score = (
            METHOD_SUCCESS_RATE[method] * 0.40 +
            (1 - normalized_cost(method, transaction)) * 0.35 +
            CUSTOMER_PREFERENCE_WEIGHT[method] * 0.25
        )
        scored.append((method, score))
    
    return sorted(scored, key=lambda x: -x[1])
```

**Q16. How does intelligent routing interact with tokenization and network tokens?**
A: Network tokens (Visa Token Service, Mastercard MDES) replace the physical PAN with a processor-specific token that is tied to a merchant or processor domain. They interact with routing in important ways:

**Auth rate improvement from network tokens:**
- Network tokens carry a higher trust signal from the issuer — the token is cryptographically bound to the merchant, making it harder to misuse.
- Reported auth rate improvements with network tokens: 2–4% uplift on recurring transactions, up to 10% for some BIN ranges.
- Issuers automatically update tokens when cards are reissued (account updater) — reducing declines from expired or replaced cards.

**Routing constraint:**
- Network tokens are *processor-specific* (a Stripe token cannot be used with Adyen). This means you cannot freely route a network-tokenized transaction to any processor — you must route to the processor that holds the token.
- If you want multi-processor routing flexibility, you need either: (a) raw PAN processing (requires PCI DSS SAQ D / Level 1 compliance), (b) a token service provider (TSP) that maintains tokens across processors (e.g., Spreedly), or (c) obtaining network tokens from multiple processors for the same card.

**TSP (Token Service Provider) architecture:**
```
Customer Card (PAN)
      │
      ▼
┌─────────────┐      ┌─────────────┐
│     TSP      │─────►│  Processor A │
│ (Spreedly,  │      │  (Stripe)    │
│  Basis      │─────►│  Processor B │
│  Theory)    │      │  (Adyen)     │
└─────────────┘      └─────────────┘
```
The TSP stores the PAN once, provides a TSP token to your system, and translates to processor-specific tokens at routing time. This decouples tokenization from routing.

## Section 7: System Design Scenarios

**Q17. "Design an intelligent payment routing engine for a global e-commerce platform processing $5B GMV annually."**
A: At this scale, routing is a dedicated service, not a module inside the payment service.

**Service architecture:**

```
API Gateway
    │
    ▼
Payment Service
    │
    ├── RouteTransaction(ctx, txn) ──► Routing Engine Service
    │                                        │
    │                          ┌─────────────▼──────────────┐
    │                          │        Routing Engine        │
    │                          │                              │
    │                          │  1. BIN Lookup (Redis)       │
    │                          │  2. Eligibility Filter       │
    │                          │  3. Score Each Processor     │
    │                          │     - Auth rate model        │
    │                          │     - Cost model             │
```

**Data model for auth rate tracking:**
```sql
routing_stats (
  id                BIGSERIAL PRIMARY KEY,
  bin_prefix        VARCHAR(8) NOT NULL,
  processor_id      VARCHAR(32) NOT NULL,
  card_type         VARCHAR(16) NOT NULL,
  currency          CHAR(3) NOT NULL,
  amount_bucket     VARCHAR(16) NOT NULL,   -- '0-50', '50-200', '200+'
  card_country      CHAR(2) NOT NULL,
  hour_bucket       TIMESTAMPTZ NOT NULL,   -- truncated to hour
  attempts          INTEGER NOT NULL DEFAULT 0,
  authorizations    INTEGER NOT NULL DEFAULT 0,
  auth_rate         NUMERIC(5,4) GENERATED ALWAYS AS
                      (authorizations::numeric / NULLIF(attempts, 0)) STORED,
  UNIQUE (bin_prefix, processor_id, card_type, currency, amount_bucket, card_country, hour_bucket)
)
```

**Auth rate estimate with confidence:**
```python
def get_auth_rate_estimate(bin, processor, features, lookback_days=7):
    stats = query_stats(bin, processor, features, lookback_days)
    
    if stats.attempts < MIN_SAMPLE_THRESHOLD:   # e.g., 100 attempts
        # Fall back to broader segment (less granular BIN prefix, wider amount bucket)
        return get_auth_rate_estimate(bin[:6], processor, features.broaden(), lookback_days)
    
    # Wilson score confidence interval — returns lower bound
    return wilson_lower_bound(stats.authorizations, stats.attempts, confidence=0.95)
```

Using the Wilson lower bound for auth rate estimates ensures that low-sample-count processors are ranked conservatively — a processor with 2/2 successes (100%) ranks below one with 900/1000 (90% with high confidence).

**SLA requirements:**
- Routing decision: < 10ms P99 (in-memory computation, Redis lookups).
- BIN lookup: < 2ms P99 (Redis).
- Auth rate stats update: asynchronous, via event stream from transaction outcomes.
- Processor health update: < 30-second lag from transaction outcome to health signal.

**Q18. "How would you A/B test a new ML-based routing algorithm against your existing rule-based system?"**
A: This is a controlled experiment on live payment traffic, which requires more care than a standard web A/B test — the outcome (payment success or failure) has direct revenue consequences.

**Experimental design:**

```
Incoming transactions
        │
        ▼
┌───────────────────┐
│  Experiment       │
│  Assignment       │  ← Deterministic: hash(card_fingerprint + experiment_id) % 100
│  (10% treatment)  │
└───────┬───────────┘
        │
   ┌────┴────┐
   │          │
Control    Treatment
(rules)    (ML model)
   │          │
   └────┬─────┘
        │
   Record: transaction_id, variant, processor_chosen,
           auth_rate, cost, latency, amount
```

**Assignment:** use `card_fingerprint` (not `transaction_id`) as the hash key, so the same card always goes to the same variant. This prevents the same customer from experiencing both variants within the experiment window.

**Primary metric:** first-attempt authorization rate, segmented by `(card_type, card_country, amount_bucket)`. Don't use revenue — it conflates routing improvement with organic demand changes.

**Guardrail metrics (must not regress):**
- Transaction cost per dollar (if ML chases auth rate at the expense of cost).
- P99 routing latency (ML inference must not add latency beyond SLA).
- Processor concentration (ML must not send 95% of traffic to one processor, creating single-point-of-failure risk).

**Stopping rules:**
- Stop early for harm: if treatment auth rate drops > 2% below control for 2 consecutive hours → auto-revert to control.
- Stop early for success: if treatment shows > 1.5% auth rate improvement with p < 0.01 after minimum 50,000 transactions per variant.
- Run minimum 2 weeks to capture weekly seasonality patterns.

**Q19. "Your authorization rate dropped 3% overnight. Walk me through your diagnostic process."**
A: A 3% auth rate drop overnight is a significant revenue event. Systematic diagnosis:

**Step 1 — Segment the drop (first 15 minutes)**
```
Is it affecting all processors or one?
  → One processor → likely processor or acquirer issue.
  → All processors → likely card network, fraud pattern, or your code change.

Is it affecting all card types?
  → Only debit → check debit network routing or Durbin-related rule change.
  → Only credit → check interchange category or issuer fraud scoring.
  → Only specific BIN ranges → issuer-specific issue or BIN data change.

Is it affecting all geographies?
  → Only one country → local acquirer, regulatory change, or regional fraud spike.
  → Global → systemic.

Did you deploy anything in the last 24 hours?
  → Yes → correlate deployment time with drop time. Check routing rule changes,
    BIN table updates, processor SDK version bump.
```

**Step 2 — Check external signals (15–30 minutes)**
- Processor status pages (Stripe, Adyen status dashboards).
- Card network status (Visa, Mastercard operational status pages).
- Industry Slack channels / forums — are other merchants seeing the same?
- Your processor's merchant support Slack channel — ask directly.

**Step 3 — Analyze response code distribution**
```sql
SELECT response_code, classified_as, COUNT(*), COUNT(*) * 100.0 / SUM(COUNT(*)) OVER () AS pct
FROM payment_attempts
WHERE created_at > NOW() - INTERVAL '2 hours'
GROUP BY response_code, classified_as
ORDER BY COUNT(*) DESC;
```
Compare to the same window 24h and 7 days ago. A spike in `05 Do Not Honor` or `51 Insufficient Funds` has different implications than a spike in `91 Issuer Unavailable`.

**Step 4 — Check for routing changes**
```sql
SELECT processor_id, COUNT(*), auth_rate
FROM payment_attempts
WHERE created_at BETWEEN [drop_time - 1h] AND [drop_time + 1h]
GROUP BY processor_id;
```
If routing shifted traffic to a processor with historically lower auth rates (due to health monitor misfire, rule change, or experiment assignment), that explains the drop.

**Step 5 — Remediation**
- Processor issue confirmed → increase failover traffic to backup processor.
- BIN data changed → rollback BIN table update.
- Code deployment → rollback routing rule change.
- Issuer fraud pattern → contact processor's risk team; may require adjusting 3DS thresholds.
