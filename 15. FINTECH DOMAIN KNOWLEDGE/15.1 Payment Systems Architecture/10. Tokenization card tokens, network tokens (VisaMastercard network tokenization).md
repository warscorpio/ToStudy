# Payment Lifecycle: Tokenization — Card Tokens, Network Tokens & PCI Compliance — Interview Q&A (5 YOE Level)

> **Domain:** Fintech / Payment Systems Architecture

---

## Section 1: Fundamentals

**Q1. What is tokenization in the context of payments, and what problem does it solve?**

A: Payment tokenization is the process of replacing a sensitive card credential — the 16-digit Primary Account Number (PAN) — with a surrogate value called a **token**. The token is a non-sensitive identifier that can be stored, transmitted, and used in payment flows without exposing the underlying PAN.

The problem it solves has two dimensions:

- **Security:** A PAN is a static credential. Any system that stores a PAN becomes a high-value target — a breach exposes every card stored in that system permanently (the PAN doesn't change unless the customer gets a new card). A token, by contrast, is useless to an attacker outside the specific context it was issued for — it cannot be used at a different merchant, through a different channel, or decoded back to a PAN without calling the issuing vault or network.

- **Compliance scope reduction:** The Payment Card Industry Data Security Standard (PCI DSS) mandates strict controls on any system that stores, processes, or transmits PANs: network segmentation, encryption at rest, encryption in transit, quarterly vulnerability scans, annual audits. Tokenization moves PANs out of your system entirely, dramatically reducing PCI scope. Your database stores tokens, not PANs; your servers never see the raw PAN after the initial tokenization call.

Tokenization is distinct from encryption: an encrypted PAN is still a PAN — it can be decrypted with the right key. A token has no mathematical relationship to the PAN; there is no key that converts it back without the token vault's cooperation.

---

**Q2. What are the two categories of payment tokens, and how do they differ?**

A: The industry uses two distinct categories of tokens, solving different problems at different layers of the payment stack:

**Category 1 — Payment Service Provider (PSP) / Gateway Tokens:**
- Issued by a payment gateway (Razorpay, JusPay, Stripe, Braintree).
- Represent a PAN stored in that gateway's vault.
- Scoped to the issuing gateway: a Razorpay token cannot be used through Stripe.
- Used for: saving cards for recurring payments, one-click checkout, subscription billing.
- Example: Razorpay's `token_id`, JusPay's `card_token`.

**Category 2 — Network Tokens:**
- Issued by the card network itself (Visa Token Service / VTS, Mastercard Digital Enablement Service / MDES).
- Represent a PAN at the network level, independent of any specific gateway.
- Portable across acquirers and processors that support the network.
- Include a **cryptogram** (a one-time, transaction-specific value) that proves the token is being used by an authorized party.
- Used for: device-based payments (Apple Pay, Google Pay), card-on-file at large merchants, RBI's mandate on recurring payments.
- Example: A 16-digit DPAN (Device PAN) that looks like a card number but routes through the network's token service.

The key distinction: PSP tokens are a merchant-gateway relationship; network tokens are a cardholder-network relationship. Network tokens are more secure (they include cryptograms), more portable, and have higher authorization rates because issuers trust them more.

---

**Q3. What is a PAN, and what makes it sensitive enough to require tokenization?**

A: The **Primary Account Number** is the 14–19 digit number embossed on a payment card, governed by ISO/IEC 7812. Its structure:

```
4532 1234 5678 9010
│    │              └─ Check digit (Luhn algorithm)
│    └──────────────── Individual account identifier (varies by issuer)
└───────────────────── Issuer Identification Number (IIN / BIN) — first 6 digits
```

What makes the PAN sensitive:

1. **Static credential:** Unlike a password, a PAN cannot be reset by the customer on demand — it is tied to the physical card and changes only when the card expires or is replaced.
2. **Universally recognizable:** Any acquiring bank, any payment processor worldwide that accepts Visa/Mastercard can initiate a transaction with a PAN + expiry + CVV. It is a globally accepted credential.
3. **Partially guessable:** The BIN (first 6 digits) is semi-public; the check digit is deterministic (Luhn). An attacker who obtains a partial PAN can reduce the search space significantly.
4. **PCI DSS classifies it as CHD (Cardholder Data):** Storing PANs triggers the full PCI DSS compliance framework — 12 requirements covering network security, access control, cryptography, monitoring, and annual audits. The cost of PCI compliance for a Level 1 merchant (>6M transactions/year) can exceed $1M/year.

---

**Q4. What is PCI DSS, and how does tokenization reduce compliance scope?**

A: **PCI DSS (Payment Card Industry Data Security Standard)** is a set of security requirements established by the PCI Security Standards Council (founded by Visa, Mastercard, Amex, Discover, JCB) that applies to any entity that stores, processes, or transmits cardholder data. There are four merchant levels based on transaction volume, each with different audit requirements.

**Key requirements most relevant to tokenization:**

- Requirement 3: Protect stored cardholder data (encrypt PANs at rest, never store CVV after authorization).
- Requirement 4: Encrypt transmission of cardholder data across open networks.
- Requirement 7: Restrict access to cardholder data by business need to know.
- Requirement 9: Restrict physical access to cardholder data.

**How tokenization reduces scope:**

Without tokenization, your entire backend — the API server, the database, the analytics pipeline, the data warehouse, the logging system, the backup storage — is in PCI scope if any of these systems touch the PAN.

With tokenization (using a third-party vault or gateway):
- The PAN is collected in the browser/app via a gateway-hosted form (JS widget, SDK) and sent directly to the gateway. Your server never sees the PAN.
- Your server receives and stores a token.
- Your database, your analytics pipeline, your logs, and your backups contain only tokens.
- **Only the tokenization call itself (the initial card save) and the vault provider's infrastructure are in PCI scope.** Everything downstream is out of scope.

This transforms PCI compliance from an organization-wide burden to a narrow integration point — typically the gateway SDK configuration, the HTTPS connection to the gateway, and the token storage schema.

## Section 2: PSP / Gateway Tokens

**Q5. How does gateway tokenization work end-to-end? Walk through the flow.**

A: The tokenization flow is designed so the merchant's server never touches the PAN:

```
Step 1 — Card Capture (browser/mobile)
  Customer enters card details in a hosted fields widget (Razorpay.js / JusPay SDK)
  The widget is an iframe served from the gateway's domain
  Card data is submitted directly to the gateway's servers via JS — never to your server

Step 2 — Tokenization at Gateway
  Gateway validates the PAN (Luhn check, BIN lookup)
  Gateway stores the PAN in its PCI-compliant vault (HSM-backed, encrypted at rest)
  Gateway returns a token to the browser: { token_id: "tok_abc123", last4: "9010", brand: "Visa" }

Step 3 — Token sent to your server
  Browser sends the token_id to your API (POST /api/payments)
  Your server receives token_id — no PAN ever transmitted to or stored by your server

Step 4 — Payment / Charge using token
  Your server calls gateway API: POST /v1/charges { token_id: "tok_abc123", amount: 19999, currency: "INR" }
  Gateway looks up the PAN from its vault using the token
  Gateway routes the charge to the card network

Step 5 — Token stored for future use
  Your DB stores: { user_id, token_id, last4, brand, expiry_month, expiry_year, created_at }
  For recurring payments, you reuse token_id without the customer re-entering card details
```

**What your system never stores:**
- Full PAN (only `last4` for display)
- CVV (gateways must not store CVV after authorization — PCI DSS Requirement 3.2)
- Full magnetic stripe data

**What your system does store:**
- `token_id` — the gateway's token, safe to store
- `last4` — the last four digits, considered non-sensitive (PCI DSS allows storage)
- BIN / first 6 digits — allowed for routing and display purposes
- `brand`, `expiry_month`, `expiry_year` — non-sensitive metadata

**Q6. What is the token lifecycle? How are tokens created, used, updated, and deleted?**

A:

**Creation:**
- Triggered by customer saving a card (checkout flow, account settings, first recurring payment).
- Results in a `token_id` stored in your database linked to the user.
- Some gateways issue a separate `customer_id` that groups all tokens for a user — use this for multi-card support.

**Usage:**
- For a one-time payment: pass `token_id` to the charge API along with amount and currency.
- For a recurring payment (subscription, EMI, NACH): pass `token_id` with a flag indicating recurring (`recurring: true`, or use the mandate flow). Some gateways require the customer to authenticate the first transaction (3DS) before recurring use is permitted.
- For card display: use `last4`, `brand`, and `expiry_month/year` — never expose the token itself to the frontend, as it is a payment credential.

**Update (card expiry / reissuance):**
- When a card expires and the bank issues a new card with a new expiry (but the same PAN), the gateway may support **account updater** — an automatic service that refreshes the expiry date on the stored token without customer action.
- When a card is replaced (lost/stolen, new PAN), the old token becomes invalid. Your system must handle charge failures with specific error codes (e.g., `card_declined: invalid_card`) as signals to prompt the customer to re-add their card.

**Deletion:**
- Customer requests card removal (DELETE /api/payment-methods/:tokenId).
- Your server calls the gateway's delete token API: `DELETE /v1/customers/:customerId/cards/:tokenId`.
- Your DB soft-deletes or hard-deletes the token record.
- Soft-delete is preferable for audit — you may need to know that a token existed for a dispute or refund investigation.

**Q7. How do you handle multiple saved cards for a user, and what is the data model?**

A: A user may have multiple saved cards. The data model must support this cleanly while enabling display, selection, and deletion without exposing sensitive data.

**Schema:**

```sql
CREATE TABLE payment_methods (
    payment_method_id  UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id            UUID        NOT NULL REFERENCES users(user_id),
    gateway            TEXT        NOT NULL,    -- 'razorpay' | 'juspay' | 'stripe'
    gateway_token      TEXT        NOT NULL,    -- the gateway's token_id
    gateway_customer_id TEXT,                   -- gateway's customer_id if applicable
    card_brand         TEXT        NOT NULL,    -- 'Visa' | 'Mastercard' | 'Rupay'
    card_last4         CHAR(4)     NOT NULL,
    card_bin           CHAR(6),                 -- first 6 digits, for routing/display
    expiry_month       SMALLINT    NOT NULL CHECK (expiry_month BETWEEN 1 AND 12),
    expiry_year        SMALLINT    NOT NULL,
    is_default         BOOLEAN     NOT NULL DEFAULT false,
    nickname           TEXT,                    -- user-defined label: "My HDFC card"
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at         TIMESTAMPTZ,             -- soft delete
    UNIQUE (user_id, gateway, gateway_token)    -- prevent duplicate tokens per gateway
);

CREATE INDEX idx_payment_methods_user ON payment_methods (user_id) WHERE deleted_at IS NULL;
```

**Application rules:**
- Enforce at most one `is_default = true` per user at the application layer (or use a partial unique index).
- When the customer selects a card at checkout, send only the `payment_method_id` — your server maps it to `gateway_token` before calling the gateway.
- Never return `gateway_token` in API responses to the client. Return `payment_method_id`, `card_last4`, `card_brand`, and `expiry_month/year` for display.

**Q8. What happens when a gateway token becomes invalid? How do you handle it gracefully?**

A: Gateway tokens can become invalid for several reasons:

| Reason | Gateway error code (example) | Action |
|---|---|---|
| Card expired | `card_declined: expired_card` | Mark token as expired; prompt re-add |
| Card reported lost/stolen | `card_declined: lost_card` / `stolen_card` | Soft-delete token; notify user |
| Issuer declined: do not honor | `card_declined: do_not_honor` | Retry logic or prompt user |
| Token deleted from gateway | `invalid_request: token_not_found` | Hard-delete from your DB; prompt re-add |
| CVV mismatch (for CVC-required flow) | `card_declined: incorrect_cvc` | Do not retry; prompt user |
| Insufficient funds | `card_declined: insufficient_funds` | Retry on next billing cycle (subscription) or prompt user |

**Retry logic for subscription / recurring payments:**

```typescript
async function chargeWithRetry(
  tokenId: string,
  amountPaise: bigint,
  attemptNumber: number,
): Promise<ChargeResult> {
  try {
    return await gateway.charge({ tokenId, amount: amountPaise });
  } catch (err) {
    if (isRetryableDecline(err)) {
      // Retry on days 3, 7, 14 after initial failure (dunning logic)
      await scheduleRetry(tokenId, amountPaise, attemptNumber + 1);
      return { status: 'RETRY_SCHEDULED' };
    }
    if (isHardDecline(err)) {
      // Card is permanently invalid — do not retry
      await markTokenInvalid(tokenId);
      await notifyUserToUpdateCard(tokenId);
      return { status: 'HARD_DECLINE' };
    }
    throw err; // Network error, gateway error — bubble up
  }
}

// Retryable: insufficient_funds, do_not_honor, temporary errors
// Hard decline: expired, lost, stolen, invalid_account, do_not_retry
function isHardDecline(err: GatewayError): boolean {
  return ['expired_card', 'lost_card', 'stolen_card', 'invalid_account',
          'card_not_supported', 'do_not_retry'].includes(err.declineCode);
}
```

## Section 3: Network Tokens

**Q9. What is a network token, and how does it differ architecturally from a gateway token?**

A: A **network token** (also called a DPAN — Device PAN, or FPAN replacement token) is a 16-digit surrogate issued by the card network (Visa Token Service / VTS for Visa cards, Mastercard Digital Enablement Service / MDES for Mastercard) to replace the FPAN (Funding PAN — the actual card number).

**Architectural differences from gateway tokens:**

| Dimension | Gateway Token | Network Token |
|---|---|---|
| **Issued by** | Payment gateway (Razorpay, Stripe) | Card network (Visa, Mastercard) |
| **Scope** | Single gateway's ecosystem | Any acquirer/processor that supports the network |
| **Format** | Opaque string (non-card-number format) | 16-digit number (looks like a card number; routes through network) |
| **Cryptogram** | None | Yes — a one-time TAVV/CAVV cryptogram per transaction |
| **Authorization rate** | Standard | Higher — issuers trust network tokens more than raw PANs |
| **Card updates** | Manual or account updater service | Automatic lifecycle management by the network |
| **RBI compliance (India)** | Partial (CoF mandate) | Full (RBI's Card-on-File Tokenisation framework) |
| **Who manages lifecycle** | You + gateway | Network manages updates, suspensions, deletions |

The critical insight: a network token has no mathematical relationship to the FPAN, but the network knows the mapping. When a transaction arrives at the network with a DPAN, the network de-tokenizes it to the FPAN before routing to the issuer. The issuer sees the FPAN and makes an authorization decision exactly as it would for a direct card transaction.

---

**Q10. What is a cryptogram in network tokenization, and why is it necessary?**

A: A **cryptogram** (called **TAVV** — Token Authentication Verification Value for Visa; **DSRP cryptogram** for Mastercard) is a one-time, transaction-specific value generated by the Token Requestor (the entity that holds the network token) and verified by the card network during authorization.

**Why it is necessary:** A network token looks like a 16-digit card number. An attacker who obtains a DPAN cannot use it for a transaction without the corresponding cryptogram — and each cryptogram is valid for exactly one transaction (bound to the specific amount, merchant, and timestamp). Even if the DPAN is intercepted, replaying it with a different amount or at a different merchant fails cryptogram validation at the network.

**How a cryptogram is generated:**

```
Inputs to cryptogram generation:
  - Token (DPAN)
  - Token cryptography key (provided by network during token provisioning)
  - Transaction counter (monotonically increasing, prevents replay)
  - Transaction amount
  - Merchant ID
  - Timestamp

Process:
  TAVV = HMAC-SHA256(key, DPAN || counter || amount || merchantId || timestamp)
         truncated and encoded per network specification
```

In practice, the cryptogram is generated by:
- The **device secure element** (for Apple Pay, Google Pay hardware-backed tokens).
- The **Token Requestor's server** (for card-on-file network tokens, using a key provisioned by the network).

The cryptogram is included in the authorization request alongside the DPAN and verified by the card network before the transaction is routed to the issuer.

**Q11. How does Visa Token Service (VTS) and Mastercard Digital Enablement Service (MDES) work at a technical level?**

A: Both VTS and MDES follow the same conceptual flow with different APIs and terminology:

**Token Provisioning (one-time setup per card):**

```
Token Requestor (your platform) → VTS/MDES API
  Request: { fpan, expiry, cvv, requestorId, tokenType: 'COF' }
  VTS/MDES validates the card with the issuer (Account Holder Verification)
  VTS/MDES generates a DPAN (Device PAN) — 16 digits, same BIN structure as FPAN
  Response: {
    dpan: "4111 9900 0012 3456",
    dpanExpiry: "12/2027",
    tokenReferenceId: "VTS-TRF-abc123",
    tokenStatus: "ACTIVE",
    cryptogramKey: <key material for generating TAVV>
  }
  You store: dpan (encrypted), dpanExpiry, tokenReferenceId
  You never store: fpan, cvv
```

**Transaction (per payment):**

```
Token Requestor → Your payment server
  1. Generate TAVV cryptogram using: dpan + cryptogramKey + transactionData
  2. Build authorization request:
     {
       pan:        dpan,           // DPAN, not FPAN
       expiry:     dpanExpiry,
       cryptogram: tavv,
       eci:        "07",          // Electronic Commerce Indicator for network token
     }
  3. Send to acquirer/gateway as a standard authorization message
  4. Acquirer routes to Visa/Mastercard network
  5. Network detects DPAN → de-tokenizes to FPAN → routes to issuer
  6. Issuer verifies cryptogram + authorizes transaction
  7. Network returns authorization response to acquirer
```

**Token Lifecycle Management (ongoing):**

VTS/MDES send lifecycle notifications to the Token Requestor's webhook:
- `TOKEN_STATUS_UPDATED` — card replaced, token suspended, token resumed.
- `FPAN_ACCOUNT_RANGE_UPDATE` — issuer updates BIN details.
- `CARD_METADATA_UPDATE` — expiry date updated (card renewed).

Your system must handle these webhooks to update the stored DPAN and avoid attempting to use a suspended token.

**Q12. What is RBI's Card-on-File Tokenisation (CoFT) framework, and how does it affect Indian payment systems?**

A: In September 2021 (effective October 2022, after extensions), the Reserve Bank of India issued guidelines requiring that **no entity in the payment chain other than card networks and issuers can store actual card data** (PAN + expiry + CVV) for Card-on-File (CoF) transactions.

**Key mandates:**

1. **No raw PAN storage:** Merchants, payment aggregators (Razorpay, JusPay, CCAvenue), and payment gateways cannot store the full PAN. Only card networks (Visa, Mastercard, RuPay) and card issuers (banks) are permitted to hold PANs.
2. **Tokenisation is mandatory for saved cards:** Any "saved card" feature must use a network token issued by Visa/Mastercard/RuPay's token service — not a gateway-generated opaque token backed by a PAN in the gateway's vault.
3. **Customer consent:** Tokenisation must be explicitly consented to by the cardholder. The customer must actively opt in, not be opted in by default.
4. **Token Requestor registration:** Entities that want to tokenize cards must register as Token Requestors with each card network. This is a formal certification process.

**Impact on the payment stack in India:**

- Razorpay, JusPay, and other gateways had to completely rebuild their card-save flows — previously they stored PANs in their own HSM-backed vaults; post-RBI mandate, they must call VTS/MDES/RuPay Token Service and store only network tokens.
- For merchants using these gateways, the change was largely abstracted — the gateway handles the network tokenization and exposes its existing `token_id` API, but the underlying token is now a network token.
- For platforms doing direct integration with card networks (large merchants, aggregators), they had to build Token Requestor infrastructure: network enrollment, TAVV cryptogram generation, lifecycle webhook handling.
- Existing stored PANs had to be migrated: deleted from merchant/gateway storage and re-tokenized (customers had to re-consent to save their card, or the card was removed from saved cards).

## Section 4: Token Security & Architecture

**Q13. How do you store tokens securely? Are tokens sensitive data?**

A: Network tokens and gateway tokens differ in their sensitivity:

**Gateway tokens (`tok_abc123`, JusPay `card_token`):**
- Functionally sensitive — they are payment credentials that can initiate a charge against the customer's card.
- Not PCI CHD (Cardholder Data) — they are not PANs and don't fall under PCI DSS's strictest requirements.
- Should be treated as **secrets**: stored in an encrypted column or with application-level encryption, not exposed in URLs, not logged in plaintext, access-controlled at the DB level.
- Consider them analogous to an OAuth refresh token — not as sensitive as a password, but a credential that grants financial power.

**Network tokens (DPANs):**
- Look like card numbers (16 digits) and route through card networks.
- PCI DSS considers DPANs to be in scope — they are a form of PAN from the compliance perspective.
- Must be stored encrypted (AES-256-GCM in an HSM-backed key management system) or in a dedicated vault.
- The cryptogram key material is even more sensitive — it must be stored in an HSM; software storage is not acceptable.

**Practical storage for gateway tokens (Node.js + Postgres):**

```typescript
// Application-level encryption before storage
import { createCipheriv, createDecipheriv, randomBytes } from 'crypto';

const ENCRYPTION_KEY = Buffer.from(process.env.TOKEN_ENCRYPTION_KEY!, 'hex'); // 32 bytes

function encryptToken(plaintext: string): string {
  const iv = randomBytes(16);
  const cipher = createCipheriv('aes-256-gcm', ENCRYPTION_KEY, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const authTag = cipher.getAuthTag();
  // Store: iv + authTag + ciphertext as hex
  return Buffer.concat([iv, authTag, encrypted]).toString('hex');
}

function decryptToken(ciphertext: string): string {
  const buf = Buffer.from(ciphertext, 'hex');
  const iv      = buf.subarray(0, 16);
  const authTag = buf.subarray(16, 32);
  const data    = buf.subarray(32);
  const decipher = createDecipheriv('aes-256-gcm', ENCRYPTION_KEY, iv);
  decipher.setAuthTag(authTag);
  return decipher.update(data) + decipher.final('utf8');
}
```

In practice, use AWS KMS or HashiCorp Vault's transit encryption rather than managing keys directly — key rotation, audit logging, and HSM backing are handled by the KMS.

**Q14. What is token scoping, and what happens if a token is used outside its intended scope?**

A: **Token scoping** defines the boundaries within which a token is valid. Both gateway tokens and network tokens are scoped, though differently:

**Gateway token scope:**
- Scoped to the issuing gateway: a Razorpay token cannot be used through Stripe.
- Scoped to the merchant's account: a token issued under Merchant A's Razorpay account cannot be used by Merchant B — even on the same gateway.
- Optionally scoped to a specific customer: some gateways bind a token to a `customer_id` and reject charges if the `customer_id` doesn't match.

**Network token scope (more granular):**

| Scope dimension | How enforced |
|---|---|
| Token Requestor | DPAN is bound to the Token Requestor ID that provisioned it; another requestor cannot use it |
| Merchant | Card-on-file tokens can be scoped to a specific Merchant ID in the network's registry |
| Channel | A DPAN provisioned for e-commerce (COF) cannot be used for in-store (contactless) transactions |
| Cryptogram validity | Single transaction; expired after use or after a timeout (typically 30 seconds) |

**What happens on scope violation:**
- Gateway scope violation: gateway API returns `401 Unauthorized` or `invalid_token`.
- Network scope violation: network rejects the authorization; issuer sees an `ECI` mismatch or cryptogram failure; decline code propagates to the merchant.

**Why scoping matters beyond security:** It is why a hacked merchant database containing tokens is much less dangerous than one containing PANs. The attacker gets tokens valid only for that specific merchant, through that specific gateway — not reusable raw card credentials.

**Q15. What is token provisioning versus token requestor registration, and what is the difference?**

A: These are two distinct steps in the network tokenization lifecycle:

**Token Requestor Registration (one-time, per network):**
- A Token Requestor is any entity authorized by a card network to provision and use network tokens. Examples: Apple (for Apple Pay), Google (for Google Pay), Razorpay (for CoF tokenization), a large merchant (direct integration).
- Registration involves: application to the network, technical certification (API integration testing), security audit, and assignment of a **Token Requestor ID (TRID)** — a unique identifier that is embedded in every token the requestor provisions.
- In India under RBI's CoFT: aggregators and gateways must register separately with Visa, Mastercard, and RuPay.
- Registration is a business and compliance process, not a per-card technical step.

**Token Provisioning (per card, per requestor):**
- The act of calling the network's tokenization API for a specific card (FPAN) and receiving a DPAN.
- Triggered by: customer saving a card, first use of a new payment method, device enrollment (for Apple/Google Pay).
- Involves: FPAN validation, Account Holder Verification (AHV — the network checks the card is valid and active), DPAN generation, cryptogram key provisioning.
- The result is a mapping in the network's token vault: `TRID + DPAN → FPAN`.

**In code terms:**
- Token Requestor Registration = the OAuth application registration — done once per integration.
- Token Provisioning = the OAuth authorization flow — done once per user + card combination.

**Q16. What is the difference between a FPAN and a DPAN, and what is an FPAN token?**

A:

| Term | Stands for | What it is |
|---|---|---|
| **FPAN** | Funding PAN | The actual card number issued by the bank to the cardholder — what's printed on the physical card |
| **DPAN** | Device PAN (also called Token PAN or TPAN) | A network-issued surrogate that replaces the FPAN in digital transactions |
| **FPAN Token** | — | A gateway-generated opaque token (e.g., `tok_abc123`) that represents a stored FPAN in the gateway's vault — not a card number; this is NOT a network token |

The naming is unfortunately confusing:

- "Token" in **FPAN Token** (PSP token) = an opaque identifier referencing a stored PAN.
- "Token" in **DPAN** (network token) = a surrogate card number that transacts through the network.

Both are called "tokens" in industry parlance but are architecturally different. The distinction matters because:
- An FPAN Token requires the issuing gateway to hold the FPAN in its vault — the PAN exists somewhere.
- A DPAN is issued by the network — no entity except the network holds the FPAN-to-DPAN mapping. The gateway never had access to the FPAN if the card was provisioned directly through the network.

Under RBI's CoFT rules, the distinction becomes regulatory: only DPAN-based storage (true network tokenization) satisfies the mandate. FPAN Token storage (PSP vault) does not.

## Section 5: Apple Pay, Google Pay & Device Tokenization

**Q17. How do Apple Pay and Google Pay use network tokens? What happens during a payment?**

A: Apple Pay and Google Pay are both Token Requestors registered with card networks. Each uses network tokenization — specifically device-bound tokens stored in a secure element or trusted execution environment.

**Apple Pay provisioning flow:**

```
1. User adds card to Wallet app
2. iOS sends card details to Apple's servers (Apple is a registered Token Requestor)
3. Apple calls VTS/MDES API to provision a DPAN for that card+device combination
4. DPAN and cryptogram keys are stored in the iPhone's Secure Element (hardware chip)
   — not in iCloud, not on Apple's servers
5. Apple notifies the issuer; issuer may prompt for additional verification (SMS OTP)
```

**Apple Pay payment flow:**

```
1. User double-clicks side button, authenticates with Face ID / Touch ID
2. Secure Element generates a TAVV cryptogram using:
   - DPAN stored in Secure Element
   - Cryptogram key stored in Secure Element
   - Transaction counter (increments per transaction)
   - Transaction amount (from the merchant's POS/app)
3. Device sends to merchant terminal/app:
   { dpan, dpanExpiry, tavv, eci: "07" }
4. Merchant sends to acquirer as a standard EMV/NFC or in-app payment
5. Network de-tokenizes DPAN → FPAN, verifies TAVV
6. Issuer authorizes against FPAN
```

**Key security property:** The FPAN never leaves the issuer's systems after the initial provisioning. The merchant terminal receives only the DPAN + cryptogram — not the FPAN. Even Apple's servers don't have the DPAN after provisioning; it lives in the device's Secure Element.

**Google Pay on Android** uses the same architecture on certified Android devices with a hardware-backed secure element. On devices without a secure element, Google uses a cloud-based token model (HCE — Host Card Emulation), where the DPAN and limited-use cryptogram keys are stored in Google's servers and delivered to the device on demand.

**Q18. What is a "limited use key" and how does it relate to cryptogram generation for in-app payments?**

A: A **Limited Use Key (LUK)** is a short-lived symmetric cryptographic key provisioned by the card network to a Token Requestor for generating transaction cryptograms without requiring a real-time network call per transaction. It is the mechanism that enables offline-capable cryptogram generation (as in NFC tap-to-pay) and efficient in-app payment flows.

**Properties of a LUK:**
- Bound to a specific DPAN and Token Requestor.
- Has a **limited use count** (e.g., valid for 10 transactions) and a **time-to-live** (e.g., 24 hours), whichever is exhausted first.
- Stored in the Secure Element (for hardware-backed) or in the Token Requestor's HSM (for cloud-based COF tokens).
- When exhausted, the Token Requestor requests a new LUK from the network's key provisioning service.

**Cryptogram generation using LUK (simplified):**

```
TAVV = MAC(
  key    = LUK,
  data   = DPAN || LUK_version || transaction_counter || amount || currency || timestamp
)
truncated to 8 bytes and base64-encoded
```

The `transaction_counter` is a monotonically increasing value stored alongside the LUK. It prevents replay attacks — the network validates that the counter in the TAVV is greater than the last counter it accepted for that DPAN.

**Why this matters for your system:** If you're building a direct network token integration (not via a gateway), you must implement LUK management:
- Store current LUK + version + remaining use count per DPAN (in an HSM or KMS-backed store).
- Replenish LUKs before they are exhausted (proactive replenishment at, say, 2 uses remaining).
- Handle LUK rotation atomically — if you use a LUK for transaction N and the replenishment fails before N+1, you must not generate an invalid cryptogram.

## Section 6: Failure Modes, Reconciliation & System Design

**Q19. What are the failure modes specific to tokenization, and how do you handle each?**

A:

| Failure | Layer | Symptom | Handling |
|---|---|---|---|
| **Token provisioning failure** | Network API call | Card save fails; user can't add card | Retry with exponential backoff; surface error to user; do not create a partial record |
| **Token suspended by network** | Lifecycle webhook | Subsequent charges fail with `token_suspended` | Handle webhook → mark token inactive → notify user to re-add card |
| **FPAN changed (card replaced)** | Lifecycle webhook | `TOKEN_STATUS_UPDATED: DELETED` | Delete token from DB; notify user |
| **FPAN expiry updated** | Lifecycle / account updater | Charge succeeds without action if account updater is enabled | Apply updated expiry from webhook to your stored token record |
| **Cryptogram replay** | Authorization | Network returns `TAVV_VALIDATION_FAILURE` | Do not retry with the same cryptogram; generate a new one for a new attempt |
| **LUK exhausted mid-transaction** | Token Requestor server | Unable to generate cryptogram | Replenish LUK proactively; have a fallback to request emergency LUK |
| **Webhook delivery failure** | Network → your server | Token lifecycle events missed | Implement idempotent webhook handler; poll network's token status API as a fallback |
| **Gateway token orphaned** | DB + gateway out of sync | Your DB has token; gateway deleted it | Handle `token_not_found` at charge time; soft-delete from DB; prompt user |

**Idempotent webhook handler pattern:**

```typescript
async function handleNetworkTokenWebhook(event: TokenLifecycleEvent) {
  // Idempotency: skip if already processed
  const alreadyProcessed = await db.query(
    'SELECT 1 FROM processed_webhook_events WHERE event_id = $1',
    [event.eventId]
  );
  if (alreadyProcessed.rowCount > 0) return;

  await db.transaction(async (trx) => {
    switch (event.eventType) {
      case 'TOKEN_STATUS_UPDATED':
        await trx('payment_methods')
          .where({ dpan_reference: event.tokenReferenceId })
          .update({ status: event.newStatus, updated_at: new Date() });
        break;
      case 'CARD_METADATA_UPDATE':
        await trx('payment_methods')
          .where({ dpan_reference: event.tokenReferenceId })
          .update({
            expiry_month: event.newExpiryMonth,
            expiry_year:  event.newExpiryYear,
          });
        break;
    }

    await trx('processed_webhook_events').insert({
      event_id:   event.eventId,
      event_type: event.eventType,
      processed_at: new Date(),
    });
  });
}
```

**Q20. How do you reconcile token-based payments against gateway and network settlement reports?**

A: Reconciliation with tokens is complicated by the fact that your internal records use tokens (gateway token IDs or DPAN references), while settlement reports use different identifiers:

- Gateway settlement reports reference the gateway's internal transaction ID and may include a masked PAN (`****9010`).
- Network settlement reports reference the DPAN (for network token transactions) or FPAN (for non-tokenized transactions), not your internal token ID.
- Your DB contains the gateway token ID, the DPAN reference, and your internal `payment_id`.

**Reconciliation key mapping:**

```sql
-- Your payments table must store all relevant identifiers
CREATE TABLE payments (
    payment_id           UUID     PRIMARY KEY,
    internal_order_id    UUID     NOT NULL,
    gateway_txn_id       TEXT     NOT NULL,    -- gateway's transaction reference
    payment_method_id    UUID     REFERENCES payment_methods(payment_method_id),
    amount_paise         BIGINT   NOT NULL,
    status               TEXT     NOT NULL,
    gateway_settled_at   TIMESTAMPTZ,
    gateway_settled_amount BIGINT,             -- what the gateway actually settled
    created_at           TIMESTAMPTZ NOT NULL
);

-- During reconciliation, join on gateway_txn_id
SELECT
    p.payment_id,
    p.amount_paise,
    s.settled_amount,
    p.amount_paise - s.settled_amount AS diff
FROM payments p
JOIN gateway_settlement_report s ON p.gateway_txn_id = s.transaction_id
WHERE p.created_at::date = $settlement_date
  AND p.amount_paise != s.settled_amount;
```

**Special cases for tokenized payments:**
- A token may be used across multiple transactions. Ensure your reconciliation joins on `gateway_txn_id`, not on `payment_method_id` (which is reused per card, not per transaction).
- For network token transactions, the settlement report may show the DPAN rather than a masked FPAN. Your `payment_methods` table stores the `dpan_reference`; use it as a secondary join key for disputes.
- Account updater changes (expiry refresh) generate a new settlement event in some gateway formats. Ensure your reconciliation logic doesn't flag these as new charges.

**Q21. "Design the tokenization architecture for a lending platform that needs to support saved cards, recurring NACH-linked repayments, and RBI CoFT compliance."**

A: This is a multi-layer design that must satisfy RBI's mandate (no raw PAN storage), support recurring debits, and handle the full token lifecycle.

**Component architecture:**

```
Customer Browser/App
  │
  │ [Card capture via hosted fields — PAN never reaches your server]
  ▼
Payment Gateway SDK (Razorpay / JusPay)
  │  ← PAN captured in gateway-hosted iframe
  │  ← Gateway provisions network token via VTS/MDES
  │  ← Gateway returns: { token_id, dpan_reference, card_last4, brand, expiry }
  ▼
Your API Server
  │
  ├─ Stores in payment_methods: token_id, dpan_reference, last4, brand, expiry, user_id
  │  (No PAN, no CVV — RBI compliant)
  │
  ├─ For first transaction: passes token_id to gateway for 3DS authentication
  │  (AFA — Additional Factor Authentication, required by RBI for first recurring transaction)
  │
  └─ For subsequent recurring debits:
       ├─ Retrieve token_id from payment_methods
       ├─ Call gateway recurring charge API (token_id, amount, mandate_id)
       └─ Gateway generates cryptogram using stored network token credentials
          └─ Routes through network using DPAN + TAVV
```

**Data model additions for recurring:**

```sql
CREATE TABLE recurring_mandates (
    mandate_id       UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id          UUID        NOT NULL REFERENCES users(user_id),
    payment_method_id UUID       NOT NULL REFERENCES payment_methods(payment_method_id),
    gateway_mandate_id TEXT      NOT NULL UNIQUE,    -- gateway's mandate reference
    max_amount_paise BIGINT      NOT NULL,
    frequency        TEXT        NOT NULL,            -- 'MONTHLY' | 'WEEKLY' | etc.
    status           TEXT        NOT NULL,            -- 'ACTIVE' | 'PAUSED' | 'REVOKED'
    afa_completed    BOOLEAN     NOT NULL DEFAULT false,
    afa_completed_at TIMESTAMPTZ,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at       TIMESTAMPTZ
);
```

**RBI CoFT compliance checklist for this design:**

- ✅ No PAN stored anywhere — gateway holds network token, not raw PAN.
- ✅ Customer explicitly consented to tokenization (checkbox + T&C at card save flow).
- ✅ AFA (OTP / 3DS) completed on first recurring transaction.
- ✅ Pre-debit notification sent 24 hours before each recurring charge (RBI mandate).
- ✅ Customer can revoke mandate at any time (DELETE /mandates/:id → gateway mandate cancellation → token lifecycle update).
- ✅ Token lifecycle webhooks handled — if the card is replaced, the mandate is paused and customer notified.
- ✅ Network token used — satisfies "no entity in the payment chain stores actual card data" requirement.

**Token lifecycle event handling for mandates:**

```typescript
async function handleTokenSuspended(dpanReference: string) {
  // Find all active mandates using this token
  const mandates = await db('recurring_mandates')
    .join('payment_methods', 'recurring_mandates.payment_method_id', 'payment_methods.payment_method_id')
    .where('payment_methods.dpan_reference', dpanReference)
    .where('recurring_mandates.status', 'ACTIVE');

  for (const mandate of mandates) {
    await db('recurring_mandates')
      .where({ mandate_id: mandate.mandate_id })
      .update({ status: 'PAUSED' });

    await notificationService.sendCardUpdateRequired(mandate.user_id, {
      reason: 'Your saved card is no longer valid. Please update your payment method to continue your subscription.',
    });
  }
}
```

## Quick Reference Table

| Property | PSP / Gateway Token | Network Token (DPAN) |
|---|---|---|
| **Issued by** | Payment gateway (Razorpay, JusPay) | Card network (Visa VTS, Mastercard MDES, RuPay) |
| **Format** | Opaque string (`tok_abc123`) | 16-digit card number (DPAN) |
| **PAN stored where** | Gateway's HSM vault | Network's token vault only |
| **Cryptogram** | None | TAVV / DSRP — one per transaction |
| **Authorization rate** | Standard | Higher (issuer trust) |
| **Portability** | Gateway-locked | Any acquirer on the network |
| **RBI CoFT compliant** | No (PAN in gateway vault) | Yes (no PAN outside network/issuer) |
| **Lifecycle management** | Manual + account updater | Network manages, webhooks to requestor |
| **Card replacement handling** | Charge fails → user re-adds card | Network issues new DPAN → webhook update |
| **Used by** | Merchant saved-cards, subscriptions | Apple Pay, Google Pay, CoFT mandates |
| **PCI DSS scope** | Reduces scope (no PAN at merchant) | Reduces scope further (no PAN at gateway) |
| **Your DB stores** | `gateway_token_id`, `last4`, `brand` | `dpan_reference`, `last4`, `brand` (never DPAN in plaintext) |
