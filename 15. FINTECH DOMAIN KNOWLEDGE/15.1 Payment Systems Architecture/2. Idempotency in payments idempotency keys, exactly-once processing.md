# Payment Lifecycle: Idempotency in Payments — Idempotency Keys & Exactly-Once Processing — Interview Q&A (5 YOE Level)

> **Domain:** Fintech / Payment Systems Architecture

---

## Section 1: Fundamentals

**Q1. What is idempotency, and why does it matter specifically in payments?**

A: An operation is **idempotent** if performing it multiple times produces the same result as performing it once. In mathematics, `f(f(x)) = f(x)`. In HTTP terms, `GET`, `PUT`, and `DELETE` are idempotent by spec; `POST` is not.

In payments, idempotency isn't optional — it's a correctness requirement. Consider a customer clicking "Pay ₹5,000" and their network drops immediately after the request leaves the client but before the response arrives. The client has no idea whether the charge succeeded. If it retries — as it should — and the server lacks idempotency guarantees, the customer is charged twice. In fintech, a double-charge is not a UX bug; it is a regulatory, legal, and trust problem that triggers chargebacks, customer support escalations, and potential RBI/SEBI scrutiny.

The general principle: **any mutating operation that can be retried (by a client, a queue consumer, a cron job) must be idempotent at the server.** Payment initiation, refund creation, mandate registration, and disbursement are the most critical surfaces.

---

**Q2. What is an idempotency key, and what contract does it establish between client and server?**

A: An **idempotency key** is a unique token — typically a UUID or a high-entropy string — generated by the **client** before making a mutating request and sent as a header (e.g., `Idempotency-Key: <uuid>`). The contract:

- **First call:** The server processes the request and stores the result, indexed by the idempotency key.
- **Subsequent calls with the same key:** The server returns the *stored result* from the first call without reprocessing — even if the underlying operation would now behave differently (e.g., the account is now closed).
- **Expiry:** The server retains the key for a defined window (commonly 24 hours to 7 days, depending on the operation's retry horizon).

Key properties:
- The client is responsible for key **generation** and **scoping** — the same key must not be reused across different logical operations.
- The server is responsible for key **storage**, **lookup**, and **response replay**.
- The key must be **unique per intent** — not per session or per user. A retry of the same intent reuses the same key; a new payment attempt generates a new key.

---

**Q3. What is "exactly-once" processing, and is it actually achievable in distributed systems?**

A: Exactly-once processing means a message or request is processed **exactly one time** — not zero times (at-most-once) and not one-or-more times (at-least-once). In distributed systems, true exactly-once delivery at the transport layer is theoretically impossible: the Two Generals Problem guarantees that a sender can never know with certainty whether a message was received.

What *is* achievable — and what the industry means when it says "exactly-once" — is **effectively-once processing via idempotent consumers**:

1. The **delivery layer** guarantees **at-least-once** (messages may be redelivered).
2. The **consumer** is written to be **idempotent** — processing the same message twice produces the same outcome as processing it once.
3. Together, these two properties produce **effectively-once** observable behavior.

Kafka's "exactly-once semantics" (EOS), introduced in 0.11, is a well-known example: it provides exactly-once within a Kafka-to-Kafka pipeline using idempotent producers + transactional APIs, but once the data leaves Kafka into an external system (your Postgres, your payment gateway call), you are back to at-least-once + idempotent consumer.

**The practical answer for a payment system interview:** "Exactly-once delivery is not achievable, but exactly-once *effect* is achievable through idempotent design. Our charge API deduplicates using an idempotency key stored in Postgres; our Kafka consumer deduplicates using a processed-event log. The business sees each payment processed once regardless of how many times the message was delivered."

---

**Q4. What are the three delivery semantics, and which does each layer of a payment system typically use?**

A:

| Semantic | Guarantee | Risk | Typical use |
|---|---|---|---|
| **At-most-once** | Message delivered 0 or 1 times | Data loss | Fire-and-forget logs, non-critical metrics |
| **At-least-once** | Message delivered 1+ times | Duplicate processing | Default for Kafka consumers, SQS, webhook delivery |
| **Exactly-once** | Message delivered exactly 1 time | Theoretically unachievable across systems | Kafka-to-Kafka with EOS; approximated elsewhere via idempotent consumers |

In a typical payment system:
- **Client → API Gateway:** at-least-once (client retries on timeout); API layer must be idempotent.
- **API → internal Kafka topic:** at-least-once (producer retries); consumer must be idempotent.
- **Kafka consumer → Payment Gateway (JusPay/Razorpay):** at-least-once (consumer retries on failure); gateway call must be idempotent (most provide their own idempotency key support).
- **Payment Gateway → DB write:** wrapped in a transaction; effectively-once if the consumer checks for existing records before inserting.

## Section 2: Idempotency Key Design

**Q5. How should idempotency keys be generated, and who generates them?**

A: The **client generates** the key before making the request — not the server. This is a critical design decision: if the server generated the key, the client would need a round-trip to obtain it *before* the actual operation, which adds latency and introduces a second failure point.

**Generation rules:**
- Use **UUIDv4** (128 bits of randomness, ~5 × 10²² keys before collision probability becomes non-negligible). UUIDv4 is the industry default for idempotency keys.
- Alternatively, use a deterministic key composed of business-meaningful fields: `sha256(userId + orderId + amount + currency)`. This allows the server to detect conflicting retries (same key, different payload) more precisely.
- Never use auto-incremented integers, timestamps, or session IDs as idempotency keys — they lack sufficient entropy or uniqueness across retries.

**Scoping rule:** One key per *logical intent*. A customer placing a ₹5,000 order generates one key. If the payment fails and the customer places the *same* order again (a genuine retry), the same key is reused. If the customer places a *new* order for ₹5,000 (a different intent), a new key is generated.

---

**Q6. How do you store and look up idempotency keys efficiently?**

A: The idempotency key store is a hot path — it is read on *every* mutating API call and written on *every first call*. Design considerations:

**Storage options:**
- **Redis (with TTL):** The most common choice for high-throughput payment APIs. Key lookup is O(1). TTL handles expiry automatically. Downside: Redis is not durable by default; a crash before the response is persisted can cause incorrect replay.
- **PostgreSQL (dedicated table):** More durable. Use a table like `idempotency_records(key, response_status, response_body, created_at, expires_at)` with an index on `key`. Suitable when volume is lower or when you need to audit idempotency record usage.
- **Hybrid:** Write to both Redis (for fast lookup) and Postgres (for durability and audit). Accept that a Redis miss may require a Postgres fallback.

**Schema (Postgres example):**
```sql
CREATE TABLE idempotency_records (
    idempotency_key   UUID        PRIMARY KEY,
    status            TEXT        NOT NULL,  -- 'processing' | 'completed' | 'failed'
    request_hash      TEXT        NOT NULL,  -- SHA256 of request payload
    response_code     INT,
    response_body     JSONB,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at        TIMESTAMPTZ NOT NULL
);

CREATE INDEX idx_idempotency_expires ON idempotency_records(expires_at);
```

A background job or Postgres `pg_cron` deletes expired rows. The `request_hash` enables conflict detection (same key, different payload = reject with 422).

---

**Q7. What is the "in-flight" problem, and how do you handle concurrent retries with the same idempotency key?**

A: The **in-flight problem** occurs when two requests arrive simultaneously with the same idempotency key — both are "first" calls from the client's perspective (e.g., a client-side double-tap, or two load balancer nodes forwarding the same retried request concurrently).

Without protection, both requests pass the initial key lookup (key doesn't exist yet), and both proceed to process — resulting in a double charge.

**Solution — optimistic locking with a status field:**

1. On arrival, attempt an atomic **INSERT** of the key with `status = 'processing'`. In Postgres: `INSERT ... ON CONFLICT DO NOTHING` returning the inserted row count.
2. If insert succeeds (row count = 1) → this request is the first; proceed with processing.
3. If insert fails (row count = 0, conflict on primary key) → a concurrent request is already processing this key. Return **409 Conflict** or poll for the result.
4. On completion, **UPDATE** the row to `status = 'completed'` and store the response.
5. Future retries hit the completed row and receive the stored response.

**In Redis**, use `SET key value NX PX <ttl_ms>` — the `NX` flag (set if Not eXists) is atomic and serves the same purpose as the INSERT with conflict detection.

---

**Q8. What should you do when the idempotency key exists but the request payload has changed?**

A: This is a **conflict** — the client is attempting to reuse a key for a different logical operation. The correct response is **422 Unprocessable Entity** (or **409 Conflict**) with an error body explaining the mismatch. Do *not* process the new payload and do *not* return the stored result from the original payload.

To detect payload changes, store a hash of the original request body alongside the idempotency key:

```typescript
const requestHash = sha256(JSON.stringify({
  amount: req.body.amount,
  currency: req.body.currency,
  customerId: req.body.customerId,
}));

if (existingRecord.requestHash !== requestHash) {
  throw new ConflictException(
    'Idempotency key already used with a different request payload.'
  );
}
```

Fields to include in the hash: all semantically meaningful fields (amount, currency, recipient, purpose). Exclude headers, timestamps, and request metadata.

This protects against a subtle bug: a client that generates keys insufficiently randomly (e.g., based on user ID alone) and inadvertently reuses a key across different intents.

## Section 3: Idempotent Consumer Patterns

**Q9. How do you implement an idempotent Kafka consumer for payment events?**

A: A Kafka consumer receives a payment event (e.g., `payment.initiated`) and must perform a DB write or a downstream API call. Since Kafka guarantees at-least-once delivery, the consumer must be written to handle duplicate messages safely.

**Pattern — Deduplication table:**

```sql
CREATE TABLE processed_events (
    event_id      TEXT PRIMARY KEY,   -- Kafka message key or a field in the payload
    topic         TEXT NOT NULL,
    partition_key INT,
    offset        BIGINT,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Consumer logic:**

```typescript
async function handlePaymentInitiated(message: KafkaMessage) {
  const eventId = message.headers['event-id'] as string;

  // Attempt to insert; conflict = duplicate
  const inserted = await db.query(`
    INSERT INTO processed_events (event_id, topic, partition_key, offset)
    VALUES ($1, $2, $3, $4)
    ON CONFLICT (event_id) DO NOTHING
    RETURNING event_id
  `, [eventId, message.topic, message.partition, message.offset]);

  if (inserted.rowCount === 0) {
    logger.info({ eventId }, 'Duplicate event — skipping');
    return; // Already processed; commit offset and move on
  }

  // Process inside the same DB transaction if possible
  await processPayment(message.value);
}
```

**Key consideration — transactional outbox vs. dedup table:** If the consumer writes to Postgres *and* publishes downstream events, wrap the dedup insert, the business write, and the outbox insert in a single DB transaction. This prevents partial processing where the dedup row is inserted but the business logic fails (or vice versa).

---

**Q10. What is the transactional outbox pattern, and how does it guarantee exactly-once effect in a payment flow?**

A: The **transactional outbox** solves a dual-write problem: a service needs to (1) update its own database and (2) publish a message to a broker, and these two operations cannot be made atomic across different systems.

Without the pattern, two failure modes exist:
- DB write succeeds, broker publish fails → downstream sees no event; payment is "lost" from the event stream.
- Broker publish succeeds, DB write fails → downstream processes an event for a payment that doesn't exist in the DB.

**Pattern:**

```sql
-- Outbox table lives in the same Postgres database as your business tables
CREATE TABLE outbox_events (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_id  TEXT NOT NULL,    -- e.g., payment_id
    event_type    TEXT NOT NULL,    -- e.g., 'payment.initiated'
    payload       JSONB NOT NULL,
    published     BOOLEAN NOT NULL DEFAULT false,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Write path (within one DB transaction):**
```sql
BEGIN;
  INSERT INTO payments (...) VALUES (...);
  INSERT INTO outbox_events (aggregate_id, event_type, payload)
    VALUES ($payment_id, 'payment.initiated', $payload);
COMMIT;
```

**Publisher (a separate process / Debezium CDC):**
- Polls (or receives CDC events for) `outbox_events WHERE published = false`.
- Publishes each event to Kafka.
- Marks the row `published = true`.

**Result:** The business write and the event are always in sync. The publisher may publish duplicates (if it crashes after publishing but before marking published), but the Kafka consumer handles those with its dedup table — giving effectively-once end-to-end semantics.

---

**Q11. What is the difference between idempotency at the API layer and idempotency at the consumer layer? Do you need both?**

A:

| Layer | What it deduplicates | Mechanism | Who drives retries |
|---|---|---|---|
| **API layer** | HTTP requests from a client | Idempotency key in header; stored in Redis/Postgres | Client (mobile app, partner API) |
| **Consumer layer** | Kafka messages / queue jobs | Dedup table or transactional outbox | Broker redelivery, consumer crash/restart |

Yes, you need both — they protect against different failure modes:

- A client retrying an HTTP POST is caught by the **API layer**.
- A Kafka consumer processing the same message after a crash is caught by the **consumer layer**.
- A CDC publisher re-publishing an outbox event is caught by the **consumer layer**.

A common mistake is implementing API-layer idempotency and assuming downstream consumers are safe. They are not: the API may successfully deduplicate the HTTP request and produce a single Kafka message, but the consumer is a separate process with its own failure modes.

## Section 4: Idempotency with Payment Gateways

**Q12. How do JusPay and Razorpay implement idempotency, and how should your service interact with them?**

A: Most payment gateways expose idempotency via a dedicated request header or a first-class field in the order creation payload.

**Razorpay:** Accepts `X-Razorpay-Idempotency-Key` on order creation. If the same key is sent twice, the second call returns the original order object with an `HTTP 200` and a `duplicate` flag in the response body, without creating a new order.

**JusPay:** Uses `order_id` as a natural idempotency key — sending the same `order_id` twice returns the existing order rather than creating a duplicate. Your service must generate the `order_id` on your side (not let JusPay generate it), and that ID becomes your idempotency handle for all future operations on that order.

**Practical contract for your service:**

```typescript
async function initiatePayment(paymentId: string, payload: PaymentPayload) {
  // Use your internal payment ID as the gateway's idempotency key
  const response = await jusPayClient.createOrder({
    order_id: paymentId,   // idempotent: same order_id → same response
    amount: payload.amount,
    currency: 'INR',
    // ...
  });

  // Store the gateway's order_id for all future status checks
  await paymentRepo.updateGatewayOrderId(paymentId, response.order_id);
  return response;
}
```

**Critical:** Always generate the `order_id` / idempotency key on *your* side before calling the gateway. If you let the gateway generate IDs and your service crashes after the gateway call but before you store the ID, you've lost the reference and cannot deduplicate future retries.

**Q13. What happens when a payment gateway call times out? How do you handle the retry safely?**

A: A gateway timeout is the most dangerous failure mode in payment systems. The request may have:
- **Never reached the gateway** — safe to retry with the same idempotency key.
- **Reached the gateway but the response was lost** — the gateway processed the payment; a naive retry would attempt a duplicate charge, but the gateway's idempotency key prevents it and returns the original result.
- **Is still processing at the gateway** — the gateway is in an in-flight state; a retry may return a 202 or a "pending" status.

**Safe retry algorithm:**

```typescript
async function callGatewayWithRetry(
  idempotencyKey: string,
  payload: GatewayPayload,
  maxAttempts = 3,
): Promise<GatewayResponse> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      // Same idempotency key on every attempt
      return await gatewayClient.charge(payload, {
        headers: { 'Idempotency-Key': idempotencyKey },
        timeout: 10_000,
      });
    } catch (err) {
      if (err instanceof TimeoutError || isRetryableError(err)) {
        const backoff = Math.min(1000 * 2 ** attempt, 30_000); // exp backoff, max 30s
        logger.warn({ attempt, idempotencyKey }, 'Gateway call failed — retrying');
        await sleep(backoff);
        continue;
      }
      throw err; // Non-retryable (4xx) — surface immediately
    }
  }
  // After exhausting retries, move to async status polling
  await enqueueStatusCheck(idempotencyKey);
  throw new GatewayTimeoutException('Payment status indeterminate — polling scheduled');
}
```

**After exhausting retries:** Do not mark the payment as failed. Mark it as `pending` and schedule a status-check job that polls the gateway's order status endpoint until the state is terminal (`SUCCESS` or `FAILED`). The `order_id` / idempotency key is your handle for this query.

---

**Q14. What is a "ghost charge," and how do idempotency keys prevent them?**

A: A **ghost charge** (also called a phantom charge) is a charge that appears on a customer's bank statement but is not reflected in the merchant's system — typically because the merchant's database write failed *after* the gateway successfully debited the customer.

**Failure sequence without idempotency protection:**
1. Service calls gateway → success (customer charged).
2. DB write to `payments` table fails (network blip, DB overload).
3. Service retries the full flow — calls gateway again.
4. Gateway processes a second charge (no deduplication).
5. Customer is charged twice; merchant's system shows one payment.

**Prevention:**
- Use the gateway's idempotency key — step 3's retry hits the same key and returns the original charge result without a new debit.
- Use the transactional outbox — the DB write and the event that triggers downstream processing are atomic; partial writes don't produce zombie states.
- Reconcile daily — a reconciliation job that compares your `payments` table against the gateway's settlement report catches any residual mismatches (ghost charges or missing charges) that slipped through.

## Section 5: Failure Modes, Edge Cases & Best Practices

**Q15. What are the key failure modes of an idempotency key implementation, and how do you defend against each?**

A:

| Failure mode | Cause | Defense |
|---|---|---|
| **Duplicate charge despite key** | Key stored in Redis; Redis crashes before response; client retries; new key lookup misses | Use Postgres (durable) as primary store, Redis as cache only |
| **In-flight duplicate** | Two concurrent requests with same key; both pass initial key lookup before either writes | Atomic `INSERT ... ON CONFLICT` or Redis `SET NX`; return 409 to the second |
| **Key reuse across different intents** | Client generates keys with insufficient entropy (e.g., timestamp-based) | Validate payload hash on every request; return 422 on mismatch |
| **Expired key replay** | Client retries after TTL expiry; server treats it as a new request and reprocesses | Set TTL longer than the realistic retry window; log expired key replays for monitoring |
| **Response not persisted before crash** | Server processes payment, crashes before writing response to idempotency store | Store response in same DB transaction as the business write (not as a separate step) |
| **Gateway idempotency key mismatch** | Different internal retries use different keys for the same gateway call | Generate and persist the gateway idempotency key before the first call; always reload it on retry |

---

**Q16. How do you handle idempotency for refunds, which may be issued multiple times for the same original payment?**

A: Refunds are multiply-idempotent: a single payment may legitimately have multiple refunds (partial refunds), but each individual refund initiation must be idempotent.

**Scoping rule:** The idempotency key for a refund must be scoped to the **refund intent**, not the original payment. A good key: `refund:{orderId}:{refundRequestId}` where `refundRequestId` is generated by the client per refund attempt.

**Schema consideration:**
```sql
CREATE TABLE refunds (
    refund_id         UUID PRIMARY KEY,
    payment_id        UUID NOT NULL REFERENCES payments(payment_id),
    idempotency_key   TEXT UNIQUE NOT NULL,
    amount            NUMERIC(12, 2) NOT NULL,
    status            TEXT NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

The `UNIQUE` constraint on `idempotency_key` enforces deduplication at the DB level — a second insert with the same key fails, and the application returns the existing refund record.

**Guard against over-refunding:** Before initiating a refund, check that `SUM(refunds.amount) WHERE payment_id = $1 AND status != 'failed'` does not exceed the original charge amount. This is a business rule check separate from idempotency.

**Q17. How do you test idempotency implementations?**

A: Testing idempotency is a checklist of the scenarios the key is designed to handle:

**Unit tests:**
- Pure logic: given the same idempotency key twice, the handler returns the same response object on the second call without invoking the downstream function.
- Conflict detection: given the same key with a different payload hash, the handler throws a conflict exception.

**Integration tests (with real Postgres + Redis via Testcontainers):**
- First call creates a record and returns a `201`; second call with the same key returns a `200` with the original response body.
- Concurrent calls with the same key (use `Promise.all` with two simultaneous requests): only one creates a charge; the other returns a `409`.
- Expired key: manually set `expires_at` to the past; assert the next call treats it as new.

**Chaos / failure tests:**
- Kill the DB after the gateway call but before the idempotency record is written; verify that a retry re-processes correctly (or fails safely) rather than creating a duplicate.
- This is best done as a narrow integration test with a transaction-scoped DB client that is deliberately rolled back.

**Contract test with gateway sandbox:**
- Send the same `order_id` to JusPay/Razorpay sandbox twice; assert the sandbox returns the same order, not two orders. Confirms your understanding of the gateway's idempotency contract before relying on it in production.

---

**Q18. How does idempotency interact with database transactions? Should the idempotency check and the business write be in the same transaction?**

A: Yes — they must be. If the idempotency key insert and the business write are in separate transactions, a failure window exists between them that creates ghost charges or orphaned idempotency records.

**Correct pattern:**
```typescript
async function createPayment(idempotencyKey: string, payload: PaymentPayload) {
  return await db.transaction(async (trx) => {
    // 1. Atomically claim the key
    const claim = await trx.raw(`
      INSERT INTO idempotency_records (idempotency_key, status, request_hash, expires_at)
      VALUES (?, 'processing', ?, now() + interval '24 hours')
      ON CONFLICT (idempotency_key) DO UPDATE SET idempotency_key = EXCLUDED.idempotency_key
      RETURNING status, response_body
    `, [idempotencyKey, hashPayload(payload)]);

    if (claim.rows[0].status === 'completed') {
      // Replay stored response — do not reprocess
      return claim.rows[0].response_body;
    }

    // 2. Execute business logic
    const gatewayResponse = await paymentGateway.charge(payload);
    const payment = await trx('payments').insert({ ... }).returning('*');

    // 3. Finalize the idempotency record within the same transaction
    await trx('idempotency_records')
      .where({ idempotency_key: idempotencyKey })
      .update({ status: 'completed', response_body: payment[0] });

    return payment[0];
  });
}
```

If the transaction rolls back, both the idempotency record and the business write are rolled back atomically. The next retry finds no record and reprocesses cleanly.

## Section 6: System Design Scenario Questions

**Q19. "Design an idempotent payment initiation API for a lending platform. Walk me through the full request lifecycle."**

A: Full lifecycle for `POST /v1/payments` with `Idempotency-Key: <uuid>`:

```
Client
  │
  ├──[1] Generate UUIDv4 idempotency key (client-side, before request)
  │
  ▼
API Gateway (NestJS)
  │
  ├──[2] Extract Idempotency-Key header; validate format (UUID, length)
  ├──[3] Hash request body: sha256(amount + currency + customerId + purpose)
  │
  ▼
Idempotency Middleware
  │
  ├──[4] BEGIN DB transaction
  ├──[5] INSERT INTO idempotency_records ... ON CONFLICT DO NOTHING
  │       └─ Conflict → load existing record
  │           ├─ status = 'completed' → return stored response (HTTP 200 + original body)
  │           ├─ status = 'processing' → return HTTP 409 (concurrent request in flight)
  │           └─ request_hash mismatch → return HTTP 422 (key reuse with different payload)
  │
  ▼
Payment Service (only reached on first call)
  │
  ├──[6] Validate payload (amount > 0, currency supported, customer KYC'd)
  ├──[7] Reserve amount in ledger (debit hold)
  ├──[8] Call JusPay/Razorpay with order_id = paymentId (gateway idempotency)
  ├──[9] INSERT INTO payments (paymentId, gatewayOrderId, status='PENDING')
  ├──[10] INSERT INTO outbox_events (payment.initiated, payload)
  ├──[11] UPDATE idempotency_records SET status='completed', response_body=payment
  ├──[12] COMMIT transaction
  │
  ▼
Outbox Publisher
  │
  └──[13] Poll outbox → publish to Kafka topic `payments.initiated` → mark published
```

**Retry handling:** Steps 4–12 are a single DB transaction. If the server crashes at any step, the transaction rolls back. The client retries with the same idempotency key; step 5 finds no record (transaction was rolled back) and processes from step 6 again.

**Q20. "Your team is seeing duplicate payments in production. Customers are being charged twice. Walk through how you'd diagnose and fix this."**

A: Structured diagnosis:

**Phase 1 — Contain (same day)**
- Identify the scope: is this affecting all payment methods, one gateway, one client SDK version, or one region? Pull metrics: duplicate `payment_id` count, duplicate gateway `order_id` count.
- If duplicates are actively accruing, check whether the idempotency key middleware is deployed and enabled. A misconfigured feature flag or a middleware not registered in the NestJS app is a common culprit.
- Check for a recent deploy that changed idempotency key generation logic (e.g., switched from UUID to something non-unique like `Date.now()`).

**Phase 2 — Root cause (1–2 days)**
- Pull logs for duplicate gateway `order_id`s. A duplicate gateway order = the gateway was called twice, meaning your service generated two *different* idempotency keys for the same logical intent, or the gateway's idempotency was bypassed.
- Check `idempotency_records` table: does each duplicate payment have one record or two? Two records → the key changed between requests. One record → the record was found but the stored response was ignored (bug in replay logic).
- Check client-side key generation: is the mobile app / partner SDK generating a new key on every retry? (It should reuse the key from the first attempt.)

**Phase 3 — Fix**
- If the client is generating new keys on retry: fix the SDK to persist the key and reuse it. Until the fix ships, add server-side deduplication on `(customerId, amount, currency, createdAt window)` as a heuristic guard.
- If the server is not enforcing idempotency: fix the middleware registration or the feature flag. Add an integration test that makes two identical requests and asserts exactly one DB row.
- Reconcile duplicates: refund the extra charges. Use the gateway's sandbox to verify that your refund flow is also idempotent.

**Phase 4 — Prevent**
- Add a metric: `duplicate_payment_rate = payments_with_same_gateway_order_id / total_payments`. Alert if > 0.
- Add a DB unique constraint on `gateway_order_id` in your `payments` table. This is the last line of defense — even if all middleware fails, the DB constraint will raise an exception rather than silently inserting a duplicate.

**Q21. "How would you implement idempotency for a NACH mandate registration that involves three external systems: your DB, the NPCI gateway, and a notification service?"**

A: NACH mandate registration is a long-running, multi-step flow — classic saga territory. Idempotency must be enforced at each step independently, not just at the entry point.

**Flow:**
```
1. Validate mandate request (sync)
2. Insert mandate record in DB with status = INITIATED
3. Call NPCI gateway to register mandate (async, confirmation via webhook)
4. On NPCI webhook: update mandate status = REGISTERED
5. Call notification service to send SMS/email to customer
```

**Idempotency per step:**

| Step | Idempotency mechanism |
|---|---|
| API entry | Idempotency key in header; stored in `idempotency_records` |
| DB insert (step 2) | `mandate_id` as primary key; `INSERT ... ON CONFLICT DO NOTHING` |
| NPCI call (step 3) | Use your `mandate_id` as the NPCI reference ID; NPCI deduplicates on their end |
| Webhook handler (step 4) | Check `IF mandate.status = 'REGISTERED' THEN skip` before updating; use the transactional outbox to emit the `mandate.registered` event exactly once |
| Notification (step 5) | Notification service should accept an idempotency key; alternatively, check `notifications_sent WHERE mandate_id = $1 AND type = 'mandate_registered'` before sending |

**Saga compensation:** If step 3 fails after step 2 has committed, the mandate sits in `INITIATED` status. A background job polls NPCI for mandates in `INITIATED` status older than 10 minutes and either retrieves the NPCI confirmation (if NPCI processed it) or cancels and resets.

The key insight: **idempotency in a saga is not a single key — it is a state machine.** Each step checks the current state before executing; the state itself is the idempotency record.

## Quick Reference Table

| Property | API Idempotency Key | Consumer Dedup Table | Transactional Outbox |
|---|---|---|---|
| **What it deduplicates** | HTTP retries from client | Kafka/queue message redelivery | Dual-write between DB and broker |
| **Where the key lives** | Request header | Message payload / Kafka key | Outbox table in same DB |
| **Storage** | Redis + Postgres | Postgres (dedicated table) | Postgres (same DB as business tables) |
| **Atomicity boundary** | Same DB transaction as business write | Same DB transaction as business write | Same DB transaction as business write |
| **TTL / cleanup** | 24h–7d (configurable) | Retain for at least consumer's retry window | Retain until published + grace period |
| **Who drives retries** | Client (SDK, mobile app, partner) | Kafka broker / SQS | CDC / polling publisher |
| **Failure it prevents** | Double charge from client retry | Double-process from broker redeliver | Lost event or phantom event |
| **Tools (Node.js)** | `uuid`, Redis `SET NX`, Postgres `INSERT ON CONFLICT` | `INSERT ON CONFLICT DO NOTHING` | Debezium CDC or polling job |

**Tip for the interview:** At the 5 YOE level in a fintech context, idempotency questions surface in three forms: (1) "design a payment API" — they expect you to immediately mention idempotency keys without being prompted; (2) "debug a duplicate charge" — you should diagnose the idempotency layer first before looking elsewhere; (3) "how do you handle Kafka consumer failures" — the answer is always dedup table + transactional outbox. Have a concrete story ready: a real or hypothetical scenario where you added or fixed idempotency and prevented duplicate charges. Know the difference between idempotency at the API layer vs. the consumer layer — many engineers know one but not both. And always anchor your answer to the business consequence: a non-idempotent payment API is not a latency problem, it is a trust, regulatory, and revenue problem.
