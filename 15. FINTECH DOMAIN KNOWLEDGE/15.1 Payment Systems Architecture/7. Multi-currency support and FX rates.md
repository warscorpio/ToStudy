# Multi-Currency Support and FX Rates — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does "multi-currency support" mean in a payment system, and what are the distinct layers it touches?**
A: Multi-currency support means the system can accept, store, process, and settle payments in more than one currency. It is not a single feature — it cuts across every layer of the stack:

| Layer | Multi-currency concern |
|---|---|
| **Data model** | How amounts are stored (integer paise vs decimal dollars vs currency-tagged struct) |
| **FX rate engine** | Where rates come from, how fresh they must be, how they're applied |
| **Payment processing** | Which currencies each gateway supports; DCC (Dynamic Currency Conversion) rules |
| **Ledger / accounting** | Functional currency vs transaction currency; unrealized vs realized FX gain/loss |
| **Reconciliation** | Cross-currency settlement files; bank credits in a different currency than charges |
| **Display / rounding** | Different currencies have different decimal places (JPY: 0, KWD: 3, USD: 2) |
| **Regulatory** | FEMA in India; cross-border payment reporting to RBI; currency control regimes |

A common mistake is to treat multi-currency as only a display concern ("just multiply by a rate before showing the user"). The harder problems are: what rate do you lock in for a transaction, who bears FX risk, and how do you reconcile your ledger when exchange rates shift between charge and settlement?

**Q2. How should monetary amounts be stored in a database when supporting multiple currencies?**
A: Two rules, both non-negotiable:

**Rule 1 — Store as integers in the smallest unit**
Never store monetary amounts as `FLOAT` or `DOUBLE`. Floating-point binary representation cannot exactly represent most decimal fractions:
```
0.1 + 0.2 = 0.30000000000000004  (JavaScript / IEEE 754)
```
For USD, store cents (`$12.50 → 1250`). For INR, store paise (`₹99.00 → 9900`). For JPY, store yen (`¥500 → 500` — no subunit). Use `BIGINT` (PostgreSQL) or `DECIMAL(19,0)` — never `NUMERIC(10,2)` with a decimal point baked in.

**Rule 2 — Always store the currency alongside the amount**
An amount without a currency is meaningless. The correct schema:
```sql
CREATE TABLE payments (
  id            UUID PRIMARY KEY,
  amount        BIGINT NOT NULL,         -- in smallest unit of currency
  currency      CHAR(3) NOT NULL,        -- ISO 4217: 'INR', 'USD', 'EUR', 'JPY'
  -- NEVER: amount DECIMAL(10,2)  ← loses currency context
  -- NEVER: amount_usd FLOAT      ← loses precision AND assumes USD
);
```

**Currency subunit lookup** — store a reference table, not hardcoded logic:
```sql
CREATE TABLE currencies (
  code            CHAR(3) PRIMARY KEY,   -- ISO 4217
  name            TEXT NOT NULL,
  subunit_factor  INT NOT NULL,          -- 100 for USD/INR, 1 for JPY, 1000 for KWD
  symbol          TEXT NOT NULL
);
```

Application-layer helper:
```typescript
// Amount codec — converts between human-readable and storage integer
function toMinorUnits(amount: number, currency: string): bigint {
  const factor = currencySubunitFactor(currency); // e.g., 100 for USD
  return BigInt(Math.round(amount * factor));
}

function toDisplayAmount(minorUnits: bigint, currency: string): string {
  const factor = currencySubunitFactor(currency);
  const decimal = Number(minorUnits) / factor;
  return new Intl.NumberFormat('en', { style: 'currency', currency }).format(decimal);
}
```

**Q3. What is ISO 4217 and what do currency codes, numeric codes, and subunit factors represent?**
A: ISO 4217 is the international standard for currency codes. Every currency has:
- **Alphabetic code** (3 letters) — used in software: `USD`, `INR`, `EUR`, `GBP`, `JPY`, `AED`, `SGD`.
- **Numeric code** (3 digits) — used in financial messaging (SWIFT, ISO 8583): `840` for USD, `356` for INR. Useful when a text field is unavailable.
- **Minor unit** — number of decimal places: `2` for most currencies, `0` for JPY/KRW, `3` for KWD/BHD/OMR.

Critical edge cases for a backend engineer:
- **JPY (Japanese Yen)** — 0 decimal places. `¥500` stored as `500`, not `50000`. A bug that assumes 2 decimal places charges 100× in JPY.
- **KWD (Kuwaiti Dinar)** — 3 decimal places. Subunit factor = 1000. A payment of `KWD 1.500` stores as `1500`.
- **CLF (Chilean Unidad de Fomento)** — 4 decimal places. Exotic but real; appears in Chile-based SaaS contracts.
- **XAU / XAG** — Gold and Silver have ISO 4217 codes (precious metal clearing). You'll see them in commodity trading platforms.
- **INR** — 2 decimal places (paise), subunit factor 100. `₹99.50` = `9950` paise.

**Q4. What is a functional currency, and how does it relate to multi-currency transaction storage?**
A: The **functional currency** is the primary currency in which a business reports its financials — for an Indian company, typically INR; for a US-headquartered SaaS, USD. It's the currency used for your P&L, balance sheet, and tax filings.

When a transaction occurs in a non-functional currency (a US customer paying $50 to an Indian company), two amounts must be stored:
- **Transaction currency amount** — what the customer actually paid: `5000 USD-cents`.
- **Functional currency equivalent** — what it's worth in your books at the time of transaction: `415000 INR-paise` (at the rate on that day).

```sql
CREATE TABLE payments (
  id                      UUID PRIMARY KEY,
  amount                  BIGINT NOT NULL,        -- transaction currency
  currency                CHAR(3) NOT NULL,        -- transaction currency code
  functional_amount       BIGINT,                  -- in functional currency (INR paise)
  functional_currency     CHAR(3) DEFAULT 'INR',
  fx_rate                 NUMERIC(18,8),           -- rate applied at time of transaction
  fx_rate_source          TEXT,                    -- 'rbi_reference', 'xe_api', 'razorpay_rate'
  fx_rate_locked_at       TIMESTAMPTZ              -- when rate was fixed
);
```

Why store `functional_amount` at transaction time? Because exchange rates change. If you only store the transaction-currency amount and compute the INR equivalent at report time, your historical P&L will show different numbers every time you run it — a compliance disaster. The INR equivalent must be **locked at the time of the transaction** (or at invoice date, as per your accounting policy).

**Q5. What is the difference between a mid-market rate, a buy rate, and a sell rate?**
A: Foreign exchange rates come in three flavors, reflecting the perspective of the party quoting them:

| Rate type | Definition | Who uses it |
|---|---|---|
| **Mid-market rate** | The midpoint between buy and sell; no spread; theoretical "fair" rate | Reference rates (XE, ECB, RBI); benchmark for FX markup calculations |
| **Buy rate** | The rate at which a bank/FX provider *buys* foreign currency from you | When you (merchant) receive USD and convert to INR, the bank's buy rate applies |
| **Sell rate** | The rate at which a bank/FX provider *sells* foreign currency to you | When you need to pay out in a foreign currency, the bank's sell rate applies |

The spread (sell rate − buy rate) is the FX provider's profit margin. For a mid-market rate of `USD/INR = 83.50`:
- Buy rate: `83.10` (bank pays you less INR when buying your USD)
- Sell rate: `83.90` (bank charges you more INR when selling you USD)

In payment systems:
- **Display rate** shown to the customer is typically mid-market (for transparency).
- **Applied rate** (what actually executes) includes spread — this is where gateway FX margin lives.
- **RBI reference rate** is the official mid-market rate published daily by Reserve Bank of India; used as the benchmark for regulatory reporting and transfer pricing.

## Section 2: FX Rate Architecture

**Q6. Where do FX rates come from, and how do you architect a rate-fetching service?**
A: Rate sources, ranked by reliability and cost:

| Source | Update frequency | Accuracy | Cost | Use case |
|---|---|---|---|---|
| **ECB (European Central Bank)** | Daily (16:00 CET) | Mid-market reference | Free | Non-critical display; EUR-base pairs |
| **RBI Reference Rate** | Daily (12:00 IST) | Official INR reference | Free | INR pairs; regulatory reporting |
| **Open Exchange Rates** | Hourly | Good | Freemium | Mid-market display at low volume |
| **Fixer.io** | Hourly | Good | Freemium | Same |
| **XE Currency API** | Real-time | Excellent | Paid | Display rates in production |
| **CurrencyBeacon** | Real-time | Excellent | Paid | Production alternative |
| **Bloomberg / Reuters** | Real-time (ms) | Institutional | Very expensive | FX desk; treasury |
| **Payment gateway rates** | Per-transaction | Applied rate (with spread) | Embedded in gateway fee | Actual transaction execution |

**Rate service architecture:**

```typescript
// rates.service.ts — fetches, caches, and serves FX rates
@Injectable()
export class FxRateService {
  constructor(
    private readonly http: HttpService,
    private readonly redis: Redis,
    private readonly db: Knex,
  ) {}

  async getRate(from: string, to: string): Promise<FxRate> {
    const cacheKey = `fx:${from}:${to}`;
    const cached = await this.redis.get(cacheKey);
    if (cached) return JSON.parse(cached);

    const rate = await this.fetchFromProvider(from, to);
    await this.redis.setex(cacheKey, 300, JSON.stringify(rate)); // 5-min TTL
    await this.persistRate(rate); // store in DB for audit/reconciliation
    return rate;
  }

  private async fetchFromProvider(from: string, to: string): Promise<FxRate> {
    const response = await this.http.get(
      `https://api.exchangerate.host/convert?from=${from}&to=${to}`
    ).toPromise();
    return {
      from,
      to,
      rate: response.data.result,
      source: 'exchangerate_host',
      fetchedAt: new Date(),
    };
  }

  private async persistRate(rate: FxRate): Promise<void> {
    await this.db('fx_rates').insert({
      from_currency: rate.from,
      to_currency: rate.to,
      rate: rate.rate,
      source: rate.source,
      fetched_at: rate.fetchedAt,
    });
  }
}
```

**Q7. How do you store historical FX rates, and why is this non-negotiable for fintech?**
A: FX rates must be stored as an append-only time-series — never updated, only inserted. Every rate snapshot must be queryable for any past timestamp.

```sql
CREATE TABLE fx_rates (
  id            BIGSERIAL PRIMARY KEY,
  from_currency CHAR(3) NOT NULL,
  to_currency   CHAR(3) NOT NULL,
  rate          NUMERIC(18, 8) NOT NULL,  -- 8 decimal places: 1 USD = 83.45210000 INR
  source        TEXT NOT NULL,
  fetched_at    TIMESTAMPTZ NOT NULL,
  valid_from    TIMESTAMPTZ NOT NULL,
  valid_until   TIMESTAMPTZ             -- NULL = still current
);

CREATE INDEX idx_fx_rates_pair_time
  ON fx_rates(from_currency, to_currency, valid_from DESC);
```

Query: "what was the USD/INR rate at the time of a payment made on 2024-03-15 14:32:00?"
```sql
SELECT rate FROM fx_rates
WHERE from_currency = 'USD'
  AND to_currency = 'INR'
  AND valid_from <= '2024-03-15 14:32:00'
ORDER BY valid_from DESC
LIMIT 1;
```

Why non-negotiable:
- **Audit and dispute resolution** — if a customer disputes the FX rate applied to their transaction, you must produce the exact rate that was in effect at that moment.
- **Reconciliation** — the INR equivalent of a USD settlement differs from today's rate; you need the historical rate to reconcile correctly.
- **Regulatory reporting** — FEMA and RBI reporting requires the exchange rate applied to each cross-border transaction.
- **Accounting** — your accountant needs the rate at invoice date and at payment date to compute FX gain/loss.

**Q8. How do you handle FX rate staleness? What happens if your rate provider goes down?**
A: Stale rates are a real risk — if your rate feed dies and you serve a 6-hour-old rate, you're mispricing every transaction. Defensive layers:

**Layer 1 — TTL-based staleness detection**
```typescript
async function getRateWithStalenessCheck(from: string, to: string): Promise<FxRate> {
  const rate = await fxRateService.getRate(from, to);
  const ageMs = Date.now() - rate.fetchedAt.getTime();
  const MAX_AGE_MS = 15 * 60 * 1000; // 15 minutes

  if (ageMs > MAX_AGE_MS) {
    logger.warn({ from, to, ageMs }, 'FX rate is stale');
    // Options: throw error, use rate with warning flag, fallback to secondary provider
    throw new StaleRateError(from, to, ageMs);
  }
  return rate;
}
```

**Layer 2 — Provider fallback chain**
```typescript
const PROVIDERS = [primaryProvider, secondaryProvider, rbiReferenceRate];

async function getRateWithFallback(from: string, to: string): Promise<FxRate> {
  for (const provider of PROVIDERS) {
    try {
      return await provider.getRate(from, to);
    } catch (err) {
      logger.warn({ provider: provider.name, err }, 'FX provider failed, trying next');
    }
  }
  throw new NoFxRateAvailableError(from, to);
}
```

**Layer 3 — Circuit breaker on rate provider**
If the primary provider fails 5 consecutive times, open the circuit and route directly to the secondary for 60 seconds. Standard circuit breaker pattern applied to an external HTTP dependency.

**Layer 4 — Conservative fallback for display vs. execution**
- For **display** (showing a customer an indicative price): a stale rate with a warning banner is acceptable.
- For **transaction execution** (locking a rate for a payment): stale rates are unacceptable — fail the transaction and surface a user-visible error rather than execute at a bad rate.

**Q9. What is cross-rate derivation, and when do you need it?**
A: Most FX providers quote rates against a base currency (typically USD or EUR). If you need SGD/JPY and your provider only gives you USD/SGD and USD/JPY, you derive the cross-rate:

```
SGD/JPY = (USD/JPY) / (USD/SGD)
        = 149.50 / 1.3420
        = 111.40
```

In code:
```typescript
async function getCrossRate(from: string, to: string, base: string = 'USD'): Promise<number> {
  if (from === base) return (await getRate(base, to)).rate;
  if (to === base) return 1 / (await getRate(base, from)).rate;

  const [fromToBase, baseToTo] = await Promise.all([
    getRate(base, from),
    getRate(base, to),
  ]);
  return baseToTo.rate / fromToBase.rate;
}
```

Cross-rate risk: each leg introduces spread and precision loss. For a three-way cross (exotic currency pair through two intermediaries), the effective spread compounds — always prefer a direct rate if available from your provider.

## Section 3: FX Application in Payments

**Q10. What is Dynamic Currency Conversion (DCC), and what are the engineering and ethical concerns?**
A: DCC is the practice of offering a foreign cardholder the option to pay in their home currency at the point of sale, rather than the merchant's currency. An Indian merchant charging a US customer in USD instead of INR is DCC.

**How it works technically:**
1. Card BIN lookup identifies the card's home currency (USD for a US Visa).
2. Merchant's gateway applies a real-time FX rate (with markup) to convert from INR to USD.
3. The customer sees a USD amount and approves.
4. The transaction settles in USD; the merchant receives INR.

**Engineering concerns:**
- **BIN database** — requires a current BIN-to-currency mapping. Stale BIN data misidentifies card currency.
- **Rate locking** — the DCC rate must be locked at display time and honored at execution. If 30 seconds pass between quote and execution, the rate cannot change.
- **Fallback** — if BIN lookup fails, default to merchant currency (no DCC).
- **Transparency** — regulatory requirements (PSD2 in EU, RBI guidelines) mandate showing both the transaction currency and home currency amounts, with the FX rate and any markup clearly disclosed.

**Ethical concerns:**
- DCC rates typically carry a 3–8% markup over mid-market, which is much higher than the cardholder's home bank would charge for currency conversion.
- It primarily benefits the merchant/gateway, not the customer.
- Many consumers accidentally accept DCC when they should decline — the "pay in your home currency" prompt feels safer but is usually more expensive.

From an engineering perspective: implement DCC correctly (BIN lookup, rate locking, disclosure), but default-opt the customer out unless they explicitly choose it.

**Q11. How do you handle FX rate locking for a multi-step checkout flow?**
A: A checkout flow takes time — product display, cart review, address entry, payment details. Exchange rates move during this time. The rate shown on the product page may differ from the rate at payment execution.

**Strategy: rate lock with TTL**
```typescript
// When customer reaches checkout / payment page — lock the rate
async function lockFxRate(from: string, to: string, ttlSeconds: number = 900): Promise<LockedRate> {
  const rate = await fxRateService.getRate(from, to);
  const lockId = crypto.randomUUID();

  await redis.setex(
    `fx_lock:${lockId}`,
    ttlSeconds,
    JSON.stringify({ from, to, rate: rate.rate, lockedAt: new Date() })
  );

  return { lockId, rate: rate.rate, expiresAt: addSeconds(new Date(), ttlSeconds) };
}

// At payment execution — validate the lock is still valid
async function executeWithLockedRate(lockId: string, amount: bigint): Promise<Payment> {
  const lock = await redis.get(`fx_lock:${lockId}`);
  if (!lock) throw new RateLockExpiredError('FX rate lock expired — please refresh');

  const { rate } = JSON.parse(lock);
  // Use `rate` for the conversion, not a freshly fetched rate
  return paymentService.create({ amount, fxRate: rate, fxLockId: lockId });
}
```

**TTL choices:**
- **15 minutes** — typical for e-commerce checkout.
- **30 minutes** — subscription checkout (user may be reading T&Cs).
- **24 hours** — invoice-based B2B payments where the customer may take time to approve.
- **Never infinite** — a locked rate must expire; floating exchange rates make infinite locks a liability.

On lock expiry, show the customer a non-blocking notification: "Your price has been refreshed due to exchange rate movement" — refresh the display amount and issue a new lock.

**Q12. How do FX gains and losses appear in a payment system's ledger, and how do you model them?**
A: FX gain/loss arises when the exchange rate at settlement differs from the rate at transaction time.

**Example:**
- Invoice issued: USD 1,000 at rate 83.00 = INR 83,000 (recorded in your books)
- Payment received 10 days later: USD 1,000 at rate 84.50 = INR 84,500 (settled amount)
- **FX gain: INR 1,500** (realized, because payment has been received)

Two types:
- **Unrealized FX gain/loss** — the rate has moved but the transaction hasn't settled yet. Reported at period-end for open receivables/payables.
- **Realized FX gain/loss** — the transaction has settled; the gain/loss is locked in. Goes to P&L.

Ledger entries for the above example:
```
Dr  Bank (INR)           84,500
  Cr  Accounts Receivable (USD equivalent at invoice rate)   83,000
  Cr  FX Gain (realized)                                      1,500
```

Database model:
```sql
CREATE TABLE ledger_entries (
  id                UUID PRIMARY KEY,
  payment_id        UUID REFERENCES payments(id),
  entry_type        TEXT NOT NULL,     -- 'RECEIVABLE', 'SETTLEMENT', 'FX_GAIN', 'FX_LOSS'
  amount            BIGINT NOT NULL,   -- in functional currency (INR paise)
  currency          CHAR(3) NOT NULL,
  fx_rate_applied   NUMERIC(18,8),
  reference_rate    NUMERIC(18,8),     -- invoice-date rate (for FX gain/loss calculation)
  posted_at         TIMESTAMPTZ NOT NULL
);
```

For a fintech platform, FX gain/loss entries are auto-generated by the reconciliation job when a cross-currency payment settles at a different rate than the invoice rate.

## Section 4: Indian Fintech & Regulatory Context

**Q13. What FEMA and RBI rules govern cross-border payments, and what do they mean for your data model?**
A: FEMA (Foreign Exchange Management Act, 1999) governs all foreign exchange transactions in India. Key implications for engineering:

**Permitted currencies for cross-border inward remittance:**
- Payments to Indian merchants from foreign customers must be in a permitted currency (USD, EUR, GBP, JPY, AED, etc.).
- Receipt must be through authorized dealer banks (AD banks) — your payment gateway (Razorpay, Cashfree) acts as the intermediary but must hold an AD license.

**Reporting requirements:**
- Inward remittances above USD 10,000 equivalent must be reported to RBI via the AD bank.
- Your system must maintain: foreign currency amount, INR equivalent, RBI reference rate on transaction date, purpose code (RBI purpose codes: P0101 for software services export, P0108 for maintenance, etc.).
- FEMA requires records to be maintained for 5 years.

**Purpose codes** — every cross-border transaction must carry an RBI purpose code:
```sql
ALTER TABLE payments ADD COLUMN rbi_purpose_code CHAR(5);  -- e.g., 'P0101'
ALTER TABLE payments ADD COLUMN fema_category TEXT;         -- 'CURRENT_ACCOUNT', 'CAPITAL_ACCOUNT'
```

**LRS (Liberalised Remittance Scheme):**
- Indian residents can remit up to USD 250,000 per financial year for permitted purposes.
- Outward payments (Indian company paying foreign vendors) must track against the LRS limit.
- Your system must aggregate annual outward remittances per PAN and block when the limit is approached.

```sql
CREATE TABLE lrs_utilization (
  pan             CHAR(10) NOT NULL,
  financial_year  CHAR(7) NOT NULL,    -- e.g., '2024-25'
  utilized_usd    BIGINT NOT NULL DEFAULT 0,  -- USD cents
  limit_usd       BIGINT NOT NULL DEFAULT 25000000,  -- USD 250,000 in cents
  PRIMARY KEY (pan, financial_year)
);
```

**Q14. How does GST apply to FX conversion fees in India?**
A: This is a frequently missed detail. When an Indian payment gateway charges an FX conversion fee or markup:
- The fee itself is subject to 18% GST.
- The tax point is the service delivery date (when the conversion happens), not the settlement date.
- GST must be reported in GSTR-1 with the correct SAC (Service Accounting Code) for forex services: **9954** (Banking and related financial services).

Engineering implications:
- Store FX fee and GST on FX fee as separate line items in your fee structure.
- Your invoice generation system must break out: transaction amount, FX markup, GST on FX markup, net payable.
- For B2B transactions (your merchant is GST-registered), provide a GST-compliant tax invoice so they can claim input tax credit.

```typescript
interface FxFeeBreakdown {
  transactionAmountINR: bigint;   // in paise
  fxMarkupAmountINR: bigint;      // FX fee in paise
  gstOnFxMarkup: bigint;          // 18% of fxMarkupAmountINR
  totalFeeINR: bigint;            // fxMarkupAmountINR + gstOnFxMarkup
  gstRate: number;                // 0.18
  sacCode: string;                // '9954'
}
```

**Q15. How do multi-currency payouts work for Indian export-oriented SaaS companies, and what infrastructure do they require?**
A: An Indian SaaS company billing customers in USD/EUR/GBP receives inward remittances and must convert to INR (or hold in an EEFC account). The payout infrastructure:

**EEFC (Exchange Earners' Foreign Currency) Account:**
- Authorized dealers allow exporters to hold up to 100% of foreign exchange earnings in an EEFC account without immediate conversion.
- Useful for companies with ongoing foreign currency expenses (AWS bills, contractor payments in USD) — avoids double conversion (USD→INR→USD).
- Your treasury module must model EEFC balances separately from INR balances.

**Payout flow:**
```
Foreign customer pays USD → Gateway collects → AD bank converts to INR (or holds in EEFC)
                                             → INR credited to current account
                                             → NEFT/RTGS to merchant's bank
```

**Multi-currency payout to foreign vendors (AP):**
```
Your INR account → AD bank FX → SWIFT wire → Foreign vendor's bank
```
SWIFT wires require: IBAN (Europe), routing number + account (US), IFSC equivalent for each country, BIC/SWIFT code of recipient bank.

Your `vendor_bank_accounts` table must model all these fields per country:
```sql
CREATE TABLE vendor_bank_accounts (
  id              UUID PRIMARY KEY,
  vendor_id       UUID NOT NULL,
  currency        CHAR(3) NOT NULL,
  country         CHAR(2) NOT NULL,    -- ISO 3166-1 alpha-2
  account_number  TEXT NOT NULL,
  routing_type    TEXT NOT NULL,       -- 'SWIFT', 'IBAN', 'ACH', 'IFSC'
  routing_value   TEXT NOT NULL,       -- the actual SWIFT/IBAN/routing number
  bank_name       TEXT,
  is_verified     BOOLEAN NOT NULL DEFAULT FALSE
);
```

## Section 5: Rounding, Precision & Display

**Q16. What are the rounding rules for FX conversion and why does getting them wrong cause reconciliation failures?**
A: FX conversion involves multiplying two numbers (amount × rate) and rounding to the target currency's subunit precision. The rounding rule matters because:
- Different rounding rules (round-half-up, round-half-even/banker's rounding, truncate) produce different results for the same input.
- A systematic bias (always rounding up) accumulates across millions of transactions and creates a discrepancy between your ledger total and the gateway settlement total.

**Correct approach — banker's rounding (round-half-to-even):**
```typescript
function convertAmount(
  amount: bigint,         // source currency minor units
  rate: number,           // exchange rate (e.g., 83.45)
  sourceFactor: number,   // subunit factor of source currency (100 for USD)
  targetFactor: number,   // subunit factor of target currency (100 for INR)
): bigint {
  // Work in high-precision arithmetic to avoid intermediate rounding
  const sourceDecimal = Number(amount) / sourceFactor;   // e.g., 10.00 USD
  const targetDecimal = sourceDecimal * rate;             // e.g., 834.5 INR
  const targetMinorUnits = targetDecimal * targetFactor;  // e.g., 83450 paise

  // Banker's rounding: 0.5 rounds to nearest even number
  return BigInt(Math.round(targetMinorUnits)); // JS Math.round uses round-half-away-from-zero
  // For strict banker's rounding, use a Decimal library (decimal.js, big.js)
}
```

In production, use `decimal.js` or `big.js` for all FX arithmetic — never native JavaScript floating-point:
```typescript
import Decimal from 'decimal.js';

function convertAmountDecimal(amount: bigint, rate: string, targetFactor: number): bigint {
  const result = new Decimal(amount.toString())
    .mul(new Decimal(rate))
    .toDecimalPlaces(0, Decimal.ROUND_HALF_EVEN);
  return BigInt(result.toString());
}
```

**Q17. How do you display multi-currency amounts correctly across locales?**
A: Currency display is deceptively complex — the same amount formats differently by locale:

| Currency | en-US | de-DE | hi-IN | ja-JP |
|---|---|---|---|---|
| USD 1,234.56 | $1,234.56 | 1.234,56 $ | $1,234.56 | $1,234.56 |
| EUR 1,234.56 | €1,234.56 | 1.234,56 € | €1,234.56 | €1,234.56 |
| INR 1,234.56 | ₹1,234.56 | 1.234,56 ₹ | ₹1,234.56 | ₹1,234.56 |
| JPY 1,235 | ¥1,235 | 1.235 ¥ | ¥1,235 | ¥1,235 |

Use the platform's `Intl.NumberFormat` API — never build a formatter manually:
```typescript
function formatCurrency(minorUnits: bigint, currency: string, locale: string): string {
  const factor = getCurrencySubunitFactor(currency);
  const amount = Number(minorUnits) / factor;

  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency,
    minimumFractionDigits: getCurrencyDecimalPlaces(currency),
    maximumFractionDigits: getCurrencyDecimalPlaces(currency),
  }).format(amount);
}

// Usage
formatCurrency(124500n, 'INR', 'hi-IN');  // ₹1,245.00
formatCurrency(124500n, 'USD', 'en-US');  // $1,245.00
formatCurrency(1245n,   'JPY', 'ja-JP');  // ¥1,245
```

**Never** display the raw minor unit integer to users — `124500` instead of `₹1,245.00` is a data breach-level UX failure that has resulted in real customer support crises.

## Section 6: Scenario / System Design Questions

**Q18. "Design a multi-currency pricing engine for a B2B SaaS with monthly invoicing."**
A: Requirements: customers in 30+ countries, prices set in USD, invoiced in local currency, FX rate locked monthly.

**Data model:**

```sql
-- Price catalog in functional currency (USD)
CREATE TABLE product_prices (
  id          UUID PRIMARY KEY,
  product_id  UUID NOT NULL,
  amount_usd  BIGINT NOT NULL,   -- USD cents
  billing_cycle TEXT NOT NULL,   -- 'monthly', 'annual'
  valid_from  DATE NOT NULL,
  valid_until DATE
);

-- Monthly FX rate snapshot — locked on 1st of each month
CREATE TABLE monthly_fx_snapshots (
  snapshot_month DATE NOT NULL,         -- first day of month, e.g., 2024-03-01
  from_currency  CHAR(3) NOT NULL,      -- 'USD'
  to_currency    CHAR(3) NOT NULL,
  rate           NUMERIC(18,8) NOT NULL,
  source         TEXT NOT NULL,
  PRIMARY KEY (snapshot_month, from_currency, to_currency)
);

-- Invoice in customer's local currency
CREATE TABLE invoices (
  id                UUID PRIMARY KEY,
  customer_id       UUID NOT NULL,
  billing_month     DATE NOT NULL,
  currency          CHAR(3) NOT NULL,      -- customer's billing currency
  amount_local      BIGINT NOT NULL,        -- in local minor units
  amount_usd        BIGINT NOT NULL,        -- for reporting
  fx_rate           NUMERIC(18,8) NOT NULL, -- rate applied (from monthly_fx_snapshots)
  fx_snapshot_month DATE NOT NULL
);
```

**Invoice generation job (runs on 1st of month):**
```typescript
async function generateMonthlyInvoices(billingMonth: Date) {
  // Step 1: lock FX rates for this month
  const currencies = await db('customers').distinct('billing_currency');
  for (const { billing_currency } of currencies) {
    if (billing_currency === 'USD') continue;
    const rate = await fxRateService.getRate('USD', billing_currency);
    await db('monthly_fx_snapshots').insert({
      snapshot_month: startOfMonth(billingMonth),
      from_currency: 'USD',
      to_currency: billing_currency,
      rate: rate.rate,
      source: rate.source,
    });
  }

  // Step 2: generate invoices using locked rates
  const customers = await db('customers').where({ billing_active: true });
  for (const customer of customers) {
    const priceUsd = await getEffectivePrice(customer.product_id, billingMonth);
    const rate = await getMonthlySnapshot('USD', customer.billing_currency, billingMonth);
    const localAmount = convertAmount(priceUsd, rate, 100, getCurrencySubunitFactor(customer.billing_currency));

    await db('invoices').insert({
      customer_id: customer.id,
      billing_month: startOfMonth(billingMonth),
      currency: customer.billing_currency,
      amount_local: localAmount,
      amount_usd: priceUsd,
      fx_rate: rate,
      fx_snapshot_month: startOfMonth(billingMonth),
    });
  }
}
```

**Key design decisions:**
- Rates are locked on the 1st of the month — customers know the exact rate upfront; no mid-month surprises.
- `amount_usd` stored alongside `amount_local` — enables USD-denominated revenue reporting without re-querying rates.
- Historical rates are immutable — re-running the invoice generator always produces the same result.

**Q19. "Your reconciliation job is showing a ₹50,000 discrepancy between your ledger and the bank settlement for USD transactions. How do you debug it?"**
A: Systematic decomposition:

**Step 1 — Scope the discrepancy (15 minutes)**
```sql
-- How many transactions are in scope?
SELECT COUNT(*), SUM(amount), currency
FROM payments
WHERE currency = 'USD'
  AND status = 'SUCCESS'
  AND DATE(updated_at) = '2024-03-15'  -- settlement date
GROUP BY currency;

-- Compare to settlement file total
SELECT SUM(settled_amount_inr) FROM gateway_settlement_file
WHERE settlement_date = '2024-03-15';
```

Determine: is the discrepancy in the *count* of transactions (missing transactions) or the *amount* per transaction (wrong rate applied)?

**Step 2 — Identify the rate mismatch pattern**
```sql
-- For each USD transaction, compare your recorded rate vs gateway's applied rate
SELECT
  p.id,
  p.amount AS amount_usd_cents,
  p.functional_amount AS your_inr_paise,
  p.fx_rate AS your_rate,
  sf.settled_amount_inr AS gateway_inr_paise,
  sf.fx_rate AS gateway_rate,
  (sf.settled_amount_inr - p.functional_amount) AS discrepancy_paise
FROM payments p
JOIN gateway_settlement_file sf ON sf.gateway_payment_id = p.gateway_payment_id
WHERE p.currency = 'USD'
  AND p.status = 'SUCCESS'
  AND ABS(sf.settled_amount_inr - p.functional_amount) > 100  -- > ₹1 discrepancy
ORDER BY discrepancy_paise DESC;
```

**Step 3 — Root cause branches**

*Your rate ≠ gateway rate*: Expected and normal — your system used the rate at checkout time; the gateway applied their rate at settlement time. The question is whether the difference is within tolerance and whether you're booking the right amount. Fix: book the gateway-settled INR amount as the realized amount; record the difference as FX gain/loss.

*Transaction in your DB not in settlement file*: Possible webhook miss — payment shows SUCCESS in your DB but gateway hasn't settled it yet. Check `gateway_payment_id` against gateway dashboard. May be in next day's settlement batch.

*Transaction in settlement file not in your DB*: Most dangerous — gateway settled a payment your system has no record of. Could be a ghost payment, a webhook that failed to write to DB, or a duplicate in the gateway. Escalate immediately.

*Rounding errors accumulated*: 500 transactions each off by ₹0.10 = ₹50 discrepancy. Check your rounding function — likely using JavaScript float arithmetic instead of a Decimal library.

**Step 4 — Fix and prevent**
- Apply FX gain/loss entries for legitimate rate differences.
- Fix rounding: migrate `amount * rate` calculations to `decimal.js`.
- Add monitoring: alert if daily reconciliation discrepancy exceeds ₹1,000 or 0.1% of settlement value.

**Q20. "A customer complains they were charged a different amount than what was shown at checkout. Walk through all the possible causes."**
A: This is a cross-layer debugging problem. Possible causes in order of likelihood:

**1. FX rate drift between display and execution**
Rate shown at product display was fetched at T=0; payment executed at T=12 minutes. If no rate lock was implemented, the live rate at T=12 was used — a 0.3% move in 12 minutes is normal for volatile pairs.
Fix: implement rate locking (Q11); show the locked rate and its expiry time to the customer.

**2. DCC applied unexpectedly**
Customer saw a USD price; at payment, the gateway offered DCC and converted to their card's home currency (EUR) at a rate with a 4% markup. Customer expected USD charge; saw EUR charge on their statement.
Fix: disable DCC by default; require explicit customer opt-in.

**3. Bank FX conversion on top of gateway FX**
Customer has a non-USD card in a USD-priced checkout. The gateway charges in USD; the customer's issuing bank then converts USD to their local currency at yet another rate (with the bank's own spread). Two FX conversions applied.
Fix: this is expected behavior, not a bug — but requires clear disclosure at checkout ("You will be charged USD X; your bank may apply additional conversion fees").

**4. Rounding difference**
The displayed amount was rounded to 2 decimal places; the charged amount used a different rounding method. On large amounts or exotic currency pairs, this can be a visible difference.
Fix: use identical rounding logic in the display layer and the payment execution layer.

**5. Promotional discount race condition**
A discount was applied at display time but not re-validated at checkout; the promotion expired between display and payment. Customer sees the promotional price but is charged full price.
Fix: re-validate discounts at payment execution, not just at cart add.

**6. Tax applied at execution not at display**
GST or VAT was not included in the displayed price but was added at checkout. Common in B2C where prices are shown ex-tax.
Fix: establish and communicate clearly whether displayed prices are inclusive or exclusive of tax; apply consistently.
