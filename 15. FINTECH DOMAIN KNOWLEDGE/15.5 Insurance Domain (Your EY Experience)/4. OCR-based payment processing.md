## Section 1: Fundamentals

**Q1. What is OCR, and why does fintech rely on it so heavily?**

A: **OCR (Optical Character Recognition)** is the process of converting images of text — photographs of documents, scanned PDFs, screenshots — into machine-readable strings. At its core it is a computer vision task: the model must detect character regions in an image, classify each region as a character, and assemble characters into words, words into lines, and lines into structured fields.

Fintech relies on OCR heavily for a specific structural reason: the financial world runs on documents — cheques, demand drafts, utility bills, bank statements, salary slips, ITRs, PAN cards, Aadhaar cards, GST invoices, NACH mandate forms — and most of these documents arrive from customers as photographs or scans taken on mobile phones. Manual data entry from these documents is:

- **Slow:** A human operator reading a bank statement to extract 12 months of transactions takes 20–40 minutes. OCR does it in seconds.
- **Expensive:** At scale, manual data entry requires large ops teams. OCR reduces headcount or eliminates the need entirely.
- **Error-prone:** Manual entry has a ~1–3% error rate on structured documents. OCR on high-quality images can achieve < 0.1% character error rate.
- **A bottleneck:** Loan underwriting pipelines where a human must read each document before approval cannot scale to millions of applications. OCR enables straight-through processing.

The specific payment-relevant use cases:

- **Cheque processing:** Extract payee name, amount (in words and figures), date, MICR code, account number, IFSC.
- **Bank statement analysis:** Extract transaction rows, dates, amounts, balances, categorise transactions for credit assessment.
- **KYC document extraction:** Extract name, date of birth, PAN number, Aadhaar number, address from identity documents.
- **Invoice processing:** Extract vendor name, GST number, invoice number, line items, total amount for B2B payment automation.
- **Salary slip extraction:** Extract gross salary, net salary, employer name, employee ID for income verification.
- **NACH mandate OCR:** Extract account number, IFSC, MICR, customer name from physically signed mandate forms.

**Q2. What is the difference between template-based OCR, zonal OCR, and AI-based document understanding?**

A: These represent three generations of OCR technology with fundamentally different architectures and accuracy profiles:

**Template-based OCR (1st generation):**

Relies on the document having a fixed, known layout. Coordinates of each field are hardcoded — "the account number is always at pixel coordinates (x1, y1) to (x2, y2)." The OCR engine crops each region and extracts text.

```
Advantages: Fast, deterministic, no ML model needed, easy to audit.
Disadvantages: Breaks on any layout variation — a different bank's cheque book,
               a slightly rotated scan, a different year's ITR format.
               Requires a separate template per document type per issuer.
               Completely fails on unstructured or semi-structured documents.

Use when: you control the document format entirely
          (e.g., your own platform generates the document you later receive).
```

**Zonal OCR (2nd generation):**

Adds intelligent region detection — the engine uses heuristics, rules, or lightweight classifiers to locate fields without fixed coordinates. It understands that "the PAN number is a 10-character alphanumeric string that follows the label 'PAN:'."

```
Advantages: More robust to layout variation within a document type.
            Can handle different templates of the same document (ITR-1 vs ITR-2).
Disadvantages: Still requires rule engineering per document type.
               Fails on novel layouts, rotated/skewed documents,
               and low-quality images (blur, shadow, crease).

Use when: document types are known and finite; layout variations are limited.
```

**AI-based document understanding (3rd generation — current standard):**

Uses deep learning models — typically a combination of computer vision (for layout analysis) and NLP (for semantic understanding of extracted text). Models like LayoutLM, Donut, and commercial APIs (Google Document AI, AWS Textract, Azure Form Recognizer) understand both the visual layout and the semantic meaning of document regions.

```
Architecture:
  1. Document layout analysis: detect text regions, tables, checkboxes, signatures
  2. Text recognition: OCR within each detected region
  3. Key-value extraction: identify which text is a label and which is its value
  4. Table extraction: reconstruct tabular data with row/column structure
  5. Entity normalisation: "Jan 15, 2024" → { date: "2024-01-15" }

Advantages: Works across layouts; robust to moderate image quality issues;
            can handle previously unseen document formats.
Disadvantages: Higher latency (200ms–5s per document);
               requires careful post-processing and validation;
               model confidence scores must be thresholded correctly;
               hallucination risk (model "fills in" characters it cannot see).
```

**The hallucination problem** is specific to neural OCR and critical for payments: a model trained to expect a 10-digit account number may confidently predict "0987654321" for a blurry region that is actually illegible. The model's confidence score may still be high. This is why OCR output in payment processing must never be used without downstream validation.

**Q3. What are the key quality metrics for an OCR system in a payment context?**

A: Standard OCR metrics measure character or word accuracy. Payment OCR requires additional metrics that capture the cost of errors on specific fields.

**Standard metrics:**

```
Character Error Rate (CER):
  CER = (Substitutions + Insertions + Deletions) / Total characters in ground truth
  Target for payment-grade OCR: CER < 0.5% on clean documents

Word Error Rate (WER):
  WER = (Substituted words + Inserted words + Deleted words) / Total words
  Less useful for payments (a single wrong digit in an account number = full field error)

Field Accuracy Rate:
  For each field (account_number, amount, ifsc):
  Field Accuracy = Correct extractions / Total extractions
  Target: > 99% for critical payment fields (account number, amount)
          > 95% for reference fields (payee name, date)
```

**Payment-specific metrics:**

```typescript
interface OCRQualityMetrics {
  // Per-field accuracy (most important for payments)
  fieldAccuracy: {
    accountNumber:  number;    // target: > 99.5%
    ifscCode:       number;    // target: > 99.5%
    amount:         number;    // target: > 99.9% (errors here = financial loss)
    amountInWords:  number;    // target: > 98%
    payeeName:      number;    // target: > 97%
    date:           number;    // target: > 99%
    micrCode:       number;    // target: > 99.5%
  };

  // Straight-through processing (STP) rate:
  // % of documents processed without human intervention
  // Target: > 85% for bank statements, > 95% for printed cheques
  stpRate: number;

  // Confidence calibration: when model says 95% confidence, is it right 95% of the time?
  // Poorly calibrated models make wrong thresholding decisions
  confidenceCalibrationScore: number;

  // Rejection rate: % of documents sent for manual review
  // Too high = defeats the purpose; too low = errors slip through
  rejectionRate: number;    // target: < 10% for good-quality document sources

  // False acceptance rate:
  // % of incorrect extractions that passed confidence threshold and were not caught
  // This is the dangerous metric — errors that your system accepted as correct
  falseAcceptanceRate: number;   // target: < 0.1% for amount fields
}
```

**The amount field requires special treatment:** A 1% error rate on a ₹10,00,000 cheque means ₹10,000 wrong. Amounts extracted by OCR must be validated against amounts in words (when present), against the MICR amount encoding, and against business-rule ranges (loan repayment cannot exceed outstanding balance).

## Section 2: Cheque OCR Processing

**Q4. Walk through the complete OCR processing pipeline for a cheque payment.**

A: Cheque processing is the canonical OCR-in-payments use case. A cheque contains multiple fields that must all be correctly extracted and cross-validated for the payment to proceed.

**Cheque anatomy — fields to extract:**

```
┌─────────────────────────────────────────────────────────────────────┐
│  BANK NAME                                    Date: __ / __ / ____  │
│                                                                     │
│  Pay to __________________________________________________ or Bearer│
│                                                                     │
│  Rupees (in words): ____________________________________________    │
│                                                                     │
│  ₹ ________________                                                 │
│                                                                     │
│  A/c No: ________________   IFSC: __________                       │
│                                                                     │
│  ┌──────────────────┐                                               │
│  │   MICR BAND      │   [Signature]                                 │
│  │ 000000 ∶ 000000 ∶│                                               │
│  └──────────────────┘                                               │
└─────────────────────────────────────────────────────────────────────┘

Fields:
  - payee_name: string
  - date: Date (DD/MM/YYYY)
  - amount_figures: bigint (paise)
  - amount_words: string
  - account_number: string (9–18 digits)
  - ifsc_code: string (11 chars)
  - micr_code: string (9 digits: cheque no + bank code + account no)
  - bank_name: string
  - has_bearer_cancelled: boolean (if "Bearer" is struck through → account payee only)
```

**Pipeline stages:**

```typescript
interface ChequeOCRResult {
  rawExtractions:   RawExtraction[];    // raw OCR output per field
  normalised:       NormalisedCheque;   // cleaned, parsed fields
  validationResult: ValidationResult;   // cross-field and rule validations
  confidence:       FieldConfidence;    // per-field confidence scores
  processingDecision: 'STP' | 'MANUAL_REVIEW' | 'REJECT';
  rejectionReasons: string[];
}

async function processChequeImage(
  imageBuffer: Buffer,
  chequeId:    string,
): Promise<ChequeOCRResult> {

  // Stage 1: Image pre-processing
  const preprocessed = await preprocessImage(imageBuffer, {
    deskew:       true,    // correct rotation up to ±15°
    denoise:      true,    // remove scan noise
    binarise:     true,    // convert to black/white for better OCR
    enhanceContrast: true,
    targetDPI:    300,     // resample to 300 DPI if below
  });

  // Stage 2: Document classification
  const docClass = await classifyDocument(preprocessed);
  if (docClass.type !== 'CHEQUE' || docClass.confidence < 0.90) {
    throw new DocumentClassificationError(
      `Expected CHEQUE, got ${docClass.type} with confidence ${docClass.confidence}`
    );
  }

  // Stage 3: Layout analysis and field detection
  const layout = await detectChequeLayout(preprocessed);
  // Returns: bounding boxes for each field region

  // Stage 4: OCR per field region
  const rawExtractions = await Promise.all([
    extractField(preprocessed, layout.payeeName,     'PAYEE_NAME'),
    extractField(preprocessed, layout.date,          'DATE'),
    extractField(preprocessed, layout.amountFigures, 'AMOUNT_FIGURES'),
    extractField(preprocessed, layout.amountWords,   'AMOUNT_WORDS'),
    extractField(preprocessed, layout.accountNumber, 'ACCOUNT_NUMBER'),
    extractField(preprocessed, layout.ifscCode,      'IFSC_CODE'),
    extractMICR(preprocessed,  layout.micrBand),     // special MICR font reader
  ]);

  // Stage 5: Normalisation
  const normalised = normaliseExtractions(rawExtractions);

  // Stage 6: Cross-field validation
  const validationResult = validateCheque(normalised);

  // Stage 7: Confidence thresholding and routing decision
  const decision = makeProcessingDecision(normalised, validationResult);

  // Stage 8: Audit logging
  await logChequeProcessing(chequeId, rawExtractions, normalised, validationResult, decision);

  return { rawExtractions, normalised, validationResult, confidence: computeConfidence(rawExtractions), processingDecision: decision.decision, rejectionReasons: decision.reasons };
}
```

**Q5. How do you normalise raw OCR output into structured payment fields?**

A: Raw OCR output is messy text — the model outputs what it sees, including OCR errors, formatting variations, noise characters, and encoding inconsistencies. Normalisation converts this into clean, typed, validated payment data.

**Amount normalisation (most critical):**

```typescript
function normaliseAmount(rawText: string): bigint | null {
  if (!rawText || rawText.trim() === '') return null;

  // Remove common OCR noise characters
  let cleaned = rawText
    .replace(/[^\d.,\s]/g, '')   // remove non-numeric chars except . and ,
    .replace(/\s+/g, '')          // remove whitespace
    .trim();

  // Handle Indian number format: 1,00,000.50 → 100000.50
  // Also handle European format confusion: 1.00.000,50 (rare but occurs)
  const hasIndianFormat = /^\d{1,2}(,\d{2})*,\d{3}(\.\d{1,2})?$/.test(cleaned)
                       || /^\d{1,3}(,\d{3})*(\.\d{1,2})?$/.test(cleaned);

  // Remove commas (thousand separators)
  cleaned = cleaned.replace(/,/g, '');

  // Parse to decimal — use Decimal.js to avoid float errors
  const decimal = new Decimal(cleaned);

  // Convert to paise (smallest unit)
  const paise = decimal.mul(100).toDecimalPlaces(0, Decimal.ROUND_HALF_UP);

  // Sanity range check — reject obviously wrong extractions
  const MIN_CHEQUE_PAISE = 100n;          // ₹1 minimum
  const MAX_CHEQUE_PAISE = 100_000_000_00n;  // ₹10 crore maximum
  const paiseValue = BigInt(paise.toFixed(0));

  if (paiseValue < MIN_CHEQUE_PAISE || paiseValue > MAX_CHEQUE_PAISE) {
    return null;  // out of range — flag for review
  }

  return paiseValue;
}

// Amount in words → paise (for cross-validation)
function normaliseAmountWords(rawText: string): bigint | null {
  const text = rawText.toLowerCase().trim();

  // Build a parser for Indian English number words
  const UNITS = {
    'zero': 0n, 'one': 1n, 'two': 2n, 'three': 3n, 'four': 4n,
    'five': 5n, 'six': 6n, 'seven': 7n, 'eight': 8n, 'nine': 9n,
    'ten': 10n, 'eleven': 11n, 'twelve': 12n, 'thirteen': 13n,
    'fourteen': 14n, 'fifteen': 15n, 'sixteen': 16n, 'seventeen': 17n,
    'eighteen': 18n, 'nineteen': 19n,
    'twenty': 20n, 'thirty': 30n, 'forty': 40n, 'fifty': 50n,
    'sixty': 60n, 'seventy': 70n, 'eighty': 80n, 'ninety': 90n,
  };
  const MULTIPLIERS = {
    'hundred': 100n, 'thousand': 1000n, 'lakh': 100_000n,
    'lac': 100_000n, 'crore': 10_000_000n,
  };

  // Handle common OCR errors in words
  const corrected = text
    .replace(/\brupees?\b/gi, '')
    .replace(/\bonly\b/gi, '')
    .replace(/\band\b/gi, '')
    .replace(/\bpaise?\b/gi, '')
    // Common OCR confusions in English amount words
    .replace(/\bthousnad\b/gi, 'thousand')
    .replace(/\bhundred\b/gi, 'hundred')
    .replace(/\blakhs?\b/gi, 'lakh');

  // Parse the corrected text into a paise value
  return parseAmountWords(corrected, UNITS, MULTIPLIERS);
}
```

**IFSC normalisation:**

```typescript
function normaliseIFSC(rawText: string): string | null {
  // Remove all non-alphanumeric characters
  let cleaned = rawText.toUpperCase().replace(/[^A-Z0-9]/g, '');

  // IFSC format: 4 alpha + '0' + 6 alphanumeric = 11 chars
  // Common OCR errors: O↔0, I↔1, l↔1, S↔5, B↔8, G↔6

  // Apply character correction for known OCR confusions in IFSC context
  // Position 4 must be '0' — correct common OCR mistakes at that position
  if (cleaned.length === 11) {
    const chars = cleaned.split('');
    if (chars[4] !== '0') {
      // Position 4 is always the digit zero
      const corrected = chars[4]
        .replace('O', '0')  // letter O → digit 0
        .replace('D', '0')  // D → 0 (rare)
        .replace('Q', '0'); // Q → 0 (rare)
      chars[4] = corrected;
    }
    cleaned = chars.join('');
  }

  // Validate against IFSC format regex
  if (!/^[A-Z]{4}0[A-Z0-9]{6}$/.test(cleaned)) return null;

  // Validate against known IFSC database (look up in pre-loaded map)
  if (!ifscDatabase.isValidIFSC(cleaned)) return null;

  return cleaned;
}
```

**Date normalisation:**

```typescript
function normaliseDate(rawText: string): Date | null {
  // Cheques have dates in DD/MM/YYYY, DD-MM-YYYY, DD.MM.YYYY formats
  const separators = /[\/\-\.]/;
  const parts = rawText.trim().split(separators);

  if (parts.length !== 3) return null;

  let [day, month, year] = parts.map(p => parseInt(p.replace(/\D/g, ''), 10));

  // Fix 2-digit year: 24 → 2024 (valid cheques are typically within ±1 year)
  if (year < 100) year = year >= 0 && year <= 30 ? 2000 + year : 1900 + year;

  // Validate ranges
  if (month < 1 || month > 12) return null;
  if (day < 1 || day > 31)     return null;
  if (year < 2000 || year > 2030) return null;  // sanity range for cheques

  const date = new Date(year, month - 1, day);

  // Detect stale cheques: cheques are valid for 3 months in India
  const threeMonthsAgo = subMonths(new Date(), 3);
  if (date < threeMonthsAgo) {
    return null;  // stale cheque — flag for rejection, not normalisation failure
  }

  return date;
}
```

**Q6. What cross-field validations must you run on a cheque before accepting it for payment?**

A: OCR extracts fields independently. Cross-field validation checks that the extracted fields are internally consistent and satisfy payment rules. A cheque that passes OCR may still fail cross-field validation.

```typescript
interface ValidationResult {
  isValid:  boolean;
  errors:   ValidationError[];
  warnings: ValidationWarning[];
}

function validateCheque(cheque: NormalisedCheque): ValidationResult {
  const errors:   ValidationError[]   = [];
  const warnings: ValidationWarning[] = [];

  // Rule 1: Amount in figures vs. amount in words must match
  if (cheque.amountFiguresPaise !== null && cheque.amountWordsPaise !== null) {
    const diff = cheque.amountFiguresPaise > cheque.amountWordsPaise
      ? cheque.amountFiguresPaise - cheque.amountWordsPaise
      : cheque.amountWordsPaise   - cheque.amountFiguresPaise;
    const tolerance = 0n;  // zero tolerance for amount mismatch

    if (diff > tolerance) {
      errors.push({
        code:    'AMOUNT_MISMATCH',
        message: `Amount in figures (${cheque.amountFiguresPaise} paise) does not match ` +
                 `amount in words (${cheque.amountWordsPaise} paise)`,
        severity: 'CRITICAL',
        fields:  ['amount_figures', 'amount_words'],
      });
    }
  }

  // Rule 2: MICR cheque number must match the cheque number on the body
  if (cheque.micrChequeNumber && cheque.bodyChequeNumber) {
    if (cheque.micrChequeNumber !== cheque.bodyChequeNumber) {
      errors.push({
        code:    'CHEQUE_NUMBER_MISMATCH',
        message: 'MICR cheque number does not match printed cheque number',
        severity: 'CRITICAL',
        fields:  ['micr_code', 'cheque_number'],
      });
    }
  }

  // Rule 3: MICR bank code must be consistent with IFSC bank code
  if (cheque.ifscCode && cheque.micrBankCode) {
    const ifscBankCode = cheque.ifscCode.substring(0, 4);
    const expectedMICRBankCode = ifscToMICRBankCode(ifscBankCode);
    if (expectedMICRBankCode && cheque.micrBankCode !== expectedMICRBankCode) {
      errors.push({
        code:    'BANK_CODE_MISMATCH',
        message: 'MICR bank code inconsistent with IFSC bank code',
        severity: 'CRITICAL',
      });
    }
  }

  // Rule 4: Date must not be stale (> 3 months old) or post-dated beyond acceptable window
  if (cheque.date) {
    const today = new Date();
    const threeMonthsAgo = subMonths(today, 3);
    const sixMonthsAhead = addMonths(today, 6);

    if (cheque.date < threeMonthsAgo) {
      errors.push({ code: 'STALE_CHEQUE', message: 'Cheque is more than 3 months old', severity: 'CRITICAL' });
    }
    if (cheque.date > sixMonthsAhead) {
      warnings.push({ code: 'FAR_FUTURE_DATE', message: 'Cheque date is more than 6 months in the future' });
    }
  }

  // Rule 5: Account number format must be valid for the given bank (IFSC)
  if (cheque.accountNumber && cheque.ifscCode) {
    const bankCode = cheque.ifscCode.substring(0, 4);
    const expectedLength = BANK_ACCOUNT_LENGTHS[bankCode];
    if (expectedLength && cheque.accountNumber.length !== expectedLength) {
      warnings.push({
        code:    'ACCOUNT_NUMBER_LENGTH',
        message: `Account number length ${cheque.accountNumber.length} unusual for bank ${bankCode} (expected ${expectedLength})`,
      });
    }
  }

  // Rule 6: Amount must be positive and within policy limits
  if (cheque.amountFiguresPaise !== null) {
    if (cheque.amountFiguresPaise <= 0n) {
      errors.push({ code: 'INVALID_AMOUNT', message: 'Amount must be positive', severity: 'CRITICAL' });
    }
    // Business rule: cheques > ₹1 crore require additional verification
    if (cheque.amountFiguresPaise > 1_00_00_000_00n) {
      warnings.push({ code: 'HIGH_VALUE_CHEQUE', message: 'Cheque exceeds ₹1 crore — requires enhanced verification' });
    }
  }

  // Rule 7: Payee name must not be blank (blank payees = bearer cheques = high risk)
  if (!cheque.payeeName || cheque.payeeName.trim() === '') {
    errors.push({ code: 'MISSING_PAYEE', message: 'Payee name is blank', severity: 'HIGH' });
  }

  return {
    isValid: errors.filter(e => e.severity === 'CRITICAL').length === 0,
    errors,
    warnings,
  };
}
```

**Q7. What is MICR, and why does it matter for cheque OCR?**

A: **MICR (Magnetic Ink Character Recognition)** is a technology developed in the 1950s for machine-reading the ink-printed band at the bottom of cheques. MICR characters are printed in a special font (E-13B in the US/India; CMC-7 in Europe) using ink that contains iron oxide particles — making the characters readable both optically and magnetically.

**India MICR code format (9 digits):**

```
123456 ∶ 789012 ∶ 345678 9
│         │         │      │
│         │         │      └── Transaction code (1 digit): 0=cheque; 5=dividend warrant
│         │         └───────── Account number (6 digits, bank-specific encoding)
│         └─────────────────── Bank/branch code (6 digits)
└───────────────────────────── Cheque number (6 digits)

The ∶ symbols are MICR delimiter characters, not colons.
```

**Why MICR matters for OCR pipelines:**

1. **MICR is the authoritative source for cheque numbers and bank codes.** The printed text on the body of the cheque may be wrong (manually filled in, misprinted). The MICR band is machine-printed at the time of cheque book issuance and is the authoritative reference.

2. **MICR reading requires a specialised model.** Standard OCR models trained on regular fonts perform poorly on MICR E-13B — the font was specifically designed to be read by magnetic readers, not human eyes or standard vision models. Dedicated MICR recognition engines or fine-tuned models are needed.

3. **MICR enables cross-validation.** If the OCR-extracted account number from the cheque body disagrees with the MICR-encoded account number, one of them is wrong — and the MICR version is more reliable.

4. **MICR damage is a common failure mode.** The MICR band is at the bottom of the cheque and is frequently damaged — torn, folded, written over, or stained. A robust pipeline must handle partial MICR reads and fall back to body-of-cheque extraction.

```typescript
interface MICRExtraction {
  chequeNumber:      string | null;  // 6 digits
  bankBranchCode:    string | null;  // 6 digits
  accountCode:       string | null;  // 6 digits
  transactionCode:   string | null;  // 1 digit
  confidence:        number;
  isDamaged:         boolean;
  damageRegions:     BoundingBox[];
}

async function extractMICR(image: ProcessedImage, micrRegion: BoundingBox): Promise<MICRExtraction> {
  // Use MICR-specific model (E-13B font trained)
  const micrResult = await micrRecognitionModel.extract(image, micrRegion);

  // Check for damage in the MICR region
  const damageScore = await assessMICRDamage(image, micrRegion);

  // Validate MICR check digit (RBI cheque standard)
  const isValid = validateMICRCheckDigit(micrResult.raw);

  return {
    chequeNumber:   micrResult.chequeNumber,
    bankBranchCode: micrResult.bankBranchCode,
    accountCode:    micrResult.accountCode,
    transactionCode: micrResult.transactionCode,
    confidence:     isValid ? micrResult.confidence : micrResult.confidence * 0.5,
    isDamaged:      damageScore > 0.3,
    damageRegions:  micrResult.damageRegions,
  };
}
```

## Section 3: Bank Statement OCR

**Q8. How do you extract structured transaction data from a bank statement PDF or image?**

A: Bank statement OCR is harder than cheque OCR because statements are tabular, multi-page, and vary significantly across banks and statement generations. The goal is to extract every transaction row with its date, description, debit/credit amount, and running balance.

**Statement types and their processing challenges:**

```
Type 1 — Digital PDF (text layer present):
  PDF contains selectable text — OCR not needed, text extraction is sufficient.
  Challenge: text order in PDF may not follow visual reading order;
             tables may be encoded as floating text elements, not proper table structures.
  Tool: pdf-parse, pdfplumber (Python), PDF.js

Type 2 — Scanned PDF (image-based):
  PDF is a wrapper around scanned images — must OCR each page as an image.
  Challenge: varying scan quality, skew, coffee stains, handwritten annotations.
  Tool: Tesseract, Google Document AI, AWS Textract

Type 3 — Mobile photograph:
  Customer photographed a printed statement with their phone.
  Worst case for quality: perspective distortion, uneven lighting, motion blur.
  Challenge: Must deskew, correct perspective, enhance contrast before OCR.
  Tool: Document scanner SDK (e.g., Scanbot, Anyline) for pre-processing

Type 4 — Net banking screenshot:
  Screenshot from a banking app or net banking portal.
  Generally high-quality text rendering but may include UI chrome to strip.
  Challenge: Watermarks, varied fonts, multi-column layouts.
```

**Table extraction pipeline:**

```typescript
interface BankStatementRow {
  serialNumber?:   number;
  transactionDate: Date;
  valueDate?:      Date;
  description:     string;
  referenceNumber?: string;
  debitPaise?:     bigint;
  creditPaise?:    bigint;
  balancePaise:    bigint;
  rawText:         string;   // original extracted text for audit
}

async function extractBankStatement(
  document: DocumentInput,
): Promise<BankStatementResult> {

  // Step 1: Detect document type and extract pages
  const pages = await extractPages(document);

  // Step 2: Per-page OCR and layout analysis
  const pageResults = await Promise.all(pages.map(async (page, idx) => {
    const ocrResult  = await ocrPage(page);
    const tables     = await extractTables(ocrResult);  // detect table regions
    return { pageNumber: idx + 1, ocrResult, tables };
  }));

  // Step 3: Identify the transaction table
  // (statements may have multiple tables: header info, transaction table, summary)
  const transactionTable = identifyTransactionTable(pageResults);

  // Step 4: Parse header row to understand column mapping
  const columnMap = parseTableHeader(transactionTable.headerRow);
  // columnMap = { date: 0, description: 1, debit: 2, credit: 3, balance: 4 }

  // Step 5: Parse each data row
  const rawRows = transactionTable.dataRows.map(row =>
    parseTransactionRow(row, columnMap)
  );

  // Step 6: Validate and clean rows
  const validatedRows = validateStatementRows(rawRows);

  // Step 7: Verify running balance
  const balanceCheck = verifyRunningBalance(validatedRows);

  return {
    accountNumber:   extractAccountNumber(pageResults[0]),
    accountHolder:   extractAccountHolder(pageResults[0]),
    ifscCode:        extractIFSC(pageResults[0]),
    statementPeriod: extractStatementPeriod(pageResults[0]),
    openingBalance:  extractOpeningBalance(pageResults[0]),
    closingBalance:  extractClosingBalance(pageResults[pageResults.length - 1]),
    transactions:    validatedRows,
    balanceCheckPassed: balanceCheck.passed,
    balanceDiscrepancy: balanceCheck.discrepancyPaise,
  };
}
```

**Running balance verification — a critical integrity check:**

```typescript
function verifyRunningBalance(rows: BankStatementRow[]): BalanceCheckResult {
  let computedBalance = rows[0].balancePaise;

  for (let i = 1; i < rows.length; i++) {
    const prevBalance = computedBalance;
    const row         = rows[i];

    if (row.creditPaise) computedBalance += row.creditPaise;
    if (row.debitPaise)  computedBalance -= row.debitPaise;

    const discrepancy = computedBalance > row.balancePaise
      ? computedBalance - row.balancePaise
      : row.balancePaise - computedBalance;

    // Allow a 1 paise tolerance for rounding
    if (discrepancy > 1n) {
      return {
        passed:             false,
        firstFailureRow:    i,
        computedBalance,
        extractedBalance:   row.balancePaise,
        discrepancyPaise:   discrepancy,
      };
    }
  }

  return { passed: true, discrepancyPaise: 0n };
}
```

This balance check is the most powerful validation available for bank statements — if the OCR misread any debit/credit amount on any row, the running balance will diverge from the computed balance, surfacing the error even if you don't know which specific row is wrong.

**Q9. How do you categorise bank statement transactions for credit assessment?**

A: Raw transaction descriptions are bank-formatted strings that vary wildly across banks, transaction types, and time periods. Categorisation converts them into semantic labels useful for credit assessment: salary, rent, utility bills, loan EMIs, gambling, etc.

**Categorisation pipeline:**

```typescript
type TransactionCategory =
  | 'SALARY_CREDIT'          // regular salary credit
  | 'EMI_DEBIT'              // loan repayment going out
  | 'RENTAL_PAYMENT'         // rent paid
  | 'UTILITY_BILL'           // electricity, water, gas, internet
  | 'INSURANCE_PREMIUM'      // insurance payments
  | 'INVESTMENT'             // mutual funds, SIP, stocks
  | 'ATM_WITHDRAWAL'         // cash withdrawal
  | 'UPI_TRANSFER'           // UPI P2P transfer
  | 'NEFT_INWARD'            // incoming NEFT
  | 'CHEQUE_PAYMENT'         // outgoing cheque
  | 'CREDIT_CARD_BILL'       // credit card payment
  | 'GAMBLING_SUSPECTED'     // gaming/betting platforms
  | 'BOUNCED_CHEQUE'         // returned cheque (negative signal)
  | 'INTERNATIONAL_TRANSFER' // forex transactions
  | 'OTHER';

interface CategorisedTransaction extends BankStatementRow {
  category:          TransactionCategory;
  categoryConfidence: number;
  subCategory?:      string;
  merchantName?:     string;
  isRegular?:        boolean;  // appears at same interval repeatedly
  regularityScore?:  number;   // 0–1: how regular is this?
}

class TransactionCategoriser {
  categorise(txn: BankStatementRow): CategorisedTransaction {
    const desc = txn.description.toUpperCase();

    // Rule-based first pass (fast, high precision for known patterns)
    const ruleMatch = this.applyRules(desc, txn);
    if (ruleMatch && ruleMatch.confidence > 0.90) {
      return { ...txn, ...ruleMatch };
    }

    // ML model second pass (handles ambiguous descriptions)
    const mlPrediction = this.mlCategoriser.predict(desc);

    return {
      ...txn,
      category:           mlPrediction.category,
      categoryConfidence: mlPrediction.confidence,
      merchantName:       this.extractMerchantName(desc),
    };
  }

  private applyRules(
    desc:  string,
    txn:   BankStatementRow,
  ): Partial<CategorisedTransaction> | null {
    // Salary: credit transactions with salary-related keywords
    if (txn.creditPaise && (
      /\bSALARY\b/.test(desc)   ||
      /\bSAL\/\b/.test(desc)    ||
      /\bPAYROLL\b/.test(desc)  ||
      /\bSTIPEND\b/.test(desc)
    )) {
      return { category: 'SALARY_CREDIT', categoryConfidence: 0.97 };
    }

    // EMI: debit with EMI/loan keywords
    if (txn.debitPaise && (
      /\bEMI\b/.test(desc)       ||
      /\bLOAN\b/.test(desc)      ||
      /\bEQUITED\b/.test(desc)   ||
      /HDFC.*LOAN/.test(desc)    ||
      /BAJAJ.*FIN/.test(desc)
    )) {
      return { category: 'EMI_DEBIT', categoryConfidence: 0.95 };
    }

    // Bounced cheque: specific return memo patterns
    if (/\bRETURN\b/.test(desc) || /\bBOUNCE\b/.test(desc) || /\bDISHONOU?R/.test(desc)) {
      return { category: 'BOUNCED_CHEQUE', categoryConfidence: 0.98 };
    }

    // ATM
    if (/\bATM\b/.test(desc) || /\bCASH WDL\b/.test(desc)) {
      return { category: 'ATM_WITHDRAWAL', categoryConfidence: 0.99 };
    }

    // Gambling (high-risk for credit assessment)
    const GAMBLING_KEYWORDS = ['DREAM11', 'MPL ', 'MY11CIRCLE', 'PAYTM FIRST GAMES',
                               'RUMMY', 'POKER', 'BETWAY', 'SPORTA', '1XBET'];
    if (GAMBLING_KEYWORDS.some(kw => desc.includes(kw))) {
      return { category: 'GAMBLING_SUSPECTED', categoryConfidence: 0.93 };
    }

    return null;
  }
}
```

```typescript
function detectRecurringTransactions(
  transactions: CategorisedTransaction[],
): RecurringPattern[] {
  const salaryCandidates = transactions.filter(
    t => t.category === 'SALARY_CREDIT' && t.creditPaise
  );

  if (salaryCandidates.length < 2) return [];

  // Group by approximate amount (within ±5% — salary may vary due to bonus)
  const grouped = groupByApproximateAmount(salaryCandidates, 0.05);

  return grouped
    .filter(group => group.length >= 3)  // at least 3 occurrences = pattern
    .map(group => {
      const intervals = computeIntervals(group.map(t => t.transactionDate));
      const avgInterval = average(intervals);
      const intervalStdDev = stdDev(intervals);

      return {
        category:        'SALARY_CREDIT',
        occurrences:     group.length,
        avgAmountPaise:  average(group.map(t => t.creditPaise!)),
        expectedInterval: avgInterval,     // days between occurrences
        regularityScore: 1 - (intervalStdDev / avgInterval),  // 1 = perfectly regular
        isMonthly:       Math.abs(avgInterval - 30) < 5,
        lastOccurrence:  maxDate(group.map(t => t.transactionDate)),
      };
    });
}
```

## Section 4: Confidence Scoring & Human-in-the-Loop

**Q10. How do you design a confidence scoring system that correctly routes documents to STP vs. manual review?**

A: The routing decision — straight-through processing (STP) vs. human review — is the most consequential output of the OCR pipeline. Routing too aggressively to STP passes incorrect extractions through without human checks. Routing too conservatively to manual review defeats the automation benefit.

**Confidence score composition:**

```typescript
interface FieldConfidence {
  fieldName:          string;
  rawConfidence:      number;   // model's softmax confidence (0–1)
  calibratedConfidence: number; // post-calibration (Platt scaling or isotonic regression)
  validationBoost:    number;   // +/- adjustment from validation rules
  finalConfidence:    number;   // composite score
}

interface DocumentConfidence {
  fields:               FieldConfidence[];
  overallConfidence:    number;    // weighted average; critical fields weighted higher
  imageQualityScore:    number;    // 0–1: how clean is the source image?
  crossValidationScore: number;    // 0–1: how consistent are fields with each other?
  recommendation:       'STP' | 'SOFT_REVIEW' | 'MANUAL_REVIEW' | 'REJECT';
}

function computeDocumentConfidence(
  extractions:      RawExtraction[],
  validationResult: ValidationResult,
  imageQuality:     ImageQualityMetrics,
): DocumentConfidence {

  // Field weights for payment-critical fields
  const FIELD_WEIGHTS: Record<string, number> = {
    amount_figures: 0.30,    // highest weight — financial loss if wrong
    account_number: 0.25,
    ifsc_code:      0.20,
    date:           0.10,
    payee_name:     0.10,
    micr_code:      0.05,
  };

  const fieldConfidences = extractions.map(ext => {
    // Start with model's raw confidence
    let score = ext.modelConfidence;

    // Penalise for validation errors on this field
    const fieldErrors = validationResult.errors.filter(e => e.fields?.includes(ext.fieldName));
    score *= Math.pow(0.5, fieldErrors.length);  // each error halves the confidence

    // Boost if cross-field validation passed (e.g., amount figures = amount words)
    if (validationResult.crossFieldChecks[ext.fieldName]?.passed) {
      score = Math.min(1.0, score * 1.1);
    }

    // Penalise for low image quality in the specific field region
    const regionQuality = imageQuality.perRegionScores[ext.fieldName] ?? imageQuality.overall;
    if (regionQuality < 0.5) score *= regionQuality;

    return {
      fieldName:            ext.fieldName,
      rawConfidence:        ext.modelConfidence,
      calibratedConfidence: ext.calibratedConfidence,
      validationBoost:      score - ext.modelConfidence,
      finalConfidence:      score,
    };
  });

  // Weighted overall confidence
  const overallConfidence = fieldConfidences.reduce((sum, fc) => {
    const weight = FIELD_WEIGHTS[fc.fieldName] ?? 0.02;
    return sum + fc.finalConfidence * weight;
  }, 0);

  // Routing decision based on thresholds
  const lowestCriticalFieldScore = Math.min(
    ...fieldConfidences
      .filter(fc => (FIELD_WEIGHTS[fc.fieldName] ?? 0) >= 0.20)
      .map(fc => fc.finalConfidence)
  );

  let recommendation: DocumentConfidence['recommendation'];
  if (lowestCriticalFieldScore < 0.50 || validationResult.errors.some(e => e.severity === 'CRITICAL')) {
    recommendation = 'REJECT';
  } else if (lowestCriticalFieldScore < 0.80 || overallConfidence < 0.85) {
    recommendation = 'MANUAL_REVIEW';
  } else if (overallConfidence < 0.95) {
    recommendation = 'SOFT_REVIEW';  // show to analyst; auto-approve if no changes in 30 mins
  } else {
    recommendation = 'STP';
  }

  return {
    fields:               fieldConfidences,
    overallConfidence,
    imageQualityScore:    imageQuality.overall,
    crossValidationScore: computeCrossValidationScore(validationResult),
    recommendation,
  };
}
```

**Threshold calibration — how to set the right thresholds:**

The thresholds (0.80, 0.95 above) must be calibrated empirically against your document population. The process:

1. Collect a labelled dataset of 1,000+ documents with ground-truth extractions.
2. Run your pipeline on all of them.
3. For each threshold value from 0.50 to 1.00, compute: STP rate, false acceptance rate (errors that passed STP), and manual review rate.
4. Choose the threshold that achieves your target false acceptance rate (e.g., < 0.1% for amount fields) while maximising STP rate.
5. Re-calibrate quarterly as your document population shifts.

**Q13. "Design an OCR pipeline for processing 100,000 cheques per day with a 99.9% accuracy requirement on the amount field."**

A: 100,000 cheques/day = ~1.16 cheques/second average, peaking at 5–10x during banking hours. The 99.9% accuracy on amount means at most 100 errors per day — and since even one wrong amount causes a financial loss, the system must have defense in depth.

**For the 99.9% amount accuracy target:**

The pipeline achieves this through five independent layers of defense:

```
Layer 1 — Model accuracy: target 99.5% on clean images
Layer 2 — Cross-validation: amount figures vs. amount words agreement
          (catches most model errors; flags for review when they disagree)
Layer 3 — MICR cross-validation: MICR amount encoding (where present) vs. OCR amount
Layer 4 — Business rule range check: amount within expected range for this customer/use case
Layer 5 — Manual review for low-confidence amounts: any amount below 99% confidence → human eyes

Combined: 99.5% model × (cross-validation catches 80% of remaining errors)
          × (MICR catches 60% of what cross-validation misses)
          × (manual review catches 95% of what passes through)
          ≈ 99.999% effective accuracy
```

**Q14. "A bank statement uploaded by a customer shows ₹6 lakh in monthly salary credits, but the salary appears as 12 separate credits of ₹50,000 each on different dates. Your credit assessment system only looks at the highest single credit. What is wrong and how do you fix it?"**

A: This is a **transaction aggregation** problem — the credit assessment engine is incorrectly using a single-transaction view when it should be using an aggregated periodic-income view.

**Root causes:**

```
1. Salary is split across multiple credits in the same month:
   - Common for freelancers, consultants, gig workers receiving multiple client payments
   - Common for employees paid weekly or bi-weekly instead of monthly
   - Common for earnings from multiple part-time jobs
   - Sometimes indicates multiple income sources (rental income + salary)

2. Your credit engine's `max_single_credit` metric is wrong for this use case.
   It was probably designed for a salaried employee with one credit per month.

3. The OCR extraction is correct — the problem is in the downstream analysis logic.
```

**The correct income signal for credit assessment:**

```typescript
interface IncomeAnalysis {
  // Don't use: max single credit
  maxSingleCredit:        bigint;   // WRONG for split salary

  // Use instead: monthly aggregates
  monthlyCredits: Array<{
    month:              string;     // 'YYYY-MM'
    totalCreditPaise:   bigint;     // sum of all credits in this month
    creditCount:        number;     // how many credits contributed
    regularCredits:     bigint;     // credits matching salary pattern
    irregularCredits:   bigint;     // one-off credits to exclude from income
  }>;

  // Derived income signals
  averageMonthlyIncome:   bigint;   // average of last 6 months' total credits
  medianMonthlyIncome:    bigint;   // median is more robust to outliers than average
  incomeStability:        number;   // stdDev / mean of monthly income (lower = more stable)
  monthsOfHistory:        number;   // how many months of data available
  salaryPattern:          RecurringPattern | null;  // is there a detectable salary pattern?
}

function analyseIncome(transactions: CategorisedTransaction[]): IncomeAnalysis {
  // Group all credit transactions by month
  const byMonth = groupBy(
    transactions.filter(t => t.creditPaise && t.creditPaise > 0n),
    t => format(t.transactionDate, 'yyyy-MM')
  );

  const monthlyCredits = Object.entries(byMonth).map(([month, txns]) => {
    // Separate regular income from one-off credits
    // One-off signals: unusually large, first occurrence, labelled as 'GIFT' / 'LOAN_RECEIVED'
    const regularCredits = txns
      .filter(t => !isOneOffCredit(t))
      .reduce((sum, t) => sum + t.creditPaise!, 0n);

    const irregularCredits = txns
      .filter(t => isOneOffCredit(t))
      .reduce((sum, t) => sum + t.creditPaise!, 0n);

    return {
      month,
      totalCreditPaise:  regularCredits + irregularCredits,
      creditCount:       txns.length,
      regularCredits,
      irregularCredits,
    };
  });

  // Use last 6 months for income estimate
  const last6Months = monthlyCredits
    .sort((a, b) => b.month.localeCompare(a.month))
    .slice(0, 6);

  const regularMonthlyIncomes = last6Months.map(m => m.regularCredits);

  return {
    maxSingleCredit:      maxBigInt(transactions.map(t => t.creditPaise ?? 0n)),
    monthlyCredits,
    averageMonthlyIncome: averageBigInt(regularMonthlyIncomes),
    medianMonthlyIncome:  medianBigInt(regularMonthlyIncomes),
    incomeStability:      computeStabilityScore(regularMonthlyIncomes),
    monthsOfHistory:      last6Months.length,
    salaryPattern:        detectRecurringTransactions(
                            transactions.filter(t => t.category === 'SALARY_CREDIT')
                          )[0] ?? null,
  };
}
```

**The fix for the credit assessment system:**

Replace `max_single_credit` with `median_monthly_regular_income` as the primary income signal. Additionally:
- If `incomeStability` < 0.3 (coefficient of variation < 30%), the income is regular — use average.
- If `incomeStability` >= 0.3 (high variability), use the median or the 25th percentile — more conservative for irregular earners.
- Flag cases where `creditCount > 4` in a month for analyst review — may indicate split salary (positive) or payment aggregation through a single account (risk signal).

## Quick Reference Table

| Concept | Detail | Engineering implication |
|---|---|---|
| **OCR types** | Template → Zonal → AI-based (LayoutLM, Document AI) | Use AI-based for production; template only for fully controlled document formats |
| **MICR** | 9-digit magnetic ink band: cheque no + bank code + account code | Cross-validate OCR amounts with MICR; use dedicated MICR model |
| **Amount normalisation** | Indian format (1,00,000); use Decimal.js; never float | `parseFloat("1,00,000") → NaN`; strip commas first; convert to paise |
| **Amount cross-validation** | Figures vs. words → zero tolerance; any mismatch → MANUAL_REVIEW | Most powerful single validation rule; catches majority of amount errors |
| **Running balance check** | Recompute balance row-by-row; divergence = OCR error somewhere | Apply to every bank statement; localises errors even without knowing which row is wrong |
| **Confidence calibration** | Model confidence ≠ accuracy; must calibrate on labelled dataset | Uncalibrated 95% confidence may be only 80% accurate on your document population |
| **STP routing thresholds** | Critical field < 80% → MANUAL_REVIEW; all fields > 95% → STP | Calibrate per document type per bank per channel; recalibrate quarterly |
| **PAN verification** | Format check + NSDL/UTI API call | OCR of a forged PAN passes format check; only API verifies it exists |
| **Aadhaar storage** | Never store raw 12-digit number; store masked (last 4) + SHA-256 hash | UIDAI regulation; violation = significant penalty |
| **Image quality gate** | DPI > 200, blur score, coverage check before OCR | Reject bad images early; cheaper than running OCR and getting bad results |
| **Stale cheque check** | Indian cheques valid for 3 months; reject older | Cross-validate date against current date; not just format validation |
| **Income aggregation** | Monthly sum of regular credits, not max single credit | Split salary appears as N small credits; sum-per-month is the correct signal |
| **Feedback loop** | Every reviewer correction → training example | Models without feedback loops degrade on new bank formats and seasonal variations |
| **Hallucination risk** | Neural models confidently predict wrong characters on illegible regions | Confidence scores can be high even when wrong; cross-validation and human review are essential |
| **Pre-processing** | Deskew (±15°), denoise, binarise, 300 DPI, contrast enhance | Each step measurably improves OCR accuracy; skip pre-processing = higher error rate |

**Tip for the interview:** At the 5 YOE level in a fintech that uses OCR, questions appear in three forms: (1) "how do you ensure OCR accuracy is high enough for payment processing?" — the expected answer is defense in depth: image quality gate, pre-processing, cross-field validation (amount figures vs. words), confidence thresholding, and human-in-the-loop for low-confidence cases — not just "use a better model"; (2) "how do you extract income from a bank statement?" — they expect you to describe the full pipeline: table extraction, row parsing, running balance verification, transaction categorisation, and aggregated monthly income calculation using median (not max single credit); (3) "a cheque OCR extracted ₹1,00,000 but the actual cheque says ₹10,00,000 — how do you prevent this?" — the answer is: amount-in-words cross-validation catches this (one lakh vs. ten lakhs are very different strings), MICR cross-validation as a second check, and any amount discrepancy routes to manual review with zero tolerance. Know that amounts must be handled in paise (bigint) from the moment they are parsed from the OCR output — normaliseAmount() returns bigint, not float. Know the Aadhaar storage rule cold: masked display + SHA-256 hash only, never the raw 12 digits. That rule comes up every time Aadhaar appears in an architecture discussion.
