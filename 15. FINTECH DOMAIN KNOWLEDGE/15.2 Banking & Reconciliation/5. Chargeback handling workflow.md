# Chargeback Handling Workflow — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a chargeback, and how does it differ from a refund?**
A: A chargeback is a forced reversal of a payment transaction initiated by the cardholder's issuing bank, triggered when a cardholder disputes a charge. A refund is a voluntary reversal initiated by the merchant. The distinction is critical:

| Property | Refund | Chargeback |
|--|--|--|
| **Initiated by** | Merchant | Cardholder → Issuing bank |
| **Merchant consent** | Yes (merchant controls it) | No (forced on the merchant) |
| **Funds flow** | Merchant → Cardholder | Issuing bank → Cardholder; Acquirer debits merchant |
| **Cost** | Transaction amount only | Transaction amount + chargeback fee ($15–$100) |
| **Timeline** | Immediate to 5–10 days | 30–120 days for full resolution |
| **Fraud signal** | None | Yes — counts toward chargeback ratio |
| **Evidence required** | None | Required to contest (representment) |
| **Outcome options** | None — always succeeds | Merchant wins or loses after dispute cycle |

The chargeback mechanism exists to protect cardholders from fraud and merchant non-performance. It is guaranteed by the card networks (Visa, Mastercard) as a core feature of the card payment system — the merchant implicitly accepts chargeback risk when they agree to accept card payments. For merchants, chargebacks represent both a direct financial loss (the transaction amount + fee) and a ratio threshold risk (exceed 1% chargeback rate and the network places you in a monitoring program).

**Q2. What are the main chargeback reason codes, and what categories do they fall into?**
A: Card networks categorize chargebacks by reason codes that determine the dispute rules, evidence requirements, and time limits. The four major categories:

**1. Fraud (Unauthorized Transaction)**
The cardholder states they did not authorize the transaction. The most common chargeback type for card-not-present (CNP) merchants.
- Visa: `10.4` (Other Fraud — Card Absent), `10.2` (EMV Liability Shift — Card Present)
- Mastercard: `4837` (No Cardholder Authorization), `4863` (Cardholder Does Not Recognize)
- Win rate for merchant: **low** without 3DS authentication or strong device/behavioral evidence.

**2. Authorization (Processing Errors)**
The transaction was not properly authorized or was processed after an authorization expired.
- Visa: `11.1` (Card Recovery Bulletin), `11.2` (Declined Authorization), `11.3` (No Authorization)
- Mastercard: `4808` (Authorization-Related Chargeback)
- Win rate: **high if authorization evidence is available**; these are often merchant error.

**3. Consumer Dispute (Service / Product Issues)**
The cardholder received no goods, received damaged/defective goods, or the merchant failed to provide the promised service.
- Visa: `13.1` (Merchandise/Services Not Received), `13.2` (Cancelled Recurring), `13.3` (Not as Described), `13.5` (Misrepresentation), `13.7` (Cancelled Merchandise — Return)
- Mastercard: `4853` (Cardholder Dispute), `4841` (Cancelled Recurring)
- Win rate: **medium** — depends on quality of delivery evidence and communication records.

**4. Processing Errors**
Duplicate processing, incorrect amount, credit not processed.
- Visa: `12.1` (Late Presentment), `12.2` (Incorrect Transaction Code), `12.6` (Duplicate Processing)
- Mastercard: `4834` (Duplicate Processing), `4831` (Incorrect Transaction Amount)
- Win rate: **high** — usually merchant or processor error; straightforward to identify and concede or correct.

**Q3. What is the full lifecycle of a chargeback, from dispute to resolution?**
A: The chargeback lifecycle has defined phases with strict time limits set by the card networks. Missing a deadline is an automatic loss.

```
Day 0:      Cardholder contacts issuing bank to dispute a charge
            Issuer validates the claim meets minimum criteria

Day 1–5:    Issuer initiates chargeback
            → Sends chargeback notification to card network
            → Network routes to acquirer
            → Acquirer debits merchant's account for the dispute amount + fee
            → Acquirer notifies merchant (via dashboard, webhook, or file)

Day 1–30:   MERCHANT RESPONSE WINDOW
            Merchant chooses: Accept (do nothing) or Contest (representment)

            If Accept:
              Chargeback closes. Funds remain with cardholder.
              Chargeback counts toward merchant's ratio.

            If Contest:
              Merchant submits representment package to acquirer
              → Acquirer forwards to network → Network to issuer

Day 30–45:  Issuer reviews representment
            → If issuer sides with merchant: funds returned, case closed
            → If issuer upholds chargeback: merchant loses

Day 45–60:  PRE-ARBITRATION (Visa) / SECOND CHARGEBACK (Mastercard)
            If merchant won representment but issuer disagrees:
            Issuer can escalate to pre-arbitration / second chargeback
            Merchant must respond again or accept the loss

Day 60–120: ARBITRATION
            Either party can escalate to card network as final arbiter
            Network makes binding decision
            Losing party pays arbitration fees ($250–$500 per case)
            Arbitration is high-stakes: rarely the right choice without very strong evidence

Final state:  MERCHANT WIN — funds reversed back to merchant
              MERCHANT LOSS — funds remain with cardholder; fee retained
```

**Time limits are jurisdictional and network-specific:**
| Phase | Visa | Mastercard |
|--|--|--|
| Cardholder dispute window | 120 days from transaction | 120 days from transaction |
| Merchant response window | Typically 30 days | Typically 45 days |
| Issuer re-presentment | 30 days after merchant response | 45 days |
| Arbitration filing | 10 days after pre-arb | 45 days after second chargeback |

## Section 2: Chargeback Economics

**Q4. What is the true cost of a chargeback, and how do you calculate it?**
A: Merchants systematically undercount chargeback costs because they only see the line-item debit in their settlement report. The true cost has four components:

**1. Direct financial loss**
```
Transaction amount:          $150.00   (funds reversed to cardholder)
Chargeback fee:               $25.00   (acquirer fee per dispute)
Non-refunded interchange:     $2.25    (interchange paid on original capture is not returned)
Total direct loss:           $177.25
```

**2. Operational cost**
Disputing a chargeback requires human or automated labor:
```
Evidence gathering:           15–30 min of staff time
Representment filing:         10–20 min of staff time
Average loaded cost/hour:     $50–$100 (operations staff)
Operational cost per dispute: $12–$50
```

**3. Cost of goods / services delivered**
For physical goods: the product was shipped and is now unrecoverable (unless return was completed before chargeback).
For digital goods: marginal cost is low, but licensing or COGS still applies.

**4. Indirect costs**
- Processor penalty fees if chargeback ratio exceeds thresholds.
- Risk of being placed in Visa VDMP or Mastercard MDMP monitoring program.
- Higher processing fees from acquirer renegotiation if risk profile worsens.
- Engineering and compliance cost of remediation programs.

**True cost model:**
```python
def true_chargeback_cost(txn_amount, interchange_rate, dispute_fee,
                         cogs_rate, ops_cost_per_dispute, win_rate):
    direct_loss = txn_amount + dispute_fee + (txn_amount * interchange_rate)
    cogs_loss   = txn_amount * cogs_rate
    ops_cost    = ops_cost_per_dispute
    
    # Win rate reduces direct loss (merchant gets transaction back if they win)
    # but ops cost and interchange are sunk regardless
    expected_direct = (1 - win_rate) * direct_loss + win_rate * dispute_fee
    
    return expected_direct + cogs_loss + ops_cost

# Example: $150 digital goods transaction
true_cost = true_chargeback_cost(
    txn_amount=150.00, interchange_rate=0.015,
    dispute_fee=25.00, cogs_rate=0.30,
    ops_cost_per_dispute=20.00, win_rate=0.35
)
# Result: ~$90–$120 per chargeback depending on win rate
```

At scale: a merchant doing $5M/month with a 1% chargeback rate faces 500 chargebacks/month. At $100 true cost per chargeback = $50,000/month in chargeback costs — 1% of revenue lost entirely to dispute handling.

**Q5. What are chargeback ratio thresholds, and what happens when you exceed them?**
A: Card networks monitor every merchant's chargeback ratio monthly and enforce tiered consequences for merchants that exceed thresholds.

**Visa's Dispute Monitoring Programs:**

| Program | Threshold | Consequence |
|--|--|--|
| **Visa Dispute Monitoring Program (VDMP)** — Early Warning | > 0.65% ratio OR > 75 disputes/month | Informal warning; no fees yet |
| **VDMP — Standard** | > 0.9% ratio AND > 100 disputes/month | Monthly fines ($50/dispute above threshold); required remediation plan |
| **VDMP — High Risk** | > 1.8% ratio AND > 1,000 disputes/month | Fines escalate ($50–$100/dispute); acquirer may terminate account |
| **Visa Fraud Monitoring Program (VFMP)** | > 0.65% fraud-to-sales ratio | Same escalation as VDMP but for fraud-specific disputes |

**Mastercard's MATCH and Programs:**
| Program | Threshold | Consequence |
|--|--|--|
| **Excessive Chargeback Program (ECP)** | > 1.0% ratio AND > 100 disputes/month | $1,000/month fine; escalates after 6 months |
| **High Excessive Chargeback Program (HECP)** | > 1.5% ratio AND > 300 disputes/month | $25,000/month fine; acquirer risk review |

**Calculation methodology:**
```
Chargeback Ratio = (Chargebacks received in month N) / (Transactions processed in month N-1)

Note: the numerator and denominator use DIFFERENT months.
A spike in chargebacks this month is compared to last month's volume.
For fast-growing merchants, this ratio is naturally deflated (good).
For declining merchants, it is naturally inflated (bad).
```

**The MATCH list:**
Merchants terminated for excessive chargebacks or fraud are added to Mastercard's MATCH (Member Alert to Control High-risk) list — a shared industry blacklist. Being on MATCH makes it extremely difficult to obtain a new merchant account from any acquirer (all major acquirers check it). MATCH records remain for 5 years.

## Section 3: Prevention Architecture

**Q6. What are the most effective technical controls for preventing chargebacks before they occur?**
A: Chargeback prevention is upstream fraud and dispute prevention. Controls operate at three layers:

**Layer 1 — Authentication (Fraud Chargebacks)**

*3D Secure 2 (3DS2):*
- Shifts fraud liability from merchant to issuer when 3DS authentication is completed.
- A successful 3DS authentication means a fraud-based chargeback (`10.4`, `4837`) cannot be filed — the issuer already authenticated the transaction.
- 3DS2 supports frictionless flow (no customer challenge for low-risk transactions) using risk-based authentication signals (device fingerprint, transaction history, behavioral biometrics).
- Implementation: integrate 3DS2 via your processor SDK or directly via Cardinal Commerce, Stripe Radar, or Adyen Authentication.
- Tradeoff: 3DS adds 200–400ms latency and a small conversion friction for challenged flows (3–7% of transactions).

*Device fingerprinting and behavioral signals:*
- Collect device fingerprint (IP, browser, OS, screen resolution, fonts) at checkout.
- Detect mismatches between billing address country and IP geolocation.
- Flag velocity patterns: same device purchasing with multiple cards; multiple accounts using same device.
- Tools: Sift, Kount, Signifyd, or build a feature store from your own transaction events.

*Address Verification Service (AVS) and CVV:*
- AVS matches the billing address zip code against the issuer's records.
- CVV verifies the physical card is present (or was present when the card was tokenized).
- Decline or flag transactions where AVS fails (mismatch on zip or full address) or CVV fails.
- Limitation: not available in all countries; some issuers do not participate in AVS.

**Layer 2 — Order Clarity (Consumer Dispute Chargebacks)**

*Descriptor clarity:*
- The merchant descriptor that appears on the cardholder's statement must be recognizable. "ACME CORP 800-555-1234" is better than "ACMEPYT*7623918." An unrecognized descriptor is the #1 cause of "I don't recognize this charge" chargebacks — even for legitimate transactions.
- Use the soft descriptor (dynamic descriptor) to include the product name or order number: "SHOPNAME.COM ORD-4821."
- Provide a customer support phone number in the descriptor. A cardholder who can call you is a cardholder who does not file a chargeback.

*Order confirmation and communication:*
- Send order confirmation emails immediately after purchase (timestamp proof of customer action).
- Send shipping confirmation with tracking numbers.
- For digital goods: send access confirmation with delivery timestamp.
- For subscriptions: send reminder emails before each billing cycle renewal.

*Proactive customer service:*
- Make refunds easy. A customer who gets a $30 refund in 2 minutes does not file a $30 chargeback + $25 fee + 30 minutes of your staff time.
- Monitor for orders flagged as "not received" via support tickets before the chargeback window; proactive outreach and resolution prevents escalation.

**Layer 3 — Chargeback Alerts (Early Warning)**

*Chargeback alert services:*
- **Verifi (Visa's CDRN)** and **Ethoca (Mastercard/Amex)** are pre-dispute alert networks. When a cardholder calls their bank to dispute a charge, the bank queries these networks before filing the chargeback. If the merchant is enrolled, they receive a real-time alert with a 24–72 hour window to issue a refund — which prevents the chargeback from ever being filed.
- Alert services cost $15–$40 per alert, but this is cheaper than a chargeback ($25–$100 fee + lost transaction + ratio impact).
- Engineering integration: alerts arrive via webhook or API; your system must automatically check whether the order is refundable (not already refunded, not older than refund policy allows) and initiate a refund or flag for manual review.

```python
def handle_chargeback_alert(alert):
    order = db.get_order(alert.order_id)
    
    if order is None:
        log_alert(alert, status='order_not_found')
        return
    
    if order.already_refunded:
        log_alert(alert, status='already_refunded')
        return
    
    if order.age_days > REFUND_POLICY_DAYS:
        log_alert(alert, status='outside_refund_window', action='manual_review')
        flag_for_human_review(alert)
        return
    
    # Auto-refund to prevent chargeback
    refund = payment_client.refund(order.payment_id, amount=alert.dispute_amount)
    log_alert(alert, status='auto_refunded', refund_id=refund.id)
    notify_customer(order, reason='dispute_prevention_refund')
```

**Q7. What is 3DS liability shift, and when does it fail to protect the merchant?**
A: The 3DS liability shift is the mechanism by which fraud liability moves from the merchant to the issuing bank when a transaction is authenticated via 3D Secure. If a fraudster completes a 3DS-authenticated transaction, and the cardholder later files a fraud chargeback, the *issuer* — not the merchant — bears the loss.

**When liability shift applies:**
- The merchant attempted 3DS authentication.
- The issuer either authenticated the cardholder (full authentication) or accepted the transaction without challenge (frictionless authentication where the issuer took the risk decision).
- The transaction was processed with the authentication result (ECI value) included in the authorization.

**When liability shift does NOT protect the merchant:**

1. **3DS attempted but issuer declined to authenticate** — if the issuer returns a "not authenticated" result and the merchant proceeds with the transaction anyway (allowed in some regions), liability does NOT shift. The merchant chose to accept an unauthenticated transaction.

2. **Consumer dispute chargebacks** — liability shift only applies to *fraud* chargebacks (unauthorized transaction claims). It provides zero protection against:
   - `13.1` Merchandise Not Received
   - `13.3` Not as Described
   - `13.2` Cancelled Recurring
   These are disputes about the merchant's service, not about authorization. 3DS cannot help here.

3. **Merchant processing error chargebacks** — duplicate processing, incorrect amount — 3DS is irrelevant.

4. **Frictionless 3DS on high-risk transactions** — some issuers frictionlessly approve high-risk transactions they shouldn't, then later accept the chargeback anyway and argue the merchant should have triggered a challenge. Edge case, but real.

5. **Countries without 3DS mandate** — in markets where 3DS is not required (parts of North America pre-PSD2), liability shift rules may be less enforced.

**Engineering implication:** do not treat 3DS as a universal chargeback shield. It eliminates the fraud chargeback vector but leaves all other reason code categories unaffected. A merchant with zero fraud chargebacks can still breach the 1% threshold purely from `13.1` (not received) and `13.2` (cancelled recurring) disputes.

## Section 4: Representment Workflow

**Q8. What is representment, and what evidence is required to win?**
A: Representment is the merchant's formal rebuttal of a chargeback. The merchant "re-presents" the original transaction to the card network along with evidence that the charge was legitimate. If the issuer accepts the representment, the funds are returned to the merchant.

**Evidence requirements by reason code:**

**For fraud chargebacks (`10.4`, `4837` — Unauthorized Transaction):**
- 3DS authentication result with ECI value and authentication value (CAVV/AAV). This alone may be sufficient for liability shift.
- Device fingerprint matching the cardholder's historical devices.
- IP address geolocation consistent with cardholder's billing address or known location.
- Signed delivery confirmation (physical goods) or access logs showing the customer used the digital product/service after purchase.
- Prior successful transactions on the same card (establishes relationship, undermines "never authorized" claim).
- Customer service communication showing the cardholder engaged with the product.

**For `13.1` (Not Received):**
- Carrier tracking showing delivery to the billing address with signature confirmation.
- For digital goods: server-side access logs with timestamps showing product access; IP address of the accessing device; download logs.
- Email/SMS delivery confirmation with timestamps.
- Customer service communication acknowledging receipt (most valuable — if the cardholder emailed you saying "I got it," that is strong evidence).

**For `13.2` (Cancelled Recurring):**
- Subscription terms the cardholder agreed to at signup (screenshot of checkout page with terms visible; terms URL with hash to prove content hasn't changed).
- Timestamp of when the cardholder agreed to recurring billing.
- Evidence that cancellation was not requested before the billing date (customer portal logs, support ticket history with no cancellation request).
- Any communication acknowledging the recurring billing and the cancellation policy.

**For `13.3` (Not as Described):**
- Product description at time of purchase (archived screenshot with timestamp).
- Customer service communication showing either (a) no complaint was received, or (b) a complaint was received and resolved.
- Photos or product documentation showing the item matches the description.
- Comparison of what was described vs. what was delivered.

**For `12.6` (Duplicate Processing):**
- Evidence that the two transactions are legitimately different (different items, different dates).
- If it was genuinely a duplicate: concede and offer a refund without filing representment.

**Q9. What does a representment package look like structurally, and how do you build it?**
A: A representment package is a formal document submitted to the acquirer (who forwards it to the card network). It has a required structure:

```
REPRESENTMENT PACKAGE STRUCTURE
─────────────────────────────────
1. REBUTTAL LETTER (1–2 pages)
   - Case identifier (chargeback reference number)
   - Transaction details (date, amount, card last four, order ID)
   - Statement of position ("We dispute this chargeback for the following reasons...")
   - Summary of evidence provided
   - Specific reason code addressed
   - Requested outcome

2. TRANSACTION EVIDENCE
   - Authorization record (approval code, timestamp)
   - Capture record
   - 3DS authentication record (if applicable)
   - Order details (line items, shipping address, billing address)

3. DELIVERY / FULFILLMENT EVIDENCE
   - Tracking number and carrier confirmation
   - Delivery timestamp and recipient name (if signature required)
   - For digital: access logs, download records, activation timestamps

4. CUSTOMER RELATIONSHIP EVIDENCE
   - Terms of service agreed to at checkout (archived, timestamped)
   - Account creation record (email, IP, device)
   - Login history after purchase date
   - Support ticket history (proving no cancellation or complaint was filed)
   - Email correspondence with timestamps

5. FRAUD SIGNALS (for unauthorized transaction disputes)
   - 3DS ECI value and CAVV
   - Device fingerprint match
   - IP/geolocation consistency
   - Prior transaction history on same card

6. SUPPORTING DOCUMENTATION (as applicable)
   - Photos of product before shipment
   - Return merchandise authorization (RMA) records
   - Refund policy as presented at checkout
```

**Engineering the representment pipeline:**
At any meaningful scale, building representment packages manually is not viable. The system must automatically assemble evidence from distributed sources:

```python
class RepresentmentBuilder:
    def build(self, chargeback_id):
        cb = db.get_chargeback(chargeback_id)
        order = db.get_order(cb.order_id)
        
        package = RepresentmentPackage(chargeback=cb, order=order)
        
        # Pull evidence from each system
        package.add(auth_service.get_authorization_record(order.payment_id))
        package.add(auth_service.get_3ds_record(order.payment_id))
        package.add(fulfillment_service.get_delivery_record(order.id))
        package.add(access_log_service.get_access_logs(order.user_id, after=order.created_at))
        package.add(crm_service.get_support_history(order.user_id, order.id))
        package.add(account_service.get_login_history(order.user_id, after=order.created_at))
        package.add(terms_service.get_terms_at_time(order.created_at))
        
        package.generate_rebuttal_letter(reason_code=cb.reason_code)
        package.compile_pdf()
        
        return package
```

## Section 5: Chargeback Operations at Scale

**Q10. How do you triage chargebacks to decide which to fight and which to concede?**
A: Fighting every chargeback is not economically rational. The representment costs (staff time, system cost) must be weighed against the probability of winning and the transaction amount. The triage framework:

**Automatic concession criteria (do not fight):**
- Transaction amount < fight threshold (typically $25–$50 for low-win-rate categories; the fee and ops cost exceed the recovery value).
- Reason code is a legitimate merchant error (genuine duplicate processing, incorrect amount).
- Refund was already issued before the chargeback arrived (file evidence of refund; acquirer may waive the chargeback fee).
- The cardholder did cancel the subscription and the billing system failed to process it — this is your error; concede immediately.
- Evidence is unavailable (order was more than 18 months ago; records purged; digital product access logs not retained).

**Automatic fight criteria (always contest):**
- 3DS authentication evidence exists for a fraud chargeback — near-certain win with liability shift.
- Signed delivery confirmation exists and matches billing address — strong evidence for `13.1`.
- Transaction amount > $200 AND win rate for this reason code > 40%.
- Multiple chargebacks from the same cardholder (pattern suggests professional disputer / friendly fraud).

**Human triage criteria (case-by-case review):**
- Transaction amount in the $50–$200 range — economics depend on evidence quality.
- Mixed evidence: delivery confirmed but customer service complaint exists.
- High-value customer with account history — conceding may preserve the relationship.

**Triage scoring model:**
```python
def triage_chargeback(chargeback):
    order = get_order(chargeback.order_id)
    evidence = assess_available_evidence(chargeback)
    
    expected_win_rate = estimate_win_rate(
        reason_code=chargeback.reason_code,
        evidence_strength=evidence.strength_score,
        has_3ds=evidence.has_3ds_auth,
        has_delivery_confirmation=evidence.has_signed_delivery
    )
    
    fight_value = order.amount * expected_win_rate
    fight_cost = REPRESENTMENT_COST + (order.amount * INTERCHANGE_RATE)  # sunk regardless
    
    if fight_value > fight_cost and order.amount > MINIMUM_FIGHT_THRESHOLD:
        return TriageDecision.FIGHT
    elif chargeback.reason_code in AUTO_CONCEDE_CODES:
        return TriageDecision.CONCEDE
    else:
        return TriageDecision.HUMAN_REVIEW
```

**Q11. What is friendly fraud, and how do you detect and fight it systematically?**
A: Friendly fraud (also called first-party fraud or chargeback fraud) occurs when a legitimate cardholder makes a purchase, receives the goods or services, and then files a chargeback claiming the transaction was unauthorized or the goods were not received. Unlike third-party fraud, the transaction itself was authorized by the actual cardholder.

**Scale of the problem:** Industry estimates suggest 60–80% of chargebacks in e-commerce are friendly fraud, not genuine unauthorized transactions.

**Detection signals:**
- **Digital product access after dispute**: the customer downloaded or accessed the product *after* the date they claimed it was unauthorized.
- **Multiple chargebacks on same account**: a customer who files chargebacks on 3+ purchases over 12 months is very likely a repeat abuser.
- **Chargeback filed immediately after delivery**: a fraud-based chargeback filed the day a package is confirmed delivered is suspicious.
- **High-value item, no return initiated**: for `13.3` (not as described), a genuine claimant typically requests a return first. Skipping returns and going straight to chargeback is a signal.
- **Known device / IP match**: the device fingerprint that placed the order matches the device on the cardholder's account — the same person who ordered placed the order.
- **Cardholder engages with support after filing**: a cardholder who files a chargeback then emails support asking about reordering is engaging in bad faith.

**Systematic response to known friendly fraud:**
- Maintain a blocklist of cardholders (by card fingerprint, not PAN) and email addresses with prior friendly fraud history. Decline future orders or require additional verification.
- For digital goods: implement access revocation on chargeback filing. If they dispute the charge, revoke their account access immediately — this removes the incentive for friendly fraud (they can't keep the goods and the money).
- Submit device-level evidence aggressively in representment: access logs showing the disputed account was used *after* the claimed dispute date are very strong evidence.
- If the cardholder continues placing orders with new cards, consider IP / device blocking.

**Q12. How does chargeback handling differ for marketplaces and platforms vs. direct merchants?**
A: Marketplaces (platforms where third-party sellers transact) have layered chargeback complexity because the platform is the merchant of record (MOR) but the underlying seller owns the fulfillment.

**The platform-as-MOR chargeback flow:**
```
Buyer files chargeback
        │
        ▼
Card network → Platform's acquirer → Platform (MOR)
        │
        ├── Platform is debited (chargeback amount + fee)
        │
        ├── Platform must decide:
        │     Option A: Absorb the loss (if seller already paid out)
        │     Option B: Claw back from seller's pending payouts
        │     Option C: Debit seller's negative balance (if insufficient pending payouts)
        │
        └── Platform must gather evidence from seller
              (seller has delivery proof, customer communication)
              Platform cannot fight the chargeback without seller's evidence
```

**Key engineering requirements for marketplace chargeback handling:**

1. **Seller payout hold on chargeback** — when a chargeback is received for a seller's order, immediately place a hold on that seller's pending payouts equal to the chargeback amount + fee. Do not release until the chargeback is resolved.

2. **Evidence collection from sellers** — build a seller portal where sellers can upload delivery proof, tracking numbers, and customer communication in response to a chargeback notification. The platform's system compiles this evidence into the representment package.

3. **Seller chargeback ratio monitoring** — track chargeback rates at the seller level, not just the platform level. A single high-fraud seller can push the platform's aggregate ratio above Visa/MC thresholds. Implement automatic seller suspension when their individual chargeback rate exceeds 2–3%.

4. **Reserve policy** — hold a rolling reserve from seller payouts specifically sized to cover their historical chargeback rate: `reserve = seller_gmv * chargeback_rate * avg_chargeback_amount`. This ensures the platform is not left with unrecoverable losses when a seller disappears.

5. **Chargeback liability terms** — the seller agreement must clearly specify that chargebacks arising from their orders are the seller's financial liability (even if the card network names the platform as MOR). This is enforceable in the payout clawback mechanism.

## Section 6: System Design

**Q13. Design a chargeback management system for a payment platform processing 500K transactions/month.**
A: At 500K transactions/month with a 0.5% chargeback rate, expect ~2,500 chargebacks/month. This is beyond spreadsheet management but below the scale requiring fully custom ML — a well-structured automated system with human review for edge cases is the right architecture.

**System components:**

```
Card Network / Acquirer
        │
        │ Chargeback notification
        │ (webhook / SFTP file / API)
        ▼
┌───────────────────────────────────────────────────────┐
│              Chargeback Ingestion Service              │
│  - Parse notification (Visa/MC/Amex format)           │
│  - Normalize to internal chargeback schema            │
│  - Create chargeback record in DB                     │
│  - Debit merchant's account                           │
│  - Start deadline clock                               │
└──────────────────────────┬────────────────────────────┘
                           │
                           ▼
┌───────────────────────────────────────────────────────┐
│              Evidence Aggregation Service              │
│  - Pull authorization record (payments DB)            │
│  - Pull 3DS authentication record (auth service)      │
│  - Pull fulfillment / delivery record (OMS)           │
│  - Pull access logs (analytics / product DB)          │
│  - Pull customer support history (CRM)                │
│  - Pull account / login history (identity service)    │
│  - Score evidence strength                            │
└──────────────────────────┬────────────────────────────┘
                           │
                           ▼
```

**Deadline monitoring (critical — missing a deadline is an automatic loss):**
```python
# Runs every hour
def check_chargeback_deadlines():
    open_cbs = db.query("""
        SELECT id, response_deadline, status, triage_decision
        FROM chargebacks
        WHERE status IN ('open', 'under_review', 'human_queue')
        AND response_deadline > NOW()
        ORDER BY response_deadline ASC
    """)
    
    for cb in open_cbs:
        hours_remaining = (cb.response_deadline - now()).total_hours()
        
        if hours_remaining <= 48 and not cb.escalation_48h_sent:
            alert_ops_team(cb, urgency='HIGH', hours_remaining=hours_remaining)
        
        if hours_remaining <= 168 and not cb.escalation_7d_sent:  # 7 days
            alert_ops_team(cb, urgency='MEDIUM', hours_remaining=hours_remaining)
        
        if hours_remaining <= 2:  # 2 hours before deadline
            if cb.triage_decision == 'human_review' and cb.status == 'human_queue':
                # Human didn't act — force auto-concede to avoid hard deadline miss
                auto_concede(cb, reason='deadline_forced_concession')
                alert_ops_team(cb, urgency='CRITICAL', message='Forced concession due to inaction')
```

**Q14. How do you instrument and report on chargeback health across a merchant portfolio?**
A: Chargeback health reporting must operate at three levels: individual chargeback resolution, merchant-level ratio monitoring, and portfolio-level trend analysis.

**Key metrics:**

```sql
-- Merchant chargeback ratio (Visa/MC methodology: N chargebacks / N-1 transactions)
SELECT
    merchant_id,
    DATE_TRUNC('month', filed_at)                        AS month,
    COUNT(*)                                             AS chargebacks_received,
    LAG(COUNT(*)) OVER (PARTITION BY merchant_id
                        ORDER BY DATE_TRUNC('month', filed_at)) AS prev_month_txns,
    COUNT(*)::FLOAT / NULLIF(
        LAG(COUNT(*)) OVER (PARTITION BY merchant_id
                            ORDER BY DATE_TRUNC('month', filed_at)), 0
    )                                                    AS chargeback_ratio
FROM chargebacks cb
JOIN transactions t ON t.merchant_id = cb.merchant_id
GROUP BY merchant_id, DATE_TRUNC('month', filed_at);

-- Win rate by reason code
SELECT
    reason_code,
    COUNT(*)                                             AS total_disputed,
    SUM(CASE WHEN outcome = 'won' THEN 1 ELSE 0 END)    AS won,
    AVG(CASE WHEN outcome = 'won' THEN 1.0 ELSE 0.0 END) AS win_rate,
    AVG(dispute_amount)                                  AS avg_dispute_amount
FROM chargebacks
WHERE outcome IS NOT NULL
GROUP BY reason_code
ORDER BY total_disputed DESC;

-- Evidence strength vs. win rate correlation
SELECT
    CASE
        WHEN evidence_score >= 80 THEN 'strong'
        WHEN evidence_score >= 50 THEN 'medium'
        ELSE 'weak'
    END                                                  AS evidence_tier,
    COUNT(*)                                             AS count,
    AVG(CASE WHEN outcome = 'won' THEN 1.0 ELSE 0.0 END) AS win_rate
FROM chargebacks
WHERE triage_decision = 'auto_fight' AND outcome IS NOT NULL
GROUP BY evidence_tier;
```

**Alerting thresholds:**
- Merchant chargeback ratio reaches 0.65% (Visa VDMP early warning threshold): automated email to merchant + account manager review.
- Merchant chargeback ratio reaches 0.90%: account manager escalation + required merchant remediation call within 48 hours.
- Merchant ratio reaches 1.0%: risk team review; consider requiring additional reserve; evaluate account suspension.
- Portfolio-wide chargeback ratio increases > 0.1% month-over-month: investigate for systemic fraud pattern or processor/routing issue.
- Response deadline missed on any chargeback: PagerDuty to operations team (this is an avoidable loss).

**Q15. "A merchant's chargeback rate jumped from 0.4% to 1.2% in a single month. Walk through your investigation."**
A: A 3× spike in chargeback rate in one month is a serious signal requiring immediate, systematic investigation.

**Step 1 — Segment the spike (first 2 hours)**
```sql
-- Which reason codes are driving the spike?
SELECT reason_code, COUNT(*),
       COUNT(*) * 100.0 / SUM(COUNT(*)) OVER () AS pct_of_total
FROM chargebacks
WHERE merchant_id = [merchant] AND filed_at >= [spike_month_start]
GROUP BY reason_code ORDER BY COUNT(*) DESC;

-- Is it concentrated in a time range, product, or payment method?
SELECT
    DATE_TRUNC('week', order.created_at) AS order_week,
    order.product_category,
    payment.card_type,
    COUNT(cb.id)
FROM chargebacks cb
JOIN orders order ON order.id = cb.order_id
JOIN payments payment ON payment.order_id = order.id
WHERE cb.merchant_id = [merchant]
GROUP BY 1, 2, 3 ORDER BY 1;
```

**Step 2 — Identify the pattern:**

*Spike is in `10.4` (Fraud — Unauthorized Transaction):*
- Check if the merchant had a data breach or account compromise event.
- Check if a batch of stolen card numbers is being tested against this merchant (card testing attack — many small-amount transactions in a short window, many of which may have succeeded before fraud was detected).
- Check if 3DS is enabled and functioning — a sudden auth rate drop on 3DS could indicate misconfiguration.
- Check for a new product or channel launch that bypassed fraud controls.

*Spike is in `13.1` (Not Received):*
- Check if there was a fulfillment or shipping delay (carrier issues, warehouse problem, supplier disruption).
- Check if delivery confirmation data is being properly captured — a system bug that stopped recording delivery proof will cause all these to be unwinnable.
- Check if a geographic region is affected (shipping carrier failure in a specific region).

*Spike is in `13.2` (Cancelled Recurring):*
- Check for a subscription billing system bug that charged lapsed subscribers.
- Check for a failed cancellation flow — customers who attempted to cancel but were still billed.
- Check if a free trial converted to paid without clear notification.

*Spike is in `12.6` (Duplicate Processing):*
- Check for a double-charge bug in the payment processing code — a common cause is an idempotency key failure allowing duplicate captures.
- Check if a batch re-processing job ran accidentally.

**Step 3 — Immediate containment:**
- If card testing is detected: enable velocity rules (max N transactions per card per hour), enable CAPTCHA on checkout, alert the processor's risk team.
- If fulfillment failure: pause new orders in the affected region; proactively contact customers with undelivered orders before they file chargebacks (alert service-style).
- If billing bug: immediately halt the billing run; identify all affected customers; issue refunds proactively (a refund costs less than a chargeback).
- If duplicate charge: trigger automatic refunds for all confirmed duplicates before chargebacks are filed.

**Step 4 — Long-term remediation:**
- Document root cause and fix.
- File representment for all winnable chargebacks (3DS evidence for fraud spike, delivery proof for `13.1`).
- Implement the missing control (3DS, delivery confirmation capture, billing idempotency).
- Monitor chargeback ratio weekly for 3 months to confirm return to baseline.
- If already in VDMP: submit a formal remediation plan to the acquirer.
