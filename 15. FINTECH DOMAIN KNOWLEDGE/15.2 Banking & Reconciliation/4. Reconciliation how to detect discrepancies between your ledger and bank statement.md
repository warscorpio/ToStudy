# Reconciliation: Detecting Discrepancies Between Ledger and Bank Statement — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is financial reconciliation, and why is it a core engineering responsibility in fintech — not just an accounting task?**
A: Reconciliation is the process of comparing two or more independent records of financial activity to confirm they agree, and systematically investigating and resolving any differences. In fintech, the canonical reconciliation is your internal ledger vs. the bank statement — but in practice it is always at minimum a three-way comparison:

```
Your internal ledger
      ↕
Payment gateway settlement file
      ↕
Bank account statement (credit/debit advices)
```

Why it is an engineering responsibility:
- **Data arrives from external systems with no delivery guarantees** — gateway webhooks are lost, bank files arrive late, NPCI reversals happen asynchronously. Without reconciliation, your ledger silently diverges from reality.
- **Financial bugs are silent** — a missing ledger entry doesn't throw an exception. It accumulates into an unexplained ₹50,000 shortfall discovered weeks later.
- **Regulatory mandate** — RBI requires payment aggregators to reconcile daily and maintain audit trails. SEBI requires brokers to reconcile client funds daily. PCI-DSS requires transaction reconciliation. Non-compliance is a license risk, not just a fine.
- **Customer money is involved** — a discrepancy between your ledger and the bank is not an abstract data inconsistency; it means either you owe a merchant money you haven't paid, or you've paid money you shouldn't have. Both are business-critical.

At the 5 YOE level, you are expected to design reconciliation systems, not just run them. This means: schema design for reconciliation state tracking, matching algorithms, exception queues, SLA monitoring, and automated resolution for common discrepancy types.

**Q2. What are the four types of reconciliation discrepancies, and what does each indicate?**
A: Every reconciliation discrepancy falls into one of four categories:

| Discrepancy Type | Definition | Typical cause |
|---|---|---|
| **Missing in ledger, present in bank** | Bank shows a credit/debit with no matching ledger entry | Webhook missed; DB write failed after gateway confirmed; direct bank transfer bypassed your API |
| **Present in ledger, missing in bank** | Ledger shows a transaction that has no corresponding bank movement | Gateway settled but bank hasn't credited yet (timing); ledger entry posted in error; bank batch not yet received |
| **Amount mismatch** | Both records exist but amounts differ | FX rate difference; fee deduction not modeled; rounding error; partial settlement |
| **Date mismatch** | Both records exist with matching amounts but different dates | Settlement lag (T+1, T+2); cut-off time differences (bank processes at midnight; gateway reports at 6pm) |

A well-designed reconciliation system classifies every exception into one of these four buckets automatically — it doesn't dump a list of unmatched rows on an analyst's desk. Each bucket has a different investigation path and a different expected resolution time.

**Q3. What is the difference between real-time reconciliation and batch reconciliation, and when do you use each?**
A: The two modes address different failure classes:

**Real-time reconciliation (event-driven)**
- Triggered on every incoming webhook or payment event.
- Checks: does this gateway event have a matching internal transaction? Does the amount match? Does the status transition make sense?
- Catches: duplicate webhooks, unexpected status transitions, amount tampering.
- Implemented as: a webhook handler that runs a matching query before processing.

```typescript
// Real-time check on every webhook
async function processGatewayWebhook(event: GatewayEvent): Promise<void> {
  const internal = await db('payments')
    .where({ gateway_payment_id: event.payment_id })
    .first();

  if (!internal) {
    await reconciliationExceptionQueue.add({
      type: 'MISSING_IN_LEDGER',
      gateway_event_id: event.id,
      gateway_payment_id: event.payment_id,
      amount: event.amount,
      currency: event.currency,
      severity: 'HIGH',
    });
    return;
  }

  if (internal.amount !== BigInt(event.amount)) {
    await reconciliationExceptionQueue.add({
      type: 'AMOUNT_MISMATCH',
      internal_payment_id: internal.id,
      gateway_event_id: event.id,
      internal_amount: internal.amount,
      gateway_amount: BigInt(event.amount),
      delta: BigInt(event.amount) - internal.amount,
      severity: 'CRITICAL',
    });
    return;
  }

  // Amounts match — proceed with normal processing
  await transitionPaymentStatus(internal.id, mapGatewayStatus(event.status));
}
```

**Batch reconciliation (scheduled)**
- Runs once per day (typically at 02:00–06:00, after bank files arrive).
- Compares the full set of transactions for the prior business day across all three sources.
- Catches: timing gaps that closed overnight, accumulation of small discrepancies, missing settlements.
- Implemented as: a job that loads the gateway settlement CSV and bank statement, matches against ledger entries for the period, and produces an exception report.

Use both: real-time catches individual event anomalies immediately; batch catches systemic gaps that individual event checks miss.

**Q4. What is a settlement file, and what fields does it typically contain?**
A: A settlement file is the gateway's or bank's authoritative record of what funds they actually moved for a given settlement period. It is the external source of truth — if your ledger disagrees with the settlement file, your ledger is wrong until proven otherwise.

Typical gateway settlement file (Razorpay, Cashfree, PayU — CSV format):

| Field | Description | Reconciliation use |
|---|---|---|
| `settlement_id` | Unique ID for this settlement batch | Links settlement to bank credit |
| `payment_id` | Gateway's transaction reference | Primary match key against your `gateway_payment_id` |
| `order_id` | Your order reference (if sent to gateway) | Secondary match key |
| `amount` | Gross transaction amount (paise) | Match against `payments.amount` |
| `fee` | Gateway transaction fee deducted | Match against your `gateway_fee` model |
| `tax` | GST on gateway fee | Verify against expected GST rate |
| `settlement_amount` | Net amount after fee and tax | Should match your `merchant_payable` ledger credit |
| `settled_at` | Date of settlement | Used for date-range filtering |
| `payment_type` | UPI / card / netbanking | For method-level reconciliation |
| `utr` | Unique Transaction Reference (NPCI) | Matches to bank statement credit |

The bank statement has a corresponding credit entry:
- `UTR` / `reference_number` — matches the settlement file's `utr` field.
- `amount` — should equal `SUM(settlement_amount)` for that settlement batch.
- `value_date` — the date funds were available (may differ from the gateway's `settled_at` by 1 day).

**Q5. What is a UTR number, and why is it the critical linking key in Indian payment reconciliation?**
A: UTR (Unique Transaction Reference) is the reference number assigned by NPCI or the banking network to every fund transfer in India. It is the primary key that links:

```
Gateway settlement file (utr column)
      ↕
Bank statement (reference / transaction_id column)
      ↕
NPCI transaction log (for UPI)
```

UTR format by payment type:
- **NEFT**: 16-character alphanumeric (e.g., `HDFC224170000001`)
- **RTGS**: 22-character (e.g., `HDFCN24170000001`)
- **IMPS**: 12-digit numeric (e.g., `410123456789`)
- **UPI**: 12-digit numeric (same as IMPS reference, assigned by NPCI)

Why UTR is the critical key:
- A settlement batch may contain 10,000 transactions but arrive at the bank as a single NEFT credit. The UTR on the bank statement identifies the batch; the gateway settlement file maps individual transactions to that UTR.
- Without UTR matching, you cannot tell which bank credit corresponds to which gateway settlement batch — you can only match on amount, which fails when two batches have the same amount.
- UTR is immutable — it never changes after assignment. It is the stable foreign key that makes three-way reconciliation possible.

Schema:
```sql
ALTER TABLE payments ADD COLUMN utr TEXT;   -- populated on settlement receipt
CREATE INDEX idx_payments_utr ON payments(utr) WHERE utr IS NOT NULL;
```

## Section 2: The Reconciliation Engine

**Q6. How do you design a reconciliation engine schema to track the matching state of every transaction?**
A: The reconciliation engine needs its own data model — not just the `payments` table. Each transaction in each source system gets a `reconciliation_record`, and the engine tracks matching state across records.

```sql
-- Canonical source of each transaction from an external system
CREATE TABLE reconciliation_records (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  recon_run_id      UUID NOT NULL REFERENCES reconciliation_runs(id),
  source            recon_source NOT NULL,   -- 'LEDGER', 'GATEWAY', 'BANK'
  source_id         TEXT NOT NULL,            -- payment_id / settlement_id / bank_ref
  amount            BIGINT NOT NULL,          -- in minor units
  currency          CHAR(3) NOT NULL,
  transaction_date  DATE NOT NULL,
  raw_data          JSONB NOT NULL,           -- original row from source (for audit)
  matched_to_id     UUID REFERENCES reconciliation_records(id),
  match_status      match_status NOT NULL DEFAULT 'UNMATCHED',
  -- UNMATCHED, MATCHED, PARTIAL_MATCH, EXCEPTION
  exception_type    TEXT,   -- MISSING_IN_LEDGER, AMOUNT_MISMATCH, etc.
  exception_notes   TEXT,
  resolved_at       TIMESTAMPTZ,
  resolved_by       TEXT
);

CREATE TYPE recon_source AS ENUM ('LEDGER', 'GATEWAY', 'BANK');
CREATE TYPE match_status AS ENUM ('UNMATCHED', 'MATCHED', 'PARTIAL_MATCH', 'EXCEPTION');

-- A reconciliation run covers one settlement period
CREATE TABLE reconciliation_runs (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  settlement_date   DATE NOT NULL UNIQUE,
  status            TEXT NOT NULL DEFAULT 'PENDING',
  -- PENDING, LOADING, MATCHING, COMPLETE, FAILED
  ledger_count      INT,
  gateway_count     INT,
  bank_count        INT,
  matched_count     INT,
  exception_count   INT,
  total_ledger_amount     BIGINT,
  total_gateway_amount    BIGINT,
  total_bank_amount       BIGINT,
  started_at        TIMESTAMPTZ,
  completed_at      TIMESTAMPTZ,
  error_message     TEXT
);
```

**Q7. What is the matching algorithm for a three-way reconciliation, and how do you handle the order of matching?**
A: Matching proceeds in passes, from most confident to least confident. Each pass marks matched records, leaving only genuinely unmatched rows for the next pass.

```typescript
async function runReconciliation(runId: string, settlementDate: Date): Promise<void> {
  // Pass 1 — Exact match: gateway_payment_id + amount + currency
  // Highest confidence: unique ID from gateway matches both ledger and bank
  await matchByGatewayId(runId, settlementDate);

  // Pass 2 — UTR match: for bank ↔ gateway matching
  // Bank statement has UTR; gateway settlement file has UTR
  await matchByUtr(runId, settlementDate);

  // Pass 3 — Order ID match: if gateway_payment_id diverges but order_id is consistent
  // Handles cases where payment was retried with a new gateway_payment_id
  await matchByOrderId(runId, settlementDate);

  // Pass 4 — Amount + date window match (fuzzy): ±1 day, exact amount
  // Catches date-shifted entries (bank processes at midnight; ledger at 11:59pm)
  await matchByAmountAndDateWindow(runId, settlementDate, windowDays: 1);

  // Pass 5 — Remainder: all still-UNMATCHED records become exceptions
  await classifyExceptions(runId);

  await updateRunSummary(runId);
}
```

**Pass 1 — Exact match implementation:**
```typescript
async function matchByGatewayId(runId: string, settlementDate: Date): Promise<void> {
  // Find ledger records and gateway records with the same gateway_payment_id
  await db.raw(`
    WITH matches AS (
      SELECT
        l.id AS ledger_rec_id,
        g.id AS gateway_rec_id
      FROM reconciliation_records l
      JOIN reconciliation_records g
        ON l.source_id = g.source_id          -- same gateway_payment_id
        AND l.amount   = g.amount              -- same amount
        AND l.currency = g.currency
      WHERE l.recon_run_id = :runId
        AND l.source = 'LEDGER'
        AND l.match_status = 'UNMATCHED'
        AND g.source = 'GATEWAY'
        AND g.match_status = 'UNMATCHED'
    )
    UPDATE reconciliation_records r
    SET
      match_status  = 'MATCHED',
      matched_to_id = CASE
        WHEN r.id = m.ledger_rec_id  THEN m.gateway_rec_id
        WHEN r.id = m.gateway_rec_id THEN m.ledger_rec_id
      END
    FROM matches m
    WHERE r.id IN (m.ledger_rec_id, m.gateway_rec_id)
  `, { runId });
}
```

**Pass 4 — Amount + date window (fuzzy) match:**
```typescript
async function matchByAmountAndDateWindow(
  runId: string,
  settlementDate: Date,
  windowDays: number,
): Promise<void> {
  await db.raw(`
    WITH candidates AS (
      SELECT
        l.id  AS ledger_rec_id,
        g.id  AS gateway_rec_id,
        ROW_NUMBER() OVER (
          PARTITION BY l.id
          ORDER BY ABS(g.transaction_date - l.transaction_date)
        ) AS rn   -- prefer closest date when multiple candidates
      FROM reconciliation_records l
      JOIN reconciliation_records g
        ON l.amount   = g.amount
        AND l.currency = g.currency
        AND ABS(g.transaction_date - l.transaction_date) <= :windowDays
      WHERE l.recon_run_id = :runId
        AND l.source = 'LEDGER'  AND l.match_status = 'UNMATCHED'
        AND g.source = 'GATEWAY' AND g.match_status = 'UNMATCHED'
    )
    UPDATE reconciliation_records r
    SET match_status = 'MATCHED', matched_to_id = ...
    FROM candidates c WHERE c.rn = 1 AND r.id IN (c.ledger_rec_id, c.gateway_rec_id)
  `, { runId, windowDays });
}
```

**Q8. How do you ingest and parse settlement files reliably, given that gateways change their formats?**
A: Settlement file ingestion is a classic ETL problem with financial stakes. The failures are silent — a malformed CSV that parses to zero rows passes silently and your reconciliation shows "100% matched" because there was nothing to match against.

**Defensive ingestion pipeline:**
```typescript
interface SettlementFileIngestor {
  parse(rawContent: Buffer): Promise<RawSettlementRow[]>;
  validate(rows: RawSettlementRow[]): ValidationResult;
  normalize(rows: RawSettlementRow[]): NormalizedSettlementRecord[];
}

class RazorpaySettlementIngestor implements SettlementFileIngestor {
  async parse(rawContent: Buffer): Promise<RawSettlementRow[]> {
    const text = rawContent.toString('utf-8');
    const rows = await parseCSV(text, { headers: true, skipEmptyLines: true });

    if (rows.length === 0) {
      throw new EmptySettlementFileError('Razorpay settlement file has zero rows');
    }
    return rows;
  }

  validate(rows: RawSettlementRow[]): ValidationResult {
    const errors: string[] = [];

    // Schema validation: required columns present
    const required = ['payment_id', 'amount', 'fee', 'settlement_amount', 'settled_at'];
    for (const col of required) {
      if (!Object.keys(rows[0]).includes(col)) {
        errors.push(`Missing required column: ${col}`);
      }
    }

    // Arithmetic validation: amount - fee - tax = settlement_amount for each row
    for (const row of rows) {
      const expected = BigInt(row.amount) - BigInt(row.fee) - BigInt(row.tax);
      const actual = BigInt(row.settlement_amount);
      if (expected !== actual) {
        errors.push(`Row ${row.payment_id}: arithmetic mismatch: ${expected} ≠ ${actual}`);
      }
    }

    // Control total: sum of settlement_amount should match header total (if present)
    if (rows[0].header_total) {
      const summed = rows.reduce((acc, r) => acc + BigInt(r.settlement_amount), 0n);
      if (summed !== BigInt(rows[0].header_total)) {
        errors.push(`Control total mismatch: computed=${summed}, header=${rows[0].header_total}`);
      }
    }

    return { valid: errors.length === 0, errors };
  }

  normalize(rows: RawSettlementRow[]): NormalizedSettlementRecord[] {
    return rows.map(row => ({
      source: 'GATEWAY' as const,
      source_id: row.payment_id,
      amount: BigInt(row.amount),
      fee: BigInt(row.fee),
      tax: BigInt(row.tax),
      settlement_amount: BigInt(row.settlement_amount),
      currency: 'INR',
      utr: row.utr ?? null,
      transaction_date: parseISO(row.settled_at),
      raw_data: row,
    }));
  }
}
```

**Format versioning:** Gateway formats change without notice. Maintain a version table:
```sql
CREATE TABLE settlement_file_formats (
  gateway       TEXT NOT NULL,
  version       TEXT NOT NULL,
  effective_from DATE NOT NULL,
  column_mapping JSONB NOT NULL,   -- {"payment_id": "txn_id", "amount": "gross_amount"}
  PRIMARY KEY (gateway, version)
);
```

When a format change breaks ingestion, add a new version row and deploy the updated parser. Old files can be re-parsed against the old format version.

**Q9. How do you handle timing differences between when your ledger records a transaction and when it appears on the bank statement?**
A: Timing differences are the most common "false discrepancy" in reconciliation — transactions that are genuinely correct but appear in different periods depending on the source's cut-off time.

**Common timing gaps in Indian payments:**

| Scenario | Ledger records | Bank statement shows | Gap |
|---|---|---|---|
| NEFT batch | Transaction time (e.g., 15:00) | Value date next business day | T+1 |
| RTGS | Transaction time | Same day if before cut-off (18:00) | 0 or T+1 |
| UPI (NPCI) | On webhook receipt | Bank statement next morning | Hours |
| Gateway settlement | On webhook | After bank batch processing | T+1 to T+2 |
| Month-end | March 31 (ledger) | April 1 (bank value date) | Crosses period |

**Handling strategy — the open items window:**
```sql
-- Transactions that are unmatched but within the timing tolerance window
-- are "open items" — not exceptions yet
CREATE TABLE reconciliation_open_items (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  recon_record_id   UUID NOT NULL REFERENCES reconciliation_records(id),
  expected_in_source recon_source NOT NULL,  -- which source we're waiting for
  earliest_expected_date DATE NOT NULL,       -- when we expect it to appear
  latest_expected_date   DATE NOT NULL,       -- after this, escalate to exception
  carry_forward_count    INT NOT NULL DEFAULT 0,  -- how many days it's been open
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```typescript
async function classifyTimingDifferences(runId: string, settlementDate: Date): Promise<void> {
  // Ledger entries present but not yet in gateway file — check if within T+2 window
  const ledgerOnly = await getUnmatchedLedgerRecords(runId);

  for (const record of ledgerOnly) {
    const daysSinceTransaction = differenceInBusinessDays(settlementDate, record.transaction_date);

    if (daysSinceTransaction <= 2) {
      // Within T+2 window — open item, not exception
      await db('reconciliation_open_items').insert({
        recon_record_id: record.id,
        expected_in_source: 'GATEWAY',
        earliest_expected_date: settlementDate,
        latest_expected_date: addBusinessDays(record.transaction_date, 3),
      });
    } else {
      // Beyond T+2 — genuine exception
      await db('reconciliation_records').where({ id: record.id }).update({
        match_status: 'EXCEPTION',
        exception_type: 'MISSING_IN_GATEWAY_BEYOND_WINDOW',
      });
    }
  }
}
```

## Section 3: Exception Handling

**Q10. How do you classify, prioritize, and route reconciliation exceptions?**
A: Not all exceptions are equal. A ₹5 rounding difference and a ₹5,00,000 missing settlement require different response times and teams. The exception routing system:

```typescript
interface ReconciliationException {
  type: ExceptionType;
  amount: bigint;
  currency: string;
  age_days: number;        // how many days since the discrepancy first appeared
  affected_merchant_id?: string;
  is_customer_facing: boolean;
}

type ExceptionType =
  | 'MISSING_IN_LEDGER'           // bank/gateway has it; we don't
  | 'MISSING_IN_GATEWAY'          // we have it; gateway doesn't (yet)
  | 'MISSING_IN_BANK'             // gateway settled; bank hasn't credited
  | 'AMOUNT_MISMATCH'             // amounts differ
  | 'DATE_MISMATCH'               // amounts match; dates differ by > tolerance
  | 'DUPLICATE_IN_LEDGER'         // same transaction posted twice
  | 'DUPLICATE_IN_GATEWAY'        // gateway sent duplicate settlement
  | 'UNIDENTIFIED_BANK_CREDIT'    // bank credit with no gateway match
  | 'UNIDENTIFIED_BANK_DEBIT';    // bank debit not in our ledger

function classifySeverity(exception: ReconciliationException): 'CRITICAL' | 'HIGH' | 'MEDIUM' | 'LOW' {
  // Any missing amount above ₹10,000 or customer-facing: critical
  if (exception.amount > 1_000_000n || exception.is_customer_facing) return 'CRITICAL';

  // Duplicate posting: always high — money created or destroyed
  if (exception.type === 'DUPLICATE_IN_LEDGER') return 'CRITICAL';

  // Unidentified bank debit: possible fraud or bank error — high
  if (exception.type === 'UNIDENTIFIED_BANK_DEBIT') return 'HIGH';

  // Amount mismatch: high if delta > ₹100
  if (exception.type === 'AMOUNT_MISMATCH' && exception.amount > 10_000n) return 'HIGH';

  // Old open items: escalate with age
  if (exception.age_days > 3) return 'HIGH';
  if (exception.age_days > 1) return 'MEDIUM';

  return 'LOW';
}

async function routeException(exception: ReconciliationException): Promise<void> {
  const severity = classifySeverity(exception);

  switch (severity) {
    case 'CRITICAL':
      await pagerDuty.trigger({ severity: 'critical', summary: exceptionSummary(exception) });
      await createJiraTicket({ priority: 'P1', team: 'payments-ops', exception });
      break;
    case 'HIGH':
      await slack.post('#recon-alerts', formatException(exception));
      await createJiraTicket({ priority: 'P2', team: 'payments-ops', exception });
      break;
    case 'MEDIUM':
      await createJiraTicket({ priority: 'P3', team: 'finance-ops', exception });
      break;
    case 'LOW':
      // Batch into daily finance ops report — no ticket
      await appendToDailyReport(exception);
      break;
  }
}
```

**Q11. What are the most common reconciliation exception types, and what is the automated resolution for each?**
A: Exceptions with well-defined root causes can be auto-resolved; those with ambiguous causes require human review.

**Exception: MISSING_IN_LEDGER (gateway has it; ledger doesn't)**
Root cause: webhook was not delivered or DB write failed after gateway confirmed.
Auto-resolution:
```typescript
async function resolveGatewayWebhookMiss(exception: ReconException): Promise<void> {
  // Re-fetch from gateway API to confirm
  const gatewayPayment = await gatewayClient.getPayment(exception.gateway_payment_id);

  if (gatewayPayment.status === 'captured') {
    // Post the missing ledger entry
    await postLedgerTransaction({
      idempotencyKey: `recon-recovery:${exception.gateway_payment_id}`,
      entries: buildCaptureEntries(gatewayPayment),
    });
    await transitionPaymentStatus(exception.internal_payment_id, 'SUCCESS', 'recon_recovery');
    await markExceptionResolved(exception.id, 'AUTO_RESOLVED: webhook miss recovered');
  }
}
```

**Exception: DUPLICATE_IN_LEDGER**
Root cause: idempotency bug — same payment posted twice.
Auto-resolution: identify the duplicate (usually the later one), post a reversal entry, flag for manual confirmation. Never auto-delete — immutable ledger.

**Exception: AMOUNT_MISMATCH (small delta)**
Root cause: rounding difference between your calculation and gateway's.
Auto-resolution if delta ≤ ₹1 (100 paise): post a rounding adjustment entry to a `Reconciliation Rounding` GL account.
```typescript
if (Math.abs(Number(delta)) <= 100) {  // ≤ ₹1
  await postLedgerTransaction({
    idempotencyKey: `recon-rounding:${exception.id}`,
    entries: [
      { account: 'RECONCILIATION_ROUNDING', type: delta > 0 ? 'DEBIT' : 'CREDIT', amount: abs(delta) },
      { account: 'GATEWAY_SETTLEMENT_RECEIVABLE', type: delta > 0 ? 'CREDIT' : 'DEBIT', amount: abs(delta) },
    ],
  });
}
// Delta > ₹1: require human review
```

**Exception: UNIDENTIFIED_BANK_CREDIT**
Root cause: bank received a fund transfer your system has no record of. Possible: customer direct transfer, bank error, test transaction.
Resolution: never auto-resolve. Create a `suspense` liability account credit; require finance team to investigate and reclassify within 5 business days (RBI requirement for unexplained credits to a PA nodal account).

**Q12. How do you design a suspense account for unresolved reconciliation differences?**
A: A suspense account is a temporary holding GL account used when you receive money but don't yet know where it belongs, or when there's a confirmed difference that hasn't been investigated yet. It is a liability (you owe someone this money, you just don't know who).

```sql
-- Suspense account in Chart of Accounts
INSERT INTO accounts (code, name, type, currency) VALUES
  ('2099', 'Reconciliation Suspense', 'LIABILITY', 'INR');
```

When an unidentified bank credit arrives:
```
Dr  Bank Account (Asset)           ₹10,000
  Cr  Reconciliation Suspense (Liability)  ₹10,000
```

When the suspense is cleared (cause identified):
```
Dr  Reconciliation Suspense (Liability)  ₹10,000
  Cr  [correct account — Merchant Payable, Customer Refund, etc.]  ₹10,000
```

Suspense account rules:
- **Must be zero by period close** (monthly, or daily for RBI-regulated entities). A non-zero suspense balance at period close is a red flag in audit.
- **Every suspense entry must carry an expiry SLA** — typically 5 business days before escalation.
- **Report daily** — finance team must review all suspense entries every morning; no entry should age without an owner.

```sql
-- Suspense aging report
SELECT
  le.id,
  le.amount,
  le.description,
  le.posted_at,
  CURRENT_DATE - le.posted_at::DATE AS age_days,
  le.created_by
FROM ledger_entries le
JOIN accounts a ON a.id = le.account_id
WHERE a.code = '2099'   -- Reconciliation Suspense
  AND le.id NOT IN (
    SELECT reverses_entry_id FROM ledger_entries WHERE reverses_entry_id IS NOT NULL
  )  -- not yet reversed (i.e., still open)
ORDER BY le.posted_at ASC;
```

## Section 4: Indian Fintech & Regulatory Context

**Q13. What are the RBI mandates on reconciliation for payment aggregators, and how do they translate to engineering requirements?**
A: RBI's PA/PG Master Directions (2020) and subsequent circulars impose specific reconciliation obligations:

**Mandate 1 — Daily reconciliation**
PAs must reconcile all transactions between their system, the payment network (NPCI/card networks), and their nodal bank account every business day. Engineering requirement: automated daily reconciliation job that completes by 09:00 the next morning, with a summary report filed with the compliance team.

**Mandate 2 — Unexplained credits to nodal account**
Any credit to the nodal account that cannot be matched to a known settlement within 5 business days must be reported to the RBI. Engineering requirement: `UNIDENTIFIED_BANK_CREDIT` exceptions must be automatically escalated at T+3 with a Jira ticket; a formal report generated at T+5 if still unresolved.

**Mandate 3 — Merchant settlement SLA**
Collected funds must be settled to merchants within T+1 for standard e-commerce and T+0 for some categories. Engineering requirement: settlement lag must be tracked per transaction in the ledger, and an SLA breach alert fires if a merchant's receivable is older than the allowed settlement window.

```sql
-- SLA breach detection
SELECT
  p.id AS payment_id,
  p.merchant_id,
  p.amount,
  p.status,
  p.updated_at AS captured_at,
  CURRENT_DATE - p.updated_at::DATE AS days_since_capture,
  m.settlement_sla_days
FROM payments p
JOIN merchants m ON m.id = p.merchant_id
WHERE p.status = 'SUCCESS'
  AND p.payout_id IS NULL    -- not yet paid out
  AND (CURRENT_DATE - p.updated_at::DATE) > m.settlement_sla_days
ORDER BY days_since_capture DESC;
```

**Mandate 4 — Audit trail retention**
All reconciliation records, settlement files, exception logs, and resolution actions must be retained for 5 years. Engineering requirement: settlement files stored in S3 (versioned, immutable); reconciliation run records never deleted; exception audit trail with every action timestamped and attributed.

**Q14. How do NPCI's dispute and chargeback timelines affect your reconciliation design?**
A: Chargebacks and disputes create delayed reversals — a transaction that was `SUCCESS` in your ledger can be reversed by NPCI or the card network weeks later.

UPI dispute timeline (NPCI mandate):
- **T+3**: Customer can raise a dispute via their UPI app.
- **T+5**: Merchant must respond with transaction evidence.
- **T+7–T+30**: NPCI arbitrates; if ruled in customer's favor, NPCI debits the PA's nodal account.

Card chargeback timeline (Visa/Mastercard):
- **Up to 120 days** after transaction: customer can file a chargeback.
- Your nodal account is debited immediately when chargeback is filed; you then have 30–45 days to provide evidence for reversal.

Engineering implications:
1. **Never consider a reconciliation period "closed"** — a `SUCCESS` transaction from 90 days ago can still generate a ledger debit today via chargeback. Reconciliation must handle out-of-period adjustments.
2. **Chargeback staging**: when a chargeback debit appears on the bank statement, it must be matched against the original payment. Schema:

```sql
CREATE TABLE chargebacks (
  id                UUID PRIMARY KEY,
  payment_id        UUID NOT NULL REFERENCES payments(id),
  chargeback_ref    TEXT NOT NULL,         -- network's chargeback reference
  amount            BIGINT NOT NULL,
  currency          CHAR(3) NOT NULL,
  reason_code       TEXT NOT NULL,         -- e.g., 'UNAUTHORIZED_TRANSACTION'
  network           TEXT NOT NULL,         -- 'NPCI', 'VISA', 'MASTERCARD'
  filed_at          DATE NOT NULL,
  response_due_date DATE NOT NULL,
  status            TEXT NOT NULL DEFAULT 'RECEIVED',
  -- RECEIVED, EVIDENCE_SUBMITTED, WON, LOST
  bank_debit_utr    TEXT,                  -- UTR of the bank debit for this chargeback
  resolution_at     TIMESTAMPTZ
);
```

3. **Reconciliation rule for chargeback debits**: bank statement shows a debit with a chargeback reference. Reconciliation engine matches on `chargeback_ref`, transitions chargeback to `RECEIVED`, posts a reversal entry on the original payment's ledger account.

**Q15. How do you reconcile UPI transactions specifically, given NPCI's two-leg settlement model?**
A: UPI has a split-leg settlement architecture that creates reconciliation complexity unique to India:

```
Customer's bank (debit leg)  ─── NPCI ───  Merchant's bank (credit leg)
                                  ↓
                          PA's nodal account
```

For a payment aggregator:
- NPCI debits the customer's account and credits the PA's nodal account (debit leg settled).
- PA's system then credits the merchant's account (either same-day or T+1).

The two NPCI files:
- **Inward settlement file**: credits to your nodal account (customer payments collected).
- **Outward settlement file**: debits from your nodal account (merchant payouts made).

Three-way reconciliation for UPI:
```
Inward NPCI file ↔ Your payment ledger (payment receipts) ↔ Nodal bank credit
Outward NPCI file ↔ Your payout ledger (merchant payouts) ↔ Nodal bank debit
```

Special case — **UPI reversal (NPCI-initiated)**:
When a UPI credit leg fails (merchant's bank is down), NPCI auto-reverses the debit leg within 48 hours. Your ledger shows `SUCCESS` (debit leg succeeded); the reversal arrives as an unexpected debit on your nodal account.

Reconciliation handling:
```typescript
async function handleNpciReversal(bankDebit: BankStatement): Promise<void> {
  // Try to match the debit to a known NPCI reversal
  const reversal = await db('npci_reversals')
    .where({ utr: bankDebit.reference_number })
    .first();

  if (reversal) {
    // Known reversal — post reversal ledger entry on original payment
    await postLedgerTransaction({
      idempotencyKey: `npci-reversal:${reversal.id}`,
      entries: buildReversalEntries(reversal.payment_id, reversal.amount),
    });
    await transitionPaymentStatus(reversal.payment_id, 'REVERSED', 'npci_auto_reversal');
  } else {
    // Unknown debit — suspense account, escalate
    await postSuspenseDebit(bankDebit.amount, `UNKNOWN_NPCI_DEBIT:${bankDebit.reference_number}`);
    await escalateUnknownDebit(bankDebit);
  }
}
```

**Q17. How do you design the reconciliation job for reliability — what happens when the job fails midway?**
A: A reconciliation job that partially runs and then fails is worse than one that didn't run at all — it leaves the system in an inconsistent state where some records are marked MATCHED and others are still UNMATCHED but should have been matched.

**Idempotent, restartable design:**
```typescript
async function runReconciliationJob(settlementDate: Date): Promise<void> {
  // Step 1 — Create or resume a run record
  let run = await db('reconciliation_runs')
    .where({ settlement_date: settlementDate })
    .first();

  if (!run) {
    run = await db('reconciliation_runs').insert({
      settlement_date: settlementDate,
      status: 'PENDING',
    }).returning('*').then(r => r[0]);
  }

  if (run.status === 'COMPLETE') {
    logger.info('Reconciliation already complete for', settlementDate);
    return;
  }

  // Step 2 — Load sources (idempotent: skip if already loaded for this run)
  if (run.status === 'PENDING') {
    await updateRunStatus(run.id, 'LOADING');
    await loadLedgerRecords(run.id, settlementDate);
    await loadGatewaySettlementFile(run.id, settlementDate);
    await loadBankStatement(run.id, settlementDate);
    await updateRunStatus(run.id, 'MATCHING');
  }

  // Step 3 — Match (each pass is idempotent: only touches UNMATCHED records)
  if (run.status === 'MATCHING') {
    await matchByGatewayId(run.id, settlementDate);
    await matchByUtr(run.id, settlementDate);
    await matchByOrderId(run.id, settlementDate);
    await matchByAmountAndDateWindow(run.id, settlementDate, 1);
    await classifyExceptions(run.id);
    await updateRunStatus(run.id, 'COMPLETE');
  }
}
```

Each matching pass operates only on `UNMATCHED` records — re-running a completed pass is a no-op because there are no `UNMATCHED` records left to process. If the job crashes mid-pass, restarting picks up from the same status and completes cleanly.

**Q18. How do you handle month-end and financial-year-end reconciliation, which involves cut-off timing complications?**
A: Period-end reconciliation is harder than daily reconciliation because a single-day cut-off must cleanly divide transactions that spanned the boundary.

**The cut-off problem:**
- A customer pays at 23:58 on March 31.
- Your ledger records it at 23:58 on March 31 (financial year end).
- NPCI settles it on April 1 (new financial year).
- Bank statement shows it on April 2.

Which financial year does this transaction belong to? Answer: the year in which the economic event occurred — March 31, per accrual accounting. The settlement on April 1 is a subsequent event.

**Cut-off reconciliation approach:**
```sql
-- March 31 year-end: classify all open items as prior-year or new-year
UPDATE reconciliation_open_items oi
SET
  accounting_period  = CASE
    WHEN r.transaction_date <= '2024-03-31' THEN '2023-24'
    ELSE '2024-25'
  END
FROM reconciliation_records r
WHERE r.id = oi.recon_record_id
  AND oi.created_at::DATE IN ('2024-03-31', '2024-04-01');
```

**Accrual entries for year-end:**
For NPCI settlements that occurred March 31 but haven't been credited to the bank yet, post an accrual:
```
March 31 (year-end accrual):
  Dr  NPCI Settlement Receivable (Asset)  ₹5,00,000
    Cr  Merchant Payable (Liability)         ₹5,00,000

April 1 (actual receipt):
  Dr  Nodal Bank Account (Asset)          ₹5,00,000
    Cr  NPCI Settlement Receivable (Asset)  ₹5,00,000   ← clears the accrual
```

The `effective_date` column on ledger entries is critical here — it allows posting with `effective_date = 2024-03-31` even when `posted_at = 2024-04-01`.

## Section 6: Scenario / System Design Questions

**Q19. "Design a reconciliation system for a payment aggregator processing ₹500 crore/day across UPI, cards, and net banking."**
A: At ₹500 crore/day with an average transaction of ₹2,000, that's ~2.5 lakh transactions/day, ~5 lakh ledger entries/day across 3 payment methods.

**Architecture:**
```
Settlement Files (S3)
  ├── Razorpay daily CSV (UPI + card)
  ├── NPCI inward/outward files (UPI direct)
  └── Bank statement (HDFC nodal account)
           ↓
     File Watcher (S3 Event → SQS)
           ↓
     Ingestion Service (validates, normalizes, loads into reconciliation_records)
           ↓
     Matching Engine (runs 4-pass algorithm, classifies exceptions)
           ↓
     Exception Router (severity classification → PagerDuty / Jira / Slack / Report)
           ↓
     Resolution Tracker (auto-resolve where possible, human queue for the rest)
           ↓
     Compliance Reporter (RBI daily report, suspense aging, settlement SLA)
```

**Scale considerations:**
- Ingestion: parallel per gateway (3 workers, one per source). S3 Select for large files — only pull rows for the settlement date, not full file history.
- Matching: pass 1 (exact match by payment_id) as a single bulk UPDATE JOIN — handles 90%+ of matches in seconds. Passes 2–4 on the residual.
- Partitioning: `reconciliation_records` partitioned by `recon_run_id` (one partition per run = one partition per day). Drops entire partition when archiving instead of bulk DELETE.
- Exception SLA: < 2 hours from file receipt to all exceptions routed.

**File receipt SLAs:**

| Source | Expected by | Alert if late |
|---|---|---|
| Razorpay settlement CSV | 06:00 IST | 08:00 IST |
| NPCI inward file | 07:00 IST | 09:00 IST |
| HDFC bank statement | 08:00 IST | 10:00 IST |

```typescript
// File receipt monitoring — runs every 30 minutes
async function checkFileReceipts(settlementDate: Date): Promise<void> {
  const expectedFiles = [
    { source: 'RAZORPAY', expectedBy: setHours(settlementDate, 6), alertAfter: setHours(settlementDate, 8) },
    { source: 'NPCI_INWARD', expectedBy: setHours(settlementDate, 7), alertAfter: setHours(settlementDate, 9) },
    { source: 'HDFC_BANK', expectedBy: setHours(settlementDate, 8), alertAfter: setHours(settlementDate, 10) },
  ];

  for (const file of expectedFiles) {
    const received = await db('settlement_file_receipts')
      .where({ source: file.source, settlement_date: settlementDate })
      .first();

    if (!received && isAfter(new Date(), file.alertAfter)) {
      await pagerDuty.trigger({
        severity: 'high',
        summary: `${file.source} settlement file not received for ${settlementDate}`,
      });
    }
  }
}
```

**Q20. "Your daily reconciliation is showing a ₹2 lakh discrepancy between your ledger total and the gateway settlement total. How do you debug it?"**
A: Systematic decomposition — never guess at the root cause of a financial discrepancy.

**Step 1 — Confirm the number (5 minutes)**
```sql
-- Your ledger total for the settlement date
SELECT SUM(amount) FILTER (WHERE entry_type = 'CREDIT') AS ledger_credits,
       SUM(amount) FILTER (WHERE entry_type = 'DEBIT')  AS ledger_debits,
       COUNT(*) AS entry_count
FROM ledger_entries
WHERE effective_date = '2024-03-15'
  AND account_id IN (SELECT id FROM accounts WHERE code = '1002');  -- Settlement Receivable

-- Gateway file total
SELECT SUM(amount) AS gateway_gross, SUM(settlement_amount) AS gateway_net, COUNT(*) AS txn_count
FROM reconciliation_records
WHERE recon_run_id = '<run-id-for-march-15>'
  AND source = 'GATEWAY';
```

Are we comparing the right things? Ledger gross vs gateway gross, or ledger net vs gateway net (after fees)? Confirm apples-to-apples.

**Step 2 — Count mismatch or amount mismatch? (10 minutes)**
```sql
-- Count comparison
SELECT
  (SELECT COUNT(*) FROM reconciliation_records WHERE source = 'LEDGER'  AND recon_run_id = '<id>') AS ledger_count,
  (SELECT COUNT(*) FROM reconciliation_records WHERE source = 'GATEWAY' AND recon_run_id = '<id>') AS gateway_count;
```

If counts differ by N, the discrepancy is likely N missing transactions (₹2L / N = average transaction size — does it make sense?).

If counts are equal, the discrepancy is in amounts — look for systematic fee/FX/rounding errors.

**Step 3 — Isolate by payment method (10 minutes)**
```sql
SELECT r.payment_type,
       SUM(r.amount) AS gateway_total,
       SUM(l.amount) AS ledger_total,
       SUM(r.amount) - SUM(l.amount) AS delta
FROM reconciliation_records r
LEFT JOIN reconciliation_records l
  ON l.source_id = r.source_id AND l.source = 'LEDGER'
WHERE r.source = 'GATEWAY' AND r.recon_run_id = '<id>'
GROUP BY r.payment_type;
```

If the discrepancy is entirely in UPI, check for NPCI timing differences. If entirely in card, check for partial-capture or authorization-only transactions included in the file.

**Step 4 — Find the specific unmatched transactions**
```sql
-- Gateway transactions with no ledger match
SELECT source_id, amount, transaction_date, raw_data
FROM reconciliation_records
WHERE recon_run_id = '<id>'
  AND source = 'GATEWAY'
  AND match_status IN ('UNMATCHED', 'EXCEPTION')
ORDER BY amount DESC;
```

Look at the largest unmatched transactions first — a single ₹2L transaction missing is different from 2,000 × ₹100 missing.

**Step 5 — Root cause by exception type**
- All missing in ledger → webhook delivery failure. Check webhook logs for that date. Re-trigger.
- All amount mismatches, same delta → fee rate change. Did the gateway change their fee structure without notice?
- Random missing transactions across methods → DB write failure during a deploy or outage window. Cross-reference deployment log with the transaction timestamps.
- Batch of transactions missing for one merchant → their sub-merchant account was deactivated mid-day and transactions were held.

**Q21. "How would you build a self-healing reconciliation system that minimizes the need for human intervention?"**
A: Self-healing requires: classification of every exception into a known type, a resolution strategy for each type, confidence thresholds for auto-resolution, and a human escalation path for everything else.

**Resolution decision tree:**
```typescript
async function attemptAutoResolution(exception: ReconException): Promise<ResolutionResult> {
  switch (exception.type) {
    case 'MISSING_IN_LEDGER':
      // Confirm with gateway API; post missing entry if confirmed
      if (exception.age_days <= 2) {
        return await reconcileWebhookMiss(exception);
      }
      return { resolved: false, reason: 'Too old for auto-recovery — human review required' };

    case 'AMOUNT_MISMATCH':
      if (abs(exception.delta) <= 100n) {  // ≤ ₹1
        return await postRoundingAdjustment(exception);
      }
      return { resolved: false, reason: `Delta ₹${exception.delta / 100n} exceeds auto-resolve threshold` };

    case 'DATE_MISMATCH':
      if (exception.delta_days <= 2) {
        // Mark as timing difference; carry forward to next day's recon
        return await markAsTimingDifference(exception);
      }
      return { resolved: false, reason: 'Date gap too large for timing difference classification' };

    case 'DUPLICATE_IN_LEDGER':
      // Post reversal on the duplicate; flag for human confirmation
      const reversal = await postDuplicateReversal(exception);
      return { resolved: false, pendingConfirmation: true, reversalId: reversal.id };

    default:
      return { resolved: false, reason: 'No auto-resolution strategy for this exception type' };
  }
}
```

**Confidence guardrails — never auto-resolve:**
- Amount > ₹10,000 (even with a known type).
- Exception type `UNIDENTIFIED_BANK_DEBIT` or `UNIDENTIFIED_BANK_CREDIT` — always human review.
- More than 3 auto-resolutions of the same type in a single run — may indicate a systemic bug being silently masked. Pause and alert.

**Self-healing rate tracking:**
```typescript
metrics.gauge('recon.auto_resolution_rate',
  autoResolvedCount / totalExceptionCount * 100
);
// Target: > 80% auto-resolution for LOW/MEDIUM severity exceptions
// Any run with auto-resolution rate < 60% triggers a review
```

## Quick Reference Table

| Concept | Detail | Engineering action |
|---|---|---|
| **Three-way reconciliation** | Ledger ↔ Gateway file ↔ Bank statement | All three sources loaded per run; match in passes |
| **UTR** | Primary link key between gateway file and bank statement | Store on every payment; index for fast join |
| **Matching passes** | gateway_id → UTR → order_id → amount+date window | Each pass only touches UNMATCHED records; idempotent |
| **Timing window** | T+1/T+2 for UPI/NEFT; ±1 day for cut-off | Open items, not exceptions, within the window |
| **Suspense account** | Temporary liability for unidentified movements | Must clear within 5 business days; RBI mandate |
| **Immutable exceptions** | Never delete recon records; use resolution notes | Append-only; `resolved_at` + `resolved_by` |
| **Auto-resolution threshold** | ≤ ₹1 rounding; ≤ 2 days timing; age ≤ 2 days | Hard cap: never auto-resolve > ₹10,000 |
| **Settlement file validation** | Row count, arithmetic, control total | Fail loudly on empty file — never silently recon zero rows |
| **Chargeback lag** | Up to 120 days post-transaction | Never close a period for chargebacks; out-of-period adjustments |
| **NPCI two-leg** | Debit leg ≠ credit leg success | `SUCCESS` only after both legs confirmed |
| **RBI daily recon mandate** | Must complete by business start next day | Job SLA alert if not complete by 09:00 |
| **Settlement SLA** | T+1 for standard e-commerce per RBI | Alert per merchant if payable older than SLA |
| **Effective date** | Accounting date; may differ from posted_at | Use for period-close and cut-off queries |
| **Idempotent job** | Resume from status; passes operate on UNMATCHED only | Safe to restart after any failure |
| **Self-healing rate** | Target > 80% auto-resolution for LOW/MEDIUM | Alert if run auto-resolution rate < 60% |
