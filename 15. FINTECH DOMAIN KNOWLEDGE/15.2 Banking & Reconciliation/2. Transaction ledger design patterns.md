# Transaction Ledger Design Patterns — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a transaction ledger, and why does every fintech system need one?**
A: A transaction ledger is the authoritative, append-only record of every financial movement in a system. It is the financial equivalent of a write-ahead log — before any balance changes hands, the movement is recorded. Every other financial view (balances, statements, reports, reconciliation) is derived from the ledger.

Why fintech systems need one:
- **Auditability** — regulators (RBI, SEBI, PCI-DSS auditors) require a complete, tamper-evident history of every rupee that moved. A mutable `balance` column with no history is not auditable.
- **Balance correctness** — a user's current balance is not a stored number; it is the sum of all credit and debit entries for that account. Computing balance from the ledger guarantees consistency; storing a `balance` column separately creates a source-of-truth split that diverges under concurrent writes.
- **Dispute resolution** — when a customer disputes a charge, you must produce the exact sequence of events that produced their current balance. A ledger makes this a simple query.
- **Reconciliation** — your internal ledger must match the bank's statement and the payment gateway's settlement file. The ledger is what you compare.
- **Regulatory reporting** — GST filings, TDS deductions, RBI reporting, FEMA compliance all require transaction-level data, not aggregate balances.

**Q2. What is double-entry bookkeeping, and why is it the correct foundation for a financial ledger?**
A: Double-entry bookkeeping (DEB) is the accounting principle that every financial transaction affects at least two accounts, with total debits always equaling total credits. It was formalized by Luca Pacioli in 1494 and remains the foundation of every accounting system today.

The invariant:
```
∀ transaction T: Σ debits(T) = Σ credits(T)
```

In software, this means every `INSERT` to your ledger must create at least two entries — one debit and one credit — that net to zero. If they don't net to zero, you have a bug, and the invariant check will catch it.

Why DEB over single-entry:
- **Self-auditing** — if debits ≠ credits, money was created or destroyed. This is always a bug. Single-entry systems (a log of "customer paid ₹500") have no built-in consistency check.
- **Complete picture** — DEB captures where money came from *and* where it went. Single-entry captures only one side.
- **Standard compatibility** — every accounting software (Tally, QuickBooks, SAP) and every auditor expects double-entry. Building single-entry means a translation layer for every external integration.
- **Balance sheet consistency** — Assets = Liabilities + Equity is maintained automatically when every transaction is double-entry.

**Q3. What are the five account types in double-entry bookkeeping, and how do debits and credits affect each?**
A: The five account types and their normal balances (the side that increases the account):

| Account Type | Normal Balance | Debit effect | Credit effect | Examples |
|---|---|---|---|---|
| **Asset** | Debit | Increases | Decreases | Bank account, Accounts Receivable, Cash |
| **Liability** | Credit | Decreases | Increases | Accounts Payable, Merchant Payable, Loan |
| **Equity** | Credit | Decreases | Increases | Retained Earnings, Share Capital |
| **Revenue** | Credit | Decreases | Increases | Transaction Fee Income, FX Income |
| **Expense** | Debit | Increases | Decreases | Gateway Fee Expense, Fraud Loss |

The mnemonic **DEALER** (Dividends, Expenses, Assets — Debit normal; Liabilities, Equity, Revenue — Credit normal) is the fastest recall path.

Example — customer pays ₹1,000 via UPI to a merchant:
```
Dr  UPI Settlement Receivable (Asset)     ₹1,000   ← we will receive this from NPCI
  Cr  Merchant Payable (Liability)          ₹1,000   ← we owe this to the merchant

On settlement receipt from NPCI:
Dr  Bank Account (Asset)                  ₹1,000
  Cr  UPI Settlement Receivable (Asset)    ₹1,000

On merchant payout:
Dr  Merchant Payable (Liability)          ₹1,000
  Cr  Bank Account (Asset)                 ₹1,000
```

**Q4. What is the difference between a chart of accounts and a ledger?**
A: These are related but distinct:

- **Chart of Accounts (CoA)** — the master list of all accounts in the system, each with a unique code, name, type, and currency. It defines *what* can be tracked. Think of it as the schema.
- **Ledger** — the actual record of entries posted to each account. It contains the data. The general ledger is the sum of all accounts; a subsidiary ledger is the detail for one account (e.g., one entry per merchant in the Merchant Payable subsidiary ledger).

```sql
-- Chart of Accounts
CREATE TABLE accounts (
  id            UUID PRIMARY KEY,
  code          TEXT UNIQUE NOT NULL,   -- e.g., '1001', '2001', '4001'
  name          TEXT NOT NULL,          -- e.g., 'UPI Settlement Receivable'
  type          account_type NOT NULL,  -- ASSET, LIABILITY, EQUITY, REVENUE, EXPENSE
  currency      CHAR(3) NOT NULL DEFAULT 'INR',
  parent_id     UUID REFERENCES accounts(id),  -- for hierarchical CoA
  is_active     BOOLEAN NOT NULL DEFAULT TRUE,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- General Ledger
CREATE TABLE ledger_entries (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  transaction_id  UUID NOT NULL,        -- groups the debit/credit pair(s)
  account_id      UUID NOT NULL REFERENCES accounts(id),
  entry_type      entry_type NOT NULL,  -- DEBIT or CREDIT
  amount          BIGINT NOT NULL,      -- in minor units; always positive
  currency        CHAR(3) NOT NULL,
  description     TEXT,
  posted_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  effective_date  DATE NOT NULL,        -- accounting date (may differ from posted_at)
  created_by      TEXT NOT NULL         -- service name or user ID
);
```

**Q5. What is the difference between cash-basis and accrual-basis accounting, and which should a fintech ledger support?**
A: The difference is *when* revenue and expenses are recognized:

- **Cash basis** — revenue recognized when cash is received; expense recognized when cash is paid. Simple, but legally inadequate for most businesses above a certain revenue threshold.
- **Accrual basis** — revenue recognized when *earned* (invoice issued / service delivered), regardless of when cash arrives; expense recognized when *incurred*, regardless of when paid. Required by Ind AS (Indian Accounting Standards), GAAP, and IFRS for any company with turnover above the tax audit threshold.

Example: you issue a ₹1 lakh invoice on March 31; payment arrives April 10:
- Cash basis: revenue recognized April 10 (cash received).
- Accrual basis: revenue recognized March 31 (invoice issued); a separate "collection" entry on April 10 clears the receivable.

**Why fintech ledgers must support accrual:**
- RBI PA/PG guidelines and Ind AS require accrual-basis accounting for payment aggregators.
- Subscription SaaS must recognize revenue ratably over the subscription period (deferred revenue), not on cash receipt.
- FX gain/loss, interest income, and fee income all have accrual recognition rules.

The engineering implication: every ledger entry needs both a `posted_at` (when the system recorded it) and an `effective_date` (the accounting date, which may be different). A payment received on April 2 for a March 31 invoice has `effective_date = 2024-03-31`.

## Section 2: Ledger Schema Design Patterns

**Q6. What is the immutable ledger pattern, and how do you implement corrections without violating immutability?**
A: The immutable ledger pattern forbids `UPDATE` and `DELETE` on ledger entries. Once posted, an entry cannot be modified — not even by admins. This is the accounting equivalent of the append-only event store.

Why immutability is non-negotiable:
- An auditor must be able to reproduce any historical balance at any point in time. Mutable entries make historical queries unreliable.
- Regulators treat altered financial records as potential fraud.
- Immutability enables aggressive caching of historical balances (they will never change).

**How to correct errors without mutating entries — the reversal pattern:**

If entry E was posted incorrectly (wrong amount, wrong account), you never update E. Instead you post a reversal entry E' that exactly negates E, then post the correct entry E'':

```sql
-- Original (wrong) entry: credited Revenue ₹1,000 instead of ₹900
INSERT INTO ledger_entries (transaction_id, account_id, entry_type, amount, description)
VALUES ('txn-001', 'revenue-account', 'CREDIT', 100000, 'Fee income - original');  -- ₹1,000 paise

-- Reversal: debit Revenue ₹1,000 (exact negation)
INSERT INTO ledger_entries (transaction_id, account_id, entry_type, amount, description, reverses_entry_id)
VALUES ('txn-002', 'revenue-account', 'DEBIT', 100000, 'Reversal of txn-001', 'entry-id-of-txn-001');

-- Correction: credit Revenue ₹900
INSERT INTO ledger_entries (transaction_id, account_id, entry_type, amount, description)
VALUES ('txn-002', 'revenue-account', 'CREDIT', 90000, 'Fee income - corrected');  -- ₹900
```

Add a `reverses_entry_id` column to make the reversal chain queryable:
```sql
ALTER TABLE ledger_entries ADD COLUMN reverses_entry_id UUID REFERENCES ledger_entries(id);
```

Database-level enforcement of immutability:
```sql
-- Rule: no UPDATE or DELETE on ledger_entries, ever
CREATE RULE no_update_ledger AS ON UPDATE TO ledger_entries DO INSTEAD NOTHING;
CREATE RULE no_delete_ledger AS ON DELETE TO ledger_entries DO INSTEAD NOTHING;

-- Or revoke permissions at the role level
REVOKE UPDATE, DELETE ON ledger_entries FROM app_service_role;
```

**Q7. How do you enforce the double-entry constraint at the database level?**
A: Application-level enforcement is insufficient — a bug, a migration script, or a direct DB write can violate it. Database-level enforcement is mandatory.

**Method 1 — Check constraint on transaction sum (PostgreSQL deferred constraint)**
```sql
-- A transaction's debits must equal its credits
-- Enforced at COMMIT time via a deferred constraint trigger

CREATE OR REPLACE FUNCTION check_double_entry()
RETURNS TRIGGER AS $$
DECLARE
  debit_total  BIGINT;
  credit_total BIGINT;
BEGIN
  SELECT
    COALESCE(SUM(amount) FILTER (WHERE entry_type = 'DEBIT'), 0),
    COALESCE(SUM(amount) FILTER (WHERE entry_type = 'CREDIT'), 0)
  INTO debit_total, credit_total
  FROM ledger_entries
  WHERE transaction_id = NEW.transaction_id;

  IF debit_total <> credit_total THEN
    RAISE EXCEPTION 'Double-entry violation: transaction % debits=% credits=%',
      NEW.transaction_id, debit_total, credit_total;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Deferred: runs at COMMIT, not at each INSERT — allows inserting debit then credit
CREATE CONSTRAINT TRIGGER enforce_double_entry
  AFTER INSERT OR UPDATE ON ledger_entries
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION check_double_entry();
```

**Method 2 — Signed amount column (alternative schema)**
Instead of a `DEBIT`/`CREDIT` enum, store amounts as signed integers: positive = credit, negative = debit (or vice versa, per convention). The constraint becomes: `SUM(amount) = 0` per transaction.

```sql
ALTER TABLE ledger_entries ADD COLUMN signed_amount BIGINT NOT NULL;
-- Convention: positive = credit, negative = debit

-- Constraint: transaction must sum to zero
CREATE OR REPLACE FUNCTION check_zero_sum()
RETURNS TRIGGER AS $$
BEGIN
  IF (SELECT SUM(signed_amount) FROM ledger_entries WHERE transaction_id = NEW.transaction_id) <> 0 THEN
    RAISE EXCEPTION 'Zero-sum violation on transaction %', NEW.transaction_id;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

Method 2 simplifies balance queries (`SELECT SUM(signed_amount)` vs `SELECT SUM(debit) - SUM(credit)`) but is less readable for humans debugging ledger entries. Both approaches are valid; choose one and be consistent.

**Q8. How do you calculate account balances from the ledger efficiently, and what are the tradeoffs of materialized vs. computed balances?**
A: Balance = sum of all ledger entries for an account. Two approaches:

**Approach 1 — Compute on demand**
```sql
-- Current balance for account X
SELECT
  COALESCE(SUM(amount) FILTER (WHERE entry_type = 'CREDIT'), 0) -
  COALESCE(SUM(amount) FILTER (WHERE entry_type = 'DEBIT'), 0) AS balance
FROM ledger_entries
WHERE account_id = 'account-uuid'
  AND posted_at <= NOW();

-- Historical balance at a point in time
SELECT
  COALESCE(SUM(amount) FILTER (WHERE entry_type = 'CREDIT'), 0) -
  COALESCE(SUM(amount) FILTER (WHERE entry_type = 'DEBIT'), 0) AS balance
FROM ledger_entries
WHERE account_id = 'account-uuid'
  AND posted_at <= '2024-03-15 14:32:00';
```

Pros: always accurate; supports point-in-time queries natively; no synchronization issues.
Cons: O(n) scan over all entries; slow for accounts with millions of entries (active merchant accounts in production).

**Approach 2 — Materialized balance with periodic checkpoints**
```sql
CREATE TABLE account_balance_snapshots (
  account_id      UUID NOT NULL REFERENCES accounts(id),
  snapshot_at     TIMESTAMPTZ NOT NULL,
  balance         BIGINT NOT NULL,      -- balance as of snapshot_at
  entry_count     BIGINT NOT NULL,      -- number of entries included
  PRIMARY KEY (account_id, snapshot_at)
);
```

Balance query using latest checkpoint:
```sql
-- Step 1: find the most recent checkpoint
WITH latest_snapshot AS (
  SELECT balance, snapshot_at
  FROM account_balance_snapshots
  WHERE account_id = 'account-uuid'
  ORDER BY snapshot_at DESC
  LIMIT 1
)
-- Step 2: add entries since checkpoint
SELECT
  ls.balance +
  COALESCE(SUM(le.amount) FILTER (WHERE le.entry_type = 'CREDIT'), 0) -
  COALESCE(SUM(le.amount) FILTER (WHERE le.entry_type = 'DEBIT'), 0)
FROM latest_snapshot ls
LEFT JOIN ledger_entries le
  ON le.account_id = 'account-uuid'
  AND le.posted_at > ls.snapshot_at;
```

Pros: O(1) for the checkpoint read + O(entries since last checkpoint) for the delta — fast for high-volume accounts.
Cons: checkpoints must be created consistently (background job or trigger); if the checkpoint is stale, balance may reflect an older state.

**Recommendation:** compute on demand for accounts with < 10,000 entries; use checkpoints for high-volume accounts (active merchants, aggregated settlement accounts). Create checkpoints daily at midnight, or after every N entries (e.g., every 1,000 entries).

**Q9. What is a subledger, and when do you need one in a payment system?**
A: A subledger (subsidiary ledger) is a detailed breakdown of a general ledger account. The general ledger has one "Merchant Payable" account with a total balance; the subledger has one entry per merchant, with the amount owed to each.

The relationship:
```
General Ledger: Merchant Payable (code 2001) → total balance ₹45,23,000
  Subledger:
    Merchant A payable: ₹12,00,000
    Merchant B payable: ₹8,50,000
    Merchant C payable: ₹24,73,000
    Sum: ₹45,23,000  ← must always equal GL balance
```

Common subledger accounts in a payment system:

| GL Account | Subledger dimension | Use case |
|---|---|---|
| Merchant Payable | Per merchant_id | How much is owed to each merchant |
| UPI Settlement Receivable | Per UTR (UPI Transaction Reference) | Which NPCI settlements are pending |
| Customer Wallet Balance | Per customer_id | Each customer's prepaid wallet |
| Tax Payable | Per GST period | TDS/GST breakdown for filing |
| Fee Income | Per gateway / per product | Revenue attribution |

Subledger entries must always reconcile to the parent GL account. A reconciliation job that checks `SUM(subledger entries) = GL balance` daily is standard practice and catches bugs before they compound.

## Section 3: Advanced Patterns

**Q10. What is the wallet ledger pattern for prepaid wallets, and how do you prevent negative balance bugs?**
A: A prepaid wallet (like Paytm wallet, UPI Lite, or an internal credit balance) has two invariants:
1. Balance = sum of all credits minus sum of all debits (same as any account).
2. Balance must never go below zero (prepaid — you can't spend what you haven't loaded).

The wallet ledger schema:
```sql
CREATE TABLE wallet_ledger (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  wallet_id       UUID NOT NULL,
  transaction_id  UUID NOT NULL,
  entry_type      entry_type NOT NULL,    -- CREDIT (load) or DEBIT (spend)
  amount          BIGINT NOT NULL CHECK (amount > 0),
  description     TEXT,
  reference_id    TEXT,                   -- payment_id, refund_id, etc.
  posted_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Preventing negative balance — pessimistic locking pattern:**
```typescript
async function debitWallet(walletId: string, amount: bigint, description: string): Promise<void> {
  await db.transaction(async (trx) => {
    // Lock the wallet row — prevents concurrent debits from racing
    const wallet = await trx('wallets')
      .where({ id: walletId })
      .forUpdate()
      .first();

    const balance = await computeWalletBalance(trx, walletId);

    if (balance < amount) {
      throw new InsufficientBalanceError(
        `Wallet ${walletId}: balance ${balance} < debit ${amount}`
      );
    }

    await trx('wallet_ledger').insert({
      wallet_id: walletId,
      transaction_id: crypto.randomUUID(),
      entry_type: 'DEBIT',
      amount,
      description,
    });
  });
}
```

**Database-level guard (belt and suspenders):**
```sql
-- Partial index: prevents wallet balance from going negative
-- Enforced by a check trigger, not a column constraint (balance is computed)
CREATE OR REPLACE FUNCTION prevent_negative_wallet_balance()
RETURNS TRIGGER AS $$
DECLARE
  current_balance BIGINT;
BEGIN
  IF NEW.entry_type = 'DEBIT' THEN
    SELECT
      COALESCE(SUM(amount) FILTER (WHERE entry_type = 'CREDIT'), 0) -
      COALESCE(SUM(amount) FILTER (WHERE entry_type = 'DEBIT'), 0)
    INTO current_balance
    FROM wallet_ledger
    WHERE wallet_id = NEW.wallet_id;

    IF current_balance - NEW.amount < 0 THEN
      RAISE EXCEPTION 'Insufficient wallet balance: wallet=%, balance=%, debit=%',
        NEW.wallet_id, current_balance, NEW.amount;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**Q11. What is the escrow ledger pattern, and how is it used in marketplace payments?**
A: In a marketplace (like Meesho, Urban Company, or a ride-hailing platform), a customer pays the platform; the platform holds the funds in escrow until the service/delivery is complete; then releases to the merchant. The escrow pattern requires three distinct accounts per transaction:

```
Customer pays ₹1,000
  Dr  UPI Receivable (Asset)          ₹1,000
    Cr  Customer Escrow (Liability)     ₹1,000   ← funds held in escrow

Service confirmed; release to merchant
  Dr  Customer Escrow (Liability)     ₹1,000
    Cr  Platform Fee Income (Revenue)     ₹20    ← platform commission
    Cr  Merchant Payable (Liability)     ₹980    ← merchant's share

Merchant payout
  Dr  Merchant Payable (Liability)     ₹980
    Cr  Bank Account (Asset)             ₹980
```

The escrow account balance must always be ≥ 0 and must equal the sum of all funds held for pending orders. A daily reconciliation that checks `escrow_balance = SUM(pending_order_amounts)` is mandatory for RBI PA/PG compliance (RBI mandates that customer funds in escrow must be segregated from the platform's own operating funds).

```sql
-- Escrow account per transaction for fine-grained tracking
CREATE TABLE escrow_holds (
  id              UUID PRIMARY KEY,
  order_id        UUID NOT NULL UNIQUE,
  payment_id      UUID NOT NULL,
  amount          BIGINT NOT NULL,
  currency        CHAR(3) NOT NULL,
  status          TEXT NOT NULL DEFAULT 'HELD',  -- HELD, RELEASED, REFUNDED
  held_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  released_at     TIMESTAMPTZ,
  ledger_entry_id UUID REFERENCES ledger_entries(id)
);
```

**Q12. How do you implement a multi-currency ledger? What are the tradeoffs between per-currency entries and functional-currency normalization?**
A: Two approaches for multi-currency:

**Approach 1 — Store in transaction currency; normalize to functional currency at reporting time**
```sql
ALTER TABLE ledger_entries ADD COLUMN currency CHAR(3) NOT NULL;
ALTER TABLE ledger_entries ADD COLUMN fx_rate  NUMERIC(18,8);

-- Entry in USD
INSERT INTO ledger_entries (account_id, entry_type, amount, currency, fx_rate, ...)
VALUES ('revenue-account', 'CREDIT', 100000, 'USD', 83.45, ...);  -- $1,000 at 83.45
```

Pros: preserves exact transaction-currency amounts; supports currency-specific balance queries.
Cons: balance queries require FX conversion at query time; historical rate must be stored per entry (can't use today's rate to compute historical balance).

**Approach 2 — Store both transaction currency and functional currency equivalent**
```sql
ALTER TABLE ledger_entries ADD COLUMN amount_txn          BIGINT NOT NULL;
ALTER TABLE ledger_entries ADD COLUMN currency_txn        CHAR(3) NOT NULL;
ALTER TABLE ledger_entries ADD COLUMN amount_functional   BIGINT NOT NULL;    -- in INR paise
ALTER TABLE ledger_entries ADD COLUMN currency_functional CHAR(3) NOT NULL DEFAULT 'INR';
ALTER TABLE ledger_entries ADD COLUMN fx_rate             NUMERIC(18,8);
ALTER TABLE ledger_entries ADD COLUMN fx_rate_source      TEXT;
```

Pros: functional currency balance queries are simple (`SUM(amount_functional)`); no need to store or look up historical rates at report time.
Cons: functional amount is locked at posting time; cannot restate historical financials if the company changes its functional currency.

**Recommendation:** Approach 2 for operational ledgers (fast balance queries, regulatory reporting). Approach 1 (or both) for treasury/accounting ledgers where multi-currency restatement is required. The functional amount column must be populated at INSERT time — never at query time.

**Q13. What is deferred revenue, and how do you model it in a subscription billing ledger?**
A: Deferred revenue (also called unearned revenue) is a liability — you've received cash from a customer for a service not yet delivered. In a subscription business, a customer pays ₹12,000 annually upfront; you've only *earned* ₹1,000 per month as you deliver the service.

```
On annual payment receipt (January 1):
  Dr  Bank Account (Asset)               ₹12,000
    Cr  Deferred Revenue (Liability)       ₹12,000   ← not yet earned

Monthly revenue recognition job (February 1):
  Dr  Deferred Revenue (Liability)        ₹1,000
    Cr  Subscription Revenue (Revenue)     ₹1,000    ← earned this month
```

Schema:
```sql
CREATE TABLE deferred_revenue_schedule (
  id                UUID PRIMARY KEY,
  invoice_id        UUID NOT NULL,
  customer_id       UUID NOT NULL,
  total_amount      BIGINT NOT NULL,       -- ₹12,000 in paise
  recognized_amount BIGINT NOT NULL DEFAULT 0,
  recognition_start DATE NOT NULL,         -- 2024-01-01
  recognition_end   DATE NOT NULL,         -- 2024-12-31
  recognition_frequency TEXT NOT NULL,     -- 'MONTHLY', 'DAILY'
  currency          CHAR(3) NOT NULL
);

-- Monthly recognition job
async function recognizeRevenue(month: Date) {
  const schedules = await db('deferred_revenue_schedule')
    .where('recognition_start', '<=', month)
    .where('recognition_end', '>=', month)
    .where(db.raw('recognized_amount < total_amount'));

  for (const schedule of schedules) {
    const monthlyAmount = schedule.total_amount / monthsBetween(
      schedule.recognition_start, schedule.recognition_end
    );
    await postLedgerTransaction([
      { account: 'DEFERRED_REVENUE', type: 'DEBIT',  amount: monthlyAmount },
      { account: 'SUBSCRIPTION_REVENUE', type: 'CREDIT', amount: monthlyAmount },
    ]);
    await db('deferred_revenue_schedule')
      .where({ id: schedule.id })
      .increment('recognized_amount', monthlyAmount);
  }
}
```

RBI and Ind AS both require revenue recognition per the schedule, not on cash receipt for prepaid subscriptions — deferred revenue modeling is an auditor-facing requirement.

## Section 4: Indian Fintech & Regulatory Context

**Q14. What is the RBI nodal account requirement, and how does it affect ledger design for payment aggregators?**
A: RBI's Payment Aggregator guidelines (2020) require that all customer funds collected by a PA must be held in a dedicated nodal/escrow account with a scheduled commercial bank. The PA's own operating funds must be completely segregated.

Ledger design implications:
- **Two separate legal entities of accounts**: customer money pool (nodal) and PA's own P&L accounts. Transactions must be posted to the correct account from day one.
- **Nodal account balance must be ≥ total outstanding merchant payables at all times**. If the nodal account balance drops below total merchant payables, the PA is in violation.
- **Daily settlement mandate**: RBI requires that merchant payables from T-day transactions be released to merchants by T+1 (or T+2 for certain categories). Your ledger must track settlement lag per transaction.

```sql
-- Segregated account structure
INSERT INTO accounts (code, name, type) VALUES
  ('1001', 'Nodal Bank Account - HDFC', 'ASSET'),          -- customer funds
  ('1002', 'Operating Bank Account - ICICI', 'ASSET'),      -- PA's own funds
  ('2001', 'Merchant Payable', 'LIABILITY'),                -- amounts owed to merchants
  ('2002', 'Refund Payable', 'LIABILITY'),                  -- pending refunds
  ('4001', 'Transaction Fee Income', 'REVENUE'),            -- PA's own revenue
  ('5001', 'Gateway Fee Expense', 'EXPENSE');               -- PA's cost

-- Invariant: account_balance('1001') >= SUM(merchant_payable) + SUM(refund_payable)
-- Checked daily by compliance job
```

```typescript
async function checkNodalAccountCompliance(): Promise<ComplianceResult> {
  const nodalBalance = await computeAccountBalance('1001');
  const merchantPayable = await computeAccountBalance('2001');
  const refundPayable = await computeAccountBalance('2002');
  const requiredReserve = merchantPayable + refundPayable;

  if (nodalBalance < requiredReserve) {
    await alertComplianceTeam({
      severity: 'CRITICAL',
      message: `Nodal account deficit: balance=${nodalBalance}, required=${requiredReserve}`,
    });
  }
  return { nodalBalance, requiredReserve, compliant: nodalBalance >= requiredReserve };
}
```

**Q15. How do you model TDS (Tax Deducted at Source) in a payment system ledger?**
A: TDS (under Income Tax Act, 1961) is deducted at source when a platform makes certain payments to merchants — typically 1% under Section 194O for e-commerce operators paying merchants above ₹5 lakh in a financial year.

Ledger entries for a ₹1,000 payout with 1% TDS (₹10):
```
Merchant payout with TDS:
  Dr  Merchant Payable (Liability)      ₹1,000
    Cr  Bank Account (Asset)               ₹990   ← actual payout
    Cr  TDS Payable (Liability)             ₹10   ← held for remittance to IT dept

TDS remittance to Income Tax (quarterly):
  Dr  TDS Payable (Liability)            ₹10
    Cr  Bank Account (Asset)               ₹10
```

Schema additions:
```sql
CREATE TABLE tds_deductions (
  id              UUID PRIMARY KEY,
  payment_id      UUID NOT NULL REFERENCES payments(id),
  merchant_id     UUID NOT NULL,
  pan             CHAR(10) NOT NULL,    -- merchant's PAN (required for Form 26AS)
  tds_section     TEXT NOT NULL,        -- '194O', '194H', '194J'
  gross_amount    BIGINT NOT NULL,
  tds_rate        NUMERIC(5,4) NOT NULL, -- 0.0100 for 1%
  tds_amount      BIGINT NOT NULL,
  financial_year  CHAR(7) NOT NULL,     -- '2024-25'
  quarter         CHAR(2) NOT NULL,     -- 'Q1', 'Q2', 'Q3', 'Q4'
  deducted_at     TIMESTAMPTZ NOT NULL,
  deposited_at    TIMESTAMPTZ,          -- when remitted to IT dept
  challan_number  TEXT                  -- IT department reference
);
```

TDS data feeds into Form 26AS (merchant's annual tax credit statement) and Form 27EQ (TDS return filed by the platform). Your system must generate TDS certificates (Form 16A) for each merchant per quarter — a regulatory obligation, not optional.

**Q16. How does GST affect ledger entries for a payment aggregator's fee income?**
A: When a PA charges a merchant a transaction fee, that fee is a taxable service. GST at 18% applies to the fee. The entries:

```
Transaction fee charged to merchant: ₹100 + 18% GST = ₹118 total
  Dr  Merchant Payable (Liability)     ₹118   ← merchant owes more (or we deduct from payout)
    Cr  Transaction Fee Income (Revenue)  ₹100
    Cr  GST Payable - Output (Liability)  ₹18

GST remittance (monthly, by 20th of following month):
  Dr  GST Payable - Output (Liability)  ₹18
    Cr  Bank Account (Asset)               ₹18

Input tax credit on gateway fees (we pay ₹50 + 9% GST to Razorpay):
  Dr  Gateway Fee Expense (Expense)      ₹50
  Dr  GST Receivable - Input (Asset)      ₹4.50
    Cr  Accounts Payable - Razorpay        ₹54.50
```

The GST payable in the ledger is net: `Output GST (collected) - Input GST (paid) = Net GST payable to government`. This is computed monthly for GSTR-3B filing.

Schema:
```sql
ALTER TABLE ledger_entries ADD COLUMN gst_component TEXT;    -- 'OUTPUT', 'INPUT', NULL
ALTER TABLE ledger_entries ADD COLUMN hsn_sac_code  TEXT;    -- '9971' for financial services
ALTER TABLE ledger_entries ADD COLUMN gstin         TEXT;    -- merchant's GSTIN for B2B
```

## Section 5: Performance & Scalability

**Q17. How do you partition a high-volume ledger table, and what are the tradeoffs?**
A: A payment platform processing 1M transactions/day generates ~2M ledger entries/day. At this volume, a single `ledger_entries` table becomes a performance bottleneck within months.

**Partitioning strategies:**

**Range partitioning by time (most common)**
```sql
CREATE TABLE ledger_entries (
  id              UUID NOT NULL,
  transaction_id  UUID NOT NULL,
  account_id      UUID NOT NULL,
  entry_type      entry_type NOT NULL,
  amount          BIGINT NOT NULL,
  posted_at       TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (posted_at);

-- Monthly partitions
CREATE TABLE ledger_entries_2024_01
  PARTITION OF ledger_entries
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE ledger_entries_2024_02
  PARTITION OF ledger_entries
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
```

Pros: historical partitions can be archived (moved to cheaper storage), indexes are smaller per partition, query planner prunes old partitions for recent-data queries.
Cons: cross-partition queries (like all-time balance computation) must scan all partitions; partition pruning only works when the query includes a date filter.

**Hash partitioning by account_id**
```sql
CREATE TABLE ledger_entries (
  -- ... columns
) PARTITION BY HASH (account_id);

CREATE TABLE ledger_entries_p0 PARTITION OF ledger_entries FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE ledger_entries_p1 PARTITION OF ledger_entries FOR VALUES WITH (MODULUS 4, REMAINDER 1);
-- ... p2, p3
```

Pros: distributes writes evenly; balance queries for one account_id always hit one partition.
Cons: no temporal archiving benefit; queries without account_id filter scan all partitions.

**Recommendation:** range-partition by month + index on `(account_id, posted_at)` within each partition. This optimizes the two most common query patterns: recent entries for an account (balance computation), and audits for a date range.

**Q18. How do you design the ledger for high-concurrency balance reads without serving stale data?**
A: The classic problem: 10,000 concurrent balance reads during a sale event, all hitting the same merchant account's ledger entries. Options:

**Option 1 — Read replicas with bounded staleness**
Route balance reads to a PostgreSQL read replica (replication lag typically < 100ms). Acceptable for display-only balance checks (showing wallet balance in UI). Not acceptable for "check before debit" (risk of stale read permitting an overdraft).

**Option 2 — Redis balance cache with write-through**
Every ledger `INSERT` also updates a Redis balance key atomically:
```typescript
async function postLedgerEntry(entry: LedgerEntry): Promise<void> {
  await db.transaction(async (trx) => {
    await trx('ledger_entries').insert(entry);

    const delta = entry.entry_type === 'CREDIT' ? entry.amount : -entry.amount;
    // Atomic Redis increment — fails safely if Redis is down (no update)
    await redis.incrby(`balance:${entry.account_id}`, delta.toString());
  });
}

async function getBalance(accountId: string): Promise<bigint> {
  const cached = await redis.get(`balance:${accountId}`);
  if (cached !== null) return BigInt(cached);

  // Cache miss: compute from ledger and populate
  const balance = await computeBalanceFromLedger(accountId);
  await redis.set(`balance:${accountId}`, balance.toString());
  return balance;
}
```

Tradeoff: Redis is the fast path; the ledger is the source of truth. If Redis loses the balance key (eviction, flush), the cache miss path recomputes from the ledger. Never trust Redis as the sole source of balance — it's a cache, not a ledger.

**Option 3 — Materialized balance table with optimistic concurrency**
A `wallet_balances` table with a `version` column; balance queries read this table; ledger entries increment it atomistically. Requires careful conflict resolution on concurrent writes.

**Q19. How do you implement ledger entry idempotency to prevent double-posting?**
A: Double-posting (inserting the same ledger entry twice) is a critical bug — it creates phantom money. Causes: network retry, message queue redelivery, duplicate webhook, bug in the calling service.

**Pattern — idempotency key on ledger transactions:**
```sql
CREATE TABLE ledger_transactions (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  idempotency_key   TEXT UNIQUE NOT NULL,   -- caller-provided, unique per logical operation
  description       TEXT,
  posted_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ledger_entries reference the transaction
ALTER TABLE ledger_entries ADD COLUMN ledger_transaction_id UUID
  REFERENCES ledger_transactions(id) NOT NULL;
```

```typescript
async function postLedgerTransaction(
  idempotencyKey: string,
  entries: LedgerEntryInput[],
): Promise<LedgerTransaction> {
  return db.transaction(async (trx) => {
    // Check if already posted — idempotent no-op if so
    const existing = await trx('ledger_transactions')
      .where({ idempotency_key: idempotencyKey })
      .first();

    if (existing) {
      logger.info({ idempotencyKey }, 'Ledger transaction already posted — skipping');
      return existing;
    }

    // Insert transaction header
    const [txn] = await trx('ledger_transactions').insert({
      idempotency_key: idempotencyKey,
      description: entries[0].description,
    }).returning('*');

    // Insert entries
    await trx('ledger_entries').insert(
      entries.map(e => ({ ...e, ledger_transaction_id: txn.id }))
    );

    return txn;
  });
}
```

The `UNIQUE` constraint on `idempotency_key` is the database-level guard. If two concurrent requests race with the same key, PostgreSQL's unique constraint ensures only one succeeds; the other gets a constraint violation, which the application handles by returning the existing transaction.

## Section 6: Scenario / System Design Questions

**Q20. "Design the ledger for a UPI payment aggregator handling 5M transactions per day."**
A: Requirements: collect from customers via UPI, hold in nodal account, settle to merchants T+1, charge fees, pay TDS, support reconciliation.

**Account structure (Chart of Accounts):**
```
Assets (1xxx)
  1001 - Nodal Bank Account (HDFC)
  1002 - UPI Settlement Receivable      ← NPCI owes us
  1003 - Merchant Fee Receivable

Liabilities (2xxx)
  2001 - Merchant Payable
  2002 - Customer Refund Payable
  2003 - TDS Payable (194O)
  2004 - GST Payable (Output)

Revenue (4xxx)
  4001 - Transaction Fee Income
  4002 - FX Income (for cross-border)

Expenses (5xxx)
  5001 - Bank Charges
  5002 - NPCI Fee
```

**Transaction flow through ledger:**
```
Phase 1 — Customer pays ₹1,000 via UPI
  Dr  UPI Settlement Receivable (1002)  ₹1,000
    Cr  Merchant Payable (2001)           ₹980   ← net of 2% fee
    Cr  Transaction Fee Income (4001)       ₹20

Phase 2 — NPCI settles (T+1)
  Dr  Nodal Bank Account (1001)         ₹1,000
    Cr  UPI Settlement Receivable (1002) ₹1,000

Phase 3 — Merchant payout (T+1) with TDS
  Dr  Merchant Payable (2001)             ₹980
    Cr  Nodal Bank Account (1001)          ₹970.20  ← actual transfer
    Cr  TDS Payable 194O (2003)              ₹9.80  ← 1% TDS

Phase 4 — GST on fee (monthly)
  Dr  Transaction Fee Income (4001)        ₹20
    Cr  GST Payable Output (2004)            ₹3.60  ← 18% of ₹20
    Cr  Net Fee Income (retained)           ₹16.40
```

**Scale considerations at 5M transactions/day:**
- 10M ledger entries/day → partition by month; each monthly partition ~300M rows.
- Index `(account_id, posted_at DESC)` on each partition.
- Redis balance cache for merchant payable per merchant_id (hot path for merchant dashboard).
- Separate write DB (primary) and read DB (replica) for the ledger.
- Background job for checkpoint snapshots: every account with > 10,000 entries since last checkpoint gets a new snapshot at midnight.

**Q21. "A merchant reports their balance is showing ₹50,000 but they expected ₹75,000. Walk through your debugging approach."**
A: Systematic from ledger to gateway to bank:

**Step 1 — Reproduce the balance**
```sql
-- Compute balance from raw ledger entries — do NOT trust any cached balance
SELECT
  COALESCE(SUM(amount) FILTER (WHERE entry_type = 'CREDIT'), 0) -
  COALESCE(SUM(amount) FILTER (WHERE entry_type = 'DEBIT'), 0) AS computed_balance
FROM ledger_entries
WHERE account_id = (SELECT id FROM accounts WHERE merchant_id = '<merchant>' AND type = 'LIABILITY');
```

Does the ledger confirm ₹50,000? If yes, proceed — the ledger is the source of truth.

**Step 2 — Show the merchant their statement**
```sql
SELECT entry_type, amount, description, posted_at, reference_id
FROM ledger_entries
WHERE account_id = '<merchant-account>'
ORDER BY posted_at DESC
LIMIT 50;
```

Walk through with the merchant: which specific entries are missing or unexpected?

**Step 3 — Branch by what's missing**

*Missing credit (payment they expected to see)*: find the payment in `payments` table. Is it `SUCCESS`? If `SUCCESS` but no ledger entry, the ledger posting job failed — check the job logs. Post the missing entry manually with the original `payment_id` as the idempotency key.

*Unexpected debit (deduction they didn't expect)*: look for TDS deductions, fee charges, or refund debits they weren't aware of. Each should have a `reference_id` tracing to the source record.

*Fee calculation wrong*: check the fee rate applied. Was the merchant on a 1.5% rate but charged 2%? Look at `fee_config` effective at the time of the transaction — rates may have changed and the wrong config was applied.

*TDS deducted when PAN not provided*: without PAN, TDS rate doubles (20% instead of 1%). Check `tds_deductions` for this merchant — if PAN was missing, the higher rate applies. Merchant must provide PAN for rectification.

**Step 4 — Reconcile against gateway**
Pull the gateway settlement file for the relevant date range and compare `SUM(gateway_settled_amount)` for this merchant vs your ledger credits. Discrepancy here indicates a gateway settlement not posted to the ledger.

**Step 5 — Prevent recurrence**
- Add per-merchant daily balance reconciliation: `ledger_balance = gateway_settled_total - fees - TDS - payouts`.
- Alert if discrepancy > ₹1,000 or 0.5% of merchant's daily volume.

**Q22. "How would you migrate a legacy payment system that stores balances as a mutable column to a proper ledger?"**
A: This is a zero-downtime migration of a critical financial system. Phases:

**Phase 1 — Audit (2 weeks)**
- Map all places in the codebase that read or write the `balance` column.
- Identify every business event that should produce a ledger entry (payment, refund, fee, payout, adjustment).
- Design the chart of accounts and ledger schema.

**Phase 2 — Dual-write (4 weeks)**
- Deploy new `ledger_entries` table alongside the old `balance` column.
- Every code path that updates `balance` also inserts a ledger entry. Write to both.
- The `balance` column remains the read path (no change to reads yet).
- Run a daily job that computes `SUM(ledger entries)` per account and compares to `balance`. Alert on any discrepancy.

```typescript
// Dual-write shim
async function updateBalance(accountId: string, delta: bigint, description: string) {
  await db.transaction(async (trx) => {
    // Old path (still authoritative)
    await trx('accounts').where({ id: accountId }).increment('balance', Number(delta));

    // New path (shadow, for validation)
    await trx('ledger_entries').insert({
      account_id: accountId,
      entry_type: delta > 0 ? 'CREDIT' : 'DEBIT',
      amount: delta > 0 ? delta : -delta,
      description,
    });
  });
}
```

**Phase 3 — Backfill (1 week)**
- Generate ledger entries for all historical transactions. Work backward from the current balance.
- Validate: `SUM(historical ledger entries) = current balance` for every account.

**Phase 4 — Read cutover (1 week)**
- Switch all balance reads from `balance` column to ledger computation (or the Redis cache backed by the ledger).
- Monitor for discrepancies; keep `balance` column as a cross-check.

**Phase 5 — Deprecate `balance` column (2 weeks later)**
- Stop writing to `balance`. Remove the column. Ledger is now the sole source of truth.

Total timeline: ~3 months. The dual-write phase is the risk mitigation — it proves the ledger is correct before any read cutover.

| Concept | Detail | Engineering action |
|---|---|---|
| **Double-entry invariant** | Σ debits = Σ credits per transaction | Deferred constraint trigger at COMMIT |
| **Immutability** | No UPDATE/DELETE on ledger entries | REVOKE permissions; use reversal pattern for corrections |
| **Balance computation** | SUM(credits) - SUM(debits) per account | Index on `(account_id, posted_at)`; checkpoint for high-volume |
| **Idempotency key** | `UNIQUE` on `ledger_transactions.idempotency_key` | Prevents double-posting on retry/redelivery |
| **Effective date vs posted_at** | `effective_date` = accounting date; `posted_at` = system time | Both required; use `effective_date` for period-close queries |
| **Subledger reconciliation** | `SUM(subledger) = GL balance` | Run daily; alert on discrepancy |
| **Escrow segregation** | Nodal account balance ≥ merchant payable | RBI PA/PG mandate; check daily |
| **TDS 194O** | 1% on e-commerce merchant payouts > ₹5L/year | Deduct at payout; generate Form 16A quarterly |
