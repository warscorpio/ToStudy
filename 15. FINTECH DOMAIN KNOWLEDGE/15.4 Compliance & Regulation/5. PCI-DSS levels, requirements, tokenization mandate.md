# PCI-DSS: Levels, Requirements, Tokenization Mandate — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is PCI-DSS, who created it, and why does it exist?**
A: PCI-DSS (Payment Card Industry Data Security Standard) is a set of security requirements for any organization that stores, processes, or transmits cardholder data (CHD). It was created in 2004 by the **PCI Security Standards Council (PCI SSC)** — a body founded jointly by Visa, Mastercard, American Express, Discover, and JCB — to replace the fragmented, card-network-specific security programs that existed before (Visa's CISP, Mastercard's SDP, etc.).

**Why it exists:** Before PCI-DSS, merchants and processors handled card data inconsistently. Breaches at large processors (Heartland Payment Systems, 2008 — 130 million cards) and retailers (TJX Companies, 2007 — 94 million cards) demonstrated that inadequate security at any point in the card data chain exposed all participants. PCI-DSS creates a minimum security floor for the entire ecosystem.

**Who enforces it:** PCI-DSS is not a law — it is a contractual requirement imposed by card networks on acquirers, who impose it downstream on merchants and service providers through their merchant agreements. Non-compliance consequences:
- Fines from card networks to the acquirer (typically $5,000–$100,000/month for non-compliant merchants).
- Acquirer passes fines to the merchant.
- Increased transaction fees (risk-based pricing).
- Termination of merchant account (inability to accept card payments).
- In breach scenarios: liability for fraud losses and card replacement costs shifts entirely to the non-compliant merchant.

**Current version:** PCI-DSS v4.0 (released March 2022; v3.2.1 retired March 2024). v4.0 introduces significant changes: customized implementation approach, stronger multi-factor authentication requirements, and targeted risk analysis for some controls.

**Q2. What is the cardholder data environment (CDE), and what data elements does PCI-DSS protect?**
A: The CDE (Cardholder Data Environment) is the collection of people, processes, and technology that stores, processes, or transmits CHD — plus any system component that is connected to or could impact the security of CHD systems.

PCI-DSS defines two categories of protected data:

**Cardholder Data (CHD) — may be stored (with protection):**

| Data Element | Storage Permitted? | Protection Required |
|---|---|---|
| Primary Account Number (PAN) | Yes | Must be unreadable — encryption, truncation, tokenization, or hashing |
| Cardholder Name | Yes | No specific encryption required (low sensitivity alone) |
| Expiration Date | Yes | No specific encryption required (low sensitivity alone) |
| Service Code | Yes | No specific encryption required |

**Sensitive Authentication Data (SAD) — must NEVER be stored post-authorization:**

| Data Element | Storage Permitted? | Notes |
|---|---|---|
| Full magnetic stripe data | Never | Track 1 + Track 2 data — enables card cloning |
| CAV2 / CVC2 / CVV2 / CID (3-4 digit code) | Never | The number on the back of the card |
| PIN / PIN block | Never | Even if encrypted — prohibited |

The **PAN is the anchor** of PCI-DSS scope. Any system that touches the unmasked PAN is in scope. Systems that only see the last 4 digits (e.g., `XXXX XXXX XXXX 1234`) are generally out of scope. This is the engineering motivation for tokenization — replace PAN with a token everywhere possible, minimizing the number of systems in scope.

**SAD prohibition is absolute:** even if a business process temporarily needs the CVV (it does not — authorization is the only time CVV is used), storing it after authorization response is a PCI-DSS violation with no exception. Engineers must ensure that CVV fields in request logs, debug outputs, and database backups are never captured.

**Q3. What are the four PCI-DSS merchant levels, and what validation requirements correspond to each?**
A: Merchant levels are determined by annual transaction volume processed across all channels (card-present + card-not-present) for a given card brand. Visa and Mastercard define levels identically; Amex has a slightly different structure.

**Visa/Mastercard Merchant Levels:**

| Level | Transaction Volume (per year) | Validation Requirement | Assessment Type |
|---|---|---|---|
| **Level 1** | > 6 million Visa OR Mastercard transactions | Annual Report on Compliance (ROC) by a QSA; quarterly network scan by ASV | External QSA audit — most rigorous |
| **Level 2** | 1–6 million transactions | Annual SAQ (Self-Assessment Questionnaire) + quarterly ASV scan | Self-assessed with SAQ |
| **Level 3** | 20,000–1 million e-commerce transactions | Annual SAQ + quarterly ASV scan | Self-assessed with SAQ |
| **Level 4** | < 20,000 e-commerce OR up to 1 million other | Annual SAQ recommended; quarterly ASV scan recommended | Merchant-discretion + acquirer requirements |

**Key terms:**
- **QSA (Qualified Security Assessor)** — a company certified by PCI SSC to audit organizations and produce ROCs. QSA auditors are individuals certified within a QSA company.
- **ISA (Internal Security Assessor)** — an employee certified by PCI SSC who can perform internal assessments (not external Level 1 ROC).
- **ASV (Approved Scanning Vendor)** — company certified to perform automated external vulnerability scans of internet-facing systems.
- **ROC (Report on Compliance)** — the formal audit report produced by a QSA after a Level 1 assessment.
- **SAQ (Self-Assessment Questionnaire)** — a self-assessment tool; multiple variants (SAQ A, B, C, D) depending on how the merchant processes cards.

**Service Provider levels (separate from merchant levels):**

| Level | Criteria | Validation |
|---|---|---|
| **SP Level 1** | Stores/processes/transmits > 300,000 transactions/year OR any third-party processor | Annual ROC by QSA + quarterly ASV |
| **SP Level 2** | < 300,000 transactions/year | Annual SAQ + quarterly ASV |

Most fintechs building payment infrastructure are **Service Providers** — they handle card data on behalf of merchants and are therefore subject to SP Level 1 or SP Level 2 requirements regardless of whether they are themselves "merchants."

**Q4. What are the 12 PCI-DSS requirements, and how are they organized?**
A: PCI-DSS v4.0 organizes 12 requirements into six control objectives:

**Build and Maintain a Secure Network and Systems:**
1. **Install and maintain network security controls** — firewalls between CDE and untrusted networks; deny-all inbound rule with explicit allow exceptions; documented network diagrams showing all CHD flows.
2. **Apply secure configurations to all system components** — no vendor defaults for passwords and security parameters; disable unnecessary services/ports; maintain a system configuration standard.

**Protect Account Data:**
3. **Protect stored account data** — PAN must be unreadable in storage; SAD must never be stored post-auth; data retention policy with secure deletion; encryption key management.
4. **Protect cardholder data with strong cryptography during transmission** — TLS 1.2+ for all CHD transmission; no SSL or early TLS; strong cipher suites only.

**Maintain a Vulnerability Management Program:**
5. **Protect all systems and networks from malicious software** — anti-malware on all in-scope systems; regular updates; malware scan logs.
6. **Develop and maintain secure systems and software** — OWASP-aligned secure SDLC; vulnerability management; web application firewall (WAF) for internet-facing applications handling CHD; penetration testing.

**Implement Strong Access Control Measures:**
7. **Restrict access to system components and cardholder data by business need to know** — role-based access control; principle of least privilege; documented access roles.
8. **Identify users and authenticate access to system components** — unique user IDs; MFA for all access to CDE (v4.0 strengthened this to all non-console administrative access); password complexity; session management.
9. **Restrict physical access to cardholder data** — data center physical controls; visitor logs; media disposal; device tamper protection (for POS terminals).

**Regularly Monitor and Test Networks:**
10. **Log and monitor all access to system components and cardholder data** — audit logs for all access to CHD; time synchronization (NTP); log retention 12 months (3 months immediately accessible); SIEM.
11. **Test security of systems and networks regularly** — quarterly ASV scans; annual penetration test; intrusion detection/prevention (IDS/IPS); file integrity monitoring (FIM) on CDE systems.

**Maintain an Information Security Policy:**
12. **Support information security with organizational policies and programs** — security policy; risk assessment; security awareness training; vendor management (TPSP due diligence); incident response plan.

**Q5. What are the different SAQ types, and which one applies to a typical fintech payment integration?**
A: The SAQ variant determines which subset of PCI-DSS requirements apply. The correct SAQ depends on exactly how card data flows through the merchant's environment:

| SAQ | Who it applies to | Card Data Flow | Applicable Requirements |
|---|---|---|---|
| **SAQ A** | Card-not-present merchants who have fully outsourced card data handling to a PCI-compliant third party | PAN never touches merchant's systems or servers | ~22 requirements — smallest scope |
| **SAQ A-EP** | E-commerce merchants with a payment page hosted on their own domain (even if payment is processed by a third party) | Merchant's web server serves the page; JavaScript from PG loads in browser | ~191 requirements |
| **SAQ B** | Merchants using standalone dial-up terminals (imprinters); no electronic CHD storage | Card data enters terminal; not stored electronically | ~41 requirements |
| **SAQ B-IP** | Merchants using standalone IP-connected terminals (certified PTS devices); no electronic CHD storage | Card enters PTS-certified terminal; not stored on merchant systems | ~83 requirements |
| **SAQ C** | Merchants with a payment application connected to the internet; no electronic CHD storage | Card data in payment app on internet-connected system | ~160 requirements |
| **SAQ C-VT** | Merchants using a web-based virtual terminal from a PCI-compliant provider | Agent manually keys card into PCI-compliant hosted virtual terminal | ~79 requirements |
| **SAQ D** | All other merchants and all service providers | Any other card handling scenario | All 12 requirements — largest scope |

**For a typical fintech using a hosted payment page (Razorpay, Stripe Checkout, Cashfree):**
- If the payment page is **fully hosted by the PG** (redirect or iFrame from PG's domain): **SAQ A** — minimal scope; PAN never reaches the fintech's servers.
- If the fintech **hosts its own payment form** and uses JavaScript SDK that posts directly to the PG: **SAQ A-EP** — the fintech's web server is in scope even though it never sees the PAN.
- If the fintech collects card data in its own server-side code (builds its own payment page, posts to its own API): **SAQ D (Service Provider)** — full scope; this is the highest-risk and highest-cost option.

The engineering implication is clear: **use PG-hosted payment pages wherever possible to qualify for SAQ A**. Every line of code that touches card data is potential liability.

## Section 2: Technical Requirements In Depth

**Q6. What does Requirement 3 (Protect Stored Account Data) demand technically, and how do you implement it?**
A: Requirement 3 is the most technically demanding for engineering teams. The core rule: the PAN, if stored at all, must be rendered unreadable using one of four approved methods:

- **One-way hashing** (SHA-256 or stronger) — hash of the PAN; cannot be reversed to recover PAN. Used for searching (can hash the PAN to look it up) but not for display or re-transmission.
- **Truncation** — store only a portion of the PAN (most commonly first 6 + last 4 digits: `424242XXXXXX4242`). The middle digits are discarded — cannot be recovered.
- **Tokenization** — replace PAN with a non-sensitive surrogate (token) that has no mathematical relationship to the PAN. The PAN-to-token mapping is maintained in a secure token vault.
- **Strong cryptography** — encrypt the PAN with AES-256 or equivalent. Key management is then the critical control: encryption is only as strong as its key management.

**Key management requirements (Requirement 3.6–3.7):**

```typescript
// kyc/encryption/card-data-encryption.service.ts
// Illustrates the key management architecture — not a complete implementation

@Injectable()
export class CardDataEncryptionService {
  // Key management principles required by PCI-DSS:
  // 1. Key Encryption Keys (KEK) must be stored separately from Data Encryption Keys (DEK)
  // 2. DEKs must be rotated at least annually
  // 3. Split knowledge / dual control for key custodians (two people required for key access)
  // 4. Keys must never exist in plaintext outside a Hardware Security Module (HSM) or Key Management System

  constructor(
    private readonly awsKms: KMSClient,         // AWS KMS acts as the HSM-backed key store
    private readonly auditLogRepo: AuditLogRepo,
  ) {}

  async encryptPan(pan: string, context: EncryptionContext): Promise<EncryptedPan> {
    // AWS KMS generates a data key — DEK — encrypted under a CMK (Customer Master Key)
    // CMK never leaves KMS; DEK is used in-memory only
    const { Plaintext: dek, CiphertextBlob: encryptedDek } = await this.awsKms.send(
      new GenerateDataKeyCommand({
        KeyId: process.env.KMS_CMK_ARN,
        KeySpec: 'AES_256',
        EncryptionContext: {
          purpose: context.purpose,
          merchantId: context.merchantId,
        },
      }),
    );

    // Encrypt PAN with DEK in memory — DEK never persisted in plaintext
    const iv = randomBytes(16);
    const cipher = createCipheriv('aes-256-gcm', dek, iv);
    const encrypted = Buffer.concat([cipher.update(pan, 'utf8'), cipher.final()]);
    const authTag = cipher.getAuthTag();

    // Zero out plaintext DEK from memory immediately after use
    dek.fill(0);

    // Store: encrypted PAN + IV + auth tag + encrypted DEK (not plaintext DEK)
    // Decryption requires calling KMS to unwrap the DEK — creates audit trail in KMS
    const encryptedPan: EncryptedPan = {
      ciphertext: encrypted.toString('base64'),
      iv: iv.toString('base64'),
      authTag: authTag.toString('base64'),
      encryptedDek: Buffer.from(encryptedDek!).toString('base64'),
      keyVersion: await this.getCurrentKeyVersion(),
      encryptedAt: new Date(),
    };

    // Log every encryption operation for audit
    await this.auditLogRepo.record({
      operation: 'pan_encrypt',
      keyId: process.env.KMS_CMK_ARN,
      purpose: context.purpose,
      timestamp: new Date(),
      // Never log PAN or DEK
    });

    return encryptedPan;
  }

  async decryptPan(encryptedPan: EncryptedPan, context: EncryptionContext): Promise<string> {
    // Call KMS to decrypt the DEK — this call is logged in AWS CloudTrail
    const { Plaintext: dek } = await this.awsKms.send(
      new DecryptCommand({
        CiphertextBlob: Buffer.from(encryptedPan.encryptedDek, 'base64'),
        EncryptionContext: {
          purpose: context.purpose,
          merchantId: context.merchantId,
        },
      }),
    );

    const decipher = createDecipheriv(
      'aes-256-gcm',
      dek!,
      Buffer.from(encryptedPan.iv, 'base64'),
    );
    decipher.setAuthTag(Buffer.from(encryptedPan.authTag, 'base64'));

    const pan = decipher.update(
      Buffer.from(encryptedPan.ciphertext, 'base64'),
    ).toString('utf8') + decipher.final('utf8');

    dek!.fill(0); // zero DEK immediately

    await this.auditLogRepo.record({
      operation: 'pan_decrypt',
      keyId: process.env.KMS_CMK_ARN,
      purpose: context.purpose,
      timestamp: new Date(),
    });

    return pan;
  }
}
```

**Cryptographic requirements (PCI-DSS v4.0):**
- AES-256 is the standard; AES-128 is accepted but discouraged for new implementations.
- RSA-2048 minimum for asymmetric operations (key exchange); RSA-4096 preferred.
- TLS 1.2 minimum; TLS 1.3 strongly recommended. SSL and TLS 1.0/1.1 are prohibited.
- SHA-256 minimum for hashing; MD5 and SHA-1 are prohibited.
- Key rotation: at least annually; immediately upon suspected or confirmed compromise.

**Q7. What does Requirement 4 demand for data in transit, and what specific TLS configurations are non-compliant?**
A: Requirement 4.2.1 mandates that all transmission of CHD over open, public networks uses strong cryptography. "Open, public networks" includes the internet, wireless networks, Bluetooth, GSM/GPRS/cellular, and satellite communications.

**Non-compliant configurations — prohibited by PCI-DSS:**

| Protocol/Configuration | Status | Reason |
|---|---|---|
| SSL 2.0 / SSL 3.0 | Prohibited | POODLE, DROWN attacks |
| TLS 1.0 | Prohibited | BEAST, POODLE-TLS attacks |
| TLS 1.1 | Prohibited | Deprecated; known weaknesses |
| TLS 1.2 with RC4 cipher | Prohibited | RC4 is broken |
| TLS 1.2 with DES/3DES | Prohibited | Sweet32 attack |
| TLS 1.2 with NULL cipher | Prohibited | No encryption |
| TLS 1.2 with export-grade ciphers | Prohibited | Deliberately weakened |
| Self-signed certificates for external-facing | Non-compliant | No chain of trust |
| Certificates with < 2048-bit RSA key | Non-compliant | Insufficient key strength |

**Compliant TLS configuration for a NestJS payment API:**

```typescript
// main.ts — NestJS HTTPS configuration
import { readFileSync } from 'fs';
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const httpsOptions = {
    key: readFileSync('/etc/ssl/private/server.key'),
    cert: readFileSync('/etc/ssl/certs/server.crt'),
    ca: readFileSync('/etc/ssl/certs/ca-bundle.crt'),

    // PCI-DSS compliant TLS configuration
    minVersion: 'TLSv1.2' as const,
    maxVersion: 'TLSv1.3' as const,

    // Explicitly specify allowed cipher suites — deny all others
    // PCI-DSS requires documented justification for each cipher allowed
    ciphers: [
      // TLS 1.3 cipher suites (automatically used when TLS 1.3 negotiated)
      'TLS_AES_256_GCM_SHA384',
      'TLS_CHACHA20_POLY1305_SHA256',
      'TLS_AES_128_GCM_SHA256',
      // TLS 1.2 cipher suites
      'ECDHE-RSA-AES256-GCM-SHA384',
      'ECDHE-RSA-AES128-GCM-SHA256',
      'ECDHE-RSA-CHACHA20-POLY1305',
      'DHE-RSA-AES256-GCM-SHA384',
    ].join(':'),

    honorCipherOrder: true,  // server cipher preference — not client's

    // Disable session resumption tickets (reduces PFS guarantees)
    // acceptPCI: some assessors require this; check with QSA
    sessionTimeout: 300,     // 5 minutes
  };

  const app = await NestFactory.create(AppModule, { httpsOptions });

  // Security headers — required by Requirement 6 (secure development)
  app.use((req, res, next) => {
    res.setHeader('Strict-Transport-Security', 'max-age=31536000; includeSubDomains; preload');
    res.setHeader('X-Frame-Options', 'DENY');
    res.setHeader('X-Content-Type-Options', 'nosniff');
    res.setHeader('Content-Security-Policy', "default-src 'self'; script-src 'self'");
    next();
  });

  await app.listen(443);
}
```

**Internal network traffic:** PCI-DSS v4.0 (Requirement 4.2.2) now also requires encryption of CHD transmitted over internal networks — not just internet-facing transmission. Internal API-to-API calls, database connections, and message queue messages that carry CHD must use TLS. This is a significant change from v3.2.1, which only required strong cryptography for transmission over open/public networks.

**Q8. What does Requirement 8 demand for authentication, and how does v4.0 change MFA requirements?**
A: Requirement 8 mandates that every person with access to the CDE has a unique user ID (no shared accounts), uses strong authentication, and is subject to access controls that limit what they can do.

**PCI-DSS v4.0 MFA expansion (breaking change from v3.2.1):**

- **v3.2.1:** MFA required only for remote access into the CDE and for non-console administrative access.
- **v4.0:** MFA required for **all access into the CDE** — including console access at a terminal physically in the data center, access from internal networks, and access from within segmented CDE zones to other CDE zones.

This means a developer SSH-ing into a production database server from a corporate VPN — previously MFA-exempt — now requires MFA under v4.0.

**Authentication requirements (Requirement 8.3–8.6):**

```typescript
// auth/mfa/cde-access.guard.ts
// Illustrates the MFA enforcement pattern for CDE access

@Injectable()
export class CdeAccessGuard implements CanActivate {
  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest();
    const user = request.user;

    // Requirement 8.2.1: unique user IDs — no shared/generic accounts
    if (!user || user.isSharedAccount) {
      throw new ForbiddenException('Shared accounts are not permitted for CDE access');
    }

    // Requirement 8.4.2 (v4.0): MFA for ALL CDE access
    if (!user.mfaVerifiedAt || !this.isMfaFresh(user.mfaVerifiedAt)) {
      throw new UnauthorizedException('MFA required for CDE access. Please re-authenticate.');
    }

    // Requirement 8.2.8: session idle timeout — 15 minutes for CDE access
    if (this.isSessionIdle(request.session)) {
      throw new UnauthorizedException('Session expired due to inactivity. Re-authentication required.');
    }

    // Requirement 8.6.1: restrict access for application/system accounts (service accounts)
    if (user.accountType === 'service_account') {
      this.validateServiceAccountRestrictions(user, request);
    }

    return true;
  }

  private isMfaFresh(mfaVerifiedAt: Date): boolean {
    // MFA step-up must be within the current session — not just "MFA enrolled"
    // PCI-DSS does not specify a max MFA age; convention is per-session
    return differenceInMinutes(new Date(), mfaVerifiedAt) < 15;
  }

  private isSessionIdle(session: Session): boolean {
    return differenceInMinutes(new Date(), session.lastActivityAt) > 15;
  }
}

// Password requirements (Requirement 8.3):
// Minimum 12 characters (v4.0 — up from 7 in v3.2.1)
// Must include: uppercase, lowercase, numeric, special character
// No password reuse for last 4 passwords
// Lock account after 10 failed attempts (v4.0 allows up to 10; v3.2.1 was 6)
// Lockout duration: minimum 30 minutes or until administrator unlock
```

**Q9. What does Requirement 10 (Logging and Monitoring) demand, and how do you implement it for a payment service?**
A: Requirement 10 mandates comprehensive audit logging of all activity involving CHD and CDE system components — and the integrity and availability of those logs.

**What must be logged (Requirement 10.2):**
- All individual user access to CHD.
- All actions taken by root or administrative privileges.
- Access to all audit trails.
- Invalid logical access attempts.
- Use of and changes to identification and authentication mechanisms.
- Initialization, stopping, or pausing of audit logs.
- Creation and deletion of system-level objects.

**Log content requirements (Requirement 10.3):** every log entry must contain: user identification, event type, date/time, success/failure, origination (IP/hostname), and identity or name of affected data/component.

**Log retention:** 12 months minimum; at least 3 months immediately available for analysis.

```typescript
// audit/pci-audit-logger.service.ts
export interface PciAuditEvent {
  eventType: PciEventType;
  userId: string;          // unique user ID — never shared accounts
  userRole: string;
  sourceIp: string;
  sourceHostname?: string;
  targetResource: string;  // what was accessed (table name, API endpoint, file)
  targetDataType?: string; // 'CHD' | 'SAD' | 'key_material' | 'audit_log'
  action: string;          // 'read' | 'write' | 'delete' | 'admin'
  outcome: 'success' | 'failure';
  failureReason?: string;
  sessionId: string;
  timestamp: Date;         // must be from NTP-synchronized clock
  // NEVER include: PAN, CVV, PIN, expiry date, magnetic stripe data
}

export type PciEventType =
  | 'chd_access'           // someone accessed cardholder data
  | 'chd_modify'           // CHD was modified
  | 'failed_auth'          // failed login attempt
  | 'privilege_escalation' // user gained elevated access
  | 'admin_action'         // administrative action taken
  | 'audit_log_access'     // audit log itself was read
  | 'key_access'           // encryption key accessed
  | 'system_event';        // service start/stop/restart

@Injectable()
export class PciAuditLogger {
  constructor(
    private readonly logRepo: ImmutableLogRepository,
    private readonly integrity: LogIntegrityService,
  ) {}

  async log(event: PciAuditEvent): Promise<void> {
    // Validate — never log CHD elements
    this.assertNoChdInEvent(event);

    // Compute HMAC of log entry — detects tampering (Requirement 10.3.3)
    const entryHash = this.integrity.computeHmac(JSON.stringify(event));

    await this.logRepo.appendImmutable({
      ...event,
      entryHash,
      // Logs must be on a separate, protected log server (Requirement 10.5)
      // ImmutableLogRepository writes to a separate, write-only log service
    });
  }

  private assertNoChdInEvent(event: PciAuditEvent): void {
    const serialized = JSON.stringify(event);
    // Pattern-match for PAN-like strings (16 digits), CVV (3-4 digits in known fields)
    // This is a safety net — upstream code should never include CHD in audit events
    if (/\b\d{16}\b/.test(serialized)) {
      throw new SecurityError('Potential PAN detected in audit log entry — rejected');
    }
  }
}

// NTP synchronization (Requirement 10.6) — all CDE servers must sync from internal NTP
// AWS: use Amazon Time Sync Service (169.254.169.123)
// Configured in /etc/chrony.conf or /etc/ntp.conf on each CDE instance
```

**Log server segregation (Requirement 10.5):** log files must be stored on a system that is separate from the system generating the logs. If a CDE server is compromised, the attacker must not be able to modify or delete the audit logs. In AWS: CDE application servers send logs to CloudWatch Logs with resource-based policies that deny `logs:DeleteLogGroup` and `logs:PutRetentionPolicy` to all roles except the security team's.

## Section 3: Tokenization In Depth

**Q10. What is tokenization, how does it differ from encryption, and why does it reduce PCI-DSS scope?**
A: Tokenization is the process of replacing a sensitive data element (the PAN) with a non-sensitive surrogate value (the token) that has no mathematical or algorithmic relationship to the original PAN. The mapping between PAN and token is maintained in a secure, isolated token vault.

**Tokenization vs. Encryption:**

| Property | Encryption | Tokenization |
|---|---|---|
| Relationship to original | Mathematical — decryptable with key | None — lookup-table-based |
| Reversibility | Always reversible (with key) | Reversible only via vault lookup |
| Key compromise risk | Compromise of key compromises all data | No key to compromise — vault access controls |
| Performance | Computationally cheap | Requires vault API call per token operation |
| PCI scope impact | Encrypted PAN is still in scope (key management in scope) | Token is out of scope — PAN never leaves vault |
| Format preservation | Not inherent — ciphertext is different length/format | Can be format-preserving (same length as PAN) |
| Use in legacy systems | May require schema changes for ciphertext | Format-preserving tokens need no schema changes |

**How tokenization reduces PCI-DSS scope:**

```
WITHOUT tokenization:
  Customer → Merchant App Server [PAN in memory] → Payment DB [PAN stored] → PG
  All three systems are in PCI-DSS scope.

WITH tokenization (PG-based):
  Customer → Merchant Checkout [PAN collected in PG iFrame/SDK, never reaches merchant] → PG Token Vault
  PG returns token to merchant.
  Merchant App Server [token only] → Merchant DB [token only]
  Only the PG's Token Vault and the customer's browser (PG iFrame) hold the PAN.
  Merchant App Server and DB are OUT of PCI-DSS scope.
```

This scope reduction is the primary business driver for tokenization: a merchant who would otherwise face a full SAQ D assessment (all 12 requirements, 300+ controls) may qualify for SAQ A (22 controls) after implementing PG-hosted tokenization.

**Q11. What are the two types of payment tokens in the Indian/global context, and how do they differ technically?**
A: Two distinct token types serve different purposes in the payment ecosystem:

**Type 1 — PG/Acquirer Tokens (Merchant Tokenization):**
- Issued by a payment gateway (Razorpay, Stripe, Cashfree) or acquirer to a specific merchant.
- Token is merchant-specific: the same card tokenized by Razorpay for Merchant A has a different token for Merchant B — even for the same card.
- Purpose: allows the merchant to charge a customer's saved card without the customer re-entering card details, without the merchant ever holding the PAN.
- Scope: used for recurring payments, one-click checkout, EMI conversions.
- Example: Razorpay's `card_token` or Stripe's `PaymentMethod` object — both are opaque references to a PAN stored in the PG's vault.

**Type 2 — Network Tokens (EMVCo Tokenization):**
- Issued by the card network (Visa Token Service — VTS; Mastercard Digital Enablement Service — MDES; RuPay's equivalent) via the issuing bank.
- Token is device/merchant-scoped but network-level: the same card on the same device at the same merchant gets the same network token consistently.
- Purpose: end-to-end tokenization through the entire payment chain — from merchant to acquirer to network to issuer. The network token replaces the PAN in the authorization message itself.
- Cryptographic binding: each transaction uses a **cryptogram** (transaction-specific value) derived from the token and a dynamic value — even if the token is intercepted, it cannot be replayed without the cryptogram.
- Example: Apple Pay, Google Pay, and Samsung Pay all use network tokens. In India, RBI mandated network tokenization for card-on-file (CoF) recurring payments effective October 2022.

```typescript
// payments/tokenization/token-resolver.service.ts
@Injectable()
export class TokenResolverService {
  // Determine which type of token to use for a given payment scenario
  resolveTokenStrategy(context: PaymentContext): TokenStrategy {
    if (context.paymentType === 'one_time' && context.cardPresent) {
      // Card-present: network token via NFC (Apple Pay / Google Pay)
      return { type: 'network_token', provider: 'emvco' };
    }

    if (context.paymentType === 'recurring' && context.hasCoFMandate) {
      // RBI CoF tokenization mandate: must use network token for saved-card recurring
      // Direct PAN storage for CoF is prohibited since October 2022
      return { type: 'network_token', provider: context.cardNetwork };
    }

    if (context.paymentType === 'one_time' && !context.cardPresent) {
      // One-time CNP: PG token sufficient — customer will re-enter card if needed
      return { type: 'pg_token', provider: context.pgName };
    }

    // Default: PG token
    return { type: 'pg_token', provider: context.pgName };
  }
}
```

**Q12. What is RBI's card-on-file (CoF) tokenization mandate, and how did it change Indian payment engineering?**
A: RBI issued a circular in September 2021 (effective October 2022, after multiple extensions) mandating that no entity in the payment chain — merchant, payment aggregator, payment gateway — can store actual card data (PAN, expiry, CVV) for card-on-file transactions. All CoF must use tokens issued by card networks or card issuers.

**What changed:**
- Before the mandate: merchants and PGs stored raw PANs (or weakly encrypted PANs) in their databases to enable one-click checkout and recurring payments.
- After the mandate: only the card network's token service (Visa VTS, Mastercard MDES, RuPay TSP) can hold the PAN mapping. Merchants hold only a token; PGs hold only a token.

**Token Requestor ID (TRID):** Every entity that requests network tokens must register with the card networks and obtain a TRID. In India, RBI requires all payment aggregators to register as token requestors. Merchants can also register directly, but most use their PA's TRID.

**Engineering impact — the tokenization flow for a new card save:**

```
1. Customer enters card details in PG-hosted iFrame (card data goes directly to PG)
2. PG calls Card Network Token Service API:
   POST /vts/v2/tokens (Visa)
   {
     "cardInfo": { "encryptedData": "<PG-encrypted PAN>" },
     "tokenRequestorId": "TRID_12345",
     "paymentInstrument": { ... }
   }
3. Card Network calls Issuer for approval (issuer may send OTP to cardholder for
   first-time tokenization — consent-based)
4. Network returns Token + Token Expiry + DPAN (Device PAN — the token)
5. PG stores: Token + Token Expiry (not raw PAN)
6. PG returns to merchant: PG's own reference token (wraps the network token)
7. Merchant stores: PG reference token only
```

**Recurring payment using CoF token:**

```typescript
// payments/cof/cof-payment.service.ts

export class CofPaymentService {
  async chargeStoredCard(
    customerId: string,
    merchantId: string,
    amount: number,
    currency: string,
  ): Promise<PaymentResult> {
    // Retrieve PG token — not a PAN
    const savedCard = await this.savedCardRepo.findByCustomer(customerId, merchantId);

    // Validate: only network-tokenized cards may be used for CoF post-RBI mandate
    if (savedCard.tokenType !== 'network_token') {
      throw new CoFComplianceError(
        'Direct PAN storage for CoF is prohibited under RBI CoF Tokenization Mandate. ' +
        'Customer must re-save card using the tokenization flow.',
      );
    }

    // Call PG with token — PG resolves token to network token, adds cryptogram
    const result = await this.pgClient.chargeToken({
      tokenId: savedCard.pgTokenId,        // PG's reference to network token
      amount,
      currency,
      recurring: true,
      merchantId,
      // cryptogram is generated by PG/network for each transaction — not by merchant
    });

    return result;
  }
}
```

**Q13. What is format-preserving tokenization (FPT), and when is it used in legacy systems?**
A: Format-preserving tokenization (FPT) produces a token that has the same length and character set as the original PAN — a 16-digit token for a 16-digit PAN, passing Luhn check validation. This is critical for legacy systems that:
- Have database columns typed as `CHAR(16)` with Luhn validation constraints.
- Have downstream APIs that validate PAN format before forwarding.
- Cannot be modified to accept a different token format.

**FPT vs standard tokenization:**

| Property | Standard Token | Format-Preserving Token |
|---|---|---|
| Length | Variable (UUID, hash, etc.) | Same as PAN (16 digits) |
| Luhn validity | No | Yes (passes Luhn check) |
| Schema changes required | Yes — new column type/length | No — drops into existing schema |
| Uniqueness guarantee | Strong (UUID-space) | Must be carefully designed |
| Legacy system compatibility | No | Yes |
| PCI scope | Out of scope (if properly tokenized) | Out of scope (if properly tokenized) |

**Important caveat:** FPT tokens that pass Luhn validation look like valid PANs. If a system accidentally routes an FPT token to a card network for authorization, it may fail in ways that are difficult to debug. Systems using FPT must strictly distinguish tokens from PANs in their data model.

```typescript
// payments/tokenization/format-preserving-token.service.ts
// FPT is typically implemented by a tokenization vendor (Bluefin, TokenEx, Futurex)
// or a hardware security module (HSM) using AES-FF1 or AES-FF3-1 algorithms

@Injectable()
export class FormatPreservingTokenService {
  // AES-FF1 (NIST SP 800-38G) — format-preserving encryption
  // This is a conceptual illustration; production implementation uses an HSM or certified library

  async tokenize(pan: string): Promise<string> {
    // Delegate to HSM or tokenization vault — never implement FPE yourself
    const token = await this.hsmClient.tokenize({
      data: pan,
      algorithm: 'AES-FF1',
      radix: 10,       // decimal digits only
      tweak: this.config.tweakValue,  // domain separation parameter
    });

    // Store mapping: token → encrypted PAN reference in vault
    // The vault is the only place that knows the mapping
    await this.vaultClient.store(token, pan);

    return token; // 16-digit, Luhn-valid surrogate
  }

  async detokenize(token: string, authorizedContext: string): Promise<string> {
    // Detokenization requires authorization — not all systems can detokenize
    // Only the payment processing path (for authorization) should ever detokenize
    if (!this.isAuthorizedDetokenizer(authorizedContext)) {
      throw new UnauthorizedError('Detokenization not permitted in this context');
    }
    return this.vaultClient.retrieve(token);
  }

  private isAuthorizedDetokenizer(context: string): boolean {
    const AUTHORIZED = new Set(['payment_authorization', 'refund_processing', 'dispute_management']);
    return AUTHORIZED.has(context);
  }
}
```

## Section 4: Scope Reduction, Network Segmentation, and Compliance Operations

**Q14. What is network segmentation in PCI-DSS, and how do you implement it in an AWS-hosted payment system?**
A: Network segmentation isolates CDE systems from non-CDE systems so that a compromise of a non-CDE system cannot directly lead to CHD exposure. PCI-DSS does not mandate segmentation — but without it, every system in the entire network is potentially in scope.

**Without segmentation:** A company's entire AWS account — every EC2, every RDS, every Lambda — is in PCI-DSS scope if any one of them can communicate with a CDE component.

**With segmentation:** Only the CDE VPC (and the systems in it) are in scope. Development, analytics, HR, and other systems are in separate VPCs with no direct connectivity to the CDE.

```
                   Internet

              ┌────────▼────────┐
              │   WAF + ALB     │  ← Req 6: WAF mandatory for internet-facing CHD apps

                       │  HTTPS only — port 443

              │         CDE VPC (isolated)           │
```

**Q15. What is a penetration test under PCI-DSS, and what must it cover?**
A: Requirement 11.4 mandates penetration testing of all CDE systems and segmentation controls at least annually and after any significant change to the CDE. A PCI penetration test differs from a standard security assessment:

**Scope of a PCI penetration test:**
- **External penetration test** — attacker perspective from the internet; targets all internet-facing CDE components (payment API, hosted payment page, admin portals).
- **Internal penetration test** — attacker perspective from inside the network (simulating a compromised internal server or rogue employee); targets all internal CDE components.
- **Segmentation testing** — verifies that CDE network segments are properly isolated; a tester positioned in the non-CDE network must not be able to reach CDE systems. This is often missed but is explicitly required by PCI-DSS v4.0.
- **Application-layer testing** — not just network-level; must include web application testing against OWASP Top 10 (SQL injection, XSS, authentication flaws, etc.) on any application that touches CHD.

**Testing methodology:**
- Must follow an industry-accepted penetration testing methodology: OWASP Testing Guide, PTES (Penetration Testing Execution Standard), NIST SP 800-115, or similar.
- Must be performed by a qualified tester — either an internal ISA or an external party with no conflict of interest in the system being tested.
- Resulting report must document: scope, methodology, findings, evidence (screenshots, output), risk rating, and remediation recommendations.
- All critical and high vulnerabilities must be remediated and retested before the PCI assessment is complete.

## Section 5: Scenario / System Design Style Questions

**Q16. "Design the PCI-DSS compliant architecture for a payment gateway that processes card-not-present transactions."**
A: A full PCI-DSS compliant PG architecture for CNP transactions:

```
Data Flow:

1. Merchant Website (SAQ A scope — out of PCI)
   └── Loads PG-hosted JavaScript SDK from CDN
   └── PAN entered in PG iFrame — never touches merchant's DOM or servers

2. PG JavaScript SDK (in cardholder's browser)
   └── Collects PAN, expiry, CVV
   └── Encrypts client-side using PG's public RSA key
   └── POST to PG's tokenization endpoint (TLS 1.3)

3. PG Tokenization Service [CDE]
   └── Decrypts PAN using HSM-stored private key
   └── Sends PAN to Network Token Service (Visa VTS / MDES) for tokenization
   └── Receives network token (DPAN)
   └── Stores mapping: network_token → PAN in Token Vault (HSM-backed)
   └── Returns PG token to merchant

4. Authorization Service [CDE]
   └── Receives PG token from merchant (for charge)
   └── Looks up network token from vault
   └── Generates cryptogram
   └── Sends ISO 8583 auth request to acquirer (network token + cryptogram — not raw PAN)
   └── Returns auth response to merchant

5. Settlement Service [CDE]
   └── Batches captured transactions
   └── Sends settlement file to acquirer (uses network tokens — not PANs)

6. Audit / Logging [CDE — isolated log tier]
   └── All CHD access logged with user ID, timestamp, source IP, outcome
   └── Logs written to write-only SIEM — developers cannot modify
   └── Log retention: 12 months; 3 months immediately searchable

Infrastructure controls:
- CDE VPC: isolated from all non-CDE systems
- HSM: AWS CloudHSM or Thales Luna for key operations
- KMS: AWS KMS for DEK generation and wrapping
- MFA: enforced for all CDE access (Okta + TOTP)
- WAF: AWS WAF on all internet-facing endpoints (OWASP rule set)
- ASV scans: quarterly (Trustwave, Qualys, or equivalent)
- Penetration test: annual + post-significant-change
- FIM: AWS Config + custom Lambda for file integrity monitoring on CDE instances
- NTP: Amazon Time Sync Service on all CDE instances
- Patch management: critical patches within 1 month (Req 6.3.3)
```

**Q17. "A developer accidentally logged the full PAN in an API debug log. What do you do?"**
A: This is a PCI-DSS incident — specifically a CHD exposure event. The response must follow the organization's incident response plan (Requirement 12.10) and move fast:

**Immediate response (first 30 minutes):**

```
Step 1: Contain
  - Identify the log file location and disable further logging to that sink immediately.
  - If logs are in a centralized log system (Splunk, CloudWatch): restrict access to the log stream.
  - Do not delete the logs — that would destroy forensic evidence and is itself a compliance violation.

Step 2: Assess scope
  - How many PANs were logged? (query log for PAN-pattern matches: \b\d{16}\b)
  - What log systems received the data? (application log → CloudWatch → S3 → any analytics pipeline?)
  - Who has access to those log systems?
  - How long was the logging active before discovery?
```

```typescript
// Incident: scan logs to quantify PANs exposed
// Run this in a forensic environment, not production
async function scanLogsForPans(logGroupName: string, startTime: Date): Promise<number> {
  const query = `
    fields @timestamp, @message
    | filter @message like /\b\d{13,19}\b/
    | stats count() as potential_pan_count
  `;
  const result = await cloudwatchLogs.startQuery({
    logGroupName,
    startTime: startTime.getTime(),
    endTime: Date.now(),
    queryString: query,
  }).promise();
  // Returns count of log entries with potential PAN-like strings
  return result.results?.[0]?.[0]?.value ?? 0;
}
```

**Remediation (within 24 hours):**
- Remove or mask the PAN from logs (replace with masked equivalent: `XXXXXXXXXXXX1234`).
- If logs have been shipped to S3/archives: purge from all downstream destinations.
- Rotate any keys or tokens that may have been associated with the exposed PANs.
- Review and fix the code that caused the logging — add CHD scrubbing to the logging middleware.

**Notification obligations:**
- Notify the QSA and acquirer — PCI-DSS Requirement 12.10 requires a defined incident response plan; the QSA must be informed of incidents that affect the CDE.
- If the breach involved actual card fraud, card networks (Visa, Mastercard) must be notified per their incident reporting timelines (typically within 24–72 hours of confirmed breach).
- CERT-In (India): if the organization is a SEBI/RBI-regulated entity, CERT-In breach notification within 6 hours of detection is now mandatory (CERT-In 2022 directions).

**Prevention — logging middleware that scrubs CHD:**

```typescript
// middleware/log-scrubber.middleware.ts
@Injectable()
export class LogScrubberMiddleware implements NestMiddleware {
  // Patterns that indicate CHD — scrub before any logging
  private readonly CHD_PATTERNS = [
    { pattern: /\b(\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4})\b/g, replacement: 'XXXX-XXXX-XXXX-$1'.slice(-4), label: 'PAN' },
    { pattern: /"cvv"\s*:\s*"\d{3,4}"/gi, replacement: '"cvv":"***"', label: 'CVV' },
    { pattern: /"cvv2"\s*:\s*"\d{3,4}"/gi, replacement: '"cvv2":"***"', label: 'CVV2' },
    { pattern: /"expiry"\s*:\s*"\d{2}\/\d{2,4}"/gi, replacement: '"expiry":"**/**"', label: 'Expiry' },
    { pattern: /"card_number"\s*:\s*"\d+"/gi, replacement: '"card_number":"XXXXXXXXXXXX****"', label: 'CardNumber' },
  ];

  use(req: Request, res: Response, next: NextFunction) {
    // Wrap the request body before it reaches any logger
    const originalBody = req.body;
    req.body = this.scrubObject(originalBody);
    next();
  }

  scrubString(input: string): string {
    let scrubbed = input;
    for (const { pattern, replacement } of this.CHD_PATTERNS) {
      scrubbed = scrubbed.replace(pattern, replacement);
    }
    return scrubbed;
  }

  private scrubObject(obj: unknown): unknown {
    if (typeof obj === 'string') return this.scrubString(obj);
    if (Array.isArray(obj)) return obj.map(item => this.scrubObject(item));
    if (obj && typeof obj === 'object') {
      return Object.fromEntries(
        Object.entries(obj).map(([k, v]) => [k, this.scrubObject(v)]),
      );
    }
    return obj;
  }
}
```

**Q18. "How do you achieve and maintain PCI-DSS compliance as a fast-moving fintech startup — without slowing down product delivery?"**
A: PCI-DSS compliance and engineering velocity are often framed as opposites — they are not, but reconciling them requires deliberate architectural choices made early:

**Strategy 1: Maximize scope reduction through outsourcing CHD handling**

The single highest-leverage action: use a PG-hosted payment page (Razorpay Checkout, Stripe Elements, Cashfree Checkout). The PG's iFrame handles card data; your servers never see the PAN. You qualify for SAQ A (22 controls) instead of SAQ D (300+ controls). This is the correct starting point for any fintech that is not itself a payment processor.

**Strategy 2: Build PCI controls into the platform, not as an afterthought**

```typescript
// Example: CDE network segmentation from day one using Infrastructure as Code
// Changing from flat to segmented network post-launch is a multi-month project.
// Building it segmented from day one costs days, not months.

// Compliance as code — PCI controls checked in CI/CD:
// - Terraform/CDK modules for CDE VPC are the only approved way to deploy CDE infra.
// - Security group rules are codified — no manual console changes allowed.
// - AWS Config rules automatically flag non-compliant resources (unencrypted S3, open security groups).
// - Pre-commit hooks prevent CHD-pattern strings from appearing in code.
```

**Strategy 3: Automate continuous compliance monitoring**

Instead of a once-yearly scramble for the QSA audit, build continuous monitoring:

```
AWS Config Rules → detect non-compliant resources in real-time
AWS Security Hub → aggregate findings from GuardDuty, Inspector, Config
Quarterly ASV scans → automated via Qualys or Trustwave API
Penetration testing → schedule annually + after each major release
Log review → SIEM rules alert on CHD-access anomalies daily (not just at audit time)
Key rotation → automated via AWS KMS key rotation policy (annual rotation enforced by policy)
```

**Strategy 4: Use a shared responsibility model with your PG**

Your PG (Razorpay, Stripe) is a PCI-DSS Level 1 certified Service Provider. Their compliance attestation (Attestation of Compliance — AoC) partially satisfies your own compliance obligation for the components they manage. Download their AoC and map which PCI requirements are covered by the PG and which remain your responsibility. This reduces your assessment scope to only the controls you directly own.

**Strategy 5: Treat PCI DSS like a product backlog**

Each of the 12 requirements is a set of controls. Map every control to either:
- **Inherited from PG/cloud provider** (AWS's physical security covers Requirement 9 for cloud-hosted systems).
- **Platform-level** (network segmentation, encryption, logging — built into the platform once).
- **Application-level** (code-level controls: no CHD in logs, TLS enforcement, access control).
- **Process-level** (training, vendor management, incident response — HR/Ops owned).

Engineering owns platform and application controls. When sprint planning, PCI controls for a new feature are acceptance criteria — not a separate compliance task. A feature that processes card data and ships without proper logging or without going through the CHD scrubber fails its acceptance criteria.
