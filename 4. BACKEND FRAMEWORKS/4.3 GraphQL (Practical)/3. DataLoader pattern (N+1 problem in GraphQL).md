# GraphQL DataLoader Pattern (N+1 Problem) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the N+1 problem in GraphQL and why does it occur more acutely than in REST?**
A: The N+1 problem occurs when fetching a list of N items triggers N additional queries — one per item — to resolve a nested field. It exists in REST too, but GraphQL exposes it more acutely because resolvers are the primary composition mechanism and each field resolves independently:

```
REST: the developer writes the SQL — they can JOIN manually
GraphQL: each resolver is a black box, called independently per object
         the framework has no knowledge that 100 resolvers will run the same query

Example schema:
  type Query {
      loans: [Loan!]!
  }
  type Loan {
      id: ID!
      amount: Float!
      borrower: User!   ← this field triggers the N+1
  }
  type User {
      id: ID!
      name: String!
  }

Query:
  {
    loans {
      id
      amount
      borrower { name }
    }
  }

Naive resolver execution:
  1 query:  SELECT * FROM loans                          → returns 100 loans
  100 queries: SELECT * FROM users WHERE id = 'u1'
               SELECT * FROM users WHERE id = 'u2'
               ...
               SELECT * FROM users WHERE id = 'u100'
  Total: 101 queries (1 + N)

Why GraphQL worsens this:
  - Resolver for Loan.borrower fires once per Loan object in the parent list
  - Each resolver call is isolated — it doesn't know 99 others are about to run
  - Nesting amplifies it: 3 levels deep → 1 + N + N² queries
    loans → borrowers → borrower.address → 1 + 100 + 100×5 = 601 queries
```

**Q2. What is a DataLoader and what two mechanisms does it use to solve the N+1 problem?**
A: DataLoader (originally by Facebook, now maintained as a community library) solves the N+1 problem through two complementary mechanisms — batching and caching — applied to a single request lifecycle:

```
Mechanism 1: Batching
  Instead of executing a load immediately, DataLoader defers it to the next tick
  of the event loop. All loads queued within the same tick are collected and
  dispatched together as a single batch function call.

  Without DataLoader:
    tick 0:  load(u1) → SELECT WHERE id='u1'
    tick 1:  load(u2) → SELECT WHERE id='u2'
    ...
    tick 99: load(u100) → SELECT WHERE id='u100'
    Result: 100 queries

  With DataLoader:
    tick 0:  load(u1)  ─┐
    tick 0:  load(u2)   ├─ all deferred
    ...                  │
    tick 0:  load(u100) ─┘
    tick 1:  batchFn(['u1','u2',...,'u100']) → SELECT WHERE id IN (...)
    Result: 1 query

Mechanism 2: Per-request caching (memoization)
  Within the same request, if the same key is loaded twice,
  the second call returns the cached Promise — no second query:

    load('u1') → hits DB, caches Promise<User>
    load('u1') → returns cached Promise<User> immediately (same tick or later)

  The cache is scoped to the DataLoader INSTANCE — which must be
  created per-request (not shared across requests — that would be a
  data isolation bug: user A sees user B's cached data).
```

**Q3. How does DataLoader's batching work mechanically with the event loop?**
A: DataLoader exploits the single-threaded nature of Node.js — specifically, the microtask queue and `process.nextTick`. When `load(key)` is called, the key is queued and a flush is scheduled. All synchronous code runs first, accumulating keys, then the flush fires:

```javascript
// Simplified DataLoader internals:
class DataLoader {
    constructor(batchFn) {
        this._batchFn = batchFn;
        this._queue = [];       // keys waiting to be batched
        this._cache = new Map(); // key → Promise
        this._scheduled = false;
    }

    load(key) {
        // Check cache first:
        if (this._cache.has(key)) return this._cache.get(key);

        const promise = new Promise((resolve, reject) => {
            this._queue.push({ key, resolve, reject });
        });

        this._cache.set(key, promise);

        // Schedule a flush if not already scheduled:
        if (!this._scheduled) {
            this._scheduled = true;
            // process.nextTick fires AFTER all synchronous code in the current tick
            // but BEFORE I/O events — ensures all resolver calls in one resolver
            // cycle are batched together:
            process.nextTick(() => this._dispatch());
        }

        return promise;
    }

    async _dispatch() {
        this._scheduled = false;
        const queue = this._queue.splice(0);  // drain the queue
        const keys = queue.map(q => q.key);

        try {
            // batchFn receives ALL keys collected since last flush:
            const values = await this._batchFn(keys);

            // CRITICAL CONTRACT: values must be same length and same order as keys
            // values[i] corresponds to keys[i]
            queue.forEach(({ resolve, reject }, i) => {
                if (values[i] instanceof Error) reject(values[i]);
                else resolve(values[i]);
            });
        } catch (err) {
            queue.forEach(({ reject }) => reject(err));
        }
    }
}

// The ordering contract — batch function MUST return results in key order:
async function userBatchFn(userIds) {
    const users = await db.query('SELECT * FROM users WHERE id = ANY($1)', [userIds]);

    // DB may return in any order — must map back to input key order:
    const userMap = new Map(users.map(u => [u.id, u]));

    // Return array aligned to input userIds:
    return userIds.map(id => userMap.get(id) ?? new Error(`User ${id} not found`));
    //                                              ↑ missing keys get Error, not null
    //                                                DataLoader rejects that specific promise
}
```

## Section 2: Implementation

**Q4. How do you implement DataLoader in a NestJS GraphQL application with per-request scoping?**
A: The critical constraint is that DataLoader instances must be created per request — shared instances leak cached data across users. In NestJS, the standard pattern passes a DataLoader factory through the GraphQL context:

```typescript
// dataloader.factory.ts — creates fresh DataLoader instances per request:
import DataLoader from 'dataloader';
import { Injectable } from '@nestjs/common';
import { UserRepository } from '../user/user.repository';
import { User } from '../user/user.entity';

@Injectable()
export class DataLoaderFactory {
    constructor(private userRepo: UserRepository) {}

    // Called once per request — returns a new DataLoader:
    createUserLoader(): DataLoader<string, User> {
        return new DataLoader<string, User>(
            async (userIds: readonly string[]) => {
                const users = await this.userRepo.findByIds([...userIds]);
                const userMap = new Map(users.map(u => [u.id, u]));
                // Must return same-length array in same order as input:
                return userIds.map(
                    id => userMap.get(id) ?? new Error(`User not found: ${id}`)
                );
            },
            {
                // Options:
                cache: true,           // per-request memoization (default: true)
                maxBatchSize: 1000,    // max keys per batch call
                batchScheduleFn: (callback) => setTimeout(callback, 0),
                // default: process.nextTick — use setTimeout(0) if you want
                // to accumulate across microtasks too
            }
        );
    }
}

// app.module.ts — attach loaders to GraphQL context:
@Module({
    imports: [
        GraphQLModule.forRootAsync<ApolloDriverConfig>({
            driver: ApolloDriver,
            imports: [DataLoaderModule],
            inject: [DataLoaderFactory],
            useFactory: (loaderFactory: DataLoaderFactory) => ({
                autoSchemaFile: true,
                context: ({ req }) => ({
                    req,
                    // Create fresh DataLoader instances per request:
                    loaders: {
                        user: loaderFactory.createUserLoader(),
                        loan: loaderFactory.createLoanLoader(),
                        document: loaderFactory.createDocumentLoader(),
                    },
                }),
            }),
        }),
    ],
})
export class AppModule {}

// loan.resolver.ts — use the loader from context:
@Resolver(() => Loan)
export class LoanResolver {
    @ResolveField(() => User)
    async borrower(
        @Parent() loan: Loan,
        @Context() ctx: { loaders: AppLoaders },
    ): Promise<User> {
        // All borrower() calls within one request batch automatically:
        return ctx.loaders.user.load(loan.borrowerId);
    }
}
```

**Q5. How do you implement a DataLoader for a one-to-many relationship (e.g., a loan has many documents)?**
A: One-to-many loaders are subtly different from one-to-one — the batch function returns arrays, and missing keys must return empty arrays (not errors), since "no documents for this loan" is a valid state:

```typescript
// document.loader.ts — one-to-many: each loanId → Document[]
import DataLoader from 'dataloader';
import { Injectable } from '@nestjs/common';
import { DocumentRepository } from './document.repository';
import { Document } from './document.entity';

@Injectable()
export class DocumentLoaderFactory {
    constructor(private documentRepo: DocumentRepository) {}

    createDocumentsByLoanLoader(): DataLoader<string, Document[]> {
        return new DataLoader<string, Document[]>(
            async (loanIds: readonly string[]) => {
                // Fetch ALL documents for ALL loan IDs in one query:
                const documents = await this.documentRepo.findByLoanIds([...loanIds]);

                // Group by loanId:
                const docMap = new Map<string, Document[]>(
                    loanIds.map(id => [id, []])   // initialize with empty arrays
                );
                for (const doc of documents) {
                    docMap.get(doc.loanId)?.push(doc);
                }

                // Return in input key order — missing keys return [] not Error:
                return loanIds.map(id => docMap.get(id) ?? []);
            }
        );
    }
}

// loan.resolver.ts:
@Resolver(() => Loan)
export class LoanResolver {
    @ResolveField(() => [Document])
    async documents(
        @Parent() loan: Loan,
        @Context() ctx: { loaders: AppLoaders },
    ): Promise<Document[]> {
        return ctx.loaders.documentsByLoan.load(loan.id);
    }
}

// The SQL it generates:
// Without DataLoader: SELECT * FROM documents WHERE loan_id = 'L001'
//                     SELECT * FROM documents WHERE loan_id = 'L002'  (× N)
// With DataLoader:    SELECT * FROM documents WHERE loan_id = ANY('{L001,L002,...}'::uuid[])
```

**Q6. How do you implement a DataLoader with composite keys (e.g., fetching by two fields)?**
A: DataLoader keys are strings by default. For composite keys, you serialize them to a string and deserialize in the batch function. Alternatively, use the `cacheKeyFn` option:

```typescript
// Composite key: fetch loan documents filtered by type and status
interface DocumentKey {
    loanId: string;
    type: DocumentType;
}

export function createDocumentByTypeLoader(
    documentRepo: DocumentRepository,
): DataLoader<DocumentKey, Document[]> {
    return new DataLoader<DocumentKey, Document[]>(
        async (keys: readonly DocumentKey[]) => {
            // Decompose to unique loanIds and types:
            const conditions = keys.map(k => ({ loanId: k.loanId, type: k.type }));

            // Single query with OR conditions or IN clause on composite:
            const documents = await documentRepo.findByLoanIdsAndTypes(conditions);

            // Map results back to composite keys:
            const resultMap = new Map<string, Document[]>();
            for (const doc of documents) {
                const compositeKey = `${doc.loanId}:${doc.type}`;
                if (!resultMap.has(compositeKey)) resultMap.set(compositeKey, []);
                resultMap.get(compositeKey)!.push(doc);
            }

            return keys.map(k => resultMap.get(`${k.loanId}:${k.type}`) ?? []);
        },
        {
            // Tell DataLoader how to cache composite key objects:
            // Without this, object identity is used — two { loanId: 'L1', type: 'KYC' }
            // objects are different cache entries even if they're equal:
            cacheKeyFn: (key: DocumentKey) => `${key.loanId}:${key.type}`,
        },
    );
}

// Usage:
@ResolveField(() => [Document])
async kycDocuments(@Parent() loan: Loan, @Context() ctx: AppContext) {
    return ctx.loaders.documentByType.load({
        loanId: loan.id,
        type: DocumentType.KYC,
    });
}
```

**Q7. How do you implement DataLoaders using NestJS's `@nestjs/dataloader` or a custom `NestDataLoader` abstraction?**
A: A common pattern in NestJS is to define an interface that standardizes DataLoader creation, then register loaders as request-scoped providers and inject them via a custom decorator:

```typescript
// interfaces/nest-dataloader.interface.ts:
import DataLoader from 'dataloader';

export interface NestDataLoader<K, V> {
    generateDataLoader(): DataLoader<K, V>;
}

export const DATALOADER_CONTEXT_KEY = '__graphqlDataLoaders';

// user.loader.ts — request-scoped provider:
import { Injectable, Scope } from '@nestjs/common';
import DataLoader from 'dataloader';
import { NestDataLoader } from '../interfaces/nest-dataloader.interface';

@Injectable({ scope: Scope.REQUEST })  // NEW instance per request — critical
export class UserLoader implements NestDataLoader<string, User> {
    constructor(private userRepo: UserRepository) {}

    generateDataLoader(): DataLoader<string, User> {
        return new DataLoader<string, User>(async (ids: readonly string[]) => {
            const users = await this.userRepo.findByIds([...ids]);
            const map = new Map(users.map(u => [u.id, u]));
            return ids.map(id => map.get(id) ?? new Error(`User ${id} not found`));
        });
    }
}

// dataloader.interceptor.ts — creates loaders and attaches to GQL context:
@Injectable()
export class DataLoaderInterceptor implements NestInterceptor {
    constructor(private readonly moduleRef: ModuleRef) {}

    intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
        const graphqlExecutionContext = GqlExecutionContext.create(context);
        const ctx = graphqlExecutionContext.getContext();

        if (ctx[DATALOADER_CONTEXT_KEY] === undefined) {
            ctx[DATALOADER_CONTEXT_KEY] = this.createLoaders();
        }

        return next.handle();
    }

    private createLoaders() {
        return {
            user: this.moduleRef
                .get<UserLoader>(UserLoader, { strict: false })
                .generateDataLoader(),
            loan: this.moduleRef
                .get<LoanLoader>(LoanLoader, { strict: false })
                .generateDataLoader(),
        };
    }
}

// Loader() decorator for clean injection in resolvers:
export const Loader = (loader: Type<NestDataLoader<unknown, unknown>>) =>
    createParamDecorator(
        (_data: unknown, ctx: ExecutionContext) => {
            const gqlCtx = GqlExecutionContext.create(ctx).getContext();
            // Instantiate loader lazily if not yet created:
            return gqlCtx[DATALOADER_CONTEXT_KEY][loader.name];
        },
    )();

// Usage in resolver:
@Resolver(() => Loan)
export class LoanResolver {
    @ResolveField(() => User)
    async borrower(
        @Parent() loan: Loan,
        @Loader(UserLoader) userLoader: DataLoader<string, User>,
    ): Promise<User> {
        return userLoader.load(loan.borrowerId);
    }
}
```

## Section 3: Caching Behaviour and Edge Cases

**Q8. What is the difference between DataLoader's request-scoped cache and a shared cache, and what bugs arise from each?**
A: DataLoader has a built-in per-instance cache (a `Map` from key to Promise). Its scope is determined entirely by the lifetime of the DataLoader instance — this is why instance creation strategy is the most important operational decision:

```typescript
// BUG 1: Singleton DataLoader (shared across all requests — data leak):
@Injectable()
export class UserService {
    // Created once at module init — shared by ALL users of ALL requests:
    private userLoader = new DataLoader(this.batchFn);

    async getUser(id: string) {
        return this.userLoader.load(id);  // User A's data leaks to User B's request
    }
}
// Fix: create DataLoader inside the GraphQL context factory (per-request)

// BUG 2: Request-scoped DataLoader (correct for isolation, but beware mutations):
// The cache persists for the lifetime of the request.
// If a mutation changes User u1 mid-request, subsequent loads return STALE data:

@Mutation(() => User)
async updateUser(@Args('input') input: UpdateUserInput, @Context() ctx: AppContext) {
    const updated = await this.userService.update(input);

    // Cache still has the OLD user at key input.id:
    const stale = await ctx.loaders.user.load(input.id);  // returns pre-update data!

    // Fix: clear the specific cache entry after mutation:
    ctx.loaders.user.clear(input.id);
    const fresh = await ctx.loaders.user.load(input.id);  // re-fetches

    return fresh;
}

// BUG 3: Caching null vs Error — handle missing entities correctly:
// BAD batch function:
return ids.map(id => userMap.get(id) ?? null);
// null is a valid resolved value — DataLoader caches it
// On retry: returns cached null, never retries the DB
// If the null was a transient DB error, the user is stuck with null for the request

// GOOD batch function:
return ids.map(id => userMap.get(id) ?? new Error(`User ${id} not found`));
// Error causes the individual Promise to reject — not cached — retried on next load()

// Disabling cache entirely when freshness matters more than batching:
const freshLoader = new DataLoader(batchFn, { cache: false });
// Each load() always joins the next batch — no memoization
// Useful for loaders inside mutation resolvers
```

**Q9. How does DataLoader interact with GraphQL field-level concurrency and what is the execution order you should expect?**
A: GraphQL resolvers execute concurrently at each level of the tree — all sibling fields of the same object resolve in parallel, but a parent must resolve before its children. DataLoader's batching window is the event loop tick between levels:

```
Query execution order with DataLoader:

Level 0 — Query.loans resolves:
  tick 0: loans() runs → returns [L1, L2, L3] synchronously (or awaits one DB call)

Level 1 — Loan fields resolve concurrently:
  tick 1: L1.id, L1.amount, L1.borrower() ─┐
           L2.id, L2.amount, L2.borrower() ─┤ all fire in the same tick
           L3.id, L3.amount, L3.borrower() ─┘
  Each borrower() calls userLoader.load(loanN.borrowerId)
  All three loads are queued in userLoader's queue

  process.nextTick fires → batchFn(['u1','u2','u3']) → 1 SQL query
  All three Promises resolve with their respective User objects

Level 2 — User fields resolve concurrently:
  tick 2: U1.name, U1.address() ─┐
           U2.name, U2.address() ─┤ all fire in same tick → addressLoader batches
           U3.name, U3.address() ─┘

// Total DB queries regardless of N:
//   1 (loans) + 1 (users batch) + 1 (addresses batch) = 3 queries
//   vs naive: 1 + N + N = 1 + 3 + 3 = 7 (and exponentially worse at scale)

// Important: the batch window is ONE event loop tick
// If resolvers at the same level call load() asynchronously (after an await),
// they may batch separately:

// BAD — loses batching:
@ResolveField()
async borrower(@Parent() loan: Loan, @Context() ctx: AppContext) {
    await someAsyncWork();           // this yields the event loop
    return ctx.loaders.user.load(loan.borrowerId);  // may fire in a different tick
}

// GOOD — preserve batching:
@ResolveField()
async borrower(@Parent() loan: Loan, @Context() ctx: AppContext) {
    const loaderPromise = ctx.loaders.user.load(loan.borrowerId);  // queue first
    await someAsyncWork();           // now it's safe to yield
    return loaderPromise;
}
```

**Q10. How do you handle DataLoader errors — both batch-level failures and per-key failures?**

```typescript
// Two failure modes:

// Mode 1: Batch-level failure (DB connection lost, query throws):
// batchFn throws → ALL promises in the batch reject with the same error
// DataLoader does NOT cache rejections — next load() for those keys retries

async function userBatchFn(ids: readonly string[]): Promise<(User | Error)[]> {
    try {
        const users = await db.query('SELECT * FROM users WHERE id = ANY($1)', [ids]);
        const map = new Map(users.map(u => [u.id, u]));
        return ids.map(id => map.get(id) ?? new Error(`Not found: ${id}`));
    } catch (dbErr) {
        // Entire batch failed — map to per-key errors so DataLoader
        // rejects each Promise individually (better DX than one global rejection):
        return ids.map(() => new Error(`DB unavailable: ${dbErr.message}`));
        // Each caller gets their own rejection — can be caught independently
    }
}

// Mode 2: Per-key failure (some users exist, some don't):
return ids.map(id => {
    const user = map.get(id);
    if (!user) return new Error(`User ${id} not found`);  // only THIS key rejects
    return user;
});

// Caller handling:
@ResolveField(() => User, { nullable: true })
async borrower(@Parent() loan: Loan, @Context() ctx: AppContext): Promise<User | null> {
    try {
        return await ctx.loaders.user.load(loan.borrowerId);
    } catch (err) {
        if (err.message.includes('not found')) return null;  // graceful null
        throw err;  // propagate real errors to GraphQL error list
    }
}

// Global error handling — log loader errors without crashing:
const userLoader = new DataLoader<string, User>(
    async (ids) => {
        try {
            return await userBatchFn(ids);
        } catch (err) {
            logger.error('UserLoader batch failed', { err, ids });
            return ids.map(() => err);  // propagate to callers
        }
    }
);
```

## Section 4: Performance and Observability

**Q11. How do you add instrumentation to DataLoaders to measure batch sizes, cache hit rates, and query counts?**

```typescript
// Instrumented DataLoader wrapper:
import DataLoader from 'dataloader';

interface LoaderStats {
    batchCount: number;
    totalLoads: number;
    cacheHits: number;
    avgBatchSize: number;
    batchSizes: number[];
}

function instrumentedLoader<K, V>(
    name: string,
    batchFn: DataLoader.BatchLoadFn<K, V>,
    options?: DataLoader.Options<K, V>,
): DataLoader<K, V> {
    const stats: LoaderStats = {
        batchCount: 0,
        totalLoads: 0,
        cacheHits: 0,
        avgBatchSize: 0,
        batchSizes: [],
    };

    const wrappedBatchFn: DataLoader.BatchLoadFn<K, V> = async (keys) => {
        stats.batchCount++;
        stats.batchSizes.push(keys.length);
        stats.avgBatchSize = stats.batchSizes.reduce((a, b) => a + b, 0) / stats.batchCount;

        const start = Date.now();
        try {
            const results = await batchFn(keys);
            const duration = Date.now() - start;

            // Emit to your metrics system:
            metrics.histogram(`dataloader.${name}.batch_size`, keys.length);
            metrics.histogram(`dataloader.${name}.batch_duration_ms`, duration);
            metrics.increment(`dataloader.${name}.batch_count`);

            return results;
        } catch (err) {
            metrics.increment(`dataloader.${name}.batch_error`);
            throw err;
        }
    };

    const loader = new DataLoader<K, V>(wrappedBatchFn, options);

    // Wrap load() to track cache hits:
    const originalLoad = loader.load.bind(loader);
    loader.load = (key: K) => {
        stats.totalLoads++;
        const cacheKey = (options?.cacheKeyFn ?? String)(key);
        const isCacheHit = (loader as unknown as { _cacheMap: Map<unknown, unknown> })
            ._cacheMap?.has(cacheKey);
        if (isCacheHit) stats.cacheHits++;
        return originalLoad(key);
    };

    return loader;
}

// Logging batch stats at request end (Apollo plugin):
const requestEndPlugin = {
    requestDidStart: () => ({
        willSendResponse: ({ context }) => {
            for (const [name, loader] of Object.entries(context.loaders)) {
                logger.debug(`DataLoader stats [${name}]`, {
                    // access stats from loader instance
                });
            }
        },
    }),
};
```

**Q12. What is the `maxBatchSize` option and when do you need it?**
A: By default DataLoader batches every key queued in one event loop tick into a single batch function call. With very large N, this can produce a single SQL `IN (...)` clause with thousands of values — which some databases handle poorly or which exceeds query length limits:

```typescript
// PostgreSQL handles large IN clauses well but has practical limits:
// 65535 parameters per query (prepared statement limit)
// Very large IN clauses can be slower than smaller batches due to planner cost

const userLoader = new DataLoader<string, User>(
    async (ids: readonly string[]) => {
        // ids.length is bounded by maxBatchSize:
        const users = await db.query('SELECT * FROM users WHERE id = ANY($1)', [ids]);
        const map = new Map(users.map(u => [u.id, u]));
        return [...ids].map(id => map.get(id) ?? new Error(`Not found: ${id}`));
    },
    {
        maxBatchSize: 500,  // split into batches of ≤500
        // If 1200 keys are queued: DataLoader calls batchFn 3 times:
        //   batchFn(keys[0..499])
        //   batchFn(keys[500..999])
        //   batchFn(keys[1000..1199])
        // All three run concurrently (Promise.all internally)
    },
);

// For external APIs with rate limits — use maxBatchSize to control burst:
const externalApiLoader = new DataLoader<string, CibilScore>(
    async (panNumbers: readonly string[]) => {
        // CIBIL API: max 100 records per request
        return Promise.all(panNumbers.map(pan => cibilApi.getScore(pan)));
        // With maxBatchSize: 100, never sends >100 per request
    },
    { maxBatchSize: 100 }
);
```

**Q13. How do you tune DataLoader's batch scheduling for different workloads?**

```typescript
// Default scheduler: process.nextTick
// — batches all loads queued synchronously in the current tick
// — very tight window: only synchronous loads batch together

// Custom scheduler: setTimeout(0) / setImmediate
// — wider window: allows async loads across microtasks to batch together

const loader = new DataLoader(batchFn, {
    batchScheduleFn: (callback) => setImmediate(callback),
    // setImmediate fires after I/O events — slightly wider window than nextTick
    // Can improve batch sizes when resolvers do a small async op before loading
});

// Promise.resolve().then() — microtask level (between nextTick and setTimeout):
const loader = new DataLoader(batchFn, {
    batchScheduleFn: (callback) => Promise.resolve().then(callback),
});

// Choosing the scheduler:
//
// process.nextTick (default):
//   ✓ Fastest response time — flush happens as soon as possible
//   ✗ Tightest batching window — async resolver code before load() misses the batch
//   Use: when resolvers call load() synchronously, response latency is priority
//
// setImmediate / setTimeout(0):
//   ✓ Wider batching window — more keys collected per batch
//   ✗ Slightly higher latency — waits one full event loop cycle
//   Use: when resolvers do async work before calling load(), batch size is priority
//
// Custom (debounce with time window):
const loader = new DataLoader(batchFn, {
    batchScheduleFn: (callback) => setTimeout(callback, 5),
    // Wait 5ms — accumulate loads from slightly delayed resolvers
    // Risk: adds 5ms minimum latency to every first load
});
```

## Section 5: Advanced Patterns

**Q14. How do you implement a DataLoader that fetches from a cache (Redis) first and falls back to the database?**

```typescript
// Two-tier DataLoader: Redis L1 cache → PostgreSQL L2
@Injectable({ scope: Scope.REQUEST })
export class UserLoader implements NestDataLoader<string, User> {
    constructor(
        private redis: RedisService,
        private userRepo: UserRepository,
    ) {}

    generateDataLoader(): DataLoader<string, User> {
        return new DataLoader<string, User>(async (ids: readonly string[]) => {
            const cacheKeys = ids.map(id => `user:${id}`);

            // Step 1: Bulk fetch from Redis:
            const cached = await this.redis.mget(...cacheKeys);

            const missingIds: string[] = [];
            const results = new Map<string, User>();

            cached.forEach((val, i) => {
                if (val) results.set(ids[i], JSON.parse(val));
                else missingIds.push(ids[i]);
            });

            // Step 2: Fetch misses from DB in one query:
            if (missingIds.length > 0) {
                const dbUsers = await this.userRepo.findByIds(missingIds);

                // Populate Redis for future requests (pipeline for efficiency):
                const pipeline = this.redis.pipeline();
                for (const user of dbUsers) {
                    results.set(user.id, user);
                    pipeline.setex(`user:${user.id}`, 300, JSON.stringify(user));  // TTL 5min
                }
                await pipeline.exec();
            }

            // Return in input order:
            return ids.map(id => results.get(id) ?? new Error(`User not found: ${id}`));
        });
    }
}

// Cache invalidation on update (in UserService):
async updateUser(id: string, data: UpdateUserDto): Promise<User> {
    const updated = await this.userRepo.update(id, data);
    await this.redis.del(`user:${id}`);  // invalidate Redis entry
    return updated;
}
```

**Q15. How do you handle DataLoader in subscriptions and websocket contexts?**
A: GraphQL subscriptions have a different lifecycle from queries and mutations — the connection is long-lived, not per-request. A DataLoader instance inside a subscription must be scoped carefully to avoid stale cache across multiple subscription events:

```typescript
// WRONG: single DataLoader for the entire subscription lifecycle
// The cache from event 1 bleeds into event 2:
@Subscription(() => Loan)
async loanUpdated(@Context() ctx: AppContext) {
    // ctx.loaders.user is created once per WS connection — stale cache after first event
    return this.pubSub.asyncIterator('LOAN_UPDATED');
}

// RIGHT: create a fresh DataLoader per subscription event:
@Subscription(() => LoanUpdatePayload)
async loanUpdated() {
    return {
        [Symbol.asyncIterator]: async function* () {
            for await (const event of pubSub.asyncIterator('LOAN_UPDATED')) {
                // Create fresh loaders per-event to avoid cross-event cache pollution:
                const loaders = {
                    user: createUserLoader(userRepo),
                    document: createDocumentLoader(documentRepo),
                };

                // Resolve nested fields using fresh loaders:
                const enriched = {
                    ...event,
                    _loaders: loaders,  // pass to @ResolveField via context
                };

                yield enriched;
            }
        },
    };
}

// Alternative: disable DataLoader cache for subscriptions entirely
// (batching still works; only memoization disabled):
function createSubscriptionUserLoader(userRepo: UserRepository) {
    return new DataLoader<string, User>(batchFn(userRepo), {
        cache: false,  // no memoization — each event always hits DB/Redis
    });
}
```

**Q16. How do you implement a priming strategy to pre-populate DataLoader cache from a parent resolver?**
A: Priming lets you populate the DataLoader cache from data you've already fetched — avoiding a second batch entirely. When you load a list and already have the objects, prime the cache so nested resolvers find them immediately:

```typescript
// Without priming:
// Query.loans fetches [L1, L2, L3] with borrower data included (JOIN)
// Loan.borrower resolver calls userLoader.load(borrowerId) anyway → extra batch

// With priming:
@Query(() => [Loan])
async loans(@Context() ctx: AppContext): Promise<Loan[]> {
    // Fetch loans with borrowers in a JOIN:
    const loansWithBorrowers = await this.loanRepo.findAllWithBorrower();

    // Prime the user loader cache with already-fetched data:
    for (const loan of loansWithBorrowers) {
        if (loan.borrower) {
            // prime(key, value) — sets the cache entry without a DB call:
            ctx.loaders.user.prime(loan.borrowerId, loan.borrower);
        }
    }

    return loansWithBorrowers;
}

// Now when Loan.borrower resolver fires:
@ResolveField(() => User)
async borrower(@Parent() loan: Loan, @Context() ctx: AppContext): Promise<User> {
    return ctx.loaders.user.load(loan.borrowerId);
    // Cache hit — returns primed value immediately, no DB call
}

// Bulk prime after a findAll:
@Query(() => [User])
async users(@Context() ctx: AppContext): Promise<User[]> {
    const users = await this.userRepo.findAll();
    // Prime all returned users:
    users.forEach(user => ctx.loaders.user.prime(user.id, user));
    return users;
}

// Prime with a Promise (useful when you have an async value incoming):
ctx.loaders.user.prime('u1', Promise.resolve(partialUserData));

// Clear a primed value to force re-fetch:
ctx.loaders.user.clear('u1');
const fresh = await ctx.loaders.user.load('u1');  // now hits DB
```

**Q17. "You inherit a NestJS GraphQL API. A query that returns 50 loans with nested borrower and documents fields takes 4 seconds and fires 150 SQL queries. Walk through your diagnosis and fix."**
A: Methodical diagnosis followed by targeted DataLoader introduction:

```typescript
// Step 1: Confirm N+1 with query logging
// In TypeORM: enable logging in ormconfig
// { logging: true } or { logging: ['query'] }
// Count SELECT statements in the log for one GraphQL request

// Step 2: Identify which resolvers are the culprits:
// 50 loans → Loan.borrower fires 50 times → 50 user queries (1 + 50 = 51)
//          → Loan.documents fires 50 times → 50 document queries (+ 50 = 101)
//          → Document.uploadedBy fires ~50 times → another 50 user queries (+ 50 = 151)
//            ← total: 151 queries (close to the reported 150)

// Step 3: Check if borrower and uploadedBy share a UserLoader:
// If not: two separate DataLoaders, but they can share the same batch function

// Fix — introduce DataLoaders in GraphQL context:
// context factory in AppModule:
context: ({ req }) => ({
    req,
    loaders: {

}),

}
```

**Q18. "A DataLoader in your application is returning stale data. A user updates their profile, but the same request's subsequent GraphQL field still shows the old data. How do you fix this without disabling the cache entirely?"**

```typescript
// Root cause: DataLoader per-request cache memoizes the FIRST load result
// Mutation updated the DB but the in-memory Promise still holds old data

// Fix 1: clear() the specific key after mutation:
@Mutation(() => User)
async updateUserProfile(
    @Args('input') input: UpdateProfileInput,
    @Context() ctx: AppContext,
): Promise<User> {
    const updated = await this.userService.update(input.id, input);

    // Invalidate DataLoader cache for this key:
    ctx.loaders.user.clear(input.id);

    // Next load() for this key will re-fetch from DB:
    return ctx.loaders.user.load(input.id);
}

// Fix 2: prime() the cache with the fresh value (avoids extra DB round-trip):
@Mutation(() => User)
async updateUserProfile(
    @Args('input') input: UpdateProfileInput,
    @Context() ctx: AppContext,
): Promise<User> {
    const updated = await this.userService.update(input.id, input);

    // Replace cached value with the updated entity directly:
    ctx.loaders.user.clear(input.id).prime(input.id, updated);
    // clear() + prime() is the pattern — prime() alone won't overwrite existing cache

    return updated;
}

// Fix 3: clearAll() if the mutation affects multiple keys:
@Mutation(() => [User])
async bulkUpdateUsers(@Args('inputs') inputs: UpdateProfileInput[], @Context() ctx: AppContext) {
    const updated = await this.userService.bulkUpdate(inputs);
    ctx.loaders.user.clearAll();  // wipe entire cache — next loads re-fetch
    return updated;
}

// Fix 4: disable cache on loaders that sit behind mutable data:
// (loses memoization but keeps batching)
const mutableUserLoader = new DataLoader(batchFn, { cache: false });
```

**Q19. "You're building a multi-tenant GraphQL API. How do you ensure DataLoader doesn't leak tenant A's cached data to tenant B?"**

```typescript
// The guarantee: DataLoader instance must never outlive a single request
// If the instance is request-scoped, tenant isolation is automatic

// Risk pattern — module-level or singleton DataLoader:
@Injectable()
export class UserService {
    private static sharedLoader = new DataLoader(batchFn);  // BUG: shared across tenants
}

// Safe pattern 1: GraphQL context factory (creates per-request loaders):
GraphQLModule.forRootAsync({
    useFactory: (loaderFactory: DataLoaderFactory) => ({
        context: ({ req }) => ({
            tenantId: req.user?.tenantId,   // extracted from JWT
            loaders: loaderFactory.create(req.user?.tenantId),
        }),
    }),
});

// Safe pattern 2: Tenant-scoped batch function (even if loader is shared, SQL is isolated):
// This is defense-in-depth — still prefer per-request instances:
function createTenantAwareUserLoader(tenantId: string, userRepo: UserRepository) {
    return new DataLoader<string, User>(async (userIds: readonly string[]) => {
        // Query is scoped to tenantId — even if loader leaked, wrong-tenant
        // IDs would return empty results not another tenant's data:
        const users = await userRepo.findByIdsAndTenant([...userIds], tenantId);
        const map = new Map(users.map(u => [u.id, u]));
        return userIds.map(id => map.get(id) ?? new Error(`Not found: ${id}`));
    });
}

// Safe pattern 3: Request-scoped NestJS provider (Scope.REQUEST):
@Injectable({ scope: Scope.REQUEST })
export class UserLoaderFactory {
    constructor(
        private userRepo: UserRepository,
        @Inject(REQUEST) private request: Request,
    ) {}

    create(): DataLoader<string, User> {
        const tenantId = this.request['user']?.tenantId;
        // New instance per request + tenant-scoped query = double isolation
        return new DataLoader(async (ids: readonly string[]) => {
            const users = await this.userRepo.findByIdsAndTenant([...ids], tenantId);
            const map = new Map(users.map(u => [u.id, u]));
            return [...ids].map(id => map.get(id) ?? new Error('Not found'));
        });
    }
}
```

**Q20. "You need to implement DataLoader for a third-party REST API that has a bulk endpoint (POST /users/bulk with a JSON body of IDs) and rate-limits you to 10 requests/second. Design the loader."**

```typescript
import DataLoader from 'dataloader';
import Bottleneck from 'bottleneck';  // rate limiter library

// Rate limiter: max 10 API calls per second:
const limiter = new Bottleneck({
    reservoir: 10,             // start with 10 tokens
    reservoirRefreshAmount: 10,// refill to 10 every interval
    reservoirRefreshInterval: 1000,  // refill every 1000ms
    maxConcurrent: 5,          // max 5 concurrent in-flight requests
});

// Bulk API call with rate limiting:
async function fetchUsersFromApi(ids: string[]): Promise<Map<string, ExternalUser>> {
    const response = await limiter.schedule(() =>
        fetch('https://api.partner.com/users/bulk', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${API_KEY}` },
            body: JSON.stringify({ ids }),
        }).then(res => res.json())
    );

    return new Map(response.users.map((u: ExternalUser) => [u.id, u]));
}

// DataLoader with maxBatchSize to respect API's own batch limit (e.g., 100 IDs):
export function createExternalUserLoader(): DataLoader<string, ExternalUser> {
    return new DataLoader<string, ExternalUser>(
        async (ids: readonly string[]) => {
            // ids.length ≤ maxBatchSize (100) due to DataLoader splitting
            try {
                const userMap = await fetchUsersFromApi([...ids]);
                return ids.map(
                    id => userMap.get(id) ?? new Error(`External user not found: ${id}`)
                );
            } catch (err) {
                // Network / API error — fail all keys in this batch:
                return ids.map(() => new Error(`External API error: ${err.message}`));
            }
        },
        {
            maxBatchSize: 100,     // respect API's bulk endpoint limit
            cache: true,           // memoize within request — same ID requested twice = 1 call
            // Wider batch window to accumulate more IDs before flushing:
            batchScheduleFn: (callback) => setTimeout(callback, 10),
        },
    );
}

// Usage in resolver — transparent to the caller:
@ResolveField(() => ExternalUser)
async kycProfile(@Parent() loan: Loan, @Context() ctx: AppContext): Promise<ExternalUser> {
    return ctx.loaders.externalUser.load(loan.borrowerPan);
}

// With 250 loans resolving kycProfile:
// DataLoader splits into 3 batches: 100, 100, 50
// Bottleneck rate-limits API calls to ≤10/second
// Total API calls: 3 (vs 250 without DataLoader) — within rate limit
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| N+1 problem | 1 query for list + N queries for nested field = N+1 total |
| DataLoader batching | Defers loads to next tick, collects all keys, calls batchFn once |
| DataLoader caching | Per-instance Map from key → Promise; scoped to loader lifetime |
| Instance scope | Must be per-request — never singleton (data isolation) |
| Batch function contract | Must return array of same length and order as input keys array |
| Missing key | Return `new Error(...)` not `null` — `null` is cached; Error is not |
| One-to-one loader | `batchFn` returns `(K → V)[]` |
| One-to-many loader | `batchFn` returns `(K → V[])[]`; missing keys return `[]` not Error |
| Composite key | Serialize to string; use `cacheKeyFn` option |
| `clear(key)` | Remove one key from cache — forces re-fetch on next `load()` |
| `clearAll()` | Wipe entire cache |
| `prime(key, value)` | Pre-populate cache — use after `clear()` to replace stale entry |
| `maxBatchSize` | Splits large batches; useful for DB param limits or API rate limits |
| `cache: false` | Keeps batching but disables memoization — good for mutation resolvers |
| Priming | Populate cache from already-fetched parent data to prevent extra batch |

| Pattern | When to use |
|---|---|
| Per-request context factory | Standard NestJS GraphQL setup — loaders created in `context:` option |
| `Scope.REQUEST` provider | When loaders need injected services (repos, Redis) |
| `clear()` + `prime()` after mutation | Replace stale cache with updated entity |
| `cache: false` on loader | Subscription resolvers, mutation contexts where freshness matters |
| Two-tier (Redis → DB) loader | High-traffic fields; batch Redis MGET then DB for misses |
| Priming from parent query | When parent resolver already has child data via JOIN |
| `maxBatchSize` + rate limiter | External API calls with per-request limits |

---

**Tip for interviews:** Five things separate strong candidates on DataLoader: (1) being precise about **instance scoping** (Q4, Q19) — not just saying "create per request" but explaining *why* (cache isolation between tenants/users) and *how* (GraphQL context factory or `Scope.REQUEST` provider); (2) knowing the **batch function contract** precisely (Q3) — results must be same length and same order as input keys, missing keys must return `Error` not `null` (null is cached and the caller silently gets null forever; Error rejects the Promise and allows retry); (3) distinguishing **one-to-one vs one-to-many loaders** (Q5) — one-to-many initializes the result map with empty arrays for all input keys so missing keys return `[]` not an Error; (4) knowing the **three cache manipulation methods** and when to use each (Q8, Q18) — `clear(key)` to invalidate after a mutation, `prime(key, value)` to pre-populate from already-fetched data, `clearAll()` for bulk mutations; and (5) explaining **why async work before `load()` breaks batching** (Q9) — resolvers that `await` something before calling `load()` yield the event loop, potentially missing the batch window, so the correct pattern is to call `load()` first (queuing the key) and then do async work while the Promise is pending.
