# GraphQL: Schema-First vs Code-First — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is GraphQL and what problems does it solve over REST?**
A: GraphQL is a query language for APIs and a runtime for executing those queries. Rather than exposing a fixed set of URL endpoints that return fixed data shapes, GraphQL exposes a single endpoint where the client declares exactly what data it needs and receives exactly that — no more, no less.

```
REST — server decides the response shape:

  GET /users/42
  Response: { id, name, email, address, createdAt, role, preferences, ... }
  ← Client wanted only id and name — overfetching

  GET /orders?userId=42
  GET /products?ids=1,2,3     ← separate round trips for related data
  ← Underfetching — one page needs 3 requests

GraphQL — client declares the response shape:

  POST /graphql
  Query:
    {
      user(id: "42") {
        id
        name
        orders {
          id
          total
          items { product { name price } }
        }
      }
    }
  Response: exactly this shape, nothing more
  ← One request, no overfetch, no underfetch
```

```
Core GraphQL concepts:

Schema:
  The contract between server and client. Defines every type,
  field, query, mutation, and subscription the API exposes.
  Written in SDL (Schema Definition Language) or generated from code.

Resolvers:
  Functions that return data for each field in the schema.
  A resolver receives (parent, args, context, info) and returns
  the field's value — from a DB, cache, or another service.

Operations:
  Query     — read data (like GET)
  Mutation  — write data (like POST/PUT/DELETE)
  Subscription — real-time updates over WebSocket

Types:
  Scalar:  String, Int, Float, Boolean, ID
  Object:  { field: Type, ... }
  Input:   Like Object but used for mutation arguments
  Enum:    A fixed set of string values
  Union:   Result is one of several types
  Interface: Shared fields across multiple types
```

**Q2. What is the Schema Definition Language (SDL) and why does it matter regardless of which approach you choose?**
A: SDL is the human-readable text format for writing GraphQL schemas. It is transport-agnostic, language-agnostic, and serves as the canonical source of truth that all GraphQL tools understand:

```graphql
# SDL — the lingua franca of GraphQL

# Scalar types (built-in):
# String, Int, Float, Boolean, ID

# Custom scalar:
scalar DateTime
scalar JSON

# Enum:
enum OrderStatus {
  PENDING
  CONFIRMED
  SHIPPED
  DELIVERED
  CANCELLED
}

# Interface — shared fields:
interface Node {
  id: ID!           # ! = non-null (required)
}

# Object type:
type User implements Node {
  id: ID!
  email: String!
  name: String!
  createdAt: DateTime!
  orders: [Order!]!  # Non-null list of non-null Orders
  role: UserRole!
}

# Input type — for mutations:
input CreateOrderInput {
  items: [OrderItemInput!]!
  shippingAddressId: ID!
}

input OrderItemInput {
  productId: ID!
  quantity: Int!
}

# Union — resolver returns one of these types:
union SearchResult = User | Product | Order

# Root types — entry points:
type Query {
  user(id: ID!): User          # Returns null if not found
  users(limit: Int, offset: Int): [User!]!
  searchAll(query: String!): [SearchResult!]!
}

type Mutation {
  createOrder(input: CreateOrderInput!): Order!
  cancelOrder(id: ID!): Order!
}

type Subscription {
  orderStatusChanged(orderId: ID!): Order!
}
```

```
Why SDL matters regardless of approach:

Schema-first: SDL IS your source code — you write it directly.

Code-first:   SDL is GENERATED from your decorators/code.
              You never write SDL by hand, but the output is still SDL.
              Tools (Apollo Studio, GraphQL Inspector, clients) all read SDL.
              The generated SDL is what you commit and version.

In both cases:
  - Introspection: clients query __schema to see available types/fields
  - Codegen: tools generate TypeScript types from the SDL
  - Federation: Apollo Federation stitches schemas using SDL
  - Documentation: GraphiQL / GraphQL Playground renders SDL as docs
```

**Q3. What is the fundamental difference between schema-first and code-first, and what is the tradeoff in one sentence?**
A: In schema-first, the SDL file is the source of truth and TypeScript types are generated from it; in code-first, TypeScript classes/decorators are the source of truth and SDL is generated from them. The tradeoff: schema-first gives SDL clarity and tooling compatibility at the cost of synchronisation overhead; code-first gives TypeScript type-safety and colocation at the cost of less readable schema definitions.

```
Schema-first flow:

  schema.graphql ──► TypeScript types (generated by graphql-codegen)
       ↑                      ↓
  (you write this)     (you use these in resolvers)
  Source of truth      Derived artefact


Code-first flow:

  TypeScript classes/decorators ──► schema.graphql (generated by NestJS/type-graphql)
            ↑                              ↓
  (you write this)               (derived artefact — commit for tooling)
  Source of truth                SDL output


Key question when choosing:
  "Do I want to design the API in GraphQL SDL and then implement it?
   Or do I want to write TypeScript and have the schema fall out of it?"

  Team writes SDL fluently, API-design-first culture → schema-first
  TypeScript-heavy codebase, backend-driven API, NestJS ecosystem → code-first
```

## Section 2: Schema-First in Depth

**Q4. How do you implement schema-first GraphQL in a NestJS application?**
A: Schema-first in NestJS uses the `typePaths` or `typeDefs` option to load SDL files, then you write resolver classes that implement the handlers declared in the schema:

```typescript
// Installation:
// npm install @nestjs/graphql @apollo/server graphql

// app.module.ts
import { GraphQLModule } from '@nestjs/graphql';
import { ApolloDriver, ApolloDriverConfig } from '@nestjs/apollo';
import { join } from 'path';

@Module({
    imports: [
        GraphQLModule.forRoot<ApolloDriverConfig>({
            driver: ApolloDriver,

            // Schema-first: load SDL files
            typePaths: ['./**/*.graphql'],      // Glob — all .graphql files in src/
            // or:
            typePaths: [join(process.cwd(), 'src/**/*.graphql')],

            // Generate TypeScript types from the SDL (run separately):
            // definitions: {
            //   path: join(process.cwd(), 'src/graphql.ts'),
            //   outputAs: 'class',    // 'class' | 'interface'
            // },

            context: ({ req }) => ({ req }),    // Attach request to context
            playground: process.env.NODE_ENV !== 'production',
            introspection: process.env.NODE_ENV !== 'production',
        }),
    ],
})
export class AppModule {}
```

```graphql
# src/order/order.graphql — the SDL file you write by hand

type Order {
  id: ID!
  status: OrderStatus!
  total: Float!
  items: [OrderItem!]!
  user: User!
  createdAt: DateTime!
}

type OrderItem {
  id: ID!

  PENDING
  CONFIRMED
  SHIPPED
  DELIVERED
  CANCELLED
```

```typescript
// src/order/order.resolver.ts — implements the SDL declarations
import { Resolver, Query, Mutation, Args, ResolveField, Parent, Context } from '@nestjs/graphql';
import { OrderService } from './order.service';
import { UserService } from '../user/user.service';

// In schema-first, TypeScript types come from graphql-codegen output:
import { Order, CreateOrderInput, OrderStatus, QueryOrderArgs } from '../graphql';
// ↑ These are GENERATED from the SDL — you don't write them manually

@Resolver('Order')   // ← String in schema-first (matches SDL type name)
export class OrderResolver {
    constructor(
        private orderService: OrderService,
        private userService: UserService,
    ) {}

    // Matches: order(id: ID!): Order in SDL
    @Query('order')                            // ← String matching SDL Query field
    async getOrder(@Args('id') id: string): Promise<Order | null> {
        return this.orderService.findById(id);
    }

    @Query('myOrders')
    async getMyOrders(
        @Args('status') status: OrderStatus,
        @Context() ctx: { req: { user: { sub: string } } }
    ): Promise<Order[]> {
        return this.orderService.findByUser(ctx.req.user.sub, status);
    }

    @Mutation('createOrder')
    async createOrder(
        @Args('input') input: CreateOrderInput,
        @Context() ctx: { req: { user: { sub: string } } }
    ): Promise<Order> {
        return this.orderService.create(ctx.req.user.sub, input);
    }

    @Mutation('cancelOrder')
    async cancelOrder(@Args('id') id: string): Promise<Order> {
        return this.orderService.cancel(id);
    }

    // Field resolver — resolves Order.user (the nested User type)
    @ResolveField('user')
    async resolveUser(@Parent() order: Order): Promise<User> {
        return this.userService.findById(order.userId);
    }

    @ResolveField('items')
    async resolveItems(@Parent() order: Order): Promise<OrderItem[]> {
        return this.orderService.getItems(order.id);
    }
}
```

**Q5. What is the schema-first development workflow and what are its advantages?**
A: Schema-first treats the SDL file as an API contract that can be designed, reviewed, and agreed upon before any implementation begins:

```
Schema-first workflow:

  1. Design session (SDL):
     Backend + frontend engineers + product together:
     "We need these fields, this query, this mutation"
     → Write / update the .graphql SDL file
     → PR review: "should status be an enum or a string?"

  2. Frontend starts immediately:
     Frontend runs graphql-codegen against the SDL → TypeScript types + hooks
     Mocks the schema locally (Apollo MockedProvider or msw-graphql)
     Builds UI components against the agreed types
     → Zero waiting for backend

  3. Backend implements:
     graphql-codegen generates TypeScript resolver interfaces from SDL
     Backend implements the resolver interfaces
     TypeScript compiler enforces: "you haven't implemented mutation.cancelOrder"

  4. Validate alignment:
     graphql-inspector diff old-schema.graphql new-schema.graphql
     → Lists breaking changes before merge (removed fields, changed types)
     Integration tests run against the combined schema

  5. Breaking change management:
     SDL diff in CI pipeline flags: "field User.address removed — breaking"
     → Requires explicit deprecation cycle or major version
```

```typescript
// The generated resolver interface (from graphql-codegen typescript-resolvers):
// Ensures your resolver implements every field in the schema:

export type Resolvers = {
    Query: {
        order: Resolver<Maybe<Order>, {}, Context, QueryOrderArgs>;
        myOrders: Resolver<Order[], {}, Context, QueryMyOrdersArgs>;
    };
    Mutation: {
        createOrder: Resolver<Order, {}, Context, MutationCreateOrderArgs>;
        cancelOrder: Resolver<Order, {}, Context, MutationCancelOrderArgs>;
    };
    Order: {
        id: Resolver<string, Order, Context>;
        status: Resolver<OrderStatus, Order, Context>;
        user: Resolver<User, Order, Context>;   // ← must implement field resolver
        items: Resolver<OrderItem[], Order, Context>;
    };
    // ... all other types
};

// If your resolver is missing a field, TypeScript tells you at compile time.
// You cannot accidentally leave a schema field without an implementation.
```

```
Advantages of schema-first:

  API design independence:
    SDL files can be written by anyone — product, tech lead, architect.
    Frontend teams can contribute to API design without writing TypeScript.
    The schema is the documentation — readable without code context.

  Parallel development:
    Frontend + backend work simultaneously after the SDL is agreed.
    Mock servers, storybook fixtures, and tests all use the same SDL.

  Tooling compatibility:
    Every GraphQL tool reads SDL natively:
    Apollo Studio, GraphQL Inspector, Rover CLI, GraphQL Voyager,
    Postman, Insomnia — zero configuration needed.

  Explicit contract:
    Changing the API requires changing the SDL — highly visible PR diff.
    "Did we break any clients?" is answerable by diff alone.

  Schema stitching / federation:
    Apollo Federation subgraph schemas are written in SDL.
    Schema-first maps naturally to the federation model.
```

## Section 3: Code-First in Depth

**Q6. How do you implement code-first GraphQL in a NestJS application?**
A: Code-first uses TypeScript classes decorated with `@ObjectType`, `@Field`, `@Resolver`, `@Query`, and `@Mutation`. NestJS generates the SDL at startup. The `autoSchemaFile` option writes the generated SDL to disk:

```typescript
// app.module.ts
@Module({
    imports: [
        GraphQLModule.forRoot<ApolloDriverConfig>({
            driver: ApolloDriver,

            // Code-first: generate SDL from decorators
            autoSchemaFile: join(process.cwd(), 'src/schema.gql'),
            // or: autoSchemaFile: true  (in-memory only, not written to disk)

            sortSchema: true,       // Alphabetical output — deterministic diffs
            context: ({ req }) => ({ req }),
        }),
    ],
})
export class AppModule {}
```

```typescript
// src/order/order.model.ts — GraphQL type definition
import { ObjectType, Field, ID, Float, registerEnumType } from '@nestjs/graphql';
import { User } from '../user/user.model';
import { Product } from '../product/product.model';

export enum OrderStatus {
    PENDING    = 'PENDING',
    CONFIRMED  = 'CONFIRMED',
    SHIPPED    = 'SHIPPED',
    DELIVERED  = 'DELIVERED',
    CANCELLED  = 'CANCELLED',
}

// Registers enum in the GraphQL schema:
registerEnumType(OrderStatus, {
    name: 'OrderStatus',
    description: 'The current fulfilment status of an order',
    valuesMap: {
        PENDING:   { description: 'Order received, awaiting payment confirmation' },
        CANCELLED: { description: 'Order cancelled by customer or system' },
    },
});

@ObjectType({ description: 'A customer order' })
export class Order {
    @Field(() => ID)
    id: string;

    @Field(() => OrderStatus)
    status: OrderStatus;

    @Field(() => Float)
    total: number;

    @Field(() => [OrderItem])
    items: OrderItem[];

    @Field(() => User)
    user: User;

    @Field()
    createdAt: Date;   // Date is mapped to DateTime scalar automatically

    // NOT a GraphQL field — internal only (not decorated):
    userId: string;    // Used by ResolveField to load user — not exposed
}

@ObjectType()
export class OrderItem {
    @Field(() => ID)
    id: string;

    @Field(() => Int)
    quantity: number;

    @Field(() => Float)
    unitPrice: number;

    @Field(() => Product)
    product: Product;
}
```

```typescript
// src/order/order.input.ts — Input types for mutations
import { InputType, Field, ID, Int } from '@nestjs/graphql';
import { IsUUID, IsInt, Min, ArrayMinSize, ValidateNested } from 'class-validator';
import { Type } from 'class-transformer';

@InputType()
export class OrderItemInput {
    @Field(() => ID)
    @IsUUID()
    productId: string;

    @Field(() => Int)
    @IsInt()
    @Min(1)
    quantity: number;
}

@InputType()
export class CreateOrderInput {
    @Field(() => [OrderItemInput])
    @ArrayMinSize(1)
    @ValidateNested({ each: true })
    @Type(() => OrderItemInput)
    items: OrderItemInput[];

    @Field(() => ID)
    @IsUUID()
    shippingAddressId: string;
}
```

```typescript
// src/order/order.resolver.ts — Resolver with full DI
import {
    Resolver, Query, Mutation, Args, ResolveField,
    Parent, Context, ID, Int
} from '@nestjs/graphql';
import { UseGuards } from '@nestjs/common';
import { Order } from './order.model';
import { CreateOrderInput } from './order.input';
import { OrderService } from './order.service';
import { UserService } from '../user/user.service';
import { JwtAuthGuard } from '../auth/jwt-auth.guard';
import { CurrentUser } from '../auth/current-user.decorator';
import { JwtPayload } from '../auth/jwt-auth.guard';

@Resolver(() => Order)   // ← Pass the class, not a string (code-first difference)
@UseGuards(JwtAuthGuard)
export class OrderResolver {
    constructor(
        private orderService: OrderService,
        private userService: UserService,
    ) {}

    @Query(() => Order, { nullable: true, description: 'Fetch a single order by ID' })
    async order(
        @Args('id', { type: () => ID }) id: string
    ): Promise<Order | null> {
        return this.orderService.findById(id);
    }

    @Query(() => [Order], { description: 'Fetch orders for the authenticated user' })
    async myOrders(
        @Args('status', { type: () => OrderStatus, nullable: true }) status: OrderStatus,
        @CurrentUser() user: JwtPayload
    ): Promise<Order[]> {
        return this.orderService.findByUser(user.sub, status);
    }

    @Mutation(() => Order)
    async createOrder(
        @Args('input') input: CreateOrderInput,
        @CurrentUser() user: JwtPayload
    ): Promise<Order> {
        return this.orderService.create(user.sub, input);
    }

    @Mutation(() => Order)
    async cancelOrder(
        @Args('id', { type: () => ID }) id: string
    ): Promise<Order> {
        return this.orderService.cancel(id);
    }

    // Field resolvers — run when the field is requested:
    @ResolveField(() => User)
    async user(@Parent() order: Order): Promise<User> {
        // order.userId exists on the DB entity but not exposed in GraphQL schema
        return this.userService.findById(order.userId);
    }

    @ResolveField(() => [OrderItem])
    async items(@Parent() order: Order): Promise<OrderItem[]> {
        return this.orderService.getItems(order.id);
    }
}
```

**Q7. What are the TypeScript-specific advantages of code-first, and how does it handle complex type scenarios?**
A: Code-first's primary advantage is that the GraphQL type system and the TypeScript type system stay in sync automatically. There is no intermediate codegen step where they can diverge:

```typescript
// Generics — reuse pagination wrapper across types:
import { Type } from '@nestjs/common';
import { ObjectType, Field, Int } from '@nestjs/graphql';

// Generic pagination type — used with different entity types:
export function Paginated<T>(classRef: Type<T>) {
    @ObjectType({ isAbstract: true })
    abstract class PaginatedType {
        @Field(() => [classRef])
        nodes: T[];

        @Field(() => Int)
        totalCount: number;

        @Field()
        hasNextPage: boolean;

        @Field({ nullable: true })
        endCursor?: string;
    }
    return PaginatedType;
}

// Concrete paginated types — generate their own SDL entries:
@ObjectType()
export class PaginatedOrders extends Paginated(Order) {}

@ObjectType()
export class PaginatedUsers extends Paginated(User) {}

// Usage in resolver:
@Query(() => PaginatedOrders)
async orders(
    @Args('first', { type: () => Int, defaultValue: 20 }) first: number,
    @Args('after', { nullable: true }) after?: string,
): Promise<PaginatedOrders> {
    return this.orderService.findPaginated({ first, after });
}
```

```typescript
// Unions — when a field can return one of several types:
import { createUnionType } from '@nestjs/graphql';
import { User } from './user.model';
import { Product } from './product.model';
import { Order } from './order.model';

export const SearchResult = createUnionType({
    name: 'SearchResult',
    types: () => [User, Product, Order] as const,
    resolveType(value) {
        // Discriminate at runtime — which type does this object represent?
        if ('email' in value) return User;
        if ('price' in value) return Product;
        if ('total' in value) return Order;
        return null;
    },
});

@Query(() => [SearchResult])
async search(@Args('query') query: string): Promise<Array<typeof SearchResult>> {
    return this.searchService.searchAll(query);
}
```

```typescript
// Interfaces — shared fields, multiple implementations:
import { InterfaceType, Field, ID } from '@nestjs/graphql';

@InterfaceType()
export abstract class Node {
    @Field(() => ID)
    id: string;
}

@InterfaceType()
export abstract class Timestamped {
    @Field()
    createdAt: Date;

    @Field()
    updatedAt: Date;
}

@ObjectType({ implements: [Node, Timestamped] })
export class Order extends Timestamped implements Node {
    @Field(() => ID)
    id: string;

    @Field()
    createdAt: Date;

    @Field()
    updatedAt: Date;

    @Field(() => OrderStatus)
    status: OrderStatus;
    // ...
}

// Resolver for abstract interface type — resolveType needed:
@Resolver(() => Node)
export class NodeResolver {
    @ResolveField()
    __resolveType(obj: any): string {
        if (obj instanceof Order) return 'Order';
        if (obj instanceof User) return 'User';
        return 'Unknown';
    }
}
```

```typescript
// Custom scalars — DateTime, JSON, UUID:
import { Scalar, CustomScalar } from '@nestjs/graphql';
import { Kind, ValueNode } from 'graphql';

@Scalar('DateTime', () => Date)
export class DateTimeScalar implements CustomScalar<string, Date> {
    description = 'ISO 8601 date-time string';

    // From client input → internal value:
    parseValue(value: string): Date {
        return new Date(value);
    }

    // From internal value → JSON response:
    serialize(value: Date): string {
        return value instanceof Date
            ? value.toISOString()
            : new Date(value).toISOString();
    }

    // From query literal (inline in query string):
    parseLiteral(ast: ValueNode): Date {
        if (ast.kind === Kind.STRING) return new Date(ast.value);
        throw new Error('DateTime must be a string');
    }
}

// Register in module:
@Module({
    providers: [DateTimeScalar, OrderResolver],
})
```

## Section 4: Resolvers in Depth

**Q8. How does the resolver execution model work — parent, args, context, info?**
A: Every resolver function receives four arguments. Understanding them is essential because incorrect use (especially of `info`) is a common source of performance problems and bugs:

```typescript
// The four resolver arguments:
type ResolverFn<TResult, TParent, TContext, TArgs> = (
    parent:  TParent,   // Return value of the parent field's resolver
    args:    TArgs,     // Arguments passed to this field in the query
    context: TContext,  // Shared across ALL resolvers in one request
    info:    GraphQLResolveInfo  // Query AST, field path, schema — rarely needed
) => TResult | Promise<TResult>;
```

```typescript
// parent — the resolved value of the containing object:
@Resolver(() => Order)
export class OrderResolver {
    // Query.order resolver — parent is the root Query object (usually {})
    @Query(() => Order, { nullable: true })
    async order(@Args('id') id: string): Promise<Order | null> {
        // parent is {} — not used (root query has no parent)
        return this.orderService.findById(id);
    }

    // Order.user field resolver — parent is the Order object returned above:
    @ResolveField(() => User)
    async user(
        @Parent() order: Order   // ← the Order returned by Query.order above
    ): Promise<User> {
        // order.userId is available — set on the DB entity
        return this.userService.findById(order.userId);
    }

    // Order.items field resolver — same pattern:
    @ResolveField(() => [OrderItem])
    async items(@Parent() order: Order): Promise<OrderItem[]> {
        return this.orderService.getItems(order.id);
    }
}
```

```typescript
// context — injected once per request, shared across all resolvers:
// This is where request-scoped data lives: current user, DataLoader instances,
// database transaction, request ID, etc.

// Define the context type:
export interface GraphQLContext {
    req: Request;
    user?: JwtPayload;              // Set by auth middleware/guard
    loaders: DataLoaderRegistry;   // DataLoader instances (see Q10)
    requestId: string;
}

// Attach in GraphQL module setup:
GraphQLModule.forRoot({
    context: ({ req }): GraphQLContext => ({
        req,
        user: req.user,             // Set by JwtAuthGuard before GraphQL layer
        loaders: buildLoaders(),    // Fresh DataLoader per request
        requestId: req.headers['x-request-id'] as string ?? randomUUID(),
    }),
});

// Access in resolver via @Context():
@Query(() => [Order])
async myOrders(
    @Context() ctx: GraphQLContext

    return this.orderService.findByUser(ctx.user!.sub);
}

    @Parent() order: Order,
    @Context('loaders') loaders: DataLoaderRegistry
```

```typescript
// info — the GraphQL execution info (use sparingly):
import { GraphQLResolveInfo, fieldsList } from 'graphql-fields-list';

@Query(() => Order, { nullable: true })
async order(
    @Args('id') id: string,
    @Info() info: GraphQLResolveInfo
): Promise<Order | null> {
    // Inspect which fields the client actually requested:
    const requestedFields = fieldsList(info);
    // ['id', 'status', 'total'] — if client only asked for these

    // Use to avoid loading relations the client didn't ask for:
    const includeItems = requestedFields.includes('items');
    const includeUser = requestedFields.includes('user');

        includeItems,
        includeUser,
    });
    // More efficient than always loading all relations
    // But: DataLoader (Q10) is usually a better solution
}
```

**Q9. What is the N+1 problem in GraphQL and how do you solve it?**
A: The N+1 problem occurs when a list query triggers one database query per item in the list for a nested field. It's the most common GraphQL performance issue:

```
N+1 scenario — query for 10 orders with their users:

  Query:
    { myOrders { id status user { name email } } }

  Without DataLoader:
    SELECT * FROM orders WHERE user_id = 'u1'  → 10 orders
    SELECT * FROM users WHERE id = 'user-a'    ← order 1
    SELECT * FROM users WHERE id = 'user-b'    ← order 2
    SELECT * FROM users WHERE id = 'user-a'    ← order 3 (same user — duplicate query!)
    SELECT * FROM users WHERE id = 'user-c'    ← order 4
    ... 10 more queries
    Total: 11 queries (1 + N)

  With DataLoader:
    SELECT * FROM orders WHERE user_id = 'u1'  → 10 orders
    SELECT * FROM users WHERE id IN ('user-a', 'user-b', 'user-c', ...)  ← 1 batched query
    Total: 2 queries
```

```typescript
// DataLoader — batches and deduplicates loads within a single request tick:
// npm install dataloader

import DataLoader from 'dataloader';

// User DataLoader — batches individual user.load(id) calls into one query:
export function createUserLoader(userRepo: UserRepository): DataLoader<string, User> {
    return new DataLoader<string, User>(
        async (userIds: readonly string[]) => {
            // Called once per tick with ALL accumulated IDs:
            const users = await userRepo.findByIds([...userIds]);

            // CRITICAL: return array in the SAME ORDER as input keys:
            const userMap = new Map(users.map(u => [u.id, u]));
            return userIds.map(id => userMap.get(id) ?? new Error(`User ${id} not found`));
            //                                           ↑ Error per missing ID (not null)
            //                                             DataLoader expects exact length match
        },
        {
            // Deduplication: if the same ID is requested twice in one tick,
            // the batch function only sees it once and the result is shared:
            cache: true,   // default — deduplicate within a request
            // cache: false — for mutations where data changes mid-request
        }
    );
}

// Registry — one DataLoader per type per request:
export interface DataLoaderRegistry {
    user: DataLoader<string, User>;
    product: DataLoader<string, Product>;
    orderItems: DataLoader<string, OrderItem[]>;
}

export function buildLoaders(
    userRepo: UserRepository,
    productRepo: ProductRepository,
    orderItemRepo: OrderItemRepository,
): DataLoaderRegistry {
    return {
        user: createUserLoader(userRepo),
        product: createProductLoader(productRepo),
        // One-to-many: load all items for an order ID:
        orderItems: new DataLoader<string, OrderItem[]>(async (orderIds) => {
            const items = await orderItemRepo.findByOrderIds([...orderIds]);
            const itemMap = new Map<string, OrderItem[]>();
            items.forEach(item => {
                const list = itemMap.get(item.orderId) ?? [];
                list.push(item);
                itemMap.set(item.orderId, list);
            });
            return orderIds.map(id => itemMap.get(id) ?? []);
        }),
    };
}
```

```typescript
// Using DataLoaders in resolvers:
@Resolver(() => Order)
export class OrderResolver {
    @ResolveField(() => User)
    async user(
        @Parent() order: Order,
        @Context() ctx: GraphQLContext
    ): Promise<User> {
        // Instead of this.userService.findById(order.userId) — one query per order
        return ctx.loaders.user.load(order.userId);
        // DataLoader batches: if 10 orders resolve in the same tick,
        // this fires once as: WHERE id IN (id1, id2, ..., id10)
    }

    @ResolveField(() => [OrderItem])
    async items(
        @Parent() order: Order,
        @Context() ctx: GraphQLContext
    ): Promise<OrderItem[]> {
        return ctx.loaders.orderItems.load(order.id);
    }
}

// DataLoader per-request lifecycle — CRITICAL:
// DataLoaders MUST be created fresh per request (in the context factory)
// If shared across requests: cached data from one user leaks to another

// WRONG — shared DataLoader instance (security/correctness bug):
const sharedUserLoader = createUserLoader(userRepo);   // ← module-level singleton
GraphQLModule.forRoot({
    context: () => ({ loaders: { user: sharedUserLoader } })
    // sharedUserLoader caches user-1's data and returns it for ALL requests
});

// CORRECT — new DataLoader per request:
GraphQLModule.forRoot({
    context: ({ req }) => ({
        req,
        loaders: buildLoaders(userRepo, productRepo, orderItemRepo)
        // Fresh instance each request — cache is request-scoped
    }),
});
```

```typescript
// Code-first subscription:
import { Subscription, Args, ID } from '@nestjs/graphql';
import { PubSub } from 'graphql-subscriptions';
// In production: use graphql-redis-subscriptions for multi-instance support

const pubSub = new PubSub();    // In production: inject as provider

export const ORDER_STATUS_CHANGED = 'orderStatusChanged';

@Resolver(() => Order)
export class OrderResolver {
    // Subscription definition:
    @Subscription(() => Order, {
        // Filter: only send updates to subscribers watching this specific order:
        filter: (payload, variables) =>
            payload.orderStatusChanged.id === variables.orderId,

        // Transform: reshape payload before sending to client:
        resolve: (payload) => payload.orderStatusChanged,
    })
    orderStatusChanged(
        @Args('orderId', { type: () => ID }) orderId: string
    ) {
        return pubSub.asyncIterator(ORDER_STATUS_CHANGED);
    }

    // In the mutation that triggers the subscription:
    @Mutation(() => Order)
    async cancelOrder(@Args('id') id: string): Promise<Order> {
        const order = await this.orderService.cancel(id);

        // Publish the event — all subscribers with matching orderId receive this:
        await pubSub.publish(ORDER_STATUS_CHANGED, {
            orderStatusChanged: order,
        });

        return order;
    }
}
```

**Q11. How do you implement Apollo Federation with schema-first and code-first?**
A: Apollo Federation splits a monolithic GraphQL schema across multiple services (subgraphs), each owning a slice of the type graph. NestJS supports this via `@nestjs/apollo` with federation:

```typescript

    // or:
    typePaths: ['./src/**/*.graphql'],  // Schema-first
});
```

```graphql
# Schema-first federation — order subgraph:
# Uses federation directives to declare ownership and references

# Declare that this subgraph extends the User type owned by user-service:
type User @key(fields: "id") @extends {
  id: ID! @external        # Owned by user-service — @external marks it as borrowed
  orders: [Order!]!        # This subgraph adds orders to User
}

type Order @key(fields: "id") {  # @key: this field identifies the entity
  id: ID!
  status: OrderStatus!
  total: Float!
  user: User!
}

type Query {
  order(id: ID!): Order
}
```

**Q12. How do you handle errors in GraphQL — what is the difference between operational errors and unexpected errors?**
A: GraphQL always returns HTTP 200 with errors in the `errors` array. The challenge is distinguishing operational errors (expected, safe to surface) from bugs (unexpected, must be hidden in production):

```typescript
// GraphQL error response shape:
// {
//   "data": { "order": null },
//   "errors": [{
//     "message": "Order not found",
//     "locations": [{ "line": 2, "column": 3 }],
//     "path": ["order"],
//     "extensions": {
//       "code": "NOT_FOUND",
//       "statusCode": 404
//     }
//   }]
// }
```

```typescript
// Custom error classes — operational errors the client can handle:
import { ApolloError } from 'apollo-server-errors';

export class NotFoundError extends ApolloError {
    constructor(resource: string, id: string) {
        super(`${resource} with id '${id}' not found`, 'NOT_FOUND', {
            resource,
            id,
        });
        Object.defineProperty(this, 'name', { value: 'NotFoundError' });
    }
}

export class ForbiddenError extends ApolloError {
    constructor(message = 'Access denied') {
        super(message, 'FORBIDDEN');
    }
}

export class ValidationError extends ApolloError {
    constructor(message: string, fields: Record<string, string>) {
        super(message, 'VALIDATION_ERROR', { fields });
    }
}

// Throw in resolvers — automatically serialised into errors array:
@Query(() => Order, { nullable: true })
async order(@Args('id') id: string): Promise<Order> {
    const order = await this.orderService.findById(id);
    if (!order) throw new NotFoundError('Order', id);
    return order;
}
```

```typescript
// Global error formatting — hide internals in production:
GraphQLModule.forRoot({
    formatError: (error: GraphQLError) => {
        const originalError = error.originalError;

        // Operational errors — safe to expose as-is:
        if (originalError instanceof ApolloError) {
            return {
                message: error.message,
                extensions: {
                    code: originalError.extensions?.code,
                    ...originalError.extensions,
                },
                path: error.path,
                locations: error.locations,
            };
        }

        // NestJS HTTP exceptions from guards/pipes — map to GraphQL errors:
        if (originalError instanceof HttpException) {
            return {
                message: originalError.message,
                extensions: {
                    code: httpStatusToGraphQLCode(originalError.getStatus()),
                    statusCode: originalError.getStatus(),
                },
                path: error.path,
            };
        }

        // Unexpected errors (bugs) — log fully, return generic message:
        logger.error('Unexpected GraphQL error', {
            error: error.message,
            stack: originalError?.stack ?? error.stack,
            path: error.path,
        });

        return process.env.NODE_ENV === 'production'
            ? {
                message: 'Internal server error',
                extensions: { code: 'INTERNAL_SERVER_ERROR' },
                path: error.path,
            }
            : error;  // Return full error in development
    },
});

function httpStatusToGraphQLCode(status: number): string {
    const map: Record<number, string> = {
        400: 'BAD_USER_INPUT',
        401: 'UNAUTHENTICATED',
        403: 'FORBIDDEN',
        404: 'NOT_FOUND',
        429: 'RATE_LIMITED',
    };
    return map[status] ?? 'INTERNAL_SERVER_ERROR';
}
```

## Section 7: Comparison and Decision Framework

**Q14. When should you choose schema-first vs code-first — what are the deciding factors?**
A: Neither approach is universally better — the decision depends on team composition, API design culture, and existing tooling:

```
Choose SCHEMA-FIRST when:

  ✓ API design is a distinct phase with dedicated designers/architects
    SDL is the design artifact — reviewable by non-engineers

  ✓ Frontend and backend are separate teams with parallel development
    Frontend generates types from SDL without waiting for backend code
    Contract is agreed before implementation begins

  ✓ You're building a public API or developer platform
    SDL is the documentation — clear, tool-agnostic, language-agnostic

  ✓ Team includes engineers from multiple languages/stacks
    SDL is the common language — Ruby, Go, Python backends all understand it

  ✓ Apollo Federation is in your roadmap
    Federation naturally maps to SDL-first subgraph design

  ✓ GraphQL Inspector / Rover in CI pipeline
    These tools work directly on SDL files — schema-first is frictionless

Choose CODE-FIRST when:

  ✓ TypeScript-only team, backend-driven API design
    One source of truth in TypeScript — no SDL sync overhead

  ✓ NestJS is already in use — ecosystem alignment
    @nestjs/graphql code-first is deeply integrated with NestJS DI

  ✓ Rapid prototyping — schema evolves with code
    Add a @Field() and it appears in the schema automatically
    No separate codegen step, no SDL file to update

  ✓ Complex TypeScript generics / reuse patterns
    Generic types (Paginated<T>) are hard to express in SDL
    Code-first handles them naturally

  ✓ Single team owns both API design and implementation
    No need for SDL as coordination artifact

  ✓ IDE-first development (decorators, autocomplete, go-to-definition)
    Type safety and IDE navigation are first-class
```

```
Common hybrid pattern — code-first with SDL output committed:

  1. Write TypeScript classes with decorators (code-first)
  2. autoSchemaFile: 'src/schema.gql' — generates SDL on startup
  3. Commit schema.gql to version control
  4. CI diff check: if schema.gql changed, require review
  5. Frontend uses schema.gql for codegen (graphql-codegen)

  Result: code-first development experience
          + SDL visibility for reviewers and frontend
          + Schema change tracking in git history
          + No SDL file to manually maintain
```

**Q15. What are the key SDL syntax rules and how do they translate between the two approaches?**
A: Understanding the SDL-to-code-first translation lets you move between approaches and debug generated schemas:

```
SDL construct → Code-first equivalent:

  Non-null (!)
    SDL:       name: String!
    Code-first: @Field() name: string  ← TypeScript non-null implies GraphQL non-null
    Code-first: @Field({ nullable: false }) name: string  ← explicit

  Nullable
    SDL:       middleName: String
    Code-first: @Field({ nullable: true }) middleName?: string

  List (non-null items)
    SDL:       items: [OrderItem!]!
    Code-first: @Field(() => [OrderItem]) items: OrderItem[]

  List (nullable items)
    SDL:       tags: [String]
    Code-first: @Field(() => [String], { nullable: 'items' }) tags: (string | null)[]

  Default value
    SDL:       limit: Int = 20
    Code-first: @Args('limit', { defaultValue: 20 }) limit: number

  Deprecation
    SDL:       oldField: String @deprecated(reason: "Use newField instead")
    Code-first: @Field({ deprecationReason: 'Use newField instead' })
                oldField: string

  Description
    SDL:       """The total price including tax"""
               total: Float!
    Code-first: @Field({ description: 'The total price including tax' })
                total: number

  Enum value rename
    SDL:       enum Role { SUPER_ADMIN }
    Code-first: @Field(() => Role)
                registerEnumType(Role, { valuesMap: { SUPER_ADMIN: { description: '...' } } })

  Interface
    SDL:       interface Node { id: ID! }
               type Order implements Node { id: ID! ... }
    Code-first: @InterfaceType() abstract class Node { @Field(() => ID) id: string }
                @ObjectType({ implements: [Node] }) class Order extends Node { ... }
```

## Section 8: Performance and Production

**Q16. What are the performance concerns specific to GraphQL in production and how do you address them?**
A: GraphQL's flexibility introduces performance challenges not present in REST: unbounded query depth, expensive introspection, and the N+1 problem. Each requires a specific mitigation:

```typescript
// 1. Query depth limiting — prevent deeply nested queries:
// { user { orders { items { product { seller { orders { items { ... } } } } } } } }
// This could trigger thousands of DB queries

import depthLimit from 'graphql-depth-limit';

GraphQLModule.forRoot({
    validationRules: [
        depthLimit(7),   // Max 7 levels of nesting — adjust to your deepest legitimate query
    ],
});

// npm install graphql-depth-limit
```

```typescript
// 2. Query complexity — cost-based throttling:
// Flat queries on expensive types should also be limited
// A query for 1000 users × their 100 orders = 100,000 items without pagination

import { createComplexityLimitRule } from 'graphql-validation-complexity';
// or: import costAnalysis from 'graphql-cost-analysis'

GraphQLModule.forRoot({
    validationRules: [
        createComplexityLimitRule(1000, {
            // Assign complexity costs to fields:
            scalarCost: 1,       // Each scalar field costs 1
            objectCost: 2,       // Each object type costs 2
            listFactor: 10,      // Lists multiply cost by 10
        }),
        // query { users { orders { items } } }
        // = (users: 2 × 10) + (orders: 2 × 10) + (items: 1 × 10) = 110
        // Under 1000 → allowed. Query for 10 users × each field = 1100 → blocked.
    ],
});
```

```typescript
// 3. Disable introspection in production — prevent schema enumeration:
GraphQLModule.forRoot({
    introspection: process.env.NODE_ENV !== 'production',
    // In production: introspection reveals your full schema to attackers
    // Use a private schema registry (Apollo Studio) for internal documentation
    playground: process.env.NODE_ENV !== 'production',
});
```


## Quick Reference Table

| Concept | Key Idea | Common Mistake |
|---|---|---|
| SDL source of truth | Schema-first: SDL is hand-written, TS types generated from it. Code-first: TS decorators are hand-written, SDL generated from them | Manually editing the generated `schema.gql` in code-first — it's overwritten on next startup |
| `@ObjectType` vs SDL `type` | Code-first: `@ObjectType() class Order` → SDL `type Order`. Every `@Field()` becomes a field in the SDL | Forgetting `@Field()` on a property — it exists in TypeScript but is invisible to GraphQL |
| `@Resolver('Order')` vs `@Resolver(() => Order)` | Schema-first uses string matching SDL type name; code-first passes the class reference | Using a string in code-first (`@Resolver('Order')`) — works but loses type-safety and go-to-definition |
| N+1 problem | Without DataLoader: one DB query per item in a list. With DataLoader: one batched query for all items | Creating DataLoader instances in the module (singleton) instead of per request — cached data leaks between users |
| DataLoader per request | DataLoader instances MUST be created fresh in the `context` factory — they cache within a request and must not persist across requests | Sharing DataLoader instances across requests — stale or cross-user data returned |
| `nullable` vs `!` | SDL `field: Type!` = required; `field: Type` = nullable. Code-first: `@Field({ nullable: true })` = nullable; default is non-null | Forgetting `nullable: true` for optional fields — GraphQL throws if resolver returns null |
| `@ResolveField` | Runs only when the client requests that field — lazy loading. Without DataLoader: N+1. Must be in `@Resolver(() => ParentType)` class | Putting a `@ResolveField` for `Order.user` in a `@Resolver(() => User)` class instead of `@Resolver(() => Order)` |
| Subscription pubsub | In-memory `PubSub` only works in single-instance deployments. Production multi-instance requires Redis-backed pubsub (`graphql-redis-subscriptions`) | Using the default in-memory PubSub in a multi-pod deployment — subscribers on different pods never receive events |
| Error handling | GraphQL always returns HTTP 200. Operational errors go in `errors[]` with `extensions.code`. Unexpected errors must be masked in production via `formatError` | Returning HTTP 4xx/5xx status codes from GraphQL errors — clients and caches handle this incorrectly |
| Depth limiting | Without `depthLimit`, a malicious client can nest queries arbitrarily deep — potential DoS | Setting `depthLimit` too high (20+) — deeply nested queries can still cause N+1 cascades before DataLoader can batch |
| Introspection in production | `introspection: true` reveals your entire schema to unauthenticated clients — useful for attackers | Leaving `introspection: true` in production — always disable or guard behind auth |
| autoSchemaFile commit | Generated `schema.gql` should be committed to version control — enables frontend codegen, schema diff in CI, and auditing schema changes | Not committing `schema.gql` — frontend teams cannot run codegen, and schema changes are invisible in PRs |

---

**Tip for interviews:** Five things separate strong candidates on GraphQL schema-first vs code-first: (1) being able to articulate **both flows concretely** — schema-first: SDL → `graphql-codegen` → TypeScript resolver interfaces → implement them; code-first: TypeScript decorators → NestJS generates SDL at startup → commit `schema.gql` for tooling — candidates who describe only one direction miss the symmetry and the tradeoffs; (2) diagnosing and solving the **N+1 problem with DataLoader** — knowing that `@ResolveField` fires once per parent object in a list, why that's a problem without batching, how DataLoader's batch function collects all IDs in one event loop tick, and critically that DataLoader instances **must be created per-request** in the context factory or you get cross-user data leaks; (3) understanding **why GraphQL always returns HTTP 200** — that errors live in the `errors` array alongside partial `data`, that `formatError` must mask unexpected errors in production, and that `extensions.code` is the machine-readable error type that clients switch on (not the HTTP status); (4) knowing the **code-first type-safety gotchas** — that TypeScript interfaces are erased at runtime so unions and interfaces need `resolveType` functions, that `@Field()` must be explicit on every property or it won't appear in the schema, and that the `() =>` thunk in `@Field(() => [Order])` is required for circular references and arrays (not just optional syntax); and (5) being able to reason about **when the SDL approach is the right choice** — specifically that federation, public APIs, and multi-team parallel development favour schema-first because the SDL is the coordination artifact, while code-first wins when the backend team owns both design and implementation and wants TypeScript as the single source of truth without a synchronisation step.
