# Schema Stitching vs Federation — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Distributed GraphQL Fundamentals

**Q1. Why does a distributed GraphQL architecture exist — what problem does it solve?**
A: A single monolithic GraphQL schema becomes a maintenance and scaling problem as an organization grows. Every team editing one schema file creates merge conflicts, deployment coupling, and unclear ownership boundaries. A frontend developer needing a new field must coordinate with whichever team owns the relevant part of the schema.

Distributed GraphQL solves this by letting each team own a slice of the schema — their own types, resolvers, and data sources — while presenting a **single unified API** to clients. Clients never know the underlying schema is distributed; they send one query to one endpoint and receive a complete response.

```
Monolithic GraphQL (one team, one schema):
  Frontend → GraphQL Server → one codebase → { Users DB, Orders DB, Payments DB, ... }

  Problem:
    - Every team edits the same schema.graphql file
    - One broken resolver blocks all teams' deployments
    - Hard to scale teams or services independently

Distributed GraphQL (each team owns their slice):
  Frontend → Gateway/Router → Users Service   → Users DB
                            → Orders Service  → Orders DB
                            → Payments Service → Payments API

  Result:
    - Users team deploys independently
    - Orders team has complete ownership of Order type
    - Frontend still sends queries to ONE endpoint
    - Gateway/Router assembles the complete response
```

Both **schema stitching** and **federation** achieve this goal. They differ in **where** the composition logic lives — at the gateway layer (stitching) or encoded in the subgraph schemas themselves (federation).

**Q2. What is the fundamental architectural difference between schema stitching and federation?**
A: The core distinction is about **where composition is defined** and **who is responsible** for understanding the distributed nature of the schema:

```
Schema Stitching — composition at the gateway:
  ┌─────────────────────────────────────────────┐
  │              Gateway / Stitcher             │
  │  Knows about: all services + their schemas  │
  │  Owns: all type merging rules               │
  │  Holds: remote executor configs             │
  │  Requires: central configuration            │
  └────────┬─────────────────────────┬──────────┘
           │                         │
  ┌────────▼──────┐         ┌────────▼──────┐
  │  Users Service│         │ Orders Service │
  │  (plain GQL)  │         │  (plain GQL)  │
  │  No knowledge │         │  No knowledge │
  │  of stitching │         │  of stitching │
  └───────────────┘         └───────────────┘

  Services are dumb — they're just GraphQL endpoints.
  All intelligence about cross-service composition lives in the gateway.

Federation — composition in the subgraphs:
  ┌─────────────────────────────────────────────┐
  │         Apollo Router / Gateway             │
  │  Knows: how to route and plan queries       │
  │  Owns: very little business logic           │
  │  Config: minimal (just service URLs)        │
  └────────┬─────────────────────────┬──────────┘
           │                         │
  ┌────────▼──────────┐  ┌──────────▼──────────┐
  │   Users Subgraph  │  │  Orders Subgraph     │
  │  @key(fields: "id")  │  extend type User @key│
  │  Knows it's part  │  │  Extends User type   │
  │  of a federation  │  │  Knows about entities│
  └───────────────────┘  └─────────────────────┘

  Services are smart — they declare their relationships.
  Intelligence is distributed across subgraph schemas.
```

### Section 2: Schema Stitching

**Q3. What is schema stitching and how does it work mechanically?**
A: Schema stitching (via `@graphql-tools/stitch`) takes multiple GraphQL schemas — which may be remote HTTP endpoints, local schemas, or SDL strings — and merges them into a single executable schema. The stitching layer intercepts incoming queries, delegates sub-queries to the appropriate upstream service, and assembles the results.

```ts
// Conceptual stitching pipeline:
import { stitchSchemas }   from '@graphql-tools/stitch';
import { buildHTTPExecutor } from '@graphql-tools/executor-http';
import { schemaFromExecutor } from '@graphql-tools/wrap';

// Step 1: connect to remote GraphQL services
const usersExecutor  = buildHTTPExecutor({ endpoint: 'http://users-service/graphql' });
const ordersExecutor = buildHTTPExecutor({ endpoint: 'http://orders-service/graphql' });

// Step 2: introspect remote schemas (or load SDL statically)
const usersSchema  = await schemaFromExecutor(usersExecutor);
const ordersSchema = await schemaFromExecutor(ordersExecutor);

// Step 3: stitch them together with merge rules
const gatewaySchema = stitchSchemas({
  subschemas: [
    {
      schema:   usersSchema,
      executor: usersExecutor,
    },
    {
      schema:   ordersSchema,
      executor: ordersExecutor,

      // Type merging — how to resolve User fields from Orders service:
      merge: {
        User: {
          fieldName:    'user',               // the Orders query to fetch a User
          selectionSet: '{ id }',             // what Orders needs from User
          args: (user) => ({ id: user.id }), // map User.id → query argument
        },
      },
    },
  ],
});

// Step 4: expose the stitched schema via HTTP
```

Internally, stitching uses **schema delegation**: when the gateway receives a query touching multiple services, it splits it into sub-queries, delegates each to the relevant executor, and merges the results before returning to the client:

```
Client query:
  query {
    user(id: 1) {          ← from Users service
      name                 ← from Users service
      email                ← from Users service
      orders {             ← from Orders service (User type extended here)
        id
        total
      }
    }
  }

Gateway splits into:
  → Users service: query { user(id: 1) { name email } }
  → Orders service: query { ordersForUser(userId: 1) { id total } }

Gateway merges: { user: { name, email, orders: [...] } }
```

**Q4. What is "type merging" in schema stitching and why is it necessary?**
A: Type merging allows the same type (e.g., `User`) to be **defined across multiple subschemas**, with each subschema owning some of the type's fields. At query time, the stitching layer fetches from whichever subschema owns each requested field and merges the results into one coherent object.

Without type merging, types must be entirely owned by one service — if Orders needs to return `User` fields, Orders would have to re-implement user resolution or the gateway would have to do expensive manual stitching.

```ts
// Users service schema:
type User {
  id:    ID!
  name:  String!
  email: String!
}
type Query {
  user(id: ID!): User
  users: [User!]!
}

// Orders service schema:
type User {
  id:     ID!             # only id is known here
  orders: [Order!]!       # this service owns this field
}
type Order {
  id:    ID!
  total: Float!
}
type Query {
  user(id: ID!):  User   # Orders service can resolve User.orders
  order(id: ID!): Order
}

// Stitching configuration with type merging:
const gatewaySchema = stitchSchemas({
  subschemas: [
    {
      schema:   usersSchema,
      executor: usersExecutor,
      merge: {
        User: {
          selectionSet: '{ id }',               // "I can resolve User if I have id"
          fieldName:    'user',                  // call user(id:) to fetch
          args: (user) => ({ id: user.id }),
        },
      },
    },
    {
      schema:   ordersSchema,
      executor: ordersExecutor,
      merge: {
        User: {
          selectionSet: '{ id }',               // "I can resolve User.orders if I have id"
          fieldName:    'user',
          args: (user) => ({ id: user.id }),
        },
      },
    },
  ],
});

// Result: unified schema where User has name, email (from Users) + orders (from Orders)
// Merged type:
// type User {
//   id:     ID!
//   name:   String!  ← Users service
//   email:  String!  ← Users service
//   orders: [Order]! ← Orders service
// }
```

**Q5. What are schema transforms in stitching and when do you use them?**
A: Schema transforms modify a subschema's types or fields **before** they are incorporated into the stitched schema. They are used to rename conflicting types, filter out fields that shouldn't be exposed, prefix types to avoid collisions, or wrap fields with additional logic.

```ts
import {
  FilterTypes, RenameTypes, RenameRootFields, FilterRootFields,
  WrapType, PruneSchema, TransformEnumValues,
} from '@graphql-tools/wrap';

const gatewaySchema = stitchSchemas({
  subschemas: [
    {
      schema:   legacyUsersSchema,
      executor: legacyExecutor,
      transforms: [
        // Rename a type that conflicts with another subschema:
        new RenameTypes(name => name === 'Error' ? 'UsersError' : name),

        // Rename root field to match the gateway's naming convention:
        new RenameRootFields((op, name) =>
          name === 'getUser' ? 'user' : name   // getUser → user
        ),

        // Remove internal/admin queries from the public schema:
        new FilterRootFields((op, name) =>
          !name.startsWith('admin_')   // hide adminDeleteUser etc.
        ),

        // Remove internal types entirely:
        new FilterTypes(name => !['InternalConfig', 'DebugInfo'].includes(name)),
      ],
    },
  ],
});
```

### Section 3: Apollo Federation

**Q6. What is Apollo Federation and what are its core concepts?**
A: Apollo Federation is a specification — and Apollo's implementation of it — for composing multiple GraphQL services into one. Unlike stitching where the gateway owns composition, Federation encodes composition rules **within the subgraph schemas themselves** using special directives. The gateway (Apollo Router or legacy Apollo Gateway) reads these directives and constructs a query plan at runtime.

Core concepts:

```graphql
# ── Subgraph (a service that participates in federation) ──────────────
# Each subgraph is a full, standalone GraphQL service plus federation directives

# ── @key — declares an entity and its primary key ────────────────────
# An entity is a type that can be referenced and extended across subgraphs

# Users subgraph:
type User @key(fields: "id") {
  id:    ID!
  name:  String!
  email: String!
}
# @key(fields: "id") means:
#   - User is an ENTITY (can be referenced by other subgraphs)
#   - The 'id' field is the primary key used to look up a User

# ── @external — declares a field owned by another subgraph ────────────
# ── @requires — declares fields from other subgraphs needed to resolve ─
# ── @provides — declares fields this subgraph can provide (optimization)

# Orders subgraph:
type User @key(fields: "id") {
  id:       ID! @external          # owned by Users subgraph — don't resolve here
  orders:   [Order!]!              # owned by this (Orders) subgraph
  fullName: String @external       # owned by Users subgraph
  # @requires: need fullName from Users to compute shippingLabel:
  shippingLabel: String @requires(fields: "fullName")
}

type Order @key(fields: "id") {
  id:       ID!
  total:    Float!
  customer: User!       # reference to User entity (cross-service relationship)
}

# ── Reference resolver — how a subgraph resolves its entities ─────────
# Every subgraph owning an entity MUST implement __resolveReference

# In Orders subgraph resolver:
const resolvers = {
  User: {
    __resolveReference(reference: { id: string }) {
      // reference = { id: '42', __typename: 'User' }
      // Orders service can fetch orders for this user:
      return ordersService.findOrdersByUserId(reference.id);
      // Returns { id: '42', orders: [...] }
      // Router merges this with Users service's name/email fields
    },
    shippingLabel(user: { fullName: string }) {
      // fullName was fetched from Users subgraph via @requires
      return `SHIP TO: ${user.fullName}`;
    },
  },
};
```

**Q7. What is the Apollo Router and how does it differ from the legacy Apollo Gateway?**
A: The Apollo Router and Apollo Gateway are both federation gateways — they receive client queries, plan which subgraphs to query, assemble results. They differ in implementation and capabilities:

```
Apollo Gateway (legacy — @apollo/gateway):
  Language:     Node.js / JavaScript
  Performance:  Moderate — query planning in JS
  Config:       serviceList or managed (Apollo Studio)
  Plugins:      Custom plugins via Node.js
  Status:       Maintenance mode — no new features
  Federation:   v1 and v2 (with adapter)

Apollo Router (current — @apollo/router):
  Language:     Rust (compiled binary — very fast)
  Performance:  High — Rust query planning, low latency
  Config:       router.yaml + supergraph schema (compiled by Rover CLI)
  Plugins:      Rhai scripting or custom Rust plugins (compiled in)
  Status:       Actively developed — all new features
  Federation:   v2 native, v1 with compatibility
  Features:     CORS, JWT auth, rate limiting, entity caching, distributed tracing
                — all configurable in YAML without code

// Apollo Gateway setup (legacy):
import { ApolloGateway } from '@apollo/gateway';
import { ApolloServer }  from '@apollo/server';

const gateway = new ApolloGateway({
  serviceList: [
    { name: 'users',    url: 'http://users-service/graphql' },
    { name: 'orders',   url: 'http://orders-service/graphql' },
    { name: 'payments', url: 'http://payments-service/graphql' },
  ],
});

// Apollo Router setup (current):
# No Node.js code — just YAML config:
# router.yaml
supergraph:
  listen: 0.0.0.0:4000
cors:
  origins:
    - https://myapp.com
    - http://localhost:3000
headers:
  all:
    request:
      - propagate:
          matching: x-.*  # forward all x- headers to subgraphs
authentication:
  router:
    jwt:
      jwks:
        - url: https://auth.mycompany.com/.well-known/jwks.json

# Run with:
# router --config router.yaml --supergraph supergraph.graphql
```

**Q8. What is the federation supergraph and how is it composed with the Rover CLI?**
A: The **supergraph schema** is the compiled, unified schema that the Router uses to plan queries. It is produced by **composition** — Rover CLI fetches each subgraph's SDL, validates that they compose correctly (no conflicts, all entities properly defined), and outputs a single `supergraph.graphql` file.

```yaml
# supergraph.yaml — tells Rover where each subgraph lives
federation_version: =2.6.0

subgraphs:
  users:
    routing_url: http://users-service:4001/graphql
    schema:
      subgraph_url: http://users-service:4001/graphql  # fetch schema from running service
      # OR load from file:
      # file: ./users/schema.graphql

  orders:
    routing_url: http://orders-service:4002/graphql
    schema:
      subgraph_url: http://orders-service:4002/graphql

  payments:
    routing_url: http://payments-service:4003/graphql
    schema:
      file: ./payments/schema.graphql  # static file (useful in CI)
```

```bash
# Compose the supergraph:
rover supergraph compose --config supergraph.yaml > supergraph.graphql

# Rover validates composition at this step — fails if:
#   - A @key field doesn't exist on the type
#   - @external fields are missing their owning subgraph
#   - Type conflicts that can't be resolved
#   - Invalid @requires fields

# Start the Router:
router --supergraph supergraph.graphql --config router.yaml

# With managed federation (Apollo Studio):
# Supergraph is published to Studio; Router polls for updates
rover subgraph publish my-graph@production \
  --name users \
  --schema ./users/schema.graphql \
  --routing-url http://users-service:4001/graphql
# Studio composes automatically; Router fetches new supergraph live (zero-downtime)
```

**Q9. How does Apollo Router's query planning work — what does a query plan look like?**
A: The query planner analyzes an incoming GraphQL query against the supergraph schema to produce a **query plan** — a tree of `Fetch`, `Parallel`, `Sequence`, and `Flatten` operations describing the exact sub-queries to send to each subgraph and how to assemble the result.

```graphql
# Client query:
query GetUserWithOrders {
  user(id: "42") {
    id
    name          # Users subgraph
    email         # Users subgraph
    orders {      # Orders subgraph
      id
      total
      items {     # Orders subgraph
        product { # Products subgraph (extends Order)
          name
          price
        }
      }
    }
  }
}
```

```
Query Plan:
  Sequence [
    Parallel [
      Fetch(users) {
        user(id: "42") {
          id
          name
          email
        }
      }
    ],
    Flatten(path: "user") [
      Fetch(orders) {
        # Called with user entity reference from step above:
        { user(id: "42") @requires(id) {
            orders {
              id
              total
              items { id }
            }
          }
        }
      }
    ],
    Flatten(path: "user.orders[*].items[*]") [
      Fetch(products) {
        # Called for EACH product id (batched via _entities query):
        _entities(representations: [{ __typename: "Product", id: $id }]) {
          ... on Product {
            name
            price
          }
        }
      }
    ]
  ]

Key insight: Federation batches entity lookups via the `_entities` query
  → Instead of N separate product queries, one _entities(representations: [...])
    with all product IDs at once → solves the distributed N+1 problem
```

**Q10. What are the key Federation v2 improvements over Federation v1?**
A: Federation v2 (2022+) addressed several v1 pain points:

```graphql
# Federation v1 — extend syntax (verbose, confusing):
# Orders subgraph must explicitly "extend" User even though it's defining new fields:
extend type User @key(fields: "id") {
  id:     ID! @external
  orders: [Order!]!
}
# Problem: every subgraph that wants to ADD fields to User must write this boilerplate
# Also: the "extend" keyword is borrowed from SDL — semantically confusing

# Federation v2 — no extend required (cleaner):
# Orders subgraph just declares User with its fields:
type User @key(fields: "id") {
  id:     ID! @external  # @external still needed to mark non-owned fields
  orders: [Order!]!      # this subgraph owns this field
}

# Federation v2 — @shareable: multiple subgraphs can own the SAME field
# (v1 required exactly one owner — breaks for shared utility types)
type Position @shareable {   # any subgraph can resolve position fields
  lat: Float!
  lon: Float!
}

# Federation v2 — @inaccessible: hide from supergraph without removing
type InternalTag @inaccessible {  # not exposed to clients but used internally
  id: ID!
}

# Federation v2 — @override: migrate field ownership between subgraphs safely
type Order {
  # Moving 'status' field from Orders subgraph to Fulfillment subgraph:
  status: String @override(from: "orders")  # Fulfillment says "I'm taking over"
  # During migration: both subgraphs can serve the field
  # After migration: remove @override and the orders subgraph's field
}

# Federation v2 — @composeDirective: include custom directives in the supergraph
# Allows schema-level directives to be preserved through composition

# Federation v2 — progressive @override with labels (v2.7+):
status: String @override(from: "orders", label: "percent(10)")
# Routes 10% of traffic to new subgraph — gradual migration with traffic splitting
```

### Section 4: Head-to-Head Comparison

**Q11. When should you choose schema stitching over federation, and vice versa?**
A: The choice depends on team structure, existing infrastructure, and control requirements:

```
Choose SCHEMA STITCHING when:

  1. Integrating third-party or vendor GraphQL APIs you don't control:
     → Shopify, GitHub, Stripe — you can't add federation directives to their schemas
     → Stitching wraps any GraphQL endpoint regardless of its implementation

  2. Heterogeneous infrastructure with non-Apollo servers:
     → Hasura, PostGraphile, Hot Chocolate, Ruby/Python GraphQL servers
     → No need for all services to use Apollo Server or understand federation

  3. Central team owns the gateway and coordination:
     → The platform/API team explicitly manages cross-service relationships
     → This is acceptable when services are few and change is slow

  4. Adding GraphQL to an existing REST API landscape:
     → Stitch over REST endpoints using custom executors
     → Teams don't need to learn federation concepts

  5. Proof of concept or small number of services (< 3–4):
     → Stitching is simpler to get started with
     → Less operational overhead initially

Choose FEDERATION when:

  1. Multiple teams owning separate microservices independently:
     → Each team deploys their subgraph without coordinating with a central team
     → Ownership is clear: Orders team owns Order type, Users team owns User type

  2. Needing schema validation at publish time (not at runtime):
     → Rover composition fails immediately if schemas don't compose correctly
     → Catch breaking changes before deployment reaches the gateway

  3. GraphQL-first organization with Apollo ecosystem investment:
     → Apollo Studio for schema registry, metrics, change management
     → Managed federation — zero-downtime schema updates
     → Federation is the industry standard for distributed GraphQL at scale

  4. Performance is critical:
     → Apollo Router is a Rust binary — orders of magnitude lower latency than JS gateway
     → Query planning is highly optimized
     → Entity batching prevents distributed N+1

  5. Scale (many services, many teams, complex type relationships):
     → Federation's declarative model scales better than centralized stitching config
     → Adding a new subgraph requires no gateway code changes
```

**Q12. What are the operational trade-offs between stitching and federation at scale?**
A: At scale, the differences in operational burden become significant:

```
ADDING A NEW SERVICE:

  Schema Stitching:
    1. Deploy new service
    2. Edit gateway code: add executor + merge rules → gateway team required
    3. Redeploy gateway with new configuration
    4. Test that type merging works correctly

  Federation:
    1. Deploy new subgraph (implements federation spec)
    2. Run: rover subgraph publish my-graph --name new-service --schema ...
    3. Apollo Studio composes, validates, publishes new supergraph automatically
    4. Router polls Studio, receives new supergraph → zero-downtime update
    No gateway code changes. Gateway team not required.

HANDLING A BREAKING SCHEMA CHANGE:

  Schema Stitching:
    → No compile-time composition check
    → A service changing its schema breaks silently
    → Gateway continues routing to old schema; type errors appear at runtime
    → No central schema registry — hard to track "what's deployed where"

  Federation:
    → rover subgraph publish validates composition BEFORE accepting the change
    → Apollo Studio runs composition checks: "does this change break the supergraph?"
    → Schema checks against production traffic: "do any current queries use the removed field?"
    → Breaking change blocked at CI/publish time, not discovered in production

SERVICE DISCOVERY:

  Schema Stitching:
    → Static config: manually update executor list when services change URL
    → Or: implement custom discovery (Consul, service registry)

  Federation:
    → Apollo Studio as the source of truth for all subgraph URLs
    → Router polls Studio periodically — gets updated URLs automatically
    → Or: static supergraph file (managed in CI/CD pipeline)

DEBUGGING A FAILING QUERY:

  Schema Stitching:
    → Must manually trace: "which service did this field resolve from?"
    → No native distributed tracing
    → Add custom logging; correlate logs across services

  Federation:
    → Apollo Router has native distributed tracing (OpenTelemetry)
    → Apollo Studio shows query plans, field usage, error rates per subgraph
    → x-query-plan header shows the exact plan that ran
```

### Section 5: Technical Deep Dives

**Q13. How does entity resolution work in Federation and what is the `_entities` query?**
A: The `_entities` query is a special Federation-defined query that the Router uses to batch-fetch entities from subgraphs. It accepts an array of **representations** — objects containing `__typename` and the key fields — and returns the matching entities.

```graphql
# The _entities query (generated by federation spec, not written manually):
query($representations: [_Any!]!) {
  _entities(representations: $representations) {
    ... on User {
      name
      email
    }
    ... on Product {
      name
      price
    }
  }
}

# Representations are the "primary keys" the Router passes:
{
  "representations": [
    { "__typename": "User",    "id": "42" },
    { "__typename": "User",    "id": "43" },
    { "__typename": "Product", "id": "P-001" },
    { "__typename": "Product", "id": "P-002" }
  ]
}
```

```ts
// Subgraph implements reference resolver — called by _entities:
// Users subgraph resolvers:
const resolvers = {
  User: {
    // __resolveReference called once per User in the representations array:
    __resolveReference(reference: { id: string }, context: Context) {
      // reference = { __typename: 'User', id: '42' }
      return usersService.findById(reference.id);
      // Returns the full User object — Router picks only the requested fields
    },
  },
};

// DataLoader pattern — critical for avoiding N+1 across entity calls:
// Without DataLoader: N separate DB queries for N users
// With DataLoader: one batched query for all N users

const userLoader = new DataLoader(async (ids: string[]) => {
  const users = await db.users.findMany({ where: { id: { in: ids } } });
  // Return users in same order as ids (DataLoader requirement):
  return ids.map(id => users.find(u => u.id === id) ?? null);
});

const resolvers = {
  User: {
    __resolveReference(reference: { id: string }) {
      return userLoader.load(reference.id);
      // DataLoader batches all reference.id calls within the same tick
      // → ONE database query regardless of how many User entities are needed
    },
  },
};
```

**Q14. What is the N+1 problem in distributed GraphQL and how does each approach handle it?**
A: The distributed N+1 problem is more severe than the standard N+1: for N order items, you need N separate HTTP calls to the Products service to resolve each item's product details — each call is a network round-trip, not just a DB query.

```
Standard N+1 (single service):
  query orders → N queries for product details
  Fix: DataLoader batches queries within one request

Distributed N+1 (federated/stitched services):
  1 query to Orders service → N separate HTTP calls to Products service
  Each call: TCP handshake (if not keep-alive) + network latency + serialization
  Impact: 50 orders × 10ms/call = 500ms of Product service calls alone

Federation's solution — _entities batching:
  Router collects ALL product IDs needed from the entire query plan
  → ONE _entities call to Products service with all IDs
  → Products service resolves them all in one batch
  → Router maps results back to each order item

  50 orders → 1 _entities call with 50 representations → 1 Products service call
  Network overhead: 1 round-trip instead of 50

Stitching's solution — batching delegations:
  @graphql-tools/stitch with batchDelegateToSchema:
```

```ts
// Schema stitching batching — uses DataLoader under the hood:
import { batchDelegateToSchema } from '@graphql-tools/delegate';

const gatewaySchema = stitchSchemas({
  subschemas: [
    {
      schema:   productsSchema,
      executor: productsExecutor,
      merge: {
        Product: {
          selectionSet:  '{ id }',
          fieldName:     'productsByIds',   // batch query on Products service
          key:           ({ id }) => id,    // extract the key
          argsFromKeys:  (ids) => ({ ids }), // map keys → query args
          // → one productsByIds(ids: [...]) call for all products
        },
      },
    },
  ],
});

// Products service must expose a batch query:
type Query {
  productsByIds(ids: [ID!]!): [Product]! # returns null for not-found IDs
  # Stitching expects results in same order as input IDs (null for missing)
}
```

### Section 6: Scenario / Interview-Style Questions

**Q15. "Your organization currently uses schema stitching with 5 services. As you scale to 20 services with 15 teams, what problems will emerge and should you migrate to federation?"**
A: Classic stitching pain points that emerge at scale — and the migration considerations:

```
Problems that emerge at scale with stitching:

1. Gateway becomes a bottleneck:
   Each new service → gateway team must update executor list + merge rules
   15 teams × 2 deploys/week = 30 gateway PRs/week — impossible to keep up
   Teams are blocked waiting for the gateway team

2. Type merge configuration rot:
   200+ merge rules → nobody fully understands them
   A service changes a field → merge rule silently breaks
   No schema validation at publish time → production errors

3. Introspection overhead:
   Gateway introspects all 20 services on startup (or periodically)
   20 HTTP calls × up to 100ms each = 2s startup delay
   More during rolling deploys

4. No schema registry:
   "What schema is service X running in production?"
   → SSH into the service and look? → not scalable

5. Testing composition changes:
   "If Orders changes the User.orders return type, does the full schema still work?"
   → Must deploy and test — no pre-deploy composition validation

Migration decision framework:
  Migrate if:     teams > 5, services > 5, gateway team is a bottleneck
  Stay stitched:  external APIs, non-Node services that can't add federation,
                  stable schema with rare changes

Migration path (incremental — recommended):
  Phase 1: Add Apollo Studio + Rover to document current schemas
  Phase 2: Add federation directives to 2-3 services (start with the simplest)
           Run Apollo Gateway alongside existing stitcher, point some routes to it
  Phase 3: Migrate remaining services one by one
           Federation Gateway takes over when all services are federated
  Phase 4: Retire stitching gateway, switch to Apollo Router
```

**Q16. "A junior developer asks: in federation, if I add a new field to the User type in the Orders subgraph, do I need to deploy both the Orders service AND the Users service?"**
A: Only the Orders service — this is a key benefit of federation's composition model. Here's the complete reasoning:

```
Scenario: Orders subgraph wants to add User.lifetimeValue: Float
          (computed from order history, owned by Orders subgraph)

Steps required:
  1. Orders subgraph adds the field:
     type User @key(fields: "id") {
       id:            ID! @external
       orders:        [Order!]!
       lifetimeValue: Float!   # new field — owned by Orders subgraph
     }
     # + add __resolveReference to compute lifetimeValue from orders data

  2. Deploy ONLY the Orders service — Users service unchanged

  3. Run: rover subgraph publish my-graph@production \
       --name orders --schema ./schema.graphql
     Rover: validates composition (does lifetimeValue conflict with anything?)
     Studio: composes new supergraph, publishes it
     Router: polls Studio, receives new supergraph → immediately serves the new field

Users service:
  → Never touched
  → Never redeployed
  → Has no idea Orders added a field to User
  → Users service continues serving its own User fields (id, name, email)

Client query immediately available:
  query {
    user(id: "42") {
      name            # Users subgraph
      lifetimeValue   # Orders subgraph — resolves via __resolveReference
    }
  }

This is the federation value proposition:
  Each team extends types they own independently
  No central gatekeeper (no gateway team deployment)
  No other services need to be aware of the change
  Composition validation happens at publish time, not at runtime
```

### Stitching Gateway

```ts
// gateway/index.ts
import { stitchSchemas }      from '@graphql-tools/stitch';
import { buildHTTPExecutor }  from '@graphql-tools/executor-http';
import { schemaFromExecutor } from '@graphql-tools/wrap';
import { createServer }       from 'http';
import { createYoga }         from 'graphql-yoga';

async function buildGatewaySchema() {
  // ── Connect to services ─────────────────────────────────────────────
  const usersExecutor = buildHTTPExecutor({
    endpoint: process.env.USERS_SERVICE_URL ?? 'http://localhost:4001/graphql',
    headers:  { 'x-gateway': 'true' },       // identify gateway requests in service logs
  });

  const ordersExecutor = buildHTTPExecutor({
    endpoint: process.env.ORDERS_SERVICE_URL ?? 'http://localhost:4002/graphql',
    headers:  { 'x-gateway': 'true' },
  });

  // ── Load schemas (with retry for service startup order) ────────────
  const [usersSchema, ordersSchema] = await Promise.all([
    schemaFromExecutor(usersExecutor),
    schemaFromExecutor(ordersExecutor),
  ]);

  // ── Stitch with type merging ────────────────────────────────────────
  return stitchSchemas({
    subschemas: [
      {
        schema:   usersSchema,
        executor: usersExecutor,
        merge: {
          User: {
            selectionSet: '{ id }',           // Users service needs id to resolve a User
            fieldName:    'usersByIds',        // batch query to call
            key:          (user) => user.id,   // extract key from User object
            argsFromKeys: (ids) => ({ ids }),  // map array of ids → query argument
            // → ONE usersByIds(ids: [...]) call regardless of how many Users are requested
          },
        },
      },
      {
        schema:   ordersSchema,
        executor: ordersExecutor,
        merge: {
          User: {
            selectionSet: '{ id }',
            fieldName:    'ordersForUsers',    // batch query: fetch orders for multiple users
            key:          (user) => user.id,
            argsFromKeys: (ids) => ({ userIds: ids }),
            // → ONE ordersForUsers(userIds: [...]) call for all users needing orders resolved
          },
        },
      },
    ],

    // Gateway-level resolvers for fields that span services:
    typeDefs: /* GraphQL */ `
      extend type Query {
        # A gateway-level query that merges both services:
        userWithOrders(id: ID!): User
      }
    `,
    resolvers: {
      Query: {
        userWithOrders: async (_, { id }, context, info) => {
          // Delegate to both subschemas — stitching handles the merge:
          return { id }; // returning just the id lets type merging fill in the rest
        },
      },
    },
  });
}

// Start the gateway:
async function main() {
  const schema = await buildGatewaySchema();

  const yoga = createYoga({ schema });
  const server = createServer(yoga);

  server.listen(4000, () => {
    console.log('Gateway running at http://localhost:4000/graphql');
  });
}

main().catch(console.error);
```

### How Type Merging Resolves a Query

```
Client query:
  { user(id: "42") { name email orders { id total } } }

Step 1: Gateway recognizes:
  - name, email: from Users subschema
  - orders: from Orders subschema
  Both need { id } as the key

Step 2: Fetch from Users (resolves name, email):
  → usersByIds(ids: ["42"]) → [{ id: "42", name: "Alice", email: "alice@..." }]

Step 3: Fetch from Orders (resolves orders using id="42"):
  → ordersForUsers(userIds: ["42"]) → [{ id: "42", orders: [...] }]

Step 4: Merge on id field:
  { id: "42", name: "Alice", email: "alice@...", orders: [...] }

Step 5: Return to client — sees a unified User object
```

```ts
import DataLoader from 'dataloader';

function createUserLoader() {
  return new DataLoader<string, User | null>(async (ids) => {
    const users = await db.users.findMany({ where: { id: { in: [...ids] } } });
    return ids.map(id => users.find(u => u.id === id) ?? null);
  });
}

export const resolvers = {
  Query: {
    me:    (_, __, { currentUser }) => currentUser,
    user:  (_, { id }, { loaders }) => loaders.user.load(id),
    users: ()                        => db.users.findAll(),
  },

  User: {
    // __resolveReference is called by the Router when other subgraphs
    // request User entities via _entities query:
    __resolveReference(reference: { id: string }, { loaders }: Context) {
      // reference = { __typename: 'User', id: '42' }
      return loaders.user.load(reference.id);
      // DataLoader batches: if Router requests 50 users, one DB query
    },
  },
};

  return {
    loaders: { user: createUserLoader() },
```

```ts
      if (!userId) throw new GraphQLError('Unauthorized', { extensions: { code: 'UNAUTHORIZED' } });
      return db.users.findById(userId);
    },
  },
};
```

### Federation — Router-Level JWT + Subgraph Authorization

```yaml
# router.yaml — JWT validation at Router level:
authentication:
  router:
    jwt:
      jwks:
        - url: https://auth.mycompany.com/.well-known/jwks.json
          poll_interval: 60s
      header_name: Authorization
      header_value_prefix: "Bearer "
      # JWT claims are available as context in coprocessors / Rhai scripts

# Header propagation — forward claims to subgraphs:
headers:
  all:
    request:
      - insert:
          name: x-user-id
          value: "{context.identity.sub}"       # from JWT claims
      - insert:
          name: x-user-role
          value: "{context.identity.role}"
      - propagate:
          matching: x-.*                         # forward all x- headers
```

```ts
// Users subgraph — receives user identity from Router headers:
const resolvers = {
  Query: {
    me: (_, __, context) => {
      const userId = context.req.headers['x-user-id'];
      if (!userId) throw new GraphQLError('Unauthenticated', {
        extensions: { code: 'UNAUTHENTICATED' },
      });
      return db.users.findById(userId);
    },

    user: (_, { id }, context) => {
      const role = context.req.headers['x-user-role'];
      if (role !== 'admin' && context.req.headers['x-user-id'] !== id) {
        throw new GraphQLError('Not authorized to view other users', {
          extensions: { code: 'FORBIDDEN' },
        });
      }
      return db.users.findById(id);
    },
  },

  User: {
    email: (user, _, context) => {
      const userId = context.req.headers['x-user-id'];
      // Only return email to the owner or admins:
      if (context.req.headers['x-user-role'] === 'admin' || userId === user.id) {
        return user.email;
      }
      return null;   // redact email for other users
    },

    __resolveReference(ref: { id: string }, context: Context) {
      // When called via _entities: context still has x-user-id headers
      // Can apply field-level auth in the resolved User object's field resolvers
      return db.users.findById(ref.id);
    },
  },
};

// Field-level authorization with a custom directive:
// schema.graphql:
directive @requiresRole(role: String!) on FIELD_DEFINITION

type User @key(fields: "id") {
  id:    ID!
  name:  String!
  email: String! @requiresRole(role: "admin")  # only admins see email
  ssn:   String  @requiresRole(role: "admin")  # PII — strict access
}

// Directive implementation:
export const requiresRoleDirective = {
  requiresRole: (next) => async (root, args, context, info) => {
    const requiredRole = info.fieldNodes[0].directives
      ?.find(d => d.name.value === 'requiresRole')
      ?.arguments?.[0]?.value?.value;

    const userRole = context.req.headers['x-user-role'];
    if (requiredRole && userRole !== requiredRole) {
      throw new GraphQLError(`Requires role: ${requiredRole}`, {
        extensions: { code: 'FORBIDDEN' },
      });
    }
    return next(root, args, context, info);
  },
};
```

## Quick Reference — Schema Stitching vs Federation Cheat Sheet

```
SCHEMA STITCHING (@graphql-tools/stitch):
  Architecture:   Composition at the gateway — services are plain GraphQL endpoints
  Gateway owns:   All merge rules, executor configs, type merging configuration
  Services know:  Nothing about stitching — any GraphQL server works
  Adding service: Edit gateway code → redeploy gateway → gateway team required
  Validation:     Runtime — errors surface when queries are executed
  Best for:       Third-party APIs, mixed GQL implementations, small # of services

  Key APIs:
    stitchSchemas({ subschemas })     → creates the stitched schema
    buildHTTPExecutor({ endpoint })   → connects to a remote GQL service
    schemaFromExecutor(executor)      → introspects remote schema
    batchDelegateToSchema()           → N+1 solution via DataLoader-style batching
    stitchingDirectives()             → enables @merge directive (declarative config)

  Type merging config:
    merge: {
      TypeName: {
        selectionSet: '{ id }',              # key fields needed
        fieldName:    'batchQueryName',       # batch resolver to call
        key:          (obj) => obj.id,        # extract key from object
        argsFromKeys: (keys) => ({ ids: keys }), # map keys → query arg
      }
    }

APOLLO FEDERATION (@apollo/subgraph + Apollo Router):
  Architecture:   Composition in subgraphs — services declare their relationships
  Router owns:    Query planning and routing (minimal business logic)
  Services know:  They're part of a federation — implement federation spec
  Adding service: Deploy subgraph, rover publish → Studio auto-composes, Router updates
  Validation:     Composition time — rover CLI catches errors before deployment
  Best for:       Multiple teams, microservices, large schemas, Apollo ecosystem

  Key directives:
    @key(fields: "id")           → declares entity + primary key
    @external                    → field owned by another subgraph
    @requires(fields: "name")    → needs field from another subgraph to resolve
    @provides(fields: "name")    → can provide field (optimization hint)
    @shareable                   → multiple subgraphs can resolve this field (v2)
    @inaccessible                → hide from supergraph clients (v2)
    @override(from: "subgraph")  → migrate field ownership between subgraphs (v2)

  Entity resolution flow:
    1. Router builds query plan from supergraph schema
    2. Fetches entity key fields (e.g., id) from owning subgraph
    3. Sends _entities query with representations to other subgraphs
    4. Subgraphs call __resolveReference(ref) → return entity data
    5. Router merges results → returns complete response to client

  Rover CLI:
    rover supergraph compose --config supergraph.yaml  → local composition
    rover subgraph check my-graph@env --schema ...     → pre-publish validation
    rover subgraph publish my-graph@env --name ...     → publish to Studio

COMPARISON TABLE:
  ┌─────────────────────┬────────────────────┬────────────────────┐
  │                     │ Schema Stitching   │  Federation        │
  ├─────────────────────┼────────────────────┼────────────────────┤
  │ Service coupling    │ Services are dumb  │ Services aware     │
  │ Gateway complexity  │ High (owns config) │ Low (just routing) │
  │ Team autonomy       │ Low (need gateway) │ High (self-service) │
  │ Third-party APIs    │ Excellent          │ Impossible         │
  │ Schema validation   │ Runtime            │ Composition time   │
  │ Schema registry     │ Manual/custom      │ Apollo Studio      │
  │ Performance (GW)    │ Node.js            │ Rust (much faster) │
  │ N+1 batching        │ Manual DataLoader  │ Automatic (_entities)│
  │ Zero-downtime update│ Gateway redeploy   │ Router polls Studio│
  │ Breaking change det.│ Manual/none        │ Automated checks   │
  └─────────────────────┴────────────────────┴────────────────────┘

COMMON BUGS:

  Stitching:
    Missing batch query        → use fieldName pointing to single resolver →
                                 N+1 for every N users (fix: add batch query + batchDelegateToSchema)
    Type name collision        → two subschemas define 'Error' differently →
                                 use RenameTypes transform on one schema
    Introspection at startup   → schemaFromExecutor fails if service not ready →
                                 add retry logic / health check before stitching
    Context not forwarded      → executor headers not reading from context →
                                 executor must be a function: executor: (req) => ...

  Federation:
    Missing __resolveReference → Router can't fetch entity fields from subgraph →
                                 every entity type MUST implement __resolveReference
    @external without owner    → field marked @external but no subgraph owns it →
                                 composition fails: "field not defined in any subgraph"
    @requires field not @external → @requires(fields: "name") but 'name' not @external →
                                    composition error: required field must be external
    DataLoader not per-request → DataLoader instantiated at module level →
                                  cache leaks between requests (create new per context)
    Subgraph not reachable     → Router returns "subgraph not available" → health check
    Composition failure in CI  → rover subgraph check exits non-zero → inspect error message
```

**Final Tip:** At the 5 YOE level, schema stitching vs federation questions test whether you can reason about **architectural trade-offs and team dynamics**, not just the APIs. The highest-signal answer on when to choose each: "Stitching is the right choice when you don't control the upstream services — Shopify, GitHub, Stripe — or when your services are implemented in non-Node languages. Stitching puts all the composition intelligence in the gateway, which is great when you have one team maintaining it but becomes a bottleneck when 15 teams need to add new types independently. Federation shifts that intelligence into the subgraphs themselves — each team publishes their schema, Rover validates it composes correctly, and the Router gets the new supergraph without a gateway deployment. The gateway team becomes optional." For entity resolution: "The `_entities` query is the key mechanism that makes federation work without N+1. When the Router needs User.orders for 50 users, it doesn't make 50 calls to the Orders subgraph — it makes one `_entities` call with 50 representations, Orders subgraph gets all 50 IDs at once and can batch-fetch them in a single database query via `__resolveReference`. You still need DataLoader inside `__resolveReference` if multiple representations arrive in the same request — which is always the case." For migration: "I always migrate incrementally — `buildSubgraphSchema` from `@apollo/subgraph` is backward-compatible with plain GraphQL usage, so you can federation-enable one service while the stitching gateway still uses it. Run the Router alongside the stitching gateway on a different port, shift canary traffic, validate, then cut over fully. Never a big bang migration."
