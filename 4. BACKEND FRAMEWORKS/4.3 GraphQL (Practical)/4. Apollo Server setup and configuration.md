# Apollo Server Setup and Configuration — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Apollo Server and how does it fit into the GraphQL execution pipeline?**
A: Apollo Server is a spec-compliant GraphQL server library for Node.js. It sits between the HTTP layer and your business logic — parsing incoming GraphQL documents, validating them against your schema, executing resolvers, and serializing the result back to the client:

```
HTTP Request (POST /graphql)
  ↓
Transport layer (Express / Fastify / Koa / standalone HTTP)
  ↓
Apollo Server middleware
  ├── Parse: graphql-js parses the query string into an AST
  ├── Validate: checks the AST against the schema (field existence, type correctness)
  ├── Context build: calls your contextFn → attaches user, loaders, services
  ├── Execute: walks the AST, calls resolvers depth-first per the GraphQL spec
  │     Query   → resolvers run concurrently per level
  │     Mutation → resolvers run serially at the top level
  │     Subscription → resolver returns AsyncIterable
  └── Format: serializes { data, errors } to JSON
  ↓
HTTP Response (200 / 400)

Apollo Server adds on top of graphql-js:
  - Plugin system (lifecycle hooks for every phase above)
  - Persisted queries
  - Schema introspection controls
  - Built-in Apollo Studio integration (tracing, metrics)
  - Landing page (Sandbox) in development
  - Error formatting and masking
  - HTTP transport handling (multipart, GET/POST, batching)
```

**Q2. What are the three generations of Apollo Server (v2, v3, v4) and what changed in v4?**
A: Each version made breaking changes to the integration model and middleware API. v4 (2022) is the current version and is the one to know for interviews:

```
Apollo Server 2 (2018–2022):
  - Built-in Express integration (applyMiddleware)
  - context() function on the ApolloServer constructor
  - plugins as objects with lifecycle methods
  - apollo-server, apollo-server-express, apollo-server-fastify as separate packages

Apollo Server 3 (2021):
  - Dropped built-in Express integration — required explicit expressMiddleware
  - Introduced standalone server (startStandaloneServer)
  - context() moved inside integration functions
  - Still had separate integration packages

Apollo Server 4 (2022 — current):
  - Single package: @apollo/server (replaces all apollo-server-* packages)
  - Two integration modes:
      startStandaloneServer — wraps Node http.Server, zero config, good for dev
      expressMiddleware — integrates with existing Express app
  - context() is a parameter of the integration function, not ApolloServer constructor
  - httpBatchedRequests disabled by default (security: CSRF protection)
  - csrfPrevention enabled by default
  - schema reporting and usage reporting moved to @apollo/usage-reporting-plugin
  - ApolloServerPluginLandingPageLocalDefault (Sandbox) replaces GraphQL Playground

// v3 pattern (no longer correct in v4):
const server = new ApolloServer({
    typeDefs,
    resolvers,
    context: ({ req }) => ({ user: req.user }),  // ← v3: context on constructor
});
await server.start();
app.use('/graphql', expressMiddleware(server));   // missing context here

// v4 pattern (correct):
const server = new ApolloServer({ typeDefs, resolvers });
await server.start();
app.use(
    '/graphql',
    expressMiddleware(server, {
        context: async ({ req }) => ({ user: req.user }),  // ← v4: context on middleware
    }),
);
```

**Q3. What is the difference between `startStandaloneServer` and `expressMiddleware`, and when do you use each?**
A: They serve different integration needs — standalone for simplicity, express middleware for composition with existing infrastructure:

```typescript
import { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';
import { expressMiddleware } from '@apollo/server/express4';
import express from 'express';
import cors from 'cors';
import { json } from 'body-parser';

const typeDefs = `#graphql
    type Query { hello: String }
`;
const resolvers = { Query: { hello: () => 'world' } };

// ── Option 1: startStandaloneServer ──────────────────────────────────────────
// Wraps Apollo Server in a plain Node.js HTTP server
// No Express, no CORS config, no body-parser — all handled internally
// Good for: microservices, development, standalone GraphQL APIs

const server = new ApolloServer({ typeDefs, resolvers });
const { url } = await startStandaloneServer(server, {
    listen: { port: 4000 },
    context: async ({ req }) => {
        const token = req.headers.authorization ?? '';
        const user = await validateToken(token);
        return { user };
    },
});
console.log(`Server ready at ${url}`);

// ── Option 2: expressMiddleware ───────────────────────────────────────────────
// Mounts Apollo as Express middleware — shares the Express app with REST routes,
// auth middleware, health checks, rate limiters, etc.
// Good for: hybrid REST+GraphQL apps, adding GraphQL to existing Express server

const app = express();
const server = new ApolloServer({ typeDefs, resolvers });
await server.start();

app.use(
    '/graphql',
    cors<cors.CorsRequest>({ origin: ['https://app.example.com'] }),
    json(),                          // body-parser required — standalone handles this internally
    expressMiddleware(server, {
        context: async ({ req }) => {
            const user = req.user;  // set by earlier auth middleware
            return { user, loaders: createLoaders(user?.tenantId) };
        },
    }),
);

app.get('/health', (_req, res) => res.json({ status: 'ok' }));  // REST + GraphQL coexist

await new Promise<void>((resolve) => app.listen(4000, resolve));

// Comparison:
//                      │ startStandaloneServer │ expressMiddleware
// ─────────────────────┼───────────────────────┼──────────────────────
// CORS handling        │ Built-in              │ Manual (cors package)
// Body parsing         │ Built-in              │ Manual (body-parser)
// REST routes          │ Not supported         │ Supported
// Auth middleware      │ context() only        │ Express middleware chain
// HTTP/2              │ No                    │ Yes (with http2 + express)
// Complexity          │ Low                   │ Higher
```

## Section 2: Schema Definition and Resolver Setup

**Q4. What are the three ways to define a schema in Apollo Server and what are the tradeoffs?**
A: SDL-first, code-first, and programmatic schema construction each have different ergonomics and use cases:

```typescript
import { ApolloServer } from '@apollo/server';
import { buildSchema, GraphQLSchema, GraphQLObjectType, GraphQLString } from 'graphql';
import { makeExecutableSchema } from '@graphql-tools/schema';

// ── Approach 1: SDL-first with typeDefs + resolvers (most common) ─────────────
// Schema defined in GraphQL SDL strings; resolvers in a separate map
// Apollo Server merges them via graphql-tools makeExecutableSchema internally

const typeDefs = `#graphql
    type Query {
        user(id: ID!): User
    }
    type User {
        id: ID!
        name: String!
        loans: [Loan!]!
    }
`;

const resolvers = {
    Query: {
        user: (_parent, { id }, ctx) => ctx.userService.findById(id),
    },
    User: {
        loans: (parent, _args, ctx) => ctx.loanService.findByUserId(parent.id),
    },
};

const server = new ApolloServer({ typeDefs, resolvers });

// ── Approach 2: Pre-built GraphQLSchema (escape hatch for programmatic control) ─
// Useful when schema is generated by a third-party tool (Nexus, Pothos, TypeGraphQL)
// or when you need dynamic schema construction at runtime

const schema: GraphQLSchema = buildSchema(`
    type Query { hello: String }
`);

const server = new ApolloServer({ schema });

// ── Approach 3: Schema merging (multiple SDL files / modules) ─────────────────
// Standard pattern for large codebases — schema split by domain
import { mergeTypeDefs, mergeResolvers } from '@graphql-tools/merge';
import { loadFilesSync } from '@graphql-tools/load-files';

const typeDefs = mergeTypeDefs(
    loadFilesSync(path.join(__dirname, '**/*.graphql'))  // glob all .graphql files
);
const resolvers = mergeResolvers(
    loadFilesSync(path.join(__dirname, '**/resolvers.ts'))
);

const server = new ApolloServer({ typeDefs, resolvers });

// ── Tradeoffs ─────────────────────────────────────────────────────────────────
//                  │ SDL-first          │ Code-first (Nexus/Pothos) │ Programmatic
// ─────────────────┼────────────────────┼───────────────────────────┼──────────────
// Type safety      │ None (string SDL)  │ Full TypeScript inference  │ Full
// Tooling          │ .graphql intellij  │ IDE autocomplete          │ Verbose
// Runtime overhead │ Parse at startup   │ Build at startup          │ None
// Dynamic schema   │ Awkward            │ Moderate                  │ Full control
// SDL export       │ Native             │ Needs codegen             │ Needs printSchema
```

**Q5. How do you split a large schema across multiple files and modules in Apollo Server?**
A: The standard pattern for production schemas is module-based splitting — each domain owns its typeDefs and resolvers, merged at startup:

```typescript
// Directory structure:
// src/
//   graphql/
//     user/
//       user.typedefs.ts
//       user.resolvers.ts
//     loan/
//       loan.typedefs.ts
//       loan.resolvers.ts
//     index.ts  ← merges everything

// user/user.typedefs.ts:
import { gql } from 'graphql-tag';
export const userTypeDefs = gql`
    type User {
        id: ID!
        name: String!
        email: String!
        createdAt: String!
    }

    extend type Query {
        user(id: ID!): User
        users(filter: UserFilterInput): [User!]!
    }

    extend type Mutation {
        updateUser(id: ID!, input: UpdateUserInput!): User!
    }

    input UserFilterInput {
        name: String
        email: String
    }

    input UpdateUserInput {
        name: String
        email: String
    }
`;

// user/user.resolvers.ts:
import { Resolvers } from '../../generated/graphql';  // generated types from codegen

export const userResolvers: Resolvers = {
    Query: {
        user: (_parent, { id }, ctx) => ctx.services.user.findById(id),
        users: (_parent, { filter }, ctx) => ctx.services.user.findAll(filter),
    },
    Mutation: {
        updateUser: (_parent, { id, input }, ctx) => ctx.services.user.update(id, input),
    },
};

// graphql/index.ts — merge all modules:
import { makeExecutableSchema } from '@graphql-tools/schema';
import { mergeTypeDefs, mergeResolvers } from '@graphql-tools/merge';
import { userTypeDefs } from './user/user.typedefs';
import { userResolvers } from './user/user.resolvers';
import { loanTypeDefs } from './loan/loan.typedefs';
import { loanResolvers } from './loan/loan.resolvers';

// Root type must be declared once (not in extend):
const rootTypeDefs = gql`
    type Query
    type Mutation
    type Subscription
`;

export const schema = makeExecutableSchema({
    typeDefs: mergeTypeDefs([rootTypeDefs, userTypeDefs, loanTypeDefs]),
    resolvers: mergeResolvers([userResolvers, loanResolvers]),
});

// server.ts:
const server = new ApolloServer({ schema });
```

## Section 3: Context and Authentication

**Q6. How do you build and type the GraphQL context in Apollo Server v4?**
A: Context is built once per request and passed to every resolver. In v4, the context function lives on the integration layer, not the `ApolloServer` constructor. Typing it end-to-end requires a shared interface:

```typescript
// context.ts — shared context type:
import DataLoader from 'dataloader';
import { User } from './entities/user.entity';
import { UserService } from './services/user.service';
import { LoanService } from './services/loan.service';

export interface AppContext {
    user: AuthenticatedUser | null;
    tenantId: string | null;
    services: {
        user: UserService;
        loan: LoanService;
    };
    loaders: {
        user: DataLoader<string, User>;
    };
    requestId: string;
}

export interface AuthenticatedUser {
    id: string;
    email: string;
    roles: string[];
    tenantId: string;
}

// context.factory.ts — builds context per request:
import { verifyJwt } from './auth/jwt';
import { UserService } from './services/user.service';
import { createUserLoader } from './loaders/user.loader';

export async function buildContext(
    req: express.Request,
    services: { user: UserService; loan: LoanService },
): Promise<AppContext> {
    let user: AuthenticatedUser | null = null;
    const token = req.headers.authorization?.replace('Bearer ', '');

    if (token) {
        try {
            user = await verifyJwt(token);
        } catch {
            // Token invalid — user stays null
            // Resolvers that need auth will throw themselves
        }
    }

    return {
        user,
        tenantId: user?.tenantId ?? null,
        services,
        loaders: {
            user: createUserLoader(services.user, user?.tenantId),
        },
        requestId: req.headers['x-request-id'] as string ?? crypto.randomUUID(),
    };
}

// server.ts — wire up context with full typing:
import { ApolloServer } from '@apollo/server';
import { expressMiddleware } from '@apollo/server/express4';
import { AppContext } from './context';

const server = new ApolloServer<AppContext>({  // ← generic parameter types the context
    schema,
});
await server.start();

app.use(
    '/graphql',
    cors(),
    json(),
    expressMiddleware(server, {
        context: async ({ req }): Promise<AppContext> =>
            buildContext(req, { user: userService, loan: loanService }),
    }),
);

// Resolver usage — fully typed ctx:
const resolvers: Resolvers<AppContext> = {
    Query: {
        user: (_parent, { id }, ctx: AppContext) => {
            if (!ctx.user) throw new GraphQLError('Unauthenticated', {
                extensions: { code: 'UNAUTHENTICATED' },
            });
            return ctx.services.user.findById(id);
        },
    },
};
```

**Q7. How do you implement authentication and authorization in Apollo Server without a framework like NestJS?**
A: The pattern separates concerns — authentication in the context builder (identify who is calling), authorization in resolvers or a middleware layer (decide what they can do):

```typescript
// auth.ts — authentication utilities:
import { GraphQLError } from 'graphql';

export function requireAuth(ctx: AppContext): AuthenticatedUser {
    if (!ctx.user) {
        throw new GraphQLError('You must be logged in', {
            extensions: {
                code: 'UNAUTHENTICATED',
                http: { status: 401 },
            },
        });
    }
    return ctx.user;
}

export function requireRole(ctx: AppContext, role: string): AuthenticatedUser {
    const user = requireAuth(ctx);
    if (!user.roles.includes(role)) {
        throw new GraphQLError('You do not have permission', {
            extensions: {
                code: 'FORBIDDEN',
                http: { status: 403 },
            },
        });
    }
    return user;
}

// Resolver using auth helpers:
const resolvers: Resolvers<AppContext> = {
    Query: {
        // Public — no auth required:
        publicLoans: (_parent, _args, _ctx) => loanService.findPublic(),

        // Authenticated — any logged-in user:
        myLoans: (_parent, _args, ctx) => {
            const user = requireAuth(ctx);
            return loanService.findByUserId(user.id);
        },

        // Role-based — admin only:
        allLoans: (_parent, args, ctx) => {
            requireRole(ctx, 'admin');
            return loanService.findAll(args.filter);
        },
    },

    Mutation: {
        approveLoan: async (_parent, { loanId }, ctx) => {
            const user = requireRole(ctx, 'agent');
            return loanService.approve(loanId, user.id);
        },
    },
};

// Schema directives for declarative auth (alternative to inline checks):
// @auth and @hasRole directives applied in SDL:
const typeDefs = `#graphql
    directive @auth on FIELD_DEFINITION
    directive @hasRole(role: String!) on FIELD_DEFINITION

    type Query {
        myLoans: [Loan!]! @auth
        allLoans: [Loan!]! @hasRole(role: "admin")
    }
`;

// Directive implementation via mapSchema:
import { mapSchema, getDirective, MapperKind } from '@graphql-tools/utils';

function authDirectiveTransformer(schema: GraphQLSchema): GraphQLSchema {
    return mapSchema(schema, {
        [MapperKind.OBJECT_FIELD]: (fieldConfig) => {
            const authDirective = getDirective(schema, fieldConfig, 'auth')?.[0];
            if (authDirective) {
                const { resolve = defaultFieldResolver } = fieldConfig;
                fieldConfig.resolve = async (source, args, ctx, info) => {
                    requireAuth(ctx);
                    return resolve(source, args, ctx, info);
                };
            }
            return fieldConfig;
        },
    });
}
```

## Section 4: Error Handling

**Q8. How does Apollo Server handle errors and what is the difference between `GraphQLError`, `ApolloError`, and HTTP errors?**
A: Apollo Server v4 unified error handling around `GraphQLError` from `graphql-js`. `ApolloError` (from v2/v3) is deprecated — v4 uses `GraphQLError` with an `extensions` object to encode error codes and HTTP status:

```typescript
import { GraphQLError } from 'graphql';

// GraphQLError — the standard way in v4:
throw new GraphQLError('User not found', {
    extensions: {
        code: 'NOT_FOUND',      // machine-readable code for clients
        http: { status: 404 }, // controls the HTTP status code of the response
        // Any additional data you want to expose to clients:
        userFacingMessage: 'The requested user does not exist',
    },
});

// Built-in error codes Apollo Server uses (match these in clients):
// GRAPHQL_PARSE_FAILED     — query string failed to parse
// GRAPHQL_VALIDATION_FAILED — query doesn't match schema
// BAD_USER_INPUT           — invalid arguments (use this for validation errors)
// UNAUTHENTICATED          — not logged in
// FORBIDDEN                — logged in but no permission
// NOT_FOUND                — resource doesn't exist
// INTERNAL_SERVER_ERROR    — unhandled error (default for unexpected throws)

// What the JSON response looks like:
// {
//   "errors": [
//     {
//       "message": "User not found",
//       "locations": [{ "line": 2, "column": 3 }],
//       "path": ["user"],
//       "extensions": {
//         "code": "NOT_FOUND"
//         // Note: http.status is NOT included in the response body — it only
//         // affects the HTTP status code of the response, not the JSON
//       }
//     }
//   ],
//   "data": { "user": null }   ← null for nullable fields; absent for non-nullable
// }

// HTTP status code behaviour:
// Default: GraphQL responses are 200 even with errors (GraphQL spec)
// With http.status in extensions: Apollo Server sets the HTTP status accordingly
// Multiple errors: uses the highest status code among all errors

// formatError — transform errors before sending to client (mask internals):
const server = new ApolloServer({
    schema,
    formatError: (formattedError, error) => {
        // 'error' is the original thrown error (may have stack traces, DB details)
        // 'formattedError' is what Apollo has already prepared for the client

        // Never expose internal error details to clients:
        if (formattedError.extensions?.code === 'INTERNAL_SERVER_ERROR') {
            // Log the real error internally:
            logger.error('Unhandled GraphQL error', { error });
            // Return a sanitized version to the client:
            return {
                message: 'An internal error occurred',
                extensions: { code: 'INTERNAL_SERVER_ERROR' },
            };
        }

        // Validation errors — safe to pass through:
        return formattedError;
    },
});
```

**Q9. How do you handle errors from resolvers consistently across the whole schema?**

```typescript
// Pattern 1: Error wrapper utility — standardize all resolver errors:
import { GraphQLError } from 'graphql';

export class AppError extends Error {
    constructor(
        message: string,
        public readonly code: string,
        public readonly httpStatus: number = 400,
        public readonly meta?: Record<string, unknown>,
    ) {
        super(message);
    }
}

// Convert AppError to GraphQLError in formatError:
const server = new ApolloServer({
    schema,
    formatError: (formattedError, originalError) => {
        if (originalError instanceof AppError) {
            return new GraphQLError(originalError.message, {
                extensions: {
                    code: originalError.code,
                    http: { status: originalError.httpStatus },
                    ...originalError.meta,
                },
            }).toJSON();
        }

        // Unexpected errors — log and mask:
        if (!(originalError instanceof GraphQLError)) {
            logger.error('Unexpected resolver error', { originalError });
            return {
                message: 'Internal server error',
                extensions: { code: 'INTERNAL_SERVER_ERROR' },
            };
        }

        return formattedError;
    },
});

// Pattern 2: Resolver error boundary — wrap all resolvers automatically:
import { mapSchema, MapperKind } from '@graphql-tools/utils';
import { defaultFieldResolver } from 'graphql';

function withErrorBoundary(schema: GraphQLSchema): GraphQLSchema {
    return mapSchema(schema, {
        [MapperKind.OBJECT_FIELD]: (fieldConfig) => {
            const { resolve = defaultFieldResolver } = fieldConfig;
            fieldConfig.resolve = async (...args) => {
                try {
                    return await resolve(...args);
                } catch (err) {
                    if (err instanceof GraphQLError) throw err;  // pass through intentional errors
                    if (err instanceof AppError) {
                        throw new GraphQLError(err.message, {
                            extensions: { code: err.code, http: { status: err.httpStatus } },
                        });
                    }
                    logger.error('Unhandled resolver error', { err, field: args[3].fieldName });
                    throw new GraphQLError('Internal error', {
                        extensions: { code: 'INTERNAL_SERVER_ERROR', http: { status: 500 } },
                    });
                }
            };
            return fieldConfig;
        },
    });
}
```

## Section 5: Plugins and Lifecycle

**Q10. What is the Apollo Server plugin system and what lifecycle events are available?**
A: Plugins are objects that implement lifecycle hooks — they fire at specific points in the request pipeline. Every hook receives context specific to its phase. Hooks can be sync or async:

```typescript
import { ApolloServerPlugin, GraphQLRequestListener } from '@apollo/server';

// Full lifecycle hook order per request:
// serverWillStart              — once at server startup
// renderLandingPage            — once, for GET /graphql (dev only)
// requestDidStart              — every request enters here
//   parsingDidStart            — query string parse begins
//   parsingDidEnd              — parse complete (or failed)
//   validationDidStart         — schema validation begins
//   validationDidEnd           — validation complete (or failed)
//   didResolveOperation        — operation name + type resolved
//   responseForOperation       — (optional) short-circuit with cached response
//   executionDidStart          — resolver execution begins
//     willResolveField         — before each field resolver (expensive — use sparingly)
//     didEncounterErrors       — one or more resolvers threw
//   executionDidEnd            — execution complete
//   willSendResponse           — final response being prepared
//   didEncounterSubsequentErrors — for incremental delivery (@defer / @stream)
// serverWillStop               — on graceful shutdown

// Example: request logging plugin:
const requestLoggingPlugin: ApolloServerPlugin<AppContext> = {
    async requestDidStart({ request, contextValue }) {
        const start = Date.now();
        const operationName = request.operationName ?? 'anonymous';
        const requestId = contextValue.requestId;

        logger.info('GraphQL request started', { operationName, requestId });

        return {
            async parsingDidStart() {
                // Parse phase started
            },

            async didEncounterErrors({ errors }) {
                logger.error('GraphQL errors encountered', {
                    operationName,
                    requestId,
                    errors: errors.map(e => ({
                        message: e.message,
                        path: e.path,
                        code: e.extensions?.code,
                    })),
                });
            },

            async willSendResponse({ response }) {
                const duration = Date.now() - start;
                logger.info('GraphQL request completed', {
                    operationName,
                    requestId,
                    durationMs: duration,
                    hasErrors: !!(response.body.kind === 'single' && response.body.singleResult.errors),
                });
                // Attach timing header:
                response.http.headers.set('X-Response-Time', `${duration}ms`);
            },
        };
    },
};

const server = new ApolloServer({
    schema,
    plugins: [requestLoggingPlugin],
});
```

**Q11. How do you implement a caching plugin that short-circuits execution for repeated queries?**

```typescript
import { ApolloServerPlugin } from '@apollo/server';
import { createHash } from 'crypto';

// Response cache plugin — serves identical queries from Redis:
export function responseCachePlugin(redis: RedisClient): ApolloServerPlugin<AppContext> {
    return {
        async requestDidStart({ request }) {
            // Only cache GET-style queries (not mutations):
            if (request.operationName?.startsWith('Mutation')) {
                return {};
            }

            // Build cache key from query + variables:
            const cacheKey = createHash('sha256')
                .update(JSON.stringify({
                    query: request.query,
                    variables: request.variables,
                    operationName: request.operationName,
                }))
                .digest('hex');

            return {
                async responseForOperation({ response }) {
                    const cached = await redis.get(`gql:${cacheKey}`);
                    if (cached) {
                        // Short-circuit: return cached response, skip resolver execution
                        response.body = {
                            kind: 'single',
                            singleResult: JSON.parse(cached),
                        };
                        response.http.headers.set('X-Cache', 'HIT');
                        return response;  // non-null return short-circuits execution
                    }
                    response.http.headers.set('X-Cache', 'MISS');
                    return null;  // null continues normal execution
                },

                async willSendResponse({ response }) {
                    // Cache the response if it has no errors:
                    if (
                        response.body.kind === 'single' &&
                        !response.body.singleResult.errors &&
                        response.http.headers.get('X-Cache') === 'MISS'
                    ) {
                        await redis.setex(
                            `gql:${cacheKey}`,
                            60,  // TTL 60 seconds
                            JSON.stringify(response.body.singleResult),
                        );
                    }
                },
            };
        },
    };
}
```

**Q12. How do you implement query depth limiting and query complexity analysis in Apollo Server?**
A: Without depth and complexity limits, a client can craft deeply nested or highly expensive queries that DoS your resolvers. Both are implemented via validation rules or plugins:

```typescript
import { ApolloServer } from '@apollo/server';
import depthLimit from 'graphql-depth-limit';
import { createComplexityLimitRule } from 'graphql-validation-complexity';
import { fieldExtensionsEstimator, simpleEstimator, getComplexity } from 'graphql-query-complexity';

// ── Depth limiting ────────────────────────────────────────────────────────────
const server = new ApolloServer({
    schema,
    validationRules: [
        depthLimit(10),  // reject queries nested deeper than 10 levels
        // Example rejected query (depth 11):
        // { loan { borrower { loans { borrower { loans { borrower { ...} } } } } } }
    ],
});

// ── Complexity limiting ───────────────────────────────────────────────────────
// Complexity assigns a cost to each field and rejects queries above a threshold:

const server = new ApolloServer({
    schema,
    plugins: [
        {
            async requestDidStart() {
                return {
                    async didResolveOperation({ request, document }) {
                        const complexity = getComplexity({
                            schema,
                            operationName: request.operationName,
                            query: document,
                            variables: request.variables,
                            estimators: [
                                // Field-level complexity from schema extensions:
                                fieldExtensionsEstimator(),
                                // Default: 1 per field (fallback):
                                simpleEstimator({ defaultComplexity: 1 }),
                            ],
                        });

                        const MAX_COMPLEXITY = 500;
                        if (complexity > MAX_COMPLEXITY) {
                            throw new GraphQLError(
                                `Query complexity ${complexity} exceeds limit ${MAX_COMPLEXITY}`,
                                { extensions: { code: 'QUERY_TOO_COMPLEX', complexity } },
                            );
                        }

                        logger.debug('Query complexity', { complexity });
                    },
                };
            },
        },
    ],
});

// Mark expensive fields in schema extensions:
const resolvers = {
    Query: {
        loans: {
            resolve: (_parent, args, ctx) => ctx.services.loan.findAll(args),
            extensions: { complexity: ({ args }) => (args.limit ?? 10) * 2 },
            // Cost scales with the limit argument
        },
    },
};
```

## Section 6: Introspection, Security, and Production Config

**Q13. What is introspection, why do you disable it in production, and what are the tradeoffs?**
A: Introspection is a built-in GraphQL feature that lets clients query the schema itself (`__schema`, `__type`). It powers GraphQL IDEs, code generators, and client tooling — but in production it exposes your full API surface to attackers:

```typescript
// Development (default — introspection enabled):
const server = new ApolloServer({
    schema,
    // introspection defaults to true in development
    // (when NODE_ENV !== 'production')
});

// Production — disable introspection:
const server = new ApolloServer({
    schema,
    introspection: process.env.NODE_ENV === 'production' ? false : true,
    // Or simply:
    introspection: process.env.ENABLE_INTROSPECTION === 'true',
});

// What attackers do with introspection:
// 1. Map your entire schema — all types, fields, arguments
// 2. Identify fields like deleteUser, transferFunds, adminReset
// 3. Craft targeted queries for those sensitive operations
// 4. Automate with tools like graphql-cop, InQL, clairvoyance

// Tradeoff — disabling introspection breaks:
// - Apollo Sandbox / GraphQL Playground (can't explore schema)
// - graphql-codegen (can't generate client types from server schema)
// - Postman GraphQL schema import

// Solutions when introspection is disabled:
// 1. Publish SDL file to internal registry (Apollo Studio schema registry)
// 2. Use a separate introspection-enabled endpoint behind VPN/auth
// 3. Generate and commit SDL at build time:
import { printSchema } from 'graphql';
import { writeFileSync } from 'fs';
writeFileSync('schema.graphql', printSchema(schema));  // run at build time

// Authenticated introspection (best of both worlds — only devs can introspect):
const server = new ApolloServer({
    schema,
    introspection: true,  // enabled globally
    plugins: [
        {
            async requestDidStart({ request, contextValue }) {
                return {
                    async didResolveOperation({ operation }) {
                        // Block introspection for non-admin users:
                        if (
                            operation.operation === 'query' &&
                            operation.selectionSet.selections.some(
                                s => s.kind === 'Field' && s.name.value.startsWith('__')
                            )
                        ) {
                            if (!contextValue.user?.roles.includes('developer')) {
                                throw new GraphQLError('Introspection not allowed', {
                                    extensions: { code: 'FORBIDDEN' },
                                });
                            }
                        }
                    },
                };
            },
        },
    ],
});
```

**Q14. What is CSRF protection in Apollo Server v4 and how does it work?**
A: Apollo Server v4 enables CSRF prevention by default — it rejects requests that look like they could be cross-site request forgery attacks. The mechanism relies on the fact that browsers can't set custom headers (like `Content-Type: application/json`) in cross-origin requests without a CORS preflight:

```typescript
// Apollo Server v4 CSRF prevention (enabled by default):
// Rejects requests that:
//   1. Are a GET request with a query string (can be triggered by <img src> or <a href>)
//   2. Are a POST with Content-Type: text/plain (can be triggered by HTML form)
//   3. Do not have a Content-Type header

// Safe requests (allowed):
//   POST with Content-Type: application/json   ← standard GraphQL client
//   POST with Content-Type: multipart/form-data ← file uploads
//   Any request with a non-empty Apollo-Require-Preflight header

// Why this works:
//   Browser CORS policy: cross-origin POST with Content-Type: application/json
//   requires a preflight OPTIONS request
//   If your CORS config rejects the preflight from an unauthorized origin,
//   the actual request never reaches Apollo Server

// Configuration:
const server = new ApolloServer({
    schema,
    csrfPrevention: true,      // default in v4
    // csrfPrevention: false,  // disable only if you understand the risk
    // csrfPrevention: {
    //     requestHeaders: ['X-Custom-Header'],  // additional headers that bypass the check
    // },
});

// What you need on the client side (if using Apollo Client):
// apollo-client sets Content-Type: application/json automatically — no action needed

// If you have a custom client or REST client that sends GraphQL:
// Must include: Content-Type: application/json
// Or include:   Apollo-Require-Preflight: true

// Testing: requests that will be rejected with 400 Bad Request:
// fetch('/graphql', { method: 'GET', query: '?query={hello}' })  → rejected
// fetch('/graphql', {
//   method: 'POST',
//   headers: { 'Content-Type': 'text/plain' },
//   body: '{"query":"{hello}"}',
// }) → rejected

// Batched HTTP requests (disabled by default in v4):
const server = new ApolloServer({
    schema,
    allowBatchedHttpRequests: true,  // opt-in only — sends array of operations
});
```

**Q15. How do you configure Apollo Server for production with proper logging, timeouts, and security headers?**

```typescript
import { ApolloServer } from '@apollo/server';
import { expressMiddleware } from '@apollo/server/express4';

                message: 'An internal error occurred',

    crossOriginEmbedderPolicy: isProd,

app.use(
    '/graphql',
    cors<cors.CorsRequest>({
        origin: isProd
            ? ['https://app.yourdomain.com']  // strict allow-list in prod
            : true,                            // allow all in dev
        credentials: true,
    }),
    json({ limit: '1mb' }),  // limit request body size
    expressMiddleware(server, {
        context: async ({ req }) => buildContext(req),
    }),
);

// Graceful shutdown:
process.on('SIGTERM', async () => {
    logger.info('SIGTERM received — shutting down GraphQL server');
    await server.stop();
    process.exit(0);
});
```

## Section 7: Subscriptions and File Uploads

**Q16. How do you add GraphQL subscriptions to Apollo Server?**
A: Apollo Server v4 does not bundle a subscription transport — you add it separately via `graphql-ws` (WebSocket, the current standard) or `subscriptions-transport-ws` (legacy). The subscription server runs alongside HTTP on a separate path:

```typescript
import { ApolloServer } from '@apollo/server';
import { expressMiddleware } from '@apollo/server/express4';
import { createServer } from 'http';
import { WebSocketServer } from 'ws';
import { useServer } from 'graphql-ws/lib/use/ws';
import { makeExecutableSchema } from '@graphql-tools/schema';
import { PubSub } from 'graphql-subscriptions';

const pubSub = new PubSub();
// Note: in-memory PubSub is for development only — use graphql-redis-subscriptions
// or graphql-postgres-subscriptions for multi-instance production deployments

const typeDefs = `#graphql
    type Query { hello: String }
    type Subscription {
        loanStatusChanged(loanId: ID!): LoanStatusEvent!
    }
    type LoanStatusEvent {
        loanId: ID!
        status: String!
        updatedAt: String!
    }
`;

const resolvers = {
    Subscription: {
        loanStatusChanged: {
            // subscribe() returns an AsyncIterator:
            subscribe: (_parent, { loanId }) =>
                pubSub.asyncIterator([`LOAN_STATUS_${loanId}`]),
            // resolve() transforms the event payload (optional):
            resolve: (payload) => payload.loanStatusChanged,
        },
    },
};

const schema = makeExecutableSchema({ typeDefs, resolvers });

// HTTP server (shared between Express and WebSocket server):
const app = express();
const httpServer = createServer(app);

// WebSocket server for subscriptions:
const wsServer = new WebSocketServer({
    server: httpServer,
    path: '/graphql',  // subscriptions and queries share the same path
});

// graphql-ws server setup:
const wsServerCleanup = useServer(
    {
        schema,
        // context for subscriptions (different from HTTP context):
        context: async (ctx, _msg, _args) => {
            // ctx.connectionParams contains auth data sent during WS connection:
            const token = ctx.connectionParams?.Authorization as string;
            const user = token ? await verifyJwt(token.replace('Bearer ', '')) : null;
            return { user, pubSub };
        },
        onConnect: async (ctx) => {
            // Reject unauthorized connections early:
            const token = ctx.connectionParams?.Authorization as string;
            if (!token) return false;  // refuse connection
            return true;
        },
        onDisconnect: (ctx, code, reason) => {
            logger.info('WebSocket disconnected', { code, reason });
        },
    },
    wsServer,
);

// Apollo Server (HTTP):
const apolloServer = new ApolloServer({
    schema,
    plugins: [
        // Proper shutdown — drain WebSocket connections before stopping:
        {
            async serverWillStart() {
                return {
                    async drainServer() {
                        await wsServerCleanup.dispose();
                    },
                };
            },
        },
    ],
});

await apolloServer.start();
app.use('/graphql', cors(), json(), expressMiddleware(apolloServer, {
    context: async ({ req }) => buildContext(req),
}));

// Start the shared HTTP server (serves both HTTP and WebSocket):
await new Promise<void>((resolve) => httpServer.listen(4000, resolve));

// Publishing events from service layer:
await pubSub.publish(`LOAN_STATUS_${loanId}`, {
    loanStatusChanged: { loanId, status: 'APPROVED', updatedAt: new Date().toISOString() },
});
```

**Q17. How do you handle file uploads in Apollo Server v4?**
A: Apollo Server v4 removed built-in multipart upload support. File uploads now require `graphql-upload` as an explicit middleware:

```typescript
import { ApolloServer } from '@apollo/server';
import { expressMiddleware } from '@apollo/server/express4';
import graphqlUploadExpress from 'graphql-upload/graphqlUploadExpress.mjs';
import GraphQLUpload from 'graphql-upload/GraphQLUpload.mjs';

const typeDefs = `#graphql
    scalar Upload

    type Mutation {
        uploadKycDocument(
            loanId: ID!
            documentType: DocumentType!
            file: Upload!
        ): Document!
    }
`;

const resolvers = {
    Upload: GraphQLUpload,  // register the scalar resolver
    Mutation: {
        uploadKycDocument: async (_parent, { loanId, documentType, file }, ctx) => {
            // file is a Promise that resolves to { filename, mimetype, encoding, createReadStream }
            const { filename, mimetype, createReadStream } = await file;

            // Validate file type:
            const allowedTypes = ['image/jpeg', 'image/png', 'application/pdf'];
            if (!allowedTypes.includes(mimetype)) {
                throw new GraphQLError('Invalid file type', {
                    extensions: { code: 'BAD_USER_INPUT' },
                });
            }

            // Stream to storage (S3, GCS, etc.):
            const stream = createReadStream();
            const uploadedUrl = await storageService.upload(stream, {
                filename,
                mimetype,
                path: `loans/${loanId}/kyc/${documentType}`,
            });

            return documentService.create({ loanId, documentType, url: uploadedUrl });
        },
    },
};

// Middleware must be applied BEFORE expressMiddleware:
app.use(
    '/graphql',
    // graphql-upload middleware — processes multipart before Apollo touches the request:
    graphqlUploadExpress({
        maxFileSize: 10_000_000,   // 10MB
        maxFiles: 5,
    }),
    expressMiddleware(server, { context: buildContext }),
);
```

## Section 8: Scenario-Based Questions

**Q18. "Your GraphQL API is experiencing slow responses on some queries. How do you diagnose and add query-level tracing to Apollo Server?"**

```typescript
// Step 1: Enable field-level tracing via willResolveField plugin hook:
// WARNING: willResolveField fires for EVERY field — use only in dev/profiling mode

const tracingPlugin: ApolloServerPlugin<AppContext> = {
    async requestDidStart({ request }) {
        const operationName = request.operationName ?? 'anonymous';
        const traces: Array<{ field: string; duration: number }> = [];
        const requestStart = Date.now();

        return {
            async executionDidStart() {
                return {
                    willResolveField({ info }) {
                        const fieldStart = Date.now();
                        const fieldPath = `${info.parentType.name}.${info.fieldName}`;
                        return (error) => {
                            const duration = Date.now() - fieldStart;
                            if (duration > 10) {   // only log fields taking >10ms
                                traces.push({ field: fieldPath, duration });
                            }
                        };
                    },
                };
            },

            async willSendResponse({ response }) {
                const totalDuration = Date.now() - requestStart;

                // Sort by slowest fields:
                const slowFields = traces
                    .sort((a, b) => b.duration - a.duration)
                    .slice(0, 10);

                logger.info('GraphQL query trace', {
                    operationName,
                    totalDurationMs: totalDuration,
                    slowestFields: slowFields,
                });

                // Attach trace to response extensions (dev only):
                if (process.env.NODE_ENV !== 'production') {
                    if (response.body.kind === 'single') {
                        response.body.singleResult.extensions = {
                            ...response.body.singleResult.extensions,
                            tracing: { duration: totalDuration, slowestFields },
                        };
                    }
                }
            },
        };
    },
};

// Step 2: Identify N+1 via query count logging (TypeORM):
// Add TypeORM query logger that counts queries per request
// If a 50-item list results in 51+ DB calls → N+1 → introduce DataLoader

// Step 3: Apollo Studio (production) — full distributed tracing:
// Add APOLLO_KEY env var + ApolloServerPluginUsageReporting
// Apollo Studio shows per-field latency percentiles, resolver tree, slowest operations
import { ApolloServerPluginUsageReporting } from '@apollo/server/plugin/usageReporting';

const server = new ApolloServer({
    schema,
    plugins: [
        ApolloServerPluginUsageReporting({
            sendVariableValues: { none: true },   // don't send user data to Apollo Studio
            sendHeaders: { onlyNames: ['x-request-id'] },
        }),
    ],
});
```

**Q20. "A client reports that your GraphQL API returns 200 OK even on failed queries, which breaks their error handling. Explain the behavior and how you configure it correctly."**
A: This is expected GraphQL spec behavior — and understanding it precisely is what separates senior candidates from mid-level:

```typescript
// The GraphQL spec says:
// - 200 OK: the request was understood and executed (even if resolvers errored)
// - 400 Bad Request: the request was malformed (parse or validation failed)
// - The response body always contains { data, errors }
// - errors array contains resolver errors alongside partial data

// This is intentional — GraphQL supports partial success:
// { data: { user: { name: "Alice" }, loans: null }, errors: [{ message: "Loans failed" }] }
// The user field succeeded; the loans field failed — partial data is still useful

// Correctly explaining this to a client:

// Response shapes to communicate:
//
// 1. Parse/validation failure (request is invalid):
//    HTTP 400 Bad Request
//    { "errors": [{ "message": "...", "extensions": { "code": "GRAPHQL_PARSE_FAILED" } }] }
//    data field is absent
//
// 2. Resolver error (request valid, execution partially/fully failed):
//    HTTP 200 OK  ← this is what confuses clients
//    { "data": { "loan": null }, "errors": [{ "message": "Loan not found", "path": ["loan"] }] }
//    Client must check for errors even on 200
//
// 3. Full success:
//    HTTP 200 OK
//    { "data": { "loan": { "id": "L1", "amount": 50000 } } }
//    errors field is absent

// If the client insists on HTTP error codes for resolver errors:
// Use the http extension in GraphQLError to control status codes:
throw new GraphQLError('Not found', {
    extensions: {
        code: 'NOT_FOUND',
        http: { status: 404 },  // Apollo Server sets HTTP status to 404
    },
});

// For a "fail-hard" API where any error should return a non-200:
const failHardPlugin: ApolloServerPlugin = {
    async requestDidStart() {
        return {
            async willSendResponse({ response }) {
                if (
                    response.body.kind === 'single' &&
                    response.body.singleResult.errors?.length
                ) {
                    // Override to 500 if any resolver errored and no http status set:
                    const currentStatus = response.http.status ?? 200;
                    if (currentStatus === 200) {
                        response.http.status = 500;
                    }
                }
            },
        };
    },
};

// Best practice — educate clients to check both:
// if (response.status !== 200) { handleHttpError(); }
// else if (response.data?.errors?.length) { handleGraphQLError(); }
// else { handleSuccess(response.data.data); }
```

| Config option | Default | Purpose |
|---|---|---|
| `introspection` | `true` in dev, `false` in prod (when using `NODE_ENV`) | Expose schema to clients |
| `csrfPrevention` | `true` | Block CSRF-style cross-origin requests |
| `includeStacktraceInErrorResponses` | `true` in dev | Stack traces in error extensions |
| `formatError` | Identity | Transform errors before sending to client |
| `allowBatchedHttpRequests` | `false` | Allow array of operations in one HTTP request |
| `validationRules` | Built-in GraphQL rules | Add depth limit, complexity checks |
| `plugins` | `[]` | Lifecycle hooks for logging, caching, tracing |
| `schema` | — | Pre-built `GraphQLSchema` (alternative to `typeDefs` + `resolvers`) |

| Pattern | When to use |
|---|---|
| `startStandaloneServer` | Standalone GraphQL service, no existing Express app |
| `expressMiddleware` | Hybrid REST+GraphQL, existing Express app, custom middleware chain |
| `ApolloServer<AppContext>` generic | Type-safe context throughout resolvers |
| `formatError` | Mask internal errors in production, normalize error shape |
| `http: { status: N }` in extensions | Return non-200 HTTP status for specific errors |
| `willResolveField` plugin | Field-level tracing (dev/profiling only — expensive in prod) |
| `responseForOperation` plugin | Short-circuit with cached response before execution |
| `graphql-ws` | WebSocket subscriptions (current standard — replaces `subscriptions-transport-ws`) |
| `graphql-upload` | File uploads (must be added separately — removed from v4 core) |
| `depthLimit` + complexity | DoS protection against deeply nested or expensive queries |

**Tip for interviews:** Five things separate strong candidates on Apollo Server: (1) knowing the **v4 breaking change** where `context()` moved from the `ApolloServer` constructor to the `expressMiddleware` / `startStandaloneServer` call (Q2, Q6) — getting this wrong in a code sample signals you haven't used v4 in practice; (2) explaining **why GraphQL returns 200 on resolver errors** (Q20) — this is the most common client integration confusion, and being able to articulate partial success semantics and the `http` extension pattern for overriding status codes shows GraphQL spec depth; (3) understanding the **CSRF prevention mechanism** in v4 (Q14) — knowing it's enabled by default, why it works (browsers can't send `Content-Type: application/json` cross-origin without a preflight), and what breaks without it; (4) building out the **plugin lifecycle correctly** (Q10, Q11) — knowing that `requestDidStart` returns an object with per-request hooks, that `responseForOperation` can short-circuit execution with a non-null return, and that `willResolveField` is expensive and should be dev-only; and (5) knowing that **subscriptions are separate from Apollo Server v4 core** (Q16) — `graphql-ws` is the current standard transport, it runs on a `WebSocketServer` that shares the `httpServer`, and the Apollo Server `drainServer` plugin hook is how you tie their lifecycles together for graceful shutdown.
