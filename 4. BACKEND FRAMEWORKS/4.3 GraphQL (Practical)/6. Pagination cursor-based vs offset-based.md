# Pagination: Cursor-Based vs Offset-Based — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is pagination, what problem does it solve, and what are the two main strategies?**

A: Pagination is the practice of returning a subset of a large result set per request, rather than the entire dataset at once. Without it, a query that matches millions of rows would transfer gigabytes of data per request, exhaust server memory assembling the response, and make the client wait tens of seconds before rendering anything.

The two main strategies:

```
OFFSET-BASED (page-number model)
─────────────────────────────────────────────────────────────────────────────
Client: "Give me page 4 of 20 items each"
Server: SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 60;
               ↑ fetch 20 items after skipping the first 60

Analogy: a book with page numbers — you can jump to any page instantly
(conceptually), but the database must "flip through" all prior pages first

CURSOR-BASED (keyset / seek model)
─────────────────────────────────────────────────────────────────────────────
Client: "Give me 20 items after the one with id=abc123"
Server: SELECT * FROM posts WHERE id < 'abc123' ORDER BY id DESC LIMIT 20;
               ↑ fetch 20 items starting from a known position in the index

Analogy: a bookmark — you resume from where you left off without re-reading
all prior pages
```

| Property | Offset-based | Cursor-based |
|---|---|---|
| Navigation | Random access (jump to page 5) | Sequential only (next / prev) |
| Deep page performance | Degrades with offset size | Constant regardless of depth |
| Consistency | Duplicates/gaps on concurrent writes | Stable — unaffected by concurrent writes |
| Total count | Natural (COUNT query) | No inherent total (requires separate query) |
| Implementation complexity | Low | Medium |
| Best fit | Admin tables, small stable datasets | Infinite scroll, feeds, real-time data |

**Q2. Why does every pagination strategy need a deterministic sort order, and what happens without one?**

A: Pagination assumes the result set has a **total order** — a way to split it into non-overlapping, contiguous pages such that every row appears on exactly one page. Without a deterministic sort, the database may return rows in any order it finds convenient (usually heap scan order), and that order can change between queries:

```sql
-- BROKEN: no ORDER BY — rows return in arbitrary, unstable order
SELECT * FROM posts LIMIT 20 OFFSET 20;

-- On the same query a second later, the database might reorganize pages,
-- return a different execution plan, or access rows in a different sequence.
-- Page 2 might include rows already seen on page 1, or skip some entirely.

-- CORRECT: deterministic ORDER BY
SELECT * FROM posts ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 20;
--                                           ↑
--                  'id' as a tiebreaker ensures rows with the same created_at
--                  always appear in the same relative order
```

**The composite sort key requirement:**
If you sort by a non-unique column (like `created_at`), multiple rows can have the same value. Without a tiebreaker, rows with identical `created_at` can appear on different pages or be duplicated depending on how the DB breaks ties internally. Always include a unique column as the final sort key:

```sql
ORDER BY created_at DESC, id DESC
--       ↑ non-unique    ↑ unique tiebreaker — guarantees a total order
```

## Section 2: Offset-Based Pagination

**Q3. How is offset-based pagination implemented in SQL and in TypeORM?**

A:

```sql
-- SQL: explicit LIMIT and OFFSET
-- Page 1 (first 20):
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;

-- Page 2 (next 20):
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 20;

-- Page N:
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET (N - 1) * 20;

-- Total count (for "Page 4 of 47"):
SELECT COUNT(*) FROM posts;
-- On large tables this is a separate, potentially slow query
```

```typescript
// TypeORM — find with skip and take:
async findPage(page: number, pageSize: number): Promise<[Post[], number]> {
  return this.repo.findAndCount({
    skip:  (page - 1) * pageSize,   // OFFSET
    take:  pageSize,                  // LIMIT
    order: { createdAt: 'DESC', id: 'DESC' },
    // findAndCount runs: SELECT ... LIMIT ? OFFSET ?
    //                    SELECT COUNT(*) FROM posts
    // Returns: [items, totalCount]
  });
}

// Response:
const [items, total] = await findPage(4, 20);
return {
  data:       items,
  pagination: {
    page:       4,
    pageSize:   20,
    total,                              // e.g. 934
    totalPages: Math.ceil(total / 20),  // 47
    hasNext:    4 < Math.ceil(total / 20),
    hasPrev:    4 > 1,
  },
};

// TypeORM — Query Builder for more complex cases:
const [items, total] = await this.repo
  .createQueryBuilder('post')
  .leftJoinAndSelect('post.author', 'author')
  .where('post.status = :status', { status: 'published' })
  .orderBy('post.createdAt', 'DESC')
  .addOrderBy('post.id', 'DESC')
  .skip((page - 1) * pageSize)
  .take(pageSize)
  .getManyAndCount();
```

**Q4. What are the three core problems with offset-based pagination?**

A:

**Problem 1 — Phantom records (new rows inserted between pages):**
```
Timeline of events for a client paginating "latest posts first":

Page 1 fetched:  rows 1–20  (posts A, B, C ... T in created_at DESC order)
↓ New post X is inserted — it's now row 1 (newest)
Page 2 fetched:  OFFSET 20 → rows 21–40

But because X is now row 1, all other rows shifted down by one:
  - Former row 20 (post T) is now row 21
  - Page 2 starts at former row 21, but post T is now at row 21 again

Result: post T appears on BOTH page 1 (as row 20) AND page 2 (shifted to row 21)
        — the client sees a duplicate post
```

**Problem 2 — Skipped records (rows deleted between pages):**
```
Page 1 fetched:  rows 1–20  (posts A–T)
↓ Post A is deleted — all rows shift UP by one
Page 2 fetched:  OFFSET 20 → now row 20 is what was row 21

Former row 21 (which the client hasn't seen yet) shifts into the
position of former row 20 (which the client already saw on page 1).
The item at former row 21 is now SKIPPED — the client never sees it.
```

**Problem 3 — Deep offset performance degrades linearly:**
```sql
-- Retrieving page 1 (fast):
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 0;
-- Database reads 20 rows from the index → done

-- Retrieving page 50,000 (slow):
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 999980;
-- Database must traverse 999,980 index entries before returning the first row
-- Cost is O(OFFSET) — linear scan regardless of index presence
```

These three problems make offset pagination fundamentally unsuitable for: high-frequency data (social feeds, real-time logs), large datasets (>100K rows paginated), and infinite-scroll UIs where the client never "jumps" to a page.

**Q5. Why is `COUNT(*)` a problem at scale, and what are the alternatives?**

A: `SELECT COUNT(*) FROM posts WHERE status = 'published'` must visit every row that satisfies the WHERE clause to count them — even with an index. On a 10M-row table with 8M published posts, this is an 8M-row scan:

```sql
-- On PostgreSQL — EXPLAIN ANALYZE reveals the cost:
EXPLAIN ANALYZE SELECT COUNT(*) FROM posts WHERE status = 'published';
-- Seq Scan on posts (cost=0.00..189432.00 rows=8000000 width=0)
--                                    ↑ 189,432 cost units — takes ~2 seconds on warm cache
--                                      and 10+ seconds on cold cache
```

**Alternatives depending on accuracy requirements:**

```sql
-- Option 1: Approximate count from pg_statistics (near-instant, ±1-5% accuracy)
SELECT reltuples::bigint AS approximate_count
FROM pg_class
WHERE relname = 'posts';
-- Returns immediately — updated by ANALYZE (runs automatically)
-- Use for: "about 8 million posts" UI labels where exactness doesn't matter

-- Option 2: Exact count cached in a counter table
CREATE TABLE post_counts (
  status   TEXT PRIMARY KEY,
  count    BIGINT NOT NULL DEFAULT 0
);
-- Increment/decrement via triggers or application logic on INSERT/DELETE
-- Reads are O(1): SELECT count FROM post_counts WHERE status = 'published'
-- Consistent with eventual-consistency acceptable drift

-- Option 3: Omit total count from the API entirely
-- Cursor-based APIs typically don't return totals:
{
  "data": [...],
  "pagination": { "nextCursor": "...", "hasNextPage": true }
  // No 'total' — clients don't show "page 4 of 47", just "Load more"
}

-- Option 4: Materialized view refreshed periodically
CREATE MATERIALIZED VIEW post_count_by_status AS
  SELECT status, COUNT(*) FROM posts GROUP BY status;
-- Refresh hourly: REFRESH MATERIALIZED VIEW CONCURRENTLY post_count_by_status;
```

## Section 3: Cursor-Based Pagination

**Q6. What is cursor-based (keyset) pagination and how does it work mechanically?**

A: Cursor-based pagination uses a **position marker** — the values of the sort columns for the last seen row — as the starting point for the next query. Instead of "skip N rows," it says "find rows where the sort key is less than / greater than this known value":

```sql
-- First page: no cursor — fetch newest 20 posts + 1 to detect hasNextPage
SELECT id, title, created_at
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 21;                              -- Fetch 21, show 20, use 21st to check hasNextPage

-- Results (21 rows): posts A–U in order
-- Last SHOWN row (20th): created_at='2024-01-10', id='1500'
-- Cursor encodes this position: { created_at: '2024-01-10', id: '1500' }

-- Next page: use cursor to find rows that come AFTER position
SELECT id, title, created_at
FROM posts
WHERE (created_at, id) < ('2024-01-10', '1500')
--     ↑ rows whose (created_at, id) tuple is "earlier" than the cursor
ORDER BY created_at DESC, id DESC
LIMIT 21;
```

**How the tuple comparison `(a, b) < (x, y)` works in PostgreSQL:**
```sql
-- (created_at, id) < ('2024-01-10', '1500') means:
--   created_at < '2024-01-10'
--   OR (created_at = '2024-01-10' AND id < '1500')
--
-- This correctly handles the tiebreaker: rows from the same second
-- but with id < 1500 are included; those with id > 1500 are excluded
-- because they were on the previous page

-- The database executes this as an index range scan:
-- Index: (created_at DESC, id DESC)
-- Start at: cursor position (binary search — O(log N))
-- Read forward: 21 rows from that point (O(LIMIT))
-- Total work: O(log N + LIMIT) regardless of how deep into the dataset we are
```

**Q7. What must a cursor encode, and how do you handle multi-column sort keys?**

A: A cursor must encode **all sort key columns** used in the ORDER BY clause, including the unique tiebreaker. Missing any column makes the cursor ambiguous:

```typescript
// For ORDER BY created_at DESC, id DESC:
interface Cursor {
  createdAt: string;  // ISO 8601 timestamp
  id:        string;  // Unique tiebreaker
}

// Encoding: opaque to clients — base64-encoded JSON is the standard
function encodeCursor(createdAt: Date, id: string): string {
  const payload: Cursor = {
    createdAt: createdAt.toISOString(),
    id,
  };
  return Buffer.from(JSON.stringify(payload)).toString('base64url');
  // 'base64url' uses URL-safe characters (no +, /, =) — safe in query strings
}

function decodeCursor(cursor: string): Cursor {
  try {
    const decoded = Buffer.from(cursor, 'base64url').toString('utf-8');
    const parsed  = JSON.parse(decoded) as Cursor;
    // Validate structure before using:
    if (!parsed.createdAt || !parsed.id) throw new Error('Invalid cursor');
    return parsed;
  } catch {
    throw new BadRequestException('Invalid pagination cursor');
  }
}

// Usage:
const lastItem = items[items.length - 1];
const nextCursor = encodeCursor(lastItem.createdAt, lastItem.id);
// Client sends back: GET /posts?after=eyJjcmVhdGVkQXQiOiIyMDI0LTAxLTEwVDAwOjAwOjAwLjAwMFoiLCJpZCI6IjE1MDAifQ
```

**Why cursors should be opaque (base64-encoded, not raw values):**
```typescript
// BAD — exposes internal schema and is brittle to change:
GET /posts?after_created_at=2024-01-10&after_id=1500

// Problems:
// - Reveals database column names
// - Clients might try to construct cursors manually (fragile)
// - Changing sort strategy requires clients to update their parameter parsing
// - Not forward-compatible (can't add sort keys without breaking API)

// GOOD — opaque token, clients treat it as a black box:
GET /posts?after=eyJjcmVhdGVkQXQiOiIyMDI0LTAxLTEwVDAwOjAwOjAwLjAwMFoiLCJpZCI6IjE1MDAifQ

// Benefits:
// - Backend can change the cursor encoding without clients knowing
// - Can add versioning: { v: 2, createdAt: ..., id: ... }
// - Prevents cursor forgery / injection attacks
```

**Q8. How does the "fetch n+1" trick detect `hasNextPage` without an extra COUNT query?**

A: Request one more item than the page size. If you receive `pageSize + 1` items back, there is at least one more page. Return only `pageSize` items to the client and derive `hasNextPage` from the presence of the extra item:

```typescript
async findPage(limit: number, cursor?: string): Promise<PaginatedResult<Post>> {
  const fetchSize = limit + 1;   // Always fetch one extra

  const decoded = cursor ? decodeCursor(cursor) : null;

  const rows = await this.repo.createQueryBuilder('post')
    .where(decoded
      ? '(post.created_at, post.id) < (:createdAt, :id)'
      : '1 = 1',
      decoded ?? {}
    )
    .orderBy('post.created_at', 'DESC')
    .addOrderBy('post.id',         'DESC')
    .limit(fetchSize)
    .getMany();

  // Determine if there's another page BEFORE trimming:
  const hasNextPage = rows.length === fetchSize;

  // Return only 'limit' items — discard the probe item:
  const items = hasNextPage ? rows.slice(0, limit) : rows;

  // Build next cursor from the LAST RETURNED item (not the probe):
  const lastItem  = items[items.length - 1];
  const nextCursor = lastItem && hasNextPage
    ? encodeCursor(lastItem.createdAt, lastItem.id)
    : null;

  return {
    items,
    pageInfo: {
      hasNextPage,
      nextCursor,     // null if this is the last page
      count:  items.length,
    },
  };
}

// Example:
// limit=20, fetchSize=21
// rows.length=21 → hasNextPage=true, return rows[0..19], cursor=encode(rows[19])
// rows.length=17 → hasNextPage=false, return all 17, cursor=null (no more pages)
// rows.length=0  → hasNextPage=false, return [], cursor=null (empty result)
```

## Section 4: Implementation

**Q9. How do you implement cursor pagination in TypeORM with composite sort keys?**

A:

```typescript
// posts.repository.ts
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Post } from './post.entity';

export interface CursorPage<T> {
  items:    T[];
  pageInfo: {
    hasNextPage:     boolean;
    hasPreviousPage: boolean;
    startCursor:     string | null;
    endCursor:       string | null;
  };
}

export interface PostCursor {
  createdAt: string;
  id:        string;
}

@Injectable()
export class PostsRepository {
  constructor(
    @InjectRepository(Post)
    private readonly repo: Repository<Post>,
  ) {}

  async paginate(opts: {
    limit:   number;
    after?:  string;   // Cursor for next page
    before?: string;   // Cursor for previous page
  }): Promise<CursorPage<Post>> {
    const { limit, after, before } = opts;
    const fetchSize = limit + 1;

    const qb = this.repo.createQueryBuilder('p')
      .orderBy('p.created_at', 'DESC')
      .addOrderBy('p.id',         'DESC')
      .limit(fetchSize);

    if (after) {
      const cursor = decodeCursor<PostCursor>(after);
      // Rows that come AFTER the cursor (i.e., older than cursor position):
      qb.where('(p.created_at, p.id) < (:createdAt, :id)', {
        createdAt: cursor.createdAt,
        id:        cursor.id,
      });
    } else if (before) {
      const cursor = decodeCursor<PostCursor>(before);
      // Rows that come BEFORE the cursor (i.e., newer than cursor position):
      // We reverse the order, fetch, then reverse results:
      qb.where('(p.created_at, p.id) > (:createdAt, :id)', {
        createdAt: cursor.createdAt,
        id:        cursor.id,
      })
        .orderBy('p.created_at', 'ASC')   // Reversed order for backward pagination
        .addOrderBy('p.id', 'ASC');
    }

    let rows = await qb.getMany();

    // For backward pagination, reverse the result to get correct DESC order:
    if (before) rows = rows.reverse();

    const hasNextPage     = !before && rows.length === fetchSize;
    const hasPreviousPage = !!before && rows.length === fetchSize;

    const items = rows.length === fetchSize ? rows.slice(0, limit) : rows;

    return {
      items,
      pageInfo: {
        hasNextPage,
        hasPreviousPage,
        startCursor: items.length > 0
          ? encodeCursor(items[0].createdAt, items[0].id)
          : null,
        endCursor: items.length > 0
          ? encodeCursor(items[items.length - 1].createdAt, items[items.length - 1].id)
          : null,
      },
    };
  }
}
```

**Q10. How do you implement cursor pagination in Prisma?**

A: Prisma has first-class cursor support but with important differences from raw SQL:

```typescript
// Prisma's built-in cursor (works on unique fields only):
async paginatePrisma(opts: {
  limit: number;
  cursor?: string;   // Encodes { id: string } for Prisma's id-based cursor
}) {
  const { limit, cursor } = opts;
  const decoded = cursor ? decodeCursor<{ id: string }>(cursor) : null;

  const items = await this.prisma.post.findMany({
    take:    limit + 1,
    cursor:  decoded ? { id: decoded.id } : undefined,
    skip:    decoded ? 1 : 0,   // Skip the cursor item itself (it was on the prev page)
    orderBy: [{ createdAt: 'desc' }, { id: 'desc' }],
    include: { author: true },
  });

  const hasNextPage = items.length === limit + 1;
  const data        = hasNextPage ? items.slice(0, limit) : items;
  const last        = data[data.length - 1];

  return {
    data,
    nextCursor: hasNextPage && last
      ? encodeCursor({ id: last.id })
      : null,
    hasNextPage,
  };
}

// For composite cursor (Prisma doesn't support tuple comparison natively — use $queryRaw):
async paginateComposite(opts: { limit: number; cursor?: string }) {
  const { limit, cursor } = opts;
  const decoded = cursor ? decodeCursor<PostCursor>(cursor) : null;

  const rows = await this.prisma.$queryRaw<Post[]>`
    SELECT id, title, created_at, author_id
    FROM posts
    WHERE ${decoded
      ? Prisma.sql`(created_at, id) < (${new Date(decoded.createdAt)}, ${decoded.id}::uuid)`
      : Prisma.sql`true`
    }
    ORDER BY created_at DESC, id DESC
    LIMIT ${limit + 1}
  `;

  const hasNextPage = rows.length === limit + 1;
  const items = hasNextPage ? rows.slice(0, limit) : rows;
  const last  = items[items.length - 1];

  return {
    items,
    nextCursor: hasNextPage && last
      ? encodeCursor({ createdAt: last.createdAt.toISOString(), id: last.id })
      : null,
    hasNextPage,
  };
}
```

## Section 5: API Design

**Q11. How should you design the paginated response envelope for a REST API?**

A: The envelope must carry enough information for the client to request the next page without knowing the internal implementation:

```typescript
// ── Offset-based envelope ─────────────────────────────────────────────────────
interface OffsetPageResponse<T> {
  data: T[];
  pagination: {
    page:       number;   // Current page (1-indexed)
    pageSize:   number;   // Items per page
    total:      number;   // Total matching rows
    totalPages: number;   // Math.ceil(total / pageSize)
    hasNext:    boolean;
    hasPrev:    boolean;
    // Optional convenience links:
    links?: {
      first?: string;   // '?page=1&pageSize=20'
      prev?:  string;   // '?page=3&pageSize=20'
      next?:  string;   // '?page=5&pageSize=20'
      last?:  string;   // '?page=47&pageSize=20'
    };
  };
}

// ── Cursor-based envelope ─────────────────────────────────────────────────────
interface CursorPageResponse<T> {
  data: T[];
  pagination: {
    limit:           number;        // Requested page size
    nextCursor:      string | null; // null if no next page
    prevCursor:      string | null; // null if no prev page (often omitted in simple APIs)
    hasNextPage:     boolean;
    hasPreviousPage: boolean;
    // Typically omit 'total' — requires expensive COUNT query
  };
}

// Client paginates forward:
GET /api/posts?limit=20
← { data: [...20 posts...], pagination: { nextCursor: "eyJjcm...", hasNextPage: true } }

GET /api/posts?limit=20&after=eyJjcm...
← { data: [...20 posts...], pagination: { nextCursor: "eyJpZC...", hasNextPage: false } }
```

**Query parameter naming conventions:**

```typescript
// Offset-based — common patterns:
?page=4&pageSize=20          // Most common
?page=4&limit=20             // Also common
?offset=60&limit=20          // Explicit byte-offset style (less common in REST)

// Cursor-based — common patterns:
?after=<cursor>&limit=20     // Most common (forward pagination)
?before=<cursor>&limit=20    // Backward pagination
?cursor=<cursor>&direction=next&limit=20   // Explicit direction (verbose)

// Relay-style (GraphQL conventions ported to REST):
?first=20&after=<cursor>     // Forward: first 20 after cursor
?last=20&before=<cursor>     // Backward: last 20 before cursor
```

**Q12. What is the GraphQL Relay cursor connection specification?**

A: The Relay spec defines a standard cursor pagination schema for GraphQL that enables client-side pagination libraries to work with any Relay-compliant API:

```graphql
# The standard Relay connection types:
type PostConnection {
  edges:      [PostEdge!]!
  pageInfo:   PageInfo!
  totalCount: Int   # Optional — expensive; omit for large datasets
}

type PostEdge {
  node:   Post!     # The actual item
  cursor: String!   # Opaque cursor for THIS specific item
}

type PageInfo {
  hasNextPage:     Boolean!  # Are there more items after endCursor?
  hasPreviousPage: Boolean!  # Are there more items before startCursor?
  startCursor:     String    # Cursor of the first item in this page
  endCursor:       String    # Cursor of the last item in this page
}

# Query:
type Query {
  posts(
    first:  Int     # Forward: how many items to return
    after:  String  # Forward: cursor to start after
    last:   Int     # Backward: how many items to return
    before: String  # Backward: cursor to start before
  ): PostConnection!
}
```

```typescript
// NestJS GraphQL implementation of Relay connection:
@ObjectType()
export class PageInfo {
  @Field(() => Boolean) hasNextPage:     boolean;
  @Field(() => Boolean) hasPreviousPage: boolean;
  @Field({ nullable: true }) startCursor?: string;
  @Field({ nullable: true }) endCursor?:   string;
}

@ObjectType()
export class PostEdge {
  @Field(() => Post)   node:   Post;
  @Field(() => String) cursor: string;
}

@ObjectType()
export class PostConnection {
  @Field(() => [PostEdge]) edges:    PostEdge[];
  @Field(() => PageInfo)   pageInfo: PageInfo;
  @Field({ nullable: true }) totalCount?: number;
}

@Resolver()
export class PostsResolver {
  @Query(() => PostConnection)
  async posts(
    @Args('first', { type: () => Int, nullable: true }) first?: number,
    @Args('after', { nullable: true }) after?: string,
  ): Promise<PostConnection> {
    const { items, pageInfo } = await this.postsService.paginate({ limit: first ?? 20, after });

    const edges: PostEdge[] = items.map(item => ({
      node:   item,
      cursor: encodeCursor(item.createdAt, item.id),
    }));

    return {
      edges,
      pageInfo: {
        hasNextPage:     pageInfo.hasNextPage,
        hasPreviousPage: false,   // Simplified — no backward pagination in this example
        startCursor:     edges[0]?.cursor ?? null,
        endCursor:       edges[edges.length - 1]?.cursor ?? null,
      },
    };
  }
}
```

**Q13. What are the tradeoffs of including `total` in a cursor-based pagination response?**

A:

```typescript
// Including total count:
// Pros:
// - "Showing 61–80 of 934 results" — meaningful to users in search/admin contexts
// - Clients can compute progress ("you've seen 8% of results")
// - No UI changes needed vs offset-based APIs

// Cons:
// - Requires a separate COUNT query — potentially seconds on large tables
// - The total can become stale between pages (insertions/deletions)
// - Cursor pagination's main advantage is avoiding this scan

// When to include:
// - Admin panels where users need to know total scope
// - Search results where "N results found" is a primary UX signal
// - Small datasets where COUNT is fast

// When to omit:
// - Infinite scroll UIs (no "page X of Y" concept)
// - Real-time feeds where total changes constantly
// - Tables with millions of rows where COUNT is expensive

// Compromise: provide an estimate instead of exact count
async paginate(opts: PaginateOpts): Promise<PaginatedResult<Post>> {
  const [items, approximateTotal] = await Promise.all([
    this.fetchPage(opts),
    this.getApproximateCount(),   // pg_class.reltuples — O(1)
  ]);
  return {
    items,
    approximateTotal,    // "about 934,000" — no spinner required
    exactTotal: null,    // Would require slow COUNT(*)
  };
}
```

## Section 6: Performance

**Q14. Why is `OFFSET 1000000` slow even with a properly indexed column?**

A: An index on `(created_at DESC, id DESC)` is a B-tree that allows the database to efficiently find a starting position. But `OFFSET N` doesn't mean "start at position N in the B-tree" — it means "find all matching rows in order, then discard the first N":

```sql
EXPLAIN ANALYZE
SELECT * FROM posts ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 1000000;

-- Output (simplified):
-- Limit (cost=47832.56..47833.51 rows=20)
--   -> Index Scan on idx_posts_created_at_id
--        (cost=0.56..478315.60 rows=10000000)
--        Index Cond: ...
--        Rows Removed by Offset: 1000000   ← MUST traverse 1,000,000 entries

-- The database walks the B-tree from the beginning, following 1,000,000 leaf entries
-- BEFORE it can start returning your 20 rows.
-- Each leaf entry may require a separate heap read (if not a covering index).
-- Cost is O(OFFSET) — linear, not logarithmic.
```

```sql
-- Cursor-based equivalent (keyset seek):
EXPLAIN ANALYZE
SELECT * FROM posts
WHERE (created_at, id) < ('2024-01-10', '1500')
ORDER BY created_at DESC, id DESC LIMIT 20;

-- Output (simplified):
-- Limit (cost=0.56..1.72 rows=20)
--   -> Index Scan on idx_posts_created_at_id
--        (cost=0.56..474.23 rows=8278)
--        Index Cond: (created_at < '2024-01-10') OR
--                    (created_at = '2024-01-10' AND id < '1500')
--        ← Binary search to cursor position: O(log N)
--        ← Read 20 rows forward: O(LIMIT)
-- Total: O(log 10000000 + 20) ≈ O(23) — constant regardless of depth
```

The performance difference at page 50,000:

| Approach | Database work | Typical latency |
|---|---|---|
| OFFSET 1,000,000 | Traverse 1M index entries | 500ms–5s |
| Cursor (keyset) | Binary search + read 20 | 1–5ms |

**Q15. What are covering indexes and how do they help pagination queries?**

A: A covering index includes all columns needed to satisfy a query — the database never needs to fetch the actual row from the heap. For pagination, this means all SELECT columns are in the index:

```sql
-- Regular index: only the sort columns
CREATE INDEX idx_posts_basic ON posts (created_at DESC, id DESC);

-- For a query like:
SELECT id, title, author_id, created_at FROM posts
ORDER BY created_at DESC, id DESC LIMIT 20;

-- The database:
-- 1. Scans idx_posts_basic to find 20 (id, created_at) pairs  → index-only scan
-- 2. For each pair, fetches the full row from the heap to get title and author_id
--    → 20 random heap reads (each potentially a separate disk seek)

-- Covering index: includes all projected columns
CREATE INDEX idx_posts_covering ON posts (created_at DESC, id DESC)
INCLUDE (title, author_id);
-- 'INCLUDE' adds payload columns to the leaf pages without affecting B-tree order

-- Now the database:
-- 1. Scans idx_posts_covering to get (id, created_at, title, author_id)  → all in one read
-- 2. No heap access needed — all required data is in the index
-- 20 rows from one contiguous section of the index → no random reads

-- Impact:
-- Non-covering: 20 random heap reads per page fetch
-- Covering:     0 heap reads per page fetch — 10x–100x faster on cold cache
```

**When NOT to use covering indexes:**
- Indexes have write amplification — each INSERT/UPDATE/DELETE must update all covering indexes
- Large `INCLUDE` columns bloat the index size significantly
- For frequently-written tables, measure write throughput impact before adding wide covering indexes

## Section 7: Consistency

**Q16. How do offset and cursor pagination handle concurrent inserts, updates, and deletes?**

A:

```
SCENARIO: A user slowly scrolls through a feed while new posts are being created.

OFFSET PAGINATION:
─────────────────────────────────────────────────────────────────────────────
State at page 1 fetch (sorted by created_at DESC):
  Position 1: Post E (newest)
  Position 2: Post D
  Position 3: Post C  ← page 1 ends here
  ...
  Position 4: Post B  ← page 2 starts here
  Position 5: Post A

↓ User reads page 1. Meanwhile, Post F is created (new position 1).

State at page 2 fetch:
  Position 1: Post F  (new!)
  Position 2: Post E  (shifted down)
  Position 3: Post D  (shifted down)
  Position 4: Post C  (shifted down) ← now at OFFSET 3 — page 2 starts here!
  Position 5: Post B
  Position 6: Post A

Page 2 query: OFFSET 3 → returns [Post C, Post B, Post A]
              Post C was already on page 1 → DUPLICATE seen by user

CURSOR PAGINATION:
─────────────────────────────────────────────────────────────────────────────
Page 1 returns: [Post E, Post D, Post C]
Cursor encodes: { createdAt: C.created_at, id: C.id }

↓ Post F is created.

Page 2 query: WHERE (created_at, id) < (C.created_at, C.id)
              → returns [Post B, Post A]
              Post C's cursor position is fixed in the index.
              New Post F is NEWER than C (created_at > C.created_at),
              so it does NOT appear in the WHERE (created_at < C.created_at) result.
              Post B and A are correctly returned — no duplicates, no gaps.

Note: Post F will NOT appear in the user's current session.
This is correct behavior for "catch up later" UX — the user sees a
consistent snapshot from when they started browsing.
```

**Handling deletes:**
```
OFFSET: If Post D is deleted after page 1 is fetched:
  Position 1: Post E (same)
  Position 2: Post C  (jumped up — D is gone)
  Position 3: Post B  (jumped up)
  Position 4: Post A
Page 2 (OFFSET 3): Returns [Post A] — Post B is SKIPPED

CURSOR: If Post D is deleted after page 1 is fetched:
  Page 2: WHERE (created_at, id) < (C.created_at, C.id)
  → Returns [Post B, Post A] — D's deletion is invisible to the cursor
  Cursor seeks by value comparison, not by position — deletions have no effect
```

## Section 8: When to Use Which

**Q17. How do you decide between offset and cursor pagination for a given use case?**

A:

**Choose offset-based when:**

```typescript
// 1. Users need random access / "jump to page"
//    Admin panel: "Go to page 47" — users expect this for browsing tables
GET /api/admin/users?page=47&pageSize=20

// 2. Small, stable datasets where O(OFFSET) cost is negligible
//    A settings page listing 200 records — OFFSET 180 is trivial

// 3. Sorting by column with high cardinality changes and you need total count
//    "Search results: 934 matching products" — users make decisions based on total

// 4. UI requires "Page X of Y" display
//    Document listing in a CMS where editors navigate by page number

// 5. The dataset is read-heavy and rarely mutated while users browse
//    Historical report data, archived records
```

**Choose cursor-based when:**

```typescript
// 1. Infinite scroll or "Load more" UIs
//    Social feed, comments section, notifications — no page numbers shown
//    Users scroll continuously; consistency between loads is essential

// 2. High-write datasets where concurrent mutations are common
//    Real-time activity feeds, chat history, log viewers
//    New rows constantly inserted — offset would cause duplicates

// 3. Deep pagination (page > 1000)
//    "Export all 10M records" in batches
//    Log analysis tools processing billions of rows

// 4. Ordered by non-count-friendly columns
//    "Trending score" changes every minute — total count would be stale immediately

// 5. External / consumer APIs at scale
//    GitHub, Twitter, Stripe all use cursor pagination for public APIs
//    because clients may page through thousands of results
```

**Hybrid approach — offset for shallow pages, cursor for deep:**

```typescript
// Many production APIs use offset for the first N pages and cursor beyond that:
async paginate(opts: PaginateOpts): Promise<PageResult> {
  const { page, cursor, limit } = opts;

  if (cursor) {
    // Deep pagination — cursor is most efficient
    return this.cursorPage(cursor, limit);
  }

  if (page && page <= 100) {
    // Shallow offset pages — OFFSET < 2000 is fast enough
    return this.offsetPage(page, limit);
  }

  // Page > 100 without cursor — reject or convert to cursor:
  throw new BadRequestException(
    'For pages beyond 100, use cursor pagination. ' +
    'Fetch page 100 first to obtain a cursor, then continue with ?after=<cursor>.'
  );
}
```

**Q18. "Predict what happens when this offset-based pagination code runs against a live feed."**

```typescript
// A mobile app polls every 30 seconds and fetches the next page of notifications:
```

A: Tracing the failure:

```
t=0s:  User opens app. loadNextPage() → page=1
       Fetches notifications 1–20 (newest first)
       currentPage becomes 2

t=30s: 6 new notifications arrive during the pause.
       Now there are 26 new notifications above position 20.

       loadNextPage() → page=2, OFFSET=20
       But positions 1–20 are now the 20 newest notifications (6 new + 14 old)
       Position 21 = what was position 15 thirty seconds ago

       User sees: notifications 15–34 (from the original ordering)
       Notifications 1–14 from the original ordering appear AGAIN
       (they were on page 1, now they're ALSO in page 2's OFFSET range)

t=60s: 6 more new notifications arrive.
       page=3, OFFSET=40 — skips another 12 notifications the user never saw.

Result after 5 minutes:
  - User has seen 12 duplicate notifications
  - User has missed 18 notifications entirely
  - Duplicates appear worse the faster new notifications arrive
  - User has no way to know they're missing anything

CORRECT APPROACH — cursor-based:
  Page 1 returns items with endCursor = encode(createdAt=T, id=N)
  Page 2: WHERE created_at < T OR (created_at = T AND id < N)
  New notifications (created_at > T) NEVER appear in subsequent pages
  No duplicates. No gaps. The session is a consistent snapshot.
```

**Q19. "Design a cursor-based pagination system for a social media feed sorted by a dynamic score."**

A: Social feeds often sort by a "relevance score" that changes in real-time (like count, engagement weighting). This breaks simple cursor approaches because the sort key is mutable:

```typescript
// Challenge: posts have a 'score' column updated by a background job every minute
// ORDER BY score DESC, id DESC
// If post A's score changes between page 1 and page 2:
// - Cursor encoded score=100 for post A
// - After update, post A has score=150 — it's now EARLIER in the result set
// - The cursor WHERE score < 100 no longer includes post A in the right position

// Strategy 1: Snapshot the feed at session start (most consistent)
// Store the ordered list of post IDs at session creation in Redis:
async function createFeedSession(userId: string): Promise<string> {
  const sessionId = randomUUID();

  // Pre-compute the full ordered list once:
  const postIds = await this.db.query<string[]>(`
    SELECT id FROM posts
    WHERE $1 = ANY(audience_user_ids)
    ORDER BY score DESC, id DESC
    LIMIT 1000   -- Cap at 1000 for memory efficiency
  `, [userId]);

  // Store in Redis with TTL:
  await this.redis.set(
    `feed:${sessionId}`,
    JSON.stringify(postIds),
    'EX',
    3600   // 1 hour TTL
  );

  return sessionId;
}

// Cursor is now an index into the Redis list:
async function getPage(sessionId: string, cursor?: string): Promise<FeedPage> {
  const postIdsJson = await this.redis.get(`feed:${sessionId}`);
  if (!postIdsJson) throw new NotFoundException('Feed session expired — start a new session');

  const postIds:  string[] = JSON.parse(postIdsJson);
  const startIdx: number   = cursor ? decodeCursor<{ index: number }>(cursor).index : 0;
  const limit     = 20;

  const pageIds   = postIds.slice(startIdx, startIdx + limit + 1);
  const hasMore   = pageIds.length === limit + 1;
  const returnIds = hasMore ? pageIds.slice(0, limit) : pageIds;

  // Fetch the actual post data (may be stale from cache or fresh from DB):
  const posts = await this.postsService.findByIds(returnIds);

  return {
    posts,
    nextCursor: hasMore
      ? encodeCursor({ index: startIdx + limit })
      : null,
    hasNextPage: hasMore,
  };
}

// Strategy 3: Accept inconsistency for real-time feeds
// Sort by created_at (stable) instead of score for pagination
// Show score-sorted order within each page via client-side sort
// Simple, predictable, explains "sort within window" behavior to users
```

**Q20. "Implement a complete, production-ready cursor pagination module for a NestJS/TypeORM application."**

A:

```typescript
// pagination/cursor.ts — encoding/decoding utilities
import { BadRequestException } from '@nestjs/common';

export function encodeCursor(payload: Record<string, unknown>): string {
  return Buffer.from(JSON.stringify(payload)).toString('base64url');
}

export function decodeCursor<T extends Record<string, unknown>>(cursor: string): T {
  try {
    const json   = Buffer.from(cursor, 'base64url').toString('utf-8');
    const parsed = JSON.parse(json);
    if (typeof parsed !== 'object' || parsed === null) throw new Error();
    return parsed as T;
  } catch {
    throw new BadRequestException(
      'Invalid cursor — cursors are opaque tokens from previous responses'
    );
  }
}

// pagination/page.dto.ts — request DTO

// pagination/page-result.ts — response shape
export interface PageResult<T> {
  data:     T[];
  pageInfo: {
    hasNextPage:     boolean;
    hasPreviousPage: boolean;
    startCursor:     string | null;
    endCursor:       string | null;
    count:           number;   // Items in THIS page
  };
}

// pagination/paginate.helper.ts — generic cursor pagination for any TypeORM entity
import { SelectQueryBuilder } from 'typeorm';

interface PaginateOptions {
  limit:      number;
  after?:     string;
  before?:    string;
  // Column config: what to put in the cursor and how to build the WHERE clause
  sortColumns: Array<{
    alias:     string;  // Query alias: 'p.created_at'
    direction: 'ASC' | 'DESC';
    cursorKey: string;  // Key in the cursor JSON: 'createdAt'
    type:      'timestamp' | 'uuid' | 'int' | 'text';
  }>;
}

export async function paginate<T>(
  qb:   SelectQueryBuilder<T>,
  opts: PaginateOptions,
): Promise<PageResult<T>> {
  const { limit, after, before, sortColumns } = opts;
  const fetchSize = limit + 1;
  const backward  = !!before;
  const cursor    = after
    ? decodeCursor<Record<string, string>>(after)
    : before
    ? decodeCursor<Record<string, string>>(before)
    : null;

  // Apply sort order (reversed for backward pagination):
  for (const col of sortColumns) {
    const direction = backward
      ? (col.direction === 'DESC' ? 'ASC' : 'DESC')
      : col.direction;
    qb.addOrderBy(col.alias, direction);
  }

  // Apply cursor WHERE clause using tuple comparison:
  if (cursor) {
    const operator = backward ? '>' : '<';
    // Build: (a, b) < (x, y)
    const cols   = sortColumns.map(c => c.alias).join(', ');
    const params = sortColumns.map(c => `:${c.cursorKey}`).join(', ');
    const values = Object.fromEntries(
      sortColumns.map(c => [c.cursorKey, cursor[c.cursorKey]])
    );
    qb.andWhere(`(${cols}) ${operator} (${params})`, values);
  }

  const rows = await qb.limit(fetchSize).getMany();

  // Re-order for backward pagination:
  if (backward) rows.reverse();

  const hasExtra         = rows.length === fetchSize;
  const items            = hasExtra ? rows.slice(0, limit) : rows;
  const hasNextPage      = !backward && hasExtra;
  const hasPreviousPage  = backward && hasExtra;

  function buildCursor(item: T): string {
    const payload = Object.fromEntries(
      sortColumns.map(c => {
        const [alias, col] = c.alias.split('.');
        const value = (item as any)[col];
        return [c.cursorKey, value instanceof Date ? value.toISOString() : String(value)];
      })
    );
    return encodeCursor(payload);
  }

  return {
    data: items,
    pageInfo: {
      hasNextPage,
      hasPreviousPage,
      startCursor: items.length > 0 ? buildCursor(items[0])                 : null,
      endCursor:   items.length > 0 ? buildCursor(items[items.length - 1])  : null,
      count:       items.length,
    },
  };
}

// posts.service.ts — using the generic helper
@Injectable()
export class PostsService {
  constructor(
    @InjectRepository(Post)
    private readonly repo: Repository<Post>,
  ) {}

  async findAll(dto: CursorPageDto): Promise<PageResult<Post>> {
    const qb = this.repo
      .createQueryBuilder('p')
      .select(['p.id', 'p.title', 'p.createdAt', 'p.authorId'])
      .where('p.status = :status', { status: 'published' });

      limit:       dto.limit,
      after:       dto.after,
      before:      dto.before,

        { alias: 'p.createdAt', direction: 'DESC', cursorKey: 'createdAt', type: 'timestamp' },
        { alias: 'p.id',        direction: 'DESC', cursorKey: 'id',        type: 'uuid' },
      ],
    });
  }
}
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| **Offset pagination SQL** | `SELECT ... ORDER BY col DESC LIMIT n OFFSET skip` — skip = (page-1) × pageSize |
| **Cursor pagination SQL** | `WHERE (col_a, col_b) < (:a, :b) ORDER BY col_a DESC, col_b DESC LIMIT n+1` |
| **Tuple comparison** | `(a, b) < (x, y)` ↔ `a < x OR (a = x AND b < y)` — handles tiebreakers correctly |
| **Deterministic order** | Every ORDER BY must end with a unique column tiebreaker (usually `id`) — prevents ambiguity |
| **Cursor encoding** | base64url-encoded JSON — opaque to clients, prevents forgery, schema-agnostic |
| **Cursor decoding** | Always validate structure — throw `BadRequestException` for invalid cursors |
| **n+1 trick** | Fetch `limit + 1` rows; if count equals `limit + 1`, `hasNextPage = true`; return only `limit` rows |
| **Phantom records (offset)** | New inserts shift all rows — page 2 contains rows already seen on page 1 |
| **Skipped records (offset)** | Deletes shift rows up — page 2 misses rows that fell into page 1's range |
| **Cursor consistency** | Seeks by value, not position — inserts/deletes after the cursor are invisible to the session |
| **Deep offset cost** | O(OFFSET) — traverse N index entries before returning any rows; degrades linearly |
| **Cursor cost** | O(log N + LIMIT) — binary search to position, then sequential read; constant regardless of depth |
| **Covering index** | `CREATE INDEX ... INCLUDE (col1, col2)` — eliminates heap reads for projected columns |
| **COUNT(*) cost** | Full scan of matching rows — seconds on millions of rows; avoid in cursor APIs |
| **Approximate count** | `SELECT reltuples FROM pg_class WHERE relname = 'table'` — O(1), ±1-5% accuracy |
| **TypeORM offset** | `repo.findAndCount({ skip, take, order })` — returns `[items, total]` |
| **TypeORM cursor** | `createQueryBuilder().where('(a,b)<(:a,:b)', cursor).orderBy().limit(n+1).getMany()` |
| **Prisma cursor** | `findMany({ take: n+1, cursor: { id: cursor.id }, skip: 1, orderBy })` |
| **Relay spec** | `edges[]{node, cursor}` + `pageInfo{hasNextPage, hasPreviousPage, startCursor, endCursor}` |
| **Forward params** | `first: Int, after: String` (Relay) / `limit, after` (REST) |
| **Backward params** | `last: Int, before: String` (Relay) / `limit, before` (REST) |
| **Choose offset** | Admin panels, random-access navigation, small stable datasets, "page X of Y" UI |
| **Choose cursor** | Infinite scroll, real-time feeds, large datasets, consumer APIs, high-write tables |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) explaining the **O(OFFSET) vs O(log N)** cost difference precisely — offset pagination physically traverses all prior index entries before returning the first row of the requested page, while cursor pagination performs a binary search to the cursor position and reads forward; at page 50,000 the difference is the entire index traversal vs 23 comparisons; (2) knowing that **the tiebreaker column is not optional** — sorting by a non-unique column like `created_at` makes the order indeterminate for rows with the same timestamp; without `id` as a final sort key, the same row can appear on both page 1 and page 2 even without concurrent mutations; (3) the **phantom record and skipped record problems** by name — being able to draw the before/after state of the sorted list and show which rows are duplicated vs skipped, and then demonstrating why cursor's value-comparison approach is immune to both; (4) why **cursors must be opaque** — base64-encoding the cursor prevents clients from constructing or manipulating cursor values, hides database column names, and allows the server to change the encoding or add version numbers without breaking existing client code; and (5) the **n+1 detection trick** — fetching one extra row to detect `hasNextPage` without a COUNT query; this is a zero-cost way to paginate without COUNT and is the reason well-designed cursor APIs don't need a `total` field.
