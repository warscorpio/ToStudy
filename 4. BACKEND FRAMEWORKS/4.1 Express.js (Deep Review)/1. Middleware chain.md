# Middleware Chain: `app.use`, `router.use`, Order of Execution in Express.js — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is middleware in Express and what contract does its function signature define?**

A: In Express, middleware is any function that has access to the request object (`req`), the response object (`res`), and the `next` function. The `next` function is a reference to the next middleware in the stack — calling it passes control forward; not calling it terminates the chain for that request.

```typescript
import { Request, Response, NextFunction } from 'express';

// The middleware contract:
type Middleware = (req: Request, res: Response, next: NextFunction) => void;

// A concrete example:
function requestLogger(req: Request, res: Response, next: NextFunction): void {
  console.log(`${new Date().toISOString()} ${req.method} ${req.originalUrl}`);
  next();    // Pass control to the next middleware — required unless sending a response
}

// Middleware can:
// 1. Execute any code
// 2. Mutate req and res objects (attach data, set headers)
// 3. End the request-response cycle (call res.send(), res.json(), res.end(), etc.)
// 4. Call next() to pass control to the next middleware
// 5. Call next(err) to pass to error-handling middleware

// What it MUST NOT do:
// Call both res.send() AND next() — headers already sent error
// Neither send a response NOR call next() — request hangs forever
```

Middleware is the primary composition mechanism in Express. Route handlers are middleware too — `app.get('/users', handler)` is syntactic sugar for mounting a middleware that only activates on `GET /users`.

**Q2. How does Express build and process the middleware stack internally?**

A: Express maintains an ordered array of **Layer** objects. Each Layer encapsulates a path pattern, a flag for whether it is a route handler, and the middleware function. When a request arrives, Express walks this array from top to bottom:

```
Incoming request: GET /api/users/123

Express internal Layer stack (in registration order):
┌─────────────────────────────────────────────────────────┐
│ Layer 0:  path='/', fn=requestLogger      ← app.use()   │
│ Layer 1:  path='/', fn=express.json()     ← app.use()   │
│ Layer 2:  path='/api', fn=apiRouter       ← app.use()   │
│ Layer 3:  path='/health', fn=healthCheck  ← app.get()   │
│ Layer 4:  path='/', fn=errorHandler       ← app.use()   │
└─────────────────────────────────────────────────────────┘

Processing:
1. Layer 0 matches '/' (matches everything) → call requestLogger → next()
2. Layer 1 matches '/' → call express.json() → next()
3. Layer 2 matches '/api' (prefix of '/api/users/123') → call apiRouter
   Inside apiRouter, a sub-stack runs:
   3a. Layer 0: path='/users/:id', fn=authMiddleware → next()
   3b. Layer 1: path='/users/:id', fn=getUserById → res.json(user) → DONE
4. Layer 3: never reached (response already sent)
5. Layer 4: never reached (no error)
```

A critical implication: **registration order determines execution order**. A middleware registered after a route handler that sends a response is never reached for requests that match that route.

## Section 2: `app.use` and Path Matching

**Q3. What is the difference between `app.use` and `app.get`/`app.post`?**

A: The two axes of difference are **path matching strategy** and **HTTP method filtering**:

```typescript
import express from 'express';
const app = express();

// app.use: PREFIX match, ALL HTTP methods
app.use('/api', middleware);
// Matches: GET /api, POST /api/users, DELETE /api/users/123/orders
// Does NOT match: GET /apiv2 (must be a path segment boundary)
// Method-agnostic: matches GET, POST, PUT, DELETE, OPTIONS, HEAD...

// app.get: EXACT pattern match (path-to-regexp), GET only
app.get('/api/users', handler);
// Matches: GET /api/users, GET /api/users/ (trailing slash optional)
// Does NOT match: GET /api/users/123, POST /api/users
// Express uses path-to-regexp for pattern matching — supports params, wildcards, regex

// The practical distinction:
app.use('/static', express.static('./public'));   // All methods, prefix match → correct for serving files
app.get('/users/:id', getUserById);              // GET only, pattern match → correct for route handler

// app.use with no path — matches ALL requests:
app.use(morgan('combined'));   // Equivalent to app.use('/', morgan('combined'))
```

**Path matching table:**

| Registration | Request | Matches? |
|---|---|---|
| `app.use('/api')` | `GET /api` | ✓ |
| `app.use('/api')` | `GET /api/users` | ✓ |
| `app.use('/api')` | `GET /apiv2` | ✗ (must be segment boundary) |
| `app.get('/api')` | `GET /api` | ✓ |
| `app.get('/api')` | `GET /api/users` | ✗ (exact pattern match) |
| `app.get('/api')` | `POST /api` | ✗ (wrong method) |
| `app.use('/api')` | `POST /api` | ✓ (method-agnostic) |

**Q4. How does Express handle URL path stripping when `app.use` matches a prefix?**

A: When `app.use('/prefix', fn)` matches a request, Express temporarily **strips the matched prefix from `req.url`** before calling `fn`. The original URL is preserved in `req.originalUrl`. This is what enables routers to define routes relative to their mount point without knowing where they're mounted:

```typescript
app.use('/api/v1', apiRouter);

// Request: GET /api/v1/users/123

// Inside apiRouter:
apiRouter.get('/users/:id', (req, res) => {
  req.path;         // '/users/123'       ← prefix stripped
  req.url;          // '/users/123'       ← same as path for simple cases
  req.originalUrl;  // '/api/v1/users/123' ← always the full original URL
  req.baseUrl;      // '/api/v1'          ← the matched mount prefix
  req.params.id;    // '123'
});

// This is why apiRouter.get('/users/:id') works — the router
// never sees '/api/v1'; it only sees '/users/:id'.
// You can mount the same router at different prefixes without changing any route definitions.
```

```typescript
// Real-world implication — versioning a single router at two paths:
const usersRouter = createUsersRouter();
app.use('/api/v1/users', usersRouter);  // v1 — router sees '/', '/:id'
app.use('/api/v2/users', usersRouter);  // v2 — same router, different mount point
// Works because the router defines routes relative to '/', not absolute paths
```

## Section 3: The `next()` Function

**Q5. What does calling `next()` do, and what are all the ways the chain can terminate?**

A: `next()` is a callback provided by Express that advances to the next matching Layer in the stack. Every middleware must either call `next()` (to continue the chain) or terminate the request-response cycle by sending a response — otherwise the client connection hangs indefinitely.

```typescript
// All termination paths:

// 1. Send a response — ends the chain
app.get('/a', (req, res) => {
  res.status(200).json({ ok: true });   // res.json calls res.end internally
  // next() is NOT called — chain stops here for this request
});

// 2. Pass to the next middleware
app.use((req, res, next) => {
  req.startTime = Date.now();
  next();   // Continue — next middleware will run
});

// 3. Pass an error to error-handling middleware
app.use(async (req, res, next) => {
  try {
    req.user = await authenticate(req.headers.authorization);
    next();
  } catch (err) {
    next(err);   // Skip all normal middleware; jump to error handler
  }
});

// 4. The chain runs out — 404
// If no middleware sends a response and the stack is exhausted:
// Express sends a default 404 plain-text response
// Override this by adding a catch-all route:
app.use((req, res) => {
  res.status(404).json({ error: `Route ${req.method} ${req.path} not found` });
});
```

**Calling both `res.send()` and `next()` — a common mistake:**
```typescript
// WRONG — causes "Cannot set headers after they are sent to the client" error
app.get('/broken', (req, res, next) => {
  res.json({ data: 'first response' });
  next();   // BUG: continues chain after response is sent — next middleware
            // may try to set headers on an already-closed response
});

// CORRECT — return after sending to prevent further execution
app.get('/correct', (req, res, next) => {
  if (!req.user) {
    return res.status(401).json({ error: 'Unauthorized' });
    // return ensures next() is never accidentally called
  }
  next();
});
```

**Q6. What is `next('route')` and how does it differ from `next()`?**

A: `next('route')` is a special signal that only works within route handlers registered with `app.METHOD` or `router.METHOD`. It skips **all remaining handlers on the current route** and passes control to the **next route** that matches the same path:

```typescript
// Multiple handlers on the same route:
app.get('/users/:id',
  // Handler 1: check if special admin ID
  (req, res, next) => {
    if (req.params.id === 'me') {
      // Skip handler 2 — jump to the next ROUTE matching /users/:id
      return next('route');
    }
    next();   // Continue to handler 2
  },
  // Handler 2: load user by ID (only runs if handler 1 called next(), not next('route'))
  async (req, res, next) => {
    try {
      const user = await User.findById(req.params.id);
      res.json(user);
    } catch (err) {
      next(err);
    }
  }
);

// Next matching route for /users/:id — runs only when next('route') is called above
app.get('/users/:id', (req, res) => {
  // This handles the 'me' case
  res.json(req.currentUser);   // Populated by earlier auth middleware
});
```

**`next()` vs `next('route')` in context:**
```
Stack: [auth middleware] → [route: /users/:id handler1, handler2] → [route: /users/:id handler3]

next():         auth middleware → handler1 → handler2 (stops here, sends response)
next('route'):  auth middleware → handler1 → [SKIPS handler2] → handler3
next(err):      auth middleware → handler1 → [SKIPS all normal] → error handler
```

`next('route')` is useful when you have a catch-all route with specific overrides — the override uses `next('route')` to fall through when its special condition isn't met.

**Q7. What is `next('router')` and when is it needed?**

A: `next('router')` causes the current **router to relinquish control entirely**, passing the request back to the parent application or parent router. It bypasses all remaining middleware and routes within the current router, including error handlers within it:

```typescript
const apiRouter = express.Router();

apiRouter.use((req, res, next) => {
  if (!req.headers['x-api-version']) {
    // This request didn't include the API version header
    // Don't handle it in this router — let the parent decide
    return next('router');
  }
  next();
});

apiRouter.get('/users', getUsersHandler);

app.use('/api', apiRouter);

// Fallback in parent app — catches requests that escaped the router:
app.use('/api', (req, res) => {
  res.status(400).json({ error: 'API version header required' });
});
```

The distinction between `next()`, `next('route')`, and `next('router')`:

| Call | Effect | Use case |
|---|---|---|
| `next()` | Advance to next matching layer | Normal middleware pass-through |
| `next('route')` | Skip remaining handlers on this route | Route-level conditional bypass |
| `next('router')` | Escape current router entirely | Router-level conditional bypass |
| `next(err)` | Jump to nearest error handler | Propagate an error |

## Section 4: Order of Execution

**Q8. How does registration order determine execution, and what are the rules?**

A: Express processes the middleware stack strictly in the order middleware was registered. There is no priority system, no sorting, no dependency resolution — first registered, first executed.

```typescript
const app = express();

// Registration order determines execution order:
app.use(A);              // runs 1st for every request
app.use('/api', B);      // runs 2nd for requests to /api/*
app.get('/api/users', C); // runs 3rd for GET /api/users specifically
app.get('/api/users', D); // runs 4th (after C calls next())
app.use(errorHandler);   // runs last, only if next(err) is called

// For a request GET /api/users:
// A → B → C → D (if C calls next()) → done
// For a request GET /health:
// A → (B skipped, path doesn't match) → (C,D skipped) → 404
```

**Rule: later-registered middleware cannot affect earlier-registered middleware.** This means setup order for certain middleware is non-negotiable:

```typescript
// CORRECT ORDER — each middleware depends on the previous one:
app.use(helmet());                  // 1. Security headers — before anything sets headers
app.use(cors(corsOptions));         // 2. CORS — before routes (handles OPTIONS preflight)
app.use(express.json());            // 3. Body parsing — before any route reads req.body
app.use(express.urlencoded({ extended: true }));
app.use(morgan('combined'));        // 4. Request logging — after body parsed, log full request
app.use(rateLimiter);               // 5. Rate limiting — before auth (save DB calls on rate-limited reqs)
app.use(authenticate);              // 6. Auth — populates req.user before route handlers
app.use('/api/v1', apiRouter);      // 7. Routes — after all global middleware
app.use(notFoundHandler);           // 8. 404 handler — after all routes (catches unmatched requests)
app.use(errorHandler);              // 9. Error handler — last (must be last to catch all errors)
```

**Q9. What are the most common middleware ordering mistakes that cause production bugs?**

A:

**Mistake 1 — Body parser after route that reads `req.body`:**
```typescript
// WRONG:
app.post('/users', (req, res) => {
  console.log(req.body);   // undefined — body hasn't been parsed yet
  res.status(201).json(req.body);
});
app.use(express.json());   // Too late! Route already ran.

// CORRECT:
app.use(express.json());   // Parse body first
app.post('/users', (req, res) => {
  console.log(req.body);   // { name: 'Alice', email: '...' } ✓
  res.status(201).json(req.body);
});
```

**Mistake 2 — CORS after routes (preflight OPTIONS requests never handled):**
```typescript
// WRONG — OPTIONS /api/users returns 404, browser blocks the actual request:
app.use('/api', apiRouter);   // Routes run first
app.use(cors());              // CORS headers never added (response already sent or 404'd)

// CORRECT:
app.use(cors());              // Handles OPTIONS preflight before any routes
app.use('/api', apiRouter);   // Routes run after CORS headers are set
```

**Mistake 3 — Error handler not last:**
```typescript
// WRONG — routes registered after error handler are never reached:
app.use(errorHandler);        // Error handler registered too early
app.get('/users', getUsers);  // This route NEVER executes — handler above catches everything

// CORRECT:
app.get('/users', getUsers);
app.post('/users', createUser);
// ... all routes ...
app.use(notFoundHandler);     // 404 — after all routes
app.use(errorHandler);        // Errors — always last
```

**Mistake 4 — Auth middleware not covering all protected routes:**
```typescript
// WRONG — auth middleware only applies to routes registered after it:
app.get('/public', publicHandler);   // ✓ No auth needed here — correct by accident
app.use(authenticate);               // Auth starts here
app.get('/private', privateHandler); // ✓ Protected

// ADDED LATER by a developer who forgot the order:
app.get('/admin', adminHandler);     // ✓ Protected — registered after auth
// But someone inserts this above authenticate:
app.get('/sensitive', sensitiveHandler);  // ✗ NOT protected — registered before auth!
```

The safer pattern is to mount auth middleware directly on protected routers rather than relying on global registration order:
```typescript
app.use('/public', publicRouter);                // No auth
app.use('/api', authenticate, privateRouter);    // Auth applied inline — cannot be bypassed
app.use('/admin', authenticate, adminCheck, adminRouter);
```

## Section 5: Express Router

**Q10. What is `express.Router()` and what does `router.use` add that `app.use` doesn't?**

A: `express.Router()` creates a mini Express application — a self-contained middleware and routing stack that can be mounted at any path in the parent application. It solves the problem of organizing a large application's routes without cluttering `app`:

```typescript
// Without Router — everything on app (hard to organize, hard to test):
app.use(authForUsers);
app.get('/users', listUsers);
app.get('/users/:id', getUser);
app.post('/users', createUser);
app.use(authForOrders);
app.get('/orders', listOrders);
// ... 50 more routes on app, all in one file

// With Router — each domain has its own isolated router:
// users.router.ts
const usersRouter = express.Router();
usersRouter.use(authForUsers);          // Only applies to users routes
usersRouter.get('/', listUsers);        // Relative to mount point
usersRouter.get('/:id', getUser);
usersRouter.post('/', createUser);
export default usersRouter;

// orders.router.ts
const ordersRouter = express.Router();
ordersRouter.use(authForOrders);
ordersRouter.get('/', listOrders);
export default ordersRouter;

// app.ts
app.use('/users', usersRouter);    // Mount at /users
app.use('/orders', ordersRouter);  // Mount at /orders
```

**`router.use` vs `app.use`:**
- Both register middleware on a layer stack
- `router.use` registers on the **router's** stack — only affects requests that reach this router
- `app.use` registers on the **application's** stack — affects all requests (or all matching a path)
- A Router's middleware stack is completely isolated: auth registered on `usersRouter` never runs for `ordersRouter`, even if mounted under the same prefix

```typescript
// Isolation demonstration:
const aRouter = express.Router();
const bRouter = express.Router();

aRouter.use(logForA);    // Only runs for requests handled by aRouter
bRouter.use(logForB);    // Only runs for requests handled by bRouter

app.use('/a', aRouter);  // GET /a/* → logForA runs
app.use('/b', bRouter);  // GET /b/* → logForB runs (logForA does NOT run)
```

**Q11. How does the middleware stack flow through nested routers?**

A: When a Router is mounted with `app.use('/prefix', router)`, the application's Layer stack contains a single Layer for the router. When that Layer matches, Express transfers control into the router's own internal Layer stack. The two stacks are distinct, but `next()` inside the router eventually returns control to the parent app's stack:

```typescript
// Nested router stack visualization:
app.use(globalLogger);           // App stack: Layer 0
app.use(express.json());         // App stack: Layer 1
app.use('/api', apiRouter);      // App stack: Layer 2 → contains apiRouter

apiRouter.use(apiLogger);        // apiRouter stack: Layer 0
apiRouter.use(authenticate);     // apiRouter stack: Layer 1
apiRouter.use('/users', usersRouter);  // apiRouter stack: Layer 2 → usersRouter

usersRouter.get('/', listUsers);        // usersRouter stack: Layer 0
usersRouter.get('/:id', getUser);       // usersRouter stack: Layer 1

// For request: GET /api/users/123
//
// App stack:
//   globalLogger → next()
//   express.json() → next()
//   Layer 2 matches '/api' → enter apiRouter
//
// apiRouter stack:
//   apiLogger → next()
//   authenticate → next() (populates req.user)
//   Layer 2 matches '/users' → enter usersRouter
//
// usersRouter stack:
//   Layer 0: '/' does NOT match '/123' after stripping '/users' → skip
//   Layer 1: '/:id' matches '/123' → getUser handler → res.json(user) → DONE
```

When `next()` is called in a router and no further layers in that router match, control returns to the parent router's stack, then to the app stack. This "bubble up" behavior is what makes `next('router')` useful — it skips the rest of the current router and forces the bubble-up immediately.

## Section 6: Error-Handling Middleware

**Q12. What is error-handling middleware and how does Express identify it?**

A: Express identifies error-handling middleware by a function's **arity** (number of declared parameters): an error handler has **exactly four parameters** — `(err, req, res, next)`. Express reads `.length` on the function at registration time:

```typescript
// Normal middleware — 3 parameters:
app.use((req, res, next) => {   // .length === 3 → normal middleware
  next();
});

// Error-handling middleware — 4 parameters:
app.use((err, req, res, next) => {   // .length === 4 → error handler
  console.error(err);
  res.status(500).json({ error: err.message });
});

// IMPORTANT: all 4 parameters must be declared even if you don't use next:
// This is WRONG — Express sees .length === 3 and treats it as normal middleware:
app.use((err, req, res) => {         // .length === 3 → NOT an error handler!
  res.status(500).json({ error: err.message });
});

// TypeScript: use the explicit ErrorRequestHandler type to enforce the signature:
import { ErrorRequestHandler } from 'express';
const errorHandler: ErrorRequestHandler = (err, req, res, next) => {
  // TypeScript enforces 4 parameters — can't accidentally drop next
  res.status(err.status ?? 500).json({ error: err.message });
};
```

**Q13. How does an error propagate through the middleware chain once `next(err)` is called?**

A: Calling `next(err)` with any argument other than `'route'` or `'router'` causes Express to skip all remaining **normal** middleware (3-parameter) in the stack and jump to the first matching **error-handling** middleware (4-parameter). Normal middleware registered after the error point is bypassed entirely:

```typescript
app.use(requestLogger);              // Normal — runs for all requests
app.use(express.json());             // Normal — parses body

app.get('/users/:id', async (req, res, next) => {
  try {
    const user = await db.users.findById(req.params.id);
    if (!user) {
      const err = new Error('User not found');
      (err as any).status = 404;
      return next(err);   // ← JUMPS past the two middleware below
    }
    res.json(user);
  } catch (err) {
    next(err);   // ← Also jumps past everything to error handler
  }
});

app.use(someOtherNormalMiddleware);  // SKIPPED when next(err) was called above
app.use(anotherNormalMiddleware);    // SKIPPED

// ↓ Error jumps here:
app.use((err: any, req: Request, res: Response, next: NextFunction) => {
  const status = err.status ?? 500;
  res.status(status).json({
    error: err.message,
    ...(process.env.NODE_ENV === 'development' && { stack: err.stack }),
  });
});
```

**Chaining multiple error handlers:**
You can have multiple error handlers for different error categories. Each can call `next(err)` to pass to the next error handler:

```typescript
// Specialized error handler for DB errors:
app.use((err: any, req: Request, res: Response, next: NextFunction) => {
  if (err.code === 'SQLITE_CONSTRAINT') {
    return res.status(409).json({ error: 'Duplicate entry' });
  }
  next(err);   // Not a DB error — pass to the next error handler
});

// Specialized handler for validation errors:
app.use((err: any, req: Request, res: Response, next: NextFunction) => {
  if (err.name === 'ValidationError') {
    return res.status(422).json({ error: err.message, fields: err.fields });
  }
  next(err);
});

// Catch-all fallback — must be last:
app.use((err: any, req: Request, res: Response, next: NextFunction) => {
  console.error('Unhandled error:', err);
  res.status(500).json({ error: 'Internal server error' });
});
```

**Q14. What is the difference between synchronous and asynchronous error handling in Express, and what changed in Express 5?**

A: Express 4 only automatically catches synchronous errors thrown in middleware. Errors from async functions must be explicitly caught and passed to `next(err)`:

```typescript
// Express 4: synchronous throw — caught automatically:
app.get('/sync', (req, res) => {
  throw new Error('Sync error');   // Express catches this and calls next(err)
});

// Express 4: async error — NOT caught automatically:
app.get('/async', async (req, res, next) => {
  const user = await db.findUser(req.params.id);  // If this rejects, Express 4 doesn't catch it
  res.json(user);
  // → Unhandled Promise Rejection — process may crash in Node.js < v15
});

// Express 4: correct async pattern — explicit try/catch:
app.get('/async-correct', async (req, res, next) => {
  try {
    const user = await db.findUser(req.params.id);
    res.json(user);
  } catch (err) {
    next(err);   // Manually forwarded to error handler
  }
});

// Express 4: utility wrapper to avoid try/catch boilerplate:
const asyncHandler = (fn: Function) => (req: Request, res: Response, next: NextFunction) =>
  Promise.resolve(fn(req, res, next)).catch(next);

app.get('/users/:id', asyncHandler(async (req, res) => {
  const user = await db.findUser(req.params.id);   // Rejection → next(err) automatically
  res.json(user);
}));
```

**Express 5 (released 2024):** Automatically handles async errors. Any middleware can be an `async` function, and any rejected promise is automatically forwarded to error-handling middleware:

```typescript
// Express 5: async works natively — no asyncHandler wrapper needed:
app.get('/users/:id', async (req, res) => {
  const user = await db.findUser(req.params.id);   // Rejection → automatically next(err)
  if (!user) throw new NotFoundError('User not found');   // Throw → automatically next(err)
  res.json(user);
});
```

## Section 7: Composition Patterns

**Q15. How do you compose multiple middleware functions for a single route?**

A: Express route methods accept multiple middleware as variadic arguments or as arrays. All forms are equivalent — they're flattened into the same layer stack:

```typescript
// Form 1: Variadic arguments — most common
app.get('/admin/users',
  authenticate,          // Must be logged in
  requireRole('admin'),  // Must be admin
  validateQuery(schema), // Query params must be valid
  listUsers              // Final handler
);

// Form 2: Array — useful when composing programmatically
const adminGuard = [authenticate, requireRole('admin')];
app.get('/admin/users', adminGuard, validateQuery(schema), listUsers);
app.get('/admin/posts', adminGuard, validateQuery(postSchema), listPosts);
// adminGuard is reused across multiple routes

// Form 3: router.use — applies to all routes on the router
const adminRouter = express.Router();
adminRouter.use(authenticate);         // Runs for every admin route
adminRouter.use(requireRole('admin')); // Runs for every admin route
adminRouter.get('/users', listUsers);  // Only route-specific logic here
adminRouter.get('/posts', listPosts);

// Form 4: inline factory functions returning middleware
function requireRole(role: string) {
  return (req: Request, res: Response, next: NextFunction) => {
    if (!req.user?.roles.includes(role)) {
      return res.status(403).json({ error: `Role '${role}' required` });
    }
    next();
  };
}

// Combining: route-level composition vs router-level composition
// Route-level: specific middleware for one route
app.get('/users/:id/profile', authenticate, cacheFor(300), getUserProfile);

// Router-level: middleware shared across all routes on a router
const privateRouter = express.Router();
privateRouter.use(authenticate);
privateRouter.get('/profile', getUserProfile);   // authenticate always runs before this
privateRouter.get('/settings', getSettings);     // and before this
```

**Q16. What is `router.param()` and how does it reduce repetitive middleware?**

A: `router.param(name, callback)` registers a callback that fires automatically whenever a route on this router contains the named parameter. It runs **before** the route handler, allowing you to load a resource once and attach it to `req` rather than repeating the lookup in every handler:

```typescript
const usersRouter = express.Router();

// Without router.param — repetitive lookup in every handler:
usersRouter.get('/:userId', async (req, res, next) => {
  try {
    const user = await User.findById(req.params.userId);
    if (!user) return res.status(404).json({ error: 'User not found' });
    res.json(user);
  } catch (err) { next(err); }
});

usersRouter.patch('/:userId', async (req, res, next) => {
  try {
    const user = await User.findById(req.params.userId);   // Same lookup again!
    if (!user) return res.status(404).json({ error: 'User not found' });
    await user.update(req.body);
    res.json(user);
  } catch (err) { next(err); }
});

// With router.param — centralized, runs once per request per param:
usersRouter.param('userId', async (req, res, next, id) => {
  //                                                  ↑ the actual value of :userId
  try {
    const user = await User.findById(id);
    if (!user) return res.status(404).json({ error: 'User not found' });
    req.targetUser = user;   // Attach to request — available in all subsequent handlers
    next();
  } catch (err) { next(err); }
});

usersRouter.get('/:userId', (req, res) => {
  res.json(req.targetUser);   // Already loaded — no DB call here
});

usersRouter.patch('/:userId', async (req, res, next) => {
  try {
    await req.targetUser.update(req.body);   // Already loaded
    res.json(req.targetUser);
  } catch (err) { next(err); }
});

usersRouter.delete('/:userId', async (req, res, next) => {
  try {
    await req.targetUser.delete();
    res.status(204).end();
  } catch (err) { next(err); }
});

// router.param callback signature: (req, res, next, paramValue)
// It fires once per request, even if the same param appears in multiple routes
// It only fires for THIS router — app.param() is separate
```

## Section 8: Built-in and Common Middleware

**Q17. What built-in middleware does Express provide, and what are their ordering requirements?**

A: Express v4.16+ includes several built-in middleware functions that were previously in the separate `body-parser` and `serve-static` packages:

```typescript
// express.json() — parse application/json request bodies
// Must come BEFORE any route that reads req.body
app.use(express.json({
  limit: '1mb',           // Max body size (default: 100kb)
  strict: true,           // Only accept arrays and objects (not primitives)
  type: 'application/json',
}));

// express.urlencoded() — parse application/x-www-form-urlencoded bodies
app.use(express.urlencoded({
  extended: true,         // Use qs library (supports nested objects)
  limit: '1mb',
}));

// express.raw() — parse body as a Buffer (useful for webhook signature verification)
app.post('/webhooks/stripe',
  express.raw({ type: 'application/json' }),   // Must be raw Buffer for signature check
  (req, res) => {
    const sig = req.headers['stripe-signature'];
    const event = stripe.webhooks.constructEvent(req.body, sig, secret);
    // req.body is a Buffer here, not parsed JSON
  }
);

// express.text() — parse body as a plain string
app.use(express.text({ type: 'text/plain' }));

// express.static() — serve static files from a directory
// Should be early in the chain — before auth, before logging heavy middleware
// Static files don't need authentication; add performance by not running middleware for them
app.use(express.static(path.join(__dirname, 'public'), {
  maxAge: '1d',           // Cache-Control: max-age
  etag: true,             // ETag support for conditional requests
  index: 'index.html',    // Default file for directory requests
  dotfiles: 'ignore',     // Don't serve .gitignore, .env, etc.
}));

// Ordering note: express.static before auth allows public file serving:
app.use(express.static('./public'));   // No auth needed — public assets
app.use(authenticate);                 // Auth only for API routes below
app.use('/api', apiRouter);
```

**Q18. How does CORS middleware interact with the preflight request, and why must it come first?**

A: CORS (Cross-Origin Resource Sharing) works via two distinct mechanisms: simple requests get `Access-Control-Allow-Origin` headers added to the response, while non-simple requests (POST with JSON body, custom headers, DELETE, etc.) trigger a **preflight** — an automatic `OPTIONS` request the browser sends before the real request:

```typescript
import cors from 'cors';

const corsOptions = {
  origin: ['https://app.example.com', 'https://admin.example.com'],
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  credentials: true,        // Allow cookies / Authorization header
  maxAge: 86400,            // Cache preflight for 24h (reduces preflight requests)
};

// CORRECT — CORS before everything else:
app.use(cors(corsOptions));   // Handles OPTIONS preflight AND adds headers to all responses

// What the CORS middleware does for a preflight OPTIONS request:
// 1. Checks if the Origin header is in the allowed list
// 2. Responds with 204 No Content + the Access-Control headers
// 3. Does NOT call next() — terminates the request (preflight is handled)
//
// What it does for a normal request:
// 1. Adds Access-Control-Allow-Origin (and other headers) to res
// 2. Calls next() — continues to routes

// If CORS comes after routes:
app.get('/api/users', getUsers);  // Route responds — CORS headers never added!
app.use(cors(corsOptions));       // Never reached for matched routes
// Browser sees the response but with no CORS headers → blocks it

// Route-specific CORS (for public endpoints that need different CORS than the API):
app.get('/public/data', cors({ origin: '*' }), publicDataHandler);
```

## Section 9: Scenario-Based Questions

**Q19. "Predict the behavior of each request against this Express application."**

```typescript
const app = express();

app.use((req, res, next) => {
  req.log = [];
  req.log.push('MW1');
  next();
});

app.use('/api', (req, res, next) => {
  req.log.push('MW2');
  next();
});

app.get('/api/users', (req, res, next) => {
  req.log.push('R1a');
  next();
}, (req, res) => {
  req.log.push('R1b');
  res.json(req.log);
});

app.get('/api/users', (req, res) => {
  req.log.push('R2');
  res.json(req.log);
});

app.use((err: any, req: Request, res: Response, next: NextFunction) => {
  res.status(500).json({ error: err.message, log: req.log });
});
```

A: Tracing each request:

**`GET /api/users`:**
```
MW1 runs → req.log = ['MW1']
MW2 runs ('/api' prefix matches) → req.log = ['MW1', 'MW2']
R1a runs → req.log = ['MW1', 'MW2', 'R1a'] → calls next()
R1b runs → req.log = ['MW1', 'MW2', 'R1a', 'R1b'] → res.json(['MW1','MW2','R1a','R1b'])
R2 never runs — R1b sent the response
Response: ["MW1", "MW2", "R1a", "R1b"]
```

**`GET /api/posts`:**
```
MW1 runs → req.log = ['MW1']
MW2 runs ('/api' matches '/api/posts') → req.log = ['MW1', 'MW2']
R1 does NOT match (path is '/api/posts', not '/api/users')
R2 does NOT match (same reason)
No route handled it → Express default 404 plain-text response
req.log is never sent — 404 response: "Cannot GET /api/posts"
```

**`GET /health`:**
```
MW1 runs → req.log = ['MW1']
MW2 does NOT run ('/api' does not match '/health')
No routes match → Express default 404
Response: "Cannot GET /health"
```

**What if R1a called `next('route')` instead of `next()`?**
```
MW1 → MW2 → R1a (calls next('route')) → [R1b skipped] → R2 runs
req.log = ['MW1', 'MW2', 'R1a', 'R2']
Response: ["MW1", "MW2", "R1a", "R2"]
```

**Q20. "Design the complete middleware chain for a production REST API with authentication, rate limiting, request validation, and centralized error handling."**

A:

```typescript
import express from 'express';
import helmet from 'helmet';
import cors from 'cors';
import morgan from 'morgan';
import rateLimit from 'express-rate-limit';

const app = express();

// ── LAYER 1: Infrastructure / Security Headers ──────────────────────────────
// These run before everything — they set up the response environment
app.use(helmet());          // Sets X-Frame-Options, HSTS, CSP, etc.
app.use(cors({
  origin: process.env.ALLOWED_ORIGINS?.split(',') ?? [],
  credentials: true,
}));                        // Must precede routes to handle OPTIONS preflight

// ── LAYER 2: Request Parsing ──────────────────────────────────────────────
// Must run before any middleware or route that reads req.body
app.use(express.json({ limit: '1mb' }));
app.use(express.urlencoded({ extended: true, limit: '1mb' }));

// ── LAYER 3: Observability ───────────────────────────────────────────────
// After body parsing so we can log body size; before auth so we log all requests
app.use(morgan('combined'));
app.use((req, res, next) => {
  req.id = crypto.randomUUID();   // Attach request ID for tracing
  res.setHeader('X-Request-Id', req.id);
  next();
});

// ── LAYER 4: Rate Limiting ───────────────────────────────────────────────
// Before auth — rate limiting stops bots before they hit the DB at all
app.use('/api', rateLimit({
  windowMs: 15 * 60 * 1000,     // 15 minutes
  max: 100,                       // 100 requests per window per IP
  standardHeaders: true,          // Return rate limit info in RateLimit-* headers
  legacyHeaders: false,
  handler: (req, res) => {
    res.status(429).json({ error: 'Too many requests — try again later' });
  },
}));

// ── LAYER 5: Authentication (global check — sets req.user) ───────────────
// Runs before all API routes; doesn't reject — leaves that to authorization
app.use('/api', async (req, res, next) => {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) { return next(); }   // Allow unauthenticated — routes decide if auth is required
  try {
    req.user = await verifyJWT(token);
    next();
  } catch {
    next();   // Invalid token — req.user stays undefined; route decides response
  }
});

// ── LAYER 6: Routes (Routers) ────────────────────────────────────────────
// Each router handles its own authorization checks
import { authRouter }  from './routes/auth.router';
import { usersRouter } from './routes/users.router';
import { postsRouter } from './routes/posts.router';

app.use('/api/auth', authRouter);
app.use('/api/users', requireAuth, usersRouter);  // requireAuth inline — explicit, visible
app.use('/api/posts', requireAuth, postsRouter);

// requireAuth middleware (used inline — not global, so routes can see it clearly):
function requireAuth(req: Request, res: Response, next: NextFunction): void {
  if (!req.user) {
    res.status(401).json({ error: 'Authentication required' });
    return;
  }
  next();
}

// ── LAYER 7: 404 Handler (after all routes) ──────────────────────────────
app.use((req: Request, res: Response) => {
  res.status(404).json({
    error: `Route ${req.method} ${req.path} not found`,
    requestId: req.id,
  });
});

// ── LAYER 8: Error Handler (always last) ─────────────────────────────────
// Four parameters — Express identifies this as the error handler
app.use((err: any, req: Request, res: Response, next: NextFunction) => {
  // Log with request context
  console.error({
    requestId: req.id,
    method: req.method,
    path: req.path,
    error: err.message,
    stack: err.stack,
  });

  // Distinguish operational errors (expected) from programmer errors (bugs):
  const status = err.status ?? err.statusCode ?? 500;
  const isOperational = status < 500;

  res.status(status).json({
    error: isOperational ? err.message : 'Internal server error',
    requestId: req.id,
    // Stack trace only in development:
    ...(process.env.NODE_ENV === 'development' && { stack: err.stack }),
  });
});

// Inside a router — example of consistent error propagation pattern:
// routes/users.router.ts
const usersRouter = express.Router();

// router.param — centralized user loading for all /:userId routes
usersRouter.param('userId', async (req, res, next, id) => {
  try {
    const user = await User.findById(id);
    if (!user) {
      const err = Object.assign(new Error('User not found'), { status: 404 });
      return next(err);
    }
    req.targetUser = user;
    next();
  } catch (err) { next(err); }
});

usersRouter.get('/', asyncHandler(async (req, res) => {
  const users = await User.findAll({ limit: 50 });
  res.json({ data: users });
}));

usersRouter.get('/:userId', (req, res) => {
  res.json({ data: req.targetUser });  // Loaded by router.param
});

usersRouter.patch('/:userId', asyncHandler(async (req, res) => {
  await req.targetUser.update(req.body);
  res.json({ data: req.targetUser });
}));
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| Middleware signature | `(req, res, next) => void` — must call `next()` OR send a response, never both |
| Error handler signature | `(err, req, res, next) => void` — exactly 4 params; Express reads `.length` to identify it |
| `app.use(path, fn)` | Prefix path match, all HTTP methods; path defaults to `'/'` |
| `app.get(path, fn)` | Exact pattern match (path-to-regexp), GET only |
| Registration order | Strictly top-to-bottom; first registered = first executed; no exceptions |
| `next()` | Advance to next matching Layer in the current stack |
| `next(err)` | Skip all normal middleware; jump to nearest error-handling middleware |
| `next('route')` | Skip remaining handlers on the current route; pass to next matching route |
| `next('router')` | Escape current router entirely; return control to parent stack |
| Path stripping | `app.use('/api', router)` strips `/api` from `req.url` before calling router; `req.originalUrl` is unchanged |
| `req.baseUrl` | The matched mount prefix (e.g., `/api/v1`) — useful inside mounted routers |
| `req.originalUrl` | Always the full original URL — never modified by Express |
| `express.Router()` | Mini Express app with isolated middleware stack; can be mounted at any path |
| `router.use()` | Same as `app.use()` but scoped to the router's stack only |
| `router.param(name, cb)` | Callback fires when `:name` appears in a matched route; runs before route handler; centralizes resource loading |
| Express.json() ordering | Must be before any route that reads `req.body` |
| CORS ordering | Must be before routes to handle `OPTIONS` preflight requests |
| Auth ordering | After body parsing, before protected routes; use inline for clarity |
| Error handler ordering | Always last — after all routes and the 404 handler |
| `next('route')` scope | Only valid in route handlers (`app.METHOD`/`router.METHOD`), not in `app.use` middleware |
| Async errors (Express 4) | Must be caught explicitly: `try/catch + next(err)` or `asyncHandler` wrapper |
| Async errors (Express 5) | Handled natively — rejected promises automatically call `next(err)` |
| Double response | Calling `res.send()` then `next()` (or `next()` then `res.send()` downstream) causes `ERR_HTTP_HEADERS_SENT` — always `return res.send()` |
| Empty `next()` call | No argument = proceed normally; `'route'` = skip route handlers; `'router'` = escape router; anything else = error |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) understanding that Express's middleware stack is just an **ordered array of Layer objects** walked top-to-bottom, and that this makes registration order the single most important rule in Express architecture — every ordering mistake (body parser after routes, CORS after routes, error handler not last) is a consequence of forgetting this; (2) explaining the **three flavors of `next()`** precisely — `next()` advances normally, `next('route')` skips the current route's remaining handlers (only in `app.METHOD`, not `app.use`), and `next('router')` escapes the current router entirely — and knowing that anything else passed to `next()` is treated as an error; (3) the **four-parameter signature** for error handlers — Express identifies error middleware by arity (function `.length`), not by name or decorator, which means a dropped `next` parameter silently converts an error handler into a normal middleware that never fires for errors; (4) **path stripping** with `app.use('/prefix', router)` — the prefix is stripped from `req.url` inside the router (enabling path-relative route definitions), but `req.originalUrl` always has the full path, and `req.baseUrl` has the matched prefix — this is what enables the same router to be mounted at multiple paths without modifying its route definitions; and (5) the difference between **router-level isolation** and global `app.use` — middleware registered on a Router only runs for requests that reach that router, which is why `router.use(authenticate)` is safer and more explicit than `app.use(authenticate)` at an arbitrary position in a large file where the ordering relationship to routes is easy to lose track of.
