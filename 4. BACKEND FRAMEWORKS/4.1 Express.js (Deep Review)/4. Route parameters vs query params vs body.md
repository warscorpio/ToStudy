# Express: Route Parameters vs Query Params vs Body — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are the three ways to pass data to an Express route — and what does each part of an HTTP request carry?**

A: Every HTTP request has a fixed anatomy. The three input mechanisms map to distinct parts of that anatomy, each with different semantics, constraints, and appropriate use cases:

```
HTTP Request anatomy:

GET /api/users/42/orders?status=pending&page=2 HTTP/1.1
    ├─────────────────────┤├────────────────┤
    │   Path (URL path)   ││  Query string  │
    │                     ││                │
Host: api.example.com
Authorization: Bearer eyJhbG...
Content-Type: application/json

{"status": "shipped", "note": "urgent"}
├──────────────────────────────────────┤
│            Request body              │
```

The three mechanisms and where they live:

```javascript
// 1. Route parameters — embedded IN the URL path
// Defined with : prefix in the route pattern
// Accessed via req.params
app.get('/users/:userId/orders/:orderId', (req, res) => {
    console.log(req.params);
    // { userId: '42', orderId: '17' }
    // Parsed from: GET /users/42/orders/17
});

// 2. Query parameters — in the URL query string after ?
// Key=value pairs separated by &
// Accessed via req.query
app.get('/orders', (req, res) => {
    console.log(req.query);
    // { status: 'pending', page: '2', limit: '20' }
    // Parsed from: GET /orders?status=pending&page=2&limit=20
});

// 3. Request body — in the HTTP message body
// Requires a body-parsing middleware (express.json(), express.urlencoded())
// Accessed via req.body
app.post('/orders', express.json(), (req, res) => {
    console.log(req.body);
    // { userId: '42', items: [...], shippingAddress: {...} }
    // Parsed from the JSON body of the POST request
});
```

The conceptual split in one sentence:

```
Route params  → WHERE (identity: which resource)
Query params  → HOW   (modifiers: filter, sort, paginate)
Body          → WHAT  (content: the data being submitted)
```

**Q2. What is `req.params` — how does Express parse route parameters and what types do they produce?**

A: `req.params` is a plain object populated by Express when it matches a route pattern against the incoming URL path. Route parameters are defined using the `:name` syntax in the route path string, and Express uses the `path-to-regexp` library internally to convert that pattern into a regular expression:

```javascript
// Basic route parameter:
app.get('/users/:id', (req, res) => {
    console.log(req.params.id);    // '42'   (always a string)
    console.log(typeof req.params.id); // 'string'
    // Parsed from: GET /users/42
});

// Multiple parameters:
app.get('/orgs/:orgId/repos/:repoId/commits/:sha', (req, res) => {
    console.log(req.params);
    // { orgId: 'acme', repoId: 'backend', sha: 'a1b2c3d' }
    // Parsed from: GET /orgs/acme/repos/backend/commits/a1b2c3d
});

// Optional parameter — the ? makes it optional:
app.get('/files/:filename.:ext?', (req, res) => {
    console.log(req.params);
    // GET /files/report.pdf → { filename: 'report', ext: 'pdf' }
    // GET /files/report    → { filename: 'report', ext: undefined }
});

// Wildcard parameter — matches everything including slashes:
app.get('/static/*', (req, res) => {
    console.log(req.params[0]);
    // GET /static/css/main.css → 'css/main.css'
    // Wildcard captured as req.params[0] (numeric index, not named)
});

// Regex constraint on a parameter:
app.get('/users/:id(\\d+)', (req, res) => {
    // Only matches if :id is all digits
    // GET /users/42    → matches, req.params.id = '42'
    // GET /users/alice → does NOT match (falls through to next route)
    console.log(req.params.id); // '42' — still a string despite matching \d+
});

// CRITICAL: ALL route parameters are STRINGS regardless of appearance
// Never assume a numeric-looking param is a number:
app.get('/items/:id', (req, res) => {
    const id = req.params.id;

    // WRONG: treating string as number directly
    const item = db.findById(id + 1); // String concatenation: '421', not 43

    // CORRECT: explicit conversion with validation
    const idNum = parseInt(id, 10);
    if (isNaN(idNum) || idNum <= 0) {
        return res.status(400).json({ error: 'id must be a positive integer' });
    }
    const item2 = db.findById(idNum);
});
```

How Express builds the regex from your pattern:

```javascript
// Behind the scenes — path-to-regexp converts patterns to regex:
// '/users/:id'           → /^\/users\/([^\/]+?)\/?$/i
// '/users/:id(\\d+)'    → /^\/users\/(\d+)\/?$/i
// '/files/*'             → /^\/files\/(.*)\/?$/i

// Named parameters are captured groups in order:
// '/orgs/:orgId/repos/:repoId' →
//   /^\/orgs\/([^\/]+?)\/repos\/([^\/]+?)\/?$/i
//   Group 1 → req.params.orgId
//   Group 2 → req.params.repoId
```

## Section 2: Query Parameters

**Q3. What is `req.query` — how does Express parse query strings and what types does it produce?**

A: `req.query` is populated by Express's built-in query string parser, which parses everything after the `?` in the URL. The default parser (`qs` library) supports nested objects, arrays, and complex structures beyond simple key=value pairs:

```javascript
// Simple key-value pairs:
// GET /orders?status=pending&page=2&limit=20
app.get('/orders', (req, res) => {
    console.log(req.query);
    // { status: 'pending', page: '2', limit: '20' }
    // ALL values are strings — even '2' and '20'
    console.log(typeof req.query.page); // 'string'
});

// Repeated keys → array:
// GET /tags?tag=node&tag=express&tag=typescript
app.get('/search', (req, res) => {
    console.log(req.query.tag);
    // ['node', 'express', 'typescript']  ← array when key repeated
    // BUT: a single value is a string, not a single-element array:
    // GET /tags?tag=node → req.query.tag = 'node'  (string, NOT ['node'])
    // This inconsistency is a very common source of bugs — always normalize:
    const tags = [req.query.tag].flat(); // ['node'] or ['node', 'express', ...]
    //            Always an array regardless of how many values were provided
});

// Nested objects — qs syntax with bracket notation:
// GET /filter?where[status]=active&where[role]=admin
app.get('/users', (req, res) => {
    console.log(req.query);
    // { where: { status: 'active', role: 'admin' } }
    // qs parses bracket notation into nested objects
});

// Array with bracket notation:
// GET /ids?ids[]=1&ids[]=2&ids[]=3
app.get('/bulk', (req, res) => {
    console.log(req.query.ids);
    // ['1', '2', '3'] — still strings
});

// Deep nesting:
// GET /q?filter[meta][created][gte]=2024-01-01
app.get('/q', (req, res) => {
    console.log(req.query.filter);
    // { meta: { created: { gte: '2024-01-01' } } }
});

// Boolean-like values — NO automatic coercion:
// GET /items?active=true&deleted=false
app.get('/items', (req, res) => {
    console.log(req.query.active);         // 'true'  (string)
    console.log(req.query.active === true); // false!  Not a boolean

    // Explicit coercion pattern:
    const active = req.query.active === 'true';
    const deleted = req.query.deleted === 'true';
});

// Empty string vs missing:
// GET /search?q=           → req.query.q = '' (empty string)
// GET /search              → req.query.q = undefined
if (req.query.q === undefined) {
    // Parameter was not provided at all
} else if (req.query.q === '') {
    // Parameter was provided but empty
}
```

Switching query parsers — Express lets you swap the underlying parser:

```javascript
// Default: 'extended' mode uses qs library (supports nesting)
app.set('query parser', 'extended'); // Default

// Simple mode: uses Node.js built-in querystring (no nesting, slightly faster)
app.set('query parser', 'simple');
// GET /q?a[b]=1 → req.query = { 'a[b]': '1' } (brackets treated literally)

// Custom parser:
app.set('query parser', (str) => {
    return require('qs').parse(str, {
        allowDots: true,        // Support dot notation: a.b=1 → { a: { b: '1' } }
        parseArrays: false,     // Disable array parsing (security: prevent array injection)
        depth: 3,               // Maximum nesting depth (default 5 — limit for security)
    });
});
```

**Q4. What is `req.body` — what middleware is required and what formats does it support?**

A: `req.body` is `undefined` by default — Express does not parse the request body automatically. You must attach body-parsing middleware that reads the raw stream, parses it, and sets `req.body`. The choice of middleware depends on the `Content-Type` of incoming requests:

```javascript
import express from 'express';
const app = express();

// 1. JSON body — Content-Type: application/json
app.use(express.json({
    limit: '10mb',         // Maximum body size (default: '100kb') — ALWAYS set this
    strict: true,          // Only accept arrays and objects at root (default: true)
    type: 'application/json', // Which Content-Type to parse
}));

// After middleware: req.body is a parsed JS object
app.post('/api/orders', (req, res) => {
    console.log(req.body);
    // { userId: '42', items: [{ id: 'A1', qty: 2 }], shippingAddress: {...} }
    console.log(typeof req.body.userId); // 'string' (JSON preserves types)
    console.log(Array.isArray(req.body.items)); // true
});

// 2. URL-encoded form body — Content-Type: application/x-www-form-urlencoded
// (HTML form submissions without enctype="multipart/form-data")
app.use(express.urlencoded({
    extended: true,  // true = use qs (supports nesting), false = use querystring
    limit: '1mb',
}));

app.post('/contact', (req, res) => {
    // Form: <input name="email"> <input name="message">
    console.log(req.body);
    // { email: 'user@example.com', message: 'Hello' }
    // ALL values are strings — same as query params
});

// 3. Raw body — for webhooks, binary uploads, custom formats
import { createHmac } from 'crypto';

app.post('/webhook/stripe',
    express.raw({ type: 'application/json', limit: '1mb' }),
    (req, res) => {
        // req.body is a Buffer — NOT parsed JSON
        // Stripe requires the raw body to verify signatures:
        const sig = req.headers['stripe-signature'];
        const event = stripe.webhooks.constructEvent(
            req.body,      // Must be raw Buffer — JSON.parse would break verification
            sig,
            process.env.STRIPE_WEBHOOK_SECRET
        );
        res.json({ received: true });
    }
);

// 4. Text body — for plain text payloads
app.use(express.text({ type: 'text/plain', limit: '1mb' }));
app.post('/text', (req, res) => {
    console.log(typeof req.body); // 'string'
    console.log(req.body);        // 'Hello, this is plain text'
});

// 5. Multipart form data (file uploads) — requires multer or busboy
// express.json() and express.urlencoded() do NOT handle multipart
import multer from 'multer';
const upload = multer({ dest: '/tmp/uploads/', limits: { fileSize: 5 * 1024 * 1024 } });

app.post('/upload', upload.single('avatar'), (req, res) => {
    console.log(req.file);   // File metadata + path
    console.log(req.body);   // Other form fields (non-file fields)
});
```

What happens when `Content-Type` doesn't match the middleware:

```javascript
// If a client sends Content-Type: text/xml but only express.json() is registered:
// → express.json() SKIPS the body (Content-Type doesn't match)
// → req.body remains undefined
// → Your route handler receives req.body = undefined

// WRONG: assuming body is always parsed
app.post('/data', (req, res) => {
    const { name } = req.body; // TypeError: Cannot destructure 'undefined'
    // If body parsing failed or wrong Content-Type → req.body is undefined
});

// CORRECT: always check body is defined before accessing:
app.post('/data', (req, res) => {
    if (!req.body || typeof req.body !== 'object') {
        return res.status(400).json({ error: 'Request body must be JSON' });
    }
    const { name } = req.body;
});
```

## Section 3: Choosing the Right Mechanism

**Q5. How do you decide which mechanism to use — route params, query params, or body?**

A: The choice follows REST conventions and HTTP method semantics. The primary decision tree:

```
Is the data identifying WHICH resource you're operating on?
  → Route parameter

Is the data modifying HOW you retrieve the resource
  (filtering, sorting, pagination, field selection)?
  → Query parameter

Is the data the CONTENT being created, updated, or submitted?
  → Request body

Are you reading data (GET, HEAD)?
  → Body is technically allowed but strongly discouraged (most clients/proxies strip it)
  → Use route params + query params only

Are you creating or modifying data (POST, PUT, PATCH)?
  → Body for the payload; route params for identity; query params rarely needed
```

Concrete decision examples:

```javascript
// Scenario: E-commerce API

// GET a specific product → route param (identity)
// GET /products/SKU-123
app.get('/products/:sku', handler);

// GET products with filters → query params (modifiers)
// GET /products?category=electronics&minPrice=100&maxPrice=500&sort=price&order=asc
app.get('/products', handler);

// CREATE a product → body (content)
// POST /products
// Body: { name, price, category, description, images }
app.post('/products', handler);

// UPDATE a specific product → route param (identity) + body (new content)
// PUT /products/SKU-123
// Body: { name, price, category }
app.put('/products/:sku', handler);

// PARTIAL UPDATE → route param + body
// PATCH /products/SKU-123
// Body: { price: 89.99 }  ← only the fields being changed
app.patch('/products/:sku', handler);

// DELETE → route param only (no body needed — the identity is sufficient)
// DELETE /products/SKU-123
app.delete('/products/:sku', handler);

// Relationship: get orders for a user
// GET /users/42/orders?status=pending&limit=10
// Route params: userId=42 (which user's orders)
// Query params: status=pending, limit=10 (which orders, how many)
app.get('/users/:userId/orders', handler);

// Search: query params, not route params
// GET /search?q=laptop+wireless&category=electronics&page=1
// NOT: GET /search/laptop+wireless/electronics
app.get('/search', handler);

// Action endpoints (non-CRUD) — consider POST with descriptive path
// POST /orders/ORD-456/cancel
// POST /users/42/email/verify
// The action is in the path, parameters are in the body or path
app.post('/orders/:orderId/cancel', handler);
```

The gray areas and their conventions:

```javascript
// Gray area: filtering by IDs list
// Option A: query params (simple, but ugly for many IDs)
// GET /products?ids=1&ids=2&ids=3&ids=4...
//
// Option B: POST body (cleaner for large lists, but uses POST for read)
// POST /products/batch
// Body: { ids: [1, 2, 3, 4, ...100] }
//
// Option C: route param with comma-separated (common but non-REST)
// GET /products/1,2,3,4
//
// Convention: use POST for batch reads when the list could be large

// Gray area: search with complex query
// Option A: GET with query params (cacheable, shareable URL)
// GET /search?q=keyword&filters[brand]=Apple&filters[ram]=16GB
//
// Option B: POST with body (cleaner for complex queries, NOT cacheable)
// POST /search
// Body: { query: 'keyword', filters: { brand: 'Apple', ram: '16GB' }, sort: {...} }
//
// Convention: GET for simple search, POST for complex structured queries

// Gray area: authentication credentials
// Option A: body (most common for login)
// POST /auth/login
// Body: { email, password }   ← CORRECT: sensitive data never in URL
//
// NOT in query params: GET /auth/login?email=x&password=y
// → Password appears in server logs, browser history, proxy logs → NEVER
```

**Q6. What are the security implications of each mechanism?**

A: The three mechanisms have fundamentally different security profiles. Understanding them prevents common vulnerabilities:

```javascript
// ROUTE PARAMETERS — URL path is always logged
// Risk: sensitive data in logs, browser history, Referer headers

// WRONG: putting sensitive data in route params
app.get('/reset-password/:token', (req, res) => {
    // GET /reset-password/abc123secrettoken
    // This URL appears in: server access logs, browser history,
    // Referer header when user clicks a link, CDN/proxy logs
    // Token is now exposed to any log reader
});

// CORRECT: put sensitive data in the body or as a short-lived session
app.post('/reset-password', (req, res) => {
    // Body: { token: 'abc123secrettoken', newPassword: '...' }
    // Token stays out of logs (assuming HTTPS and no body logging)
});

// QUERY PARAMETERS — also in URL, same logging concerns + additional issues
// WRONG: credentials in query string
// GET /api/data?api_key=sk_live_secret123
// → Appears in logs, Referer headers, browser history

// CORRECT: credentials in Authorization header or body
// GET /api/data
// Authorization: Bearer sk_live_secret123

// QUERY PARAMETERS — pollution and injection
app.get('/users', (req, res) => {
    const { role } = req.query;
    // If role = 'admin' injected by attacker: may bypass auth checks
    // Never trust query params for authorization decisions

    // qs nested object injection:
    // GET /users?__proto__[isAdmin]=true
    // → Prototype pollution if req.query passed to Object.assign or lodash.merge
    // Sanitize or use Zod/Joi to validate query params
});

// BODY — largest attack surface due to size and complexity
// Risk: large body DoS, prototype pollution, type confusion

// Always set limits:
app.use(express.json({ limit: '1mb' })); // Prevent 1GB JSON body DoS

// Prototype pollution via body:
app.post('/config', (req, res) => {
    const settings = req.body;
    // If body = { "__proto__": { "isAdmin": true } }
    // Object.assign({}, settings) → pollutes Object.prototype
    // Use JSON schema validation to whitelist allowed fields
    const safeSettings = pick(settings, ['theme', 'language', 'timezone']);
});

// Mass assignment — avoid spreading req.body into DB operations:
app.post('/users', async (req, res) => {
    // WRONG: spreads ALL body fields into the create call
    const user = await User.create(req.body);
    // Attacker sends: { email, password, role: 'admin', isVerified: true }
    // → Unauthorized field assignment

    // CORRECT: explicit field extraction:
    const { email, password, name } = req.body;
    const user2 = await User.create({ email, password, name });
    // Only allowed fields are extracted — 'role' and 'isVerified' ignored
});

// Content-Type bypass — validate body content type explicitly:
app.post('/api/data',
    (req, res, next) => {
        if (!req.is('application/json')) {
            return res.status(415).json({ error: 'Content-Type must be application/json' });
        }
        next();
    },
    express.json(),
    handler
);
```

## Section 4: Validation

**Q7. How do you validate and type-coerce all three input mechanisms with Zod?**

A: Raw values from `req.params`, `req.query`, and `req.body` are all untyped at runtime — any of them could be `undefined`, the wrong type, or malicious input. Zod lets you validate and transform all three in one schema definition:

```typescript
import { z } from 'zod';
import { Request, Response, NextFunction } from 'express';

// Schema definitions for each mechanism:

// Route params schema — always strings from Express, coerce to types you need:
const GetOrderParamsSchema = z.object({
    userId: z.string()
        .regex(/^\d+$/, 'userId must be numeric')
        .transform(Number),           // '42' → 42
    orderId: z.string()
        .uuid('orderId must be a UUID'), // Validates format, stays string
});

// Query params schema — strings and arrays, coerce to appropriate types:
const ListOrdersQuerySchema = z.object({
    status: z.enum(['pending', 'processing', 'shipped', 'delivered', 'cancelled'])
        .optional(),
    page: z.string()
        .regex(/^\d+$/)
        .transform(Number)
        .pipe(z.number().min(1).max(1000))
        .optional()
        .default('1'),               // Default if not provided
    limit: z.string()
        .regex(/^\d+$/)
        .transform(Number)
        .pipe(z.number().min(1).max(100))
        .optional()
        .default('20'),
    sort: z.enum(['createdAt', 'total', 'status'])
        .optional()
        .default('createdAt'),
    order: z.enum(['asc', 'desc'])
        .optional()
        .default('desc'),
    // Array handling — normalize single value and array:
    tags: z.union([z.string(), z.array(z.string())])
        .transform(val => [val].flat())  // Always array
        .optional(),
});

// Body schema — types already correct from JSON parsing:
const CreateOrderBodySchema = z.object({
    userId: z.string().uuid(),
    items: z.array(z.object({
        productId: z.string().uuid(),
        quantity: z.number().int().min(1).max(999),
        unitPrice: z.number().positive(),
    })).min(1, 'Order must have at least one item'),
    shippingAddress: z.object({
        street: z.string().min(1).max(200),
        city: z.string().min(1).max(100),
        country: z.string().length(2), // ISO 3166-1 alpha-2
        postalCode: z.string().regex(/^[A-Z0-9\s-]{3,10}$/i),
    }),
    note: z.string().max(500).optional(),
});

// Generic validation middleware factory:
type SchemaTarget = 'params' | 'query' | 'body';

function validate<T extends z.ZodTypeAny>(
    schema: T,
    target: SchemaTarget
) {
    return (req: Request, res: Response, next: NextFunction) => {
        const result = schema.safeParse(req[target]);

        if (!result.success) {
            return res.status(400).json({
                error: 'Validation failed',
                code: 'VALIDATION_ERROR',
                fields: result.error.flatten().fieldErrors,
            });
        }

        // Attach validated + coerced data back to req:
        // Use a separate namespace to avoid polluting req.params/query/body:
        (req as any)[`validated${target.charAt(0).toUpperCase() + target.slice(1)}`]
            = result.data;

        next();
    };
}

// Route using all three validators:
app.get(
    '/users/:userId/orders/:orderId',
    validate(GetOrderParamsSchema, 'params'),
    validate(ListOrdersQuerySchema, 'query'),
    async (req, res) => {
        const { userId, orderId } = (req as any).validatedParams;
        // userId: number (coerced from string)
        // orderId: string (UUID validated)

        const { status, page, limit } = (req as any).validatedQuery;
        // page: number (coerced from string, defaulted to 1)
        // limit: number (coerced and bounded)

        const order = await orderService.findOne(userId, orderId, { status, page, limit });
        res.json(order);
    }
);

app.post(
    '/orders',
    validate(CreateOrderBodySchema, 'body'),
    async (req, res) => {
        const orderData = (req as any).validatedBody;
        // Fully typed and validated — safe to pass to service layer
        const order = await orderService.create(orderData);
        res.status(201).json(order);
    }
);
```

**Q8. What are the common type coercion bugs when reading `req.params` and `req.query` — and how do you prevent them?**

A: Because both `req.params` and `req.query` are always strings (or arrays of strings), type confusion bugs are extremely common. These fail silently in ways that are hard to debug:

```javascript
// BUG 1: Arithmetic on string params
app.get('/items/:id', async (req, res) => {
    const id = req.params.id; // '42' — string

    // String arithmetic:
    console.log(id + 1);     // '421' — string concatenation!
    console.log(id * 2);     // 84   — implicit coercion by *

    // Wrong comparison:
    if (id === 42) { ... }   // Always false — string vs number

    // DB query with string where number expected:
    const item = await db.query(
        'SELECT * FROM items WHERE id = $1',
        [id]           // pg driver handles string→int coercion, but:
    );
    // If id = '42; DROP TABLE items--' and you template it in:
    db.query(`SELECT * FROM items WHERE id = ${id}`); // SQL injection!
});

// BUG 2: Boolean coercion from query params
app.get('/products', (req, res) => {
    const { active } = req.query; // 'true' or 'false' — both are TRUTHY strings!

    if (active) {
        // This block runs even when active='false' because 'false' is a truthy string
        filterByActive(true); // WRONG — should filter to active=false
    }

    // CORRECT:
    const isActive = active === 'true'
        ? true
        : active === 'false'
            ? false
            : undefined; // Not provided
});

// BUG 3: Array vs string inconsistency in query params
app.get('/search', (req, res) => {
    const { tag } = req.query;

    // If URL is: /search?tag=node
    // tag = 'node' (string)

    // If URL is: /search?tag=node&tag=express
    // tag = ['node', 'express'] (array)

    tag.toUpperCase(); // Works for single value (string)
    // TypeError: tag.toUpperCase is not a function (when array)

    // CORRECT: always normalize to array:
    const tags = [tag ?? []].flat().filter(Boolean);
    // Single: ['node']
    // Multiple: ['node', 'express']
    // Missing: []
});

// BUG 4: NaN propagation from failed parseInt
app.get('/pages/:page', async (req, res) => {
    const page = parseInt(req.params.page, 10);
    // If params.page = 'abc': parseInt returns NaN
    // NaN in arithmetic: NaN + 1 = NaN, NaN > 0 = false

    const offset = (page - 1) * 10; // NaN if page is NaN
    const results = await db.query('SELECT * FROM items LIMIT 10 OFFSET $1', [offset]);
    // OFFSET NaN → DB error or OFFSET 0 → silently wrong results
});

// BUG 5: Prototype pollution via query params (qs library)
// GET /search?__proto__[isAdmin]=true&constructor[prototype][isAdmin]=true
app.get('/search', (req, res) => {
    const filters = req.query; // Could contain __proto__ key

    const merged = Object.assign({}, filters); // Pollutes Object.prototype!
    // Now every {} in the process has isAdmin = 'true'
});

// Prevention pattern — Zod strips unknown keys and validates shape:
const SafeQuerySchema = z.object({
    q: z.string().max(200).optional(),
    page: z.coerce.number().int().min(1).default(1),
    active: z.enum(['true', 'false']).transform(v => v === 'true').optional(),
    tags: z.union([z.string(), z.array(z.string())])
            .transform(v => [v].flat())
            .optional(),
}).strict(); // .strict() rejects unknown keys — blocks __proto__ injection

const result = SafeQuerySchema.safeParse(req.query);
// __proto__ and constructor keys are rejected by .strict()
```

## Section 5: Advanced Patterns

**Q9. How do you handle route parameter middleware with `router.param()`?**

A: `router.param()` registers a callback that runs whenever a specific named parameter appears in a matched route. It's Express's built-in hook for preprocessing route parameters — loading a resource by ID before the route handler runs:

```typescript
import { Router, Request, Response, NextFunction } from 'express';

const router = Router();

// Register a param handler for 'userId':
// Runs before any route handler that has :userId in its path
router.param('userId', async (req: Request, res: Response, next: NextFunction, id: string) => {
    //                                                                        ↑
    //                                             4th argument is the param value as string

    // Validate format:
    if (!/^\d+$/.test(id)) {
        return res.status(400).json({ error: 'userId must be numeric' });
    }

    const userId = parseInt(id, 10);

    try {
        const user = await db.findUser(userId);
        if (!user) {
            return res.status(404).json({ error: `User ${userId} not found` });
        }
        // Attach to req so route handlers can use it without re-fetching:
        (req as any).resolvedUser = user;
        next();
    } catch (err) {
        next(err);
    }
});

// All routes with :userId now have req.resolvedUser pre-loaded:
router.get('/users/:userId', (req, res) => {
    res.json((req as any).resolvedUser); // Already loaded, no DB call needed
});

router.get('/users/:userId/orders', async (req, res) => {
    const user = (req as any).resolvedUser; // Available here too
    const orders = await db.findOrdersByUserId(user.id);
    res.json({ user, orders });
});

router.delete('/users/:userId', async (req, res) => {
    const user = (req as any).resolvedUser;
    await db.deleteUser(user.id);
    res.status(204).end();
});

// param() deduplication: if a route has the same param multiple times,
// the handler only runs once:
router.get('/users/:userId/reports/:userId', (req, res) => {
    // Even though :userId appears twice, param handler runs once
});

// Multiple param handlers on the same param — run in registration order:
router.param('userId', (req, res, next, id) => {
    // Second handler — runs after the first
    (req as any).userId = parseInt(id, 10); // Can add more preprocessing
    next();
});

// param() vs middleware — key differences:
// middleware: runs for ALL routes in the router
// param():    runs ONLY for routes that contain the named parameter
// param():    receives the param value as the 4th argument (middleware doesn't)
```

**Q10. How do you parse complex nested query parameters — and when should you use POST body instead?**

A: The `qs` library (used by Express's default query parser) supports nested objects and arrays. But there are limits — deep nesting in URLs becomes unreadable, breaks bookmarks, and can hit URL length limits. Knowing when to cross over to POST is a key design decision:

```javascript
// Moderate complexity — still fine as query params:
// GET /products?filter[category]=electronics&filter[brand][]=Apple&filter[brand][]=Samsung
//              &price[min]=100&price[max]=500&sort[field]=price&sort[order]=asc

app.get('/products', (req, res) => {
    const { filter, price, sort } = req.query;
    // filter = { category: 'electronics', brand: ['Apple', 'Samsung'] }
    // price  = { min: '100', max: '500' }
    // sort   = { field: 'price', order: 'asc' }
});

// qs has security-related defaults you should understand:
const qs = require('qs');

// Depth limit — prevents deeply nested objects from DoS:
// Default depth is 5 — objects nested deeper than 5 levels are dropped
qs.parse('a[b][c][d][e][f][g]=1'); // depth 7 — g's value is ignored by default

// Array length limit — prevents huge arrays:
qs.parse('a[0]=1&a[1]=2&...&a[1000]=1001'); // items past index 20 dropped by default
// Override with: qs.parse(str, { arrayLimit: 100 })

// Prototype pollution protection in qs >= 6.7:
qs.parse('__proto__[isAdmin]=true');
// Safely handled — not merged into Object.prototype

// When to switch from GET + query params to POST + body:
//
// Signals that query params are the wrong tool:
// 1. Query string is > 2000 characters (URL length limits)
// 2. Nested structure has > 3 levels (readability breaks down)
// 3. Values contain binary data or need precise number types
// 4. The query contains sensitive data (passwords, tokens)
// 5. The query structure needs to be dynamic/programmatic (easier as JSON)

// Example: complex search that crosses the threshold — use POST
// POST /products/search
// Body:
// {
//   "query": "wireless keyboard",
//   "filters": {
//     "category": ["electronics", "accessories"],
//     "brand": ["Apple", "Logitech"],
//     "price": { "min": 20, "max": 200 },
//     "rating": { "min": 4 },
//     "availability": "in-stock",
//     "attributes": { "wireless": true, "backlit": true }
//   },
//   "sort": [{ "field": "rating", "order": "desc" }, { "field": "price", "order": "asc" }],
//   "pagination": { "page": 1, "limit": 24 }
// }

// Trade-off: POST search is NOT cacheable (major HTTP semantics violation)
// Workaround: use a cache key derived from the request body hash
// Or use a search service (Elasticsearch, Algolia) that accepts POST natively
```

**Q11. How do you handle missing parameters gracefully — what does Express set when a parameter is absent?**

A: The behavior when a parameter is absent differs between the three mechanisms, and mishandling these differences causes TypeScript type errors and runtime crashes:

```typescript
// ROUTE PARAMETERS: never absent if the route matched
// If the route is '/users/:id' and it matched, :id is ALWAYS present
// (A route without :id won't match '/users/:id' pattern)
app.get('/users/:id', (req, res) => {
    req.params.id; // Always a string — never undefined
    // But it could still be semantically invalid ('abc' when you expected a number)
});

// Optional route param with ?:
app.get('/files/:name.:ext?', (req, res) => {
    req.params.name; // Always present (not optional)
    req.params.ext;  // string | undefined — may be absent
    // Must check before using:
    const ext = req.params.ext ?? 'txt'; // Default if absent
});

// QUERY PARAMETERS: absent means undefined
app.get('/search', (req, res) => {
    // GET /search (no query string at all)
    req.query.q;       // undefined
    req.query.page;    // undefined

    // GET /search?q= (present but empty)
    req.query.q;       // '' (empty string)

    // GET /search?page (present with no value)
    req.query.page;    // '' (empty string in qs, 'simple' parser gives '')

    // Safe access patterns:
    const q = typeof req.query.q === 'string' ? req.query.q.trim() : undefined;
    const page = typeof req.query.page === 'string'
        ? Math.max(1, parseInt(req.query.page, 10) || 1)
        : 1;

    // TypeScript: req.query values are string | string[] | ParsedQs | ParsedQs[] | undefined
    // Always narrow the type before use
});

// BODY: undefined if middleware didn't parse it, or if body was empty
app.post('/data', express.json(), (req, res) => {
    // POST with Content-Type: application/json, body: {}
    req.body; // {} (empty object — not undefined)

    // POST with Content-Type: text/plain (wrong type for express.json())
    req.body; // undefined — express.json() skipped it

    // POST with no body at all, Content-Type: application/json
    req.body; // undefined

    // POST with body: null (JSON null)
    req.body; // null

    // Safe pattern: always guard before destructuring
    const { name, email } = req.body ?? {}; // Never throws even if body is undefined/null
    // Both name and email will be undefined — validate with schema
});

// TypeScript narrowing pattern:
import type { Request } from 'express';

function getStringParam(req: Request, name: string): string | undefined {
    const val = req.query[name];
    if (typeof val === 'string') return val || undefined; // Convert '' to undefined
    return undefined;
}

function getNumericParam(req: Request, name: string, defaultValue: number): number {
    const val = req.query[name];
    if (typeof val !== 'string') return defaultValue;
    const num = Number(val);
    return Number.isFinite(num) ? num : defaultValue;
}
```

## Section 6: Scenario-Based Questions

**Q12. "What's wrong with this route? Users report they can update other users' data."**

```javascript
app.put('/users/:id', async (req, res) => {
    const userId = req.params.id;
    await db.updateUser(userId, req.body);
    res.json({ success: true });
});
```

A: Three bugs — no authentication check, no authorization check, and mass assignment vulnerability:

```typescript
// Bug 1: No authentication — anyone can hit this endpoint
// Bug 2: No authorization — authenticated user can update ANY userId, not just their own
// Bug 3: Mass assignment — req.body spread directly into updateUser
//         Attacker sends: { role: 'admin', isVerified: true, password: 'hacked' }

// Fixed version:
import { requireAuth } from './middleware/auth';

app.put('/users/:id',
    requireAuth,                    // Must be authenticated
    validate(UpdateUserBodySchema, 'body'),
    async (req: AuthRequest, res, next) => {
        const targetUserId = parseInt(req.params.id, 10);
        if (isNaN(targetUserId)) {
            return res.status(400).json({ error: 'id must be numeric' });
        }

        // Authorization: users can only update themselves (unless admin)
        if (req.user.id !== targetUserId && req.user.role !== 'admin') {
            return res.status(403).json({
                error: 'You can only update your own account',
                code: 'FORBIDDEN',
            });
        }

        // Explicit field extraction — no mass assignment
        const { name, email, bio, avatarUrl } = (req as any).validatedBody;
        // role, isVerified, password — not in UpdateUserBodySchema → ignored

        try {
            const updated = await db.updateUser(targetUserId, { name, email, bio, avatarUrl });
            if (!updated) {
                return res.status(404).json({ error: 'User not found' });
            }
            res.json(updated);
        } catch (err) {
            next(err);
        }
    }
);

// UpdateUserBodySchema — only permits safe fields:
const UpdateUserBodySchema = z.object({
    name: z.string().min(1).max(100).optional(),
    email: z.string().email().optional(),
    bio: z.string().max(500).optional(),
    avatarUrl: z.string().url().optional(),
}).refine(obj => Object.keys(obj).length > 0, {
    message: 'At least one field must be provided',
});
```

**Q13. "Design the parameter strategy for a REST API that has: listing blog posts with filtering, getting a specific post, creating a post, and a search endpoint."**

A: Applying all three mechanisms deliberately for each operation:

```typescript
import { z } from 'zod';

// 1. List posts with filtering, sorting, pagination → GET + query params
// GET /posts?status=published&authorId=42&tag=nodejs&tag=express
//           &sort=publishedAt&order=desc&page=1&limit=10&fields=id,title,excerpt

const ListPostsQuerySchema = z.object({
    status: z.enum(['draft', 'published', 'archived']).optional(),
    authorId: z.coerce.number().int().positive().optional(),
    tag: z.union([z.string(), z.array(z.string())])
          .transform(v => [v].flat().filter(Boolean))
          .optional()
          .default([]),
    sort: z.enum(['publishedAt', 'createdAt', 'title', 'viewCount'])
          .optional()
          .default('publishedAt'),
    order: z.enum(['asc', 'desc']).optional().default('desc'),
    page: z.coerce.number().int().min(1).optional().default(1),
    limit: z.coerce.number().int().min(1).max(50).optional().default(10),
    fields: z.string()
             .transform(v => v.split(',').map(f => f.trim()).filter(Boolean))
             .optional(), // Field selection: ?fields=id,title,excerpt
}).strict();

app.get('/posts', validate(ListPostsQuerySchema, 'query'), async (req, res) => {
    const query = (req as any).validatedQuery;
    const posts = await postService.list(query);
    res.json({
        data: posts.items,
        pagination: {
            page: query.page,
            limit: query.limit,
            total: posts.total,
            totalPages: Math.ceil(posts.total / query.limit),
        },
    });
});

// 2. Get a specific post → route param (identity)
// GET /posts/my-post-slug   OR   GET /posts/42
// Supporting both slug and numeric ID:

const GetPostParamsSchema = z.object({
    // Accepts either a numeric ID or a slug
    id: z.string().min(1),
});

app.get('/posts/:id',
    validate(GetPostParamsSchema, 'params'),
    async (req, res, next) => {
        const { id } = (req as any).validatedParams;

        try {
            // Try numeric ID first, fall back to slug lookup:
            const post = /^\d+$/.test(id)
                ? await postService.findById(parseInt(id, 10))
                : await postService.findBySlug(id);

            if (!post) {
                return res.status(404).json({ error: 'Post not found', code: 'NOT_FOUND' });
            }
            // Only return published posts to non-authors:
            if (post.status !== 'published' && post.authorId !== req.user?.id) {
                return res.status(404).json({ error: 'Post not found', code: 'NOT_FOUND' });
                // Return 404 not 403 — don't reveal existence of private posts
            }
            res.json(post);
        } catch (err) { next(err); }
    }
);

// 3. Create a post → POST with body (content)
// POST /posts
// Body: { title, content, tags, status, scheduledAt? }

const CreatePostBodySchema = z.object({
    title: z.string().min(1).max(200),
    content: z.string().min(1).max(50_000),
    excerpt: z.string().max(500).optional(),
    tags: z.array(z.string().min(1).max(50)).max(10).optional().default([]),
    status: z.enum(['draft', 'published']).default('draft'),
    scheduledAt: z.string().datetime().optional()
        .transform(v => v ? new Date(v) : undefined),
});

app.post('/posts',
    requireAuth,
    validate(CreatePostBodySchema, 'body'),
    async (req: AuthRequest, res, next) => {
        const data = (req as any).validatedBody;
        try {
            const post = await postService.create({
                ...data,
                authorId: req.user.id, // From auth middleware — not from body
                slug: generateSlug(data.title),
            });
            res.status(201)
               .setHeader('Location', `/posts/${post.slug}`)
               .json(post);
        } catch (err) { next(err); }
    }
);

// 4. Search endpoint → GET for simple, POST for complex
// Simple: GET /posts/search?q=express+middleware&tag=nodejs
// Complex: POST /posts/search  with body for advanced filters

// Simple search (cacheable, shareable URL):
const SearchQuerySchema = z.object({
    q: z.string().min(1).max(200),
    tag: z.union([z.string(), z.array(z.string())])
          .transform(v => [v].flat())
          .optional(),
    page: z.coerce.number().int().min(1).default(1),
    limit: z.coerce.number().int().min(1).max(20).default(10),
});

app.get('/posts/search',   // Must be BEFORE /posts/:id to not be captured by it
    validate(SearchQuerySchema, 'query'),
    async (req, res, next) => {
        const { q, tag, page, limit } = (req as any).validatedQuery;
        try {
            const results = await searchService.search({ q, tags: tag, page, limit });
            res.json(results);
        } catch (err) { next(err); }
    }
);

// Route ordering note: /posts/search must be before /posts/:id
// Otherwise 'search' would be captured as the :id param value
// Express matches routes in registration order — specific before dynamic
```

## Quick Reference Table

| | Route Params (`req.params`) | Query Params (`req.query`) | Body (`req.body`) |
|---|---|---|---|
| **Location in request** | URL path segment | URL after `?` | HTTP message body |
| **HTTP methods** | All | All (GET preferred) | POST, PUT, PATCH (GET technically allowed but avoid) |
| **Raw type** | `string` (always) | `string \| string[] \| ParsedQs \| undefined` | Any (depends on parser: object, Buffer, string) |
| **Defined by** | Route pattern (`:name`) | Client (any key=value) | Client (freeform, constrained by Content-Type) |
| **Middleware required** | None | None | `express.json()`, `express.urlencoded()`, etc. |
| **Absent value** | Never absent if route matched | `undefined` | `undefined` (if middleware skipped or no body) |
| **Size limit** | URL length (~2000 chars) | URL length (~2000 chars) | Configurable (`limit` option, default 100kb) |
| **Appears in logs** | Yes (URL logged) | Yes (URL logged) | No (body not logged by default) |
| **Cacheable** | Yes (part of URL) | Yes (part of URL) | No |
| **Primary use** | Resource identity (which one) | Filters, sort, pagination (how to retrieve) | Payload (what to create/update) |
| **Security concern** | Logged, URL-visible | Logged, URL-visible, pollution | Mass assignment, DoS via large body |

| Anti-pattern | Correct pattern |
|---|---|
| `parseInt(req.params.id)` without NaN check | `z.coerce.number()` or manual `isNaN` guard |
| `if (req.query.active)` for boolean | `req.query.active === 'true'` |
| `req.query.tag.toUpperCase()` | `[req.query.tag].flat()` first, then iterate |
| `User.create(req.body)` | Extract allowed fields explicitly |
| Sensitive data in query params | Move to request body |
| Route params for filter/sort | Use query params |
| Body on GET requests | Use query params |
| `req.params.id === 42` | Convert to number first, then compare |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) stating precisely that **all route params and query params are strings** — `typeof req.params.id` is always `'string'` regardless of whether the URL contains `42` or `abc`, and the common bug of doing `params.id + 1` producing `'421'` instead of `43` is the canonical example; (2) explaining the **`req.query` array vs string inconsistency** — a single `?tag=node` gives a string but `?tag=node&tag=express` gives an array, and the normalization pattern `[val].flat()` that makes it always an array regardless of count; (3) knowing that **`req.body` is `undefined` by default** and requires body-parsing middleware, and that the middleware only runs if the `Content-Type` matches — passing the wrong Content-Type header is the most common reason body parsing silently produces `undefined`; (4) articulating the **`WHERE / HOW / WHAT` decision framework** — route params for identity (which resource), query params for modifiers (how to filter/sort), body for content (what to create or change) — and the exception that sensitive data never goes in the URL regardless of this framework; (5) knowing the **mass assignment vulnerability** — spreading `req.body` directly into a database create/update call allows attackers to set fields like `role: 'admin'` or `isVerified: true` that should never be user-settable, and the fix is explicit field extraction or a validated schema that only permits allowed fields; and (6) knowing the **route ordering issue** with static vs dynamic segments — `/posts/search` must be registered before `/posts/:id` or `search` is captured as the `:id` value, because Express matches routes in registration order and `:id` matches any string including `search`.
