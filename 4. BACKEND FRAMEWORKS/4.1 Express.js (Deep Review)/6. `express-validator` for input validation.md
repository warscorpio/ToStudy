## Topic A: Core Architecture and the Validation Chain

### Section A1: Fundamentals

**Q1. What is `express-validator`, how does it integrate with Express, and what problem does it solve?**

A: `express-validator` is a set of Express.js middleware functions built on top of the [`validator.js`](https://github.com/validatorjs/validator.js) library. It solves the input validation and sanitization problem: before any business logic runs, incoming request data (`body`, `query`, `params`, `headers`, `cookies`) must be checked for type correctness, format validity, length constraints, and business rules — and potentially cleaned (trimmed, escaped, normalized) to a safe form. Without it, validating a single form field takes 5-10 lines of imperative `if` checks; with it, the same validation is one declarative chain. The integration model: `express-validator` exports functions (`body()`, `query()`, etc.) that return middleware functions. You include these in an Express route's middleware array before the final handler, then call `validationResult(req)` inside the handler (or in a shared error-checking middleware) to read the accumulated errors.

```js
const { body, validationResult } = require('express-validator');

// Validation chains are middleware — add them before the route handler:
app.post('/users',
  body('email').isEmail().normalizeEmail(),
  body('age').isInt({ min: 0, max: 120 }),
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) {
      return res.status(422).json({ errors: errors.array() });
    }
    // req.body is now validated (and sanitized if sanitizers were applied)
    createUser(req.body);
  }
);
```

**Q2. What are the six request location functions, what does each target, and are they interchangeable?**

A: Each function creates validators that extract and validate from a specific part of the HTTP request:

| Function | Source | Common Use |
|---|---|---|
| `body(path)` | `req.body` | POST/PUT JSON or form data |
| `param(path)` | `req.params` | URL path segments: `/users/:id` |
| `query(path)` | `req.query` | URL query strings: `?page=1&limit=10` |
| `header(path)` | `req.headers` | HTTP headers (case-insensitive lookup) |
| `cookie(path)` | `req.cookies` | Cookie values (requires `cookie-parser`) |
| `check(path)` | All locations | Multi-location fallback search |

They are NOT interchangeable — each constrains where the value comes from. `body('email')` fails validation for a query-string `?email=...` even if the body has no email field. `check('email')` searches all locations and returns the first match — useful for APIs where a field might come from either body or query, but it's generally better to be explicit about the expected location. `header()` searches case-insensitively (`header('Content-Type')` matches `content-type`).

**Q3. What is a validation chain, and how does the builder pattern enable declarative composition?**

A: A validation chain is an object returned by any of the location functions — it represents a series of operations to perform on a specific field. Each method call (`.isEmail()`, `.trim()`, `.withMessage()`) mutates and returns the same chain object, enabling fluent method chaining. Validators and sanitizers are queued in the order they appear. Validators check the current value and add errors if they fail; sanitizers transform the value in-place (mutating `req.body[field]`). Order matters: a `.trim()` before `.isEmail()` removes whitespace first; a `.trim()` after would trim an already-validated email. The chain object is also a valid Express middleware function — it can be spread into a route's middleware array or used as a standalone middleware.

```js
const emailValidator = body('email')
  .trim()                             // sanitizer: remove surrounding whitespace
  .toLowerCase()                      // sanitizer: normalize to lowercase
  .notEmpty().withMessage('Email is required')  // validator: not blank
  .isEmail().withMessage('Invalid email format')  // validator: email format
  .normalizeEmail();                  // sanitizer: a@B.COM → a@b.com

// The chain IS middleware — use it directly:
app.post('/signup', emailValidator, (req, res) => { /* ... */ });

// Or spread alongside other chains:
app.post('/signup', [emailValidator, passwordValidator], handler);
```

**Q4. What does `validationResult(req)` return, and what does the error object structure look like?**

A: `validationResult(req)` returns a `Result` object — a container for all errors accumulated by all validators that ran on the request. The `Result` has four key methods: `isEmpty()` (boolean — no errors), `array(options?)` (flat array of error objects), `mapped()` (first error per field as an object keyed by field path), and `throw()` (throws a typed error if validation failed — for use without a manual check). Each error object in the array (v7 structure):

```js
{
  type:     'field',          // 'field' | 'alternative' | 'alternative_grouped' | 'unknown_fields'
  path:     'email',          // field path (was 'param' in v6)
  location: 'body',           // where the field came from
  value:    'not-an-email',   // the invalid value that was submitted
  msg:      'Invalid email',  // the error message
}
```

```js
// Inside a handler or middleware:
const errors = validationResult(req);

if (!errors.isEmpty()) {
  // errors.array() — all errors (multiple per field possible):
  return res.status(422).json({
    errors: errors.array()
  });
  // [{ type:'field', path:'email', location:'body', value:'bad', msg:'Invalid email' }]

  // errors.array({ onlyFirstError: true }) — at most one error per field:
  // errors.mapped() — first error per field as { fieldPath: errorObj }:
  // { email: { type:'field', msg:'Invalid email', ... } }
}
```

**Q5. What is the difference between validators and sanitizers, and why does their order in the chain matter?**

A: **Validators** check the current value and, if the check fails, add an error message to the request's error list. They do NOT change the value. Examples: `.isEmail()`, `.isLength({ min: 8 })`, `.isInt()`, `.notEmpty()`. **Sanitizers** transform the value in `req.body`/`req.query`/etc. in-place and return the chain — they modify the request. They do NOT add errors. Examples: `.trim()`, `.escape()`, `.toInt()`, `.normalizeEmail()`, `.toLowerCase()`. Order matters because each operation in the chain acts on the output of the previous: `body('email').trim().isEmail()` trims whitespace first, then validates the trimmed result as an email (correct). Reversing them would validate the untrimmed string. Similarly, `toInt()` must come before any numeric validator that expects an integer — `body('count').toInt().isInt({ min: 1 })` converts the string `"5"` to `5` first, then validates.

```js
// Order matters: sanitize BEFORE validate
body('username')
  .trim()         // '  Ada  ' → 'Ada'  (sanitize first)
  .toLowerCase()  // 'Ada'    → 'ada'
  .isLength({ min: 3, max: 20 }) // validate the cleaned value

// NOT the same as:
body('username')
  .isLength({ min: 3, max: 20 }) // validates '  Ada  ' (7 chars — may pass unexpectedly)
  .trim()                        // THEN trims — but validation already ran on untrimmed value

// Sanitizers mutate req.body:
// Before: req.body.username = '  Ada  '
// After chain runs: req.body.username = 'ada'
```

**Q6. What is `matchedData()`, and why is it safer than reading `req.body` directly after validation?**

A: `matchedData(req, options?)` returns a plain object containing only the values from request locations that had at least one validator or sanitizer applied. It prevents **over-posting / mass assignment attacks**: if a client sends `{ username: 'ada', role: 'admin', isVerified: true }` but the server only validated `username`, `matchedData` returns `{ username: 'ada' }` — the unvalidated `role` and `isVerified` fields are excluded even if they exist in `req.body`. Reading `req.body` directly would include the malicious extra fields. Options: `locations: ['body']` restricts to specific request locations; `includeOptionals: false` (default) excludes optional fields that were not submitted.

```js
const { body, matchedData } = require('express-validator');

app.post('/profile',
  body('username').trim().isString().isLength({ min: 3 }),
  body('bio').optional().trim().isString(),
  async (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) return res.status(422).json({ errors: errors.array() });

    // req.body = { username: 'ada', bio: 'Programmer', role: 'admin', isAdmin: true }
    const data = matchedData(req);
    // data    = { username: 'ada', bio: 'Programmer' }
    // 'role' and 'isAdmin' excluded — never validated → not in matchedData ✓

    await db.updateProfile(req.user.id, data); // safe: only validated fields
  }
);
```

### Section A2: Validation Control Flow

**Q7. What does `optional()` do, and what are its three value modes?**

A: `optional()` marks a field as not required — if the value is absent (or meets the "optional" condition), all validators and sanitizers in the chain are skipped. Without `optional()`, any validator on a missing field produces an error. Three modes via the `values` option: **`'undefined'`** (default): skips validation only when the field is `undefined` (not present in the request) — `null`, `""`, and `0` still trigger validation. **`'null'`** (or `{ nullable: true }` in v6 compat): skips validation for `undefined` or `null`. **`'falsy'`**: skips validation for `undefined`, `null`, `""`, `0`, `false`, `NaN` — any falsy value is treated as "not provided."

```js
// Skips if field is absent (undefined only — the default):
body('middleName').optional().isString().trim();
// '' empty string → validates (isString passes for empty string)
// null          → validates and will fail if validators don't accept null
// undefined     → skipped entirely ✓

// Skips for undefined or null:
body('profilePicture').optional({ values: 'null' }).isURL();
// undefined → skipped ✓
// null      → skipped ✓ (useful for allowing explicit null to clear a field)
// ''        → validates → isURL fails → error added

// Skips for any falsy value:
body('tags').optional({ values: 'falsy' }).isArray();
// undefined, null, '', 0, false → all skipped ✓
// []  → validates — isArray() passes
```

**Q8. What does `bail()` do, what two forms does it take, and when does it improve performance?**

A: `bail()` stops the validation chain at the point of insertion if any earlier validator in the chain has failed. Without `bail()`, ALL validators in a chain run regardless of earlier failures — a field might accumulate three errors when only the first one is meaningful (e.g., "field is empty," "not a valid email," "email too long" for an empty field). Two forms: **instance `bail()`**: stops the current field's chain at that point. **`bail({ level: 'request' })`**: stops ALL validation for the entire request the moment this field fails — useful when a critical prerequisite field (e.g., auth token) is invalid and further validation is pointless. `bail()` also improves performance: expensive operations (database lookups, HTTP calls) in `.custom()` validators are not executed if an earlier cheap validator (like `.notEmpty()`) already failed.

```js
// Instance bail — stop this field's chain on first failure:
body('email')
  .trim()
  .notEmpty().withMessage('Email is required').bail()   // if empty, stop here
  .isEmail().withMessage('Invalid email').bail()         // if invalid format, stop here
  .custom(checkEmailNotTaken);                           // ONLY runs if format is valid ✓

// Without bail — ALL validators run even if email is empty:
body('email')
  .notEmpty()         // fails for ''
  .isEmail()          // also fails for '' (3 validators run, 2+ errors added for one field)
  .custom(checkEmailNotTaken); // ALSO runs (expensive DB call for clearly invalid input!)

// Request-level bail — stop everything if auth header is invalid:
header('Authorization')
  .notEmpty().withMessage('Authorization required')
  .bail({ level: 'request' }); // all subsequent validators skipped if auth is missing
```

**Q9. How does `withMessage()` customize error messages, and what is the function form?**

A: `withMessage(message)` sets the error message for the *immediately preceding* validator in the chain. Without it, express-validator uses a default message (e.g., `"Invalid value"`). Two forms: **string**: a static message applied to all failures of that validator. **function**: receives `(value, { req, location, path })` — lets you include context like the invalid value, field name, or request-derived information in the error message. The function form is useful for: translating messages based on `req.headers['accept-language']`, including the submitted value, or generating a message from the constraint parameters. `withMessage()` only covers the single preceding validator — chain it after each validator separately.

```js
body('age')
  .isInt({ min: 0 })  .withMessage('Age must be a non-negative integer')
  .isInt({ max: 120 }).withMessage((value, { path }) =>
    `${path} cannot exceed 120, received: ${value}`
  );

// Dynamic message using request context:
body('username')
  .isLength({ min: 3 })
  .withMessage((value, { req }) => {
    const lang = req.headers['accept-language']?.startsWith('es') ? 'es' : 'en';
    return lang === 'es'
      ? `El usuario debe tener al menos 3 caracteres`
      : `Username must be at least 3 characters`;
  });

// Common mistake: withMessage applies to the IMMEDIATELY preceding validator only:
body('email')
  .notEmpty()
  .isEmail()
  .withMessage('Bad email'); // only covers .isEmail(), NOT .notEmpty()
```

**Q10. What is `if()` for conditional validation, and what two argument types does it accept?**

A: `if(condition)` makes the remaining validators in the chain conditional — they only run if `condition` evaluates to true for the current request. Two argument types: **(1) Another validation chain**: `if(body('paymentMethod').equals('card'))` — the condition is evaluated as a validator chain; if its result has no errors, the condition is "true." **(2) A custom function** `if((value, { req }) => boolean | Promise<boolean>)`: evaluates a function against the current request. `if()` is the correct tool for "field A is required ONLY IF field B has a specific value." It does not apply to the validators before `if()` in the chain — only those after the `if()` call.

```js
// Conditional on another field's value:
body('cardNumber')
  .if(body('paymentMethod').equals('card'))
  .notEmpty().withMessage('Card number required for card payment')
  .isCreditCard().withMessage('Invalid card number');

body('paypalEmail')
  .if(body('paymentMethod').equals('paypal'))
  .isEmail().withMessage('Valid PayPal email required');

// Conditional on a custom function:
body('discountCode')
  .if((value, { req }) => req.body.subtotal > 0 && req.user?.isPremium)
  .isAlphanumeric()
  .isLength({ min: 6, max: 10 });

// Negated condition (run validators when paymentMethod is NOT 'cash'):
body('cardNumber')
  .if(body('paymentMethod').not().equals('cash'))
  .notEmpty();
```

**Q11. What is `oneOf()`, what does it validate, and what is the error format when it fails?**

A: `oneOf(chains[], options?)` creates a validator that passes if AT LEAST ONE of the provided chain groups validates successfully — an OR condition. If all groups fail, `oneOf` adds a single error of `type: 'alternative'` (with nested per-group errors as `nestedErrors`). Use cases: accept either a username or an email; accept either an ID or a slug; allow either a direct value or a lookup reference. `options.message` sets the top-level error message when all alternatives fail; `options.errorType` controls how nested errors appear (`'grouped'` wraps per-group, `'flat'` flattens all errors). `oneOf` is not simply a logical OR on field values — it runs complete validation chains and passes if any chain produces zero errors.

```js
const { oneOf, body, validationResult } = require('express-validator');

app.post('/login',
  oneOf([
    // Alternative 1: login with email
    [body('email').isEmail(), body('password').notEmpty()],
    // Alternative 2: login with username
    [body('username').isAlphanumeric().isLength({ min: 3 }), body('password').notEmpty()],
  ], {
    message: 'Provide either email+password or username+password',
    errorType: 'grouped',
  }),
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) {
      return res.status(422).json({ errors: errors.array() });
      // On failure: [{ type:'alternative', msg:'Provide either...', nestedErrors:[...] }]
    }
  }
);
```

**Q12. What does `not()` do, and how do you combine it with standard validators?**

A: `not()` inverts the result of the next validator in the chain — a validator that would pass now fails, and vice versa. It only inverts the *immediately following* validator, not the entire rest of the chain. Common patterns: `not().isEmpty()` (equivalent to `notEmpty()` — non-empty field), `not().isIn(['admin', 'superuser'])` (field must NOT be one of these values), `not().matches(/\s/)` (field must NOT contain whitespace). `notEmpty()` is a convenience alias for `not().isEmpty()`.

```js
// Reject reserved usernames:
body('username')
  .isAlphanumeric()
  .not().isIn(['admin', 'root', 'superuser', 'system'])
  .withMessage('Username is reserved');

// Password must not be too common:
body('password')
  .isLength({ min: 8 })
  .not().isIn(['password', 'password123', '12345678', 'qwerty'])
  .withMessage('Password is too common');

// Value must not contain whitespace:
body('apiKey')
  .not().matches(/\s/)
  .withMessage('API key must not contain spaces');
```

## Topic B: Custom Logic, Schemas, and Advanced Patterns

### Section B1: Custom Validators and Schemas

**Q13. How do you write a custom synchronous validator with `.custom()`, and what makes it pass or fail?**

A: `.custom(validator)` accepts a function `(value, { req, location, path }) => any`. The function **passes** if it returns any truthy value, `undefined`, or a resolved Promise. It **fails** if it throws an Error (the thrown message becomes the error message) or returns a rejected Promise. The `{ req, location, path }` meta-argument gives access to the full request (for cross-field validation) and the field's location and path. Custom validators are the escape hatch for business-logic constraints that go beyond format checking — uniqueness in a database, cross-field dependencies, custom format rules.

```js
const { body } = require('express-validator');

// Synchronous custom validator — throw to fail:
body('username')
  .custom((value) => {
    if (value.includes(' ')) {
      throw new Error('Username must not contain spaces');
    }
    if (['admin', 'root'].includes(value.toLowerCase())) {
      throw new Error('Username is reserved');
    }
    return true; // explicit return true (or just don't throw — implicit pass)
  });

// Cross-field validation using req:
body('passwordConfirm')
  .custom((value, { req }) => {
    if (value !== req.body.password) {
      throw new Error('Passwords do not match');
    }
    return true;
  });

// Returning false also fails (uses generic 'Invalid value' message unless withMessage used):
body('evenNumber')
  .custom((value) => parseInt(value) % 2 === 0)
  .withMessage('Must be an even number');
```

**Q14. How do you write an async custom validator, and how do errors propagate from rejected promises?**

A: Async validators are identical in syntax to synchronous ones — return a Promise from the custom function. If the Promise resolves, the validator passes; if it rejects, the rejection reason (`.message` of the thrown error) becomes the error message. Async validators enable database lookups, external API calls, and any async business-logic checks. `bail()` before `.custom()` is especially important for async validators — don't make a database call when earlier validators already proved the input is invalid.

```js
const { body } = require('express-validator');

// Async validator — return a Promise that resolves or rejects:
body('email')
  .trim()
  .isEmail().bail()  // ← bail: don't hit DB if format is invalid
  .custom(async (value) => {
    const existingUser = await User.findOne({ email: value });
    if (existingUser) {
      throw new Error('Email already registered');
      // Equivalent: return Promise.reject(new Error('Email already registered'));
    }
    // Implicit return (undefined = pass)
  });

// More explicit async with full error context:
body('username')
  .isAlphanumeric().bail()
  .custom(async (value, { req }) => {
    const [existing, reserved] = await Promise.all([
      User.findOne({ username: value }),
      ReservedName.findOne({ name: value.toLowerCase() }),
    ]);
    if (existing)  throw new Error('Username is taken');
    if (reserved)  throw new Error('Username is reserved');
  });
```

**Q15. What is `customSanitizer()`, how does it transform values, and what invariant must it maintain?**

A: `customSanitizer(fn)` takes a function `(value, { req, location, path }) => newValue | Promise<newValue>` and replaces the field's current value with the function's return value. It is the escape hatch for transformations not covered by built-in sanitizers: parsing custom date formats, normalizing phone numbers, converting objects, or computing derived values. The invariant: `customSanitizer` MUST return a value (even if the same value unchanged) — returning `undefined` implicitly sets the field to `undefined`. If the function throws, the error is propagated but no validation error is added (unlike `custom()`); if you want both sanitization and validation, use `custom()` with side effects or chain `custom()` after `customSanitizer()`.

```js
const { body } = require('express-validator');
const { parsePhoneNumber } = require('libphonenumber-js');

// Convert a raw phone string to E.164 format:
body('phone')
  .customSanitizer((value) => {
    try {
      return parsePhoneNumber(value, 'US').number; // '+15551234567'
    } catch {
      return value; // return original if parsing fails (let isPhoneNumber validator fail)
    }
  })
  .custom((value) => {
    const parsed = parsePhoneNumber(value);
    if (!parsed?.isValid()) throw new Error('Invalid phone number');
    return true;
  });

// Convert comma-separated string to array:
body('tags')
  .customSanitizer((value) =>
    typeof value === 'string'
      ? value.split(',').map(t => t.trim()).filter(Boolean)
      : value
  )
  .isArray({ min: 1 });
```

**Q16. What is `checkSchema()`, what are its advantages, and what does its schema object look like?**

A: `checkSchema(schemaObject, defaultLocations?)` creates validation chains from a plain object definition instead of fluent method calls. Each key is a field name; each value is a descriptor object where properties map to validator/sanitizer names (as keys) and their options (as values). Advantages: (1) externalized, serializable validation rules — schemas can be stored in config files or generated programmatically; (2) centralized documentation of all fields in one place; (3) TypeScript-friendly with full type definitions; (4) easier to merge/extend schemas by spreading objects. `checkSchema` returns an array of chain middlewares — spread it into the route middleware array.

```js
const { checkSchema, validationResult } = require('express-validator');

const createProductSchema = {
  name: {
    in: ['body'],
    trim: true,
    notEmpty: { errorMessage: 'Product name is required' },
    isLength: {
      options: { min: 2, max: 100 },
      errorMessage: 'Name must be 2–100 characters',
    },
  },
  price: {
    in: ['body'],
    toFloat: true,
    isFloat: {
      options: { min: 0.01 },
      errorMessage: 'Price must be greater than 0',
    },
  },
  category: {
    in: ['body'],
    isIn: {
      options: [['electronics', 'clothing', 'books', 'food']],
      errorMessage: 'Invalid category',
    },
  },
  sku: {
    in: ['body'],
    optional: true,
    matches: {
      options: /^[A-Z]{3}-\d{4}$/,
      errorMessage: 'SKU must match pattern XXX-0000',
    },
  },
};

app.post('/products',
  ...checkSchema(createProductSchema), // spread the array of middlewares
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) return res.status(422).json({ errors: errors.array() });
    // proceed
  }
);
```

**Q17. How do you validate arrays and nested objects using wildcard paths?**

A: `express-validator` uses dot-notation and the `*` wildcard for nested paths. `body('items.*.name')` matches `items[0].name`, `items[1].name`, etc. `body('address.city')` matches the nested `city` property of the `address` object. First validate the array/object structure itself (`.isArray()`, `.isObject()`), then validate individual fields using wildcards. For deeply nested structures, chain wildcards: `body('orders.*.items.*.productId')`.

```js
// Validate an array of items:
body('items')
  .isArray({ min: 1 }).withMessage('At least one item required'),

body('items.*.productId')
  .isMongoId().withMessage('Invalid product ID'),

body('items.*.quantity')
  .isInt({ min: 1 }).withMessage('Quantity must be at least 1')
  .toInt(),

body('items.*.price')
  .isFloat({ min: 0 }).withMessage('Price must be non-negative')
  .toFloat(),

// Nested object:
body('address')
  .exists().withMessage('Address is required'),

body('address.street')
  .trim()
  .notEmpty().withMessage('Street is required'),

body('address.zip')
  .matches(/^\d{5}(-\d{4})?$/).withMessage('Invalid ZIP code'),

// Deeply nested:
body('orders.*.items.*.productId')
  .isMongoId(),
```

**Q18. What is `.run(req)` for non-middleware use, and when would you call it programmatically?**

A: Every validation chain (returned by `body()`, `param()`, etc.) is both a middleware function AND has a `.run(req)` method. `.run(req)` returns a Promise that resolves when all validators and sanitizers in the chain have completed. This is useful for: (1) using validation outside the Express request lifecycle (background jobs, WebSocket handlers, gRPC services); (2) conditionally running specific chains; (3) testing validation chains without spinning up an HTTP server; (4) running validators in parallel with `Promise.all()`. After `.run()`, call `validationResult(req)` as normal to read errors.

```js
// Run validators programmatically (e.g., in a test or non-Express context):
const req = {
  body: { email: 'invalid', password: '123' }
};

const emailChain    = body('email').isEmail();
const passwordChain = body('password').isLength({ min: 8 });

// Run in parallel:
await Promise.all([
  emailChain.run(req),
  passwordChain.run(req),
]);

const errors = validationResult(req);
console.log(errors.array());
// [{ path:'email', msg:'Invalid value' }, { path:'password', msg:'Invalid value' }]

// Or sequential (when order matters):
await emailChain.run(req);
if (validationResult(req).isEmpty()) {
  await expensiveAsyncChain.run(req);
}
```

### Section B2: Error Handling and Production Patterns

**Q19. What is `Result.formatWith()`, and how do you customize the error object shape for your API?**

A: `validationResult.withDefaults({ formatter })` creates a custom version of `validationResult` with a different error format applied globally. Alternatively, call `.formatWith(formatter)` on a specific result. The formatter is `(error) => formattedValue` — transform each raw error object into any shape. This lets you: rename fields (`param` → `field`), add HTTP-friendly metadata, translate messages, or match your API's established error contract.

```js
const { validationResult } = require('express-validator');

// Create a custom validationResult with a specific error format:
const myValidationResult = validationResult.withDefaults({
  formatter: (error) => ({
    field:    error.path,          // rename 'path' to 'field'
    message:  error.msg,
    received: error.value,
    location: error.location,
  }),
});

// Use it in handlers — same API as validationResult:
app.post('/users', validators, (req, res) => {
  const errors = myValidationResult(req);
  if (!errors.isEmpty()) {
    return res.status(422).json({
      status:  'error',
      code:    'VALIDATION_ERROR',
      errors:  errors.array(),
      // [{ field:'email', message:'Invalid email', received:'bad', location:'body' }]
    });
  }
});

// Or per-response formatting:
const errors = validationResult(req)
  .formatWith(({ path, msg }) => `${path}: ${msg}`);
// errors.array() → ['email: Invalid email', 'password: Too short']
```

**Q20. What is `unknownFields()` (also `checkExact()`), and why is it useful for strict API contracts?**

A: `checkExact(chains, options?)` is a meta-validator that runs the provided chains AND adds errors for any fields in the request that were NOT covered by any of those chains. This enforces a strict allowlist — extra fields that no validator covers produce errors of `type: 'unknown_fields'`. Use it when you want to reject requests that include fields not in your schema, preventing clients from sending undocumented parameters. Without it, extra fields silently pass through (express-validator only validates fields you explicitly declare).

```js
const { checkExact, body, validationResult } = require('express-validator');

// Strict validation — extra fields are errors:
app.post('/users',
  checkExact([
    body('email').isEmail(),
    body('password').isLength({ min: 8 }),
    body('name').trim().notEmpty(),
  ], {
    message: 'Unknown fields are not allowed',
    locations: ['body'], // only check body for unknown fields
  }),
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) return res.status(422).json({ errors: errors.array() });
    // req.body = { email:'a@b.com', password:'12345678', name:'Ada', role:'admin' }
    // → Error: 'role' is an unknown field → rejected ✓
  }
);
```

**Q21. What are the common pitfalls when sanitizers mutate `req.body`, and how do you handle immutable request objects?**

A: Sanitizers mutate the request object in-place — `body('email').trim()` modifies `req.body.email` directly. Three common pitfalls: (1) **Middleware order**: if another middleware has already consumed/forwarded `req.body` before validators run (e.g., body was logged or passed to a service), the sanitized version doesn't reach that downstream code. Always run validators before business logic. (2) **Shared request object in tests**: when running `.run(req)` on a shared test request object, sanitizers permanently change it. Use a fresh req object per test. (3) **Object.freeze'd body**: some security middleware freezes `req.body` — sanitizers silently fail (no error thrown, but values are unchanged). Use `matchedData()` to get sanitized values in a new object, bypassing the frozen original.

```js
// Pitfall: sanitized value may not match what downstream code sees:
app.post('/data',
  body('tags').customSanitizer(v => v.split(',')), // mutates req.body.tags
  (req, res) => {
    console.log(req.body.tags); // ['tag1', 'tag2'] — correct, sanitizer ran ✓
  }
);

// Safe pattern: use matchedData() which reads from a separate sanitized store:
const data = matchedData(req);
// data.tags is the sanitized value from express-validator's internal store
// (matchedData doesn't re-read req.body — it uses the validated/sanitized values)

// Test isolation:
function makeReq(body) {
  return { body: { ...body } }; // fresh object each time
}
const req1 = makeReq({ email: ' test@example.com ' });
await body('email').trim().run(req1); // mutates req1.body.email
// req1.body.email = 'test@example.com'
// Original body was not shared — safe ✓
```

**Q22. How do you validate request headers and route params, and what are their unique constraints?**

A: `header(name)` validates HTTP headers — name lookup is case-insensitive (Express normalizes them to lowercase). Common uses: validating `Authorization` format, checking `Content-Type`, requiring custom `X-Api-Key` headers. `param(name)` validates URL path parameters from `:name` segments. Route params are always strings in Express — use `.toInt()` or `.toFloat()` sanitizers if you need numeric types. Route params are always present for a matched route, so `optional()` is rarely needed for params.

```js
// Validate Authorization header (Bearer token format):
header('authorization')
  .notEmpty().withMessage('Authorization header required').bail()
  .matches(/^Bearer\s+\S+/).withMessage('Authorization must be a Bearer token');

// Route param validation:
// Route: GET /posts/:id/comments/:commentId
param('id')
  .isMongoId().withMessage('Invalid post ID'),

param('commentId')
  .isMongoId().withMessage('Invalid comment ID'),

// Numeric param:
param('page')
  .optional()
  .isInt({ min: 1 }).withMessage('Page must be a positive integer')
  .toInt(),

// Query string pagination:
query('limit')
  .optional()
  .isInt({ min: 1, max: 100 }).withMessage('Limit must be 1–100')
  .toInt()
  .default(20), // Note: .default() is NOT a built-in — use: .customSanitizer(v => v ?? 20)
```

## Topic C: Advanced Patterns and Cross-Topic

**Q23. How do you create a reusable validation middleware factory, and what patterns compose well?**

A: Compose validation into factories — functions that return arrays of validation chains. Group related validators, compose them for different operations, and merge them with spread syntax. The validate-and-error-check pattern is commonly extracted to a shared function to avoid repeating the `validationResult` check in every handler.

```js
// ─── validators/user.js ──────────────────────────────────────
const { body } = require('express-validator');

const emailValidator = () =>
  body('email').trim().normalizeEmail().notEmpty().isEmail();

const passwordValidator = (fieldName = 'password') =>
  body(fieldName)
    .notEmpty().withMessage('Password is required').bail()
    .isLength({ min: 8 }).withMessage('At least 8 characters')
    .matches(/[A-Z]/).withMessage('At least one uppercase letter')
    .matches(/\d/).withMessage('At least one number');

const userRegistrationValidators = () => [
  emailValidator(),
  passwordValidator('password'),
  body('passwordConfirm')
    .custom((val, { req }) => {
      if (val !== req.body.password) throw new Error('Passwords must match');
    }),
  body('username')
    .trim().isAlphanumeric().isLength({ min: 3, max: 30 }),
];

module.exports = { emailValidator, passwordValidator, userRegistrationValidators };

// ─── middleware/validate.js ─── shared error-check middleware ─
const { validationResult } = require('express-validator');

const validate = (req, res, next) => {
  const errors = validationResult(req);
  if (!errors.isEmpty()) {
    return res.status(422).json({
      status: 'error',
      errors: errors.array({ onlyFirstError: true }),
    });
  }
  next();
};

module.exports = { validate };

// ─── routes/auth.js ──────────────────────────────────────────
const { userRegistrationValidators } = require('../validators/user');
const { validate } = require('../middleware/validate');

router.post('/register',
  ...userRegistrationValidators(), // spread the array
  validate,                         // shared error-check middleware
  async (req, res) => {
    const data = matchedData(req);
    await registerUser(data);
    res.status(201).json({ status: 'created' });
  }
);
```

**Q24. What changed between express-validator v6 and v7, and what are the migration impacts?**

A: Key v7 changes that affect existing code: (1) **`path` replaces `param`**: error objects now have `path` instead of `param` for the field name — code reading `error.param` must switch to `error.path`; (2) **`optional()` behavior**: in v6, `optional({ nullable: true })` was the way to allow null; in v7, use `optional({ values: 'null' })` — the `nullable` option is deprecated; (3) **`type` field on errors**: each error now has a `type` property (`'field' | 'alternative' | 'alternative_grouped' | 'unknown_fields'`) — code that only handles field errors should check `error.type === 'field'`; (4) **`checkExact()`**: new in v7, replaces the old `allowUnknownFields` option pattern; (5) **`.run()` always returns a Promise**: previously some sync chains resolved synchronously — now always use `await`; (6) **Better ESM support**: v7 ships with proper ESM exports alongside CJS.

```js
// v6 error handling:
errors.array().forEach(err => console.log(err.param, err.msg));

// v7 migration:
errors.array()
  .filter(err => err.type === 'field') // filter to only field errors
  .forEach(err => console.log(err.path, err.msg));
//                               ^^^^ was .param in v6

// v6 optional with null:
body('field').optional({ nullable: true }).isString();

// v7 equivalent:
body('field').optional({ values: 'null' }).isString();
```

**Q25. State the invariant for validator placement, the sanitizer mutation invariant, and the error-checking invariant in one sentence each.**

A:
- **Placement invariant**: validation chains must be added as middleware *before* the final route handler — they add errors to the request object as they run, and `validationResult(req)` only reflects the errors accumulated by chains that have already executed by the time it is called.
- **Sanitizer mutation invariant**: sanitizers mutate the request object in-place — any downstream middleware or code that reads `req.body[field]` after validators have run receives the sanitized (transformed) value, not the original submitted value; use `matchedData(req)` to get sanitized values from express-validator's internal store rather than reading `req.body` directly to avoid mass-assignment vulnerabilities.
- **Error-checking invariant**: `validationResult(req)` must be called exactly once per request after all validation chains have run — calling it before all chains complete (e.g., only after the first of several parallel chains) returns an incomplete error set; calling it multiple times on the same request returns the same accumulated errors each time (the error list is not consumed or cleared by reading it).

## Problem 1 — Complete User Registration Validation

### Problem

Implement a complete `/register` endpoint validator covering: email (format, uniqueness), password (strength requirements), password confirmation (must match), username (alphanumeric, length, uniqueness), and an optional phone number (E.164 format).

```js
POST /register
{
  "email": "ada@example.com",
  "password": "Secure123!",
  "passwordConfirm": "Secure123!",
  "username": "ada_lovelace",
  "phone": "+15551234567"   // optional
}
```

### Pattern Recognition
Chain multiple validators per field with specific `withMessage` for each failure case. Use `bail()` before async validators. Cross-field validation via `req` in `custom()`. `optional()` for the phone field.

### Key Insight
Place `bail()` after cheap, synchronous format validators and before expensive async validators (DB lookups). This prevents unnecessary database calls when the format is already wrong. The `passwordConfirm` validator reads `req.body.password` — this only works correctly if it runs after the body is parsed and the password field is not sanitized to a different value before this check runs.

### Solution

```js
const { body, validationResult, matchedData } = require('express-validator');

// ─── validators/registration.js ──────────────────────────────
const registrationValidators = [
  // 1. Email: format → uniqueness
  body('email')
    .trim()
    .notEmpty().withMessage('Email is required').bail()
    .isEmail().withMessage('Invalid email address').bail()
    .normalizeEmail()                            // sanitizer: a@B.COM → a@b.com
    .custom(async (email) => {
      const exists = await User.exists({ email });
      if (exists) throw new Error('Email is already registered');
    }),

  // 2. Password: presence → length → complexity
  body('password')
    .notEmpty().withMessage('Password is required').bail()
    .isLength({ min: 8 }).withMessage('Password must be at least 8 characters').bail()
    .matches(/[A-Z]/).withMessage('Password must include at least one uppercase letter')
    .matches(/[a-z]/).withMessage('Password must include at least one lowercase letter')
    .matches(/\d/).withMessage('Password must include at least one number')
    .matches(/[^A-Za-z0-9]/).withMessage('Password must include at least one special character'),

  // 3. Password confirmation: must match password
  body('passwordConfirm')
    .notEmpty().withMessage('Password confirmation is required').bail()
    .custom((value, { req }) => {
      if (value !== req.body.password) {
        throw new Error('Passwords do not match');
      }
      return true;
    }),

  // 4. Username: format → uniqueness
  body('username')
    .trim()
    .notEmpty().withMessage('Username is required').bail()
    .matches(/^[a-zA-Z0-9_]+$/)
      .withMessage('Username may only contain letters, numbers, and underscores').bail()
    .isLength({ min: 3, max: 30 })
      .withMessage('Username must be 3–30 characters').bail()
    .custom(async (username) => {
      const exists = await User.exists({ username: username.toLowerCase() });
      if (exists) throw new Error('Username is already taken');
    }),

  // 5. Phone: optional, E.164 format
  body('phone')
    .optional({ values: 'null' })  // allow missing or null
    .trim()
    .matches(/^\+[1-9]\d{7,14}$/)
    .withMessage('Phone must be in E.164 format (e.g., +15551234567)'),
];

// ─── routes/auth.js ──────────────────────────────────────────
const handleValidation = (req, res, next) => {
  const errors = validationResult(req);
  if (!errors.isEmpty()) {
    return res.status(422).json({
      status: 'error',
      code:   'VALIDATION_FAILED',
      errors: errors.array({ onlyFirstError: true }), // one error per field
    });
  }
  next();
};

router.post('/register',
  ...registrationValidators,
  handleValidation,
  async (req, res) => {
    const data = matchedData(req); // { email, password, username, phone? }
    // data does NOT include passwordConfirm (it had no sanitizer — still use matchedData)
    const { passwordConfirm: _, ...safeData } = data; // exclude confirm from save
    const user = await User.create({
      ...safeData,
      passwordHash: await bcrypt.hash(data.password, 12),
    });
    res.status(201).json({ id: user.id });
  }
);
```

### Trace

```js
// Request body: { email: ' ada@EXAMPLE.COM', password: 'weak', passwordConfirm: 'weak', username: 'ada' }

// email chain:
//   trim()         → 'ada@EXAMPLE.COM'
//   notEmpty()     → passes
//   isEmail()      → passes
//   normalizeEmail → 'ada@example.com'  (req.body.email mutated)
//   custom(unique) → no existing user → passes

// password chain:
//   notEmpty()          → passes
//   isLength({ min:8 }) → 'weak' is 4 chars → FAIL: 'Password must be at least 8 characters'
//   bail() not present  → continues to next validators
//   matches(/[A-Z]/)    → 'weak' has no uppercase → FAIL
//   matches(/[a-z]/)    → passes
//   matches(/\d/)       → no number → FAIL
//   matches(/[^A-Za-z0-9]/) → no special char → FAIL

// After all chains run:
errors.array({ onlyFirstError: true }) → [
  { path:'password', msg:'Password must be at least 8 characters', ... },
  // (only first error per field shown)
]
// Response: 422 { status:'error', code:'VALIDATION_FAILED', errors:[...] }
```

### Edge Cases
- `normalizeEmail()` modifies `req.body.email` — downstream code and `matchedData` see the normalized form, not the original.
- `passwordConfirm` is in `matchedData` because it had a custom validator — explicitly exclude it before saving to DB.
- Async validators run concurrently within express-validator — both email and username uniqueness DB queries may run in parallel.

## Problem 2 — Schema-Based Product API Validation

### Problem

Use `checkSchema()` to validate a product creation endpoint. The product has required fields, optional fields, an enum constraint, a numeric range, a URL, and a tags array.

```js
POST /products
{
  "name": "Mechanical Keyboard",
  "price": 149.99,
  "category": "electronics",
  "sku": "KEY-1234",
  "imageUrl": "https://cdn.example.com/keyboard.jpg",
  "stock": 50,
  "tags": ["mechanical", "keyboard", "gaming"]
}
```

### Pattern Recognition
`checkSchema()` with `in`, `optional`, `isIn`, `isFloat`, `isInt`, `isURL`, `isArray`, and custom validators. Demonstrates how schemas can be defined as plain objects and reused or extended.

### Solution

```js
const { checkSchema, validationResult, matchedData } = require('express-validator');

const productSchema = {
  name: {
    in:       ['body'],
    trim:     true,
    notEmpty: { errorMessage: 'Product name is required' },
    isLength: {
      options:      { min: 2, max: 100 },
      errorMessage: 'Name must be 2–100 characters',
    },
  },

  price: {
    in:      ['body'],
    toFloat: true,
    isFloat: {
      options:      { min: 0.01, max: 999_999.99 },
      errorMessage: 'Price must be between $0.01 and $999,999.99',
    },
  },

  category: {
    in:    ['body'],
    isIn:  {
      options:      [['electronics', 'clothing', 'books', 'food', 'home']],
      errorMessage: 'Invalid category',
    },
  },

  sku: {
    in:       ['body'],
    optional: true,
    trim:     true,
    matches:  {
      options:      /^[A-Z]{2,4}-\d{4}$/,
      errorMessage: 'SKU must match format XX-0000 (e.g., KEY-1234)',
    },
    custom: {
      options: async (sku) => {
        if (!sku) return true;
        const exists = await Product.exists({ sku: sku.toUpperCase() });
        if (exists) throw new Error('SKU is already in use');
      },
    },
  },

  imageUrl: {
    in:       ['body'],
    optional: true,
    isURL:    {
      options:      { protocols: ['https'], require_tld: true },
      errorMessage: 'Image URL must be a valid HTTPS URL',
    },
  },

  stock: {
    in:    ['body'],
    toInt: true,
    isInt: {
      options:      { min: 0 },
      errorMessage: 'Stock must be a non-negative integer',
    },
  },

  tags: {
    in:      ['body'],
    optional: true,
    isArray:  {
      options:      { max: 10 },
      errorMessage: 'Tags must be an array with at most 10 items',
    },
  },

  'tags.*': {
    in:       ['body'],
    optional: true,   // only runs if tags is present
    trim:     true,
    isString: { errorMessage: 'Each tag must be a string' },
    isLength: {
      options:      { min: 1, max: 30 },
      errorMessage: 'Tags must be 1–30 characters',
    },
    toLowerCase: true,
  },
};

// Route:
router.post('/products',
  ...checkSchema(productSchema),
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) {
      return res.status(422).json({ errors: errors.array() });
    }
    const data = matchedData(req);
    // data.tags may have been lowercased by toLowerCase sanitizer
    return Product.create(data).then(p => res.status(201).json(p));
  }
);

// Schema extension for updates (all fields optional):
const updateProductSchema = Object.fromEntries(
  Object.entries(productSchema).map(([key, rules]) => [
    key,
    { ...rules, optional: true } // make every field optional for PATCH
  ])
);

router.patch('/products/:id',
  param('id').isMongoId(),
  ...checkSchema(updateProductSchema),
  handler
);
```

### Trace

```js

// name: '' → trim → '' → notEmpty FAILS: 'Product name is required'
// price: -5 → toFloat → -5 → isFloat({ min:0.01 }) FAILS: 'Price must be between...'
// category: 'invalid' → isIn(['electronics',...]) FAILS: 'Invalid category'
// tags[0]: 'gaming' → isString ✓ isLength ✓
// tags[1]: 42 → isString FAILS: 'Each tag must be a string'

// errors.array() → [
//   { path:'name',     msg:'Product name is required' },
//   { path:'price',    msg:'Price must be between $0.01 and $999,999.99' },
//   { path:'category', msg:'Invalid category' },
//   { path:'tags[1]',  msg:'Each tag must be a string' },
// ]
```

## Problem 3 — Conditional Payment Form Validation

### Problem

Validate a checkout form where required fields depend on the chosen payment method. Card payments require `cardNumber`, `cvv`, and `expiryDate`. PayPal requires `paypalEmail`. Bank transfer requires `routingNumber` and `accountNumber`.

```js
POST /checkout
{
  "paymentMethod": "card",
  "cardNumber": "4111111111111111",
  "cvv": "123",
  "expiryDate": "12/26"
}
```

### Pattern Recognition
`body('field').if(body('otherField').equals('value'))` for conditional chains. First validate `paymentMethod` is a valid enum, then use conditional chains for each method's specific fields.

### Key Insight
The `if()` condition itself uses a validation chain — `body('paymentMethod').equals('card')` returns truthy when the value IS `'card'`. Fields for other payment methods are simply skipped (not validated, not required) when their condition doesn't match. Use `bail()` on `paymentMethod` to skip all conditional validation if paymentMethod itself is invalid.

### Solution

```js
const { body, validationResult } = require('express-validator');

const checkoutValidators = [
  // 1. Validate paymentMethod first — bail if invalid:
  body('paymentMethod')
    .isIn(['card', 'paypal', 'bank_transfer'])
    .withMessage('Payment method must be: card, paypal, or bank_transfer')
    .bail({ level: 'request' }), // if invalid, skip ALL conditional validation below

  // 2. Amount: required regardless of payment method:
  body('amount')
    .isFloat({ min: 0.01 }).withMessage('Amount must be greater than 0')
    .toFloat(),

  // ── CARD fields (only when paymentMethod === 'card') ─────────
  body('cardNumber')
    .if(body('paymentMethod').equals('card'))
    .notEmpty().withMessage('Card number is required for card payment').bail()
    .isCreditCard().withMessage('Invalid card number'),

  body('cvv')
    .if(body('paymentMethod').equals('card'))
    .notEmpty().withMessage('CVV is required for card payment').bail()
    .matches(/^\d{3,4}$/).withMessage('CVV must be 3 or 4 digits'),

  body('expiryDate')
    .if(body('paymentMethod').equals('card'))
    .notEmpty().withMessage('Expiry date is required').bail()
    .matches(/^(0[1-9]|1[0-2])\/\d{2}$/).withMessage('Expiry date must be MM/YY format')
    .custom((value) => {
      const [month, year] = value.split('/');
      const expiry = new Date(2000 + parseInt(year), parseInt(month) - 1, 1);
      if (expiry < new Date()) throw new Error('Card has expired');
      return true;
    }),

  // ── PAYPAL fields ─────────────────────────────────────────────
  body('paypalEmail')
    .if(body('paymentMethod').equals('paypal'))
    .notEmpty().withMessage('PayPal email is required').bail()
    .isEmail().withMessage('Invalid PayPal email'),

  // ── BANK TRANSFER fields ──────────────────────────────────────
  body('routingNumber')
    .if(body('paymentMethod').equals('bank_transfer'))
    .notEmpty().withMessage('Routing number is required').bail()
    .matches(/^\d{9}$/).withMessage('Routing number must be 9 digits'),

  body('accountNumber')
    .if(body('paymentMethod').equals('bank_transfer'))
    .notEmpty().withMessage('Account number is required').bail()
    .matches(/^\d{4,17}$/).withMessage('Account number must be 4–17 digits'),
];

router.post('/checkout',
  ...checkoutValidators,
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) return res.status(422).json({ errors: errors.array() });

    const data = matchedData(req);
    // Only the relevant fields for the chosen method are in `data`
    processPayment(data);
  }
);
```

// amount: 99.99 → isFloat ✓

// cardNumber:
//   if(body('paymentMethod').equals('card')) → 'card' === 'card' → condition TRUE
//   notEmpty() → req.body.cardNumber is undefined → FAIL: 'Card number is required'

//   condition TRUE → notEmpty() → FAIL: 'CVV is required for card payment'

//   condition TRUE → notEmpty() → FAIL: 'Expiry date is required'

//   SKIPPED entirely ✓ (not in errors)

## Problem 4 — Shopping Cart with Nested Array Validation

### Problem

Validate a shopping cart order that contains an array of items. Each item must have a valid product ID, a positive integer quantity, and an optional note. The cart must have at least one item and no more than 20.

```js
POST /orders
{
  "items": [
    { "productId": "507f1f77bcf86cd799439011", "quantity": 2 },
    { "productId": "507f1f77bcf86cd799439012", "quantity": 1, "note": "Gift wrap" }
  ],
  "shippingAddress": {
    "street": "123 Main St",
    "city": "Springfield",
    "zip": "12345"
  }
}
```

### Pattern Recognition
`body('items').isArray()` for the array itself. `body('items.*.field')` for per-item field validation using the wildcard `*`. Nested object validation with `body('shippingAddress.field')`. Async cross-item validation (duplicate productId check) in a custom validator on the array.

### Solution

```js
const { body, validationResult, matchedData } = require('express-validator');

const orderValidators = [
  // ── Top-level array ───────────────────────────────────────────
  body('items')
    .isArray({ min: 1, max: 20 })
    .withMessage('Order must contain 1–20 items')
    .bail()
    .custom((items) => {
      // Check for duplicate productIds in the order:
      const ids = items.map(item => item.productId);
      const unique = new Set(ids);
      if (unique.size !== ids.length) {
        throw new Error('Duplicate products in order — use quantity to order multiple');
      }
      return true;
    }),

  // ── Per-item validation (wildcard *) ─────────────────────────
  body('items.*.productId')
    .notEmpty().withMessage('Product ID is required').bail()
    .isMongoId().withMessage('Invalid product ID').bail()
    .custom(async (productId, { path }) => {
      const product = await Product.findById(productId);
      if (!product) throw new Error(`Product not found: ${productId}`);
      if (!product.isActive) throw new Error(`Product is unavailable: ${productId}`);
    }),

  body('items.*.quantity')
    .notEmpty().withMessage('Quantity is required').bail()
    .isInt({ min: 1, max: 999 })
    .withMessage('Quantity must be between 1 and 999')
    .toInt(),

  body('items.*.note')
    .optional()
    .trim()
    .isString()
    .isLength({ max: 200 }).withMessage('Note must be at most 200 characters'),

  // ── Nested shippingAddress object ─────────────────────────────
  body('shippingAddress')
    .exists().withMessage('Shipping address is required')
    .isObject().withMessage('Shipping address must be an object'),

  body('shippingAddress.street')
    .trim()
    .notEmpty().withMessage('Street address is required')
    .isLength({ max: 200 }),

  body('shippingAddress.city')
    .trim()
    .notEmpty().withMessage('City is required')
    .isLength({ max: 100 }),

  body('shippingAddress.zip')
    .trim()
    .matches(/^\d{5}(-\d{4})?$/)
    .withMessage('Invalid ZIP code (e.g., 12345 or 12345-6789)'),
];

router.post('/orders',
  ...orderValidators,
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) {
      return res.status(422).json({ errors: errors.array() });
    }
    const { items, shippingAddress } = matchedData(req);
    // items[0].quantity is now an integer (toInt() ran)
    return createOrder({ items, shippingAddress, userId: req.user.id })
      .then(order => res.status(201).json(order));
  }
);
```

## Problem 5 — Reusable Validation Middleware with Error Formatting

### Problem

Implement `createValidationMiddleware(chains, options)` — a factory that takes validation chains, runs them, and returns a standardized error response. Support custom error formatters, request-level logging of validation failures, and an option to throw errors instead of responding (for programmatic use).

```js
const validate = createValidationMiddleware([
  body('email').isEmail(),
  body('age').isInt({ min: 18 }),
], {
  onError: 'respond',    // 'respond' | 'throw' | 'next'
  statusCode: 422,
  logErrors: true,
});

router.post('/register', validate, handler);
```

### Pattern Recognition
Factory function returning middleware. `validationResult.withDefaults()` for custom formatting. `next(error)` vs `res.status().json()` vs `throw` for different error handling strategies.

### Solution

```js
const { validationResult } = require('express-validator');

const DEFAULT_FORMATTER = (error) => ({
  field:    error.path,
  message:  error.msg,
  location: error.location,
  received: error.value !== undefined ? String(error.value).slice(0, 100) : undefined,
});

/**
 * Factory: create a validation middleware from a set of chains.
 *
 * @param {ValidationChain[]} chains - express-validator chains
 * @param {object} options
 * @param {'respond'|'throw'|'next'} options.onError - how to handle failures
 * @param {number} options.statusCode - HTTP status for 'respond' mode (default 422)
 * @param {function} options.formatter - custom error formatter
 * @param {boolean} options.onlyFirstError - one error per field (default false)
 * @param {boolean|function} options.logErrors - log validation failures
 */
function createValidationMiddleware(chains, options = {}) {
  const {
    onError      = 'respond',
    statusCode   = 422,
    formatter    = DEFAULT_FORMATTER,
    onlyFirstError = false,
    logErrors    = false,
  } = options;

  // Create a custom validationResult with the formatter applied:
  const customResult = validationResult.withDefaults({ formatter });

  // Return an async middleware:
  return async function validationMiddleware(req, res, next) {
    // Run all chains in parallel:
    await Promise.all(chains.map(chain => chain.run(req)));

    const errors = customResult(req);
    if (errors.isEmpty()) return next(); // no errors — proceed

    const errorList = errors.array({ onlyFirstError });

    // Optional logging:
    if (logErrors) {
      const logFn = typeof logErrors === 'function' ? logErrors : console.warn;
      logFn({
        event:    'validation_failed',
        method:   req.method,
        path:     req.path,
        errors:   errorList,
        body:     req.body,   // careful: may contain sensitive data
        ip:       req.ip,
      });
    }

    // Error handling strategies:
    if (onError === 'respond') {
      return res.status(statusCode).json({
        status: 'error',
        code:   'VALIDATION_FAILED',
        errors: errorList,
      });
    }

    if (onError === 'throw') {
      const err = new Error('Validation failed');
      err.code         = 'VALIDATION_FAILED';
      err.statusCode   = statusCode;
      err.validationErrors = errorList;
      throw err; // caught by Express error handler
    }

    if (onError === 'next') {
      const err = Object.assign(new Error('Validation failed'), {
        statusCode,
        validationErrors: errorList,
      });
      return next(err); // pass to Express error handler middleware
    }
  };
}

// ─── Usage examples ───────────────────────────────────────────

// 1. Standard respond mode:
const validateUser = createValidationMiddleware([
  body('email').trim().isEmail(),
  body('age').isInt({ min: 18 }).toInt(),
]);

// 2. Custom formatter + logging:
const validateProduct = createValidationMiddleware([
  body('name').trim().notEmpty(),
  body('price').isFloat({ min: 0 }).toFloat(),
], {
  formatter: ({ path, msg }) => ({ field: path, error: msg }),
  logErrors: (info) => logger.warn('Validation failure', info),
  onlyFirstError: true,
});

// 3. Throw mode for programmatic use:
const validateOrder = createValidationMiddleware(orderValidators, { onError: 'throw' });

// Express error handler catches:
app.use((err, req, res, next) => {
  if (err.code === 'VALIDATION_FAILED') {
    return res.status(err.statusCode).json({
      status: 'error',
      errors: err.validationErrors,
    });
  }
  next(err);
});

router.post('/users',   validateUser,    userHandler);
router.post('/products', validateProduct, productHandler);
router.post('/orders',   validateOrder,   orderHandler);
```

## Problem 6 — Dynamic Pagination Query Validator

### Problem

Validate pagination query parameters with smart defaults. `page` and `limit` are optional integers with defaults applied via `customSanitizer`. `sort` must be one of the allowed columns. `order` must be `asc` or `desc`. `search` is optional and must be sanitized to prevent injection.

```js
GET /users?page=2&limit=25&sort=createdAt&order=desc&search=ada
```

### Solution

```js
const { query, validationResult, matchedData } = require('express-validator');

const ALLOWED_SORT_FIELDS = ['name', 'email', 'createdAt', 'updatedAt', 'age'];
const DEFAULT_LIMIT = 20;
const MAX_LIMIT     = 100;

const paginationValidators = [
  query('page')
    .optional()
    .customSanitizer((val) => {
      const n = parseInt(val, 10);
      return isNaN(n) || n < 1 ? 1 : n; // default to 1 if invalid or missing
    })
    .isInt({ min: 1 }).withMessage('Page must be a positive integer'),

  query('limit')
    .optional()
    .customSanitizer((val) => {
      const n = parseInt(val, 10);
      if (isNaN(n) || n < 1) return DEFAULT_LIMIT;
      return Math.min(n, MAX_LIMIT); // cap at max
    })
    .isInt({ min: 1, max: MAX_LIMIT })
    .withMessage(`Limit must be 1–${MAX_LIMIT}`),

  query('sort')
    .optional()
    .customSanitizer((val) => val || 'createdAt') // default sort field
    .isIn(ALLOWED_SORT_FIELDS)
    .withMessage(`Sort must be one of: ${ALLOWED_SORT_FIELDS.join(', ')}`),

  query('order')
    .optional()
    .toLowerCase()
    .customSanitizer((val) => val || 'desc') // default order
    .isIn(['asc', 'desc'])
    .withMessage('Order must be asc or desc'),

  query('search')
    .optional()
    .trim()
    .escape()         // sanitize: < → &lt;, > → &gt;, etc.
    .isLength({ max: 100 }).withMessage('Search term must be at most 100 characters'),
];

router.get('/users',
  ...paginationValidators,
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) return res.status(422).json({ errors: errors.array() });

    const { page = 1, limit = DEFAULT_LIMIT, sort = 'createdAt', order = 'desc', search } =
      matchedData(req, { locations: ['query'] });

    const skip = (page - 1) * limit;
    return User.find(search ? { $text: { $search: search } } : {})
      .sort({ [sort]: order === 'asc' ? 1 : -1 })
      .skip(skip)
      .limit(limit)
      .then(users => res.json({ page, limit, users }));
  }
);
```

## Problem 7 — `checkExact` for Strict API Contracts

### Problem

Implement a strict endpoint that rejects any request containing unknown fields, using `checkExact()`. The endpoint creates an API key with a specific set of allowed fields.

```js
POST /api-keys
{ "name": "My Key", "scopes": ["read", "write"], "expiresInDays": 30 }
// Extra fields like "isAdmin: true" must be rejected
```

### Solution

```js
const { checkExact, body, validationResult, matchedData } = require('express-validator');

const ALLOWED_SCOPES = ['read', 'write', 'admin', 'delete'];

const apiKeyChains = [
  body('name')
    .trim()
    .notEmpty().withMessage('API key name is required')
    .isLength({ min: 1, max: 50 }).withMessage('Name must be 1–50 characters'),

  body('scopes')
    .isArray({ min: 1 }).withMessage('At least one scope is required').bail()
    .custom((scopes) => {
      const invalid = scopes.filter(s => !ALLOWED_SCOPES.includes(s));
      if (invalid.length > 0) {
        throw new Error(`Invalid scopes: ${invalid.join(', ')}. Allowed: ${ALLOWED_SCOPES.join(', ')}`);
      }
      return true;
    }),

  body('expiresInDays')
    .optional()
    .isInt({ min: 1, max: 365 })
    .withMessage('Expiry must be 1–365 days')
    .toInt(),
];

router.post('/api-keys',
  // checkExact wraps the chains AND rejects unknown fields:
  checkExact(apiKeyChains, {
    message: (unknownFields) =>
      `Unknown fields are not allowed: ${unknownFields.map(f => f.path).join(', ')}`,
    locations: ['body'],
  }),
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) return res.status(422).json({ errors: errors.array() });

    const data = matchedData(req);
    return createApiKey({ ...data, userId: req.user.id })
      .then(key => res.status(201).json({ id: key.id, key: key.token }));
  }
);
```

## Quick Reference — Validation Chain Decision Tree

```
Choosing the right express-validator tool:
│
├── VALIDATING A SPECIFIC FIELD?
│   ├── From POST body          → body('fieldName')
│   ├── From URL :param         → param('paramName')
│   ├── From ?query=string      → query('fieldName')
│   ├── From request header     → header('Header-Name')
│   ├── From cookie             → cookie('cookieName')
│   └── From any location       → check('fieldName')
│
├── MAKING A FIELD OPTIONAL?
│   ├── Skip if absent          → .optional()
│   ├── Skip if null or absent  → .optional({ values: 'null' })
│   └── Skip if any falsy       → .optional({ values: 'falsy' })
│
├── VALIDATING A CONDITION?
│   ├── Negate next validator   → .not().isIn([...])
│   ├── Field A only if Field B → body('a').if(body('b').equals('value'))
│   ├── Either/or (OR logic)    → oneOf([[chain1, chain2], [chain3]])
│   └── Custom business rule    → .custom((val, {req}) => { throw / return })
│
├── STOPPING ON FIRST FAILURE?
│   ├── Stop this field's chain → .bail()
│   └── Stop all validation     → .bail({ level: 'request' })
│
├── TRANSFORMING VALUES?
│   ├── Built-in sanitizer      → .trim() .escape() .toInt() .normalizeEmail()
│   └── Custom transformation   → .customSanitizer((val) => transform(val))
│
├── VALIDATING ARRAYS/NESTED?
│   ├── Array exists/length     → body('items').isArray({ min:1, max:20 })
│   ├── Per-item field          → body('items.*.field').isString()
│   └── Nested object field     → body('address.city').notEmpty()
│
├── DEFINING VALIDATION AS OBJECTS?
│   └── checkSchema({ field: { validators... }, ... })
│
├── REJECTING UNKNOWN FIELDS?
│   └── checkExact(chains, { message, locations })
│
├── READING ERRORS?
│   ├── All errors              → validationResult(req).array()
│   ├── First per field         → validationResult(req).array({ onlyFirstError:true })
│   ├── As field map            → validationResult(req).mapped()
│   └── Throw if errors         → validationResult(req).throw()
│
└── READING SAFE VALIDATED DATA?
    ├── All validated fields    → matchedData(req)
    ├── From specific location  → matchedData(req, { locations:['body'] })
    └── Include unset optionals → matchedData(req, { includeOptionals:true })
```

## Common Bugs Checklist

Before shipping validation code, verify:

1. **Missing `bail()` before async validators?** — An expensive async validator (database lookup, HTTP call) runs even when a cheap synchronous validator already failed. Always add `.bail()` after `.notEmpty()`, `.isEmail()`, `.isMongoId()`, etc. before any `.custom(async ...)` validator. This can cause hundreds of unnecessary database calls per second under invalid input traffic.

2. **`validationResult(req)` called before all chains have run?** — Middleware are async — if any chain contains an async `custom()` validator and the handler doesn't await the chain's completion, `validationResult(req)` may return an empty result even though validation failed. Ensure all chains are middleware (added to the route array) or explicitly `await chain.run(req)` before calling `validationResult`.

3. **Reading `req.body` directly after sanitizers instead of `matchedData()`?** — Sanitizers mutate `req.body`, so reading it is technically correct — but it exposes your code to mass-assignment: if a client sends undeclared fields and you do `User.create(req.body)`, those extra fields go to the database. Use `matchedData(req)` to get only declared fields. Add `checkExact()` if your API must reject unknown fields entirely.

4. **`withMessage()` placed after the wrong validator?** — `withMessage('msg')` covers only the *immediately preceding* validator. `body('x').isEmail().isLength({ min: 5 }).withMessage('bad')` applies the message to `isLength`, not `isEmail`. Each validator needs its own `withMessage()` call: `.isEmail().withMessage('A').isLength({ min:5 }).withMessage('B')`.

5. **`optional()` not preventing validation of `null` or empty string?** — `optional()` with no arguments only skips validation when the value is `undefined` (the field is absent from the request). Sending `{ field: null }` or `{ field: "" }` still triggers validation. Use `optional({ values: 'null' })` for null, or `optional({ values: 'falsy' })` to skip all falsy values.

6. **Sanitizer order wrong — validating before sanitizing?** — `body('email').isEmail().trim()` validates the original (possibly whitespace-padded) string and then trims. The correct order is `body('email').trim().isEmail()` — sanitize first, validate the clean result. The same applies to `.toInt()` before numeric validators: always convert type before checking numeric constraints.

7. **`checkSchema()` wildcard field missing `optional: true`?** — `body('items.*.note')` without `optional: true` requires every item to have a `note` property. When validating arrays with optional per-item fields, add `optional: true` (or `optional: { values: 'falsy' }`) to the wildcard field schema entry.

8. **Not handling `type !== 'field'` in error responses?** — `oneOf()` produces errors of `type: 'alternative'` and `checkExact()` produces `type: 'unknown_fields'`. Code that does `errors.array().forEach(e => console.log(e.path, e.msg))` may fail or produce confusing output for these non-field error types. Filter with `errors.array().filter(e => e.type === 'field')` or handle each type explicitly.

9. **Password confirm validator reading `req.body.password` after a sanitizer changed it?** — If `.trim()` or another sanitizer runs on `password` and changes its value, and the `passwordConfirm` validator compares against `req.body.password`, it should see the post-sanitizer value. Verify the chain order: if both fields are validated in parallel (all chains in a route array run concurrently), one chain's sanitizer may not have finished before another chain's custom validator reads the same field.

10. **Using `escape()` when you want to store raw HTML but display it safely?** — `.escape()` permanently transforms `<` to `&lt;` in `req.body`. If you store this escaped value in the database and then display it via a template engine that already escapes output, the user sees `&lt;p&gt;` instead of `<p>`. Only use `.escape()` when the final output destination is raw HTML without further escaping. For most APIs storing raw input, rely on output-level escaping (template engines, DOMPurify on the frontend) instead of input-level escape sanitization.

---

**Final Tip:** At the 5 YOE level, the decisive signal for express-validator questions is understanding *when validation runs relative to business logic and why the ordering invariant matters* — not just knowing which methods exist. The mental model: *"each validation chain is an independent middleware that queues errors onto `req` as it runs; `validationResult(req)` is a snapshot reader that returns all accumulated errors at the moment it is called; the only correct pattern is all chains before the handler, then one `validationResult` check at the entry of the handler or in a shared `validate` middleware."* For sanitizers: *"sanitizers mutate the original request object in-place — every downstream middleware and handler sees the sanitized values; `matchedData()` is the safe alternative that returns only the fields your code explicitly declared validators for, preventing mass-assignment regardless of what extra fields the client sends."* For performance: *"`bail()` after synchronous validators and before `async custom()` validators is not just style — it's the difference between making zero database calls for malformed input and making one per validation field; on a server receiving 1000 invalid requests per second, missing `bail()` before an async validator multiplies database load by the number of async validators."*
