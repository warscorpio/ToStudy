# Static Files Serving, Compression Middleware — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is static file serving and how does it differ from dynamic request handling?**
A: Static file serving delivers pre-existing files from disk to the client with no server-side computation per request — the file content is the same regardless of who requests it or when. Dynamic request handling computes a response on the fly (database queries, template rendering, business logic). The distinction drives fundamentally different optimization strategies:

- **Static files**: optimization targets are I/O speed (reading from disk), protocol efficiency (caching, compression, HTTP/2 push), and bandwidth (serving compressed payloads). The same bytes are sent to every client — any client that caches the file costs zero server work for all subsequent requests.
- **Dynamic responses**: optimization targets are computation time, database query performance, and backend throughput. No two responses are guaranteed identical — caching is conditional on the request context.

The practical implication: static files should be served as close to the client as possible (CDN edge), with aggressive caching, by infrastructure optimized for file delivery — not by your Node.js application server whose CPU is expensive and should be reserved for dynamic computation.

**Q2. What are the main categories of static assets and how do their serving requirements differ?**
A: Different asset types have different optimal cache lifetimes and delivery patterns:

```
Asset type          │ Cache duration │ Compression │ CDN-appropriate │ Notes
────────────────────┼────────────────┼─────────────┼─────────────────┼─────────────────
JavaScript bundles  │ 1 year (∞)     │ Yes (high)  │ Yes             │ Content-hashed filenames
CSS stylesheets     │ 1 year (∞)     │ Yes (high)  │ Yes             │ Content-hashed filenames
HTML pages          │ No-cache or    │ Yes (medium)│ With caution    │ Must re-validate — contains
                    │ short (60s)    │             │                 │ references to other assets
Images/SVG          │ 1 year         │ SVG yes;    │ Yes             │ PNG/JPG pre-compressed;
                    │                │ JPEG/PNG no │                 │ SVG highly compressible
Web fonts (woff2)   │ 1 year         │ No          │ Yes             │ woff2 is already compressed
Videos              │ 1 year         │ No          │ Yes             │ Range requests essential
JSON/XML data       │ Short or none  │ Yes (high)  │ Conditional     │ Depends on data volatility
Favicon             │ 1 week-1 month │ No          │ Yes             │ Small file, low impact
Service workers     │ max 24 hours   │ Yes         │ With caution    │ Spec limits SW cache age
```

**Q3. What happens in Node.js's `express.static` when a request arrives for a static file?**
A: `express.static` (which wraps the `serve-static` package, which uses `send`) performs these steps:

```
Request: GET /static/bundle.js HTTP/1.1
         If-None-Match: "33a64df551425fcc55e4d42a148795d9f25f89d"
         Accept-Encoding: gzip, br, deflate

Step 1: Path resolution
  - Combine mount path + URL path: /var/app/public/bundle.js
  - Sanitize: decode %XX, resolve ../ (path traversal protection)
  - If directory: look for index.html (if dotfiles: 'deny', block hidden files)

Step 2: File existence check
  - fs.stat() → check existence + get mtime, size

Step 3: Conditional request handling (before reading file)
  - Check If-None-Match vs ETag → 304 Not Modified if match
  - Check If-Modified-Since vs Last-Modified → 304 if not modified
  - If 304: no file read, no bandwidth consumed

Step 4: Set response headers
  - Content-Type from MIME type lookup (path.extname → mime.lookup)
  - Last-Modified: file's mtime
  - ETag: generated from file size + mtime (weak ETag)
  - Cache-Control: based on maxAge option
  - Accept-Ranges: bytes (enables range requests)

Step 5: Range request handling (optional)
  - Parse Range: bytes=0-1023 header
  - 206 Partial Content with requested byte range

Step 6: Send file
  - fs.createReadStream() with appropriate range
  - Pipe through any compression transform
  - Stream to response

Step 7: Compression
  - If compression middleware is active, the response stream is wrapped
  - Checks Accept-Encoding: gzip, br
  - Compresses on-the-fly (or serves pre-compressed variant)
```

## Section 2: HTTP Caching for Static Files

**Q4. What is the difference between `Cache-Control`, `ETag`, `Last-Modified`, and `Expires`, and which combination is correct for long-lived static assets?**
A: These are four HTTP headers that control caching behavior at the browser and CDN level, each addressing a different aspect:

```
Cache-Control: max-age=31536000, immutable
└── Freshness: how long the cache can serve this response WITHOUT revalidating
    max-age=31536000 = 1 year in seconds (the maximum browsers respect)
    immutable: hint that the resource won't change during max-age (skip revalidation)

ETag: "33a64df551425fcc55e4d42a148795d9f25f89d"
└── Validation: a fingerprint of the content
    Used in If-None-Match: <etag> for revalidation requests
    Strong ETag: exact byte identity
    Weak ETag (W/"..."):  semantically equivalent but may differ in bytes

Last-Modified: Tue, 15 Jan 2024 09:30:00 GMT
└── Validation: timestamp of last content change
    Used in If-Modified-Since: <date> for revalidation
    Less reliable than ETag (1-second granularity, clock skew between servers)

Expires: Tue, 15 Jan 2025 09:30:00 GMT
└── Legacy freshness: absolute expiry timestamp (HTTP/1.0)
    Superseded by Cache-Control: max-age in HTTP/1.1
    Avoid: relies on synchronized client-server clocks
```

**Correct pattern for content-hashed static assets** (JS bundles with `bundle.a1b2c3.js`):

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=31536000, immutable
Content-Type: application/javascript; charset=utf-8
ETag: "a1b2c3d4e5f6..."
Content-Encoding: gzip
Content-Length: 45231
Vary: Accept-Encoding
```

**Correct pattern for HTML** (which must always be fresh to pick up new asset hashes):

```http
HTTP/1.1 200 OK
Cache-Control: no-cache
ETag: "xyz789"
Content-Type: text/html; charset=utf-8
```

`no-cache` means "don't use the cached response without revalidating" — the browser must send a conditional request. If the ETag hasn't changed, it gets a 304 Not Modified instantly. This ensures HTML is always fresh while still benefiting from revalidation efficiency.

**Q5. What is an ETag, how is it generated, and what is the 304 Not Modified response path?**
A: An ETag (Entity Tag) is a string that identifies a specific version of a resource. When a browser has a cached version, it sends the cached ETag back on revalidation requests; the server returns 304 if the content hasn't changed, saving the payload transfer:

```javascript
// How express.static/serve-static generates ETags:
// Uses file stats (mtime + size) for a weak ETag:
const etag = `W/"${mtime.getTime().toString(16)}-${size.toString(16)}"`;
// Example: W/"18e5c9a3-1a2b3"

// A strong content-based ETag (your own middleware):
import crypto from 'node:crypto';
import fs from 'node:fs';

function generateStrongETag(filePath) {
    const content = fs.readFileSync(filePath);
    return `"${crypto.createHash('sha256').update(content).digest('hex').slice(0, 27)}"`;
}

// The 304 flow:
//
// Initial request:
// GET /bundle.a1b2c3.js HTTP/1.1
//
// Response:
// HTTP/1.1 200 OK
// ETag: "abc123"
// Cache-Control: max-age=3600
// [45KB of JavaScript]
//
// Client caches response + ETag.
// 3601 seconds later (cache expired), client wants the file again:
//
// Conditional request:
// GET /bundle.a1b2c3.js HTTP/1.1
// If-None-Match: "abc123"
//
// Server checks: current file's ETag still "abc123"?
// YES → 304 Not Modified (empty body — no bandwidth)
// NO  → 200 OK + new ETag + new content

// Express.static handles this automatically.
// For custom static servers:
app.get('/file', (req, res) => {
    const currentETag = generateETag(filePath);
    if (req.headers['if-none-match'] === currentETag) {
        return res.status(304).end();  // No body!
    }
    res.setHeader('ETag', currentETag);
    res.setHeader('Cache-Control', 'max-age=3600');
    res.sendFile(filePath);
});
```

**Q6. What is the cache-busting pattern with content hashes and why is it the gold standard for static asset versioning?**
A: Content hashing (fingerprinting) embeds a hash of the file's content in its filename. The URL changes when the content changes, making CDN/browser cache invalidation automatic and reliable:

```
Without content hashing (URL versioning):
  /static/bundle.js?v=1.2.3     → user may have old v=1.2.2 cached
  /static/bundle.js?v=1.2.4     → URL changes, cache miss, new file served
  Problem: query strings are sometimes ignored by CDNs (Cloudflare ignores them
           by default for cache keying). URL versioning is unreliable at CDN layer.

With content hashing:
  /static/bundle.a1b2c3.js      → Cache-Control: max-age=31536000, immutable
  /static/bundle.d4e5f6.js      → Different content → different URL → automatic cache miss
  Benefits:
  1. CDN caches with max-age=1 year — zero origin requests for cached assets
  2. Old and new versions coexist during deployments (users in the middle of a session
     still load old bundle; new page loads get new bundle)
  3. Cache invalidation is URL-based (no CDN purge API needed)
  4. Rollback: just re-deploy the old bundle (its URL hasn't changed)

Implementation (webpack/vite/rollup):
  output: { filename: '[name].[contenthash].js' }
  // webpack content hash is based on the file's actual content
  // → identical content = same hash = same URL = cache hit even after re-deploy

HTML references the hashed bundle names:
  <script src="/static/bundle.a1b2c3.js"></script>
  HTML itself: Cache-Control: no-cache (always fresh, always gets latest bundle names)
```

## Section 3: Compression

**Q7. What is HTTP content encoding compression and which algorithms should you know?**
A: Content encoding compression reduces the size of the response body in transit between server and client. The client advertises supported algorithms via `Accept-Encoding`; the server chooses one and indicates it via `Content-Encoding`:

```http
Request:  Accept-Encoding: br, gzip, deflate, identity
Response: Content-Encoding: br
          Vary: Accept-Encoding
```

**The three relevant algorithms**:

**Gzip** (`gzip`): 1992, RFC 1952. Based on DEFLATE (LZ77 + Huffman coding). Universally supported — every browser and HTTP client since the mid-1990s. Compression ratio: good (typically 70-80% reduction for text). Compression speed: fast. Decompression speed: very fast. The baseline — use gzip when brotli isn't available.

**Brotli** (`br`): 2015, designed by Google for web compression. RFC 7932. Based on LZ77, Huffman coding, and a static dictionary of common web strings (HTML/CSS/JS keywords, common URLs, common attributes). Better compression ratio than gzip (typically 15-25% smaller output). Slower to compress at high quality levels (pre-compress for production). Decompression speed comparable to gzip. Supported in all modern browsers. Use brotli for production static assets.

**Deflate** (`deflate`): DEFLATE algorithm wrapped in zlib format. Historical implementation confusion (some servers sent raw DEFLATE, some sent zlib-wrapped DEFLATE) made it unreliable. Avoid in new implementations.

**Quality levels** (higher = smaller output, slower compression):
- Gzip: 1-9 (default: 6). For on-the-fly: 1-4 (fast). For pre-compression: 9.
- Brotli: 0-11 (default: 11). For on-the-fly: 4-6. For pre-compression: 11.

**Q8. How does the `compression` middleware work in Express, and what are its configuration options?**
A:

```javascript
import compression from 'compression';
import express from 'express';

const app = express();

// Basic usage — compress all responses above threshold:
app.use(compression());

// Production configuration:
app.use(compression({
    // Minimum size to compress (default: 1024 bytes = 1KB)
    // Compressing tiny responses wastes CPU — the compressed output may be larger
    threshold: 1024,

    // Compression level for gzip: 1 (fastest) to 9 (best compression)
    // For dynamic responses: lower level (faster) is usually right
    // pre-compress static files at level 9 separately
    level: 6,  // default (balance of speed and ratio)

    // Memory level for gzip: 1-9, higher = more memory = faster = better compression
    memLevel: 8,

    // Custom filter: decide per-response whether to compress
    filter: (req, res) => {
        // Don't compress if the requester explicitly says not to:
        if (req.headers['x-no-compression']) return false;
        // Fall back to default filter (checks Content-Type):
        return compression.filter(req, res);
    },

    // Strategy: Z_DEFAULT_STRATEGY, Z_FILTERED, Z_HUFFMAN_ONLY, Z_RLE, Z_FIXED
    strategy: require('zlib').constants.Z_DEFAULT_STRATEGY
}));

// What the default filter compresses (mime-type check):
// text/*, application/json, application/javascript, application/xml,
// image/svg+xml — anything with compressible content type
// Does NOT compress: image/jpeg, image/png, image/webp, video/*, audio/* (already compressed)

// compression middleware location — MUST be before express.static and route handlers:
app.use(compression());          // 1. Compression wrapper
app.use(express.static('public')); // 2. Static file serving (will be compressed)
app.get('/api/data', handler);   // 3. API routes (will be compressed)
```

**Q9. How does `compression` middleware integrate with response streams?**
A: `compression` wraps the response's write methods (`res.write`, `res.end`) with a compression transform stream. It defers the decision to compress until the response headers are being sent:

```javascript
// Simplified internals of what compression middleware does:
function compressionMiddleware(req, res, next) {
    const acceptEncoding = req.headers['accept-encoding'] || '';

    // Choose algorithm (brotli > gzip > identity)
    const encoding = acceptEncoding.includes('br') ? 'br' :
                     acceptEncoding.includes('gzip') ? 'gzip' : null;

    if (!encoding) return next();  // Client doesn't accept compression

    // Create compression stream
    const compressStream = encoding === 'br'
        ? zlib.createBrotliCompress({ params: { [zlib.constants.BROTLI_PARAM_QUALITY]: 4 } })
        : zlib.createGzip({ level: 6 });

    // Intercept the response before it goes out:
    const originalWrite = res.write.bind(res);
    const originalEnd = res.end.bind(res);

    // Pipe res through compressStream
    compressStream.pipe(res);  // compressStream output goes to actual response socket

    res.write = (chunk) => compressStream.write(chunk);  // intercept writes
    res.end = (chunk) => {
        if (chunk) compressStream.write(chunk);
        compressStream.end();  // signals end of input → flushes compressed output
    };

    // Set headers (but not Content-Length — we don't know compressed size ahead of time)
    res.setHeader('Content-Encoding', encoding);
    res.setHeader('Vary', 'Accept-Encoding');  // CRITICAL — CDN must vary cache by encoding
    res.removeHeader('Content-Length');  // Remove: compression changes the length

    next();
}
```

**Q10. What is the `Vary: Accept-Encoding` header and why is it critical when serving compressed responses?**
A: `Vary` tells caches (CDNs, proxy caches, browser caches) which request headers affect the response. Without `Vary: Accept-Encoding`, a CDN might cache the gzip version of a file and serve it to a client that doesn't support gzip (or vice versa):

```
Without Vary: Accept-Encoding:
CDN request 1: Accept-Encoding: gzip → server returns gzip bundle → CDN caches it
CDN request 2: Accept-Encoding: (none, old browser) → CDN serves cached gzip → broken!

With Vary: Accept-Encoding:
CDN caches separate versions per Accept-Encoding value:
  Cache key: URL + (Accept-Encoding: gzip)   → gzip response
  Cache key: URL + (Accept-Encoding: br)     → brotli response
  Cache key: URL + (no Accept-Encoding)      → identity response
Each client gets the right version.

// compression middleware sets this automatically.
// If you set Content-Encoding manually, you MUST also set Vary: Accept-Encoding:
res.setHeader('Content-Encoding', 'gzip');
res.setHeader('Vary', 'Accept-Encoding');  // Don't forget this!

// CDN behavior with Vary:
// Cloudflare: respects Vary but normalizes Accept-Encoding to reduce cache versions
//             (all gzip-accepting clients get one cache entry)
// Fastly: respects Vary natively
// AWS CloudFront: requires explicit configuration to respect Vary: Accept-Encoding
//   → In CloudFront: add Accept-Encoding to the "Cache Policy Allowed Headers"
//   → Or use the "Compress Objects Automatically" option (CloudFront does compression itself)
```

## Section 4: Pre-Compression and Production Optimization

**Q11. What is pre-compression and why is it superior to on-the-fly compression for static assets?**
A: On-the-fly compression (what `compression` middleware does) re-compresses the same file on every request that isn't cached. Pre-compression compresses files once at build time and stores the compressed variants alongside the originals. The server then serves the pre-compressed file directly without any CPU work per request:

```bash
# Build step: pre-compress all static assets
# Gzip at max compression:
find dist/ -type f \( -name "*.js" -o -name "*.css" -o -name "*.html" \) \
  -exec gzip -k -9 {} \;
# Creates: bundle.a1b2c3.js AND bundle.a1b2c3.js.gz

# Brotli at max compression (quality 11 = best ratio, slow — acceptable at build time):
find dist/ -type f \( -name "*.js" -o -name "*.css" -o -name "*.html" \) \
  -exec brotli -k --quality=11 {} \;
# Creates: bundle.a1b2c3.js AND bundle.a1b2c3.js.br
```

Serving pre-compressed files in Nginx (the standard production approach):

```nginx
server {
    root /var/app/dist;

    # Enable gzip_static module to serve .gz files automatically
    gzip_static on;

    # Serve .br files automatically (requires nginx-module-brotli or openresty)
    brotli_static on;

    location /static/ {
        # With gzip_static on:
        # Request for /static/bundle.js with Accept-Encoding: gzip
        # → nginx looks for /static/bundle.js.gz first
        # → If found AND Accept-Encoding includes gzip: serve the .gz file directly
        # → Sets Content-Encoding: gzip automatically
        # → No compression CPU work at request time

        expires 1y;
        add_header Cache-Control "public, max-age=31536000, immutable";
        add_header Vary Accept-Encoding;
    }
}
```

Node.js serving pre-compressed files (when nginx isn't in front):

```javascript
import express from 'express';
import path from 'path';
import fs from 'fs';

function servePrecompressed(staticDir) {
    return (req, res, next) => {
        const filePath = path.join(staticDir, req.path);
        const acceptEncoding = req.headers['accept-encoding'] || '';

        // Try brotli first (best compression), then gzip, then identity
        const candidates = [];
        if (acceptEncoding.includes('br') && fs.existsSync(filePath + '.br')) {
            candidates.push({ path: filePath + '.br', encoding: 'br' });
        }
        if (acceptEncoding.includes('gzip') && fs.existsSync(filePath + '.gz')) {
            candidates.push({ path: filePath + '.gz', encoding: 'gzip' });
        }

        if (candidates.length === 0) return next();

        const { path: compressedPath, encoding } = candidates[0];
        res.setHeader('Content-Encoding', encoding);
        res.setHeader('Vary', 'Accept-Encoding');
        // Content-Type must be the ORIGINAL file's type, not the compressed file's type
        const contentType = mime.lookup(req.path) || 'application/octet-stream';
        res.setHeader('Content-Type', contentType);

        res.sendFile(compressedPath);
    };
}

app.use('/static', servePrecompressed('/var/app/dist'));
app.use('/static', express.static('/var/app/dist'));  // Fallback for non-compressible files
```

**Q12. What are the performance implications of using Node.js to serve static files in production, and what is the recommended architecture?**
A: Node.js is not optimized for static file serving — it's a JavaScript runtime designed for computation, not I/O-heavy file delivery. Using Node.js for static files:

```
Node.js for static files:
  - Each file read goes through JavaScript event loop
  - Compression is CPU-bound → competes with application logic
  - No sendfile() syscall optimization (nginx uses this to bypass user space)
  - No kernel-level caching optimization
  - JS/GC overhead per request even for cache hits

nginx for static files (in front of Node.js):
  - Uses sendfile() syscall → file data goes directly from page cache to socket
    (bypasses user space → zero data copies)
  - Built-in gzip_static / brotli_static modules
  - Efficient memory mapping for large files
  - Kernel-level connection handling
  - 10-100× faster per-file throughput than Node.js

CDN in front of everything:
  - Static files served from edge nodes near users
  - Node.js only handles requests CDN can't cache (authenticated, personalized)
  - Zero static file requests reach your Node.js process in steady state
```

**Recommended production architecture**:
```
Browser → CDN (serves 95%+ of static requests from cache)
              ↓ (cache miss — only on new deployments)
          nginx (reverse proxy + static file serving from disk)
              ↓ (non-static requests only)
          Node.js (application logic, API, SSR)
              ↓ (database, external APIs)
          PostgreSQL, Redis, etc.
```

## Section 5: Security in Static File Serving

**Q13. What are the security vulnerabilities specific to static file serving and how does `express.static` mitigate them?**
A:

**Path traversal** — the most critical vulnerability. A malicious URL like `/static/../../../../etc/passwd` could potentially read sensitive files outside the static directory:

```javascript
// express.static / serve-static mitigates this via:
// 1. path.resolve() + ensureRoot: the final path MUST start with root
// 2. Decoding %2F (%2F = /) and %2E (%2E = .) in URL before comparison
// 3. Normalizing .. sequences before checking against root

// Example of what serve-static does internally:
function safePath(root, urlPath) {
    // Decode URL encoding first (prevents %2E%2E%2F bypass)
    const decoded = decodeURIComponent(urlPath);
    // Normalize: /static/../../etc/passwd → /etc/passwd
    const normalized = path.normalize(decoded);
    // Resolve against root
    const full = path.resolve(root, normalized.slice(1));
    // Check: must start with root
    if (!full.startsWith(root)) {
        throw new Error('Path traversal attempt');
    }
    return full;
}

// NEVER do this (vulnerable to path traversal):
app.get('/static/*', (req, res) => {
    res.sendFile(req.params[0]);  // NO! Unsanitized path
});

// Use express.static or validate paths explicitly:
app.use('/static', express.static(path.resolve('./public'), {
    dotfiles: 'deny',   // Deny access to .env, .gitignore, etc.
    index: false,       // Don't serve directory indexes
    redirect: false     // Don't redirect directory URLs to add trailing /
}));
```

**Dotfile exposure** — `.env`, `.git/`, `.htpasswd` contain secrets and should never be served:

```javascript
express.static('./public', {
    dotfiles: 'deny'    // 'allow' | 'deny' | 'ignore' (default: 'ignore')
    // 'ignore': no file not found error, just 404
    // 'deny': explicit 403 Forbidden
    // 'allow': serve dotfiles (never use in production)
});
```

**Directory listing** — exposing directory contents reveals file structure:

```javascript
express.static('./public', {
    index: false  // Don't serve index.html for directory requests
    // Without index.html, a directory request returns 404 (not a listing)
});
```

**MIME type sniffing** — browsers sniff content type if not provided, enabling XSS via uploaded SVG:

```javascript
// Always set X-Content-Type-Options: nosniff
app.use((req, res, next) => {
    res.setHeader('X-Content-Type-Options', 'nosniff');
    next();
});
// express.static sets Content-Type correctly based on extension
// The nosniff header tells the browser to trust our Content-Type and not sniff
```

## Section 6: MIME Types and Content Negotiation

**Q14. How are MIME types determined for static files and what happens when the type is wrong?**
A: MIME types are determined from the file extension using a lookup table. Wrong MIME types cause browsers to mishandle responses:

```javascript
import mime from 'mime';

// Express.static uses the 'mime' package internally:
mime.lookup('file.js');       // 'application/javascript'
mime.lookup('file.ts');       // 'video/mp2t' (TypeScript files have no standard MIME)
mime.lookup('file.json');     // 'application/json'
mime.lookup('file.woff2');    // 'font/woff2'
mime.lookup('file.svg');      // 'image/svg+xml'
mime.lookup('unknown.xyz');   // 'application/octet-stream' (fallback)

// Adding custom MIME types:
import mime from 'mime';
mime.define({ 'application/wasm': ['wasm'] }, { force: true });

// Wrong MIME types and their consequences:
// JavaScript served as text/plain → browser won't execute it (CORB)
// CSS served as text/plain → browser won't apply it
// Images served as application/octet-stream → browser prompts download instead of displaying
// JSON served as text/html → XSS risk if content contains HTML (JSONP-style attacks)
// Fonts: must be served with correct MIME for CORS font loading to work
// WebAssembly: MUST be application/wasm for streaming compilation to work

// Custom mime type configuration in express.static:
// express.static doesn't expose direct MIME type customization
// Workaround: use send package directly with custom options
import send from 'send';
app.get('/assets/*', (req, res) => {
    send(req, req.path, {
        root: './public',
        extensions: ['html', 'htm']
    })
    .on('headers', (res, path) => {
        // Override MIME type here if needed
        if (path.endsWith('.ts')) {
            res.setHeader('Content-Type', 'text/typescript');
        }
    })
    .pipe(res);
});
```

**Q15. What are range requests and why are they essential for large static files like videos?**
A: Range requests allow clients to download specific byte ranges of a file — enabling: video scrubbing (seeking to arbitrary positions), download resumption after connection drops, and parallel downloads (multiple threads downloading different ranges):

```javascript
// Server signals range request support:
// Accept-Ranges: bytes  →  client can use Range header

// Client requests a specific range (video player seeking to position 2 minutes in):
// GET /video/movie.mp4 HTTP/1.1
// Range: bytes=10485760-20971519  (bytes 10MB-20MB)

// Server response:
// HTTP/1.1 206 Partial Content
// Content-Range: bytes 10485760-20971519/104857600  (requested range / total size)
// Content-Length: 10485759  (size of this chunk)
// Accept-Ranges: bytes
// Content-Type: video/mp4

// express.static handles range requests automatically via the 'send' package.
// For custom implementations:
app.get('/video/*', (req, res) => {
    const filePath = path.join('./media', req.params[0]);
    const stat = fs.statSync(filePath);
    const fileSize = stat.size;

    if (req.headers.range) {
        const [startStr, endStr] = req.headers.range.replace(/bytes=/, '').split('-');
        const start = parseInt(startStr, 10);
        const end = endStr ? parseInt(endStr, 10) : fileSize - 1;
        const chunkSize = end - start + 1;

        res.status(206);
        res.setHeader('Content-Range', `bytes ${start}-${end}/${fileSize}`);
        res.setHeader('Accept-Ranges', 'bytes');
        res.setHeader('Content-Length', chunkSize);
        res.setHeader('Content-Type', 'video/mp4');

        fs.createReadStream(filePath, { start, end }).pipe(res);
    } else {
        // Full file request
        res.status(200);
        res.setHeader('Content-Length', fileSize);
        res.setHeader('Content-Type', 'video/mp4');
        res.setHeader('Accept-Ranges', 'bytes');
        fs.createReadStream(filePath).pipe(res);
    }
});
```

## Section 7: Advanced Serving Patterns

**Q16. What is HTTP/2 Server Push and how does it apply to static file delivery?**
A: HTTP/2 Server Push allows the server to proactively send resources to the client before they're requested — the server "pushes" CSS and JavaScript bundles at the same time it sends HTML, eliminating the round-trip where the browser must parse HTML before discovering and requesting assets:

```javascript
import spdy from 'spdy';  // HTTP/2 / SPDY support for Node.js
// Or use the native http2 module for more control

// With express + spdy (simplest HTTP/2 approach):
const options = {
    key: fs.readFileSync('./server.key'),
    cert: fs.readFileSync('./server.crt')
};

spdy.createServer(options, app).listen(443);

// Server push in a route handler:
app.get('/', (req, res) => {
    // Push CSS before sending HTML
    if (res.push) {  // Only in HTTP/2 connections
        const cssStream = res.push('/static/styles.css', {
            status: 200,
            method: 'GET',
            request: { accept: '*/*' },
            response: {
                'content-type': 'text/css',
                'cache-control': 'max-age=3600'
            }
        });
        fs.createReadStream('./public/styles.css').pipe(cssStream);

        // Push JS bundle
        const jsStream = res.push('/static/bundle.js', {
            status: 200,
            method: 'GET',
            request: { accept: '*/*' },
            response: {
                'content-type': 'application/javascript',
                'cache-control': 'max-age=31536000'
            }
        });
        fs.createReadStream('./public/bundle.js').pipe(jsStream);
    }

    // Then send the HTML
    res.sendFile('./public/index.html');
});

// Modern alternative: Link header with rel=preload
// (hints to CDN and browser without the HTTP/2 push complexity):
res.setHeader('Link', [
    '</static/styles.css>; rel=preload; as=style',
    '</static/bundle.js>; rel=preload; as=script'
].join(', '));

// Caveat: HTTP/2 Push is being deprecated by major browsers
// (Chrome removed it, Safari never fully supported it)
// Link preload headers are the modern replacement
```

**Q17. What is `sendFile` vs `createReadStream` vs `pipe` in Node.js static serving, and when does each apply?**
A:

```javascript
import fs from 'node:fs';

// Option 1: res.sendFile (Express) — highest-level, handles everything
app.get('/file', (req, res) => {
    res.sendFile(path.resolve('./public/file.txt'), {
        maxAge: '1d',        // Sets Cache-Control
        headers: { 'X-Custom': 'value' }
    });
    // Handles: Content-Type, Last-Modified, ETag, Range requests,
    //          streaming, error handling, directory handling
    // Uses: send package internally → streams the file
});

// Option 2: res.download — sends with Content-Disposition: attachment (forces download)
app.get('/download', (req, res) => {
    res.download('./private/report.pdf', 'my-report.pdf');
    // Content-Disposition: attachment; filename="my-report.pdf"
    // Browser prompts save dialog instead of displaying inline
});

// Option 3: fs.createReadStream().pipe(res) — lowest level, maximum control
app.get('/stream', (req, res) => {
    const fileStream = fs.createReadStream('./large-file.csv', {
        highWaterMark: 64 * 1024  // 64KB chunks
    });

    res.setHeader('Content-Type', 'text/csv');
    res.setHeader('Content-Disposition', 'attachment; filename="export.csv"');

    // Pipe with error handling:
    fileStream
        .on('error', (err) => {
            if (!res.headersSent) {
                res.status(500).json({ error: 'File read failed' });
            } else {
                res.destroy();  // Abort the connection if headers already sent
            }
        })
        .pipe(res);

    // Handle client disconnect (don't keep reading if nobody's listening):
    req.on('close', () => fileStream.destroy());
});

// Option 4: Streaming transformation + pipe (compressing on-the-fly for large files)
import { createGzip } from 'node:zlib';

app.get('/compressed-export', async (req, res) => {
    res.setHeader('Content-Type', 'application/octet-stream');
    res.setHeader('Content-Encoding', 'gzip');
    res.setHeader('Content-Disposition', 'attachment; filename="export.csv.gz"');
    res.setHeader('Vary', 'Accept-Encoding');

    const fileStream = fs.createReadStream('./large-file.csv');
    const gzipStream = createGzip({ level: 6 });

    pipeline(fileStream, gzipStream, res, (err) => {
        if (err) logger.error('Streaming failed', err);
    });
    // pipeline() handles cleanup of all streams on error — better than manual .pipe()
});
```

## Section 8: Scenario-Based Questions

**Q18. "Your SPA (React/Vue app) is deployed. Users report that after deploying a new version, they still see the old version for hours. How do you fix this with static file serving and caching strategy?"**
A: This is a classic cache invalidation problem — the HTML is cached with long max-age and users keep getting the old version, which references old bundle filenames:

**Root cause analysis**:
```
Typical broken setup:
  index.html → Cache-Control: max-age=3600 (1 hour) ← TOO LONG
  bundle.js  → Cache-Control: max-age=3600

After deployment:
  Old bundle.js is overwritten with new content at the SAME URL
  CDN/browser serves cached old bundle.js for up to 1 hour
  Even if HTML is served fresh, old bundle.js is served from cache
```

**Correct fix**:
```javascript
// 1. Content-hash ALL versioned assets (webpack/vite handles this):
// dist/
//   index.html                     ← no hash (entry point)
//   assets/bundle.a1b2c3.js        ← content-hashed
//   assets/styles.d4e5f6.css       ← content-hashed
//   assets/logo.g7h8i9.png         ← content-hashed

// 2. Serve HTML with no-cache (always revalidate):
app.get('/', (req, res) => {
    res.setHeader('Cache-Control', 'no-cache');  // Always revalidate
    res.setHeader('ETag', htmlEtag);             // Efficient: 304 if unchanged
    res.sendFile('./dist/index.html');
});

// 3. Serve hashed assets with immutable long cache:
app.use('/assets', (req, res, next) => {
    res.setHeader('Cache-Control', 'public, max-age=31536000, immutable');
    next();
}, express.static('./dist/assets'));

// 4. CDN configuration:
//   - HTML: TTL=0 (always fetch from origin) → origin sets Cache-Control: no-cache
//   - /assets/*: TTL=1year (cache by URL, content-hash = unique URL per version)

// 5. Test by checking:
//   curl -I https://yourapp.com/          → Cache-Control: no-cache
//   curl -I https://yourapp.com/assets/bundle.a1b2c3.js → Cache-Control: max-age=31536000, immutable
```

**Q19. "You're building a Node.js API that returns large JSON responses (10-50MB). Response time under gzip compression spikes to 8 seconds on large responses. What's happening and how do you fix it?"**
A: The issue is synchronous compression blocking the event loop — `compression` middleware with a high compression level blocks Node.js's single thread for the duration of compression:

**Diagnosis**:
```javascript
// HIGH COMPRESSION LEVEL (default zlib level 6-9) blocks for large payloads:
// 50MB JSON at level 6 → ~500ms-2s of CPU blocking
// During this time: no other requests can be processed → 8s queue time for concurrent requests

// Diagnosis:
const start = process.hrtime.bigint();
const compressed = zlib.gzipSync(largeJsonBuffer, { level: 9 });
const elapsed = Number(process.hrtime.bigint() - start) / 1_000_000;
console.log(`Compression took ${elapsed}ms`);  // Could be 500ms-2000ms for 50MB!
```

**Solutions**:

```javascript
// Solution 1: Lower compression level (balance speed vs ratio)
app.use(compression({ level: 1 }));
// Level 1 is much faster, ratio only slightly worse for JSON
// 50MB JSON: level 9 → 5MB (90% reduction), level 1 → 6MB (88% reduction)
// vs blocking for 2s vs 50ms → clear winner

// Solution 2: Pre-compress large responses (if they're cacheable)
app.get('/api/large-dataset', async (req, res) => {
    const cacheKey = 'large-dataset-cache';
    let compressed = await redis.getBuffer(cacheKey);

    if (!compressed) {
        const data = await db.getLargeDataset();
        const json = JSON.stringify(data);
        // Compress in a Worker Thread (doesn't block event loop):
        compressed = await compressInWorker(json);
        await redis.setex(cacheKey, 300, compressed);  // Cache 5 minutes
    }

    res.setHeader('Content-Encoding', 'gzip');
    res.setHeader('Content-Type', 'application/json');
    res.setHeader('Vary', 'Accept-Encoding');
    res.send(compressed);
});

// Compress in a Worker Thread:
import { Worker, isMainThread, parentPort, workerData } from 'node:worker_threads';
import { gzip } from 'node:zlib';
import { promisify } from 'node:util';

const gzipAsync = promisify(gzip);

function compressInWorker(data) {
    return new Promise((resolve, reject) => {
        const worker = new Worker(`
            const { workerData, parentPort } = require('node:worker_threads');
            const zlib = require('node:zlib');
            zlib.gzip(Buffer.from(workerData), { level: 6 }, (err, result) => {
                if (err) parentPort.postMessage({ error: err.message });
                else parentPort.postMessage({ result: result.toString('base64') });
            });
        `, { eval: true, workerData: data });
        worker.on('message', ({ result, error }) => {
            if (error) reject(new Error(error));
            else resolve(Buffer.from(result, 'base64'));
        });
    });
}

// Solution 3: Stream the response instead of buffering
// Streaming sends chunks as they're generated — client sees data faster
app.get('/api/large-dataset', async (req, res) => {
    const cursor = db.getLargeDatasetCursor();
    res.setHeader('Content-Type', 'application/json');
    res.write('[');  // Open JSON array
    let first = true;
    for await (const row of cursor) {
        if (!first) res.write(',');
        res.write(JSON.stringify(row));  // compression middleware wraps res.write
        first = false;
    }
    res.write(']');  // Close JSON array
    res.end();  // Flush and close
});
// With compression middleware at level 1, streaming keeps buffers small
// and avoids the 50MB-in-memory problem entirely
```

**Q20. "You're setting up a Node.js server that serves a React SPA with an Express API. The /api/* routes should not be compressed (internal only) but /static/* should be served with Brotli + aggressive caching + pre-compressed files. Design the middleware stack."**
A: Complete production-grade middleware stack:

```javascript
import express from 'express';
import compression from 'compression';
import path from 'path';
import { fileURLToPath } from 'url';
import helmet from 'helmet';

const __dirname = path.dirname(fileURLToPath(import.meta.url));
const DIST_DIR = path.resolve(__dirname, '../dist');
const PUBLIC_DIR = path.resolve(__dirname, '../public');

const app = express();

// ─── Layer 1: Security headers (always first) ───────────────────────────────
app.use(helmet({
    contentSecurityPolicy: {
        directives: {
            defaultSrc: ["'self'"],
            scriptSrc: ["'self'"],
            styleSrc: ["'self'"],
        }
    }
}));
app.use((req, res, next) => {
    res.setHeader('X-Content-Type-Options', 'nosniff');
    next();
});

// ─── Layer 2: Compression (only for non-API routes) ────────────────────────
app.use((req, res, next) => {
    if (req.path.startsWith('/api/')) return next();  // Skip API routes
    compression({ level: 4, threshold: 1024 })(req, res, next);
});

// ─── Layer 3: Pre-compressed static assets ─────────────────────────────────
// Middleware to serve .br and .gz variants of static files
const precompressedMiddleware = (req, res, next) => {
    if (req.method !== 'GET' && req.method !== 'HEAD') return next();

    const filePath = path.join(DIST_DIR, req.path);
    const acceptEncoding = req.headers['accept-encoding'] || '';

    const candidates = [];
    if (acceptEncoding.includes('br') && fileExists(filePath + '.br')) {
        candidates.push({ path: filePath + '.br', encoding: 'br' });
    }
    if (acceptEncoding.includes('gzip') && fileExists(filePath + '.gz')) {
        candidates.push({ path: filePath + '.gz', encoding: 'gzip' });
    }

    if (candidates.length === 0) return next();

    const { path: compPath, encoding } = candidates[0];
    res.setHeader('Content-Encoding', encoding);
    res.setHeader('Vary', 'Accept-Encoding');
    res.setHeader('Content-Type', mime.lookup(req.path) || 'application/octet-stream');
    res.sendFile(compPath);
};

// ─── Layer 4: Static files with appropriate cache headers ───────────────────
// Hashed assets (/assets/**) — immutable, cache 1 year
app.use('/assets', precompressedMiddleware);
app.use('/assets', express.static(path.join(DIST_DIR, 'assets'), {
    maxAge: '1y',
    immutable: true,
    dotfiles: 'deny',
    index: false,
    etag: true,
    setHeaders: (res) => {
        res.setHeader('Cache-Control', 'public, max-age=31536000, immutable');
    }
}));

// Other static public files (favicon, robots.txt, manifest.json) — shorter cache
app.use(express.static(PUBLIC_DIR, {
    maxAge: '7d',
    dotfiles: 'deny',
    index: false,
    setHeaders: (res, filePath) => {
        if (filePath.endsWith('/service-worker.js')) {
            // Service workers must not be cached > 24 hours
            res.setHeader('Cache-Control', 'max-age=0, no-cache');
        }
    }
}));

// ─── Layer 5: API routes (no compression, no static caching) ────────────────
app.use('/api', apiRouter);

// ─── Layer 6: SPA fallback (send index.html for all unmatched routes) ───────
app.get('*', (req, res) => {
    res.setHeader('Cache-Control', 'no-cache');  // Always revalidate HTML
    res.setHeader('X-Frame-Options', 'DENY');
    res.sendFile(path.join(DIST_DIR, 'index.html'));
});

// ─── Start ──────────────────────────────────────────────────────────────────
app.listen(3000);
```

## Quick Reference Table

| Header | Purpose | Example |
|---|---|---|
| `Cache-Control: max-age=31536000, immutable` | Cache 1 year, skip revalidation | Content-hashed JS/CSS/fonts |
| `Cache-Control: no-cache` | Always revalidate (use ETag) | HTML entry points |
| `Cache-Control: no-store` | Never cache (sensitive data) | Authenticated API responses |
| `ETag: "abc123"` | Content fingerprint for revalidation | All cacheable static files |
| `Content-Encoding: br` | Response is Brotli-compressed | Any compressed response |
| `Vary: Accept-Encoding` | CDN must store per-encoding | ANY compressed response |
| `Accept-Ranges: bytes` | Server supports range requests | All static files |
| `Content-Range: bytes 0-999/5000` | Range request response | Video, download resume |
| `X-Content-Type-Options: nosniff` | Prevent MIME sniffing | All responses |
| `Content-Disposition: attachment` | Force download dialog | File downloads |

| Technique | When to use |
|---|---|
| Content-hash filenames | All JS/CSS/image assets (enables 1-year cache) |
| `Cache-Control: no-cache` on HTML | Ensures users always get latest bundle references |
| Pre-compression (build-time) | Production static assets (brotli Q11, gzip Q9) |
| `compression` middleware | Development, dynamic JSON responses |
| `Vary: Accept-Encoding` | Mandatory with any Content-Encoding |
| nginx `gzip_static on` | Pre-compressed files in nginx (zero CPU per request) |
| Range requests | Video, large file downloads |
| CDN in front | Production (serves >95% of static requests from edge) |

**Tip for interviews:** Five things separate strong candidates on static files and compression: (1) explaining why **`Cache-Control: no-cache` on HTML + `max-age=31536000, immutable` on content-hashed assets** is the correct pattern (Q4, Q6) — not "set everything to 1 year" or "set everything to no-cache" but understanding that HTML must be fresh to pick up new asset filenames while assets themselves can be cached forever because the URL changes with content; (2) knowing that **`Vary: Accept-Encoding` is mandatory** with any compressed response (Q10) — forgetting it causes CDNs to serve gzip responses to non-gzip clients or vice versa, a subtle but impactful bug; (3) being able to articulate **why Node.js shouldn't serve static files in production** and the correct nginx + CDN architecture (Q12) — this shows systems thinking beyond "does it work" to "does it scale"; (4) knowing the difference between **on-the-fly compression and pre-compression** (Q11) — pre-compressing at build time with brotli Q11 provides better compression with zero per-request CPU cost, and knowing how to configure nginx's `gzip_static` to serve `.gz` files automatically; and (5) knowing that **high compression levels block Node.js's event loop** (Q19) — this is a real production performance footgun that many engineers discover the hard way, and being able to explain why (CPU-bound work on the single thread) and the fix (lower level, Worker Threads, pre-compression, streaming) demonstrates Node.js runtime understanding.
