# Express Error Handling Middleware: 4-Argument Signature — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the 4-argument error handling middleware signature and why does Express require exactly four arguments?**

A: Express differentiates between regular middleware (3 arguments) and error handling middleware (4 arguments) purely by the function's `.length` property — the number of formal parameters declared in the function signature. If Express sees a middleware with exactly four parameters, it treats it as an error handler. Three parameters means regular middleware. This is a hard rule with no configuration:

```javascript
// Regular middleware — 3 arguments:
app.use((req, res, next) => {
    // req: IncomingMessage (request)
    // res: ServerResponse (response)
    // next: function to pass control to the next middleware
    next();
});

// Error handling middleware — exactly 4 arguments:
app.use((err, req, res, next) => {
    // err: the error object (first argument — that's the key difference)
    // req: IncomingMessage
    // res: ServerResponse
    // next: function to pass to the next error handler
    res.status(500).json({ error: err.message });
});

// WHY exactly 4? Express inspects the function's .length property:
const regularFn = (req, res, next) => {};
const errorFn   = (err, req, res, next) => {};

console.log(regularFn.length); // 3
console.log(errorFn.length);   // 4

// Express router internals check this at registration and at dispatch time:
// if (fn.length === 4) → treat as error handler → only called when next(err) was invoked
// if (fn.length !== 4) → treat as regular middleware → called for every matching request
```

The consequence of getting the argument count wrong:

```javascript
// BROKEN: missing the 'err' parameter — Express sees length=3 → regular middleware
// This handler will be called on EVERY request, not just errors
app.use((req, res, next) => {
    // 'err' is silently missing — you've lost the error reference entirely
    res.status(500).json({ error: 'Something went wrong' }); // Called on every request!
});

// BROKEN: using default parameter — .length still counts as 3 (default params excluded)
app.use((err = new Error(), req, res, next) => {
    // Function.length does not count parameters with default values
    // This function's .length is 3 — Express won't treat it as an error handler
});

// BROKEN: using rest parameter — .length counts only params before the rest
app.use((err, req, res, ...args) => {
    // .length is 3 (err + req + res, rest not counted)
    // Express treats this as regular middleware
});

// SAFE: always declare all four parameters explicitly, even if next is unused
app.use((err, req, res, next) => { // eslint-disable-line @typescript-eslint/no-unused-vars
    res.status(500).json({ error: err.message });
    // next is declared but not called — Express still routes errors here correctly
});
```

TypeScript makes the contract explicit:

```typescript
import { Request, Response, NextFunction, ErrorRequestHandler } from 'express';

// The ErrorRequestHandler type enforces 4 parameters:
const errorHandler: ErrorRequestHandler = (err, req, res, next) => {
    res.status(500).json({ error: err.message });
};

// TypeScript will error if you try to assign a 3-arg function to ErrorRequestHandler:
const broken: ErrorRequestHandler = (req, res, next) => {}; // Type error
// Argument of type '(req, res, next) => void' is not assignable to type 'ErrorRequestHandler'
```

**Q2. How does Express route errors to error handling middleware — what triggers it and what path does execution take?**

A: Express maintains two separate middleware stacks within each router: one for regular middleware/routes and one for error handlers. Error routing is triggered by calling `next(err)` with a non-falsy argument, or by a synchronous throw inside a route handler (Express 5 only — not Express 4):

```javascript
// Three ways to trigger error routing in Express 4:

// 1. next(err) — explicit error forwarding:
app.get('/users/:id', async (req, res, next) => {
    try {
        const user = await db.findUser(req.params.id);
        if (!user) {
            return next(new NotFoundError(`User ${req.params.id} not found`));
            // next() receives a non-falsy value → Express skips all regular middleware
            // and routes directly to the first error handler
        }
        res.json(user);
    } catch (err) {
        next(err); // Uncaught error → forward to error handling middleware
    }
});

// 2. next('route') — special string that skips remaining handlers in current route:
app.get('/data', (req, res, next) => {
    if (!req.user) return next('route'); // Skip to next route matching /data
    // NOT an error — skips to next route, not error handler
});

// 3. Synchronous throw inside a SYNCHRONOUS route handler — Express 4 catches this:
app.get('/sync', (req, res) => {
    throw new Error('Synchronous error'); // Caught by Express 4's sync wrapper
    // Express wraps synchronous route handlers in try/catch automatically
});

// DANGER in Express 4: async throws are NOT caught automatically:
app.get('/async', async (req, res) => {
    throw new Error('Async error'); // NOT caught by Express 4!
    // → UnhandledPromiseRejection → process may crash
    // You MUST use try/catch + next(err) in Express 4 async handlers
});
```

The execution path when `next(err)` is called:

```
Request arrives
     │
     ▼
Regular middleware 1 (req, res, next)   ← executes
     │
     ▼
Regular middleware 2 (req, res, next)   ← executes
     │
     │ next(new Error('something failed'))
     │
     ▼
Regular middleware 3 (req, res, next)   ← SKIPPED
Regular middleware 4 (req, res, next)   ← SKIPPED
Route handler        (req, res, next)   ← SKIPPED
     │
     ▼
Error handler 1 (err, req, res, next)  ← executes first matching error handler
     │
     │ next(err) or next(newErr) — pass to next error handler
     ▼
Error handler 2 (err, req, res, next)  ← executes if error handler 1 called next(err)
     │
     ▼
Express default error handler          ← if no error handler sent a response
     (sends 500 with err.stack in dev, "Internal Server Error" in prod)
```

## Section 2: Registering and Ordering Error Handlers

**Q3. Where must error handling middleware be registered — why does order matter?**

A: Error handling middleware must be registered **after** all routes and regular middleware it is meant to catch errors from. Express processes middleware in the order they are registered using `app.use()` or `router.use()`. An error handler registered before a route cannot catch errors from that route:

```javascript
import express from 'express';
const app = express();

// WRONG: error handler registered before routes — catches nothing
app.use((err, req, res, next) => {
    res.status(500).json({ error: err.message }); // Never reached from routes below
});

app.get('/users', async (req, res, next) => {
    next(new Error('DB failure')); // Error is NOT caught by the handler above
});
// Result: Express uses the default error handler — sends 500 with stack trace in dev

// CORRECT: error handler registered after routes:
app.use(express.json());
app.use(cors());

app.get('/users', userRouter);
app.get('/orders', orderRouter);
app.post('/auth/login', loginHandler);

// 404 handler — registered after routes, before error handler:
app.use((req, res, next) => {
    next(new NotFoundError(`Route ${req.method} ${req.path} not found`));
});

// Error handler — LAST in the chain:
app.use((err, req, res, next) => {
    const status = err.status ?? err.statusCode ?? 500;
    res.status(status).json({
        error: err.message,
        ...(process.env.NODE_ENV === 'development' && { stack: err.stack }),
    });
});

app.listen(3000);
```

Multiple error handlers for separation of concerns:

```javascript
// You can have multiple error handlers — they execute in order, just like regular middleware
// Each can decide to handle the error, transform it, or pass it to the next handler

// Handler 1: Log all errors
app.use((err, req, res, next) => {
    logger.error({
        err,
        method: req.method,
        path: req.path,
        requestId: req.id,
    });
    next(err); // MUST call next(err) to pass to the next error handler
               // Calling next() without args would return to regular middleware (wrong)
               // Sending a response here would prevent handler 2 from running
});

// Handler 2: Handle operational errors (known, expected errors)
app.use((err, req, res, next) => {
    if (err instanceof AppError) {
        return res.status(err.statusCode).json({
            error: err.message,
            code: err.code,
        });
    }
    next(err); // Unknown error — pass to the final catch-all
});

// Handler 3: Catch-all for unexpected errors (last resort)
app.use((err, req, res, next) => {
    // Don't expose internal error details in production
    res.status(500).json({
        error: process.env.NODE_ENV === 'production'
            ? 'Internal server error'
            : err.message,
    });
});
```

**Q4. How do Express Router instances interact with error handling middleware — do errors propagate between routers?**

A: Errors propagate up through the router hierarchy. When a `Router` calls `next(err)`, the error bubbles up to the parent router or application, where it is caught by the first error handler found:

```javascript
import { Router } from 'express';

// Child router — no error handler:
const userRouter = Router();
userRouter.get('/:id', async (req, res, next) => {
    try {
        const user = await db.findUser(req.params.id);
        res.json(user);
    } catch (err) {
        next(err); // Propagates up to app-level error handler
    }
});

// Child router with its OWN error handler:
const orderRouter = Router();
orderRouter.get('/:id', async (req, res, next) => {
    const order = await db.findOrder(req.params.id);
    res.json(order);
});

// This error handler only catches errors from routes in orderRouter:
orderRouter.use((err, req, res, next) => {
    if (err.code === 'ORDER_NOT_FOUND') {
        return res.status(404).json({ error: 'Order not found' });
    }
    next(err); // Pass non-order errors up to app-level handler
});

// App-level:
app.use('/users', userRouter);
app.use('/orders', orderRouter);

// App-level error handler catches:
// - All errors from userRouter (no router-level handler)
// - Errors from orderRouter that were passed up via next(err)
app.use((err, req, res, next) => {
    res.status(500).json({ error: err.message });
});
```

Router-level error handling is useful for domain-specific error translation:

```typescript
// Each domain router translates its own errors before the app sees them:
const paymentRouter = Router();

paymentRouter.post('/charge', async (req, res, next) => {
    const result = await stripeClient.charge(req.body);
    res.json(result);
});

// Payment-specific error translation:
paymentRouter.use((err: Error, req: Request, res: Response, next: NextFunction) => {
    // Translate Stripe-specific errors to app errors:
    if (err.name === 'StripeCardError') {
        return res.status(402).json({
            error: 'Payment failed',
            code: 'PAYMENT_DECLINED',
            declineCode: (err as any).decline_code,
        });
    }
    if (err.name === 'StripeRateLimitError') {
        return res.status(429).json({
            error: 'Too many payment requests',
            retryAfter: 60,
        });
    }
    // All other errors: pass to app-level handler
    next(err);
});

app.use('/payments', paymentRouter);
```

## Section 3: Async Error Handling

**Q5. Why is async error handling different in Express 4 vs Express 5 — and how do you handle it in Express 4?**

A: Express 4 was written before async/await existed. Its route dispatch loop is synchronous — it calls each middleware function and catches synchronous throws, but it does not await the return value. A rejected Promise from an async handler is invisible to Express 4 and becomes an unhandled rejection:

```javascript
// Express 4 route dispatch (simplified concept):
function dispatch(req, res, next) {
    try {
        layer.handle(req, res, next); // Calls your middleware function
        // If handle() returns a Promise, Express 4 ignores it
        // A rejected Promise → UnhandledPromiseRejection
    } catch (err) {
        next(err); // Only catches synchronous throws
    }
}

// The consequence:
app.get('/data', async (req, res) => {
    const data = await db.query(); // If this rejects:
    // → Unhandled Promise rejection
    // → Express error handlers are NOT called
    // → Node.js emits 'unhandledRejection' event
    // → In Node.js 15+: process crashes
    res.json(data);
});

// Express 5 fixes this: it awaits route handlers and catches rejected Promises
// But Express 5 is still not widely used — know Express 4 patterns
```

Three patterns for Express 4 async error handling:

```typescript
import { Request, Response, NextFunction, RequestHandler } from 'express';

// Pattern 1: try/catch in every handler (verbose but explicit)
app.get('/users/:id', async (req: Request, res: Response, next: NextFunction) => {
    try {
        const user = await userService.findById(req.params.id);
        res.json(user);
    } catch (err) {
        next(err); // Manually forward to error handler
    }
});

// Pattern 2: asyncHandler wrapper (most common pattern in Express 4 codebases)
// Wraps an async function, attaches a .catch(next) to the returned promise:
function asyncHandler(fn: RequestHandler): RequestHandler {
    return (req, res, next) => {
        Promise.resolve(fn(req, res, next)).catch(next);
        // Promise.resolve() handles both sync (fn returns non-promise) and async cases
        // .catch(next) → on rejection, calls next(err) → routes to error handler
    };
}

// Usage — no try/catch needed in the handler itself:
app.get('/users/:id', asyncHandler(async (req, res) => {
    const user = await userService.findById(req.params.id);
    res.json(user);
}));

app.post('/orders', asyncHandler(async (req, res) => {
    const order = await orderService.create(req.body);
    res.status(201).json(order);
}));

// Pattern 3: express-async-errors (monkey-patch approach)
// Patches Express internals to handle async automatically — no wrapper needed
// npm install express-async-errors
import 'express-async-errors'; // Must be imported before express and routes

// After importing, async errors are forwarded automatically:
app.get('/users/:id', async (req, res) => {
    const user = await userService.findById(req.params.id); // Rejection auto-forwarded
    res.json(user);
});

// Pattern 4: Router-level async middleware wrapper
// For teams that don't want to change handler signatures, wrap at use/get/post level:
function wrapAsync(router: Router) {
    ['get', 'post', 'put', 'patch', 'delete', 'use'].forEach(method => {
        const original = (router as any)[method].bind(router);
        (router as any)[method] = (...args: any[]) => {
            const handlers = args.map(arg =>
                typeof arg === 'function' && arg.constructor.name === 'AsyncFunction'
                    ? asyncHandler(arg)
                    : arg
            );
            return original(...handlers);
        };
    });
    return router;
}
```

**Q6. How do you handle errors in Express middleware that uses callbacks rather than async/await?**

A: Callback-based code needs special care — errors thrown inside a callback are not caught by either Express's synchronous wrapper or by `.catch(next)` patterns, because the callback executes in a different call stack:

```javascript
// BROKEN: error thrown inside callback is uncaught:
app.get('/file', (req, res, next) => {
    fs.readFile('/data/config.json', (err, data) => {
        if (err) {
            throw err; // WRONG: thrown in callback stack — not caught by Express
                       // → uncaught exception → process may crash
        }
        res.json(JSON.parse(data));
    });
});

// CORRECT: use next(err) inside the callback:
app.get('/file', (req, res, next) => {
    fs.readFile('/data/config.json', (err, data) => {
        if (err) {
            return next(err); // Correctly routes to error handler
        }
        try {
            res.json(JSON.parse(data)); // JSON.parse can throw — wrap in try/catch
        } catch (parseErr) {
            next(parseErr);
        }
    });
});

// BETTER: promisify callback-based APIs, use async/await + asyncHandler:
import { promisify } from 'util';
const readFile = promisify(fs.readFile);

app.get('/file', asyncHandler(async (req, res) => {
    const data = await readFile('/data/config.json', 'utf8');
    res.json(JSON.parse(data));
}));

// EventEmitter errors inside a route — common with streams:
app.get('/stream', (req, res, next) => {
    const readStream = fs.createReadStream('/large-file.bin');

    readStream.on('error', (err) => {
        next(err); // Stream errors must be caught with 'error' event + next(err)
    });

    readStream.pipe(res);
    req.on('close', () => readStream.destroy()); // Clean up if client disconnects
});

// Third-party library with callback — db driver example:
app.get('/users', (req, res, next) => {
    db.query('SELECT * FROM users', (err, rows) => {
        if (err) return next(err);
        res.json(rows);
    });
});
```

## Section 4: Error Classification and Custom Error Classes

**Q7. How do you design a custom error hierarchy for use with Express error handling middleware?**

A: A well-designed error hierarchy separates operational errors (expected, recoverable, safe to expose) from programmer errors (bugs, unexpected, hide from clients). Express error handlers use the error type and properties to decide HTTP status, response body, and logging behavior:

```typescript
// Base application error — all intentional errors extend this
export class AppError extends Error {
    public readonly statusCode: number;
    public readonly code: string;
    public readonly isOperational: boolean; // true = safe to show to client

    constructor(
        message: string,
        statusCode = 500,
        code = 'INTERNAL_ERROR',
        isOperational = true
    ) {
        super(message);
        this.name = this.constructor.name;
        this.statusCode = statusCode;
        this.code = code;
        this.isOperational = isOperational;
        Error.captureStackTrace(this, this.constructor); // Cleaner stack trace
    }
}

// HTTP-specific error classes:
export class NotFoundError extends AppError {
    constructor(message = 'Resource not found') {
        super(message, 404, 'NOT_FOUND');
    }
}

export class ValidationError extends AppError {
    public readonly fields: Record<string, string>;

    constructor(message: string, fields: Record<string, string> = {}) {
        super(message, 400, 'VALIDATION_ERROR');
        this.fields = fields;
    }
}

export class AuthenticationError extends AppError {
    constructor(message = 'Authentication required') {
        super(message, 401, 'UNAUTHENTICATED');
    }
}

export class AuthorizationError extends AppError {
    constructor(message = 'Insufficient permissions') {
        super(message, 403, 'FORBIDDEN');
    }
}

export class ConflictError extends AppError {
    constructor(message: string) {
        super(message, 409, 'CONFLICT');
    }
}

export class RateLimitError extends AppError {
    public readonly retryAfter: number;

    constructor(retryAfterSeconds = 60) {
        super('Too many requests', 429, 'RATE_LIMITED');
        this.retryAfter = retryAfterSeconds;
    }
}

export class ExternalServiceError extends AppError {
    public readonly service: string;

    constructor(service: string, message: string) {
        super(message, 502, 'EXTERNAL_SERVICE_ERROR', false); // isOperational=false
        this.service = service;
    }
}

// Type guard — safely check if any error is an operational AppError:
export function isAppError(err: unknown): err is AppError {
    return err instanceof AppError;
}

// Check if an error should be logged as a critical alert:
export function isCriticalError(err: unknown): boolean {
    if (isAppError(err)) return !err.isOperational; // Programmer errors are critical
    return true; // Unknown errors are always critical
}
```

Using the hierarchy in error handling middleware:

```typescript
import { Request, Response, NextFunction } from 'express';
import { AppError, isAppError, isCriticalError, RateLimitError, ValidationError } from './errors';

export function errorHandler(
    err: unknown,
    req: Request,
    res: Response,
    next: NextFunction // Must be declared even if unused — Express checks .length
): void {
    // Normalize: ensure we always have an Error instance
    const error = err instanceof Error ? err : new Error(String(err));

    // Log based on severity:
    if (isCriticalError(error)) {
        logger.error({ err: error, req: { method: req.method, path: req.path, id: req.id } });
    } else {
        logger.warn({ err: error, path: req.path });
    }

    // Response already started — can't change status, just close connection:
    if (res.headersSent) {
        return next(error); // Let Express close the connection
    }

    // Operational AppError — safe to send details to client:
    if (isAppError(error)) {
        const body: Record<string, unknown> = {
            error: error.message,
            code: error.code,
        };

        // Add error-specific fields:
        if (error instanceof ValidationError) {
            body.fields = error.fields;
        }
        if (error instanceof RateLimitError) {
            res.setHeader('Retry-After', error.retryAfter);
            body.retryAfter = error.retryAfter;
        }

        return void res.status(error.statusCode).json(body);
    }

    // Unknown/programmer error — hide details in production:
    res.status(500).json({
        error: process.env.NODE_ENV === 'production'
            ? 'Internal server error'
            : error.message,
        ...(process.env.NODE_ENV === 'development' && { stack: error.stack }),
    });
}
```

**Q8. How do you translate third-party library errors into your own error hierarchy inside Express middleware?**

A: Third-party libraries throw their own error types (Prisma, Mongoose, Joi, pg, etc.). Translating them in the error handling middleware keeps your HTTP layer clean and your error semantics consistent:

```typescript
import { Prisma } from '@prisma/client';
import { ValidationError as JoiValidationError } from 'joi';
import { JsonWebTokenError, TokenExpiredError } from 'jsonwebtoken';
import { AppError, NotFoundError, ValidationError, ConflictError, AuthenticationError } from './errors';

// Translation middleware — runs before the final error handler:
export function translateErrors(
    err: unknown,
    req: Request,
    res: Response,
    next: NextFunction
): void {
    // Already one of ours — pass through unchanged:
    if (err instanceof AppError) {
        return next(err);
    }

    // Prisma errors:
    if (err instanceof Prisma.PrismaClientKnownRequestError) {
        switch (err.code) {
            case 'P2002': // Unique constraint violation
                return next(new ConflictError(
                    `${(err.meta?.target as string[])?.join(', ')} already exists`
                ));
            case 'P2025': // Record not found
                return next(new NotFoundError('Record not found'));
            case 'P2003': // Foreign key constraint
                return next(new ValidationError('Referenced record does not exist', {}));
            default:
                return next(new AppError(`Database error: ${err.code}`, 500, 'DB_ERROR', false));
        }
    }

    if (err instanceof Prisma.PrismaClientValidationError) {
        return next(new ValidationError('Invalid data provided', {}));
    }

    // Mongoose errors:
    if ((err as any).name === 'ValidationError' && (err as any).errors) {
        const mongooseErr = err as any;
        const fields: Record<string, string> = {};
        for (const [field, error] of Object.entries(mongooseErr.errors)) {
            fields[field] = (error as any).message;
        }
        return next(new ValidationError('Validation failed', fields));
    }

    if ((err as any).code === 11000) {
        // Mongoose duplicate key error
        const field = Object.keys((err as any).keyPattern ?? {})[0] ?? 'field';
        return next(new ConflictError(`${field} already exists`));
    }

    // Joi validation error:
    if (err instanceof JoiValidationError) {
        const fields: Record<string, string> = {};
        err.details.forEach(detail => {
            const key = detail.path.join('.');
            fields[key] = detail.message.replace(/"/g, '');
        });
        return next(new ValidationError('Validation failed', fields));
    }

    // JWT errors:
    if (err instanceof TokenExpiredError) {
        return next(new AuthenticationError('Token has expired'));
    }
    if (err instanceof JsonWebTokenError) {
        return next(new AuthenticationError('Invalid token'));
    }

    // SyntaxError from JSON body parsing (express.json() throws this):
    if (err instanceof SyntaxError && (err as any).status === 400 && 'body' in err) {
        return next(new ValidationError('Invalid JSON in request body', {}));
    }

    // Unknown error — pass through to final handler:
    next(err);
}

// Registration order matters — translateErrors before errorHandler:
app.use(translateErrors);
app.use(errorHandler);
```

## Section 5: Production Patterns

**Q9. How do you handle `res.headersSent` — what happens when an error occurs after the response has started streaming?**

A: Once Express (or your code) has called `res.write()` or begun streaming, the HTTP status code and headers have been sent to the client. At that point you cannot change the status code or send a JSON error body — the client has already received a 200 OK. The only correct action is to close the connection:

```javascript
app.use((err, req, res, next) => {
    // Check FIRST — before any attempt to write a response:
    if (res.headersSent) {
        // Headers already sent — cannot change status or send JSON error
        // Delegate to Express's default handler which will close the connection:
        return next(err);
        // Express's default handler, when called with an error after headers are sent,
        // calls res.end() or destroys the socket — terminates the connection cleanly
    }

    // Safe to send error response:
    res.status(500).json({ error: err.message });
});

// Real-world scenario — streaming a large file:
app.get('/download', (req, res, next) => {
    const stream = fs.createReadStream('/large-file.bin');

    // Headers sent as soon as pipe starts:
    res.setHeader('Content-Type', 'application/octet-stream');
    stream.pipe(res); // res.headersSent becomes true after first chunk

    // If stream errors mid-transfer:
    stream.on('error', (err) => {
        // res.headersSent is now true — client already received HTTP 200
        // Cannot send a 500 response — just destroy the connection
        if (!res.headersSent) {
            res.status(500).json({ error: 'Download failed' });
        } else {
            res.destroy(err); // Abruptly close — client will see a broken stream
        }
    });
});

// With pipeline — cleaner handling:
app.get('/download', asyncHandler(async (req, res) => {
    const stream = fs.createReadStream('/large-file.bin');
    res.setHeader('Content-Type', 'application/octet-stream');

    try {
        await pipeline(stream, res);
    } catch (err) {
        // pipeline error after headers sent — nothing we can do about the HTTP status
        // Log it (client knows something went wrong from the broken stream)
        logger.error({ err, path: req.path }, 'Stream failed mid-transfer');
        // Don't call next(err) here — pipeline already destroyed the streams
    }
}));

// Preventing the scenario: use asyncHandler + pipeline for all streaming responses
```

**Q10. How do you attach request context (request ID, user ID, trace ID) to error logs inside error handling middleware?**

A: Error logs without context are nearly useless in production — you can't correlate a logged error to a specific user or request. The pattern is to attach context to `req` in early middleware so it's available in the error handler:

```typescript
import { v4 as uuidv4 } from 'uuid';
import { Request, Response, NextFunction } from 'express';

// Extend Express Request type to include custom properties:
declare global {
    namespace Express {
        interface Request {
            id: string;
            startTime: number;
            user?: { id: string; role: string };
            traceId?: string; // From upstream service (X-Trace-Id header)
        }
    }
}

// Request ID middleware — register FIRST, before all other middleware:
app.use((req, res, next) => {
    req.id = req.headers['x-request-id'] as string ?? uuidv4();
    req.startTime = Date.now();
    req.traceId = req.headers['x-trace-id'] as string | undefined;

    // Echo back the request ID in every response:
    res.setHeader('X-Request-Id', req.id);

    next();
});

// Auth middleware — attaches user context:
app.use(async (req, res, next) => {
    try {
        const token = req.headers.authorization?.replace('Bearer ', '');
        if (token) {
            req.user = await verifyToken(token);
        }
        next();
    } catch (err) {
        next(err);
    }
});

// Error handler — context is available on req:
app.use((err: unknown, req: Request, res: Response, next: NextFunction) => {
    const error = err instanceof Error ? err : new Error(String(err));
    const durationMs = Date.now() - req.startTime;

    // Structured log with full context:
    logger.error({
        // Error details:
        err: {
            name: error.name,
            message: error.message,
            stack: error.stack,
            ...(isAppError(error) && {
                code: error.code,
                statusCode: error.statusCode,
                isOperational: error.isOperational,
            }),
        },
        // Request context:
        request: {
            id: req.id,
            traceId: req.traceId,
            method: req.method,
            path: req.path,
            query: req.query,
            durationMs,
        },
        // User context (if authenticated):
        user: req.user ? { id: req.user.id, role: req.user.role } : undefined,
    });

    if (res.headersSent) return next(error);

    const statusCode = isAppError(error) ? error.statusCode : 500;
    res.status(statusCode).json({
        error: isAppError(error) && error.isOperational
            ? error.message
            : 'Internal server error',
        requestId: req.id, // Include in response — client can use for support tickets
    });
});

// Using AsyncLocalStorage for context that flows through async operations:
import { AsyncLocalStorage } from 'async_hooks';

interface RequestContext {
    requestId: string;
    userId?: string;
}

const requestContext = new AsyncLocalStorage<RequestContext>();

app.use((req, res, next) => {
    requestContext.run({ requestId: req.id, userId: req.user?.id }, next);
});

// Now any code in the request lifecycle can access the context:
function logWithContext(message: string, data?: object): void {
    const context = requestContext.getStore();
    logger.info({ ...context, ...data, message });
}
// Useful in service/repository layers where req is not available
```

**Q11. How do you prevent error handling middleware from leaking sensitive information in production?**

A: Error handlers are a common source of information leakage — stack traces, database query strings, and internal service names can all appear in error responses if you're not careful:

```typescript
// Information that must NEVER reach the client in production:
// - Stack traces (reveal file structure, module versions, line numbers)
// - Database error messages (reveal schema names, query structure)
// - Internal service URLs or connection strings
// - Third-party API keys or tokens that appear in error messages
// - System paths (/var/app/node_modules/...)

// Safe error response builder:
function buildErrorResponse(
    err: unknown,
    isDevelopment: boolean
): { status: number; body: Record<string, unknown> } {
    if (isAppError(err) && err.isOperational) {
        // Operational errors: safe to show message and code
        const body: Record<string, unknown> = {
            error: err.message,
            code: err.code,
        };
        if (err instanceof ValidationError) body.fields = err.fields;
        if (err instanceof RateLimitError) body.retryAfter = err.retryAfter;

        return { status: err.statusCode, body };
    }

    // Non-operational / unknown errors:
    return {
        status: 500,
        body: {
            error: 'Internal server error',
            // Only include debug info in development:
            ...(isDevelopment && err instanceof Error && {
                message: err.message,
                stack: err.stack,
                name: err.name,
            }),
        },
    };
}

const isDev = process.env.NODE_ENV === 'development';

app.use((err: unknown, req: Request, res: Response, next: NextFunction) => {
    if (res.headersSent) return next(err);

    // Sanitize error message before logging — some errors embed secrets:
    const sanitizedMessage = err instanceof Error
        ? err.message
              .replace(/password=\S+/gi, 'password=[REDACTED]')
              .replace(/key=\S+/gi, 'key=[REDACTED]')
              .replace(/token=\S+/gi, 'token=[REDACTED]')
        : String(err);

    logger.error({
        err: { ...err, message: sanitizedMessage },
        requestId: req.id,
    });

    const { status, body } = buildErrorResponse(err, isDev);
    res.status(status).json(body);
});

// Preventing Prisma/Sequelize query strings from leaking:
// These ORMs sometimes include the full SQL query in error messages:
// "Error executing query: SELECT * FROM users WHERE token='abc123secret'"

app.use((err: unknown, req: Request, res: Response, next: NextFunction) => {
    if (err instanceof Prisma.PrismaClientKnownRequestError) {
        // Log the full error internally:
        logger.error({ err, requestId: req.id });
        // But send only a sanitized message to the client:
        return next(new AppError('A database error occurred', 500, 'DB_ERROR', false));
    }
    next(err);
});
```

## Section 7: Scenario-Based Questions

**Q13. "What's wrong with this error handling setup? Errors from the `/api` routes are not being caught."**

```javascript
const app = express();
const apiRouter = express.Router();

app.use((err, req, res, next) => {
    res.status(500).json({ error: err.message });
});

apiRouter.get('/users', async (req, res) => {
    const users = await db.getUsers();
    res.json(users);
});

app.use('/api', apiRouter);
```

A: Three bugs — ordering, async handling, and the async handler missing `next`:

```javascript
// Bug 1: Error handler registered BEFORE the routes — catches nothing from /api
// Express processes middleware top-to-bottom at registration time
// The error handler was registered before app.use('/api', apiRouter)
// So errors from apiRouter bubble up past the error handler

// Bug 2: Async handler in Express 4 with no try/catch and no asyncHandler wrapper
// If db.getUsers() rejects, Express 4 does NOT catch it
// → UnhandledPromiseRejection → crash in Node.js 15+

// Bug 3: Async route handler signature is (req, res) — missing next
// Even if we add try/catch, we can't call next(err) without next in scope

// Fixed version:
const app = express();
const apiRouter = express.Router();

// asyncHandler wrapper:
const asyncHandler = (fn) => (req, res, next) =>
    Promise.resolve(fn(req, res, next)).catch(next);

// Routes registered FIRST:
apiRouter.get('/users', asyncHandler(async (req, res) => {
    const users = await db.getUsers(); // Rejection caught by asyncHandler → next(err)
    res.json(users);
}));

app.use('/api', apiRouter);

// 404 handler — after routes, before error handler:
app.use((req, res, next) => {
    next(Object.assign(new Error(`${req.method} ${req.path} not found`), { status: 404 }));
});

// Error handler LAST:
app.use((err, req, res, next) => {
    const status = err.status ?? err.statusCode ?? 500;
    res.status(status).json({ error: err.message });
});
```

**Q14. "Design a complete error handling system for a production Express API with multiple domains (auth, orders, payments), structured logging, and different error types."**

A: The complete production-grade setup combining all the patterns from this guide:

```typescript
// errors.ts — error hierarchy (see Q7 for full implementation)
export { AppError, NotFoundError, ValidationError, AuthenticationError,
         AuthorizationError, ConflictError, RateLimitError, isAppError };

// middleware/request-id.ts
export const requestId = (req: Request, res: Response, next: NextFunction) => {
    req.id = (req.headers['x-request-id'] as string) ?? uuidv4();
    req.startTime = Date.now();
    res.setHeader('X-Request-Id', req.id);
    next();
};

// middleware/async-handler.ts
export const asyncHandler =
    (fn: RequestHandler): RequestHandler =>
    (req, res, next) =>
        Promise.resolve(fn(req, res, next)).catch(next);

// middleware/not-found.ts
export const notFound = (req: Request, res: Response, next: NextFunction) => {
    next(new NotFoundError(`${req.method} ${req.path} not found`));
};

// middleware/translate-errors.ts — see Q8 for full implementation
export { translateErrors };

// middleware/error-handler.ts — final catch-all
export const errorHandler = (
    err: unknown,
    req: Request,
    res: Response,
    next: NextFunction
): void => {
    const error = err instanceof Error ? err : new Error(String(err));
    const durationMs = Date.now() - (req.startTime ?? Date.now());

    // Severity-based logging:
    const logFn = isCriticalError(error) ? logger.error : logger.warn;
    logFn.call(logger, {
        err: {
            name: error.name,
            message: error.message,
            stack: process.env.NODE_ENV !== 'production' ? error.stack : undefined,
            ...(isAppError(error) && { code: error.code, statusCode: error.statusCode }),
        },
        requestId: req.id,
        method: req.method,
        path: req.path,
        durationMs,
        userId: req.user?.id,
    });

    if (res.headersSent) return next(error);

    const { status, body } = buildErrorResponse(error, process.env.NODE_ENV === 'development');
    res.status(status).json({ ...body, requestId: req.id });
};

// routers/auth.router.ts
export const authRouter = Router();
authRouter.post('/login', asyncHandler(loginHandler));
authRouter.post('/refresh', asyncHandler(refreshHandler));
// Auth-specific error translation:
authRouter.use((err: unknown, req: Request, res: Response, next: NextFunction) => {
    if (err instanceof JsonWebTokenError) return next(new AuthenticationError());
    if (err instanceof TokenExpiredError) return next(new AuthenticationError('Token expired'));
    next(err);
});

// routers/orders.router.ts
export const ordersRouter = Router();
ordersRouter.use(requireAuth); // Auth middleware for all order routes
ordersRouter.get('/', asyncHandler(listOrdersHandler));
ordersRouter.post('/', asyncHandler(createOrderHandler));
ordersRouter.get('/:id', asyncHandler(getOrderHandler));

// routers/payments.router.ts — see Q4 for payment error translation
export const paymentsRouter = Router();

// app.ts — wire everything together:

// Global middleware (request context first):
```

## Quick Reference Table

| Signature | Type | When called |
|---|---|---|
| `(req, res, next)` | Regular middleware | Every matching request |
| `(err, req, res, next)` | Error handler | Only when `next(err)` called or sync throw |
| `(req, res)` | Route handler (no next) | Every matching request — can't forward errors |

| Method | Behavior |
|---|---|
| `next()` | Pass to next regular middleware or route |
| `next(err)` | Skip all regular middleware, go to next error handler |
| `next('route')` | Skip remaining handlers in current route, try next matching route |
| `next('router')` | Skip remaining middleware in current router, bubble up to parent |

| Anti-pattern | Problem | Fix |
|---|---|---|
| Error handler with 3 args | `fn.length === 3` → treated as regular middleware, called on every request | Always declare all 4 params |
| Default param in error handler | `fn.length` doesn't count default params → treated as regular middleware | No defaults on `err` parameter |
| Error handler before routes | Registered before routes can't catch their errors | Register after all routes |
| `throw` in async handler (Express 4) | Uncaught promise rejection — Express 4 doesn't await handlers | Use `asyncHandler` wrapper or try/catch |
| `throw` inside callback | Thrown in different call stack — Express can't catch | Use `next(err)` inside callbacks |
| Not checking `res.headersSent` | Attempting to send a response after streaming started crashes | Always check `headersSent` first |
| Calling `next()` (no arg) in error handler | Returns to regular middleware stack — skips remaining error handlers | Call `next(err)` to stay in error chain |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) explaining **why exactly four arguments** are required — Express uses `Function.length` to distinguish error handlers from regular middleware, and `Function.length` does not count parameters with default values or rest parameters, so `(err = new Error(), req, res, next)` still has `length: 3` and won't be treated as an error handler; (2) being precise about **async error handling in Express 4** — the framework does not await handler return values, so a rejected Promise in an `async` route handler is an unhandled rejection, not a routed error, and the fix is either `asyncHandler` wrapper, `express-async-errors`, or manual try/catch with `next(err)`; (3) knowing the **`next()` vs `next(err)` distinction** inside an error handler — calling `next()` with no argument exits the error handling chain and returns to regular middleware (almost never what you want), while `next(err)` passes the error to the next error handler; (4) handling **`res.headersSent`** — once streaming has started you cannot change the HTTP status or body, and the only correct response is `next(err)` which lets Express close the connection cleanly; (5) knowing the **registration order rule** — error handlers must be registered after all the routes they are meant to catch, and a common mistake is putting the error handler at the top of the file before routes; and (6) designing a **layered error middleware pipeline** — a logging handler that calls `next(err)`, a translation handler that converts library errors to app errors, and a final catch-all — rather than putting all logic in one monolithic function, which is how production Express apps are actually structured.
