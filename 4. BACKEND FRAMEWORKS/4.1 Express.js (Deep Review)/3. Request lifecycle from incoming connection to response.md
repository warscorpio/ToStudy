# Request Lifecycle — From Incoming Connection to Response (Interview Q&A, 5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Walk me through what happens when a browser makes an HTTP request to your Node.js server — end to end.**
A: At the highest level, eight distinct stages happen in sequence:

```
Client                        OS / Network                   Node.js Process
  │                               │                               │
  │──── TCP SYN ─────────────────►│                               │
  │◄─── TCP SYN-ACK ─────────────│                               │
  │──── TCP ACK ─────────────────►│                               │
  │                               │──── accept() syscall ────────►│ (1) TCP connection
  │──── TLS ClientHello ─────────►│                               │
  │◄─── TLS ServerHello ─────────│                               │
  │──── TLS Finished ────────────►│                               │ (2) TLS handshake
  │──── HTTP request bytes ──────►│──── readable event ──────────►│ (3) HTTP parsing
  │                               │                               │ (4) Router match
  │                               │                               │ (5) Middleware chain
  │                               │                               │ (6) Handler + services
  │                               │                               │ (7) Response serialise
  │◄─── HTTP response bytes ──────│◄─── socket.write() ──────────│ (8) TCP write
```

**Why this matters in interviews:** Strong candidates frame the answer in terms of *where responsibility lives* — OS kernel owns TCP, Node.js's `llhttp` owns HTTP parsing, the framework owns routing and middleware, application code owns business logic. Conflating these layers is the tell that someone only knows Express, not what Express sits on top of.

**Q2. What is the difference between a TCP connection, an HTTP request, and an HTTP session?**
A: Three different lifetimes, frequently confused:

```
TCP connection:
  ├── Established via 3-way handshake (SYN / SYN-ACK / ACK)
  ├── Torn down via 4-way FIN sequence (FIN / ACK / FIN / ACK)
  ├── Exists at Layer 4 (Transport) — just a reliable byte stream
  └── One TCP connection can carry many HTTP requests (Keep-Alive)

HTTP request:
  ├── A single message exchange: one request + one response
  ├── Starts when client sends "GET /path HTTP/1.1\r\n..."
  ├── Ends when the response body is fully transmitted
  └── Stateless — the server has no memory of prior requests on the same connection

HTTP session:
  ├── An application-level concept — NOT a protocol primitive
  ├── Implemented by the application via cookies, JWT, or session IDs
  ├── Can span many TCP connections and many HTTP requests
  └── The server must reconstruct session state from each request's token
```

```
Timeline with Keep-Alive:
  TCP OPEN
    │
    ├── Request 1 (GET /api/user)   → Response 1
    ├── Request 2 (POST /api/order) → Response 2   ← same TCP connection
    ├── Request 3 (GET /api/items)  → Response 3
    │
  TCP CLOSE  (after idle timeout or Connection: close header)
```

HTTP/1.1 defaults to Keep-Alive — multiple requests reuse one TCP connection, amortising the handshake cost. HTTP/2 takes this further with multiplexing: multiple requests in flight simultaneously over one connection using numbered streams.

**Q3. What role does the OS kernel play before Node.js sees a request?**
A: The kernel handles everything up to handing Node.js a connected socket:

```
OS Kernel responsibilities:

1. Listening socket:
   - Node.js calls server.listen(3000) → wraps bind() + listen() syscalls
   - OS allocates a listening socket and a backlog queue
   - Backlog queue holds completed-but-not-yet-accept()ed connections

2. TCP handshake (fully kernel-space):
   - Kernel answers SYN, sends SYN-ACK, confirms ACK
   - Node.js is NOT woken up during this — it happens in kernel space
   - Only after the handshake completes does the connection move to backlog

3. accept() syscall:
   - libuv (Node.js's async I/O library) calls accept() in its I/O poll phase
   - Returns a new file descriptor representing the connected socket
   - THIS is when Node.js first becomes aware of the connection
   - Node.js wraps this fd in a net.Socket and emits 'connection' on the server

4. Buffering:
   - Kernel has its own receive buffer (TCP receive window)
   - Data can arrive and sit in kernel buffer before Node.js reads it
   - Node.js calls read() to pull bytes out of the kernel buffer into userspace
```

```javascript
// You never write this — Node.js internals do — but this is what happens:
const server = net.createServer((socket) => {
    // socket = result of accept() — the kernel handed us this fd
    socket.on('data', (chunk) => {
        // Each 'data' event = one read() syscall returning available bytes
        // from the kernel's receive buffer
    });
});
server.listen(3000);  // bind() + listen()
```

## Section 2: The Network Layer

**Q4. How does TLS fit into the request lifecycle — what happens during a TLS handshake?**
A: TLS sits between TCP and HTTP. After the TCP connection is established, TLS negotiates before any HTTP bytes flow:

```
TLS 1.3 Handshake (simplified — 1 round trip):

Client                                          Server
  │                                               │
  │──── ClientHello ─────────────────────────────►│
  │     (TLS versions, cipher suites,             │
  │      key_share for ECDH)                      │
  │                                               │
  │◄─── ServerHello ──────────────────────────────│
  │◄─── {Certificate} ────────────────────────────│
  │◄─── {CertificateVerify} ──────────────────────│
  │◄─── {Finished} ───────────────────────────────│
  │     (Server public key, signature,            │
  │      server's Finished MAC)                   │
  │                                               │
  │──── {Finished} ─────────────────────────────►│  ← 1 RTT total
  │──── {HTTP GET /...} ────────────────────────►│  ← encrypted from here
  │                                               │
  │◄─── {HTTP 200 OK...} ─────────────────────────│
```

```
Where Node.js handles TLS:
  - node:tls module wraps OpenSSL
  - Creates a TLSSocket on top of a net.Socket
  - TLS decryption happens BEFORE the HTTP parser sees bytes

Where production often offloads TLS:
  ┌─────────────────────────────────────────────────────┐
  │  Client ──HTTPS──► nginx / AWS ALB / Cloudflare     │
  │  (TLS terminated here)                              │
  │            ──HTTP──► Node.js process                │
  │  (Node.js sees plain HTTP on internal network)      │
  └─────────────────────────────────────────────────────┘
  Benefits: hardware TLS acceleration, certificate management
            in one place, Node.js not burdened with crypto
```

TLS 1.3's 0-RTT mode allows resuming a prior session with zero round trips — the client sends encrypted data alongside the first ClientHello — but this has replay-attack implications and is typically disabled for non-idempotent requests.

**Q5. What is `llhttp` and how does it turn raw bytes into a request object?**
A: `llhttp` is Node.js's HTTP parser, a C library that replaced the older `http_parser` in Node.js 12. It's a state machine that processes HTTP/1.x byte streams:

```
Raw TCP bytes arrive:
"POST /api/orders HTTP/1.1\r\n
Content-Type: application/json\r\n
Content-Length: 47\r\n
Authorization: Bearer eyJ...\r\n
\r\n
{\"userId\":\"42\",\"items\":[{\"id\":\"abc\"}]}"

llhttp state machine processes character by character:

State: REQUEST_LINE
  → method = "POST"
  → url = "/api/orders"
  → http_major = 1, http_minor = 1

State: HEADERS
  → "Content-Type" : "application/json"
  → "Content-Length" : "47"
  → "Authorization" : "Bearer eyJ..."
  → \r\n\r\n → headers complete

State: BODY
  → Content-Length = 47 → read exactly 47 bytes
  → body bytes available (but NOT parsed to JSON yet)
```

```javascript
// What Node.js's http module builds from llhttp callbacks:
IncomingMessage {
    method: 'POST',
    url: '/api/orders',
    httpVersion: '1.1',
    headers: {
        'content-type': 'application/json',
        'content-length': '47',
        'authorization': 'Bearer eyJ...'
    },
    // body is NOT here yet — it's a Readable stream
    // req.body is undefined until a body-parser middleware reads it
}
```

```javascript
// The body arrives as a stream:
req.on('data', (chunk) => buffer.push(chunk));
req.on('end', () => {
    const body = JSON.parse(Buffer.concat(buffer).toString());
    // Only NOW do you have req.body
});
// express.json() does exactly this, then attaches result to req.body
// and calls next()
```

Critical interview point: **`req.body` is not populated by Node.js**. It's `undefined` until body-parser middleware reads and parses the stream. This is a source of subtle bugs when middleware order is wrong.

## Section 3: Event Loop Integration

**Q6. How does the Node.js event loop process incoming connections — which phase handles I/O?**
A: Node.js uses libuv, which runs an event loop with distinct phases. Network I/O lives in the **poll phase**:

```
Node.js Event Loop — one tick:

  ┌─────────────────────────────────┐
  │           timers                │  ← setTimeout, setInterval callbacks
  ├─────────────────────────────────┤
  │       pending callbacks         │  ← I/O errors from previous tick
  ├─────────────────────────────────┤
  │           idle, prepare         │  ← internal libuv use
  ├─────────────────────────────────┤
  │             poll                │  ← NEW I/O EVENTS (accept, read, write)
  │                                 │     blocks here if queue empty + no timers
  ├─────────────────────────────────┤
  │            check                │  ← setImmediate callbacks
  ├─────────────────────────────────┤
  │        close callbacks          │  ← socket.on('close', ...)
  └─────────────────────────────────┘
         ↑                ↓
    microtasks         microtasks
    (process.nextTick, Promise.then — run after EVERY phase)
```

```
How a new connection flows through:

1. TCP handshake completes (kernel-space) → fd added to kernel event set
2. Poll phase: epoll_wait() / kqueue returns → "fd X is readable"
3. libuv calls accept() → new connected socket fd
4. libuv wraps fd in uv_tcp_t → Node.js wraps in net.Socket
5. Node.js emits 'connection' on the http.Server
6. http.Server attaches llhttp parser to the socket's 'data' event
7. Next tick's poll phase: socket fd is readable (HTTP bytes arrived)
8. llhttp parses bytes → emits 'request' on the server
9. http.Server calls requestListener(req, res) → Express app(req, res)
```

```javascript
// The requestListener is what you pass to createServer:
const server = http.createServer((req, res) => {
    // This callback fires in the poll phase when a complete request line
    // and headers have been parsed. Body hasn't been read yet.
    app(req, res);  // Express takes over from here
});
```

**Q7. What is the relationship between `async/await` in a route handler and the event loop?**
A: Every `await` in a handler is a suspension point — the event loop is free to process other requests while waiting:

```javascript
// Route handler:
app.get('/api/order/:id', async (req, res) => {
    // [TICK 1] Synchronous — runs until first await
    const { id } = req.params;

    // [SUSPEND] event loop free to handle other requests
    const order = await db.query('SELECT * FROM orders WHERE id = $1', [id]);
    // [TICK 2] Resumes in microtask queue (Promise.then) after DB responds
    // This runs in the poll phase when the socket to DB becomes readable

    // [SUSPEND] event loop free again
    const user = await userService.get(order.userId);
    // [TICK 3] Resumes after user service responds

    // Synchronous JSON serialization and socket write
    res.json({ order, user });
    // [DONE] res.end() schedules a writev() syscall
});

// While the above handler is awaiting the DB, the event loop is free to:
// - Accept new TCP connections
// - Parse HTTP bytes on other sockets
// - Run other route handlers that aren't awaiting
// This is how Node.js handles thousands of concurrent requests on one thread
```

```
Timeline with 3 concurrent requests:

Event loop tick →  T1    T2    T3    T4    T5    T6    T7
Request A          ──►  [db]         [res]
Request B                ──►  [db]               [res]
Request C                      ──►  [db]   [res]

[db] = awaiting database — event loop free
──►  = CPU-bound synchronous JS code running
[res] = writing response to socket
```

The critical implication: synchronous CPU-bound code in a route handler **blocks all other requests**. `JSON.parse` on a 50MB body, a tight loop, or synchronous `fs.readFileSync` blocks the event loop for every request in flight.

## Section 4: HTTP Framework Layer

**Q8. How does Express route matching work — what happens between `app(req, res)` and your handler firing?**
A: Express maintains a stack of `Layer` objects. Each has a regex compiled from the route pattern and a handle function. Matching is a sequential scan:

```javascript
// What Express builds internally when you write:
app.use('/api', apiRouter);
app.get('/api/users/:id', authMiddleware, handler);
app.use(errorHandler);

// Internal layer stack (simplified):
[
  Layer { regexp: /^\/api\/?/i,        handle: apiRouter },
  Layer { regexp: /^\/api\/users\/([^\/]+)\/?$/i, handle: authMiddleware },
  Layer { regexp: /^\/api\/users\/([^\/]+)\/?$/i, handle: handler },
  Layer { regexp: /.*/,                handle: errorHandler }
]
```

```
Matching algorithm (router.handle):

  req = { method: 'GET', url: '/api/users/42' }

  Layer 0: regexp.test('/api/users/42') → true, but no method check (app.use)
    → execute apiRouter
    → apiRouter has its own stack, doesn't match '/users/42', falls through
  Layer 1: regexp.test('/api/users/42') → true, method 'GET' matches
    → extract params: { id: '42' } → attach to req.params
    → execute authMiddleware
    → authMiddleware calls next()
  Layer 2: same regexp, same method
    → execute handler
    → handler calls res.json() → response sent
  Layer 3: never reached (response already sent)
```

```javascript
// Route parameters are extracted via capturing groups:
// Pattern: /api/users/:id
// Compiled: /^\/api\/users\/([^\/]+)\/?$/i
//                            ↑ captures '42' from /api/users/42
// req.params.id = '42'  (always a string — never a number)

// Query strings are NOT part of route matching:
// GET /api/users/42?include=orders
// req.params.id = '42'           ← from path
// req.query.include = 'orders'   ← from query string, parsed separately
```

**Q9. Explain the Express middleware execution model — what does `next()` actually do?**
A: `next` is a closure over the router's layer stack. Calling it advances the stack pointer and attempts the next matching layer:

```javascript
// Simplified implementation of what Express's next() does:
function createNext(stack, index, req, res) {
    return function next(err) {
        const layer = findNextMatch(stack, index + 1, req, err);
        if (!layer) {
            // No more layers — unhandled request or unhandled error
            return res.status(err ? 500 : 404).end();
        }
        try {
            if (err) {
                // Skip regular middleware, find error handler (4 params)
                layer.handle_error(err, req, res, createNext(stack, layer.index, req, res));
            } else {
                layer.handle_request(req, res, createNext(stack, layer.index, req, res));
            }
        } catch (thrownErr) {
            // Synchronous throw → convert to error path
            next(thrownErr);
        }
    };
}
```

```javascript
// The practical implications:

// 1. Calling next() is optional — middleware that ends the response doesn't need it:
app.get('/health', (req, res) => {
    res.json({ status: 'ok' });
    // No next() needed — response is done
    // Calling next() AFTER res.json() causes "headers already sent" error
});

// 2. next(err) with any truthy value triggers the error path:
app.use(async (req, res, next) => {
    try {
        await riskyOperation();
        next();
    } catch (err) {
        next(err);  // Jumps to first 4-argument middleware
    }
});

// 3. Express doesn't automatically catch async rejections:
app.get('/bad', async (req, res, next) => {
    await failingOp();  // If this rejects, next(err) is NOT called automatically
    // The rejection becomes an unhandledRejection and the request hangs
});

// Fix — always wrap async handlers:
app.get('/good', asyncHandler(async (req, res) => {
    await failingOp();  // asyncHandler catches rejection and calls next(err)
}));

// Or in Express 5 (async errors are caught automatically):
// app.get('/express5', async (req, res) => { ... });  ← just works
```

**Q10. What is the correct middleware order in a production Express application, and why does order matter?**
A: Middleware fires in registration order. Dependencies between layers create hard ordering constraints:

```javascript
const app = express();

// ① Context / tracing — MUST be first
// Everything else reads requestId from async context
app.use(contextMiddleware);     // als.run() — attaches requestId, traceId

// ② Security headers — early, before any response can be sent
app.use(helmet());              // X-Frame-Options, CSP, HSTS, etc.

// ③ CORS — before auth, because preflight OPTIONS requests don't have tokens
app.use(cors(corsOptions));     // Handles OPTIONS → 204, sets Access-Control headers

// ④ Request logging — after tracing (needs requestId), before auth (logs before auth fails)
app.use(requestLogger);

// ⑤ Body parsing — before any middleware that reads req.body
app.use(express.json({ limit: '1mb' }));
app.use(express.urlencoded({ extended: true }));

// ⑥ Rate limiting — after body parsing (may need body), before auth (fail fast)
app.use(rateLimiter);

// ⑦ Auth — after body parsing, after rate limiting
app.use(authMiddleware);        // Reads token, populates req.user

// ⑧ Routes — after all global middleware
app.use('/api/v1', apiRouter);

// ⑨ 404 handler — after all routes (nothing matched)
app.use((req, res) => {
    res.status(404).json({ error: 'Not found' });
});

// ⑩ Error handler — MUST be last, MUST have 4 arguments
app.use((err, req, res, next) => {
    const status = err.status || 500;
    res.status(status).json({ error: err.message, requestId: getRequestId() });
});
```

```
Why order matters — concrete failure modes:

WRONG: auth before body parser
  authMiddleware reads req.body.apiKey → undefined (body not parsed yet)
  → Always fails, even with valid credentials in body

WRONG: CORS after auth
  Preflight OPTIONS request has no Authorization header
  → authMiddleware rejects with 401 before CORS can set headers
  → Browser never sees CORS headers → blocks the real request

WRONG: error handler before routes
  Express never reaches error handler for route errors
  → Errors propagate to Express's built-in error handler (stack trace in HTML)

WRONG: 404 handler before routes
  Every request returns 404 — no routes are reachable
```

## Section 5: The Middleware Pipeline in Detail

**Q11. How does body parsing actually work — what does `express.json()` do internally?**
A: `express.json()` is a thin wrapper around the `body-parser` package. It reads the request stream, enforces limits, checks `Content-Type`, and parses:

```javascript
// Conceptual implementation of express.json():
function jsonParser(limit = '100kb') {
    return function(req, res, next) {
        // 1. Only parse if Content-Type matches
        if (!req.headers['content-type']?.startsWith('application/json')) {
            return next();  // Not JSON — skip silently
        }

        // 2. Only parse methods that can have a body
        if (['GET', 'HEAD', 'DELETE'].includes(req.method)) {
            return next();  // No body expected
        }

        const chunks = [];
        let size = 0;
        const maxBytes = bytes(limit);  // '100kb' → 102400

        // 3. Read stream
        req.on('data', (chunk) => {
            size += chunk.length;
            if (size > maxBytes) {
                // Abort — payload too large
                req.destroy();
                return next(createError(413, 'Payload too large'));
            }
            chunks.push(chunk);
        });

        req.on('end', () => {
            try {
                const raw = Buffer.concat(chunks).toString('utf8');
                req.body = JSON.parse(raw);   // 4. Parse
                next();
            } catch (err) {
                next(createError(400, 'Invalid JSON'));  // Malformed body
            }
        });

        req.on('error', next);  // Stream errors → error handler
    };
}
```

```javascript
// What can go wrong with body parsing:

// 1. Missing Content-Type header
fetch('/api', {
    method: 'POST',
    body: JSON.stringify({ key: 'value' })
    // ← forgot: headers: { 'Content-Type': 'application/json' }
});
// Result: req.body === undefined — parser skips it silently

// 2. Payload too large
// express.json() default limit is 100kb
// A file upload disguised as JSON will hit this → 413 error

// 3. Body read twice
// If a middleware reads req as a stream before express.json() processes it,
// the stream is consumed — express.json() gets empty body
// Solution: always let body-parser run first, or use req.rawBody

// 4. Async handler starts before body is fully read
// This can't happen via express.json() (it calls next() only after 'end')
// But it CAN happen if you skip body-parser and read req manually
```

**Q12. How does authentication middleware work — what does it read, verify, and attach?**
A: Auth middleware is the gatekeeper between the framework and application code. For JWT-based auth:

```javascript
// Full JWT auth middleware:
import jwt from 'jsonwebtoken';
import { RequestContext } from './context';

export async function authMiddleware(req, res, next) {
    // 1. Extract token — check multiple locations by convention
    const authHeader = req.headers['authorization'];
    const token = authHeader?.startsWith('Bearer ')
        ? authHeader.slice(7)                    // "Bearer eyJ..." → "eyJ..."
        : req.cookies?.accessToken               // Fallback to cookie
        ?? req.query?.token;                     // Fallback to query (avoid in prod)

    if (!token) {
        return next(createError(401, 'No token provided'));
    }

    try {
        // 2. Verify signature + expiry
        // jwt.verify is SYNCHRONOUS — it's CPU-bound crypto (HMAC or RSA verify)
        // For RSA/ECDSA with large key sizes, this can be slow
        const payload = jwt.verify(token, process.env.JWT_SECRET, {
            algorithms: ['HS256'],    // Explicitly allowlist — never omit this
            audience: 'my-api',      // Validate audience claim
            issuer: 'my-auth-service'
        });
        // throws JsonWebTokenError if signature invalid
        // throws TokenExpiredError if exp claim is in the past

        // 3. Check token revocation (if maintaining a blocklist)
        const isRevoked = await tokenBlocklist.has(payload.jti);
        if (isRevoked) {
            return next(createError(401, 'Token revoked'));
        }

        // 4. Attach user to request — available to all downstream middleware
        req.user = {
            id: payload.sub,
            roles: payload.roles,
            tenantId: payload.tenantId
        };

        // 5. Also store in async context (available without req parameter)
        RequestContext.set('userId', payload.sub);

        next();
    } catch (err) {
        if (err.name === 'TokenExpiredError') {
            return next(createError(401, 'Token expired'));
        }
        return next(createError(401, 'Invalid token'));
    }
}

// Route-level auth — skip auth for public routes:
app.get('/api/health', handler);                          // No auth
app.post('/api/auth/login', loginHandler);               // No auth
app.get('/api/orders', authMiddleware, ordersHandler);   // Auth required
// Or apply globally and use skipAuth() pattern for exceptions
```

```javascript
// Role-based access control as a separate middleware (after auth):
function requireRole(...roles) {
    return (req, res, next) => {
        if (!req.user) {
            return next(createError(401, 'Not authenticated'));
        }
        const hasRole = roles.some(role => req.user.roles.includes(role));
        if (!hasRole) {
            return next(createError(403, 'Insufficient permissions'));
        }
        next();
    };
}

// Usage:
app.delete('/api/users/:id', authMiddleware, requireRole('admin'), deleteUserHandler);
```

## Section 6: The Route Handler and Application Code

**Q13. What happens inside a route handler — how do services, database queries, and external APIs fit in?**
A: The route handler is the boundary between framework code and application code. It should be thin — extract params, call services, send response:

```javascript
// Well-structured route handler (controller pattern):
app.post('/api/orders', authMiddleware, async (req, res, next) => {
    try {
        // 1. Extract and validate input
        const { items, shippingAddressId } = req.body;
        const userId = req.user.id;

        if (!items?.length) {
            return res.status(400).json({ error: 'items required' });
        }

        // 2. Call the service layer — business logic lives here, not in the handler
        const order = await orderService.create({ userId, items, shippingAddressId });
        //            ↑ this may: validate inventory, calculate totals,
        //              write to DB, publish to queue, send confirmation email

        // 3. Respond — handler's only job
        res.status(201).json({
            order,
            requestId: RequestContext.get().requestId  // from async context
        });

    } catch (err) {
        next(err);  // Hand all unhandled errors to Express error handler
    }
});

// The service layer (orderService.create):
async function create({ userId, items, shippingAddressId }) {
    // Uses Unit of Work pattern — all DB writes in one transaction:
    return withTransaction(async () => {
        // Validate inventory (DB read)
        const inventory = await inventoryRepo.checkAvailability(items);
        if (!inventory.allAvailable) {
            throw new ValidationError('Some items are out of stock', inventory.unavailable);
        }

        // Calculate pricing (in-memory)
        const { total, lineItems } = pricingEngine.calculate(items, inventory.prices);

        // Write order (DB write — uses transaction from withTransaction())
        const order = await orderRepo.create({ userId, total, lineItems, shippingAddressId });

        // Publish domain event (Kafka/SQS — fire and forget, NOT in transaction)
        await eventBus.publish('order.created', { orderId: order.id, userId, total });

        return order;
    });
}
```

```
Layered architecture — what lives where:

Route handler (Controller):
  ├── Parse req.params, req.body, req.query
  ├── Call service methods
  └── Map service result to HTTP response (status code, body shape)

Service layer:
  ├── Business logic and rules
  ├── Orchestrate multiple repositories
  ├── Domain events
  └── No knowledge of HTTP (never imports express or req/res)

Repository layer:
  ├── Database queries (SELECT, INSERT, UPDATE)
  ├── Data mapping (DB row → domain object)
  └── No business logic

Infrastructure:
  ├── DB connection pool
  ├── External API clients
  └── Message queue producers/consumers
```

**Q14. How does database transaction propagation work across service and repository layers without passing the transaction object everywhere?**
A: The cleanest solution is `AsyncLocalStorage` for implicit transaction propagation — the Unit of Work pattern without parameter drilling:

```typescript
// db/transaction.ts
import { AsyncLocalStorage } from 'node:async_hooks';
import { Knex } from 'knex';
import db from './db';

const txStorage = new AsyncLocalStorage<Knex.Transaction>();

export async function withTransaction<T>(fn: () => Promise<T>): Promise<T> {
    return db.transaction(async (trx) => {
        // Everything called within fn() sees this transaction
        return txStorage.run(trx, fn);
    });
}

export function getCurrentTx(): Knex.Transaction | undefined {
    return txStorage.getStore();
}

// db/base-repo.ts
export function getQueryBuilder(table: string) {
    const trx = getCurrentTx();
    return trx ? trx(table) : db(table);
    //           ↑ use transaction if one is active, raw DB otherwise
}

// repositories/order.repo.ts
export async function createOrder(data: OrderData): Promise<Order> {
    const [order] = await getQueryBuilder('orders').insert(data).returning('*');
    return order;
}

export async function updateInventory(itemId: string, delta: number): Promise<void> {
    await getQueryBuilder('inventory')
        .where({ item_id: itemId })
        .decrement('quantity', delta);
}

// Usage — both operations in the same transaction, no parameter passing:
await withTransaction(async () => {
    const order = await createOrder({ userId, total });          // same trx
    await updateInventory(itemId, quantity);                      // same trx
    // If updateInventory throws → entire transaction rolls back
});
```

## Section 7: The Response Path

**Q15. How does `res.json()` actually send data — what happens between calling it and bytes leaving the socket?**
A: `res.json()` is a chain of operations that ends in a `write()` syscall to the socket file descriptor:

```javascript
// What res.json(data) does internally (Express source, simplified):
res.json = function(obj) {
    // 1. Serialize to string
    const body = JSON.stringify(obj);
    //            ↑ synchronous, blocks event loop for large objects

    // 2. Set headers (if not already set)
    if (!this.get('Content-Type')) {
        this.set('Content-Type', 'application/json; charset=utf-8');
    }
    this.set('Content-Length', Buffer.byteLength(body));

    // 3. Call res.send() → res.end()
    return this.send(body);
};

res.send = function(body) {
    // Set ETag, handle conditional GET (304), apply charset encoding
    // ...
    return this.end(body, 'utf8');
};

// res.end() is Node.js core (http.ServerResponse):
// → calls this.socket.write(responseHeaders + body)
// → schedules writev() syscall (may batch headers + body in one syscall)
// → emits 'finish' event on res when all data has been flushed to kernel buffer

// Note: 'finish' ≠ "client received it"
// It means Node.js passed the bytes to the kernel — kernel handles actual TCP delivery
```

```javascript
// Streaming response — for large datasets:
app.get('/api/orders/export', async (req, res) => {
    res.setHeader('Content-Type', 'application/json');
    res.setHeader('Transfer-Encoding', 'chunked');  // No Content-Length needed

    // Streaming from DB using cursor:
    const cursor = db.orders.find({}).cursor();

    res.write('[');
    let first = true;
    for await (const order of cursor) {
        if (!first) res.write(',');
        res.write(JSON.stringify(order));
        first = false;
    }
    res.write(']');
    res.end();
    // Each res.write() → a TCP chunk; browser can parse incrementally
    // Memory usage stays constant — one record in memory at a time
});

// Contrast with:
app.get('/api/orders/export-bad', async (req, res) => {
    const orders = await db.orders.findAll();  // 1M records → OOM crash
    res.json(orders);
});
```

**Q16. What HTTP status codes should different error conditions return, and how does the error handler determine them?**
A: Status codes communicate the nature of the failure to clients and intermediaries. Mapping error types to codes:

```javascript
// Error class hierarchy with built-in status codes:
class AppError extends Error {
    constructor(message, status = 500, code = 'INTERNAL_ERROR') {
        super(message);
        this.status = status;
        this.code = code;
        this.isOperational = true;  // vs programming errors (bugs)
    }
}

class ValidationError extends AppError {
    constructor(message, fields) {
        super(message, 400, 'VALIDATION_ERROR');
        this.fields = fields;
    }
}

class UnauthorizedError extends AppError {
    constructor(message = 'Authentication required') {
        super(message, 401, 'UNAUTHORIZED');
    }
}

class ForbiddenError extends AppError {
    constructor(message = 'Insufficient permissions') {
        super(message, 403, 'FORBIDDEN');
    }
}

class NotFoundError extends AppError {
    constructor(resource) {
        super(`${resource} not found`, 404, 'NOT_FOUND');
    }
}

class ConflictError extends AppError {
    constructor(message) {
        super(message, 409, 'CONFLICT');  // e.g. duplicate email
    }
}

class RateLimitError extends AppError {
    constructor() {
        super('Too many requests', 429, 'RATE_LIMITED');
    }
}

// Central error handler — maps all errors to HTTP responses:
app.use((err, req, res, next) => {
    const requestId = RequestContext.tryGet()?.requestId;

    // Log operational errors at warn, bugs at error
    if (err.isOperational) {
        logger.warn('Operational error', { err, requestId });
    } else {
        logger.error('Unexpected error (bug)', { err, requestId });
    }

    // Hide internal error details in production
    const isProduction = process.env.NODE_ENV === 'production';
    const status = err.status || 500;

    res.status(status).json({
        error: {
            code: err.code || 'INTERNAL_ERROR',
            message: (err.isOperational || !isProduction)
                ? err.message
                : 'An unexpected error occurred',
            fields: err.fields,       // ValidationError only
            requestId,                // Always include for support reference
        }
    });
});
```

```
Status code cheat sheet for common scenarios:

200 OK              → Successful GET, PUT, PATCH
201 Created         → Successful POST that created a resource (include Location header)
204 No Content      → Successful DELETE, or OPTIONS preflight
400 Bad Request     → Missing/invalid fields, malformed JSON, failed validation
401 Unauthorized    → No token, expired token, invalid token signature
                      (misleading name — means "unauthenticated", not "unauthorized")
403 Forbidden       → Valid token, but insufficient permissions
                      (what "unauthorized" actually means semantically)
404 Not Found       → Resource doesn't exist (or hidden for security — same as 403)
409 Conflict        → Duplicate key, optimistic lock conflict
422 Unprocessable   → Valid JSON but semantically invalid (some APIs use this vs 400)
429 Too Many Req.   → Rate limit exceeded (include Retry-After header)
500 Internal Error  → Unhandled exception — never reveal stack trace in response
503 Service Unavail.→ Dependency down, circuit breaker open, intentional downtime
```

## Section 8: Performance and Production Concerns

**Q17. What can block the Node.js event loop during request processing, and how do you detect and fix it?**
A: Event loop blocking is the most common Node.js performance problem — a single synchronous operation can delay every request in flight:

```javascript
// BLOCKING OPERATIONS — avoid in request handlers:

// 1. Synchronous filesystem access
const config = fs.readFileSync('./config.json');  // BLOCKS — entire event loop stalls
// Fix: read at startup, cache in memory, never on each request

// 2. Large JSON.parse / JSON.stringify
app.get('/data', async (req, res) => {
    const data = await db.getLargeDataset();  // 50,000 records
    res.json(data);  // JSON.stringify blocks for ~100ms+ — all other requests wait
    // Fix: stream using res.write() / json-stream-stringify
    // Or: paginate — never return 50k records
});

// 3. Tight computation loops
function fibonacci(n) {
    if (n <= 1) return n;
    return fibonacci(n - 1) + fibonacci(n - 2);  // fib(45) blocks for ~10s
}
app.get('/fib/:n', (req, res) => {
    res.json({ result: fibonacci(parseInt(req.params.n)) });
    // Fix: worker_threads for CPU-bound work
});

// 4. Synchronous crypto (for large inputs)
const hash = crypto.createHash('sha256').update(hugePdfBuffer).digest('hex');
// Fix: stream through crypto, or offload to worker thread

// 5. RegEx catastrophic backtracking
/^(a+)+$/.test('aaaaaaaaaaaaaaaaaaaaaaaaaaaa!');  // exponential time — blocks forever
// Fix: validate regex complexity, use non-backtracking alternatives
```

```javascript
// Detection:

// 1. --inspect flag + Chrome DevTools Performance tab
// node --inspect app.js → open chrome://inspect → record profile

// 2. clinic.js (most practical tool):
// npx clinic doctor -- node app.js
// Generates flamegraph + event loop delay chart

// 3. Built-in event loop lag measurement:
let lastTick = Date.now();
setInterval(() => {
    const now = Date.now();
    const lag = now - lastTick - 100;  // Expected 100ms interval
    if (lag > 50) {
        logger.warn('Event loop lag detected', { lagMs: lag });
    }
    lastTick = now;
}, 100);

// 4. perf_hooks.monitorEventLoopDelay()
const { monitorEventLoopDelay } = require('perf_hooks');
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
    logger.info('Event loop p99 delay', { p99Ms: h.percentile(99) / 1e6 });
    h.reset();
}, 10000);
```

**Q18. How do connection pools, Keep-Alive, and backpressure affect the lifecycle at scale?**
A:

```
Connection pooling (database):

Without pool:
  Request 1 → new DB connection → query → close → (3-way TCP + auth = ~20ms overhead)
  Request 2 → new DB connection → query → close
  At 1000 req/s: 1000 DB connections per second, most DB servers reject above ~100

With pool (pg-pool, Knex, Sequelize all use this):
  Pool: [conn1, conn2, ... conn10]  ← 10 persistent connections at startup
  Request 1 → acquire conn3 → query → release conn3 back to pool
  Request 2 → acquire conn3 (reused) → query → release
  Connection overhead paid once; queries take milliseconds not 20ms+

Pool sizing:
  Too small → requests queue waiting for a connection → latency spikes
  Too large → DB overwhelmed → global slowdown
  Rule of thumb: (number_of_cores × 2) + effective_spindle_count
  For PostgreSQL: start at 10-20, tune based on pg_stat_activity
```

```javascript
// Backpressure — when the client can't receive data fast enough:
app.get('/api/stream', (req, res) => {
    const readable = getLargeDataStream();

    readable.on('data', (chunk) => {
        const canContinue = res.write(chunk);
        if (!canContinue) {
            // res.write returned false → kernel TCP send buffer is full
            // Client is reading slower than we're writing
            readable.pause();  // Stop reading from source — apply backpressure upstream
        }
    });

    res.on('drain', () => {
        // Kernel buffer has space again → resume
        readable.resume();
    });

    readable.on('end', () => res.end());
});

// Simpler — pipe() handles backpressure automatically:
app.get('/api/stream', (req, res) => {
    getLargeDataStream().pipe(res);
    // pipe() calls pause()/resume() internally — no manual backpressure management
});
```

```
Keep-Alive and HTTP/2:

HTTP/1.1 Keep-Alive:
  Client sends: Connection: keep-alive
  Server keeps socket open after response
  Next request reuses same TCP connection — saves RTT + TCP handshake
  Server timeout: typically 5-60s idle → then FIN sequence

HTTP/2 multiplexing:
  Multiple logical streams (requests) share ONE TCP connection
  Streams are numbered: request A = stream 1, request B = stream 3
  No head-of-line blocking between streams (unlike HTTP/1.1 pipelining)
  Server push: server can push assets before client requests them
  
Node.js http2 module: native support
nginx proxy: negotiate HTTP/2 with client, forward HTTP/1.1 to Node.js
```

## Section 9: Scenario-Based Questions

**Q19. "A route handler is slow — sometimes 2 seconds, usually 50ms. How do you diagnose this?"**
A: Intermittent latency spikes have a short list of root causes. A systematic investigation:

```javascript
// Step 1: Add timing instrumentation to isolate the slow segment
app.get('/api/orders/:id', async (req, res, next) => {
    const t = {};
    t.start = Date.now();

    const order = await orderRepo.findById(req.params.id);
    t.afterDb = Date.now();

    const user = await userService.get(order.userId);
    t.afterUserSvc = Date.now();

    const enriched = enrichmentService.enrich(order, user);
    t.afterEnrich = Date.now();

    res.json(enriched);

    logger.info('Request timing', {
        dbMs: t.afterDb - t.start,
        userSvcMs: t.afterUserSvc - t.afterDb,
        enrichMs: t.afterEnrich - t.afterUserSvc,
        totalMs: t.afterEnrich - t.start,
        orderId: req.params.id
    });
});

// Run the route 100 times, compare fast vs slow logs:
// If dbMs is always fast but userSvcMs spikes → issue is in userService
// If dbMs spikes → DB query plan, index, or connection pool exhaustion
```

```
Common causes and their signatures:

1. DB connection pool exhaustion
   Signature: dbMs spikes to 1800ms+ intermittently (waiting for pool slot)
   Cause: all pool connections busy, new queries queue
   Fix: increase pool size, reduce query duration, check for leaked connections
   Detect: SELECT count(*) FROM pg_stat_activity WHERE state = 'active'

2. Missing index (query plan regression)
   Signature: dbMs consistently slow for specific orderId patterns
   Cause: new data volume crossed threshold where seq scan is slower than index
   Fix: EXPLAIN ANALYZE the slow query → add missing index
   Detect: pg_stat_statements for slow query log

3. External service cold start / timeout
   Signature: userSvcMs spikes to 2000ms exactly (= timeout value)
   Cause: userService pod recycled, connection reset, or circuit breaker tripping
   Fix: retry with exponential backoff, fallback to cached data, reduce timeout

4. Event loop blocking by other requests
   Signature: ALL routes slow simultaneously, not just this one
   Cause: a concurrent request is running CPU-intensive synchronous code
   Fix: clinic.js flamegraph → find the blocking call → offload to worker_threads

5. Memory pressure / GC pauses
   Signature: latency spikes correlate with heap size (visible in --inspect)
   Cause: high allocation rate → frequent GC → pauses
   Fix: reduce allocations in hot paths, use Buffer pooling, check for memory leaks
```

**Q20. "Your service is receiving 10,000 requests/second but only 8,000 are completing — the rest time out. Walk through how you'd find and fix the bottleneck."**
A: A saturated system needs systematic throughput analysis:

```
Step 1: Identify WHERE requests are dying

Check at each layer:

a) Load balancer logs:
   502/504 errors → Node.js isn't responding (process crash or queue full)
   504 gateway timeout → Node.js accepted connection but didn't respond in time

b) Node.js metrics (prometheus-style):
   http_requests_total{status="timeout"} — which routes are timing out?
   http_request_duration_seconds{p99} — are ALL routes slow or specific ones?
   event_loop_lag_seconds — is the event loop blocked?

c) System metrics:
   CPU at 100% → event loop blocked by computation
   Memory at limit → GC pauses or OOM kills
   File descriptor limit → 'EMFILE too many open files' errors
   Network I/O saturation → packets dropped by kernel
```

```javascript
// Step 2: Add queue depth instrumentation
let activeRequests = 0;
app.use((req, res, next) => {
    activeRequests++;
    logger.info('Queue depth', { activeRequests });  // Log on each request
    res.on('finish', () => activeRequests--);
    next();
});

// If activeRequests grows without bound → leak: requests never complete (no res.end())
// If activeRequests plateaus at exactly pool size → pool exhaustion
```

```
Step 3: Bottleneck type and fix

Throughput bottleneck: Node.js CPU (event loop)
  Symptom: CPU 100%, event loop lag >50ms
  Fix: horizontal scaling (more Node processes / pods)
       cluster mode: os.cpus().length worker processes
       OR: PM2 cluster mode / Kubernetes HPA

Throughput bottleneck: Database
  Symptom: CPU <30% in Node but DB CPU at 100%, slow queries
  Fix: add replicas for reads, connection pool tuning,
       query optimization, add caching (Redis)

Throughput bottleneck: External HTTP calls (fan-out)
  Symptom: many concurrent outgoing requests, all waiting
  Fix: cache results (stale-while-revalidate),
       circuit breaker (opossum / cockatiel),
       batch requests where API supports it

Throughput bottleneck: Memory (GC)
  Symptom: periodic throughput drops (GC pauses) visible in event loop lag
  Fix: reduce object allocation in hot paths,
       use --max-old-space-size to increase heap,
       profile with --inspect and Chrome DevTools → Memory tab

Throughput bottleneck: File descriptors
  Symptom: EMFILE errors in logs
  Fix: ulimit -n 65536 (Linux), or set in systemd unit:
       LimitNOFILE=65536
       Each open TCP socket consumes one fd —
       10,000 req/s × 100ms avg response = ~1,000 concurrent sockets minimum
```

## Quick Reference Table

| Stage | Responsible component | Common mistake |
|---|---|---|
| TCP accept | OS kernel + libuv poll phase | Confusing TCP connection with HTTP request — they're separate lifetimes |
| TLS handshake | node:tls / OpenSSL (or load balancer) | Forgetting that Node.js often receives plain HTTP behind an ALB/nginx |
| HTTP parsing | llhttp (C parser in Node.js core) | Expecting `req.body` to be populated — it's a stream until body-parser runs |
| Router matching | Express Layer stack | Using `req.params.id` without coercing from string to number |
| Middleware chain | Express `next()` closure | Registering error handler before routes, or CORS after auth |
| Body parsing | `express.json()` / `body-parser` | Missing `Content-Type: application/json` header → `req.body` is `undefined` |
| Auth middleware | JWT verify + `req.user` | Not calling `next(err)` on rejection, or forgetting `algorithms` allowlist |
| Route handler | Application controller | Putting business logic in the handler instead of a service layer |
| Database access | Connection pool + repo layer | Not using connection pooling, or forgetting to release connections |
| Response | `res.json()` → `socket.write()` | Calling `res.json()` after headers already sent (calling next after res.end) |
| Error handler | 4-argument Express middleware | Registering before routes, or using 3 arguments (not recognized as error handler) |
| Event loop | libuv poll + microtask queue | Blocking the event loop with synchronous CPU work (JSON.stringify on large data) |

---

**Tip for interviews:** Five things separate strong candidates on request lifecycle: (1) knowing that **`req.body` is not populated by Node.js** — it's `undefined` until middleware explicitly reads and parses the stream, and being able to explain why this is the source of a specific class of bugs when middleware order is wrong; (2) understanding the **event loop phase where I/O fires** — that requests are processed in libuv's poll phase, and that any synchronous code in a handler blocks all concurrent requests, not just the current one; (3) being able to explain the **exact behavior of `next(err)` vs `next()`** — that passing a truthy value to `next` skips all regular middleware and routes to the first 4-argument handler, and that Express 4 does NOT automatically catch async rejections (this changed in Express 5); (4) knowing that **TLS termination is usually offloaded** — in production the Node.js process typically receives plain HTTP from nginx or an ALB, not HTTPS directly, and that the TLS diagram is real but often applies to the proxy layer, not Node.js itself; and (5) being able to articulate **why connection pooling is critical at scale** — that without it, each request's DB latency includes TCP + auth overhead, and that pool exhaustion is the most common cause of the "works fine at 100 req/s, falls apart at 1000 req/s" pattern.
