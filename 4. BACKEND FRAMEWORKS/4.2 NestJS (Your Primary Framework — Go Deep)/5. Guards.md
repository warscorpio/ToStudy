# Guards: `CanActivate`, JWT Guard, Role-Based Guard — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a guard in NestJS, and how does it differ from middleware and interceptors?**
A: A guard is a class that implements `CanActivate` and makes a single boolean decision: should this request be allowed to reach the route handler? Guards are the authorisation layer — they run after middleware but before interceptors and pipes, and they have access to the `ExecutionContext` which exposes the full NestJS metadata system.

```
Request lifecycle — where each concern lives:

  Incoming request
       │
       ▼
  ┌─────────────┐
  │  Middleware  │  ← app.use() — no ExecutionContext, no metadata access
  │             │     Use for: request ID, CORS, body parsing, logging
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │   Guards    │  ← CanActivate — knows the handler, class, and custom metadata
  │             │     Use for: authentication, authorisation, feature flags
  └──────┬──────┘
         │  (throws ForbiddenException / UnauthorizedException if false)
         ▼
  ┌─────────────┐
  │  Interceptors│  ← pre/post handler wrapping (logging, caching, transform)
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │    Pipes    │  ← validation and transformation of route arguments
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │   Handler   │  ← your @Get() / @Post() method
  └─────────────┘
```

```typescript
// The three layers compared side by side:

// Middleware — no NestJS context
app.use((req, res, next) => {
    req.requestId = randomUUID();   // can set things on req
    // Cannot access: route metadata, handler name, controller class
    // Cannot access: @Roles() decorator values, @Public() flags
    next();
});

// Guard — full ExecutionContext
@Injectable()
class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean {
        const handler = context.getHandler();         // ← the @Get() method ref
        const controller = context.getClass();        // ← the @Controller() class ref
        const isPublic = this.reflector.get(IS_PUBLIC_KEY, handler);  // custom metadata
        const req = context.switchToHttp().getRequest();
        return this.validateToken(req.headers.authorization);
    }
}

// Interceptor — wraps handler, runs before AND after
@Injectable()
class TimingInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
        const start = Date.now();
        return next.handle().pipe(
            tap(() => console.log(`Took ${Date.now() - start}ms`))
        );
        // Runs after the guard approves — never runs if guard rejects
    }
}
```

```typescript
// Why guards exist as a separate concept from middleware:

// Middleware runs on a URL pattern — it doesn't know about NestJS routing:
app.use('/api', authMiddleware);  // Runs for ALL /api routes

// A guard can be selective per-handler using metadata:
@Controller('orders')
@UseGuards(AuthGuard)      // ← applies to all routes in controller
class OrderController {
    @Get('public-stats')
    @Public()              // ← metadata flag: this route skips the guard
    getStats() { ... }

    @Get(':id')            // ← guard enforces auth here
    getOrder() { ... }
}
// Middleware cannot achieve this per-handler selectivity without inspecting URLs manually
```

**Q2. What does `CanActivate` look like, and what can it return?**
A: `CanActivate` is a single-method interface. The method can return a synchronous boolean, a `Promise<boolean>`, or an `Observable<boolean>` — NestJS handles all three transparently:

```typescript
import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';
import { Observable } from 'rxjs';

// The interface (from NestJS source):
interface CanActivate {
    canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean>;
}

// Synchronous guard — for fast in-memory checks:
@Injectable()
class ApiKeyGuard implements CanActivate {
    private readonly validKeys = new Set(process.env.API_KEYS?.split(','));

    canActivate(context: ExecutionContext): boolean {
        const req = context.switchToHttp().getRequest<Request>();
        const key = req.headers['x-api-key'] as string;
        return this.validKeys.has(key);
        // Returning false → NestJS throws ForbiddenException automatically
    }
}

// Async guard — for database lookups, remote verification:
@Injectable()
class JwtGuard implements CanActivate {
    async canActivate(context: ExecutionContext): Promise<boolean> {
        const req = context.switchToHttp().getRequest();
        const token = this.extractToken(req);
        if (!token) return false;

        try {
            const payload = await this.jwtService.verifyAsync(token);
            req.user = payload;   // Attach to request for downstream use
            return true;
        } catch {
            return false;         // Expired, malformed, or invalid signature
        }
    }
}

// Observable guard — for reactive streams (rare, useful with Redis pub/sub):
@Injectable()
class FeatureFlagGuard implements CanActivate {
    canActivate(context: ExecutionContext): Observable<boolean> {
        return this.featureFlags.isEnabled('new-checkout').pipe(
            map(enabled => enabled),
            catchError(() => of(false))  // Fail closed on flag service error
        );
    }
}

// What NestJS does when canActivate returns false (and doesn't throw):
// → Throws ForbiddenException (403) automatically
// You can throw explicitly for more control over the status code:
@Injectable()
class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean {
        const isAuthed = this.checkAuth(context);
        if (!isAuthed) {
            throw new UnauthorizedException('Authentication required');
            // 401 instead of NestJS's default 403
        }
        return true;
    }
}
```

**Q3. What is `ExecutionContext` and what can you learn from it inside a guard?**
A: `ExecutionContext` extends `ArgumentsHost` and provides access to the raw arguments of the current request, plus NestJS-specific metadata about the handler being invoked:

```typescript
interface ExecutionContext extends ArgumentsHost {
    getClass<T = any>(): Type<T>;        // The controller class constructor
    getHandler(): Function;              // The route handler method
}

interface ArgumentsHost {
    getArgs<T extends Array<any> = any[]>(): T;
    getArgByIndex<T = any>(index: number): T;
    switchToRpc(): RpcArgumentsHost;
    switchToHttp(): HttpArgumentsHost;
    switchToWs(): WsArgumentsHost;
    getType<TContext extends string = ContextType>(): TContext;
}

// What you can extract in a guard:
@Injectable()
class DiagnosticGuard implements CanActivate {
    constructor(private reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        // 1. The controller class:
        const controllerClass = context.getClass();
        console.log(controllerClass.name);  // 'OrderController'

        // 2. The handler method:
        const handler = context.getHandler();
        console.log(handler.name);  // 'createOrder'

        // 3. Custom metadata set by decorators:
        const roles = this.reflector.get<string[]>('roles', handler);
        // ['admin', 'manager'] if handler has @Roles('admin', 'manager')

        // 4. Metadata at class OR handler level (checks both):
        const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
            handler,           // handler-level metadata checked first
            controllerClass    // falls back to class-level
        ]);

        // 5. The raw HTTP request (Express or Fastify):
        const http = context.switchToHttp();
        const req = http.getRequest<express.Request>();
        const res = http.getResponse<express.Response>();

        // 6. The context type — 'http', 'rpc', 'ws':
        const contextType = context.getType();
        if (contextType === 'http') {
            // HTTP-specific logic
        } else if (contextType === 'rpc') {
            // gRPC microservice — req is a different shape
            const rpcData = context.switchToRpc().getData();
        }

        return true;
    }
}
```

```typescript
// Reflector — the key to reading custom metadata:

// Step 1: Define a metadata key constant
export const ROLES_KEY = 'roles';
export const IS_PUBLIC_KEY = 'isPublic';

// Step 2: Create decorator factories that attach metadata
export const Roles = (...roles: string[]) =>
    SetMetadata(ROLES_KEY, roles);
// SetMetadata is NestJS's built-in: Reflect.defineMetadata(key, value, target)

export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);

// Step 3: Read metadata in a guard via Reflector
@Injectable()
class RoleGuard implements CanActivate {
    constructor(private reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        // reflector.get(key, target) — reads from ONE target:
        const handlerRoles = this.reflector.get<string[]>(ROLES_KEY, context.getHandler());

        // reflector.getAllAndOverride(key, targets) — checks targets in order,
        // returns first defined value (handler overrides controller):
        const roles = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
            context.getHandler(),
            context.getClass()
        ]);

        // reflector.getAllAndMerge(key, targets) — merges arrays from all targets:
        const mergedRoles = this.reflector.getAllAndMerge<string[]>(ROLES_KEY, [
            context.getHandler(),
            context.getClass()
        ]);
        // Controller: @Roles('user'), Handler: @Roles('admin')
        // getAllAndMerge → ['user', 'admin']
        // getAllAndOverride → ['admin'] (handler wins)
    }
}
```

## Section 2: JWT Guard

**Q4. How do you implement a production-grade JWT authentication guard?**
A: A complete JWT guard verifies the token signature and expiry, extracts the payload, handles edge cases (missing header, wrong format, revoked tokens), and attaches the decoded user to the request for downstream use:

```typescript
// auth/guards/jwt-auth.guard.ts
import {
    CanActivate, ExecutionContext, Injectable,
    UnauthorizedException, Logger
} from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import { Reflector } from '@nestjs/core';
import { Request } from 'express';
import { IS_PUBLIC_KEY } from '../decorators/public.decorator';
import { TokenBlocklistService } from '../services/token-blocklist.service';

export interface JwtPayload {
    sub: string;        // Subject — the user's ID (standard JWT claim)
    email: string;
    roles: string[];
    tenantId?: string;
    iat: number;        // Issued at (Unix timestamp)
    exp: number;        // Expiry (Unix timestamp)
    jti: string;        // JWT ID — unique per token, used for revocation
}

@Injectable()
export class JwtAuthGuard implements CanActivate {
    private readonly logger = new Logger(JwtAuthGuard.name);

    constructor(
        private jwtService: JwtService,
        private reflector: Reflector,
        private blocklist: TokenBlocklistService,
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        // 1. Check if route is marked @Public() — skip auth entirely
        const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
            context.getHandler(),
            context.getClass(),
        ]);
        if (isPublic) return true;

        const request = context.switchToHttp().getRequest<Request>();

        // 2. Extract the token from the Authorization header
        const token = this.extractBearerToken(request);
        if (!token) {
            throw new UnauthorizedException('No authentication token provided');
        }

        // 3. Verify signature, algorithm, issuer, audience, and expiry
        let payload: JwtPayload;
        try {
            payload = await this.jwtService.verifyAsync<JwtPayload>(token, {
                algorithms: ['HS256'],          // Allowlist — NEVER omit this
                issuer: 'acme-auth-service',    // Reject tokens from other issuers
                audience: 'acme-api',           // Reject tokens meant for other services
            });
        } catch (err) {
            // Distinguish error types for useful logging (not exposed to client):
            if (err.name === 'TokenExpiredError') {
                this.logger.debug('Expired token presented');
                throw new UnauthorizedException('Token has expired');
            }
            if (err.name === 'JsonWebTokenError') {
                this.logger.warn('Malformed token', { error: err.message });
                throw new UnauthorizedException('Invalid token');
            }
            throw new UnauthorizedException('Authentication failed');
        }

        // 4. Check token revocation blocklist (for logout / security incidents)
        const isRevoked = await this.blocklist.has(payload.jti);
        if (isRevoked) {
            this.logger.warn('Revoked token presented', { jti: payload.jti, sub: payload.sub });
            throw new UnauthorizedException('Token has been revoked');
        }

        // 5. Attach decoded payload to request — available in handlers via @User()
        request['user'] = payload;

        return true;
    }

    private extractBearerToken(request: Request): string | null {
        const authorization = request.headers.authorization;
        if (!authorization) return null;

        const [scheme, token] = authorization.split(' ');
        if (scheme?.toLowerCase() !== 'bearer' || !token) return null;

        return token;
    }
}
```

```typescript
import { createParamDecorator, ExecutionContext } from '@nestjs/common';

export const CurrentUser = createParamDecorator(
    (data: keyof JwtPayload | undefined, ctx: ExecutionContext): JwtPayload | unknown => {
        const request = ctx.switchToHttp().getRequest();
        const user = request.user as JwtPayload;

        // @CurrentUser() → full payload
        // @CurrentUser('sub') → just the userId string
    }

// auth/services/token-blocklist.service.ts
@Injectable()
export class TokenBlocklistService {
    constructor(
        @Inject(REDIS_CLIENT) private redis: Redis
    ) {}

    async revoke(jti: string, expiresInSeconds: number): Promise<void> {
        // Store revoked token until its natural expiry — no need to keep beyond that
        await this.redis.setex(`blocklist:${jti}`, expiresInSeconds, '1');
    }

    async has(jti: string): Promise<boolean> {
        const result = await this.redis.exists(`blocklist:${jti}`);
        return result === 1;
    }
}
```

**Q5. What are the security considerations for JWT verification — what can go wrong?**
A: JWT vulnerabilities are almost always in the verification step, not the token format itself. Each parameter to `verifyAsync` closes a specific attack vector:

```typescript
// The insecure version — common in tutorials, dangerous in production:
const payload = jwt.verify(token, secret);
// Missing: algorithm check, issuer check, audience check

// Attack 1: Algorithm confusion — "alg: none" attack
// An attacker modifies the JWT header to { "alg": "none" }
// A library that accepts "none" will skip signature verification entirely
// The payload claims are trusted without any cryptographic check

// Mitigation: ALWAYS provide an algorithms allowlist:
jwt.verify(token, secret, { algorithms: ['HS256'] });
//                          ↑ 'none' would throw — not in the allowlist

// Attack 2: RS256 → HS256 confusion (asymmetric key confusion)
// System issues RS256 tokens (private key signs, public key verifies)
// Attacker gets the public key (it's public), signs a token with HS256
// using the public key as the HMAC secret
// A library that auto-detects algorithm trusts this token!

// Mitigation: same fix — explicit algorithms: ['RS256'] rejects HS256 tokens
const publicKey = fs.readFileSync('./public.pem');
jwt.verify(token, publicKey, { algorithms: ['RS256'] });

// Attack 3: Token from a different service accepted
// auth-service issues tokens with issuer 'acme-auth'
// internal-tools also issues JWT tokens (maybe with weaker secrets)
// Without issuer check, internal-tools tokens work on the API

// Mitigation: verify issuer and audience:
jwt.verify(token, secret, {
    algorithms: ['HS256'],
    issuer: 'acme-auth-service',   // Only accept our tokens
    audience: 'acme-api',          // Only accept tokens meant for this service
});

// Attack 4: JWT secret in client-side code / weak secret
// HS256 with a short secret is brute-forceable
// Common mistake: secret = 'secret' or process.env.JWT_SECRET = 'changeme'

// Mitigation:
// - Use cryptographically random secrets: crypto.randomBytes(64).toString('hex')
// - Or switch to RS256/ES256 — private key never leaves the auth service
// - Minimum secret length for HS256: 256 bits (32 bytes)
// - Rotate secrets periodically with a transition window

// Attack 5: Missing expiry check / long-lived tokens
// A stolen token is valid forever if exp is not checked or is set years ahead

// Mitigation: short-lived access tokens + refresh token rotation
{
    expiresIn: '15m',     // Access token: 15 minutes
    // Refresh token: 7 days (longer, but single-use and stored server-side)
}
// jwtService.verifyAsync() checks exp automatically — do NOT disable this
```

```typescript
// Correct RS256 setup (production preference — private key stays server-side):
// auth service (SIGNS tokens):
const privateKey = fs.readFileSync('./keys/private.pem');
const token = jwt.sign(payload, privateKey, {
    algorithm: 'RS256',
    issuer: 'acme-auth-service',
    audience: 'acme-api',
    expiresIn: '15m',
    jwtid: randomUUID()      // jti — unique per token for revocation
});

// api service (VERIFIES tokens — never has the private key):
const publicKey = fs.readFileSync('./keys/public.pem');
jwt.verify(token, publicKey, {
    algorithms: ['RS256'],   // ← NOT 'HS256' — prevents key confusion attack
    issuer: 'acme-auth-service',
    audience: 'acme-api',
});
// Public key can be distributed freely — it can only verify, not sign
// Auth service can publish its JWKS (JSON Web Key Set) endpoint:
// GET https://auth.acme.com/.well-known/jwks.json
// API fetches public keys dynamically and caches them
```

## Section 3: Role-Based Guard

**Q6. How do you implement role-based access control (RBAC) as a guard?**
A: RBAC grants access based on what roles a user holds. The guard reads required roles from route metadata and compares against roles in the JWT payload:

```typescript
// auth/decorators/roles.decorator.ts
import { SetMetadata } from '@nestjs/common';

export enum Role {
    User    = 'user',
    Manager = 'manager',
    Admin   = 'admin',
}

export const ROLES_KEY = 'roles';
export const Roles = (...roles: Role[]) => SetMetadata(ROLES_KEY, roles);

// auth/guards/roles.guard.ts
import { CanActivate, ExecutionContext, Injectable, ForbiddenException } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { Role, ROLES_KEY } from '../decorators/roles.decorator';
import { JwtPayload } from './jwt-auth.guard';

@Injectable()
export class RolesGuard implements CanActivate {
    constructor(private reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        // 1. Read required roles from metadata
        // getAllAndOverride: handler-level metadata takes precedence over class-level
        const requiredRoles = this.reflector.getAllAndOverride<Role[]>(ROLES_KEY, [
            context.getHandler(),
            context.getClass(),
        ]);

        // 2. No @Roles() decorator — route is accessible to any authenticated user
        if (!requiredRoles || requiredRoles.length === 0) return true;

        // 3. Get the user attached by JwtAuthGuard (runs before RolesGuard)
        const request = context.switchToHttp().getRequest();
        const user = request.user as JwtPayload;

        // 4. User must exist (JwtAuthGuard should have ensured this, but be defensive)
        if (!user) {
            throw new ForbiddenException('User context not found');
        }

        // 5. Check if user holds at least one of the required roles
        const hasRole = requiredRoles.some(role => user.roles?.includes(role));

        if (!hasRole) {
            throw new ForbiddenException(
                `Access denied: requires one of [${requiredRoles.join(', ')}], ` +
                `user has [${user.roles?.join(', ') ?? 'none'}]`
            );
        }

        return true;
    }
}
```

```typescript
// Registration — JWT guard runs first (authn), then roles guard (authz):
@Module({
    providers: [
        {
            provide: APP_GUARD,
            useClass: JwtAuthGuard,    // 1st: authenticate
        },
        {
            provide: APP_GUARD,
            useClass: RolesGuard,      // 2nd: authorise
        },
    ]
})
export class AppModule {}

// Usage in controllers:
@Controller('users')
export class UserController {
    @Get()
    @Roles(Role.Admin)                     // Only admins can list all users
    findAll(): Promise<User[]> { ... }

    @Get(':id')                            // Any authenticated user — no @Roles()
    findOne(@Param('id') id: string) { ... }

    @Patch(':id')
    @Roles(Role.Admin, Role.Manager)       // Admin OR manager can update
    update(@Param('id') id: string, @Body() dto: UpdateUserDto) { ... }

    @Delete(':id')
    @Roles(Role.Admin)                     // Only admins can delete
    remove(@Param('id') id: string) { ... }
}

// Class-level roles (all routes in controller require admin):
@Controller('admin')
@Roles(Role.Admin)                         // Applies to ALL routes below
export class AdminController {
    @Get('stats')                          // Requires admin (inherited)
    getStats() { ... }

    @Get('config')                         // Requires admin (inherited)
    getConfig() { ... }
}
```

**Q7. How do you implement hierarchical roles where admin implicitly has all user permissions?**
A: Flat `includes()` checks require every role to be listed explicitly. A hierarchy model lets admins inherit lower roles:

```typescript
// Define role hierarchy — each role inherits those below it:
export enum Role {
    Guest   = 'guest',
    User    = 'user',
    Manager = 'manager',
    Admin   = 'admin',
}

// Role hierarchy: higher index = more permissions
const ROLE_HIERARCHY: Record<Role, number> = {
    [Role.Guest]:   0,
    [Role.User]:    1,
    [Role.Manager]: 2,
    [Role.Admin]:   3,
};

@Injectable()
export class HierarchicalRolesGuard implements CanActivate {
    constructor(private reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        const requiredRoles = this.reflector.getAllAndOverride<Role[]>(ROLES_KEY, [
            context.getHandler(),
            context.getClass(),
        ]);
        if (!requiredRoles?.length) return true;

        const { user } = context.switchToHttp().getRequest<{ user: JwtPayload }>();
        if (!user) throw new ForbiddenException();

        // Find the user's highest-ranking role:
        const userMaxLevel = Math.max(
            ...user.roles.map(r => ROLE_HIERARCHY[r as Role] ?? -1)
        );

        // Find the minimum required level (any role in @Roles() suffices):
        const requiredMinLevel = Math.min(
            ...requiredRoles.map(r => ROLE_HIERARCHY[r])
        );

        // User's highest role must meet the minimum required:
        const hasAccess = userMaxLevel >= requiredMinLevel;

        if (!hasAccess) {
            throw new ForbiddenException(
                `Requires at least '${requiredRoles[0]}' role`
            );
        }

        return true;
    }
}

// With hierarchy:
// @Roles(Role.User) → admin (level 3) ≥ user (level 1) → ACCESS GRANTED
// @Roles(Role.Manager) → user (level 1) ≥ manager (level 2) → DENIED
// @Roles(Role.Admin) → manager (level 2) ≥ admin (level 3) → DENIED
```

**Q8. How do you implement attribute-based access control (ABAC) — going beyond flat roles?**
A: ABAC grants access based on attributes of the user, the resource, and the environment — not just role membership. This enables rules like "user can only edit their own orders":

```typescript
// Policy-based ABAC — define policies as injectable services:
export interface PolicyHandler {
    handle(user: JwtPayload, resource?: unknown): boolean | Promise<boolean>;
}

// A policy: users can only read their own orders, admins can read any:
@Injectable()
export class ReadOrderPolicy implements PolicyHandler {
    async handle(user: JwtPayload, order: Order): Promise<boolean> {
        if (user.roles.includes(Role.Admin)) return true;
        return order.userId === user.sub;     // Owner check
    }
}

// A policy: only admins can delete, and not within 24h of creation:
@Injectable()
export class DeleteOrderPolicy implements PolicyHandler {
    async handle(user: JwtPayload, order: Order): Promise<boolean> {
        if (!user.roles.includes(Role.Admin)) return false;
        const ageHours = (Date.now() - order.createdAt.getTime()) / 3_600_000;
        return ageHours > 24;    // Can only delete orders older than 24h
    }
}
```

```typescript
// Policy decorator and guard:
export const CHECK_POLICIES_KEY = 'check_policies';
export const CheckPolicies = (...handlers: PolicyHandler[]) =>
    SetMetadata(CHECK_POLICIES_KEY, handlers);

@Injectable()
export class PoliciesGuard implements CanActivate {
    constructor(
        private reflector: Reflector,
        private orderService: OrderService,  // Needs to fetch the resource
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        const policyHandlers = this.reflector.get<PolicyHandler[]>(
            CHECK_POLICIES_KEY,
            context.getHandler(),
        );
        if (!policyHandlers?.length) return true;

        const request = context.switchToHttp().getRequest();
        const user = request.user as JwtPayload;

        // Fetch the resource the policy needs to evaluate:
        // (the guard knows the route params from the request)
        const orderId = request.params.id;
        const order = orderId ? await this.orderService.findById(orderId) : null;

        // All policies must pass:
        const results = await Promise.all(
            policyHandlers.map(handler => handler.handle(user, order))
        );
        return results.every(Boolean);
    }
}

// Usage:
@Controller('orders')
export class OrderController {
    @Get(':id')
    @CheckPolicies(new ReadOrderPolicy())          // Inline policy instance
    async getOrder(@Param('id') id: string) { ... }

    @Delete(':id')
    @CheckPolicies(new DeleteOrderPolicy())
    async deleteOrder(@Param('id') id: string) { ... }
}
```

## Section 4: Composing Guards

**Q9. How do you compose multiple guards, and what is their execution order?**
A: Guards applied with `@UseGuards()` run in the order they are listed. The first to return `false` or throw short-circuits execution — subsequent guards never run:

```typescript
// Execution order with @UseGuards():
@Controller('orders')
@UseGuards(JwtAuthGuard, TenantGuard)    // Class-level: JwtAuthGuard runs first
export class OrderController {

    @Get(':id')
    @UseGuards(RolesGuard)               // Method-level: runs AFTER class-level guards
    async getOrder() { ... }

    // Effective order for GET /orders/:id:
    // 1. JwtAuthGuard  (class-level, first)
    // 2. TenantGuard   (class-level, second)
    // 3. RolesGuard    (method-level)
    // If any throws or returns false, subsequent guards don't run
}

// Global guards (via APP_GUARD) run BEFORE class and method guards:
// Effective full order:
// 1. GlobalGuard (APP_GUARD — registered in AppModule)
// 2. JwtAuthGuard (class-level)
// 3. TenantGuard  (class-level)
// 4. RolesGuard   (method-level)
```

```typescript
// Building a composite guard — combines multiple checks into one class:
@Injectable()
export class AuthAndRoleGuard implements CanActivate {
    constructor(
        private jwtGuard: JwtAuthGuard,
        private rolesGuard: RolesGuard,
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        // Run in sequence — explicit ordering and error handling
        const isAuthed = await this.jwtGuard.canActivate(context);
        if (!isAuthed) return false;

        const hasRole = await this.rolesGuard.canActivate(context);
        return hasRole;
    }
}

// Or combine with explicit error handling between steps:
@Injectable()
export class SecureGuard implements CanActivate {
    constructor(
        private jwt: JwtAuthGuard,
        private roles: RolesGuard,
        private rateLimit: RateLimitGuard,
        private logger: Logger,
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        // 1. Rate limiting first — fail fast, cheapest check
        if (!await this.rateLimit.canActivate(context)) {
            throw new HttpException('Too many requests', 429);
        }

        // 2. Auth — verify identity
        if (!await this.jwt.canActivate(context)) {
            throw new UnauthorizedException();
        }

        // 3. Roles — verify permissions
        if (!await this.roles.canActivate(context)) {
            throw new ForbiddenException();
        }

        return true;
    }
}
```

**Q10. How do guards work in non-HTTP contexts — WebSockets and microservices?**
A: Guards implement `CanActivate` once and work across all NestJS transports. The `ExecutionContext` exposes different argument shapes per transport:

```typescript
// WebSocket guard — context.switchToWs() instead of switchToHttp():
@Injectable()
export class WsAuthGuard implements CanActivate {
    constructor(private jwtService: JwtService) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        // Guards on @SubscribeMessage() use WS context
        const client: Socket = context.switchToWs().getClient();
        const data = context.switchToWs().getData();

        // For WS, the token usually comes in the handshake:
        const token = client.handshake.auth?.token
            ?? client.handshake.headers?.authorization?.split(' ')[1];

        if (!token) {
            client.disconnect();   // Disconnect unauthorized WebSocket client
            return false;
        }

        try {
            const payload = await this.jwtService.verifyAsync(token);
            client.data.user = payload;   // Attach to socket data for handler access
            return true;
        } catch {
            client.disconnect();
            return false;
        }
    }
}

// WebSocket controller with guard:
@WebSocketGateway()
@UseGuards(WsAuthGuard)                  // Applies to all @SubscribeMessage handlers
export class OrdersGateway {
    @SubscribeMessage('subscribeToOrder')
    handleSubscription(
        @ConnectedSocket() client: Socket,
        @MessageBody() data: { orderId: string }
    ) {
        const user = client.data.user;   // Set by WsAuthGuard
        // ...
    }
}
```

```typescript
// Microservice / gRPC guard — context.switchToRpc():
@Injectable()
export class MicroserviceAuthGuard implements CanActivate {
    async canActivate(context: ExecutionContext): Promise<boolean> {
        // Detect context type — same guard can handle multiple transports:
        if (context.getType() === 'rpc') {
            const rpcContext = context.switchToRpc();
            const metadata = rpcContext.getContext<Metadata>();   // gRPC Metadata
            const data = rpcContext.getData();

            const token = metadata.get('authorization')[0] as string;
            // Verify token same as HTTP guard...
            return this.verifyToken(token?.replace('Bearer ', ''));
        }

        if (context.getType() === 'http') {
            const req = context.switchToHttp().getRequest();
            return this.verifyToken(req.headers.authorization?.split(' ')[1]);
        }

        return false;
    }

    private async verifyToken(token: string): Promise<boolean> {
        // Shared verification logic regardless of transport
        try {
            await this.jwtService.verifyAsync(token);
            return true;
        } catch {
            return false;
        }
    }
}
```

## Section 5: Advanced Patterns

**Q11. How do you implement rate limiting as a guard?**
A: Rate limiting as a guard gives you per-route control and access to the full `ExecutionContext`, including route metadata for different limits per endpoint:

```typescript
// auth/decorators/rate-limit.decorator.ts
export interface RateLimitOptions {
    limit: number;        // Max requests
    windowMs: number;     // Time window in milliseconds
    keyPrefix?: string;   // Namespace in Redis
}

export const RATE_LIMIT_KEY = 'rateLimit';
export const RateLimit = (options: RateLimitOptions) =>
    SetMetadata(RATE_LIMIT_KEY, options);

// auth/guards/rate-limit.guard.ts
@Injectable()
export class RateLimitGuard implements CanActivate {
    constructor(
        private reflector: Reflector,
        @Inject(REDIS_CLIENT) private redis: Redis,
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        // Read per-route config, fall back to global default:
        const options = this.reflector.getAllAndOverride<RateLimitOptions>(
            RATE_LIMIT_KEY,
            [context.getHandler(), context.getClass()]
        ) ?? { limit: 100, windowMs: 60_000 };   // Default: 100/min

        const request = context.switchToHttp().getRequest<Request>();
        const response = context.switchToHttp().getResponse<Response>();

        // Key = IP + route for unauthenticated, userId + route for authenticated:
        const user = request['user'] as JwtPayload | undefined;
        const identifier = user?.sub ?? this.getClientIp(request);
        const route = `${request.method}:${request.route?.path ?? request.path}`;
        const key = `ratelimit:${options.keyPrefix ?? ''}:${identifier}:${route}`;

        // Sliding window counter using Redis:
        const now = Date.now();
        const windowStart = now - options.windowMs;

        const pipeline = this.redis.pipeline();
        pipeline.zremrangebyscore(key, '-inf', windowStart);   // Remove old entries
        pipeline.zadd(key, now, `${now}-${Math.random()}`);    // Add current request
        pipeline.zcard(key);                                     // Count in window
        pipeline.pexpire(key, options.windowMs);                // Auto-expire key

        const results = await pipeline.exec();
        const count = results?.[2]?.[1] as number ?? 0;

        // Set rate limit headers (RFC 6585):
        response.setHeader('X-RateLimit-Limit', options.limit);
        response.setHeader('X-RateLimit-Remaining', Math.max(0, options.limit - count));
        response.setHeader('X-RateLimit-Reset', Math.ceil((now + options.windowMs) / 1000));

        if (count > options.limit) {
            response.setHeader('Retry-After', Math.ceil(options.windowMs / 1000));
            throw new HttpException('Too Many Requests', 429);
        }

        return true;
    }

    private getClientIp(request: Request): string {
        // Trust X-Forwarded-For only if behind a known proxy:
        const forwarded = request.headers['x-forwarded-for'];
        if (forwarded) {
            return (Array.isArray(forwarded) ? forwarded[0] : forwarded.split(',')[0]).trim();
        }
        return request.ip ?? 'unknown';
    }
}

// Per-route rate limits:
@Controller('auth')
export class AuthController {
    @Post('login')
    @Public()
    @RateLimit({ limit: 5, windowMs: 60_000, keyPrefix: 'login' })   // 5/min — brute force protection
    async login(@Body() dto: LoginDto) { ... }

    @Post('register')
    @Public()
    @RateLimit({ limit: 3, windowMs: 3_600_000, keyPrefix: 'register' })  // 3/hour
    async register(@Body() dto: RegisterDto) { ... }
}

@Controller('api')
@RateLimit({ limit: 1000, windowMs: 60_000 })   // 1000/min for API routes
export class ApiController { ... }
```

**Q12. How do you write a tenant isolation guard in a multi-tenant system?**
A: Multi-tenant guards enforce that a user only accesses data within their own tenant — a hard boundary that must exist at the guard layer, not scattered through service logic:

```typescript
// auth/guards/tenant.guard.ts
@Injectable()
export class TenantGuard implements CanActivate {
    constructor(
        private reflector: Reflector,
        private tenantService: TenantService,
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        // Skip for routes marked as cross-tenant (super-admin only):
        const isCrossTenant = this.reflector.getAllAndOverride<boolean>(
            'crossTenant',
            [context.getHandler(), context.getClass()]
        );
        if (isCrossTenant) return true;

        const request = context.switchToHttp().getRequest<Request>();
        const user = request['user'] as JwtPayload;

        // Tenant ID can come from: subdomain, header, URL param, or JWT claim
        const tenantId = this.extractTenantId(request, user);

        if (!tenantId) {
            throw new ForbiddenException('Tenant context required');
        }

        // Verify the tenant exists and is active:
        const tenant = await this.tenantService.findById(tenantId);
        if (!tenant) {
            throw new ForbiddenException('Tenant not found');
        }
        if (tenant.status !== 'active') {
            throw new ForbiddenException(`Tenant account is ${tenant.status}`);
        }

        // Verify the user belongs to this tenant:
        if (user.tenantId !== tenantId) {
            // Log this — it may indicate a misconfigured client or an attack:
            this.logger.warn('Cross-tenant access attempt', {
                userTenant: user.tenantId,
                requestedTenant: tenantId,
                userId: user.sub,
                path: request.path,
            });
            throw new ForbiddenException('Access denied for this tenant');
        }

        // Attach tenant to request for downstream use:
        request['tenant'] = tenant;

        // Set DB schema or RLS context (Row-Level Security):
        // This runs in the same async context — services can read it via ALS
        TenantContext.set({ tenantId, dbSchema: `tenant_${tenantId}` });

        return true;
    }

    private extractTenantId(request: Request, user: JwtPayload): string | null {
        // Priority: JWT claim → header → subdomain
        if (user?.tenantId) return user.tenantId;

        const headerTenant = request.headers['x-tenant-id'] as string;
        if (headerTenant) return headerTenant;

        // Subdomain: acme-corp.api.example.com → 'acme-corp'
        const host = request.hostname;
        const subdomain = host.split('.')[0];
        if (subdomain && subdomain !== 'api' && subdomain !== 'www') {
            return subdomain;
        }

        return null;
    }
}

// Decorator for cross-tenant admin routes:
export const CrossTenant = () => SetMetadata('crossTenant', true);

// Super-admin controller that can access any tenant's data:
@Controller('admin/tenants')
@UseGuards(JwtAuthGuard, RolesGuard, TenantGuard)
@Roles(Role.SuperAdmin)
export class TenantAdminController {
    @Get(':tenantId/users')
    @CrossTenant()           // Bypasses tenant isolation for super-admin
    async getTenantUsers(@Param('tenantId') tenantId: string) { ... }
}
```

## Section 6: Testing Guards

**Q13. How do you unit test a guard without spinning up a NestJS application?**
A: Guards are classes with a single method — test them directly without `Test.createTestingModule()`. The only trick is mocking `ExecutionContext`, which is an interface you must implement:

```typescript
// Helper: build a mock ExecutionContext
function buildMockContext(overrides: {
    user?: Partial<JwtPayload>;
    headers?: Record<string, string>;
    handlerMetadata?: Record<string, unknown>;
    classMetadata?: Record<string, unknown>;
}): ExecutionContext {
    const mockRequest = {
        headers: overrides.headers ?? {},
        user: overrides.user ?? null,
    };

    const mockHandler = () => {};
    const mockClass = class {};

    // Apply metadata to handler/class so Reflector can read it:
    if (overrides.handlerMetadata) {
        Object.entries(overrides.handlerMetadata).forEach(([key, value]) => {
            Reflect.defineMetadata(key, value, mockHandler);
        });
    }
    if (overrides.classMetadata) {
        Object.entries(overrides.classMetadata).forEach(([key, value]) => {
            Reflect.defineMetadata(key, value, mockClass);
        });
    }

    return {
        switchToHttp: () => ({
            getRequest: () => mockRequest,
            getResponse: () => ({ setHeader: jest.fn() }),
            getNext: () => jest.fn(),
        }),
        getHandler: () => mockHandler,
        getClass: () => mockClass,
        getType: () => 'http',
        getArgs: () => [],
        getArgByIndex: () => null,
        switchToRpc: () => ({ getData: () => null, getContext: () => null }),
        switchToWs: () => ({ getData: () => null, getClient: () => null }),
    } as unknown as ExecutionContext;
}
```

## Section 7: Common Pitfalls

**Q14. What are the most common guard implementation mistakes and how do you avoid them?**
A:

```typescript
// PITFALL 1: Throwing the wrong exception type
// NestJS automatically throws ForbiddenException (403) when canActivate returns false
// But the semantics differ: unauthenticated = 401, unauthorised = 403

// WRONG:
canActivate(context: ExecutionContext): boolean {
    const token = this.extractToken(context);
    if (!token) return false;   // Returns false → NestJS throws 403 — wrong!
}

// CORRECT: throw explicitly with the right status:
canActivate(context: ExecutionContext): boolean | never {
    const token = this.extractToken(context);
    if (!token) throw new UnauthorizedException('Token required');   // 401
    const isAuthed = this.verify(token);
    if (!isAuthed) throw new UnauthorizedException('Invalid token'); // 401
    const hasRole = this.checkRole(context);
    if (!hasRole) throw new ForbiddenException('Insufficient permissions'); // 403
    return true;
}
```

```typescript
// PITFALL 2: Guard order — roles guard runs before JWT guard populates req.user
// BAD: Roles guard reads req.user but JWT guard hasn't set it yet
@Module({
    providers: [
        { provide: APP_GUARD, useClass: RolesGuard },   // Runs first — req.user is undefined!
        { provide: APP_GUARD, useClass: JwtAuthGuard }, // Runs second — too late
    ]
})

// CORRECT: JWT guard always before roles guard:
@Module({
    providers: [
        { provide: APP_GUARD, useClass: JwtAuthGuard },  // 1st: sets req.user
        { provide: APP_GUARD, useClass: RolesGuard },    // 2nd: reads req.user
    ]
})

// Also valid: @UseGuards(JwtAuthGuard, RolesGuard) at route level
// The array order determines execution order
```

```typescript
// PITFALL 3: Forgetting that global guards also apply to health checks / metrics
```

```typescript
async findById(id: string, requestingUserId: string): Promise<Order> {

}

// Fix 2: Scope queries by user at the DB level (defence in depth):
async findByIdForUser(id: string, userId: string): Promise<Order | null> {
    // WHERE id = $1 AND user_id = $2 — impossible to return another user's order
    return this.db.query(
        'SELECT * FROM orders WHERE id = $1 AND user_id = $2',
        [id, userId]
    );
    // Returns null if order exists but belongs to different user
    // Indistinguishable from "order not found" — prevents enumeration
}

@Get(':id')
@CheckPolicies(
    (user: JwtPayload, order: Order) =>
        user.roles.includes(Role.Admin) || order.userId === user.sub

// Guard fetches the order, evaluates the policy — authorisation and resource fetch in one step
```

**Q16. "Design a guard system for a SaaS API where routes need: authentication, tenant isolation, feature-flag gating, and role checks — without repeating logic everywhere."**
A: The solution is a single composable guard hierarchy with decorator-driven configuration:

```typescript
// One composite guard that handles all four concerns in the right order:
@Injectable()
export class SaasGuard implements CanActivate {
    constructor(
        private reflector: Reflector,
        private jwtService: JwtService,
        private tenantService: TenantService,
        private featureFlagService: FeatureFlagService,
        private blocklist: TokenBlocklistService,
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        const handler = context.getHandler();
        const controller = context.getClass();
        const targets = [handler, controller];

        // STEP 1: Skip everything for @Public() routes
        const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, targets);
        if (isPublic) return true;

        const request = context.switchToHttp().getRequest<Request>();

        // STEP 2: Authentication — verify JWT
        const token = this.extractBearerToken(request);
        if (!token) throw new UnauthorizedException('Token required');

        let user: JwtPayload;
        try {
            user = await this.jwtService.verifyAsync(token, {
                algorithms: ['HS256'],
                issuer: 'acme-auth',
                audience: 'acme-api'
            });
        } catch (err) {
            throw new UnauthorizedException(
                err.name === 'TokenExpiredError' ? 'Token expired' : 'Invalid token'
            );
        }

        if (await this.blocklist.has(user.jti)) {
            throw new UnauthorizedException('Token revoked');
        }

        request['user'] = user;

        // STEP 3: Tenant isolation
        const skipTenant = this.reflector.getAllAndOverride<boolean>('crossTenant', targets);
        if (!skipTenant) {
            const tenant = await this.tenantService.findById(user.tenantId);
            if (!tenant || tenant.status !== 'active') {
                throw new ForbiddenException('Tenant inactive or not found');
            }
            request['tenant'] = tenant;
        }

        // STEP 4: Feature flag gating
        const requiredFeature = this.reflector.getAllAndOverride<string>('requiresFeature', targets);
        if (requiredFeature) {
            const enabled = await this.featureFlagService.isEnabled(
                requiredFeature,
                user.tenantId
            );
            if (!enabled) throw new ForbiddenException(`Feature '${requiredFeature}' not enabled`);
        }

        // STEP 5: Role check
        const requiredRoles = this.reflector.getAllAndOverride<Role[]>(ROLES_KEY, targets);
        if (requiredRoles?.length) {
            const hasRole = requiredRoles.some(r => user.roles.includes(r));
            if (!hasRole) throw new ForbiddenException('Insufficient permissions');
        }

        return true;
    }

    private extractBearerToken(req: Request): string | null {
        const auth = req.headers.authorization;
        if (!auth?.startsWith('Bearer ')) return null;
        return auth.slice(7);
    }
}

// Register as the single global guard:
@Module({
    providers: [{ provide: APP_GUARD, useClass: SaasGuard }]
})
export class AppModule {}

// All decorator combinations work cleanly:
@Controller('orders')
export class OrderController {
    @Get('public-count')
    @Public()                               // No auth
    count() { ... }

    @Get()
    @Roles(Role.User)                       // Auth + tenant + role
    findAll() { ... }

    @Post('bulk-import')
    @Roles(Role.Manager)
    @SetMetadata('requiresFeature', 'bulk-import')   // Auth + tenant + feature + role
    bulkImport() { ... }

    @Get('cross-tenant-report')
    @Roles(Role.Admin)
    @CrossTenant()                          // Auth + role, no tenant isolation
    adminReport() { ... }
}
```

## Quick Reference Table

| Concept | Key Idea | Common Mistake |
|---|---|---|
| `CanActivate` | Single-method interface; return `boolean`, `Promise<boolean>`, or `Observable<boolean>` | Returning `false` for unauthenticated requests — NestJS throws 403, but 401 is semantically correct; throw `UnauthorizedException` explicitly |
| `ExecutionContext` | Provides `getHandler()`, `getClass()`, and `switchToHttp/Rpc/Ws()` — the gateway to NestJS metadata | Using `req.headers` only — missing metadata means missing `@Public()`, `@Roles()` awareness |
| `Reflector` | Reads metadata set by `SetMetadata` decorators; use `getAllAndOverride` for handler-over-class precedence | Using `reflector.get()` with only the handler — misses class-level `@Roles()` on the controller |
| `APP_GUARD` | Applies a guard globally to every route in the application | Forgetting to mark health checks and metrics endpoints `@Public()` — Kubernetes probes return 401 |
| Guard execution order | Global (APP_GUARD) → class-level `@UseGuards` → method-level `@UseGuards`; within each level, left-to-right | Registering `RolesGuard` before `JwtAuthGuard` — roles guard reads `req.user` before it's set |
| `@Public()` | Custom decorator using `SetMetadata` to opt specific routes out of a global guard | Omitting `getAllAndOverride` in the guard — only checks handler metadata, misses the decorator on the controller class |
| JWT `algorithms` allowlist | `verifyAsync` must specify allowed algorithms to prevent "alg: none" and RS256→HS256 confusion attacks | Omitting `algorithms: ['HS256']` — library auto-detects algorithm, enabling algorithm confusion attacks |
| `jti` + blocklist | Unique token ID stored in Redis until token expiry — enables stateless logout and token revocation | Not including `jti` in token payload — no way to invalidate specific tokens without rotating the secret |
| RBAC vs ABAC | RBAC: role membership check only; ABAC: user attributes + resource attributes + environment | Using only RBAC and missing ownership checks — a user with the `user` role can access any other user's resource |
| Async guard | Return type must be `Promise<boolean>` and the method must be `async` with `await` on async calls | Non-async guard calling `jwtService.verifyAsync()` without `await` — always returns a truthy Promise, never actually verifies |
| Guard vs middleware | Guards have `ExecutionContext` (metadata access, handler reference); middleware operates on URL patterns only | Using middleware for auth and trying to read `@Roles()` metadata — middleware has no access to NestJS decorator metadata |
| Testing guards | Instantiate with `new Guard(...)` and pass a mock `ExecutionContext`; no `Test.createTestingModule()` needed | Standing up the full NestJS test module for guard unit tests — slow and tests more than the guard |

---

**Tip for interviews:** Five things separate strong candidates on NestJS guards: (1) knowing the **precise execution order** — global `APP_GUARD` runs before class-level `@UseGuards`, which runs before method-level, and within each level the array is left-to-right — and being able to explain why `JwtAuthGuard` must always precede `RolesGuard` since the roles guard reads `req.user` that the JWT guard sets; (2) understanding the **`401` vs `403` distinction** — that returning `false` from `canActivate` always produces 403, but unauthenticated requests (no token, invalid signature, expired) should return 401 (`UnauthorizedException`), and that the semantic difference matters for clients implementing retry and redirect logic; (3) knowing the **JWT security checklist**: explicit `algorithms` allowlist prevents the `alg: none` and RS256→HS256 confusion attacks, explicit `issuer` and `audience` validation prevents tokens from other services being accepted, and `jti` with a blocklist enables revocation without secret rotation — candidates who cite these specifically have gone beyond tutorials; (4) explaining the **difference between RBAC and ABAC** with a concrete example — that `@Roles(Role.User)` on `GET /orders/:id` still allows any user to read any other user's order (horizontal privilege escalation), and that the fix requires an ownership attribute check either in the guard policy or the service layer; and (5) being able to design a **single composite guard** that handles auth, tenant isolation, feature flags, and roles in sequence with `@Public()`, `@CrossTenant()`, and `@RequiresFeature()` decorator opt-ins — this demonstrates that they understand guards as a composable policy layer, not just "the thing that checks JWTs."
