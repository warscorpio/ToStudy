# Dependency Injection: IoC Container, Provider Scopes — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is dependency injection, and what problem does it solve over direct instantiation?**
A: Dependency injection (DI) is a technique where a class declares what it needs rather than creating its dependencies itself. Something external — a container, a factory, or a calling function — constructs those dependencies and passes them in.

The problem it solves is tight coupling between construction and usage:

```typescript
// WITHOUT DI — direct instantiation:
class OrderService {
    private db: Database;
    private emailer: EmailService;
    private logger: Logger;

    constructor() {
        // OrderService owns construction of its dependencies
        this.db = new PostgresDatabase({              // ← hard-coded implementation
            host: process.env.DB_HOST,               // ← reads config itself
            pool: new ConnectionPool({ size: 10 })   // ← creates transitive deps too
        });
        this.emailer = new SendGridEmailService(process.env.SENDGRID_KEY);
        this.logger = new WinstonLogger({ level: 'info' });
    }

    async createOrder(userId: string, items: Item[]): Promise<Order> {
        // business logic
    }
}

// Problems:
// 1. To test OrderService, you get a real DB and real email sends — slow, side-effectful
// 2. To swap PostgresDatabase for MySQL, you must edit OrderService
// 3. To reuse OrderService with a different logger, you must edit OrderService
// 4. New() is called inside — you cannot intercept or observe construction
// 5. Transitive deps (ConnectionPool) are invisible from the outside
```

```typescript
// WITH DI — constructor injection:
class OrderService {
    constructor(
        private readonly db: Database,           // ← interface, not concrete class
        private readonly emailer: EmailService,  // ← interface
        private readonly logger: Logger          // ← interface
    ) {}

    async createOrder(userId: string, items: Item[]): Promise<Order> {
        // same business logic — unchanged
    }
}

// Benefits:
// 1. Test with fakes: new OrderService(fakeDb, fakeEmailer, fakeLogger) — instant
// 2. Swap implementations: container decides PostgresDatabase vs MysqlDatabase
// 3. OrderService has ZERO knowledge of construction — pure business logic
// 4. Dependencies visible in the constructor signature — self-documenting

// Usage in production (manual DI, no container):
const db = new PostgresDatabase({ host: process.env.DB_HOST });
const emailer = new SendGridEmailService(process.env.SENDGRID_KEY);
const logger = new WinstonLogger();
const orderService = new OrderService(db, emailer, logger);
// This is DI without a container — explicit wiring in a composition root
```

**Q2. What is Inversion of Control, and what is the difference between IoC and DI?**
A: Inversion of Control (IoC) is the broader principle — "don't call us, we'll call you." Control over a concern is *inverted* from the component to an external orchestrator. DI is one specific form of IoC:

```
IoC is the principle. DI is one pattern that implements it.

Other IoC patterns beyond DI:
  ┌─────────────────────────────────────────────────────────────┐
  │ Event system: you register a handler, the framework calls   │
  │   it when the event fires — you don't poll                  │
  │                                                             │
  │ Template method: base class defines algorithm structure,    │
  │   subclass fills in steps — base class calls your code      │
  │                                                             │
  │ Service locator: component asks a registry for its deps     │
  │   (anti-pattern — deps are hidden, not declared)            │
  │                                                             │
  │ Dependency injection: container constructs and supplies deps │
  │   — the specific IoC form this document covers              │
  └─────────────────────────────────────────────────────────────┘
```

```typescript
// The "Hollywood Principle" — "Don't call us, we'll call you"

// Traditional control flow (you control):
function bootstrap() {
    const db = new Database();
    const service = new OrderService(db);
    service.start();         // ← you call service
}

// IoC control flow (framework controls):
@Injectable()
class OrderService {
    constructor(private db: Database) {}
    // You declare what you need
    // Framework decides WHEN to construct, with WHAT, and WHEN to call your code
}
// Framework: "We'll construct your OrderService when it's needed,
//             we'll call its methods in response to HTTP requests.
//             You don't call us — we'll call you."
```

**Q3. What are the three forms of dependency injection, and which should you prefer?**
A: Constructor, property (field), and method injection — each with different tradeoffs:

```typescript
// FORM 1: Constructor injection (preferred)
@Injectable()
class OrderService {
    constructor(
        private readonly db: Database,
        private readonly emailer: EmailService
    ) {}
    // Dependencies required to instantiate — object is always fully initialized
    // readonly enforces immutability — deps can't be swapped after construction
    // Dependencies visible in signature — easy to see what a class needs
    // Works naturally with TypeScript's type system
}

// FORM 2: Property (field) injection
@Injectable()
class OrderService {
    @Inject(Database)
    private db: Database;  // Not readonly — can be swapped (usually undesirable)

    @Inject(EmailService)
    private emailer: EmailService;
    // Object is partially initialized until framework injects properties
    // Methods called before injection → undefined reference errors
    // Required when: circular dependency forces one side to use property injection
    // Or: optional dependencies where constructor would always require the dep
}

// FORM 3: Method injection (rare)
@Injectable()
class ReportGenerator {
    generateReport(@Inject(DataSource) dataSource: DataSource): Report {
        // Dep injected per-call — different source per invocation
        // Use when the dependency varies per method call, not per class instance
        // Rare in IoC containers — more common in frameworks like Angular's DI
    }
}
```

```typescript
// Why constructor injection wins:

// 1. The class is always fully initialized after construction:
const svc = new OrderService(db, emailer);
svc.createOrder(...);  // db and emailer are guaranteed non-null

// 2. TypeScript readonly + required constructor args = impossible to forget a dep:
// new OrderService()  ← compile error: expected 2 arguments

// 3. Testing is explicit — fake deps passed at construction:
const svc = new OrderService(
    new FakeDatabase(),
    new FakeEmailer()
);
// No reflection, no framework, no magic — just new()

// 4. Circular dependency = compile-time detection (vs silent runtime undefined):
// If A needs B and B needs A, TypeScript will flag one of them
// (property injection defers this to runtime)
```

## Section 2: The IoC Container

**Q4. What is an IoC container, and what does it do that manual wiring cannot?**
A: An IoC container is a runtime registry that maps tokens (class constructors, strings, or symbols) to factory functions or instances. It resolves the entire dependency graph automatically:

```typescript
// Manual wiring — the "composition root" pattern without a container:
// Works fine for small apps, becomes unwieldy at scale

import { PostgresDatabase } from './infra/database';
import { SendGridEmailService } from './infra/email';
import { WinstonLogger } from './infra/logger';
import { UserRepository } from './repositories/user.repo';
import { OrderRepository } from './repositories/order.repo';
import { InventoryRepository } from './repositories/inventory.repo';
import { PricingService } from './services/pricing.service';
import { InventoryService } from './services/inventory.service';
import { OrderService } from './services/order.service';
import { OrderController } from './controllers/order.controller';

// You must wire in dependency order manually:
const db = new PostgresDatabase(config.db);
const logger = new WinstonLogger(config.log);
const emailer = new SendGridEmailService(config.sendgrid);
const userRepo = new UserRepository(db, logger);
const orderRepo = new OrderRepository(db, logger);
const inventoryRepo = new InventoryRepository(db, logger);
const pricingService = new PricingService(logger);
const inventoryService = new InventoryService(inventoryRepo, logger);
const orderService = new OrderService(orderRepo, userRepo, inventoryService, pricingService, emailer, logger);
const orderController = new OrderController(orderService, logger);
// 10 classes → 10 lines. 100 classes → 100 lines and you must know the exact order.
```

```typescript
// With an IoC container (NestJS / tsyringe / InversifyJS style):

// Step 1: Annotate classes with @Injectable() — registers them as providable
@Injectable()
class PostgresDatabase implements Database { ... }

@Injectable()
class OrderRepository {
    constructor(private db: Database, private logger: Logger) {}
}

@Injectable()
class OrderService {
    constructor(
        private orderRepo: OrderRepository,
        private inventoryService: InventoryService,
        private emailer: EmailService,
        private logger: Logger
    ) {}
}

// Step 2: Register providers in a module
const container = new Container();
container.bind(Database).to(PostgresDatabase);      // interface → implementation
container.bind(EmailService).to(SendGridEmailService);
container.bind(Logger).to(WinstonLogger);
container.bind(OrderRepository).toSelf();           // class → itself
container.bind(OrderService).toSelf();

// Step 3: Resolve — container builds the entire graph in correct order
const orderService = container.get(OrderService);
// Container automatically:
//   1. Sees OrderService needs OrderRepository, InventoryService, EmailService, Logger
//   2. Sees OrderRepository needs Database, Logger
//   3. Constructs Database first (no deps)
//   4. Constructs Logger (no deps)
//   5. Constructs OrderRepository(database, logger)
//   6. Constructs OrderService(orderRepository, ...)
// You never explicitly construct anything
```

```
What a container provides beyond manual wiring:

Automatic topological sort:
  Container reads constructor metadata via TypeScript decorators + reflect-metadata
  Resolves the dependency tree bottom-up without you specifying order

Lifetime management:
  Singleton: one instance, reused everywhere (default in NestJS)
  Request-scoped: new instance per HTTP request
  Transient: new instance every time resolved
  Container enforces these automatically — you just declare them

Circular dependency detection:
  Container detects A→B→A cycles at startup and throws with the cycle path
  vs manual wiring where you discover this at runtime as a cryptic undefined

Lazy initialization:
  Container can defer construction until first use
  vs manual wiring where everything initializes at startup even if unused

Interceptors / decorators:
  Container can wrap instances with logging, caching, retry logic
  without the class knowing about it (AOP — aspect-oriented programming)
```

**Q5. How does an IoC container use TypeScript decorators and `reflect-metadata` to resolve types?**
A: TypeScript's experimental decorator support, combined with the `reflect-metadata` polyfill, allows classes to emit their constructor parameter types into metadata at runtime — which the container reads to build the dependency graph:

```typescript
// tsconfig.json — required settings:
{
  "compilerOptions": {
    "experimentalDecorators": true,   // Enables @Injectable(), @Inject() etc.
    "emitDecoratorMetadata": true     // Emits design:paramtypes metadata
  }
}

// At the top of your app entry point:
import 'reflect-metadata';  // Polyfill — must be imported before any decorated classes
```

```typescript
// What TypeScript emits when emitDecoratorMetadata is true:

// Your source:
@Injectable()
class OrderService {
    constructor(
        private orderRepo: OrderRepository,
        private emailer: EmailService,
        private logger: Logger
    ) {}
}

// Compiled JavaScript (roughly):
OrderService = __decorate(
    [Injectable()],
    OrderService
);
// TypeScript ALSO emits:
Reflect.defineMetadata(
    'design:paramtypes',            // ← standard metadata key
    [OrderRepository, EmailService, Logger],  // ← array of constructor refs
    OrderService
);
```

```typescript
// What @Injectable() and the container do with this:

function Injectable(): ClassDecorator {
    return (target) => {
        // Mark this class as injectable (container can instantiate it)
        Reflect.defineMetadata('injectable', true, target);
        // design:paramtypes already set by TypeScript — we just need to flag this class
    };
}

// Container resolution logic:
class Container {
    resolve<T>(token: Constructor<T>): T {
        // 1. Read the constructor's parameter types from metadata
        const paramTypes: Constructor[] =
            Reflect.getMetadata('design:paramtypes', token) ?? [];

        // 2. Recursively resolve each dependency
        const deps = paramTypes.map(dep => this.resolve(dep));

        // 3. Construct with resolved deps
        return new token(...deps);
    }
}

// Limitation: interfaces are erased at runtime — you cannot inject by interface
// The container sees design:paramtypes as [Object, Object] for interfaces
// Solution: use injection tokens (symbols or abstract classes):

const DATABASE_TOKEN = Symbol('Database');

@Injectable()
class OrderRepository {
    constructor(
        @Inject(DATABASE_TOKEN) private db: Database  // ← token, not interface
    ) {}
}

container.bind(DATABASE_TOKEN).to(PostgresDatabase);
```

```typescript
// Abstract classes work as tokens because they survive compilation:
abstract class Database {
    abstract query<T>(sql: string, params: unknown[]): Promise<T[]>;
}

@Injectable()
class PostgresDatabase extends Database { ... }

@Injectable()
class OrderRepository {
    constructor(private db: Database) {}
    // Database (abstract class) survives as a reference at runtime
    // reflect-metadata sees [Database] — not [Object]
    // Container binds Database → PostgresDatabase
}
```

## Section 3: Provider Scopes

**Q6. What are provider scopes, and why does the distinction between singleton, request, and transient matter?**
A: A provider scope defines the *lifetime* of an instance — when it is created, how long it lives, and whether it is shared:

```
Three fundamental scopes:

SINGLETON (default):
  Created: once, at module initialization
  Destroyed: when the application shuts down
  Shared: one instance across the ENTIRE application
  Use for: stateless services, connection pools, configuration, loggers

REQUEST:
  Created: once per incoming HTTP request
  Destroyed: when the request/response cycle completes
  Shared: one instance across all classes resolved within the same request
  Use for: per-request context (current user, trace ID, DB transaction)

TRANSIENT:
  Created: every time the class is resolved from the container
  Destroyed: when the consumer that holds it is garbage collected
  Shared: never — each consumer gets its own private instance
  Use for: stateful value objects, builders, factories that must not share state
```

```typescript
// NestJS scope declaration:
import { Injectable, Scope } from '@nestjs/common';

@Injectable()                          // Singleton (default — scope not specified)
class LoggerService { ... }

@Injectable({ scope: Scope.REQUEST })  // New instance per HTTP request
class RequestContextService { ... }

@Injectable({ scope: Scope.TRANSIENT }) // New instance every resolve
class QueryBuilder { ... }
```

```
Lifetime diagram for a single HTTP request to POST /api/orders:

App lifetime:          │←────────────── application running ──────────────────────►│
                       │                                                            │

Singleton instances:   LoggerService[1]          ← created at startup
                       DatabasePool[1]           ← created at startup
                       OrderService[1]           ← created at startup (depends on above)

Request lifetime:      │←── req A ──►│           │←── req B ──►│
Request instances:         Context[A]                 Context[B]   ← separate instances
                           Transaction[A]             Transaction[B]

Transient instances:       QB[A-1] QB[A-2]            QB[B-1]
(one per resolve)          ↑ OrderService  ↑           ↑
                             resolved QB   ReportService
                             separately    resolved QB separately
```

**Q7. How does singleton scope work — what are the implications for stateful vs stateless services?**
A: Singleton scope means the container constructs the class exactly once and returns the same instance for every subsequent resolution. This is safe for stateless services but dangerous for anything that holds mutable per-request state:

```typescript
// SAFE: Stateless singleton — no mutable instance state
@Injectable()
class PricingService {
    // No instance variables that change per-request
    calculateTotal(items: Item[], prices: PriceMap): number {
        return items.reduce((sum, item) =>
            sum + (prices[item.id] ?? 0) * item.quantity, 0);
    }
}
// Same instance handles request A and request B simultaneously
// No shared state between calls → perfectly safe as singleton
```

```typescript
// SAFE: Singleton with immutable state
@Injectable()
class ConfigService {
    private readonly config: Readonly<AppConfig>;

    constructor() {
        this.config = Object.freeze({
            dbHost: process.env.DB_HOST,
            apiKey: process.env.API_KEY,
            // ...
        });
    }

    get<K extends keyof AppConfig>(key: K): AppConfig[K] {
        return this.config[key];
    }
}
// Config set once at construction, frozen — safe to share across all requests
```

```typescript
// DANGEROUS: Mutable state in a singleton
@Injectable()                          // ← singleton (default)
class OrderService {
    private currentUser: User;         // ← SHARED ACROSS ALL REQUESTS

    async handleRequest(userId: string) {
        this.currentUser = await userRepo.find(userId);
        // Request A sets currentUser = UserA
        // Request B sets currentUser = UserB  ← overwrites A's value!
        // Request A continues and sees UserB ← data leak between requests
        await this.processOrder();
    }

    private async processOrder() {
        // this.currentUser could be from any request
    }
}

// Fix option 1: pass state as parameters (preferred for pure logic):
@Injectable()
class OrderService {
    async handleRequest(userId: string) {
        const user = await userRepo.find(userId);
        await this.processOrder(user);  // ← pass explicitly, no instance state
    }

    private async processOrder(user: User) {
        // user is a local variable — no shared state
    }
}

// Fix option 2: use REQUEST scope (when state is genuinely per-request):
@Injectable({ scope: Scope.REQUEST })
class OrderContext {
    currentUser: User;                 // ← safe: new instance per request
}
```

```typescript
// Singleton and connection pooling — the right use case:
@Injectable()
class DatabaseService {
    private pool: Pool;

    constructor(config: ConfigService) {
        // Pool created ONCE — expensive, holds persistent connections
        this.pool = new Pool({
            host: config.get('dbHost'),
            max: 20,              // 20 persistent connections
            idleTimeoutMillis: 30000
        });
    }

    async query<T>(sql: string, params: unknown[]): Promise<T[]> {
        // Pool.query() acquires a connection from the pool, executes, releases
        // Safe for concurrent requests — pool manages connection assignment
        const { rows } = await this.pool.query(sql, params);
        return rows;
    }
}
// Creating a new Pool per request would be disastrous:
// Each request: new TCP connection to DB + auth handshake + TLS = ~50ms overhead
// Singleton pool: reuses existing connections = ~1ms
```

**Q8. How does request scope work — how does the container create and destroy instances per-request?**
A: Request-scoped providers are created when the request enters the DI layer and are tied to the request's async context. The container uses `AsyncLocalStorage` (or equivalent) to track which instance belongs to which request:

```typescript
// NestJS request scope — under the hood:

// When a request arrives:
// 1. NestJS creates a DI sub-context for this request
// 2. Any REQUEST-scoped provider resolved in this sub-context gets a new instance
// 3. The same instance is shared for all resolutions WITHIN the same request
// 4. When the request ends, the sub-context is destroyed → GC collects instances

@Injectable({ scope: Scope.REQUEST })
class RequestContextService {
    private data: Map<string, unknown> = new Map();

    set(key: string, value: unknown): void {
        this.data.set(key, value);
    }

    get<T>(key: string): T | undefined {
        return this.data.get(key) as T;
    }
}

// Both services in the same request get THE SAME RequestContextService instance:
@Injectable()
class AuthService {
    constructor(private context: RequestContextService) {}

    async authenticate(token: string): Promise<void> {
        const user = await verifyToken(token);
        this.context.set('user', user);   // Sets on the shared request context
    }
}

@Injectable()
class OrderService {
    constructor(private context: RequestContextService) {}

    async createOrder(items: Item[]): Promise<Order> {
        const user = this.context.get<User>('user');  // Gets the SAME context
        // user is available here without passing it through every call
    }
}
```

```typescript
// Request scope propagation — important: consumers of a REQUEST-scoped provider
// are themselves treated as REQUEST-scoped even if not declared so:

@Injectable({ scope: Scope.REQUEST })
class RequestContext { ... }

@Injectable()        // Singleton declared, but...
class OrderService {
    constructor(private ctx: RequestContext) {}
    // NestJS promotes OrderService to REQUEST scope automatically
    // because its dependency is REQUEST-scoped
    // If OrderService stayed singleton, the same ctx would be shared across requests
}

// The scope "bubble up" rule:
// TRANSIENT dep in SINGLETON → TRANSIENT dep is re-resolved every time,
//   but SINGLETON keeps its own copy — the transient dep doesn't update
// REQUEST dep in SINGLETON → Nest/InversifyJS warns or throws at startup
// SINGLETON dep in REQUEST → fine — singleton outlives the request
// SINGLETON dep in TRANSIENT → fine — singleton is shared

// Valid combinations:
// Singleton can depend on: Singleton
// Request can depend on:   Singleton, Request
// Transient can depend on: Singleton, Request, Transient
```

```typescript
// Implementing request scope manually (without a full IoC framework):
import { AsyncLocalStorage } from 'node:async_hooks';

interface RequestStore {
    instances: Map<Function, unknown>;
}

const requestStorage = new AsyncLocalStorage<RequestStore>();

function getOrCreate<T>(constructor: new(...args: unknown[]) => T, factory: () => T): T {
    const store = requestStorage.getStore();
    if (!store) {
        throw new Error('Called outside request context');
    }
    if (!store.instances.has(constructor)) {
        store.instances.set(constructor, factory());
    }
    return store.instances.get(constructor) as T;
}

// Express middleware that establishes the request DI scope:
app.use((req, res, next) => {
    const store: RequestStore = { instances: new Map() };
    requestStorage.run(store, () => {
        res.on('finish', () => {
            // Clean up — call dispose() on request-scoped instances
            store.instances.forEach((instance: any) => {
                instance.dispose?.();
            });
            store.instances.clear();
        });
        next();
    });
});
```

**Q9. How does transient scope work, and when is it the right choice over singleton or request?**
A: Transient scope creates a new instance every time the provider is resolved from the container. The container neither caches nor tracks transient instances after handing them off:

```typescript
@Injectable({ scope: Scope.TRANSIENT })
class QueryBuilder {
    private conditions: string[] = [];
    private params: unknown[] = [];

    where(condition: string, ...params: unknown[]): this {
        this.conditions.push(condition);
        this.params.push(...params);
        return this;
    }

    build(): { sql: string; params: unknown[] } {
        return {
            sql: `WHERE ${this.conditions.join(' AND ')}`,
            params: this.params
        };
    }
}

// Why transient here: QueryBuilder has mutable state (.conditions, .params)
// Two consumers building different queries simultaneously must NOT share state

// Each service gets its OWN QueryBuilder:
@Injectable()
class OrderRepository {
    constructor(private qb: QueryBuilder) {}

    async findByUser(userId: string): Promise<Order[]> {
        const { sql, params } = this.qb
            .where('user_id = $1', userId)
            .where('deleted_at IS NULL')
            .build();
        // this.qb is OrderRepository's private instance
    }
}

@Injectable()
class ProductRepository {
    constructor(private qb: QueryBuilder) {}

    async findActive(): Promise<Product[]> {
        const { sql, params } = this.qb
            .where('active = true')
            .build();
        // this.qb is ProductRepository's private instance — not shared with OrderRepository
    }
}
```

```typescript
// Transient scope decision criteria:

// Use TRANSIENT when:
// 1. The class has mutable state that must not be shared between consumers
// 2. The class is a builder, accumulator, or context object for a single operation
// 3. You need guaranteed isolation between two uses of the same class

// Use SINGLETON instead of transient when:
// 1. The class is stateless — same behavior regardless of which instance
// 2. Construction is expensive (DB pool, config parsing, connection establishment)
// 3. The class holds a shared resource (cache, rate limiter, metrics counter)

// Use REQUEST instead of transient when:
// 1. You need one instance shared within a request, but isolated between requests
// 2. The state is per-request context (user, transaction, trace ID)
// 3. Consumers in the same request should see the same data (set by auth, read by service)

// TRANSIENT performance note:
// Transient = new instance on every resolve
// For expensive-to-construct classes, this is a meaningful cost
// Prefer singleton + explicit state passing for expensive stateless utilities
```

## Section 4: NestJS DI in Practice

**Q10. How does NestJS's module system relate to dependency injection — what do modules, providers, and exports mean?**
A: NestJS's module system is a layer on top of its IoC container that creates encapsulation boundaries — providers registered in a module are private to that module unless explicitly exported:

```typescript
// A well-structured NestJS module:

// order/order.module.ts
@Module({
    imports: [
        DatabaseModule,          // Makes DatabaseService available in this module
        UserModule,              // Makes UserService available (if UserModule exports it)
        forwardRef(() => NotificationModule)  // Handle circular module dependency
    ],
    providers: [
        OrderService,            // Registered in OrderModule's DI container scope
        OrderRepository,
        {
            provide: PRICING_ENGINE,         // Custom injection token
            useClass: TieredPricingEngine,   // Which class implements it
        },
        {
            provide: ORDER_CONFIG,
            useFactory: (config: ConfigService) => ({
                maxItemsPerOrder: config.get('MAX_ITEMS'),
                allowedCurrencies: ['USD', 'EUR', 'GBP']
            }),
            inject: [ConfigService],         // Deps for the factory function
        }
    ],
    controllers: [OrderController],
    exports: [OrderService]      // Only OrderService is visible to other modules
    // OrderRepository is private — other modules cannot inject it
})
export class OrderModule {}
```

```typescript
// Provider registration forms:

// 1. Shorthand — class is both the token and the implementation:
providers: [OrderService]
// Equivalent to:
providers: [{ provide: OrderService, useClass: OrderService }]

// 2. useClass — different implementation for the same token:
providers: [{
    provide: EmailService,              // token (interface/abstract class)
    useClass: process.env.NODE_ENV === 'test'
        ? MockEmailService              // test environment
        : SendGridEmailService          // production
}]

// 3. useValue — provide a constant or pre-constructed value:
providers: [{
    provide: 'APP_CONFIG',
    useValue: { version: '1.0.0', env: process.env.NODE_ENV }
}]

// 4. useFactory — async setup, computed values, conditional construction:
providers: [{
    provide: REDIS_CLIENT,
    useFactory: async (config: ConfigService): Promise<Redis> => {
        const client = new Redis({ host: config.get('REDIS_HOST') });
        await client.ping();    // Verify connection at startup
        return client;
    },
    inject: [ConfigService]
}]

// 5. useExisting — alias one token to another already-registered provider:
providers: [{
    provide: LEGACY_LOGGER_TOKEN,
    useExisting: LoggerService     // Same instance as LoggerService
}]
```

```typescript
// Injecting in a controller or service:

@Controller('orders')
export class OrderController {
    constructor(
```

**Q11. How do you handle circular dependencies in NestJS DI?**
A: Circular dependencies (A depends on B, B depends on A) need explicit resolution because the container cannot construct either without the other already existing:

```typescript
// The problem:
@Injectable()
class OrderService {
    constructor(private notificationService: NotificationService) {}
    //           ↑ needs NotificationService
}

@Injectable()
class NotificationService {
    constructor(private orderService: OrderService) {}
    //           ↑ needs OrderService
    // Container: to build OrderService I need NotificationService,
    //            to build NotificationService I need OrderService — deadlock
}
```

```typescript
// Solution 1: forwardRef — defers the reference until after both classes are defined
import { forwardRef, Inject, Injectable } from '@nestjs/common';

@Injectable()
class OrderService {
    constructor(
        @Inject(forwardRef(() => NotificationService))
        private notificationService: NotificationService
    ) {}
}

@Injectable()
class NotificationService {
    constructor(
        @Inject(forwardRef(() => OrderService))
        private orderService: OrderService
    ) {}
}

// And in the module:
@Module({
    imports: [forwardRef(() => NotificationModule)],
    // ...
})
export class OrderModule {}

// forwardRef wraps the reference in a thunk () => NotificationService
// Container resolves the thunk lazily — by the time it's called, both
// classes are defined. One is instantiated first with a Proxy for the
// circular dep; after both are constructed, the Proxy is replaced.
```

```typescript
// Solution 2 (preferred): break the cycle by introducing a mediator
// Circular deps often signal missing abstraction — a shared dependency

// Before: OrderService ↔ NotificationService (circular)
// After:  OrderService → EventBus ← NotificationService (no cycle)

@Injectable()
class OrderEventBus {
    private handlers = new Map<string, Function[]>();

    emit(event: string, payload: unknown): void {
        this.handlers.get(event)?.forEach(h => h(payload));
    }

    on(event: string, handler: Function): void {
        if (!this.handlers.has(event)) this.handlers.set(event, []);
        this.handlers.get(event)!.push(handler);
    }
}

@Injectable()
class OrderService {
    constructor(private eventBus: OrderEventBus) {}

    async createOrder(data: CreateOrderData): Promise<Order> {
        const order = await this.save(data);
        this.eventBus.emit('order.created', order);  // Emit, don't call NotificationService directly
        return order;
    }
}

@Injectable()
class NotificationService {
    constructor(private eventBus: OrderEventBus) {
        this.eventBus.on('order.created', this.onOrderCreated.bind(this));
    }

    private async onOrderCreated(order: Order): Promise<void> {
        await this.sendConfirmationEmail(order);
    }
}
// No cycle — both depend on EventBus, neither depends on each other
```

## Section 5: Advanced Patterns

**Q12. How do you implement the repository pattern with DI — and how does it interact with transaction scope?**
A: Repositories are the data-access layer, injected into services. The transaction challenge is propagating a single DB transaction across multiple repository calls without parameter drilling:

```typescript
// Repository interface (token for DI):
abstract class OrderRepository {
    abstract findById(id: string): Promise<Order | null>;
    abstract create(data: CreateOrderData): Promise<Order>;
    abstract updateStatus(id: string, status: OrderStatus): Promise<Order>;
}

// Concrete implementation:
@Injectable()
class PgOrderRepository extends OrderRepository {
    constructor(private db: DatabaseService) { super(); }

    async findById(id: string): Promise<Order | null> {
        // Gets current transaction from async context (or falls back to pool):
        const conn = this.db.getConnection();  // ALS-aware: returns trx if in one
        const row = await conn.query(
            'SELECT * FROM orders WHERE id = $1', [id]
        );
        return row ? mapToOrder(row) : null;
    }

    async create(data: CreateOrderData): Promise<Order> {
        const conn = this.db.getConnection();
        const [row] = await conn.query(
            'INSERT INTO orders (...) VALUES (...) RETURNING *',
            [data.userId, data.total]
        );
        return mapToOrder(row);
    }
}

// Transaction service — uses ALS to propagate transaction:
@Injectable()
class TransactionService {
    private txStorage = new AsyncLocalStorage<PoolClient>();

    async run<T>(fn: () => Promise<T>): Promise<T> {
        const client = await this.pool.connect();
        await client.query('BEGIN');
        try {
            const result = await this.txStorage.run(client, fn);
            await client.query('COMMIT');
            return result;
        } catch (err) {
            await client.query('ROLLBACK');
            throw err;
        } finally {
            client.release();
        }
    }

    getConnection(): PoolClient | Pool {
        return this.txStorage.getStore() ?? this.pool;
        // Returns active transaction client, or pool for auto-commit queries
    }
}

// DatabaseService delegates to TransactionService:
@Injectable()
class DatabaseService {
    constructor(private txService: TransactionService) {}

    getConnection() {
        return this.txService.getConnection();
    }

    async transaction<T>(fn: () => Promise<T>): Promise<T> {
        return this.txService.run(fn);
    }
}

// Usage — transaction propagates to all repositories:
@Injectable()
class OrderService {
    constructor(
        private db: DatabaseService,
        private orderRepo: OrderRepository,
        private inventoryRepo: InventoryRepository,
    ) {}

    async createOrder(data: CreateOrderData): Promise<Order> {
        return this.db.transaction(async () => {
            // Both repos use the SAME transaction client via ALS — no parameter passing
            const order = await this.orderRepo.create(data);
            await this.inventoryRepo.decrement(data.items);
            return order;
        });
    }
}
```

**Q13. How do you write a custom provider using `useFactory` for async initialization — database connections, Redis clients?**

```typescript
// Redis client with reconnection strategy:
export const REDIS_CLIENT = Symbol('REDIS_CLIENT');

{
    provide: REDIS_CLIENT,
```

**Q14. How do you implement interceptors and decorators with DI — and what is AOP in this context?**
A: Aspect-Oriented Programming (AOP) separates cross-cutting concerns (logging, caching, timing, retry) from business logic. IoC containers enable AOP by wrapping instances with interceptors without the class knowing:

```typescript
// NestJS interceptor — wraps every method call in a controller or service:
@Injectable()
class LoggingInterceptor implements NestInterceptor {
    constructor(private logger: LoggerService) {}  // ← DI works in interceptors

    intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
        const request = context.switchToHttp().getRequest();
        const { method, url } = request;
        const start = Date.now();

        this.logger.log(`→ ${method} ${url}`);

        return next.handle().pipe(
            tap(() => {
                this.logger.log(`← ${method} ${url} ${Date.now() - start}ms`);
            }),
            catchError((err) => {
                this.logger.error(`✗ ${method} ${url} ${err.message}`);
                return throwError(() => err);
            })
        );
    }
}

// Applied at controller level:
@UseInterceptors(LoggingInterceptor)
@Controller('orders')
class OrderController { ... }

// Or globally (wraps every route in the app):
app.useGlobalInterceptors(app.get(LoggingInterceptor));
```

```typescript
// Cache interceptor — transparent caching via DI:
@Injectable()
class CacheInterceptor implements NestInterceptor {
    constructor(
        @Inject(REDIS_CLIENT) private redis: Redis
    ) {}

    async intercept(context: ExecutionContext, next: CallHandler): Promise<Observable<unknown>> {
        const request = context.switchToHttp().getRequest();
        if (request.method !== 'GET') return next.handle();

        const key = `cache:${request.url}`;
        const cached = await this.redis.get(key);
        if (cached) {
            return of(JSON.parse(cached));  // Return cached response, skip handler
        }

        return next.handle().pipe(
            tap(async (data) => {
                await this.redis.setex(key, 60, JSON.stringify(data));  // Cache for 60s
            })
        );
    }
}

// The controller knows nothing about caching:
@UseInterceptors(CacheInterceptor)
@Get(':id')
async getOrder(@Param('id') id: string): Promise<Order> {
    return this.orderService.findById(id);
    // First call: runs, caches response
    // Subsequent calls within 60s: interceptor returns cache, handler never runs
}
```


## Section 6: Testing with DI

**Q15. How does DI enable unit testing — what is the difference between a stub, a mock, and a fake?**
A: DI makes testing trivial because you control what gets injected — real implementations are swapped for test doubles without touching the class under test:

```typescript
// The three types of test doubles:

// STUB — returns fixed data, no behavior verification:
class StubOrderRepository implements OrderRepository {
    async findById(id: string): Promise<Order | null> {
        return { id, userId: 'user-1', total: 99.99, status: 'pending' };
        // Always returns this — no matter what id is
    }
    async create(data: CreateOrderData): Promise<Order> {
        return { id: 'new-order-id', ...data, status: 'pending' };
    }
    async updateStatus(id: string, status: OrderStatus): Promise<Order> {
        return { id, status } as Order;
    }
}

// MOCK — records calls, allows behavior verification:
class MockEmailService implements EmailService {
    public sentEmails: Array<{ to: string; subject: string }> = [];

    async send(to: string, subject: string, body: string): Promise<void> {
        this.sentEmails.push({ to, subject });  // Record the call
        // Returns void — no actual email sent
    }

    assertEmailSentTo(to: string): void {
        const found = this.sentEmails.some(e => e.to === to);
        if (!found) throw new Error(`Expected email to ${to}, got: ${JSON.stringify(this.sentEmails)}`);
    }
}

// FAKE — working lightweight implementation (in-memory database, etc.):
class FakeOrderRepository implements OrderRepository {
    private store = new Map<string, Order>();

    async findById(id: string): Promise<Order | null> {
        return this.store.get(id) ?? null;  // Real behavior, no DB
    }

    async create(data: CreateOrderData): Promise<Order> {
        const order = { id: randomUUID(), ...data, status: 'pending' as const };
        this.store.set(order.id, order);
        return order;
    }

    async updateStatus(id: string, status: OrderStatus): Promise<Order> {
        const order = this.store.get(id);
        if (!order) throw new Error('Order not found');
        const updated = { ...order, status };
        this.store.set(id, updated);
        return updated;
    }

    // Test helper — seed initial state:
    seed(orders: Order[]): void {
        orders.forEach(o => this.store.set(o.id, o));
    }
}
```

## Section 7: Common Pitfalls

**Q16. What are the most common DI anti-patterns and how do you avoid them?**
A:

```typescript
// ANTI-PATTERN 1: Service Locator — asking the container for deps instead of declaring them
@Injectable()
class OrderService {
    async createOrder(data: CreateOrderData): Promise<Order> {
        // BAD: reaching into the container at runtime
        const repo = Container.get(OrderRepository);
        const emailer = Container.get(EmailService);
        return repo.create(data);
    }
}
// Problems:
// - Dependencies are hidden — you can't see what OrderService needs from its signature
// - Testing requires a full container setup, not just new()
// - Container.get() is a global — hard to intercept or replace in tests

// FIX: declare dependencies in the constructor
@Injectable()
class OrderService {
    constructor(
        private repo: OrderRepository,   // ← declared, visible, injectable, testable
        private emailer: EmailService
    ) {}
}
```

```typescript
// ANTI-PATTERN 2: Scope mismatch — singleton holding a request-scoped dep
@Injectable()                                     // Singleton
class OrderService {
    constructor(
        private ctx: RequestContextService         // Request-scoped!
    ) {}
    // At startup: container injects the RequestContextService instance from
    // the FIRST request (or a proxy). All subsequent requests see stale context.
    // NestJS throws a warning for this — in raw containers it silently corrupts data.
}

// FIX: use the REQUEST scope on the consumer too
@Injectable({ scope: Scope.REQUEST })             // Promoted to REQUEST
class OrderService {
    constructor(private ctx: RequestContextService) {}
}

// Or: inject a factory and resolve per-call
@Injectable()
class OrderService {
    constructor(
        @Inject(REQUEST_CONTEXT_FACTORY)
        private ctxFactory: () => RequestContextService
    ) {}

    async doWork() {
        const ctx = this.ctxFactory();  // New call to factory each time — gets current
    }
}
```

```typescript
// ANTI-PATTERN 3: Constructor doing async work or side effects
@Injectable()
class DatabaseService {
    private pool: Pool;

    constructor(config: ConfigService) {
        // BAD: async work in constructor
        this.pool = new Pool(config.get('db'));
        this.pool.connect().then(() => console.log('connected'));
        // Constructor returns synchronously — 'connected' may log AFTER first use
        // If connect() fails, the error is an unhandled rejection
    }
}

// FIX: use useFactory for async init, or onModuleInit lifecycle hook
@Injectable()
class DatabaseService implements OnModuleInit {
    private pool: Pool;

    constructor(private config: ConfigService) {
        // Synchronous construction only
        this.pool = new Pool(this.config.get('db'));
    }

    async onModuleInit(): Promise<void> {
        // NestJS waits for this to resolve before app starts accepting requests
        const client = await this.pool.connect();
        await client.query('SELECT 1');  // Verify connection
        client.release();
    }
}
```

**Q18. "A request-scoped service is leaking data between requests in production. How do you diagnose it?"**
A: Request scope leaks almost always trace to one of three root causes: scope mismatch, shared object reference, or missing ALS boundary:

```typescript
// Step 1: Verify the service IS actually request-scoped
// Check the @Injectable() decorator:
@Injectable()          // ← missing scope: Scope.REQUEST — this is SINGLETON!
class UserContextService {
    currentUser: User;
}

// vs
@Injectable({ scope: Scope.REQUEST })  // ← correct
class UserContextService {
    currentUser: User;
}

// Step 2: Check if a singleton holds a reference to the request-scoped instance
@Injectable()                                  // Singleton
class AuditService {
    constructor(private ctx: UserContextService) {}  // REQUEST scope!
    // NestJS should warn about this at startup
    // If using a raw container: ctx is whatever was injected at first resolution
    // All requests use the SAME ctx — data from Request A visible in Request B
}

// Diagnosis: add logging to the request-scoped service constructor
@Injectable({ scope: Scope.REQUEST })
class UserContextService {
    private readonly instanceId = randomUUID();

    constructor() {
        console.log(`UserContextService created: ${this.instanceId}`);
        // Each request should log a different instanceId
        // If you see the SAME instanceId for different requests → scope mismatch
    }
}
```

```typescript
// Step 3: Check the ALS boundary in middleware
// The requestStorage.run() must wrap the ENTIRE request lifecycle:

// WRONG — ALS scope doesn't cover the route handler:
app.use((req, res, next) => {
    requestStorage.run({ user: null }, next);
    // run() starts the scope and immediately exits
    // next() is called synchronously but route handlers are async
    // The ALS scope exits before the async handler runs
});

// CORRECT — scope wraps next() call:
app.use((req, res, next) => {
    requestStorage.run({ user: null }, () => next());
    //                                   ↑ next() runs INSIDE the als.run() callback
    //                                     All async operations triggered by next()
    //                                     inherit this scope
});

// Step 4: Verify cleanup is happening
// If request-scoped instances hold resources (DB connections, open files),
// missing cleanup → resource leak that also causes data leaks

@Injectable({ scope: Scope.REQUEST })
class RequestTransactionService implements OnRequestEnd {
    private client: PoolClient | null = null;

    async begin(): Promise<void> {
        this.client = await pool.connect();
        await this.client.query('BEGIN');
    }

    async onRequestEnd(): Promise<void> {
        // Called by NestJS when request lifecycle ends
        if (this.client) {
            await this.client.query('ROLLBACK');  // Safety — commit should have been explicit
            this.client.release();
            this.client = null;
        }
    }
}
```

| Concept | Key Idea | Common Mistake |
|---|---|---|
| Dependency injection | Class declares what it needs; something external constructs and supplies it | Constructing dependencies inside the class (`new Service()` in a constructor) |
| IoC container | Registry that resolves the full dependency graph, manages lifetimes, and wires instances | Treating it as a service locator — calling `container.get()` inside business logic |
| `reflect-metadata` | Polyfill that preserves TypeScript types at runtime for container introspection | Forgetting `import 'reflect-metadata'` at app entry point — container sees no param types |
| Constructor injection | Dependencies declared as constructor parameters — class is always fully initialized | Property injection where class methods can run before deps are injected |
| Singleton scope | One instance for the entire application lifetime | Mutable instance state in a singleton — shared across concurrent requests |
| Request scope | New instance per HTTP request, shared within that request's async tree | Using a request-scoped dep in a singleton — singleton keeps the first request's instance |
| Transient scope | New instance every time the token is resolved from the container | Using transient for expensive-to-construct classes — pays construction cost on every resolve |
| Scope mismatch | Singleton consuming request/transient — deps frozen at first resolution | NestJS warns at startup; raw containers silently share stale instances |
| `forwardRef` | Defers class reference resolution to break circular dependency declarations | Using it as the first solution — prefer refactoring to remove the cycle |
| `useFactory` | Async provider initialization — app waits for factory to resolve before starting | Doing async work in a constructor instead — race condition on first use |
| `emitDecoratorMetadata` | TypeScript compiler option that emits constructor param types into metadata | Injecting by interface — interfaces are erased at runtime, container sees `Object` |
| Test doubles | Stub (fixed data), mock (verifiable calls), fake (working in-memory impl) | Using a full DI container and real deps in unit tests — slow, side-effectful |

---

**Tip for interviews:** Five things separate strong candidates on dependency injection: (1) explaining **why interfaces disappear at runtime** and therefore cannot be used as injection tokens without `abstract class` or `Symbol` — knowing that `design:paramtypes` sees `[Object, Object]` for interfaces and being able to propose the correct fix shows real TypeScript + DI depth, not just NestJS API familiarity; (2) articulating the **scope compatibility rules** — that singleton can only safely depend on singleton, request can depend on singleton or request, and transient can depend on anything, and being able to describe *why* (a singleton holding a request-scoped dep freezes the first request's instance for the app's lifetime); (3) knowing that **circular dependencies are a design signal**, not a technical problem to solve with `forwardRef` — the right answer to "A depends on B and B depends on A" is to introduce a mediator or event bus, not to reach for `forwardRef` as the first tool; (4) being able to explain **the difference between DI and a service locator** — that service locator hides dependencies inside method bodies (same as `new()`, just delegated), while DI exposes them in the constructor signature, and why this distinction matters for testability and maintainability; and (5) understanding **async provider initialization** — that constructors must be synchronous, that `useFactory` is the hook for async setup, and that the container (NestJS's `onModuleInit`, InversifyJS's async bindings) awaits factory resolution before the app accepts traffic — preventing the class of bugs where an app starts but silently has no DB connection.
