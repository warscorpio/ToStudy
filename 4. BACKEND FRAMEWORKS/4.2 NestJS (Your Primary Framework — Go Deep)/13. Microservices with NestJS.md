# NestJS Microservices: TCP, Redis Transporter, Kafka Transporter — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the NestJS microservices module and how does it differ from a standard HTTP-based NestJS application?**
A: A standard NestJS app uses HTTP as its transport — request/response is tied to TCP connections managed by Express or Fastify, and routes are defined with `@Get()`, `@Post()`, etc. The microservices module abstracts the transport layer so the same message-passing semantics work over TCP sockets, Redis pub/sub, Kafka topics, NATS, RabbitMQ, and gRPC — without changing your handler code.

The key conceptual shift:

```
HTTP app:
  Client → HTTP request (verb + path) → Controller → HTTP response
  One-to-one, synchronous, stateless per request

Microservice app:
  Client → Message (pattern + data) → MessageHandler → Response (optional)
  Pattern-matched, transport-agnostic, can be:
    - Request-response (client awaits reply)
    - Event (fire-and-forget, no reply)
```

Structural differences:

```typescript
// Standard HTTP app:
async function bootstrap() {
    const app = await NestFactory.create(AppModule);
    await app.listen(3000);
}

// Microservice app (standalone, no HTTP):
async function bootstrap() {
    const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
        transport: Transport.TCP,
        options: { host: '0.0.0.0', port: 3001 },
    });
    await app.listen();  // no port arg — transport handles it
}

// Hybrid app (HTTP + microservice listener on same process):
async function bootstrap() {
    const app = await NestFactory.create(AppModule);       // HTTP
    app.connectMicroservice<MicroserviceOptions>({
        transport: Transport.REDIS,
        options: { host: 'localhost', port: 6379 },
    });
    await app.startAllMicroservices();  // start all microservice listeners
    await app.listen(3000);             // start HTTP server
}
```

**Q2. What are the two communication patterns in NestJS microservices and when do you use each?**
A: NestJS microservices support two patterns — request-response and event-based. The choice drives both how you send messages and how handlers respond:

```
Pattern             │ Client sends   │ Handler returns │ Client receives │ Use case
────────────────────┼────────────────┼─────────────────┼─────────────────┼──────────────────────────
Request-Response    │ send()         │ value or Observable │ Observable  │ Query (need data back)
                    │                │                 │ (subscribed)    │ Command with confirmation
────────────────────┼────────────────┼─────────────────┼─────────────────┼──────────────────────────
Event (fire & forget)│ emit()        │ void (ignored)  │ nothing         │ Audit logs, notifications
                    │                │                 │                 │ Cache invalidation, fanout
```

```typescript
// ── Server side ──────────────────────────────────────────────────────────────

@Controller()
export class LoanController {
    // Request-response handler: @MessagePattern
    // Client is waiting for a reply — return value is sent back
    @MessagePattern({ cmd: 'get_loan' })
    getLoan(@Payload() data: { id: string }): LoanDto {
        return this.loanService.findOne(data.id);
    }

    // Event handler: @EventPattern
    // Fire-and-forget — return value is discarded, client gets no reply
    @EventPattern('loan_disbursed')
    handleLoanDisbursed(@Payload() data: LoanDisbursedEvent): void {
        this.notificationService.sendDisbursementEmail(data);
    }
}

// ── Client side ──────────────────────────────────────────────────────────────

@Injectable()
export class GatewayService {
    constructor(
        @Inject('LOAN_SERVICE') private client: ClientProxy,
    ) {}

    // Request-response: returns Observable, must subscribe (or use firstValueFrom)
    async getLoan(id: string): Promise<LoanDto> {
        return firstValueFrom(
            this.client.send<LoanDto>({ cmd: 'get_loan' }, { id })
        );
    }

    // Event: returns Observable<void> that completes when message is dispatched
    async notifyDisbursement(event: LoanDisbursedEvent): Promise<void> {
        await firstValueFrom(
            this.client.emit('loan_disbursed', event)
        );
    }
}
```

**Q3. What is `ClientProxy` and how does NestJS's `ClientsModule` register microservice clients?**
A: `ClientProxy` is the abstract base class for all transport-specific clients — `ClientTCP`, `ClientRedis`, `ClientKafka`, etc. It exposes two methods: `send()` for request-response and `emit()` for events. Both return `Observable` — cold observables that only connect when subscribed.

`ClientsModule` registers named client providers via DI:

```typescript
// Registration in a feature module:
@Module({
    imports: [
        ClientsModule.register([
            {
                name: 'LOAN_SERVICE',               // injection token
                transport: Transport.TCP,
                options: { host: 'loan-service', port: 3001 },
            },
            {
                name: 'NOTIFICATION_SERVICE',
                transport: Transport.REDIS,
                options: { host: 'redis', port: 6379 },
            },
        ]),
    ],
    controllers: [GatewayController],
    providers: [GatewayService],
})
export class GatewayModule {}

// Async registration (reading from ConfigService):
@Module({
    imports: [
        ClientsModule.registerAsync([
            {
                name: 'LOAN_SERVICE',
                imports: [ConfigModule],
                inject: [ConfigService],
                useFactory: (config: ConfigService) => ({
                    transport: Transport.TCP,
                    options: {
                        host: config.get('LOAN_SERVICE_HOST'),
                        port: config.get<number>('LOAN_SERVICE_PORT'),
                    },
                }),
            },
        ]),
    ],
})
export class GatewayModule {}

// Injecting the client:
@Injectable()
export class GatewayService {
    constructor(
        @Inject('LOAN_SERVICE') private loanClient: ClientProxy,
    ) {}

    // ClientProxy is lazy — connection happens on first send/emit
    // Call connect() explicitly if you want to fail fast at startup:
    async onModuleInit() {
        await this.loanClient.connect();
    }

    async onModuleDestroy() {
        await this.loanClient.close();
    }
}
```

**Q4. What is the `@Payload()` decorator and how does message deserialization work in NestJS microservices?**
A: `@Payload()` extracts the `data` field from the incoming message envelope. Every NestJS microservice message has the shape `{ pattern, data }` internally — `@Payload()` gives you the `data` portion, analogous to `@Body()` in HTTP:

```typescript
// Internal message envelope (what travels over the wire):
// { pattern: { cmd: 'create_loan' }, data: { amount: 50000, userId: 'u1' } }

@Controller()
export class LoanController {
    // @Payload() extracts the data field:
    @MessagePattern({ cmd: 'create_loan' })
    createLoan(@Payload() dto: CreateLoanDto): Observable<LoanDto> {
        return from(this.loanService.create(dto));
    }

    // @Payload() with a property path (like @Body('field')):
    @MessagePattern({ cmd: 'get_loan' })
    getLoan(@Payload('id') id: string): LoanDto {
        return this.loanService.findOne(id);
    }

    // @Ctx() for transport-specific context (e.g., Kafka record metadata):
    @MessagePattern('loan_events')
    handleEvent(
        @Payload() data: LoanEvent,
        @Ctx() context: KafkaContext,
    ) {
        const { offset, partition, topic } = context.getMessage();
        this.logger.log(`Processing ${topic}[${partition}]@${offset}`);
        return this.loanService.processEvent(data);
    }
}

// Pipe validation on @Payload() — identical to HTTP:
@MessagePattern({ cmd: 'create_loan' })
@UsePipes(new ValidationPipe({ whitelist: true, transform: true }))
createLoan(@Payload() dto: CreateLoanDto): LoanDto {
    return this.loanService.create(dto);
}

// Global pipe for all message handlers (set in main.ts):
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, options);
app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
```

## Section 2: TCP Transporter

**Q5. How does the NestJS TCP transporter work, and what are its serialization and connection characteristics?**
A: The TCP transporter uses raw TCP sockets with a length-prefixed JSON protocol. NestJS wraps messages in a JSON envelope and prefixes each message with its byte length so the receiver knows where one message ends and the next begins — necessary because TCP is a stream, not a message protocol:

```
Wire format (length-prefixed JSON):
  [4-byte length][JSON payload]
  e.g.: [0x00, 0x00, 0x00, 0x2F]{"pattern":{"cmd":"get_loan"},"data":{"id":"1"}}

Server-side:
  TcpServer listens on a raw TCP socket
  For each connection: maintains a buffer, reads length prefix, waits for full message
  Dispatches to matching @MessagePattern handler
  Writes response back on the same connection

Client-side:
  ClientTCP maintains a persistent connection pool (one connection per ClientProxy instance)
  Each send() assigns a unique id to the message and awaits reply with matching id
  Multiplexes multiple in-flight requests over one TCP connection
```

```typescript
// Microservice setup:
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
    transport: Transport.TCP,
    options: {
        host: '0.0.0.0',  // listen on all interfaces
        port: 3001,
        // retryAttempts: 5,      // how many times to retry failed connection (client)
        // retryDelay: 3000,      // ms between retries
    },
});

// Client registration:
ClientsModule.register([{
    name: 'LOAN_SERVICE',
    transport: Transport.TCP,
    options: {
        host: 'loan-service',  // hostname (Docker service name, k8s DNS name)
        port: 3001,
    },
}]);

// Custom serializer/deserializer (if you need non-JSON wire format):
import { Serializer, Deserializer, IncomingResponse } from '@nestjs/microservices';

class MsgPackSerializer implements Serializer {
    serialize(value: unknown) {
        return msgpack.encode(value);  // returns Buffer
    }
}

class MsgPackDeserializer implements Deserializer {
    deserialize(value: Buffer): IncomingResponse {
        return msgpack.decode(value);
    }
}

ClientsModule.register([{
    name: 'LOAN_SERVICE',
    transport: Transport.TCP,
    options: {
        host: 'loan-service',
        port: 3001,
        serializer: new MsgPackSerializer(),
        deserializer: new MsgPackDeserializer(),
    },
}]);
```

**Q6. When should you use TCP transport and what are its limitations in production?**

```
TCP transport: strengths and limitations

Strengths:
  ✓ Zero external dependencies — no broker to run or manage
  ✓ Lowest latency: direct point-to-point socket connection
  ✓ Simple to set up for development or internal RPC between two known services
  ✓ Request-response semantics built-in

Limitations:
  ✗ No message persistence — if the receiver is down, the message is lost
  ✗ No fan-out — one sender → one receiver (point-to-point only)
  ✗ No built-in load balancing — you must put a load balancer in front for multiple instances
  ✗ No replay or backpressure — no way to replay missed messages
  ✗ Tight coupling — client must know the exact host:port of the server
  ✗ Connection management is manual — dropped connections require reconnect logic
  ✗ Not suitable for async workflows or event-driven fan-out

When to use TCP:
  - Internal RPC between two services that are always co-located or in the same cluster
  - Development / local setup where a broker is overhead
  - Low-latency synchronous calls where Redis/Kafka overhead is unacceptable
  - Simple two-service architectures where fan-out and persistence are not required

When NOT to use TCP:
  - Multiple consumer instances (need load balancing at the broker level)
  - Event-driven architectures with multiple subscribers
  - Any scenario requiring message durability or replay
  - Cross-datacenter communication
```

## Section 3: Redis Transporter

**Q7. How does the NestJS Redis transporter work, and what is the pub/sub model it relies on?**
A: The Redis transporter uses Redis's native pub/sub mechanism. For request-response, it uses two channels per message — one for the request and one for the reply. For events, it uses a single channel with all subscribers receiving every message:

```
Request-Response over Redis pub/sub:

Client publishes to:  "{ cmd: 'get_loan' }"   channel
                      message: { pattern, data, id: 'req-123' }

Server subscribes to: "{ cmd: 'get_loan' }"   channel
Server publishes reply to: "{ cmd: 'get_loan' }.reply"  channel
                      message: { response: <data>, id: 'req-123', isDisposed: true }

Client subscribes to: "{ cmd: 'get_loan' }.reply"
Client matches reply by id: 'req-123' → resolves the Observable

Event over Redis pub/sub:

Publisher emits to:   "loan_disbursed"  channel
ALL subscribers to:   "loan_disbursed"  receive a copy
                      (fan-out: N subscribers get N copies)
```

```typescript
// Microservice (server) setup:
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
    transport: Transport.REDIS,
    options: {
        host: 'localhost',
        port: 6379,
        password: process.env.REDIS_PASSWORD,
        tls: process.env.NODE_ENV === 'production' ? {} : undefined,
        // retryAttempts: 10,
        // retryDelay: 3000,
    },
});

// Client registration:
ClientsModule.registerAsync([{
    name: 'NOTIFICATION_SERVICE',
    imports: [ConfigModule],
    inject: [ConfigService],
    useFactory: (config: ConfigService): ClientProviderOptions => ({
        transport: Transport.REDIS,
        options: {
            host: config.get('REDIS_HOST'),
            port: config.get<number>('REDIS_PORT'),
            password: config.get('REDIS_PASSWORD'),
        },
    }),
}]);

// Handler — identical to TCP; transport is transparent:
@Controller()
export class NotificationController {
    @EventPattern('loan_disbursed')
    handleDisbursement(@Payload() event: LoanDisbursedEvent) {
        return this.notificationService.send(event);
    }

    @MessagePattern({ cmd: 'send_otp' })
    sendOtp(@Payload() data: SendOtpDto): Observable<OtpResult> {
        return from(this.otpService.send(data));
    }
}
```

**Q8. What are the operational differences between Redis pub/sub and Redis Streams, and when does NestJS Redis transporter fall short?**
A: NestJS's Redis transporter uses classic pub/sub, not Redis Streams. Understanding the difference is essential for production decisions:

```
Redis pub/sub (what NestJS Redis transporter uses):
  - Message is delivered to currently-connected subscribers only
  - If a subscriber is down: message is LOST permanently
  - If no subscribers: message is silently dropped
  - No persistence, no backlog
  - Fan-out: all subscribers get all messages (no consumer groups)
  - Message acknowledgment: none — Redis doesn't know if processing succeeded

Redis Streams (NOT used by NestJS transport — requires custom implementation):
  - Messages are persisted in an append-only log
  - Consumer groups: one message delivered to exactly ONE consumer in a group
  - Acknowledgment: XACK — message stays in the "pending" list until ack'd
  - Consumer restart: reads from last unack'd message (no messages lost)
  - Replay: can read from any position in the stream

Practical implications for production:

  Scenario: Notification service is restarting (zero-downtime deploy, 30s gap)
    Redis pub/sub: all events published during the 30s gap are LOST
    Redis Streams: events accumulate; consumer reads them on restart

  Scenario: 5 instances of notification service running
    Redis pub/sub: EACH instance gets EVERY event (5× processing)
    Redis Streams: consumer group ensures each event processed ONCE across 5 instances

When NestJS Redis transporter is appropriate:
  ✓ Cache invalidation signals (idempotent — duplicate is harmless)
  ✓ Real-time dashboards / websocket fanout (stateless, latest data matters)
  ✓ Development/staging environments

When to use Redis Streams or Kafka instead:
  ✗ Business-critical events that must not be lost
  ✗ Exactly-once processing requirements
  ✗ Multiple consumer instances sharing work
  ✗ Audit trail or event replay needs
```

**Q9. How do you handle Redis transporter connection failures and implement retry logic?**

```typescript
// Client-side retry and connection management:
ClientsModule.register([{
    name: 'REDIS_SERVICE',
    transport: Transport.REDIS,
    options: {
        host: 'redis',
        port: 6379,
        retryAttempts: 10,     // retry failed connection 10 times before throwing
        retryDelay: 3000,      // wait 3s between retries
    },
}]);

// Handling timeouts on send() — default: no timeout (hangs forever if service is down):
@Injectable()
export class GatewayService {
    constructor(@Inject('REDIS_SERVICE') private client: ClientProxy) {}

    async sendWithTimeout<T>(pattern: unknown, data: unknown, timeoutMs = 5000): Promise<T> {
        return firstValueFrom(
            this.client.send<T>(pattern, data).pipe(
                timeout(timeoutMs),
                catchError((err) => {
                    if (err instanceof TimeoutError) {
                        throw new ServiceUnavailableException(
                            `Service did not respond within ${timeoutMs}ms`
                        );
                    }
                    throw err;
                }),
            )
        );
    }

    // emit() fire-and-forget — but you can still handle errors from the dispatch:
    async emitSafe(event: string, data: unknown): Promise<void> {
        try {
            await firstValueFrom(this.client.emit(event, data));
        } catch (err) {
            // Log but don't throw — event delivery failure shouldn't crash the caller
            this.logger.error(`Failed to emit ${event}`, err);
        }
    }
}

// Server-side: if handler throws, NestJS sends error back to the client:
@MessagePattern({ cmd: 'send_otp' })
async sendOtp(@Payload() dto: SendOtpDto) {
    try {
        return await this.otpService.send(dto);
    } catch (err) {
        // Throwing RpcException sends a structured error to the client:
        throw new RpcException({ message: err.message, code: 'OTP_SEND_FAILED' });
    }
}

// Client receives RpcException as an error in the Observable:
this.client.send({ cmd: 'send_otp' }, dto).pipe(
    catchError((err: RpcException) => {
        this.logger.error('OTP send failed', err.message);
        throw new InternalServerErrorException(err.message);
    })
);
```

## Section 4: Kafka Transporter

**Q10. How does Kafka differ from TCP and Redis as a microservice transport, and what are its core concepts you must know?**
A: Kafka is a distributed, persistent, ordered log — fundamentally different from TCP (direct socket) and Redis (pub/sub). Understanding the Kafka data model is prerequisite to using the NestJS Kafka transporter correctly:

```
Core Kafka concepts:

Topic:
  Named, durable, ordered log of messages
  Partitioned: each partition is an independent ordered sequence
  Replicated: each partition has N replicas across brokers (fault tolerance)

Partition:
  Unit of parallelism — N partitions = up to N parallel consumers
  Messages within a partition are strictly ordered
  Across partitions: no ordering guarantee
  Partition key: determines which partition a message goes to
    same key → same partition → ordered delivery for that key

Consumer Group:
  Logical subscriber unit — each group gets all messages
  Within a group: each partition assigned to exactly ONE consumer
  N consumers in group, M partitions:
    if N ≤ M: each consumer handles M/N partitions
    if N > M: some consumers are idle (can't assign same partition to two consumers)

Offset:
  Position within a partition — monotonically increasing integer
  Consumer commits offset to mark "processed up to here"
  On restart: consumer resumes from committed offset (no lost messages)

Kafka vs Redis pub/sub vs TCP:

                    │ TCP        │ Redis pub/sub │ Kafka
────────────────────┼────────────┼───────────────┼──────────────────────
Persistence         │ None       │ None          │ Configurable (days/forever)
Fan-out             │ No         │ All receive   │ Per consumer group
Load balancing      │ Manual     │ None          │ Automatic (partition assignment)
Ordering            │ N/A        │ None          │ Per partition/key
Message replay      │ No         │ No            │ Yes (seek to offset)
Delivery guarantee  │ At-most-1  │ At-most-1     │ At-least-once (configurable)
Throughput          │ High       │ Very high     │ Extremely high
Operational cost    │ Low        │ Low           │ High (ZooKeeper/KRaft + brokers)
```

**Q11. How do you set up a NestJS Kafka microservice consumer and producer?**

```typescript
// ── Consumer (microservice that handles messages) ─────────────────────────

// main.ts:
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
    transport: Transport.KAFKA,
    options: {
        client: {
            clientId: 'loan-service',               // identifies this client in Kafka logs
            brokers: ['kafka-broker-1:9092', 'kafka-broker-2:9092'],
            ssl: true,
            sasl: {
                mechanism: 'plain',
                username: process.env.KAFKA_USERNAME,
                password: process.env.KAFKA_PASSWORD,
            },
            retry: {
                initialRetryTime: 300,
                retries: 8,
            },
        },
        consumer: {
            groupId: 'loan-service-group',         // consumer group — critical for load balancing
            allowAutoTopicCreation: false,          // never auto-create in production
            sessionTimeout: 30000,                  // ms before broker considers consumer dead
            heartbeatInterval: 3000,
        },
        subscribe: {
            fromBeginning: false,                   // true = replay all messages from offset 0
        },
    },
});
await app.listen();

// Controller — handlers register as consumers for topics:
@Controller()
export class LoanController {
    // @MessagePattern subscribes to a Kafka topic, enables request-response:
    @MessagePattern('loan.commands')
    handleCommand(
        @Payload() message: KafkaMessage,
        @Ctx() context: KafkaContext,
    ) {
        const heartbeat = context.getHeartbeat();
        // Call heartbeat() during long processing to prevent session timeout:
        return this.loanService.processCommand(message, heartbeat);
    }

    // @EventPattern for fire-and-forget (no reply sent back):
    @EventPattern('loan.events')
    handleEvent(@Payload() event: LoanEvent, @Ctx() context: KafkaContext) {
        const { offset, partition } = context.getMessage();
        this.logger.log(`Processing partition ${partition} offset ${offset}`);
        return this.loanService.handleEvent(event);
    }
}

// ── Producer (service that sends messages) ───────────────────────────────

@Module({
    imports: [
        ClientsModule.registerAsync([{
            name: 'KAFKA_SERVICE',
            imports: [ConfigModule],
            inject: [ConfigService],
            useFactory: (config: ConfigService): ClientProviderOptions => ({
                transport: Transport.KAFKA,
                options: {
                    client: {
                        clientId: 'gateway',
                        brokers: config.get<string[]>('KAFKA_BROKERS'),
                    },
                    producer: {
                        allowAutoTopicCreation: false,
                        idempotent: true,              // exactly-once produce (retries don't duplicate)
                        transactionTimeout: 30000,
                    },
                    producerOnlyMode: true,            // this client only produces, never consumes
                },
            }),
        }]),
    ],
})
export class GatewayModule {}
```

**Q12. How does Kafka message key-based partitioning work in NestJS, and why does it matter for ordering?**
A: Kafka assigns a message to a partition based on its key. Same key always goes to the same partition, which is strictly ordered. This is the primary tool for ensuring related messages are processed in order:

```typescript
// Sending with a partition key:
@Injectable()
export class LoanProducerService {
    constructor(@Inject('KAFKA_SERVICE') private client: ClientKafka) {}

    async onModuleInit() {
        // Subscribe to reply topics for request-response patterns:
        this.client.subscribeToResponseOf('loan.commands');
        await this.client.connect();
    }

    // emit() with a key: ensures all events for the same loanId go to the same partition
    async emitLoanEvent(loanId: string, event: LoanEvent): Promise<void> {
        await firstValueFrom(
            this.client.emit('loan.events', {
                key: loanId,        // partition key — loanId determines partition
                value: event,       // actual payload
                headers: {
                    'correlation-id': crypto.randomUUID(),
                    'event-type': event.type,
                    'timestamp': Date.now().toString(),
                },
            })
        );
    }

    // send() for request-response:
    async getApplicationStatus(loanId: string): Promise<ApplicationStatus> {
        return firstValueFrom(
            this.client.send('loan.commands', {
                key: loanId,
                value: { type: 'GET_STATUS', loanId },
            })
        );
    }
}

// Why key-based ordering matters — example:
// Without key:
//   LOAN_CREATED → partition 0
//   LOAN_APPROVED → partition 2
//   LOAN_DISBURSED → partition 1
//   Consumer 1 processes partition 0, consumer 2 processes partition 1, consumer 3 partition 2
//   Possible processing order: LOAN_APPROVED → LOAN_DISBURSED → LOAN_CREATED ← incorrect!

// With key = loanId:
//   All events for loan 'L001' → partition 0
//   Consumer processing partition 0 sees: LOAN_CREATED → LOAN_APPROVED → LOAN_DISBURSED ← correct
//   Ordering guaranteed within a loan's lifecycle
```

**Q13. How do you implement manual offset commit in the NestJS Kafka transporter for at-least-once processing guarantees?**
A: By default, NestJS commits the offset automatically after the handler returns. For critical processing — where you only want to commit after successful database write — you disable auto-commit and commit manually:

```typescript
// Consumer setup with manual commits:
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
    transport: Transport.KAFKA,
    options: {
        client: { clientId: 'loan-service', brokers: ['kafka:9092'] },
        consumer: {
            groupId: 'loan-service-group',
            allowAutoTopicCreation: false,
        },
        run: {
            autoCommit: false,  // disable automatic offset commits
        },
    },
});

// Handler with manual commit:
@Controller()
export class LoanEventController {
    constructor(private loanService: LoanService) {}

    @EventPattern('loan.events')
    async handleLoanEvent(
        @Payload() event: LoanEvent,
        @Ctx() context: KafkaContext,
    ) {
        const message = context.getMessage();
        const partition = context.getPartition();
        const topic = context.getTopic();
        const heartbeat = context.getHeartbeat();

        try {
            // Process the event — database write, downstream call, etc.
            await this.loanService.processEvent(event);

            // Only commit AFTER successful processing:
            const { offset } = message;
            await context.getConsumer().commitOffsets([{
                topic,
                partition,
                offset: (BigInt(offset) + 1n).toString(),  // commit NEXT offset
            }]);
        } catch (err) {
            // Don't commit — message will be redelivered on restart
            // Log the error with context for debugging:
            this.logger.error('Failed to process event', {
                err: err.message,
                topic,
                partition,
                offset: message.offset,
                key: message.key?.toString(),
            });
            // Optionally: send to a dead-letter topic for manual inspection
            throw err;  // re-throw so NestJS knows handler failed
        }
    }
}
```

**Q14. What is a dead letter queue (DLQ) pattern and how do you implement it with the Kafka transporter?**
A: A DLQ is a separate topic where messages that repeatedly fail processing are sent instead of blocking the main consumer. Without a DLQ, one bad message can halt partition processing indefinitely:

```typescript
// Dead letter queue implementation:
@Injectable()
export class LoanEventConsumer {
    private readonly DLQ_TOPIC = 'loan.events.dlq';
    private readonly MAX_RETRIES = 3;

    constructor(
        @Inject('KAFKA_SERVICE') private producer: ClientKafka,
        private loanService: LoanService,
        private logger: Logger,
    ) {}

    @EventPattern('loan.events')
    async handleLoanEvent(
        @Payload() event: LoanEvent,
        @Ctx() context: KafkaContext,
    ) {
        const message = context.getMessage();
        const headers = message.headers as Record<string, Buffer>;

        // Track retry count via Kafka headers:
        const retryCount = headers['retry-count']
            ? parseInt(headers['retry-count'].toString(), 10)
            : 0;

        try {
            await this.loanService.processEvent(event);
        } catch (err) {
            if (retryCount >= this.MAX_RETRIES) {
                // Max retries exceeded — send to DLQ and commit (don't block):
                await firstValueFrom(
                    this.producer.emit(this.DLQ_TOPIC, {
                        key: message.key,
                        value: event,
                        headers: {
                            ...headers,
                            'original-topic': 'loan.events',
                            'error-message': err.message,
                            'failed-at': new Date().toISOString(),
                            'retry-count': retryCount.toString(),
                        },
                    })
                );
                this.logger.error(`Message sent to DLQ after ${retryCount} retries`, {
                    key: message.key?.toString(),
                    error: err.message,
                });
                // Commit offset — message is in DLQ, don't reprocess
                return;
            }

            // Re-emit to original topic with incremented retry count:
            await firstValueFrom(
                this.producer.emit('loan.events', {
                    key: message.key,
                    value: event,
                    headers: {
                        ...headers,
                        'retry-count': (retryCount + 1).toString(),
                        'retry-reason': err.message,
                    },
                })
            );
        }
    }

    // Separate handler to process DLQ messages manually:
    @EventPattern('loan.events.dlq')
    async handleDlqEvent(
        @Payload() event: LoanEvent,
        @Ctx() context: KafkaContext,
    ) {
        const headers = context.getMessage().headers as Record<string, Buffer>;
        // Alert, store in DB for manual review, send Slack notification:
        await this.alertService.notifyDlqMessage({
            event,
            error: headers['error-message']?.toString(),
            failedAt: headers['failed-at']?.toString(),
        });
    }
}
```

## Section 5: Cross-Cutting Concerns

**Q15. How do exception filters work in NestJS microservices and how do they differ from HTTP exception filters?**
A: HTTP exception filters catch exceptions and write HTTP responses (status codes, JSON bodies). Microservice exception filters catch exceptions and write RPC responses — the reply message sent back to the client. Both use `@Catch()` but implement different interfaces:

```typescript
// HTTP filter implements ExceptionFilter:
@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
    catch(exception: HttpException, host: ArgumentsHost) {
        const ctx = host.switchToHttp();
        const response = ctx.getResponse<Response>();
        response.status(exception.getStatus()).json({ message: exception.message });
    }
}

// RPC filter implements RpcExceptionFilter:
import { Catch, RpcExceptionFilter, ArgumentsHost } from '@nestjs/common';
import { RpcException } from '@nestjs/microservices';
import { Observable, throwError } from 'rxjs';

@Catch(RpcException)
export class MicroserviceExceptionFilter implements RpcExceptionFilter<RpcException> {
    catch(exception: RpcException, host: ArgumentsHost): Observable<never> {
        // throwError() wraps the error as an Observable error — sent back as error reply
        return throwError(() => exception.getError());
    }
}

// Catch all errors (not just RpcException) in a microservice:
@Catch()
export class AllExceptionsFilter implements RpcExceptionFilter {
    catch(exception: unknown, host: ArgumentsHost): Observable<never> {
        const error = exception instanceof RpcException
            ? exception.getError()
            : { message: 'Internal microservice error', code: 'INTERNAL_ERROR' };
        return throwError(() => error);
    }
}

// Register globally in main.ts:
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, options);
app.useGlobalFilters(new AllExceptionsFilter());

// Client receiving the error:
this.client.send({ cmd: 'create_loan' }, dto).pipe(
    catchError((err: { message: string; code: string }) => {
        throw new InternalServerErrorException(`${err.code}: ${err.message}`);
    })
);
```

**Q16. How do you propagate distributed tracing context (trace IDs, span IDs) across microservice boundaries?**
A: Each transport has a different mechanism for passing metadata. The pattern: extract trace context from the incoming request, inject it into outgoing microservice messages as headers or metadata:

```typescript
// Interceptor that propagates trace context via message headers:
@Injectable()
export class TraceContextInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
        const contextType = context.getType<'http' | 'rpc'>();

        if (contextType === 'rpc') {
            // Extract trace context from incoming Kafka/Redis message headers:
            const kafkaCtx = context.switchToRpc().getContext<KafkaContext>();
            const headers = kafkaCtx.getMessage()?.headers;
            const traceId = headers?.['x-trace-id']?.toString() ?? crypto.randomUUID();
            // Store in AsyncLocalStorage for downstream use:
            traceStorage.run({ traceId }, () => next.handle());
        }

        return next.handle();
    }
}

// ClientProxy interceptor — attach trace context to every outgoing message:
@Injectable()
export class TracingClientProxy extends ClientProxy {
    async dispatchEvent(packet: ReadPacket): Promise<void> {
        const traceContext = traceStorage.getStore();
        const enriched = {
            ...packet,
            data: {
                ...packet.data,
                _headers: {
                    'x-trace-id': traceContext?.traceId ?? crypto.randomUUID(),
                    'x-span-id': crypto.randomUUID(),
                },
            },
        };
        return super.dispatchEvent(enriched);
    }

    // For Kafka specifically, headers are first-class:
    async emitWithTrace(topic: string, event: unknown): Promise<void> {
        const traceId = traceStorage.getStore()?.traceId ?? crypto.randomUUID();
        await firstValueFrom(
            (this as unknown as ClientKafka).emit(topic, {
                key: (event as { id?: string }).id,
                value: event,
                headers: {
                    'x-trace-id': traceId,
                    'x-span-id': crypto.randomUUID(),
                    'x-source-service': process.env.SERVICE_NAME,
                },
            })
        );
    }
}
```

**Q17. How do you implement health checks for microservice clients in a hybrid NestJS app?**

```typescript
// Using @nestjs/terminus for health checks:
import { Injectable } from '@nestjs/common';
import { HealthIndicator, HealthIndicatorResult, HealthCheckError } from '@nestjs/terminus';
import { ClientProxy } from '@nestjs/microservices';
import { firstValueFrom, timeout, catchError } from 'rxjs';
import { of } from 'rxjs';

@Injectable()
export class MicroserviceHealthIndicator extends HealthIndicator {
    constructor(
        @Inject('LOAN_SERVICE') private loanClient: ClientProxy,
    ) {
        super();
    }

    async isHealthy(key: string): Promise<HealthIndicatorResult> {
        try {
            const result = await firstValueFrom(
                this.loanClient.send<{ status: string }>({ cmd: 'health' }, {}).pipe(
                    timeout(2000),                     // fail fast if service doesn't respond
                    catchError(() => of({ status: 'down' })),
                )
            );

            const isHealthy = result?.status === 'ok';
            const data = this.getStatus(key, isHealthy, { status: result?.status });

            if (!isHealthy) throw new HealthCheckError(`${key} is down`, data);
            return data;
        } catch (err) {
            const data = this.getStatus(key, false, { error: err.message });
            throw new HealthCheckError(`${key} failed health check`, data);
        }
    }
}

// Health check controller:
@Controller('health')
export class HealthController {
    constructor(
        private health: HealthCheckService,
        private microserviceHealth: MicroserviceHealthIndicator,
        private redis: MicroserviceHealthIndicator,
    ) {}

    @Get()
    @HealthCheck()
    check() {
        return this.health.check([
            () => this.microserviceHealth.isHealthy('loan-service'),
            () => this.redis.isHealthy('redis'),
        ]);
    }
}

// Corresponding health handler on the microservice:
@MessagePattern({ cmd: 'health' })
healthCheck(): { status: string; timestamp: string } {
    return { status: 'ok', timestamp: new Date().toISOString() };
}
```

## Section 6: Scenario-Based Questions

**Q18. "You have a monolithic NestJS app handling loan applications. You need to extract the notification service as a microservice. How do you do it without downtime, and which transporter do you pick?"**
A: The pattern is strangler fig — extract incrementally, run old and new in parallel, then remove the old code:

```typescript
// Phase 1: Add the microservice client to the monolith WHILE keeping in-process calls
// (no risk — new code is dead until you switch the call site)

// notification.module.ts (in monolith):
@Module({
    imports: [
        ClientsModule.register([{
            name: 'NOTIFICATION_SERVICE',
            transport: Transport.REDIS,              // Redis chosen: fan-out, decoupled
            options: { host: process.env.REDIS_HOST, port: 6379 },
        }]),
    ],
    providers: [NotificationService, NotificationRouter],  // router decides in-process vs remote
})
export class NotificationModule {}

// notification.router.ts — feature-flagged routing:
@Injectable()
export class NotificationRouter {
    constructor(
        @Inject('NOTIFICATION_SERVICE') private client: ClientProxy,
        private legacyService: LegacyNotificationService,
        private config: ConfigService,
    ) {}

    async send(event: NotificationEvent): Promise<void> {
        if (this.config.get('USE_REMOTE_NOTIFICATION_SERVICE') === 'true') {
            // Route to extracted microservice:
            await firstValueFrom(this.client.emit('notification.events', event));
        } else {
            // Legacy in-process call:
            await this.legacyService.send(event);
        }
    }
}

// Phase 2: Deploy the standalone notification microservice
// notification-service/main.ts:
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
    transport: Transport.REDIS,
    options: { host: process.env.REDIS_HOST, port: 6379 },
});
await app.listen();

// Phase 3: Flip the feature flag → monolith routes to extracted service
// Phase 4: Monitor for errors in the new service
// Phase 5: Remove LegacyNotificationService and the feature flag

// Why Redis over TCP here:
// - Multiple notification service instances can subscribe (fan-out, load sharing via event)
// - Notifications are fire-and-forget — no reply needed
// - Redis already in the stack (session cache) — no new infrastructure
// - TCP would require a load balancer in front of notification service instances
```

**Q19. "Your Kafka consumer group has 4 consumers but only 2 partitions on the `loan.events` topic. Two consumers are always idle. How do you fix it and what is the production-safe way to repartition?"**
A: The number of active consumers in a group is bounded by the partition count — you can never have more active consumers than partitions. The fix is to increase partitions:

```typescript
// Diagnosis — check partition assignment:
// consumer group: loan-service-group
// topic: loan.events, partitions: 0, 1
// consumer-0: assigned [partition-0]
// consumer-1: assigned [partition-1]
// consumer-2: assigned [] ← idle
// consumer-3: assigned [] ← idle

// Fix: increase partition count from 2 → 8 (rule of thumb: partitions = max expected consumers × 2)
// Kafka only allows ADDING partitions (never removing — it would change key routing)
// Production-safe repartition steps:

// Step 1: Pause producers (or let in-flight messages drain)
// Step 2: kafka-topics.sh --alter --topic loan.events --partitions 8 --bootstrap-server kafka:9092
// Step 3: Restart consumers — Kafka triggers a rebalance and assigns new partitions

// WARNING: adding partitions changes partition assignment for existing keys
// Key 'L001' may have gone to partition 0 (of 2) but after repartition goes to partition 4 (of 8)
// This means ordered processing guarantees for a key are broken for messages produced BEFORE the repartition
// Safe approach: drain the topic fully before repartitioning if ordering is critical

// NestJS consumer config for 8 partitions — concurrency per instance:
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
    transport: Transport.KAFKA,
    options: {
        client: { clientId: 'loan-service', brokers: ['kafka:9092'] },
        consumer: {
            groupId: 'loan-service-group',
        },
        run: {
            // Process up to 4 messages concurrently per consumer instance:
            // Total concurrency = instances × partitionsPerInstance
            eachBatchAutoResolve: false,
            partitionsConsumedConcurrently: 4,
        },
    },
});

// After repartition: 8 partitions, 4 consumers = 2 partitions each
// All consumers are active, throughput doubles
```

**Q20. "A senior engineer says 'use Kafka for everything — it's more reliable than Redis'. How do you evaluate this claim?"**
A: This is a classic over-engineering trap. The right transport depends on the specific requirement, not a blanket rule:

```
Evaluation framework — ask these questions per use case:

1. Must the message survive consumer downtime?
   YES → Kafka (or Redis Streams). Redis pub/sub drops messages when consumer is down.
   NO  → Redis pub/sub is fine (cache invalidation, dashboard updates)

2. Do multiple independent services need to receive the same event?
   YES → Both work: Kafka (multiple consumer groups), Redis (pub/sub fan-out)
   For Kafka: each consumer group reads the full stream independently
   For Redis pub/sub: all current subscribers get every message

3. Do multiple instances of the SAME service share processing load?
   YES → Kafka (consumer groups give exactly-one-per-group semantics)
   Redis pub/sub: ALL instances get ALL messages → duplicate processing

4. Is ordering required across related messages?
   YES → Kafka with a consistent partition key
   Redis pub/sub: no ordering guarantees at all

5. Do you need replay (re-process historical events)?
   YES → Only Kafka (offset-based replay). Redis pub/sub: no history.

6. What is your ops capacity?
   Kafka: needs brokers, ZooKeeper or KRaft, monitoring, retention tuning,
          consumer lag alerting, schema registry (for Avro/Protobuf)
   Redis: one Redis instance or Redis Sentinel — already in most stacks

Practical decision table:

Use case                          │ Recommended transport
──────────────────────────────────┼────────────────────────────────────
Direct service-to-service RPC     │ TCP (simplest, lowest latency)
Cache invalidation broadcast      │ Redis pub/sub (fire-and-forget, fanout)
Real-time websocket fanout        │ Redis pub/sub
Critical business events          │ Kafka (durable, ordered, at-least-once)
Event sourcing / audit log        │ Kafka (persistent, replayable)
Multiple consumers sharing work   │ Kafka (consumer groups)
Low-latency notification (ok if   │ Redis pub/sub
  occasionally lost)              │
High-volume transactional events  │ Kafka

Conclusion: 'use Kafka for everything' adds operational cost and complexity
where simpler transports are sufficient. Right answer: match transport to
the durability, ordering, and fan-out requirements of each specific event.
```

## Quick Reference Table

| Concept | TCP | Redis | Kafka |
|---|---|---|---|
| Persistence | None | None | Configurable (retention policy) |
| Fan-out | No (point-to-point) | All current subscribers | Per consumer group |
| Load balancing | Manual (external LB) | None (all instances get all) | Automatic (partition assignment) |
| Ordering | N/A | None | Per partition / key |
| Replay | No | No | Yes (seek to offset) |
| Delivery guarantee | At-most-once | At-most-once | At-least-once |
| Ops complexity | Minimal | Low | High |
| Good for | Internal RPC, dev | Cache invalidation, fanout | Durable event streams |

| Pattern | API | Usage |
|---|---|---|
| Request-response | `client.send(pattern, data)` | Query, command with confirmation |
| Event (fire & forget) | `client.emit(event, data)` | Audit log, notification, cache bust |
| Extract value from Observable | `firstValueFrom(observable)` | Await single reply in async/await code |
| Timeout on send | `.pipe(timeout(ms))` | Prevent indefinite hang if service is down |
| Structured error from handler | `throw new RpcException({...})` | Send structured error back to client |
| Catch RPC error on client | `.pipe(catchError(...))` | Handle structured RpcException |
| Manual Kafka offset commit | `consumer.commitOffsets([...])` | At-least-once with manual control |
| Partition key | `emit(topic, { key, value })` | Order related messages on same partition |
| Global pipe in microservice | `app.useGlobalPipes(new ValidationPipe())` | Validate @Payload() across all handlers |
| Global filter in microservice | `app.useGlobalFilters(new Filter())` | Catch and format all RPC errors |

**Tip for interviews:** Five things separate strong candidates on NestJS microservices: (1) understanding the **two communication patterns** and their RxJS mechanics (Q2) — knowing that `client.send()` returns a cold Observable that only opens a connection when subscribed, and using `firstValueFrom()` to bridge into async/await, rather than thinking of it as a Promise; (2) knowing **why Redis pub/sub loses messages** when consumers are down and being able to articulate when that matters vs when it doesn't (Q8) — distinguishing it from Redis Streams and Kafka is a concrete systems knowledge signal; (3) explaining **Kafka partition mechanics** from first principles — partition count bounds concurrency, key-based routing ensures ordering, consumer groups enable exactly-one-per-group delivery (Q10, Q12) — and knowing the practical implication that repartitioning breaks key routing for existing messages (Q19); (4) implementing **manual offset commits and the DLQ pattern** (Q13, Q14) — showing you understand the failure modes of at-least-once delivery and how to handle poison messages without halting the consumer; and (5) being able to **evaluate transport tradeoffs honestly** (Q20) — not "Kafka is always better" but matching durability, ordering, fan-out, and operational cost requirements to the right transport per use case.
