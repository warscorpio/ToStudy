# NestJS Middleware vs Guards vs Interceptors vs Pipes — Execution Order: Interview Q&A (5 YOE Level)

---

## Section 1: The Full Request Lifecycle

**Q1. What is the complete NestJS request/response pipeline — in exact order?**

A: NestJS processes every incoming request through a fixed sequence of pipeline stages. Each stage has a distinct responsibility and a different mechanism for stopping or modifying the flow:

```
Incoming HTTP Request
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│  1. MIDDLEWARE  (app.use / @Module forRoutes)                 │
│     • Runs before everything else                             │
│     • Access: raw request/response objects                    │
│     • Can terminate response OR call next()                   │
│     • No access to NestJS DI context (unless injected)        │
│     • Compatible with Express / Fastify middleware             │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│  2. GUARDS  (canActivate)                                     │
│     • Determines if the request is AUTHORISED to proceed      │
│     • First NestJS-native stage (has ExecutionContext)        │
│     • Returns true (proceed) or false / throws (reject)       │
│     • Does NOT transform data                                 │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│  3. INTERCEPTORS — before phase  (next.handle() not yet called)│
│     • Runs synchronously before the handler                   │
│     • Can short-circuit (skip handler entirely)               │
│     • Records start time, checks cache, starts timers         │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│  4. PIPES  (transform / validate)                             │
│     • Runs per route parameter, per @Body / @Query / @Param   │
│     • Validates and/or transforms incoming data               │
│     • Throws BadRequestException on validation failure        │
│     • Does NOT see the response — only sees input             │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│  5. ROUTE HANDLER  (controller method)                        │
│     • Executes business logic                                 │
│     • Returns data or throws an exception                     │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│  6. INTERCEPTORS — after phase  (.pipe() operators)           │
│     • Runs after handler returns                              │
│     • Transforms response, logs latency, stores cache         │
│     • Executes in REVERSE registration order                  │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│  7. EXCEPTION FILTERS  (catch)                                │
│     • ONLY runs when an error is thrown anywhere above        │
│     • Catches exceptions from guards, pipes, interceptors,    │
│       and handlers                                            │
│     • Shapes the error response sent to the client            │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
   Response to Client
```

The essential one-liner for each stage:

```typescript
// Middleware  → "Can this request reach NestJS at all?" (raw, pre-NestJS)
// Guard       → "Is this request allowed to hit this handler?" (auth/authz)
// Interceptor → "Wrap the handler — run before AND after it"
// Pipe        → "Is this parameter valid and correctly typed?"
// Filter      → "If something threw, what should the client receive?"
```

**Q2. Show me the exact lifecycle in running code — all stages active at once.**

A: The clearest way to see ordering is to wire all five stages on a single route and trace the console output:

```typescript
// middleware/logger.middleware.ts
import { Injectable, NestMiddleware } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';

@Injectable()
export class LoggerMiddleware implements NestMiddleware {
    use(req: Request, res: Response, next: NextFunction) {
        console.log('1. MIDDLEWARE — before next()');
        next(); // ← Must call next() or the request hangs
        // Note: code after next() runs after next() returns synchronously,
        // but the response may already be committed by then.
        // Middleware cannot hook the RESPONSE body reliably — use interceptors for that.
        console.log('1. MIDDLEWARE — after next() (response may already be sent)');
    }
}

// guards/auth.guard.ts
import { Injectable, CanActivate, ExecutionContext } from '@nestjs/common';
import { Observable } from 'rxjs';

@Injectable()
export class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean> {
        console.log('2. GUARD — canActivate');
        // Return false or throw ForbiddenException to reject the request here.
        // The interceptor, pipe, and handler will NEVER run if this returns false.
        return true;
    }
}

// interceptors/lifecycle.interceptor.ts
import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from '@nestjs/common';
import { Observable } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class LifecycleInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        console.log('3. INTERCEPTOR — before phase (before next.handle())');

        return next.handle().pipe(
            tap(data => {
                // This runs AFTER the handler returns:
                console.log('6. INTERCEPTOR — after phase (after handler)', data);
            }),
        );
    }
}

// pipes/parse-int.pipe.ts
import { PipeTransform, Injectable, ArgumentMetadata, BadRequestException } from '@nestjs/common';

@Injectable()
export class LoggingParseIntPipe implements PipeTransform<string, number> {
    transform(value: string, metadata: ArgumentMetadata): number {
        console.log('4. PIPE — transform/validate param:', metadata.data, '=', value);
        const parsed = parseInt(value, 10);
        if (isNaN(parsed)) throw new BadRequestException(`${value} is not a number`);
        return parsed;
    }
}

// filters/http-exception.filter.ts
import { ExceptionFilter, Catch, ArgumentsHost, HttpException } from '@nestjs/common';
import { Response } from 'express';

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
    catch(exception: HttpException, host: ArgumentsHost) {
        // Only runs when something THROWS — guards, pipes, interceptors, or handler.
        console.log('7. EXCEPTION FILTER — caught:', exception.message);
        const ctx = host.switchToHttp();
        ctx.getResponse<Response>().status(exception.getStatus()).json({
            error: exception.message,
        });
    }
}

// Controller wiring everything together:
@Controller('demo')
@UseGuards(AuthGuard)
@UseInterceptors(LifecycleInterceptor)
@UseFilters(HttpExceptionFilter)
export class DemoController {
    @Get(':id')
    findOne(@Param('id', LoggingParseIntPipe) id: number) {
        console.log('5. HANDLER — executing with id:', id);
        return { id };
    }
}

// Console output for GET /demo/42:
// 1. MIDDLEWARE — before next()
// 2. GUARD — canActivate
// 3. INTERCEPTOR — before phase (before next.handle())
// 4. PIPE — transform/validate param: id = 42
// 5. HANDLER — executing with id: 42
// 6. INTERCEPTOR — after phase (after handler) { id: 42 }
// 1. MIDDLEWARE — after next() (response may already be sent)
```

## Section 2: Middleware

**Q3. What is middleware in NestJS and what can it uniquely do that other pipeline stages cannot?**

A: NestJS middleware is functionally identical to Express middleware — it is a function that sits between the raw HTTP request and the NestJS execution context. Its unique position means it runs before NestJS has parsed the route or resolved the handler:

```typescript
// Two forms: functional and class-based

// ── Functional middleware (no DI) ─────────────────────────────────────────────
import { Request, Response, NextFunction } from 'express';

export function corsMiddleware(req: Request, res: Response, next: NextFunction) {
    res.header('Access-Control-Allow-Origin', '*');
    next(); // MUST call next() or the request stalls
}

// ── Class-based middleware (supports DI) ──────────────────────────────────────
@Injectable()
export class AuthTokenMiddleware implements NestMiddleware {
    constructor(private readonly jwtService: JwtService) {} // DI works

    use(req: Request, res: Response, next: NextFunction) {
        const token = req.headers.authorization?.replace('Bearer ', '');
        if (token) {
            try {
                // Attach decoded user to request so guards can read it:
                (req as any).user = this.jwtService.verify(token);
            } catch {
                // Token invalid — don't throw here, let the guard reject it.
                // Middleware throwing terminates the request without a clean error shape.
            }
        }
        next(); // Always call next() — middleware decides routing, not auth.
    }
}

// ── Registration — in a Module, not main.ts ───────────────────────────────────
@Module({})
export class AppModule implements NestModule {
    configure(consumer: MiddlewareConsumer) {
        consumer
            .apply(AuthTokenMiddleware)
            .forRoutes('*');           // All routes

        consumer
            .apply(LoggerMiddleware)
            .forRoutes(               // Specific routes:
                { path: 'users', method: RequestMethod.GET },
                { path: 'products', method: RequestMethod.ALL },
                UserController,       // All routes in a controller
            );

        consumer
            .apply(RateLimitMiddleware)
            .exclude(
                { path: 'health', method: RequestMethod.GET }, // Skip health checks
            )
            .forRoutes('*');
    }
}

// ── What middleware CAN do that other stages cannot ───────────────────────────
// 1. Use any Express/Fastify ecosystem middleware directly:
consumer.apply(helmet(), compression(), morgan('combined')).forRoutes('*');

// 2. Terminate the response without entering NestJS at all:
export function maintenanceMiddleware(req: Request, res: Response, next: NextFunction) {
    if (process.env.MAINTENANCE_MODE === 'true') {
        res.status(503).json({ message: 'Service temporarily unavailable' });
        return; // next() NOT called — NestJS never sees this request
    }
    next();
}

// 3. Mutate the raw request before NestJS parses it:
export function requestIdMiddleware(req: Request, res: Response, next: NextFunction) {
    (req as any).id = crypto.randomUUID(); // Attach before NestJS routing
    res.setHeader('X-Request-Id', (req as any).id);
    next();
}

// ── What middleware CANNOT do ─────────────────────────────────────────────────
// ✗ Access handler metadata (no Reflector, no @SetMetadata)
// ✗ Know which controller/handler will handle the request (no ExecutionContext)
// ✗ Intercept the response body (next() is synchronous in Express middleware)
// ✗ Run after the handler — for that, use interceptors
```

**Q4. What is the critical difference between middleware `next()` and interceptor `next.handle()`?**

A: They look similar but behave completely differently — confusing them is a very common interview mistake:

```typescript
// ── Middleware next() ─────────────────────────────────────────────────────────
// next() is a plain Express callback.
// It tells Express to move to the next middleware or route handler.
// It is SYNCHRONOUS — it does not return a Promise or Observable.
// Code after next() runs, but the response may already be committed.

export function middlewareExample(req: Request, res: Response, next: NextFunction) {
    console.log('A'); // Runs first
    next();           // Hands control to next middleware / NestJS pipeline
    console.log('B'); // Runs after next() returns — but response may be sent by now
    // 'B' always runs; it is not an "after phase" — it is just the next line of code.
    // You CANNOT reliably read the response body here.
}

// ── Interceptor next.handle() ─────────────────────────────────────────────────
// next.handle() returns an Observable<T>.
// Subscribing to it (via .pipe() or returning it) invokes the handler.
// Code in .pipe() operators runs AFTER the handler emits a value.
// This is a true two-phase wrap — the after phase is guaranteed to see response data.

@Injectable()
export class InterceptorExample implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        console.log('A'); // Before phase — handler not yet called

        return next.handle().pipe(
            tap(data => {
                console.log('B', data); // After phase — handler has returned data
                // data IS the response body — you CAN read and transform it
            }),
        );
        // If you never call next.handle(), the handler never executes — intentional for caching.
    }
}

// ── Side-by-side comparison ───────────────────────────────────────────────────
// Feature                   Middleware next()       Interceptor next.handle()
// ─────────────────────────────────────────────────────────────────────────────
// Returns                   void                    Observable<T>
// After-phase access        No (timing unreliable)  Yes (guaranteed)
// Can skip handler          Yes (don't call next()) Yes (don't call next.handle())
// Can read response body    No                      Yes (via operators)
// Can transform response    No                      Yes (via map())
// Async support             Callback-based          Native (RxJS / Promise)
```

## Section 3: Guards

**Q5. What is a guard, when does it run, and how does it differ from middleware for authentication?**

A: Guards answer a single question: "Should this request be allowed to proceed to the handler?" They are the correct place for authentication and authorisation — not middleware:

```typescript
import {
    Injectable, CanActivate, ExecutionContext,
    UnauthorizedException, ForbiddenException,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { JwtService } from '@nestjs/jwt';
import { Observable } from 'rxjs';
import { Request } from 'express';

// ── Simple JWT auth guard ─────────────────────────────────────────────────────
@Injectable()
export class JwtAuthGuard implements CanActivate {
    constructor(private readonly jwtService: JwtService) {}

    canActivate(context: ExecutionContext): boolean {
        const request = context.switchToHttp().getRequest<Request>();
        const token   = request.headers.authorization?.replace('Bearer ', '');

        if (!token) {
            throw new UnauthorizedException('No token provided');
            // Throwing is preferred over returning false:
            // - false sends 403 Forbidden (generic)
            // - throwing lets you send 401 Unauthorized with a message
        }

        try {
            const payload   = this.jwtService.verify(token);
            request.user    = payload; // Attach for downstream use
            return true;
        } catch {
            throw new UnauthorizedException('Invalid or expired token');
        }
    }
}

// ── Role-based authorisation guard (uses Reflector for metadata) ───────────────
export const Roles = (...roles: string[]) => SetMetadata('roles', roles);
export const Public = () => SetMetadata('isPublic', true);

@Injectable()
export class RolesGuard implements CanActivate {
    constructor(private readonly reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        // Check if the route is marked as public — skip auth entirely:
        const isPublic = this.reflector.getAllAndOverride<boolean>('isPublic', [
            context.getHandler(),
            context.getClass(),
        ]);
        if (isPublic) return true;

        // Read required roles from handler or controller metadata:
        const requiredRoles = this.reflector.getAllAndOverride<string[]>('roles', [
            context.getHandler(), // Handler metadata takes precedence
            context.getClass(),   // Controller metadata as fallback
        ]);

        if (!requiredRoles?.length) return true; // No role restriction

        const request = context.switchToHttp().getRequest();
        const user    = request.user; // Set by JwtAuthGuard earlier

        if (!user) throw new UnauthorizedException();

        const hasRole = requiredRoles.some(role => user.roles?.includes(role));
        if (!hasRole) {
            throw new ForbiddenException(
                `Requires one of [${requiredRoles.join(', ')}], user has [${user.roles}]`
            );
        }
        return true;
    }
}

// ── Async guard — guard can return a Promise ──────────────────────────────────
@Injectable()
export class ApiKeyGuard implements CanActivate {
    constructor(private readonly apiKeyService: ApiKeyService) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        const request = context.switchToHttp().getRequest<Request>();
        const apiKey  = request.headers['x-api-key'] as string;

        if (!apiKey) throw new UnauthorizedException('API key required');

        // Async DB lookup — guard awaits it:
        const isValid = await this.apiKeyService.validate(apiKey);
        if (!isValid) throw new UnauthorizedException('Invalid API key');

        return true;
    }
}

// ── Registration scopes ───────────────────────────────────────────────────────

// Global (every route):
app.useGlobalGuards(new JwtAuthGuard(jwtService)); // No DI
// OR (with DI — preferred):
@Module({
    providers: [{ provide: APP_GUARD, useClass: JwtAuthGuard }],
})
export class AppModule {}

// Controller-level (all routes in controller):
@Controller('admin')
@UseGuards(JwtAuthGuard, RolesGuard)
export class AdminController {}

// Route-level (one endpoint):
@Get('secret')
@UseGuards(JwtAuthGuard)
getSecret() {}

// ── Why guards, not middleware, for auth ──────────────────────────────────────
// Middleware             │  Guard
// ──────────────────────┼───────────────────────────────────────────────────
// No ExecutionContext    │  Full ExecutionContext (handler, class, metadata)
// No Reflector access   │  Can read @SetMetadata() decorators
// Runs before all stages│  Runs after middleware — can use decoded user from middleware
// Cannot know handler   │  Knows exactly which handler will run
// Cannot use DI easily  │  Full DI support (inject repositories, services)
```

**Q6. What happens to the pipeline when a guard returns `false` vs throws an exception?**

A: The behaviour differs subtly — and knowing this distinction matters in production:

```typescript
@Injectable()
export class DemoGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean {
        const allowed = false;

        // ── Option A: return false ────────────────────────────────────────────
        // NestJS internally throws a ForbiddenException (403).
        // The exception filter chain is triggered.
        // The interceptor after-phase does NOT run.
        // Response: { "statusCode": 403, "message": "Forbidden", "error": "Forbidden" }
        if (!allowed) return false;

        // ── Option B: throw an exception ─────────────────────────────────────
        // The specific exception you throw determines the status code and message.
        // The exception filter chain is triggered.
        // The interceptor after-phase does NOT run.
        // Preferred — gives you control over the error response.
        if (!allowed) throw new UnauthorizedException('Token expired');

        // ── Option C: return true ─────────────────────────────────────────────
        // Pipeline continues to next guard → interceptors → pipes → handler.
        return true;
    }
}

// Key fact for interviews:
// When a guard rejects (return false OR throws):
//   ✓ Subsequent guards       → DO NOT run
//   ✓ Interceptors (before)   → DO NOT run (handler never reached)
//   ✓ Pipes                   → DO NOT run
//   ✓ Route handler           → DOES NOT run
//   ✓ Interceptors (after)    → DO NOT run (no Observable was returned)
//   ✓ Exception filters       → DO run (they catch everything)
//
// This is critical: if your LoggingInterceptor records every request,
// REJECTED requests (by guards) will NOT appear in interceptor logs.
// To log rejected auth attempts, log inside the guard or use middleware.

@Injectable()
export class AuditGuard implements CanActivate {
    constructor(
        private readonly logger: Logger,
        private readonly jwtService: JwtService,
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        const request = context.switchToHttp().getRequest<Request>();
        const token   = request.headers.authorization?.replace('Bearer ', '');

        try {
            const payload = this.jwtService.verify(token!);
            request.user  = payload;
            this.logger.log(`Auth success: user ${payload.sub}`); // Log success here
            return true;
        } catch (err) {
            // Log the rejection IN the guard — the interceptor won't see this:
            this.logger.warn(`Auth failed: ${err.message}`, { ip: request.ip });
            throw new UnauthorizedException('Authentication failed');
        }
    }
}
```

## Section 4: Pipes

**Q7. Where exactly in the pipeline do pipes run, and what distinguishes them from interceptors for data transformation?**

A: Pipes run after guards and the interceptor before-phase, but before the handler executes. Their scope is narrow and precise — they operate per-parameter, not per-request:

```typescript
import {
    PipeTransform, Injectable, ArgumentMetadata,
    BadRequestException, ParseIntPipe,
} from '@nestjs/common';

// ── Pipe fundamentals ─────────────────────────────────────────────────────────
// A pipe receives ONE parameter value and returns the transformed value.
// It knows WHICH parameter it is processing via ArgumentMetadata.
// It does NOT see other parameters, the response, or the handler's return value.

@Injectable()
export class TrimStringPipe implements PipeTransform<string, string> {
    transform(value: string, metadata: ArgumentMetadata): string {
        // metadata.type    → 'body' | 'query' | 'param' | 'custom'
        // metadata.metatype → the TypeScript type (String, Number, UserDto, etc.)
        // metadata.data    → the decorator argument ('@Param('id')' → data = 'id')

        console.log('PIPE — processing:', metadata.type, metadata.data, '=', value);

        if (typeof value !== 'string') return value;
        return value.trim();
    }
}

// ── Where pipes are applied ───────────────────────────────────────────────────
@Controller('users')
export class UserController {
    // Param-level: only this parameter is piped
    @Get(':id')
    findOne(@Param('id', ParseIntPipe) id: number) {
        // ParseIntPipe transforms '42' → 42, throws BadRequestException for 'abc'
        return this.userService.findById(id);
    }

    // Multiple pipes on one parameter: applied left to right
    @Get('search')
    search(@Query('q', TrimStringPipe, new DefaultValuePipe('*')) q: string) {
        // 1. TrimStringPipe runs first: '  hello  ' → 'hello'
        // 2. DefaultValuePipe runs second: undefined → '*'
        return this.userService.search(q);
    }

    // Body-level: pipes the entire body (commonly for DTO validation)
    @Post()
    create(@Body(new ValidationPipe({ whitelist: true })) dto: CreateUserDto) {
        // ValidationPipe validates the entire DTO against class-validator decorators
        return this.userService.create(dto);
    }
}

// ── Global pipe registration ──────────────────────────────────────────────────
// In main.ts:
app.useGlobalPipes(new ValidationPipe({
    whitelist: true,          // Strip unknown properties
    forbidNonWhitelisted: true, // Throw if unknown properties sent
    transform: true,          // Auto-transform to declared types
    transformOptions: {
        enableImplicitConversion: true, // '42' → 42 for @Param() without ParseIntPipe
    },
}));

// ── Custom validation pipe ────────────────────────────────────────────────────
@Injectable()
export class ParsePositiveIntPipe implements PipeTransform<string, number> {
    transform(value: string, metadata: ArgumentMetadata): number {
        const parsed = parseInt(value, 10);

        if (isNaN(parsed)) {
            throw new BadRequestException(
                `Validation failed: '${value}' is not a number (param: ${metadata.data})`
            );
        }
        if (parsed <= 0) {
            throw new BadRequestException(
                `Validation failed: '${value}' must be a positive integer (param: ${metadata.data})`
            );
        }
        return parsed;
    }
}

// ── Pipe vs Interceptor for transformation — the key distinction ──────────────
//
// Use a PIPE when:
//   • You are validating/transforming INPUT (request data) before the handler
//   • The scope is a single parameter (@Param, @Body, @Query)
//   • A bad value should throw BadRequestException (400)
//   • Example: parse ':id' to a number, validate a DTO, trim whitespace
//
// Use an INTERCEPTOR when:
//   • You are transforming OUTPUT (response data) after the handler
//   • The scope is the entire request/response cycle
//   • You need both before AND after handler access
//   • Example: wrap response in { success, data }, strip sensitive fields

// ── Execution order of multiple global pipes ──────────────────────────────────
// Global pipes run BEFORE controller/method-level pipes.
// For @Body(): global ValidationPipe runs, then any param-level pipes.
// For @Param(':id', ParseIntPipe): global pipes run first, then ParseIntPipe.
```

**Q8. How does `ValidationPipe` fit into the pipeline, and what happens when validation fails?**

A: `ValidationPipe` is a built-in pipe that uses `class-validator` and `class-transformer` under the hood. When it fails, it throws a `BadRequestException` — which then propagates to exception filters:

```typescript
import { IsEmail, IsString, MinLength, IsOptional, IsInt, Min } from 'class-validator';
import { Type } from 'class-transformer';

export class CreateUserDto {
    @IsEmail()
    email: string;

    @IsString()
    @MinLength(8)
    password: string;

    @IsOptional()
    @IsString()
    name?: string;

    @IsOptional()
    @IsInt()
    @Min(0)
    @Type(() => Number) // Needed when transform: true is not set
    age?: number;
}

// What happens when POST /users receives { email: 'not-an-email', password: '123' }:
//
// 1. Middleware runs       → passes through
// 2. Guard runs            → passes through (or not present)
// 3. Interceptor (before)  → passes through
// 4. ValidationPipe runs   → THROWS BadRequestException:
//    {
//      "statusCode": 400,
//      "message": [
//        "email must be an email",
//        "password must be longer than or equal to 8 characters"
//      ],
//      "error": "Bad Request"
//    }
// 5. Route Handler         → NEVER RUNS
// 6. Interceptor (after)   → NEVER RUNS (exception was thrown)
// 7. Exception Filter      → catches BadRequestException, shapes the 400 response

// ── ValidationPipe options that affect pipeline behaviour ─────────────────────
app.useGlobalPipes(new ValidationPipe({
    whitelist: true,
    // Strips properties not in the DTO silently — never reaches the handler.
    // { email, password, maliciousField } → { email, password }

    forbidNonWhitelisted: true,
    // Instead of stripping, THROWS BadRequestException if unknown property sent.
    // Stricter than whitelist alone.

    transform: true,
    // Transforms the plain JSON body into the DTO class instance.
    // Without this, dto is a plain object — class-validator works but class methods don't.
    // Also converts ':id' string → number if the DTO param is typed as number.

    exceptionFactory: (errors) => {
        // Customise the error response shape:
        const messages = errors.flatMap(e => Object.values(e.constraints ?? {}));
        return new BadRequestException({
            statusCode: 400,
            message: messages,
            error: 'Validation Error',
        });
    },

    disableErrorMessages: process.env.NODE_ENV === 'production',
    // In production, don't leak field names in validation errors.
}));
```

## Section 5: Exception Filters

**Q9. Where do exception filters sit in the pipeline — what can and cannot throw into them?**

A: Exception filters are the last line of defence. They catch exceptions thrown at ANY earlier stage — but they only activate on errors, not on successful requests:

```typescript
import {
    ExceptionFilter, Catch, ArgumentsHost,
    HttpException, HttpStatus,
    NotFoundException, BadRequestException,
} from '@nestjs/common';
import { Request, Response } from 'express';

// ── Catch all HttpExceptions ──────────────────────────────────────────────────
@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
    constructor(private readonly logger: Logger) {}

    catch(exception: HttpException, host: ArgumentsHost) {
        const ctx      = host.switchToHttp();
        const response = ctx.getResponse<Response>();
        const request  = ctx.getRequest<Request>();
        const status   = exception.getStatus();
        const body     = exception.getResponse();

        this.logger.error({
            message:    'HTTP Exception',
            status,
            path:       request.url,
            method:     request.method,
            error:      body,
        });

        response.status(status).json(
            typeof body === 'object'
                ? { ...body as object, timestamp: new Date().toISOString(), path: request.url }
                : { message: body, statusCode: status, path: request.url }
        );
    }
}

// ── Catch everything (including non-HTTP errors) ───────────────────────────────
@Catch() // No argument = catch ALL exceptions
export class AllExceptionsFilter implements ExceptionFilter {
    catch(exception: unknown, host: ArgumentsHost) {
        const ctx      = host.switchToHttp();
        const response = ctx.getResponse<Response>();
        const request  = ctx.getRequest<Request>();

        let status  = HttpStatus.INTERNAL_SERVER_ERROR;
        let message = 'Internal server error';

        if (exception instanceof HttpException) {
            status  = exception.getStatus();
            message = exception.message;
        } else if (exception instanceof Error) {
            // Database errors, network errors, etc. — not HttpExceptions:
            message = exception.message;
            // Log full stack trace for non-HTTP errors:
            console.error('Unhandled exception:', exception.stack);
        }

        response.status(status).json({ statusCode: status, message, path: request.url });
    }
}

// ── What CAN throw into exception filters ─────────────────────────────────────
// • Middleware (if it throws — not just calls next(error))
// • Guards (return false → 403; throw → whatever you throw)
// • Interceptors before-phase (throw in the code before next.handle())
// • Pipes (throw BadRequestException on validation failure)
// • Route handlers (throw any HttpException or unknown error)
// • Interceptors after-phase (throw or catchError re-throws in .pipe())

// ── What does NOT throw into exception filters ────────────────────────────────
// • Errors thrown AFTER the response is sent (e.g., in a tap() side-effect)
//   These become UnhandledPromiseRejections — the filter cannot catch them
// • Errors in finalize() — these are swallowed by RxJS
// • Errors in app lifecycle hooks (OnModuleInit, OnApplicationBootstrap)

// ── Registration — same four scopes as everything else ────────────────────────
// Global:
app.useGlobalFilters(new AllExceptionsFilter());
// OR with DI:
@Module({
    providers: [{ provide: APP_FILTER, useClass: AllExceptionsFilter }],
})
export class AppModule {}

// Controller-level:
@Controller('payments')
@UseFilters(HttpExceptionFilter)
export class PaymentController {}

// Route-level:
@Post('charge')
@UseFilters(new HttpExceptionFilter())
chargeCard() {}

// ── Multiple filters: execution order ─────────────────────────────────────────
// @UseFilters(FilterA, FilterB) — FilterA is tried first.
// The MOST SPECIFIC filter that matches the exception type wins.
// @Catch(NotFoundException) takes priority over @Catch(HttpException)
// @Catch(HttpException) takes priority over @Catch() (catch-all).
```

## Section 6: Execution Order Deep Dives

**Q10. What is the exact order when multiple guards, interceptors, and pipes are stacked?**

A: When you have multiple instances of the same stage, there are specific ordering rules — and the before/after phases for interceptors add another layer:

```typescript
// ── Multiple guards: left-to-right, first failure stops the chain ─────────────
@Controller('admin')
@UseGuards(JwtAuthGuard, SubscriptionGuard, RolesGuard)
// Order: JwtAuthGuard → SubscriptionGuard → RolesGuard
// If JwtAuthGuard throws UnauthorizedException:
//   → SubscriptionGuard DOES NOT run
//   → RolesGuard        DOES NOT run
//   → Pipeline stops at first failing guard
export class AdminController {}

// ── Multiple interceptors: onion model ────────────────────────────────────────
@UseInterceptors(TimeoutInterceptor, LoggingInterceptor, CacheInterceptor)
// BEFORE phase (left to right):
//   TimeoutInterceptor before → LoggingInterceptor before → CacheInterceptor before → HANDLER
//
// AFTER phase (right to left — reverse):
//   HANDLER → CacheInterceptor after → LoggingInterceptor after → TimeoutInterceptor after
//
// Think of it as nested function calls:
// timeout(logging(cache(handler())))
// Outer wraps inner — TimeoutInterceptor wraps everything.

// Concrete example showing the nesting:
@Injectable()
export class OuterInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        console.log('OUTER — before');
        return next.handle().pipe(
            tap(() => console.log('OUTER — after')),
        );
    }
}

@Injectable()
export class InnerInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        console.log('INNER — before');
        return next.handle().pipe(
            tap(() => console.log('INNER — after')),
        );
    }
}

@Get()
@UseInterceptors(OuterInterceptor, InnerInterceptor)
findAll() {
    console.log('HANDLER');
    return [];
}

// Output:
// OUTER — before
// INNER — before
// HANDLER
// INNER — after     ← reverse order in after phase
// OUTER — after

// ── Multiple pipes on one parameter: left-to-right ────────────────────────────
@Get(':id')
findOne(
    @Param(
        'id',
        new ParseIntPipe(),          // Runs first: '42' → 42
        new ParsePositiveIntPipe(),  // Runs second: receives 42 (number, not string)
    )
    id: number,
) {}
// ParseIntPipe converts, ParsePositiveIntPipe validates the converted value.

// ── Global vs controller vs route scope ordering ──────────────────────────────
// For guards:       Global → Controller → Route (left to right within each scope)
// For interceptors: Global → Controller → Route (left to right within each scope)
//                   After phase: Route → Controller → Global (full reverse)
// For pipes:        Global → Controller → Route → Param (left to right)
// For filters:      Route → Controller → Global (most specific first)
//
// Note: Filters are the OPPOSITE of guards/interceptors —
// the most specific (narrowest scope) filter is tried first.

// ── Visualising the full order with all scopes ────────────────────────────────
// Guards:       GlobalGuard → ControllerGuard → RouteGuard
// Interceptors (before): GlobalI → ControllerI → RouteI → HANDLER
// Pipes:        GlobalPipe → ControllerPipe → RoutePipe → ParamPipe
// Handler:      executes
// Interceptors (after): RouteI → ControllerI → GlobalI
// Filters (on error): RouteFilter → ControllerFilter → GlobalFilter
```

**Q11. What happens to the pipeline when an exception is thrown at each stage?**

A: The pipeline short-circuits differently depending on where the exception originates. Knowing exactly what runs and what doesn't at each failure point is critical:

```typescript
// ── Exception in MIDDLEWARE ────────────────────────────────────────────────────
// If middleware throws (not calls next(err)):
//   → NestJS exception filters are NOT triggered (middleware is outside NestJS)
//   → Express default error handler catches it (sends HTML error page)
//   → All subsequent pipeline stages DO NOT run
//
// Correct pattern — pass errors through next() for Express error handling:
export function riskyMiddleware(req: Request, res: Response, next: NextFunction) {
    try {
        const result = doSomethingRisky();
        next();
    } catch (err) {
        next(err); // ← Pass to Express error handler — NOT NestJS filters
        // For NestJS exception filters to catch it, the error must come from
        // inside the NestJS pipeline (guard, pipe, interceptor, handler).
    }
}

// ── Exception in GUARD ────────────────────────────────────────────────────────
// If guard throws:
//   → Subsequent guards          → DO NOT run
//   → Interceptors (before)      → DO NOT run
//   → Pipes                      → DO NOT run
//   → Handler                    → DOES NOT run
//   → Interceptors (after phase) → DO NOT run
//   → Exception filters          → RUN (catch the guard's exception)

// ── Exception in INTERCEPTOR (before phase) ───────────────────────────────────
// If interceptor throws before calling next.handle():
//   → next.handle() (handler)         → DOES NOT run
//   → Interceptor's own after phase   → DOES NOT run
//   → Subsequent interceptors         → DO NOT run
//   → Exception filters               → RUN

// ── Exception in PIPE ─────────────────────────────────────────────────────────
// If pipe throws BadRequestException:
//   → Handler                    → DOES NOT run
//   → Interceptors (after phase) → DO NOT run
//   → Exception filters          → RUN (catch the pipe's exception)

// ── Exception in HANDLER ──────────────────────────────────────────────────────
// If handler throws:
//   → Interceptors (after phase) → PARTIALLY run:
//        tap(next, error) → fires for error
//        catchError()     → can catch and transform
//        finalize()       → ALWAYS runs (success or error)
//        map()            → does NOT run (no value emitted)
//   → Exception filters          → RUN (unless catchError re-emits a value)

// ── Exception in INTERCEPTOR (after phase) ────────────────────────────────────
// If an operator in .pipe() throws:
//   → catchError() in the same interceptor can catch it
//   → If uncaught, it propagates to outer interceptors' catchError()
//   → Finally, exception filters catch it

// ── Demonstrating which phases run using finalize ─────────────────────────────
@Injectable()
export class ObservabilityInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        const start = Date.now();

        return next.handle().pipe(
            tap({
                next:     (data) => console.log('Success:', data),    // Only on success
                error:    (err)  => console.log('Error:', err.message), // Only on error
                complete: ()     => console.log('Complete'),           // After next
            }),
            catchError(err => {
                // Can transform the error here:
                if (err.name === 'QueryFailedError') {
                    return throwError(() => new InternalServerErrorException('DB error'));
                }
                return throwError(() => err); // Re-throw unchanged
            }),
            finalize(() => {
                // ALWAYS runs — use for cleanup and metrics:
                console.log(`Duration: ${Date.now() - start}ms`);
            }),
        );
    }
}
```

## Section 7: Choosing the Right Stage

**Q12. Given a requirement, which pipeline stage should you use — and why?**

A: Most interview scenarios come down to "why not X?" as much as "why Y?". Here is the decision logic for common requirements:

```typescript
// ── Scenario 1: Attach a request ID to every request ──────────────────────────
// ✓ MIDDLEWARE — runs before everything, can attach to the raw request object
//   before NestJS sees it. No need for handler metadata.
export function requestIdMiddleware(req: Request, res: Response, next: NextFunction) {
    (req as any).id = crypto.randomUUID();
    res.setHeader('X-Request-Id', (req as any).id);
    next();
}
// ✗ Guard     — guards are for auth decisions, not request enrichment
// ✗ Interceptor — could work but middleware is simpler and runs earlier

// ── Scenario 2: Block unauthenticated users ────────────────────────────────────
// ✓ GUARD — designed exactly for this. Has ExecutionContext, can read @Public() metadata.
@Injectable()
export class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean {
        return !!context.switchToHttp().getRequest().user;
    }
}
// ✗ Middleware — no access to handler metadata (can't check @Public())
// ✗ Interceptor — runs after guards; semantically wrong (auth ≠ transformation)

// ── Scenario 3: Validate request body ─────────────────────────────────────────
// ✓ PIPE (ValidationPipe) — per-parameter, throws 400, transforms to class instance
@Post()
create(@Body(new ValidationPipe({ whitelist: true })) dto: CreateUserDto) {}
// ✗ Guard     — guards should only make pass/fail decisions, not validate shape
// ✗ Interceptor — interceptors run after guards and before pipes; transforming
//                 in the before phase is possible but ValidationPipe is the idiom

// ── Scenario 4: Wrap every response in { success: true, data: ... } ───────────
// ✓ INTERCEPTOR (map) — after-phase access to the handler's return value
@Injectable()
export class TransformInterceptor implements NestInterceptor {
    intercept(ctx: ExecutionContext, next: CallHandler): Observable<any> {
        return next.handle().pipe(map(data => ({ success: true, data })));
    }
}
// ✗ Middleware — cannot see or modify the response body
// ✗ Pipe      — only processes input, not output

// ── Scenario 5: Strip sensitive fields before sending response ─────────────────
// ✓ INTERCEPTOR (map + plainToInstance) — transforms the outgoing value
// ✓ OR: ClassSerializerInterceptor with @Exclude() on entity fields
// ✗ Pipe — pipes run before the handler, not after; they cannot see the response

// ── Scenario 6: Log request + response with timing ────────────────────────────
// ✓ INTERCEPTOR — only stage with both before AND after phases and response access
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
    intercept(ctx: ExecutionContext, next: CallHandler): Observable<any> {
        const start = Date.now();
        return next.handle().pipe(
            finalize(() => console.log(`${Date.now() - start}ms`)),
        );
    }
}
// ✗ Middleware — cannot reliably read response body or timing after handler

// ── Scenario 7: Cache GET responses ───────────────────────────────────────────
// ✓ INTERCEPTOR — can short-circuit next.handle() on cache hit, store on miss
// ✗ Middleware — no access to the handler return value to cache it
// ✗ Guard     — semantically wrong; guards are for auth, not caching

// ── Scenario 8: Shape error responses (e.g., add timestamp field) ──────────────
// ✓ EXCEPTION FILTER — only stage that processes thrown exceptions
@Catch(HttpException)
export class TimestampedExceptionFilter implements ExceptionFilter {
    catch(exception: HttpException, host: ArgumentsHost) {
        const response = host.switchToHttp().getResponse<Response>();
        response.status(exception.getStatus()).json({
            ...exception.getResponse() as object,
            timestamp: new Date().toISOString(),
        });
    }
}
// ✗ Interceptor — catchError can re-throw or transform errors, but cannot
//                 shape the HTTP response body (the filter handles that)

// ── Scenario 9: Enforce a 5-second timeout on all routes ──────────────────────
// ✓ INTERCEPTOR (timeout operator) — wraps next.handle() with a deadline
// ✗ Middleware — cannot abort the handler after it starts
// ✗ Guard     — runs before handler, cannot impose a time limit on it

// ── Scenario 10: Parse ':id' route param from string to number ────────────────
// ✓ PIPE (ParseIntPipe) — per-parameter transformation before the handler
@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {}
// ✗ Interceptor — by the time the interceptor runs, params are already strings
//                 and are passed to the handler as strings without pipes
```

## Section 8: Scenario-Based Questions

**Q13. "A request hits a guard, which passes, but the interceptor never logs it — what could cause this?"**

A: This reveals a misunderstanding of the interceptor registration method or scope. Several things could cause this:

```typescript
// ── Cause 1: Global interceptor registered without DI (most common) ───────────
// In main.ts:
app.useGlobalInterceptors(new LoggingInterceptor());
// If LoggingInterceptor has constructor dependencies (Logger, Reflector),
// this will fail silently or inject nothing — the interceptor may throw during
// construction and never register, OR it registers but crashes on first use.

// FIX: Register with DI via APP_INTERCEPTOR:
@Module({
    providers: [
        { provide: APP_INTERCEPTOR, useClass: LoggingInterceptor },
    ],
})
export class AppModule {}

// ── Cause 2: Interceptor registered on a controller but guard is global ────────
// If the guard is applied globally and the interceptor is controller-scoped,
// the interceptor still runs (guards don't affect interceptor registration).
// But if the interceptor is applied to a DIFFERENT controller than the one handling
// the request, it won't run for that route.

// ── Cause 3: Guard short-circuits before interceptor (impossible by design) ──
// Actually: guards run AFTER the interceptor before-phase.
// Wait — this is WRONG. The correct order is:
//   Middleware → Guards → Interceptors (before) → Pipes → Handler
// Guards run BEFORE interceptors.
// So if a guard PASSES, the interceptor WILL run.
// But if a guard FAILS (throws), the interceptor before-phase DOES NOT run.

// This is the real answer: if the guard fails on SOME requests,
// those rejected requests will NOT appear in interceptor logs.
// You must log rejections inside the guard itself.

// ── Cause 4: Interceptor throws before calling next.handle() ──────────────────
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        const user = context.switchToHttp().getRequest().user;
        // If user is undefined and you destructure it:
        const { id } = user; // TypeError: Cannot destructure property 'id' of undefined
        // ↑ This throws before logging or calling next.handle() —
        //   logs never fire, error goes to the exception filter.
        return next.handle().pipe(tap(data => console.log('logged:', data)));
    }
}

// FIX: Optional chaining:
const userId = context.switchToHttp().getRequest().user?.id ?? 'anonymous';

// ── Cause 5: Interceptor scope is narrower than expected ──────────────────────
// @UseInterceptors() on a specific route method only covers that one endpoint.
// If the request hits a different method on the same controller, it won't log.
```

**Q14. "Design the registration order and explain the flow for: global auth guard, logging interceptor, validation pipe, and custom error filter."**

A: The order of registration and the interaction between all four stages in a real-world setup:

```typescript
// main.ts — bootstrap with all stages:
async function bootstrap() {
    const app = await NestFactory.create(AppModule);

    // 1. Middleware (configured in AppModule.configure())
    // — already wired via MiddlewareConsumer

    // 2. Global pipe — ValidationPipe for all routes:
    app.useGlobalPipes(new ValidationPipe({
        whitelist: true,
        transform: true,
        exceptionFactory: (errors) => new BadRequestException(
            errors.flatMap(e => Object.values(e.constraints ?? {}))
        ),
    }));

    // 3. Global exception filter — must be registered LAST so it catches
    //    errors from all stages including guards and pipes:
    app.useGlobalFilters(new AllExceptionsFilter());

    // Note: Global guards and interceptors with DI must use APP_GUARD / APP_INTERCEPTOR
    // in the module providers — not app.useGlobalGuards() — to support injection.

    await app.listen(3000);
}

// AppModule — DI-aware global registrations:
@Module({
    imports: [JwtModule, CacheModule],
    providers: [
        // Global guard — runs on EVERY route:
        { provide: APP_GUARD, useClass: JwtAuthGuard },

        // Global interceptor — wraps EVERY route:
        { provide: APP_INTERCEPTOR, useClass: LoggingInterceptor },

        // Global filter — catches ALL unhandled exceptions:
        { provide: APP_FILTER, useClass: AllExceptionsFilter },
    ],
})
export class AppModule {}

// For a POST /users request with a valid token and valid body:
//
// 1. MIDDLEWARE (RequestIdMiddleware)
//    → Attaches requestId to req
//    → Calls next()
//
// 2. GUARD (JwtAuthGuard)
//    → Verifies Bearer token
//    → Attaches req.user = { id: 'user-1', roles: ['user'] }
//    → Returns true
//
// 3. INTERCEPTOR before (LoggingInterceptor)
//    → Records startTime
//    → Logs { event: 'request.received', method: 'POST', url: '/users' }
//    → Calls next.handle() — continues pipeline
//
// 4. PIPE (ValidationPipe — global)
//    → Validates @Body() against CreateUserDto
//    → Strips extra fields (whitelist: true)
//    → Transforms to CreateUserDto instance (transform: true)
//
// 5. HANDLER (UserController.create)
//    → Calls userService.create(dto)
//    → Returns created User entity
//
// 6. INTERCEPTOR after (LoggingInterceptor)
//    → Logs { event: 'request.completed', durationMs: 42, statusCode: 201 }
//
// Response: 201 Created with { id: 'new-id', email: '...', name: '...' }

// For a POST /users request with an INVALID body ({ email: 'not-email' }):
//
// 1. MIDDLEWARE  → attaches requestId, calls next()
// 2. GUARD       → verifies token, passes
// 3. INTERCEPTOR before → logs request.received, calls next.handle()
// 4. PIPE (ValidationPipe) → THROWS BadRequestException(['email must be an email'])
//    ← Handler NEVER runs
//    ← Interceptor AFTER phase NEVER runs (no value emitted from next.handle())
// 5. EXCEPTION FILTER (AllExceptionsFilter) → catches BadRequestException
//    → Logs the error
//    → Sends 400 { statusCode: 400, message: [...], path: '/users' }

// For a POST /users request with NO token:
//
// 1. MIDDLEWARE  → attaches requestId, calls next()
// 2. GUARD (JwtAuthGuard) → THROWS UnauthorizedException('No token provided')
//    ← Interceptor before phase NEVER runs
//    ← Pipe NEVER runs
//    ← Handler NEVER runs
//    ← Interceptor after phase NEVER runs
// 3. EXCEPTION FILTER → catches UnauthorizedException
//    → Sends 401 { statusCode: 401, message: 'No token provided' }

// IMPORTANT IMPLICATION:
// The LoggingInterceptor will NOT log the rejected 401 request.
// To log all requests including rejections, log in the GUARD or MIDDLEWARE.
// To log ONLY successful (authorised) requests, the interceptor is sufficient.
```

## Section 9: Common Gotchas

**Q15. What are the most common ordering and lifecycle mistakes — and how do you fix them?**

A:

```typescript
// ── Gotcha 1: Expecting middleware to see the response body ───────────────────
// WRONG assumption:
export function responseLoggerMiddleware(req: Request, res: Response, next: NextFunction) {
    next();
    console.log('Response body:', res.body); // ← res.body is NOT the response body
    // res.body does not exist on Express Response.
    // The response has likely already been sent by the time this line runs.
}

// FIX: Use an interceptor for after-handler logic:
@Injectable()
export class ResponseLoggerInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        return next.handle().pipe(
            tap(data => console.log('Response body:', data)), // ← This IS the response body
        );
    }
}

// ── Gotcha 2: Putting authentication logic in a pipe ──────────────────────────
// WRONG: Pipes run after guards. Returning null from a pipe to "reject" auth
// is semantically incorrect and bypasses the guard chain.
@Injectable()
export class AuthPipe implements PipeTransform {
    transform(value: string): string {
        if (!value) throw new UnauthorizedException(); // ← Wrong stage for this
        return value;
    }
}

// FIX: Auth belongs in a Guard:
@Injectable()
export class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean {
        const token = context.switchToHttp().getRequest().headers.authorization;
        if (!token) throw new UnauthorizedException();
        return true;
    }
}

// ── Gotcha 3: Registering guards/interceptors via app.use instead of useGlobal ──
// WRONG:
app.use(new JwtAuthGuard()); // ← Guards are not Express middleware; this does nothing useful

// CORRECT:
app.useGlobalGuards(new JwtAuthGuard(jwtService));
// OR (with DI):
providers: [{ provide: APP_GUARD, useClass: JwtAuthGuard }]

// ── Gotcha 4: Filter scope is INVERSE of guard/interceptor scope ───────────────
// Guards/interceptors: Global → Controller → Route (broad to narrow)
// Filters: Route → Controller → Global (narrow to broad — most specific first)
//
// This means a @Catch(NotFoundException) on a route is tried BEFORE a global @Catch()
// For guards, the GLOBAL guard runs BEFORE the route guard.
// These are opposite orderings — confusing them is a very common mistake.

// ── Gotcha 5: Global pipe runs before param-level pipes — not after ────────────
// WRONG mental model: "param pipe runs, then global pipe validates"
// CORRECT: Global pipe runs FIRST on the raw value, then param-level pipes
//
// Example:
app.useGlobalPipes(new ValidationPipe({ transform: true }));

@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {
    // Order: ValidationPipe (global) runs on ':id' first,
    // then ParseIntPipe (param-level) runs on the result.
    // With transform: true, ValidationPipe may already convert '42' → 42
    // before ParseIntPipe sees it. ParseIntPipe then receives 42 (a number),
    // not a string — parseInt(42, 10) still works, but be aware of this.
}

// ── Gotcha 6: Interceptor after-phase skipped when guard rejects ───────────────
// If you have a global LoggingInterceptor that records every request,
// requests rejected by guards will NOT be logged by that interceptor.
// The interceptor before-phase is NEVER entered when a guard throws.
//
// FIX: Log rejected requests inside the guard, or use middleware for universal logging.

// ── Gotcha 7: Exception filters don't run for synchronous middleware errors ────
// If Express middleware throws (or calls next(err)), NestJS exception filters
// do NOT handle the error — Express's own error handling takes over.
// NestJS filters only catch errors that originate inside the NestJS pipeline
// (guards, interceptors, pipes, handlers).
```

## Quick Reference Tables

### Stage Comparison

| Stage | Runs when | Direction | Has ExecutionContext | Can access response | Throws stop at |
|---|---|---|---|---|---|
| **Middleware** | Before NestJS | Before only | No | No (body) | Express error handler |
| **Guard** | After middleware | Before only | Yes | No | Exception Filters |
| **Interceptor** | After guards | **Before AND after** | Yes | Yes (after phase) | Exception Filters |
| **Pipe** | After interceptor before-phase | Before only | Partial (via metadata) | No | Exception Filters |
| **Handler** | After pipes | — | — | Writes response | Exception Filters |
| **Exception Filter** | Only on error | After (error only) | Via ArgumentsHost | Yes | — (last stage) |

### Execution Order Summary

| # | Stage | Order within stage | Notes |
|---|---|---|---|
| 1 | Middleware | Registration order (top to bottom) | Outside NestJS DI context |
| 2 | Guards | Global → Controller → Route, left to right | First failure stops chain |
| 3 | Interceptors (before) | Global → Controller → Route, left to right | Before `next.handle()` |
| 4 | Pipes | Global → Controller → Route → Param, left to right | Per-parameter |
| 5 | Handler | — | Single method execution |
| 6 | Interceptors (after) | **Reverse**: Route → Controller → Global | `.pipe()` operators |
| 7 | Exception Filters | Route → Controller → Global | Most specific first |

### "Which stage?" Decision Table

| Requirement | Correct stage | Why not others |
|---|---|---|
| Block unauthenticated requests | **Guard** | Has metadata access; semantically correct |
| Parse/validate request param | **Pipe** | Per-parameter, throws 400 automatically |
| Wrap response in envelope | **Interceptor** (map) | After-phase access to response data |
| Log request + response timing | **Interceptor** (finalize) | Only stage with both phases |
| Cache GET responses | **Interceptor** (of / tap) | Can short-circuit handler |
| Enforce request timeout | **Interceptor** (timeout) | Wraps handler with deadline |
| Attach request ID header | **Middleware** | Runs before NestJS, raw request access |
| Apply helmet/compression | **Middleware** | Express ecosystem compatibility |
| Shape error response body | **Exception Filter** | Only stage that processes thrown errors |
| Strip sensitive response fields | **Interceptor** (map) | After handler, before response sent |
| Role-based access control | **Guard** (+ Reflector) | Can read @Roles() metadata |
| Validate entire DTO | **Pipe** (ValidationPipe) | class-validator integration built in |

### RxJS Operators by Use Case in Interceptors

| Operator | Phase | Purpose |
|---|---|---|
| `map(fn)` | After | Transform response value |
| `tap(fn)` | After | Side effects (logging, metrics) without transforming |
| `catchError(fn)` | After | Handle/transform errors from handler |
| `finalize(fn)` | After | Always runs — cleanup and timing |
| `timeout(ms)` | After | Emit TimeoutError if no emission within ms |
| `switchMap(fn)` | After | Replace stream with async result (awaited) |
| `of(value)` | Before | Short-circuit — return value without calling handler |
| `throwError(fn)` | After | Re-throw or create new error |

---

**Tip for interviews:** Seven things separate strong candidates on this topic: (1) **reciting the exact order** — Middleware → Guards → Interceptors (before) → Pipes → Handler → Interceptors (after) → Exception Filters — and explaining the mnemonic: "middleware is outside NestJS, guards are gatekeepers, interceptors are wrappers, pipes are input processors, filters are error catchers"; (2) knowing that **guards rejecting a request prevents the interceptor before-phase from running** — so a logging interceptor will miss rejected requests and you must log inside the guard or middleware; (3) understanding that **middleware cannot see the response body** — `next()` in Express middleware is synchronous and the response is written asynchronously by NestJS; only interceptors can reliably hook the response; (4) knowing that **exception filter scope order is the INVERSE of guard and interceptor scope order** — filters apply most-specific first (Route → Controller → Global), while guards and interceptors apply most-general first (Global → Controller → Route); (5) being precise about **multiple interceptors forming an onion** — `@UseInterceptors(A, B, C)` means before phase is A→B→C and after phase is C→B→A (the outermost interceptor wraps everything including the after-phases of inner interceptors); (6) knowing that **pipes are per-parameter** — they only see one parameter value at a time and are the correct stage for transformation and validation of input, not output; and (7) understanding that **errors thrown in middleware do not reach NestJS exception filters** — they are handled by Express's own error system, so you cannot use `@Catch()` filters to shape errors from middleware.
