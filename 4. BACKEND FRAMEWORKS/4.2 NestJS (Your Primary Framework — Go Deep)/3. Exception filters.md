# Exception Filters: Built-in, Custom Filters, Global Filters — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are exception filters in NestJS, where do they sit in the request lifecycle, and what problem do they solve?**

A: Exception filters are the last layer in NestJS's request processing pipeline. They intercept any unhandled exception thrown anywhere in the pipeline — from guards, interceptors, pipes, or route handlers — and transform it into a structured HTTP response.

```
Incoming Request
     │
     ▼
  Middleware          ← express/fastify middleware
     │
     ▼
  Guards             ← throws ForbiddenException → caught by filter
     │
     ▼
  Interceptors (pre) ← throws HttpException → caught by filter
     │
     ▼
  Pipes              ← throws BadRequestException → caught by filter
     │
     ▼
  Route Handler      ← throws anything → caught by filter
     │
     ▼
  Interceptors (post)
     │
     ▼
  Exception Filters  ← handles any unhandled exception from above
     │
     ▼
  Response sent
```

Without exception filters, an unhandled `throw` inside a route handler would crash the Node.js process or return an opaque 500 with no useful body. Filters give you a single, centralized point to:

- Transform exceptions into consistent response shapes
- Add `requestId`, `timestamp`, and `path` to every error response
- Log errors with full context before responding
- Separate operational errors (known HttpExceptions) from programmer errors (unknown exceptions)
- Handle domain-specific exceptions differently from generic HTTP errors

**Q2. What is `HttpException`, what is its constructor signature, and what built-in subclasses does NestJS provide?**

A: `HttpException` is NestJS's base class for all HTTP errors. Its constructor accepts a response body and an HTTP status code:

```typescript
import { HttpException, HttpStatus } from '@nestjs/common';

// Constructor: HttpException(response: string | object, status: number, options?: HttpExceptionOptions)
throw new HttpException('User not found', HttpStatus.NOT_FOUND);

// With an object response body:
throw new HttpException(
  { statusCode: 404, message: 'User not found', code: 'USER_NOT_FOUND' },
  HttpStatus.NOT_FOUND
);

// With cause (NestJS v9+) — wraps underlying error, not exposed in response:
throw new HttpException('Database error', HttpStatus.INTERNAL_SERVER_ERROR, {
  cause: new Error('Connection refused'),
});
```

NestJS provides a built-in subclass for every standard HTTP status code — you rarely construct `HttpException` directly:

| Class | Status | Class | Status |
|---|---|---|---|
| `BadRequestException` | 400 | `TooManyRequestsException` | 429 |
| `UnauthorizedException` | 401 | `InternalServerErrorException` | 500 |
| `ForbiddenException` | 403 | `NotImplementedException` | 501 |
| `NotFoundException` | 404 | `BadGatewayException` | 502 |
| `MethodNotAllowedException` | 405 | `ServiceUnavailableException` | 503 |
| `ConflictException` | 409 | `GatewayTimeoutException` | 504 |
| `UnprocessableEntityException` | 422 | `RequestTimeoutException` | 408 |

```typescript
// Common usage patterns:
throw new NotFoundException('User not found');
// Response: { statusCode: 404, message: 'User not found', error: 'Not Found' }

throw new BadRequestException(['email must be valid', 'name is required']);
// Response: { statusCode: 400, message: ['email must be valid', 'name is required'], error: 'Bad Request' }

throw new ConflictException({
  message: 'Email already registered',
  field: 'email',
  code: 'DUPLICATE_EMAIL',
});
// Response: { statusCode: 409, message: 'Email already registered', field: 'email', code: 'DUPLICATE_EMAIL' }
```

## Section 2: The Built-in Exception Filter

**Q3. What does NestJS's built-in global exception filter do, and what is its default response format?**

A: NestJS registers a built-in `BaseExceptionFilter` globally on every application. It handles two cases:

**Case 1 — `HttpException` (and subclasses):** Extracts the status code and response body from the exception and sends them directly:

```typescript
// Thrown in a route handler:
throw new NotFoundException('User not found');

// Built-in filter produces:
// HTTP 404
// {
//   "statusCode": 404,
//   "message": "User not found",
//   "error": "Not Found"
// }

// When response is an object, it's used as-is:
throw new HttpException({ code: 'USER_NOT_FOUND', detail: 'No user with id 123' }, 404);
// {
//   "code": "USER_NOT_FOUND",
//   "detail": "No user with id 123"
// }
// Note: when you pass an object, NestJS uses that object as the entire response body
// — statusCode and error are NOT automatically added
```

**Case 2 — Unknown exceptions (not `HttpException`):** Returns a generic 500 response, hiding all internal details:

```typescript
// Thrown in a route handler:
throw new Error('Database connection refused');

// Built-in filter produces:
// HTTP 500
// {
//   "statusCode": 500,
//   "message": "Internal server error"
// }
// The original error message is deliberately hidden — never expose stack traces or
// internal error messages to clients in production
```

The default response format for `HttpException` with a string message:
```json
{
  "statusCode": 404,
  "message": "User not found",
  "error": "Not Found"
}
```

This format is acceptable for simple APIs but most production systems need additional fields (`timestamp`, `path`, `requestId`, `code`). That is the primary reason to write a custom filter.

**Q4. What is `BaseExceptionFilter` and when do you extend it instead of implementing `ExceptionFilter` from scratch?**

A: `BaseExceptionFilter` is the concrete class that NestJS uses internally as its built-in filter. Extending it lets you layer custom behavior on top of the default — you preprocess the exception (log it, send to Sentry, attach context), then fall back to the standard handling:

```typescript
import { Catch, ArgumentsHost } from '@nestjs/common';
import { BaseExceptionFilter } from '@nestjs/core';

@Catch()
export class LoggingExceptionFilter extends BaseExceptionFilter {
  private readonly logger = new Logger(LoggingExceptionFilter.name);

  catch(exception: unknown, host: ArgumentsHost): void {
    // Custom pre-processing — log before delegating to default behavior:
    const ctx  = host.switchToHttp();
    const req  = ctx.getRequest<Request>();
    const status = exception instanceof HttpException
      ? exception.getStatus()
      : 500;

    if (status >= 500) {
      // Log server errors with full stack trace:
      this.logger.error({
        requestId: req['id'],
        method:    req.method,
        path:      req.url,
        exception: exception instanceof Error ? exception.message : String(exception),
        stack:     exception instanceof Error ? exception.stack : undefined,
      }, 'Unhandled exception');
    } else {
      // Log client errors as warnings (not actionable by ops):
      this.logger.warn({
        requestId: req['id'],
        status,
        path:      req.url,
      }, 'HTTP client error');
    }

    // Delegate to default NestJS exception handling:
    super.catch(exception, host);
  }
}
```

**When to extend `BaseExceptionFilter` vs implement `ExceptionFilter` from scratch:**

| Approach | Use when |
|---|---|
| Extend `BaseExceptionFilter` | You want default behavior + pre-processing (logging, Sentry) |
| Implement `ExceptionFilter` | You need full control over the response format |
| Implement for specific type | You want custom handling for one exception type, default for all others |

## Section 3: Custom Exception Filters

**Q5. How do you create a custom exception filter and what is the role of `@Catch()` and `ExceptionFilter`?**

A: A custom filter is a class decorated with `@Catch()` that implements the `ExceptionFilter` interface. The `@Catch()` decorator specifies which exception type(s) this filter handles:

```typescript
import {
  ExceptionFilter, Catch, ArgumentsHost,
  HttpException, HttpStatus, Logger,
} from '@nestjs/common';
import { Request, Response } from 'express';

@Catch(HttpException)   // ← Only handles HttpException and its subclasses
export class HttpExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(HttpExceptionFilter.name);

  catch(exception: HttpException, host: ArgumentsHost): void {
    const ctx      = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    const request  = ctx.getRequest<Request>();
    const status   = exception.getStatus();

    // getResponse() returns either the string message or the object response body:
    const exceptionResponse = exception.getResponse();
    const message =
      typeof exceptionResponse === 'string'
        ? exceptionResponse
        : (exceptionResponse as any).message;

    const body = {
      statusCode: status,
      timestamp:  new Date().toISOString(),
      path:       request.url,
      requestId:  request['id'],          // Injected by request ID middleware
      message,
      ...(typeof exceptionResponse === 'object' && exceptionResponse !== null
        ? exceptionResponse                // Spread additional fields from the exception
        : {}),
    };

    // Log 5xx as errors, 4xx as warnings:
    if (status >= 500) {
      this.logger.error({ body, stack: exception.stack }, 'HTTP exception');
    } else {
      this.logger.warn({ body }, 'HTTP exception');
    }

    response.status(status).json(body);
  }
}
```

**`@Catch()` argument rules:**

```typescript
@Catch()                              // No args: catches EVERY exception (including non-HttpException)
@Catch(HttpException)                 // All HttpException subclasses
@Catch(NotFoundException)             // Only NotFoundException
@Catch(NotFoundException, ConflictException)  // Either of these
@Catch(DatabaseException)             // A custom exception class
```

**`ExceptionFilter` interface:**
```typescript
interface ExceptionFilter<T = any> {
  catch(exception: T, host: ArgumentsHost): any;
  // - exception: the thrown value (typed via @Catch generic)
  // - host: access to the current execution context (HTTP, WS, RPC)
  // - return value: not used by NestJS — response must be sent via host
}
```

**Q6. What is `ArgumentsHost` and how do you use it to access the request and response?**

A: `ArgumentsHost` is an abstraction over the underlying transport context. A NestJS application may handle HTTP requests, WebSocket messages, and gRPC calls simultaneously. `ArgumentsHost` provides a unified interface to switch between them:

```typescript
import { ArgumentsHost, ContextType } from '@nestjs/common';
import { Request, Response } from 'express';

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost): void {
    const contextType = host.getType<ContextType>();
    // contextType: 'http' | 'ws' | 'rpc' — tells you which transport this request is

    switch (contextType) {
      case 'http':
        return this.handleHttp(exception, host);
      case 'ws':
        return this.handleWs(exception, host);
      case 'rpc':
        return this.handleRpc(exception, host);
    }
  }

  private handleHttp(exception: unknown, host: ArgumentsHost): void {
    const ctx      = host.switchToHttp();
    const request  = ctx.getRequest<Request>();   // Express Request (or Fastify Request)
    const response = ctx.getResponse<Response>(); // Express Response (or Fastify Reply)
    const next     = ctx.getNext();               // Express next() — rarely needed in filters

    const status = exception instanceof HttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    response.status(status).json({
      statusCode: status,
      path:       request.url,
      timestamp:  new Date().toISOString(),
    });
  }

  private handleWs(exception: unknown, host: ArgumentsHost): void {
    const ctx    = host.switchToWs();
    const client = ctx.getClient();    // WebSocket client instance
    const data   = ctx.getData();      // Incoming WS message data

    // WS: send an error message back over the socket instead of an HTTP response:
    client.send(JSON.stringify({
      event: 'error',
      data:  { message: exception instanceof Error ? exception.message : 'Unknown error' },
    }));
  }

  private handleRpc(exception: unknown, host: ArgumentsHost): void {
    const ctx  = host.switchToRpc();
    const data = ctx.getData();   // Incoming RPC message
    // gRPC: throw the exception so the framework converts it to an RPC status code:
    throw exception;
  }
}
```

The key insight: **never assume the context is HTTP**. A filter registered globally will receive exceptions from any transport the application handles. Always check `host.getType()` or use the appropriate `switchTo*()` method after confirming context type.

**Q7. What is `HttpAdapterHost` and when must you use it over `host.switchToHttp().getResponse()`?**

A: `host.switchToHttp().getResponse()` returns the raw response object of the underlying HTTP framework — an Express `Response` when using `ExpressAdapter`, a Fastify `Reply` when using `FastifyAdapter`. Calling `response.status(404).json({...})` works on Express but crashes on Fastify because Fastify's reply API differs (`reply.code(404).send({...})`).

`HttpAdapterHost` wraps the active adapter and exposes a **platform-agnostic** `reply()` method that works with both:

```typescript
import { Catch, ArgumentsHost, HttpException, HttpStatus } from '@nestjs/common';
import { HttpAdapterHost } from '@nestjs/core';
import { ExceptionFilter } from '@nestjs/common';

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  constructor(
    // Inject HttpAdapterHost — works for any HTTP framework NestJS supports
    private readonly httpAdapterHost: HttpAdapterHost,
  ) {}

  catch(exception: unknown, host: ArgumentsHost): void {
    // Only handle HTTP context — this filter might also receive WS/RPC exceptions
    if (host.getType() !== 'http') return;

    const { httpAdapter } = this.httpAdapterHost;
    const ctx = host.switchToHttp();

    const status =
      exception instanceof HttpException
        ? exception.getStatus()
        : HttpStatus.INTERNAL_SERVER_ERROR;

    const responseBody = {
      statusCode: status,
      timestamp:  new Date().toISOString(),
      path:       httpAdapter.getRequestUrl(ctx.getRequest()),  // Platform-agnostic URL read
      message:
        exception instanceof HttpException
          ? exception.message
          : 'Internal server error',
    };

    // httpAdapter.reply() works on both Express and Fastify:
    httpAdapter.reply(ctx.getResponse(), responseBody, status);
  }
}

// Registering — requires HttpAdapterHost to be injected, so must use APP_FILTER:
// app.module.ts
providers: [
  { provide: APP_FILTER, useClass: AllExceptionsFilter },
]
```

**Rule of thumb:**
- Writing a filter for a codebase that will only ever use Express? Use `host.switchToHttp().getResponse()` — it's simpler.
- Writing a filter for a library, a multi-adapter codebase, or a production app where you might switch adapters? Use `HttpAdapterHost`.

## Section 4: Custom Exception Classes

**Q8. How do you build a custom exception hierarchy for domain errors?**

A: Domain exceptions extend `HttpException` and carry domain-specific metadata. A layered hierarchy keeps the HTTP concerns at the base class and domain concerns at the leaves:

```typescript
import { HttpException, HttpStatus } from '@nestjs/common';

// Base class for all domain exceptions — adds code and metadata:
export abstract class DomainException extends HttpException {
  constructor(
    readonly code:    string,          // Machine-readable error code for clients
    message:          string,          // Human-readable message
    status:           number,
    readonly meta?:   Record<string, unknown>,  // Optional structured metadata
  ) {
    super({ message, code, ...(meta ?? {}) }, status);
  }
}

// Resource not found domain errors:
export class ResourceNotFoundException extends DomainException {
  constructor(resource: string, id: string | number) {
    super(
      'RESOURCE_NOT_FOUND',
      `${resource} with id '${id}' not found`,
      HttpStatus.NOT_FOUND,
      { resource, id },
    );
  }
}

// Conflict errors:
export class DuplicateResourceException extends DomainException {
  constructor(resource: string, field: string, value: string) {
    super(
      'DUPLICATE_RESOURCE',
      `${resource} with ${field} '${value}' already exists`,
      HttpStatus.CONFLICT,
      { resource, field, value },
    );
  }
}

// Business rule violations:
export class BusinessRuleException extends DomainException {
  constructor(rule: string, message: string, meta?: Record<string, unknown>) {
    super('BUSINESS_RULE_VIOLATION', message, HttpStatus.UNPROCESSABLE_ENTITY, { rule, ...meta });
  }
}

// Usage in services:
async findUser(id: string): Promise<User> {
  const user = await this.repo.findById(id);
  if (!user) throw new ResourceNotFoundException('User', id);
  return user;
}

async createUser(dto: CreateUserDto): Promise<User> {
  const existing = await this.repo.findByEmail(dto.email);
  if (existing) throw new DuplicateResourceException('User', 'email', dto.email);
  return this.repo.create(dto);
}

async transferFunds(from: string, to: string, amount: number): Promise<void> {
  const account = await this.repo.findById(from);
  if (account.balance < amount) {
    throw new BusinessRuleException('INSUFFICIENT_FUNDS', 'Insufficient balance', {
      available: account.balance,
      requested: amount,
    });
  }
}
```

```typescript
// Filter catching all DomainException subclasses:
@Catch(DomainException)
export class DomainExceptionFilter implements ExceptionFilter {
  catch(exception: DomainException, host: ArgumentsHost): void {
    const ctx    = host.switchToHttp();
    const res    = ctx.getResponse<Response>();
    const req    = ctx.getRequest<Request>();
    const status = exception.getStatus();

    res.status(status).json({
      statusCode: status,
      code:       exception.code,        // 'RESOURCE_NOT_FOUND', 'DUPLICATE_RESOURCE', etc.
      message:    exception.message,
      meta:       exception.meta,        // { resource: 'User', id: '123' }
      requestId:  req['id'],
      timestamp:  new Date().toISOString(),
      path:       req.url,
    });
  }
}

// Client receives a structured, actionable error:
// {
//   "statusCode": 404,
//   "code": "RESOURCE_NOT_FOUND",
//   "message": "User with id '123' not found",
//   "meta": { "resource": "User", "id": "123" },
//   "requestId": "550e8400-...",
//   "timestamp": "2024-01-15T10:23:45.123Z",
//   "path": "/api/users/123"
// }
```

## Section 5: Binding Filters

**Q9. How do you bind a filter at method, controller, and global scope?**

A: Filters bind at three levels using `@UseFilters()` or global registration. Each level adds filters to a specific scope:

```typescript
import { UseFilters } from '@nestjs/common';

// ── METHOD LEVEL — applies to a single route handler ─────────────────────────
@Controller('users')
export class UsersController {
  @Get(':id')
  @UseFilters(ResourceNotFoundFilter)    // Only this endpoint uses this filter
  async getUser(@Param('id') id: string) {
    return this.usersService.findOne(id);
  }

  @Post()
  @UseFilters(DomainExceptionFilter, ValidationExceptionFilter)  // Multiple filters
  async createUser(@Body() dto: CreateUserDto) {
    return this.usersService.create(dto);
  }
}

// ── CONTROLLER LEVEL — applies to all routes in the controller ────────────────
@Controller('orders')
@UseFilters(DomainExceptionFilter)      // All routes in OrdersController use this filter
export class OrdersController {
  @Get(':id')
  async getOrder(@Param('id') id: string) { ... }

  @Post()
  async createOrder(@Body() dto: CreateOrderDto) { ... }
  // Both routes are covered by DomainExceptionFilter
}

// ── GLOBAL LEVEL — applies to every route in the application ─────────────────
// Option A: app.useGlobalFilters() — does NOT support dependency injection
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalFilters(new AllExceptionsFilter());  // Cannot inject Logger, ConfigService, etc.
  await app.listen(3000);
}

// Option B: APP_FILTER provider token — DOES support dependency injection (preferred)
// app.module.ts
import { APP_FILTER } from '@nestjs/core';
@Module({
  providers: [
    { provide: APP_FILTER, useClass: AllExceptionsFilter },
    // Multiple global filters — each becomes a separate provider:
    { provide: APP_FILTER, useClass: DomainExceptionFilter },
  ],
})
export class AppModule {}
```

**Prefer class reference over instance in `@UseFilters()`:**
```typescript
// PREFERRED: pass the class — NestJS manages instantiation and caching:
@UseFilters(DomainExceptionFilter)

// AVOID: pass an instance — a new instance is created per request, bypassing DI:
@UseFilters(new DomainExceptionFilter())  // Works but wasteful — no singleton, no DI
```

**Q10. Why does `app.useGlobalFilters()` not support dependency injection, and how does `APP_FILTER` fix this?**

A: `app.useGlobalFilters(new SomeFilter())` registers the filter instance directly — it was instantiated outside the NestJS IoC container. The container never knows about it, so it cannot inject dependencies into it.

```typescript
// BROKEN: Logger cannot be injected — filter instantiated outside the container
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  constructor(private readonly logger: Logger) {}  // ← Never injected!
  catch(exception: unknown, host: ArgumentsHost): void {
    this.logger.error(exception);  // TypeError: Cannot read property 'error' of undefined
  }
}

// In main.ts:
app.useGlobalFilters(new AllExceptionsFilter());  // No Logger provided — constructor gets nothing
```

`APP_FILTER` is a multi-provider token that NestJS resolves through the container. The filter class is registered as a provider, so its constructor dependencies are injected normally:

```typescript
// CORRECT: Logger is injected because the container manages instantiation
@Catch()
@Injectable()
export class AllExceptionsFilter implements ExceptionFilter {
  constructor(
    private readonly logger:        Logger,
    private readonly configService: ConfigService,   // Also injected
  ) {}

  catch(exception: unknown, host: ArgumentsHost): void {
    const isDev = this.configService.get('NODE_ENV') === 'development';
    this.logger.error({ exception, stack: isDev ? exception?.stack : undefined });
    // ...
  }
}

// app.module.ts — registered via APP_FILTER:
@Module({
  imports:   [ConfigModule],   // ConfigService must be available in this module
  providers: [
    { provide: APP_FILTER, useClass: AllExceptionsFilter },
    Logger,
  ],
})
export class AppModule {}
```

`APP_FILTER` is a **multi-provider** (`multi: true` internally). This means you can register multiple global filters without overwriting each other — each `{ provide: APP_FILTER, ... }` adds to the list rather than replacing it.

## Section 6: Filter Execution Order

**Q11. In what order do multiple filters execute when an exception is thrown?**

A: NestJS collects all applicable filters (method → controller → global) and finds the first one whose `@Catch()` matches the exception type. The specificity hierarchy is:

```
For a given route, filters are considered in order:
  1. Method-level filters (most specific — checked first)
  2. Controller-level filters
  3. Global filters (least specific — checked last)

Within the same scope, filters are checked in registration order (left-to-right for @UseFilters).
```

```typescript
// Global:    @Catch()                → AllExceptionsFilter
// Controller: @Catch(DomainException) → DomainExceptionFilter
// Method:    @Catch(NotFoundException) → NotFoundFilter

@Controller('users')
@UseFilters(DomainExceptionFilter)
export class UsersController {
  @Get(':id')
  @UseFilters(NotFoundFilter)
  async getUser(@Param('id') id: string) {
    throw new NotFoundException('User not found');  // Which filter handles this?
  }
}

// Answer: NotFoundFilter (method-level, most specific)
// @Catch(NotFoundException) matches NotFoundException → NotFoundFilter wins

// If NotFoundFilter were @Catch(ConflictException) instead:
// NotFoundFilter: @Catch(ConflictException) → does NOT match NotFoundException
// DomainExceptionFilter: @Catch(DomainException) → NotFoundException IS a DomainException? Only
//   if NotFoundException extends DomainException — if not, skip
// AllExceptionsFilter: @Catch() → matches everything → handles it

// Key rule: NestJS finds the FIRST matching filter in specificity order
// It does NOT run ALL matching filters — only one filter handles each exception
```

**`@Catch()` type matching uses `instanceof`:**
```typescript
@Catch(HttpException)
class HFilter implements ExceptionFilter { ... }

// Matches:
throw new HttpException('msg', 400);         // ✓ exact type
throw new NotFoundException('not found');    // ✓ NotFoundException extends HttpException
throw new DomainException('code', 'msg', 400); // ✓ if DomainException extends HttpException

// Does NOT match:
throw new Error('raw error');                // ✗ Error is not HttpException
throw new DatabaseException('connection');   // ✗ if DatabaseException doesn't extend HttpException
```

**Q12. What happens when `@Catch()` is given multiple exception types, and how do filters with overlapping types interact?**

A: When `@Catch(TypeA, TypeB)` is used, the filter handles exceptions that are an `instanceof` TypeA OR TypeB. This is an OR relationship — the filter fires if the exception matches any of the listed types:

```typescript
// Handles NotFoundException OR ConflictException (but not other HttpExceptions):
@Catch(NotFoundException, ConflictException)
export class ResourceFilter implements ExceptionFilter {
  catch(exception: NotFoundException | ConflictException, host: ArgumentsHost): void {
    const status = exception.getStatus();   // 404 or 409 depending on which was thrown
    // ...
  }
}

// Overlapping scopes — the most specific (method-level) wins:
@Controller('products')
@UseFilters(ConflictExceptionFilter)         // Controller: @Catch(ConflictException)
export class ProductsController {
  @Post()
  @UseFilters(ResourceFilter)                // Method: @Catch(NotFoundException, ConflictException)
  async createProduct(@Body() dto: CreateProductDto) {
    // throw new ConflictException('Duplicate SKU') — which filter?
    // ResourceFilter (method-level) handles ConflictException → ResourceFilter wins
  }
}
```

## Section 7: Advanced Patterns

**Q13. How do you handle `ValidationPipe` errors in a custom filter and reformat them?**

A: `ValidationPipe` throws `BadRequestException` when class-validator rules fail. The exception's `getResponse()` returns an object with a `message` array of constraint violation strings. A custom filter can intercept this and transform it into a structured validation error format:

```typescript
import {
  Catch, ExceptionFilter, ArgumentsHost,
  BadRequestException,
} from '@nestjs/common';
import { Request, Response } from 'express';

interface ValidationErrorResponse {
  message: string | string[];
  error:   string;
}

@Catch(BadRequestException)
export class ValidationExceptionFilter implements ExceptionFilter {
  catch(exception: BadRequestException, host: ArgumentsHost): void {
    const ctx    = host.switchToHttp();
    const res    = ctx.getResponse<Response>();
    const req    = ctx.getRequest<Request>();

    const exceptionResponse = exception.getResponse() as ValidationErrorResponse;

    // Distinguish ValidationPipe errors (message is an array) from plain BadRequest:
    const isValidationError = Array.isArray(exceptionResponse.message);

    if (isValidationError) {
      // Transform flat array into field-grouped structure:
      const violations = (exceptionResponse.message as string[]).map(msg => {
        // ValidationPipe default messages: "fieldName must be a string", "fieldName should not be empty"
        // Parse the field name from the message:
        const parts    = msg.split(' ');
        const property = parts[0];
        const message  = parts.slice(1).join(' ');
        return { property, message };
      });

      return res.status(400).json({
        statusCode: 400,
        code:       'VALIDATION_ERROR',
        message:    'Request validation failed',
        violations,                // [{ property: 'email', message: 'must be an email' }]
        requestId:  req['id'],
        timestamp:  new Date().toISOString(),
        path:       req.url,
      });
    }

    // Plain BadRequestException — not from ValidationPipe:
    res.status(400).json({
      statusCode: 400,
      code:       'BAD_REQUEST',
      message:    typeof exceptionResponse === 'string'
        ? exceptionResponse
        : exceptionResponse.message,
      requestId:  req['id'],
      timestamp:  new Date().toISOString(),
      path:       req.url,
    });
  }
}
```

**Better approach: use `ValidationPipe`'s `exceptionFactory` option to produce structured errors before they hit the filter:**

```typescript
// In main.ts or a module — customize ValidationPipe error format at the source:
app.useGlobalPipes(new ValidationPipe({
  transform:       true,
  whitelist:       true,
  forbidNonWhitelisted: true,
  exceptionFactory: (errors: ValidationError[]) => {
    // errors is an array of class-validator ValidationError objects
    const violations = errors.flatMap(error =>
      Object.entries(error.constraints ?? {}).map(([rule, message]) => ({
        property: error.property,
        value:    error.value,
        rule,
        message,
      }))
    );

    return new BadRequestException({
      code:       'VALIDATION_ERROR',
      message:    'Request validation failed',
      violations,  // Structured from the start — filter sees this without parsing strings
    });
  },
}));
```

**Q14. How do you write a catch-all filter that differentiates `HttpException` from unknown errors and adds structured logging?**

A:

```typescript
import {
  Catch, ArgumentsHost, HttpException, HttpStatus,
  Logger, Injectable,
} from '@nestjs/common';
import { HttpAdapterHost } from '@nestjs/core';
import { ExceptionFilter } from '@nestjs/common';
import { Request } from 'express';

@Catch()
@Injectable()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  constructor(private readonly httpAdapterHost: HttpAdapterHost) {}

  catch(exception: unknown, host: ArgumentsHost): void {
    // Only handle HTTP — let other transports fall through
    if (host.getType() !== 'http') {
      // Re-throw for WS/RPC — let those transports handle it
      throw exception;
    }

    const { httpAdapter } = this.httpAdapterHost;
    const ctx = host.switchToHttp();
    const req = ctx.getRequest<Request>();

    // Classify the exception:
    const isHttpException = exception instanceof HttpException;
    const status = isHttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    const isClientError = status >= 400 && status < 500;
    const isServerError = status >= 500;

    // ── Structured logging ────────────────────────────────────────────────────
    const logContext = {
      requestId: req['id'],
      method:    req.method,
      path:      req.url,
      status,
      userAgent: req.headers['user-agent'],
      ip:        req.ip,
    };

    if (isServerError) {
      this.logger.error(
        {
          ...logContext,
          // Only log full error details for server errors — client errors are not our bugs
          exception: exception instanceof Error ? exception.message : String(exception),
          stack:     exception instanceof Error ? exception.stack : undefined,
          cause:     isHttpException ? (exception as any).cause?.message : undefined,
        },
        'Unhandled server error',
      );
    } else if (isClientError) {
      this.logger.warn(logContext, 'HTTP client error');
    }

    // ── Response body ─────────────────────────────────────────────────────────
    const responseBody = isHttpException
      ? {
          // HttpException: expose the exception's response, enriched:
          statusCode: status,
          ...(typeof exception.getResponse() === 'object'
            ? exception.getResponse() as object
            : { message: exception.getResponse() }),
          requestId: req['id'],
          timestamp: new Date().toISOString(),
          path:      req.url,
        }
      : {
          // Unknown error: hide all internal details from clients:
          statusCode: 500,
          code:       'INTERNAL_ERROR',
          message:    'An unexpected error occurred',
          requestId:  req['id'],
          timestamp:  new Date().toISOString(),
          path:       req.url,
        };

    httpAdapter.reply(ctx.getResponse(), responseBody, status);
  }
}
```

## Section 8: Multi-Transport and Testing

**Q15. How do you write a filter that correctly handles HTTP, WebSocket, and microservice (RPC) contexts?**

A:

```typescript
import {
  Catch, ArgumentsHost, HttpException, HttpStatus,
  WsException,
} from '@nestjs/common';
import { RpcException } from '@nestjs/microservices';
import { throwError } from 'rxjs';

@Catch()
export class CrossContextExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost): any {
    const contextType = host.getType<'http' | 'ws' | 'rpc'>();

    switch (contextType) {
      case 'http':  return this.handleHttp(exception, host);
      case 'ws':    return this.handleWs(exception, host);
      case 'rpc':   return this.handleRpc(exception, host);
    }
  }

  private handleHttp(exception: unknown, host: ArgumentsHost): void {
    const ctx    = host.switchToHttp();
    const res    = ctx.getResponse();
    const req    = ctx.getRequest();
    const status = exception instanceof HttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    res.status(status).json({
      statusCode: status,
      message:    exception instanceof HttpException
        ? exception.message
        : 'Internal server error',
      requestId:  req.id,
      timestamp:  new Date().toISOString(),
    });
  }

  private handleWs(exception: unknown, host: ArgumentsHost): void {
    const ctx    = host.switchToWs();
    const client = ctx.getClient();

    // WebSocket: send structured error event back to the client
    const error = exception instanceof WsException
      ? exception.getError()
      : { message: 'WebSocket error' };

    client.send(JSON.stringify({ event: 'error', data: error }));
  }

  private handleRpc(exception: unknown, host: ArgumentsHost): never {
    // Microservices: wrap in RpcException so the framework can serialize it
    // and return the Observable error to the caller:
    if (exception instanceof RpcException) {
      throw exception;
    }
    throw new RpcException(
      exception instanceof Error ? exception.message : 'RPC error'
    );
    // For Observable-based transports, return: return throwError(() => exception);
  }
}
```

## Section 9: Scenario-Based Questions

**Q17. "Trace exactly what happens when this code throws, identifying which filter handles it and why."**

```typescript
// Global:     @Catch()                 → AllExceptionsFilter (via APP_FILTER)
// Global:     @Catch(HttpException)    → HttpExceptionFilter (via APP_FILTER)
// Controller: @Catch(DomainException)  → DomainExceptionFilter

@Controller('orders')
@UseFilters(DomainExceptionFilter)
export class OrdersController {
  constructor(private readonly ordersService: OrdersService) {}

  @Post()
  @UseFilters(ValidationExceptionFilter)    // @Catch(BadRequestException)
  async createOrder(@Body() dto: CreateOrderDto) {
    return this.ordersService.create(dto);  // throws new ConflictException('Order exists')
  }

  @Delete(':id')
  async cancelOrder(@Param('id') id: string) {
    return this.ordersService.cancel(id);  // throws new Error('Stripe API down')
  }

  @Get(':id')
  async getOrder(@Param('id') id: string) {
    return this.ordersService.find(id);    // throws new ResourceNotFoundException('Order', id)
  }
}
```

A: Tracing each throw:

**`POST /orders` — throws `ConflictException('Order exists')`:**
```
ConflictException is a subclass of HttpException.
Filters considered in order (method → controller → global):
  1. ValidationExceptionFilter: @Catch(BadRequestException)
     ConflictException instanceof BadRequestException? NO → skip
  2. DomainExceptionFilter: @Catch(DomainException)
     ConflictException instanceof DomainException? Only if ConflictException extends DomainException
     — here it extends HttpException, not DomainException → skip
  3. HttpExceptionFilter (global): @Catch(HttpException)
     ConflictException instanceof HttpException? YES → HttpExceptionFilter handles it
Result: HttpExceptionFilter → HTTP 409
```

**`DELETE /orders/:id` — throws `new Error('Stripe API down')`:**
```
Plain Error, not HttpException or DomainException.
Filters considered:
  1. No method-level filter for DELETE route
  2. DomainExceptionFilter: @Catch(DomainException)
     Error instanceof DomainException? NO → skip
  3. HttpExceptionFilter (global): @Catch(HttpException)
     Error instanceof HttpException? NO → skip
  4. AllExceptionsFilter (global): @Catch()
     @Catch() with no args catches EVERYTHING → AllExceptionsFilter handles it
Result: AllExceptionsFilter → HTTP 500, "Internal server error" (Error message hidden)
```

**`GET /orders/:id` — throws `ResourceNotFoundException('Order', id)`:**
```
ResourceNotFoundException extends DomainException extends HttpException.
Filters considered:
  1. No method-level filter for GET route
  2. DomainExceptionFilter: @Catch(DomainException)
     ResourceNotFoundException instanceof DomainException? YES → DomainExceptionFilter handles it
Result: DomainExceptionFilter → HTTP 404, structured domain response
```

**Q18. "What is wrong with this exception filter, and what are the consequences?"**

```typescript
@Catch(HttpException)
export class BrokenFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse();
    const status   = exception.getStatus();

    console.log('Error:', exception.message);

    response.status(status).json({
      status,
      msg:  exception.message,
      when: Date.now(),
    });

    // Called after res.json() — what happens?
    next();
  }
}
```

A: Five problems:

**Problem 1 — `next` is not in scope:**
```typescript
// next() is called but 'next' is not imported or destructured
// TypeScript: 'next' is not defined
// Runtime: ReferenceError: next is not defined
// This crashes the filter itself — client gets an unhandled error
```

**Problem 2 — Response already sent, then `next()` would advance the chain:**
```typescript
// Even if next were available (e.g., ctx.getNext()), calling it after res.json()
// causes "Cannot set headers after they are sent to the client" if any downstream
// code tries to set headers. Filters should NEVER call next() after sending a response.
```

**Problem 3 — `console.log` instead of NestJS Logger:**
```typescript
// console.log bypasses NestJS's logging infrastructure:
// - No log level filtering
// - No structured JSON output for log aggregators
// - No request ID, no timestamp, no context
// Replace with: private readonly logger = new Logger(BrokenFilter.name);
//               this.logger.error(exception);
```

**Problem 4 — Inconsistent response field names (`status` not `statusCode`, `msg` not `message`):**
```typescript
// NestJS convention and most client SDKs expect:
// { statusCode: 404, message: '...' }
// This filter returns:
// { status: 404, msg: '...' }
// Clients that check body.statusCode will see undefined
// Logging tools that parse body.message will miss the field
```

**Problem 5 — `Date.now()` instead of ISO timestamp:**
```typescript
// Date.now() returns an integer: 1705312800000
// Logs and APIs conventionally use ISO 8601: "2024-01-15T10:00:00.000Z"
// Epoch integers are not human-readable and require conversion
// Replace with: new Date().toISOString()
```

**Corrected filter:**
```typescript
@Catch(HttpException)
export class FixedFilter implements ExceptionFilter {
  private readonly logger = new Logger(FixedFilter.name);

  catch(exception: HttpException, host: ArgumentsHost): void {  // void return — no next()
    const ctx    = host.switchToHttp();
    const res    = ctx.getResponse<Response>();
    const req    = ctx.getRequest<Request>();
    const status = exception.getStatus();

    this.logger.warn({ requestId: req['id'], status, path: req.url }, exception.message);

    res.status(status).json({
      statusCode: status,                // Correct field name
      message:    exception.message,     // Correct field name
      timestamp:  new Date().toISOString(),  // ISO format
      path:       req.url,
      requestId:  req['id'],
    });
    // No next() call — response sent, chain terminates here
  }
}
```

**Q19. "Design a complete exception filter system for a production NestJS API with domain exceptions, validation errors, and logging."**

A:

```typescript
// ── 1. Custom domain exception base ─────────────────────────────────────────
export abstract class AppException extends HttpException {
  constructor(
    readonly code:   string,
    message:         string,
    status:          number,
    readonly meta?:  Record<string, unknown>,
  ) {
    super({ message, code, ...(meta ?? {}) }, status);
  }
}

export class EntityNotFoundException extends AppException {
  constructor(entity: string, id: string | number) {
    super('ENTITY_NOT_FOUND', `${entity} '${id}' not found`, 404, { entity, id });
  }
}
export class EntityConflictException extends AppException {
  constructor(entity: string, field: string) {
    super('ENTITY_CONFLICT', `${entity} with this ${field} already exists`, 409, { entity, field });
  }
}

// ── 2. Validation exception filter ──────────────────────────────────────────
@Catch(BadRequestException)
@Injectable()
export class ValidationFilter implements ExceptionFilter {
  catch(exception: BadRequestException, host: ArgumentsHost): void {
    const ctx  = host.switchToHttp();
    const res  = ctx.getResponse<Response>();
    const req  = ctx.getRequest<Request>();
    const body = exception.getResponse() as any;

    res.status(400).json({
      statusCode: 400,
      code:       'VALIDATION_ERROR',
      message:    'Validation failed',
      violations: Array.isArray(body.message) ? body.message : [body.message],
      requestId:  req['id'],
      timestamp:  new Date().toISOString(),
      path:       req.url,
    });
  }
}

// ── 3. Domain exception filter ──────────────────────────────────────────────
@Catch(AppException)
@Injectable()
export class AppExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(AppExceptionFilter.name);

  catch(exception: AppException, host: ArgumentsHost): void {
    const ctx    = host.switchToHttp();
    const res    = ctx.getResponse<Response>();
    const req    = ctx.getRequest<Request>();
    const status = exception.getStatus();

    this.logger.warn({
      requestId: req['id'],
      code:      exception.code,
      status,
      path:      req.url,
    }, `Domain exception: ${exception.code}`);

    res.status(status).json({
      statusCode: status,
      code:       exception.code,
      message:    exception.message,
      meta:       exception.meta,
      requestId:  req['id'],
      timestamp:  new Date().toISOString(),
      path:       req.url,
    });
  }
}

// ── 4. Catch-all filter (registered last — lowest priority) ─────────────────
@Catch()
@Injectable()
export class GlobalExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(GlobalExceptionFilter.name);

  constructor(private readonly httpAdapterHost: HttpAdapterHost) {}

  catch(exception: unknown, host: ArgumentsHost): void {
    if (host.getType() !== 'http') return;

    const { httpAdapter } = this.httpAdapterHost;
    const ctx = host.switchToHttp();
    const req = ctx.getRequest<Request>();

    // This should only be reached for true programmer errors — always 500:
    this.logger.error({
      requestId: req['id'],
      method:    req.method,
      path:      req.url,
      error:     exception instanceof Error ? exception.message : String(exception),
      stack:     exception instanceof Error ? exception.stack : undefined,
    }, 'Unhandled exception');

    httpAdapter.reply(ctx.getResponse(), {
      statusCode: 500,
      code:       'INTERNAL_ERROR',
      message:    'An unexpected error occurred',
      requestId:  req['id'],
      timestamp:  new Date().toISOString(),
      path:       req.url,
    }, 500);
  }
}

// ── 5. Registration in AppModule ─────────────────────────────────────────────
// Order matters: NestJS checks in reverse registration order (last registered = highest priority)
// APP_FILTER uses multi-providers — all are collected, most-specific @Catch wins per-exception
@Module({
  providers: [
    { provide: APP_FILTER, useClass: GlobalExceptionFilter },    // Catch-all — lowest priority
    { provide: APP_FILTER, useClass: AppExceptionFilter },       // Domain exceptions
    { provide: APP_FILTER, useClass: ValidationFilter },         // Validation errors — highest priority
  ],
})
export class AppModule {}

// ── Resulting behavior ───────────────────────────────────────────────────────
// throw new BadRequestException([...])                → ValidationFilter
// throw new EntityNotFoundException('User', '123')    → AppExceptionFilter
// throw new EntityConflictException('User', 'email')  → AppExceptionFilter
// throw new Error('Unexpected DB error')              → GlobalExceptionFilter
// throw new InternalServerErrorException('msg')       → AppExceptionFilter? No —
//   InternalServerErrorException extends HttpException, not AppException
//   → GlobalExceptionFilter handles it (HttpException that's not AppException falls through)
// Better: make GlobalExceptionFilter also handle HttpException as a fallback:
// @Catch(HttpException) — or rely on @Catch() and check instanceof inside
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| **`ExceptionFilter` interface** | `catch(exception: T, host: ArgumentsHost): any` — must send a response; return value ignored |
| **`@Catch()`** | No args: catches everything. `@Catch(HttpException)`: catches HttpException + subclasses. `@Catch(A, B)`: catches A OR B |
| **`@Catch()` matching** | Uses `instanceof` — subclasses match parent type patterns |
| **`ArgumentsHost`** | Context-switching abstraction; `.getType()` returns `'http'`, `'ws'`, or `'rpc'` |
| **`host.switchToHttp()`** | Returns `{ getRequest, getResponse, getNext }` — platform-specific (Express or Fastify) |
| **`HttpAdapterHost`** | Platform-agnostic adapter; `httpAdapter.reply(res, body, status)` works for Express and Fastify |
| **Built-in filter** | NestJS registers `BaseExceptionFilter` globally by default — returns `{ statusCode, message, error }` |
| **Extending `BaseExceptionFilter`** | `super.catch(exception, host)` delegates to default behavior after your pre-processing |
| **`@UseFilters()`** | Method or controller decorator — binds one or more filters to that scope |
| **Binding priority** | Method-level → controller-level → global; first matching filter (by `instanceof`) handles the exception |
| **`app.useGlobalFilters()`** | Registers globally but OUTSIDE the DI container — no dependency injection |
| **`APP_FILTER` token** | Multi-provider — registers globally INSIDE the DI container; supports DI; preferred approach |
| **`APP_FILTER` order** | Multiple `APP_FILTER` providers collect additively; more-specific `@Catch()` wins over less-specific |
| **`HttpException.getResponse()`** | Returns `string` or `object` — use `typeof` to distinguish; object is spread as response body |
| **`HttpException.getStatus()`** | Returns the HTTP status code |
| **`HttpException.cause`** | Wrapped underlying error — not sent to client; used for logging only |
| **Custom exceptions** | Extend `HttpException` or a `DomainException` base — override constructor to add `code`, `meta` fields |
| **Validation errors** | `ValidationPipe` throws `BadRequestException` with `message: string[]`; use `exceptionFactory` to structure at source |
| **`@Catch()` with no args** | Only way to catch non-HttpException (raw `Error`, db errors, etc.) — always needed as a fallback |
| **`res.end()` after filter** | Never call `next()` after sending a response — causes headers-already-sent crash |
| **Testing filters** | Create mock `ArgumentsHost` — no full test module needed; assert on mock response methods |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) knowing the **`APP_FILTER` vs `app.useGlobalFilters()` distinction** precisely — `useGlobalFilters()` instantiates filters outside the IoC container so dependencies cannot be injected, while `APP_FILTER` is a multi-provider that registers the filter class as a regular provider; being able to explain why this matters (a logger, config service, or Sentry client needs injection) and that the `multi: true` behavior means multiple `APP_FILTER` providers accumulate rather than overriding; (2) explaining **`ArgumentsHost` and context switching** — a global filter registered with `@Catch()` receives exceptions from HTTP requests, WebSocket messages, and RPC calls; calling `host.switchToHttp().getResponse()` on a WebSocket exception crashes, so always guard with `host.getType() === 'http'`; (3) the difference between **`HttpAdapterHost` and `host.switchToHttp().getResponse()`** — the latter returns a platform-specific object (Express `res` or Fastify `reply`) with different APIs, while `httpAdapterHost.httpAdapter.reply()` is platform-agnostic; this matters whenever a filter might run on multiple adapters; (4) the **`@Catch()` specificity and execution order** — method-level filters are consulted before controller-level before global, and within each level the first filter whose `@Catch()` matches (via `instanceof`) handles the exception; no other filter runs for that exception; understanding this means being able to predict which filter handles a `NotFoundException` when `@Catch(NotFoundException)` exists at method level and `@Catch(HttpException)` at global level; and (5) **extending `BaseExceptionFilter`** vs implementing `ExceptionFilter` from scratch — `super.catch()` delegates to the default NestJS handling, which is the right approach when you only need to add logging or Sentry capture before the standard response; implementing from scratch is needed when you want to change the response format entirely.
