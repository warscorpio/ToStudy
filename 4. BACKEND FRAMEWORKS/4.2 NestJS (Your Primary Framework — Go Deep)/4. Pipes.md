---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Pipe Fundamentals

**Q1. What is a pipe in NestJS and what are its two core purposes?**
A: A pipe is a class annotated with `@Injectable()` that implements the `PipeTransform` interface. NestJS calls every configured pipe **before** the route handler receives its arguments. Pipes sit between the incoming request and the controller method — they intercept route arguments and either transform or validate them.

The two distinct purposes:

**Transformation**: convert input data to the desired form before the handler receives it — parse a string `"42"` to a number `42`, convert a plain object literal to a typed class instance, normalize an email to lowercase, trim whitespace from strings.

**Validation**: evaluate input and either pass it through unchanged or throw an exception if the input does not satisfy the declared rules. The handler never runs if validation fails.

```
Request lifecycle:
  Incoming request
      │
      ▼
  [Guards]           ← authorization / authentication
      │
      ▼
  [Interceptors]     ← before() — logging, caching, request transformation
      │
      ▼
  [Pipes]            ← TRANSFORM + VALIDATE each @Param, @Body, @Query argument
      │
      ├── valid/transformed → Controller method executes
      │
      └── invalid → throws exception → Exception Filter → error response
                    (handler never called)
      │
      ▼
  [Interceptors]     ← after() — response transformation, mapping
      │
      ▼
  [Exception Filters]
```

```ts
// The PipeTransform interface every pipe implements:
export interface PipeTransform<T = any, R = any> {
  transform(value: T, metadata: ArgumentMetadata): R;
}

// ArgumentMetadata describes the argument the pipe is processing:
export interface ArgumentMetadata {
  type:     'body' | 'query' | 'param' | 'custom'; // which decorator sourced it
  metatype?: Type<unknown>;  // the TypeScript type (e.g., CreateUserDto class)
  data?:    string;          // the name passed to the decorator (e.g., 'id' in @Param('id'))
}
```

**Q2. How can pipes be scoped — parameter-level, method-level, controller-level, and globally — and what are the differences?**
A: NestJS provides four binding scopes. Narrower scopes override broader ones for the same argument.

```ts
// 1. PARAMETER-LEVEL — applies to one specific argument only:
@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {
  //                 ^^^^^^^^^^^^ only this one param goes through the pipe
}

// 2. METHOD-LEVEL — applies to ALL arguments of this handler:
@Get(':id')
@UsePipes(new ValidationPipe({ whitelist: true }))
findOne(@Param('id') id: string, @Body() dto: UpdateUserDto) {
  // both id AND dto pass through ValidationPipe
}

// 3. CONTROLLER-LEVEL — applies to ALL handlers in this controller:
@Controller('users')
@UsePipes(ValidationPipe)
export class UsersController {
  // every @Get, @Post, @Put handler uses ValidationPipe
}

// 4. GLOBAL-LEVEL — applies to EVERY route in the entire application:
// main.ts
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      whitelist:            true,
      forbidNonWhitelisted: true,
      transform:            true,
    }),
  );
  await app.listen(3000);
}
// This is the most common production pattern — one global ValidationPipe

// Alternative: register globally via module (enables DI injection in the pipe):
// app.module.ts
@Module({
  providers: [
    {
      provide:  APP_PIPE,
      useClass: ValidationPipe,
    },
  ],
})
export class AppModule {}
// APP_PIPE token → NestJS registers it as a global pipe with full DI support
// useClass vs useFactory: use useFactory when you need to inject services into the pipe
```

**Q3. What are the built-in pipes NestJS ships with, and when should each be used?**
A: NestJS provides eight built-in pipes for common type-coercion scenarios:

```ts
// ParseIntPipe — parses string to integer, throws on NaN:
@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {}
// GET /users/42  → id = 42 (number)
// GET /users/abc → 400 Bad Request: "Validation failed (numeric string is expected)"

// ParseFloatPipe — parses string to float:
@Get('price/:value')
getPrice(@Param('value', ParseFloatPipe) price: number) {}

// ParseBoolPipe — parses "true"/"false" strings to boolean:
@Get()
find(@Query('active', ParseBoolPipe) active: boolean) {}
// ?active=true  → active = true
// ?active=false → active = false
// ?active=yes   → 400 Bad Request

// ParseArrayPipe — parses comma-separated strings to arrays:
@Get()
findMany(@Query('ids', new ParseArrayPipe({ items: Number, separator: ',' })) ids: number[]) {}
// ?ids=1,2,3 → ids = [1, 2, 3]

// ParseUUIDPipe — validates and passes through UUID strings:
@Get(':id')
findOne(@Param('id', ParseUUIDPipe) id: string) {}
// Validates UUID v1–v5 format; throws on invalid UUID

// ParseEnumPipe — validates value is a member of an enum:
enum Direction { Up = 'UP', Down = 'DOWN' }
@Get(':dir')
move(@Param('dir', new ParseEnumPipe(Direction)) dir: Direction) {}
// GET /UP → dir = 'UP'
// GET /LEFT → 400 Bad Request

// DefaultValuePipe — provides fallback for undefined/null:
@Get()
findAll(
  @Query('page',  new DefaultValuePipe(1),  ParseIntPipe) page: number,
  @Query('limit', new DefaultValuePipe(10), ParseIntPipe) limit: number,
) {}
// ?page=2  → page=2, limit=10 (default)
// no query → page=1, limit=10 (both defaults)
// Pipe execution: DefaultValuePipe first → if value provided, passes through; if not, returns default
// Then ParseIntPipe coerces the string (or default number) to an integer

// ParseFilePipe — validates uploaded files (used with FileInterceptor):
@Post('upload')
@UseInterceptors(FileInterceptor('file'))
uploadFile(
  @UploadedFile(
    new ParseFilePipe({
      validators: [
        new MaxFileSizeValidator({ maxSize: 5 * 1024 * 1024 }), // 5MB
        new FileTypeValidator({ fileType: 'image/jpeg' }),
      ],
    }),
  )
  file: Express.Multer.File,
) {}
```

### Section 2: `class-validator` — Declarative Validation

**Q4. What is `class-validator` and how does it integrate with NestJS's `ValidationPipe`?**
A: `class-validator` is a decorator-based validation library. Decorators are applied to class properties; calling `validate(instance)` returns an array of validation errors. It works with class *instances*, not plain objects — which is why `class-transformer` is needed to convert the incoming plain JSON body into an instance first.

```ts
// Install:
// npm install class-validator class-transformer

// DTO with class-validator decorators:
import { IsString, IsEmail, IsNumber, IsOptional, Min, Max, MinLength } from 'class-validator';

export class CreateUserDto {
  @IsString()
  @MinLength(2, { message: 'Name must be at least 2 characters' })
  name: string;

  @IsEmail({}, { message: 'Invalid email format' })
  email: string;

  @IsNumber()
  @Min(13, { message: 'Must be at least 13 years old' })
  @Max(120)
  age: number;

  @IsOptional()      // field may be absent entirely — if present, validates below
  @IsString()
  bio?: string;
}

// Without pipes — manual validation:
import { validate } from 'class-validator';
import { plainToInstance } from 'class-transformer';

const plain   = { name: 'Alice', email: 'alice@example.com', age: 30 };
const dto     = plainToInstance(CreateUserDto, plain); // plain object → class instance
const errors  = await validate(dto);
if (errors.length > 0) throw new BadRequestException(errors);

// With ValidationPipe (automatic — what you use in practice):
// ValidationPipe does plainToInstance + validate internally
// You just declare the DTO type on the parameter:
@Post()
create(@Body() dto: CreateUserDto) {
  // dto is already validated — this code only runs if all decorators pass
}
```

The `ValidationPipe` internally does three things:
1. Reads the `metatype` from `ArgumentMetadata` (the `CreateUserDto` class)
2. Uses `plainToInstance(metatype, value)` to convert the plain JSON body to a class instance
3. Calls `validate(instance)` and throws `BadRequestException` with formatted errors if any fail

**Q5. What are the most important `class-validator` decorators and what do they check?**
A: Grouped by category:

```ts
import {
  // String validators:
  IsString, IsNotEmpty, MinLength, MaxLength, Matches, IsEmail,
  IsUrl, IsUUID, IsAlpha, IsAlphanumeric, Contains,

  // Number validators:
  IsNumber, IsInt, Min, Max, IsPositive, IsNegative,

  // Boolean:
  IsBoolean,

  // Date:
  IsDate, IsDateString, MinDate, MaxDate,

  // Array:
  IsArray, ArrayNotEmpty, ArrayMinSize, ArrayMaxSize, ArrayUnique,

  // Object / nested:
  IsObject, ValidateNested, IsInstance,

  // Enum:
  IsEnum,

  // Presence:
  IsOptional, IsDefined, IsNotEmpty,

  // Type coercion in validator (unusual — prefer class-transformer):
  IsNumberString, IsBooleanString,

  // Conditional:
  ValidateIf,
} from 'class-validator';

export class AdvancedDto {
  @IsString()
  @IsNotEmpty()                    // not empty string '' (different from @IsDefined)
  @MinLength(3)
  @MaxLength(50)
  username: string;

  @IsEmail()
  email: string;

  @IsUrl({ protocols: ['https'] }) // only HTTPS URLs
  website: string;

  @IsUUID('4')                     // specifically UUID v4
  tenantId: string;

  @Matches(/^[A-Z][a-z]+$/, { message: 'Must start with capital letter' })
  firstName: string;

  @IsInt()                         // must be an integer (no decimals)
  @Min(0)
  @Max(100)
  score: number;

  @IsEnum(UserRole)                // must be a value in the UserRole enum
  role: UserRole;

  @IsArray()
  @ArrayNotEmpty()
  @ArrayUnique()                   // all elements must be unique
  @IsString({ each: true })        // each array element must be a string
  tags: string[];

  @IsOptional()
  @IsDateString()                  // ISO 8601 date string format
  birthDate?: string;

  @ValidateIf(o => o.accountType === 'business') // only validate if condition is true
  @IsString()
  @IsNotEmpty()
  companyName?: string;
}
```

**Q6. What is `@ValidateNested()` and why is `@Type()` from `class-transformer` required alongside it?**
A: `@ValidateNested()` tells class-validator to recursively validate a nested object property using the nested object's own class-validator decorators. But class-validator receives a plain JavaScript object `{}` for the nested property — it has no decorators, because decorators are metadata on a *class*, not on a plain object literal.

`@Type(() => NestedClass)` from class-transformer instructs the transformation step to convert the plain nested object into an instance of `NestedClass` before validation runs. Without `@Type`, validation of nested objects silently passes (no class instance = no decorator metadata = no validation).

```ts
// address.dto.ts
import { IsString, IsPostalCode, IsNotEmpty } from 'class-validator';

export class AddressDto {
  @IsString() @IsNotEmpty()
  street: string;

  @IsString() @IsNotEmpty()
  city: string;

  @IsPostalCode('US')
  postalCode: string;
}

// create-user.dto.ts
import { ValidateNested, IsString, IsArray, ArrayNotEmpty } from 'class-validator';
import { Type } from 'class-transformer';

export class CreateUserDto {
  @IsString()
  name: string;

  // Single nested object:
  @ValidateNested()          // validate the nested object recursively
  @Type(() => AddressDto)    // convert plain object → AddressDto instance first
  address: AddressDto;

  // Array of nested objects:
  @IsArray()
  @ArrayNotEmpty()
  @ValidateNested({ each: true })   // validate EACH element in the array
  @Type(() => AddressDto)           // convert EACH plain object → AddressDto instance
  addresses: AddressDto[];
}

// What happens without @Type():
// Input: { name: 'Alice', address: { street: '123 Main', city: '', postalCode: 'bad' } }
// Without @Type: address is a plain object {} — no class decorators → validates as VALID (bug!)
// With @Type:    address is AddressDto instance → @IsNotEmpty() on city fails → 400 error ✓
```

**Q7. How do you write a custom class-validator decorator for business logic validation?**
A: Custom validators implement the `ValidatorConstraintInterface` and are registered with `@ValidatorConstraint()`. The constraint class is then used in a custom decorator.

```ts
import {
  registerDecorator, ValidationOptions, ValidationArguments,
  ValidatorConstraint, ValidatorConstraintInterface,
} from 'class-validator';
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';

// Step 1: Implement the constraint:
@ValidatorConstraint({ name: 'isUniqueEmail', async: true })
@Injectable()
export class IsUniqueEmailConstraint implements ValidatorConstraintInterface {
  constructor(
    @InjectRepository(User)
    private readonly userRepository: Repository<User>,
  ) {}

  async validate(email: string, args: ValidationArguments): Promise<boolean> {
    const user = await this.userRepository.findOne({ where: { email } });
    return !user; // return true = valid, false = invalid
  }

  defaultMessage(args: ValidationArguments): string {
    return `Email "${args.value}" is already registered`;
  }
}

// Step 2: Create the decorator factory:
export function IsUniqueEmail(validationOptions?: ValidationOptions) {
  return function (object: object, propertyName: string) {
    registerDecorator({
      target:     object.constructor,
      propertyName,
      options:    validationOptions,
      constraints: [],
      validator:  IsUniqueEmailConstraint,   // reference the constraint class
    });
  };
}

// Step 3: Register the constraint as a provider (for DI):
// app.module.ts
@Module({
  providers: [IsUniqueEmailConstraint],  // DI-enabled, gets userRepository injected
})
export class AppModule {}

// Also: enable DI in ValidationPipe:
app.useGlobalPipes(new ValidationPipe({
  transform: true,
  whitelist: true,
  // without useContainer, async validators can't use DI:
}));
// And: wire up class-validator's DI to NestJS's container:
import { useContainer } from 'class-validator';
useContainer(app.select(AppModule), { fallbackOnErrors: true });

// Step 4: Use the decorator:
export class RegisterDto {
  @IsEmail()
  @IsUniqueEmail({ message: 'This email is already in use' })
  email: string;
}
```

### Section 3: `class-transformer` — Object Transformation

**Q8. What is `class-transformer` and what transformation does it enable beyond what `class-validator` does?**
A: `class-transformer` converts between plain JavaScript objects (from JSON bodies, database query results) and typed class instances, applying transformation rules declared as decorators. While `class-validator` only *checks* values, `class-transformer` actually *changes* them.

```ts
import { Expose, Exclude, Transform, Type } from 'class-transformer';
import { plainToInstance, instanceToPlain } from 'class-transformer';

// @Exclude() — remove a property from the output:
export class UserResponseDto {
  @Expose() id: number;
  @Expose() email: string;
  @Exclude()               // password is NEVER included in the plain output
  password: string;
}

// @Expose() with excludeExtraneousValues — whitelist properties:
// Only @Expose()-decorated properties appear; everything else is stripped
const user = plainToInstance(UserResponseDto, rawDbUser, {
  excludeExtraneousValues: true, // WITHOUT this, @Expose has no effect on exclusion
});

// @Transform() — custom transformation function:
export class ProductDto {
  @Transform(({ value }) => value.trim().toLowerCase())
  slug: string;

  @Transform(({ value }) => parseFloat(value.toFixed(2)))
  price: number;

  @Transform(({ value }) => new Date(value))
  createdAt: Date;

  // Transform on serialization (to plain object) — useful for responses:
  @Transform(({ value }) => value?.toString(), { toPlainOnly: true })
  bigIntId: bigint;
}

// @Type() — specify the class to use for a nested property:
export class OrderDto {
  @Type(() => UserDto)
  buyer: UserDto;          // plain object → UserDto instance (with its decorators)

  @Type(() => ProductDto)
  items: ProductDto[];     // each plain object in array → ProductDto instance
}

// plainToInstance vs instanceToPlain:
const plain    = { name: '  Alice  ', email: 'ALICE@EXAMPLE.COM', password: 'secret' };
const instance = plainToInstance(UserResponseDto, plain);
// → UserResponseDto { name: '  Alice  ', email: 'ALICE@EXAMPLE.COM', password: 'secret' }
// (no transformation yet unless @Transform decorators applied)

const output   = instanceToPlain(instance, { excludeExtraneousValues: true });
// → { name: '...', email: '...' }  ← password stripped by @Exclude
```

**Q9. What is the `transform` option on `ValidationPipe` and what does it enable?**
A: When `transform: true` is set on `ValidationPipe`, NestJS automatically converts incoming values to the TypeScript type declared for each parameter — without requiring explicit `@Type()` decorators for primitive route parameters.

```ts
// With transform: false (default):
@Get(':id')
findOne(@Param('id') id: string) {
  typeof id; // 'string' — URL params are always strings, never coerced
}

// With transform: true on ValidationPipe:
@Get(':id')
findOne(@Param('id') id: number) {
  typeof id; // 'number' — ValidationPipe coerced '42' → 42 automatically
  // Equivalent to manually adding ParseIntPipe
}

// Also enables automatic class instantiation for body DTOs:
// With transform: false: body is a plain object {} (no class instance, no @Transform decorators run)
// With transform: true:  body is converted to the declared DTO class instance
//                        → @Transform decorators execute
//                        → DTO methods are available (if any)
//                        → instanceof checks work

// Global setup — recommended for most applications:
app.useGlobalPipes(
  new ValidationPipe({
    transform:            true,   // auto-coerce primitives; instantiate DTO classes
    whitelist:            true,   // strip properties without decorators
    forbidNonWhitelisted: true,   // throw if extra properties sent (not just strip)
    transformOptions: {
      enableImplicitConversion: true, // coerce without explicit @Type() on primitives
    },
  }),
);

// enableImplicitConversion — deeper coercion:
// Without it: @Param('page') page: number → still 'string' unless ParseIntPipe used
// With it:    TypeScript type hint 'number' causes coercion automatically
// Trade-off: implicit can cause surprising behaviors — prefer explicit @Type() on complex types
```

**Q10. What is the `whitelist` option and how does it differ from `forbidNonWhitelisted`?**
A: These two options address the **mass assignment vulnerability** — where an attacker sends extra fields (like `role: 'admin'`) in the request body hoping the server passes them through to the database or business logic.

```ts
export class CreateUserDto {
  @IsString() name: string;
  @IsEmail()  email: string;
  // no 'role' property — deliberately not exposed
}

// Scenario: attacker sends { name: 'Alice', email: 'a@b.com', role: 'admin' }

// Without whitelist (default: false):
// ValidationPipe passes ALL fields through — role: 'admin' reaches the handler
// If handler does: userRepository.save(dto) → role is saved → privilege escalation!

// whitelist: true — silently STRIPS extra properties:
// dto received by handler = { name: 'Alice', email: 'a@b.com' }
// 'role' is removed before the handler runs — no error, just stripped
// Protects against mass assignment — handler never sees undeclared fields

// forbidNonWhitelisted: true — THROWS 400 if extra properties sent:
// Response: { statusCode: 400, message: ['property role should not exist'] }
// Stricter: rejects the entire request instead of silently ignoring extra fields
// Better developer experience: tells the client "you sent something unexpected"

// Recommended combination for APIs:
new ValidationPipe({
  whitelist:            true,    // strip extra props
  forbidNonWhitelisted: true,    // AND throw if extras are found
  transform:            true,
})

// Note: these only apply to properties declared with class-validator decorators
// A property with NO decorators at all is treated the same as an unknown property:
export class Dto {
  @IsString() name: string;    // ← decorated → allowed
  age: number;                  // ← no decorator → stripped (whitelist) or rejected (forbidNonWhitelisted)
}
```

### Section 4: Custom Pipes

**Q11. What is the full anatomy of a custom pipe and what responsibilities does `transform()` have?**
A: A custom pipe is a class implementing `PipeTransform`. The `transform` method receives the raw value and metadata, does its work, and either returns the transformed value or throws an exception.

```ts
import { PipeTransform, Injectable, ArgumentMetadata, BadRequestException } from '@nestjs/common';

@Injectable()
export class ParsePositiveIntPipe implements PipeTransform<string, number> {
  //                                                       ^input  ^output types

  transform(value: string, metadata: ArgumentMetadata): number {
    // value:    the raw input (always string for @Param, @Query)
    // metadata: { type: 'param', metatype: Number, data: 'id' }

    // Step 1: coerce type
    const parsed = parseInt(value, 10);

    // Step 2: validate the coerced value
    if (isNaN(parsed)) {
      throw new BadRequestException(
        `Validation failed: '${value}' is not a number (param: ${metadata.data})`
      );
    }
    if (parsed <= 0) {
      throw new BadRequestException(
        `Validation failed: '${value}' must be a positive integer (param: ${metadata.data})`
      );
    }

    // Step 3: return the transformed value (what the handler receives)
    return parsed;
  }
}

// Usage:
@Get(':id')
findOne(@Param('id', ParsePositiveIntPipe) id: number) {
  // id is guaranteed to be a positive integer — or 400 was already thrown
}

// Pipe with constructor options (configurable pipe):
@Injectable()
export class ParseIntRangePipe implements PipeTransform<string, number> {
  constructor(
    private readonly min: number,
    private readonly max: number,
  ) {}

  transform(value: string, metadata: ArgumentMetadata): number {
    const parsed = parseInt(value, 10);
    if (isNaN(parsed))        throw new BadRequestException(`Expected a number`);
    if (parsed < this.min)    throw new BadRequestException(`Must be >= ${this.min}`);
    if (parsed > this.max)    throw new BadRequestException(`Must be <= ${this.max}`);
    return parsed;
  }
}

// Usage — instantiate with options:
@Get(':page')
getPage(@Param('page', new ParseIntRangePipe(1, 1000)) page: number) {}
```

**Q12. When should you create a custom pipe rather than using `class-validator` decorators or built-in pipes?**
A: The choice depends on what you're doing and where you need to do it:

```
Use built-in pipes (ParseIntPipe, ParseUUIDPipe, etc.) when:
  → Converting a single @Param or @Query from string to a primitive type
  → The conversion is standard (int, float, bool, UUID, enum)
  → No custom error messages needed

Use class-validator decorators + ValidationPipe when:
  → Validating the shape and values of a @Body() DTO
  → Multiple fields with interdependencies (@ValidateIf)
  → The validation rule is reusable across multiple DTOs
  → You want declarative, colocated validation rules on the DTO class

Use a CUSTOM PIPE when:
  → Transformation requires application logic not expressible as decorators
    (e.g., fetch a related entity from DB based on an ID param → return the entity)
  → You need to transform @Param or @Query in a way no built-in pipe handles
    (e.g., parse a custom date format, decode a JWT, parse a compound ID "type:id")
  → You want encapsulated transformation logic applied consistently across routes
  → The same transformation is needed on multiple parameters across controllers
  → You need to access NestJS services inside the transformation

// Example of the "entity from ID" pattern — a pipe that fetches from the DB:
@Injectable()
export class UserByIdPipe implements PipeTransform<string, Promise<User>> {
  constructor(private readonly usersService: UsersService) {}

  async transform(id: string, metadata: ArgumentMetadata): Promise<User> {
    const parsed = parseInt(id, 10);
    if (isNaN(parsed)) throw new BadRequestException('Invalid user ID');

    const user = await this.usersService.findOne(parsed);
    if (!user) throw new NotFoundException(`User #${parsed} not found`);

    return user; // handler receives User entity directly — no findOne() in handler
  }
}

// Handler receives entity directly — no boilerplate:
@Get(':userId')
getUser(@Param('userId', UserByIdPipe) user: User) {
  return user; // already fetched and validated
}
```

### Section 5: Transformation Pipes

**Q13. What are transformation pipes (as distinct from validation-only pipes) and what patterns do they implement?**
A: A transformation pipe changes the shape or type of data — it returns something different from what it received. Validation pipes check and pass through (or throw). Transformation pipes actively rewrite the value.

```ts
// Pattern 1: String normalization pipe — trim and lowercase:
@Injectable()
export class NormalizeEmailPipe implements PipeTransform<string, string> {
  transform(value: string): string {
    if (typeof value !== 'string') return value;
    return value.trim().toLowerCase();
  }
}

// Pattern 2: Sanitization pipe — strip HTML to prevent XSS:
import * as sanitizeHtml from 'sanitize-html';

@Injectable()
export class StripHtmlPipe implements PipeTransform<string, string> {
  transform(value: string): string {
    if (typeof value !== 'string') return value;
    return sanitizeHtml(value, { allowedTags: [], allowedAttributes: {} });
  }
}

// Pattern 3: JSON parsing pipe — parse stringified JSON query params:
@Injectable()
export class ParseJsonPipe implements PipeTransform {
  transform(value: string, metadata: ArgumentMetadata) {
    if (typeof value !== 'string') return value;
    try {
      return JSON.parse(value);
    } catch {
      throw new BadRequestException(
        `Parameter '${metadata.data}' must be valid JSON`
      );
    }
  }
}

// Usage:
@Get()
search(
  @Query('filter', ParseJsonPipe) filter: Record<string, unknown>,
) {}
// GET /search?filter={"status":"active","minAge":18}
// filter = { status: 'active', minAge: 18 }  (parsed object, not string)

// Pattern 4: Default value + type coercion in one pipe:
@Injectable()
export class PaginationPipe implements PipeTransform {
  transform(value: any): { page: number; limit: number; offset: number } {
    const page  = Math.max(1,  parseInt(value?.page  ?? '1',  10) || 1);
    const limit = Math.min(100, parseInt(value?.limit ?? '20', 10) || 20);
    return { page, limit, offset: (page - 1) * limit };
  }
}

// Pattern 5: File transformation pipe — reads stream, computes hash:
@Injectable()
export class FileHashPipe implements PipeTransform {
  async transform(file: Express.Multer.File): Promise<Express.Multer.File & { hash: string }> {
    const hash = crypto.createHash('sha256').update(file.buffer).digest('hex');
    return { ...file, hash };
  }
```

**Q14. What is `ValidationPipe`'s `exceptionFactory` option and how do you customize error response format?**
A: By default, `ValidationPipe` throws a `BadRequestException` with NestJS's default error shape. The `exceptionFactory` option lets you intercept the raw `ValidationError[]` array and return any exception you want — reshaping the error response.

```ts
import { ValidationError } from 'class-validator';
import { BadRequestException } from '@nestjs/common';

// Default error shape (without exceptionFactory):
// {
//   "statusCode": 400,
//   "message": ["name must be a string", "email must be an email"],
//   "error": "Bad Request"
// }

// Custom error shape — nested, field-keyed errors:
function formatValidationErrors(errors: ValidationError[]): Record<string, string[]> {
  const formatted: Record<string, string[]> = {};

  function flatten(errors: ValidationError[], prefix = '') {
    for (const error of errors) {
      const field = prefix ? `${prefix}.${error.property}` : error.property;
      if (error.constraints) {
        formatted[field] = Object.values(error.constraints);
      }
      if (error.children?.length) {
        flatten(error.children, field); // recurse into nested DTOs
      }
    }
  }

  flatten(errors);
  return formatted;
}

app.useGlobalPipes(
  new ValidationPipe({
    transform:            true,
    whitelist:            true,
    forbidNonWhitelisted: true,
    exceptionFactory(errors: ValidationError[]) {
      return new BadRequestException({
        statusCode: 400,
        error:      'Validation Failed',
        fields:     formatValidationErrors(errors),
        // { "email": ["email must be an email"], "address.city": ["must not be empty"] }
      });
    },
  }),
);

// Output with custom factory:
// {
//   "statusCode": 400,
//   "error": "Validation Failed",
//   "fields": {
//     "name": ["name must be longer than or equal to 2 characters"],
//     "email": ["email must be an email"],
//     "address.city": ["city should not be empty"]
//   }
// }
```

**Q15. "What is the difference between `skipMissingProperties: true` and marking a field `@IsOptional()`?"**
A: Both deal with optional fields but at different levels with different semantics:

```ts
// @IsOptional() on a property:
export class UpdateUserDto {
  @IsOptional()     // ← if 'name' is absent from the body, SKIP all other decorators on it
  @IsString()       // ← only checked if 'name' is present
  @MinLength(2)     // ← only checked if 'name' is present
  name?: string;

  @IsOptional()
  @IsEmail()
  email?: string;
}
// Effect: if a field is missing (undefined/null), its other validators are skipped
// But: a field WITH @IsOptional() that IS present still validates against its other decorators

// skipMissingProperties: true on ValidationPipe:
new ValidationPipe({ skipMissingProperties: true })
// Effect: GLOBALLY skips validation for ANY missing (undefined) property in ANY DTO
// Equivalent to adding @IsOptional() to every single property
// Use case: PATCH endpoints where any field may be absent (partial update)

// Key difference:
// @IsOptional() is per-field and explicit — you choose which fields are optional
// skipMissingProperties is global — makes ALL fields optional, which can mask required-field bugs

// Best practice for PATCH endpoints: use a separate PartialType DTO:
import { PartialType } from '@nestjs/mapped-types';

export class CreateUserDto {
  @IsString() @MinLength(2) name: string;  // required in creation
  @IsEmail()               email: string; // required in creation
}

export class UpdateUserDto extends PartialType(CreateUserDto) {
  // PartialType makes all properties optional (adds @IsOptional() to each)
  // AND keeps all other validators (IsString, IsEmail, etc.) — they run if the field is present
  // This is the cleanest pattern for PATCH endpoints
}
// UpdateUserDto = { name?: string; email?: string } with validators active when present
```

**Q16. "A junior developer is sending requests but getting unexpected 400 errors with `property X should not exist` — what's causing it and how do you fix it?"**
A: This is the `forbidNonWhitelisted` option throwing because the client is sending a property that has no class-validator decorator on the DTO.

```ts
// DTO:
export class CreateProductDto {
  @IsString() name: string;
  @IsNumber() price: number;
}

// Client sends: { name: 'Widget', price: 9.99, category: 'tools' }
// Error: "property category should not exist"

// Cause 1: The property is genuinely unknown (client bug — sending extra field):
// Fix: tell the client not to send 'category' — or add the field to the DTO

// Cause 2: The property IS expected but missing a decorator:
export class CreateProductDto {
  @IsString() name: string;
  @IsNumber() price: number;
  category: string; // ← no decorator → treated as "should not exist" by whitelist
  // Fix: add @IsString() @IsOptional() category?: string;
}

// Cause 3: Nested object properties — outer DTO has whitelist, nested doesn't:
export class OrderDto {
  @IsString() orderId: string;
  @ValidateNested()
  @Type(() => AddressDto)
  address: AddressDto; // ← if AddressDto properties lack decorators → forbidden

// Cause 4: Using @Exclude() from class-transformer expecting it to work like whitelist:
// @Exclude() only affects serialization (toPlain) — not incoming validation
// For incoming: use class-validator decorators on the DTO

// Debugging approach:
// Temporarily disable forbidNonWhitelisted and log the received body:
@Post()
```

## Problem 2 — Custom Validation Decorator: Cross-Field Validation

### Problem
A `CreateEventDto` must validate that `endDate` is after `startDate`, that if `isPaid` is `true` then `price` must be provided and positive, and that `maxAttendees` is at least 1. These rules involve multiple fields — impossible to express with single-field decorators alone.

```ts
// ❌ Can't do cross-field validation with single-field decorators:
export class CreateEventDto {
  startDate: Date;
  endDate: Date;    // how to check endDate > startDate here?
  isPaid: boolean;
  price?: number;   // how to require price only when isPaid = true?
}
```

### Solution: Class-Level Custom Validators

```ts
import {
  registerDecorator, ValidationOptions, ValidationArguments,
  ValidatorConstraint, ValidatorConstraintInterface,
  IsDate, IsBoolean, IsOptional, IsNumber, IsPositive,
  IsString, IsInt, Min, validate,
} from 'class-validator';
import { Type } from 'class-transformer';

// Constraint 1: endDate must be after startDate:
@ValidatorConstraint({ name: 'isAfterDate', async: false })
export class IsAfterDateConstraint implements ValidatorConstraintInterface {
  validate(endDate: Date, args: ValidationArguments): boolean {
    const [relatedPropertyName] = args.constraints;  // 'startDate'
    const obj   = args.object as any;
    const startDate = obj[relatedPropertyName];

    if (!(endDate instanceof Date) || !(startDate instanceof Date)) return true; // skip if not dates
    return endDate.getTime() > startDate.getTime();
  }

  defaultMessage(args: ValidationArguments): string {
    const [relatedPropertyName] = args.constraints;
    return `${args.property} must be after ${relatedPropertyName}`;
  }
}

export function IsAfterDate(
  property: string,
  validationOptions?: ValidationOptions,
) {
  return (object: object, propertyName: string) => {
    registerDecorator({
      target:      object.constructor,
      propertyName,
      options:     validationOptions,
      constraints: [property],       // pass the related property name
      validator:   IsAfterDateConstraint,
    });
  };
}

// Constraint 2: field required when another field is true:
@ValidatorConstraint({ name: 'isRequiredWhen', async: false })
export class IsRequiredWhenConstraint implements ValidatorConstraintInterface {
  validate(value: any, args: ValidationArguments): boolean {
    const [conditionProperty, conditionValue] = args.constraints;
    const obj = args.object as any;

    // If condition is not met, field is not required:
    if (obj[conditionProperty] !== conditionValue) return true;

    // Condition IS met — value must be present and not null/undefined/empty:
    return value !== null && value !== undefined && value !== '';
  }

  defaultMessage(args: ValidationArguments): string {
    const [conditionProperty, conditionValue] = args.constraints;
    return `${args.property} is required when ${conditionProperty} is ${conditionValue}`;
  }
}

export function IsRequiredWhen(
  conditionProperty: string,
  conditionValue: any,
  validationOptions?: ValidationOptions,
) {
  return (object: object, propertyName: string) => {
    registerDecorator({
      target:      object.constructor,
      propertyName,
      options:     validationOptions,
      constraints: [conditionProperty, conditionValue],
      validator:   IsRequiredWhenConstraint,
    });
  };
}

// DTO using custom validators:
export class CreateEventDto {
  @IsString()
  @IsNotEmpty()
  title: string;

  @IsDate()
  @Type(() => Date)           // transform ISO string → Date instance
  startDate: Date;

  @IsDate()
  @Type(() => Date)
  @IsAfterDate('startDate', { message: 'End date must be after start date' })
  endDate: Date;

  @IsBoolean()
  isPaid: boolean;

  @IsOptional()                    // optional in terms of class-validator
  @IsRequiredWhen('isPaid', true)  // but required when isPaid is true
  @IsNumber({ maxDecimalPlaces: 2 })
  @IsPositive()
  price?: number;

  @IsInt()
  @Min(1)
  maxAttendees: number;

  @IsOptional()
  @ValidateIf(o => o.isPaid)       // only validate description format when paid
  @IsString()
  @IsNotEmpty()
  pricingDescription?: string;
}
```

```ts
// 1. Base entity pipe (generic — reusable for any entity):
import {
  PipeTransform, Injectable, ArgumentMetadata,
  BadRequestException, NotFoundException, Type,
} from '@nestjs/common';

export interface EntityService<T> {
  findOne(id: number): Promise<T | null>;
}

// Generic factory function that creates a typed pipe for any service:
export function EntityByIdPipe<T>(
  serviceToken: Type<EntityService<T>>,
  entityName: string,
): Type<PipeTransform> {
  @Injectable()
  class EntityPipe implements PipeTransform<string, Promise<T>> {
    constructor(private readonly service: EntityService<T>) {}

    async transform(value: string, metadata: ArgumentMetadata): Promise<T> {
      const id = parseInt(value, 10);
      if (isNaN(id) || id <= 0) {
        throw new BadRequestException(
          `Invalid ${entityName} ID: '${value}' — must be a positive integer`,
        );
      }

      const entity = await this.service.findOne(id);
      if (!entity) {
        throw new NotFoundException(`${entityName} with ID ${id} not found`);
      }

      return entity;
    }
  }

  // Wire DI: tell NestJS to inject the service into EntityPipe:
  Injectable()(EntityPipe);
  // Inject service by token:
  Reflect.defineMetadata(
    'design:paramtypes',
    [serviceToken],
    EntityPipe,
  );

  return EntityPipe;
}
```

## Problem 4 — Query Parameter Transformation and Normalization Pipe

### Problem
A search endpoint receives filter, sort, and pagination parameters as query strings. Raw query strings come in as: `?status=ACTIVE,PENDING&sort=createdAt:desc&page=2&limit=50&tags=js,ts,node`. Build a `SearchQueryPipe` that parses and normalizes these into a typed object.

```ts
// ❌ Without pipe — query parsing scattered in handler:
@Get()
search(
  @Query('status') statusStr: string,
  @Query('sort')   sortStr:   string,
  @Query('page')   pageStr:   string,
  @Query('limit')  limitStr:  string,
  @Query('tags')   tagsStr:   string,
) {
  const statuses = statusStr?.split(',').filter(Boolean) ?? [];
  const [sortField, sortDir] = sortStr?.split(':') ?? ['createdAt', 'desc'];
  const page  = Math.max(1, parseInt(pageStr ?? '1'));
  const limit = Math.min(100, parseInt(limitStr ?? '20'));
  const offset = (page - 1) * limit;
  const tags = tagsStr?.split(',').filter(Boolean) ?? [];
  // 8 lines before any business logic — repeated in every search endpoint

```

### Solution: Typed Query DTO + Transformation Pipe

```ts
// 1. Output type:
export enum SortDirection { Asc = 'asc', Desc = 'desc' }

export interface ParsedSearchQuery {
  statuses:  string[];
  sort:      { field: string; direction: SortDirection };
  page:      number;
  limit:     number;
  offset:    number;
  tags:      string[];
  search?:   string;
}

// 2. Transformation pipe:
@Injectable()
export class SearchQueryPipe implements PipeTransform<Record<string, string>, ParsedSearchQuery> {
  // Allowed sort fields (whitelist — prevent SQL injection via sort param):
  private readonly ALLOWED_SORT_FIELDS = new Set([
    'createdAt', 'updatedAt', 'name', 'price', 'relevance',
  ]);

  // Allowed statuses:
  private readonly ALLOWED_STATUSES = new Set([
    'active', 'inactive', 'pending', 'archived',
  ]);

  transform(query: Record<string, string>): ParsedSearchQuery {
    return {
      statuses: this.parseStatuses(query.status),
      sort:     this.parseSort(query.sort),
      page:     this.parsePage(query.page),
      limit:    this.parseLimit(query.limit),
      offset:   this.parseOffset(query.page, query.limit),
      tags:     this.parseTags(query.tags),
      search:   query.search?.trim() || undefined,
    };
  }

  private parseStatuses(value?: string): string[] {
    if (!value) return [];
    return value
      .split(',')
      .map(s => s.trim().toLowerCase())
      .filter(s => {
        if (!this.ALLOWED_STATUSES.has(s)) {
          throw new BadRequestException(
            `Invalid status: '${s}'. Allowed: ${[...this.ALLOWED_STATUSES].join(', ')}`
          );
        }
        return true;
      });
  }

  private parseSort(value?: string): { field: string; direction: SortDirection } {
    const DEFAULT = { field: 'createdAt', direction: SortDirection.Desc };
    if (!value) return DEFAULT;

    const parts = value.split(':');
    const field = parts[0]?.trim();
    const dir   = (parts[1]?.trim().toLowerCase() ?? 'desc') as SortDirection;

    if (!this.ALLOWED_SORT_FIELDS.has(field)) {
      throw new BadRequestException(
        `Invalid sort field: '${field}'. Allowed: ${[...this.ALLOWED_SORT_FIELDS].join(', ')}`
      );
    }
    if (!Object.values(SortDirection).includes(dir)) {
      throw new BadRequestException(`Sort direction must be 'asc' or 'desc'`);
    }

    return { field, direction: dir };
  }

  private parsePage(value?: string): number {
    const page = parseInt(value ?? '1', 10);
    if (isNaN(page) || page < 1) throw new BadRequestException('page must be >= 1');
    if (page > 10000) throw new BadRequestException('page must be <= 10000');
    return page;
  }

  private parseLimit(value?: string): number {
    const limit = parseInt(value ?? '20', 10);
    if (isNaN(limit) || limit < 1)  throw new BadRequestException('limit must be >= 1');
    if (limit > 100)                throw new BadRequestException('limit must be <= 100');
    return limit;
  }

  private parseOffset(pageStr?: string, limitStr?: string): number {
    const page  = this.parsePage(pageStr);
    const limit = this.parseLimit(limitStr);
    return (page - 1) * limit;
  }

  private parseTags(value?: string): string[] {
    if (!value) return [];
    return [...new Set(            // deduplicate
      value
        .split(',')
        .map(t => t.trim().toLowerCase())
        .filter(Boolean)
    )];
  }
}

// 3. Controller usage — single decorated parameter:
@Controller('products')
export class ProductsController {
  @Get('search')
  search(@Query(SearchQueryPipe) query: ParsedSearchQuery) {
    // query = {
    //   statuses: ['active', 'pending'],
    //   sort: { field: 'createdAt', direction: 'desc' },
    //   page: 2, limit: 50, offset: 50,
    //   tags: ['js', 'ts', 'node'],
    //   search: undefined
    // }
    return this.productsService.search(query);
  }
}
```

## Problem 5 — Response Transformation Pipe with `class-transformer` (Exclude Sensitive Fields)

### Problem
User entities contain sensitive fields (`password`, `resetToken`, `internalNotes`). These must never appear in API responses. Implement a transformation pipe that strips sensitive fields and shapes responses, and compare it with the `ClassSerializerInterceptor` approach.

```ts
// ❌ Naive approach — forgetting to exclude sensitive fields:
@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {
  return this.usersService.findOne(id);
  // Returns: { id: 1, name: 'Alice', email: '...', password: 'hash', resetToken: '...' }
  // Password hash and reset token exposed in API response!
}
```

### Solution A: Response DTO + ClassSerializerInterceptor (NestJS Standard)

```ts
// 1. Define a response DTO with @Expose() on safe fields only:
import { Expose, Exclude, Transform } from 'class-transformer';

@Exclude()  // exclude EVERYTHING by default — only @Expose() fields appear
export class UserResponseDto {
  @Expose()
  id: number;

  @Expose()
  name: string;

  @Expose()
  email: string;

  @Expose()
  role: string;

  @Expose()
  @Transform(({ value }) => value?.toISOString())
  createdAt: Date;

  // These are NOT @Expose() → excluded from output:
  // password, resetToken, internalNotes, deletedAt — never serialized
}

// 2. Map entity to response DTO in the service:
import { plainToInstance } from 'class-transformer';

@Injectable()
export class UsersService {
  async findOne(id: number): Promise<UserResponseDto> {
    const user = await this.userRepository.findOne({ where: { id } });
    if (!user) throw new NotFoundException();

    // Map to response DTO — strips sensitive fields:
    return plainToInstance(UserResponseDto, user, {
      excludeExtraneousValues: true,  // only @Expose() fields kept
    });
  }
}

// 3. Or use ClassSerializerInterceptor — automatic transformation on every response:
// main.ts:
import { ClassSerializerInterceptor, ReflectMetadata } from '@nestjs/common';
import { Reflector } from '@nestjs/core';

app.useGlobalInterceptors(new ClassSerializerInterceptor(app.get(Reflector)));

// Controller — annotate response type:
@Controller('users')
@SerializeOptions({ excludeExtraneousValues: true })  // apply to all handlers
export class UsersController {
  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.usersService.findOne(id); // returns User entity
    // ClassSerializerInterceptor applies @Exclude/@Expose automatically
  }
}
```

### Solution B: Custom Response Transformation Pipe

```ts
// For cases where ClassSerializerInterceptor is too coarse
// or you need transformation in the request pipeline:

@Injectable()
export class SerializeUserPipe implements PipeTransform {
  transform(user: User): UserResponseDto {
    return plainToInstance(UserResponseDto, user, {
      excludeExtraneousValues: true,
    });
  }
}

// Factory pipe — configurable for any DTO class:
export function SerializePipe<T>(cls: Type<T>): Type<PipeTransform> {
  @Injectable()
  class MixinSerializePipe implements PipeTransform {
    transform(value: any): T {
      return plainToInstance(cls, value, { excludeExtraneousValues: true });
    }
  }
  return MixinSerializePipe;
}

// Usage — applied to the handler output (uncommon pattern but valid for specific cases):
@Get(':id')
@UsePipes(SerializePipe(UserResponseDto))
async findOne(@Param('id', ParseIntPipe) id: number) {
  return this.usersService.findOneEntity(id); // returns raw User
  // pipe transforms User → UserResponseDto before sending response
}

// Nested response DTOs:
@Exclude()
export class PostResponseDto {
  @Expose() id: number;
  @Expose() title: string;
  @Expose() content: string;

  @Expose()
  @Type(() => UserResponseDto)  // nested: author entity → UserResponseDto
  author: UserResponseDto;      // author's password also excluded recursively

  @Expose()
  @Transform(({ value }) => value?.length ?? 0)
  commentCount: number;         // transforms the array to just its length
}
```

### Comparison: Pipe vs ClassSerializerInterceptor

```
ClassSerializerInterceptor (recommended for most cases):
  ✓ Applies automatically to ALL responses from decorated controllers
  ✓ Works with arrays and nested objects transparently
  ✓ No boilerplate in service methods
  ✓ Works with @SerializeOptions() for per-handler overrides
  ✗ Runs after the handler (response transformation, not request transformation)
  ✗ Can't conditionally apply per-user-role easily
  ✗ Interceptor ordering may conflict with other interceptors

Custom Pipe approach:
  ✓ Explicit — easy to see which transformation applies where
  ✓ Can be applied selectively to specific parameters or handlers
  ✓ Runs in pipe phase — value available before handler runs
  ✓ Can combine transformation + validation in one step
  ✗ More boilerplate — must apply to every handler manually
  ✗ Less conventional — team may not expect transformation in pipes

Recommendation:
  Standard field exclusion → ClassSerializerInterceptor
  Complex transformation with business logic → service layer plainToInstance
  Request-time normalization (trim, lowercase, sanitize) → Pipe
  Entity-from-ID lookup → Pipe (as shown in Problem 3)
```

## Quick Reference — Pipes Cheat Sheet

```
PIPE PURPOSES:
  Transformation: convert input type/shape before handler runs
  Validation:     check input; throw BadRequestException if invalid
  Both:           validate then transform (most common — ValidationPipe does both)

BINDING SCOPES (narrowest wins):
  @Param('id', ParseIntPipe)      → parameter-level (one arg)
  @UsePipes(ValidationPipe)       → method-level (all args in handler)
  @Controller + @UsePipes(...)    → controller-level (all handlers)
  app.useGlobalPipes(...)         → global (entire app, no DI)
  APP_PIPE provider               → global (entire app, WITH DI)

BUILT-IN PIPES:
  ParseIntPipe       → '42' → 42
  ParseFloatPipe     → '3.14' → 3.14
  ParseBoolPipe      → 'true' → true
  ParseUUIDPipe      → validates UUID format
  ParseEnumPipe      → validates enum membership
  ParseArrayPipe     → '1,2,3' → [1, 2, 3]
  DefaultValuePipe   → undefined → provided default
  ParseFilePipe      → validates uploaded file (size, type)

VALIDATION PIPE OPTIONS:
  transform: true              → plainToInstance + coerce primitives
  whitelist: true              → strip undeclared properties silently
  forbidNonWhitelisted: true   → throw 400 if extra properties present
  skipMissingProperties: true  → skip validation for absent fields (prefer PartialType)
  transformOptions.enableImplicitConversion: true → coerce by TypeScript type hint
  exceptionFactory             → custom error response shape
  stopAtFirstError: true       → stop validating at first failure per property

CLASS-VALIDATOR KEY DECORATORS:
  @IsString / @IsNumber / @IsBoolean / @IsDate / @IsEnum
  @IsEmail / @IsUrl / @IsUUID / @Matches(regex)
  @IsNotEmpty → not '' | null | undefined
  @IsOptional → skip if absent
  @Min / @Max / @MinLength / @MaxLength
  @IsArray / @ArrayNotEmpty / @IsString({ each: true })
  @ValidateNested + @Type → nested DTO validation
  @ValidateIf(o => condition) → conditional per-field
  Custom: @ValidatorConstraint + registerDecorator

CLASS-TRANSFORMER KEY DECORATORS:
  @Expose()            → include in excludeExtraneousValues mode
  @Exclude()           → never include in output (passwords, tokens)
  @Transform(fn)       → custom transform: trim, lowercase, parse, format
  @Type(() => Class)   → convert nested plain obj → class instance
  plainToInstance(Cls, obj, opts)  → plain → class instance (incoming)
  instanceToPlain(instance, opts)  → class → plain object (outgoing)

CUSTOM PIPE ANATOMY:
  @Injectable()
  export class MyPipe implements PipeTransform<TInput, TOutput> {
    transform(value: TInput, metadata: ArgumentMetadata): TOutput {
      // metadata.type:     'body' | 'query' | 'param' | 'custom'
      // metadata.metatype: the TypeScript class (CreateUserDto)
      // metadata.data:     the key passed to the decorator ('id')
      // throw BadRequestException for validation failures
      // throw NotFoundException for not-found errors
      return transformedValue;
    }
  }

PARTIAL UPDATE PATTERN:
  export class UpdateDto extends PartialType(CreateDto) {}
  // Makes ALL fields optional, preserves all validators for present fields
  // Never use skipMissingProperties globally — use PartialType per DTO

ENTITY-FROM-ID PATTERN:
  transform(id: string): Promise<Entity> {
    const parsed = parseInt(id, 10);
    if (isNaN(parsed)) throw new BadRequestException('Invalid ID');
    const entity = await this.service.findOne(parsed);
    if (!entity) throw new NotFoundException(`Entity #${parsed} not found`);
    return entity;
  }
  // Handler receives Entity directly — no findOne() boilerplate

COMMON BUGS:
  @ValidateNested without @Type      → nested validation silently skipped
  transform: false with @Transform   → @Transform decorators don't execute
  Custom constraint without DI setup → async validators can't inject services
  ValidationPipe after routes        → middleware order — applies to nothing
  @Exclude on DTO input field        → @Exclude is serialization-only, not input stripping
  whitelist without forbidNonWhitelisted → extra fields stripped silently (no client feedback)
  forbidNonWhitelisted without whitelist → throws on non-whitelisted but whitelist: false = no effect
  Async pipe without async transform → Promise not awaited — returns Promise object, not value
```

**Final Tip:** At the 5 YOE level, pipe questions test whether you understand **the full data flow** — from incoming request through transformation to the handler — and can connect `class-validator`, `class-transformer`, and NestJS's pipe lifecycle into a coherent system. The highest-signal answer on `@ValidateNested`: "Without `@Type(() => NestedDto)` the nested property arrives as a plain object literal — it has no class, so class-validator finds no decorator metadata and skips validation entirely. The combination of `@ValidateNested` + `@Type` is inseparable: `@Type` converts the plain object to a class instance so that `@ValidateNested` can find and execute the decorators on that class." For `whitelist` vs `forbidNonWhitelisted`: "Whitelist alone silently strips extra fields — which protects against mass assignment but gives the client no feedback. Forbid-non-whitelisted throws a 400 if anything undeclared arrives — better DX because clients learn immediately that they're sending something wrong. I always enable both together in production." For `PartialType`: "For PATCH endpoints I always use `PartialType(CreateDto)` rather than duplicating the DTO or using `skipMissingProperties` globally. `PartialType` copies all the validator metadata and wraps each field in `@IsOptional()`, so absent fields are skipped but present fields still validate fully — you get exactly the semantics you want for partial updates without touching any global config."
