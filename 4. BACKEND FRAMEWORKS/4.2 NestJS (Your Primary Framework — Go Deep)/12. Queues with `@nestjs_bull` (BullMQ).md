# Queues with `@nestjs/bull` (BullMQ) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do queues solve, and why would you reach for Bull/BullMQ over solving it inline?**
A: Queues decouple work that is slow, unreliable, or resource-intensive from the HTTP request that triggered it. The core insight is that a user does not need to wait for a confirmation email to be sent, a PDF to be generated, or a third-party API to respond — they need confirmation that the work *will be done*, not that it *is done*.

```
Without a queue — synchronous processing:

  Client ──POST /checkout──► Handler
                              │
                              ├── charge card (300ms)
                              ├── send email via SendGrid (400ms)   ← network call
                              ├── generate PDF receipt (800ms)       ← CPU work
                              ├── update inventory (200ms)
                              └── respond 201 Created ◄── 1700ms total

  Problems:
  - Client waits 1.7s for work it doesn't need to block on
  - If SendGrid is down: request fails, card was already charged
  - If pod restarts mid-request: work is lost
  - Spike in orders: all 1.7s operations run concurrently — pool exhaustion
```

```
With a queue — asynchronous processing:

  Client ──POST /checkout──► Handler
                              │
                              ├── charge card (300ms)     ← must be synchronous
                              ├── enqueue { orderId }     ← 1ms Redis write
                              └── respond 201 Created ◄── 301ms total

  Queue worker (separate process / concurrency):
    Job: { orderId: 'ord-123' }
      ├── send email
      ├── generate PDF
      └── update inventory
    Automatic retry if any step fails
    Exponential backoff if SendGrid is rate-limiting
    Dead-letter queue for permanently failed jobs
```

```
Why Bull/BullMQ specifically over alternatives:

  Custom setTimeout/setInterval:
    - No persistence — restarts lose all pending work
    - No retry — failed jobs vanish
    - No visibility — you can't inspect what's queued

  Database polling (SELECT WHERE status='pending'):
    - Polling interval creates latency floor
    - Concurrent workers race — need SELECT FOR UPDATE SKIP LOCKED
    - Works but is operationally heavy

  AWS SQS / RabbitMQ:
    - Excellent for polyglot / multi-service setups
    - Operational overhead: another managed service, IAM, VPC config
    - Bull uses Redis which you likely already have for caching/sessions

  Bull/BullMQ + Redis:
    - Redis persistence (AOF/RDB) — jobs survive restarts
    - Atomic operations (LPUSH, BRPOP, Lua scripts) — no race conditions
    - Priority queues, delayed jobs, repeatable jobs, rate limiting
    - Bull Board / Arena UI — visual job inspection
    - BullMQ (the v2 rewrite) has TypeScript-first API, worker threads, flows
```

**Q2. What is the difference between Bull and BullMQ, and which does `@nestjs/bull` use?**
A: Bull and BullMQ are two separate npm packages from the same author (Taskforce.sh). BullMQ is a ground-up TypeScript rewrite with architectural improvements. `@nestjs/bull` wraps the older Bull package; `@nestjs/bullmq` wraps BullMQ:

```
Bull (original):
  Package: bull
  NestJS wrapper: @nestjs/bull
  Language: JavaScript with TS types bolted on
  Redis commands: custom protocol on top of raw Redis commands
  Architecture: single Queue class handles producers + consumers
  Worker threads: not supported
  Job flows: not supported
  Rate limiting: basic

BullMQ (v2 rewrite):
  Package: bullmq
  NestJS wrapper: @nestjs/bullmq
  Language: TypeScript-first
  Redis commands: uses Redis Streams internally (more reliable delivery)
  Architecture: separate Queue (producer), Worker (consumer), QueueEvents classes
  Worker threads: supported — CPU-heavy jobs don't block the event loop
  Job flows: supported — parent/child job dependency trees
  Rate limiting: per-queue rate limiting built in
  Minimum Redis: 5.0+ (for streams)
```

```typescript
// @nestjs/bull — older, widely deployed:
import { BullModule } from '@nestjs/bull';

@Module({
    imports: [
        BullModule.forRoot({
            redis: { host: 'localhost', port: 6379 },
        }),
        BullModule.registerQueue({ name: 'email' }),
    ],
})
export class AppModule {}

// @nestjs/bullmq — newer, preferred for greenfield:
import { BullMQModule } from '@nestjs/bullmq';

@Module({
    imports: [
        BullMQModule.forRoot({
            connection: { host: 'localhost', port: 6379 },
        }),
        BullMQModule.registerQueue({ name: 'email' }),
    ],
})
export class AppModule {}
```

```
This document covers both, using @nestjs/bull syntax for examples with
BullMQ-specific sections called out explicitly. The concepts (job lifecycle,
retries, processors, dead-letter) are identical between the two.
```

**Q3. How does Bull use Redis internally — what data structures back the queue?**
A: Bull implements its queue entirely in Redis using sorted sets, lists, and hashes. Understanding the data structures explains why Bull is reliable and what happens during each job lifecycle transition:

```
Redis keys for a queue named 'email':

  bull:email:id              ← Counter (INCR) — generates unique job IDs
  bull:email:wait            ← List (RPUSH/BLPOP) — jobs waiting to be picked up
  bull:email:active          ← List — jobs currently being processed
  bull:email:delayed         ← Sorted Set — score = timestamp to run, for delayed jobs
  bull:email:completed       ← Sorted Set — score = completedOn timestamp
  bull:email:failed          ← Sorted Set — score = failedOn timestamp
  bull:email:{id}            ← Hash — full job data: { data, opts, progress, ... }
  bull:email:stalled-check   ← Set — for stall detection heartbeat
```

```
Job lifecycle — atomic Redis operations:

  ENQUEUE (producer):
    1. INCR bull:email:id → jobId = 42
    2. HMSET bull:email:42 { data: {...}, attempts: 0, timestamp: now }
    3. RPUSH bull:email:wait 42   ← or ZADD bull:email:delayed for delayed jobs

  PICK UP (worker):
    4. BRPOPLPUSH bull:email:wait bull:email:active
       ↑ Atomic: removes from wait, adds to active in one operation
       ↑ BRPOP = blocking pop — worker sleeps until a job arrives
       ↑ Multiple workers: only one gets each job (atomic)

  PROCESSING:
    5. Worker processes job
    6. Heartbeat: EXPIRE bull:email:active:42 (stall detection)

  COMPLETE:
    7. LREM bull:email:active 1 42
    8. ZADD bull:email:completed timestamp 42
    9. HMSET bull:email:42 { returnValue: {...}, finishedOn: now }

  FAIL:
    7. LREM bull:email:active 1 42
    8a. attempts < maxAttempts → RPUSH bull:email:wait 42 (retry)
        or ZADD bull:email:delayed (backoff delay)
    8b. attempts >= maxAttempts → ZADD bull:email:failed timestamp 42

  STALL DETECTION (background process):
    Periodically: scan bull:email:active for jobs with expired heartbeats
    Move stalled jobs back to bull:email:wait for retry
    This handles worker process crashes mid-job
```

## Section 2: Setup and Configuration

**Q4. How do you configure `@nestjs/bull` in a production application?**
A: A production setup separates configuration from module registration, uses Redis connection pooling, and handles both producer and consumer module needs:

```typescript
// Installation:
// npm install @nestjs/bull bull
// npm install -D @types/bull

// config/queue.config.ts
import { registerAs } from '@nestjs/config';

export default registerAs('queue', () => ({
    redis: {
        host: process.env.REDIS_HOST ?? 'localhost',
        port: parseInt(process.env.REDIS_PORT ?? '6379', 10),
        password: process.env.REDIS_PASSWORD,
        tls: process.env.NODE_ENV === 'production'
            ? { rejectUnauthorized: true }
            : undefined,
        maxRetriesPerRequest: 3,
        enableReadyCheck: true,
        connectTimeout: 10_000,
    },
    defaultJobOptions: {
        attempts: 3,
        backoff: {
            type: 'exponential',
            delay: 1000,      // 1s, 2s, 4s
        },
        removeOnComplete: {
            age: 24 * 3600,   // Keep completed jobs for 24h
            count: 1000,      // Keep at most 1000 completed jobs
        },
        removeOnFail: {
            age: 7 * 24 * 3600,   // Keep failed jobs for 7 days
        },
    },
}));
```

```typescript
// queue/queue.module.ts — shared module imported everywhere that needs queues
import { BullModule } from '@nestjs/bull';
import { Module } from '@nestjs/common';
import { ConfigModule, ConfigService } from '@nestjs/config';
import queueConfig from '../config/queue.config';

export const QUEUE_NAMES = {
    EMAIL: 'email',
    PDF: 'pdf-generation',
    NOTIFICATIONS: 'notifications',
    WEBHOOKS: 'webhooks',
} as const;

@Module({
    imports: [
        // forRootAsync — connect once, shared across all queue modules
        BullModule.forRootAsync({
            imports: [ConfigModule],
            useFactory: (config: ConfigService) => ({
                redis: config.get('queue.redis'),
                defaultJobOptions: config.get('queue.defaultJobOptions'),
            }),
            inject: [ConfigService],
        }),

        // Register each queue — creates the Redis key namespace
        BullModule.registerQueue(
            { name: QUEUE_NAMES.EMAIL },
            { name: QUEUE_NAMES.PDF },
            { name: QUEUE_NAMES.NOTIFICATIONS },
            {
                name: QUEUE_NAMES.WEBHOOKS,
                // Queue-specific overrides:
                defaultJobOptions: {
                    attempts: 10,                   // Webhooks retry more aggressively
                    backoff: { type: 'exponential', delay: 5000 },
                    timeout: 30_000,                // 30s per attempt
                },
            },
        ),
    ],
    exports: [BullModule],   // Export so other modules can inject the queues
})
export class QueueModule {}
```

## Section 3: Producers — Adding Jobs

**Q5. How do you add jobs to a queue — what options matter for production use?**
A: Producers inject the queue by name using `@InjectQueue()` and call `queue.add()`. The job options control retry behaviour, priority, delay, and deduplication:

```typescript
// email/email-queue.producer.ts
import { Injectable, Logger } from '@nestjs/common';
import { InjectQueue } from '@nestjs/bull';
import { Queue, JobOptions } from 'bull';
import { QUEUE_NAMES } from '../queue/queue.module';

// Type the job payloads — this is the "contract" between producer and consumer:
export interface EmailJobData {
    type: 'order-confirmation' | 'password-reset' | 'welcome' | 'invoice';
    to: string;
    userId: string;
    orderId?: string;
    templateVars: Record<string, unknown>;
}

@Injectable()
export class EmailQueueProducer {
    private readonly logger = new Logger(EmailQueueProducer.name);

    constructor(
        @InjectQueue(QUEUE_NAMES.EMAIL)
        private readonly emailQueue: Queue<EmailJobData>
    ) {}

    // Basic job — inherits defaultJobOptions:
    async enqueueOrderConfirmation(orderId: string, userEmail: string): Promise<void> {
        await this.emailQueue.add('order-confirmation', {
            type: 'order-confirmation',
            to: userEmail,
            userId: 'user-1',
            orderId,
            templateVars: { orderId, supportEmail: 'help@acme.com' },
        });
        this.logger.log(`Enqueued order confirmation for ${orderId}`);
    }

    // Delayed job — runs after a delay:
    async enqueueAbandonedCartReminder(userId: string, cartId: string): Promise<void> {
        await this.emailQueue.add(
            'abandoned-cart',
            { type: 'order-confirmation', to: userId, userId, templateVars: { cartId } },
            {
                delay: 60 * 60 * 1000,   // Send reminder 1 hour later
                jobId: `cart-reminder-${cartId}`,   // Deduplication key
                // If a job with this ID already exists in the queue, this add() is a no-op
                // Prevents duplicate reminders if the endpoint is called twice
            }
        );
    }

    // Priority job — lower number = higher priority (processed first):
    async enqueuePasswordReset(email: string, resetToken: string): Promise<void> {
        await this.emailQueue.add(
            'password-reset',
            { type: 'password-reset', to: email, userId: '', templateVars: { resetToken } },
            {
                priority: 1,          // Highest priority — process before order emails
                attempts: 5,          // Override default attempts
                backoff: { type: 'fixed', delay: 2000 },   // Fixed 2s retry (not exponential)
                timeout: 10_000,      // Fail the job if processor takes >10s
            }
        );
    }

    // Bulk enqueue — efficient for batch operations:
    async enqueueBulkNotifications(jobs: Array<{ email: string; orderId: string }>): Promise<void> {
        await this.emailQueue.addBulk(
            jobs.map(({ email, orderId }) => ({
                name: 'order-confirmation',
                data: {
                    type: 'order-confirmation' as const,
                    to: email,
                    userId: '',
                    orderId,
                    templateVars: { orderId },
                },
                opts: { priority: 2 }
            }))
        );
        this.logger.log(`Bulk enqueued ${jobs.length} notification jobs`);
    }

    // Get queue state for monitoring:
    async getQueueStats() {
        const [waiting, active, completed, failed, delayed] = await Promise.all([
            this.emailQueue.getWaitingCount(),
            this.emailQueue.getActiveCount(),
            this.emailQueue.getCompletedCount(),
            this.emailQueue.getFailedCount(),
            this.emailQueue.getDelayedCount(),
        ]);
        return { waiting, active, completed, failed, delayed };
    }
}
```

```typescript
// Job options reference — the most important ones:
const criticalOptions: JobOptions = {
    // Retry configuration:
    attempts: 3,                   // Total attempts (including first try)
    backoff: {
        type: 'exponential',       // 'exponential' | 'fixed'
        delay: 1000,               // Base delay: 1s → 2s → 4s (exponential)
    },

    // Deduplication:
    jobId: 'unique-id',            // If set, duplicate jobId = no-op (idempotent adds)

    // Scheduling:
    delay: 5000,                   // Wait 5s before job becomes eligible for processing
    priority: 1,                   // 1 = highest, higher numbers = lower priority

    // Timeouts:
    timeout: 30_000,               // Fail job if processor runs longer than 30s
    // (important: without this, a hung processor holds the job in 'active' forever)

    // Retention:
    removeOnComplete: true,        // Remove from Redis immediately on success
    removeOnComplete: {
        age: 3600,                 // Keep for 1h
        count: 100,                // Keep last 100 completed
    },
    removeOnFail: false,           // Keep failed jobs (default) — for inspection

    // Stack trace:
    stackTraceLimit: 5,            // How many stack frames to store on failure
};
```

**Q6. How do you implement repeatable (cron) jobs with Bull?**
A: Bull supports repeatable jobs backed by Redis sorted sets — no external cron daemon needed. The job recurs automatically and survives process restarts:

```typescript
// Repeatable jobs are added once; Bull recreates them automatically:
@Injectable()
export class ScheduledJobsService implements OnApplicationBootstrap {
    constructor(
        @InjectQueue(QUEUE_NAMES.NOTIFICATIONS)
        private notificationsQueue: Queue
    ) {}

    // onApplicationBootstrap — runs after all modules initialized,
    // before the app starts accepting requests:
    async onApplicationBootstrap(): Promise<void> {
        await this.registerRepeatableJobs();
    }

    private async registerRepeatableJobs(): Promise<void> {
        // Remove stale repeatable jobs before re-registering
        // (prevents duplicates on redeploy with changed schedules):
        const existing = await this.notificationsQueue.getRepeatableJobs();
        await Promise.all(
            existing.map(job =>
                this.notificationsQueue.removeRepeatableByKey(job.key)
            )
        );

        // Cron syntax:
        await this.notificationsQueue.add(
            'daily-digest',
            { type: 'daily-digest' },
            {
                repeat: {
                    cron: '0 8 * * *',          // Every day at 8:00 AM UTC
                    tz: 'America/New_York',      // Timezone-aware
                },
                jobId: 'daily-digest',           // Stable ID across restarts
            }
        );

        // Every N milliseconds:
        await this.notificationsQueue.add(
            'sync-inventory',
            { source: 'warehouse-api' },
            {
                repeat: {
                    every: 5 * 60 * 1000,        // Every 5 minutes
                    limit: 100,                  // Optional: stop after 100 executions
                },
                jobId: 'inventory-sync',
            }
        );

        // With start/end time:
        await this.notificationsQueue.add(
            'flash-sale-reminder',
            { saleId: 'summer-2024' },
            {
                repeat: {
                    cron: '0 * * * *',           // Every hour
                    startDate: new Date('2024-07-01'),
                    endDate: new Date('2024-07-07'),
                },
            }
        );
    }
}
```

## Section 4: Consumers — Processing Jobs

**Q7. How do you implement a job processor with `@Processor` and `@Process`?**
A: A processor is a NestJS provider decorated with `@Processor(queueName)`. Individual job handlers are methods decorated with `@Process(jobName)`. The processor has full access to DI — any injectable service can be constructor-injected:

```typescript
// email/email.processor.ts
import {
    Processor, Process, OnQueueActive, OnQueueCompleted,
    OnQueueFailed, OnQueueStalled, InjectQueue
} from '@nestjs/bull';
import { Job, Queue } from 'bull';
import { Injectable, Logger } from '@nestjs/common';
import { EmailJobData } from './email-queue.producer';
import { EmailService } from './email.service';
import { UserService } from '../user/user.service';
import { MetricsService } from '../monitoring/metrics.service';
import { QUEUE_NAMES } from '../queue/queue.module';

@Processor(QUEUE_NAMES.EMAIL)   // Connects this class to the 'email' queue
export class EmailProcessor {
    private readonly logger = new Logger(EmailProcessor.name);

    constructor(
        private emailService: EmailService,
        private userService: UserService,
        private metrics: MetricsService,
        @InjectQueue(QUEUE_NAMES.EMAIL)
        private emailQueue: Queue,    // Can inject own queue for re-queuing / introspection
    ) {}

    // Named handler — processes jobs added as queue.add('order-confirmation', data):
    @Process('order-confirmation')
    async handleOrderConfirmation(job: Job<EmailJobData>): Promise<{ sent: boolean }> {
        this.logger.log(`Processing order confirmation job ${job.id}`);

        // job.data — the typed payload
        const { to, orderId, templateVars } = job.data;

        // Progress reporting — visible in Bull Board:
        await job.progress(10);

        // Fetch additional data needed for the email:
        const order = await this.fetchOrderDetails(orderId!);
        await job.progress(30);

        // Build and send:
        await this.emailService.send({
            to,
            subject: `Order ${orderId} confirmed`,
            template: 'order-confirmation',
            context: { ...templateVars, order },
        });
        await job.progress(100);

        // Return value is stored in job.returnvalue (visible in Bull Board):
        return { sent: true };
    }

    // Catch-all handler — processes any job name not matched by a specific @Process:
    @Process()
    async handleGeneric(job: Job<EmailJobData>): Promise<void> {
        this.logger.warn(`No specific handler for job type '${job.name}' — using generic`);
        await this.emailService.sendGeneric(job.data);
    }

    // Concurrency per-processor — processes up to 5 jobs simultaneously:
    @Process({ name: 'bulk-send', concurrency: 5 })
    async handleBulkSend(job: Job<EmailJobData>): Promise<void> {
        await this.emailService.send({ to: job.data.to, subject: 'Update', template: 'update', context: {} });
    }

    // ── Queue Event Hooks ──────────────────────────────────────────────────

    @OnQueueActive()
    onActive(job: Job): void {
        this.logger.debug(`Job ${job.id} (${job.name}) started, attempt ${job.attemptsMade + 1}`);
        this.metrics.increment('queue.email.active');
    }

    @OnQueueCompleted()
    onCompleted(job: Job, result: unknown): void {
        this.logger.log(`Job ${job.id} completed in ${Date.now() - job.timestamp}ms`);
        this.metrics.timing('queue.email.duration', Date.now() - job.timestamp);
        this.metrics.increment('queue.email.completed');
    }

    @OnQueueFailed()
    onFailed(job: Job, error: Error): void {
        this.logger.error(
            `Job ${job.id} (${job.name}) failed on attempt ${job.attemptsMade}/${job.opts.attempts}`,
            { error: error.message, stack: error.stack, jobData: job.data }
        );
        this.metrics.increment('queue.email.failed');

        // On final failure (all retries exhausted), alert:
        if (job.attemptsMade >= (job.opts.attempts ?? 1)) {
            this.alertFinalFailure(job, error);
        }
    }

    @OnQueueStalled()
    onStalled(job: Job): void {
        // Job was in 'active' state but worker stopped sending heartbeats
        // Bull will automatically retry it — this is informational
        this.logger.warn(`Job ${job.id} stalled (worker likely crashed), will be retried`);
        this.metrics.increment('queue.email.stalled');
    }

    private async fetchOrderDetails(orderId: string) {
        // ... fetch from DB
        return { id: orderId, total: 99.99 };
    }

    private alertFinalFailure(job: Job, error: Error): void {
        // Send to Slack / PagerDuty / Sentry
        this.logger.error(`FINAL FAILURE: job ${job.id} exhausted all retries`, {
            queue: QUEUE_NAMES.EMAIL,
            jobName: job.name,
            data: job.data,
            error: error.message,
        });
    }
}
```

**Q8. How does concurrency work in Bull — what is the difference between process-level and job-level concurrency?**
A: Bull has two distinct concurrency axes: how many workers (processes/instances) consume from the queue, and how many jobs each worker processes simultaneously:

```
Concurrency axis 1: Number of worker instances

  ┌───────────────┐     ┌───────────────┐     ┌───────────────┐
  │  Worker Pod 1  │     │  Worker Pod 2  │     │  Worker Pod 3  │
  │  EmailProcessor│     │  EmailProcessor│     │  EmailProcessor│
  └───────┬───────┘     └───────┬───────┘     └───────┬───────┘
          │                     │                     │
          └─────────────────────┼─────────────────────┘
                                │
                     ┌──────────▼──────────┐
                     │    Redis Queue       │
                     │  bull:email:wait     │
                     └──────────────────────┘

  Redis BRPOPLPUSH is atomic — each job goes to exactly one worker.
  Scaling = adding more worker pods. No coordination needed.
```

```
Concurrency axis 2: Concurrent jobs per worker (processor-level)

  @Processor(QUEUE_NAMES.EMAIL)                ← Default: concurrency = 1
  class EmailProcessor { }                     ← One job at a time per instance

  @Processor({ name: QUEUE_NAMES.EMAIL, concurrency: 10 })
  class EmailProcessor { }                     ← 10 jobs simultaneously per instance

  Or per-handler:
  @Process({ name: 'send-email', concurrency: 5 })
  async handleSend(job: Job) { ... }           ← This handler: 5 concurrent
```

```typescript
// Concurrency strategy by job type:

// I/O-bound jobs (email, HTTP calls, DB queries):
// High concurrency — most time is spent awaiting, event loop is free
@Processor({ name: QUEUE_NAMES.EMAIL, concurrency: 20 })
export class EmailProcessor {
    @Process('send')
    async handleSend(job: Job): Promise<void> {
        await this.emailService.send(job.data);  // Awaiting network — event loop free
    }
}

// CPU-bound jobs (PDF generation, image resizing, encryption):
// Low concurrency — or use worker threads to avoid blocking event loop
@Processor({ name: QUEUE_NAMES.PDF, concurrency: 2 })
export class PdfProcessor {
    @Process('generate')
    async handleGenerate(job: Job): Promise<void> {
        // Runs on main thread — blocks event loop while computing
        // With concurrency: 2, at most 2 PDFs generate at once per worker
        const pdf = await this.pdfService.generate(job.data);
        await this.storageService.upload(pdf);
    }
}

// BullMQ-specific: true worker thread isolation for CPU work:
// workers/pdf.worker.ts
import { Worker } from 'bullmq';

const worker = new Worker(
    'pdf-generation',
    async (job) => {
        // This runs in a WORKER THREAD — not the main Node.js thread
        // Heavy computation here doesn't affect HTTP request handling
        const pdf = await generatePdf(job.data);
        return pdf;
    },
    {
        connection: redisConnection,
        concurrency: 4,              // 4 parallel jobs in this worker thread
        useWorkerThreads: true,      // Each job gets its own worker thread
    }
);
```

## Section 5: Error Handling and Retries

**Q9. How does Bull's retry mechanism work, and how do you implement custom backoff and dead-letter behaviour?**
A: When a processor throws an error, Bull catches it, increments `attemptsMade`, and either reschedules the job (if attempts remain) or moves it to the failed set. The backoff strategy controls how long to wait before each retry:

```typescript
// Retry flow:
// Job fails → attemptsMade++ → attemptsMade < attempts → delay → re-queue
//                                                        → wait delay → pick up again
//           → attemptsMade >= attempts → move to bull:email:failed

// Retry strategies:
const jobOptions = {
    attempts: 5,
    backoff: {
        type: 'exponential',    // Delay doubles each attempt
        delay: 1000,            // 1s → 2s → 4s → 8s → 16s
    },
};

const jobOptions2 = {
    attempts: 3,
    backoff: {
        type: 'fixed',          // Same delay every retry
        delay: 5000,            // 5s → 5s → 5s
    },
};

// Custom backoff — implement via queue event:
// Bull doesn't expose custom backoff functions directly,
// but you can re-queue with a custom delay in the onFailed hook:
@OnQueueFailed()
async onFailed(job: Job, error: Error): Promise<void> {
    const isRateLimited = error.message.includes('429');

    if (isRateLimited && job.attemptsMade < 10) {
        // Re-queue with jittered delay to avoid thundering herd:
        const jitter = Math.random() * 1000;
        const delay = Math.min(30_000, 1000 * 2 ** job.attemptsMade) + jitter;

        await job.queue.add(job.name, job.data, {
            ...job.opts,
            delay,
            attempts: job.opts.attempts,
            jobId: undefined,   // New job ID — not a retry, a fresh enqueue
        });
    }
}
```

**Q10. What is job stalling and how does Bull handle it?**
A: A stalled job is one that was picked up by a worker (moved to `active`) but the worker stopped sending heartbeats — because the process crashed, ran out of memory, or became unresponsive:

```
Stall scenario:

  Worker picks up job → job in bull:email:active
  Worker sets a lock: bull:email:42:lock (TTL = lockDuration)

  Normal flow:
    Worker renews lock every lockRenewTime ms
    Job completes → lock released, job moved to completed

  Stall scenario:
    Worker process crashes / OOM killed
    Lock TTL expires (default: 30s)
    Bull's stall checker (runs on a separate timer) detects:
      "job 42 is in active but its lock has expired"
    → Moves job back to wait (or failed if maxStalledCount exceeded)
    → @OnQueueStalled() event fires on other workers
```

```typescript
// Configure stall detection:
BullModule.forRoot({
    redis: { host: 'localhost', port: 6379 },
    settings: {
        lockDuration: 30_000,      // Lock TTL — worker must renew within this time
        lockRenewTime: 15_000,     // Renew lock every 15s (half of lockDuration)
        stalledInterval: 30_000,   // Check for stalled jobs every 30s
        maxStalledCount: 2,        // Job fails permanently after stalling 2 times
    },
})

// For long-running jobs, manually renew progress to extend the lock:
@Process('generate-report')
async handleReport(job: Job): Promise<void> {
    const records = await this.db.fetchLargeDataset();

    for (let i = 0; i < records.length; i++) {
        await this.processRecord(records[i]);

        // Every 100 records: update progress to renew the lock
        if (i % 100 === 0) {
            await job.progress(Math.floor((i / records.length) * 100));
            // progress() internally calls job.extendLock() in Bull
        }
    }
}

// Or extend lock explicitly for jobs with no measurable progress:
@Process('long-running')
async handleLongRunning(job: Job): Promise<void> {
    const lockExtender = setInterval(async () => {
        await job.extendLock(30_000);   // Extend by 30s
    }, 15_000);

    try {
        await this.doLongWork();
    } finally {
        clearInterval(lockExtender);
    }
}
```

## Section 6: BullMQ-Specific Features

**Q11. How do job flows work in BullMQ — parent/child job dependencies?**
A: BullMQ Flows allow you to define dependency trees: a parent job only runs after all its child jobs complete. This replaces manual orchestration patterns (chaining jobs by hand):

```typescript
// BullMQ Flow example — order fulfilment:
// Parent: 'fulfill-order' runs only after all three children succeed

import { FlowProducer } from 'bullmq';

@Injectable()
export class OrderFulfillmentService {
    private flowProducer: FlowProducer;

    constructor(
        @Inject(REDIS_CLIENT) private redis: Redis,
    ) {
        this.flowProducer = new FlowProducer({ connection: redis });
    }

    async fulfillOrder(orderId: string): Promise<void> {
        await this.flowProducer.add({
            name: 'fulfill-order',
            queueName: 'fulfillment',
            data: { orderId },
            children: [
                {
                    name: 'charge-payment',
                    queueName: 'payments',
                    data: { orderId, amount: 99.99 },
                    // No children — leaf node, runs immediately
                },
                {
                    name: 'reserve-inventory',
                    queueName: 'inventory',
                    data: { orderId, items: ['sku-1', 'sku-2'] },
                },
                {
                    name: 'generate-invoice',
                    queueName: 'pdf-generation',
                    data: { orderId },
                    children: [
                        {
                            // Grandchild: fetch order data before generating PDF
                            name: 'fetch-order-data',
                            queueName: 'data-fetching',
                            data: { orderId },
                        }
                    ],
                },
            ],
        });

        // Execution order (resolved by BullMQ):
        // 1. charge-payment, reserve-inventory, fetch-order-data (all parallel)
        // 2. generate-invoice (after fetch-order-data completes)
        // 3. fulfill-order (after ALL children complete)
    }
}

// Parent job accesses children's return values:
@Processor('fulfillment')

    @Process('fulfill-order')

        // Children's return values available here:
        const childrenValues = await job.getChildrenValues();
        // {
        //   'payments:charge-payment': { transactionId: 'txn-123', charged: 99.99 },
        //   'inventory:reserve-inventory': { reservationId: 'res-456' },
        //   'pdf-generation:generate-invoice': { pdfUrl: 'https://...' },
```

**Q12. How do you implement rate limiting on a BullMQ queue?**
A: BullMQ has built-in rate limiting that throttles how many jobs are processed per time window — without any external coordination:

```typescript
// BullMQ rate limiting — built into the Worker:
import { Worker, Queue } from 'bullmq';

// Rate limit: process at most 100 jobs per minute:
const worker = new Worker(
    'webhooks',
    async (job) => {
        await this.sendWebhook(job.data);
    },
    {
        connection: redis,
        limiter: {
            max: 100,           // Max jobs per duration
            duration: 60_000,   // 60 second window
        },
    }

// When rate limit is hit:
// - Worker automatically pauses
// - Jobs stay in queue (not failed)
// - Worker resumes when window resets
// - Rate limit state stored in Redis — works across multiple workers

// NestJS integration:
@BullMQModule.registerQueue({
    name: QUEUE_NAMES.WEBHOOKS,
    defaultJobOptions: {
        attempts: 5,
        backoff: { type: 'exponential', delay: 2000 },
    },

@Processor({
    name: QUEUE_NAMES.WEBHOOKS,
    limiter: {
        max: 50,             // 50 webhook deliveries per second per worker
        duration: 1_000,
    },
})
export class WebhookProcessor {
    @Process('deliver')
    async deliver(job: Job): Promise<void> {
        const { endpoint, payload, secret } = job.data;
        const signature = this.signPayload(payload, secret);

        const response = await fetch(endpoint, {
            method: 'POST',
            headers: {
                'Content-Type': 'application/json',
                'X-Webhook-Signature': signature,
            },
            body: JSON.stringify(payload),
            signal: AbortSignal.timeout(10_000),
        });

        if (!response.ok) {
            throw new Error(`Webhook delivery failed: ${response.status}`);
        }
    }
}
```

## Section 9: Scenario-Based Questions

**Q15. "Jobs are piling up in the queue faster than they're being consumed. Walk through how you'd diagnose and resolve this."**
A: Queue backlog is a throughput problem — enqueue rate exceeds processing rate. The diagnosis isolates whether the bottleneck is in the worker, its dependencies, or the infrastructure:

```
Step 1: Measure current rates

  Enqueue rate: how many jobs/sec are being added?
  Process rate: how many jobs/sec are completing?
  If enqueue rate > process rate → backlog grows indefinitely

  Check via Bull Board or:
```

```typescript
// Add a metrics endpoint:
@Get('queue-health')
async queueHealth() {
    const [waiting, active, completed, failed] = await Promise.all([
        this.emailQueue.getWaitingCount(),
        this.emailQueue.getActiveCount(),
        this.emailQueue.getCompletedCount(),
        this.emailQueue.getFailedCount(),
    ]);
    // Track completed count over time → throughput = delta / interval
    return { waiting, active, completed, failed };
}
```

```
Step 2: Find the bottleneck in job processing

  If active === concurrency limit:
    Workers are busy — not enough concurrency or workers

  If active < concurrency limit but waiting is high:
    Workers are idle despite waiting jobs — stall detection issue?
    Worker crash loop? Check pod logs for OOM, crashes

  Measure time per job:
```

```typescript
@OnQueueCompleted()
onCompleted(job: Job): void {
    const durationMs = Date.now() - job.processedOn!;
    this.logger.log(`Job duration: ${durationMs}ms`, { jobName: job.name });
    // If durations are rising: dependency (DB / API) is getting slower
    // If durations are constant but throughput is low: need more workers
}
```

```
Step 3: Solutions based on diagnosis

  Bottleneck: processing too slow (DB queries, external API)
    → Add indexes, optimize queries
    → Cache frequently fetched data
    → Use connection pooling (don't open new DB conn per job)
    → Switch from synchronous external API to async / batched

  Bottleneck: not enough concurrency
    → Increase @Processor({ concurrency: N }) — more concurrent jobs per worker
    → Only works for I/O-bound jobs (network, DB) — NOT CPU-bound
    → For CPU-bound: add more worker instances (scale horizontally)

  Bottleneck: not enough worker instances
    → Add more pods/processes consuming from the queue
    → Redis BRPOPLPUSH is atomic — no coordination needed, just add workers
    → In Kubernetes: scale the worker deployment
      kubectl scale deployment email-worker --replicas=5

  Bottleneck: one slow job type blocking others
    → Split into separate queues by job type
    → Each queue has independent worker pool and concurrency
    → Priority jobs on dedicated queue with higher concurrency
```

**Q16. "You're seeing duplicate job processing — the same job runs twice. What causes this and how do you fix it?**
A: Duplicate processing has two root causes: at-least-once delivery semantics (stall → retry), and accidental double-enqueue. The fixes differ:

```
Cause 1: Stalled job recovery

  Timeline:
  Worker A picks up job 42 → starts processing
  Worker A process is killed (OOM, deploy) after 60% completion
  Job 42's lock expires → stall detection fires
  Worker B picks up job 42 → processes from start
  Duplicate side effect: email sent twice, payment charged twice

  This is expected Bull behaviour — at-least-once delivery.
  The fix is idempotent job handlers, not preventing the retry.
```

```typescript
// Idempotent processor — safe to run multiple times with the same result:
@Process('charge-payment')
async handleCharge(job: Job<{ orderId: string; amount: number }>): Promise<void> {
    const { orderId, amount } = job.data;

    // Idempotency key: only one charge per orderId ever succeeds
    const existingCharge = await this.db.query(
        'SELECT id FROM payment_charges WHERE order_id = $1 AND status = $2',
        [orderId, 'completed']
    );

    if (existingCharge.length > 0) {
        // Already charged — job was retried after stall
        // Return successfully without charging again:
        this.logger.warn(`Order ${orderId} already charged — skipping duplicate`);
        return;
    }

    // Safe to proceed — first time processing this orderId:
    await this.paymentService.charge({ orderId, amount });
}

// For email: track sent status in DB with unique constraint:
@Process('order-confirmation')
async handleEmail(job: Job<EmailJobData>): Promise<void> {
    const { orderId, to } = job.data;

    // Upsert with idempotency — if already sent, do nothing:
    const [, wasInserted] = await this.db.query(`
        INSERT INTO sent_emails (order_id, type, sent_at)
        VALUES ($1, 'order-confirmation', NOW())
        ON CONFLICT (order_id, type) DO NOTHING
        RETURNING id
    `, [orderId]);

    if (!wasInserted) {
        this.logger.log(`Confirmation email for order ${orderId} already sent`);
        return;
    }

    await this.emailService.send({ to, template: 'order-confirmation', context: { orderId } });
}
```

## Quick Reference Table

| Concept | Key Idea | Common Mistake |
|---|---|---|
| `@Processor(queueName)` | Marks a class as the consumer for a named queue; the queue must also be registered with `BullModule.registerQueue` | Registering the processor in a module that doesn't import `BullModule.registerQueue` — processor silently never fires |
| `@Process(jobName)` | Handles a specific named job type; `@Process()` with no name is a catch-all | Multiple `@Process('same-name')` methods in the same processor — only the last one registered wins |
| `@InjectQueue(name)` | Injects the `Queue` instance by name for producing jobs; uses the same token as `BullModule.registerQueue` | Injecting the queue with just `@Inject('email')` — use `@InjectQueue` or `getQueueToken('email')` for the correct token |
| `attempts` + `backoff` | Set in job options at enqueue time or in `defaultJobOptions`; `attempts` is total tries including first | Setting `attempts: 3` expecting 3 retries — it means 3 total attempts (first try + 2 retries) |
| Stall detection | Jobs in `active` with an expired lock are moved back to `wait` — at-least-once delivery guarantee | Writing non-idempotent processors — a stalled job will run again, causing double side effects |
| Job deduplication via `jobId` | Pass `jobId` in options — if a job with that ID already exists in any non-completed state, the `add()` is silently ignored | Using `jobId` and expecting it to also deduplicate across completed jobs — it doesn't; completed jobs with the same ID are ignored too |
| `removeOnComplete` / `removeOnFail` | Control Redis retention; without `removeOnComplete`, Redis fills with completed job hashes | Setting `removeOnComplete: true` in production without any log of completions — you lose all job history for debugging |
| Concurrency per processor | `@Processor({ name, concurrency: N })` — N simultaneous jobs per worker instance | Setting high concurrency for CPU-bound jobs — blocks the event loop; use worker threads or horizontal scaling instead |
| Repeatable jobs | Added once with `repeat: { cron }` or `repeat: { every }`; persisted in Redis and recreated automatically | Re-registering repeatable jobs on every deploy without removing old ones first — creates duplicate schedules |
| Dead-letter queue | Bull has no built-in DLQ; implement via `@OnQueueFailed()` + `queue.add()` on a separate `*-dlq` queue | Relying solely on `removeOnFail: false` — failed jobs stay in Redis but no alerting or reprocessing pipeline |
| `APP_GUARD` vs queue auth | Queued jobs bypass HTTP guards entirely — they're not HTTP requests | Assuming `JwtAuthGuard` protects job processors — it doesn't; processors run outside the HTTP context |
| BullMQ Flows | Parent job runs only after all children complete; children's return values available in parent via `getChildrenValues()` | Using BullMQ Flows with the `@nestjs/bull` wrapper — Flows are BullMQ-only; switch to `@nestjs/bullmq` |

---

**Tip for interviews:** Five things separate strong candidates on Bull/BullMQ: (1) explaining **at-least-once delivery semantics and stall recovery** — that Bull guarantees a job will run *at least* once but not *exactly* once, and that the correct response is idempotent job handlers (checking for prior completion before acting), not trying to prevent stalls from happening; (2) understanding **the Redis data structure backing the queue** — knowing that `BRPOPLPUSH` from `wait` to `active` is the atomic operation that prevents two workers from getting the same job, and that lock TTL expiry is what triggers stall detection, shows genuine understanding rather than just API usage; (3) knowing the **difference between process-level and job-level concurrency** — that horizontal scaling (more pods) and per-worker concurrency (`concurrency: N`) are additive, and that high concurrency is only safe for I/O-bound work because CPU-bound work blocks the event loop for all concurrent jobs; (4) being able to design a **dead-letter queue pipeline** — recognising that Bull has no built-in DLQ, implementing it via `@OnQueueFailed()` after `attemptsMade >= attempts`, and describing what a DLQ processor does (alert, inspect, optional requeue); and (5) articulating the **duplicate job problem and its two distinct causes** — stall-induced retries (fix: idempotent handlers with DB unique constraint) vs double-enqueue at the producer (fix: `jobId` deduplication or HTTP idempotency keys), since conflating the two causes leads to incomplete solutions.
