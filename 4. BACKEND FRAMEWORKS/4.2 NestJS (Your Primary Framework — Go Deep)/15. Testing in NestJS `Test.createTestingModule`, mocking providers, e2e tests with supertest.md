# Testing in NestJS: `Test.createTestingModule`, Mocking Providers, E2E with Supertest — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is `Test.createTestingModule()` and how does it differ from a real NestJS module?**

A: `Test.createTestingModule()` builds a fully functional NestJS IoC container from a module metadata object — the same DI resolution, the same lifecycle hooks, the same injection tokens — but without starting an HTTP server or binding to a port. It is the foundation of every NestJS test: unit tests use it to instantiate isolated providers; e2e tests use it to create the entire application.

```typescript
import { Test, TestingModule } from '@nestjs/testing';
import { UsersService } from './users.service';
import { UsersRepository } from './users.repository';

describe('UsersService', () => {
  let module: TestingModule;
  let service: UsersService;

  beforeEach(async () => {
    module = await Test.createTestingModule({
      // Same metadata shape as @Module():
      providers: [
        UsersService,
        {
          provide:   UsersRepository,
          useValue:  { findAll: jest.fn(), findOne: jest.fn(), save: jest.fn() },
        },
      ],
    }).compile();   // ← compile() resolves all dependencies and runs onModuleInit

    service = module.get<UsersService>(UsersService);
  });

  afterEach(async () => {
    await module.close();   // Triggers onModuleDestroy lifecycle hooks — important for cleanup
  });
});
```

**Key differences from a real module:**

| Property | Real `AppModule` | `TestingModule` |
|---|---|---|
| HTTP server | Bound to a port | None — unless you call `createNestApplication()` |
| Middleware | Applied via `app.use()` | Not applied unless you call `app.init()` |
| Global providers | Inherited from `AppModule` | Only what you declare |
| Module scope | Full dependency graph | Exactly what you declare |
| Lifecycle | `onModuleInit`, `onApplicationBootstrap`, shutdown hooks | `onModuleInit` runs on `.compile()`; shutdown on `.close()` |

The deliberate isolation is the feature: you declare only the providers relevant to the system under test and provide fakes for everything else.

**Q2. What is the difference between `module.get()`, `module.resolve()`, and `module.select()`?**

A:

```typescript
// module.get<T>(token): T
// ─────────────────────────────────────────────────────────────────────────────
// Synchronous. Retrieves a SINGLETON-scoped provider from the DI container.
// Returns the exact same instance that would be injected anywhere in the app.
// Works for most services, repositories, and config providers.

const service = module.get<UsersService>(UsersService);
const config  = module.get<ConfigService>(ConfigService);
const repo    = module.get<UsersRepository>(getRepositoryToken(User));

// module.resolve<T>(token, contextId?): Promise<T>
// ─────────────────────────────────────────────────────────────────────────────
// Asynchronous. Creates a new instance for REQUEST or TRANSIENT scoped providers.
// Each call to resolve() creates a fresh instance (like a new request would).
// Pass a contextId to share the same instance across multiple resolve() calls
// within the same simulated "request".

import { STATIC_CONTEXT } from '@nestjs/core';

const requestScopedService = await module.resolve<RequestScopedService>(
  RequestScopedService,
  STATIC_CONTEXT  // Without contextId, each resolve() call gets a different instance
);

// Sharing instances across resolves in the same "request":
import { ContextIdFactory } from '@nestjs/core';
const contextId = ContextIdFactory.create();
const svcA = await module.resolve<ServiceA>(ServiceA, contextId);
const svcB = await module.resolve<ServiceB>(ServiceB, contextId);
// svcA and svcB share the same REQUEST-scoped instances as if from one request

// module.select<T>(moduleClass): TestingModule
// ─────────────────────────────────────────────────────────────────────────────
// Navigates to a specific submodule within a larger testing module graph.
// Used when you've imported a full feature module and need to get a provider
// that's internal to it (not exported).

const catsModule  = module.select(CatsModule);
const catsService = catsModule.get<CatsService>(CatsService);
// Without select(), module.get(CatsService) would throw if CatsService is not exported
```

## Section 2: Unit Testing Services

**Q3. How do you write a unit test for a service that has multiple dependencies?**

A: The pattern is: declare the service under test as a real provider, replace every dependency with a mock, retrieve them from the module, and assert on the mock interactions:

```typescript
// users.service.ts (the system under test):
@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(User)
    private readonly repo: Repository<User>,
    private readonly mailer: MailerService,
    private readonly config: ConfigService,
  ) {}

  async createUser(dto: CreateUserDto): Promise<User> {
    const existing = await this.repo.findOne({ where: { email: dto.email } });
    if (existing) throw new ConflictException('Email already registered');

    const user = this.repo.create(dto);
    const saved = await this.repo.save(user);

    const appUrl = this.config.getOrThrow<string>('APP_URL');
    await this.mailer.sendWelcome(saved.email, appUrl);

    return saved;
  }
}
```

```typescript
// users.service.spec.ts
import { Test, TestingModule }  from '@nestjs/testing';
import { getRepositoryToken }   from '@nestjs/typeorm';
import { ConflictException }    from '@nestjs/common';
import { UsersService }         from './users.service';
import { User }                 from './user.entity';
import { MailerService }        from '../mailer/mailer.service';
import { ConfigService }        from '@nestjs/config';

describe('UsersService', () => {
  let service:       UsersService;
  let repo:          jest.Mocked<Repository<User>>;
  let mailer:        jest.Mocked<MailerService>;
  let configService: jest.Mocked<ConfigService>;

  // ── Mock factory functions ───────────────────────────────────────────────
  // Defined outside beforeEach so they can be referenced in expectations:
  const mockRepo = {
    findOne: jest.fn(),
    create:  jest.fn(),
    save:    jest.fn(),
  };

  const mockMailer = {
    sendWelcome: jest.fn(),
  };

  const mockConfig = {
    getOrThrow: jest.fn(),
    get:        jest.fn(),
  };

  beforeEach(async () => {
    const module: TestingModule = await Test.createTestingModule({
      providers: [
        UsersService,                              // Real implementation
        {
          provide:  getRepositoryToken(User),      // TypeORM repository token
          useValue: mockRepo,
        },
        {
          provide:  MailerService,
          useValue: mockMailer,
        },
        {
          provide:  ConfigService,
          useValue: mockConfig,
        },
      ],
    }).compile();

    service       = module.get<UsersService>(UsersService);
    repo          = module.get(getRepositoryToken(User));
    mailer        = module.get(MailerService);
    configService = module.get(ConfigService);
  });

  afterEach(() => jest.clearAllMocks());  // Reset call counts between tests

  describe('createUser', () => {
    const dto: CreateUserDto = { email: 'alice@example.com', name: 'Alice', password: 'pass123' };
    const savedUser: User    = { id: '1', ...dto, createdAt: new Date() } as User;

    it('creates and returns a new user', async () => {
      mockRepo.findOne.mockResolvedValue(null);       // No existing user
      mockRepo.create.mockReturnValue(dto as User);   // create() is synchronous
      mockRepo.save.mockResolvedValue(savedUser);
      mockConfig.getOrThrow.mockReturnValue('https://app.example.com');
      mockMailer.sendWelcome.mockResolvedValue(undefined);

      const result = await service.createUser(dto);

      expect(result).toEqual(savedUser);
      expect(repo.findOne).toHaveBeenCalledWith({ where: { email: dto.email } });
      expect(repo.create).toHaveBeenCalledWith(dto);
      expect(repo.save).toHaveBeenCalledWith(dto);
      expect(mailer.sendWelcome).toHaveBeenCalledWith(
        savedUser.email,
        'https://app.example.com'
      );
    });

    it('throws ConflictException if email already exists', async () => {
      mockRepo.findOne.mockResolvedValue({ id: '2', email: dto.email } as User);

      await expect(service.createUser(dto)).rejects.toThrow(ConflictException);
      expect(repo.save).not.toHaveBeenCalled();
      expect(mailer.sendWelcome).not.toHaveBeenCalled();
    });

    it('propagates mailer errors without saving twice', async () => {
      mockRepo.findOne.mockResolvedValue(null);
      mockRepo.create.mockReturnValue(dto as User);
      mockRepo.save.mockResolvedValue(savedUser);
      mockConfig.getOrThrow.mockReturnValue('https://app.example.com');
      mockMailer.sendWelcome.mockRejectedValue(new Error('SMTP connection refused'));

      await expect(service.createUser(dto)).rejects.toThrow('SMTP connection refused');
      expect(repo.save).toHaveBeenCalledTimes(1);  // Saved once, not retried
    });
  });
});
```

**Q4. What are the different ways to provide mocks in `createTestingModule()`?**

A:

```typescript
// ── useValue: a plain object or primitive ────────────────────────────────────
{
  provide:  UserService,
  useValue: {
    findAll: jest.fn().mockResolvedValue([]),
    findOne: jest.fn().mockResolvedValue(null),
    create:  jest.fn(),
  },
}
// Use when: you need a simple stub with controlled return values
// Downside: not type-checked against the real class shape

// ── useClass: an injectable class ────────────────────────────────────────────
@Injectable()
class MockUserService implements Partial<UserService> {
  async findAll() { return []; }
  async findOne(_id: string) { return null; }
}
{
  provide:  UserService,
  useClass: MockUserService,
}
// Use when: mock needs its own injected dependencies or complex logic
// NestJS instantiates the class through the DI container

// ── useFactory: a factory function with optional DI ───────────────────────────
{
  provide:  UserService,
  inject:   [ConfigService],              // DI into the factory
  useFactory: (config: ConfigService) => ({
    findAll: jest.fn().mockResolvedValue([]),
    getBaseUrl: () => config.get('APP_URL'),
  }),
}
// Use when: mock value depends on other providers in the module

// ── useExisting: alias to another token ──────────────────────────────────────
{
  provide:  'LEGACY_USER_SERVICE',
  useExisting: UserService,   // Both tokens resolve to the same instance
}
// Use when: testing code that injects by string/symbol token
// and you want to alias it to the class-token mock

// ── Direct class reference (shorthand) — no mock ─────────────────────────────
providers: [UserService]
// Provides the real implementation — NestJS resolves its own dependencies
// Use when: you want to test a real service but mock only its dependencies
```

## Section 3: Mocking Strategies

**Q5. What is the difference between `jest.fn()`, `jest.spyOn()`, and overriding a provider outright?**

A:

```typescript
// ── jest.fn() — standalone mock function ─────────────────────────────────────
const findOne = jest.fn();
findOne.mockResolvedValue({ id: '1', name: 'Alice' });
// Used in useValue objects — no connection to a real implementation
// Call tracking, return value control, implementation replacement all built in

// ── jest.spyOn() — wraps an existing method ──────────────────────────────────
// Retrieves the REAL service from the module, then wraps one method:
const service = module.get<UsersService>(UsersService);
const findOneSpy = jest.spyOn(service, 'findOne').mockResolvedValue(null);

// Advantages over useValue mock:
// - TypeScript catches method name typos (spy target must exist on the real class)
// - Can call through to the real implementation: .mockImplementation is opt-in
// - afterEach: jest.restoreAllMocks() restores the original implementation

// ── Spy on a dependency instead of the service under test ────────────────────
const repo = module.get<Repository<User>>(getRepositoryToken(User));
jest.spyOn(repo, 'findOne').mockResolvedValue(null);
// More granular than useValue — the repository still has its other methods

// ── overrideProvider() — replacing a provider in an already-built test module ─
// Useful when you've imported a full feature module and want to override one provider:
const module = await Test.createTestingModule({
  imports: [UsersModule],   // Imports the whole module, including all its providers
})
  .overrideProvider(UsersRepository)
  .useValue(mockRepository)
  .compile();
// Unlike useValue in providers[], this can override providers INSIDE imported modules

// ── When to use each ──────────────────────────────────────────────────────────
// jest.fn() in useValue:   Pure unit tests — full control, no real code
// jest.spyOn():            Integration-leaning tests where most real code should run
// overrideProvider():      E2E or module-level tests where you import real modules
//                          but need to mock one deep dependency (e.g., the DB)
```

**Q6. What are the differences between `mockReturnValue`, `mockResolvedValue`, `mockRejectedValue`, and `mockImplementation`?**

A:

```typescript
const fn = jest.fn();

// ── mockReturnValue — synchronous return ─────────────────────────────────────
fn.mockReturnValue(42);
fn();           // → 42  (synchronous)
fn();           // → 42  (same value every call)

// Use for: synchronous methods (repo.create(), entity getters, config.get())

// ── mockResolvedValue — Promise.resolve wrapper ────────────────────────────────
fn.mockResolvedValue({ id: '1', name: 'Alice' });
await fn();     // → { id: '1', name: 'Alice' }  (resolves)

// Equivalent to: fn.mockReturnValue(Promise.resolve({ id: '1', name: 'Alice' }))
// Use for: async service methods, repository async queries (findOne, save)

// ── mockRejectedValue — Promise.reject wrapper ────────────────────────────────
fn.mockRejectedValue(new Error('Connection refused'));
await fn();     // throws Error: Connection refused

// Use for: testing error paths — DB timeouts, service failures, auth errors

// ── mockImplementation — full control per-call logic ─────────────────────────
fn.mockImplementation((id: string) => {
  if (id === 'not-found') return Promise.resolve(null);
  return Promise.resolve({ id, name: 'Alice' });
});
await fn('123');         // → { id: '123', name: 'Alice' }
await fn('not-found');   // → null

// Use for: conditional behavior based on arguments

// ── mockImplementationOnce — single-call override ─────────────────────────────
// Sequences: first call returns X, second returns Y:
fn
  .mockResolvedValueOnce({ id: '1' })   // First call
  .mockResolvedValueOnce({ id: '2' })   // Second call
  .mockResolvedValue(null);              // All subsequent calls

// Use for: testing retry logic, paginated responses, or call ordering

// ── Common pitfall — forgetting to await ─────────────────────────────────────
// WRONG — test passes but doesn't actually test async behavior:
it('finds user', () => {
  fn.mockResolvedValue({ id: '1' });
  const result = service.findOne('1');    // ← missing await
  expect(result).toEqual({ id: '1' });   // result is a Promise, not the value
});

// CORRECT:
it('finds user', async () => {
  fn.mockResolvedValue({ id: '1' });
  const result = await service.findOne('1');
  expect(result).toEqual({ id: '1' });
});
```

## Section 4: Testing Controllers

**Q7. How do you unit test a NestJS controller and when is it worth doing?**

A: Controllers in NestJS are thin — they parse request parameters, call a service, and return the result. A controller unit test verifies this delegation, not the business logic:

```typescript
// users.controller.ts
@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get()
  findAll(): Promise<User[]> {
    return this.usersService.findAll();
  }

  @Get(':id')
  async findOne(@Param('id') id: string): Promise<User> {
    const user = await this.usersService.findOne(id);
    if (!user) throw new NotFoundException(`User ${id} not found`);
    return user;
  }

  @Post()
  @HttpCode(201)
  create(@Body() dto: CreateUserDto): Promise<User> {
    return this.usersService.create(dto);
  }
}
```

```typescript
// users.controller.spec.ts
describe('UsersController', () => {
  let controller: UsersController;
  let service:    jest.Mocked<UsersService>;

  const mockService = {
    findAll: jest.fn(),
    findOne: jest.fn(),
    create:  jest.fn(),
  };

  beforeEach(async () => {
    const module = await Test.createTestingModule({
      controllers: [UsersController],
      providers:   [{ provide: UsersService, useValue: mockService }],
    }).compile();

    controller = module.get<UsersController>(UsersController);
    service    = module.get(UsersService);
  });

  afterEach(() => jest.clearAllMocks());

  describe('findOne', () => {
    it('returns a user when found', async () => {
      const user = { id: '1', name: 'Alice' } as User;
      mockService.findOne.mockResolvedValue(user);

      const result = await controller.findOne('1');

      expect(result).toEqual(user);
      expect(service.findOne).toHaveBeenCalledWith('1');
    });

    it('throws NotFoundException when user is not found', async () => {
      mockService.findOne.mockResolvedValue(null);

      await expect(controller.findOne('999')).rejects.toThrow(NotFoundException);
      await expect(controller.findOne('999')).rejects.toThrow('User 999 not found');
    });
  });
});
```

**When controller unit tests are worth writing vs skipping:**

```
Worth writing:
✓ Controller has conditional logic (the NotFoundException throw above)
✓ Controller maps or transforms the service result before returning
✓ Controller has complex parameter extraction logic (@Query, @Headers, @Body validation)
✓ Testing HTTP code decorators (@HttpCode, @Header) are applied

Skip (test the service instead, or write e2e test):
✗ Controller is a pure delegate: return this.service.method(params)
  — the test would just verify that one line of delegation
✗ You have an e2e test covering the same endpoint
  — controller unit + e2e is redundant for pure delegates
```

## Section 5: Guards, Interceptors, Filters

**Q8. How do you unit test a guard's `canActivate()` method and mock `ExecutionContext`?**

A: Guards receive `ExecutionContext` — a NestJS abstraction over the raw request. In tests, you build a mock that returns whatever the guard needs to inspect:

```typescript
// jwt-auth.guard.ts
@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly jwtService: JwtService) {}

  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest<Request>();
    const token   = request.headers['authorization']?.replace('Bearer ', '');

    if (!token) return false;

    try {
      const payload  = this.jwtService.verify(token);
      request['user'] = payload;
      return true;
    } catch {
      return false;
    }
  }
}
```

```typescript
// jwt-auth.guard.spec.ts
import { ExecutionContext } from '@nestjs/common';
import { JwtService }       from '@nestjs/jwt';

describe('JwtAuthGuard', () => {
  let guard:      JwtAuthGuard;
  let jwtService: jest.Mocked<JwtService>;

  const mockJwtService = { verify: jest.fn() };

  beforeEach(async () => {
    const module = await Test.createTestingModule({
      providers: [
        JwtAuthGuard,
        { provide: JwtService, useValue: mockJwtService },
      ],
    }).compile();

    guard      = module.get<JwtAuthGuard>(JwtAuthGuard);
    jwtService = module.get(JwtService);
  });

  afterEach(() => jest.clearAllMocks());

  // ── ExecutionContext mock factory ─────────────────────────────────────────
  function buildContext(authHeader?: string): ExecutionContext {
    const request: Partial<Request> = {
      headers: authHeader ? { authorization: authHeader } : {},
    };

    return {
      switchToHttp: () => ({
        getRequest:  () => request,
        getResponse: () => ({}),
        getNext:     () => jest.fn(),
      }),
      getClass:    jest.fn().mockReturnValue(UsersController),
      getHandler:  jest.fn().mockReturnValue(() => {}),
      getType:     jest.fn().mockReturnValue('http'),
      getArgs:     jest.fn().mockReturnValue([]),
    } as unknown as ExecutionContext;
  }

  it('returns true for a valid token', () => {
    const payload = { sub: 'user-1', email: 'alice@example.com' };
    mockJwtService.verify.mockReturnValue(payload);

    const context = buildContext('Bearer valid.jwt.token');
    const result  = guard.canActivate(context);

    expect(result).toBe(true);
    expect(jwtService.verify).toHaveBeenCalledWith('valid.jwt.token');
    // Verify the user was attached to the request:
    expect(context.switchToHttp().getRequest()['user']).toEqual(payload);
  });

  it('returns false when no Authorization header', () => {
    const result = guard.canActivate(buildContext());
    expect(result).toBe(false);
    expect(jwtService.verify).not.toHaveBeenCalled();
  });

  it('returns false when token is invalid', () => {
    mockJwtService.verify.mockImplementation(() => { throw new Error('Invalid token'); });

    const result = guard.canActivate(buildContext('Bearer bad.token'));
    expect(result).toBe(false);
  });
});
```

**Q9. How do you override guards, interceptors, pipes, and filters in a TestingModule?**

A: The `TestingModuleBuilder` exposes four override methods that are used when you've imported a real module and need to replace a cross-cutting concern without rebuilding the entire module:

```typescript
import { Test }           from '@nestjs/testing';
import { APP_GUARD }      from '@nestjs/core';
import { JwtAuthGuard }   from '../auth/jwt-auth.guard';
import { LoggingInterceptor } from '../common/logging.interceptor';
import { ParseIntPipe }   from '@nestjs/common';
import { AllExceptionsFilter } from '../common/all-exceptions.filter';

const module = await Test.createTestingModule({
  imports: [UsersModule],
})
  // ── Override a guard ───────────────────────────────────────────────────────
  .overrideGuard(JwtAuthGuard)
  .useValue({
    canActivate: (ctx: ExecutionContext) => {
      // Attach a fake user so routes that read req.user work:
      const req = ctx.switchToHttp().getRequest();
      req.user  = { id: 'test-user-id', email: 'test@example.com', roles: ['user'] };
      return true;
    },
  })

  // ── Override an interceptor ────────────────────────────────────────────────
  .overrideInterceptor(LoggingInterceptor)
  .useValue({ intercept: (_ctx: any, next: CallHandler) => next.handle() })
  // Pass-through mock: doesn't log but doesn't break the request flow

  // ── Override a pipe ────────────────────────────────────────────────────────
  .overridePipe(ParseIntPipe)
  .useValue({ transform: (value: string) => parseInt(value, 10) })
  // Use when the pipe has external dependencies (config, db) you don't want to spin up

  // ── Override an exception filter ───────────────────────────────────────────
  .overrideFilter(AllExceptionsFilter)
  .useClass(TestExceptionFilter)
  // Use a simpler test filter that doesn't need Sentry, logger, etc.

  .compile();

// ── Overriding APP_GUARD (globally registered guard) ─────────────────────────
// APP_GUARD is a multi-provider token — overrideGuard() handles it:
.overrideGuard(JwtAuthGuard)   // This overrides the guard whether it's route-level or APP_GUARD

// ── Alternative: skip the guard in tests by providing a permissive version ────
providers: [
  {
    provide:  APP_GUARD,
    useValue: { canActivate: () => true },  // Allow all requests in tests
  },
]
```

## Section 6: E2E Tests with Supertest

**Q10. How do you set up an e2e test with `createNestApplication()` and supertest?**

A:

```typescript
// test/users.e2e-spec.ts
import { Test, TestingModule }   from '@nestjs/testing';
import { INestApplication }      from '@nestjs/common';
import { ValidationPipe }        from '@nestjs/common';
import * as request              from 'supertest';
import { AppModule }             from '../src/app.module';

describe('UsersController (e2e)', () => {
  let app:    INestApplication;
  let module: TestingModule;

  beforeAll(async () => {
    module = await Test.createTestingModule({
      imports: [AppModule],
    })
      // Override anything that hits external systems:
      .overrideProvider(DatabaseService)
      .useValue(mockDatabaseService)
      .overrideGuard(JwtAuthGuard)
      .useValue({ canActivate: (ctx: ExecutionContext) => {
        ctx.switchToHttp().getRequest().user = { id: 'e2e-user', roles: ['user'] };
        return true;
      }})
      .compile();

    app = module.createNestApplication();

    // Apply the same global configuration as main.ts:
    // If your main.ts has global middleware/pipes/guards, replicate them here.
    // Any global setup NOT applied here will be missing — a common source of
    // "passes in e2e but not in production" bugs.
    app.useGlobalPipes(new ValidationPipe({
      transform:            true,
      whitelist:            true,
      forbidNonWhitelisted: true,
    }));
    app.setGlobalPrefix('api');   // If your app uses a global prefix

    await app.init();
  });

  afterAll(async () => {
    // CRITICAL: app.close() triggers onModuleDestroy, closes DB connections,
    // stops timers. Without it, Jest hangs after tests complete.
    await app.close();
  });

  // ── GET /api/users ─────────────────────────────────────────────────────────
  it('GET /api/users → 200 with array', async () => {
    const response = await request(app.getHttpServer())
      .get('/api/users')
      .expect(200);

    expect(response.body).toBeInstanceOf(Array);
  });

  // ── POST /api/users — valid body ─────────────────────────────────────────
  it('POST /api/users → 201 with created user', async () => {
    const dto = { name: 'Alice', email: 'alice@example.com', password: 'securePass1!' };

    const response = await request(app.getHttpServer())
      .post('/api/users')
      .send(dto)
      .expect(201);

    expect(response.body).toMatchObject({
      id:    expect.any(String),
      name:  'Alice',
      email: 'alice@example.com',
    });
    expect(response.body).not.toHaveProperty('password');  // Password must not be exposed
  });

  // ── POST /api/users — invalid body (ValidationPipe) ───────────────────────
  it('POST /api/users with missing email → 400', async () => {
    const response = await request(app.getHttpServer())
      .post('/api/users')
      .send({ name: 'Alice' })          // Missing email and password
      .expect(400);

    expect(response.body.message).toBeInstanceOf(Array);
    expect(response.body.message).toContain(expect.stringContaining('email'));
  });

  // ── GET /api/users/:id — not found ────────────────────────────────────────
```

**Q11. How do you handle `beforeAll` vs `beforeEach` in e2e tests, and what are the tradeoffs?**

A:

```typescript
// ── beforeAll: shared app across all tests in the describe block ──────────────
// app is created once, all tests share the same instance
// Faster: module compilation and app.init() are expensive (100–500ms each)
// Risk: tests that mutate shared state (DB rows, in-memory stores) can affect
//       each other — test order matters, isolation is weaker

describe('UsersController (e2e) — beforeAll', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const module = await Test.createTestingModule({ imports: [AppModule] }).compile();
    app = module.createNestApplication();
    await app.init();
  });

  afterAll(() => app.close());

  // All tests share the same app — mutations persist between tests
  // If test 1 creates user A, test 2 sees user A in the DB
});

// ── beforeEach: fresh app per test ────────────────────────────────────────────
// New module and app compiled for every test
// Slower: compilation runs N times for N tests (can be 2–10 seconds per test)
// Safer: complete isolation — no shared state between tests
// Use for: tests that mutate state, integration tests with a real DB

describe('UsersController (e2e) — beforeEach', () => {
  let app: INestApplication;

  beforeEach(async () => {
    const module = await Test.createTestingModule({ imports: [AppModule] }).compile();
    app = module.createNestApplication();
    await app.init();
  });

  afterEach(() => app.close());

  // Each test gets a fresh app — complete isolation
});

// ── Best practice: beforeAll with database cleanup ────────────────────────────
// Fast (one compilation) + isolated (DB reset between tests):
describe('UsersController (e2e)', () => {
  let app: INestApplication;
  let dataSource: DataSource;

  beforeAll(async () => {
    const module = await Test.createTestingModule({ imports: [AppModule] }).compile();
    app        = module.createNestApplication();
    dataSource = module.get<DataSource>(DataSource);
    await app.init();
  });

  beforeEach(async () => {
    // Truncate tables between tests — fast and isolated:
    await dataSource.query('TRUNCATE TABLE users CASCADE');
  });

  afterAll(() => app.close());
});
```

**Q12. How do you test authenticated endpoints in e2e tests?**

A: Three strategies depending on test intent:

```typescript
// ── Strategy 1: Override the guard entirely (fastest, most common) ─────────────
// Best when: you're testing business logic, not auth itself
.overrideGuard(JwtAuthGuard)
.useValue({
  canActivate: (context: ExecutionContext) => {
    const req = context.switchToHttp().getRequest();
    req.user  = {
      id:    'e2e-user-id',
      email: 'e2e@test.com',
      roles: ['admin'],     // Set roles as needed per test
    };
    return true;
  },
})

// ── Strategy 2: Generate a real JWT using the app's own JwtService ─────────────
// Best when: you're testing that auth headers are correctly processed
let jwtService: JwtService;
// After module.compile():
jwtService = module.get<JwtService>(JwtService);

it('GET /api/profile → 200 for authenticated user', async () => {
  const token = jwtService.sign({ sub: 'user-1', email: 'alice@example.com' });

  const response = await request(app.getHttpServer())
    .get('/api/profile')
    .set('Authorization', `Bearer ${token}`)   // Set the header like a real client
    .expect(200);
});

it('GET /api/profile → 401 without token', async () => {
  await request(app.getHttpServer())
    .get('/api/profile')
    .expect(401);
});

// ── Strategy 3: Hit the login endpoint first, then use the returned token ──────
// Best when: testing the full auth flow end-to-end
it('full auth flow', async () => {
  // Step 1: Register
  await request(app.getHttpServer())
    .post('/api/auth/register')
    .send({ email: 'alice@test.com', password: 'Password1!' })
    .expect(201);

  // Step 2: Login → get token
  const loginRes = await request(app.getHttpServer())
    .post('/api/auth/login')
    .send({ email: 'alice@test.com', password: 'Password1!' })
    .expect(200);

  const { accessToken } = loginRes.body;

  // Step 3: Use token for protected endpoint
  const profileRes = await request(app.getHttpServer())
    .get('/api/profile')
    .set('Authorization', `Bearer ${accessToken}`)
    .expect(200);

  expect(profileRes.body.email).toBe('alice@test.com');
});
```

**Q13. How do you provide a TypeORM repository mock using `getRepositoryToken()`?**

A: TypeORM repositories are provided in NestJS using a special token generated from the entity class. `getRepositoryToken(Entity)` returns this token — you must use it to provide a mock, not the `Repository` class itself:

```typescript
import { getRepositoryToken } from '@nestjs/typeorm';
import { Repository }         from 'typeorm';
import { User }               from './user.entity';

// ── Mock repository factory ───────────────────────────────────────────────────
// Type-safe: every method on Repository<User> has a corresponding jest.fn()
type MockRepository<T = any> = Partial<Record<keyof Repository<T>, jest.Mock>>;

const createMockRepository = <T>(): MockRepository<T> => ({
  find:     jest.fn(),
  findOne:  jest.fn(),
  findBy:   jest.fn(),
  save:     jest.fn(),
  create:   jest.fn(),
  delete:   jest.fn(),
  update:   jest.fn(),
  count:    jest.fn(),
  exist:    jest.fn(),
  createQueryBuilder: jest.fn().mockReturnValue({
    where:    jest.fn().mockReturnThis(),
    andWhere: jest.fn().mockReturnThis(),
    orderBy:  jest.fn().mockReturnThis(),
    skip:     jest.fn().mockReturnThis(),
    take:     jest.fn().mockReturnThis(),
    getMany:  jest.fn().mockResolvedValue([]),
    getOne:   jest.fn().mockResolvedValue(null),
    getManyAndCount: jest.fn().mockResolvedValue([[], 0]),
  }),
});

// ── TestingModule setup ───────────────────────────────────────────────────────
describe('UsersService with TypeORM mock', () => {
  let service:    UsersService;
  let userRepo:   MockRepository<User>;

  beforeEach(async () => {
    userRepo = createMockRepository<User>();

    const module = await Test.createTestingModule({
      providers: [
        UsersService,
        {
          provide:  getRepositoryToken(User),   // ← MUST use getRepositoryToken
          useValue: userRepo,
        },
      ],
    }).compile();

    service = module.get<UsersService>(UsersService);
  });

  afterEach(() => jest.clearAllMocks());

  it('finds users by email domain', async () => {
    const users = [{ id: '1', email: 'a@test.com' }] as User[];
    userRepo.findBy!.mockResolvedValue(users);

    const result = await service.findByDomain('test.com');
    expect(result).toHaveLength(1);
    expect(userRepo.findBy).toHaveBeenCalledWith(
      expect.objectContaining({ email: expect.any(Object) })
    );
  });
});
```

**Q14. When do you test with a real database vs a mock repository, and how do you set up an in-memory DB?**

A:

| Approach | Tests what | Speed | Isolation | Use for |
|---|---|---|---|---|
| Mock repository | Service logic, error handling | Fast | Perfect | Unit tests of business logic |
| In-memory SQLite | Real SQL queries, TypeORM behavior | Medium | Good | Integration tests of query logic |
| Real Postgres (test container) | Full stack including DB | Slow | Moderate | True integration / e2e |

```typescript
// ── In-memory SQLite for integration tests ────────────────────────────────────
// Catches real query bugs (wrong column names, missing relations) that mocks hide

import { TypeOrmModule }   from '@nestjs/typeorm';
import { DataSource }       from 'typeorm';

describe('UsersService (integration)', () => {
  let module:     TestingModule;
  let service:    UsersService;
  let dataSource: DataSource;

  beforeAll(async () => {
    module = await Test.createTestingModule({
      imports: [
        TypeOrmModule.forRoot({
          type:        'better-sqlite3',  // npm install better-sqlite3 @types/better-sqlite3
          database:    ':memory:',         // In-memory — no file, no cleanup needed
          entities:    [User, Order],
          synchronize: true,               // Auto-create schema from entities
          dropSchema:  true,               // Start fresh (important with forRoot)
          logging:     false,
        }),
        TypeOrmModule.forFeature([User, Order]),
        UsersModule,
      ],
    }).compile();

    service    = module.get<UsersService>(UsersService);
    dataSource = module.get<DataSource>(DataSource);
    await module.init();
  });

  afterAll(async () => {
    await dataSource.destroy();   // Closes the SQLite connection
    await module.close();
  });

  beforeEach(async () => {
    // Clear data between tests:
    await dataSource.query('DELETE FROM users');
  });

  it('persists and retrieves a user with real SQL', async () => {
    await service.createUser({ email: 'alice@example.com', name: 'Alice' });
    const users = await service.findAll();
    expect(users).toHaveLength(1);
    expect(users[0].email).toBe('alice@example.com');
  });

  it('raises a unique constraint error for duplicate email', async () => {
    await service.createUser({ email: 'alice@example.com', name: 'Alice' });
    await expect(
      service.createUser({ email: 'alice@example.com', name: 'Alice 2' })
    ).rejects.toThrow();   // Real DB constraint fires — no mock can simulate this
  });
});
```

## Section 8: Test Isolation and Lifecycle

**Q15. What is the difference between `jest.clearAllMocks()`, `jest.resetAllMocks()`, and `jest.restoreAllMocks()`?**

A:

```typescript
const fn = jest.fn().mockReturnValue(42);
fn();   // Recorded call

// ── jest.clearAllMocks() ────────────────────────────────────────────────────
jest.clearAllMocks();
// Clears: mock.calls, mock.instances, mock.results — call tracking reset
// Keeps:  mockReturnValue(42) — implementation stays
fn();   // Still returns 42 (implementation preserved)
expect(fn).toHaveBeenCalledTimes(1);   // Only the post-clear call counted

// Use in: afterEach() — start each test with a clean call record
//         while keeping the default mock behavior across tests

// ── jest.resetAllMocks() ────────────────────────────────────────────────────
jest.resetAllMocks();
// Clears: call tracking (same as clear)
// Resets: mockReturnValue — implementation removed, fn now returns undefined
fn();   // Returns undefined (implementation cleared)
expect(fn).toHaveBeenCalledTimes(1);

// Use in: when each test should set up its own return values
//         from scratch — prevents previous test's mockReturnValue leaking

// ── jest.restoreAllMocks() ──────────────────────────────────────────────────
const original = { getValue: () => 'real' };
jest.spyOn(original, 'getValue').mockReturnValue('mocked');
original.getValue();   // → 'mocked'

jest.restoreAllMocks();
// Restores: spy targets to their original implementation
// Only affects: spies created with jest.spyOn — NOT standalone jest.fn()
original.getValue();   // → 'real' (original restored)

// Use in: afterEach() when using jest.spyOn() on real modules
//         Never use with pure jest.fn() mocks — it has no effect on them

// ── Practical configuration — jest.config.ts ─────────────────────────────────
export default {
  clearMocks:   true,   // Equivalent to calling jest.clearAllMocks() after every test
  resetMocks:   false,  // Don't reset implementations between tests
  restoreMocks: false,  // Don't restore spies between tests
  // Recommendation: clearMocks: true for most projects;
  // add restoreMocks: true if you heavily use jest.spyOn()
};
```

## Section 9: Scenario-Based Questions

**Q17. "What is wrong with this test suite and what are the consequences?"**

```typescript
describe('UsersService', () => {
  let service: UsersService;

  const mockRepo = {
    findOne: jest.fn().mockResolvedValue({ id: '1', email: 'alice@test.com' }),
    save:    jest.fn().mockResolvedValue({ id: '2', email: 'bob@test.com' }),
  };

  beforeAll(async () => {
    const module = await Test.createTestingModule({
      providers: [
        UsersService,
        { provide: getRepositoryToken(User), useValue: mockRepo },
      ],
    }).compile();
    service = module.get<UsersService>(UsersService);
  });

  it('finds a user by id', async () => {
    const result = await service.findOne('1');
    expect(result.email).toBe('alice@test.com');
  });

  it('creates a user', async () => {
    mockRepo.findOne.mockResolvedValue(null);   // Override for this test
    const result = await service.create({ email: 'charlie@test.com' });
    expect(result.email).toBe('charlie@test.com');
  });

  it('throws when user not found', async () => {
    await expect(service.findOne('999')).rejects.toThrow(NotFoundException);
  });
});
```

A: Five problems:

**Problem 1 — `beforeAll` with mutable shared mock state:**
```typescript
// The mock object is shared across ALL tests.
// Test 2 calls mockRepo.findOne.mockResolvedValue(null) — that change persists
// into test 3. Test 3 calls service.findOne('999'), which calls mockRepo.findOne()
// — it now returns null (from test 2's override) instead of the initial
// { id: '1', email: 'alice@test.com' }. Test ordering becomes a hidden dependency.
// FIX: use beforeEach to recreate the module, or call jest.clearAllMocks() in afterEach.
```

**Problem 2 — No `afterAll(() => module.close())`:**
```typescript
// Without module.close(), Jest waits for open handles and eventually
// prints "Jest did not exit one second after the test run has completed"
// and hangs. Any onModuleDestroy lifecycle hooks never fire.
// FIX: add afterAll(async () => { await module.close(); });
```

**Problem 3 — Test 3 will fail due to stale mock state (from Problem 1):**
```typescript
// After test 2 sets mockResolvedValue(null), test 3 gets null from findOne.
// If findOne(null) returns null (not throws), the test expects a throw — it won't get one.
// Result: test 3 passes for the wrong reason OR fails intermittently based on test order.
```

**Problem 4 — Test 2's `result.email` assertion is wrong:**
```typescript
// service.create() calls repo.save() which returns { id: '2', email: 'bob@test.com' }
// (the save mock's return value). The input email was 'charlie@test.com' but
// the result will have 'bob@test.com' from the mock.
// This test would fail because it expects 'charlie@test.com' but gets 'bob@test.com'.
// FIX: mockRepo.save.mockResolvedValue({ id: '2', email: 'charlie@test.com' })
```

**Problem 5 — No `jest.clearAllMocks()` between tests:**
```typescript
// Call counts accumulate. After all 3 tests run, expect(mockRepo.findOne).toHaveBeenCalledTimes(1)
// in any test would be wrong because findOne was called in tests 1 and 3 (at minimum).
// FIX: add afterEach(() => jest.clearAllMocks()) — or set clearMocks: true in jest.config.ts.
```

**Corrected test suite:**
```typescript
describe('UsersService', () => {
  let module:  TestingModule;
  let service: UsersService;
  let repo:    MockRepository<User>;

  beforeEach(async () => {
    repo = {
      findOne: jest.fn(),
      save:    jest.fn(),
    };

    module = await Test.createTestingModule({
      providers: [
        UsersService,
        { provide: getRepositoryToken(User), useValue: repo },
      ],
    }).compile();

    service = module.get<UsersService>(UsersService);
  });

  afterEach(async () => {
    jest.clearAllMocks();
    await module.close();
  });

  it('finds a user by id', async () => {
    repo.findOne!.mockResolvedValue({ id: '1', email: 'alice@test.com' } as User);

    const result = await service.findOne('1');
    expect(result.email).toBe('alice@test.com');
  });

  it('creates a user', async () => {
    repo.findOne!.mockResolvedValue(null);  // No duplicate
    repo.save!.mockImplementation(async (user) => ({ ...user, id: '2' }));  // Reflect input

    const result = await service.create({ email: 'charlie@test.com', name: 'Charlie' });
    expect(result.email).toBe('charlie@test.com');  // Now correct
  });

  it('throws NotFoundException when user not found', async () => {
    repo.findOne!.mockResolvedValue(null);  // Explicitly set for this test

    await expect(service.findOne('999')).rejects.toThrow(NotFoundException);
  });
});
```

|---|---|
| `Test.createTestingModule({ providers, imports, controllers })` | Creates an isolated NestJS IoC container — no HTTP server |

| `overrideInterceptor(I).useValue(...)` | Replace an interceptor |
| `overridePipe(P).useValue(...)` | Replace a pipe |
| `overrideFilter(F).useClass(...)` | Replace an exception filter |

| `module.createNestApplication()` | Creates `INestApplication` from TestingModule — for e2e tests |
| `app.init()` | Starts the application (runs `onApplicationBootstrap`, applies middleware) |
| `app.close()` | Shuts down the application — always call in `afterAll` |
| `request(app.getHttpServer())` | Supertest entry point — returns a test agent for the app's HTTP server |
| `jest.fn()` | Standalone mock function — use in `useValue` objects |
| `jest.spyOn(obj, 'method')` | Wraps a real method — can call through or mock; restored with `restoreAllMocks()` |
| `mockResolvedValue(v)` | `async fn` returns `v` — equivalent to `mockReturnValue(Promise.resolve(v))` |
| `mockRejectedValue(err)` | `async fn` throws `err` |
| `mockImplementation(fn)` | Full control per-call logic based on arguments |
| `mockReturnValueOnce(v)` | Returns `v` only on the next call — combine to create sequences |
| `jest.clearAllMocks()` | Clears call tracking, keeps implementations — use in `afterEach` |
| `jest.resetAllMocks()` | Clears call tracking AND implementations — each test must re-set return values |
| `jest.restoreAllMocks()` | Restores original implementations for spies — for `jest.spyOn()` only |
| `beforeAll` vs `beforeEach` | `beforeAll`: one app for all tests (fast); `beforeEach`: fresh app per test (isolated) |
| Global pipes in e2e | `app.useGlobalPipes(new ValidationPipe(...))` — must replicate `main.ts` setup |
| Auth in e2e tests | Override guard, generate real JWT, or hit login endpoint — choose by test intent |
| In-memory SQLite | `type: 'better-sqlite3', database: ':memory:', synchronize: true` — real queries, no cleanup |

**Tip for interviews:** Five things separate strong candidates on this topic: (1) knowing **why `module.close()` matters** — without it, the NestJS IoC container's `onModuleDestroy` hooks never fire, database connections stay open, timers keep running, and Jest hangs after tests finish with "open handles" warnings; this is the single most common NestJS test bug in practice; (2) explaining the **`getRepositoryToken(Entity)` requirement** — TypeORM repository tokens in NestJS are not the `Repository` class itself but a symbol generated by `getRepositoryToken()`, so `{ provide: Repository, useValue: mock }` never matches and the real repository gets injected instead of the mock; the provider silently does nothing and the test fails mysteriously; (3) the **`overrideProvider()` vs `useValue` in providers[]** distinction — `useValue` in providers works when you're building the module yourself; `overrideProvider()` is needed when you've imported a real feature module and want to replace a provider deep inside it without re-declaring the whole module; this is the standard pattern for e2e tests that import `AppModule` but mock the database; (4) the **global setup gap in e2e tests** — `app.useGlobalPipes(new ValidationPipe(...))`, `app.useGlobalFilters(...)`, and `app.setGlobalPrefix(...)` must be explicitly applied after `createNestApplication()` because they're not part of the module — they're applied in `main.ts` to the running application; an e2e test that skips these will validate against a different configuration than production and miss real bugs like validation failures returning 201 instead of 400; and (5) the **`beforeAll` stale mock trap** — defining mock objects outside `beforeEach` and using `beforeAll` means test 2's `mockResolvedValue()` override persists into test 3; `jest.clearAllMocks()` in `afterEach` resets call counts but NOT implementations; the safe pattern is to create fresh mock objects inside `beforeEach` so every test starts from a known state.
