# Dynamic Modules: `forRoot`, `forRootAsync`, `forFeature` — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Static vs Dynamic Modules

**Q1. What is the difference between a static module and a dynamic module in NestJS?**
A: A **static module** has a fixed set of providers and imports declared at class definition time. Its behavior is identical every time it is imported — there is no way to pass configuration into it.

A **dynamic module** is a module whose providers, controllers, exports, and configuration can be computed at runtime based on arguments passed when importing it. The `@Module()` decorator is replaced or supplemented by a static method (conventionally `forRoot`, `forRootAsync`, `forFeature`, or `register`) that returns a `DynamicModule` object describing what the module should contain for that specific use.

```ts
// Static module — fixed, not configurable:
@Module({
  providers: [DatabaseService],
  exports:   [DatabaseService],
})
export class DatabaseModule {}

// Importing it — no way to pass a connection URL:
@Module({ imports: [DatabaseModule] })
export class AppModule {}

// -----------------------------------------------------------------------

// Dynamic module — configurable at import time:
@Module({})
export class DatabaseModule {
  static forRoot(connectionUrl: string): DynamicModule {
    return {
      module:    DatabaseModule,
      providers: [
        {
          provide:  'CONNECTION_URL',        // inject the config as a token
          useValue: connectionUrl,
        },
        DatabaseService,                     // DatabaseService can inject 'CONNECTION_URL'
      ],
      exports: [DatabaseService],
    };
  }
}

// Importing it — pass the configuration:
@Module({
  imports: [DatabaseModule.forRoot('postgres://localhost:5432/mydb')],
})
export class AppModule {}

// Different modules can import with different configs:
@Module({
  imports: [DatabaseModule.forRoot('postgres://localhost:5432/analytics')],
})
export class AnalyticsModule {}
```

The `DynamicModule` interface that every dynamic module factory must return:
```ts
export interface DynamicModule extends ModuleMetadata {
  module: Type<any>;            // ← the class itself (required)
  global?: boolean;             // ← true = available app-wide without importing
  providers?: Provider[];
  controllers?: Type<any>[];
  imports?: Array<...>;
  exports?: Array<...>;
}
// It is exactly a @Module() metadata object plus the required `module` field
```

**Q2. Why do dynamic modules exist — what problem do they solve that providers and config files cannot?**
A: The core problem: NestJS resolves the module graph at bootstrap before any provider is instantiated. A static `@Module()` decorator is evaluated when the file is parsed — at that point, no `ConfigService` exists yet, no environment variables have been validated, and no async operations can be awaited.

Dynamic modules solve three distinct problems:

**Problem 1 — Configuration must flow into provider factories**:
```ts
// ❌ Can't access ConfigService in a static @Module decorator:
@Module({
  providers: [
    {
      provide:    DatabaseService,
      useFactory: (config: ConfigService) => new DatabaseService(config.get('DB_URL')),
      inject:     [ConfigService],
      // ConfigService is from another module — how does this module know about it?
      // With static module, it doesn't know what's available at import time.
    },
  ],
})
export class DatabaseModule {}

// ✓ Dynamic module receives the module context — can declare what it needs:
static forRootAsync(options: {
  useFactory: (...args: any[]) => DatabaseOptions;
  inject?: any[];
  imports?: any[];
}): DynamicModule {
  return {
    module: DatabaseModule,
    imports: options.imports ?? [],     // ← import ConfigModule here
    providers: [
      {
        provide:    DATABASE_OPTIONS,
        useFactory: options.useFactory, // ← factory runs after ConfigService is available
        inject:     options.inject ?? [],
      },
      DatabaseService,
    ],
    exports: [DatabaseService],
  };
}
```

**Problem 2 — The same module needs different behavior in different parts of the app**:
```ts
// TypeORM: one connection configured globally (forRoot),
//          different entities registered per feature (forFeature):
TypeOrmModule.forRoot({ type: 'postgres', ... })   // once, in AppModule
TypeOrmModule.forFeature([User, Post])             // in UsersModule — only User + Post repos
TypeOrmModule.forFeature([Order, Product])         // in OrdersModule — only Order + Product repos
```

**Problem 3 — Module options need async resolution (database credentials from AWS Secrets Manager, etc.)**:
```ts
// ❌ Synchronous forRoot can't await anything:
DatabaseModule.forRoot({ url: process.env.DB_URL }) // must be known at parse time

// ✓ forRootAsync can await:
DatabaseModule.forRootAsync({
  useFactory: async (secretsService: SecretsService) => {
    const secret = await secretsService.getSecret('db/production'); // async!
    return { url: secret.connectionString };
  },
  inject:   [SecretsService],
  imports:  [SecretsModule],
})
```

### Section 2: `forRoot` — Synchronous Global Configuration

**Q3. What is the `forRoot` pattern, what does it return, and when is it the right choice?**
A: `forRoot` is a static method on a module class that synchronously returns a `DynamicModule`. It is conventionally used when:
- The configuration is available at module instantiation time (environment variables, config objects)
- The module should be configured **once** at the application root (`AppModule`) and shared across the entire app
- No async work is needed to produce the configuration

```ts
// Complete forRoot implementation:
import { DynamicModule, Module, Global } from '@nestjs/common';

export interface HttpClientOptions {
  baseUrl:      string;
  timeout:      number;
  retries:      number;
  apiKey?:      string;
}

export const HTTP_CLIENT_OPTIONS = Symbol('HTTP_CLIENT_OPTIONS');

@Global()   // ← optional: @Global() makes forRoot providers available everywhere
@Module({}) // ← empty @Module() — all providers come from forRoot's return value
export class HttpClientModule {
  static forRoot(options: HttpClientOptions): DynamicModule {
    return {
      module:  HttpClientModule,
      global:  true,             // ← alternative to @Global() decorator
      providers: [
        {
          provide:  HTTP_CLIENT_OPTIONS,
          useValue: options,               // synchronous — just store the options
        },
        HttpClientService,                 // injects HTTP_CLIENT_OPTIONS
      ],
      exports: [HttpClientService],        // make service available to importers
    };
  }
}

// Service that uses the options:
@Injectable()
export class HttpClientService {
  private readonly client: AxiosInstance;

  constructor(
    @Inject(HTTP_CLIENT_OPTIONS)
    private readonly options: HttpClientOptions,
  ) {
    this.client = axios.create({
      baseURL: options.baseUrl,
      timeout: options.timeout,
      headers: options.apiKey ? { 'X-API-Key': options.apiKey } : {},
    });
  }
}

// AppModule — configure once:
@Module({
  imports: [
    HttpClientModule.forRoot({
      baseUrl: 'https://api.partner.com',
      timeout: 5000,
      retries: 3,
      apiKey:  process.env.PARTNER_API_KEY,
    }),
  ],
})
export class AppModule {}

// Any module in the app can inject HttpClientService (because global: true)
// without importing HttpClientModule
```

**Q4. What does `global: true` on a dynamic module mean and what are the trade-offs of using it?**
A: A module with `global: true` (or decorated with `@Global()`) registers its exports in the **global module scope**. Every other module in the application can inject the exported providers without explicitly importing the module.

```ts
// With global: true on forRoot:
@Module({
  imports: [ConfigModule.forRoot({ isGlobal: true })],  // NestJS ConfigModule's option
})
export class AppModule {}

// Other modules: ConfigService is available without importing ConfigModule
@Injectable()
export class UsersService {
  constructor(private config: ConfigService) {}  // ✓ works — no ConfigModule import needed
}

// Without global: true:
@Module({
  imports: [ConfigModule.forRoot()],  // not global
})
export class AppModule {}

@Module({
  imports: [ConfigModule],  // ← must import explicitly in EVERY module that needs ConfigService
})
export class UsersModule {}
```

Trade-offs:
```
global: true — BENEFITS:
  ✓ Eliminates repetitive imports across many modules (ConfigModule, LoggerModule)
  ✓ Cleaner module files — one import instead of N
  ✓ Appropriate for cross-cutting infrastructure (logging, config, metrics)

global: true — COSTS:
  ✗ Hidden dependencies: UsersService depends on ConfigService but UsersModule doesn't
    declare that dependency — harder to understand and test in isolation
  ✗ Harder to tree-shake or replace: every module silently depends on globals
  ✗ Name collisions: global providers with the same token overwrite each other

GUIDELINE:
  Use global for: NestJS ConfigModule, LoggerModule, EventEmitterModule
                  — things consumed by nearly every module
  Avoid global for: domain services, feature modules
                    — keep dependencies explicit and visible
```

### Section 3: `forRootAsync` — Asynchronous Configuration

**Q5. What is `forRootAsync` and what three strategies can it use to resolve the options?**
A: `forRootAsync` accepts an options object describing *how* to asynchronously produce the module's configuration, rather than accepting the configuration directly. This allows the configuration to depend on other providers (like `ConfigService`) that are only available after NestJS bootstraps its DI container.

The three strategies mirror NestJS's general provider patterns:

**Strategy 1: `useFactory` — most common:**
```ts
DatabaseModule.forRootAsync({
  imports:    [ConfigModule],          // import modules whose providers we need
  useFactory: (config: ConfigService) => ({
    type:     'postgres',
    host:     config.get('DB_HOST'),
    port:     config.get<number>('DB_PORT'),
    database: config.get('DB_NAME'),
    username: config.get('DB_USER'),
    password: config.get('DB_PASS'),
  }),
  inject: [ConfigService],            // inject these into the factory function
});

// useFactory can be async — await external secrets, wait for connections, etc.:
DatabaseModule.forRootAsync({
  imports:    [SecretsModule],
  useFactory: async (secrets: SecretsService) => {
    const creds = await secrets.get('db/prod');   // async! can await anything
    return { url: creds.connectionString };
  },
  inject: [SecretsService],
});
```

**Strategy 2: `useClass` — factory as a provider class:**
```ts
// Define a class that implements the options factory interface:
@Injectable()
export class DatabaseConfigFactory implements DatabaseOptionsFactory {
  constructor(private config: ConfigService) {}   // can inject its own deps

  createDatabaseOptions(): DatabaseModuleOptions {
    return {
      host: this.config.get('DB_HOST'),
      port: this.config.get<number>('DB_PORT'),
    };
  }
}

// Register via useClass — NestJS instantiates the factory class:
DatabaseModule.forRootAsync({
  useClass: DatabaseConfigFactory,
  // NestJS creates a new DatabaseConfigFactory, calls createDatabaseOptions()
  // The factory instance is local to this module (not shared)
});
```

**Strategy 3: `useExisting` — reuse an already-registered provider:**
```ts
// If ConfigService already implements DatabaseOptionsFactory:
@Injectable()
export class ConfigService implements DatabaseOptionsFactory {
  createDatabaseOptions() {
    return { host: this.get('DB_HOST'), ... };
  }
}

// useExisting: reuse the existing ConfigService singleton (no new instance):
DatabaseModule.forRootAsync({
  imports:     [ConfigModule],
  useExisting: ConfigService,     // uses the SAME ConfigService instance from ConfigModule
  // vs useClass: DatabaseConfigFactory which creates a NEW instance of the factory
});
```

**Q6. How do you implement `forRootAsync` inside your own custom module?**
A: The implementation translates the async options object into a provider definition that resolves the options, plus the module's own providers that inject those options.

```ts
// The async options type (what callers pass to forRootAsync):
export interface EmailModuleAsyncOptions {
  imports?:    any[];
  useFactory?: (...args: any[]) => Promise<EmailModuleOptions> | EmailModuleOptions;
  inject?:     any[];
  useClass?:   Type<EmailOptionsFactory>;
  useExisting?: Type<EmailOptionsFactory>;
}

// Factory interface for useClass / useExisting:
export interface EmailOptionsFactory {
  createEmailOptions(): Promise<EmailModuleOptions> | EmailModuleOptions;
}

@Module({})
export class EmailModule {
  // Synchronous — options known at call time:
  static forRoot(options: EmailModuleOptions): DynamicModule {
    return {
      module:    EmailModule,
      providers: [
        { provide: EMAIL_OPTIONS, useValue: options },
        EmailService,
      ],
      exports: [EmailService],
    };
  }

  // Asynchronous — options resolved from DI container:
  static forRootAsync(asyncOptions: EmailModuleAsyncOptions): DynamicModule {
    return {
      module:    EmailModule,
      imports:   asyncOptions.imports ?? [],       // ← imported modules (e.g. ConfigModule)
      providers: [
        ...EmailModule.createAsyncProviders(asyncOptions), // ← resolves options
        EmailService,                                       // ← uses resolved options
      ],
      exports: [EmailService],
    };
  }

  // Build the correct provider based on the strategy chosen:
  private static createAsyncProviders(
    asyncOptions: EmailModuleAsyncOptions,
  ): Provider[] {
    if (asyncOptions.useFactory) {
      return [
        {
          provide:    EMAIL_OPTIONS,
          useFactory: asyncOptions.useFactory,
          inject:     asyncOptions.inject ?? [],
        },
      ];
    }

    if (asyncOptions.useClass) {
      return [
        // 1. Register the factory class as a provider (so it can inject its own deps):
        {
          provide:  asyncOptions.useClass,
          useClass: asyncOptions.useClass,
        },
        // 2. Use the factory class to produce the options:
        {
          provide:    EMAIL_OPTIONS,
          useFactory: async (factory: EmailOptionsFactory) =>
            factory.createEmailOptions(),
          inject:     [asyncOptions.useClass],
        },
      ];
    }

    if (asyncOptions.useExisting) {
      return [
        {
          provide:    EMAIL_OPTIONS,
          useFactory: async (factory: EmailOptionsFactory) =>
            factory.createEmailOptions(),
          inject:     [asyncOptions.useExisting],
        },
        // NOTE: no separate provider for useExisting — it's already registered elsewhere
      ];
    }

    throw new Error('EmailModule.forRootAsync: must provide useFactory, useClass, or useExisting');
  }
}
```

### Section 4: `forFeature` — Feature-Level Registration

**Q7. What is `forFeature` and how does it relate to `forRoot`?**
A: The `forRoot` / `forFeature` pairing is a two-tier pattern: `forRoot` establishes a global configuration once (a database connection, a schema registry, a message broker connection); `forFeature` registers feature-specific resources (entity repositories, schemas, queue definitions) that use the global configuration but are scoped to the importing feature module.

```
forRoot  → called once in AppModule
           → sets up the shared infrastructure (connection pool, client instance)
           → its providers are exported globally or imported by feature modules

forFeature → called in each feature module
             → registers feature-specific providers (repositories, schemas, queues)
             → those providers are available ONLY within that feature module (not exported globally)
             → uses the infrastructure established by forRoot

TypeORM example (the canonical forRoot + forFeature pair):
  AppModule:
    TypeOrmModule.forRoot({ type: 'postgres', host: '...', entities: [...] })
    → Creates and exports the DataSource (shared connection)

  UsersModule:
    TypeOrmModule.forFeature([User, UserProfile])
    → Creates getRepository(User) and getRepository(UserProfile) providers
    → These providers are only available inside UsersModule
    → UsersService can inject Repository<User> without AppModule knowing about it

  OrdersModule:
    TypeOrmModule.forFeature([Order, OrderItem])
    → Creates getRepository(Order) and getRepository(OrderItem) providers
    → OrdersService gets its own repositories, scoped to OrdersModule
```

**Q8. How does `forFeature` work mechanically — how does it produce scoped providers?**
A: `forFeature` uses the global infrastructure (DataSource, connection) that `forRoot` established as a shared provider, and wraps it in feature-specific factory providers that generate the feature's resources on demand.

```ts
// Simplified TypeORM forFeature implementation (conceptual):
@Module({})
export class TypeOrmModule {
  static forRoot(options: TypeOrmModuleOptions): DynamicModule {
    return {
      module:  TypeOrmModule,
      global:  true,
      providers: [
        {
          provide:    DataSource,               // ← shared connection
          useFactory: async () => {
            const ds = new DataSource(options);
            await ds.initialize();
            return ds;
          },
        },
        EntityManager,                          // ← shared entity manager
      ],
      exports: [DataSource, EntityManager],
    };
  }

  static forFeature(entities: EntityClassOrSchema[]): DynamicModule {
    // Create a provider for each entity's repository:
    const repositoryProviders: Provider[] = entities.map(entity => ({
      provide:    getRepositoryToken(entity),       // e.g. 'UserRepository'
      useFactory: (dataSource: DataSource) =>
        dataSource.getRepository(entity),           // creates Repository<User>
      inject:     [DataSource],                     // uses the shared DataSource
    }));

    return {
      module:    TypeOrmModule,
      providers: repositoryProviders,
      exports:   repositoryProviders,   // export so the feature module's services can inject them
      // NOTE: these repositories are NOT exported globally — scoped to the importing module
    };
  }
}

// What happens at runtime:
// 1. AppModule imports TypeOrmModule.forRoot(...)
//    → DataSource created, registered globally
// 2. UsersModule imports TypeOrmModule.forFeature([User])
//    → NestJS creates a 'UserRepository' provider using the global DataSource
//    → UserRepository is available in UsersModule's DI scope
// 3. OrdersModule imports TypeOrmModule.forFeature([Order])
//    → NestJS creates an 'OrderRepository' provider in OrdersModule's scope
//    → OrdersModule doesn't see UserRepository; UsersModule doesn't see OrderRepository

@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(User)             // resolves 'UserRepository' token
    private userRepo: Repository<User>,
  ) {}
}
```

**Q9. How do Mongoose, BullMQ, and JWT implement `forFeature` / `register` and what does each register?**
A: Each library adapts the pattern to its own domain resources:

```ts
// ── MONGOOSE ─────────────────────────────────────────────────────────────
// forRoot: establishes the MongoDB connection
MongooseModule.forRoot('mongodb://localhost/mydb')

// forFeature: registers schemas for that feature module
MongooseModule.forFeature([
  { name: User.name,    schema: UserSchema },
  { name: Profile.name, schema: ProfileSchema },
])
// → creates providers: getModelToken('User') and getModelToken('Profile')
// → scoped to the importing module

@Injectable()
export class UsersService {
  constructor(
    @InjectModel(User.name) private userModel: Model<UserDocument>,
  ) {}
}

// ── BULLMQ ───────────────────────────────────────────────────────────────
// forRoot: registers Redis connection shared by all queues
BullModule.forRoot({
  connection: { host: 'localhost', port: 6379 },
})

// forFeature (registerQueue): registers a specific named queue
BullModule.registerQueue({ name: 'email' })  // in EmailModule
BullModule.registerQueue({ name: 'orders' }) // in OrdersModule
// → each queue uses the shared Redis connection but has its own queue name/prefix

@InjectQueue('email') private emailQueue: Queue   // only available in EmailModule
@InjectQueue('orders') private ordersQueue: Queue // only available in OrdersModule

// ── JWT ──────────────────────────────────────────────────────────────────
// No forRoot for JWT (no shared connection) — each module registers its own:
JwtModule.register({ secret: 'my-secret', signOptions: { expiresIn: '1h' } })
JwtModule.registerAsync({
  useFactory: (config: ConfigService) => ({
    secret:      config.get('JWT_SECRET'),
    signOptions: { expiresIn: config.get('JWT_EXPIRY') },
  }),
  inject: [ConfigService],
})
// → JwtService available in the importing module only
// Different modules can register with different secrets/expiry if needed

// ── TYPEORM (detailed) ───────────────────────────────────────────────────
// forRootAsync with multiple databases:
TypeOrmModule.forRootAsync({
  name:        'analytics',             // named connection
  useFactory:  (config: ConfigService) => ({
    type:      'postgres',
    host:      config.get('ANALYTICS_DB_HOST'),
    entities:  [AnalyticsEvent],
  }),
  inject: [ConfigService],
})
// forFeature with named connection:
TypeOrmModule.forFeature([AnalyticsEvent], 'analytics')
@InjectRepository(AnalyticsEvent, 'analytics') repo: Repository<AnalyticsEvent>
```

### Section 5: `ConfigurableModuleBuilder` (NestJS 9+)

**Q10. What is `ConfigurableModuleBuilder` and what boilerplate does it eliminate?**
A: `ConfigurableModuleBuilder` is a utility introduced in NestJS 9 that generates `forRoot`, `forRootAsync`, and the `MODULE_OPTIONS_TOKEN` provider automatically — eliminating the need to hand-write the async provider creation logic for every custom module.

```ts
// Before ConfigurableModuleBuilder — manual boilerplate (from Q6):
export class EmailModule {
  static forRoot(options: EmailModuleOptions): DynamicModule { /* 15 lines */ }
  static forRootAsync(asyncOptions: EmailModuleAsyncOptions): DynamicModule { /* 30 lines */ }
  private static createAsyncProviders(...): Provider[] { /* 20 lines */ }
}

// After ConfigurableModuleBuilder — generated automatically:
import { ConfigurableModuleBuilder } from '@nestjs/common';

export interface EmailModuleOptions {
  host:     string;
  port:     number;
  secure:   boolean;
  user:     string;
  password: string;
}

// This one call generates forRoot, forRootAsync, and the options token:
export const {
  ConfigurableModuleClass,   // ← base class your module extends
  MODULE_OPTIONS_TOKEN,      // ← injection token for the options object
  OPTIONS_TYPE,              // ← type of forRoot's argument
  ASYNC_OPTIONS_TYPE,        // ← type of forRootAsync's argument
} = new ConfigurableModuleBuilder<EmailModuleOptions>()
  .setClassMethodName('forRoot')       // generates forRoot + forRootAsync
  .setExtras(                          // add extra options beyond the core options
    { isGlobal: false },               // default value for extras
    (definition, extras) => ({
      ...definition,
      global: extras.isGlobal,         // map isGlobal extra to DynamicModule.global
    }),
  )
  .build();

// Module extends the generated base class:
@Module({
  providers: [EmailService],
  exports:   [EmailService],
})
export class EmailModule extends ConfigurableModuleClass {}
// ConfigurableModuleClass already has forRoot and forRootAsync methods!

// Service injects options via MODULE_OPTIONS_TOKEN:
@Injectable()
export class EmailService {
  private transporter: Transporter;

  constructor(
    @Inject(MODULE_OPTIONS_TOKEN)      // ← generated token
    private readonly options: EmailModuleOptions,
  ) {
    this.transporter = nodemailer.createTransport({
      host:   options.host,
      port:   options.port,
      secure: options.secure,
      auth:   { user: options.user, pass: options.password },
    });
  }
}

// Usage — generated forRoot and forRootAsync just work:
EmailModule.forRoot({
  host: 'smtp.sendgrid.net', port: 587, secure: false,
  user: 'apikey', password: process.env.SENDGRID_KEY,
  isGlobal: true,             // ← the extra we configured
})

EmailModule.forRootAsync({
  imports:    [ConfigModule],
  useFactory: (config: ConfigService) => ({
    host: config.get('SMTP_HOST'),
    port: config.get<number>('SMTP_PORT'),
    // ... all EmailModuleOptions fields
  }),
  inject:   [ConfigService],
  isGlobal: true,             // ← extras work in async too
})
```

### Section 6: Scenario / Interview-Style Questions

**Q11. "What is the `MODULE_OPTIONS_TOKEN` pattern and why use a Symbol token instead of injecting the options class directly?"**
A: The `MODULE_OPTIONS_TOKEN` is a unique injection token (typically a Symbol or string constant) used to provide and inject the configuration options object. Using a dedicated token instead of injecting the options class directly solves two problems:

```ts
// ❌ Problem with injecting the options object by class type:
export class DatabaseOptions {
  host: string; port: number;
}
// If DatabaseModule and CacheModule both have a 'DatabaseOptions' class →
// TypeScript type collision — injecting DatabaseOptions is ambiguous

// ✓ Unique symbol token — unambiguous injection:
export const DATABASE_OPTIONS = Symbol('DATABASE_OPTIONS');  // unique, never collides
export const CACHE_OPTIONS    = Symbol('CACHE_OPTIONS');

@Injectable()
export class DatabaseService {
  constructor(
    @Inject(DATABASE_OPTIONS) private opts: DatabaseModuleOptions,
    // No ambiguity — the symbol is the key, not the type name
  ) {}
}

// Why Symbol (not string):
// - Symbols are guaranteed unique — 'DATABASE_OPTIONS' string could clash across packages
// - Symbol('DATABASE_OPTIONS') === Symbol('DATABASE_OPTIONS') → false (always unique)
// - Prevents accidental overrides when multiple packages use the same string token name

// Pattern for token naming:
// In single-package use: constant name is sufficient
export const HTTP_CLIENT_OPTIONS = 'HTTP_CLIENT_OPTIONS';  // fine within one codebase

// In published packages: use Symbol + package prefix or UUID:
export const HTTP_CLIENT_OPTIONS = Symbol.for('mycompany:http-client:options');
// Symbol.for() = global registry — same string = same Symbol across iframes/workers
// Plain Symbol() = always new — two calls produce different Symbols
```

**Q12. "How do you share the same database module between multiple modules when each needs a different connection (multi-tenancy)?"**
A: This is the **named connection** pattern — `forRoot` can be called multiple times with a `name` option, and `forFeature` references the same name.

```ts
// AppModule — register multiple named connections:
@Module({
  imports: [
    TypeOrmModule.forRoot({
      name:     'primary',          // default connection name
      type:     'postgres',
      host:     'primary-db.internal',
      entities: [User, Order],
    }),
    TypeOrmModule.forRoot({
      name:     'analytics',        // second named connection
      type:     'postgres',
      host:     'analytics-db.internal',
      entities: [PageView, Event],
    }),
  ],
})
export class AppModule {}

// UsersModule — uses primary connection:
@Module({
  imports: [
    TypeOrmModule.forFeature([User, Order], 'primary'), // named: 'primary'
  ],
})
export class UsersModule {}

// AnalyticsModule — uses analytics connection:
@Module({
  imports: [
    TypeOrmModule.forFeature([PageView, Event], 'analytics'), // named: 'analytics'
  ],
})
export class AnalyticsModule {}

// Inject with named connection:
@Injectable()
export class AnalyticsService {
  constructor(
    @InjectRepository(PageView, 'analytics') // ← second arg = connection name
    private pageViewRepo: Repository<PageView>,
  ) {}
}

// Custom module with named instances — implementing the pattern yourself:
static forRoot(options: DatabaseOptions & { name?: string }): DynamicModule {
  const token = options.name
    ? `DATABASE_OPTIONS_${options.name}`
    : DATABASE_OPTIONS;

  return {
    module:    DatabaseModule,
    providers: [
      { provide: token, useValue: options },
      {
        provide:    options.name ? `DatabaseService_${options.name}` : DatabaseService,
        useFactory: (opts) => new DatabaseService(opts),
        inject:     [token],
      },
    ],
    exports: [options.name ? `DatabaseService_${options.name}` : DatabaseService],
  };
}
```

**Q13. "What is the difference between `register` / `registerAsync` and `forRoot` / `forRootAsync`?"**
A: Purely conventional naming, but the convention carries semantic meaning about intended usage:

```
forRoot / forRootAsync:
  → Module is intended to be configured ONCE at the application root
  → Usually paired with global: true
  → Calling it multiple times is unexpected/wrong (e.g., ConfigModule.forRoot)
  → Convention: "this is the root configuration that the whole app shares"
  → Examples: ConfigModule.forRoot, TypeOrmModule.forRoot, MongooseModule.forRoot

forFeature:
  → Module is called multiple times, once per feature module
  → Uses infrastructure established by forRoot
  → Convention: "register feature-specific resources against the shared infrastructure"
  → Examples: TypeOrmModule.forFeature, MongooseModule.forFeature, BullModule.registerQueue

register / registerAsync:
  → No single "root" configuration — each import is independent
  → Safe to call in any module without a prior forRoot call
  → Convention: "each usage is self-contained with its own options"
  → Examples: JwtModule.register, ClientsModule.register, PassportModule.register

// Usage mental model:
// forRoot  → "install the module globally once"
// forFeature → "plug specific things into the globally installed module"
// register → "install a self-contained copy of the module here"

// Nothing enforces this — just convention, but it's near-universal in the ecosystem
```

```ts
      host:   options.host,
      port:   options.port,
      secure: options.secure,
      auth:   options.auth,

      from:    this.options.from,
      to:      sendOptions.to,
      subject: sendOptions.subject,
      html,
    });
  }

  async verify(): Promise<boolean> {

      await this.transporter.verify();
      return true;
    } catch {
      return false;
    }
  }
```

```ts
  // ── forRoot: synchronous configuration ───────────────────────────────
  static forRoot(options: EmailModuleOptions): DynamicModule {
    return {
      module:    EmailModule,
      providers: [
        { provide: EMAIL_OPTIONS, useValue: options },
        EmailService,
      ],
      exports: [EmailService],
    };

  static forRootAsync(asyncOptions: EmailAsyncOptions): DynamicModule {
    return {
      module:    EmailModule,
      imports:   asyncOptions.imports ?? [],
      providers: [
        ...EmailModule.buildAsyncProviders(asyncOptions),
        EmailService,
      ],
      exports: [EmailService],
    };
  }

  // ── forFeature: per-module template directory ────────────────────────
  static forFeature(featureOptions: EmailFeatureOptions): DynamicModule {
    return {
      module:    EmailModule,
      providers: [
        // Override feature options for this module's scope:
        { provide: EMAIL_FEATURE_TOKEN, useValue: featureOptions },
        // EmailService with BOTH global options AND feature options:
        // Note: EMAIL_OPTIONS must already be available (via forRoot in parent)
        EmailService,
      ],
      exports: [EmailService],
      // This EmailService is DIFFERENT from the global one —
      // it has featureOptions injected (different template dir)
    };
  }

  // ── Private: translate async options → provider array ────────────────
  private static buildAsyncProviders(
    asyncOptions: EmailAsyncOptions,
  ): Provider[] {
    if (asyncOptions.useFactory) {
      return [{
        provide:    EMAIL_OPTIONS,
        useFactory: asyncOptions.useFactory,
        inject:     asyncOptions.inject ?? [],
      }];
    }
    if (asyncOptions.useClass) {
      return [
        { provide: asyncOptions.useClass, useClass: asyncOptions.useClass },
        {
          provide:    EMAIL_OPTIONS,
          useFactory: (factory: EmailOptionsFactory) => factory.createEmailOptions(),
          inject:     [asyncOptions.useClass],
        },
      ];
    }
    if (asyncOptions.useExisting) {
      return [{
        provide:    EMAIL_OPTIONS,
        useFactory: (factory: EmailOptionsFactory) => factory.createEmailOptions(),
        inject:     [asyncOptions.useExisting],
      }];
    }
    throw new Error('EmailModule: must provide useFactory, useClass, or useExisting');
  }
}
```

## Problem 2 — `forRootAsync` with Multiple Config Sources (ConfigService + Secret Manager)

### Problem
A `PaymentsModule` needs credentials from two places: non-sensitive config from `ConfigService` and sensitive keys from AWS Secrets Manager. The `forRootAsync` factory must combine both asynchronously before the module initializes.

```ts
// ❌ Can't do this with forRoot — credentials not available synchronously:
PaymentsModule.forRoot({
  apiKey:     process.env.STRIPE_KEY,       // potentially undefined at parse time
  webhookSecret: '???',                     // must come from AWS — can't be env var
})
```

### Solution: `forRootAsync` with Multiple Injected Services

```ts
// secrets/secrets.service.ts
@Injectable()
export class SecretsService {
  private readonly client: SecretsManagerClient;
  private readonly cache = new Map<string, string>();

  constructor() {
    this.client = new SecretsManagerClient({ region: 'us-east-1' });
  }

  async getSecret(secretName: string): Promise<Record<string, string>> {
    if (this.cache.has(secretName)) {
      return JSON.parse(this.cache.get(secretName)!);
    }
    const response = await this.client.send(
      new GetSecretValueCommand({ SecretId: secretName }),
    );
    this.cache.set(secretName, response.SecretString!);
    return JSON.parse(response.SecretString!);
  }
}

// payments/payments.module.ts
export interface PaymentsModuleOptions {
  apiKey:        string;
  webhookSecret: string;
  currency:      string;
  testMode:      boolean;
}

@Module({})
export class PaymentsModule {
  static forRootAsync(asyncOptions: PaymentsAsyncOptions): DynamicModule {
    return {
      module:  PaymentsModule,
      global:  true,
      imports: asyncOptions.imports ?? [],
      providers: [
        {
          provide:    PAYMENTS_OPTIONS,
          useFactory: asyncOptions.useFactory,
          inject:     asyncOptions.inject ?? [],
        },
        StripeService,
        WebhookService,
      ],
      exports: [StripeService, WebhookService],
    };
  }
}

// app.module.ts — factory injecting BOTH ConfigService AND SecretsService:
@Module({
  imports: [
    SecretsModule,      // provides SecretsService
    ConfigModule.forRoot({ isGlobal: true }),

    PaymentsModule.forRootAsync({
      imports:  [SecretsModule],         // import SecretsModule so its providers are available
      inject:   [ConfigService, SecretsService],  // inject both

      useFactory: async (
        config:  ConfigService,          // synchronous config (env vars)
        secrets: SecretsService,         // async secrets (AWS)
      ): Promise<PaymentsModuleOptions> => {
        // Fetch sensitive keys asynchronously:
        const stripeSecrets = await secrets.getSecret('payments/stripe/production');
        // stripeSecrets = { apiKey: 'sk_live_...', webhookSecret: 'whsec_...' }

        return {
          apiKey:        stripeSecrets.apiKey,
          webhookSecret: stripeSecrets.webhookSecret,
          currency:      config.get('PAYMENTS_CURRENCY', 'usd'),
          testMode:      config.get<boolean>('PAYMENTS_TEST_MODE', false),
          // Combining: non-sensitive from env, sensitive from AWS
        };
      },
    }),
  ],
})
export class AppModule {}
```

### How NestJS Handles the Async Factory

```
Bootstrap sequence with forRootAsync:

1. NestJS parses module graph (synchronous):
   AppModule → PaymentsModule (dynamic)
   PaymentsModule depends on: SecretsModule, ConfigModule

2. NestJS resolves module graph order:
   ConfigModule → SecretsModule → PaymentsModule

3. NestJS instantiates providers in order:
   ConfigService (ConfigModule) — synchronous, immediate
   SecretsService (SecretsModule) — synchronous constructor (no await in ctor)

4. NestJS creates PAYMENTS_OPTIONS provider:
   Calls: useFactory(configService, secretsService)
   → async function runs: await secrets.getSecret('payments/stripe/...')
   → returns { apiKey, webhookSecret, currency, testMode }
   NestJS awaits the factory's Promise before continuing
   StripeService cannot be created until PAYMENTS_OPTIONS resolves

5. StripeService created with resolved options
6. App starts listening

Total: app.listen() is called AFTER all async factories resolve
→ No race condition — NestJS's DI awaits each async provider
```

## Problem 3 — Implementing `forFeature` for a Multi-Database Module

### Problem
Build a `DatabaseModule` supporting multiple named connections. Each feature module calls `forFeature` with the connection name and the entity classes it needs, receiving repository providers scoped to that module.


### Implementation

```ts
// database/database.constants.ts
export const getConnectionToken  = (name: string) => `DB_CONNECTION_${name.toUpperCase()}`;
export const getRepositoryToken  = (entity: Function, connName: string) =>
  `${connName.toUpperCase()}_REPOSITORY_${entity.name}`;
export const getOptionsToken     = (name: string) => `DB_OPTIONS_${name.toUpperCase()}`;

// database/interfaces.ts
export interface DatabaseModuleOptions {
  name:        string;
  url:         string;
  entities?:   Function[];
  synchronize?: boolean;
  logging?:    boolean;
}
export interface DatabaseAsyncOptions {
  name:        string;        // connection name required for async too
  imports?:    any[];
  useFactory?: (...args: any[]) => DatabaseModuleOptions | Promise<DatabaseModuleOptions>;
  inject?:     any[];
}

// database/database.module.ts
@Module({})
export class DatabaseModule {

  // ── forRoot: create and register a named connection ─────────────────
  static forRoot(options: DatabaseModuleOptions): DynamicModule;
  static forRoot(asyncOptions: DatabaseAsyncOptions): DynamicModule;
  static forRoot(
    options: DatabaseModuleOptions | DatabaseAsyncOptions,
  ): DynamicModule {
    // Determine if sync or async by checking for useFactory:
    if ('useFactory' in options || 'useExisting' in options) {
      return DatabaseModule.forRootAsync(options as DatabaseAsyncOptions);
    }
    return DatabaseModule.forRootSync(options as DatabaseModuleOptions);
  }

  private static forRootSync(options: DatabaseModuleOptions): DynamicModule {
    const optionsToken    = getOptionsToken(options.name);
    const connectionToken = getConnectionToken(options.name);

    return {
      module:  DatabaseModule,
      global:  true,          // connection available app-wide
      providers: [
        { provide: optionsToken,    useValue: options },
        {
          provide:    connectionToken,
          useFactory: async (opts: DatabaseModuleOptions) => {
            const ds = new DataSource({
              type:        'postgres',
              url:          opts.url,
              entities:     opts.entities ?? [],
              synchronize:  opts.synchronize ?? false,
              logging:      opts.logging ?? false,
            });
            await ds.initialize();
            return ds;
          },
          inject: [optionsToken],
        },
      ],
      exports: [connectionToken],
    };
  }

  private static forRootAsync(asyncOptions: DatabaseAsyncOptions): DynamicModule {
    const optionsToken    = getOptionsToken(asyncOptions.name);
    const connectionToken = getConnectionToken(asyncOptions.name);

    return {
      module:  DatabaseModule,
      global:  true,
      imports: asyncOptions.imports ?? [],
      providers: [
        {
          provide:    optionsToken,
          useFactory: asyncOptions.useFactory!,
          inject:     asyncOptions.inject ?? [],
        },
        {
          provide:    connectionToken,
          useFactory: async (opts: DatabaseModuleOptions) => {
            const ds = new DataSource({ type: 'postgres', url: opts.url, entities: opts.entities });
            await ds.initialize();
            return ds;
          },
          inject: [optionsToken],
        },
      ],
      exports: [connectionToken],
    };
  }

  // ── forFeature: register entity repositories for a named connection ──
  static forFeature(connectionName: string, entities: Function[]): DynamicModule {
    const connectionToken = getConnectionToken(connectionName);

    const repositoryProviders: Provider[] = entities.map(entity => ({
      provide:    getRepositoryToken(entity, connectionName),
      useFactory: (dataSource: DataSource) => dataSource.getRepository(entity),
      inject:     [connectionToken],
      // connectionToken is globally available (from forRoot with global:true)
    }));

    return {
      module:    DatabaseModule,
      providers: repositoryProviders,
      exports:   repositoryProviders,
      // Note: providers are NOT global — scoped to the importing feature module
    };
  }
}

// ── Injection decorator helpers ────────────────────────────────────────
export const InjectRepository = (entity: Function, connectionName = 'primary') =>
  Inject(getRepositoryToken(entity, connectionName));

export const InjectConnection = (name = 'primary') =>
  Inject(getConnectionToken(name));
```

## Problem 4 — Using `ConfigurableModuleBuilder` with Extras and `forFeature`

### Problem
Build a `CacheModule` using `ConfigurableModuleBuilder` (NestJS 9+) that generates `forRoot`/`forRootAsync` automatically, adds an `isGlobal` extra, and implements a hand-written `forFeature` for per-namespace cache prefixes.

### Implementation

```ts
// cache/cache.service.ts
export const CACHE_FEATURE_OPTIONS = Symbol('CACHE_FEATURE_OPTIONS');

@Injectable()
export class CacheService {
  private client: Redis;

  constructor(
    @Inject(CACHE_MODULE_OPTIONS)
    private readonly options: CacheModuleOptions,

    @Optional()
    @Inject(CACHE_FEATURE_OPTIONS)
    private readonly featureOptions?: CacheFeatureOptions,
  ) {
    this.client = new Redis({
      host:     options.host,
      port:     options.port,
      password: options.password,
      db:       options.db ?? 0,
      keyPrefix: options.keyPrefix ?? '',
    });
  }

  private buildKey(key: string): string {
    const prefix = this.featureOptions?.namespace
      ? `${this.featureOptions.namespace}:`
      : '';
    return `${prefix}${key}`;
  }

  private getDefaultTtl(): number {
    return this.featureOptions?.ttl ?? 3600;
  }

  async get<T>(key: string): Promise<T | null> {
    const value = await this.client.get(this.buildKey(key));
    return value ? JSON.parse(value) : null;
  }

  async set<T>(key: string, value: T, ttl?: number): Promise<void> {
    await this.client.setex(
      this.buildKey(key),
      ttl ?? this.getDefaultTtl(),
      JSON.stringify(value),
    );
  }

  async del(key: string): Promise<void> {
    await this.client.del(this.buildKey(key));
  }

  async flush(pattern?: string): Promise<void> {
    const prefix = this.featureOptions?.namespace
      ? `${this.featureOptions.namespace}:*`
      : '*';
    const keys = await this.client.keys(pattern ?? prefix);
    if (keys.length) await this.client.del(...keys);
  }
}

// cache/cache.module.ts
@Module({
  providers: [CacheService],
  exports:   [CacheService],
})
export class CacheModule extends CacheConfigurableModuleClass {
  // forRoot and forRootAsync are inherited from CacheConfigurableModuleClass
  // Only need to add forFeature manually:

  static forFeature(featureOptions: CacheFeatureOptions): DynamicModule {
    return {
      module:    CacheModule,
      providers: [
        { provide: CACHE_FEATURE_OPTIONS, useValue: featureOptions },
        CacheService,               // feature-scoped instance with namespace injected
        // CACHE_MODULE_OPTIONS must be available (from forRoot — global: true)
      ],
      exports: [CacheService],
    };
  }
}
```

```ts
// ❌ Common testing mistakes:
```

### Solution: Test at Three Levels

```ts
describe('EmailService (unit)', () => {
```

## Quick Reference — Dynamic Modules Cheat Sheet

```
STATIC vs DYNAMIC:
  Static module:  @Module({ providers, imports, exports }) — fixed, no runtime config
  Dynamic module: static forRoot(...): DynamicModule — config passed at import time
  DynamicModule interface = ModuleMetadata + required `module` field + optional `global`

NAMING CONVENTIONS:
  forRoot / forRootAsync   → configure once in AppModule; usually global; shared app-wide
  forFeature               → per-feature, multiple times; uses forRoot infrastructure
  register / registerAsync → self-contained; safe to call multiple times independently
  (Nothing enforces these names — they are ecosystem conventions)

forRoot PATTERN:
  static forRoot(options: ModuleOptions): DynamicModule {
    return {
      module:    TheModule,           // required — the class itself
      global:    true,               // optional — available without importing
      providers: [
        { provide: MODULE_OPTIONS_TOKEN, useValue: options },
        TheService,
      ],
      exports:   [TheService],
    };
  }

forRootAsync PATTERN:
  static forRootAsync(asyncOpts: AsyncOptions): DynamicModule {
    return {
      module:    TheModule,
      imports:   asyncOpts.imports ?? [],    // import ConfigModule etc.
      providers: [
        ...TheModule.buildProviders(asyncOpts),
        TheService,
      ],
      exports:   [TheService],
    };
  }
  private static buildProviders(opts): Provider[] {
    if (opts.useFactory)  return [{ provide: TOKEN, useFactory: opts.useFactory, inject: opts.inject }]
    if (opts.useClass)    return [{ provide: opts.useClass, useClass: opts.useClass },
                                  { provide: TOKEN, useFactory: f => f.create(), inject: [opts.useClass] }]
    if (opts.useExisting) return [{ provide: TOKEN, useFactory: f => f.create(), inject: [opts.useExisting] }]
  }

forFeature PATTERN:
  static forFeature(entities: Type[], connectionName = 'default'): DynamicModule {
    const providers = entities.map(e => ({
      provide:    getToken(e, connectionName),
      useFactory: (conn) => conn.getRepository(e),
      inject:     [getConnectionToken(connectionName)],
    }));
    return { module: TheModule, providers, exports: providers };
    // forFeature providers are NOT global — scoped to the importing module
  }

ConfigurableModuleBuilder (NestJS 9+):
  const { ConfigurableModuleClass, MODULE_OPTIONS_TOKEN, OPTIONS_TYPE, ASYNC_OPTIONS_TYPE }
    = new ConfigurableModuleBuilder<OptionsType>()
        .setClassMethodName('forRoot')          // generates forRoot + forRootAsync
        .setExtras({ isGlobal: false }, (def, extras) => ({ ...def, global: extras.isGlobal }))
        .build();
  export class MyModule extends ConfigurableModuleClass { }
  // forRoot and forRootAsync are inherited — only add forFeature manually

INJECTION TOKENS:
  Symbol('TOKEN_NAME')   → unique within process — recommended for published packages
  'TOKEN_STRING'         → string tokens — risk of name collision across packages
  Symbol.for('pkg:name') → global registry — same across iframes/workers, unique per string
  @Inject(TOKEN) in provider → inject the value at that token

GLOBAL MODULES:
  global: true on DynamicModule — exports available without explicit import
  @Global() class decorator    — same effect as global: true
  Use for: ConfigModule, LoggerModule, cross-cutting infrastructure
  Avoid for: domain modules — keeps dependencies explicit and testable

MULTIPLE INSTANCES (named):
  Use a name string to differentiate: forRoot({ name: 'analytics', ... })
  Token factory: getConnectionToken(name) → `DB_CONNECTION_${name}`
  forFeature references by name: forFeature('analytics', [Entity])
  @InjectRepository(Entity, 'analytics') — named connection in decorator

TESTING DYNAMIC MODULES:
  Unit test:       provide TOKEN directly — skip forRoot entirely
  forRoot test:    Test.createTestingModule({ imports: [Module.forRoot(opts)] })
  forRootAsync:    provide mock services as test providers; use inject token directly
  forFeature test: import both forRoot + forFeature in the test module
  Avoid:           real async operations (DB, network) in unit tests — mock the service

COMMON BUGS:
  Missing `module` field in DynamicModule return → "Module has no module property" error
  forRootAsync missing `imports: [ConfigModule]` → ConfigService undefined in factory
  useClass without registering the class as provider → DI cannot resolve the factory class
  global: true omitted → other modules must import the module explicitly each time
  forFeature using global providers not yet initialized → depends on forRoot being imported first
  Testing: injecting by class type when token is a Symbol → provider not found
  ConfigurableModuleBuilder: forgetting to extend the generated class → forRoot not inherited
```

---

**Final Tip:** At the 5 YOE level, dynamic module questions test whether you can reason about **NestJS's module graph resolution and DI lifetime** — not just know the API. The highest-signal answer on `forRootAsync`: "The factory function runs *after* NestJS resolves all declared `inject` dependencies from the `imports` modules. By the time your `useFactory` fires, `ConfigService` is fully initialized — that's why `forRootAsync` can read environment variables through `ConfigService` even though the module decorator was evaluated at parse time. NestJS `await`s the factory Promise before creating any provider that depends on its result, so async initialization is always complete before the service is constructed." For `forFeature`: "The key insight is that `forRoot` establishes a shared infrastructure provider — a DataSource, Redis client, message broker connection — registered globally. `forFeature` creates feature-specific providers that *wrap* that infrastructure: they inject the global DataSource and produce a `Repository<User>` scoped only to `UsersModule`. The feature module gets its own DI scope — `OrdersModule` can't accidentally inject `UserRepository` because that provider only exists in `UsersModule`'s scope." For `ConfigurableModuleBuilder`: "It eliminates the biggest source of boilerplate in custom dynamic modules — the `buildAsyncProviders` private method with its `useFactory` / `useClass` / `useExisting` branching logic. The builder generates that entire infrastructure; you extend the generated class and only hand-write the parts that are actually unique to your module, like `forFeature`."
