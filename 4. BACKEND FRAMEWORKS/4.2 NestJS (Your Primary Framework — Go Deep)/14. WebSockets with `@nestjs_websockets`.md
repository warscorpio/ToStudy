# NestJS WebSockets with `@nestjs/websockets` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a NestJS WebSocket gateway — how does it differ from an HTTP controller?**

A: A gateway is NestJS's abstraction over a persistent, bidirectional connection. Where a controller handles one request and sends one response, a gateway manages a stateful socket that can send and receive messages at any time from either side:

```
HTTP Controller (stateless, request-response):

  Client ──── POST /messages ────────────────► Controller
  Client ◄─── 201 { id: 1, text: 'hi' } ────── Controller
  (connection closed)

WebSocket Gateway (stateful, bidirectional):

  Client ──── WS handshake ──────────────────► Gateway
  Client ──── sendMessage { text: 'hi' } ────► Gateway
  Client ◄─── newMessage { id: 1 } ─────────── Gateway  (response to sender)
  Client ◄─── userJoined { userId: 2 } ──────── Gateway  (pushed by server, unprompted)
  Client ──── typing {} ──────────────────────► Gateway
  Client ◄─── broadcast to all room members ─── Gateway
  (connection stays open until explicitly closed)
```

The gateway class:

```typescript
import {
    WebSocketGateway,
    WebSocketServer,
    SubscribeMessage,
    MessageBody,
    ConnectedSocket,
    OnGatewayInit,
    OnGatewayConnection,
    OnGatewayDisconnect,
} from '@nestjs/websockets';
import { Server, Socket } from 'socket.io';

// @WebSocketGateway — marks this class as a WebSocket gateway.
// NestJS creates a socket.io (or ws) server and manages all connections.
@WebSocketGateway({
    namespace: '/chat',   // socket.io namespace (optional, default is '/')
    cors: {
        origin: 'http://localhost:3001',
        credentials: true,
    },
    // Any socket.io ServerOptions can be passed here:
    pingInterval: 10000,
    pingTimeout:  5000,
    transports: ['websocket', 'polling'],
})
export class ChatGateway
    implements OnGatewayInit, OnGatewayConnection, OnGatewayDisconnect
{
    // @WebSocketServer — injects the underlying socket.io Server instance.
    // Use it to broadcast to multiple clients, manage rooms, emit server-initiated events.
    @WebSocketServer()
    server: Server;

    // ── Lifecycle hooks ────────────────────────────────────────────────────────

    // Called once when the gateway is initialised (WebSocket server is ready).
    afterInit(server: Server) {
        console.log('Gateway initialised:', server);
    }

    // Called when ANY client connects.
    handleConnection(client: Socket, ...args: any[]) {
        console.log(`Client connected: ${client.id}`);
        console.log('Handshake query:', client.handshake.query);
        // client.id — unique socket ID assigned by socket.io
        // client.handshake — headers, query params, auth token for initial negotiation
    }

    // Called when ANY client disconnects (intentional or network drop).
    handleDisconnect(client: Socket) {
        console.log(`Client disconnected: ${client.id} — reason: ${client.disconnected}`);
        // Clean up: remove from rooms map, update presence, notify others.
    }

    // ── Message handlers ───────────────────────────────────────────────────────

    // @SubscribeMessage — registers a handler for a named event from the client.
    // Equivalent of @Get()/@Post() for WebSockets.
    @SubscribeMessage('sendMessage')
    handleSendMessage(
        @MessageBody() data: { text: string; roomId: string },
        @ConnectedSocket() client: Socket,
    ) {
        // Return value is sent back ONLY to the sender as the event acknowledgement.
        // This is the one-to-one "response" pattern.
        return { event: 'messageSent', data: { id: Date.now(), ...data } };
    }
}
```

**Q2. How does NestJS support multiple WebSocket adapters — what is the difference between `socket.io` and `ws`?**

A: NestJS is transport-agnostic via the `WebSocketAdapter` interface. The two built-in adapters are `IoAdapter` (socket.io) and `WsAdapter` (raw ws). They have significant behavioural differences:

```typescript
// ── Adapter registration ───────────────────────────────────────────────────────
import { NestFactory }  from '@nestjs/core';
import { IoAdapter }    from '@nestjs/platform-socket.io';  // socket.io
import { WsAdapter }    from '@nestjs/platform-ws';         // raw ws

async function bootstrap() {
    const app = await NestFactory.create(AppModule);

    // Option A: socket.io (default — richer feature set)
    app.useWebSocketAdapter(new IoAdapter(app));

    // Option B: raw ws (lighter, no socket.io overhead)
    app.useWebSocketAdapter(new WsAdapter(app));

    await app.listen(3000);
}

// ── Feature comparison ─────────────────────────────────────────────────────────
//
// Feature                    socket.io (IoAdapter)    raw ws (WsAdapter)
// ─────────────────────────────────────────────────────────────────────────────
// Rooms / namespaces         ✓ Built-in               ✗ Manual implementation
// Automatic reconnection     ✓ Built-in               ✗ Client-side only
// Fallback to polling        ✓ (long-polling fallback) ✗ WebSocket only
// Acknowledgements           ✓ Callback-based ACK      ✗ Manual
// Broadcasting               ✓ server.emit() / to()    ✗ Iterate connected clients
// Binary data                ✓                         ✓ Native
// Browser support            ✓ Excellent               ✓ Modern browsers only
// Overhead                   Higher (Socket.IO proto)  Lower (pure WebSocket)
// Scaling (Redis adapter)    ✓ @socket.io/redis-adapter ✗ Manual
//
// Rule of thumb:
// Use socket.io if you need rooms, namespaces, fallback transport, or Redis scaling.
// Use ws if you control both client and server, need low latency, or use non-browser clients.

// ── Custom adapter (e.g., extending IoAdapter for Redis) ─────────────────────
import { IoAdapter }          from '@nestjs/platform-socket.io';
import { createAdapter }      from '@socket.io/redis-adapter';
import { createClient }       from 'redis';
import { ServerOptions }      from 'socket.io';

export class RedisIoAdapter extends IoAdapter {
    private adapterConstructor: ReturnType<typeof createAdapter>;

    async connectToRedis(): Promise<void> {
        const pubClient = createClient({ url: process.env.REDIS_URL });
        const subClient = pubClient.duplicate();
        await Promise.all([pubClient.connect(), subClient.connect()]);
        this.adapterConstructor = createAdapter(pubClient, subClient);
    }

    createIOServer(port: number, options?: ServerOptions): any {
        const server = super.createIOServer(port, options);
        server.adapter(this.adapterConstructor);
        return server;
    }
}

// Registration:
const redisAdapter = new RedisIoAdapter(app);
await redisAdapter.connectToRedis();
app.useWebSocketAdapter(redisAdapter);
```

## Section 2: Gateways

**Q3. How do you structure a gateway module — what belongs in the gateway vs the service?**

A: A gateway should be thin — it handles the WebSocket protocol concerns (event routing, client identity, broadcasting) while delegating business logic to services. This mirrors how controllers relate to services in HTTP:

```typescript
// ── Module structure ──────────────────────────────────────────────────────────
// src/chat/
//   chat.module.ts
//   chat.gateway.ts    ← WebSocket protocol layer (like a controller)
//   chat.service.ts    ← Business logic (message persistence, room management)
//   chat.repository.ts ← Data access
//   dto/
//     send-message.dto.ts
//     join-room.dto.ts

// chat.module.ts
@Module({
    imports:   [TypeOrmModule.forFeature([Message, Room])],
    providers: [ChatGateway, ChatService, ChatRepository],
    // Note: Gateways are providers — they go in the providers array, not controllers.
})
export class ChatModule {}

// chat.gateway.ts — protocol layer only
@WebSocketGateway({ namespace: '/chat', cors: { origin: '*' } })
export class ChatGateway implements OnGatewayConnection, OnGatewayDisconnect {
    @WebSocketServer() server: Server;

    constructor(private readonly chatService: ChatService) {}

    async handleConnection(client: Socket) {
        // Protocol concern: authenticate the socket connection
        const token = client.handshake.auth?.token
                   ?? client.handshake.headers?.authorization?.replace('Bearer ', '');

        if (!token) {
            client.disconnect(true); // Reject unauthenticated connections immediately
            return;
        }

        try {
            const user = await this.chatService.validateToken(token);
            client.data.user = user; // Attach user to socket for later handlers
            await this.chatService.setUserOnline(user.id, client.id);
            // Notify other clients that this user came online:
            client.broadcast.emit('userOnline', { userId: user.id });
        } catch {
            client.disconnect(true);
        }
    }

    async handleDisconnect(client: Socket) {
        const user = client.data.user;
        if (!user) return;
        await this.chatService.setUserOffline(user.id);
        client.broadcast.emit('userOffline', { userId: user.id });
    }

    @SubscribeMessage('joinRoom')
    async handleJoinRoom(
        @MessageBody() data: JoinRoomDto,
        @ConnectedSocket() client: Socket,
    ) {
        // Protocol concern: join the socket.io room
        await client.join(data.roomId);
        // Business logic: delegate to service
        const room = await this.chatService.joinRoom(client.data.user.id, data.roomId);
        // Notify room members via server
        this.server.to(data.roomId).emit('userJoinedRoom', {
            userId: client.data.user.id,
            roomId: data.roomId,
        });
        return { event: 'joinedRoom', data: room };
    }

    @SubscribeMessage('sendMessage')
    async handleMessage(
        @MessageBody() dto: SendMessageDto,
        @ConnectedSocket() client: Socket,
    ) {
        // Business logic: delegate completely to service
        const message = await this.chatService.saveMessage({
            text:   dto.text,
            roomId: dto.roomId,
            userId: client.data.user.id,
        });
        // Protocol concern: broadcast to the room
        this.server.to(dto.roomId).emit('newMessage', message);
        return { event: 'messageSent', data: { id: message.id } };
    }
}

// chat.service.ts — pure business logic, no WebSocket dependencies
@Injectable()
export class ChatService {
    constructor(
        @InjectRepository(Message) private readonly messageRepo: Repository<Message>,
        private readonly jwtService: JwtService,
        private readonly redis: RedisService,
    ) {}

    validateToken(token: string): Promise<User> {
        return this.jwtService.verifyAsync(token);
    }

    async setUserOnline(userId: string, socketId: string): Promise<void> {
        await this.redis.set(`user:online:${userId}`, socketId, 'EX', 3600);
    }

    async saveMessage(data: { text: string; roomId: string; userId: string }): Promise<Message> {
        const message = this.messageRepo.create(data);
        return this.messageRepo.save(message);
    }

    // No reference to Socket, Server, or any WebSocket type — pure domain logic.
}
```

**Q4. What are the return value patterns for `@SubscribeMessage` handlers — how do you send data back to clients?**

A: There are four distinct patterns for sending data from a gateway. Each has a different audience (sender only vs room vs all) and a different trigger (request-response vs server push):

```typescript
@WebSocketGateway({ namespace: '/chat' })
export class ChatGateway {
    @WebSocketServer() server: Server;

    // ── Pattern 1: Return value — sends ACK to the sender only ────────────────
    // The return value of a @SubscribeMessage handler is sent back as the
    // socket.io acknowledgement callback to the single client who sent the event.
    // Client-side: socket.emit('ping', {}, (ack) => console.log(ack))
    @SubscribeMessage('ping')
    handlePing(@MessageBody() data: any): WsResponse<string> {
        // WsResponse<T> = { event: string; data: T }
        // Sends: { event: 'pong', data: 'pong!' } to the sender only
        return { event: 'pong', data: 'pong!' };

        // Alternatively, return a plain value:
        // return 'pong!'; — sends the string as the ACK data
    }

    // ── Pattern 2: client.emit() — push to one specific connected socket ───────
    // Use @ConnectedSocket() to get the specific socket, then emit directly.
    @SubscribeMessage('getProfile')
    async handleGetProfile(@ConnectedSocket() client: Socket): Promise<void> {
        const user    = client.data.user; // Attached during handleConnection
        const profile = await this.userService.getProfile(user.id);
        // Emit directly to this client:
        client.emit('profileData', profile);
        // Return nothing — no ACK
    }

    // ── Pattern 3: server.to(room).emit() — broadcast to a room ──────────────
    // Sends to ALL sockets in a socket.io room, INCLUDING the sender.
    @SubscribeMessage('sendMessage')
    async handleSendMessage(
        @MessageBody() dto: { roomId: string; text: string },
        @ConnectedSocket() client: Socket,
    ): Promise<void> {
        const message = await this.messageService.save(dto);
        // server.to() targets a room by name:
        this.server.to(dto.roomId).emit('newMessage', message);
        // ALL clients in the room receive 'newMessage', including the sender.
    }

    // ── Pattern 4: client.broadcast.to(room).emit() — broadcast, exclude sender ──
    // Sends to all sockets in a room EXCEPT the sender.
    @SubscribeMessage('typing')
    handleTyping(
        @MessageBody() data: { roomId: string },
        @ConnectedSocket() client: Socket,
    ): void {
        // client.broadcast.to() targets the room but skips the sender:
        client.broadcast.to(data.roomId).emit('userTyping', {
            userId: client.data.user.id,
        });
        // Useful for typing indicators — don't tell yourself you're typing.
    }

    // ── Pattern 5: Observable return — stream multiple values ─────────────────
    // @SubscribeMessage handlers can return an Observable.
    // Each emitted value is sent as a separate event to the client.
    @SubscribeMessage('subscribe')
    handleSubscribe(@MessageBody() data: { topic: string }): Observable<WsResponse<any>> {
        return interval(1000).pipe(
            take(10),
            map((i) => ({
                event: 'update',
                data: { topic: data.topic, value: i, timestamp: Date.now() },
            })),
        );
        // Client receives 10 'update' events, one per second, then stream ends.
    }

    // ── Server-initiated push (outside a @SubscribeMessage handler) ────────────
    // Services can inject the gateway and call server.emit() directly.
    // Or use a shared event emitter. See Q10 for the pattern.
    pushNotification(userId: string, notification: Notification): void {
        const socketId = this.connectedUsers.get(userId);
        if (socketId) {
            this.server.to(socketId).emit('notification', notification);
        }
    }
}

// ── Summary table ─────────────────────────────────────────────────────────────
// Pattern                           | Who receives it?              | When to use
// ──────────────────────────────────|──────────────────────────────|────────────────────────────
// return { event, data }            | Sender (ACK)                  | Request-response (one client)
// client.emit(event, data)          | Sender only                   | Push data to specific socket
// server.to(room).emit(event, data) | All in room (incl. sender)    | Broadcast to a group
// client.broadcast.to(room).emit()  | All in room (excl. sender)    | Notify others (e.g. typing)
// server.emit(event, data)          | ALL connected clients         | Global announcements
// return Observable<WsResponse>     | Sender (stream of ACKs)       | Real-time streaming to one client
```

**Q5. How do `@MessageBody()`, `@ConnectedSocket()`, and other parameter decorators work?**

A: Gateway method parameters use decorators instead of type inference, just as HTTP controllers use `@Body()`, `@Param()`, etc.:

```typescript
import {
    SubscribeMessage,
    MessageBody,
    ConnectedSocket,
    WsResponse,
} from '@nestjs/websockets';
import { Socket } from 'socket.io';
import { UseGuards, UsePipes, ValidationPipe } from '@nestjs/common';

@WebSocketGateway()
export class EventsGateway {
    // ── @MessageBody() ────────────────────────────────────────────────────────
    // Extracts the message payload (the data argument of socket.emit on client).
    // Client: socket.emit('sendMessage', { text: 'hello', roomId: 'room-1' })
    @SubscribeMessage('sendMessage')
    handleMessage(
        @MessageBody() data: { text: string; roomId: string },
    ): WsResponse<string> {
        console.log(data.text, data.roomId);
        return { event: 'ack', data: 'received' };
    }

    // ── @MessageBody() with a specific key ────────────────────────────────────
    // If the client sends an object, extract just one property:
    // Client: socket.emit('sendMessage', { text: 'hello', roomId: 'room-1' })
    @SubscribeMessage('sendMessage')
    handleText(@MessageBody('text') text: string): void {
        console.log(text); // 'hello'
    }

    // ── @MessageBody() with ValidationPipe ────────────────────────────────────
    // Validate the payload before the handler runs.
    // The pipe works identically to HTTP pipes — throws WsException on failure.
    @SubscribeMessage('createRoom')
    @UsePipes(new ValidationPipe({ whitelist: true, transform: true }))
    handleCreateRoom(
        @MessageBody() dto: CreateRoomDto,
    ): Observable<WsResponse<Room>> {
        // dto is a validated, class-transformed CreateRoomDto instance
        return from(this.roomService.create(dto)).pipe(
            map(room => ({ event: 'roomCreated', data: room })),
        );
    }

    // ── @ConnectedSocket() ────────────────────────────────────────────────────
    // Injects the specific Socket instance for the connected client.
    // Use it to: read socket.id, join/leave rooms, read socket.data, emit directly.
    @SubscribeMessage('joinRoom')
    handleJoinRoom(
        @MessageBody() data: { roomId: string },
        @ConnectedSocket() client: Socket,
    ): void {
        console.log('Client socket ID:', client.id);
        console.log('User attached to socket:', client.data.user);
        console.log('Current rooms:', client.rooms); // Set of room names this socket is in
        client.join(data.roomId);
    }

    // ── Combining decorators ───────────────────────────────────────────────────
    // You can have any combination of @MessageBody, @ConnectedSocket in a handler.
    @SubscribeMessage('leaveRoom')
    async handleLeaveRoom(
        @MessageBody('roomId') roomId: string,
        @ConnectedSocket() client: Socket,
    ): Promise<void> {
        await client.leave(roomId);
        this.server.to(roomId).emit('userLeft', {
            userId: client.data.user?.id,
            roomId,
        });
    }

    // ── Accessing raw socket.io event data ────────────────────────────────────
    // If you need the full socket.io message object (not just the data payload):
    @SubscribeMessage('rawEvent')
    handleRaw(
        @MessageBody() data: any,
        @ConnectedSocket() client: Socket,
    ): void {
        // For socket.io, the client sends: socket.emit('rawEvent', payload, callback)
        // data = payload
        // If you need the acknowledgement callback, inject @ConnectedSocket()
        // and use the socket.io low-level API — NestJS does not expose the callback directly.
    }
}
```

## Section 3: Rooms and Namespaces

**Q6. How do rooms and namespaces differ — when do you use each?**

A: Rooms and namespaces are both grouping mechanisms in socket.io, but they operate at different levels and solve different problems:

```typescript
// ── Namespace — a partitioned connection endpoint ─────────────────────────────
// Each namespace has its own:
//   • Connection URL: ws://localhost:3000/admin vs ws://localhost:3000/chat
//   • Event listeners (handlers don't bleed across namespaces)
//   • Middleware chain (auth can differ per namespace)
//   • Set of rooms
//
// A client must explicitly connect to a namespace:
// Client (socket.io-client):
//   const chatSocket  = io('http://localhost:3000/chat');
//   const adminSocket = io('http://localhost:3000/admin');
//   // These are TWO separate socket connections.

@WebSocketGateway({ namespace: '/chat' })
export class ChatGateway {
    @WebSocketServer() server: Server; // Server scoped to /chat namespace only
}

@WebSocketGateway({ namespace: '/admin' })
export class AdminGateway {
    @WebSocketServer() server: Server; // Server scoped to /admin namespace only
    // server.emit() from AdminGateway only reaches /admin clients
}

// ── Room — a logical channel within a namespace ────────────────────────────────
// Rooms are created on-the-fly by calling client.join(roomName).
// Any string can be a room name. A socket can be in multiple rooms.
// Clients do not explicitly "connect" to a room — the server adds them.
//
// Default room: every socket is automatically in a room named by their socket.id.
// This lets you target a specific socket: server.to(socketId).emit(...)

@WebSocketGateway({ namespace: '/chat' })
export class ChatGateway {
    @WebSocketServer() server: Server;

    @SubscribeMessage('joinRoom')
    async handleJoin(
        @MessageBody() data: { roomId: string },
        @ConnectedSocket() client: Socket,
    ) {
        await client.join(data.roomId);
        // client.rooms is now: Set { socket.id, 'room-uuid-1' }

        // Emit to everyone in the room (including the joiner):
        this.server.to(data.roomId).emit('userJoined', { userId: client.data.user.id });

        // Emit to everyone in the room EXCEPT the joiner:
        client.to(data.roomId).emit('userJoined', { userId: client.data.user.id });

        // Query who is in a room:
        const sockets = await this.server.in(data.roomId).fetchSockets();
        console.log(`${sockets.length} clients in room ${data.roomId}`);
    }

    @SubscribeMessage('leaveRoom')
    async handleLeave(
        @MessageBody() data: { roomId: string },
        @ConnectedSocket() client: Socket,
    ) {
        await client.leave(data.roomId);
        this.server.to(data.roomId).emit('userLeft', { userId: client.data.user.id });
    }

    // ── Private messaging using socket ID as a room ────────────────────────────
    // Every socket is in a room named by its own socket.id — use this for DMs:
    async sendDirectMessage(toSocketId: string, message: Message): Promise<void> {
        this.server.to(toSocketId).emit('directMessage', message);
        // Only the socket with that ID receives it.
    }
}

// ── Decision guide: Namespace vs Room ─────────────────────────────────────────
//
// Use a NAMESPACE when:
//   • Different parts of your app have different auth/middleware requirements
//   • Different features need isolated event name spaces (/chat, /notifications, /admin)
//   • You want to prevent event name collisions between product areas
//   • Example: /chat for chat, /admin for admin dashboards (different JWT checks)
//
// Use a ROOM when:
//   • You need to group clients dynamically at runtime (by channel, topic, game session)
//   • The grouping is user-initiated (join a chat room, subscribe to a topic)
//   • A client can belong to multiple groups simultaneously
//   • Example: user joins 'room:general' and 'room:engineering' at the same time
//
// Use BOTH when:
//   • /chat namespace containing rooms per channel (the most common real-world pattern)
```

**Q7. How do you manage a socket-to-user mapping to send server-initiated messages to a specific user?**

A: Socket IDs are ephemeral — they change on reconnect. You need a mapping from stable user IDs to current socket IDs, stored either in memory (single instance) or Redis (multi-instance):

```typescript
import { Injectable } from '@nestjs/common';
import { InjectRedis } from '@liaoliaots/nestjs-redis';
import Redis from 'ioredis';

// ── In-memory approach (single server instance) ───────────────────────────────
@Injectable()
export class SocketStateService {
    // Map: userId → Set of socket IDs (a user can have multiple tabs open)
    private readonly userSockets = new Map<string, Set<string>>();

    addSocket(userId: string, socketId: string): void {
        if (!this.userSockets.has(userId)) {
            this.userSockets.set(userId, new Set());
        }
        this.userSockets.get(userId)!.add(socketId);
    }

    removeSocket(userId: string, socketId: string): void {
        const sockets = this.userSockets.get(userId);
        if (!sockets) return;
        sockets.delete(socketId);
        if (sockets.size === 0) this.userSockets.delete(userId);
    }

    getSocketIds(userId: string): string[] {
        return [...(this.userSockets.get(userId) ?? [])];
    }

    isOnline(userId: string): boolean {
        return (this.userSockets.get(userId)?.size ?? 0) > 0;
    }
}

// ── Redis approach (multi-instance / horizontally scaled) ─────────────────────
@Injectable()
export class RedisSocketStateService {
    constructor(@InjectRedis() private readonly redis: Redis) {}

    async addSocket(userId: string, socketId: string): Promise<void> {
        // SADD: Add socketId to the set for this user
        await this.redis.sadd(`user:sockets:${userId}`, socketId);
        await this.redis.expire(`user:sockets:${userId}`, 86400); // 24h TTL
    }

    async removeSocket(userId: string, socketId: string): Promise<void> {
        await this.redis.srem(`user:sockets:${userId}`, socketId);
    }

    async getSocketIds(userId: string): Promise<string[]> {
        return this.redis.smembers(`user:sockets:${userId}`);
    }

    async isOnline(userId: string): Promise<boolean> {
        const count = await this.redis.scard(`user:sockets:${userId}`);
        return count > 0;
    }
}

// ── Gateway using the socket state service ────────────────────────────────────
@WebSocketGateway({ namespace: '/notifications' })
export class NotificationGateway implements OnGatewayConnection, OnGatewayDisconnect {
    @WebSocketServer() server: Server;

    constructor(private readonly socketState: SocketStateService) {}

    async handleConnection(client: Socket) {
        const user = client.data.user; // Set by WsJwtGuard or handleConnection auth
        if (!user) { client.disconnect(); return; }
        this.socketState.addSocket(user.id, client.id);
    }

    async handleDisconnect(client: Socket) {
        const user = client.data.user;
        if (!user) return;
        this.socketState.removeSocket(user.id, client.id);
    }

    // Called by other services to push notifications:
    async pushToUser(userId: string, event: string, data: unknown): Promise<void> {
        const socketIds = this.socketState.getSocketIds(userId);
        for (const socketId of socketIds) {
            // server.to(socketId) works because every socket is in a room by its own ID:
            this.server.to(socketId).emit(event, data);
        }
    }

    // Or using socket.io rooms directly (works with Redis adapter for multi-instance):
    async pushToUserViaRoom(userId: string, event: string, data: unknown): Promise<void> {
        // Join a user-specific room in handleConnection:
        // client.join(`user:${user.id}`)
        // Then target the room:
        this.server.to(`user:${userId}`).emit(event, data);
        // With Redis adapter, this works across ALL server instances — the adapter
        // relays the emit to whichever instance holds that socket.
    }
}

// ── Injecting the gateway into a service for server-initiated push ─────────────
@Injectable()
export class OrderService {
    constructor(
        private readonly orderRepo: OrderRepository,
        private readonly gateway: NotificationGateway,
    ) {}

    async fulfillOrder(orderId: string): Promise<Order> {
        const order = await this.orderRepo.fulfill(orderId);
        // Push to the specific user who owns the order:
        await this.gateway.pushToUser(order.userId, 'orderFulfilled', {
            orderId: order.id,
            status:  'fulfilled',
        });
        return order;
    }
}
```

## Section 4: Guards, Pipes, Interceptors with WebSockets

**Q8. How do guards, pipes, and interceptors work differently in a WebSocket context?**

A: All three pipeline stages apply to gateways just as they do to controllers, but WebSockets introduce important differences in execution timing and what "context" means:

```typescript
import {
    CanActivate, ExecutionContext, Injectable,
    PipeTransform, ArgumentMetadata,
    NestInterceptor, CallHandler,
} from '@nestjs/common';
import { WsException } from '@nestjs/websockets';
import { Socket } from 'socket.io';
import { Observable } from 'rxjs';

// ── WebSocket Guard ───────────────────────────────────────────────────────────
// Guards on a gateway run per MESSAGE (per @SubscribeMessage handler call),
// NOT per connection — the connection itself is handled in handleConnection().
// Use handleConnection() to reject the connection outright.
// Use guards to check authorization for specific actions AFTER connection.

@Injectable()
export class WsAuthGuard implements CanActivate {
    constructor(private readonly jwtService: JwtService) {}

    canActivate(context: ExecutionContext): boolean {
        // For WebSocket context, switch to WS — NOT HTTP:
        const client = context.switchToWs().getClient<Socket>();
        const data   = context.switchToWs().getData(); // The message payload

        // The user was attached to client.data.user during handleConnection:
        if (!client.data?.user) {
            // Throw WsException, not HttpException — wrong exception type causes issues:
            throw new WsException('Unauthorised: no authenticated user on socket');
        }
        return true;
    }
}

@Injectable()
export class WsRolesGuard implements CanActivate {
    constructor(private readonly reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        const requiredRoles = this.reflector.getAllAndOverride<string[]>('roles', [
            context.getHandler(),
            context.getClass(),
        ]);
        if (!requiredRoles?.length) return true;

        const client = context.switchToWs().getClient<Socket>();
        const user   = client.data.user;
        const hasRole = requiredRoles.some(r => user?.roles?.includes(r));
        if (!hasRole) throw new WsException('Forbidden: insufficient role');
        return true;
    }
}

// ── WebSocket Pipe ────────────────────────────────────────────────────────────
// Pipes on gateways validate/transform the @MessageBody() payload.
// Throw WsException (not BadRequestException) so the error propagates correctly.

@Injectable()
export class WsValidationPipe implements PipeTransform {
    private readonly validationPipe = new ValidationPipe({
        whitelist: true,
        transform: true,
        // Custom exception factory to throw WsException:
        exceptionFactory: (errors) => {
            const messages = errors.flatMap(e => Object.values(e.constraints ?? {}));
            return new WsException({ event: 'validationError', data: messages });
        },
    });

    async transform(value: any, metadata: ArgumentMetadata): Promise<any> {
        return this.validationPipe.transform(value, metadata);
    }
}

// Apply at handler level:
@SubscribeMessage('sendMessage')
@UsePipes(WsValidationPipe)
handleMessage(@MessageBody() dto: SendMessageDto): WsResponse<any> {
    // dto is guaranteed to be valid here
    return { event: 'ack', data: { received: true } };
}

// Or globally — but note: global pipes apply to BOTH HTTP and WS handlers.
// If throwing BadRequestException from a WebSocket pipe, it may not be caught cleanly.
// Use a pipe that throws WsException for WS handlers.

// ── WebSocket Interceptor ─────────────────────────────────────────────────────
// Interceptors on gateways work the same as HTTP interceptors.
// They wrap @SubscribeMessage handlers with before/after phases.

@Injectable()
export class WsLoggingInterceptor implements NestInterceptor {
    private readonly logger = new Logger('WebSocket');

    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        const wsContext = context.switchToWs();
        const client    = wsContext.getClient<Socket>();
        const data      = wsContext.getData();
        const handler   = context.getHandler().name;
        const start     = Date.now();

        this.logger.log({
            event: 'ws.message.received',
            handler,
            socketId: client.id,
            userId:   client.data?.user?.id,
            data,
        });

        return next.handle().pipe(
            tap(result => {
                this.logger.log({
                    event:      'ws.message.handled',
                    handler,
                    durationMs: Date.now() - start,
                    socketId:   client.id,
                });
            }),
            catchError(err => {
                this.logger.error({
                    event:      'ws.message.error',
                    handler,
                    durationMs: Date.now() - start,
                    error:      err.message,
                });
                return throwError(() => err);
            }),
        );
    }
}

// ── Applying to a gateway ─────────────────────────────────────────────────────
@WebSocketGateway({ namespace: '/chat' })
@UseGuards(WsAuthGuard)              // Guard applies to ALL @SubscribeMessage handlers
@UseInterceptors(WsLoggingInterceptor)
export class ChatGateway {
    @SubscribeMessage('sendMessage')
    @UseGuards(WsRolesGuard)         // Additional guard on this specific handler
    @UsePipes(WsValidationPipe)
    @Roles('user', 'admin')
    handleMessage(@MessageBody() dto: SendMessageDto): WsResponse<any> {
        // Execution order for this handler:
        // WsAuthGuard → WsRolesGuard → WsLoggingInterceptor (before) →
        // WsValidationPipe → handler → WsLoggingInterceptor (after)
        return { event: 'ack', data: { received: true } };
    }
}
```

**Q9. How do exception filters work for WebSockets — what is `WsException`?**

A: WebSocket exceptions require `WsException` (not `HttpException`) and a filter that implements `BaseWsExceptionFilter` or catches `WsException` explicitly. Unhandled errors in a gateway can silently fail without a proper filter:

```typescript
import {
    Catch, ArgumentsHost,
    WsExceptionFilter as NestWsExceptionFilter,
} from '@nestjs/common';
import { BaseWsExceptionFilter, WsException } from '@nestjs/websockets';
import { Socket } from 'socket.io';

// ── WsException — the correct error type for WebSocket handlers ───────────────
// WsException wraps the error data into the format expected by the WS error filter.
// The data can be a string or an object:
throw new WsException('Unauthorised');
throw new WsException({ event: 'error', data: { message: 'Room not found', code: 'ROOM_404' } });

// ── Custom WebSocket exception filter ─────────────────────────────────────────
@Catch(WsException)
export class WsExceptionFilter extends BaseWsExceptionFilter {
    catch(exception: WsException, host: ArgumentsHost) {
        // host.switchToWs() gives access to the WebSocket client:
        const client  = host.switchToWs().getClient<Socket>();
        const data    = exception.getError();

        // Shape the error event sent to the client:
        const error = typeof data === 'string'
            ? { message: data, code: 'WS_ERROR' }
            : data;

        // Emit an error event to the sender:
        client.emit('exception', {
            status:    'error',
            timestamp: new Date().toISOString(),
            ...error,
        });

        // Optionally call super to also trigger the default NestJS WS error handling:
        // super.catch(exception, host);
    }
}

// ── Catch-all WS filter (catches both WsException and unknown errors) ─────────
@Catch()
export class AllWsExceptionsFilter extends BaseWsExceptionFilter {
    catch(exception: unknown, host: ArgumentsHost): void {
        const client = host.switchToWs().getClient<Socket>();

        if (exception instanceof WsException) {
            const data = exception.getError();
            client.emit('exception', {
                status:    'error',
                message:   typeof data === 'string' ? data : (data as any)?.message ?? 'WS error',
                timestamp: new Date().toISOString(),
            });
            return;
        }

        // Unknown error (DB error, null reference, etc.):
        console.error('Unhandled WS exception:', exception);
        client.emit('exception', {
            status:    'error',
            message:   'Internal server error',
            timestamp: new Date().toISOString(),
        });
    }
}

// ── Registration on the gateway ───────────────────────────────────────────────
@WebSocketGateway({ namespace: '/chat' })
@UseFilters(AllWsExceptionsFilter) // Class-level — applies to all handlers
export class ChatGateway {
    @SubscribeMessage('sendMessage')
    @UseFilters(WsExceptionFilter) // Method-level — overrides class-level for this handler
    handleMessage(@MessageBody() dto: SendMessageDto) {
        if (!dto.roomId) {
            throw new WsException('roomId is required');
            // Filter catches this and emits 'exception' event to the client
        }
    }
}

// ── Global WS filter ─────────────────────────────────────────────────────────
// In main.ts (no DI — use APP_FILTER for DI-aware global filters):
app.useGlobalFilters(new AllWsExceptionsFilter());

// ── What happens without a WS exception filter ────────────────────────────────
// If a @SubscribeMessage handler throws an HttpException (e.g. NotFoundException):
//   • NestJS catches it internally
//   • The error message is emitted as an 'exception' event to the client
//   • The raw HttpException shape may be sent (not ideal for the client)
//   • In some versions, unhandled WS errors are silently swallowed
//
// Always register a WsExceptionFilter for predictable error behaviour.
```

## Section 5: Authentication

**Q10. How do you authenticate WebSocket connections — what are the strategies and their trade-offs?**

A: WebSocket authentication is more complex than HTTP because the connection is persistent. There are three common strategies, each with different security profiles:

```typescript
// ── Strategy 1: Authenticate in handleConnection (most common) ────────────────
// The JWT is passed in the socket.io handshake (query param or auth object).
// The connection is rejected immediately if the token is invalid.

@WebSocketGateway({ namespace: '/chat' })
export class ChatGateway implements OnGatewayConnection {
    constructor(private readonly jwtService: JwtService) {}

    async handleConnection(client: Socket): Promise<void> {
        try {
            // socket.io-client sends: io(url, { auth: { token: 'Bearer xyz' } })
            // OR: io(url, { query: { token: 'xyz' } })
            const token =
                client.handshake.auth?.token?.replace('Bearer ', '') ??
                client.handshake.headers?.authorization?.replace('Bearer ', '') ??
                client.handshake.query?.token as string;

            if (!token) throw new Error('No token');

            const payload = await this.jwtService.verifyAsync(token);
            // Attach user to the socket for all subsequent handler calls:
            client.data.user = payload;
            // Join a user-specific room for targeted pushes:
            client.join(`user:${payload.sub}`);

        } catch (err) {
            console.log(`Auth failed for ${client.id}: ${err.message}`);
            // disconnect(true) — true means "close the underlying connection":
            client.disconnect(true);
            // After disconnect(), no @SubscribeMessage handlers can fire for this socket.
        }
    }
}

// ── Strategy 2: Guard on every @SubscribeMessage ──────────────────────────────
// The connection is accepted; each message is individually authenticated.
// Useful when the token can change or expire during a long-lived connection.

@Injectable()
export class WsJwtGuard implements CanActivate {
    constructor(private readonly jwtService: JwtService) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
        const client = context.switchToWs().getClient<Socket>();

        // Re-verify on each message (expensive but secure against expired tokens):
        const token = client.handshake.auth?.token;
        if (!token) throw new WsException('No token provided');

        try {
            const payload    = await this.jwtService.verifyAsync(token);
            client.data.user = payload; // Refresh user data on each verification
            return true;
        } catch {
            throw new WsException('Invalid or expired token');
        }
    }
}

@WebSocketGateway({ namespace: '/secure' })
@UseGuards(WsJwtGuard) // Applied to all @SubscribeMessage handlers in this gateway
export class SecureGateway {
    @SubscribeMessage('action')
    handleAction(@MessageBody() data: any, @ConnectedSocket() client: Socket) {
        console.log('Authenticated user:', client.data.user);
    }
}

// ── Strategy 3: Middleware on socket.io namespace ─────────────────────────────
// socket.io has its own middleware system (different from Express middleware).
// It runs during the handshake, before handleConnection fires.
// Register it in afterInit via the namespace object.

@WebSocketGateway({ namespace: '/chat' })
export class ChatGateway implements OnGatewayInit {
    constructor(private readonly jwtService: JwtService) {}

    afterInit(server: Server): void {
        // server here is the namespace server object for /chat.
        // Use .use() to register socket.io middleware:
        server.use(async (socket: Socket, next: (err?: Error) => void) => {
            try {
                const token = socket.handshake.auth?.token;
                if (!token) return next(new Error('Authentication error'));

                const payload = await this.jwtService.verifyAsync(token);
                socket.data.user = payload;
                next(); // Call next() to allow the connection
            } catch (err) {
                next(new Error('Authentication error')); // Reject the connection
            }
        });
    }

    // handleConnection fires AFTER middleware has passed:
    handleConnection(client: Socket): void {
        console.log('Connected and authenticated:', client.data.user);
    }
}

// ── Strategy comparison ────────────────────────────────────────────────────────
//
// Strategy                          | When runs            | DI support | Pros / Cons
// ─────────────────────────────────────────────────────────────────────────────────────
// handleConnection auth             | On WS connect        | Yes (class) | Simple; one check per connection
// WsJwtGuard on @SubscribeMessage   | On each message      | Yes (guard) | Secure for long-lived connections
// socket.io namespace middleware    | During WS handshake  | Limited     | Earliest rejection point
//
// RECOMMENDATION:
// Authenticate in handleConnection for most use cases.
// Add WsJwtGuard for specific handlers that need re-verification (e.g., financial actions).
// Use socket.io middleware only for low-level transport-layer concerns.

// ── Token refresh for long-lived connections ───────────────────────────────────
// If a JWT expires during an active WebSocket session:
// Option A: Client sends a 'refreshToken' message; gateway responds with a new token.
// Option B: Use long-lived refresh tokens for WS, short-lived for HTTP.
// Option C: Re-authenticate on each message (Strategy 2 above).

@SubscribeMessage('refreshAuth')
async handleRefresh(
    @MessageBody() data: { refreshToken: string },
    @ConnectedSocket() client: Socket,
): Promise<WsResponse<{ token: string }>> {
    try {
        const newToken = await this.authService.refreshToken(data.refreshToken);
        const payload  = await this.jwtService.verifyAsync(newToken);
        client.data.user = payload; // Update the user on the socket
        return { event: 'authRefreshed', data: { token: newToken } };
    } catch {
        client.disconnect(true);
        throw new WsException('Refresh token invalid');
    }
}
```

## Section 6: Integration Patterns

**Q11. How do you push WebSocket events from an HTTP controller or service — "server-initiated" messages?**

A: Server-initiated WebSocket pushes are one of the most common real-world patterns. A REST endpoint or background job needs to notify connected clients without a client triggering it first:

```typescript
// ── Pattern A: Inject the gateway directly into a service ─────────────────────
// Simple and direct — works when service and gateway are in the same module.

@Injectable()
export class OrderService {
    constructor(
        @InjectRepository(Order) private readonly orderRepo: Repository<Order>,
        private readonly notificationGateway: NotificationGateway, // Injected gateway
    ) {}

    async processOrder(orderId: string): Promise<Order> {
        const order = await this.orderRepo.findOneOrFail({ where: { id: orderId } });
        order.status = 'processing';
        await this.orderRepo.save(order);

        // Push WebSocket event to the customer:
        this.notificationGateway.sendToUser(order.userId, 'orderStatusChanged', {
            orderId: order.id,
            status:  order.status,
        });

        return order;
    }
}

// Corresponding gateway method:
@WebSocketGateway({ namespace: '/notifications' })
export class NotificationGateway {
    @WebSocketServer() server: Server;

    sendToUser(userId: string, event: string, data: unknown): void {
        // Using the user-specific room pattern from Q7:
        this.server.to(`user:${userId}`).emit(event, data);
    }

    sendToAll(event: string, data: unknown): void {
        this.server.emit(event, data);
    }
}

// ── Pattern B: EventEmitter2 — decouple gateway from services ─────────────────
// Better for cross-module communication without circular dependency risk.
// Use NestJS's built-in EventEmitter module.

// npm install --save @nestjs/event-emitter

@Module({
    imports: [EventEmitterModule.forRoot()],
})
export class AppModule {}

// In the service — emit domain events:
@Injectable()
export class PaymentService {
    constructor(private readonly eventEmitter: EventEmitter2) {}

    async processPayment(paymentId: string): Promise<void> {
        // ... process payment ...
        // Emit domain event — no direct dependency on the gateway:
        this.eventEmitter.emit('payment.completed', {
            paymentId,
            userId:    payment.userId,
            amount:    payment.amount,
        });
    }
}

// In the gateway — listen for domain events:
@WebSocketGateway({ namespace: '/payments' })
export class PaymentGateway {
    @WebSocketServer() server: Server;

    // @OnEvent() from @nestjs/event-emitter — listens for the domain event:
    @OnEvent('payment.completed')
    handlePaymentCompleted(payload: { paymentId: string; userId: string; amount: number }) {
        this.server.to(`user:${payload.userId}`).emit('paymentCompleted', {
            paymentId: payload.paymentId,
            amount:    payload.amount,
        });
    }

    @OnEvent('payment.failed')
    handlePaymentFailed(payload: { paymentId: string; userId: string; reason: string }) {
        this.server.to(`user:${payload.userId}`).emit('paymentFailed', {
            paymentId: payload.paymentId,
            reason:    payload.reason,
        });
    }
}

// ── Pattern C: HTTP controller triggering WS push ────────────────────────────
// A REST endpoint that causes a broadcast — common for admin panels:
@Controller('admin/announcements')
@UseGuards(AdminGuard)
export class AnnouncementController {
    constructor(private readonly gateway: NotificationGateway) {}

    @Post()
    async sendAnnouncement(@Body() dto: AnnouncementDto): Promise<void> {
        await this.announcementService.save(dto);
        // Broadcast to all connected WS clients from an HTTP handler:
        this.gateway.sendToAll('announcement', {
            title:   dto.title,
            message: dto.message,
        });
    }
}
```

**Q12. How do you build a hybrid HTTP + WebSocket app — what are the key configuration concerns?**

A: NestJS supports HTTP and WebSocket on the same app instance. By default they share the same port, but there are important configuration details:

```typescript
// ── Default: HTTP and WS on the same port ─────────────────────────────────────
// socket.io attaches itself to the HTTP server automatically.
// No special configuration needed — NestJS handles the upgrade.

async function bootstrap() {
    const app = await NestFactory.create(AppModule);

    // HTTP listens on 3000:
    await app.listen(3000);
    // WebSocket (socket.io) also available on port 3000 via the /socket.io path.
    // Client: io('http://localhost:3000') or io('http://localhost:3000/chat')
}

// ── Separate port for WebSocket ────────────────────────────────────────────────
// Specify a port in @WebSocketGateway to run WS on a different port:
@WebSocketGateway(3001, {         // WS on port 3001, HTTP on 3000
    namespace: '/chat',
    cors: { origin: '*' },
})
export class ChatGateway {}
// Useful for: firewall rules, separate scaling, different SSL termination.

// ── CORS configuration — critical for browser clients ─────────────────────────
// WebSocket connections from browsers are subject to CORS for the initial HTTP
// upgrade handshake. Misconfigured CORS is the most common WS connection failure.

@WebSocketGateway({
    namespace: '/chat',
    cors: {
        origin: ['http://localhost:3001', 'https://myapp.com'],
        methods: ['GET', 'POST'],
        credentials: true,      // Required if sending cookies with the WS connection
        allowedHeaders: ['Authorization', 'Content-Type'],

export class ChatGateway {}

// Global guards registered via APP_GUARD apply to BOTH HTTP controllers and WS gateways.
// This is often not what you want — HTTP and WS have different auth flows.

// WRONG: global HTTP guard applied to WS (context.switchToHttp() in a WS handler):
@Module({
    providers: [{ provide: APP_GUARD, useClass: HttpJwtGuard }], // Breaks WS handlers
})
export class AppModule {}

// CORRECT: Use separate guards and apply them at the right level:
// HTTP: use APP_GUARD for JwtHttpGuard

@Module({

        ConfigModule.forRoot(),
        TypeOrmModule.forRootAsync({ ... }),
        JwtModule.registerAsync({ ... }),
        ChatModule,            // Contains ChatGateway + HTTP ChatController

    providers: [

        { provide: APP_GUARD, useClass: JwtHttpAuthGuard },

        //       unless you also add @UseInterceptors() to the gateway class.
    ],

    controllers: [ChatController],          // HTTP endpoint for message history
    exports:   [ChatService],               // Share with other modules

export class ChatModule {}
// ChatController handles GET /messages (REST)
// ChatGateway handles sendMessage (WS)
// ChatService is used by both — no duplication.
```

## Section 7: Scaling

**Q13. How do you scale NestJS WebSockets horizontally — what is the role of the Redis adapter?**

A: A single socket.io server can only communicate with sockets connected to that instance. When you add a second server, clients on server A cannot receive events emitted by server B. The Redis adapter solves this with a pub/sub relay:

```
Without Redis adapter (broken with 2 instances):

  User A connected to Instance 1 ←── emits 'newMessage' ──── Instance 1
  User B connected to Instance 2     (User B never receives it — wrong instance)

With Redis adapter (pub/sub relay):

  User A connected to Instance 1 ──── emits to Redis ──► Instance 1 → Redis
  User B connected to Instance 2                         Redis → Instance 2 → User B ✓
  (Redis relays the emit to all instances — they deliver to their own clients)
```

```typescript
// ── Setting up the Redis adapter ──────────────────────────────────────────────
// npm install @socket.io/redis-adapter redis

import { IoAdapter }     from '@nestjs/platform-socket.io';
import { createAdapter } from '@socket.io/redis-adapter';
import { createClient }  from 'redis';
import { ServerOptions } from 'socket.io';

export class RedisIoAdapter extends IoAdapter {
    private adapterConstructor: ReturnType<typeof createAdapter>;

    async connectToRedis(): Promise<void> {
        const pubClient = createClient({
            url:      process.env.REDIS_URL,
            password: process.env.REDIS_PASSWORD,
        });
        const subClient = pubClient.duplicate();

        await Promise.all([pubClient.connect(), subClient.connect()]);
        this.adapterConstructor = createAdapter(pubClient, subClient);

        pubClient.on('error', err => console.error('Redis pub error:', err));
        subClient.on('error', err => console.error('Redis sub error:', err));
    }

    createIOServer(port: number, options?: ServerOptions): any {
        const server = super.createIOServer(port, options);
        server.adapter(this.adapterConstructor);
        return server;
    }
}

// Registration in main.ts:
async function bootstrap() {
    const app = await NestFactory.create(AppModule);

    const redisAdapter = new RedisIoAdapter(app);
    await redisAdapter.connectToRedis();
    app.useWebSocketAdapter(redisAdapter);

    await app.listen(3000);
}

// ── What the Redis adapter handles automatically ───────────────────────────────
// server.emit(event, data)              → relayed to all instances → all clients
// server.to(room).emit(event, data)     → relayed to instances that have room members
// server.to(socketId).emit(event, data) → relayed to the instance holding that socket
// client.broadcast.to(room).emit()      → relayed via Redis

// ── What you still need to handle manually with Redis ─────────────────────────
// 1. Socket state (user→socketId mapping) must be in Redis, not in-memory:
//    In-memory Map won't work across instances (see RedisSocketStateService in Q7).
//
// 2. client.join(room) / client.leave(room) — these are per-instance operations.
//    With the Redis adapter, room membership IS shared via Redis automatically
//    for socket.io rooms. But your own user→socket mapping still needs Redis.
//
// 3. handleConnection() fires on one instance only — the one that accepted the connection.
//    Store connection state in Redis, not in gateway class properties.

// ── Sticky sessions — required for socket.io with polling fallback ─────────────
// If a client uses long-polling (not WebSocket), each HTTP poll request
// may hit a different server instance. Without sticky sessions, the session
// context is lost between requests.
//
// Configure your load balancer (nginx, AWS ALB) to use sticky sessions:
// nginx: ip_hash; or cookie-based upstream hashing
// AWS ALB: enable sticky sessions on the target group
//
// With WebSocket-only transport (no polling fallback), sticky sessions are NOT needed:
@WebSocketGateway({
    transports: ['websocket'], // Disable polling — no sticky sessions needed
})
export class ChatGateway {}

// ── Kubernetes deployment considerations ──────────────────────────────────────
// Each pod gets its own socket.io server.
// Use Redis adapter so events cross pods.
// Use a Service with sticky sessions (sessionAffinity: ClientIP) for polling fallback.
// Use WebSocket-only transport to avoid sticky session complexity.
// Liveness probe: monitor Redis connection health alongside HTTP health.
```

**Q14. How do you unit test a NestJS WebSocket gateway?**

## Section 9: Scenario-Based Questions

**Q15. "The WebSocket gateway receives messages but never sends any response — what are the likely causes?"**

A: This is a list of the most common silent-failure patterns in NestJS WebSocket gateways:

```typescript
// ── Cause 1: Wrong return value shape for @SubscribeMessage ───────────────────
// WRONG — the return value is a plain object without 'event':
@SubscribeMessage('ping')
handlePing(): object {
    return { message: 'pong' }; // ← NestJS doesn't know what event to emit
}

// CORRECT — WsResponse requires { event, data }:
@SubscribeMessage('ping')
handlePing(): WsResponse<string> {
    return { event: 'pong', data: 'pong!' }; // ← Client receives 'pong' event
}

// ── Cause 2: Async handler not returning the Observable/Promise ───────────────
// WRONG — async function inside, but the return is void:
@SubscribeMessage('getUser')
handleGetUser(@ConnectedSocket() client: Socket): void {
    this.userService.findById(client.data.user.id).then(user => {
        client.emit('userData', user); // ← The emit inside then() may work,
        // but if the handler throws before here, it's swallowed silently.
    });
    // Handler returns void — no ACK sent to client for the original emit.
}

// CORRECT — return the Promise:
@SubscribeMessage('getUser')
async handleGetUser(@ConnectedSocket() client: Socket): Promise<WsResponse<User>> {
    const user = await this.userService.findById(client.data.user.id);
    return { event: 'userData', data: user };
}

// ── Cause 3: Exception thrown but no WsExceptionFilter registered ─────────────
// WRONG — HttpException thrown in a WS handler; no filter catches it cleanly:
@SubscribeMessage('findRoom')
handleFindRoom(@MessageBody() data: { roomId: string }): WsResponse<Room> {
    const room = this.roomService.findById(data.roomId);
    if (!room) throw new NotFoundException('Room not found'); // HttpException in WS context!
    // NestJS may swallow this or send it in an unexpected format.
    // The client receives nothing or a malformed error.
    return { event: 'roomData', data: room };
}

// CORRECT — throw WsException and register AllWsExceptionsFilter:
@SubscribeMessage('findRoom')
handleFindRoom(@MessageBody() data: { roomId: string }): WsResponse<Room> {
    const room = this.roomService.findById(data.roomId);
    if (!room) throw new WsException({ event: 'error', data: 'Room not found' });
    return { event: 'roomData', data: room };
}

// ── Cause 4: Broadcasting to a room the client hasn't joined ──────────────────
// WRONG — emitting to a room name, but the client never called client.join():
@SubscribeMessage('sendMessage')
handleMessage(@MessageBody() dto: { roomId: string; text: string }): void {
    this.server.to(dto.roomId).emit('newMessage', dto);
    // If no client has joined 'room-1', this emit goes nowhere silently.
}

// FIX — ensure client.join() is called before broadcasting to a room:
@SubscribeMessage('joinRoom')
handleJoin(@MessageBody() data: { roomId: string }, @ConnectedSocket() client: Socket): void {
    client.join(data.roomId); // ← Must happen before any to(roomId).emit()
}

// ── Cause 5: Wrong namespace — client and server on different namespaces ───────
// Server:
@WebSocketGateway({ namespace: '/chat' })   // Listening on /chat
export class ChatGateway {}

// Client:
const socket = io('http://localhost:3000');  // Connecting to default / namespace
// Client never connects to /chat — all events are silently ignored.

// FIX — match namespace:
const socket = io('http://localhost:3000/chat');

// ── Cause 6: CORS blocking the WebSocket upgrade ──────────────────────────────
// The initial WebSocket handshake is an HTTP request — CORS applies.
// If CORS is misconfigured, the browser blocks the connection before it opens.
// No events can flow because the connection is never established.
// Check browser console for: "Cross-Origin Request Blocked" or "WebSocket is closed"

// FIX:
@WebSocketGateway({
    cors: { origin: process.env.FRONTEND_URL, credentials: true },
})
export class ChatGateway {}

// ── Cause 7: Emitting from a service after connection — wrong server reference ──
// WRONG — service holds a reference to server before the gateway is initialised:
@Injectable()
export class NotificationService {
    private server: Server;

    constructor(private readonly gateway: ChatGateway) {
        this.server = gateway.server; // ← gateway.server is undefined at injection time!
        // @WebSocketServer() is populated AFTER the app initialises, not at construction.
    }

    notify(event: string, data: any) {
        this.server.emit(event, data); // TypeError: Cannot read properties of undefined
    }
}

// CORRECT — always call gateway.server at emit time, not at construction time:
@Injectable()
export class NotificationService {
    constructor(private readonly gateway: ChatGateway) {}

    notify(event: string, data: any) {
        this.gateway.server.emit(event, data); // server is populated by now
    }
}
```

**Q16. "Design a real-time collaborative document editing system using NestJS WebSockets."**

A: A collaborative editing system requires presence tracking, operational transformation or CRDT for concurrent edits, room management per document, and conflict resolution:

```typescript
// Architecture overview:
//
// Client A ──[join doc-1]──► DocumentGateway ──► DocumentService
// Client B ──[join doc-1]──► DocumentGateway        │
//                                                    ▼
// Client A ──[edit]────────► DocumentGateway   Redis (doc state + OT log)
//                              │
//                              ├──[broadcast edit to doc-1 room]──► Client B
//                              └──[save to DB asynchronously]

// document.gateway.ts
@WebSocketGateway({ namespace: '/documents', cors: { origin: '*' } })
@UseGuards(WsAuthGuard)
@UseFilters(AllWsExceptionsFilter)
export class DocumentGateway implements OnGatewayConnection, OnGatewayDisconnect {
    @WebSocketServer() server: Server;

    constructor(
        private readonly docService:      DocumentService,
        private readonly presenceService: PresenceService,
    ) {}

    async handleConnection(client: Socket): Promise<void> {
        const user = await this.docService.validateToken(
            client.handshake.auth?.token
        ).catch(() => null);

        if (!user) { client.disconnect(true); return; }
        client.data.user = user;
    }

    async handleDisconnect(client: Socket): Promise<void> {
        const user = client.data.user;
        if (!user) return;

        // Remove user from all documents they had open:
        for (const room of client.rooms) {
            if (room.startsWith('doc:')) {
                const docId = room.replace('doc:', '');
                await this.presenceService.removeUser(docId, user.id);
                this.server.to(room).emit('presenceUpdate', {
                    docId,
                    users: await this.presenceService.getUsers(docId),
                });
            }
        }
    }

    @SubscribeMessage('joinDocument')
    async handleJoinDocument(
        @MessageBody() data: { docId: string },
        @ConnectedSocket() client: Socket,
    ): Promise<WsResponse<{ content: string; version: number; users: User[] }>> {
        const { docId } = data;
        const user      = client.data.user;

        // Check read permission:
        const canRead = await this.docService.canAccess(user.id, docId, 'read');
        if (!canRead) throw new WsException('Forbidden: no read access');

        // Join the socket.io room for this document:
        await client.join(`doc:${docId}`);
        await presenceService.addUser(docId, user.id, client.id);

        // Notify other editors that this user joined:
        client.to(`doc:${docId}`).emit('userJoinedDocument', { user: { id: user.id, name: user.name } });

        // Return current document state to the joining client:
        const doc   = await this.docService.getDocument(docId);
        const users = await this.presenceService.getUsers(docId);
        return { event: 'documentState', data: { content: doc.content, version: doc.version, users } };
    }

    @SubscribeMessage('applyOperation')
    async handleOperation(
        @MessageBody() data: { docId: string; operation: Operation; baseVersion: number },
        @ConnectedSocket() client: Socket,
    ): Promise<WsResponse<{ transformedOp: Operation; newVersion: number }>> {
        const { docId, operation, baseVersion } = data;
        const user = client.data.user;

        const canWrite = await this.docService.canAccess(user.id, docId, 'write');
        if (!canWrite) throw new WsException('Forbidden: no write access');

        // Apply operational transformation to handle concurrent edits:
        const { transformedOp, newVersion } = await this.docService.applyOperation(
            docId, operation, baseVersion, user.id
        );

        // Broadcast the transformed operation to all OTHER editors in the room:
        client.to(`doc:${docId}`).emit('remoteOperation', {
            operation:  transformedOp,
            version:    newVersion,
            userId:     user.id,
        });

        // Return the confirmed (transformed) operation to the sender:
        return { event: 'operationAck', data: { transformedOp, newVersion } };
    }

    @SubscribeMessage('updateCursor')
    handleCursorUpdate(
        @MessageBody() data: { docId: string; position: { line: number; col: number } },
        @ConnectedSocket() client: Socket,
    ): void {
        // Broadcast cursor position to other editors (fire-and-forget, no ACK):
        client.to(`doc:${data.docId}`).emit('cursorMoved', {
            userId:   client.data.user.id,
            position: data.position,
        });
    }
}

// Client-side flow:
// 1. Connect: const socket = io('/documents', { auth: { token } })
// 2. Join:    socket.emit('joinDocument', { docId: '...' })
//             receive: 'documentState' → render document
// 3. Edit:    socket.emit('applyOperation', { docId, operation, baseVersion })
//             receive: 'operationAck'    → apply confirmed version locally
//             receive: 'remoteOperation' → apply others' operations via OT
// 4. Cursor:  socket.emit('updateCursor', { docId, position })
//             receive: 'cursorMoved'    → show collaborators' cursors
```

## Quick Reference Tables

### Gateway vs Controller

| Feature | HTTP Controller | WebSocket Gateway |
|---|---|---|
| Decorator | `@Controller()` | `@WebSocketGateway()` |
| Handler | `@Get()` / `@Post()` | `@SubscribeMessage()` |
| Body | `@Body()` | `@MessageBody()` |
| Client | `@Req()` | `@ConnectedSocket()` |
| Response | Return value / `@Res()` | Return `WsResponse` / `server.emit()` |
| Lifecycle | Request/response | Connect → messages → disconnect |
| Error type | `HttpException` | `WsException` |
| Module placement | `controllers: []` | `providers: []` |

### Emission Patterns

| Pattern | Reaches | Code |
|---|---|---|
| Return `WsResponse` | Sender only (ACK) | `return { event: 'ack', data }` |
| `client.emit()` | Sender only | `client.emit('event', data)` |
| `server.to(room).emit()` | All in room (incl. sender) | `this.server.to(roomId).emit(...)` |
| `client.to(room).emit()` | All in room (excl. sender) | `client.to(roomId).emit(...)` |
| `client.broadcast.emit()` | All clients (excl. sender) | `client.broadcast.emit(...)` |
| `server.emit()` | All connected clients | `this.server.emit(...)` |
| Return `Observable<WsResponse>` | Sender (stream) | `return interval(1000).pipe(map(...))` |

### Exception Handling by Stage

| Thrown in | Correct type | Caught by |
|---|---|---|
| `handleConnection()` | N/A — call `client.disconnect()` | Nothing — you control it |
| `@UseGuards` on gateway | `WsException` | `WsExceptionFilter` |
| `@SubscribeMessage` handler | `WsException` | `WsExceptionFilter` |
| `ValidationPipe` (WS) | `WsException` (via `exceptionFactory`) | `WsExceptionFilter` |
| HTTP `@Get()` etc. | `HttpException` | `ExceptionFilter` |

### Adapter Comparison

| Feature | `IoAdapter` (socket.io) | `WsAdapter` (ws) |
|---|---|---|
| Rooms | ✓ Built-in | ✗ Manual |
| Namespaces | ✓ Built-in | ✗ Manual |
| Reconnection | ✓ Auto | ✗ Client-only |
| Redis scaling | ✓ `@socket.io/redis-adapter` | ✗ Manual |
| Polling fallback | ✓ Long-polling | ✗ None |
| Binary support | ✓ | ✓ Native |
| Overhead | Higher | Lower |
| Best for | Browser clients, rooms, scale | Low-latency, binary, controlled clients |

**Tip for interviews:** Eight things separate strong candidates on this topic: (1) knowing that **gateways belong in the `providers` array, not `controllers`** — placing them in `controllers` silently fails; (2) understanding that **`@WebSocketServer()` is populated after module initialisation, not at construction time** — storing `this.server = gateway.server` in a service constructor gives `undefined`; always dereference `gateway.server` at call time; (3) being precise about the **four emission patterns** (return WsResponse for sender ACK, `client.emit` for sender push, `server.to(room)` for all-in-room, `client.to(room)` for all-in-room-except-sender) and when each applies; (4) knowing that **guards, interceptors, and pipes apply per `@SubscribeMessage` call, not per connection** — the connection lifecycle is handled in `handleConnection/handleDisconnect` lifecycle hooks; (5) understanding that **WsException must be used instead of HttpException** in WebSocket handlers — HttpException thrown in a WS context is not reliably caught by default and can cause silent failures; always register `AllWsExceptionsFilter`; (6) knowing that **socket.io rooms require explicit `client.join()` before any `server.to(room).emit()` will reach that client** — emitting to an empty room is silently dropped; (7) understanding the **Redis adapter requirement for horizontal scaling** — without it, a `server.emit()` from Instance A never reaches clients connected to Instance B; and (8) knowing that **`handleConnection` is the correct place to authenticate and reject connections**, while `handleDisconnect` is where you clean up state — and that rejected connections (via `client.disconnect(true)`) mean no `@SubscribeMessage` handlers will ever fire for that socket.
