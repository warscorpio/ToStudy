# NestJS Module System: `@Module`, `imports`, `exports`, `providers`, `controllers` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the NestJS module system and what problem does it solve over plain Express?**

A: NestJS's module system is a dependency injection (DI) container that organises code into cohesive, self-describing units called modules. Each module declares exactly what it provides to the rest of the application and what it needs from others. This solves three problems that plain Express leaves entirely to the developer:

```
Plain Express:
  - No enforced structure — any file can require() any other file
  - No dependency injection — classes instantiate their own dependencies
  - No encapsulation — internals of one feature leak into others freely
  - Testing requires manual mock wiring

NestJS modules:
  - Enforced structure — each feature lives in a module with declared boundaries
  - DI container — NestJS creates and wires instances automatically
  - Encapsulation — providers are private unless explicitly exported
  - Testing — swap real providers for mocks via the module metadata
```

The Angular-inspired mental model:

```typescript
// Everything in NestJS revolves around the @Module() decorator.
// A module is a class annotated with @Module() that groups:
//   providers   → services, repositories, guards, interceptors (injectable classes)
//   controllers → HTTP route handlers (thin layer between HTTP and services)
//   imports     → other modules whose exports this module needs
//   exports     → subset of this module's providers others can use

// The NestJS IoC container reads this metadata at bootstrap time,
// builds a directed graph of modules and their dependencies,
// and instantiates everything in the correct order.

// Conceptual flow:
// AppModule imports UserModule
// UserModule provides UserService (uses TypeORM UserRepository)
// UserModule has UserController (injects UserService)
// NestJS: create UserRepository → create UserService(repo) → create UserController(service)
// No manual `new UserService(new UserRepository(connection))` anywhere
```

**Q2. What does the `@Module()` decorator do and what does each of its four properties mean?**

A: `@Module()` is a class decorator that attaches metadata to a TypeScript class, turning it into a module that the NestJS IoC container understands. The four properties form a complete picture of the module's boundaries:

```typescript
import { Module } from '@nestjs/common';

@Module({
  imports:     [],   // Other modules this module depends on
  controllers: [],   // Route handlers registered in this module
  providers:   [],   // Services/repositories/guards available via DI in this module
  exports:     [],   // Subset of providers made available to importing modules
})
export class FeatureModule {}
```

Each property in depth:

```typescript
// ─── providers ───────────────────────────────────────────────────────────────
// Classes decorated with @Injectable() that the DI container creates and manages.
// Scope is LOCAL to this module by default — invisible outside unless exported.
// "Provider" is the general term; the specific roles are:
//   Service      → business logic
//   Repository   → data access (often TypeORM/Mongoose repos wrapped with @InjectRepository)
//   Guard        → authorisation checks
//   Interceptor  → request/response transformation
//   Pipe         → input validation/transformation
//   Factory      → custom provider that runs async logic to produce a value

// ─── controllers ─────────────────────────────────────────────────────────────
// Classes decorated with @Controller() that handle incoming HTTP requests.
// NestJS registers their routes with the underlying HTTP adapter (Express/Fastify).
// Controllers are implicitly providers (they can inject things) but are NOT exported —
// they are registered directly with the framework, not shared between modules.

// ─── imports ─────────────────────────────────────────────────────────────────
// Other @Module() classes. By importing a module you gain access to
// everything that module explicitly lists in its 'exports' array.
// Importing a module does NOT give you access to its non-exported providers.

// ─── exports ─────────────────────────────────────────────────────────────────
// Subset of this module's 'providers' (or re-exported imported modules)
// that should be available to any module that imports this one.
// Think of exports as the module's public API.

// Concrete example:
import { TypeOrmModule } from '@nestjs/typeorm';
import { UserService } from './user.service';
import { UserController } from './user.controller';
import { User } from './entities/user.entity';
import { UserRepository } from './user.repository';

@Module({
  imports: [
    TypeOrmModule.forFeature([User]),  // Makes InjectRepository(User) available here
  ],
  controllers: [UserController],       // Handles GET/POST /users routes
  providers: [UserService, UserRepository], // Available within this module only
  exports: [UserService],              // Other modules can inject UserService
  // UserRepository is NOT exported — encapsulated inside UserModule
})
export class UserModule {}
```

## Section 2: Providers

**Q3. What is a provider — what is `@Injectable()` doing and how does the DI container resolve dependencies?**

A: `@Injectable()` is a class decorator that does two things: it marks the class as a candidate for injection (the container can create it) and it enables TypeScript `emitDecoratorMetadata` to record the class's constructor parameter types so NestJS can resolve them automatically:

```typescript
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { User } from './entities/user.entity';

@Injectable()
export class UserService {
    constructor(
        // NestJS reads the TypeScript type 'Repository<User>' here at runtime
        // via reflect-metadata — resolves it from the DI container
        @InjectRepository(User)
        private readonly userRepository: Repository<User>,

        // Plain constructor injection — NestJS creates MailService and injects it
        private readonly mailService: MailService,
    ) {}

    async findById(id: number): Promise<User> {
        return this.userRepository.findOneByOrFail({ id });
    }

    async create(dto: CreateUserDto): Promise<User> {
        const user = this.userRepository.create(dto);
        const saved = await this.userRepository.save(user);
        await this.mailService.sendWelcome(saved.email);
        return saved;
    }
}
```

How the DI container resolves the dependency graph:

```typescript
// NestJS IoC container resolution (simplified):
//
// 1. Read @Module() metadata for UserModule:
//    providers: [UserService, UserRepository, MailService]
//
// 2. For UserService — read constructor parameter types via reflect-metadata:
//    param 0: Repository<User>  (from @InjectRepository token)
//    param 1: MailService       (TypeScript type used as token)
//
// 3. For each parameter, look up the token in the module's provider registry:
//    Repository<User> → provided by TypeOrmModule.forFeature([User]) via imports
//    MailService      → provided by MailModule via imports, OR listed in providers
//
// 4. Recursively resolve dependencies of each dependency
//
// 5. Create instances in dependency order:
//    new UserRepository(dataSource)
//    new MailService(configService, smtpClient)
//    new UserService(userRepository, mailService)
//
// 6. Cache instances (singleton by default — same instance reused)

// Provider tokens — how NestJS identifies what to inject:
// By class (most common):
providers: [UserService]
// Equivalent to:
providers: [{ provide: UserService, useClass: UserService }]

// By string token:
providers: [{ provide: 'JWT_SECRET', useValue: process.env.JWT_SECRET }]
// Inject with:
constructor(@Inject('JWT_SECRET') private jwtSecret: string) {}

// By symbol token (avoids string collision):
export const JWT_SECRET = Symbol('JWT_SECRET');
providers: [{ provide: JWT_SECRET, useValue: process.env.JWT_SECRET }]
constructor(@Inject(JWT_SECRET) private jwtSecret: string) {}
```

**Q4. What are the different provider types — `useClass`, `useValue`, `useFactory`, `useExisting`?**

A: The full provider syntax is an object with a `provide` token and one of four `use*` keys. Each serves a different instantiation strategy:

```typescript
import { Module, Provider } from '@nestjs/common';

// ─── useClass ────────────────────────────────────────────────────────────────
// NestJS instantiates this class and manages its lifecycle.
// Short form: providers: [UserService]
// Full form:
const useClassProvider: Provider = {
    provide: UserService,
    useClass: UserService,     // NestJS calls new UserService(...injected deps)
};

// useClass shines for environment-specific swaps:
const cacheProvider: Provider = {
    provide: CacheService,
    useClass: process.env.NODE_ENV === 'test'
        ? InMemoryCacheService
        : RedisCacheService,   // Different implementation, same interface
};

// ─── useValue ────────────────────────────────────────────────────────────────
// Provide a pre-existing value directly — no instantiation.
// Common for config objects, constants, mock instances in tests.
const configProvider: Provider = {
    provide: 'APP_CONFIG',
    useValue: {
        port: parseInt(process.env.PORT ?? '3000'),
        jwtSecret: process.env.JWT_SECRET,
        dbUrl: process.env.DATABASE_URL,
    },
};

// ─── useFactory ──────────────────────────────────────────────────────────────
// A function that returns the provider value — can be async.
// Inject other providers via the 'inject' array.
const dbProvider: Provider = {
    provide: 'DATABASE_CONNECTION',
    useFactory: async (config: ConfigService): Promise<DataSource> => {
        const dataSource = new DataSource({
            type: 'postgres',
            url: config.get('DATABASE_URL'),
            entities: [__dirname + '/**/*.entity{.ts,.js}'],
        });
        await dataSource.initialize(); // Async setup — NestJS awaits this
        return dataSource;
    },
    inject: [ConfigService], // Injected as positional args to the factory function
};

// Async factory is common for connections that need await:
const redisProvider: Provider = {
    provide: 'REDIS_CLIENT',
    useFactory: async (config: ConfigService) => {
        const client = createClient({ url: config.get('REDIS_URL') });
        await client.connect();
        return client;
    },
    inject: [ConfigService],
};

// ─── useExisting ─────────────────────────────────────────────────────────────
// Create an alias — make one token resolve to the same instance as another.
// Useful for providing an interface token that resolves to a concrete class.
const aliasProvider: Provider = {
    provide: 'IUserRepository',    // Interface token (string or Symbol)
    useExisting: UserRepository,   // Resolves to the same singleton instance
};
// Now both UserRepository and 'IUserRepository' resolve to the same object.
// No new instance created — truly aliased.

// Full module example with mixed provider types:
@Module({
    providers: [
        UserService,                    // useClass (shorthand)
        UserRepository,
        configProvider,                 // useValue
        cacheProvider,                  // useClass (conditional)
        dbProvider,                     // useFactory (async)
        { provide: 'IUserService', useExisting: UserService }, // useExisting
    ],
    exports: [UserService, 'IUserService'],
})
export class UserModule {}
```

## Section 3: Imports and Exports

**Q5. How do `imports` and `exports` work together — what is actually shared when a module is imported?**

A: `imports` and `exports` form the module boundary contract. When module A imports module B, A gets access to exactly what B lists in its `exports` — nothing more. This is the encapsulation mechanism:

```typescript
// ─── MailModule ──────────────────────────────────────────────────────────────
@Module({
    providers: [
        MailService,          // Public — will be exported
        SmtpTransport,        // Private — internal implementation detail
        MailTemplateEngine,   // Private — internal
    ],
    exports: [MailService],   // ONLY MailService is shared with importers
})
export class MailModule {}

// SmtpTransport and MailTemplateEngine are invisible to any module that imports MailModule.
// They are created by NestJS but scoped to MailModule's container.

// ─── UserModule ──────────────────────────────────────────────────────────────
@Module({
    imports: [MailModule],    // Grants access to MailModule's exports
    providers: [UserService],
    exports: [UserService],
})
export class UserModule {}

// UserService CAN inject MailService (it's in MailModule's exports)
@Injectable()
export class UserService {
    constructor(private readonly mailService: MailService) {} // ✓ Works

    // UserService CANNOT inject SmtpTransport — not exported by MailModule
    // constructor(private readonly smtp: SmtpTransport) {} // ✗ Error at runtime
}

// ─── AppModule ───────────────────────────────────────────────────────────────
@Module({
    imports: [UserModule], // Gets access to UserService (UserModule's export)
    // Does NOT get access to MailService — MailModule not imported here
})
export class AppModule {}

// The visibility rules in a diagram:
//
//  MailModule                UserModule               AppModule
//  ┌──────────────────┐     ┌─────────────────┐      ┌───────────────┐
//  │ SmtpTransport    │     │ UserService ◄────│─────▶│               │
//  │ MailTemplateEngine│    │   injects:       │      │               │
//  │ MailService ─────│────▶│   MailService ✓  │      │               │
//  │                  │     │   SmtpTransport ✗│      │               │
//  └──────────────────┘     └─────────────────┘      └───────────────┘
//       exports: [MailService]    exports: [UserService]
```

Re-exporting imported modules — propagating access up the chain:

```typescript
// SharedModule re-exports everything it imports:
@Module({
    imports: [ConfigModule, LoggerModule, CacheModule],
    exports: [ConfigModule, LoggerModule, CacheModule],
    // Any module that imports SharedModule gets ConfigService, LoggerService, CacheService
})
export class SharedModule {}

// Instead of every feature module importing ConfigModule, LoggerModule, CacheModule:
@Module({
    imports: [SharedModule], // Gets all three via SharedModule's re-exports
    providers: [OrderService],
})
export class OrderModule {}

// Re-exporting a provider directly (not the whole module):
@Module({
    imports: [TypeOrmModule.forFeature([User])],
    providers: [UserRepository],
    exports: [
        UserRepository,                    // Export the service
        TypeOrmModule,                     // Re-export the TypeOrmModule itself
        // Now importers can also use InjectRepository(User)
    ],
})
export class UserModule {}
```

**Q6. What is the difference between a feature module and a shared/core module — when do you use each?**

A: NestJS applications typically organise modules into three categories, each with different export and import patterns:

```typescript
// ─── Feature Module ──────────────────────────────────────────────────────────
// Encapsulates ONE domain: users, orders, payments, notifications.
// Usually NOT re-used — imported once into AppModule or a parent module.
// Exports only what truly needs to be shared (often just its primary service).

@Module({
    imports: [
        TypeOrmModule.forFeature([Order, OrderItem]),
        UserModule,      // Needs UserService to verify ownership
        PaymentModule,   // Needs PaymentService to charge card
    ],
    controllers: [OrderController],
    providers: [OrderService, OrderRepository, OrderValidator],
    exports: [OrderService], // Only the service — controller and validator are internal
})
export class OrderModule {}

// ─── Shared Module ───────────────────────────────────────────────────────────
// Contains utilities used by many feature modules.
// Registered once; imported by many.
// NestJS modules are singletons — importing SharedModule 10 times doesn't create 10 instances.

@Module({
    imports: [ConfigModule.forRoot()],
    providers: [
        LoggerService,
        CryptoService,
        HttpClientService,
        PaginationHelper,
    ],
    exports: [
        ConfigModule,       // Re-export so importers get ConfigService
        LoggerService,
        CryptoService,
        HttpClientService,
        PaginationHelper,
    ],
})
export class SharedModule {}

// ─── Core Module ─────────────────────────────────────────────────────────────
// Application-wide concerns: authentication, logging middleware, global guards.
// Typically imported ONLY in AppModule and often uses @Global().
// @Global() makes its exports available everywhere without explicit importing.

import { Global, Module, MiddlewareConsumer, NestModule } from '@nestjs/common';

@Global() // Every module in the app can inject GlobalLoggerService without importing CoreModule
@Module({
    providers: [GlobalLoggerService, RequestContextService],
    exports: [GlobalLoggerService, RequestContextService],
})
export class CoreModule {}
// CoreModule is imported once in AppModule
// ALL other modules can inject GlobalLoggerService without listing CoreModule in their imports

// When to use @Global() — use sparingly:
// ✓ Application-wide logger
// ✓ Request context (AsyncLocalStorage)
// ✓ Configuration service (though ConfigModule.forRoot({ isGlobal: true }) is cleaner)
// ✗ Feature-specific services — defeats the purpose of module encapsulation

// ─── AppModule ───────────────────────────────────────────────────────────────
@Module({
    imports: [
        CoreModule,        // Global providers available everywhere
        SharedModule,      // Shared utilities — import in each feature module that needs them
        // Feature modules:
        UserModule,
        OrderModule,
        PaymentModule,
        NotificationModule,
    ],
})
export class AppModule {}
```

## Section 4: Controllers

**Q7. What is a controller and how does it relate to the module system?**

A: A controller is a class decorated with `@Controller()` that handles incoming HTTP requests and returns responses. It lives in the `controllers` array of a `@Module()` and is the thinnest layer in NestJS — it delegates all business logic to injected services:

```typescript
import {
    Controller, Get, Post, Put, Delete, Patch,
    Param, Query, Body, HttpCode, HttpStatus,
    ParseIntPipe, UseGuards, ParseUUIDPipe,
} from '@nestjs/common';
import { UserService } from './user.service';
import { CreateUserDto } from './dto/create-user.dto';
import { UpdateUserDto } from './dto/update-user.dto';
import { ListUsersQueryDto } from './dto/list-users-query.dto';
import { JwtAuthGuard } from '../auth/guards/jwt-auth.guard';

@Controller('users')          // Route prefix: all methods here are under /users
@UseGuards(JwtAuthGuard)      // Applied to all methods in this controller
export class UserController {
    constructor(
        // Controller injects UserService — service layer handles the business logic
        private readonly userService: UserService,
    ) {}

    @Get()                    // GET /users
    findAll(@Query() query: ListUsersQueryDto) {
        return this.userService.findAll(query);
        // Return value is automatically serialized to JSON
        // Returned Promise is automatically awaited
    }

    @Get(':id')               // GET /users/:id
    findOne(
        @Param('id', ParseIntPipe) id: number,
        // ParseIntPipe transforms ':id' string → number, throws 400 if not numeric
    ) {
        return this.userService.findById(id);
    }

    @Post()                   // POST /users
    @HttpCode(HttpStatus.CREATED) // Override default 200 → 201
    create(@Body() dto: CreateUserDto) {
        return this.userService.create(dto);
    }

    @Put(':id')               // PUT /users/:id
    update(
        @Param('id', ParseIntPipe) id: number,
        @Body() dto: UpdateUserDto,
    ) {
        return this.userService.update(id, dto);
    }

    @Patch(':id')             // PATCH /users/:id
    partialUpdate(
        @Param('id', ParseIntPipe) id: number,
        @Body() dto: Partial<UpdateUserDto>,
    ) {
        return this.userService.patch(id, dto);
    }

    @Delete(':id')            // DELETE /users/:id
    @HttpCode(HttpStatus.NO_CONTENT) // 204 No Content
    remove(@Param('id', ParseIntPipe) id: number) {
        return this.userService.delete(id);
    }

    @Get(':id/orders')        // GET /users/:id/orders (nested resource)
    getOrders(
        @Param('id', ParseIntPipe) id: number,
        @Query('status') status?: string,
    ) {
        return this.userService.getOrdersForUser(id, status);
    }
}
```

Why controllers are NOT exported:

```typescript
// Controllers are registered with the HTTP framework (Express/Fastify) — they don't
// need to be injected into other providers. Other modules never 'inject a controller'.
// So there is no reason to list them in 'exports'.
// NestJS will throw if you try to export a controller — they are not shareable providers.

@Module({
    controllers: [UserController],
    providers: [UserService],
    exports: [
        UserService,     // ✓ Correct — providers can be exported
        // UserController, // ✗ Error: Cannot export a controller
    ],
})
export class UserModule {}
```

**Q8. How do route prefixes compose between `@Controller()`, `@Module()`, and `app.setGlobalPrefix()`?**

A: NestJS builds the full route path by concatenating three optional layers. Understanding the composition prevents duplicate or missing prefix bugs:

```typescript
// Layer 1: Global prefix (applies to ALL routes in the app)
async function bootstrap() {
    const app = await NestFactory.create(AppModule);
    app.setGlobalPrefix('api/v1', {
        exclude: [{ path: 'health', method: RequestMethod.GET }],
        // Health check at /health (no prefix), all others at /api/v1/...
    });
    await app.listen(3000);
}

// Layer 2: Module-level prefix via RouterModule (optional — rarely used)
import { RouterModule } from '@nestjs/core';

@Module({
    imports: [
        RouterModule.register([
            { path: 'admin', module: AdminModule }, // All AdminModule routes under /admin
        ]),
        AdminModule,
    ],
})
export class AppModule {}

// Layer 3: Controller prefix (most commonly used)
@Controller('users')  // Prefix for all methods in this controller
export class UserController {
    @Get()            // Final path: /api/v1/users
    @Get(':id')       // Final path: /api/v1/users/:id
    @Get(':id/orders')// Final path: /api/v1/users/:id/orders
}

// Versioning — NestJS has first-class version support:
import { VersioningType } from '@nestjs/common';

async function bootstrap() {
    const app = await NestFactory.create(AppModule);
    app.enableVersioning({ type: VersioningType.URI });
    // URI versioning: /v1/users, /v2/users
    await app.listen(3000);
}

@Controller({ path: 'users', version: '1' })
export class UserV1Controller { ... }

@Controller({ path: 'users', version: '2' })
export class UserV2Controller { ... }

// Or version individual routes:
@Controller('users')
export class UserController {
    @Version('1') @Get()
    findAllV1() { ... } // GET /v1/users

    @Version('2') @Get()
    findAllV2() { ... } // GET /v2/users
}
```

## Section 5: Module Lifecycle and Scopes

**Q9. What is module scope vs provider scope — what are `DEFAULT`, `REQUEST`, and `TRANSIENT` scopes?**

A: By default, every provider in NestJS is a singleton — one instance per application. NestJS supports two other scopes for cases where you need per-request or per-injection instances:

```typescript
import { Injectable, Scope, Inject } from '@nestjs/common';
import { REQUEST } from '@nestjs/core';
import { Request } from 'express';

// ─── DEFAULT (Singleton) scope ────────────────────────────────────────────────
// One instance created per application bootstrap. Shared across all requests.
// Most efficient — use by default for stateless services.
@Injectable() // Default: scope = Scope.DEFAULT
export class UserService {
    private callCount = 0; // Shared across ALL requests — mutable state is dangerous
}

// ─── REQUEST scope ────────────────────────────────────────────────────────────
// One instance created per incoming HTTP request.
// Useful for: per-request context (tenant ID, user from JWT), per-request logging.
// COST: NestJS cannot cache request-scoped providers — DI chain is rebuilt per request.
// Any singleton that depends on a REQUEST-scoped provider becomes REQUEST-scoped too.
@Injectable({ scope: Scope.REQUEST })
export class RequestContextService {
    constructor(
        @Inject(REQUEST) private readonly request: Request,
        // NestJS injects the current Express/Fastify request object
    ) {}

    getUserId(): string | undefined {
        return (this.request as any).user?.id;
    }

    getTenantId(): string | undefined {
        return this.request.headers['x-tenant-id'] as string;
    }
}

// ─── TRANSIENT scope ─────────────────────────────────────────────────────────
// A new instance is created for each injection point.
// If ServiceA and ServiceB both inject TransientLogger, each gets their own instance.
// Useful for: stateful utilities that need to be independent per consumer.
@Injectable({ scope: Scope.TRANSIENT })
export class QueryBuilder {
    private conditions: string[] = [];

    where(condition: string): this {
        this.conditions.push(condition); // State is isolated per injection
        return this;
    }

    build(): string {
        return `SELECT * FROM table WHERE ${this.conditions.join(' AND ')}`;
    }
}

// Scope propagation — the "dirtying" effect:
// If a singleton depends on a REQUEST-scoped provider → becomes REQUEST-scoped
// This propagates up the entire dependency chain

// Recommendation: use AsyncLocalStorage instead of REQUEST scope for context:
import { AsyncLocalStorage } from 'async_hooks';

@Injectable()
export class RequestContextService {
    // Singleton — but context is per-request via AsyncLocalStorage
    private storage = new AsyncLocalStorage<{ userId: string; tenantId: string }>();

    run(context: { userId: string; tenantId: string }, fn: () => void) {
        this.storage.run(context, fn);
    }

    get userId(): string | undefined {
        return this.storage.getStore()?.userId;
    }
}
```

**Q10. What are the module lifecycle hooks — `OnModuleInit`, `OnApplicationBootstrap`, `OnModuleDestroy`, `BeforeApplicationShutdown`?**

A: NestJS provides lifecycle hooks that let providers perform setup and teardown at specific points in the application lifecycle. These are essential for initialising connections, seeding data, and closing resources gracefully:

```typescript
import {
    Injectable, Module,
    OnModuleInit, OnApplicationBootstrap,
    OnModuleDestroy, BeforeApplicationShutdown,
} from '@nestjs/common';
import { InjectDataSource } from '@nestjs/typeorm';
import { DataSource } from 'typeorm';

@Injectable()
export class DatabaseService implements OnModuleInit, OnModuleDestroy {

    constructor(
        @InjectDataSource() private readonly dataSource: DataSource,
    ) {}

    async onModuleInit(): Promise<void> {
        // Called after the module's dependencies are resolved and instantiated.
        // Safe to use injected dependencies here.
        // Use for: running migrations, seeding reference data, verifying connections.
        await this.dataSource.runMigrations();
        console.log('Migrations complete');
    }

    async onModuleDestroy(): Promise<void> {
        // Called when the module is being destroyed (app shutdown initiated).
        // Use for: closing DB connections, flushing write buffers.
        await this.dataSource.destroy();
        console.log('Database connection closed');
    }
}

@Injectable()
export class CacheWarmupService implements OnApplicationBootstrap {

    constructor(private readonly cacheService: CacheService) {}

    async onApplicationBootstrap(): Promise<void> {
        // Called AFTER all modules are initialised AND the HTTP server starts listening.
        // Use for: warming caches that require all modules to be ready.
        // Unlike onModuleInit, guaranteed to run after the full app is ready.
        await this.cacheService.warmup(['products', 'categories', 'config']);
        console.log('Cache warmed');
    }
}

@Injectable()
export class GracefulShutdownService implements BeforeApplicationShutdown {

    constructor(private readonly queueService: QueueService) {}

    async beforeApplicationShutdown(signal: string): Promise<void> {
        // Called when a termination signal (SIGTERM, SIGINT) is received,
        // BEFORE onModuleDestroy hooks run.
        // Use for: stopping job queues from accepting new work, draining in-flight requests.
        console.log(`Received ${signal} — stopping queue`);
        await this.queueService.pause();
        await this.queueService.drain(); // Wait for in-flight jobs to complete
    }
}

// Enabling shutdown hooks (required for BeforeApplicationShutdown to receive signals):
async function bootstrap() {
    const app = await NestFactory.create(AppModule);
    app.enableShutdownHooks(); // Listen for SIGTERM, SIGINT
    await app.listen(3000);
}

// Lifecycle order on startup:
// 1. All providers instantiated (constructors called)
// 2. onModuleInit() — per module, in import order
// 3. onApplicationBootstrap() — after all modules init
// 4. HTTP server starts listening

// Lifecycle order on shutdown:
// 1. beforeApplicationShutdown(signal)
// 2. HTTP server stops accepting new connections
// 3. onModuleDestroy() — per module, in reverse import order
// 4. Process exits
```

## Section 6: Dynamic Modules

**Q11. What are dynamic modules and when should you use them over static modules?**

A: A dynamic module is one where the module's providers are determined at runtime — configured when imported, not hardcoded in the module definition. The pattern is used for libraries that need configuration (ConfigModule, TypeOrmModule, JwtModule):

```typescript
import { Module, DynamicModule, Global } from '@nestjs/common';
import { ConfigService } from './config.service';

// ─── Static module — same providers every time ────────────────────────────────
@Module({
    providers: [UserService],
    exports: [UserService],
})
export class UserModule {} // UserModule always provides UserService the same way

// ─── Dynamic module — providers vary based on configuration ───────────────────
interface JwtModuleOptions {
    secret: string;
    expiresIn: string;
    algorithm?: 'HS256' | 'RS256';
}

@Module({})
export class JwtModule {
    // forRoot() — app-wide singleton, typically in AppModule
    static forRoot(options: JwtModuleOptions): DynamicModule {
        return {
            module: JwtModule,           // Must include the module class itself
            global: true,                // Make this a global module
            providers: [
                {
                    provide: 'JWT_OPTIONS',
                    useValue: options,
                },
                JwtService,              // JwtService injects JWT_OPTIONS
            ],
            exports: [JwtService],
        };
    }

    // forFeature() — feature-level registration with different config
    static forFeature(options: Partial<JwtModuleOptions>): DynamicModule {
        return {
            module: JwtModule,
            providers: [
                { provide: 'JWT_FEATURE_OPTIONS', useValue: options },
                FeatureJwtService,
            ],
            exports: [FeatureJwtService],
        };
    }

    // forRootAsync() — when config comes from async sources (e.g., ConfigService)
    static forRootAsync(options: {
        useFactory: (...args: any[]) => Promise<JwtModuleOptions> | JwtModuleOptions;
        inject?: any[];
        imports?: any[];
    }): DynamicModule {
        return {
            module: JwtModule,
            global: true,
            imports: options.imports ?? [],
            providers: [
                {
                    provide: 'JWT_OPTIONS',
                    useFactory: options.useFactory,
                    inject: options.inject ?? [],
                },
                JwtService,
            ],
            exports: [JwtService],
        };
    }
}

// Usage of dynamic module:
@Module({
    imports: [
        // Static options:
        JwtModule.forRoot({
            secret: 'hardcoded-secret',
            expiresIn: '1h',
        }),

        // Async options — reads from ConfigService:
        JwtModule.forRootAsync({
            imports: [ConfigModule],
            useFactory: (config: ConfigService) => ({
                secret: config.get<string>('JWT_SECRET'),
                expiresIn: config.get<string>('JWT_EXPIRES_IN', '1h'),
            }),
            inject: [ConfigService],
        }),
    ],
})
export class AppModule {}

// Real-world: TypeORM uses this exact pattern:
TypeOrmModule.forRoot({ type: 'postgres', ... })          // App-level DB connection
TypeOrmModule.forFeature([User, Order, Product])          // Feature-level entity registration
TypeOrmModule.forRootAsync({ useFactory: ..., inject: [] }) // Async config
```

## Section 7: Testing

**Q12. How do you test NestJS modules in isolation — what is `Test.createTestingModule()`?**

A: NestJS provides `@nestjs/testing` with a `TestingModule` builder that creates a miniature NestJS application for testing. You can override providers with mocks, test the full module graph, or test a single service in isolation:

```typescript
import { Test, TestingModule } from '@nestjs/testing';
import { getRepositoryToken } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { UserService } from './user.service';
import { UserModule } from './user.module';
import { User } from './entities/user.entity';
import { MailService } from '../mail/mail.service';

// ─── Unit test — service in isolation ────────────────────────────────────────
describe('UserService (unit)', () => {
    let service: UserService;
    let userRepo: jest.Mocked<Repository<User>>;
    let mailService: jest.Mocked<MailService>;

    beforeEach(async () => {
        const module: TestingModule = await Test.createTestingModule({
            providers: [
                UserService,
                // Override TypeORM repository with a jest mock:
                {
                    provide: getRepositoryToken(User),
                    useValue: {
                        findOneBy: jest.fn(),
                        findOneByOrFail: jest.fn(),
                        create: jest.fn(),
                        save: jest.fn(),
                    },
                },
                // Override MailService with a mock:
                {
                    provide: MailService,
                    useValue: {
                        sendWelcome: jest.fn().mockResolvedValue(undefined),
                    },
                },
            ],
        }).compile();

        service = module.get<UserService>(UserService);
        userRepo = module.get(getRepositoryToken(User));
        mailService = module.get(MailService);
    });

    it('should create a user and send a welcome email', async () => {
        const dto = { email: 'test@example.com', name: 'Alice', password: 'secret' };
        const mockUser = { id: 1, ...dto };

        userRepo.create.mockReturnValue(mockUser as User);
        userRepo.save.mockResolvedValue(mockUser as User);

        const result = await service.create(dto);

        expect(userRepo.create).toHaveBeenCalledWith(dto);
        expect(userRepo.save).toHaveBeenCalledWith(mockUser);
        expect(mailService.sendWelcome).toHaveBeenCalledWith('test@example.com');
        expect(result).toEqual(mockUser);
    });

    it('should throw NotFoundException when user not found', async () => {
        userRepo.findOneByOrFail.mockRejectedValue(new EntityNotFoundError(User, {}));

        await expect(service.findById(999)).rejects.toThrow();
    });
});

// ─── Integration test — full module with mocked DB ────────────────────────────
describe('UserModule (integration)', () => {
    let app: INestApplication;

    beforeAll(async () => {
        const module: TestingModule = await Test.createTestingModule({
            imports: [UserModule],
        })
        .overrideProvider(getRepositoryToken(User))
        .useValue({
            findOneBy: jest.fn().mockResolvedValue({ id: 1, email: 'a@b.com' }),
            create: jest.fn(),
            save: jest.fn(),
        })
        .overrideProvider(MailService)
        .useValue({ sendWelcome: jest.fn() })
        .compile();

        app = module.createNestApplication();
        await app.init();
    });

    afterAll(async () => {
        await app.close();
    });

    it('GET /users/1 returns a user', async () => {
        return request(app.getHttpServer())
            .get('/users/1')
            .expect(200)
            .expect(res => {
                expect(res.body).toHaveProperty('id', 1);
                expect(res.body).toHaveProperty('email', 'a@b.com');
            });
    });
});

// ─── Testing a guard or interceptor with the module ───────────────────────────
describe('JwtAuthGuard', () => {
    let guard: JwtAuthGuard;

    beforeEach(async () => {
        const module = await Test.createTestingModule({
            providers: [
                JwtAuthGuard,
                { provide: JwtService, useValue: { verifyAsync: jest.fn() } },
                { provide: 'JWT_OPTIONS', useValue: { secret: 'test' } },
            ],
        }).compile();

        guard = module.get<JwtAuthGuard>(JwtAuthGuard);
    });

    it('should allow request with valid token', async () => {
        const mockContext = createMockExecutionContext({ authorization: 'Bearer valid.jwt.token' });
        jest.spyOn(module.get(JwtService), 'verifyAsync').mockResolvedValue({ sub: 1 });

        await expect(guard.canActivate(mockContext)).resolves.toBe(true);
    });
});
```

## Section 8: Scenario-Based Questions

**Q13. "Your UserService needs ConfigService but you're getting a dependency injection error. What are the likely causes?"**

```typescript
@Module({
    providers: [UserService],
    exports: [UserService],
})
export class UserModule {}

@Injectable()
export class UserService {
    constructor(private readonly config: ConfigService) {}
}
```

A: There are four likely causes, each with a distinct fix:

```typescript
// Cause 1: ConfigModule not imported into UserModule
// NestJS can only inject providers that are in the module's providers array
// OR in an imported module's exports.
// ConfigService lives in ConfigModule — UserModule must import it.

// BROKEN — UserModule has no access to ConfigService:
@Module({
    providers: [UserService],
})
export class UserModule {}

// FIXED — import ConfigModule to gain access to ConfigService:
@Module({
    imports: [ConfigModule],  // ConfigModule exports ConfigService
    providers: [UserService],
})
export class UserModule {}

// Cause 2: ConfigModule registered without isGlobal: true, and not imported here
// If AppModule uses ConfigModule.forRoot({ isGlobal: true }),
// then ALL modules get ConfigService without importing it explicitly.
// But if isGlobal: false (the default), every module that needs it must import it.
ConfigModule.forRoot({ isGlobal: true }); // In AppModule → no need to import elsewhere
ConfigModule.forRoot({ isGlobal: false }); // Must import ConfigModule in every module

// Cause 3: Circular dependency — UserModule imports AuthModule, AuthModule imports UserModule
// NestJS detects circular module dependencies and throws.
// Fix: extract the shared dependency to a third module both can import.

// BROKEN circular dependency:
// UserModule → imports AuthModule
// AuthModule → imports UserModule

// FIXED: extract shared concern to SharedModule:
@Module({
    providers: [SharedTokenService],
    exports: [SharedTokenService],
})
export class SharedModule {}

@Module({ imports: [SharedModule], providers: [UserService] })
export class UserModule {}

@Module({ imports: [SharedModule], providers: [AuthService] })
export class AuthModule {}

// Cause 4: Using forwardRef() when circular dependency is unavoidable
// (Rare — usually means the design should be refactored instead)
import { forwardRef } from '@nestjs/common';

@Module({
    imports: [forwardRef(() => AuthModule)], // Lazy reference resolves circular dep
    providers: [UserService],
})
export class UserModule {}

@Injectable()
export class UserService {
    constructor(
        @Inject(forwardRef(() => AuthService))
        private readonly authService: AuthService, // Lazy injection
    ) {}
}
```

**Q14. "Design the module structure for a multi-tenant SaaS application with: authentication, users, billing, notifications, and shared utilities."**

A: A complete production module architecture applying all patterns from this guide:

```typescript
// Directory structure:
// src/
//   app.module.ts
//   core/
//     core.module.ts           ← @Global() module for app-wide concerns
//     request-context.service.ts
//     logger.service.ts
//   shared/
//     shared.module.ts         ← re-exports utilities needed by feature modules
//     crypto.service.ts
//     pagination.helper.ts
//   config/
//     config.module.ts         ← dynamic module wrapping @nestjs/config
//   auth/
//     auth.module.ts
//     auth.controller.ts
//     auth.service.ts
//     strategies/
//     guards/
//   users/
//     user.module.ts
//     user.controller.ts
//     user.service.ts
//     user.repository.ts
//     entities/user.entity.ts
//     dto/
//   billing/
//     billing.module.ts
//     billing.controller.ts
//     billing.service.ts
//     stripe.service.ts        ← private, not exported
//   notifications/
//     notification.module.ts
//     notification.service.ts
//     channels/
//       email.service.ts
//       sms.service.ts

// ─── CoreModule — global, app-wide concerns ──────────────────────────────────
@Global()
@Module({
    providers: [
        RequestContextService,   // AsyncLocalStorage-based per-request context
        AppLoggerService,        // Structured logger with request context
    ],
    exports: [RequestContextService, AppLoggerService],
})
export class CoreModule {}

// ─── SharedModule — utilities for feature modules ────────────────────────────
@Module({
    imports: [ConfigModule],
    providers: [CryptoService, PaginationHelper, HttpClientService],
    exports: [
        ConfigModule,        // Re-export ConfigModule so importers get ConfigService
        CryptoService,
        PaginationHelper,
        HttpClientService,
    ],
})
export class SharedModule {}

// ─── AuthModule — JWT issuance and verification ──────────────────────────────
@Module({
    imports: [
        SharedModule,        // ConfigService for JWT secret
        UserModule,          // UserService for user lookup during login
        JwtModule.forRootAsync({
            imports: [ConfigModule],
            useFactory: (config: ConfigService) => ({
                secret: config.get('JWT_SECRET'),
                expiresIn: config.get('JWT_EXPIRES_IN', '1h'),
            }),
            inject: [ConfigService],
        }),
    ],
    controllers: [AuthController],
    providers: [AuthService, JwtStrategy, LocalStrategy],
    exports: [AuthService],  // Other modules can verify tokens
})
export class AuthModule {}

// ─── UserModule — user CRUD ──────────────────────────────────────────────────
@Module({
    imports: [
        TypeOrmModule.forFeature([User]),
        SharedModule,
        NotificationModule,  // To send welcome emails on registration
    ],
    controllers: [UserController],
    providers: [UserService, UserRepository],
    exports: [UserService],  // AuthModule and BillingModule need this
})
export class UserModule {}

// ─── BillingModule — Stripe integration ─────────────────────────────────────
@Module({
    imports: [
        TypeOrmModule.forFeature([Subscription, Invoice]),
        SharedModule,
        UserModule,          // To attach subscriptions to users
    ],
    controllers: [BillingController],
    providers: [
        BillingService,
        StripeService,          // Private — Stripe SDK wrapper
        WebhookHandlerService,  // Private — handles Stripe webhook events
    ],
    exports: [BillingService],  // Check subscription status from other modules
})
export class BillingModule {}

// ─── NotificationModule — multi-channel notifications ────────────────────────
@Module({
    imports: [SharedModule],
    providers: [
        NotificationService,  // Orchestrates channels
        EmailService,         // Private implementation
        SmsService,           // Private implementation
        PushService,          // Private implementation
    ],
    exports: [NotificationService], // Only the orchestrator is public
})
export class NotificationModule {}

// ─── AppModule — root composition ────────────────────────────────────────────
@Module({
    imports: [
        // Infrastructure (loaded first):
        CoreModule,                          // @Global — available everywhere
        ConfigModule.forRoot({ isGlobal: true }), // ConfigService globally available
        TypeOrmModule.forRootAsync({
            useFactory: (config: ConfigService) => ({
                type: 'postgres',
                url: config.get('DATABASE_URL'),
                autoLoadEntities: true,
            }),

        }),

        // Shared utilities:
        SharedModule,

        // Feature modules:
        AuthModule,
        UserModule,
        BillingModule,
        NotificationModule,
    ],
})
export class AppModule {}

// Dependency graph (who imports what):
//
//  AppModule
//  ├── CoreModule (@Global)
//  ├── ConfigModule (isGlobal: true)
//  ├── TypeOrmModule (forRootAsync)
//  ├── SharedModule
//  ├── AuthModule

//  │   ├── SharedModule

//  └── NotificationModule
```

## Quick Reference Table

| Property | Type | Purpose | What happens if omitted |
|---|---|---|---|
| `providers` | `Provider[]` | Services/repos injectable within this module | Nothing injectable — DI fails for empty module |
| `controllers` | `Type[]` | HTTP route handlers registered with the framework | No routes registered for this module |
| `imports` | `ModuleType[]` | Other modules whose exports are needed | Cannot inject from those modules — DI error |
| `exports` | `(Provider \| Type)[]` | Subset of providers available to importing modules | All providers are private — module is a black box |

| Provider type | Syntax | When to use |
|---|---|---|
| `useClass` | `{ provide: Token, useClass: MyClass }` | Standard injectable class (most common) |
| `useValue` | `{ provide: Token, useValue: obj }` | Constants, config objects, mock instances |
| `useFactory` | `{ provide: Token, useFactory: fn, inject: [] }` | Async setup, conditional logic, external SDK init |
| `useExisting` | `{ provide: AliasToken, useExisting: RealToken }` | Interface aliasing, backwards-compatible renaming |

| Scope | Instances | Use case | Cost |
|---|---|---|---|
| `DEFAULT` (singleton) | 1 per app | Stateless services (most services) | None |
| `REQUEST` | 1 per HTTP request | Per-request context, tenant isolation | DI chain rebuilt per request |
| `TRANSIENT` | 1 per injection point | Stateful utilities needing isolation | New instance per consumer |

| Lifecycle hook | When called | Use for |
|---|---|---|
| `onModuleInit` | After module's providers instantiated | DB migrations, connection validation |
| `onApplicationBootstrap` | After all modules init + server listening | Cache warmup, post-boot setup |
| `onModuleDestroy` | During shutdown, before process exit | Close connections, flush buffers |
| `beforeApplicationShutdown` | On SIGTERM/SIGINT signal | Stop queues, drain in-flight requests |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) explaining precisely that **`exports` is the public API of a module** — providers not listed in `exports` are invisible to importing modules even if those modules import the module containing them, and the analogy to `public` vs `private` class members is exact; (2) knowing that **controllers are never exported** — they are registered with the HTTP framework, not with the DI container for injection into other services, and attempting to export a controller is an error; (3) understanding **provider token resolution** — `providers: [UserService]` is shorthand for `{ provide: UserService, useClass: UserService }`, the `provide` key is the token used for lookup, and `@Inject()` with a string or symbol token is needed when the type alone is insufficient; (4) being precise about **`@Global()` vs importing** — `@Global()` makes a module's exports available everywhere without being imported, but it should be used sparingly (application-wide logger, request context) since it defeats encapsulation for anything domain-specific; (5) knowing the **scope propagation rule** — if a singleton provider depends on a REQUEST-scoped provider, the singleton becomes REQUEST-scoped too, propagating up the entire dependency chain, which is why `AsyncLocalStorage` is often a better pattern than REQUEST scope for per-request context; and (6) understanding **dynamic modules** — the `forRoot()` / `forFeature()` / `forRootAsync()` pattern lets a module receive configuration at import time, and `forRootAsync()` is needed when configuration comes from another provider like `ConfigService` rather than a static value.
