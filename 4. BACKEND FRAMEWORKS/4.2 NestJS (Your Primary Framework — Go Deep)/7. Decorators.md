# NestJS Decorators: Custom Route Decorators, Parameter Decorators — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a decorator in TypeScript/NestJS and how does it work at the metadata level?**
A: A decorator is a special function that wraps a class, method, property, or parameter and can attach metadata or modify behavior. In NestJS, decorators are the primary mechanism for declaring routes, guards, interceptors, pipes, and extracting request data — all via metadata rather than runtime logic scattered through handlers.

TypeScript decorators are stage-3 proposals; NestJS relies on `reflect-metadata` to read and write typed metadata at runtime:

```typescript
// reflect-metadata must be imported once at app entry:
import 'reflect-metadata';

// Decorator factory (returns a decorator function):
function MyDecorator(value: string) {
    return function (target: object, key: string | symbol, descriptor: PropertyDescriptor) {
        // target    = prototype of the class (for method decorators)
        // key       = method name
        // descriptor = property descriptor ({ value: fn, writable, configurable, enumerable })

        // Attach metadata:
        Reflect.defineMetadata('my-key', value, target, key);

        // Optionally wrap the original method:
        const original = descriptor.value;
        descriptor.value = function (...args: unknown[]) {
            console.log(`Calling ${String(key)} with`, args);
            return original.apply(this, args);
        };
    };
}
```

**Decorator execution order** (critical interview point — often tested):

```typescript
@ClassDecoratorA       // 4. runs last
@ClassDecoratorB       // 3. runs third
class MyController {
    @MethodDecoratorA  // 2. runs second
    @MethodDecoratorB  // 1. runs first (closest to the declaration)
    handler(
        @ParamDecoratorA() a: string,  // parameter decorators run before method decorators
        @ParamDecoratorB() b: string   // right-to-left within the parameter list
    ) {}
}
// Execution order: ParamDecoratorB → ParamDecoratorA → MethodDecoratorB → MethodDecoratorA → ClassDecoratorB → ClassDecoratorA
```

**Q2. What metadata keys does NestJS use internally, and how does the framework read them?**
A: NestJS uses a fixed set of metadata keys defined in `@nestjs/common/constants`. Understanding these explains how decorators like `@Get()`, `@UseGuards()`, and `@Roles()` actually work:

```typescript
// Internal NestJS metadata keys (from @nestjs/common/constants):
export const PATH_METADATA = 'path';
export const METHOD_METADATA = 'method';
export const GUARDS_METADATA = '__guards__';
export const INTERCEPTORS_METADATA = '__interceptors__';
export const PIPES_METADATA = '__pipes__';
export const ROLES_METADATA = 'roles';  // custom — you define this
export const ROUTE_ARGS_METADATA = '__routeArguments__';

// How @Get('/users') works internally:
function Get(path: string): MethodDecorator {
    return (target, key, descriptor) => {
        Reflect.defineMetadata(PATH_METADATA, path, descriptor.value);
        Reflect.defineMetadata(METHOD_METADATA, RequestMethod.GET, descriptor.value);
    };
}

// How the NestJS router reads it at bootstrap:
// RouterExplorer scans every method on every controller,
// reads PATH_METADATA + METHOD_METADATA to register express/fastify routes:
const path   = Reflect.getMetadata(PATH_METADATA, method);
const method = Reflect.getMetadata(METHOD_METADATA, method);
router[method](path, handler);
```

**Q3. What are the four types of decorators in TypeScript and which does NestJS use for each purpose?**

```
Decorator type      │ Applies to     │ Signature                                        │ NestJS examples
────────────────────┼────────────────┼──────────────────────────────────────────────────┼────────────────────────────────────
Class decorator     │ Class          │ (target: Function) => void | Function            │ @Controller(), @Injectable(), @Module()
Method decorator    │ Method         │ (target, key, descriptor) => void | descriptor   │ @Get(), @Post(), @UseGuards(), @HttpCode()
Property decorator  │ Property       │ (target, key) => void                            │ @InjectRepository(), @Inject()
Parameter decorator │ Parameter      │ (target, key, parameterIndex) => void            │ @Param(), @Body(), @Query(), @Req(), @Res()
```

## Section 2: Custom Route Decorators

**Q4. How do you compose multiple NestJS decorators into a single custom route decorator using `applyDecorators`?**
A: `applyDecorators` (from `@nestjs/common`) takes a spread of decorators and merges them. It's the primary tool for building composite route decorators that bundle auth, swagger docs, and response types into one:

```typescript
import {
    applyDecorators,
    UseGuards,
    SetMetadata,
    HttpCode,
    HttpStatus,
} from '@nestjs/common';
import { ApiBearerAuth, ApiOperation, ApiResponse } from '@nestjs/swagger';
import { JwtAuthGuard } from '../guards/jwt-auth.guard';
import { RolesGuard } from '../guards/roles.guard';

// Custom metadata key:
export const ROLES_KEY = 'roles';

// Reusable decorator that bundles: auth guard + roles guard + swagger docs
export function AuthenticatedRoute(
    roles: string[],
    summary: string,
    responseType: new (...args: unknown[]) => unknown
) {
    return applyDecorators(
        SetMetadata(ROLES_KEY, roles),   // attach roles metadata for RolesGuard
        UseGuards(JwtAuthGuard, RolesGuard),
        ApiBearerAuth(),
        ApiOperation({ summary }),
        ApiResponse({ status: 200, type: responseType }),
        ApiResponse({ status: 401, description: 'Unauthorized' }),
        ApiResponse({ status: 403, description: 'Forbidden' }),
    );
}

// Usage — replaces 6+ decorators per route with one:
@Controller('loans')
export class LoanController {
    @Get(':id')
    @AuthenticatedRoute(['admin', 'agent'], 'Get loan by ID', LoanResponseDto)
    getLoan(@Param('id') id: string) {
        return this.loanService.findOne(id);
    }
}
```

**Q5. How do you create a custom HTTP method decorator (e.g., `@ApiGet`) that encodes path, response type, and guards in one call?**
A: You compose the HTTP method decorator with Swagger and auth decorators. The key insight: HTTP method decorators (`@Get`, `@Post`) are themselves just wrappers over `Reflect.defineMetadata` — they can be nested inside `applyDecorators` freely:

```typescript
import { applyDecorators, Get, UseGuards } from '@nestjs/common';
import { ApiOperation, ApiResponse, ApiParam } from '@nestjs/swagger';
import { JwtAuthGuard } from '../guards/jwt-auth.guard';

interface ApiGetOptions {
    path?: string;
    summary: string;
    responseType: new (...args: unknown[]) => unknown;
    auth?: boolean;
    paramName?: string;
}

export function ApiGet({
    path = '',
    summary,
    responseType,
    auth = true,
    paramName,
}: ApiGetOptions) {
    const decorators = [
        Get(path),
        ApiOperation({ summary }),
        ApiResponse({ status: 200, type: responseType }),
        ApiResponse({ status: 404, description: 'Not found' }),
    ];

    if (auth) {
        decorators.push(UseGuards(JwtAuthGuard));
    }
    if (paramName) {
        decorators.push(ApiParam({ name: paramName, type: String }));
    }

    return applyDecorators(...decorators);
}

// Usage:
@Controller('users')
export class UserController {
    @ApiGet({ path: ':id', summary: 'Get user by ID', responseType: UserDto, paramName: 'id' })
    getUser(@Param('id') id: string) {
        return this.userService.findOne(id);
    }

    @ApiGet({ path: '', summary: 'List all users', responseType: UserDto, auth: false })
    getUsers() {
        return this.userService.findAll();
    }
}
```

**Q6. What is `SetMetadata` and how do you build a `@Roles` decorator with it?**
A: `SetMetadata(key, value)` is a NestJS utility that creates a decorator which calls `Reflect.defineMetadata(key, value, target, propertyKey)`. It's the building block for all custom metadata-based decorators — `@Roles`, `@Public`, `@Permissions`, etc.:

```typescript
import { SetMetadata } from '@nestjs/common';

export const ROLES_KEY = 'roles';

// Option 1: Direct SetMetadata (simple but less type-safe)
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

// Option 2: Typed enum (preferred for large codebases)
export enum UserRole {
    Admin = 'admin',
    Agent = 'agent',
    Customer = 'customer',
}

export const Roles = (...roles: UserRole[]) => SetMetadata(ROLES_KEY, roles);

// Reading it in a RolesGuard:
import { Injectable, CanActivate, ExecutionContext } from '@nestjs/common';
import { Reflector } from '@nestjs/core';

@Injectable()
export class RolesGuard implements CanActivate {
    constructor(private reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        // Reflector.getAllAndOverride reads metadata from the handler first,
        // then the controller class if not found on the method:
        const requiredRoles = this.reflector.getAllAndOverride<UserRole[]>(ROLES_KEY, [
            context.getHandler(),  // method-level metadata
            context.getClass(),    // class-level metadata (fallback)
        ]);

        if (!requiredRoles || requiredRoles.length === 0) return true;  // No roles = public

        const { user } = context.switchToHttp().getRequest();
        return requiredRoles.some((role) => user?.roles?.includes(role));
    }
}

// Usage:
@Controller('admin')
@Roles(UserRole.Admin)  // class-level: applies to all routes unless overridden
export class AdminController {
    @Get('reports')
    @Roles(UserRole.Admin, UserRole.Agent)  // method-level: overrides class default
    getReports() {}

    @Get('config')
    // Inherits class-level @Roles(UserRole.Admin)
    getConfig() {}
}
```

**Q7. How do you create a `@Public` decorator to bypass global auth guards for specific routes?**
A: The pattern uses a boolean metadata flag that the global guard checks before enforcing auth. This is cleaner than maintaining an allow-list of public routes:

```typescript
// public.decorator.ts
import { SetMetadata } from '@nestjs/common';

export const IS_PUBLIC_KEY = 'isPublic';
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);

// jwt-auth.guard.ts — global guard that respects @Public():
import { Injectable, CanActivate, ExecutionContext } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { JwtService } from '@nestjs/jwt';

@Injectable()
export class JwtAuthGuard implements CanActivate {
    constructor(
        private jwtService: JwtService,
        private reflector: Reflector,
    ) {}

    canActivate(context: ExecutionContext): boolean {
        // Check @Public() on method or class:
        const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
            context.getHandler(),
            context.getClass(),
        ]);

        if (isPublic) return true;  // Skip auth entirely

        const request = context.switchToHttp().getRequest();
        const token = this.extractTokenFromHeader(request);
        if (!token) return false;

        try {
            request.user = this.jwtService.verify(token);
            return true;
        } catch {
            return false;
        }
    }

    private extractTokenFromHeader(request: Request): string | undefined {
        const [type, token] = request.headers['authorization']?.split(' ') ?? [];
        return type === 'Bearer' ? token : undefined;
    }
}

// Register as global guard in AppModule:
providers: [{ provide: APP_GUARD, useClass: JwtAuthGuard }]

// Usage:
@Controller('auth')
export class AuthController {
    @Public()  // bypasses global JwtAuthGuard
    @Post('login')
    login(@Body() loginDto: LoginDto) {}

    @Public()
    @Post('register')
    register(@Body() registerDto: RegisterDto) {}

    @Get('profile')
    // No @Public() → protected by global guard automatically
    getProfile(@Req() req) { return req.user; }
}
```

## Section 3: Parameter Decorators

**Q8. How do you create a custom parameter decorator using `createParamDecorator`?**
A: `createParamDecorator` is a NestJS factory that produces a parameter decorator. It receives the `ExecutionContext` and a `data` argument (whatever was passed to the decorator at call site). The factory function returns the value that will be injected into the route handler parameter:

```typescript
import { createParamDecorator, ExecutionContext } from '@nestjs/common';
import { Request } from 'express';

// Basic custom decorator — extract the current user from req.user:
export const CurrentUser = createParamDecorator(
    (data: unknown, ctx: ExecutionContext) => {
        const request = ctx.switchToHttp().getRequest<Request>();
        return request.user;
    },
);

// Usage:
@Get('profile')
getProfile(@CurrentUser() user: UserEntity) {
    return user;  // user is req.user, typed
}
```

**With a `data` argument** — extract a specific property from the user object:

```typescript
// Type the data parameter to what callers will pass:
export const CurrentUser = createParamDecorator(
    (field: keyof UserEntity | undefined, ctx: ExecutionContext) => {
        const request = ctx.switchToHttp().getRequest<Request>();
        const user = request.user as UserEntity;
        return field ? user?.[field] : user;
    },
);

// Usage variations:
@Get('profile')
getProfile(@CurrentUser() user: UserEntity) {}  // full user object

@Get('id')
getId(@CurrentUser('id') id: string) {}  // just user.id

@Get('email')
getEmail(@CurrentUser('email') email: string) {}  // just user.email
```

**Q9. How do you extract a tenant or org ID from a JWT claim using a custom parameter decorator?**
A: Common pattern in multi-tenant fintech/SaaS apps — the JWT payload has `tenantId`, `orgId`, or similar, and every service layer call needs it without manually reading `req.user.tenantId` everywhere:

```typescript
// tenant.decorator.ts
import { createParamDecorator, ExecutionContext, UnauthorizedException } from '@nestjs/common';

export interface JwtPayload {
    sub: string;
    email: string;
    tenantId: string;
    roles: string[];
}

export const TenantId = createParamDecorator(
    (data: unknown, ctx: ExecutionContext): string => {
        const request = ctx.switchToHttp().getRequest();
        const user = request.user as JwtPayload;

        if (!user?.tenantId) {
            throw new UnauthorizedException('Tenant context missing from token');
        }

        return user.tenantId;
    },
);

// Usage:
@Controller('loans')
export class LoanController {
    @Get()
    findAll(@TenantId() tenantId: string) {
        // tenantId is validated and extracted — no manual req.user parsing
        return this.loanService.findAllByTenant(tenantId);
    }

    @Post()
    create(@TenantId() tenantId: string, @Body() dto: CreateLoanDto) {
        return this.loanService.create(tenantId, dto);
    }
}
```

**Q10. How do you add pipe validation to a custom parameter decorator?**
A: Custom parameter decorators can accept pipes as additional arguments (same as built-in `@Param()`, `@Body()`). NestJS will run the pipe on the value returned by the decorator factory before injecting it:

```typescript
import { createParamDecorator, ExecutionContext, ParseIntPipe, ParseUUIDPipe } from '@nestjs/common';

export const LoanId = createParamDecorator(
    (data: unknown, ctx: ExecutionContext): string => {
        const request = ctx.switchToHttp().getRequest();
        return request.params.loanId;
    },
);

// Usage with built-in pipes:
@Get(':loanId')
getLoan(@LoanId(new ParseUUIDPipe({ version: '4' })) loanId: string) {
    // loanId is validated as UUID before this runs
    return this.loanService.findById(loanId);
}

// Custom validation pipe for domain-specific logic:
import { PipeTransform, Injectable, BadRequestException } from '@nestjs/common';

@Injectable()
export class LoanIdFormatPipe implements PipeTransform<string> {
    transform(value: string): string {
        // LAN-XXXXXXXX format validation
        if (!/^LAN-[A-Z0-9]{8}$/.test(value)) {
            throw new BadRequestException(`Invalid loan ID format: ${value}`);
        }
        return value;
    }
}

// Apply custom pipe inline:
@Get(':loanId')
getLoan(@LoanId(new LoanIdFormatPipe()) loanId: string) {}

// Or apply it at module level for reuse:
@Get(':loanId')
getLoan(@LoanId(LoanIdFormatPipe) loanId: string) {}
// NestJS instantiates class-based pipes via DI when passed as a class (not instance)
```

**Q11. How do you extract headers or cookies cleanly with a custom parameter decorator?**
A: Built-in `@Headers()` and `@Query()` exist but are loosely typed. Custom decorators provide typed, named extraction with optional transformation:

```typescript
import { createParamDecorator, ExecutionContext } from '@nestjs/common';

// Extract a specific header with a typed default:
export const Header = (headerName: string) =>
    createParamDecorator(
        (_data: unknown, ctx: ExecutionContext): string | undefined => {
            const request = ctx.switchToHttp().getRequest();
            return request.headers[headerName.toLowerCase()];
        },
    )();

// Cleaner: parameterized factory pattern
export const RequestHeader = createParamDecorator(
    (headerName: string, ctx: ExecutionContext): string | undefined => {
        const request = ctx.switchToHttp().getRequest();
        return request.headers[headerName.toLowerCase()];
    },
);

// Typed cookie extractor:
export const Cookie = createParamDecorator(
    (cookieName: string, ctx: ExecutionContext): string | undefined => {
        const request = ctx.switchToHttp().getRequest();
        return request.cookies?.[cookieName];
    },
);

// Trace/correlation ID decorator (common in distributed systems):
export const CorrelationId = createParamDecorator(
    (_data: unknown, ctx: ExecutionContext): string => {
        const request = ctx.switchToHttp().getRequest();
        return (
            request.headers['x-correlation-id'] ||
            request.headers['x-request-id'] ||
            crypto.randomUUID()
        );
    },
);

// Usage:
@Get('data')
getData(
    @RequestHeader('x-api-version') apiVersion: string,
    @Cookie('session_token') sessionToken: string,
    @CorrelationId() correlationId: string,
) {
    this.logger.log(`Request ${correlationId} — API v${apiVersion}`);
}
```

## Section 4: Advanced Patterns

**Q12. How do you use `Reflector` to read metadata set by decorators, and what is the difference between `get`, `getAllAndMerge`, and `getAllAndOverride`?**
A: `Reflector` is the NestJS service for reading metadata from decorators. The three methods handle different inheritance scenarios:

```typescript
import { Reflector } from '@nestjs/core';

@Injectable()
export class PermissionGuard implements CanActivate {
    constructor(private reflector: Reflector) {}

    canActivate(ctx: ExecutionContext): boolean {
        // Reflector.get — reads metadata from ONE target (handler or class, not both):
        const handlerRoles = this.reflector.get<string[]>('roles', ctx.getHandler());
        // If handler has no metadata, returns undefined (does NOT fall back to class)

        // Reflector.getAllAndOverride — reads from handler FIRST, class as fallback:
        // Use when method-level should completely override class-level
        const roles = this.reflector.getAllAndOverride<string[]>('roles', [
            ctx.getHandler(),  // checked first
            ctx.getClass(),    // fallback if handler has no metadata
        ]);

        // Reflector.getAllAndMerge — reads from BOTH handler and class, merges arrays:
        // Use when you want UNION of method and class metadata (e.g., all required permissions)
        const permissions = this.reflector.getAllAndMerge<string[]>('permissions', [
            ctx.getHandler(),
            ctx.getClass(),
        ]);
        // If class has ['read'] and handler has ['write'], result is ['read', 'write']

        //            │ Handler only │ Class only │ Both defined │ Neither
        // ───────────┼──────────────┼────────────┼──────────────┼──────────
        // get        │ handler val  │ undefined  │ handler val  │ undefined
        // Override   │ handler val  │ class val  │ handler val  │ undefined
        // Merge      │ handler val  │ class val  │ merged array │ []

        return true;
    }
}
```

**Q13. How do you create a decorator that works differently based on the execution context (HTTP vs WebSocket vs gRPC)?**
A: `ExecutionContext` has type-safe context switching. Custom decorators using `createParamDecorator` should handle multiple context types:

```typescript
import { createParamDecorator, ExecutionContext } from '@nestjs/common';

export const User = createParamDecorator(
    (field: string | undefined, ctx: ExecutionContext) => {
        const contextType = ctx.getType<'http' | 'ws' | 'rpc'>();

        let user: unknown;

        switch (contextType) {
            case 'http': {
                const request = ctx.switchToHttp().getRequest();
                user = request.user;
                break;
            }
            case 'ws': {
                // WebSocket — user attached to client handshake data
                const client = ctx.switchToWs().getClient();
                user = client.handshake?.auth?.user ?? client.data?.user;
                break;
            }
            case 'rpc': {
                // gRPC / microservice — user in metadata
                const rpcData = ctx.switchToRpc().getData();
                user = rpcData?.user;
                break;
            }
            default:
                return null;
        }

        return field ? (user as Record<string, unknown>)?.[field] : user;
    },
);

// Works identically across all transports:
// HTTP controller:
@Get('profile')
getProfile(@User() user: UserEntity) {}

// WebSocket gateway:
@SubscribeMessage('profile')
handleProfile(@User() user: UserEntity) {}

// gRPC controller:
@GrpcMethod('UserService', 'GetProfile')
getProfile(@User() user: UserEntity) {}
```

**Q14. How do you create a decorator that logs method calls and response times?**
A: Method decorators can wrap the original function. For async methods, return the wrapped promise; for sync, return the value:

```typescript
import { Logger } from '@nestjs/common';

export function LogExecution(label?: string): MethodDecorator {
    return (
        target: object,
        propertyKey: string | symbol,
        descriptor: PropertyDescriptor,
    ) => {
        const originalMethod = descriptor.value as (...args: unknown[]) => unknown;
        const logger = new Logger(target.constructor.name);
        const methodLabel = label ?? String(propertyKey);

        descriptor.value = async function (...args: unknown[]) {
            const start = Date.now();
            logger.log(`→ ${methodLabel} called`);

            try {
                const result = await originalMethod.apply(this, args);
                const elapsed = Date.now() - start;
                logger.log(`← ${methodLabel} completed in ${elapsed}ms`);
                return result;
            } catch (err) {
                const elapsed = Date.now() - start;
                logger.error(`✗ ${methodLabel} failed after ${elapsed}ms`, (err as Error).stack);
                throw err;
            }
        };

        return descriptor;
    };
}

// Usage:
@Controller('loans')
export class LoanController {
    @Get(':id')
    @LogExecution('getLoan')
    async getLoan(@Param('id') id: string) {
        return this.loanService.findOne(id);
    }
}

// Combining with applyDecorators for a route-level all-in-one:
export function TracedGet(path: string) {
    return applyDecorators(
        Get(path),
        LogExecution(),
    );
}
```

**Q15. How do you implement a decorator that throttles specific routes independently of the global throttler?**
A: NestJS's `@nestjs/throttler` uses metadata decorators internally. You can compose custom throttle configuration per route:

```typescript
import { applyDecorators, UseGuards } from '@nestjs/common';
import { Throttle, ThrottlerGuard } from '@nestjs/throttler';
import { SkipThrottle } from '@nestjs/throttler';

// Strict throttle for sensitive endpoints (e.g., OTP, login):
export function StrictRateLimit() {
    return applyDecorators(
        Throttle({ default: { limit: 3, ttl: 60000 } }),  // 3 requests/minute
    );
}

// Relaxed throttle for public data endpoints:
export function RelaxedRateLimit() {
    return applyDecorators(
        Throttle({ default: { limit: 100, ttl: 60000 } }),  // 100 requests/minute
    );
}

// Skip global throttler for internal health checks:
export function InternalRoute() {
    return applyDecorators(
        SkipThrottle(),
        SetMetadata('internal', true),
    );
}

// Usage:
@Controller('auth')
export class AuthController {
    @StrictRateLimit()
    @Post('otp/send')
    sendOtp(@Body() dto: SendOtpDto) {}

    @StrictRateLimit()
    @Post('login')
    login(@Body() loginDto: LoginDto) {}

    @InternalRoute()
    @Get('health')
    health() { return { status: 'ok' }; }
}
```

## Section 5: Testing Decorators

**Q16. How do you unit test a custom parameter decorator?**
A: The `createParamDecorator` factory function is just a function. Test the factory directly by mocking `ExecutionContext`:

```typescript
// current-user.decorator.spec.ts
import { ExecutionContext } from '@nestjs/common';
import { ROUTE_ARGS_METADATA } from '@nestjs/common/constants';
import { CurrentUser } from './current-user.decorator';
import { UserController } from './user.controller';

// Helper to extract the factory function from a parameter decorator:
function getParamDecoratorFactory(decorator: Function) {
    class TestController {
        test(@decorator() _value: unknown) {}
    }
    const metadata = Reflect.getMetadata(ROUTE_ARGS_METADATA, TestController, 'test');
    return Object.values(metadata)[0] as { factory: Function };
}

describe('CurrentUser decorator', () => {
    it('should return the full user when no field specified', () => {
        const mockUser = { id: '123', email: 'test@test.com', roles: ['admin'] };

        const mockContext = {
            switchToHttp: () => ({
                getRequest: () => ({ user: mockUser }),
            }),
            getType: () => 'http',
        } as unknown as ExecutionContext;

        // Direct invocation of factory logic:
        const factory = (field: string | undefined, ctx: ExecutionContext) => {
            const request = ctx.switchToHttp().getRequest();
            return field ? request.user[field] : request.user;
        };

        expect(factory(undefined, mockContext)).toEqual(mockUser);
        expect(factory('email', mockContext)).toBe('test@test.com');
    });

    it('should return undefined when user is not set', () => {
        const mockContext = {
            switchToHttp: () => ({
                getRequest: () => ({}),  // no user
            }),
        } as unknown as ExecutionContext;

        const factory = (field: string | undefined, ctx: ExecutionContext) => {
            const request = ctx.switchToHttp().getRequest();
            return field ? request.user?.[field] : request.user;
        };

        expect(factory(undefined, mockContext)).toBeUndefined();
        expect(factory('email', mockContext)).toBeUndefined();
    });
});
```

## Section 6: Scenario-Based Questions

**Q18. "You have 40+ controller routes and each one manually has `@UseGuards(JwtAuthGuard, RolesGuard)`, `@ApiBearerAuth()`, and `@ApiResponse({ status: 401 })`. How do you reduce this boilerplate?"**
A: Three layers of consolidation:

```typescript
// Layer 1: composite decorator for authenticated routes
export const Auth = (...roles: UserRole[]) =>
    applyDecorators(
        roles.length ? SetMetadata(ROLES_KEY, roles) : SetMetadata(IS_PUBLIC_KEY, false),
        UseGuards(JwtAuthGuard, RolesGuard),
        ApiBearerAuth(),
        ApiResponse({ status: 401, description: 'Unauthorized' }),
        ApiResponse({ status: 403, description: 'Forbidden' }),
    );

// Layer 2: composite HTTP method decorators
export const AuthGet = (path: string, ...roles: UserRole[]) =>
    applyDecorators(Get(path), Auth(...roles));

export const AuthPost = (path: string, ...roles: UserRole[]) =>
    applyDecorators(Post(path), Auth(...roles));

// Layer 3: move guard to controller class (covers all methods by default)
@Controller('loans')
@Auth(UserRole.Agent, UserRole.Admin)  // class-level — all routes require this
export class LoanController {
    @AuthGet(':id')  // inherits class auth, just adds HTTP method + path
    getLoan(@Param('id') id: string) {}

    @AuthPost('')
    @Roles(UserRole.Admin)  // method-level override — stricter than class default
    createLoan(@Body() dto: CreateLoanDto) {}
}
```

**Q19. "A junior dev reports that `@CurrentUser()` returns `undefined` in a controller protected by a global `JwtAuthGuard`. After verifying the guard runs, what do you check?"**
A: Methodical diagnosis:

```typescript
// Checklist:
// 1. Is the guard actually setting req.user?
@Injectable()
export class JwtAuthGuard implements CanActivate {
    canActivate(ctx: ExecutionContext) {
        const request = ctx.switchToHttp().getRequest();
        const payload = this.jwtService.verify(token);
        request.user = payload;          // ← must be 'user', not 'currentUser' or 'auth'
        return true;
    }
}

// 2. Is the decorator reading from the right property?
export const CurrentUser = createParamDecorator(
    (_data, ctx: ExecutionContext) => {
        const req = ctx.switchToHttp().getRequest();
        console.log('req.user:', req.user);  // add temporary debug log
        return req.user;                     // must match what guard sets
    },
);

// 3. Is there a Passport strategy wrapping the guard?
// passport.js sets req.user via the 'done(null, user)' callback
// Ensure super.canActivate(context) is called if extending AuthGuard:
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
    canActivate(context: ExecutionContext) {
        return super.canActivate(context);  // this runs passport strategy + sets req.user
    }
}

// 4. Is the guard registered correctly as global?
// In AppModule providers:
{ provide: APP_GUARD, useClass: JwtAuthGuard }  // correct — DI-aware global guard
// NOT: app.useGlobalGuards(new JwtAuthGuard())  // wrong — not DI-aware, can't inject services

// 5. Guard execution order — if multiple global guards:
// APP_GUARD providers run in the order they are registered
// JwtAuthGuard must run before RolesGuard so req.user is populated first:
providers: [
    { provide: APP_GUARD, useClass: JwtAuthGuard },   // first
    { provide: APP_GUARD, useClass: RolesGuard },      // second
]
```

**Q20. "You need a `@CacheResponse(ttl: number)` decorator that caches GET route responses in Redis. Design it end-to-end."**
A: The pattern uses a method decorator to set TTL metadata, a custom interceptor to read it and handle cache logic:

```typescript
// cache-response.decorator.ts
import { SetMetadata, UseInterceptors, applyDecorators } from '@nestjs/common';
import { CacheInterceptor } from './cache.interceptor';

export const CACHE_TTL_KEY = 'cacheTtl';

export function CacheResponse(ttlSeconds: number) {
    return applyDecorators(
        SetMetadata(CACHE_TTL_KEY, ttlSeconds),
        UseInterceptors(CacheInterceptor),
    );
}

// cache.interceptor.ts
import {
    Injectable,
    NestInterceptor,
    ExecutionContext,
    CallHandler,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { Observable, of, tap } from 'rxjs';
import { RedisService } from '../redis/redis.service';

@Injectable()
export class CacheInterceptor implements NestInterceptor {
    constructor(
        private redis: RedisService,
        private reflector: Reflector,
    ) {}

    async intercept(ctx: ExecutionContext, next: CallHandler): Promise<Observable<unknown>> {
        const request = ctx.switchToHttp().getRequest();

        // Only cache GET requests:
        if (request.method !== 'GET') return next.handle();

        const ttl = this.reflector.getAllAndOverride<number>(CACHE_TTL_KEY, [
            ctx.getHandler(),
            ctx.getClass(),
        ]);

        if (!ttl) return next.handle();

        // Build cache key from URL + query:
        const cacheKey = `response:${request.url}`;

        const cached = await this.redis.get(cacheKey);
        if (cached) {
            return of(JSON.parse(cached));  // Short-circuit: return cached response
        }

        // Not cached — execute handler, then cache the result:
        return next.handle().pipe(
            tap(async (response) => {
                await this.redis.setex(cacheKey, ttl, JSON.stringify(response));
            }),
        );
    }
}

// Usage:
@Controller('products')
export class ProductController {
    @Get()
    @CacheResponse(300)  // cache for 5 minutes
    findAll() {
        return this.productService.findAll();
    }

    @Get(':id')
    @CacheResponse(60)   // cache for 1 minute
    findOne(@Param('id') id: string) {
        return this.productService.findOne(id);
    }

    @Post()
    // No @CacheResponse → not cached, not intercepted
    create(@Body() dto: CreateProductDto) {
        return this.productService.create(dto);
    }
}
```

## Quick Reference Table

| Decorator utility | Purpose | Example |
|---|---|---|
| `SetMetadata(key, value)` | Attach arbitrary metadata to handler or class | `@Roles('admin')` |
| `applyDecorators(...d)` | Compose multiple decorators into one | `@Auth()`, `@ApiGet()` |
| `createParamDecorator(factory)` | Create a parameter decorator that extracts request data | `@CurrentUser()`, `@TenantId()` |
| `Reflector.get(key, target)` | Read metadata from one target | Single-level metadata read |
| `Reflector.getAllAndOverride(key, targets)` | Read from handler first, class as fallback | Roles, permissions |
| `Reflector.getAllAndMerge(key, targets)` | Union metadata from handler + class | Permission sets |
| `UseGuards(...guards)` | Apply guards to a class or method | `@UseGuards(JwtAuthGuard)` |
| `UseInterceptors(...i)` | Apply interceptors to a class or method | `@UseInterceptors(CacheInterceptor)` |

| Pattern | When to use |
|---|---|
| `applyDecorators` composite | Reduce boilerplate across many routes (auth + swagger + http method) |
| `SetMetadata` + `Reflector` | Any metadata-driven guard or interceptor (`@Roles`, `@Public`, `@CacheResponse`) |
| `createParamDecorator` | Typed extraction from request (`@CurrentUser`, `@TenantId`, `@CorrelationId`) |
| Class-level decorators | Defaults that apply to all routes in a controller (`@Auth()` on controller class) |
| `APP_GUARD` provider | Global guards with DI support (preferred over `app.useGlobalGuards()`) |
| Method decorator wrapping | Cross-cutting concerns on specific methods (`@LogExecution`, `@Throttle`) |

---

**Tip for interviews:** Five things separate strong candidates on NestJS decorators: (1) knowing that **`applyDecorators` is for composition** (Q4, Q5) — not manually stacking 6 decorators per route, but understanding how to bundle auth + Swagger + method into one reusable decorator; (2) understanding the **`SetMetadata` + `Reflector` pair** (Q6, Q7, Q12) — the foundation of every metadata-driven feature in NestJS, and knowing when to use `getAllAndOverride` vs `getAllAndMerge` and why they differ; (3) being fluent with **`createParamDecorator`** (Q8, Q9, Q10) — including passing a `data` argument for field extraction, and composing it with pipes for validation; (4) knowing the **global guard registration pattern** using `APP_GUARD` provider (Q19) — not `app.useGlobalGuards(new Guard())` which bypasses DI; and (5) understanding **decorator execution order** (Q1) — parameter decorators run before method decorators, and method decorators run bottom-up, which affects when metadata is available and how stacking works in practice.
