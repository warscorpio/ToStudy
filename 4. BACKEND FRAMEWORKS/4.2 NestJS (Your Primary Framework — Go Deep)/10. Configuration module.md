# Configuration Module: `@nestjs/config`, Environment Validation with Joi/Zod — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problems does `@nestjs/config` solve over reading `process.env` directly?**

A: Reading `process.env.DATABASE_URL` directly in a service creates four compounding problems that `@nestjs/config` addresses:

**Problem 1 — No validation at startup.** If `DATABASE_URL` is missing, the error surfaces as a runtime crash on first use — potentially minutes into a request handler after all other startup work has completed. Config validation should be the first thing that fails, loudly and immediately.

**Problem 2 — No type safety.** Every `process.env` value is `string | undefined`. You litter the codebase with non-null assertions (`process.env.PORT!`) or silent coercions (`Number(process.env.PORT)`) that carry no type guarantees.

**Problem 3 — Global coupling.** Services that read `process.env` directly are impossible to unit test without manipulating the global process environment — which is shared across all parallel test runs.

**Problem 4 — No namespacing or structure.** A large application accumulates dozens of environment variables. Without structure, it becomes unclear which variables belong to which subsystem, and sharing or reusing config across modules requires re-reading and re-validating the same raw strings.

```typescript
// BEFORE — scattered, unsafe, untestable:
@Injectable()
export class DatabaseService {
  connect() {
    const url = process.env.DATABASE_URL;    // string | undefined — no validation
    const poolSize = Number(process.env.DB_POOL_SIZE);  // NaN if missing — silent bug
    return createConnection(url!, poolSize);  // ! is a lie if URL is missing
  }
}

// AFTER — validated at startup, typed, injectable, testable:
@Injectable()
export class DatabaseService {
  constructor(private readonly config: ConfigService) {}

  connect() {
    const url = this.config.getOrThrow<string>('database.url');    // throws at startup if missing
    const pool = this.config.get<number>('database.poolSize', 10); // typed with default
    return createConnection(url, pool);
  }
}
```

**Q2. What are all the options for `ConfigModule.forRoot()` and what does each control?**

A:

```typescript
import { ConfigModule } from '@nestjs/config';
import * as Joi from 'joi';

ConfigModule.forRoot({
  // ── Module scope ─────────────────────────────────────────────────────────
  isGlobal: true,
  // Makes ConfigModule a global module — ConfigService injectable everywhere
  // without importing ConfigModule in each feature module.
  // Default: false

  // ── .env file loading ─────────────────────────────────────────────────────
  envFilePath: ['.env.local', '.env'],
  // Path(s) to .env files — loaded left-to-right; first definition wins.
  // Default: '.env'

  ignoreEnvFile: process.env.NODE_ENV === 'production',
  // Skip loading .env files — use when env vars are injected by the platform
  // (Kubernetes, ECS, AWS Lambda). Prevents accidental override of platform vars.
  // Default: false

  // ── Variable expansion ────────────────────────────────────────────────────
  expandVariables: true,
  // Enables ${VAR} interpolation in .env files:
  //   DB_HOST=localhost
  //   DB_PORT=5432
  //   DATABASE_URL=${DB_HOST}:${DB_PORT}/myapp
  // Default: false

  // ── Validation ───────────────────────────────────────────────────────────
  validationSchema: Joi.object({
    PORT: Joi.number().default(3000),
    DATABASE_URL: Joi.string().required(),
  }),
  // Joi schema — validated before the module initializes.
  // Mutually exclusive with `validate`.

  validationOptions: {
    abortEarly: false,      // Report ALL violations, not just the first. Default: true
    allowUnknown: true,     // Allow env vars not listed in schema. Default: true
    stripUnknown: false,    // Remove vars not in schema from the config object. Default: false
  },

  validate: (config: Record<string, unknown>) => {
    // Custom validation function — receives the raw merged config object.
    // Must return the (possibly transformed) config or throw.
    // Use this for Zod or any non-Joi validator. Mutually exclusive with validationSchema.
    return zodSchema.parse(config);
  },

  // ── Custom config factories ───────────────────────────────────────────────
  load: [databaseConfig, authConfig, emailConfig],
  // Array of factory functions (from registerAs()) that contribute
  // namespaced config objects. Loaded after .env files are parsed.

  // ── Performance ───────────────────────────────────────────────────────────
  cache: true,
  // Caches configService.get() results. Useful when config is accessed
  // frequently in hot paths (e.g., per-request middleware).
  // Default: false

  // ── Advanced ─────────────────────────────────────────────────────────────
  ignoreEnvVars: false,
  // If true, ignores process.env entirely — only uses values from `load` functions.
  // Useful for fully code-defined configuration with no env dependency.
  // Default: false
});
```

## Section 2: Basic Setup and ConfigService

**Q3. How do you set up `ConfigModule` and use `ConfigService` in a feature module?**

A:

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal:    true,    // Available in all modules — no per-module import needed
      envFilePath: '.env',
    }),
    UsersModule,
    OrdersModule,
  ],
})
export class AppModule {}
```

```typescript
// users.service.ts — ConfigService injected without importing ConfigModule
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';

@Injectable()
export class UsersService {
  constructor(private readonly config: ConfigService) {}

  getJwtSecret(): string {
    return this.config.getOrThrow<string>('JWT_SECRET');
  }

  getDatabaseUrl(): string {
    return this.config.getOrThrow<string>('DATABASE_URL');
  }

  getPort(): number {
    return this.config.get<number>('PORT', 3000);  // 3000 is the fallback
  }
}
```

```typescript
// users.module.ts — no ConfigModule import needed because isGlobal: true
@Module({
  providers: [UsersService],
  controllers: [UsersController],
})
export class UsersModule {}
```

**Without `isGlobal: true`** — each module that needs `ConfigService` must import `ConfigModule`:

```typescript
@Module({
  imports: [ConfigModule],   // Must import in every module that uses ConfigService
  providers: [UsersService],
})
export class UsersModule {}
```

The right choice depends on your team's preferences: `isGlobal: true` reduces boilerplate; explicit per-module imports make dependencies visible.

**Q4. What is the difference between `configService.get()`, `configService.getOrThrow()`, and generic typing?**

A:

```typescript
import { ConfigService } from '@nestjs/config';

@Injectable()
export class AppService {
  constructor(private readonly config: ConfigService) {}

  demonstrateMethods() {
    // ── get<T>(key, defaultValue?) ───────────────────────────────────────────
    const port = this.config.get<number>('PORT');
    // Return type: number | undefined
    // Returns undefined if the key doesn't exist (no default provided)

    const port2 = this.config.get<number>('PORT', 3000);
    // Return type: number
    // Returns 3000 if PORT is not set — default prevents undefined

    const nested = this.config.get<string>('database.host');
    // Dot-notation accesses nested config from registerAs() namespaces

    // ── getOrThrow<T>(key) ───────────────────────────────────────────────────
    const secret = this.config.getOrThrow<string>('JWT_SECRET');
    // Return type: string (never undefined)
    // Throws ConfigNotFoundException if key doesn't exist:
    // Error: Configuration key "JWT_SECRET" does not exist

    // ── Why getOrThrow() is better than get()! ───────────────────────────────
    // UNSAFE: non-null assertion — silently wrong if JWT_SECRET is missing
    const unsafeSecret = this.config.get<string>('JWT_SECRET')!;

    // SAFE: getOrThrow — throws at the point of access with a clear error
    const safeSecret = this.config.getOrThrow<string>('JWT_SECRET');

    // ── Typed ConfigService (flat config only) ───────────────────────────────
    // TypeScript generics on ConfigService itself:
    interface AppEnvironment {
      PORT:         number;
      DATABASE_URL: string;
      JWT_SECRET:   string;
    }

    // Inject ConfigService<AppEnvironment> — get() return type is inferred
    // But this only works reliably for flat (non-namespaced) config
  }
}
```

```typescript
// Fully typed ConfigService injection:
@Injectable()
export class TypedService {
  constructor(
    private readonly config: ConfigService<{
      PORT:         number;
      DATABASE_URL: string;
      JWT_SECRET:   string;
    }, true>    // ← second generic 'true' = WasValidated (enables inference for getOrThrow)
  ) {}

  example() {
    // TypeScript infers return type as number without explicit <number>:
    const port = this.config.getOrThrow('PORT');   // type: number
    const url  = this.config.getOrThrow('DATABASE_URL');  // type: string
    const bad  = this.config.getOrThrow('UNKNOWN_KEY');   // TypeScript error: key not in type
  }
}
```

## Section 3: Validation with Joi

**Q5. How do you validate environment variables with Joi using `validationSchema`?**

A:

```typescript
// Install: npm install joi
import * as Joi from 'joi';
import { ConfigModule } from '@nestjs/config';

const validationSchema = Joi.object({
  // ── Application ──────────────────────────────────────────────────────────
  NODE_ENV: Joi.string()
    .valid('development', 'production', 'test', 'staging')
    .default('development'),

  PORT: Joi.number()
    .integer()
    .min(1)
    .max(65535)
    .default(3000),

  // ── Database ──────────────────────────────────────────────────────────────
  DATABASE_URL: Joi.string()
    .uri({ scheme: ['postgres', 'postgresql'] })
    .required(),

  DB_POOL_MIN: Joi.number().integer().min(0).default(2),
  DB_POOL_MAX: Joi.number().integer().min(1).default(10)
    .greater(Joi.ref('DB_POOL_MIN')),   // Cross-field validation: max > min

  // ── Auth ──────────────────────────────────────────────────────────────────
  JWT_SECRET: Joi.string()
    .min(32)
    .required()
    .messages({
      'string.min': 'JWT_SECRET must be at least 32 characters for security',
    }),

  JWT_EXPIRES_IN: Joi.string()
    .pattern(/^\d+[smhd]$/)   // e.g., 15m, 7d, 24h, 3600s
    .default('7d'),

  // ── External services ─────────────────────────────────────────────────────
  REDIS_URL: Joi.string()
    .uri({ scheme: ['redis', 'rediss'] })
    .when('NODE_ENV', {
      is:   Joi.string().valid('production', 'staging'),
      then: Joi.required(),    // Required in production but optional in development
    }),

  SMTP_HOST: Joi.string().hostname().required(),
  SMTP_PORT: Joi.number().integer().valid(25, 465, 587, 2525).default(587),
  SMTP_USER: Joi.string().required(),
  SMTP_PASS: Joi.string().required(),
});

// app.module.ts:
ConfigModule.forRoot({
  validationSchema,
  validationOptions: {
    abortEarly:    false,   // IMPORTANT: see all errors at once, not just the first
    allowUnknown:  true,    // Allow CI-injected vars (CI_COMMIT_SHA, etc.) not in schema
  },
})

// When NODE_ENV=production and DATABASE_URL is missing, startup fails with:
// Error: Config validation error:
//   "DATABASE_URL" is required
//   "JWT_SECRET" length must be at least 32 characters long
//   "REDIS_URL" is required
// (abortEarly:false shows all errors simultaneously)
```

**Q6. What do `abortEarly` and `allowUnknown` do and what are the correct values for a production app?**

A:

```typescript
// abortEarly: true (Joi's DEFAULT — wrong for config validation)
// Stops at the FIRST validation failure and throws.
// Problem: you fix one error, restart, discover the next error, fix it, repeat.
// A server restart cycle per error is painful in production deployments.

// abortEarly: false (RECOMMENDED for config)
// Collects ALL failures and reports them together.
// Fix all environment variable issues before the next restart.

// allowUnknown: true (RECOMMENDED for config)
// Variables not in your Joi schema are permitted (just ignored).
// Without it: CI systems inject variables like CI=true, GITHUB_ACTIONS=true,
// HOME=/root, LANG=en_US.UTF-8 — your validation would reject all of these.
// Joi's default for object validation is allowUnknown: false, but
// @nestjs/config sets it to true by default for validationOptions.

// stripUnknown: false (DEFAULT — usually leave this alone)
// If true, removes variables not in the schema from the config object.
// Use with caution — process.env itself is not modified, but the config
// object that ConfigService reads from would lose unlisted variables.

// Recommended production validationOptions:
validationOptions: {
  abortEarly:   false,   // See all errors at once
  allowUnknown: true,    // Permit CI/platform variables not in schema
}
```

## Section 4: Validation with Zod

**Q7. How do you validate environment variables with Zod using the `validate` function?**

A: Zod uses the `validate` option in `forRoot()` — a function that receives the raw merged environment object and must return the validated (and optionally coerced) config or throw:

```typescript
// Install: npm install zod
import { z, ZodError } from 'zod';
import { ConfigModule } from '@nestjs/config';

const envSchema = z.object({
  NODE_ENV: z
    .enum(['development', 'production', 'test', 'staging'])
    .default('development'),

  PORT: z.coerce
    .number()         // z.coerce converts the string "3000" to the number 3000
    .int()
    .min(1)
    .max(65535)
    .default(3000),

  DATABASE_URL: z
    .string()
    .url()
    .startsWith('postgres'),

  DB_POOL_MIN: z.coerce.number().int().min(0).default(2),
  DB_POOL_MAX: z.coerce.number().int().min(1).default(10),

  JWT_SECRET: z
    .string()
    .min(32, 'JWT_SECRET must be at least 32 characters'),

  JWT_EXPIRES_IN: z
    .string()
    .regex(/^\d+[smhd]$/, 'Must be a duration like 15m, 7d, 24h')
    .default('7d'),

  REDIS_URL: z
    .string()
    .url()
    .optional(),

  SMTP_HOST: z.string().min(1),
  SMTP_PORT: z.coerce.number().int().default(587),
  SMTP_USER: z.string().min(1),
  SMTP_PASS: z.string().min(1),
}).refine(
  (data) => data.DB_POOL_MAX > data.DB_POOL_MIN,
  { message: 'DB_POOL_MAX must be greater than DB_POOL_MIN', path: ['DB_POOL_MAX'] }
);

// Export the inferred TypeScript type — use this throughout the app
export type Env = z.infer<typeof envSchema>;
// {
//   NODE_ENV:       'development' | 'production' | 'test' | 'staging';
//   PORT:           number;
//   DATABASE_URL:   string;
//   DB_POOL_MIN:    number;
//   DB_POOL_MAX:    number;
//   JWT_SECRET:     string;
//   JWT_EXPIRES_IN: string;
//   REDIS_URL?:     string;
//   SMTP_HOST:      string;
//   SMTP_PORT:      number;
//   SMTP_USER:      string;
//   SMTP_PASS:      string;
// }

// The validate function wired into ConfigModule:
export function validateEnv(config: Record<string, unknown>): Env {
  const result = envSchema.safeParse(config);

  if (!result.success) {
    // Format all ZodErrors into a readable startup message:
    const errors = result.error.errors.map(
      e => `  ${e.path.join('.')}: ${e.message}`
    ).join('\n');
    throw new Error(`Configuration validation failed:\n${errors}`);
  }

  return result.data;  // Coerced and fully typed
}

// app.module.ts:
ConfigModule.forRoot({
  validate: validateEnv,
  // validationSchema must NOT be used alongside validate — they're mutually exclusive
})
```

**Q8. Why does Zod's `z.coerce` matter for environment variables, and what happens without it?**

A: All environment variables — whether from `.env` files or `process.env` — are **strings**. Schemas that expect numbers or booleans must explicitly convert them. Zod and Joi handle this differently:

```typescript
// process.env.PORT is always "3000" — a string, never a number

// ── Zod WITHOUT z.coerce ──────────────────────────────────────────────────
const schema = z.object({
  PORT: z.number(),  // Expects a JS number at runtime
});
schema.parse({ PORT: process.env.PORT });
// ZodError: Expected number, received string
// — crashes even when PORT is correctly set to "3000"

// ── Zod WITH z.coerce ─────────────────────────────────────────────────────
const schema = z.object({
  PORT: z.coerce.number(),  // Calls Number("3000") = 3000
});
schema.parse({ PORT: '3000' });       // { PORT: 3000 } — number ✓
schema.parse({ PORT: '' });            // ZodError: NaN is not a number
schema.parse({ PORT: 'abc' });         // ZodError: Expected number, received nan

// ── Boolean coercion ──────────────────────────────────────────────────────
// process.env.ENABLE_CACHE = "true" (string)
ENABLE_CACHE: z.coerce.boolean(),
// z.coerce.boolean() calls Boolean("true") = true (all non-empty strings are truthy!)
// This is WRONG for booleans — "false" becomes true because Boolean("false") = true

// Correct boolean from env:
ENABLE_CACHE: z.string()
  .transform(val => val === 'true' || val === '1')
// OR use a preprocessing step:
ENABLE_CACHE: z.preprocess(
  val => val === 'true' || val === '1' || val === 'yes',
  z.boolean()
),

// ── Joi coercion (for comparison) ─────────────────────────────────────────
// Joi.number() automatically coerces strings to numbers by default
PORT: Joi.number().default(3000),
// Joi handles "3000" → 3000 without z.coerce — slightly more ergonomic here
```

## Section 5: Joi vs Zod

**Q9. What are the practical differences between Joi and Zod for config validation, and when do you choose each?**

A:

| Concern | Joi | Zod |
|---|---|---|
| NestJS integration | First-class via `validationSchema` | Via `validate` function wrapper |
| TypeScript inference | Limited — inferred types are loose | Precise via `z.infer<typeof schema>` |
| Coercion behavior | Auto-coerces strings (convenient) | Explicit via `z.coerce.*` |
| Boolean from string | `Joi.boolean()` — coerces `'true'` → true | `z.coerce.boolean()` treats any non-empty string as true — must use `transform()` |
| Cross-field validation | `.when()` — verbose but built-in | `.refine()` or `.superRefine()` |
| Custom messages | `.messages({ 'rule': 'message' })` | Per-validation `.min(32, 'message')` |
| Bundle size | ~28 KB gzipped | ~13 KB gzipped |
| Ecosystem | Older, widely used in Node.js | Modern, TypeScript-first |
| Type export | Requires separate TS interfaces | `z.infer<typeof schema>` — single source of truth |

```typescript
// Key Zod advantage: single source of truth for type AND validation
const envSchema = z.object({ PORT: z.coerce.number(), DATABASE_URL: z.string().url() });
type Env = z.infer<typeof envSchema>;
// ↑ TypeScript type is DERIVED from the runtime schema — they can never diverge

// Joi equivalent requires separate type declaration:
const schema = Joi.object({ PORT: Joi.number(), DATABASE_URL: Joi.string().uri() });
interface Env { PORT: number; DATABASE_URL: string; }  // Must maintain separately
// Risk: Joi schema adds a field but Env interface isn't updated — types lie

// Key Joi advantage: conditional required fields
DATABASE_URL: Joi.string().when('NODE_ENV', {
  is:   'production',
  then: Joi.required(),
  otherwise: Joi.optional().default('postgres://localhost/dev'),
});
// Zod equivalent requires .superRefine() or separate schemas per env — more verbose
```

**Choose Joi when:** migrating an existing Express app that already uses Joi, or when you need complex conditional validation (`.when()`) without verbosity.

**Choose Zod when:** starting a new project, TypeScript-first philosophy, the same schema powers both config validation and DTO validation (avoiding a second dependency), or you want `z.infer<>` to eliminate the manual type interface.

## Section 6: Custom Configuration with `registerAs`

**Q10. What is `registerAs()` and how do you create typed, namespaced configuration objects?**

A: `registerAs(namespace, factory)` creates a **configuration token** — a factory function that, when loaded via `ConfigModule.forRoot({ load: [...] })`, makes the factory's return value available under a dot-notation namespace key and as a directly injectable token:

```typescript
// config/database.config.ts
import { registerAs } from '@nestjs/config';

export interface DatabaseConfig {
  url:      string;
  poolMin:  number;
  poolMax:  number;
  ssl:      boolean;
  schema:   string;
}

export const databaseConfig = registerAs('database', (): DatabaseConfig => ({
  url:     process.env.DATABASE_URL ?? 'postgres://localhost/app',
  poolMin: parseInt(process.env.DB_POOL_MIN ?? '2', 10),
  poolMax: parseInt(process.env.DB_POOL_MAX ?? '10', 10),
  ssl:     process.env.DATABASE_URL?.includes('sslmode=require') ?? false,
  schema:  process.env.DB_SCHEMA ?? 'public',
}));
// registerAs returns a function with an additional .KEY property:
// databaseConfig.KEY = 'database'  ← the injection token
```

```typescript
// config/auth.config.ts
export const authConfig = registerAs('auth', () => ({
  jwtSecret:   process.env.JWT_SECRET!,
  jwtExpires:  process.env.JWT_EXPIRES_IN ?? '7d',
  bcryptRounds: parseInt(process.env.BCRYPT_ROUNDS ?? '12', 10),
}));

// config/email.config.ts
export const emailConfig = registerAs('email', () => ({
  host:   process.env.SMTP_HOST!,
  port:   parseInt(process.env.SMTP_PORT ?? '587', 10),
  user:   process.env.SMTP_USER!,
  pass:   process.env.SMTP_PASS!,
  from:   process.env.SMTP_FROM ?? 'noreply@example.com',
}));
```

```typescript
// app.module.ts — load all namespaced configs
ConfigModule.forRoot({
  isGlobal:  true,
  validate:  validateEnv,
  load:      [databaseConfig, authConfig, emailConfig],
})

// Access via ConfigService dot-notation:
this.config.get<string>('database.url');
this.config.get<number>('database.poolMax');
this.config.get<string>('auth.jwtSecret');
this.config.get<string>('email.host');
```

**Q11. How do you inject a namespaced config directly using `ConfigType`, and why is this preferable to `ConfigService` with dot-notation?**

A: `ConfigType<typeof configFactory>` infers the exact return type of a `registerAs()` factory. Combined with `@Inject(config.KEY)`, you get fully typed, directly injectable config without any string keys:

```typescript
import { Injectable, Inject } from '@nestjs/common';
import { ConfigType } from '@nestjs/config';
import { databaseConfig } from './config/database.config';
import { authConfig }     from './config/auth.config';

@Injectable()
export class DatabaseService {
  constructor(
    // @Inject uses the .KEY symbol of the registerAs factory as the token:
    @Inject(databaseConfig.KEY)
    private readonly dbConfig: ConfigType<typeof databaseConfig>,
    // dbConfig type: { url: string; poolMin: number; poolMax: number; ssl: boolean; schema: string }
    // — fully typed, derived from the factory's return type
  ) {}

  getConnectionOptions() {
    return {
      connectionString: this.dbConfig.url,         // TypeScript knows this is string
      min:              this.dbConfig.poolMin,      // TypeScript knows this is number
      max:              this.dbConfig.poolMax,
      ssl:              this.dbConfig.ssl,
    };
  }
}

@Injectable()
export class AuthService {
  constructor(
    @Inject(authConfig.KEY)
    private readonly auth: ConfigType<typeof authConfig>,
  ) {}

  signToken(payload: object): string {
    return jwt.sign(payload, this.auth.jwtSecret, { expiresIn: this.auth.jwtExpires });
    //                         ↑ string — TypeScript knows; no .get<string>('auth.jwtSecret')
  }
}
```

**Why `@Inject(config.KEY)` over `configService.get('auth.jwtSecret')`:**

```typescript
// APPROACH 1: ConfigService dot-notation
const secret = this.config.get<string>('auth.jwtSecret');
// Problems:
// - String key 'auth.jwtSecret' is not type-checked — typo compiles silently
// - Return type is only as good as your <string> annotation — no inference
// - No autocomplete on the key name
// - Renaming the namespace requires a global search-and-replace of strings

// APPROACH 2: @Inject(authConfig.KEY) + ConfigType<>
const secret = this.auth.jwtSecret;
// Benefits:
// - TypeScript knows the type of 'jwtSecret' — no annotation needed
// - Typo on 'jwtSecret' is a TypeScript error
// - Renaming the property in the factory updates all usages (rename refactoring works)
// - The token (authConfig.KEY) is a Symbol — no string typos
```

## Section 7: `forFeature()` and Module-Level Config

**Q12. What is `ConfigModule.forFeature()` and when do you use it over importing from `load`?**

A: `ConfigModule.forFeature(configFactory)` lazily registers a namespaced config factory within a specific feature module — the factory's values become injectable in that module without needing to be listed in `forRoot()`'s `load` array:

```typescript
// email/email.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';
import { emailConfig } from './email.config';
import { EmailService } from './email.service';

@Module({
  imports: [
    // Register emailConfig only for this module:
    ConfigModule.forFeature(emailConfig),
  ],
  providers: [EmailService],
  exports:   [EmailService],
})
export class EmailModule {}

// email/email.service.ts
@Injectable()
export class EmailService {
  constructor(
    @Inject(emailConfig.KEY)
    private readonly config: ConfigType<typeof emailConfig>,
  ) {}
}
```

**`forFeature()` vs `load` in `forRoot()`:**

| | `forRoot({ load })` | `forFeature()` |
|---|---|---|
| Scope | Global — config available app-wide | Module-local — config available in that module only |
| When registered | At app initialization | When the feature module initializes |
| Use case | Core configs (DB, auth) needed everywhere | Feature-specific config (email, S3) |
| TypeScript | Same — `ConfigType<>` works for both | Same |

```typescript
// Pattern: put core config in forRoot().load, feature config in forFeature():

// app.module.ts (forRoot):
ConfigModule.forRoot({
  load: [databaseConfig, authConfig],  // Core — needed everywhere
})

// email.module.ts (forFeature):
ConfigModule.forFeature(emailConfig)   // Email-specific — only email module needs it

// s3.module.ts (forFeature):
ConfigModule.forFeature(s3Config)      // S3-specific — only file upload module needs it
```

## Section 8: Advanced Options

**Q13. How does `expandVariables` work and what are its practical uses?**

A: When `expandVariables: true`, NestJS uses `dotenv-expand` to resolve `${VAR}` references within `.env` file values before the config object is built. This lets you compose complex values from simpler parts:

```bash
# .env — with expandVariables: true

# Component parts:
DB_USER=myapp
DB_PASS=s3cr3t
DB_HOST=db.internal.example.com
DB_PORT=5432
DB_NAME=myapp_prod

# Composed from parts — avoids duplicating host/port/name:
DATABASE_URL=postgresql://${DB_USER}:${DB_PASS}@${DB_HOST}:${DB_PORT}/${DB_NAME}
# Resolves to: postgresql://myapp:s3cr3t@db.internal.example.com:5432/myapp_prod

# Another use: environment-tagged naming
SERVICE_NAME=api-gateway
LOG_PREFIX=[${SERVICE_NAME}]
# Resolves to: [api-gateway]
```

```typescript
ConfigModule.forRoot({
  envFilePath:     '.env',
  expandVariables: true,    // Enable ${VAR} interpolation
})

// Result: ConfigService.get('DATABASE_URL') returns the fully composed URL
// — no interpolation code needed in the config factory
```

**When `expandVariables` is particularly useful:**
- Database connection strings (composed from individual components for readability)
- Internal service URLs that share a base domain (`https://${INTERNAL_BASE}/service-name`)
- Naming conventions where many values share a common prefix

**Q14. How do you configure different `.env` files for different environments?**

A: `envFilePath` accepts a string array — files are loaded left-to-right, and **first definition wins** (earlier files take precedence over later ones):

```typescript
// Dynamic envFilePath based on NODE_ENV:
ConfigModule.forRoot({
  envFilePath: [
    `.env.${process.env.NODE_ENV}.local`,  // e.g., .env.development.local
    `.env.${process.env.NODE_ENV}`,        // e.g., .env.development
    '.env.local',                           // Local overrides (gitignored)
    '.env',                                 // Base defaults
  ],
  // Left-to-right, first definition wins:
  // .env.development.local overrides .env.development, which overrides .env

  ignoreEnvFile: process.env.NODE_ENV === 'production',
  // In production: env vars are injected by the platform — don't load .env files
})
```

```bash
# File hierarchy (committed to git):
.env                      # Base defaults — safe to commit (no secrets)
.env.development          # Dev-specific values
.env.test                 # Test-specific values (in-memory DB, mock services)

# Local overrides (gitignored — contains actual secrets):
.env.local                # Personal local overrides
.env.development.local    # Dev-specific personal overrides
.env.test.local           # Test-specific personal overrides
.env.production.local     # Never commit this — production secrets belong in a secrets manager
```

```bash
# .gitignore
*.local           # Ignore all .local files
.env.production   # Never commit production environment files
```

**Q15. What does `cache: true` do, when does it matter, and what are its tradeoffs?**

A: By default, `ConfigService.get()` reads from the underlying config store on every call. With `cache: true`, the first read caches the value in memory and subsequent calls return the cached value instantly:

```typescript
ConfigModule.forRoot({ cache: true })

// Without cache: every call reads from the internal store (in-memory object lookup)
// With cache: first call stores in a Map; subsequent calls hit the Map

// When it matters:
// ✓ Middleware or interceptors that call ConfigService on every request
// ✓ Per-iteration config access in tight loops
// ✗ Rarely accessed one-time config (startup configuration) — no measurable benefit

// The tradeoff:
// If config values change at runtime (unusual — typically they don't),
// the cache won't reflect the change. For static env-based config, this is fine.

// Typical pattern — use cache in production, skip in dev for hot-reload scenarios:
ConfigModule.forRoot({
  cache: process.env.NODE_ENV === 'production',
})
```

## Section 9: Testing

**Q16. How do you unit test a service that depends on `ConfigService`?**

A: Provide a mock `ConfigService` using `TestingModule` — no real config file loading, no environment dependency:

```typescript
import { Test, TestingModule } from '@nestjs/testing';
import { ConfigService } from '@nestjs/config';
import { AuthService } from './auth.service';

describe('AuthService', () => {
  let service: AuthService;
  let configService: ConfigService;

  // Approach 1: Jest mock object
  const mockConfigService = {
    get: jest.fn(),
    getOrThrow: jest.fn(),
  };

  beforeEach(async () => {
    const module: TestingModule = await Test.createTestingModule({
      providers: [
        AuthService,
        { provide: ConfigService, useValue: mockConfigService },
      ],
    }).compile();

    service        = module.get(AuthService);
    configService  = module.get(ConfigService);
  });

  it('signs a token with the configured secret', () => {
    mockConfigService.getOrThrow.mockImplementation((key: string) => {
      const config: Record<string, unknown> = {
        'auth.jwtSecret':  'test-secret-that-is-at-least-32-chars!!',
        'auth.jwtExpires': '1h',
      };
      if (!(key in config)) throw new Error(`Missing config: ${key}`);
      return config[key];
    });

    const token = service.signToken({ userId: '123' });
    expect(token).toBeDefined();
    expect(configService.getOrThrow).toHaveBeenCalledWith('auth.jwtSecret');
  });
});
```

**For services using `@Inject(config.KEY)` with `ConfigType`:**

```typescript
// Testing with direct @Inject injection tokens:
import { authConfig } from './config/auth.config';
import { ConfigType } from '@nestjs/config';

const mockAuthConfig: ConfigType<typeof authConfig> = {
  jwtSecret:    'test-secret-that-is-at-least-32-chars!!',
  jwtExpires:   '1h',
  bcryptRounds: 1,   // Lower rounds in tests for speed
};

const module: TestingModule = await Test.createTestingModule({
  providers: [
    AuthService,
    { provide: authConfig.KEY, useValue: mockAuthConfig },
    // The KEY token is a Symbol — same token that @Inject(authConfig.KEY) resolves
  ],
}).compile();
```

## Section 10: Scenario-Based Questions

**Q18. "What is wrong with this configuration setup, and what are the production consequences?"**

```typescript
// config/app.config.ts
export const appConfig = registerAs('app', () => ({
  port: process.env.PORT,
  nodeEnv: process.env.NODE_ENV,
  dbUrl: process.env.DATABASE_URL,
  jwtSecret: process.env.JWT_SECRET,
  jwtExpires: process.env.JWT_EXPIRES_IN || '7d',
}));

// app.module.ts
ConfigModule.forRoot({
  isGlobal: true,
  load: [appConfig],
});

// app.service.ts
@Injectable()
export class AppService {
  constructor(private readonly config: ConfigService) {}

  getPort(): number {
    return this.config.get('app.port');
  }

  getDbUrl(): string {
    return this.config.get('app.dbUrl');
  }

  getSecret(): string {
    return this.config.get('app.jwtSecret');
  }
}
```

A: Six problems:

**Problem 1 — No validation — app starts with missing critical config:**
```typescript
// No validationSchema or validate — if DATABASE_URL and JWT_SECRET are not set:
// appConfig.dbUrl  = undefined
// appConfig.jwtSecret = undefined
// The app starts normally and crashes when these values are first used in production
```

**Problem 2 — `process.env.PORT` is a string, `getPort()` returns a string typed as `number`:**
```typescript
// port: process.env.PORT  → type: string | undefined (not number)
// configService.get('app.port') returns the string "3000", not the number 3000
// app.listen(this.getPort())
// → Node.js's listen() accepts both, but:
//   port === "3000" + 1 = "30001" (string concatenation) in some codepaths
// Must use: port: parseInt(process.env.PORT ?? '3000', 10)
// Or: port: Number(process.env.PORT) || 3000
```

**Problem 3 — `configService.get()` returns `undefined` silently for missing keys:**
```typescript
// getDbUrl(): string — the return type annotation is a lie
// If DATABASE_URL is undefined, this.config.get('app.dbUrl') returns undefined
// The caller receives undefined but TypeScript says it's a string
// Use: this.config.getOrThrow('app.dbUrl') — throws if missing
```

**Problem 4 — No type safety on `configService.get()` calls:**
```typescript
// configService.get('app.port') — no generic type argument
// Returns any — TypeScript cannot catch type mismatches
// Should be: configService.get<number>('app.port') or use @Inject(appConfig.KEY)
```

**Problem 5 — String key typos compile silently:**
```typescript
// this.config.get('app.jwt_secret')  // Typo: underscore instead of camelCase
// Returns undefined — TypeScript doesn't catch it
// Should use: @Inject(appConfig.KEY) + ConfigType<typeof appConfig>
```

**Problem 6 — `jwtSecret` is logged or exposed in stack traces:**
```typescript
// If the config object is accidentally logged (console.log(this.config)) or
// included in an error message, JWT_SECRET appears in plaintext in logs
// Secrets should be accessed only at point of use, never stored in logs
```

**Corrected version:**
```typescript
// config/app.config.ts
import { registerAs } from '@nestjs/config';

export const appConfig = registerAs('app', () => ({
  port:       parseInt(process.env.PORT ?? '3000', 10),
  nodeEnv:    process.env.NODE_ENV ?? 'development',
  dbUrl:      process.env.DATABASE_URL!,    // Validated at startup
  jwtExpires: process.env.JWT_EXPIRES_IN ?? '7d',
  // jwtSecret NOT in the config object — injected directly only where needed
}));

// app.module.ts — with validation:
ConfigModule.forRoot({
  isGlobal:  true,
  load:      [appConfig],
  validate:  validateEnv,   // Zod schema catches missing vars at startup
})

// app.service.ts — typed injection:
@Injectable()
export class AppService {
  constructor(
    @Inject(appConfig.KEY)
    private readonly app: ConfigType<typeof appConfig>,
  ) {}

  getPort(): number { return this.app.port; }    // number — typed correctly
  getDbUrl(): string { return this.app.dbUrl; }  // string — required by Zod
}
```

**Q19. "Design a complete, type-safe configuration system for a production NestJS application with database, auth, email, and feature flags."**

A:

```typescript
// ── 1. Zod validation schema ──────────────────────────────────────────────────
// env.validation.ts
import { z } from 'zod';

const envSchema = z.object({
  NODE_ENV:  z.enum(['development', 'production', 'test', 'staging']).default('development'),
  PORT:      z.coerce.number().int().min(1).max(65535).default(3000),

  DATABASE_URL:  z.string().url(),
  DB_POOL_MIN:   z.coerce.number().int().min(0).default(2),
  DB_POOL_MAX:   z.coerce.number().int().min(1).default(10),

  JWT_SECRET:    z.string().min(32),
  JWT_EXPIRES:   z.string().regex(/^\d+[smhd]$/).default('7d'),

  SMTP_HOST:     z.string().min(1),
  SMTP_PORT:     z.coerce.number().int().default(587),
  SMTP_USER:     z.string().min(1),
  SMTP_PASS:     z.string().min(1),
  SMTP_FROM:     z.string().email().default('noreply@example.com'),

  FEATURE_NEW_DASHBOARD: z.preprocess(v => v === 'true', z.boolean()).default(false),
  FEATURE_BETA_API:      z.preprocess(v => v === 'true', z.boolean()).default(false),
}).refine(d => d.DB_POOL_MAX > d.DB_POOL_MIN, {
  message: 'DB_POOL_MAX must exceed DB_POOL_MIN',
  path:    ['DB_POOL_MAX'],
});

export type Env = z.infer<typeof envSchema>;

export function validateEnv(raw: Record<string, unknown>): Env {
  const result = envSchema.safeParse(raw);
  if (!result.success) {
    const errors = result.error.errors
      .map(e => `  ${e.path.join('.')}: ${e.message}`)
      .join('\n');
    throw new Error(`\n[Config] Validation failed:\n${errors}\n`);
  }
  return result.data;
}

// ── 2. Namespaced config factories ────────────────────────────────────────────
// config/database.config.ts
export const databaseConfig = registerAs('database', () => ({
  url:     process.env.DATABASE_URL!,
  poolMin: parseInt(process.env.DB_POOL_MIN ?? '2', 10),
  poolMax: parseInt(process.env.DB_POOL_MAX ?? '10', 10),
}));

// config/auth.config.ts
export const authConfig = registerAs('auth', () => ({
  jwtSecret:  process.env.JWT_SECRET!,
  jwtExpires: process.env.JWT_EXPIRES ?? '7d',
}));

// config/email.config.ts
export const emailConfig = registerAs('email', () => ({
  host:  process.env.SMTP_HOST!,
  port:  parseInt(process.env.SMTP_PORT ?? '587', 10),
  user:  process.env.SMTP_USER!,
  pass:  process.env.SMTP_PASS!,
  from:  process.env.SMTP_FROM ?? 'noreply@example.com',
}));

// config/features.config.ts
export const featuresConfig = registerAs('features', () => ({
  newDashboard: process.env.FEATURE_NEW_DASHBOARD === 'true',
  betaApi:      process.env.FEATURE_BETA_API === 'true',
}));

// ── 3. AppModule registration ─────────────────────────────────────────────────
// app.module.ts
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal:        true,
      envFilePath:     [`.env.${process.env.NODE_ENV}.local`, `.env.${process.env.NODE_ENV}`, '.env'],
      ignoreEnvFile:   process.env.NODE_ENV === 'production',
      validate:        validateEnv,
      expandVariables: true,
      load:            [databaseConfig, authConfig, featuresConfig],
      // emailConfig loaded per-feature module with forFeature()
    }),
    DatabaseModule,
    AuthModule,
    EmailModule,
  ],

export class AppModule {}

// ── 4. Feature module with forFeature() ──────────────────────────────────────
// email/email.module.ts

  providers: [EmailService],
  exports:   [EmailService],

export class EmailModule {}

// ── 5. Fully typed service consumption ───────────────────────────────────────
// database/database.service.ts
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| `ConfigModule.forRoot()` | Module-level setup — options: `isGlobal`, `envFilePath`, `validate`, `validationSchema`, `load`, `cache`, `expandVariables`, `ignoreEnvFile` |
| `isGlobal: true` | Makes `ConfigService` injectable app-wide without importing `ConfigModule` per module |
| `envFilePath` | String or string array — loaded left-to-right, first definition wins |
| `ignoreEnvFile` | Skip `.env` loading — use `process.env.NODE_ENV === 'production'` as the value |
| `expandVariables` | Enables `${VAR}` interpolation within `.env` values |
| `validationSchema` | Joi schema — mutually exclusive with `validate`; `abortEarly: false` is essential |
| `validate` | Custom function `(raw: Record<string, unknown>) => Config` — use for Zod or any validator |
| `load` | Array of `registerAs()` factories — populates namespaced config |
| `cache: true` | Memoizes `configService.get()` results — useful in hot request paths |
| `configService.get<T>(key, default?)` | Returns `T \| undefined`; second arg prevents undefined |
| `configService.getOrThrow<T>(key)` | Returns `T` or throws `ConfigNotFoundException` — prefer over `get()!` |
| `registerAs(namespace, factory)` | Creates a named config token; `factory.KEY` is the DI injection token |
| `ConfigType<typeof factory>` | Infers the TypeScript type of a `registerAs()` factory's return value |
| `@Inject(config.KEY)` | Injects the namespaced config directly — fully typed, no string keys |
| `ConfigModule.forFeature(factory)` | Registers a namespaced config for a specific feature module only |
| `z.coerce.number()` | Converts string env var `"3000"` → number `3000` — required since `process.env` is always strings |
| `z.coerce.boolean()` | Converts any non-empty string to `true` — WRONG for booleans; use `.preprocess(v => v === 'true', z.boolean())` |
| `z.infer<typeof schema>` | Derives TypeScript type from Zod schema — single source of truth for type AND validation |
| Joi `.when()` | Conditional required based on another field — cleaner than Zod's `.superRefine()` |
| `abortEarly: false` | Reports all Joi validation errors at once — critical for startup config debugging |
| `allowUnknown: true` | Permits env vars not in Joi schema (CI vars, platform vars) — Joi's default is false but NestJS sets true |
| Testing | Mock `ConfigService` with `useValue`; mock `@Inject(config.KEY)` tokens with `{ provide: config.KEY, useValue: mockValue }` |
| Production pattern | `ignoreEnvFile: true` + platform-injected env vars + `validate` with Zod/Joi for fail-fast startup |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) knowing that **`validationSchema` (Joi) and `validate` (Zod) are mutually exclusive** and explaining why both exist — `validationSchema` is the native NestJS option that handles Joi internally, while `validate` is an escape hatch for any validator including Zod; being able to write a complete `validate` function that formats `ZodError` into a readable startup message and returns the coerced typed object is a strong signal; (2) the **`ConfigType<typeof factory>` + `@Inject(config.KEY)` pattern** over `configService.get<T>('dot.notation')` — the former gives compile-time type checking on property access and makes refactoring safe (rename the property in the factory and TypeScript catches all usages), while the latter uses untyped strings where typos silently return `undefined`; (3) explaining why **`z.coerce` matters specifically for environment variables** — all `process.env` values are strings, so `z.number()` always fails while `z.coerce.number()` correctly converts `"3000"` to `3000`; and the boolean coercion trap (`z.coerce.boolean()` converts `"false"` to `true` because any non-empty string is truthy — must use `z.preprocess(v => v === 'true', z.boolean())`); (4) the **`app.useGlobalFilters()` DI problem applied to config** — the equivalent here is that `app.useGlobalFilters(new SomeFilter())` mirrors using `ConfigService` directly in `main.ts` before the module is fully initialized; the correct pattern is `app.get(ConfigService)` after `NestFactory.create()` but before `app.listen()`; and (5) the **`ignoreEnvFile: process.env.NODE_ENV === 'production'` pattern** — in production, environment variables are injected by Kubernetes, ECS, or Lambda and a `.env` file either doesn't exist or has stale values; loading it would silently override the platform-injected values with wrong ones; always gate file loading on the environment.
