## Part 1 — Theory & Interview Q&A

---

### Section 1: What PM2 Is and Why It Exists

**Q1. What is PM2, and what problems does it solve for Node.js production deployments?**
A: PM2 (Process Manager 2) is a production-grade **process manager for Node.js applications**. It solves three fundamental problems with running Node.js in production:

1. **Process resurrection**: Node.js processes crash. Without a supervisor, a crash means downtime until someone manually restarts the server. PM2 automatically restarts processes on crash, exiting with non-zero codes, or on file changes — keeping applications alive without human intervention.

2. **CPU underutilization**: Node.js is single-threaded. A server with 8 CPU cores runs only one core's worth of JavaScript without additional infrastructure. PM2's **cluster mode** spawns multiple Node.js instances sharing a single port, leveraging all available cores.

3. **Operational complexity**: managing multiple processes (start, stop, reload, monitor, log) without tooling requires significant shell scripting. PM2 provides a unified CLI and programmatic API for all lifecycle management, log aggregation, and monitoring.

PM2 is not a container orchestration tool (it doesn't replace Docker, Kubernetes, or systemd for multi-server setups), but it is the de-facto standard for managing Node.js processes on a single server or within a container.

**Q2. How does PM2 keep a process alive after it crashes — what is the underlying mechanism?**
A: PM2 itself runs as a daemon (a background Node.js process, the "PM2 daemon") that monitors the processes it manages. When a managed process exits (crash, `process.exit()`, or OOM kill), the daemon detects the exit via the OS's process exit notification (via Node.js's child process `'exit'` event on the spawned child). The daemon then waits for the configured restart delay (`restart_delay`, default 0ms) and spawns a fresh copy of the process.

PM2 tracks **restart count** and applies exponential backoff by default with `exp_backoff_restart_delay`, preventing rapid crash-restart loops (a "restart storm") that could exhaust resources. The `max_restarts` and `min_uptime` settings work together — if a process restarts more than `max_restarts` times within a window where it never stays up longer than `min_uptime`, PM2 marks it as "errored" and stops attempting to restart it.

```bash
# The daemon runs separately from your application:
pm2 start app.js

# PM2 daemon is already running (or starts if not):
# PID 1234: PM2 daemon
# PID 5678: your app.js (child of daemon)
# If 5678 crashes → PM2 daemon detects exit → spawns new PID 5679

pm2 status # shows: app | online | restarts: 1
```

### Section 2: Cluster Mode

**Q3. What is PM2's cluster mode, and how does it differ from fork mode?**
A: PM2 runs processes in two fundamental modes:

**Fork mode** (default): PM2 spawns a single child process using Node.js's `child_process.fork()`. One process, one event loop, one CPU core utilized. Straightforward but wastes CPU on multi-core machines.

**Cluster mode**: PM2 uses Node.js's built-in `cluster` module to spawn multiple worker processes that **share a single TCP port**. The OS kernel distributes incoming connections across all workers using a round-robin (or OS-specific load balancing) strategy. Each worker is a full Node.js process with its own V8 instance, heap, and event loop — true parallelism across CPU cores.

```bash
# Fork mode (default): 1 process
pm2 start app.js

# Cluster mode: N processes sharing port 3000
pm2 start app.js --instances 4 --name my-api

# Or let PM2 determine optimal instance count (one per CPU core):
pm2 start app.js --instances max --name my-api
# On an 8-core machine: spawns 8 worker instances
```

**Q4. How does Node.js's `cluster` module work, and how does PM2 use it internally?**
A: Node.js's `cluster` module allows a "master" process to fork "worker" processes. The master and workers share the same server port via a special socket-passing mechanism: the master process owns the TCP listening socket and distributes incoming connections to workers. In PM2's cluster mode, **PM2 itself acts as the master** — the PM2 daemon manages the cluster, not your application code. This is a key distinction: with raw `cluster`, your application code must handle the master/worker split (checking `cluster.isMaster`). With PM2, your application code is always just the worker — it's a regular Express/Fastify/Hapi server with no `cluster` knowledge required.

```js
// WITHOUT PM2 — application must manage cluster itself:
const cluster = require('cluster');
const http = require('http');
const numCPUs = require('os').cpus().length;

if (cluster.isMaster) {
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }
  cluster.on('exit', (worker) => {
    console.log(`Worker ${worker.process.pid} died, spawning new one`);
    cluster.fork();
  });
} else {
  // Worker: run the actual server
  http.createServer((req, res) => res.end('Hello')).listen(3000);
}

// WITH PM2 cluster mode — application is always just the server:
const http = require('http');
http.createServer((req, res) => res.end('Hello')).listen(3000);
// pm2 start app.js --instances 4 -- PM2 handles the clustering externally
```

**Q5. What is `instances: 'max'` vs a specific number, and how do you choose?**
A: `instances: 'max'` tells PM2 to spawn one worker per logical CPU core (using `os.cpus().length`). A specific number like `instances: 4` spawns exactly 4, regardless of core count.

Choosing:
- **`max`**: default for CPU-bound or high-concurrency I/O-bound workloads where you want full core utilization. Ensure your machine has spare capacity for the OS and other processes.
- **Specific number less than core count**: when your application is memory-intensive (each instance uses 200MB and you have 8 cores but only 1GB RAM → max 4 instances safely), or when you need to leave cores free for other services on the same machine.
- **`instances: -1`**: spawn `(numCPUs - 1)` workers — leaving one core free for the OS and PM2 daemon itself. A common production choice for dedicated Node.js servers.
- **`instances: 1`**: cluster mode with a single worker — rarely useful (equivalent to fork mode but with cluster overhead). Use fork mode instead.

**Q6. What are the critical requirements for an application to work correctly in PM2 cluster mode?**
A: Cluster mode multiplexes connections across independent processes. For this to work correctly:

1. **Stateless request handling**: each request must be fully handleable by any worker, with no requirement for session state on a specific worker. If your app stores session data in worker memory (e.g., in-memory Maps, local caches), sessions will break — requests may hit a different worker on subsequent calls.

2. **Shared state via external services**: use Redis (sessions, caches), a database, or a message queue for any state that must be consistent across workers. In-process state (global variables, local caches) is private to each worker.

3. **No port conflicts**: all workers bind to the same port via the cluster module's socket sharing. Do NOT call `server.listen()` in a way that bypasses this (e.g., binding to a Unix socket per-worker with different paths).

4. **Graceful shutdown handling**: each worker should listen for `SIGINT`/`SIGTERM` and complete in-flight requests before exiting. PM2 sends `SIGINT` during reload — workers that don't handle it gracefully will drop requests during restarts.

5. **Careful use of cron jobs and scheduled tasks**: if each worker independently runs a cron job, you get N copies of the job running simultaneously. Use a distributed lock (via Redis `SET NX`) or designate a single worker (checking `process.env.NODE_APP_INSTANCE === '0'`) to run scheduled tasks.

### Section 3: Zero-Downtime Restarts

**Q7. What is a zero-downtime restart (graceful reload), and how does PM2 implement it?**
A: A zero-downtime restart (triggered by `pm2 reload`) means deploying a new version of the application without dropping any in-flight HTTP requests and without any gap in the server's ability to accept new connections. PM2 implements this via a **rolling restart** of the cluster workers:

1. PM2 starts a new worker with the updated code.
2. Waits for the new worker to be "ready" (either after `listen_timeout` ms, or after the worker sends a `'ready'` signal via `process.send('ready')`).
3. Sends `SIGINT` (or the configured `kill_signal`) to ONE old worker.
4. The old worker completes in-flight requests and exits gracefully.
5. Repeats steps 1–4 for each remaining old worker.

At every point during this process, at least one worker is actively serving requests — there is no moment when the port has zero listeners.

```
Before reload:      Worker A (old), Worker B (old), Worker C (old)
During reload:
  Step 1: Spawn Worker D (new) → serves requests once ready
          Workers A, B, C (old) still serve in parallel
  Step 2: Kill Worker A → Worker D, B, C serve
  Step 3: Spawn Worker E (new) → Workers E, D, B, C serve
  Step 4: Kill Worker B → Workers E, D, C serve
  ... (continues until all old workers replaced)
After reload:       Worker D (new), Worker E (new), Worker F (new)
```

**Q8. What is the "ready" signal pattern, and why is it critical for correct zero-downtime restarts?**
A: By default, PM2 considers a worker "ready" (safe to start accepting connections) after a configurable `listen_timeout` (default: 8000ms). This is a time-based heuristic — if your application takes longer than 8 seconds to start (database connection pool initialization, loading large config files), PM2 may mark the worker as ready before it can actually serve requests, causing brief errors during reload.

The correct approach is the **explicit ready signal**: the application sends `process.send('ready')` to PM2 precisely when it's fully initialized and listening. PM2 waits for this signal (up to `wait_ready: true` + `listen_timeout`) instead of using a fixed timer.

```js
// app.js — with explicit ready signal
const app = require('express')();
const db = require('./db');

async function start() {
  // Perform all initialization before signaling readiness
  await db.connect();              // database connection pool
  await loadConfig();             // remote config fetch
  await warmCache();              // cache warming

  const server = app.listen(3000, () => {
    console.log('Server ready on port 3000');

    // Signal PM2 that this worker is ready to receive traffic
    // PM2 won't kill old workers until this signal is received
    if (process.send) {
      process.send('ready');       // only available when spawned by PM2
    }
  });

  // Graceful shutdown: handle SIGINT sent by PM2 during reload
  process.on('SIGINT', () => {
    server.close(() => {
      // All existing connections closed — safe to exit
      db.disconnect();
      process.exit(0);
    });

    // Force exit if graceful shutdown takes too long:
    setTimeout(() => process.exit(1), 10000);
  });
}

start().catch(err => {
  console.error('Failed to start:', err);
  process.exit(1);
});
```

**Q9. What is the difference between `pm2 restart` and `pm2 reload`, and when should each be used?**
A: Two distinct commands with fundamentally different behavior:

**`pm2 restart <name>`**: **hard restart** — kills all workers simultaneously and immediately spawns fresh workers. There is a brief moment (milliseconds to seconds, depending on startup time) where no workers are available. In-flight requests are dropped. Use for: development, applying changes that require a clean process state, recovering from a hung/stuck cluster, or when your application is not stateless (so rolling reload would create state inconsistencies during the transition).

**`pm2 reload <name>`**: **rolling graceful reload** — replaces workers one at a time as described in Q7. No dropped requests, no downtime. Use for: production deployments, environment variable changes, updating application code on a live server. Requires the application to be stateless (Q6) and to handle `SIGINT` gracefully (Q8).

```bash
pm2 restart my-api   # hard restart: brief downtime, fast, stateful OK
pm2 reload my-api    # graceful rolling reload: zero downtime, requires stateless + SIGINT handling
pm2 restart my-api --update-env  # hard restart + re-read environment variables
pm2 reload my-api --update-env   # graceful reload + re-read environment variables
```

**Q10. What is `kill_timeout`, and how does it interact with graceful shutdown?**
A: `kill_timeout` is the maximum time (in milliseconds) PM2 waits for a worker to exit gracefully after sending `SIGINT` before forcibly sending `SIGKILL`. Default is 1600ms. If your graceful shutdown logic (completing in-flight requests, closing database connections) takes longer than `kill_timeout`, PM2 will `SIGKILL` the worker, potentially interrupting in-flight requests and leaving external resources (database connections, file handles) unclosed.

For applications with potentially long-running requests (file uploads, large queries), increase `kill_timeout` to a value greater than your P99 request duration plus database close time:

```js
// ecosystem.config.js
module.exports = {
  apps: [{
    name: 'api',
    script: 'app.js',
    kill_timeout: 30000, // 30 seconds — allows long requests to complete
    // App's SIGINT handler should finish within 30s or force-exit itself
  }]
};
```

### Section 4: The Ecosystem File

**Q11. What is a PM2 ecosystem file, and what are its advantages over CLI flags?**
A: A PM2 ecosystem file (`ecosystem.config.js` or `ecosystem.config.cjs`) is a JavaScript (or JSON) configuration file that defines all PM2-managed applications, their runtime parameters, and environment-specific settings in a **declarative, version-controlled format**. Advantages over CLI flags:

1. **Version control**: committed to the repository alongside the application code — deployment configuration is part of the codebase, not undocumented shell scripts.
2. **Reproducibility**: `pm2 start ecosystem.config.js` starts all applications with exactly the same configuration on every server, every time.
3. **Multiple environments**: define different configurations for development, staging, and production in one file using `env`, `env_staging`, `env_production` blocks.
4. **Multiple applications**: define a microservices deployment (API server, worker process, cron service) in one file, started and stopped atomically with `pm2 start ecosystem.config.js`.
5. **Readability**: JSON-like structure is far more readable than a long CLI command with 15 flags.

**Q12. What are the most important ecosystem file options, and what does each control?**
A: A comprehensive annotated ecosystem file:

```js
// ecosystem.config.js
module.exports = {
  apps: [
    {
      // ── Identity ──────────────────────────────────────────────────
      name: 'my-api',            // Name used in pm2 commands and logs
      script: './src/server.js', // Entry point (relative to cwd)
      cwd: '/app',               // Working directory for the process
      args: '--port 3000',       // CLI args passed to the script

      // ── Cluster / Process ─────────────────────────────────────────
      instances: 'max',          // Number of instances: integer, 'max', or '-1'
      exec_mode: 'cluster',      // 'cluster' or 'fork'

      // ── Environment ───────────────────────────────────────────────
      env: {                     // Base environment (always applied)
        NODE_ENV: 'development',
        PORT: 3000,
        LOG_LEVEL: 'debug',
      },
      env_staging: {             // Merged over `env` when using --env staging
        NODE_ENV: 'staging',
        PORT: 3000,
        LOG_LEVEL: 'info',
        DATABASE_URL: 'postgres://staging-db:5432/app',
      },
      env_production: {          // Merged over `env` when using --env production
        NODE_ENV: 'production',
        PORT: 3000,
        LOG_LEVEL: 'warn',
        DATABASE_URL: 'postgres://prod-db:5432/app',
      },

      // ── Startup & Readiness ───────────────────────────────────────
      wait_ready: true,          // Wait for process.send('ready') before marking ready
      listen_timeout: 10000,     // Max ms to wait for 'ready' signal (default: 8000)
      kill_timeout: 30000,       // Max ms for graceful shutdown before SIGKILL

      // ── Restart Behavior ─────────────────────────────────────────
      autorestart: true,         // Auto-restart on crash (default: true)
      max_restarts: 10,          // Give up after 10 restarts within watch window
      min_uptime: '5s',          // Minimum uptime before counting as a stable start
      restart_delay: 1000,       // ms to wait between restarts (default: 0)
      exp_backoff_restart_delay: 100, // Exponential backoff starting at 100ms

      // ── Logging ───────────────────────────────────────────────────
      out_file: './logs/out.log',   // stdout log path (set to /dev/null to disable)
      error_file: './logs/err.log', // stderr log path
      log_file: './logs/combined.log', // combined log (optional)
      log_date_format: 'YYYY-MM-DD HH:mm:ss Z', // timestamp format
      merge_logs: true,          // Merge logs from all cluster instances into one file

      // ── Memory / CPU ──────────────────────────────────────────────
      max_memory_restart: '500M', // Restart if memory exceeds 500MB
      // (useful for detecting memory leaks automatically)

      // ── File Watching (development only) ─────────────────────────
      watch: false,              // Watch files for changes and restart (dev only!)
      ignore_watch: ['node_modules', 'logs'],

      // ── Startup on Boot ───────────────────────────────────────────
      // (handled separately via `pm2 startup` command, not in ecosystem file)
    },

    // Second application in the same ecosystem file:
    {
      name: 'worker',
      script: './src/worker.js',
      instances: 2,
      exec_mode: 'fork',          // Workers are stateful — use fork, not cluster
      env_production: {
        NODE_ENV: 'production',
        QUEUE_URL: 'redis://redis:6379',
      }
    }
  ]
};
```

**Q13. How do environment-specific configurations work in the ecosystem file, and how do you activate them?**
A: Environment configurations use a naming convention: `env`, `env_<name>`, where `<name>` matches the `--env` flag passed to `pm2 start` or `pm2 reload`. The base `env` block is always applied; the named `env_<name>` block is **merged over** the base `env`, with the named block's values taking precedence on conflicts.

```bash
# Start with base env (development):
pm2 start ecosystem.config.js

# Start with production env merged:
pm2 start ecosystem.config.js --env production

# Reload production deployment with updated env:
pm2 reload ecosystem.config.js --env production --update-env

# The --update-env flag is critical: without it, PM2 reload
# uses the environment from when the app was first started,
# not the current ecosystem file — env changes would be ignored.
```

Note: `--update-env` is required when using `pm2 reload` if you've changed environment variables in the ecosystem file since the app was started. Without it, existing workers pass their current environment to new workers, ignoring any changes.

### Section 5: Advanced Operations

**Q14. How do you persist PM2's process list across server reboots?**
A: By default, PM2's process list is in-memory — a server reboot starts a fresh PM2 daemon with no processes. Two steps for persistence:

```bash
# Step 1: Generate and install a startup script for the current OS
# (systemd on Linux, launchd on macOS, etc.)
pm2 startup

# This outputs a command like:
# sudo env PATH=$PATH:/usr/bin pm2 startup systemd -u ubuntu --hp /home/ubuntu
# Run that exact command (it configures PM2 as a systemd service)

# Step 2: Save the current process list to be restored on boot
pm2 save
# Creates ~/.pm2/dump.pm2 with the current process list

# After a reboot, systemd starts PM2, which reads dump.pm2 and restarts all processes

# When you change the process list (add/remove apps), save again:
pm2 save
```

**Q15. What is PM2's inter-process messaging (`pm2.sendDataToProcessId`), and when is it useful?**
A: PM2 provides an IPC channel between the PM2 daemon and managed processes via `process.on('message', handler)` (receive) and `process.send(data)` (send from worker to daemon) and `pm2.sendDataToProcessId(pid, packet, callback)` (send from daemon/external to a specific worker). This is useful for: triggering a cache flush in all workers simultaneously, hot-reloading configuration without a full restart, and sending control messages to specific workers.

```js
// In the worker: listen for control messages
process.on('message', (packet) => {
  if (packet.type === 'flush-cache') {
    cache.clear();
    console.log('Cache flushed in worker', process.pid);
  }
  if (packet.type === 'reload-config') {
    config.reload();
  }
});

// From a management script or CLI:
const pm2 = require('pm2');
pm2.connect((err) => {
  pm2.list((err, list) => {
    list
      .filter(proc => proc.name === 'my-api')
      .forEach(proc => {
        pm2.sendDataToProcessId(proc.pm_id, {
          type: 'flush-cache',
          data: {}
        }, (err) => { /* handle */ });
      });
  });
});
```

**Q16. What is `max_memory_restart`, and how should it be used in practice?**
A: `max_memory_restart` configures PM2 to automatically restart a worker when its RSS (Resident Set Size) memory exceeds the specified threshold. It's a **safety net for memory leaks** — not a substitute for fixing them. PM2 polls memory usage periodically and triggers a restart when the threshold is crossed.

Practical guidance:
- Set to 10-20% above your application's normal steady-state memory usage. If your API normally uses 200MB, set `max_memory_restart: '250M'`.
- Do NOT set it very low (equal to normal usage) — normal GC behavior causes temporary spikes; too-aggressive thresholds cause unnecessary restarts.
- Use it alongside memory profiling tools (clinic.js, `--heap-prof`) to find and fix the underlying leak — `max_memory_restart` restarts symptoms, doesn't cure the disease.
- Accepts: `'150M'`, `'1G'`, `'512K'`, or raw bytes: `314572800`.

### Section 6: Scenario / Interview-Style Questions

**Q17. "Your Node.js API runs on a server with 16 CPU cores but handles only as many requests as a single-core server. What's likely wrong, and how do you fix it with PM2?"**
A: Without cluster mode, Node.js uses one core regardless of how many are available. With PM2 running in fork mode (the default), it's still one process, one core. Fix:

```bash
# Check current mode:
pm2 show my-api  # look for "exec mode: fork"

# Switch to cluster mode:
pm2 delete my-api
pm2 start app.js --name my-api --instances max --exec-mode cluster

# Or update the ecosystem file:
# instances: 'max', exec_mode: 'cluster'
# pm2 reload ecosystem.config.js
```

But also verify that the application is stateless (Q6) — if it stores session state in memory, moving to cluster mode will break session continuity without first migrating sessions to Redis.

**Q18. "During a deployment with `pm2 reload`, you observe that some HTTP requests receive connection refused errors for about 2 seconds. What's going wrong, and how do you fix it?"**
A: Two likely causes, same root: PM2 is killing old workers before new workers are truly ready to serve requests.

Cause 1 — No ready signal: PM2 uses a time-based heuristic (`listen_timeout: 8000ms` default). If the new worker isn't listening on the port yet when `listen_timeout` expires (slow startup — DB connections, config loading), PM2 kills the old worker anyway, creating a gap. Fix: add `process.send('ready')` in the application after the server starts listening and set `wait_ready: true`.

Cause 2 — Ready signal sent too early: The application sends `process.send('ready')` before `server.listen()` resolves (e.g., before the TCP socket is actually bound). Fix: send `'ready'` inside the `server.listen()` callback, not before it.

```js
// WRONG — ready before listening:
process.send('ready'); // sends ready before server is actually up
server.listen(3000);

// CORRECT — ready after listening:
server.listen(3000, () => {
  if (process.send) process.send('ready'); // sends ready once port is bound
});
```

**Q19. "You deploy a new version with `pm2 reload`, and `pm2 logs` shows the new instances starting. But API responses still return the old version. What's happening?"**
A: The new workers started but immediately crashed (returning a non-zero exit code), and PM2 fell back to the old workers still running. Or the new workers started but PM2 didn't gracefully kill the old workers (leaving both old and new running — old workers serving most requests due to established connections).

Debugging steps:
```bash
pm2 logs my-api   # check for error messages from the new workers
pm2 status        # check if any instances are in "errored" state
pm2 show my-api   # check restart count, uptime, exec mode

# Common cause: new code has a startup error (syntax error, missing module)
# The new worker crashes immediately, PM2 keeps old workers
# Fix: test the new version locally before deploying
node app.js  # run locally to verify it starts without errors
```

**Q20. "How would you use PM2 to run both a web API and a background worker in a single ecosystem file, with different scaling settings?"**
A: Define two separate `apps` entries with different `exec_mode` and `instances`:

```js
module.exports = {
  apps: [
    {
      name: 'api',
      script: './api/server.js',
      instances: 'max',
      exec_mode: 'cluster',      // Stateless HTTP API — use all cores
      env_production: { NODE_ENV: 'production', PORT: 3000 }
    },
    {
      name: 'worker',
      script: './worker/index.js',
      instances: 2,
      exec_mode: 'fork',          // Worker is stateful (job locks) — fork mode
      env_production: {
        NODE_ENV: 'production',
        QUEUE_URL: 'redis://redis:6379',
        WORKER_CONCURRENCY: 5
      }
    },
    {
      name: 'scheduler',
      script: './scheduler/cron.js',
      instances: 1,               // Exactly 1 — cron must not run in parallel
      exec_mode: 'fork',
      cron_restart: '0 3 * * *',  // Restart at 3am daily (optional)
      env_production: { NODE_ENV: 'production' }
    }
  ]
};

// Deploy all three:
// pm2 start ecosystem.config.js --env production
// pm2 reload ecosystem.config.js --env production  (rolling reload for api, restart for worker)
```

## Problem 1 — Production Cluster Deployment with Graceful Shutdown

### Problem
Configure a production Node.js HTTP API to: use all available CPU cores, restart automatically on crash, perform zero-downtime deployments, and handle in-flight requests gracefully during restarts.

### Pattern Recognition
Cluster mode + ready signal + SIGINT handler + kill_timeout — the complete production PM2 setup.

### Key Insight
Zero-downtime requires three coordinated pieces: PM2's rolling reload strategy, the application's explicit readiness signal, and the application's graceful shutdown handler. Missing any one of them breaks zero-downtime.

### Solution

```js
// src/server.js — production-ready with PM2 integration
const express = require('express');
const { createServer } = require('http');
const db = require('./db');

const app = express();
app.use(express.json());

// Routes
app.get('/health', (req, res) => res.json({ status: 'ok', pid: process.pid }));
app.get('/api/users', async (req, res) => {
  const users = await db.query('SELECT * FROM users LIMIT 100');
  res.json(users);
});

// ─────────────────────────────────────────────
// APPLICATION STARTUP WITH EXPLICIT READY SIGNAL
// ─────────────────────────────────────────────
const server = createServer(app);

async function start() {
  try {
    // All initialization before signaling readiness:
    await db.connect({ pool: { min: 2, max: 10 } });

    await new Promise((resolve, reject) => {
      server.listen(process.env.PORT || 3000, (err) => {
        if (err) return reject(err);
        console.log(`[PID ${process.pid}] Listening on port ${process.env.PORT || 3000}`);
        resolve();
      });
    });

    // Signal PM2: this worker is ready to receive traffic
    // PM2 will NOT kill old workers until this fires
    if (process.send) {
      process.send('ready');
    }

  } catch (err) {
    console.error('Startup failed:', err);
    process.exit(1); // PM2 will restart the process
  }
}

// ─────────────────────────────────────────────
// GRACEFUL SHUTDOWN — HANDLES PM2'S SIGINT
// ─────────────────────────────────────────────
let shuttingDown = false;

async function gracefulShutdown(signal) {
  if (shuttingDown) return; // Idempotent: ignore duplicate signals
  shuttingDown = true;
  console.log(`[PID ${process.pid}] ${signal} received, shutting down gracefully`);

  // Step 1: Stop accepting new connections
  // (existing keep-alive connections continue until they're idle)
  server.close(async () => {
    console.log(`[PID ${process.pid}] HTTP server closed`);

    // Step 2: Close database connections after HTTP server is done
    await db.disconnect();
    console.log(`[PID ${process.pid}] DB connections closed`);

    process.exit(0);
  });

  // Step 3: Force exit if graceful shutdown exceeds kill_timeout
  // (should be less than kill_timeout in ecosystem.config.js)
  setTimeout(() => {
    console.error(`[PID ${process.pid}] Force exit after timeout`);
    process.exit(1);
  }, 25000); // 25s — leave 5s buffer before PM2's 30s kill_timeout
}

process.on('SIGINT', () => gracefulShutdown('SIGINT'));   // pm2 reload sends this
process.on('SIGTERM', () => gracefulShutdown('SIGTERM')); // systemd / Docker sends this

start();
```

- **Long-running requests (file uploads, SSE connections)**: if a keep-alive connection is transferring a large file when SIGINT arrives, `server.close()` won't close that connection immediately — it completes naturally. Multi-app ecosystem file with `env`, `env_staging`, `env_production` blocks, different `exec_mode` and `instances` per application.

## Problem 3 — Diagnosing and Fixing a Botched Zero-Downtime Deployment

### Problem
After a `pm2 reload`, the application is returning 502 errors for about 30 seconds. Diagnose the problem systematically and implement the fix.

### Pattern Recognition
Broken zero-downtime deployment — new workers crash on startup, PM2 restarts them repeatedly, old workers are killed before new ones are stable, creating a coverage gap.

### Key Insight
`pm2 reload` is only zero-downtime if new workers start successfully. If they crash immediately, PM2 kills old workers (based on `listen_timeout`), new workers restart and crash again, and there's no stable worker to serve requests. Systematic diagnosis exposes exactly which startup step is failing.

### Solution

```bash

# ─────────────────────────────────────────────

# Check current process state:
pm2 status
# Look for: errored, stopping, restarting states
# Look for: high restart count (e.g., restarts: 47)

pm2 logs my-api --lines 100 --err

# - "Cannot find module './config'" — missing file
# - "EADDRINUSE: address already in use" — port conflict
# - "Connection refused" — database not reachable
# - Syntax errors — code bug in new version

pm2 show my-api   # or pm2 show 0 (by id)
# Shows: uptime, restart count, last restart time, memory, cpu

# ─────────────────────────────────────────────

git stash  # or git checkout previous-version

pm2 restart my-api
```

```js
// SCENARIO B: Database connection fails on startup
// Log: "Error: connect ECONNREFUSED prod-db:5432"
// Fix: implement retry logic on startup with proper error handling:

const MAX_DB_RETRIES = 5;
const DB_RETRY_DELAY = 2000;

async function connectWithRetry() {
  for (let attempt = 1; attempt <= MAX_DB_RETRIES; attempt++) {
    try {
      await db.connect();
      console.log('Database connected');
      return;
    } catch (err) {
      if (attempt === MAX_DB_RETRIES) throw err; // give up after max retries
      console.warn(`DB connection attempt ${attempt} failed, retrying in ${DB_RETRY_DELAY}ms...`);
      await new Promise(resolve => setTimeout(resolve, DB_RETRY_DELAY));
    }
  }
}

// SCENARIO C: listen_timeout too short for slow startup
// Log: no error — worker DOES start, but PM2 kills old workers before new one is listening
// Fix: increase listen_timeout AND add process.send('ready') signal:

async function start() {
  await connectWithRetry();
  await loadConfiguration();    // may be slow (remote config fetch)
  await warmupCache();          // may be slow (pre-warming caches)

  server.listen(PORT, () => {
    console.log(`Worker ${process.pid} ready on port ${PORT}`);

    // CRITICAL: only send ready AFTER server.listen() callback fires
    // This is the ONLY correct place to send this signal
    if (process.send) process.send('ready');
  });
}
```

## Common Bugs Checklist

Before shipping any PM2 configuration, verify:

1. **`exec_mode: 'cluster'` with stateful application?** — Session state, in-memory caches, or distributed locks that aren't externalized (Redis, database) will produce inconsistent behavior in cluster mode. Either make the application stateless or use `exec_mode: 'fork'`.

2. **No `process.send('ready')` signal but `wait_ready: true` configured?** — PM2 will wait `listen_timeout` milliseconds and then proceed anyway. If startup takes longer than `listen_timeout`, PM2 kills old workers while new ones aren't ready. Without `process.send('ready')`, the benefit of `wait_ready: true` is lost — add the signal.

3. **`process.send('ready')` sent before `server.listen()` callback fires?** — If the ready signal is sent before the TCP socket is bound, new workers may receive connections before they're actually listening, causing connection refused errors. Send the signal inside the `server.listen(port, () => { process.send('ready'); })` callback.

4. **`kill_timeout` less than P99 request duration?** — Long-running requests (file uploads, large queries, streaming responses) get killed mid-execution. Increase `kill_timeout` or implement connection draining with a hard maximum.

5. **`pm2 reload` without `--update-env` when env vars changed?** — Without `--update-env`, PM2 passes the environment from the originally-started workers to newly spawned workers, ignoring any changes in `ecosystem.config.js`. New workers run with old environment variables.

6. **Scheduler/cron app with `instances > 1`?** — Scheduled tasks run N times (once per instance). Always set `instances: 1` for single-execution scheduled tasks. Alternatively, use distributed locking inside the task.

7. **`watch: true` in production ecosystem config?** — File watching causes PM2 to restart on any file change, including log file writes, temporary files, and `node_modules` changes. This causes infinite restart loops in production. Use `watch: false` (the default) in production.

8. **No `pm2 save` after changing the process list?** — Changes to running processes (added apps, changed instances) are lost on server reboot unless `pm2 save` is run after each change. Automate this in your deployment script.

**Final Tip:** At the 5 YOE level, interviewers expect you to explain PM2 not just as "a tool that keeps Node.js running," but as a solution to specific, concrete problems: single-threaded CPU underutilization (solved by cluster mode), crash recovery (autorestart + backoff), and stateless application constraints (the prerequisite for cluster mode and graceful reloads to work correctly). The detail that most distinguishes fluent PM2 understanding is the relationship between `process.send('ready')`, `wait_ready: true`, and `listen_timeout` — knowing that `wait_ready` without the corresponding signal in the app code is pointless, and that the signal must be sent inside the `server.listen()` callback (not before) is the kind of subtle operational knowledge that separates configuration-copiers from practitioners who understand what each option actually does.
