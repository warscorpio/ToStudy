# `cluster` Module: Master-Worker Pattern, IPC — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why does the `cluster` module exist? What problem does it solve?**

A: Node.js runs JavaScript on a single thread. A single Node.js process can only ever use one CPU core — no matter how many cores the machine has. On a 16-core production server, a naive Node.js application leaves 15 cores idle.

The `cluster` module solves this by letting you spawn multiple Node.js **worker processes**, each running on its own core, that all share the same TCP/HTTP port. Incoming connections are distributed among the workers, multiplying throughput proportionally to CPU count.

```
                     ┌─────────────────────────┐
   Client request    │        OS Kernel         │
   ─────────────────>│   Port 3000 (shared)     │
                     └────────────┬────────────┘
                                  │ distributes connections
                     ┌────────────▼────────────┐
                     │     Master Process       │
                     │   (cluster manager)      │
                     └────┬──────┬──────┬───────┘
                          │      │      │   IPC channels
                     ┌────▼──┐ ┌─▼───┐ ┌▼────┐
                     │Worker1│ │W. 2 │ │W. N │   ← one per CPU core
                     └───────┘ └─────┘ └─────┘
                      PID 101   PID 102  PID 103
```

Each worker is a full, independent Node.js process with its own V8 instance, memory heap, and event loop. They do not share memory — they share only the listening socket.

**Q2. How does the `cluster` module relate to `child_process.fork`?**

A: `cluster.fork()` is a thin wrapper around `child_process.fork()`, with two additions:

1. It passes the **server handle** (the listening socket) from master to each worker over IPC, enabling all workers to accept connections on the same port
2. It registers the worker in `cluster.workers` and wires up lifecycle events (`online`, `exit`, `disconnect`, etc.)

Under the hood, `child_process.fork()` spawns a new Node.js process running the same entry file, with a built-in bidirectional IPC channel between parent and child. `cluster.fork()` exploits that IPC channel to pass the shared socket handle — something that plain `child_process.fork()` requires manual setup to achieve.

```typescript
import cluster from 'cluster';
import { cpus } from 'os';

// cluster.fork() is roughly:
//   const worker = child_process.fork(process.argv[1], { env: process.env });
//   worker.send('NODE_CLUSTER_SCHED_POLICY', masterHandle);
//   cluster.workers[worker.id] = wrappedWorker;
```

## Section 2: The Master-Worker Pattern

**Q3. What does a minimal cluster setup look like and how does it work?**

A: The same entry file runs in both the master and every worker. The `cluster.isPrimary` flag (formerly `cluster.isMaster`, deprecated in v16) tells the process which role it should play:

```typescript
import cluster from 'cluster';
import http from 'http';
import { cpus } from 'os';

if (cluster.isPrimary) {
  // ─── MASTER PROCESS ────────────────────────────────────────────
  const numCPUs = cpus().length;
  console.log(`Master PID ${process.pid} spawning ${numCPUs} workers`);

  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  cluster.on('exit', (worker, code, signal) => {
    console.log(`Worker ${worker.process.pid} died (${signal || code}). Restarting...`);
    cluster.fork();   // Replace the dead worker
  });

} else {
  // ─── WORKER PROCESS ────────────────────────────────────────────
  // Each worker independently creates a server. The OS handle is
  // shared — they all end up listening on the same port.
  http.createServer((req, res) => {
    res.writeHead(200);
    res.end(`Handled by worker ${process.pid}\n`);
  }).listen(3000);

  console.log(`Worker ${process.pid} started`);
}
```

When the master calls `cluster.fork()`, it spawns a child process running the same file. In the child, `cluster.isPrimary` is `false` and `cluster.isWorker` is `true`, so the `else` branch runs. The worker calls `server.listen(3000)` — but instead of binding a real socket, the cluster module intercepts the call and receives the shared handle from the master over IPC.

**Q4. What is `cluster.workers` and how do you iterate over all live workers?**

A: `cluster.workers` is a plain object mapping worker ID (a cluster-assigned integer, not the PID) to `Worker` instances. It only exists in the master process and only contains living workers — entries are removed automatically on `exit`:

```typescript
if (cluster.isPrimary) {
  // Spawn workers
  for (let i = 0; i < 4; i++) cluster.fork();

  // Access a specific worker by cluster ID (not PID):
  const worker = cluster.workers[1];

  // Iterate over all live workers:
  for (const id in cluster.workers) {
    const worker = cluster.workers[id]!;
    console.log(`Worker ${id}: PID ${worker.process.pid}`);
  }

  // Or as an array:
  const workers = Object.values(cluster.workers);
  workers.forEach(w => w?.send({ type: 'CONFIG_UPDATE', payload: newConfig }));
}
```

Useful `Worker` instance properties:
- `worker.id` — cluster-assigned ID (1, 2, 3...)
- `worker.process` — the underlying `ChildProcess` (has `.pid`)
- `worker.process.pid` — the OS process ID
- `worker.isDead()` — has the worker exited?
- `worker.isConnected()` — is the IPC channel still open?

## Section 3: Connection Distribution

**Q5. How does the cluster module distribute incoming connections across workers?**

A: The cluster module supports two scheduling strategies, controlled by `cluster.schedulingPolicy`:

**Round-robin (default on all platforms except legacy Windows):**
The **master process** accepts every incoming TCP connection and then passes the socket handle to the next available worker over IPC. The master itself never handles HTTP — it only accepts and distributes. This guarantees even distribution regardless of what the workers are doing.

```
Client → Master (accepts TCP connection) → passes socket to Worker N (round-robin)
                                         → Worker N handles the HTTP request
```

**Shared socket (`SCHED_NONE`, opt-in):**
All workers directly `accept()` on the same file descriptor. The OS kernel decides which worker gets each connection — typically the next one that calls `accept()`. Distribution can be uneven; under high load, some workers may get many more connections than others.

```typescript
import cluster from 'cluster';

// Override scheduling policy before forking:
cluster.schedulingPolicy = cluster.SCHED_RR;   // Round-robin (default)
cluster.schedulingPolicy = cluster.SCHED_NONE; // OS-level shared socket

// Or via environment variable before starting Node:
// NODE_CLUSTER_SCHED_POLICY=rr node server.js
// NODE_CLUSTER_SCHED_POLICY=none node server.js
```

In practice, round-robin provides more predictable distribution under typical HTTP workloads. The shared-socket approach can have lower latency overhead (no socket-passing over IPC) but at the cost of uneven load distribution.

**Q6. Do workers compete for connections or does the master assign them?**

A: With round-robin (default), the master **assigns** connections — workers do not compete. The master process has the actual listening socket and accepts each TCP connection itself, then passes the accepted socket file descriptor to a worker via IPC. Workers are passive recipients.

With `SCHED_NONE`, workers do **compete** — they all call `accept()` on the shared file descriptor. The OS uses its own scheduling, which tends to favor workers that recently handled a connection (the "thundering herd" effect in reverse — the most-recently-idle worker tends to get the next one, leading to uneven utilization).

```typescript
// Round-robin under the hood (conceptually, simplified):
// Master:
tcpServer.on('connection', (socket) => {
  const worker = pickNextWorker();     // Round-robin selection
  worker.process.send('socket', socket); // Pass the handle over IPC
  // socket is now owned by the worker — master drops it
});

// Worker:
process.on('message', (msg, handle) => {
  if (msg === 'socket') {
    httpServer.emit('connection', handle);  // Worker processes it
  }
});
```

## Section 4: IPC — Inter-Process Communication

**Q7. What is IPC in the context of `cluster` and how is it used?**

A: Every worker spawned by `cluster.fork()` has a built-in bidirectional IPC channel to the master — the same channel established by `child_process.fork()`. Messages are serialized with `JSON.stringify` and deserialized with `JSON.parse`, so they must be JSON-serializable. Circular references, functions, and `undefined` values are dropped.

Sending from **worker → master**:
```typescript
// In worker:
process.send({ type: 'METRIC', pid: process.pid, requestCount: 1240 });
```

Receiving in **master**:
```typescript
// In master:
cluster.on('message', (worker, message) => {
  // 'worker' is the Worker instance, 'message' is the parsed JSON
  console.log(`Worker ${worker.id} says:`, message);

  if (message.type === 'METRIC') {
    metrics.record(worker.id, message.requestCount);
  }
});

// Or on a specific worker's instance:
cluster.workers[1]?.on('message', (message) => {
  console.log('From worker 1:', message);
});
```

Sending from **master → worker**:
```typescript
// In master:
const worker = cluster.workers[2];
worker?.send({ type: 'RELOAD_CONFIG', config: newConfig });
```

Receiving in **worker**:
```typescript
// In worker:
process.on('message', (message) => {
  if (message.type === 'RELOAD_CONFIG') {
    applyConfig(message.config);
  }
});
```

**Q8. Can you pass handles (sockets, servers) over IPC, and when is this useful?**

A: Yes — `process.send(message, handle)` supports passing TCP socket and server handles as the second argument. The handle is duplicated into the receiving process using OS-level file descriptor passing (not serialized as JSON).

```typescript
// Master: manually pass an accepted socket to a specific worker
// (this is essentially what round-robin does internally)
const net = require('net');
const server = net.createServer();

server.on('connection', (socket) => {
  const worker = selectWorkerByStickyHash(socket.remoteAddress);
  worker.send('socket', socket);   // Pass the handle
  socket.unref();                  // Detach from master — worker now owns it
});

// Worker: receive the handle
process.on('message', (msg, handle) => {
  if (msg === 'socket') {
    httpServer.emit('connection', handle);  // Inject into HTTP server
  }
});
```

This technique is how **sticky sessions** are implemented manually — the master inspects the client's IP (or cookie) and always routes it to the same worker, ensuring session continuity with in-memory session stores.

**Q9. What are the performance and reliability constraints of IPC messaging?**

A: IPC has several constraints that matter in production:

**Serialization cost:** Every message is `JSON.stringify`'d in the sender and `JSON.parse`'d in the receiver. Large payloads — config objects, bulk data, log batches — add measurable CPU overhead on both sides. Keep IPC messages small and structural, not large data blobs.

**Reliability:** IPC messages are delivered in order and reliably within a process lifetime. But if the worker crashes before processing a message, the message is lost — IPC is not a durable queue. For critical cross-worker operations, use a real message broker (Redis pub/sub, etc.).

**IPC channel closure:** If the worker calls `worker.disconnect()` or crashes, the IPC channel closes. Sending to a disconnected worker throws `ERR_IPC_CHANNEL_CLOSED`. Always guard sends:

```typescript
function safeSend(worker: cluster.Worker, message: unknown): void {
  if (worker.isConnected() && !worker.isDead()) {
    worker.send(message);
  }
}
```

**No broadcast primitive:** There is no `cluster.broadcast()`. To send a message to all workers, you iterate `cluster.workers` manually:

```typescript
function broadcast(message: unknown): void {
  for (const id in cluster.workers) {
    safeSend(cluster.workers[id]!, message);
  }
}
```

## Section 5: Worker Lifecycle and Events

**Q10. What events does the cluster module emit and what do they tell you?**

A: The master process can listen on the `cluster` object for lifecycle events across all workers:

```typescript
import cluster from 'cluster';

cluster.on('fork', (worker) => {
  // Fired when cluster.fork() is called — worker object created, process not yet running
  console.log(`Worker ${worker.id} forked`);
});

cluster.on('online', (worker) => {
  // Worker process started and sent a message back to master — it's running
  console.log(`Worker ${worker.id} (PID ${worker.process.pid}) is online`);
});

cluster.on('listening', (worker, address) => {
  // Worker called server.listen() and is accepting connections
  // address: { address, family, port }
  console.log(`Worker ${worker.id} listening on port ${address.port}`);
});

cluster.on('disconnect', (worker) => {
  // IPC channel closed — either graceful disconnect or worker crashed
  // worker.exitedAfterDisconnect tells you if it was intentional
  console.log(`Worker ${worker.id} disconnected`);
});

cluster.on('exit', (worker, code, signal) => {
  // Worker process exited
  // code: exit code (0 = clean), signal: kill signal (e.g., 'SIGTERM')
  if (worker.exitedAfterDisconnect) {
    // Intentional — we called worker.disconnect() or worker.kill()
    console.log(`Worker ${worker.id} exited cleanly`);
  } else {
    // Unintentional crash — restart it
    console.error(`Worker ${worker.id} crashed (${signal || code}). Restarting...`);
    cluster.fork();
  }
});

cluster.on('message', (worker, message, handle) => {
  // Message received from a worker over IPC
});
```

The `worker.exitedAfterDisconnect` flag is the canonical way to distinguish intentional shutdown from a crash in the `exit` handler. Set it by calling `worker.disconnect()` (graceful) or `worker.kill()` (forceful) — both set this flag before the process exits.

**Q11. What is the difference between `worker.kill()`, `worker.disconnect()`, and `worker.process.kill()`?**

A: Three different termination approaches with distinct semantics:

```typescript
// worker.kill(signal?)
// Sends SIGTERM (or specified signal) to the worker process immediately.
// Sets worker.exitedAfterDisconnect = true before sending the signal.
// The process is terminated — no graceful shutdown of in-flight requests.
worker.kill();             // SIGTERM
worker.kill('SIGKILL');    // Force kill — cannot be caught or ignored

// worker.disconnect()
// Closes the IPC channel gracefully.
// Existing connections continue to be served until they close naturally.
// Once all handles are closed, the worker exits on its own.
// Sets worker.exitedAfterDisconnect = true.
// The worker stops accepting NEW connections but finishes current ones.
worker.disconnect();       // Graceful: finish in-flight requests, then exit

// worker.process.kill(signal?)
// Directly accesses the underlying ChildProcess and kills it.
// Does NOT set worker.exitedAfterDisconnect — treated as a crash in exit handler.
// Avoid unless you explicitly want crash-like behavior (e.g., testing restart logic).
worker.process.kill('SIGTERM');   // Looks like a crash to the cluster module

// In the exit handler:
cluster.on('exit', (worker, code, signal) => {
  if (worker.exitedAfterDisconnect) {
    // kill() or disconnect() was called — intentional
  } else {
    // Unhandled crash — restart
    cluster.fork();
  }
});
```

For graceful shutdowns and rolling restarts, always use `worker.disconnect()` — it lets the worker drain its existing connections before dying, which prevents cutting off clients mid-request.

## Section 6: Graceful Restarts and Zero-Downtime Deploys

**Q12. How do you implement a zero-downtime rolling restart in a cluster?**

A: A rolling restart replaces workers one at a time. The master kills one worker, waits for its replacement to come online, then moves to the next. At no point are all workers down simultaneously:

```typescript
import cluster from 'cluster';
import { cpus } from 'os';

if (cluster.isPrimary) {
  const NUM_WORKERS = cpus().length;

  // Spawn initial workers
  for (let i = 0; i < NUM_WORKERS; i++) cluster.fork();

  // Auto-restart on unexpected crashes
  cluster.on('exit', (worker) => {
    if (!worker.exitedAfterDisconnect) {
      console.log(`Worker ${worker.id} crashed — restarting`);
      cluster.fork();
    }
  });

  // Rolling restart function — call this when deploying new code
  async function rollingRestart(): Promise<void> {
    const workerIds = Object.keys(cluster.workers!);

    for (const id of workerIds) {
      await new Promise<void>((resolve) => {
        const worker = cluster.workers![Number(id)];
        if (!worker) { resolve(); return; }

        console.log(`Restarting worker ${worker.id}...`);

        // Wait for replacement to come online before killing this one
        cluster.once('online', (newWorker) => {
          console.log(`Replacement worker ${newWorker.id} online`);
          resolve();
        });

        // Disconnect gracefully — finishes in-flight requests first
        worker.disconnect();

        // Safety net: force kill after 30s if disconnect hangs
        setTimeout(() => {
          if (!worker.isDead()) {
            worker.kill();
            resolve();
          }
        }, 30_000);
      });

      // Brief pause between worker replacements
      await new Promise(r => setTimeout(r, 500));
    }

    console.log('Rolling restart complete');
  }

  // Trigger rolling restart on SIGUSR2 (common convention)
  process.on('SIGUSR2', rollingRestart);
  // Deploy: kill -USR2 <master_pid>
}
```

**Q13. How does a worker handle graceful shutdown when `worker.disconnect()` is called?**

A: When the master calls `worker.disconnect()`, the worker's server stops accepting new connections but continues to serve in-flight requests. The worker must also clean up its own resources:

```typescript
// In the worker process:
import http from 'http';

const server = http.createServer(requestHandler);
server.listen(3000);

// Handle graceful shutdown triggered by master calling worker.disconnect()
process.on('disconnect', () => {
  console.log(`Worker ${process.pid} disconnecting gracefully`);

  // Stop accepting new connections
  server.close(() => {
    console.log(`Worker ${process.pid} server closed — exiting`);
    // Clean up resources: DB connections, caches, etc.
    dbPool.end().then(() => process.exit(0));
  });

  // Force exit after timeout if server.close() hangs
  // (e.g., long-lived WebSocket connections that never close)
  setTimeout(() => {
    console.warn(`Worker ${process.pid} force-exiting after timeout`);
    process.exit(1);
  }, 30_000).unref();  // .unref() prevents this timer from keeping the process alive
});
```

The sequence for a graceful worker replacement:
1. Master calls `worker.disconnect()`
2. Worker's IPC channel closes; `'disconnect'` event fires in worker
3. Worker calls `server.close()` — no new connections accepted
4. Existing connections finish naturally
5. `server.close()` callback fires — worker exits cleanly
6. Master's `cluster.on('exit')` fires with `worker.exitedAfterDisconnect === true`

## Section 7: Shared State and Common Pitfalls

**Q14. Workers are separate processes — what does this mean for shared state?**

A: Workers do **not** share memory. Each worker has its own V8 heap, its own copies of every variable, and its own module-level state. Mutations in one worker are invisible to all others:

```typescript
// BROKEN: in-memory counter across workers
let requestCount = 0;

http.createServer((req, res) => {
  requestCount++;   // Only increments in THIS worker's memory
  res.end(`Total requests: ${requestCount}`);
  // Each worker reports its own partial count — never the true total
}).listen(3000);
```

Anything that must be shared across workers needs to live **outside all worker processes**:

| Shared state type | Solution |
|---|---|
| Request counters, metrics | Aggregate in master via IPC, or use external store |
| Session data | Redis, Memcached, or DB-backed sessions (not in-memory) |
| Rate limiting | Redis-based rate limiter (e.g., `rate-limiter-flexible`) |
| Distributed locks | Redis SETNX / Redlock |
| Pub/Sub | Redis pub/sub or a message broker |
| Configuration | Master reads config, broadcasts to workers via IPC |

**Q15. What is session affinity (sticky sessions) and when is it required?**

A: With round-robin scheduling, consecutive requests from the same client can land on different workers. If session state is stored **in-process** (in-memory express-session, in-memory WebSocket state), the client will appear to lose their session on every other request.

**Sticky sessions** route all requests from a given client to the same worker — typically by hashing the client IP or a session cookie:

```typescript
// Master: manual sticky routing via handle passing
const net = require('net');

function selectWorker(remoteAddress: string): cluster.Worker {
  const workerIds = Object.keys(cluster.workers!);
  const hash = remoteAddress
    .split('.')
    .reduce((acc, octet) => acc + parseInt(octet, 10), 0);
  const index = hash % workerIds.length;
  return cluster.workers![Number(workerIds[index])]!;
}

const proxy = net.createServer({ pauseOnConnect: true }, (connection) => {
  const worker = selectWorker(connection.remoteAddress ?? '');
  worker.send('sticky:balance', connection);
});
proxy.listen(3000);

// Worker: receive the sticky-routed socket
process.on('message', (msg: string, connection: net.Socket) => {
  if (msg === 'sticky:balance') {
    httpServer.emit('connection', connection);
    connection.resume();
  }
});
```

In practice, avoid in-process session state entirely. Use Redis-backed sessions so any worker can serve any request — this is simpler, more reliable, and works across multiple machines.

**Q16. What are common database connection pool pitfalls with clustering?**

A: Each worker creates its own connection pool. With N workers and a pool size of M per worker, you open `N × M` total connections to the database — far more than a single-process app:

```typescript
// Single process: pool of 10 connections
const pool = createPool({ max: 10 });

// With 16 workers: 16 × 10 = 160 connections
// Most databases (Postgres default: 100 max) will reject the excess connections
```

Solutions:

```typescript
// Option 1: reduce pool size per worker proportionally
const numWorkers = cpus().length;
const pool = createPool({ max: Math.ceil(100 / numWorkers) });  // ~6 each

// Option 2: use PgBouncer or a connection proxy that pools at the infrastructure level
// Workers connect to PgBouncer, which multiplexes over a smaller real pool

// Option 3: dedicated database worker (less common in Node)
// One worker holds the DB pool; others request data via IPC
// Adds latency but centralizes connection management

// Option 4: use pg-pool's built-in max total connections
// (library-specific — some ORMs expose this setting)
```

## Section 8: `cluster` vs `worker_threads`

**Q17. When should you use `cluster` vs `worker_threads`?**

A: They solve different problems and operate at different levels:

| | `cluster` | `worker_threads` |
|---|---|---|
| Unit | Separate OS processes | OS threads within one process |
| Memory | Isolated — no sharing | Can share `SharedArrayBuffer` |
| IPC | JSON over Unix socket / pipe | `MessageChannel`, `SharedArrayBuffer` |
| Crash isolation | Full — a worker crash doesn't affect others | Partial — a thread crash can destabilize the process |
| Use case | HTTP serving across CPU cores | CPU-intensive computation with data sharing |
| Port sharing | Built-in (cluster's main feature) | Not designed for this |
| Startup overhead | High — full Node.js process per worker | Lower — thread within existing process |
| Module isolation | Complete — each process has its own module cache | Shared module cache (with caveats) |

```typescript
// Use cluster for: horizontally scaling an HTTP server across cores
// ─────────────────────────────────────────────────────────────────
if (cluster.isPrimary) {
  for (let i = 0; i < cpus().length; i++) cluster.fork();
} else {
  http.createServer(handler).listen(3000);
}

// Use worker_threads for: offloading a CPU-intensive computation from the main thread
// ─────────────────────────────────────────────────────────────────
import { Worker, isMainThread, workerData, parentPort } from 'worker_threads';

if (isMainThread) {
  http.createServer((req, res) => {
    const worker = new Worker(__filename, { workerData: { input: req.body } });
    worker.on('message', (result) => res.end(JSON.stringify(result)));
  }).listen(3000);
} else {
  const result = heavyCompute(workerData.input);
  parentPort!.postMessage(result);
}
```

The common production pattern is to **combine both**: use `cluster` to create one process per CPU core (for network I/O throughput), and within each worker use `worker_threads` for CPU-intensive tasks (image processing, crypto, ML inference) so they don't block the worker's event loop.

## Section 9: Scenario-Based Questions

**Q18. "Predict what happens when a worker throws an unhandled error."**

```typescript
// worker code:
http.createServer((req, res) => {
  if (req.url === '/crash') {
    throw new Error('Unhandled error!');
  }
  res.end('OK');
}).listen(3000);
```

A: An unhandled error in a worker propagates to Node.js's internal `uncaughtException` handler. If no `uncaughtException` listener is registered, Node.js prints the stack trace and **exits with code 1**. The `cluster` module detects this via the `exit` event:

```
Worker PID 12345 died with signal null, code 1
```

In the master's `exit` handler:
```typescript
cluster.on('exit', (worker, code, signal) => {
  // code === 1, signal === null, worker.exitedAfterDisconnect === false
  // → unintentional crash → restart
  console.error(`Worker ${worker.id} crashed with code ${code}`);
  cluster.fork();
});
```

The critical behavior: **other workers are completely unaffected**. Each worker is an isolated process — a crash in one does not corrupt or affect any other. This is the main reliability advantage of the cluster model over `worker_threads` for HTTP serving.

To prevent crashes from taking down a worker at all, add a per-worker `uncaughtException` handler — though this is controversial (running after an uncaught exception leaves the process in an unknown state):

```typescript
// In worker — last resort to log before dying
process.on('uncaughtException', (err) => {
  console.error(`Worker ${process.pid} uncaught exception:`, err);
  // Still exit — don't try to recover; let the master restart a clean worker
  process.exit(1);
});
```

**Q19. "Design a cluster-based metrics aggregation system — workers collect metrics, master exposes them via a `/metrics` endpoint."**

A:

```typescript
// ─── master.ts ────────────────────────────────────────────────────────────────
import cluster from 'cluster';
import http from 'http';
import { cpus } from 'os';

interface WorkerMetrics {
  requestCount: number;
  errorCount: number;
  avgResponseMs: number;
  pid: number;
}

const metricsStore = new Map<number, WorkerMetrics>();

if (cluster.isPrimary) {
  // Spawn workers
  for (let i = 0; i < cpus().length; i++) cluster.fork();

  // Collect metrics from workers
  cluster.on('message', (worker, message) => {
    if (message.type === 'METRICS') {
      metricsStore.set(worker.id, message.data as WorkerMetrics);
    }
  });

  // Re-request metrics every 10 seconds from all workers
  setInterval(() => {
    for (const id in cluster.workers) {
      cluster.workers[id]?.send({ type: 'REPORT_METRICS' });
    }
  }, 10_000);

  // Master exposes a /metrics endpoint on a different port (not 3000)
  http.createServer((req, res) => {
    if (req.url === '/metrics') {
      const aggregated = {
        totalRequests: 0,
        totalErrors: 0,
        workers: [] as WorkerMetrics[],
      };
      for (const m of metricsStore.values()) {
        aggregated.totalRequests += m.requestCount;
        aggregated.totalErrors += m.errorCount;
        aggregated.workers.push(m);
      }
      res.writeHead(200, { 'Content-Type': 'application/json' });
      res.end(JSON.stringify(aggregated));
    } else {
      res.writeHead(404);
      res.end();
    }
  }).listen(9090);  // Metrics port separate from app port

  cluster.on('exit', (worker) => {
    metricsStore.delete(worker.id);  // Clean up dead worker's metrics
    if (!worker.exitedAfterDisconnect) cluster.fork();
  });
}

// ─── worker.ts (same file, different branch) ──────────────────────────────────
else {
  let requestCount = 0;
  let errorCount = 0;
  const responseTimes: number[] = [];

  const server = http.createServer((req, res) => {
    const start = Date.now();
    requestCount++;

    try {
      handleRequest(req, res);
    } catch (err) {
      errorCount++;
      res.writeHead(500).end();
    } finally {
      responseTimes.push(Date.now() - start);
      if (responseTimes.length > 1000) responseTimes.shift();  // Rolling window
    }
  });
  server.listen(3000);

  // Respond to master's metrics requests
  process.on('message', (msg: { type: string }) => {
    if (msg.type === 'REPORT_METRICS') {
      const avg = responseTimes.length
        ? responseTimes.reduce((a, b) => a + b, 0) / responseTimes.length
        : 0;

      process.send?.({
        type: 'METRICS',
        data: {
          requestCount,
          errorCount,
          avgResponseMs: Math.round(avg),
          pid: process.pid,
        } satisfies WorkerMetrics,
      });
    }
  });
}
```

**Q20. "How would you implement hot-reload of application configuration without restarting any workers?"**

A: The master holds the source of truth for configuration. It reads the new config and broadcasts it to all workers over IPC — no process restarts needed:

```typescript
// ─── In master ────────────────────────────────────────────────────────────────
import fs from 'fs';

let currentConfig = loadConfig('./config.json');

function loadConfig(path: string): Record<string, unknown> {
  return JSON.parse(fs.readFileSync(path, 'utf-8'));
}

function broadcastConfig(config: Record<string, unknown>): void {
  for (const id in cluster.workers) {
    cluster.workers[id]?.send({ type: 'CONFIG_UPDATE', config });
  }
}

// Reload on SIGHUP (standard Unix convention for config reload)
process.on('SIGHUP', () => {
  try {
    currentConfig = loadConfig('./config.json');
    console.log('Config reloaded — broadcasting to workers');
    broadcastConfig(currentConfig);
  } catch (err) {
    console.error('Config reload failed — keeping current config:', err);
    // Crucially: DO NOT broadcast invalid config — workers keep the old one
  }
});

// Send initial config when a new worker comes online
cluster.on('online', (worker) => {
  worker.send({ type: 'CONFIG_UPDATE', config: currentConfig });
});

// ─── In worker ────────────────────────────────────────────────────────────────
interface AppConfig {
  rateLimit: number;
  timeout: number;
  featureFlags: Record<string, boolean>;
}

let config: AppConfig = DEFAULT_CONFIG;

process.on('message', (msg: { type: string; config?: AppConfig }) => {
  if (msg.type === 'CONFIG_UPDATE' && msg.config) {
    config = msg.config;
    console.log(`Worker ${process.pid}: config updated`);
    // No restart needed — next request uses new config
  }
});

http.createServer((req, res) => {
  // config is read here on each request — always reflects latest broadcast
  applyRateLimit(req, config.rateLimit);
  setRequestTimeout(req, config.timeout);
  handleRequest(req, res, config.featureFlags);
}).listen(3000);
```

This pattern — master as config owner, workers as stateless consumers — extends to feature flags, A/B test configuration, and allowlists. The master is the single source of truth; workers never read config files directly.

## Quick Reference Table

| Concept | Detail |
|---|---|
| `cluster.isPrimary` | `true` in the master process; use to split master/worker code paths |
| `cluster.isWorker` | `true` in worker processes |
| `cluster.fork([env])` | Spawn a new worker; returns a `Worker` instance |
| `cluster.workers` | `{ [id]: Worker }` — all live workers; only available in master |
| `cluster.schedulingPolicy` | `SCHED_RR` (round-robin, default) or `SCHED_NONE` (OS-level) |
| `worker.id` | Cluster-assigned integer ID (not the PID) |
| `worker.process.pid` | OS-level PID of the worker |
| `worker.send(msg)` | Master → worker IPC (JSON-serialized) |
| `process.send(msg)` | Worker → master IPC (JSON-serialized) |
| `worker.disconnect()` | Graceful shutdown: close IPC, finish requests, then exit |
| `worker.kill(signal?)` | Immediate SIGTERM (or other signal); `exitedAfterDisconnect = true` |
| `worker.isDead()` | Has the worker process exited? |
| `worker.isConnected()` | Is the IPC channel still open? |
| `worker.exitedAfterDisconnect` | `true` if `disconnect()`/`kill()` was called — use in `exit` handler to tell crash from intentional |
| `cluster.on('exit', cb)` | Fires when any worker exits; `cb(worker, code, signal)` |
| `cluster.on('message', cb)` | Fires when any worker sends IPC; `cb(worker, message, handle)` |
| Shared memory | Workers are separate processes — no shared memory. Use Redis or IPC for shared state. |
| Session affinity | Round-robin breaks in-memory sessions; use Redis-backed sessions or sticky routing |
| DB connection pools | Each worker opens its own pool — `N workers × M pool = N×M connections` |
| `cluster` vs `worker_threads` | cluster: process-per-core for HTTP throughput; worker_threads: threads for CPU tasks with shared memory |
| Zero-downtime restart | `worker.disconnect()` one at a time, wait for replacement `'online'` before next |

**Tip for interviews:** Five things separate strong candidates on this topic: (1) understanding that **`cluster.fork()` is built on `child_process.fork()`** and that the key addition is sharing the listening socket handle via IPC — not just "it spawns processes"; being able to explain how the master accepts connections and passes socket handles to workers in round-robin mode; (2) knowing the **`worker.exitedAfterDisconnect` flag** and why it exists — it's the only reliable way to distinguish a crash from an intentional shutdown in the `exit` handler, and using it correctly is the difference between infinite crash loops and clean rolling restarts; (3) the **shared-state trap** — workers are isolated processes, and any code that assumes in-process state (in-memory sessions, local counters, singleton caches) will silently misbehave in a cluster without producing an error; being able to enumerate the consequences (sessions lost, counters undercounted, locks broken) and their solutions (Redis, IPC aggregation) demonstrates production experience; (4) the **`N × M` database connection explosion** — `numWorkers × poolSize` total connections, which can exhaust Postgres's `max_connections` and cause cascading failures on cluster restarts; and (5) understanding **when to use `worker_threads` instead of `cluster`** — clusters are for scaling HTTP throughput across cores (I/O bound work); worker_threads are for offloading CPU-intensive computation from the main event loop while keeping shared memory access; the mature production pattern is to combine both.
