## Topic A: Worker Thread Fundamentals

### Section A1: Core Concepts

**Q1. What is the `worker_threads` module, and what problem does it solve that neither async I/O nor `child_process` fully addresses?**

A: The `worker_threads` module enables running JavaScript on multiple OS threads within a single Node.js process. It solves the **CPU-bound parallelism** problem that neither async I/O nor `child_process` handles well. Async I/O solves I/O-bound bottlenecks by delegating work to the OS or libuv thread pool while keeping the event loop free — but it doesn't help when JavaScript itself is doing the heavy lifting (sorting large datasets, image processing, cryptography, machine learning inference). `child_process.fork()` creates a fully separate Node.js process, which solves the CPU problem but has high overhead: separate V8 heap initialization (~50-100ms), no shared memory, and IPC limited to serialized JSON. `worker_threads` occupies the middle ground: each worker gets its own V8 instance and event loop (true CPU parallelism), but runs within the same OS process, enabling **shared memory via `SharedArrayBuffer`**, lower creation overhead, and shared native addon instances.

```
Problem: CPU-intensive JavaScript on a single thread blocks EVERYTHING

     Main thread only:                 With worker_threads:
  ┌──────────────────────┐         ┌──────────┐  ┌──────────┐
  │ [sort 10M records]   │ 800ms   │ Main     │  │ Worker 1 │
  │ (blocks all requests)│ ───────>│ (I/O)    │  │ (sort)   │
  └──────────────────────┘         └──────────┘  └──────────┘
                                      run concurrently on separate OS threads

  child_process.fork(): 60-100ms to start + separate heap + JSON IPC only
  worker_threads:       10-30ms to start + shared memory possible + structured clone IPC
```

**Q2. What is the architecture of a worker thread relative to the main thread?**

A: Each worker thread has its own: **V8 isolate** (independent heap, garbage collection, and JavaScript engine instance), **event loop** (powered by libuv, the same as the main thread's), **module cache** (requiring modules is independent), and **call stack**. They do NOT share: the V8 heap (no shared JavaScript objects by default), global state (each worker has its own `global`), or the main thread's event loop. What they DO share: the OS process (same PID), the libuv thread pool (the four default threads for file I/O are shared among all workers), native code loaded from `.node` addons (if the addon supports it), and `SharedArrayBuffer` memory regions explicitly shared between threads. The key architectural implication: running CPU-intensive code in a worker never blocks the main thread's event loop — they execute concurrently on separate OS threads managed by the OS scheduler.

```
Single Node.js Process (PID 12345):

  ┌─────────────────────────┐   ┌──────────────────────────┐
  │  Main Thread             │   │  Worker Thread 1          │
  │  ┌────────┐ ┌─────────┐ │   │  ┌────────┐ ┌─────────┐  │
  │  │  V8    │ │ Event   │ │   │  │  V8    │ │ Event   │  │
  │  │ Heap A │ │ Loop    │ │   │  │ Heap B │ │ Loop    │  │
  │  └────────┘ └─────────┘ │   │  └────────┘ └─────────┘  │
  │                          │   │                           │
  │  [postMessage channel]───┼───┼───[postMessage channel]  │
  │                          │   │                           │
  │  [SharedArrayBuffer]─────┼───┼───[SharedArrayBuffer]    │
  └─────────────────────────┘   └──────────────────────────┘
         │                                    │
         └────────────────────────────────────┘
              Shared: libuv thread pool, OS process, native addons
```

**Q3. How do you create a Worker, and what are the key constructor options?**

A: `new Worker(filename, options)` creates a worker. `filename` can be a JavaScript file path, a URL, or (with `eval: true`) inline JavaScript code. Key options:

- **`workerData`**: data passed to the worker at creation — available as `workerData` in the worker file immediately. Cloned via structured clone (not a reference).
- **`transferList`**: array of transferable objects (ArrayBuffers, MessagePorts) to transfer (not clone) from the parent.
- **`env`**: environment variables for the worker; use `SHARE_ENV` (from `worker_threads`) to share the parent's environment.
- **`resourceLimits`**: `{ maxOldGenerationSizeMb, maxYoungGenerationSizeMb, codeRangeSizeMb, stackSizeMb }` — caps the worker's memory.
- **`eval`**: if `true`, treats `filename` as inline code string.
- **`name`**: display name for debugging.

```js
const { Worker, isMainThread, workerData, SHARE_ENV } = require('worker_threads');

if (isMainThread) {
  const worker = new Worker('./heavy-task.js', {
    workerData: { inputData: [1, 2, 3], config: { threshold: 0.5 } },
    env: SHARE_ENV,                  // share parent's process.env
    resourceLimits: { maxOldGenerationSizeMb: 256 }, // cap at 256MB heap
    name: 'heavy-task-worker',       // visible in debugger/profiler
  });

  worker.on('message',  (result) => console.log('Got:', result));
  worker.on('error',    (err)    => console.error('Worker error:', err));
  worker.on('exit',     (code)   => console.log('Exited with code:', code));
}
```

**Q4. What is `workerData`, how is it passed to the worker, and what distinguishes it from using `postMessage`?**

A: `workerData` is the **initial, one-time data package** delivered to a worker at creation time. It is available synchronously as `require('worker_threads').workerData` the moment the worker script begins executing — before any async operations or message listeners are set up. It is cloned using the structured clone algorithm when the worker is constructed. `postMessage`, by contrast, is **ongoing bidirectional communication** — either side can call it at any time during the worker's lifetime, and the receiver handles the message asynchronously via the `'message'` event. The practical distinction: use `workerData` for configuration, initial datasets, and parameters needed before the worker starts its event loop; use `postMessage` for task results, streaming progress updates, and sending additional work to an already-running worker. `workerData` cannot be used for responses — it's one-way, parent-to-worker, at-creation-time only.

```js
// workerData: available synchronously, one-time initialization
const { workerData } = require('worker_threads');
const { threshold, modelWeights } = workerData; // immediately available
// No 'message' listener needed to receive initial config

// postMessage: asynchronous, bidirectional, multiple times
parentPort.on('message', (task) => {
  const result = processTask(task, threshold); // uses workerData threshold
  parentPort.postMessage({ result, taskId: task.id }); // responds via postMessage
});
```

**Q5. What is `parentPort`, and how does bidirectional communication work between parent and worker?**

A: `parentPort` is the worker's end of the communication channel to the parent thread. It is a `MessagePort` instance — specifically the worker's side of the implicit `MessageChannel` that Node.js creates when you use `new Worker(...)`. The parent communicates via `worker.postMessage(data)` → received as `parentPort.on('message', cb)` in the worker. The worker responds via `parentPort.postMessage(result)` → received as `worker.on('message', cb)` in the parent. Both sides are symmetric `MessagePort` objects. The channel is automatically established when the worker is created; no manual `MessageChannel` setup is needed for basic parent-worker communication.

```js
// ─── worker.js ───────────────────────────────────────────────
const { parentPort } = require('worker_threads');

// Receive tasks from parent:
parentPort.on('message', ({ type, payload }) => {
  if (type === 'PROCESS') {
    const result = heavyCompute(payload);
    parentPort.postMessage({ type: 'RESULT', result });
  } else if (type === 'SHUTDOWN') {
    parentPort.postMessage({ type: 'GOODBYE' });
    process.exit(0);
  }
});

// ─── main.js ─────────────────────────────────────────────────
const worker = new Worker('./worker.js');

worker.postMessage({ type: 'PROCESS', payload: { data: [1,2,3] } });

worker.on('message', ({ type, result }) => {
  if (type === 'RESULT') console.log('Result:', result);
});
```

**Q6. What is `isMainThread`, and what is the single-file worker pattern and its trade-offs?**

A: `isMainThread` is a boolean that is `true` in the main thread and `false` in any worker thread. It enables the **single-file worker pattern**: a single JavaScript file contains both the main-thread logic and the worker logic, distinguished by the `isMainThread` check. The advantage: no separate file needed — simpler project structure, easier code sharing, single deployment unit. The trade-offs: (1) the entire module is evaluated in both contexts — all `require()` calls and top-level code at module scope run in both main and worker; expensive initializations must be guarded with `if (isMainThread)`. (2) bundlers and transpilers (webpack, esbuild) need special handling — the `__filename` reference inside the `Worker` constructor must resolve correctly. (3) Debugging is slightly harder with mixed logic in one file.

```js
// single-file-worker.js
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

if (isMainThread) {
  // ─── MAIN THREAD SECTION ────────────────────────────────
  console.log('Main thread: spawning worker');
  const worker = new Worker(__filename, {  // __filename: this file IS the worker
    workerData: { numbers: [1, 2, 3, 4, 5] }
  });
  worker.on('message', (sum) => console.log('Sum:', sum)); // → 15
  worker.on('exit', (code) => console.log('Worker done:', code));

} else {
  // ─── WORKER THREAD SECTION ──────────────────────────────
  const { numbers } = workerData;
  const sum = numbers.reduce((a, b) => a + b, 0);
  parentPort.postMessage(sum); // send result back to main
  // Worker exits when all tasks complete (no more message listeners, nothing pending)
}
```

### Section A2: Message Passing Details

**Q7. What is the structured clone algorithm, what can it clone, and what can it NOT clone?**

A: The structured clone algorithm (SCA) is the serialization mechanism used by `postMessage`. It is more powerful than `JSON.stringify` but has important limitations. **Can clone**: all primitives (number, string, boolean, null, undefined, BigInt, Symbol is NOT cloned — TypeError), `Date`, `RegExp`, `ArrayBuffer`, `SharedArrayBuffer` (reference shared, not cloned), typed arrays (`Int32Array`, `Float64Array`, etc.), `Map`, `Set`, plain objects and arrays (including nested), `Error` objects, `Blob` and `File` (Node.js 18+). **Cannot clone**: functions (TypeError), DOM nodes (browser only), objects with unserializable internal state (e.g., `Promise`, `WeakMap`, `WeakSet`), class instances lose their prototype chain (methods are not cloned — only data properties survive). SCA is always a deep copy — circular references are preserved (unlike JSON), and multiple references to the same object are correctly represented as the same object in the clone.

```js
// What survives structured clone:
const msg = {
  num: 42,              ✓  → 42
  str: 'hello',         ✓  → 'hello'
  date: new Date(),     ✓  → Date (full Date object, not string)
  regex: /abc/gi,       ✓  → /abc/gi
  map: new Map([[1,2]]),✓  → Map with same entries
  set: new Set([1,2]),  ✓  → Set
  arr: [1,[2,3]],       ✓  → deep copy
  typed: new Uint8Array([1,2,3]), ✓ → new Uint8Array (copy of data)
};

// What does NOT survive:
const bad = {
  fn: () => 42,                    ✗  DataCloneError: function not cloneable
  sym: Symbol('id'),               ✗  DataCloneError
  promise: Promise.resolve(),      ✗  DataCloneError
  weakMap: new WeakMap(),          ✗  DataCloneError
  proto: Object.create({ method() {} }), → method() lost (prototype not cloned)
  instance: new MyClass(),         → MyClass methods lost (just plain object)
};
```

**Q8. What are transferable objects, why do they enable zero-copy transfer, and what happens to the sender after transfer?**

A: Transferable objects are special objects that can be **moved** (not cloned) to another thread — no data is copied; ownership is transferred. After transfer, the sender's reference becomes detached (neutered): `ArrayBuffer.byteLength === 0`, the buffer is no longer accessible from the sending side. This is a zero-copy operation for potentially large data. Transferable types in Node.js: `ArrayBuffer`, `MessagePort`, `ReadableStream`, `WritableStream`, `TransformStream` (Node.js 18+). A `SharedArrayBuffer` is NOT transferred (it has no owner to transfer — all threads can access it simultaneously). To transfer, pass the object in the `transfer` array (second argument to `postMessage` or `transferList` in Worker constructor).

```js
// Without transfer: 100MB COPIED between threads (slow, doubles memory)
const bigBuffer = new ArrayBuffer(100 * 1024 * 1024); // 100MB
worker.postMessage({ buf: bigBuffer }); // clones 100MB → 200MB total in process

// With transfer: ZERO-COPY, buffer ownership moved to worker
const bigBuffer2 = new ArrayBuffer(100 * 1024 * 1024);
worker.postMessage({ buf: bigBuffer2 }, [bigBuffer2]); // transfer (zero-copy)
console.log(bigBuffer2.byteLength); // 0 — buffer is detached! can't use it anymore

// In worker: receives full 100MB buffer
const { buf } = message;
console.log(buf.byteLength); // 104857600 ✓

// Round-trip pattern: worker sends buffer back when done
parentPort.on('message', ({ buf }) => {
  processData(buf);
  parentPort.postMessage({ buf }, [buf]); // transfer back to parent
});
```

**Q9. What is `MessageChannel`, and when would you use it for direct worker-to-worker communication?**

A: `MessageChannel` creates a pair of connected `MessagePort` objects (`port1` and `port2`). Sending a message to one port delivers it to the other. By default, workers can only communicate with their parent. `MessageChannel` enables **worker-to-worker communication** by: (1) creating a channel in the main thread; (2) transferring one port to Worker A and the other port to Worker B via `postMessage` with `transferList`; (3) Workers A and B then communicate directly without the main thread relaying messages. This reduces latency (no main thread hop) and simplifies orchestration when workers need to pipeline data (Worker A processes raw data, sends directly to Worker B for aggregation).

```js
const { Worker, MessageChannel } = require('worker_threads');

const { port1, port2 } = new MessageChannel();

const workerA = new Worker('./worker-a.js');
const workerB = new Worker('./worker-b.js');

// Transfer port1 to workerA and port2 to workerB:
workerA.postMessage({ peerPort: port1 }, [port1]); // transfer: port1 detached here
workerB.postMessage({ peerPort: port2 }, [port2]);

// Now workerA and workerB communicate directly:
// ─── worker-a.js ─────────────────────────────────────────
const { workerData, parentPort } = require('worker_threads');

parentPort.once('message', ({ peerPort }) => {
  peerPort.postMessage({ data: computePartA() }); // direct to workerB
  peerPort.on('message', (result) => {
    parentPort.postMessage({ finalResult: result }); // notify main when done
  });
});
```

**Q10. What is `receiveMessageOnPort`, and when is synchronous message receiving useful?**

A: `receiveMessageOnPort(port)` synchronously checks if a message is available on the given `MessagePort` and returns it as `{ message: value }` or `undefined` if none is available. It does NOT block — it's a non-blocking poll. Its primary use: in workers where you need to periodically check for control messages (e.g., "should I stop?") without setting up an async `'message'` listener — useful in tight synchronous computation loops where the worker can't yield to the event loop. Commonly paired with `SharedArrayBuffer` + `Atomics.wait` patterns: `Atomics.wait` blocks the thread until a signal arrives, then `receiveMessageOnPort` retrieves the associated message data. This creates a synchronous communication channel useful in scenarios where the worker must perform blocking operations.

```js
const { receiveMessageOnPort, MessageChannel } = require('worker_threads');
const { port1, port2 } = new MessageChannel();

// Non-blocking poll — receive if available, null if not:
port1.postMessage('hello');
const received = receiveMessageOnPort(port2); // { message: 'hello' }
const empty    = receiveMessageOnPort(port2); // undefined (no more messages)

// In a computation loop — check for cancellation:
function computeWithCancellation(port) {
  for (let i = 0; i < 1_000_000; i++) {
    if (i % 1000 === 0) { // check every 1000 iterations
      const msg = receiveMessageOnPort(port);
      if (msg?.message?.type === 'CANCEL') {
        console.log('Cancelled at iteration', i);
        return null;
      }
    }
    doHeavyWork(i);
  }
}
```

**Q11. How do you handle errors in workers, and what are the four key events a Worker instance emits?**

A: A Worker instance is an `EventEmitter` that emits four key events: **`'message'`** — received when the worker calls `parentPort.postMessage()` — carries the deserialized message data; **`'error'`** — received when the worker throws an unhandled error or rejects a top-level Promise — carries the Error object (if no listener is registered, the error is thrown in the main thread); **`'exit'`** — emitted when the worker's event loop drains or `process.exit()` is called — carries the integer exit code (0 = clean exit, non-zero = error); **`'messageerror'`** — emitted when a received message fails to deserialize — rare but possible with malformed buffers. Best practice: always attach `'error'` and `'exit'` listeners before the worker starts running. Unhandled rejections inside workers since Node.js 15+ are treated as uncaught exceptions and propagate via the `'error'` event.

```js
const worker = new Worker('./task.js', { workerData: payload });

worker.on('message', (result) => {
  console.log('Result:', result);
});

worker.on('error', (err) => {
  // Uncaught exception or unhandled rejection in worker
  console.error('Worker threw:', err.message);
  // Restart worker or fail gracefully:
  restartWorker();
});

worker.on('exit', (code) => {
  if (code !== 0) {
    console.error(`Worker stopped with exit code ${code}`);
  }
  // code=1: uncaught exception; code=null: worker.terminate() called
});

worker.on('messageerror', (err) => {
  console.error('Failed to deserialize message:', err);
});

// Gracefully terminate a running worker:
await worker.terminate(); // returns exit code; resolves when worker stops
```

**Q12. What is the worker lifecycle from creation to termination?**

A: The worker lifecycle has four stages: **(1) Initialization**: `new Worker(filename, options)` is called — Node.js creates a new V8 isolate and OS thread, clones `workerData` via structured clone, and begins executing the worker file from the top. **(2) Running**: the worker's event loop runs, processing message events, async I/O, timers, etc. — completely independently of the main thread's event loop. **(3) Natural exit**: when the worker's event loop has no more work (no pending timers, no active message listeners, no open handles), the thread exits cleanly with code 0 — the main thread receives the `'exit'` event. **(4) Forced termination**: `worker.terminate()` sends a signal to stop the worker's event loop; the worker exits with code 1 (or null in some Node.js versions). Workers do not automatically exit when `parentPort.postMessage` returns — the worker's event loop must genuinely empty.

```js
// Worker exits naturally (event loop drains):
// worker.js:
const { parentPort, workerData } = require('worker_threads');
const result = heavyCompute(workerData.input);
parentPort.postMessage(result);
// ← No more listeners, timers, or async operations. Event loop drains → exit code 0

// Worker stays alive (event loop has active listener):
// worker.js:
parentPort.on('message', (task) => { // ← active listener keeps event loop alive
  parentPort.postMessage(process(task));
});
// Worker stays alive until: parentPort.close() OR worker.terminate() from main

// Explicitly exit from worker:
parentPort.on('message', (msg) => {
  if (msg === 'SHUTDOWN') process.exit(0); // or parentPort.close()
  else handleTask(msg);
});
```

## Topic B: Shared Memory and Architecture Patterns

### Section B1: SharedArrayBuffer and Atomics

**Q13. What is `SharedArrayBuffer`, and how does it differ from transferring an `ArrayBuffer`?**

A: `SharedArrayBuffer` (SAB) is a fixed-size binary data buffer that multiple threads can access *simultaneously* — changes made by one thread are immediately visible to all other threads without any message passing. This is fundamentally different from `ArrayBuffer` transfer: when an `ArrayBuffer` is transferred, ownership moves and the sender's reference is detached (only one thread owns it at a time). With `SharedArrayBuffer`, all threads hold valid references to the same memory region — writes from any thread are immediately visible in all other threads. This enables high-throughput communication patterns like ring buffers and progress counters without serialization overhead. The trade-off: shared mutable state without coordination leads to data races; `Atomics` must be used for safe concurrent access.

```js
// ArrayBuffer transfer: one owner at a time (like moving a file)
const buf = new ArrayBuffer(1024);
worker.postMessage({ buf }, [buf]);
console.log(buf.byteLength); // 0 — detached! one owner (worker) now

// SharedArrayBuffer: all threads see same memory (like a shared file on disk)
const sharedBuf = new SharedArrayBuffer(1024);
const view = new Int32Array(sharedBuf);
view[0] = 42;

worker.postMessage({ sharedBuf }); // NOT in transferList — it's shared, not moved
// Worker receives the SAME sharedBuf (same physical memory)
// If worker writes view[0] = 99, main thread sees 99 immediately
// No postMessage round-trip needed!

// Inside worker:
const { sharedBuf } = workerData;
const sharedView = new Int32Array(sharedBuf);
sharedView[0] = 99; // immediately visible in main thread
```

**Q14. What is a data race, and why does `SharedArrayBuffer` require synchronized access via `Atomics`?**

A: A **data race** occurs when two or more threads access the same memory location concurrently, at least one access is a write, and there is no synchronization mechanism to order the accesses. The result is undefined behavior — the final value depends on the CPU's execution order, which is non-deterministic. Even a simple `i++` operation is three separate instructions (read → increment → write): two threads performing `i++` concurrently may both read the same value, both increment, and both write the same result, effectively losing one increment. `Atomics` provides operations that are **guaranteed to be atomic** (indivisible at the CPU level): `Atomics.add`, `Atomics.sub`, `Atomics.load`, `Atomics.store`, `Atomics.compareExchange`, etc. These are implemented as CPU-level atomic instructions (LOCK prefix on x86) that prevent other threads from interleaving.

```js
// DATA RACE — DO NOT DO THIS:
const counter = new Int32Array(new SharedArrayBuffer(4));
counter[0] = 0;

// Thread A and Thread B both do:
counter[0]++; // read 0, increment, write 1

// Both threads might read 0 simultaneously → both write 1 → counter = 1 (not 2!)
// Expected: 2. Actual: 1. This is a data race.

// SAFE — using Atomics:
Atomics.add(counter, 0, 1); // atomic read-modify-write at index 0
// CPU guarantees this is indivisible — the counter correctly reaches 2

// Atomics.load/store prevent torn reads/writes (partial reads of multi-byte values):
Atomics.store(counter, 0, 42); // atomically write 42
const val = Atomics.load(counter, 0); // atomically read

// Atomics.compareExchange — conditional atomic write (test-and-set):
const oldVal = Atomics.compareExchange(counter, 0, 42, 100);
// If counter[0] === 42, set it to 100 and return 42 (old value)
// If counter[0] !== 42, do nothing and return the actual current value
```

**Q15. What are the Atomics operations, and what two categories do they fall into?**

A: Atomics operations fall into two categories: **data operations** (atomic reads/writes/modifications) and **synchronization operations** (blocking and signaling). Data operations: `Atomics.load(ta, index)` — atomic read; `Atomics.store(ta, index, value)` — atomic write; `Atomics.add/sub/and/or/xor(ta, index, value)` — atomic read-modify-write, returns OLD value; `Atomics.compareExchange(ta, index, expected, replacement)` — atomic CAS (compare-and-swap), the foundation of lock-free algorithms; `Atomics.exchange(ta, index, value)` — atomic swap, returns old value. Synchronization operations: `Atomics.wait(ta, index, value, timeout)` — blocks the calling thread until `ta[index] !== value`; `Atomics.notify(ta, index, count)` — wakes up threads blocked in `Atomics.wait`. Crucially: `Atomics.wait` **cannot be called on the main thread** (it would freeze the event loop) — only worker threads can block.

```js
const shared = new Int32Array(new SharedArrayBuffer(4));

// ─── MAIN THREAD — cannot use Atomics.wait ──────────────────
// Use Atomics.notify to wake workers:
Atomics.store(shared, 0, 1); // signal that work is ready
Atomics.notify(shared, 0, 1); // wake up 1 waiting worker

// ─── WORKER THREAD — can use Atomics.wait ───────────────────
// Block until shared[0] changes from 0:
const waitResult = Atomics.wait(shared, 0, 0, 5000); // wait up to 5000ms
// Returns 'ok' (notified), 'timed-out' (timeout elapsed), 'not-equal' (already ≠ value)
if (waitResult === 'ok') {
  const value = Atomics.load(shared, 0);
  // process value
}

// Atomics.waitAsync: non-blocking wait (works on main thread too, returns Promise):
const { async: isAsync, value: waitPromise } = Atomics.waitAsync(shared, 0, 0);
// Available since Node.js 16 — resolves when notified or timed out
```

**Q16. What is the `Atomics.wait` / `Atomics.notify` pattern, and what synchronization does it implement?**

A: `Atomics.wait` + `Atomics.notify` implements **condition variable** semantics — a primitive for one thread to signal another that a condition has changed. The canonical pattern: a worker calls `Atomics.wait(ta, index, expectedValue)` to sleep until the value at that index changes from `expectedValue`. The main thread writes a new value to that index and calls `Atomics.notify(ta, index)` to wake the sleeping worker. This is more efficient than polling — a waiting worker consumes no CPU while blocked (unlike a busy-wait loop). Combined with `SharedArrayBuffer` data buffers and `Atomics` data operations, this creates a complete inter-thread communication system that can achieve higher throughput than `postMessage` for high-frequency, small-data scenarios (ring buffer queues, work-stealing schedulers, high-frequency signal processing).

```js
// Semaphore using Atomics.wait/notify:
const SEMAPHORE_INDEX = 0;
const semaphoreBuffer = new SharedArrayBuffer(4);
const semaphore = new Int32Array(semaphoreBuffer);

// ─── Worker: wait for work to be available ─────────────────
function workerWait() {
  while (true) {
    Atomics.wait(semaphore, SEMAPHORE_INDEX, 0); // block until value ≠ 0
    // Atomically decrement (take one "token"):
    const prev = Atomics.compareExchange(semaphore, SEMAPHORE_INDEX, 1, 0);
    if (prev === 1) {
      // Successfully acquired — do work
      doWork();
    }
    // else: lost the race (another worker took it) — wait again
  }
}

// ─── Main thread: signal worker that work is ready ─────────
function mainSignal() {
  // Produce work, then signal:
  Atomics.store(semaphore, SEMAPHORE_INDEX, 1); // post one token
  Atomics.notify(semaphore, SEMAPHORE_INDEX, 1); // wake one waiting worker
}
```

**Q17. When should you choose `SharedArrayBuffer` over `postMessage`, and when is `postMessage` preferable?**

A: **Prefer `SharedArrayBuffer`** when: (1) you need to share large amounts of data that would be expensive to clone (image frames, audio buffers, large typed arrays); (2) workers need to see each other's writes immediately without serialization latency (real-time processing, game loops); (3) you're implementing high-throughput inter-thread communication (ring buffers, work queues where `postMessage` overhead is measurable). **Prefer `postMessage`** when: (1) data is small-to-medium and copy cost is acceptable; (2) isolation is important — separate copies prevent accidental cross-thread mutations; (3) you're sending structured data (objects, Maps, Errors) that `SharedArrayBuffer` can't represent; (4) your team is not experienced with concurrent programming — `postMessage` is harder to misuse than shared memory. The rule of thumb: start with `postMessage` for correctness and simplicity; switch to `SharedArrayBuffer` only when profiling shows message-passing is a bottleneck.

### Section B2: Architecture and Performance

**Q18. What is the overhead of creating a Worker, and what does that imply for architecture?**

A: Creating a Worker involves: spinning up a new OS thread, initializing a new V8 isolate (heap, GC, JIT compiler state), loading and executing the worker script (module resolution, parsing, compilation), and establishing the communication channel. In practice: **10-60ms** startup time (varies by system load and worker script complexity), **~4-10MB baseline memory** for the V8 isolate even before any application code runs. Implications: (1) creating a Worker per request (like a process per request in CGI) is prohibitively expensive for short tasks — the overhead exceeds the work being done; (2) the correct pattern for short, frequent tasks is a **thread pool** (workers created upfront, reused across tasks); (3) Workers are appropriate for tasks that take longer than ~50ms — below that threshold, the creation overhead dominates. For tasks <1ms, keep them on the main thread or use the existing libuv thread pool for I/O.

```
Task duration vs Worker overhead:

  100μs task:  Worker overhead (50ms) = 500x the task duration → DON'T use worker
  10ms task:   Worker overhead (50ms) = 5x the task duration   → Marginal (use pool)
  100ms task:  Worker overhead (50ms) = 0.5x the task duration → Beneficial
  1000ms task: Worker overhead (50ms) = 0.05x the task         → Always beneficial

Thread pool amortizes creation cost:
  Without pool: 100 tasks × 50ms creation = 5000ms wasted
  With pool (4 workers): 50ms × 4 creation = 200ms one-time cost, then zero overhead
```

**Q19. What are the key components of a thread pool implementation with `worker_threads`?**

A: A production-quality thread pool needs: **(1) Fixed worker count** — created at startup, kept alive for the process lifetime; **(2) Task queue** — FIFO queue of pending tasks with their associated `resolve`/`reject` callbacks; **(3) Available worker tracking** — which workers are idle and ready to accept tasks; **(4) Task dispatch** — when a worker becomes idle (after completing a task), immediately assign the next queued task; **(5) Error handling** — if a worker crashes, optionally restart it to maintain pool size; **(6) Graceful shutdown** — `worker.terminate()` all workers when the pool is no longer needed. The worker script must be designed to receive tasks via `postMessage`, process them, send results back, and then await the next task (keep-alive loop).

```js
// ─── pool-worker.js — long-lived worker awaiting tasks ──────
const { parentPort } = require('worker_threads');

parentPort.on('message', ({ taskId, task }) => {
  try {
    const result = runTask(task); // CPU-bound work
    parentPort.postMessage({ taskId, result });
  } catch (error) {
    parentPort.postMessage({ taskId, error: { message: error.message } });
  }
  // No process.exit() — stays alive for next task
});

// ─── thread-pool.js — pool implementation ───────────────────
class ThreadPool {
  #workers;
  #queue = [];
  #taskCounter = 0;
  #pending = new Map(); // taskId → { resolve, reject }

  constructor(workerFile, size = 4) {
    this.#workers = Array.from({ length: size }, () => this.#createWorker(workerFile));
  }

  #createWorker(file) {
    const w = { worker: new Worker(file), busy: false };
    w.worker.on('message', ({ taskId, result, error }) => {
      const { resolve, reject } = this.#pending.get(taskId);
      this.#pending.delete(taskId);
      w.busy = false;
      error ? reject(new Error(error.message)) : resolve(result);
      this.#dispatch(); // pick up next queued task
    });
    w.worker.on('error', (err) => {
      // Worker crashed — find its pending task and reject it:
      // (In production: also restart the worker here)
      console.error('Worker crashed:', err);
      w.busy = false;
      this.#dispatch();
    });
    return w;
  }

  run(task) {
    return new Promise((resolve, reject) => {
      const taskId = ++this.#taskCounter;
      this.#pending.set(taskId, { resolve, reject });
      this.#queue.push({ taskId, task });
      this.#dispatch();
    });
  }

  #dispatch() {
    if (!this.#queue.length) return;
    const idle = this.#workers.find(w => !w.busy);
    if (!idle) return; // all workers busy — task waits in queue
    const item = this.#queue.shift();
    idle.busy = true;
    idle.worker.postMessage(item);
  }

  async destroy() {
    await Promise.all(this.#workers.map(w => w.worker.terminate()));
  }
}
```

**Q20. How do `worker_threads`, `child_process.fork`, and `cluster` compare for CPU parallelism?**

A:

| Dimension | `worker_threads` | `child_process.fork` | `cluster` |
|---|---|---|---|
| Unit | OS thread (same process) | OS process (separate PID) | OS process (same codebase) |
| Startup time | 10-60ms | 60-200ms | 60-200ms |
| Memory per unit | ~4-10MB (V8 isolate) | ~20-50MB (full Node process) | ~20-50MB |
| Shared memory | Yes (`SharedArrayBuffer`) | No (IPC only) | No (IPC only) |
| IPC mechanism | Structured clone, transfer | Serialized JSON | Serialized JSON |
| Module cache | Separate (own require cache) | Separate | Separate |
| Crash isolation | Weak (uncaught throws → process) | Strong (child crashes don't affect parent) | Strong |
| Use case | CPU-bound JS computation | Shell commands, external processes | HTTP server scaling |

**Rule**: use `worker_threads` for CPU-bound JavaScript; `child_process.exec/spawn` for external programs; `cluster` for scaling HTTP servers across CPU cores.

**Q21. What types of work are NOT well-suited for `worker_threads`?**

A: Five anti-patterns: (1) **I/O-bound work** — reading files, making HTTP requests, querying databases: these already use the libuv thread pool asynchronously without blocking the event loop; wrapping async I/O in a Worker adds overhead without benefit. (2) **Short tasks** — tasks completing in <10ms: worker creation overhead (10-60ms) exceeds the task duration; keep short tasks on the main thread or batch them. (3) **Tasks requiring shared JavaScript objects** — workers cannot share JavaScript objects; if your task needs to mutate a shared object graph, you'd need to serialize/deserialize it (slow) or restructure using `SharedArrayBuffer` (complex). (4) **Tasks with many small messages** — high-frequency small `postMessage` calls can bottleneck: the structured clone overhead per message may exceed the computation. Use `SharedArrayBuffer` ring buffers for high-frequency communication. (5) **Sequential tasks with data dependencies** — if task B must wait for task A's output, parallelism doesn't help; workers shine for independent parallel workloads.

**Q22. What resource limits can you set on worker threads, and what happens when they are exceeded?**

A: The `resourceLimits` option caps a worker's memory usage: `maxOldGenerationSizeMb` (maximum old generation heap size — where long-lived objects live), `maxYoungGenerationSizeMb` (maximum young generation — where new objects are allocated), `codeRangeSizeMb` (maximum size for JIT-compiled code), `stackSizeMb` (maximum call stack size — reduces per-thread stack usage for high worker counts). When a limit is exceeded, the worker throws an `OOMError` (out-of-memory error), which propagates to the main thread as an `'error'` event. Setting these limits is important for: (1) preventing runaway workers from consuming all available memory; (2) running many concurrent workers (reducing default stack size from ~8MB to ~1MB allows 8× more workers); (3) protecting the main process from a misbehaving worker.

```js
const worker = new Worker('./heavy-task.js', {
  resourceLimits: {
    maxOldGenerationSizeMb: 128,  // max old heap: 128MB (default: ~no limit)
    maxYoungGenerationSizeMb: 32, // max young heap: 32MB
    codeRangeSizeMb: 16,          // JIT code: 16MB
    stackSizeMb: 2,               // stack: 2MB (default: 4-8MB depending on OS)
    // Lower stackSizeMb if running many workers (each thread needs OS stack allocation)
  }
});

worker.on('error', (err) => {
  if (err.code === 'ERR_WORKER_OUT_OF_MEMORY') {
    console.error('Worker exceeded memory limit — shutting down');
  }
});
```

**Q23. What is `Atomics.waitAsync`, and how does it enable non-blocking SharedArrayBuffer signaling on the main thread?**

A: `Atomics.wait` blocks the calling thread — it cannot be used on the main thread because it would freeze the event loop. `Atomics.waitAsync(typedArray, index, value, timeout?)` (available since Node.js 16) returns an object with `{ async: boolean, value: Promise | 'not-equal' }` — if the current value already differs from `value`, it returns `{ async: false, value: 'not-equal' }` synchronously; otherwise it returns `{ async: true, value: Promise }` that resolves when notified or when the timeout expires. This enables the main thread to coordinate with workers via shared memory without blocking. The resolved Promise value is either `'ok'` (notified), `'timed-out'`, or `'not-equal'`.

```js
// Main thread waiting for worker completion signal:
const done = new Int32Array(new SharedArrayBuffer(4));
Atomics.store(done, 0, 0); // 0 = not done

const worker = new Worker('./worker.js', { workerData: { done: done.buffer } });

// Main thread: non-blocking wait using waitAsync:
const { value: waitPromise } = Atomics.waitAsync(done, 0, 0); // wait until done[0] ≠ 0
const result = await waitPromise;
console.log('Worker signaled:', result); // 'ok'

// ─── worker.js ───────────────────────────────────────────────
const doneArray = new Int32Array(workerData.done);
doHeavyWork();
Atomics.store(doneArray, 0, 1);   // write completion signal
Atomics.notify(doneArray, 0, 1);  // wake waitAsync promise in main thread
```

**Q24. What is the `SHARE_ENV` constant, and what other environment control options exist?**

A: `SHARE_ENV` (imported from `worker_threads`) is a symbol used as the `env` option to give a worker access to the *same* `process.env` object as the parent — mutations to `process.env` in one thread are visible in the other. The default behavior (without `env` option) is to inherit a *copy* of the parent's environment at creation time — changes after creation are not reflected. Using `SHARE_ENV` enables a shared environment where all workers see the same configuration, but introduces a potential race condition if multiple workers modify `process.env` concurrently (environment mutations are not atomic). Three `env` options: `SHARE_ENV` (shared, mutable), an object like `{ ...process.env, DEBUG: '1' }` (new copy with modifications — worker gets its own isolated copy), or no `env` option (inherits copy of parent's env at creation time).

```js
const { Worker, SHARE_ENV } = require('worker_threads');

// Option 1: SHARE_ENV — all workers share the same process.env object
const w1 = new Worker('./task.js', { env: SHARE_ENV });

// Option 2: Custom env — worker gets a specific environment (isolated copy)
const w2 = new Worker('./task.js', {
  env: { ...process.env, WORKER_ID: '2', LOG_LEVEL: 'debug' }
});
// Changing process.env in main thread does NOT affect w2

// Option 3: Default (copy at creation) — no env option
const w3 = new Worker('./task.js'); // copy of process.env at this moment
```

**Q25. State the invariant for worker creation, message passing, shared memory, and lifecycle each in one sentence.**

A:
- **Worker creation**: each `new Worker()` creates a fully isolated V8 isolate with its own heap, module cache, and event loop on a separate OS thread — no JavaScript state is shared by default, and the creation costs approximately 10-60ms plus ~4-10MB of baseline memory.
- **`workerData`**: the `workerData` option delivers a one-time structured clone to the worker synchronously at startup — it is always a deep copy, never a reference, and cannot be used for worker-to-parent communication.
- **`postMessage` / structured clone**: every message sent via `postMessage` is independently serialized using the structured clone algorithm — functions, prototype chains, and Symbols are not cloneable and will throw `DataCloneError`.
- **Transfer semantics**: transferring an `ArrayBuffer` in the `transferList` moves ownership to the receiver in zero time and zero copies — the sender's reference is immediately detached (`byteLength === 0`) and the receiver gets the full buffer.
- **`SharedArrayBuffer`**: a `SharedArrayBuffer` is the same physical memory in all threads simultaneously — any thread's write is immediately visible in all others, making it the only way to achieve true zero-latency inter-thread communication, but requiring `Atomics` operations to prevent data races.
- **Worker lifecycle**: a worker's event loop continues running as long as it has active handles, pending timers, or open message port listeners — it exits naturally when all work drains, or immediately when `worker.terminate()` is called from the parent.

## Problem 1 — CPU-Bound Task Offloaded to Worker

### Problem

Implement a function `computePrimes(limit)` that finds all prime numbers up to `limit`. Without workers it blocks the event loop for large inputs. Wrap it in a worker-based API that keeps the main thread responsive.

```js
// Main thread stays responsive while primes are computed:
const primes = await findPrimesAsync(10_000_000);
console.log(`Found ${primes.length} primes`); // non-blocking call
```

### Pattern Recognition
Single-file worker pattern using `isMainThread` + `__filename`. `workerData` delivers the limit; `parentPort.postMessage` returns the result. The main thread returns a Promise that resolves when the worker exits.

### Key Insight
The CPU-intensive sieve algorithm on the main thread would block all incoming HTTP requests, timers, and other callbacks for several seconds. Moving it to a worker thread allows the event loop to continue processing I/O, health checks, and other requests while the sieve runs in parallel on a separate OS thread.

### Solution

```js
// primes-worker.js (or inline with isMainThread check)
const {
  Worker, isMainThread, parentPort, workerData
} = require('worker_threads');

// ─── Shared computation function ─────────────────────────────
function sieveOfEratosthenes(limit) {
  const isPrime = new Uint8Array(limit + 1).fill(1);
  isPrime[0] = isPrime[1] = 0;
  for (let i = 2; i * i <= limit; i++) {
    if (isPrime[i]) {
      for (let j = i * i; j <= limit; j += i) isPrime[j] = 0;
    }
  }
  const primes = [];
  for (let i = 2; i <= limit; i++) if (isPrime[i]) primes.push(i);
  return primes;
}

if (isMainThread) {
  // ─── Main thread: public API ──────────────────────────────
  function findPrimesAsync(limit) {
    return new Promise((resolve, reject) => {
      const worker = new Worker(__filename, { workerData: { limit } });

      worker.on('message', (primes) => resolve(primes));
      worker.on('error', reject);
      worker.on('exit', (code) => {
        if (code !== 0) reject(new Error(`Worker exited with code ${code}`));
      });
    });
  }

  // Demonstrate non-blocking behavior:
  console.time('total');

  const healthCheck = setInterval(() => console.log('  [event loop alive]'), 100);

  findPrimesAsync(5_000_000)
    .then(primes => {
      clearInterval(healthCheck);
      console.log(`Found ${primes.length} primes below 5M`);
      console.timeEnd('total');
    });

  // This runs immediately — main thread is NOT blocked:
  console.log('Worker spawned; main thread free to handle requests');

} else {
  // ─── Worker thread: computation ───────────────────────────
  const { limit } = workerData;
  const primes = sieveOfEratosthenes(limit); // ~200ms for limit=5M — runs on worker thread
  parentPort.postMessage(primes);            // transfer result; worker exits naturally
}
```

### Trace

```
t=0ms:    new Worker(__filename, { workerData: { limit: 5_000_000 } })
          Worker thread starts, begins sieve computation on separate OS thread

t=0ms:    main thread continues:
          'Worker spawned; main thread free to handle requests'

t=0ms:    setInterval(healthCheck, 100) scheduled

t=100ms:  [event loop alive]   ← main thread event loop running normally ✓
t=200ms:  [event loop alive]   ← still responsive ✓

t=220ms:  Worker sieve completes → parentPort.postMessage(primes)
```

### Edge Cases
- Sending large `primes` array via `postMessage` clones it — for very large results, consider sending via transfer: `parentPort.postMessage(buffer, [buffer.buffer])` with a `Uint32Array`.
- Worker exceptions propagate to `'error'` event — always attach error listener before worker starts.

### Follow-up Questions
- "For results >100MB, how would you avoid copying?" — Return a `SharedArrayBuffer` that the sieve writes into; the main thread reads directly without cloning.
- "What if the limit is unknown — the user provides it at request time?" — Use a thread pool (Problem 2) to avoid creating a new worker per request.

## Problem 2 — Worker Thread Pool

### Problem

Implement `WorkerPool` — a reusable pool of worker threads that distributes tasks across `N` workers. Tasks are queued if all workers are busy. The pool must handle worker crashes gracefully by restarting the crashed worker.

```js
const pool = new WorkerPool('./task-worker.js', 4);
const results = await Promise.all([
  pool.exec({ type: 'HASH',  data: 'hello' }),
  pool.exec({ type: 'SORT',  data: [3,1,2] }),
  pool.exec({ type: 'REGEX', data: 'test string' }),
]);
await pool.destroy();
```

### Pattern Recognition
Fixed-size worker array with busy-tracking. Task queue for overflow. Promise resolution via stored callbacks keyed by task ID. Worker crash detection restarts the worker to maintain pool size.

### Key Insight
The pool's correctness hinges on three invariants: (1) a worker is marked `busy = false` only after sending its result (in the `'message'` handler, before calling `#dispatch`); (2) `#dispatch` is called whenever a worker becomes free OR a new task is queued; (3) crashed workers are restarted to maintain pool capacity.

### Solution

```js
const { Worker } = require('worker_threads');
const { EventEmitter } = require('events');

class WorkerPool extends EventEmitter {
  #workerFile;
  #workers = [];   // Array<{ worker, busy, taskId }>
  #queue = [];     // Array<{ taskId, data, resolve, reject }>
  #taskId = 0;
  #callbacks = new Map(); // taskId → { resolve, reject }
  #destroyed = false;

  constructor(workerFile, size = 4) {
    super();
    this.#workerFile = workerFile;
    for (let i = 0; i < size; i++) this.#addWorker();
  }

  #addWorker() {
    const entry = { worker: null, busy: false, taskId: null };

    const startWorker = () => {
      entry.worker = new Worker(this.#workerFile);

      entry.worker.on('message', ({ taskId, result, error }) => {
        const cb = this.#callbacks.get(taskId);
        this.#callbacks.delete(taskId);
        entry.busy   = false;
        entry.taskId = null;

        // Resolve/reject BEFORE dispatching next task:
        if (error) cb.reject(new Error(error.message ?? error));
        else       cb.resolve(result);

        if (!this.#destroyed) this.#dispatch(entry);
      });

      entry.worker.on('error', (err) => {
        this.emit('workerError', err);
        // Fail the in-progress task:
        if (entry.taskId !== null) {
          const cb = this.#callbacks.get(entry.taskId);
          this.#callbacks.delete(entry.taskId);
          cb?.reject(err);
        }
        entry.busy   = false;
        entry.taskId = null;
        // Restart the worker to maintain pool size:
        if (!this.#destroyed) startWorker();
      });

      entry.worker.on('exit', (code) => {
        if (!this.#destroyed && code !== 0) {
          this.emit('workerCrash', code);
          startWorker(); // restart on abnormal exit
        }
      });
    };

    startWorker();
    this.#workers.push(entry);
  }

  #dispatch(entry) {
    if (this.#queue.length === 0 || entry.busy) return;
    const { taskId, data, resolve, reject } = this.#queue.shift();
    entry.busy   = true;
    entry.taskId = taskId;
    this.#callbacks.set(taskId, { resolve, reject });
    entry.worker.postMessage({ taskId, data });
  }

  exec(data) {
    if (this.#destroyed) return Promise.reject(new Error('Pool is destroyed'));

    return new Promise((resolve, reject) => {
      const taskId = ++this.#taskId;
      this.#queue.push({ taskId, data, resolve, reject });

      // Try to dispatch immediately to any idle worker:
      for (const entry of this.#workers) {
        if (!entry.busy) { this.#dispatch(entry); break; }
      }
    });
  }

  async destroy() {
    this.#destroyed = true;
    // Reject all queued tasks:
    for (const { reject } of this.#queue) {
      reject(new Error('Pool destroyed'));
    }
    this.#queue.length = 0;
    await Promise.all(this.#workers.map(e => e.worker.terminate()));
  }

  get stats() {
    return {
      total:   this.#workers.length,
      busy:    this.#workers.filter(e => e.busy).length,
      queued:  this.#queue.length,
    };
  }
}

// ─── task-worker.js — long-lived task executor ─────────────
const { parentPort } = require('worker_threads');

parentPort.on('message', ({ taskId, data }) => {
  try {
    let result;
    if (data.type === 'HASH')  result = computeHash(data.data);
    if (data.type === 'SORT')  result = [...data.data].sort((a, b) => a - b);
    if (data.type === 'REGEX') result = data.data.match(/\w+/g)?.length ?? 0;
    parentPort.postMessage({ taskId, result });
  } catch (err) {
    parentPort.postMessage({ taskId, error: { message: err.message } });
  }
});
```

### Trace

```
Pool(size=4). Workers W1-W4 created and idle.

exec('HASH'): queue=[{id:1,HASH}]. W1 idle → dispatch to W1. W1.busy=true.
exec('SORT'): queue=[{id:2,SORT}]. W2 idle → dispatch to W2. W2.busy=true.
exec('REGEX'): dispatch to W3. W3.busy=true.
exec('REGEX2'): dispatch to W4. W4.busy=true. All workers busy.
exec('EXTRA'): queue=[{id:5,EXTRA}]. No idle workers → queued.

W1 completes HASH:
  message {taskId:1, result:'abc'} → cb.resolve('abc')
  W1.busy=false → dispatch({id:5,EXTRA}) to W1. W1.busy=true again.

W2 completes SORT: resolve([1,2,3]). W2.busy=false. queue empty → idle.
W3, W4 complete similarly.
W1 completes EXTRA: resolve. queue empty. All workers idle.

Pool.destroy(): terminate all 4 workers. Any queued tasks rejected.
```

### Edge Cases
- `#dispatch` is called both when a task is added (eager dispatch) and when a worker finishes (chained dispatch) — no task is ever "stranded" in the queue.
- Worker restart: if `startWorker()` is called during `destroy()`, the `!this.#destroyed` check prevents restart.

### Follow-up Questions
- "How would you add worker affinity (send related tasks to the same worker for cache locality)?" — Hash a task's `affinity` key to a worker index; dispatch to that specific worker regardless of queue.
- "What if you need to time out individual tasks?" — Wrap `exec` return value: `Promise.race([pool.exec(data), new Promise((_, r) => setTimeout(() => r(new Error('timeout')), 5000))])`. Terminate the specific worker if needed.

## Problem 3 — Progress Reporting via `SharedArrayBuffer`

### Problem

Implement a long-running worker task that reports progress to the main thread in real time using `SharedArrayBuffer`. The main thread should display a live progress bar without polling via `postMessage`.

```js
// Main thread displays live progress updated directly from worker:
//   Processing: [████████░░░░░░░░░░░░] 40% (400/1000 items)
```

### Pattern Recognition
`SharedArrayBuffer` + typed array for the progress counter (writable by worker, readable by main). `Atomics.store` in worker for safe writes. Main thread polls the shared counter with `setInterval` for display.

### Key Insight
The worker increments `progress[0]` using `Atomics.add` to avoid data races (even though only one thread writes, `Atomics` ensures the value is flushed from CPU cache to main memory). The main thread reads with `Atomics.load` to ensure it reads the latest value, not a CPU-cached stale copy. Without `Atomics`, CPU cache coherency issues could cause the main thread to see stale values.

### Solution

```js
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

if (isMainThread) {
  // ─── Main thread ──────────────────────────────────────────
  const TOTAL = 1000;
  const progressBuffer = new SharedArrayBuffer(8); // 2 × Int32
  const progress = new Int32Array(progressBuffer);
  // progress[0] = current count, progress[1] = total

  Atomics.store(progress, 0, 0);     // init: 0 processed
  Atomics.store(progress, 1, TOTAL); // init: total items

  const worker = new Worker(__filename, {
    workerData: { progressBuffer, total: TOTAL }
  });

  // Live display: read shared memory directly (no postMessage polling)
  const displayInterval = setInterval(() => {
    const current = Atomics.load(progress, 0); // safe read
    const total   = Atomics.load(progress, 1);
    const pct     = Math.floor((current / total) * 100);
    const filled  = Math.floor(pct / 5);
    const bar     = '█'.repeat(filled) + '░'.repeat(20 - filled);
    process.stdout.write(
      `\r  Processing: [${bar}] ${pct}% (${current}/${total} items)`
    );
    if (current >= total) clearInterval(displayInterval);
  }, 100); // update display 10 times per second

  worker.on('message', ({ timeTaken }) => {
    process.stdout.write('\n');
    console.log(`\nDone! Processed ${TOTAL} items in ${timeTaken}ms`);
  });

} else {
  // ─── Worker thread ────────────────────────────────────────
  const { progressBuffer, total } = workerData;
  const progress = new Int32Array(progressBuffer);
  const start = Date.now();

  for (let i = 0; i < total; i++) {
    processItem(i); // simulate ~1ms of work per item
    Atomics.add(progress, 0, 1); // atomic increment — safe even with concurrent reads
  }

  parentPort.postMessage({ timeTaken: Date.now() - start });
}

function processItem(i) {
  // Simulate CPU work (~1ms):
  let x = 0;
  for (let j = 0; j < 100_000; j++) x += Math.sqrt(j);
  return x;
}
```

### Trace

```
t=0ms:    SharedArrayBuffer(8) created: progress = [0, 1000]
          Worker spawned, begins processing items

t=100ms:  setInterval fires:
          Atomics.load(progress, 0) → ~100 (worker processed ~100 items)
          Display: [█░░░░░░░░░░░░░░░░░░░] 10% (100/1000)

t=200ms:  Atomics.load → ~200
          Display: [████░░░░░░░░░░░░░░░░] 20% (200/1000)

t=400ms:  Display: [████████░░░░░░░░░░░░] 40% (400/1000)

t=1000ms: Worker finishes. Atomics.load → 1000.
          Display: [████████████████████] 100% (1000/1000)
          worker.on('message') fires: 'Done! Processed 1000 items in 1023ms'

Key: main thread's setInterval reads progress WITHOUT postMessage — zero serialization cost.
Atomics.load ensures fresh read (not CPU-cached stale value).
```

### Edge Cases
- `Atomics.add` vs `++`: plain `progress[0]++` is NOT atomic (read-modify-write, three separate operations). Always use `Atomics.add(progress, 0, 1)` for safe increment even with a single writer (cache coherency).
- Buffer size: `Int32Array` holds 32-bit signed integers (max ~2 billion). For larger counts, use `BigInt64Array` with `Atomics.add` operations on `BigInt` values.

### Follow-up Questions
- "How would you let the user cancel the operation?" — Add a second index `progress[2]` as a cancel flag: `Atomics.store(progress, 2, 1)` from main thread. Worker checks `Atomics.load(progress, 2) === 1` every N iterations and breaks if set.
- "Why not just `postMessage` progress every 1%?" — For 1000 items, that's 100 postMessage calls, each with serialization overhead. SharedArrayBuffer progress is zero-overhead reads.

## Problem 4 — Fan-Out/Fan-In Parallel Processing

### Problem

Process an array of `N` items in parallel by splitting the work across `K` workers (fan-out), collecting all results back in the main thread and combining them (fan-in).

```js
const items = generateLargeArray(100_000);
const results = await parallelProcess(items, 4); // 4 workers
// 4x speedup over single-threaded processing
```

### Pattern Recognition
Split input into K chunks, dispatch one chunk per worker, use `Promise.all` to await all workers, concatenate results. Workers each process their chunk independently and terminate when done.

### Key Insight
The fan-out/fan-in pattern achieves near-linear speedup for embarrassingly parallel workloads (no data dependencies between items). Using `transferList` to move the input ArrayBuffer to each worker avoids cloning overhead for large datasets. Workers send results back by constructing a typed array and transferring it back.

### Solution

```js
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

if (isMainThread) {
  // ─── Main thread: fan-out/fan-in orchestrator ─────────────
  async function parallelProcess(items, numWorkers = 4) {
    const chunkSize = Math.ceil(items.length / numWorkers);
    const workerPromises = [];

    for (let i = 0; i < numWorkers; i++) {
      const start = i * chunkSize;
      const end   = Math.min(start + chunkSize, items.length);
      const chunk = items.slice(start, end); // extract chunk

      // Wrap chunk in ArrayBuffer for efficient transfer:
      const buffer = new Float64Array(chunk).buffer;

      const promise = new Promise((resolve, reject) => {
        const worker = new Worker(__filename, {
          workerData: { buffer, start } // pass start index for result ordering
        });

        worker.postMessage({ buffer }, [buffer]); // TRANSFER: zero-copy
        // Note: workerData is used for config; actual data sent via postMessage+transfer

        worker.on('message', ({ resultBuffer, start }) => {
          resolve({ resultBuffer, start });
        });
        worker.on('error', reject);
      });

      workerPromises.push(promise);
    }

    // Fan-in: wait for all workers and reassemble in order:
    const workerResults = await Promise.all(workerPromises);
    workerResults.sort((a, b) => a.start - b.start); // restore original order

    // Concatenate result arrays:
    const totalLength = workerResults.reduce(
      (sum, { resultBuffer }) => sum + new Float64Array(resultBuffer).length, 0
    );
    const combined = new Float64Array(totalLength);
    let offset = 0;
    for (const { resultBuffer } of workerResults) {
      const resultArray = new Float64Array(resultBuffer);
      combined.set(resultArray, offset);
      offset += resultArray.length;
    }

    return Array.from(combined);
  }

  const items = Array.from({ length: 100_000 }, () => Math.random() * 1000);
  console.time('parallel');
  parallelProcess(items, 4).then(results => {
    console.timeEnd('parallel');
    console.log('Result count:', results.length);
  });

} else {
  // ─── Worker thread: process a chunk ────────────────────────
  const { start } = workerData;

  // Receive the chunk via postMessage (with transfer):
  parentPort.once('message', ({ buffer }) => {
    const input  = new Float64Array(buffer);
    const output = new Float64Array(input.length);

    // Apply some transformation (e.g., square root + normalize):
    for (let i = 0; i < input.length; i++) {
      output[i] = Math.sqrt(input[i]) * 2; // CPU-bound transform
    }

    // Transfer result back to main thread (zero-copy):
    parentPort.postMessage({ resultBuffer: output.buffer, start }, [output.buffer]);
    // Worker exits naturally after postMessage returns
  });
}
```

### Trace

```
items = [100,000 elements]

Fan-out (t=0ms):
  Chunk 0: items[0..24999]   → Worker 0 (transferred as Float64Array buffer, 200KB)
  Chunk 1: items[25000..49999] → Worker 1
  Chunk 2: items[50000..74999] → Worker 2
  Chunk 3: items[75000..99999] → Worker 3

All 4 workers compute in parallel on 4 OS threads:
  Worker 0: sqrt+normalize for 25,000 items ← ~50ms
  Worker 1: same ← ~50ms  (concurrent with W0, W2, W3)
  Worker 2: same ← ~50ms
  Worker 3: same ← ~50ms

Fan-in (t≈50ms): all workers done, results collected via Promise.all
  Sort by start index → order: chunk0, chunk1, chunk2, chunk3
  Concatenate: combined Float64Array of 100,000 elements

Without parallelism: ~200ms (single thread)
With 4 workers: ~50ms + overhead ≈ 60ms total (≈3.3x speedup)
```

### Edge Cases
- Uneven chunks: if `items.length = 100001`, the last chunk gets 1 extra item — `Math.ceil(items.length / numWorkers)` handles this correctly.
- Worker reuse: these workers terminate after one chunk. For repeated calls, use the thread pool (Problem 2) to avoid repeated startup overhead.

### Follow-up Questions
- "How would you handle partial failures (one worker crashes)?" — `Promise.all` rejects on first failure. Use `Promise.allSettled` instead and retry failed chunks on other workers.
- "What if items must be processed in strict order (A must finish before B)?" — Fan-out only works for embarrassingly parallel tasks. For ordered pipelines, use a worker-per-stage pipeline connected via `MessageChannel`.

## Problem 5 — Worker with Timeout and Graceful Termination

### Problem

Implement `runWithTimeout(workerFile, data, timeoutMs)` — runs a task in a worker with a maximum execution time. If the worker doesn't complete within `timeoutMs`, terminate it and reject with a timeout error. Clean up all resources properly.

```js
try {
  const result = await runWithTimeout('./task.js', { n: 1e9 }, 3000);
} catch (err) {
  if (err.code === 'WORKER_TIMEOUT') {
    console.log('Task exceeded time limit');
  }
}
```

### Pattern Recognition
`Promise.race` between the worker's result promise and a timeout promise. `worker.terminate()` on timeout to prevent resource leaks. Error code convention for distinguishing timeout from computation errors.

### Key Insight
`Promise.race` resolves/rejects as soon as the first Promise settles — the "loser" Promise is abandoned (JavaScript has no Promise cancellation). The `finally` clause ensures `clearTimeout` and `worker.terminate()` always run, preventing zombie workers that consume memory and CPU even after the timeout.

### Solution

```js
const { Worker } = require('worker_threads');

function runWithTimeout(workerFile, data, timeoutMs) {
  return new Promise((resolve, reject) => {
    const worker = new Worker(workerFile, { workerData: data });
    let settled = false;

    const settle = (fn, value) => {
      if (settled) return; // prevent double-settle
      settled = true;
      clearTimeout(timer);
      fn(value);
    };

    // Worker result path:
    worker.on('message', (result) => {
      worker.terminate().then(() => settle(resolve, result));
    });
    worker.on('error',   (err)  => {
      settle(reject, err);
    });
    worker.on('exit', (code) => {
      if (!settled && code !== 0) {
        settle(reject, new Error(`Worker exited with code ${code}`));
      }
    });

    // Timeout path:
    const timer = setTimeout(() => {
      const timeoutErr = Object.assign(
        new Error(`Worker timed out after ${timeoutMs}ms`),
        { code: 'WORKER_TIMEOUT' }
      );
      worker.terminate()   // forcefully terminate
        .then(() => settle(reject, timeoutErr))
        .catch(() => settle(reject, timeoutErr)); // terminate error itself
    }, timeoutMs);
  });
}

// Advanced: with cancellation signal
function runWithAbort(workerFile, data, signal) {
  return new Promise((resolve, reject) => {
    if (signal.aborted) return reject(signal.reason);

    const worker = new Worker(workerFile, { workerData: data });
    let settled = false;

    const settle = (fn, val) => {
      if (settled) return;
      settled = true;
      signal.removeEventListener('abort', onAbort);
      fn(val);
    };

    const onAbort = () => {
      worker.terminate();
      settle(reject, signal.reason ?? new Error('Worker aborted'));
    };

    signal.addEventListener('abort', onAbort);
    worker.on('message', (result) => settle(resolve, result));
    worker.on('error', (err) => settle(reject, err));
  });
}

// Usage:
const controller = new AbortController();
setTimeout(() => controller.abort(), 3000); // cancel after 3s

try {
  const result = await runWithAbort('./heavy.js', { data }, controller.signal);
} catch (err) {
  console.log('Aborted:', err.message);
}
```

### Trace

```
Case 1: Worker completes in time (2500ms, timeout=3000ms):
  t=0:    Worker starts
  t=2500: worker.on('message') fires → clearTimeout(timer) → resolve(result)
  t=3000: timer would have fired but was cleared ✓

Case 2: Worker exceeds timeout (task takes 5000ms, timeout=3000ms):
  t=0:    Worker starts (computing...)
  t=3000: timer fires:
    → worker.terminate() called
    → Worker's event loop forcefully stopped (exit code: null)
    → settle(reject, { code: 'WORKER_TIMEOUT', message: '...' })
  t=3000+: Promise rejected with WORKER_TIMEOUT ✓
  t=5000+: Worker would have finished, but it's already terminated — no zombie ✓

Case 3: Worker throws uncaught exception:
  t=0:    Worker starts
  t=500:  Uncaught error in worker
    → worker.on('error') fires → clearTimeout → reject(err) ✓
```

### Edge Cases
- `settled` flag prevents double-settling: if `'message'` and `'exit'` fire nearly simultaneously, only the first one resolves/rejects.
- `worker.terminate()` before `settle`: ensures the worker thread is released before resolving, preventing the caller from seeing "success" while the thread is still running.
- `terminate()` returns a Promise — always `await` it or `.then()` to ensure the OS thread is actually released before continuing.

### Follow-up Questions
- "What if terminate() itself hangs?" — Add a timeout on `terminate()` itself: `Promise.race([worker.terminate(), new Promise(r => setTimeout(r, 1000))])`.
- "How do you limit total concurrent workers across the application?" — A semaphore: `await semaphore.acquire()` before `new Worker()`, `semaphore.release()` in `finally`.

## Problem 6 — Synchronized Ring Buffer with `Atomics`

### Problem

Implement a **ring buffer** using `SharedArrayBuffer` and `Atomics` for lock-free, thread-safe producer-consumer communication between a worker (producer) and main thread (consumer). The worker writes items without blocking; the main thread reads them.

```js
// Ring buffer: worker produces 10,000 items; main thread consumes them
// No postMessage per item — pure shared memory communication
```

### Pattern Recognition
Ring buffer uses two indices (head and tail) in shared memory. Producer writes to `tail`, advances tail. Consumer reads from `head`, advances head. `Atomics.load/store` for safe index reads/writes. `Atomics.wait`/`Atomics.notify` for blocking when buffer is full or empty.

### Key Insight
A ring buffer achieves FIFO ordering with O(1) read/write. The invariant: `tail` is always where the next write goes; `head` is always where the next read comes from. Buffer is full when `(tail + 1) % capacity == head`. Buffer is empty when `head == tail`. Using `SharedArrayBuffer` with power-of-2 capacity allows fast modulo with bitwise AND.

### Solution

```js
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

const CAPACITY   = 1024;  // must be power of 2
const INDEX_SIZE = 8;     // bytes for two Int32 indices (head, tail)
const ITEM_SIZE  = 4;     // bytes per item (Int32)

const HEAD_IDX = 0;
const TAIL_IDX = 1;
const MASK     = CAPACITY - 1; // CAPACITY - 1 for fast modulo (bitwise AND)

class RingBuffer {
  #indices;  // Int32Array: [head, tail]
  #data;     // Int32Array: circular data buffer

  constructor(sharedBuffer) {
    this.#indices = new Int32Array(sharedBuffer, 0, 2);
    this.#data    = new Int32Array(sharedBuffer, INDEX_SIZE, CAPACITY);
  }

  // Producer: write one item (blocks if full)
  write(value) {
    while (true) {
      const tail = Atomics.load(this.#indices, TAIL_IDX);
      const head = Atomics.load(this.#indices, HEAD_IDX);
      const next = (tail + 1) & MASK;

      if (next === head) {
        // Buffer full: wait for consumer to advance head
        Atomics.wait(this.#indices, TAIL_IDX, tail); // wait until tail changes
        continue;
      }

      this.#data[tail] = value;
      Atomics.store(this.#indices, TAIL_IDX, next);
      Atomics.notify(this.#indices, HEAD_IDX, 1); // wake reader if waiting
      return;
    }
  }

  // Consumer: read one item (returns null if empty, blocks if blocking=true)
  read(blocking = false) {
    while (true) {
      const head = Atomics.load(this.#indices, HEAD_IDX);
      const tail = Atomics.load(this.#indices, TAIL_IDX);

      if (head === tail) {
        if (!blocking) return null; // non-blocking: nothing available
        // Blocking: wait for producer to add item
        Atomics.wait(this.#indices, HEAD_IDX, head);
        continue;
      }

      const value = this.#data[head];
      const next  = (head + 1) & MASK;
      Atomics.store(this.#indices, HEAD_IDX, next);
      Atomics.notify(this.#indices, TAIL_IDX, 1); // wake writer if waiting
      return value;
    }
  }

  get size() {
    const head = Atomics.load(this.#indices, HEAD_IDX);
    const tail = Atomics.load(this.#indices, TAIL_IDX);
    return (tail - head + CAPACITY) & MASK;
  }
}

if (isMainThread) {
  // ─── Main thread: consumer (uses event-driven reading) ────
  const bufferSize = INDEX_SIZE + CAPACITY * ITEM_SIZE;
  const sharedBuffer = new SharedArrayBuffer(bufferSize);
  const ring = new RingBuffer(sharedBuffer);

  const worker = new Worker(__filename, { workerData: { sharedBuffer } });

  // Main thread can't use Atomics.wait (would block event loop)
  // Instead: poll with setImmediate (fast polling):
  let consumed = 0;
  const EXPECTED = 10_000;

  function drainBuffer() {
    let item;
    while ((item = ring.read(false)) !== null) { // non-blocking reads
      consumed++;
      // process item...
    }
    if (consumed < EXPECTED) setImmediate(drainBuffer); // continue draining
    else console.log(`Consumer: received all ${consumed} items`);
  }

  worker.on('message', () => drainBuffer()); // start draining when worker signals
  console.log('Consumer ready, waiting for producer...');

} else {
  // ─── Worker thread: producer (can use blocking writes) ────
  const { sharedBuffer } = workerData;
  const ring = new RingBuffer(sharedBuffer);

  for (let i = 0; i < 10_000; i++) {
    ring.write(i); // blocks if buffer full (waits for consumer)
  }

  parentPort.postMessage('done'); // signal consumer to drain remainder
  console.log('Producer: all 10,000 items written');
}
```

### Trace

```
Shared buffer: [head=0, tail=0, data=empty]

Producer writes 0-1023 (fills buffer):
  write(0): tail=0, head=0, next=1. data[0]=0. tail→1. notify head.
  write(1): tail=1, head=0, next=2. data[1]=1. tail→2.
  ...
  write(1022): tail=1022, next=1023. Write.
  write(1023): next=(1024&1023)=0. next===head(0)! FULL. wait.

Consumer drains 0-100:
  read(): head=0,tail=1023(was blocked at 1023). val=data[0]=0. head→1. notify tail.
  read(): head=1. val=1. head→2.
  ...
  notify unblocks producer at tail=1023:
    write(1023): next=0. 0 !== head(100) ✓. data[1023]=1023. tail→0(wraps!). notify head.

Ring wraps correctly. Producer and consumer run concurrently.
Final: consumer reads all 10,000 items via ring buffer. Zero postMessage calls.
```

### Edge Cases
- `CAPACITY` must be power of 2 for the bitwise-AND modulo trick (`& MASK`).
- `Atomics.wait` returns `'not-equal'` if value already changed — always loop.
- Main thread uses `setImmediate` polling (can't use `Atomics.wait`); for true blocking consumer, use a second worker.

### Follow-up Questions
- "How does throughput compare to postMessage?" — Ring buffer: ~100ns per item (atomic operations only). `postMessage`: ~1-10μs per item (serialization + event loop overhead). For >1M items/second, ring buffer is the only viable approach.
- "How would you handle multiple producers?" — Use `Atomics.compareExchange` for lock-free multi-producer: each producer atomically claims a slot by CAS-ing the tail index.

## Problem 7 — Parallel Image Processing Pipeline

### Problem

Implement a parallel image processing pipeline that converts RGB images to grayscale using multiple workers. Each worker processes one image; the pipeline accepts images as `Uint8ClampedArray` buffers (simulating canvas pixel data) and processes up to `K` images concurrently.

```js
const pipeline = new ImagePipeline({ workers: 4 });
const grayscaleImages = await pipeline.processAll(rgbImages);
await pipeline.close();
```

### Pattern Recognition
Worker pool (Problem 2's pattern) adapted for typed array data. Transfer `ArrayBuffer` to each worker for zero-copy input; transfer the processed `ArrayBuffer` back as output. Key difference from Problem 2: explicitly using transfer semantics to handle large image data efficiently.

### Key Insight
A typical 1920×1080 RGBA image is 8.3MB (1920 × 1080 × 4 bytes). Cloning 8.3MB per `postMessage` call at 60fps would be 499MB/s of memory bandwidth from serialization alone. Transfer moves the buffer without copying — the worker receives the same memory in nanoseconds regardless of image size.

### Solution

```js
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

if (isMainThread) {
  // ─── Main thread: pipeline orchestrator ───────────────────
  class ImagePipeline {
    #pool;

    constructor({ workers = 4 } = {}) {
      this.#pool = Array.from({ length: workers }, () => ({
        worker: new Worker(__filename),
        busy: false,
      }));
      this.#pool.forEach(entry => {
        entry.worker.on('error', err => console.error('Worker error:', err));
      });
    }

    processImage(pixelBuffer) {
      return new Promise((resolve, reject) => {
        const assign = () => {
          const entry = this.#pool.find(e => !e.busy);
          if (!entry) return setTimeout(assign, 0); // wait for idle worker

          entry.busy = true;
          const transferBuffer = pixelBuffer.slice(0); // copy input (preserve original)
          // In production with mutable input, transfer directly and reconstruct

          entry.worker.postMessage(
            { imageBuffer: transferBuffer },
            [transferBuffer] // TRANSFER: zero-copy to worker
          );

          entry.worker.once('message', ({ grayscaleBuffer }) => {
            entry.busy = false;
            resolve(new Uint8ClampedArray(grayscaleBuffer));
          });
        };
        assign();
      });
    }

    processAll(images) {
      return Promise.all(images.map(img => this.processImage(img.buffer)));
    }

    async close() {
      await Promise.all(this.#pool.map(e => e.worker.terminate()));
    }
  }

  // Test:
  function makeTestImage(width, height) {
    const data = new Uint8ClampedArray(width * height * 4);
    for (let i = 0; i < data.length; i += 4) {
      data[i]   = Math.random() * 255; // R
      data[i+1] = Math.random() * 255; // G
      data[i+2] = Math.random() * 255; // B
      data[i+3] = 255;                 // A
    }
    return data;
  }

  const images = Array.from({ length: 20 }, () => makeTestImage(1920, 1080));
  const pipeline = new ImagePipeline({ workers: 4 });

  console.time('processAll');
  const results = await pipeline.processAll(images);
  console.timeEnd('processAll');
  console.log(`Processed ${results.length} images`);
  await pipeline.close();

} else {
  // ─── Worker thread: grayscale conversion ──────────────────
  parentPort.on('message', ({ imageBuffer }) => {
    const pixels    = new Uint8ClampedArray(imageBuffer);
    const grayscale = new Uint8ClampedArray(pixels.length);

    // ITU-R BT.601 luminance formula:
    for (let i = 0; i < pixels.length; i += 4) {
      const gray = 0.299 * pixels[i] + 0.587 * pixels[i+1] + 0.114 * pixels[i+2];
      grayscale[i] = grayscale[i+1] = grayscale[i+2] = gray;
      grayscale[i+3] = pixels[i+3]; // preserve alpha
    }

    // Transfer processed buffer back (zero-copy):
    parentPort.postMessage(
      { grayscaleBuffer: grayscale.buffer },
      [grayscale.buffer]
    );
    // Worker stays alive for next message (pool pattern)
  });
}
```

### Trace

```
20 images, 1920×1080 RGBA each = 8.3MB per image

Without workers (single thread):
  20 images × ~100ms/image = 2000ms sequential

With 4 workers:
  Images  1, 2, 3, 4: dispatched simultaneously to W1, W2, W3, W4
    (each transferred as 8.3MB buffer — zero copy, nanoseconds)
  t≈100ms: W1,W2,W3,W4 complete batch 1 → results transferred back
  Images  5, 6, 7, 8: immediately dispatched to now-idle workers
  ...
  t≈500ms: all 20 images processed (20/4 = 5 rounds × ~100ms)

Transfer overhead: ~0ms (zero-copy) vs clone overhead: ~8ms per 8.3MB image
With 4 workers: effective throughput: 4 images × 10fps = 40fps processing rate ✓
```

### Edge Cases
- `pixelBuffer.slice(0)` in the pipeline creates a copy before transfer — if the input image must remain accessible after `processImage()` returns. If the caller won't reuse the buffer, transfer directly without copying.
- Worker pool reuse: workers stay alive between images. Unlike Problem 1 (one worker per task), these workers process many images over their lifetime — creation cost is amortized.

### Follow-up Questions
- "How would you add a second processing stage (e.g., blur after grayscale)?" — Use `MessageChannel` (Problem's Q9): connect the grayscale worker's output port to the blur worker's input port, creating a pipeline where data flows directly between workers without returning to main thread.
- "What if an image is corrupted and the worker crashes?" — The worker's `'error'` event fires; the promise for that image rejects; restart the worker for future tasks (same pattern as the pool in Problem 2).

## Quick Reference — `worker_threads` Decision Tree

```
Should you use worker_threads?
│
├── IS THE WORK I/O-BOUND? (file reads, HTTP calls, database queries)
│   └── NO — use async I/O (fs.promises, axios, etc.)
│       These already use libuv thread pool without blocking the event loop.
│       Adding a worker_thread adds overhead with no benefit.
│
├── IS THE WORK CPU-BOUND JS? (sorting, crypto, compression, ML inference)
│   └── YES → use worker_threads ✓
│       How long does the task take?
│       < 1ms:   Keep on main thread (worker overhead > task time)
│       1-50ms:  Use thread pool (amortize creation cost)
│       > 50ms:  Create a worker per task or use thread pool
│
├── HOW TO PASS DATA?
│   ├── INITIAL CONFIGURATION (once, at worker start)
│   │   → workerData option: sync available in worker, cloned once
│   │
│   ├── STRUCTURED DATA (objects, arrays, Maps, small buffers)
│   │   → postMessage: cloned via structured clone
│   │       - Objects lose prototype chain (just data)
│   │       - Functions cannot be sent (DataCloneError)
│   │
│   ├── LARGE BINARY DATA (>1MB ArrayBuffer, typed arrays)
│   │   → postMessage + transferList: zero-copy transfer
│   │       worker.postMessage({ buf }, [buf])
│   │       ⚠️ Sender's reference detached after transfer
│   │
│   └── HIGH-FREQUENCY / REAL-TIME shared state
│       → SharedArrayBuffer + Atomics
│           All threads see same memory; no serialization
│           ⚠️ Requires Atomics for safe concurrent access
│           ⚠️ Requires COOP + COEP headers in browsers
│
├── HOW TO STRUCTURE WORKERS?
│   ├── ONE-SHOT (task → result → terminate)
│   │   → new Worker() per task
│   │       Simple but expensive for short/frequent tasks
│   │
│   ├── LONG-LIVED POOL (many tasks, few workers)
│   │   → Fixed-size WorkerPool (workers created once, reused)
│   │       Best for: request handlers, batch processors
│   │
│   ├── PIPELINE (A processes → sends to B → sends to C)
│   │   → MessageChannel between workers (no main thread relay)
│   │
│   └── FAN-OUT/FAN-IN (split large input, process in parallel)
│       → N workers × 1 chunk each → Promise.all → merge
│
├── HOW TO TERMINATE WORKERS?
│   ├── Natural exit: parentPort.close() or all handles close
```

## Common Bugs Checklist

Before shipping worker_threads code, verify:

1. **Creating a new worker per request without pooling?** — Each `new Worker()` takes 10-60ms and allocates ~4-10MB. For a server handling 100 requests/second, this means 10 new workers per second — each consuming memory and startup time. The correct pattern is a fixed-size thread pool created at startup. Profile: if worker creation time exceeds 10% of task time, you need a pool.

2. **Sending large data via `postMessage` without transfer?** — `postMessage({ bigBuffer })` where `bigBuffer` is an `ArrayBuffer` or TypedArray copies all the bytes — 100MB of data means 100MB of allocation and memcpy. Always use `transferList` for buffers >1MB: `worker.postMessage({ buf }, [buf])`. Remember: after transfer, `buf.byteLength === 0` in the sender — plan your data flow accordingly.

3. **Attempting to call `Atomics.wait` on the main thread?** — `Atomics.wait` blocks the calling thread. On the main thread, this freezes the event loop — Node.js throws `TypeError: Atomics.wait cannot be called in the main thread`. Use `Atomics.waitAsync` (Node.js 16+) for non-blocking waits that return a Promise, or poll via `setImmediate`.

4. **Sharing JavaScript objects (not SharedArrayBuffer) across workers?** — Workers cannot share JavaScript objects by reference. `worker.postMessage(sharedObject)` clones `sharedObject` — mutations in the worker are invisible to the main thread and vice versa. Only `SharedArrayBuffer` provides true shared memory. If you need to share structured data, use message passing with explicit synchronization.

5. **Data races on `SharedArrayBuffer` without Atomics?** — `sharedArray[0]++` from two threads simultaneously is a data race — the result is undefined behavior. Always use `Atomics.add(sharedArray, 0, 1)` for increments, `Atomics.load/store` for reads and writes, and `Atomics.compareExchange` for conditional updates. The absence of data races is not guaranteed by luck — only Atomics operations provide CPU-level atomicity.

6. **Not handling worker `'error'` events?** — If no `'error'` listener is attached, unhandled worker errors are thrown in the main thread as uncaught exceptions, potentially crashing the process. Always attach `worker.on('error', handler)` before the worker starts. In a pool, 'error' should mark the worker as not-busy, reject the in-progress task, and optionally restart the worker.

7. **Forgetting that class instances lose their prototype after `postMessage`?** — Structured clone copies enumerable own properties but not the prototype chain. An instance of `class User { greet() { ... } }` becomes a plain object `{ name: '...' }` after cloning — the `greet()` method is gone. Either serialize class instances to plain objects explicitly, use `workerData` for read-only configuration, or redesign to avoid sending class instances between threads.

8. **Not calling `.terminate()` on workers in the pool during shutdown?** — Active worker threads prevent Node.js from exiting — their handles keep the event loop alive. A pool without a `destroy()` method that calls `worker.terminate()` will cause the application to hang on shutdown. Always implement graceful shutdown: reject queued tasks, then `await Promise.all(workers.map(w => w.terminate()))`.

9. **Using `require` side effects or global state that doesn't work across threads?** — Each worker gets its own module cache and global scope. Code that reads/modifies Node.js global state (e.g., overriding `console`, setting global exception handlers, configuring singleton database connections) must be set up independently in each worker's script. There is no automatic inheritance of main thread's module-scope state.

10. **Passing `undefined` or functions in `workerData`?** — `workerData` is serialized with the structured clone algorithm. `undefined` values in objects are preserved (unlike JSON), but functions throw `DataCloneError`. Validate `workerData` before creating the worker: any function, Symbol, WeakMap, WeakSet, or non-cloneable object will cause the `Worker` constructor to throw synchronously.

---

**Final Tip:** At the 5 YOE level, the decisive signal for `worker_threads` questions is knowing *why* each mechanism exists — not just what the API looks like. For `workerData` vs `postMessage`: *"`workerData` is synchronously available at the top of the worker script before any event loop iteration — use it for configuration the worker needs to initialize; `postMessage` is asynchronous event-loop-driven communication — use it for tasks submitted to a running worker and results returned from it."* For transfer vs clone: *"cloning copies bytes — O(n) in data size; transferring moves ownership in O(1) regardless of size by reassigning the underlying memory pointer; after transfer, `buffer.byteLength === 0` in the sender, so plan your data flow before you transfer."* For `SharedArrayBuffer` vs `postMessage`: *"start with `postMessage` — it's correct by default and the structured clone algorithm handles most types; switch to `SharedArrayBuffer` only when profiling shows that serialization overhead is measurable, and be prepared to add `Atomics` operations everywhere you read or write the buffer — unsynchronized access to shared memory is a data race regardless of how unlikely it seems."* And the critical architecture insight: *"the creation cost of a worker is 10-60ms and ~4-10MB of memory — a thread pool created at startup amortizes this to zero per task, which is why any application that runs more than a few dozen worker tasks in its lifetime should use a pool rather than creating workers on demand."*
