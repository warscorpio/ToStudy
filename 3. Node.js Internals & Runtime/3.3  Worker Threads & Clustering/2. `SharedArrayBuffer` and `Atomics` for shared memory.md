# `SharedArrayBuffer` and `Atomics` for Shared Memory — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: `SharedArrayBuffer` Fundamentals

**Q1. What is `SharedArrayBuffer` and how does it differ from `ArrayBuffer`?**
A: Both are fixed-length raw binary memory buffers, but they differ in one fundamental way: **ownership**.

`ArrayBuffer` is owned by a single thread. When you transfer it to a Worker via `postMessage`, it is **neutered** — the sending thread loses access entirely (ownership is transferred, not copied). This is the structured clone algorithm's "transferable" mechanism.

`SharedArrayBuffer` has no single owner. It represents a region of memory accessible by **multiple threads simultaneously** — the main thread and any number of Workers all hold a reference to the exact same bytes. No transfer occurs; no copying occurs. Every thread reads and writes the same physical memory.

```js
// ArrayBuffer — transfer (sender loses access):
const buffer = new ArrayBuffer(1024);
const view   = new Int32Array(buffer);
view[0] = 42;

worker.postMessage({ buffer }, [buffer]); // ← transferable list
console.log(buffer.byteLength); // → 0 — buffer is neutered, sender has no memory

// SharedArrayBuffer — share (all threads keep access):
const shared = new SharedArrayBuffer(1024);
const view2  = new Int32Array(shared);
view2[0] = 42;

worker.postMessage({ shared }); // ← NOT in transferable list — it's shared, not transferred
console.log(shared.byteLength); // → 1024 — still accessible on main thread

// Inside the worker:
// self.onmessage = ({ data: { shared } }) => {
//   const workerView = new Int32Array(shared);
//   workerView[0]; // → 42 — same memory as main thread's view2[0]
// };
```

`SharedArrayBuffer` does not hold typed data itself — it is raw bytes. You layer a **TypedArray view** (`Int32Array`, `Float64Array`, `Uint8Array`, etc.) or a `DataView` on top to interpret those bytes as a specific numeric type.

**Q2. What TypedArray views can be used with `SharedArrayBuffer`, and what are their trade-offs?**
A: Any TypedArray can view a `SharedArrayBuffer`. The choice determines element size, type, and which `Atomics` operations are valid:

| TypedArray | Element Size | Value Range | Atomics Support |
|---|---|---|---|
| `Int8Array` | 1 byte | –128 to 127 | ✓ |
| `Uint8Array` | 1 byte | 0 to 255 | ✓ |
| `Int16Array` | 2 bytes | –32768 to 32767 | ✓ |
| `Uint16Array` | 2 bytes | 0 to 65535 | ✓ |
| `Int32Array` | 4 bytes | –2³¹ to 2³¹–1 | ✓ (most common for Atomics) |
| `Uint32Array` | 4 bytes | 0 to 2³²–1 | ✓ |
| `BigInt64Array` | 8 bytes | –2⁶³ to 2⁶³–1 | ✓ (ES2020) |
| `BigUint64Array` | 8 bytes | 0 to 2⁶⁴–1 | ✓ (ES2020) |
| `Float32Array` | 4 bytes | IEEE 754 float | ✗ (no Atomics) |
| `Float64Array` | 8 bytes | IEEE 754 double | ✗ (no Atomics) |

`Int32Array` is the most commonly used with `Atomics` because:
- 4-byte alignment matches the CPU's native word size — atomic operations on it are natively supported by most hardware instruction sets (e.g., x86's `LOCK XADD`, `CMPXCHG`).
- `Atomics.wait()` and `Atomics.notify()` only accept `Int32Array` and `BigInt64Array`.
- Covers the most common counter / flag / lock use cases.

Float arrays have no `Atomics` support because hardware lacks native atomic float arithmetic instructions — float operations require multiple machine instructions and cannot be made atomic cheaply.

**Q3. Why was `SharedArrayBuffer` disabled in all browsers in January 2018 and how was it re-enabled?**
A: In January 2018, following disclosure of the **Spectre** and **Meltdown** CPU vulnerabilities, all major browsers disabled `SharedArrayBuffer`. The reason: `SharedArrayBuffer` combined with a high-resolution timer enables a **timing side-channel attack** that can read arbitrary memory from other browser tabs or processes.

The attack mechanism:
```
1. Attacker allocates a SharedArrayBuffer
2. A Worker thread increments a counter in shared memory as fast as possible
3. Main thread reads the counter value before and after a sensitive memory access
4. The delta reveals how long the memory access took
5. Timing variations expose cache state — whether specific memory addresses are cached
6. Cache state reveals bits of memory content from other origins (Spectre)

SharedArrayBuffer makes this attack precise because:
  - The shared counter acts as a high-resolution timer (~5ns precision)
  - Performance.now() was coarsened to 1ms — but SharedArrayBuffer bypasses this
  - No SharedArrayBuffer = no precise timer = attack impractical
```

Re-enabled in 2020 with **two required HTTP response headers** that create a **Cross-Origin Isolated** browsing context:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

```js
// Express.js: setting the required headers:
app.use((req, res, next) => {
  res.setHeader('Cross-Origin-Opener-Policy',  'same-origin');
  res.setHeader('Cross-Origin-Embedder-Policy', 'require-corp');
  next();
});

// Check if cross-origin isolated (SharedArrayBuffer available):
if (crossOriginIsolated) {
  const sab = new SharedArrayBuffer(1024); // ✓ works
} else {
  console.error('SharedArrayBuffer not available — missing COOP/COEP headers');
}
```

COOP isolates the browsing context's process from other origins — other tabs can no longer share a process with the page, closing the cross-process side channel. COEP prevents the page from loading cross-origin resources unless they explicitly opt in, preventing the page from embedding untrusted content that could be attacked.

In **Node.js Worker Threads**, `SharedArrayBuffer` is always available — there is no browser security model, and Node.js workers cannot load cross-origin content.

### Section 2: `Atomics` Operations

**Q4. What is a data race and why does accessing `SharedArrayBuffer` without `Atomics` cause them?**
A: A **data race** occurs when two or more threads access the same memory location concurrently, at least one access is a write, and there is no synchronization mechanism ordering the accesses. The result is **undefined behavior** — not just incorrect results, but behavior that violates your mental model of how programs execute.

Without `Atomics`, a simple increment on shared memory is not atomic at the hardware level. It compiles to three separate machine instructions:

```
JavaScript:  view[0]++

Compiles to three machine instructions:
  1. LOAD:  read value from memory into CPU register     → reg = mem[0]
  2. ADD:   increment the register                       → reg = reg + 1
  3. STORE: write register back to memory                → mem[0] = reg
```

Two threads executing this simultaneously can interleave:

```
Thread A                    Thread B                  mem[0]
──────────────────────────────────────────────────────────
LOAD  reg_A = mem[0]                                  0
                            LOAD  reg_B = mem[0]      0
ADD   reg_A = 0 + 1 = 1                               0
                            ADD   reg_B = 0 + 1 = 1   0
STORE mem[0] = reg_A = 1                              1
                            STORE mem[0] = reg_B = 1  1  ← lost update!

Expected: mem[0] = 2
Actual:   mem[0] = 1 — Thread A's write was overwritten
```

This is a **lost update** — a classic data race. It is non-deterministic: sometimes you get 2 (correct), sometimes 1 (wrong), depending on exact CPU scheduling. Impossible to reproduce reliably.

```js
// ❌ Data race — looks correct but isn't:
const sab  = new SharedArrayBuffer(4);
const view = new Int32Array(sab);

// Main thread and worker both run this concurrently:
for (let i = 0; i < 100_000; i++) {
  view[0]++; // NOT ATOMIC — read-modify-write is three separate ops
}
// Expected after both finish: 200,000
// Actual: somewhere between 100,000 and 200,000 — nondeterministic
```

**Q5. What does `Atomics.add()` do and what other arithmetic operations does `Atomics` provide?**
A: `Atomics.add(typedArray, index, value)` performs an atomic read-modify-write: it reads the current value at `index`, adds `value`, writes the result back — all as a single indivisible hardware instruction. No other thread can observe the intermediate state. It returns the **old value** (before the add).

```js
const sab  = new SharedArrayBuffer(4);
const view = new Int32Array(sab);

// Atomic add — returns old value:
const old = Atomics.add(view, 0, 5); // old value + 5 stored atomically
console.log(old);       // → 0  (the value before adding)
console.log(view[0]);   // → 5

// Safe concurrent increment from multiple workers:
Atomics.add(view, 0, 1); // ← no matter how many threads call this simultaneously,
                          //   every increment is counted — zero lost updates
```

Full set of atomic arithmetic and bitwise operations:

```js
const sab  = new SharedArrayBuffer(4);
const i32  = new Int32Array(sab);

// Arithmetic:
Atomics.add(i32, 0, 10);     // i32[0] += 10  → returns old value
Atomics.sub(i32, 0, 3);      // i32[0] -= 3   → returns old value

// Bitwise:
Atomics.and(i32, 0, 0b1010); // i32[0] &= mask → returns old value
Atomics.or (i32, 0, 0b0101); // i32[0] |= mask → returns old value
Atomics.xor(i32, 0, 0b1111); // i32[0] ^= mask → returns old value

// Load / Store — atomic read and write:
Atomics.store(i32, 0, 42);   // write 42 atomically (no torn write)
const val = Atomics.load(i32, 0); // read atomically (no torn read)

// Exchange — atomic swap, returns old value:
const prev = Atomics.exchange(i32, 0, 99); // sets i32[0] = 99, returns old value
```

**Q6. What is `Atomics.compareExchange()` and why is it the foundation of lock-free programming?**
A: `Atomics.compareExchange(typedArray, index, expectedValue, replacementValue)` is a **Compare-And-Swap (CAS)** operation. It atomically:
1. Reads the current value at `index`
2. Compares it to `expectedValue`
3. **Only if they match**: writes `replacementValue`
4. Returns the **old value** (whether or not the swap occurred)

If the returned value equals `expectedValue`, the swap succeeded. If not, another thread changed the value between your read and the CAS — you must retry.

```js
const sab  = new SharedArrayBuffer(4);
const i32  = new Int32Array(sab);
i32[0] = 10;

// CAS: "if the value is 10, change it to 20":
const old = Atomics.compareExchange(i32, 0, 10, 20);
// old === 10 → swap succeeded → i32[0] is now 20
console.log(old);    // → 10 (old value)
console.log(i32[0]); // → 20

// CAS fails if value changed between our read and the swap:
const old2 = Atomics.compareExchange(i32, 0, 10, 99);
// i32[0] is 20 now, not 10 → CAS fails → i32[0] unchanged
console.log(old2);   // → 20 (actual value — not 10 as expected)
console.log(i32[0]); // → 20 (unchanged)
```

CAS is the foundation of lock-free data structures because it gives you a way to make a conditional update without holding a lock. The standard pattern is a **CAS loop**:

```js
// Lock-free increment using CAS loop:
function atomicIncrement(view, index) {
  while (true) {
    const current = Atomics.load(view, index);        // read current value
    const next    = current + 1;                       // compute new value
    const actual  = Atomics.compareExchange(view, index, current, next);
    if (actual === current) return next;               // swap succeeded — done
    // actual !== current: another thread changed the value — retry
    // This loop is "optimistic" — assumes no contention, retries on conflict
  }
}
// Under low contention: almost always succeeds on first try
// Under high contention: may spin many times — CAS loops can waste CPU
```

**Q7. What are `Atomics.wait()` and `Atomics.notify()` and how do they enable thread synchronization?**
A: These are the blocking synchronization primitives — analogous to a **futex** (fast userspace mutex) in Linux, or `condition_variable` in C++.

`Atomics.wait(typedArray, index, value, timeout?)`:
- Checks if `typedArray[index] === value`
- If yes: **blocks the calling thread** until either `Atomics.notify()` wakes it, or the optional timeout expires
- If no: returns `"not-equal"` immediately (value already changed — no need to wait)
- Returns: `"ok"` (woken by notify), `"timed-out"`, or `"not-equal"`
- **Cannot be called on the main thread** in browsers (would freeze the UI). Use `Atomics.waitAsync()` on the main thread.

`Atomics.notify(typedArray, index, count?)`:
- Wakes up to `count` threads (default: all) that are waiting at `typedArray[index]`
- Returns the number of threads actually woken
- Can be called from any thread including the main thread

```js
// Worker A — waits for a signal:
const sab  = new SharedArrayBuffer(4);
const flag = new Int32Array(sab);

// worker-a.js:
const result = Atomics.wait(flag, 0, 0); // "block until flag[0] !== 0"
// → thread is suspended here, consumes zero CPU
// → wakes up when notify() is called
console.log('Worker A woke up:', result); // "ok"
doWork();

// Main thread or Worker B — sends the signal:
flag[0] = 1;                    // set the value so wait's condition changes
Atomics.notify(flag, 0, 1);    // wake 1 waiting thread at index 0
```

The combination of `wait` + `notify` is how you build:
- **Mutexes** (lock/unlock)
- **Condition variables** (wait for a condition, signal when ready)
- **Semaphores** (counting locks)
- **Work queues** (workers sleep until work arrives, producer notifies)

**Q8. What is `Atomics.waitAsync()` and when do you need it?**
A: `Atomics.waitAsync(typedArray, index, value, timeout?)` is the **non-blocking** variant of `Atomics.wait()`. Instead of blocking the thread, it returns a Promise that resolves when the wait condition is met.

It is required when:
- You need to wait on the **main thread** (browsers forbid blocking the main thread)
- You want to wait inside an `async` function without blocking the entire thread
- You are coordinating between the main thread and a Worker

```js
// Main thread cannot call Atomics.wait() — would freeze the tab
// Use waitAsync() instead:

const sab  = new SharedArrayBuffer(4);
const flag = new Int32Array(sab);

// Main thread:
async function waitForWorker() {
  const { async, value } = Atomics.waitAsync(flag, 0, 0);
  // async: true if it will wait (value matched), false if resolved immediately

  if (async) {
    const result = await value; // Promise<"ok" | "timed-out" | "not-equal">
    console.log('Main thread notified:', result); // "ok"
  }
}

// Worker thread signals completion:
// flag[0] = 1;
// Atomics.notify(flag, 0, 1); // ← main thread's Promise resolves

// waitAsync is also composable with Promise.race for timeouts:
async function waitWithTimeout(flag, index, currentValue, ms) {
  const { async, value } = Atomics.waitAsync(flag, index, currentValue, ms);
  if (!async) return 'not-equal';
  return value; // resolves with "ok" or "timed-out"
}
```

### Section 3: Memory Model and Ordering

**Q9. What is the JavaScript memory model and what guarantees do `Atomics` provide?**
A: JavaScript's memory model defines what values a thread is *allowed* to observe when reading shared memory. Without `Atomics`, the spec gives very weak guarantees — CPUs and compilers reorder reads and writes for performance, so threads may observe stale values or operations in unexpected orders.

`Atomics` operations are **sequentially consistent** — they impose a total ordering of operations visible to all threads. Every atomic operation includes an implicit **memory fence** (memory barrier): it flushes the CPU's store buffer and invalidates cache lines so all other threads see the write immediately.

```js
// Without Atomics — memory ordering NOT guaranteed:
// Thread A:
view[0] = 1;          // write flag
view[1] = computedResult; // write data

// Thread B:
if (view[0] === 1) {  // read flag
  use(view[1]);       // read data — NOT SAFE: may see old value of view[1]
                      // CPU/compiler may reorder Thread A's writes
                      // Thread B may see view[0] = 1 but view[1] = 0 (old)
}

// With Atomics — sequentially consistent ordering guaranteed:
// Thread A:
view[1] = computedResult;        // write data FIRST
Atomics.store(view, 0, 1);       // store flag — full memory fence
                                 // guarantees view[1] is visible before flag

// Thread B:
if (Atomics.load(view, 0) === 1) { // load flag — full memory fence
  use(view[1]);                    // SAFE: if flag is 1, data is visible
}
```

The sequential consistency guarantee means:
1. Atomic operations appear to execute in a single global order visible to all threads.
2. No thread can observe atomic operations "out of order" relative to other atomics.
3. Non-atomic accesses near atomic operations gain ordering too — the fence prevents the CPU from floating non-atomic reads/writes across an atomic operation.

**Q10. What is a "torn read" or "torn write" and does `Atomics` protect against them?**
A: A torn read (or torn write) occurs when a multi-byte value is read or written by multiple separate memory transactions, and another thread reads the value mid-write — observing a partially updated state that never actually existed.

```
Torn write example (64-bit double, 8 bytes):
  Thread A writes 0xDEADBEEFCAFEBABE to Float64Array[0]

  Without atomic guarantee, the CPU may write in two 4-byte transactions:
    Write lower 4 bytes: 0xCAFEBABE  ← Thread B reads HERE
    Write upper 4 bytes: 0xDEADBEEF

  Thread B reads: 0x00000000CAFEBABE — a value that was never stored!
  This is a torn read.
```

`Atomics` protects against torn reads and writes for the types it supports (`Int32Array` and smaller are naturally aligned and atomic on all modern hardware). Non-atomic accesses to `SharedArrayBuffer` elements have **no torn-write protection** in the spec, even for small types — only in practice on most current CPUs.

```js
// Float64Array — no Atomics support → torn reads possible in theory:
const sab     = new SharedArrayBuffer(8);
const float64 = new Float64Array(sab);

// Thread A: float64[0] = 3.14159265358979  ← may be two 4-byte writes
// Thread B: const x = float64[0]           ← may read mid-write

// Safe pattern for floats: use a lock (mutex) around float reads/writes,
// or encode floats as Int32Array pairs with Atomics coordination.

// Int32Array — atomic by hardware alignment on all x86/ARM CPUs:
const int32 = new Int32Array(sab);
// Single 4-byte aligned access — hardware guarantees atomicity even without Atomics
// But: still no ordering guarantee without Atomics.load/store
```

### Section 4: Patterns and Use Cases

**Q11. What are the primary use cases for `SharedArrayBuffer` and `Atomics` in practice?**
A: Four dominant use cases:

**1. High-throughput Worker Thread pools with shared work queues**: instead of serializing tasks through `postMessage`, workers dequeue tasks directly from shared memory — eliminating serialization overhead for large volumes of small tasks.

**2. Shared metrics and counters across workers**: a cluster of request-handling workers atomically increment shared counters (request count, error count, bytes transferred) without inter-process communication.

**3. Parallel numerical computation**: image processing, audio analysis, physics simulation — split a `Float32Array` of pixel values or sample data across workers, each processing its own segment of the shared buffer.

**4. WebAssembly multi-threading**: `wasm-bindgen`, Emscripten, and other Wasm toolchains use `SharedArrayBuffer` to give WebAssembly the equivalent of `pthread` (POSIX threads). Wasm threads use `SharedArrayBuffer` for their stack and heap.

**Q12. What are the performance trade-offs of `SharedArrayBuffer` + `Atomics` vs `postMessage`?**
A:

| Concern | `postMessage` | `SharedArrayBuffer` + `Atomics` |
|---|---|---|
| **Data transfer** | Serialized (structured clone) — O(n) copy | Zero copy — O(1) reference |
| **Latency per message** | ~0.01ms + serialization time | ~0 (direct memory access) |
| **Large data (100MB+)** | Very slow (copying 100MB) | Instant (pointer share) |
| **Small messages** | Fine — overhead is absolute, small at low volume | Overkill — CAS loop overhead |
| **Synchronization** | Implicit (messages are ordered) | Explicit — you must use Atomics |
| **Complexity** | Low — familiar async model | High — concurrent programming is hard |
| **Bugs** | Race conditions impossible (no sharing) | Race conditions possible if Atomics misused |
| **Debugging** | Straightforward | Extremely hard — heisenbugs, non-deterministic |

Rule of thumb:
- Data < ~1MB and exchanged infrequently → `postMessage`
- Data > 10MB or exchanged at >1,000 Hz → `SharedArrayBuffer`
- Need a result from a Worker immediately without async overhead → `SharedArrayBuffer` + `Atomics.wait()`

### Section 5: Scenario / Interview-Style Questions

**Q13. "Explain how you would implement a mutex (mutual exclusion lock) using `SharedArrayBuffer` and `Atomics`."**
A: A mutex ensures only one thread executes a critical section at a time. Implementation uses `Atomics.compareExchange` to acquire the lock and `Atomics.wait` / `Atomics.notify` to block and wake waiters:

```js
// Mutex uses one Int32 in shared memory:
//   0 = UNLOCKED
//   1 = LOCKED

const UNLOCKED = 0;
const LOCKED   = 1;

class Mutex {
  constructor(sharedBuffer, byteOffset = 0) {
    this._lock = new Int32Array(sharedBuffer, byteOffset, 1);
  }

  // Acquire: block until lock is obtained
  lock() {
    while (true) {
      // CAS: if UNLOCKED → set to LOCKED (returns old value)
      const old = Atomics.compareExchange(this._lock, 0, UNLOCKED, LOCKED);
      if (old === UNLOCKED) return; // ← acquired the lock

      // Lock is held by another thread — wait efficiently (no busy-spin):
      // Atomics.wait blocks until _lock[0] changes OR is notified
      Atomics.wait(this._lock, 0, LOCKED); // "wait while lock[0] === LOCKED"
      // When woken: loop back and try CAS again
    }
  }

  // Release: unlock and wake one waiting thread
  unlock() {
    Atomics.store(this._lock, 0, UNLOCKED); // release the lock
    Atomics.notify(this._lock, 0, 1);       // wake one waiter
  }

  // Convenience: run fn inside the lock, unlock even if fn throws
  withLock(fn) {
    this.lock();
    try {
      return fn();
    } finally {
      this.unlock();
    }
  }
}

// Usage across workers:
// All workers share the same SharedArrayBuffer
const sab   = new SharedArrayBuffer(4 + /* data size */ 4);
const mutex = new Mutex(sab, 0);           // lock at byte offset 0
const data  = new Int32Array(sab, 4, 1);   // data at byte offset 4

// Worker A and Worker B can call this simultaneously — safe:
function incrementSharedCounter() {
  mutex.withLock(() => {
    data[0]++; // non-atomic increment is fine inside the mutex
  });
}
```

The subtle correctness point: `Atomics.wait(lock, 0, LOCKED)` checks "is `lock[0]` still `LOCKED`?" before blocking. If the lock was released between our failed CAS and the wait call, `wait` returns `"not-equal"` immediately — no deadlock. This check-then-wait pattern is the futex optimization: no kernel involvement when there's no contention.

**Q14. "How does `SharedArrayBuffer` enable zero-copy data sharing between workers, and what are the gotchas?"**
A: When a Worker receives a `SharedArrayBuffer` via `postMessage`, no data is copied. The Worker receives a reference to the same memory region. Writes by one thread are immediately visible to all others — subject to memory ordering guarantees.

```js
// Zero-copy: send 500MB image buffer to 4 workers instantly
const imageBuffer = new SharedArrayBuffer(500 * 1024 * 1024); // 500MB
const pixels      = new Uint8Array(imageBuffer);

// Fill with image data (single copy from disk/network → SharedArrayBuffer)
loadImageInto(pixels);

// Send to 4 workers — zero bytes copied:
for (const worker of workers) {
  worker.postMessage({ imageBuffer }); // reference, not copy
}

// Each worker processes its own region — no overlap → no Atomics needed:
// worker.js:
self.onmessage = ({ data: { imageBuffer, start, end } }) => {
  const pixels = new Uint8Array(imageBuffer);
  for (let i = start; i < end; i++) {
    pixels[i] = 255 - pixels[i]; // invert — safe: each worker has exclusive range
  }
  self.postMessage('done');
};
```

**Gotchas:**

1. **Visibility is not guaranteed without Atomics**: a worker writing to `view[0] = 42` without `Atomics.store` may not be visible to another worker reading `view[0]` without `Atomics.load` due to CPU cache and store buffer effects.

2. **No garbage collection coordination**: the `SharedArrayBuffer` is kept alive as long as *any* thread holds a reference. Forgetting to null out references in workers leaks memory.

3. **No built-in bounds tracking**: two workers writing overlapping index ranges will silently corrupt data. You must manually partition ranges and document which indices each worker owns.

4. **COOP/COEP headers required in browsers**: deploying without them means `SharedArrayBuffer` is `undefined` at runtime — no error at import time.

5. **`Atomics.wait()` blocks the OS thread**: calling it with a long timeout in a Worker blocks that Worker's thread entirely — it can't process other messages. Design workers to be either "blocked waiting" or "processing work", not both.

## Problem 1 — Demonstrating and Fixing a Data Race

### Problem
The following code runs a counter increment across two Worker Threads and expects the result to be 200,000. It consistently produces a lower number. Explain why and fix it with and without `Atomics`.

```js
// main.js
const { Worker, isMainThread, workerData, parentPort } = require('worker_threads');

if (isMainThread) {
  const sab     = new SharedArrayBuffer(4);
  const counter = new Int32Array(sab);

  const w1 = new Worker(__filename, { workerData: { sab } });
  const w2 = new Worker(__filename, { workerData: { sab } });

  let done = 0;
  function onDone() {
    if (++done === 2) {
      console.log('Final counter:', counter[0]); // Expected: 200,000 — actual: less
    }
  }
  w1.on('exit', onDone);
  w2.on('exit', onDone);

} else {
  const counter = new Int32Array(workerData.sab);
  for (let i = 0; i < 100_000; i++) {
    counter[0]++; // ← data race: not atomic
  }
  process.exit(0);
}
```

### Root Cause: The Three-Instruction Problem

```
counter[0]++ compiles to three separate machine instructions:

  1. LOAD  : reg ← mem[counter + 0]   (read current value)
  2. ADD   : reg ← reg + 1            (increment in register)
  3. STORE : mem[counter + 0] ← reg   (write back)

Worker 1 and Worker 2 execute this loop concurrently.
The instructions from both workers interleave arbitrarily:

  W1: LOAD (reads 1000)
  W2: LOAD (reads 1000)   ← reads SAME value as W1
  W1: ADD  (1000 → 1001)
  W2: ADD  (1000 → 1001)
  W1: STORE (writes 1001)
  W2: STORE (writes 1001) ← overwrites W1's write — lost update!

Net effect: two increments were executed but counter only increased by 1.
This "lost update" happens tens of thousands of times → final value far below 200,000.
Result is non-deterministic: varies by CPU scheduling, load, core count.
```

### Fix 1 — `Atomics.add()` (correct and fast)

```js
// Replace counter[0]++ with an atomic add:
} else {
  const counter = new Int32Array(workerData.sab);
  for (let i = 0; i < 100_000; i++) {
    Atomics.add(counter, 0, 1); // ← atomic: LOAD+ADD+STORE as single instruction
    // Hardware: LOCK XADD (x86) — no interleaving possible
    // Every increment is counted — zero lost updates
  }
  process.exit(0);
}

// Final counter: always exactly 200,000
```

### Fix 2 — Mutex (for more complex critical sections)

```js
// When the critical section is more than a single add:
```

## Problem 2 — Implementing a Lock-Free Ring Buffer (Shared Work Queue)

### Problem
Design a lock-free single-producer single-consumer (SPSC) ring buffer using `SharedArrayBuffer` for a work queue between a main thread (producer) and a Worker (consumer). The consumer should block when the queue is empty without busy-spinning.

### Design

```
Ring buffer layout in SharedArrayBuffer:

  Byte offset 0:  Int32 — writeIndex (producer increments this)
  Byte offset 4:  Int32 — readIndex  (consumer increments this)
  Byte offset 8:  N × Int32 — the data slots

  Queue is FULL when:  (writeIndex - readIndex) === capacity
  Queue is EMPTY when: writeIndex === readIndex
  Available items:     writeIndex - readIndex
  Free slots:          capacity - (writeIndex - readIndex)

  Both indices are monotonically increasing (never wrap around in the index itself)
  Slot for index i: data[ i % capacity ]
```

```js
// ring-buffer.js — shared between main and worker:
const WRITE_INDEX = 0; // element index in Int32Array
const READ_INDEX  = 1;
const DATA_OFFSET = 2; // data starts at element index 2

class SPSCRingBuffer {
  constructor(sharedBuffer, capacity) {
    this.capacity = capacity;
    this.i32      = new Int32Array(sharedBuffer);
    // sharedBuffer must be at least (2 + capacity) * 4 bytes
  }

  // Producer: returns false if full
  tryPush(value) {
    const write = Atomics.load(this.i32, WRITE_INDEX);
    const read  = Atomics.load(this.i32, READ_INDEX);

    if (write - read >= this.capacity) return false; // full

    // Write data first, THEN advance writeIndex
    // (consumer checks writeIndex to know data is ready)
    const slot = write % this.capacity;
    Atomics.store(this.i32, DATA_OFFSET + slot, value);
    Atomics.store(this.i32, WRITE_INDEX, write + 1); // publish

    // Wake consumer if it was waiting on an empty queue:
    Atomics.notify(this.i32, READ_INDEX, 1);
    // Note: notifying on READ_INDEX — consumer waits on READ_INDEX
    // (it checks "has writeIndex changed past readIndex?")
    // Better: use a separate "empty" flag for clarity — see below

    return true;
  }

  // Consumer: returns undefined if empty
  tryPop() {
    const read  = Atomics.load(this.i32, READ_INDEX);
    const write = Atomics.load(this.i32, WRITE_INDEX);

    if (read >= write) return undefined; // empty

    const slot  = read % this.capacity;
    const value = Atomics.load(this.i32, DATA_OFFSET + slot);

    // Advance readIndex AFTER reading data:
    Atomics.store(this.i32, READ_INDEX, read + 1);

    return value;
  }

  // Consumer: block until item is available (Worker thread only — not main thread)
  pop() {
    while (true) {
      const value = this.tryPop();
      if (value !== undefined) return value;

      // Queue is empty — sleep until producer pushes something
      // Wait while writeIndex === readIndex (empty condition)
      const read  = Atomics.load(this.i32, READ_INDEX);
      const write = Atomics.load(this.i32, WRITE_INDEX);
      if (read < write) continue; // item appeared between tryPop and here

      // Atomics.wait: sleep until WRITE_INDEX changes
      // (we pass writeIndex value — if producer already wrote, returns "not-equal")
      Atomics.wait(this.i32, WRITE_INDEX, write);
      // Woken by producer's Atomics.notify → retry
    }
  }

  // Consumer: async wait (for main thread use)
  async popAsync() {
    while (true) {
      const value = this.tryPop();
      if (value !== undefined) return value;

      const write = Atomics.load(this.i32, WRITE_INDEX);
      const { async, value: p } = Atomics.waitAsync(this.i32, WRITE_INDEX, write);
      if (async) await p;
    }
  }
}
```

### Why This Is Faster Than `postMessage`

```

  → 10,000 IPC messages through Node.js internals
  → 10,000 structured clone deserializations
  → Overhead: ~0.05ms per message = 500ms total overhead

SharedArrayBuffer ring buffer:
  → 10,000 atomic stores (write) + 10,000 atomic loads (read)
  → No serialization, no IPC, no copying
  → Overhead: ~0.0001ms per item = 1ms total overhead
  → ~500× less overhead for small items at high throughput

When postMessage is still better:
  → Items are large objects (SAB serializes them as structured clone anyway)
  → Low message volume (< ~100/s) — postMessage's simplicity wins
  → Correctness over performance — postMessage can't have data races
```

### Why No `Atomics` Are Needed Here

```
Memory layout: [ row 0 | row 1 | ... | row 2999 ]

Worker assignment (8 workers, 375 rows each):
  Worker 0: rows 0–374     bytes [0,         600,000)
  Worker 1: rows 375–749   bytes [600,000,   1,200,000)
  Worker 2: rows 750–1124  bytes [1,200,000, 1,800,000)
  ...
  Worker 7: rows 2625–2999 bytes [4,200,000, 4,800,000)

Ranges are DISJOINT — no overlap.
Each worker is the sole reader AND writer of its range.
No concurrent access to any memory address.
→ No data race possible → no Atomics needed

This is the "partition" pattern:
  Data is statically divided so each worker owns a region exclusively.
  Workers communicate only via the completion signal (postMessage 'done').
  Fastest possible access — no atomic overhead, no cache line bouncing.

Contrast with shared counter example:
  Multiple writers to the same index → race condition → need Atomics
  Partitioned data → no sharing → no synchronization needed
```

## Problem 4 — Semaphore for Limiting Concurrent Worker Access

### Problem
A connection pool has 3 database connections. Ten Worker Threads need to use the pool but only 3 can hold a connection at a time. Implement a semaphore using `SharedArrayBuffer` and `Atomics` so workers block when no connection is available.

```js
// semaphore.js — counting semaphore
// Allows up to `initial` concurrent holders; others block until one is released

class Semaphore {
  // Layout:
  //   index 0: current available count (Int32)

  constructor(sharedBuffer, byteOffset = 0, initial) {
    this._i32 = new Int32Array(sharedBuffer, byteOffset, 1);
    if (initial !== undefined) {
      // Only the creator initializes (other workers just use the existing value):
      Atomics.store(this._i32, 0, initial);
    }
  }

  // Decrement (acquire a permit) — blocks if count is 0:
  acquire() {
    while (true) {
      const current = Atomics.load(this._i32, 0);

      if (current > 0) {
        // Try to decrement atomically:
        const actual = Atomics.compareExchange(this._i32, 0, current, current - 1);
        if (actual === current) return; // ← acquired: count was current, now current-1
        // CAS failed (another thread decremented first) → retry
        continue;
      }

      // Count is 0 — no permits available → sleep until a release:
      // wait while count is still 0:
      Atomics.wait(this._i32, 0, 0); // blocks until notify() is called
      // When woken: loop back and try CAS again
    }
  }

  // Increment (release a permit) — wake one waiter:
  release() {
    Atomics.add(this._i32, 0, 1);     // increment count atomically
    Atomics.notify(this._i32, 0, 1);  // wake one blocked acquirer
  }

  // Try acquire without blocking — returns true if acquired, false if not:
  tryAcquire() {
    while (true) {
      const current = Atomics.load(this._i32, 0);
      if (current === 0) return false; // no permits — don't block
      const actual = Atomics.compareExchange(this._i32, 0, current, current - 1);
      if (actual === current) return true; // acquired
      // CAS raced — retry (still non-blocking: we re-read and try again)
    }
  }
}

// connection-pool-worker.js
const { workerData, parentPort } = require('worker_threads');
const { Semaphore } = require('./semaphore');

const sem = new Semaphore(workerData.sab, 0); // byteOffset 0, no initial (already set)

async function runQuery(workerId, queryNum) {
  console.log(`Worker ${workerId}: waiting for connection (query ${queryNum})`);

  sem.acquire(); // ← blocks here if all 3 connections are in use

  try {
    console.log(`Worker ${workerId}: GOT connection (query ${queryNum})`);
    // Simulate DB query:
    await new Promise(r => setTimeout(r, 100 + Math.random() * 200));
    console.log(`Worker ${workerId}: RELEASED connection (query ${queryNum})`);
  } finally {
    sem.release(); // always release — even if query throws
  }
}

(async () => {
  const workerId = workerData.workerId;
  for (let i = 0; i < 3; i++) {
    await runQuery(workerId, i);
  }
  parentPort.postMessage('done');
})();

// main.js

const { Semaphore } = require('./semaphore');

const NUM_WORKERS = 10;

const sab = new SharedArrayBuffer(4); // 1 Int32 for semaphore
const sem = new Semaphore(sab, 0, CONNECTIONS); // init to 3

let done = 0;
for (let i = 0; i < NUM_WORKERS; i++) {
  const w = new Worker('./connection-pool-worker.js', {
    workerData: { sab, workerId: i }
  });
  w.on('message', () => {
    if (++done === NUM_WORKERS) console.log('All workers finished');
  });

// Other workers block in sem.acquire() — efficiently, via Atomics.wait()
```

### Semaphore State Machine

```
Initial state: count = 3 (3 permits available)

Worker 1 acquire(): CAS(3 → 2) ✓  count = 2
Worker 2 acquire(): CAS(2 → 1) ✓  count = 1
Worker 3 acquire(): CAS(1 → 0) ✓  count = 0
Worker 4 acquire(): count = 0 → Atomics.wait(count, 0) → BLOCKED
Worker 5 acquire(): count = 0 → Atomics.wait(count, 0) → BLOCKED

Worker 1 release():
  Atomics.add(count, 0, 1)  → count = 1
  Atomics.notify(count, 0, 1) → wakes Worker 4

Worker 4 woken:
  CAS(1 → 0) ✓ → count = 0 → acquired!
  (Worker 5 still sleeping — not notified yet)

Worker 2 release():
  count → 1
  notify → wakes Worker 5
  Worker 5 acquired
```

## Problem 5 — Shared Metrics Aggregator Across a Worker Cluster

### Problem
A web server spawns one Worker per CPU core. Each Worker handles HTTP requests and must record per-status-code counts (200, 400, 404, 500) into a shared metrics buffer so the main thread can read live metrics without IPC overhead.

```js
// metrics.js — shared layout and helpers:
// Layout (Int32Array):
//   index 0: count of 2xx responses
//   index 1: count of 4xx responses
//   index 2: count of 404 responses (subset of 4xx)
//   index 3: count of 5xx responses
//   index 4: total requests
//   index 5: total response time in ms (use Int32 × 10 for 0.1ms precision)

const METRIC = {
  STATUS_2XX:   0,
  STATUS_4XX:   1,
  STATUS_404:   2,
  STATUS_5XX:   3,
  TOTAL_REQS:   4,
  TOTAL_TIME:   5,
};

class SharedMetrics {
  constructor(sharedBuffer) {
    this._i32 = new Int32Array(sharedBuffer);
  }

  record(statusCode, durationMs) {
    // All increments atomic — multiple workers write simultaneously:
    Atomics.add(this._i32, METRIC.TOTAL_REQS, 1);
    Atomics.add(this._i32, METRIC.TOTAL_TIME, Math.round(durationMs * 10)); // 0.1ms precision

    if (statusCode >= 200 && statusCode < 300) {
      Atomics.add(this._i32, METRIC.STATUS_2XX, 1);
    } else if (statusCode >= 400 && statusCode < 500) {
      Atomics.add(this._i32, METRIC.STATUS_4XX, 1);
      if (statusCode === 404) Atomics.add(this._i32, METRIC.STATUS_404, 1);
    } else if (statusCode >= 500) {
      Atomics.add(this._i32, METRIC.STATUS_5XX, 1);
    }
  }

  // Read a snapshot — no locking needed: Atomics.load for consistent reads
  // Individual metrics may be slightly stale relative to each other (no snapshot atomicity)
  // For a fully atomic snapshot you'd need a lock — acceptable for metrics dashboards
  snapshot() {
    const totalReqs  = Atomics.load(this._i32, METRIC.TOTAL_REQS);
    const totalTime  = Atomics.load(this._i32, METRIC.TOTAL_TIME);
    const status2xx  = Atomics.load(this._i32, METRIC.STATUS_2XX);
    const status4xx  = Atomics.load(this._i32, METRIC.STATUS_4XX);
    const status404  = Atomics.load(this._i32, METRIC.STATUS_404);
    const status5xx  = Atomics.load(this._i32, METRIC.STATUS_5XX);

    return {
      totalRequests:  totalReqs,
      avgLatencyMs:   totalReqs > 0 ? (totalTime / 10 / totalReqs).toFixed(2) : 0,
      successRate:    totalReqs > 0 ? ((status2xx / totalReqs) * 100).toFixed(1) + '%' : '0%',
      status: { '2xx': status2xx, '4xx': status4xx, '404': status404, '5xx': status5xx },
    };
  }

  // Reset all counters atomically (e.g. for per-minute windows):
  reset() {
    for (let i = 0; i < 6; i++) Atomics.store(this._i32, i, 0);
  }
}

module.exports = { SharedMetrics, METRIC };
```

### Why This Is Better Than the Alternative

```
Alternative: workers postMessage their counts to main thread periodically

Problems:
  → Latency: metrics are stale by up to N seconds (the reporting interval)
  → Overhead: N workers × messages per second × serialization cost
  → Coordination: main thread must aggregate N separate snapshots
  → Accuracy: if a worker crashes between reports, its last interval is lost

SharedArrayBuffer approach:
  → Latency: zero — metrics.snapshot() reads the current atomic values
  → Overhead: one Atomics.add() per request (nanoseconds) — no messaging
  → Coordination: none — all workers write to the same counters
  → Accuracy: atomic adds ensure no lost updates even under concurrent load

The only limitation: metrics.snapshot() is not a fully atomic snapshot
(the 6 reads are 6 separate Atomics.load calls — a worker could record
a request between reads). For a dashboard, this is acceptable.
For a precise billing system, wrap the snapshot reads in a mutex.
```

## Quick Reference — `SharedArrayBuffer` and `Atomics` Cheat Sheet

```
SHAREDARRAYBUFFER:
  new SharedArrayBuffer(byteLength)     → fixed-size shared memory region
  View with: new Int32Array(sab)        → element access (read/write)
  Transfer:  NOT transferable — shared by reference, not copied
  In browsers: requires COOP + COEP headers (crossOriginIsolated === true)
  In Node.js:  always available in Worker Threads

ATOMICS — ARITHMETIC (return old value):
  Atomics.add(ta, i, val)              → ta[i] += val,  returns old ta[i]
  Atomics.sub(ta, i, val)              → ta[i] -= val,  returns old ta[i]
  Atomics.and(ta, i, val)              → ta[i] &= val,  returns old ta[i]
  Atomics.or (ta, i, val)              → ta[i] |= val,  returns old ta[i]
  Atomics.xor(ta, i, val)              → ta[i] ^= val,  returns old ta[i]

ATOMICS — LOAD / STORE / EXCHANGE:
  Atomics.load(ta, i)                  → atomic read (with memory fence)
  Atomics.store(ta, i, val)            → atomic write (with memory fence)
  Atomics.exchange(ta, i, val)         → atomic swap; returns old value

ATOMICS — COMPARE AND SWAP:
  Atomics.compareExchange(ta, i, expected, replacement)
    → if ta[i] === expected: ta[i] = replacement
    → returns old ta[i] (check old === expected to know if swap succeeded)
    → foundation of lock-free algorithms and mutex implementation

ATOMICS — WAIT / NOTIFY (blocking synchronization):
  Atomics.wait(ta, i, value, timeout?) → block thread if ta[i] === value
    → returns "ok" (woken), "timed-out", or "not-equal"
    → ONLY in Worker threads (not main browser thread)
    → Int32Array and BigInt64Array only
  Atomics.notify(ta, i, count?)        → wake up to count waiting threads
    → returns number of threads woken
    → works from any thread including main
  Atomics.waitAsync(ta, i, value, timeout?)  → non-blocking Promise-based wait
    → works on main thread
    → returns { async: bool, value: Promise | string }

PATTERNS:
  Shared counter:     Atomics.add(i32, 0, 1)
  Flag/signal:        Atomics.store(i32, 0, 1); Atomics.notify(i32, 0, 1)
  Wait for signal:    Atomics.wait(i32, 0, 0)  ("wait while flag is 0")
  Mutex acquire:      CAS loop: compareExchange(0, UNLOCKED, LOCKED)
  Mutex release:      Atomics.store(lock, 0, UNLOCKED); notify(lock, 0, 1)
  Semaphore acquire:  CAS(count, count, count-1); if count=0 → wait
  Semaphore release:  Atomics.add(count, 0, 1); notify(count, 0, 1)
  Partition (no sync):Divide array into disjoint ranges per worker — no Atomics needed

MEMORY MODEL:
  Atomics operations: sequentially consistent — total global order across threads
  Atomics.load/store: full memory fence — other threads see writes immediately
  Non-atomic access:  NO ordering guarantee — use Atomics.load/store for coordination flags
  Write data THEN set flag: Atomics.store(flag, 0, 1) after writing data ensures data visible

WHEN TO USE vs postMessage:
  postMessage:        simple, safe (no races), small data, low frequency
  SharedArrayBuffer:  large data (no copy), high frequency, tight latency budgets
  Partitioned work:   no Atomics needed — just share the buffer + coordinate ranges
  Shared state:       Atomics required — use the right primitive for the pattern

COMMON BUGS:
  Forgetting Atomics for flags    → data race: other thread sees stale flag
  Atomics.wait() on main thread   → TypeError in browsers — use waitAsync()
  Float64Array with Atomics       → TypeError — Atomics only supports integer arrays
  Notify before wait              → fine: wait checks value first; returns "not-equal"
  Missing COOP/COEP headers       → SharedArrayBuffer is undefined at runtime
  Workers write overlapping ranges → data race; partition carefully or use a mutex
  Lock acquired but not released  → deadlock; always release in finally {}
```

**Final Tip:** At the 5 YOE level, `SharedArrayBuffer` and `Atomics` questions test whether you can reason about **concurrent memory access** at the hardware level — not just the JavaScript API. The highest-signal answer on data races: "A non-atomic `counter[0]++` is three machine instructions — load, add, store — and two threads can interleave those instructions arbitrarily. `Atomics.add` maps to a single hardware instruction with a LOCK prefix that makes the bus inaccessible to other cores for the duration. The result: every increment is counted, zero lost updates." For `Atomics.wait` / `notify`: "This is essentially a JavaScript futex — the thread suspends at the OS level and consumes zero CPU while waiting, exactly like `pthread_cond_wait`. The key subtlety is that `wait` checks the value atomically before sleeping, so if `notify` fires between your load and your `wait` call, `wait` returns `not-equal` immediately rather than sleeping forever." For the mutex pattern: "The CAS loop implements a spinlock for fast acquisition, with `Atomics.wait` as the fallback for contended cases — giving you the performance of a spinlock when uncontended and the CPU efficiency of a blocking wait under contention. That's the same design as Linux's `futex` system call."
