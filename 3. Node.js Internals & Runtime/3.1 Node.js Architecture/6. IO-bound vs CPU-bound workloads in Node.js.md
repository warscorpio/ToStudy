# I/O-Bound vs CPU-Bound Workloads in Node.js — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the difference between an I/O-bound and a CPU-bound workload?**
A: The distinction is about where the bottleneck lives — what the program is *waiting on*:

**I/O-bound**: the program spends most of its time waiting for external systems to respond — a database query to return rows, a file to be read from disk, a remote API to reply, a DNS lookup to resolve. The CPU is idle during this wait. Throwing more CPU at the problem does not help; the bottleneck is latency of the external system.

**CPU-bound**: the program spends most of its time doing computation — parsing a large JSON payload, running a compression algorithm, processing an image, executing a machine learning inference, computing a cryptographic hash of a large buffer. The CPU is pegged at 100%. Adding more cores *does* help; the bottleneck is raw compute capacity.

```
I/O-bound timeline:
  Thread: [---request---][WAIT for DB 90ms][---response---]
  CPU:     working         idle              working
  Bottleneck: network/disk latency

CPU-bound timeline:
  Thread: [=================compute 500ms=================]
  CPU:     100% the entire time
  Bottleneck: processor speed / number of cores
```

This distinction is the root of nearly every Node.js architecture decision: Node.js handles I/O-bound work excellently by design, but requires deliberate engineering to handle CPU-bound work without catastrophic consequences.

**Q2. Why does Node.js excel at I/O-bound workloads but struggle with CPU-bound ones?**
A: Node.js is built on a single-threaded event loop. That single thread runs JavaScript, but it delegates I/O operations to the operating system or libuv's thread pool, both of which handle the actual waiting. The JS thread is free to do other work while I/O is in flight.

```
Node.js single-threaded event loop handling I/O:

Main Thread (JS):
  receive request A → kick off DB query A → [free to handle request B]
  receive request B → kick off DB query B → [free to handle request C]
  DB query A returns → handle A's response
  DB query B returns → handle B's response

   Time →
   [A setup][B setup][C setup][A done][B done]
    ↑ Main thread never idles — always processing something

OS/libuv (underneath):
   [======= DB query A waiting =======]
              [======= DB query B waiting =======]
   These wait in parallel on OS-level I/O threads
```

For CPU-bound work, the equation reverses entirely:

```
Main Thread handling CPU work:

  receive request A → [=== compute 500ms ===] → respond A
  receive request B → [blocked — can't run]
  receive request C → [blocked — can't run]

   Time →
   [A compute 500ms               ][B compute][C compute]
    ↑ Every other request WAITS
    ↑ Event loop is blocked — no timers, no I/O callbacks, nothing runs
```

The event loop blocking is the core problem. One synchronous CPU-heavy computation starves every other concurrent request, timer, and I/O callback that is waiting to run.

**Q3. What is the Node.js event loop and what are its phases?**
A: The event loop is the mechanism Node.js uses to perform non-blocking I/O despite running JavaScript on a single thread. It is implemented by libuv and runs in a continuous loop of phases:

```
   ┌────────────────────────────┐
   │         timers             │  ← executes setTimeout / setInterval callbacks
   │  (callbacks whose delay    │    whose delay threshold has elapsed
   │   threshold has passed)    │
   └────────────┬───────────────┘
                │
   ┌────────────▼───────────────┐
   │     pending callbacks      │  ← I/O error callbacks deferred from prev iteration
   └────────────┬───────────────┘
                │
   ┌────────────▼───────────────┐
   │      idle, prepare         │  ← internal use only
   └────────────┬───────────────┘
                │
   ┌────────────▼───────────────┐
   │           poll             │  ← fetch new I/O events; execute I/O callbacks
   │                            │    if no timers pending: block here waiting for I/O
   └────────────┬───────────────┘
                │
   ┌────────────▼───────────────┐
   │          check             │  ← setImmediate() callbacks run here
   └────────────┬───────────────┘
                │
   ┌────────────▼───────────────┐
   │      close callbacks       │  ← socket.on('close', ...) etc.
   └────────────┬───────────────┘
                │
                └──────────────► (back to top)

Between EVERY phase transition:
   → process.nextTick() queue is drained (entire queue)
   → Microtask queue (Promise .then callbacks) is drained (entire queue)
   → These run before moving to the next phase
```

The **poll phase** is where I/O-bound work happens: Node.js blocks here, waiting for I/O events from the OS. This blocking is intentional — the thread has nothing to do until I/O is ready. The moment an I/O event arrives (file read complete, TCP data received, DB response), the poll phase wakes up and runs the associated callback.

CPU-bound JavaScript runs *within* a phase callback and blocks the entire loop from advancing to the next phase until it returns.

**Q4. What is libuv and what role does its thread pool play?**
A: libuv is the C library that powers Node.js's event loop and asynchronous I/O. It provides a cross-platform abstraction over OS-level async primitives (epoll on Linux, kqueue on macOS, IOCP on Windows).

libuv handles two categories of "async" very differently:

**Network I/O** — TCP, UDP, pipes:
- Uses the OS's native async event notification (epoll/kqueue/IOCP)
- Zero threads required — the OS kernel handles the waiting
- Truly non-blocking at the OS level

**File system I/O, DNS, and some crypto** — `fs.readFile`, `dns.lookup`, `crypto.pbkdf2`:
- These APIs do NOT have async equivalents on all OS platforms
- libuv runs them on a **thread pool** (default: 4 threads, configurable via `UV_THREADPOOL_SIZE`)
- The main JS thread delegates the work to a pool thread and gets a callback when done

```
                          ┌─────────────────────────────────┐
JavaScript (main thread)  │  event loop + your JS code      │
                          └──────┬────────────────┬──────────┘
                                 │                │
                    ┌────────────▼──┐    ┌────────▼──────────────┐
                    │  OS Kernel    │    │  libuv Thread Pool    │
                    │  (epoll etc.) │    │  (4 threads default)  │
                    │               │    │                       │
                    │  TCP/UDP      │    │  fs.readFile          │
                    │  (truly async │    │  dns.lookup           │
                    │   — no thread │    │  crypto.pbkdf2        │
                    │   needed)     │    │  zlib                 │
                    └───────────────┘    └───────────────────────┘
```

The thread pool is the source of a common misconception: developers assume `fs.readFile` is "non-blocking" in the same way a network request is. It's non-blocking for *JavaScript*, but a real OS thread is busy doing the file I/O behind the scenes. This matters when the thread pool is exhausted:

```js
// If all 4 libuv threads are busy with fs operations:
fs.readFile('a.txt', cb); // → thread pool thread 1
fs.readFile('b.txt', cb); // → thread pool thread 2
fs.readFile('c.txt', cb); // → thread pool thread 3
fs.readFile('d.txt', cb); // → thread pool thread 4
fs.readFile('e.txt', cb); // → QUEUED — waits for a free thread
// e.txt doesn't start reading until one of the above finishes
// This is thread pool starvation — looks like slow I/O but is a concurrency limit
```

### Section 2: I/O-Bound Workloads

**Q5. How does Node.js achieve concurrency for I/O-bound work without multiple threads?**
A: Through non-blocking I/O and the event loop's callback mechanism. When you initiate an I/O operation, Node.js registers a callback and immediately returns control to the event loop. The actual waiting happens in the OS or libuv thread pool — not on the main JS thread. When the I/O completes, the OS signals libuv, which queues the callback in the poll phase.

```js
// This code handles 3 database queries "concurrently" on one thread:
async function getStats() {
  // All three queries are IN FLIGHT simultaneously:
  const [users, orders, products] = await Promise.all([
    db.query('SELECT COUNT(*) FROM users'),    // kicked off → event loop free
    db.query('SELECT COUNT(*) FROM orders'),   // kicked off → event loop free
    db.query('SELECT COUNT(*) FROM products'), // kicked off → event loop free
  ]);
  // Event loop handled other requests while all three were waiting
  // Total time ≈ slowest single query (parallel), not sum of all (sequential)
  return { users, orders, products };
}

// vs sequential (bad for I/O-bound):
async function getStatsSequential() {
  const users    = await db.query('SELECT COUNT(*) FROM users');    // wait...
  const orders   = await db.query('SELECT COUNT(*) FROM orders');   // then wait...
  const products = await db.query('SELECT COUNT(*) FROM products'); // then wait...
  // Total time = sum of all three query times
  // Event loop was available between awaits but this function didn't use it
}
```

The key insight: `await` does not block the event loop. It suspends *this async function* and returns control to the event loop, which can run other callbacks, handle other requests, fire timers — until the awaited Promise resolves and this function resumes.

**Q6. What is backpressure and why does it matter for I/O-bound streaming?**
A: Backpressure occurs when a readable source produces data faster than a writable destination can consume it. Without backpressure handling, the unconsumed data accumulates in memory buffers — eventually causing memory exhaustion or process crash.

```js
// ❌ No backpressure — can OOM for large files:
const readable = fs.createReadStream('huge-file.csv');   // reads as fast as possible
const writable = fs.createWriteStream('output.csv');     // writes as fast as possible
                                                          // but network is slower

readable.on('data', chunk => {
  writable.write(chunk); // writable.write() returns false when buffer is full
  // but we never CHECK the return value — keep pumping data into memory
});

// ✓ With backpressure — pause source when destination is overwhelmed:
readable.on('data', chunk => {
  const ok = writable.write(chunk);
  if (!ok) {
    readable.pause(); // stop reading until writable drains
  }
});
writable.on('drain', () => {
  readable.resume(); // writable buffer cleared — resume reading
});

// ✓ Best: use pipe() — handles backpressure automatically:
readable.pipe(writable);

// ✓ Best (modern): use pipeline() — pipe() + proper error handling + cleanup:
const { pipeline } = require('stream/promises');

await pipeline(
  fs.createReadStream('huge-file.csv'),
  transformStream,
  fs.createWriteStream('output.csv')
); // automatically pauses/resumes; cleans up all streams on error
```

Backpressure is specifically an I/O-bound concern — it only matters when you're piping between two I/O sources with different speeds (disk read → network write, database cursor → HTTP response, S3 download → processing pipeline).

**Q7. What is the difference between `fs.readFile` and `fs.createReadStream`, and when do you use each?**
A: Both are non-blocking from JavaScript's perspective, but they differ in how data is buffered:

`fs.readFile` — reads the entire file into memory as a Buffer before calling the callback. Simple API, one callback, but unsuitable for large files because the entire file must fit in RAM.

`fs.createReadStream` — reads the file in chunks (default 64KB) and emits them via the `data` event. Memory usage is bounded by chunk size regardless of file size. Composable with pipe/pipeline for streaming transformations.

```js
// fs.readFile — entire file in memory before you can use any of it:
fs.readFile('10gb-log.txt', 'utf8', (err, data) => {
  // ← data is a 10GB string in memory
  // If you have 5 concurrent requests doing this → 50GB RAM used
  process(data);
});

// fs.createReadStream — bounded memory, process as chunks arrive:
const stream = fs.createReadStream('10gb-log.txt', { encoding: 'utf8' });
stream.on('data', chunk => {
  // ← chunk is ~64KB, processed and discarded before next chunk
  processChunk(chunk);
});
stream.on('end', () => console.log('done'));

// Decision rule:
// File < a few MB AND you need the whole content at once → readFile
// File > ~10MB OR you're piping to another I/O destination → createReadStream
// File > available RAM → createReadStream (no choice)
```

**Q8. What is connection pooling and why is it critical for I/O-bound Node.js services?**
A: Every database connection is a network socket — establishing one requires a TCP handshake, authentication round-trips, and server-side resource allocation. Doing this for every query adds 5–50ms of overhead and puts pressure on the database's connection limit.

Connection pooling maintains a set of pre-established, reusable connections. Queries borrow a connection from the pool, use it, and return it — amortizing the setup cost across many queries.

```js
// ❌ New connection per query (devastating at scale):
async function getUser(id) {
  const conn = await mysql.createConnection(config); // TCP handshake + auth
  const [rows] = await conn.query('SELECT * FROM users WHERE id = ?', [id]);
  await conn.end(); // teardown
  return rows[0];
  // 1000 req/s → 1000 connections/s → database falls over
}

// ✓ Connection pool (correct):
const pool = mysql.createPool({
  ...config,
  connectionLimit: 10,  // max 10 simultaneous DB connections
  waitForConnections: true,
  queueLimit: 0,        // queue requests when all connections are in use
});

async function getUser(id) {
  const [rows] = await pool.query('SELECT * FROM users WHERE id = ?', [id]);
  // pool automatically: borrows connection → runs query → returns connection
  return rows[0];
  // 1000 req/s → max 10 DB connections → queries queue → DB is happy
}

// Pool sizing: connectionLimit should match DB server's max concurrent query capacity
// Rule of thumb: (number of CPU cores on DB server) * 2 + effective_spindle_count
// For Postgres specifically: don't exceed max_connections setting
```

### Section 3: CPU-Bound Workloads

**Q9. Why does a CPU-bound task block the Node.js event loop, and what are the visible symptoms?**
A: JavaScript in Node.js runs on a single thread — the same thread that runs the event loop, executes I/O callbacks, fires timers, and processes incoming HTTP requests. When your JavaScript code is computing — a tight loop, a complex algorithm, a large array sort — that thread is 100% occupied. The event loop cannot advance to its next phase until the current synchronous execution completes (the "run to completion" rule).

Visible symptoms:
```
1. HTTP request latency spikes:
   Normal: p99 latency = 20ms
   During CPU spike: p99 latency = 520ms (20ms normal + 500ms blocked)

2. Timers fire late:
   setTimeout(() => console.log('tick'), 100);
   // Fires at 600ms if event loop was blocked for 500ms

3. Health check timeouts:
   Load balancer pings /health every 5s
   During 10s CPU-bound task: /health doesn't respond → LB marks node as unhealthy

4. WebSocket disconnects:
   Keep-alive pings can't be sent while event loop is blocked
   Clients time out and disconnect

// Measuring event loop lag:
let lastCheck = Date.now();
setInterval(() => {
  const now = Date.now();
  const lag = now - lastCheck - 1000; // expected 1000ms, actual difference
  if (lag > 100) console.warn(`Event loop lag: ${lag}ms`);
  lastCheck = now;
}, 1000);

// Or with the perf_hooks API:
const { monitorEventLoopDelay } = require('perf_hooks');
const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();
setInterval(() => {
  console.log(`mean lag: ${histogram.mean / 1e6}ms`); // nanoseconds → ms
}, 5000);
```

**Q10. What are Worker Threads in Node.js and when should you use them?**
A: Worker Threads (`worker_threads` module, stable since Node.js 12) allow running JavaScript in parallel threads — each with its own V8 instance, event loop, and memory heap. Workers communicate with the main thread via message passing, and can share memory via `SharedArrayBuffer`.

Workers are the correct solution for CPU-bound work that is too large to chunk and yield:

```js
// main.js
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

if (isMainThread) {
  // Main thread: dispatch work to a worker
  function runCPUIntensiveTask(data) {
    return new Promise((resolve, reject) => {
      const worker = new Worker(__filename, { workerData: data });
      worker.on('message', resolve);
      worker.on('error', reject);
      worker.on('exit', code => {
        if (code !== 0) reject(new Error(`Worker exited with code ${code}`));
      });
    });
  }

  // Main thread stays free while worker computes:
  const app = express();
  app.get('/compute', async (req, res) => {
    const result = await runCPUIntensiveTask(req.body);
    // Event loop was free to handle other /compute requests while worker ran
    res.json(result);
  });

} else {
  // Worker thread: do the CPU-intensive work
  const result = heavyComputation(workerData);
  parentPort.postMessage(result);
}

function heavyComputation(data) {
  // Safe to block here — this is NOT the main thread / event loop
  let sum = 0;
  for (let i = 0; i < 1e9; i++) sum += i;
  return sum;
}
```

**When to use Workers vs other solutions:**

| Scenario | Solution |
|---|---|
| CPU task < ~1ms | Run synchronously on main thread — overhead of worker isn't worth it |
| CPU task 1ms–100ms | Break into chunks, yield with `setImmediate` |
| CPU task > 100ms, one-off | Spawn a Worker |
| CPU task > 100ms, frequent | Maintain a Worker Pool (reuse workers) |
| CPU task = child process isolation needed | `child_process.fork()` |
| Scale across all CPU cores | `cluster` module + workers inside each process |

**Q11. What is a Worker Pool and why is spawning a new Worker per request a mistake?**
A: Spawning a Worker Thread has non-trivial overhead: V8 initialization, heap allocation, thread creation — typically 30–100ms. Doing this per HTTP request means:

- First response is always slow (worker startup cost)
- Under load: dozens of threads spinning up simultaneously
- Memory spike: each Worker has its own heap (default 1.5GB limit)

A Worker Pool pre-creates a fixed number of workers and reuses them across requests:

```js
// worker-pool.js — simplified worker pool implementation
const { Worker } = require('worker_threads');
const os = require('os');

class WorkerPool {
  constructor(workerScript, size = os.cpus().length) {
    this.workerScript = workerScript;
    this.size = size;
    this.workers = [];
    this.queue = [];       // pending tasks waiting for a free worker
    this.freeWorkers = []; // available workers

    // Pre-create all workers:
    for (let i = 0; i < size; i++) {
      this._addWorker();
    }
  }

  _addWorker() {
    const worker = new Worker(this.workerScript);

    worker.on('message', (result) => {
      // Task complete — resolve the waiting promise and free the worker
      const { resolve } = worker._currentTask;
      worker._currentTask = null;
      this.freeWorkers.push(worker);
      resolve(result);
      this._drain(); // pick up next queued task if any
    });

    worker.on('error', (err) => {
      const { reject } = worker._currentTask;
      worker._currentTask = null;
      // Replace crashed worker:
      this.workers = this.workers.filter(w => w !== worker);
      this._addWorker();
      reject(err);
    });

    this.workers.push(worker);
    this.freeWorkers.push(worker);
  }

  _drain() {
    if (this.queue.length > 0 && this.freeWorkers.length > 0) {
      const { task, resolve, reject } = this.queue.shift();
      const worker = this.freeWorkers.pop();
      worker._currentTask = { resolve, reject };
      worker.postMessage(task);
    }
  }

  run(task) {
    return new Promise((resolve, reject) => {
      if (this.freeWorkers.length > 0) {
        const worker = this.freeWorkers.pop();
        worker._currentTask = { resolve, reject };
        worker.postMessage(task);
      } else {
        // All workers busy — queue the task
        this.queue.push({ task, resolve, reject });
      }
    });
  }

  destroy() {
    this.workers.forEach(w => w.terminate());
  }
}

// Usage:
const pool = new WorkerPool('./compute-worker.js', os.cpus().length);

app.post('/process-image', async (req, res) => {
  const result = await pool.run({ imageBuffer: req.body });
  res.send(result);
  // Worker was already warm — no startup cost
  // Max concurrency = number of CPU cores
});
```

**Q12. What is the difference between `child_process.fork()`, `child_process.spawn()`, and `worker_threads`?**
A: Three different tools for offloading work from the main Node.js process, with different isolation levels and communication models:

| | `worker_threads` | `child_process.fork()` | `child_process.spawn()` |
|---|---|---|---|
| **Process** | Same process | New process | New process |
| **Memory** | Separate heaps, optional SharedArrayBuffer | Fully separate | Fully separate |
| **Communication** | `postMessage` (structured clone / transferable) | IPC channel (`process.send`) | stdin/stdout streams |
| **Startup cost** | ~30–100ms (V8 init) | ~30–100ms (new process) | Minimal (exec new binary) |
| **Crash isolation** | Worker crash can affect main process (uncaught) | Crash is fully isolated | Crash is fully isolated |
| **Use case** | CPU-bound JS work | CPU-bound JS work, isolated | Run non-JS executables |

```js
// worker_threads — best for CPU-bound JS, shared memory possible:
const { Worker } = require('worker_threads');
const w = new Worker('./hash-worker.js', { workerData: buffer });
// Can share memory: new Worker('./worker.js', { workerData: { buf: sharedBuffer } })

// child_process.fork() — separate process, crashes are isolated, Node.js only:
const { fork } = require('child_process');
const child = fork('./hash-worker.js');
child.send({ buffer }); // IPC serializes via JSON → slower than structured clone
child.on('message', result => res.json(result));
// Use when: you need full crash isolation (untrusted input, unstable native addon)

// child_process.spawn() — run ANY executable:
const { spawn } = require('child_process');
const ffmpeg = spawn('ffmpeg', ['-i', 'input.mp4', '-codec:v', 'libx264', 'output.mp4']);
ffmpeg.stdout.on('data', data => console.log(data.toString()));
ffmpeg.on('close', code => console.log(`ffmpeg exited: ${code}`));
// Use when: calling Python scripts, ffmpeg, imagemagick, or any binary
```

**Q13. When is it appropriate to split CPU work into chunks and yield to the event loop?**
A: For CPU tasks that are naturally iterative (processing array items, walking a tree, reading chunks of a large buffer), you can break the work across multiple event loop ticks using `setImmediate`. This keeps the event loop responsive between chunks.

This is the right approach when:
- Work is naturally decomposable into independent iterations
- Each chunk completes fast (< 1–5ms)
- You don't want Worker Thread overhead for moderately sized work
- You need the work to run in the main thread's context (access to app state)

```js
// ❌ Blocks the event loop for the entire array:
function processAllItems(items) {
  const results = [];
  for (const item of items) {
    results.push(heavyTransform(item)); // each heavyTransform = 0.1ms
    // 10,000 items × 0.1ms = 1000ms of blocking!
  }
  return results;
}

// ✓ Chunked processing — yields to event loop between batches:
function processInChunks(items, chunkSize = 100) {
  return new Promise((resolve) => {
    const results = [];
    let index = 0;

    function processNextChunk() {
      const end = Math.min(index + chunkSize, items.length);

      // Process one chunk synchronously:
      while (index < end) {
        results.push(heavyTransform(items[index]));
        index++;
      }

      if (index < items.length) {
        // Yield to event loop: allow I/O callbacks, timers, HTTP requests to run
        setImmediate(processNextChunk);
        // setImmediate fires in the "check" phase — after I/O events
        // setTimeout(processNextChunk, 0) also works but has ~1ms minimum delay
      } else {
        resolve(results);
      }
    }

    processNextChunk();
  });
}

// Usage — event loop stays responsive during processing:
app.post('/process', async (req, res) => {
  const results = await processInChunks(req.body.items);
  // Other requests were handled between each 100-item chunk
  res.json(results);
});
```

The tradeoff: chunking makes the total processing time *longer* (setImmediate overhead per chunk), but keeps latency for *other requests* acceptable. For very large workloads (millions of items), a Worker Thread is better.

### Section 4: Identification and Architecture

**Q14. How do you identify whether a production bottleneck is I/O-bound or CPU-bound?**
A: The signals are different and diagnostics tools approach them differently:

**I/O-bound signals:**
- CPU usage is low (20–40%) but latency is high
- Database slow query logs show long-running queries
- `strace` / `dtruss` shows many `read`, `write`, `epoll_wait` syscalls with long waits
- Network interface shows high traffic
- Thread pool queue depth is high (libuv metric)

**CPU-bound signals:**
- CPU usage is high (80–100%) on one core
- Other cores are idle (single-threaded bottleneck)
- Event loop lag metrics spike (mean/p99 lag > 50ms)
- Latency histogram shows bimodal distribution (fast requests vs very slow requests)
- Profiler shows a specific JS function consuming >50% CPU time

```js
// Diagnostic 1: Event loop lag (CPU-bound indicator)
const { monitorEventLoopDelay } = require('perf_hooks');
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
setInterval(() => {
  console.log({
    min:  (h.min  / 1e6).toFixed(2) + 'ms',
    mean: (h.mean / 1e6).toFixed(2) + 'ms',
    p99:  (h.percentile(99) / 1e6).toFixed(2) + 'ms',
    max:  (h.max  / 1e6).toFixed(2) + 'ms',
  });
  h.reset();
}, 10_000);
// p99 lag > 50ms: something is blocking the event loop periodically

// Diagnostic 2: CPU profiling to find the hot function
// node --prof server.js        ← collect V8 profiler data
// node --prof-process isolate-*.log ← process the profile
// Or: clinic.js flame (https://clinicjs.org/flame/)

// Diagnostic 3: libuv thread pool monitoring
// UV_THREADPOOL_SIZE defaults to 4
// If fs/dns/crypto is slow: check if thread pool is saturated
// process.env.UV_THREADPOOL_SIZE = '16'; // set before requiring anything
```

**Q15. How does the `cluster` module help CPU-bound workloads, and what are its limits?**
A: The `cluster` module allows spawning multiple Node.js processes, each with its own event loop, listening on the same port. The OS or Node.js master process distributes incoming connections across worker processes.

```js
// cluster.js
const cluster = require('cluster');
const http    = require('http');
const os      = require('os');
const numCPUs = os.cpus().length;

if (cluster.isPrimary) {
  console.log(`Primary ${process.pid}: forking ${numCPUs} workers`);

  for (let i = 0; i < numCPUs; i++) {
    cluster.fork(); // spawn one worker per CPU core
  }

  cluster.on('exit', (worker, code) => {
    console.log(`Worker ${worker.process.pid} died — restarting`);
    cluster.fork(); // automatic restart on crash
  });

} else {
  // Each worker is a full Node.js process with its own event loop:
  http.createServer((req, res) => {
    // CPU-bound work here blocks this worker's event loop,
    // but the other N-1 workers are still serving requests
    const result = heavyComputation(req.url);
    res.end(result);
  }).listen(3000);

  console.log(`Worker ${process.pid} started`);
}
```

What cluster helps and doesn't help:

```
cluster DOES help:
  ✓ Utilizes all CPU cores (Node.js is single-threaded — without cluster, N-1 cores idle)
  ✓ One worker's CPU spike doesn't affect other workers' responsiveness
  ✓ Process-level crash isolation
  ✓ Zero-downtime restarts (restart workers one by one)

cluster does NOT help:
  ✗ A single request's computation still blocks that worker's event loop
  ✗ State is NOT shared between workers (each has separate memory)
  ✗ WebSocket session affinity is complex (a client might connect to a different worker)
  ✗ Heavier than worker_threads (full OS processes vs threads)

When to use:
  cluster: HTTP servers where each request is independently handled, stateless
  worker_threads: CPU-bound tasks within a single request that must not block the event loop
  Both together: cluster of processes, each using a worker pool for heavy per-request compute
```

### Fix 2 — Algorithmic optimization (reduces blocking even without workers)

```js
// Pre-compute the expensive global baseline scan at startup (or on a schedule):
let segmentAverages = new Map(); // segment → pre-computed adjustment

function precomputeSegmentAverages() {
  const sums   = new Map();
  const counts = new Map();
  for (const [, baseline] of globalUserBaselines) {
    sums.set(baseline.segment,   (sums.get(baseline.segment)   ?? 0) + baseline.avg);
    counts.set(baseline.segment, (counts.get(baseline.segment) ?? 0) + 1);
  }
  for (const [seg, sum] of sums) {
    segmentAverages.set(seg, sum / counts.get(seg));
  }
}

setInterval(precomputeSegmentAverages, 60_000); // refresh every minute

### Problem
A dashboard API endpoint fetches data from five microservices and aggregates it. The endpoint currently takes 1.2 seconds. Optimize it.

### Analysis of Sequential Awaits

```
Sequential execution timeline:

0ms    → fetchProfile starts
150ms  → fetchProfile returns → fetchOrders starts
450ms  → fetchOrders returns → fetchPreferences starts
550ms  → fetchPreferences returns → fetchAnalytics starts
950ms  → fetchAnalytics returns → fetchInventory starts
1200ms → fetchInventory returns → respond

Each await PAUSES this function (but NOT the event loop) until

Actual network time is 1200ms.

### Fix 1 — Full Parallelism with `Promise.all`

    fetchProfile(userId),       // ←┐
    fetchOrders(userId),        // ←┤ all kicked off synchronously
    fetchPreferences(userId),   // ←┤ before the first await
    fetchAnalytics(userId),     // ←┤
    fetchInventory(),            // ←┘
  ]);

  res.json({ profile, orders, preferences, analytics, inventory });
});
// Total: max(150, 300, 100, 400, 250) = 400ms — the slowest single call
// 3× faster, same amount of work

0ms   → all 5 requests start simultaneously
        [======= profile 150ms =======]
        [=============== orders 300ms ===============]

## Problem 3 — Streaming a Large I/O-Bound Report

### Problem
An admin endpoint queries 500,000 database rows and returns them as a CSV download. The current implementation runs out of memory under concurrent load. Fix it using streams.

```js
// ❌ Current implementation — loads everything into memory:

  const users = await db.query('SELECT * FROM users LIMIT 500000');
  // ↑ 500,000 rows × ~200 bytes each ≈ 100MB in RAM — per request!

  const csv = users.map(u =>
    `${u.id},${u.name},${u.email},${u.createdAt}`
  ).join('\n');
  // ↑ Another 100MB string

  res.set('Content-Type', 'text/csv');
  res.send(csv);
  // With 5 concurrent downloads: 5 × 200MB = 1GB RAM → OOM crash
});
```

### Root Cause

```
Memory usage per request, current approach:
  db.query() → 100MB array of row objects
  .map().join() → 100MB string
  res.send() → 100MB HTTP buffer
  Total: ~300MB per concurrent request

At 5 concurrent downloads: ~1.5GB → Out of Memory

Also: event loop is stressed during the map/join on 500,000 items
  500,000 iterations × 0.001ms = 500ms of CPU work on the main thread
```

### Fix — Database Cursor + Transform Stream + HTTP Response Stream

```js
// ✓ Streaming: O(1) memory regardless of result size
const { Transform, pipeline: pipelineCallback } = require('stream');
const { promisify } = require('util');
const pipeline = promisify(pipelineCallback);

app.get('/export/users', async (req, res) => {
  res.set({
    'Content-Type':        'text/csv',
    'Content-Disposition': 'attachment; filename="users.csv"',
    'Transfer-Encoding':   'chunked', // stream without knowing total length
  });

  // Write CSV header immediately:
  res.write('id,name,email,createdAt\n');

  // Database cursor — fetches rows in batches (not all at once):
  const cursor = db.queryStream('SELECT id, name, email, created_at FROM users');
  // cursor is a Readable stream — emits one row object at a time (or in small batches)

  // Transform stream — converts row objects to CSV lines:
  const rowToCSV = new Transform({
    objectMode: true,           // accepts objects (rows), outputs strings
    transform(row, encoding, callback) {
      const line = `${row.id},${escapeCSV(row.name)},${escapeCSV(row.email)},${row.created_at}\n`;
      callback(null, line);     // push the CSV line downstream
    }
  });

  try {
    await pipeline(
      cursor,      // Readable: DB rows arrive in chunks (backpressure handled)
      rowToCSV,    // Transform: row objects → CSV strings
      res          // Writable: HTTP response (backpressure: slow client → pauses DB read)
    );
    // pipeline: automatically handles backpressure + cleanup on error
  } catch (err) {
    // pipeline destroys all streams on error — res may be partially written
    if (!res.headersSent) res.status(500).json({ error: 'Export failed' });
    else res.destroy(); // can't send error — connection was already streaming
    logger.error('CSV export failed', err);
  }
});

function escapeCSV(value) {
  if (typeof value !== 'string') return value ?? '';
  if (value.includes(',') || value.includes('"') || value.includes('\n')) {
    return `"${value.replace(/"/g, '""')}"`;
  }
  return value;
}
```

### How Backpressure Protects Memory

```
Without backpressure (current ❌):
  DB server:  sends all 500,000 rows as fast as possible
  Node.js:    buffers them all in memory → 100MB+ RAM used
  HTTP client: consumes at network speed (possibly slow)

With pipeline backpressure (fixed ✓):
  DB cursor:   sends chunk (e.g. 1,000 rows)
  rowToCSV:    transforms → ~200KB CSV text
  res (HTTP):  writes to TCP send buffer
  TCP:         if client is slow, TCP window fills up
               → res.write() returns false (backpressure signal)
               → pipeline pauses rowToCSV
               → cursor stops fetching from DB
  Memory used: ~200KB (one chunk) at any moment — regardless of total rows
```

### Batch Size Tuning

// Too small: many round-trips to DB (high latency)
// Too large: more memory pressure, slower first byte
// Sweet spot: 500–2,000 rows per batch for most use cases

```js
// image-worker-pool.js — manages a fixed set of persistent workers:
const { Worker } = require('worker_threads');
const os   = require('os');
const path = require('path');

class ImageWorkerPool {
  constructor(size = Math.max(2, os.cpus().length - 1)) {
    // Leave 1 core for the main event loop and I/O:
    this.workers  = [];
    this.pending  = new Map(); // taskId → { resolve, reject }
    this.queue    = [];        // tasks waiting for a free worker
    this.taskId   = 0;

    for (let i = 0; i < size; i++) {
      this._spawnWorker();
    }
  }

  _spawnWorker() {
    const worker = new Worker(path.join(__dirname, 'thumbnail-worker.js'));

    worker.busy = false;

    worker.on('message', ({ taskId, success, outputPath, error }) => {
      worker.busy = false;
      const { resolve, reject } = this.pending.get(taskId);
      this.pending.delete(taskId);

      if (success) resolve(outputPath);
      else reject(new Error(error));

      // Pick up next queued task:
      if (this.queue.length > 0) {
        const next = this.queue.shift();
        this._dispatch(worker, next);
      }
    });

    worker.on('error', (err) => {
      worker.busy = false;
      // Crash: fail the current task, replace the worker:
      for (const [taskId, { reject }] of this.pending) {
        reject(err);
        this.pending.delete(taskId);
      }
      this.workers = this.workers.filter(w => w !== worker);
      this._spawnWorker(); // auto-heal
    });

    this.workers.push(worker);
  }

  _dispatch(worker, task) {
    worker.busy = true;
    this.pending.set(task.taskId, { resolve: task.resolve, reject: task.reject });
    worker.postMessage(task);
  }

  process(inputPath, outputPath, width = 200, height = 200) {
    return new Promise((resolve, reject) => {
      const taskId = ++this.taskId;
      const task   = { taskId, inputPath, outputPath, width, height, resolve, reject };

      const freeWorker = this.workers.find(w => !w.busy);
      if (freeWorker) {
        this._dispatch(freeWorker, task);
      } else {
        this.queue.push(task); // all workers busy — queue it
      }
    });
  }
}

// Singleton pool — created once at app startup:
const imagePool = new ImageWorkerPool();
module.exports = imagePool;
```

### Performance Characteristics

```
Without worker pool (main thread):
  10 concurrent uploads × 300ms per thumbnail = event loop blocked 3 seconds
  All other requests stall for those 3 seconds

With worker pool (os.cpus().length - 1 workers, e.g. 7 on 8-core machine):

    Main thread event loop: completely free the entire time
    Other API routes: unaffected

    Without pool: sequential on main thread = 10 × 300ms = 3000ms
    With pool (7 workers): 2 rounds = ~600ms total
    Plus: no other requests were delayed

Pool sizing rule:
  Number of image workers = CPUs - 1
  Leaves 1 core for: event loop + libuv thread pool + OS overhead
  If CPUs = 1: still use 1 worker — off main thread is the goal, not parallelism
```

## Problem 5 — Identifying and Fixing libuv Thread Pool Starvation

### Problem
A Node.js service makes database queries AND reads configuration files. The DB queries are fast (10ms) but occasionally spike to 800ms with no change in DB load. The bug is subtle. Diagnose and fix it.

```js
// Feature: hot-reload config files every 30 seconds:
setInterval(async () => {
  const configs = await Promise.all([
    fs.promises.readFile('./config/database.json',    'utf8'),
    fs.promises.readFile('./config/features.json',    'utf8'),
    fs.promises.readFile('./config/rate-limits.json', 'utf8'),
    fs.promises.readFile('./config/cache.json',       'utf8'),
    // ... 10 more config files total
  ]);
  updateConfig(configs.map(JSON.parse));
}, 30_000);

// Database: uses pg library — crypto for connection hashing:
const pool = new pg.Pool({ max: 10 });

// Also: incoming requests trigger password hashing:
app.post('/register', async (req, res) => {
  const hash = await bcrypt.hash(req.body.password, 12); // uses crypto
  await pool.query('INSERT INTO users (hash) VALUES ($1)', [hash]);
  res.json({ success: true });
});
```

### Root Cause: Thread Pool Starvation

```
libuv thread pool has 4 threads (default).

At the moment the config reload fires (every 30s):
  Thread 1 → fs.readFile('database.json')
  Thread 2 → fs.readFile('features.json')
  Thread 3 → fs.readFile('rate-limits.json')
  Thread 4 → fs.readFile('cache.json')
  ← ALL 4 THREADS OCCUPIED

Simultaneously, incoming requests call:
  bcrypt.hash(password, 12) → needs a thread pool thread → QUEUED
  pg's internal crypto ops  → needs a thread pool thread → QUEUED
  fs.readFile('config5.json')  → QUEUED (6 more config files waiting!)

bcrypt.hash queued at T=0ms
Config reads take 50ms × 10 files / 4 threads = ~125ms total
bcrypt.hash finally gets a thread at T=125ms → runs for 80ms (12 rounds)
Total bcrypt time: 125ms queue wait + 80ms compute = 205ms
  (normally: 0ms wait + 80ms compute = 80ms)

Pg also queues → DB queries that need crypto "seem slow" → latency spike
DB server is not slow at all — it's waiting for Node's thread pool!
```

### Fix 1 — Increase Thread Pool Size

```js
// Set BEFORE any require() calls — must be in the very first lines:
process.env.UV_THREADPOOL_SIZE = '16'; // 4 → 16 threads

// Or set as environment variable before starting Node:
// UV_THREADPOOL_SIZE=16 node server.js

// Rule of thumb for sizing:
// UV_THREADPOOL_SIZE = max simultaneous file I/O + crypto operations expected
// For this service: 10 config files + bcrypt + pg crypto = 12+ → set to 16
```

### Fix 2 — Stagger Config Reloads (avoid burst I/O)

```js
// ❌ All 10 files at once → 10 thread pool requests simultaneously:
setInterval(async () => {
  const configs = await Promise.all(configFiles.map(f => fs.promises.readFile(f)));
  // Burst of 10 reads → thread pool saturated → everything else queues
}, 30_000);

// ✓ Read files sequentially — use one thread at a time:
setInterval(async () => {
  const configs = [];
  for (const file of configFiles) {
    configs.push(await fs.promises.readFile(file, 'utf8')); // one at a time
  }
  updateConfig(configs.map(JSON.parse));
  // Thread pool never has more than 1 file read in-flight at once
}, 30_000);
```

### Fix 3 — Use `fs.readFileSync` at Startup, Watcher for Updates

```js
// Config files are small and rarely change — sync read at startup is fine:
const config = {
  database:   JSON.parse(fs.readFileSync('./config/database.json',    'utf8')),
  features:   JSON.parse(fs.readFileSync('./config/features.json',    'utf8')),
  rateLimits: JSON.parse(fs.readFileSync('./config/rate-limits.json', 'utf8')),
};
// Sync at startup: blocks event loop ONCE before serving any requests — acceptable

// For hot reloading, use fs.watch (event-driven — no polling, no thread pool):
for (const [key, filePath] of Object.entries(configPaths)) {
  fs.watch(filePath, (eventType) => {
    if (eventType === 'change') {
      // Re-read only the changed file — one thread pool slot used on change:
      fs.readFile(filePath, 'utf8', (err, data) => {
        if (!err) config[key] = JSON.parse(data);
      });
    }
  });
}
// fs.watch uses OS inotify/FSEvents — zero thread pool usage during idle
```

### Fix 4 — Move bcrypt to Worker Thread (keep thread pool for I/O only)

```js
// bcrypt is CPU-bound crypto — it shouldn't compete with I/O for thread pool slots:
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

// bcrypt-worker.js:
if (!isMainThread) {
  const bcrypt = require('bcrypt');
  bcrypt.hash(workerData.password, workerData.rounds)
    .then(hash => parentPort.postMessage(hash));
}

// main thread:
function hashPassword(password, rounds = 12) {
  return new Promise((resolve, reject) => {
    const worker = new Worker(__filename, {
      workerData: { password, rounds }
    });
    worker.on('message', resolve);
    worker.on('error', reject);
  });
}

app.post('/register', async (req, res) => {
  // bcrypt runs in a Worker Thread — doesn't use libuv thread pool at all
  const hash = await hashPassword(req.body.password, 12);
  await pool.query('INSERT INTO users (hash) VALUES ($1)', [hash]);
  res.json({ success: true });
});
// Now: file I/O and pg crypto use thread pool
//      bcrypt uses Worker Thread (separate from thread pool)
//      No contention between the two
```

## Quick Reference — I/O vs CPU Cheat Sheet

```
IDENTIFY THE BOTTLENECK:
  I/O-bound:  CPU low, latency high, DB/network slow queries, strace shows epoll_wait
  CPU-bound:  CPU pegged (one core 100%), event loop lag spikes, profiler shows hot JS fn

EVENT LOOP RULES:
  await does NOT block the event loop — it suspends the async fn, loop runs freely
  Synchronous JS DOES block — loops, array methods, crypto, JSON.parse of huge payloads
  process.nextTick > microtasks (Promise.then) > setImmediate > setTimeout(fn, 0)

I/O-BOUND BEST PRACTICES:
  Parallel:    Promise.all for independent I/O (not sequential await)
  Fault tolerance: Promise.allSettled for partial success (one service fails → degrade)
  Timeouts:    Promise.race(fetch, timeout) — don't let one service delay all
  Streams:     fs.createReadStream + pipeline for large files (O(1) memory)
  Backpressure: always use pipeline() not pipe() — handles cleanup + errors
  Pooling:     db/http connection pools — amortize connection setup cost
  Thread pool: UV_THREADPOOL_SIZE=16 if fs + crypto + dns compete; default is 4

CPU-BOUND SOLUTIONS:
  Small (<1ms):     run on main thread — overhead of offloading not worth it
  Medium (1–100ms): setImmediate chunking — break into iterations, yield between chunks
  Large (>100ms):   Worker Threads — parallel JS execution, own heap, message passing
  Persistent:       Worker Pool — pre-spawn workers, reuse across requests (no startup cost)
  Per-core scaling: cluster module — one process per CPU, OS distributes connections
  Non-JS work:      child_process.spawn — run Python/ffmpeg/binary as a child process

WORKER THREAD vs CHILD PROCESS:
  worker_threads: same process, shared SharedArrayBuffer possible, ~30ms startup
  child_process.fork: new process, fully isolated, crash-safe, ~30ms startup, JSON IPC
  child_process.spawn: run any binary, streams for communication, no Node.js required

COMMON BUGS:
  Sequential awaits for independent I/O  → use Promise.all
  No backpressure on streams             → use pipeline(), check write() return value
  Thread pool starvation (UV_THREADPOOL_SIZE=4) → increase or stagger file I/O
  CPU work on main thread                → Worker Thread or setImmediate chunking
  New Worker per request                 → use a Worker Pool (pre-warm workers)
  delete on hot objects (V8)             → separate topic but often co-occurs
  Blocking at startup (readFileSync)     → acceptable once; not in request handlers
```

---

**Final Tip:** At the 5 YOE level, I/O vs CPU questions test whether you can reason about *where work actually happens* — not just whether code is async. The highest-signal answer on I/O parallelism: "Sequential `await` doesn't block the event loop — it's just inefficient. The fix is `Promise.all`, which kicks off all I/O simultaneously before the first `await`. The event loop is free either way — we're just eliminating artificial serialization." For CPU-bound work: "The event loop blocking is the problem, not the CPU usage itself. A `setImmediate` chunk buys you responsiveness for moderate work. For heavy computation, a Worker Pool with pre-warmed workers eliminates both the blocking and the per-request startup cost." For thread pool starvation: "libuv's default of 4 threads means 4 simultaneous `fs.readFile` calls saturate the pool — bcrypt or DNS then queues behind them. This looks like slow DB queries but is actually a thread pool concurrency limit. The fix is `UV_THREADPOOL_SIZE` or moving bcrypt to a Worker Thread so it doesn't compete with I/O for pool slots."
