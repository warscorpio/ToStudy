# `process.nextTick` vs `setImmediate` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Node.js event loop and why does it matter for understanding `process.nextTick` and `setImmediate`?**

A: Node.js is single-threaded and non-blocking. I/O operations, timers, and other async callbacks are placed into queues and processed by the event loop — an internal loop that cycles through phases, draining each queue in turn. Understanding the loop's phase structure is prerequisite to understanding when `nextTick` and `setImmediate` fire, because each targets a different point in that cycle.

The key insight: deferred callbacks are not equal. "Do this later" has multiple meanings in Node.js — before any I/O, after all I/O for this cycle, or on the next timer tick. `process.nextTick` and `setImmediate` represent two of those meanings.

**Q2. What are the phases of the Node.js event loop and where do these APIs fit?**

A: The Node.js event loop has six phases, executed in order each iteration:

```
   ┌──────────────────────────┐
┌─>│  1. timers               │  ← setTimeout / setInterval callbacks
│  └──────────────────────────┘
│  ┌──────────────────────────┐
│  │  2. pending callbacks    │  ← I/O callbacks deferred from prior iteration
│  └──────────────────────────┘
│  ┌──────────────────────────┐
│  │  3. idle, prepare        │  ← internal Node.js use only
│  └──────────────────────────┘
│  ┌──────────────────────────┐
│  │  4. poll                 │  ← retrieve new I/O events; execute their callbacks
│  └──────────────────────────┘
│  ┌──────────────────────────┐
│  │  5. check                │  ← setImmediate callbacks fire here
│  └──────────────────────────┘
│  ┌──────────────────────────┐
└──│  6. close callbacks      │  ← socket.on('close', ...) etc.
   └──────────────────────────┘
```

Between **every** phase (and between every individual callback within a phase), Node.js drains two special queues before moving on:

1. The **nextTick queue** — `process.nextTick` callbacks, higher priority
2. The **microtask queue** — `Promise.then` and `queueMicrotask` callbacks, lower priority

Both are drained completely — in that order — before the next phase starts. This is what makes `process.nextTick` fire "sooner" than `setImmediate`.

## Section 2: `process.nextTick`

**Q3. What is `process.nextTick` and when exactly does it fire?**

A: `process.nextTick` schedules a callback to run after the current synchronous operation completes, but before the event loop advances to its next phase. Technically, it is **not part of the event loop at all** — it is a separate queue that interrupts between phases.

```typescript
console.log('A');

process.nextTick(() => {
  console.log('B — nextTick');
});

console.log('C');

// Output:
// A
// C
// B — nextTick
// The synchronous code (A, C) finishes; BEFORE Node enters any event loop phase,
// the nextTick queue drains — B fires.
```

The nextTick queue is drained **exhaustively** — if a nextTick callback schedules another nextTick, that new callback also runs before the event loop moves on:

```typescript
process.nextTick(() => {
  console.log('first');
  process.nextTick(() => console.log('second — added by first'));
});

process.nextTick(() => console.log('third'));

setImmediate(() => console.log('setImmediate'));

// Output:
// first
// second — added by first   ← runs before 'third'? No — see below.
// third
// setImmediate
```

All nextTick callbacks — including ones added during draining — are processed before `setImmediate` fires.

**Q4. What is the nextTick queue and how is it distinct from the microtask queue?**

A: Node.js maintains two high-priority queues that both run between event loop phases. They are separate queues with different priorities:

| Queue | Populated by | Runs relative to other |
|---|---|---|
| **nextTick queue** | `process.nextTick(cb)` | First — before microtasks |
| **Microtask queue** | `Promise.then`, `queueMicrotask` | Second — after nextTick drains |

Both drain completely before any event loop phase runs. The ordering is stable and guaranteed:

```typescript
Promise.resolve().then(() => console.log('promise 1'));
process.nextTick(() => console.log('nextTick 1'));
Promise.resolve().then(() => console.log('promise 2'));
process.nextTick(() => console.log('nextTick 2'));

// Output:
// nextTick 1    ← entire nextTick queue first
// nextTick 2
// promise 1     ← then microtask queue
// promise 2
```

This ordering has been stable since Node.js v11 (which aligned Node's microtask behavior with the browser event loop standard). The rule: **the nextTick queue always empties before any Promise callback runs.**

**Q5. What is nextTick starvation and why can it silently freeze a Node.js server?**

A: Because `process.nextTick` drains exhaustively — consuming any new callbacks added during draining — a recursive `nextTick` will starve the event loop indefinitely. I/O, timers, and `setImmediate` callbacks never fire:

```typescript
// DANGEROUS: event loop starvation
function recursiveTick() {
  process.nextTick(recursiveTick);
}
recursiveTick();

// The nextTick queue never empties.
// The poll phase never runs — incoming HTTP requests queue up but get no callbacks.
// CPU is high (burning in nextTick drain loop), server appears frozen to clients.
// No errors thrown — the process is alive, just starved.
```

Compare with `setImmediate`, which yields to the event loop after each check phase:

```typescript
// SAFE: yields between iterations
function recursiveImmediate() {
  setImmediate(recursiveImmediate);
}
recursiveImmediate();

// setImmediate fires once per event loop iteration (check phase).
// I/O callbacks, timers, and incoming requests can interleave between iterations.
```

The Node.js documentation explicitly states: "We recommend developers use `setImmediate` in all cases [for recursive deferral] because it's easier to reason about."

## Section 3: `setImmediate`

**Q6. What is `setImmediate` and when exactly does it fire?**

A: `setImmediate` schedules a callback to run in the **check phase** of the event loop — phase 5, which comes immediately after the poll phase. It fires once per event loop iteration, as part of the loop rather than interrupting it. This is the fundamental structural difference from `process.nextTick`.

```typescript
setImmediate(() => console.log('fires in the check phase'));

// Unlike nextTick, this does not fire before the event loop's next phase.
// It fires during the check phase of this (or the next) iteration.
```

The poll phase (phase 4) is where Node.js waits for and processes I/O events. When the poll queue empties, Node.js checks:
- If `setImmediate` callbacks are scheduled → move immediately to check phase
- If no `setImmediate` is scheduled → wait in poll for timers or I/O up to a timeout

**Q7. Why does `setImmediate` reliably fire before `setTimeout(fn, 0)` inside I/O callbacks but not at the top level?**

A: From **top-level / main module code**, the ordering of `setImmediate` vs `setTimeout(fn, 0)` is **non-deterministic** — it depends on the system clock and how quickly the timer gets registered before the timers phase begins:

```typescript
// Top-level — order is non-deterministic between runs
setImmediate(() => console.log('immediate'));
setTimeout(() => console.log('timeout'), 0);
// Sometimes prints: immediate → timeout
// Sometimes prints: timeout → immediate
// Depends on how fast the OS processes the setTimeout registration
```

But from **inside an I/O callback**, `setImmediate` **always** fires before `setTimeout(fn, 0)`:

```typescript
const fs = require('fs');

fs.readFile(__filename, () => {
  // We're executing inside the poll phase.
  // After poll drains, the event loop moves to check phase (setImmediate) BEFORE
  // looping back to the timers phase.
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));

  // Always outputs:
  // immediate
  // timeout
});
```

The reason is structural: inside a poll-phase callback, the next phase in the event loop cycle is always the check phase. The loop must complete its current cycle (check → close) before looping back to timers. So `setImmediate` wins, deterministically, every time when called from within I/O.

## Section 4: Comparison

**Q8. What is the complete, guaranteed execution order of `nextTick`, Promises, `setImmediate`, and `setTimeout(fn, 0)`?**

A:

```typescript
console.log('1 — sync start');

setTimeout(() => console.log('2 — setTimeout'), 0);

setImmediate(() => console.log('3 — setImmediate'));

Promise.resolve().then(() => console.log('4 — promise then'));

process.nextTick(() => console.log('5 — nextTick'));

console.log('6 — sync end');

// Guaranteed output:
// 1 — sync start
// 6 — sync end
// 5 — nextTick      ← nextTick queue (before any phase transition)
// 4 — promise then  ← microtask queue (after nextTick, before any phase)
// 3 — setImmediate  ← check phase   ⎫ non-deterministic relative
// 2 — setTimeout    ← timers phase  ⎭ to each other at top level
```

The guaranteed ordering across both contexts:

| Priority | API | Queue / Phase | Fires |
|---|---|---|---|
| 1st | `process.nextTick` | nextTick queue | After current op, before any phase |
| 2nd | `Promise.then`, `queueMicrotask` | Microtask queue | After nextTick queue empties |
| 3rd | `setImmediate` | Check phase (phase 5) | After poll, same iteration |
| 4th | `setTimeout(fn, 0)` | Timers phase (phase 1) | Next iteration (after check + close) |

Inside I/O callbacks, `setImmediate` is guaranteed to fire before `setTimeout(fn, 0)`. At the top level, their relative order is non-deterministic.

**Q9. When should you use `process.nextTick` vs `setImmediate`?**

A:

**Use `process.nextTick` when:**
- You need the callback to fire after the current synchronous code but before any I/O events are processed — typically to allow a caller to attach event listeners before an event emits
- Implementing Node.js internal patterns: emitting events from constructors, resolving API callback style in user-land
- The callback is very short-lived, not recursive, and not at risk of starvation

```typescript
// Classic pattern: defer event emission until after constructor returns
// so callers have time to attach .on() listeners
class Connection extends EventEmitter {
  constructor(host: string) {
    super();
    this.connect(host).then(() => {
      // WRONG — calling this.emit('ready') synchronously here means
      // the caller never sees it (constructor hasn't returned yet)
    });

    // RIGHT — nextTick fires after the constructor returns
    // and the caller has run new Connection(host).on('ready', handler)
    process.nextTick(() => this.emit('ready'));
  }
}

const conn = new Connection('localhost');
conn.on('ready', () => console.log('connected'));  // This WILL fire
```

**Use `setImmediate` when:**
- Running recursive or iterative work that must yield to I/O between steps
- You want execution after the current poll phase completes (reliable ordering inside I/O)
- Any time you're not sure — the Node.js docs recommend `setImmediate` as the default choice because it cannot starve I/O

```typescript
// Process a large array in chunks without blocking I/O between batches
function processInChunks(
  items: unknown[],
  batchSize: number,
  processFn: (item: unknown) => void,
  done: () => void
): void {
  let index = 0;

  function nextBatch() {
    const end = Math.min(index + batchSize, items.length);
    while (index < end) processFn(items[index++]);

    if (index < items.length) {
      setImmediate(nextBatch);  // yield to event loop — I/O can interleave
    } else {
      done();
    }
  }

  setImmediate(nextBatch);  // Don't start synchronously
}
// Using process.nextTick here would still block I/O because
// nextTick runs before the poll phase, not after it
```

**Q10. Can you nest `nextTick` and `setImmediate` calls? What happens?**

A: Yes, and the behavior reflects how each queue is drained:

```typescript
// Nested nextTick — ALL run before the event loop moves on, including newly added ones
process.nextTick(() => {
  console.log('tick 1');
  process.nextTick(() => {
    console.log('tick 2');
    process.nextTick(() => console.log('tick 3'));
  });
});

setImmediate(() => console.log('immediate'));

// Output:
// tick 1
// tick 2
// tick 3
// immediate
// Reason: exhaustive drain — tick 2 and tick 3 are added mid-drain but still consumed.
```

```typescript
// Nested setImmediate — each fires one check phase later (NOT in the current pass)
setImmediate(() => {
  console.log('immediate 1');
  setImmediate(() => {
    console.log('immediate 2');    // next check phase
    setImmediate(() => console.log('immediate 3'));  // the one after
  });
  process.nextTick(() => console.log('nextTick inside immediate 1'));
});

// Output:
// immediate 1
// nextTick inside immediate 1   ← nextTick fires between individual check callbacks
// immediate 2
// immediate 3
```

Key distinction: `setImmediate` callbacks added inside a `setImmediate` callback run in the **next event loop iteration's** check phase — not the current one. This gives I/O and timers a chance to interleave between recursive `setImmediate` iterations, which is exactly why it's safe for recursive work.

## Section 5: Promises and Microtasks

**Q11. How do Promise callbacks relate to `process.nextTick`? Which runs first and why does it matter?**

A: `process.nextTick` always fires before Promise `.then` callbacks, because the nextTick queue is drained first, then the microtask queue. This has a subtle but important consequence: `await` continuations can be "beaten" by `nextTick` callbacks registered before the `await`:

```typescript
async function example() {
  console.log('async fn start');
  await Promise.resolve();
  // The continuation after await is scheduled as a microtask (Promise.then)
  console.log('after await');
}

example();

process.nextTick(() => console.log('nextTick'));

// Output:
// async fn start
// nextTick         ← fires before the resumed async function
// after await      ← resumed continuation is a microtask, runs after nextTick
```

In practice this creates ordering traps in production code:

```typescript
async function fetchAndProcess() {
  const data = await loadFromDb();   // resumes as microtask after await
  await writeToCache(data);          // runs AFTER any pending nextTicks
}

fetchAndProcess();

// This fires before writeToCache(data) runs, even though fetchAndProcess started first:
process.nextTick(() => {
  cache.invalidate();  // Bug: cache invalidated before writeToCache even starts
});
```

**Q12. What is `queueMicrotask` and how does it compare to `process.nextTick`?**

A: `queueMicrotask` (Node.js v11+ / browser standard) adds a callback to the **microtask queue** — the same queue that `Promise.then` uses. It runs after `process.nextTick` but before `setImmediate` or `setTimeout`:

```typescript
queueMicrotask(() => console.log('queueMicrotask'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise then'));

// Output:
// nextTick          ← nextTick queue (always first)
// queueMicrotask    ← microtask queue, in registration order
// promise then      ← also microtask queue, registered after
```

Key differences:

| | `process.nextTick` | `queueMicrotask` |
|---|---|---|
| Queue | nextTick queue | Microtask queue |
| Priority | Higher (fires first) | Lower (fires after nextTick) |
| Available in browsers | No | Yes |
| Equivalent to | — | `Promise.resolve().then(fn)` |
| Risk | Starvation if recursive | Starvation if recursive |

Prefer `queueMicrotask` in isomorphic (Node.js + browser) code. Prefer `process.nextTick` when you explicitly need to fire before Promise chains — e.g., in Node.js internal patterns.

## Section 6: Advanced Patterns and Gotchas

**Q13. The constructor-emit pattern: why is `process.nextTick` essential here?**

A: Node.js's own core APIs — `net.Server`, `dns`, `stream` — emit events like `'connect'` or `'listening'` using `process.nextTick` internally. Without it, the event fires during the constructor, before the caller has a chance to attach a listener:

```typescript
import { EventEmitter } from 'events';

// BROKEN: emits before caller can call .on()
class Server extends EventEmitter {
  constructor(port: number) {
    super();
    this.emit('listening', port);  // Fires right now — no listeners yet
  }
}
const server = new Server(3000);
server.on('listening', (port) => console.log(`Listening on ${port}`));
// NEVER FIRES — event already emitted before this line ran
```

```typescript
// CORRECT: defers until caller's synchronous setup is complete
class Server extends EventEmitter {
  constructor(port: number) {
    super();
    process.nextTick(() => this.emit('listening', port));
    // nextTick fires after the constructor returns and the caller has run .on()
  }
}
const server = new Server(3000);
server.on('listening', (port) => console.log(`Listening on ${port}`));
// Fires correctly: "Listening on 3000"
```

This is one of the canonical, documented reasons to prefer `process.nextTick` over `setImmediate` for this specific pattern — `setImmediate` would also work, but `nextTick` fires sooner and avoids any risk of I/O events interleaving before the emit.

**Q14. Error handling: how do errors in `nextTick` and `setImmediate` callbacks propagate?**

A: Errors thrown inside either callback **cannot be caught** by a `try/catch` in the calling synchronous code — the callbacks execute in a different call stack, after the synchronous frame has exited:

```typescript
try {
  process.nextTick(() => {
    throw new Error('nextTick error');
  });
} catch (e) {
  console.log('caught:', e);  // NEVER executes
}

// The error propagates to process.on('uncaughtException')
// or crashes the process if unhandled

process.on('uncaughtException', (err) => {
  console.error('Caught at process level:', err.message);
});
```

The same applies to `setImmediate`. The practical rule: **errors in deferred callbacks must be handled inside the callback itself**, or via a global `uncaughtException` / `unhandledRejection` handler. For async work, wrap the body in `try/catch` and reject a Promise or call an error-first callback:

```typescript
setImmediate(async () => {
  try {
    await doWork();
  } catch (err) {
    handleError(err);  // Errors must be caught here — not by the caller
  }
});
```

**Q15. How does `setImmediate` enable cooperative multitasking for CPU-bound work?**

A: Long-running synchronous loops block the event loop — HTTP requests, database callbacks, and timers stall until the loop finishes. `setImmediate` lets you split work into chunks and voluntarily yield between them:

```typescript
// BLOCKING — nothing runs until the full loop completes
function processAllBlocking(items: string[]): void {
  for (const item of items) heavyCompute(item);
}

// NON-BLOCKING — yields to the event loop between batches
function processAllAsync(items: string[], batchSize = 100): Promise<void> {
  return new Promise((resolve) => {
    let index = 0;

    function batch() {
      const limit = Math.min(index + batchSize, items.length);
      while (index < limit) heavyCompute(items[index++]);

      if (index < items.length) {
        setImmediate(batch);    // Yield — I/O callbacks can run here
      } else {
        resolve();
      }
    }

    setImmediate(batch);        // Don't start synchronously
  });
}

// Why setImmediate and NOT process.nextTick here?
// nextTick runs BEFORE the poll phase — I/O callbacks still can't fire between batches.
// setImmediate runs AFTER the poll phase — actual I/O, timers, and connections
// can be handled between each batch.
```

## Section 7: Scenario-Based Questions

**Q16. "Predict the exact output of this code."**

```typescript
console.log('start');

setTimeout(() => {
  console.log('timeout 1');
  process.nextTick(() => console.log('nextTick inside timeout'));
}, 0);

setImmediate(() => {
  console.log('immediate 1');
  process.nextTick(() => console.log('nextTick inside immediate'));
});

process.nextTick(() => {
  console.log('nextTick 1');
  Promise.resolve().then(() => console.log('promise inside nextTick'));
});

Promise.resolve().then(() => console.log('promise 1'));

setImmediate(() => console.log('immediate 2'));

console.log('end');
```

A: Tracing step by step:

```
start                        ← sync
end                          ← sync

// nextTick queue drained first:
nextTick 1                   ← process.nextTick(() => { ... })

// microtask queue drained (after all nextTicks):
promise inside nextTick      ← queued by nextTick 1's body
promise 1                    ← original Promise.resolve().then(...)

// check phase (both setImmediate calls were registered before poll):
immediate 1
// nextTick queue drains between each check-phase callback:
nextTick inside immediate
// back to check phase:
immediate 2

// timers phase:
timeout 1
// nextTick queue drains after timeout 1's callback:
nextTick inside timeout
```

Full output (assuming `setImmediate` fires before `setTimeout` — common at top level but not guaranteed):

```
start
end
nextTick 1
promise inside nextTick
promise 1
immediate 1
nextTick inside immediate
immediate 2
timeout 1
nextTick inside timeout
```

Critical observations: (1) `promise inside nextTick` fires before `promise 1` because it was added to the microtask queue during the nextTick drain — when the microtask queue runs, it processes in FIFO order, but `promise inside nextTick` was queued first. (2) `nextTick inside immediate` fires between `immediate 1` and `immediate 2` because nextTick is drained after each individual check-phase callback. (3) `nextTick inside timeout` fires after `timeout 1` but before the next event loop phase.

**Q17. "Why might a Node.js HTTP server stop responding to requests even though the process is running?"**

A: A classic production incident caused by recursive `process.nextTick`:

```typescript
// Somewhere in a request handler or startup code — a subtle bug
function pollCondition() {
  process.nextTick(() => {
    if (!isReady()) {
      pollCondition();   // Keeps re-scheduling if isReady() stays false
    }
    // Bug: isReady() gets stuck returning false (e.g., a DB connection times out)
  });
}
pollCondition();

// Effect:
// - The nextTick queue never empties
// - The poll phase never runs
// - Incoming TCP connections queue up at the OS level — eventually drop
// - process.cpuUsage() shows ~100% (burning in nextTick drain)
// - No errors thrown — process.exit() still responds
// - Health checks time out; load balancer removes the instance

// Diagnosis: top-level CPU high + zero throughput + no error logs
// Fix: replace process.nextTick with setImmediate — yields to I/O between checks
```

**Q18. "Design a rate-limited async task queue that processes jobs without starving I/O."**

A:

```typescript
class TaskQueue {
  private queue: Array<() => Promise<void>> = [];
  private running = false;
  private readonly batchSize: number;

  constructor(batchSize = 10) {
    this.batchSize = batchSize;
  }

  enqueue(task: () => Promise<void>): void {
    this.queue.push(task);
    if (!this.running) this.start();
  }

  private start(): void {
    this.running = true;
    // Use setImmediate to not start synchronously — let caller finish setup first
    setImmediate(() => this.drain());
  }

  private async drain(): Promise<void> {
    const batch = this.queue.splice(0, this.batchSize);

    if (batch.length === 0) {
      this.running = false;
      return;
    }

    // Run this batch concurrently
    await Promise.all(batch.map(task => task().catch(console.error)));

    if (this.queue.length > 0) {
      // KEY: setImmediate instead of process.nextTick
      // setImmediate yields to the poll phase — HTTP requests, DB responses,
      // file reads can all interleave between batches.
      // process.nextTick would yield too, but BEFORE I/O — starving it.
      setImmediate(() => this.drain());
    } else {
      this.running = false;
    }
  }
}

// Usage
const queue = new TaskQueue(5);

for (let i = 0; i < 50; i++) {
  queue.enqueue(async () => {
    await someDbQuery(i);
    console.log(`Task ${i} complete`);
  });
}

// Incoming HTTP requests are not blocked between batches because
// setImmediate yields to the poll phase between each group of 5 tasks.
```

## Section 8: Interview Edge Cases

**Q19. What happens if you call `process.nextTick` inside a `Promise.then` callback? Does it fire before or after the next `.then` in the same chain?**

A: `process.nextTick` inside a microtask fires before subsequent microtasks in the queue — because draining switches from "microtask queue" back to "nextTick queue" immediately when a new nextTick is added:

```typescript
Promise.resolve()
  .then(() => {
    console.log('then 1');
    process.nextTick(() => console.log('nextTick from then 1'));
  })
  .then(() => {
    console.log('then 2');
  });

// Output:
// then 1
// nextTick from then 1    ← fires before 'then 2'
// then 2

// Why: after 'then 1' runs, the nextTick queue is checked before
// the microtask queue continues. 'then 2' is in the microtask queue;
// 'nextTick from then 1' is in the nextTick queue — nextTick wins.
```

This can create ordering surprises in long Promise chains that mix `process.nextTick` with `.then`.

**Q20. Does `setImmediate` have a return value, and can you cancel it?**

A: Yes — `setImmediate` returns an `Immediate` object (in Node.js) analogous to the ID returned by `setTimeout`. You can cancel a pending `setImmediate` with `clearImmediate`:

```typescript
const immediate = setImmediate(() => {
  console.log('this will not run');
});

clearImmediate(immediate);  // Cancels the scheduled callback

// Compare with setTimeout / clearTimeout — same pattern.
// process.nextTick has NO cancellation mechanism —
// once scheduled, a nextTick callback WILL run.
// This is another reason to prefer setImmediate for work that may need to be aborted.
```

There is no `clearNextTick` or equivalent. Once `process.nextTick(fn)` is called, `fn` is committed to running. For cancellable deferred work, always use `setImmediate`.

## Quick Reference Table

| Property | `process.nextTick` | `setImmediate` | `Promise.then` / `queueMicrotask` | `setTimeout(fn, 0)` |
|---|---|---|---|---|
| Part of event loop | No — interrupts between phases | Yes — check phase (phase 5) | No — microtask queue | Yes — timers phase (phase 1) |
| Fires relative to I/O | Before (runs before poll) | After (runs after poll) | Before (runs before poll) | After check phase |
| Priority order | 1st (highest) | 3rd | 2nd | 4th (lowest) |
| Exhaustively drained | Yes — including new additions | No — new ones wait for next iteration | Yes — including new additions | No — one per timers phase pass |
| Starvation risk | Yes — can block I/O indefinitely | No — yields per iteration | Yes — if Promises chain infinitely | No |
| Cancellable | No — no `clearNextTick` | Yes — `clearImmediate` | No | Yes — `clearTimeout` |
| Available in browsers | No | No | Yes | Yes |
| Ordering vs `setTimeout(fn,0)` | Always before | Before inside I/O; non-deterministic at top level | Always before | — |
| Best use case | Constructor-emit pattern; defer until after sync code | Iterative/recursive async work; avoid starvation | Standard async continuation | Minimum-delay timer with low priority |

**Tip for interviews:** Five things separate strong candidates on this topic: (1) knowing that **`process.nextTick` is not technically part of the event loop** — it is a separate queue that interrupts between every event loop phase; saying "it fires before the next iteration of the event loop" is correct, but saying "it fires after the current operation, before the event loop's next phase" is more precise and impressive; (2) demonstrating **nextTick starvation** with a concrete example and explaining why it freezes a server (CPU high, no I/O, no errors — deceptively silent); (3) knowing the complete **three-level priority order**: `process.nextTick` → `Promise.then / queueMicrotask` → `setImmediate` → `setTimeout(fn, 0)`, and being able to trace output through code that mixes all four; (4) explaining **why `setImmediate` vs `setTimeout(fn, 0)` is non-deterministic at the top level but deterministic inside I/O callbacks** — the event loop phase structure makes check phase always precede timers phase within a single iteration, which only matters when you're already inside the poll phase; and (5) knowing the **constructor-emit pattern** — why Node.js core uses `process.nextTick` to emit events, that there is no `clearNextTick`, and when to reach for `setImmediate` instead (recursive work, anything that needs to yield to I/O).
