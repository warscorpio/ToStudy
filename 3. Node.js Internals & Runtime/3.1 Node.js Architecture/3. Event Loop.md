## Part 1 — Theory & Interview Q&A

## Topic A: Event Loop Architecture

### Section A1: Fundamentals

**Q1. What is the event loop, what problem does it solve in Node.js's single-threaded model, and what implements it?**

A: The event loop is the mechanism that allows Node.js to perform non-blocking I/O operations despite running JavaScript on a single thread. The fundamental problem: JavaScript can only execute one thing at a time, but a server must handle thousands of concurrent connections, file reads, network calls, and database queries. Without the event loop, a single slow disk read would freeze the entire process. The event loop solves this by delegating work to the operating system (via kernel APIs like `epoll`, `kqueue`, `IOCP`) or to a C thread pool for operations the OS can't handle asynchronously. When that work completes, the event loop routes the result callback back into the JavaScript execution queue. The event loop itself is implemented in **libuv** — a cross-platform C library that abstracts OS-level I/O and provides the phase-based event loop. Node.js's JavaScript runtime (V8) only executes callbacks; libuv decides when and in what order those callbacks are ready to run.

```
                    ┌───────────────────────────┐
                    │       Node.js Process      │
                    │  ┌──────────┐  ┌────────┐  │
                    │  │    V8    │  │libuv   │  │
                    │  │(JS exec) │◄─►(event  │  │
      JS code ─────►│  └──────────┘  │ loop)  │  │
                    │               └────────┘  │
                    │  ┌─────────────────────┐  │
                    │  │    Thread Pool       │  │
                    │  │  (fs, crypto, dns)  │  │
                    │  └─────────────────────┘  │
                    └───────────────────────────┘
```

**Q2. What are the six phases of the event loop, in order, and what type of callback does each phase execute?**

A: The event loop processes callbacks in six phases that execute in a fixed, repeating cycle. Each phase has a FIFO queue of callbacks:

```
   ┌─────────────────────────────────┐
   │           timers                │ ← setTimeout / setInterval callbacks
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │       pending callbacks         │ ← I/O errors deferred from previous tick
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │       idle, prepare             │ ← internal use only (libuv internals)
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │             poll                │ ← retrieve I/O events; execute I/O callbacks
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │             check               │ ← setImmediate callbacks
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │        close callbacks          │ ← socket.on('close', ...), etc.
   └────────────────┬────────────────┘
                    │
        ────────────┘ (repeat)

Between EVERY phase: nextTick queue drained → microtask queue drained
```

**Q3. What is the difference between an event loop "tick" and a full event loop "iteration"?**

A: The terminology is unfortunately inconsistent in the Node.js ecosystem. A full event loop **iteration** (sometimes called a "loop cycle") is one complete pass through all six phases: timers → pending callbacks → idle/prepare → poll → check → close callbacks. A **tick** is ambiguous — it is commonly used to mean any single callback execution, but `process.nextTick`'s name implies "next tick of the event loop," which actually means "before the next phase begins," not "next full iteration." More precisely: the nextTick queue runs at the boundary between any C++ and JavaScript execution — after the current JavaScript call stack empties. This is why `process.nextTick` runs *before* the event loop even enters its first phase, and between every phase transition. An event loop iteration completes only when all six phases have been visited; if there are no more pending callbacks, timers, or I/O, the event loop exits and the process terminates.

```
[sync code] → [nextTick queue] → [microtask queue]
    → [Phase 1: timers]
    → [nextTick queue] → [microtask queue]
    → [Phase 2: pending callbacks]
    → [nextTick queue] → [microtask queue]
    → ...
    → [Phase 6: close callbacks]
    → [nextTick queue] → [microtask queue]
    → (next iteration or exit)
```

**Q4. What are microtasks, and what two queues process them, and what is their ordering relative to the six phases?**

A: Microtasks are callbacks that run "between" macrotasks — they have higher priority than any of the six event loop phases. In Node.js there are two microtask queues: **`process.nextTick` queue** and the **Promise microtask queue** (from `Promise.then()`, `Promise.resolve()`, `queueMicrotask()`). The critical ordering: the **nextTick queue is always drained before the Promise microtask queue**. Both queues run completely (including any newly queued callbacks) before the event loop moves on. In Node.js v11+, microtask queues are drained between every *individual callback* within a phase (not just between phases) — matching browser behavior. The invariant: when V8 finishes executing any JavaScript, the nextTick queue empties first, then the Promise queue, before any event loop phase callback gets a turn.

```
Microtask drain order (between any JS execution):
  Step 1: while nextTick queue not empty:
    run all nextTick callbacks (new ones added here run in same drain)
  Step 2: while Promise microtask queue not empty:
    run one Promise callback
    then drain nextTick queue again before next Promise callback

Key: process.nextTick ALWAYS beats Promise.then, even if .then was scheduled first
```

**Q5. What is `process.nextTick`, why is it named "next tick" when it doesn't run in the next tick, and what is its performance tradeoff?**

A: `process.nextTick` is not a phase of the event loop — it's a special queue that drains immediately after the current JavaScript execution completes, before any I/O, timer, or `setImmediate` callback can run. Its misleading name dates to early Node.js: "next tick" referred to the next opportunity for the event loop to process, not the next full iteration. Its primary use: allowing a function to call a callback asynchronously (avoiding synchronous callback invocation, which can cause subtle ordering issues) while ensuring the callback runs *before* any I/O event. The performance tradeoff: `process.nextTick` can starve the event loop — if a `nextTick` callback queues another `nextTick` recursively, the poll phase never runs and I/O callbacks never fire. This is why Node.js documentation recommends using `setImmediate` for recursive calls.

```js
// Common use: ensure callback is always async (even if result is sync):
function getData(id, callback) {
  const cached = cache.get(id);
  if (cached) {
    // BAD: synchronous callback — caller's nextTick callbacks run after this
    // callback(null, cached);

    // GOOD: async callback — maintains consistent ordering
    process.nextTick(() => callback(null, cached));
    return;
  }
  db.find(id, callback); // always async
}
```

**Q6. What is libuv's role, and what is the thread pool it provides?**

A: **libuv** is the C library that implements the event loop, handles OS-level asynchronous I/O, and provides a platform-independent API for Node.js. For operations the OS can handle asynchronously (network sockets, `epoll`/`kqueue` event notification), libuv uses kernel primitives directly — no threads needed. For operations that don't have OS-level async APIs (file system operations on Linux, DNS resolution via `getaddrinfo`, some crypto operations), libuv maintains a **thread pool** (default size: 4 threads, configurable via `UV_THREADPOOL_SIZE` up to 1024). Thread pool workflow: JavaScript calls `fs.readFile()` → libuv dispatches to a thread pool worker → worker reads the file (blocking, in C) → when done, worker signals the event loop → poll phase picks up the completion event → the callback runs in the JS thread. The thread pool is what enables non-blocking file I/O without OS async file APIs.

```
UV_THREADPOOL_SIZE=4 (default):
  Thread 1: fs.readFile('a.txt')  ─┐
  Thread 2: fs.readFile('b.txt')   ├─ run concurrently in C
  Thread 3: crypto.pbkdf2(...)    ─┘
  Thread 4: dns.lookup('host')

When any thread completes:
  → signals event loop
  → poll phase picks up the completion
  → JS callback runs on the SINGLE JS thread
```

### Section A2: Phase-by-Phase Details

**Q7. What happens in the timers phase, how does Node.js check if a timer has expired, and why is `setTimeout(fn, 0)` never exactly 0ms?**

A: The timers phase executes callbacks whose scheduled delay has elapsed. Internally, libuv maintains a **min-heap of timers** sorted by their earliest expiration timestamp. At the start of the timers phase, Node.js records the current time *once* and compares it against the heap's minimum — if the earliest timer's threshold has passed, its callback runs; Node.js continues popping from the heap as long as the current time exceeds each timer's threshold. **Why `setTimeout(fn, 0)` is never exactly 0ms**: The minimum timer resolution in Node.js is 1ms (libuv clamps delay to at minimum 1ms). Beyond that, the timers phase only runs when the event loop *reaches* it — if the poll phase is blocking waiting for I/O, timers are delayed until poll exits. Additionally, the OS scheduler has its own delays: the process may not be scheduled immediately. The delay is thus `max(1ms, actualSystemDelay + timeInOtherPhases)`. Specifying `delay = 0` is treated as `delay = 1` by libuv internally.

```
Timer min-heap at event loop timers phase entry (t = 105ms):

  Heap: [(fire_at=100ms, fn1), (fire_at=110ms, fn2), (fire_at=120ms, fn3)]
  
  Pop (100ms): 100 <= 105 → execute fn1 ✓
  Pop (110ms): 110 > 105  → STOP. 110ms timer not yet expired.
  
  t=105: fn1 runs. fn2 and fn3 wait for next iteration.
  
  (Between fn1 and moving to next phase: nextTick + microtask queues drain)
```

**Q8. What happens in the poll phase, what two decisions does it make, and what is the blocking behavior?**

A: The poll phase is the heart of Node.js's I/O model. It does two things: (1) **retrieves new I/O completion events** (socket data, file reads, etc.) and executes their callbacks; (2) **blocks** if there is nothing to do, waiting for new I/O events. The blocking decision: if `setImmediate` callbacks are scheduled, the poll phase will not block — it processes available I/O and then immediately moves to the check phase. If no `setImmediate` callbacks are pending, poll calculates how long to block: `min(timeUntilNextTimer, OS_default)` — it will block until either an I/O event arrives or a timer becomes eligible. If no timers and no `setImmediate` are pending and no more I/O events are expected, the event loop exits and the process terminates. The poll phase is the only phase that can block, which is why `setImmediate` inside an I/O callback always runs before the next `setTimeout(fn, 0)` — the poll phase has already started before checking timers.

```
Poll phase logic:
  ┌─ Are there callbacks in the poll queue?
  │   YES → execute them all (up to limit)
  │   NO  → wait...
  │         if setImmediate registered → exit poll immediately → check phase
  │         if pending timers → block for (time_until_next_timer)
  │         if nothing pending → block indefinitely (or exit process)
  │
  └─ When an I/O event arrives → execute its callback → repeat decision

Key insight: poll CAN block. No other phase does.
```

**Q9. What happens in the check phase, and why does `setImmediate` run before the NEXT iteration's timers — not immediately?**

A: The check phase runs all callbacks registered with `setImmediate()`. Despite the name "immediate," `setImmediate` doesn't run truly immediately — it runs after the poll phase completes in the current event loop iteration. The name reflects that it fires at the *next available opportunity after I/O* — specifically, immediately after the poll phase, before the loop wraps around to the timers phase. This is why, inside an I/O callback, `setImmediate` is *guaranteed* to run before any `setTimeout(fn, 0)` — the event loop is already inside the current iteration's poll phase; when the I/O callback returns, it moves to check (setImmediate), then close callbacks, then wraps to the *next* iteration's timers. Outside I/O callbacks (e.g., at the top level of a script), the order of `setTimeout(fn, 0)` and `setImmediate` is *non-deterministic* because it depends on whether 1ms has elapsed by the time the event loop starts its first timers phase.

```
Inside I/O callback — setImmediate GUARANTEED before setTimeout:

  [poll phase: I/O callback runs]
       ↓
  [check phase: setImmediate runs] ← DETERMINISTIC: check is next
       ↓
  [close callbacks]
       ↓
  [next iteration timers: setTimeout runs] ← always AFTER setImmediate

At top level — ORDER IS NON-DETERMINISTIC:
  [script executes]
       ↓
  [event loop starts]
       ↓
  [timers phase]: has 1ms elapsed? 
    YES → setTimeout runs first
    NO  → setTimeout skipped, check phase runs setImmediate first
```

**Q10. What happens in the pending callbacks phase, and what specific callbacks does it handle?**

A: The pending callbacks phase executes I/O callbacks that were **deferred to the next iteration** by the previous event loop pass. This is distinct from the poll phase: the poll phase executes I/O callbacks as soon as they complete; the pending callbacks phase handles a small set of situations where callbacks couldn't run in the poll phase. The primary case: TCP error callbacks on some operating systems — when a TCP connection receives an `ECONNREFUSED` error, some systems report it asynchronously; libuv defers these to the pending callbacks phase so they don't interfere with the poll phase's flow. In practice, developers rarely encounter the pending callbacks phase directly — most I/O callbacks run in the poll phase. The pending callbacks phase is a libuv implementation detail for edge cases in system-level I/O error reporting.

**Q11. What is the idle/prepare phase, and why can't Node.js developers interact with it directly?**

A: The idle and prepare phases are **internal to libuv** and exist for bookkeeping. The idle phase runs when the event loop would otherwise block in the poll phase — libuv uses it for internal wakeup signaling. The prepare phase runs immediately before the poll phase blocks — libuv uses it to set up the `epoll`/`kqueue`/`IOCP` watch lists before asking the OS "wait for any of these events." Node.js exposes no JavaScript API for these phases; they are transparent to developers. They appear in the Node.js documentation for completeness and for authors of native Node.js addons written in C++ (which can register their own libuv handles that trigger during these phases). For all practical purposes at the JavaScript level, the event loop has four relevant phases: timers, poll, check, and close — plus the nextTick and microtask queues.

**Q12. What happens in the close callbacks phase, and what triggers a close callback?**

A: The close callbacks phase executes callbacks for abruptly closed handles and streams — specifically the `'close'` event emitted when a resource is destroyed. Examples: `socket.destroy()` emits `'close'`; `stream.on('close', cb)` is a close callback; `process.on('exit', cb)` runs here for some implementations. If a socket or handle is closed with `.destroy()` rather than being gracefully shut down, the `'close'` event fires during this phase. The close callbacks phase is the last in the iteration; after it completes, the event loop either repeats (if more async work is pending) or exits (if all references to async resources are dropped and all queues are empty). `process.on('beforeExit', cb)` fires when the event loop empties — not a phase, but triggered between iterations when no more work is queued.

## Topic B: Ordering and Timing

### Section B1: Output Ordering

**Q13. Why is `setTimeout(fn, 0)` vs `setImmediate` non-deterministic at the top level but fully deterministic inside an I/O callback?**

A: The non-determinism at the top level is caused by process startup time. When a script executes, the event loop hasn't started yet. By the time the JavaScript finishes and the event loop begins its first iteration, either ≥1ms has elapsed (making the setTimeout threshold satisfied → timer runs first) or <1ms has elapsed (timer not satisfied → poll phase runs → check phase runs setImmediate → then next iteration's timers). Whether 1ms has passed depends on CPU load, OS scheduling, and Node.js startup overhead — entirely non-deterministic. Inside an I/O callback, the situation is completely deterministic: the event loop is already inside the current iteration at the poll phase. After the I/O callback returns: poll phase completes → check phase runs (setImmediate) → close callbacks → *next* iteration's timers phase. `setImmediate` always precedes the next timers phase, making the order guaranteed.

```js
// Non-deterministic at top level:
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// Output: either order depending on startup time

// Deterministic inside I/O callback:
const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);   // runs AFTER setImmediate
  setImmediate(() => console.log('immediate'));   // ALWAYS runs first
});
// Output: always 'immediate' then 'timeout' ✓
```

**Q14. What is the complete priority ordering of async mechanisms from highest to lowest priority?**

A: From highest to lowest execution priority:

```
1. Synchronous code (current call stack)
   ─────────────────────────────────────────
2. process.nextTick callbacks
   (all queued, including ones added during drain)
   ─────────────────────────────────────────
3. Promise microtasks (.then, .catch, .finally, queueMicrotask)
   (nextTick queue checked and drained between each Promise callback)
   ─────────────────────────────────────────
4. Event loop phases (in order per iteration):
   4a. setTimeout / setInterval (timers phase)
   4b. I/O callbacks (poll phase)
   4c. setImmediate (check phase)
   4d. close callbacks

   Between each callback in steps 4a-4d (Node.js v11+):
   → nextTick queue drains
   → microtask queue drains
```

The key asymmetry: `process.nextTick` beats `Promise.then` even if the Promise was created first. `setImmediate` has LOWER priority than both, but HIGHER priority than the next event loop iteration's timers.

**Q15. What is "nextTick starvation," and what is its root cause?**

A: nextTick starvation occurs when `process.nextTick` callbacks recursively queue more `process.nextTick` callbacks, preventing the event loop from ever advancing to its phases. Because the nextTick queue is fully drained before any phase runs, and newly queued nextTick callbacks are processed in the same drain, an infinite nextTick chain blocks all I/O, timers, and `setImmediate` indefinitely. The event loop never reaches the poll phase, so no I/O callbacks can fire. This is the opposite of `setImmediate` recursion — `setImmediate` only runs one callback per check phase visit, so recursion via `setImmediate` allows I/O and timers to run between iterations.

```js
// STARVATION: blocks everything else
function starveLoop() {
  process.nextTick(starveLoop); // infinite nextTick chain
}
starveLoop();
// setTimeout(() => console.log('never runs'), 1);  // NEVER fires ✗
// fs.readFile('file.txt', cb);                      // NEVER fires ✗

// SAFE: setImmediate allows I/O to run between iterations
function safeRecurse() {
  setImmediate(safeRecurse); // one per check phase — I/O can run between iterations
}
safeRecurse();
// fs.readFile('file.txt', cb); // CAN fire between setImmediate iterations ✓
```

**Q16. How do nested `process.nextTick` callbacks behave — do callbacks added during a drain run in the same drain?**

A: Yes — callbacks queued by other `process.nextTick` callbacks run in the **same drain**, not the next one. When the nextTick queue is draining, any callback that queues another `nextTick` adds it to the *back* of the current drain queue. The drain continues until the queue is empty. This is what makes starvation possible — a single `process.nextTick(fn)` that always re-queues itself will drain forever. Contrast with `setImmediate`: callbacks added inside a `setImmediate` run in the *next* check phase (next iteration), not the current one — giving the event loop breathing room. This distinction is fundamental: nextTick has no "generation boundary" within a drain; setImmediate does.

```js
process.nextTick(() => {
  console.log('nextTick 1');
  process.nextTick(() => {
    console.log('nextTick 2'); // runs in SAME drain as nextTick 1
    process.nextTick(() => console.log('nextTick 3')); // also same drain
  });
});
// Output (all before any phase):
// nextTick 1
// nextTick 2
// nextTick 3

setImmediate(() => {
  console.log('immediate 1');
  setImmediate(() => console.log('immediate 2')); // runs in NEXT check phase
});
// immediate 1 runs in iteration 1
// immediate 2 runs in iteration 2 (I/O can run between them)
```

**Q17. How do microtasks run between individual callbacks in Node.js v11+ vs earlier versions?**

A: Before Node.js v11, microtasks (nextTick and Promises) ran between *phases*, not between individual callbacks within a phase. This meant that if two `setTimeout(fn, 0)` callbacks were queued and the first one scheduled a Promise, that Promise ran after BOTH timer callbacks completed. Node.js v11 changed this to match browser behavior: microtasks now run after **each individual callback** within every phase. This means a Promise scheduled inside the first `setTimeout` callback runs before the second `setTimeout` callback. This behavioral change was a breaking change for code relying on the old ordering.

```js
setTimeout(() => {
  console.log('timer 1');
  Promise.resolve().then(() => console.log('promise 1'));
}, 0);

setTimeout(() => {
  console.log('timer 2');
}, 0);

// Node.js <= 10:
// timer 1 → timer 2 → promise 1
// (promise ran after ALL timers in the phase)

// Node.js >= 11:
// timer 1 → promise 1 → timer 2
// (microtasks drain between EACH timer callback, matching browser behavior)
```

**Q18. What is the minimum timer resolution, and what is "timer clamping" for nested timers in browsers vs Node.js?**

A: In Node.js, the minimum `setTimeout` delay is **1ms** — libuv clamps any value below 1 (including 0 and negative values) to 1ms. There is no additional clamping for nested timers in Node.js, unlike browsers. In browsers (following the HTML spec), `setTimeout` has a minimum delay of 0ms, but *nested* `setTimeout` calls (5+ levels deep) are clamped to 4ms to prevent timer spam from nested event-polling patterns. Node.js does not implement this nesting clamping — a `setTimeout(fn, 0)` at any nesting depth still fires at ~1ms. The practical implication: if you're porting timer-based code from browsers to Node.js, `setTimeout(fn, 0)` fires slightly more frequently in Node.js (1ms vs 4ms for deeply nested browser timers).

### Section B2: Practical Implications

**Q19. What is "event loop lag" (or event loop latency), and how do you measure it?**

A: Event loop lag is the delay between when a callback is *scheduled* and when it *actually runs*. For a server with no synchronous blocking, event loop lag should be small (1-5ms). Blocking the event loop with synchronous CPU work increases lag — during a 200ms synchronous computation, ALL other callbacks (I/O responses, timers, incoming requests) are queued but cannot run. The canonical measurement: schedule a `setTimeout(fn, 0)` (expected to fire in ~1ms) and measure how long it actually took. The difference is the event loop lag at that moment.

```js
// Measure event loop lag:
function measureLag() {
  const start = performance.now();
  setTimeout(() => {
    const lag = performance.now() - start - 1; // subtract expected 1ms delay
    console.log(`Event loop lag: ${lag.toFixed(2)}ms`);
    measureLag(); // keep measuring
  }, 1);
}
measureLag();

// Better: use process.hrtime for high-resolution timing:
function eventLoopLagMonitor(cb: (lagMs: number) => void, interval = 100) {
  let lastCheck = process.hrtime.bigint();
  setInterval(() => {
    const now = process.hrtime.bigint();
    const elapsedMs = Number(now - lastCheck) / 1e6;
    const lagMs = elapsedMs - interval; // how much longer than `interval` ms did it take?
    lastCheck = now;
    cb(lagMs);
  }, interval).unref(); // .unref() prevents this monitor from keeping process alive
}
```

**Q20. What happens to ALL pending async operations when the call stack is blocked by synchronous code?**

A: All of them wait. While synchronous code runs, the event loop is blocked — no callbacks fire, no I/O is processed, no timers can advance. If an HTTP request arrives during a 500ms synchronous operation, the response is delayed by 500ms regardless of how fast the handler would be. If a timer was scheduled to fire during those 500ms, it fires *immediately when the sync code completes* (the timer already expired; it just couldn't run). This is why CPU-intensive operations (sorting large arrays, complex regex, bcrypt password hashing) can kill Node.js server performance. The fix: offload CPU work to the thread pool (`worker_threads`) or break it into chunks with `setImmediate` between chunks.

```js
// Blocking example: server can't respond during this:
app.get('/heavy', (req, res) => {
  // 200ms of synchronous work blocks ALL other requests
  const result = performHeavyComputation(); // 200ms sync
  res.json(result);
  // During those 200ms: other HTTP requests pile up, timers misfire, I/O backs up
});

// Non-blocking alternative: use Worker thread
app.get('/heavy', async (req, res) => {
  const result = await runInWorkerThread(heavyComputationFn, data);
  res.json(result); // event loop was free during the 200ms
});
```

**Q21. How does the Promise microtask queue interact with `process.nextTick` — what runs first within a microtask drain?**

A: The precise interleaving between `process.nextTick` and Promise callbacks: the nextTick queue is checked and fully drained *before the first Promise callback*, and then again *between each subsequent Promise callback*. This means: (1) all pending `process.nextTick` callbacks run first; (2) one Promise `.then` callback runs; (3) all newly-queued nextTick callbacks run; (4) the next Promise `.then` callback runs; repeat. The invariant: at no point does a Promise callback run when there are pending `process.nextTick` callbacks — nextTick always wins the "run next" competition.

```js
Promise.resolve()
  .then(() => {
    console.log('Promise 1');
    process.nextTick(() => console.log('nextTick inside Promise 1'));
  })
  .then(() => console.log('Promise 2'));

process.nextTick(() => console.log('nextTick outer'));

// Output:
// nextTick outer           ← nextTick queue drains FIRST
// Promise 1                ← first Promise callback
// nextTick inside Promise 1 ← nextTick queue drained between Promise callbacks
// Promise 2                ← second Promise callback

// Counterintuitive: the nextTick INSIDE the Promise callback runs
// BEFORE the next .then(), not after all .then() calls
```

**Q22. When should you use `setImmediate` vs `process.nextTick` vs `setTimeout(fn, 0)`?**

A:

| Use | When |
|---|---|
| `process.nextTick` | Callback must run before any I/O — API callbacks that should always be async, error propagation, resolving a race condition before I/O fires |
| `setImmediate` | Running something "after I/O" without blocking the loop — recursive async iteration, breaking up CPU work, non-critical cleanup |
| `setTimeout(fn, 0)` | Compatibility with browser code; when 1ms delay is acceptable; when you want something "after timers" might matter |

Rule of thumb: use `setImmediate` over `process.nextTick` for any recursion. Use `process.nextTick` only when you specifically need to guarantee execution before I/O events. Avoid `setTimeout(fn, 0)` for ordering guarantees — its relationship to `setImmediate` is non-deterministic at the top level.

## Topic C: Advanced and Cross-Topic

**Q23. How does the Node.js event loop differ from the browser event loop?**

A: Three key differences: (1) **Phases**: Node.js has six explicit phases implemented in C by libuv; browsers have a simpler model with macrotask queue, microtask queue, and rendering steps — no distinct "poll phase" or "pending callbacks phase." (2) **`setImmediate`**: exists only in Node.js; browsers don't have it. (3) **`process.nextTick`**: Node.js-only; the closest browser equivalent is `queueMicrotask()`, but nextTick runs before Promise microtasks, while `queueMicrotask` and `Promise.then` are same-priority in browsers. (4) **Rendering**: browsers interleave rendering (style/layout/paint) between macrotasks — this is the "task → microtasks → render → next task" cycle. Node.js has no rendering step. (5) **v11+ convergence**: Node.js v11 aligned microtask timing (between individual callbacks) with browsers, reducing one major difference.

```
Browser event loop:
  task (macrotask) → microtasks → render → task → microtasks → render → ...

Node.js event loop:
  sync → nextTick → microtasks
  → [timers] → nextTick → microtasks
  → [pending callbacks] → nextTick → microtasks
  → [poll] → nextTick → microtasks
  → [check] → nextTick → microtasks
  → [close] → nextTick → microtasks
  → repeat

Common misconceptions:
  Browser 'macrotask' ≈ Node.js event loop 'callback' (not phase)
  Browser 'microtask' = both nextTick AND Promise in Node.js
  setImmediate does not exist in browsers
```

**Q24. Do Worker threads have their own event loops, and how do they communicate with the main thread?**

A: Yes — each `Worker` thread is a completely separate V8 instance with its own isolated event loop, its own heap, and its own stack. Workers do not share memory (except for explicitly shared `SharedArrayBuffer` segments). Communication happens through message passing: `parentPort.postMessage(data)` and `worker.postMessage(data)`. When a worker sends a message, it becomes an I/O event from the perspective of the receiving thread's event loop — it arrives in the poll phase like any other I/O. Crucially: spawning a Worker thread doesn't block the main thread's event loop; the Worker runs on a separate OS thread. This makes Workers the correct tool for CPU-intensive work — the main event loop stays responsive while the Worker thread computes.

```js
// main.js
const { Worker, isMainThread, parentPort } = require('worker_threads');

if (isMainThread) {
  const worker = new Worker(__filename); // separate thread + separate event loop
  worker.on('message', (result) => {    // arrives as I/O event in main's poll phase
    console.log('Result from worker:', result);
  });
  worker.postMessage({ data: [1, 2, 3, 4, 5] });
  // Main thread event loop is NOT blocked while worker computes
} else {
  parentPort.on('message', ({ data }) => { // worker's own event loop
    const result = data.reduce((a, b) => a + b, 0); // CPU work on this thread
    parentPort.postMessage(result);
  });
}
```

**Q25. State the invariant for each phase and each microtask queue in one sentence each.**

A:
- **`process.nextTick` queue**: all queued callbacks — including any queued during the drain — run to completion before any Promise microtask or event loop phase runs; the queue is never partially drained.
- **Promise microtask queue**: runs after the nextTick queue is empty, and the nextTick queue is checked and drained between each individual Promise callback, so a nextTick queued inside a `.then` always runs before the next `.then`.
- **Timers phase**: runs all `setTimeout`/`setInterval` callbacks whose delay has elapsed *as of the moment the phase begins* — new timers scheduled during this phase do not run until the next iteration.
- **Pending callbacks phase**: runs deferred I/O error callbacks from the previous iteration — specifically callbacks that libuv could not process in the poll phase.
- **Idle/prepare phase**: internal libuv bookkeeping; no JavaScript callbacks are ever directly executed here; invisible to application code.
- **Poll phase**: the only phase that can block — it processes available I/O completion events and blocks (waiting for more I/O) until either a `setImmediate` callback is pending, a timer has elapsed, or the process has no more async work.
- **Check phase**: runs all `setImmediate` callbacks registered since the last check phase; callbacks added inside a `setImmediate` run in the *next* check phase, not the current one.
- **Close callbacks phase**: runs `'close'` event callbacks for abruptly destroyed handles and streams; if none are pending, this phase is skipped and the iteration completes.

## Problem 2 — `process.nextTick` Starvation: Demonstration and Fix

### Problem

The following code intends to process items from a large array one at a time, yielding control back to the event loop between each item. Identify why it starves the event loop and rewrite it correctly.

```js
const items = Array.from({ length: 100_000 }, (_, i) => i);
let index = 0;

function processNext() {
  if (index >= items.length) {
    console.log('Done processing');
    return;
  }
  const item = items[index++];
  doWork(item);
  process.nextTick(processNext); // BUG: starves the event loop
}

processNext();

// This timer should fire every ~10ms but won't during starvation:
setInterval(() => console.log('health check'), 10);
```

### Pattern Recognition
nextTick recursion causes starvation because the nextTick queue drains completely (including newly queued items) before any phase runs. The fix: replace `process.nextTick` with `setImmediate` which only executes one batch per check phase, allowing I/O and timers to run between iterations.

### Key Insight
`process.nextTick(fn)` says "run fn before any I/O or timers, guaranteed." When `fn` itself calls `process.nextTick(fn)`, the loop never exits the nextTick drain — 100,000 iterations of `processNext` all run before the event loop can fire a single `setInterval` callback. `setImmediate(fn)` says "run fn in the next check phase" — each recursive call schedules work for a future iteration, allowing the event loop to run other callbacks between items.

### Solution

```js
const items = Array.from({ length: 100_000 }, (_, i) => i);
let index = 0;

// FIX 1: Use setImmediate — one callback per check phase
function processNextImmediate() {
  if (index >= items.length) { console.log('Done'); return; }
  const item = items[index++];
  doWork(item);
  setImmediate(processNextImmediate); // schedules for NEXT check phase
  // The event loop can run I/O, timers, and other callbacks between each call ✓
}

// FIX 2: Process in batches for better throughput (fewer context switches)
function processNextBatch(batchSize = 100) {
  const end = Math.min(index + batchSize, items.length);
  while (index < end) {
    doWork(items[index++]);
  }
  if (index < items.length) {
    setImmediate(() => processNextBatch(batchSize)); // next batch next iteration
  } else {
    console.log('Done');
  }
}

// FIX 3: Promise-based with explicit yield (for async/await pattern)
async function processAllAsync() {
  for (const item of items) {
    doWork(item);
    // Yield to event loop every N items:
    if (item % 100 === 0) {
      await new Promise(resolve => setImmediate(resolve));
    }
  }
  console.log('Done');
}
```

### Trace

```
BUGGY version (process.nextTick):
  t=0ms: processNext() → doWork(0) → nextTick(processNext)
  [nextTick drain: processes ALL 100,000 items before yielding]
  t=???ms: all items done, nextTick drain complete
  t=???ms: setInterval fires (100,000ms late!)

FIXED version (setImmediate):
  Iteration 1: check phase → processNextImmediate() → doWork(0)
    → schedules processNextImmediate for check phase of NEXT iteration
  [event loop continues: timers, poll, close, THEN next check phase]
  t=~1ms: setInterval fires ✓ (health check works!)
  Iteration 2: check phase → doWork(1) → schedules next...
  [~100,000 iterations spread across event loop iterations]

BATCHED version (most efficient):
  Iteration 1: check phase → doWork(0-99) [100 items]
    → schedules next batch for next check phase
  [event loop continues: health check fires ✓]
  Iteration 2: check phase → doWork(100-199) [100 items]
  ...
  Iterations: 1000 (not 100,000 context switches)
  Health check fires between each batch ✓
```

### Edge Cases
- `batchSize` tuning: too small → too many context switches; too large → blocks event loop during each batch. Typical sweet spot: 100–1000 items per batch depending on `doWork` cost.
- If `doWork` is async (returns a Promise): switch to the Promise-based approach; `setImmediate` with synchronous `doWork` only.

### Follow-up Questions
- "When IS `process.nextTick` appropriate for recursion?" — Never for unbounded recursion. For a bounded recursive call (e.g., "emit event then check state once"), nextTick is appropriate because it's a known, finite operation.
- "What does Node.js itself warn about?" — Node.js documentation explicitly warns against using `process.nextTick` recursively and recommends `setImmediate` for recursive async patterns.

## Problem 3 — `setTimeout(fn, 0)` vs `setImmediate` Race

### Problem

Implement a function `raceTest()` that demonstrates the non-determinism between `setTimeout(fn, 0)` and `setImmediate` at the top level, and a function `deterministicTest()` that shows why the order is always fixed inside an I/O callback. Run each 1000 times and report the distribution.

### Pattern Recognition
The race condition arises because the 1ms timer minimum interacts with Node.js startup and system scheduling unpredictably. The I/O context is deterministic because the event loop is already inside an iteration when the I/O callback fires.

### Key Insight
At the top level: the event loop's first timers-phase check either finds the 1ms timer expired (setTimeout wins) or not (setImmediate wins via check phase). The elapsed time since the script started is not under developer control. Inside I/O: the order through phases is structurally fixed — the event loop has already passed the timers phase when the poll phase fires the I/O callback; the next phases in sequence are check (setImmediate), then close, then the NEXT iteration's timers. setImmediate is structurally earlier.

### Solution

const fs = require('fs');

## Problem 4 — Event Loop Lag Monitor

### Problem

Implement `EventLoopMonitor` — a class that continuously measures event loop lag (the delay between when a timer is scheduled and when it actually fires), with configurable alert thresholds and aggregated statistics.

```js
const monitor = new EventLoopMonitor({ intervalMs: 100, alertThresholdMs: 50 });
monitor.on('lag', ({ lagMs, p50, p95, p99 }) => { /* ... */ });
monitor.on('alert', ({ lagMs }) => console.warn(`High lag: ${lagMs}ms!`));
monitor.start();
```

### Pattern Recognition
Measure lag by scheduling a timer for `t` ms in the future and measuring actual elapsed time. The difference between actual elapsed and expected elapsed is the event loop lag. Track a rolling window of measurements for percentile calculations.

### Key Insight
The measurement must use `process.hrtime.bigint()` for sub-millisecond precision (not `Date.now()`, which has 1ms resolution on some platforms). Calling `.unref()` on the interval timer prevents it from keeping the process alive — the monitor should not be the reason the process doesn't exit.

### Solution

```js
const EventEmitter = require('events');

class EventLoopMonitor extends EventEmitter {
  #intervalMs;
  #alertThresholdMs;
  #windowSize;
  #lagHistory = [];
  #timer = null;
  #running = false;

  constructor({ intervalMs = 100, alertThresholdMs = 50, windowSize = 100 } = {}) {
    super();
    this.#intervalMs      = intervalMs;
    this.#alertThresholdMs = alertThresholdMs;
    this.#windowSize      = windowSize;
  }

  start() {
    if (this.#running) return;
    this.#running = true;
    this.#schedule();
  }

  stop() {
    this.#running = false;
    if (this.#timer) { clearTimeout(this.#timer); this.#timer = null; }
  }

  #schedule() {
    const expected = this.#intervalMs;
    const scheduledAt = process.hrtime.bigint();

    this.#timer = setTimeout(() => {
      const firedAt = process.hrtime.bigint();
      const actualMs  = Number(firedAt - scheduledAt) / 1e6; // ns → ms
      const lagMs     = Math.max(0, actualMs - expected);    // excess over expected

      this.#record(lagMs);

      if (lagMs >= this.#alertThresholdMs) {
        this.emit('alert', { lagMs, timestamp: Date.now() });
      }

      this.emit('lag', {
        lagMs,
        ...this.#stats(),
      });

      if (this.#running) this.#schedule(); // reschedule
    }, expected);

    this.#timer.unref(); // don't keep process alive just for monitoring
  }

  #record(lagMs) {
    this.#lagHistory.push(lagMs);
    if (this.#lagHistory.length > this.#windowSize) {
      this.#lagHistory.shift(); // rolling window
    }
  }

  #stats() {
    const sorted = [...this.#lagHistory].sort((a, b) => a - b);
    const n = sorted.length;
    return {
      p50:  sorted[Math.floor(n * 0.50)] ?? 0,
      p95:  sorted[Math.floor(n * 0.95)] ?? 0,
      p99:  sorted[Math.floor(n * 0.99)] ?? 0,
      mean: sorted.reduce((a, b) => a + b, 0) / n || 0,
      max:  sorted[n - 1] ?? 0,
    };
  }

  get currentStats() { return this.#stats(); }
}

// Usage — detect CPU-blocking code:
const monitor = new EventLoopMonitor({ intervalMs: 100, alertThresholdMs: 50 });

monitor.on('lag', ({ lagMs, p99 }) => {
  if (lagMs > 10) console.log(`Lag: ${lagMs.toFixed(1)}ms | p99: ${p99.toFixed(1)}ms`);
});

monitor.on('alert', ({ lagMs }) => {
  console.error(`⚠️  Event loop blocked for ${lagMs.toFixed(1)}ms`);
  // In production: send to metrics system (DataDog, Prometheus, etc.)
});

monitor.start();

// Demonstrate detection:
setTimeout(() => {
  // Simulate blocking work — monitor will detect ~200ms lag:
  const end = Date.now() + 200;
  while (Date.now() < end) {} // 200ms sync block
}, 500);
```

### Trace

```
t=0ms:   monitor.start() → schedules measurement timer for t=100ms
t=100ms: timer fires:
  firedAt - scheduledAt ≈ 100ms → lagMs ≈ 0ms. Normal. Emit 'lag'.
  Schedule next measurement for t=200ms.

t=200ms: fires ≈ 100ms later → lagMs ≈ 0ms. Normal.
...
t=500ms: blocking code starts. While loop runs for 200ms.
  During 200ms: event loop CANNOT fire ANY callbacks.

t=600ms: measurement timer was due at t=600ms.
  Event loop was blocked until t=700ms.
  firedAt - scheduledAt = 200ms → lagMs = 200ms - 100ms = 100ms!
  Emit 'alert' with lagMs=100ms.

t=700ms: blocking code ends, event loop unblocks.
  Late measurement fires immediately.
```

### Edge Cases
- `.unref()` is essential — a monitoring timer that prevents process exit defeats the purpose.
- `Math.max(0, ...)` prevents negative lag (impossible but guards against clock jitter).
- Rolling window prevents unbounded memory growth for long-running processes.

### Follow-up Questions
- "How does Node.js's built-in `perf_hooks.monitorEventLoopDelay()` differ?" — It uses a histogram API sampling at 1ms resolution, tracking lag directly inside libuv — more accurate than the timer approach. Available since Node.js 11.10.
- "What lag threshold is considered dangerous in production?" — >10ms is notable; >50ms will cause user-visible latency in web servers; >100ms is a significant problem that warrants immediate investigation.

## Problem 5 — Poll Phase and Timer Precision

### Problem

Demonstrate how the poll phase's I/O blocking affects timer precision, and implement a `precisionTest()` that quantifies the accuracy of `setTimeout(fn, delay)` across different I/O loads.

### Pattern Recognition
Timers can only fire when the event loop reaches the timers phase. If the poll phase is waiting for I/O (blocking), timers are delayed until I/O arrives or the poll timeout expires. Show that heavy I/O load increases timer jitter.

### Key Insight
The poll phase's blocking timeout is `min(timeUntilNextTimer, maxPollTimeout)`. This means: if a timer fires in 50ms and the poll phase starts blocking now, poll will block for at most 50ms — then exit to let the timer phase run. However, if many short I/O callbacks arrive during that 50ms, the poll phase is occupied running those callbacks and may accumulate delay before the timer phase gets a turn.

### Solution

```js
const fs = require('fs');
const { promisify } = require('util');

async function timerPrecisionTest() {
  const measurements = [];

  // Test 1: Low I/O load — timers should be relatively precise
  console.log('=== Low I/O Load ===');
  for (let i = 0; i < 10; i++) {
    const delay = 50;
    const start = process.hrtime.bigint();
    await new Promise(resolve => setTimeout(resolve, delay));
    const actual = Number(process.hrtime.bigint() - start) / 1e6;
    measurements.push(actual - delay);
    console.log(`  Expected: ${delay}ms, Actual: ${actual.toFixed(2)}ms, Jitter: +${(actual-delay).toFixed(2)}ms`);
  }

  // Test 2: High I/O load — I/O callbacks compete with timers
  console.log('\n=== High I/O Load (concurrent file reads) ===');
  const ioMeasurements = [];

  for (let i = 0; i < 10; i++) {
    const delay = 50;
    const start = process.hrtime.bigint();

    // Schedule many concurrent I/O operations (saturates thread pool):
    const ioOps = Array.from({ length: 50 }, () =>
      fs.promises.readFile(process.execPath) // read same large file 50 times
    );

    // Timer scheduled alongside I/O load:
    await new Promise(resolve => setTimeout(resolve, delay));
    const actual = Number(process.hrtime.bigint() - start) / 1e6;

    // Wait for all I/O to complete:
    await Promise.all(ioOps);

    ioMeasurements.push(actual - delay);
    console.log(`  Expected: ${delay}ms, Actual: ${actual.toFixed(2)}ms, Jitter: +${(actual-delay).toFixed(2)}ms`);
  }

  const avgLow = measurements.reduce((a, b) => a + b, 0) / measurements.length;
  const avgHigh = ioMeasurements.reduce((a, b) => a + b, 0) / ioMeasurements.length;
  console.log(`\nAverage jitter — Low I/O: ${avgLow.toFixed(2)}ms, High I/O: ${avgHigh.toFixed(2)}ms`);
  // High I/O average jitter is typically 2-10x higher than low I/O
}

timerPrecisionTest();
```

### Trace

```

t=0ms:    setTimeout(fn, 50) scheduled. timer threshold = t+50ms
t=0ms:    poll phase blocks (nothing else to do)
          poll timeout = min(50ms, ∞) = 50ms
t=50ms:   poll timeout expires → poll exits
t=50ms:   event loop wraps to timers phase
t=50ms:   fn() fires. Jitter ≈ 0.1ms (just phase transition overhead)

Under high I/O load:

t=0ms:    poll phase: 4 thread pool workers start working on readFiles
t=0ms:    poll blocks. Some readFiles complete...
t=5ms:    3 readFiles complete → poll processes their callbacks (takes ~1ms)
t=10ms:   more readFiles complete → poll processes callbacks
...
t=50ms:   poll has been BUSY processing I/O callbacks
          event loop reaches timers phase AFTER processing I/O backlog
t=52ms:   fn() fires. Jitter ≈ 2ms (poll was occupied with I/O)
          (This varies: heavy I/O can cause 5-20ms timer jitter)
```

### Key Insight from Results
The poll phase has a "greedy" behavior — when I/O events arrive, it processes them. The timer threshold is only rechecked when poll becomes idle. Heavy concurrent I/O can delay timers by preventing the event loop from reaching the timers phase promptly.

### Follow-up Questions
- "How does `libuv` prevent timers from being delayed indefinitely by I/O?" — The poll timeout is clamped to `min(timeUntilNextTimer, UV_MAX_TIMEOUT)`. When the next timer is due, poll will exit even if more I/O is available.
- "What is `UV_THREADPOOL_SIZE` and how does it affect this?" — Increasing the thread pool size completes I/O faster, reducing poll phase time, potentially improving timer precision under heavy I/O.

## Problem 6 — Batch Processor Using `setImmediate`

### Problem

Implement a `BatchProcessor<T>` that accepts items and processes them in batches, yielding to the event loop between each batch using `setImmediate`. The processor should support a maximum batch size and a callback when all items are processed.

```js
const processor = new BatchProcessor({
  batchSize: 100,
  processor: (items) => items.map(x => x * 2),
  onComplete: (results) => console.log('Done:', results.length),
});

for (let i = 0; i < 10_000; i++) processor.add(i);
processor.flush(); // begin processing
```

### Pattern Recognition
Recursive `setImmediate` for event-loop-friendly iteration. The key property of `setImmediate`: exactly one callback per check phase, allowing the timers, pending callbacks, and poll phases to run between batches.

### Key Insight
`setImmediate` creates a "cooperative multitasking" pattern — each batch runs in one check phase, then the processor yields, allowing other work (HTTP requests, timers, health checks) to run before the next batch. This prevents the processor from monopolizing the event loop while still making progress.

### Solution

```js
class BatchProcessor {
  #queue = [];
  #results = [];
  #processing = false;
  #batchSize;
  #processorFn;
  #onComplete;

  constructor({ batchSize = 100, processor, onComplete = () => {} }) {
    this.#batchSize    = batchSize;
    this.#processorFn  = processor;
    this.#onComplete   = onComplete;
  }

  add(item) {
    this.#queue.push(item);
  }

  flush() {
    if (this.#processing) return; // already running
    this.#processing = true;
    this.#scheduleNextBatch();
  }

  #scheduleNextBatch() {
    // Use setImmediate — NOT process.nextTick (would starve event loop)
    // NOT setTimeout(fn, 0) — adds unnecessary ~1ms delay between each batch
    setImmediate(() => this.#processBatch());
  }

  #processBatch() {
    if (this.#queue.length === 0) {
      // All items processed:
      this.#processing = false;
      this.#onComplete(this.#results);
      return;
    }

    // Take up to batchSize items from the front of the queue:
    const batch = this.#queue.splice(0, this.#batchSize);

    // Process synchronously within this check phase:
    const batchResults = this.#processorFn(batch);
    this.#results.push(...batchResults);

    // Yield to event loop via setImmediate:
    this.#scheduleNextBatch();
    // The event loop will run timers, poll (I/O), and then come back to check phase
  }

  get progress() {
    return {
      processed: this.#results.length,
      remaining: this.#queue.length,
    };
  }
}

// Usage with monitoring:
const processor = new BatchProcessor({
  batchSize: 100,
  processor: (items) => items.map(x => x * x),
  onComplete: (results) => {
    console.log(`Processed ${results.length} items`);
    console.log('First 5:', results.slice(0, 5));
  },
});

for (let i = 0; i < 10_000; i++) processor.add(i);

// Health check — WILL fire between batches (unlike with nextTick):
setInterval(() => {
  const { processed, remaining } = processor.progress;
  console.log(`Progress: ${processed} done, ${remaining} remaining`);
}, 50);

processor.flush();
```

### Trace

```
t=0ms:   10,000 items added. flush() called.
         setImmediate(processBatch) scheduled for check phase.
         setInterval(health check, 50ms) scheduled for timers phase.

Iteration 1:
  Timers: setInterval not due yet (0ms < 50ms)
  Poll:   nothing to poll; setImmediate pending → exit immediately
  Check:  processBatch() runs:
    - Takes items 0-99. Processes synchronously. ~0.5ms
    - schedules setImmediate(processBatch) for next check phase
  nextTick + microtasks: nothing pending

Iteration 2: (same structure)
  Check: items 100-199 processed

...

Iteration ~50:
  t=50ms: setInterval becomes due
  Timers: 'Progress: 5000 done, 5000 remaining' ← health check fires ✓
  Poll → Check: next batch runs

...

Iteration 100:
  Check: items 9900-9999 processed. queue empty.
  onComplete fires: 'Processed 10000 items'

Result: health check fires ~20 times during processing ✓
With nextTick: health check would fire 0 times until all 10,000 done ✗
```

### Edge Cases
- `splice(0, batchSize)` modifies the queue in-place and returns the removed items — O(n) for large queues (shifting the array). For performance with very large queues, use a linked list or index-based approach instead of `splice`.
- If `processorFn` itself is async (returns a Promise), this pattern needs to `await` it before scheduling the next batch — add `async #processBatch()` and `await this.#processorFn(batch)`.

### Follow-up Questions
- "Why not `setTimeout(fn, 0)` instead of `setImmediate`?" — Each batch would incur a ~1ms delay, turning 100 batches (for 10,000 items) into ~100ms of artificial delay. `setImmediate` is immediate relative to the current event loop, only yielding for poll-phase work, not adding timer delay.
- "How would you add priority queuing?" — Maintain multiple queues with different priorities; in `#processBatch`, first drain the high-priority queue's batch, then normal, then low.

## Problem 7 — Async Scheduler with Microtask Awareness

### Problem

Implement a `Scheduler` class that runs tasks with configurable execution contexts — some tasks need to run "as soon as possible" (nextTick), some need to run "after current I/O" (setImmediate), and some need to run "after a delay" (setTimeout). The scheduler tracks total execution time and demonstrates each context's timing.

```js
const scheduler = new Scheduler();
scheduler.schedule('task-A', { context: 'nextTick' });
scheduler.schedule('task-B', { context: 'immediate' });
scheduler.schedule('task-C', { context: 'timeout', delay: 0 });
scheduler.schedule('task-D', { context: 'timeout', delay: 100 });
scheduler.run();
```

### Pattern Recognition
Factory function routing to the correct scheduling mechanism. Each mechanism represents a different event loop position. Tracking execution order exposes the event loop's actual behavior.

### Key Insight
A scheduler that abstracts over these timing mechanisms reveals the event loop's priority hierarchy through the order in which tasks execute. Adding a `Promise`-based `schedule` shows that Promise microtasks (after nextTick) run between event loop phases.

### Solution

```js
class Scheduler extends EventEmitter {
  #tasks = [];
  #startTime = BigInt(0);
  #executed = [];

  schedule(name, { context = 'immediate', delay = 0, fn = null } = {}) {
    this.#tasks.push({ name, context, delay, fn: fn ?? (() => {}) });
    return this;
  }

  run() {
    this.#startTime = process.hrtime.bigint();
    this.emit('start');

    for (const task of this.#tasks) {
      this.#dispatch(task);
    }
  }

  #dispatch({ name, context, delay, fn }) {
    const record = (label) => {
      const elapsed = Number(process.hrtime.bigint() - this.#startTime) / 1e6;
      this.#executed.push({ name: label, elapsedMs: elapsed.toFixed(2) });
      console.log(`[${elapsed.toFixed(2)}ms] ${label} executed`);
      fn();
    };

    switch (context) {
      case 'nextTick':
        process.nextTick(() => record(`${name} [nextTick]`));
        break;

      case 'promise':
        Promise.resolve().then(() => record(`${name} [promise]`));
        break;

      case 'immediate':
        setImmediate(() => record(`${name} [setImmediate]`));
        break;

      case 'timeout':
        setTimeout(() => record(`${name} [setTimeout(${delay})]`), delay);
        break;

      default:
        throw new Error(`Unknown context: ${context}`);
    }
  }

  report() {
    return this.#executed;
  }
}

// Demonstration:
const scheduler = new Scheduler();
console.log('[0ms] Scheduling tasks...');

scheduler
  .schedule('alpha',   { context: 'timeout',   delay: 0 })
  .schedule('beta',    { context: 'immediate' })
  .schedule('gamma',   { context: 'nextTick' })
  .schedule('delta',   { context: 'promise' })
  .schedule('epsilon', { context: 'nextTick' })
  .schedule('zeta',    { context: 'timeout',   delay: 50 })
  .run();

console.log('[sync] All tasks scheduled, sync code done');
```

### Trace

```
Synchronous execution:
  [0.00ms] Scheduling tasks...
  [sync] All tasks scheduled, sync code done  ← call stack empties

Microtask drain (before event loop):
  [0.12ms] gamma [nextTick]    ← nextTick queue: gamma, epsilon
  [0.13ms] epsilon [nextTick]  ← nextTick queue drains both
  [0.14ms] delta [promise]     ← promise microtask queue

Event loop begins:

  Timers phase (is 1ms elapsed?):
    Case: 1ms elapsed:
      [1.05ms] alpha [setTimeout(0)]
    Case: not elapsed:
      alpha deferred

  Poll phase:
    beta [setImmediate] pending → exit poll immediately (no blocking)

  Check phase:
    [1.10ms] beta [setImmediate]

  (Next iteration if alpha was deferred):
    [1.15ms] alpha [setTimeout(0)]

  Timers phase 2:
    Not yet: 50ms not elapsed

  ... (event loop continues until 50ms mark)

  Timers phase (t≈50ms):
    [50.20ms] zeta [setTimeout(50)]

Final execution order (most common):
  0.12ms - gamma [nextTick]         ← 1st: nextTick
  0.13ms - epsilon [nextTick]       ← 2nd: nextTick
  0.14ms - delta [promise]          ← 3rd: promise microtask
  1.05ms - alpha [setTimeout(0)]    ← 4th or 5th: timer (non-deterministic with beta)
  1.10ms - beta [setImmediate]      ← 4th or 5th: check phase

```

### Edge Cases
- `gamma` (nextTick) always before `delta` (promise) regardless of scheduling order — nextTick wins.
- `alpha` (setTimeout 0) vs `beta` (setImmediate) — non-deterministic at top level.
- If `fn` inside a task calls `scheduler.schedule(...)`, new tasks are dispatched from within event loop callbacks — they correctly queue for their respective mechanisms.

### Follow-up Questions
- "How would you add task cancellation?" — Store the return value of `setTimeout`/`setImmediate` in a Map keyed by task name; add a `cancel(name)` method that calls `clearTimeout`/`clearImmediate`.
- "How would you enforce task ordering (task B only after task A)?" — Chain them: task A's `fn` schedules task B when done, rather than scheduling both upfront.

## Quick Reference — Event Loop Decision Tree

```
Which async mechanism should you use?
│
├── NEED TO RUN CODE SYNCHRONOUSLY AFTER CURRENT CODE?
│   └── Can't — nothing runs synchronously unless you call it.
│       Closest: process.nextTick — runs before any I/O or timers.
│
├── NEED CODE TO RUN BEFORE ANY I/O OR TIMER FIRES?
│   └── process.nextTick
│       - Runs in same nextTick drain (including nested nextTick calls)
│       - Higher priority than Promise.then
│       - WARNING: recursive nextTick starves the event loop
│       - Use for: API async consistency, error propagation, DI bootstrap
│
├── NEED CODE TO RUN AFTER CURRENT SYNC BUT BEFORE EVENT LOOP PHASES?
│   └── Promise.resolve().then(fn) or queueMicrotask(fn)
│       - Runs after nextTick queue empties
│       - nextTick is checked between each Promise callback
│       - Use for: async/await continuations, promise chains
│
├── NEED CODE TO RUN AFTER CURRENT I/O POLL PHASE?
│   └── setImmediate
│       - Always runs BEFORE next iteration's timers
│       - Inside I/O callback: GUARANTEED before setTimeout(0)
│       - Safe for recursion (one per check phase, I/O can run between)
│       - Use for: batch processing, recursive async loops, post-I/O work
│
├── NEED CODE TO RUN AFTER A MINIMUM DELAY?
│   └── setTimeout(fn, delay)
│       - Minimum delay is 1ms (delay=0 becomes 1ms)
│       - NOT guaranteed exact — timer phase might be delayed by I/O
│       - At top level: non-deterministic vs setImmediate
│       - Use for: actual time delays, debouncing, retry with delay
│
├── NEED RECURRING EXECUTION?
│   ├── Fixed interval: setInterval(fn, delay) — may drift under load
│   └── Tight loop that yields to event loop: setImmediate recursion
│       (safer than setInterval for CPU-bound work that should not stack)
│
├── NEED TO AVOID BLOCKING THE EVENT LOOP?
│   ├── Break sync work into chunks with setImmediate between chunks
│   ├── Offload CPU work to Worker threads
│   └── Use async I/O (never sync I/O methods: readFileSync, execSync)
│
└── PRIORITY ORDERING (highest to lowest):
    1. Synchronous code (call stack)
    2. process.nextTick (drains completely, including nested)
    3. Promise microtasks (nextTick between each)
    4a. setTimeout/setInterval (timers phase)
    4b. I/O callbacks (poll phase)
    4c. setImmediate (check phase)
    4d. close callbacks
    Note: 4a-4d order depends on event loop position and timing
```

## Common Bugs Checklist

Before shipping any async Node.js code, verify:

1. **Recursive `process.nextTick` starving the event loop?** — Any function that calls `process.nextTick(itself)` recursively prevents I/O callbacks, timers, and `setImmediate` from ever running. The nextTick drain processes all queued callbacks including newly-added ones before exiting. Always replace recursive `process.nextTick` with `setImmediate` for iteration patterns. A quick check: if a health check `setInterval` stops firing, you likely have a nextTick loop somewhere.

2. **Assuming `setTimeout(fn, 0)` fires immediately after the current operation?** — `setTimeout(fn, 0)` has a minimum delay of 1ms plus any time the event loop spends in the poll phase or processing other callbacks. Inside I/O callbacks, `setImmediate` is more appropriate for "run after current I/O" semantics. `setTimeout(fn, 0)` is not a substitute for `process.nextTick` or `setImmediate` — all three have different semantics and positions in the event loop.

3. **Depending on the order of `setTimeout(fn, 0)` and `setImmediate` at the top level?** — The ordering between these two is non-deterministic outside of I/O callbacks. Code that assumes "setImmediate always runs before setTimeout(0)" or vice versa at the module's top level will have intermittent ordering bugs. If ordering matters, place both inside an I/O callback (where setImmediate is guaranteed first), or use `process.nextTick` / Promise chains for guaranteed ordering.

4. **Blocking the event loop with synchronous operations?** — `fs.readFileSync`, `crypto.pbkdf2Sync`, JSON parsing of large payloads, complex regular expressions, and long-running computations all block the event loop. During a 100ms synchronous block, all incoming HTTP requests queue up, all timers drift by 100ms, and no I/O callbacks can fire. Use async APIs or Worker threads for any operation that takes more than a few milliseconds.

5. **Expecting `process.nextTick` inside a Promise to run before the current Promise chain continues?** — A `process.nextTick` queued inside a Promise `.then` callback runs before the *next* `.then` (because nextTick is drained between each microtask), but it does NOT interrupt the current `.then` callback's execution. The current `.then` runs to completion first, then nextTick queue drains, then the next `.then` runs. This ordering (nextTick between Promise callbacks) is sometimes surprising when debugging output order.

6. **Not calling `.unref()` on monitoring timers/intervals?** — A `setInterval` or `setTimeout` that's only for monitoring purposes will prevent the Node.js process from exiting normally, because active timer handles keep the event loop alive. Always call `.unref()` on monitoring, health-check, or keep-alive timers: `timer.unref()`. The timer still fires if the event loop is otherwise busy, but it won't prevent exit when no other work is pending.

7. **Misunderstanding that close callbacks and 'close' events fire immediately on `.destroy()`?** — When you call `socket.destroy()`, the 'close' event doesn't fire synchronously — it fires in the close callbacks phase of the *next* event loop iteration. Code that checks state immediately after `.destroy()` will run before the close callback. Use `socket.on('close', cb)` to react to the actual close, not code after the `.destroy()` call.

8. **Node.js v11+ microtask timing assumptions in shared codebase?** — If your code runs on both Node.js < v11 and >= v11, the ordering of microtasks relative to timer callbacks differs. Pre-v11: all timer callbacks in a phase ran before any microtasks; v11+: microtasks run between each individual timer callback. Code that depends on "all setTimeout callbacks complete before any Promise.then runs" will behave differently across versions.

9. **Assuming the thread pool size is unlimited?** — The default `UV_THREADPOOL_SIZE` is 4. If your application makes 10 concurrent `fs.readFile` calls, 6 of them queue behind the 4 active threads. Heavy file I/O or `crypto.pbkdf2` (which uses the thread pool) under concurrency can create a bottleneck. Increase `UV_THREADPOOL_SIZE` via environment variable for CPU-heavy crypto operations, or use Worker threads for true parallelism.

10. **Thinking the event loop exits immediately when async work is done?** — The event loop exits only when its **reference count** drops to zero — when there are no more active handles (servers, timers, open files) or requests (pending I/O). A `setInterval` with no `.unref()` keeps the process alive forever. Calling `server.close()` stops accepting new connections but doesn't forcefully close existing ones — the process won't exit until existing connections close. Use `server.closeAllConnections()` (Node.js 18.2+) or track connections manually for graceful shutdown.

---

**Final Tip:** At the 5 YOE level, the decisive signal for event loop questions is naming *the specific mechanism each async tool uses to position itself in the loop* — not just "it's async." For `process.nextTick`: *"it's not a phase — it's a queue that drains after every C++-to-JavaScript transition, including between each individual callback in Node.js v11+; because the drain processes all pending callbacks (including newly queued ones), any recursion starves the loop."* For `setImmediate`: *"it fires in the check phase — specifically after the poll phase which processes I/O, which is why inside an I/O callback setImmediate is guaranteed to run before the next iteration's timers phase."* For the poll phase: *"it's the only phase that can block — when nothing is immediately available it blocks for exactly `min(timeUntilNextTimer, ∞)` milliseconds, which is why a timer always eventually fires even if the poll phase was blocking: libuv calculates the maximum block duration from the timer heap."* And for output ordering questions: *"always drain the call stack first, then nextTick completely (including any nextTick queued during the drain), then Promise microtasks (with nextTick checks between each), then enter the phases in order — and in v11+, repeat the nextTick + microtask drain after every individual callback within every phase."*
