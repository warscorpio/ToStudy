# Node.js: Single-Threaded Nature and Why It's Still Scalable — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does it mean that Node.js is "single-threaded," and what exactly runs on that single thread?**

A: Node.js runs JavaScript on a single thread — the **main thread** — powered by the V8 JavaScript engine. All JavaScript code you write, including business logic, callbacks, event listeners, and Promises, executes on this one thread sequentially. There is no parallelism for JavaScript code itself.

But "single-threaded" is a simplification. The Node.js runtime is not entirely single-threaded:

```
┌─────────────────────────────────────────────────────┐
│                  Node.js Process                    │
│                                                     │
│  ┌──────────────┐     ┌───────────────────────────┐ │
│  │  Main Thread │     │     libuv Thread Pool     │ │
│  │  (V8 + JS)   │     │  (4 threads by default)   │ │
│  │              │────▶│  - File I/O               │ │
│  │  Event Loop  │     │  - DNS lookups            │ │
│  │  runs here   │◀────│  - crypto (some ops)      │ │
│  │              │     │  - zlib compression        │ │
│  └──────────────┘     └───────────────────────────┘ │
│                                                     │
│  ┌───────────────────────────────────────────────┐  │
│  │         OS Kernel (async I/O)                 │  │
│  │  - Network I/O (TCP/UDP)                      │  │
│  │  - Timers (managed by OS)                     │  │
│  └───────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

What runs on the single thread:
- All JavaScript code
- The **Event Loop** (the scheduler that decides what JS runs next)
- V8 garbage collection (mostly, with some concurrent phases)

What does NOT run on the single thread:
- File system I/O — offloaded to **libuv's thread pool**
- Network I/O — handled by the **OS kernel** via epoll/kqueue/IOCP
- DNS resolution — libuv thread pool
- Certain crypto operations — libuv thread pool

This distinction is critical: the main thread is never blocked waiting for I/O; it only runs JS while I/O happens elsewhere.

**Q2. What is the Event Loop and how does it work?**

A: The Event Loop is the mechanism that allows Node.js to perform non-blocking I/O despite being single-threaded. It's a continuous loop that picks up completed tasks and executes their callbacks on the main thread.

The Event Loop has **six phases**, each with its own queue:

```
   ┌─────────────────────────────────┐
   │           timers                │  ← setTimeout, setInterval callbacks
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │       pending callbacks         │  ← I/O callbacks deferred from prev iteration
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │          idle, prepare          │  ← Internal use only
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │            poll                 │  ← Fetch new I/O events; execute I/O callbacks
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │            check                │  ← setImmediate callbacks
   └────────────────┬────────────────┘
                    │
   ┌────────────────▼────────────────┐
   │        close callbacks          │  ← socket.on('close', ...)
   └────────────────┬────────────────┘
                    │
        (back to timers if more work)
```

Between each phase transition, Node.js drains two **microtask queues** (highest priority):
1. `process.nextTick()` queue — drained completely before moving on
2. Promise microtask queue (`then`, `catch`, `finally`, `await` continuations)

```javascript
setTimeout(() => console.log('1: setTimeout'), 0);
setImmediate(() => console.log('2: setImmediate'));
Promise.resolve().then(() => console.log('3: Promise'));
process.nextTick(() => console.log('4: nextTick'));
console.log('5: sync');

// Output order:
// 5: sync              ← synchronous, runs immediately
// 4: nextTick          ← nextTick queue drained first
// 3: Promise           ← Promise microtask queue
// 1: setTimeout        ← timers phase (0ms ≈ ~1ms actual minimum)
// 2: setImmediate      ← check phase
```

The key insight: the main thread is **never idly waiting**. When there's no JS to run, the Event Loop blocks in the **poll phase** waiting for the OS to signal I/O completion. The moment an I/O event arrives, it queues the callback and the main thread picks it up.

**Q3. What is the difference between blocking and non-blocking I/O, and why does this distinction make Node.js scalable?**

A: The core difference is where the CPU waits:

**Blocking I/O** (traditional thread-per-request model):
```
Thread 1: [JS] → [waiting for DB...........] → [JS continues]
Thread 2: [JS] → [waiting for file.......] → [JS continues]
Thread 3: [JS] → [waiting for HTTP.........] → [JS continues]
```
Each thread is parked (blocked) while waiting. Handling 10,000 concurrent connections means 10,000 threads — which means:
- ~8MB stack memory per thread → 80GB RAM for 10k threads
- Context-switching overhead between threads
- OS scheduling pressure

**Non-blocking I/O** (Node.js Event Loop model):
```
Main Thread: [JS]→[req I/O]→[JS]→[req I/O]→[JS]→[handle completion]→[JS]...
                      ↓              ↓
                 OS handles      OS handles
                 in background   in background
```
One thread handles 10,000 concurrent connections because it never sits idle waiting. The OS (via epoll on Linux, kqueue on macOS, IOCP on Windows) multiplexes thousands of I/O operations and notifies Node.js when each completes.

```javascript
// Blocking (hypothetical — never do this in Node.js):
const data = fs.readFileSync('large-file.txt'); // Thread stops here
processData(data); // Runs only after file is fully read

// Non-blocking (correct Node.js pattern):
fs.readFile('large-file.txt', (err, data) => {
    processData(data); // Runs when OS signals file read is complete
});
// Event Loop is free to handle other requests while file is being read
handleOtherRequests(); // Runs immediately, doesn't wait for file
```

For I/O-bound workloads (web servers, API gateways, database-heavy apps), most time is spent waiting for I/O — not executing CPU-intensive JS. The Event Loop turns this wait time into productive time processing other requests.

## Section 2: The Thread Pool and libuv

**Q4. What is libuv and what role does its thread pool play?**

A: **libuv** is the C library that powers Node.js's async I/O. It provides:
- The Event Loop implementation
- Async TCP and UDP sockets
- Async DNS resolution
- Async file system operations
- A **thread pool** for operations that can't be done asynchronously by the OS

The thread pool is libuv's escape hatch for operations that don't have async kernel APIs. It runs **4 threads by default** (configurable via `UV_THREADPOOL_SIZE`, max 1024):

```javascript
// Operations that use the libuv thread pool:
fs.readFile(...)         // File I/O
fs.stat(...)             // File metadata
dns.lookup(...)          // DNS (NOT dns.resolve — that uses kernel async DNS)
crypto.pbkdf2(...)       // Expensive key derivation
crypto.scrypt(...)       // Another expensive hash
zlib.gzip(...)           // Compression

// Operations handled by OS kernel (NOT thread pool):
http.get(...)            // Network I/O — OS epoll/kqueue
net.createServer(...)    // TCP server — OS async
setTimeout(...)          // Timer — OS timer facility
```

The thread pool distinction matters in practice:

```javascript
// This can bottleneck under load — thread pool has only 4 threads by default
// 5 concurrent pbkdf2 calls: first 4 run in parallel, 5th waits for a thread
async function hashPassword(password: string): Promise<string> {
    return new Promise((resolve, reject) => {
        crypto.pbkdf2(password, salt, 100000, 64, 'sha512', (err, key) => {
            if (err) reject(err);
            else resolve(key.toString('hex'));
        });
    });
}

// Monitor thread pool pressure:
// UV_THREADPOOL_SIZE=16 node server.js  ← increase for crypto/fs-heavy apps
```

A common interview gotcha: if you benchmark `fs.readFile` and find it doesn't scale past 4 concurrent reads — you've hit the thread pool limit, not the Event Loop.

**Q5. What kinds of I/O bypass the thread pool entirely?**

A: Network I/O bypasses the thread pool because modern operating systems provide native asynchronous APIs for it:

| Operation | Mechanism | Thread Pool? |
|---|---|---|
| TCP/UDP reads and writes | OS epoll / kqueue / IOCP | No |
| HTTP requests (client) | OS async sockets | No |
| HTTP server connections | OS async sockets | No |
| File reads/writes | libuv thread pool | Yes |
| `dns.lookup()` | libuv thread pool | Yes |
| `dns.resolve()` | OS async DNS (c-ares) | No |
| `crypto.pbkdf2()` | libuv thread pool | Yes |
| `crypto.randomBytes()` | libuv thread pool (sometimes) | Yes |
| `setTimeout` / `setInterval` | OS timer APIs | No |

The implication: a Node.js web server handling 10,000 HTTP connections uses **zero thread pool threads** for those connections — pure kernel async I/O. The thread pool is only engaged for specific file system and crypto operations.

## Section 3: Why Scalability Works in Practice

**Q6. How does the C10K problem relate to Node.js, and how does Node.js solve it?**

A: The **C10K problem** (coined by Dan Kegel in 1999) asks: how do you handle 10,000 concurrent connections on a single server? Traditional Apache-style thread-per-connection models failed because:

- 10,000 threads × 8MB stack = ~80GB RAM just for thread stacks
- Context switching between 10,000 threads creates enormous CPU overhead
- Most threads are parked waiting for I/O, wasting resources

Node.js solves C10K with the **Reactor pattern**: a single thread drives an event loop backed by the OS's I/O multiplexing facility (epoll on Linux). The OS can watch thousands of file descriptors for readiness and notify Node.js when any becomes ready — in a single system call.

```javascript
// What Node.js looks like to the OS:
// One process, one active thread, but the OS tracks thousands of connections
const server = http.createServer((req, res) => {
    // This callback runs on the main thread
    // But the OS was watching this connection for data in the background
    db.query('SELECT * FROM users WHERE id = ?', [req.params.id], (err, rows) => {
        // While the DB query ran, the main thread handled other requests
        res.json(rows);
    });
});

server.listen(3000);
// At this point, OS epoll watches port 3000
// Each incoming connection gets a file descriptor
// OS notifies Node.js (via Event Loop poll phase) when data arrives on any fd
```

Real-world numbers: a single Node.js process has been demonstrated handling 600,000+ concurrent WebSocket connections on commodity hardware — impossible with a thread-per-connection model.

**Q7. Where does the single-thread model break down? What are CPU-bound limitations?**

A: The Event Loop is a liability for **CPU-bound work**. If your JavaScript takes a long time to execute (without yielding), it blocks every other request:

```javascript
// BLOCKING — this freezes the entire server for every request
app.get('/calculate', (req, res) => {
    let result = 0;
    for (let i = 0; i < 10_000_000_000; i++) {
        result += Math.sqrt(i); // CPU-intensive — main thread is stuck here
    }
    // While this runs, NO other request can be processed
    // All concurrent connections are frozen waiting
    res.json({ result });
});

// Impact:
// Request A hits /calculate → takes 8 seconds
// Request B hits /health   → should return instantly
// Request B actually waits 8 seconds because the Event Loop is blocked
```

The rule of thumb: **any synchronous JS that takes >10ms is a problem** in a latency-sensitive server. Common CPU-bound culprits:
- Image manipulation in pure JS
- Complex cryptographic operations
- Large JSON serialization (`JSON.stringify` on 50MB objects)
- Heavy templating / server-side rendering
- Fibonacci, sorting, prime generation — toy examples of real patterns

Solutions (in order of preference):

```javascript
// 1. Use Worker Threads for CPU-bound tasks (Node.js 12+)
import { Worker, isMainThread, parentPort, workerData } from 'worker_threads';

if (isMainThread) {
    app.get('/calculate', (req, res) => {
        const worker = new Worker(__filename, {
            workerData: { iterations: 10_000_000_000 }
        });
        worker.on('message', result => res.json({ result }));
        worker.on('error', err => res.status(500).json({ error: err.message }));
    });
} else {
    // Runs in a separate thread — main thread stays free
    let result = 0;
    for (let i = 0; i < workerData.iterations; i++) {
        result += Math.sqrt(i);
    }
    parentPort!.postMessage(result);
}

// 2. Break work into chunks with setImmediate (yields to Event Loop between chunks)
function chunkedWork(data: number[], res: Response) {
    let i = 0;
    let result = 0;

    function doChunk() {
        const end = Math.min(i + 10_000, data.length);
        while (i < end) {
            result += Math.sqrt(data[i++]);
        }
        if (i < data.length) {
            setImmediate(doChunk); // Yield — allow other callbacks to run
        } else {
            res.json({ result });
        }
    }
    doChunk();
}

// 3. Delegate to a separate microservice or native addon
// Heavy computation → dedicated Python/Go service called via HTTP/gRPC
```

**Q8. How does Node.js clustering allow you to use multiple CPU cores?**

A: A single Node.js process only uses one CPU core. The `cluster` module (and the higher-level `pm2`) solves this by forking multiple worker processes that all share the same port:

```javascript
import cluster from 'cluster';
import os from 'os';
import http from 'http';

if (cluster.isPrimary) {
    const numCPUs = os.cpus().length;
    console.log(`Primary ${process.pid} running — spawning ${numCPUs} workers`);

    for (let i = 0; i < numCPUs; i++) {
        cluster.fork(); // Each worker is a full Node.js process
    }

    cluster.on('exit', (worker, code, signal) => {
        console.log(`Worker ${worker.process.pid} died (${signal || code}). Restarting...`);
        cluster.fork(); // Automatically restart dead workers
    });

} else {
    // Worker processes share the TCP connection
    http.createServer((req, res) => {
        res.writeHead(200);
        res.end(`Handled by worker ${process.pid}\n`);
    }).listen(8000);

    console.log(`Worker ${process.pid} started`);
}
```

How OS load balancing works with cluster:
- The primary process opens a socket and passes the file descriptor to workers
- The OS kernel distributes incoming connections across workers (round-robin on Linux)
- Each worker is an independent process with its own Event Loop, heap, and JS context
- A crash in one worker doesn't affect others

```
           ┌─────────────┐
           │   Primary   │  (manages workers, no HTTP handling)
           │  PID: 1234  │
           └──────┬──────┘
          ┌───────┼───────┐
    ┌─────▼───┐ ┌─▼─────┐ ┌▼──────┐ ┌──────▼┐
    │Worker 1 │ │Worker2│ │Worker3│ │Worker4│
    │PID:1235 │ │PID:36 │ │PID:37 │ │PID:38 │
    │ :8000   │ │ :8000 │ │ :8000 │ │ :8000 │
    └─────────┘ └───────┘ └───────┘ └───────┘
         ↑            ↑        ↑         ↑
         └────────────┴────────┴─────────┘
              OS distributes connections
```

In production, `pm2` handles this more elegantly:
```bash
pm2 start app.js -i max    # Spawn one worker per CPU core
pm2 start app.js -i 4      # Spawn exactly 4 workers
pm2 reload app.js           # Zero-downtime rolling restart
```

## Section 4: Worker Threads

**Q9. What are Worker Threads and how do they differ from the cluster module?**

A: Worker Threads (`worker_threads` module, stable since Node.js 12) bring true in-process parallelism to Node.js — separate JavaScript execution contexts running on OS threads, sharing the same process memory space:

| Feature | `cluster` | `worker_threads` |
|---|---|---|
| Isolation | Full process isolation | Shared process, separate V8 contexts |
| Memory sharing | None (IPC only) | `SharedArrayBuffer` + `Atomics` |
| Communication | JSON over IPC pipe | `postMessage` (structured clone) |
| Startup cost | High (full process fork) | Lower (new V8 context) |
| Use case | Scale HTTP serving across CPUs | CPU-bound computation alongside serving |
| Crash behavior | Isolated (other workers survive) | Can be isolated with try/catch |

```typescript
// worker.ts — runs in a worker thread
import { workerData, parentPort } from 'worker_threads';

function processLargeDataset(data: number[]): number {
    // CPU-intensive work — runs on a separate OS thread
    // Main thread continues handling HTTP requests while this runs
    return data.reduce((sum, n) => sum + Math.sqrt(n), 0);
}

const result = processLargeDataset(workerData.data);
parentPort!.postMessage({ result });
```

```typescript
// main.ts — HTTP server with worker thread pool
import { Worker } from 'worker_threads';
import path from 'path';

class WorkerPool {
    private workers: Worker[] = [];
    private queue: Array<{ data: unknown; resolve: Function; reject: Function }> = [];
    private available: Worker[] = [];

    constructor(size: number, workerFile: string) {
        for (let i = 0; i < size; i++) {
            const worker = new Worker(workerFile);
            worker.on('message', (result) => {
                const task = this.queue.shift();
                if (task) {
                    task.resolve(result);
                }
                this.available.push(worker);
                this.drain();
            });
            this.workers.push(worker);
            this.available.push(worker);
        }
    }

    run(data: unknown): Promise<unknown> {
        return new Promise((resolve, reject) => {
            this.queue.push({ data, resolve, reject });
            this.drain();
        });
    }

    private drain() {
        while (this.queue.length > 0 && this.available.length > 0) {
            const worker = this.available.pop()!;
            const task = this.queue[0];
            worker.postMessage(task.data);
        }
    }
}

const pool = new WorkerPool(4, path.resolve(__dirname, 'worker.js'));

app.post('/process', async (req, res) => {
    // Offload CPU work to a worker — main thread stays responsive
    const result = await pool.run(req.body.data);
    res.json({ result });
});
```

**Zero-copy with SharedArrayBuffer** — the power move for high-throughput inter-thread data sharing:

```typescript
// Transfer ownership of a buffer (no copy — O(1) regardless of size):
const buffer = new ArrayBuffer(1024 * 1024 * 100); // 100MB
worker.postMessage({ buffer }, [buffer]); // Transfer (not copy) — main thread loses access

// Share a buffer between threads (requires careful synchronization with Atomics):
const shared = new SharedArrayBuffer(4);
const view = new Int32Array(shared);
worker.postMessage({ shared });
Atomics.store(view, 0, 42); // Write atomically
Atomics.load(view, 0);      // Read atomically
Atomics.wait(view, 0, 42);  // Block worker thread until value changes (not available on main)
```

**Q10. How does `process.nextTick` differ from `setImmediate` and `Promise.resolve().then()`?**

A: These are all ways to schedule microtasks or callbacks, but they fire at different points in the Event Loop:

```javascript
// Execution order demonstration:
setImmediate(() => console.log('A: setImmediate'));   // check phase of NEXT iteration
setTimeout(() => console.log('B: setTimeout 0'), 0); // timers phase (≥1ms)
Promise.resolve().then(() => console.log('C: Promise.then')); // microtask queue
process.nextTick(() => console.log('D: nextTick'));   // nextTick queue (before microtasks)
console.log('E: synchronous');

// Output:
// E: synchronous     — runs first (synchronous)
// D: nextTick        — nextTick queue drained before ANY other async
// C: Promise.then    — microtask queue (after nextTick, before phases)
// B: setTimeout 0    — timers phase (actual min is ~1ms, not 0)
// A: setImmediate    — check phase (after poll, so after timers if I/O pending)
```

Priority order (highest to lowest):
1. **Synchronous code** — runs immediately
2. **`process.nextTick`** — after current operation, before Event Loop phases, before Promises
3. **Promise microtasks** — after nextTick, before Event Loop phases
4. **Event Loop phases** (timers → poll → check → close in order)
5. **`setImmediate`** — check phase (roughly "after I/O callbacks")
6. **`setTimeout(fn, 0)`** — timers phase (minimum ~1ms, not truly 0)

```javascript
// A common bug: accidentally starving the Event Loop with process.nextTick
function recursiveNextTick() {
    process.nextTick(recursiveNextTick); // NEVER lets the Event Loop advance!
    // I/O callbacks, timers, setImmediate — none of them can run
}

// Correct approach if you need recursive async yielding:
function recursiveSetImmediate() {
    setImmediate(recursiveSetImmediate); // Yields after each iteration
}
```

Interview framing: `process.nextTick` was designed for internal Node.js use cases where a callback must fire before any I/O, but after synchronous code completes (e.g., emitting an 'error' event on a constructor). Overusing it is an anti-pattern.

## Section 5: Practical Patterns and Gotchas

**Q11. What is "blocking the Event Loop" and how do you detect and prevent it?**

A: Blocking the Event Loop means running synchronous JavaScript for so long that no other callbacks can execute, making the server appear frozen to all concurrent clients.

Common blocking scenarios:

```javascript
// 1. Synchronous file operations in request handlers — NEVER do this
app.get('/config', (req, res) => {
    const config = fs.readFileSync('./config.json', 'utf8'); // BLOCKS everything
    res.json(JSON.parse(config));
});

// 2. Large JSON operations
app.get('/export', (req, res) => {
    const data = getAllUsers(); // Returns 100,000 users
    res.json(data);             // JSON.stringify of ~50MB object — blocks for seconds
});

// 3. Synchronous crypto
app.post('/hash', (req, res) => {
    // crypto.pbkdf2Sync blocks — use async version
    const hash = crypto.pbkdf2Sync(req.body.password, salt, 100000, 64, 'sha512');
    res.json({ hash: hash.toString('hex') });
});

// 4. Long-running pure JS computation
app.get('/primes', (req, res) => {
    const primes = sieveOfEratosthenes(10_000_000); // May take 200ms+ — blocks
    res.json(primes);
});
```

**Detection tools:**

```javascript
// 1. --inspect flag + Chrome DevTools profiler
// node --inspect server.js → open chrome://inspect → record CPU profile

// 2. blocked-at package — logs what's blocking and for how long:
// npm install blocked-at
const blocked = require('blocked-at');
blocked((ms, stack) => {
    console.warn(`Event Loop blocked for ${ms}ms:\n${stack.join('\n')}`);
}, { threshold: 50 }); // Alert when blocked > 50ms

// 3. clinic.js — Node.js performance profiling suite:
// npx clinic doctor -- node server.js
// Generates a flame graph showing blocking operations

// 4. perf_hooks for manual measurement:
import { performance, PerformanceObserver } from 'perf_hooks';

const obs = new PerformanceObserver((list) => {
    list.getEntries().forEach(entry => {
        if (entry.duration > 10) { // Alert on >10ms operations
            console.warn(`Slow operation: ${entry.name} took ${entry.duration.toFixed(2)}ms`);
        }
    });
});
obs.observe({ entryTypes: ['measure'] });

performance.mark('start');
// ... operation ...
performance.mark('end');
performance.measure('my-operation', 'start', 'end');
```

**Q12. How does async/await interact with the Event Loop — does `await` block the thread?**

A: `await` does **not** block the main thread. It's syntactic sugar over Promises. When execution hits an `await`, the current async function suspends and **returns control to the Event Loop**, allowing other callbacks to run. The function resumes when the awaited Promise resolves.

```javascript
async function fetchUserData(id: string) {
    console.log('1: before await');

    // await suspends THIS function and returns control to Event Loop
    // Other requests can be processed while waiting for DB response
    const user = await db.query('SELECT * FROM users WHERE id = ?', [id]);

    // This line runs in a microtask when the Promise resolves
    console.log('3: after await');
    return user;
}

console.log('2: after calling fetchUserData (runs before log 3)');
```

Under the hood:
```javascript
// async/await desugars to:
function fetchUserData(id) {
    return new Promise((resolve) => {
        console.log('1: before await');
        db.query('SELECT * FROM users WHERE id = ?', [id])
            .then(user => {
                console.log('3: after await');
                resolve(user);
            });
    });
}
// The .then callback is queued as a microtask when the DB Promise resolves
// Between the db.query call and the .then firing, the Event Loop is free
```

Key nuances:

```javascript
// await only suspends the async function — synchronous code BEFORE the await still blocks
async function dangerous() {
    const data = bigSyncOperation(); // This BLOCKS before the await even runs
    await someAsyncOp();
    return data;
}

// Sequential awaits are slower than parallel:
// SLOW — waits for each in series:
const user = await fetchUser(id);      // 100ms
const orders = await fetchOrders(id);  // 100ms
// Total: 200ms

// FAST — both in parallel:
const [user, orders] = await Promise.all([
    fetchUser(id),    // 100ms
    fetchOrders(id),  // 100ms — runs concurrently
]);
// Total: ~100ms
```

**Q13. How does Node.js handle backpressure, and why does it matter for scalability?**

A: Backpressure is the mechanism by which a data consumer signals to a producer to slow down when the consumer can't keep up. Without backpressure, a fast producer can overwhelm a slow consumer, filling memory until the process crashes.

```javascript
// Problem: no backpressure — memory fills with unprocessed data
const readStream = fs.createReadStream('huge-file.csv');
const writeStream = fs.createWriteStream('output.csv');

// WRONG — readable fires events faster than write can handle them:
readStream.on('data', (chunk) => {
    writeStream.write(chunk); // write() buffers internally — unbounded memory growth
});

// CORRECT — use pipe() which handles backpressure automatically:
readStream.pipe(writeStream); // pipe pauses readable when writable buffer is full

// OR manually with backpressure handling:
readStream.on('data', (chunk) => {
    const canContinue = writeStream.write(chunk);
    if (!canContinue) {
        readStream.pause(); // Backpressure: tell producer to slow down
        writeStream.once('drain', () => {
            readStream.resume(); // Buffer drained — producer can continue
        });
    }
});
```

In HTTP servers, backpressure matters for:
- Streaming large responses to slow clients (mobile on 3G)
- Processing large upload bodies
- Piping database result streams to HTTP responses

```javascript
// Streaming a large DB result without loading it all in memory:
app.get('/export', async (req, res) => {
    res.setHeader('Content-Type', 'application/json');
    res.setHeader('Transfer-Encoding', 'chunked');

    const stream = db.query('SELECT * FROM orders').stream();

    // pipeline handles backpressure and error cleanup automatically
    const { pipeline } = require('stream/promises');
    await pipeline(
        stream,
        new Transform({
            objectMode: true,
            transform(row, _, callback) {
                callback(null, JSON.stringify(row) + '\n');
            }
        }),
        res
    );
    // If res (the HTTP response) is slow, pipeline pauses the DB stream
    // Memory usage stays constant regardless of result set size
});
```

## Section 6: Scenario-Based Questions

**Q14. "You have a Node.js service that handles both API requests and heavy PDF generation. How would you architect it?"**

A: PDF generation is CPU-bound (layout calculation, font rendering, compression) — exactly what blocks the Event Loop. The architecture separates concerns:

```typescript
// Option A: Worker Thread Pool for same-process PDF generation
import { Worker, isMainThread, parentPort, workerData } from 'worker_threads';

// pdf-worker.ts
if (!isMainThread) {
    const { template, data } = workerData;
    // import and use puppeteer/pdfkit in worker thread
    const pdfBuffer = generatePDF(template, data); // CPU-bound — fine in worker
    parentPort!.postMessage(pdfBuffer, [pdfBuffer.buffer]); // Transfer, no copy
}

// server.ts
const pdfWorkerPool = new WorkerPool(os.cpus().length, './pdf-worker.js');

app.post('/generate-pdf', authenticate, async (req, res) => {
    try {
        const pdfBuffer = await pdfWorkerPool.run({
            template: req.body.template,
            data: req.body.data
        }) as Buffer;

        res.setHeader('Content-Type', 'application/pdf');
        res.setHeader('Content-Disposition', 'attachment; filename=report.pdf');
        res.send(pdfBuffer);
        // Main thread was free to handle other API requests the whole time
    } catch (err) {
        res.status(500).json({ error: 'PDF generation failed' });
    }
});

// Option B: Separate microservice (better for scale-out):
// PDF requests → queue (SQS/RabbitMQ) → dedicated PDF workers → S3 → callback URL
// API service never touches PDF generation — fully decoupled
// Scale PDF workers independently of API servers based on queue depth
```

**Q15. "Why is Node.js good for real-time applications but potentially bad for CPU-intensive ones? Give examples."**

A:

**Node.js excels at (I/O-bound, concurrent, event-driven):**

```javascript
// 1. Real-time chat — thousands of idle WebSocket connections, minimal CPU per message
io.on('connection', (socket) => {
    socket.on('message', (msg) => {
        // ~microseconds of JS: validate, save to Redis, broadcast
        io.to(socket.roomId).emit('message', msg);
    });
    // Socket sits idle between messages — costs almost nothing
});

// 2. API Gateway / BFF — mostly proxying, minimal transformation
app.get('/dashboard', async (req, res) => {
    const [user, metrics, alerts] = await Promise.all([
        userService.get(req.userId),    // Network I/O — Event Loop free
        metricsService.get(req.userId), // Network I/O — Event Loop free
        alertsService.get(req.userId),  // Network I/O — Event Loop free
    ]);
    res.json({ user, metrics, alerts }); // Microseconds of JS
});

// 3. Streaming data pipelines — transform data as it arrives
sensorStream
    .pipe(validate())
    .pipe(transform())
    .pipe(writeToTimeseries()); // Memory-efficient, Event Loop rarely blocked
```

**Node.js struggles at (CPU-bound):**

```javascript
// 1. Video transcoding — CPU-bound for minutes
// Node.js: main thread blocked for the entire transcode
// Better: spawn ffmpeg subprocess, or use dedicated Go/C++ service

// 2. Machine learning inference — matrix operations are CPU/GPU-bound
// Node.js with TensorFlow.js blocks the Event Loop during inference
// Better: Python FastAPI service with NumPy/PyTorch, called via gRPC

// 3. Image resizing at high concurrency — libuv thread pool saturated
// With 4 threads and 100 concurrent resize requests, 96 requests wait
// Better: Sharp with worker threads or dedicated image CDN (Cloudflare Images)

// 4. Cryptographic mining / brute force — pure CPU
// A Node.js process can only use one core for this
// Better: Rust/C++ with native threading
```

The deciding question: **"What percentage of time does the request spend waiting for I/O vs executing JavaScript?"**
- >90% I/O wait → Node.js shines
- >50% CPU time → consider alternatives or Worker Threads

**Q16. "What happens when you call `setTimeout(fn, 0)` — does it run immediately?"**

A: No. `setTimeout(fn, 0)` does **not** run immediately. It schedules `fn` to run in the **timers phase** of the next (or a future) Event Loop iteration, with a **minimum delay of ~1ms** (the HTML spec minimum, also enforced by libuv).

```javascript
console.log('A');

setTimeout(() => console.log('B'), 0); // Minimum ~1ms, not truly 0

Promise.resolve().then(() => console.log('C')); // Microtask — sooner than setTimeout

process.nextTick(() => console.log('D')); // Even sooner

console.log('E');

// Output: A, E, D, C, B
// B runs last because setTimeout has minimum delay AND waits for timers phase
```

Practical implications:

```javascript
// setTimeout(fn, 0) is NOT equivalent to setImmediate(fn):
// - setTimeout: fires in timers phase (before poll)
// - setImmediate: fires in check phase (after poll/I/O)
// When called from within an I/O callback, setImmediate always fires before setTimeout(fn,0):

fs.readFile('file.txt', () => {
    setTimeout(() => console.log('timeout'), 0);
    setImmediate(() => console.log('immediate'));
    // Output: always "immediate" then "timeout" — inside I/O callback, check < timers
});

// When called from main module (not inside I/O), order is non-deterministic:
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// Could be either order — depends on OS timer precision
```

## Quick Reference Table

| Concept | Key Point | Common Gotcha |
|---|---|---|
| Single thread | JS runs on one thread; I/O does not | "Single-threaded" doesn't mean no threads — libuv has a pool |
| Event Loop | 6 phases; polls OS for I/O events | nextTick > Promises > all other phases |
| libuv thread pool | 4 threads for fs, dns, crypto | Saturates at 4 concurrent blocking ops; increase with UV_THREADPOOL_SIZE |
| Network I/O | OS kernel handles async (epoll/kqueue) | Doesn't use thread pool — scales to thousands |
| Blocking the Loop | Long-running JS freezes all requests | Even 50ms is noticeable at scale |
| Worker Threads | True parallelism for CPU work | Not needed for I/O; adds complexity |
| cluster | Multiple processes, one port | No shared memory; use for HTTP scaling |
| `await` | Suspends function, NOT the thread | Sync code before `await` still blocks |
| `process.nextTick` | Runs before Promises, before Event Loop | Recursive nextTick starves the loop |
| Backpressure | Signal producer to slow down | Not using `pipe/pipeline` can OOM the process |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) knowing that **libuv's thread pool** exists and which operations use it (fs, dns.lookup, crypto) vs. which use OS async I/O (network) — most candidates don't know this distinction; (2) being able to explain the **Event Loop phases** in order and where `nextTick`, Promises, `setTimeout`, and `setImmediate` fit — especially that nextTick fires *before* Promises, and both fire before the next phase; (3) articulating clearly **when Node.js is the wrong tool** (CPU-bound workloads) and what to do about it (Worker Threads, subprocesses, separate services) rather than just saying "Node.js scales"; (4) knowing that **`await` does not block the thread** and explaining why (suspends the current async function, returns control to Event Loop, resumes as a microtask) — this trips up many mid-level candidates; and (5) understanding **backpressure** in streams — not using `pipe`/`pipeline` when streaming large data is a real production incident waiting to happen, and knowing how to detect and handle it shows genuine production experience.
