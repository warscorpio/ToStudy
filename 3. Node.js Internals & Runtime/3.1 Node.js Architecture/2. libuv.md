# Node.js Internals: libuv — Thread Pool, I/O Polling & Timers — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: What libuv Is and Why It Exists

**Q1. What is libuv, and what problem does it solve for Node.js?**
A: libuv is a **cross-platform C library** that provides Node.js with its event loop, asynchronous I/O primitives, thread pool, timers, and platform-independent abstractions over OS-level facilities like file system operations, networking, child processes, signals, and DNS resolution. It was created specifically to give Node.js a unified, non-blocking I/O foundation that works identically across Linux, macOS, and Windows — despite these platforms having fundamentally different native async I/O APIs (`epoll` on Linux, `kqueue` on macOS/BSD, `IOCP` on Windows).

Without libuv, Node.js would need to write platform-specific code for every asynchronous operation and maintain separate codebases per OS. libuv hides all of that, exposing a single event loop abstraction. JavaScript code (and the V8 engine) runs on a single thread; libuv lets that thread initiate long-running I/O operations, hand them to the OS or a thread pool, and receive results via callbacks without ever blocking the JS thread.

**Q2. What is the relationship between the V8 engine, Node.js, and libuv?**
A: Three distinct layers with specific responsibilities:
- **V8**: Google's JavaScript engine — compiles and executes JS code. Knows nothing about the file system, network, or timers. V8 provides the JS runtime (garbage collection, object model, call stack), and exposes a C++ API that Node.js uses to bind native functions to JavaScript.
- **Node.js (core)**: The C++ layer that bridges V8 and libuv. It uses V8's C++ API to expose Node.js's built-in modules (`fs`, `net`, `http`, `crypto`, etc.) as JavaScript-callable functions, and uses libuv's C API to implement those functions asynchronously.
- **libuv**: The async I/O and event loop layer. Manages all non-blocking I/O, the thread pool, timers, and event-driven callback scheduling. It's the engine room that makes "non-blocking" possible.

```
Your JavaScript Code
       ↓
    V8 Engine  ←→  Node.js C++ Bindings
                          ↓
                        libuv
                   ↙          ↘
            Thread Pool    OS Kernel
          (CPU/file I/O)   (network I/O,
                            epoll/kqueue/IOCP)
```

**Q3. What is the event loop, and what does libuv's event loop do in each iteration ("tick")?**
A: The event loop is a **continuous loop** that drives all asynchronous activity in a Node.js process. Each iteration processes one category of pending work, moving through a fixed sequence of **phases**. libuv defines these phases:

1. **Timers**: executes callbacks from `setTimeout` and `setInterval` whose delay has elapsed.
2. **Pending callbacks**: executes I/O callbacks deferred to the next loop iteration (typically from previous I/O errors).
3. **Idle/Prepare**: internal libuv use only (not directly accessible from JS).
4. **Poll**: retrieves new I/O events (via `epoll`/`kqueue`/`IOCP`); blocks here if there are no timers or `setImmediate` callbacks pending and no other events ready.
5. **Check**: executes `setImmediate` callbacks.
6. **Close callbacks**: handles close events (e.g., `socket.on('close', ...)`).

Between every phase transition, Node.js drains the **microtask queue** (Promise `.then`/`.catch` callbacks and `queueMicrotask()`) and the **`process.nextTick` queue**. Critically, `process.nextTick` callbacks run before Promise microtasks — both run between every phase, effectively making them higher-priority than any event loop phase callback.

### Section 2: The Thread Pool

**Q4. What operations does libuv's thread pool handle, and why do they need a thread pool rather than the OS's native async I/O?**
A: libuv's thread pool (implemented via `uv_threadpool`) exists because **not all operations can be made non-blocking at the OS level**. Specifically:

**File system operations** (`fs.readFile`, `fs.writeFile`, `fs.stat`, etc.): POSIX file I/O is fundamentally synchronous at the kernel level — the Linux `read()`/`write()` syscalls block the calling thread. `epoll` does not support regular files (only sockets, pipes, and similar). libuv solves this by running file I/O on thread pool threads, where blocking is acceptable because it doesn't block the main JS thread.

**DNS resolution** (`dns.lookup`): The standard `getaddrinfo()` function is synchronous. `dns.resolve()` uses `c-ares` (a non-blocking DNS library) and doesn't need the thread pool, but `dns.lookup()` uses `getaddrinfo()` and does.

**CPU-intensive `crypto` operations**: `crypto.pbkdf2()`, `crypto.scrypt()`, and `crypto.randomBytes()` (in some cases) are computationally expensive and run in the thread pool to avoid blocking the event loop.

**User code via `uv_queue_work`**: Native Node.js add-ons can submit arbitrary C++ work to the thread pool.

```
Operations via thread pool:          Operations via OS async I/O (no thread pool):
─────────────────────────            ─────────────────────────────────────────────
fs.readFile / writeFile              net.connect / http requests
fs.stat / mkdir / readdir            server.listen / connection events
dns.lookup (getaddrinfo)             pipe / socket read/write
crypto.pbkdf2                        child_process stdio pipes
crypto.scrypt
Native add-on work (uv_queue_work)
```

**Q5. What is the default thread pool size, how do you change it, and what happens under contention?**
A: The default thread pool size is **4 threads**. It can be changed by setting the `UV_THREADPOOL_SIZE` environment variable **before the Node.js process starts** (not at runtime, since threads are pre-allocated):

```bash
UV_THREADPOOL_SIZE=16 node server.js
```

The maximum is **1024 threads** (a libuv compile-time limit). Practical recommendations:

When all 4 (or N) threads are busy and another async operation tries to use the thread pool, it **queues and waits**. This is why `fs.readFile` called 10 times simultaneously doesn't mean 10 concurrent file reads — only 4 (default) will be in-flight at any moment; the other 6 wait in the queue. This is a common source of surprising performance bottlenecks: Node.js appears async, but all the file reads are actually serialized through the 4-thread bottleneck.

```js
// Demonstrating the bottleneck: 10 concurrent fs.stat calls
// with UV_THREADPOOL_SIZE=4 (default):
const { stat } = require('fs');

const start = Date.now();
for (let i = 0; i < 10; i++) {
  stat('/etc/hosts', (err, s) => {
    console.log(`stat ${i} done after ${Date.now() - start}ms`);
  });
}
// With 4 threads: first 4 complete quickly, next 4 wait, last 2 wait
// Total time ≈ 3 × (time for one stat), not 1 × (time for one stat)
```

**Q6. Why should you generally NOT set `UV_THREADPOOL_SIZE` to very large values (e.g., 128)?**
A: Each thread consumes OS resources (stack memory, kernel thread structures — typically 1-8 MB stack per thread). More threads than CPU cores also introduces **context-switching overhead** — the OS kernel spends CPU cycles switching between threads rather than doing actual work. The optimal thread pool size for I/O-bound work (file operations) is typically the number of concurrent I/O operations you expect, but capped by what the underlying storage can handle simultaneously (a single spinning disk can only serve one request at a time anyway; SSDs and NVMe can handle many more). For CPU-bound work (crypto), the optimal is closer to the number of CPU cores. Setting `UV_THREADPOOL_SIZE` to a high value without benchmarking often harms rather than helps performance due to contention and context switching.

### Section 3: I/O Polling

**Q7. How does libuv perform non-blocking network I/O — why does it NOT use the thread pool for TCP connections?**
A: Network I/O (TCP connections, UDP sockets, HTTP requests/responses) uses **OS-level non-blocking I/O combined with I/O multiplexing**, not the thread pool. The key difference: network sockets can be made non-blocking with `O_NONBLOCK`, and the OS provides I/O multiplexing APIs (`epoll` on Linux, `kqueue` on macOS, `IOCP` on Windows) that allow a single thread to monitor thousands of sockets simultaneously and be notified when any of them have data ready to read or space to write.

libuv's **Poll phase** calls `epoll_wait()` (or equivalent) on a set of file descriptors, blocking until one or more sockets are ready for I/O (or until a timeout expires if there are pending timers). This is vastly more efficient than using a thread per connection, since a single OS thread can simultaneously watch thousands of connections and wake up only when work is available.

```
Thread Pool path (file I/O):
  JS thread → submit work → thread pool thread blocks on read() → work done → callback queue

OS async I/O path (network):
  JS thread → register socket with epoll → continue running other JS
  [OS kernel monitors socket in hardware]
  Data arrives → epoll notifies libuv → callback queued → JS thread runs callback
```

**Q8. What is `epoll`, and how does libuv use it on Linux?**
A: `epoll` is the Linux kernel's I/O event notification mechanism — it lets a process monitor a set of file descriptors and be notified when I/O operations can proceed without blocking. libuv uses `epoll` in edge-triggered mode (`EPOLLET`) for efficiency. The lifecycle:

1. libuv creates an `epoll` instance (`epoll_create1()`).
2. When Node.js opens a socket/pipe/etc., libuv registers it with `epoll` (`epoll_ctl(EPOLL_CTL_ADD, fd, event)`), specifying which events to monitor (read-ready, write-ready, etc.).
3. In the Poll phase of each event loop iteration, libuv calls `epoll_wait(epollfd, events, maxEvents, timeout)`, which blocks until one or more registered file descriptors are ready (or the timeout expires).
4. `epoll_wait` returns with a list of ready file descriptors and what events occurred on them.
5. libuv dispatches the appropriate callbacks for each ready fd.
6. The next event loop iteration begins.

On macOS/BSD, `kqueue` serves the same role. On Windows, `IOCP` (I/O Completion Ports) works somewhat differently — rather than "this fd is ready," IOCP notifies "this I/O operation has completed" — but libuv abstracts the difference.

**Q9. What determines how long the Poll phase blocks (the `epoll_wait` timeout)?**
A: The Poll phase timeout is calculated by libuv at the start of each iteration:
- If there are **`setImmediate` callbacks pending** (from previous phases or newly scheduled): timeout = 0 (don't block — check for I/O events but return immediately).
- If there are **timers pending** whose expiry is approaching: timeout = time until the soonest timer expires.
- If there are **no pending timers and no `setImmediate` callbacks**: timeout = -1 (block indefinitely until an I/O event arrives).

This is why a Node.js process **exits cleanly** when there's no more work to do — no pending I/O, timers, or callbacks means the event loop has no more phases to process, and the process terminates instead of looping forever on an empty event queue.

```js
// This process exits immediately (no pending async work):
console.log('hello');

// This process stays alive until the timer fires (event loop has a timer):
setTimeout(() => console.log('world'), 1000);

// This process stays alive until the connection closes (event loop has a pending I/O handle):
const server = require('net').createServer();
server.listen(3000);
// process won't exit because `server` is a "ref'd" handle in libuv's event loop
```

### Section 4: Timers

**Q10. How does libuv implement timers — what data structure does it use internally?**
A: libuv stores timers in a **min-heap** (binary min-heap) ordered by expiration time. The minimum element (soonest-expiring timer) is always at the root. In the Timers phase of each event loop iteration, libuv checks the root of the heap: if the soonest timer's expiry is ≤ current time, it fires that timer's callback, pops the root, and checks the new root, repeating until no expired timer remains. This is O(log n) per timer insertion/removal and O(1) per heap-minimum inspection — efficient even with many concurrent timers.

**Q11. What is the difference between `setTimeout`, `setImmediate`, and `process.nextTick` in terms of when their callbacks execute?**
A: Three distinct scheduling mechanisms with different execution points in the event loop:

- **`process.nextTick(fn)`**: runs at the end of the current operation, **before the event loop's next phase begins** — technically not even a libuv timer, it's a Node.js-specific queue drained between every event loop phase (and before Promise microtasks). Use for: deferring a callback to after the current synchronous code finishes, but before any I/O.
- **`setImmediate(fn)`**: runs in the **Check phase** of the current (or next) event loop iteration — after the Poll phase (I/O callbacks) but before Timers in the next iteration. Use for: running something after all I/O in the current iteration.
- **`setTimeout(fn, 0)`**: runs in the **Timers phase** of the next (or a later) event loop iteration, with a minimum delay of ~1ms (the OS timer resolution; Node.js enforces a minimum of 1ms). Use for: deferring execution with a minimum delay.

Execution order — important nuances:
```js
// Order within the SAME synchronous block:
setImmediate(() => console.log('setImmediate'));
setTimeout(() => console.log('setTimeout'), 0);
// ORDER IS NOT GUARANTEED — depends on when the event loop processes phases
// relative to the timer's exact expiry (usually setImmediate if I/O is pending,
// can be either if started from the main module)

// BUT from within an I/O callback, setImmediate ALWAYS fires before setTimeout:
require('fs').readFile('/etc/hosts', () => {
  setImmediate(() => console.log('immediate')); // ← ALWAYS first in I/O context
  setTimeout(() => console.log('timeout'), 0);  // ← ALWAYS second in I/O context
});

// process.nextTick ALWAYS before both:
process.nextTick(() => console.log('nextTick'));   // 1st
setImmediate(() => console.log('setImmediate'));   // later
setTimeout(() => console.log('setTimeout'), 0);   // later
```

**Q12. Why can excessive `process.nextTick` usage "starve" the event loop?**
A: `process.nextTick` callbacks are drained completely before any event loop phase runs. If a `process.nextTick` callback schedules another `process.nextTick`, that new callback also runs before any I/O callbacks or timers — potentially creating an endless cycle that prevents the event loop from ever reaching the Poll, Check, or Timer phases. This is "starvation": pending I/O callbacks, `setImmediate` callbacks, and timers are indefinitely deferred while the `nextTick` queue stays non-empty.

```js
// This starves the event loop — I/O callbacks never run:
function recursiveNextTick() {
  process.nextTick(recursiveNextTick);
}
recursiveNextTick();
// fs.readFile callbacks, setTimeout callbacks, HTTP requests — all blocked

// The same behavior with setImmediate does NOT starve:
function recursiveImmediate() {
  setImmediate(recursiveImmediate);
}
recursiveImmediate();
// This allows I/O to be processed each iteration (setImmediate runs in Check phase,
// then Poll phase runs in the next iteration, processing any ready I/O)
```

**Q13. What is `setInterval`'s behavior when its callback takes longer than the interval?**
A: `setInterval(fn, n)` schedules `fn` to run every `n` milliseconds. But if `fn` takes longer than `n` ms to complete, the next execution does NOT run concurrently — the event loop is single-threaded. The next invocation is scheduled from the time the current callback completes (or more precisely, from when libuv processes it in the next Timers phase). This means if `fn` takes 500ms and the interval is 100ms, executions effectively run at 500ms intervals, not 100ms. The timer doesn't "pile up" or miss executions; it simply falls behind schedule without accumulation.

### Section 5: Advanced Patterns & Interactions

**Q14. What is `uv__io_t`, and what is the relationship between libuv "handles" and "requests"?**
A: libuv models async operations via two C-level types:
- **Handles** (`uv_tcp_t`, `uv_udp_t`, `uv_timer_t`, `uv_fs_event_t`, etc.): **long-lived** objects representing capabilities or streams — a TCP server listening on a port, a timer that fires repeatedly, a file system watcher. Handles keep the event loop alive while they're active (ref'd). Node.js `net.Server`, `net.Socket`, timers, and file watchers are wrappers around libuv handles.
- **Requests** (`uv_fs_t`, `uv_getaddrinfo_t`, `uv_work_t`, etc.): **short-lived** objects representing a single async operation — read a file, resolve a hostname, run a work function on the thread pool. Requests don't keep the event loop alive on their own; they're associated with a handle or the event loop and complete, after which the object is freed.

Understanding handles also explains `ref()`/`unref()` in Node.js: calling `server.unref()` tells libuv to not count that handle when deciding whether to keep the event loop alive — useful for background timers that shouldn't prevent program exit.

**Q15. How does libuv handle the case where a thread pool task completes while the event loop is blocked in the Poll phase?**
A: This is solved by libuv's **interrupt mechanism**. The thread pool maintains an async handle (`uv_async_t`) connected to a pipe or `eventfd` (on Linux). When a thread pool task completes, the worker thread writes to this pipe/eventfd. The `epoll_wait` call in the Poll phase is monitoring this pipe's file descriptor — writing to it makes `epoll_wait` return immediately, interrupting the block. The Poll phase then processes the completed I/O event and queues the associated callback. This is how thread pool completions (file reads, crypto) "wake up" the event loop without polling or busy-waiting.

**Q16. What is the difference between `dns.lookup` and `dns.resolve` in terms of libuv interaction, and why does it matter?**
A: A critical but under-documented distinction:
- **`dns.lookup(hostname, callback)`**: calls the OS's `getaddrinfo()` — synchronous, uses the thread pool (one of the 4 default threads). Also respects `/etc/hosts`, OS-level DNS configuration, and system resolver caches. **Blocks a thread pool thread** for the duration of the DNS query.
- **`dns.resolve(hostname, callback)`** (and `dns.resolve4`, `dns.resolve6`, etc.): uses `c-ares`, a fully non-blocking async DNS library. Makes DNS queries directly as network I/O (UDP/TCP), goes through the event loop's Poll phase (OS async I/O), and **does not use the thread pool**.

Why it matters: under high concurrency, many `dns.lookup` calls can exhaust the thread pool (all 4 threads busy doing DNS), blocking unrelated file system operations. `dns.resolve` has no such limitation. However, `dns.resolve` bypasses the OS resolver (no `/etc/hosts`, no system DNS cache), which may cause behavioral differences for certain configurations. Node.js's `http.get` and `https.get` use `dns.lookup` by default, which is why HTTP clients under high concurrency can unexpectedly saturate the thread pool.

### Section 6: Scenario / Interview-Style Questions

**Q17. "A Node.js server handles 1000 concurrent HTTP requests, but the route handler calls `fs.readFile` for each request. What performance problem might arise, and how would you fix it?"**
A: `fs.readFile` uses the libuv thread pool. With the default pool size of 4 threads, only 4 file reads happen concurrently — the other 996 are queued. If each file read takes 10ms, the total time for all reads approaches 250 × 10ms = 2500ms in the worst case (1000 reads ÷ 4 concurrent = 250 rounds × 10ms). Meanwhile, the event loop processes callbacks as threads complete, but the end-to-end latency is dominated by thread pool queuing.

Fixes in increasing order of impact:
1. **`UV_THREADPOOL_SIZE`**: increase to match expected concurrency (up to hardware limits). Helps for I/O-bound file reads.
2. **Caching**: cache file contents in memory after first read. Subsequent requests skip the thread pool entirely.
3. **Streaming**: use `fs.createReadStream` instead of `fs.readFile` where possible — streams still use the thread pool but process data in chunks without buffering entire files.
4. **`node:fs/promises` with proper concurrency limits**: use `Promise.all` with a bounded concurrency pattern to limit how many file reads are in-flight simultaneously.
5. **Use a CDN or static file server** (nginx): static file serving is most efficient outside of Node.js.

**Q18. "Explain why `setTimeout(fn, 0)` doesn't always run before `setImmediate(fn)` even though the delay is zero."**
A: When `setTimeout(fn, 0)` is called from the main module (outside an I/O callback), the event loop may or may not have already passed the Timers phase by the time the setTimeout is registered. The OS timer resolution is not exactly 0ms — libuv enforces a minimum of 1ms and rounds up. If the event loop reaches the Timers phase before the 1ms timer has expired, `setTimeout` doesn't fire that iteration; the loop continues to the Poll and Check phases where `setImmediate` runs. In the next iteration, `setTimeout` fires. Conversely, if enough time has passed (the 1ms has elapsed) before the Timers phase, `setTimeout` fires first. The non-determinism is because the exact elapsed time when the Timers phase runs varies depending on OS scheduling and how fast the main module's synchronous code executed. From within an I/O callback, the relationship becomes deterministic: `setImmediate` always runs before `setTimeout(fn, 0)` because by the time we're inside an I/O callback, the Timers phase for this iteration has already passed.

**Q19. "What happens to the event loop when your server is idle (no active connections, no timers)?"**
A: With no pending handles or requests, the event loop has nothing left to do. libuv detects this condition (all active handles are either unref'd or there are none), exits the event loop, and the Node.js process terminates. If the server has a `net.Server` listening on a port, that server handle is active and keeps the event loop alive — `epoll_wait` will block in the Poll phase indefinitely (timeout = -1) until a new connection arrives or an OS signal interrupts it. This is why a simple `require('http').createServer(...).listen(3000)` keeps the process running forever even with no active requests — the listening socket handle is "ref'd" and libuv's event loop considers the process to have pending work.

**Q20. "A CPU-intensive computation is blocking the event loop. What are the options to fix it?"**
A: Six approaches in increasing sophistication:
1. **Chunk the work** with `setImmediate`: break the computation into smaller pieces, yielding to the event loop between chunks via `setImmediate(nextChunk)`. Keeps the event loop responsive but may make the computation slower due to overhead.
2. **`worker_threads` module** (Node.js 12+): run the CPU-intensive work on a separate thread using `Worker`. The worker has its own V8 instance and event loop. Use `MessageChannel` to communicate results. Best for parallelizable CPU work.
3. **`child_process`**: spawn a child Node.js process (`fork()`/`spawn()`), send work via IPC, receive results. Higher overhead than `worker_threads` but stronger isolation.
4. **Native add-on with `uv_queue_work`**: write a C++ add-on that submits the work to the libuv thread pool. Keeps the JavaScript interface clean while running the computation off the main thread.
5. **WebAssembly**: compile the computation to WASM, but note that synchronous WASM execution still blocks the main thread — still needs `worker_threads` for true off-thread execution.
6. **Rethink the algorithm**: many "CPU-intensive" problems in Node.js are CPU-intensive because of inefficient JavaScript — switching to typed arrays, caching, or more efficient algorithms can eliminate the problem at the source.

## Problem 1 — Understanding Event Loop Phase Order

### Problem
Predict the exact output of the following code and explain the ordering in terms of event loop phases.

```js
const fs = require('fs');

console.log('A');

setTimeout(() => console.log('B'), 0);

setImmediate(() => console.log('C'));

fs.readFile('/etc/hosts', () => {
  console.log('D');
  setTimeout(() => console.log('E'), 0);
  setImmediate(() => console.log('F'));
  process.nextTick(() => console.log('G'));
});

process.nextTick(() => console.log('H'));

Promise.resolve().then(() => console.log('I'));

console.log('J');
```

### Pattern Recognition
Event loop phase sequencing: synchronous code → `process.nextTick` queue → Promise microtask queue → Timers phase → Poll phase → Check phase, plus the inner ordering within an I/O callback.

### Key Insight
Two separate ordering contexts exist here: the top-level context (main module) and the I/O callback context. Inside the I/O callback, `setImmediate` ALWAYS fires before `setTimeout(fn, 0)` because the Timers phase for the current iteration has already passed — the only path forward is the Check phase (this iteration) and then the next Timers phase.

### Solution

```
Output (with reasoning):

A   ← synchronous: console.log runs immediately
J   ← synchronous: before the call stack is empty, we run all sync code to completion

H   ← process.nextTick queue is drained FIRST (before Promise microtasks),
      before any event loop phase runs

I   ← Promise microtask queue is drained NEXT (after nextTick, before event loop phases)

B   ← Timers phase of the FIRST event loop iteration.
      setTimeout(0) may fire here IF enough time has passed (non-deterministic at top-level)
      — BUT in practice on most systems, B often fires before C from the top level
      because the 1ms minimum may have elapsed by the time the Timers phase runs.

C   ← Check phase (setImmediate) of this iteration — BUT if B fired first (Timers came
      before Check), C fires second. If Timers hasn't expired yet, C fires first.
      *** From the TOP-LEVEL, B vs C ordering is non-deterministic ***

D   ← I/O callback from fs.readFile, fires in the Poll phase of some event loop iteration
      (after the thread pool completes the stat/read)

G   ← process.nextTick inside the I/O callback: drains BEFORE returning to the event loop,
      so G runs immediately after D's callback, before any other phase

E   ← setTimeout(fn, 0) from inside I/O callback: must wait for the NEXT event loop
      iteration's Timers phase (current Timers phase already ran this iteration)

F   ← setImmediate from inside I/O callback: runs in the Check phase of the CURRENT
      iteration (the same iteration whose Poll phase ran the I/O callback)
      → F ALWAYS runs before E when both are scheduled inside an I/O callback
```

### Definitive output:
```
A
J
H
I
[B and C: non-deterministic at top-level — usually B then C, but not guaranteed]
D
G
F
E
```

### Verification

```js
// To verify the I/O callback ordering (D/G/F/E), run just the I/O part:
const fs = require('fs');
fs.readFile('/etc/hosts', () => {
  console.log('D');
  setTimeout(() => console.log('E'), 0);   // always LAST — next Timers phase
  setImmediate(() => console.log('F'));     // always BEFORE E — current Check phase
  process.nextTick(() => console.log('G')); // always FIRST — before loop resumes
});
// Output guaranteed: D, G, F, E
```

### Edge Cases
- **Top-level `setTimeout(0)` vs `setImmediate`**: the only genuinely non-deterministic ordering in the entire Node.js event loop. The Node.js documentation explicitly acknowledges this. All other orderings (inside I/O callbacks, or between nextTick/microtasks and the event loop) are fully deterministic.
- **Multiple `process.nextTick` callbacks**: they run in FIFO order. If `H` scheduled another `nextTick`, it would run before `I` (the Promise microtask) — the entire nextTick queue drains before the microtask queue.

### Follow-up Questions
- "What if `setTimeout(fn, 0)` was replaced with `setTimeout(fn, 100)`?" → E fires ~100ms after D, well into future event loop iterations. F still fires before E (same Check phase as the I/O callback).
- "Why does `process.nextTick` run before Promise microtasks?" → Historical: `nextTick` predates Promises in Node.js and was implemented as a separate, higher-priority queue. The Promise microtask queue was added later. Node.js preserved this ordering for backwards compatibility, though in browsers (where Node.js-style `nextTick` doesn't exist), Promise microtasks have no such competitor.

## Problem 2 — Diagnosing and Fixing Thread Pool Starvation

### Problem
A production Node.js API server handles file-upload processing. Each request calls `crypto.pbkdf2` (password hashing) and `fs.readFile` (loading a template). Under load (50 concurrent requests), response times balloon from ~100ms to 3000ms. Diagnose why, and fix it.

### Pattern Recognition
Thread pool starvation — both `crypto.pbkdf2` and `fs.readFile` consume libuv thread pool threads. With the default pool of 4 threads and 50 concurrent requests each doing two thread-pool operations, the queue depth is enormous.

### Key Insight
Thread pool operations queue up when all threads are busy. The apparent concurrency of `async/await` is illusory for thread-pool operations — they're concurrent from JavaScript's perspective but serialized through the thread pool. Increasing pool size and reducing thread pool usage are the two levers.

### Solution

```js
// DIAGNOSIS: measure thread pool contention
// Add timing to see the queuing effect:
async function diagnosePoolContention() {
  const iterations = 20;
  const times = [];

  for (let i = 0; i < iterations; i++) {
    const start = Date.now();
    await new Promise((resolve, reject) => {
```

## Problem 3 — Building a Timer-Based Rate Limiter Using the Event Loop

### Problem
Implement a rate limiter that allows at most N operations per time window using only Node.js timer mechanisms — no external libraries. Demonstrate understanding of libuv's timer behavior (minimum delay, ordering).

```js
const limiter = createRateLimiter({ maxOps: 3, windowMs: 1000 });

await limiter.acquire(); // immediately
await limiter.acquire(); // immediately
await limiter.acquire(); // immediately
await limiter.acquire(); // waits ~1000ms (window refills)
```

### Pattern Recognition
Sliding window rate limiting using `setTimeout` for delayed resolution of queued Promises, with awareness of how libuv's timer min-heap schedules callbacks.

### Key Insight
`setTimeout`'s callback fires in the Timers phase after the specified delay — not exactly after, but never before. Queued `acquire()` calls resolve in the correct order because libuv's min-heap delivers timer callbacks in expiration-time order, and we schedule each queued waiter's timeout at the precise time the window refills.

### Solution

```js
function createRateLimiter({ maxOps, windowMs }) {
  // Sliding window: track when each operation "expires" from the count
  const operationTimestamps = []; // sorted queue of when each op was acquired
  const waitQueue = [];            // Promises waiting for capacity

  function acquire() {
    return new Promise((resolve) => {
      tryAcquire(resolve);
    });
  }

  function tryAcquire(resolve) {
    const now = Date.now();

    // Remove operations that have left the current window
    while (operationTimestamps.length > 0 && operationTimestamps[0] <= now - windowMs) {
      operationTimestamps.shift();
    }

    if (operationTimestamps.length < maxOps) {
      // Capacity available: record this operation and resolve immediately
      operationTimestamps.push(now);
      resolve();
    } else {
      // No capacity: calculate exactly when the oldest operation expires
      // and schedule a retry at that moment
      const oldestExpiry = operationTimestamps[0] + windowMs;
      const delayUntilExpiry = oldestExpiry - now;

      // Schedule resolution via setTimeout — libuv's Timers phase handles this
      // The minimum delay is 1ms per libuv; actual delay may be slightly longer
      // depending on event loop iteration time and OS timer resolution
      setTimeout(() => tryAcquire(resolve), delayUntilExpiry);
    }
  }

  return { acquire };
}

// Demonstration:
async function demo() {
  const limiter = createRateLimiter({ maxOps: 3, windowMs: 1000 });

  console.time('total');

  // These 3 acquire immediately (within the 3-op/1s window):
  await limiter.acquire(); console.log(`Op 1 at ${Date.now() % 10000}ms`);
  await limiter.acquire(); console.log(`Op 2 at ${Date.now() % 10000}ms`);
  await limiter.acquire(); console.log(`Op 3 at ${Date.now() % 10000}ms`);

  // This waits until the window refills (~1000ms later):
  await limiter.acquire(); console.log(`Op 4 at ${Date.now() % 10000}ms`); // ~1000ms later

  // This is immediate again (window has 3 slots, only 1 used):
  await limiter.acquire(); console.log(`Op 5 at ${Date.now() % 10000}ms`);

  console.timeEnd('total');
}

demo();
// Output:
// Op 1 at Tms
// Op 2 at Tms      (effectively same ms as Op 1 — synchronous resolution)
// Op 3 at Tms
// Op 4 at T+1000ms (waited for the window to refill)
// Op 5 at T+1000ms (immediate — within the new window)
// total: ~1000ms
```

### Verification

```js

// (Timer callbacks fire in the Timers phase, AFTER the delay)

setTimeout(() => {
  const actual = Date.now() - start;
  console.log(`Requested 100ms delay, actual: ${actual}ms`);
  // Actual is always ≥ 100ms; typically 100-102ms depending on system load
}, 100);

// Test minimum delay:
setTimeout(() => console.log('0ms timer'), 0);
// Actually fires after ~1ms (libuv minimum) — demonstrates why
// multiple setTimeout(fn, 0) calls don't all fire in the same Timers phase
```

### Edge Cases
- **libuv timer minimum**: `setTimeout(fn, 0)` has a minimum delay of 1ms. Rate limiters using very small windows (< 10ms) may have imprecise timing due to this floor plus OS scheduling jitter.
- **Many waiters**: if 1000 calls to `acquire()` pile up, 1000 `setTimeout` calls are queued in libuv's min-heap. They all fire at the correct time (when the window refills), but each invocation of `tryAcquire` sees the up-to-date `operationTimestamps` array and correctly allows exactly `maxOps` through.

### Follow-up Questions
- "How does `setInterval` differ from recursive `setTimeout` for periodic tasks?" → `setInterval` fires at a fixed interval from the initial schedule; drift accumulates if callbacks run longer than the interval. Recursive `setTimeout(fn, delay)` (re-scheduling inside the callback) measures the delay from when the callback *completes*, so the interval between executions is `delay + callbackExecutionTime` — it never "stacks up" concurrent calls.

## Quick Reference — libuv Internals

```
EVENT LOOP PHASES (per iteration):
─────────────────────────────────────────────────────────────────────
[between every phase]: process.nextTick queue, then Promise microtask queue

1. TIMERS PHASE:        Fire expired setTimeout / setInterval callbacks
                        (uses min-heap: O(log n) insert/remove, O(1) min-lookup)

2. PENDING CALLBACKS:   I/O callbacks deferred from previous iteration

3. IDLE / PREPARE:      Internal libuv use only

4. POLL PHASE:          epoll_wait / kqueue / IOCP
                        - Retrieves I/O events from OS kernel
                        - Blocks if no pending timers/immediates and no ready events
                        - Timeout = min(soonest timer expiry, -1 if none)
                        - Woken by: I/O ready, thread pool completion (via uv_async_t)

5. CHECK PHASE:         Fire setImmediate callbacks

6. CLOSE CALLBACKS:     socket.on('close'), etc.

─────────────────────────────────────────────────────────────────────
THREAD POOL (default 4 threads, max 1024 via UV_THREADPOOL_SIZE):
─────────────────────────────────────────────────────────────────────
Uses thread pool:                     Does NOT use thread pool:
  fs.* (all file operations)            net / http / https
  dns.lookup (getaddrinfo)              dns.resolve (uses c-ares)
  crypto.pbkdf2, crypto.scrypt          child_process I/O pipes
  crypto.randomBytes (sometimes)        UDP / TCP sockets
  Native add-on uv_queue_work           Timers, setImmediate

Starvation: all N threads busy → subsequent ops queue → latency spikes
Fix: UV_THREADPOOL_SIZE=N (before startup), caching, worker_threads

─────────────────────────────────────────────────────────────────────
TIMER ORDERING (deterministic rules):
─────────────────────────────────────────────────────────────────────
process.nextTick  → ALWAYS runs before Promise microtasks
Promise .then     → ALWAYS runs before any event loop phase
setImmediate      → Check phase (same iteration as triggering I/O callback)
setTimeout(fn,0)  → Next Timers phase (at least 1ms later)

FROM WITHIN AN I/O CALLBACK: setImmediate ALWAYS before setTimeout(fn,0)
FROM TOP-LEVEL (main module): setTimeout(fn,0) vs setImmediate — NON-DETERMINISTIC

─────────────────────────────────────────────────────────────────────
HANDLES vs REQUESTS:
─────────────────────────────────────────────────────────────────────
Handle (long-lived): uv_tcp_t, uv_timer_t, uv_fs_event_t
  → Keeps event loop alive while active (ref'd)
  → .unref() = don't keep event loop alive
  → .ref() = restore default (keep loop alive)

Request (short-lived): uv_fs_t, uv_work_t, uv_getaddrinfo_t
  → Single async op, freed on completion
```

## Common Bugs Checklist

Before shipping Node.js code with async I/O or timers, verify:

1. **Thread pool starvation: are multiple `fs.*`, `crypto.pbkdf2`, or `dns.lookup` calls happening concurrently?** — With default 4 threads, concurrent thread-pool operations queue up. Profile with timing logs or `clinic.js` / `0x` flamegraphs. Fix with `UV_THREADPOOL_SIZE`, caching, or `worker_threads`.

2. **`process.nextTick` recursion: is any `nextTick` callback unconditionally scheduling another `nextTick`?** — This starves the event loop, preventing I/O callbacks, timers, and `setImmediate` from ever running. Replace recursive `nextTick` with recursive `setImmediate` if yielding to I/O is acceptable.

3. **Depending on `setTimeout(fn, 0)` vs `setImmediate` ordering at the top level?** — This ordering is non-deterministic at the module level. If ordering matters, use either one exclusively, or put both in an I/O callback where `setImmediate` is guaranteed to precede `setTimeout(fn, 0)`.

4. **Using `dns.lookup` (thread pool) instead of `dns.resolve` (non-blocking) for high-concurrency DNS?** — Under load, many `dns.lookup` calls (used by default in `http.get`) exhaust the thread pool. Configure the HTTP agent with a custom DNS resolver or use `dns.resolve` + manual socket management.

5. **Long-running synchronous code in the main thread blocking the event loop?** — Synchronous code (including synchronous `fs.readFileSync`, `JSON.parse` of large strings, CPU-intensive computation) blocks the entire event loop — no I/O callbacks, timers, or requests are processed while it runs. Use `worker_threads` for CPU-intensive work. Monitor with `--perf-basic-prof` or `clinic.js doctor`.

6. **Not handling thread pool completion races: are you assuming all concurrent `Promise.all` file reads complete in a predictable order?** — Thread pool tasks complete in the order the OS schedules them (first-available thread), not submission order. Don't rely on `Promise.all([readA, readB, readC])` completing A before B before C.

7. **Forgetting `ref()`/`unref()` on timers used as background heartbeats?** — A long-running `setInterval` prevents process exit even after all real work is done. Call `.unref()` on background timers that shouldn't hold the process open. Similarly, `server.unref()` allows the process to exit naturally if the server is only kept for graceful shutdown handling.
