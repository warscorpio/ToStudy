# V8 Heap Structure: New Space (Scavenger), Old Space (Mark-Compact) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the V8 heap and how is it structured at a high level?**

A: The V8 heap is the region of memory where JavaScript objects, strings, and closures are allocated. V8 divides it into several distinct **spaces**, each with a different allocation strategy and GC algorithm tailored to the lifetime and size characteristics of its occupants:

```
┌──────────────────────────────────────────────────────────────────┐
│                         V8 HEAP                                   │
│                                                                    │
│  ┌──────────────────────────────┐  ┌──────────────────────────┐  │
│  │       NEW SPACE              │  │       OLD SPACE           │  │
│  │   (Young Generation)         │  │   (Old Generation)        │  │
│  │   ~1–16 MB (adaptive)        │  │   up to ~1.5 GB (64-bit)  │  │
│  │                              │  │                           │  │
│  │  ┌────────┐  ┌────────┐     │  │   Objects that survived   │  │
│  │  │Nursery │  │ Inter- │     │  │   2+ Minor GCs            │  │
│  │  │(From)  │  │mediate │     │  │   (long-lived)            │  │
│  │  │        │  │ (To)   │     │  │                           │  │
│  │  └────────┘  └────────┘     │  │   GC: Mark-Compact        │  │
│  │   GC: Scavenger (copying)   │  │                           │  │
│  └──────────────────────────────┘  └──────────────────────────┘  │
│                                                                    │
│  ┌──────────────────┐  ┌──────────────┐  ┌────────────────────┐  │
│  │  LARGE OBJECT    │  │ CODE SPACE   │  │    MAP SPACE       │  │
│  │  SPACE           │  │              │  │                    │  │
│  │  Objects >512KB  │  │  JIT-compiled│  │  Hidden class      │  │
│  │  Never moved     │  │  bytecode    │  │  descriptors (Maps) │  │
│  └──────────────────┘  └──────────────┘  └────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
```

The two most important spaces are **new space** (where all fresh allocations go) and **old space** (where long-lived objects eventually end up). They use completely different GC algorithms because their object populations have different characteristics: new space is mostly garbage (the "generational hypothesis"), old space contains survivors.

**Q2. What is the generational hypothesis and why does it justify a split heap?**

A: The generational hypothesis is an empirically observed pattern in most programs: **most objects die young**. Objects created during a function call, a request handler, or a render cycle tend to become unreachable within milliseconds of allocation. A small fraction of objects — configuration, caches, long-lived data structures — survive indefinitely.

If you run one GC over the entire heap to reclaim all garbage, you spend most of your time tracing and re-verifying objects that were long-lived last time and will be long-lived again. Splitting the heap into generations optimizes for the common case:

```
Object created
     │
     ▼
  NEW SPACE ──── 99% of allocations die here ───> freed by cheap Minor GC
     │           (fast, small, frequent)
     │ 1% survive long enough
     ▼
  OLD SPACE ──── Major GC runs infrequently, only when old space fills up
                 (slower, larger, rare)
```

Minor GC on new space (Scavenger) is extremely fast — it only needs to trace **live** objects, which are few. Major GC on old space (Mark-Compact) is expensive but runs rarely because only survivors accumulate there.

## Section 2: New Space and the Scavenger

**Q3. How is new space structured and how are objects allocated in it?**

A: New space is divided into two equal-sized **semi-spaces**. In modern V8 these are called **Nursery** (where brand-new objects land) and **Intermediate** (where first-time survivors land). Older literature calls them **from-space** and **to-space** — the roles are equivalent.

```
NEW SPACE
┌─────────────────────┬─────────────────────┐
│      NURSERY        │    INTERMEDIATE      │
│   (from-space)      │    (to-space)        │
│                     │                      │
│  ████████░░░░░░░░░  │  (empty)             │
│  ↑ allocated so far │                      │
│                     │                      │
│  Allocation pointer │                      │
│  bumps forward ──►  │                      │
└─────────────────────┴─────────────────────┘
         ↑ Minor GC triggered when this fills up
```

Object allocation in new space is a **bump-pointer allocation** — the single fastest possible allocation strategy. V8 maintains an allocation pointer and a limit pointer. Allocating an object of size N:

```cpp
// Conceptually (V8 internals):
if (alloc_ptr + N <= limit_ptr) {
    object = alloc_ptr;
    alloc_ptr += N;          // Bump the pointer
    return object;           // O(1), no list traversal, no locking
}
// else: trigger Minor GC to make room
```

This is why object allocation in V8 is nearly free — a pointer increment and a bounds check. The nursery is typically 1–8 MB (adaptive, based on allocation rate). When it fills, the Scavenger runs.

**Q4. How does the Scavenger (Minor GC) work — step by step?**

A: The Scavenger implements **Cheney's copying algorithm** — a breadth-first copying traversal. It operates only on new space and runs in a stop-the-world pause (though V8's parallel Scavenger uses multiple threads to reduce pause time):

```
BEFORE SCAVENGE:
Nursery (from-space):
┌────────────────────────────────────────────────┐
│  A(live) │ B(dead) │ C(live) │ D(dead) │ E(live)│
└────────────────────────────────────────────────┘
  ↑ root references: A, C, E

Intermediate (to-space):
┌────────────────────────────────────────────────┐
│  (empty)                                        │
└────────────────────────────────────────────────┘
```

**Step 1 — Start from roots.** V8 scans GC roots: stack frames, global handles, CPU registers, and **remembered set entries** (old-space → new-space pointers — more on this in Section 5). Every root pointing into the nursery is a live object.

**Step 2 — Copy live objects.** For each live object found:
- Copy it verbatim into the intermediate semi-space (to-space), compacting as it goes
- Write a **forwarding pointer** at the original location: "I moved to address X"
- Update the root pointer to point to the new location

**Step 3 — Scan copied objects transitively.** Each copied object may itself contain pointers to other nursery objects. Scan those pointers and copy their targets too, following references breadth-first until no new live objects are found.

**Step 4 — Flip.** The old nursery (now containing only dead objects and forwarding pointers) is abandoned wholesale — no individual reclamation needed. The intermediate space (now containing all live objects, compacted) becomes the new nursery for the next allocation. The old nursery becomes the new to-space.

```
AFTER SCAVENGE:
Former nursery (now to-space / empty):
┌────────────────────────────────────────────────┐
│  fwd→X │ (dead) │ fwd→Y │ (dead) │ fwd→Z       │
└────────────────────────────────────────────────┘
  (entire space abandoned — reclaimed in bulk)

Former intermediate (now nursery):
┌────────────────────────────────────────────────┐
│  A'    │ C'     │ E'     │ (free)              │
└────────────────────────────────────────────────┘
  (compacted, allocation pointer reset to after E')
```

The Scavenger's cost is proportional to **live objects only**, not to total allocation. If 95% of new-space objects are dead, the Scavenger only does 5% of the theoretical work — this is why Minor GC pauses are short (typically <1ms on healthy workloads).

**Q5. What determines when an object gets promoted to old space?**

A: An object is promoted from new space to old space under two conditions:

**Condition 1 — Survived two Scavenges:**
Objects that survive the first Scavenge move from nursery to the intermediate semi-space. Objects that survive a second Scavenge (still reachable when the intermediate space is collected) are **promoted** — copied directly into old space instead of back into the nursery.

```
Allocation → Nursery
     │
     │ Scavenge #1: still live?
     ▼
  Intermediate semi-space
     │
     │ Scavenge #2: still live?
     ▼
  OLD SPACE  ← promoted, never subject to Minor GC again
```

**Condition 2 — To-space fill threshold:**
During a Scavenge, if the to-space (intermediate) would exceed 25% occupancy after copying a live object, that object is promoted directly to old space instead. This prevents the intermediate semi-space from becoming so full that the next Scavenge immediately needs to promote everything. It's a heuristic to keep Minor GC cost predictable.

**Condition 3 — Large object fast path:**
Objects exceeding ~512 KB (one V8 heap page) are never allocated in new space at all — they go directly to Large Object Space and are never moved.

```typescript
// Objects that tend to stay in new space (short-lived):
function handleRequest(req: Request): Response {
  const parsed = JSON.parse(req.body);          // Temporary object — dies after return
  const result = transform(parsed);             // Temporary — dies after return
  return new Response(JSON.stringify(result));  // Dies after response is sent
}

// Objects that tend to be promoted (long-lived):
const cache = new Map<string, CacheEntry>();    // Module-level — lives forever
const config = loadConfig();                    // Read once, used always — promoted quickly
```

**Q6. What is "minor Mark-Compact" and how does it differ from Scavenger?**

A: In newer V8 versions (Node.js v18+), V8 introduced a **Minor Mark-Compact** algorithm as an alternative to the Scavenger for young generation collection. Instead of the copying semi-space approach, it runs a simplified version of the full Mark-Compact algorithm restricted to new space objects:

1. **Mark** live objects in new space using the standard marking algorithm
2. **Compact** by moving live objects to consolidate free space

The advantage over Scavenger: Minor Mark-Compact does not need a second semi-space as "to-space" — it operates in place, reducing new space's memory footprint by half. The tradeoff: it requires pointer update bookkeeping (since it moves objects without forwarding pointers being visible to the JS heap the same way).

V8 chooses between Scavenger and Minor Mark-Compact based on heuristics — allocation rate, heap pressure, and available memory. For interviews, the Scavenger semi-space model is the canonical answer; mentioning Minor Mark-Compact demonstrates awareness of V8's ongoing evolution.

## Section 3: Old Space and Mark-Compact

**Q7. What is old space and what triggers a Major GC (Mark-Compact)?**

A: Old space (the old generation) holds all promoted objects — objects that survived at least two Minor GCs, plus large objects that were never in new space. Its size grows dynamically as more objects are promoted, up to `--max-old-space-size` (default ~1.5 GB on 64-bit systems).

A Major GC is triggered when old space is **nearly full** — V8 monitors the ratio of used old-space bytes to total old-space bytes and triggers marking when the heap grows beyond a dynamic threshold. The threshold itself is adaptive: if the previous Major GC freed a lot, V8 delays the next one; if it freed little, V8 triggers sooner.

```typescript
// Trigger pattern — promote enough objects to fill old space:
const longLivedArray: object[] = [];

setInterval(() => {
  // These objects survive multiple GC cycles → promoted → accumulate in old space
  longLivedArray.push({ timestamp: Date.now(), data: new Array(1000).fill(0) });
  // Eventually old space hits the threshold → Major GC triggers
}, 10);
```

```
process.memoryUsage() over time with a leak:
{
  heapUsed:  50 MB  ← right after startup
  heapUsed: 120 MB  ← after 30s of accumulation
  heapUsed:  80 MB  ← Major GC ran, freed some
  heapUsed: 160 MB  ← growing again — the retained objects are real leaks
  ...               ← eventually OOM if leak isn't fixed
}
```

**Q8. How does tri-color marking work in the Mark-Compact algorithm?**

A: Tri-color marking assigns every heap object one of three colors representing its state in the marking traversal:

| Color | Meaning | Invariant |
|---|---|---|
| **White** | Not yet visited | Assumed garbage until proven otherwise |
| **Grey** | Discovered (reachable), but outgoing pointers not yet scanned | In the marking worklist |
| **Black** | Fully scanned — all pointers followed | No black object may point to a white object |

The algorithm:

```
Step 1 — Mark roots grey:
  GC roots (stack variables, global handles, CPU registers):
  → All objects directly referenced by roots become GREY
  → Added to the marking worklist (a queue/stack)

Step 2 — Process the worklist (drain grey objects to black):
  While worklist is not empty:
    obj = worklist.pop()
    for each pointer field in obj:
      if field points to a WHITE object:
        mark it GREY, add to worklist
    mark obj BLACK

Step 3 — When worklist is empty:
  All BLACK objects are live (reachable from roots)
  All WHITE objects are garbage (unreachable) → reclaim
```

The **tri-color invariant** — no black object points to a white object — is what guarantees correctness. If this invariant holds when the worklist empties, every reachable object has been marked black. The write barrier (Q12) maintains this invariant during incremental marking.

```
Example object graph:

  ROOT ──► A(grey) ──► B(white)
                └────► C(white) ──► D(white)

After processing A:
  A becomes black; B and C become grey

After processing B:
  B becomes black; no new grey objects (B has no pointers)

After processing C:
  C becomes black; D becomes grey

After processing D:
  D becomes black; worklist empty

Result: A, B, C, D are all BLACK → all live
Any white objects not shown → garbage → swept
```

**Q9. What is the difference between the sweeping and compaction phases?**

A: After marking, V8 knows which objects are live (black) and which are garbage (white). It then reclaims the garbage — but has two strategies for doing so:

**Sweeping (always runs):**
Walk through old space linearly. For every white (dead) object encountered, add its memory region to a **free list** — a data structure that tracks available gaps. Future allocations in old space draw from the free list. Fast but leaves fragmentation — the heap looks like Swiss cheese, with live objects interspersed with free gaps.

```
After sweeping:
┌─────────────────────────────────────────────────┐
│ [live] │ [free] │ [live] │ [free][free] │ [live] │
└─────────────────────────────────────────────────┘
          ↑ Free list entries — allocations may find these insufficient
            for large objects even though total free bytes is large
```

**Compaction (runs only when fragmentation warrants it):**
Move all live objects to the beginning of old space, updating every pointer that referenced a moved object. Eliminates fragmentation entirely — leaves a large contiguous free region at the end.

```
After compaction:
┌─────────────────────────────────────────────────┐
│ [live] │ [live] │ [live] │ [free .......        │
└─────────────────────────────────────────────────┘
                             ↑ One large contiguous free region
                               bump-pointer allocation possible again
```

Compaction is expensive: every live object must be copied, and every pointer to each moved object must be found and updated (V8 maintains "slots" — recorded pointer locations — to make this feasible). V8 only compacts pages that are sufficiently fragmented (below a threshold of live-bytes-to-page-size ratio), trading off compaction cost against allocation efficiency.

**Q10. Why does V8 segregate old space into separate Map Space and Code Space?**

A: Certain old-space object types benefit from isolation:

**Map Space:** Stores V8's **hidden class descriptors** (called "Maps" in V8 internals — not the JS `Map` type). Every JavaScript object has an associated Map that describes its shape: property names, property types, prototype chain. Maps are frequently accessed during property lookups and must have predictable memory layout for V8's optimizing compiler. Isolating them makes pointer enumeration during GC more efficient (Maps have a known structure) and improves CPU cache behavior for property lookups.

**Code Space:** Stores JIT-compiled native machine code generated by V8's Turbofan and Sparkplug compilers. Code objects must have **executable permissions** (`rwx` on the memory pages), while data objects must not. Mixing them would require executable permissions on data pages — a security vulnerability. Isolating code objects into their own space allows the OS to mark data pages as non-executable (W^X policy).

**Large Object Space:** Stores objects exceeding one V8 heap page (~512 KB). These are never moved during compaction because updating all pointers to a large object is prohibitively expensive and large objects are rare. The Mark-Sweep algorithm reclaims them without relocation.

## Section 4: Incremental and Concurrent GC

**Q11. What is a stop-the-world pause and why is it a problem?**

A: A stop-the-world (STW) pause is a period during which the JavaScript thread is completely suspended while the GC runs. During a STW pause, no JS code executes — HTTP requests time out, frames drop, timers stall, and IPC messages queue up.

```
Without incremental GC (naive Major GC):
────────── JS ──────────┬──── GC (STW, 200ms) ────┬─── JS ────────────
                         ↑                          ↑
                   All JS pauses             JS resumes
                  (requests stall,          (requests complete,
                   frames drop)              delayed by 200ms)
```

For new space, Scavenger pauses are typically <1ms — acceptable. For old space, a full Mark-Compact on a 1 GB heap can take 100–500ms — catastrophic for latency-sensitive applications. V8 addresses this with incremental and concurrent GC.

**Q12. What is incremental marking and what write barrier does it require?**

A: Incremental marking breaks the marking phase into **small increments** (~1–5ms each), interleaved with JavaScript execution. Instead of one 200ms pause, you get 100–200 increments of 1ms spread over time — the same total work, but in smaller slices the application barely notices.

```
With incremental marking:
──JS──┬GC┬──JS──┬GC┬──JS──┬GC┬──JS──┬GC┬──JS──┬sweep/compact┬──JS──
       1ms      1ms      1ms      1ms                ~5-20ms
```

The problem: while the GC is mid-marking (some objects grey, some black, some white), JavaScript keeps running and **mutating the object graph**. A new pointer from a black object to a white object would violate the tri-color invariant — the GC thinks the black object is done, so it never visits the new white target, which then gets collected while still live.

The **write barrier** is a small piece of code V8 injects at every pointer-write site that maintains the invariant:

```typescript
// Every time JS executes: obj.field = value
// V8 inserts a write barrier BEFORE the actual write:

function writeBarrier(obj: HeapObject, value: HeapObject): void {
  if (isBlack(obj) && isWhite(value)) {
    // Violation: black → white pointer about to be created
    markGrey(value);          // Make value grey — add it to the worklist
    // Now invariant holds: black → grey (not black → white)
  }
  // Proceed with the actual write
}
```

This is called the **Dijkstra write barrier** (insertion barrier). It fires on every pointer write in the program, which adds a small per-write overhead — but the overhead is far less than the latency of 200ms STW pauses.

**Q13. What is concurrent marking and how does it differ from incremental marking?**

A: Concurrent marking goes further than incremental marking: it runs the marking algorithm on **background threads** simultaneously with JavaScript execution on the main thread. The main thread barely pauses — it only stops for a brief "atomic pause" at the start (to snapshot the roots) and end (to finalize marking):

```
Incremental marking:
Main thread: ──JS──┬GC┬──JS──┬GC┬──JS──┬GC┬──JS──  (alternates)

Concurrent marking:
Main thread: ──JS──────────────────────────────┬─atomic─┬──JS──
Background:       ─────── MARKING ─────────────┘        │
                  (runs in parallel with JS)      (finalize)
```

With concurrent marking, the main thread's pauses drop to milliseconds even for gigabyte-sized heaps. The tradeoff: a more complex write barrier is needed, because now the background thread and the main thread are both accessing the object graph simultaneously:

```cpp
// Concurrent write barrier (simplified):
// When JS writes obj.field = value on the main thread:
// The background marker might be mid-traversal of obj's neighborhood.
// The barrier must ensure the background thread doesn't miss 'value'.

// V8 uses a combination of:
// 1. Snapshot-at-the-beginning (SATB): record the OLD value before overwriting
//    → background thread re-marks the old value (it was reachable before, must trace it)
// 2. Colour-checking: if the NEW value is white, mark it grey
```

V8 has used concurrent marking (as part of the **Orinoco** project) since Node.js v10 / Chrome 64. It is now the dominant GC mode for old space collection.

**Q14. What is the Orinoco project and which GC optimizations did it introduce?**

A: Orinoco is V8's multi-year project to make garbage collection mostly concurrent and parallel, minimizing main-thread pauses. It introduced several techniques that are now standard in V8:

| Feature | What it does | Introduced |
|---|---|---|
| **Parallel Scavenger** | Multiple threads run Scavenger simultaneously | Node.js v10 |
| **Concurrent Marking** | Background threads mark old space while JS runs | Node.js v10 |
| **Concurrent Sweeping** | Background threads sweep dead objects while JS runs | Node.js v10 |
| **Parallel Compaction** | Multiple threads compact old space pages simultaneously | Node.js v12 |
| **Idle-time GC** | Runs GC increments during JS idle gaps (requestIdleCallback) | Browser only |
| **Minor Mark-Compact** | Mark-Compact for young generation (reduces semi-space overhead) | Node.js v18+ |

The result: a workload that previously triggered 200ms stop-the-world pauses now typically sees <10ms pauses even for large heaps, with most marking and sweeping happening off the main thread entirely. The main thread only stops for brief atomic phases at GC boundaries.

## Section 5: Write Barriers and Remembered Sets

**Q15. What is a write barrier and why is it needed for generational GC (not just incremental)?**

A: The write barrier serves two distinct purposes in V8, corresponding to two different GC challenges:

**Purpose 1 — Incremental/concurrent marking (tri-color invariant):**
As covered in Q12, the write barrier maintains the tri-color invariant during incremental marking. This is the "marking write barrier."

**Purpose 2 — Generational GC (inter-generational pointer tracking):**
The Scavenger only traces new space objects. But an old-space object can hold a pointer to a new-space object — if the Scavenger doesn't know about this pointer, it will think the new-space object is unreachable and collect it, creating a dangling pointer in the old-space object.

```typescript
// Example: old-space object pointing to new-space object
const cache: Map<string, object> = new Map();   // Promoted to old space long ago

function handleRequest() {
  const freshResult = computeResult();          // Allocated in new space
  cache.set('latest', freshResult);             // Old-space Map now points to new-space freshResult
}
// When Minor GC runs: freshResult appears unreachable unless the GC
// finds the old-space → new-space pointer in cache.
// Without tracking this, freshResult gets collected — cache now holds a dangling pointer.
```

The **generational write barrier** fires whenever a pointer is written into an old-space object:

```cpp
// When JS executes: oldSpaceObject.field = newSpaceValue
void generationalWriteBarrier(HeapObject* oldObj, HeapObject* newValue) {
  if (isInNewSpace(newValue)) {
    // Record that 'oldObj' now contains a new-space pointer
    rememberedSet.add(addressOf(oldObj.field));
    // → During the next Minor GC, scan remembered set entries as additional roots
  }
}
```

**Q16. What is the card table and how does it implement the remembered set efficiently?**

A: Scanning all of old space to find inter-generational pointers before every Minor GC would be prohibitively expensive. The **card table** implements the remembered set efficiently using a compact bitmap:

```
OLD SPACE (conceptually):
┌─────────────────────────────────────────────────────────┐
│ card 0  │ card 1  │ card 2  │ card 3  │ card 4  │ ...  │
│ 512 bytes each                                          │
└─────────────────────────────────────────────────────────┘

CARD TABLE (1 byte per card):
┌───┬───┬───┬───┬───┬─────┐
│ 0 │ 1 │ 0 │ 1 │ 0 │ ... │   ← 1 = "dirty" (contains new-space pointer)
└───┴───┴───┴───┴───┴─────┘
          ↑       ↑
       card 1   card 3 are dirty — scan these during Minor GC
```

When the generational write barrier fires (a pointer to new space is written into old space), it **marks the card** containing the write location as "dirty" — a single byte write:

```cpp
void cardTableWriteBarrier(HeapObject* slotAddress, HeapObject* value) {
  if (isInNewSpace(value)) {
    uint8_t* card = cardTable + (uintptr_t(slotAddress) >> 9);  // 512-byte cards
    *card = DIRTY;   // Mark card dirty — O(1), extremely cheap
  }
}
```

During Minor GC, V8 scans only the dirty cards in old space (instead of all of old space), finds the new-space pointers within them, and adds those as additional GC roots. After the Minor GC, dirty cards are cleared.

The card table overhead: 1 byte per 512 bytes of old space = ~0.2% memory overhead. For a 1 GB old space, the card table is ~2 MB — cheap, and it fits in CPU cache.

## Section 6: Memory Diagnostics

**Q17. How do you measure and interpret V8 heap memory in Node.js?**

A: `process.memoryUsage()` returns a snapshot of the current memory state:

```typescript
const usage = process.memoryUsage();
// {
//   rss:          150_994_944,   // Resident Set Size — total process memory in OS
//   heapTotal:     85_196_800,   // V8 heap committed from OS (includes free pages)
//   heapUsed:      62_414_312,   // Actually used by live objects
//   external:       1_423_216,   // C++ memory owned by V8-bound JS objects (Buffers)
//   arrayBuffers:   1_049_600    // Memory for ArrayBuffers and SharedArrayBuffers
// }
```

Interpreting the numbers:

| Field | What it tells you | Red flag |
|---|---|---|
| `heapUsed` | Live objects (closures, objects, strings) | Grows monotonically without GC cycles → leak |
| `heapTotal` | Memory committed from OS — always ≥ heapUsed | Much larger than heapUsed = fragmentation or over-reservation |
| `rss` | Total process footprint (heap + stack + native code + OS overhead) | Growing while heapUsed is stable → native/Buffer leak |
| `external` | Buffers, TypedArrays, native bindings | High when using binary protocols or image processing |
| `arrayBuffers` | Subset of external for ArrayBuffer/SharedArrayBuffer | High with streaming or binary IO |

```typescript
// Memory leak detection: sample heapUsed over time after forced GC
import v8 from 'v8';

// Requires --expose-gc flag: node --expose-gc server.js
function measureAfterGC(): number {
  global.gc?.();                        // Force a full GC cycle
  return process.memoryUsage().heapUsed;
}

// If heapUsed keeps growing after GC cycles → genuine leak (GC can't collect it)
// If heapUsed drops significantly after GC → allocation spike, not a leak

// Heap statistics with more detail:
const stats = v8.getHeapStatistics();
// {
//   total_heap_size: 85_196_800,
//   used_heap_size:  62_414_312,
//   total_available_size: 1_526_909_736,    ← how much old space can still grow
//   heap_size_limit: 1_610_612_736,         ← --max-old-space-size ceiling
//   malloced_memory: 319_504,
//   peak_malloced_memory: 1_170_664,
//   does_zap_garbage: 0,
//   number_of_native_contexts: 1,
//   number_of_detached_contexts: 0          ← > 0 means detached context leak
// }

// Space-by-space breakdown:
const spaceStats = v8.getHeapSpaceStatistics();
// [
//   { space_name: 'read_only_space', ... },
//   { space_name: 'new_space', space_used_size: 1_234_567, ... },
//   { space_name: 'old_space', space_used_size: 59_000_000, ... },
//   { space_name: 'code_space', ... },
//   { space_name: 'map_space', ... },
//   { space_name: 'large_object_space', ... },
// ]
```

For production leak detection, generate heap snapshots:

```typescript
import v8 from 'v8';
import fs from 'fs';
```

**Q18. What V8 flags control heap sizes and when should you tune them?**

A: The most commonly tuned flags in production Node.js deployments:

```bash
# Old space (most impactful for memory-intensive apps):
node --max-old-space-size=4096 server.js    # 4 GB old space limit
# Default: ~1.5 GB on 64-bit (historically 1.76 GB, now adaptive)
# Set this when: process OOMs before running out of physical RAM

# New space size:
node --max-new-space-size=64 server.js      # 64 MB new space (note: units are KB in some versions)
# Larger new space → fewer Minor GC cycles → higher per-GC pause
# Smaller new space → more frequent Minor GC → lower per-GC pause, higher CPU overhead
# Tune when: profiling shows Minor GC rate is too high or too low

# Total heap hard cap:
node --max-heap-size=8192 server.js         # 8 GB total heap
# Useful when running in containers with strict memory limits

# Expose gc() for debugging/profiling only — never in production:
node --expose-gc server.js                  # Enables global.gc()

# Trace GC events to stderr (useful during load testing):
node --trace-gc server.js
# Output example:
# [gc] ... Scavenge 2.1 / 16.0 ms -> 2.0 / 16.0 ms, 1.2 / 0.0 / 0.0 ms
#          ↑ before    ↑ limit     ↑ after  ↑ limit   ↑ wall ↑ user ↑ idle
```

```typescript
// Container-aware heap sizing: set --max-old-space-size to ~75% of container RAM
// to leave headroom for OS, native modules, and new space:

// In a Dockerfile or start script:
// node --max-old-space-size=$(node -e "console.log(Math.floor(require('os').totalmem() / 1024 / 1024 * 0.75))") server.js

// Or compute dynamically:
const totalMemMB = Math.floor(require('os').totalmem() / 1024 / 1024);
const oldSpaceMB = Math.floor(totalMemMB * 0.75);
// Spawn child with: --max-old-space-size=${oldSpaceMB}
```

Common mistake: not setting `--max-old-space-size` in containers. The default was calculated for full-RAM machines; a container with a 512 MB memory limit will OOM-kill the process at the OS level without ever triggering V8's GC, because V8 thinks it has 1.5 GB available.

## Section 7: Scenario-Based Questions

**Q19. "What are the most common V8 memory leak patterns and how do you diagnose each?"**

A:

**Pattern 1 — Closures retaining large outer-scope objects:**
```typescript
// LEAK: 'largeData' is retained by the returned closure indefinitely
function createHandler(largeData: Buffer) {
  const processed = process(largeData);   // Wanted: just 'processed'
  return function handler(req: Request) {
    // 'handler' closes over 'largeData' even if it only uses 'processed'
    return processed;
    // largeData stays in memory as long as handler exists
  };
}

// FIX: nullify the reference after extracting what you need
function createHandler(largeData: Buffer) {
  const processed = process(largeData);
  largeData = null as any;  // Allow GC to collect it
  return function handler(req: Request) {
    return processed;
  };
}
```

**Pattern 2 — Event listener accumulation:**
```typescript
// LEAK: adding listeners without removing them
class DataPoller extends EventEmitter {
  start(emitter: EventEmitter): void {
    // Called repeatedly — listener count grows unboundedly
    emitter.on('data', (chunk) => this.emit('processed', transform(chunk)));
    //   ↑ Previous listeners never removed — each call adds one more
  }
}

// Diagnosis: emitter.listenerCount('data') growing over time
// Fix: remove before adding, or use .once() for one-shot listeners
  start(emitter: EventEmitter): void {
    emitter.removeAllListeners('data');   // Remove stale listener first
    emitter.on('data', (chunk) => this.emit('processed', transform(chunk)));
  }
```

**Pattern 3 — Unbounded caches (the most common production leak):**
```typescript
// LEAK: cache grows forever — no eviction, no TTL
const responseCache = new Map<string, CachedResponse>();

async function fetchWithCache(url: string): Promise<Response> {
  if (responseCache.has(url)) return responseCache.get(url)!;
  const response = await fetch(url);
  responseCache.set(url, response);   // Map grows monotonically
  return response;
}

// Fix: use a bounded cache with LRU eviction, or WeakRef for automatic reclamation
import { LRUCache } from 'lru-cache';
const responseCache = new LRUCache<string, CachedResponse>({ max: 1000, ttl: 60_000 });
```

**Pattern 4 — Detached DOM / context leaks (Node.js variant: detached closures in Workers):**
```typescript
// LEAK: interval holds reference to large object, never cleared
function startMonitoring(config: HeavyConfig): void {
  const interval = setInterval(() => {
    checkHealth(config);   // config (potentially large) held alive by interval closure
  }, 5000);
  // No clearInterval called — interval (and config) lives until process exit
}

// Fix: return a cleanup function
function startMonitoring(config: HeavyConfig): () => void {
  const interval = setInterval(() => checkHealth(config), 5000);
  return () => clearInterval(interval);
}
```

**Diagnosis workflow:**
```
1. node --expose-gc --max-old-space-size=256 server.js
2. Under load: send requests for 5 minutes
3. global.gc() — force a full GC
4. Record heapUsed
5. Wait 1 minute (no load)
6. global.gc() again
7. Record heapUsed

If heapUsed after step 6 is significantly > baseline → retained objects → genuine leak.

8. v8.writeHeapSnapshot('./snap1.heapsnapshot')   ← before reproduction
9. Reproduce the leak scenario
10. v8.writeHeapSnapshot('./snap2.heapsnapshot')  ← after reproduction
11. Open Chrome DevTools → Memory → Load both → Comparison view
    → Sort by "# Delta" or "Size Delta" → Find the growing object type
```

**Q20. "Explain what happens in V8 memory when this code runs, and why the process eventually OOMs."**

```typescript
const store: Record<string, unknown[]> = {};

app.post('/append', (req, res) => {
  const { key, value } = req.body;
  if (!store[key]) store[key] = [];
  store[key].push(value);            // A
  res.json({ length: store[key].length });
});

app.delete('/clear/:key', (req, res) => {
  delete store[req.params.key];      // B
  res.json({ ok: true });
});
```

A: Tracing the V8 memory lifecycle:

**Initial allocation (line A, first few requests):**
- `store` is a module-level object — it was allocated in new space, survived multiple GCs, and was promoted to old space
- Each new `value` from `req.body` is allocated in new space as a fresh object
- The `.push(value)` writes a pointer from the old-space array (`store[key]`) into the new-space `value` → **generational write barrier fires** → records this old→new pointer in the card table
- At the next Minor GC, the Scavenger finds `value` via the card table and keeps it alive, eventually promoting it

**Accumulation (many requests, no `/clear` called):**
- `store[key]` arrays grow without bound — their underlying backing stores are periodically replaced with larger arrays (JS array reallocation), all promoted to old space
- Each `value` object pushed is eventually promoted to old space — never collected because `store` (a GC root via the global module scope) holds strong references all the way down
- Old space grows with every request; Major GC runs but can only collect objects with no live references — `store` has references to everything

**Major GC cycle (old space ~80% full):**
- Concurrent marking begins on background thread
- All of `store`, its arrays, and every pushed value are marked black — they are all live
- Sweep finds nothing to collect (all live)
- Old space was not reduced — GC completed with near-zero reclamation
- V8 raises the old space limit and continues → this escalation repeats

**OOM:**
- Old space hits `--max-old-space-size` ceiling
- V8 throws a JavaScript `RangeError: JavaScript heap out of memory` **or** the process is killed by the OS (SIGKILL) if RSS exceeds the container memory limit before V8's own limit triggers
- The fix: enforce a max size per key, or use Redis / an external store that can evict entries independently of the GC

```typescript
// Fix 1: bounded per-key storage
const MAX_PER_KEY = 10_000;
store[key].push(value);
if (store[key].length > MAX_PER_KEY) store[key].shift();  // FIFO eviction

// Fix 2: WeakRef-based store (values collected if no other references)
const store: Record<string, WeakRef<unknown[]>> = {};
// But: WeakRef only helps if nobody else holds a reference — here, the array is the reference,
// so this doesn't help. The real fix is architectural: external storage.
```

## Quick Reference Table

| Concept | Detail |
|---|---|
| **New space** | Young generation — small (1–16 MB adaptive), holds brand-new objects; bump-pointer allocation |
| **Nursery** | First half of new space — objects allocated here first |
| **Intermediate** | Second half — objects that survived first Scavenge; survives again → promoted |
| **Scavenger** | Minor GC — Cheney's copying algorithm; traces only live objects; cost ∝ survivors not garbage |
| **Promotion** | Object moved to old space after surviving 2 Scavenges, or if to-space >25% full after copy |
| **Old space** | Long-lived objects; grows up to `--max-old-space-size` (default ~1.5 GB on 64-bit) |
| **Mark-Compact** | Major GC — tri-color marking + sweeping + optional compaction |
| **Tri-color invariant** | No black object points to a white object — maintained by write barrier |
| **Sweeping** | Walk heap; add dead (white) objects to free lists — leaves fragmentation |
| **Compaction** | Move live objects contiguously — eliminates fragmentation; expensive; runs when needed |
| **Large Object Space** | Objects >512 KB; allocated here directly; never moved; collected by Mark-Sweep only |
| **Map Space** | V8 hidden class descriptors; isolated for cache efficiency and GC optimization |
| **Code Space** | JIT-compiled machine code; isolated so executable-permission pages stay separate |
| **Incremental marking** | Break marking into ~1ms increments interleaved with JS; requires write barrier |
| **Concurrent marking** | Background threads mark while JS runs; main thread pauses only at atomic boundaries |
| **Write barrier (marking)** | Fires on every pointer write; maintains tri-color invariant during incremental/concurrent GC |
| **Write barrier (generational)** | Fires when old-space object gets pointer to new-space object; marks card dirty |
| **Card table** | 1 byte per 512 bytes of old space; dirty = contains new-space pointer; scanned during Minor GC |
| **Remembered set** | Logical set of old→new pointers, implemented via card table |
| **`process.memoryUsage()`** | `heapUsed` = live objects; `heapTotal` = committed; `rss` = total process; `external` = Buffers |
| **`--max-old-space-size`** | Old space ceiling in MB; set to ~75% of container RAM in containerized deployments |
| **`--expose-gc`** | Enables `global.gc()` — forced full GC; use only in profiling/debugging, never production |
| **Heap snapshot** | `v8.writeHeapSnapshot()` — full object graph; load in Chrome DevTools Memory tab; compare two snapshots to find leaks |
| **Orinoco** | V8 GC project: parallel Scavenger, concurrent marking, concurrent sweeping, parallel compaction |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) articulating the **semi-space copying mechanism** with precision — the Scavenger's cost is proportional to *live* objects, not garbage, which is why it's fast even when the nursery is 95% dead; knowing that after a Scavenge, from-space and to-space swap roles rather than being zeroed-out proves real understanding of the algorithm; (2) explaining the **two distinct purposes of the write barrier** — one for the tri-color invariant during incremental/concurrent marking (maintains old-space correctness), and one for the card table / remembered set (enables Minor GC to find old→new pointers without scanning all of old space) — conflating these two into one barrier shows shallow understanding; (3) knowing the **compaction vs sweeping distinction**: sweeping always runs (fast but leaves fragmentation), compaction runs only when fragmentation exceeds a threshold (slow but enables bump-pointer allocation again), and large objects are never compacted regardless; (4) the **`--max-old-space-size` container trap** — the default assumes a full-RAM machine; in a container with a 512 MB limit, V8 may attempt to allocate 1.5 GB, getting killed by the OOM killer before its own GC can trigger; always set this flag explicitly in containerized Node.js; and (5) the **generational hypothesis and why it matters operationally**: most production memory leaks are objects that *should* die young but are accidentally retained — understanding promotion criteria (survived 2 GCs, or to-space >25% full) tells you exactly what makes a "temporary" object permanent, which is the root cause of most heap growth issues in production.
