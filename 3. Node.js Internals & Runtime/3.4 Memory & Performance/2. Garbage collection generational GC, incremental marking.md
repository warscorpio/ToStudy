# Garbage Collection: Generational GC, Incremental Marking — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Garbage Collection Fundamentals

**Q1. What is garbage collection and what problem does it solve?**
A: Garbage collection (GC) is automatic memory management — the runtime reclaims memory occupied by objects that are no longer reachable from the program. Without it, developers must manually free memory (`free()` in C, `delete` in C++) which leads to two classes of bugs:

- **Use-after-free**: accessing memory after it has been freed — reads garbage values or corrupts other data
- **Memory leaks**: forgetting to free memory — program's RSS grows unboundedly until OOM crash

JavaScript's GC eliminates both classes by defining **reachability**: an object is alive if it can be reached by following references from a **GC root**. Anything unreachable from roots is garbage.

GC roots in a JavaScript engine:
```
GC Roots:
  ├── Global object (window / globalThis)
  ├── Currently executing call stack (local variables, parameters)
  ├── Active closures
  ├── Native C++ references held by the engine (setTimeout callbacks, event listeners)
  └── CPU registers (objects referenced by current machine code)

Anything reachable by following object references from these roots → ALIVE
Everything else → GARBAGE → can be collected
```

The core tension in GC design: **throughput vs latency**. Collecting more aggressively keeps memory low (good throughput) but pauses the program more often (bad latency). Every GC algorithm makes a different trade-off on this spectrum.

**Q2. What is the mark-and-sweep algorithm and why is it the foundation of modern GCs?**
A: Mark-and-sweep is the classic tracing GC algorithm. It runs in two phases:

**Mark phase**: Starting from GC roots, traverse the entire object graph, marking every reachable object as "live". Uses a depth-first or breadth-first traversal of references.

**Sweep phase**: Scan the entire heap linearly. Any object not marked as live is garbage — its memory is added back to the free list (or returned to the OS).

```
Heap before GC:
  [A]→[B]→[C]      A is reachable from root
  [D]→[E]           D is NOT reachable from root — garbage
  [F]               F is reachable from root via global

Mark phase:
  Start from roots → visit A (mark), visit B (mark), visit C (mark)
                   → visit F (mark)
  D and E: never reached → stay unmarked

Sweep phase:
  Scan heap: A ✓, B ✓, C ✓, D ✗ (free!), E ✗ (free!), F ✓

Heap after GC:
  [A]→[B]→[C]   [FREE][FREE]   [F]
                  ↑ returned to allocator
```

Mark-and-sweep handles **cyclic references** correctly — something reference-counting cannot do without additional mechanisms:

```js
// Reference counting fails here:
function createCycle() {
  const a = {};
  const b = {};
  a.ref = b; // a → b
  b.ref = a; // b → a (cycle!)
  // a and b each have ref count 1 — neither reaches 0 when function returns
  // Reference counting: LEAK
  // Mark-and-sweep: both unreachable from roots → collected correctly ✓
}
createCycle(); // a and b are garbage after this — mark-and-sweep handles it
```

Modern GCs (V8, SpiderMonkey, JavaScriptCore) use mark-and-sweep as their foundation, layering generational collection, incremental marking, concurrent execution, and compaction on top.

**Q3. What is a "stop-the-world" pause and why is it a problem?**
A: A stop-the-world (STW) pause is a period during which the GC suspends all JavaScript execution — the main thread halts — while the collector runs. From the application's perspective, time simply stops: no code runs, no frames render, no events fire.

The pause exists because the GC needs a **consistent snapshot** of the heap. If JavaScript ran concurrently with the GC traversal, objects could be modified mid-scan:

```
Without stop-the-world (concurrent access problem):
  GC: marks A as live, traverses A's references
  JS: A.child = null          ← severs reference during scan
  GC: marks B as live (B was A.child, now unreachable — but GC already visited)
  Result: GC missed that B became unreachable → B lives one more GC cycle (fine)
  
  Worse scenario:
  GC: has NOT yet visited C
  JS: creates new object D, stores reference only in C
      C.child = D             ← new object, not yet seen by GC
  GC: marks C as live, but C's references changed — D may be missed
  Result: D is collected while JS still holds a reference → USE AFTER FREE 💥
```

This is the **tricolor invariant** problem — more on that in incremental marking.

STW pause duration scales with heap size: a 100MB heap with 50MB of live objects requires traversing ~50MB of references — easily 100–500ms on a mobile device. At 60fps, frames must render every 16.6ms. A 100ms GC pause causes 6 dropped frames — visible jank.

```
Timeline with full STW GC:
  JS  [===run===][===run===][  GC PAUSE 150ms  ][===run===]
  UI  [frame][frame][frame][dropped dropped dropped dropped][frame]
                                ↑ user perceives stutter

Timeline goal with modern incremental/concurrent GC:
  JS  [=run=][=run=][=run=][=run=][=run=][=run=][=run=]
  GC        [.][.][.][.][.][.][.][.][.]    ← small increments
  UI  [frame][frame][frame][frame][frame][frame][frame] ← smooth
```

### Section 2: Generational Garbage Collection

**Q4. What is the generational hypothesis and why does it make GC faster?**
A: The **generational hypothesis** is an empirical observation that holds across virtually all programs in any language:

> **Most objects die young** — the majority of allocated objects become garbage within milliseconds of allocation, before their first GC cycle.

This was observed empirically across Lisp programs in the 1980s and has held true for every major language since. In JavaScript specifically:

```js
// These objects are allocated and die within one function call:
function processRequest(req) {
  const parsed   = JSON.parse(req.body);      // dies after this function
  const headers  = buildHeaders(parsed);      // dies after this function
  const response = formatResponse(headers);   // dies after this function
  return response;
}
// Every intermediate object created inside is unreachable when processRequest returns.
// In a server handling 1000 req/s: thousands of short-lived objects per second.
```

The generational hypothesis enables a fundamental optimization: **instead of scanning the entire heap every GC cycle, only scan the region where new objects live**. Since most new objects are dead, most of the heap (old objects) can be ignored.

The heap is divided into **generations**:

```
                    ┌─────────────────────────────────────────────┐
                    │                    HEAP                     │
     ┌──────────────┴──────────────┐    ┌────────────────────────┴─┐
     │       YOUNG GENERATION      │    │      OLD GENERATION       │
     │    (New Space / Nursery)    │    │   (Old Space / Tenured)   │
     │                             │    │                           │
     │  Small: 1–32MB              │    │  Large: 256MB–several GB  │
     │  Collected: every few ms    │    │  Collected: every seconds │
     │  Collection cost: ~1ms      │    │  Collection cost: 10–100ms│
     │  Objects: brand-new         │    │  Objects: long-lived      │
     └─────────────────────────────┘    └───────────────────────────┘
                    ↑                                  ↑
         Most allocations go here          Survivors promoted here
         Most die here (fast to collect)   Rarely collected (expensive but rare)
```

**Minor GC** (young gen only): fast (scans only 1–32MB), runs every few MB of allocation, pauses ~1ms.
**Major GC** (full heap): slow (scans hundreds of MB), runs when old gen is full, pauses 10–100ms.

The result: 95% of GC cycles are minor GCs — cheap, fast, frequent. The expensive major GC runs rarely. Average GC overhead is dramatically reduced compared to collecting the full heap every cycle.

**Q5. How does V8's new space (young generation) implement GC using semi-spaces?**
A: V8's young generation uses **Cheney's copying algorithm** with two **semi-spaces** of equal size. At any moment, only one semi-space is active (called "from-space"). When a minor GC triggers:

1. **Scan from roots**: find all live objects in from-space
2. **Copy live objects**: evacuate (copy) each live object into "to-space"
3. **Update references**: all pointers to copied objects are updated to the new addresses
4. **Flip spaces**: to-space becomes the new from-space; old from-space is entirely discarded

```
Before Minor GC (Scavenge):

  From-space:                       To-space:
  [ A | B | C(dead) | D | E(dead) ] [ empty                             ]
    ↑       ↑           ↑
  root     root       dead

After Minor GC:

  From-space (was to-space):        Old From-space (discarded entirely):
  [ A | B | D |                   ] [ A | B | C | D | E ] ← freed as a block
    ↑   ↑   ↑  ← compacted
  root root root

Key insight: the "sweep" phase is free — the entire old from-space
is reclaimed as a single block. No per-object bookkeeping needed.
Dead objects are simply left behind and overwritten next cycle.
```

This approach has two major advantages:
- **Allocation is O(1)**: new objects are allocated by bumping a pointer — no searching for a free slot
- **Compaction is free**: surviving objects end up contiguous in to-space — no fragmentation

The trade-off: you can only use 50% of the total new-space memory at any time (one semi-space is always empty). This is acceptable because new-space is small (1–16MB).

**Q6. What is object promotion and what determines when an object moves to old space?**
A: Objects that survive a minor GC are not immediately promoted to old space — they might still die soon. V8 promotes objects based on two criteria:

1. **Survival count**: an object that survives **two** minor GCs (i.e., it exists long enough to be copied twice) is promoted to old space. V8 stores this age in the object's header.

2. **To-space filling**: if the to-space is more than 25% full during a scavenge, surviving objects overflow directly into old space regardless of their age — this prevents the semi-space flip from running out of memory.

```
Object lifetime tracking:

Minor GC #1:
  Object X is in from-space → copied to to-space (age: 1)
  X survived once → stays in new space

Minor GC #2:
  Object X is in from-space (age: 1) → would be copied again
  V8 checks: age >= 1 (promoted after surviving once, actually depends on V8 heuristics)
  → Object X is copied to OLD SPACE instead of to-space
  → X is now "tenured" — will only be collected in major GC

// In practice, V8's promotion is based on object size too:
// Large objects (> 512KB) bypass new space entirely → allocated directly in old space
// (copying a 10MB object in every minor GC would negate the performance benefit)
```

**Q7. What is a "remembered set" (or "card table") and why is it essential for generational GC?**
A: When a GC collects only the young generation, it must find all references **into** the young generation — not just from GC roots, but also from old-generation objects. Without tracking these cross-generational references, the GC would miss old objects that reference young objects, incorrectly collecting them.

The **remembered set** is a data structure that tracks old-to-young references. Any time a reference from an old object to a young object is created, it is recorded. During minor GC, the remembered set is treated as additional roots.

The implementation uses a **card table**: the old-generation heap is divided into fixed-size "cards" (typically 512 bytes). Each card has a 1-byte "dirty bit" in the card table. When any write to an old object occurs, the card containing that object is marked dirty.

```
Write barrier — executes after EVERY heap reference write:

  obj.field = newValue;
  // ↑ compiled to:
  obj.field = newValue;                  // the actual write
  if (isOldObject(obj) && isYoungObject(newValue)) {
    cardTable[addressOf(obj) >> 9] = 1; // mark card dirty (9 = log2(512))
  }
  // This executes millions of times per second — must be extremely cheap
  // Modern CPUs: ~1–2 extra instructions — typically cache hit

Minor GC uses card table:
  For each dirty card in old space:
    Scan the 512-byte card for references pointing into new space
    Add those referenced young objects as roots
  → All young objects reachable from old space are kept alive
  → Card is then cleaned (dirty bit = 0)
```

The write barrier is a correctness requirement — without it, you could have this bug:

```js
// WITHOUT write barrier:
const cache = {};          // allocated, survives → promoted to OLD SPACE
// Minor GC runs — cache is in old space, not scanned

cache.value = freshData(); // freshData() is in NEW SPACE
                           // Without tracking this: cache.value is now an
                           // old→young reference not in remembered set

// Next minor GC: freshData() appears unreachable from roots
// (root → cache is old space, not scanned; not in remembered set)
// GC collects freshData() ← USE AFTER FREE when cache.value is accessed 💥
```

### Section 3: Incremental Marking

**Q8. What is incremental marking and how does it reduce GC pause times?**
A: Incremental marking breaks the mark phase of mark-and-sweep into small **increments** (steps) that interleave with JavaScript execution. Instead of one large STW pause that marks the entire heap, the GC does a little marking, lets JS run for a bit, then marks a little more — repeatedly until all live objects are marked.

```
Full STW mark-and-sweep (old approach):
  JS  [======= running =======][======= MARK 200ms =======][SWEEP][JS runs]
  GC                            ↑ entire heap marked at once
                                  200ms pause → 12 dropped frames

Incremental marking (modern approach):
  JS  [=JS=][=JS=][=JS=][=JS=][=JS=][=JS=][=JS=][=JS=][=JS=][JS]
  GC       [m]   [m]   [m]   [m]   [m]   [m]   [m]   [m]  [SW]
            ↑ each marking step ~1–5ms — below the 16ms frame budget
            Total marking time = 200ms but spread over 40+ steps
            Worst-case pause per step: ~5ms → no visible jank
```

V8 uses incremental marking for the **major GC** (old space). Each increment is scheduled:
- During **idle time**: when the event loop has no pending work, V8 uses deadline-aware scheduling to mark as much as possible before the next frame must render
- During **allocation**: each time JS allocates a certain amount (the "allocation step"), a fixed amount of marking work is done — this ties marking progress to allocation rate, preventing the mutator from outrunning the GC

**Q9. What is tricolor marking and why is it required for incremental marking correctness?**
A: Tricolor marking assigns every heap object one of three colors, representing its marking state. It is the invariant-preservation mechanism that keeps incremental marking correct when JavaScript modifies the heap between marking steps.

```
Colors:
  WHITE:  Not yet visited. At the end of marking: garbage.
  GRAY:   Discovered (reachable from roots) but children not yet visited.
          Represents the "marking frontier" — work remaining.
  BLACK:  Fully processed — object and ALL its direct children are gray or black.

Marking algorithm:
  1. Paint all objects WHITE
  2. Paint GC roots GRAY (add to worklist)
  3. While worklist (grays) is not empty:
     a. Take a GRAY object
     b. Paint each of its WHITE children GRAY (add to worklist)
     c. Paint the object itself BLACK
  4. At end: WHITE objects are unreachable → collect them

Invariant (must hold at all times):
  "No BLACK object may reference a WHITE object"

  If this is violated: a black object (marked live) points to a white object
  (not yet marked). If marking ends now, the white object is collected —
  but the black object still references it → use-after-free bug.
```

The problem: JavaScript runs between incremental steps and can create new references that violate the invariant:

```
Step 1 of marking:
  GC marks A (black) and discovers it references B
  GC marks B gray (added to worklist), will visit B later

JavaScript runs (between steps):
  A.child = C          // C is WHITE — not yet seen by GC
  B.child = null       // B's reference to C is severed (B was going to lead us to C)

Step 2 of marking:
  GC visits B (gray) → B.child is null → no children to gray → B becomes BLACK
  GC never visits C via B (reference was severed)
  C is not reachable from any gray or black object via unmodified refs
  GC ends: C is WHITE → collected as garbage
  But A still has A.child = C → USE AFTER FREE 💥
```

This is a **black-to-white reference introduced by the mutator** — a violation of the tricolor invariant. The write barrier fixes this.

**Q10. What is the incremental marking write barrier and what forms does it take?**
A: The write barrier for incremental marking intercepts every reference write and preserves the tricolor invariant. Two approaches:

**Dijkstra-style (snapshot-at-the-beginning / insertion barrier)**:
When a new reference is written into a BLACK object, gray the referenced (possibly WHITE) object. This ensures the invariant holds after the write.

```js
// Dijkstra write barrier — fires on EVERY reference write:
// obj.field = newValue
//   → if obj is BLACK and newValue is WHITE:
//       gray(newValue)   ← add newValue to worklist, preventing premature collection

// Example:
// A is BLACK, C is WHITE
A.child = C;
// Write barrier fires: A is black, C is white → C becomes GRAY (added to worklist)
// Now: A (black) → C (gray) — invariant restored
// GC will visit C in a future step
```

**Yuasa-style (snapshot-at-the-beginning / deletion barrier)**:
When a reference is **overwritten**, gray the **old** value before it is lost. This preserves a "snapshot" of the heap at the start of marking — anything reachable in the snapshot will be kept alive through the current cycle.

```js
// Yuasa write barrier — fires before overwriting:
// obj.field = newValue
//   → gray(obj.field)  ← gray the OLD value before it's overwritten

// Example:
// B.child used to be C (not yet visited)
// JS runs: B.child = null
// Barrier fires: gray(old value = C) ← C is added to worklist before being severed
// GC later visits C and marks it — even though the only path to it was severed
// C survives this cycle (may be collected NEXT cycle if still unreachable)
// This is the "floating garbage" trade-off: objects may live one extra cycle
```

V8 uses a combination: **a write barrier that grays both the old and new value** during incremental marking. The cost is ~2–5 extra instructions per reference write — always executing, even when GC is not running (cannot know when marking will start).

**Q11. What is concurrent marking and how does it differ from incremental marking?**
A: Incremental marking still runs marking on the **main thread** — it just does so in small steps. Each step pauses JavaScript. The total STW time is the sum of all steps.

**Concurrent marking** moves the marking work to **background threads** that run **truly in parallel** with JavaScript on the main thread. The main thread continues executing; background threads traverse the object graph simultaneously.

```
Incremental marking:
  Main thread: [JS][mark][JS][mark][JS][mark][JS][mark][JS][mark][sweep]
                     ↑ small pauses but main thread still pauses

Concurrent marking:
  Main thread: [JS   JS   JS   JS   JS   JS   JS   JS   JS][re-mark][sweep]
  BG thread 1: [        mark mark mark mark mark mark        ]
  BG thread 2: [        mark mark mark mark mark mark        ]
                ↑ JS runs uninterrupted — BG threads mark concurrently
                ↑ Only "re-mark" is STW: fix any invalidated refs from concurrent writes
```

The challenge: concurrent marking requires the same write barrier as incremental marking — JavaScript writes can race with the background marker. When the main thread stores a reference, the background thread might be traversing that same object simultaneously. The write barrier ensures the background thread's view remains consistent.

V8's **Orinoco** GC project (shipped incrementally from 2016–2019) introduced concurrent marking, parallel compaction, and concurrent sweeping, reducing major GC pause times from 100–500ms to typically 1–5ms for the final STW phase.

```
V8 major GC phases (post-Orinoco):

  1. Incremental marking start    [STW, ~1ms]  — set up marking, gray roots
  2. Concurrent marking           [background] — BG threads traverse heap
     JS runs concurrently              — write barrier tracks mutations
  3. Marking finalization         [STW, ~1ms]  — drain gray worklist
                                               — process objects modified during concurrent phase
  4. Sweeping / compaction        [background] — reclaim/compact memory
     JS runs concurrently              — allocation routed around in-progress compaction

  Total STW time: ~2–5ms per major GC cycle (was 100–500ms pre-Orinoco)
```

**Q12. What is parallel marking/compaction and how does it differ from concurrent?**
A: The terms describe *which threads* are involved and *when*:

- **Sequential**: one thread (main), everything else paused
- **Incremental**: one thread (main), work interleaved with JS, JS still pauses per step
- **Parallel**: multiple threads (main + helpers), all running simultaneously *during a STW pause* — reduces pause duration by dividing work
- **Concurrent**: background threads run *while JS executes* — no STW for that phase

```
Parallel compaction during a STW pause:
  Main thread:   [compact region A][compact region C]
  Helper thread: [compact region B][compact region D]
  ↑ Both run simultaneously DURING the pause
  ↑ Pause duration halved (roughly) — but it IS still a pause

Concurrent sweeping after STW:
  Main thread: [JS runs normally    JS    JS     JS   ]
  BG thread:   [sweep free pages] [sweep] [sweep]
  ↑ Main thread never paused — sweeping happens in background
```

V8 uses all four strategies in different phases of the same GC cycle. The final "remark" STW is parallelized across helper threads. Sweeping is concurrent. Compaction can be parallel-within-STW for the unavoidable pauses.

### Section 4: Memory and GC in Practice

**Q13. What are the common causes of memory leaks in JavaScript and how does each evade GC?**
A: JavaScript memory leaks happen when objects remain **reachable** from GC roots but are no longer needed by the application. The GC correctly identifies them as live — they are not garbage by the GC's definition. The bug is in the application maintaining unexpected references.

**Cause 1: Forgotten event listeners**
```js
class VideoPlayer {
  constructor(element) {
    this.element = element;
    this.onResize = () => this.handleResize(); // bound method

    // Listener registered on the GLOBAL window — window is a GC root
    window.addEventListener('resize', this.onResize);
    // window → onResize → this (VideoPlayer) → this.element
    // Even if VideoPlayer is "destroyed" by the app, window holds the reference chain
  }

  destroy() {
    this.element = null;
    // WRONG: listener not removed — VideoPlayer is still reachable via window
    // VideoPlayer leaks forever
  }

  // FIX: remove listener in destroy():
  destroyFixed() {
    window.removeEventListener('resize', this.onResize);
    this.element = null;
  }
}

// Modern fix: AbortController — automatically removes multiple listeners:
class VideoPlayerFixed {
  constructor(element) {
    this.element = element;
    this.controller = new AbortController();
    window.addEventListener('resize', () => this.handleResize(), {
      signal: this.controller.signal // ← auto-removed when controller.abort() is called
    });
  }
  destroy() {
    this.controller.abort(); // removes ALL listeners registered with this signal
    this.element = null;
  }
}
```

**Cause 2: Closures capturing large objects**
```js
// Closure keeps the entire scope alive — even if only a small part is needed:
function setupHandler() {
  const hugeDataset = loadMillionRows(); // 100MB in memory

  const id = hugeDataset.id;             // only need this tiny field

  document.querySelector('#btn').addEventListener('click', () => {
    console.log(id);          // only references id
    // BUT: the closure scope captures everything in setupHandler's scope
    // hugeDataset is kept alive as long as the listener exists — 100MB leak
  });
}

// Fix: extract only what you need — close over the small value, not the large object:
function setupHandlerFixed() {
  const hugeDataset = loadMillionRows();
  const id = hugeDataset.id;

  // hugeDataset can be GC'd after this line — closure captures only id:
  document.querySelector('#btn').addEventListener('click', (() => {
    const capturedId = id;          // copy primitive into closure
    return () => console.log(capturedId);
  })());
  // hugeDataset goes out of scope here → GC-eligible
}
```

**Cause 3: Detached DOM nodes**
```js
// DOM nodes removed from the document but still referenced in JS:
let cachedList = document.getElementById('item-list');

function refreshList() {
  const parent = cachedList.parentNode;
  const newList = createNewList();
  parent.replaceChild(newList, cachedList);
  cachedList = newList;                   // update reference to new node

  // OLD list: removed from DOM (no longer document-reachable)
  // But if any JS variable still holds the old node:
  globalRefs.push(oldNode);              // ← old node kept alive in globalRefs
  // oldNode's entire subtree (potentially thousands of DOM nodes) is leaked
}

// Fix: null out references to detached nodes explicitly:
function refreshListFixed() {
  const old = cachedList;
  cachedList = createNewList();
  old.parentNode.replaceChild(cachedList, old);
  // old goes out of scope — no variable holds it → GC can collect it
}
```

**Cause 4: Unbounded caches / maps**
```js
// Cache with no eviction — grows forever:
const requestCache = new Map();

function getCachedResponse(url) {
  if (requestCache.has(url)) return requestCache.get(url);
  const response = fetchSync(url);
  requestCache.set(url, response); // grows unboundedly — never evicts old entries
  return response;
}

// Fix: use WeakRef + FinalizationRegistry for GC-friendly caching,
// or implement LRU with explicit size limit:
class LRUCache {
  constructor(maxSize) {
    this.maxSize = maxSize;
    this.cache   = new Map();
  }
  get(key) {
    if (!this.cache.has(key)) return undefined;
    const value = this.cache.get(key);
    this.cache.delete(key);
    this.cache.set(key, value); // move to most-recently-used position
    return value;
  }
  set(key, value) {
    if (this.cache.has(key)) this.cache.delete(key);
    else if (this.cache.size >= this.maxSize) {
      // Delete the least-recently-used entry (first entry in Map):
      this.cache.delete(this.cache.keys().next().value);
    }
    this.cache.set(key, value);
  }
}
```

**Q14. What is `WeakRef` and `FinalizationRegistry`, and when are they appropriate?**
A: `WeakRef` holds a reference to an object that does NOT prevent GC. The held object can be collected at any time; `weakRef.deref()` returns the object if still alive or `undefined` if collected.

`FinalizationRegistry` registers a callback that fires *after* an object is collected — useful for cleanup of associated external resources.

```js
// WeakRef — GC-friendly cache:
const cache = new Map(); // key → WeakRef<value>

function getCached(key) {
  const ref   = cache.get(key);
  const value = ref?.deref(); // deref: returns value or undefined

  if (value !== undefined) return value; // still alive

  // Compute fresh value:
  const fresh = computeExpensive(key);

  // Cache with WeakRef — GC can collect `fresh` if memory is needed:
  cache.set(key, new WeakRef(fresh));
  return fresh;
}
// If GC collects a cached value, next call recomputes it — transparent to caller
// Memory pressure automatically clears the cache — no manual eviction needed

// FinalizationRegistry — cleanup external resources when object is GC'd:
const registry = new FinalizationRegistry((heldValue) => {
  console.log(`Object with id ${heldValue} was collected`);
  releaseExternalResource(heldValue); // e.g., close file handle, free GPU buffer
});

function createResource() {
  const resource = { data: new ArrayBuffer(1024 * 1024) }; // 1MB
  const resourceId = allocateExternalHandle();

  // Register: when `resource` is GC'd, call the cleanup callback with resourceId:
  registry.register(resource, resourceId);

  return resource;
}
// When resource goes out of scope and is GC'd → callback fires → external handle freed

// IMPORTANT CAVEATS:
// 1. WeakRef.deref() may return undefined at any time after the GC runs
//    (not just when memory is low — GC timing is unpredictable)
// 2. FinalizationRegistry callbacks fire asynchronously and on GC timing —
//    not deterministic — do not rely on them for program correctness
// 3. Callbacks may NEVER fire (e.g., page closes before GC collects object)
// Use for: performance hints, cache invalidation, leak detection
// Do NOT use for: correctness-critical cleanup (use explicit .dispose() pattern instead)
```

**Q15. "A Node.js service's memory grows steadily over 24 hours and eventually crashes. How do you diagnose and fix it?"**
A: Steady memory growth that never plateaus is the signature of a **memory leak** — not just high memory use. A phased diagnostic approach:

**Phase 1: Confirm and characterize**
```js
// Add memory monitoring to confirm the leak pattern:
setInterval(() => {
  const mem = process.memoryUsage();
  console.log({
    rss:      (mem.rss       / 1024 / 1024).toFixed(1) + 'MB', // total process memory
    heapUsed: (mem.heapUsed  / 1024 / 1024).toFixed(1) + 'MB', // live JS objects
    heapTotal:(mem.heapTotal / 1024 / 1024).toFixed(1) + 'MB', // heap capacity
    external: (mem.external  / 1024 / 1024).toFixed(1) + 'MB', // C++ objects (Buffers)
  });
}, 30_000);

// Interpretation:
// heapUsed grows continuously → JS objects leaking (closure, Map, event listener)
// external grows continuously  → Buffer / native memory leak
// rss grows but heapUsed stable → possible heap fragmentation or native module leak
```

**Phase 2: Take heap snapshots and diff them**
```
In Chrome DevTools (attach to Node.js with --inspect):
  1. Take snapshot A (baseline after warmup)
  2. Send load for 10 minutes
  3. Force GC (click GC button in DevTools)
  4. Take snapshot B
  5. In snapshot B: view "Objects allocated between snapshots A and B"
  6. Sort by "Retained Size" — top entries are the leak

CLI alternative:
  node --expose-gc --inspect server.js
  // Then: curl localhost:PORT to generate load
  // Then: examine heap in DevTools

Common finding: "Array" or "Object" or "closure" with thousands of instances,
all retained by a single common ancestor (the leaked Map, EventEmitter, etc.)
```

**Phase 3: Pattern-match to common leak types**
```js
// Leak pattern: EventEmitter with many listeners (common in Node.js):
emitter.on('data', handler); // called in a loop without removing
// Fix: emitter.removeListener or use emitter.once() for one-shot events

// Node.js built-in warning:
// "MaxListenersExceededWarning: Possible EventEmitter memory leak detected.
//  11 data listeners added. Use emitter.setMaxListeners() to increase limit"
// This warning IS a leak signal — don't suppress it, fix the root cause.

// Leak pattern: timers not cleared:
function startPolling(resource) {
  const interval = setInterval(() => resource.poll(), 1000);
  // If resource is "destroyed" but interval is not cleared:
  // interval → callback → resource → all of resource's references
  // Fix:
  return () => clearInterval(interval); // return cleanup function
}
const stopPolling = startPolling(resource);
// When done: stopPolling() — clears the interval, resource can be GC'd

// Leak pattern: request-scoped data stored in module-level Map:
const activeSessions = new Map(); // module-level — lives forever
app.post('/login', (req, res) => {
  const session = createSession(req.user);
  activeSessions.set(session.id, session); // added but never removed on logout/expiry
  // Fix: remove on logout + add TTL-based eviction
});
```

**Q16. "How does GC interact with large `Buffer` allocations in Node.js?"**
A: Node.js `Buffer` objects are interesting from a GC perspective because they have a **split existence**:

- The JavaScript `Buffer` object lives on the V8 heap — small, tracked by GC
- The underlying memory is allocated **outside** the V8 heap via C++ (`malloc`) — large, **not** tracked by V8's GC

```js
// Buffer: JS object (8 bytes on heap) + C++ memory (outside heap):
const buf = Buffer.allocUnsafe(100 * 1024 * 1024); // 100MB

// process.memoryUsage():
//   heapUsed: +8 bytes   ← the JS Buffer object
//   external: +100MB     ← the C++ backing memory

// When buf becomes unreachable:
//   V8 GC collects the JS object
//   FinalizationRegistry (internal) triggers → C++ memory freed
//   external: -100MB

// THE TRAP: V8 doesn't "see" the 100MB — heap pressure from Buffers
// doesn't trigger GC. You can have 4GB of Buffers with heapUsed = 50MB
// → V8 has no urgency to GC → JS objects holding Buffer refs live indefinitely
// → External memory grows unboundedly

// Symptom:
//   heapUsed is stable (low), rss keeps growing
//   → Likely: Buffer leak or C++ addon memory leak

// Fix: ensure Buffer-holding objects are properly released
// and check for reference chains keeping Buffers alive

// For streaming: prefer pipeline() over accumulating into a Buffer:
// ❌ accumulates entire response in memory:
const chunks = [];
res.on('data', chunk => chunks.push(chunk));
res.on('end', () => process(Buffer.concat(chunks))); // one 500MB Buffer

// ✓ streams through without accumulating:
await pipeline(res, transformStream, outputStream);
```

### Problem

// Monitoring infrastructure to add:

const { PerformanceObserver, performance } = require('perf_hooks');

### Finding the Root Cause: Allocation Rate Analysis

```js
// Hypothesis 1: High allocation rate causing frequent minor GC → promotion pressure
// → Objects created fast enough to survive 2 minor GCs → old gen fills quickly

// Profile allocation sites with Node.js:
// node --prof --prof-sampling-interval=1 app.js
// (--prof-sampling-interval=1 samples every 1ms — high resolution)
// node --prof-process isolate-*.log | grep -A5 "Heap"

// Hypothesis 2: Long-lived objects polluting old gen
// → Large arrays / maps accumulating items without eviction

// Common culprit pattern (found by heap snapshot diff):
class DataGrid {
  constructor() {
    this.rowCache = [];  // never cleared — grows with every render cycle
  }

  render(newData) {
    // ❌ Appends to cache on every render — rowCache grows unboundedly:
    this.rowCache.push(...newData.map(row => ({
      ...row,
      computed: this.computeExpensive(row),
      element: document.createElement('tr'), // DOM node in cache!
    })));
    // rowCache survives multiple minor GCs → promoted to old gen
    // old gen fills → major GC triggers → 287ms pause
  }
}

// Fix: bounded cache, explicit cleanup, avoid accumulating in long-lived objects:
class DataGridFixed {
  constructor() {
    this.rowCache = new LRUCache(100); // max 100 rows cached
  }
  render(newData) {
    const rendered = newData.map(row => {
      const cached = this.rowCache.get(row.id);
      if (cached) return cached;
      const result = { ...row, computed: this.computeExpensive(row) };
      this.rowCache.set(row.id, result);
      return result;
    });
    // DOM elements NOT cached — created fresh, GC'd after each render
  }
}
```

## Problem 2 — Object Pooling to Reduce GC Pressure

### Problem
A physics simulation creates and destroys 10,000 `Vector3` objects per frame at 60fps. The constant allocation and GC causes frame rate to drop to 40fps with regular minor GC pauses. Implement an object pool to eliminate GC pressure.

```js
// ❌ Current — 10,000 allocations per frame:
class Vector3 {
  constructor(x = 0, y = 0, z = 0) {
    this.x = x; this.y = y; this.z = z;
  }
  add(other) {
    return new Vector3(this.x + other.x, this.y + other.y, this.z + other.z);
    // ↑ new allocation every call — in a hot loop: thousands per frame
  }
  scale(s) {
    return new Vector3(this.x * s, this.y * s, this.z * s); // another allocation
  }
}

// Simulation update — allocates ~10,000 Vector3 per frame:
function updateParticles(particles, dt) {
  for (const p of particles) {
    const force    = computeForce(p);          // new Vector3 allocation
    const accel    = force.scale(1 / p.mass);  // new Vector3 allocation
    const velocity = p.velocity.add(accel.scale(dt)); // 2 more allocations
    const position = p.position.add(velocity.scale(dt)); // 2 more allocations
    p.velocity = velocity;
    p.position = position;
    // Old force, accel, intermediate Vectors → immediately garbage
    // 6 allocations × 1,666 particles × 60fps = 600,000 allocs/sec
    // Minor GC fires every ~16ms (new space fills) → pause during rendering
  }
}
```

### Root Cause: Allocation in Hot Loop

```
Memory timeline without pooling:

  Frame 1: allocate 10,000 Vector3 → new space fills → minor GC (1ms pause) → 40fps
  Frame 2: allocate 10,000 Vector3 → new space fills → minor GC (1ms pause) → 40fps
  Frame 3: allocate 10,000 Vector3 → new space fills → minor GC (1ms pause) → 40fps

  New space size: ~8MB
  Vector3 size: ~48 bytes (3 doubles + object overhead)
  Objects per new-space fill: 8MB / 48B ≈ 166,000 objects ≈ 16 frames worth
  → Minor GC every 16 frames → ~3–4 GCs per second → visible stuttering

  Promotion pressure:
  Some Vectors survive long enough to be promoted → old gen grows → eventual major GC
```

### Solution: Object Pool

```js
// Object pool: pre-allocate a fixed set of objects, reuse them:
class Vector3Pool {
  constructor(initialSize = 1000) {
    this._pool    = [];
    this._created = 0;

    // Pre-warm: allocate objects before simulation starts
    // (avoids allocation during first few frames)
    for (let i = 0; i < initialSize; i++) {
      this._pool.push(new Vector3());
    }
  }

  // Acquire: get an object from the pool (or allocate if empty):
  acquire(x = 0, y = 0, z = 0) {
    let v;
    if (this._pool.length > 0) {
      v = this._pool.pop(); // O(1) — reuse existing object
    } else {
      v = new Vector3();    // pool empty — allocate new (rare after warmup)
      this._created++;
    }
    v.x = x; v.y = y; v.z = z; // reset state
    return v;
  }

  // Release: return an object to the pool:
  release(v) {
    // Guard: don't let pool grow unboundedly (memory pressure in the other direction):
    if (this._pool.length < 2000) {
      v.x = 0; v.y = 0; v.z = 0; // optional: zero out for safety
      this._pool.push(v);         // O(1) — return to pool
    }
    // If pool is full: let it be GC'd — better than holding too much memory
  }

  get stats() {
    return { poolSize: this._pool.length, totalCreated: this._created };
  }
}

const vectorPool = new Vector3Pool(5000); // pre-allocate 5,000 vectors

// Rewrite Vector3 to work with pool:
class Vector3 {
  constructor(x = 0, y = 0, z = 0) {
    this.x = x; this.y = y; this.z = z;
  }

  // Mutating operations — no allocation:
  addInPlace(other) {
    this.x += other.x; this.y += other.y; this.z += other.z;
    return this;
  }
  scaleInPlace(s) {
    this.x *= s; this.y *= s; this.z *= s;
    return this;
  }
  copyFrom(other) {
    this.x = other.x; this.y = other.y; this.z = other.z;
    return this;
  }

  // Pool-aware operations — acquire from pool, caller must release:
  addToNew(other) {
    return vectorPool.acquire(this.x + other.x, this.y + other.y, this.z + other.z);
  }
  scaleToNew(s) {
    return vectorPool.acquire(this.x * s, this.y * s, this.z * s);
  }
}

// Updated simulation — zero allocations in hot loop:
function updateParticles(particles, dt) {
  // Temporary vectors acquired from pool:
  const tmpForce = vectorPool.acquire();
  const tmpAccel = vectorPool.acquire();
  const tmpDV    = vectorPool.acquire();
  const tmpDP    = vectorPool.acquire();

  for (const p of particles) {
    computeForceInto(p, tmpForce);       // writes into tmpForce — no allocation

    // accel = force / mass — mutate tmpAccel:
    tmpAccel.copyFrom(tmpForce).scaleInPlace(1 / p.mass);

    // velocity += accel * dt — mutate in place:
    tmpDV.copyFrom(tmpAccel).scaleInPlace(dt);
    p.velocity.addInPlace(tmpDV);        // p.velocity is mutated in place — no allocation

    // position += velocity * dt — mutate in place:
    tmpDP.copyFrom(p.velocity).scaleInPlace(dt);
    p.position.addInPlace(tmpDP);        // no allocation
  }

  // Release temporaries back to pool:
  vectorPool.release(tmpForce);
  vectorPool.release(tmpAccel);
  vectorPool.release(tmpDV);
  vectorPool.release(tmpDP);
  // Total allocations this frame: 0 (pool was pre-warmed)
}
```

### Performance Impact

```
Without pool — 10,000 Vector3 per frame:
  Memory churn: 10,000 × 48 bytes = 480KB of garbage per frame
  At 60fps: 28.8MB/s of allocation → minor GC every ~0.3s → pause budget blown
  Actual fps: ~40 (minor GC steals ~1ms every 3 frames)

With pool — 0 allocations per frame (after warmup):
  Memory churn: ~0 bytes per frame (pool objects are reused)
  GC: no minor GC triggered during simulation (new space stays empty)
  Actual fps: 60 (stable — no GC pauses)

Pool memory overhead:
  5,000 Vector3 × 48 bytes = 240KB pre-allocated
  These objects survive in old gen — never collected during simulation
  This is acceptable: trade 240KB of persistent memory for 0 GC pauses

Pool sizing rule:
  Max pool size ≥ peak number of objects alive simultaneously
  For this simulation: 4 temporaries × 1 (reused per particle) = 4 vectors needed
  Plus particle positions/velocities (pre-allocated with particles) = 2 × N
  Initial pool of 5,000 covers 2,500 particles with buffers
```

## Problem 3 — Write Barrier Cost and Generational-Aware Code

### Problem
A real-time leaderboard stores score updates into a long-lived `Map` of player objects. After profiling, the team notices the write barrier cost is surprisingly high. Explain why, show how to measure it, and restructure the data to minimize it.

```js
// Long-lived leaderboard — promoted to old gen after startup:
class Leaderboard {
  constructor() {
    this.players = new Map(); // promoted to OLD GEN — persists for the session
  }

  // Called 100 times/second with fresh score updates:
  update(playerId, newScore, timestamp) {
    let player = this.players.get(playerId);
    if (!player) {
      player = { id: playerId, score: 0, history: [], lastUpdate: null };
      this.players.set(playerId, player); // OLD → NEW reference: triggers write barrier
    }

    player.score = newScore;              // OLD → (possibly NEW) reference
    player.lastUpdate = timestamp;        // OLD → NEW reference: timestamp is new object

    const entry = { score: newScore, time: Date.now() }; // NEW object
    player.history.push(entry);           // OLD → NEW reference: write barrier fires
    // player (old) → player.history (old array) → entry (new)
    //                                              ↑ OLD → NEW: write barrier fires
  }
}
```

### Why Write Barriers Are Expensive Here

```
Write barrier fires on EVERY old-to-new reference write.
Cards (512-byte regions) are dirtied and scanned during every minor GC.

Tracing the write barrier calls per update():
  this.players.set(playerId, player)    → Map internals write (old→new) → barrier
  player.score = newScore               → player is old, newScore is primitive → no barrier
  player.lastUpdate = timestamp         → player is old, timestamp could be new → barrier
  player.history.push(entry)            → player.history is old, entry is new → barrier

At 100 updates/second × 1000 players:
  100,000 write barrier checks/second
  Each barrier: dirty card table entry (cache write)
  Card table scanning during minor GC: must scan all dirty cards in old gen
  
  If old gen is 100MB and cards are 512 bytes:
  100MB / 512B = 200,000 cards
  If 10% are dirty: 20,000 cards scanned per minor GC
  At minor GC every 50ms: 400 card scans/second of 512 bytes each = 200KB/minor GC scan

  Not catastrophic — but can be measured and reduced.
```

### Measuring Write Barrier Cost

```
Profiling tools:
  node --prof --log-all-code app.js
  node --prof-process isolate-*.log | grep "WriteBarrier\|StoreBuffer"

  In V8 internals output, look for:
    "Remembered set entries written" in GC trace
    "Scavenger: roots" count — high count means many old-to-new pointers

  Chrome DevTools Memory > Allocation instrumentation:
    Check "Objects promoted to old space" count
    If high: objects are dying in old gen instead of new gen (generational hypothesis violated)
```

### Restructuring to Reduce Write Barrier Frequency

```js
// Strategy 1: Keep frequently-updated data in NEW SPACE (separate from long-lived data)

class Leaderboard {
  constructor() {
    // Stable data in one long-lived map:
    this.playerIds   = new Set();      // string IDs — primitives, no barrier issue

    // Volatile data in a FRESH object every update cycle:
    // Instead of mutating old objects, replace with new ones:
    this.scoreBuffer = new Float64Array(10000); // TypedArray: no GC for elements!
    this.idToIndex   = new Map();              // playerId → index in scoreBuffer
  }

  // TypedArray elements are unboxed — no object references → no write barriers:
  update(playerId, newScore) {
    const idx = this.idToIndex.get(playerId);
    if (idx === undefined) {
      const newIdx = this.idToIndex.size;
      this.idToIndex.set(playerId, newIdx);
      this.scoreBuffer[newIdx] = newScore; // TypedArray write: NO write barrier
    } else {
      this.scoreBuffer[idx] = newScore;    // TypedArray write: NO write barrier
    }
    // No old-to-new reference writes — write barriers eliminated for score updates
  }

  getScore(playerId) {
    const idx = this.idToIndex.get(playerId);
    return idx !== undefined ? this.scoreBuffer[idx] : 0;
  }
}

// Strategy 2: Batch new objects — create them all at once in a fresh container
// so they're all in new space together (fewer cross-gen pointers):

class LeaderboardV2 {
  constructor() {
    this.players  = new Map();   // long-lived: promoted to old gen
    // SEPARATE container for current-tick updates:
    this.pendingUpdates = null;  // replaced wholesale each tick
  }

  queueUpdate(playerId, score) {
    if (!this.pendingUpdates) {
      this.pendingUpdates = new Map(); // new Map each tick → stays in new gen
    }
    this.pendingUpdates.set(playerId, score); // new → new: no write barrier
  }

  // Called once per tick to merge updates — batch commit:
  flushUpdates() {
    if (!this.pendingUpdates) return;

    for (const [id, score] of this.pendingUpdates) {
      // Only one write barrier per player per tick (not per field per update):
      let player = this.players.get(id);
      if (!player) {
        player = { id, score, peakScore: score };
        this.players.set(id, player); // old → new: one barrier
      } else {
        player.score = score;         // old → primitive: no barrier
        if (score > player.peakScore) player.peakScore = score; // no barrier
      }
    }

    this.pendingUpdates = null; // old reference cleared — new Map is now garbage → new gen collected
  }
}

// Strategy 3: Primitives instead of objects — biggest win
// Store scores as numbers in a TypedArray, not as objects in a Map:

class LeaderboardV3 {
  constructor(maxPlayers = 10000) {
    this.scores    = new Float64Array(maxPlayers);  // no GC, no barriers
    this.peakScore = new Float64Array(maxPlayers);  // no GC, no barriers
    this.playerMap = new Map();  // playerId → array index (set once at join)
    this.nextIdx   = 0;
  }

  registerPlayer(playerId) {
    if (!this.playerMap.has(playerId)) {
      this.playerMap.set(playerId, this.nextIdx++); // done once — barrier acceptable
    }
  }

  update(playerId, score) {
    const idx = this.playerMap.get(playerId);
    if (idx === undefined) return;
    this.scores[idx]    = score;                          // NO write barrier
    if (score > this.peakScore[idx]) this.peakScore[idx] = score; // NO write barrier
  }
  // 100,000 updates/second with zero write barriers
}
```

## Problem 4 — Understanding Promotion and Old-Gen Pressure

### Problem
A web server handles many short HTTP requests. Each request creates a `RequestContext` object. Memory profiling shows these objects are being promoted to old space even though each request completes in under 5ms. Explain why and fix it.

```js
// Request handler:
const activeContexts = new Map(); // module-level — LIVES FOREVER in old gen

app.use((req, res, next) => {
  const context = {             // allocated in NEW SPACE (young gen)
    id:        generateId(),
    startTime: Date.now(),
    user:      req.user,
    headers:   req.headers,
    body:      req.body,
    metadata:  {},
  };

  activeContexts.set(context.id, context); // ← OLD MAP → NEW CONTEXT object!
                                           // ← write barrier fires
                                           // ← context is referenced by OLD GEN object
                                           // ← context survives next minor GC (it's in remembered set)

  req.context = context;
  next();
});

app.post('/api/data', (req, res) => {
  const { context } = req;
  context.metadata.processed = true;
  // ... handle request (fast, < 5ms total) ...
  activeContexts.delete(context.id); // remove from map when done
  res.json({ ok: true });
});
```

### Why Contexts Are Promoted Despite Short Lifetimes

```
Timeline of a request context:

  T=0ms:    context allocated → NEW SPACE (young gen)
            activeContexts.set(id, context) → OLD MAP now references context
            → context added to REMEMBERED SET (old → new reference tracked)

  T=1ms:    Minor GC fires (new space full from other traffic)
            GC scans remembered set → finds activeContexts → context
            context appears reachable from old gen → MUST SURVIVE
            context is COPIED TO TO-SPACE (survives once)

  T=3ms:    Request completes → activeContexts.delete(context.id)
            context no longer in map → truly unreachable now
            BUT: it already survived one minor GC!

  T=5ms:    Next minor GC fires
            context is now in FROM-SPACE (survived last GC)
            Scavenger checks: survived once → AGE ≥ 1 → PROMOTE TO OLD SPACE
            context is copied to OLD SPACE

  T=10ms:   context is in OLD SPACE, unreachable (was deleted from map at T=3ms)
            It will only be collected in the NEXT MAJOR GC — potentially seconds later

Result: every request context (which should live < 5ms) ends up in OLD GEN
        → old gen fills with dead objects → frequent major GC → long pauses
        This is called "premature promotion" or "tenured garbage"
```

### Fix 1 — Avoid the Old-to-New Reference

```js
// Don't store short-lived objects in long-lived collections:
// The module-level Map forces contexts into remembered set → premature promotion

// Instead: store context directly on req (which lives exactly as long as the request):
app.use((req, res, next) => {
  // req is managed by the framework — NOT in activeContexts map
  req.context = {
    id:        generateId(),
    startTime: Date.now(),
    user:      req.user,       // req is already in scope — no extra reference chain
    metadata:  {},
  };
  // req.context is new → new reference within the same object → no write barrier to old gen
  // (req itself is a new object per request — stays in new gen for its short life)
  next();
});

// For tracking active requests (e.g., for graceful shutdown):
// Use WeakRef to avoid pinning contexts in old gen:
const activeRequestRefs = new Set(); // holds WeakRefs — doesn't prevent GC

app.use((req, res, next) => {
  const context = { id: generateId(), startTime: Date.now(), metadata: {} };
  req.context = context;
  const ref = new WeakRef(context);
  activeRequestRefs.add(ref);

  // Clean up the WeakRef after response (WeakRef itself is tiny, can stay in Set):
  res.on('finish', () => activeRequestRefs.delete(ref));
  next();
});

// Check active requests (e.g., for shutdown):
function getActiveRequests() {
  return [...activeRequestRefs]
    .map(ref => ref.deref())          // deref: undefined if already GC'd
    .filter(Boolean);                  // keep only alive ones
}
```

### Full Audit and Fix

```js
// Fix 1: Single hidden class — always same properties in same order:
class Tick {
  constructor(data) {
    // Declare ALL properties unconditionally with null defaults:
    this.symbol   = data.symbol;
    this.price    = data.price;
    this.volume   = data.volume   ?? 0;        // null default → same hidden class always
    this.bid      = data.spread?.bid ?? null;
    this.ask      = data.spread?.ask ?? null;
    this.exchange = data.meta?.exchange ?? null;
    // All Tick instances share ONE hidden class → monomorphic ICs everywhere
  }
}

// Fix 2: Ring buffer for bounded history — O(1) memory:
class TickHistory {
  constructor(capacity = 10_000) {    // hold only last 10,000 ticks — bounded
    this.capacity = capacity;
    this.buffer   = new Array(capacity).fill(null); // fixed-size ring
    this.head     = 0;  // next write position
    this.size     = 0;
  }

  record(tick) {
    // Overwrite oldest entry (circular — no allocation beyond initial array):
    this.buffer[this.head] = tick;
    this.head = (this.head + 1) % this.capacity;
    if (this.size < this.capacity) this.size++;
  }

  // Iterate in insertion order:
  [Symbol.iterator]() {
    let count = 0;
    let pos   = this.size < this.capacity
      ? 0
      : this.head; // oldest position when full
    return {
      next: () => {
        if (count >= this.size) return { done: true };
        const value = this.buffer[pos % this.capacity];
        pos++; count++;
        return { value, done: false };
      }
    };
  }
}

// Fix 3: Pre-allocated output buffer — reuse string builder, avoid per-tick allocs:
class TickFormatter {
  constructor() {
    // Reuse a single output buffer — write into it, reset head each tick:
    this._parts = new Array(4); // pre-allocated slot array
  }

  format(tick) {
    // Avoid new object — reuse parts array slots:
    this._parts[0] = tick.symbol;
    this._parts[1] = tick.price;       // number — no string conversion yet
    this._parts[2] = tick.volume;
    this._parts[3] = Date.now();       // number — milliseconds since epoch

    // Single template literal: only ONE string allocated per tick:
    return `${this._parts[0]},${this._parts[1].toFixed(4)},${this._parts[2]},${this._parts[3]}`;
    // toFixed() is unavoidable (one string) — but we've eliminated 3 other allocations
  }
}

// Fix 4: Avoid Promise-per-tick — use synchronous batch processing or queues:

// ❌ Promise + setTimeout per tick (50,000 timers/s):
function processTickBad(tick) {
  return new Promise(resolve => setTimeout(() => resolve(compute(tick)), 0));
}

// ✓ Batch synchronous processing with setImmediate yielding:
class TickProcessor {
  constructor() {
    this.queue   = [];
    this.running = false;
  }

  enqueue(tick) {
    this.queue.push(tick); // one push per tick
    if (!this.running) this._drain();
  }

  _drain() {
    this.running = true;
    const BATCH  = 500; // process 500 ticks per event loop turn
    let processed = 0;

    while (this.queue.length > 0 && processed < BATCH) {
      const tick = this.queue.shift(); // single dequeue — no closure
      compute(tick);                   // synchronous — no Promise
      processed++;
    }

    if (this.queue.length > 0) {
      setImmediate(() => this._drain()); // yield; continue next tick
    } else {
      this.running = false;
    }
  }
}

// Fix 5: Synchronous reduce instead of async Promise chain:
function aggregateAll(ticks) {
  let sum = 0;
  for (const tick of ticks) sum += tick.price; // one loop, zero allocations
  return sum;
  // 50,000 iterations: ~0.5ms — no Promise chain of 50,000 entries
}
```

## Quick Reference — GC Cheat Sheet

```
GENERATIONAL GC:
  Young gen (new space):  small (1–16MB), collected every few ms (~1ms pause)
  Old gen (old space):    large (256MB+), collected every seconds (10–100ms)
  Minor GC (Scavenge):    copies live objects, discards entire old from-space
  Major GC (MarkSweep):   full heap marking + sweeping — expensive
  Promotion:              object survives 2 minor GCs → moved to old gen
  Large objects (>512KB): bypass new space → allocated directly in old gen
  Remembered set:         tracks old-to-new references for minor GC roots
  Card table:             512-byte cards; dirty bit set on any write to card
  Write barrier:          fires on every reference write; ~2 extra instructions

INCREMENTAL MARKING:
  Tricolor: WHITE (unvisited), GRAY (seen, children pending), BLACK (done)
  Invariant: no BLACK object may reference a WHITE object
  Incremental step: mark a small portion → let JS run → repeat
  Write barrier: grays old/new value on write to maintain invariant
  Concurrent marking: BG threads mark while JS runs → main thread mostly unpaused
  Parallel: multiple threads work DURING a STW pause → shorter pause
  Final STW: ~1–5ms remark pass; sweep is concurrent (background)

MEMORY LEAK PATTERNS:
  Event listeners: always removeEventListener / AbortController / once
  Closures: close over small values, not large containing objects
  Detached DOM: null refs to removed DOM nodes after removal
  Unbounded caches: LRU with max size or WeakRef-based eviction
  timers: always clearInterval / clearTimeout when scope ends
  EventEmitter: MaxListenersExceeded warning → real leak signal

ALLOCATION REDUCTION PATTERNS:
  TypedArray: elements are unboxed primitives — no per-element GC, no write barriers
  Object pool: pre-allocate, reuse; eliminates allocation in hot loops
  Mutating in place: avoid creating new objects for intermediate results
  Single hidden class: always same properties in same order → monomorphic ICs
  Ring buffer: fixed-size circular array → O(1) memory, no GC pressure
  Batch + yield: process N items synchronously, setImmediate between batches

GC DIAGNOSTIC TOOLS:
  Node.js:
    PerformanceObserver entryTypes: ['gc'] → log each GC with kind + duration
    process.memoryUsage()            → heapUsed, heapTotal, external, rss
    node --expose-gc + global.gc()   → force GC, measure before/after heap
    node --prof + node --prof-process → V8 CPU profiler (allocation sites)
    node --trace-gc                  → verbose GC log to stderr
    Chrome DevTools (--inspect)      → Heap snapshots, allocation timeline

  Browser:
    PerformanceObserver entryTypes: ['longtask']  → GC shows as long tasks
    Chrome DevTools → Memory → Heap Snapshot       → object retention paths
    Chrome DevTools → Memory → Allocation Timeline → allocation over time
    chrome://tracing → category: "v8.gc"           → GC phases with timestamps

AVOID:
  delete operator on hot-path objects  → dictionary mode, slow property access
  Storing new objects in old-gen collections → premature promotion
  Per-iteration allocations in hot loops → GC pressure, minor GC every few ms
  Float64Array with Atomics            → Atomics needs Int32/BigInt64
  Async Promise chain for N items      → N Promises allocated; use for-of + await
  JSON.stringify per item in hot path  → new string + new object per call
  new Date() in hot path               → new Date object per call; use Date.now()
```

**Final Tip:** At the 5 YOE level, GC questions test whether you can reason from **algorithm → consequence → diagnosis → fix** — not just recite definitions. The highest-signal answer on generational GC: "The generational hypothesis means most objects die before their first minor GC — so the Scavenger only needs to copy the survivors, which are few, and reclaims the dead as a free block. Minor GC costs ~1ms regardless of old-gen size because it never touches old gen. The write barrier exists because an old-to-new reference bypasses root scanning — without tracking it, the minor GC would miss objects referenced only from old gen and incorrectly collect them." For incremental marking: "The tricolor invariant prevents use-after-free during concurrent/incremental marking. The write barrier grays objects on every reference write — it fires millions of times per second, which is why it has to be as cheap as a dirty-bit set on a card table rather than a full lookup. The final STW remark phase fixes up any objects written between marking steps — it's the only pause users actually notice, and post-Orinoco V8 reduces it to ~1–2ms by doing almost all the work concurrently." For memory leaks: "JavaScript leaks are reachability leaks — the GC is working correctly; the bug is that a root holds an unexpected reference chain to the object. The fix is always to break the chain: removeEventListener, clear from Map, null out module-level refs. WeakRef is the escape hatch for caches — it lets the object be collected without requiring explicit invalidation."
