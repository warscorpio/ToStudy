# Node.js Memory Leaks: `--inspect`, Chrome DevTools, `heapdump` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What constitutes a memory leak in Node.js — what is actually happening at the V8 level?**

A: A memory leak in Node.js is not a bug in V8's garbage collector — it is application code unintentionally holding references to objects that should be eligible for collection. V8's GC can only free memory that has no live references pointing to it. A "leak" means your code is keeping references alive longer than intended, so the GC correctly refuses to collect those objects.

Understanding V8's heap layout is essential for diagnosing leaks:

```
┌─────────────────────────────────────────────────────────────┐
│                     V8 Heap                                 │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              New Space (Young Generation)           │   │
│  │  ┌──────────────┐  ┌──────────────┐                │   │
│  │  │   From Space  │  │   To Space   │  ~1-8MB        │   │
│  │  │  (live objs) │  │   (empty)    │                │   │
│  │  └──────────────┘  └──────────────┘                │   │
│  │  Scavenge GC: fast, frequent, stop-the-world ~1ms  │   │
│  └─────────────────────────────────────────────────────┘   │
│                           │ survives 2 scavenges            │
│                           ▼                                 │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              Old Space (Old Generation)             │   │
│  │  Objects that survived young-gen GC                │   │
│  │  Mark-Sweep-Compact: slower, less frequent          │   │
│  │  Default limit: 1.4GB (64-bit), 700MB (32-bit)     │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────────────┐ │
│  │   Code   │  │   Map    │  │   Large Object Space     │ │
│  │  Space   │  │  Space   │  │   (> 512KB, no moving)   │ │
│  └──────────┘  └──────────┘  └──────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

The four most common reference patterns that cause leaks:

```javascript
// Pattern 1: Global variables — GC root, never collected
global.cache = {};
function processRequest(data) {
    global.cache[data.id] = data; // Grows forever — global is always reachable
}

// Pattern 2: Closures capturing outer scope unintentionally
function createHandler() {
    const largeBuffer = Buffer.alloc(10 * 1024 * 1024); // 10MB
    return function handler(req, res) {
        // handler is stored somewhere (event listener, etc.)
        // largeBuffer is captured by the closure even if never used in handler
        // It will not be collected until handler itself is collected
        res.json({ ok: true });
    };
}

// Pattern 3: Event listeners not removed
class DataProcessor extends EventEmitter {
    attach(emitter) {
        // Every call to attach() adds a new listener — old ones never removed
        emitter.on('data', (chunk) => this.process(chunk));
        // If attach() is called 1000 times: 1000 listeners, 1000 closure captures
    }
}

// Pattern 4: Timers and intervals keeping references alive
function startPolling(resource) {
    setInterval(() => {
        resource.fetch(); // resource cannot be GC'd while interval is alive
    }, 1000);
    // If this interval is never cleared, resource is leaked for the process lifetime
}
```

The symptom profile of a genuine leak vs. normal behavior:

```javascript
// Normal: RSS grows, then GC fires, then drops back — sawtooth pattern
// Leak:   RSS grows monotonically across GC cycles — GC fires but can't reclaim

import v8 from 'v8';
import process from 'process';

function logMemory(label) {
    const heap = v8.getHeapStatistics();
    const rss = process.memoryUsage().rss;
    console.log(`[${label}]`);
    console.log(`  heapUsed:  ${(heap.used_heap_size / 1024 / 1024).toFixed(1)}MB`);
    console.log(`  heapTotal: ${(heap.total_heap_size / 1024 / 1024).toFixed(1)}MB`);
    console.log(`  RSS:       ${(rss / 1024 / 1024).toFixed(1)}MB`);
    console.log(`  external:  ${(process.memoryUsage().external / 1024 / 1024).toFixed(1)}MB`);
}

// external = memory used by C++ objects (Buffers) — NOT in V8 heap
// A Buffer leak shows up in 'external', not 'heapUsed'
```

**Q2. What is the difference between `heapUsed`, `heapTotal`, `rss`, and `external` in `process.memoryUsage()`?**

A: These four numbers describe different layers of memory, and misreading them leads to misdiagnosis:

```javascript
const mem = process.memoryUsage();
// {
//   rss:          85_000_000,  // Resident Set Size
//   heapTotal:    50_000_000,  // V8 heap capacity (committed from OS)
//   heapUsed:     38_000_000,  // V8 heap in use (live objects)
//   external:     1_200_000,   // C++ objects (Buffers, native modules)
//   arrayBuffers: 900_000      // ArrayBuffers and SharedArrayBuffers (subset of external)
// }
```

What each means:

```
rss (Resident Set Size)
  ├── V8 heap (heapTotal)
  │     ├── heapUsed  (live JS objects: strings, arrays, objects, closures...)
  │     └── free heap (allocated but not yet used — V8 pre-allocates in chunks)
  ├── external (Buffer memory, native addons — off-heap but in RSS)
  ├── code (compiled JS/wasm — JIT-compiled machine code)
  └── stack (call stack for current thread)
```

Diagnostic implications:

```javascript
// Scenario A: heapUsed growing → JS objects accumulating → JS-level leak
// Scenario B: external growing, heapUsed stable → Buffer/native object leak
// Scenario C: heapTotal >> heapUsed → V8 pre-allocated but hasn't GC'd yet
//             (common after a spike — heapTotal shrinks on next major GC)
// Scenario D: rss >> heapTotal + external → memory fragmentation or
//             JIT code cache growing (less common)

// Monitoring over time to identify the pattern:
import v8 from 'v8';

const samples: { time: number; heapUsed: number; external: number }[] = [];

setInterval(() => {
    const { heapUsed, external } = process.memoryUsage();
    samples.push({ time: Date.now(), heapUsed, external });

    if (samples.length > 10) {
        const first = samples[0];
        const last = samples[samples.length - 1];
        const heapDelta = (last.heapUsed - first.heapUsed) / 1024 / 1024;
        const extDelta = (last.external - first.external) / 1024 / 1024;

        if (heapDelta > 50) {
            console.warn(`Possible JS heap leak: +${heapDelta.toFixed(1)}MB in ${samples.length} samples`);
        }
        if (extDelta > 50) {
            console.warn(`Possible Buffer/native leak: +${extDelta.toFixed(1)}MB external`);
        }
    }
}, 30_000);
```

## Section 2: `--inspect` and Chrome DevTools

**Q3. How do you attach Chrome DevTools to a running Node.js process — what are the different `--inspect` flags?**

A: Node.js has a built-in V8 inspector that exposes the Chrome DevTools Protocol over a WebSocket. Several flags control when and how it activates:

```bash
# Start with inspector open immediately (pauses execution until debugger attaches):
node --inspect-brk server.js
#           ↑ 'brk' = break on first line — useful for debugging startup code

# Start with inspector open but don't pause (production-safe profiling):
node --inspect server.js
# Inspector listens on ws://127.0.0.1:9229 by default

# Custom host/port (needed when running in Docker/remote):
node --inspect=0.0.0.0:9229 server.js
# WARNING: 0.0.0.0 exposes inspector to all network interfaces
# Anyone who can reach port 9229 has full access to the process (eval arbitrary code)
# Always use SSH tunneling for remote inspection — never expose 9229 publicly

# Attach to an already-running process by sending SIGUSR1:
kill -SIGUSR1 <pid>
# This activates the inspector on the running process without restarting it
# The inspector URL is printed to stderr

# Programmatic activation (useful in production monitoring):
import inspector from 'inspector';
inspector.open(9229, '127.0.0.1', true); // port, host, pauseOnStart
```

Connecting Chrome DevTools:

```
1. Open Chrome (or Edge) browser
2. Navigate to: chrome://inspect
3. Under "Remote Target", click "inspect" next to your Node process
   (or use "Open dedicated DevTools for Node" for a persistent connection)

Alternatively: Open DevTools → click the green Node.js hexagon icon in top-left

The Memory tab gives you:
- Heap Snapshot    → point-in-time view of all live objects
- Allocation Instrumentation on Timeline → track allocations over time
- Allocation Sampling → statistical profiler, low overhead, suitable for production
```

SSH tunnel for remote debugging (the safe way):

```bash
# On your local machine — forward remote port 9229 to local 9229:
ssh -L 9229:localhost:9229 user@remote-server

# On the remote server:
kill -SIGUSR1 $(pgrep -f 'node server.js')

# Now chrome://inspect on your local machine connects to the remote process
# All traffic goes over the encrypted SSH tunnel — port 9229 never exposed
```

**Q4. How do you take a heap snapshot and what does it show you?**

A: A heap snapshot is a point-in-time dump of every live object in the V8 heap — their types, sizes, and the reference chains connecting them to GC roots. You take multiple snapshots and compare them to find what grew.

The three-snapshot workflow for finding leaks:

```
1. Snapshot 1 (Baseline): Take after app startup and initial warm-up
   → establishes what "normal" looks like

2. Exercise the suspected leaky operation N times
   (e.g., make 1000 API requests, trigger the suspected flow repeatedly)

3. Force a garbage collection: in Chrome DevTools Memory tab → "Collect garbage" button
   OR programmatically: require('v8').setFlagsFromString('--expose-gc'); global.gc();

4. Snapshot 2 (After load): Take immediately after

5. Compare Snapshot 1 vs Snapshot 2 using the "Comparison" view in DevTools
   → Objects that increased in count are the leak candidates
```

Taking snapshots programmatically with `v8.writeHeapSnapshot()`:

```typescript
import v8 from 'v8';
import path from 'path';
import fs from 'fs';

// Manual snapshot — write to disk:
function takeHeapSnapshot(label = 'snapshot'): string {
    const filename = path.join(
        '/tmp',
        `heap-${label}-${Date.now()}.heapsnapshot`
    );
    v8.writeHeapSnapshot(filename);
    console.log(`Heap snapshot written to ${filename}`);
    return filename;
}

// Automatic snapshot on memory threshold:
const HEAP_THRESHOLD_MB = 500;

setInterval(() => {
    const { heapUsed } = process.memoryUsage();
    const heapUsedMB = heapUsed / 1024 / 1024;

    if (heapUsedMB > HEAP_THRESHOLD_MB) {
        console.warn(`Heap exceeded ${HEAP_THRESHOLD_MB}MB — taking snapshot`);
        takeHeapSnapshot(`auto-${heapUsedMB.toFixed(0)}MB`);
    }
}, 60_000);

// Snapshot on demand via HTTP endpoint (protect this in production!):
app.get('/internal/heap-snapshot', (req, res) => {
    // MUST be protected — heap snapshots can contain secrets (passwords, tokens in memory)
    if (req.ip !== '127.0.0.1') return res.status(403).end();

    const filename = takeHeapSnapshot('on-demand');
    res.download(filename, () => fs.unlinkSync(filename)); // Send then delete
});
```

Reading the snapshot in Chrome DevTools — the three views:

```
Summary view (default):
  Groups objects by constructor name
  Columns:
    Constructor  → type name (Array, Object, HTTPParser, Closure, ...)
    Distance     → hops from GC root to this object (shorter = more suspicious)
    Shallow size → bytes for this object itself (not counting what it references)
    Retained size → total bytes freed if this object were collected
                    (itself + everything only reachable through it)

  → Sort by "Retained size" descending: the top entries are the biggest leaks

Comparison view:
  Diff two snapshots — shows new/deleted/size delta
  Columns: # New, # Deleted, # Delta, Alloc. Size, Freed Size, Size Delta
  → Sort by "# Delta" descending: types that grew the most between snapshots

Containment view:
  Tree of GC roots and what they hold
  Shows the reference chain from root to any object
  → Use this to trace WHY a leaked object is still reachable
```

**Q5. How do you use the "Allocation instrumentation on timeline" feature to find allocation hot spots?**

A: Allocation instrumentation records every allocation event in the heap during a recording session, tagged with the JavaScript call stack. This tells you not just WHAT is leaking but WHERE it was allocated — the precise line of code responsible:

```
Steps in Chrome DevTools:
1. Memory tab → select "Allocation instrumentation on timeline"
2. Click "Start"
3. Exercise your application (make the requests/operations you suspect are leaking)
4. Click "Stop"

The timeline shows:
  - Blue bars: memory allocated during the recording
  - Grey bars: memory that was subsequently freed (collected by GC)
  - Blue bars that REMAIN BLUE after recording ends: allocations not yet collected
    → These are your leak candidates

Clicking a blue bar shows the allocation call stack:
  > processRequest (server.js:145)
    > buildResponse (response.js:67)
      > Array (anonymous)
  → Line 145 of server.js created an Array that was never freed
```

Programmatic approach using `inspector` module for automated leak detection in tests:

```typescript
import inspector from 'inspector';
import { promisify } from 'util';

class AllocationTracker {
    private session: inspector.Session;

    constructor() {
        this.session = new inspector.Session();
        this.session.connect();
    }

    async startTracking(): Promise<void> {
        await promisify(this.session.post.bind(this.session))(
            'HeapProfiler.startTrackingHeapObjects',
            { trackAllocations: true }
        );
    }

    async stopAndGetProfile(): Promise<string> {
        await promisify(this.session.post.bind(this.session))(
            'HeapProfiler.stopTrackingHeapObjects'
        );

        const { profile } = await promisify(this.session.post.bind(this.session))(
            'HeapProfiler.takeHeapSnapshot',
            {}
        ) as { profile: string };

        return profile;
    }

    close(): void {
        this.session.disconnect();
    }
}

// In tests — detect allocations that survive across a request:
describe('memory leak detection', () => {
    it('should not leak on POST /api/process', async () => {
        const tracker = new AllocationTracker();
        await tracker.startTracking();

        // Warm up (first run may have legitimate one-time allocations):
        await fetch('http://localhost:3000/api/process', { method: 'POST' });

        // Force GC between warm-up and measurement:
        global.gc?.(); // Only available with --expose-gc flag

        const heapBefore = process.memoryUsage().heapUsed;

        // Run the operation N times:
        for (let i = 0; i < 100; i++) {
            await fetch('http://localhost:3000/api/process', { method: 'POST' });
        }

        global.gc?.();
        const heapAfter = process.memoryUsage().heapUsed;
        const leakPerRequest = (heapAfter - heapBefore) / 100;

        tracker.close();

        // Allow for small variance (module cache, etc.) but flag real growth:
        expect(leakPerRequest).toBeLessThan(1024); // Less than 1KB per request
    });
});
```

## Section 3: `heapdump` and Programmatic Tools

**Q6. What is the `heapdump` package and how does it compare to `v8.writeHeapSnapshot()`?**

A: `heapdump` is an npm package that was the standard way to take heap snapshots before Node.js 11.13 added `v8.writeHeapSnapshot()` natively. In modern Node.js, the native API is preferred — it has no external dependency and identical output format (`.heapsnapshot` files that Chrome DevTools reads directly).

```typescript
// Old approach — heapdump package (still widely used in existing codebases):
import heapdump from 'heapdump';

// Write snapshot to a file:
heapdump.writeSnapshot('/tmp/heap-' + Date.now() + '.heapsnapshot', (err, filename) => {
    if (err) console.error('heapdump failed:', err);
    else console.log('Snapshot written to', filename);
});

// Signal-triggered snapshot (register once, trigger via kill -SIGUSR2 <pid>):
process.on('SIGUSR2', () => {
    heapdump.writeSnapshot((err, filename) => {
        console.log('Heap snapshot written on SIGUSR2 to', filename);
    });
});

// Modern approach — v8.writeHeapSnapshot() (Node.js ≥ 11.13, no dependency):
import v8 from 'v8';

// Synchronous — blocks the event loop while writing (usually < 1s for < 500MB heaps):
const filename = v8.writeHeapSnapshot('/tmp/heap-' + Date.now() + '.heapsnapshot');
console.log('Snapshot written to', filename);

// Signal-triggered — same pattern, no package needed:
process.on('SIGUSR2', () => {
    const file = v8.writeHeapSnapshot();
    console.log(`[${new Date().toISOString()}] Heap snapshot: ${file}`);
});

// Key differences between heapdump and v8.writeHeapSnapshot():
// heapdump:              npm dependency, callback-based, Node < 11 support
// v8.writeHeapSnapshot(): built-in, synchronous, returns filename, Node ≥ 11.13
// Output format:          identical — both produce Chrome-compatible .heapsnapshot
```

Production snapshot strategy — take paired snapshots around the suspected period:

```typescript
import v8 from 'v8';
import path from 'path';

class HeapSnapshotManager {
    private readonly dir: string;
    private snapshots: string[] = [];

    constructor(outputDir = '/tmp') {
        this.dir = outputDir;
    }

    take(label = ''): string {
        const name = `heap-${label}-${Date.now()}.heapsnapshot`;
        const filepath = path.join(this.dir, name);
        v8.writeHeapSnapshot(filepath);
        this.snapshots.push(filepath);
        console.log(`Snapshot taken: ${filepath}`);
        return filepath;
    }

    // Keep only N most recent snapshots — old ones consume significant disk space
    prune(keep = 3): void {
        while (this.snapshots.length > keep) {
            const old = this.snapshots.shift()!;
            try {
                require('fs').unlinkSync(old);
                console.log(`Pruned old snapshot: ${old}`);
            } catch {}
        }
    }

    // Schedule automatic paired snapshots:
    scheduleComparison(intervalMs: number): void {
        let baseline: string | null = null;

        setInterval(() => {
            if (!baseline) {
                baseline = this.take('baseline');
            } else {
                this.take('comparison');
                console.log(`Compare in Chrome DevTools:\n  ${baseline}\n  ${this.snapshots.at(-1)}`);
                this.prune(2);
            }
        }, intervalMs);
    }
}

const manager = new HeapSnapshotManager('/var/log/heapshots');
// Take baseline 5 minutes after startup (warm state), then comparison 10 min later:
setTimeout(() => {
    manager.scheduleComparison(10 * 60 * 1000);
}, 5 * 60 * 1000);
```

**Q7. How do you use `clinic.js` for memory leak diagnosis — and how does it complement Chrome DevTools?**

A: `clinic.js` (from NearForm) is a suite of Node.js diagnostic tools that wrap your process and produce flamegraphs, heap timelines, and event loop delay visualizations with a single command. It's faster to reach for than manual DevTools profiling:

```bash
# Install:
npm install -g clinic

# clinic doctor — general health check (CPU, memory, event loop delay):
clinic doctor -- node server.js
# Runs your server, exercises it with autocannon, generates an HTML report
# Identifies: event loop blocking, memory leaks, I/O bottlenecks

# clinic heapprofiler — heap allocation timeline:
clinic heapprofiler -- node server.js
# Records allocations over time with call stacks
# Shows which functions are allocating and not releasing

# clinic flame — CPU flamegraph (not memory, but useful alongside):
clinic flame -- node server.js
```

Where `clinic.js` fits vs Chrome DevTools:

```
clinic.js:
  ✓ Quick CI/CD integration — one command, auto-generates report
  ✓ Combines heap + event loop + CPU in one view
  ✓ Auto-exercises the server (uses autocannon under the hood)
  ✓ Good for: catching regressions, initial triage
  ✗ Less interactive — can't drill into individual objects
  ✗ Can't trace the reference chain keeping an object alive

Chrome DevTools:
  ✓ Full object-level inspection — see every instance, every reference
  ✓ Comparison view between snapshots — precise delta
  ✓ Retainer chain — WHY is this object still alive?
  ✓ Allocation timeline with call stacks
  ✗ Requires manual setup and interaction
  ✗ Harder to integrate into automated testing

Workflow: clinic.js for triage → Chrome DevTools for root-cause
```

## Section 4: Common Leak Patterns and Fixes

**Q8. How do event listener leaks happen and how do you detect and fix them?**

A: Event listener leaks are the most common Node.js memory leak pattern. Every `.on()` call creates a closure that retains references to the surrounding scope. If you call `.on()` repeatedly without removing old listeners, you accumulate both the closures and everything they capture.

```typescript
import { EventEmitter } from 'events';

// --- LEAK: adding listeners without removing them ---
class RequestHandler {
    constructor(private db: Database) {}

    handleRequest(req: Request, emitter: EventEmitter): void {
        // WRONG: called on every request — adds a new listener every time
        emitter.on('dataReady', (data) => {
            // This closure captures: req, this (RequestHandler), this.db
            this.db.save(req.userId, data);
        });
        // After 10,000 requests: 10,000 listeners, 10,000 copies of req captured
        // Node.js will warn: "MaxListenersExceededWarning: Possible EventEmitter memory leak"
    }
}

// --- DETECTION ---
// Node.js warns at 11 listeners by default:
emitter.setMaxListeners(0); // 0 = unlimited — SUPPRESSES the warning, doesn't fix the leak
// Never suppress the warning without fixing the underlying cause

// Check listener count programmatically:
console.log(emitter.listenerCount('dataReady')); // Should be 1, not growing
console.log(emitter.eventNames());               // All events with listeners

// Detect leaks in tests:
const before = emitter.listenerCount('dataReady');
handler.handleRequest(req, emitter);
const after = emitter.listenerCount('dataReady');
expect(after).toBe(before); // Listener count should not grow per request

// --- FIX 1: Use once() for one-shot listeners ---
emitter.once('dataReady', (data) => {
    // Automatically removed after first firing — no accumulation
    this.db.save(req.userId, data);
});

// --- FIX 2: Remove listener explicitly with a named function ---
class RequestHandler {
    handleRequest(req: Request, emitter: EventEmitter): void {
        const onDataReady = (data: unknown) => {
            this.db.save(req.userId, data);
            emitter.off('dataReady', onDataReady); // Remove after use
        };
        emitter.on('dataReady', onDataReady);
    }
}

// --- FIX 3: Use AbortSignal to tie listener lifetime to request lifetime ---
class RequestHandler {
    handleRequest(req: Request, emitter: EventEmitter): void {
        const controller = new AbortController();

        emitter.on('dataReady', (data) => {
            this.db.save(req.userId, data);
        }, { signal: controller.signal }); // Node.js 20+: signal option auto-removes listener

        req.on('close', () => controller.abort()); // Listener removed when request ends
    }
}

// --- FIX 4: Attach listener once on the emitter, not per request ---
class RequestHandler {
    constructor(private db: Database, emitter: EventEmitter) {
        // Attach ONCE during construction, not per request
        emitter.on('dataReady', this.onDataReady.bind(this));
    }

    private onDataReady(userId: string, data: unknown): void {
        this.db.save(userId, data);
    }

    destroy(emitter: EventEmitter): void {
        emitter.off('dataReady', this.onDataReady); // Clean up when done
    }
}
```

**Q9. How do closures cause leaks and what is the "accidental closure capture" pattern?**

A: Closures hold a reference to their entire enclosing scope — not just the variables they actually use. V8 optimizes this in many cases, but the outer scope object itself is shared among all closures defined in the same function, meaning one closure using a variable keeps the entire scope alive for all other closures.

```typescript
// --- Classic accidental closure capture ---
function setupServer() {
    const diagnosticsBuffer = Buffer.alloc(50 * 1024 * 1024); // 50MB diagnostic data
    const serverConfig = loadConfig(); // 5MB config object

    function handleRequest(req: Request, res: Response): void {
        // handleRequest only needs serverConfig — never uses diagnosticsBuffer
        // BUT: diagnosticsBuffer is in the same scope as handleRequest's closure
        // V8 may keep diagnosticsBuffer alive as long as handleRequest is alive
        res.json(serverConfig.routes[req.path]);
    }

    return handleRequest; // handleRequest is returned and stored — lives forever
    // diagnosticsBuffer should be GC'd but may be retained via closure scope sharing
}

// --- Fix: separate scopes ---
function setupServer() {
    const serverConfig = loadConfig();

    // diagnosticsBuffer lives in its own scope — collected when this IIFE returns
    (function runDiagnostics() {
        const diagnosticsBuffer = Buffer.alloc(50 * 1024 * 1024);
        runInitialChecks(diagnosticsBuffer);
        // diagnosticsBuffer goes out of scope here
    })();

    function handleRequest(req: Request, res: Response): void {
        res.json(serverConfig.routes[req.path]);
        // diagnosticsBuffer not in this scope — cannot be accidentally retained
    }

    return handleRequest;
}

// --- Timer closures — common and subtle ---
class DataFetcher {
    private cache: Map<string, unknown> = new Map();

    startRefresh(): void {
        // WRONG: interval captures 'this' (the DataFetcher instance)
        // If DataFetcher is meant to be temporary but interval is never cleared:
        const intervalId = setInterval(() => {
            this.cache.clear();
            this.fetchLatest(); // 'this' keeps DataFetcher alive forever
        }, 5000);
        // intervalId is not stored — can never be cleared — permanent leak
    }

    startRefreshFixed(): () => void {
        const intervalId = setInterval(() => {
            this.cache.clear();
            this.fetchLatest();
        }, 5000);

        // Return cleanup function — caller is responsible for calling it
        return () => clearInterval(intervalId);
    }
}

// --- WeakRef and FinalizationRegistry for optional retention ---
// When you want a cache that doesn't prevent GC:
class WeakCache<K extends object, V> {
    private map = new WeakMap<K, V>();

    set(key: K, value: V): void {
        this.map.set(key, value);
        // key is held weakly — if nothing else references key, GC can collect it
        // and the entry is automatically removed
    }

    get(key: K): V | undefined {
        return this.map.get(key);
    }
}
```

**Q10. How do you find and fix leaks from unbounded caches and collections?**

A: Caches that grow without eviction are one of the most common production memory leaks — they look intentional (caching is good!) but lack a bound.

```typescript
// --- LEAK: unbounded in-memory cache ---
const cache = new Map<string, { data: unknown; timestamp: number }>();

app.get('/user/:id', async (req, res) => {
    const { id } = req.params;

    if (cache.has(id)) {
        return res.json(cache.get(id)!.data);
    }

    const user = await db.getUser(id);
    cache.set(id, { data: user, timestamp: Date.now() });
    // Cache grows with every unique user ID ever seen — unbounded
    res.json(user);
});

// After 1 million unique requests: 1 million entries in memory, never collected

// --- FIX 1: TTL (time-to-live) eviction ---
class TTLCache<K, V> {
    private map = new Map<K, { value: V; expiresAt: number }>();
    private cleanupInterval: ReturnType<typeof setInterval>;

    constructor(private ttlMs: number, cleanupIntervalMs = ttlMs / 2) {
        this.cleanupInterval = setInterval(() => {
            const now = Date.now();
            for (const [key, entry] of this.map) {
                if (entry.expiresAt < now) {
                    this.map.delete(key);
                }
            }
        }, cleanupIntervalMs);

        // Critical: allow the interval to be GC'd if the cache is abandoned
        this.cleanupInterval.unref();
    }

    set(key: K, value: V): void {
        this.map.set(key, { value, expiresAt: Date.now() + this.ttlMs });
    }

    get(key: K): V | undefined {
        const entry = this.map.get(key);
        if (!entry) return undefined;
        if (entry.expiresAt < Date.now()) {
            this.map.delete(key);
            return undefined;
        }
        return entry.value;
    }

    destroy(): void {
        clearInterval(this.cleanupInterval);
        this.map.clear();
    }
}

// --- FIX 2: LRU (Least Recently Used) eviction ---
class LRUCache<K, V> {
    private map = new Map<K, V>();

    constructor(private maxSize: number) {}

    set(key: K, value: V): void {
        if (this.map.has(key)) {
            this.map.delete(key); // Remove to re-insert at end (most recent)
        } else if (this.map.size >= this.maxSize) {
            // Map preserves insertion order — first entry is least recently used
            const lruKey = this.map.keys().next().value;
            this.map.delete(lruKey);
        }
        this.map.set(key, value);
    }

    get(key: K): V | undefined {
        if (!this.map.has(key)) return undefined;
        const value = this.map.get(key)!;
        // Move to end (most recently used):
        this.map.delete(key);
        this.map.set(key, value);
        return value;
    }

    get size(): number { return this.map.size; }
}

// --- FIX 3: Use proven libraries ---
// npm: lru-cache (most popular), quick-lru, tiny-lru
import { LRUCache as LRU } from 'lru-cache';

const userCache = new LRU<string, User>({
    max: 1000,              // Maximum 1000 entries
    ttl: 5 * 60 * 1000,    // Each entry lives 5 minutes
    maxSize: 50_000_000,    // Maximum 50MB total (requires sizeCalculation)
    sizeCalculation: (value) => JSON.stringify(value).length,
});
```

**Q11. What are the less obvious sources of memory leaks — things that don't look like leaks?**

A: Several Node.js APIs have leak-prone behavior that isn't obvious from the documentation:

```typescript
// --- 1. http.Agent connection pooling ---
import http from 'http';

// http.request uses a global Agent with keepAlive: false by default
// But if you create custom agents without limits:
const agent = new http.Agent({
    keepAlive: true,
    // maxSockets defaults to Infinity — unbounded connection pool
    // maxFreeSockets defaults to 256 — sockets kept alive indefinitely
});

// Fix: always set explicit limits:
const safeAgent = new http.Agent({
    keepAlive: true,
    maxSockets: 50,          // Maximum concurrent connections per host
    maxFreeSockets: 10,      // Maximum idle connections per host
    timeout: 30_000,         // Socket timeout
});

// --- 2. Stream not consumed / not destroyed ---
// An unconsumed Readable stream holds its internal buffer AND keeps its
// underlying resource (file, socket) open:
app.get('/file', (req, res) => {
    const stream = fs.createReadStream('/large-file.bin');

    if (req.query.format !== 'binary') {
        // Stream created but not consumed — file descriptor open, buffer allocated
        res.status(400).json({ error: 'Use ?format=binary' });
        return; // LEAK: stream never destroyed
    }

    stream.pipe(res);
});

// Fix: always destroy streams you don't use:
app.get('/file', (req, res) => {
    const stream = fs.createReadStream('/large-file.bin');

    if (req.query.format !== 'binary') {
        stream.destroy(); // Closes fd, releases buffer
        res.status(400).json({ error: 'Use ?format=binary' });
        return;
    }

    stream.pipe(res);
    req.on('close', () => stream.destroy()); // Also destroy if client disconnects
});

// --- 3. Promise chains holding references ---
// Pending Promises keep their resolution callbacks (and captured scope) alive:
const pendingRequests = new Set<Promise<unknown>>();

function makeRequest(url: string): Promise<Response> {
    const promise = fetch(url)
        .then(res => {
            pendingRequests.delete(promise); // Clean up on success
            return res;
        })
        .catch(err => {
            pendingRequests.delete(promise); // Clean up on failure
            throw err;
        });

    pendingRequests.add(promise); // Track inflight — prevents GC of promise
    return promise;
    // If cleanup is forgotten: pendingRequests grows forever with timed-out requests
}

// --- 4. console.log retaining references ---
const ENABLE_DEBUG = process.env.DEBUG === 'true';

function processData(data: unknown): void {
    // If not careful, debug logging can retain object references:
    if (!ENABLE_DEBUG) return;

    // console.log() arguments are kept in memory until the next GC cycle
    // For very large objects in tight loops, this can appear as a temporary leak
    // In DevTools: you'll see Console references in retainer chains
    console.log('Processing:', JSON.stringify(data)); // JSON.stringify → string (OK)
    console.log('Processing:', data); // Reference to data itself (brief retention)
}

// --- 5. require() cache of large modules ---
// require() caches modules globally — intentional but can be surprising:
// A module that loads a 100MB lookup table at import time keeps it for the process lifetime

// Fix: lazy-load and allow manual cache clearing for optional features:
let heavyModule: typeof import('./heavy-module') | null = null;

function getHeavyModule() {
    if (!heavyModule) {
        heavyModule = require('./heavy-module');
    }
    return heavyModule;
}

function unloadHeavyModule() {
    delete require.cache[require.resolve('./heavy-module')];
    heavyModule = null; // Allow GC of the module object
}

// --- 6. Async context / AsyncLocalStorage leaks ---
import { AsyncLocalStorage } from 'async_hooks';

const requestContext = new AsyncLocalStorage<{ requestId: string; data: unknown }>();

app.use((req, res, next) => {
    // Large context objects can leak if async operations outlive the request:
    requestContext.run(
        {
            requestId: req.id,
            data: req.body  // If body is large and an async op fires after res.end()...
        },
        next
    );
    // Fix: keep context objects small — IDs and lightweight metadata only
    // Never store large payloads in AsyncLocalStorage context
});
```

## Section 5: Production Strategies

**Q12. How do you monitor memory in production without taking the process offline?**

A: Production memory monitoring combines passive metrics, threshold alerting, and on-demand snapshot capability — without requiring a restart or attaching a debugger interactively:

```typescript
import v8 from 'v8';
import process from 'process';
import os from 'os';

// --- Lightweight production memory monitor ---
class MemoryMonitor {
    private history: Array<{ ts: number; heapUsed: number; external: number }> = [];
    private readonly historyLength = 20; // Keep 20 samples

    start(intervalMs = 30_000): void {
        const interval = setInterval(() => this.sample(), intervalMs);
        interval.unref(); // Don't keep process alive just for monitoring
    }

    private sample(): void {
        const { heapUsed, external } = process.memoryUsage();
        const heapStats = v8.getHeapStatistics();
        const now = Date.now();

        this.history.push({ ts: now, heapUsed, external });
        if (this.history.length > this.historyLength) this.history.shift();

        // Emit metrics to your APM (DataDog, New Relic, Prometheus, etc.):
        metrics.gauge('node.heap.used_mb', heapUsed / 1024 / 1024);
        metrics.gauge('node.heap.total_mb', heapStats.total_heap_size / 1024 / 1024);
        metrics.gauge('node.heap.limit_mb', heapStats.heap_size_limit / 1024 / 1024);
        metrics.gauge('node.external_mb', external / 1024 / 1024);

        this.detectLeak();
    }

    private detectLeak(): void {
        if (this.history.length < 5) return;

        // Linear regression over heap samples — positive slope = possible leak:
        const n = this.history.length;
        const xMean = (n - 1) / 2;
        const yMean = this.history.reduce((s, h) => s + h.heapUsed, 0) / n;

        let numerator = 0, denominator = 0;
        for (let i = 0; i < n; i++) {
            numerator += (i - xMean) * (this.history[i].heapUsed - yMean);
            denominator += (i - xMean) ** 2;
        }

        const slope = denominator !== 0 ? numerator / denominator : 0;
        const slopeMBPerSample = slope / 1024 / 1024;

        if (slopeMBPerSample > 5) {
            // Heap growing > 5MB per sample interval — alert
            console.error(
                `[MEMORY ALERT] Possible heap leak: +${slopeMBPerSample.toFixed(1)}MB/sample. ` +
                `Current heapUsed: ${(this.history.at(-1)!.heapUsed / 1024 / 1024).toFixed(1)}MB`
            );
            metrics.increment('node.possible_memory_leak');

            // Auto-snapshot when leak detected:
            if (process.env.AUTO_HEAPDUMP === 'true') {
                const file = v8.writeHeapSnapshot('/var/log/heapshots/');
                console.error(`Auto-snapshot written: ${file}`);
            }
        }
    }
}

// --- Graceful degradation: restart before OOM ---
const HEAP_LIMIT_MB = parseInt(process.env.MAX_HEAP_MB ?? '1400');
const RESTART_THRESHOLD = 0.85; // Restart at 85% of limit

setInterval(() => {
    const { heapUsed } = process.memoryUsage();
    const heapStats = v8.getHeapStatistics();
    const usageRatio = heapUsed / heapStats.heap_size_limit;

    if (usageRatio > RESTART_THRESHOLD) {
        console.error(
            `Heap at ${(usageRatio * 100).toFixed(1)}% of limit ` +
            `(${(heapUsed / 1024 / 1024).toFixed(0)}MB / ` +
            `${(heapStats.heap_size_limit / 1024 / 1024).toFixed(0)}MB). ` +
            `Initiating graceful restart.`
        );

        // Graceful: stop accepting new requests, let in-flight complete, then exit
        server.close(() => {
            console.error('Server closed — exiting for memory restart');
            process.exit(1); // PM2/cluster will restart the process
        });

        // Force exit after 30s if graceful close hangs:
        setTimeout(() => process.exit(1), 30_000).unref();
    }
}, 10_000).unref();
```

**Q14. "Our Node.js server's memory grows by ~200MB per hour under load and never comes back down, even after traffic stops. Walk through how you'd diagnose and fix it."**

A: Systematic triage from broad to specific:

```typescript
// Step 1: Confirm it's a heap leak, not a Buffer/external leak:
setInterval(() => {
    const { heapUsed, external, rss } = process.memoryUsage();
    console.log(JSON.stringify({
        ts: new Date().toISOString(),
        heapUsedMB: (heapUsed / 1024 / 1024).toFixed(1),
        externalMB: (external / 1024 / 1024).toFixed(1),
        rssMB: (rss / 1024 / 1024).toFixed(1),
    }));
}, 60_000);

// If heapUsed is growing → JS object leak (Q8, Q9, Q10 patterns)
// If external is growing → Buffer leak or native module leak
// If rss >> heapUsed + external → fragmentation or JIT code cache

// Step 2: Take paired heap snapshots in production:
// T=0  (baseline after restart)
// T=60 (one hour in, under load)
// Force GC before each snapshot to exclude already-unreachable objects

// Step 3: Load snapshot 2, switch to Comparison view vs snapshot 1
// Sort by "# Delta" descending
// Common findings and their causes:
//
// "(closure)" growing → event listener or timer leak (Q8)
// "Object" or specific class name → unbounded cache (Q10)
// "Array" → growing collection never cleared
// "HTTPParser" → http.Agent connections not being released

// Step 4: Click the constructor with the highest delta → "Retainers" panel
// This shows the reference chain keeping those objects alive:
//
// Example retainer chain for a closure leak:
//   closure @123456  [retained by]
//   → EventEmitter._events.dataReady  [retained by]
//   → DataProcessor instance @789  [retained by]
//   → module.exports (server.js:45)
//
// → Line 45 of server.js is where DataProcessor is created
// → dataReady listener is added but never removed

// Step 5: Fix identified in code — example cleanup:
class DataProcessor {
    private handlers = new Map<EventEmitter, () => void>();

    attach(emitter: EventEmitter): void {
        const handler = () => this.process();
        emitter.on('dataReady', handler);
        this.handlers.set(emitter, handler); // Track for cleanup
    }

    detach(emitter: EventEmitter): void {
        const handler = this.handlers.get(emitter);
        if (handler) {
            emitter.off('dataReady', handler);
            this.handlers.delete(emitter);
        }
    }
}

// Step 6: Verify fix with memory regression test:
describe('DataProcessor memory regression', () => {
    it('does not accumulate listeners', async () => {
        const emitter = new EventEmitter();
        const processor = new DataProcessor();

        // Run 1000 attach/detach cycles:
        for (let i = 0; i < 1000; i++) {
            processor.attach(emitter);
            emitter.emit('dataReady');
            processor.detach(emitter);
        }

        // Force GC:
        global.gc?.();

        expect(emitter.listenerCount('dataReady')).toBe(0);

        const { heapUsed } = process.memoryUsage();
        const heapMB = heapUsed / 1024 / 1024;
        expect(heapMB).toBeLessThan(50); // Baseline shouldn't be significantly exceeded
    });
});
```

## Quick Reference Table

| Tool | How to trigger | What it shows | Best for |
|---|---|---|---|
| `--inspect` | CLI flag or `kill -SIGUSR1 <pid>` | Full DevTools access: heap, CPU, network | Interactive debugging session |
| `--inspect-brk` | CLI flag | Same + pauses on first line | Debugging startup leaks |
| Heap Snapshot | DevTools Memory tab or `v8.writeHeapSnapshot()` | All live objects, sizes, retainer chains | Identifying WHAT is leaking |
| Allocation Timeline | DevTools Memory tab → "Allocation instrumentation" | Allocations over time with call stacks | Finding WHERE allocations happen |
| Allocation Sampling | DevTools Memory tab → "Allocation sampling" | Statistical allocation profiler | Low-overhead production profiling |
| `process.memoryUsage()` | Programmatic | heapUsed, external, rss, heapTotal | Monitoring and alerting |
| `v8.getHeapStatistics()` | Programmatic | Detailed GC space breakdown | Tuning GC, detecting fragmentation |
| `clinic heapprofiler` | `clinic heapprofiler -- node app.js` | Heap timeline with call stacks | Quick CI/triage |
| `clinic doctor` | `clinic doctor -- node app.js` | Health check: memory + CPU + event loop | Initial investigation |

| Leak type | Symptom in snapshot | Common cause | Fix |
|---|---|---|---|
| Event listener | `(closure)` count growing | `.on()` in hot path, never `.off()` | Use `.once()`, `.off()`, or `AbortSignal` |
| Unbounded cache | Specific class/Object count growing | Map/object with no eviction | Add TTL or LRU eviction |
| Timer/interval | `(closure)` + timer in retainer chain | `setInterval` never `clearInterval`'d | Store and clear interval IDs |
| Stream not consumed | `ReadStream` or Buffer in retainer | Created but not piped or destroyed | Always call `.destroy()` on unused streams |
| Closure capture | Large Buffer/object in closure context | Variable in enclosing scope captured unintentionally | Separate scopes, nullify after use |
| Buffer leak | `external` growing, `heapUsed` stable | Native addon or Buffer not released | Check `arrayBuffers` in `memoryUsage()`, audit native code |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) knowing that **`external` in `process.memoryUsage()` tracks Buffers, not heap** — a Buffer leak shows up in `external`, not `heapUsed`, and candidates who only watch `heapUsed` will miss an entire class of leaks; (2) understanding the **retainer chain in Chrome DevTools** — not just "take a snapshot and look for big objects" but specifically using the Comparison view to find delta, then the Retainers panel to trace the reference chain from the leaked object back to the GC root that's keeping it alive — this is the skill that actually resolves leaks; (3) explaining the **`'exit'` vs `'close'` distinction on child processes is irrelevant here** but the equivalent for memory is knowing **`heapTotal` vs `heapUsed`** — `heapTotal` can be large because V8 pre-allocates in chunks and shrinks lazily, so `heapTotal` > `heapUsed` alone is not a leak; (4) knowing that **`setMaxListeners(0)` suppresses the warning without fixing anything** — this is the cargo-cult fix and identifying it as wrong demonstrates real understanding of event listener leaks; (5) articulating the **three-snapshot workflow** — baseline after warmup, exercise, force GC, compare — specifically that you force GC before the comparison snapshot to exclude objects that are unreachable but not yet collected, giving you a clean view of true leaks; and (6) having a **production strategy beyond "attach Chrome DevTools"** — signal-triggered snapshots via `SIGUSR2`, HTTP endpoints guarded by internal tokens, and the graceful restart at memory threshold pattern show that the candidate has actually operated Node.js services in production environments.
