# `AsyncLocalStorage` for Request-Scoped Context (Replaces `cls-hooked`) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does `AsyncLocalStorage` solve and why did it take so long for Node.js to provide a solution?**
A: In a multithreaded language (Java, Go, C#), thread-local storage solves a common problem: attaching context to the current execution thread so that any code running in that thread can access it without passing it explicitly. Log a request ID on every log line, make the authenticated user available to any service called during a request — it all flows through the thread. Every request gets its own thread; the thread local is the request local.

Node.js has one thread. A single Node.js process handles thousands of concurrent requests by multiplexing them through the event loop. There is no "current thread" per request. When Request A's callback runs and logs a message, there's no built-in mechanism to know that this callback was initiated by Request A versus Request B, because both callbacks look the same to Node.js's single thread.

`AsyncLocalStorage` solves this by tracking *async context* — a causal chain of "this async operation was created by this other async operation, which was created by the original request handler." It threads a context object through the entire async tree of an HTTP request, making it accessible to any code running within that tree without explicit parameter passing.

Why it took so long: the underlying mechanism (`AsyncHooks`, added in Node.js 8.x as an experimental API in 2017) had significant performance overhead and stability issues. `AsyncLocalStorage`, built on top of `AsyncHooks`, was stabilized only in Node.js 16 (2021). The community worked around it for years with `domain` (deprecated, not recommended), `continuation-local-storage` (CLS, unmaintained), and `cls-hooked` (a CLS implementation using `AsyncHooks`).

**Q2. What is a "context" in the request-scoped context pattern and what does it typically contain?**
A: A context is an object associated with the lifetime of one logical operation (typically one HTTP request, one message queue handler invocation, or one job execution). It carries cross-cutting data that multiple layers of the system need without anyone explicitly threading it as a function parameter:

```typescript
// A typical request context object:
interface RequestContext {
    // Identity / tracing
    requestId: string;        // Unique ID for this request (for log correlation)
    traceId: string;          // OpenTelemetry / Jaeger trace ID
    spanId: string;           // Current span ID
    parentSpanId?: string;    // Parent span (for distributed tracing)

    // Authentication
    userId?: string;          // Authenticated user's ID
    sessionId?: string;       // Session ID
    roles?: string[];         // User's roles/permissions

    // Operational
    startTime: number;        // Request start time (for duration tracking)
    userAgent?: string;       // Client user agent
    ipAddress?: string;       // Client IP address
    tenantId?: string;        // Multi-tenant: which tenant this request belongs to

    // Feature flags / experiment context
    experiments?: Record<string, string>;

    // Database / transaction
    dbTransaction?: DbTransaction;  // Current DB transaction for unit-of-work pattern
}
```

The key insight: this context should be accessible in:
- Business logic services (for authorization, tenancy)
- Database layer (for transaction propagation, query logging)
- External API clients (to forward the trace ID in outgoing headers)
- Logging layer (to include requestId in every log line automatically)

Without `AsyncLocalStorage`, every function in the call chain must accept `ctx` as a parameter — deeply polluting signatures and creating tight coupling between layers. With it, the context is implicit and available anywhere within the request's async tree.

## Section 2: The Mechanism

**Q3. How does `AsyncLocalStorage` work internally — what are `AsyncHooks` and how do they track async operations?**
A: `AsyncLocalStorage` is built on Node.js's `AsyncHooks` API, which provides lifecycle hooks for every async resource (Promises, Timers, I/O callbacks, etc.):

```
AsyncHooks lifecycle for a Promise:
                           init(asyncId, type, triggerAsyncId)
                           ↑
Promise created ──────────│──── asyncId=42 assigned, triggerAsyncId=current async context
                          │
                          │    before(asyncId)
                          │    ↑
Promise resolves ─────────│────│──── context switches to asyncId=42
                          │    │
                          │    │    [callback runs]
                          │    │
                          │    after(asyncId)
                          │    ↓
                          │    context switches back
                          │
Promise destroyed ─────────────── destroy(asyncId)
```

Every async resource gets a unique `asyncId`. When a new async resource is created (e.g., `new Promise(...)`, `setTimeout(fn)`, `fs.readFile(...)`), it captures the currently-active `asyncId` as its `triggerAsyncId`. This creates a parent-child relationship: the Promise created inside an HTTP request handler has `triggerAsyncId` pointing to the request handler's async context.

`AsyncLocalStorage` exploits this tree: when you call `als.run(store, fn)`, it associates `store` with the current `asyncId`. Any async resource created within `fn` inherits a snapshot of the current store through the `asyncId` → `triggerAsyncId` chain. When those resources' callbacks eventually fire, `AsyncLocalStorage` restores the correct store based on the current `asyncId`.

The result: the store "flows" through the async tree automatically — any `await`, `Promise.then`, `setTimeout`, `setImmediate`, event emitter callback, or I/O callback scheduled within the `run()` scope carries the store forward.

**Q4. What is the precise API of `AsyncLocalStorage` and what does each method do?**
A:

```typescript
import { AsyncLocalStorage } from 'async_hooks';  // Node.js 14.x
import { AsyncLocalStorage } from 'node:async_hooks';  // Modern Node.js 18+

// Constructor: creates a new storage slot (you can have multiple)
const als = new AsyncLocalStorage<RequestContext>();

// als.run(store, callback, ...args)
// Creates a new async context where als.getStore() returns `store`
// Everything called/awaited within callback inherits this store
als.run({ requestId: 'abc-123', userId: '42' }, () => {
    doWork();  // can call als.getStore() → { requestId: 'abc-123', userId: '42' }
});

// als.getStore()
// Returns the store for the current async context, or undefined if outside a run()
const store = als.getStore();
// undefined if called outside an als.run() context

// als.enterWith(store)
// Changes the current async context's store IN PLACE (no new scope)
// DANGEROUS: changes the store for ALL subsequent code in the same async context
// Rarely needed — prefer run()
als.enterWith({ requestId: 'xyz' });

// als.disable()
// Disables the instance, allowing garbage collection of stored data
// Call when the ALS instance is no longer needed
als.disable();

// Static: AsyncLocalStorage.snapshot()  (Node.js 18.7+)
// Captures current async context and returns a function that runs a callback in it
const snapshot = AsyncLocalStorage.snapshot();
setTimeout(() => {
    snapshot(() => {
        // Runs in the original context, even though it's a new setTimeout
        als.getStore();  // available here
    });
}, 1000);
```

**Q5. What is the difference between `als.run()` creating a new scope vs `als.enterWith()` mutating the current scope?**
A: `run()` creates a child async context — only code within the callback (and async operations it creates) sees the new store. `enterWith()` mutates the current async context's store in place — all subsequent code in the current context sees the new store, including code that runs after `enterWith()` returns:

```javascript
const als = new AsyncLocalStorage();

// === run() === creates a new scope ===
als.run({ value: 'A' }, async () => {
    console.log(als.getStore().value);  // 'A'
    await somethingAsync();
    console.log(als.getStore().value);  // 'A' — same scope preserved
});
// Code outside the run() callback:
console.log(als.getStore());  // undefined — we're outside the run() scope

// === enterWith() === mutates in place ===
async function handler(req) {
    als.enterWith({ requestId: req.id });
    // All subsequent code in THIS async context sees the store
    console.log(als.getStore().requestId);  // req.id
    await service.doWork();  // sees the store too
}
// BUT: if handler is called multiple times concurrently,
// each call stack is its own async context — they don't interfere.
// enterWith() is safe ONLY if called once at the very start of an async context
// (like the top of an Express middleware or Koa ctx handler).

// DANGEROUS misuse of enterWith():
als.enterWith({ value: 'B' });  // If called inside setTimeout or promise chain,
                                 // you're mutating a context you don't own
```

## Section 3: Request Context in Practice

**Q6. How do you implement request context propagation in an Express.js application using `AsyncLocalStorage`?**
A: The pattern: middleware at the top of the stack initializes the store; all subsequent middleware and route handlers can access it without parameter passing:

```typescript
// context/request-context.ts
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';

interface RequestContext {
    requestId: string;
    traceId: string;
    userId?: string;
    startTime: number;
    [key: string]: unknown;  // Allow arbitrary additions
}

const als = new AsyncLocalStorage<RequestContext>();

export const RequestContext = {
    // Called by middleware to create the context for this request
    create(initial: Partial<RequestContext> = {}): RequestContext {
        return {
            requestId: randomUUID(),
            traceId: randomUUID(),
            startTime: Date.now(),
            ...initial
        };
    },

    // Get the current context (throws if outside a request)
    get(): RequestContext {
        const ctx = als.getStore();
        if (!ctx) throw new Error('No request context — called outside als.run()');
        return ctx;
    },

    // Get the current context (returns null if outside a request)
    tryGet(): RequestContext | null {
        return als.getStore() ?? null;
    },

    // Set a value on the current context
    set<K extends keyof RequestContext>(key: K, value: RequestContext[K]): void {
        const ctx = als.getStore();
        if (ctx) ctx[key] = value;
    },

    // Run a function within a new request context
    run<T>(context: RequestContext, fn: () => T): T {
        return als.run(context, fn) as T;
    }
};

// middleware/context.middleware.ts
import express from 'express';
import { RequestContext } from '../context/request-context';

export function contextMiddleware(
    req: express.Request,
    res: express.Response,
    next: express.NextFunction
): void {
    // Extract trace ID from incoming headers (if from upstream service)
    const incomingTraceId = req.headers['x-trace-id'] as string;
    const incomingRequestId = req.headers['x-request-id'] as string;

    const context = RequestContext.create({
        requestId: incomingRequestId || undefined,
        traceId: incomingTraceId || undefined,
    });

    // Add request ID to response headers for client-side correlation
    res.setHeader('X-Request-ID', context.requestId);

    // Run the rest of the request within this context
    RequestContext.run(context, () => next());
    // next() starts the async chain — all subsequent middleware and route handlers
    // run within the als.run() scope and can call als.getStore()
}

// app.ts
const app = express();
app.use(contextMiddleware);  // MUST be first — establishes context for all subsequent middleware

// auth.middleware.ts
export async function authMiddleware(req, res, next) {
    try {
        const token = req.headers.authorization?.split(' ')[1];
        const user = await verifyToken(token);
        RequestContext.set('userId', user.id);  // Store on context — no parameter passing needed
        next();
    } catch {
        res.status(401).json({ error: 'Unauthorized' });
    }
}

// services/order.service.ts — deep in the call chain, no context parameter needed
export async function createOrder(items: Item[]): Promise<Order> {
    const { userId, requestId } = RequestContext.get();  // accessible anywhere!
    logger.info('Creating order', { userId, requestId, itemCount: items.length });
    return db.orders.create({ userId, items });
}
```

**Q7. How do you propagate context to child workers, external HTTP calls, and message queues?**
A: Context propagation beyond the current Node.js process requires explicit serialization and forwarding — `AsyncLocalStorage` only covers in-process async operations:

```typescript
// 1. Outgoing HTTP requests — forward trace headers
// http-client.ts
import axios from 'axios';
import { RequestContext } from './context/request-context';

const httpClient = axios.create();

httpClient.interceptors.request.use((config) => {
    const ctx = RequestContext.tryGet();
    if (ctx) {
        // Forward context as headers to downstream services
        config.headers['X-Request-ID'] = ctx.requestId;
        config.headers['X-Trace-ID'] = ctx.traceId;
        config.headers['X-User-ID'] = ctx.userId ?? '';
    }
    return config;
});

// 2. Message queue publishing — embed context in message
// producer.ts
async function publishOrderEvent(order: Order): Promise<void> {
    const ctx = RequestContext.tryGet();
    await kafka.producer.send({
        topic: 'orders',
        messages: [{
            key: order.id,
            value: JSON.stringify({
                payload: order,
                metadata: {
                    requestId: ctx?.requestId,
                    traceId: ctx?.traceId,
                    userId: ctx?.userId,
                    publishedAt: new Date().toISOString()
                }
            })
        }]
    });
}

// Consumer side: restore context from message metadata
// consumer.ts
async function handleOrderMessage(message: KafkaMessage): Promise<void> {
    const { payload, metadata } = JSON.parse(message.value.toString());

    // Re-establish context from the original request's metadata
    const context = RequestContext.create({
        requestId: metadata.requestId || undefined,
        traceId: metadata.traceId || undefined,
        userId: metadata.userId || undefined
    });

    await RequestContext.run(context, async () => {
        // Now all processing within this consumer handler has context
        await processOrder(payload);  // can use RequestContext.get() internally
    });
}

// 3. Worker Threads — pass context via workerData or MessageChannel
// main.ts
import { Worker } from 'node:worker_threads';
const ctx = RequestContext.get();
const worker = new Worker('./worker.js', {
    workerData: {
        context: {  // Serialize — ALS state does NOT transfer to workers automatically
            requestId: ctx.requestId,
            traceId: ctx.traceId,
            userId: ctx.userId
        },
        payload: workPayload
    }
});

// worker.js
import { workerData } from 'node:worker_threads';
// Re-establish context in the worker process
RequestContext.run(RequestContext.create(workerData.context), async () => {
    await processHeavyWork(workerData.payload);
});
```

## Section 4: Logging Integration

**Q8. How do you integrate `AsyncLocalStorage` with a logging library (Winston, Pino) for automatic request ID injection?**
A: The most impactful use case: every log line automatically includes the request ID and trace ID without any explicit passing:

```typescript
// logger.ts — Winston with automatic context injection
import winston from 'winston';
import { RequestContext } from './context/request-context';

// Custom format that adds context to every log entry
const contextFormat = winston.format((info) => {
    const ctx = RequestContext.tryGet();
    if (ctx) {
        info.requestId = ctx.requestId;
        info.traceId = ctx.traceId;
        info.userId = ctx.userId;
    }
    return info;
})();

export const logger = winston.createLogger({
    format: winston.format.combine(
        contextFormat,           // Inject context fields
        winston.format.timestamp(),
        winston.format.json()    // Output as structured JSON
    ),
    transports: [new winston.transports.Console()]
});

// Usage — no request ID needed in the call:
// service/order.service.ts
logger.info('Processing order', { orderId: '123', amount: 99.99 });
// Output: { "requestId": "abc-xyz", "traceId": "def-uvw", "userId": "42",
//           "message": "Processing order", "orderId": "123", "amount": 99.99 }

// --- Pino alternative ---
import pino from 'pino';

const basePino = pino({ level: 'info' });

// Create a child logger that injects context on each log call
export const logger = {
    info: (msg: string, obj?: object) => {
        const ctx = RequestContext.tryGet();
        basePino.child({ requestId: ctx?.requestId, traceId: ctx?.traceId })
               .info(obj ?? {}, msg);
    },
    error: (msg: string, obj?: object) => {
        const ctx = RequestContext.tryGet();
        basePino.child({ requestId: ctx?.requestId, traceId: ctx?.traceId })
               .error(obj ?? {}, msg);
    }
};

// Even simpler with pino-http: the package uses AsyncLocalStorage internally
// to make req.log available in route handlers with request context pre-bound
```

## Section 5: `cls-hooked` vs `AsyncLocalStorage`

**Q9. What was `cls-hooked` and why is `AsyncLocalStorage` its replacement?**
A: `continuation-local-storage` (CLS) was a 2013 library that used Node.js's `domain` API (now deprecated) to propagate context through callbacks. `cls-hooked` (2016) was a major improvement that used the experimental `AsyncHooks` API instead, providing more reliable context propagation. For years, `cls-hooked` was the only practical solution:

```javascript
// cls-hooked style (pre-AsyncLocalStorage)
const createNamespace = require('cls-hooked').createNamespace;
const ns = createNamespace('request');

// Middleware:
app.use((req, res, next) => {
    ns.bindEmitter(req);
    ns.bindEmitter(res);
    ns.run(() => {
        ns.set('requestId', generateId());
        next();
    });
});

// Access in service:
const requestId = ns.get('requestId');
```

Why `AsyncLocalStorage` replaces it:

| Dimension | `cls-hooked` | `AsyncLocalStorage` |
|---|---|---|
| Maintenance | Effectively unmaintained (last meaningful update 2019) | Active, part of Node.js standard library |
| Stability | Built on experimental AsyncHooks API directly | Built on stabilized AsyncHooks internals |
| Dependencies | External npm package with known memory leaks | Zero dependencies — in Node.js core |
| TypeScript | Poor built-in types | First-class generics: `AsyncLocalStorage<T>` |
| API | Imperative, namespace-based | Clean, ergonomic `run`/`getStore` API |
| Node.js 18+ | Not reliably compatible | Fully supported, stable |
| Performance | Overhead on every async operation | Same underlying mechanism, better implementation |
| Memory leaks | Known issues with certain patterns | Better-managed internally |

**Q10. What are the migration steps from `cls-hooked` to `AsyncLocalStorage`?**
A: The concepts map directly; the API surface changes:

```typescript
// BEFORE: cls-hooked
import { createNamespace } from 'cls-hooked';
const ns = createNamespace('my-app');

// Creating context (middleware):
ns.run(() => {
    ns.set('requestId', '123');
    ns.set('userId', '42');
    next();
});

// Reading context (anywhere):
const requestId = ns.get('requestId');
const userId = ns.get('userId');

// AFTER: AsyncLocalStorage
import { AsyncLocalStorage } from 'node:async_hooks';
interface Context { requestId: string; userId?: string; }
const als = new AsyncLocalStorage<Context>();

// Creating context (middleware):
als.run({ requestId: '123', userId: '42' }, () => next());

// Reading context (anywhere):
const ctx = als.getStore();
const requestId = ctx?.requestId;
const userId = ctx?.userId;

// Key differences in migration:
// 1. cls-hooked: set/get individual keys — store is effectively a Map
//    AsyncLocalStorage: store is a single typed object — access via properties

// 2. cls-hooked: bindEmitter() needed for EventEmitters
//    AsyncLocalStorage: EventEmitters work automatically in Node.js 14.8+
//    (EventEmitter.captureRejections and AsyncResource.bind handle this)

// 3. cls-hooked: ns.bind(fn) to manually bind a callback
//    AsyncLocalStorage: use AsyncResource or snapshot() for manual binding

// 4. cls-hooked: createNamespace creates global registry entries
//    AsyncLocalStorage: each instance is independent, garbage collected normally
```

## Section 6: Advanced Patterns

**Q11. How do you implement database transaction propagation using `AsyncLocalStorage`?**
A: The Unit of Work pattern — a database transaction that automatically encompasses all DB operations within a request — without passing the transaction object to every function:

```typescript
// db/transaction.ts
import { AsyncLocalStorage } from 'node:async_hooks';
import { Knex } from 'knex';
import db from './db';

const transactionStorage = new AsyncLocalStorage<Knex.Transaction>();

export async function withTransaction<T>(fn: () => Promise<T>): Promise<T> {
    return db.transaction(async (trx) => {
        // All DB operations within fn() use this transaction automatically
        return transactionStorage.run(trx, fn);
    });
}

export function getCurrentTransaction(): Knex.Transaction | undefined {
    return transactionStorage.getStore();
}

// db/repository.ts — uses transaction if one exists, otherwise direct DB
export async function insertUser(userData: Partial<User>): Promise<User> {
    const trx = getCurrentTransaction();
    const queryBuilder = trx ? trx('users') : db('users');  // Use trx if in transaction
    const [user] = await queryBuilder.insert(userData).returning('*');
    return user;
}

// Usage — transaction propagates automatically:
async function registerUser(email: string): Promise<void> {
    await withTransaction(async () => {
        // Both operations automatically use the same transaction
        const user = await insertUser({ email });
        await insertWelcomeNotification(user.id);  // Uses same transaction — no parameter!
        await updateUserCount();                   // Uses same transaction — no parameter!
        // If any throws, the entire transaction rolls back
    });
}
```

**Q12. How do you implement multi-tenant context isolation using `AsyncLocalStorage`?**
A: Multi-tenant applications need to ensure that tenant A's data is never accidentally accessible from tenant B's request context:

```typescript
// tenant/context.ts
import { AsyncLocalStorage } from 'node:async_hooks';

interface TenantContext {
    tenantId: string;
    tenantName: string;
    dbSchema: string;  // PostgreSQL schema for row-level isolation
    features: Set<string>;
    plan: 'free' | 'pro' | 'enterprise';
    rateLimit: number;
}

const tenantStorage = new AsyncLocalStorage<TenantContext>();

export const TenantContext = {
    run: <T>(ctx: TenantContext, fn: () => T) => tenantStorage.run(ctx, fn),
    get: (): TenantContext => {
        const ctx = tenantStorage.getStore();
        if (!ctx) throw new Error('No tenant context');
        return ctx;
    },
    getTenantId: (): string => TenantContext.get().tenantId,
    hasFeature: (feature: string): boolean =>
        TenantContext.get().features.has(feature)
};

// middleware/tenant.middleware.ts
export async function tenantMiddleware(req, res, next) {
    const tenantId = req.headers['x-tenant-id'];
    if (!tenantId) return res.status(400).json({ error: 'Missing tenant' });

    const tenant = await tenantRegistry.lookup(tenantId);
    if (!tenant) return res.status(403).json({ error: 'Unknown tenant' });

    TenantContext.run({
        tenantId: tenant.id,
        tenantName: tenant.name,
        dbSchema: `tenant_${tenant.id}`,
        features: new Set(tenant.enabledFeatures),
        plan: tenant.plan,
        rateLimit: tenant.rateLimit
    }, () => next());
}

// db/tenant-db.ts — all queries scoped to the current tenant's schema
export async function query<T>(sql: string, params: unknown[]): Promise<T[]> {
    const { dbSchema } = TenantContext.get();
    // Set PostgreSQL schema search path per-query to enforce tenant isolation
    const conn = await pool.connect();
    try {
        await conn.query(`SET search_path TO ${dbSchema}, public`);
        const { rows } = await conn.query<T>(sql, params);
        return rows;
    } finally {
        conn.release();
    }
}

// Feature gating with no parameter passing:
export async function exportData(): Promise<void> {
    if (!TenantContext.hasFeature('data-export')) {
        throw new Error('Data export not available on your plan');
    }
    // Proceed with export
}
```

**Q13. How does `AsyncLocalStorage` work with EventEmitters, streams, and timers?**
A: In Node.js 14.8+, `EventEmitter` events automatically propagate the async context from when the listener was added (not when the event fires). Streams (which are EventEmitters) and timers also propagate context:

```javascript
import { AsyncLocalStorage } from 'node:async_hooks';
import { EventEmitter } from 'node:events';

const als = new AsyncLocalStorage();

// EventEmitter: listener captures context at the time it's ADDED
const emitter = new EventEmitter();

als.run({ value: 'request-A' }, () => {
    emitter.on('data', () => {
        console.log(als.getStore()?.value);  // 'request-A' — captures context at .on() time
    });
});

// Later, when the event fires (outside any als.run):
emitter.emit('data');  // Logs 'request-A' — context preserved!

// Timers: context propagates from where setTimeout is called
als.run({ requestId: 'req-123' }, () => {
    setTimeout(() => {
        console.log(als.getStore()?.requestId);  // 'req-123' — preserved through timer
    }, 100);
});

// Streams: context flows through transform streams
import { Transform } from 'node:stream';

als.run({ userId: '42' }, () => {
    const transform = new Transform({
        transform(chunk, encoding, callback) {
            console.log(als.getStore()?.userId);  // '42' — context in transform
            callback(null, chunk);
        }
    });
    readable.pipe(transform).pipe(writable);
});

// CAUTION: EventEmitter before Node.js 14.8 does NOT propagate context
// CAUTION: If using EventEmitter with removeListener, the context snapshots
//          at each .on() call independently

// Manual binding for edge cases (when automatic propagation isn't sufficient):
import { AsyncResource } from 'node:async_hooks';

const boundCallback = AsyncResource.bind(() => {
    console.log(als.getStore());  // Always sees the context from when bind() was called
});

// Pass boundCallback to any non-context-propagating API
someOldLibrary.onEvent(boundCallback);
```

## Section 7: Testing and Error Handling

**Q14. How do you write tests for code that uses `AsyncLocalStorage`?**
A: Tests must set up the async context explicitly since test runners don't automatically establish a request context:

```typescript
// utils/test-context.ts
import { RequestContext } from '../context/request-context';

export function withTestContext<T>(
    overrides: Partial<RequestContext> = {},
    fn: () => T
): T {
    const context = RequestContext.create({
        requestId: 'test-request-id',
        traceId: 'test-trace-id',
        userId: 'test-user-id',
        ...overrides
    });
    return RequestContext.run(context, fn);
}

// order.service.test.ts
import { withTestContext } from '../utils/test-context';
import { createOrder } from '../services/order.service';
import { RequestContext } from '../context/request-context';

describe('OrderService', () => {
    it('creates order with the current user from context', async () => {
        const order = await withTestContext(
            { userId: 'user-999' },
            () => createOrder([{ productId: 'prod-1', quantity: 2 }])
        );
        expect(order.userId).toBe('user-999');
    });

    it('includes requestId in log output', async () => {
        const logSpy = jest.spyOn(logger, 'info');

        await withTestContext({ requestId: 'req-abc' }, async () => {
            await createOrder([{ productId: 'prod-1', quantity: 1 }]);
        });

        expect(logSpy).toHaveBeenCalledWith(
            expect.stringContaining('Creating order'),
            expect.objectContaining({ requestId: 'req-abc' })
        );
    });

    it('throws when accessed outside context', async () => {
        // Accessing context outside withTestContext (no als.run()) should throw
        await expect(createOrder([])).rejects.toThrow('No request context');
    });

    it('isolates context between concurrent requests', async () => {
        // Run two concurrent "requests" and verify they don't share context
        const [result1, result2] = await Promise.all([
            withTestContext({ userId: 'user-1' }, async () => {
                await delay(50);  // simulate async work
                return RequestContext.get().userId;
            }),
            withTestContext({ userId: 'user-2' }, async () => {
                await delay(25);  // different timing
                return RequestContext.get().userId;
            })
        ]);

        expect(result1).toBe('user-1');
        expect(result2).toBe('user-2');
        // If context leaked, one would see the other's userId
    });
});
```

**Q15. What are the error handling implications of `AsyncLocalStorage` — does context propagate through errors?**
A: Context propagates correctly through thrown errors and rejected Promises — the async context is maintained even when the promise chain is rejected:

```typescript
als.run({ requestId: 'req-123' }, async () => {
    try {
        await riskyOperation();  // throws
    } catch (error) {
        // Context is still accessible in the catch block:
        const ctx = als.getStore();
        logger.error('Operation failed', {
            requestId: ctx?.requestId,  // 'req-123' — still accessible!
            error
        });
        throw error;  // re-throw — context still propagates
    }
});

// Context in global error handlers:
process.on('uncaughtException', (error) => {
    const ctx = als.getStore();  // MAY be available if the error originated in an als.run()
    // But: not reliable for all uncaughtExceptions — depends on where the error originated
    logger.error('Uncaught exception', { requestId: ctx?.requestId, error });
});

// Express error handler — context IS available because Express calls it within
// the same async context as the request:
app.use((error, req, res, next) => {
    const ctx = RequestContext.tryGet();
    logger.error('Request failed', {
        requestId: ctx?.requestId,  // Available!
        path: req.path,
        error: error.message
    });
    res.status(500).json({ requestId: ctx?.requestId, error: 'Internal Server Error' });
});
```

## Section 8: Performance and Pitfalls

**Q16. What is the performance overhead of `AsyncLocalStorage` and how do you mitigate it?**
A: `AsyncLocalStorage` has measurable overhead because `AsyncHooks` instruments every async operation in Node.js. The overhead comes from the `init` hook firing when each Promise, timer, or I/O operation is created:

```
Performance impact (approximate benchmarks, varies by Node.js version):
- Node.js 12/13: ~20-30% throughput reduction (AsyncHooks overhead was high)
- Node.js 16/18: ~5-10% throughput reduction (significant optimization of AsyncHooks)
- Node.js 20+: ~2-5% throughput reduction (ongoing optimizations)

For a typical web server handling 10,000 req/s at 1ms response time:
- 5% overhead = ~500 extra microseconds per request = 9,500 effective req/s
- Acceptable for most applications; significant for latency-critical high-throughput services

Mitigation strategies:
```

```typescript
// 1. Disable ALS for known hot paths that don't need context
//    (use judiciously — this bypasses context propagation)
import { AsyncResource } from 'node:async_hooks';
// Not currently a public API, but some applications use raw asynchooks disable

// 2. Use a single ALS instance, not multiple
// BAD: multiple ALS instances multiply the overhead
const userAls = new AsyncLocalStorage<User>();
const requestAls = new AsyncLocalStorage<RequestInfo>();
const traceAls = new AsyncLocalStorage<TraceContext>();

// GOOD: one ALS instance, composite store
const als = new AsyncLocalStorage<{
    user?: User;
    request?: RequestInfo;
    trace?: TraceContext;
}>();

// 3. Avoid storing large objects — getStore() is called frequently
// BAD: store 10MB of cached data in the context
als.run({ userId: '42', bigCache: loadMegabytesOfData() }, fn);

// GOOD: store only small identifying/routing data
als.run({ userId: '42', requestId: 'abc' }, fn);
// Fetch larger data by ID when needed

// 4. Node.js 20+ has AsyncContextFrame which significantly reduces overhead
// Check node --version and upgrade if performance is critical
```

**Q17. What are the most common `AsyncLocalStorage` pitfalls and how do you avoid them?**
A:

```typescript
// PITFALL 1: Context not established before async boundaries
// express middleware order matters:
app.use(someOtherMiddleware);  // If this creates async operations...
app.use(contextMiddleware);    // ...this runs AFTER, so context isn't in those operations
// FIX: contextMiddleware must be FIRST

// PITFALL 2: Mutating the store object directly across concurrent requests
als.run({ count: 0 }, async () => {
    const ctx = als.getStore();
    ctx.count++;               // DANGER if multiple concurrent requests share state
    await asyncOperation();
    ctx.count++;               // Both concurrent requests modify the SAME object!
});
// FIX: use als.run() with a FRESH object per request (not a shared reference)
// Each als.run() call creates a new scope, but if the SAME object is passed
// to multiple run() calls, mutations are visible across scopes

const sharedCtx = { count: 0 };
als.run(sharedCtx, () => req1Handler());  // Both share the same object!
als.run(sharedCtx, () => req2Handler());  // req1 and req2 mutate the same ctx

// FIX: always create a fresh object per request
app.use((req, res, next) => {
    als.run({ requestId: generateId(), count: 0 }, () => next());
    //         ↑ new object literal each time
});

// PITFALL 3: Losing context in EventEmitter callbacks on Node.js < 14.8
// Before Node.js 14.8, EventEmitter .on() callbacks don't propagate ALS context
// FIX: manually bind the callback
const boundHandler = AsyncResource.bind(handler);
emitter.on('event', boundHandler);

// PITFALL 4: Context not propagated to Worker Threads
// ALS state does NOT automatically transfer to Worker Threads
// FIX: serialize context to workerData and re-establish in worker (Q7)

// PITFALL 5: Using enterWith() in middleware chains
// enterWith() modifies the CURRENT context — if the current context is shared
// between multiple in-flight requests (it shouldn't be, but bugs happen),
// one request's enterWith() affects others
// FIX: always use als.run() in middleware to create a new scope

// PITFALL 6: Forgetting cleanup for long-lived processes
// ALS stores are released when the async context ends
// For long-lived connections (WebSockets, SSE streams), the context lives as long
// as the connection — potentially leaking large objects for hours
// FIX: store only small identifiers, not large objects
```

## Section 9: Scenario-Based Questions

**Q18. "Your Node.js microservice logs don't show which request caused an error in production. Design a solution using `AsyncLocalStorage` that adds request tracing to all logs automatically."**
A: A complete distributed tracing + logging solution:

```typescript
// tracing/context.ts
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';

interface TracingContext {
    requestId: string;    // Unique per request (for log correlation)
    traceId: string;      // Same across all services for one user action
    spanId: string;       // Current service's span
    service: string;      // Service name (e.g., 'order-service')
    method?: string;      // HTTP method
    path?: string;        // HTTP path
    userId?: string;
}

const als = new AsyncLocalStorage<TracingContext>();

export const Tracing = {
    start(initial: Partial<TracingContext> = {}): void {
        // Called at request entry point
    },
    run<T>(ctx: TracingContext, fn: () => T): T {
        return als.run(ctx, fn) as T;
    },
    get(): TracingContext | undefined {
        return als.getStore();
    },
    // Returns headers to forward to downstream services
    getOutgoingHeaders(): Record<string, string> {
        const ctx = als.getStore();
        if (!ctx) return {};
        return {
            'X-Request-ID': ctx.requestId,
            'X-Trace-ID': ctx.traceId,
            'X-Span-ID': ctx.spanId   // downstream creates a child span
        };
    }
};

// middleware/tracing.middleware.ts
export function tracingMiddleware(req, res, next) {
    const ctx: TracingContext = {
        requestId: (req.headers['x-request-id'] as string) || randomUUID(),
        traceId: (req.headers['x-trace-id'] as string) || randomUUID(),
        spanId: randomUUID(),  // Always new per service
        service: process.env.SERVICE_NAME || 'unknown',
        method: req.method,
        path: req.path
    };

    res.setHeader('X-Request-ID', ctx.requestId);
    res.setHeader('X-Trace-ID', ctx.traceId);

    Tracing.run(ctx, () => next());
}

// logger.ts — Winston with automatic context injection
import winston from 'winston';

const tracingFormat = winston.format((info) => {
    const ctx = Tracing.get();
    return ctx ? { ...ctx, ...info } : info;  // merge context into every log entry
})();

export const logger = winston.createLogger({
    format: winston.format.combine(
        tracingFormat,
        winston.format.timestamp(),
        winston.format.json()
    ),
    transports: [new winston.transports.Console()]
});

// Every log anywhere in the service now includes:
// { "requestId": "...", "traceId": "...", "spanId": "...", "service": "order-service",
//   "method": "POST", "path": "/orders", "message": "...", "timestamp": "..." }

// http-client.ts — forward trace context to downstream services
import axios from 'axios';

export const http = axios.create();
http.interceptors.request.use(config => ({
    ...config,
    headers: { ...config.headers, ...Tracing.getOutgoingHeaders() }
}));

// Now querying all logs for traceId=X shows the complete journey across all services
```

**Q19. "You're debugging a race condition where User A's data appears in User B's response. The suspicion is context contamination. How would you diagnose this and what is the likely cause?"**
A: Context contamination between requests is almost always caused by one of three root causes — shared object references, wrong middleware order, or EventEmitter binding issues:

```typescript
// DIAGNOSIS TOOLKIT

// 1. Add context ID logging at entry and exit:
app.use((req, res, next) => {
    const ctxId = randomUUID();  // a unique ID per context scope
    als.run({ ctxId, userId: null }, () => {
        console.log(`[ENTER] ctx=${ctxId} path=${req.path}`);
        res.on('finish', () => {
            console.log(`[EXIT] ctx=${ctxId} userId=${als.getStore()?.userId}`);
        });
        next();
    });
});

// If logs show: [EXIT] ctx=ctx-A userId=user-B — contamination confirmed

// 2. Detect mutation of shared reference:
// BAD pattern that causes the bug:
const sharedBase = { defaults: { timeout: 30000 } };

app.use((req, res, next) => {
    als.run(sharedBase, () => next());
    //       ↑ SAME OBJECT passed to all requests — mutations are shared!
});

// Request A: als.getStore().userId = 'user-A'  ← mutates sharedBase
// Request B: als.getStore().userId  ← returns 'user-A' from sharedBase!

// FIX: always spread to create a new object per request:
app.use((req, res, next) => {
    als.run({ ...sharedBase, requestId: randomUUID() }, () => next());
    //        ↑ new object every time via spread
});

// 3. EventEmitter context leak pattern (pre-Node.js 14.8 or with legacy emitters):
const globalEmitter = new EventEmitter();

als.run({ userId: 'user-A' }, () => {
    globalEmitter.on('data', handler);  // handler captures user-A's context
});

als.run({ userId: 'user-B' }, () => {
    globalEmitter.emit('data', something);  // triggers handler, but handler
    // runs with user-A's context! Different userId than current context.
});

// FIX: don't use global EventEmitters that are shared across requests,
// or use AsyncResource.bind() explicitly

// 4. Assertion guard in production:
// Wrap all context reads with an assertion that validates the context is correct:
function getVerifiedContext(expectedUserId: string): RequestContext {
    const ctx = als.getStore();
    if (!ctx) throw new Error('No context');
    if (ctx.userId !== expectedUserId) {
        // Log this as a critical security alert
        logger.error('CONTEXT CONTAMINATION DETECTED', {
            expected: expectedUserId,
            actual: ctx.userId,
            requestId: ctx.requestId
        });
        throw new Error('Context contamination detected');
    }
    return ctx;
}
```

## Quick Reference Table

| Concept | Key Idea | Common Mistake |
|---|---|---|
| `als.run(store, fn)` | Creates new async scope where `getStore()` returns `store` | Forgetting to call it at the start of each request |
| `als.getStore()` | Returns the current scope's store, or `undefined` | Not handling `undefined` (called outside any `run()`) |
| `als.enterWith(store)` | Mutates current scope's store in-place | Using it in middleware instead of `run()` |
| `AsyncResource.bind(fn)` | Binds a function to the current async context | Forgetting to bind callbacks for EventEmitters on older Node.js |
| `AsyncLocalStorage.snapshot()` | Captures current context for later use | Not available below Node.js 18.7 |
| Context store object | Should be a fresh object per `run()` call | Passing the same object reference to multiple `run()` calls — mutations shared |
| Worker Threads | ALS does NOT propagate to workers | Forgetting to serialize/restore context in `workerData` |
| EventEmitters | Context propagates from `.on()` call in Node.js 14.8+ | Using ALS with EventEmitters on Node.js < 14.8 without `AsyncResource.bind()` |
| Middleware order | Context middleware must be FIRST | Placing it after other middleware that creates async operations |
| Performance | ~2-10% overhead depending on Node.js version | Using multiple ALS instances instead of one composite store |

**Tip for interviews:** Five things separate strong candidates on `AsyncLocalStorage`: (1) explaining **why Node.js doesn't have thread-local storage** (there's one thread, no "current thread" per request) and why `AsyncLocalStorage` had to be invented to solve this — starting with the "why" before the "how" shows systems understanding, not just API memorization; (2) knowing that **`als.run()` with a shared object reference causes contamination** (Q17) — the most common and hardest-to-debug production bug with ALS, where mutations on the store object from Request A are visible to Request B because they share the same JS object, not just the same context; (3) knowing the **difference between `run()` and `enterWith()`** (Q5) and being able to articulate when each is appropriate — `run()` for middleware (creates a new scope), `enterWith()` almost never (mutates in place, dangerous); (4) being able to design the **cross-service context propagation pattern** (Q7) — ALS is in-process only, and distributed tracing requires explicitly forwarding context as HTTP headers or message metadata; and (5) knowing that **`cls-hooked` is unmaintained** (Q9) and being able to articulate the concrete reasons to migrate (stable stdlib, TypeScript generics, better memory management, compatibility with Node.js 18+) rather than just saying "it's newer."
