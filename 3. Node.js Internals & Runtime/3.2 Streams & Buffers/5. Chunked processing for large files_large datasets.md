# Chunked Processing for Large Files / Large Datasets — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is chunked processing, and what fundamental constraints make it necessary?**
A: Chunked processing is the technique of dividing a large dataset or file into smaller, manageable pieces ("chunks") and processing them sequentially or in parallel, rather than loading the entire dataset into memory at once. It is necessitated by three physical constraints that no software design can overcome:

- **RAM capacity**: a process has a finite address space and available physical memory. A 100GB log file cannot fit in 16GB of RAM. Even if it could, the OS would thrash (swapping pages to disk), making processing slower than disk I/O.
- **Network bandwidth and latency**: transferring a 50GB file as a single HTTP request is not practical — a dropped connection requires restarting from zero, progress cannot be reported, and the request would time out.
- **CPU cache efficiency**: processing data in chunks that fit in CPU caches (L1: 32-64KB, L2: 256KB-1MB, L3: 4-64MB) is dramatically faster than random-access over a large dataset, even if the full dataset fits in RAM, because cache misses cost 50-200 CPU cycles each.

The central design question for any large-data system is: "What is the right chunk size?" — too small increases per-chunk overhead (function call overhead, I/O seeks, memory allocation); too large approaches the constraints you're trying to avoid (OOM, slow checkpointing, poor parallelism granularity).

**Q2. What is the difference between streaming, batching, and chunked processing — and when does each term apply?**
A: These terms overlap significantly and are often used interchangeably, but have distinct emphases:

**Streaming**: a continuous flow of data processed element-by-element or in small amounts as it arrives, without buffering the full dataset. The emphasis is on low latency and unbounded data. A Kafka consumer processing events one at a time is streaming. Node.js readable streams are streaming. The data source is often infinite or very large and timing is important.

**Chunking**: dividing a finite, bounded dataset into fixed-size or variable-size segments for processing. The emphasis is on memory management and parallelism. Chunking implies you know (or can determine) the total size and divide it deliberately. Reading a 10GB file in 64MB chunks is chunked processing.

**Batching**: grouping multiple items together for processing as a unit, typically to amortize per-item overhead (database round-trips, API calls, network packets). A batch may contain 100 records at a time; batching emphasizes throughput and reducing overhead rather than memory bounds. Writing 1000 database rows in one INSERT statement instead of 1000 individual INSERTs is batching.

In practice: chunked file reading uses streaming under the hood, processes data in batches, and the chunks are the units of parallelism. A real system typically combines all three.

## Section 2: File Chunking

**Q3. What are the strategies for determining chunk boundaries in a file, and why is naive byte-offset splitting often wrong?**
A: A naive approach splits a file into N equal byte-offset chunks (file_size / N bytes each) and processes them in parallel. This is correct for purely binary data (images, video, compressed archives) but wrong for structured text data:

```python
# NAIVE (wrong for CSV/JSON lines/log records):
chunk_size = file_size // num_workers
chunk_1 = file[0 : chunk_size]
chunk_2 = file[chunk_size : 2 * chunk_size]
# PROBLEM: chunk boundaries may split in the middle of a record!
# "alice,30,engi" | "neer,100000\nbob,25,manager,80000\n"
# chunk_1's last record is broken; chunk_2's first "neer,..." is orphaned

# CORRECT strategies:

# 1. Line-aligned chunking (for line-delimited formats: CSV, NDJSON, logs):
def find_line_aligned_chunks(filepath, num_chunks):
    file_size = os.path.getsize(filepath)
    approximate_chunk_size = file_size // num_chunks
    boundaries = [0]

    with open(filepath, 'rb') as f:
        for i in range(1, num_chunks):
            f.seek(i * approximate_chunk_size)
            f.readline()  # advance past the current incomplete line
            boundaries.append(f.tell())  # record the start of the next full line
    boundaries.append(file_size)
    return list(zip(boundaries[:-1], boundaries[1:]))

# 2. Delimiter-aligned chunking (for CSV with embedded newlines in quoted fields):
#    Use a proper CSV parser that tracks quote state while seeking

# 3. Record-count-based chunking (when records have known fixed size):
#    RECORD_SIZE = 128 bytes → chunk_count = file_size // RECORD_SIZE // records_per_chunk

# 4. Index-based chunking (for formats with built-in indexes — Parquet row groups):
#    Each Parquet row group is a natural chunk boundary — read the footer metadata,
#    get row group offsets, process each row group as one chunk
```

**Q4. How does memory-mapped file I/O work for large files and when is it preferable to explicit chunked reads?**
A: Memory-mapped files (`mmap`) expose a file's contents as if they were directly in the process's virtual address space — no explicit `read()` calls needed. The OS pages in only the portions of the file that are actually accessed (demand paging), and pages can be shared between processes mapping the same file:

```python
import mmap

# Traditional read (copies data into Python heap):
with open('large_file.bin', 'rb') as f:
    f.seek(offset)
    chunk = f.read(chunk_size)  # explicit read, data copied to process memory

# Memory-mapped read (no copy — OS pages data in on demand):
with open('large_file.bin', 'rb') as f:
    mm = mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ)
    # Access like a bytearray — OS handles page-in transparently:
    value = mm[offset:offset + chunk_size]  # page fault loads the page if not cached
    # Finding a byte offset:
    pos = mm.find(b'\n', start_pos)
    mm.close()
```

**When mmap is preferable**:
- Random access patterns (seeking around a large file nonsequentially)
- Sharing large read-only datasets between multiple processes (the OS shares one physical copy)
- Files that fit in virtual address space and where OS page cache is effective
- Reading a file multiple times — the OS keeps recently-accessed pages in RAM automatically

**When explicit reads are preferable**:
- Sequential processing of the entire file (OS read-ahead for sequential reads is highly optimized and sometimes beats mmap)
- Files significantly larger than available RAM (mmap causes page thrashing; explicit reads with a small buffer keep memory bounded)
- Network-mounted filesystems (mmap semantics become complex and page faults are slow)
- When you need to control exactly how much memory is used at any time

**Q5. What is the producer-consumer pattern for chunked file processing and how does it prevent bottlenecks?**
A: The producer-consumer pattern separates I/O (disk reading) from CPU work (parsing/transforming), allowing them to overlap:

```python
import queue
import threading

def chunked_file_processor(filepath, chunk_size=64*1024*1024, num_workers=4):
    """
    Producer: reads file chunks from disk (I/O bound)
    Queue: bounded buffer preventing memory overflow
    Consumers: process chunks in parallel (CPU bound)
    """
    chunk_queue = queue.Queue(maxsize=num_workers * 2)  # bound prevents OOM
    results_queue = queue.Queue()
    SENTINEL = object()

    def producer():
        with open(filepath, 'r', buffering=1024*1024) as f:
            while True:
                lines = []
                size = 0
                while size < chunk_size:
                    line = f.readline()
                    if not line:
                        if lines:
                            chunk_queue.put(lines)
                        # Send one sentinel per worker to signal completion
                        for _ in range(num_workers):
                            chunk_queue.put(SENTINEL)
                        return
                    lines.append(line)
                    size += len(line)
                chunk_queue.put(lines)  # blocks if queue is full (backpressure!)

    def consumer(worker_id):
        while True:
            chunk = chunk_queue.get()
            if chunk is SENTINEL:
                results_queue.put(SENTINEL)
                return
            result = process_chunk(chunk)  # CPU-intensive work
            results_queue.put(result)

    # Start producer thread
    prod = threading.Thread(target=producer, daemon=True)
    prod.start()

    # Start consumer threads
    consumers = [
        threading.Thread(target=consumer, args=(i,), daemon=True)
        for i in range(num_workers)
    ]
    for c in consumers:
        c.start()

    # Collect results, stopping when all workers send SENTINEL
    results = []
    done_workers = 0
    while done_workers < num_workers:
        result = results_queue.get()
        if result is SENTINEL:
            done_workers += 1
        else:
            results.append(result)

    return aggregate_results(results)
```

The bounded queue (`maxsize=num_workers * 2`) implements backpressure — the producer blocks when the queue is full, preventing it from reading the entire file into memory while consumers are busy.

## Section 3: Database Chunked Processing

**Q6. What is cursor-based chunked processing for databases, and why is offset-based pagination the wrong approach for large datasets?**
A: Processing millions of database rows in one query is impractical (fills the DB server's memory, holds a long transaction, transfers enormous result sets). Chunked processing reads rows in pages. The naive approach — offset-based pagination — fails for large datasets:

```sql
-- NAIVE: offset-based (broken for large N)
SELECT * FROM orders ORDER BY created_at LIMIT 1000 OFFSET 500000;
-- Problem: the database must scan and discard 500,000 rows before returning 1,000
-- At page N, cost = O(N × page_size) → quadratic total cost for a full scan
-- Also: if rows are inserted/deleted between pages, pages shift → duplicates or gaps
```

Cursor-based (keyset) pagination solves both problems:

```sql
-- CORRECT: keyset / cursor-based pagination
-- First page:
SELECT id, user_id, total, created_at
FROM orders
ORDER BY created_at ASC, id ASC  -- stable, unique ordering (id breaks ties)
LIMIT 1000;

-- Subsequent pages: use the last row's values as the cursor
-- After getting rows where last row is (created_at='2024-01-15', id=98765):
SELECT id, user_id, total, created_at
FROM orders
WHERE (created_at, id) > ('2024-01-15 14:30:00', 98765)  -- row comparison (most DBs)
ORDER BY created_at ASC, id ASC
LIMIT 1000;

-- This is O(log N) per page (B-tree index seek), O(N) total for a full scan
-- Unaffected by concurrent inserts: the cursor anchors to a specific position
```

Python implementation of cursor-based chunked processing:

```python
def process_all_orders(db, batch_size=1000, process_fn=None):
    cursor = (None, None)  # (created_at, id) — None means start from beginning

    while True:
        if cursor == (None, None):
            rows = db.execute("""
                SELECT id, user_id, total, created_at
                FROM orders ORDER BY created_at ASC, id ASC
                LIMIT %s
            """, (batch_size,)).fetchall()
        else:
            rows = db.execute("""
                SELECT id, user_id, total, created_at
                FROM orders
                WHERE (created_at, id) > (%s, %s)
                ORDER BY created_at ASC, id ASC
                LIMIT %s
            """, (*cursor, batch_size)).fetchall()

        if not rows:
            break  # no more data

        if process_fn:
            process_fn(rows)  # process this batch

        # Advance cursor to last row of this batch
        last = rows[-1]
        cursor = (last['created_at'], last['id'])

        if len(rows) < batch_size:
            break  # last partial page
```

**Q7. What is the "server-side cursor" approach in PostgreSQL and how does it differ from keyset pagination?**
A: PostgreSQL named cursors maintain state on the database server between fetches — the query plan executes once and the server holds the result set position. The client fetches rows in batches:

```python
import psycopg2

def process_with_server_cursor(conn, query, batch_size=10000):
    with conn.cursor(name='large_dataset_cursor') as cursor:
        # Server executes the query once and holds the cursor position
        cursor.execute(query)

        while True:
            # Fetches next batch_size rows from the server's cursor position
            rows = cursor.fetchmany(batch_size)
            if not rows:
                break
            process_batch(rows)
        # Cursor is automatically closed when exiting the context manager

# Benefits over keyset pagination:
# - Works for complex queries with no natural ordered unique key
# - The ORDER BY and filtering are computed once (one query plan)
# - No repeated index seeks per page

# Costs:
# - Holds a database transaction open for the entire duration (lock implications)
# - Memory held on the server for the cursor state
# - The cursor is only valid within its transaction — cannot resume after disconnect
# - autocommit must be off for named cursors in psycopg2

# Usage:
conn = psycopg2.connect(dsn)
conn.autocommit = False
process_with_server_cursor(conn, """
    SELECT u.id, u.email, COUNT(o.id) as order_count
    FROM users u
    LEFT JOIN orders o ON o.user_id = u.id
    GROUP BY u.id, u.email
    ORDER BY u.id
""")
conn.commit()
```

**Q8. How do you perform chunked updates or deletes in a database without locking the entire table?**
A: Large `UPDATE` or `DELETE` statements acquire locks for their entire duration, blocking concurrent reads (in some isolation levels) and writes. Chunked updates limit lock scope to one batch at a time:

```sql
-- WRONG: one massive update locks everything
UPDATE orders SET status = 'archived'
WHERE created_at < '2020-01-01';  -- Could be millions of rows, long lock

-- CORRECT: chunked update in batches
-- Application loop:
DO $$
DECLARE
    rows_updated INTEGER;
BEGIN
    LOOP
        UPDATE orders SET status = 'archived'
        WHERE id IN (
            SELECT id FROM orders
            WHERE created_at < '2020-01-01'
              AND status != 'archived'
            LIMIT 1000  -- process at most 1000 rows per batch
            FOR UPDATE SKIP LOCKED  -- skip rows locked by other transactions
        );

        GET DIAGNOSTICS rows_updated = ROW_COUNT;
        COMMIT;  -- Release locks after each batch

        EXIT WHEN rows_updated < 1000;  -- Stop when last batch was not full
        PERFORM pg_sleep(0.01);         -- Brief pause to allow other queries
    END LOOP;
END $$;
```

Python implementation with exponential backoff:
```python
def chunked_delete(db, table, condition_sql, condition_params, batch_size=500):
    total_deleted = 0
    while True:
        result = db.execute(f"""
            DELETE FROM {table}
            WHERE id IN (
                SELECT id FROM {table}
                WHERE {condition_sql}
                LIMIT %s
            )
        """, (*condition_params, batch_size))
        deleted = result.rowcount
        db.commit()

        total_deleted += deleted
        logger.info(f'Deleted {deleted} rows ({total_deleted} total)')

        if deleted < batch_size:
            break  # last incomplete batch

        time.sleep(0.01)  # yield to other connections

    return total_deleted
```

## Section 4: Parallel Chunked Processing

**Q9. What are the architecture patterns for parallel chunked processing, and how do you choose between them?**
A: Three primary patterns, each suited to different resource constraints:

**1. Fork-join (multiprocessing, for CPU-bound on a single machine)**:
```python
from concurrent.futures import ProcessPoolExecutor, as_completed
import os

def parallel_file_process(filepath, num_workers=os.cpu_count()):
    # Step 1: divide file into byte-aligned chunks
    chunks = compute_line_aligned_chunks(filepath, num_workers)

    # Step 2: process each chunk in a separate process (bypasses Python GIL)
    results = []
    with ProcessPoolExecutor(max_workers=num_workers) as executor:
        futures = {
            executor.submit(process_chunk, filepath, start, end): (start, end)
            for start, end in chunks
        }
        for future in as_completed(futures):
            start, end = futures[future]
            try:
                result = future.result()
                results.append(result)
            except Exception as e:
                logger.error(f'Chunk {start}-{end} failed: {e}')

    return merge_results(results)

def process_chunk(filepath, start_byte, end_byte):
    # This runs in a separate OS process
    with open(filepath, 'r') as f:
        f.seek(start_byte)
        chunk_text = f.read(end_byte - start_byte)
    return compute_on_chunk(chunk_text)
```

**2. Worker pool with a task queue (for I/O-bound or heterogeneous work)**:
```python
from concurrent.futures import ThreadPoolExecutor  # threads for I/O bound
import queue

def process_s3_dataset(bucket, prefix, num_workers=20):
    file_keys = list_s3_keys(bucket, prefix)
    results = {}

    with ThreadPoolExecutor(max_workers=num_workers) as executor:
        future_to_key = {
            executor.submit(download_and_process, bucket, key): key
            for key in file_keys
        }
        for future in as_completed(future_to_key):
            key = future_to_key[future]
            try:
                results[key] = future.result()
            except Exception as e:
                logger.error(f'{key} failed: {e}', exc_info=True)

    return results
```

**3. Distributed worker fleet (for data too large for one machine)**:
```
Coordinator:
  1. Scan source (S3, GCS, database) → list of chunk descriptors
  2. Publish descriptors to a work queue (SQS, Kafka, Redis)
  3. Monitor worker health and chunk completion
  4. Handle failed chunks (re-enqueue after visibility timeout)

Workers (N machines):
  1. Pull a chunk descriptor from the queue
  2. Download/read the chunk from source
  3. Process, write output to sink (S3, DB)
  4. Acknowledge the message (SQS delete, Kafka commit)
  5. Repeat until queue empty

Exactly-once via idempotency:
  - Each chunk has a unique ID
  - Workers write results keyed by chunk ID
  - Duplicate processing produces the same output (idempotent)
  - Final aggregation deduplicates by chunk ID
```

**Q10. What are the trade-offs in chunk size selection, and how do you empirically determine the optimal size?**
A: Chunk size involves multiple opposing forces:

```
Too small:                          Too large:
- High per-chunk overhead           - Approaches memory limit
  (function calls, I/O seeks,       - Long checkpoint intervals
   queue operations)                  (failure = re-do more work)
- More queue messages               - Poor parallelism granularity
- Worse cache utilization             (worker count > chunk count)
  (chunk setup/teardown cost        - Slow progress reporting
   dominates processing time)       - Memory pressure, GC pauses

Factors that push chunk size UP:    Factors that push chunk size DOWN:
- High per-chunk overhead cost      - Limited available RAM
- Fast I/O (NVMe SSD, RAM)          - Slow/unreliable processing
- Low record complexity             - Many parallel workers
- Low failure rate                  - Need fine progress granularity

Empirical tuning process:
1. Measure per-chunk overhead: time a null-process chunk (no real work)
   → This is your fixed cost floor per chunk
2. Measure throughput at different sizes: 1MB, 10MB, 64MB, 256MB
   → Plot throughput vs chunk size → find the "knee" where gains flatten
3. Measure memory per worker at peak load
   → Ensure chunk_size × num_workers_per_machine < available_RAM × 0.7
4. Target: processing time >> overhead time (10x is a reasonable minimum)
   If processing 1MB takes 50ms and overhead is 5ms: overhead = 10% → acceptable
   If processing 1MB takes 6ms and overhead is 5ms: overhead = 45% → too small

Common reference points:
- CPU cache (L3) fit: 4-64MB → ideal for CPU-bound single-threaded work
- Disk block size: 4KB-1MB → minimum meaningful I/O unit
- S3 multipart: minimum 5MB per part (API requirement)
- Network MTU: 1500 bytes (Ethernet) → too small for bulk data chunks
```

## Section 5: Resumability and Checkpointing

**Q11. What is checkpointing in long-running chunked jobs and how do you design a resumable processing pipeline?**
A: A job processing 1TB of data that takes 6 hours must handle the reality of transient failures (network blips, OOM kills, preempted spot instances). Without checkpointing, every failure restarts from zero. With checkpointing, the job resumes from the last successfully processed chunk:

```python
import json
import hashlib
from pathlib import Path

class ResumableChunkProcessor:
    def __init__(self, job_id: str, checkpoint_path: str):
        self.job_id = job_id
        self.checkpoint_file = Path(checkpoint_path) / f"{job_id}.checkpoint.json"
        self.completed_chunks = self._load_checkpoint()

    def _load_checkpoint(self) -> set:
        """Load the set of completed chunk IDs from disk."""
        if self.checkpoint_file.exists():
            with open(self.checkpoint_file) as f:
                data = json.load(f)
            logger.info(f"Resuming job {self.job_id}: "
                       f"{len(data['completed'])} chunks already done")
            return set(data['completed'])
        return set()

    def _save_checkpoint(self):
        """Atomically write checkpoint to disk."""
        temp_path = self.checkpoint_file.with_suffix('.tmp')
        with open(temp_path, 'w') as f:
            json.dump({'job_id': self.job_id,
                       'completed': list(self.completed_chunks)}, f)
        temp_path.replace(self.checkpoint_file)  # atomic rename

    def chunk_id(self, chunk_descriptor) -> str:
        """Deterministic, content-based chunk ID."""
        return hashlib.sha256(
            json.dumps(chunk_descriptor, sort_keys=True).encode()
        ).hexdigest()[:16]

    def process_all(self, chunks, process_fn, checkpoint_every=100):
        """Process chunks, skipping already-completed ones."""
        skipped = 0
        processed = 0

        for i, chunk in enumerate(chunks):
            cid = self.chunk_id(chunk)

            if cid in self.completed_chunks:
                skipped += 1
                continue

            try:
                process_fn(chunk)
                self.completed_chunks.add(cid)
                processed += 1

                # Save checkpoint periodically (not every chunk — too slow)
                if processed % checkpoint_every == 0:
                    self._save_checkpoint()
                    logger.info(f"Checkpoint: {processed} new, {skipped} skipped")

            except Exception as e:
                self._save_checkpoint()  # Save before failing
                logger.error(f"Chunk {cid} failed: {e}")
                raise

        self._save_checkpoint()  # Final checkpoint
        logger.info(f"Complete: {processed} processed, {skipped} skipped")

# Usage:
processor = ResumableChunkProcessor('etl-job-2024-01-15', '/tmp/checkpoints')
chunks = compute_all_chunks(source_path)
processor.process_all(chunks, write_to_warehouse)
# If the job is killed and restarted, it resumes from the checkpoint
```

**Q12. What is idempotent processing and why is it essential for resumable chunked jobs?**
A: Idempotent processing means that processing the same chunk twice produces the same result as processing it once — re-processing doesn't create duplicates or corrupt state. This is non-negotiable for chunked jobs with checkpointing (the last checkpoint interval may be re-processed on restart) or distributed systems (network failures can cause re-delivery):

```python
# NON-IDEMPOTENT: double-processing causes duplicates
def process_chunk_bad(rows):
    for row in rows:
        db.execute("INSERT INTO aggregates (user_id, total) VALUES (%s, %s)",
                   (row.user_id, row.amount))  # duplicate insert if chunk re-processed!

# IDEMPOTENT: same chunk produces same output regardless of how many times it runs
def process_chunk_good(rows, chunk_id):
    # Pattern 1: INSERT ... ON CONFLICT DO NOTHING (upsert)
    db.execute_many("""
        INSERT INTO aggregates (chunk_id, user_id, total)
        VALUES (%s, %s, %s)
        ON CONFLICT (chunk_id, user_id) DO NOTHING
    """, [(chunk_id, r.user_id, r.amount) for r in rows])

    # Pattern 2: Write to a keyed output (last write wins, idempotent by key)
    for row in rows:
        s3.put_object(
            Bucket='results',
            Key=f'chunk-{chunk_id}/user-{row.user_id}.json',
            Body=json.dumps({'total': row.amount})
        )  # Writing the same key twice: second write replaces the first — idempotent

    # Pattern 3: Track chunk ID in a processed-chunks table
    db.execute("""
        INSERT INTO processed_chunks (chunk_id, processed_at)
        VALUES (%s, NOW())
        ON CONFLICT (chunk_id) DO NOTHING
    """, (chunk_id,))

    # Pattern 4: Use chunk_id as a deduplication window key (SQS FIFO / Kafka transactional)
    # MessageDeduplicationId=chunk_id prevents duplicate processing at the broker level

# Testing idempotency:
def test_idempotency(chunk, process_fn):
    result_1 = process_fn(chunk)
    result_2 = process_fn(chunk)  # process same chunk again
    assert result_1 == result_2, "Processing is not idempotent!"
```

## Section 6: Chunked Uploads and Downloads

**Q13. What is multipart upload and how does it solve large file upload reliability?**
A: Cloud object storage (S3, GCS, Azure Blob) supports multipart upload: dividing a large file into parts (minimum 5MB each for S3), uploading each independently (in parallel, with individual retries), then completing with a "combine" API call. Only failed parts need to be re-uploaded:

```python
import boto3
from concurrent.futures import ThreadPoolExecutor, as_completed
import os

def multipart_upload_s3(filepath, bucket, key, part_size=64*1024*1024, num_workers=8):
    """Upload a large file to S3 using multipart upload with parallel part uploads."""
    s3 = boto3.client('s3')
    file_size = os.path.getsize(filepath)

    # Step 1: Initiate multipart upload
    mpu = s3.create_multipart_upload(Bucket=bucket, Key=key)
    upload_id = mpu['UploadId']

    try:
        # Step 2: Divide into parts
        parts_config = []
        offset = 0
        part_number = 1
        while offset < file_size:
            size = min(part_size, file_size - offset)
            parts_config.append((part_number, offset, size))
            offset += size
            part_number += 1

        # Step 3: Upload all parts in parallel
        completed_parts = []
        def upload_part(part_num, offset, size):
            with open(filepath, 'rb') as f:
                f.seek(offset)
                data = f.read(size)
            response = s3.upload_part(
                Bucket=bucket, Key=key, UploadId=upload_id,
                PartNumber=part_num, Body=data
            )
            return {'PartNumber': part_num, 'ETag': response['ETag']}

        with ThreadPoolExecutor(max_workers=num_workers) as executor:
            futures = {
                executor.submit(upload_part, pn, off, sz): pn
                for pn, off, sz in parts_config
            }
            for future in as_completed(futures):
                completed_parts.append(future.result())

        # Step 4: Complete multipart upload (S3 assembles the parts server-side)
        completed_parts.sort(key=lambda p: p['PartNumber'])
        s3.complete_multipart_upload(
            Bucket=bucket, Key=key, UploadId=upload_id,
            MultipartUpload={'Parts': completed_parts}
        )
        logger.info(f"Uploaded {file_size / (1024**3):.2f}GB in {len(parts_config)} parts")

    except Exception as e:
        # Abort the upload to free S3 storage for incomplete parts
        s3.abort_multipart_upload(Bucket=bucket, Key=key, UploadId=upload_id)
        raise

# Resumable upload: save upload_id and ETag per completed part to disk
# On restart: create_multipart_upload → list_parts to see what succeeded → upload remaining
```

**Q14. How do HTTP Range requests enable chunked downloads and resumable file transfers?**
A: HTTP Range requests (`Range: bytes=start-end`) allow clients to download specific byte ranges of a file, enabling: resumable downloads (resume from where the connection dropped), parallel downloading (multiple threads each downloading a different range), and progressive loading:

```python
import requests
import threading
from pathlib import Path

def parallel_download(url, dest_path, num_chunks=8, chunk_size=None):
    """Download a file in parallel using HTTP Range requests."""
    # Step 1: Discover file size
    head = requests.head(url)
    total_size = int(head.headers['Content-Length'])
    accepts_ranges = head.headers.get('Accept-Ranges', 'none') == 'bytes'

    if not accepts_ranges:
        # Server doesn't support Range — fall back to single download
        return simple_download(url, dest_path)

    # Step 2: Divide into ranges
    if chunk_size is None:
        chunk_size = total_size // num_chunks

    ranges = []
    start = 0
    while start < total_size:
        end = min(start + chunk_size - 1, total_size - 1)
        ranges.append((start, end))
        start = end + 1

    # Step 3: Pre-allocate the output file
    dest = Path(dest_path)
    dest.write_bytes(b'\0' * total_size)  # Sparse file or explicit pre-allocation

    # Step 4: Download each range in a separate thread
    errors = []
    def download_range(range_start, range_end):
        response = requests.get(
            url,
            headers={'Range': f'bytes={range_start}-{range_end}'},
            stream=True
        )
        response.raise_for_status()
        with open(dest_path, 'r+b') as f:
            f.seek(range_start)
            for chunk in response.iter_content(chunk_size=1024*1024):
                f.write(chunk)

    threads = [
        threading.Thread(target=download_range, args=(s, e), daemon=True)
        for s, e in ranges
    ]
    for t in threads:
        t.start()
    for t in threads:
        t.join()

    return dest_path

# Resume logic: track which ranges completed (write to .download-state file)
# On restart: re-issue Range requests only for incomplete ranges
```

## Section 7: Memory Management

**Q15. What are the memory management principles for chunked processing, and what are the common failure modes?**
A: Memory management in chunked processing requires understanding the lifecycle of objects across chunks:

```python
# FAILURE MODE 1: Accumulating results without bounded memory
```

## Section 8: Chunked Processing Patterns

**Q16. What is the sliding window pattern for chunked processing and when is it necessary?**
A: Some computations require context from adjacent chunks — a record at the end of chunk N needs records from the beginning of chunk N+1 to be correctly processed. The sliding window pattern maintains overlap between consecutive chunks:

```python
# Example: detecting duplicate records that span chunk boundaries
# Without overlap: a record at the end of chunk 1 and start of chunk 2 might be "same record"
# but both chunks process it independently as "new"

def process_with_overlap(filepath, chunk_size=10000, overlap=100):
    """
    Process a file where records can span the boundary between chunks.
    Each chunk includes `overlap` records from the end of the previous chunk.
    """
    prev_tail = []  # last `overlap` records from previous chunk

    for chunk in read_chunks(filepath, chunk_size):
        # Prepend the tail of the previous chunk as context
        full_window = prev_tail + chunk

        # Process with awareness of the overlap
        # Records in the overlap region: only count them once (from the previous chunk)
        results_for_this_chunk = process_with_boundary_awareness(
            full_window,
            overlap_count=len(prev_tail)
        )
        yield results_for_this_chunk

        # Keep the last `overlap` records for the next iteration
        prev_tail = chunk[-overlap:]

# Practical use cases for sliding windows:
# - N-gram generation (a 3-gram at the end of chunk needs 2 words from the next chunk)
# - Running average/sum (compute a 7-day rolling average: each chunk needs 6 extra days)
# - Deduplication (dedup window spans chunks: "have I seen this record in the last N records?")
# - Session boundary detection (user session may span the chunk boundary)

# For session detection specifically:
def detect_sessions_chunked(events, session_timeout=30*60):
    """Events must be sorted by user_id, then timestamp."""
    prev_event = None  # carry state across chunk boundary

    for chunk in read_event_chunks(events):
        for event in chunk:
            if prev_event and \
               event.user_id == prev_event.user_id and \
               (event.timestamp - prev_event.timestamp) < session_timeout:
                # Same session — extend it
                current_session.add(event)
            else:
                # New session — yield the completed previous one
                if prev_event:
                    yield current_session
                current_session = Session(event)
            prev_event = event

    if current_session:
        yield current_session  # Don't forget the last session
```

**Q17. What is the map-reduce pattern for chunked processing and how does it decompose a large-data computation?**
A: Map-reduce is a two-phase chunked processing pattern: the "map" phase independently processes each chunk (embarrassingly parallel), and the "reduce" phase combines the per-chunk results into a final answer:

```python
from collections import defaultdict
from functools import reduce

# Example: word frequency count across a 100GB text corpus

# MAP phase (runs in parallel, one per chunk):
def map_word_count(chunk_lines):
    """Returns a dict of {word: count} for this chunk."""
    counts = defaultdict(int)
    for line in chunk_lines:
        for word in line.lower().split():
            word = word.strip('.,!?";')
            if word:
                counts[word] += 1
    return dict(counts)

# REDUCE phase (merges results from all chunks):
def reduce_word_counts(count_a, count_b):
    """Merges two word-count dicts by summing counts."""
    merged = defaultdict(int, count_a)
    for word, count in count_b.items():
        merged[word] += count
    return dict(merged)

# Complete map-reduce pipeline:
def word_count_map_reduce(filepath, num_workers=8):
    chunks = compute_line_aligned_chunks(filepath, num_chunks=num_workers * 4)

    # Map phase: process all chunks in parallel
    with ProcessPoolExecutor(max_workers=num_workers) as executor:
        futures = [
            executor.submit(process_file_chunk, filepath, start, end, map_word_count)
            for start, end in chunks
        ]
        partial_results = [f.result() for f in futures]

    # Reduce phase: merge all partial results into final count
    final_count = reduce(reduce_word_counts, partial_results, {})
    return dict(sorted(final_count.items(), key=lambda x: -x[1])[:100])  # top 100

# Properties that make map-reduce correct:
# - Map functions are STATELESS: each chunk processes independently, no shared state
# - Reduce function is ASSOCIATIVE: reduce(reduce(a, b), c) == reduce(a, reduce(b, c))
# - Reduce function is COMMUTATIVE: reduce(a, b) == reduce(b, a)
# These properties enable arbitrary reordering and tree-reduction in distributed systems
```

## Section 9: Scenario-Based Questions

**Q18. "You need to process a 500GB CSV file containing 2 billion e-commerce transactions to compute total revenue per product. You have a single machine with 32GB RAM and 16 CPU cores. Design the solution."**
A: This is a classic embarrassingly-parallel map-reduce over a large file:

**Step 1 — Pre-analysis**:
- File is 500GB, RAM is 32GB → cannot load entirely. Chunks of ~1GB fit comfortably in RAM with workers.
- 16 cores → 14 worker processes (leave 2 for OS + coordination).
- Target chunk size: 1GB (fits in L3 cache of modern server CPUs, 500 chunks total).

**Step 2 — Chunk plan**:
```python
# Divide file into 500 × 1GB line-aligned chunks
chunks = compute_line_aligned_chunks('transactions.csv', num_chunks=500)
# Each chunk: ~1GB, ~4M rows at ~250 bytes/row
```

**Step 3 — Map function (runs in each worker process)**:
```python
def map_revenue(filepath, start_byte, end_byte):
    """Returns {product_id: total_revenue} for this chunk."""
    revenue = defaultdict(float)
    with open(filepath, 'rb') as f:
        f.seek(start_byte)
        # Read to end_byte, parse CSV
        chunk_text = f.read(end_byte - start_byte).decode('utf-8')
    reader = csv.DictReader(io.StringIO(chunk_text),
                            fieldnames=['order_id','product_id','quantity','unit_price'])
    for row in reader:
        revenue[row['product_id']] += float(row['quantity']) * float(row['unit_price'])
    return dict(revenue)
```

**Step 4 — Parallel execution with bounded concurrency**:
```python
from concurrent.futures import ProcessPoolExecutor, as_completed

revenue_totals = defaultdict(float)
checkpoint = ResumableCheckpoint('revenue-job')  # resumability

with ProcessPoolExecutor(max_workers=14) as executor:
    pending = {}
    chunk_iter = iter(chunks)

    # Submit initial batch of 28 tasks (2× num_workers for utilization)
    for chunk in itertools.islice(chunk_iter, 28):
        if not checkpoint.is_done(chunk):
            f = executor.submit(map_revenue, 'transactions.csv', *chunk)
            pending[f] = chunk

    # As each finishes, submit the next chunk
    for future in as_completed(pending):
        chunk = pending.pop(future)
        try:
            partial = future.result()
            for product_id, rev in partial.items():
                revenue_totals[product_id] += rev  # reduce phase (in main process)
            checkpoint.mark_done(chunk)
        except Exception as e:
            logger.error(f'Chunk {chunk} failed: {e}')

        # Submit next chunk
        next_chunk = next(chunk_iter, None)
        if next_chunk and not checkpoint.is_done(next_chunk):
            f = executor.submit(map_revenue, 'transactions.csv', *next_chunk)
            pending[f] = next_chunk
```

**Step 5 — Output**:
```python
# Write sorted results
sorted_revenue = sorted(revenue_totals.items(), key=lambda x: -x[1])
with open('revenue_by_product.csv', 'w') as f:
    writer = csv.writer(f)
    writer.writerow(['product_id', 'total_revenue'])
    writer.writerows(sorted_revenue)
```

**Performance estimate**: 500GB / (1GB/s sequential disk read × 14 workers) ≈ 36 seconds of I/O; CPU processing of CSV parsing at ~500MB/s per core × 14 cores = ~70 seconds. Total: ~2-5 minutes depending on disk throughput.

**Q19. "Your company needs to migrate 50 million user records from a legacy database to a new schema with backfill of computed fields. The migration must run with zero downtime and take no more than 24 hours. Design the chunked migration."**
A: A zero-downtime migration requires running the old and new systems simultaneously during the migration window:

**Phase 1 — Dual-write (start before migration)**:

```python
def save_user(user):
```

**Phase 2 — Bulk backfill (the chunked migration)**:

```python
        if not rows:

        migrated = [transform_user(row) for row in rows]

# Divide user ID space into chunks
```

## Quick Reference Table

| Pattern | Best for | Key implementation detail |
|---|---|---|
| Line-aligned file chunking | CSV, NDJSON, log files | Seek to N bytes, advance past incomplete line |
| Fixed-size binary chunking | Images, video, compressed files | Exact byte offsets — no boundary alignment needed |
| Keyset (cursor) pagination | Database table scans | Use `(col, id) > (last_col_val, last_id)` — O(log N) per page |
| Server-side DB cursor | Complex queries, no natural key | Named cursor, `fetchmany()`, holds transaction open |
| Chunked DB update/delete | Large data modifications | Batch + `COMMIT` + brief sleep — avoid long locks |
| S3 multipart upload | Files > 100MB | Minimum 5MB parts; abort on failure to free storage |
| HTTP Range requests | Resumable downloads | `Range: bytes=start-end`; check `Accept-Ranges: bytes` |
| Map-reduce | Aggregation over large files | Map must be stateless; reduce must be associative + commutative |
| Sliding window | Boundary-crossing records | Overlap N records between consecutive chunks |
| Producer-consumer | I/O + CPU pipeline | Bounded queue provides backpressure; daemon threads |
| Resumable with checkpoint | Long-running jobs | Atomic checkpoint write; idempotent chunk processing |

**Tip for interviews:** Five things separate strong candidates on chunked processing: (1) immediately flagging **why naive byte-offset splitting is wrong for text formats** (Q3) — splitting in the middle of a CSV record produces garbage, and knowing how to find line-aligned boundaries shows you've actually done this; (2) knowing that **offset-based database pagination is O(N²) total cost** (Q6) — at page 1000 with 1000 rows/page, the database scans and discards 1 million rows before returning results — and being able to implement keyset pagination as the O(N) alternative; (3) designing for **idempotency before writing a line of code** (Q12) — because checkpoints and retries mean every chunk may run more than once, and non-idempotent processing produces duplicates that are silent and hard to detect; (4) knowing that a **bounded queue implements backpressure** (Q5) in the producer-consumer pattern — an unbounded queue lets the producer read the entire file into memory while consumers lag, defeating the purpose of chunking; and (5) being able to articulate the **map-reduce correctness requirements** (Q17) — map functions must be stateless, reduce must be associative and commutative — these constraints are what enable arbitrary parallelism and reordering, and knowing the "why" behind the pattern shows systems design depth beyond knowing the pattern name.
