# Node.js Streams: `pipe()` and `pipeline()` — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do `pipe()` and `pipeline()` solve — why not just read data and write it manually?**

A: Both are mechanisms for connecting a Readable stream to a Writable stream so data flows automatically from one to the other. The alternative — manually listening to `'data'` events and calling `write()` — forces you to handle several hard problems yourself:

```javascript
// Manual approach — everything you have to handle yourself:
const readable = fs.createReadStream('input.mp4');
const writable = fs.createWriteStream('output.mp4');

readable.on('data', (chunk) => {
    const ok = writable.write(chunk);

    // Problem 1: Backpressure — writable buffer may be full
    if (!ok) {
        readable.pause(); // Stop producer
        writable.once('drain', () => readable.resume()); // Resume when drained
    }
});

readable.on('end', () => {
    writable.end(); // Don't forget to signal end-of-stream
});

// Problem 2: Error handling — must attach listeners to EVERY stream
readable.on('error', (err) => {
    writable.destroy(err); // Must also clean up the writable
    // What if there are 3 more streams in the chain?
});
writable.on('error', (err) => {
    readable.destroy(err); // And the readable
});

// Problem 3: Cleanup — destroyed streams may not close file descriptors
// Problem 4: With 4 streams in a chain, error wiring is N² complexity
```

`pipe()` automates backpressure and data flow. `pipeline()` adds correct error propagation and cleanup on top. As chains grow longer, the gap between manual wiring and `pipeline()` grows dramatically.

---

**Q2. What is `pipe()` and what does it actually do under the hood?**

A: `readable.pipe(writable)` is a method on `Readable` streams (inherited from the `Stream` class) that wires data flow and backpressure between two streams automatically. It returns the destination stream, enabling chaining.

```javascript
import fs from 'fs';
import zlib from 'zlib';

// Basic pipe: reads file, compresses, writes output
fs.createReadStream('data.csv')
    .pipe(zlib.createGzip())      // Transform stream (readable + writable)
    .pipe(fs.createWriteStream('data.csv.gz'));

// pipe() returns the destination — that's what enables chaining:
// readStream.pipe(transform) returns transform (a Readable)
// transform.pipe(writeStream) returns writeStream
```

What `pipe()` wires up internally:

```javascript
// Simplified mental model of what pipe() does:
Readable.prototype.pipe = function(dest) {
    const src = this;

    // 1. Forward data chunks as they arrive
    src.on('data', (chunk) => {
        // 2. Backpressure: if dest buffer is full, pause src
        const ok = dest.write(chunk);
        if (!ok) {
            src.pause();
            dest.once('drain', () => src.resume()); // Resume when dest drains
        }
    });

    // 3. Signal end of stream to dest when src is exhausted
    src.on('end', () => {
        dest.end();
    });

    // 4. Return dest to allow chaining
    return dest;
};
```

What `pipe()` does NOT do — the critical gaps:
- Does **not** destroy the source stream if the destination errors
- Does **not** destroy the destination if the source errors
- Does **not** propagate errors up the chain
- Does **not** clean up intermediate streams in a multi-pipe chain

## Section 2: The Error Handling Problem with `pipe()`

**Q3. What is the error handling gap in `pipe()` — show the exact failure mode?**

A: The canonical `pipe()` bug: an error in any stream in the chain leaves all other streams open and leaking resources. The error does not propagate — it's emitted on the stream that failed and goes nowhere unless you've manually attached a listener to every stream.

```javascript
import fs from 'fs';
import zlib from 'zlib';

// This looks correct — but has a critical bug:
fs.createReadStream('input.txt')
    .pipe(zlib.createGzip())
    .pipe(fs.createWriteStream('/invalid/path/output.txt.gz')); // Will error

// What actually happens when the WriteStream errors:
// 1. WriteStream emits 'error' — no listener attached → Node.js throws UnhandledPromiseRejection
//    or crashes (depending on Node.js version and mode)
// 2. The ReadStream is NOT destroyed — file descriptor stays open
// 3. The Gzip transform is NOT destroyed — stays in memory
// 4. If there were 3 more transforms, all of them stay open too
```

Demonstrating the leak explicitly:

```javascript
import fs from 'fs';
import zlib from 'zlib';

const read = fs.createReadStream('large-file.txt');
const gzip = zlib.createGzip();
const write = fs.createWriteStream('/nonexistent/path/out.gz');

read.pipe(gzip).pipe(write);

write.on('error', (err) => {
    console.error('Write error:', err.message);
    // You manually caught the error — but:
    console.log('read destroyed?', read.destroyed);  // false — LEAKING
    console.log('gzip destroyed?', gzip.destroyed);  // false — LEAKING

    // You must manually clean them up:
    read.destroy();
    gzip.destroy();
    // In a real chain with 5 transforms, you have to know about all of them
    // and destroy each one explicitly
});

// And you STILL need separate error listeners on read and gzip:
read.on('error', (err) => {
    console.error('Read error:', err.message);
    gzip.destroy();
    write.destroy();
});

gzip.on('error', (err) => {
    console.error('Gzip error:', err.message);
    read.destroy();
    write.destroy();
});
// N streams → N*(N-1) destroy calls to think about
```

The unhandled error crash:

```javascript
// If you don't attach error listeners and a stream errors:
fs.createReadStream('file.txt')
    .pipe(fs.createWriteStream('/bad/path'));

// Node.js process crashes with:
// events.js:292
//     throw er; // Unhandled 'error' event
//     ^
// Error: ENOENT: no such file or directory, open '/bad/path'
//
// Because 'error' on an EventEmitter with no listener throws by default
```

**Q4. What exactly does `pipe()` do with the `end` event — and when is that a problem?**

A: By default, `pipe()` calls `dest.end()` when the source emits `'end'`. This is usually correct, but becomes a problem when one destination is shared across multiple sources:

```javascript
import fs from 'fs';
import { PassThrough } from 'stream';

const output = fs.createWriteStream('combined.txt');

const source1 = fs.createReadStream('file1.txt');
const source2 = fs.createReadStream('file2.txt');

source1.pipe(output); // When source1 ends → output.end() called → output closed
source2.pipe(output); // source2 tries to write to an already-closed stream → Error

// Fix: pass { end: false } to suppress automatic end:
source1.pipe(output, { end: false });
source2.pipe(output, { end: false });

// Manually end the output when both sources are done:
let completed = 0;
function onSourceEnd() {
    completed++;
    if (completed === 2) output.end();
}
source1.on('end', onSourceEnd);
source2.on('end', onSourceEnd);
```

This is a sharp edge that `pipeline()` sidesteps by design — it handles one chain at a time and manages the `end` signal correctly within that chain.

## Section 3: `pipeline()` — The Correct Solution

**Q5. What does `pipeline()` provide that `pipe()` doesn't?**

A: `stream.pipeline()` (added in Node.js 10, promisified in Node.js 15 via `stream/promises`) solves all three gaps in `pipe()`:

```javascript
import { pipeline } from 'stream/promises'; // Node.js 15+
import fs from 'fs';
import zlib from 'zlib';

// Correct: pipeline handles errors and cleanup automatically
async function compressFile(input: string, output: string): Promise<void> {
    await pipeline(
        fs.createReadStream(input),
        zlib.createGzip(),
        fs.createWriteStream(output)
    );
    // If ANY stream in the chain errors:
    // 1. The error propagates to the returned Promise (rejection)
    // 2. ALL streams in the chain are destroyed automatically
    // 3. No file descriptor leaks, no dangling transforms in memory
}

try {
    await compressFile('data.csv', 'data.csv.gz');
    console.log('Compression complete');
} catch (err) {
    // One catch block handles errors from ANY stream in the chain
    console.error('Pipeline failed:', err.message);
    // All streams already cleaned up — no manual destroy needed
}
```

The three guarantees `pipeline()` provides:

```
pipe()          →   Data flow + backpressure only
pipeline()      →   Data flow + backpressure + error propagation + cleanup
```

Specifically:
1. **Error propagation**: if any stream emits `'error'`, the error is forwarded to the callback/Promise
2. **Automatic cleanup**: on error (or successful completion), `destroy()` is called on every stream in the chain
3. **Single error surface**: one `catch` block (or callback) handles all streams — no per-stream `'error'` listeners needed

**Q6. What are the two signatures of `pipeline()` — callback and Promise — and when should you use each?**

A: `pipeline()` exists in two forms:

```javascript
// Form 1: Callback-based — stream module (all Node.js versions ≥ 10)
import { pipeline } from 'stream';

pipeline(
    fs.createReadStream('input.txt'),
    zlib.createGzip(),
    fs.createWriteStream('output.txt.gz'),
    (err) => {
        if (err) {
            console.error('Pipeline failed:', err);
        } else {
            console.log('Pipeline complete');
        }
        // All streams already destroyed regardless of error/success
    }
);

// Form 2: Promise-based — stream/promises (Node.js 15+, preferred)
import { pipeline } from 'stream/promises';

async function run() {
    try {
        await pipeline(
            fs.createReadStream('input.txt'),
            zlib.createGzip(),
            fs.createWriteStream('output.txt.gz')
        );
    } catch (err) {
        // Handles errors from all streams
    }
}
```

Use the callback form only when:
- You must support Node.js < 15
- You're in a non-async context and converting would ripple widely

Use the Promise form always otherwise — it composes naturally with `async/await`, `Promise.all`, and `try/catch` error handling, and avoids callback-nesting in chains with conditional transforms.

```typescript
// Real-world: conditional transforms with Promise form
async function processUpload(
    inputStream: Readable,
    outputPath: string,
    options: { compress: boolean; encrypt: boolean }
): Promise<void> {
    const transforms: (Readable | Transform | Writable)[] = [inputStream];

    if (options.compress) {
        transforms.push(zlib.createGzip());
    }
    if (options.encrypt) {
        transforms.push(createCipheriv('aes-256-gcm', key, iv));
    }

    transforms.push(fs.createWriteStream(outputPath));

    // pipeline() accepts a spread of streams — works with dynamic chains
    await pipeline(...transforms as Parameters<typeof pipeline>);
}
```

**Q7. How does `pipeline()` handle stream destruction internally — what does "cleanup" actually mean?**

A: When `pipeline()` encounters an error (or the chain completes), it calls `stream.destroy(err)` on every stream it was given. `destroy()` does several things:

```javascript
// What destroy() does on a stream:
stream.destroy(err);
// 1. Marks the stream as destroyed (stream.destroyed === true)
// 2. Aborts any pending I/O associated with the stream
// 3. Closes the underlying resource (file descriptor, socket, etc.)
// 4. Emits 'error' (if err provided) then 'close'
// 5. Prevents any further data events from firing
```

The cleanup sequence when a middle-of-chain stream errors:

```
ReadStream → Transform1 → Transform2 → WriteStream
                               ↑ error here

pipeline() receives the error, then:
1. Calls WriteStream.destroy(err)   → file descriptor closed
2. Calls Transform2.destroy(err)    → buffer released, no more processing
3. Calls Transform1.destroy(err)    → buffer released
4. Calls ReadStream.destroy(err)    → file descriptor closed
5. Rejects the returned Promise with err (or calls callback with err)
```

Contrast with `pipe()` after the same error:

```
ReadStream → Transform1 → Transform2 → WriteStream
                               ↑ error here

pipe(): error emitted on Transform2, goes nowhere unless listener attached
ReadStream:  still open  (destroyed: false)
Transform1:  still in memory (destroyed: false)
WriteStream: errored but not destroyed (destroyed: false, fd may still be open)
```

You can observe this:

```typescript
import { pipeline } from 'stream/promises';
import { Readable, Transform } from 'stream';

const source = new Readable({ read() {} });
const failingTransform = new Transform({
    transform(chunk, _, callback) {
        callback(new Error('Transform exploded'));
    }
});
const sink = new Transform({ transform(c, _, cb) { cb(null, c); } });

try {
    source.push('data');
    source.push(null);
    await pipeline(source, failingTransform, sink);
} catch (err) {
    console.log(err.message);              // 'Transform exploded'
    console.log(source.destroyed);         // true  — pipeline cleaned up
    console.log(failingTransform.destroyed); // true
    console.log(sink.destroyed);           // true
}
```

## Section 4: AbortSignal and Cancellation

**Q8. How do you cancel a `pipeline()` mid-flight using `AbortSignal`?**

A: The Promise form of `pipeline()` accepts an options object with an `signal` property. When the signal is aborted, all streams in the pipeline are destroyed and the Promise rejects with an `AbortError`:

```typescript
import { pipeline } from 'stream/promises';
import fs from 'fs';
import zlib from 'zlib';

async function compressWithTimeout(
    input: string,
    output: string,
    timeoutMs: number
): Promise<void> {
    const controller = new AbortController();
    const timeout = setTimeout(() => controller.abort(), timeoutMs);

    try {
        await pipeline(
            fs.createReadStream(input),
            zlib.createGzip(),
            fs.createWriteStream(output),
            { signal: controller.signal } // Pass signal as last argument
        );
    } catch (err) {
        if ((err as NodeJS.ErrnoException).name === 'AbortError') {
            console.warn(`Compression of ${input} cancelled after ${timeoutMs}ms`);
        }
        throw err; // All streams already destroyed
    } finally {
        clearTimeout(timeout);
    }
}

// HTTP request cancellation — abort pipeline when client disconnects:
app.get('/download', async (req, res) => {
    const controller = new AbortController();

    req.on('close', () => {
        // Client disconnected — stop reading from disk
        controller.abort();
    });

    try {
        await pipeline(
            fs.createReadStream('large-file.bin'),
            zlib.createGzip(),
            res,
            { signal: controller.signal }
        );
    } catch (err) {
        if ((err as any).name !== 'AbortError') {
            console.error('Download error:', err);
        }
        // AbortError is expected when client disconnects — no logging needed
    }
});
```

This pattern is important in production: without abort handling, a client that disconnects mid-download leaves a `ReadStream` reading from disk and a `Gzip` transform compressing data — all writing into a closed socket — until the file is fully read. With `AbortSignal`, the pipeline tears down immediately.

## Section 5: Custom Streams and `pipeline()`

**Q9. How do you write a custom Transform stream that works correctly with `pipeline()`?**

A: Transform streams are the middle pieces in a pipeline — they consume data from the readable side, process it, and emit transformed data on the writable side. Implementing them correctly means handling the `_transform` and `_flush` callbacks properly:

```typescript
import { Transform, TransformCallback, TransformOptions } from 'stream';

// Custom Transform: parse newline-delimited JSON (NDJSON)
class NDJSONParser extends Transform {
    private buffer = '';

    constructor(options?: TransformOptions) {
        super({ ...options, objectMode: true }); // Output is objects, not Buffers
    }

    _transform(chunk: Buffer | string, _encoding: string, callback: TransformCallback): void {
        this.buffer += chunk.toString();
        const lines = this.buffer.split('\n');

        // Keep the last (potentially incomplete) line in the buffer
        this.buffer = lines.pop() ?? '';

        for (const line of lines) {
            if (line.trim() === '') continue;
            try {
                this.push(JSON.parse(line)); // Emit parsed object downstream
            } catch (err) {
                // Pass error to callback — pipeline() will catch and propagate it
                return callback(err as Error);
            }
        }

        callback(); // Signal: ready for next chunk (backpressure)
    }

    _flush(callback: TransformCallback): void {
        // Called when the upstream is done — handle any remaining buffered data
        if (this.buffer.trim()) {
            try {
                this.push(JSON.parse(this.buffer));
            } catch (err) {
                return callback(err as Error);
            }
        }
        callback(); // Signal: transform is fully done
    }
}

// Usage in a pipeline:
await pipeline(
    fs.createReadStream('events.ndjson'),
    new NDJSONParser(),
    new Transform({
        objectMode: true,
        transform(obj, _, callback) {
            // Filter and re-serialize
            if (obj.type === 'purchase') {
                callback(null, JSON.stringify(obj) + '\n');
            } else {
                callback(); // Skip — push nothing, call callback
            }
        }
    }),
    fs.createWriteStream('purchases.ndjson')
);
```

Key contract rules for custom transforms that work with `pipeline()`:
- Always call `callback()` exactly once per `_transform` call — not calling it stalls the pipeline (backpressure never releases); calling it twice corrupts the stream
- Call `callback(err)` to signal an error — `pipeline()` catches it and tears down the chain
- Call `this.push(data)` to emit data downstream — can be called multiple times before calling `callback()`
- Implement `_flush` for any data buffered across chunks (CSV headers, JSON fragments, etc.)

**Q10. How do you use `pipeline()` with async generators — and why is this pattern powerful?**

A: Node.js streams support async generators as pipeline stages, introduced in Node.js 12. This lets you write stream transformation logic as plain async functions without the Transform class boilerplate:

```typescript
import { pipeline } from 'stream/promises';
import fs from 'fs';
import readline from 'readline';

// Async generator as a pipeline stage:
async function* parseCSV(source: AsyncIterable<string>) {
    let isHeader = true;
    let headers: string[] = [];

    for await (const line of source) {
        if (isHeader) {
            headers = line.split(',').map(h => h.trim());
            isHeader = false;
            continue;
        }
        const values = line.split(',');
        // Yield objects — no class, no _transform, no callback
        yield Object.fromEntries(headers.map((h, i) => [h, values[i]?.trim()]));
    }
}

async function* filterActive(source: AsyncIterable<Record<string, string>>) {
    for await (const row of source) {
        if (row.status === 'active') {
            yield row; // Only pass through active rows
        }
        // Inactive rows are simply not yielded — they're dropped
    }
}

async function* toNDJSON(source: AsyncIterable<Record<string, string>>) {
    for await (const obj of source) {
        yield JSON.stringify(obj) + '\n';
    }
}

// Compose the generators into a pipeline:
await pipeline(
    fs.createReadStream('users.csv', { encoding: 'utf8' }),
    async function* (source) {
        // Split into lines before passing to parseCSV
        const rl = readline.createInterface({ input: source as any });
        yield* rl;
    },
    parseCSV,
    filterActive,
    toNDJSON,
    fs.createWriteStream('active-users.ndjson')
);
```

Why this pattern is powerful:
- Each stage is a plain `async function*` — no stream class, no callback, no objectMode options
- `for await...of` + `yield` replaces `_transform` + `callback`
- Early `return` from a generator replaces `stream.destroy()` — automatic cleanup
- Error handling: an unhandled throw inside the generator propagates to `pipeline()`'s rejection, which destroys all other stages — same guarantee as Transform streams

## Section 6: Real-World Patterns

**Q11. How do you implement a production-grade file upload handler with `pipeline()`?**

A: Combining `pipeline()` with proper error handling, cleanup, partial-write prevention, and abort on client disconnect:

```typescript
import { pipeline } from 'stream/promises';
import fs from 'fs';
import path from 'path';
import crypto from 'crypto';
import zlib from 'zlib';
import { Request, Response } from 'express';

async function handleUpload(req: Request, res: Response): Promise<void> {
    const uploadId = crypto.randomUUID();
    const tmpPath = path.join('/tmp', `upload-${uploadId}.gz`);
    const finalPath = path.join('/data/uploads', `${uploadId}.gz`);

    const controller = new AbortController();

    // Abort the pipeline if the client disconnects mid-upload
    req.on('close', () => {
        if (!res.writableEnded) {
            controller.abort();
        }
    });

    try {
        // Write to temp path first — prevents partial writes to final location
        await pipeline(
            req,                        // Readable: HTTP request body
            zlib.createGzip(),          // Transform: compress on the fly
            fs.createWriteStream(tmpPath),
            { signal: controller.signal }
        );

        // Atomic rename — only appears in final path when fully written
        await fs.promises.rename(tmpPath, finalPath);

        res.json({ uploadId, path: finalPath });

    } catch (err) {
        // pipeline() already destroyed all streams — no fd leaks
        // Clean up the temp file if it was partially written
        await fs.promises.unlink(tmpPath).catch(() => {}); // Ignore if doesn't exist

        if ((err as any).name === 'AbortError') {
            // Client disconnected — no response to send
            return;
        }

        res.status(500).json({ error: 'Upload failed' });
    }
}
```

**Q12. How do you stream a large database result set to an HTTP response without loading it all in memory?**

A: The classic memory blow-up pattern: fetching 500,000 rows into an array and calling `res.json()` serializes everything at once. `pipeline()` with a streaming query fixes this:

```typescript
import { pipeline } from 'stream/promises';
import { Transform } from 'stream';
import { Pool } from 'pg';

const db = new Pool();

async function streamOrders(req: Request, res: Response): Promise<void> {
    // pg's query().stream() returns a Readable that emits one row at a time
    const queryStream = db.query(
        new QueryStream('SELECT * FROM orders WHERE status = $1', ['completed'])
    );

    res.setHeader('Content-Type', 'application/x-ndjson');
    res.setHeader('Transfer-Encoding', 'chunked');

    // Transform: serialize each row to a newline-delimited JSON string
    const rowToNDJSON = new Transform({
        objectMode: true, // Input: JS objects from pg
        transform(row, _, callback) {
            callback(null, JSON.stringify(row) + '\n');
        }
    });

    try {
        await pipeline(
            queryStream,  // Reads rows one at a time from PG cursor
            rowToNDJSON,  // Serialize each row
            res           // HTTP response (a Writable stream)
        );
        // Memory usage: constant regardless of result set size
        // If client is slow, backpressure pauses the DB cursor — no buffering

    } catch (err) {
        // pipeline() destroyed queryStream — DB cursor closed, no connection leak
        if (!res.headersSent) {
            res.status(500).json({ error: 'Stream failed' });
        }
        // If headers already sent (streaming started), can't send a new status
        // — connection will just drop, client handles it
    }
}
```

The backpressure chain here is critical: if the client is a slow mobile connection, `res` (the HTTP writable) fills up and signals backpressure, which flows back through `rowToNDJSON` to `queryStream`, which pauses the PostgreSQL cursor. The DB doesn't read the next row until the client has consumed the previous one. Memory usage stays flat at roughly one row + buffer size.

## Section 7: Scenario-Based Questions

**Q13. "What's wrong with this code? How would you fix it?"**

```javascript
function compressAndUpload(inputPath, outputPath) {
    fs.createReadStream(inputPath)
        .pipe(zlib.createGzip())
        .pipe(fs.createWriteStream(outputPath));
}

compressAndUpload('data.csv', 'data.csv.gz');
```

A: Four problems:

```typescript
// Problem 1: No error handling on any stream
// If createReadStream fails (file not found), process crashes with unhandled 'error'
// If createWriteStream fails (disk full), same crash
// If zlib errors (corrupt stream), same crash

// Problem 2: No way to know when the operation completes
// The function returns before the pipeline finishes
// Caller can't await completion or handle errors from outside

// Problem 3: Stream leaks on error
// If the WriteStream errors: ReadStream and Gzip are NOT destroyed
// File descriptors stay open until GC or process exit

// Problem 4: No cleanup of partial output file on error
// If compression fails mid-way, 'data.csv.gz' exists but is corrupt

// Fixed version:
import { pipeline } from 'stream/promises';
import fs from 'fs';
import zlib from 'zlib';

async function compressAndUpload(inputPath: string, outputPath: string): Promise<void> {
    const tmpPath = outputPath + '.tmp';

    try {
        await pipeline(
            fs.createReadStream(inputPath),   // Error propagates to catch
            zlib.createGzip(),                // Error propagates to catch
            fs.createWriteStream(tmpPath)     // Error propagates to catch
            // All streams destroyed automatically on any error
        );
        // Only rename if pipeline completed successfully — no corrupt output files
        await fs.promises.rename(tmpPath, outputPath);

    } catch (err) {
        await fs.promises.unlink(tmpPath).catch(() => {});
        throw err; // Re-throw so caller knows it failed
    }
}

// Caller can now handle errors and await completion:
try {
    await compressAndUpload('data.csv', 'data.csv.gz');
    console.log('Done');
} catch (err) {
    console.error('Compression failed:', err.message);
}
```

**Q14. "You need to process a 10GB log file: parse each line, filter errors, enrich with a DB lookup, and write results to S3. Walk through the architecture."**

A: This is a streaming pipeline problem — loading the file into memory is impossible at 10GB. The solution chains transforms with careful async handling:

```typescript
import { pipeline } from 'stream/promises';
import fs from 'fs';
import readline from 'readline';
import { Transform } from 'stream';
import { S3 } from '@aws-sdk/client-s3';
import { Upload } from '@aws-sdk/lib-storage';

const s3 = new S3({ region: 'ap-south-1' });

// Stage 1: Parse raw log lines into structured objects
function createLogParser(): Transform {
    return new Transform({
        objectMode: true,
        transform(line: string, _, callback) {
            const match = line.match(/^(\S+) (\S+) (\S+) (.*)$/);
            if (!match) return callback(); // Skip malformed lines
            const [, timestamp, level, service, message] = match;
            callback(null, { timestamp, level, service, message });
        }
    });
}

// Stage 2: Filter to error-level entries only
function createErrorFilter(): Transform {
    return new Transform({
        objectMode: true,
        transform(entry, _, callback) {
            if (entry.level === 'ERROR') {
                callback(null, entry); // Pass through
            } else {
                callback(); // Drop — push nothing
            }
        }
    });
}

// Stage 3: Enrich with DB lookup (async Transform)
function createEnricher(db: DatabaseClient): Transform {
    return new Transform({
        objectMode: true,
        // concurrency: process up to 10 DB lookups in parallel using a semaphore
        // For simplicity here: sequential
        async transform(entry, _, callback) {
            try {
                const metadata = await db.getServiceMetadata(entry.service);
                callback(null, { ...entry, team: metadata.ownerTeam, sla: metadata.sla });
            } catch (err) {
                callback(null, entry); // Enrich with what we have, don't fail the pipeline
            }
        }
    });
}

// Stage 4: Serialize to NDJSON
function createSerializer(): Transform {
    return new Transform({
        objectMode: true, // Input: objects
        // Output: strings (not objectMode on output side — mixed mode)
        transform(entry, _, callback) {
            callback(null, JSON.stringify(entry) + '\n');
        }
    });
}

async function processLogFile(inputPath: string, s3Key: string): Promise<void> {
    // S3 multipart upload wraps a PassThrough as a Writable
    const passThrough = new PassThrough();
    const upload = new Upload({
        client: s3,
        params: {
            Bucket: 'my-logs-bucket',
            Key: s3Key,
            Body: passThrough,
            ContentType: 'application/x-ndjson'
        }
    });

    // Run S3 upload concurrently with the pipeline
    const uploadPromise = upload.done();

    await pipeline(
        fs.createReadStream(inputPath, { encoding: 'utf8' }),
        async function* (source) {
            // Split into lines using readline — handles partial chunks
            const rl = readline.createInterface({ input: source as any });
            yield* rl;
        },
        createLogParser(),
        createErrorFilter(),
        createEnricher(db),
        createSerializer(),
        passThrough // pipeline writes into passThrough, S3 Upload reads from it
    );

    await uploadPromise; // Wait for S3 to confirm all parts received

    // Memory usage throughout: O(1) — one log line in memory at a time
    // Backpressure: S3 upload slowing down? → passThrough fills → serializer pauses
    //               → enricher pauses → filter pauses → parser pauses
    //               → readline pauses → file read rate slows
    // The entire chain self-throttles to the speed of S3 uploads
}
```

**Q15. "When would you still reach for `pipe()` instead of `pipeline()`?"**

A: Honestly, rarely — but there are legitimate cases:

```javascript
// Case 1: You're targeting Node.js < 10 (pipeline was added in 10.0)
// — but this is increasingly rare in 2024+

// Case 2: You're building stream utilities that return the chain for further piping,
// not consuming the final output yourself:
function createProcessingChain() {
    const transform1 = new SomeTransform();
    const transform2 = new AnotherTransform();
    transform1.pipe(transform2);
    return { writable: transform1, readable: transform2 };
    // Caller connects their source/sink and owns error handling
}

// Case 3: Multiple sources feeding one sink with { end: false }
// (pipeline manages one linear chain — fan-in is naturally a pipe concern)
const merged = new PassThrough();
source1.pipe(merged, { end: false });
source2.pipe(merged, { end: false });
let done = 0;
const end = () => { if (++done === 2) merged.end(); };
source1.on('end', end);
source2.on('end', end);
await pipeline(merged, destination);

// Case 4: Hot observables / infinite streams where you explicitly don't
// want the chain to end when the source ends (event buses, log tailing, etc.)
// — though this is more of a design choice than pipe() being better
```

The default answer in modern Node.js (≥15) is always `pipeline()` from `stream/promises`. Reach for `pipe()` only when you have an explicit reason — fan-in topologies, library authoring where you're returning partial chains, or legacy Node.js targets.

## Quick Reference Table

| Feature | `pipe()` | `pipeline()` |
|---|---|---|
| Added in | Node.js 0.9.4 | Node.js 10.0 (callback) / 15.0 (Promise) |
| Returns | Destination stream | `void` (callback) or `Promise<void>` |
| Backpressure | Yes | Yes |
| Error propagation | No — manual per-stream listeners required | Yes — one catch/callback for all streams |
| Stream cleanup on error | No — streams leak | Yes — all streams destroyed |
| Stream cleanup on success | Partial (`dest.end()` called) | Yes — all streams destroyed |
| `AbortSignal` support | No | Yes |
| Async generator stages | No | Yes |
| Chaining syntax | `.pipe(a).pipe(b).pipe(c)` | `pipeline(src, a, b, c, dest)` |
| Use today | Fan-in, library internals, legacy | Everything else |

---

**Tip for interviews:** Five things separate strong candidates on this topic: (1) being able to state the **exact failure mode of `pipe()`** — not just "it doesn't handle errors" but specifically that the other streams are NOT destroyed on error, causing file descriptor leaks, and that an unlistened `'error'` event on an EventEmitter crashes the Node.js process; (2) knowing the **difference between the callback and Promise forms** of `pipeline()` and that the Promise form comes from `stream/promises` (Node.js 15+), not `stream` — getting this import wrong in an interview is an easy way to look unprepared; (3) understanding **backpressure flows backward through the chain** — a slow Writable causes the upstream Readable to pause, which is the whole point of both APIs and what prevents memory blow-up on large files; (4) knowing when `pipe()` is still appropriate — **fan-in topologies** (multiple sources into one sink), returning partial chains from library functions, or needing the return value for further chaining — rather than saying `pipeline()` is always superior; and (5) being able to implement a **custom Transform** with `_transform` and `_flush` — specifically knowing that you must call `callback()` exactly once per `_transform` invocation and that errors go to `callback(err)`, not `throw` — because this is where stream pipelines break in subtle ways that are hard to debug.
