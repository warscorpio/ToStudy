# Node.js: Backpressure — What It Is and How to Handle It — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is backpressure, and why does it matter for Node.js applications?**
A: Backpressure is the buildup of pressure in a pipeline when **a consumer cannot process data as fast as a producer generates it**. In a water pipe analogy, if you pump water faster than the pipe at the far end can drain it, pressure builds up — eventually the pipe bursts or the system stalls. In software, the analogous failure is **memory exhaustion**: the producer keeps generating data and the system must buffer it somewhere, accumulating unbounded memory until the process crashes or becomes unusably slow.

In Node.js specifically, backpressure arises in stream pipelines — reading from a fast source (network socket, file on an NVMe SSD) and writing to a slow sink (a compressed file, a congested network connection, a rate-limited upstream API). Without backpressure handling, the readable side keeps producing chunks, they pile up in memory buffers, and the process's heap grows without bound. Correct backpressure handling signals the producer to **pause** when the consumer's buffer is full and **resume** only when the consumer has drained enough to accept more data — keeping memory usage flat regardless of total data size.

```
Without backpressure:
Producer → [growing buffer ↑↑↑ memory] → Consumer (slow)
           Eventually: OOM crash or severe GC pressure

With backpressure:
Producer ⇌ [bounded buffer] ⇌ Consumer (slow)
           Producer pauses when buffer full, resumes when buffer drains
           Memory stays flat, throughput maximized
```

**Q2. What is Node.js's stream system, and how is it the primary context for backpressure in Node.js?**
A: Node.js streams are abstractions over sequential data — `Readable` (data sources), `Writable` (data sinks), `Duplex` (both), and `Transform` (duplex with transformation). Streams were specifically designed to handle large data without loading it all into memory. The backpressure mechanism is built into the `Readable`/`Writable` protocol:

- A **`Writable`** stream has an internal buffer and a **`highWaterMark`** — a soft limit (default 16KB for byte streams, 16 objects for object-mode streams) indicating the maximum amount of data the writable should buffer before signaling "I'm full."
- When `writable.write(chunk)` returns `false`, the writable's buffer is at or beyond its `highWaterMark` — this is the backpressure signal. The producer should stop calling `.write()` until the `'drain'` event fires.
- When the buffer drains below the `highWaterMark`, the writable emits `'drain'` — signaling the producer to resume.

```js
// The write() return value is the backpressure signal:
const canContinue = writable.write(chunk);
if (!canContinue) {
  // STOP producing data — buffer is full
  readable.pause(); // or stop generating data manually
  writable.once('drain', () => {
    // RESUME — buffer has drained
    readable.resume(); // or re-start generating data
  });
}
```

**Q3. What is `highWaterMark`, and what happens when it's set too high or too low?**
A: `highWaterMark` is the **soft buffer limit** for both Readable and Writable streams. It's the threshold at which the stream signals backpressure rather than the absolute maximum data in the buffer — data can exceed it, it's not a hard cap.

For a **Readable**: `highWaterMark` controls how much data is pre-fetched from the underlying source. When the internal buffer fills to `highWaterMark`, the readable stops calling `_read()` and waits for consumers to drain the buffer.

For a **Writable**: `highWaterMark` is the point at which `write()` returns `false` (backpressure signal). Data continues to be buffered until the stream processes it, but the producer should stop sending more.

Effects of misconfiguration:
- **Too high** (`highWaterMark: 100 * 1024 * 1024` — 100MB): backpressure only triggers when 100MB is buffered. Memory use can spike to hundreds of MB before the signal fires. Safe for burst scenarios but risky for sustained high-throughput pipelines.
- **Too low** (`highWaterMark: 1`): backpressure triggers after every single byte/object. Producer and consumer spend most of their time in pause/resume cycles with minimal data in flight. Reduces throughput due to overhead.
- **Default (16KB for byte streams, 16 for object mode)**: a balanced starting point for most workloads. Tune based on profiling.

### Section 2: The Backpressure Protocol in Detail

**Q4. What is the complete backpressure protocol — all the signals and their meaning?**
A: The backpressure protocol between a Readable and a Writable consists of five signals:

| Signal | Direction | Meaning |
|---|---|---|
| `write(chunk)` returns `true` | Writable → Producer | Buffer below `highWaterMark` — continue writing |
| `write(chunk)` returns `false` | Writable → Producer | Buffer at/above `highWaterMark` — **stop writing** |
| `'drain'` event | Writable → Producer | Buffer drained below `highWaterMark` — **resume writing** |
| `readable.pause()` | Consumer → Readable | Stop emitting `'data'` events |
| `readable.resume()` | Consumer → Readable | Resume emitting `'data'` events |

The full manually-managed backpressure loop:

```js
function pump(readable, writable) {
  readable.on('data', (chunk) => {
    const shouldContinue = writable.write(chunk);

    if (!shouldContinue) {
      readable.pause(); // honor backpressure: stop the source

      writable.once('drain', () => {
        readable.resume(); // writable drained: restart the source
      });
    }
  });

  readable.on('end', () => writable.end());
  readable.on('error', (err) => writable.destroy(err));
  writable.on('error', (err) => readable.destroy(err));
}
```

**Q5. What is `pipe()`, and how does it automatically handle backpressure?**
A: `readable.pipe(writable)` is Node.js's built-in method for connecting a readable to a writable while automatically implementing the backpressure protocol described in Q4 — it calls `pause()` when `write()` returns `false` and calls `resume()` on `'drain'`. This is the simplest correct way to handle backpressure for linear pipelines:

```js
// Pipe handles backpressure automatically:
const fs = require('fs');
const zlib = require('zlib');

fs.createReadStream('large-file.txt')
  .pipe(zlib.createGzip())      // Transform: handles backpressure internally
  .pipe(fs.createWriteStream('large-file.txt.gz'));
// No manual pause/resume needed — pipe handles it throughout the chain
```

However, `pipe()` has known limitations: error handling requires manually attaching `.on('error')` handlers to every stream in the chain (errors don't propagate automatically through a pipe chain), and cleanup (destroying all streams when one errors) is not automatic.

**Q6. What is `pipeline()`, and how does it improve on `pipe()` for production code?**
A: `stream.pipeline()` (available from Node.js 10+) wraps a pipe chain with **automatic error propagation, cleanup, and a completion callback**. When any stream in the pipeline errors, all other streams in the chain are automatically destroyed (preventing resource leaks), and the callback receives the error. This makes it the recommended production-grade alternative to chained `.pipe()`.

```js
const { pipeline } = require('stream');
const { promisify } = require('util');

const pipelineAsync = promisify(pipeline);

// OR with stream.promises (Node.js 15+):
const { pipeline } = require('stream/promises');

async function compressFile(inputPath, outputPath) {
  await pipeline(
    fs.createReadStream(inputPath),
    zlib.createGzip(),
    fs.createWriteStream(outputPath)
  );
  console.log('Pipeline complete — file compressed');
  // If any stream errors, ALL streams are destroyed and the error is thrown here
}

// The equivalent pipe() version requires manual error handling on each stream:
// const r = fs.createReadStream(input);
// const g = zlib.createGzip();
// const w = fs.createWriteStream(output);
// r.on('error', cleanup); g.on('error', cleanup); w.on('error', cleanup);
// r.pipe(g).pipe(w);
// w.on('finish', done);
// — much more boilerplate, much easier to get wrong
```

### Section 3: Backpressure Beyond Streams

**Q7. Does backpressure only apply to Node.js streams, or are there other contexts?**
A: Backpressure is a general concept that appears anywhere a producer and consumer operate at different speeds. In Node.js, backpressure manifests in several contexts beyond the stream API:

1. **HTTP/TCP at the socket level**: TCP has its own flow-control mechanism (receiver window). When a TCP receiver's buffer fills, it sends a window size of 0, signaling the sender to stop. Node.js's `net.Socket` exposes this via `socket.write()` return value and `'drain'` events — the same protocol as streams.

2. **`child_process` stdio pipes**: writing to a child process's stdin can trigger backpressure if the child isn't consuming stdin fast enough. The `ChildProcess.stdin` is a `Writable` stream — the same `write()` return value and `'drain'` protocol applies.

3. **Message queues and event emitters**: if you're using a queue (RabbitMQ, Kafka, Redis Streams) and the consumer falls behind, the queue itself buffers messages. Backpressure here is managed by the queue's flow control protocol — typically by acknowledging messages only when processed and limiting prefetch count.

4. **WebSocket servers**: sending too many messages to a client with a slow connection buffers data in the `ws` library's internal queue. The `WebSocket.bufferedAmount` property (browser) and `ws.bufferedAmount` (Node.js `ws` library) indicate how much data is queued. Production WebSocket code should check `bufferedAmount` before sending more data.

5. **Database write operations**: inserting faster than the database can commit builds up in the connection's write buffer. Connection pool exhaustion is a higher-level manifestation of the same pressure.

**Q8. How does backpressure manifest in HTTP streaming responses, and what happens without it?**
A: When using `res.write()` in Node.js's HTTP server to stream a response to a client, `res` is a `Writable` stream backed by the underlying TCP socket. If the client is consuming the response slowly (small TCP receive window, slow network), the socket's kernel buffer fills up, and `res.write()` returns `false` — signaling that the response buffer is full.

Without respecting this signal:
- The process continues reading from the data source (database query results, file, etc.) and calling `res.write()`.
- Node.js buffers the unwritten data in memory in the `ServerResponse`'s internal buffer.
- With enough slow clients and a fast data source, this accumulates into massive memory usage.
- Worst case: the process OOMs or severe GC pressure makes the entire server unresponsive.

```js
// WRONG — ignores backpressure on HTTP response:
app.get('/stream', (req, res) => {
  const readable = getDatabaseStream();
  readable.on('data', (chunk) => {
    res.write(chunk); // returns false when client is slow — IGNORED
  });
  readable.on('end', () => res.end());
});

// CORRECT — respects backpressure using pipeline:
app.get('/stream', (req, res) => {
  const readable = getDatabaseStream();
  pipeline(readable, res, (err) => {
    if (err && err.code !== 'ERR_STREAM_PREMATURE_CLOSE') {
      console.error('Pipeline error:', err);
    }
  });
});
```

### Section 4: Implementing Custom Streams with Correct Backpressure

**Q9. How do you implement a custom `Readable` stream that correctly signals backpressure from its data source?**
A: A custom `Readable` must implement `_read(size)`, which is called by the stream internals whenever the consumer wants more data. The key contract: **only push more data when `_read` is called** — never push proactively from a timer or external event without being asked. When `push()` returns `false`, the internal buffer is full and `_read` will NOT be called again until the consumer has drained some data.

```js
const { Readable } = require('stream');

class DatabaseCursorStream extends Readable {
  constructor(cursor, options) {
    super({ objectMode: true, highWaterMark: 16, ...options });
    this.cursor = cursor;
    this._reading = false;
  }

  _read() {
    // This is called when the consumer wants more data.
    // We should fetch ONE record (or a small batch) and push it.
    // We must NOT fetch multiple records proactively without being asked.

    if (this._reading) return; // prevent concurrent fetches
    this._reading = true;

    this.cursor.next((err, record) => {
      this._reading = false;

      if (err) {
        this.destroy(err);
        return;
      }

      if (record === null) {
        this.push(null); // signal end-of-stream
        return;
      }

      const canContinue = this.push(record);

      if (canContinue) {
        // Consumer wants more — call _read again
        this._read();
      }
      // If canContinue is false: stop. _read() will be called again when the
      // consumer drains enough from the internal buffer.
    });
  }
}
```

**Q10. How do you implement a custom `Writable` stream that signals backpressure to its producer?**
A: A custom `Writable` must implement `_write(chunk, encoding, callback)`. The callback is the backpressure mechanism: **only call `callback()` when truly ready to receive the next chunk**. Calling `callback()` immediately (before the actual write is done) loses backpressure — the stream internals consider the write "done" and accept more data, building up a queue. Calling `callback()` only after the underlying write completes correctly applies backpressure.

```js
const { Writable } = require('stream');

class RateLimitedSink extends Writable {
  constructor(rateLimitMs, options) {
    super({ highWaterMark: 4, ...options });
    this.rateLimitMs = rateLimitMs;
  }

  _write(chunk, encoding, callback) {
    // Simulate a slow consumer — processes one chunk per rateLimitMs
    // CRITICAL: we call callback() only AFTER we're done with this chunk.
    // This tells the stream internals that we're ready for the next chunk.
    // While this timer is running, the stream knows we're busy and
    // applies backpressure (write() may return false) if the buffer fills.

    doActualWork(chunk)
      .then(() => {
        // We're done. Signal "ready for next chunk" by calling callback.
        callback();
        // The stream internals will now allow the next write to proceed.
      })
      .catch((err) => {
        callback(err); // Signal an error — stream emits 'error' event
      });
  }

  _writev(chunks, callback) {
    // Optional: handle multiple buffered chunks at once (batch processing)
    // Called when multiple writes were buffered while _write was in progress.
    Promise.all(chunks.map(({ chunk }) => doActualWork(chunk)))
      .then(() => callback())
      .catch(callback);
  }
}

async function doActualWork(chunk) {
  // Simulate database write, API call, etc.
  await new Promise(resolve => setTimeout(resolve, 100));
}
```

### Section 5: Advanced Patterns

**Q11. What is "object mode" in streams, and how does `highWaterMark` work differently in it?**
A: By default, Node.js streams operate in **byte mode** — chunks are `Buffer` or `string` values, and `highWaterMark` is measured in bytes. In **object mode** (`objectMode: true`), chunks can be any JavaScript value (plain objects, arrays, etc.), and `highWaterMark` is measured in **number of objects** rather than bytes.

This matters for backpressure because the relationship between "number of objects" and "memory consumed" is application-specific and unknown to the stream — a stream with `highWaterMark: 16` (16 objects) will behave very differently if those objects are `{ id: 1 }` (tiny) versus large result sets with 1MB of data each. When using object mode streams with large per-object memory footprints, set `highWaterMark` lower than the default 16, or implement custom backpressure based on object size rather than count.

```js
// Object mode: highWaterMark = 16 objects by default
const objectStream = new Transform({
  objectMode: true,
  highWaterMark: 4, // buffer at most 4 objects before signaling backpressure
  transform(obj, enc, cb) {
    cb(null, processObject(obj));
  }
});
```

**Q12. How does `stream.pipeline()` handle backpressure through a Transform stream?**
A: A `Transform` stream is simultaneously a `Writable` (receiving data from upstream) and a `Readable` (emitting data to downstream). `pipeline()` wires up backpressure bidirectionally: if the downstream `Writable` signals backpressure (its `write()` returns `false`), the Transform pauses emitting to the downstream. When the Transform pauses emitting, it doesn't call `callback()` in its `_transform` method — which in turn causes the Transform's `Writable` side to stop accepting data from upstream — which causes the upstream Readable to pause. This forms a **backpressure chain** that propagates from the slowest consumer all the way back to the original source.

```
[Readable source] → [Transform A] → [Transform B] → [Writable sink]

If sink's buffer fills → sink's write() returns false → Transform B pauses emitting
→ Transform B doesn't call _transform's callback → Transform B's writable buffer fills
→ Transform A pauses emitting → Transform A's writable buffer fills
→ Source readable pauses _read

All propagated automatically by pipeline()
```

**Q13. What are the `cork()` and `uncork()` methods on a `Writable`, and how do they relate to backpressure?**
A: `writable.cork()` suspends processing of `write()` calls — data is buffered in memory instead of being immediately written to the underlying resource. `writable.uncork()` flushes all buffered data at once by calling `_writev()` (if implemented) or multiple `_write()` calls. This is an **optimization for batching**: instead of processing many small writes one at a time (with the overhead of many async operations), cork/uncork groups them into one efficient batch.

```js
// Without cork: N individual writes → N individual I/O operations
writable.write(chunk1);
writable.write(chunk2);
writable.write(chunk3);

// With cork/uncork: N writes buffered, then ONE batched I/O operation via _writev:
writable.cork();
writable.write(chunk1);
writable.write(chunk2);
writable.write(chunk3);
process.nextTick(() => writable.uncork()); // uncork in nextTick to batch same-tick writes
```

`cork()`/`uncork()` interact with backpressure: while corked, `write()` will likely return `true` (data is buffering), but the real backpressure check happens at `uncork()`. It's important to use `process.nextTick(() => writable.uncork())` rather than synchronous `uncork()` so that all `write()` calls within the same synchronous block are gathered before the flush.

**Q14. How do you handle backpressure when using `async/await` and `for await...of` instead of stream events?**
A: The `for await...of` loop over an async iterable (including Node.js Readable streams in Node.js 12+) **automatically handles backpressure** — the loop suspends when the readable's internal buffer is empty (waiting for more data) and the reading side naturally throttles. For the writable side, pairing `for await...of` on the readable with `await write()` on the writable handles backpressure:

```js
const { Writable } = require('stream');

// Promisify write to await individual writes:
function writeAsync(writable, chunk) {
  return new Promise((resolve, reject) => {
    const ok = writable.write(chunk, (err) => {
      if (err) reject(err);
    });
    if (ok) {
      resolve(); // buffer has space — can continue immediately
    } else {
      writable.once('drain', resolve); // wait for drain before resolving
    }
  });
}

async function copyWithBackpressure(readable, writable) {
  for await (const chunk of readable) {
    await writeAsync(writable, chunk); // pause loop iteration until write is drained
  }
  writable.end();
}
```

Or using `stream.pipeline` with async generators:

```js
const { pipeline } = require('stream/promises');

async function* processRecords(source) {
  for await (const record of source) {
    // Apply transformation and yield — pipeline handles backpressure
    yield transform(record);
  }
}

await pipeline(
  databaseStream,
  processRecords,    // async generator as a Transform
  outputFileStream
);
```

### Section 6: Scenario / Interview-Style Questions

**Q15. "You write a Node.js service that reads from a fast database (returns rows at 100,000/s) and writes them to a slow HTTP upstream (accepts 1,000/s). What happens without backpressure handling, and how do you fix it?"**
A: Without backpressure handling, the database stream continuously emits rows at 100,000/s, each row is buffered in the HTTP client's write buffer (since the upstream only accepts 1,000/s), and the buffer grows by 99,000 rows per second. After a few seconds, the process runs out of memory and crashes — or if it doesn't crash, GC pressure from hundreds of MB of buffered data makes the entire service unresponsive.

Fix using `pipeline()`:
```js
const { pipeline } = require('stream/promises');

await pipeline(
  db.queryStream('SELECT * FROM large_table'),  // Readable: fast source
  new Transform({
    objectMode: true,
    transform(row, enc, cb) { cb(null, serialize(row)); }
  }),
  httpUpstreamWritable   // Writable: slow sink — signals backpressure when full
);
// pipeline automatically pauses the db stream when the HTTP sink can't keep up
```

The database cursor emits at 100,000/s but the pipeline's backpressure propagation causes it to pause reading after `highWaterMark` rows are buffered. The HTTP writable drains at 1,000/s; only `highWaterMark` rows (e.g., 16 by default in object mode) are ever in memory at once. Memory stays flat.

**Q16. "A colleague replaces `pipeline()` with a manual `pipe()` chain and says it's fine because they added `.on('error')` to the final stream. What's wrong?"**
A: Adding `.on('error')` to the final stream only catches errors from that final stream. Errors from intermediate streams (the first readable, any transforms in the middle) do not propagate through a `pipe()` chain to the final stream's error handler — they emit on the intermediate stream itself and go unhandled, potentially crashing the process with an uncaughtException. Additionally, when one stream errors, `pipe()` does NOT automatically destroy the other streams, causing resource leaks (open file handles, database connections). `pipeline()` correctly: (1) propagates errors from any stream to a single callback, (2) automatically destroys all streams when any one of them errors, and (3) handles the case where the writable stream closes before the readable is finished.

**Q17. "How would you implement a 'throttling' transform that limits the rate of data passing through a pipeline to 1,000 records per second?"**
A: Implement a Transform that adds a delay before calling the `_transform` callback when the throughput would exceed the limit — the delay itself implements backpressure by holding up the pipeline:

```js
class ThrottleTransform extends Transform {
  constructor(maxPerSecond, options = {}) {
    super({ objectMode: true, ...options });
    this.interval = 1000 / maxPerSecond; // ms per item
    this.lastEmit = 0;
  }

  _transform(chunk, encoding, callback) {
    const now = Date.now();
    const elapsed = now - this.lastEmit;
    const waitTime = Math.max(0, this.interval - elapsed);

    if (waitTime === 0) {
      this.lastEmit = now;
      this.push(chunk);
      callback(); // ready for next chunk immediately
    } else {
      setTimeout(() => {
        this.lastEmit = Date.now();
        this.push(chunk);
        callback(); // ready for next chunk after throttle delay
      }, waitTime);
    }
    // By delaying callback(), we hold up the pipeline — upstream pauses
    // until we signal we're ready, naturally limiting throughput
  }
}

// Usage:
await pipeline(
  fastDatabaseStream,
  new ThrottleTransform(1000), // limits to 1000 items/sec
  slowUpstreamWritable
);
```

## Problem 1 — File Copy with Correct Backpressure (Manual Protocol vs. `pipeline`)

### Problem
Implement a file copy function three ways: (1) incorrectly without backpressure, (2) correctly with manual pause/resume, (3) correctly with `pipeline`. Show why (1) fails and why (2) and (3) are equivalent.

### Pattern Recognition
The foundational `write()`→`false`→`pause()`→`'drain'`→`resume()` backpressure protocol, and `pipeline()` as the canonical correct implementation.

### Key Insight
`write()` returning `false` is the only backpressure signal — ignoring it means unbounded memory buffering. `pipeline()` implements the full protocol internally, plus adds error propagation and cleanup that the manual version requires explicit handling for.

### Solution

```js
const fs = require('fs');
const { pipeline } = require('stream/promises');

// ─────────────────────────────────────────────
// VERSION 1: WRONG — ignores backpressure signal
// ─────────────────────────────────────────────
function copyFileWrong(src, dest) {
  const readable = fs.createReadStream(src);
  const writable = fs.createWriteStream(dest);

  readable.on('data', (chunk) => {
    // write() may return false — we IGNORE it
    // If the writable can't keep up (e.g., slow disk, network),
    // Node.js buffers all the chunks in the writable's internal queue
    writable.write(chunk); // ← return value discarded — BUG
  });

  readable.on('end', () => writable.end());
  // No error handling — another bug, but separate from backpressure
}

// Failure mode: copy a 10GB file. The writable's buffer grows unbounded
// because the readable emits data faster than the writable can flush.
// Process memory spikes to multiple GB before potential OOM crash.

// ─────────────────────────────────────────────
// VERSION 2: CORRECT — manual backpressure protocol
// ─────────────────────────────────────────────
function copyFileManual(src, dest, callback) {
  const readable = fs.createReadStream(src);
  const writable = fs.createWriteStream(dest);

  function onError(err) {
    readable.destroy();
    writable.destroy();
    callback(err);
  }

  readable.on('error', onError);
  writable.on('error', onError);

  readable.on('data', (chunk) => {
    // write() returns false when the writable's buffer is at/above highWaterMark
    const canContinue = writable.write(chunk);

    if (!canContinue) {
      // PAUSE the readable — stop generating data
      // (fs.createReadStream pauses, stops calling read() on the fd)
      readable.pause();

      // WAIT for the writable to drain its buffer
      writable.once('drain', () => {
        // Writable has drained: RESUME the readable
        readable.resume();
        // Now readable will emit 'data' events again
      });
    }
    // If canContinue is true: keep reading — buffer has room
  });

  readable.on('end', () => {
    writable.end(); // Signal no more data to the writable
  });

  writable.on('finish', () => {
    callback(null); // All data flushed to disk
  });
}

// ─────────────────────────────────────────────
// VERSION 3: CORRECT — using pipeline (recommended)
// ─────────────────────────────────────────────
async function copyFilePipeline(src, dest) {
  await pipeline(
    fs.createReadStream(src),
    fs.createWriteStream(dest)
    // pipeline internally does exactly what copyFileManual does,
    // PLUS it destroys all streams on error AND handles the finish event
  );
}

// Version 3 in a callback style (Node.js < 15, or when not using async/await):
function copyFilePipelineCallback(src, dest, callback) {
  const { pipeline } = require('stream');
  pipeline(
    fs.createReadStream(src),
    fs.createWriteStream(dest),
    callback // called with (err) on error or null on success
  );
}
```

### Verification

```js
// Create a test: copy a "large" file and observe memory:
const { execSync } = require('child_process');

// Create a 100MB test file:
execSync('dd if=/dev/zero of=/tmp/test-input bs=1M count=100');

// Measure memory during copy:
async function measureMemory(copyFn) {
  const before = process.memoryUsage().heapUsed;
  const snapshots = [];

  const interval = setInterval(() => {
    snapshots.push(process.memoryUsage().heapUsed);
  }, 10);

  await copyFn('/tmp/test-input', '/tmp/test-output');

  clearInterval(interval);
  const maxMem = Math.max(...snapshots);
  console.log(`Peak memory during copy: ${((maxMem - before) / 1024 / 1024).toFixed(1)} MB`);
}

// With copyFileWrong: peak memory may be 50-100MB+ (buffering entire file)
// With copyFileManual or copyFilePipeline: peak memory stays near 0 (16KB highWaterMark)
```

### Edge Cases
- **Source file disappears during copy**: `readable.on('error')` fires. In Version 3, `pipeline()` automatically destroys the writable and throws the error. In Version 1, the writable is left open (fd leak).
- **Destination disk full**: `writable.on('error')` fires with `ENOSPC`. Same cleanup behavior.
- **Very slow destination (e.g., network filesystem)**: Version 1 accumulates the entire file's worth of chunks in the writable's buffer. Versions 2 and 3 pause the readable and wait, keeping memory at ~16KB.

### Follow-up Questions
- "What if you want to add a progress callback during the copy?" → Add a `Transform` stream that counts bytes and calls the progress callback, then insert it into the pipeline: `pipeline(readable, progressTransform, writable)`.

## Problem 2 — Database-to-HTTP Streaming with Backpressure

### Problem
Implement a route that streams all users from a database cursor directly to an HTTP response as NDJSON (newline-delimited JSON), respecting backpressure from both the database cursor (readable) and the slow HTTP client (writable).

```
Database cursor → Transform (serialize to NDJSON) → HTTP response
```

### Pattern Recognition
Multi-stage pipeline with a Transform, where the HTTP response `res` is the slow writable and the database cursor is a fast readable. `pipeline()` handles the two-directional backpressure chain automatically.

### Key Insight
`res` (the HTTP `ServerResponse`) is a `Writable` stream. When the client's TCP window is full (slow connection, large response), `res.write()` returns `false`. Without backpressure, the server buffers the entire query result in memory. With `pipeline()`, the database cursor pauses when the HTTP client can't keep up.

### Solution

```js
const { pipeline, Transform } = require('stream');
const { promisify } = require('util');
const pipelineAsync = promisify(pipeline);

// Step 1: A Transform that converts database row objects → NDJSON chunks
class NDJSONTransform extends Transform {
  constructor() {
    super({
      readableObjectMode: false, // output: Buffers/strings for HTTP
      writableObjectMode: true,  // input: plain JS objects from database
    });
  }

  _transform(row, encoding, callback) {
    try {
      // Convert each object to a JSON line + newline
      const line = JSON.stringify(row) + '\n';
      this.push(line);   // emit the serialized chunk to the HTTP response
      callback();        // signal: ready for next row from the database
    } catch (err) {
      callback(err);     // serialization error: propagate up the pipeline
    }
  }

  _flush(callback) {
    // Called when the readable side is done — no trailing data needed for NDJSON
    callback();
  }
}

// Step 2: Express route handler
app.get('/api/users', async (req, res) => {
  // Set response headers before starting the stream
  res.setHeader('Content-Type', 'application/x-ndjson');
  res.setHeader('Transfer-Encoding', 'chunked');

  let cursor;
  try {
    cursor = await db.collection('users').find({}).stream(); // MongoDB cursor stream

    await pipelineAsync(
      cursor,             // Readable: fast — database can emit millions of rows/sec
      new NDJSONTransform(),  // Transform: serializes each row to JSON line
      res                 // Writable: slow — depends on client's connection speed
    );
    // pipeline automatically:
    // - Pauses cursor when res.write() returns false (client too slow)
    // - Resumes cursor when res drains
    // - Destroys cursor and res if any stream errors
    // - Ends res when cursor is exhausted

  } catch (err) {
    if (!res.headersSent) {
      res.status(500).json({ error: 'Stream failed' });
    } else {
      // Headers already sent — can't send a proper error response
      // The connection will be closed by pipeline's cleanup
      console.error('Streaming error after headers sent:', err);
    }
  }
});

// Step 3: Handle client disconnection (client closes the connection early)
app.get('/api/users-with-abort', async (req, res) => {
  res.setHeader('Content-Type', 'application/x-ndjson');

  const cursor = await db.collection('users').find({}).stream();

  // When client disconnects, 'close' fires on res — destroy the cursor
  res.on('close', () => {
    cursor.destroy(); // Stop the database query immediately
    // pipeline will detect the destroyed cursor and clean up
  });

  try {
    await pipelineAsync(cursor, new NDJSONTransform(), res);
  } catch (err) {
    // ERR_STREAM_PREMATURE_CLOSE is expected when client disconnects
    if (err.code !== 'ERR_STREAM_PREMATURE_CLOSE') {
      console.error('Unexpected streaming error:', err);
    }
  }
});
```

### Verification

### Edge Cases
- **Client disconnects mid-stream**: `res.on('close')` fires. Without the `cursor.destroy()` call, the database query continues consuming server resources (CPU, database connections) even though no one is reading the result. Always handle `'close'` on `res` to cancel the upstream data source.
- **Serialization error** (object with circular reference): `JSON.stringify` throws. The `catch` in `_transform` passes the error to `callback(err)`, which `pipeline` catches and propagates — closing both the cursor and the response connection.
- **Database connection drop**: the cursor emits `'error'`. `pipeline` catches it, destroys `res`, and the `catch` block handles cleanup.

### Follow-up Questions
- "How would you add pagination instead of streaming?" → For small datasets where loading all into memory is acceptable, use `cursor.toArray()`. For large datasets where both streaming and pagination are needed, implement cursor-based pagination using `cursor.sort({ _id: 1 }).skip(page * limit).limit(limit)`.

## Problem 3 — Custom Writable with Explicit Backpressure (Rate-Limited API Sink)

### Problem
Implement a `Writable` stream that sends data to a rate-limited external API (max 10 requests per second). The stream must apply backpressure so upstream producers naturally slow down to match the API's rate limit.

### Pattern Recognition
Custom `Writable` with a delayed `callback()` — the delay in calling the `_write` callback is precisely how backpressure is communicated upward: the producer cannot write the next chunk until the current chunk's `callback()` is called.

### Key Insight
The `_write` callback is the backpressure lever in a custom Writable. Every millisecond of delay in calling `callback()` is a millisecond of backpressure applied to the upstream producer — effectively throttling the entire pipeline to match the rate of this Writable.

### Solution

```js
const { Writable } = require('stream');

class RateLimitedAPIWriter extends Writable {
  /**
   * @param {Function} apiCall - async function that sends one chunk to the API
   * @param {number} maxPerSecond - maximum API calls per second
   */
  constructor(apiCall, maxPerSecond = 10) {
    super({
      objectMode: true,       // accepts JS objects (not raw buffers)
      highWaterMark: 5,       // buffer at most 5 objects before backpressure
    });

    this.apiCall = apiCall;
    this.minIntervalMs = 1000 / maxPerSecond; // ms between calls to stay under limit
    this.lastCallTime = 0;
    this.pendingRetries = 0;
  }

  async _write(chunk, encoding, callback) {
    // Calculate how long to wait before making the next API call
    const now = Date.now();
    const elapsed = now - this.lastCallTime;
    const waitTime = Math.max(0, this.minIntervalMs - elapsed);

    if (waitTime > 0) {
      // Rate limit: wait before making the call
      // While waiting, callback() hasn't been called, so the upstream
      // pipeline is paused — this IS the backpressure in action
      await new Promise(resolve => setTimeout(resolve, waitTime));
    }

    try {
      this.lastCallTime = Date.now();
      await this.apiCall(chunk);

      // SUCCESS: call callback() to signal "ready for next chunk"
      // This releases the backpressure for this write
      callback();

    } catch (err) {
      if (err.code === 'RATE_LIMIT_EXCEEDED') {
        // API-level rate limit hit (despite our own throttling):
        // wait 1 second and retry
        this.pendingRetries++;
        if (this.pendingRetries > 5) {
          callback(new Error('API rate limit exceeded after 5 retries'));
          return;
        }

        await new Promise(resolve => setTimeout(resolve, 1000));
        // Retry by calling _write again
        this._write(chunk, encoding, callback);
        this.pendingRetries--;

      } else {
        // Non-retryable error: propagate up the pipeline
        callback(err);
      }
    }
  }

  _writev(chunks, callback) {
    // Handle multiple buffered chunks — process them sequentially
    // This method is called when multiple writes were buffered while
    // _write was in progress (e.g., during the rate limit wait)
    const processNext = (index) => {
      if (index >= chunks.length) {
        callback();
        return;
      }
      this._write(chunks[index].chunk, chunks[index].encoding, (err) => {
        if (err) return callback(err);
        processNext(index + 1);
      });
    };
    processNext(0);
  }
}

// Usage — the upstream Transform will naturally slow down
// to match the API's 10/s rate limit:
const { pipeline } = require('stream/promises');

async function syncToAPI(sourceStream) {
  const apiWriter = new RateLimitedAPIWriter(
    async (record) => {
      await fetch('https://api.example.com/records', {
        method: 'POST',
        body: JSON.stringify(record),
        headers: { 'Content-Type': 'application/json' }
      });
    },
    10 // max 10 requests per second
  );

  // The pipeline's backpressure propagation ensures the database cursor
  // (which could emit 10,000 records/sec) is throttled to 10 records/sec
  // automatically — no polling, no explicit rate limiting in the source:
  await pipeline(
    sourceStream,         // fast: 10,000 records/sec
    apiWriter             // slow: max 10 records/sec
  );
}
```

### Verification

```js

  10 // max 10/sec
);

  Array.from({ length: 100 }, (_, i) => ({ id: i }))
```

### Edge Cases
- **`_write` called while a previous write is still in progress**: the stream internals guarantee this doesn't happen — `_write` is called again only after `callback()` is invoked. The stream manages its own internal queue and calls `_write` sequentially.
- **`_writev` called with many buffered chunks**: if 5 chunks are buffered during a 1-second retry wait, `_writev` receives all 5. Processing them sequentially still respects the rate limit per call.
- **Upstream destroyed while waiting**: if the upstream source is destroyed (e.g., error, early close) while `_write` is waiting in `setTimeout`, Node.js will call `_destroy()` on the Writable. The pending `setTimeout` should be cleared — add `this._timeout = setTimeout(...)` and `_destroy(err, callback) { clearTimeout(this._timeout); callback(err); }`.

### Follow-up Questions
- "How would you add concurrency — e.g., allow 3 API calls in-flight simultaneously (burst of 30 per second in a 100ms window)?" → Maintain a semaphore (a counter of in-flight requests) inside `_write`. If `inFlight < maxConcurrency`, proceed without waiting. Use `Promise.all` for concurrent work and call `callback()` only when all in-flight calls resolve. Alternatively, implement `_writev` to fire up to `maxConcurrency` API calls in parallel.

## Quick Reference — Backpressure Patterns

```
CORE SIGNALS (Writable stream):
─────────────────────────────────────────────────────────────────────
writable.write(chunk) → true   Buffer below highWaterMark, continue writing
writable.write(chunk) → false  Buffer at/above highWaterMark, STOP writing
'drain' event                  Buffer drained, RESUME writing
readable.pause()               Stop emitting 'data' events (honor backpressure)
readable.resume()              Resume emitting 'data' events (after 'drain')

IMPLEMENTATIONS (in order of preference):
─────────────────────────────────────────────────────────────────────
1. stream.pipeline(src, [transforms...], dest, cb)  — ALWAYS prefer this
   ✓ Automatic backpressure throughout the chain
   ✓ Automatic error propagation and cleanup
   ✓ All streams destroyed on any error

2. src.pipe(dest)  — Simple but incomplete
   ✓ Automatic backpressure
   ✗ Errors don't propagate (must add .on('error') to every stream)
   ✗ Streams not cleaned up on error (resource leaks)

3. Manual: pause/resume + drain event  — Only when pipe/pipeline won't work
   ✓ Full control
   ✗ Error-prone, verbose, easy to miss edge cases

4. for await...of + writeAsync()  — For async/await code style
   ✓ Readable backpressure automatic
   ✓ Writable backpressure via awaiting drain promise
   Works well with async generators as transforms

CUSTOM STREAM RULES:
─────────────────────────────────────────────────────────────────────
Custom Readable:
  - Only push() data when _read() is called — never push proactively
  - Stop pushing when push() returns false — wait for next _read() call
  - Set highWaterMark lower for large objects (default 16 may be too many)

Custom Writable:
  - Call callback() ONLY when truly ready for the next chunk
  - Delay in callback() = backpressure applied upstream
  - Use _writev() for batching multiple buffered writes efficiently
  - Handle errors by calling callback(err)

COMMON MISTAKES:
─────────────────────────────────────────────────────────────────────
✗ Ignoring write() return value          → unbounded memory growth
✗ Using .pipe() without error handlers   → unhandled errors, fd leaks
✗ Calling _write's callback() immediately → defeats backpressure
✗ Pushing in Readable without _read call → defeats backpressure
✗ Not handling client 'close' in HTTP    → upstream runs after client gone
✗ highWaterMark too high for large objs  → memory spikes before backpressure
```

## Common Bugs Checklist

Before shipping any code involving Node.js streams or data pipelines, verify:

1. **`write()` return value checked — does your code pause the source when `write()` returns `false`?** — Discarding the return value is the single most common backpressure bug. Even if it "works fine" in testing (small data, fast hardware), it will fail in production with large datasets or slow consumers.

2. **`pipeline()` used instead of chained `.pipe()` for any pipeline with more than 2 streams?** — Every additional `.pipe()` in a chain that lacks `.on('error')` on every intermediate stream is a resource leak waiting to happen. `pipeline()` handles this for free.

3. **Custom Readable: is `_read()` the only place that calls `this.push()`?** — Pushing data from a `'data'` event handler, a timer, or any external callback (rather than from within `_read`) bypasses the backpressure mechanism and causes unbounded buffering.

4. **Custom Writable: does `_write`'s `callback` get called AFTER the actual work is done, not before?** — `callback()` immediately releases the backpressure signal. If called before the work completes, subsequent chunks are queued and processed concurrently, defeating the purpose of the `Writable` interface.

5. **HTTP streaming: is the `'close'` event on `res` handled to cancel the upstream source?** — Without this, a client that disconnects mid-stream still causes the server to keep reading from the database/file/etc., wasting resources. Always wire `res.on('close', () => source.destroy())`.

6. **Object mode `highWaterMark` set appropriately for the object size?** — The default 16 objects is sensible for small objects but can mean 16 × 1MB = 16MB in memory for large objects. Tune `highWaterMark` based on actual object sizes in your application.

7. **`for await...of` loops on a Readable: is the Readable destroyed if the loop exits early (via `break` or exception)?** — In Node.js 14+, `break`ing out of `for await...of` calls the iterator's `return()` method which destroys the stream. In older versions, call `stream.destroy()` explicitly in a `finally` block if exiting early.

8. **Transform streams: does `_transform` always eventually call `callback()` (either on success or error)?** — A `_transform` that never calls `callback()` in some code path will silently stall the entire pipeline forever — no error is thrown, data just stops flowing. Every code path through `_transform` must call `callback()`.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to explain backpressure not just as "pause/resume" mechanics, but as a **flow control mechanism that bounds memory usage** — the fundamental reason it matters is that without it, memory grows proportionally to the speed difference between producer and consumer, and in production with large datasets or slow clients, that means OOM crashes. The three things that signal genuine fluency: (1) immediately naming `pipeline()` (not `pipe()`) as the correct tool; (2) knowing that the `_write` callback timing IS the backpressure signal in custom Writables; and (3) recognizing that `write()` returning `false` is not an error — it's a normal, expected flow control signal that must be acted on, not ignored.
