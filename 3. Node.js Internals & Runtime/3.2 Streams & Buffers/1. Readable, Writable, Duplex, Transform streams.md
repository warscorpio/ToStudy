# Node.js Streams: Readable, Writable, Duplex, Transform — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a stream in Node.js and why does the abstraction exist?**

A: A stream is an abstract interface for working with sequential data that may not be available all at once. Instead of waiting for an entire dataset to load into memory before processing it, a stream lets you work with data in chunks as it arrives — reading, transforming, and writing incrementally.

The motivation is resource efficiency. Consider reading a 4GB log file:

```javascript
// WITHOUT streams — loads entire file into memory first:
const data = fs.readFileSync('app.log');         // 4GB in RAM
const lines = data.toString().split('\n');        // Another 4GB for the string
const errors = lines.filter(l => l.includes('ERROR')); // Iterating 4GB array
// Peak memory: ~12GB for a 4GB file — unworkable on most servers

// WITH streams — constant memory regardless of file size:
const results = [];
fs.createReadStream('app.log', { encoding: 'utf8' })
    .pipe(new LineFilter('ERROR'))               // Process chunk by chunk
    .on('data', line => results.push(line));     // ~64KB in memory at any time
// Peak memory: ~64KB (one chunk) no matter how large the file
```

Streams also model real-world I/O naturally. Network data arrives in TCP packets, not all at once. Disk reads happen in blocks. User input comes keystroke by keystroke. The stream abstraction unifies all of these as a sequence of chunks with a consistent API.

Node.js streams inherit from `EventEmitter` and implement four abstract types — each representing a different direction of data flow:

```
Readable   →  produces data (source)
Writable   ←  consumes data (sink)
Duplex     ↔  produces and consumes independently (e.g., TCP socket)
Transform  →T→ consumes, transforms, and re-emits (e.g., gzip)
```

---

**Q2. What are the four stream types and what real-world things does each model?**

A: Each type maps to a concrete role in a data pipeline:

```
┌────────────────────────────────────────────────────────────────┐
│                     Stream Type Map                            │
│                                                                │
│  [Disk]──ReadStream──▶  [Transform]  ──▶──WriteStream──[Disk] │
│                Readable    Duplex     Writable                  │
│                            Transform                            │
└────────────────────────────────────────────────────────────────┘
```

**Readable** — a source of data. You pull from it or it pushes to you:
- `fs.createReadStream()` — file contents
- `http.IncomingMessage` (server-side `req`) — HTTP request body
- `process.stdin` — keyboard input
- `crypto.createHash()` — not a readable; but `fs.createReadStream()` → hash is readable
- Database query result streams (`pg`'s `QueryStream`, Mongoose `.cursor()`)
- `Readable.from(['a', 'b', 'c'])` — in-memory array as a stream

**Writable** — a sink that consumes data. You write to it:
- `fs.createWriteStream()` — write to a file
- `http.ServerResponse` (server-side `res`) — HTTP response body
- `process.stdout`, `process.stderr` — terminal output
- `crypto.createCipheriv()` result — writable side accepts plaintext

**Duplex** — both readable and writable, but the two sides are independent. Data you write doesn't become data you read:
- `net.Socket` — a TCP socket; you write data to send, you read data received
- `tls.TLSSocket` — same, with encryption
- `WebSocket` — bidirectional messages
- `zlib.createDeflateRaw()` — raw deflate (some zlib streams are Duplex)

**Transform** — a special Duplex where written data is processed and re-emitted on the readable side. What goes in comes out transformed:
- `zlib.createGzip()` — write uncompressed, read compressed
- `crypto.createCipheriv()` — write plaintext, read ciphertext
- `crypto.createHash()` — write data, read the hash digest
- CSV parsers, JSON parsers, line splitters — any data-transformation step

## Section 2: Readable Streams

**Q3. What are the two modes of a Readable stream and how do you switch between them?**

A: Readable streams operate in one of two modes — **flowing** and **paused** — which determine how data is delivered to consumers.

**Paused mode** (default): data is not delivered automatically. You must explicitly call `.read()` to pull chunks. The stream buffers internally until you ask for data.

**Flowing mode**: data is delivered as fast as it arrives, via `'data'` events. The stream does not buffer — if you don't consume fast enough, data is lost (or backpressure kicks in if a pipe is attached).

```javascript
import fs from 'fs';

const readable = fs.createReadStream('data.bin');

// --- PAUSED MODE (default) ---
// Stream starts paused. Pull data manually with .read():
readable.on('readable', () => {
    let chunk;
    // .read(n) pulls up to n bytes; null means no more data available right now
    while ((chunk = readable.read(64 * 1024)) !== null) {
        process(chunk);
    }
});
readable.on('end', () => console.log('Done'));

// --- FLOWING MODE ---
// Activated by attaching a 'data' listener — stream starts pushing immediately:
readable.on('data', (chunk) => {
    process(chunk); // Called for every chunk as soon as it arrives
});
readable.on('end', () => console.log('Done'));
```

**What switches between modes:**

```javascript
// Paused → Flowing:
readable.on('data', handler);  // Attaching 'data' listener starts flow
readable.resume();             // Explicitly start flowing (discards data if no listener)
readable.pipe(writable);       // pipe() puts stream in flowing mode

// Flowing → Paused:
readable.pause();              // Explicitly pause
readable.unpipe();             // Removing all pipe() destinations pauses it
readable.removeListener('data', handler); // Removing last 'data' listener pauses it

// Check current mode:
console.log(readable.readableFlowing);
// null   = not yet decided (default)
// true   = flowing
// false  = paused
```

The practical implication: if you attach a `'data'` listener and then do slow async work in it, you're in flowing mode with no backpressure — the stream keeps emitting chunks into your async handler regardless of how far behind you fall. Use `readable.pause()` / `readable.resume()` manually, or use `pipeline()` which handles this for you.

**Q4. How do you implement a custom Readable stream?**

A: Extend the `Readable` class and implement `_read(size)`. This method is called by the stream internals when the consumer wants more data. Inside `_read`, you push data with `this.push(chunk)` and signal end-of-stream with `this.push(null)`:

```typescript
import { Readable, ReadableOptions } from 'stream';

// Custom Readable: emits paginated API results as a stream
class PaginatedAPIStream extends Readable {
    private page = 1;
    private hasMore = true;
    private fetching = false;

    constructor(
        private readonly fetchPage: (page: number) => Promise<{ items: unknown[]; hasMore: boolean }>,
        options?: ReadableOptions
    ) {
        super({ ...options, objectMode: true }); // objectMode: emit objects, not Buffers
    }

    // _read is called when the consumer is ready for more data (backpressure signal)
    _read(_size: number): void {
        if (this.fetching || !this.hasMore) return;
        this.fetching = true;

        this.fetchPage(this.page)
            .then(({ items, hasMore }) => {
                this.page++;
                this.hasMore = hasMore;
                this.fetching = false;

                for (const item of items) {
                    // push() returns false when internal buffer is full
                    // If false: stop pushing, wait for next _read() call
                    const ok = this.push(item);
                    if (!ok) return; // Backpressure — _read will be called again later
                }

                if (!hasMore) {
                    this.push(null); // Signal: no more data
                }
            })
            .catch(err => {
                this.destroy(err); // Propagate error — 'error' event fires on the stream
            });
    }
}

// Usage:
const stream = new PaginatedAPIStream(async (page) => {
    const res = await fetch(`/api/orders?page=${page}&limit=100`);
    const data = await res.json();
    return { items: data.orders, hasMore: data.hasNextPage };
});

await pipeline(
    stream,
    new Transform({
        objectMode: true,
        transform(order, _, cb) { cb(null, JSON.stringify(order) + '\n'); }
    }),
    fs.createWriteStream('orders.ndjson')
);
```

Key rules for `_read`:
- Never call `_read` yourself — the stream internals call it when ready
- `this.push(chunk)` can be called multiple times before returning from `_read`
- `this.push(null)` signals end-of-stream — no more data after this
- For async operations, call `this.destroy(err)` on failure — don't throw
- `push()` returning `false` means the internal buffer is full — respect it to avoid unbounded memory growth

**Q5. What is `Readable.from()` and when is it useful?**

A: `Readable.from()` creates a Readable stream from any iterable or async iterable — arrays, generators, Maps, Sets, or anything implementing `[Symbol.asyncIterator]`. It's the fastest way to create a Readable without subclassing:

```javascript
import { Readable } from 'stream';

// From a plain array:
const arrayStream = Readable.from(['line1\n', 'line2\n', 'line3\n']);

// From a generator function (lazy — produces values on demand):
function* range(start, end) {
    for (let i = start; i <= end; i++) yield i;
}
const numberStream = Readable.from(range(1, 1_000_000));
// Only generates numbers as they are consumed — O(1) memory

// From an async generator (e.g., DB cursor wrapping):
async function* fetchUsers(db) {
    let cursor = 0;
    while (true) {
        const batch = await db.query(
            'SELECT * FROM users WHERE id > $1 ORDER BY id LIMIT 100',
            [cursor]
        );
        if (batch.rows.length === 0) break;
        for (const row of batch.rows) yield row;
        cursor = batch.rows.at(-1).id;
    }
}

// Stream 10 million users with constant memory:
await pipeline(
    Readable.from(fetchUsers(db), { objectMode: true }),
    new Transform({
        objectMode: true,
        transform(user, _, cb) { cb(null, JSON.stringify(user) + '\n'); }
    }),
    fs.createWriteStream('all-users.ndjson')
);

// Readable.from() with objectMode: true (default for non-Buffer iterables):
const objStream = Readable.from([{ id: 1 }, { id: 2 }]); // objectMode: true by default
```

`Readable.from()` handles backpressure automatically — it won't advance the iterator until the consumer is ready for more data. This makes it safe for large or infinite sequences.

## Section 3: Writable Streams

**Q6. How do you implement a custom Writable stream?**

A: Extend `Writable` and implement `_write(chunk, encoding, callback)`. The callback signals when the current chunk is processed — the stream will not deliver the next chunk until you call it. This is the mechanism for backpressure:

```typescript
import { Writable, WritableOptions } from 'stream';

// Custom Writable: batch-insert records into a database
class BatchInsertStream extends Writable {
    private batch: unknown[] = [];
    private readonly batchSize: number;

    constructor(
        private readonly db: DatabaseClient,
        private readonly table: string,
        options?: WritableOptions & { batchSize?: number }
    ) {
        super({ ...options, objectMode: true });
        this.batchSize = options?.batchSize ?? 500;
    }

    // _write: called for each chunk written to the stream
    _write(record: unknown, _encoding: string, callback: (err?: Error | null) => void): void {
        this.batch.push(record);

        if (this.batch.length >= this.batchSize) {
            this._flush_batch(callback); // Flush when batch is full
        } else {
            callback(); // Not full yet — ready for next record immediately
        }
    }

    // _writev: optional — called when multiple chunks are queued at once (more efficient)
    _writev(
        chunks: Array<{ chunk: unknown; encoding: string }>,
        callback: (err?: Error | null) => void
    ): void {
        this.batch.push(...chunks.map(c => c.chunk));

        if (this.batch.length >= this.batchSize) {
            this._flush_batch(callback);
        } else {
            callback();
        }
    }

    // _final: called when the stream is ending — flush any remaining records
    _final(callback: (err?: Error | null) => void): void {
        if (this.batch.length > 0) {
            this._flush_batch(callback);
        } else {
            callback();
        }
    }

    private _flush_batch(callback: (err?: Error | null) => void): void {
        const toInsert = this.batch;
        this.batch = [];

        this.db.batchInsert(this.table, toInsert)
            .then(() => callback())
            .catch(err => callback(err)); // Error propagates through the stream
    }
}

// Usage: stream 1 million CSV rows into PostgreSQL
await pipeline(
    fs.createReadStream('million-rows.csv'),
    new CSVParser({ objectMode: true }),
    new BatchInsertStream(db, 'events', { batchSize: 1000 }),
);
// Memory: ~1000 records in RAM at a time regardless of CSV size
```

Key rules for `_write`:
- Always call `callback()` exactly once — this is the backpressure signal telling the stream you're ready for the next chunk
- Call `callback(err)` to propagate an error — it surfaces as an `'error'` event on the stream
- `_writev` is optional but efficient — implement it if you want to handle multiple queued chunks at once
- `_final` runs after all `_write` calls complete but before the stream emits `'finish'` — use it to flush state

**Q7. What is the `highWaterMark` and how does it affect backpressure?**

A: `highWaterMark` is the threshold (in bytes for byte streams, in object count for `objectMode`) at which the stream's internal buffer is considered "full." It's the knob that controls how aggressively the stream buffers data before applying backpressure.

```javascript
// Default highWaterMark values:
// Readable:  16384 bytes (16KB)
// Writable:  16384 bytes (16KB)
// objectMode Readable/Writable: 16 objects

// Custom highWaterMark:
const readable = fs.createReadStream('file.bin', { highWaterMark: 64 * 1024 }); // 64KB chunks
const writable = fs.createWriteStream('out.bin', { highWaterMark: 1024 * 1024 }); // 1MB buffer
```

How it drives backpressure:

```javascript
import { Writable } from 'stream';

const sink = new Writable({
    highWaterMark: 3,         // objectMode: buffer up to 3 objects before signaling backpressure
    objectMode: true,
    write(chunk, _, callback) {
        setTimeout(callback, 100); // Simulate slow write (100ms per item)
    }
});

// write() returns false when the internal buffer exceeds highWaterMark:
console.log(sink.write('a')); // true  — buffer: 1/3, not full
console.log(sink.write('b')); // true  — buffer: 2/3, not full
console.log(sink.write('c')); // true  — buffer: 3/3, at limit
console.log(sink.write('d')); // false — buffer OVER limit: backpressure!

// Producer should pause when write() returns false:
sink.once('drain', () => {
    // Buffer drained below highWaterMark — safe to write again
    console.log('drained — resuming');
});
```

Tuning `highWaterMark`:
- **Too low**: frequent pausing and resuming — high overhead, lower throughput
- **Too high**: large memory buffers before backpressure kicks in — throughput increases but memory spikes
- **Matching highWaterMarks** across pipe stages avoids stalls: if the Readable's highWaterMark is 64KB and the Writable's is 16KB, the Writable signals backpressure after 16KB, causing the Readable to buffer up to 64KB before pausing — a 64KB memory spike before the chain slows down

## Section 4: Duplex Streams

**Q8. What is a Duplex stream and how does it differ from a Transform?**

A: A `Duplex` stream is both Readable and Writable, but the two sides are **completely independent**. Data you write to the Writable side does not appear on the Readable side. The two sides communicate through an external mechanism (a network socket, for example).

A `Transform` is a special case of Duplex where the two sides **are connected** — data written to the Writable side is processed and emitted on the Readable side.

```
Duplex:
  write side ──▶ [external system] ──▶ read side
  (TCP socket: you write outgoing bytes, you read incoming bytes — completely separate)

Transform:
  write side ──▶ [_transform function] ──▶ read side
  (Gzip: you write plaintext, the transform function compresses it, you read compressed bytes)
```

```javascript
import net from 'net';

// net.Socket IS a Duplex — classic example:
const socket = net.createConnection({ port: 8080, host: 'api.example.com' });

// Write side — sends data to the remote server:
socket.write('GET /status HTTP/1.1\r\nHost: api.example.com\r\n\r\n');

// Read side — receives data from the remote server (independent of writes):
socket.on('data', (chunk) => {
    console.log('Received:', chunk.toString());
});

// The two sides have nothing to do with each other internally —
// writes go out over TCP, reads come in over TCP, managed by the OS
```

Custom Duplex — when to implement one directly (rather than Transform):

```javascript
import { Duplex } from 'stream';

// A Duplex that wraps a WebSocket: write sends messages, read receives messages
class WebSocketDuplex extends Duplex {
    constructor(private ws: WebSocket) {
        super({ objectMode: true });

        // Wire incoming messages to the readable side:
        ws.on('message', (data) => {
            if (!this.push(data)) {     // Push into readable buffer
                ws.pause?.();           // If buffer full, pause the WS (backpressure)
            }
        });

        ws.on('close', () => this.push(null));  // Signal end of readable
        ws.on('error', (err) => this.destroy(err));
    }

    // Called when consumer wants more data (readable side)
    _read(): void {
        // Data arrives via the 'message' handler above — nothing to do here
        // ws.resume?.() would go here if we paused in the message handler
    }

    // Called when producer writes data (writable side)
    _write(chunk: unknown, _enc: string, callback: () => void): void {
        this.ws.send(chunk, () => callback()); // Send over WebSocket, then signal ready
    }

    _final(callback: () => void): void {
        this.ws.close();
        callback();
    }
}
```

## Section 5: Transform Streams

**Q9. How do you implement a custom Transform stream correctly?**

A: Extend `Transform` and implement `_transform(chunk, encoding, callback)` and optionally `_flush(callback)`. The key difference from Writable's `_write`: you can call `this.push()` to emit data on the readable side before calling `callback()`.

```typescript
import { Transform, TransformCallback, TransformOptions } from 'stream';

// Transform 1: Split a byte stream into lines
class LineSplitter extends Transform {
    private remainder = '';

    constructor(options?: TransformOptions) {
        super({ ...options, readableObjectMode: true }); // Output: strings; Input: Buffers
    }

    _transform(chunk: Buffer, _encoding: string, callback: TransformCallback): void {
        const data = this.remainder + chunk.toString('utf8');
        const lines = data.split('\n');

        // The last element is either empty (chunk ended with \n)
        // or an incomplete line — save it for the next chunk
        this.remainder = lines.pop() ?? '';

        for (const line of lines) {
            this.push(line); // Emit each complete line downstream
        }

        callback(); // Ready for next chunk
    }

    _flush(callback: TransformCallback): void {
        // Stream ended — emit any remaining buffered data
        if (this.remainder.length > 0) {
            this.push(this.remainder);
        }
        callback(); // Signal: transform fully done
    }
}

// Transform 2: Rate-limit a stream (emit at most N items per second)
class RateLimiter extends Transform {
    private count = 0;
    private windowStart = Date.now();

    constructor(
        private readonly maxPerSecond: number,
        options?: TransformOptions
    ) {
        super({ ...options, objectMode: true });
    }

    _transform(chunk: unknown, _enc: string, callback: TransformCallback): void {
        const now = Date.now();

        if (now - this.windowStart >= 1000) {
            // New second window — reset counter
            this.count = 0;
            this.windowStart = now;
        }

        if (this.count < this.maxPerSecond) {
            this.count++;
            this.push(chunk); // Pass through immediately
            callback();
        } else {
            // Delay until next window
            const delay = 1000 - (now - this.windowStart);
            setTimeout(() => {
                this.count = 1;
                this.windowStart = Date.now();
                this.push(chunk);
                callback();
            }, delay);
        }
    }
}

// Transform 3: One-to-many — one input chunk → multiple output chunks
class JSONExpander extends Transform {
    constructor(options?: TransformOptions) {
        super({ ...options, objectMode: true });
    }

    _transform(batch: { items: unknown[] }, _enc: string, callback: TransformCallback): void {
        // One batch object → many individual items
        for (const item of batch.items) {
            this.push(item); // push() can be called multiple times per _transform
        }
        callback(); // Signal done with this chunk
    }
}

// Transform 4: Many-to-one — accumulate until condition met, then emit once
class ChunkAccumulator extends Transform {
    private buffer: Buffer[] = [];
    private size = 0;

    constructor(
        private readonly targetSize: number,
        options?: TransformOptions
    ) {
        super(options);
    }

    _transform(chunk: Buffer, _enc: string, callback: TransformCallback): void {
        this.buffer.push(chunk);
        this.size += chunk.length;

        if (this.size >= this.targetSize) {
            this.push(Buffer.concat(this.buffer)); // Emit one large chunk
            this.buffer = [];
            this.size = 0;
        }
        // push() NOT called if buffer not full — nothing emitted this round
        callback();
    }

    _flush(callback: TransformCallback): void {
        if (this.buffer.length > 0) {
            this.push(Buffer.concat(this.buffer)); // Emit remaining data
        }
        callback();
    }
}
```

The `_transform` / `_flush` contract at a glance:
- `this.push(data)` → zero, one, or many times per `_transform` call — all valid
- `callback()` → exactly once per `_transform` — signals "ready for next chunk"
- `callback(err)` → propagates error through the pipeline
- `_flush` → runs once, after all `_transform` calls, before `'finish'` is emitted
- Never `throw` inside `_transform` or `_flush` — always pass errors to `callback(err)`

**Q10. What is the difference between `readableObjectMode`, `writableObjectMode`, and `objectMode` on a Transform?**

A: By default, streams work with `Buffer` and `string` chunks. `objectMode: true` allows any JavaScript value — objects, arrays, numbers, `null` — to pass through as a single chunk. On a Transform, you can set the mode independently for each side:

```javascript
import { Transform } from 'stream';

// objectMode: true — BOTH sides accept/emit arbitrary JS values
const fullObjectMode = new Transform({
    objectMode: true,
    transform(obj, _, cb) { cb(null, obj); }
});

// readableObjectMode: true — writable side gets Buffers, readable side emits objects
// Classic use case: parse binary/text input into structured objects
const parser = new Transform({
    readableObjectMode: true,    // Output: objects
    // writableObjectMode not set — Input: Buffer/string (default)
    transform(chunk: Buffer, _, cb) {
        try {
            cb(null, JSON.parse(chunk.toString())); // Buffer in, object out
        } catch (err) {
            cb(err as Error);
        }
    }
});

// writableObjectMode: true — writable side accepts objects, readable side emits Buffers
// Classic use case: serialize objects to bytes/strings for writing to a file or network
const serializer = new Transform({
    writableObjectMode: true,    // Input: objects
    // readableObjectMode not set — Output: Buffer/string (default)
    transform(obj: Record<string, unknown>, _, cb) {
        cb(null, JSON.stringify(obj) + '\n'); // Object in, string out
    }
});

// Real-world pipeline showing mixed modes:
await pipeline(
    fs.createReadStream('events.ndjson'),   // Buffer output
    new LineSplitter(),                      // Buffer in, string out (readableObjectMode)
    parser,                                  // string in, object out (readableObjectMode)
    new Transform({                          // object in, object out (objectMode)
        objectMode: true,
        transform(event, _, cb) {
            cb(null, { ...event, processedAt: Date.now() });
        }
    }),
    serializer,                              // object in, string out (writableObjectMode)
    fs.createWriteStream('processed.ndjson') // string in
);
// Each stage has the right mode for its role — no manual Buffer.toString() calls
```

Mode mismatch is a common bug — passing an object through a non-objectMode stream converts it to `[object Object]` silently. Always check that adjacent stream stages agree on their chunk type.

## Section 6: Stream Internals and Backpressure

**Q11. Walk through exactly what happens when backpressure propagates through a pipeline.**

A: Backpressure is the signal that a slow consumer sends upstream to a fast producer — "slow down, I'm full." Here's the exact sequence when it kicks in:

```
Producer (Readable) → Transform → Consumer (Writable: slow disk write)

Step-by-step when the Writable's buffer fills:

1. Producer pushes chunks faster than Consumer can write
2. Consumer.write(chunk) returns false — internal buffer exceeds highWaterMark
3. pipeline() (or pipe()) sees the false return value
4. pipeline() calls Transform.pause() — stops Transform from pulling from Producer
5. Transform's internal readable buffer starts filling
6. Transform's writable side signals backpressure to Producer via pause()
7. Producer._read() is no longer called — Producer stops generating data
8. Consumer drains its buffer (writes complete, OS flushes)
9. Consumer emits 'drain' event
10. pipeline() calls Transform.resume()
11. Transform starts pulling from Producer again
12. Producer._read() is called — data flows again
```

Visualizing the buffer states:

```
Normal flow:
Producer [▓▓░░░░░░] → Transform [▓░░░░░░░] → Consumer [▓░░░░░░░]
          buffer 25%              buffer 12%              buffer 12%
          All below highWaterMark — flow continues

Backpressure:
Producer [▓▓░░░░░░] → Transform [▓▓▓▓░░░░] → Consumer [▓▓▓▓▓▓▓▓]
          PAUSED                 filling                  FULL (hwm exceeded)
          _read() not called                              write() returned false

Draining:
Producer [PAUSED  ] → Transform [▓▓▓░░░░░] → Consumer [▓▓░░░░░░]
                                draining                 draining → 'drain' fires
                                                         → Transform.resume()
                                                         → Producer._read() called again
```

You can observe this directly:

```javascript
import { Writable, Readable } from 'stream';

const producer = new Readable({
    read() {
        const chunk = Buffer.alloc(1024); // 1KB at a time
        const ok = this.push(chunk);
        console.log(`Pushed chunk, buffer ok: ${ok}`);
    }
});

const consumer = new Writable({
    highWaterMark: 4096, // 4KB buffer — fills after 4 chunks
    write(chunk, _, callback) {
        setTimeout(callback, 50); // Simulate slow disk: 50ms per chunk
    }
});

producer.pipe(consumer);
// Watch: after ~4 chunks, producer's push() returns false, flow pauses
// Every 50ms a chunk is written, 'drain' fires, flow resumes
```

**Q12. How do streams handle the `'end'`, `'finish'`, and `'close'` events — what's the difference?**

A: Three distinct events signal different lifecycle stages across Readable and Writable streams:

```
'end'    — Readable: all data has been consumed by the reader
'finish' — Writable: all data has been flushed to the underlying resource
'close'  — Either:  the underlying resource (file descriptor, socket) has been closed
```

```javascript
import fs from 'fs';

const readable = fs.createReadStream('input.txt');
const writable = fs.createWriteStream('output.txt');

readable
    .on('data', chunk => writable.write(chunk))
    .on('end', () => {
        // ALL data has been READ by the consumer
        // The readable stream is exhausted — no more 'data' events
        // The writable may NOT be done yet — data might still be flushing
        console.log('readable: all data read');
        writable.end(); // Signal: no more writes coming
    })
    .on('close', () => {
        // The file descriptor for input.txt has been closed
        // Fires after 'end' (for normal completion) or after destroy()
        console.log('readable: fd closed');
    });

writable
    .on('finish', () => {
        // ALL data has been FLUSHED to disk (or OS buffer)
        // Fires after writable.end() is called AND all _write/_final callbacks complete
        // This is when you know the data is safely written
        console.log('writable: all data flushed');
    })
    .on('close', () => {
        // The file descriptor for output.txt has been closed
        // Fires after 'finish'
        console.log('writable: fd closed');
    });

// Event order for a successful pipeline:
// readable 'data' × N
// readable 'end'
// writable 'finish'
// readable 'close'
// writable 'close'

// Event order when destroyed (e.g., error):
// readable 'error'  (or writable 'error')
// readable 'close'  (destroy() closes the fd)
// writable 'close'
// 'finish' is NOT emitted on an errored/destroyed writable
```

Common mistake — checking `'end'` instead of `'finish'` for write completion:

```javascript
// WRONG: readable 'end' fires before writable finishes
readable.pipe(writable);
readable.on('end', () => {
    // Writable may still be writing! Data not fully flushed.
    fs.rename('output.txt', 'final.txt', callback); // Race condition!
});

// CORRECT: wait for writable 'finish'
readable.pipe(writable);
writable.on('finish', () => {
    // All data flushed — safe to rename
    fs.rename('output.txt', 'final.txt', callback);
});

// BEST: use pipeline() and await — it resolves after 'finish' on the last stream
await pipeline(readable, writable);
// Safe to rename here
await fs.promises.rename('output.txt', 'final.txt');
```

## Section 7: Advanced Patterns

**Q13. How do you compose multiple Transform streams into a reusable pipeline factory?**

A: Composing streams into reusable units avoids repeating long `pipeline()` calls. `stream.compose()` (Node.js 16+) and `PassThrough` chaining are two approaches:

```typescript
import { compose, Transform, PassThrough } from 'stream';
import { pipeline } from 'stream/promises';

// Individual reusable transforms:
const createDecompressor = () => zlib.createGunzip();

const createJSONParser = () => new Transform({
    readableObjectMode: true,
    transform(chunk, _, cb) {
        try { cb(null, JSON.parse(chunk.toString())); }
        catch (e) { cb(e as Error); }
    }
});

const createValidator = (schema: Schema) => new Transform({
    objectMode: true,
    transform(obj, _, cb) {
        const result = schema.safeParse(obj);
        if (result.success) cb(null, result.data);
        else cb(new ValidationError(result.error));
    }
});

const createSerializer = () => new Transform({
    writableObjectMode: true,
    transform(obj, _, cb) { cb(null, JSON.stringify(obj) + '\n'); }
});

// stream.compose() — wraps multiple transforms into one reusable Duplex:
// Input to the composed stream = input to first stage
// Output of the composed stream = output of last stage
const createProcessingPipeline = (schema: Schema) =>
    compose(
        createDecompressor(),    // Buffer → Buffer (decompressed)
        createJSONParser(),      // Buffer → Object
        createValidator(schema), // Object → Object (validated)
        createSerializer()       // Object → string
    );

// Now use the composed pipeline as a single Transform anywhere:
await pipeline(
    fs.createReadStream('data.json.gz'),
    createProcessingPipeline(UserSchema),
    fs.createWriteStream('validated.ndjson')
);

// Reuse the same composition with a different source/sink:
await pipeline(
    httpResponse,                        // HTTP response body
    createProcessingPipeline(UserSchema),
    dbWriteStream,                       // DB insert sink
);

// Alternative for Node.js < 16: manual PassThrough chaining
function createProcessingPipelineCompat(schema: Schema) {
    const entry = new PassThrough(); // Entry point
    const exit = entry               // Exit point (chain returns last stream)
        .pipe(createDecompressor())
        .pipe(createJSONParser())
        .pipe(createValidator(schema))
        .pipe(createSerializer());

    // Expose both ends as a { writable, readable } pair
    return { writable: entry, readable: exit };
}
```

**Q14. How do you use streams in an async iteration context — `for await...of` on a Readable?**

A: Node.js Readable streams implement `Symbol.asyncIterator`, making them directly consumable with `for await...of`. This is often cleaner than event listeners for simple consumption patterns:

```typescript
import fs from 'fs';
import readline from 'readline';

// for await...of on a Readable — paused mode, one chunk per iteration:
async function countLines(filePath: string): Promise<number> {
    const stream = fs.createReadStream(filePath, { encoding: 'utf8' });
    let count = 0;

    for await (const chunk of stream) {
        // chunk is a string (because encoding: 'utf8' specified)
        count += (chunk.match(/\n/g) ?? []).length;
    }
    // Stream is automatically cleaned up when the loop exits
    return count;
}

// Error handling: try/catch works naturally
async function processFile(path: string): Promise<void> {
    try {
        for await (const chunk of fs.createReadStream(path)) {
            processChunk(chunk);
        }
    } catch (err) {
        // Covers both stream errors AND errors thrown inside the loop body
        console.error('Failed:', err);
        // Stream is destroyed automatically when the for-await loop exits on error
    }
}

// readline.createInterface is also async iterable — line by line:
async function parseLogFile(path: string): Promise<ErrorEntry[]> {
    const fileStream = fs.createReadStream(path);
    const rl = readline.createInterface({ input: fileStream, crlfDelay: Infinity });

    const errors: ErrorEntry[] = [];

    for await (const line of rl) {
        // One complete line per iteration — no manual split/buffer logic
        if (line.includes('ERROR')) {
            errors.push(parseLine(line));
        }
    }

    return errors; // rl and fileStream are cleaned up automatically
}

// Early exit: break destroys the stream (no fd leak)
async function findFirst(path: string, predicate: (line: string) => boolean): Promise<string | null> {
    const rl = readline.createInterface({
        input: fs.createReadStream(path)
    });

    for await (const line of rl) {
        if (predicate(line)) {
            rl.close(); // Explicitly close before break — closes underlying stream
            return line;
        }
    }
    return null;
}
```

One caveat: when using `for await...of` on a stream and you `break` or `throw` early, always close or destroy the underlying stream explicitly. The `for await...of` protocol calls `.return()` on the iterator, which destroys the stream in most cases — but calling `rl.close()` or `stream.destroy()` explicitly is safer and more readable.

## Section 8: Scenario-Based Questions

**Q15. "What's wrong with this Transform implementation? How would you fix it?"**

```javascript
class UpperCaseTransform extends Transform {
    _transform(chunk, encoding, callback) {
        const upper = chunk.toString().toUpperCase();
        this.push(upper);
        // callback not called
    }
}
```

A: The bug is the missing `callback()` call. The Transform stream uses `callback` as its backpressure signal — calling it tells the stream "I'm done processing this chunk, send me the next one." Without it:

```javascript
// What happens:
const transform = new UpperCaseTransform();
const writable = fs.createWriteStream('out.txt');

fs.createReadStream('input.txt')
    .pipe(transform)
    .pipe(writable);

// First chunk arrives → _transform called → 'upper' pushed downstream → callback NOT called
// Stream waits for callback before sending chunk 2...
// ...forever. The pipeline stalls after the first chunk.
// No error is thrown — it just silently stops processing
// This is one of the hardest stream bugs to debug because it's completely silent

// Fix:
class UpperCaseTransform extends Transform {
    _transform(chunk, encoding, callback) {
        try {
            const upper = chunk.toString().toUpperCase();
            this.push(upper);
            callback(); // ← Must call to allow next chunk
        } catch (err) {
            callback(err); // ← Errors must go to callback, not throw
        }
    }
}

// Or more concisely — pass result directly to callback as second argument:
class UpperCaseTransform extends Transform {
    _transform(chunk, encoding, callback) {
        callback(null, chunk.toString().toUpperCase());
        // callback(error, data) — equivalent to this.push(data); callback()
        // Only valid for single-push transforms (not one-to-many)
    }
}
```

**Q16. "Design a streaming ETL pipeline: read from a CSV, validate rows, enrich from a Redis cache, and write valid rows to Postgres and invalid rows to a separate error log."**

A: This is a fan-out pipeline — one source, two sinks, with conditional routing:

```typescript
import { pipeline } from 'stream/promises';
import { Transform, PassThrough, Writable } from 'stream';
import fs from 'fs';
import { parse } from 'csv-parse';
import { createClient } from 'redis';
import { Pool } from 'pg';

const redis = createClient();
const pg = new Pool();
await redis.connect();

// Stage 1: Parse CSV → objects
const csvParser = parse({ columns: true, trim: true });

// Stage 2: Validate each row
class RowValidator extends Transform {
    constructor(
        private validSink: Writable,
        private invalidSink: Writable
    ) {
        super({ objectMode: true });
    }

    _transform(row: Record<string, string>, _, callback: TransformCallback): void {
        const errors = validateRow(row); // Returns string[] of error messages

        if (errors.length === 0) {
            // Valid: pass downstream for enrichment
            callback(null, row);
        } else {
            // Invalid: write to error log directly, don't pass downstream
            const errorEntry = JSON.stringify({ row, errors }) + '\n';
            const ok = this.invalidSink.write(errorEntry);
            if (!ok) {
                // Backpressure from error log — wait for drain before continuing
                this.invalidSink.once('drain', callback);
            } else {
                callback(); // Push nothing — invalid row dropped from main flow
            }
        }
    }
}

// Stage 3: Enrich with Redis lookups
class RedisEnricher extends Transform {
    constructor(private redis: RedisClient) {
        super({ objectMode: true });
    }

    async _transform(row: Record<string, string>, _, callback: TransformCallback) {
        try {
            const metadata = await this.redis.hGetAll(`product:${row.product_id}`);
            callback(null, { ...row, ...metadata });
        } catch (err) {
            // Enrichment failure: pass row through without enrichment
            callback(null, row);
        }
    }
}

// Stage 4: Batch insert to PostgreSQL
class PGBatchWriter extends Writable {
    private batch: Record<string, unknown>[] = [];

    constructor(private pg: Pool, private batchSize = 500) {
        super({ objectMode: true });
    }

    _write(row: Record<string, unknown>, _, callback: TransformCallback): void {
        this.batch.push(row);
        if (this.batch.length >= this.batchSize) {
            this._flush_batch(callback);
        } else {
            callback();
        }
    }

    _final(callback: TransformCallback): void {
        if (this.batch.length > 0) this._flush_batch(callback);
        else callback();
    }

    private _flush_batch(callback: TransformCallback): void {
        const rows = this.batch.splice(0);
        insertBatch(this.pg, rows)
            .then(() => callback())
            .catch(callback);
    }
}

// Wire it all together:
const errorLog = fs.createWriteStream('errors.ndjson');
const pgWriter = new PGBatchWriter(pg);
const validator = new RowValidator(pgWriter, errorLog);

// Main pipeline: CSV → parse → validate+route → enrich → PG
// Invalid rows branch off inside RowValidator directly to errorLog
await pipeline(
    fs.createReadStream('import.csv'),
    csvParser,
    validator,
    new RedisEnricher(redis),
    pgWriter
);

// Close error log after pipeline completes
await new Promise<void>((resolve, reject) =>
    errorLog.end(err => err ? reject(err) : resolve())
);

await redis.disconnect();
await pg.end();
```

The fan-out here is handled inside `RowValidator`: invalid rows are written directly to `errorLog` (a separate Writable), while valid rows flow downstream. The backpressure from `errorLog` is manually respected by checking `invalidSink.write()` return value and waiting for `'drain'` before calling `callback()` — preventing the main pipeline from outrunning the error log.

## Quick Reference Table

| Stream Type | Readable | Writable | Key Method | `objectMode` Default | Common Examples |
|---|---|---|---|---|---|
| `Readable` | ✅ | ❌ | `_read(size)` | `false` | `fs.createReadStream`, `http.IncomingMessage`, `Readable.from()` |
| `Writable` | ❌ | ✅ | `_write(chunk, enc, cb)` | `false` | `fs.createWriteStream`, `http.ServerResponse`, `process.stdout` |
| `Duplex` | ✅ | ✅ (independent) | `_read()` + `_write()` | `false` | `net.Socket`, `tls.TLSSocket`, WebSocket wrappers |
| `Transform` | ✅ | ✅ (connected) | `_transform(chunk, enc, cb)` + `_flush(cb)` | `false` | `zlib.createGzip()`, `crypto.createCipheriv()`, CSV parsers |

| Event | Fires on | Meaning |
|---|---|---|
| `'data'` | Readable | A chunk is available (flowing mode) |
| `'readable'` | Readable | Data is available to `.read()` (paused mode) |
| `'end'` | Readable | All data has been consumed |
| `'finish'` | Writable | All data has been flushed to the underlying resource |
| `'close'` | Both | Underlying resource (fd, socket) closed |
| `'error'` | Both | An error occurred — stream is unusable |
| `'drain'` | Writable | Buffer drained below `highWaterMark` — safe to write again |
| `'pipe'` | Writable | A Readable was piped to this Writable |
| `'unpipe'` | Writable | A Readable was unpiped |

---

**Tip for interviews:** Six things separate strong candidates on this topic: (1) knowing that **Duplex and Transform are different** despite both being readable + writable — a Duplex's two sides are independent (TCP socket: you write outgoing data, you read incoming data), while a Transform connects them (gzip: you write plaintext, you read compressed bytes); (2) understanding the **`_transform` callback contract precisely** — it must be called exactly once, errors go to `callback(err)` not `throw`, and `this.push()` can be called zero or many times before calling it — missing the callback silently stalls the pipeline with no error thrown; (3) being able to explain **backpressure end-to-end** — `write()` returning `false`, the `'drain'` event, `pause()`/`resume()` on Readable, and how `pipeline()` wires this automatically; (4) knowing the **difference between `'end'`, `'finish'`, and `'close'`** — confusing `'end'` (readable consumed) with `'finish'` (writable flushed) is a race condition that causes data loss in production; (5) understanding **mixed objectMode** — `readableObjectMode` vs `writableObjectMode` vs `objectMode` on a Transform, and that mode mismatch between adjacent stages silently converts objects to `[object Object]`; and (6) knowing that **`for await...of` works on Readable streams** and that `break`ing early requires explicitly destroying the stream — this is increasingly the idiomatic way to consume streams in modern Node.js and shows familiarity with the async iteration protocol.
