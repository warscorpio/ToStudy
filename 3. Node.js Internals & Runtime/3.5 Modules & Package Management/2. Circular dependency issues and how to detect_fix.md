# Circular Dependency Issues: Detection and Fixes — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is a circular dependency and why does it occur?**
A: A circular dependency exists when module A depends on module B and — directly or through a chain — module B depends back on module A. The dependency graph contains a cycle.

```
Direct cycle (A → B → A):
  a.js: import { foo } from './b'
  b.js: import { bar } from './a'

Indirect cycle (A → B → C → A):
  a.js: import { foo } from './b'
  b.js: import { baz } from './c'
  c.js: import { bar } from './a'    ← closes the cycle back to A
```

Circular dependencies are not always bugs in isolation — the module system *allows* them — but they reliably produce one of three failure modes:

1. **`undefined` exports at runtime** (CommonJS): module A is required while it is still being initialized, so the exports object is partially populated. Module B receives `undefined` for values that haven't been assigned yet.

2. **Temporal Dead Zone errors** (ESM): a `const` or `let` binding from a circularly dependent module is accessed before it has been initialized, throwing `ReferenceError: Cannot access 'X' before initialization`.

3. **Silent wrong behavior**: the module loads without throwing, but functions close over stale or `undefined` references, producing incorrect results at runtime rather than at import time.

Circular dependencies typically emerge from **architectural drift**: modules that started with a clear separation of concerns accumulate cross-references as features are added. The most common root cause is a "utility" or "shared" module that begins importing from the business-logic modules it originally served.

**Q2. How does CommonJS (`require()`) handle circular dependencies at the module-loading level?**
A: CommonJS uses a **module registry** (cache) keyed by resolved file path. When `require('./a')` is called, Node.js:

1. Checks the cache. If the module is already there, return `module.exports` immediately.
2. If not cached: create a new `Module` object with an empty `exports = {}`, **add it to the cache**, then execute the file.

The critical detail: the module is added to the cache **before its code runs**. This is what allows cycles to not infinite-loop — but it is also what causes the partial initialization problem.

```
Execution order with A → B → A cycle:

Step 1: require('./a')
  Cache: {}
  → Create module A: exports = {}
  → Add to cache: { './a': { exports: {} } }
  → Start executing a.js...

Step 2: a.js line 1: const B = require('./b')
  Cache: { './a': { exports: {} } }
  → Create module B: exports = {}
  → Add to cache: { './a': {...}, './b': { exports: {} } }
  → Start executing b.js...

Step 3: b.js line 1: const A = require('./a')
  Cache HIT → return current module.exports of A = {}    ← A is INCOMPLETE
  B receives: A = {}      ← A's exports are an empty object — nothing assigned yet

Step 4: b.js continues executing...
  module.exports.foo = 'hello';
  → cache: './b': { exports: { foo: 'hello' } }
  → b.js done

Step 5: a.js continues (require('./b') returned { foo: 'hello' })
  module.exports.bar = 'world';
  → cache: './a': { exports: { bar: 'world' } }
  → a.js done

Result:
  B captured A at Step 3 → A was {} → B.capturedA = {} (not { bar: 'world' })
  A captured B at Step 4 → B was { foo: 'hello' } → A.capturedB = { foo: 'hello' }

  Whoever required A first gets the complete { bar: 'world' }
  But B's reference to A is forever stuck at {}
```

**Q3. How does ES Modules (ESM) handle circular dependencies differently from CommonJS?**
A: ESM uses **live bindings** — fundamentally different from CommonJS's value-copy approach. When ESM imports a name from another module, it does not get a copy of the value at import time. It gets a **live reference to the binding** in the exporting module's scope. When the exporting module's binding is later assigned, all importers see the updated value through the reference.

ESM loading happens in three distinct phases:

```
Phase 1 — Construction (parse, build module graph, detect cycles):
  All module files are parsed. Import/export statements are resolved.
  A module record is created for every module. Cycles are detected here.
  No code executes in this phase.

Phase 2 — Instantiation (allocate bindings, wire live references):
  For every export, an uninitialized binding slot is allocated.
  Importing modules receive a live reference to that slot.
  The binding slot exists but has no value yet (in TDZ for let/const).

Phase 3 — Evaluation (execute module bodies in post-order):
  Modules execute in depth-first post-order (dependencies before dependents).
  As each module executes, it assigns values to its binding slots.
  Any importer that reads the slot after assignment sees the correct value.
  Any importer that reads the slot BEFORE the exporter runs → TDZ error.
```

```js
// ESM cycle: a.mjs and b.mjs

// a.mjs:
import { foo } from './b.mjs';
export const bar = 'world';
export function usesFoo() { return foo; } // function — safe: evaluated lazily

// b.mjs:
import { bar } from './a.mjs';
export const foo = 'hello';
console.log(bar); // ← DANGER: is a.mjs's bar initialized yet?

// Evaluation order: b.mjs evaluates first (it's a dependency of a.mjs's importer)
// When b.mjs runs: bar binding exists (live ref) but a.mjs hasn't run yet
// console.log(bar) → ReferenceError: Cannot access 'bar' before initialization

// BUT: usesFoo() is safe because it is called AFTER both modules finish evaluating:
// a.mjs's usesFoo references foo via live binding → by call time, foo is assigned
```

The key distinction: CommonJS gives you a **snapshot copy** of exports at require-time (often incomplete). ESM gives you a **live reference** to a binding that may or may not be initialized when accessed, depending on execution order.

**Q4. What is the "exports object mutation" pattern in CommonJS that partially avoids circular dependency bugs?**
A: Instead of reassigning `module.exports`, mutate the original exports object by adding properties to it. Since both sides of the cycle hold a reference to the **same object**, properties added later are visible to earlier requirers through the shared reference.

```js
// ❌ Reassignment pattern — breaks with circular deps:
// a.js
const { baz } = require('./b');
module.exports = { bar: 'world' }; // ← REPLACES the exports object
// b.js got a reference to the OLD empty object — not this new one

// ✓ Mutation pattern — works with circular deps:
// a.js
const { baz } = require('./b');
module.exports.bar = 'world';      // ← MUTATES the shared exports object
// b.js holds a reference to this same object → b.js.capturedA.bar is now 'world'
// BUT: only if b.js accesses capturedA.bar AFTER a.js finishes executing

// Demonstration:
// a.js
const B = require('./b');
exports.bar = function() { return 'bar from A'; };
// Notice: using `exports.bar =` not `module.exports = { bar: ... }`

// b.js
const A = require('./a');
exports.baz = function() {
  return A.bar(); // accessed at CALL TIME, not at require-time
                  // by call time, a.js has finished → A.bar is defined ✓
};

// WORKS because:
// A.bar is not accessed at require time (line 2 of b.js)
// It's accessed inside a function body — called later, after all modules load
// This is the "lazy access" pattern for breaking circular dep bugs
```

### Section 2: Detection

**Q5. What tools exist to detect circular dependencies and what are their trade-offs?**
A: Detection approaches fall into three layers — static analysis (before runtime), bundler plugins (at build time), and runtime detection (during execution).

**Static analysis — `madge`**:
```bash
# Install:
npm install -D madge

# List all circular dependency chains:
npx madge --circular src/

# Generate a visual graph (requires graphviz):
npx madge --circular --image graph.svg src/

# Target TypeScript projects:
npx madge --circular --ts-config tsconfig.json --extensions ts,tsx src/

# Output:
# Circular dependency found!
# services/user.ts → services/auth.ts → services/user.ts
# utils/format.ts → utils/date.ts → utils/string.ts → utils/format.ts
```

**ESLint — `eslint-plugin-import` `no-cycle` rule**:
```json
// .eslintrc.json
{
  "plugins": ["import"],
  "rules": {
    "import/no-cycle": ["error", {
      "maxDepth": 10,       // only detect cycles up to depth 10 (performance)
      "ignoreExternal": true // ignore node_modules cycles (common, usually harmless)
    }]
  }
}
// Runs on every lint pass → catches cycles as they're introduced, not just in CI
// Best for: preventing NEW cycles; slow on very large codebases (O(edges²) worst case)
```

**Webpack — `circular-dependency-plugin`**:
```js
// webpack.config.js
const CircularDependencyPlugin = require('circular-dependency-plugin');

module.exports = {
  plugins: [
    new CircularDependencyPlugin({
      exclude: /node_modules/,     // skip third-party
      include: /src/,              // only check our code
      failOnError: true,           // break the build on any cycle
      allowAsyncCycles: false,     // treat dynamic import cycles as errors too
      cwd: process.cwd(),
      onDetected({ module, paths, compilation }) {
        compilation.errors.push(new Error(paths.join(' → ')));
      },
    }),
  ],
};
```

**Vite / Rollup — `rollup-plugin-circular-dependency`** or built-in warnings:
```js
// vite.config.ts
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    rollupOptions: {
      onwarn(warning, warn) {
        if (warning.code === 'CIRCULAR_DEPENDENCY') {
          throw new Error(warning.message); // fail build on circular dep
        }
        warn(warning);
      },
    },
  },
});
// Rollup natively detects and warns on circular dependencies
```

**Runtime detection in Node.js**:
```js
// Node.js prints a warning for CommonJS circular deps:
// (node:12345) Warning: Circular dependency detected: a.js -> b.js -> a.js
// Enable with:
node --trace-warnings server.js

// Or programmatically — wrap require to detect cycles:
const originalRequire = Module.prototype.require;
const loading = new Set();

Module.prototype.require = function(id) {
  const resolved = require.resolve(id);
  if (loading.has(resolved)) {
    console.warn(`CIRCULAR DEPENDENCY: ${resolved}`);
    console.trace(); // print the require stack
  }
  loading.add(resolved);
  try {
    return originalRequire.apply(this, arguments);
  } finally {
    loading.delete(resolved);
  }
};
```

**Trade-off summary:**

| Tool | When it runs | False positives | Performance | Best for |
|---|---|---|---|---|
| `eslint-plugin-import/no-cycle` | Per-file on save | Low | Slow on large codebases | Preventing new cycles |
| `madge` | Manual / CI | None | Fast (one-shot) | Auditing existing codebase |
| `circular-dependency-plugin` | Every build | None | Medium | CI enforcement |
| Rollup `onwarn` | Build | None | Fast | Vite / Rollup projects |
| `--trace-warnings` | Runtime | None | Zero | Debugging existing cycles |

**Q6. How do you read a circular dependency chain report and prioritize which cycles to fix?**
A: A cycle report lists chains; the question is which ones cause runtime bugs vs which are structurally harmless.

```
Example madge output:
  1) src/services/UserService.ts
       → src/services/AuthService.ts
       → src/services/UserService.ts          ← 2-node cycle

  2) src/utils/format.ts
       → src/utils/date.ts
       → src/utils/string.ts
       → src/utils/format.ts                  ← 3-node cycle

  3) src/components/Header.tsx
       → src/store/userSlice.ts
       → src/store/index.ts
       → src/store/rootReducer.ts
       → src/components/Header.tsx            ← 4-node cycle, likely a store re-export issue

Prioritization:
  High risk (fix immediately):
    → Cycles involving CLASSES or MODULE-LEVEL VALUE REFERENCES
    → Any cycle where A accesses B's export at module evaluation time (not inside a function)
    → Cycles in the critical startup path (modules loaded first)

  Lower risk (fix when convenient):
    → Cycles where all cross-references are inside function bodies
      (by the time the function is called, all modules have finished loading)
    → Cycles in lazily loaded modules (dynamic import — loaded on demand, after startup)
    → Type-only cycles (TypeScript `import type` — erased at compile time, no runtime effect)
```

```ts
// Distinguishing runtime-safe from runtime-dangerous cycles:

// DANGEROUS: value accessed at module evaluation time:
// serviceA.ts
import { helperFromB } from './serviceB';
export const result = helperFromB('init'); // ← called at module load → helperFromB may be undefined

// SAFE: value accessed inside a function body:
// serviceA.ts
import { helperFromB } from './serviceB';
export function doWork() {
  return helperFromB('runtime'); // ← called after all modules loaded → helperFromB is defined
}

// SAFE in TypeScript: import type (zero runtime existence):
import type { UserDTO } from './UserService'; // erased at compile time
// No runtime cycle — TypeScript strips all `import type` before emitting JS
```

### Section 3: Fix Patterns

**Q7. What is the "extract to shared module" pattern and when does it apply?**
A: The most common root cause of cycles is two modules that each need a type, constant, or utility that the other also defines — creating a situation where both reach into each other. The fix is to extract the shared dependency into a **third module** that neither A nor B defines but both import from.

```
Before (cycle):
  UserService.ts ──imports──► AuthService.ts
       ▲                             │
       └──────────imports────────────┘

Why the cycle exists:
  UserService needs: AuthService.validateToken()
  AuthService needs: UserService.getUserById()  (to validate the token's user)

After (extract shared types/interfaces):
  UserService.ts ──imports──► IUserRepository.ts ◄── AuthService.ts
  UserService.ts ──────────────────────────────────► AuthService.ts
  (one-way: UserService imports Auth, but Auth only imports the interface)
```

```ts
// Before — cycle:
// user.service.ts
import { AuthService } from './auth.service';
export class UserService {
  constructor(private auth: AuthService) {}
  findById(id: string) { /* ... */ }
  getProfile(token: string) {
    this.auth.validate(token);
  }
}

// auth.service.ts
import { UserService } from './user.service'; // ← creates cycle
export class AuthService {
  constructor(private users: UserService) {}
  validate(token: string) {
    const userId = decodeToken(token);
    return this.users.findById(userId); // needs UserService
  }
}

// After — extract interface to break cycle:
// user.repository.interface.ts  ← new shared module (no deps on user or auth)
export interface IUserRepository {
  findById(id: string): Promise<User | null>;
}

// user.service.ts  ← unchanged, still imports AuthService
import { AuthService } from './auth.service';
export class UserService implements IUserRepository {
  constructor(private auth: AuthService) {}
  findById(id: string) { /* ... */ }
}

// auth.service.ts  ← now imports INTERFACE only, not UserService
import { IUserRepository } from './user.repository.interface'; // no cycle!
export class AuthService {
  constructor(private users: IUserRepository) {}
  validate(token: string) {
    const userId = decodeToken(token);
    return this.users.findById(userId); // works via interface
  }
}
// Cycle eliminated: AuthService depends on an interface, not on UserService
// Dependency graph is now a DAG (directed acyclic graph)
```

**Q8. What is the lazy require / dynamic import pattern and when is it the right fix?**
A: Instead of importing at the top of the file (module evaluation time), defer the import to inside a function body (call time). By call time, all modules have finished initializing, so the circular dependency resolves to a complete module.

In CommonJS, this is a `require()` call inside a function. In ESM, this is a dynamic `import()`.

```js
// CommonJS — lazy require (inline require inside a function):
// ❌ Before: top-level require causes partial initialization:
const { processOrder } = require('./orderService'); // orderService requires back → undefined

function handleCheckout(cart) {
  return processOrder(cart); // processOrder is undefined — called on partially initialized module
}

// ✓ After: lazy require inside function body:
function handleCheckout(cart) {
  const { processOrder } = require('./orderService'); // require runs at CALL time
  // By now, all modules are fully loaded → processOrder is defined
  return processOrder(cart);
}
// Note: require() is cached — subsequent calls return the cached module (no re-execution)
// Performance impact: first call has cache lookup overhead (~microseconds) — negligible
```

```ts
// ESM — dynamic import (lazy):
// ❌ Before: static import at top — evaluated before module is ready:
import { generateReport } from './reportService'; // may be undefined in cycle

// ✓ After: dynamic import inside async function:
async function onRequestReport(params: ReportParams) {
  const { generateReport } = await import('./reportService');
  // import() resolves AFTER all statically imported modules have evaluated
  return generateReport(params);
}
```

When to use lazy import vs extract-to-shared-module:

```
Lazy import is appropriate when:
  → The dependency is only needed in one function / code path (not all callers)
  → The cycle is genuinely bi-directional with no obvious "shared thing" to extract
  → You're fixing an urgent production bug and need a minimal-diff fix
  → The imported module is large and deferring it improves startup time (bonus)

Lazy import is NOT appropriate when:
  → The dependency is needed at class construction time (can't defer)
  → The import is used in many places (lazy require scattered everywhere = unreadable)
  → You're in a TypeScript codebase with strict noImplicitAny — type inference breaks
  → The real fix is architectural (lazy import is a band-aid, not a cure)
```

**Q9. What is the dependency inversion principle (DIP) and how does it eliminate circular dependencies structurally?**
A: The Dependency Inversion Principle states: high-level modules should not depend on low-level modules; both should depend on **abstractions** (interfaces). Abstractions should not depend on details; details should depend on abstractions.

Applied to circular dependencies: when A and B depend on each other, the cycle exists because at least one of them is a "concrete detail" that the other reaches into directly. By introducing an interface/abstraction, one of the directions in the cycle becomes a dependency on an abstraction — which can live in a third module with no imports from either A or B.

```ts
// Cycle: PaymentService ↔ OrderService
// PaymentService.processPayment() needs to call OrderService.updateStatus()
// OrderService.placeOrder()        needs to call PaymentService.processPayment()

// ❌ Direct dependency (cycle):
// payment.service.ts
import { OrderService } from './order.service'; // cycle!
export class PaymentService {
  constructor(private orders: OrderService) {}
  async processPayment(orderId: string, amount: number) {
    const charged = await chargeCard(amount);
    if (charged) await this.orders.updateStatus(orderId, 'paid'); // needs OrderService
  }
}

// ✓ DIP: introduce an event/callback abstraction:
// payment-events.interface.ts  ← no imports from payment or order
export interface IPaymentEvents {
  onPaymentSuccess(orderId: string): Promise<void>;
  onPaymentFailure(orderId: string, reason: string): Promise<void>;
}

// payment.service.ts  ← depends only on the interface, not on OrderService
import { IPaymentEvents } from './payment-events.interface';
export class PaymentService {
  constructor(private events: IPaymentEvents) {}
  async processPayment(orderId: string, amount: number) {
    const charged = await chargeCard(amount);
    if (charged) await this.events.onPaymentSuccess(orderId); // calls interface method
    else         await this.events.onPaymentFailure(orderId, 'card_declined');
  }
}
// PaymentService no longer imports OrderService → cycle eliminated

// order.service.ts  ← implements the interface
import { IPaymentEvents } from './payment-events.interface';
import { PaymentService } from './payment.service'; // one-way: Order → Payment ✓
export class OrderService implements IPaymentEvents {
  constructor(private payment: PaymentService) {}
  async placeOrder(cart: Cart) {
    const order = await createOrder(cart);
    await this.payment.processPayment(order.id, order.total);
    return order;
  }
  async onPaymentSuccess(orderId: string) { // implements IPaymentEvents
    await updateOrderStatus(orderId, 'paid');
  }
  async onPaymentFailure(orderId: string, reason: string) {
    await updateOrderStatus(orderId, 'failed');
    await notifyCustomer(orderId, reason);
  }
}
// Dependency graph: OrderService → PaymentService → IPaymentEvents ← OrderService
//                                                                    (implements)
// No cycle — OrderService implements the interface, not imports-from PaymentService's concrete dep
```

**Q10. What is the "event emitter" decoupling pattern and how does it break cycles without interfaces?**
A: When two modules need to communicate but neither should directly import the other, a **shared event bus** — a third module both import — allows decoupled communication. Module A emits events; Module B listens. Neither imports the other.

```ts
// events.ts  ← shared event bus — no imports from A or B
import { EventEmitter } from 'events';
export const bus = new EventEmitter();
// This module is a leaf node — nothing imports it except A and B

// user.service.ts  ← emits events, does NOT import auth.service
import { bus } from './events';
export class UserService {
  async updateEmail(userId: string, email: string) {
    await db.updateUserEmail(userId, email);
    bus.emit('user:emailChanged', { userId, email }); // fire and forget
    // No import of AuthService — no cycle
  }
}

// auth.service.ts  ← listens to events, does NOT import user.service
import { bus } from './events';
export class AuthService {
  constructor() {
    bus.on('user:emailChanged', async ({ userId, email }) => {
      await this.invalidateSessionsForUser(userId); // react to event
    });
  }
  async invalidateSessionsForUser(userId: string) { /* ... */ }
}

// Dependency graph:
//   UserService → events (bus)
//   AuthService → events (bus)
//   No edge between UserService and AuthService → no cycle

// Trade-offs:
//   ✓ Completely decoupled — adding a new listener requires no changes to emitter
//   ✗ Harder to trace: "who handles user:emailChanged?" requires searching listeners
//   ✗ No TypeScript type safety on event payload without typed event maps
//   ✗ Listeners must be registered before events fire (initialization order matters)
```

For TypeScript type safety on events:
```ts
// typed-events.ts
import { EventEmitter } from 'events';

interface AppEvents {
  'user:emailChanged': [{ userId: string; email: string }];
  'order:placed':      [{ orderId: string; total: number }];
  'payment:success':   [{ orderId: string }];
}

class TypedEventEmitter extends EventEmitter {
  emit<K extends keyof AppEvents>(event: K, ...args: AppEvents[K]): boolean {
    return super.emit(event, ...args);
  }
  on<K extends keyof AppEvents>(event: K, listener: (...args: AppEvents[K]) => void): this {
    return super.on(event, listener);
  }
}
export const bus = new TypedEventEmitter();
// Now: bus.emit('user:emailChanged', { userId: '1', email: 'x@y.z' }) is type-checked
```

**Q11. What is the "index barrel file" anti-pattern that creates accidental circular dependencies?**
A: A barrel file (`index.ts`) re-exports everything from a directory, providing a single import point for consumers. This is convenient, but in large codebases, barrel files become hubs that connect everything to everything — and cycles emerge through the barrel even when the underlying files have no direct dependency.

```
Without barrel — clear DAG:
  components/Button.tsx (no imports from components/)
  components/Modal.tsx  (imports Button directly)
  components/Form.tsx   (imports Button and Modal directly)
  pages/Login.tsx       (imports Form directly)
  ✓ No cycles

With barrel (components/index.ts re-exports all):
  components/index.ts: export * from './Button'; export * from './Modal'; export * from './Form';

  pages/Login.tsx:         import { Form } from '../components'; // imports barrel
  components/Modal.tsx:    import { Button } from '../components'; // imports barrel (!)
  components/Form.tsx:     import { Button, Modal } from '../components'; // imports barrel (!)

  Modal.tsx → components/index.ts → Modal.tsx    ← CYCLE through barrel
  Form.tsx  → components/index.ts → Form.tsx     ← CYCLE through barrel

  The barrel becomes a circular hub even though Modal and Button have no direct dependency.
```

```ts
// ❌ Anti-pattern: intra-directory barrel imports
// components/Modal.tsx
import { Button } from './index'; // ← imports barrel which re-exports Modal itself → cycle

// ✓ Fix: import directly from the source file, not the barrel
// components/Modal.tsx
import { Button } from './Button'; // ← direct import, no cycle

// ✓ External consumers still use the barrel:
// pages/Login.tsx
import { Form, Modal, Button } from '../components'; // ← barrel fine for external consumers
// Rule: only FILES OUTSIDE the directory import from the barrel
//       files INSIDE the directory import from siblings directly

// ESLint rule to enforce this:
// "import/no-cycle": "error" catches barrel cycles
// Or: custom rule checking that ./index is not imported from within the same directory
```

### Section 4: TypeScript-Specific Concerns

**Q12. How does `import type` help with circular dependencies in TypeScript?**
A: TypeScript's `import type` imports only type information — interfaces, type aliases, enums used as types. The TypeScript compiler erases all `import type` declarations before emitting JavaScript. The resulting JS file has no `require()` or `import` for that dependency at all.

This means `import type` cycles are **not runtime circular dependencies**. They exist in the type graph (checked by `tsc`) but not in the module graph (executed by Node.js/browser).

```ts
// user.service.ts
import type { AuthToken } from './auth.service'; // type-only — erased at compile time
import { AuthService } from './auth.service';    // value — emitted as require/import

// Compiled output (JS):
// const auth_service_1 = require('./auth.service'); // ← only the VALUE import survives
// import type line → completely gone from output

// Result: if the only dependency from A on B is `import type`, the runtime cycle is broken
// (The type cycle still exists — TypeScript checks it — but no runtime effect)

// ✓ Pattern: separate types from implementation to break cycles in TypeScript
// auth.types.ts  ← pure types, no runtime code, no imports
export interface AuthToken { userId: string; exp: number; scope: string[] }
export type TokenValidationResult = { valid: boolean; reason?: string };

// auth.service.ts  ← runtime implementation, imports types
import type { AuthToken } from './auth.types';    // safe — types only
import { UserService } from './user.service';    // value import

// user.service.ts  ← runtime implementation
import type { AuthToken } from './auth.types';   // safe — same types file
import type { TokenValidationResult } from './auth.types'; // safe
// Does NOT import from auth.service → no cycle

// Both services share types through a types file → no runtime cycle
```

**Q13. How do circular dependencies manifest in module bundlers (Webpack/Rollup/Vite) differently from Node.js?**
A: Bundlers face the same underlying problem but handle it in the context of generating a single output bundle. Key differences:

**Webpack**: Converts all modules to CommonJS internally (historically), applies the same partial-initialization behavior as Node.js CJS. `circular-dependency-plugin` can detect and fail the build.

**Rollup / Vite**: Native ESM-aware. Rollup emits a warning for every cycle it detects. Since it processes the full dependency graph before emitting, it can determine the evaluation order. Cycles in pure-type code (TypeScript) are resolved because types are stripped.

**Execution order in bundles**:
```
// Without a bundler: Node.js loads modules lazily (on first require/import)
// With a bundler: ALL modules are included in the bundle regardless of runtime code paths
// The bundler determines a static evaluation order — cycles force an arbitrary choice

// Rollup cycle warning:
// (!) Circular dependency: src/a.js -> src/b.js -> src/a.js
// Rollup will pick one module to evaluate first, which may cause issues

// Vite dev mode: native ESM in the browser — cycle behavior matches ESM spec
// Vite build mode: uses Rollup — same warnings apply

// Tree-shaking and cycles:
// Bundlers cannot tree-shake (dead code eliminate) modules in a cycle perfectly
// because they can't prove which exports are "dead" when exports depend on each other
// Circular dependencies → larger bundle sizes (entire cycle must be included)
```

**Q15. "How can a circular dependency cause a production incident that doesn't appear in development or tests?"**
A: Circular dependency bugs are **order-sensitive** — the runtime behavior depends on which module is required/imported first. In development, the entry point may happen to require modules in a safe order. A different code path in production may trigger a different require-order, hitting the cycle when a module is still partially initialized.

```
Scenario: Feature flag change in production

  Development entry: server.js → userRouter → authService → userService
  Evaluation order: authService loads first → userService loads → no cycle hit
  Tests pass: always enters through the same path

  Production incident: new feature flag enables adminRouter BEFORE userRouter
  New evaluation order: adminRouter → userService → authService → userService (CYCLE HIT)
  userService is partially initialized when authService reads it
  authService.startup() calls userService.getSystemUser() → undefined → TypeError → crash

Other triggers for order-sensitive cycle bugs:
  → Changing webpack splitChunks configuration changes bundle evaluation order
  → Adding a new entry point (SSR server vs client entry)
  → Dynamic imports resolving in different order (race condition in load)
  → A/B testing system lazy-loading a module that changes require order
  → Hot module replacement (HMR) re-evaluating modules in a different order
```

## Problem 2 — ESM Temporal Dead Zone Crash

### Problem
A Vite-bundled React app crashes in production with `ReferenceError: Cannot access 'CONFIG' before initialization`. The error doesn't appear in development. Identify the ESM cycle causing it and explain why it's environment-dependent.

```ts
// config.ts
import { getEnvironment } from './environment';      // ← imports environment
export const CONFIG = {
  apiUrl:  getEnvironment('API_URL'),
  timeout: Number(getEnvironment('TIMEOUT') ?? 3000),
};

// environment.ts
import { CONFIG } from './config';                   // ← imports config (CYCLE!)
const defaults: Record<string, string> = {
  API_URL: 'http://localhost:3000',
  TIMEOUT: '5000',
};
export function getEnvironment(key: string): string {
  // Falls back to config values if env var not set — but this creates the cycle:
  return process.env[key] ?? CONFIG?.[key as keyof typeof CONFIG]?.toString() ?? defaults[key];
}
```

### Why Development vs Production Differs

```
Development (Vite dev server — native ESM):
  Browser imports modules on demand as they are first needed.
  Entry point: main.tsx → App.tsx → some component → config.ts first
  
  ESM evaluation (depth-first, config.ts evaluated before environment.ts is requested):
  Actually depends on which component first touches config — may work by luck

Production (Vite build — Rollup bundles):
  Rollup statically analyzes the full graph and must pick evaluation order.
  With a cycle, Rollup picks one module to evaluate first.
  Rollup chose: environment.ts evaluates first (it's "lower" in its traversal)
  
  environment.ts evaluates:
    → import { CONFIG } from './config'
    → CONFIG binding exists (live binding slot allocated) but config.ts hasn't run yet
    → CONFIG is in TDZ (Temporal Dead Zone) — const, not yet initialized
  
  config.ts evaluates:
    → import { getEnvironment } from './environment'  ← getEnvironment is defined ✓
    → export const CONFIG = { apiUrl: getEnvironment('API_URL'), ... }
    → getEnvironment() runs → accesses CONFIG → CONFIG is still TDZ in this execution
    → ReferenceError: Cannot access 'CONFIG' before initialization 💥

Why dev didn't crash:
  In dev with HMR, modules can be loaded in a different order (based on browser fetch order)
  The browser happened to load config.ts before environment.ts → no TDZ error
  OR: the specific code path that triggers the fallback to CONFIG wasn't exercised
```

### Fixing the ESM TDZ Cycle

```ts
// Root cause: environment.ts and config.ts depend on each other
// environment should be a LEAF module with no imports from the app

// Fix 1: Remove the circular fallback — environment.ts should not read CONFIG
// environment.ts — FIXED: no import from config
const defaults: Record<string, string> = {
  API_URL: 'http://localhost:3000',
  TIMEOUT: '5000',
};
export function getEnvironment(key: string): string {
  return process.env[key] ?? defaults[key] ?? ''; // defaults here, not from CONFIG
}
// environment.ts is now a leaf — no imports from the app → no cycle

// config.ts — unchanged but cycle is gone
import { getEnvironment } from './environment'; // one-way: config → environment ✓
export const CONFIG = {
  apiUrl:  getEnvironment('API_URL'),
  timeout: Number(getEnvironment('TIMEOUT') ?? 3000),
};
```

```ts
// Fix 2: If CONFIG defaults are genuinely needed in environment resolution,
// extract them to a shared constants module (leaf node):

// constants.ts  ← no imports, pure data
export const DEFAULTS = {
  API_URL:  'http://localhost:3000',
  TIMEOUT:  '5000',
} as const;

// environment.ts  ← imports constants (not config)
import { DEFAULTS } from './constants';
export function getEnvironment(key: keyof typeof DEFAULTS): string {
  return process.env[key] ?? DEFAULTS[key];
}

// config.ts  ← imports environment (one-way)
import { getEnvironment } from './environment';
export const CONFIG = {
  apiUrl:  getEnvironment('API_URL'),
  timeout: Number(getEnvironment('TIMEOUT')),
};

// Dependency graph:
//   config → environment → constants (leaf)
//   No cycles — clean DAG
```

```ts
// Fix 3: If the cycle is between two ESM files and refactoring is not immediately possible:
// Use a lazy getter to defer access past module initialization:

// environment.ts — lazy getter breaks TDZ:
import { CONFIG } from './config';

export function getEnvironment(key: string): string {
  return process.env[key]
    ?? defaults[key]
    // Lazy: CONFIG is only READ when the function is CALLED (not when module is evaluated)
    // By call time, config.ts has finished evaluating → CONFIG is defined
    ?? String(CONFIG?.[key as keyof typeof CONFIG] ?? '');
}
// getEnvironment is a function — function bodies are not evaluated at module load time
// CONFIG is accessed INSIDE the function → read at call time, not at import time → no TDZ

import type { IOrderService, IInventoryService, OrderItem, Order } from './service.interfaces';

export class OrderService implements IOrderService {
  // Receives IInventoryService via constructor injection — not imported directly:
  constructor(private inventory: IInventoryService) {}

  async placeOrder(items: OrderItem[]): Promise<Order> {
    for (const item of items) {
      const available = await this.inventory.checkStock(item.productId, item.qty);
      if (!available) throw new Error(`Out of stock: ${item.productId}`);
    }
    const order = await createOrderRecord(items);
    await this.inventory.reserveStock(items, order.id);
    return order;
  }

  async getOrderById(id: string): Promise<Order> {
    return db.orders.findById(id);
  }

  async cancelOrder(id: string): Promise<void> {
    const order = await this.getOrderById(id);
    await this.inventory.releaseStock(id); // releases via injected service
    await db.orders.update(id, { status: 'cancelled' });
  }
}
// OrderService no longer imports InventoryService → half the cycle broken

// inventory.service.ts  ← depends on IOrderService interface, not OrderService class
import type { IInventoryService, IOrderService, OrderItem } from './service.interfaces';

export class InventoryService implements IInventoryService {
  constructor(private orders: IOrderService) {}

  async checkStock(productId: string, qty: number): Promise<boolean> {
    const stock = await db.inventory.findByProduct(productId);
    return stock.available >= qty;
  }

  async reserveStock(items: OrderItem[], orderId: string): Promise<void> {
    for (const item of items) {
      await db.inventory.reserve(item.productId, item.qty, orderId);
    }
  }

  async releaseStock(orderId: string): Promise<void> {
    const order = await this.orders.getOrderById(orderId); // via injected interface
    for (const item of order.items) {
      await db.inventory.release(item.productId, item.qty, orderId);
    }
  }
}
// InventoryService no longer imports OrderService → cycle fully broken
```

### Step 3: Wire Dependencies in a Composition Root

```ts
// container.ts  ← the ONLY file that knows about concrete classes
// All imports are one-directional: container → services
import { OrderService }     from './order.service';
import { InventoryService } from './inventory.service';
import type { IOrderService, IInventoryService } from './service.interfaces';

// Lazy singleton container to handle mutual dependency:
let _orderService:     IOrderService     | null = null;
let _inventoryService: IInventoryService | null = null;

// Use factory functions with lazy initialization to handle mutual construction:
function getInventoryService(): IInventoryService {
  if (!_inventoryService) {
    // Inventory needs Order — but Order isn't created yet when Inventory is first built.
    // Solution: pass a proxy/factory that resolves lazily:
    _inventoryService = new InventoryService({
      getOrderById:  (id) => getOrderService().getOrderById(id),
      placeOrder:    (items) => getOrderService().placeOrder(items),
      cancelOrder:   (id) => getOrderService().cancelOrder(id),
    });
  }
  return _inventoryService;
}

function getOrderService(): IOrderService {
  if (!_orderService) {
    _orderService = new OrderService(getInventoryService());
  }
  return _orderService;
}

// Export the container:
export const container = {
  orderService:     getOrderService,
  inventoryService: getInventoryService,
};

// Usage in route handlers:
// routes/orders.ts
import { container } from '../container';

router.post('/orders', async (req, res) => {
  const orderService = container.orderService(); // lazy singleton
  const order = await orderService.placeOrder(req.body.items);
  res.json(order);
});
```

## Quick Reference — Circular Dependency Cheat Sheet

```
HOW CYCLES MANIFEST:
  CommonJS:  partial exports object ({} instead of complete module)
             top-level: { name } = require('b') → name is undefined if b hasn't run
             inside function: safe — module.exports complete by call time
  ESM:       live binding in TDZ — ReferenceError: Cannot access 'X' before initialization
             functions safe (body not evaluated at import time)
             const/let top-level: dangerous if exporter hasn't run yet
  Bundlers:  Rollup warns; webpack/circular-dependency-plugin can fail build
             evaluation order determined statically — differs from Node.js dev order

DETECTION TOOLS:
  madge --circular src/              → audit existing codebase (one-shot)
  eslint-plugin-import/no-cycle     → prevent new cycles (per-file on save + CI)
  circular-dependency-plugin        → Webpack build-time detection
  rollupOptions.onwarn CIRCULAR_DEPENDENCY → Vite/Rollup build-time detection
  node --trace-warnings             → runtime detection for CJS
  madge test (jest/vitest)          → architecture test — fails CI if cycle introduced

FIX PATTERNS:
  Extract shared module:    A → C ← B    (C is new leaf; A and B both import C)
  Dependency inversion:     A → IFace ← B  (interface in separate file; B implements it)
  Lazy require/import:      move require() inside a function body (CJS)
                            use dynamic import() inside async function (ESM)
  Event bus:                A → bus ← B   (bus is shared emitter; no A↔B edge)
  import type:              TypeScript only — erased at compile time, no runtime cycle
  Constructor injection:    pass dependencies as parameters; wire in a container

BARREL FILE RULES:
  ✓ External consumers import from barrel (index.ts)
  ✗ Files INSIDE the directory must NOT import from the barrel (import sibling directly)
  Enforce: eslint-plugin-import/no-cycle catches barrel cycles automatically

ARCHITECTURAL RULES THAT PREVENT CYCLES:
  Services never import middleware/routes (inward dependencies only)
  Utils are pure (no imports from business logic modules)
  Types/interfaces in a separate file — shared freely (no runtime cost)
  Each layer only imports from the layer directly below it (strict layering)
  Shared constants/types live in leaf modules (no imports from the rest of the app)

COMMON MISTAKES:
  "It works in dev, fails in prod"  → evaluation order differs (entry point, bundler)
  import type used but still cycles → import type only removes TYPE edges; VALUE edges remain
  Lazy require "fixes" the bug      → addresses symptom; architecture still wrong
  Barrel exports internal files     → inevitable cycles as directory grows
  Class instantiated at module level → forces top-level resolution; use DI container instead
  Cross-package barrel imports       → packages/A/src imported by packages/B → bundle cycle
```

---

**Final Tip:** At the 5 YOE level, circular dependency questions test whether you can reason about **module evaluation order and its consequences** — not just name the tools. The highest-signal answer on the CJS behavior: "CommonJS adds modules to the cache before executing them, so when a circular require fires mid-execution, the requirer gets the *current* exports object — which may be empty or partially populated. The fix is either to restructure so the dependency isn't needed at module load time, or to wrap the require inside a function so it executes *after* all modules have initialized. The module cache means no re-execution — just a stale snapshot." For ESM: "ESM live bindings mean the binding *exists* but may be in the Temporal Dead Zone — the slot is allocated in phase two, but assigned in phase three when the exporting module runs. If your importer reads it before the exporter has executed, you get a TDZ ReferenceError. `import type` is the clean escape hatch in TypeScript — it's completely erased before emit, so it only exists in the type graph, never the runtime module graph." For architecture: "Most circular dependencies are a symptom of a domain concept being in the wrong module — a 'utility' function that imports from business logic is really a business logic function. The fix is to move it to where it belongs, not to paper over the cycle with a lazy require."
