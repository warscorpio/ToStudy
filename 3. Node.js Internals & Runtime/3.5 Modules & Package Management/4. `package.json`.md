# `package.json`: `engines` Field, `exports` Field, ESM/CJS Dual Packages — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem does the `exports` field solve that `main` and `module` could not?**

A: Before `exports`, package authors had two fields to point consumers to their code — `main` (for CommonJS, respected by Node.js) and `module` (for ES modules, a bundler convention never adopted by Node.js itself). This two-field system had three fundamental problems:

```json
// Old-style package.json — three problems:
{
  "name": "my-lib",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts"
}
```

```javascript
// Problem 1: Deep imports were completely uncontrolled
// A consumer could import ANY file inside your package:
import { something } from 'my-lib/dist/internal/secret-helper';
// You cannot prevent this — no way to say "this file is private"
// Refactoring internals breaks consumers who imported private paths

// Problem 2: Node.js ignored the 'module' field entirely
// Node.js only reads 'main' — so ESM consumers on Node.js got the CJS build
// Bundlers (webpack, rollup) read 'module' — so bundled apps got ESM
// Two different environments, two different behaviors, subtle bugs

// Problem 3: No environment-conditional resolution
// You couldn't serve different code to:
//   - Node.js vs browser
//   - CommonJS require() vs ESM import
//   - Development vs production
//   - With types vs without
// One entry point for everyone, regardless of their environment
```

The `exports` field (introduced in Node.js 12, stable in Node.js 14) solves all three:

```json
{
  "name": "my-lib",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "types": "./dist/index.d.ts"
    },
    "./utils": {
      "import": "./dist/utils.mjs",
      "require": "./dist/utils.cjs"
    }
  }
}
```

```javascript
// Solution 1: Deep imports are blocked by default
import { x } from 'my-lib/dist/internal/secret'; // Error: not in exports map
// Only paths explicitly listed in 'exports' are accessible

// Solution 2: Node.js natively reads 'exports' and picks the right format
import { x } from 'my-lib';   // → Node.js picks "import": "./dist/index.mjs"
const x = require('my-lib');  // → Node.js picks "require": "./dist/index.cjs"

// Solution 3: Conditional exports for different environments
// "import" / "require" / "node" / "browser" / "development" / "production"
// Each consumer gets the right build for their context
```

**Q2. What is the structure of the `exports` field — what are subpath exports and conditions?**

A: The `exports` field is a JSON object whose keys are **subpath patterns** and whose values are either strings (direct file paths) or objects containing **conditions**:

```json
{
  "exports": {
    "./subpath": "<condition-map or path>"
  }
}
```

Subpath exports — controlling which paths consumers can import:

```json
{
  "name": "my-lib",
  "exports": {
    ".": "./dist/index.js",
    "./utils": "./dist/utils.js",
    "./parser": "./dist/parser.js",
    "./package.json": "./package.json"
  }
}
```

```javascript
import lib    from 'my-lib';             // → ./dist/index.js  ✓
import utils  from 'my-lib/utils';       // → ./dist/utils.js  ✓
import parser from 'my-lib/parser';      // → ./dist/parser.js ✓
import pjson  from 'my-lib/package.json';// → ./package.json   ✓ (must be explicit)
import secret from 'my-lib/internal';    // Error: not exported ✗
```

Condition maps — choosing different files per environment:

```json
{
  "exports": {
    ".": {
      "node": {
        "import": "./dist/node/index.mjs",
        "require": "./dist/node/index.cjs"
      },
      "browser": "./dist/browser/index.js",
      "default": "./dist/index.js"
    }
  }
}
```

Node.js built-in conditions (resolved in order, first match wins):

```
"import"      → matched when file is loaded via ESM import statement
"require"     → matched when file is loaded via CJS require()
"node"        → matched in any Node.js environment
"node-addons" → matched when C++ addons are needed
"browser"     → matched by bundlers targeting browser environments
"worker"      → matched when running in a Web Worker / Node Worker
"default"     → always matches — used as the fallback (must be last)
"types"       → matched by TypeScript (not Node.js — TS-specific convention)
"development" → matched by some build tools in dev mode
"production"  → matched by some build tools in prod mode
```

Subpath patterns — glob-style wildcards for bulk exports:

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./features/*": "./dist/features/*.js",
    "./icons/*.svg": "./assets/icons/*.svg"
  }
}
```

```javascript
import btn from 'my-lib/features/button';  // → ./dist/features/button.js
import icon from 'my-lib/icons/arrow.svg'; // → ./assets/icons/arrow.svg
// The * is replaced with whatever the consumer imports after the prefix
// You cannot use multiple * in a single pattern (unlike glob)
```

The `"exports": null` pattern — explicitly blocking a subpath:

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./internal/*": null
  }
}
```

```javascript
import x from 'my-lib/internal/helper'; // Error: blocked by null export
// Useful when you have files that exist on disk but must never be imported directly
```

## Section 2: The `engines` Field

**Q3. What does the `engines` field do and how is it enforced?**

A: The `engines` field declares which versions of Node.js (and npm/yarn/pnpm) your package is designed to work with. It is a **communication** field — it tells consumers and CI systems what runtime version is required. Enforcement depends on the package manager and context:

```json
{
  "engines": {
    "node": ">=18.0.0",
    "npm":  ">=9.0.0",
    "pnpm": ">=8.0.0"
  }
}
```

How enforcement works per context:

```bash
# npm: engines is NOT enforced for end users by default
# If you install a package whose engine requirement you don't meet, npm warns but proceeds:
npm warn EBADENGINE Unsatisfied engine for my-lib:
npm warn EBADENGINE   Required: { node: '>=18.0.0' }
npm warn EBADENGINE   Actual:   { npm: '9.5.1', node: 'v16.20.0' }
# npm still installs it — just warns

# To make npm enforce engines strictly:
npm install --engine-strict
# OR set in .npmrc:
echo "engine-strict=true" >> .npmrc

# pnpm: enforces engines by default (stricter than npm)
# pnpm install will ERROR (not warn) if Node.js version doesn't match

# yarn: warns by default, can configure to error
# In package.json:
{
  "engines": { "node": ">=18.0.0" },
  "engineStrict": true  // yarn-specific: error instead of warn (deprecated in yarn 2+)
}
```

Version range syntax — the same semver ranges as dependencies:

```json
{
  "engines": {
    "node": ">=18.0.0",           // 18.0.0 and above
    "node": ">=16.0.0 <21.0.0",   // range: 16.x and 17.x and 18.x and 19.x and 20.x
    "node": "^20.0.0",             // 20.x.x (compatible with 20.0.0)
    "node": "18.x || >=20.0.0",   // 18.x OR 20.0.0+
    "node": "18.19.0",             // Exactly this version (rare — usually too strict)
    "node": "*"                    // Any version (still worth stating explicitly)
  }
}
```

The `engines` field also informs tooling beyond package managers:

```yaml
# CI pipeline reads engines.node to pick the right Node.js version:
# .github/workflows/ci.yml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version-file: '.nvmrc'  # OR: read from package.json engines.node

# .nvmrc — a separate file that many tools read (nvm, volta, etc.):
# echo "20" > .nvmrc

# volta (Node.js version manager) reads 'engines' directly:
# "volta": { "node": "20.11.0" }  — volta's own field, pinned version
```

Using `engines` for monorepo workspace consistency:

```json
// Root package.json in a monorepo:
{
  "engines": {
    "node": ">=20.0.0"
  },
  "workspaces": ["packages/*"]
}
// All workspace packages inherit this constraint
// If a package has its own engines field, the stricter one applies

// Checking programmatically at runtime:
const [major] = process.versions.node.split('.').map(Number);
if (major < 18) {
    console.error(`This package requires Node.js 18+. Current: ${process.version}`);
    process.exit(1);
}
```

**Q4. How does the `engines` field interact with the `exports` field when supporting multiple Node.js versions?**

A: When your package must support a range of Node.js versions, `engines` and `exports` work together — `engines` declares the minimum, while `exports` conditions let you serve different code based on what features the runtime supports:

```json
{
  "name": "my-lib",
  "engines": { "node": ">=16.0.0" },
  "exports": {
    ".": {
      "node": {
        "import": "./dist/index.mjs",
        "require": "./dist/index.cjs"
      },
      "default": "./dist/index.cjs"
    }
  }
}
```

```javascript
// Handling Node.js 16 vs 18+ API differences via exports conditions:
// Node.js 18+ has native fetch — Node.js 16 does not

// You can't directly express "node >= 18" in the exports conditions map,
// but you can expose a separate entry for features that need a version check:
```

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./fetch-compat": {
      "import": "./dist/fetch-compat.mjs",
      "require": "./dist/fetch-compat.cjs"
    }
  }
}
```

```typescript
// dist/fetch-compat.mjs — runtime check for version-dependent API:
const nodeMajor = parseInt(process.versions.node.split('.')[0]);

export const fetchImpl = nodeMajor >= 18
    ? globalThis.fetch                        // Native fetch in Node.js 18+
    : (await import('node-fetch')).default;   // Polyfill for Node.js 16

// dist/index.mjs — main entry can import the compat shim:
export { fetchImpl as fetch } from './fetch-compat.mjs';
```

The engines field also guides which syntax you can use in your distributed files:

```javascript
// engines: "node": ">=18.0.0" means you can use:
// ✓ Top-level await in ESM
// ✓ native fetch, Headers, Request, Response
// ✓ Error.cause
// ✓ Array.prototype.at()
// ✓ Object.hasOwn()

// engines: "node": ">=16.0.0" means you must avoid:
// ✗ native fetch (not available until 18)
// ✗ Array.prototype.findLast() (not available until 18)
// ✗ structuredClone() (available from 17 — be careful)

// CI matrix test — verify your declared engines range actually works:
// .github/workflows/ci.yml
strategy:
  matrix:
    node-version: [16, 18, 20, 22]  // Test all versions in your engines range
```

## Section 3: ESM/CJS Dual Packages

**Q5. What is the "dual package hazard" and why does it matter?**

A: The dual package hazard is a class of bugs that occur when a package is loaded as BOTH its ESM version and its CJS version in the same Node.js process. Because Node.js caches modules separately by format, the two copies do not share identity — `instanceof` checks fail, singletons duplicate, and shared state diverges.

```javascript
// How the hazard occurs:
// your-app (ESM) imports my-lib → gets ./dist/index.mjs
// your-app also requires legacy-plugin (CJS) which requires my-lib → gets ./dist/index.cjs
// Result: TWO copies of my-lib in memory with no shared state

// Consequences:

// 1. instanceof fails across the format boundary:
import { MyClass } from 'my-lib';          // ESM version
const obj = new MyClass();

const { MyClass: MyClassCJS } = require('my-lib'); // CJS version
console.log(obj instanceof MyClassCJS);    // false! Different class objects
                                           // Even though it's "the same" class

// 2. Singletons are duplicated:
// my-lib/dist/index.mjs:
const registry = new Map(); // ESM singleton
export { registry };

// my-lib/dist/index.cjs:
const registry = new Map(); // CJS singleton — DIFFERENT MAP than the ESM one!
module.exports = { registry };

// Consumer code:
import { registry } from 'my-lib'; // ESM registry
const { registry: cjsRegistry } = require('my-lib'); // CJS registry
registry.set('key', 'value');
console.log(cjsRegistry.has('key')); // false — different Map!

// 3. Event emitters and pub/sub systems break:
// A listener added via the ESM version won't receive events emitted via the CJS version
```

The three strategies to handle or avoid the dual package hazard:

```javascript
// Strategy 1: ESM-only package (no CJS at all)
// Safest against the hazard — can't be required(), eliminates the problem
// Cost: drops support for CJS consumers (CommonJS require() users)
// Use when: building a new library targeting modern Node.js only

// Strategy 2: CJS-only package (no ESM)
// Also eliminates the hazard — can't be imported as ESM
// Cost: no native ESM support (bundlers still work via the 'module' field)
// Use when: maintaining existing libraries, broad compatibility is required

// Strategy 3: Stateless dual package (the supported dual-package approach)
// Provide both formats, but ensure neither format contains mutable state
// Hazard still technically possible but harmless if there's no shared state to diverge
```

**Q6. How do you correctly set up a dual ESM/CJS package using the `exports` field?**

A: A production dual package requires careful setup of both the `exports` field and the build pipeline. Here is the complete pattern:

```json
{
  "name": "my-lib",
  "version": "1.0.0",
  "description": "A dual ESM/CJS library",
  "engines": { "node": ">=16.0.0" },

  "type": "module",

  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",

  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.mts",
        "default": "./dist/index.mjs"
      },
      "require": {
        "types": "./dist/index.d.cts",
        "default": "./dist/index.cjs"
      }
    },
    "./utils": {
      "import": {
        "types": "./dist/utils.d.mts",
        "default": "./dist/utils.mjs"
      },
      "require": {
        "types": "./dist/utils.d.cts",
        "default": "./dist/utils.cjs"
      }
    },
    "./package.json": "./package.json"
  },

  "files": [
    "dist",
    "!dist/**/*.test.*",
    "!dist/**/*.spec.*"
  ],

  "scripts": {
    "build": "tsup src/index.ts --format esm,cjs --dts",
    "test": "vitest"
  },

  "devDependencies": {
    "tsup": "^8.0.0",
    "typescript": "^5.0.0",
    "vitest": "^1.0.0"
  }
}
```

Why each field matters:

```
"type": "module"
  → Makes .js files in this package treated as ESM by Node.js
  → Forces you to use .cjs extension for CommonJS files
  → Without this, .js = CJS and you need .mjs for ESM (opposite convention)

"main": "./dist/index.cjs"
  → Fallback for Node.js < 12 and tools that don't read "exports"
  → Points to CJS because most legacy tools expect CJS from "main"

"module": "./dist/index.mjs"
  → Not read by Node.js — read by bundlers (webpack, rollup, vite)
  → Bundlers use this for tree-shaking-friendly ESM builds

"types": "./dist/index.d.ts"
  → TypeScript fallback when "exports" conditions aren't used
  → Modern TS (4.7+) reads "types" inside "exports" conditions instead

"exports"
  → The authoritative resolution map for Node.js 14+ and modern bundlers
  → Overrides "main" and "module" for consumers that support it
  → "types" inside conditions: TypeScript 4.7+ with moduleResolution "bundler" or "node16"
```

The `tsup` build configuration for dual packages:

```typescript
// tsup.config.ts
import { defineConfig } from 'tsup';

export default defineConfig({
    entry: ['src/index.ts', 'src/utils.ts'],
    format: ['esm', 'cjs'],       // Produce both formats
    dts: true,                     // Generate .d.ts files
    splitting: false,              // Disable code splitting (simpler output)
    sourcemap: true,
    clean: true,                   // Clean dist/ before build
    outExtension({ format }) {
        return {
            js: format === 'esm' ? '.mjs' : '.cjs',
            // tsup maps: .d.ts → .d.mts (ESM) and .d.cts (CJS) automatically
        };
    },
});

// What tsup produces:
// dist/index.mjs      ← ES module
// dist/index.cjs      ← CommonJS module
// dist/index.d.mts    ← TypeScript declarations for ESM consumers
// dist/index.d.cts    ← TypeScript declarations for CJS consumers
// dist/index.d.ts     ← Fallback declarations (for "types" field)
// dist/utils.mjs
// dist/utils.cjs
// etc.
```

Verifying the dual package works correctly:

```bash
# Test CJS resolution:
node -e "const lib = require('my-lib'); console.log(lib);"

# Test ESM resolution:
node --input-type=module -e "import lib from 'my-lib'; console.log(lib);"

# Test subpath exports:
node -e "const utils = require('my-lib/utils'); console.log(utils);"
node --input-type=module -e "import utils from 'my-lib/utils'; console.log(utils);"

# Test that private paths are blocked:
node -e "require('my-lib/dist/internal');"
# Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './dist/internal'
# is not defined by "exports" in node_modules/my-lib/package.json

# Use publint to lint your package.json exports:
npx publint
# Checks: are all exported files present? Do conditions match actual files?
# Are there missing fallbacks? Are extension conventions correct?

# Use are-the-types-wrong to verify TypeScript declarations:
npx @arethetypeswrong/cli my-lib
# Checks: do "types" conditions in exports point to the right .d.mts/.d.cts files?
# Does TypeScript resolve correctly under different moduleResolution settings?
```

**Q7. What is the `"type"` field in `package.json` and how does it interact with file extensions?**

A: The `"type"` field tells Node.js how to interpret `.js` files within the package. It has two values — `"module"` or `"commonjs"` (default when omitted) — and resolves the longstanding ambiguity between `.js` as ESM vs `.js` as CJS:

```
File extension resolution rules:

.mjs  → ALWAYS treated as ESM (regardless of "type" field)
.cjs  → ALWAYS treated as CJS (regardless of "type" field)
.js   → Depends on "type" field of the nearest package.json:
         "type": "module"     → .js is ESM
         "type": "commonjs"   → .js is CJS (default if "type" omitted)
.json → Always treated as a JSON module
.node → Always treated as a native addon
```

```javascript
// Package A: "type": "module" (an ESM-first package)
// index.js    → ESM (because "type": "module")
// utils.js    → ESM (same package)
// legacy.cjs  → CJS (extension overrides "type")
// data.json   → JSON module

// Package B: "type": "commonjs" (or no "type" — CJS-first, the historical default)
// index.js    → CJS
// utils.js    → CJS
// modern.mjs  → ESM (extension overrides "type")
```

The file extension strategy for dual packages:

```javascript
// Option A: "type": "module" + .cjs for CJS files (recommended for new packages)
// Pros: .js files are ESM by default — matches modern expectations
// Cons: all CJS files need .cjs extension — slightly more typing
//
// package.json: { "type": "module" }
// dist/index.mjs → ESM (or .js since type=module)
// dist/index.cjs → CJS

// Option B: "type": "commonjs" (omitted) + .mjs for ESM files (for existing packages)
// Pros: backward compatible — .js files stay CJS for existing consumers
// Cons: ESM files need .mjs extension
//
// package.json: no "type" field
// dist/index.js  → CJS (or .cjs — explicit is better)
// dist/index.mjs → ESM

// The .d.mts / .d.cts TypeScript convention mirrors the .mjs / .cjs pattern:
// .d.mts = declarations for an .mjs file (TSC emits this automatically)
// .d.cts = declarations for a .cjs file
// .d.ts  = declarations for a .js file (interpreted per package "type")
```

How Node.js resolves the format when loading a file:

```javascript
// Node.js format detection algorithm (simplified):
//
// 1. If file ends in .mjs  → ESM
// 2. If file ends in .cjs  → CJS
// 3. If file ends in .json → JSON
// 4. Find nearest package.json by walking up directories
//    If package.json has "type": "module" → ESM
//    Otherwise → CJS
// 5. If no package.json found → CJS

// This means a .js file in a subdirectory can be a different format
// from .js files in the parent directory if there's a nested package.json
// with a different "type" — a confusing edge case to avoid
```

## Section 4: TypeScript and the `exports` Field

**Q8. How does TypeScript resolve types through the `exports` field — what `moduleResolution` settings matter?**

A: TypeScript's type resolution through `exports` depends on the `moduleResolution` compiler option. This is one of the most confusing areas in modern TypeScript tooling because four different settings exist, each with different behavior:

```json
// tsconfig.json — the moduleResolution setting determines how TS reads exports:
{
  "compilerOptions": {
    "moduleResolution": "node"       // TS 1+: ignores "exports" entirely — legacy
    "moduleResolution": "node16"     // TS 4.7+: reads "exports", requires .js extensions
    "moduleResolution": "nodenext"   // TS 4.7+: same as node16 (future-proof alias)
    "moduleResolution": "bundler"    // TS 5.0+: reads "exports", no extension requirement
  }
}
```

```
moduleResolution: "node" (legacy):
  → Ignores the "exports" field completely
  → Falls back to "types" / "typings" at package root, then index.d.ts
  → Cannot see "types" conditions inside "exports"
  → Still the default for module: "commonjs" — a common footgun

moduleResolution: "node16" / "nodenext":
  → Reads the "exports" field including "types" conditions
  → Enforces explicit .js extensions on imports (to match Node.js behavior)
  → import { x } from './utils'      → Error! Must be './utils.js'
  → import { x } from './utils.js'   → OK (resolves to utils.ts at build time)
  → Required when your package is "type": "module"

moduleResolution: "bundler" (TS 5.0+):
  → Reads the "exports" field including "types" conditions
  → Does NOT require explicit extensions (bundlers handle resolution)
  → Best for projects using Vite, webpack, esbuild, etc.
  → Not suitable for pure Node.js packages (bundlers aren't involved)
```

How TypeScript finds types for a dual package:

```json
// Library package.json (what the library author writes):
{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.mts",  // Types for ESM consumers
        "default": "./dist/index.mjs"
      },
      "require": {
        "types": "./dist/index.d.cts",  // Types for CJS consumers
        "default": "./dist/index.cjs"
      },
      "types": "./dist/index.d.ts"      // Fallback for "moduleResolution": "node"
    }
  },
  "types": "./dist/index.d.ts"          // Additional fallback for very old TS
}
```

```typescript
// Consumer — TypeScript picks types based on moduleResolution and how they import:

// tsconfig: moduleResolution: "node16", module: "ESNext" (ESM consumer)
import { fn } from 'my-lib';
// TS reads: exports["."].import.types = ./dist/index.d.mts ✓

// tsconfig: moduleResolution: "node16", module: "CommonJS" (CJS consumer)
const { fn } = require('my-lib');
// TS reads: exports["."].require.types = ./dist/index.d.cts ✓

// tsconfig: moduleResolution: "node" (legacy — ignores exports)
import { fn } from 'my-lib';
// TS reads: "types" field at root = ./dist/index.d.ts ✓ (fallback works)

// The .d.mts and .d.cts files are essential when your API differs between ESM/CJS:
// ESM can export things CJS cannot (live bindings, namespace imports)
// With separate declaration files, TS can type-check correctly for each format
```

Verifying TypeScript resolution with `@arethetypeswrong/cli`:

```bash
npx @arethetypeswrong/cli my-lib

# Output format:

#
# 💀 Resolution type   Types path              Module type
# node10               dist/index.d.ts         CommonJS

# node16 (from ESM)    dist/index.d.mts        ESM       ✓
# bundler              dist/index.d.mts        ESM       ✓
#
# ⚠ node10: Types not in exports map — consumers on moduleResolution:node get root types
# ✓ All modern moduleResolution settings resolve correctly

# Common errors arethetypeswrong reports:
# "masquerading as CJS" — .d.ts file claims CJS types but the actual file is ESM
# "missing types"       — no types condition in an exports entry
# "incorrect default export" — default export types don't match what the module exports
```

**Q9. What are the `"imports"` field and self-referential package imports?**

A: The `"imports"` field (note: plural, lowercase) is the **internal** counterpart to `"exports"`. While `"exports"` defines what outside consumers can import, `"imports"` defines path aliases that only code within the same package can use — useful for internal conditional imports and replacing `tsconfig.paths`:

```json
{
  "name": "my-app",
  "imports": {
    "#utils": {
      "node": "./src/utils.node.js",
      "browser": "./src/utils.browser.js",
      "default": "./src/utils.js"
    },
    "#db": {
      "development": "./src/db.mock.js",
      "production": "./src/db.real.js",
      "default": "./src/db.real.js"
    },
    "#*": "./src/*.js"
  }
}
```

```javascript
// Inside your package — use #-prefixed imports (must start with #):
import { query } from '#db';          // Resolves based on NODE_ENV condition
import { formatDate } from '#utils';  // Resolves based on environment (node/browser)
import { helper } from '#helpers';    // → ./src/helpers.js via #* pattern

// Outside your package — consumers CANNOT use your # imports:
import { x } from 'my-app/#db'; // Error — # imports are private to the package

// The # prefix is mandatory and distinguishes internal package imports
// from absolute paths (no #) and relative paths (./ or ../)
```

Self-referential imports — a package importing itself by name:

```json
{
  "name": "my-lib",
  "exports": {
    ".": "./dist/index.js",
    "./utils": "./dist/utils.js"
  }
}
```

```javascript
// Inside my-lib's own source code, you can import your own package by name:
import { helper } from 'my-lib/utils'; // Self-reference — uses the exports map

// This is useful for:
// 1. Writing tests that import the package the same way consumers do
// 2. Ensuring your own package's internal imports match the public API
// 3. Avoiding deeply nested relative paths (../../utils → 'my-lib/utils')

// Without self-referential imports, you'd need:
import { helper } from '../../dist/utils.js'; // Fragile relative path

// With self-referential imports (Node.js 13+ / npm 7+):
import { helper } from 'my-lib/utils'; // Uses exports map — same as consumer experience
```

## Section 5: Advanced Patterns

**Q10. How do you handle the `exports` field for packages with optional peer dependencies or platform-specific code?**

A: Conditional exports let you serve platform-optimized code without requiring consumers to do anything special — the resolution happens automatically based on the environment:

```json
{
  "name": "fast-hash",
  "exports": {
    ".": {
      "node": {
        "import": "./dist/node.mjs",
        "require": "./dist/node.cjs"
      },
      "browser": "./dist/browser.js",
      "default": "./dist/fallback.js"
    }
  }
}
```

```javascript
// dist/node.mjs — uses Node.js native crypto (fastest):
import { createHash } from 'crypto';
export const hash = (data) => createHash('sha256').update(data).digest('hex');

// dist/browser.js — uses Web Crypto API:
export const hash = async (data) => {
    const encoded = new TextEncoder().encode(data);
    const hashBuffer = await crypto.subtle.digest('SHA-256', encoded);
    return Array.from(new Uint8Array(hashBuffer))
        .map(b => b.toString(16).padStart(2, '0'))
        .join('');
};

// dist/fallback.js — pure JS implementation for unknown environments:
export const hash = (data) => purJSHash(data);
```

Optional native addon with graceful fallback:

```json
{
  "exports": {
    ".": {
      "node-addons": "./dist/native-addon.node",
      "node": {
        "import": "./dist/index.mjs",
        "require": "./dist/index.cjs"
      },
      "default": "./dist/index.js"
    }
  }
}
```

```javascript
// node-addons condition: only matched when native addons are preferred
// If the .node file fails to load (missing, wrong platform), falls through to "node"

// Runtime feature detection within the file itself (when conditions aren't granular enough):
// dist/index.mjs:
let nativeImpl;
try {
    nativeImpl = await import('./native-addon.node');
} catch {
    // Native addon not available (wrong arch, not compiled, etc.)
    nativeImpl = null;
}

export const compress = nativeImpl?.compress ?? purJSCompress;
```

**Q11. How do you migrate an existing CJS package to support ESM without breaking existing consumers?**

A: Migration requires adding ESM output alongside CJS without removing anything consumers currently depend on. The key principle: `exports` takes precedence over `main`, so old consumers (Node.js < 14, old bundlers) fall back to `main` automatically:

```json
// BEFORE: CJS-only package
{
  "name": "my-lib",
  "main": "./index.js",
  "types": "./index.d.ts"
}

// AFTER: Dual package — backward compatible
{
  "name": "my-lib",
  "main": "./dist/index.cjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.mts",
        "default": "./dist/index.mjs"
      },
      "require": {
        "types": "./dist/index.d.cts",
        "default": "./dist/index.cjs"
      },
      "types": "./dist/index.d.ts"
    },
    "./package.json": "./package.json"
  }
}
```

Migration checklist and common pitfalls:

```javascript
// Pitfall 1: Named exports that differ between CJS and ESM
// CJS: module.exports = { fn }           → require('my-lib').fn
//      module.exports.default = myLib    → require('my-lib').default (NOT the default)
// ESM: export default myLib              → import myLib from 'my-lib' (IS the default)
//      export { fn }                     → import { fn } from 'my-lib'

// In your CJS wrapper, re-export the default to maintain compatibility:
// dist/index.cjs (generated by tsup/rollup):
'use strict';
const { fn, MyClass } = require('./index-impl.cjs');
module.exports = { fn, MyClass };
module.exports.default = module.exports; // CJS interop: require().default works

// Pitfall 2: __dirname and __filename don't exist in ESM
// Must use import.meta.url instead:
// CJS:
const path = require('path');
const dir = __dirname;

// ESM equivalent:
import { fileURLToPath } from 'url';
import { dirname } from 'path';
const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

// Pitfall 3: require() of ESM is not supported (Node.js < 22)
// A CJS file cannot require() an .mjs file — it must use dynamic import():
// dist/compat.cjs:
async function getLib() {
    return import('./index.mjs'); // Dynamic import() works from CJS
}
// But this is async — breaks code that expects synchronous require()
// → This is why dual packages provide a SEPARATE .cjs build, not a CJS wrapper around .mjs

// Pitfall 4: Circular imports behave differently in ESM vs CJS
// CJS: circular require() gets a partially-initialized module (common pattern)
// ESM: circular imports work via live bindings — different semantics
// Check your package for circular dependencies: madge --circular src/

// Pitfall 5: JSON imports need an import assertion in ESM (Node.js 18+)
// CJS: const data = require('./data.json');  ← works
// ESM: import data from './data.json' assert { type: 'json' }; ← needs assertion
//   OR: const data = JSON.parse(fs.readFileSync('./data.json', 'utf8'));
```

**Q12. "You published an npm package and consumers are reporting that TypeScript can't find the types for subpath exports like `my-lib/utils`. What's wrong and how do you fix it?"**

A: This is the most common dual-package TypeScript bug. There are three likely causes, each with a specific fix:

```json
// Diagnosis: consumer does:
// import { helper } from 'my-lib/utils';
// TypeScript error: "Cannot find module 'my-lib/utils' or its type declarations"

// Cause 1: 'types' condition missing from the subpath export
// BROKEN:
{
  "exports": {
    "./utils": {
      "import": "./dist/utils.mjs",
      "require": "./dist/utils.cjs"
      // No "types" condition!
    }
  }
}

// FIXED: add "types" inside each condition
{
  "exports": {
    "./utils": {
      "import": {
        "types": "./dist/utils.d.mts",
        "default": "./dist/utils.mjs"
      },
      "require": {
        "types": "./dist/utils.d.cts",
        "default": "./dist/utils.cjs"
      }
    }
  }
}
```

```json
// Cause 2: Consumer is using moduleResolution: "node" (ignores exports entirely)
// TypeScript on "node" resolution falls back to the root "types" field only
// Fix: add a typesVersions field as a fallback for old moduleResolution:
{
  "types": "./dist/index.d.ts",
  "typesVersions": {
    "*": {
      "utils": ["./dist/utils.d.ts"],
      "parser": ["./dist/parser.d.ts"]
    }
  },
  "exports": {
    "./utils": {
      "import": { "types": "./dist/utils.d.mts", "default": "./dist/utils.mjs" },
      "require": { "types": "./dist/utils.d.cts", "default": "./dist/utils.cjs" }
    }
  }
}
// typesVersions is the legacy equivalent of "types" in exports conditions
// It's needed for consumers on TS < 4.7 or moduleResolution: "node"
```

```bash
# Cause 3: The .d.mts / .d.cts files don't exist (build didn't generate them)
# Verify:
ls dist/
# Should contain: utils.mjs, utils.cjs, utils.d.mts, utils.d.cts

# Fix: update tsup config to generate dual declaration files:
# tsup.config.ts
export default defineConfig({
    entry: ['src/index.ts', 'src/utils.ts'],
    format: ['esm', 'cjs'],
    dts: true,  // This generates .d.ts; tsup 7+ also generates .d.mts and .d.cts
    outExtension({ format }) {
        return { js: format === 'esm' ? '.mjs' : '.cjs' };
    },
});

# Verify the package is correct with publint and arethetypeswrong:
npx publint                        # Checks exports map consistency
npx @arethetypeswrong/cli ./       # Checks TypeScript resolution for all moduleResolution modes
```

**Q13. "A consumer says `require('your-package')` works fine but `import defaultExport from 'your-package'` gives them `undefined` as the default. What's happening?"**

A: This is the CJS default export interop problem — one of the most common dual-package bugs. The root cause is that CommonJS doesn't have a native concept of a "default export" and the interop between CJS and ESM default exports is non-obvious:

```javascript
// The problem — your CJS file:
// dist/index.cjs
module.exports = { fn, MyClass }; // Named exports only, no .default property

// What happens when an ESM consumer imports it:
import myLib from 'your-package';
// Node.js performs "CJS default interop":
// → Takes the entire module.exports object as the "default" export
// → myLib = { fn, MyClass }   ← This WORKS, myLib is the whole object

// But if they use named imports:
import { fn } from 'your-package';
// → Node.js wraps module.exports in a namespace: { default: { fn, MyClass } }
// → TS might complain: module has no exported member 'fn' (only 'default')

// The common tsup/rollup CJS output includes an interop helper:
// dist/index.cjs (tsup output):
'use strict';
Object.defineProperty(exports, '__esModule', { value: true }); // ← magic flag
exports.fn = fn;
exports.MyClass = MyClass;
exports.default = myLib; // explicit default

// When Node.js ESM loads a CJS file with __esModule: true:
// → It uses the .default property as the ESM default export
// → Named exports (exports.fn) become named ESM exports
// → import { fn } from 'pkg' AND import pkg from 'pkg' both work
```

```typescript
// The correct fix — ensure your CJS output has both named and default exports:
// src/index.ts:
export function fn() { ... }
export class MyClass { ... }
const myLib = { fn, MyClass };
export default myLib; // Explicit default export

// tsup config: generates correct interop in both .mjs and .cjs:
// dist/index.mjs:
export { fn, MyClass };
export default myLib;

// dist/index.cjs (tsup handles interop):
Object.defineProperty(exports, '__esModule', { value: true });
exports.fn = fn;
exports.MyClass = MyClass;
exports.default = myLib;

// Verify with:
// node -e "const x = require('your-package'); console.log(x.default, x.fn)"
// node --input-type=module -e "
//   import x from 'your-package';
//   import { fn } from 'your-package';
//   console.log(x, fn);
// "
```

## Quick Reference Table

| Field | Read by | Purpose |
|---|---|---|
| `"main"` | Node.js (all), bundlers (fallback) | Entry point for CJS consumers; fallback when `exports` not supported |
| `"module"` | Bundlers only (webpack, rollup, vite) | ESM entry for bundlers; NOT read by Node.js |
| `"browser"` | Bundlers only | Browser-specific entry; can be string or object mapping node paths to browser paths |
| `"types"` / `"typings"` | TypeScript | Type declarations fallback; used when `exports` has no `types` condition |
| `"exports"` | Node.js 14+, bundlers, TS 4.7+ | Authoritative resolution map; overrides `main`/`module` for supported tools |
| `"imports"` | Node.js 14+, bundlers, TS 4.7+ | Internal package path aliases; only usable within the same package |
| `"type"` | Node.js | Whether `.js` files are ESM (`"module"`) or CJS (default `"commonjs"`) |
| `"engines"` | npm (warn), pnpm (error), CI tools | Declares required Node.js / npm / pnpm version range |
| `"typesVersions"` | TypeScript < 4.7 | Fallback for subpath type resolution when `moduleResolution: "node"` |
| `"files"` | npm | Which files to include in the published package |

| Condition | Matched by | When to use |
|---|---|---|
| `"import"` | ESM `import` statement | Main ESM entry |
| `"require"` | CJS `require()` | Main CJS entry |
| `"node"` | Any Node.js environment | Node-specific code (crypto, fs, etc.) |
| `"browser"` | Bundlers targeting browser | Browser-specific code (Web APIs) |
| `"types"` | TypeScript | Type declaration paths |
| `"default"` | Everything (fallback) | Must be last; universal fallback |
| `"development"` | Some build tools | Dev-mode builds (more logging, assertions) |
| `"production"` | Some build tools | Prod-mode builds (optimized, minified) |
| `"deno"` | Deno runtime | Deno-specific entry |
| `"worker"` | Web/Node Workers | Worker-context entry |

**Tip for interviews:** Six things separate strong candidates on this topic: (1) explaining the **dual package hazard** concretely — not just "you get two copies" but specifically that `instanceof` fails across format boundaries, singletons duplicate, and event emitters split — and knowing that the mitigation is stateless dual packages or picking one format; (2) knowing that the **`"module"` field is a bundler convention never adopted by Node.js** — Node.js only reads `"main"` and `"exports"`, so `"module"` does nothing for Node.js consumers without a bundler, and candidates who think `"module"` makes a package ESM-compatible in Node.js are wrong; (3) understanding the **`"type"` field and extension rules** precisely — `.mjs` is always ESM, `.cjs` is always CJS, `.js` depends on the nearest `package.json`'s `"type"` field, and the reason `tsup` uses `.mjs`/`.cjs` extensions is to be unambiguous regardless of where the files land; (4) knowing which **TypeScript `moduleResolution` settings** read `"exports"` and which don't — `"node"` ignores it entirely, `"node16"`/`"nodenext"` requires explicit `.js` extensions, `"bundler"` is the modern choice for bundled projects — and that `typesVersions` is the fallback for old TS; (5) being able to explain the **`__esModule` interop flag** and why CJS files generated by tsup/rollup include it — without it, `import defaultExport from 'pkg'` gets the entire `module.exports` object as the default rather than `module.exports.default`; and (6) knowing that **`publint` and `@arethetypeswrong/cli` exist** and what they check — candidates who have actually published packages use these tools and can speak to the specific errors they catch (missing `types` conditions, `.d.mts` not generated, fallback missing for legacy `moduleResolution`).
