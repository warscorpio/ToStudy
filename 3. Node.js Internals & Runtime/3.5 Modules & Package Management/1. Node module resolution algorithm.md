## Topic A: CommonJS Resolution Algorithm

### Section A1: Core Algorithm Steps

**Q1. What are the top-level steps of `require(X)` from a module at path Y, in order?**

A: Node.js resolves `require(X)` through seven ordered steps — the first match wins and resolution stops:

```
require(X) from module at path Y:

Step 1: Is X a core module (e.g., 'fs', 'path', 'http')?
        → YES: return the built-in module immediately. STOP.

Step 2: Does X begin with '/'?
        → Treat Y as the filesystem root (absolute path).

Step 3: Does X begin with './', '../', or '/'?
        → LOAD_AS_FILE(Y/X)     — try as a file
        → LOAD_AS_DIRECTORY(Y/X) — try as a directory with index/package.json
        → THROW "not found" if both fail.

Step 4: Does X begin with '#'?
        → LOAD_PACKAGE_IMPORTS(X, dirname(Y))  — self-referencing via "imports" field
        → THROW "not found" if not matched.

Step 5: LOAD_PACKAGE_SELF(X, dirname(Y))
        → Can the CURRENT package's "exports" field satisfy X?

Step 6: LOAD_NODE_MODULES(X, dirname(Y))
        → Search each node_modules/ up the directory tree.

Step 7: THROW "MODULE_NOT_FOUND" error.
```

The order is critical: core modules always win (Step 1) before any file search. Relative/absolute paths (Step 3) are resolved before walking `node_modules` (Step 6). This prevents a local `node_modules/fs` from hijacking the built-in.

**Q2. How does Node.js resolve built-in (core) modules, and what is the `node:` prefix for?**

A: Core modules are compiled into the Node.js binary itself — they have no file on disk. When the specifier matches a known core module name (`fs`, `path`, `http`, `crypto`, `events`, etc.), Node.js returns the built-in immediately, without any file system access. The `node:` prefix (`require('node:fs')`) is an **explicit, unambiguous** way to require a built-in. It was introduced (stable in Node.js 14.18+) to solve two problems: (1) some npm packages have the same name as built-ins (`events`, `punycode`, `assert`) — `require('events')` could resolve to either; (2) in ESM, `import 'fs'` is ambiguous while `import 'node:fs'` is unambiguous. The `node:` prefix always means the built-in — it cannot be shadowed by anything in `node_modules`. It is now the recommended style for new code, especially ESM.

```js
// Both work for CJS — `node:` is preferred for clarity:
const fs1 = require('fs');        // might ambiguously match a node_modules/fs
const fs2 = require('node:fs');   // unambiguous — always the built-in

// For ESM, node: prefix is required in some contexts:
import fs from 'node:fs/promises'; // ✓ unambiguous
import fs from 'fs/promises';       // ✓ also works but less explicit

// Core modules (partial list):
// assert, buffer, child_process, cluster, crypto, dgram, dns,
// events, fs, http, https, module, net, os, path, perf_hooks,
// process, readline, repl, stream, string_decoder, timers,
// tls, url, util, v8, vm, worker_threads, zlib
```

**Q3. How are relative and absolute paths resolved, and what is the role of `__dirname`?**

A: Relative specifiers (`./ ../`) are resolved relative to the **directory of the requiring module** — captured in the `__dirname` variable. `require('./utils')` from `/project/src/app.js` looks for `/project/src/utils` (then tries file extensions). `require('../config')` looks for `/project/config`. Absolute specifiers (starting with `/`) are resolved from the filesystem root — rare in application code, more common in tooling. The key invariant: `__dirname` is the directory of the *current file*, not the current working directory (`process.cwd()`). This ensures modules find their own siblings correctly regardless of where Node was launched from.

```js
// /project/src/app.js
console.log(__dirname); // '/project/src'
console.log(__filename); // '/project/src/app.js'

require('./utils');       // → resolve '/project/src/utils'
require('../config');     // → resolve '/project/config'
require('/etc/app.conf'); // → absolute path (unusual)

// __dirname vs process.cwd():
// Running from /project: node src/app.js
// __dirname   = '/project/src' (always the module's directory)
// process.cwd() = '/project'   (the launch directory — changes with cd)

// Always use __dirname for file paths relative to the current module:
const configPath = path.join(__dirname, '../config/database.json'); // ✓
const configBad  = path.join(process.cwd(), 'config/database.json'); // ✗ fragile
```

**Q4. What is `LOAD_AS_FILE`, and in what order are file extensions tried?**

A: `LOAD_AS_FILE(X)` tries to load `X` as a file, testing extensions in a fixed order:

```
LOAD_AS_FILE(X):
  1. If X is an existing file → load it (format determined by extension or package.json "type")
  2. If X.js  exists → load X.js  as JavaScript
  3. If X.json exists → load X.json, parse as JSON, export as object
  4. If X.node exists → load X.node as a native C++ addon (.node binary)
  STOP — no other extensions are tried automatically.
```

Only three extensions are tried: `.js`, `.json`, `.node`. TypeScript's `.ts`, `.tsx`, `.mjs`, `.cjs` are NOT automatically tried — they require tools like `ts-node`, `tsx`, or explicit specifiers. The format of `.js` files is determined by the nearest `package.json`'s `"type"` field: `"type": "module"` makes `.js` files ESM; `"type": "commonjs"` (the default) makes them CJS. `.mjs` files are always ESM; `.cjs` files are always CJS, regardless of `package.json`.

```
require('./config')  →  tries, in order:
  1. /path/config      (exact file — maybe config.js was passed without extension)
  2. /path/config.js
  3. /path/config.json
  4. /path/config.node

require('./data.json') →  tries:
  1. /path/data.json  ✓  (exact file exists)
  → loads and parses as JSON, returns the object

require('./native')  →  tries:
  1. /path/native       (no extension file — not found)
  2. /path/native.js    (not found)
  3. /path/native.json  (not found)
  4. /path/native.node  ✓  (native addon — loads with dlopen)
```

**Q5. What is `LOAD_AS_DIRECTORY`, and what does it do when `require('./utils')` points to a folder?**

A: `LOAD_AS_DIRECTORY(X)` handles the case where X is (or could be) a directory:

```
LOAD_AS_DIRECTORY(X):
  1. If X/package.json exists:
     a. Parse it; read the "main" field (e.g., "main": "./lib/index.js")
     b. If "main" is falsy → skip to step 2
     c. Let M = X + "/" + main_value
     d. LOAD_AS_FILE(M)   — try M, M.js, M.json, M.node
     e. LOAD_INDEX(M)     — try M/index.js, M/index.json, M/index.node
     f. THROW if still not found
  2. LOAD_INDEX(X):       — try X/index.js, X/index.json, X/index.node
  3. THROW "not found"

LOAD_INDEX(X):
  1. X/index.js   exists → load
  2. X/index.json exists → parse and load
  3. X/index.node exists → load native addon
```

The `"main"` field in `package.json` declares the entry point for directory-style imports. Without it, `index.js` is the fallback convention. Note: if `"exports"` is also defined in `package.json`, it takes complete precedence over `"main"` — `"main"` is only consulted if `"exports"` is absent or doesn't match.

```
require('./utils') where utils/ is a directory:

  Step 1: Check utils/package.json
    If exists and has "main": "lib/core.js":
      → try utils/lib/core.js    (LOAD_AS_FILE)
      → try utils/lib/core.json
      → try utils/lib/core.node
      → try utils/lib/core/index.js  (LOAD_INDEX on the main value)
      → THROW if all fail

  Step 2: (if no package.json or no "main"):
    → try utils/index.js
    → try utils/index.json
    → try utils/index.node
    → THROW if all fail
```

**Q6. What is `LOAD_NODE_MODULES`, and how does Node.js walk the directory tree?**

A: `LOAD_NODE_MODULES(X, START)` searches for X in every `node_modules` directory from `START` up to the filesystem root. The path list is computed by `NODE_MODULES_PATHS(START)`:

```
NODE_MODULES_PATHS('/home/user/project/src'):
  → /home/user/project/src/node_modules
  → /home/user/project/node_modules
  → /home/user/node_modules
  → /home/node_modules
  → /node_modules

For each DIR in that list:
  LOAD_PACKAGE_EXPORTS(X, DIR)  — check DIR/X/package.json "exports"
  LOAD_AS_FILE(DIR/X)           — try DIR/X, DIR/X.js, DIR/X.json, DIR/X.node
  LOAD_AS_DIRECTORY(DIR/X)      — try DIR/X/package.json, DIR/X/index.js
```

This walking behavior is how **hoisting** works in npm: when package A and package B both depend on `lodash@4`, npm places one copy in `/project/node_modules/lodash` (shared), and both packages find it by walking up. When packages require incompatible versions, npm places local copies in each package's own `node_modules`, found before the shared one. The tree walk stops at the filesystem root — `node_modules` folders inside another `node_modules` are never skipped (they follow the same algorithm).

```
/project/
  node_modules/
    lodash/          ← found for all packages (hoisted)
  packages/
    app/
      node_modules/
        semver/      ← app's local semver (different version)
      src/
        index.js     ← require('semver') from here:
                        1. /project/packages/app/src/node_modules/semver  (not found)
                        2. /project/packages/app/node_modules/semver      ✓ (local version)
                     ← require('lodash') from here:
                        1. /project/packages/app/src/node_modules/lodash  (not found)
                        2. /project/packages/app/node_modules/lodash      (not found)
                        3. /project/packages/node_modules/lodash           (not found)
                        4. /project/node_modules/lodash                    ✓ (hoisted)
```

**Q7. What does `require.resolve()` do, and when would you use it over `require()`?**

A: `require.resolve(specifier, options?)` runs the full resolution algorithm and returns the **resolved file path** as a string — without actually loading the module or executing its code. It is used when you need the absolute path for some purpose other than loading: validating a module exists, passing a path to a child process, computing relative paths between modules, or checking which version of a package was resolved (by reading the returned path). `require.resolve.paths(specifier)` returns the list of directories that would be searched for a non-relative specifier — useful for debugging resolution issues. The `options.paths` array lets you override the search directories.

```js
// Get resolved path without loading:
const lodashPath = require.resolve('lodash');
// → '/project/node_modules/lodash/lodash.js'

// Validate module exists:
function moduleExists(specifier) {
  try { require.resolve(specifier); return true; }
  catch { return false; }
}

// Resolve relative to a different base:
const fromDifferentDir = require.resolve('./config', {
  paths: ['/other/directory']
});
// Searches as if the requiring module is in /other/directory

// Inspect the search path:
require.resolve.paths('lodash');
// → ['/project/src/node_modules', '/project/node_modules', '/home/user/node_modules', ...]

// Useful: pass resolved path to child_process.fork instead of a relative path:
const workerPath = require.resolve('./worker');
child_process.fork(workerPath); // absolute path — safe regardless of cwd
```

**Q8. What is `require.cache`, how does it work, and what are the implications?**

A: `require.cache` is a plain object keyed by the **resolved absolute file path** of each loaded module, with the `Module` object as the value. The first time any file is required, Node.js loads it, executes it, caches its `exports` in `require.cache`, and returns those exports. Subsequent `require()` calls for the same path return the cached `exports` object directly — the file is not re-read or re-executed. This means: (1) **modules are singletons** — all requirers share the same exported object; mutations to an export are visible to all requirers; (2) **require is synchronous** — it blocks until the module and all its dependencies are loaded; (3) you can **manually invalidate** the cache by deleting an entry, forcing the next require to reload the file. Cache invalidation is the basis of hot-reload patterns in development.

```js
// Module is a singleton — shared exports object:
const a = require('./config');
const b = require('./config');
console.log(a === b); // true — same object reference

// Mutating shared exports (usually an anti-pattern):
a.value = 99;
console.log(b.value); // 99 — same object!

// Inspect the cache:
console.log(Object.keys(require.cache));
// → ['/project/node_modules/lodash/lodash.js', '/project/src/app.js', ...]

// Manual cache invalidation (hot-reload):
function freshRequire(module) {
  const resolved = require.resolve(module);
  delete require.cache[resolved];
  return require(resolved);
}

// Child module cache: each Module object tracks its own children
const mod = require.cache[require.resolve('./config')];
console.log(mod.children.map(c => c.filename)); // modules that config.js required
```

**Q9. What is `NODE_PATH`, and why is it discouraged in modern projects?**

A: `NODE_PATH` is an environment variable containing a colon-separated (or semicolon on Windows) list of additional directories that Node.js searches for modules — appended to the end of the `NODE_MODULES_PATHS` list. It was commonly used to create "absolute imports" (e.g., `require('components/Button')` instead of `require('../../components/Button')`). It is discouraged because: (1) it creates implicit, environment-dependent behavior — the same code resolves differently depending on the shell environment; (2) it's not portable (the env var must be set on every machine); (3) modern alternatives are better: package `exports` with `imports` for self-referencing, TypeScript `paths` (compile-time only), or bundler alias plugins. The correct modern solution for absolute imports within a package is the `imports` field in `package.json`.

### Section A2: Advanced CJS Mechanics

**Q10. How do circular dependencies work in CJS, and what is returned when the cycle is detected?**

A: When module A requires module B, and module B requires module A (before A finishes loading), Node.js returns A's **partially-completed `exports`** object to B — whatever A has assigned to `exports` so far. Node.js detects the cycle using the module cache: when A is first required, it's immediately added to `require.cache` with an empty `exports` object *before its code runs*. When B (called during A's execution) requires A again, the cache entry is found — so B gets A's current (partial) exports without re-executing A. The practical implication: properties assigned to `module.exports` before the circular require work; properties assigned after do not. Using the `exports.x = ...` style (mutating the cached reference) is more cycle-safe than `module.exports = newObject` (which replaces the cached reference).

```js
// ─── a.js ─────────────────────────────────────────────────
exports.aName = 'module A'; // ← assigned before requiring B

const b = require('./b');

exports.bRef = b; // ← assigned AFTER b.js has finished — too late for b's require(./a)

// ─── b.js ─────────────────────────────────────────────────
const a = require('./a'); // ← cycle: a is loading! Gets partial exports of a

exports.bName  = 'module B';
exports.aName  = a.aName;  // 'module A' ✓ (was assigned before require('./b'))
exports.bRef   = a.bRef;   // undefined  ✗ (not yet assigned when b required a)

// ─── main.js ──────────────────────────────────────────────
const a = require('./a');
const b = require('./b');
// a.aName = 'module A', a.bRef = { bName:'module B', aName:'module A', bRef:undefined }
// b.aName = 'module A', b.bRef = undefined

// Key invariant: always assign exports.x = before any require() that creates a cycle
```

**Q11. What is the `main` field in `package.json`, and how does its resolution differ from `exports`?**

A: `"main"` specifies the entry point when a package is required as a directory — it's a relative path from the package root. `"main": "./lib/index.js"` means `require('my-package')` loads `./lib/index.js`. Limitations: (1) `"main"` only sets the primary entry point — there's no way to restrict which internal files are accessible; (2) no conditional resolution (can't specify different files for CJS vs ESM); (3) no subpath exports. The `"exports"` field (Node.js 12+) supersedes `"main"` with encapsulation and conditions. When both are present, `"exports"` takes complete precedence for `"exports"`-compatible paths; `"main"` is used as a fallback for older Node.js versions that don't understand `"exports"`. For packages targeting Node.js 12+, `"exports"` should be the primary configuration with `"main"` as a fallback for older tooling.

```json
{
  "name": "my-lib",
  "main": "./dist/index.js",        // legacy: used by old Node.js and old tooling
  "exports": {                       // modern: takes precedence over main in Node.js 12+
    ".": "./dist/index.js"
  }
}

// Without "exports" — internal files are accessible:
require('my-lib/src/internal'); // ✓ (no encapsulation)

// With "exports" — only listed paths work:
require('my-lib');              // ✓ (mapped to ./dist/index.js)
require('my-lib/src/internal'); // ✗ ERR_PACKAGE_PATH_NOT_EXPORTED
```

**Q12. What is the `__filename`/`__dirname`/`require` availability in different module types?**

A: These module-local globals are **only available in CommonJS modules** — they are injected by the CJS module wrapper. Node.js wraps every CJS module's code in a function:

```js
(function(exports, require, module, __filename, __dirname) {
  // your module code here
});
```

In ESM modules (`.mjs` files or `.js` with `"type": "module"`), these do NOT exist. The ESM equivalents: `import.meta.url` provides the file URL (`file:///path/to/file.js`); `import.meta.dirname` (Node.js 21.2+) and `import.meta.filename` provide equivalents. For older ESM support: derive them from `import.meta.url` using `new URL`. The `require` function also doesn't exist in ESM — use `import()` (dynamic import) or `createRequire` from the `module` built-in for calling CJS from ESM.

```js
// CJS — available natively:
console.log(__filename); // '/path/to/file.js'
console.log(__dirname);  // '/path/to'

// ESM — must derive from import.meta.url:
import { fileURLToPath } from 'url';
import { dirname }       from 'path';

const __filename = fileURLToPath(import.meta.url); // ESM equivalent
const __dirname  = dirname(__filename);             // ESM equivalent

// Or use the new Node.js 21.2+ meta fields directly:
const __filename = import.meta.filename;
const __dirname  = import.meta.dirname;

// require() in ESM — use createRequire:
import { createRequire } from 'module';
const require = createRequire(import.meta.url);
const data    = require('./data.json'); // ✓ use CJS require from ESM
```

## Topic B: Package Configuration and ESM

### Section B1: The `exports` Map

**Q13. What is the `exports` field in `package.json`, and how does it differ from `main`?**

A: `"exports"` is a package configuration field that provides **encapsulation and conditional resolution**. It defines an explicit map of which paths a package exposes and what file each maps to. When `"exports"` is defined, Node.js uses it exclusively for all entry-point resolution — access to any path not listed in `"exports"` throws `ERR_PACKAGE_PATH_NOT_EXPORTED`. This is the encapsulation feature: internal implementation files (`src/`, `lib/`) are no longer accessible by outside packages unless explicitly exported. The `"exports"` field supports: (1) single entry point (`"exports": "./dist/index.js"`), (2) named subpath exports (`"exports": { ".": "...", "./utils": "..." }`), (3) conditional exports (per environment), and (4) subpath patterns (glob-like patterns). It is stable since Node.js 12 and is the modern standard for package entry-point configuration.

```json
{
  "name": "my-sdk",
  "exports": {
    // The main entry point:
    ".": "./dist/index.js",

    // Named subpath (accessible as require('my-sdk/client')):
    "./client": "./dist/client.js",
    "./server": "./dist/server.js",

    // Subpath pattern (matches my-sdk/plugins/anything):
    "./plugins/*": "./dist/plugins/*.js",

    // package.json itself (needed for some tooling):
    "./package.json": "./package.json"
  }
}

// From consumer code:
require('my-sdk');            // → dist/index.js
require('my-sdk/client');     // → dist/client.js
require('my-sdk/plugins/auth');// → dist/plugins/auth.js
require('my-sdk/src/internal');// ✗ ERR_PACKAGE_PATH_NOT_EXPORTED
```

**Q14. What are conditional exports, what conditions does Node.js check, and what is the evaluation order?**

A: Conditional exports allow the same subpath to resolve to different files depending on the environment. Each export target can be an **object of conditions** rather than a string. Node.js evaluates conditions in **object key order** — the first matching condition wins. Built-in conditions that Node.js checks:

- **`import`** — the consumer used `import` (ESM)
- **`require`** — the consumer used `require()` (CJS)
- **`node`** — running in Node.js (as opposed to browsers or other runtimes)
- **`node-addons`** — Node.js with native addons support
- **`browser`** — set by bundlers targeting browser environments
- **`development`** / **`production`** — set by bundlers
- **`default`** — unconditional fallback; always matches if reached

Custom conditions can be added and activated with `--conditions` CLI flag or `node:module`'s `conditions` API. The invariant: `"default"` should always be the last condition; `"require"` and `"import"` are mutually exclusive per call.

```json
{
  "exports": {
    ".": {
      "import": {
        "types":   "./dist/esm/index.d.ts",
        "default": "./dist/esm/index.js"
      },
      "require": {
        "types":   "./dist/cjs/index.d.ts",
        "default": "./dist/cjs/index.js"
      },
      "default": "./dist/cjs/index.js"
    },
    "./client": {
      "browser": "./dist/browser/client.js",
      "node":    "./dist/node/client.js",
      "default": "./dist/node/client.js"
    }
  }
}

// Evaluation: import 'my-sdk' from ESM code
// → check "import" → found → check inner "types" (no match, tools-only) → "default" → ✓
// → resolves to ./dist/esm/index.js

// Evaluation: require('my-sdk') from CJS code
// → check "import" → NO (it's require) → check "require" → found → "default" → ✓
// → resolves to ./dist/cjs/index.js
```

**Q15. What are subpath patterns, and how do wildcards work in the `exports` map?**

A: Subpath patterns allow one exports entry to match many paths using `*` as a wildcard. The pattern `"./plugins/*": "./src/plugins/*.js"` means any `require('pkg/plugins/X')` maps to `./src/plugins/X.js`, where the `*` in both sides is replaced by the same matched string. Wildcards: (1) match any string segment including path separators (`/`), so `my-sdk/plugins/auth/oauth` matches `"./plugins/*"` with `*` = `auth/oauth`; (2) can only appear once per key and value; (3) the value can reference `*` to insert the matched string. This is more expressive than the old `"directories"` field and safer than exposing entire directory trees.

```json
{
  "exports": {
    ".":           "./dist/index.js",
    "./utils/*":   "./dist/utils/*.js",
    "./plugins/*": "./dist/plugins/*.js"
  }
}

// require('my-lib/utils/string')     → ./dist/utils/string.js
// require('my-lib/utils/array')      → ./dist/utils/array.js
// require('my-lib/plugins/auth')     → ./dist/plugins/auth.js
// require('my-lib/plugins/auth/oauth')→ ./dist/plugins/auth/oauth.js  (/ in wildcard)
// require('my-lib/internal/secret')  → ✗ ERR_PACKAGE_PATH_NOT_EXPORTED

// Combined with conditions:
{
  "./plugins/*": {
    "import": "./dist/esm/plugins/*.js",
    "require": "./dist/cjs/plugins/*.js"
  }
}
```

**Q16. What are `imports` (package self-imports), and how do internal package paths use them?**

A: The `"imports"` field in `package.json` defines **private subpath imports** for a package's own source files. It is the internal counterpart to `"exports"`. A specifier starting with `#` (e.g., `#utils`, `#db/client`) is resolved via the `"imports"` map of the **nearest enclosing package**. This enables path aliases within a package — avoiding long relative paths like `'../../../utils'` — without leaking the aliases to consumers. `"imports"` also supports conditional resolution (node/browser conditions), making it powerful for internal cross-environment compatibility.

```json
// package.json
{
  "name": "my-app",
  "imports": {
    "#utils":     "./src/utils/index.js",
    "#db/*":      "./src/database/*.js",
    "#config":    {
      "development": "./src/config/dev.js",
      "production":  "./src/config/prod.js",
      "default":     "./src/config/default.js"
    }
  }
}
```

```js
// src/features/user/service.js — instead of:
// const db = require('../../../database/client');
// Use self-import via "imports":
const db     = require('#db/client');   // → ./src/database/client.js
const utils  = require('#utils');       // → ./src/utils/index.js
const config = require('#config');      // → conditional: dev.js / prod.js

// # imports are PRIVATE — consumers of 'my-app' cannot use #db/client
// Consumers of the package only see what "exports" exposes
```

**Q17. What error is thrown when an `exports`-defined package path is not found, and how does it differ from a missing module?**

A: When a package has an `"exports"` field and the requested subpath is not listed, Node.js throws `ERR_PACKAGE_PATH_NOT_EXPORTED` — a specific error distinct from `MODULE_NOT_FOUND`. The distinction: `MODULE_NOT_FOUND` means the package or file doesn't exist at all; `ERR_PACKAGE_PATH_NOT_EXPORTED` means the package exists and the file probably exists, but the package author has explicitly chosen not to expose that path. This is an **intentional encapsulation error**, not a missing-file error. Before `"exports"` existed, any internal file was accessible — `require('lodash/src/internal/_util')` would work. With `"exports"`, the package controls its public API surface. The fix: request only officially exported paths, or (if you control the package) add the path to `"exports"`.

```js
// Package with "exports" that doesn't list ./src/internal:
require('my-package/src/internal');

  }

```

**Q18. How does the dual CJS/ESM package pattern work, and what is the "wrapper" anti-pattern to avoid?**

A: A dual package exposes both a CJS and an ESM build, letting `require()` callers get CJS and `import` callers get ESM. The correct approach is **two separate build outputs** in the `exports` map with `"require"` and `"import"` conditions. The critical risk: **dual package hazard** — if a package is loaded as both CJS (`require`) and ESM (`import`) in the same process (through different parts of the dependency graph), there are two separate module instances with potentially different state. This violates the singleton expectation. The safe patterns: (1) pure ESM (no CJS build); (2) pure CJS (no ESM build — simplest); (3) stateless dual package (safe because no shared state); (4) CJS wrapper — the ESM build is a thin re-export of the CJS build, ensuring one instance. Never put stateful objects (caches, connections, registries) in a dual package — the hazard makes two instances possible.

```json
{
  "name": "my-package",
  "main": "./dist/cjs/index.js",
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",  // ESM consumers get ESM build
      "require": "./dist/cjs/index.js"  // CJS consumers get CJS build
    }
  }
}
```

```js
// ─── dist/esm/index.js — CJS WRAPPER PATTERN (safest for stateful packages) ───
// Rather than a separate ESM build, re-export the CJS build:
import cjsModule from '../cjs/index.js'; // dynamic import of CJS into ESM wrapper
export const { createClient, version } = cjsModule; // re-export named exports
export default cjsModule;

// This ensures: there is ONE module instance regardless of how it's loaded.
// Both `require('my-package')` and `import 'my-package'` get the same CJS module.
```

### Section B2: ESM Module System

**Q19. How does ESM (import/export) resolution differ from CJS (require) resolution?**

A: Three critical differences: **(1) Mandatory file extensions**: `import './utils'` throws — you must write `import './utils.js'`. Node.js ESM does not try to add `.js`, `.json`, `.node` automatically. **(2) No automatic `index.js`**: `import './utils/'` (with trailing slash, if supported) does not automatically resolve to `utils/index.js`. **(3) Specifier forms**: ESM recognizes `node:` built-in specifiers, `bare` specifiers (node_modules lookup — same as CJS), `relative` specifiers (must include extension), and `absolute URL` specifiers (`file:///path.js`). The node_modules traversal logic is similar to CJS, but ESM respects the `"exports"` map (for the `"import"` condition) and does not fall back to the `"main"` field if `"exports"` exists. ESM is always asynchronous at the top level (the module graph is analyzed and loaded before any code runs), while CJS is synchronous.

```js
// CJS — extensions are optional, index.js is implicit:
const utils = require('./utils');     // ✓ tries utils.js, utils/index.js
const data  = require('./data');      // ✓ tries data.json

// ESM — extensions and filenames are required:
import utils from './utils.js';      // ✓ explicit
import utils from './utils';         // ✗ ERR_MODULE_NOT_FOUND (no extension)
import utils from './utils/index.js';// ✓ explicit index
import utils from './utils/';        // ✗ directory import not supported in ESM

// ESM consuming CJS — works via named default export:
import lodash from 'lodash';         // ✓ CJS default import
const { map } = await import('lodash'); // ✓ dynamic import of CJS

// CJS consuming ESM — NOT synchronously possible:
const esm = require('./esm-module.mjs'); // ✗ ERR_REQUIRE_ESM (Node.js < 22)
// Node.js 22+ added experimental require(esm) support
```

**Q20. What does `"type": "module"` in `package.json` do, and what are `.mjs` and `.cjs` extensions for?**

A: `"type": "module"` changes the interpretation of all `.js` files within that package from CommonJS (default) to ECMAScript Modules. Without this field, `.js` files are CJS. File extension overrides: `.mjs` always means ESM regardless of `package.json`; `.cjs` always means CJS regardless of `package.json`. This allows gradual migration: a CJS project can include isolated `.mjs` ESM files without converting the whole package. A pure ESM project (`"type": "module"`) can include isolated `.cjs` CJS files. The lookup chain for format determination: explicit extension (`.mjs` = ESM, `.cjs` = CJS) → nearest `package.json`'s `"type"` field (`"module"` = ESM, `"commonjs"` or absent = CJS).

```
Format determination for a file at /project/src/app.js:

1. Is extension .mjs?   → Always ESM
   Is extension .cjs?   → Always CJS

2. Walk up from /project/src/ looking for package.json:
   /project/src/package.json: found? look at "type" field
   /project/package.json: found? look at "type" field

3. "type": "module"    → app.js is ESM
   "type": "commonjs"  → app.js is CJS
   "type" absent       → app.js is CJS (default)

Practical usage:
  package.json: { "type": "module" }     → all .js files are ESM
  package.json: {}  (or omitted "type")  → all .js files are CJS (historical default)
  my-module.mjs → always ESM (overrides package.json)
  my-module.cjs → always CJS (overrides package.json)
```

**Q21. What is `import()` (dynamic import), and when is it the only way to cross the CJS/ESM boundary?**

A: `import(specifier)` is an async function that dynamically loads a module at runtime, returning a Promise that resolves to the module's namespace object. It works in both CJS and ESM contexts, enabling: (1) **lazy loading** — load a module only when needed (reduces startup time); (2) **conditional loading** — choose a module at runtime based on conditions; (3) **CJS loading ESM** — the only way for a CJS module to consume an ESM module (synchronous `require` of ESM is not supported prior to Node.js 22). ESM modules can be loaded synchronously (static imports analyzed at parse time) or dynamically (at runtime via `import()`). The `await import()` pattern in ESM, and `.then()` in CJS, handle the asynchronous nature.

```js
// ─── CJS consuming ESM (only via dynamic import) ─────────────
// sync-require-esm.cjs:
async function loadEsmModule() {
  const { doSomething } = await import('./esm-module.mjs');
  return doSomething();
}

// Cannot do at module top level (await requires ESM or async function):
// const esm = await import('./esm-module.mjs'); // ✗ top-level await in CJS

// ─── Lazy loading in ESM ──────────────────────────────────────
// Delay loading a heavy module until it's needed:
let parser;
async function parseDocument(input) {
  if (!parser) {
    ({ default: parser } = await import('heavy-parser'));
  }
  return parser.parse(input);
}

// ─── Conditional platform loading ────────────────────────────
const platform = process.platform;
const { readdir } = await import(
  platform === 'win32' ? './win32/fs.js' : './posix/fs.js'
);
```

**Q22. How does the `--experimental-require-module` flag (Node.js 22+) allow `require()` of ESM?**

A: Node.js 22 introduced experimental support for requiring ESM modules synchronously via `require()` when the ESM module has no top-level `await`. This resolves the historical CJS/ESM boundary: `require('./esm-module.mjs')` (or any ESM `.js` file in a `"type": "module"` package) returns the module's exports as a plain object. The limitation: the ESM module cannot use top-level `await` — it must be synchronously completable. Without the flag, `require()` of ESM throws `ERR_REQUIRE_ESM`. With it enabled (`--experimental-require-module` or via `REQUIRE_MODULE_LOAD_OP_SUPPORT_FLAG`), the synchronous import works. This enables gradual ESM adoption without the async overhead of `import()`.

## Topic C: Advanced and Cross-Topic

**Q23. How do symlinks affect module resolution, and what does `--preserve-symlinks` do?**

A: When Node.js follows a symlink to resolve a module (common in workspaces and monorepos where `node_modules` entries are symlinked to packages in the workspace), it **dereferences the symlink by default** — the module's `__dirname`, `require.resolve`, and cache key all reflect the **real path** (the symlink target), not the symlink location. This matters for relative requires inside a symlinked package: a symlinked package at `/project/node_modules/my-package → /project/packages/my-package` will have `__dirname = /project/packages/my-package/src`, so relative requires resolve from the real location. `--preserve-symlinks` changes this: modules are cached and resolved by the symlink path, not the real path. This can cause the same code to be loaded twice (once via symlink, once via real path) if both paths are used — generally harmful. Avoid `--preserve-symlinks` in most cases; the default behavior (resolve symlinks) is correct.

```
Monorepo structure:
  /project/
    packages/
      utils/
        src/index.js   (real location)
    node_modules/
      utils → ../../packages/utils  (symlink)

require('utils') from /project/packages/app/src/app.js:
  → LOAD_NODE_MODULES finds: /project/node_modules/utils → symlink
  → Node follows symlink to: /project/packages/utils
  → DEFAULT: caches as /project/packages/utils/src/index.js (real path)
    __dirname inside utils = /project/packages/utils/src
  → --preserve-symlinks: caches as /project/node_modules/utils/src/index.js (symlink path)
    __dirname inside utils = /project/node_modules/utils/src
    (different! relative requires may break)
```

**Q24. What are the performance implications of deep `node_modules` traversal, and how does npm v7+ hoisting mitigate them?**

A: For each `require('some-module')` from a deeply nested file, Node.js generates a path list with one entry per directory level up to the root, then checks each `node_modules` directory for the module. For a file at depth 10, that's 10 `stat` system calls per `require()` in the worst case (module not found at any higher level). Node.js mitigates this through: (1) the **module cache** — each resolved path is cached after the first successful lookup, so repeated `require('lodash')` never traverses again; (2) **require() is synchronous** — the traversal blocks the event loop, but for cached modules it's a single hash lookup. npm's **hoisting** algorithm minimizes nesting depth — packages with compatible versions are raised to the top-level `node_modules`, so most lookups succeed at the first or second directory level. The worst case (many incompatible nested packages) is rare in well-maintained dependency trees.

**Q25. State the invariant for each major resolution step in one sentence each.**

A:
- **Core module check**: built-in modules (`fs`, `path`, `http`) are always resolved from the Node.js binary first, before any file system search, and can never be shadowed by `node_modules` packages of the same name when using the bare specifier.
- **Relative path resolution**: a `./` or `../` specifier is always resolved relative to `__dirname` of the requiring file — the result is independent of the working directory from which Node.js was launched.
- **`LOAD_AS_FILE`**: extensions are tried in fixed order `.js → .json → .node` only — no other extensions are tried automatically, and the exact file (with extension explicitly written) is always tried first.
- **`LOAD_AS_DIRECTORY`**: the `"main"` field in `package.json` is consulted before `index.js`; if no `package.json` or no valid `"main"` field, `index.js` is the unconditional fallback.
- **`LOAD_NODE_MODULES`**: the traversal always starts from the current module's directory and walks toward the filesystem root, stopping at the first `node_modules` directory that satisfies the request — directories at higher levels are tried only if lower levels don't have the module.
- **`"exports"` encapsulation**: when a package defines `"exports"`, accessing any unlisted subpath throws `ERR_PACKAGE_PATH_NOT_EXPORTED` — the package's `"exports"` field is an exhaustive contract of its public API surface.
- **Module cache**: every successfully resolved module is cached by its resolved absolute path; all subsequent `require()` calls for the same resolved path return the identical `exports` object without re-executing the module.

## Problem 2 — Module Cache Invalidation and Hot-Reload

### Problem

Implement `hotRequire(modulePath)` that: (1) returns a fresh module load by clearing the cached version and all its cached dependencies; (2) supports a `watch(modulePath, onChange)` pattern that re-loads a module whenever its file changes on disk.

```js
const config = hotRequire('./config');
// config now reflects the current file state, even if it was cached

watch('./config', (freshConfig) => {
  updateServerConfig(freshConfig);
});
```

### Pattern Recognition
`require.cache` stores modules by resolved absolute path. Clearing a module requires clearing it AND clearing any modules that required it (to force them to re-require the fresh version). Use `fs.watch` for file change detection; on change, clear the relevant cache entries and re-require.

### Key Insight
The module cache records each module's `children` (modules it required) and `parent`. To fully hot-reload a module tree, you must clear the cache for the module AND for all of its transitive dependencies (otherwise cached modules that required the changed file still hold the old reference). After clearing, a fresh `require()` re-executes the module file.

### Solution

```js
const path = require('path');
const fs   = require('fs');

/**
 * Recursively clears a module and all its children from require.cache.
 * Returns a Set of the cleared paths.
 */
function clearModuleCache(resolvedPath, cleared = new Set()) {
  if (cleared.has(resolvedPath)) return cleared; // avoid infinite loops (circular deps)

  const mod = require.cache[resolvedPath];
  if (!mod) return cleared;

  cleared.add(resolvedPath);

  // Recursively clear children (modules that this module required):
  for (const child of mod.children) {
    // Only clear children that are not node_modules (avoid clearing all of lodash):
    if (!child.filename.includes('node_modules')) {
      clearModuleCache(child.filename, cleared);
    }
  }

  delete require.cache[resolvedPath];
  return cleared;
}

/**
 * Require a module fresh — bypassing and clearing the cache.
 */
function hotRequire(modulePath) {
  const resolved = require.resolve(modulePath);
  clearModuleCache(resolved);
  return require(resolved); // re-executes the module
}

/**
 * Watch a module file for changes and re-require it on change.
 * Returns an unwatch() function to stop watching.
 */
function watch(modulePath, onChange, { debounceMs = 100 } = {}) {
  const resolved = require.resolve(modulePath);
  let debounceTimer = null;

  const watcher = fs.watch(resolved, (event) => {
    if (event !== 'change') return;

    // Debounce: editors often write files in multiple events:
    clearTimeout(debounceTimer);
    debounceTimer = setTimeout(() => {
      try {
        const fresh = hotRequire(resolved);
        onChange(fresh);
      } catch (err) {
        console.error(`[hot-reload] Error reloading ${modulePath}:`, err.message);
      }
    }, debounceMs);
  });

  // Initial load:
  const initial = require(resolved);
  onChange(initial);

  return function unwatch() {
    watcher.close();
    clearTimeout(debounceTimer);
  };
}

// ─── Usage ────────────────────────────────────────────────────
// config.js:  module.exports = { port: 3000, debug: true };

const unwatch = watch('./config', (config) => {
  console.log('Config updated:', config);
  // Update server with new config...
});

// Later, when done watching:
unwatch();
```

### Trace

```
Initial state:
  require.cache = {
    '/project/src/config.js': Module { exports: { port:3000 } },
    '/project/src/app.js':    Module { ... }
  }

hotRequire('./config'):
  resolve('./config') → '/project/src/config.js'
  clearModuleCache('/project/src/config.js'):
    mod.children = []  (config.js doesn't require other local files)
    cleared = { '/project/src/config.js' }
    delete require.cache['/project/src/config.js']
  require('/project/src/config.js'):
    → Module not in cache → re-execute config.js
    → Returns fresh { port:3000, debug:true }

File config.js changes (port: 3000 → port: 4000):
  fs.watch fires 'change'
  debounce timer starts (100ms)
  After 100ms:
    clearModuleCache('/project/src/config.js')
    require('/project/src/config.js') → { port: 4000, debug: true }
    onChange({ port: 4000, debug: true }) called ✓
```

### Edge Cases
- **Circular dependencies**: the `cleared` Set prevents infinite recursion in the recursive clear.
- **Not clearing `node_modules`**: clearing third-party packages on every reload would be catastrophically slow. The `node_modules` guard ensures only local files are cleared.
- **File rename vs change**: `fs.watch` may emit 'rename' events on some systems (Linux `inotify`); watch for both 'change' and 'rename' if needed.

### Follow-up Questions
- "What if the hot-reloaded module changes its export shape?" — All existing references in other modules still point to the old export object. Hot-reload only helps if consumers re-read the export on each use (e.g., re-require or access via the returned fresh module).
- "Does this work for ESM modules?" — No. ESM modules are immutable once loaded — `import.meta.url` cache cannot be deleted from the outside. Hot-reload in ESM requires bundler support or VM-level reimplementation.

## Problem 4 — Path Alias Resolver

### Problem

Implement a `registerAliases(aliases)` function that intercepts `require()` calls and rewrites specifiers matching alias patterns (like `@/` for the project root, `~components/` for a components directory). This enables TypeScript-like path aliases at runtime.

```js
registerAliases({
  '@/':        path.join(__dirname, 'src/'),
  '~components': path.join(__dirname, 'src/components'),
  '~utils':      path.join(__dirname, 'src/utils'),
});

// In any module:
const Button = require('~components/Button'); // → src/components/Button
const api    = require('@/api/client');        // → src/api/client
```

### Pattern Recognition
Hook into Node.js module resolution by monkey-patching `Module._resolveFilename` — the internal function Node calls before LOAD_AS_FILE. Intercept the specifier, check against alias patterns, rewrite if matched, then call the original resolver.

### Key Insight
`Module._resolveFilename(request, parent, isMain, options)` is Node.js's internal resolution entry point. It is not a public API (the `_` prefix), but it is the stable hook point for custom resolution. Each alias is either a prefix replacement (`@/src/` → absolute path) or an exact replacement (`~utils` → absolute path). After rewriting, the original resolver handles the rest of the algorithm (LOAD_AS_FILE, LOAD_AS_DIRECTORY, etc.).

### Solution

```js
const Module = require('module');
const path   = require('path');

function registerAliases(aliases) {
  const originalResolve = Module._resolveFilename.bind(Module);

  // Pre-sort: longer prefixes first to prevent short aliases shadowing long ones
  const sortedAliases = Object.entries(aliases).sort(
    ([a], [b]) => b.length - a.length
  );

  Module._resolveFilename = function(request, parent, isMain, options) {
    for (const [alias, target] of sortedAliases) {
      let rewritten = null;

      if (alias.endsWith('/') && request.startsWith(alias)) {
        // Prefix alias: '@/foo/bar' → '/abs/path/src/foo/bar'
        rewritten = path.join(target, request.slice(alias.length));
      } else if (request === alias || request.startsWith(alias + '/')) {
        // Exact or subpath alias: '~utils' or '~utils/string'
        const suffix = request.slice(alias.length);
        rewritten = path.join(target, suffix);
      }

      if (rewritten) {
        // Recursively resolve the rewritten path through the normal algorithm:
        try {
          return originalResolve(rewritten, parent, isMain, options);
        } catch {
          // Fall through if rewritten path fails — try next alias
        }
      }
    }

    // No alias matched — use normal resolution:
    return originalResolve(request, parent, isMain, options);
  };

  // Return an unregister function:
  return function unregister() {
    Module._resolveFilename = originalResolve;
  };
}

// ─── Usage ────────────────────────────────────────────────────
const unregister = registerAliases({
  '@/':          path.resolve(__dirname, 'src/'),
  '~components': path.resolve(__dirname, 'src/components'),
  '~utils':      path.resolve(__dirname, 'src/utils'),
  '~types':      path.resolve(__dirname, 'src/types'),
});

// These now resolve correctly:
const Button = require('~components/Button');  // → src/components/Button.js
const api    = require('@/services/api');       // → src/services/api.js
const { format } = require('~utils');           // → src/utils/index.js

unregister(); // clean up when done

// Equivalent ESM approach: use import maps (Node.js experimental) or a loader:
// node --import ./register-aliases.js my-module.mjs
```

```

  sortedAliases (sorted by length, longest first):
    ['~components', '/project/src/components']  (14 chars)
    ['~utils',      '/project/src/utils']        (6 chars)
    ['@/',          '/project/src/']              (2 chars)

  Check '~components':
    request = '~components/Button'
    alias = '~components', not ending in '/'
```

### Edge Cases
- **Re-entrant resolution**: `originalResolve(rewritten, ...)` with the rewritten path goes back through the normal algorithm — if the rewritten path itself starts with an alias (unusual but possible), it's not re-processed (we call `originalResolve`, not our patched version). To support chained aliases, use `Module._resolveFilename(rewritten, ...)` (which calls our patch) instead.
- **ESM**: `Module._resolveFilename` only intercepts `require()`. For ESM `import`, use `--experimental-loader` with a custom `resolve` hook.

### Follow-up Questions
- "Is `Module._resolveFilename` stable across Node.js versions?" — It's a private API (`_` prefix) that has existed for many Node.js versions but is not in the public API contract. It may change in major versions. Production code should test across Node.js versions. The public equivalent is a custom loader (`module.register()` in Node.js 20.6+).

## Problem 5 — Circular Dependency Detector

### Problem

Implement `detectCircularDependencies(entryPath)` that loads a module entry point, inspects the `require.cache` module graph after loading, and returns all detected circular dependency chains.

```js
const cycles = detectCircularDependencies('./src/app.js');
// → [['./src/a.js', './src/b.js', './src/a.js'],
//    ['./src/x.js', './src/y.js', './src/z.js', './src/x.js']]
```

### Pattern Recognition
The `require.cache` after loading contains every module and its `children` (modules it directly required). A circular dependency forms a directed cycle in this graph. DFS with a "currently in stack" tracking detects back-edges (cycle indicators).

### Key Insight
`module.children` in `require.cache` is the adjacency list — each module's direct dependencies. A DFS that tracks the current traversal path detects cycles when an already-in-path node is encountered. Filter to only application files (exclude `node_modules`) to focus on actionable cycles.

### Solution

```js
const path = require('path');

function detectCircularDependencies(entryPath) {
  const resolved = require.resolve(entryPath);

  // Load the entry point (populates require.cache):
  require(resolved);

  const cycles = [];
  const visited = new Set();    // fully explored nodes
  const stack   = new Set();    // nodes in current DFS path
  const stackArr = [];          // ordered current path (for cycle extraction)

  function isAppFile(filePath) {
    return !filePath.includes('node_modules') && !filePath.startsWith('<'); // exclude built-ins
  }

  function dfs(modulePath) {
    if (!isAppFile(modulePath)) return;
    if (visited.has(modulePath)) return; // already fully explored — no new cycles from here
    if (stack.has(modulePath)) {
      // Back-edge found: extract the cycle from stackArr:
      const cycleStart = stackArr.indexOf(modulePath);
      const cycle      = stackArr.slice(cycleStart).concat(modulePath);
      cycles.push(cycle.map(p => path.relative(process.cwd(), p)));
      return;
    }

    stack.add(modulePath);
    stackArr.push(modulePath);

    const mod = require.cache[modulePath];
    if (mod) {
      for (const child of mod.children) {
        dfs(child.filename);
      }
    }

    stackArr.pop();
    stack.delete(modulePath);
    visited.add(modulePath);
  }

  // Start DFS from the entry:
  dfs(resolved);

  // Also check all app modules in case entry doesn't reach all files:
  for (const filePath of Object.keys(require.cache)) {
    dfs(filePath);
  }

  return cycles;
}

// ─── Usage ────────────────────────────────────────────────────
const cycles = detectCircularDependencies('./src/index.js');

if (cycles.length === 0) {
  console.log('✓ No circular dependencies detected');
} else {
  console.warn(`⚠️  Found ${cycles.length} circular dependency chain(s):`);
  cycles.forEach((cycle, i) => {
    console.warn(`  ${i + 1}: ${cycle.join(' → ')}`);
  });
}
// Sample output:
// ⚠️  Found 2 circular dependency chain(s):
//   1: src/a.js → src/b.js → src/a.js
//   2: src/services/auth.js → src/models/user.js → src/services/auth.js
```

### Trace

```
  index.js → a.js, b.js
  a.js     → b.js
  b.js     → a.js   ← CYCLE!
  b.js     → c.js
  c.js     → (no local deps)

DFS from index.js:

    visit a.js: stack={index,a}, path=[index,a]
      visit b.js: stack={index,a,b}, path=[index,a,b]
        visit a.js: a IS in stack! → CYCLE FOUND
          cycleStart = indexOf(a) = 1
          cycle = path[1..] + 'a' = [a, b, a]
          cycles.push(['src/a.js', 'src/b.js', 'src/a.js'])
        visit c.js: stack={index,a,b,c}, path=[index,a,b,c]

```

### Edge Cases
- Modules loaded via dynamic `require()` (inside functions) appear in `require.cache` only if they've been called — static analysis at load time may miss them.
- The `visited` set prevents reporting the same cycle multiple times from different starting points.

### Follow-up Questions
- "How does ESM handle circular dependencies differently?" — ESM uses live bindings: circular imports don't get a "partial export" snapshot; instead, the imported binding is a live reference that becomes defined when the exporting module runs. ESM cycles are generally safer but can still cause `undefined` access if the binding is used before it's initialized.

## Problem 6 — `require()` Interceptor for Testing

### Problem

Implement `mockRequire(moduleName, mockFactory)` and `restoreAll()` — a lightweight mock registry that intercepts `require()` for specific modules and returns mock implementations instead of the real modules.

```js
mockRequire('axios', { get: jest.fn(), post: jest.fn() });
mockRequire('./database', createFakeDatabase());

const service = require('./user-service'); // uses mocked axios and database
await service.fetchUser(1);

restoreAll();
```

### Pattern Recognition
Insert a mock into `require.cache` at the resolved path — Node.js's cache check happens before any file system access, so the mock is returned without executing the real file. Store original entries to restore later.

### Key Insight
`require.cache[resolvedPath]` must be a `Module`-like object with at least an `exports` property. Creating a minimal `Module` wrapper around the mock satisfies this. The resolution must use `require.resolve()` to get the same cache key that real consumers would use.

### Solution

```js
const Module = require('module');
const path   = require('path');

const originalCache = new Map(); // path → original Module (or undefined)

function mockRequire(specifier, mockValue, { from = process.cwd() } = {}) {
  let resolved;
  try {
    // Resolve from the given directory (to match what consuming modules see):
    resolved = require.resolve(specifier, { paths: [from] });
  } catch {
    // Module doesn't exist (e.g., mocking a not-yet-installed package):
    // Create a synthetic path key:
    resolved = path.join(from, 'node_modules', specifier);
  }

  // Store original for restore:
  if (!originalCache.has(resolved)) {
    originalCache.set(resolved, require.cache[resolved]); // may be undefined
  }

  // Create a synthetic Module object:
  const mockModule = new Module(resolved);
  mockModule.exports  = mockValue;
  mockModule.filename = resolved;
  mockModule.loaded   = true;

  require.cache[resolved] = mockModule;

  // Return a function to restore just this mock:
  return function restore() {
    const original = originalCache.get(resolved);
    if (original === undefined) {
      delete require.cache[resolved];
    } else {
      require.cache[resolved] = original;
    }
    originalCache.delete(resolved);
  };
}

function restoreAll() {
  for (const [resolved, original] of originalCache) {
    if (original === undefined) {
      delete require.cache[resolved];
    } else {
      require.cache[resolved] = original;
    }
  }
  originalCache.clear();
}

// ─── Usage ────────────────────────────────────────────────────
const http  = { get: () => Promise.resolve({ data: [] }) };
const restore = mockRequire('axios', http);

const service = require('./user-service');
await service.fetchUser(1); // uses the mock axios

restore(); // restore just axios
// OR:
restoreAll(); // restore everything

// ─── Testing pattern (Jest-compatible) ────────────────────────
describe('UserService', () => {
  let axiosMock;
  beforeEach(() => {
    axiosMock = { get: jest.fn(), post: jest.fn() };
    mockRequire('axios', axiosMock);
    // Clear user-service from cache so it re-requires the mocked axios:
    delete require.cache[require.resolve('./user-service')];
  });
  afterEach(() => restoreAll());

  it('fetches a user', async () => {
    axiosMock.get.mockResolvedValue({ data: { id: 1, name: 'Ada' } });
    const svc = require('./user-service');
    const user = await svc.fetchUser(1);
    expect(user.name).toBe('Ada');
    expect(axiosMock.get).toHaveBeenCalledWith('/users/1');
  });
});
```

### Trace

```
  resolve('axios') → '/project/node_modules/axios/index.js'
  original = require.cache['/project/node_modules/axios/index.js']
```

### Follow-up Questions
- "Why do you need to delete user-service from cache too?" — If user-service is already cached, it holds a reference to the real axios (captured when it first loaded). Clearing user-service forces re-execution, which picks up the mocked axios from the cache.
- "Does this work if user-service uses ES6 `import` for axios?" — No. ESM live bindings cannot be patched via `require.cache`. For ESM mocking, use `jest.mock()` (babel transform), `esmock` library, or `--experimental-vm-modules`.

## Problem 7 — Resolution Debugger

### Problem

Implement `traceRequire(specifier, fromPath)` that simulates and logs every step of Node.js's resolution algorithm without actually loading any files — useful for debugging "MODULE_NOT_FOUND" errors.

```js
traceRequire('lodash', '/project/src/app.js');
// Logs each attempted path and whether it was found or skipped
```

### Solution

```js
const fs   = require('fs');
const path = require('path');

function traceRequire(specifier, fromPath) {
  const log = (found, msg) => console.log(`  ${found ? '✓' : '✗'} ${msg}`);

  console.log(`\nTracing: require('${specifier}') from ${fromPath}`);

  // Step 1: Core module?
  const builtins = require('module').builtinModules;
  const specBase = specifier.replace(/^node:/, '');
  if (builtins.includes(specBase) || specifier.startsWith('node:')) {
    log(true, `CORE MODULE: '${specifier}' is a Node.js built-in. Resolution stops here.`);
    return;
  }
  log(false, `Not a core module`);

  const fromDir = path.dirname(fromPath);

  // Step 3: Relative/absolute path?
  if (specifier.startsWith('./') || specifier.startsWith('../') || specifier.startsWith('/')) {
    console.log(`  → Relative/absolute path resolution from: ${fromDir}`);
    const target = path.resolve(fromDir, specifier);
    traceLoadAsFile(target, log);
    traceLoadAsDirectory(target, log);
    return;
  }

  // Step 6: node_modules traversal:
  console.log(`  → Bare specifier: searching node_modules up the tree`);
  const dirs = getNodeModulesPaths(fromDir);

  for (const dir of dirs) {
    const base = path.join(dir, specifier);
    const pkgJson = path.join(base, 'package.json');

    if (fs.existsSync(base)) {
      // Check for exports map:
      if (fs.existsSync(pkgJson)) {
        const pkg = JSON.parse(fs.readFileSync(pkgJson, 'utf8'));
        if (pkg.exports) {
          log(true, `FOUND: ${dir}/${specifier}/package.json with "exports" field`);
          console.log(`       "exports" maps "." to: ${JSON.stringify(pkg.exports['.'] ?? pkg.exports)}`);
          return;
        }
        if (pkg.main) {
          const mainPath = path.join(base, pkg.main);
          if (fs.existsSync(mainPath)) {
            log(true, `FOUND: ${mainPath} (via package.json "main")`);
            return;
          }
        }
      }
      const indexJs = path.join(base, 'index.js');
      if (fs.existsSync(indexJs)) {
        log(true, `FOUND: ${indexJs} (via index.js fallback)`);
        return;
      }
    }
    log(false, `${dir} — ${specifier} not found`);
  }

  console.log(`  ✗ MODULE_NOT_FOUND: '${specifier}' could not be resolved`);
  console.log(`\n  Searched directories:`);
  dirs.forEach(d => console.log(`    ${d}`));
}

function traceLoadAsFile(X, log) {
  const attempts = [X, X + '.js', X + '.json', X + '.node'];
  for (const attempt of attempts) {
    const exists = fs.existsSync(attempt) && fs.statSync(attempt).isFile();
    log(exists, `LOAD_AS_FILE: ${attempt}`);
    if (exists) return true;
  }
  return false;
}

function traceLoadAsDirectory(X, log) {
  const pkgJson = path.join(X, 'package.json');
  if (fs.existsSync(pkgJson)) {
    const pkg = JSON.parse(fs.readFileSync(pkgJson, 'utf8'));
    if (pkg.main) {
      log(true, `  package.json "main": ${pkg.main}`);
      return traceLoadAsFile(path.join(X, pkg.main), log);
    }
  }
  const indexJs = path.join(X, 'index.js');
  log(fs.existsSync(indexJs), `LOAD_INDEX: ${indexJs}`);
}

function getNodeModulesPaths(start) {
  const dirs = [];
  let current = start;
  while (true) {
    if (path.basename(current) !== 'node_modules') {
      dirs.push(path.join(current, 'node_modules'));
    }
    const parent = path.dirname(current);
    if (parent === current) break;
    current = parent;
  }
  return dirs;
}

traceRequire('lodash', '/project/src/features/auth.js');
// Tracing: require('lodash') from /project/src/features/auth.js
//   ✗ Not a core module
//   → Bare specifier: searching node_modules up the tree
//   ✗ /project/src/features/node_modules — lodash not found
//   ✗ /project/src/node_modules — lodash not found
//   ✓ FOUND: /project/node_modules/lodash/package.json with "exports" field
//     "exports" maps "." to: "./lodash.js"

traceRequire('./helpers', '/project/src/app.js');
// Tracing: require('./helpers') from /project/src/app.js
//   ✗ LOAD_AS_FILE: /project/src/helpers
//   ✓ LOAD_AS_FILE: /project/src/helpers.js
```

## Quick Reference — Resolution Algorithm Cheat Sheet

```
require(X) from module at Y — decision order:

  1. X is 'fs', 'path', 'http'...?     → built-in, STOP
     X is 'node:fs'?                   → built-in, STOP (unambiguous)

  2. X starts with './' '../' '/'?     → RELATIVE / ABSOLUTE path
     a. LOAD_AS_FILE(resolved):
        try: X, X.js, X.json, X.node
     b. LOAD_AS_DIRECTORY(resolved):
        try: package.json → "main" → LOAD_AS_FILE(main) + LOAD_INDEX(main)
        try: index.js, index.json, index.node

  3. X starts with '#'?                → LOAD_PACKAGE_IMPORTS (private self-ref)
     Look in nearest package.json "imports" field

  4. LOAD_PACKAGE_SELF                 → current package's "exports" match X?

  5. LOAD_NODE_MODULES(X, dirname(Y)):
     NODE_MODULES_PATHS(dirname(Y)):
       dirname(Y)/node_modules
       dirname(dirname(Y))/node_modules
       ... up to root /node_modules
     For each DIR:
       If DIR/X/package.json has "exports": use exports map
       Else: LOAD_AS_FILE(DIR/X), LOAD_AS_DIRECTORY(DIR/X)

  6. THROW MODULE_NOT_FOUND

─────────────────────────────────────────────────────────────────────────

package.json field priority for entry point:

  "exports" (present) → used exclusively, encapsulates internals
  "main"   (no "exports") → legacy entry point, no encapsulation
  "index.js" (no "main")   → fallback convention

─────────────────────────────────────────────────────────────────────────

Condition evaluation order (first match wins):

  "import"      → ESM (import keyword / import())
  "require"     → CJS (require() function)
  "node"        → Node.js runtime
  "browser"     → browser bundler target
  "node-addons" → native addon support
  "development" / "production" → bundler-set
  "default"     → unconditional fallback (put last)
  "types"       → TypeScript type resolution only

─────────────────────────────────────────────────────────────────────────

ESM vs CJS resolution differences:

  CJS:    require('./utils')    → tries utils, utils.js, utils/index.js  (implicit)
  ESM:    import './utils'      → ✗ (must write './utils.js' or './utils/index.js')

  CJS:    require('fs')         → built-in fs
  ESM:    import 'node:fs'      → built-in fs (preferred)
  ESM:    import 'fs'           → built-in fs (also works, node: recommended)

  CJS:    circular deps → partial exports (snapshot at time of cycle)
  ESM:    circular deps → live bindings (become defined when exporter runs)
```

## Common Bugs Checklist

Before debugging a module resolution error, verify:

1. **`MODULE_NOT_FOUND` for a package that is installed?** — Check: (a) the package name is spelled correctly (case-sensitive on Linux); (b) run `npm install` / `yarn install` to ensure `node_modules` is populated; (c) for a monorepo, the package may be in the workspace's root `node_modules`, not a nested one — check the hoist result; (d) use `require.resolve.paths('package-name')` to see where Node looked; (e) if using `--require` or loader files, those run before `node_modules` is fully available.

2. **`ERR_PACKAGE_PATH_NOT_EXPORTED` after upgrading a dependency?** — The package added an `"exports"` field, encapsulating its internals. You were importing `require('pkg/src/internal')` which worked before (no exports map) but now fails. Fix: use only the officially exported paths. If you're a maintainer: add the needed path to `"exports"`. Workaround (fragile): import the absolute path directly via `require('/absolute/path/to/node_modules/pkg/src/internal')`.

3. **CJS module loaded twice (two separate instances of a singleton)?** — Cause: the module is resolved via two different paths (e.g., symlink path vs real path, or two different `node_modules` locations with two incompatible versions). Check: `require.cache` — are there two entries for what should be the same module? Fix: ensure consistent resolution by checking for duplicate versions in `node_modules` (`npm ls package-name`), or use `--preserve-symlinks=false` (default) if symlinks are causing dual resolution.

4. **Extensions not resolved — `MODULE_NOT_FOUND` for a file that exists?** — CJS only tries `.js`, `.json`, `.node` — not `.ts`, `.jsx`, `.tsx`, `.mjs`, `.cjs` automatically. Either: (a) write the extension explicitly; (b) configure `ts-node` / `tsx` / `babel-register` for `.ts` support; (c) add a custom loader. For ESM, extensions are ALWAYS required — `import './utils'` never tries `.js` automatically.

5. **`require()` of an ESM file throws `ERR_REQUIRE_ESM`?** — CJS cannot synchronously `require()` a file marked as ESM (`.mjs` or `.js` in a `"type":"module"` package). Fix: (a) use `import()` (dynamic, async); (b) convert the ESM module to CJS; (c) if the ESM module is yours, add a CJS build with a `"require"` condition in `"exports"`; (d) Node.js 22+ with `--experimental-require-module` allows `require()` of ESM without top-level `await`.

6. **Circular dependency returning `{}` or `undefined` for an export?** — A requires B, B requires A, and the needed export from A wasn't assigned before the `require('./b')` call. Fix: assign the export *before* requiring the circular module, or refactor to break the cycle (extract shared code to a third module C that neither A nor B requires). Or use `module.exports.fn = function(){}` style (mutates the existing cache reference) rather than `module.exports = { fn: function(){} }` (replaces it).

7. **`require()` inside `if` blocks or functions — module not found at startup?** — `require()` is synchronous and lazily loaded when called. If a required module has a syntax error or `MODULE_NOT_FOUND`, the error throws only when that `require()` call executes — not at startup. This can cause surprising runtime errors. Pre-validate required modules at startup with a try-catch wrapper if the dependency is optional, or ensure required optional modules always exist.

8. **`__dirname` and `require` not available in an `.mjs` file?** — These are CJS module wrapper injections, not available in ESM. Use `fileURLToPath(import.meta.url)` for `__filename`, `path.dirname(__filename)` for `__dirname`, and `createRequire(import.meta.url)` from the `module` built-in for a CJS-compatible `require` in ESM context.

9. **`"exports"` map with `"types"` condition not resolving TypeScript types?** — TypeScript 4.x and earlier ignore conditions in `"exports"` maps. Set `"moduleResolution": "bundler"`, `"node16"`, or `"nodenext"` in `tsconfig.json` (TypeScript 4.7+) to enable conditional exports type resolution. Also verify the `"types"` condition is listed before `"default"` in each export (conditions are checked in key order).

10. **Installed package as both `dependency` and `devDependency`?** — If a package appears in both, npm may install two separate copies (or merge, depending on version). This creates two instances in `require.cache`, breaking singletons. Always put a package in only one of `dependencies`, `devDependencies`, or `peerDependencies` — not multiple.

---

**Final Tip:** At the 5 YOE level, the decisive signal for module resolution questions is knowing *the exact ordered steps* and *what stops evaluation vs what falls through*. The mental model: *"require(X) tries to match X against five categories in strict order — built-in, relative/absolute path, package self-reference via imports, package self-reference via exports, and bare node_modules lookup — stopping the moment any category produces a file; within each category, LOAD_AS_FILE then LOAD_AS_DIRECTORY are tried in that order."* For exports maps: *"when `exports` is defined, it is the entire public API — any path not listed throws ERR_PACKAGE_PATH_NOT_EXPORTED; conditions are evaluated left-to-right in object key order with the first match winning; `default` must be last; `require` and `import` are mutually exclusive conditions that Node.js sets automatically based on how the module is loaded."* For the CJS vs ESM boundary: *"CJS is synchronous so it cannot `require()` an ESM module (async module graph); ESM can `import` a CJS module via static import (gets the `module.exports` as the default export) or via `import()` (dynamic); the `node:` prefix is the unambiguous way to require built-ins in any context and should be the default choice in new code."*
