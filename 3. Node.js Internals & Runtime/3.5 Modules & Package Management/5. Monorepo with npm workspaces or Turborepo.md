# Monorepo with npm Workspaces or Turborepo — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a monorepo, why would you choose one, and what problems does it create?**
A: A monorepo is a single version-controlled repository that contains multiple distinct projects — typically a set of apps and packages that belong to the same organization or product. The alternative is a polyrepo: one repository per project.

Why choose a monorepo:

- **Atomic cross-package changes:** In a polyrepo, changing a shared library and updating all its consumers requires N PRs across N repos, coordinated versioning, and a publish cycle. In a monorepo, one commit updates the library and all consumers simultaneously — the diff is always consistent and reviewable in one place.
- **Unified tooling:** One ESLint config, one TypeScript config, one CI pipeline definition, one test runner setup. No drift across repos.
- **Code sharing without npm publish:** An internal `@acme/ui` package can be imported by `@acme/web` and `@acme/mobile` without publishing to any registry — workspaces handle the resolution.
- **Easier refactoring:** Rename a function across 10 packages in one IDE session with full type-safety.
- **Visibility:** All code is visible to all engineers without managing repository access.

Problems it creates:

- **Build speed at scale:** Without caching, every CI run rebuilds every package even if only one file changed. This is the core scaling problem Turborepo and Nx solve.
- **Tooling complexity:** Standard npm/yarn/pnpm wasn't designed for monorepos; workspace-aware task running, dependency graphing, and cache invalidation require additional tooling.
- **Flaky ownership:** Without clear package boundaries, engineers accidentally depend on internals they shouldn't. `tsconfig` path aliases and import enforcement rules help.
- **Large clone size:** All history for all projects in one repo — mitigated with shallow clones or VCS tools like Git sparse checkout.

**Q2. What are npm workspaces, and how do they differ from the old approach of using `npm link`?**
A: npm workspaces (added in npm 7, Node.js 15 era) is npm's built-in monorepo support. You declare workspace locations in the root `package.json`, and npm installs all packages into a single `node_modules` at the root, symlinking local packages so they can reference each other as if installed from the registry.

```json
// Root package.json
{
  "name": "acme-monorepo",
  "private": true,
  "workspaces": [
    "apps/*",
    "packages/*"
  ]
}
```

With this configuration:

```
acme-monorepo/
├── package.json           ← root, declares workspaces
├── node_modules/
│   ├── react/             ← hoisted, shared by all packages
│   └── @acme/
│       ├── ui/            ← symlink → packages/ui
│       └── utils/         ← symlink → packages/utils
├── apps/
│   ├── web/package.json   ← can import @acme/ui without publishing
│   └── mobile/package.json
└── packages/
    ├── ui/package.json
    └── utils/package.json
```

`npm link` vs workspaces:

| Dimension | `npm link` | npm workspaces |
|---|---|---|
| Scope | Manual, per-package, per-machine | Declared in config, automatic for all workspace members |
| Install | Two-step: `link` in source, `link pkg` in consumer | One `npm install` at root sets everything up |
| `node_modules` | Each package has its own full `node_modules` | Single hoisted `node_modules` at root |
| Version conflicts | Common — link doesn't resolve peer deps consistently | npm handles hoisting and conflict resolution |
| CI reproducibility | Fragile — links are filesystem-local, don't survive fresh CI checkouts | Fully reproducible from `package-lock.json` |
| Housekeeping | `npm unlink` to clean up; easy to forget | Declarative — nothing to clean up |

**Q3. What does "dependency hoisting" mean in a monorepo and when does it cause problems?**
A: Hoisting is the npm/yarn mechanism of installing a dependency once at the root `node_modules` rather than inside each package's own `node_modules`. If `packages/ui` and `apps/web` both need `react@18`, hoisting installs it once at `<root>/node_modules/react` and both find it via Node.js's module resolution walk-up.

```
Without hoisting:                    With hoisting:
apps/
  web/
    node_modules/
      react@18  ←── duplicated       <root>/node_modules/react@18  ←── shared
packages/
  ui/
    node_modules/
      react@18  ←── duplicated
```

Problems hoisting causes:

```json
// packages/utils/package.json — does NOT declare lodash as a dependency
{
  "name": "@acme/utils",
  "dependencies": {}   ← lodash not listed
}
```

```javascript
// packages/utils/src/index.js
import _ from 'lodash';  // Works locally because lodash is hoisted from another package!
                          // Breaks in production / other repos where it isn't hoisted
```

This is a **phantom dependency** — a package successfully imports something it didn't declare because the dependency happens to be hoisted from a sibling. It works locally, breaks elsewhere. pnpm solves this with a non-flat `node_modules` using symlinks and a content-addressable store; npm/yarn workspaces require discipline (linting with `eslint-plugin-import` or `publint`).

Version conflicts: if `packages/a` needs `lodash@4` and `packages/b` needs `lodash@3`, only one can be hoisted. npm keeps one at the root and puts the other inside the package's local `node_modules` — this can lead to two instances of the same module in a bundle, breaking singleton patterns (like React context).

## Section 2: npm Workspaces in Practice

**Q4. How do you run commands across all packages in an npm workspace monorepo?**
A: npm provides the `--workspaces` (or `-ws`) flag and `--workspace` (singular) for targeting one package:

```bash
# Run `build` script in ALL workspace packages
npm run build --workspaces

# Run `build` only in packages/ui
npm run build --workspace=packages/ui
# or by package name:
npm run build --workspace=@acme/ui

# Install a dependency in a specific package (not the root)
npm install lodash --workspace=packages/utils

# Install a local package as a dependency of another package
npm install @acme/ui --workspace=apps/web
# This adds "@acme/ui": "*" to apps/web/package.json and symlinks it

# Run a command in all packages that have that script (ignore missing):
npm run test --workspaces --if-present

# Add a devDependency to the root (shared tooling like eslint, typescript):
npm install typescript --save-dev  # at root, no --workspace flag
```

The critical limitation: `npm run build --workspaces` runs scripts in parallel by default with no awareness of dependency order. If `apps/web` depends on `packages/ui`, and both have a `build` script, npm might build `apps/web` before `packages/ui` is done — resulting in stale artifacts. This is why Turborepo exists.

**Q5. How do you structure `tsconfig.json` in a monorepo for cross-package TypeScript type-checking?**
A: The standard pattern uses TypeScript project references — a mechanism that makes `tsc` aware of the dependency graph between packages:

```
acme-monorepo/
├── tsconfig.base.json        ← shared compiler options
├── tsconfig.json             ← root, references all packages
├── packages/
│   ├── utils/
│   │   ├── tsconfig.json     ← references tsconfig.base.json
│   │   └── src/
│   └── ui/
│       ├── tsconfig.json     ← references @acme/utils
│       └── src/
└── apps/
    └── web/
        ├── tsconfig.json     ← references @acme/ui and @acme/utils
        └── src/
```

```json
// tsconfig.base.json — shared compiler options
{
  "compilerOptions": {
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "moduleResolution": "bundler",
    "target": "ES2022",
    "module": "ESNext",
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}

// packages/utils/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src",
    "composite": true          // ← REQUIRED for project references
  },
  "include": ["src"]
}

// packages/ui/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src",
    "composite": true
  },
  "references": [
    { "path": "../utils" }   // ← declares dependency on @acme/utils
  ],
  "include": ["src"]
}

// apps/web/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "outDir": "dist", "rootDir": "src", "composite": true },
  "references": [
    { "path": "../../packages/ui" },
    { "path": "../../packages/utils" }
  ]
}

// Root tsconfig.json — used by editors and `tsc -b` to build the whole graph
{
  "files": [],
  "references": [
    { "path": "packages/utils" },
    { "path": "packages/ui" },
    { "path": "apps/web" }
  ]
}
```

```bash
# Build the entire dependency graph in correct order:
tsc --build  # or tsc -b
# TypeScript resolves the project reference graph and builds packages/utils first,
# then packages/ui (which depends on it), then apps/web

# Type-check without emitting:
tsc --build --noEmit
```

The `composite: true` flag tells TypeScript to emit `.d.ts` files and a `.tsbuildinfo` cache file — this enables incremental builds where only changed packages are recompiled.

**Q6. How do you share ESLint, Prettier, and other tooling configs across packages in a monorepo?**
A: The pattern is a shared config package that all other packages extend:

```
packages/
  eslint-config/          ← internal package, not published
    package.json
    index.js
  tsconfig/               ← shared tsconfig base
    package.json
    base.json
    react.json
    node.json
```

```json
// packages/eslint-config/package.json
{
  "name": "@acme/eslint-config",
  "version": "0.0.0",
  "private": true,
  "main": "index.js",
  "dependencies": {
    "@typescript-eslint/eslint-plugin": "^7.0.0",
    "@typescript-eslint/parser": "^7.0.0",
    "eslint-config-prettier": "^9.0.0"
  }
}
```

```javascript
// packages/eslint-config/index.js
module.exports = {
  parser: '@typescript-eslint/parser',
  plugins: ['@typescript-eslint'],
  extends: [
    'eslint:recommended',
    'plugin:@typescript-eslint/recommended',
    'prettier'
  ],
  rules: {
    'no-console': 'warn',
    '@typescript-eslint/no-explicit-any': 'error'
  }
};
```

```json
// apps/web/package.json — consume the shared config
{
  "devDependencies": {
    "@acme/eslint-config": "*"
  }
}
```

```javascript
// apps/web/.eslintrc.js
module.exports = {
  extends: ['@acme/eslint-config'],
  rules: {
    // app-specific overrides
  }
};
```

```json
// packages/tsconfig/base.json
{
  "compilerOptions": {
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true
  }
}
```

```json
// apps/web/tsconfig.json — extend shared tsconfig
{
  "extends": "@acme/tsconfig/base.json",
  "compilerOptions": { "outDir": "dist" }
}
```

Prettier config at the root `package.json` (it doesn't support per-package overrides well):

```json
// root package.json
{
  "prettier": {
    "semi": true,
    "singleQuote": true,
    "tabWidth": 2,
    "printWidth": 100
  }
}
```

## Section 3: Turborepo

**Q7. What problem does Turborepo solve that npm workspaces alone cannot?**
A: npm workspaces solve package linking and dependency installation. They don't solve task orchestration — specifically: running build/test/lint tasks in the correct dependency order, in parallel where possible, and with caching so that unchanged packages aren't rebuilt.

```
Dependency graph:
  @acme/utils ←── @acme/ui ←── apps/web
                         ↑
                    apps/mobile

Without Turborepo (npm --workspaces):
  npm run build --workspaces
  → Runs build in all packages in PARALLEL with no order guarantee
  → apps/web might start building before @acme/ui has emitted its dist/
  → No caching — every CI run rebuilds everything

With Turborepo:
  turbo run build
  → Resolves the dependency graph from package.json `dependencies`
  → Builds @acme/utils first (no deps)
  → Then builds @acme/ui (after utils is done) and nothing else in parallel
  → Then builds apps/web and apps/mobile in PARALLEL (both depend on ui, which is done)
  → Caches the output of each task by content hash
  → Next run: if @acme/utils didn't change, restores its build output from cache instantly
```

The key value props:

- **Task pipeline:** declare that `build` in package B depends on `build` in package A (`^build` syntax) — Turborepo schedules accordingly.
- **Local cache:** outputs are cached by a hash of inputs (source files + env vars + task config). Cache hit = zero re-execution.
- **Remote cache:** cache shared across all CI machines and developer machines (Vercel's hosted cache or self-hosted). Developer pulls cache warmed by CI — never rebuilds what CI already built.
- **Parallel execution:** tasks with no dependency relationship run concurrently, bounded by CPU count.

**Q8. How do you configure Turborepo — what does `turbo.json` define and how does the pipeline syntax work?**
A:

```json
// turbo.json — root of the monorepo
{
  "$schema": "https://turbo.build/schema.json",
  "globalDependencies": [
    ".env",               // Changes to these files invalidate ALL package caches
    "tsconfig.base.json"
  ],
  "globalEnv": [
    "NODE_ENV",           // Changes to these env vars invalidate ALL caches
    "CI"
  ],
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],  // ← KEY: run `build` in all dependencies first
      "outputs": ["dist/**", ".next/**"],  // cache these directories
      "env": ["API_URL"]        // invalidate this task's cache if API_URL changes
    },
    "test": {
      "dependsOn": ["build"],   // run SAME package's build first (no ^)
      "outputs": ["coverage/**"],
      "env": ["NODE_ENV"]
    },
    "lint": {
      "outputs": []             // lint produces no artifact — cache the exit code only
    },
    "dev": {
      "cache": false,           // never cache dev server (long-running, side-effectful)
      "persistent": true        // marks as long-running — turbo won't wait for it to exit
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "outputs": []
    }
  }
}
```

The `^` prefix is the critical syntax:

```
"dependsOn": ["^build"]  → Run `build` in all packages that THIS package depends on
                           (i.e., everything in its `dependencies`/`devDependencies`) FIRST

"dependsOn": ["build"]   → Run `build` in THIS SAME package first (before the current task)

"dependsOn": ["@acme/utils#build"]  → Run `build` in a specific named package first
```

```bash
# Run build for all packages (in dependency order, parallel where possible):
turbo run build

# Run build only for apps/web and its transitive dependencies:
turbo run build --filter=apps/web

# Run build for packages changed since the main branch:
turbo run build --filter="[origin/main]"

# Run multiple tasks:
turbo run build test lint

# Dry-run to see what would execute and cache status:
turbo run build --dry-run
```

**Q9. How does Turborepo's caching work — what is the cache key composed of and what gets cached?**
A: Every task execution produces a cache entry keyed by a hash. If the hash matches a prior run, the task is skipped and outputs are restored from cache:

```
Cache key = hash of:
  ├── Source files in the package's `inputs` (default: all files not in .gitignore)
  ├── Values of `env` variables declared in pipeline config
  ├── Values of `globalEnv` variables
  ├── Contents of `globalDependencies` files (e.g., tsconfig.base.json)
  ├── The task's pipeline config in turbo.json
  ├── The package's package.json
  └── Cache keys of all dependent tasks (transitively — if utils changed, ui's key changes)
```

What gets cached:

```json
// In pipeline config:
"build": {
  "outputs": ["dist/**", ".next/**", "*.tsbuildinfo"]
  //           ↑ These file globs are captured after a CACHE MISS run
  //             and restored on a CACHE HIT
}
```

```
Cache miss (first run or after change):
  1. turbo runs the task (e.g., `tsc --build`)
  2. After success, turbo captures all files matching `outputs` globs
  3. Stores them in ~/.turbo/cache/<hash>/ (local) or remote cache

Cache hit (nothing changed):
  1. turbo computes hash → matches a stored entry
  2. Restores all output files from cache to their original paths
  3. Replays stdout/stderr from the cached run
  4. Reports "(FULL TURBO)" — zero rebuild time

Remote cache (Vercel or self-hosted):
  1. CI runs build, fills remote cache
  2. Developer runs `turbo run build`:
      → Hash matches remote cache entry
      → Downloads outputs from remote cache
      → Local build: instant
```

Fine-tuning cache inputs:

```json
"pipeline": {
  "build": {
    "inputs": ["src/**", "package.json", "tsconfig.json"],
    // ← Override: only these files affect cache key for `build`
    // Changing README.md won't invalidate the build cache
    "outputs": ["dist/**"]
  }
}
```

**Q10. How do you use `--filter` in Turborepo to run tasks for a subset of packages?**
A: `--filter` is the primary mechanism for incremental CI — running only what's affected by a change:

```bash
# By package name (exact):
turbo run build --filter=@acme/ui

# By directory glob:
turbo run build --filter="./packages/*"

# By package name glob:
turbo run build --filter="@acme/*"

# By changed files since a git ref:
# All packages whose source files changed since origin/main:
turbo run build --filter="[origin/main]"

# Changed packages AND their dependents (downstream impact):
turbo run build --filter="...[origin/main]"
#                           ↑ the ... means "and all packages that depend on these"

# Changed packages AND their dependencies (upstream):
turbo run build --filter="[origin/main]..."
#                                       ↑ trailing ... means "and all dependencies"

# All dependents of @acme/ui (packages that import @acme/ui):
turbo run build --filter="...@acme/ui"

# All dependencies of apps/web (what apps/web depends on):
turbo run build --filter="apps/web..."

# Combine filters: run for changed packages AND apps/web specifically:
turbo run build --filter="[origin/main]" --filter="apps/web"

# Exclude a package:
turbo run build --filter="!apps/mobile"
```

In CI, the typical pattern for PR builds:

```yaml
# .github/workflows/ci.yml
- name: Turbo build
  run: turbo run build test lint --filter="[origin/main]..."
  # Rebuilds only what's affected by this PR's changes
  # and their downstream dependents
```

## Section 4: Remote Caching and CI Integration

**Q11. How do you set up Turborepo's remote cache and what are the options for hosting it?**
A: Remote caching shares the artifact cache across all CI runners and developer machines, so work done in one place is never repeated elsewhere:

```bash
# Option 1: Vercel Remote Cache (official, easiest)
# Login to Vercel from CLI:
npx turbo login
npx turbo link
# This creates .turbo/config.json with teamId and token
# All subsequent `turbo run` commands upload/download from Vercel's cache

# .turbo/config.json (auto-generated, commit this):
{
  "teamId": "team_xxxx",
  "apiUrl": "https://vercel.com"
}

# TURBO_TOKEN and TURBO_TEAM env vars in CI:
TURBO_TOKEN=${{ secrets.TURBO_TOKEN }}
TURBO_TEAM=acme
```

```bash
# Option 2: Self-hosted — ducktape/turbo-remote-cache (open source)
# A minimal HTTP server implementing Turborepo's cache API
npx create-turbo-remote-cache-server
# Or use the Turborepo Remote Cache spec to implement your own

# In turbo.json:
{
  "remoteCache": {
    "apiUrl": "https://cache.your-company.com"
  }
}

# Option 3: S3-compatible storage via turbo-cache-handler or similar
# Many teams proxy cache reads/writes through an S3 bucket
```

```yaml
# GitHub Actions — full CI setup with remote cache:
name: CI
on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
      TURBO_TEAM: ${{ vars.TURBO_TEAM }}

    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # ← Required for --filter=[origin/main] git comparisons

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'

      - run: npm ci

      - name: Build and test
        run: turbo run build test lint
        # First CI run: slow — builds everything, populates remote cache
        # Subsequent runs: fast — cache hits for unchanged packages
        # Developer machines: turbo pull hits remote cache warmed by CI
```

**Q12. How do you handle versioning and publishing packages from a monorepo?**
A: Two major strategies: independent versioning (each package has its own version) vs fixed/unified versioning (all packages share one version). The tooling landscape:

```
Changesets (most common for OSS and internal publishing):
  1. Developer makes change to @acme/ui
  2. Runs: npx changeset
     → Interactive prompt: which packages changed? what kind of change (patch/minor/major)?
     → Creates: .changeset/purple-lions-eat.md  (human-readable description)
  3. PR includes the changeset file
  4. On merge to main: changeset version bot bumps versions, updates CHANGELOG.md
  5. CI publishes to npm registry

Lerna (legacy, but still used):
  - lerna version — bumps versions based on git commits
  - lerna publish — publishes changed packages to npm
  - Lerna 5+ integrates with Turborepo for task running

nx release (if using Nx instead of Turborepo):
  - Similar to changesets — designed for nx-managed monorepos
```

```bash
# Changesets workflow:
npm install --save-dev @changesets/cli

# Initialize:
npx changeset init
# Creates .changeset/ directory and config.json

# .changeset/config.json:
{
  "changelog": "@changesets/cli/changelog",
  "commit": false,
  "linked": [],              // packages that should always be bumped together
  "access": "restricted",   // or "public" for npm publish
  "baseBranch": "main",
  "updateInternalDependencies": "patch",
  "ignore": ["@acme/eslint-config"]  // private packages — never published
}

# After making a change:
npx changeset
# → "Which packages have changed?" (select @acme/ui)
# → "What type of change?" (minor)
# → "Summary:" (Added dark mode support)
# Creates: .changeset/teal-wolves-jump.md

# In CI after PR merge:
npx changeset version   # bumps versions in package.json, updates CHANGELOG
git commit -m "chore: version packages"
npx changeset publish   # publishes all changed packages to npm
```

## Section 5: Advanced Patterns

**Q13. How do you implement a `dev` task in Turborepo that starts all services correctly with watch mode?**
A: `dev` tasks are long-running and require special handling — they never exit, so Turborepo can't wait for them to "complete":

```json
// turbo.json
{
  "pipeline": {
    "dev": {
      "cache": false,         // Never cache dev server output
      "persistent": true,     // Mark as long-running — turbo runs these concurrently
      "dependsOn": []         // No dependency ordering for dev (start all at once)
    },
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    }
  }
}
```

```json
// packages/ui/package.json
{
  "scripts": {
    "dev": "tsc --watch --noEmit",
    "build": "tsc --build"
  }
}

// apps/web/package.json
{
  "scripts": {
    "dev": "next dev --port 3000",
    "build": "next build"
  }
}

// apps/api/package.json
{
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "build": "tsc --build"
  }
}
```

```bash
# Start all services:
turbo run dev
# → Starts packages/ui's tsc --watch, apps/web's next dev, apps/api's tsx watch
# → All run concurrently (persistent: true)
# → Turborepo streams all stdout/stderr with package name prefix:
#   [ui:dev] Watching for file changes...
#   [web:dev] - ready started server on 0.0.0.0:3000
#   [api:dev] Server running on port 4000

# Start dev for only one app and its dependencies:
turbo run dev --filter=apps/web...
# → Starts ui's watch mode AND web's dev server (because web depends on ui)
```

**Q14. How do you enforce package boundary rules — preventing a package from importing internals it shouldn't?**
A: Several layers of enforcement:

```
Layer 1: TypeScript `paths` without leaking internals
```

```json
// packages/ui/tsconfig.json — only expose what's in the public entrypoint
{
  "compilerOptions": {
    "paths": {
      "@acme/ui": ["./src/index.ts"]
      // NOT: "@acme/ui/internal/*" — internals are not aliased
    }
  }
}
```

```json
// packages/ui/package.json — declare exports map (Node.js package exports)
{
  "name": "@acme/ui",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "types": "./dist/index.d.ts"
    },
    "./button": {
      "import": "./dist/button.js",
      "types": "./dist/button.d.ts"
    }
    // No export for ./src/internal/* — not accessible
  }
}
```

```
Layer 2: ESLint import rules
```

```javascript
// packages/eslint-config/index.js — add to shared config
module.exports = {
  rules: {
    // Prevent importing from sibling package internals
    'no-restricted-imports': ['error', {
      patterns: [
        {
          group: ['@acme/*/src/*'],
          message: 'Import from package public API only, not internal src/'
        },
        {
          group: ['../../../*'],  // Prevent deep relative imports crossing package boundaries
          message: 'Use package name imports (@acme/...) instead of relative paths across packages'
        }
      ]
    }]
  }
};
```

```
Layer 3: Turborepo + dependency-cruiser for architectural constraints
```


**Q15. What is `pnpm` and why do some teams choose it over npm workspaces for monorepos?**
A: pnpm is an alternative package manager that solves npm's phantom dependency problem at the filesystem level using a non-flat `node_modules` and a global content-addressable store:

```
npm/yarn workspaces (flat node_modules):
  node_modules/
    react/            ← hoisted (any package can import this, even if not declared)
    lodash/           ← hoisted (phantom dependency risk)
    @acme/ui → (symlink)

pnpm workspaces (non-flat, strict):
  node_modules/
    .pnpm/
      react@18.2.0/node_modules/react/   ← real install location
      lodash@4.17.21/node_modules/lodash/
    react → .pnpm/react@18.2.0/.../react  ← symlink only if declared in package.json
    @acme/ui → packages/ui               ← workspace symlink

  packages/ui/node_modules/
    react → ../../node_modules/.pnpm/react@18.2.0/.../react
    lodash → ← NOT PRESENT (ui doesn't declare lodash — import would fail!)
```

Key differences:

| Dimension | npm workspaces | pnpm workspaces |
|---|---|---|
| Phantom dependencies | Allowed (hoisting grants access) | Blocked (strict symlink structure) |
| Disk usage | Duplicated across projects on disk | Global content-addressable store — each file stored once |
| Install speed | Slow (copies files) | Fast (hardlinks from global store) |
| node_modules structure | Flat (easy to debug) | Nested symlinks (harder to inspect manually) |
| Peer dep handling | Requires manual resolution | Automatic, strict |
| `workspace:*` protocol | Supported in npm 7+ | pnpm-native, more ergonomic |

```json
// pnpm-workspace.yaml (pnpm's alternative to root package.json workspaces field)
packages:
  - 'apps/*'
  - 'packages/*'

// packages/ui/package.json — reference local package with workspace protocol:
{
  "dependencies": {
    "@acme/utils": "workspace:*"  // ← pnpm resolves to local version; replaced with real
                                   //   semver range on publish
  }
}
```

## Section 6: Testing and Debugging

**Q16. How do you run only affected tests in a monorepo CI pipeline?**
A: The most efficient pattern uses Turborepo's `--filter` with git comparison plus test result caching:

```yaml
# .github/workflows/pr.yml
name: PR Checks
on: pull_request

jobs:
  test:
    runs-on: ubuntu-latest
    env:
      TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
      TURBO_TEAM: ${{ vars.TURBO_TEAM }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # Full history needed for git diff

      - run: npm ci

      - name: Run affected tests
        run: |
          turbo run test --filter="[origin/${{ github.base_ref }}]..."
          # [origin/main] → packages changed vs target branch
          # ... → plus all their downstream dependents
          # Result: tests only in packages affected by this PR
```

```json
// turbo.json — test task config
{
  "pipeline": {
    "test": {
      "dependsOn": ["^build"],       // Build dependencies first
      "outputs": ["coverage/**"],    // Cache coverage reports
      "env": ["NODE_ENV", "CI"],
      "inputs": [
        "src/**",
        "tests/**",
        "jest.config.*",
        "package.json"
      ]                               // Only re-run tests if these change
    }
  }
}
```

```bash
# Locally: run tests for changed packages only (vs main):
turbo run test --filter="[origin/main]"

# Run tests for a specific package and everything it depends on:
turbo run test --filter="apps/web..."

# Force re-run without cache (when debugging flakiness):
turbo run test --force

# See what would run and cache status without executing:
turbo run test --dry-run
```

**Q17. How do you debug a situation where `turbo run build` succeeds but the built artifact is stale or missing?**
A: A systematic debugging approach for cache/output issues:

```bash
# Step 1: Check what turbo thinks it cached and what it restored
turbo run build --verbosity=2
# Shows: FULL TURBO (cache hit), MISS (ran fresh), and which files were restored

# Step 2: Verify output globs are correct
# In turbo.json, if you have:
#   "outputs": ["dist/**"]
# But your build emits to dist/esm/ and dist/cjs/ — check if glob covers it:
ls dist/   # Verify structure matches glob pattern

# Step 3: Force-run without cache to confirm the task itself works:
turbo run build --force
# Ignores all cache entries — runs everything from scratch

# Step 4: Check if inputs are causing unexpected cache misses:
turbo run build --summarize
# Creates .turbo/runs/<id>.json with full input hash computation
# Shows every file included in the hash — look for unexpected files

# Step 5: Verify build script output location matches package.json `main`/`exports`:
cat packages/ui/package.json
# "main": "dist/index.js"    ← must exist after build
# "exports": { ".": "./dist/index.js" }

# Step 6: Check TypeScript project references are set up correctly:
tsc -b --verbose
# Shows build order and which packages were rebuilt vs skipped

# Step 7: Common root cause — missing `composite: true`:
# Without composite: true, TypeScript doesn't emit .tsbuildinfo
# → tsc -b can't do incremental builds → always rebuilds everything
# → Turbo's outputs might be correct but TS is slow
```

```json
// Fixing output glob issues:
{
  "pipeline": {
    "build": {
      "outputs": [
        "dist/**",          // catches dist/index.js, dist/esm/**, etc.
        "*.tsbuildinfo",    // TypeScript incremental build cache
        ".next/**",         // Next.js build output
        "!dist/**/*.test.*" // Exclude test files from cache
      ]
    }
  }
}
```

## Quick Reference Table

| Concept | Key Idea | Common Mistake |
|---|---|---|
| `workspaces` in package.json | Declares all workspace member locations; npm installs into one root `node_modules` | Running `npm install` inside a workspace package instead of at root |
| Dependency hoisting | Shared deps installed once at root and symlinked | Phantom dependencies — importing a package not declared in your own package.json |
| `npm run --workspaces` | Runs a script in all packages | No dependency ordering — apps may build before their dependencies |
| `turbo.json` pipeline | Declares task dependencies, outputs, and env vars for caching | Missing `"dependsOn": ["^build"]` — tasks run in wrong order |
| `^build` syntax | Run `build` in all declared dependencies before this package | Confusing `^build` (transitive) with `build` (same package) |
| `outputs` in pipeline | File globs captured after a cache miss and restored on hit | Wrong glob — cached files don't include actual build output |
| `inputs` in pipeline | Files whose changes invalidate the cache for this task | Missing `inputs` override — README changes invalidate test cache |
| Remote cache | Shared cache across all CI machines and developer machines | Forgetting to set `TURBO_TOKEN` and `TURBO_TEAM` env vars in CI |
| `--filter` flag | Runs tasks for subset of packages — by name, path, or git diff | Forgetting `fetch-depth: 0` in CI — git diff comparison fails |
| `persistent: true` | Marks a task as long-running so turbo doesn't wait for it to exit | Not setting this for `dev` — turbo hangs waiting for dev server to exit |
| TypeScript `composite` | Required for project references and incremental builds | Missing `composite: true` — `tsc -b` rebuilds everything every time |
| Shared config packages | Internal packages for ESLint/tsconfig — consumed via workspace `*` version | Publishing internal config packages to npm instead of keeping them private |

---

**Tip for interviews:** Five things separate strong candidates on monorepo tooling: (1) explaining **why npm workspaces alone are insufficient** — the ordering and caching problem that Turborepo solves — rather than treating them as alternatives to each other; they're complementary. npm workspaces handle package linking; Turborepo handles task orchestration and caching on top of that; (2) understanding the **`^` prefix in `dependsOn`** — knowing that `"^build"` means "run `build` in my dependencies first" versus `"build"` meaning "run `build` in this same package first" is the single most-tested Turborepo detail; (3) knowing that **phantom dependencies are npm workspace's Achilles heel** — being able to describe why pnpm's strict non-flat `node_modules` prevents phantom deps that flat hoisting allows, and giving a concrete example of a phantom dep breaking in production; (4) designing a **complete CI pipeline** that uses remote cache + `--filter=[origin/main]...` — describing why `fetch-depth: 0` is required for the git diff to work; and (5) being able to articulate **the `composite: true` + `declarationMap: true` TypeScript setup** for project references — without these, either `tsc -b` doesn't do incremental builds, or Go-to-Definition in the editor jumps to `.d.ts` files instead of source.
