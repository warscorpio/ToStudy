# `npm` vs `yarn` vs `pnpm` — Practical Differences: Interview Q&A (5 YOE Level)

---

## Section 1: History and Motivation

**Q1. Why were Yarn and pnpm created if npm already existed?**

A: npm was the original Node.js package manager but had significant problems by 2016 that motivated alternatives:

**Yarn (2016, Facebook/Meta):** npm v3 introduced flat (hoisted) `node_modules` to reduce nesting depth, but installation was slow and non-deterministic — running `npm install` twice on the same `package.json` could produce different `node_modules` trees depending on install order and registry state. There was no lockfile. Yarn solved these with:
- A `yarn.lock` lockfile for reproducible installs
- Parallel package downloads (npm was sequential)
- Offline cache — if a package was downloaded once, it never re-downloaded from the network

**pnpm (2017, community):** Even with a lockfile, both npm and Yarn had a structural problem: flat hoisting wastes disk space (each project gets its own copy of every package) and creates phantom dependencies (code can require packages not in its own `package.json`). pnpm solved these with a content-addressable global store and a symlink-based `node_modules` structure that enforces strict dependency declaration.

npm eventually caught up: lockfiles arrived in npm v5 (2017), parallel installs improved in v6, workspaces in v7, and automatic peer dependency installation in v7. But by then, Yarn and pnpm had features and semantics that npm still doesn't replicate — particularly pnpm's strict `node_modules` model.

**Q2. What is `corepack` and how does it relate to package manager choice?**

A: `corepack` is a zero-config package manager manager bundled with Node.js since v16.9.0. It allows you to specify which package manager — and which exact version — a project expects, and enforces it:

```json
// package.json
{
  "packageManager": "pnpm@9.1.0"
}
```

```bash
# Enable corepack (one-time setup — activates yarn and pnpm shims)
corepack enable

# Now running 'pnpm install' in this project uses exactly pnpm@9.1.0
# even if you have a different global pnpm installed.
# Running 'npm install' in a project with "packageManager": "pnpm@9.1.0" warns or errors.
```

`corepack` downloads and caches package manager binaries on demand from the npm registry. In CI, it reads `packageManager` from `package.json` and installs the exact version before any scripts run — no separate `npm install -g pnpm` step needed.

The `packageManager` field is now the recommended way to lock which tool (and version) a project uses, solving the "works on my machine with pnpm 7 but CI uses pnpm 9" class of bugs.

## Section 2: Lockfiles and Determinism

**Q3. How do the three lockfile formats differ and what do they each guarantee?**

A: All three tools generate a lockfile that records the exact resolved version of every dependency (direct and transitive), their download URLs, and integrity hashes. The formats differ:

**`package-lock.json` (npm):** JSON format, verbose and machine-generated. Contains the full resolved dependency tree with nested structure mirroring `node_modules`. As of npm v7, it also contains the `packages` field with the full flat list:

```json
// package-lock.json (npm v7+ format — "lockfileVersion": 3)
{
  "lockfileVersion": 3,
  "packages": {
    "node_modules/express": {
      "version": "4.18.2",
      "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
      "integrity": "sha512-...",
      "dependencies": {
        "body-parser": "1.20.1"
      }
    }
  }
}
```

**`yarn.lock` (Yarn Classic 1.x / Berry 2+):** Custom non-JSON, non-YAML format. Human-readable at a glance but not a standard format. Yarn Berry uses the same file format but a different internal schema — a v1 lockfile is not compatible with Berry and Berry will convert it:

```yaml
# yarn.lock (classic format)
express@^4.18.0:
  version "4.18.2"
  resolved "https://registry.yarnpkg.com/express/-/express-4.18.2.tgz#..."
  integrity sha512-...
  dependencies:
    body-parser "1.20.1"
```

**`pnpm-lock.yaml` (pnpm):** YAML format. Contains a `snapshots` section describing the full dependency tree and an `importers` section per workspace. More readable than npm's JSON for diff review:

```yaml
# pnpm-lock.yaml
lockfileVersion: '9.0'
importers:
  .:
    dependencies:
      express:
        specifier: ^4.18.0
        version: 4.18.2
packages:
  express@4.18.2:
    resolution: {integrity: sha512-...}
    dependencies:
      body-parser: 1.20.1
```

All three lockfiles guarantee **deterministic installs** — the exact same tree is installed every time, regardless of registry state or install order. The guarantee only holds if the lockfile is committed to version control and the correct install command is used.

**Q4. What is the difference between `npm install` and `npm ci`, and what are the equivalents in Yarn and pnpm?**

A: The distinction between "update the lockfile if needed" vs "fail if lockfile is out of sync" is critical in CI:

| Behavior | npm | Yarn Classic | Yarn Berry | pnpm |
|---|---|---|---|---|
| Install from lockfile, update if needed | `npm install` | `yarn` | `yarn install` | `pnpm install` |
| Fail if lockfile doesn't match `package.json` | `npm ci` | `yarn --frozen-lockfile` | `yarn install --immutable` | `pnpm install --frozen-lockfile` |
| Delete `node_modules` before installing | `npm ci` (always) | manual | manual | `pnpm install --force` |

```bash
# CI pipelines should ALWAYS use the frozen/immutable form:
# npm:
npm ci

# yarn classic:
yarn --frozen-lockfile

# yarn berry:
yarn install --immutable

# pnpm:
pnpm install --frozen-lockfile
# or (pnpm-specific shorthand since pnpm v8):
pnpm install --frozen

# Why: if a developer adds a dependency but forgets to commit the updated lockfile,
# the non-frozen form silently regenerates it in CI — different versions than tested locally.
# The frozen form catches the discrepancy immediately with a clear error.
```

## Section 3: `node_modules` Structure

**Q5. How does npm (and Yarn Classic) structure `node_modules` through flat hoisting?**

A: Before npm v3, `node_modules` was nested — every package contained its own `node_modules` with its dependencies, which nested arbitrarily deep. npm v3 introduced **flat hoisting**: all packages are lifted to the root `node_modules` as much as possible, with nesting only when version conflicts require it.

```
# package.json: { "dependencies": { "A": "1.0", "B": "1.0" } }
# A@1.0 depends on: C@1.0
# B@1.0 depends on: C@2.0

Nested (pre-npm v3):
node_modules/
  A/
    node_modules/
      C/  (v1.0)
  B/
    node_modules/
      C/  (v2.0)

Flat hoisted (npm v3+):
node_modules/
  A/
  B/
  C/  (v1.0 — hoisted: first encountered wins)
  B/
    node_modules/
      C/  (v2.0 — nested: can't hoist, conflicts with v1.0)
```

The "first encountered wins" rule means which version gets hoisted depends on the order packages appear in `package.json` — a subtle source of non-determinism if the lockfile isn't present or is ignored.

**Doppelgangers:** When the same package at the same version appears at multiple levels of the tree (due to separate resolution paths), it becomes a "doppelganger" — two physically distinct copies with the same content. This breaks `instanceof` checks and singleton assumptions:

```typescript
// Package 'A' and package 'B' both depend on 'schema-validator@2.0'
// If they're doppelgangers, each has its own copy of SchemaValidator class:
import { SchemaValidator } from 'A';        // uses node_modules/A/node_modules/schema-validator
import { SchemaValidator as SV2 } from 'B'; // uses node_modules/B/node_modules/schema-validator

const v = new SchemaValidator();
v instanceof SV2;  // false — different class objects from different module instances
```

**Q6. What are phantom dependencies and why does flat hoisting create them?**

A: A phantom dependency is a package your code `import`s or `require`s that is **not listed** in your `package.json` — it works only because flat hoisting placed it in the root `node_modules` as a dependency of something else you depend on.

```
# Your package.json:
{ "dependencies": { "express": "^4.18.0" } }

# express depends on: body-parser, lodash (hypothetically), etc.
# After flat install, your node_modules/ looks like:
node_modules/
  express/
  body-parser/    ← not in your package.json
  lodash/         ← not in your package.json
  ...dozens more transitive deps...
```

```typescript
// This works — but it's a phantom dependency:
import bodyParser from 'body-parser';  // Not in your package.json!
import _ from 'lodash';               // Not in your package.json!

// Consequences:
// 1. You never explicitly chose these — you don't know their versions
// 2. If express drops lodash in a new version, your import breaks with no warning
//    because you never declared the dependency
// 3. npm audit only audits what's in your package.json — phantom deps may be unaudited
// 4. Tool output ("your project uses lodash 4.x") is misleading
```

Phantom dependencies are ubiquitous in npm-managed projects and often go unnoticed until an upstream package changes its own dependencies. pnpm's architecture eliminates them entirely.

**Q7. How does pnpm's `node_modules` structure prevent phantom dependencies?**

A: pnpm uses a two-layer structure: a **global content-addressable store** and a **virtual store** in `node_modules/.pnpm/`. The top-level `node_modules` only contains symlinks to packages explicitly listed in your `package.json`:

```
pnpm's node_modules/ after installing { "dependencies": { "express": "^4.18.0" } }:

node_modules/
  express → .pnpm/express@4.18.2/node_modules/express    ← symlink (direct dep only)
  .pnpm/
    express@4.18.2/
      node_modules/
        express/                                          ← hard links to global store
          index.js
          package.json
          ...
        body-parser → ../../body-parser@1.20.1/node_modules/body-parser  ← express's dep
        accepts → ../../accepts@1.3.8/node_modules/accepts
    body-parser@1.20.1/
      node_modules/
        body-parser/                                      ← hard links to global store
    accepts@1.3.8/
      node_modules/
        accepts/
```

From your application code's perspective:
- `import express from 'express'` — resolves via `node_modules/express` symlink ✓ (declared dep)
- `import bodyParser from 'body-parser'` — `node_modules/body-parser` **does not exist** → `Error: Cannot find module 'body-parser'` ✗ (undeclared phantom dep, correctly rejected)

From express's code perspective:
- `require('body-parser')` inside `node_modules/.pnpm/express@4.18.2/node_modules/express/` — resolves via the `body-parser` symlink in that package's own `.pnpm` directory ✓ (express declared it, express can use it)

Each package can only access what it explicitly declared. The strictness is the point: it forces you to declare everything you actually use.

**Q8. What is the global content-addressable store and how do hard links make pnpm storage-efficient?**

A: pnpm maintains a single global store (default: `~/.local/share/pnpm/store` on Linux, `~/Library/pnpm/store` on macOS) where every version of every package is stored exactly once, keyed by content hash.

When pnpm installs packages, the files in `node_modules/.pnpm/` are **hard links** to files in the global store — not copies:

```
Global store (~/.local/share/pnpm/store/v3/):
  files/
    00/abc123...  (react@18.2.0's index.js — one copy on disk)
    01/def456...  (lodash@4.17.21's lodash.js — one copy on disk)
    ...

Project A node_modules/.pnpm/react@18.2.0/node_modules/react/index.js
  └── hard link → global store file 00/abc123...  ← same inode, no extra disk space

Project B node_modules/.pnpm/react@18.2.0/node_modules/react/index.js
  └── hard link → global store file 00/abc123...  ← same inode, no extra disk space
```

```bash
# Verify hard links (same inode = same file on disk):
ls -li project-a/node_modules/.pnpm/react@18.2.0/node_modules/react/index.js
# 12345678 ... react/index.js

ls -li project-b/node_modules/.pnpm/react@18.2.0/node_modules/react/index.js
# 12345678 ... react/index.js  ← same inode number → zero extra disk usage

# Disk savings at scale:
# 50 projects all using react@18.2.0, lodash@4.17.21, etc.
# npm/yarn: 50 × (react + lodash + ...) = massive duplication
# pnpm: 1 × (react + lodash + ...) in the global store + lightweight symlinks per project
```

Warm installs (package already in the global store) are extremely fast: pnpm only creates hard links and symlinks — no network access, no file copying, just inode references. This is why pnpm is typically the fastest of the three tools on repeat installs.

```bash
pnpm store path         # Print global store location
pnpm store status       # Check for corrupted store entries
pnpm store prune        # Remove unreferenced packages from the store
```

## Section 4: Workspaces and Monorepos

**Q9. How does each tool support monorepo workspaces, and what are the practical differences?**

A: All three tools support workspaces — a way to manage multiple packages in a single repository. The configuration and behavior differ meaningfully:

**npm workspaces (v7+):**
```json
// Root package.json
{
  "workspaces": ["packages/*", "apps/*"]
}
```
```bash
npm install                              # installs all workspace deps, hoisted to root
npm install lodash -w packages/utils     # add dep to a specific workspace
npm run build -w packages/ui             # run script in one workspace
npm run build --workspaces               # run script in ALL workspaces
```
npm hoists all workspace dependencies to the root `node_modules`. Simple but inherits all flat-hoisting problems.

**Yarn Classic workspaces:**
```json
// Root package.json
{
  "private": true,
  "workspaces": ["packages/*"]
}
```
Similar to npm — flat hoisting at the root. Yarn was the first to introduce workspaces (2017), predating npm's implementation.

**pnpm workspaces:**
```yaml
# pnpm-workspace.yaml (separate file, not package.json)
packages:
  - 'packages/*'
  - 'apps/*'
  - '!**/test/**'    # Glob exclusions supported
```
```bash
pnpm install                             # installs all workspace deps
pnpm add lodash --filter packages/utils  # add dep to specific workspace
pnpm run build --filter packages/ui      # run in one workspace
pnpm run build --filter '...^packages/utils'  # run in utils AND packages that depend on it
```

pnpm's `--filter` flag is significantly more powerful than npm's `-w`:
```bash
# pnpm --filter patterns:
pnpm --filter packages/ui build          # specific package by path
pnpm --filter '@myorg/ui' build          # by package name
pnpm --filter '...' build                # all packages
pnpm --filter '...^@myorg/utils' build   # @myorg/utils and all its dependents
pnpm --filter '@myorg/utils...' build    # @myorg/utils and all its dependencies
pnpm --filter '[main...HEAD]' build      # packages changed since main branch (Git-aware)
```

The Git-aware filter (`[main...HEAD]`) is unique to pnpm and extremely useful in CI: only build/test packages affected by the current PR.

**Q10. What is pnpm's `workspace:` protocol and why is it safer than alternatives?**

A: In a monorepo, packages within the same workspace often depend on each other. Without the `workspace:` protocol, you'd reference them by version number — but that version might not be published yet, or the local version might be ahead of the published one:

```json
// packages/app/package.json — WITHOUT workspace protocol (problematic)
{
  "dependencies": {
    "@myorg/utils": "^1.2.0"   // Installs from registry — ignores local changes!
  }
}
```

The `workspace:` protocol forces pnpm to use the local workspace package instead of the registry:

```json
// packages/app/package.json — WITH workspace protocol
{
  "dependencies": {
    "@myorg/utils": "workspace:*",      // Always use local version (any version)
    "@myorg/ui":    "workspace:^1.0.0", // Use local if it matches range
    "@myorg/core":  "workspace:~2.1.0"  // Use local if it matches range
  }
}
```

When publishing, pnpm automatically replaces `workspace:*` with the actual version from that package's `package.json` — so published packages have real version numbers:

```bash
pnpm publish -r   # Publish all changed packages
# workspace:* → replaced with actual version (e.g., "1.2.0") in the published package
```

npm has no equivalent — it uses `file:../utils` which is not replaced at publish time (published packages contain the `file:` reference, which breaks for consumers). Yarn Berry has `workspace:` support too, but pnpm pioneered the pattern.

## Section 5: Peer Dependencies and Security

**Q11. How do npm, Yarn, and pnpm handle peer dependencies differently?**

A: Peer dependencies are packages your library requires the consumer to provide — e.g., a React component library lists `react` as a peer dep because it shouldn't bundle its own React, it should use the host application's.

**Historical behavior (before npm v7, Yarn Classic):**
Peer deps were advisory only — printed as a warning but not installed. Developers had to manually add them to their own `package.json`. This caused subtle "React loaded twice" bugs when consumers forgot.

**npm v7+ behavior:** Automatically installs peer dependencies. If you install `react-router-dom`, npm automatically installs `react` if it's not already present. This broke many projects during the npm v7 migration because packages with loose peer dep ranges (`react@>=16`) would install React 18 even in React 16 projects.

**pnpm behavior:** Installs peer deps automatically but with a unique structural approach — each package that has peer dependencies gets its own "instance" in `node_modules/.pnpm/` for each unique combination of resolved peer dependencies:

```
# Two packages, both peer-depending on react, but resolving to different versions:
node_modules/.pnpm/
  some-lib@1.0.0_react@17.0.2/    ← some-lib instance for React 17
  some-lib@1.0.0_react@18.2.0/    ← same some-lib, different peer context
```

This means pnpm correctly handles the case where two packages in your tree require different React versions — each gets the right peer dep. npm and Yarn would install one version and let the other break silently.

**Yarn Berry behavior:** Automatically installs peer deps. More strict than Classic about peer dep resolution — will error rather than silently pick a wrong version.

```bash
# pnpm: control peer dep behavior via .npmrc:
auto-install-peers=true          # default in pnpm v8+: auto-install peers
strict-peer-dependencies=false   # default: warn but don't fail on unresolved peers
strict-peer-dependencies=true    # CI-hardened: fail if any peer dep is unresolved
```

**Q12. How do `npm audit`, `yarn audit`, and `pnpm audit` compare?**

A: All three query the **same underlying vulnerability database** (npm's advisory database, which aggregates from NVD, GitHub Security Advisories, etc.). Their practical differences are in output format and integration:

```bash
# npm: runs automatically after install (configurable with --audit=false)
npm audit                     # Full vulnerability report
npm audit --json              # Machine-readable JSON
npm audit fix                 # Auto-upgrade to non-vulnerable versions
npm audit fix --force         # Allow major version bumps to fix vulns (risky)
npm audit --omit=dev          # Skip dev dependencies (production-relevant only)

# yarn classic:
yarn audit                    # Similar output to npm
# Note: yarn audit does NOT have an auto-fix command — must fix manually

# yarn berry:
yarn npm audit

# pnpm:
pnpm audit                    # Same advisory database as npm
pnpm audit --fix              # Auto-fix (pnpm v8+)
pnpm audit --prod             # Skip devDependencies
```

Key practical difference: **npm auto-runs audit on install** (by default). This adds network latency to every `npm install` in CI. Disable it for CI install steps and run a dedicated audit step separately:

```bash
# Faster CI install + explicit audit step:
npm ci --audit=false   # Skip audit during install
npm audit --omit=dev   # Separate audit step, only production deps

# pnpm and yarn: audit is not run automatically during install — already separated
```

## Section 6: Yarn Berry and Plug'n'Play

**Q13. What is Yarn Berry's Plug'n'Play (PnP) mode and how does it differ architecturally from `node_modules`?**

A: Yarn Berry (v2+) defaults to **Plug'n'Play** — an approach that eliminates `node_modules` entirely. Instead of a directory tree, PnP uses a single `.pnp.cjs` file that maps every `import`/`require` to a location in Yarn's cache of zip archives:

```
Traditional node_modules:                    Yarn PnP:
node_modules/                                .pnp.cjs        ← resolution map
  react/                                     .yarn/
    index.js                                   cache/
    package.json                                 react-npm-18.2.0-abc123.zip
  lodash/                                        lodash-npm-4.17.21-def456.zip
    lodash.js                                    ...
  ...thousands of files...                  (no node_modules directory)
```

The `.pnp.cjs` file is loaded as a Node.js loader that intercepts all `require()` and `import` calls:

```javascript
// .pnp.cjs (simplified concept):
const packageLocations = {
  'react@18.2.0': '/home/user/.yarn/cache/react-npm-18.2.0-abc123.zip/node_modules/react',
  'lodash@4.17.21': '/home/user/.yarn/cache/lodash-npm-4.17.21-def456.zip/node_modules/lodash',
};
// Node.js's module resolver is patched to use this map
// instead of the filesystem walk through node_modules
```

**Advantages of PnP:**
- Install is near-instant on subsequent runs — no files to copy or link, just update the map
- Strict: like pnpm, you can only import declared dependencies
- "Zero installs": commit `.pnp.cjs` and `.yarn/cache/` zip files to git, skip `yarn install` entirely in CI

**Disadvantages:**
- Compatibility: some packages assume `node_modules` exists and use `path.resolve(__dirname, '../../node_modules')` or read the filesystem directly. These break under PnP.
- Build tools: Webpack, Vite, Jest, TypeScript all need PnP-specific plugins/configuration
- `node_modules` linker mode: Yarn Berry can be configured to use traditional `node_modules` as a fallback:

```yaml
# .yarnrc.yml
nodeLinker: node-modules    # Use flat node_modules (lose PnP benefits, gain compatibility)
nodeLinker: pnp             # Default PnP mode
nodeLinker: pnpm            # Use pnpm-style symlinked node_modules (Yarn Berry v3+)
```

**Q14. What are Yarn Berry's "zero installs" and when are they practical?**

A: Zero installs means committing the entire Yarn cache (`.yarn/cache/`) to git alongside `.pnp.cjs`. CI and other developers can `git pull` and run the application immediately — no `yarn install` needed:

```
Committed to the repository:
.pnp.cjs                        ← module resolution map
.yarn/
  cache/
    react-npm-18.2.0-abc123.zip ← compressed package archives
    express-npm-4.18.2-...zip
    ...every dependency...
  releases/
    yarn-4.0.0.cjs              ← the Yarn binary itself
```

```yaml
# .gitignore adjustments for zero-installs:
.yarn/*
!.yarn/cache      # Commit the cache
!.yarn/patches    # Commit any patches
!.yarn/plugins    # Commit plugins
!.yarn/releases   # Commit the Yarn binary
!.yarn/sdks       # Commit editor SDKs
!.yarn/versions   # Commit version plugins
```

**When zero installs are practical:**
- Small-to-medium dependency trees (large dependency sets make the git repo enormous)
- Air-gapped environments (CI with no internet access)
- Reproducibility-critical projects (pharmaceutical, financial compliance)
- Projects where `yarn install` time in CI is a significant bottleneck

**When zero installs are impractical:**
- Large dependency trees (React monorepos with thousands of packages — `.yarn/cache/` can be hundreds of MB)
- Frequent dependency updates (every `yarn add` commits large zip files → bloated git history)
- Organizations where policy prohibits committing built artifacts

## Section 7: CLI Differences and Migration

**Q15. What are the key CLI command differences between the three tools?**

A:

| Operation | npm | Yarn Classic | Yarn Berry | pnpm |
|---|---|---|---|---|
| Install all deps | `npm install` | `yarn` | `yarn install` | `pnpm install` |
| CI install (frozen) | `npm ci` | `yarn --frozen-lockfile` | `yarn install --immutable` | `pnpm install --frozen-lockfile` |
| Add dependency | `npm install pkg` | `yarn add pkg` | `yarn add pkg` | `pnpm add pkg` |
| Add dev dependency | `npm install -D pkg` | `yarn add -D pkg` | `yarn add -D pkg` | `pnpm add -D pkg` |
| Add exact version | `npm install pkg@1.2.3 -E` | `yarn add pkg@1.2.3 --exact` | `yarn add pkg@1.2.3 --exact` | `pnpm add pkg@1.2.3` |
| Remove dependency | `npm uninstall pkg` | `yarn remove pkg` | `yarn remove pkg` | `pnpm remove pkg` |
| Run script | `npm run script` | `yarn script` (no `run`) | `yarn script` | `pnpm script` or `pnpm run script` |
| Run without installing | `npx pkg` | `yarn dlx pkg` | `yarn dlx pkg` | `pnpm dlx pkg` |
| Execute local binary | `npx pkg` | `yarn pkg` | `yarn pkg` | `pnpm pkg` or `pnpm exec pkg` |
| List installed | `npm list` | `yarn list` | `yarn info --all` | `pnpm list` |
| Outdated packages | `npm outdated` | `yarn outdated` | `yarn upgrade-interactive` | `pnpm outdated` |
| Update all | `npm update` | `yarn upgrade` | `yarn up` | `pnpm update` |
| Update interactive | *(none built-in)* | `yarn upgrade-interactive` | `yarn upgrade-interactive` | `pnpm update -i` |
| Audit | `npm audit` | `yarn audit` | `yarn npm audit` | `pnpm audit` |
| Publish | `npm publish` | `yarn publish` | `yarn npm publish` | `pnpm publish` |
| Workspace command | `npm run X -w pkg` | `yarn workspace pkg X` | `yarn workspace pkg X` | `pnpm --filter pkg X` |

Notable differences:
- **`yarn` vs `yarn install`**: Yarn Classic allows `yarn` as a shorthand; Berry requires `yarn install`
- **`yarn run` is optional**: Yarn omits `run` for scripts — `yarn build` instead of `yarn run build`. npm always requires `run`. pnpm accepts both.
- **`pnpm dlx` vs `npx`**: Both download and run a package once without installing. pnpm's is faster because of the global store.
- **Interactive update**: Yarn's `upgrade-interactive` and pnpm's `update -i` show a TUI letting you choose which packages to update — npm has no equivalent.

**Q16. What gotchas arise when migrating from npm to pnpm?**

A: The migration is mostly mechanical, but pnpm's strictness surfaces problems that npm was silently hiding:

**Gotcha 1 — Phantom dependency failures:**
```bash
# After migrating to pnpm, code that was silently using phantom deps breaks:
# Error: Cannot find module 'lodash'
# → lodash is used in code but not in package.json

# Fix: add it explicitly
pnpm add lodash
```

**Gotcha 2 — `shamefully-hoist` as a temporary escape hatch:**
```ini
# .npmrc — temporary workaround while fixing phantom deps
shamefully-hoist=true
# Restores flat hoisting behavior — pnpm works like npm
# Defeats the purpose of pnpm but lets you migrate incrementally
```

**Gotcha 3 — Scripts that assume `node_modules/.bin` is in PATH:**
```bash
# npm puts node_modules/.bin in PATH when running scripts
# pnpm does the same — but nested tools that spawn subprocesses may not inherit it

# Affected: Makefiles, shell scripts called from npm scripts that use local binaries
# Fix: use pnpm exec or pnpm run, or add node_modules/.bin to PATH explicitly
```

**Gotcha 4 — `require.resolve` and `__dirname` path assumptions:**
```typescript
// Some packages hardcode paths relative to node_modules:
const configPath = path.join(__dirname, '../../node_modules/some-tool/config.js');
// pnpm's node_modules structure puts packages at different paths
// node_modules/.pnpm/some-tool@1.0.0/node_modules/some-tool/config.js
// This path doesn't exist at '../../node_modules/some-tool'

// Fix: use require.resolve() instead of path.join + __dirname:
const configPath = require.resolve('some-tool/config.js');
// pnpm patches require.resolve to work correctly — path.join does not
```

**Gotcha 5 — Post-install scripts and native addons:**
Some packages with native bindings assume `node_modules` is a sibling of `package.json`. They run `node-gyp` or `node-pre-gyp` during postinstall. pnpm generally handles these, but obscure native addons occasionally need `--shamefully-hoist` or manual configuration.

## Section 8: Performance and CI/CD

**Q17. How do you optimize CI/CD caching for each package manager?**

A: Cache configuration is the single highest-impact CI optimization for dependency installation. Each tool has a different cache location:

**npm:**
```yaml
# GitHub Actions
- name: Cache npm
  uses: actions/cache@v4
  with:
    path: ~/.npm                      # npm's global cache
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-npm-

- run: npm ci                         # Uses the cache automatically
```

**Yarn Classic:**
```yaml
- name: Get Yarn cache directory
  id: yarn-cache-dir
  run: echo "dir=$(yarn cache dir)" >> $GITHUB_OUTPUT

- name: Cache Yarn
  uses: actions/cache@v4
  with:
    path: ${{ steps.yarn-cache-dir.outputs.dir }}
    key: ${{ runner.os }}-yarn-${{ hashFiles('**/yarn.lock') }}
    restore-keys: |
      ${{ runner.os }}-yarn-

- run: yarn --frozen-lockfile
```

**pnpm:**
```yaml
- name: Setup pnpm
  uses: pnpm/action-setup@v4         # Official pnpm GitHub Action
  with:
    version: 9

- name: Get pnpm store directory
  id: pnpm-cache
  run: echo "dir=$(pnpm store path)" >> $GITHUB_OUTPUT

- name: Cache pnpm store
  uses: actions/cache@v4
  with:
    path: ${{ steps.pnpm-cache.outputs.dir }}
    key: ${{ runner.os }}-pnpm-${{ hashFiles('**/pnpm-lock.yaml') }}
    restore-keys: |
      ${{ runner.os }}-pnpm-

- run: pnpm install --frozen-lockfile
```

**Yarn Berry (zero-installs — no install step needed at all):**
```yaml
# With zero-installs: nothing to cache — .yarn/cache is in the repo
- run: yarn --immutable --check-cache   # Verify cache integrity, skip install
```

**Speed comparison (rough benchmarks on a medium-sized project, cold → warm cache):**

| Scenario | npm | Yarn Classic | pnpm |
|---|---|---|---|
| No cache, no lockfile | ~45s | ~30s | ~25s |
| No cache, with lockfile | ~40s | ~25s | ~20s |
| Warm cache, no changes | ~20s | ~10s | ~3s |
| Warm cache, one package added | ~22s | ~12s | ~4s |

pnpm's warm-cache advantage is most pronounced because it creates hard links to cached files — no file copying, just inode references.

## Section 9: Scenario-Based Questions

**Q18. "When would you choose pnpm over npm for a new project, and when would you stick with npm?"**

A:

**Choose pnpm when:**

```
Monorepo with multiple packages
  → pnpm workspaces + workspace: protocol + --filter are best-in-class

Disk space is a concern (developer machines with many projects, shared CI agents)
  → global store + hard links mean 10 projects with the same deps use disk space of 1

Security/compliance requires you cannot have implicit dependencies
  → pnpm's strict module resolution makes phantom deps a compile-time error

You're seeing `instanceof` failures or singleton issues in a complex dependency tree
  → pnpm's per-package peer-dep resolution eliminates doppelgangers

Large team where "it works on my machine" dep issues are common
  → pnpm's strictness surfaces these problems during install, not at runtime
```

**Stick with npm when:**

```
Maximum compatibility is required
  → Some packages with unusual postinstall scripts or native addons work only with flat node_modules
  → npm is the universal baseline; pnpm's strictness reveals problems, which you may not have time to fix

The team is unfamiliar with package manager internals
  → pnpm's symlink structure confuses debugging ("where is this file?")
  → npm's node_modules is what every tutorial and StackOverflow answer assumes

You're maintaining a legacy project with many phantom dependencies
  → Migrating to pnpm forces you to fix all phantom deps first
  → shamefully-hoist=true is available but defeats the purpose
```

**Q19. "Walk me through exactly what happens when you run `pnpm install` on a fresh machine with an existing `pnpm-lock.yaml`."**

A:

```
1. pnpm reads pnpm-lock.yaml
   └─► Resolves the complete dependency tree deterministically from the lockfile
       (no registry lookups for versions — versions are locked)

2. pnpm checks the global store (~/.local/share/pnpm/store/v3/)
   For each package in the lockfile:
   └─► Does this hash exist in the store?
       YES → skip download (hard link directly from store)
       NO  → download the tarball from the registry

3. For packages that need downloading:
   └─► Download tarballs in parallel (configurable concurrency)
   └─► Verify integrity (SHA-512 hash against lockfile's integrity field)
   └─► Extract into the global store, keyed by content hash

4. Create node_modules/.pnpm/ virtual store
   For each package:
   └─► Create directory: node_modules/.pnpm/{name}@{version}/node_modules/{name}/
   └─► Each file in that directory is a hard link to the corresponding global store file
       (zero additional disk space if already in store)

5. Create symlinks in node_modules/.pnpm/ for each package's dependencies
   └─► node_modules/.pnpm/express@4.18.2/node_modules/body-parser
           → ../../body-parser@1.20.1/node_modules/body-parser

6. Create symlinks in the root node_modules/ for direct dependencies only
   └─► node_modules/express → .pnpm/express@4.18.2/node_modules/express

7. Run lifecycle scripts (preinstall, install, postinstall) for packages that declare them
   └─► In the package's own directory inside .pnpm/

8. Complete: node_modules/ ready, strict module resolution enforced
```

On a warm run (all packages already in the global store): steps 3 is skipped entirely. Steps 4–6 are pure filesystem operations (hard link creation and symlink creation) — typically 1–5 seconds for large projects.

**Q20. "Your CI pipeline takes 4 minutes on `npm install`. Walk through every optimization and what each saves."**

A: Systematic optimizations in order of impact:

**Optimization 1 — Use `npm ci` instead of `npm install` (saves ~10–30s):**
```yaml
# BEFORE:
- run: npm install    # May update lockfile; does dependency resolution

# AFTER:
- run: npm ci         # Uses lockfile exactly; skips resolution; cleans node_modules first
```

**Optimization 2 — Cache `~/.npm` (saves 60–90% of time on unchanged lockfile):**
```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}
    restore-keys: npm-
# Cold: downloads everything. Warm: extracts from cache. 4min → ~40s
```

**Optimization 3 — Skip audit during install (saves ~5–15s):**
```yaml
- run: npm ci --audit=false   # Run audit as a separate step if needed
```

**Optimization 4 — Omit dev dependencies in production builds (saves 20–50% of install time):**
```yaml
- run: npm ci --omit=dev   # Only production dependencies
# Only if the CI step is a production build/deploy, not testing
```

**Optimization 5 — Migrate to pnpm (saves additional 50–70% on warm cache):**
```yaml
- uses: pnpm/action-setup@v4
  with: { version: 9 }
- uses: actions/cache@v4
  with:
    path: ~/.local/share/pnpm/store
    key: pnpm-${{ hashFiles('pnpm-lock.yaml') }}
- run: pnpm install --frozen-lockfile
# Warm: hard links from store. ~40s → ~8s
```

**Optimization 6 — Parallelize with workspaces (applicable in monorepos):**
```bash
# pnpm: build only changed packages
pnpm --filter '[main...HEAD]' run build   # Git-aware incremental builds
# In a 20-package monorepo: 4min → ~30s if only 2 packages changed
```

**Cumulative result:**
```
Baseline:        4m 00s  (npm install, no cache, no optimizations)
+ npm ci:        3m 30s  (-30s: skip unnecessary resolution)
+ cache:         0m 40s  (-2m 50s: warm cache avoids downloads)
+ --audit=false: 0m 30s  (-10s: skip network audit call)
+ pnpm migrate:  0m 08s  (-22s: hard links vs file copies from cache)
+ --filter:      0m 03s  (-5s: skip unchanged packages in monorepo)
```

The biggest single win is almost always the cache. The second biggest is pnpm's hard-link model. `--audit=false` and `--omit=dev` are smaller wins but require zero migration effort.

**Tip for interviews:** Five things separate strong candidates on this topic: (1) being able to explain **flat hoisting and phantom dependencies** with a concrete example — the ability to `require('lodash')` when only `express` is in `package.json` because express depends on lodash and npm hoisted it; knowing this isn't "fine" because it silently breaks when express changes its own deps; (2) explaining **pnpm's two-layer storage** — global content-addressable store + per-project hard links — and why it means installing `react@18.2.0` in 50 projects uses the disk space of one; the hard link / inode explanation is the core of the answer; (3) the distinction between **pnpm's symlinked `node_modules`** (packages resolve only what they declared) vs npm's flat model (everything floats to the top), and what `shamefully-hoist` does — it's the escape hatch that makes pnpm behave like npm, useful for migration but defeats the purpose; (4) knowing that **`npm ci` and `npm install` are not interchangeable in CI** — `npm install` can update the lockfile silently, which means CI might test different versions than were developed with; `npm ci` fails if the lockfile is out of sync, which is the correct behavior for reproducible builds; and (5) Yarn Berry's **PnP vs node-modules linker trade-off** — PnP is faster and stricter but breaks packages that assume `node_modules` exists on disk (build tools, path-resolution hacks), which is why many teams use `nodeLinker: node-modules` as a compatibility fallback, effectively getting Yarn Classic behavior but on the Berry runtime.
