## Part 1 — Theory & Interview Q&A

### Section 1: Private Package Fundamentals

**Q1. What makes an npm package "private" and what options exist for hosting one?**
A: A private npm package is one whose source code and published artifacts are accessible only to authenticated, authorized consumers — not publicly downloadable from the open internet. "Private" can mean two different things depending on context:

**Package-level privacy** (`"private": true` in `package.json`):
```json
{ "private": true }
```
This simply prevents `npm publish` from accidentally publishing the package to any registry. It is used for application repositories and monorepo roots that should never be published. It does not create a private registry entry — it just blocks publishing entirely.

**Registry-level privacy** — a published package that requires authentication to install:
The package exists in a registry, has a version history and metadata, but the registry enforces authentication before serving tarball downloads. This is what people mean by "private npm package" in production contexts.

Registry options for hosting private packages:

| Registry | Hosting | Cost | Best For |
|---|---|---|---|
| **npm (npmjs.com)** | Managed (npm Inc.) | Free for public; paid for private org packages | Teams already using npm, simplest setup |
| **GitHub Packages** | Managed (GitHub) | Free for public; included in GitHub plans | Teams already on GitHub, tight GH Actions integration |
| **GitLab Packages** | Managed / Self-hosted | Included in GitLab plans | GitLab-centric organizations |
| **AWS CodeArtifact** | Managed (AWS) | Pay-per-use (~$0.05/GB storage) | AWS-native organizations, fine-grained IAM |
| **Verdaccio** | Self-hosted | Free (open source) | Air-gapped networks, full control, zero cost |
| **JFrog Artifactory** | Managed / Self-hosted | Paid (enterprise) | Large enterprises, multi-format artifact management |
| **Nexus Repository** | Self-hosted | Free (OSS) / Paid | On-premise, multi-format |

The choice is typically driven by: where your team already authenticates (GitHub, AWS, GitLab), compliance requirements (self-hosted vs managed), and cost.

**Q2. What is a scoped package and why are scopes essential for private packages?**
A: A scoped package has a name in the format `@scope/package-name`. The scope (`@company`, `@my-org`) acts as a namespace. Scopes are essential for private packages for three reasons:

**1. Registry routing**: npm allows you to point a specific scope at a different registry while leaving all unscoped packages pointed at the public registry:
```ini
# .npmrc
@mycompany:registry=https://npm.pkg.github.com  # private packages use GitHub
registry=https://registry.npmjs.org             # public packages use npm
```

**2. Namespace isolation**: `@mycompany/utils` cannot conflict with a public `utils` package, even if both are installed simultaneously.

**3. Access control on npmjs.com**: on the npm registry, scoped packages under an organization scope (`@mycompany`) can be published as private — unscoped private packages require a paid individual account with a special flag.

```json
// package.json for a private scoped package:
{
  "name": "@mycompany/auth-client",
  "version": "1.2.0",
  "private": false,         // false = can be published (to private registry)
  "publishConfig": {
    "access": "restricted", // "restricted" = private; "public" = public
    "registry": "https://npm.pkg.github.com"
  }
}
```

```bash
# Publishing a scoped package as private:
npm publish --access restricted   # restricted = private (requires auth to install)
npm publish --access public       # public = anyone can install (free, open source)

# First publish of a scoped package defaults to restricted (private) if org exists
# Must explicitly pass --access public to make a scoped package public on npmjs.com
```

**Q3. What are the different types of `.npmrc` files and how do they interact?**
A: npm reads configuration from multiple `.npmrc` files, merging them with a defined priority order. Understanding the hierarchy is critical for authentication configuration:

```
Priority (highest to lowest):
  1. Command-line flags:        npm install --registry https://...
  2. Per-project .npmrc:       /path/to/your/project/.npmrc
  3. User-level .npmrc:        ~/.npmrc   (home directory)
  4. Global .npmrc:            $(npm config get globalconfig)
  5. Built-in npm defaults

Higher priority overrides lower priority for the same key.
```

```ini
# ~/.npmrc  — user-level (developer's machine):
# Stores personal auth tokens — never commit this file
//registry.npmjs.org/:_authToken=npm_xxxxxxxxxxxxxxxxxxxx
//npm.pkg.github.com/:_authToken=ghp_xxxxxxxxxxxxxxxxxxxx
@mycompany:registry=https://npm.pkg.github.com

# /project/.npmrc  — project-level (committed to git):
# No tokens here — only registry routing configuration
@mycompany:registry=https://npm.pkg.github.com
@mycompany:always-auth=true

# Tokens in project .npmrc use environment variable interpolation:
//npm.pkg.github.com/:_authToken=${NPM_TOKEN}
# ${NPM_TOKEN} is replaced at runtime from the environment
# → safe to commit because the actual token value is in CI secrets / local .env
```

The **project-level `.npmrc`** is committed to source control and contains registry routing rules and environment variable references for tokens — never literal token values. The **user-level `~/.npmrc`** contains actual token values on developer machines and is never committed (add `~/.npmrc` to gitignore at the global level, not per-project).

**Q4. What is an npm authentication token, what types exist, and how are they scoped?**
A: An npm token is a credential that authenticates a user or automated system to an npm registry. There are two generations:

**Legacy ("Classic") Tokens** — still widely used:
- `Automation` type: read and publish permissions, bypasses 2FA (designed for CI/CD)
- `Publish` type: read and publish, requires 2FA interaction
- `Read-only` type: install packages only — cannot publish
- No expiry by default — must be manually rotated

**Granular Access Tokens** — introduced 2022, recommended for new setups:
- Expire on a configurable date (max 1 year, or no-expiry)
- Can be scoped to specific packages (e.g., only `@mycompany/auth-client`)
- Can be scoped to specific IP CIDR ranges
- Separate read vs publish permissions per scope

```bash
# Create a token via CLI:
npm token create                           # publish token (requires 2FA)
npm token create --read-only               # read-only token
npm token create --automation             # automation token (bypasses 2FA prompt)

# Granular token: created in the npmjs.com web UI (Settings → Access Tokens → Generate New Token → Granular)

# List tokens:
npm token list

# Revoke a token:
npm token revoke <token-prefix-or-id>
```

For **GitHub Packages**, authentication uses GitHub Personal Access Tokens (PATs) or GITHUB_TOKEN:
```
PAT scopes needed:
  read:packages  → install packages
  write:packages → publish packages
  delete:packages → delete package versions (rarely needed)
```

For **AWS CodeArtifact**, authentication uses short-lived tokens generated from AWS credentials:
```bash
# Generate a token valid for 12 hours:
aws codeartifact get-authorization-token \
  --domain mycompany \
  --domain-owner 123456789012 \
  --query authorizationToken \
  --output text
# Returns a temporary token — must be refreshed before expiry
```

### Section 2: Publishing Packages

**Q5. What files should and shouldn't be published, and how do you control the package contents?**
A: What ends up in a published tarball is controlled by three mechanisms in priority order: `.npmignore`, the `files` field in `package.json`, and sensible defaults. Getting this wrong means either publishing source files that should be private (`.env`, internal configs, test fixtures) or forgetting to publish compiled output that consumers need.

```
What npm includes/excludes by default (when no files field and no .npmignore):

Always included (regardless of .npmignore or files):
  package.json, README, LICENSE, CHANGELOG, NOTICE

Always excluded (hardcoded):
  .git/, node_modules/, .npmrc, .env, *.lock files,
  coverage/, .DS_Store, Thumbs.db, *.log

Everything else: included by default unless .npmignore or files says otherwise
```

```json
// package.json — "files" field (recommended over .npmignore):
{
  "name": "@mycompany/auth-client",
  "files": [
    "dist/",        // compiled JS output
    "types/",       // generated .d.ts files
    "README.md"     // docs
    // Implicitly included: package.json, LICENSE
    // NOT included: src/, tests/, *.spec.ts, tsconfig.json, .eslintrc
  ]
}
```

```
Comparison of approaches:

.npmignore (blacklist):
  → List what to EXCLUDE
  → If .npmignore doesn't exist, npm falls back to .gitignore
  → Easy to accidentally publish new files when added to the project
  → Harder to reason about "what is in the package?"

files field (whitelist) — RECOMMENDED:
  → List what to INCLUDE
  → New files are not published by accident
  → Easy to audit: "exactly these directories and files"
  → npm pack outputs what will be published — use for verification
```

```bash
# Verify package contents BEFORE publishing:
npm pack --dry-run      # list files without creating tarball
npm pack                # create tarball (.tgz) — inspect it:
tar -tzf mycompany-auth-client-1.2.0.tgz | sort

# Output should show ONLY:
# package/package.json
# package/README.md
# package/LICENSE
# package/dist/index.js
# package/dist/index.cjs
# package/types/index.d.ts
# package/types/index.d.ts.map
# NOT: package/src/**, package/tests/**, package/.env
```

**Q6. What are the critical `package.json` fields for a publishable package, and how do `main`, `module`, `exports`, and `types` interact?**
A: A well-configured `package.json` tells consuming tools (Node.js, bundlers, TypeScript) exactly which file to use for each context:

```json
{
  "name": "@mycompany/auth-client",
  "version": "1.2.0",
  "description": "Authentication client for MyCompany services",
  "license": "UNLICENSED",      // "UNLICENSED" for private; SPDX identifier for open source

  // Entry points — order of precedence varies by tool:

  "main": "./dist/cjs/index.js",      // Node.js require() — CommonJS entry
  "module": "./dist/esm/index.js",    // Bundlers (webpack/rollup) — ESM entry (non-standard but widely supported)
  "types": "./dist/types/index.d.ts", // TypeScript — declaration file location

  // "exports" — modern, authoritative entry point map (Node.js 12+, supported by bundlers):
  "exports": {
    ".": {
      "import": {
        "types": "./dist/types/index.d.ts",
        "default": "./dist/esm/index.js"
      },
      "require": {
        "types": "./dist/types/index.d.ts",
        "default": "./dist/cjs/index.js"
      }
    },
    "./react": {                       // sub-path export: @mycompany/auth-client/react
      "import": {
        "types": "./dist/types/react.d.ts",
        "default": "./dist/esm/react.js"
      },
      "require": {
        "types": "./dist/types/react.d.ts",
        "default": "./dist/cjs/react.js"
      }
    }
  },

  // What to publish:
  "files": ["dist/", "README.md"],

  // Where it can be installed:
  "publishConfig": {
    "access": "restricted",
    "registry": "https://npm.pkg.github.com"
  },

  // Runtime requirements:
  "engines": { "node": ">=18.0.0" },

  // Peer dependencies (consumed, not bundled):
  "peerDependencies": {
    "react": ">=17.0.0"
  },
  "peerDependenciesMeta": {
    "react": { "optional": true }   // React is optional (non-React consumers won't need it)
  }
}
```

```
Resolution priority when a consumer does `import { login } from '@mycompany/auth-client'`:

  Bundler (Vite, webpack, Rollup):
    1. "exports" map (if present) — most authoritative
    2. "module" field — ESM entry (bundler-specific, non-standard)
    3. "main" field — CommonJS entry

  Node.js (>=12):
    1. "exports" map (if present) — only entry point that matters in modern Node.js
    2. "main" field (fallback for packages without "exports")

  TypeScript:
    1. "types" / "typings" in the matched "exports" condition
    2. "types" / "typings" at the package root
    3. Looks for index.d.ts next to package's main entry
```

**Q7. What is semantic versioning and what npm commands automate versioning for private packages?**
A: Semantic versioning (semver) is the version format `MAJOR.MINOR.PATCH` where each number has a defined meaning:

- **PATCH** (`1.2.3 → 1.2.4`): backwards-compatible bug fixes — no API changes
- **MINOR** (`1.2.3 → 1.3.0`): new backwards-compatible functionality — added features
- **MAJOR** (`1.2.3 → 2.0.0`): breaking changes — consumers must update their code
- **Pre-release** (`1.3.0-beta.1`): unstable versions for testing before stable release

```bash
# npm version — updates package.json, commits, and tags:
npm version patch     # 1.2.3 → 1.2.4  + git commit + git tag v1.2.4
npm version minor     # 1.2.3 → 1.3.0
npm version major     # 1.2.3 → 2.0.0
npm version prerelease --preid=beta  # 1.2.3 → 1.2.4-beta.0
npm version 1.5.2     # set explicit version

# Options:
npm version patch --no-git-tag-version  # update package.json only, no git operations
npm version patch -m "chore: release %s" # custom commit message (%s = new version)

# Pre-release workflow:
npm version prerelease --preid=alpha  # → 1.3.0-alpha.0
npm publish --tag alpha               # publish with dist-tag "alpha" (not "latest")

# Consumer installs pre-release explicitly:
npm install @mycompany/auth-client@alpha    # installs latest alpha
npm install @mycompany/auth-client@1.3.0-alpha.0  # specific pre-release

# Dist-tags — named pointers to versions:
npm dist-tag add @mycompany/auth-client@1.3.0 latest  # promote to latest
npm dist-tag ls @mycompany/auth-client
# → alpha: 1.3.0-alpha.3
# → latest: 1.2.4
# → beta: 1.3.0-beta.1
```

**Q8. What is the publishing flow end-to-end, and what checks should be automated before `npm publish`?**
A: A production-grade publishing flow validates the package before it reaches consumers. The naive `npm publish` skips all checks.

```bash
# Manual flow (for understanding — automate in CI):

# 1. Ensure clean working directory:
git status  # should show nothing uncommitted

# 2. Run tests:
npm test

# 3. Build the package (compile TS, bundle, generate .d.ts):
npm run build

# 4. Verify what will be published:
npm pack --dry-run

# 5. Bump version (creates commit + tag):
npm version minor

# 6. Push commit and tag to trigger CI:
git push && git push --tags

# 7. CI publishes (or publish locally for simple setups):
npm publish --access restricted
```

```json
// package.json — automated pre-publish hooks:
{
  "scripts": {
    "build":        "tsc --emitDeclarationOnly && tsup src/index.ts",
    "test":         "vitest run",
    "lint":         "eslint src/",
    "typecheck":    "tsc --noEmit",

    // "prepublishOnly" runs automatically before `npm publish`:
    "prepublishOnly": "npm run lint && npm run typecheck && npm run test && npm run build",

    // "prepare" runs on npm install (for git hooks via husky) and before publish:
    "prepare":      "npm run build",

    // "prepack" runs before npm pack and npm publish (after prepare):
    "prepack":      "npm run build",

    // "postpublish" runs after a successful publish:
    "postpublish":  "echo 'Published successfully' && git push --tags"
  }
}

// Script execution order during `npm publish`:
// prepare → prepublishOnly → [pack the tarball] → publish → postpublish
```

### Section 3: Consuming Private Packages

**Q9. How do you configure a project to consume packages from a private registry alongside public npm packages?**
A: The key is **scoped registry routing** in `.npmrc` — different scopes can point to different registries. Public unscoped packages continue to resolve from the public npm registry.

```ini
# .npmrc (committed to project root — no tokens, only routing)

# Private packages under @mycompany scope → GitHub Packages:
@mycompany:registry=https://npm.pkg.github.com
@mycompany:always-auth=true

# Private packages under @internal scope → self-hosted Verdaccio:
@internal:registry=https://verdaccio.mycompany.com
@internal:always-auth=true

# Everything else → public npm (default — this line is optional):
registry=https://registry.npmjs.org

# Token via environment variable (not hardcoded — safe to commit):
//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
//verdaccio.mycompany.com/:_authToken=${VERDACCIO_TOKEN}
```

```bash
# Developer setup (one-time, on their machine):
# Add token to ~/.npmrc:
npm login --scope=@mycompany --auth-type=legacy --registry=https://npm.pkg.github.com
# Prompts for GitHub username, PAT (as password), and email
# Writes token to ~/.npmrc automatically

# Or manually add to ~/.npmrc:
echo "//npm.pkg.github.com/:_authToken=ghp_yourpersonalaccesstoken" >> ~/.npmrc

# Then install normally — npm routes @mycompany/* to GitHub Packages:
npm install @mycompany/auth-client
npm install lodash                  # still from public npm
```

**Q10. How do you handle private package authentication in CI/CD pipelines (GitHub Actions, Jenkins, Docker)?**
A: CI/CD environments have no developer identity — they authenticate using machine tokens stored as secrets. The pattern is consistent: inject the token as an environment variable, reference it in `.npmrc`, never hardcode it.

**GitHub Actions:**
```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          registry-url: 'https://npm.pkg.github.com'  # sets NODE_AUTH_TOKEN in .npmrc
          scope: '@mycompany'

      - name: Install dependencies
        run: npm ci
        env:
          # GITHUB_TOKEN is auto-provided by GitHub Actions for the repo's org packages:
          NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          # For cross-org packages, use a PAT stored as a secret:
          # NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

      - name: Build and test
        run: npm run build && npm test

  publish:
    needs: build
    runs-on: ubuntu-latest
    if: startsWith(github.ref, 'refs/tags/v')  # only on version tags
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          registry-url: 'https://npm.pkg.github.com'
          scope: '@mycompany'

      - run: npm ci
        env:
          NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

      - name: Publish
        run: npm publish
        env:
          NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          # GITHUB_TOKEN has write:packages permission for the repo's own packages
```

**Docker build (consuming private packages during image build):**
```dockerfile
# Dockerfile — using BuildKit secrets (most secure approach):
# syntax=docker/dockerfile:1

FROM node:20-alpine AS builder

WORKDIR /app

# Copy .npmrc with env var reference (not the token itself):
COPY .npmrc package.json package-lock.json ./

# --mount=type=secret makes NPM_TOKEN available only during this RUN command
# It does NOT persist in the image layer — secret never baked into the image:
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) \
    npm ci

COPY . .
RUN npm run build

# Production image — no tokens, no node_modules with token residue:
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package.json .
CMD ["node", "dist/server.js"]
```

```bash
# Build with secret:
docker buildx build \
  --secret id=npm_token,env=NPM_TOKEN \  # reads from environment variable
  -t myapp:latest .
```

```dockerfile
# Alternative (less secure — token baked into intermediate layer but not final):
FROM node:20-alpine AS builder
ARG NPM_TOKEN
RUN echo "//npm.pkg.github.com/:_authToken=${NPM_TOKEN}" >> ~/.npmrc
COPY package*.json ./
RUN npm ci && rm -f ~/.npmrc  # remove npmrc — but token IS in the layer history
```

**Q11. What is `npm ci` and why should it be used instead of `npm install` in CI/CD?**
A: `npm ci` (Clean Install) is designed for automated environments. Key differences from `npm install`:

```
npm install:
  → Reads package.json for version ranges
  → Updates package-lock.json if ranges allow newer versions
  → Adds/removes packages based on current package.json
  → Does NOT fail if package-lock.json is out of sync
  → Slower: checks registry for updates

npm ci:
  → Reads package-lock.json EXCLUSIVELY (exact versions, exact checksums)
  → Fails if package-lock.json is missing or out of sync with package.json
  → Deletes node_modules entirely before installing (clean slate)
  → Never modifies package-lock.json
  → Faster: no resolution, no registry version checks (for cached packages)
  → Verifies integrity hashes of downloaded packages

Use npm ci in CI/CD because:
  1. Reproducible: installs exactly what was tested (same lockfile)
  2. Safe: fails loudly if lockfile is stale (catches "works locally, fails in CI" bugs)
  3. Faster in CI: node_modules caching + no resolution overhead
```

```yaml
# Caching node_modules in GitHub Actions for faster npm ci:
- uses: actions/cache@v4
  with:
    path: ~/.npm          # npm cache directory (not node_modules)
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-
# npm ci uses the cache to avoid re-downloading packages
# Cache is keyed on lockfile hash — invalidated when lockfile changes
```

### Section 4: Registry Options Deep Dive

**Q12. How does GitHub Packages work as a private npm registry, and what are its limitations?**
A: GitHub Packages provides a per-repository or per-organization npm registry at `https://npm.pkg.github.com`. Packages are scoped to a GitHub user or organization — the scope must match the GitHub owner.

```
GitHub Packages rules:
  Package name:     MUST be @owner/package-name where owner is your GitHub user or org
  Visibility:       Follows the GitHub repository visibility (private repo → private package)
  Authentication:   GitHub PAT or GITHUB_TOKEN — always required, even for public packages
  Storage:          Counted against GitHub storage quota (depends on plan)
  Registry URL:     https://npm.pkg.github.com
```

```bash
# Authenticate with GitHub Packages:
npm login --scope=@mycompany \
          --auth-type=legacy \
          --registry=https://npm.pkg.github.com
# Username: your GitHub username
# Password: your GitHub PAT (with read:packages or write:packages)
# Email: your email

# Publish to GitHub Packages:
npm publish  # publishConfig.registry in package.json must point to GitHub

# Install from GitHub Packages:
npm install @mycompany/auth-client  # with .npmrc routing @mycompany → GitHub
```

**Critical limitation — authentication required for ALL packages, even public ones**:
```
Unlike npmjs.com where public packages need no auth, GitHub Packages requires
a valid GitHub PAT even to install a public package. This means:

- Open source libraries published to GitHub Packages cannot be consumed
  anonymously — every consumer must have a GitHub account and PAT
- This makes GitHub Packages unsuitable for public-facing OSS libraries
- Excellent choice for private/internal packages where all consumers
  already have GitHub access
```

**Q13. How does AWS CodeArtifact differ from npm and GitHub Packages, and when should you choose it?**
A: AWS CodeArtifact is a fully managed artifact repository that integrates with AWS IAM for authentication and supports npm, Maven, PyPI, NuGet, and more in one service.

**Key differentiators:**

```
Authentication model:
  npm/GitHub: static long-lived tokens (PATs, npm tokens)
  CodeArtifact: short-lived tokens generated from AWS credentials (12-hour max)

  Advantage: tokens expire automatically — no token rotation needed
  Disadvantage: must refresh tokens (add to CI pipelines, use CodeArtifact login scripts)

Upstream proxying:
  CodeArtifact can proxy public npm and cache packages internally:
  → Install @mycompany/auth-client from CodeArtifact (private)
  → Install lodash from CodeArtifact (cached from npm upstream)
  → Single .npmrc pointing to CodeArtifact for ALL packages
  → Faster installs (cached), reduced egress costs
  → Supply chain control: scan/block packages before they enter your network

Access control:
  npm: package-level access via npm access
  CodeArtifact: IAM policies — tie access to AWS roles, not usernames
  → EC2/ECS/Lambda can authenticate with their instance role — no token management
  → Perfect for AWS-native teams using IAM everywhere
```

```bash
# AWS CodeArtifact authentication flow:
# 1. Get a temporary token (valid 12h):
export CODEARTIFACT_TOKEN=$(aws codeartifact get-authorization-token \
  --domain mycompany \
  --domain-owner 123456789012 \
  --region us-east-1 \
  --query authorizationToken \
  --output text)

# 2. Configure npm to use CodeArtifact:
aws codeartifact login \
  --tool npm \
  --domain mycompany \
  --domain-owner 123456789012 \
  --repository my-npm-repo \
  --region us-east-1
# This command updates ~/.npmrc with the token automatically

# 3. Now npm install works for both private and public packages via CodeArtifact:
npm install @mycompany/auth-client
npm install lodash  # served from CodeArtifact's npm upstream cache

# In CI (GitHub Actions with OIDC):
- name: Configure AWS credentials
  uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
    aws-region: us-east-1

- name: Login to CodeArtifact
  run: |
    aws codeartifact login \
      --tool npm \
      --domain mycompany \
      --domain-owner 123456789012 \
      --repository my-npm-repo
```

**Q14. What is Verdaccio and when does self-hosting make sense?**
A: Verdaccio is a lightweight, open-source, self-hosted npm proxy/registry. It runs as a Node.js server and stores packages on the local filesystem or configurable storage backends.

```yaml
# verdaccio/config.yaml — minimal private registry config:
storage: ./storage
auth:
  htpasswd:
    file: ./htpasswd    # user credentials file (bcrypt-hashed passwords)
    max_users: 100

packages:
  '@mycompany/*':
    access: $authenticated     # only authenticated users can install
    publish: $authenticated    # only authenticated users can publish
    unpublish: $authenticated

  '**':                        # all other packages:
    access: $all               # anyone can read
    publish: $authenticated    # only authenticated can publish
    proxy: npmjs               # if not found locally, fetch from npm registry and cache

uplinks:
  npmjs:
    url: https://registry.npmjs.org/

server:
  port: 4873
```

```bash
# Run Verdaccio with Docker:
docker run -d \
  --name verdaccio \
  -p 4873:4873 \
  -v /opt/verdaccio/storage:/verdaccio/storage \
```

### Section 5: Security and Maintenance

**Q15. What security risks exist with private npm packages and how do you mitigate them?**
A: Private packages introduce security risks distinct from public packages — primarily around credential management and supply chain integrity.

**Risk 1: Token leakage**
```bash
# ❌ Tokens committed to source control — found in git history:
# .npmrc (committed by mistake):
//npm.pkg.github.com/:_authToken=ghp_realtoken123456

# Detection:
git log --all -p | grep "_authToken"            # search entire git history
git-secrets --scan                               # git-secrets tool
trufflehog git file://. --only-verified          # truffleHog secret scanner
gitleaks detect --source .                      # gitleaks

# Remediation if leaked:
# 1. Immediately revoke the token (GitHub → Settings → Personal access tokens → Delete)
# 2. Assume the token was used — audit registry logs for unexpected publishes/installs
# 3. Remove from git history (git filter-repo or BFG Repo Cleaner):
git filter-repo --replace-text <(echo 'ghp_realtoken123456==>REMOVED')
# 4. Force-push and notify all collaborators to re-clone
```

**Risk 2: Dependency confusion attacks**
```
Dependency confusion (2021 — Alex Birsan):
  An attacker finds internal package names (from error messages, job listings,
  public code, package-lock.json snippets) and publishes a malicious PUBLIC
  package with the same name but a higher version number.

  npm's default behavior: prefer the highest version number
  If @mycompany/auth-client is at v1.2.0 internally, attacker publishes
  @mycompany/auth-client@99.0.0 to public npm → npm installs the attacker's version.

Mitigations:
  1. Always publish your private package to public npm with a dummy version
     that's higher than any internal version (e.g., publish a stub at v99.99.99)
     with publishConfig.access=restricted or a package.json "private":true stub

  2. Lock registry per scope in .npmrc (registry routing):
     @mycompany:registry=https://npm.pkg.github.com
     → npm will ONLY look in GitHub Packages for @mycompany/* — never public npm

  3. Enable "allowExternalPrivate" setting on the registry to reject
     public packages with the same scope

  4. Use npm audit and Dependabot for private packages too
```

**Risk 3: Overpermissioned CI tokens**
```bash
# ❌ One token with publish rights used for everything (installs AND publishes):
# If the token leaks from a PR check: attacker can publish malicious versions

# ✓ Separate tokens by capability:
# CI build jobs (run on every PR):
#   → Read-only token: NPM_READ_TOKEN
#   → Can install packages, cannot publish

# Release jobs (run on version tags, restricted to main branch):
#   → Publish token: NPM_PUBLISH_TOKEN
#   → Protected by branch protection rules — can't be triggered from PRs

# GitHub Actions implementation:
jobs:
  test:
    # Uses read-only token — safe for PRs from forks:
    env:
      NODE_AUTH_TOKEN: ${{ secrets.NPM_READ_TOKEN }}

  publish:
    # Only runs on tag pushes to main branch:
    if: startsWith(github.ref, 'refs/tags/v') && github.ref_name == 'main'
    environment: npm-publish  # GitHub environment with required reviewers
    env:
      NODE_AUTH_TOKEN: ${{ secrets.NPM_PUBLISH_TOKEN }}
```

**Q16. How do you manage breaking changes in private packages consumed by multiple internal teams?**
A: Private packages shared across teams have the same versioning contract as public packages, but with one advantage: you control all consumers and can coordinate upgrades. A disciplined process prevents "surprise breakage" when a team updates a dependency.

```
Version strategy for shared private packages:

Phase 1: Minor version (1.2.0 → 1.3.0) — additive changes:
  → New exports, new options with defaults, new overloads
  → All consumers can upgrade without any code changes
  → Encourage immediate upgrade; support both minor versions briefly

Phase 2: Major version (1.x → 2.0.0) — breaking changes:
  → Changed function signatures, removed exports, behavior changes
  → Use a migration guide: MIGRATION.md with code diffs
  → Provide a codemod (jscodeshift) for mechanical changes
  → Give consumers a deprecation window (deprecate in 1.x, remove in 2.x)
  → Consider a lockstep release: upgrade all consumers in one PR wave

Deprecation in code (before removal in major):
```

### Section 6: Scenario / Interview-Style Questions

**Q17. "Your CI pipeline suddenly fails with `401 Unauthorized` when installing private packages. What are all the causes you would investigate?"**
A: A 401 on `npm ci` in a pipeline that was working previously is almost always an authentication problem. Systematic investigation in priority order:

```
1. Token expiry or revocation:
   → GitHub PAT tokens can be set to expire (30/60/90/custom days)
   → Check: GitHub → Settings → Personal Access Tokens → is it expired?
   → npm tokens: npm token list (on npmjs.com)
   → Fix: generate a new token, update the CI secret

2. Secret not available in the current context:
   → GitHub Actions: secrets are NOT available in PRs from forks (security)
   → Check: is this a PR from a fork? Is the secret scoped to the right environment?
   → Fix: use read-only token exposed to fork PRs; restrict publish token to internal only

3. Token scope/permission insufficient:
   → PAT was created with read:packages but the package is in a different org
   → npm token is read-only but someone called npm publish
   → Fix: ensure token has correct scopes for the operation

4. Registry URL mismatch:
   → .npmrc routes @scope to registry A, but token is for registry B
   → Check: does //registry.url/:_authToken= match the @scope:registry= value exactly?
   → Common mistake: trailing slash mismatch or http vs https

5. .npmrc not being read:
   → Working directory at time of npm ci doesn't contain the .npmrc
   → The setup-node action overwrote .npmrc (it creates one for its registry)
   → Fix: ensure .npmrc is in the root, or set NPM_CONFIG_USERCONFIG env var

6. Package visibility changed:
   → Package was public, converted to private (now needs auth)
   → Or: org plan downgraded, private packages became inaccessible
   → Check: registry web UI for the package's current visibility

7. GitHub Packages: GITHUB_TOKEN doesn't have cross-repo access:
   → GITHUB_TOKEN only has access to the current repo's packages
   → A package in a different repo needs a PAT with read:packages
   → Fix: add NPM_TOKEN secret (PAT) for cross-org packages

Diagnostic commands:
  npm install --verbose 2>&1 | grep -E "(401|403|Unauthorized|registry)"
  npm config list  # shows effective .npmrc configuration
  curl -H "Authorization: Bearer $TOKEN" https://npm.pkg.github.com/@mycompany/auth-client
```

**Q18. "How do you set up a new private package from scratch for a team of 10 developers across 3 projects? Walk through every decision."**
A: End-to-end setup covering registry choice, authentication, publishing, and consuming:

```
Decision 1: Registry

Decision 2: Package scope
```

## Problem 2 — Consuming Private Packages in a Dockerfile Without Leaking Tokens

### Problem
A Node.js service (deployed to Kubernetes) depends on `@mycompany/auth-client`. The Docker build must install the private package without baking the auth token into any image layer.

```dockerfile
# ❌ Naive approach — token in image history:
FROM node:20-alpine
ARG NPM_TOKEN
RUN echo "//npm.pkg.github.com/:_authToken=${NPM_TOKEN}" > .npmrc
COPY package*.json ./
RUN npm ci    # token in this layer's filesystem history
RUN rm .npmrc # too late — it's in the layer above
```

### Why the Naive Approach Leaks Tokens

```
Docker image layers are immutable. When you run:
  RUN echo "token" > .npmrc
  RUN rm .npmrc

Two layers are created:
  Layer 1: .npmrc exists with token content
  Layer 2: .npmrc is deleted

BUT: Layer 1 still exists in the image and is readable:
  docker save myimage:latest | tar -xO | \
    tar -xO layer1/layer.tar | \
    tar -xO .npmrc
  → Prints the token 💥

Anyone with access to the Docker image can extract the token.
This is a common security vulnerability in container images.
```

### Fix 1: BuildKit `--mount=type=secret` (Recommended)

```dockerfile
# syntax=docker/dockerfile:1
FROM node:20-alpine AS deps

WORKDIR /app

# Copy .npmrc that uses env variable reference (safe to include in image):
COPY .npmrc package.json package-lock.json ./

# --mount=type=secret: mounts the secret only during THIS RUN step
# It is NOT copied into the image filesystem — only visible to this command:
RUN --mount=type=secret,id=npm_token,env=NPM_TOKEN \
    npm ci --prefer-offline

# Production stage — no npm credentials at all:
FROM node:20-alpine AS runner
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build
CMD ["node", "dist/server.js"]
```

```ini
# .npmrc (committed — safe):
@mycompany:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NPM_TOKEN}
```

```bash
# Build with the secret:
export NPM_TOKEN="ghp_yourtoken"
docker buildx build \
  --secret id=npm_token,env=NPM_TOKEN \
  -t myservice:latest \
  --no-cache \
  .

# Verify no token in image:
docker save myservice:latest | \
  python3 -c "
import sys, tarfile, io
with tarfile.open(fileobj=io.BytesIO(sys.stdin.buffer.read())) as t:
    for m in t.getmembers():
        if m.isfile():
            content = t.extractfile(m).read().decode('utf-8', errors='ignore')
            if 'ghp_' in content:
                print(f'TOKEN FOUND in {m.name}')
"
# → No output — token not present in any layer ✓
```

### Fix 2: Multi-stage Build with Token Only in Build Stage

```dockerfile
# syntax=docker/dockerfile:1
# This approach is acceptable when BuildKit secrets are unavailable

# Single RUN = single layer = token never persisted in its own layer:

    && cat .npmrc  \

    && rm .npmrc   \

# Token exists only within this single RUN execution — not in the layer filesystem

FROM node:20-alpine AS runner

COPY --from=deps /app/node_modules ./node_modules
COPY . .

EXPOSE 3000
```


### Consuming Published Packages vs Workspace Symlinks

```ts
// Problem: ui's package.json has @mycompany/core: "^2.1.0"
// In workspace: resolves to symlink → local source (TypeScript)
// When published: consumer installs from registry → compiled JS + .d.ts

// This creates a subtle issue: if ui imports something that's in core/src
// but NOT yet exported from core/dist (e.g., developer forgot to build),
// the workspace resolves fine but the published package would fail.

// Fix: ensure your tsconfig.json "paths" for workspace packages
// point to the DIST output, not src:
// packages/ui/tsconfig.json
{
  "compilerOptions": {
    "paths": {
      // ✓ Point to dist output — same as what external consumers get:
      "@mycompany/core": ["../core/dist/types/index.d.ts"]
      // (Only needed if TypeScript doesn't auto-resolve via node_modules symlink)
    }
  }
}

// Or: use TypeScript project references (composite: true) which enforce
// that referenced packages are built before their consumers:
// packages/ui/tsconfig.json:
{
  "references": [{ "path": "../core" }]
}
// tsc --build packages/ui → builds core first, then ui
```

## Problem 5 — Debugging a `403 Forbidden` on `npm publish`

### Problem
A developer runs `npm publish` and receives `403 Forbidden`. The same token installs packages fine. Systematically diagnose and resolve it.

```bash
$ npm publish
npm error code E403
npm error 403 403 Forbidden - PUT https://npm.pkg.github.com/@mycompany%2fauth-client
npm error 403 In most cases, you or one of your dependencies are requesting
npm error 403 a package version that is forbidden by your security policy, or
npm error 403 on a server you do not have access to.
```

### Diagnostic Checklist

```bash
# Step 1: Verify the correct registry is being targeted:
npm config get registry                          # → https://registry.npmjs.org (wrong — public!)
npm config get @mycompany:registry               # → https://npm.pkg.github.com (correct)
cat package.json | grep publishConfig -A5        # check publishConfig.registry

# Fix if hitting wrong registry:
# Ensure publishConfig.registry is set in package.json, OR
# use explicit flag: npm publish --registry https://npm.pkg.github.com

# Step 2: Verify the token has write:packages permission:
curl -H "Authorization: Bearer $GITHUB_TOKEN" \
     https://api.github.com/user | jq '.login'
# → confirms token is valid

# Check token scopes:
curl -I -H "Authorization: Bearer $GITHUB_TOKEN" \
     https://api.github.com | grep -i "x-oauth-scopes"
# → x-oauth-scopes: read:packages, write:packages, repo   ✓
# → x-oauth-scopes: read:packages                         ✗ (missing write:packages)

# Step 3: Verify you are a member of the org and have publish access:
# GitHub → @mycompany org → Packages → @mycompany/auth-client → Manage access
# Your account must be in a team with "Admin" or "Write" access to the package

# Step 4: Check if the package name matches the GitHub org:
cat package.json | grep '"name"'
# → "@wrongorg/auth-client"  ← scope MUST match GitHub org name
# GitHub Packages requires @<github-org-name>/<package-name>

# Step 5: Verify the version doesn't already exist:
npm view @mycompany/auth-client@1.2.0 --registry https://npm.pkg.github.com
# If version exists → 403 (cannot overwrite published versions)
# Fix: bump version first: npm version patch

# Step 6: Check package.json for conflicting "private": true:
cat package.json | grep '"private"'
# → "private": true  ← blocks ALL publishing regardless of registry
# Fix: remove "private": true OR keep it and use workspace publish scripts
```

### Common 403 Causes and Fixes

```bash
# Cause 1: Token in .npmrc doesn't match the registry being published to:
# Symptom: npm ping works, npm publish 403

# .npmrc has:
# //npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
# But publishing to registry.npmjs.org (npm default)

# Fix: ensure publishConfig.registry in package.json matches the .npmrc registry line:
# package.json: "publishConfig": { "registry": "https://npm.pkg.github.com" }

# Cause 2: Publishing a scoped package for the first time with wrong access flag:
npm publish --access public   # ← trying to publish private package as public (if plan doesn't allow)
npm publish --access restricted  # ← correct for private packages

# Cause 3: Organization package permissions not configured:
# GitHub → Org Settings → Packages → Package creation
# Must be enabled for your org (default: disabled for private orgs)

# Cause 4: Two-factor auth required for publish but using automation token:
# npm accounts with 2FA enforcement need --automation tokens (bypass 2FA for CI)
# Or: use npm token create --automation to create an automation token

# Cause 5: Version already exists:
npm view @mycompany/auth-client versions --registry https://npm.pkg.github.com
# Check if your version is already published — cannot republish same version
# Fix: npm version patch (bump to next version)

# Verification after fix:
npm publish --dry-run   # simulate without actually publishing
npm publish             # publish
npm view @mycompany/auth-client --registry https://npm.pkg.github.com
# → shows version, dist-tags, publish time — confirms success
```

## Quick Reference — Private npm Packages Cheat Sheet

```
REGISTRIES:
  npmjs.com:        managed, free for public; paid for org private; simplest
  GitHub Packages:  managed; auth required even for public; GITHUB_TOKEN in Actions
  AWS CodeArtifact: managed; short-lived IAM tokens; upstream proxy; AWS-native
  Verdaccio:        self-hosted; free; full control; air-gapped networks

.NPMRC HIERARCHY (highest → lowest priority):
  CLI flags > project .npmrc > user ~/.npmrc > global > npm defaults
  Project .npmrc:  commit this — routing only, ${ENV_VAR} for tokens
  User ~/.npmrc:   never commit — actual token values, per-developer

SCOPED REGISTRY ROUTING:
  @mycompany:registry=https://npm.pkg.github.com   ← all @mycompany/* go here
  //npm.pkg.github.com/:_authToken=${GITHUB_TOKEN} ← token for that registry
  registry=https://registry.npmjs.org              ← everything else

PACKAGE.JSON FIELDS:
  "private": true          → blocks npm publish entirely (for apps, monorepo roots)
  "publishConfig"          → registry + access for this package
  "files": ["dist/"]       → whitelist published files (preferred over .npmignore)
  "exports"                → authoritative entry point map (Node 12+, bundlers)
  "main"                   → CJS entry (legacy fallback)
  "module"                 → ESM entry (bundlers, non-standard)
  "types"                  → TypeScript declarations

TOKEN TYPES:
  npm Classic:     read-only / publish / automation (bypasses 2FA)
  npm Granular:    expiry date + package scope + IP range (recommended for new setups)
  GitHub PAT:      read:packages (install) + write:packages (publish)
  GITHUB_TOKEN:    auto-injected in Actions; read:packages same org; write for own repo
  CodeArtifact:    short-lived (12h max) generated from IAM credentials

CI/CD AUTHENTICATION:
  GitHub Actions:   setup-node with registry-url + NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  Docker BuildKit:  --mount=type=secret (never baked into image layers)
  Docker ARG:       last resort — in image history; use single-RUN create+install+delete
  npm ci vs install: always use npm ci in CI (reproducible, lockfile-enforced, faster)

PUBLISHING:
  npm pack --dry-run       → verify files before publish
  npm version patch        → bump + git commit + git tag
  npm publish              → triggers prepublishOnly hook first
  npm publish --tag beta   → publish without updating "latest" dist-tag
  npm publish --dry-run    → simulate publish, see what would be sent

SECURITY:
  Never commit tokens      → use ${ENV_VAR} in .npmrc, tokens in ~/.npmrc or CI secrets
  Dependency confusion     → lock scope to private registry; publish stub to public npm
  Separate read/write tokens → read-only for PR checks; publish token for release jobs only
  Docker secrets           → --mount=type=secret prevents token in image history
  Token rotation           → PATs: 90 days; npm granular tokens: configurable expiry

COMMON ERRORS:
  401 Unauthorized         → token missing/expired/wrong scope; secret not available in CI context
  403 Forbidden (install)  → token lacks read:packages; not a member of org
  403 Forbidden (publish)  → wrong registry; lacks write:packages; version exists; "private":true
  404 Not Found            → wrong registry URL; package doesn't exist; scope misconfigured
  ERESOLVE                 → version range mismatch; workspace dep not found in registry

WORKSPACE PATTERNS:
  Inter-package deps:      use version range "^x.y.z" — workspace symlink in dev, registry in prod
  TypeScript references:   "references" array in tsconfig for composite packages
  publishConfig.directory: publish from dist/ without moving files (some bundlers)
  Changesets:              @changesets/cli for versioning + changelog in monorepos
```

**Final Tip:** At the 5 YOE level, private npm package questions test whether you can reason end-to-end about **the full lifecycle** — from configuring registry routing, to authentication across environments, to what lands in the published tarball, to what consumers actually receive. The highest-signal answer on `.npmrc`: "The project `.npmrc` is committed and contains only routing — which scope goes to which registry, with `${ENV_VAR}` references for tokens. The actual token lives in `~/.npmrc` on developer machines and in CI secrets as an environment variable. This way the auth configuration is documented in the repo without ever committing a credential." For Docker: "The naive `RUN echo token > .npmrc && npm ci && rm .npmrc` doesn't work because `rm` creates a new layer — the token still exists in the previous layer and can be extracted with `docker save`. The correct fix is `--mount=type=secret` with BuildKit, which makes the secret available only for that single RUN step and writes nothing to any layer." For 403 on publish: "The first thing I check is whether `publishConfig.registry` in `package.json` matches the token configured in `.npmrc` — a mismatch means npm sends the token to the wrong registry header, which rejects it. The second check is whether the token has `write:packages` scope and not just `read:packages` — a read-only token produces a 403 that looks identical to a permissions error."
