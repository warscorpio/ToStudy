# BullMQ (Node.js): Job Queues, Priorities, Delayed Jobs, Repeatable Jobs, Rate Limiting — Interview Q&A (5 YOE Level)

---

## Section 1: BullMQ Fundamentals

**Q1. What is BullMQ and what problem does it solve?**
A: BullMQ is a Node.js job and message queue library backed by Redis. It solves the problem of reliably offloading work from the request-response cycle — tasks that are too slow, too resource-intensive, or too failure-prone to handle inline in an HTTP handler:
- **Decoupling**: The API responds immediately; the work happens asynchronously in a separate worker process.
- **Reliability**: If a worker crashes mid-job, the job is not lost — it is reclaimed and retried by another worker.
- **Backpressure**: Workers process at their own rate; the queue absorbs spikes without overwhelming downstream services.
- **Scheduling**: Jobs can be delayed, repeated on a cron schedule, or rate-limited — capabilities that in-process `setTimeout` cannot provide reliably across restarts and multiple instances.

BullMQ is the v4+ successor to Bull — a full rewrite in TypeScript with better flow support, a cleaner API, and the removal of the separate `QueueScheduler` class (its responsibilities merged into `Worker`).

**Q2. What are the four main BullMQ classes and what is each responsible for?**
A:
- **`Queue`**: The producer-side interface. Used to add jobs, pause/resume the queue, get job counts, and remove jobs or repeatable job schedules. Does not process jobs — it only enqueues them.
- **`Worker`**: The consumer-side interface. Connects to a queue, dequeues jobs (via Redis blocking operations), runs the processor function, handles concurrency, retries, stall detection, delayed job promotion, and repeatable job scheduling. One Worker can process multiple jobs concurrently.
- **`QueueEvents`**: A subscriber to queue lifecycle events emitted by all workers across all processes — `completed`, `failed`, `progress`, `stalled`, `delayed`, `active`. Used for monitoring, metrics, and notifying callers when their job finishes.
- **`FlowProducer`**: Adds trees of jobs where parent jobs wait for all child jobs to complete before starting. Used for dependency graphs and pipeline workflows.

**Q3. What does BullMQ store in Redis, and why does this make it reliable?**
A: BullMQ uses Redis as its durable state store. Every job is a Redis hash containing its data, options, and current state. State transitions use Redis sorted sets, lists, and atomic Lua scripts:

- **`{queue}:wait`** — Redis list; jobs waiting in FIFO order (no priority)
- **`{queue}:prioritized`** — Redis sorted set; jobs waiting with priority scores
- **`{queue}:active`** — Redis set; jobs currently being processed
- **`{queue}:delayed`** — Redis sorted set; score = Unix timestamp ms when job becomes available
- **`{queue}:completed`** — Redis sorted set; successfully completed jobs (auto-cleaned by `removeOnComplete`)
- **`{queue}:failed`** — Redis sorted set; jobs that exhausted all retry attempts
- **`{queue}:repeat`** — Redis sorted set; repeatable job schedules with next-run timestamps

All state transitions are atomic Lua scripts — moving a job from `active` to `completed` is a single multi-key Redis operation that either fully succeeds or fully fails. There is no window where a job is in neither state. This is what makes BullMQ reliable across crashes: if a worker dies, the job remains in `active` until stall detection moves it back to `wait` for reprocessing.

**Q4. How do you set up a basic Queue and Worker in TypeScript/NestJS?**
A:

```typescript
// queue.module.ts (NestJS with @nestjs/bullmq)
import { BullModule } from '@nestjs/bullmq';

@Module({
  imports: [
    BullModule.forRoot({
      connection: { host: 'localhost', port: 6379 },
    }),
    BullModule.registerQueue({ name: 'email' }),
  ],
})
export class QueueModule {}

// email.producer.ts — adds jobs
@Injectable()
export class EmailProducer {
  constructor(@InjectQueue('email') private queue: Queue) {}

  async sendWelcomeEmail(userId: string) {
    await this.queue.add(
      'welcome',                    // job name
      { userId },                   // job data
      {
        attempts: 3,                // retry up to 3 times on failure
        backoff: { type: 'exponential', delay: 2000 },
        removeOnComplete: 100,      // keep last 100 completed jobs in Redis
        removeOnFail: 500,          // keep last 500 failed jobs
      },
    );
  }
}

// email.processor.ts — processes jobs
@Processor('email')
export class EmailProcessor extends WorkerHost {
  @Process('welcome')
  async handleWelcome(job: Job<{ userId: string }>) {
    await this.emailService.sendWelcomeEmail(job.data.userId);
    return { sent: true };          // stored as job.returnvalue
  }
}
```

**Q5. What is a "stalled" job and how does BullMQ handle it?**
A: A stalled job is one that was moved to `active` (a worker started processing it) but the worker never acknowledged completion — because the process crashed, the event loop was blocked, or the worker lost its Redis connection. Without stall detection, the job would be stuck in `active` forever — never completed, never failed, never retried.

BullMQ handles this with a heartbeat + periodic check mechanism:
- While processing, each Worker maintains a lock key in Redis (`{queue}:lock:{jobId}`) with a TTL (`lockDuration`, default 30s). The Worker renews this lock every `lockRenewTime` (default 15s, half of `lockDuration`).
- A background task (running in every Worker instance) periodically scans `active` jobs. Any job whose lock has expired is considered stalled.
- Stalled jobs are moved back to `wait` (counting as a retry attempt) and a `stalled` event is emitted.
- If a job stalls more than `maxStalledCount` times (default 1), it is moved to `failed` rather than retried again — preventing infinite stall loops for jobs that consistently crash their worker.

## Section 2: Job Lifecycle and States

**Q6. What is the full job state machine in BullMQ?**
A:

```
                      ┌─────────┐
  queue.add()  ──────▶│  wait   │ (FIFO list or prioritized ZSET)
  (no delay)          └────┬────┘
                           │ worker dequeues
                      ┌────▼────┐
  queue.add()  ──────▶│ delayed │ ─── scheduler promotes ──▶  wait
  (with delay)        └─────────┘     when delay elapses
                           │
                      ┌────▼────┐
                      │ active  │ (being processed by a worker)
                      └────┬────┘
              ┌────────────┼────────────┐
              │            │            │
         ┌────▼────┐  ┌────▼────┐  ┌───▼────────────────┐
         │completed│  │ failed  │  │ delayed (for retry) │
         └─────────┘  └─────────┘  └────────────────────┘
                           ▲
                    all attempts exhausted

Additional states:
  paused           — queue is paused; jobs wait here instead of wait
  waiting-children — parent job waiting for child jobs (Flows)
```

Each state corresponds to a Redis data structure. State transitions are atomic — a job is always in exactly one state.

**Q7. What is the difference between `job.data`, `job.opts`, `job.returnvalue`, and `job.failedReason`?**
A:
- **`job.data`**: The payload passed to `queue.add()` — the input to the processor function. Arbitrary JSON, stored in the job's Redis hash. Immutable after job creation (though `job.updateData()` exists for edge cases).
- **`job.opts`**: The options passed to `queue.add()` — `attempts`, `backoff`, `delay`, `priority`, `removeOnComplete`, `jobId`, etc. Also immutable after creation.
- **`job.returnvalue`**: Whatever the processor function returns, serialized to JSON and stored on the job. Accessible via `QueueEvents` `completed` event or by fetching the job after completion. Used to pass results back to callers that are polling or listening.
- **`job.failedReason`**: A string (the error message) set when a job fails. For a job that has exhausted all attempts and is in `failed` state, this contains the last error's message. The full stack trace is in `job.stacktrace` (an array, one entry per failed attempt).

**Q8. How does BullMQ's `jobId` option work and when should you use it?**
A: By default, BullMQ assigns each job a unique auto-incrementing ID. Setting `jobId` manually lets you control the job's identity:

```typescript
await queue.add('send-invoice', { invoiceId }, { jobId: `invoice:${invoiceId}` });
```

When you add a job with a `jobId` that already exists in the queue (in `wait`, `delayed`, or `active` state), BullMQ **does not add a duplicate** — it silently ignores the add. This makes `jobId` the primary mechanism for **job deduplication**: if your producer might emit the same job twice (due to retries, webhooks, at-least-once delivery), setting `jobId` to a stable business key prevents duplicate processing. Note: once a job with that ID has completed or failed and been removed from Redis (via `removeOnComplete`/`removeOnFail`), a new job with the same ID can be added again.

## Section 3: Priorities

**Q9. How does BullMQ implement job priorities?**
A: BullMQ maintains two separate waiting structures:
- **`{queue}:wait`** — a Redis list for jobs without priority (FIFO, `RPUSH`/`BLMOVE`)
- **`{queue}:prioritized`** — a Redis sorted set for jobs with `priority` set, scored so that lower priority numbers are dequeued first

When a job is added with `priority: N`, it goes into the `prioritized` sorted set with a score calculated to respect both priority and FIFO ordering within the same priority level:

```
score = priority * (2^48) + timestamp_counter
```

Workers use `ZPOPMIN` on the `prioritized` set to get the job with the lowest score (= highest priority). The `prioritized` set is checked before the `wait` list — meaning **any prioritized job is processed before any non-prioritized FIFO job**. Within the same priority value, FIFO order is maintained by the timestamp component of the score.

```typescript
// Priority 1 = highest; processed before priority 10
await queue.add('critical-alert', data, { priority: 1 });
await queue.add('bulk-report',   data, { priority: 10 });
await queue.add('routine-sync',  data);                    // no priority — FIFO
```

**Q10. What is priority starvation and how do you mitigate it?**
A: Priority starvation occurs when high-priority jobs arrive continuously, preventing low-priority jobs from ever being dequeued. If your system constantly produces `priority: 1` jobs, `priority: 10` jobs may wait indefinitely — technically correct by priority semantics, but operationally dangerous if those low-priority jobs include important maintenance tasks or SLA-bound work.

Mitigations:
- **Time-based priority escalation (aging)**: A background process periodically promotes old low-priority jobs to a higher priority level — jobs waiting more than N seconds get their priority decremented (lower number = higher priority). BullMQ doesn't do this natively; you implement it by polling `queue.getWaiting()` and calling `job.changePriority()`.
- **Separate queues by priority tier**: Use three queues (`critical`, `standard`, `bulk`) and allocate workers proportionally — e.g., 5 workers on `critical`, 3 on `standard`, 1 on `bulk`. Each queue is FIFO internally, but workers on `critical` are always free to serve critical work without being blocked by bulk jobs.
- **Bounded priority usage**: Reserve `priority: 1` for genuinely urgent work (incidents, time-sensitive payments) and let routine work be FIFO. Don't use priority as a general sorting mechanism — use it as an emergency override.

**Q11. Can you change a job's priority after it has been added?**
A: Yes — `job.changePriority({ priority: newValue })` atomically moves the job to its new position in the `prioritized` sorted set. This is useful for real-time escalation:

```typescript
// Escalate a job when SLA deadline approaches
const job = await queue.getJob(jobId);
if (job && (await job.getState()) === 'waiting') {
  await job.changePriority({ priority: 1 });
}
```

`changePriority` only works on jobs currently in `waiting` or `paused` state — a job in `active`, `completed`, or `failed` state cannot have its priority changed (it's no longer in the priority data structure). The operation is atomic — there is no window where the job is in neither the old nor the new priority position.

## Section 4: Delayed Jobs

**Q12. How do delayed jobs work in BullMQ?**
A: A delayed job is added with a `delay` option (milliseconds) or a specific `timestamp` (Unix ms):

```typescript
// Delay by duration
await queue.add('send-reminder', { userId }, { delay: 24 * 60 * 60 * 1000 }); // 24h

// Delay until a specific time
await queue.add('publish-post', { postId }, {
  timestamp: new Date('2025-09-01T09:00:00Z').getTime()
});
```

Internally:
1. The job is stored in `{queue}:delayed` — a Redis sorted set where the **score is the target execution Unix timestamp** (ms).
2. A scheduler running inside every `Worker` instance periodically calls a Lua script that:
   - Scans `{queue}:delayed` for jobs with `score <= Date.now()`
   - Moves those jobs atomically to `{queue}:wait` (or `{queue}:prioritized` if they have a priority)
3. The check interval is tuned by the `drainDelay` Worker option (default: 5ms) — the scheduler uses `BZPOPMIN` with a timeout to efficiently wait without busy-polling.

**Q13. What are the practical use cases for delayed jobs?**
A: Delayed jobs are the correct tool for several patterns that `setTimeout` cannot reliably implement across process restarts and multiple instances:

- **Retry with backoff**: On job failure, re-add the same job with an exponential delay rather than immediately requeuing. BullMQ's `backoff` option does this automatically — but manual delayed re-adds give you more control over the delay value.
- **Scheduled notifications**: "Send a re-engagement email 3 days after signup" — add the job at signup time with a `delay: 3 * 24 * 60 * 60 * 1000`. The delay survives server restarts.
- **Debouncing with jobId**: Add a job with `jobId: 'user:123:sync'` and `delay: 5000`. Subsequent events within 5 seconds try to add the same `jobId` — which is a no-op (deduplication). Only one sync job runs after 5 seconds of inactivity.
- **Deferred side effects**: After a payment is captured, delay the invoice generation by 10 seconds to allow the payment webhook to fully process before the invoice is generated (avoiding a race condition with the payment record being visible).
- **Time-of-day scheduling**: For jobs that should run at a specific wall-clock time (not a cron interval) — compute `delay = targetTimestamp - Date.now()` and add once.

**Q14. What happens to delayed jobs if the Worker is down when the delay elapses?**
A: The delayed job remains in the `{queue}:delayed` sorted set — it does not expire or disappear. When a Worker starts up (even hours or days later), the scheduler immediately runs and promotes all delayed jobs whose timestamp has passed into `wait`. The job will be processed when a worker becomes available, just later than intended.

This is a crucial reliability property: **delayed jobs are durable**. The delay is a "not before" guarantee, not an "exactly at" guarantee. If precision timing matters (e.g., a scheduled meeting reminder that is worthless if delivered an hour late), your processor should check `Date.now()` against the intended time and drop the job if it's too late rather than processing a stale notification.

## Section 5: Repeatable Jobs

**Q15. What is a repeatable job and how do you create one?**
A: A repeatable job is a job that automatically re-schedules itself after each execution, on either a cron schedule or a fixed interval:

```typescript
// Cron: run every day at 9AM UTC
await queue.add('daily-report', {}, {
  repeat: { cron: '0 9 * * *', tz: 'UTC' },
});

// Every: run every 30 seconds
await queue.add('health-check', {}, {
  repeat: { every: 30_000 },
});

// With limits
await queue.add('trial-reminder', { userId }, {
  repeat: {
    cron: '0 9 * * *',
    limit: 7,           // run at most 7 times (daily for one week)
    endDate: new Date('2025-12-31'),  // stop after this date
  },
});
```

BullMQ stores the repeat schedule in `{queue}:repeat` — a sorted set where each entry is a unique repeat key and the score is the **next execution timestamp**. The scheduler promotes a repeat entry to an actual job instance when its score <= `Date.now()`, then immediately calculates and updates the score to the next execution time.

**Q16. What is the repeat key and why does it prevent duplicate repeatable jobs?**
A: When you add a repeatable job, BullMQ derives a stable unique key from the combination of `(queueName, jobName, repeatOptions)`. If you call `queue.add('daily-report', {}, { repeat: { cron: '0 9 * * *' } })` multiple times — across deployments, restarts, or duplicate initialization code — BullMQ detects that a repeatable job with this key already exists and **does not create a second schedule**. This idempotency is critical for application startup code: you can safely call `queue.add` with repeat options on every server boot without accumulating duplicate cron jobs.

The key is computed deterministically — if you want to *change* a cron schedule, you must first remove the old repeatable job and then add the new one:

```typescript
// Wrong: adds a second repeat schedule alongside the existing one
await queue.add('daily-report', {}, { repeat: { cron: '0 10 * * *' } }); // won't replace 0 9

// Correct: remove old, add new
const repeatables = await queue.getRepeatableJobs();
const old = repeatables.find(r => r.name === 'daily-report');
if (old) await queue.removeRepeatableByKey(old.key);
await queue.add('daily-report', {}, { repeat: { cron: '0 10 * * *' } });
```

**Q17. How do you pass dynamic data to repeatable jobs if the data changes each run?**
A: Repeatable jobs store the `data` payload at schedule creation time — the same data is used for every execution. This works well for parameterless jobs (`daily-report` just runs the report) but breaks for jobs that need fresh data per run.

Patterns for dynamic data:
- **Thin payload, fat processor**: The repeatable job's payload contains only stable identifiers (a config key, a tenant ID). The processor fetches the actual runtime data from the database when it runs. The schedule is just the trigger; the processor assembles its own inputs.
- **Separate scheduler job**: A single repeatable job runs every N minutes and acts as a "scheduler" — it reads from the database to determine what work is due, then adds individual (non-repeatable) jobs for each unit of work with the current data. The repeatable job is a cron trigger; the actual work jobs are regular jobs with fresh payloads.
- **`job.updateData()`**: Inside the processor, after reading new data, update the job's data payload before it completes. This affects the stored job record but not the next execution's payload (which is set at schedule time). Not a clean pattern.

**Q18. How do you inspect and manage all repeatable jobs in a queue?**
A:

```typescript
// List all repeatable schedules
const repeatables = await queue.getRepeatableJobs();
/*
  [
    {
      key: 'daily-report:::0 9 * * *',
      name: 'daily-report',
      cron: '0 9 * * *',
      tz: 'UTC',
      next: 1751356800000,  // next run timestamp
    },
    ...
  ]
*/

// Remove by key (from getRepeatableJobs())
await queue.removeRepeatableByKey(repeatables[0].key);

// Remove by original options (reconstructs the key)
await queue.removeRepeatable('daily-report', { cron: '0 9 * * *', tz: 'UTC' });

// Pause all execution without removing the schedule
await queue.pause();      // stops workers from dequeuing
await queue.resume();
```

Monitoring repeatable jobs is critical in production: it's easy to accumulate stale schedules from old deploys. A startup check that logs all `getRepeatableJobs()` entries and alerts on unexpected ones is good operational hygiene.

## Section 6: Rate Limiting

**Q19. How does BullMQ's rate limiter work?**
A: Rate limiting is configured on the `Worker`, not the `Queue`. It limits how many jobs the worker processes within a given time window:

```typescript
const worker = new Worker('email', processor, {
  connection,
  limiter: {
    max: 100,        // max 100 jobs
    duration: 60_000, // per 60 seconds (1 minute window)
  },
});
```

Internally, BullMQ uses a Redis sorted set (`{queue}:limiter`) to track job completions within the window. When the worker is about to dequeue a job:
1. It checks how many jobs have been processed in the last `duration` ms.
2. If the count is below `max`: dequeue and process the job normally.
3. If the count has reached `max`: the job is moved to `delayed` state with a delay calculated to align with when the window resets. The worker waits and checks again.

This is a **sliding window** approach — `max` jobs per any `duration`-ms window, not per fixed calendar interval. Rate-limited jobs are not dropped; they are delayed and will be processed as soon as capacity is available.

**Q20. What is group rate limiting and when do you need it?**
A: Standard rate limiting applies a single global limit to all jobs in the queue. Group rate limiting applies independent limits per logical group — identified by a `rateLimiterKey` on each job:

```typescript
// Producer: tag jobs by tenant
await queue.add('send-sms', { message }, {
  rateLimiterKey: `tenant:${tenantId}`,  // each tenant gets its own bucket
});

// Worker: enable group limiting
const worker = new Worker('send-sms', processor, {
  connection,
  limiter: {
    max: 10,
    duration: 1000,
    groupKey: 'rateLimiterKey',   // read the group from job's opts
  },
});
```

With group rate limiting, each unique `rateLimiterKey` value gets its own independent `max/duration` bucket. Tenant A hitting its limit does not affect Tenant B's processing rate — isolation is per group, not global.

Use cases:
- **Multi-tenant SaaS**: Each tenant gets N API calls/second to a downstream SMS or email provider. Tenants don't compete with each other for throughput.
- **Per-user throttling**: Sending push notifications — each user gets at most 1 notification/minute, but high-volume users don't block low-volume users.
- **Third-party API quotas**: Different API keys have different rate limits — group by API key to apply the right limit per key.

**Q21. How does rate limiting interact with job priorities and delays?**
A: When a rate-limited job is moved to `delayed`, it retains its original priority. When the delay elapses and the job re-enters the `wait`/`prioritized` queue, it is processed in priority order among waiting jobs — it doesn't automatically jump to the front.

This interaction has a subtle implication: if your rate limit is very tight (`max: 1, duration: 60000` — 1 job per minute) and you have a high-priority job that is rate-limited, it may sit in `delayed` for up to 60 seconds even with `priority: 1`. Other high-priority jobs that arrive during that window will also be rate-limited and delayed. The rate limit is enforced regardless of priority — priority only determines order among jobs that are currently eligible to be processed, not whether the rate limit applies.

## Section 7: Concurrency, Retries, and Resilience

**Q22. How does Worker concurrency work, and how do you scale processing?**
A: The `concurrency` option on a Worker controls how many jobs it processes simultaneously within a single process:

```typescript
const worker = new Worker('image-resize', processor, {
  connection,
  concurrency: 10,  // process up to 10 jobs at the same time
});
```

For I/O-bound jobs (HTTP calls, database queries), high concurrency (10–50) is effective — the event loop can handle many concurrent async operations without being blocked. For CPU-bound jobs, concurrency should stay low (1–2 per core) or use sandboxed processors (separate child processes) to avoid starving the event loop.

Horizontal scaling — running multiple Worker instances across different processes or machines — multiplies throughput linearly. Each Worker instance independently dequeues jobs from Redis; there is no central coordinator. Scaling is as simple as starting more Worker processes. Redis acts as the shared queue; the BLMOVE operation that dequeues a job is atomic, so two workers never receive the same job.

```typescript
// Sandboxed processor: runs in a separate child process
const worker = new Worker('video-transcode', './processor.js', {
  connection,
  concurrency: 2,
  useWorkerThreads: false,  // uses child_process.fork
});
```

**Q23. How do retries and backoff work, and what are the backoff types?**
A: Retry behavior is configured per job or at the queue level:

```typescript
await queue.add('charge-payment', { orderId }, {
  attempts: 5,               // 1 initial attempt + 4 retries
  backoff: {
    type: 'exponential',     // delay doubles each retry
    delay: 1000,             // 1s, 2s, 4s, 8s (then job fails)
  },
});
```

**Backoff types**:
- **`fixed`**: Same delay between every retry. `delay: 5000` → always 5 seconds. Use when the failure is time-independent (e.g., a resource that may come back after a fixed maintenance window).
- **`exponential`**: Delay doubles each attempt: `delay * 2^(attemptNumber - 1)`. `delay: 1000` → 1s, 2s, 4s, 8s. Standard pattern for network/API failures where back-pressure helps.
- **`custom`**: Register a custom backoff strategy that computes the delay from the attempt count and error:

```typescript
// Register once at application startup
Worker.registerStrategy('jittered-exponential', (attemptsMade: number, err: Error) => {
  const base = 1000 * Math.pow(2, attemptsMade);
  const jitter = Math.random() * 1000;     // add randomness to prevent thundering herd
  return base + jitter;
});

// Use in job options
await queue.add('sync', data, {
  attempts: 4,
  backoff: { type: 'jittered-exponential' },
});
```

Failed jobs (exhausted all attempts) move to `failed` state. From there, they can be retried manually:

```typescript
const failed = await queue.getFailed();
await Promise.all(failed.map(job => job.retry()));
```

**Q24. How do you implement graceful shutdown to avoid losing in-flight jobs?**
A: Abruptly killing a worker process leaves its in-flight jobs in `active` state — they will be stalled and reprocessed, causing at-least-once semantics. For at-most-once side effects (payments, emails), this is dangerous. Graceful shutdown drains in-flight jobs before exiting:

```typescript
const worker = new Worker('email', processor, { connection });

// On SIGTERM (Docker stop, Kubernetes pod eviction, deployment)
process.on('SIGTERM', async () => {
  console.log('Graceful shutdown initiated');

  await worker.close();        // stop accepting new jobs; wait for active jobs to finish
  await connection.quit();     // close Redis connection

  console.log('Worker shut down cleanly');
  process.exit(0);
});
```

`worker.close()` stops the worker from dequeuing new jobs and waits for all currently active jobs to complete before resolving. In Kubernetes, the `terminationGracePeriodSeconds` must be longer than your maximum job duration — otherwise Kubernetes sends SIGKILL after the grace period, forcibly terminating jobs mid-execution.

For jobs that may run longer than the grace period, the processor should check `job.token` or listen for the worker's close event and cleanly abort the job (marking it failed or requeueing it) rather than being killed mid-processing.

## Section 8: Flows and Advanced Patterns

**Q25. What are BullMQ Flows and when should you use them?**
A: Flows allow you to create **dependency graphs of jobs** — a parent job only starts when all its child jobs have successfully completed. The `FlowProducer` API creates the entire tree atomically:

```typescript
import { FlowProducer } from 'bullmq';

const flow = new FlowProducer({ connection });

await flow.add({
  name: 'generate-annual-report',
  queueName: 'reports',
  data: { year: 2024 },
  children: [
    {
      name: 'compile-q1-data',
      queueName: 'data-compilation',
      data: { quarter: 1, year: 2024 },
    },
    {
      name: 'compile-q2-data',
      queueName: 'data-compilation',
      data: { quarter: 2, year: 2024 },
    },
    {
      name: 'compile-q4-data',
      queueName: 'data-compilation',
      data: { quarter: 4, year: 2024 },
      children: [                         // flows are arbitrarily deep trees
        { name: 'fetch-december', queueName: 'raw-data', data: { month: 12 } },
      ],
    },
  ],
});
```

Children are added first (they run first), then the parent waits in `waiting-children` state. As children complete, the parent is notified. When all children are complete, the parent moves to `wait` and is processed normally. The parent processor receives all children's return values via `job.getChildrenValues()`.

Use flows for: ETL pipelines that aggregate sub-results, report generation that depends on multiple data fetches, order fulfillment workflows (reserve inventory + charge payment + notify shipping, then send confirmation), and any DAG (Directed Acyclic Graph) of async tasks.

**Q26. How do you report job progress and listen for job completion from a caller?**
A: The producer side often needs to know when a specific job finishes — for polling endpoints, WebSocket push, or saga coordination:

```typescript
// Processor: report incremental progress
@Process('video-transcode')
async handleTranscode(job: Job) {
  for (let i = 0; i <= 100; i += 10) {
    await doTranscodeChunk(i);
    await job.updateProgress(i);        // stored as job.progress in Redis
  }
  return { outputUrl: 's3://bucket/video.mp4' };
}

// Caller: listen for completion of a specific job
const queueEvents = new QueueEvents('video-transcode', { connection });

const jobId = (await queue.add('video-transcode', { videoId })).id;

const result = await new Promise((resolve, reject) => {
  queueEvents.on('completed', ({ jobId: completedId, returnvalue }) => {
    if (completedId === jobId) resolve(JSON.parse(returnvalue));
  });
  queueEvents.on('failed', ({ jobId: failedId, failedReason }) => {
    if (failedId === jobId) reject(new Error(failedReason));
  });
});
```

For HTTP polling patterns, store the `jobId` in the response of the job-creation endpoint. The client polls `GET /jobs/:jobId/status`, which fetches `queue.getJob(jobId)` and returns `job.progress`, `job.returnvalue`, or `job.failedReason` based on state.

## Section 9: Scenario / System Design Questions

**Q27. "You need to send transactional emails (welcome, password reset, invoice) at scale. Design the BullMQ architecture."**
A: The design needs separate queues per email type (for independent scaling and monitoring), retry with backoff, and deduplication:

```typescript
// Three queues for independent scaling and dead-letter isolation
BullModule.registerQueue(
  { name: 'email:transactional' },  // welcome, password-reset — high priority
  { name: 'email:invoices' },       // invoice delivery — medium priority
  { name: 'email:marketing' },      // bulk campaigns — low priority, rate limited
)

// Welcome email: high priority, retry 3x, stable jobId prevents duplicate sends
await transactionalQueue.add(
  'welcome',
  { userId, to: email },
  {
    jobId:    `welcome:${userId}`,       // dedup: one welcome per user ever
    priority: 1,
    attempts: 3,
    backoff:  { type: 'exponential', delay: 2000 },
    removeOnComplete: 500,
  },
);

// Bulk campaign: rate-limited worker (respect SendGrid's API limits)
const marketingWorker = new Worker('email:marketing', sendEmail, {
  connection,
  concurrency: 5,
  limiter: { max: 100, duration: 1000 },  // 100 emails/sec (SendGrid free tier)
});
```

Monitoring: a `QueueEvents` listener on all three queues emits metrics to Prometheus (job duration, failure rate, queue depth). Bull Board provides a UI for inspecting and retrying failed jobs. Failed jobs in `email:transactional` trigger a PagerDuty alert; failed jobs in `email:marketing` are reviewed in batch.

**Q28. "Your repeatable job runs a nightly data sync. After a deploy, users report the sync is running twice nightly. What happened and how do you fix it?"**
A: Root cause: on each deploy, the application startup code calls `queue.add('nightly-sync', {}, { repeat: { cron: '0 2 * * *' } })`. If the cron pattern changed between deploys (even whitespace or timezone change), BullMQ generates a different repeat key — the old schedule remains and the new one is added, resulting in two independent schedules.

Diagnosis:
```typescript
const repeats = await queue.getRepeatableJobs();
console.log(repeats); // shows two entries for 'nightly-sync' with different keys
```

Fix:
```typescript
// Idempotent schedule setup — always clean before seeding
async function seedRepeatableJobs(queue: Queue) {
  const existing = await queue.getRepeatableJobs();

  // Remove all existing schedules for this job name
  for (const job of existing.filter(r => r.name === 'nightly-sync')) {
    await queue.removeRepeatableByKey(job.key);
  }

  // Add the canonical schedule fresh
  await queue.add('nightly-sync', {}, {
    repeat: { cron: '0 2 * * *', tz: 'UTC' },
  });
}
```

Running this on startup — regardless of how many times it's called — leaves exactly one schedule. Add a startup check that logs `getRepeatableJobs()` and alerts if any queue has more repeatable entries than expected.

**Q29. "A payment processing worker is marking jobs as complete before confirming the payment API response, causing missed payments. How do you ensure the job only completes if the payment actually succeeded?"**
A: The processor's return value (and thus the job's `completed` state) is determined by whether the processor function resolves or throws. If the payment API call throws (network error, 402, 500), BullMQ automatically retries according to `attempts` and `backoff`. The fix is ensuring the processor throws on payment failure:

```typescript
@Process('charge-payment')
async handleCharge(job: Job<{ orderId: string; amountCents: number }>) {
  const { orderId, amountCents } = job.data;

  let chargeResult;
  try {
    chargeResult = await this.stripeService.charge({
      amount: amountCents,
      idempotencyKey: `payment:${orderId}`,    // Stripe dedup on retry
    });
  } catch (err) {
    // Stripe threw — BullMQ will retry with backoff
    throw new Error(`Payment failed for order ${orderId}: ${err.message}`);
  }

  if (chargeResult.status !== 'succeeded') {
    // Non-exception failure — must throw explicitly to trigger retry
    throw new Error(`Payment status ${chargeResult.status} for order ${orderId}`);
  }

  // Only reaches here on confirmed success
  await this.orderService.markPaid(orderId, chargeResult.id);
  return { chargeId: chargeResult.id };   // job.returnvalue
}
```

Key patterns: the `idempotencyKey` on the Stripe call prevents double-charging on BullMQ retries (Stripe returns the original charge on duplicate key). All non-success paths throw — BullMQ only marks a job `completed` when the processor returns without throwing. After exhausting `attempts`, the job lands in `failed` where it can be inspected and manually retried after investigating.

**Q30. "You need to process webhook events from a third-party service. Events may arrive out of order and duplicate events are common. Design the BullMQ consumer to handle this."**
A: Webhook consumers need: deduplication (by event ID), order-aware processing (by entity + sequence), and resilient retries.

```typescript
// Webhook endpoint
app.post('/webhooks/payment-provider', async (req, res) => {
  const event = req.body;

  await queue.add(
    `payment.${event.type}`,          // job name = event type
    event,
    {
      jobId: event.id,                 // event.id = provider's stable UUID → dedup
      // If provider may send same event.id twice: second add is a no-op
    },
  );

  res.sendStatus(200);                 // ACK quickly; processing is async
});

// Processor: handle ordering via optimistic locking in DB
@Process('payment.charge.succeeded')
async handleChargeSucceeded(job: Job) {
  const event = job.data;

  const updated = await this.db.query(`
    UPDATE payments
    SET status = 'paid', provider_event_seq = $1
    WHERE payment_id = $2
      AND (provider_event_seq IS NULL OR provider_event_seq < $1)
  `, [event.sequence, event.paymentId]);

  if (updated.rowCount === 0) {
    // Either duplicate (same seq) or stale (older seq than current)
    // Both are safe to discard — log for observability but don't throw
    this.logger.warn(`Skipping stale/duplicate event ${event.id}`);
    return { skipped: true };
  }

  await this.orderService.fulfillOrder(event.paymentId);
}
```

The `jobId = event.id` prevents duplicate jobs for the same provider event. The `WHERE provider_event_seq < $1` guard prevents an out-of-order older event from overwriting a newer state — the conditional update is idempotent. Late-arriving or duplicate events are silently discarded after the DB check, without failing the job (which would trigger retries for a condition that isn't an error).

## Quick Reference

| Feature               | Option / API                                             | Notes                                                        |
|---                    |---                                                       |---                                                           |
| Add job               | `queue.add(name, data, opts)`                            | Returns `Job` instance with `id`                             |
| Deduplication         | `opts.jobId`                                             | Duplicate adds are no-ops while prior job is active          |
| Priority              | `opts.priority: 1` (highest) to N (lowest)               | Goes into `prioritized` ZSET; checked before FIFO `wait`     |
| Delay                 | `opts.delay: ms` or `opts.timestamp: unixMs`             | Stored in `delayed` ZSET; promoted by scheduler in Worker    |
| Repeat (cron)         | `opts.repeat: { cron, tz, limit, endDate }`              | Idempotent by key; remove old before changing cron           |
| Repeat (interval)     | `opts.repeat: { every: ms }`                             | Fixed interval; not guaranteed to drift-correct              |
| Remove repeatable     | `queue.removeRepeatableByKey(key)`                       | Get key from `queue.getRepeatableJobs()`                     |
| Retries               | `opts.attempts`, `opts.backoff: { type, delay }`         | Types: `fixed`, `exponential`, `custom`                      |
| Rate limit            | `Worker({ limiter: { max, duration } })`                 | Sliding window; rate-limited jobs go to `delayed`            |
| Group rate limit      | `opts.rateLimiterKey` + `limiter.groupKey`               | Independent buckets per group key                            |
| Concurrency           | `Worker({ concurrency: N })`                             | I/O-bound: high N; CPU-bound: low N or sandboxed             |
| Progress              | `job.updateProgress(value)` in processor                 | Readable as `job.progress` by callers                        |
| Events                | `new QueueEvents(name)` → `.on('completed', ...)`        | Listens across all workers on this queue                     |
| Flows                 | `new FlowProducer().add({ children: [...] })`            | Parent waits for all children; tree structure                |
| Graceful shutdown     | `await worker.close()`                                   | Finishes active jobs; stops dequeuing new ones               |
| Failed job retry      | `job.retry()`                                            | Moves from `failed` back to `wait`                           |
| Change priority       | `job.changePriority({ priority: N })`                    | Only works on `waiting` / `paused` jobs                      |

## The Core Mental Model

```
BullMQ = Redis-backed, durable job queue with scheduling superpowers.

Every job is a Redis hash. Every state transition is an atomic Lua script.
No job is ever in two states at once. No acknowledged job is ever lost.

The four scheduling tools:
  Immediate    → queue.add('job', data)              runs as soon as a worker is free
  Delayed      → opts.delay / opts.timestamp         runs after N ms (survives restarts)
  Repeatable   → opts.repeat: { cron / every }       runs on schedule (idempotent by key)
  Priority     → opts.priority: 1–N                  runs before lower-priority jobs

Rate limiter = "don't overload the downstream"
  Worker-level, not queue-level.
  Rate-limited jobs go to delayed, not dropped — they will be processed.
  Group rate limiting = per-tenant / per-key throttling with one queue.

Reliability chain:
  jobId dedup         → no duplicate job instances
  attempts + backoff  → resilient to transient failures
  stall detection     → survives worker crashes
  graceful shutdown   → no in-flight job loss on deploy
  idempotent processor → safe to retry (the real guarantee)

NestJS integration (@nestjs/bullmq):
  @InjectQueue('name')    → Queue instance (producer)
  @Processor('name')      → WorkerHost subclass (consumer)
  @Process('job-name')    → handler method for a specific job type
  BullModule.forRoot()    → shared Redis connection
  BullModule.registerQueue() → per-queue registration
```
