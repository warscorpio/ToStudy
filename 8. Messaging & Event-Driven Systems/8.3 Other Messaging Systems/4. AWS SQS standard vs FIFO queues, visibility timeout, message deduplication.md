# AWS SQS: Standard vs FIFO Queues, Visibility Timeout, Message Deduplication — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is AWS SQS and what problem does it solve?**
A: Amazon Simple Queue Service (SQS) is a fully managed distributed message queue service. It decouples the components of a distributed system by allowing a producer to send messages without requiring the consumer to be available at the same time. The queue acts as a durable buffer — messages persist until explicitly deleted by a consumer or until they expire.

Core problems SQS solves:
- **Temporal decoupling:** Producers and consumers don't need to run simultaneously. A producer can enqueue work while the consumer is down, scaling, or restarting.
- **Load leveling:** A burst of producer traffic is absorbed by the queue and processed at the consumer's sustainable rate — preventing downstream overload.
- **Resilience:** If a consumer crashes mid-processing, the message reappears in the queue (via visibility timeout expiry) and is retried by another consumer.
- **Horizontal scaling:** Multiple consumers can drain the same queue in parallel without coordination — adding consumers increases throughput linearly.

SQS is serverless from the operator's perspective — no cluster to manage, no partition sizing, no broker maintenance. It scales automatically and charges per API call.

**Q2. What are the two types of SQS queues and their fundamental difference?**
A: SQS offers two queue types with fundamentally different delivery and ordering guarantees:

**Standard Queue:**
- **Throughput:** Unlimited — supports virtually unlimited messages per second.
- **Ordering:** Best-effort ordering. Messages are generally delivered in roughly the order they were sent but this is not guaranteed. A message sent first may be delivered after one sent later.
- **Delivery:** At-least-once. A message may be delivered more than once (rarely, due to SQS's distributed storage architecture). Consumers must be idempotent.
- **Use cases:** Workloads where high throughput matters more than strict ordering or exactly-once delivery — image processing, log ingestion, email sending, background job queues.

**FIFO Queue (First-In-First-Out):**
- **Throughput:** 300 messages/sec (3,000 with batching of 10) per queue by default. High-throughput mode raises this to 9,000 (or 90,000 with batching) — enabled via the console or API.
- **Ordering:** Strict — messages are delivered in exactly the order they were sent within a message group.
- **Delivery:** Exactly-once processing within a 5-minute deduplication window. Duplicate messages (same deduplication ID within 5 minutes) are rejected at the queue level.
- **Use cases:** Workloads where order and exactly-once matter — financial transactions, order processing pipelines, event sourcing where event sequence is critical.

**Q3. What is the naming convention difference between Standard and FIFO queues?**
A: FIFO queues must have a name ending in `.fifo`. Standard queues have no suffix requirement:
- Standard: `order-processing`, `image-resize-jobs`, `email-notifications`
- FIFO: `order-processing.fifo`, `payment-transactions.fifo`

This suffix is enforced by AWS — attempting to create a FIFO queue without the `.fifo` suffix results in an error. The suffix is also required in the queue URL used for API calls.

## Section 2: Standard Queue Deep Dive

**Q4. What does "at-least-once delivery" mean in a Standard SQS queue, and when does a message get delivered twice?**
A: At-least-once delivery means SQS guarantees a message will eventually be delivered to a consumer, but offers no guarantee it will be delivered exactly once. Duplicate delivery happens because SQS stores messages across multiple servers for redundancy. In rare cases:

- **Storage redundancy:** A message is stored on multiple SQS servers. When a consumer calls `ReceiveMessage`, SQS typically returns each message from one server. In rare circumstances, a message can be returned from multiple servers in close temporal proximity — appearing as two deliveries.
- **Visibility timeout edge cases:** If a consumer processes a message but the `DeleteMessage` call fails (network issue, consumer crash), the message becomes visible again after the visibility timeout expires and is delivered to another consumer.
- **Consumer failure before delete:** The consumer receives the message (which starts the visibility timeout clock), processes it partially, then crashes before calling `DeleteMessage`. After the timeout, the message is redelivered.

**Implication:** Any consumer of a Standard SQS queue must be idempotent — processing the same message twice should produce the same outcome as processing it once. Design for it from the start: use `MessageId` or a business-level unique key as an idempotency key; use `INSERT ... ON CONFLICT DO NOTHING` or Redis SET NX for deduplication.

**Q5. What does "best-effort ordering" mean in practice for Standard queues?**
A: Best-effort ordering means that messages are generally but not strictly ordered. The practical behavior:
- Most of the time, messages arrive in roughly chronological order — a message sent at T=0 usually arrives before one sent at T=10s.
- Under high throughput, messages can be reordered. A message sent before another may be delivered after it.
- Messages can be delivered out of order to different consumers processing the same queue simultaneously.
- A message may be "invisible" to consumers (in flight to another consumer) while later messages are delivered — creating apparent gaps in delivery order.

**Consequence:** Any system that relies on the processing order of Standard queue messages is incorrectly designed. If order matters, include a sequence number or timestamp in the message payload, and sort/buffer at the consumer if needed — or use a FIFO queue.

## Section 3: FIFO Queue Deep Dive

**Q6. What is a Message Group ID and how does it work in FIFO queues?**
A: The Message Group ID is a required attribute for FIFO queue messages. It partitions the queue into independent ordered streams — messages with the same group ID are delivered in strict FIFO order; messages across different group IDs are independent and can be processed in parallel.

```
FIFO Queue: payment-transactions.fifo

Group "customer:alice":
  → msg1 (deposit $100)
  → msg2 (withdraw $50)
  → msg3 (deposit $200)
  These must be processed in this order. msg3 cannot be processed before msg1.

Group "customer:bob":
  → msg4 (deposit $300)
  → msg5 (withdraw $100)
  Independent of alice's group — can be processed simultaneously.
```

**Concurrency implications:**
- Within a message group: only one consumer processes messages at a time. If Consumer A is processing a message from group "customer:alice", all other messages from that group are invisible to other consumers until A deletes the message (or its visibility timeout expires).
- Across message groups: multiple consumers can process different groups simultaneously.
- Maximum parallelism = number of distinct active message group IDs. A FIFO queue with 1 message group ID is effectively single-threaded regardless of how many consumers exist.

**Choosing a Message Group ID:**
- Financial systems: `customer_id` or `account_id` — per-customer ordering.
- Order processing: `order_id` — all events for an order are ordered.
- Inventory updates for a product: `product_id`.
- Avoid a single constant group ID (e.g., `"global"`) — this serializes all processing and defeats the purpose of a queue.

**Q7. What is Message Deduplication ID in FIFO queues and how does it work?**
A: The Message Deduplication ID is an attribute provided by the producer (or derived automatically) that SQS uses to detect and discard duplicate messages within a 5-minute deduplication window.

**How it works:**
- Producer sends a message with `MessageDeduplicationId = "payment-abc-123"`.
- SQS stores the deduplication ID with a 5-minute TTL.
- If the same producer (or any producer) sends another message to the same queue with `MessageDeduplicationId = "payment-abc-123"` within 5 minutes, SQS discards the duplicate silently — returning success to the producer but not adding the message to the queue.
- After 5 minutes, the deduplication window expires. Sending the same ID again is treated as a new message.

**Two modes for deduplication ID:**

**Content-based deduplication (`ContentBasedDeduplication=true` on queue):**
SQS computes the deduplication ID as a SHA-256 hash of the message body automatically. The producer doesn't need to supply a deduplication ID. Useful when message content itself is the natural deduplication key (idempotent operations where sending the same payload twice should have the same effect).

```json
// Sending the same body twice within 5 minutes → second is deduplicated
{ "action": "charge", "amount": 100, "customer": "alice" }
{ "action": "charge", "amount": 100, "customer": "alice" }  ← discarded
```

**Producer-supplied deduplication ID (`MessageDeduplicationId` attribute):**
The producer explicitly generates a unique ID per logical operation. Recommended when the same content may represent different operations (e.g., charging the same customer $100 twice for different purchases — the content is identical but the intent is different).

```python
import boto3, uuid

sqs = boto3.client('sqs')
sqs.send_message(
    QueueUrl='https://sqs.us-east-1.amazonaws.com/123456789/payment-transactions.fifo',
    MessageBody=json.dumps({ "action": "charge", "amount": 100, "customer": "alice" }),
    MessageGroupId='customer:alice',
    MessageDeduplicationId=str(uuid.uuid4())  # unique per logical operation
)
```

**Q8. What is the throughput ceiling of FIFO queues and how do you work around it?**
A: Default FIFO throughput is 300 `SendMessage` / `ReceiveMessage` / `DeleteMessage` calls per second (3,000/sec with batching of 10). High-throughput mode increases this to 9,000 API calls/sec (90,000 with batching).

**Why FIFO is slower than Standard:** Standard queues are partitioned internally across many servers — writes and reads scale horizontally. FIFO queues maintain strict ordering and deduplication state, which requires more coordination and limits horizontal scaling.

**Workarounds for throughput constraints:**
- **Batching:** Use `SendMessageBatch` (up to 10 messages per API call) and `ReceiveMessage` (up to 10 messages per poll). This gives 10× throughput for the same API call rate.
- **Multiple FIFO queues:** Partition by a natural key. Instead of one `orders.fifo` queue, use `orders-us.fifo`, `orders-eu.fifo`, `orders-apac.fifo`. Each queue has its own throughput ceiling. Consumers for each region read from their respective queue.
- **High-throughput mode:** Enable via console or API if 3,000/sec is insufficient. Raises limit to 30,000 (90,000 with batching) but uses a different partition key scheme internally.
- **Reconsider FIFO:** If you're hitting throughput ceilings, evaluate whether strict ordering is genuinely required or whether it can be achieved at the consumer level (sequence numbers + in-consumer sorting). Standard queues with consumer-side ordering is often sufficient for many "ordered" use cases.

## Section 4: Visibility Timeout

**Q9. What is the visibility timeout and why is it the core reliability mechanism of SQS?**
A: The visibility timeout is the period during which a received message is invisible to other consumers. When Consumer A calls `ReceiveMessage` and gets message M, M is hidden from all other consumers for the duration of the visibility timeout. Consumer A is expected to process M and call `DeleteMessage` before the timeout expires. If A doesn't delete the message within the timeout (because it crashed, was too slow, or failed), M becomes visible again and is delivered to another consumer.

This mechanism provides automatic retry without any explicit retry configuration:

```
t=0:  Consumer A receives message M. Visibility timeout: 30s.
t=5:  Consumer A processes M successfully. Calls DeleteMessage. M is gone.

--- OR ---

t=0:  Consumer A receives message M. Visibility timeout: 30s.
t=15: Consumer A crashes. (Never calls DeleteMessage.)
t=30: Visibility timeout expires. M becomes visible again.
t=31: Consumer B receives message M. Processes it successfully. Deletes M.
```

**Default visibility timeout:** 30 seconds per queue (configurable 0–43,200 seconds / 12 hours). Can also be set per-message via `ChangeMessageVisibility` — useful when processing time is variable.

**Q10. How do you choose the right visibility timeout value?**
A: Setting the visibility timeout correctly is one of the most consequential SQS configuration decisions:

**Too short:**
- Consumer is still processing when the timeout expires.
- Message becomes visible and is delivered to another consumer.
- Both consumers now process the same message simultaneously — potential data corruption, duplicate side effects.

**Too long:**
- Consumer crashes or fails.
- The message is invisible for a long time before being retried.
- If the timeout is 12 hours and the consumer crashes at t=1 minute, the message won't be retried for ~12 hours — a long outage for time-sensitive work.

**Choosing the right value:**
- Profile the P99 processing time for your message type.
- Set the timeout to at least 2–3× the P99 processing time. Example: if P99 processing is 10 seconds, set timeout to 30 seconds.
- For variable-duration tasks (file processing, API calls with uncertain latency): start with a conservative timeout and use `ChangeMessageVisibility` to extend it dynamically if the task is still in progress.

```python
import boto3

sqs = boto3.client('sqs')

# Extend visibility timeout by 60 seconds while still processing
sqs.change_message_visibility(
    QueueUrl=QUEUE_URL,
    ReceiptHandle=message['ReceiptHandle'],  # required to identify the in-flight message
    VisibilityTimeout=60  # extend by another 60 seconds
)
```

**Heartbeat pattern:** For long-running tasks, run a background thread that calls `ChangeMessageVisibility` every `timeout/2` seconds, extending the timeout until the task completes. Stop the heartbeat and call `DeleteMessage` on success; stop the heartbeat and let the timeout expire (or call `ChangeMessageVisibility(0)`) on failure — returning the message to the queue immediately.

**Q11. What is the ReceiptHandle and why is it important?**
A: The `ReceiptHandle` is an identifier returned by `ReceiveMessage` that represents a specific receipt of a specific message at a specific point in time. It is required for:
- `DeleteMessage` — remove the message from the queue after successful processing.
- `ChangeMessageVisibility` — extend or reduce the visibility timeout of an in-flight message.

**Critical properties:**
- The `ReceiptHandle` is different from the `MessageId`. The `MessageId` identifies the message itself (stable across all deliveries). The `ReceiptHandle` identifies one specific delivery of the message — it changes on every re-delivery.
- `ReceiptHandle` is only valid for the current consumer during the current visibility timeout window. After the visibility timeout expires, the `ReceiptHandle` becomes invalid. Attempting to `DeleteMessage` with an expired `ReceiptHandle` fails silently (returns success but doesn't delete — the message was already requeued).
- You must store the `ReceiptHandle` from the `ReceiveMessage` response and use it promptly. If you process a message for 25 seconds and your timeout is 30 seconds, the 5-second window to call `DeleteMessage` is dangerously narrow.

**Q12. What is the MaximumReceives count and how does it interact with the visibility timeout?**
A: `MaximumReceives` is the maximum number of times SQS delivers a message before moving it to the Dead Letter Queue (DLQ). Each time a message's visibility timeout expires without being deleted, its receive count increments by 1. When the receive count exceeds `MaximumReceives`, SQS automatically moves the message to the configured DLQ.

```
MaximumReceives = 3

Delivery 1: Consumer A receives msg. Crashes. Timeout expires. ReceiveCount = 1.
Delivery 2: Consumer B receives msg. Processing fails. Timeout expires. ReceiveCount = 2.
Delivery 3: Consumer C receives msg. Crashes. Timeout expires. ReceiveCount = 3.
Delivery 4: ReceiveCount exceeds MaximumReceives (3). SQS moves msg to DLQ.
```

**Choosing MaximumReceives:**
- Too low (e.g., 1–2): Transient failures (momentary network hiccup, brief downstream unavailability) cause messages to be dead-lettered before the issue resolves. Legitimate messages are lost from the main queue prematurely.
- Too high (e.g., 100): A poison message (malformed, unprocessable) cycles through the queue many times before being dead-lettered — consuming consumer resources and delaying other messages.
- Recommended starting point: 3–5. Enough to handle transient failures; low enough to dead-letter persistent failures quickly.

## Section 5: Dead Letter Queues

**Q13. What is a Dead Letter Queue and what is its operational purpose?**
A: A Dead Letter Queue (DLQ) is a standard SQS queue that receives messages from a source queue when those messages exceed their `MaximumReceives` threshold — they couldn't be processed successfully after multiple attempts.

**Operational purposes:**
- **Poison message isolation:** A malformed or unprocessable message is removed from the main queue (where it would block or cycle) and placed in the DLQ where it can be inspected without impacting live processing.
- **Failure investigation:** The DLQ is a triage area — messages here represent failures worth investigating. Alert on DLQ depth > 0 to catch processing failures early.
- **Manual reprocessing:** After fixing the root cause (bug fix, downstream recovery), messages in the DLQ can be replayed back to the source queue using SQS's `StartMessageMoveTask` API (introduced 2023) or a custom replay script.
- **Audit trail:** DLQ messages are retained (up to 14 days) — they serve as a record of what failed and when.

**DLQ configuration requirements:**
- The DLQ must be the same type as the source queue (Standard → Standard DLQ, FIFO → FIFO DLQ).
- The DLQ's message retention period should be longer than the source queue's — you want messages in the DLQ long enough to investigate and replay.
- A DLQ can serve as the DLQ for multiple source queues.

**Q14. What is the difference between a DLQ and simply letting messages expire via the message retention period?**
A: Two different failure handling approaches:

**Message retention expiry:**
- Every SQS message has a retention period (default 4 days, max 14 days). After expiry, the message is permanently deleted regardless of whether it was processed.
- Expiry is silent — no notification, no log entry, no DLQ record. Messages silently vanish.
- No inspection or replay possible after expiry.

**Dead Letter Queue:**
- Messages move to DLQ only when they've been received and failed `MaximumReceives` times — indicating a persistent processing problem, not just slow consumption.
- DLQ entry is explicit — can trigger alerts (`ApproximateNumberOfMessagesVisible > 0` alarm on the DLQ via CloudWatch).
- Messages in DLQ are inspectable and replayable.
- DLQ messages also have a retention period — they don't live forever.

**Best practice:** Always configure a DLQ for production queues. Use retention expiry only as a backstop. Alert on DLQ depth. Periodically review DLQ contents.

## Section 6: Message Deduplication

**Q15. How does deduplication work differently in Standard vs FIFO queues?**
A: The two queue types offer fundamentally different deduplication capabilities:

**Standard Queue — no native deduplication:**
Standard queues provide no built-in deduplication. The at-least-once delivery guarantee means duplicates are an expected occurrence. The application layer must handle deduplication:
- Include a unique `MessageId` (SQS assigns one) or a business-level idempotency key in the message.
- Consumer checks a deduplication store (Redis SET NX, DynamoDB conditional write, PostgreSQL unique constraint) before processing.
- If already processed → skip and delete. If not → process, record in dedup store, delete.

**FIFO Queue — native 5-minute deduplication window:**
FIFO queues deduplicate at the queue level within a 5-minute window using the `MessageDeduplicationId`. Duplicate messages are rejected at enqueue time — the consumer never sees them.

```
Producer sends msg1 (DeduplicationId="pay-123") → queued.
Producer retries (network error) sends msg1 again (DeduplicationId="pay-123")
  → within 5 minutes → SQS discards silently. Consumer sees only one message.

After 5 minutes, the deduplication window expires.
Producer sends msg1 again (DeduplicationId="pay-123")
  → treated as new message → consumer sees it again.
```

**Q16. What are the limits of FIFO queue deduplication?**
A: FIFO deduplication has important limitations that are often overlooked:

**5-minute window only:** If a producer retries after 5 minutes, the deduplication window has expired and the message is enqueued as new. A producer retrying after a 10-minute outage will create duplicates. The consumer must still be idempotent as a defense in depth.

**Queue-scoped, not cross-queue:** Deduplication is per-queue. The same `MessageDeduplicationId` in two different queues are independent — no deduplication across queues.

**Content-based deduplication hashes the body only:** If using `ContentBasedDeduplication`, only the message body is hashed — not the attributes. Two messages with the same body but different message attributes are treated as duplicates. If your uniqueness is encoded in attributes rather than the body, use explicit deduplication IDs.

**No deduplication across consumer processing:** FIFO deduplication prevents the same message from being enqueued twice. It does not prevent a consumer from processing the same message twice if the consumer fails to delete it (visibility timeout expiry → redelivery). The consumer must still handle this.

**Producer-side retry without deduplication ID:** If using content-based deduplication and the message body is different on retry (e.g., a timestamp embedded in the body), the retry is not deduplicated — it is treated as a new message.

**Q17. How do you implement consumer-side deduplication for Standard SQS queues?**
A: Consumer-side deduplication using Redis and the SQS `MessageId`:

```python
import boto3
import redis
import json

sqs = boto3.client('sqs')
r = redis.Redis(host='redis-host', port=6379, decode_responses=True)

QUEUE_URL = 'https://sqs.us-east-1.amazonaws.com/123456789/my-standard-queue'
DEDUP_TTL = 86400  # 24 hours — longer than max redelivery window

def process_messages():
    while True:
        response = sqs.receive_message(
            QueueUrl=QUEUE_URL,
            MaxNumberOfMessages=10,
            WaitTimeSeconds=20,        # long polling
            VisibilityTimeout=60
        )
        for message in response.get('Messages', []):
            message_id = message['MessageId']
            dedup_key = f"sqs:processed:{message_id}"

            # Atomic check-and-set: SET NX = only set if not exists
            is_new = r.set(dedup_key, '1', nx=True, ex=DEDUP_TTL)

            if not is_new:
                # Already processed — delete from queue and skip
                sqs.delete_message(
                    QueueUrl=QUEUE_URL,
                    ReceiptHandle=message['ReceiptHandle']
                )
                continue

            try:
                # Process the message
                body = json.loads(message['Body'])
                handle_message(body)

                # Delete after successful processing
                sqs.delete_message(
                    QueueUrl=QUEUE_URL,
                    ReceiptHandle=message['ReceiptHandle']
                )
            except Exception as e:
                # Let the visibility timeout expire → SQS will redeliver
                # Remove from dedup store so the retry can be processed
                r.delete(dedup_key)
                raise e
```

**Key design decisions in this implementation:**
- Use SQS `MessageId` (stable across redeliveries) as the dedup key — not `ReceiptHandle` (changes per delivery).
- Redis `SET NX` is atomic — no race condition between check and set.
- On processing failure: remove the dedup key so the retry is not skipped. The visibility timeout expiry ensures SQS redelivers.
- TTL on dedup key must be longer than the maximum time a message could be in the queue (retention period) — otherwise a slow-delivered message is processed but its dedup record has expired by the time a duplicate arrives.

## Section 7: Polling, Long Polling, and Performance

**Q18. What is the difference between short polling and long polling in SQS?**
A: SQS offers two polling modes that differ in how they handle empty queues:

**Short polling (default, `WaitTimeSeconds=0`):**
- SQS queries only a subset of its servers and returns immediately — even if the queue is empty.
- If the queue appears empty (the polled servers have no messages), returns an empty response.
- Consumer must poll again immediately or after a brief sleep — high API call volume, higher cost.
- May miss messages that exist on unpolled servers — empty response does not guarantee empty queue.

**Long polling (`WaitTimeSeconds=1–20`):**
- SQS queries all servers and waits up to `WaitTimeSeconds` for a message to arrive.
- Returns as soon as a message is available (or after the wait time elapses if empty).
- Dramatically reduces empty responses and API call volume for low-traffic queues.
- Recommended for all production workloads: `WaitTimeSeconds=20` (maximum).

```python
response = sqs.receive_message(
    QueueUrl=QUEUE_URL,
    MaxNumberOfMessages=10,
    WaitTimeSeconds=20,     # long polling — wait up to 20 seconds for messages
    VisibilityTimeout=60
)
```

**Cost and performance impact:** At 10 polls/second with short polling and an empty queue: 864,000 API calls/day → significant cost. With long polling at `WaitTimeSeconds=20`: 4,320 API calls/day for the same idle period. Long polling also reduces false-empty responses, improving message visibility.

**Q19. What is batch processing in SQS and what are its trade-offs?**
A: SQS supports batch operations for both sending and receiving:

**Batch receive (`MaxNumberOfMessages=1–10`):**
Receive up to 10 messages per API call. Amortizes API call overhead across 10 messages — 10× more efficient than single-message polling.

**Batch send (`SendMessageBatch`):**
Send up to 10 messages in a single API call. Required for FIFO high-throughput mode. Each message in the batch can have a different `MessageGroupId` and `MessageDeduplicationId`.

**Batch delete (`DeleteMessageBatch`):**
Delete up to 10 messages per API call. Always batch deletes after batch receives to maintain the same throughput ratio.

```python
# Receive batch
response = sqs.receive_message(
    QueueUrl=QUEUE_URL,
    MaxNumberOfMessages=10,
    WaitTimeSeconds=20
)
messages = response.get('Messages', [])

# Process all messages
results = [process(m) for m in messages]

# Batch delete all successfully processed
successful_receipts = [
    {'Id': str(i), 'ReceiptHandle': m['ReceiptHandle']}
    for i, m in enumerate(messages)
    if results[i] == 'success'
]
if successful_receipts:
    sqs.delete_message_batch(QueueUrl=QUEUE_URL, Entries=successful_receipts)
```

**Trade-off with batch receive and visibility timeout:** If you receive 10 messages in one batch call, all 10 share the same visibility timeout clock started at receive time. If message #1 takes 50 seconds and your timeout is 60 seconds, message #10 only has 10 seconds of timeout remaining when you start processing it. Either process all messages quickly, or use `ChangeMessageVisibility` on slow messages.

## Section 8: Scenario / System Design Style Questions

**Q20. "You're building a payment processing system. Payments must be processed in order per customer and exactly once. Which queue type do you use and how do you configure it?"**
A: FIFO queue with explicit deduplication IDs:

**Queue configuration:**
```
Queue name:        payment-transactions.fifo
Queue type:        FIFO
ContentBasedDeduplication: false  (use explicit deduplication IDs — same amount
                                   charged twice to same customer is NOT a duplicate)
VisibilityTimeout: 60 seconds     (P99 processing time × 3)
MessageRetention:  4 days
MaximumReceives:   3              (DLQ after 3 failures)
DLQ:               payment-transactions-dlq.fifo
```

**Message design:**
```python
sqs.send_message(
    QueueUrl=PAYMENT_QUEUE_URL,
    MessageBody=json.dumps({
        'payment_id': 'pay-abc-123',   # business-level idempotency key
        'customer_id': 'cust-42',
        'amount_cents': 10000,
        'currency': 'USD',
        'payment_method': 'card_visa_4242'
    }),
    MessageGroupId=f'customer:{customer_id}',           # per-customer ordering
    MessageDeduplicationId=f'payment:{payment_id}'      # per-payment dedup
)
```

**Consumer design:**
```python
# Consumer still checks idempotency at the application level
# (FIFO dedup is 5-min window only — not sufficient for full lifecycle)
def process_payment(message):
    body = json.loads(message['Body'])
    payment_id = body['payment_id']

    # Application-level idempotency check
    if db.payment_already_processed(payment_id):
        sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=message['ReceiptHandle'])
        return

    # Process payment
    result = payment_gateway.charge(body)

    # Record result atomically
    db.record_payment(payment_id, result)
    sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=message['ReceiptHandle'])
```

**Q21. "Your SQS consumer is processing messages but you're seeing the same message processed twice occasionally. Diagnose the cause and propose fixes."**
A: Systematic diagnosis of duplicate processing:

**Most likely cause — visibility timeout too short:**
- The consumer is taking longer to process than the visibility timeout allows.
- By the time processing finishes and `DeleteMessage` is called, the timeout has expired.
- SQS has already redelivered the message to another consumer.
- Both consumers attempt to `DeleteMessage` — the second call fails silently (the first already deleted it), but both ran the business logic.

**Diagnosis:**
```python
# Add processing time logging
import time

start = time.time()
process_message(body)
elapsed = time.time() - start
logger.info(f"Processing took {elapsed:.2f}s for message {message_id}")

# Compare against visibility timeout — if elapsed approaches timeout, that's the cause
```

**Checks:**
1. Compare logged processing time (P99) against the queue's `VisibilityTimeout`. If processing time > 70% of timeout → resize the timeout.
2. Check CloudWatch metric `NumberOfMessagesNotVisible` — consistently high means many messages are in-flight, suggesting slow consumers.
3. Check for consumer crashes: CloudWatch Lambda errors or ECS task failures that prevent `DeleteMessage` from being called.

**Fixes:**
- Increase `VisibilityTimeout` to 3–5× P99 processing time.
- Implement the heartbeat pattern — extend visibility timeout during long processing.
- Add consumer-side deduplication (Q17) as defense in depth.
- If using Standard queue and exact delivery is critical — switch to FIFO.

**Q22. "You have a Standard SQS queue processing image resizing jobs. Suddenly one malformed image causes every consumer to crash on receipt. How does SQS handle this, and what do you need to configure?"**
A: This is the poison message scenario — a message that consistently causes consumer failure:

**What SQS does natively:**
1. Consumer A receives the malformed message. Crash. Visibility timeout expires. `ReceiveCount = 1`.
2. Consumer B receives it. Crash. Timeout expires. `ReceiveCount = 2`.
3. Consumer C receives it. Crash. Timeout expires. `ReceiveCount = 3`.
4. If `MaximumReceives = 3` and a DLQ is configured: SQS moves the message to the DLQ after the 3rd failure. Consumers stop seeing it. Other messages in the queue process normally.

**Required configuration:**
```
MaximumReceives:  3       (match retry tolerance)
DLQ:              image-resize-dlq  (must be configured before the poison message arrives)
DLQ Retention:    14 days           (time to inspect and fix)
```

**Alerting:**
```
CloudWatch Alarm:
  Metric: ApproximateNumberOfMessagesVisible (on DLQ)
  Threshold: > 0
  Action: SNS notification to on-call
```

**Without DLQ configured:** The poison message cycles indefinitely, consuming consumer capacity and delaying legitimate messages. This is why DLQ configuration is non-negotiable for production queues — configure it at queue creation time, not after a production incident.

**Q23. "Compare SQS with Kafka for an order processing pipeline. When would you choose each?"**
A: SQS and Kafka overlap in use case but differ fundamentally in model:

**Choose SQS when:**
- **Operational simplicity is paramount:** SQS is fully managed — no cluster, no partition sizing, no offset management. Teams without Kafka expertise can operate it immediately.
- **Auto-scaling consumers:** SQS + Lambda or SQS + ECS auto-scales consumers based on queue depth natively. Kafka requires manual partition count planning to limit consumer parallelism.
- **Short retention is acceptable:** SQS retains messages up to 14 days. If you only need messages processed once (not replayed), SQS is simpler.
- **Independent point-to-point communication:** One producer, one consumer group, one purpose. SQS queues are single-consumer-group by design.
- **AWS-native workloads:** SQS integrates natively with Lambda, SNS fan-out, EventBridge, Step Functions — minimal glue code.

**Choose Kafka when:**
- **Multiple independent consumer groups:** Many services need to independently consume the same events (analytics, notifications, inventory, shipping all react to `OrderPlaced`). Kafka's consumer group model allows N consumers to read the same topic independently. SQS requires N separate queues with SNS fan-out to replicate.
- **Long retention / replay:** Kafka retains messages for days or weeks — new consumers can replay history. SQS deletes messages after consumption.
- **Very high throughput:** Kafka handles millions of messages/sec per topic. SQS Standard is high throughput but Kafka edges it out for extreme-scale streaming.
- **Ordering with high parallelism:** Kafka's partition-per-consumer model gives ordered, parallelized processing with many partitions. SQS FIFO's throughput ceiling may be limiting.
- **Stream processing:** Kafka Streams, ksqlDB, and Flink integrate natively. SQS has no stream processing ecosystem.

**For order processing specifically:**
- SQS FIFO if: per-order ordering is required, the team is AWS-native, throughput is < 9,000 orders/sec, and you don't need event replay or multiple consumer groups.
- Kafka if: multiple services consume order events independently, throughput is high, you need replay for analytics backfill, or you run a Kafka-native platform.
- Many real systems use both: Kafka for high-throughput event streaming between services, SQS for job queues where work items need isolated processing with retries and DLQ.

**Q24. "Design the SQS-based retry and error handling strategy for a microservice that calls an external API to send notifications."**
A: A complete retry and error handling design:

**Queue topology:**
```
notifications-queue (Standard SQS)
  ├── VisibilityTimeout: 90s      (API call P99 ~20s × 3 = 60s, +30s buffer)
  ├── MessageRetentionPeriod: 4 days
  ├── MaximumReceives: 5          (5 attempts before DLQ)
  └── DLQ: notifications-dlq

notifications-dlq (Standard SQS)
  └── MessageRetentionPeriod: 14 days   (time for investigation + fix)
```

**Consumer logic with exponential backoff:**
```python
import time, math, boto3, json

sqs = boto3.client('sqs')
notification_api = ExternalNotificationAPI()

def process_notification(message):
    body = json.loads(message['Body'])
    receive_count = int(message['Attributes']['ApproximateReceiveCount'])

    try:
        notification_api.send(
            recipient=body['recipient'],
            content=body['content'],
            idempotency_key=message['MessageId']  # prevent API-side duplicates
        )
        sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=message['ReceiptHandle'])

    except RateLimitError:
        # Back off exponentially — extend visibility timeout
        # so message isn't redelivered until backoff period passes
        backoff_seconds = min(60 * (2 ** (receive_count - 1)), 900)  # max 15 min
        sqs.change_message_visibility(
            QueueUrl=QUEUE_URL,
            ReceiptHandle=message['ReceiptHandle'],
            VisibilityTimeout=backoff_seconds
        )
        # Don't delete — SQS will redeliver after backoff

    except PermanentError as e:
        # Non-retryable (invalid recipient, malformed payload)
        # Move to DLQ immediately rather than burning through retries
        logger.error(f"Permanent error for message {message['MessageId']}: {e}")
        # To immediately DLQ: change visibility to 0 (requeues instantly)
        # and let it fail naturally via MaximumReceives, or use a custom DLQ move
        sqs.change_message_visibility(
            QueueUrl=QUEUE_URL,
            ReceiptHandle=message['ReceiptHandle'],
            VisibilityTimeout=0   # return to queue immediately
        )
        # With MaximumReceives=5, this will reach DLQ after 5 failed attempts
        # For immediate DLQ: send to DLQ manually, then delete from source
```

**CloudWatch alarms:**
```
Alarm 1: notifications-dlq ApproximateNumberOfMessagesVisible > 0
  → PagerDuty: investigate failed notifications

Alarm 2: notifications-queue ApproximateAgeOfOldestMessage > 300s (5 min)
  → Alert: consumer is falling behind — check consumer health and scaling
```

## Quick Reference: SQS Decision Matrix

| Requirement | Standard Queue | FIFO Queue |
|---|---|---|
| Maximum throughput | Unlimited | 300/sec (3,000 with batching); 9,000 with high-throughput mode |
| Message ordering | Best-effort | Strict per message group |
| Exactly-once delivery | No (at-least-once) | Yes (within 5-min dedup window) |
| Deduplication | Application-side required | Native (content-based or explicit ID) |
| Multiple consumer groups | Not supported natively (use SNS fan-out) | Not supported natively |
| Message replay | No | No |
| Cost | Lower (Standard pricing) | Higher (FIFO pricing ~20% more) |
| DLQ support | Yes | Yes (FIFO DLQ required) |
| Lambda trigger | Yes | Yes |
| Use case | Background jobs, notifications, log ingestion | Financial transactions, order events, inventory updates |

**Tip for the interview:** SQS questions almost always escalate to three areas: (1) the visibility timeout — know that it's the core reliability mechanism, that setting it too short causes duplicates (not just retries), and how the heartbeat pattern with `ChangeMessageVisibility` handles variable-duration tasks; (2) FIFO deduplication limits — the 5-minute window means FIFO dedup is not a substitute for application-level idempotency; consumers must still handle duplicates for redeliveries after timeout expiry; (3) DLQ configuration — interviewers specifically probe whether you configure DLQs proactively or reactively. The answer is always proactively — configure `MaximumReceives` and a DLQ at queue creation time, alert on DLQ depth. Not having a DLQ in production is a red flag. The SQS vs Kafka comparison (Q23) is common in system design rounds — the key differentiator is consumer group model (SQS: one group; Kafka: many independent groups) and message replay (SQS: no; Kafka: yes).
