# RabbitMQ vs Kafka: Task Queues vs Event Streaming — Interview Q&A (5 YOE Level)

---

## Section 1: The Fundamental Mental Model Difference

**Q1. What is the core philosophical difference between RabbitMQ and Kafka?**
A: The difference is not just in features — it is in what each system considers the primary abstraction:

**RabbitMQ is a message broker**: The broker is responsible for routing, delivering, and discarding messages. A message is a transient unit of work — it exists to be consumed once and then deleted. The broker is "smart": it handles routing rules, TTLs, dead lettering, and priority. The consumers are "dumb": they receive whatever the broker delivers. The key question RabbitMQ is designed to answer is *"which consumer should handle this task?"*

**Kafka is a distributed log**: The broker is responsible for durably storing a sequence of records. A message (record) is an immutable, ordered fact — it exists in the log for as long as retention policy allows, regardless of whether anyone has consumed it. The broker is "dumb": it appends to a log and serves offset-based reads. The consumers are "smart": they track their own position, decide when to read, and can replay. The key question Kafka is designed to answer is *"what happened, in what order, and what does it mean for each system that cares?"*

This philosophical difference drives every practical comparison: routing, replay, delivery semantics, throughput design, operational complexity, and use-case fit.

**Q2. What is a "task queue" and what is "event streaming" as distinct architectural patterns?**
A: They solve structurally different problems:

**Task queue (work queue)**: A producer creates a unit of work — a task — that must be executed by exactly one worker. The task is consumed, processed, and then no longer exists. Multiple workers compete for tasks; load is distributed among them. The broker tracks which tasks are pending, in-progress, and done. The critical properties: one consumer per task, work-distribution semantics, acknowledgment-driven deletion, retry on failure. Examples: image resizing jobs, email sends, payment processing, report generation.

**Event streaming**: A producer emits a fact about something that happened — an event. Multiple independent downstream systems each need to react to that fact in their own way, on their own schedule, with no knowledge of each other. The event must be available for replay — to bring a new service up to date, to re-process after a bug fix, or to audit what happened. The critical properties: multiple independent consumers, retention beyond consumption, replay capability, ordered history. Examples: user signup events consumed by the email service, the analytics pipeline, and the ML feature store simultaneously; order events forming an audit log.

**Q3. What is the "smart broker, dumb consumer" vs. "dumb broker, smart consumer" distinction?**
A: This is the architectural compact of each system:

**RabbitMQ — smart broker, dumb consumer**: Routing logic, message filtering, TTLs, priority, dead lettering, and delivery scheduling all live in the broker configuration (exchanges, bindings, queue policies). The consumer is a recipient — it connects, receives what the broker sends, and acknowledges. Adding a new consumer type means reconfiguring the broker's exchange-queue bindings, not changing consumer logic.

**Kafka — dumb broker, smart consumer**: The broker stores ordered records in topics. It does no routing, no filtering, no TTLs per message, no priority. All intelligence is in the consumer: which topic to read, which offset to start from, how to filter relevant records, when to commit progress. Adding a new consumer means deploying a new consumer group that starts at any offset — zero broker reconfiguration.

The practical implication: RabbitMQ's power is in its broker configuration; Kafka's power is in consumer flexibility and the permanent, replayable log.

## Section 2: RabbitMQ Architecture

**Q4. What are RabbitMQ exchanges and what are the four exchange types?**
A: An exchange is the routing layer in RabbitMQ. Producers publish messages to exchanges, never directly to queues. The exchange decides which queue(s) to route each message to based on the exchange type and bindings:

- **Direct exchange**: Routes to queues whose binding key exactly matches the message's routing key. `routing_key="order.created"` → queues bound with `"order.created"`. Precise, point-to-point routing.
- **Fanout exchange**: Ignores routing keys entirely; broadcasts every message to all bound queues. Classic publish-subscribe for broadcasting the same event to multiple consumers.
- **Topic exchange**: Routes using wildcard patterns. `"orders.*.shipped"` matches `"orders.US.shipped"` and `"orders.EU.shipped"`. `"orders.#"` matches any routing key starting with `"orders."`. Enables fine-grained, pattern-based message routing — the most flexible type.
- **Headers exchange**: Routes based on message header values rather than routing keys. More expressive but rarely used; topic exchanges cover most routing needs more simply.

The exchange + binding + queue model is RabbitMQ's primary differentiator — it enables complex message routing without any application logic or consumer awareness of routing rules.

**Q5. How does RabbitMQ's consumer acknowledgment model work, and why does it matter?**
A: When a consumer receives a message, it is delivered but not yet removed from the queue. The message is held in an "unacknowledged" state. The consumer must explicitly send one of:
- **Ack**: "I processed this successfully" → broker deletes the message permanently.
- **Nack/Reject with requeue=true**: "I failed, try again" → message is returned to the queue for redelivery (to the same or another consumer).
- **Nack/Reject with requeue=false**: "I failed, discard or dead-letter this" → message goes to the Dead Letter Exchange (DLX) if configured, otherwise dropped.

If the consumer's connection drops before an ack, the broker automatically requeues the message — ensuring it is not lost due to a consumer crash. This is the core of RabbitMQ's at-least-once delivery guarantee: a message is never deleted until it is explicitly acknowledged.

**Prefetch count** (`basic.qos`) controls how many unacknowledged messages the broker will send to a consumer simultaneously. Setting `prefetch=1` ensures a consumer only receives one message at a time — the broker won't send another until the first is acked. This is essential for fair work distribution: without it, a fast broker could flood a slow consumer with hundreds of messages it can't process.

**Q6. What is a Dead Letter Exchange (DLX) and how is it used for retry logic?**
A: A Dead Letter Exchange is a regular exchange that receives messages that cannot be delivered normally — when a message is rejected (nack with requeue=false), its TTL expires, or the queue reaches its length limit. By binding a queue to a DLX, you create a separate holding area for failed messages rather than silently dropping them.

DLX enables sophisticated retry patterns:
- **Immediate retry**: DLX routes to the original queue → immediate redeliver. Simple but causes tight retry loops.
- **Delayed retry with TTL**: DLX routes to a "parking" queue with a per-message TTL. After the TTL, the parking queue's own DLX routes the message back to the original processing queue. Setting increasing TTLs per retry round (exponential backoff) requires per-retry-count TTL headers — achievable with a consumer that increments a retry-count header before nacking.
- **Dead letter archive**: After N retries (tracked via a retry-count header the consumer increments), the message is routed to a final "dead letter archive" queue for manual inspection or monitoring alerts.

RabbitMQ's DLX-based retry is more flexible than Kafka's dead letter topic pattern — it supports exponential backoff, TTL-based delay, and per-message retry counts without application-level orchestration.

**Q7. What are Quorum Queues and why do they replace classic mirrored queues?**
A: Classic mirrored queues replicated messages across multiple RabbitMQ nodes but had a significant flaw: any node in the cluster could be an "unsynchronized" mirror and be elected as the new master on failover — potentially losing messages that were acknowledged but not yet propagated. The consistency guarantee was weak.

Quorum queues (RabbitMQ 3.8+, now the recommended durable queue type) use the Raft consensus protocol: a write is only acknowledged to the producer after a quorum of nodes (majority) have written it. This guarantees no acknowledged message is lost on any single node failure. Quorum queues also support:
- Delivery limits (max retries before dead lettering, native to the queue)
- Poison message handling (automatically dead-letter after N delivery attempts)
- Predictable behavior under network partitions (Raft minority partition stops accepting writes rather than serving stale data)

For production RabbitMQ deployments where message durability matters: always use quorum queues, not classic mirrored queues.

## Section 3: Key Architectural Differences

**Q8. How does message lifetime differ between RabbitMQ and Kafka?**
A: This is the single most important practical difference:

**RabbitMQ**: A message lives in the queue from the moment it is published until it is acknowledged (or expires via TTL, or is rejected). The moment a consumer acks it, it is deleted from the queue — permanently. There is no record that the message ever existed. If you want to audit what was processed, the application must write that record elsewhere. There is no native replay.

**Kafka**: A message (record) is written to the partition log and stays there until the retention policy expires it — by time (`log.retention.hours`, default 7 days) or by size (`log.retention.bytes`). Consumer groups independently track their position (offset) in the log. Consuming a message does not delete it — other consumer groups read the same log independently. A consumer can reset its offset to re-read any message within the retention window. Replay is a first-class feature.

The retention model shapes the system's entire use case. RabbitMQ is a message conduit — messages pass through. Kafka is a message ledger — messages are stored and auditable.

**Q9. How do their consumer models differ — push vs pull?**
A: **RabbitMQ pushes** messages to consumers: the broker maintains an active connection to each consumer and delivers messages as soon as they arrive. Prefetch count governs flow control. A consumer that connects is immediately eligible to receive messages without doing anything.

**Kafka consumers pull** from the broker: consumers call `poll()` in a loop, specifying how many bytes/records they want and how long to wait. The broker responds with whatever is available at the current offset. Consumers are in full control of their read rate.

Practical implications:
- **Push (RabbitMQ)**: Lower latency for individual messages — the broker delivers immediately without waiting for a poll interval. Better for bursty workloads with spiky arrival rates.
- **Pull (Kafka)**: Consumers control their own throughput — no risk of a fast broker overwhelming a slow consumer. Better for sustained high-throughput processing where consumers need to work at their own pace. Enables consumer-side batching, which is a major contributor to Kafka's throughput advantage.

**Q10. How does message ordering differ between the two systems?**
A: **RabbitMQ** provides FIFO ordering within a single queue. However, ordering across multiple consumers of the same queue is not guaranteed: if consumer A is slow and has message 1 unacknowledged while consumer B has already processed message 2, the "effective order" of processing is out of sequence. With prefetch > 1, a consumer may process message 3 before it processes message 1 (from a previous prefetch batch). Strict end-to-end ordering in RabbitMQ requires `prefetch=1` and a single consumer per queue — eliminating the parallelism advantage of the task queue model.

**Kafka** provides strict ordering within a partition — all messages in a partition are consumed in the exact order they were produced. Across partitions, ordering is not guaranteed. To maintain ordering for related messages (e.g., all events for a specific order), produce them to the same partition using a consistent partition key (e.g., `order_id`). This is a first-class design pattern in Kafka, not a workaround.

**Q11. How does each system handle multiple consumers wanting the same messages?**
A: This is where the two systems diverge most sharply:

**RabbitMQ**: A message in a queue is delivered to exactly one consumer. To deliver the same message to multiple consumers, you must use a fanout exchange bound to multiple queues — one queue per consumer group. Each queue receives a full copy of every message. This is operationally complex at scale: adding a new consumer type requires creating a new queue and binding, and the broker holds one copy of each message per queue. For N consumers: N queues, N copies of each message in broker memory.

**Kafka**: Any number of consumer groups can independently read the same topic. Each group has its own offset — it reads all messages from the beginning (or from wherever it committed) without any broker-side configuration change. Adding a new consumer type means deploying a new consumer group with a new `group.id`. No topic reconfiguration, no new queue, no extra message copies. This is Kafka's killer feature for event streaming: one topic, infinite independent consumers, zero broker overhead per additional consumer.

**Q12. What throughput and latency profiles do the two systems have?**
A: The numbers are order-of-magnitude different:

**RabbitMQ**: Designed for message routing correctness and flexible delivery semantics, not raw throughput. A well-tuned single RabbitMQ node handles 50K–100K small messages/second. Throughput scales horizontally with clustering (shovel, federation, multiple queues across nodes) but with added operational complexity. Per-message latency: typically 1–5ms for delivered messages (push-based, low polling overhead).

**Kafka**: Designed from the ground up for throughput — sequential disk writes, zero-copy transfer, consumer-side batching, log compaction. A single Kafka partition handles hundreds of thousands of messages/second; a cluster easily handles millions/second. Kafka's latency is tunable: with `linger.ms=0`, it can approach single-digit milliseconds; with larger `linger.ms` (5–50ms), it batches aggressively for maximum throughput. The trade-off is intentional — Kafka optimizes for total throughput, not minimum per-message latency.

Rule of thumb: if throughput exceeds ~50K messages/sec sustained, or if the data volume requires days-to-weeks of retention, Kafka is the correct choice on those axes alone.

## Section 4: When to Use RabbitMQ

**Q13. What are the canonical use cases where RabbitMQ is the right choice?**
A: RabbitMQ excels in five categories:

- **Task/work queues**: Background jobs that must be processed exactly once by one worker — image processing, PDF generation, email sends, video transcoding. The competing-consumer pattern (multiple workers, each consuming one task at a time) is RabbitMQ's native strength.
- **Complex message routing**: Messages need to be dispatched to different consumers based on content, type, or properties — order events to the fulfillment service but not the analytics service; error-level logs to PagerDuty but not to the log archive. RabbitMQ's exchange-binding model handles this without application code.
- **RPC / request-reply patterns**: A producer sends a task and needs a response on a reply queue. RabbitMQ supports this natively via the `reply_to` and `correlation_id` message properties. Kafka has no native request-reply — you'd need two topics and application-level correlation.
- **Short-lived messages**: Messages that should expire if not processed quickly (e.g., real-time notifications, price quotes, one-time tokens with TTL). RabbitMQ's per-message and per-queue TTL is native; Kafka's time-based retention is coarse-grained (per-topic policy, not per-message).
- **Priority queues**: High-priority tasks should jump ahead of lower-priority ones. RabbitMQ supports queue-level priority (1–255 per message). Kafka has no priority — all messages in a partition are consumed in FIFO order.

**Q14. What RabbitMQ-specific patterns have no Kafka equivalent?**
A:
- **Dead Letter Exchanges with exponential backoff**: A message that fails processing is dead-lettered to a TTL queue; after the TTL it is re-routed to the processing queue. Increasing TTLs per retry implement exponential backoff natively in the broker, without application logic. Kafka requires application-level retry topic management or a separate framework (Spring-Retry, Resilience4j) to achieve similar behavior.
- **Per-message TTL**: Individual messages can be given different TTLs (`x-message-ttl` per message or per queue). Messages that aren't consumed within their TTL expire and are dead-lettered or dropped. Kafka's retention is topic-level — you cannot give one message a 5-minute TTL and another a 1-hour TTL on the same topic.
- **Per-consumer rate limiting via prefetch**: `basic.qos(prefetch=N)` ensures no consumer is sent more than N unacknowledged messages — a fine-grained back-pressure mechanism at the individual consumer level. Kafka's consumer-side `max.poll.records` is a blunter instrument that doesn't prevent a fast partition from overwhelming a slow consumer the same way.
- **Temporary (auto-delete) queues**: Queues that automatically delete when their last consumer disconnects. Used for transient consumers (WebSocket push delivery, session-scoped queues) that don't need durable storage.

## Section 5: When to Use Kafka

**Q15. What are the canonical use cases where Kafka is the right choice?**
A: Kafka excels in five categories:

- **Multiple independent consumers**: Many services need to react to the same events. User signup events go to the email service, the onboarding workflow, the analytics pipeline, and the fraud detection model — all independently, at their own pace, with no coupling between them. Kafka's consumer group model handles N independent readers of the same topic with zero broker reconfiguration.
- **Replay and event sourcing**: A new service needs to process all historical events to build its initial state. A bug in a consumer is fixed and needs to reprocess the last 48 hours of data. Kafka's offset reset and configurable retention window make this trivial. RabbitMQ cannot replay — consumed messages are gone.
- **High-throughput data pipelines**: Metrics collection, log aggregation, clickstream data, IoT sensor readings — workloads producing millions of events per second that must be reliably ingested and delivered to downstream consumers (analytics systems, data warehouses, ML feature stores). Kafka's sequential write model and batching make it the standard choice for this category.
- **Audit logs and compliance**: An ordered, immutable record of all events is required for regulatory compliance or forensic debugging. Kafka's append-only log with configurable retention (including infinite retention via log compaction) is a natural audit log. RabbitMQ's deletion-on-ack model makes it unsuitable.
- **Event-driven microservices at scale**: Services communicate by producing and consuming events — decoupled, asynchronous, without direct service-to-service calls. Kafka acts as the event backbone: producers emit facts, consumers react on their own schedule. The log is the integration point, and all services are consumers of the same event history.

**Q16. Why is Kafka's replay capability strategically important beyond debugging?**
A: Replay is not just a debugging tool — it is a fundamental architectural capability:

- **Bootstrapping new services**: When a new service joins the ecosystem, it needs to build its local state from all historical events. With Kafka, it simply sets its offset to 0 (or to the start of the retention window) and reads the log forward. With a traditional message queue, the historical data is gone — you need a separate "snapshot" mechanism or a manual data migration.
- **Schema evolution and backfill**: If the way an event should be processed changes (new business logic, schema change, bug fix), you can deploy the new consumer and reset its offset to replay all relevant events through the new logic. The event history is the source of truth; current state is a derived view.
- **Multiple derived views from the same events**: An order-events topic might feed an order-status database, a revenue-analytics aggregate, and a fraud-detection feature store — all derived independently from the same event log. Adding a new derived view is just adding a new consumer group; no data migration is needed.

This is the event sourcing philosophy made operational: the log is primary; everything else is a projection. RabbitMQ supports neither the model nor the capability.

## Section 6: Anti-Patterns — When Each System Is Wrong

**Q17. What are the common Kafka anti-patterns?**
A: Signs that Kafka is the wrong tool:

- **Task queues with complex routing**: Kafka topics are coarse-grained routing units. Routing messages to different workers based on message content (e.g., "high-priority orders to workers A–C, standard orders to workers D–J") requires either many topics (operational overhead) or consumer-side filtering (workers read everything and discard most). RabbitMQ's topic exchange handles this natively.
- **Request-reply / RPC**: Kafka has no request-reply primitive. Building RPC on Kafka means two topics (request + reply), correlation IDs in application code, timeout handling, and consumer-side routing of replies to the right caller. This is viable but verbose. RabbitMQ, gRPC, or REST are simpler for synchronous request-response.
- **Priority queuing**: Kafka provides no priority. If some messages must jump the queue, Kafka can't help without multiple topics of different priority (and a consumer that reads high-priority first). A native RabbitMQ priority queue handles this in one queue.
- **Very low message volumes with high operational cost**: A small application sending 100 messages/day doesn't need a Kafka cluster. The operational burden (multiple brokers, ZooKeeper or KRaft quorum, monitoring, tuning) far exceeds the value. RabbitMQ, SQS, or even a simple Postgres-backed job table are proportionate choices.
- **Using Kafka as a database**: Kafka is not designed for random-access reads by arbitrary keys. Reading one specific message by its content requires scanning the entire partition. Kafka Streams or ksqlDB can materialize state into local RocksDB stores, but the query model is stream-first. For point lookups, use a database.

**Q18. What are the common RabbitMQ anti-patterns?**
A: Signs that RabbitMQ is the wrong tool:

- **Multiple independent consumers needing the same messages**: Achieving pub-sub in RabbitMQ requires a fanout exchange with one queue per consumer type. Each queue is a separate copy of all messages. Adding a new consumer type means creating a new queue and binding — a broker-side operation. This model doesn't scale gracefully beyond a handful of consumer types and doesn't support ad-hoc consumers (e.g., running a one-off analysis against all events).
- **Needing message replay**: If a consumer dies, crashes, or is added after events were published, those events are gone. There is no offset to reset, no retained log to re-read. Any system where replay, reprocessing, or historical catch-up is a requirement is wrong for RabbitMQ.
- **Very high throughput sustained workloads**: At 500K messages/sec sustained, a RabbitMQ cluster will struggle — queue depths grow, memory pressure increases, the broker becomes the bottleneck. Kafka's log-based architecture scales to this throughput on modest hardware.
- **Using queues as durable storage**: RabbitMQ queues can become arbitrarily large (bounded by disk), but they're not a storage system — long queues degrade broker performance (index scanning, memory pressure). Kafka's log retention is designed for long-term, large-volume storage; RabbitMQ's queues are not.
- **Long retention for audit purposes**: Storing messages in a RabbitMQ queue for 7 days for audit purposes means those messages are never consumed — the queue grows indefinitely. This is an abuse of the model. Kafka's time-based retention and log compaction are designed precisely for this.

## Section 7: Hybrid Architectures

**Q19. When and how do you use RabbitMQ and Kafka together?**
A: In mature event-driven architectures, both systems coexist with distinct roles:

**Kafka as the event backbone, RabbitMQ as the task distributor**:
1. Services produce domain events to Kafka (order created, payment completed, user signed up).
2. A Kafka consumer reads these events and, for each one requiring work by a specific worker pool, publishes a task to a RabbitMQ queue.
3. Worker pods consume from RabbitMQ with competing-consumer semantics — one task to one worker, with ack-based retry.
4. The benefit: Kafka provides the durable, replayable event log (audit, analytics, new service catch-up); RabbitMQ provides the fine-grained task routing and work distribution that Kafka's consumer group model doesn't match.

**When this makes sense**: An order-created event goes to Kafka (for analytics, fraud detection, the order-status service). The specific task of "send a confirmation email for this order" goes to RabbitMQ — one email per order, retried via DLX if the email provider fails, routed to a priority queue for VIP orders. The email task doesn't belong in Kafka: it's consumed once and gone, needs per-task retry, and benefits from priority routing.

**The opposite — Kafka as the persistent layer, RabbitMQ as the push delivery layer**: Kafka stores the canonical event stream; a Kafka consumer reads events and pushes them via RabbitMQ to services that require push-based delivery (legacy systems using AMQP, IoT devices, real-time dashboards). RabbitMQ acts as the "last mile" push adapter without replacing Kafka's log.

**Q20. What managed cloud alternatives map to each system?**
A:
| Need | RabbitMQ equivalent | Kafka equivalent |
|---|---|---|
| Managed, serverless | Amazon SQS (queues) + SNS (fanout) | Amazon MSK, Confluent Cloud, Redpanda Cloud |
| Simple task queue | Amazon SQS | Amazon Kinesis (lighter than Kafka) |
| Complex routing | Amazon SNS with filter policies | — (Kafka has no equivalent; use topics) |
| High throughput log | — | Amazon MSK, Confluent, Redpanda |
| Replay / event sourcing | — | Amazon MSK, EventBridge (limited replay) |
| Fully serverless | Amazon SQS/SNS | Amazon Kinesis, Confluent Serverless |

Amazon SQS/SNS is the most common cloud-native RabbitMQ substitute: SQS for task queues (competing consumers, DLQ, visibility timeout as ack model), SNS for fanout to multiple SQS queues. Neither supports replay, ordering beyond FIFO queues, or Kafka-style consumer groups.

## Section 8: Scenario / System Design Questions

**Q21. "You're building an order processing system. Orders need to trigger: invoice generation (one job), email confirmation (one job), and inventory reservation (one job). Which system do you use?"**
A: This is a task queue pattern — each downstream action is a discrete, stateful job that must be executed exactly once by one worker. RabbitMQ is the correct choice.

Design:
- A direct or topic exchange receives order events with routing key `order.created`.
- Three queues bound: `invoice-jobs`, `email-jobs`, `inventory-jobs`.
- Three independent worker pools, one per queue. Each pool competes for tasks within its queue.
- Each worker acks on successful job completion; nacks (with requeue=false) on failure → DLX → retry queue with TTL-based backoff.

Why not Kafka: Each action needs to be triggered exactly once per order — the competing-consumer model is correct. Kafka consumer groups would re-trigger the action if the consumer offset is reset. Kafka's partition-level ordering doesn't help here (each order is independent). The routing from one event to three distinct job queues is clean in RabbitMQ's exchange model; in Kafka, it would require three topics (one per job type) with a routing consumer.

**Q22. "You're building a platform where user activity events (clicks, purchases, searches) must feed: a real-time recommendation engine, an analytics data warehouse, a fraud detection model, and a future A/B testing service not yet built. Which system?"**
A: This is the canonical event streaming use case — Kafka is the correct choice.

The decisive factors:
- **Multiple independent consumers**: Four current consumers + an unknown future consumer. Kafka's consumer group model adds new consumers with zero broker reconfiguration.
- **Future consumer catch-up**: The A/B testing service, when built, needs to train its model on historical behavior. With Kafka, it starts its consumer group at the beginning of the retention window and replays all events. With RabbitMQ, historical events are gone — the A/B service can only act on future events, severely limiting its usefulness.
- **High throughput**: User activity at any meaningful scale is millions of events/day. Kafka handles this; RabbitMQ would require significant horizontal scaling effort.
- **Decoupling**: Producers emit events without knowing who consumes them. Adding the A/B service requires zero changes to the producers or other consumers.

Topic design: one topic per event type (`user.click`, `user.purchase`, `user.search`) or one broad topic with event-type in the message (filtered by each consumer). The recommendation engine, analytics warehouse, and fraud model each have their own consumer group, consuming at their own pace independently.

**Q23. "Your email service consumes from a Kafka topic. It calls SendGrid to send emails. After a consumer crash and restart, some users report receiving duplicate emails. Explain the root cause and fix."**
A: Root cause: the consumer committed its offset after calling SendGrid but before the commit was acknowledged — or more likely, it processed a batch and the process crashed after sending some emails but before committing the offset for the batch. On restart, it re-reads from the last committed offset and re-sends the already-sent emails.

This is exactly the "at-least-once delivery + non-idempotent side effect" problem from the idempotent consumers topic. The fix does not require switching to RabbitMQ — Kafka is still appropriate here (other services need the same signup events). The fix is application-level idempotency:

Option A — Use SendGrid's native idempotency: Pass a stable `X-Message-Id` header derived from the Kafka message's `topic:partition:offset` (globally unique, stable across retries). SendGrid deduplicates sends with the same message ID within 72 hours. The consumer can re-process safely — SendGrid returns success without re-sending.

Option B — Outbox pattern: The consumer writes the email intent to a Postgres `email_outbox` table (within a transaction that also records the processed offset). A separate worker sends emails and marks them sent. The outbox table's unique key prevents duplicate email intents even if the consumer replays.

The underlying issue is not Kafka vs. RabbitMQ — it is idempotent consumer design. This bug would also occur with RabbitMQ if the consumer nacks after partial processing and the message is requeued.

**Q24. "Your team currently uses RabbitMQ for all messaging. You're adding a GDPR compliance requirement: you must be able to replay all user data events from the past 90 days if the data warehouse has a corruption. Can RabbitMQ meet this requirement?"**
A: No — not without significant architectural additions. RabbitMQ deletes messages on acknowledgment. After 90 days of normal processing, every event that passed through RabbitMQ is gone. There is no native replay from a queue.

Options to meet the requirement without ripping out RabbitMQ:
- **Add a Kafka topic in parallel**: Route all user data events to both a RabbitMQ queue (for existing consumers) and a Kafka topic (with 90-day retention). The Kafka topic serves as the durable archive for replay. New consumers that need replay use Kafka; existing task-queue consumers continue using RabbitMQ. This hybrid approach avoids a full migration.
- **Write-through to S3/object storage**: A RabbitMQ consumer that writes all events to S3 in Parquet or JSON format before processing. The S3 archive is the replay source — replay means re-reading from S3 and re-publishing to the processing queue. This is the "poor man's event log" and works but adds latency and operational complexity.
- **Migrate the user data events to Kafka**: The strongest long-term solution — events that require retention and replay belong in Kafka by design. Existing RabbitMQ-based consumers can be adapted to consume from Kafka (or a bridge service adapts between them).

The compliance requirement is the forcing function to introduce Kafka — even if not all messaging migrates, the events that need a 90-day audit history belong in a log, not a queue.

**Q25. "A startup asks: 'We have 500 background jobs per day — image resizing, report generation, email sends. Should we use Kafka or RabbitMQ?' What do you recommend and why?"**
A: RabbitMQ — or honestly, something even simpler.

500 jobs per day is ~0.006 jobs/second. Kafka is engineering for a problem that doesn't exist at this scale. The operational cost of a Kafka cluster (3 brokers minimum for fault tolerance, KRaft quorum, monitoring, tuning, storage management) is entirely disproportionate. Kafka's design advantages — millions of messages/second throughput, multi-day retention, multi-consumer replay — are irrelevant at 500 jobs/day.

For 500 jobs/day:
- **Best fit**: A managed SQS queue (no infrastructure to operate, pay-per-use, DLQ built in) or a Postgres-backed job table with a library like Sidekiq (Ruby), Celery (Python), pg-boss (Node.js), or River (Go).
- **If self-hosted is required**: A single RabbitMQ node with quorum queues is sufficient, simple to operate, and well-suited to the task queue pattern.
- **Kafka only if**: The startup expects to scale to millions of events/day within months, needs event replay from day one, or has multiple teams consuming the same events independently. Even then, a managed Kafka (Confluent Cloud, Amazon MSK with serverless) removes most of the operational burden.

The rule: start with the simplest tool that meets your current needs and can be migrated from. A Postgres job table is simpler than RabbitMQ; RabbitMQ is simpler than Kafka. Don't pay for Kafka's complexity until you need Kafka's capabilities.

## Quick Reference: Decision Framework

| Criteria                                   | RabbitMQ                              | Kafka                                     |
|---                                         |---                                    |---                                        |
| Primary model                              | Message broker (task queue)           | Distributed log (event stream)            |
| Message lifetime                           | Until acknowledged (ephemeral)        | Configurable retention (default 7 days)   |
| Multiple consumers per message             | Fanout exchange + N queues (complex)  | N consumer groups (trivial)               |
| Replay capability                          | None                                  | Full (reset offset to any point)          |
| Message ordering                           | FIFO within queue; disrupted by parallelism | Strict within partition               |
| Routing                                    | Rich (exchange types, bindings, patterns) | Simple (topics only)                  |
| Consumer model                             | Push (broker delivers to consumer)    | Pull (consumer polls broker)             |
| Throughput ceiling                         | ~100K msg/sec (single node)           | Millions/sec (designed for it)            |
| Latency                                    | Lower for small messages (push-based) | Tunable; higher floor due to polling      |
| Priority queues                            | Native                                | None (multiple topics as workaround)      |
| Per-message TTL                            | Native                                | Not supported (topic-level retention only)|
| Dead letter handling                       | DLX + flexible routing                | Dead letter topic (basic)                 |
| RPC / request-reply                        | Native (reply_to, correlation_id)     | Not native; requires two topics + correlation |
| Operational complexity                     | Moderate (single node viable)         | High (minimum 3-broker cluster)           |
| Right when                                 | Task distribution, routing, ephemeral tasks | Event streaming, audit, replay, fan-out |

## The Core Mental Model

```
RabbitMQ = Post Office
  Message is a parcel: delivered to one recipient, signed for, then gone.
  Rich routing: the post office sorts by address, type, priority.
  The parcel doesn't exist after delivery — no history.
  Right when: "someone must do this job exactly once."

Kafka = Public Library (append-only archive)
  Message is a book: shelved permanently, read by anyone, read again by the same person.
  Simple routing: books are in sections (topics); readers choose their own section.
  The book exists regardless of how many people read it.
  Right when: "many systems need to know this happened, now and in the future."

Decision triggers:
  → "Must be handled by exactly one worker"            → RabbitMQ (task queue)
  → "Must be handled by multiple independent systems"  → Kafka (event streaming)
  → "Need to replay past events"                       → Kafka (only option)
  → "Need complex routing / routing by content"        → RabbitMQ (exchanges)
  → "Need priority / TTL / DLX backoff"                → RabbitMQ (native)
  → "High throughput (>100K/sec)"                      → Kafka (designed for it)
  → "Audit log / compliance retention"                 → Kafka (log model)
  → "Startup with 500 jobs/day"                        → Postgres job table or SQS

Both in one sentence:
  Use RabbitMQ when messages are tasks to be executed.
  Use Kafka when messages are facts to be recorded.
```

---

**Tip for the interview:** RabbitMQ vs Kafka questions almost always resolve to one of three axes: (1) replay — if the interviewer mentions "new service needs historical data" or "reprocess after a bug", Kafka is the answer; (2) multiple consumers — if the same event must reach multiple independent systems, Kafka's consumer group model is the answer; (3) task routing and work distribution — if messages need to go to exactly one worker, possibly with complex routing, RabbitMQ is the answer. The strongest 5 YOE answer avoids picking a "winner" and instead names the decisive criterion: "the choice turns on whether the message is ephemeral work or a durable fact, and whether you need replay." Mentioning that at low volumes both can be overkill compared to SQS or a Postgres job table signals real-world pragmatism over architectural dogma.
