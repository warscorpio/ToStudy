# AWS SNS + SQS Fan-Out Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is AWS SNS and how does it differ from SQS?**
A: Amazon Simple Notification Service (SNS) is a fully managed pub/sub messaging service. It broadcasts a single message to multiple subscribers simultaneously. The core difference from SQS:

- **SQS is a queue:** Point-to-point. One producer writes messages; one consumer group reads and deletes them. Messages persist until consumed or expired. Pull-based — consumers poll the queue.
- **SNS is a topic:** One-to-many broadcast. One publisher sends a message; every subscriber receives a copy simultaneously. Messages are not stored (no retention) — delivery is attempted immediately and if a subscriber is unavailable, the message is gone (unless the subscriber is an SQS queue, which provides durability). Push-based — SNS pushes to subscribers.

SNS supports multiple subscriber types: SQS queues, Lambda functions, HTTP/HTTPS endpoints, email, SMS, and mobile push notifications. A single SNS message can trigger all of them in parallel.

**Q2. What is the fan-out pattern?**
A: The fan-out pattern uses SNS as a message router that distributes a single event to multiple SQS queues, each owned by a different consumer. The result: one producer publishes one message and N independent consumers each receive their own copy to process at their own pace.

```
Producer
    ↓
SNS Topic (OrderPlaced)
    ├──→ SQS Queue A (InventoryService)     ← independent, isolated
    ├──→ SQS Queue B (ShippingService)      ← independent, isolated
    ├──→ SQS Queue C (NotificationService)  ← independent, isolated
    └──→ SQS Queue D (AnalyticsService)     ← independent, isolated
```

Each SQS queue acts as a durable buffer for its subscriber. If the InventoryService is down, its messages accumulate in Queue A and are processed when it recovers — without affecting ShippingService, which drains Queue B independently.

**Q3. Why not just publish directly to multiple SQS queues from the producer?**
A: Publishing directly from the producer to N queues has several problems:

**Coupling:** The producer must know about every consumer. Adding a new consumer (a new analytics pipeline, a new compliance audit service) requires modifying and redeploying the producer.

**Partial failure:** If the producer publishes to Queue A and Queue B, but fails when publishing to Queue C, it must retry — potentially duplicating in A and B. There is no atomicity guarantee across multiple `SendMessage` calls.

**Code complexity:** The producer must manage N separate queue URLs, retry logic per queue, and error handling for each. As N grows, the producer becomes a coordination layer rather than a business logic component.

**With SNS fan-out:** The producer publishes once to the SNS topic. SNS handles delivery to all subscribers. Adding a new consumer is an infrastructure change (add a new SQS subscription to the SNS topic) — zero code change in the producer. SNS retries delivery per subscriber independently — a failure delivering to one queue does not affect delivery to others.

## Section 2: Architecture and Wiring

**Q4. Walk through the complete infrastructure setup for SNS + SQS fan-out.**
A: Three components must be configured: the SNS topic, the SQS queues, and the subscriptions linking them.

**Step 1 — Create the SNS topic:**
```bash
aws sns create-topic --name order-events
# Returns: { "TopicArn": "arn:aws:sns:us-east-1:123456789:order-events" }
```

**Step 2 — Create SQS queues per consumer:**
```bash
aws sqs create-queue --queue-name inventory-service-queue
aws sqs create-queue --queue-name shipping-service-queue
aws sqs create-queue --queue-name notification-service-queue
```

**Step 3 — Grant SNS permission to write to each SQS queue:**
Each SQS queue needs a resource-based policy allowing the SNS topic to call `sqs:SendMessage`:
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "sns.amazonaws.com" },
    "Action": "sqs:SendMessage",
    "Resource": "arn:aws:sqs:us-east-1:123456789:inventory-service-queue",
    "Condition": {
      "ArnEquals": {
        "aws:SourceArn": "arn:aws:sns:us-east-1:123456789:order-events"
      }
    }
  }]
}
```
The `ArnEquals` condition restricts write access to only the specific SNS topic — preventing other SNS topics from writing to the queue accidentally.

**Step 4 — Subscribe each SQS queue to the SNS topic:**
```bash
aws sns subscribe \
  --topic-arn arn:aws:sns:us-east-1:123456789:order-events \
  --protocol sqs \
  --notification-endpoint arn:aws:sqs:us-east-1:123456789:inventory-service-queue

# Repeat for each queue
```

**Step 5 — Producer publishes to SNS (not to SQS directly):**
```python
import boto3, json

sns = boto3.client('sns')

sns.publish(
    TopicArn='arn:aws:sns:us-east-1:123456789:order-events',
    Message=json.dumps({
        'order_id': 'ord-123',
        'customer_id': 'cust-42',
        'total_cents': 5999,
        'items': [{'product_id': 'prod-1', 'quantity': 2}]
    }),
    MessageAttributes={
        'event_type': {
            'DataType': 'String',
            'StringValue': 'OrderPlaced'
        }
    }
)
```
SNS immediately delivers a copy to each subscribed queue.

**Q5. What does an SNS message look like when it arrives in an SQS queue?**
A: SNS wraps the original message in an envelope before delivering it to SQS. Consumers must parse this envelope:

```json
{
  "Type": "Notification",
  "MessageId": "abc-uuid-123",
  "TopicArn": "arn:aws:sns:us-east-1:123456789:order-events",
  "Subject": null,
  "Message": "{\"order_id\":\"ord-123\",\"customer_id\":\"cust-42\",\"total_cents\":5999}",
  "Timestamp": "2026-03-15T10:23:44.000Z",
  "SignatureVersion": "1",
  "Signature": "EXAMPLE...",
  "SigningCertURL": "https://sns.us-east-1.amazonaws.com/...",
  "UnsubscribeURL": "https://sns.us-east-1.amazonaws.com/...",
  "MessageAttributes": {
    "event_type": {
      "Type": "String",
      "Value": "OrderPlaced"
    }
  }
}
```

The original payload is in the `Message` field as a JSON string — consumers must `json.loads()` twice: once to parse the SNS envelope, once to parse the inner message:

```python
import json

def handle_sqs_message(sqs_message):
    # Parse SNS envelope
    sns_envelope = json.loads(sqs_message['Body'])

    # Parse the actual payload
    payload = json.loads(sns_envelope['Message'])

    event_type = sns_envelope['MessageAttributes']['event_type']['Value']
    order_id = payload['order_id']
    ...
```

**Raw message delivery** (`RawMessageDelivery=true` on the subscription) skips the envelope — the SQS message body is the original SNS message body directly. Simpler for consumers, but loses SNS metadata (TopicArn, MessageAttributes in the envelope). Enable when consumers own the schema and don't need SNS metadata.

**Q6. What delivery guarantees does SNS provide to SQS subscribers?**
A: SNS provides at-least-once delivery to SQS subscribers with retry logic:

- SNS attempts delivery to each SQS queue independently.
- If SQS is unavailable or returns an error, SNS retries with exponential backoff for up to 23 days (for SQS subscribers — longer than HTTP endpoints).
- Retry policy: 3 immediate retries, then exponential backoff up to 20 seconds per retry, for a total of 100,015 retries over 23 days.
- Once SQS accepts the message, durability is SQS's responsibility (the message is in the queue until consumed or expired).

**What SNS does NOT guarantee:**
- Exactly-once delivery — SNS may deliver the same message twice to a subscriber in rare circumstances (same at-least-once caveat as SQS direct publishing).
- Ordering — SNS delivers to all subscribers roughly simultaneously but does not guarantee the order in which messages arrive at different queues.
- Delivery if the SQS queue doesn't exist or has an invalid policy — SNS silently drops the message. This is a common misconfiguration pitfall — always validate subscriptions after setup.

## Section 3: Message Filtering

**Q7. What is SNS message filtering and how does it reduce consumer noise?**
A: SNS message filtering allows each SQS subscription to declare a filter policy — only messages whose attributes match the policy are delivered to that subscription. Messages that don't match are silently discarded by SNS before delivery.

Without filtering, every subscriber receives every message from the topic regardless of relevance — a InventoryService subscribed to an `order-events` topic receives both `OrderPlaced` and `OrderCancelled` events, even if it only cares about `OrderPlaced`. The consumer must filter in code.

With filtering, this discrimination happens at the SNS layer:

**Filter policy on the InventoryService subscription:**
```json
{
  "event_type": ["OrderPlaced", "OrderCancelled"]
}
```

**Filter policy on the ShippingService subscription:**
```json
{
  "event_type": ["OrderConfirmed"]
}
```

**Filter policy on the AnalyticsService subscription:**
```json
{}
```
An empty filter policy (or no policy) receives all messages.

**Q8. What filter operators does SNS support?**
A: SNS filter policies support several matching operators on message attributes:

**Exact string match:**
```json
{ "event_type": ["OrderPlaced", "OrderShipped"] }
```
Matches if `event_type` attribute equals "OrderPlaced" OR "OrderShipped".

**Numeric comparison:**
```json
{ "amount_cents": [{ "numeric": [">=", 10000] }] }
```
Matches if `amount_cents` is greater than or equal to 10,000 (i.e., ≥ $100).

**Prefix match:**
```json
{ "customer_tier": [{ "prefix": "premium" }] }
```
Matches if `customer_tier` attribute starts with "premium".

**Exists / anything-but:**
```json
{ "country_code": [{ "exists": true }] }
{ "status": [{ "anything-but": ["cancelled", "refunded"] }] }
```

**Combined (AND logic across attributes, OR within attribute values):**
```json
{
  "event_type": ["OrderPlaced"],
  "customer_tier": ["premium", "enterprise"]
}
```
Matches only if `event_type` is "OrderPlaced" AND `customer_tier` is "premium" OR "enterprise".

**Q9. What is the difference between attribute-based filtering and message body filtering?**
A: SNS supports two filtering modes:

**Attribute-based filtering (default, simpler):**
Filters on `MessageAttributes` — key-value pairs attached to the SNS message alongside the body. The producer must explicitly set these attributes. Fast — SNS evaluates filter policies against attributes without parsing the message body.

```python
sns.publish(
    TopicArn=TOPIC_ARN,
    Message=json.dumps(payload),
    MessageAttributes={
        'event_type': { 'DataType': 'String', 'StringValue': 'OrderPlaced' },
        'customer_tier': { 'DataType': 'String', 'StringValue': 'premium' },
        'amount_cents': { 'DataType': 'Number', 'StringValue': '15000' }
    }
)
```

**Message body filtering (newer, more flexible):**
Filters on fields within the message body JSON itself — no need for separate `MessageAttributes`. The producer doesn't need to modify its publish call:

```json
{
  "$": {
    "event_type": ["OrderPlaced"],
    "customer.tier": ["premium"]
  }
}
```

Body filtering has slightly higher latency (SNS must parse the JSON body) and is only supported for JSON-formatted message bodies. Attribute-based filtering is faster and preferred for high-throughput scenarios.

## Section 4: Fan-Out with FIFO

**Q10. How does the fan-out pattern work with FIFO SNS topics and FIFO SQS queues?**
A: SNS also supports FIFO topics (name must end in `.fifo`) that maintain strict message ordering and exactly-once delivery, pairing with FIFO SQS queues:

**FIFO SNS topic characteristics:**
- Messages published in order are delivered to subscribers in the same order.
- Deduplication via `MessageDeduplicationId` — same semantics as FIFO SQS.
- Subscribers must be FIFO SQS queues (no HTTP endpoints, Lambda, SMS, or email for FIFO topics).
- Throughput ceiling mirrors FIFO SQS: 300 `Publish` calls/sec (3,000 with batching).

**When to use FIFO fan-out:**
- Multiple consumers need the same ordered stream of events.
- Example: An `account-transactions.fifo` SNS topic feeds both an `audit-service.fifo` queue (requires per-account ordering for compliance) and a `balance-calculator.fifo` queue (requires per-account ordering for correct balance computation).

```python
sns.publish(
    TopicArn='arn:aws:sns:us-east-1:123456789:account-transactions.fifo',
    Message=json.dumps(transaction),
    MessageGroupId=f'account:{account_id}',           # per-account ordering
    MessageDeduplicationId=f'txn:{transaction_id}'    # dedup
)
```

**Trade-off:** FIFO SNS + FIFO SQS is significantly more expensive and has lower throughput than Standard. Use only when ordering and exactly-once are genuinely required across multiple consumers.

**Q11. Can you mix Standard and FIFO in an SNS fan-out?**
A: No — a Standard SNS topic can only have Standard SQS queues as subscribers. A FIFO SNS topic can only have FIFO SQS queues as subscribers. You cannot cross-subscribe a Standard SNS topic to a FIFO SQS queue or vice versa. This constraint enforces consistent delivery semantics across the fan-out.

If you need some consumers to receive messages in order (FIFO) and others to receive them unordered (Standard), you must use separate topics — one FIFO and one Standard — and the producer publishes to both.

## Section 5: Dead Letter Queues in Fan-Out

**Q12. Where do DLQs sit in the SNS + SQS fan-out pattern?**
A: Each SQS queue in the fan-out has its own independent DLQ. There is also an option for an SNS-level DLQ for failed deliveries:

**SQS-level DLQ (primary pattern):**
Each SQS queue has its own DLQ configured via `RedrivePolicy`. If a consumer fails to process a message `MaximumReceives` times, the message moves to that queue's DLQ. This is the standard failure isolation pattern — InventoryService failures accumulate in `inventory-dlq`, not affecting ShippingService.

```
SNS Topic
    ├──→ inventory-queue → (on failure) → inventory-dlq
    ├──→ shipping-queue  → (on failure) → shipping-dlq
    └──→ notification-queue → (on failure) → notification-dlq
```

**SNS-level DLQ (less common):**
Configured on the SNS subscription itself (`RedrivePolicy` on the subscription). If SNS cannot deliver a message to the SQS queue after exhausting all retries (e.g., the queue was deleted, the queue policy is wrong, the queue doesn't exist), the message is sent to the SNS-level DLQ instead of being silently dropped.

```python
# Set DLQ on the SNS subscription
sns.set_subscription_attributes(
    SubscriptionArn=subscription_arn,
    AttributeName='RedrivePolicy',
    AttributeValue=json.dumps({
        'deadLetterTargetArn': 'arn:aws:sqs:us-east-1:123456789:sns-delivery-dlq'
    })
)
```

The SNS-level DLQ catches infrastructure failures (misconfigured queue policy, deleted queue) — not consumer processing failures. Consumer processing failures are caught by the SQS-level DLQ.

**Q13. How do you alert on failures in a fan-out system?**
A: Each queue and its DLQ should have independent CloudWatch alarms:

```
Alarm per SQS queue:
  ├── ApproximateAgeOfOldestMessage > 300s → consumer is falling behind
  └── NumberOfMessagesSent (to queue) with no corresponding deletes → processing stalled

Alarm per DLQ:
  └── ApproximateNumberOfMessagesVisible > 0 → processing failures, requires investigation

Alarm on SNS:
  └── NumberOfNotificationsFailed > 0 → SNS couldn't deliver to a subscriber
      (catches queue policy misconfigurations, deleted queues, etc.)
```

The independence of per-queue DLQs is a key operational advantage of the fan-out pattern: ShippingService failures don't pollute InventoryService's DLQ. Each team can alert on and investigate their own failures independently.

## Section 6: Advanced Patterns

**Q14. What is the SNS + SQS + Lambda fan-out pattern and when do you use it?**
A: Lambda can subscribe directly to SNS (without an SQS intermediary) for synchronous, low-latency processing:

```
SNS Topic
    ├──→ SQS Queue → Lambda (asynchronous, buffered)
    ├──→ Lambda Function (synchronous, direct)
    └──→ SQS Queue → Long-running ECS consumer
```

**Direct SNS → Lambda (no SQS buffer):**
- SNS invokes Lambda synchronously.
- Lambda scales instantly (no queue depth to accumulate).
- No retry buffer — if Lambda is throttled or errors, SNS retries per its retry policy, but there's no durable queue absorbing the messages.
- Lambda's own async invocation DLQ or EventSourceMapping handles failures.
- Best for: low-latency reactions, real-time processing, short-lived operations (< 15 minutes).

**SNS → SQS → Lambda (buffered):**
- SQS buffers messages. Lambda polls SQS via an Event Source Mapping.
- Lambda scales based on queue depth (1 Lambda invocation per batch of messages).
- SQS DLQ catches processing failures.
- Better for: bursty traffic (SQS absorbs bursts), long-running processing, operations requiring at-least-once with DLQ.
- The SQS intermediary also allows non-Lambda consumers (ECS, EC2) to process from the same queue.

**Q15. What is the "SNS topic per event type" vs "single topic with filtering" pattern?**
A: Two valid architectures for multi-event-type fan-out:

**Option A — One SNS topic per event type:**
```
order-placed-topic  → [inventory-queue, shipping-queue, notification-queue]
order-cancelled-topic → [inventory-queue, refund-queue, notification-queue]
order-shipped-topic → [notification-queue, analytics-queue]
```
- Simple routing: each topic delivers only one event type — no filtering needed.
- Consumer subscribes only to the topics it cares about.
- Topic proliferation: a system with 50 event types has 50 topics. Operational overhead grows.
- Adding a new consumer for an existing event requires subscribing to the existing topic — zero producer change.

**Option B — Single topic with message attribute filtering:**
```
order-events-topic (all order events)
    ├──→ inventory-queue (filter: event_type IN [OrderPlaced, OrderCancelled])
    ├──→ shipping-queue  (filter: event_type = OrderConfirmed)
    └──→ notification-queue (filter: event_type IN [OrderPlaced, OrderShipped, OrderCancelled])
```
- Fewer topics: one topic per domain, not per event.
- Producer publishes to one place regardless of event type.
- Consumers configure filters rather than multiple subscriptions.
- Adding a new event type requires no infrastructure change — just a new filter on new/existing subscriptions.
- Risk: a consumer with an incorrect filter silently receives too few (or too many) events — harder to detect than a missing subscription.

**Recommendation:** Use filtering (Option B) when one domain produces many event types and consumers are selective. Use per-event topics (Option A) when event types are few, filtering logic is complex, or consumers need absolute clarity about what they subscribe to.

**Q16. How do you implement schema evolution in an SNS + SQS fan-out system?**
A: Schema changes to SNS messages are a breaking change for all subscribers simultaneously — unlike a single queue where only one consumer is affected. Version carefully:

**Non-breaking additions (always safe):**
- Add new optional fields to the message body. Existing consumers ignore unknown fields (if using a tolerant deserializer like JSON with extra field ignoring).
- Add new `MessageAttributes`. Existing filter policies that don't reference the new attribute are unaffected.

**Breaking changes — versioning strategies:**

**Version in message attributes:**
```python
sns.publish(
    TopicArn=TOPIC_ARN,
    Message=json.dumps(new_payload),
    MessageAttributes={
        'event_type': { 'DataType': 'String', 'StringValue': 'OrderPlaced' },
        'schema_version': { 'DataType': 'String', 'StringValue': '2.0' }
    }
)
```
Consumers filter on `schema_version` to handle only the versions they support. Old consumers filter for `schema_version=1.0`; new consumers filter for `schema_version=2.0`. Run both versions simultaneously during migration.

**Parallel topics for major versions:**
```
order-events-v1-topic → legacy consumers
order-events-v2-topic → new consumers
Producer publishes to both during transition
Deprecate v1 after all consumers migrate
```

**Schema registry (Confluent, AWS Glue):**
Register the event schema in a registry. Producer validates before publishing; consumers validate on receipt. The registry enforces compatibility rules (backward-compatible additions only) and rejects invalid schemas. Used when strict schema governance is required across many teams.

## Section 7: Operational Considerations

**Q17. How do you handle message ordering in a Standard SNS + SQS fan-out?**
A: Standard SNS topics and Standard SQS queues provide no ordering guarantees. If consumer logic depends on processing events in sequence (e.g., `OrderPlaced` must be processed before `OrderCancelled`), the consumer must handle out-of-order delivery:

**Include sequence information in the message:**
```json
{
  "order_id": "ord-123",
  "event_type": "OrderCancelled",
  "sequence_number": 3,
  "occurred_at": "2026-03-15T10:25:00Z"
}
```

**Consumer-side sequencing:**
- On receipt, check if the message's `sequence_number` is the next expected for this `order_id`.
- If yes: process.
- If no (out of order): buffer the message temporarily (in Redis, DynamoDB, or in-memory) and wait for the missing predecessors to arrive.
- Set a timeout on buffered messages — if predecessors don't arrive within N seconds, process anyway (or dead-letter for investigation).

This approach adds consumer complexity. If strict ordering is a hard requirement, use FIFO SNS + FIFO SQS fan-out instead of building ordering logic into consumers.

**Q18. What are the cost considerations for SNS + SQS fan-out?**
A: Fan-out multiplies message costs proportionally to the number of subscribers:

**SNS pricing:**
- $0.50 per million SNS `Publish` requests.
- Delivery to SQS is free within the same region (SQS delivery from SNS is not charged as an SNS notification).

**SQS pricing:**
- $0.40 per million requests (Standard) / $0.50 per million (FIFO).
- Each SNS delivery to SQS counts as one SQS `SendMessage` call — billed at SQS rates.
- Consumer `ReceiveMessage` and `DeleteMessage` calls are also billed.

**Multiplication effect:**
1 SNS publish to a topic with 5 SQS subscribers = 1 SNS request + 5 SQS SendMessage requests. At scale, each event published generates N+1 billable API calls (1 SNS + N SQS). For 10M events/day with 5 subscribers: 10M SNS + 50M SQS SendMessage + 50M ReceiveMessage + 50M DeleteMessage = ~160M SQS requests/day ≈ $64/day just in API costs, plus data transfer.

**Cost optimization:**
- Reduce unnecessary subscribers — don't subscribe services that don't actually need the events.
- Use SNS message filtering to avoid delivering irrelevant events to queues.
- Batch SQS operations (receive 10, delete 10) to reduce API call count.
- Consider SNS → Lambda for real-time consumers instead of SNS → SQS → Lambda to eliminate the SQS layer cost where buffering isn't needed.

**Q19. How do you test SNS + SQS fan-out locally without deploying to AWS?**
A: Two main approaches for local development and testing:

**LocalStack:**
An open-source AWS cloud emulator that runs SNS, SQS, and other services locally in Docker. Supports the full SNS + SQS fan-out API:

```bash
# Start LocalStack
docker run -p 4566:4566 localstack/localstack

# Use with endpoint override
aws --endpoint-url=http://localhost:4566 sns create-topic --name order-events
aws --endpoint-url=http://localhost:4566 sqs create-queue --queue-name inventory-queue
```

```python
import boto3

# Point clients at LocalStack
sns = boto3.client('sns', endpoint_url='http://localhost:4566', region_name='us-east-1',
                   aws_access_key_id='test', aws_secret_access_key='test')
sqs = boto3.client('sqs', endpoint_url='http://localhost:4566', region_name='us-east-1',
                   aws_access_key_id='test', aws_secret_access_key='test')
```

**In-process mocking (unit tests):**
Use moto (Python) or aws-sdk-mock (Node.js) to mock AWS SDK calls in-process without network calls:

```python
import boto3
from moto import mock_sns, mock_sqs
import json

@mock_sns
@mock_sqs
def test_fan_out():
    sns = boto3.client('sns', region_name='us-east-1')
    sqs = boto3.client('sqs', region_name='us-east-1')

    # Set up infrastructure
    topic = sns.create_topic(Name='order-events')
    queue = sqs.create_queue(QueueName='inventory-queue')
    queue_attrs = sqs.get_queue_attributes(
        QueueUrl=queue['QueueUrl'], AttributeNames=['QueueArn'])
    queue_arn = queue_attrs['Attributes']['QueueArn']

    # Subscribe queue to topic
    sns.subscribe(TopicArn=topic['TopicArn'], Protocol='sqs',
                  Endpoint=queue_arn)

    # Publish
    sns.publish(TopicArn=topic['TopicArn'],
                Message=json.dumps({'order_id': 'ord-123'}))

    # Verify delivery
    response = sqs.receive_message(QueueUrl=queue['QueueUrl'])
    messages = response.get('Messages', [])
    assert len(messages) == 1
    envelope = json.loads(messages[0]['Body'])
    payload = json.loads(envelope['Message'])
    assert payload['order_id'] == 'ord-123'
```

## Section 8: Scenario / System Design Style Questions

**Q20. "Design the event distribution architecture for an e-commerce platform where an OrderPlaced event must reach inventory, shipping, notifications, analytics, and fraud detection — each with different reliability and latency requirements."**
A: Heterogeneous requirements call for a mixed subscriber model:

**Topology:**
```
Producer (OrderService)
    ↓ sns.publish(OrderPlaced)
SNS Topic: order-events
    │
    ├──→ SQS (inventory-queue, Standard, VT=60s, MaxReceives=5)
    │       → InventoryService (reserve stock, critical, DLQ required)
    │
    ├──→ SQS (shipping-queue, Standard, VT=120s, MaxReceives=3)
    │       → ShippingService (create shipment, critical, DLQ required)
    │
    ├──→ SQS (notification-queue, Standard, VT=30s, MaxReceives=3)
    │       → NotificationService (email/SMS, non-critical, DLQ for retry)
    │
    ├──→ Kinesis Data Firehose (via SNS subscription)
    │       → S3 → Athena (analytics, eventual, no DLQ needed)
    │
    └──→ Lambda (fraud-detection, direct, no SQS buffer)
            → Real-time scoring, synchronous with SNS retry policy
            → Lambda DLQ for failed invocations
```

**Per-subscriber configuration rationale:**
- **Inventory and Shipping:** Standard SQS with DLQ. Critical business operations — message loss is unacceptable. Visibility timeout sized to their P99 processing time.
- **Notifications:** Standard SQS with DLQ and shorter visibility timeout. Less critical — a delayed notification is annoying, not catastrophic. DLQ for retry if email provider is down.
- **Analytics:** Kinesis Firehose (or SQS → Kinesis). Eventual consistency, high-volume, batch-oriented. No DLQ — analytics can tolerate rare data loss or gaps.
- **Fraud detection:** Direct Lambda (no SQS). Must react in near-real-time to block fraudulent orders. Lambda's built-in scaling handles bursts. Lambda DLQ catches failures for investigation.

**Filter policies:** Fraud detection and inventory receive all `OrderPlaced` events. Shipping receives only `OrderConfirmed` (a separate SNS topic or a filter on the same topic for `event_type=OrderConfirmed`).

**Q21. "You've added a new ComplianceAuditService that needs to receive every order event ever published, including ones from before the service existed. How do you design for this with SNS + SQS?"**
A: This is the fundamental limitation of SNS + SQS: SNS has no message retention. A message published before a subscription exists is gone forever — the new subscriber only receives events published after subscription.

**For events published after the ComplianceAuditService is created:**
Add a new SQS subscription (`compliance-audit-queue`) to the existing SNS topic. Going forward, all new events are delivered to this queue.

**For historical events (before the subscription):**
SNS cannot help — you need an alternative source of historical events:

**Option A — Replay from a Kafka topic (if Kafka is already in the stack):**
The SNS topic co-publishes to a Kafka topic with long retention (e.g., 1 year). The ComplianceAuditService replays the Kafka topic from the beginning to catch up, then switches to the SQS queue for new events.

**Option B — Replay from a database audit log:**
If OrderService writes order events to an `orders_audit` table (append-only), the ComplianceAuditService queries this table for historical data, then subscribes to the SNS topic for new events.

**Option C — Replay from S3 (event archive):**
Add an SNS → S3 subscription (via Kinesis Firehose or direct S3 delivery) from day one. S3 becomes the persistent archive. The ComplianceAuditService reads from S3 for history, then from SQS for real-time.

**Lesson:** SNS + SQS is not a replay-capable system. If event replay is a requirement (for audit, new consumer onboarding, or reprocessing), pair the fan-out with a durable event log (Kafka, EventBridge Archive, S3 + Firehose). This is the primary architectural reason to prefer Kafka over pure SNS + SQS for systems where event history matters.

**Q22. "Your SNS + SQS fan-out is working correctly, but AnalyticsService is receiving messages 10–20 minutes late during peak hours. Diagnose and fix."**
A: Consumer lag on the analytics queue — the queue is accumulating faster than the consumer drains it.

**Diagnosis:**
```
CloudWatch metric: ApproximateNumberOfMessagesVisible on analytics-queue
  → High and growing during peak → consumer is under-provisioned

CloudWatch metric: ApproximateAgeOfOldestMessage on analytics-queue
  → 10–20 minutes → matches the observed delay

Consumer logs: processing time per message, concurrency, errors
  → Identify if slow processing, low concurrency, or errors are the bottleneck
```

**Root causes and fixes:**

**Consumer is under-scaled (most common):**
If analytics consumer is Lambda: Lambda scales based on queue depth — check the Lambda concurrent executions metric. If Lambda is hitting the concurrency limit, request a limit increase or add a Reserved Concurrency limit increase.

If analytics consumer is ECS/EC2: the autoscaling policy may not be responding fast enough. Add a scale-out step policy on `ApproximateNumberOfMessagesVisible` → scale when depth exceeds N messages.

**Consumer is processing too slowly:**
Analytics processing (writing to a data warehouse) may be slow per message. Migrate to batch processing — receive 10 messages, write them as a batch to the warehouse in one API call. DynamoDB `BatchWriteItem`, BigQuery streaming insert with batching, Redshift `COPY` command.

**Analytics doesn't need real-time:**
If 10–20 minute lag is acceptable for analytics, simply size the consumer for average throughput, not peak. Add a CloudWatch alarm on `ApproximateAgeOfOldestMessage > 30min` (the threshold beyond which it becomes operationally problematic) rather than targeting zero lag.

**Architectural fix — decouple analytics from the real-time queue:**
Replace the SQS → Consumer pattern with SNS → Kinesis Data Firehose → S3 → Athena (or Redshift Spectrum). Firehose buffers and batches automatically, writes to S3 in 1–15 minute windows, and is designed for analytics workloads. Analytics queries run against S3/Athena rather than a live queue — no consumer lag concern.

**Q23. "A security audit finds that your SQS queue policies allow any SNS topic to write to them, not just your specific topic. How do you fix this without downtime?"**
A: The insecure policy likely looks like:

```json
{
  "Effect": "Allow",
  "Principal": { "Service": "sns.amazonaws.com" },
  "Action": "sqs:SendMessage",
  "Resource": "arn:aws:sqs:us-east-1:123456789:inventory-queue"
  // Missing Condition — any SNS topic in any account can write
}
```

**Fix — add the ArnEquals condition without downtime:**
The policy update is instantaneous and non-disruptive — adding a condition to an existing Allow statement only restricts future writes, it does not affect messages already in the queue or in-flight deliveries.

```json
{
  "Effect": "Allow",
  "Principal": { "Service": "sns.amazonaws.com" },
  "Action": "sqs:SendMessage",
  "Resource": "arn:aws:sqs:us-east-1:123456789:inventory-queue",
  "Condition": {
    "ArnEquals": {
      "aws:SourceArn": "arn:aws:sns:us-east-1:123456789:order-events"
    }
  }
}
```

**Apply via CLI (no downtime):**
```bash
aws sqs set-queue-attributes \
  --queue-url https://sqs.us-east-1.amazonaws.com/123456789/inventory-queue \
  --attributes '{"Policy": "<escaped-json-policy>"}'
```

**Preventive measure going forward:**
- Use Infrastructure as Code (Terraform, CDK, CloudFormation) to define all queue policies — code review catches missing conditions before deployment.
- Run a periodic AWS Config rule or Security Hub check: flag any SQS queue with an SNS write permission that lacks an `aws:SourceArn` condition.
- Use AWS IAM Access Analyzer to detect overly permissive resource policies automatically.

## Quick Reference: SNS + SQS Fan-Out Checklist

| Concern | Configuration / Pattern |
|---|---|
| Basic fan-out | SNS topic + N SQS subscriptions + queue policies with `ArnEquals` condition |
| Message parsing | Parse SNS envelope (`Body` → JSON), then inner `Message` field → JSON |
| Raw delivery | `RawMessageDelivery=true` on subscription — skip envelope, simpler consumers |
| Subscriber filtering | Filter policy on subscription (`MessageAttributes` or message body) |
| Failure isolation | Per-consumer DLQ on each SQS queue (`RedrivePolicy`) |
| SNS delivery failure | SNS-level DLQ on subscription (`RedrivePolicy` on subscription) |
| Ordering | FIFO SNS + FIFO SQS fan-out (throughput ceiling applies) |
| Exactly-once delivery | FIFO SNS + FIFO SQS + `MessageDeduplicationId` + consumer idempotency |
| Real-time consumers | SNS → Lambda (no SQS buffer) + Lambda DLQ |
| Analytics consumers | SNS → Kinesis Firehose → S3 (batch-oriented, no queue lag) |
| Historical replay | Supplement with Kafka, S3 archive, or DB audit log (SNS has no retention) |
| Local testing | LocalStack or moto (Python) / aws-sdk-mock (Node.js) |
| Schema evolution | Version in `MessageAttributes` + parallel topics for major versions |
| Security | `ArnEquals` condition on all queue policies restricting to specific SNS topic ARN |
| Cost | N subscribers = N × SQS costs; use filtering to reduce unnecessary deliveries |
| Monitoring | CloudWatch alarms on DLQ depth, message age, SNS delivery failures |

**Tip for the interview:** SNS + SQS fan-out questions have three reliable escalation points: (1) the SNS envelope — interviewers check whether you know that messages arrive in SQS wrapped in an SNS envelope, requiring double JSON parsing; mention `RawMessageDelivery` as the alternative; (2) the "no retention in SNS" limitation — any question about onboarding a new consumer that needs historical events exposes this gap; the answer is always to pair SNS with a durable log (Kafka, S3 archive, EventBridge Archive); (3) DLQ placement — knowing that there are two independent DLQ layers (SNS-level for delivery failures, SQS-level for processing failures) and that each consumer has its own SQS DLQ demonstrates operational depth. The security question (Q23) about missing `ArnEquals` conditions is a real audit finding that comes up frequently in senior-level interviews — knowing the fix (add the condition, apply without downtime) and the preventive measure (IaC + Config rules) shows production experience.
