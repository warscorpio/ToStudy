# Idempotent Event Consumers — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Idempotency Is Necessary

**Q1. Why do event consumers receive duplicate messages in the first place?**
A: Duplicates are not a bug or an edge case — they are an architectural inevitability in any distributed messaging system operating under at-least-once delivery. Three independent layers produce them:

- **Producer retries**: A producer sends a message and doesn't receive an acknowledgment within its timeout (network hiccup, broker overloaded, brief partition leadership change). It retries — even though the broker may have already written the original message. Both the original and the retry land in the log.
- **Consumer offset lag**: A consumer reads messages, processes them, but crashes or is rebalanced before committing its offset. The new consumer (or the same consumer after restart) picks up from the last committed offset and reprocesses everything since that checkpoint. This is the most common source of duplicates in Kafka-based systems.
- **Infrastructure retries**: HTTP gateways, load balancers, service meshes, and orchestration layers all have retry logic. A downstream service processing an event that triggers an HTTP call may re-invoke that call if it times out — even if the first invocation completed successfully on the remote side.

Exactly-once delivery — the guarantee that eliminates duplicates entirely — requires distributed coordination so expensive that most systems explicitly choose at-least-once and shift the responsibility for handling duplicates to the consumer. Idempotency is how the consumer accepts that responsibility.

**Q2. What goes wrong concretely when a non-idempotent consumer processes the same message twice?**
A: The failure modes depend on the operation:
- **Counters**: Incrementing a `likes_count` by 1 twice charges the user two likes — the count becomes inflated and never converges to truth.
- **Financial operations**: Charging a payment card twice, disbursing a loan twice, or crediting an account twice causes real monetary harm and regulatory exposure.
- **Email/notification sends**: Sending a welcome email or a shipping notification twice damages user trust and marks your domain as spam.
- **Inventory updates**: Decrementing stock by 1 twice results in -1 effective inventory — potentially causing oversell even when stock is available.
- **Audit logs**: Inserting a duplicate audit record creates a false picture of system activity that can fail compliance audits or corrupt forensic investigations.

The unifying pattern: any operation with a real-world side effect, a stateful mutation, or a downstream write that doesn't naturally handle repetition will produce incorrect results when replayed. Idempotency is the engineering contract that says "replay this operation and the world ends up in exactly the same state as if it ran once."

**Q3. What is "at-least-once" vs. "exactly-once" delivery, and why is exactly-once so expensive?**
A: Delivery semantics describe the guarantee a messaging system makes about how many times a message reaches a consumer:
- **At-most-once**: The message is delivered zero or one times. Achieved by committing the offset before processing — if the consumer crashes after committing but before processing, the message is lost. Zero duplicates; potential data loss.
- **At-least-once**: The message is delivered one or more times. Achieved by processing before committing — if the consumer crashes after processing but before committing, the message is reprocessed. No data loss; potential duplicates.
- **Exactly-once**: The message is processed exactly one time, with no loss and no duplicates. Requires atomically linking the message consumption and the downstream side effect in a single transaction — so either both happen or neither does.

Exactly-once is expensive because it requires distributed coordination between the messaging system and every downstream system the consumer writes to. In Kafka, exactly-once for Kafka-to-Kafka pipelines uses transactional producers that atomically commit produced messages and consumer offsets. But for Kafka-to-database or Kafka-to-HTTP, you cannot use Kafka's transaction API — you need application-level idempotency instead. This is why "at-least-once delivery with idempotent consumers" is the dominant pattern in practice.

**Q4. Why is "exactly-once processing" a subtly different problem from "exactly-once delivery"?**
A: Exactly-once delivery is about the message transport layer. Exactly-once processing is about the effect on all downstream systems the consumer touches. Even if the transport layer guarantees exactly-once delivery (as Kafka's transactional API does for Kafka-to-Kafka pipelines), the processing is only truly exactly-once if every side effect — every database write, every HTTP call, every email send — is also executed exactly once. A consumer receiving a Kafka message exactly once but calling a payment API twice has not achieved exactly-once processing. This is the gap that makes exactly-once processing hard: the Kafka message is the trigger, not the effect, and effects are what actually matter.

## Section 2: Idempotency Fundamentals

**Q5. What is idempotency, formally and practically?**
A: Formally, an operation f is idempotent if applying it multiple times produces the same result as applying it once: `f(f(x)) = f(x)`. Practically: processing a message N times leaves the system in exactly the same state as processing it once — no cumulative effects, no side effect multiplication. The consumer doesn't need to know whether it's seeing a message for the first time or the fifth time; the outcome is identical.

Idempotency is a property of the operation plus the state it operates on, not of the message alone. Setting a field to a specific value is idempotent — doing it 100 times leaves the field at that value. Incrementing a counter is not idempotent — doing it 100 times increments by 100. A consumer designed for idempotency either chooses naturally idempotent operations or adds engineering to make non-idempotent operations safe.

**Q6. What is the difference between idempotency and immutability?**
A: Immutability means a value never changes after creation. Idempotency means an operation can be applied repeatedly without changing the result beyond the first application. They are related but distinct:
- Immutable data structures trivially produce idempotent reads — reading the same immutable value 100 times returns the same value 100 times.
- An operation on mutable data can be idempotent even though the data is mutable: `SET user.email = 'alice@example.com'` is idempotent on a mutable user record — running it 10 times leaves `email = 'alice@example.com'`, same as running it once.
- An operation on immutable data can be non-idempotent if it creates new records: `INSERT INTO audit_log (event_id, ...)` is not idempotent (without a dedup key) even though audit records themselves are immutable — each call creates a new row.

**Q7. What is a "natural" vs. an "engineered" idempotent operation?**
A: Some operations are idempotent by nature; others require explicit design:

**Naturally idempotent**: Setting a field to a fixed value (`UPDATE user SET status = 'verified'`), DELETE (if you treat 404 as success), `PUT` with a full resource representation (HTTP semantics), marking an order as shipped if it's already shipped (same final state).

**Non-idempotent by nature, requiring engineering**: Incrementing/decrementing a counter, INSERT without conflict handling, charging a payment, sending an email or notification, appending to a log, publishing another event downstream.

The engineering approaches for non-natural idempotency: deduplication keys with a seen-message store, database unique constraints, conditional writes (`UPDATE ... WHERE version = $1`), or idempotency tokens passed to downstream APIs. In most real systems, the majority of operations require engineered idempotency — natural idempotency is insufficient to cover the full range of consumer behavior.

## Section 3: Sources of Duplicate Messages in Kafka

**Q8. Walk through the exact sequence that produces a duplicate in a Kafka consumer.**
A: The canonical sequence:

```
T=0:  Consumer reads messages at offsets 100–199 from partition 3
T=1:  Consumer processes all 100 messages (writes to database, sends events)
T=2:  Consumer is about to call commitSync(offset=200)
T=3:  Broker triggers a rebalance (another consumer joins the group)
T=4:  Consumer's session is interrupted — it does not commit offset 200
T=5:  Rebalance completes; partition 3 is assigned to Consumer B
T=6:  Consumer B starts at last committed offset: 100
T=7:  Consumer B processes offsets 100–199 again — duplicate processing
```

All 100 messages in 100–199 were already processed (T=1) — their effects are in the database. Consumer B now processes them again (T=7). If those effects are idempotent, the second round is a no-op. If they are not — two emails sent, two payments charged, two inventory decrements applied.

**Q9. How do Kafka's idempotent producer and transactional API prevent producer-side duplicates?**
A: The Kafka idempotent producer (`enable.idempotence=true`) assigns each producer a unique `producer_id` and attaches a monotonically increasing sequence number to every message. The broker deduplicates: if it receives a message with a `(producer_id, sequence_number)` pair it has already seen and stored, it discards the duplicate without writing it to the log. This prevents exactly the retry-induced duplicate where the producer timed out, retried, and both the original and retry reached the broker.

The Kafka transactional API extends this: with a `transactional.id`, the producer can atomically produce messages to multiple partitions and commit consumer offsets in a single transaction. If the producer crashes mid-transaction, the uncommitted messages are aborted; downstream consumers with `isolation.level=read_committed` never see them. This gives exactly-once semantics within the Kafka ecosystem (consume from Kafka, produce to Kafka) — but does nothing for external side effects like database writes or HTTP calls, which require application-level idempotency.

## Section 4: Deduplication Strategies

**Q10. What is an idempotency key and what properties must it have?**
A: An idempotency key is a stable, unique identifier for a specific operation — the key used to detect that a message or request has already been processed. Properties:
- **Stable**: The same logical operation always produces the same key, regardless of how many times it is retried. A key derived from random data (UUID at processing time) is useless for deduplication — it changes on every attempt.
- **Unique per logical operation**: Two distinct operations must never share a key, even if they operate on the same entity. Order payment and order refund on the same order must have different keys.
- **Scoped to a deduplication window**: The key only needs to be unique within the window during which retries can occur — not for all eternity.

Common sources of good idempotency keys for Kafka consumers: `topic + partition + offset` (globally unique within a Kafka cluster, stable across retries, tied precisely to the message), `message.headers["event_id"]` if the producer stamps a UUID at creation time, or a business-level key like `order_id + event_type` if the event represents one logical state transition.

**Q11. What is the "check-then-act" race condition in deduplication, and how is it avoided?**
A: The naive deduplication pattern:
```
1. Check: SELECT COUNT(*) FROM processed_messages WHERE message_id = $1
2. If count = 0: process the message, then INSERT INTO processed_messages (message_id)
```
Between steps 1 and 2, a second consumer (on another thread or pod) can pass the same check — both see count=0, both process the message, both insert the record. You've processed the message twice despite the dedup check.

This is a TOCTOU (Time Of Check To Time Of Use) race. Fix:
- **Unique constraint + conflict handling**: `INSERT INTO processed_messages (message_id) ON CONFLICT DO NOTHING` — the database enforces uniqueness atomically. If the insert succeeds, proceed. If it fails (conflict), skip. The constraint is the guard, not the application check.
- **Atomic compare-and-set in Redis**: `SET message_id 1 NX EX 86400` — Redis's `NX` flag makes this atomic: only succeeds if the key doesn't exist. No race between check and set.
- **Database transaction**: Wrap the dedup key insert and the business operation in one database transaction. If another concurrent transaction already inserted the same key, yours will block on the unique constraint and fail — rolling back both operations atomically.

**Q12. What data stores are suitable for keeping the seen-message log, and what are the trade-offs?**
A:
- **Relational database (Postgres, MySQL)**: Strong consistency, ACID transactions — the atomic insert + business operation in one transaction is the cleanest pattern. Downside: adds a write per message to the dedup table; high-throughput systems may hit write contention on the dedup table.
- **Redis (with `SET NX EX`)**: Very high throughput dedup checks; TTL handles expiry automatically; sub-millisecond atomic set. Downside: Redis is not durable by default — a Redis crash or restart can clear the dedup store, allowing reprocessing. Use Redis with `appendonly yes` and reasonable TTL for the retry window. Not suitable when the dedup window must survive broker restarts.
- **The business table itself (preferred)**: Use the business table's unique constraint as the dedup mechanism — no separate dedup store needed. `INSERT INTO payments (payment_id, ...) ON CONFLICT (payment_id) DO NOTHING` deduplicates using the natural primary key of the domain entity. This is the most robust pattern: the dedup state is co-located with the business state, lives as long as the business data, and requires no additional infrastructure.
- **Bloom filter**: Probabilistic, space-efficient — can say "definitely not seen" or "probably seen." False positives (treating an unseen message as a duplicate) are possible; false negatives (missing a duplicate) are impossible. Use only where occasional false positive rejection is acceptable, memory is constrained, and throughput is very high (hundreds of thousands per second).

**Q13. What is the deduplication window and how do you size it?**
A: The deduplication window is how long you retain the record of a processed message in the dedup store. It must be at least as long as the maximum possible delay between a message being produced and its last retry reaching your consumer. For Kafka consumers, retries are typically driven by rebalance/crash recovery — the window between an uncommitted offset and the next successful commit is bounded by the consumer's processing time and retry configuration. A window of a few hours is usually sufficient for Kafka consumer deduplication.

Sizing trade-offs: a short window (minutes) minimizes storage but may miss retries that arrive late due to a prolonged outage or a very delayed consumer restart. A long window (weeks) is safe but consumes significant storage and requires indexing for efficient lookup. The right answer: match the window to the maximum realistic retry delay of your producer, not an arbitrary large value. For payment processors (which may retry for 3–7 days), store dedup keys for 8+ days. For internal event pipelines (which retry within seconds to minutes), store for 24 hours.

## Section 5: Database-Level Idempotency

**Q14. How do database unique constraints provide idempotency guarantees?**
A: A unique constraint on the idempotency key column makes the database itself the dedup enforcement mechanism. The first successful insert writes the record; any subsequent insert with the same key fails with a constraint violation. The application catches the violation and treats it as "already processed" — a no-op rather than an error.

```sql
-- Table design
CREATE TABLE order_events (
    event_id    UUID PRIMARY KEY,    -- the idempotency key
    order_id    UUID NOT NULL,
    event_type  TEXT NOT NULL,
    processed_at TIMESTAMPTZ DEFAULT now()
);

-- Consumer logic
INSERT INTO order_events (event_id, order_id, event_type)
VALUES ($1, $2, $3)
ON CONFLICT (event_id) DO NOTHING;

-- Zero rows affected = already processed; skip downstream effects
-- 1 row affected = first processing; proceed
```

The unique constraint is transactional — two concurrent transactions trying to insert the same `event_id` will serialize: one succeeds, one gets a conflict. No race condition. No separate dedup table. The dedup state is the business table itself.

**Q15. What is conditional update idempotency (optimistic locking) and when is it appropriate?**
A: Instead of deduplicating by message ID, conditional updates use the current state of the entity as the guard — only applying the operation if the entity is in the expected prior state:

```sql
-- Only mark shipped if currently in 'confirmed' state (not if already 'shipped')
UPDATE orders
SET status = 'shipped', shipped_at = now()
WHERE order_id = $1 AND status = 'confirmed';

-- 0 rows affected = order was already shipped (or in wrong state) → idempotent no-op
-- 1 row affected = successfully transitioned → proceed with side effects
```

This pattern is appropriate when:
- The event represents a state transition (not an accumulation)
- The desired end state is fixed and known (shipping an order → `status = 'shipped'`)
- The prior state is a meaningful guard (only ship a confirmed order)

It is NOT appropriate for: operations with no meaningful prior-state guard (inserting a new record, publishing an event), operations where the transition is valid from multiple prior states, or operations where the consumer needs to know whether it was a first-time or duplicate processing.

**Q16. How do you make database counter increments idempotent?**
A: Counter increments are among the hardest operations to make idempotent because `COUNT + 1` twice gives `COUNT + 2`. Two approaches:

**Track applied events explicitly**: Keep a log of which increment events have been applied:
```sql
-- Attempt to record the event (will fail if already recorded)
INSERT INTO inventory_events (event_id, item_id, delta)
VALUES ($1, $2, -1)
ON CONFLICT (event_id) DO NOTHING;

-- Only if insert succeeded (first time), apply the delta
UPDATE inventory SET quantity = quantity - 1 WHERE item_id = $2;
```
Both operations in one transaction. The unique constraint on `event_id` prevents the increment from being applied twice.

**Idempotent set from event state**: If the event carries the target state (not a delta), use a conditional set:
```sql
-- Event says "quantity should be 47 after this adjustment"
UPDATE inventory
SET quantity = 47
WHERE item_id = $1 AND event_sequence < $2;
```
The `event_sequence` acts as an optimistic lock — older events can't overwrite newer state. This requires the producer to encode target state, not deltas, which is a more demanding event schema design but enables simpler consumer logic.

## Section 6: Idempotent Side Effects

**Q17. Why are side effects (emails, payments, HTTP calls) the hardest part of idempotent consumer design?**
A: Database writes are contained within a transaction — the unique constraint or conditional update is atomic and locally enforceable. Side effects are calls to external systems that have their own state, their own failure modes, and often no native idempotency support:
- **Email send**: Calling `sendEmail()` twice sends two emails. The email provider has no way to know the second call is a retry.
- **Payment charge**: Charging a card twice bills the customer twice. The payment processor doesn't know the first call succeeded.
- **HTTP webhook**: Posting an event to a partner API twice may create duplicate records in their system.

The fundamental problem: you cannot atomically commit a database transaction AND call an external API. One of them will happen first, and if the system crashes after the first but before the second, you'll either miss the side effect or redo it on retry.

**Q18. What is the Outbox Pattern and how does it make side effects reliably at-least-once?**
A: The Outbox Pattern decouples the business operation from its side effects by making the side effect a record in the database — a record that is then reliably delivered by a separate process:

```
Step 1 (consumer processes event):
  BEGIN TRANSACTION
    UPDATE orders SET status = 'shipped' WHERE order_id = $1
    INSERT INTO outbox (id, event_type, payload, created_at)
    VALUES (gen_random_uuid(), 'order.shipped', $payload, now())
  COMMIT

Step 2 (separate outbox worker, continuously running):
  SELECT * FROM outbox WHERE processed = false ORDER BY created_at LIMIT 100
  FOR EACH row:
    call sendShippingEmail(row.payload)   ← external side effect
    UPDATE outbox SET processed = true WHERE id = row.id
```

The business operation and the outbox record are in one transaction — both happen or neither does. The outbox worker delivers the side effect at-least-once (retries on failure). If the email send fails, the outbox record remains unprocessed and the worker retries. If the worker crashes after sending but before marking processed, it will retry the send — the email provider must accept idempotent sends (or a dedup key is included in the payload).

The outbox pattern gives you: database-atomic coupling of state change and side effect intent, reliable at-least-once delivery of side effects, and the ability to add new side effects without changing consumer code.

**Q19. How do you make the Outbox Pattern's outbox worker idempotent toward external systems?**
A: The outbox worker delivers side effects at-least-once — it will retry failed sends. The external system must therefore be able to handle duplicate calls:
- **Email providers (SendGrid, SES)**: Pass a unique message ID or idempotency key with each send. Most providers deduplicate sends with the same key within a window (24 hours for SES). Include `outbox_id` or a stable business ID as the dedup key.
- **Payment processors (Stripe)**: Use Stripe's `Idempotency-Key` header. Pass the same key on retries — Stripe returns the original response without re-executing the charge. The key should be derived from the business operation (e.g., `order_id + 'payment'`), not from the outbox record ID (which may differ on retry).
- **Webhooks to partner APIs**: Include an `event_id` field in the payload; document that partners must deduplicate on `event_id`. Your outbox record's stable ID is the event ID.
- **Internal services**: Design downstream service endpoints to be idempotent — `PUT /orders/{id}/ship` rather than `POST /orders/{id}/ship`. The PUT semantics convey "set this state" rather than "trigger this action," making repeated calls safe.

**Q20. How does Stripe's idempotency key pattern work, and what can you borrow from it for internal APIs?**
A: Stripe requires clients to pass an `Idempotency-Key: <uuid>` header on mutating API calls. On the server side, Stripe:
1. On first receipt: stores `(idempotency_key, request_fingerprint, response)` and processes the request.
2. On retry with same key + same request body: returns the cached response without reprocessing.
3. On retry with same key + different request body: rejects with 422 — the key was already used for a different request.
4. TTL: 24 hours — after expiry, the key is gone and a new request with the same key is treated as fresh.

Borrowing for internal APIs:
- Require clients to generate and pass a stable idempotency key (request UUID, workflow step ID) for all non-idempotent endpoints.
- Store `(key, response)` in a short-lived cache (Redis with TTL, or a database table with `expires_at`).
- Return cached response on duplicate — the client gets the same result without re-execution.
- This works even for non-deterministic operations: charging a card is not idempotent, but with an idempotency key, retrying the charge API returns the original charge result, not a new charge.

## Section 7: Advanced Patterns

**Q21. How does event sourcing naturally enable idempotent consumers?**
A: In an event-sourced system, the state of an entity is derived by replaying an ordered sequence of events. Each event is assigned a monotonically increasing sequence number (or version). A consumer applies an event only if the entity's current version equals the event's expected prior version:

```
Apply event E (version=5) to entity (current version=4):
  → current + 1 = 5 = E.version → apply, advance to version 5

Apply event E (version=5) to entity (current version=5):  ← duplicate
  → current = 5 = E.version → already applied, skip (idempotent no-op)

Apply event E (version=5) to entity (current version=6):  ← stale
  → 6 > 5 → reject (this event is older than current state)
```

The version number is both an ordering mechanism and a deduplication guard. Duplicate events are detected by the version mismatch (expected version already applied). This works without a separate dedup store — the entity's own version is the guard. The pattern is naturally idempotent for ordered, non-concurrent event streams and is why event sourcing is well-suited to Kafka-driven architectures.

**Q22. How do saga compensating transactions interact with idempotency?**
A: A saga is a distributed transaction implemented as a sequence of local transactions, each with a compensating transaction to undo it if a later step fails. Both the forward steps and the compensating steps must be idempotent:

**Forward step idempotency**: If step 2 of a saga (reserve inventory) is retried after a partial failure, it must produce the same reservation without double-reserving. Use the `saga_id + step_id` as the idempotency key.

**Compensating step idempotency**: If the compensation for step 1 (cancel payment) is retried, it must produce the same cancellation without double-refunding. The payment refund API should accept the same idempotency key and return the original refund result.

**The "already compensated" guard**: If a forward step is retried after the saga has already been compensated, the consumer must detect this. Pattern: store saga state (`pending`, `compensating`, `completed`, `cancelled`) in a durable store. Check saga state before applying any step — reject forward steps when saga is `compensating` or `cancelled`.

Sagas without idempotency guarantees on both forward and backward steps are dangerous: a crash during compensation that triggers a compensation retry can produce double refunds, double cancellations, or partial re-application of forward steps that were already compensated.

**Q23. When is exactly-once processing achievable end-to-end, and when is it not?**
A: Exactly-once processing is achievable within closed, transactional systems:
- **Kafka-to-Kafka with transactions**: `consume message + produce result + commit offset` in one Kafka transaction. Used by Kafka Streams. Exactly-once within the Kafka log; the rest of the world doesn't see intermediate state.
- **Kafka-to-database with transactional outbox**: `process message + write business state + write outbox record` in one DB transaction. The downstream side effect (outbox delivery) is at-least-once, but the business state change is exactly-once.
- **Exactly-once to the database via unique constraint**: `INSERT ... ON CONFLICT DO NOTHING` — the database enforces exactly-once application of the state change.

Exactly-once processing is NOT achievable when:
- An external HTTP API lacks idempotency key support — you cannot atomically link a database commit to an HTTP call's result.
- A side effect is inherently non-repeatable — sending a physical letter, making a phone call, triggering a physical process.
- Two external systems must both be updated atomically — without a distributed transaction protocol (2PC) between them, you can guarantee at most one succeeds atomically.

In practice: design for exactly-once database writes using constraints, at-least-once external effects using outbox + idempotency keys, and accept that perfect exactly-once for all effects is unreachable in most real systems.

## Section 8: Scenario / System Design Questions

**Q24. "You're building a Kafka consumer that processes payment events and writes to a PostgreSQL `payments` table. Design it to be idempotent."**
A: The payment event contains a `payment_id` (UUID, producer-generated and stable across retries). Design:

```sql
-- Table with natural idempotency key
CREATE TABLE payments (
    payment_id      UUID PRIMARY KEY,       -- idempotency key = PK
    order_id        UUID NOT NULL,
    amount_cents    INT NOT NULL,
    status          TEXT NOT NULL,
    processed_at    TIMESTAMPTZ DEFAULT now(),
    kafka_offset    BIGINT,                 -- optional: for tracing/debugging
    kafka_partition INT
);
```

```python
# Consumer logic (pseudocode)
for message in consumer.poll():
    event = parse(message.value)
    try:
        db.execute("""
            INSERT INTO payments (payment_id, order_id, amount_cents, status,
                                  kafka_offset, kafka_partition)
            VALUES (%s, %s, %s, %s, %s, %s)
            ON CONFLICT (payment_id) DO NOTHING
        """, [event.payment_id, event.order_id, event.amount_cents,
              event.status, message.offset, message.partition])

        if db.rowcount == 1:      # first processing
            trigger_downstream_effects(event)   # outbox or idempotent API call

        # rowcount == 0 → duplicate, silently skip
        consumer.commit()

    except Exception as e:
        log_and_retry(e)
        # Do NOT commit; message will be redelivered
```

The `ON CONFLICT DO NOTHING` on `payment_id` is the idempotency guard. No separate dedup table. No application-level check-then-act race. The `db.rowcount` distinguishes first processing from duplicate, allowing downstream effects to be triggered exactly on first write without re-triggering on replay.

**Q25. "A consumer sends a confirmation email on order creation. After a deploy, customers report receiving 2–3 confirmation emails. What caused this and how do you fix it?"**
A: Root cause: the consumer calls the email API directly in the processing loop without idempotency protection. During the rolling deploy, consumer rebalancing caused messages to be reprocessed from the last committed offset — the same order creation event was processed by multiple consumer instances, each calling the email API independently.

Fix with the outbox pattern:
```
1. Consumer processes order_created event:
   BEGIN TRANSACTION
     INSERT INTO orders (order_id, ...) ON CONFLICT DO NOTHING  ← idempotent
     INSERT INTO outbox (id, type, payload, sent=false)
     VALUES (order_id || ':confirmation', 'email', {...}, false)
     ON CONFLICT (id) DO NOTHING                                 ← idempotent
   COMMIT

2. Outbox worker (separate process):
   SELECT * FROM outbox WHERE sent = false
   FOR EACH:
     send email with Idempotency-Key: outbox.id               ← SES/SendGrid dedup
     UPDATE outbox SET sent = true WHERE id = outbox.id
```

The outbox dedup key (`order_id || ':confirmation'`) prevents the same email intent from being inserted twice. The email provider's idempotency key prevents the email from being sent twice even if the outbox worker retries. The transaction links the order creation and the email intent atomically. Three layers of protection against the double-email bug.

**Q26. "A payment consumer idempotently inserts into a `charges` table using `charge_id` as the PK. A bug causes some messages to arrive without a `charge_id`. How do you defend against this without breaking idempotency?"**
A: Missing or null idempotency keys are a silent danger — without a stable key, every processing attempt looks like a new charge. Defense:

**First, reject at intake — never process a message without a key:**
```python
if not event.charge_id:
    # Dead-letter queue — do not process, do not skip silently
    dlq.send(message, reason="missing_charge_id")
    consumer.commit()  # commit to advance past the bad message
    continue
```

**If the business key isn't present on the event, derive one from Kafka metadata:**
```python
# Kafka offset is globally unique and stable for this message
derived_key = f"{message.topic}:{message.partition}:{message.offset}"
```
This is always available, always stable, and globally unique within a Kafka cluster. It's not a business key, but it's a reliable dedup key for Kafka-driven consumers.

**Fix the producer bug** to always include `charge_id`, emit to a monitoring alert when `charge_id` is absent, and replay dead-lettered messages after the fix is deployed. Never silently swallow events without a key — silent drops are worse than loud failures for financial events.

**Q27. "Your team is debating whether to use Redis or PostgreSQL for the deduplication store in a high-throughput consumer (100K messages/sec). What factors govern the decision?"**
A: At 100K messages/sec, both stores are under significant pressure. The decision turns on four factors:

**Durability requirement**: If a message being processed twice would cause real harm (financial, compliance), the dedup store must be durable. Redis with AOF persistence and `fsync=always` is more durable than the default but still has a small window of data loss on crash. Postgres with synchronous commits is fully durable. For payments: Postgres. For analytics events: Redis is fine.

**Latency budget**: A Redis `SET NX EX` is ~0.5ms; a Postgres INSERT with a unique constraint is ~2–5ms (single-node, local). At 100K msg/sec, Postgres at 5ms/op = 500K ops/sec needed on one connection pool — this requires careful connection pooling (PgBouncer) and potentially partitioning the dedup table. Redis handles 100K/sec trivially on a single instance.

**Using the business table as the dedup store**: The best solution at high throughput is often neither a separate Redis nor a separate Postgres dedup table — it's using the business table's unique constraint directly. At 100K payment inserts/sec, Postgres partitioning by time or hash can scale that write load. The dedup and the write collapse into one operation.

**Deduplication window and memory**: Redis keys with TTL are naturally garbage-collected. Postgres dedup tables require a background cleanup job. At 100K msg/sec with a 24-hour window, you're storing ~8.6B records — Redis keyed by UUID (16 bytes + overhead) approaches tens of GB; Postgres needs similar storage but on durable disk. The volume alone may force either a short window or Bloom filters with acceptable false-positive rate.

**Q28. "Design an idempotent consumer for a saga step: 'reserve inventory for order {order_id}'. The step may be called multiple times if the saga coordinator retries."**
A:

```sql
CREATE TABLE inventory_reservations (
    reservation_id  TEXT PRIMARY KEY,        -- saga_id + step = stable key
    order_id        UUID NOT NULL,
    item_id         UUID NOT NULL,
    quantity        INT NOT NULL,
    status          TEXT NOT NULL,           -- 'reserved', 'released', 'fulfilled'
    created_at      TIMESTAMPTZ DEFAULT now()
);

CREATE UNIQUE INDEX ON inventory_reservations (order_id, item_id)
  WHERE status = 'reserved';               -- one active reservation per item per order
```

```python
# Consumer for 'reserve_inventory' saga command
def handle_reserve_inventory(event):
    reservation_id = f"{event.saga_id}:reserve_inventory"

    with db.transaction():
        result = db.execute("""
            INSERT INTO inventory_reservations
                (reservation_id, order_id, item_id, quantity, status)
            VALUES (%s, %s, %s, %s, 'reserved')
            ON CONFLICT (reservation_id) DO NOTHING
            RETURNING *
        """, [reservation_id, event.order_id, event.item_id, event.quantity])

        if db.rowcount == 0:
            # Already reserved — idempotent no-op; re-emit success reply
            emit_saga_reply(event.saga_id, 'inventory_reserved', idempotent=True)
            return

        # Check if stock is available (business logic, only on first attempt)
        stock = db.query("SELECT quantity FROM inventory WHERE item_id = %s FOR UPDATE",
                         [event.item_id])
        if stock.quantity < event.quantity:
            db.rollback()
            emit_saga_reply(event.saga_id, 'inventory_insufficient')
            return

        db.execute("UPDATE inventory SET quantity = quantity - %s WHERE item_id = %s",
                   [event.quantity, event.item_id])
        emit_saga_reply(event.saga_id, 'inventory_reserved')
```

Key design choices: `reservation_id = saga_id + step_name` is the stable idempotency key — same saga retry always produces the same key. The `ON CONFLICT DO NOTHING` prevents double-reservation. On duplicate, the saga reply is re-emitted (the saga coordinator needs the reply even on retry). The inventory decrement is inside the same transaction as the reservation insert — atomically linked.

## Quick Reference

| Pattern                       | When to use                                          | Mechanism                                      | Limitation                                              |
|---                            |---                                                   |---                                             |---                                                      |
| Unique constraint             | Database writes with a natural or derived key        | `INSERT ... ON CONFLICT DO NOTHING`            | Requires a stable unique key per logical operation      |
| Conditional update            | State transitions with a known prior state           | `UPDATE ... WHERE status = 'prior_state'`      | Doesn't work for accumulations or multi-valid priors    |
| Redis SET NX                  | High-throughput, short-window dedup                  | Atomic set-if-not-exists with TTL              | Not durable by default; false security without AOF      |
| Outbox pattern                | Side effects (email, HTTP) that must be reliable     | Atomic DB write + separate delivery worker     | At-least-once delivery; external system must accept dedup key |
| Idempotency key (API)         | HTTP APIs called as side effects                     | Stable client key + server response cache      | Requires external API support; TTL limits window        |
| Version/sequence guard        | Event sourcing, ordered state transitions            | Apply only if entity version = event.prior_ver | Requires ordered events; breaks on concurrent writes    |
| Kafka message ID as key       | All Kafka consumers                                  | `topic:partition:offset` as dedup key          | Only stable within one Kafka cluster                    |

## The Core Mental Model

```
Idempotency contract: f(f(x)) = f(x)
  "Process this message twice → same result as processing it once"

Why you need it:
  At-least-once delivery is the default.
  Exactly-once delivery is only achievable within a closed transactional system.
  External side effects cannot be transactional. You must design them idempotent.

The three layers of idempotency:
  1. Message deduplication: detect and skip already-seen messages
         → Unique constraint, Redis SET NX, Kafka offset tracking
  2. Operation idempotency: design the operation to be safe to repeat
         → Conditional UPDATE, upsert, SET (not INCREMENT)
  3. Side effect idempotency: make external calls repeatable
         → Outbox pattern, provider idempotency keys, PUT over POST

Common traps:
  ✗ Check-then-act (TOCTOU race) → use atomic constraint, not application-level check
  ✗ min.insync.replicas=1 with acks=all → false durability → data loss on leader fail
  ✗ No idempotency key = no dedup possible → derive from Kafka offset if no business key
  ✗ Separate dedup table + separate business write → two-phase, not atomic → race window
  ✗ Redis dedup without persistence → clears on restart → dedup window silently wiped

The gold standard:
  Unique constraint on the business table (not a separate dedup table)
  + Outbox pattern for side effects
  + Provider idempotency keys on all external API calls
  = No separate dedup infrastructure, no race conditions, no double side effects
```

**Tip for the interview:** Idempotency questions at 5 YOE almost always escalate from "what is idempotency" to "walk me through how you'd make this specific consumer idempotent." The concrete path interviewers want to see: identify the idempotency key → use a unique DB constraint (not a separate check → insert pattern) → handle side effects via outbox → give the downstream system an idempotency key. The critical insight that separates senior answers: the check-then-act TOCTOU race and why the unique constraint (not an application-level check) is the correct fix. The most senior signal: "the business table's own primary key is the best dedup store — no extra infrastructure, no TTL to tune, atomically consistent with the data it protects."
