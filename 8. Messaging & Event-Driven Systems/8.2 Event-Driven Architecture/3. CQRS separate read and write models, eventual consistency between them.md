# CQRS: Separate Read and Write Models, Eventual Consistency — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why CQRS Exists

**Q1. What scaling and design problems does CQRS solve that a single unified model cannot?**
A: A traditional CRUD service exposes the same data model for both writes and reads. This works at low scale but creates friction on three axes:

- **Read/write asymmetry in access patterns**: Most systems have dramatically more reads than writes (10:1 to 100:1 is common). A single model must be optimized for both simultaneously — indexes that accelerate reads slow down writes; normalized schemas that make writes consistent make reads join-heavy. Trying to serve both from the same model means serving neither well.
- **Complexity bleed between concerns**: Write operations enforce business rules, validate state transitions, and maintain invariants. Read operations assemble view projections — often joining across many entities, computing aggregates, and shaping data for specific UI contracts. Cramming both responsibilities into one model produces a model that is simultaneously too rigid for reads (because it enforces write-time constraints) and too loose for writes (because it accommodates the flexibility reads need).
- **Independent scaling is impossible**: If reads are the bottleneck, you cannot scale just the read path — you must scale the entire monolith. If writes need strong consistency, you cannot relax consistency guarantees for reads without contaminating the write path. A unified model couples the scaling and consistency dimensions that are fundamentally different between reads and writes.

CQRS separates these concerns at the model level: the **command model** (write side) owns the business rules and authoritative state; the **query model** (read side) owns the projections and view data, shaped for the specific query at hand. Each can be optimized, scaled, and evolved independently.

**Q2. What does CQRS stand for and what is its foundational principle?**
A: CQRS stands for **Command Query Responsibility Segregation**. The foundational principle is Bertrand Meyer's **Command-Query Separation (CQS)** — a method should either change state (a command) or return state (a query), but never both. A method that both mutates and returns creates hidden side effects, makes reasoning harder, and entangles concerns that should be independent.

CQRS applies CQS at the architectural level rather than the method level:
- **Commands**: Intent to change state — `CreatePayment`, `ApproveTransfer`, `CancelOrder`. A command is rejected or accepted; it does not return query results. Its output is a success/failure signal (or an event indicating what happened).
- **Queries**: Requests for current state — `GetPaymentStatus`, `ListTransactionsByUser`. A query returns data and changes nothing. It can be served from a read model that is optimized purely for retrieval.

The separation is not just organizational — it has structural implications. The write side and read side can use different persistence technologies, different schemas, and different consistency models. A command writes to PostgreSQL with strict ACID guarantees; a query reads from Elasticsearch with an eventually consistent materialized view. These are first-class architectural choices enabled by the separation.

**Q3. What is the relationship between CQRS and Event Sourcing? Are they the same thing?**
A: They are distinct patterns that pair naturally but are not the same:

- **CQRS** is about separating the write and read models. The write side can use any persistence mechanism — a mutable relational table, a document store, or event sourcing. The read side projects data into query-optimized views.
- **Event Sourcing** is a persistence strategy where the write side never updates state in place — instead, it appends immutable events to an event log, and the current state is derived by replaying those events.

Event Sourcing and CQRS pair naturally because:
- Event sourcing's write side naturally produces events as its output — those events are the ideal input for updating read model projections.
- The event log is the authoritative write model; the projections are the read models. The separation is built into the pattern.
- Replaying events allows read models to be rebuilt from scratch — a powerful capability when you need a new projection or when a read model gets corrupted.

But CQRS does not require event sourcing. A CQRS system can have a write side that mutates a relational database in place and publishes change events via CDC (change data capture) or outbox patterns — the read side still gets those events and updates its projections. Event sourcing is one implementation strategy for the write side of CQRS, not a requirement.

## Section 2: The Write Side — Commands and the Command Model

**Q4. What is a command, and how is it different from an event?**
A: A **command** is an imperative request to do something — it carries intent and may be rejected. It is addressed to a specific part of the system that has the authority to decide whether the requested action is valid.

An **event** is a statement of fact about something that already happened — it cannot be rejected because it already occurred. Events are named in the past tense; commands in the imperative.

```
Command:  CreatePayment   { payment_id, user_id, amount, currency }
          ↓ (handled, business rules checked)
Event:    PaymentCreated  { payment_id, user_id, amount, currency, created_at }

Command:  ApproveTransfer { transfer_id, approver_id }
          ↓ (may be rejected if transfer is in wrong state)
Event:    TransferApproved { transfer_id, approver_id, approved_at }
       or CommandRejected  { reason: "Transfer already cancelled" }
```

The distinction matters architecturally:
- A command has one handler — the aggregate or service responsible for enforcing the business rules for that operation.
- An event has many potential consumers — multiple projections and downstream services may react to `PaymentCreated`.
- Commands are present-tense and mutable (the system can say "no"); events are past-tense and immutable (they happened).

**Q5. What is an aggregate in the context of CQRS, and what role does it play on the write side?**
A: An aggregate is a cluster of domain objects treated as a single unit for the purpose of data changes. In CQRS, the aggregate is the primary entry point for commands on the write side. It:

- **Encapsulates business rules**: The aggregate validates the command against its current state and enforces invariants. `Payment.approve()` checks that the payment is in `PENDING` state before transitioning.
- **Produces events**: When a command is valid, the aggregate produces one or more domain events that represent what changed.
- **Maintains consistency boundaries**: All changes within one aggregate happen atomically. Changes that span aggregates require eventual consistency (via events and sagas) rather than distributed transactions.

```java
public class Payment {
    private PaymentId id;
    private PaymentStatus status;
    private Money amount;

    public PaymentApproved approve(ApproverId approver) {
        if (this.status != PaymentStatus.PENDING) {
            throw new InvalidStateException("Payment " + id + " cannot be approved in state " + status);
        }
        this.status = PaymentStatus.APPROVED;
        return new PaymentApproved(this.id, approver, Instant.now());
    }
}
```

The aggregate boundary is the most critical design decision in CQRS/DDD: too large, and you create a coarse lock that serializes concurrent writes; too small, and you lose the ability to enforce multi-entity invariants atomically. The rule of thumb: an aggregate should be the smallest unit that can enforce its own business invariants without needing to coordinate with other aggregates in the same transaction.

**Q6. How does the write side persist state changes, and what is the outbox pattern's role?**
A: The write side persists state and publishes events as part of the same logical operation. The naive approach — write to the database, then publish to Kafka — creates a distributed transaction problem: the database write might succeed but the Kafka publish might fail (or vice versa), leaving the system in an inconsistent state.

The **transactional outbox pattern** solves this:

```
Within a single ACID transaction:
  1. Write the updated aggregate state to the main table (e.g., payments)
  2. Write the domain event to an outbox table (e.g., payment_outbox)
     in the same transaction

After the transaction commits:
  3. A separate process (the outbox relay) reads unpublished events from payment_outbox
  4. Publishes them to Kafka
  5. Marks them as published (or deletes them)
```

The outbox is in the same database as the aggregate state — so the write (state + event) is atomic. The relay is eventually consistent: there may be a short delay between the transaction committing and the event reaching Kafka, but the event is guaranteed to be published eventually (the relay retries on failure). This gives **at-least-once delivery** from write side to read side — idempotency on the consumer side handles the occasional duplicate.

Alternatively, **Change Data Capture (CDC)** with Debezium reads the database's binary replication log (WAL in PostgreSQL, binlog in MySQL) and produces events from every row change — eliminating the outbox table by using the database log itself as the event source.

## Section 3: The Read Side — Query Models and Projections

**Q7. What is a projection and how is it built in a CQRS system?**
A: A projection is a read-optimized materialized view of the data, derived by processing a stream of domain events. Unlike the write-side model (which enforces invariants and represents authoritative state), a projection is built purely for query performance — shaped for specific use cases without constraint from write-side normalization.

```
Events stream (from Kafka topic: payment.events):

  PaymentCreated   { payment_id, user_id, amount, currency, created_at }
  PaymentApproved  { payment_id, approver_id, approved_at }
  PaymentFailed    { payment_id, reason, failed_at }

Projection: PaymentSummaryView (stored in PostgreSQL read schema or Redis)

  Table: payment_summaries
  ┌────────────┬─────────┬────────┬──────────┬──────────────┬──────────────┐
  │ payment_id │ user_id │ amount │ currency │    status    │  updated_at  │
  ├────────────┼─────────┼────────┼──────────┼──────────────┼──────────────┤
  │ pay_001    │ usr_42  │ 500.00 │ INR      │ APPROVED     │ 2024-01-15   │
  │ pay_002    │ usr_17  │ 120.00 │ USD      │ FAILED       │ 2024-01-15   │
  └────────────┴─────────┴────────┴──────────┴──────────────┴──────────────┘
```

A projection handler subscribes to domain events and applies them to the read model:

```java
@Component
public class PaymentSummaryProjection {

    @EventHandler
    public void on(PaymentCreated event) {
        PaymentSummary summary = new PaymentSummary(
            event.getPaymentId(), event.getUserId(),
            event.getAmount(), event.getCurrency(), "PENDING"
        );
        paymentSummaryRepository.save(summary);
    }

    @EventHandler
    public void on(PaymentApproved event) {
        paymentSummaryRepository.updateStatus(event.getPaymentId(), "APPROVED");
    }

    @EventHandler
    public void on(PaymentFailed event) {
        paymentSummaryRepository.updateStatus(event.getPaymentId(), "FAILED");
    }
}
```

One write-side event stream can feed multiple projections simultaneously — each optimized for a different query pattern. A `PaymentCreated` event might update `payment_summaries` (for list views), `user_payment_totals` (for aggregate dashboards), and `fraud_signals` (for risk scoring) — all from the same event, all independently queryable.

**Q8. What storage technologies are typically used for the read model and why?**
A: The read model can use any storage that fits the query pattern — CQRS liberates the read side from the write side's technology constraints:

- **Relational (PostgreSQL, MySQL)** — for projections that still need relational queries (joins, aggregates, filtering). The read schema is often denormalized relative to the write schema — wide flat tables that avoid joins at query time.
- **Document stores (MongoDB)** — for projections where each entity maps to a document that is returned as-is. A `UserDashboard` document might embed the last 10 transactions, the current balance, and the account tier — returned in a single document fetch with no joins.
- **Search engines (Elasticsearch)** — for projections that need full-text search, faceted filtering, or relevance ranking. A `PaymentSearchIndex` allowing search by merchant name, amount range, or date is a natural Elasticsearch projection.
- **Key-value stores (Redis)** — for projections that are purely lookup by ID, especially when sub-millisecond latency is required. A `PaymentStatusCache` serving `payment_id → current_status` lookups can be a Redis hash with no disk I/O at query time.
- **Columnar / analytical (ClickHouse, BigQuery)** — for projections that serve analytical queries over large historical datasets: sum of payments by merchant per month, fraud rate by geography, average transaction value by user segment.

The key insight: **different queries can use different projections backed by different stores**. A single Kafka topic (`payment.events`) can feed a PostgreSQL projection for transactional queries, an Elasticsearch projection for search, and a Redis projection for status lookups — all from the same event stream, each optimized for its access pattern.

**Q9. How do you handle a query that needs data from multiple aggregates?**
A: In a normalized write model, cross-aggregate queries would use a join. In CQRS, the read model handles this at projection build time — the projection handler listens to events from multiple aggregates and assembles a denormalized view:

```
Events from two aggregates:

  UserRegistered { user_id, email, name }           ← from User aggregate
  PaymentCreated { payment_id, user_id, amount }    ← from Payment aggregate
  PaymentApproved { payment_id, approved_at }       ← from Payment aggregate

Projection: UserPaymentHistoryView

  Table: user_payment_history
  ┌─────────┬────────────────────┬────────────┬────────┬──────────┬──────────────┐
  │ user_id │ user_email         │ payment_id │ amount │  status  │ approved_at  │
  └─────────┴────────────────────┴────────────┴────────┴──────────┴──────────────┘
```

The projection handler subscribes to both `User` and `Payment` event streams and joins them at write time into a pre-computed view. The query reads this flat table directly — no runtime join.

This is the CQRS read model's core value proposition: **joins happen when data changes (at event processing time), not when data is queried (at read time)**. For a high-read system, moving join cost from query time to event processing time — where it happens once per change rather than once per query — is a significant throughput multiplier.

## Section 4: Eventual Consistency Between Read and Write Models

**Q10. What is eventual consistency in CQRS and what does it mean for end users?**
A: In CQRS, after a command is processed on the write side, the read model is updated asynchronously — via event propagation through a message broker. There is a window of time (milliseconds to seconds under normal conditions) during which the write model has new state but the read model still reflects old state. This is **eventual consistency**: the read model will converge to the correct state, but not instantaneously.

For end users, this manifests as:
- A user submits a payment, receives a success confirmation, and immediately refreshes the payment list — the new payment may not appear yet (the read projection hasn't been updated).
- A user's account balance on a dashboard may lag the actual balance by a few seconds after a transaction.
- A search result for a recently modified record may return stale data.

These are not bugs — they are the expected behavior of an eventually consistent system. The design challenge is deciding when eventual consistency is acceptable and when it is not, and communicating the model clearly to users and product stakeholders. "Your payment is being processed and will appear in your history shortly" is not a failure mode — it is an honest representation of the system's consistency model.

**Q11. How do you handle the "read-your-writes" problem in an eventually consistent CQRS system?**
A: The read-your-writes problem: a user executes a command, receives success, then immediately queries and sees stale data — their own write is not yet visible to them. Several strategies:

**Strategy 1 — Return the result in the command response:**
Instead of redirecting to a query after a command, return enough data in the command response itself to render the UI without a subsequent read:
```
POST /payments
Response: {
  "payment_id": "pay_001",
  "status": "PENDING",
  "amount": 500.00,
  "message": "Payment submitted. Status will update shortly."
}
```
The client renders from the command response. No immediate read required.

**Strategy 2 — Client-side optimistic update:**
The UI optimistically reflects the expected state immediately after the command, without waiting for the read model. If the command succeeded, the UI shows the expected outcome. The read model eventually catches up and confirms (or corrects) the displayed state.

**Strategy 3 — Version-aware queries:**
The command response includes the write-side version or sequence number of the change:
```
POST /payments → { "payment_id": "pay_001", "version": 47 }
GET /payments/pay_001?min_version=47
```
The read model query blocks (for a short timeout) until the projection has processed at least version 47. If the projection catches up within the timeout, the user sees their write. If not, return the current state with a `Retry-After` hint. This is complex to implement but gives strong read-your-writes guarantees.

**Strategy 4 — Read from the write side for the author:**
Immediately after a write, redirect the creator's read to the write-side model (the source of truth) rather than the read projection. Everyone else reads from the eventually consistent projection. The author gets strong consistency; other readers get eventual consistency. Works well when the query shape is simple enough to serve from the write model.

**Q12. What is the lag between a write and its read model being updated, and what drives it?**
A: The lag between a write-side state change and the read model reflecting it consists of several components:

```
Write transaction commits
         ↓ [outbox relay or CDC capture latency: ~10ms–500ms]
Event published to Kafka
         ↓ [Kafka consumer group lag: depends on consumer throughput]
Projection handler reads event from Kafka
         ↓ [projection write latency: depends on read store]
Read model updated and queryable
```

In a well-tuned system under normal load:
- Outbox relay or CDC capture: 10–100ms (relay polling interval or CDC lag).
- Kafka message propagation: <10ms (same data center).
- Projection handler processing: 10–100ms per event (simple update), up to seconds (complex aggregation).
- **Total typical lag: 50ms–500ms** under normal conditions.

Lag spikes occur when:
- **Consumer group lag accumulates**: A burst of commands produces more events than the projection handler can consume at steady state. Lag grows until the handler catches up — can be minutes during a traffic spike.
- **Projection handler is slow**: A projection that does expensive aggregation (e.g., recomputing a 30-day rolling sum on every event) will fall behind under load.
- **Infrastructure issues**: Kafka consumer rebalances, read store write latency spikes, or outbox relay being behind can all extend the lag window.

Monitoring read model lag as a metric — the difference between the event's `occurred_at` timestamp and when the projection processed it — is essential for catching consistency degradation before it impacts users.

**Q13. How do you rebuild a corrupted or missing read model projection?**
A: One of CQRS's most powerful operational properties: since the read model is derived from the event stream, it can be rebuilt from scratch by replaying all events through the projection handler.

The rebuild process:
```
1. Create a new projection table (or index) alongside the existing one.
   e.g., payment_summaries_v2 (while payment_summaries_v1 is still serving queries)

2. Replay all historical events from Kafka (or the event store) from offset 0
   through the projection handler into payment_summaries_v2.

3. Monitor replay progress — track the event timestamp lag until
   payment_summaries_v2 catches up to real-time.

4. Once caught up (lag < acceptable threshold), atomically switch the
   query endpoint to read from payment_summaries_v2.

5. Decommission payment_summaries_v1.
```

This zero-downtime rebuild is possible because:
- The event stream (Kafka topic with long retention, or a dedicated event store) retains the full history.
- The new projection processes events idempotently.
- Queries continue to be served from the old projection during the rebuild.

Beyond recovery, replay enables **adding new projections at any time**. A new analytics requirement — "show payment volume by merchant category for the last 2 years" — can be satisfied by creating a new projection and replaying 2 years of events into it. The historical data is already in the event stream; the projection is just a new view over it. This is fundamentally impossible with a mutable write model that overwrites history.

## Section 5: Consistency Patterns and Trade-offs

**Q14. When should you use a saga vs. a process manager for cross-aggregate workflows in CQRS?**
A: Cross-aggregate workflows in CQRS cannot use distributed transactions — instead they use choreography or orchestration to coordinate across aggregate boundaries.

**Saga (choreography)**: Each service/aggregate reacts to events and produces new commands/events. No central coordinator.

```
PaymentCreated      → Risk service consumes → RiskCheckPassed / RiskCheckFailed
RiskCheckPassed     → Account service consumes → FundsReserved / InsufficientFunds
FundsReserved       → Settlement service consumes → SettlementInitiated
SettlementInitiated → Notification service consumes → UserNotified
```

- Loose coupling — each service knows only about the events it consumes and produces.
- No single point of failure.
- Hard to visualize the overall workflow — the "flow" is implicit in the events.
- Debugging distributed failures is difficult — reconstructing what happened requires correlating events across multiple services.

**Process Manager (orchestration)**: A dedicated component explicitly coordinates the workflow, sending commands to each participant and waiting for their events.

```java
public class PaymentWorkflowProcessManager {

    public void on(PaymentCreated event) {
        commandGateway.send(new PerformRiskCheck(event.getPaymentId()));
    }

    public void on(RiskCheckPassed event) {
        commandGateway.send(new ReserveFunds(event.getPaymentId()));
    }

    public void on(FundsReserved event) {
        commandGateway.send(new InitiateSettlement(event.getPaymentId()));
    }

    public void on(RiskCheckFailed event) {
        commandGateway.send(new CancelPayment(event.getPaymentId(), "Risk check failed"));
    }
}
```

- The workflow is explicit and visible in one place.
- Easier to handle compensating transactions (rollbacks) — the process manager knows the full state.
- The process manager itself is a stateful component that must be persisted and recovered.
- A single point of failure if not made fault-tolerant.

**Choosing between them**: Use choreography for simple, stable workflows with few steps and clear ownership. Use process managers for complex workflows with many steps, conditional branching, and compensating actions — especially financial workflows where partial failure and rollback logic is complex. A payment workflow with risk check, fraud scoring, funds reservation, settlement, and notification is a strong candidate for a process manager: the branching is complex and the compensating transactions (cancel + refund) need coordinated rollback.

**Q15. What are compensating transactions and when do you need them in CQRS?**
A: In a distributed CQRS system with eventual consistency, a multi-step workflow may succeed partway through and then fail. Since there is no distributed transaction to roll back atomically, the system must issue **compensating transactions** — explicit domain operations that undo the effects of earlier steps.

```
Payment workflow that partially fails:

Step 1: PaymentCreated          ✅ succeeded
Step 2: RiskCheckPassed         ✅ succeeded
Step 3: FundsReserved           ✅ succeeded
Step 4: SettlementInitiated     ❌ failed (bank gateway timeout)

Compensating transactions (issued in reverse order):
Step 3': FundsReleased          ← reverses FundsReserved
Step 1': PaymentCancelled       ← reverses PaymentCreated (sets status to CANCELLED)
```

Compensating transactions are not rollbacks — they are new domain events that represent intentional business operations. `FundsReleased` is not "undo `FundsReserved`" at the database level; it is a meaningful business event that says "funds that were reserved have been released." This distinction matters: compensating transactions appear in the audit log, they are themselves projectable events, and they may trigger further reactions (like sending a cancellation notification).

Key design requirements:
- Every step in a multi-step workflow must have a defined compensating action.
- Compensating transactions must be idempotent — the saga may retry and issue the same compensating command more than once.
- The process manager (or saga) must persist its own state durably — if it crashes mid-compensation, it must be able to resume.

**Q16. How do you handle idempotency in CQRS command processing?**
A: At-least-once delivery from Kafka (or any message broker) means a command handler may receive the same command or event more than once — on retry, after a rebalance, or after a crash recovery. Command handlers and projection handlers must be idempotent: processing the same message twice produces the same outcome as processing it once.

**Command handler idempotency** (write side):
```sql
-- Deduplicate by command ID
CREATE TABLE processed_commands (
    command_id   UUID PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL
);

-- Before handling:
INSERT INTO processed_commands (command_id, processed_at)
VALUES (:command_id, NOW())
ON CONFLICT (command_id) DO NOTHING;

-- If 0 rows inserted → already processed; skip handler; return cached result
-- If 1 row inserted → new command; proceed with handler
```

This deduplication table write happens in the same transaction as the aggregate state update — atomically. A command that was already processed returns the same result without re-running business logic.

**Projection handler idempotency** (read side):
```sql
-- Track the last processed event offset per projection
UPDATE payment_summaries
SET status = :new_status, last_event_offset = :offset
WHERE payment_id = :payment_id
AND last_event_offset < :offset  -- only apply if this event is newer than last processed
```

Or use upsert semantics: applying the same event twice to a projection that uses `INSERT ... ON CONFLICT DO UPDATE` produces the same state as applying it once.

The general rule: idempotency is easier to achieve if handlers are **set-based** (set this field to this value) rather than **delta-based** (increment this counter by 1). A delta-based operation applied twice produces a wrong result; a set-based operation applied twice is harmless.

## Section 6: CQRS in Microservices and Fintech

**Q17. How does CQRS interact with microservices — does every service need separate read/write models?**
A: CQRS is a pattern, not a mandate. The right granularity depends on where the read/write asymmetry and complexity exist:

- **Services with high read:write ratio and complex query patterns** are strong CQRS candidates: a `PaymentService` that writes payment state but also serves dashboards, search, and reporting queries. The read patterns are diverse enough that a single write model can't serve all of them efficiently.
- **Services with simple CRUD semantics** do not benefit from CQRS overhead: a `ConfigurationService` that reads and writes configuration key-value pairs. Splitting read and write models adds operational complexity with no gain.
- **Services that are read-only consumers** of events from other services always have CQRS-like structure by nature: a `FraudDashboardService` that subscribes to payment events and materializes fraud signals is purely a read model — no write-side aggregate needed.

In a microservices architecture, the more common CQRS pattern is **cross-service projection**: the `PaymentService` owns the write model and publishes events; the `ReportingService` subscribes to those events and builds its own read model for analytical queries. Neither service is internally split by CQRS, but the overall system exhibits CQRS structure at the service level — the write authority and the read projection are in different services.

**Q18. How would you implement a payment status API in a CQRS architecture, ensuring sub-50ms p99 latency?**
A: A payment status query is a pure read — it should never touch the write-side model. The implementation:

**Read projection: Redis hash (sub-millisecond lookup)**
```
Key:   payment:status:{payment_id}
Value: { "status": "APPROVED", "updated_at": "2024-01-15T10:30:00Z", "version": 3 }
TTL:   24 hours (refreshed on every status event)
```

**Projection handler (Kafka consumer):**
```java
@KafkaListener(topics = "payment.events")
public void handle(PaymentEvent event) {
    String key = "payment:status:" + event.getPaymentId();

    Map<String, String> statusData = Map.of(
        "status",     event.getNewStatus(),
        "updated_at", event.getOccurredAt().toString(),
        "version",    String.valueOf(event.getVersion())
    );

    redisTemplate.opsForHash().putAll(key, statusData);
    redisTemplate.expire(key, Duration.ofHours(24));
}
```

**Query handler:**
```java
public PaymentStatus getPaymentStatus(String paymentId) {
    String key = "payment:status:" + paymentId;
    Map<String, String> status = redisTemplate.opsForHash().entries(key);

    if (status.isEmpty()) {
        // Redis miss: fall back to PostgreSQL read replica (write-side DB)
        // This handles: new payment not yet projected, cache eviction edge cases
        return paymentReadRepository.findById(paymentId)
            .map(PaymentStatus::fromEntity)
            .orElseThrow(() -> new PaymentNotFoundException(paymentId));
    }

    return PaymentStatus.fromRedisHash(status);
}
```

This layered read strategy:
- **Hot path**: Redis hash lookup — p50 <1ms, p99 <5ms. The vast majority of status queries hit this path.
- **Fallback path**: PostgreSQL read replica — p99 <50ms, handles cache misses for very recent payments or eviction edge cases.
- **Projection lag**: Status events propagate from Kafka to Redis in ~50–200ms under normal load. A payment queried immediately after creation may fall through to the fallback path, which is fine — the fallback reads from the write-side DB and returns the authoritative state.

This is CQRS's read scalability in practice: the read path is stateless, Redis is horizontally scalable, and the write side (PostgreSQL) is never touched by the read path under normal conditions.

## Section 7: Scenario / System Design Style Questions

**Q19. "Design the CQRS architecture for a payment processing system. Walk through the write path, event propagation, and multiple read projections."**
A:

```
Write Path:
  Client → POST /payments (CreatePayment command)
         → PaymentCommandHandler validates and routes
         → Payment aggregate enforces business rules (user KYC'd, amount within limit)
         → Payment aggregate state saved to PostgreSQL (payments table)
         → PaymentCreated event saved to payment_outbox (same transaction)
         → HTTP 202 Accepted: { payment_id, status: "PENDING" }

Event Propagation:
  OutboxRelay polls payment_outbox (every 100ms)
         → Publishes PaymentCreated to Kafka topic: payment.events
         → Marks outbox row as published
  
  Kafka: payment.events
         ├─ PaymentCreated  { payment_id, user_id, amount, currency, created_at }
         ├─ PaymentApproved { payment_id, approver_id, approved_at }
         ├─ PaymentFailed   { payment_id, reason, failed_at }
         └─ PaymentRefunded { payment_id, refund_amount, refunded_at }

Read Projections (all consume from payment.events):

  1. PaymentStatusCache (Redis)
     Purpose: Sub-millisecond payment status lookup
     Key: payment:status:{payment_id}
     Updated by: all events (status field changes)

  2. PaymentListProjection (PostgreSQL)
     Purpose: Paginated payment history per user
     Table: user_payment_history (user_id, payment_id, amount, status, created_at)
     Query: SELECT * FROM user_payment_history WHERE user_id = ? ORDER BY created_at DESC
     Updated by: PaymentCreated (insert), all status events (update)

  3. PaymentSearchIndex (Elasticsearch)
     Purpose: Full-text and faceted search (by merchant, amount range, date range, status)
     Index: payments-search
     Document: { payment_id, user_id, merchant_name, amount, currency, status, tags }
     Updated by: PaymentCreated (index), status events (update doc)

  4. PaymentAnalyticsProjection (ClickHouse)
     Purpose: Aggregate reporting (total volume by day, failure rate by currency)
     Table: payment_events_raw (append-only, one row per event)
     Queries: SELECT currency, SUM(amount), COUNT(*) FROM payment_events_raw GROUP BY ...
     Updated by: all events (append-only insert)

Query Path:
  GET /payments/{id}/status    → Redis  (PaymentStatusCache)
  GET /users/{id}/payments     → PostgreSQL (PaymentListProjection)
  GET /payments/search?q=...   → Elasticsearch (PaymentSearchIndex)
  GET /analytics/payments/...  → ClickHouse (PaymentAnalyticsProjection)
```

Each query path is independently scalable — scale Redis without touching ClickHouse, scale Elasticsearch without touching PostgreSQL. The write side (PostgreSQL + Kafka) is the single source of truth; read models are derivatives that can be rebuilt at any time.

**Q20. "After a deployment, you discover your payment list projection is showing incorrect data for some users. How do you fix this in a CQRS system?"**
A: The answer to a corrupted projection in CQRS is always the same: **rebuild from the event stream**.

```
Step 1: Diagnose the scope
  - Identify which users are affected and from which event offsets the corruption begins.
  - Check Kafka consumer group lag for the projection handler — is it behind, or is
    the bug in how events are being processed?
  - Read a sample of raw events from Kafka and manually trace what the projection
    handler should have produced vs. what's in the read model.

Step 2: Fix the projection handler code
  - Identify and fix the bug (e.g., wrong field being updated, missing event type handled).
  - Do NOT patch the database directly — the patch would be overwritten on the next
    event, or would diverge from what a rebuild produces. Fix the handler code.

Step 3: Rebuild the projection
  - Create payment_list_v2 table alongside the existing payment_list (still serving queries).
  - Reset the Kafka consumer group offset for the projection handler to offset 0
    (or the earliest available offset on the topic).
  - Let the fixed handler replay all events into payment_list_v2.
  - Monitor replay progress until payment_list_v2 is caught up to real-time.

Step 4: Cut over
  - Atomically update the query path to read from payment_list_v2.
  - Verify queries return correct data.
  - Decommission payment_list (old table).
```

The key operational advantage: the event stream is the ground truth. The projection is a derivative. No data is lost — a corrupted projection is annoying, not catastrophic. The ability to rebuild is what separates CQRS from a mutable model, where a bug that corrupts the single write store is a data integrity incident.

**Q21. "Your team proposes CQRS for a new internal configuration service. Should you use it? How do you argue for or against?"**
A: This is a judgment question about when not to apply CQRS, not when to apply it.

**Arguments against CQRS for a configuration service:**

- **Low read:write ratio**: Configuration is read rarely and written even more rarely. The asymmetry that motivates CQRS doesn't exist.
- **Simple query patterns**: "Get all active feature flags" or "get config by key" are served perfectly well by a single relational table. No projection complexity needed.
- **Operational overhead without benefit**: CQRS requires event propagation infrastructure, projection handlers, consistency lag management, and rebuild procedures. For a configuration service used by 5 internal services, this is pure overhead with no return.
- **Consistency requirements**: Configuration changes often need to be immediately visible to all consumers. Eventual consistency is actively harmful here — a feature flag change that propagates with a 500ms lag means different services see different flag values during the lag window.
- **Team cognitive overhead**: CQRS is a complex pattern. Applying it where it isn't warranted teaches the team to associate the pattern with complexity rather than with the specific problems it solves.

**The counter-argument (when CQRS for config might be warranted):**
- If the configuration service needs to serve millions of reads per second (feature flag evaluation in a hot path) alongside much lower write rates — and the read latency requirement is sub-millisecond — a Redis read projection might be justified. But this is a scaling solution, not a CQRS-for-CQRS's-sake solution.

**The principle to argue**: Apply CQRS when the cost of separating read and write models is lower than the cost of trying to serve both from a single model. The costs of CQRS — operational complexity, eventual consistency reasoning, projection management — are fixed. They are only worth paying when the read/write asymmetry, query diversity, or independent scaling requirements are significant enough to outweigh them.

**Q22. "A product manager asks why a user can successfully submit a payment but then sees nothing in their payment history for 2 seconds. How do you explain eventual consistency to a non-technical stakeholder?"**
A: Frame it in terms of the trade-off being made deliberately:

*"When a user submits a payment, we immediately save it to our secure, highly reliable write system — that's the confirmation they get. Their payment history is powered by a separate, fast-read system that is optimized for displaying data quickly to thousands of users simultaneously.*

*There is a brief moment — typically under 2 seconds — where the write system has the payment but the display system is still updating. This is the same reason why a bank transfer shows 'Processing' before appearing in your statement: the authorization is instant, but the display catches up shortly after.*

*The trade-off we made: by separating the 'save' system from the 'display' system, we can make payment history load in under 100ms for millions of users. If we kept them as one system, we'd have slower payments AND slower history — neither side could be optimized. The 2-second delay is the cost of that architecture. We can reduce it further [with the strategies discussed in Q11] — but eliminating it entirely would require giving up the read performance we've built."*

The framing: the eventual consistency lag is not a defect to apologize for — it is the explicit price of a deliberate architectural optimization. Making the trade-off visible and quantified ("2 seconds to enable 100ms read latency at scale") is more productive than defending it as a technical necessity.

## Quick Reference

| Concept | Detail |
|---|---|
| CQRS | Separate write model (commands) from read model (queries); each optimized independently |
| Command | Intent to change state; may be rejected; handled by one aggregate |
| Query | Request for current state; changes nothing; served from read model |
| Event | Fact about what happened; immutable; past tense; consumed by projections |
| Aggregate | Write-side domain object; enforces business rules; produces events on state change |
| Projection | Read-optimized materialized view derived from event stream |
| Eventual consistency | Read model lags write model by propagation time; converges to correct state |
| Outbox pattern | Write state + event atomically to same DB; relay publishes to Kafka separately |
| CDC | Change Data Capture; read DB binary log (WAL/binlog) to produce events without outbox table |
| Read-your-writes | Problem: user doesn't see their own write immediately; solutions: return in command response, client-side optimistic update, version-aware reads |
| Saga / choreography | Cross-aggregate workflow via events; no central coordinator; loose coupling |
| Process manager | Cross-aggregate workflow via orchestrator; explicit state; easier compensating transactions |
| Compensating transaction | Explicit business event that reverses a prior step; not a DB rollback; appears in audit log |
| Idempotency | Same command/event processed twice = same outcome; required for at-least-once delivery |
| Projection rebuild | Replay all events from Kafka into a new projection; fixes corruption; enables new views |

## The Core Mental Model

```
CQRS = two models, one truth

Write side (commands):
  Client → Command → Aggregate (business rules) → Event(s) → Event Store / Outbox
  Optimized for: correctness, invariant enforcement, transactional integrity
  Technology: relational DB, event store, strong consistency

Event propagation:
  Outbox/CDC → Kafka → Projection Handlers
  Lag: 50ms–500ms typical; up to minutes under load
  At-least-once delivery → idempotency required on both sides

Read side (queries):
  Projection Handlers → Materialized Views → Query Handlers → Client
  Optimized for: latency, throughput, query shape
  Technology: Redis (status cache), Elasticsearch (search), ClickHouse (analytics),
              PostgreSQL read replica (relational queries) — each for its query pattern

Eventual consistency contract:
  Write succeeds → "your command was accepted"
  Read may lag   → "current state as of ~500ms ago"
  Always converges → projection will catch up; event stream is the truth

Projection rebuild = operational superpower:
  Read model corrupted or wrong? → replay events from offset 0 → rebuild
  Need a new query pattern?      → create new projection → replay → serve queries
  The event stream is permanent; projections are disposable derivatives

When to apply CQRS:
  ✅ High read:write ratio (10:1 or more)
  ✅ Diverse query patterns that a single model can't serve efficiently
  ✅ Independent scaling of read and write paths required
  ✅ Long audit history and need for time-travel queries
  ❌ Simple CRUD with uniform access patterns
  ❌ Strong read-your-writes consistency required everywhere
  ❌ Small team / early-stage product where operational complexity is unaffordable

The eventual consistency nuance:
  Not every read needs to be eventually consistent.
  The author of a write can get strong consistency (read from write side).
  Other readers get eventual consistency (read from projections).
  CQRS does not mean "no strong consistency anywhere" — it means
  "strong consistency where required, eventual consistency where sufficient."
```

---

**Tip for the interview:** CQRS questions at 5 YOE almost always escalate to one of three places: (1) the eventual consistency lag and how you handle read-your-writes — knowing that "return data in the command response" is the simplest solution, and "version-aware reads" is the most robust, shows you've thought about this in production; (2) the projection rebuild — why it's possible (the event stream is the source of truth), how you do it zero-downtime (build alongside, then cut over), and why this makes read model corruption a nuisance rather than an incident; (3) when NOT to use CQRS — the strongest signal at this level is knowing that CQRS for a simple configuration service or CRUD endpoint is an anti-pattern, not an upgrade. The nuance that separates someone who has operated CQRS from someone who has only read about it: understanding that `acks=all` on the Kafka producer guarantees the event reaches the broker, but the read model is only consistent when the projection handler has processed and committed it — and those are two different moments with different failure modes.
