# Event Versioning and Backward/Forward Compatibility — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Event Versioning Exists

**Q1. What breaks when event schemas change without a versioning strategy?**
A: In an event-driven system, producers and consumers are deployed independently. An event written today may be consumed months or years later — from a Kafka topic with long retention, from an event store being replayed, or by a new downstream service onboarded after the fact. Without versioning, any schema change creates one of two failure modes:

- **Silent data corruption**: A producer removes a field the consumer relies on, or changes its type. The consumer deserializes successfully but operates on wrong data — a `null` where a required amount should be, or a string parsed as a number. No exception, no alert — the corruption propagates downstream silently until a data quality check or business anomaly surfaces it.
- **Hard deserialization failure**: A consumer encounters a field or type it cannot decode. Processing halts, consumer lag grows, and alerts fire — the more visible failure but often worse operationally because it can block entire partitions until resolved.

Both modes share the same root cause: the implicit assumption that producer and consumer are always on the same schema version. Event versioning makes the schema version **explicit** — embedded in the event itself — so consumers can handle multiple versions concurrently, and producers can evolve schemas without requiring simultaneous consumer deployment.

**Q2. Why is event schema evolution harder than API schema evolution?**
A: A REST API can enforce a contract synchronously: if the client and server disagree on the schema, the HTTP response fails immediately and both sides know it. The producer (server) and consumer (client) negotiate the schema at call time and are always in contact.

Events break this model in three ways:

- **Time decoupling**: An event written to Kafka at 9:00 AM may be consumed at 9:00 AM, next week, or during a replay 2 years from now. The producer and consumer never negotiate at the moment of consumption — they agreed (or didn't) at schema design time.
- **Fan-out**: One event may be consumed by 10 downstream services, each on its own deployment schedule. A schema change must be compatible with all 10 consumers simultaneously — you cannot negotiate with each consumer independently the way an API can.
- **Immutability**: Events are facts. Once written, they cannot be edited. A REST API response can be reformatted on the fly; an event already in Kafka cannot. All consumers that will ever read offset 42 will read exactly the bytes written at offset 42 — the producer cannot retroactively patch them.

These three properties mean event schema changes must be planned with more care than API changes. The cost of a breaking event schema change is borne by every downstream consumer, retroactively, for the full retention lifetime of the topic.

**Q3. What is the difference between backward compatibility and forward compatibility, and why do you need both?**
A: The two directions describe which side is upgraded first:

- **Backward compatibility**: A new schema version can read data written by an older schema version. The consumer is upgraded before the producer. Old events (written with the old schema) can still be processed by the new consumer code. This is the minimum requirement for any long-retention event stream — old events must remain readable.

- **Forward compatibility**: An old schema version can read data written by a newer schema version. The producer is upgraded before the consumer. New events (written with the new schema) can be processed by the consumer that hasn't been updated yet. This is what allows safe producer deployments without waiting for all consumers to be upgraded simultaneously.

```
Backward: new consumer reads old events
           Consumer upgraded first → old producers still running → must work
           Also: consumer replaying historical events → must work on all old schema versions

Forward:  old consumer reads new events
           Producer upgraded first → old consumers still running → must work
           Also: during rolling deployment, old and new consumers run concurrently
```

You need both because in practice, upgrade order is not always controllable — rolling deployments mean old and new versions of both producers and consumers run simultaneously, and any order is possible. Full compatibility (both backward and forward) is the production standard for any topic where independent deployment is a requirement.

## Section 2: Versioning Strategies

**Q4. What are the main strategies for embedding version information in events?**
A: Four strategies are in common use, with different trade-offs:

**Strategy 1 — Version field in the event payload:**
```json
{
  "event_type": "PaymentCreated",
  "version": 2,
  "payment_id": "pay_001",
  "amount": 500.00,
  "currency": "INR",
  "merchant_id": "merch_42"
}
```
Simple and self-contained. The consumer reads `version` before deserializing the rest of the payload and routes to the correct handler. Requires discipline: every schema change must bump the version, and every producer must set it correctly.

**Strategy 2 — Version in the event type name:**
```
PaymentCreated.v1
PaymentCreated.v2
PaymentCreatedV2
```
The Kafka topic, message header, or envelope field carries a versioned type name. Consumers route by event type string, and new versions are distinct types — old handlers still receive `PaymentCreated.v1`; new handlers receive `PaymentCreated.v2`. Clean separation but proliferates type names and requires consumers to register handlers for every version they support.

**Strategy 3 — Schema Registry schema ID (Avro/Protobuf):**
```
Wire format: [0x00][schema_id: 4 bytes][binary payload]
```
The schema ID in the Confluent wire format is the version identifier. Consumers look up the schema by ID and use Avro/Protobuf resolution to handle version differences automatically. This is the most robust strategy for binary serialization formats — the serialization library itself handles version negotiation, not application code. Described in the Schema Registry guide; here we focus on what the application layer must know in addition.

**Strategy 4 — Envelope pattern with explicit schema metadata:**
```json
{
  "envelope_version": 1,
  "event_type": "PaymentCreated",
  "schema_version": 2,
  "schema_url": "https://schema-registry/schemas/PaymentCreated/v2",
  "occurred_at": "2024-01-15T10:30:00Z",
  "payload": { ... }
}
```
A top-level envelope carries versioning metadata separately from the payload. Consumers can inspect the envelope before deciding how to deserialize the payload — useful when the payload serialization format itself may change across versions.

Most production systems combine strategies: Avro schema ID for binary format versioning, an explicit `version` or `event_type` field for application-level routing, and the envelope pattern for metadata that all consumers need regardless of version.

**Q5. What is the "versioned topic" strategy and when is it appropriate?**
A: The versioned topic strategy creates a new Kafka topic for each major schema version rather than evolving in place:

```
payments.events.v1   ← original topic, forever
payments.events.v2   ← new topic, new schema; producers switch to writing here
```

Consumers of the old schema continue reading from `v1` until they migrate. New consumers and migrated consumers read from `v2`. The two topics run in parallel during the transition window, then `v1` is decommissioned after its retention expires and all consumers have migrated.

**When it is appropriate:**
- **Breaking schema changes** that cannot be made compatible through evolution (removing a required field, changing a fundamental data model). A versioned topic sidesteps the compatibility problem entirely — the old schema is preserved unchanged in `v1`; the new schema is independent in `v2`.
- **Major domain model redesigns**: When the event represents a fundamentally different concept, not just an evolution of the existing one.
- **Regulatory or compliance boundaries**: When old events must be immutably preserved under their original schema for audit purposes, while new events use an updated schema.

**When it is not appropriate:**
- Routine additive changes (adding optional fields) — these are solvable through compatibility rules without the operational overhead of parallel topics.
- High-frequency schema changes — versioned topics multiply operational surface area fast: more topics, more consumer group configurations, more monitoring.

The versioned topic strategy trades compatibility complexity for operational complexity. Use it for genuinely incompatible changes; use schema evolution for everything else.

**Q6. What is the "event upcasting" pattern and how does it work?**
A: Event upcasting (also called event upgrading) is the practice of transforming an old event version into a newer version at read time — without modifying the stored event. The upcast logic lives in the consumer infrastructure layer, transparently between reading from the event store and delivering to the application handler.

```
Stored event (v1):
  { "event_type": "PaymentCreated", "version": 1,
    "payment_id": "pay_001", "user_id": "usr_42", "amount": 500.00 }

Upcast to v2 (adds merchant_id, splits amount into amount + currency):
  { "event_type": "PaymentCreated", "version": 2,
    "payment_id": "pay_001", "user_id": "usr_42",
    "amount": 500.00, "currency": "INR",  ← injected default
    "merchant_id": null }                  ← injected null (optional field)

Application handler receives only v2:
  void handle(PaymentCreatedV2 event) { ... }
  // Handler never sees v1; upcasting is transparent
```

The upcaster chain — multiple upcasters applied in sequence:
```
v1 → upcast_1_to_2 → v2 → upcast_2_to_3 → v3
```
An event written at v1 passes through all upcasters before reaching a handler written for v3. Each upcaster is small and focused — it only handles the delta between two adjacent versions.

**Trade-offs of upcasting:**
- Application code handles only the current schema version — no version-switching logic in handlers.
- Upcasters accumulate over time and must be maintained permanently for events still in the store.
- Upcasting injects derived or default values for fields that didn't exist when the event was written — these are reconstructions, not the original producer's intent. Document them clearly.
- Not appropriate when a v1 event genuinely cannot be represented as a v3 event without information that was never captured — upcasting cannot invent data.

## Section 3: Specific Compatibility Scenarios

**Q7. What schema changes are safe (non-breaking) and which are breaking?**
A: Classified by direction:

**Changes that are backward-compatible (new consumer reads old events):**

| Change | Safe? | Reason |
|---|---|---|
| Add optional field with default | ✅ | Old events lack it; consumer injects default |
| Remove a field | ✅ | Consumer ignores the field in old events; it's just absent in new events |
| Widen a numeric type | ✅ | `int` → `long`; all old values representable in the new type |
| Add a new enum value | ✅ | Old events never contain the new value |
| Add a new event type entirely | ✅ | Consumers that don't know it can ignore it |
| Rename a field (with alias) | ✅ | Avro/Protobuf aliases map old name to new |
| Change a required field to optional | ✅ | Relaxes constraint; old events still valid |

**Changes that are forward-compatible (old consumer reads new events):**

| Change | Safe? | Reason |
|---|---|---|
| Add optional field with default | ✅ | Old consumers ignore unknown fields |
| Remove a field | ⚠️ | Only if old consumers don't depend on it |
| Add a required field | ❌ | Old consumers have no value for it; fail on decode |
| Remove an enum value | ❌ | New events never produce it but old consumers expect it |

**Always breaking (neither direction):**

| Change | Breaking | Reason |
|---|---|---|
| Rename a field (without alias) | ❌ | Old consumers expect old name; new consumers expect new name |
| Change field type incompatibly | ❌ | `string` → `int`; bytes cannot be reinterpreted |
| Change field semantics | ❌ | Field name preserved but meaning changed; silent wrong data |
| Remove a required field | ❌ | Old consumers depend on it; new events don't have it |
| Change event ordering guarantees | ❌ | Consumers may depend on ordering that no longer holds |

**The hardest breaking change to detect — semantic changes**: Renaming `amount` to `gross_amount` is a syntactic rename that tools can catch. Changing `amount` to mean "amount excluding tax" when it used to mean "amount including tax" is a semantic change — the field name is the same, the type is the same, but the meaning has changed. Schema validation tools cannot catch this. Semantic changes require explicit versioning (bump the version number) and documentation, not just schema compatibility checks.

**Q8. How do you handle renaming a field in an event that is already in production?**
A: A direct rename is always breaking — old consumers expect the old name; new consumers expect the new name. The safe migration path:

**Phase 1 — Dual-write (producer adds new field, keeps old):**
```json
// v1.5 — transitional schema
{
  "payment_id": "pay_001",
  "user_id": "usr_42",        ← old field (kept)
  "account_id": "usr_42",     ← new field (added, same value)
  "amount": 500.00
}
```
Both `user_id` (old) and `account_id` (new) are present. Old consumers read `user_id` as before — no change for them. New consumers read `account_id`. The event payload is temporarily redundant, but both producer and all consumers can be deployed independently.

**Phase 2 — Consumer migration:**
Migrate all consumers to read `account_id` instead of `user_id`. This can happen incrementally — consumer by consumer — because both fields are present. No coordinated cutover required.

**Phase 3 — Remove the old field:**
Once all consumers have migrated to `account_id`, the producer removes `user_id`. Now the payload is clean and no longer redundant. Old consumers must be fully migrated before this phase — this is the only hard dependency in the migration.

```
Timeline:
  Week 1: Ship v1.5 (dual fields) — old consumers: unaffected, new consumers: can start migrating
  Weeks 2-4: Migrate consumers to account_id
  Week 5: Ship v2 (remove user_id) — all consumers already on account_id
```

The dual-write window (Phase 1 → Phase 3) is the operational cost of a safe rename. Its length depends on how many consumers exist and how quickly they can be updated. For a topic with 20 downstream consumers across 5 teams, this window may be weeks — plan accordingly.

**Q9. What is a "semantic version bump" in event schemas, and when does a patch vs minor vs major increment apply?**
A: Borrowing from semver (`MAJOR.MINOR.PATCH`) for event schema versioning:

- **PATCH (1.0.0 → 1.0.1)**: No schema change — a bug fix in the producer that changes the data the existing field contains (e.g., fixing a calculation error). The schema is identical; the data quality changes. Consumers don't need to update code but may want to re-process historical events if the fix is significant.

- **MINOR (1.0.0 → 1.1.0)**: Backward and forward compatible change — adding an optional field, adding an enum value, relaxing a constraint. Consumers can upgrade at their own pace; they gain access to the new data when ready. Old consumers continue working without any change.

- **MAJOR (1.0.0 → 2.0.0)**: Breaking change — removing a required field, renaming without alias, changing type incompatibly, or a semantic change that makes v1 and v2 logically different events. Requires coordinated migration: either the dual-write pattern, the versioned topic strategy, or consumer-side upcasting before the producer deploys.

In practice, strict semver is often relaxed for events: `version: 1`, `version: 2` in the payload (integer version). Minor-compatible changes don't bump the version; only breaking or significantly additive changes do. The version number is what consumers switch on in their routing logic — it should change when consumers need to know a new version is in play, not for every additive field addition.

## Section 4: Consumer-Side Compatibility

**Q10. What is the "tolerant reader" pattern and how does it protect consumers from schema changes?**
A: The tolerant reader pattern is a defensive deserialization discipline: consumers only extract the fields they care about and explicitly ignore everything they don't recognize. This makes consumers structurally resilient to additive producer changes.

**Brittle reader (anti-pattern):**
```java
// Fails if PaymentCreated gains new required fields or changes structure
PaymentCreated event = objectMapper.readValue(payload, PaymentCreated.class);
// objectMapper configured with FAIL_ON_UNKNOWN_PROPERTIES = true (Jackson default)
```

**Tolerant reader:**
```java
// Tolerant deserialization — unknown fields silently ignored
ObjectMapper mapper = new ObjectMapper()
    .configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false)
    .configure(DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES, false);

PaymentCreated event = mapper.readValue(payload, PaymentCreated.class);
// New fields added by producer: ignored, no exception
// Missing optional fields: null or default value
```

The tolerant reader pattern shifts the consumer from "I expect exactly this schema" to "I need these specific fields; I don't care what else is present." Combined with explicit null handling for optional fields, it makes additive producer changes invisible to consumers.

**Beyond deserialization — tolerant behavior in business logic:**
```java
// Don't fail if an optional new enum value is unrecognized
if (event.getRiskLevel() == null || !KNOWN_RISK_LEVELS.contains(event.getRiskLevel())) {
    // New enum value added by producer; treat as UNKNOWN, don't crash
    riskLevel = RiskLevel.UNKNOWN;
} else {
    riskLevel = RiskLevel.valueOf(event.getRiskLevel());
}
```

Tolerant reader is the consumer-side complement to backward-compatible producer changes. A producer that adds optional fields with defaults and a consumer that ignores unknown fields can each be deployed independently without coordination. This is the contractual basis for autonomous team deployments.

**Q11. How do you implement a multi-version event handler in a consumer service?**
A: When a consumer must support multiple schema versions simultaneously — during a migration window, or for long-running topics with mixed-version history — version routing logic handles the dispatch:

**Pattern 1 — Explicit version routing:**
```java
public void handle(ConsumerRecord<String, byte[]> record) {
    int version = extractVersion(record); // from header, envelope, or wire format

    switch (version) {
        case 1 -> handleV1(deserializeV1(record.value()));
        case 2 -> handleV2(deserializeV2(record.value()));
        default -> {
            log.warn("Unknown version {} for event, skipping", version);
            // Or: route to a dead-letter topic for inspection
        }
    }
}

private void handleV1(PaymentCreatedV1 event) {
    // Map v1 to internal domain model, filling defaults for missing fields
    processPayment(event.getPaymentId(), event.getUserId(),
                   event.getAmount(), "INR"); // currency was absent in v1
}

private void handleV2(PaymentCreatedV2 event) {
    processPayment(event.getPaymentId(), event.getUserId(),
                   event.getAmount(), event.getCurrency());
}
```

**Pattern 2 — Normalize to current version at the boundary:**
```java
public void handle(ConsumerRecord<String, byte[]> record) {
    // All version handling happens here, once
    PaymentCreatedV2 normalized = upcaster.upcast(record);
    // Everything downstream only knows about V2
    processPayment(normalized);
}
```
The upcast happens at the consumer's inbound boundary. All internal logic deals with a single version — version complexity is contained in the upcaster, not scattered across handlers.

**Pattern 3 — Avro/Protobuf schema resolution (transparent multi-version):**
When using Avro with Schema Registry, the deserializer performs writer/reader schema resolution automatically. The application handler receives a fully resolved object in the current schema shape regardless of which version the producer used. This is the cleanest approach — no application-level version routing, no explicit upcasting. The constraint: only compatible schema changes are handled; breaking changes still require one of the explicit patterns above.

**Q12. What should a consumer do when it receives an event version it doesn't recognize?**
A: Unknown versions should never silently succeed or silently fail. The options, in order of preference:

**Option 1 — Dead-letter the event:**
Route the unrecognized event to a dead-letter topic (DLT) for investigation. The consumer continues processing other events — it doesn't block on an unknown version. The DLT accumulates unknown events for manual inspection and potential replay once the consumer is updated.
```java
if (!SUPPORTED_VERSIONS.contains(version)) {
    log.error("Unsupported event version {} for type {}; routing to DLT",
              version, eventType);
    deadLetterProducer.send(DLT_TOPIC, record);
    return; // Acknowledge and continue — don't block the partition
}
```

**Option 2 — Skip with alerting:**
If the event is non-critical and missing it is tolerable, skip it but alert:
```java
if (!SUPPORTED_VERSIONS.contains(version)) {
    metrics.incrementCounter("events.unknown_version",
                             "type", eventType, "version", String.valueOf(version));
    log.warn("Skipping event with unknown version {}; consumer needs upgrade", version);
    return;
}
```

**Option 3 — Fail and stop:**
For critical events where processing an unknown version would be safer than skipping: throw an exception, do not commit the offset, alert the on-call team. The consumer stops processing the partition until the issue is resolved (consumer upgrade or manual offset management). Use this only when data loss from skipping is worse than availability loss from stopping.

**Never do**: silently commit the offset on an unknown version without logging or alerting. Unknown events disappear without a trace, making debugging impossible.

The right choice depends on the event's criticality. Payment events: dead-letter (never skip silently, don't stop indefinitely). Audit log events: skip with alerting. User activity telemetry: skip silently is arguably fine.

## Section 5: Event Store and Long-Retention Topics

**Q13. What are the specific versioning challenges for event-sourced systems with long event history?**
A: Event sourcing stores events permanently — the aggregate's current state is derived by replaying all events from the beginning. Unlike a Kafka topic with a 7-day retention window, an event store may contain events from 5+ years ago written against schemas that have gone through 10 major versions. This creates three unique challenges:

**Challenge 1 — Upcaster chain length:** Each schema version transition requires a upcaster. 10 versions = 9 upcasters, applied in sequence for every aggregate replay from the beginning. The chain must be maintained indefinitely — an upcaster for v1→v2 cannot be deleted as long as any event store contains v1 events. Over years, this chain becomes a significant maintenance burden.

**Challenge 2 — Snapshot poisoning:** Event sourcing systems use snapshots (periodic checkpoints of aggregate state) to avoid replaying the entire event history on every load. Snapshots are serialized using the schema current at snapshot time. If the schema evolves after a snapshot is taken, the snapshot must either be upcasted to the current schema or discarded and regenerated from the full event replay. Failing to handle snapshot schema evolution causes subtle correctness bugs — an aggregate loaded from a stale snapshot may have wrong state for fields added after the snapshot was taken.

**Challenge 3 — Replaying events into new projections:** When a new read model projection is built by replaying historical events, it encounters every schema version ever used. The projection handler must handle v1 through vN. Either all upcasters are applied before the projection handler (so it sees only the current schema), or the projection handler itself must be version-aware for the full history.

```
Event store contains:
  2019: PaymentCreated v1 events
  2020: PaymentCreated v2 events (added currency field)
  2021: PaymentCreated v3 events (added merchant_id)
  2022: PaymentCreated v4 events (renamed user_id → account_id)

New projection built in 2024:
  Must handle v1, v2, v3, v4 — or rely on upcasters to normalize to v4
  before projection handler sees any event.
```

The mitigation: apply upcasters in the event store infrastructure layer, before events reach application code. Application code deals only with the current schema version. The upcaster chain is maintained by a dedicated infrastructure team (or framework) rather than scattered across every service that reads the event store.

**Q14. How do snapshots interact with schema evolution in event-sourced systems?**
A: A snapshot captures the aggregate's state at a point in time, serialized with the schema current at that moment. When the schema evolves, snapshots from before the change contain old-schema data that may be structurally or semantically different from the current schema.

**The snapshot versioning problem:**
```
T=0:  Schema v1: Payment { payment_id, user_id, amount }
T=1:  Snapshot taken: { payment_id: "pay_001", user_id: "usr_42", amount: 500.00 }
T=2:  Schema v2: Payment { payment_id, account_id, amount, currency }
      (renamed user_id → account_id, added currency)
T=3:  Aggregate loaded: snapshot read → Payment { ..., user_id: "usr_42", ... }
      ← user_id doesn't exist in v2 schema; currency is missing
      ← WRONG STATE if snapshot is deserialized without upcasting
```

**Solutions:**

**Option 1 — Version the snapshot:**
```json
{ "snapshot_version": 1, "payload": { "payment_id": ..., "user_id": ... } }
```
On load, read the snapshot version and apply upcasters before hydrating the aggregate. Same upcaster chain as for events.

**Option 2 — Invalidate snapshots on schema change:**
Mark all existing snapshots as invalid when a schema change is deployed. On next load, skip the snapshot and replay from events (events are themselves upcasted). Generate a fresh snapshot in the current schema after replay. Slower on first load post-migration, but eliminates snapshot upcasting complexity.

**Option 3 — Store snapshots as the fully upcasted current-schema representation:**
When a snapshot is taken, always serialize it using the current schema — even if the aggregate was loaded from older events. A snapshot taken at T=3 is always in v2 format, regardless of the event history used to reconstruct it. Requires upcasters to be applied at snapshot-take time, but simplifies snapshot read — always deserialize as current schema, no upcasting on read.

Option 3 is the cleanest in practice: snapshots in the current schema, events in their original schema. The upcaster runs once (at snapshot time or during the replay that precedes snapshot) rather than on every aggregate load.

## Section 6: Versioning Governance and Operations

**Q15. How do you enforce schema compatibility in a CI/CD pipeline?**
A: Schema compatibility must be a hard gate in CI — not a best-effort review. The pipeline:

```
Developer pushes schema change
         ↓
CI: Schema compatibility check
  → Fetch current schema version from Schema Registry (or schema file in repo)
  → Run compatibility check: new schema vs. current (and all previous if transitive)
  → Fail build on incompatible change
         ↓ (compatible)
CI: Schema linting
  → Verify required fields have defaults
  → Verify event_type and version fields are present
  → Verify no double type changes
         ↓
CI: Consumer contract tests
  → For each known consumer, verify new schema satisfies consumer's declared contract
  → Pact or similar consumer-driven contract testing framework
         ↓
Deploy producer with new schema
```

**Schema Registry CLI check (Confluent):**
```bash
# In CI, before deploying:
curl -X POST \
  http://schema-registry:8081/compatibility/subjects/payments-value/versions/latest \
  -H "Content-Type: application/json" \
  -d "{ \"schema\": \"$(cat payment_created_v2.avsc | jq -Rs .)\" }" \
| jq '.is_compatible'
# false → fail the build; true → proceed
```

**Consumer-driven contract testing (Pact):**
Each consumer publishes a "pact" — a declaration of which events and which fields it depends on. The producer's CI runs against all consumer pacts before deployment. A producer schema change that removes a field depended on by consumer A fails the contract test for consumer A — surfacing the breakage before deployment rather than at runtime.

This is the production-grade complement to schema compatibility checks: the registry checks structural compatibility; contract tests check behavioral compatibility. A field can be structurally present but semantically meaningless to a consumer — only contract tests catch the difference.

**Q16. What is consumer-driven contract testing and how does it differ from producer-driven schema validation?**
A: **Producer-driven schema validation** (Schema Registry): The producer defines a schema and the registry enforces that new versions are structurally compatible with old ones. The producer is the authority. Consumers are assumed to be able to read anything structurally compatible.

**Consumer-driven contract testing** (Pact, Spring Cloud Contract): Each consumer defines a contract — a specification of which events it consumes and exactly which fields it uses. The producer's test suite verifies that its events satisfy every consumer's contract. The consumer is the authority on what it needs.

```
Consumer A declares:
  "I consume PaymentCreated events and I need: payment_id, amount, currency"
  → Pact file: { event: "PaymentCreated", required_fields: ["payment_id", "amount", "currency"] }

Consumer B declares:
  "I consume PaymentCreated events and I need: payment_id, user_id, merchant_id"
  → Pact file: { event: "PaymentCreated", required_fields: ["payment_id", "user_id", "merchant_id"] }

Producer CI runs against both pacts:
  New schema removes user_id → Consumer B's pact fails → build blocked
  New schema is structurally backward-compatible (user_id has default) → registry check passes
  But consumer B has no default for user_id in its business logic → pact fails → catches real breakage
```

The example illustrates why both are needed: the registry check catches structural incompatibility; the pact check catches behavioral incompatibility (a field is structurally present with a default but the consumer's business logic fails when it gets `null`). Together they form a layered compatibility guarantee.

**Q17. How do you version events in a system that uses JSON without a schema registry?**
A: Without a schema registry, versioning responsibility falls entirely on convention and tooling discipline. The minimum viable approach:

**Embed version in every event:**
```json
{
  "event_id": "evt_uuid_001",
  "event_type": "PaymentCreated",
  "schema_version": 2,
  "occurred_at": "2024-01-15T10:30:00Z",
  "payload": {
    "payment_id": "pay_001",
    "account_id": "usr_42",
    "amount": "500.00",
    "currency": "INR",
    "merchant_id": "merch_42"
  }
}
```

**Store schemas as versioned files in the codebase:**
```
schemas/
  PaymentCreated/
    v1.json    ← JSON Schema for v1
    v2.json    ← JSON Schema for v2
    CHANGELOG.md ← what changed in each version, migration notes
```

**Enforce JSON Schema validation in CI:**
```javascript
// In producer tests
const Ajv = require('ajv');
const schema = require('./schemas/PaymentCreated/v2.json');
const ajv = new Ajv();
const validate = ajv.compile(schema);

test('PaymentCreated event matches v2 schema', () => {
    const event = buildPaymentCreatedEvent();
    expect(validate(event.payload)).toBe(true);
});
```

**Use `additionalProperties: true` in consumer JSON Schema validation** (tolerant reader in schema form):
```json
{
  "type": "object",
  "required": ["payment_id", "amount"],
  "properties": {
    "payment_id": { "type": "string" },
    "amount":     { "type": "string" }
  },
  "additionalProperties": true
}
```
`additionalProperties: true` means unknown fields (new fields added by the producer) don't fail validation. The consumer validates only the fields it cares about.

The honest trade-off: JSON without a schema registry is workable at small scale (2–5 producers and consumers) with disciplined conventions. At larger scale, the manual discipline breaks down — missed version bumps, undocumented changes, schema files getting out of sync with actual events. The operational cost of adopting Avro + Schema Registry is almost always worth it once the system has more than 5–10 event types and more than one team writing producers.

## Section 7: Scenario / System Design Style Questions

**Q18. "Your team is adding a `risk_score` field to the PaymentCreated event. Three downstream teams consume this topic. Walk through the migration safely."**
A:

```
Current state:
  Schema v1: { payment_id, user_id, amount, currency }
  Consumers: Risk-Dashboard, Settlement, Notification (all on v1)

Step 1: Design the v2 schema — backward AND forward compatible
  v2: { payment_id, user_id, amount, currency, risk_score: ["null", "float"] default null }
  ↑ risk_score is optional (union with null), default null
    → Old consumers (v1): field is unknown, ignored (tolerant reader) or default-injected
    → New consumers (v2): field is present and used
  
  Register v2 in Schema Registry:
    POST /subjects/payments-value/versions
    Compatibility check: BACKWARD → compatible ✅ (new optional field with default)

Step 2: Producer deployment
  Payment service ships v2 schema — new events have risk_score populated.
  Old events already in Kafka: still v1, unchanged.
  No consumer coordination required.

Step 3: Consumer migrations (independent, any order)
  Risk-Dashboard team migrates first (they own the feature):
    Update handler to read risk_score from v2 events.
    Old events without risk_score: consumer gets null (default) → handled gracefully.
    New events with risk_score: consumed and displayed.
  
  Settlement team: risk_score irrelevant to them → no change needed ever.
    Their tolerant-reader deserializer ignores the new field silently.
  
  Notification team: may use risk_score for high-risk alerts → migrate when ready.
    Until then: old code, new events → risk_score ignored → no breakage.

Step 4: No cleanup needed
  v2 schema is additive. v1 events remain in Kafka, readable by v2 consumers
  (null default for risk_score). No version deprecation or topic migration needed.

Total coordination required: zero forced simultaneous deployments.
  Producer shipped independently. Three consumers deployed on their own schedules.
```

This is the ideal migration path: an additive, optional field with a sensible default. Real-world migrations are this clean when the schema is designed with evolution in mind from the start (optional fields, null defaults, no required fields without defaults).

**Q19. "A breaking schema change is unavoidable — the `amount` field must be split into `amount` and `currency` (currently currency is implicit). How do you execute this migration with zero consumer downtime?"**
A: Splitting a field is one of the hardest migrations — it cannot be made backward-compatible within a single schema version because the old field carries different semantic information than the new pair. The migration path:

```
Phase 1 — Dual-write (introduce new fields alongside old):
  v1: { payment_id, user_id, amount }          ← amount implicitly INR
  v2: { payment_id, user_id, amount, currency, amount_v1: <same as amount> }

  Producer ships v2:
    amount:    the raw number (same as before) — backward-compatible field, unchanged
    currency:  "INR" for existing flows (single currency), populated from business context
    amount_v1: deprecated alias, same value as amount (belt-and-suspenders for v1 consumers)

  Actually: simpler to just add currency as optional with default "INR":
  v2: { payment_id, user_id, amount, currency: ["null", "string"] default "INR" }

  Old v1 consumers: currency field unknown → ignored (tolerant reader) or default "INR"
  New v2 consumers: read both amount and currency

Phase 2 — Migrate all consumers to v2:
  Each consumer adds currency to its processing logic.
  Old events in Kafka (v1): consumer gets "INR" as default for currency — correct for
  the single-currency legacy period.
  New events (v2): consumer reads actual currency value.

Phase 3 — Formalize: mark amount as currency-explicit and currency as required:
  v3: { payment_id, user_id, amount, currency: string (required, no longer optional) }

  Before deploying v3, all consumers must:
    - Handle currency as a real field (not just the default)
    - Verified in consumer contract tests (pacts assert currency is consumed)

  v3 is a breaking change (currency is now required, not optional).
  Deploy v3 only after all consumers have been verified on v2 and contract tests pass.
  Use the versioned topic if contract test adoption across 3 teams cannot be guaranteed.

Phase 4 — Deprecate v1 events:
  v1 events in Kafka expire naturally per topic retention.
  Once retention window passes, no v1 events remain — upcaster for v1→v2→v3
  can be retired.

Timeline (realistic for a 3-team system):
  Week 1: Ship v2 (optional currency, default "INR")
  Weeks 2-6: Consumer teams add currency handling
  Week 7: Contract tests passing for all consumers
  Week 8: Ship v3 (currency required)
  Week 16 (after 30-day retention): v1 events expired; upcasters retired
```

**Q20. "Your consumer is crashing with deserialization errors after a producer deployed a new schema version. What is your immediate incident response and long-term fix?"**
A:

**Immediate response (minimize consumer downtime):**

```
T+0: Alert fires — consumer group lag climbing, DLQ accumulating errors.

T+5min: Identify the failing events
  → Check consumer logs: which schema ID is causing the failure?
  → GET /schemas/ids/{failing_schema_id} → compare new schema to expected
  → Identify the specific breaking change (new required field? type change? removed field?)

T+10min: Assess rollback options
  Option A — Roll back the producer:
    If the producer can be rolled back (last deployment, no data dependencies on new fields):
    Roll back to previous version. Consumer starts receiving old schema events → resumes.
    Risk: events written during the window with new schema are still in Kafka.
    Those events will fail when consumer encounters them during replay.
    Must handle the mixed-version window.

  Option B — Roll forward the consumer:
    If the breaking change is simple (new required field → add to consumer schema):
    Patch the consumer with tolerant-reader deserialization + null handling for new fields.
    Deploy as hotfix. Consumer resumes processing.
    Correct fix: the consumer should have been updated before the producer deployed.

  Option C — Skip and dead-letter the failing events:
    If neither rollback nor fast consumer fix is immediately available:
    Configure consumer to dead-letter events it cannot deserialize.
    Consumer resumes processing events it can handle.
    DLT accumulates failing events for replay once consumer is fixed.
    Risk: events in DLT are delayed — business processes depending on them are paused.

T+30min: Implement chosen option, verify consumer lag is declining.

T+60min: Resolve all events in DLT via replay once consumer is healthy.
```

**Long-term fix — prevent recurrence:**

```
1. Add schema compatibility check to producer CI pipeline:
   Producer deployment fails if new schema fails Schema Registry compatibility check.
   → Catches the structural breaking change before deployment.

2. Add consumer contract tests:
   Consumer publishes a pact; producer CI runs against all consumer pacts.
   → Catches behavioral breaking changes that structural compatibility allows.

3. Enforce deployment order via feature flags or consumer readiness checks:
   Producer cannot enable new schema until all registered consumers signal readiness.
   Heavyweight — only necessary for very high-stakes schema changes.

4. Add version validation at consumer startup:
   Consumer checks on startup that the current schema version in the registry
   is compatible with the schema version it was compiled against.
   Fail fast at startup rather than at event processing time.
```

The incident's root cause: a producer deployed a schema change without verifying consumer compatibility. The prevention: schema compatibility is a pipeline gate, not a code review suggestion.

## Quick Reference

| Concept | Detail |
|---|---|
| Backward compatibility | New schema reads old events; consumer upgraded first or replaying history |
| Forward compatibility | Old schema reads new events; producer upgraded first; rolling deployments |
| Full compatibility | Both; required for independent deployment of any side |
| Tolerant reader | Consumer ignores unknown fields; `FAIL_ON_UNKNOWN_PROPERTIES=false`; resilient to additive changes |
| Event upcasting | Transform old event version → current version at read time; transparent to handlers |
| Versioned topic | New Kafka topic per major version; for breaking changes; parallel topics during migration |
| Dual-write | Producer writes both old and new fields during migration window; allows independent consumer migration |
| Semantic version change | Same field name, different meaning; invisible to schema tools; requires explicit version bump |
| Consumer-driven contract testing | Consumer declares what it needs; producer CI validates it satisfies every consumer's contract |
| Dead-letter topic (DLT) | Unknown/undeserializable events routed here; consumer continues; events replayed after fix |
| Snapshot versioning | Snapshots must be versioned separately from events; invalidate or upcast on schema change |
| Phase 1 / Phase 2 / Phase 3 | Add new fields → migrate consumers → remove old fields; never skip Phase 2 |
| Schema Registry CI gate | `POST /compatibility/...` in build pipeline; fail on incompatible schema change |
| Idempotent upcasting | Upcast applied twice = same result; required for at-least-once event delivery |

## The Core Mental Model

```
Event versioning = managing the mismatch between producers and consumers
                   across time, deployment order, and team boundaries.

The three rules:
  1. Assume you cannot upgrade all consumers simultaneously.
     → Every schema change must be safe for at least one consumer version
       behind the producer.
  2. Assume events live forever (or at least as long as the retention period).
     → New consumers replaying old events must handle every version ever produced.
  3. Assume consumers will lag behind producers.
     → Forward compatibility protects the window between producer upgrade
       and consumer upgrade.

The safe change sequence for any migration:
  Phase 1: Add new optional fields (producer) → no consumer impact
  Phase 2: Migrate consumers to read new fields → independent, incremental
  Phase 3: Remove old fields (producer) → only after all consumers migrated
  Never: remove or rename a field without Phase 2 completing first.

Compatibility direction cheat sheet:
  Backward = "can I replay old events with new code?"
    → Add fields with defaults: yes. Remove fields: yes (ignored). Change type: no.
  Forward = "can old code read new events?"
    → Add optional fields: yes (ignored). Remove fields: risky. Add required: no.
  Full = both → only additive optional changes are universally safe.

The two hardest changes:
  Rename: always breaking without alias. Use dual-write; never rename directly.
  Semantic change: structurally invisible; change the version number explicitly;
                   document in CHANGELOG; consumer contract tests are the only
                   automated catch.

Tolerant reader + compatible producer = autonomous deployments:
  Producer adds optional field → deploys independently
  Consumer ignores unknown field → no breakage
  Consumer updates to use field → deploys independently
  Producer removes old field → deploys once all consumers migrated
  Zero coordinated cutover required for any additive change.

When in doubt: add, don't change.
  Adding a new field is almost always compatible.
  Changing an existing field is almost always risky.
  If you need to change semantics, add a new field with the new semantics
  and deprecate the old one through the dual-write migration cycle.
```

---

**Tip for the interview:** Event versioning questions at 5 YOE almost always escalate to one of three places: (1) the concrete migration sequence for a breaking change — know the three-phase pattern (add → migrate consumers → remove) cold, and be able to explain why skipping Phase 2 is the root cause of most production schema incidents; (2) the difference between structural compatibility and semantic compatibility — schema tools catch renaming and type changes, but a field that changes meaning without changing name is invisible to every automated check; only consumer-driven contract tests and explicit version bumps catch it; (3) the tolerant reader pattern and why it is the non-negotiable baseline for every consumer — `FAIL_ON_UNKNOWN_PROPERTIES=false` is not optional in an event-driven system, it is what makes autonomous producer deployment safe. The nuance that separates someone who has operated event versioning in production from someone who has only designed it: understanding that the dual-write window is not a temporary hack — it is the correct cost of a safe rename, and its length is determined by how many consumers you have and how fast your teams can deploy, not by how much you want the migration to be done.
