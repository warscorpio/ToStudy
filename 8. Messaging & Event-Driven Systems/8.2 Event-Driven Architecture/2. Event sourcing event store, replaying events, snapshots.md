# Event Sourcing: Event Store, Replaying Events, Snapshots — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is event sourcing?**
A: Event sourcing is an architectural pattern where the state of an application entity is derived entirely from a sequential log of immutable events — rather than storing the current state directly. Instead of a row in a database that is overwritten on every update, you store every state-changing event that has ever occurred, in order. The current state is computed by replaying those events from the beginning.

```
Traditional (state-stored):
  orders table: {id: 42, status: "shipped", amount: 150.00, updated_at: ...}
  ← one row; history is lost; you can't answer "when did it change to shipped?"

Event sourced:
  order_events stream for order 42:
    1. OrderPlaced      {amount: 150.00, items: [...]}
    2. PaymentReceived  {paymentId: "pmt_xyz", amount: 150.00}
    3. OrderShipped     {trackingNumber: "1Z999AA1", carrier: "UPS"}

  Current state = fold(initial_state, events) = {status: "shipped", ...}
  ← full history preserved; any past state reconstructable
```

The event log is the primary source of truth. Current state is a derived projection — a read-optimized view computed from events. This inversion of what is "stored" vs "derived" is the defining characteristic.

**Q2. What are the core motivations for using event sourcing?**
A: Event sourcing solves specific problems that CRUD systems handle poorly:

**Complete audit trail by design** — every state change is recorded as a first-class fact. Regulatory requirements (financial auditing, GDPR data subject access requests, HIPAA) are trivially satisfied. In a CRUD system, an audit trail is bolted on (`updated_by`, `audit_log` table) and is often incomplete. In an event-sourced system, the audit trail is the system.

**Temporal queries** — "what was the state of this order at 2pm yesterday?" is answered by replaying events up to that timestamp. Impossible in a CRUD system without point-in-time snapshots.

**Debugging and root cause analysis** — when something goes wrong, replay the exact event sequence that produced the bad state. In a CRUD system, the state that caused the bug may have been overwritten.

**Event-driven integration** — events are first-class outputs. Other services subscribe to the event stream rather than polling the database. This enables naturally decoupled architectures without a dual-write problem (the event IS the write; derived state is computed from events).

**Retroactive projections** — build a new read model of historical data without ETL. Replay all past events through a new projection handler to populate a new view. In a CRUD system, historical data must be migrated or transformed separately.

**Conflict resolution for concurrent writes** — events record intent rather than final state, enabling optimistic concurrency that is richer than version numbers.

**Q3. What problems does event sourcing introduce?**
A: Event sourcing trades familiar CRUD complexity for distributed-systems complexity:

- **Query complexity** — you cannot simply `SELECT * FROM orders WHERE status = 'shipped'`. Querying current state requires a projection (a read model built from events). Simple queries require upfront infrastructure investment.
- **Eventual consistency** — projections are updated asynchronously; a write is durable when the event is stored, but the read model may lag by milliseconds to seconds. Systems must tolerate this.
- **Schema evolution** — events are immutable and stored forever. Changing an event's schema (renaming a field, removing a field, changing a type) must be handled carefully — old events with old schemas must still be replayable by new code. This is harder than migrating a database column.
- **Replay performance** — replaying thousands of events to reconstruct state is slow. Snapshotting mitigates this (see Section 4) but adds operational complexity.
- **Unfamiliar mental model** — most developers think in CRUD. Event sourcing requires thinking in commands, events, and projections — a significant learning curve for teams.
- **Event ordering** — in distributed systems, ensuring causal ordering of events across aggregates requires coordination.

Event sourcing is not universally better than CRUD — it is a tool for specific problems. Teams that choose it for simple CRUD domains pay a high complexity tax for little benefit.

## Section 2: The Event Store

**Q4. What is an event store and what are its core requirements?**
A: An event store is the durable, append-only log that persists events. It is the heart of an event-sourced system — all other components (projections, read models, snapshots) are derived from it.

Core requirements:

**Append-only writes** — events are never updated or deleted. The store only supports inserting new events at the end of a stream. This immutability is foundational: it guarantees that the past is preserved exactly as it happened.

**Stream-based organization** — events are organized into streams, one per aggregate instance (e.g., `order-42`, `account-789`). Reading an aggregate's history means reading its stream from beginning to current.

**Optimistic concurrency control** — when appending events, the writer specifies the expected version (position) of the stream. If the stream has been written to by another process concurrently, the append fails. This prevents lost-update races:
```
Process A reads order-42 at version 5 → appends event at version 6 (expected: 5) ✓
Process B reads order-42 at version 5 → appends event at version 6 (expected: 5) ✗
  → WrongExpectedVersionException → B must re-read, re-process, re-try
```

**Ordered reads** — events within a stream are always returned in append order (causal order). The store must preserve this ordering durably.

**Global ordering / position** — a global sequence number or position across all streams enables subscribers (projections) to process all events in the order they were appended, across all aggregates.

**Subscriptions / change feed** — projections subscribe to the event store to receive new events as they are appended. This push model is more efficient than polling.

**Q5. What storage technologies can serve as an event store?**
A: Several options, each with different trade-offs:

**EventStoreDB (purpose-built):**
- Designed specifically for event sourcing. Native stream concept; built-in subscriptions (catch-up, persistent); optimistic concurrency via `expectedRevision`; projections engine built in.
- Best choice when starting an event-sourced system — fewest compromises, richest event-sourcing primitives.
- Less familiar tooling; smaller ecosystem than general-purpose databases.

**PostgreSQL (append-only table):**
- Familiar; transactional; excellent tooling. The event store is an append-only table:
```sql
CREATE TABLE events (
  id              BIGSERIAL PRIMARY KEY,        -- global ordering
  stream_id       TEXT NOT NULL,                -- aggregate identity
  stream_version  INT NOT NULL,                 -- position within stream
  event_type      TEXT NOT NULL,
  payload         JSONB NOT NULL,
  metadata        JSONB,
  occurred_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (stream_id, stream_version)            -- optimistic concurrency constraint
);
CREATE INDEX ON events(stream_id, stream_version);
CREATE INDEX ON events(id);                     -- global ordering for projections
```
Optimistic concurrency: `INSERT INTO events (stream_id, stream_version, ...) VALUES ('order-42', 6, ...)` — if another process already inserted version 6 for `order-42`, the `UNIQUE (stream_id, stream_version)` constraint raises a unique violation, which the application handles as a concurrency conflict. Subscriptions use `LISTEN/NOTIFY` or polling on the `id` sequence.

**Kafka (as an event log):**
- Partitioned, distributed, highly durable. Each Kafka topic (or partition) is an immutable log — naturally suited to event sourcing at scale.
- Caveats: no stream-level optimistic concurrency (Kafka has no compare-and-set per key); each partition is ordered but per-aggregate ordering requires routing all events for an aggregate to the same partition (by key); retention is time/size-based rather than infinite.
- Best for: high-throughput event systems where the event log is also the integration bus. Less ideal for precise per-aggregate concurrency control.

**DynamoDB (with version attribute):**
- NoSQL; horizontally scalable. Each item represents one event; `(aggregateId, version)` as composite key. Conditional writes (`ConditionExpression: "attribute_not_exists(version)"`) enforce optimistic concurrency.
- Good for: AWS-native stacks at high scale. Less convenient for range queries (replay requires querying a partition key range).

**Q6. What is the event schema and what metadata should every event carry?**
A:

```typescript
interface StoredEvent {
  // Identity
  eventId:       string;      // UUID; globally unique; idempotency key for projections
  streamId:      string;      // aggregate identity: "order-42", "account-789"
  streamVersion: number;      // position within the aggregate's stream (1-based)
  globalPosition: number;     // position in the global event log (auto-increment)

  // Classification
  eventType:     string;      // "OrderPlaced", "PaymentReceived", "OrderShipped"
  schemaVersion: number;      // version of this event type's schema; for evolution

  // Content
  payload:       object;      // the event's data (domain-specific)
  metadata: {
    causationId:   string;    // ID of the command that caused this event
    correlationId: string;    // trace ID spanning the entire operation
    userId:        string;    // who triggered the action
    timestamp:     string;    // ISO 8601; when the event occurred (not when stored)
  };

  // Storage
  storedAt:      string;      // when the event was persisted (may differ from occurred_at)
}

// Example: OrderPlaced event
{
  eventId:       "evt_01H9K...",
  streamId:      "order-42",
  streamVersion: 1,
  globalPosition: 50042,
  eventType:     "OrderPlaced",
  schemaVersion: 2,
  payload: {
    customerId:  "cust-789",
    items: [{ productId: "prod-1", quantity: 2, unitPrice: 49.99 }],
    currency:    "USD",
    totalAmount: 99.98
  },
  metadata: {
    causationId:   "cmd_PlaceOrder_abc123",
    correlationId: "req_xyz456",
    userId:        "user-789",
    timestamp:     "2024-07-23T14:03:00.000Z"
  },
  storedAt: "2024-07-23T14:03:00.042Z"
}
```

`causationId` and `correlationId` are critical for distributed tracing — they allow reconstruction of which command triggered which events across multiple aggregates.

**Q7. How does optimistic concurrency control prevent write conflicts in the event store?**
A: When a command handler loads an aggregate, it reads events up to the current stream version and reconstructs the aggregate's state. It then executes business logic and produces new events. Before appending, it specifies the version it read — the `expectedVersion`. If another process has appended events to the same stream since this process read it, the append fails:

```typescript
async function handleCommand(command: PlaceOrderCommand): Promise<void> {
  // Load aggregate — reads all events for this stream
  const { aggregate, version } = await loadAggregate('order', command.orderId);

  // Execute business logic — may throw domain exceptions
  const newEvents = aggregate.execute(command);

  // Append — will fail if stream has been written to since we read version
  await eventStore.appendEvents({
    streamId:        `order-${command.orderId}`,
    events:          newEvents,
    expectedVersion: version,    // optimistic lock
  });
  // If another process appended first: throws WrongExpectedVersionException
  // Caller retries: re-load aggregate (gets new events), re-execute command
}
```

The retry loop is correct for most conflicts (two independent commands on the same aggregate arriving simultaneously). Some commands are not safe to retry automatically — a "charge payment" command that failed due to a concurrent update should not be silently retried, as the retry may double-charge. Flag such commands for application-level retry policies.

## Section 3: Aggregates and Events

**Q8. What is an aggregate in event sourcing, and how is it different from a database entity?**
A: An aggregate (from Domain-Driven Design) is a cluster of domain objects that is treated as a single unit for data changes. In event sourcing, an aggregate:

- **Owns a stream of events** — the stream `order-42` belongs exclusively to the Order aggregate with ID 42.
- **Derives its state by replaying its events** — its current state is computed by folding events, not read from a table.
- **Validates commands against current state** — before emitting new events, the aggregate checks that the command is valid given what has already happened.
- **Emits events, never directly modifies external state** — the aggregate produces event objects; the infrastructure appends them to the store.

```typescript
class Order {
  id: string;
  status: 'pending' | 'paid' | 'shipped' | 'cancelled';
  amount: number;
  version: number = 0;

  // Reconstruct state from events (the "apply" pattern)
  static fromEvents(events: StoredEvent[]): Order {
    const order = new Order();
    for (const event of events) {
      order.apply(event);
    }
    return order;
  }

  private apply(event: StoredEvent): void {
    this.version++;
    switch (event.eventType) {
      case 'OrderPlaced':
        this.id = event.payload.orderId;
        this.status = 'pending';
        this.amount = event.payload.totalAmount;
        break;
      case 'PaymentReceived':
        this.status = 'paid';
        break;
      case 'OrderShipped':
        this.status = 'shipped';
        break;
      case 'OrderCancelled':
        this.status = 'cancelled';
        break;
    }
  }

  // Validate command against current state; return new events
  ship(command: ShipOrderCommand): StoredEvent[] {
    if (this.status !== 'paid') {
      throw new DomainError(`Cannot ship order in status ${this.status}`);
    }
    return [{
      eventType: 'OrderShipped',
      payload: { trackingNumber: command.trackingNumber, carrier: command.carrier }
    }];
  }
}
```

The key distinction from a database entity: the Order class has no `save()` method that writes to a table. It only produces events. The aggregate's state is entirely reconstructed from its event history on each load — it has no identity in the database beyond its event stream.

**Q9. How do you handle events that span multiple aggregates (cross-aggregate consistency)?**
A: The aggregate boundary is the unit of strong consistency — within one aggregate's stream, events are strictly ordered and optimistic concurrency prevents conflicts. Across aggregates, you get eventual consistency at best.

**Within one aggregate (strongly consistent):**
An Order and its Payment can be modeled as one aggregate if they always change together. But this couples them permanently and makes the aggregate large — generally discouraged.

**Across aggregates (eventual consistency via sagas/process managers):**
The standard approach: each aggregate manages its own consistency; cross-aggregate workflows are coordinated by sagas (long-running process managers that react to events and issue commands):

```
Order aggregate emits: OrderPlaced
        │
        ▼
Saga: PaymentSaga listens for OrderPlaced
  → Issues command: InitiatePayment to Payment aggregate
        │
Payment aggregate emits: PaymentCompleted or PaymentFailed
        │
        ▼
Saga: Receives PaymentCompleted
  → Issues command: ConfirmOrder to Order aggregate
        │
Order aggregate emits: OrderConfirmed
```

The saga itself is often event-sourced — its state is a series of events recording which commands it has sent and which responses it has received. This makes the saga recoverable: on crash, it replays its events to determine where it was and what to do next.

**Compensating transactions for rollback:**
If PaymentFailed arrives, the saga issues a CancelOrder command. There is no distributed rollback — instead, a compensating event (`OrderCancelled`) undoes the business effect of the original (`OrderPlaced`). The event log retains both the original and the compensation — the history is preserved.

## Section 4: Replaying Events

**Q10. What does "replaying events" mean and what are its use cases?**
A: Replaying events means reading a stream (or the entire event log) from a given position and processing each event in order, as if re-executing history. It is one of the most powerful capabilities of event sourcing.

**Use cases:**

**Reconstructing aggregate state (per-request):**
Every time a command arrives for aggregate `order-42`, the system replays its event stream to reconstruct the current state before executing the command. This is the most frequent form of replay — it happens for every write operation.

**Rebuilding a projection (read model):**
A projection is a denormalized read model optimized for querying (e.g., an `orders` table with `status`, `customer_name`, `total`). When a bug in the projection handler is fixed, or a new query pattern is needed, the projection is dropped and rebuilt by replaying all events through the corrected handler. The event log is the source of truth; the projection is disposable.

**Migrating to a new read model technology:**
If you decide to move from a PostgreSQL read model to Elasticsearch, replay all events through an Elasticsearch indexer. No ETL; no data migration scripts.

**Temporal queries:**
Replay events up to a specific timestamp or version to answer "what was the state of order-42 at 3pm yesterday?" Standard databases cannot answer this without point-in-time recovery; event-sourced systems answer it with a replay to a version or timestamp filter.

**Debugging:**
Replay the exact event sequence that preceded a bug. The system's behavior at any point in history can be reproduced deterministically.

**Q11. How do you implement event replay for rebuilding a projection?**
A: A projection rebuild reads events from the global log (not per-stream) and processes them through the projection handler:

```typescript
class OrdersProjectionRebuilder {
  constructor(
    private eventStore: EventStore,
    private db: Database
  ) {}

  async rebuild(): Promise<void> {
    // 1. Drop and recreate the projection table
    await this.db.query('TRUNCATE TABLE orders_projection');

    // 2. Read all events from global position 0, in batches
    let position = 0;
    const batchSize = 1000;

    while (true) {
      const events = await this.eventStore.readAll({
        fromPosition: position,
        limit: batchSize,
        eventTypes: ['OrderPlaced', 'PaymentReceived', 'OrderShipped', 'OrderCancelled']
        // filter to relevant event types; skip unrelated domain events
      });

      if (events.length === 0) break;

      // 3. Process each event through the projection handler
      for (const event of events) {
        await this.handleEvent(event);
      }

      position = events[events.length - 1].globalPosition + 1;
      console.log(`Rebuilt to position ${position}`);
    }

    console.log('Projection rebuild complete');
  }

  private async handleEvent(event: StoredEvent): Promise<void> {
    switch (event.eventType) {
      case 'OrderPlaced':
        await this.db.query(
          `INSERT INTO orders_projection (id, customer_id, status, amount, placed_at)
           VALUES ($1, $2, 'pending', $3, $4)
           ON CONFLICT (id) DO NOTHING`,
          [event.payload.orderId, event.payload.customerId,
           event.payload.totalAmount, event.metadata.timestamp]
        );
        break;
      case 'PaymentReceived':
        await this.db.query(
          `UPDATE orders_projection SET status = 'paid' WHERE id = $1`,
          [event.streamId.replace('order-', '')]
        );
        break;
      case 'OrderShipped':
        await this.db.query(
          `UPDATE orders_projection
           SET status = 'shipped', tracking_number = $2 WHERE id = $1`,
          [event.streamId.replace('order-', ''), event.payload.trackingNumber]
        );
        break;
    }
  }
}
```

**Q12. How do you rebuild a projection without downtime (blue/green projection rebuild)?**
A: Rebuilding a projection by truncating and replaying means the read model is unavailable (or stale) during the rebuild. For production systems with continuous traffic, use a blue/green approach:

```
Step 1: Create a new projection table (shadow)
  CREATE TABLE orders_projection_v2 (same schema as v1, or new schema)

Step 2: Replay all historical events into orders_projection_v2
  (While this runs, orders_projection_v1 continues serving queries)

Step 3: Continue tracking new events
  Once historical replay reaches the present, switch to live subscription mode:
  subscribe to new events as they arrive and apply them to both v1 and v2

Step 4: Verify v2
  Run consistency checks: row counts match? Sample records match? Spot-check queries?

Step 5: Atomic swap
  UPDATE projection_registry SET active_table = 'orders_projection_v2'
  (application reads from the active table name in the registry)
  OR rename tables atomically:
    ALTER TABLE orders_projection RENAME TO orders_projection_v1_old;
    ALTER TABLE orders_projection_v2 RENAME TO orders_projection;

Step 6: Drop old table
  DROP TABLE orders_projection_v1_old;
```

The dual-write window (Step 3) is the critical phase — new events must be applied to both tables while the historical replay catches up to the current position. The gap between "end of historical replay" and "present" must be closed before the swap. In practice, the rebuild will eventually catch up because historical events don't accumulate faster than current events (the historical replay is a finite catch-up, not a growing gap).

**Q13. How do you handle schema evolution of events during replay?**
A: Events are immutable — the `OrderPlaced` event stored 3 years ago with `schemaVersion: 1` cannot be changed. But the code that processes it can evolve. Two complementary strategies:

**Upcasting (at read time):**
When reading an old event from the store, transform it to the current schema before passing it to the aggregate or projection handler. The upcaster is a pure function: `oldEvent → newEvent`.

```typescript
class OrderPlacedUpcaster {
  upcast(event: StoredEvent): StoredEvent {
    if (event.schemaVersion === 1) {
      // v1 had 'price' instead of 'totalAmount'
      return {
        ...event,
        schemaVersion: 2,
        payload: {
          ...event.payload,
          totalAmount: event.payload.price,  // rename field
          currency: 'USD',                   // add default for missing field
          price: undefined
        }
      };
    }
    return event;  // already current schema
  }
}
```

Upcasters are chained — `v1 → v2 → v3` — so code only ever handles the current schema version. Upcasters are pure functions with no side effects; they can be tested in isolation.

**Event versioning in the type name:**
Name events with version suffixes: `OrderPlaced_v1`, `OrderPlaced_v2`. Old handlers still registered for `_v1`; new handlers registered for `_v2`. Both coexist in the system. Simpler than upcasting for breaking changes; requires the handler registry to support both names.

**Copy-and-transform (for major breaking changes):**
For a truly incompatible schema change, append a new corrected event to the relevant streams: `OrderPlacedCorrected` with the new schema. The aggregate's `apply()` method handles the corrected event. The original malformed events remain in the log but are superseded by the correction event.

## Section 5: Snapshots

**Q14. What is a snapshot in event sourcing and why is it needed?**
A: A snapshot is a point-in-time capture of an aggregate's state — a serialized checkpoint at a specific stream version. Instead of replaying all N events from the beginning of a stream to reconstruct the aggregate, the system loads the latest snapshot (which represents the aggregate's state at version M) and replays only the events from version M+1 to current (N - M events).

```
Without snapshots (N=10,000 events):
  Load order-42: replay all 10,000 events → reconstruct state
  Time: O(N) = slow for long-lived aggregates

With snapshot at version 9,950:
  Load order-42:
    1. Load snapshot at version 9,950 → state at that point
    2. Replay events 9,951–10,000 (50 events) → current state
  Time: O(snapshot_load + delta_events) = fast regardless of total history
```

Snapshots are an optimization, not a correctness requirement. A system without snapshots is correct — it just becomes slower as aggregates accumulate more events. Snapshots are needed when:
- Aggregates have many events (hundreds or thousands per instance).
- Command processing latency is sensitive to load time.
- The aggregate is loaded frequently (high-read patterns).

**Q15. When and how do you create snapshots?**
A: Snapshots are created by triggers — rules that decide when the current state is worth checkpointing:

**Event-count trigger (most common):**
After every N events appended to a stream, create a snapshot. N is tuned per aggregate type:
```typescript
const SNAPSHOT_EVERY_N_EVENTS = 50;

async function appendEventsWithSnapshotting(
  streamId: string,
  newEvents: DomainEvent[],
  aggregate: Order,
  currentVersion: number
): Promise<void> {
  await eventStore.appendEvents({ streamId, events: newEvents, expectedVersion: currentVersion });
  const newVersion = currentVersion + newEvents.length;

  if (newVersion % SNAPSHOT_EVERY_N_EVENTS === 0) {
    await snapshotStore.save({
      streamId,
      version: newVersion,
      state: aggregate.toSnapshot(),
      takenAt: new Date().toISOString()
    });
  }
}
```

**Time-based trigger:**
Create a snapshot every hour or every day, regardless of event count. Useful for aggregates with irregular activity — a customer account that has been dormant for a year and suddenly becomes active benefits from a snapshot even if it hasn't had 50 events recently.

**On-demand (for infrequently loaded aggregates):**
Create a snapshot the first time an old aggregate is loaded after a long period of inactivity. Pay the full replay cost once; subsequent loads use the snapshot.

**Q16. Where are snapshots stored and what do they contain?**
A: Snapshots are stored separately from the event log — they are cached state, not immutable facts. They can be deleted and recreated at any time without losing any information (the event log remains the source of truth).

Storage options:
- **Separate database table** — `snapshots(stream_id, version, state JSONB, taken_at)`. Queryable; easy to inspect and delete. Recommended.
- **Object storage (S3/GCS)** — for large aggregate states. Key: `snapshots/{stream_id}/v{version}.json`. Cheap; infinite retention. Slightly higher latency than a DB lookup.
- **Redis** — for frequently accessed aggregates needing sub-millisecond snapshot load. TTL-based expiry; not durable (evicted snapshots are recreated from events). Good as a cache layer on top of a durable store.

Schema:
```sql
CREATE TABLE snapshots (
  stream_id    TEXT NOT NULL,
  version      INT NOT NULL,
  state        JSONB NOT NULL,       -- serialized aggregate state
  schema_ver   INT NOT NULL,         -- snapshot schema version (for evolution)
  taken_at     TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (stream_id, version)
);
CREATE INDEX ON snapshots(stream_id, version DESC);  -- find latest snapshot
```

Snapshot state content:
```json
{
  "id": "42",
  "status": "paid",
  "amount": 150.00,
  "customerId": "cust-789",
  "items": [...],
  "version": 9950
}
```

The `version` field in the snapshot state is critical — it tells the loading code which event to start replaying from (`version + 1`).

**Q17. How does the aggregate loading algorithm work with snapshots?**
A:

```typescript
async function loadAggregate(streamId: string): Promise<{ aggregate: Order; version: number }> {
  // Step 1: try to load the latest snapshot
  const snapshot = await snapshotStore.loadLatest(streamId);

  let aggregate: Order;
  let fromVersion: number;

  if (snapshot) {
    // Restore state from snapshot
    aggregate = Order.fromSnapshot(snapshot.state);
    fromVersion = snapshot.version + 1;   // replay events AFTER the snapshot
  } else {
    // No snapshot; replay from the beginning
    aggregate = new Order();
    fromVersion = 1;
  }

  // Step 2: load events since the snapshot (or from beginning if no snapshot)
  const events = await eventStore.readStream(streamId, { fromVersion });

  // Step 3: apply remaining events
  for (const event of events) {
    aggregate.apply(event);
  }

  const currentVersion = snapshot
    ? snapshot.version + events.length
    : events.length;

  return { aggregate, version: currentVersion };
}
```

This is the standard load algorithm — try snapshot first, replay delta. Correctness: if no snapshot exists, `fromVersion = 1` causes full replay (identical to a snapshot-free system). If the snapshot is stale (events have occurred since it was taken), those events are replayed on top. The algorithm degrades gracefully whether snapshots exist or not.

**Q18. How do you handle snapshot schema evolution?**
A: Snapshots are not immutable like events — they can be deleted and recreated. But a snapshot created with schema version 1 may be unreadable after the aggregate's state schema changes:

**Strategy 1: Invalidate old snapshots on schema change.**
Set `schema_ver` on the snapshot. When loading, check `snapshot.schema_ver == CURRENT_SCHEMA_VERSION`. If not, discard the snapshot and replay from events. The next save will create a fresh snapshot with the new schema. Snapshots self-heal automatically.

```typescript
const CURRENT_SNAPSHOT_SCHEMA_VERSION = 3;

if (snapshot && snapshot.schema_ver !== CURRENT_SNAPSHOT_SCHEMA_VERSION) {
  snapshot = null;  // discard; replay from events
}
```

**Strategy 2: Upcast snapshots.**
Write a snapshot upcaster (analogous to event upcasters) that transforms old snapshot schemas to the current one. More complex; useful when the full event replay is very expensive (thousands of events) and you want to avoid it on every schema change.

**Strategy 3: Delete all snapshots on schema change (simplest).**
```sql
DELETE FROM snapshots;  -- they'll be recreated on next load
```
Crude but correct. The event log is untouched; performance degrades briefly (every aggregate load is a full replay) but recovers as new snapshots are created.

In practice, Strategy 1 is the most common — the code change that bumps `CURRENT_SNAPSHOT_SCHEMA_VERSION` automatically triggers fresh snapshots for any aggregate loaded after the deployment.

## Section 6: Scenario Questions

**Q19. "You inherit an event-sourced system where some aggregates have 100,000+ events in their stream. Command latency is 8 seconds. What do you do?"**
A: 8 seconds to load an aggregate with 100,000 events means the system is replaying all 100,000 events on every command. This is a pure snapshotting gap.

**Immediate fix — retroactive snapshot generation:**

Don't wait for natural snapshot triggers (new events). Write a one-time backfill job:

```typescript
async function backfillSnapshots(streamIds: string[]): Promise<void> {
  for (const streamId of streamIds) {
    const events = await eventStore.readStream(streamId);
    const aggregate = Order.fromEvents(events);

    await snapshotStore.save({
      streamId,
      version: events.length,
      state: aggregate.toSnapshot(),
      schema_ver: CURRENT_SNAPSHOT_SCHEMA_VERSION,
      takenAt: new Date().toISOString()
    });

    console.log(`Snapshotted ${streamId} at version ${events.length}`);
  }
}
```

Run this offline against all streams with > 500 events. After the backfill, every aggregate load reads the snapshot + at most 50 delta events → sub-100ms load time.

**Ongoing fix — reduce snapshot interval:**
Set `SNAPSHOT_EVERY_N_EVENTS = 50` (not the default 100 or 500). For aggregates with high event rates, even 50 events of delta replay is fast.

**Structural investigation:**
100,000 events per aggregate stream is a signal that the aggregate boundary may be too coarse. If an `Account` aggregate emits an event for every micro-transaction, accumulating 100k events over time, consider whether some events should be on child aggregates (`MonthlyStatement`, `TransactionBatch`) that are smaller and shorter-lived. The snapshot solves the immediate performance problem; the correct aggregate design prevents it in the future.

**Q20. "You need to add a new field (`shippingRegion`) to the read model. This field is derivable from the delivery address in the `OrderPlaced` event. How do you populate this for all existing and future orders?"**
A: This is a projection rebuild — the read model needs a new field derived from a historical event. The event log already contains all the data needed (delivery address in `OrderPlaced`); the read model just hasn't been extracting it.

**Step 1: Update the projection handler** to extract `shippingRegion` from `OrderPlaced.payload.deliveryAddress`:

```typescript
case 'OrderPlaced':
  await db.query(
    `INSERT INTO orders_projection
       (id, customer_id, status, amount, placed_at, shipping_region)
     VALUES ($1, $2, 'pending', $3, $4, $5)
     ON CONFLICT (id) DO UPDATE SET shipping_region = EXCLUDED.shipping_region`,
    [payload.orderId, payload.customerId, payload.totalAmount,
     metadata.timestamp, deriveRegion(payload.deliveryAddress)]
  );
  break;
```

**Step 2: Add the column to the projection table:**
```sql
ALTER TABLE orders_projection
  ADD COLUMN shipping_region TEXT;
-- Nullable initially; will be populated during backfill
```

**Step 3: Backfill via projection rebuild** (using the blue/green approach):
- Create `orders_projection_v2` with `shipping_region NOT NULL DEFAULT 'UNKNOWN'`.
- Replay all historical `OrderPlaced` events into `orders_projection_v2`.
- Switch the application to use `orders_projection_v2`.

The key insight: no data migration scripts, no ETL pipelines, no joins against external address databases. The `OrderPlaced` event already contains the delivery address — the event log is the only source needed. This is the retroactive projection capability that makes event sourcing powerful for evolving read models.

**Q21. "A developer accidentally produced a `PaymentProcessed` event with the wrong amount (1000x too high) to 500 order streams. How do you correct this in an event-sourced system?"**
A: Events are immutable — the wrong events cannot be deleted or modified. The correct approach is compensation events:

**Step 1: Identify affected streams**
Query the event store for all `PaymentProcessed` events in the affected time window with the inflated amount:
```sql
SELECT stream_id, stream_version, payload
FROM events
WHERE event_type = 'PaymentProcessed'
  AND stored_at BETWEEN '2024-07-23T14:00:00Z' AND '2024-07-23T14:05:00Z'
  AND (payload->>'amount')::numeric > 10000;
-- Returns 500 rows
```

**Step 2: Append correction events**
For each affected stream, append a `PaymentAmountCorrected` event (a new domain event type) with the correct amount and a reference to the erroneous event:
```typescript
for (const badEvent of affectedEvents) {
  await eventStore.appendEvents({
    streamId: badEvent.streamId,
    events: [{
      eventType: 'PaymentAmountCorrected',
      payload: {
        originalEventId: badEvent.eventId,
        originalAmount:  badEvent.payload.amount,
        correctedAmount: badEvent.payload.amount / 1000,
        reason:          'data_entry_error_2024_07_23'
      }
    }],
    expectedVersion: currentVersionOf(badEvent.streamId)
  });
}
```

**Step 3: Update aggregate `apply()` to handle `PaymentAmountCorrected`**
```typescript
case 'PaymentAmountCorrected':
  this.amount = event.payload.correctedAmount;
  break;
```

**Step 4: Rebuild affected projections**
The orders projection for the 500 affected orders now needs to be updated. Options:
- Replay only the affected streams (not the full global replay).
- Publish `PaymentAmountCorrected` events to the projection subscription; the live projection handler updates the read model in real time.

**Step 5: Audit trail**
The event log now contains both the erroneous event AND the correction event. The full history of the mistake and its resolution is preserved — regulatory requirements are satisfied. The erroneous event is not hidden; it is contextually superseded by the correction.

This is the event-sourcing answer to "what do you do when you write bad data?" — you never lie about the past; you record what happened AND what corrected it. The audit trail is complete and honest.

## Quick Reference

| Concept | Definition | Key detail |
|--- |--- |--- |
| Event sourcing | State derived from immutable event log | Events are the source of truth; current state is derived |
| Aggregate | Domain entity that owns an event stream | Reconstructed by replaying its stream; enforces business rules |
| Event store | Append-only durable log of events | Optimistic concurrency via `expectedVersion`; immutable |
| Stream | Ordered sequence of events for one aggregate | `stream_id` = aggregate identity; `stream_version` = position |
| Optimistic concurrency | `expectedVersion` check on append | Prevents lost-update races; caller retries on conflict |
| Projection | Read-optimized view derived from events | Disposable; rebuilt by replaying events; eventually consistent |
| Replay | Re-processing events in order | Used for: state reconstruction, projection rebuild, debugging |
| Blue/green rebuild | Rebuild projection into shadow table; swap | Zero-downtime projection migration |
| Snapshot | Checkpoint of aggregate state at version N | Optimization: load snapshot + replay delta instead of full stream |
| Snapshot trigger | After N events, or time-based | `N=50–200` events is typical; tune per aggregate |
| Upcasting | Transform old event schema to current at read time | Chained: v1→v2→v3; pure function; never modifies stored event |
| Compensation event | New event that semantically reverses a past event | Preserves history; never deletes or modifies past events |
| Saga | Process manager coordinating cross-aggregate workflows | Reacts to events; issues commands; itself event-sourced |
| `causationId` | ID of command that caused this event | Enables causal tracing across aggregates |

---

**Tip for the interview:** Event sourcing questions at 5 YOE level probe whether you understand the operational realities, not just the pattern definition. Lead with the trade-offs — audit trail, temporal queries, and retroactive projections are the genuine benefits; query complexity, eventual consistency, and schema evolution are the genuine costs. The questions that separate senior answers: explaining upcasting as the correct solution to event schema evolution (not "don't change events"), walking through the blue/green projection rebuild for zero-downtime migrations, and articulating why snapshots are an optimization not a correctness mechanism (the event log is always the source of truth; snapshots can always be discarded and recreated). For compensation events, the critical point is that event sourcing never lies about the past — a correction is a new event, not a mutation of an old one. If the interviewer asks "when would you NOT use event sourcing?" the honest answer is: simple CRUD domains, teams unfamiliar with eventual consistency, or systems where the query flexibility of event sourcing is not needed — the pattern's complexity must be justified by the problem it solves.
