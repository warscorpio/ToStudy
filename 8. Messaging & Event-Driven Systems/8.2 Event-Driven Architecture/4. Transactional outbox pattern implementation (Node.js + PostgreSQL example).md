# Transactional Outbox Pattern Implementation (Node.js + PostgreSQL) — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem the Pattern Solves

**Q1. What specific failure does the transactional outbox pattern prevent?**
A: The outbox pattern prevents the **dual-write problem**: the scenario where a service must atomically update a database record AND publish a message to a message broker (Kafka, RabbitMQ, SNS), but these two operations cannot be wrapped in a single ACID transaction because they involve two separate systems.

The failure without the pattern:

```
// BROKEN: two separate writes with no atomicity guarantee
await db.query('UPDATE orders SET status = $1 WHERE id = $2', ['CONFIRMED', orderId]);
await kafka.produce('order-confirmed', { orderId });  // what if THIS crashes?
```

Four failure modes this creates:

- **Crash between writes** — the order is marked CONFIRMED in the database, but Kafka never receives the event. Downstream services (inventory, shipping, notifications) never process the order. The database says "confirmed"; the rest of the system doesn't know.
- **Kafka unavailable** — the database write succeeds; the Kafka publish fails with a connection error. Same outcome as above — silent divergence between database state and event state.
- **Rollback without retract** — the database transaction rolls back (a constraint violation, a concurrent update conflict), but the Kafka message was already sent. Downstream systems process an event for an order that was never actually confirmed.
- **Non-deterministic ordering** — under high concurrency, the database write and the Kafka publish may reach their respective systems in different orders for concurrent requests, causing downstream consumers to see events in a different order than the database reflects.

The outbox pattern eliminates all four by making the message publication part of the same database transaction as the state change — atomicity is guaranteed by the database, not by coordination between two systems.

**Q2. Why can't you just use a distributed transaction (2PC) to coordinate the database write and the Kafka publish?**
A: Two reasons — one practical, one architectural:

**Practical:** Kafka does not support XA transactions (the standard distributed transaction protocol). It cannot participate as a resource manager in a 2PC transaction coordinated by an application server or a transaction manager. Even if it did, Kafka's exactly-once transactional API is scoped to Kafka-to-Kafka operations — it doesn't span Kafka and an external database in a single atomic unit.

**Architectural:** even where 2PC is technically possible (e.g., coordinating between a database and another database), it introduces the coordinator blocking problem (a crashed coordinator leaves participants locked indefinitely), adds significant latency (two round-trips per transaction), and creates tight coupling between systems that should be independently deployable and scalable. The distributed systems community has largely moved away from 2PC for cross-service coordination in favor of patterns like the outbox that use local ACID transactions as the atomicity primitive and achieve cross-system consistency eventually.

The outbox pattern's insight: you don't need 2PC if you can make the message publication a side effect of the database transaction itself. Write the message to a table in the same database, commit atomically, and let a separate process relay the message. The eventual publication is guaranteed by the persistence of the outbox record.

**Q3. What is the core invariant the outbox pattern maintains?**
A: The core invariant: **if a state change is committed to the database, the corresponding event will eventually be published to the message broker. If the state change is rolled back, no event is published.**

This invariant holds because:
- The outbox record and the state change are written in the same database transaction. They commit or roll back together — atomically, by the database engine.
- The relay process that publishes outbox events to the broker only publishes events that have been committed. It reads from the outbox table and publishes each record exactly once (with at-least-once delivery and idempotent consumers).
- If the relay crashes after publishing but before marking the event as published, it re-publishes on restart — a duplicate delivery, but not a missed delivery. This gives **at-least-once event delivery**, which when combined with idempotent consumers achieves exactly-once processing.

The invariant does NOT hold if:
- The outbox write and the state change are in separate transactions (a coding error).
- The relay deletes outbox events before confirming the broker has acknowledged them.
- The relay's "mark as published" step and the broker publish are not ordered correctly (mark first = at-most-once; publish first, then mark = at-least-once).

## Section 2: Schema Design

**Q4. What does the outbox table schema look like, and what does each column do?**
A:

```sql
CREATE TABLE outbox_events (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_type  TEXT NOT NULL,
    aggregate_id    TEXT NOT NULL,
    event_type      TEXT NOT NULL,
    payload         JSONB NOT NULL,
    status          TEXT NOT NULL DEFAULT 'PENDING',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at    TIMESTAMPTZ,
    attempts        INT NOT NULL DEFAULT 0,
    last_error      TEXT,
    idempotency_key TEXT UNIQUE,

    CONSTRAINT valid_status CHECK (status IN ('PENDING', 'PUBLISHED', 'FAILED', 'DEAD'))
);

-- Index for the relay process: fetch pending events in creation order
CREATE INDEX idx_outbox_pending ON outbox_events (created_at ASC)
    WHERE status = 'PENDING';

-- Index for monitoring / retry queries
CREATE INDEX idx_outbox_status_created ON outbox_events (status, created_at);
```

Column rationale:

- **`id`** — UUID primary key. Used as the Kafka message key (or included in the message header) to enable downstream idempotency checks by consumers.
- **`aggregate_type` + `aggregate_id`** — the business entity this event concerns (`'Order'`, `'12345'`). Enables filtering and routing. The Kafka partition key is often derived from `aggregate_id` to preserve per-entity ordering.
- **`event_type`** — the semantic name of the event: `'OrderConfirmed'`, `'PaymentProcessed'`, `'UserCreated'`. Consumers route on this field.
- **`payload`** — the full event payload as JSONB. Self-contained — the consumer should not need to query the database to process the event. Include all fields the consumer needs.
- **`status`** — lifecycle state: `PENDING` (not yet published), `PUBLISHED` (successfully published and acknowledged by broker), `FAILED` (publish attempted, broker error), `DEAD` (exceeded max retry attempts, requires manual intervention).
- **`created_at`** — controls relay ordering (publish in creation order within the same aggregate). Also used for monitoring (how old are the oldest pending events?).
- **`published_at`** — when the relay successfully published the event. Used for SLA monitoring and lag calculation.
- **`attempts`** + **`last_error`** — retry tracking. The relay increments `attempts` on each publish attempt. `last_error` stores the last broker error message for debugging.
- **`idempotency_key`** — optional, unique key derived from the business operation. Prevents the same business event from being inserted twice if the application code has a bug or retries the operation. Example: `'order-confirmed-' + orderId` ensures only one `OrderConfirmed` event exists per order.

**Q5. Should you use one outbox table or multiple, and should the payload be typed?**
A: Two schools of thought:

**Single outbox table (recommended for most systems):**
One `outbox_events` table for all event types. The `aggregate_type` and `event_type` columns carry the routing information; the `payload` is JSONB. Simple to query for monitoring and relay. The relay doesn't need schema-specific logic — it publishes all PENDING rows to the appropriate Kafka topic (determined by `aggregate_type` or `event_type`).

Downside: JSONB payloads are schemaless — a typo in the event structure is not caught by the database. Mitigate with application-layer schema validation (JSON Schema, Zod, Joi) before writing to the outbox, and with a schema registry (Confluent Schema Registry, AWS Glue Schema Registry) for consumer-side contract enforcement.

**Per-aggregate typed tables:**
A separate `order_outbox`, `payment_outbox`, `user_outbox` table per aggregate type, each with typed columns rather than a JSONB payload. The database enforces field-level constraints (`amount BIGINT NOT NULL`, `currency CHAR(3) NOT NULL`). Stronger type safety; easier to query specific event types.

Downside: a new event type requires a schema migration. The relay must know about each outbox table. Monitoring requires querying multiple tables. Operationally heavier.

**Recommendation:** start with a single table + JSON Schema validation at the application layer. Migrate to typed tables per aggregate only if type safety concerns become a production issue or if different outbox tables need different retention policies or relay configurations.

## Section 3: Application-Layer Implementation

**Q6. Show the Node.js implementation of an atomic write: state change + outbox event in one transaction.**
A:

```javascript
// db.js — PostgreSQL client with transaction helper
const { Pool } = require('pg');
const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function withTransaction(fn) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}

module.exports = { pool, withTransaction };
```

```javascript
// orderService.js — confirm an order atomically with its outbox event
const { withTransaction } = require('./db');
const { randomUUID } = require('crypto');

async function confirmOrder(orderId, userId) {
  return withTransaction(async (client) => {

    // Step 1: update the order state
    const { rows } = await client.query(
      `UPDATE orders
       SET status = 'CONFIRMED', confirmed_at = now(), version = version + 1
       WHERE id = $1 AND status = 'PENDING'
       RETURNING id, user_id, total_amount, currency, version`,
      [orderId]
    );

    if (rows.length === 0) {
      throw new Error(`Order ${orderId} not found or not in PENDING status`);
    }

    const order = rows[0];

    // Step 2: write the outbox event — SAME transaction, same client
    await client.query(
      `INSERT INTO outbox_events
         (id, aggregate_type, aggregate_id, event_type, payload, idempotency_key)
       VALUES ($1, $2, $3, $4, $5, $6)
       ON CONFLICT (idempotency_key) DO NOTHING`,
      [
        randomUUID(),
        'Order',
        orderId,
        'OrderConfirmed',
        JSON.stringify({
          orderId: order.id,
          userId: order.user_id,
          totalAmount: order.total_amount,
          currency: order.currency,
          version: order.version,
          confirmedAt: new Date().toISOString(),
        }),
        `order-confirmed-${orderId}`,   // idempotency key prevents duplicate events
      ]
    );

    return order;
  });
  // If ANY step above throws, ROLLBACK is called.
  // Both the order update AND the outbox insert are undone atomically.
}

module.exports = { confirmOrder };
```

The critical correctness property: `client` is the same database connection throughout. Both queries execute within the same `BEGIN` / `COMMIT` block. They share the same transaction — the ACID guarantee is provided by PostgreSQL, not by application logic.

**Q7. What does the `ON CONFLICT (idempotency_key) DO NOTHING` clause protect against?**
A: It protects against two failure modes:

**Application-level retry of the same operation:**
If the HTTP request to confirm an order is retried (client timeout, network retry, user double-clicking a button), the `confirmOrder` function may be called twice for the same `orderId`. The first call succeeds: the order moves to `CONFIRMED` and the outbox event is inserted. The second call: the `UPDATE` finds `status = 'CONFIRMED'` (not `'PENDING'`) and updates 0 rows — throwing an error. But if the second call somehow gets past the status check (a race condition), the `ON CONFLICT DO NOTHING` on the idempotency key prevents a second outbox event from being inserted. One outbox event → one downstream event publication → no duplicate processing.

**Consumer retry causing re-invocation of the service:**
In an event-driven architecture, this service might itself be triggered by an upstream Kafka message. If the upstream consumer re-delivers the message (at-least-once delivery), `confirmOrder` runs twice. The idempotency key on the outbox prevents a second event from being published downstream — the duplicate invocation is a no-op.

The idempotency key format (`'order-confirmed-' + orderId`) must be chosen carefully:
- Globally unique per business operation (not per execution attempt)
- Stable across retries — the same logical operation always produces the same key
- Includes the event type to allow multiple events of different types for the same aggregate: `'order-shipped-' + orderId` is different from `'order-confirmed-' + orderId`

## Section 4: The Relay Process

**Q8. What is the relay process, and what are its two implementation strategies?**
A: The relay process (sometimes called the "outbox processor" or "publisher") is the component that reads `PENDING` events from the outbox table and publishes them to the message broker. It bridges the database-centric outbox with the event-driven world.

**Strategy 1 — Polling relay:**
A background worker periodically queries the outbox table for `PENDING` events and publishes them. Simple, self-contained, works with any database without additional infrastructure.

**Strategy 2 — CDC (Change Data Capture) relay:**
A CDC tool (Debezium, AWS DMS) captures changes to the outbox table from the PostgreSQL WAL (Write-Ahead Log) and streams them to Kafka in near-real time. No polling — events are published within milliseconds of the database commit. More complex infrastructure; much lower latency.

Both strategies are legitimate. The polling relay is appropriate for most systems where sub-second event publication latency is not required. The CDC approach is appropriate for high-throughput systems where polling overhead is unacceptable or event latency must be under a few hundred milliseconds.

**Q9. Show the Node.js implementation of a polling relay.**
A:

```javascript
// outboxRelay.js — polls the outbox table and publishes events to Kafka
const { pool } = require('./db');
const { Kafka } = require('kafkajs');
const logger = require('./logger');

const kafka = new Kafka({ brokers: process.env.KAFKA_BROKERS.split(',') });
const producer = kafka.producer({
  idempotent: true,          // enables Kafka idempotent producer (exactly-once delivery into Kafka)
  maxInFlightRequests: 1,    // required for idempotent producer ordering
  transactionalId: process.env.KAFKA_TRANSACTIONAL_ID,  // for exactly-once if needed
});

const POLL_INTERVAL_MS   = parseInt(process.env.OUTBOX_POLL_INTERVAL_MS || '1000');
const BATCH_SIZE         = parseInt(process.env.OUTBOX_BATCH_SIZE || '100');
const MAX_ATTEMPTS       = parseInt(process.env.OUTBOX_MAX_ATTEMPTS || '5');
const LOCK_TIMEOUT_MS    = parseInt(process.env.OUTBOX_LOCK_TIMEOUT_MS || '30000');

// Map aggregate_type → Kafka topic name
function resolveKafkaTopic(aggregateType, eventType) {
  const topicMap = {
    'Order':   'orders',
    'Payment': 'payments',
    'User':    'users',
  };
  return topicMap[aggregateType] ?? `events.${aggregateType.toLowerCase()}`;
}

async function fetchAndLockBatch(client) {
  // SELECT FOR UPDATE SKIP LOCKED: fetches PENDING events and locks them
  // against concurrent relay instances. SKIP LOCKED means a second relay
  // instance will skip rows already locked by this instance — no double-publishing.
  const { rows } = await client.query(
    `SELECT id, aggregate_type, aggregate_id, event_type, payload, attempts
     FROM outbox_events
     WHERE status = 'PENDING'
       AND attempts < $1
     ORDER BY created_at ASC
     LIMIT $2
     FOR UPDATE SKIP LOCKED`,
    [MAX_ATTEMPTS, BATCH_SIZE]
  );
  return rows;
}

async function publishEvent(event) {
  const topic = resolveKafkaTopic(event.aggregate_type, event.event_type);
  await producer.send({
    topic,
    messages: [{
      key:   event.aggregate_id,     // partition key: preserves per-aggregate ordering
      value: JSON.stringify(event.payload),
      headers: {
        eventId:       event.id,
        eventType:     event.event_type,
        aggregateType: event.aggregate_type,
        aggregateId:   event.aggregate_id,
        publishedAt:   new Date().toISOString(),
      },
    }],
  });
}

async function processBatch() {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');

    const events = await fetchAndLockBatch(client);
    if (events.length === 0) {
      await client.query('ROLLBACK');
      return 0;
    }

    const results = await Promise.allSettled(
      events.map(async (event) => {
        try {
          await publishEvent(event);

          // Mark as PUBLISHED only after broker acknowledgment
          await client.query(
            `UPDATE outbox_events
             SET status = 'PUBLISHED',
                 published_at = now(),
                 attempts = attempts + 1
             WHERE id = $1`,
            [event.id]
          );
        } catch (err) {
          const newAttempts = event.attempts + 1;
          const newStatus   = newAttempts >= MAX_ATTEMPTS ? 'DEAD' : 'PENDING';

          await client.query(
            `UPDATE outbox_events
             SET status     = $1,
                 attempts   = $2,
                 last_error = $3
             WHERE id = $4`,
            [newStatus, newAttempts, err.message, event.id]
          );

          logger.error('Failed to publish outbox event', {
            eventId:    event.id,
            eventType:  event.event_type,
            attempts:   newAttempts,
            error:      err.message,
          });
        }
      })
    );

    await client.query('COMMIT');

    const published = results.filter(r => r.status === 'fulfilled').length;
    const failed    = results.filter(r => r.status === 'rejected').length;
    logger.info('Outbox batch processed', { total: events.length, published, failed });

    return events.length;

  } catch (err) {
    await client.query('ROLLBACK');
    logger.error('Outbox relay batch failed', { error: err.message });
    throw err;
  } finally {
    client.release();
  }
}

async function startRelay() {
  await producer.connect();
  logger.info('Outbox relay started', { pollIntervalMs: POLL_INTERVAL_MS, batchSize: BATCH_SIZE });

  async function runLoop() {
    try {
      const processed = await processBatch();
      // If we processed a full batch, run immediately (more may be waiting)
      // If we processed fewer than BATCH_SIZE, wait the poll interval
      const delay = processed >= BATCH_SIZE ? 0 : POLL_INTERVAL_MS;
      setTimeout(runLoop, delay);
    } catch (err) {
      logger.error('Outbox relay loop error', { error: err.message });
      setTimeout(runLoop, POLL_INTERVAL_MS * 2);  // back off on repeated errors
    }
  }

  runLoop();
}

async function stopRelay() {
  await producer.disconnect();
  logger.info('Outbox relay stopped');
}

module.exports = { startRelay, stopRelay };
```

**Q10. What does `SELECT FOR UPDATE SKIP LOCKED` do, and why is it essential for the relay?**
A: `SELECT FOR UPDATE` acquires a row-level exclusive lock on each selected row. `SKIP LOCKED` modifies this: instead of blocking when a row is already locked by another transaction, it silently skips that row and continues to the next unlocked row.

This is essential for the relay because:

- **Multiple relay instances** — in a horizontally scaled deployment (Kubernetes, multiple EC2 instances), multiple relay processes may run simultaneously. Without `SKIP LOCKED`, every relay instance would contend for the same rows, causing lock waits and serialized processing. With `SKIP LOCKED`, each relay instance picks up a non-overlapping subset of PENDING events — they work in parallel without contention.
- **Prevents double-publishing** — two relay instances cannot hold the lock on the same row simultaneously. The first instance to lock row R will publish and update it. The second instance, attempting the same, either waits (without `SKIP LOCKED`) or skips the row (with `SKIP LOCKED`). `SKIP LOCKED` is the right choice because waiting adds latency and risks lock contention cascading.
- **Crash safety** — if a relay instance crashes while holding locks (within an open transaction), PostgreSQL automatically releases the locks when the client connection is closed. The next relay instance (or the recovering instance) will pick up those rows on its next poll. The `BEGIN` / `COMMIT` / `ROLLBACK` wrapping ensures locks are always released — either on commit (rows are updated to `PUBLISHED`) or on rollback (rows remain `PENDING` and are retried).

The alternative — a pessimistic lock without `SKIP LOCKED` — would cause relay instances to queue behind each other, serializing throughput. `SKIP LOCKED` is the standard PostgreSQL pattern for worker pools that need to distribute work from a shared queue without coordination overhead.

**Q11. Why is the Kafka publish done inside the database transaction (not outside), and what is the risk?**
A: The `publishEvent()` call and the subsequent `UPDATE outbox_events SET status = 'PUBLISHED'` are both done within the same database transaction. This means the database transaction is held open during the network round-trip to the Kafka broker.

**Why this approach:**
If Kafka publish fails (broker unavailable, network error), the exception is caught, the status is updated to `PENDING` or `DEAD` within the same transaction, and the transaction commits with the failed status. The event is not marked as published when it wasn't published — preventing a false-positive commit. If the database update also fails, the entire transaction rolls back and the row remains `PENDING` for the next poll cycle.

**The risk — long-held transactions:**
Holding a database transaction open during an external network call is an antipattern in most contexts because: it holds locks for the duration of the network call (adding latency to other transactions contending on the same rows), it consumes a connection from the pool for the full round-trip time, and it may cause lock timeouts if the broker is slow to respond.

**Alternative — publish outside the transaction:**
```javascript
// Alternative: publish first, then mark in a separate transaction
await publishEvent(event);          // outside any DB transaction
await markAsPublished(event.id);    // separate, short DB transaction
```

If the process crashes between `publishEvent` and `markAsPublished`, the event is re-published on restart (the row is still `PENDING`). This is **at-least-once delivery** — acceptable if consumers are idempotent. This approach has shorter lock hold times and is preferred for high-throughput systems where the broker round-trip is significant.

The choice: hold the lock (simpler, avoids duplicates on crash) or publish outside the lock (higher throughput, requires idempotent consumers). For most systems, publishing outside the transaction and requiring idempotent consumers is the right trade-off.

## Section 5: CDC-Based Relay

**Q12. What is the Debezium + PostgreSQL CDC approach to the outbox pattern, and how does it differ from polling?**
A: Debezium is a CDC platform that reads PostgreSQL's Write-Ahead Log (WAL) — the same log PostgreSQL uses for replication — and streams every row-level change as a Kafka message. For the outbox pattern, Debezium watches the `outbox_events` table and publishes every INSERT (a new outbox event) to Kafka immediately — without any polling lag and without the relay process touching the database with queries.

The flow:
1. Application writes state change + outbox event in one transaction. Transaction commits.
2. PostgreSQL writes the committed change to the WAL (this happens as part of every commit).
3. Debezium's Kafka Connect source connector reads the WAL via PostgreSQL's logical replication slot.
4. Debezium publishes the INSERT into `outbox_events` as a Kafka message to a Debezium topic (e.g., `postgres.public.outbox_events`).
5. A Debezium router transform (Kafka Connect SMT — Single Message Transform) routes the event to the correct business topic based on `aggregate_type`, and uses `aggregate_id` as the Kafka message key.

Key differences from polling:

| Aspect | Polling Relay | CDC (Debezium) |
|--- |--- |--- |
| Latency | Seconds (poll interval) | Milliseconds (WAL tail) |
| Database load | Periodic SELECT queries on outbox table | WAL read (minimal DB query load) |
| Infrastructure complexity | Low (just a Node.js process) | High (Kafka Connect cluster, Debezium config, WAL slot management) |
| Outbox table updates | Relay updates status to PUBLISHED | Debezium deletes the row (or tombstones) after publishing |
| Exactly-once delivery | At-least-once (requires idempotent consumers) | At-least-once (Kafka Connect has at-least-once delivery) |
| Dead letter handling | Built into relay logic | Requires Kafka Connect DLQ configuration |

**Q13. What is a PostgreSQL logical replication slot, and what operational risks does it introduce for CDC?**
A: A logical replication slot is a PostgreSQL feature that allows an external consumer (Debezium in this case) to read the WAL in a decoded, human-readable format (rows inserted/updated/deleted, not raw binary WAL bytes). PostgreSQL retains WAL segments until the replication slot consumer has confirmed it has read them — ensuring the CDC consumer never misses a change even if it's temporarily offline.

Operational risks:

- **WAL accumulation / disk exhaustion** — if the Debezium consumer is offline for an extended period, PostgreSQL cannot delete WAL segments the slot has not yet consumed. The WAL grows until the consumer catches up or the slot is dropped. On a busy system, this can exhaust disk space within hours. Monitoring alert: `pg_replication_slots` showing `inactive = true` and `confirmed_flush_lsn` not advancing. Mitigation: `max_slot_wal_keep_size` (PostgreSQL 13+) limits WAL retention per slot at the cost of potentially invalidating the slot if the consumer falls too far behind.
- **Slot invalidation** — if the WAL grows past the configured limit (or if `wal_keep_size` is breached), PostgreSQL may invalidate the replication slot. Debezium must then be reconfigured to snapshot the current database state and restart from the current WAL position — potentially missing events between the last successful position and the snapshot.
- **Slot leaks** — a Debezium connector that is deleted without its replication slot being dropped leaves an orphaned slot. The orphaned slot continues to prevent WAL cleanup. Monitor `pg_replication_slots` for inactive slots and drop orphans.
- **Performance impact** — logical decoding from the WAL adds CPU overhead on the primary. Under heavy write loads, this overhead can be measurable (typically 5–15% additional CPU). Run Debezium against a replica if the primary is already near CPU saturation.

## Section 6: Failure Handling and Operations

**Q14. What is the retry strategy for failed outbox events, and how do you avoid infinite retries?**
A: Failed outbox events (Kafka broker unavailable, serialization error, network timeout) should be retried with exponential backoff, bounded by a maximum attempt count:

```javascript
// Retry query: fetch events eligible for retry
// Uses attempts count as a proxy for backoff — the relay skips events
// that were attempted recently by checking their last_attempted_at timestamp

async function fetchRetryEligibleEvents(client) {
  const { rows } = await client.query(
    `SELECT id, aggregate_type, aggregate_id, event_type, payload, attempts
     FROM outbox_events
     WHERE status = 'PENDING'
       AND attempts < $1
       AND (
             attempts = 0                           -- never attempted
             OR last_attempted_at < now() - (
                  interval '1 second' *
                  LEAST(POWER(2, attempts), 3600)   -- exponential backoff, max 1 hour
                )
           )
     ORDER BY created_at ASC
     LIMIT $2
     FOR UPDATE SKIP LOCKED`,
    [MAX_ATTEMPTS, BATCH_SIZE]
  );
  return rows;
}
```

This requires adding a `last_attempted_at TIMESTAMPTZ` column to the outbox table. On each failed attempt:

```sql
UPDATE outbox_events
SET attempts = attempts + 1,
    last_attempted_at = now(),
    last_error = $1,
    status = CASE
               WHEN attempts + 1 >= $2 THEN 'DEAD'
               ELSE 'PENDING'
             END
WHERE id = $3;
```

Backoff schedule (with `POWER(2, attempts)` seconds):
- Attempt 1 failure → retry after 2 seconds
- Attempt 2 failure → retry after 4 seconds
- Attempt 3 failure → retry after 8 seconds
- Attempt 4 failure → retry after 16 seconds
- Attempt 5 failure → status = `DEAD`, requires manual intervention

Events in `DEAD` status are permanently stuck until an operator either manually resolves the issue and resets status to `PENDING`, or writes a migration to republish them.

**Q15. What is a "dead letter" outbox event, and what monitoring and alerting should you build around it?**
A: A dead letter event is one that has exceeded `MAX_ATTEMPTS` and is in `DEAD` status — the relay gave up retrying it. It represents a message that was committed to the database (the state change happened) but was never published to the broker. This is a data consistency gap: the database says the event happened; the downstream event-driven world doesn't know.

Monitoring:

```sql
-- Count of dead events by type — the most important alert
SELECT event_type, aggregate_type, COUNT(*) as dead_count, MIN(created_at) as oldest
FROM outbox_events
WHERE status = 'DEAD'
GROUP BY event_type, aggregate_type
ORDER BY dead_count DESC;

-- Oldest pending event — measures relay lag
SELECT MIN(created_at) as oldest_pending
FROM outbox_events
WHERE status = 'PENDING';

-- Events pending for more than 5 minutes — relay may be stuck
SELECT COUNT(*) as stuck_count
FROM outbox_events
WHERE status = 'PENDING'
  AND created_at < now() - interval '5 minutes';

-- Recent failure rate
SELECT
  event_type,
  COUNT(*) FILTER (WHERE status = 'PUBLISHED') as published,
  COUNT(*) FILTER (WHERE status = 'DEAD')      as dead,
  COUNT(*) FILTER (WHERE status = 'PENDING')   as pending
FROM outbox_events
WHERE created_at > now() - interval '1 hour'
GROUP BY event_type;
```

Alerts to configure:
- **DEAD event count > 0** — any dead event is a data consistency issue. Alert immediately. Severity: high.
- **Oldest PENDING event age > 2 minutes** — the relay is lagging or stuck. Severity: warning.
- **Oldest PENDING event age > 10 minutes** — the relay has likely crashed or the broker is unreachable. Severity: critical (page on-call).
- **Published event count drops to 0** — the relay has stopped processing entirely. Severity: critical.

**Q16. How do you handle outbox table growth and archiving?**
A: The outbox table accumulates rows indefinitely — `PUBLISHED` events are no longer needed operationally but remain in the table. Without cleanup, the table grows unboundedly, degrading index performance and increasing storage cost.

Cleanup strategies:

**Strategy 1 — Scheduled deletion (simplest):**
```sql
-- Run via pg_cron, a Node.js cron job, or a database scheduled job
-- Delete PUBLISHED events older than 7 days
DELETE FROM outbox_events
WHERE status = 'PUBLISHED'
  AND published_at < now() - interval '7 days';

-- Delete DEAD events after manual review period
DELETE FROM outbox_events
WHERE status = 'DEAD'
  AND created_at < now() - interval '30 days';
```

Run this as a low-priority job during off-peak hours with a `LIMIT` clause to avoid long lock-holding deletes:
```sql
WITH to_delete AS (
  SELECT id FROM outbox_events
  WHERE status = 'PUBLISHED'
    AND published_at < now() - interval '7 days'
  LIMIT 10000
)
DELETE FROM outbox_events
WHERE id IN (SELECT id FROM to_delete);
```

**Strategy 2 — Table partitioning by `created_at`:**
Partition the `outbox_events` table by week or month. Cleanup becomes a partition detach + drop — a metadata operation that doesn't scan or lock individual rows:
```sql
-- Detach and drop the partition for the previous month
ALTER TABLE outbox_events DETACH PARTITION outbox_events_2026_06;
DROP TABLE outbox_events_2026_06;
```
Best for high-volume tables (millions of events per day) where row-level DELETE would be too slow.

**Strategy 3 — Relay deletes on publish:**
The relay deletes each row immediately after successful publication rather than updating status to `PUBLISHED`. The table contains only in-flight events — it stays small at all times. Downside: no audit trail of published events; monitoring is harder (you can't query published event history); replay is not possible from the outbox table.

## Section 8: Scenario / System Design Questions

**Q18. "Your outbox relay is publishing duplicate events to Kafka. What are the possible root causes?"**
A: Duplicate events from the outbox relay come from two distinct sources:

**Root cause 1 — Relay crash between Kafka publish and status update:**
The relay publishes the event to Kafka (broker acknowledges), then crashes before it can commit the `UPDATE status = 'PUBLISHED'` to the database. On restart, the row is still `PENDING` and the relay publishes again. This is the inherent at-least-once behavior of the outbox pattern and is expected under failure conditions. Fix: ensure consumers are idempotent using the `eventId` (the outbox row's `id`) as the deduplication key.

**Root cause 2 — Multiple relay instances without `SKIP LOCKED`:**
Two relay instances both SELECT the same row (no `FOR UPDATE SKIP LOCKED`), both publish to Kafka, and both update status. Fix: ensure the `SELECT FOR UPDATE SKIP LOCKED` pattern is used. Verify the locking with `EXPLAIN` and by observing `pg_locks` during a relay run.

**Root cause 3 — Relay retrying a successfully published event:**
The `status` update commits but the commit acknowledgment doesn't reach the relay (network partition between relay and database). The relay's client times out and considers the commit failed — but the database committed successfully. On retry, the status check fails to correctly filter the PUBLISHED event. Fix: use `RETURNING status` in the UPDATE and check the returned status; if it returns `PUBLISHED`, the event was already processed by a prior attempt.

**Root cause 4 — Outbox row inserted twice (application bug):**
The application calls `confirmOrder` twice for the same order (without idempotency protection), inserting two outbox events. Both are published. Fix: the `idempotency_key` unique constraint prevents this if correctly implemented. Check for missing or incorrectly scoped idempotency keys.

**Root cause 5 — Kafka producer retry creating duplicates:**
The Kafka producer times out waiting for broker acknowledgment, retries the send, and the broker receives two copies. With `idempotent: true` on the Kafka producer, the broker deduplicates these automatically (sequence numbers). Without idempotency enabled, retries can cause duplicates at the Kafka layer. Fix: enable `idempotent: true` on the producer.

**Q19. "The relay is falling behind — outbox events are accumulating faster than they're being published. How do you scale it?"**
A: Scaling the relay while maintaining per-aggregate ordering requires care — you can't just run N identical relay instances on the entire table because events for the same aggregate might be published out of order.

**Scale by partitioning the outbox work:**

```javascript
// Each relay instance handles a subset of aggregate IDs
// Determined by: hash(aggregate_id) % NUM_RELAY_INSTANCES == INSTANCE_ID

async function fetchAndLockBatch(client, instanceId, totalInstances) {
  const { rows } = await client.query(
    `SELECT id, aggregate_type, aggregate_id, event_type, payload, attempts
     FROM outbox_events
     WHERE status = 'PENDING'
       AND attempts < $1
       AND ABS(HASHTEXT(aggregate_id)) % $2 = $3  -- partition by aggregate ID
     ORDER BY created_at ASC
     LIMIT $4
     FOR UPDATE SKIP LOCKED`,
    [MAX_ATTEMPTS, totalInstances, instanceId, BATCH_SIZE]
  );
  return rows;
}
```

Each relay instance handles a stable subset of aggregate IDs. Events for the same aggregate always go to the same relay instance — per-aggregate ordering is preserved. Adding more instances reduces the per-instance load proportionally.

**Tune batch size and poll interval:**
Increase `BATCH_SIZE` (more events per poll cycle) and reduce `POLL_INTERVAL_MS` (more frequent polls). Profile to find the optimal batch size — very large batches hold the `FOR UPDATE` lock longer, increasing contention with other relay instances and with the application.

**Use CDC instead of polling:**
Switch from the polling relay to Debezium CDC. The WAL-based approach eliminates polling overhead entirely and publishes events within milliseconds of commit, preventing accumulation under sustained write load.

**Increase `log.cleaner.threads` (Kafka-side):** — if the bottleneck is Kafka producer throughput, tune the producer: increase `batch.size`, increase `linger.ms` (producer batching delay), and enable compression (`compression.type = 'snappy'`). These reduce the number of Kafka RPCs per event, increasing throughput.

**Q20. "A teammate suggests storing the Kafka message directly in the outbox (serialized as bytes) rather than as a structured JSONB payload. What are the trade-offs?"**
A: Storing pre-serialized bytes (Avro, Protobuf, or raw JSON bytes) vs structured JSONB is a real design choice with meaningful trade-offs:

**Pre-serialized bytes:**
- **Advantages**: the message is identical byte-for-byte on every publish attempt — no risk of the relay serializing differently than the application intended. Schema evolution is handled at the producer level; the outbox is schema-agnostic. Slightly faster relay (no re-serialization step).
- **Disadvantages**: the outbox is opaque — you can't query `WHERE payload->>'orderId' = 'order-1'`. Debugging requires deserialization. Schema changes require careful coordination — old outbox rows serialized with schema V1 may sit in the table while the relay uses V2. DEAD events are harder to inspect and manually replay.

**Structured JSONB (recommended for most cases):**
- **Advantages**: queryable for debugging, monitoring, and manual replay. Human-readable in `psql`. Schema changes are additive (JSON is schema-flexible); old events remain parseable. Dead events can be inspected, corrected, and re-inserted without deserialization tooling.
- **Disadvantages**: the relay must serialize the JSONB to the format the Kafka consumer expects (Avro, Protobuf). If the serialization logic changes between the time the outbox event was written and the time it is replayed (for DEAD events or manual replays), the serialized bytes may differ. JSONB is larger than binary formats.

The recommendation: use structured JSONB in the outbox. The relay's responsibility is to serialize the JSONB payload into the broker's wire format (Avro via Schema Registry, Protobuf, or plain JSON). Store the schema version or event contract version in the outbox row's metadata if schema evolution is a concern. The debuggability and operational flexibility of JSONB outweigh the minor serialization overhead for the relay.

## Quick Reference

**Outbox table schema (minimal production version):**

```sql
CREATE TABLE outbox_events (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_type  TEXT NOT NULL,
    aggregate_id    TEXT NOT NULL,
    event_type      TEXT NOT NULL,
    payload         JSONB NOT NULL,
    status          TEXT NOT NULL DEFAULT 'PENDING'
                        CHECK (status IN ('PENDING','PUBLISHED','DEAD')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at    TIMESTAMPTZ,
    last_attempted_at TIMESTAMPTZ,
    attempts        INT NOT NULL DEFAULT 0,
    last_error      TEXT,
    idempotency_key TEXT UNIQUE
);

CREATE INDEX idx_outbox_relay ON outbox_events (created_at ASC)
    WHERE status = 'PENDING';
```

**Atomic write pattern (must-have):**
```
BEGIN
  UPDATE domain_table ...         ← state change
  INSERT INTO outbox_events ...   ← same client, same txn
COMMIT
```

**Relay delivery guarantee map:**

| Relay behavior | Delivery guarantee | Consumer requirement |
|--- |--- |--- |
| Mark PUBLISHED inside txn with Kafka send | At-least-once (long lock hold) | Idempotent |
| Publish first, mark PUBLISHED after | At-least-once (short lock hold) | Idempotent |
| Transactional Kafka producer + sendOffsetsToTransaction | Exactly-once (Kafka-to-Kafka only) | None |
| Mark before publish (wrong) | At-most-once | N/A (data loss) |

**Common failure modes:**

| Failure | Symptom | Fix |
|--- |--- |--- |
| State change without outbox write | Downstream never gets event | Enforce single-client transaction; code review |
| Outbox write without state change | Phantom event | Same fix; both in same txn |
| Relay publishes, crashes before marking | Duplicate event | Idempotency key on consumer |
| Relay marks PUBLISHED before broker ack | Lost event (at-most-once) | Always publish first, mark after |
| Missing `SKIP LOCKED` | Two relay instances double-publish | Add `FOR UPDATE SKIP LOCKED` |
| No idempotency key | Duplicate business events on retry | Add `idempotency_key` unique constraint |
| No tombstone / cleanup job | Outbox table grows unboundedly | Add scheduled DELETE or partition pruning |
| Missing `DEAD` event alert | Silent consistency gap | Alert on `status = 'DEAD'` count > 0 |

**Tip for the interview:** The outbox pattern question at 5 YOE level is not about knowing the pattern name — it's about understanding why the naive dual-write is broken (the four failure modes in Q1), exactly what atomicity the database transaction provides, and where the at-least-once gap lives in the relay. The most impressive answers go beyond the happy path to cover `SKIP LOCKED` and why it's needed for horizontal relay scaling, the `SELECT FOR UPDATE` lock duration trade-off, and what happens when a DEAD event represents a permanent consistency gap. The war story that lands best: "we had a production incident where the relay was marking events as PUBLISHED before the Kafka broker acknowledged them — the relay crashed mid-batch and we lost 200 events silently. The fix was flipping the order: publish first, mark after, and alert on DEAD events. Here's exactly where the bug was in the code."
