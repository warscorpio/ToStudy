# Event Types: Domain Events, Integration Events, Commands vs Events vs Queries — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a message in event-driven architecture and what are its three fundamental types?**
A: In event-driven and distributed systems, a message is the unit of communication between components. All messages fall into one of three fundamental types, each with a distinct intent and semantic contract:

**Command:** A request to perform an action. The sender instructs a receiver to do something specific. Commands are directed — they target a specific recipient. They may succeed or fail and typically produce a response. They describe *intent* (what the sender wants to happen). Example: `PlaceOrder`, `CancelShipment`, `ChargePayment`.

**Event:** A notification that something has happened. The publisher records a fact about a past occurrence. Events are undirected — the publisher does not know or care who, if anyone, listens. They describe *fact* (what did happen). Events are immutable — you cannot "take back" a fact that occurred. Example: `OrderPlaced`, `ShipmentCancelled`, `PaymentCharged`.

**Query:** A request for information. The sender asks for data without intending to change state. Queries are read-only by contract — a query that modifies state is a design smell. They return a result. Example: `GetOrderById`, `ListActiveShipments`, `GetAccountBalance`.

This classification is the foundation of the CQRS (Command Query Responsibility Segregation) and CQS (Command Query Separation) patterns and is a prerequisite for understanding event sourcing, SAGA orchestration, and domain-driven design.

**Q2. What is the key philosophical difference between a command and an event?**
A: The difference is tense and certainty:

- **A command lives in the future tense and is conditional:** `PlaceOrder` says "I want this to happen." The receiver can reject it. The outcome is uncertain at the time of sending. The command implies a request for a state change that has not yet occurred.
- **An event lives in the past tense and is unconditional:** `OrderPlaced` says "this happened." It is a fact. Facts cannot be rejected or undone (though their consequences can be compensated). The event implies a state change that has already occurred.

This distinction has architectural consequences: commands go to one specific handler (only one service should decide whether to place an order), while events are broadcast to any interested parties (many services may react to an order being placed — inventory, shipping, notifications, analytics — and none needs to be known to the publisher).

A common naming convention enforces this: commands are imperative verbs (`PlaceOrder`, `CancelSubscription`); events are past-tense verb phrases (`OrderPlaced`, `SubscriptionCancelled`).

**Q3. What is CQS (Command Query Separation) and how does it differ from CQRS?**
A: Both enforce the same core principle at different scopes:

**CQS (Command Query Separation — Bertrand Meyer, 1988):** A principle at the method/function level. A method should either be a command (performs an action, changes state, returns void) or a query (returns data, has no side effects) — never both. Violating CQS: a function that increments a counter and returns the new value both modifies state and returns data.

**CQRS (Command Query Responsibility Segregation — Greg Young):** Applies CQS at the architectural level. The read model (query side) and write model (command side) are separate subsystems — different objects, different data stores, different optimization strategies. Commands write to the write model; queries read from the read model. The write model is normalized for consistency; the read model is denormalized for query performance.

**Key difference in scope:**
- CQS: don't mix reads and writes within a single method.
- CQRS: maintain separate read and write models at the system level, potentially with different databases, schemas, and even services.

CQRS is often combined with event sourcing: commands produce events that update the write model; events are projected into read models optimized for specific queries.

## Section 2: Domain Events

**Q4. What is a domain event?**
A: A domain event is an event that is meaningful within the business domain — it represents something significant that happened in terms the business understands and cares about. It is defined and owned by the domain model, not by infrastructure concerns.

Key characteristics:
- **Business-meaningful:** `OrderShipped` is a domain event. `DatabaseRowUpdated` is not.
- **Named in the ubiquitous language:** The name is shared between domain experts and engineers — a business stakeholder understands what `SubscriptionRenewed` means without a technical translation.
- **Past-tense fact:** Something that has already happened in the domain.
- **Immutable:** The event captures the state at the moment it occurred — it is never modified after creation.
- **Rich with context:** A well-designed domain event carries enough data to allow subscribers to react without needing to call back into the originating service. Example: `OrderPlaced` carries `order_id`, `customer_id`, `line_items[]`, `total_amount`, `placed_at` — not just `order_id`.

**Q5. What data should a domain event carry?**
A: A domain event should be self-contained enough for consumers to act on it without additional lookups (the "fat event" principle), but not so large that it couples consumers to the full domain model. A well-structured domain event carries:

**Identity and causality:**
```json
{
  "event_id": "uuid-v4",           // unique identifier for this event instance
  "event_type": "OrderPlaced",     // the type, for routing and deserialization
  "event_version": "1.0",          // schema version for compatibility
  "occurred_at": "2026-03-15T10:23:44Z",  // when it happened (domain time)
  "correlation_id": "uuid-request-123",   // tracing across services
  "causation_id": "uuid-command-456"      // the command or event that caused this
}
```

**Business data (the payload):**
```json
{
  "order_id": "ord-789",
  "customer_id": "cust-42",
  "line_items": [
    { "product_id": "prod-1", "quantity": 2, "unit_price": 29.99 }
  ],
  "total_amount": 59.98,
  "currency": "USD",
  "shipping_address": { "city": "Mumbai", "country": "IN" }
}
```

**What to omit:** Internal implementation details (database IDs that have no business meaning), derived data that can be recomputed, data that would create coupling to the publisher's internal model. Also omit data that changes frequently and isn't part of the event's fact — e.g., the customer's current email is not part of `OrderPlaced`; subscribe to `CustomerEmailChanged` if you need email updates.

**Q6. What is the difference between raising a domain event and publishing it?**
A: A critical distinction in domain-driven design implementation:

**Raising a domain event:** The domain entity (aggregate) records that an event occurred as part of executing a business operation. This happens synchronously, within the transaction, as an in-memory side effect of the domain logic. The aggregate collects events in an internal list (`domainEvents`). No external I/O occurs at this point.

```typescript
class Order {
  private domainEvents: DomainEvent[] = [];

  place(customerId: string, lineItems: LineItem[]): void {
    // Domain logic — validate, calculate total, set status
    this.status = OrderStatus.Placed;
    this.placedAt = new Date();

    // Raise the event — in memory, no I/O yet
    this.domainEvents.push(new OrderPlaced(
      this.id, customerId, lineItems, this.totalAmount, this.placedAt
    ));
  }

  getDomainEvents(): DomainEvent[] { return [...this.domainEvents]; }
  clearDomainEvents(): void { this.domainEvents = []; }
}
```

**Publishing a domain event:** After the transaction commits, the application layer (command handler, use case) reads the collected events from the aggregate and dispatches them to the infrastructure (event bus, message broker, outbox table). This happens after the DB commit — ensuring events are only published when the state change is durable.

```typescript
// In the command handler / application service:
const order = Order.create(command);
await this.orderRepository.save(order);           // DB commit
await this.eventBus.publishAll(order.getDomainEvents()); // publish after commit
order.clearDomainEvents();
```

**Why this matters:** If you publish the event before committing, consumers may react to a state that was never persisted (rollback scenario). If you commit without publishing, the event is lost. The transactional outbox pattern solves this atomicity gap — see Q18.

**Q7. What is an aggregate and how does it relate to domain events?**
A: An aggregate is a cluster of domain objects (entities and value objects) treated as a single unit for the purpose of data changes. It has a root entity (the aggregate root) that is the only entry point for mutations and the only object that can raise domain events.

The aggregate root:
- Enforces all business invariants within the aggregate boundary.
- Is the only object external services reference by ID.
- Raises domain events to signal state changes to the outside world.

Domain events cross aggregate boundaries — the `OrderPlaced` event is how the `Inventory` aggregate, the `Notification` service, and the `Analytics` service learn that an order was placed, without the `Order` aggregate coupling to any of them directly.

```
Order (Aggregate Root)
  ├── OrderLine (Entity, part of Order aggregate)
  ├── ShippingAddress (Value Object)
  └── raises: OrderPlaced, OrderConfirmed, OrderShipped, OrderCancelled

Inventory (separate Aggregate Root)
  └── listens to: OrderPlaced (to reserve stock)

ShipmentService (separate bounded context)
  └── listens to: OrderConfirmed (to create shipment)
```

## Section 3: Integration Events

**Q8. What is an integration event and how does it differ from a domain event?**
A: An integration event is an event published across service or bounded context boundaries — it is the mechanism by which separate services communicate about things that have happened. While domain events are internal signals within a bounded context, integration events are the external-facing contract between services.

**Domain event:** Internal to a bounded context. Raised by an aggregate root. May use the domain model's internal types. Not required to be backward-compatible with other teams. Published and consumed within the same service or bounded context.

**Integration event:** External contract between bounded contexts or services. Represents the same or a derived fact, translated into a stable, consumer-friendly schema. Must be versioned and backward-compatible — other teams depend on it and cannot be forced to update simultaneously.

**The translation layer:**
```
Domain Event (internal):
  OrderPlaced {
    orderId: OrderId,          // domain value object
    customerId: CustomerId,    // domain value object
    lineItems: LineItem[],     // domain entity
    total: Money               // domain value object with currency
  }

Integration Event (external, published to Kafka):
  OrderPlacedIntegrationEvent {
    order_id: string,          // primitive types, no domain objects
    customer_id: string,
    line_items: [{ product_id: string, quantity: int, unit_price_cents: int }],
    total_cents: int,
    currency: string,
    occurred_at: string        // ISO 8601
  }
```

The domain event is translated to the integration event in the application layer, often via a domain event handler that listens to domain events and publishes integration events.

**Q9. What are the design principles for a good integration event schema?**
A: Integration events are public contracts — breaking them breaks downstream consumers. Design them accordingly:

**Use primitive types only:** No domain objects, no language-specific types. JSON with strings, numbers, booleans, and arrays is universally parseable. Avoid enums (add new values rather than changing existing ones). Use ISO 8601 strings for timestamps, cents (integers) for money amounts to avoid floating-point issues.

**Make events self-describing:** Include `event_type`, `event_version`, `event_id`, and `occurred_at` in every event. Consumers must be able to deserialize and route the event without additional context.

**Design for backward compatibility:** Adding optional fields is backward-compatible (existing consumers ignore new fields). Removing or renaming fields is breaking. Changing a field's type is breaking. Use semantic versioning on event schemas (`event_version: "1.0"`, `"1.1"`, `"2.0"`). Run multiple versions simultaneously during migration.

**Prefer fat events over thin events (within reason):** A thin event carries only the ID (`{ "order_id": "ord-123" }`), forcing consumers to call back to the publisher to fetch details. This creates temporal coupling (the data must still be available), load on the publisher, and latency. A fat event carries sufficient context for consumers to act without callbacks. Balance: include what consumers predictably need, not everything in the domain model.

**Avoid choreographing business logic via event content:** The event should describe what happened, not prescribe what to do. `OrderCancelled { reason: "payment_failed" }` is better than `ProcessOrderCancellationForPaymentFailure` as an event name — the former is a fact, the latter is business logic leaking into event naming.

**Q10. How do you version integration events without breaking consumers?**
A: Schema evolution in integration events is one of the hardest long-term operational challenges:

**Backward-compatible changes (safe):**
- Add an optional field with a default value. Existing consumers ignore it; new consumers use it.
- Add a new event type. Existing consumers ignore unknown event types.
- Widen a type (change `int` → `long`, `string` with stricter format → `string` without format constraint).

**Breaking changes (require versioning strategy):**
- Remove a field consumers depend on.
- Rename a field.
- Change a field's semantic meaning (same name, different interpretation).
- Narrow a type (restrict values an existing field can take).

**Versioning strategies:**

**Topic-per-version:** Publish `order-placed-v1` and `order-placed-v2` as separate Kafka topics. Old consumers read v1; new consumers read v2. The publisher writes to both during transition, then deprecates v1 after all consumers migrate.

**Version field in event body:** `event_version: "2.0"` in the payload. Consumers deserialize based on version — a dispatcher routes to version-specific handlers.

**Schema registry (Avro/Protobuf):** Tools like Confluent Schema Registry enforce compatibility rules at publish time. The schema registry rejects a new schema that would break registered consumers. Avro and Protobuf support field addition/removal with defaults — making backward and forward compatibility manageable.

**Consumer-driven contract testing (Pact):** Each consumer publishes what fields it expects from an event. The publisher runs these contracts as part of its CI pipeline — any schema change that breaks a registered consumer contract fails the build before deployment.

## Section 4: Commands vs Events — Design Decisions

**Q11. When should you model something as a command vs an event?**
A: The decision turns on whether the sender cares about the outcome and whether intent or fact is being communicated:

**Model as a command when:**
- The sender intends to cause a specific state change and needs to know if it succeeded.
- Exactly one recipient should handle it — routing is specific.
- The action may be rejected (validation failure, business rule violation).
- The sender needs a synchronous or correlated response.
- You want to enforce that the operation is idempotent (retrying a command should be safe).

```
Commands: PlaceOrder, CancelOrder, ApproveRefund,
          AssignDriverToTrip, SendVerificationEmail
```

**Model as an event when:**
- The fact is already determined and cannot be un-published.
- Multiple independent consumers may react — the publisher doesn't know or care who listens.
- The publisher should not be coupled to the downstream consequences.
- The event enables autonomous reaction without tight coordination.
- You want to capture historical record of what happened for audit or replay.

```
Events: OrderPlaced, OrderCancelled, RefundApproved,
        DriverAssigned, VerificationEmailSent
```

**Common mistake — commands disguised as events:**
`ProcessOrderAfterPaymentConfirmation` looks like an event but is actually a command — it prescribes what to do, not what happened. The correct event is `PaymentConfirmed`; downstream services decide for themselves how to react.

**Q12. What is the "event carried state transfer" pattern?**
A: Event Carried State Transfer (ECST) is a pattern where events carry the full (or sufficient) state needed by consumers, eliminating the need for consumers to query the publisher after receiving an event.

**Without ECST (thin event + query back):**
```
OrderService publishes: OrderPlaced { order_id: "ord-123" }
ShippingService receives OrderPlaced.
ShippingService calls GET /orders/ord-123 to fetch order details.
→ Temporal coupling: the order must still be accessible.
→ Load coupling: OrderService handles N queries for every N event consumers.
→ Latency: additional round trip before Shipping can act.
```

**With ECST (fat event):**
```
OrderService publishes: OrderPlaced {
  order_id: "ord-123",
  shipping_address: { ... },
  items: [{ product_id, quantity, weight_kg }],
  ...
}
ShippingService receives OrderPlaced and has everything it needs.
→ No callback required.
→ OrderService is fully decoupled from ShippingService.
→ ShippingService can act immediately.
```

**Trade-offs of ECST:**
- Events become larger (more bandwidth, storage cost).
- The same data may be duplicated across many consumer stores — eventual consistency across copies.
- If the consumer needs data that changes after the event (e.g., the shipping address changes after ordering), it must listen to update events or query for the latest state explicitly.
- Schema changes to the payload affect all consumers — more coordination on schema evolution.

**Q13. What is the command-event duality and how does it appear in SAGA design?**
A: Many operations have a natural duality: the command triggers the action, and the event records its outcome. In a SAGA, this duality is explicit — each step is modeled as a command (sent to a participant) followed by an event (published by the participant on success or failure):

```
SAGA: Order Fulfillment

Step 1:
  Orchestrator sends:   ReserveInventory (command → InventoryService)
  InventoryService emits: InventoryReserved (event → Orchestrator) [success]
                     OR: InventoryReservationFailed (event → Orchestrator) [failure]

Step 2 (on InventoryReserved):
  Orchestrator sends:   ChargePayment (command → PaymentService)
  PaymentService emits: PaymentCharged (event → Orchestrator) [success]
                     OR: PaymentFailed (event → Orchestrator) [failure]

Step 3 (on PaymentFailed — compensation):
  Orchestrator sends:   ReleaseInventory (command → InventoryService)
  InventoryService emits: InventoryReleased (event → Orchestrator)
```

This duality makes the business process explicit and traceable. Each command represents an intent; each event records an outcome. The SAGA can be reconstructed entirely from the event stream — enabling debugging, audit, and replay.

**Q14. What is the difference between a choreography event and an orchestration command?**
A: The same business process can be implemented via choreography (events only) or orchestration (commands from a central coordinator), with different coupling and observability trade-offs:

**Choreography (events only):**
```
OrderService publishes: OrderPlaced
  → InventoryService listens, reserves stock, publishes: InventoryReserved
  → PaymentService listens to InventoryReserved, charges, publishes: PaymentCharged
  → ShippingService listens to PaymentCharged, creates shipment
```
No central coordinator. Each service reacts to events. Highly decoupled — services don't know about each other, only about events. But the workflow is implicit — understanding the full process requires reading all services' code. Debugging is hard (events scattered across topics and logs). Adding a step requires modifying existing services.

**Orchestration (commands from coordinator):**
```
OrderOrchestrator sends: ReserveInventory → InventoryService
InventoryService replies: InventoryReserved → OrderOrchestrator
OrderOrchestrator sends: ChargePayment → PaymentService
PaymentService replies: PaymentCharged → OrderOrchestrator
OrderOrchestrator sends: CreateShipment → ShippingService
```
The workflow is explicit and centralized. Adding a step modifies only the orchestrator. Debugging is easy — query the orchestrator's state. But the orchestrator is coupled to all participants. If the orchestrator fails, the workflow stalls.

## Section 5: Practical Patterns

**Q15. What is the outbox pattern and why is it essential for domain events?**
A: The outbox pattern solves the atomic dual-write problem: you need to save state to the database AND publish an event, but these are two separate operations that cannot be wrapped in a single atomic transaction (unless you use a distributed transaction, which is expensive and fragile).

**The problem without outbox:**
```
Option A — publish then save:
  1. Publish OrderPlaced to Kafka.    ← event published
  2. Save order to DB. ← CRASH here
  → Event published, state never saved. Consumers acted on a phantom order.

Option B — save then publish:
  1. Save order to DB. ← committed
  2. Publish OrderPlaced to Kafka. ← CRASH here
  → State saved, event never published. Downstream services never informed.
```

**The outbox pattern:**
```
Within a single DB transaction:
  1. Save order to the `orders` table.
  2. Insert OrderPlaced event into the `outbox` table.
  3. COMMIT (both writes are atomic).

A separate relay process (Debezium CDC, polling loop, or a scheduled job):
  4. Reads undelivered events from the `outbox` table.
  5. Publishes them to Kafka.
  6. Marks them as delivered in the outbox (or deletes them).
```

The outbox table is the durable buffer. If the relay crashes between steps 5 and 6, it retries — the event is delivered at-least-once. The consumer must be idempotent (use `event_id` for deduplication). The atomic DB transaction in step 1–3 ensures the event is either published with the state change or not at all.

```sql
CREATE TABLE outbox (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  aggregate_type TEXT NOT NULL,        -- 'Order'
  aggregate_id  TEXT NOT NULL,         -- 'ord-123'
  event_type    TEXT NOT NULL,         -- 'OrderPlaced'
  payload       JSONB NOT NULL,        -- serialized event data
  occurred_at   TIMESTAMPTZ NOT NULL,
  published_at  TIMESTAMPTZ,           -- null until delivered
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_outbox_unpublished ON outbox(created_at)
  WHERE published_at IS NULL;
```

**Q16. What is the inbox pattern and how does it complement the outbox?**
A: The inbox pattern is the consumer-side complement to the outbox: it ensures at-most-once processing by recording received events in a local `inbox` table before processing, enabling deduplication:

```
Consumer receives OrderPlaced (event_id = "evt-abc"):

1. BEGIN TRANSACTION
2. Check inbox: SELECT 1 FROM inbox WHERE event_id = 'evt-abc'
   → If found: this event was already processed. Commit (no-op) and ACK to broker.
   → If not found: proceed.
3. INSERT INTO inbox (event_id, event_type, received_at) VALUES (...)
4. Execute business logic (update inventory, etc.)
5. COMMIT (inbox insert + business logic are atomic)
6. ACK message to broker

Result: even if the broker redelivers the message (at-least-once),
the inbox check makes processing exactly-once.
```

The inbox `event_id` deduplication gives you exactly-once processing at the application level, independent of the broker's delivery guarantee. Pair with the outbox on the publishing side and you get end-to-end exactly-once without Kafka's transactional API.

**Q17. What is event sourcing and how does it relate to domain events?**
A: Event sourcing is a persistence pattern where the state of an aggregate is stored not as a current snapshot but as an ordered sequence of domain events — the full history of every state change. The current state is derived by replaying the event history.

```
Traditional persistence:
  orders table: { id: "ord-123", status: "shipped", total: 59.98, ... }
  → Current state stored. History lost.

Event sourcing:
  events table / event store:
  [OrderPlaced { order_id: "ord-123", total: 59.98, ... }]
  [PaymentConfirmed { order_id: "ord-123", payment_id: "pay-456" }]
  [OrderShipped { order_id: "ord-123", tracking_number: "TRK-789" }]
  → Full history preserved. Current state rebuilt by replaying events.
```

**Benefits:**
- Complete audit trail — every state change is recorded with its full context.
- Temporal queries — reconstruct the state at any point in history ("what was order ord-123's status on March 10?").
- Event replay — replay events through a new projection to build a new read model (e.g., add a new analytics view without migrating data).
- Natural fit with CQRS — events are the write model; projections are read models.

**Drawbacks:**
- Query complexity — you cannot `SELECT * FROM orders WHERE status = 'pending'`. You need projections (read models) built from the event stream.
- Event schema migration — changing an old event's structure requires an upcasting strategy.
- Performance — replaying hundreds of events to rebuild state requires snapshots (periodic state captures) for long-lived aggregates.

## Section 6: Trade-offs & Decision-Making

**Q18. What are the trade-offs between event-driven and request-driven (RPC/REST) communication?**
A: Event-driven and request-driven architectures solve different problems and have complementary trade-off profiles:

**Request-driven (REST / gRPC):**
- **Temporal coupling:** Both services must be available simultaneously. Caller blocks until the callee responds.
- **Strong typing:** Request/response contracts are explicit; errors surface immediately.
- **Simplicity:** Easy to reason about — one call, one response, synchronous control flow.
- **Best for:** Operations requiring immediate feedback (user-facing reads, checkout validation, login), operations where the caller must know the outcome before proceeding.

**Event-driven:**
- **Temporal decoupling:** Publisher and consumers don't need to be available simultaneously. The broker buffers events.
- **Spatial decoupling:** Publisher doesn't know about consumers — new consumers can be added without changing the publisher.
- **Eventual consistency:** Consumers may lag behind the publisher. The system converges to consistency over time.
- **Complexity:** Harder to trace a flow across services. Debugging requires distributed tracing and event log inspection.
- **Best for:** Notifying multiple systems of a state change, background processing, workflows spanning long time periods, cross-bounded-context communication where decoupling is important.

**The hybrid (common in production):** Synchronous RPC for user-facing operations requiring immediate response; event-driven for cross-service notifications and async side effects. Example: a user places an order → synchronous call confirms the order is accepted → asynchronous events trigger inventory reservation, payment, shipping, notifications.

**Q19. When should a domain event be published immediately vs deferred?**
A: Publication timing has consistency and ordering implications:

**Publish immediately (within the same thread, before returning to caller):**
- Appropriate for in-process event buses where consumers run within the same transaction.
- Risk: if the event triggers side effects that fail, rolling back the original transaction may be inconsistent with already-dispatched events.

**Publish after transaction commit (recommended for external events):**
- Ensures events are only published when the state change is durable.
- Use the outbox pattern for reliability (state + event record written atomically; relay publishes after commit).
- Slight delay between state change and event publication — acceptable for most asynchronous workflows.

**Publish at end of aggregate's unit of work:**
- Collect events during the aggregate operation; publish all at the end of the command handler after successful save.
- Ensures events are ordered correctly (all events from one command are published in the order they were raised).

**Deferred/scheduled publication:**
- For events tied to time (`SubscriptionRenewalDue`, `TrialExpiring`): store in a scheduled event table, publish at the appropriate time via a background job.
- For saga timeout events: publish after a delay if no response is received within the expected window.

**Q20. How do you handle event ordering and idempotency in consumers?**
A: Two separate concerns that are often conflated:

**Ordering:**
In Kafka, ordering is guaranteed within a partition. For events that must be processed in order for a given entity, use the entity's ID as the partition key — all events for `order:123` go to the same partition in the same order they were produced.

Cross-partition ordering is not guaranteed. Design consumers to be tolerant of out-of-order delivery:
- Include a `version` or `sequence_number` in the event. Consumers can detect and handle out-of-order events (buffer, re-sequence, or discard stale events).
- Use optimistic locking on the consumer's state: `UPDATE orders SET status=$new WHERE id=$id AND version=$expected_version`. Reject updates from events with a stale version.

**Idempotency:**
Consumers must be idempotent — processing the same event twice should produce the same outcome as processing it once. Strategies:
- **Natural idempotency:** Use `INSERT ... ON CONFLICT DO NOTHING` or `UPDATE ... WHERE NOT EXISTS (previous state)`. The DB constraint prevents duplicate effects.
- **Explicit deduplication (inbox pattern):** Track `event_id` in a processed events table. Skip events already in the table.
- **Idempotency key in external calls:** If the consumer calls an external API, pass the `event_id` as the idempotency key to the API.

## Section 7: Scenario / System Design Style Questions

**Q21. "Design the event model for an e-commerce platform's order lifecycle. What events do you define, what data do they carry, and who consumes them?"**
A: A structured event model for the full order lifecycle:

**Domain events (raised by Order aggregate):**

```
OrderPlaced {
  order_id, customer_id, line_items[],
  total_cents, currency, shipping_address,
  placed_at
}
Consumers: InventoryService (reserve stock), PaymentService (initiate charge),
           NotificationService (confirm email), AnalyticsService (order funnel)

PaymentConfirmed {
  order_id, payment_id, amount_cents, payment_method,
  confirmed_at
}
Consumers: FulfillmentService (start picking), NotificationService (payment receipt)

OrderShipped {
  order_id, shipment_id, carrier, tracking_number,
  estimated_delivery_date, shipped_at
}
Consumers: NotificationService (shipping email), CustomerService (update order view)

OrderDelivered {
  order_id, shipment_id, delivered_at
}
Consumers: ReviewService (trigger review request), LoyaltyService (credit points)

OrderCancelled {
  order_id, cancelled_by, reason, cancelled_at
}
Consumers: InventoryService (release reservation), PaymentService (initiate refund),
           NotificationService (cancellation email)

RefundIssued {
  order_id, refund_id, amount_cents, refund_method, issued_at
}
Consumers: NotificationService (refund confirmation), AccountingService (record)
```

**Design notes:**
- Each event carries enough data for consumers to act independently (fat events).
- `order_id` is the partition key on Kafka — all order events are ordered per order.
- Consumers are independent — `NotificationService` does not need to know about `InventoryService`.
- Compensation events (`RefundIssued`) are first-class events, not just reactive adjustments.

**Q22. "A colleague proposes publishing a single 'OrderUpdated' event whenever anything changes about an order. What are the problems with this design?"**
A: This is a common anti-pattern — the generic update event — with several concrete problems:

**Loss of semantic meaning:** `OrderUpdated` tells consumers that something changed, but not what. A consumer interested in shipment status must inspect the payload to determine if the relevant field changed — coupling the consumer to the full order schema.

**Forced polling behavior:** Consumers that only care about specific transitions (e.g., `status` changing from `CONFIRMED` to `SHIPPED`) must consume every `OrderUpdated` event, check if the relevant field changed, and discard most events. This reintroduces polling behavior in an event-driven system.

**Schema instability:** Every new field added to the order becomes a potential change to `OrderUpdated`'s payload — broadening the schema surface area that all consumers must handle.

**Loss of causality and intent:** `OrderUpdated` erases the reason for the change. Was the address corrected by the customer? Updated by a support agent? Auto-corrected by an address validation service? Different consumers may need to react differently based on the cause. Distinct events (`AddressCorrectedByCustomer`, `AddressCorrectedBySupport`) carry this information naturally.

**Missed events on bulk updates:** If ten fields change in one operation, one `OrderUpdated` event fires — but consumers can only see the final state, not the intermediate steps. Fine-grained events (`OrderItemQuantityAdjusted`, `ShippingAddressUpdated`) preserve the full change history.

**Correct design:** Model the specific state transitions that matter to the business as distinct, named events. `OrderConfirmed`, `OrderItemQuantityAdjusted`, `ShippingAddressUpdated`, `OrderShipped`, `OrderDelivered`, `OrderCancelled` — each named in the ubiquitous language, each carrying only the data relevant to that specific change.

**Q23. "You're designing a multi-service checkout flow: inventory reservation → payment → shipment creation → confirmation email. Model this as both choreography and orchestration. Which do you recommend and why?"**
A: Both models for the same flow:

**Choreography:**
```
OrderService publishes: OrderPlaced
  → InventoryService: listens, reserves stock
    → publishes: InventoryReserved
      → PaymentService: listens, charges payment
        → publishes: PaymentCharged
          → ShippingService: listens, creates shipment
            → publishes: ShipmentCreated
              → NotificationService: listens, sends email
                → publishes: ConfirmationEmailSent
```

**Orchestration:**
```
OrderOrchestrator (SAGA):
  1. → ReserveInventory (command to InventoryService)
  2. ← InventoryReserved (event from InventoryService)
  3. → ChargePayment (command to PaymentService)
  4. ← PaymentCharged (event from PaymentService)
  5. → CreateShipment (command to ShippingService)
  6. ← ShipmentCreated (event from ShippingService)
  7. → SendConfirmationEmail (command to NotificationService)
  8. ← ConfirmationEmailSent (event from NotificationService)
  On failure at step 4 (PaymentFailed):
    → ReleaseInventory (compensating command to InventoryService)
    → MarkOrderFailed (update Order status)
```

**Recommendation: orchestration for this use case.** Reasons:
- Four services in a strict sequence with compensation logic — the workflow is complex enough to justify a coordinator.
- Business logic (retry payment? what constitutes failure? what gets compensated?) belongs in one place, not scattered across four services.
- Observability: the orchestrator's state shows exactly where each order is in the flow — invaluable for support and debugging.
- Compensation is explicit and testable — the orchestrator knows what to undo and in what order.

Choreography would be preferable if the services were more independent (order of steps didn't matter, no compensation needed, steps could be added/removed without workflow changes). For a strict sequential flow with compensation, orchestration wins on maintainability.

**Q24. "Your team wants to use events for both internal and external communication. Should you use the same event schema for both?"**
A: Almost always no — separate schemas for internal (domain events) and external (integration events) serve different purposes and evolve at different rates:

**Internal domain events:**
- Can use domain model types (value objects, enums, domain-specific concepts).
- Optimized for the domain — carry internal IDs, internal state that may be meaningless outside.
- Can change freely as the domain model evolves — no external consumers to break.
- May be synchronous, in-process, or via an internal event bus.

**External integration events:**
- Must use primitive, language-agnostic types.
- Must be versioned and backward-compatible — external teams cannot be forced to update simultaneously.
- Must hide internal implementation details (internal database IDs, internal state names that are implementation details).
- Must be documented as a public API contract.
- May need to be translated (internal `CustomerId` → external `customer_id` string).

**The translation layer:** A domain event handler listens to internal domain events and translates them to integration events for external publication:

```typescript
class OrderPlacedDomainEventHandler {
  async handle(event: OrderPlacedDomainEvent): Promise<void> {
    // Translate domain event to integration event
    const integrationEvent: OrderPlacedIntegrationEvent = {
      event_id: uuid(),
      event_type: 'OrderPlaced',
      event_version: '1.2',
      occurred_at: event.placedAt.toISOString(),
      order_id: event.orderId.value,          // unwrap value object → primitive
      customer_id: event.customerId.value,
      line_items: event.lineItems.map(item => ({
        product_id: item.productId.value,
        quantity: item.quantity,
        unit_price_cents: item.unitPrice.toCents()  // domain Money → integer cents
      })),
      total_cents: event.total.toCents(),
      currency: event.total.currency
    };

    // Publish to external message broker via outbox
    await this.outbox.save(integrationEvent);
  }
}
```

This separation lets the domain evolve freely while the public contract remains stable. External consumers are insulated from internal refactoring.

## Quick Reference: Message Type Comparison

| Aspect | Command | Event | Query |
|---|---|---|---|
| Intent | Request to change state | Record that state changed | Request for information |
| Tense | Future / imperative | Past / declarative | Present / interrogative |
| Naming convention | Verb + Noun (`PlaceOrder`) | Noun + Past Verb (`OrderPlaced`) | Get/Find/List + Noun |
| Direction | Targeted (one recipient) | Broadcast (any subscribers) | Targeted (one responder) |
| Rejection | Can be rejected | Cannot be rejected (it happened) | Can return empty/error |
| State change | Intended | Already occurred | None (read-only) |
| Response | Expected (success/failure) | Optional (fire and forget) | Always returns data |
| Sender coupling | Knows the recipient | Doesn't know consumers | Knows the responder |
| Multiplicity | One handler | Many handlers | One handler |
| Example | `PlaceOrder` | `OrderPlaced` | `GetOrderById` |

## Quick Reference: Domain Event vs Integration Event

| Aspect | Domain Event | Integration Event |
|---|---|---|
| Scope | Within a bounded context | Across bounded contexts / services |
| Types | May use domain value objects | Primitive types only |
| Versioning | Internal — can change freely | Versioned public contract |
| Consumers | In-process or same service | External services / teams |
| Schema evolution | Free, internal refactoring | Backward-compatible only |
| Transport | In-memory bus, internal queue | Kafka, RabbitMQ, SNS/SQS |
| Durability requirement | Until transaction commits | Persistent, retained by broker |
| Naming | Domain language (may be verbose) | Public API language (stable terms) |

---

**Tip for the interview:** Event type questions expose two common confusions: (1) commands vs events — the candidate says "we publish an event to trigger X" when they mean "we send a command to X." An event doesn't trigger — it notifies. The recipient decides whether and how to react. If you're prescribing a reaction, it's a command; (2) domain vs integration events — using the same schema internally and externally is the most common anti-pattern. Know that domain events are free to change because they're internal; integration events are public contracts that require versioning. The outbox pattern question almost always follows — interviewers want to see that you know events shouldn't be published in the same transaction that modifies state, but must be published atomically with that state change. The answer is always the outbox.
