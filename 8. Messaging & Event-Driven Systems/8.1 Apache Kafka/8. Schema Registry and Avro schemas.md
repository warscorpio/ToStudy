# Schema Registry and Avro Schemas — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Schema Management Exists

**Q1. What breaks when Kafka producers and consumers share no schema contract?**
A: Without a schema contract, Kafka is a raw byte pipe — any producer can write any byte sequence to any topic. This creates three failure modes:

- **Silent data corruption**: A producer encodes a field as an integer; a consumer deserializes the same bytes as a string. No exception is thrown — the consumer silently reads garbage data downstream.
- **Tight coupling through out-of-band coordination**: Schema changes require synchronizing every producer and consumer deployment simultaneously. A producer deploying a new field must wait until all consumers are updated, or they will fail to deserialize the new payload.
- **No schema evolution safety net**: Adding a field, removing a field, or changing a type can silently break consumers that were written against an older shape of the data — with no mechanism to detect the incompatibility before it reaches production.

A schema registry solves all three by centralizing schema definitions, enforcing compatibility rules at write time, and embedding schema references into the message payload so consumers always know how to deserialize exactly what they receive.

**Q2. What is the Confluent Schema Registry and where does it fit in the Kafka architecture?**
A: The Confluent Schema Registry is a separate service (not part of the Kafka broker) that acts as a centralized repository for Avro, Protobuf, and JSON Schema definitions. Producers register schemas before (or during) their first write; consumers retrieve schemas by ID before deserializing. The registry enforces compatibility rules — rejecting schema changes that would break existing producers or consumers.

In the data flow:
```
Producer → [serializer checks/registers schema with registry] → Kafka broker
                                                                      ↓
Consumer ← [deserializer fetches schema from registry by ID] ← Kafka broker
```

The Kafka broker itself remains schema-agnostic — it stores and delivers raw bytes. The registry sits alongside it, and its availability is on the critical path for producing and consuming: if the registry is down and no cached schema is available, producers and consumers will fail. This makes the registry a component that needs its own high-availability setup (typically deployed with 3 replicas backed by a Kafka topic, `_schemas`, for durability).

**Q3. What is Apache Avro and why is it the dominant serialization format in the Kafka ecosystem?**
A: Apache Avro is a binary serialization framework developed within the Hadoop ecosystem. Its design decisions make it well-suited to Kafka:

- **Schema is required for deserialization**: Unlike JSON, which is self-describing, Avro binary encoding is compact and carries no field names — the schema must be available to decode it. This forces explicit schema management rather than allowing it to be an afterthought.
- **Binary encoding is compact**: Avro strips field names and type info from the encoded bytes. A JSON object `{"user_id": 12345, "amount": 99.99}` might serialize to 38 bytes; the Avro equivalent might be 9 bytes. For high-throughput Kafka topics, this difference in per-message overhead compounds significantly.
- **Native schema evolution support**: Avro defines clear rules for adding, removing, and renaming fields with defaults — enabling producers and consumers to evolve independently within defined compatibility bounds.
- **Rich type system**: Avro supports primitives, records, arrays, maps, unions (nullable fields), enums, and logical types (dates, timestamps, decimals) — sufficient for most event schemas without the verbosity of JSON Schema.

Protobuf is a strong alternative — more explicit field numbering, better cross-language tooling — but Avro's native integration with Confluent's ecosystem, Kafka Streams, and Kafka Connect makes it the default for most Kafka deployments.

## Section 2: Schema Registry Internals

**Q4. How does the Schema Registry store schemas, and what makes it durable?**
A: The registry stores schemas in a compacted Kafka topic named `_schemas` (by default). Every registered schema, every compatibility setting, and every subject-to-schema mapping is written as a message to this topic. The topic is compacted — the latest value for each key (schema ID, subject, etc.) is retained indefinitely.

This design gives the registry several properties:
- **Durability**: Schema data survives registry process restarts because the backing store is Kafka itself — with the same replication guarantees as any other Kafka topic.
- **Multi-node consistency**: Multiple registry instances read from `_schemas` and maintain an in-memory cache. The primary writer is elected among instances; reads can be served by any node from cache.
- **Bootstrapping**: A new registry instance replays `_schemas` from the beginning on startup, reconstructing the full schema store from the Kafka log — no separate database required.

Schema IDs are monotonically increasing integers assigned by the registry. A schema registered for the first time gets ID 1; the next new schema gets ID 2; and so on across all subjects. These IDs are global and never recycled.

**Q5. What is a "subject" in Schema Registry terminology?**
A: A subject is the namespace under which a schema is registered and versioned. By default, Confluent's serializers use two subject naming strategies:

- **TopicNameStrategy** (default): The subject name is derived from the Kafka topic name — `{topic-name}-value` for value schemas and `{topic-name}-key` for key schemas. A topic `payments` produces subjects `payments-value` and `payments-key`.
- **RecordNameStrategy**: The subject name is the fully qualified Avro record name (e.g., `com.example.payments.PaymentEvent`). The same schema can be used across multiple topics; compatibility is enforced per record type rather than per topic.
- **TopicRecordNameStrategy**: Combines both — `{topic-name}-{record-name}`. A given record type evolving differently on different topics.

The choice of naming strategy has significant architectural implications: TopicNameStrategy ties schema evolution to topic evolution (one topic = one schema lineage), while RecordNameStrategy enables reuse of the same schema type across multiple topics with a single compatibility boundary.

**Q6. How does the wire format embed schema identity into a Kafka message?**
A: Confluent's standard wire format prepends a 5-byte header to every Avro-serialized message:

```
Byte 0:   Magic byte (always 0x00) — identifies this as a Confluent-schema-encoded message
Bytes 1-4: Schema ID (4-byte big-endian integer) — the registry ID of the schema used to encode this message
Bytes 5+: Avro binary-encoded payload
```

When a consumer reads a message, the deserializer:
1. Reads byte 0 — confirms it is `0x00` (magic byte; fails if not, indicating a non-schema-registry encoded message).
2. Reads bytes 1–4 — extracts the schema ID.
3. Looks up the schema by ID in its local cache or fetches it from the registry.
4. Deserializes bytes 5+ using the retrieved writer schema.

This design means the consumer never needs to know which schema version the producer used — the schema ID embedded in the message payload carries that information. Consumers can cache schemas by ID aggressively (schema IDs are immutable once assigned) and typically only hit the registry for the first message encoded with a new schema version.

## Section 3: Avro Schema Fundamentals

**Q7. What does an Avro schema look like, and what are its core types?**
A: An Avro schema is a JSON document. A simple record schema:

```json
{
  "type": "record",
  "name": "PaymentEvent",
  "namespace": "com.example.payments",
  "fields": [
    { "name": "payment_id",  "type": "string" },
    { "name": "user_id",     "type": "long" },
    { "name": "amount",      "type": { "type": "bytes", "logicalType": "decimal", "precision": 18, "scale": 2 } },
    { "name": "currency",    "type": { "type": "enum", "name": "Currency", "symbols": ["INR", "USD", "EUR"] } },
    { "name": "timestamp",   "type": { "type": "long", "logicalType": "timestamp-millis" } },
    { "name": "metadata",    "type": ["null", "string"], "default": null }
  ]
}
```

Core Avro types:
- **Primitives**: `null`, `boolean`, `int`, `long`, `float`, `double`, `bytes`, `string`
- **Complex**: `record` (named fields), `enum` (fixed symbol set), `array` (homogeneous list), `map` (string-keyed map), `union` (one of several types), `fixed` (fixed-size bytes)
- **Logical types**: Annotations on primitives — `decimal` (on bytes/fixed), `date` (on int), `time-millis`/`time-micros` (on int/long), `timestamp-millis`/`timestamp-micros` (on long), `uuid` (on string)

Logical types are not enforced by Avro's binary codec — they are hints to code generators and readers. A `timestamp-millis` field is stored as a `long`; the logical type tells the generated class to expose it as a datetime object.

**Q8. What is the difference between the writer schema and the reader schema?**
A: When a message is written (serialized), it is encoded using the **writer schema** — the schema the producer registered and used. When a message is read (deserialized), the consumer may be using a **reader schema** — a newer (or older) version of the schema that the consumer was compiled against.

Avro's resolution algorithm reconciles the two:
- Fields present in the writer schema but absent in the reader schema are **ignored** (projection).
- Fields present in the reader schema but absent in the writer schema use the reader schema's **default value** (injection).
- Fields present in both schemas are matched by **field name** (not by position, unlike Protobuf), and their types must be compatible.

This writer/reader schema duality is what enables schema evolution — a producer can add a new optional field (with a default), and existing consumers compiled against the old schema will continue to work because the resolution algorithm injects the default for the missing field. The schemas don't need to be identical; they need to be compatible.

**Q9. How does Avro handle nullable fields? What is the union pattern?**
A: Avro does not have a native "nullable" type. Nullable fields are represented as a **union** of `null` and another type:

```json
{ "name": "metadata", "type": ["null", "string"], "default": null }
```

This union means the field can hold either a null value or a string. The `default` must match the first type in the union — so if `null` is first, the default is `null`; if `"string"` is first, the default must be a string. Conventionally, nullable fields in Kafka schemas always put `null` first in the union and default to `null` — this preserves backward compatibility (a consumer that doesn't know about this field gets `null` as the default).

In code generated by Avro (e.g., via the Avro Maven plugin), a `["null", "string"]` field generates a `CharSequence` (or `Optional<String>` in some codegen variants) rather than a plain `String`. This forces developers to handle the nullable case at compile time rather than at runtime — a useful property for a field that might not always be present.

## Section 4: Schema Evolution and Compatibility

**Q10. What are the four compatibility modes in Schema Registry and what do they each mean?**
A: Compatibility modes define which schema versions can coexist — specifically, whether a new schema version can be read by consumers using older schemas (or vice versa).

- **BACKWARD** (default): A new schema can read data written by the previous schema version. Old producers, new consumers — the consumer is upgraded first. Adding a field with a default is backward-compatible; removing a required field is not.

- **FORWARD**: A previous schema can read data written by the new schema version. New producers, old consumers — the producer is upgraded first. Removing a field with a default is forward-compatible; adding a required field is not.

- **FULL**: Both backward and forward compatibility — the new schema can read old data AND old schemas can read new data. The most restrictive: only allows adding or removing optional fields (fields with defaults). Both sides can be upgraded in any order.

- **NONE**: No compatibility checking. Any schema can be registered. Use only in development or for topics where strict decoupling of producers and consumers is guaranteed by other means.

Each mode has a `_TRANSITIVE` variant (`BACKWARD_TRANSITIVE`, `FORWARD_TRANSITIVE`, `FULL_TRANSITIVE`) that checks compatibility against **all** previous schema versions, not just the immediately preceding one. Non-transitive checks only compare v(N) with v(N-1) — a schema can be compatible with its predecessor but incompatible with v(N-3) if several steps of evolution have drifted. Transitive modes prevent this accumulation of drift.

**Q11. Which schema changes are backward-compatible and which are breaking?**
A: With `BACKWARD` compatibility (the default — new schema reads old data):

| Change | Backward-Compatible? | Reason |
|---|---|---|
| Add field with default | ✅ Yes | Old data lacks the field; new schema uses the default |
| Add field without default | ❌ No | Old data lacks the field; new schema has no fallback |
| Remove field | ✅ Yes | New schema simply ignores the field in old data |
| Rename field | ❌ No | New schema can't match old field by name |
| Change field type (incompatible) | ❌ No | e.g., `string` → `int`; bytes can't be promoted |
| Change field type (compatible promotion) | ✅ Yes | `int` → `long` is a valid Avro type promotion |
| Add enum symbol | ✅ Yes | Old data never contains the new symbol |
| Remove enum symbol | ❌ No | Old data may contain the removed symbol |
| Change default value | ✅ Yes | Defaults are a reader-schema concern; no impact on encoded data |

The mental model for `BACKWARD`: "if I upgrade the consumer before the producer, will the consumer break?" Adding a field with a default never breaks an upgraded consumer reading old producer data. Removing a required field never breaks an upgraded consumer reading old producer data (old data had the field, but the new consumer simply won't read it).

**Q12. A producer wants to rename a field in an existing Avro schema. How do you do this without a breaking change?**
A: Avro has no native field aliasing mechanism like Protobuf's field number retention. The safe rename path uses Avro's `aliases` feature:

```json
// Version 1
{ "name": "user_id", "type": "long" }

// Version 2 — rename to account_id, keep user_id as alias
{ "name": "account_id", "type": "long", "aliases": ["user_id"] }
```

When the resolution algorithm encounters a reader schema with `account_id` and a writer schema with `user_id`, it uses the alias to match the fields. This allows:
- New consumers (compiled against v2) to read data written by old producers (using `user_id`) — the alias maps `user_id` → `account_id`.
- Old consumers (compiled against v1) to read data written by new producers (using `account_id`) — forward compatibility via aliases also works if the alias is in the writer schema.

**Critical caveat**: aliases are a resolution hint for the deserialization layer — they are not a rename in the binary encoding. The binary encoding for v1 still has `user_id` as the field name in the schema context; v2 consumers just know to accept `user_id` as equivalent to `account_id`. Once all producers have migrated to v2 and all old v1 data has been consumed (or expired), the alias can be removed in v3.

## Section 5: Registry API and Serializer/Deserializer Internals

**Q13. Walk through what happens when a producer serializes its first message with `KafkaAvroSerializer`.**
A:

```
1. Producer constructs a GenericRecord or SpecificRecord (compiled from the schema).

2. KafkaAvroSerializer is invoked with the record and the topic name.

3. Serializer derives the subject name from the topic:
   "payments" + "-value" → subject = "payments-value"

4. Serializer calls Schema Registry REST API:
   POST /subjects/payments-value/versions
   Body: { "schema": "<avro schema JSON string>" }

5. Registry checks:
   a. Has this exact schema been registered before?
      → Yes: return existing schema ID (no new version created)
      → No: check compatibility against the latest version under "payments-value"
         → Compatible: register as a new version, assign a new global schema ID
         → Incompatible: return 409 Conflict — producer write fails

6. Serializer receives the schema ID (e.g., 42).

7. Serializer writes the wire-format message:
   [0x00][0x00 0x00 0x00 0x2A][<avro binary payload>]
    magic byte   schema ID = 42       encoded record

8. The raw bytes are sent to the Kafka broker as the message value.
   The broker stores bytes without any schema knowledge.

9. For subsequent messages with the same schema, the serializer uses its
   local cache (schema → ID) and skips the registry call entirely.
```

The key insight in step 5a: registering the same schema twice returns the existing ID — registration is idempotent by schema content. The registry only assigns a new ID when the schema content (not just the version) is new.

**Q14. How does `KafkaAvroDeserializer` handle schema evolution — specifically, reading a v2 message with a v1 reader schema?**
A:

```
1. Consumer reads raw bytes from the Kafka broker.

2. KafkaAvroDeserializer reads byte 0 → 0x00 (magic byte, confirms wire format).

3. Reads bytes 1-4 → schema ID = 43 (the writer schema ID, embedded by the producer).

4. Deserializer checks local cache for schema ID 43.
   → Cache miss: calls GET /schemas/ids/43 → receives the v2 schema JSON.
   → Result cached by ID 43 for all future messages.

5. Deserializer has the writer schema (v2, from registry) and the reader schema (v1, compiled into the consumer application).

6. Avro DatumReader is initialized with both schemas.
   Resolution algorithm maps writer fields to reader fields:
   - Fields in both v1 and v2: matched by name, values decoded normally.
   - Fields in v2 (writer) not in v1 (reader): decoded and discarded (ignored).
   - Fields in v1 (reader) not in v2 (writer): injected with v1 default value.

7. The consumer receives a v1-shaped object with all known fields populated —
   new fields added in v2 are invisible to the v1 consumer but don't cause errors.
```

This is the mechanism that makes independent producer/consumer deployments possible: the consumer doesn't need to know the producer upgraded its schema. The schema ID in the wire format ensures the correct writer schema is always retrievable, and Avro's resolution algorithm handles the reconciliation.

**Q15. How does Schema Registry caching work, and what are the failure implications?**
A: Both the producer serializer and consumer deserializer maintain a local in-memory cache:

- **Producer**: caches `(subject, schema) → schema ID`. Once a schema has been registered and its ID retrieved, subsequent messages skip the registry call.
- **Consumer**: caches `schema ID → Schema object`. Once a writer schema has been fetched from the registry, all subsequent messages with the same schema ID use the cached schema without a network call.

The implication: Schema Registry being unavailable is only fatal on cold start or when a new schema ID is first encountered. In steady-state operation (same schema version, warm cache), producers and consumers function without any registry connection. This is why Schema Registry downtime often goes unnoticed in short windows — running producers and consumers are cache-warm and continue operating.

The danger: if the registry is down when a new schema version is first deployed (producer sees a new schema, tries to register it, fails), the producer cannot write. The registry must be available at schema deployment time. Operationally, this means the schema registry should have higher availability SLAs than the Kafka topics it serves, or producers must implement a retry strategy on registry unavailability.

## Section 6: Kafka Connect and Schema Registry

**Q16. How does Kafka Connect integrate with Schema Registry?**
A: Kafka Connect connectors can be configured to use `AvroConverter` (from Confluent) as the value and key converter:

```properties
value.converter=io.confluent.connect.avro.AvroConverter
value.converter.schema.registry.url=http://schema-registry:8081
key.converter=io.confluent.connect.avro.AvroConverter
key.converter.schema.registry.url=http://schema-registry:8081
```

With this configuration:
- **Source connectors** (e.g., Debezium for CDC, JDBC source): The connector reads from the source system, constructs Kafka Connect's internal `Schema` + `Struct` representation, and the `AvroConverter` serializes it to Avro wire format — registering the schema in the registry as it goes. The downstream Kafka topic carries Avro messages with embedded schema IDs.
- **Sink connectors** (e.g., JDBC sink, Elasticsearch sink): The connector reads Avro messages from Kafka, uses the embedded schema ID to fetch the schema from the registry, deserializes the payload into `Schema` + `Struct`, and writes to the sink system.

This makes schema registry the single source of truth for the data shape flowing through an entire Connect pipeline. Schema evolution in a CDC connector (e.g., a column added to a PostgreSQL table) flows automatically: Debezium detects the new column, updates its internal schema, `AvroConverter` registers a new schema version, and downstream consumers receive the new shape — subject to the configured compatibility mode.

## Section 7: Schema Design Patterns

**Q17. What is the "envelope pattern" and when is it used in Kafka Avro schemas?**
A: The envelope pattern wraps the actual event payload in a top-level record that carries metadata about the event:

```json
{
  "type": "record",
  "name": "EventEnvelope",
  "namespace": "com.example",
  "fields": [
    { "name": "event_id",   "type": "string" },
    { "name": "event_type", "type": "string" },
    { "name": "version",    "type": "int" },
    { "name": "occurred_at","type": { "type": "long", "logicalType": "timestamp-millis" } },
    { "name": "source",     "type": "string" },
    { "name": "payload",    "type": "bytes" }
  ]
}
```

Or a typed variant using a union for the payload:

```json
{ "name": "payload", "type": ["PaymentCreated", "PaymentFailed", "PaymentRefunded"] }
```

Use cases:
- **Multiple event types on one topic**: A single topic carries several event types (e.g., `payment-events`). The envelope's `event_type` or union payload type tells consumers which event shape they received, allowing them to route and deserialize selectively.
- **Audit and lineage**: Every event carries `event_id`, `occurred_at`, and `source` regardless of payload type — enabling audit queries without parsing the payload.
- **Routing without deserialization**: A stream processor can route messages by `event_type` from the envelope without deserializing the `payload` bytes, reducing coupling.

The trade-off: using a union type for payload requires that all possible payload types are declared in the envelope schema — adding a new event type requires a schema change to the envelope. For very open-ended event buses, `bytes` payload with a `content_type` field (and payload deserialized separately) offers more flexibility at the cost of losing schema enforcement on the payload itself.

**Q18. Should you put multiple event types on one Kafka topic? How does Schema Registry affect this decision?**
A: The "one topic, many event types" vs. "one topic per event type" debate has schema implications:

**One topic per event type** (simpler):
- Subject per topic (`payments-created-value`, `payments-failed-value`) — each has its own schema lineage.
- Compatibility enforcement is per event type independently.
- Consumers subscribe to exactly the events they care about — no client-side filtering.
- More topics = more partitions = more broker resources. Kafka doesn't scale infinitely on topic count (though KRaft has significantly raised this ceiling).

**Multiple event types on one topic**:
- Requires either the envelope pattern (one schema, union payload) or `RecordNameStrategy` (separate schema per record type, but all on one topic).
- With `TopicNameStrategy` (the default), all event types must share one schema subject — making independent evolution of each type's schema harder.
- With `RecordNameStrategy`, each record type has its own schema lineage regardless of topic — evolution is independent, but consumers must handle multiple schema IDs on one topic.

The pragmatic recommendation for a fintech system: **one topic per event type** for domain events where schema evolution needs to be managed independently (payments, transfers, KYC events). Reserve multi-type topics for lower-stakes event buses (audit logs, activity feeds) where the envelope pattern's operational simplicity outweighs its rigidity.

## Section 8: Scenario / System Design Style Questions

**Q19. "Your team ships a new version of the payment service that adds a `merchant_id` field to the PaymentEvent Avro schema. Consumers haven't been updated yet. Walk through what happens."**
A:

```
Before deployment:
  Schema Registry: payments-value → v1 (no merchant_id field)
  Producers: using v1
  Consumers: compiled against v1, cache warm with schema ID = 7

Producer deployment:
  New producer starts, constructs PaymentEvent with merchant_id populated.
  KafkaAvroSerializer:
    POST /subjects/payments-value/versions
    { "schema": "<v2 schema with merchant_id, default: null>" }
  
  Registry checks BACKWARD compatibility:
    merchant_id has "default": null → backward-compatible ✅
    Assigns schema ID = 8
  
  Producer serializes messages with schema ID 8 in wire format.

Consumer (still on v1, schema ID 7 in cache):
  Reads a new message, extracts schema ID = 8.
  Cache miss for ID 8 → fetches v2 schema from registry.
  
  Avro resolution:
    Writer schema (v2): has merchant_id
    Reader schema (v1): no merchant_id
    Resolution: merchant_id in writer, not in reader → field decoded and discarded.
  
  Consumer deserializes successfully into a v1-shaped object.
  merchant_id is silently ignored — consumer processes normally.

No consumer errors, no redeployment required.
```

The `default: null` on `merchant_id` is what makes this work in both directions — old consumers ignore the new field (backward compatibility), and if somehow old producers were still writing without `merchant_id`, new consumers would inject `null` as the default (forward compatibility if `FULL` is configured).

**Q20. "A monitoring alert fires: Schema Registry is returning 409 Conflict errors on a producer. What happened and how do you investigate?"**
A: A 409 Conflict from the registry means the producer attempted to register a new schema version that failed the compatibility check. Steps to investigate:

1. **Identify the subject and failing schema**: Enable debug logging in the producer or check the registry's own logs — the 409 response body contains which rule was violated and against which existing version.
   ```
   GET /subjects/payments-value/versions → list all versions
   GET /subjects/payments-value/versions/latest → current schema
   ```

2. **Check what changed**: Retrieve the failing schema from the producer (log it or retrieve it from the producer configuration/classpath). Diff it against the current latest version in the registry.

3. **Test compatibility explicitly**:
   ```
   POST /compatibility/subjects/payments-value/versions/latest
   Body: { "schema": "<new schema>" }
   → { "is_compatible": false }
   ```

4. **Common causes**:
   - A field was added without a default value (breaks BACKWARD).
   - A field was removed that has no default on the reader side (breaks FORWARD if FULL_TRANSITIVE is set).
   - An enum symbol was removed.
   - A field type was changed incompatibly (`string` → `int`).
   - A developer tested against a dev registry (with NONE compatibility) and is now deploying to prod (with BACKWARD).

5. **Resolution**: Fix the schema to be compatible (add a default, retain the field, use an alias). If the change is truly breaking and intentional (rare), the options are: (a) create a new topic with the new schema rather than evolving the existing one; (b) temporarily set the subject to `NONE` compatibility, register, then restore — only acceptable in emergencies with full consumer awareness.

**Q21. "You're designing the Kafka event schema for a payments platform at a fintech company. What schema design decisions do you make and why?"**
A: Key decisions and their rationale:

**Choose Avro + Schema Registry:**
```
Rationale: Payment data must be auditable, strongly typed, and evolvable.
JSON has no type enforcement; plain bytes have no contract.
Avro gives binary compactness, type safety, and built-in evolution semantics.
```

**Set FULL_TRANSITIVE compatibility on payment topics:**
```properties
# POST /config/payments-value
{ "compatibility": "FULL_TRANSITIVE" }
```
```
Rationale: Payment topics have long retention (7 years for audit). Consumers replaying
old data must be able to read any historical schema version. Producers must be able to
write data readable by consumers still on older schema versions.
FULL_TRANSITIVE (not just FULL) ensures every schema version is compatible with
every previous version — not just the immediately preceding one.
```

**Model financial amounts as `decimal` logical type, never `double`:**
```json
{ "name": "amount", "type": { "type": "bytes", "logicalType": "decimal", "precision": 18, "scale": 2 } }
```
```
Rationale: IEEE 754 double-precision floating point cannot represent most decimal
fractions exactly. 0.1 + 0.2 ≠ 0.3 in floating point. For money, this is
unacceptable. Avro's decimal logical type on bytes gives exact decimal arithmetic
backed by BigDecimal in Java and equivalent in other languages.
```

**Use `timestamp-millis` logical type for all timestamps:**
```json
{ "name": "occurred_at", "type": { "type": "long", "logicalType": "timestamp-millis" } }
```
```
Rationale: Storing timestamps as strings ("2024-01-15T10:30:00Z") loses timezone
context, introduces parsing ambiguity, and is verbose. A long in epoch-millis is
compact, unambiguous, and maps directly to Instant in Java, datetime in Python,
and Date in JavaScript.
```

**All optional fields: union with null first, default null:**
```json
{ "name": "merchant_category_code", "type": ["null", "string"], "default": null }
```
```
Rationale: Nullable fields with null-first union and null default preserve both
BACKWARD and FORWARD compatibility when fields are added. New optional fields
added to v2 → old consumers get null (backward). Old producers omitting the field
→ new consumers get null default (forward).
```

**Separate schemas per event type with one topic per type:**
```
payments.created   → PaymentCreated schema
payments.failed    → PaymentFailed schema
payments.refunded  → PaymentRefunded schema
```
```
Rationale: Payment lifecycle events have different fields, different consumers,
and different retention/compliance requirements. Co-locating them on one topic
with a union schema creates a single compatibility boundary for all three — a change
to PaymentRefunded's schema could block deployment of unrelated PaymentCreated changes.
Separate topics give independent schema evolution and independent consumer groups.
```

**Q22. "Your service consumes Avro events from a topic. The schema is at v5. During an incident, you need to replay messages from 3 months ago that were written with v2. Will your consumer handle this?"**
A: Yes, if the Schema Registry has retained all schema versions (which it does by default — schema versions are never deleted automatically). The resolution:

```
Old message (3 months ago):
  Wire format: [0x00][schema_id = 12 (v2)][avro binary payload with v2 shape]

Consumer (compiled against v5):
  Reads schema ID 12.
  Checks cache → miss (first time seeing ID 12 since startup, or cache was cold).
  Fetches schema ID 12 from registry → gets v2 schema.
  
  Avro resolution: writer = v2, reader = v5
  
  Fields in v2 that v5 also has → decoded normally.
  Fields removed from v2 to v5 (if any were removed with defaults) → injected with v5 defaults.
  Fields added in v3/v4/v5 not in v2 → injected with their default values.
  
  Consumer receives a v5-shaped object with:
    - All v2 fields populated from the actual message.
    - All fields added in v3, v4, v5 populated with their schema defaults.
```

**Critical prerequisite**: Every schema change from v2 → v3 → v4 → v5 must have been backward-compatible (BACKWARD_TRANSITIVE). If any intermediate version added a field without a default, or removed a field in a breaking way, the resolution for old messages will fail or produce incorrect data. This is why FULL_TRANSITIVE compatibility matters for long-retention topics: it ensures the current consumer can read any historical version, not just the previous one.

If schema versions were deleted from the registry (manually, or via `DELETE /subjects/{subject}/versions/{version}`), replaying old messages with those deleted schema IDs will fail with a 404 from the registry. Schema versions should never be deleted for topics with long-lived retention.

## Quick Reference

| Concept | Detail |
|---|---|
| Schema Registry | Separate service; stores schemas in `_schemas` Kafka topic; REST API |
| Wire format | `[0x00][4-byte schema ID][avro binary payload]` |
| Subject | Namespace for schema versioning; default: `{topic}-value`, `{topic}-key` |
| Schema ID | Global monotonically increasing integer; immutable once assigned |
| Writer schema | Schema used by the producer to encode a message |
| Reader schema | Schema the consumer uses to decode; may differ from writer |
| Resolution algorithm | Avro reconciles writer ↔ reader by field name; uses defaults for missing fields |
| BACKWARD compatibility | New schema reads old data; add fields with defaults, remove fields freely |
| FORWARD compatibility | Old schema reads new data; remove fields with defaults, add fields freely |
| FULL compatibility | Both backward and forward; only add/remove fields with defaults |
| `_TRANSITIVE` variants | Check against ALL previous versions, not just latest − 1 |
| Nullable fields | Union `["null", "T"]` with `"default": null`; null first is the convention |
| `decimal` logical type | Use for financial amounts — never `double` for money |
| `timestamp-millis` | Long epoch-millis; unambiguous, compact, timezone-safe |
| Registry caching | Serializers cache (schema → ID); deserializers cache (ID → schema); warm = no registry I/O |
| NONE compatibility | No checks; dev/testing only |
| Schema deletion | Avoid for long-retention topics — replaying old messages needs the writer schema ID |

## The Core Mental Model

```
Schema Registry is the contract enforcer between producers and consumers.

Producer side:
  Schema → Registry → Schema ID
  Schema ID embedded in every message (wire format)
  Registry rejects incompatible schemas before first message is written

Consumer side:
  Schema ID (from message) → Registry → Writer schema
  Writer schema + Reader schema → Avro resolution → typed object
  Consumer always knows how to decode any message it receives

Avro evolution model:
  Writer schema ≠ Reader schema is fine, if compatible
  Resolution bridges the gap using field names and defaults
  "backward" = consumer can be deployed first (reads old producer data)
  "forward" = producer can be deployed first (old consumer reads new data)
  "full" = either side can be deployed first

The nullable field convention:
  ["null", "string"] with default null
  → Compatible in both directions
  → New optional fields never break old consumers or old producers
  → Always use this for non-required fields

The financial amount rule:
  Never use double for money.
  Always: { "type": "bytes", "logicalType": "decimal", "precision": 18, "scale": 2 }
  Floating point is an approximation. Payments are exact.

The long-retention replay rule:
  FULL_TRANSITIVE compatibility + never delete schema versions
  = consumer can always replay any historical message, regardless of how many
    schema versions have evolved since it was written
```

---

**Tip for the interview:** Schema Registry questions at 5 YOE almost always escalate to one of three places: (1) the compatibility modes and what each allows — know `BACKWARD` vs `FULL_TRANSITIVE` and why transitive matters for long-retention replay; (2) the wire format and why the schema ID is in the message payload — what breaks if the registry is unavailable, and why warm-cache consumers survive registry downtime; (3) the writer/reader schema resolution — why consumers don't need to be updated when a backward-compatible schema change is deployed, and what the default injection mechanism does. The strongest signal at this level: knowing that `["null", "string"]` with `"default": null` (null-first union) is the only safe pattern for optional fields that preserves full compatibility, and understanding that `decimal` logical type (not `double`) is non-negotiable for financial data in Avro schemas. That's the nuance that separates someone who has deployed Kafka at a fintech from someone who has only used it for hobby projects.
