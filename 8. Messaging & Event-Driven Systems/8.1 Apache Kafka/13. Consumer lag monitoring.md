# Kafka Consumer Lag Monitoring — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is consumer lag and why does it matter?**
A: Consumer lag is the difference between the latest offset produced to a Kafka partition and the last offset committed by a consumer group for that partition. It represents how far behind the consumer is relative to the producer — the number of unconsumed records waiting in the partition.

```
Partition 0:
  Log end offset (LEO):        1,500   ← latest record written by producer
  Consumer committed offset:   1,350   ← last offset the consumer processed
  Lag:                           150   ← records not yet consumed
```

Lag matters because it is a direct measure of data freshness — how stale the consumer's view of the world is. A payment fraud detector with 50,000 records of lag is making decisions on data that may be minutes or hours old. An inventory service with growing lag is showing customers stock levels that don't reflect recent purchases. Monitoring lag is how you detect that a consumer is falling behind before that staleness causes business impact.

Lag is also an early warning system for system health: a consumer that was keeping up suddenly accumulating lag indicates a slowdown in the consumer, a spike in produce rate, or a downstream dependency (database, external API) that has become slow. Catching lag growth early allows intervention before it becomes a crisis.

**Q2. What are the two components of lag — offset lag vs time lag — and why does the distinction matter?**
A: **Offset lag** (records lag): the count of unconsumed records. `lag = log_end_offset - committed_offset`. Simple to measure; universally available from Kafka's offset metadata.

**Time lag** (timestamp lag): how old the oldest unconsumed record is. Measured by comparing the timestamp of the record at the consumer's current offset against wall-clock time.

The distinction matters because offset lag alone is misleading without knowing the produce rate:

```
Scenario A:
  Offset lag: 10,000 records
  Produce rate: 100,000 records/second
  Time lag: 0.1 seconds ← negligible; consumer is fine

Scenario B:
  Offset lag: 10,000 records
  Produce rate: 10 records/second
  Time lag: 1,000 seconds (16 minutes) ← serious; consumer is far behind
```

A payment processor with a lag of 10,000 records is fine if those records were produced in the last 100ms; it is a crisis if they represent 16 minutes of unprocessed transactions. Offset lag is the metric most tools expose; time lag is the metric that maps to business impact. Production monitoring should track both: offset lag for alerting on rate-of-change (lag growing = something is wrong), and time lag for SLA assessment (oldest unprocessed record > N seconds = SLA breach).

**Q3. What is the `__consumer_offsets` topic and how does it store lag information?**
A: `__consumer_offsets` is Kafka's internal compacted topic where consumer groups store their committed offsets. It is the source of truth for all consumer lag calculations.

Structure:
- **50 partitions** by default (configurable via `offsets.topic.num.partitions`).
- Each consumer group's offsets land on a specific partition, determined by `hash(group.id) % 50`.
- Records are key-value pairs:

```
Key:   {group: "payment-consumers", topic: "payments", partition: 3}
Value: {offset: 1350, metadata: "", commitTimestamp: 1721740980000, leaderEpoch: 5}
```

The topic is compacted — only the latest offset per `(group, topic, partition)` is retained. Old offset records are garbage-collected by the log compaction process.

Lag is derived by combining two pieces of information:
1. **Committed offset** — read from `__consumer_offsets` (what the consumer has processed).
2. **Log end offset** — queried from the partition leader (what has been produced).

`lag = log_end_offset - committed_offset`

Neither piece alone gives lag — you need both, fetched at approximately the same time. This is why lag monitoring tools must query both the broker metadata (for LEO) and the offset topic (for committed offsets) and correlate them.

## Section 2: Measuring Lag

**Q4. How do you measure consumer lag using Kafka's built-in CLI tools?**
A: Two primary CLI commands:

**`kafka-consumer-groups.sh --describe`** — the standard tool for point-in-time lag inspection:

```bash
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group payment-consumers \
  --describe

# Output:
GROUP              TOPIC     PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID                        HOST
payment-consumers  payments  0          1350            1500            150  consumer-1-abc123  /10.0.1.1
payment-consumers  payments  1          2100            2100            0    consumer-2-def456  /10.0.1.2
payment-consumers  payments  2          980             1050            70   consumer-3-ghi789  /10.0.1.3
payment-consumers  payments  3          0               0               0    -                  -
```

Key columns:
- `CURRENT-OFFSET` — the last committed offset for this consumer group + partition.
- `LOG-END-OFFSET` — the latest offset written to the partition (the high watermark).
- `LAG` — `LOG-END-OFFSET - CURRENT-OFFSET`.
- `CONSUMER-ID` — which consumer instance owns this partition. A `-` means no active consumer is assigned to this partition (the group may be stopped, or the partition count exceeds the consumer count).

**`kafka-consumer-groups.sh --list`** — lists all consumer groups, useful for discovering groups before inspecting them:

```bash
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --list

# Output:
payment-consumers
fraud-detector
analytics-pipeline
```

**Limitation of CLI tools:** they are point-in-time snapshots, not continuous monitoring. They don't alert, don't track lag trends, and are slow to poll manually at scale. Use them for debugging; use dedicated monitoring tools for production observability.

**Q5. How do you measure consumer lag programmatically using the Kafka Admin API?**
A: The Admin API provides the building blocks for lag calculation without the overhead of running a CLI tool in a subprocess:

```typescript
import { Kafka, Admin } from 'kafkajs';

const kafka = new Kafka({ brokers: ['kafka:9092'] });
const admin: Admin = kafka.admin();

async function getConsumerLag(
  groupId: string,
  topic: string
): Promise<Array<{ partition: number; lag: number; currentOffset: number; logEndOffset: number }>> {
  await admin.connect();

  // Step 1: get committed offsets for the consumer group
  const { topics } = await admin.fetchOffsets({ groupId, topics: [topic] });
  const committedOffsets = new Map(
    topics[0].partitions.map(p => [p.partition, parseInt(p.offset)])
  );

  // Step 2: get log end offsets (latest produced offset) for each partition
  const topicMeta = await admin.fetchTopicOffsets(topic);
  const logEndOffsets = new Map(
    topicMeta.map(p => [p.partition, parseInt(p.high)])
  );

  // Step 3: calculate lag per partition
  const result = [];
  for (const [partition, committed] of committedOffsets) {
    const leo = logEndOffsets.get(partition) ?? 0;
    const lag = leo - (committed === -1 ? 0 : committed);
    // committed = -1 means no offset committed yet; treat as 0 consumed
    result.push({ partition, lag, currentOffset: committed, logEndOffset: leo });
  }

  await admin.disconnect();
  return result;
}

// Example usage:
const lag = await getConsumerLag('payment-consumers', 'payments');
lag.forEach(({ partition, lag }) =>
  console.log(`Partition ${partition}: lag = ${lag}`)
);
```

This pattern underlies tools like Burrow, Kafka Exporter, and custom monitoring integrations. The key subtlety: `committed_offset = -1` means the consumer group has never committed an offset for this partition — treat as 0 consumed (full lag = LEO).

**Q6. How do you measure time-based lag (how old is the oldest unconsumed record)?**
A: Time lag requires fetching the timestamp of the record at the consumer's current committed offset:

```typescript
async function getTimeLag(
  groupId: string,
  topic: string,
  partition: number
): Promise<number> {  // returns lag in milliseconds
  const consumer = kafka.consumer({ groupId: `lag-monitor-${groupId}` });
  await consumer.connect();
  await consumer.subscribe({ topic, fromBeginning: false });

  // Get the committed offset for the group
  const committedOffset = await getCommittedOffset(groupId, topic, partition);
  if (committedOffset <= 0) return 0;

  // Seek to the committed offset and read one record to get its timestamp
  consumer.seek({ topic, partition, offset: committedOffset.toString() });

  let timestampMs: number | null = null;
  await new Promise<void>(resolve => {
    consumer.run({
      eachMessage: async ({ message }) => {
        timestampMs = message.timestamp ? parseInt(message.timestamp) : null;
        await consumer.stop();
        resolve();
      }
    });
  });

  await consumer.disconnect();

  if (!timestampMs) return 0;
  return Date.now() - timestampMs;  // lag in ms
}
```

In practice, most production systems measure time lag indirectly: monitor the timestamp embedded in records processed by the consumer (log the timestamp of each processed record alongside the wall clock) and emit a metric: `message_processing_delay_ms = now() - record.timestamp`. This avoids the overhead of a separate seek-and-read operation and gives a more accurate real-time view than the committed-offset approach.

## Section 3: Monitoring Tools

**Q7. What is Burrow and how does it differ from simple lag threshold alerts?**
A: Burrow (LinkedIn's open-source consumer lag evaluator) goes beyond point-in-time lag values by evaluating lag trends over a sliding window. Its key insight: a lag value alone is not enough to determine if a consumer is healthy — what matters is whether the lag is growing, stable, or shrinking.

Burrow's evaluation model:
- Maintains a sliding window of recent committed offset values per `(group, topic, partition)`.
- Evaluates the consumer's status based on movement within the window:

```
Status: OK
  Committed offset is advancing AND lag is stable or decreasing.
  The consumer is consuming; it may have some lag but it's keeping up.

Status: WARNING
  Committed offset is NOT advancing (consumer has stopped committing)
  BUT the log end offset is not advancing either (no new records).
  The consumer may be paused or the topic is quiet — not alarming yet.

Status: ERROR
  Committed offset is NOT advancing AND log end offset IS advancing.
  New records are being produced but the consumer is not consuming them.
  → This is the condition that warrants an alert.

Status: STALLED
  Committed offset is advancing but is exactly equal to the previous window's
  LEO — the consumer is consuming but producing is catching up faster than
  the consumer can process. Lag is growing.
```

Why this is better than threshold alerts: a simple `lag > 1000` alert fires whenever lag exceeds 1000 — even during a brief burst where the consumer will catch up in seconds. Burrow's trend analysis suppresses false positives from transient spikes and catches slow-growing lag that never crosses a simple threshold but indicates a consumer falling steadily behind.

```yaml
      # Alert if total lag for a critical consumer group exceeds threshold
      - alert: KafkaConsumerLagHigh

        for: 10m

          severity: critical
        annotations:
          summary: "Consumer lag growing at {{ $value }} records/second"

      - alert: KafkaConsumerGroupDead
        expr: kafka_consumergroup_members{consumergroup="payment-consumers"} == 0

          severity: warning

```

A: Confluent Control Center (part of Confluent Platform) provides a managed UI for Kafka observability, including consumer lag:

**Trade-off:** Control Center requires Confluent Platform (commercial license for production clusters). For open-source Kafka, Kafka Exporter + Prometheus + Grafana replicates most functionality at the cost of manual setup.

## Section 4: Lag Causes and Diagnosis

**Q10. What are the most common causes of consumer lag growth?**
A: Lag grows when the consumer's consume rate falls below the producer's produce rate. Root causes fall into four categories:

**Consumer-side processing slowdown:**
- A downstream dependency (database write, external API call, cache miss) becomes slow — each record takes longer to process, reducing throughput.
- GC pause (JVM consumers) — a long GC pause causes the consumer to stop polling; Kafka may trigger a rebalance if the pause exceeds `max.poll.interval.ms`, making things worse.
- `max.poll.records` too high — the consumer fetches 500 records per poll but takes 5 minutes to process them, causing the `max.poll.interval.ms` heartbeat to expire.
- Single-threaded processing of a multi-partition topic — one consumer thread processes records from all assigned partitions sequentially; adding consumer instances spreads the load.

**Producer-side throughput spike:**
- A batch job, flash sale, or viral event produces records at 10x the normal rate.
- The consumer was sized for normal throughput; the spike overwhelms it.
- Resolution: auto-scaling based on lag metric, or pre-scaling consumer instances ahead of known events.

**Rebalancing:**
- Consumer group rebalances (triggered by member join/leave or heartbeat timeout) pause all consumers for the duration of the rebalance. Records continue to accumulate; lag grows during the pause.
- Frequent rebalancing (e.g., frequent deployments, frequent crashes) causes chronic lag growth. Monitor rebalance frequency as a separate signal.

**Topic partition imbalance:**
- One partition receives far more records than others (due to skewed partitioning by key). The consumer assigned to the hot partition cannot keep up; others are idle. Total lag is dominated by one partition.
- Diagnosis: check lag per partition, not just total lag. Resolution: add more partitions (if the key space allows) or improve the partitioning strategy.

**Q11. How do you distinguish between a consumer that is slow vs a producer that has spiked?**
A: Both cause lag growth, but the resolution is different — a slow consumer needs more consumer instances or processing optimization; a producer spike may resolve on its own when the spike ends.

Diagnostic approach:

```
Step 1: Compare produce rate vs consume rate over time

  kafka_topic_partition_current_offset rate (produce rate):
    t=0: 1,000 records/sec  ← normal
    t=5: 1,000 records/sec  ← unchanged
    → Produce rate is stable

  kafka_consumergroup_current_offset rate (consume rate):
    t=0: 1,000 records/sec  ← normal
    t=5:   500 records/sec  ← dropped by half
    → Consumer throughput has halved → consumer-side problem

Step 2: Check consumer-side metrics (if instrumented)
  - records_processing_duration_ms: did processing time per record increase?
  - downstream_db_query_duration_ms: is the database slower?
  - consumer_rebalance_count: how many rebalances in the last hour?
  - JVM GC pause duration (for JVM consumers)

Step 3: Check if lag is partition-uniform or partition-skewed
  - All partitions lagging equally → consume rate problem (throughput)
  - One partition lagging, others caught up → hot partition (key skew)
  - Alternating partitions lagging → rebalancing causing uneven load
```

**Q12. What is the `max.poll.interval.ms` setting and how does it relate to lag?**
A: `max.poll.interval.ms` (default: 300,000ms = 5 minutes) is the maximum time between two consecutive `poll()` calls that a consumer can make before Kafka considers it dead and triggers a group rebalance. If a consumer fetches 500 records, takes 6 minutes to process them, and only then calls `poll()` again — the broker has already removed it from the group after 5 minutes. The partition is reassigned to another consumer; the processing of those 500 records was wasted (they'll be re-processed by the new owner), and the rebalance itself adds more lag.

**Relationship to lag:**
- Too large `max.poll.interval.ms`: consumers that are genuinely dead take longer to be detected; their partitions accumulate unprocessed lag for up to `max.poll.interval.ms` before reassignment.
- Too small `max.poll.interval.ms`: legitimate slow processing (a single record taking 2 minutes) triggers unnecessary rebalances that cause lag spikes.

**Correct configuration:**
```properties
# Set max.poll.interval.ms to comfortably exceed the worst-case single-batch processing time
max.poll.interval.ms=600000     # 10 minutes

# Reduce max.poll.records so each batch completes well within the interval
max.poll.records=100            # fetch 100 records; process in < 10 minutes

# Keep session.timeout.ms shorter (heartbeat-based liveness)
session.timeout.ms=45000        # broker detects crash within 45s
heartbeat.interval.ms=15000     # heartbeat every 15s (1/3 of session timeout)
```

The distinction: `session.timeout.ms` detects crashed consumers (missed heartbeats); `max.poll.interval.ms` detects live-but-stuck consumers (the consumer process is alive and sending heartbeats, but its processing thread is hung and not calling `poll()`).

## Section 5: Alerting Strategy

**Q13. What is a good alerting strategy for consumer lag — what to alert on and what to suppress?**
A: A poorly designed lag alerting strategy generates constant noise (false positives on transient spikes) or misses real problems (lag growing slowly but never crossing a static threshold). A production-grade strategy uses multiple complementary signals:

**Alert 1: Absolute lag threshold (high-severity, slow burn)**
```
Condition: total_lag > N for > 10 minutes
Threshold: set N at the lag that represents a meaningful SLA breach
  (e.g., payment-consumers: lag > 5,000 → ~50 seconds of processing backlog at 100 rec/s)
Purpose: catches sustained high lag that has already impacted freshness
For: 10m  ← suppresses transient spikes
```

**Alert 2: Lag growth rate (medium-severity, early warning)**
```
Condition: rate(lag[5m]) > threshold
  (lag is growing at > 100 records/second → will breach Alert 1 in ~50 seconds)
Purpose: early warning before the absolute threshold is breached
For: 5m  ← must be sustained growth, not a momentary spike
```

**Alert 3: Consumer group death (critical, fast)**
```
Condition: consumer_group_members == 0 for > 2 minutes
Purpose: consumer process has crashed or stopped; no recovery in progress
For: 2m  ← short window; a dead consumer group needs immediate attention
```

**Alert 4: Stalled consumer (medium-severity)**
```
Condition: committed_offset has not advanced in 30 minutes
  AND log_end_offset IS advancing (new records are being produced)
Purpose: consumer is alive (not dead — no rebalance triggered) but stuck
  (processing loop hung, waiting on a lock, or downstream dependency down)
For: 30m
```

**What NOT to alert on:**
- Transient spikes < 5 minutes: normal rebalance latency, brief downstream slowness. Use `for: 5m` minimum on all lag alerts.
- Low-priority consumer groups: a nightly analytics job accumulating lag during the day is expected. Tag groups with priority labels; only page for high-priority groups.
- Lag during planned maintenance: use alert silences in Alertmanager/PagerDuty during deployment windows.

**Q14. How do you set appropriate lag thresholds for different consumer types?**
A: A single threshold for all consumer groups is wrong — the acceptable lag for a fraud detector is very different from a nightly batch job. Threshold derivation:

**SLA-based (for latency-sensitive consumers):**
```
SLA: fraud decisions must be made on data < 5 seconds old
Produce rate: 10,000 records/second
Max acceptable lag: 5 seconds × 10,000 rec/s = 50,000 records
Alert threshold: lag > 30,000 (60% of max → early warning with time to react)
Critical threshold: lag > 50,000 (SLA breach imminent)
```

**Throughput-based (for batch consumers):**
```
Batch job processes 1M records/hour at peak
Acceptable completion window: 2 hours
Max acceptable lag: 2M records
Alert threshold: lag > 1.5M (75% of window consumed → job may not complete on time)
```

**No-lag consumers (exactly-once processing):**
```
Payment processing: any lag means transactions are delayed
Alert threshold: lag > 100 (near-zero tolerance; alert immediately on any sustained lag)
Critical threshold: lag > 1,000
```

Store thresholds as labels on the consumer group (in a config file or service metadata), not hardcoded in the alerting rules. This allows per-group tuning without modifying alert definitions.

## Section 6: Operational Patterns

**Q15. How do you reset a consumer group offset and when is it appropriate?**
A: Offset reset repositions a consumer group's committed offset to a different point in the partition — causing it to re-read records it has already processed (reset to earlier) or skip records it hasn't processed (reset to later).

**When to reset:**
- **Consumer bug fixed; need to replay**: the consumer had a processing bug that produced incorrect output. After fixing the bug, reset the offset to before the bug-affected range and replay to correct the output.
- **Lag is unrecoverable**: the consumer has fallen so far behind (e.g., millions of records) that catching up would take hours; the business decision is to skip to the present and accept the data loss.
- **Initial backfill**: a new consumer group needs to process the full topic history.
- **Topic retention expiry**: records before the retention window are gone; the committed offset points to deleted records. Reset to the earliest available offset.

**CLI commands:**
```bash
# Reset to the earliest available offset (replay all retained records)
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group payment-consumers \
  --topic payments \
  --reset-offsets --to-earliest \
  --execute

# Reset to the latest offset (skip all existing records; start fresh)
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group payment-consumers \
  --topic payments \
  --reset-offsets --to-latest \
  --execute

# Reset to a specific offset on a specific partition
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group payment-consumers \
  --topic payments:2 \               # partition 2 only
  --reset-offsets --to-offset 1000 \
  --execute

# Reset to a specific timestamp (useful for "reset to 2 hours ago")
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group payment-consumers \
  --topic payments \
  --reset-offsets --to-datetime 2024-07-23T12:00:00.000 \
  --execute

# Dry run first (always)
kafka-consumer-groups.sh ... --reset-offsets --to-latest --dry-run
```

**Important constraint:** the consumer group must be inactive (no running consumers) for an offset reset to succeed. If consumers are running, the reset is rejected.

**Q16. How do you implement auto-scaling of consumers based on lag?**
A: Consumer lag is the ideal autoscaling signal — it directly measures whether the current consumer fleet can keep up with the produce rate. Implementation options:

**KEDA (Kubernetes Event-Driven Autoscaling):**
KEDA is the production-standard solution for Kubernetes-based consumers. It polls Kafka consumer lag and scales a Kubernetes Deployment based on a lag threshold:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: payment-consumer-scaler
spec:
  scaleTargetRef:
    name: payment-consumer-deployment
  minReplicaCount: 2
  maxReplicaCount: 20
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka:9092
        consumerGroup: payment-consumers
        topic: payments
        lagThreshold: "1000"       # scale up when lag per partition > 1000
        activationLagThreshold: "10" # scale from 0 when lag > 10
        offsetResetPolicy: latest
```

KEDA polls the Kafka consumer group lag every 30 seconds (configurable), calculates the desired replica count as `ceil(total_lag / lagThreshold)`, and scales the Deployment accordingly. The replica count is bounded by `minReplicaCount` and `maxReplicaCount`.

**Upper bound: partition count.** Adding consumer instances beyond the topic's partition count is useless — excess consumers sit idle with no partitions assigned. Set `maxReplicaCount` to the topic's partition count.

**Scaling down cooldown:** KEDA's `cooldownPeriod` (default: 300s) prevents rapid scale-down after a lag spike, avoiding the thrash of scaling up to handle a burst and immediately scaling back down.

**Custom scaling (for non-Kubernetes or fine-grained control):**
```typescript
async function checkAndScale(groupId: string, topic: string) {
  const lagPerPartition = await getConsumerLag(groupId, topic);
  const totalLag = lagPerPartition.reduce((sum, p) => sum + p.lag, 0);
  const partitionCount = lagPerPartition.length;

  const desiredInstances = Math.min(
    Math.ceil(totalLag / TARGET_LAG_PER_INSTANCE),
    partitionCount  // never exceed partition count
  );

  const currentInstances = await getCurrentInstanceCount(groupId);

  if (desiredInstances > currentInstances) {
    await scaleUp(groupId, desiredInstances - currentInstances);
  } else if (desiredInstances < currentInstances - SCALE_DOWN_BUFFER) {
    await scaleDown(groupId, currentInstances - desiredInstances);
  }
}

// Run every 60 seconds
setInterval(() => checkAndScale('payment-consumers', 'payments'), 60_000);
```

**Q17. How do you monitor consumer lag for Kafka Streams applications specifically?**
A: Kafka Streams applications are consumers under the hood — they read input topics, process records, and produce to output topics. Their lag is exposed via standard consumer group metrics (the Streams application has a consumer group ID: `application.id`). However, Kafka Streams also exposes internal metrics that are more informative than raw lag:

**Standard consumer group lag (works with all monitoring tools):**
```bash
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group my-streams-app \       # = application.id in Streams config
  --describe
```

**Kafka Streams built-in metrics (via JMX or Prometheus JMX exporter):**

```
# Processing rate (records processed per second by this Streams instance)
kafka.streams:type=stream-metrics,client-id=my-streams-app
  process-rate            # records processed per second
  process-total           # total records processed

# Per-task metrics (one task per partition)
kafka.streams:type=stream-task-metrics,client-id=my-streams-app,task-id=0_0
  process-rate            # records/sec for this task (partition)
  commit-latency-avg      # average time between state store commits

# State store metrics (for stateful Streams applications)
kafka.streams:type=stream-state-metrics,client-id=my-streams-app,task-id=0_0
  put-rate                # state store write rate
  get-rate                # state store read rate
  flush-rate              # how often state is flushed to changelog topic
```

**End-to-end latency for Streams:** measure the difference between the event timestamp in the input record and the wall clock when the output record is produced. This is the true measure of streaming pipeline latency, including processing time, and is more meaningful than raw offset lag for Streams applications with stateful operations (joins, aggregations with windowing).

## Section 7: Scenario Questions

**Q18. "Consumer lag for your payment processor spiked to 500,000 records at 2am. By 3am it was back to zero. No alert fired during the spike. What happened and how do you fix your alerting?"**
A: The spike resolved itself — the consumer caught up — but the absence of an alert means the alerting was purely threshold-based with a threshold above 500,000, or the `for` duration was long enough that the spike resolved before the alert fired.

**Root cause of the spike (likely candidates):**
- A batch job ran at 2am producing a burst of records the consumer wasn't sized for. Consumer caught up after the burst ended.
- A scheduled deployment caused a rebalance at 2am; consumers paused during rebalance, lag accumulated, then recovered after the rebalance completed.
- A transient downstream slowdown (DB maintenance window, GC pause) slowed processing for ~1 hour.

**Why no alert fired:**
- `for: 60m` on the lag threshold alert — the spike lasted only 1 hour; the `for` condition never completed.
- Threshold was set above 500,000 — the spike didn't cross it.
- Alert was silenced for a maintenance window that was broader than necessary.

**How to fix alerting:**

Add a lag growth rate alert that fires faster than an absolute threshold:
```yaml
- alert: KafkaConsumerLagGrowingFast
  expr: rate(kafka_consumergroup_lag_sum{consumergroup="payment-consumers"}[5m]) > 5000
  for: 5m   # sustained growth for 5 minutes → alert
  labels:
    severity: warning
```

This fires when lag is growing at > 5,000 records/minute — it would have fired within 5 minutes of the 2am spike, giving the team 55 minutes before the spike resolved, rather than no alert at all.

Also add a max-lag-seen metric: even if the alert didn't fire, the monitoring dashboard should show a chart of lag over the past 24 hours. A spike to 500,000 that silently resolved is still a signal worth investigating — it reveals a capacity gap between the producer's burst capability and the consumer's sustained throughput.

**Q19. "You have a Kafka topic with 12 partitions and a consumer group with 3 consumers. Lag on partitions 0, 4, and 8 is consistently high while others are near zero. What is causing this and how do you fix it?"**
A: With 3 consumers and 12 partitions, each consumer is assigned 4 partitions. The default range or round-robin assignment for 3 consumers over 12 partitions:

```
Consumer 1: partitions 0, 1, 2, 3
Consumer 2: partitions 4, 5, 6, 7
Consumer 3: partitions 8, 9, 10, 11
```

Lag on partitions 0, 4, and 8 — one partition from each consumer — points to hot partitions. These three partitions receive significantly more records than partitions 1-3, 5-7, and 9-11. Within each consumer's four partitions, the hot partition consumes most of the consumer's processing capacity, leaving the other three partitions easily keeping up (near-zero lag).

**Root cause: partitioning key skew.** The producer's key-to-partition assignment concentrates a large fraction of records onto partitions 0, 4, and 8. This happens when:
- A popular key (`userId="celebrity_user"`, `tenantId="large_tenant"`) hashes to these partitions.
- A sequential key range lands disproportionately on these partition numbers.

**Fixes:**

1. **Add more partitions** — increase the topic from 12 to 24 or 36 partitions. The hot keys are spread across more partitions. Existing hot partitions may still be hot if the same keys land on them (hash redistribution is not uniform). Requires consumer rebalancing; no data migration needed (partitions can be extended in Kafka).

2. **Investigate and fix the key distribution** — identify which keys are producing to partitions 0, 4, 8 at high rate. If a single key dominates (`userId` of a viral user), use a salted key: `key = userId + "_" + random(0, NUM_SALT_BUCKETS)` to spread that user's records across multiple partitions. Consumers aggregate across the salt buckets in a later step.

3. **Add more consumer instances** — add 3 more consumers (total 6) so each consumer handles 2 partitions instead of 4. The hot partition (e.g., partition 0) is now the sole responsibility of one consumer instead of competing with partitions 1, 2, 3. This doesn't fix the hot partition — it just gives it a dedicated consumer.

4. **Custom partition assignment** — implement a custom `PartitionAssignor` that assigns hot partitions to different consumers rather than grouping them. Partition 0 (hot) goes to Consumer 1 alone; Consumers 2 and 3 handle the remaining partitions. This is complex and rarely warranted — fix the key distribution instead.

**Tip for the interview:** Consumer lag questions at 5 YOE level almost always go beyond "what is lag" into either alerting strategy or diagnosis. The distinction between offset lag and time lag is the first thing to establish — interviewers who have run production Kafka systems will immediately probe whether you know that 10,000 records of lag means nothing without knowing the produce rate. On alerting, the common mistake is relying solely on absolute thresholds; the `rate(lag[5m])` growth-rate alert is the signal that separates production-hardened systems from naive ones. For diagnosis, the partition-skew pattern (one partition consistently lagging while others are fine) is a classic scenario — knowing that it indicates hot partitions from key skew, not a consumer throughput problem, shows operational depth. If the interviewer asks about tools, knowing Burrow's trend-evaluation model (not just that it exists) is the 5 YOE answer; knowing only `kafka-consumer-groups.sh --describe` is the junior answer.
