# Kafka Producers: Batching, Compression, `acks` — Interview Q&A (5 YOE Level)

---

## Section 1: Producer Fundamentals

**Q1. What is a Kafka producer and what is its job?**
A: A Kafka producer is a client that publishes records to Kafka topics. Its responsibilities go beyond "send a message" — the producer is responsible for:
- **Serializing** the key and value to bytes.
- **Partitioning** — determining which partition of the topic the record goes to (via a partitioner: hash of the key, round-robin, or custom logic).
- **Batching** — accumulating multiple records into a single network request to amortize per-request overhead.
- **Compression** — reducing batch size before transmission.
- **Retry and delivery guarantees** — retrying on transient failures based on the `acks` setting and retry configuration.
- **Back-pressure** — blocking or throwing exceptions when the in-memory send buffer (`buffer.memory`) is full and the broker is not keeping up.

The producer is a sophisticated client with its own internal threading model: the application thread calls `producer.send()`, which places records into an in-memory `RecordAccumulator`; a background I/O thread (`Sender`) drains the accumulator and dispatches batches to brokers.

**Q2. What is the internal lifecycle of a `producer.send()` call?**
A:

```
Application thread calls producer.send(record)
        │
        ▼
1. Serialize key + value (using configured serializers)
2. Determine partition:
   - Key present → hash(key) % numPartitions
   - Key null     → sticky partition (batching optimization) or round-robin
3. Check metadata: do we know the leader for this partition?
   - No → fetch metadata from bootstrap brokers; block until available
4. Append record to RecordAccumulator batch for (topic, partition)
   - If no open batch: create a new ProducerBatch (ByteBuffer of linger.ms / batch.size)
   - If batch full or linger.ms elapsed: mark batch as ready to send
5. Return a Future<RecordMetadata> to the caller

[Background Sender thread — runs continuously]
6. Drain ready batches from RecordAccumulator
7. Group batches by broker (each broker gets one request with all its partitions' batches)
8. Compress batch (if compression.type != none)
9. Send ProduceRequest to broker
10. Await response based on acks setting
11. On success: complete the Future; invoke callback
12. On failure: retry (if retries > 0 and error is retriable) or fail the Future
```

The decoupling between the application thread (step 1–5) and the Sender thread (step 6–12) is what enables batching — multiple `send()` calls from the application thread accumulate into one batch before the Sender dispatches it.

## Section 2: Batching

**Q3. What is batching in Kafka producers and why does it matter?**
A: Batching is the accumulation of multiple records into a single ProduceRequest sent to a broker. Without batching, every `send()` call would result in a separate network round-trip and disk write on the broker — prohibitively expensive at high throughput.

With batching:
- **Network efficiency** — one TCP segment carries N records instead of N TCP segments, each with its own headers and round-trip. Amortizes the ~1ms network round-trip cost across many records.
- **Compression efficiency** — compression algorithms find more redundancy across a batch of similar records than across a single record. A batch of 1,000 JSON events compresses far better than 1,000 individual JSON events.
- **Broker write efficiency** — Kafka writes to the partition log in sequential append operations. Appending a single batch of 1,000 records is one sequential write; appending 1,000 individual records still involves 1,000 fsync-triggering operations on the broker.
- **Throughput** — at high `send()` rates, batching enables producers to saturate network bandwidth rather than being limited by round-trip latency.

The trade-off: batching introduces latency — a record waits in the accumulator until the batch is full or a timer expires before it is sent.

**Q4. What are `batch.size` and `linger.ms` and how do they interact?**
A:

**`batch.size`** (default: 16,384 bytes = 16KB):
The maximum size of a single batch for a given (topic, partition) pair. When the accumulator for a partition reaches `batch.size` bytes, the batch is marked ready and dispatched immediately by the Sender thread regardless of `linger.ms`. This is a size-based trigger.

**`linger.ms`** (default: 0ms):
The maximum time the producer waits before sending a batch that has not yet reached `batch.size`. At the default of 0ms, the Sender dispatches any available batch immediately (on each I/O loop iteration), effectively disabling time-based batching. Setting `linger.ms=5` means the producer waits up to 5ms after the first record is added to a batch, giving more records time to accumulate before dispatch. This is a time-based trigger.

**Interaction:**
```
linger.ms=5, batch.size=16384

Timeline:
  t=0ms:   Record 1 added to batch (batch size: 200 bytes)
  t=1ms:   Record 2 added (400 bytes)
  t=2ms:   Record 3 added (600 bytes)
  ...
  t=5ms:   linger.ms elapsed → batch dispatched (e.g., 3KB of records)

Alternative (high-throughput scenario):
  t=0ms:   Record 1 added (200 bytes)
  t=0.1ms: Record 2 added (400 bytes)
  ...
  t=0.8ms: Batch reaches 16,384 bytes → dispatched immediately
            (linger.ms not reached; batch.size trigger fires first)
```

**Practical tuning:** for throughput-critical producers, set `linger.ms=5` to `linger.ms=20` alongside a larger `batch.size` (64KB–1MB). For low-latency producers (each record must be sent within milliseconds), keep `linger.ms=0` and accept lower throughput.

**Q5. What is `buffer.memory` and what happens when it is exhausted?**
A: `buffer.memory` (default: 32MB) is the total memory pool the producer allocates for all in-flight and accumulating batches across all partitions. When the application thread calls `send()` faster than the Sender thread can dispatch and drain batches (e.g., the broker is slow or the network is congested), the accumulator fills up.

When `buffer.memory` is exhausted:
- The `send()` call blocks for up to `max.block.ms` (default: 60 seconds) waiting for the Sender to free up buffer space.
- If `max.block.ms` elapses without space becoming available, `send()` throws `TimeoutException`.

This is Kafka's back-pressure mechanism — the producer applies back-pressure to the application by blocking `send()`. If the application doesn't handle this (e.g., it's also handling incoming requests), the back-pressure propagates upstream.

Diagnosis: `buffer.memory` exhaustion is a symptom, not the root cause. Root causes are: broker slowness (check broker I/O and replication lag), network saturation, or genuinely too many producer threads/topics for the configured buffer size. Increasing `buffer.memory` is a short-term fix; the real fix is addressing the bottleneck.

**Q6. What is the `max.in.flight.requests.per.connection` setting and how does it interact with batching?**
A: `max.in.flight.requests.per.connection` (default: 5) controls how many ProduceRequests can be in-flight to a single broker simultaneously — sent but not yet acknowledged. Allowing multiple in-flight requests increases throughput (the producer doesn't wait for one response before sending the next batch), but introduces a risk:

**Ordering risk:** if request N fails and is retried while request N+1 has already been sent and acknowledged, the retry of N may succeed after N+1 — reversing the order of records in the partition. For producers that require strict per-partition ordering (`enable.idempotence=true`), set `max.in.flight.requests.per.connection=1` or use idempotent producers which handle reordering safely up to 5 in-flight requests.

```
max.in.flight.requests.per.connection=5 (default):
  Request 1 [batch A] ─────────────────────────────► broker (succeeds)
  Request 2 [batch B] ─────────────────────────────► broker (fails → retry)
  Request 3 [batch C] ─────────────────────────────► broker (succeeds before retry of B)
  → Order in partition: A, C, B ← reordering!

With enable.idempotence=true:
  Producer assigns sequence numbers to each batch.
  Broker detects out-of-order sequence; holds C until B's retry succeeds.
  → Order preserved: A, B, C ✓
```

## Section 3: Compression

**Q7. How does compression work in the Kafka producer?**
A: Compression is applied by the producer to the entire batch of records before transmission — not to individual records. The compressed batch is written as a single compressed message set in the ProduceRequest. The broker stores the compressed batch as-is on disk (no decompression at write time); consumers decompress when reading. This means compression is applied once (at the producer) and the compressed data flows through the network and storage — benefiting both network and disk I/O.

```
Producer accumulates batch:
  [Record 1: {"userId":42,"event":"click"}]
  [Record 2: {"userId":43,"event":"click"}]
  [Record 3: {"userId":42,"event":"purchase"}]

Compress entire batch with snappy/lz4/gzip:
  → single compressed blob (e.g., 3KB → 800 bytes)

Send compressed ProduceRequest to broker
Broker stores compressed blob on disk
Consumer reads compressed blob, decompresses
```

Configuration: `compression.type` on the producer. Values: `none` (default), `gzip`, `snappy`, `lz4`, `zstd`.

**Q8. Compare gzip, snappy, lz4, and zstd — when do you use each?**
A:

| Codec | Compression ratio | Compress speed | Decompress speed | CPU cost | Best for |
|--- |--- |--- |--- |--- |--- |
| `gzip` | Best (~5:1 on JSON) | Slow | Moderate | High | Archival, batch pipelines where throughput > latency; bandwidth-constrained networks |
| `snappy` | Good (~2.5:1) | Fast | Fast | Low | General-purpose real-time streaming; Google's default choice for Kafka |
| `lz4` | Good (~2.5:1) | Fastest | Fastest | Lowest | Latency-sensitive producers; high-throughput pipelines where CPU is the bottleneck |
| `zstd` | Best-in-class (~4:1) | Moderate | Fast | Moderate | Modern deployments (Kafka 2.1+); best ratio/speed trade-off; preferred new default |

**Practical guidance:**
- **`lz4`** for real-time, latency-sensitive pipelines (payment events, user-facing request logs). Minimal CPU overhead; compression and decompression are near-free.
- **`zstd`** for new deployments where Kafka 2.1+ is available — it achieves gzip-level compression at snappy-level speed. The emerging industry default.
- **`gzip`** for overnight batch pipelines, log archival, or cases where bandwidth cost dominates CPU cost (e.g., cross-region replication over expensive WAN links).
- **`snappy`** when `zstd` is unavailable (older Kafka versions) or when existing infrastructure is already tuned for it.
- **`none`** for already-compressed data (JPEG images, video segments, pre-compressed binary formats). Compressing already-compressed data wastes CPU and often increases size.

**Q9. What is "broker-side compression" and the `compression.type` mismatch problem?**
A: The broker has its own `compression.type` configuration per topic (default: `producer` — honor whatever the producer sends). If the broker's topic compression type differs from the producer's:

**`compression.type=producer` (default):** broker stores batches exactly as the producer sends them — no decompression/recompression. Most efficient; recommended.

**`compression.type=gzip` (or any specific codec) on the broker:** if the producer sends `lz4`-compressed batches, the broker must decompress and re-compress with `gzip` before storing. This adds CPU cost on the broker and defeats the efficiency of producer-side compression.

**`compression.type=uncompressed` on the broker:** broker decompresses all incoming batches and stores uncompressed. Producer compression is stripped — sending compressed data from producers has no disk storage benefit.

**The mismatch problem in practice:** a producer configured with `compression.type=snappy` sends batches to a topic configured with `compression.type=gzip`. The broker decompresses every batch from snappy and recompresses with gzip. This hidden CPU cost on the broker causes latency spikes under load. Diagnosis: watch broker CPU metrics; unexpected CPU elevation on the receive path (not the consumer path) is a symptom.

**Rule:** always configure the producer's `compression.type` to match the topic's `compression.type`, or set the topic to `producer` and let producers decide.

**Q10. How does batch size affect compression ratio?**
A: Compression algorithms find redundancy within a data block — repeated byte sequences, common substrings, repeated field names in JSON. A larger batch contains more records, giving the compressor more redundancy to exploit:

```
10 records of {"userId": X, "event": "click", "timestamp": T}:
  Uncompressed: ~500 bytes
  lz4 compressed (10 records):    ~180 bytes → 2.8:1 ratio
  lz4 compressed (1,000 records): ~4,200 bytes / 50,000 uncompressed → 11.9:1 ratio
```

The field names (`userId`, `event`, `timestamp`) repeat 1,000 times in a batch of 1,000 records — a compressor eliminates almost all of this redundancy. At batch size 1 (no batching), each record compresses in isolation — the ratio is poor. At batch size 1,000, the compressor achieves near-theoretical maximum for the data format.

Implication: **compression and batching are multiplicatively effective**. Increasing `batch.size` and `linger.ms` improves compression ratio as well as network efficiency. For JSON or Avro data, the effective compression ratio at large batch sizes often makes the network and storage cost negligible compared to the uncompressed equivalent.

## Section 4: `acks` Setting

**Q11. What is the `acks` setting and what are its three values?**
A: The `acks` (acknowledgments) setting controls how many broker replicas must confirm receipt of a batch before the producer considers the write successful. It is the primary knob for trading off durability against latency and throughput.

**`acks=0` (fire and forget):**
The producer sends the batch and does not wait for any acknowledgment from the broker. The ProduceRequest is placed on the network; the producer immediately considers it done and moves on. If the batch is lost (broker crash, network drop), the producer has no idea — no retry, no error callback.
- Latency: minimal (no wait for broker response).
- Throughput: maximum.
- Durability: none — data can be lost silently.
- Use cases: metrics, analytics events, high-frequency telemetry where occasional loss is tolerable and throughput is paramount. Not suitable for any business-critical data.

**`acks=1` (leader acknowledgment):**
The partition leader writes the batch to its local log and responds with an acknowledgment before replicating to followers. The producer considers the write successful on receiving the leader's ack.
- Latency: one network round-trip to the leader.
- Throughput: high.
- Durability: moderate — if the leader crashes after acking but before replicating to followers, and a follower that doesn't have the record is elected as the new leader, the record is lost.
- Use cases: logging pipelines, audit trails where some loss is acceptable but acknowledged loss is not (i.e., if acked, it is expected to survive normal leader failures but not simultaneous leader crash + follower election edge case).

**`acks=all` (or `acks=-1`, full ISR acknowledgment):**
The partition leader waits until all in-sync replicas (ISR — the set of replicas caught up to within `replica.lag.time.max.ms` of the leader) have written the batch to their local logs before responding to the producer.
- Latency: one round-trip to the leader + replication lag to the slowest ISR member (typically 5–20ms additional).
- Throughput: slightly lower than `acks=1` due to the replication wait.
- Durability: strong — a batch acknowledged at `acks=all` survives the loss of any single broker (or all but one, depending on ISR size and `min.insync.replicas`).
- Use cases: financial transactions, order events, user data, any record whose loss would have business or compliance impact.

**Q12. What is the ISR (In-Sync Replica set) and why does it matter for `acks=all`?**
A: The ISR is the dynamic set of replicas that are fully caught up with the leader. A replica is in the ISR if it has fetched records from the leader within the last `replica.lag.time.max.ms` milliseconds (default: 30 seconds). Replicas that fall behind (slow I/O, GC pause, network issue) are removed from the ISR.

`acks=all` means all replicas in the **current ISR** must acknowledge — not all replicas that exist for the partition. If the ISR shrinks to 1 (just the leader, because all followers are lagging), then `acks=all` with an ISR of 1 is equivalent to `acks=1` — it provides no additional durability.

This is why `acks=all` must be paired with `min.insync.replicas`:

```
Topic config: replication.factor=3, min.insync.replicas=2

Scenario: two followers fall behind → ISR = {leader only}
  acks=all alone: producer write succeeds (ISR has 1 member; leader acks)
                  → NOT durable; equivalent to acks=1

  acks=all + min.insync.replicas=2:
  Broker checks: ISR size (1) < min.insync.replicas (2)
  → Broker rejects the ProduceRequest with NotEnoughReplicasException
  → Producer receives an error → can alert / retry / stop
  → Data is not silently accepted with fake durability guarantee
```

`min.insync.replicas=2` with `replication.factor=3` means: the cluster can tolerate 1 broker failure (ISR drops to 2, still above the minimum) while maintaining `acks=all` guarantees. If 2 brokers fail simultaneously (ISR=1), writes are rejected rather than silently weakened. This is the correct production configuration for durable topics.

**Q13. What is the latency impact of each `acks` level with concrete numbers?**
A: On a typical Kafka cluster with replicas in the same datacenter:

```
acks=0:
  Producer → network send → done
  Latency: ~0.1ms (network send only; no wait)
  Throughput: limited only by network bandwidth and producer CPU

acks=1:
  Producer → leader write → ACK → done
  Latency: ~1–5ms (network RTT + leader disk write)
  Throughput: ~95% of acks=0 throughput

acks=all (ISR=2, replication.factor=3):
  Producer → leader write → replicate to 1 follower → ACK → done
  Latency: ~5–20ms (RTT + leader disk + replication RTT + follower disk)
  Throughput: ~85–90% of acks=0 throughput
  (Modern SSDs and async replication close the gap significantly)

acks=all across datacenters (geo-replication):
  Latency: 50–200ms (cross-DC RTT dominates)
  → Not appropriate for latency-sensitive producers; use async geo-replication
    (MirrorMaker 2) and accept the weaker cross-DC durability
```

The latency cost of `acks=all` over `acks=1` is often smaller than expected in practice because Kafka uses asynchronous I/O and followers fetch in parallel — the additional wait is typically just the replication lag, not a full additional round-trip.

**Q14. What is `retries` and `delivery.timeout.ms`, and how do they interact with `acks`?**
A: When a ProduceRequest fails with a retriable error (leader not available, request timeout, `NotLeaderOrFollowerException`), the Kafka producer automatically retries up to `retries` times (default: `Integer.MAX_VALUE` in modern clients — effectively unlimited) with `retry.backoff.ms` (default: 100ms) between attempts.

`delivery.timeout.ms` (default: 120,000ms = 2 minutes) is the upper bound on how long the producer will spend attempting to deliver a single batch, including all retries. When `delivery.timeout.ms` elapses, the batch is failed regardless of remaining retry count.

**Interaction with `acks`:**
- `acks=0`: retries are meaningless — the producer doesn't know if the write succeeded, so it can't know when to retry. Setting `retries > 0` with `acks=0` has no effect.
- `acks=1` or `acks=all`: retries make sense because the producer receives an explicit error code from the broker and can retry on retriable errors.

**Ordering risk with retries:**
Retries can cause record reordering if `max.in.flight.requests.per.connection > 1`. Batch N fails and is queued for retry; batch N+1 succeeds in the meantime; retry of batch N then succeeds — N ends up after N+1 in the partition. Mitigation: `enable.idempotence=true` assigns sequence numbers that the broker uses to deduplicate and reorder, ensuring exactly-once delivery per producer session even with retries and multiple in-flight requests.

## Section 5: Idempotent and Transactional Producers

**Q15. What is `enable.idempotence` and what does it guarantee?**
A: `enable.idempotence=true` (default since Kafka 3.0) assigns each producer session a **Producer ID (PID)** and adds a **sequence number** to every batch sent to a partition. The broker tracks `(PID, partition, sequence_number)` and uses it to:

1. **Deduplicate retries**: if the producer retries a batch (e.g., a network timeout where the broker actually wrote it but the ack was lost), the broker recognizes the duplicate sequence number and ignores the re-send. The producer's `Future` completes successfully with the original offset.
2. **Detect and reject gaps**: if batch N+2 arrives before N+1, the broker holds N+2 until N+1 arrives (or rejects it if N+1 never comes). Ordering within a partition is guaranteed.

Idempotent producers provide **exactly-once delivery per producer session, per partition**. They do not provide cross-partition atomicity (writing to two partitions atomically requires transactions).

`enable.idempotence=true` automatically sets:
- `acks=all` (required for idempotency to be meaningful)
- `max.in.flight.requests.per.connection=5` (safe with sequence numbers)
- `retries=Integer.MAX_VALUE`

**Q16. What is the difference between idempotent producers and transactional producers?**
A: Idempotent producers guarantee exactly-once delivery to a single partition. Transactional producers extend this to atomic writes across multiple partitions and topics — all-or-nothing semantics:

```typescript
producer.initTransactions();

try {
  producer.beginTransaction();

  // Write to multiple partitions atomically
  producer.send(new ProducerRecord('orders', orderId, orderData));
  producer.send(new ProducerRecord('inventory', itemId, updatedStock));
  producer.send(new ProducerRecord('notifications', userId, notification));

  // Commit consumer offsets atomically with the produce
  // (enables exactly-once stream processing)
  producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);

  producer.commitTransaction();  // all writes visible atomically
} catch (err) {
  producer.abortTransaction();   // all writes rolled back
}
```

Transactional producers use a **Transaction Coordinator** (a special Kafka broker role) to coordinate the two-phase commit across partition leaders. Consumers must be configured with `isolation.level=read_committed` to only see records from committed transactions.

Use cases: exactly-once stream processing (Kafka Streams uses transactions internally), atomic fanout (write to multiple output topics from a single consumed record without risk of partial writes on failure).

## Section 6: Scenario Questions

**Q17. "Your Kafka producer is achieving only 10MB/s throughput but your network can handle 1GB/s. What's likely wrong and how do you fix it?"**
A: 10MB/s on a 1GB/s network strongly suggests the bottleneck is latency-related, not bandwidth-related — each record is being sent in its own round-trip, and the round-trip time (not bandwidth) limits throughput.

**Root cause diagnosis:**
- `linger.ms=0` (default) means the Sender dispatches a batch as soon as any record is available, before others can accumulate. Each record travels in its own ProduceRequest.
- `batch.size=16384` (16KB default) is quickly filled by large records, but at low record rates, batches are dispatched before they fill.
- `acks=1` or `acks=all` means the producer waits for a broker response before the next send can begin (if `max.in.flight.requests.per.connection=1`).

**Fixes:**
1. **Set `linger.ms=20`** — wait up to 20ms for more records to accumulate. 20ms × 50 records/ms = 1,000 records per batch instead of 1.
2. **Increase `batch.size=524288`** (512KB) — allows larger batches to form before size-based dispatch.
3. **Enable compression** (`compression.type=lz4`) — reduces batch size on the wire, increasing effective throughput.
4. **Increase `max.in.flight.requests.per.connection=5`** — allows 5 requests in flight simultaneously, hiding the round-trip latency behind parallelism.
5. **Increase `buffer.memory`** if the accumulator is filling up — ensure enough buffer for large batches to form.

After tuning: the same record stream may achieve 500MB/s on the same network, because 1,000 records travel in one round-trip instead of 1,000 separate round-trips.

**Q18. "You're building a payment processing pipeline on Kafka. What `acks`, retry, and idempotency settings do you configure and why?"**
A: Payments require the strongest durability guarantees — no silent data loss is acceptable. Configuration:

```properties
# Durability
acks=all
min.insync.replicas=2          # broker/topic config; acks=all is meaningless without this
replication.factor=3           # 3 replicas; survive 1 broker failure

# Idempotency (exactly-once per partition, deduplication of retries)
enable.idempotence=true        # auto-sets acks=all, retries=MAX_VALUE, max.in.flight=5

# Delivery timeout
delivery.timeout.ms=300000     # 5 minutes; allow retries for transient broker issues
retry.backoff.ms=500           # 500ms between retries; avoid overwhelming a recovering broker

# Batching (low latency prioritized over throughput for payments)
linger.ms=0                    # send immediately; don't accumulate (each payment is urgent)
batch.size=16384               # default; fine for low-volume payment events

# Compression (optional for payments; records are small and CPU is cheap)
compression.type=lz4           # minimal CPU overhead; small size reduction

# Transactions (if atomically writing to multiple topics: orders + audit + ledger)
transactional.id=payment-producer-{instanceId}
# Then use producer.beginTransaction() / commitTransaction() per payment
```

**What each setting prevents:**
- `acks=all + min.insync.replicas=2`: prevents silent loss on leader crash before replication.
- `enable.idempotence=true`: prevents double-charging if a network timeout causes a retry that the broker already processed.
- `delivery.timeout.ms=300000`: retries through transient failures (broker restart, leader election) without giving up too quickly.
- `linger.ms=0`: each payment event is sent immediately — a 20ms linger delay on a payment is noticeable and unnecessary.

**Q19. "A consumer is reporting duplicate records even though the producer has `enable.idempotence=true`. What are the possible causes?"**
A: `enable.idempotence=true` deduplicates at the broker level, within the producer's session. Duplicates can still appear to consumers from several causes:

**Producer session restart:** idempotency is scoped to a PID (Producer ID), which is assigned per producer instance initialization. If the producer restarts (process crash, JVM restart), it gets a new PID. Any in-flight batch from the old PID that the broker hadn't yet deduplicated gets retried with the new PID — the broker sees it as a new write from a new producer and stores it, resulting in a duplicate record in the partition.

**Transactional producer not used:** idempotency prevents duplicate writes from retries on the producer side, but if the consumer's offset commit fails after processing a record, the consumer re-reads and re-processes the same record on restart. This is a consumer-side duplicate, not a producer-side one. Fix: use transactions (`sendOffsetsToTransaction`) for exactly-once stream processing end-to-end.

**`isolation.level=read_uncommitted` on the consumer:** if the producer uses transactions and commits them, but the consumer reads with `read_uncommitted`, it may see both the in-flight records and the committed records — effectively doubling them during the transaction window. Fix: set `isolation.level=read_committed` on the consumer.

**Different producer instances without `transactional.id`:** two producer instances both writing to the same topic without coordinated transaction IDs. Each has its own PID; neither deduplicates against the other. Fix: use `transactional.id` (which is globally unique and fenced — a new producer instance with the same `transactional.id` fences out the old one) for scenarios with multiple producer instances on the same logical stream.

**Q20. "You need cross-region Kafka replication. Your producers use `acks=all` in the primary region. Should replication to the secondary region be synchronous or asynchronous?"**
A: Synchronous cross-region replication with `acks=all` across regions is almost never the right answer:

**Synchronous cross-region `acks=all`:**
- Every `producer.send()` waits for replicas in both the primary and secondary region to acknowledge.
- Cross-region RTT (e.g., US-East to EU-West): ~100ms.
- Producer P99 latency becomes ~100ms minimum, regardless of local operations.
- A secondary-region outage or network partition means `acks=all` cannot be satisfied → **all primary-region writes are blocked**. The secondary region's availability directly impacts primary region write availability. Unacceptable for most production systems.

**Asynchronous cross-region replication (standard):**
- Producer uses `acks=all` within the primary region (2 of 3 ISR members in the same datacenter, ~5–20ms).
- MirrorMaker 2 (or Confluent Replicator) asynchronously replicates topics from the primary to the secondary region, typically with 5–60 seconds of lag.
- Secondary region is a hot standby: consumers in the secondary region may lag by seconds, but primary writes are not blocked by secondary health.
- On primary region failure, failover to secondary accepts some data loss (the replication lag — records produced in the last 5–60 seconds that hadn't replicated yet). This RPO (Recovery Point Objective) must be acceptable to the business.

The correct architecture: `acks=all` with `min.insync.replicas=2` within a region for strong local durability; async MirrorMaker 2 for geo-replication with a defined and accepted RPO.

| `buffer.memory` | 33,554,432 bytes (32MB) | Increase if exhausted | Total memory for accumulating batches |
| `compression.type` | `none` | `lz4` (speed) or `zstd` (ratio) | Applied per batch; never compress already-compressed data |
| `acks` | `1` (older) / `all` (Kafka 3+) | `all` for durability | Replicas that must ack before write is confirmed |
| `min.insync.replicas` | 1 | Set to 2 (with RF=3) | `acks=all` is toothless without this |
| `retries` | `MAX_VALUE` | Leave default | Unlimited retries bounded by `delivery.timeout.ms` |
| `delivery.timeout.ms` | 120,000ms | Increase for transient failures | Total time budget for a batch including all retries |
| `enable.idempotence` | `true` (Kafka 3+) | Always enable for production | Exactly-once per partition; auto-sets `acks=all` |
| `max.in.flight.requests` | 5 | Leave at 5 with idempotence | Safe ordering with sequence numbers |
| `transactional.id` | unset | Set for atomic multi-partition writes | Enables cross-partition atomicity; fences zombie producers |

---

**Tip for the interview:** Kafka producer questions almost always spiral into one of three directions: throughput tuning (batching + compression interplay), durability guarantees (`acks` + `min.insync.replicas` pairing — the single most common interview gotcha), or ordering/deduplication (`enable.idempotence` + `max.in.flight`). The pairing that trips most candidates: `acks=all` without `min.insync.replicas=2` silently degrades to `acks=1` durability when the ISR shrinks. If you say `acks=all` in an interview, immediately follow it with `min.insync.replicas=2` — interviewers at 5 YOE level specifically probe for this. On compression: lead with the batch-size interaction (compression ratio improves multiplicatively with batch size) and the codec trade-off table (lz4 for latency, zstd for ratio, never compress already-compressed data). On throughput tuning: `linger.ms` and `batch.size` are the primary levers; `compression.type` is multiplicatively effective on top of both.
