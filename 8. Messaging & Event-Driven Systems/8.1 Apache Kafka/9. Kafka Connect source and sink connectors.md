# Kafka Connect: Source and Sink Connectors — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Kafka Connect and what problem does it solve?**
A: Kafka Connect is a framework built into Kafka for scalably and reliably streaming data between Kafka and external systems — databases, file systems, search indexes, object storage, message queues, and SaaS APIs. It solves the integration problem: without Connect, every team that wants to move data between Kafka and an external system writes bespoke producer/consumer code. This code repeatedly solves the same problems — offset tracking, exactly-once delivery, schema evolution, error handling, parallelism, restarts — in slightly different ways, with varying correctness. Kafka Connect provides a standardized, operationally mature framework that handles these concerns once, leaving teams to configure rather than code integrations.

Connect runs as a cluster of worker processes. Connectors (plugins) define how to read from or write to a specific system. Tasks (the unit of parallelism within a connector) do the actual work. The framework manages task lifecycle, offset tracking, rebalancing when workers join or leave, and REST API for management.

**Q2. What is the difference between a source connector and a sink connector?**
A:

**Source connector** — reads data from an external system and writes it into Kafka topics. The external system is the source of truth; Kafka is the destination.

```
External System                 Kafka Connect                 Kafka
(Postgres, MySQL,  ──────────►  Source Connector  ──────────►  Topic
 S3, REST API)                  (polls / CDC)
```

Examples: Debezium PostgreSQL source (captures row-level changes via WAL), JDBC source connector (polls a table for new/updated rows), S3 source connector (reads files from an S3 bucket and produces records), HTTP source connector (polls a REST API).

**Sink connector** — reads data from Kafka topics and writes it into an external system. Kafka is the source of truth; the external system is the destination.

```
Kafka                           Kafka Connect                 External System
Topic  ──────────►  Sink Connector  ──────────►  (Elasticsearch,
                    (consumes,                    S3, JDBC DB,
                     transforms,                  BigQuery,
                     writes)                      Snowflake)
```

Examples: Elasticsearch sink (indexes records from a Kafka topic into ES), S3 sink (writes records to S3 as Parquet/JSON/Avro files), JDBC sink (upserts records into a relational database table), BigQuery sink (streams records into a BigQuery table).

**Q3. What are workers, connectors, and tasks — and how do they relate?**
A: Three distinct concepts that are often conflated:

**Worker** — a JVM process running Kafka Connect. Workers form a cluster; they share configuration storage (a Kafka topic) and distribute work among themselves. Workers handle the operational concerns: REST API, connector lifecycle management, offset storage, rebalancing.

**Connector** — a logical configuration unit that defines a specific integration: which external system, which topics, authentication, transformation rules. A connector does not do I/O directly — it is a factory for tasks and a manager of their lifecycle. One connector instance = one logical data pipeline.

**Task** — the actual unit of work. A connector spawns one or more tasks; each task runs in a worker thread and does the I/O: polling the source system or writing to the sink system. Tasks are the parallelism unit: a JDBC source connector with `tasks.max=4` spawns 4 tasks, each responsible for a subset of the tables being ingested. Tasks are stateless — all state (offsets, connector config) is stored externally in Kafka topics.

```
Connect Cluster (3 workers)
├── Worker 1
│   ├── postgres-source task 1  (tables: orders, payments)
│   └── elasticsearch-sink task 1  (topic: events partition 0-2)
├── Worker 2
│   ├── postgres-source task 2  (tables: users, products)
│   └── elasticsearch-sink task 2  (topic: events partition 3-5)
└── Worker 3
    └── elasticsearch-sink task 3  (topic: events partition 6-8)
```

## Section 2: Source Connectors

**Q4. How does a source connector track its position in the source system?**
A: Source connectors use **source offsets** — a map of key-value pairs that represents the connector's current position in the source system. The framework persists these offsets to a Kafka topic (`connect-offsets` by default) after each batch of records is produced. On restart or rebalance, the connector reads its last committed offset and resumes from there.

The offset format is connector-specific — it represents whatever the source system uses for position:

```json
// JDBC source connector offset (poll-based, by timestamp or incrementing ID)
{
  "table": "orders",
  "incrementing_field": 98432
}
// Meaning: last processed row had id=98432; next poll fetches id > 98432

// Debezium PostgreSQL source offset (WAL-based CDC)
{
  "lsn": 12345678,
  "txId": 5001,
  "ts_usec": 1721740980000000
}
// Meaning: last processed WAL position; resume from LSN 12345678

// S3 source connector offset
{
  "bucket": "my-bucket",
  "prefix": "data/2024/07/",
  "lastFile": "data/2024/07/23/events-00042.json"
}
// Meaning: last processed file; next poll processes files after this one
```

Offsets are written to Kafka atomically with the records they represent — the framework guarantees that if a batch of records is committed to a Kafka topic, the corresponding offset update is also committed. This gives **at-least-once delivery**: on restart, the connector may re-read and re-produce records from around the last committed offset (if the process crashed after records were produced but before the offset was committed). Downstream consumers must be idempotent to handle this.

**Q5. What is the difference between poll-based and CDC-based source connectors?**
A: The two fundamental approaches to extracting data from a database:

**Poll-based (JDBC source connector):**
The connector periodically queries the source table for new or updated rows, using a watermark column — typically a timestamp (`updated_at`) or an auto-incrementing ID (`id`):

```sql
-- Incrementing mode: fetch rows with id > last_seen_id
SELECT * FROM orders WHERE id > 98432 ORDER BY id LIMIT 1000;

-- Timestamp mode: fetch rows updated since last poll
SELECT * FROM orders WHERE updated_at > '2024-07-23 14:03:00' ORDER BY updated_at;

-- Timestamp + incrementing combined (handles rows with same timestamp)
SELECT * FROM orders
WHERE updated_at > '2024-07-23 14:03:00'
   OR (updated_at = '2024-07-23 14:03:00' AND id > 98432)
ORDER BY updated_at, id;
```

Limitations: cannot detect DELETE operations (a deleted row disappears; the poll never sees it). Requires a reliable watermark column — tables without an `updated_at` or auto-increment ID cannot be polled incrementally. Introduces polling latency (data freshness is bounded by the poll interval, typically 1–60 seconds).

**CDC-based (Debezium):**
Change Data Capture reads the database's replication log (PostgreSQL WAL, MySQL binlog, MongoDB oplog) at the storage level. Every INSERT, UPDATE, and DELETE appears as an event in the log, in the order they occurred:

```json
// Debezium change event for a DELETE
{
  "op": "d",
  "before": {"id": 42, "status": "active", "amount": 100.00},
  "after": null,
  "source": {"lsn": 12345678, "ts_ms": 1721740980000}
}
```

CDC captures every change including DELETEs, preserves operation type and before/after state, captures changes in commit order (not poll-order), and introduces sub-second latency. The trade-off: requires database-level permissions (replication slot for PostgreSQL, binlog access for MySQL), and replication slots hold WAL segments — a stuck connector causes WAL accumulation and potential disk exhaustion on the source database.

**Q6. How does Debezium's PostgreSQL source connector work internally?**
A: Debezium uses PostgreSQL's logical replication protocol:

```
PostgreSQL                          Debezium Connector
    │                                       │
    │  1. Connector creates replication slot:│
    │     pg_create_logical_replication_slot │
    │     ('debezium_slot', 'pgoutput')      │
    │◄───────────────────────────────────────│
    │                                       │
    │  2. WAL decoder (pgoutput plugin)     │
    │     converts WAL entries to           │
    │     logical change events             │
    │                                       │
    │  3. Connector streams changes:        │
    │     START_REPLICATION SLOT debezium_slot
    │─────────────────────────────────────►│
    │  [change events stream continuously] │
    │─────────────────────────────────────►│
    │                                       │
    │  4. Connector produces to Kafka:      │
    │     topic: {server}.{schema}.{table} │
    │     e.g.: mydb.public.orders         │
    │                                       │
    │  5. Connector sends LSN acknowledgment│
    │     (advance replication slot)        │
    │◄───────────────────────────────────────│
    │     WAL segments before acked LSN     │
    │     can now be recycled               │
```

Critical operational concern: the replication slot holds WAL segments from its confirmed LSN forward. If the Debezium connector stops consuming (connector down, Kafka unavailable), the replication slot accumulates WAL without bound. PostgreSQL disk can fill and the database can crash. Mitigation: monitor replication slot lag (`pg_replication_slots`); set `max_slot_wal_keep_size` (PostgreSQL 13+) to limit WAL retention per slot; have an alerting threshold on slot lag.

**Q7. How does a source connector handle schema changes in the source system?**
A: Schema changes (adding a column, renaming a column, changing a type) are one of the hardest operational problems in data integration. Connect addresses this through the Schema Registry and schema evolution rules:

**With Schema Registry (Avro / Protobuf / JSON Schema):**
Each record carries a schema ID (not the full schema — a reference to a schema version in the registry). When the source table gains a new column, the connector detects the schema change, registers a new schema version in the registry, and starts producing records with the new schema ID. Consumers with the compatible schema evolve transparently.

Compatibility modes enforced by the registry:
- **BACKWARD**: new schema can read data written with the old schema (new optional fields with defaults). Consumers upgrade first; producers upgrade after.
- **FORWARD**: old schema can read data written with the new schema (old fields still present). Producers upgrade first; consumers upgrade after.
- **FULL**: both backward and forward compatible. Safest; most restrictive.

**Debezium's schema change topic:**
Debezium emits DDL changes (`ALTER TABLE`, `CREATE TABLE`) to a dedicated schema change topic (`{server}.schema-changes`). Downstream consumers can subscribe to this topic to learn about structural changes before they appear in the data topics.

**Breaking changes** (removing a required field, changing a type incompatibly) require manual intervention — pausing the connector, coordinating consumer upgrades, and potentially replaying history. No framework handles breaking schema changes automatically.

## Section 3: Sink Connectors

**Q8. How does a sink connector ensure data is written to the destination exactly once?**
A: Exactly-once delivery to a sink is harder than exactly-once on the Kafka side because the sink (Elasticsearch, a database, S3) is an external system outside Kafka's transaction boundary. Three approaches in increasing strength:

**At-least-once (default):** the sink connector commits its Kafka consumer offsets only after successfully writing to the external system. On failure and restart, it re-reads records from the last committed offset and re-writes them. The external system receives duplicates; must be idempotent to handle them.

**Idempotent writes:** structure writes so that re-delivering the same record has no additional effect. For a JDBC sink, use `UPSERT` (INSERT ... ON CONFLICT DO UPDATE) with the record's Kafka offset or a natural primary key — re-inserting the same row is a no-op. For Elasticsearch, use the record's key as the document ID — re-indexing the same document overwrites itself with identical content.

**Kafka transactions (for Kafka-to-Kafka sinks):** if the sink is another Kafka topic, the sink connector can use Kafka's transactional API to atomically commit the consumer offset and the produced record in a single transaction. This is how Kafka Streams achieves exactly-once stream processing. For non-Kafka sinks, this option is unavailable.

**Two-phase commit (rare):** coordinate a distributed transaction between Kafka offset commit and the external system's commit using a distributed transaction protocol. Complex and rarely implemented; most systems accept at-least-once and implement idempotency.

**Q9. How does a sink connector handle failures writing to the destination?**
A: The sink connector's error handling determines whether a write failure causes the entire connector to stop or just affects the failed record:

**Default behavior (stop on error):** any exception thrown by the sink's `put()` method causes the task to fail and stop. The task is restarted by the framework after a backoff period; it re-reads and re-attempts the same records from the last committed offset. This is safe but can cause indefinite stalling if the error is permanent (a malformed record that the sink always rejects).

**Dead letter queue (DLQ) — production standard:**
```properties
errors.tolerance=all
errors.deadletterqueue.topic.name=my-sink-dlq
errors.deadletterqueue.context.headers.enable=true
errors.log.enable=true
errors.log.include.messages=true
```

With DLQ configured, records that fail to be written to the sink after retries are routed to the DLQ topic instead of stopping the connector. The DLQ record carries error metadata in headers (exception class, message, stack trace, source topic/partition/offset). The connector continues processing subsequent records. A separate process monitors the DLQ and handles failed records (alerts, manual replay, discard).

`errors.tolerance=all` means all errors are tolerated (connector never stops for write errors). `errors.tolerance=none` (default) stops the connector on the first error.

**Retry configuration:**
```properties
errors.retry.delay.max.ms=60000   # max 60s between retries
errors.retry.timeout=300000       # retry for up to 5 minutes before DLQ
```

**Q10. How does the S3 sink connector write data, and what are the flush triggers?**
A: The S3 sink connector accumulates records from Kafka in memory, then writes them to S3 as files when a flush condition is met. Writing to S3 object-by-object per record would be prohibitively expensive (S3 has per-request cost and latency); batching into larger files amortizes this.

Flush triggers (first condition met causes a flush):
- **`flush.size`** (default: 1000) — flush when N records have accumulated per partition.
- **`rotate.interval.ms`** — flush after N milliseconds regardless of record count.
- **`rotate.schedule.interval.ms`** — flush on a wall-clock schedule (e.g., every hour) — useful for ensuring files appear in S3 at predictable intervals even during low-traffic periods.

File format and partitioning:
```properties
format.class=io.confluent.connect.s3.format.parquet.ParquetFormat
storage.class=io.confluent.connect.s3.storage.S3Storage
s3.bucket.name=my-data-lake
s3.part.size=67108864           # 64MB multipart upload threshold
topics.dir=topics
locale=en_US
timezone=UTC

# Output path: s3://my-data-lake/topics/{topic}/{partition}/{topic}+{partition}+{offset}.parquet
# With time-based partitioning:
path.format='year'=YYYY/'month'=MM/'day'=dd/'hour'=HH
partitioner.class=io.confluent.connect.storage.partitioner.TimeBasedPartitioner
```

Each Kafka partition's records are written to a separate S3 file (or set of files). Files are named with the starting Kafka offset, enabling deterministic naming — if a task restarts and re-writes the same records, the same file is overwritten (idempotent by object key).

## Section 4: Distributed Mode and Worker Management

**Q11. How does Kafka Connect distributed mode work?**
A: Distributed mode runs Connect as a cluster of worker processes, enabling fault tolerance and horizontal scalability. All configuration, offset, and status information is stored in Kafka topics (not on local disk), making workers stateless and interchangeable.

Three internal Kafka topics (created automatically on first start):
```properties
config.storage.topic=connect-configs      # connector and task configurations
offset.storage.topic=connect-offsets      # source offsets (position in source system)
status.storage.topic=connect-status       # connector/task lifecycle events
```

Worker coordination uses Kafka's consumer group protocol — workers form a consumer group; when a worker joins or leaves, a rebalance redistributes tasks across surviving workers. A worker that crashes has its tasks reassigned to other workers within seconds (the consumer group heartbeat timeout).

```
3-worker cluster, 2 connectors:
  connector-A: tasks.max=4 → 4 tasks
  connector-B: tasks.max=2 → 2 tasks
  Total: 6 tasks distributed across 3 workers → 2 tasks/worker

Worker 2 crashes:
  Rebalance triggered (group coordinator detects missed heartbeat)
  Worker 2's 2 tasks redistributed to Workers 1 and 3
  Workers 1 and 3 each now have 3 tasks
  Tasks resume from last committed offset → at-most-once or at-least-once
    depending on how far the crash occurred in the task lifecycle
```

**Q12. How do you scale a Kafka Connect connector?**
A: Scaling is controlled by `tasks.max` — the maximum number of tasks the connector framework will create for a connector instance. The actual number created depends on the connector's implementation of `taskConfigs()` — it determines the natural parallelism of the source or sink and returns at most `tasks.max` task configurations.

**Source connector parallelism:**
- JDBC source: one task per table being ingested (up to `tasks.max`). Adding tables beyond `tasks.max` means multiple tables per task (sequential, not parallel).
- Debezium: typically `tasks.max=1` because WAL streaming is inherently sequential per database. Parallelism comes from running multiple connector instances (one per database or schema).
- S3 source: one task per S3 prefix or partition of source files.

**Sink connector parallelism:**
- Tasks are assigned a subset of the source topic's partitions (like a consumer group member). `tasks.max=4` on a topic with 12 partitions → each task handles 3 partitions.
- Adding more tasks (up to the partition count) linearly increases throughput, assuming the sink can handle the parallel write rate.
- Cannot have more tasks than partitions — extra tasks sit idle.

**Scaling the worker cluster** (for more memory/CPU rather than more task parallelism): add worker nodes; existing tasks rebalance across more workers. Each worker can run more tasks, or tasks get more CPU/memory headroom.

**Q13. What is the REST API for Kafka Connect and what operations does it support?**
A: Kafka Connect exposes an HTTP REST API on each worker (default port 8083) for managing connectors without restarting the cluster:

```bash
# List all connectors
GET /connectors

# Create a connector
POST /connectors
{
  "name": "postgres-source",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "db.internal",
    "database.port": "5432",
    "database.dbname": "production",
    "database.user": "debezium",
    "database.password": "secret",
    "database.server.name": "mydb",
    "plugin.name": "pgoutput",
    "table.include.list": "public.orders,public.payments",
    "tasks.max": "1"
  }
}

# Get connector status (RUNNING / PAUSED / FAILED)
GET /connectors/postgres-source/status

# Pause a connector (stops task execution; retains config and offsets)
PUT /connectors/postgres-source/pause

# Resume a paused connector
PUT /connectors/postgres-source/resume

# Restart a failed task
POST /connectors/postgres-source/tasks/0/restart

# Update connector configuration (restarts tasks with new config)
PUT /connectors/postgres-source/config

# Delete a connector (stops tasks; removes config; does NOT delete offsets or topics)
DELETE /connectors/postgres-source
```

The REST API is the primary operational interface — used by CI/CD pipelines to deploy connector configurations, by monitoring systems to check connector health, and by on-call engineers to restart failed tasks.

## Section 5: Transforms and Schema Management

**Q14. What are Single Message Transforms (SMTs) and when do you use them?**
A: Single Message Transforms (SMTs) are lightweight, stateless transformations applied to each record as it passes through the connector — after the source reads it but before it reaches Kafka (source SMTs), or after Kafka but before the sink writes it (sink SMTs). They are configured in the connector's config, not in application code.

Common built-in SMTs:

```properties
# 1. Add a field with the current timestamp
transforms=addTimestamp
transforms.addTimestamp.type=org.apache.kafka.connect.transforms.InsertField$Value
transforms.addTimestamp.timestamp.field=ingested_at

# 2. Rename a field
transforms=renameField
transforms.renameField.type=org.apache.kafka.connect.transforms.ReplaceField$Value
transforms.renameField.renames=user_id:userId,created_at:createdAt

# 3. Route records to different topics based on a field value
transforms=topicRouter
transforms.topicRouter.type=org.apache.kafka.connect.transforms.ValueToKey
# More commonly: ExtractField to use a record field as the topic name

# 4. Filter records (drop records matching a condition)
transforms=filterDeletes
transforms.filterDeletes.type=org.apache.kafka.connect.transforms.Filter
transforms.filterDeletes.condition=\${header:__op} != 'd'

# 5. Mask sensitive fields (replace with null or placeholder)
transforms=maskPII
transforms.maskPII.type=org.apache.kafka.connect.transforms.MaskField$Value
transforms.maskPII.fields=email,credit_card_number
transforms.maskPII.replacement=REDACTED

# 6. Flatten a nested struct into a flat key-value map
transforms=flatten
transforms.flatten.type=org.apache.kafka.connect.transforms.Flatten$Value
transforms.flatten.delimiter=_
```

SMTs are composable — chain multiple transforms by listing them in order. They are **not** a replacement for stream processing: they cannot join records, aggregate, or maintain state across records. For complex transformations, use Kafka Streams or Flink after the source connector produces to Kafka.

**Q15. What is the Schema Registry's role in Kafka Connect pipelines?**
A: The Schema Registry stores and versions the Avro, Protobuf, or JSON Schema schemas for records flowing through Connect. Its role in Connect pipelines:

**Source connectors with Schema Registry:**
- The JDBC source connector infers a schema from the database table's column definitions and registers it with the Schema Registry on first run.
- Subsequent runs check whether the table schema has changed; if so, a new schema version is registered (if compatible) or the connector fails (if incompatible with the configured compatibility mode).
- Records are serialized as Avro (or Protobuf) with a 5-byte prefix containing the schema ID — consumers decode records using the schema ID to fetch the correct schema from the registry.

**Sink connectors with Schema Registry:**
- The Elasticsearch sink reads the Avro schema from each record to determine field names and types for the ES document structure.
- The JDBC sink uses the schema to construct the correct INSERT/UPSERT SQL — column names and types come from the schema, not hardcoded in the connector config.
- Schema evolution (adding optional fields) is transparent: the sink connector reads the new schema version and adapts its writes accordingly.

**Without Schema Registry (JSON mode):**
- Records are serialized as plain JSON strings. No schema enforcement; any valid JSON is accepted.
- Downstream consumers must infer or hardcode the schema.
- Schema changes are not tracked — a field rename causes silent data issues downstream.

For production pipelines where schema correctness matters, always use Schema Registry with Avro or Protobuf.

## Section 6: Scenario Questions

**Q16. "You need to replicate a PostgreSQL `orders` table to Elasticsearch in real time. Walk through the complete design."**
A: End-to-end design using Debezium source + Elasticsearch sink:

**Source connector (Debezium PostgreSQL):**
```json
{
  "name": "orders-postgres-source",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres.internal",
    "database.port": "5432",
    "database.dbname": "ecommerce",
    "database.user": "debezium_user",
    "database.password": "${file:/opt/kafka/secrets:db.password}",
    "database.server.name": "ecommerce",
    "plugin.name": "pgoutput",
    "publication.name": "debezium_pub",
    "slot.name": "debezium_orders_slot",
    "table.include.list": "public.orders",
    "transforms": "unwrap,addEventTime",
    "transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
    "transforms.unwrap.drop.tombstones": "false",
    "transforms.unwrap.delete.handling.mode": "rewrite",
    "transforms.addEventTime.type": "org.apache.kafka.connect.transforms.InsertField$Value",
    "transforms.addEventTime.timestamp.field": "kafka_ingested_at",
    "key.converter": "io.confluent.connect.avro.AvroConverter",
    "key.converter.schema.registry.url": "http://schema-registry:8081",
    "value.converter": "io.confluent.connect.avro.AvroConverter",
    "value.converter.schema.registry.url": "http://schema-registry:8081",
    "tasks.max": "1"
  }
}
```

`ExtractNewRecordState` SMT unwraps Debezium's envelope (which contains `before`, `after`, `op`, `source`) to extract just the `after` state — making the record structure match the table row. DELETE events are rewritten as tombstone records (null value) with the deleted row's key, which the Elasticsearch sink uses to delete the document.

**Sink connector (Elasticsearch):**
```json
{
  "name": "orders-elasticsearch-sink",
  "config": {
    "connector.class": "io.confluent.connect.elasticsearch.ElasticsearchSinkConnector",
    "connection.url": "http://elasticsearch:9200",
    "topics": "ecommerce.public.orders",
    "key.ignore": "false",
    "schema.ignore": "false",
    "behavior.on.null.values": "DELETE",
    "transforms": "extractKey",
    "transforms.extractKey.type": "org.apache.kafka.connect.transforms.ExtractField$Key",
    "transforms.extractKey.field": "id",
    "key.converter": "io.confluent.connect.avro.AvroConverter",
    "key.converter.schema.registry.url": "http://schema-registry:8081",
    "value.converter": "io.confluent.connect.avro.AvroConverter",
    "value.converter.schema.registry.url": "http://schema-registry:8081",
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "orders-es-sink-dlq",
    "errors.deadletterqueue.context.headers.enable": "true",
    "tasks.max": "3"
  }
}
```

`behavior.on.null.values=DELETE` causes the sink to delete the Elasticsearch document when it receives a tombstone record — handling the DELETE propagation from Debezium. `key.ignore=false` uses the record key (order ID) as the ES document ID, making writes idempotent.

**Q17. "A Debezium connector has been stopped for 48 hours. What happens when it restarts, and what risks exist?"**
A: The Debezium connector uses a PostgreSQL replication slot to track its position in the WAL. While the connector was stopped, PostgreSQL retained all WAL segments from the slot's confirmed LSN forward — 48 hours of WAL for a busy database can be tens or hundreds of gigabytes.

**On restart:**
1. The connector reads its last committed LSN from the `connect-offsets` Kafka topic.
2. It reconnects to the replication slot and begins streaming from that LSN.
3. 48 hours of changes stream as a backlog — the connector will work through the accumulated WAL at maximum throughput until it catches up to the current WAL position.
4. During catch-up, the Kafka topic receives a burst of historical change events. Downstream consumers may see a spike in lag.

**Risks:**

*PostgreSQL disk exhaustion* — the most serious risk. If the Postgres disk filled during the 48 hours (because WAL segments couldn't be recycled with the slot blocking them), the database may have already crashed or gone read-only. Check `pg_replication_slots` for `wal_status = 'lost'` — if the slot's WAL was recycled (because the database ran out of disk and force-dropped old WAL), the slot is invalid. The connector will fail on reconnect with a slot-not-found or LSN-not-available error. Resolution: drop the invalid slot, perform an initial snapshot of the source tables, and restart the connector fresh — accepting a full re-sync.

*`max_slot_wal_keep_size` eviction* — PostgreSQL 13+ allows setting a per-slot WAL retention limit. If this is set and 48 hours of WAL exceeded it, the slot was automatically invalidated to protect disk space. Same resolution as above.

*Downstream consumer lag* — the burst of catch-up events may overwhelm downstream sinks (Elasticsearch indexing rate, database write throughput). Monitor and potentially throttle the connector's `max.batch.size` and `poll.interval.ms` during catch-up.

**Prevention:** monitor `pg_replication_slots.confirmed_flush_lsn` lag in bytes; alert when lag exceeds a safe threshold (e.g., 10GB). Set `max_slot_wal_keep_size` as a safety valve. Consider pausing the source database or using Debezium's incremental snapshot feature for planned extended outages.

**Q18. "The Elasticsearch sink connector is falling behind — Kafka consumer lag is growing. How do you diagnose and fix it?"**
A: Growing consumer lag on a sink connector means the connector is consuming records from Kafka slower than they are being produced. Systematic diagnosis:

**Step 1 — locate the bottleneck:**
- Check connector task count vs topic partition count: if `tasks.max=1` but the topic has 12 partitions, only one task is consuming all 12 partitions sequentially. Increase `tasks.max` to match partition count.
- Check Elasticsearch indexing rate vs Kafka produce rate: use Elasticsearch's `_cat/indices?v` to see the current indexing rate. If ES is at its indexing throughput limit, adding tasks won't help.
- Check the sink connector's `batch.size` (default: 2000 records per ES bulk request) and `linger.ms` — small batches mean more ES bulk API round-trips.

**Step 2 — fix connector-side throughput:**
```properties
# Increase parallelism (must not exceed topic partition count)
tasks.max=12

# Increase ES bulk batch size
batch.size=5000

# Increase flush interval (allow larger batches to form)
linger.ms=100

# Increase connection pool to ES
max.in.flight.requests=10
```

**Step 3 — fix Elasticsearch-side throughput:**
- Scale ES indexing: increase the number of primary shards for the target index (must be done before index creation; requires reindex for existing data).
- Tune ES for write throughput: `refresh_interval=30s` (reduce how often ES makes new data searchable — the main write throughput limiter); `number_of_replicas=0` during initial catch-up (re-enable after).
- Check ES JVM heap and GC: high GC pauses cause ES write latency spikes, which back-pressures the connector.

**Step 4 — if lag is permanent (produce rate > max sink rate):**
- The fundamental throughput of the sink system must increase (add ES nodes, increase shard count).
- Or reduce the produce rate upstream — which is rarely acceptable.
- Or shard the sink connector across multiple ES clusters with topic-based routing.

**Q19. "How would you implement exactly-once delivery from a Kafka topic to a PostgreSQL table using a JDBC sink connector?"**
A: True exactly-once to PostgreSQL requires the sink write and the Kafka offset commit to be atomic — either both happen or neither does. The JDBC sink connector does not natively support distributed transactions between Kafka and PostgreSQL. The practical approach is idempotent at-least-once:

**Upsert mode (production standard):**
Configure the JDBC sink in upsert mode with the record's key as the primary key:
```properties
insert.mode=upsert
pk.mode=record_key
pk.fields=order_id
auto.create=false           # table must exist; don't auto-create in production
auto.evolve=false           # don't auto-alter schema; require explicit migrations
```

The generated SQL:
```sql
INSERT INTO orders (order_id, amount, status, updated_at)
VALUES (?, ?, ?, ?)
ON CONFLICT (order_id)
DO UPDATE SET amount=EXCLUDED.amount,
              status=EXCLUDED.status,
              updated_at=EXCLUDED.updated_at;
```

Re-delivering the same record (due to connector restart after crash) produces the same `ON CONFLICT DO UPDATE` — idempotent. The final state in PostgreSQL matches the Kafka record regardless of how many times it was delivered.

**Limitation:** upsert mode collapses multiple updates to the same key into the latest value. If the PostgreSQL table must record every intermediate state (an audit log), upsert is wrong — use append mode (`insert.mode=insert`) with a composite primary key that includes the Kafka offset, making each delivery unique:
```sql
INSERT INTO orders_audit (order_id, kafka_offset, amount, status, event_time)
VALUES (?, ?, ?, ?, ?)
ON CONFLICT (order_id, kafka_offset) DO NOTHING;
```

`ON CONFLICT DO NOTHING` with `(order_id, kafka_offset)` as the unique key means a re-delivered record (same offset) is silently ignored — exactly-once semantics for append-only tables.

## Quick Reference

| Concept | Definition | Key detail |
|--- |--- |--- |
| Source connector | Reads from external system → writes to Kafka | Tracks position via source offsets in `connect-offsets` topic |
| Sink connector | Reads from Kafka → writes to external system | Uses consumer group offsets; DLQ for failed records |
| Task | Unit of work within a connector | Stateless; scaled via `tasks.max`; reassigned on worker failure |
| Distributed mode | Cluster of workers; config/offsets in Kafka topics | Worker failure triggers rebalance; tasks resume from last offset |
| Poll-based source | Queries DB on interval with watermark column | Cannot capture DELETEs; requires `updated_at` or auto-increment |
| CDC source (Debezium) | Reads WAL / binlog / oplog | Captures INSERTs, UPDATEs, DELETEs; replication slot holds WAL |
| Replication slot risk | Slot blocks WAL recycling while connector is stopped | Monitor lag; set `max_slot_wal_keep_size`; alert on slot lag |
| DLQ | Dead letter queue for failed sink writes | `errors.tolerance=all`; error context in record headers |
| SMT | Stateless per-record transformation in connector config | Not for joins/aggregations; use Kafka Streams for stateful logic |
| Schema Registry | Stores and versions Avro/Protobuf/JSON schemas | Enforces compatibility; enables schema evolution without code |
| Upsert mode (JDBC sink) | `ON CONFLICT DO UPDATE` for idempotent writes | Collapses multiple updates to same key; audit log needs append mode |
| S3 sink flush | `flush.size` records or `rotate.interval.ms` elapsed | Files named by starting Kafka offset; idempotent on restart |

**Tip for the interview:** Kafka Connect questions at 5 YOE level usually probe two angles: operational correctness (exactly-once semantics, what happens on restart, DLQ configuration) and the CDC vs poll-based trade-off. Lead the CDC discussion with the replication slot WAL retention risk — it's the production gotcha that separates people who've run Debezium in production from those who've only read about it. For the exactly-once question, be precise: Connect itself provides at-least-once; exactly-once to a non-Kafka sink requires idempotent writes at the destination (`ON CONFLICT DO NOTHING` for audit tables, `ON CONFLICT DO UPDATE` for current-state tables). The SMT question is a common follow-up — know what they can do (stateless field-level transforms, routing, masking) and explicitly what they cannot do (joins, aggregations, stateful enrichment — those need Kafka Streams or Flink downstream). If the interviewer asks about schema evolution, the answer always involves Schema Registry compatibility modes and the difference between additive changes (backward compatible, handled automatically) and breaking changes (require coordination and manual intervention).
