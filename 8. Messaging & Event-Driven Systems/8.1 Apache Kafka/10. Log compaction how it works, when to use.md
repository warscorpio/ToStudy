# Log Compaction: How It Works, When to Use — Interview Q&A (5 YOE Level)

---

## Section 1: Foundations — The Two Retention Models

**Q1. What are the two fundamentally different retention models in Kafka, and what is each for?**
A: Kafka topics can be configured with one of two retention policies — or a combination of both — that govern how long data is kept and what gets deleted:

**Time/size-based retention (`cleanup.policy=delete`):**
The default. Kafka retains messages for a configured time window (`retention.ms`, default 7 days) or until the partition reaches a size limit (`retention.bytes`). Once a message ages past the retention window or the partition exceeds the size limit, Kafka deletes the oldest log segments wholesale — entire files are dropped, not individual messages. The consumer's guarantee: messages are available for at least the retention window. After that, they may be gone. This models a **stream** — a flowing sequence of events where the historical record eventually fades.

**Log compaction (`cleanup.policy=compact`):**
Kafka retains the *most recent value for each key* indefinitely, regardless of age or size. Older messages with the same key are cleaned up by a background compaction process, but the latest value for every key is always preserved. The consumer's guarantee: for any key that has ever been written to the topic, the latest value is always readable. This models a **table** — a stateful snapshot where the current value of every key is always accessible.

The conceptual difference is fundamental: delete-based retention answers "what happened recently?" and compact-based retention answers "what is the current state of every key?" Choosing between them is a question of what consumers need — a history of events or a current snapshot of state.

**Q2. What is the core problem log compaction solves that time-based retention cannot?**
A: Time-based retention solves the storage problem (logs don't grow forever) but creates a state reconstruction problem: if a consumer goes offline for longer than the retention window, it can no longer rebuild the full current state of a system by replaying the topic — some of the history it needs has been deleted.

The concrete scenario without compaction: you have a user preferences topic where each message is `{user_id: key, preferences: value}`. Users update their preferences occasionally. With 7-day retention, a consumer that rebuilds its state (a new service instance, a schema migration, a disaster recovery scenario) can only read the last 7 days of preference updates. A user who hasn't changed their preferences in 30 days has no entry in the retained log — their current preferences are invisible to a new consumer. The consumer's rebuilt state is incomplete: it knows the preferences of users who updated recently but has lost the preferences of everyone who didn't.

Log compaction solves this: for every user who has ever written a preference, their latest value is retained indefinitely. A consumer starting from the beginning of a compacted topic will always see the full current state of every key, regardless of when that key was last updated. The log is always a complete, up-to-date snapshot of every key's current value.

**Q3. What does a Kafka log physically look like, and where does compaction operate?**
A: A Kafka partition's log is stored on disk as a series of **log segments** — fixed-size files (default 1GB, controlled by `log.segment.bytes`) each containing a sequential run of messages. Accompanying each segment is an index file (for offset-based lookups) and a time index file (for timestamp-based lookups). Segments are append-only while they are "active" (the segment currently being written to). Only sealed (inactive) segments — all segments except the most recent one — are eligible for compaction.

The partition log is conceptually divided into two regions:
- **The tail (clean section)** — segments that have already been compacted. Contains at most one message per key within the compacted range (the latest value as of the last compaction pass).
- **The head (dirty section)** — the most recent, not-yet-compacted segments. May contain multiple messages per key (all the updates since the last compaction run). The active segment (currently being written) is always in the head.

Compaction operates by reading dirty segments, identifying which keys have more recent values (either in other dirty segments or in the clean section), and writing a new compacted version of those segments — dropping all messages whose key has a newer value elsewhere. The clean/dirty distinction is Kafka's internal bookkeeping for the compaction log cleaner thread.

## Section 2: The Compaction Mechanism

**Q4. Walk through how Kafka's log cleaner performs a compaction pass step by step.**
A: Kafka's log cleaner is a background thread (or pool of threads, controlled by `log.cleaner.threads`) that runs continuously on each broker. The compaction algorithm for one pass on one partition:

**Step 1 — Select the dirtiest partition:**
The log cleaner scans all compacted topics and selects the partition with the highest "dirty ratio" — the ratio of dirty (uncompacted) bytes to total partition bytes. A high dirty ratio means the most compaction benefit per unit of work. The cleaner processes the highest-priority partition first.

**Step 2 — Build the offset map:**
The cleaner reads through the dirty segments and builds an in-memory hash map: `{key → highest_offset_seen_for_key}`. For every key encountered in the dirty section, the map records the offset of the most recent message with that key. This map is bounded in size by `log.cleaner.dedupe.buffer.size` (default 128MB). If the dirty section is very large and the key space is very large, multiple compaction passes may be needed to cover the full dirty range.

**Step 3 — Copy messages to a new segment:**
The cleaner reads through the dirty segments again. For each message, it checks the offset map:
- If the message's offset equals the map's value for that key (this is the most recent message for that key in the dirty range) → **keep**: copy to the new compacted segment.
- If the message's offset is less than the map's value for that key (a newer message for this key exists) → **discard**: do not copy to the new segment.
- If the key does not exist in the map (the key only appears once in the dirty range) → **keep**: this is the only message for this key; copy it.

Additionally: any message whose key appears in the already-clean section with a higher offset than the dirty section's latest → **discard**: the clean section already has a newer value.

**Step 4 — Swap segments:**
Once the new compacted segment is written to disk, the cleaner atomically swaps the old dirty segments for the new compacted segment. The old segments are deleted. The partition's log is now smaller and fully compacted up to the current head.

**Step 5 — Log the clean offset:**
The cleaner records the offset through which compaction has been completed. On the next pass, it only needs to process segments written since this offset.

**Q5. What is a "tombstone" message, and how does it enable key deletion?**
A: Since compaction retains the latest message for every key indefinitely, you might wonder: how do you delete a key entirely from the compacted log? If you stop writing updates for a key, the compactor keeps its last value forever.

A tombstone (or "null message" or "delete marker") is a message written to the topic with the target key and a `null` value. When the compactor encounters a tombstone, it treats it as a signal to delete the key:

- While the tombstone is in the dirty (uncompacted) section, it supersedes all older messages for that key — those older messages are dropped during compaction.
- After the tombstone reaches the clean (compacted) section, it is retained for a configurable grace period (`delete.retention.ms`, default 24 hours). This gives consumers time to read the tombstone and process the deletion (update their local state to reflect the key's removal).
- After `delete.retention.ms` expires, the tombstone itself is deleted in the next compaction pass — the key is now completely absent from the topic.

The `delete.retention.ms` window exists because of the consumer catch-up problem: a consumer that was offline may not have seen the tombstone before it was deleted. The grace period gives offline consumers time to catch up and see the deletion. If a consumer misses the tombstone window entirely, it will never know the key was deleted — its local state will retain the stale value indefinitely. This is a correctness concern for consumers that rely on tombstones for state management (covered in Q22).

**Q6. What is the `min.cleanable.dirty.ratio` setting, and how does it control compaction aggressiveness?**
A: `min.cleanable.dirty.ratio` (default 0.5) is the threshold dirty ratio (dirty bytes / total partition bytes) below which the log cleaner will not compact a partition. If 40% of a partition's bytes are dirty, and `min.cleanable.dirty.ratio = 0.5`, the cleaner skips this partition and moves on to dirtier partitions.

The trade-off this controls:
- **High ratio (e.g., 0.9)** — the cleaner only intervenes when 90% of the partition is dirty (very unclean). Compaction runs infrequently; segments accumulate more duplicates between passes; the log stays larger on average; consumers see more duplicate keys before they are cleaned up. CPU and I/O overhead of compaction is spread out in infrequent, larger bursts.
- **Low ratio (e.g., 0.1)** — the cleaner intervenes aggressively whenever 10% of the partition is dirty. Compaction runs very frequently; the log stays close to its minimum size (one message per key); consumers almost never see duplicates in the clean section. But: constant compaction burns CPU and disk I/O proportional to partition size, even for topics with few updates.

For most production use cases, the default 0.5 is a reasonable balance. Lower it for topics where storage efficiency is critical and update frequency is high (a user state topic receiving thousands of updates per second). Raise it for topics with infrequent writes where compaction overhead should be minimized (a configuration topic with 100 keys updated once per hour).

**Q7. What is `min.compaction.lag.ms`, and what guarantees does it provide consumers?**
A: `min.compaction.lag.ms` (default 0) sets a minimum age before a message is eligible for compaction. A message written at time T cannot be compacted until at least `T + min.compaction.lag.ms`. Messages newer than this threshold are guaranteed to remain in the topic for at least this duration — regardless of compaction.

Why this matters: without `min.compaction.lag.ms`, the compactor can remove a message the moment a newer message with the same key arrives. A consumer reading the topic in real time might fetch message M1 for key K, then poll again and never see M1 (it was already compacted away because M2 arrived). Most consumers handle this correctly (they just see M2, the latest value), but some use cases need to see every intermediate value:

- **Audit log requirements** — regulations may require that every state transition is visible, not just the latest. Setting `min.compaction.lag.ms = 7 * 24 * 60 * 60 * 1000` (7 days) ensures every update is visible for at least 7 days before compaction eligibility.
- **Change data capture (CDC) consumers** — a CDC consumer that applies deltas (not full state snapshots) must see every intermediate update. If a key goes from value A → B → C and the consumer was offline during A → B, it needs to see B → C to apply the delta correctly. `min.compaction.lag.ms` guarantees the intermediate steps are visible for a bounded window.
- **Debugging and replay windows** — for troubleshooting purposes, engineers may want to replay all recent updates to a key to understand how its state evolved. A compaction lag window preserves this replay capability for a recent window.

Setting `min.compaction.lag.ms` effectively creates a hybrid policy: the topic behaves like a delete-retention topic within the lag window (all messages visible) and like a compacted topic outside the lag window (only latest per key visible). This is one of the most useful but underutilized configurations for compacted topics.

## Section 3: Reading a Compacted Topic

**Q8. What ordering and completeness guarantees does a compacted topic provide to consumers?**
A: A compacted topic provides weaker guarantees than a standard topic in some dimensions and stronger in others:

**What is guaranteed:**
- **Latest value always present** — for any key K that has been written and not subsequently tombstoned, the latest value is always readable from the topic. A consumer reading from offset 0 will eventually encounter the latest value for K.
- **Within-key order preserved** — if K had values written in order V1 → V2 → V3, the compacted topic will contain V3 (and possibly V2, V1 if they haven't been compacted yet). It will never contain V3 before V2 before V1 for the same key — compaction preserves the order of surviving messages.
- **Offset monotonicity** — surviving messages retain their original offsets. Compaction does not re-number offsets. A consumer can still use offsets as checkpoints — though gaps in the offset space will exist where compacted messages were removed.

**What is NOT guaranteed:**
- **All intermediate values** — depending on compaction timing and `min.compaction.lag.ms`, some intermediate values for a key may have already been compacted away. A consumer reading the topic for the first time is not guaranteed to see every historical value for a key — only the latest (plus any values in the dirty/uncompacted section).
- **Dense offset space** — offsets in a compacted topic are sparse. After compaction, offset 100 might be immediately followed by offset 250 if messages 101–249 were compacted away. Consumers must handle gaps gracefully — the `seekToBeginning()` call followed by `poll()` will skip the gaps automatically, but code that assumes `nextOffset = lastOffset + 1` will break.
- **Consistent cross-key snapshots** — a consumer reading a compacted topic does not get a point-in-time consistent snapshot of all keys simultaneously. Different keys' "latest values" may have been written at different times. If you need a consistent snapshot of all keys at time T, compaction alone doesn't provide it — you need a stream-table join or an external snapshot store.

**Q9. What is an "offset gap" in a compacted topic, and how should consumers handle it?**
A: An offset gap is a range of offset numbers that no longer have a corresponding message — the messages at those offsets were compacted away. For example, after compaction, a partition might have messages at offsets: 0, 5, 11, 24, 25, 60... with no messages at 1–4, 6–10, 12–23, 26–59.

Consumer handling:
- **`poll()`-based consumers** — the standard Kafka consumer client handles offset gaps transparently. When a consumer fetches from an offset where there is no message, the broker returns the next available message at a higher offset. The consumer's position automatically advances past the gap. No special handling needed.
- **Offset-based storage of consumer position** — consumers that store their position as an offset (which is standard Kafka offset management) must tolerate that their stored offset may point to a gap after compaction. On resume, fetching from a stored offset that has been compacted away returns the next available message at a higher offset — correct behavior, no error.
- **Assumption that `next = current + 1`** — code that assumes consecutive offsets (e.g., tracking "I've processed N messages by counting offsets from 0 to N") breaks on compacted topics. Use actual message counts, not offset arithmetic, for progress tracking.
- **Log start offset awareness** — the "log start offset" (the smallest valid offset in the partition) advances as compaction removes early segments. Consumers that try to read from offset 0 may get a `LogStartOffsetOutOfRange` error if the log start offset has advanced past 0. Handle by catching the exception and seeking to `beginningOffsets()`.

## Section 4: When to Use Log Compaction

**Q10. What are the canonical use cases for log compaction?**
A: Log compaction is the right choice whenever Kafka is modeling **current state** rather than a **stream of events**. The canonical use cases:

**Database change data capture (CDC):**
A CDC pipeline captures every row-level change in a database (INSERT, UPDATE, DELETE) and publishes it to Kafka with the row's primary key as the message key and the row's full current state as the value. Downstream consumers rebuild a copy of the database table by replaying the compacted topic. Compaction ensures: any consumer starting from the beginning of the topic eventually has the full current state of every row, regardless of when rows were last changed. Tombstones represent DELETEs. Used in: Debezium → Kafka → target database replication.

**Event sourcing aggregate snapshots:**
An event-sourced system stores all state changes as events. Periodically, the system publishes a "snapshot" of each aggregate's current state to a compacted Kafka topic. The key is the aggregate ID; the value is the full serialized aggregate. Consumers that need an aggregate's state read from the compacted topic instead of replaying the full event history — dramatically reducing startup time. The compacted topic is the materialized, always-current snapshot store.

**Distributed configuration / feature flags:**
A configuration service publishes configuration updates to Kafka with the configuration key as the message key and the current value as the value. Every service instance subscribes and maintains a local in-memory copy of all configuration. On startup, the service replays the compacted topic from the beginning to get the full current configuration, then follows the tail for live updates. Compaction ensures startup always yields the full current config regardless of when each key was last updated. Used in: feature flag distribution, service discovery, routing tables.

**Materialized views and derived state stores:**
Kafka Streams and ksqlDB use compacted topics as the backing store for KTables — Kafka's representation of a continuously-updated table. Each KTable update is written to a compacted changelog topic. On application restart, the Kafka Streams instance replays the changelog topic to restore the in-memory KTable state. Compaction ensures the changelog topic doesn't grow unboundedly — only the latest value per key is retained.

**User session state / preference stores:**
A user service publishes updates to a user profile topic with `user_id` as the key and the full profile as the value. Any service that needs to look up user profiles (for personalization, authorization, enrichment) can maintain a local cache populated from the compacted topic. Compaction ensures the topic always contains the latest profile for every user who has ever existed, at a storage cost proportional to the number of users rather than the total number of profile updates ever made.

**Q11. When should you NOT use log compaction?**
A: Log compaction is inappropriate when:

- **Every event is semantically distinct and must be preserved** — financial transaction logs, audit trails, order history. Each event is a unique fact ("user placed order #12345 at 2:34pm") that is not superseded by later events. Compaction would merge "user placed order" events with the same order ID, losing the history. Use time-based retention with a long window (or no retention limit) for immutable event facts.

- **Consumers need the full history of a key's values** — if downstream consumers apply incremental deltas (rather than full-state snapshots), they need to see every intermediate value, not just the latest. Unless `min.compaction.lag.ms` is set to cover the consumer's maximum offline window, compaction may remove intermediate values before the consumer can read them.

- **The topic has no meaningful "current state" per key** — some topics model events where the concept of "current state" doesn't apply: click events, page views, sensor readings, log lines. Each message is a standalone fact; there is no "latest click" that supersedes prior clicks for a user. Compaction on these topics produces incorrect semantics — it would retain one click per user, discarding all others.

- **High-volume, low-cardinality key spaces with frequent updates** — a topic where millions of messages per second all share one of 10 possible keys will have a very high compaction rate. The compactor constantly rewrites large segments to eliminate what are almost entirely duplicates. The I/O overhead may be significant without proportionate storage benefit. Evaluate whether a simpler aggregation (a counter in Redis, a KTable in Kafka Streams) serves the use case better.

- **The consuming application is not built to handle offset gaps or tombstones** — legacy consumers that assume dense offset spaces or don't handle `null` values will break on compacted topics. This is an operational constraint, not a theoretical one.

**Q12. What is the "hybrid" retention policy (`cleanup.policy=compact,delete`), and when is it the right choice?**
A: A hybrid policy applies both compaction and time/size-based deletion to the same topic. The behavior: Kafka compacts the topic as usual (retaining the latest value per key), and also deletes segments that are entirely past the retention age. The effective guarantee: the latest value for each key is retained for at least `retention.ms` after it was written.

This is the right choice when you need both properties:
- **Complete current state** (from compaction) — a new consumer joining the topic can rebuild the full current state.
- **Bounded staleness** — keys that haven't been updated in a very long time (months, years) are eventually deleted rather than kept indefinitely. This prevents the topic from accumulating keys for entities that no longer exist (deleted users, cancelled orders, deprecated configuration entries).

Example: a user profile topic. You want the full current profile for every active user (compaction) but don't want profiles for users who deleted their accounts 3 years ago to persist forever (time-based deletion). With `compact,delete` and `retention.ms = 90 days`: any key whose latest value is older than 90 days is eligible for deletion. Keys updated within the last 90 days are always retained with their latest value.

The important behavior under hybrid: the compaction runs first, then deletion. A key with many updates will be compacted to a single latest value; if that latest value ages past `retention.ms`, the single remaining message is deleted. So the storage guarantee is: at most one message per key, retained for at most `retention.ms` after the last write.

## Section 5: Compaction and Kafka Streams / KTables

**Q13. What is a Kafka Streams KTable, and why does it require a compacted changelog topic?**
A: A KTable in Kafka Streams is an abstraction representing the current state of a key-value store — conceptually, a mutable table where each message in the underlying Kafka topic is an upsert (INSERT or UPDATE) keyed by the message key. KTables are used for stateful stream processing: joins, aggregations, and windowed computations that need to access current values.

Every KTable is backed by two things:
1. A **state store** — an in-process RocksDB or in-memory store holding the current values, used for fast lookups during stream processing.
2. A **changelog topic** — a compacted Kafka topic that persists every state store write. The changelog is the durable, replayable backup of the state store.

The changelog must be compacted because:
- **Fault tolerance** — if the Kafka Streams instance crashes and restarts, it replays the changelog topic to restore the state store. Without compaction, the changelog grows unboundedly as the state store is updated. With compaction, the changelog retains only the latest value per key — the minimum data needed to restore the current state. Replay is fast because there are no obsolete intermediate values to re-process.
- **Rebalance recovery** — when a Kafka Streams partition is reassigned (during a rebalance), the new Streams instance must restore the state store from the changelog. Compaction minimizes the restore time by eliminating historical values that don't contribute to the current state.
- **Storage efficiency** — a state store for user sessions may be updated millions of times per day. Without compaction, the changelog would grow at millions of writes per day indefinitely. With compaction, the changelog size is O(number of distinct keys), not O(number of updates).

**Q14. What is "standby replica" in Kafka Streams, and how does the compacted changelog enable it?**
A: A standby replica is a Kafka Streams feature that keeps a warm copy of a state store on a second Streams instance — not the primary processor for those partitions, but a consumer that is following the changelog topic and continuously applying updates to a local replica of the state store. If the primary instance fails, the standby replica already has an up-to-date copy of the state and can take over immediately with minimal catch-up time.

The compacted changelog enables this: the standby instance reads the changelog topic exactly as a recovery process would, but continuously rather than only on failure. Because the changelog is compacted (not a full event history), the standby instance can catch up quickly even if it was briefly offline — it only needs to replay the changes since its last update, not the full history. The compaction ensures the total size of the changelog (and therefore the restore cost) is bounded by the number of distinct keys, not the total number of writes ever made to the state store.

## Section 6: Operational Concerns

**Q15. How do you monitor whether compaction is keeping up with write rate?**
A: Compaction falling behind means the dirty section grows faster than the cleaner can compact it — increasing storage consumption and exposing consumers to more intermediate values. Key metrics to monitor:

- **`kafka.log:type=LogCleanerManager,name=max-dirty-percent`** — the maximum dirty ratio across all compacted partitions on this broker. If consistently near or above `min.cleanable.dirty.ratio`, the cleaner is behind. Values approaching 1.0 indicate the cleaner is not keeping up.
- **`kafka.log:type=LogCleaner,name=cleaner-recopy-percent`** — the percentage of bytes recopied during compaction (vs discarded). High recopy percent means few duplicates are being cleaned — the write pattern may not be key-overwriting (few duplicate keys per compaction pass), so compaction provides little benefit but costs I/O.
- **Log size growth rate** — monitor the partition log size over time. A compacted topic should approach a steady state size proportional to the number of distinct keys × average message size. If size grows continuously, the cleaner is not keeping up or the key space is growing faster than expected.
- **`log.cleaner.threads`** — if the cleaner is consistently behind, increasing this from the default (1) to 2–4 allocates more CPU and I/O to compaction. Useful when a broker hosts many compacted partitions or has high write rates.
- **Segment file count** — a large number of small segments indicates the active segment is rolling frequently (high write rate) and the cleaner hasn't merged them yet. Segment count above ~100 per partition is a signal of cleaner lag.

**Q16. What are the storage implications of a compacted topic vs a delete-retention topic for the same workload?**
A: The storage comparison depends entirely on the key cardinality and update frequency:

**Compacted topic storage = distinct_key_count × avg_message_size (at steady state):**
A compacted topic converges to one message per key. A user profile topic with 10 million users and 1KB average profile size converges to ~10GB regardless of how frequently users update their profiles. Storage is bounded by the key space size.

**Delete-retention topic storage = write_rate × retention_window × avg_message_size:**
A delete-retention topic retains everything in the window. The same user profile topic with 100,000 profile updates/day × 7-day retention × 1KB = ~700MB. But with 10,000,000 updates/day (a highly active user base) × 7-day retention × 1KB = ~70GB — 7× larger than the compacted topic at steady state.

**The crossover point:**
- High update frequency, low key cardinality → compaction is more storage-efficient than delete retention. Each key is updated many times in the retention window; compaction reduces to one copy per key.
- Low update frequency, high key cardinality → delete retention may be more storage-efficient. Each key is updated rarely; the retention window contains mostly unique updates; compaction provides little reduction but still incurs compaction I/O overhead.

**The compaction overhead cost:**
Compaction consumes CPU (building offset maps, reading/writing segments) and disk I/O (reading dirty segments, writing new compacted segments, deleting old segments). For write-heavy topics, compaction I/O can be 2–3× the write I/O (read dirty → write compacted → delete dirty). This overhead must be factored into broker capacity planning for compacted topics under sustained write load.

**Q17. What is the `log.cleaner.min.compaction.lag.ms` vs `log.cleaner.max.compaction.lag.ms` interaction?**
A: These two settings bound the window during which a message is eligible for compaction:

- **`min.compaction.lag.ms`** (default 0) — a message is not eligible for compaction until it is at least this old. Prevents very recent messages from being compacted away before consumers have a chance to read them. Effectively: "every message is visible for at least X milliseconds."

- **`max.compaction.lag.ms`** (default `Long.MAX_VALUE` — effectively infinite) — a message must be compacted within this age if it is eligible. If the dirty ratio hasn't reached `min.cleanable.dirty.ratio` but a message's age exceeds `max.compaction.lag.ms`, the cleaner is forced to compact it anyway. Effectively: "no message waits more than Y milliseconds before being compacted, regardless of dirty ratio."

The interaction:
- A message younger than `min.compaction.lag.ms` → not eligible regardless of dirty ratio.
- A message older than `max.compaction.lag.ms` → must be compacted regardless of dirty ratio.
- A message between the two ages → compacted when the dirty ratio exceeds `min.cleanable.dirty.ratio`.

Practical use: set `max.compaction.lag.ms` to bound the worst-case lag between a write and its compaction — useful for storage budgeting (you know the topic will never exceed more than Y milliseconds of uncompacted data). Set `min.compaction.lag.ms` to guarantee consumers can see recent writes for a defined window.

## Section 7: Design Patterns

**Q18. What is the "event log vs state store" pattern, and how do compacted topics fit into it?**
A: A common architectural pattern in event-driven systems uses two separate Kafka topics for the same domain entity:

- **Event log topic (`cleanup.policy=delete`, long retention)** — records every state change as an immutable event: `OrderPlaced`, `OrderShipped`, `OrderCancelled`. Used for audit trails, event sourcing, analytics, and replay. Each message is a unique fact. Retention is set long enough for all consumers to catch up (7–30 days typically).

- **State store topic (`cleanup.policy=compact`)** — records the current full state of each entity: `{order_id: key, full_order_state: value}`. Written on every state change (alongside the event log). Consumers that need the current state of an entity read the compacted topic rather than replaying the full event log. Used for downstream view rebuilding, cache warming, new service bootstrapping.

The two topics serve different consumers with different needs: consumers that care about what happened use the event log; consumers that care about what is true now use the compacted state store. Writing to both is typically done from the same stream processor: consume the event log, compute the new state, write to both the event log (the event itself) and the compacted state store (the full current state).

This pattern is sometimes called the "dual-write" pattern — with the important note that both writes should be in a Kafka transaction to prevent inconsistency between the two topics if a producer crashes mid-write.

**Q19. How do you "bootstrap" a new service using a compacted topic, and what are the operational considerations?**
A: Bootstrapping a new service instance from a compacted topic:

1. **Consume from the beginning** — start a consumer with `auto.offset.reset = earliest`. The consumer reads all messages from offset 0 (or the current log start offset) to the current end of the topic. Since the topic is compacted, this sweep gives the full current state of every key — one message per key.

2. **Build local state** — as messages are consumed, populate the local state store (in-memory map, RocksDB, Redis). Each message is an upsert to the state store. Tombstones (null values) are deletions.

3. **Follow the tail** — once the consumer reaches the end of the topic (the high watermark), it transitions from "catchup mode" to "live mode." It continues consuming new updates as they arrive, applying them as upserts to keep the local state current.

4. **Service goes live** — the service can start handling requests once it has consumed to the high watermark (or within an acceptable lag threshold — reading to the exact current end of a high-volume topic may take longer than desired).

Operational considerations:
- **Bootstrap time** — proportional to the number of distinct keys × average message size. A topic with 50 million keys at 2KB average = 100GB to read on bootstrap. On a 1Gbps network, this takes ~800 seconds (~13 minutes). Design the service to handle delayed startup, or use Kafka Streams standby replicas to maintain pre-warmed state.
- **Snapshot semantics** — the bootstrapped state is not a point-in-time consistent snapshot. Different keys' values were written at different times. If cross-key consistency is required, either accept the eventual consistency (all keys will converge to current state within seconds of completing the bootstrap), or use a separate consistent snapshot store (a database read at a specific transaction timestamp) for initial state.
- **Topic size must be bounded** — if the key space is unbounded (new unique keys are continuously added without deletion or expiry), the compacted topic grows indefinitely. Bootstrap time increases proportionally. Use tombstones with lifecycle management (write a tombstone when an entity is deleted or expires) or use the hybrid `compact,delete` policy to bound the topic size.

**Q20. What is the "compacted topic as a read model" pattern, and how does it relate to CQRS?**
A: Command Query Responsibility Segregation (CQRS) separates the write model (the command side — how state is updated) from the read model (the query side — how state is queried). Compacted Kafka topics are a natural fit for the read model in CQRS architectures:

- **Write model** — commands are processed by a command handler that validates and applies the change, emitting events to an event log topic. The command handler's authority is the event log (append-only, all events preserved).
- **Read model (compacted topic)** — a stream processor consumes the event log and maintains a compacted topic representing the current query state. Each key in the compacted topic is a queryable entity; the value is the full denormalized read model for that entity (optimized for query access, not for event storage).

Consumers of the read model (API servers, caches, search indexes) subscribe to the compacted topic. They either maintain local in-memory replicas (bootstrapped from the topic) or query a downstream store that was populated from the compacted topic.

The advantages over a traditional CQRS read model backed by a database:
- **Replayability** — if the read model schema changes (a new field is needed, a denormalization decision is revised), the compacted topic can be replayed from the beginning to rebuild the read model in the new format. No custom migration script needed.
- **Multiple read models** — multiple downstream systems can each maintain their own projection of the same compacted topic, optimized for their query patterns (search index for text search, relational DB for complex queries, in-memory map for low-latency lookup).
- **Decoupled scaling** — the compacted topic is the contract. Read model consumers scale independently of the write model. New read models are added by adding new consumers without modifying the write model.

## Section 8: Scenario / System Design Questions

**Q21. "Design a real-time user profile service where any service in the platform can look up the current profile for any user with sub-millisecond latency."**
A: The core challenge: a profile can be updated frequently, must be read at very low latency, and must be available to every service without all of them querying a central database. A compacted topic solves this cleanly:

**Write path:**
- User profile service writes every profile update to a compacted Kafka topic: `user-profiles` (key = `user_id`, value = full serialized profile JSON). Tombstone on account deletion.
- The topic has `cleanup.policy=compact` and `min.compaction.lag.ms = 60000` (1 minute of intermediate-value visibility for any consumers tracking deltas).

**Read path (per consuming service):**
- Each consuming service (recommendation engine, ad targeting, authorization service) runs a Kafka consumer that reads the `user-profiles` topic from the beginning on startup, populating an in-memory `HashMap<user_id, Profile>`.
- After bootstrap, the consumer follows the topic tail — each new message is an upsert to the map.
- Profile lookups are served from the local in-memory map: O(1), sub-millisecond.
- The map is always eventually consistent with the latest writes — lag is typically under 100ms (the Kafka fetch interval + network RTT).

**Operational considerations:**
- **Bootstrap time** — at 10 million users × 2KB average = 20GB. At 1Gbps internal network: ~160 seconds. Service delays startup by this duration on cold start. Mitigate with Kafka Streams standby replicas or pre-built RocksDB snapshots.
- **Memory** — 10 million users × 2KB = 20GB per consuming service instance. Large but manageable for services that genuinely need all profiles. For services that need a subset, filter during bootstrap (consume only relevant user IDs) or use a tiered store (hot profiles in memory, cold profiles on disk via RocksDB).
- **Partitioning** — partition by `user_id` (hash partitioning). Compaction happens per partition; no cross-partition compaction needed.
- **Tombstone TTL** — set `delete.retention.ms = 24 * 60 * 60 * 1000` (24 hours). Consuming services see tombstones for up to 24 hours after a user account deletion, giving them time to remove the profile from their local state.

**Q22. "A consumer missed the tombstone window for a key deletion and now has stale state. How do you handle this operationally?"**
A: This is a correctness gap in tombstone-based deletion: a consumer that was offline for longer than `delete.retention.ms` will never see the tombstone and will retain the deleted key's value in its local state indefinitely.

**Detection:** the consumer's local state has a key that no longer exists in the compacted topic. There's no automatic detection — the consumer doesn't know what it missed. Detection requires an external signal: the application notices the key produces 404s from the authoritative source, an admin reports the key was deleted, or a reconciliation job compares the consumer's local state against the current compacted topic.

**Remediation strategies:**

1. **Full state rebuild from bootstrap** — the simplest fix: the consumer discards its local state and rebuilds from offset 0 of the compacted topic. After bootstrap, the stale key is absent (its tombstone was compacted away; there is no message for this key in the current topic). Cost: full bootstrap time (may be significant for large topics). Appropriate for infrequent, ad-hoc corrections.

2. **Explicit key deletion API** — the consuming application exposes an admin API that accepts a key and deletes it from local state directly, without needing the Kafka tombstone. Used for targeted correction without a full rebuild. Requires authorization and audit logging.

3. **Periodic reconciliation** — a background job periodically reads the full compacted topic and compares it against the consumer's local state. Any local keys absent from the topic are stale deletions — remove them. This is O(topic_size) but can be run infrequently (daily, weekly) for large topics.

4. **Increase `delete.retention.ms`** — the operational fix to prevent recurrence. Set `delete.retention.ms` to at least 2× the maximum expected consumer offline window. If consumers can be offline for up to 24 hours (planned maintenance, deployment windows), set `delete.retention.ms` to 48–72 hours. The storage cost is minimal (one additional small message per deleted key for the retention duration).

5. **Application-level expiry** — instead of relying on tombstones for deletion semantics, include a TTL or expiry timestamp in the message value. Consumers check the expiry field and evict expired keys from local state. Independent of Kafka compaction timing. More robust for consumers with unpredictable offline windows.

**Q23. "Your compacted topic's storage is growing unboundedly despite compaction being active. What are the possible causes?"**
A: Unbounded growth in a compacted topic despite active compaction has several possible causes:

**1. Key space is unbounded (new unique keys are continuously added):**
Compaction retains one message per key, but if new unique keys arrive at a higher rate than old keys are tombstoned, the total number of distinct keys grows indefinitely. The topic size grows proportionally. Diagnosis: plot distinct key count over time. Fix: ensure tombstones are written when entities are deleted or expire; use `compact,delete` with a retention window to eventually evict old keys.

**2. Cleaner is behind the write rate:**
The compaction log cleaner cannot keep up with the rate of incoming messages — the dirty section grows faster than the cleaner can compact it. Diagnosis: check `max-dirty-percent` metric; if it's consistently near 1.0, the cleaner is behind. Fix: increase `log.cleaner.threads`; reduce `min.cleanable.dirty.ratio`; reduce broker I/O contention by redistributing compacted partitions.

**3. `min.compaction.lag.ms` is set very high:**
If `min.compaction.lag.ms` is set to, say, 7 days, the dirty section accumulates 7 days of uncompacted writes before any compaction is eligible. For a high-write-rate topic, this window can be tens of gigabytes. Diagnosis: check topic configuration. Fix: reduce `min.compaction.lag.ms` to the minimum needed for consumer catch-up (typically hours, not days).

**4. Large message values are updated at high frequency:**
A topic with 1 million keys where each key is updated every second and the average value is 10KB: steady-state compacted size = 1M × 10KB = 10GB. But the dirty section accumulates at 1M × 10KB/s = 10GB/s. Even with fast compaction, the dirty section may always contain many duplicates in flight. This is not a bug — it's the workload characteristic. Fix: reduce value size (store only changed fields, not full state); reduce update frequency (batch updates); increase cleaner threads.

**5. Tombstones are not being written for deleted keys:**
If the application deletes entities (users are deleted, orders are cancelled) but never writes a tombstone for those keys, the compacted topic retains their last-written value forever. Diagnosis: compare the number of keys in the topic against the expected number of active entities. Fix: add tombstone writes to the entity deletion code path; implement a reconciliation job that detects and tombstones orphaned keys.

## Quick Reference

**Retention Policy Comparison:**

| Aspect | `cleanup.policy=delete` | `cleanup.policy=compact` | `cleanup.policy=compact,delete` |
|--- |--- |--- |--- |
| Retention guarantee | All messages for retention window | Latest message per key, indefinitely | Latest message per key for retention window |
| Storage bound | Time × write rate | Key count × avg value size | max(key count × value size, time × write rate) |
| Models | Stream of events | Current state snapshot | Time-bounded current state |
| Offset space | Dense (within window) | Sparse (gaps where compacted) | Sparse |
| Key deletion | Automatic (by age) | Via tombstone | Both |
| Use when | Event history, audit logs | State stores, CDC, config | Active entity profiles with lifecycle |

**Key Configuration Cheat Sheet:**

| Config | Default | Effect |
|--- |--- |--- |
| `cleanup.policy` | `delete` | `compact` or `compact,delete` for compacted topics |
| `min.cleanable.dirty.ratio` | 0.5 | Lower = more aggressive compaction |
| `min.compaction.lag.ms` | 0 | Minimum message age before compaction eligibility |
| `max.compaction.lag.ms` | Long.MAX_VALUE | Maximum age before compaction is forced |
| `delete.retention.ms` | 86400000 (24h) | How long tombstones are retained before deletion |
| `log.cleaner.threads` | 1 | Increase for high-write or many-partition brokers |
| `segment.bytes` | 1073741824 (1GB) | Smaller segments = more frequent compaction opportunities |

**When to Use What:**

```
Is the topic modeling current state (latest value per key is meaningful)?
├── Yes → cleanup.policy=compact
│   └── Do entities have a lifecycle (created, deleted)?
│       ├── Yes → add tombstones on deletion + consider compact,delete
│       └── No → compact only
└── No → cleanup.policy=delete
    └── Do consumers need intermediate values + current state?
        └── Yes → cleanup.policy=compact + min.compaction.lag.ms for intermediate window
```
