# Brokers: Leader/Follower Replicas, ISR — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Replication Exists

**Q1. What failure modes does Kafka replication protect against?**
A: A single Kafka broker is a single point of failure on two axes simultaneously:
- **Durability**: If the broker's disk fails or the process crashes with unflushed writes, messages written to that broker but not yet synced to disk are lost forever.
- **Availability**: While the broker is down — whether for seconds (a restart) or longer (hardware failure) — all partitions whose leader lives on that broker are unavailable for reads and writes.

Replication addresses both: each partition's data is copied to multiple brokers, so if the leader broker fails, a follower on a surviving broker takes over as the new leader without data loss (subject to the durability configuration). The system remains available, and no committed messages are lost.

**Q2. What is a "broker" in Kafka's architecture, and what roles can it play?**
A: A broker is a Kafka server process — a JVM process running on a machine, managing a set of partitions on local disk. In a Kafka cluster, brokers play three roles simultaneously:
- **Partition host**: Each broker stores some partitions on local disk and serves reads/writes for those partitions.
- **Leader or follower**: For each partition it hosts, the broker is either the leader (serving all client traffic) or a follower (replicating from the leader).
- **Controller** (one broker at a time, in KRaft; previously the ZooKeeper-elected controller): Manages cluster metadata — tracks which brokers are alive, which replica is the leader for each partition, and triggers leader elections when a broker fails.

A single broker typically hosts hundreds or thousands of partition replicas, split between those where it is the leader and those where it is a follower.

**Q3. What is the replication factor and how does it determine fault tolerance?**
A: The replication factor (RF) is the number of broker replicas that store each partition's data. RF=3 means each partition's data exists on 3 brokers — one leader and two followers. The fault tolerance is `RF − 1` broker failures: with RF=3, you can lose any 2 brokers and still have one surviving replica with the full data (assuming the cluster had RF=3 across those brokers). Most production deployments use RF=3 — tolerating 2 simultaneous failures is the standard reliability bar for message storage.

## Section 2: Partition Placement and Replica Assignment

**Q4. How does Kafka distribute partition replicas across brokers?**
A: When a topic is created, Kafka assigns each partition a replica list — an ordered list of broker IDs that host that partition's replicas. For example, partition 0 of a topic might have replica list `[3, 1, 2]`: the first broker in the list (broker 3) is the preferred leader, and brokers 1 and 2 are followers. Kafka spreads replicas across brokers to avoid co-locating all replicas of a partition on the same physical host. The assignment algorithm stripes replicas across all available brokers in a round-robin pattern, offsetting the starting broker for each partition so that leadership is evenly distributed.

**Q5. What is the "preferred leader" and why does it matter operationally?**
A: The preferred leader for a partition is the first broker in its replica list — the broker Kafka originally chose as the intended leader. Under normal conditions, the preferred leader should be the active leader. Over time, leader assignments drift: when a broker restarts, its partitions temporarily elect followers as leaders, and those followers remain leaders even after the original broker returns — unevenly concentrating leadership (and therefore all client traffic) on a subset of brokers.

`auto.leader.rebalance.enable=true` (the default) causes Kafka to periodically re-elect preferred leaders for partitions that have drifted, restoring balanced leadership. Each re-election triggers a brief leadership transfer — producers may see a short NotLeaderForPartitionException and retry — so the rebalance is throttled by `leader.imbalance.check.interval.seconds`.

**Q6. What is rack-aware replica placement?**
A: When brokers are configured with `broker.rack` (e.g., the AWS availability zone name), Kafka places replicas of a partition across different racks wherever possible. For RF=3 and 3 racks, each replica lands in a different rack — ensuring a single AZ failure (taking out one rack's brokers) cannot eliminate all replicas of any partition. Without rack awareness, a random assignment might co-locate 2 of 3 replicas in the same AZ, making the system vulnerable to single-AZ failure despite RF=3. Rack-aware placement is the production default in cloud deployments and is essential for meaningful multi-AZ fault tolerance.

## Section 3: Leader Replicas

**Q7. What does the leader replica do that followers do not?**
A: The leader is the sole entry point for all client traffic on a partition:
- **Writes**: Producers always write to the leader. The leader appends the message to its local log, then followers replicate it asynchronously (or synchronously for acks=all).
- **Reads**: Consumers read from the leader by default. The leader tracks which offsets have been fully replicated across the ISR (the High Watermark) and only exposes messages up to that boundary to consumers.
- **ISR management**: The leader monitors its followers' replication progress and maintains the ISR — adding replicas when they catch up, removing them when they fall behind.
- **Metadata authority**: The leader answers metadata requests for its partition (who the leader is, what the current ISR contains).

Followers do none of this — they only fetch from the leader and serve as hot standby candidates for leader election.

**Q8. What happens from the producer's perspective when the leader for a partition fails?**
A: The producer sends a write to a broker it believes is the partition leader. If that broker has failed:
1. The write attempt fails — the producer receives either a connection error or a `NotLeaderOrFollowerException`.
2. The producer retries (if `retries > 0`, which is the default in modern Kafka clients).
3. On retry, the producer refreshes its metadata from the cluster (any live broker can serve metadata) to discover the new leader.
4. The producer sends the write to the new leader.

The gap between the old leader failing and the new leader being elected is the window of unavailability — typically under a few seconds in modern Kafka (faster with KRaft than with ZooKeeper). How much data risk exists during this window depends on the `acks` configuration and whether the failed writes were committed to the ISR.

## Section 4: Follower Replicas and the Replication Protocol

**Q9. How do follower replicas replicate data from the leader?**
A: Followers replicate using the same Fetch API that consumers use — they send `FetchRequest` messages to the leader, specifying the partition and the next offset they want (their current Log End Offset + 1). The leader responds with any new messages since that offset. Followers apply the fetched messages to their local log, advancing their Log End Offset. This process runs in a tight continuous loop: followers always have an outstanding fetch request to the leader.

Critically: follower replication is **pull-based**, not push-based. The leader does not push data to followers; followers continuously pull. This design means the leader doesn't need to track each follower's state for delivery purposes — it simply responds to whatever offset the follower requests, and falls back to log-level retention if a follower falls badly behind.

**Q10. What is the Log End Offset (LEO) and how does it differ per replica?**
A: The Log End Offset (LEO) is the offset of the next message to be written to a replica's local log — one past the last written offset. Each replica maintains its own LEO independently:
- **Leader's LEO**: Advances immediately when a new message is written by a producer, before any follower has replicated it.
- **Follower's LEO**: Advances when the follower fetches and appends that message to its local log — always behind the leader's LEO by some amount (the replication lag).

The difference between the leader's LEO and a follower's LEO is the **replica lag** for that follower — how many messages the follower is behind. This lag is the primary metric used to determine ISR membership.

**Q11. Can consumers read from follower replicas? When would you use this?**
A: Yes, since Kafka 2.4. The `replica.selector.class` configuration controls which replica consumers fetch from. The `RackAwareReplicaSelector` routes consumer fetches to the closest replica (same rack/AZ), falling back to the leader if no same-rack follower is available. This reduces cross-AZ data transfer costs significantly in cloud deployments — a consumer in us-east-1a reading from a follower in us-east-1a avoids the inter-AZ bandwidth charges of fetching from the leader in us-east-1b.

The constraint: consumers still only read up to the High Watermark (the committed offset boundary), regardless of which replica they fetch from. A follower that is in the ISR but slightly behind the leader will lag in serving fresh data — so follower reads introduce slightly more read-latency in exchange for reduced network cost. Not appropriate for latency-sensitive consumers; well-suited for high-throughput, cost-sensitive analytics pipelines.

## Section 5: ISR — In-Sync Replicas

**Q12. What is the ISR and what does membership mean?**
A: The ISR (In-Sync Replica set) is the set of replicas that are considered sufficiently caught up to be eligible for leader election and for contributing to the durability guarantee. The leader maintains and updates the ISR. A replica is in the ISR if it has sent a fetch request to the leader within `replica.lag.time.max.ms` (default: 30 seconds) AND has caught up to within a small delta of the leader's Log End Offset.

ISR membership has two direct consequences:
- **Durability**: A write is considered "committed" (and the High Watermark advances) only when all ISR members have replicated it. If a replica is out of the ISR, it doesn't block commits — out-of-ISR replicas are excluded from the quorum.
- **Leader election eligibility**: Only ISR members are eligible for clean leader election. An out-of-ISR replica cannot become leader without an unclean election.

**Q13. How and when does a replica get removed from the ISR?**
A: A replica is removed from the ISR when the leader observes that it has not sent a fetch request, or has not caught up, within `replica.lag.time.max.ms` (default: 30s). The scenarios:
- **Follower broker failure or crash**: The follower stops sending fetches. After 30s of silence, the leader removes it from ISR and updates the ISR list in the cluster metadata (ZooKeeper or KRaft).
- **Follower is alive but slow**: A follower is running but its fetch loop can't keep up with the leader's write rate — perhaps due to disk I/O saturation or GC pauses. If it falls behind for more than `replica.lag.time.max.ms`, it is evicted from the ISR even though the process is running.
- **Network partition**: The follower can't reach the leader. No fetches are received by the leader for 30s → evicted from ISR.

ISR changes are cheap coordination operations — no data moves, no partition reassignment. The leader updates the ISR set in the metadata layer, and subsequent writes only need acknowledgment from the remaining ISR members.

**Q14. How does a replica rejoin the ISR after falling out?**
A: A replica that was removed from the ISR keeps fetching from the leader, advancing its LEO. When it catches up — when its LEO reaches the leader's High Watermark — the leader adds it back to the ISR. The rejoining is automatic and requires no operator intervention.

The catch-up period can take significant time if the replica fell far behind (e.g., a broker was down for an hour on a high-throughput topic). During catch-up, the replica is not in the ISR, so it doesn't contribute to the durability quorum. A cluster operating with a shrunken ISR (e.g., ISR size 1 when RF=3) is a degraded state — writes are still acknowledged by the leader alone, but no redundancy exists until replicas catch up and rejoin.

**Q15. What is the difference between the ISR and the full replica set (AR — Assigned Replicas)?**
A: The Assigned Replicas (AR) set is the complete list of brokers assigned to host a partition — set at topic creation and unchanged unless the partition is explicitly reassigned. The ISR is a dynamic subset of the AR, containing only the replicas currently caught up to the leader. 

```
AR  = {broker_1, broker_2, broker_3}    ← fixed at topic creation
ISR = {broker_1, broker_2}              ← dynamic; broker_3 has fallen behind

Out-of-sync replicas (OSR) = AR \ ISR = {broker_3}
```

The ISR is what Kafka actually uses for commit decisions and leader election eligibility. The AR is the target state — Kafka will try to bring all AR members into the ISR over time. Monitoring ISR size relative to AR size is a key health signal: `ISR size < AR size` means some replicas are out of sync — the partition has reduced redundancy.

## Section 6: High Watermark and Log End Offset

**Q16. What is the High Watermark and why do consumers only read up to it?**
A: The High Watermark (HW) is the highest offset at which every replica in the ISR has received and written the data — the offset boundary of fully committed messages. Consumers (and follower-fetch-serving replicas) only return messages up to the High Watermark, never beyond it.

The reason: messages beyond the HW have been written to the leader but not yet replicated to all ISR members. If the leader failed immediately after writing but before those messages were replicated, the new leader (elected from the ISR) would not have those messages — they'd be lost. If a consumer had already read those messages before they were lost, the consumer would have processed data that the system subsequently treats as never having existed. This creates a phantom-read anomaly — the consumer's downstream system has a record that the source system doesn't. By gating consumer reads at the HW, Kafka ensures consumers only see durable, committed data.

**Q17. Walk through exactly how the High Watermark advances after a producer write.**
A:

```
Initial state: HW = 4, Leader LEO = 5, Follower-1 LEO = 4, Follower-2 LEO = 4

Step 1: Producer writes message at offset 5
  → Leader LEO = 6
  → HW stays at 4 (followers haven't replicated offset 5 yet)

Step 2: Follower-1 sends Fetch(offset=5) → gets message → Follower-1 LEO = 6
Step 3: Follower-2 sends Fetch(offset=5) → gets message → Follower-2 LEO = 6

Step 4: Leader receives next fetch from Follower-1 (which includes Follower-1's LEO=6)
  Leader now knows all ISR members have LEO ≥ 6
  → Leader advances HW to 6

Step 5: Leader includes updated HW (6) in its FetchResponse to followers
  → Followers update their local copy of HW to 6

Step 6: Consumer can now fetch offset 5 (up to HW=6 means offset 5 is readable)
```

Key subtlety in Step 4: the HW advances on the leader when it receives the *next* fetch from each ISR member containing an updated LEO — not immediately when it writes the message. There is always a one-fetch-cycle lag between the leader writing a message and the HW advancing to include it. This means even with followers running at full speed, there is a brief window between a write and its visibility to consumers.

**Q18. What is the "HW propagation lag" and why does it matter for producer latency?**
A: With `acks=all`, the producer's write is acknowledged only after the HW advances past the written offset — which requires all ISR members to have fetched and acknowledged the message, and the leader to have received their updated LEO in the next fetch response. This means `acks=all` latency is bounded from below by one full replication round-trip: producer → leader → follower fetch → leader updates HW → producer acknowledgment. For a cluster with followers in the same data center, this might be 1–5ms. For a multi-region cluster with followers in another AZ, this could be 20–100ms per write. The HW propagation lag is the irreducible floor of `acks=all` write latency.

## Section 7: Durability — acks and min.insync.replicas

**Q19. What are the three `acks` settings and what does each guarantee?**
A:
- **`acks=0`**: The producer sends the message and does not wait for any acknowledgment. Maximum throughput, zero durability guarantee — if the broker receives the message but crashes before writing to disk, the message is lost. The producer also cannot detect or retry failures. Use only for truly disposable data (metrics, telemetry where losing some data is acceptable).
- **`acks=1`** (former default): The leader acknowledges the write after writing it to its local log, before any follower replicates it. The producer is protected against the broker rejecting the write (network failure, partition not found) but not against leader failure before replication. If the leader crashes immediately after acknowledging, the followers have not yet replicated the message — a new leader elected from the ISR will not have it, and it is lost. A common source of data loss in Kafka deployments that haven't reviewed their durability settings.
- **`acks=all` (or `acks=-1`)**: The leader acknowledges only after all ISR members have replicated the message (i.e., the HW has advanced past the written offset). A committed write survives any single broker failure — at least one ISR member has the data, and that member is eligible for leader election. This is the correct setting for any data where loss is unacceptable. Latency is higher (one replication RTT per write) but durability is guaranteed within the ISR contract.

**Q20. What is `min.insync.replicas` and how does it interact with `acks=all`?**
A: `min.insync.replicas` (min.isr) is a topic or broker configuration that sets the minimum ISR size required for writes to be accepted. If the ISR shrinks below this threshold, the leader rejects writes with `NotEnoughReplicasException` even if the leader itself is alive.

It only takes effect when `acks=all` — with `acks=1`, the leader writes locally regardless of ISR size.

The canonical production configuration: **RF=3, min.isr=2, acks=all**:
- Normally: ISR = {leader, follower-1, follower-2} — writes need all 3 to ack → very durable
- One follower falls behind: ISR = {leader, follower-1} — ISR size 2 = min.isr, writes still accepted, acknowledged when leader + follower-1 confirm — durable with 1 surviving replica
- Two followers fall behind: ISR = {leader only} — ISR size 1 < min.isr 2 — **writes rejected** — the system trades availability for durability, refusing to commit data with no redundancy

The last scenario is the intended safety stop: rather than write data with no replication redundancy (and risk total loss if the leader fails), the system refuses writes until ISR recovers. This is a deliberate availability trade-off for the durability guarantee.

**Q21. What is the practical risk of `min.insync.replicas=1` even with `acks=all`?**
A: With `min.isr=1`, the ISR can shrink to just the leader (the minimum is satisfied by the leader alone) and writes continue to be acknowledged by `acks=all`. But `acks=all` with ISR={leader only} is functionally identical to `acks=1` — the leader writes locally and immediately acknowledges, with no replica to survive a leader failure. The `acks=all` setting becomes meaningless: the "all" in "all ISR members" is satisfied by one member (the leader itself). This is a common misconfiguration — operators set `acks=all` believing they have durability, but with `min.isr=1` they have none when ISR degrades. Always set `min.isr >= 2` for actual durability guarantees.

**Q22. What does "committed" mean in Kafka, and how is it different from the producer's acknowledgment?**
A: A message is "committed" in Kafka when it has been written to the local log of every replica in the ISR — i.e., when the High Watermark has advanced past that message's offset. "Committed" in this sense is Kafka's internal durability marker. It is what enables:
- Consumers to safely read the message (they only read up to HW)
- The message to survive a leader failover (any ISR member can become leader without losing it)

The producer's acknowledgment (`acks=all`) is confirmation that the message is committed. With `acks=1`, the producer is acknowledged before the message is committed (only leader has it). The word "committed" in Kafka is distinct from "committed offsets" in consumer groups (which refers to the consumer's read position checkpoint) — two different uses of the same word in the Kafka ecosystem that confuse many engineers.

## Section 8: Leader Election and Unclean Elections

**Q23. How does leader election work when a partition's leader broker fails?**
A: When the active controller (a broker running the controller role, via KRaft or ZooKeeper) detects that a broker has failed (via heartbeat timeout), it:
1. Identifies all partitions whose leader was on the failed broker.
2. For each such partition, selects a new leader from the partition's ISR — typically the first ISR member in the replica list that is still alive.
3. Updates the cluster metadata with the new leader assignments.
4. Propagates the updated metadata to all live brokers (via LeaderAndIsrRequest in older Kafka; via KRaft log in newer versions).
5. Live brokers update their local metadata — producers and consumers refreshing their metadata will discover the new leader and reconnect.

With KRaft (Kafka 3.3+ production-stable), the metadata propagation is significantly faster — controller failover itself drops from ~30 seconds (ZooKeeper-based) to under 1 second, and partition leadership transfers are correspondingly faster.

**Q24. What is an "unclean" leader election and what are its consequences?**
A: A clean leader election elects only from ISR members — replicas that have all committed messages. An unclean election elects a replica that is NOT in the ISR — one that has fallen behind and is missing some committed messages. This happens when:
- The ISR is empty: all ISR members (including the leader) are unavailable, and only out-of-sync replicas are alive.
- `unclean.leader.election.enable=true` (default: `false` in recent Kafka versions; was `true` in older versions).

Consequences of an unclean election:
- **Data loss**: Messages that were committed (acknowledged with `acks=all`, visible to consumers up to HW) but not replicated to the new leader are permanently lost. Consumer offsets may now point past the new leader's LEO — the broker will return an `OffsetOutOfRangeException`.
- **Offset divergence**: The new leader's log diverges from what consumers have already read — messages at offsets X through Y existed on the old leader, were read by consumers, but no longer exist on the new leader's log.

Trade-off: `unclean.leader.election.enable=false` (the safe default) means if all ISR members are unavailable and only out-of-sync replicas survive, the partition remains unavailable (no leader elected) — durability over availability. `enable=true` restores availability immediately at the cost of data loss. For financial or audit data: never enable unclean election. For metrics or logging where losing some data is acceptable: enabling it is a valid choice.

**Q25. What is the role of the controller in Kafka, and how did KRaft change it?**
A: The controller is a broker elected to manage cluster-level metadata — which brokers are alive, which replica is the leader for each partition, ISR membership changes. There is exactly one active controller at a time.

**ZooKeeper era (pre-KRaft)**: One broker registers an ephemeral node in ZooKeeper to claim the controller role. ZooKeeper's session expiry detects controller failure and a new broker races to claim the role. ISR and leader information was also stored in ZooKeeper — creating a bottleneck as all metadata updates required ZooKeeper round trips. Controller failover took 20–60 seconds.

**KRaft (Kafka Raft Metadata)**: A quorum of brokers (typically 3 dedicated controller nodes) runs the Raft consensus protocol to elect an active controller and maintain a replicated metadata log. No ZooKeeper dependency. Benefits: controller failover in under 1 second; metadata stored in Kafka's own log (more consistent with the rest of the system); support for millions of partitions (ZooKeeper was a scalability bottleneck). ZooKeeper was removed entirely in Kafka 4.0.

## Section 9: Scenario / System Design Style Questions

**Q26. "Your Kafka topic has RF=3 and 3 brokers. Broker 2 fails. Walk through what happens to ISR, leadership, and producer behavior for a partition whose leader was on Broker 2."**
A:

```
Before failure:
  AR  = {Broker 2 (leader), Broker 1, Broker 3}
  ISR = {Broker 2, Broker 1, Broker 3}
  HW  = 1000

T+0:  Broker 2 crashes (disk failure)
T+1s: Controller detects Broker 2 heartbeat missing (ZooKeeper session expires / KRaft heartbeat lost)
T+2s: Controller selects new leader from ISR ∩ alive_brokers = {Broker 1, Broker 3} → elects Broker 1
      Updates metadata: leader = Broker 1, ISR = {Broker 1, Broker 3}
T+3s: Producers receiving NotLeaderForPartitionException refresh metadata → discover Broker 1 is leader
      Producers reconnect to Broker 1 and resume writes
T+3s: Broker 3 continues fetching from Broker 1 (new leader) — no disruption for Broker 3
T+30s onwards: If Broker 2 comes back online, it fetches from Broker 1 to catch up
              Once caught up, Broker 1 (leader) adds Broker 2 back to ISR
              ISR = {Broker 1, Broker 3, Broker 2}
              If auto.leader.rebalance.enable=true, preferred leader (Broker 2) eventually reclaims leadership
```

Write gap: ~2–3 seconds of producer retries during leader election. No committed data loss (Broker 1 was in ISR and had all messages up to HW=1000). Messages produced during the gap with `acks=all` will retry and succeed once Broker 1 is recognized as leader.

**Q27. "A monitoring alert fires: `kafka_server_replicamanager_underreplicatedpartitions > 0` for 10 minutes. What does this mean and how do you investigate?"**
A: Under-replicated partitions (URPs) means one or more partitions have `ISR size < AR size` — some assigned replicas are not in the ISR, reducing redundancy below the intended replication factor. For 10 minutes, this is a sustained degradation, not a transient replication blip.

Diagnosis steps:
1. **Identify which brokers are out of ISR**: `kafka-topics.sh --describe --under-replicated-partitions` shows each under-replicated partition with its current ISR vs. AR. If one broker is absent from all affected ISR sets, that broker is the problem.
2. **Check that broker's health**: Is it running? Check broker logs for disk errors, GC pauses, network errors. Check `kafka.server:type=ReplicaManager,name=ReplicaFetcherManager` metrics for fetch lag.
3. **Check disk I/O**: A follower falling behind is almost always disk-bound. `iostat`, disk queue depth, and broker metrics like `kafka.server:type=BrokerTopicMetrics,name=BytesInPerSec` can show if the broker is overwhelmed.
4. **Check network**: Is the follower unable to reach the leader? Cross-AZ bandwidth saturation?

If a broker has crashed and won't return soon: let `min.isr` configuration decide whether writes continue (if ISR ≥ min.isr) or stop (if ISR < min.isr). If it's running but slow: reduce leader write rate or give the follower headroom to catch up (temporarily reduce `quota.replication.throttled.replicas` and `replica.fetch.max.bytes`). Don't restart the broker hastily — a broker restart causes all its partitions to briefly leave ISR, potentially compounding the URP count.

**Q28. "You need to configure a Kafka topic for payment events where no payment can be lost and the system must handle a single broker failure gracefully. What configuration do you choose and why?"**
A: The configuration:

```
replication.factor          = 3       # 3 replicas; tolerate 1 broker failure cleanly
min.insync.replicas         = 2       # writes accepted only when ≥ 2 ISR members exist
acks                        = all     # producer waits for all ISR members to acknowledge
unclean.leader.election.enable = false # never elect an out-of-sync replica (data loss unacceptable)
```

Rationale:
- **RF=3 + min.isr=2 + acks=all**: A write is acknowledged only when the leader AND at least one follower have it. If the leader fails immediately after acknowledging, one follower has the data and can be elected as the new leader without data loss. We tolerate 1 broker failure without any write loss; the system also continues accepting writes as long as ISR size ≥ 2 (1 broker failure is acceptable, 2 simultaneous failures would block writes — the right trade-off for payments).
- **unclean.leader.election.enable=false**: If somehow all ISR members fail (a highly unlikely 2+ simultaneous failure scenario), the partition becomes unavailable rather than electing an out-of-sync replica that would lose committed payments. Availability is sacrificed for durability — for payments, this is non-negotiable.
- **Producer `retries=Integer.MAX_VALUE` + `delivery.timeout.ms` tuning**: With acks=all, producers should be configured to retry indefinitely within a time bound, so transient leader elections (taking 2–3 seconds) don't result in dropped messages.

**Q29. "Your team uses `acks=1` on a high-throughput topic. An engineer proposes switching to `acks=all`. The lead pushes back, citing latency concerns. How do you reason through this?"**
A: The lead's concern is valid — `acks=all` adds at least one replication round-trip to every write. But the reasoning needs to be grounded in actual numbers:

**Measure the current replication latency**: Check `kafka.server:type=ReplicaManager,name=FollowerMaxLag` and the fetch response times between brokers. In a co-located cluster (same data center, same rack), replication latency is typically 1–5ms. That's the additional p50 latency `acks=all` adds per write.

**Measure the current write latency with `acks=1`**: If the producer's current p99 write latency is 20ms, adding 5ms for replication is a 25% increase — meaningful but not catastrophic. If it's 200ms (due to batching or broker load), 5ms is noise.

**Quantify the data loss risk of `acks=1`**: With `acks=1`, every message acknowledged by the leader but not yet replicated is at risk during a leader failure. For a 100MB/s throughput topic with 30ms average replication lag, approximately 3MB of data is vulnerable to loss at any moment. Over months of operation, a leader failure during peak write will lose data.

**Propose a middle ground**: Consider `acks=all` with the producer `linger.ms` and `batch.size` increased — batching more messages together amortizes the replication RTT cost across more messages, reducing per-message latency overhead. Or use `acks=all` only on the specific high-value partitions while keeping `acks=1` on lower-value partitions within the same topic (via partition-level producer configuration).

**Q30. "After a leader failover, consumers begin throwing `OffsetOutOfRangeException` for some partitions. What happened and how do you recover?"**
A: This is the signature of an **unclean leader election** — a replica that was behind was elected leader, and its log is shorter than what consumers have already read. The new leader's LEO is at offset X, but consumer committed offsets are at X+N (messages X through X+N were committed on the old leader, read by consumers, but never reached the new leader before the election). When consumers try to fetch from X+N, the new leader says "that offset doesn't exist in my log."

Recovery options, in order of preference:

- **Restore the old leader**: If the original leader broker is recoverable (disk still intact), bring it back online. It has the authoritative log with offsets X through X+N. Trigger a preferred-leader election to restore it as leader. Consumers can resume normally.
- **Reset consumer offsets to the new leader's LEO**: With `kafka-consumer-groups.sh --reset-offsets --to-latest` on the affected partitions. Consumers skip the lost messages and resume from the current end of the log. The lost messages are permanently gone — acceptable only if loss is tolerable.
- **Replay from an external source**: If the messages that were lost were also written to an external system (database, object store), replay them from there into the topic to fill the gap, then resume normal consumption.

**Prevention**: Set `unclean.leader.election.enable=false`. If the ISR is empty and no clean election is possible, accept the partition being unavailable until the original leader recovers rather than electing an out-of-sync replica and creating this exact scenario.

| Replication factor (RF)     | Number of broker copies per partition; RF=3 tolerates 1 broker failure                      |
| Leader replica              | Serves all producer writes and consumer reads; manages ISR                                   |
| Follower replica            | Continuously fetches from leader; hot standby; eligible for leader election if in ISR        |
| ISR                         | Dynamic subset of AR; replicas within `replica.lag.time.max.ms` of leader's LEO             |
| Replica removal from ISR    | No fetch/catch-up within `replica.lag.time.max.ms` (default 30s)                            |
| Log End Offset (LEO)        | Next offset to write; each replica has its own; leader's LEO > follower LEO (lag)           |
| High Watermark (HW)         | Highest offset replicated to ALL ISR members; consumer read boundary                        |
| `acks=0`                    | Fire-and-forget; no durability                                                               |
| `acks=1`                    | Leader-local write; vulnerable to leader failure before replication                         |
| `acks=all`                  | All ISR members must acknowledge; durable within ISR contract                               |
| `min.insync.replicas`       | Minimum ISR size for writes to be accepted with `acks=all`; RF=3, min.isr=2 is standard     |
| Clean election              | New leader elected from ISR; no data loss                                                    |
| Unclean election            | Out-of-ISR replica elected; possible data loss; `unclean.leader.election.enable=false`      |
| Preferred leader            | First in replica list; auto-rebalanced to by `auto.leader.rebalance.enable=true`            |
| KRaft                       | Raft-based metadata; no ZooKeeper; controller failover <1s; default since Kafka 4.0         |

## The Core Mental Model

```
Partition replication flow:
  Producer → Leader (writes; advances Leader LEO)
           ↓
  Followers pull via Fetch API (advance Follower LEO)
           ↓
  Leader tracks min(ISR members' LEO) → advances High Watermark
           ↓
  Consumer reads up to High Watermark (never beyond — committed data only)

ISR = "who is caught up enough to be trusted"
  In ISR  → contributes to HW advancement; eligible for clean election
  Out of ISR → ignored for HW; ineligible for clean election; still replicating to catch up

Durability config:
  acks=all + min.isr=2 + RF=3 → survives 1 broker failure with zero committed data loss
  acks=1                      → survives nothing; leader failure before replication = data loss
  min.isr=1 with acks=all     → false security; ISR={leader only} → same as acks=1

The High Watermark is what keeps the system honest:
  A message exists (LEO advanced) ≠ a message is committed (HW advanced)
  Consumers only see committed messages → no phantom reads after leader failover
```

---

**Tip for the interview:** Broker replication questions at 5 YOE almost always escalate to one of three places: (1) the `acks=all` + `min.isr` combination and what exactly it guarantees — know the RF=3/min.isr=2 math and the "min.isr=1 is a trap" point cold; (2) the High Watermark vs LEO distinction — why consumers don't read the leader's full log and what would go wrong if they did; (3) unclean leader election — when it happens, what it destroys, and why `false` is the right default. The strongest signal at this level: knowing that `acks=all` with ISR shrunk to 1 is functionally identical to `acks=1`, and that `min.insync.replicas` is the guard that prevents this silent degradation. That's the kind of nuance that separates someone who has operated Kafka from someone who has only read about it.
