# ZooKeeper vs KRaft Mode (Modern Kafka) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why did Kafka depend on ZooKeeper historically, and what did ZooKeeper do for it?**
A: Kafka was designed in 2011 before it had its own distributed coordination capability. It outsourced all consensus and metadata management to ZooKeeper, which handled several critical responsibilities:

- **Broker registration:** Each broker registered an ephemeral ZooKeeper node (`/brokers/ids/{broker_id}`) on startup. When a broker died, its ephemeral node was automatically deleted — triggering the Controller to detect the failure.
- **Controller election:** One broker acts as the Controller (the cluster's brain — assigns partition leaders, handles broker failures). The Controller was elected by a ZooKeeper leader election: brokers raced to create `/controller`; the winner became Controller.
- **Topic and partition metadata:** Topic configurations, partition counts, replica assignments, and ISR state were all stored as ZooKeeper znodes.
- **Consumer group coordination (old API):** Pre-Kafka 0.9, consumer offsets were stored in ZooKeeper. Replaced by `__consumer_offsets` topic, but the underlying pattern remained ZK-dependent.
- **Access control lists (ACLs):** Security configurations were stored in ZooKeeper.

**Q2. What were the fundamental problems with the ZooKeeper dependency?**
A: The ZooKeeper dependency created architectural and operational problems that grew more severe as Kafka clusters scaled:

**Operational complexity:** Running a Kafka cluster required running and maintaining a separate ZooKeeper cluster — a different system with its own version management, configuration, monitoring, and operational expertise. Teams had to be proficient in two distributed systems instead of one. ZooKeeper cluster failures could take down Kafka even if Kafka brokers were healthy.

**Metadata scalability ceiling:** All cluster metadata (topic configs, partition assignments, ISR state) lived in ZooKeeper. ZooKeeper's in-memory data model and single-writer architecture limited the number of partitions a Kafka cluster could support. With thousands of partitions, every broker startup required reading the entire cluster state from ZooKeeper — taking minutes in large clusters. Kafka clusters at scale were limited to ~200,000 partitions before ZooKeeper became a bottleneck.

**Controller failover latency:** On Controller failure, a new Controller had to be elected via ZooKeeper and then reconstruct its full in-memory state by reading all partition metadata from ZooKeeper. In a cluster with 100,000 partitions, this took 30+ seconds — during which partition leadership changes (from broker failures) could not be processed.

**Dual write inconsistency window:** The Controller kept an in-memory cache of cluster state and periodically synced it to ZooKeeper. If the Controller crashed between an in-memory update and the ZooKeeper write, the cluster entered a briefly inconsistent state that the new Controller had to reconcile.

**Q3. What is KRaft mode and what was the motivation for building it?**
A: KRaft (Kafka Raft) is Kafka's internal consensus mechanism, introduced in KIP-500, that replaces ZooKeeper entirely. Instead of delegating coordination to an external system, Kafka runs its own Raft-based consensus protocol to manage cluster metadata. The key insight:

Kafka already stores data in an ordered, replicated, durable log — the same primitives needed for consensus. Rather than paying the overhead of ZooKeeper (separate cluster, separate protocol, separate operational tooling), Kafka uses its own log infrastructure to replicate cluster metadata among a small set of dedicated metadata nodes (the quorum).

**KRaft was motivated by:**
- Eliminating ZooKeeper as an operational dependency and failure domain.
- Removing the partition count ceiling imposed by ZooKeeper's in-memory model.
- Reducing Controller failover time from ~30 seconds to milliseconds.
- Simplifying Kafka deployment (one system, not two).
- Enabling Kafka to eventually support millions of partitions per cluster.

**Q4. What is the KRaft quorum and how does it differ from ZooKeeper's ensemble?**
A: In KRaft mode, a subset of brokers (or dedicated non-broker nodes) form the **metadata quorum** — the set of nodes that participate in Raft consensus for cluster metadata. The quorum is configured via `controller.quorum.voters` in `server.properties`.

**Key differences from ZooKeeper:**

| Aspect | ZooKeeper Ensemble | KRaft Quorum |
|---|---|---|
| Separate process? | Yes — runs on separate JVMs/machines | No — runs inside Kafka broker process (or dedicated controller process) |
| Protocol | ZAB (ZooKeeper Atomic Broadcast) | Raft |
| Data model | Hierarchical znode tree | Kafka topic log (`@metadata` topic) |
| Client protocol | Custom ZK wire protocol | Kafka's own metadata protocol |
| Recommended size | 3 or 5 nodes | 3 or 5 controller nodes |
| Read scalability | Any ZK node can serve reads | Active controller only (followers observe) |
| Election mechanism | ZK leader election via znodes | Raft leader election via term/vote |
| Operational team | Requires ZK expertise | Kafka-only expertise sufficient |

**Deployment modes in KRaft:**
- **Combined mode:** The same brokers act as both data brokers and quorum controllers. The controller role is handled by a thread within the broker process. Simpler, suitable for smaller clusters.
- **Isolated mode (recommended for production):** Dedicated controller nodes that do not host topic partitions. Quorum controllers are separate from data brokers. Decouples the metadata layer from the data layer — a metadata-heavy operation doesn't impact data throughput and vice versa.

## Section 2: Architecture Differences

**Q5. How does metadata storage differ between ZooKeeper mode and KRaft mode?**
A: This is the most fundamental architectural difference.

**ZooKeeper mode — split metadata storage:**
```
Cluster metadata lives in ZooKeeper (znodes):
/brokers/ids/1        → broker 1 registration
/brokers/topics/      → topic configurations
/admin/reassign_partitions → ongoing reassignments
/controller           → current controller ID
/config/topics/...    → per-topic config overrides

Controller's in-memory state (ephemeral, rebuilt on restart):
- Partition → leader mapping
- ISR state per partition
- Pending reassignments

Sync between ZK and controller memory: periodic, dual-write pattern.
```

**KRaft mode — single-log metadata storage:**
```
All cluster metadata lives in a special internal Kafka topic: __cluster_metadata
(also called the metadata log or @metadata topic)

Every metadata change is a record in this log:
- BrokerRegistrationRecord
- TopicRecord
- PartitionRecord (partition → replica assignments, ISR)
- PartitionChangeRecord (leader changes, ISR changes)
- ConfigRecord (topic/broker configuration)
- RemoveTopicRecord

The active controller is the Raft leader. It appends metadata changes
to the __cluster_metadata log.

Followers (standby controllers) replicate the log — they always have a
current copy of cluster state and can become active instantly.

Brokers also replicate __cluster_metadata from the active controller —
they maintain their own in-memory view of cluster state, updated
continuously as new metadata records arrive.
```

**Q6. How does Controller failover differ between ZooKeeper mode and KRaft mode?**
A: Controller failover is where KRaft shows its most dramatic improvement.

**ZooKeeper mode failover (slow path):**
```
1. Controller crashes.
2. Controller's ZK session expires (up to 18 seconds default).
3. ZK /controller ephemeral node is deleted.
4. Brokers race to create /controller — winner becomes new Controller.
5. New Controller reads ALL cluster state from ZooKeeper:
   - All broker registrations
   - All topic and partition configs
   - All replica assignments
   - All ISR states
   This is a full scan of ZooKeeper — O(partitions) reads.
6. New Controller rebuilds in-memory state.
7. New Controller becomes active and can process changes.

Total time: 30 seconds (ZK session timeout) + state load time.
For 200,000 partitions: often 60–120 seconds total.
During this window: no partition leader elections, no ISR updates.
A broker failure during controller failover creates a compounding outage.
```

**KRaft mode failover (fast path):**
```
1. Active controller (Raft leader) crashes or becomes unreachable.
2. Remaining quorum members detect missing heartbeats
   (election timeout: 2 × quorum.fetch.timeout.ms, default ~2 seconds).
3. A follower starts a Raft election — increments term, requests votes.
4. New leader is elected (requires majority of quorum members).
5. New leader is already fully up-to-date — it has been replicating
   the __cluster_metadata log continuously. No state load needed.
6. New leader becomes active controller immediately.

Total time: 2–5 seconds (election timeout + vote round trip).
For 1,000,000 partitions: same 2–5 seconds (state is already loaded).
```

**Why KRaft is faster:** Standby controllers in KRaft are always in sync with the active controller — they replicate every metadata change as it happens. On failover, there is nothing to load; the new leader starts from the tip of the log it already has. This fundamentally changes failover from an O(partitions) operation to an O(1) operation.

**Q7. How does broker startup differ between ZooKeeper mode and KRaft mode?**
A: Broker startup performance reveals another fundamental difference.

**ZooKeeper mode startup (slow for large clusters):**
```
1. Broker connects to ZooKeeper.
2. Broker registers itself (/brokers/ids/{id}).
3. Broker reads ALL partition metadata from ZooKeeper to build its
   local state: which partitions it leads, which it follows, current ISR.
   → O(partitions) ZooKeeper reads.
   → For 100,000 partitions: may take 30–120 seconds.
4. Broker starts serving requests.
```

**KRaft mode startup (fast, O(1) initial connection):**
```
1. Broker connects to the active KRaft controller.
2. Broker sends BrokerRegistrationRequest to the controller.
3. Controller sends the broker a snapshot of __cluster_metadata
   (or the broker fetches from the log if it has a recent checkpoint).
4. Broker applies the snapshot, has full current state.
   → The snapshot is a single transfer, not N ZooKeeper reads.
   → For 1,000,000 partitions: seconds, not minutes.
5. Broker subscribes to the metadata log — receives incremental updates
   as they happen. State stays current without polling.
```

The key mechanism: KRaft brokers receive a **metadata snapshot** on startup (a point-in-time serialized copy of all current metadata), then subscribe to the delta log for subsequent changes. This is efficient regardless of partition count.

**Q8. How does KRaft's Raft implementation differ from a general Raft implementation?**
A: Kafka's Raft implementation (KRaft) is tailored for the metadata log use case and differs from textbook Raft in several ways:

**Fetch-based replication (pull, not push):**
Standard Raft: the leader pushes log entries to followers (AppendEntries RPC). KRaft: followers pull from the leader using the same Fetch protocol Kafka already uses for topic replication. This reuses existing Kafka network infrastructure.

**Quorum fetch timeout instead of election timeout:**
The follower initiates an election if it hasn't successfully fetched from the leader within `quorum.fetch.timeout.ms` (default 2,000ms). The election itself has a separate `quorum.election.timeout.ms` (default 1,000ms). The combined window is larger than typical Raft implementations (which use 150–300ms timeouts) — Kafka tolerates higher latency between controller nodes than typical Raft deployments.

**Metadata log compaction (snapshots):**
The metadata log grows indefinitely as metadata changes accumulate. KRaft periodically takes snapshots of the current metadata state and truncates the log before the snapshot point. New brokers or rejoining followers can load from the latest snapshot + delta rather than replaying the full log from genesis.

**No log fragmentation:**
Unlike topic partition logs (which are split into segments and can be independently compacted), the metadata log is a single continuous log per controller. It uses a different storage format (`MetadataRecordSerde`) than topic data.

## Section 3: Migration and Compatibility

**Q9. What is the migration path from ZooKeeper mode to KRaft mode?**
A: Kafka 3.x provides a migration path that allows rolling migration without downtime, introduced in KIP-833:

**Migration phases:**

**Phase 1 — Dual-write mode:**
- Deploy KRaft controller nodes alongside the existing ZooKeeper cluster.
- Configure `zookeeper.metadata.migration.enable=true` on brokers.
- The KRaft controller becomes active but also writes all metadata changes to ZooKeeper simultaneously (dual-write). Existing ZooKeeper-dependent tooling continues to work.
- The KRaft controller reads the existing ZooKeeper metadata to bootstrap its log.

**Phase 2 — Brokers migrate:**
- Brokers are rolling-restarted with KRaft configuration.
- Each migrated broker fetches metadata from the KRaft controller instead of ZooKeeper.
- Non-migrated brokers continue using ZooKeeper during the rolling restart.

**Phase 3 — ZooKeeper decommission:**
- Once all brokers are migrated, disable the ZooKeeper dual-write.
- Decommission ZooKeeper cluster.
- The migration is complete.

**Version requirements:**
- Kafka 2.8: KRaft available as early access (not production-ready).
- Kafka 3.3: KRaft declared production-ready for new clusters.
- Kafka 3.4–3.6: Migration tooling (KIP-833) progressively stabilized.
- Kafka 4.0: ZooKeeper mode removed entirely. KRaft is the only option.

**Q10. What changed for operators when moving from ZooKeeper mode to KRaft?**
A: Operational changes are significant:

**What goes away:**
- ZooKeeper cluster — no longer needed. Eliminates ZK installation, configuration, monitoring, backup, and version management.
- ZooKeeper-specific tooling: `zookeeper-shell.sh`, ZK ACL management commands.
- ZooKeeper connection strings in broker configuration (`zookeeper.connect` property removed).
- ZooKeeper-specific metrics and alerts.

**What changes:**
- **Cluster ID:** KRaft clusters have a cluster UUID generated at format time (`kafka-storage.sh format --cluster-id`). This must be done before starting any broker or controller.
- **Bootstrap:** Instead of `zookeeper.connect`, brokers specify `controller.quorum.voters` (the addresses of KRaft controller nodes) and `bootstrap.controllers`.
- **`kafka-metadata-shell.sh`:** New tool for inspecting the `__cluster_metadata` log — replaces `zookeeper-shell.sh` for metadata inspection.
- **`kafka-metadata-quorum.sh`:** New tool for checking quorum health, leader status, and lag.
- **Broker configuration split:** In isolated mode, dedicated controller nodes have a different `server.properties` from broker nodes (`process.roles=controller` vs `process.roles=broker`).

**What stays the same:**
- Topic management (`kafka-topics.sh`), consumer group management (`kafka-consumer-groups.sh`), producer/consumer APIs — all unchanged from the client perspective.
- Replication, partitioning, offset semantics, retention — all unchanged.
- The `__consumer_offsets` topic and consumer group coordinator — unchanged.

**Q11. What are the new configuration parameters introduced by KRaft?**
A: Key KRaft-specific configuration parameters:

```properties
# Identifies the role(s) of this node
# 'broker': data broker only
# 'controller': KRaft controller only (isolated mode)
# 'broker,controller': combined mode
process.roles=broker,controller

# Node ID — must be unique across all brokers AND controllers in the cluster
node.id=1

# The list of controller nodes forming the quorum
# Format: node_id@host:port
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093

# The listener used for inter-controller communication (Raft protocol)
controller.listener.names=CONTROLLER

# Listeners configuration (must include CONTROLLER for controller nodes)
listeners=PLAINTEXT://broker-1:9092,CONTROLLER://controller-1:9093

# Directory for the metadata log (separate from topic data logs)
metadata.log.dir=/var/kafka/metadata

# Snapshot interval — how often to take a metadata snapshot
# (compacts the metadata log, enables faster broker startup)
metadata.log.max.record.bytes.between.snapshots=20971520  # 20MB
```

**Q12. How do you verify KRaft quorum health in production?**
A: New operational commands for KRaft:

```bash
# Check quorum status — who is the leader, follower lag, voter list
kafka-metadata-quorum.sh --bootstrap-server broker-1:9092 describe --status

# Output example:
# ClusterId:              abc123
# LeaderId:               1
# LeaderEpoch:            42
# HighWatermark:          1,892,441
# MaxFollowerLag:         0
# MaxFollowerLagTimeMs:   -1  # -1 means caught up
# CurrentVoters:          [1,2,3]
# CurrentObservers:       [4,5,6]  # brokers that replicate but don't vote

# Inspect metadata log contents (like zookeeper-shell.sh but for KRaft)
kafka-metadata-shell.sh --snapshot /var/kafka/metadata/__cluster_metadata-0/

# Check broker registration in KRaft metadata
kafka-metadata-shell.sh --bootstrap-server broker-1:9092 ls /brokers

# Describe a specific topic's metadata record
kafka-metadata-shell.sh --bootstrap-server broker-1:9092 cat /topics/order-events
```

**Key metrics to monitor for KRaft quorum:**
- `kafka.controller:type=KafkaController,name=ActiveControllerCount` — should be exactly 1 across the cluster.
- `kafka.server:type=MetadataQuorum,name=CurrentLeader` — the current Raft leader node ID.
- `kafka.server:type=MetadataQuorum,name=CurrentEpoch` — Raft term. Monotonically increasing; rapid increase signals instability.
- `kafka.server:type=MetadataQuorum,name=ReplicationLag` — how far behind this node is from the leader. Should be near 0.
- `kafka.server:type=BrokerMetadataStats,name=MetadataApplyErrorCount` — errors applying metadata records. Non-zero is a serious signal.

## Section 4: Operational Characteristics

**Q13. What is the metadata snapshot in KRaft and why does it matter operationally?**
A: The `__cluster_metadata` log grows as long as the cluster exists — every topic creation, partition reassignment, broker registration, ISR change, and config update appends a record. Without compaction, the log would grow indefinitely and broker startup would require replaying the entire log history.

KRaft periodically takes a **metadata snapshot**: a point-in-time serialized image of the complete current cluster state. After a snapshot is taken, log records before the snapshot point can be deleted. New brokers or rejoining controllers load the latest snapshot and then apply only the delta records since the snapshot.

**Snapshot trigger:** A new snapshot is taken when the metadata log has grown by `metadata.log.max.record.bytes.between.snapshots` (default 20MB) since the last snapshot.

**Operational concerns:**
- If the snapshot takes too long (large cluster with many partitions), it can cause brief latency spikes on the active controller. Monitor snapshot duration.
- If a broker has been offline longer than the log retention since the last snapshot, it may need to load from a snapshot that no longer covers the records it needs — handled automatically but worth monitoring.
- Snapshot files are stored in the `metadata.log.dir` directory (`__cluster_metadata-0/` subdirectory). Monitor disk usage here separately from topic data.

**Q14. How does KRaft handle the case where all controllers fail simultaneously?**
A: If all KRaft controller nodes fail simultaneously (e.g., power failure to the controller rack), the cluster loses its metadata quorum:

- **Brokers continue serving existing traffic:** Brokers have their own in-memory copy of cluster metadata (synchronized from the metadata log). They can continue serving producer and consumer requests for existing partitions.
- **No new metadata changes:** Topic creation, partition reassignment, ACL changes, and broker registrations cannot proceed without a quorum.
- **Partition leader elections blocked:** If a broker fails while quorum is down, its partitions cannot elect new leaders — those partitions become unavailable until quorum is restored.
- **Recovery:** When controller nodes come back online, the Raft protocol elects a new leader from among the surviving quorum members. The cluster state is the Raft log — as long as a majority of controllers have their data directories intact, the cluster recovers with no data loss.

**This is fundamentally the same behavior as ZooKeeper mode** — losing ZK quorum also blocked Controller failover. The difference: with KRaft, the controllers are Kafka processes (same team manages them), not a separate ZooKeeper cluster (potentially a different team).

**Recommendation:** Deploy controllers in separate availability zones / racks to reduce simultaneous failure probability. With 3 controllers: 1 per AZ. With 5 controllers: spread across 3+ AZs.

**Q15. What is the "observer" concept in KRaft and how does it differ from a voter?**
A: In KRaft, nodes in the metadata quorum have two roles:

**Voters (controllers):** Participate in Raft elections. Can become the Raft leader (active controller). Their votes count toward quorum. Configured in `controller.quorum.voters`. Typically 3 or 5 nodes.

**Observers (brokers):** Replicate the metadata log from the active controller but do not vote in elections. Their acknowledgment is not required for a write to commit. All data brokers are observers — they receive metadata updates but don't participate in elections.

This design keeps the quorum small (3–5 voters) regardless of cluster size (hundreds of brokers). Adding more brokers doesn't increase the consensus overhead. The voters need to agree on every metadata change; if voters numbered in the hundreds, write latency would grow proportionally.

**In practice:** You configure 3 dedicated controller nodes as voters (`controller.quorum.voters`). All broker nodes are observers by default — they connect to the active controller and replicate the metadata log continuously. No explicit configuration needed to add a broker as an observer.

## Section 5: Trade-offs & Decision-Making

**Q16. What are the remaining limitations of KRaft mode?**
A: Despite being production-ready since Kafka 3.3, KRaft had some feature gaps in its early versions that narrowed over time:

**Early KRaft limitations (Kafka 3.3–3.5, now resolved in 3.6+/4.0):**
- JBOD (Just a Bunch of Disks) support for KRaft was added in Kafka 3.7.
- Some delegation token features required additional work.
- Certain advanced ACL features lagged ZooKeeper mode.

**Ongoing architectural considerations:**
- **Quorum size ceiling:** Kafka recommends a maximum of 5 voter nodes in the KRaft quorum. More voters means more round trips per metadata commit — increasing metadata write latency. This is the same trade-off as ZooKeeper ensemble sizing.
- **Metadata log disk:** The metadata log directory (`metadata.log.dir`) requires its own disk monitoring. Unlike topic data which has configurable retention, metadata log retention is managed by snapshots — operators must ensure snapshot frequency is adequate.
- **No external consumers of metadata:** In ZooKeeper mode, external tools could read cluster metadata directly from ZooKeeper using standard ZK clients. In KRaft mode, the `__cluster_metadata` log uses a proprietary binary format — only Kafka's own tooling (`kafka-metadata-shell.sh`) can read it directly.

**Q17. When would you still encounter ZooKeeper mode in practice (as of 2025–2026)?**
A: Despite Kafka 4.0 dropping ZooKeeper support entirely, you encounter ZooKeeper mode in:

- **Legacy clusters:** Enterprises that deployed Kafka clusters on Kafka 2.x or 3.x before KRaft was production-ready and haven't migrated yet. Large organizations with thousands of topics may be cautious about migration.
- **Managed services lagging:** Some managed Kafka services (MSK, Confluent Cloud, Aiven) may run on older Kafka versions for stability — customers inherit whatever mode the service version supports.
- **Ecosystem tooling:** Tools like Kafka Manager (CMAK), Kafka Cruise Control (older versions), and custom scripts that directly read ZooKeeper data break in KRaft mode without updates. Organizations dependent on these may delay migration.
- **Interview context:** ZooKeeper mode is still a valid interview topic because understanding *why* it was problematic is what motivates the KRaft design — and because many production clusters still run on it.

**Q18. How do you decide between combined mode and isolated mode for KRaft?**
A: The choice between running controllers and brokers on the same nodes (combined) vs. separate nodes (isolated):

**Combined mode:**
```
node-1: process.roles=broker,controller
node-2: process.roles=broker,controller
node-3: process.roles=broker,controller
node-4: process.roles=broker         ← pure broker, not in quorum
node-5: process.roles=broker
```
- Fewer total nodes. Lower infrastructure cost.
- Suitable for: development, staging, small production clusters (< 6 brokers), clusters where metadata operations are infrequent.
- Risk: a metadata-intensive operation (creating 10,000 partitions at once) competes for CPU and I/O with the broker's data replication. Under load, controller responsiveness can degrade.

**Isolated mode (recommended for production):**
```
controller-1: process.roles=controller   ← dedicated, no topic data
controller-2: process.roles=controller
controller-3: process.roles=controller
broker-1:     process.roles=broker
broker-2:     process.roles=broker
...
broker-N:     process.roles=broker
```
- Controllers have dedicated resources. Metadata operations never compete with data throughput.
- Smaller controller nodes are sufficient (controllers don't store topic data — just the metadata log, which is typically < 1GB even for large clusters).
- Required for: large clusters (> 6 brokers), high-throughput clusters, clusters with frequent administrative operations, or strict performance SLAs.
- The controller nodes can be much smaller than broker nodes (4 vCPUs, 16GB RAM is sufficient for most controller workloads).

## Section 6: Scenario / System Design Style Questions

**Q19. "Your Kafka cluster is running ZooKeeper mode with 500,000 partitions. Controller failover takes 4 minutes. What's happening and how does KRaft fix it?"**
A: The 4-minute failover is a classic ZooKeeper-mode scaling problem:

**What's happening:**
1. The Controller fails (crash, OOM, network partition from ZK).
2. ZooKeeper detects session expiry after `zookeeper.session.timeout.ms` (default 18,000ms = 18 seconds).
3. A new Controller is elected — typically fast (< 5 seconds).
4. **The bottleneck:** The new Controller must load all cluster state from ZooKeeper. With 500,000 partitions:
   - Each partition has replica assignment and ISR state stored as separate ZK znodes.
   - Reading 500,000+ znodes from ZooKeeper sequentially takes minutes.
   - The Controller must parse and build its full in-memory partition state before it can process any leadership changes.
5. During state loading, no partition leader elections can occur — any broker failure compounds the outage.

**Intermediate mitigation (ZooKeeper mode):**
- Reduce `zookeeper.session.timeout.ms` to detect failures faster (risk: false positives on GC pauses).
- Increase Controller heap to avoid GC pauses causing spurious session timeouts.
- Reduce `controller.socket.timeout.ms` and `controller.request.timeout.ms`.
- Spread partitions across more brokers so fewer partitions are affected per broker failure.

**KRaft fix:**
- With KRaft, standby controllers replicate the metadata log continuously — they always have the full current state.
- Failover = Raft election (2–5 seconds) + zero state load time.
- 500,000 partitions or 5,000,000 partitions — failover time is the same.
- The 4-minute outage becomes a 5-second blip.

**Q20. "You're setting up a new Kafka cluster from scratch in 2025. Walk through your KRaft configuration decisions."**
A: End-to-end KRaft cluster configuration walkthrough:

**Step 1 — Choose topology:**
- Production cluster with 6 data brokers and high availability requirement.
- Use isolated mode: 3 dedicated controller nodes + 6 broker nodes.
- Deploy controllers across 3 AZs (1 per AZ).

**Step 2 — Generate cluster ID:**
```bash
kafka-storage.sh random-uuid
# Output: abc123XYZdef456
```

**Step 3 — Format storage on all nodes:**
```bash
# On each controller node and broker node
kafka-storage.sh format \
  --cluster-id abc123XYZdef456 \
  --config /etc/kafka/server.properties
```

**Step 4 — Controller node configuration (`controller-1/server.properties`):**
```properties
process.roles=controller
node.id=1
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
listeners=CONTROLLER://controller-1:9093
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
log.dirs=/var/kafka/metadata
# Controllers don't need large heaps — metadata log is small
# JVM: -Xmx4g -Xms4g
```

**Step 5 — Broker node configuration (`broker-1/server.properties`):**
```properties
process.roles=broker
node.id=4    # node IDs 1-3 are controllers; brokers start at 4
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093
listeners=PLAINTEXT://broker-1:9092
inter.broker.listener.name=PLAINTEXT
controller.listener.names=CONTROLLER
log.dirs=/var/kafka/data-1,/var/kafka/data-2    # JBOD multiple disks
# Default replication factor for auto-created topics
default.replication.factor=3
min.insync.replicas=2
# JVM: -Xmx8g -Xms8g (leave RAM for OS page cache)
```

**Step 6 — Start order:**
1. Start all controller nodes first (quorum must be established before brokers can register).
2. Start broker nodes (they connect to controllers and register via BrokerRegistrationRequest).

**Step 7 — Verify:**
```bash
kafka-metadata-quorum.sh --bootstrap-server broker-1:9092 describe --status
# Expect: LeaderId=1, MaxFollowerLag=0

kafka-topics.sh --bootstrap-server broker-1:9092 --list
# Should show empty topic list (new cluster)
```

**Q21. "A junior engineer on your team asks: 'If KRaft is so much better, why did it take Kafka until 2022 to be production-ready?' How do you answer?"**
A: A layered answer covering technical and organizational complexity:

**Technical depth of the dependency:** ZooKeeper wasn't just a feature in Kafka — it was the foundation for all correctness guarantees. Every assumption about cluster state (who is the controller, which replica is the leader, what is the current ISR) flowed through ZooKeeper. Replacing it meant redesigning the consistency model from the ground up without breaking the existing guarantees.

**Raft in a log-structured system:** General Raft is well-understood, but adapting it to Kafka's specific metadata model — where the log itself is the state, where snapshots must be taken efficiently, where thousands of partition states change per second — required significant design work beyond "implement Raft."

**Backward compatibility requirement:** Kafka could not break existing deployments. The migration path had to allow existing clusters to migrate without data loss and without forced downtime. Designing, implementing, and testing a migration path across ZooKeeper mode and KRaft mode for arbitrary cluster sizes was a multi-year effort.

**Ecosystem breadth:** Kafka is used by thousands of organizations with diverse tooling (Cruise Control, CMAK, custom monitoring, cloud provider integrations). All of these had to be updated or at least assessed before KRaft could be declared production-ready.

**Testing at scale:** The Kafka community needed to test KRaft at real-world scale — hundreds of brokers, millions of partitions, multi-year uptime — before declaring it production-ready. This required running it in production environments gradually, gathering data, and fixing edge cases. Apache Kafka's correctness bar is high; shipping early would have eroded trust.

**Q22. "How would you explain the difference between ZooKeeper mode and KRaft mode to a backend engineer who uses Kafka but doesn't manage it?"**
A: Frame it in terms they care about — reliability, simplicity, and future capabilities:

"Think of ZooKeeper like a city government for Kafka — a completely separate organization that handles all the administrative decisions: who's the boss, what the rules are, where everything is stored. Kafka had to call City Hall every time something changed, and if City Hall went down or was slow, Kafka got stuck waiting.

KRaft is like Kafka hiring its own in-house administration team. Same decisions get made, but now it's all within Kafka itself — no external dependency, faster communication, and the in-house team is always up-to-date because they're in the same building.

What this means for you practically: clusters are simpler to run (one system, not two), failover when a broker dies goes from sometimes-minutes to always-seconds, and future Kafka versions can support millions of partitions in one cluster instead of hitting a ceiling at a few hundred thousand. If you're running a managed Kafka service, your provider is probably already running KRaft under the hood, and you won't see a difference from the outside — you'll just notice your cluster is more stable."

## Quick Reference: ZooKeeper Mode vs KRaft Mode Comparison

| Aspect | ZooKeeper Mode | KRaft Mode |
|---|---|---|
| External dependency | ZooKeeper cluster required | None — self-contained |
| Metadata storage | ZooKeeper znodes | `__cluster_metadata` Kafka log |
| Controller election | ZooKeeper leader election (/controller znode) | Raft election among quorum voters |
| Controller failover time | 30 seconds to minutes (O(partitions) state load) | 2–5 seconds (state pre-loaded on standby) |
| Broker startup time | Slow for large clusters (reads all ZK metadata) | Fast — snapshot load, then delta |
| Partition ceiling | ~200,000 (ZK memory/performance limit) | Millions (log-based, not ZK in-memory) |
| Operational systems | Kafka + ZooKeeper (two systems) | Kafka only |
| Metadata inspection | `zookeeper-shell.sh` | `kafka-metadata-shell.sh` |
| Quorum health check | ZooKeeper `ruok` / `mntr` commands | `kafka-metadata-quorum.sh describe` |
| Available since | Kafka 0.x (original design) | Production-ready: Kafka 3.3 |
| Required since | N/A | Kafka 4.0 (ZK mode removed) |
| Migration path | N/A (it is the old mode) | KIP-833 rolling migration from ZK mode |
| Deployment modes | N/A | Combined (broker+controller) or Isolated |
| Observer concept | All brokers read ZK | Brokers replicate metadata log (pull model) |
| Snapshot mechanism | No (full ZK read on Controller restart) | Yes — periodic metadata snapshots |

**Tip for the interview:** ZooKeeper vs KRaft questions test whether you understand distributed systems trade-offs beyond surface-level "KRaft is newer and better." The depth markers: (1) explaining *why* ZooKeeper mode had a partition count ceiling — ZooKeeper's in-memory model required O(partitions) reads on Controller failover and broker startup, not just "ZK was slow"; (2) explaining the standby controller pre-load insight — KRaft's failover is fast not because Raft is faster than ZAB, but because standby controllers continuously replicate metadata and are always current; (3) the observer vs voter distinction — Kafka clusters can have hundreds of brokers without those brokers being Raft voters, keeping consensus overhead constant regardless of cluster size. If asked about migration, mention Kafka 4.0 dropping ZooKeeper entirely and the KIP-833 rolling migration path — it shows you're current on the ecosystem.
