# Consumer Offsets: Auto-Commit vs Manual Commit, At-Least-Once vs Exactly-Once — Interview Q&A (5 YOE Level)

---

## Section 1: Foundations

**Q1. What is a consumer offset in Kafka, and why does it exist?**
A: A consumer offset is a pointer — a numeric position within a Kafka partition — that records how far a consumer has read. Specifically, it is the offset of the next message a consumer should read from a given partition. Kafka stores offsets in an internal compacted topic called `__consumer_offsets`, keyed by `(group_id, topic, partition)`.

Offsets exist because Kafka is a durable, replayable log — unlike a traditional message queue that deletes a message after delivery, Kafka retains messages regardless of whether they've been consumed. The offset is the consumer's bookmark in that log. Without it, every consumer restart would either re-read from the beginning (wasteful) or have no way to resume from where it left off. The offset decouples consumption state from the log itself: different consumer groups can read the same topic at different positions simultaneously, and a consumer that crashes can resume exactly where it left off by reading its last committed offset.

**Q2. What is the difference between the "current offset" and the "committed offset," and why does the gap between them matter?**
A: These are two distinct positions that exist simultaneously in a consumer:

- **Current offset** — the offset of the message the consumer has most recently fetched and is either processing or about to process. It advances every time `poll()` returns a new batch of messages. It lives in the consumer's memory.
- **Committed offset** — the offset the consumer has explicitly told Kafka it has successfully processed. It is persisted in `__consumer_offsets`. On crash and restart, the consumer resumes from the committed offset, not the current offset.

The gap between them is the set of messages that have been fetched but not yet committed. This gap is the source of almost every delivery guarantee problem:

- **Gap = 0** — the consumer commits immediately on fetch, before processing. A crash after committing but before processing loses those messages. This is **at-most-once** delivery.
- **Gap > 0** — the consumer commits after processing. A crash in the gap causes those messages to be re-fetched and reprocessed on restart. This is **at-least-once** delivery.
- **Gap managed atomically** — the commit is made transactionally alongside the processing output. The gap never produces either lost or duplicated processing. This is **exactly-once** processing.

Understanding this gap is the foundation of every offset management decision.

**Q3. What are the three delivery semantics, precisely defined?**
A: The three delivery semantics describe what guarantees a messaging system makes about message processing in the presence of failures:

- **At-most-once** — every message is processed zero or one times. Messages may be lost but are never processed more than once. Achieved by committing offsets before processing. The consumer reads message M, commits M's offset, then processes M. If it crashes during processing, M was already committed and will not be redelivered. Safe for: fire-and-forget notifications, metrics sampling, log aggregation where a missing event is acceptable.

- **At-least-once** — every message is processed one or more times. No messages are lost, but a message may be processed multiple times if the consumer crashes after processing but before committing. Achieved by committing offsets after processing. The consumer reads M, processes M, commits M's offset. If it crashes between processing and committing, M is redelivered on restart. Safe for: any use case where processing is idempotent (processing twice has the same effect as processing once).

- **Exactly-once** — every message is processed exactly one time. No losses, no duplicates. Achieved through a combination of transactional producers, idempotent consumers, and atomic offset commits. More expensive than at-least-once; requires specific Kafka configuration and application-level discipline. Safe for: financial transactions, inventory updates, any case where duplicate processing has material business impact.

The important distinction: these semantics describe *processing* guarantees, not *delivery* guarantees. Kafka itself can deliver a message multiple times at the transport level — exactly-once *processing* is what the application achieves by combining Kafka's features with correct application design.

## Section 2: Auto-Commit

**Q4. How does auto-commit work in Kafka, and what are its default settings?**
A: Auto-commit is controlled by two consumer configurations:

- `enable.auto.commit = true` (default) — Kafka's consumer client automatically commits the current offset periodically without explicit application code.
- `auto.commit.interval.ms = 5000` (default) — the commit happens every 5 seconds (measured from the last commit, on the next `poll()` call after the interval has elapsed).

The commit is triggered inside `poll()`: when the consumer calls `poll()`, the client checks whether the commit interval has elapsed since the last commit. If yes, it commits the current offset of all assigned partitions before returning new messages. The commit itself is asynchronous — it does not block `poll()`. It is effectively a background operation piggybacked onto the polling loop.

The committed offset under auto-commit is the offset of the last message returned by the *previous* `poll()` call — not the last message the application has processed. The Kafka client has no knowledge of what the application has done with the messages; it commits based on what was fetched, not what was processed.

**Q5. What are the failure scenarios under auto-commit, and what delivery guarantee does it provide?**
A: Auto-commit provides **at-least-once delivery** in most cases, but can slide toward **at-most-once** depending on crash timing. The failure scenarios:

**Scenario 1 — Crash between poll() calls, before the 5-second interval:**
1. Consumer fetches batch B1 (messages 0–99). Auto-commit has not fired yet (last commit was at message 0).
2. Consumer processes messages 0–99 successfully.
3. Consumer calls `poll()` again, fetching batch B2. The 5-second interval fires; Kafka commits offset 100 (end of B1) as a side effect of this `poll()`.
4. Consumer crashes while processing B2 at message 150.
5. On restart: consumer resumes from offset 100. Messages 0–99 were processed and committed — no re-processing. Messages 100–150 are re-processed. **At-least-once.**

**Scenario 2 — Crash during processing, within the 5-second window:**
1. Consumer fetches batch B1 (messages 0–99). Last commit was at offset 0. Interval has not elapsed.
2. Consumer processes messages 0–50.
3. Consumer crashes.
4. On restart: consumer resumes from offset 0 (last committed). Messages 0–50 are re-processed. **At-least-once** (duplicates for 0–50).

**Scenario 3 — Crash after auto-commit fires but before processing completes (the at-most-once window):**
1. Consumer fetches batch B1 (messages 0–99). Interval fires: Kafka auto-commits offset 100.
2. Consumer begins processing messages 0–99.
3. Consumer crashes at message 50.
4. On restart: consumer resumes from offset 100. Messages 50–99 are **never processed**. **At-most-once** (data loss).

This third scenario is the dangerous one for auto-commit: if the commit fires mid-batch (because the interval elapsed while the previous batch was still being processed), the consumer commits messages it hasn't yet processed. Auto-commit is only "safe" if processing is faster than the commit interval, which is not a guarantee.

**Q6. When is auto-commit acceptable, and when is it dangerous?**
A: Auto-commit is acceptable when:
- Message loss is tolerable (metrics, logs, analytics sampling).
- Processing is significantly faster than the commit interval, making the at-most-once window vanishingly small in practice.
- The consumer is stateless and processing is cheap enough that re-processing a batch on restart is not a concern.
- The application is using Kafka as a fire-and-forget notification bus, not as a durable event store.

Auto-commit is dangerous when:
- Processing has side effects that must not be executed twice (charging a payment, sending an email, updating a database record without idempotency protection).
- Processing is slow (fetching a batch, processing each message by calling a downstream API, and the 5-second interval fires mid-batch).
- The application needs to know exactly which messages have been durably processed for accurate monitoring and alerting.
- The consumer processes messages in multiple threads (the commit may fire while some threads are still processing messages from a prior batch, creating an at-most-once window).

The rule of thumb: auto-commit is an operational convenience for non-critical consumers. For any consumer where message loss or duplication has a business impact, use manual commit.

## Section 3: Manual Commit

**Q7. What are the two forms of manual commit in Kafka, and when do you use each?**
A: Manual commit is enabled by setting `enable.auto.commit = false`. The application then explicitly calls one of two commit APIs:

**Synchronous commit (`commitSync()`):**
Blocks the consumer thread until the broker acknowledges the commit. If the commit fails (network error, coordinator unavailability), it retries until success or throws an exception. The consumer does not poll for new messages until the commit completes.

When to use: when you need guaranteed durability of the commit before proceeding — the commit is the checkpoint that defines "I have safely processed everything up to this offset." After processing a critical batch (database writes, payment processing), you want to know the checkpoint is durable before consuming more messages. The downside: adds latency equal to the broker round-trip time per commit, reducing throughput.

**Asynchronous commit (`commitAsync()`):**
Fires the commit request and immediately returns. The consumer continues polling for new messages. A callback is invoked when the commit completes (success or failure). On failure, the default behavior is to not retry (because a later commit may have already superseded the failed commit — retrying the stale commit could roll back the offset).

When to use: during normal operation in the processing loop when throughput is important and the occasional commit failure is acceptable (a subsequent commit will catch up). The standard pattern: use `commitAsync()` in the main processing loop (high throughput) and `commitSync()` in the finally block on consumer close (ensures the last batch is committed before shutdown).

```java
try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
        for (ConsumerRecord<String, String> record : records) {
            process(record);  // your business logic
        }
        consumer.commitAsync();  // non-blocking, high throughput
    }
} finally {
    try {
        consumer.commitSync();  // block on final commit before closing
    } finally {
        consumer.close();
    }
}
```

**Q8. What is per-message commit vs per-batch commit, and what are the trade-offs?**
A: After processing each message, you can commit that message's offset individually (per-message commit) or commit once after processing the entire batch returned by `poll()` (per-batch commit):

**Per-message commit:**
```java
for (ConsumerRecord<String, String> record : records) {
    process(record);
    consumer.commitSync(Collections.singletonMap(
        new TopicPartition(record.topic(), record.partition()),
        new OffsetAndMetadata(record.offset() + 1)
    ));
}
```
Advantage: if the consumer crashes mid-batch, only the messages after the last committed offset are reprocessed — not the entire batch. Reduces the duplicate-processing window to a single message.
Disadvantage: a network round-trip per message. At 100 messages/batch, this is 100× more broker round-trips than a per-batch commit. Throughput drops dramatically for high-volume consumers.

**Per-batch commit:**
```java
for (ConsumerRecord<String, String> record : records) {
    process(record);
}
consumer.commitSync();  // commit entire batch at once
```
Advantage: one network round-trip per batch, regardless of batch size. Much higher throughput.
Disadvantage: if the consumer crashes mid-batch, the entire batch is reprocessed from the first message — even messages already successfully processed.

The right choice depends on processing cost and idempotency. If processing each message is idempotent and cheap, per-batch commit is correct — the re-processing cost of a crash is low. If each message triggers a non-idempotent side effect (an API call, a database write without deduplication), per-message commit limits the duplicate-processing blast radius.

**Q9. What is "commit offset N+1, not N" — why do you commit offset+1 rather than the processed offset?**
A: Kafka's offset semantics define the committed offset as the offset of the *next message to be consumed* — not the offset of the last message consumed. So after processing message at offset N, you commit offset N+1.

This is a subtle but important distinction. If you commit offset N, Kafka interprets this as "start consuming from N" on the next poll — which means message N would be re-consumed. The correct semantics: "I have processed everything up to and including N; start me at N+1 next time."

In the Kafka consumer API:
```java
// Correct: commit the offset of the NEXT message to consume
consumer.commitSync(Collections.singletonMap(
    new TopicPartition(record.topic(), record.partition()),
    new OffsetAndMetadata(record.offset() + 1)  // N+1
));
```

This is one of the most common off-by-one bugs in Kafka consumer code — committing `record.offset()` instead of `record.offset() + 1`, causing the last processed message to be re-consumed on every restart.

**Q10. What is "commit on shutdown" and why does it require special handling?**
A: When a consumer shuts down (intentional restart, deployment, scaling event), it should commit its current offset before closing so the next consumer instance doesn't reprocess already-processed messages. This is the "commit on shutdown" pattern and requires special handling because:

- **`commitAsync()` may not complete before close** — asynchronous commits are fire-and-forget. If the consumer closes before the async commit's response arrives, the commit may be lost. The finally-block `commitSync()` pattern (Q7) addresses this.
- **`close()` itself commits** — `KafkaConsumer.close()` with a timeout will attempt to commit offsets before closing if auto-commit is enabled. With manual commit, close does not automatically commit — the application must call `commitSync()` explicitly.
- **Rebalance on shutdown** — when a consumer leaves a group (gracefully or by timeout), a rebalance is triggered. During a rebalance, partitions are reassigned. If the leaving consumer hasn't committed its in-progress offsets before the rebalance completes, the new consumer for those partitions starts from the last committed position — re-processing any messages the old consumer processed but didn't commit.
- **`ShutdownHook` race condition** — adding a JVM shutdown hook that calls `commitSync()` can race with the consumer's normal processing loop. The shutdown hook and the processing loop may both try to use the consumer simultaneously. The correct pattern: set a volatile boolean `running = false` in the shutdown hook; the processing loop exits on the next iteration; the finally block commits. Single-threaded consumer usage avoids concurrent access.

## Section 4: At-Least-Once in Depth

**Q11. What does "at-least-once" require from the application, and what does it not guarantee?**
A: At-least-once delivery requires:
- **Commit after processing** — only commit the offset after the processing of a message has been durably completed (the result is written to the database, the API call succeeded, the downstream event was published).
- **Never commit before processing** — the defining rule. Committing before the side effect is complete creates an at-most-once window.

What at-least-once does NOT guarantee:
- **Idempotent processing** — at-least-once means the same message will be processed more than once after a crash. If the processing side effect is not idempotent (inserting a row without a unique constraint, charging a payment without deduplication), duplicates will corrupt the output. At-least-once is only safe when combined with idempotent processing.
- **Ordered processing** — at-least-once says nothing about the order in which messages are processed after a crash. If a consumer reprocesses messages 5–10 and they interleave with new messages 11–15, the output order may differ from the input order. Ordering within a partition is preserved (Kafka guarantees within-partition order), but reprocessing creates a local re-ordering relative to what downstream systems received before the crash.
- **Exactly-once output** — at-least-once delivery from Kafka combined with a non-idempotent write to a database gives at-least-once database writes — which means duplicate rows, double credits, and double-sent emails.

**Q12. How do you implement idempotent processing on top of at-least-once delivery?**
A: Idempotent processing means that processing the same message twice produces the same result as processing it once. Implementation strategies:

**Database-level deduplication (upsert / unique constraint):**
Use the Kafka message's offset (or a business key in the message payload) as a unique constraint in the target database. A reprocessed message tries to insert a duplicate, hits the constraint, and is discarded (or updates the existing row to the same value via `INSERT ... ON CONFLICT DO NOTHING`).

```sql
INSERT INTO processed_events (event_id, data, processed_at)
VALUES ($event_id, $data, now())
ON CONFLICT (event_id) DO NOTHING;
```

The event_id is derived from the Kafka partition + offset (globally unique) or a business-level ID in the message payload. This approach is robust: the database enforces deduplication regardless of how many times the consumer reprocesses the message.

**Idempotency keys on external API calls:**
When the processing step calls an external API (payment gateway, email service), include an idempotency key in the request — typically derived from the Kafka offset. The external service deduplicates on the idempotency key. The first call succeeds; subsequent calls with the same key return the original response without re-executing the operation.

**Check-then-act with status tracking:**
Before processing a message, check whether it has already been processed:
```python
if not already_processed(event_id):
    process(event)
    mark_as_processed(event_id)
```
Weakness: the check-then-act is a race condition if multiple consumer instances run concurrently on the same partition (which Kafka prevents by design — only one consumer per partition per group). Within a single consumer, this is safe as long as `already_processed` and `mark_as_processed` are atomic (a single SQL transaction or a Redis `SET NX`).

**Idempotent state machine transitions:**
For stateful processing, model the output as a state machine where applying the same transition twice is a no-op:
```sql
UPDATE orders SET status = 'SHIPPED'
WHERE order_id = $id AND status = 'CONFIRMED';
-- If already SHIPPED, the WHERE clause matches 0 rows — safe no-op
```
The condition `AND status = 'CONFIRMED'` prevents the transition from being applied twice. If the consumer reprocesses the "order shipped" event, the update matches no rows and has no effect.

## Section 5: Exactly-Once Semantics

**Q13. What does "exactly-once" mean in Kafka, and what are the two distinct components?**
A: Exactly-once in Kafka is a compound guarantee that requires two distinct components working together:

**Component 1 — Idempotent producer (exactly-once delivery to Kafka):**
The producer may retry sends due to network failures, creating duplicate messages in the topic. The idempotent producer (enabled by `enable.idempotence=true`) assigns each message a sequence number and a producer ID. The Kafka broker deduplicates: if it receives two messages from the same producer with the same sequence number, it accepts the first and discards the second — regardless of retries. This eliminates producer-side duplicates, achieving exactly-once delivery of messages *into* Kafka.

**Component 2 — Transactional API (exactly-once processing and output):**
The consumer processing step must also be exactly-once — reading from topic A, processing, and writing to topic B (or committing offsets) must be atomic. Kafka's transactional API allows a producer to: begin a transaction, produce output messages to one or more topics AND commit the consumer's offset — all atomically. Either all outputs and the offset commit are applied, or none are. This is the "consume-transform-produce" (CTP) loop executed exactly once.

Together: idempotent producer prevents duplicate input messages; transactional CTP loop ensures each input message produces exactly one output and exactly one offset commit. The combination gives end-to-end exactly-once processing.

**Q14. How does Kafka's transactional API work mechanically?**
A: The transactional API introduces a transaction coordinator (a Kafka broker responsible for a `transactional.id`-keyed partition of the `__transaction_state` internal topic) and a two-phase protocol:

**Setup (once per producer):**
```java
producer.initTransactions();  // registers transactional.id with the coordinator
```

**Per-message-batch cycle:**
```java
producer.beginTransaction();
try {
    // 1. Produce output records
    producer.send(new ProducerRecord<>("output-topic", key, value));

    // 2. Commit the consumer's offset AS PART OF THE TRANSACTION
    //    (not via consumer.commitSync() — that would be outside the transaction)
    producer.sendOffsetsToTransaction(
        currentOffsets,   // Map<TopicPartition, OffsetAndMetadata>
        consumerGroupMetadata  // ties the offset commit to this consumer group
    );

    // 3. Commit the transaction atomically
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();  // rolls back both output and offset commit
}
```

**What the transaction coordinator does:**
1. On `beginTransaction()`: records the transaction start in `__transaction_state`.
2. On `send()` and `sendOffsetsToTransaction()`: tracks which partitions are involved in this transaction.
3. On `commitTransaction()`: writes a PREPARE record, sends COMMIT markers to all involved partitions, writes a COMMIT record. The output messages become visible to consumers only after COMMIT markers arrive.
4. On `abortTransaction()`: writes ABORT markers to all involved partitions; output messages are never visible to consumers.

The atomicity guarantee: a consumer reading the output topic will either see all messages from a transaction (after the COMMIT marker) or none (ABORT marker or incomplete transaction). It never sees partial output.

**Q15. What is `isolation.level` on the consumer, and why does it matter for exactly-once?**
A: `isolation.level` controls whether a Kafka consumer reads messages that are part of an uncommitted transaction:

- **`read_uncommitted` (default)** — the consumer reads all messages, including those written by an in-progress (not yet committed or aborted) transaction. If a transaction is later aborted, the consumer will have read "dirty" messages — messages that the producer considered part of a rolled-back transaction. This gives lower end-to-end latency but can expose consumers to transactional messages that shouldn't have been visible.
- **`read_committed`** — the consumer only reads messages that are part of committed transactions (or messages produced by non-transactional producers). It waits for transaction markers (COMMIT or ABORT) before exposing transactional messages to the application. This is required for exactly-once consuming of transactionally-produced output.

The `Last Stable Offset (LSO)`: under `read_committed`, the consumer can only read up to the LSO — the offset just before the earliest in-flight (uncommitted) transaction. If a transaction is open for a long time (a slow or stuck producer), the LSO doesn't advance, and consumers are blocked from reading newer non-transactional messages in the same partition — a form of "head-of-line blocking." This is a performance concern for high-throughput pipelines where transactions are held open for extended periods.

**Q16. What is the "zombie fencing" problem, and how does `transactional.id` solve it?**
A: The zombie fencing problem arises when an old producer instance — one that has been decommissioned, scaled down, or replaced — continues to produce messages to Kafka after a new instance has taken over. Both instances have the same logical identity (they handle the same partition assignment), but only the new one should be authoritative.

Without fencing: the old producer (the "zombie") might have an in-flight transaction. The new producer starts a new transaction. Both write to the same output partitions. The old transaction's COMMIT arrives after the new transaction has already produced output — the output partition now has duplicate or interleaved data from two transactions that were supposed to be sequential.

How `transactional.id` solves this: every producer that uses the transactional API must be configured with a unique `transactional.id`. When a new producer instance calls `initTransactions()` with a given `transactional.id`, the transaction coordinator increments the producer epoch for that ID. Any subsequent messages from the old producer with a lower epoch are rejected by the broker with a `ProducerFencedException`. The old producer is "fenced" — its messages are rejected even if it keeps trying.

The practical requirement: `transactional.id` must be stable and unique per logical producer identity. In a consumer-transform-producer pipeline where each consumer instance handles a set of partitions, the `transactional.id` is typically derived from the partition assignment (e.g., `"my-app-" + partition_id`). When partitions are reassigned (rebalance), the new consumer instance uses the same `transactional.id` for those partitions, fencing the old instance.

**Q17. What is the end-to-end overhead of exactly-once, and when is it not worth it?**
A: Exactly-once has measurable overhead compared to at-least-once:

- **Additional broker round-trips** — each transaction requires: `initTransactions()` (once), `beginTransaction()` (local), `sendOffsetsToTransaction()` (one RPC to transaction coordinator), `commitTransaction()` (two-phase: PREPARE + COMMIT markers to all involved partitions). Roughly 2–4 additional network RTTs per batch compared to at-least-once.
- **Transaction coordinator bottleneck** — all transactions for the same `transactional.id` go through one coordinator broker. Under high transaction rates, the coordinator partition can become a hotspot. Mitigated by using many distinct `transactional.id`s (one per partition assignment) to spread load.
- **`read_committed` consumer head-of-line blocking** — slow transactions can block the LSO and stall downstream consumers. At-least-once consumers with `read_uncommitted` don't have this problem.
- **Latency per transaction** — the minimum end-to-end latency for a single message through an exactly-once pipeline is higher than at-least-once because of the two-phase commit overhead.
- **Throughput reduction** — benchmarks show exactly-once throughput is roughly 20–40% lower than at-least-once at high message rates, depending on batch size, transaction frequency, and hardware.

When exactly-once is not worth it:
- The processing is genuinely idempotent — exactly-once semantics are redundant if a duplicate has no effect. Don't pay the overhead for idempotent writes that at-least-once handles correctly.
- Latency is more important than precision — high-frequency metrics pipelines, click-stream analytics, A/B test event collection. A duplicate event in 0.01% of cases has no material impact on aggregate analytics.
- The output is ephemeral — if the consumer writes to a cache that is rebuilt nightly, duplicates during the rebuild window are invisible.
- The downstream system has its own deduplication — if the target database enforces unique constraints, at-least-once delivery + database-level deduplication is simpler and faster than exactly-once Kafka transactions.

## Section 6: Rebalancing and Offset Management

**Q18. What is a consumer group rebalance, and how does it interact with offset management?**
A: A rebalance is the process by which Kafka redistributes partition assignments among the consumers in a group. It is triggered by: a consumer joining the group (new instance started), a consumer leaving the group (crash, shutdown, or session timeout), a partition count change on the topic, or a subscription change.

During a rebalance, all consumers in the group stop consuming ("stop-the-world rebalance" in the classic protocol) and reassign partitions. The interaction with offset management:

- **Uncommitted offsets are lost on rebalance** — if a consumer has processed messages but not yet committed their offsets, and a rebalance reassigns those partitions to another consumer, the new consumer starts from the last committed offset — re-processing the uncommitted messages. This is an at-least-once reprocessing event triggered by partition reassignment, not by a crash.
- **Committing before rebalance** — the `ConsumerRebalanceListener.onPartitionsRevoked()` callback fires before partitions are reassigned. This is the correct place to commit offsets for the partitions being revoked:
```java
consumer.subscribe(topics, new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // Commit offsets for partitions being taken away
        consumer.commitSync(currentOffsets);
    }
    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // Reset local state for newly assigned partitions
        currentOffsets.clear();
    }
});
```
Without this callback, every rebalance causes re-processing of the uncommitted window — a silent correctness hazard that only manifests under load when frequent rebalances occur (e.g., during deployments).

**Q19. What is the "session timeout" and "heartbeat interval" in the context of offset commits, and how do they create a failure detection trade-off?**
A: Kafka's consumer group coordinator detects consumer failures through a heartbeat mechanism:

- **`heartbeat.interval.ms` (default 3000ms)** — how frequently the consumer sends a heartbeat to the group coordinator. Heartbeats are sent in a background thread, independent of `poll()`. They signal "I am alive and processing."
- **`session.timeout.ms` (default 45000ms)** — the coordinator declares a consumer dead if it doesn't receive a heartbeat within this window. On expiry, a rebalance is triggered to reassign the dead consumer's partitions.
- **`max.poll.interval.ms` (default 300000ms = 5 minutes)** — if the consumer doesn't call `poll()` within this interval, the coordinator considers it stuck (even if heartbeats are still coming). The consumer is removed from the group and a rebalance is triggered.

The failure detection trade-off for offset management:

- **Short session timeout** — fast detection of crashed consumers; partitions are reassigned quickly; uncommitted offsets in the crash window are small. But: a consumer that is slow processing a large batch (legitimate work, not a crash) may be incorrectly declared dead. A false-positive crash detection causes a rebalance, which causes the slow consumer to lose its partition assignment mid-batch, and the new consumer reprocesses from the last committed offset. This interplay is why `max.poll.interval.ms` was introduced — it gives the consumer time to process a batch without being declared dead, while the heartbeat thread keeps the session alive.
- **Long session timeout** — tolerates slow consumers; fewer spurious rebalances. But: a genuinely crashed consumer holds its partition assignment for up to `session.timeout.ms` before detection. During this window, those partitions produce no messages to downstream — silent data lag, not an error. The longer the timeout, the longer the lag window before recovery.

The practical tuning: set `session.timeout.ms` to 3–4× `heartbeat.interval.ms` (giving multiple missed heartbeats before declaring death). Set `max.poll.interval.ms` to the maximum realistic time your application spends processing a single poll batch — if processing each batch takes up to 30 seconds, set `max.poll.interval.ms` to 60 seconds with a safety margin.

**Q20. What is the "cooperative rebalance" (incremental rebalance) protocol, and how does it improve offset management?**
A: The classic Kafka rebalance protocol ("eager rebalance") requires all consumers to revoke all their partition assignments at the start of a rebalance, even if they'll be reassigned the same partitions at the end. This creates a full stop-the-world: all consumers stop consuming during rebalance, which can last seconds to tens of seconds for large consumer groups.

Cooperative rebalance (introduced in Kafka 2.4 via the `CooperativeStickyAssignor`) changes this:

1. **Round 1** — the coordinator identifies which partitions need to move (new or changed assignments). Only the consumers losing partitions are told to revoke those specific partitions. Consumers keeping their partitions continue consuming without interruption.
2. **Round 2** — the revoked partitions are assigned to new consumers. Only the newly assigned consumers pause to join the assignment. Existing consumers with stable assignments are unaffected throughout.

Impact on offset management:
- Only consumers receiving revoked partitions need to commit offsets in `onPartitionsRevoked()`. Consumers with stable assignments continue processing — no pause, no uncommitted-offset window.
- Rebalance duration and consumer disruption are proportional to the *number of partitions moving*, not the total number of partitions. A consumer group with 1,000 partitions where 10 are being reassigned experiences near-zero disruption.
- The "stop-the-world" re-processing risk (uncommitted offsets during a full rebalance) is effectively eliminated for stable assignments.

This is why configuring `partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor` is a best practice for production consumer groups with more than a few consumers.

## Section 7: Offset Storage and Reset

**Q21. Where are consumer offsets stored, and what happens if `__consumer_offsets` is unavailable?**
A: Consumer offsets are stored in Kafka's own internal topic: `__consumer_offsets`. This is a compacted topic (keeps only the latest offset per `(group_id, topic, partition)` key) with a default replication factor of 3. The partition within `__consumer_offsets` that stores a group's offsets is determined by a hash of the group ID.

If `__consumer_offsets` is unavailable (the brokers hosting its replicas are all down):
- Consumers that already have their offsets loaded in memory can continue consuming. The offsets are already known from the last successful fetch.
- `commitSync()` and `commitAsync()` will fail with exceptions. The consumer's in-memory offset continues to advance, but committed position does not persist.
- On consumer restart, the consumer tries to fetch its committed offset from `__consumer_offsets`. If it's still unavailable, it falls back to the `auto.offset.reset` policy.
- A consumer trying to join a group (new consumer, post-rebalance) cannot get its offset assignment from the coordinator and will block or fail.

In practice, `__consumer_offsets` being unavailable is as severe as the Kafka brokers themselves being down for that group. The topic's high replication factor (3) and the fact that it's a compacted topic (fast to recover after compaction) means this is rare but not impossible during multi-broker failures.

**Q22. What is `auto.offset.reset`, and what are the trade-offs between `earliest` and `latest`?**
A: `auto.offset.reset` determines where a consumer starts reading when no committed offset exists for its group — typically a new consumer group or a consumer group whose offsets have been deleted or expired:

- **`earliest`** — start reading from the beginning of the topic (the earliest available message). The consumer processes all historical messages before catching up to the current tail. Use when: you need to process the full history of events to build state (event sourcing, rebuilding a derived database); a new consumer group should start from scratch with full data.
- **`latest` (default)** — start reading from the current end of the topic (new messages only). Historical messages are skipped. Use when: you only care about future events; backprocessing historical data would be incorrect or wasteful (e.g., a consumer that sends real-time notifications — sending notifications for yesterday's events today would confuse users).
- **`none`** — throw an exception if no offset is found. Use when: the absence of a committed offset is a bug that should fail loudly rather than silently start from an arbitrary position. Forces explicit operator intervention.

The dangerous scenario for `latest`: if a consumer group's offsets are accidentally deleted (via `kafka-consumer-groups.sh --delete-offsets` or `__consumer_offsets` data loss), and the group restarts with `latest`, it silently skips all messages produced during the time it was offline. There is no error — the consumer simply starts consuming from the current tail, and all in-between messages are never processed. For consumers where message loss is unacceptable (payment events, order events), `none` or `earliest` is safer.

## Section 8: Scenario / System Design Questions

**Q23. "A Kafka consumer is sending duplicate payments. Walk through the root cause analysis and fix."**
A: Duplicate payments from a Kafka consumer are an at-least-once delivery + non-idempotent processing problem. Root cause analysis:

1. **Identify the duplication pattern** — are duplicates correlated with consumer restarts, rebalances, or specific time windows? Duplicates immediately after a restart point to uncommitted offsets at crash time. Duplicates at regular intervals may point to a rebalance pattern.

2. **Check commit configuration** — is `enable.auto.commit = true`? If so, is the commit interval larger than the payment processing time? If the payment processing takes 3 seconds and the commit interval is 5 seconds, a crash between the 3-second and 5-second marks causes a reprocessed payment.

3. **Check where commitSync/commitAsync is called** — is the commit happening before the payment API call returns success? Committing before the external call confirms is an at-most-once bug, but if the external call sometimes returns a timeout (ambiguous outcome) and the consumer retries both the message and the payment, you get duplicates from the retry logic, not from the offset mechanics.

4. **Fix — idempotency key on the payment API call**: derive an idempotency key from the Kafka partition + offset (globally unique, stable across retries):
```java
String idempotencyKey = record.topic() + "-" + record.partition() + "-" + record.offset();
paymentGateway.charge(amount, idempotencyKey);
// If this call is retried (same key), the gateway returns the original response without charging again
```

5. **Fix — database-level deduplication**: before inserting a payment record, check for existence:
```sql
INSERT INTO payments (kafka_offset_key, amount, ...)
VALUES (?, ?, ...)
ON CONFLICT (kafka_offset_key) DO NOTHING;
```

6. **Fix — exactly-once if the payment is Kafka-to-Kafka**: if the payment event is consumed from one Kafka topic and the result is produced to another, use Kafka's transactional API to make the consume + produce atomic.

7. **Commit placement fix**: move `commitSync()` to after the payment API call returns success AND after the database record is written. Only commit when all side effects are durable.

**Q24. "Your Kafka consumer is falling behind (growing lag). Commits are slow. What do you investigate?"**
A: Consumer lag growing with slow commits is a throughput problem in the commit path. Investigation steps:

**Check commit type and placement:**
- `commitSync()` in the inner processing loop (per-message) adds one broker RTT per message. At 10,000 messages/second, that's 10,000 commits/second — likely saturating the `__consumer_offsets` partition and the network. Switch to per-batch commits.
- `commitSync()` where `commitAsync()` would suffice — synchronous commits stall the consumer thread during the broker RTT. Switching to async commits for non-final commits removes this bottleneck.

**Check `__consumer_offsets` partition load:**
- Multiple consumer groups committing to the same `__consumer_offsets` partition compete for I/O on the broker hosting that partition. Distribute consumer groups with different names to distribute the hash across more partitions.

**Check message processing time:**
- If the bottleneck is not the commit but the processing itself (database writes, API calls), the commit appears slow because the commit happens after slow processing. Profile the processing time per message vs the commit time. If processing is the bottleneck, parallelize processing (process multiple messages concurrently before committing the batch).

**Check rebalance frequency:**
- Frequent rebalances (visible in `__consumer_offsets` commit patterns and in consumer group describe output) cause stop-the-world pauses that manifest as periodic lag spikes. Check if `max.poll.interval.ms` is too short for the actual processing time — the consumer is being kicked from the group mid-batch and rebalancing.

**Check fetch size:**
- If `max.poll.records` is too low (default 500), the consumer is making many small polls. If too high, each poll takes longer to process, pushing against `max.poll.interval.ms`. Tune batch size to match processing throughput.

**Q25. "A team says 'we use exactly-once Kafka transactions, so our pipeline is correct.' What questions do you ask?"**
A: Exactly-once Kafka transactions guarantee atomicity of the consume-transform-produce loop within Kafka. They do not guarantee correctness of the entire pipeline. Questions to probe:

- **Is your consumer configured with `isolation.level = read_committed`?** If your output topic's consumers use `read_uncommitted` (the default), they see messages from aborted transactions. The transactional producer prevents duplicates going into Kafka, but `read_uncommitted` consumers undo this guarantee on the read side.
- **Are you using `sendOffsetsToTransaction()` instead of `consumer.commitSync()`?** If the team is using `producer.commitTransaction()` for output but `consumer.commitSync()` for offsets separately, the offset commit is outside the transaction — they have exactly-once output but at-least-once offset commits, meaning a crash can cause the input to be reprocessed even though the output was transactionally committed.
- **What happens when the transaction coordinator is unavailable?** Does the application handle `TimeoutException` from `commitTransaction()` by aborting and retrying? Or does it silently continue, leaving the transaction open?
- **Are all output topics included in the transaction?** If the pipeline writes to both Kafka topic B and a database as part of "processing," the database write is outside the Kafka transaction — only the Kafka output is exactly-once. Database writes still need their own idempotency mechanism.
- **What is the `transactional.id` strategy?** If multiple instances use the same `transactional.id` (a misconfiguration bug), they will fence each other and produce errors. If an instance starts with a new `transactional.id` after a restart (e.g., it includes a pod IP in the ID), it doesn't fence the old instance — zombie fencing doesn't work.
- **How long are transactions held open?** If a single transaction spans many messages or a long processing time, the LSO doesn't advance and downstream `read_committed` consumers fall behind — the exactly-once guarantee is correct but practically unusable due to head-of-line blocking.

**Q26. "Design an exactly-once payment processing pipeline from a Kafka topic to a PostgreSQL database."**
A: Exactly-once semantics from Kafka to an external database cannot use Kafka's transactional API alone — the database is outside Kafka's transaction boundary. The correct approach: implement exactly-once at the application layer using idempotency.

**Architecture:**

1. **Consumer configuration:**
```
enable.auto.commit = false
isolation.level = read_uncommitted  # no Kafka transactions needed for DB output
group.id = payment-processor
```

2. **Per-message processing with database-level idempotency:**
```python
records = consumer.poll(timeout_ms=1000)
for record in records:
    payment = deserialize(record.value())
    idempotency_key = f"{record.partition()}-{record.offset()}"

    with db.transaction():
        # Idempotent insert: skip if already processed
        result = db.execute("""
            INSERT INTO payments (idempotency_key, account_id, amount, status, created_at)
            VALUES (%s, %s, %s, 'COMPLETED', now())
            ON CONFLICT (idempotency_key) DO NOTHING
            RETURNING idempotency_key
        """, (idempotency_key, payment.account_id, payment.amount))

        if result.rowcount == 1:
            # New payment — also write the debit to the ledger
            db.execute("""
                INSERT INTO ledger_entries (idempotency_key, account_id, amount, direction)
                VALUES (%s, %s, %s, 'DEBIT')
                ON CONFLICT (idempotency_key) DO NOTHING
            """, (idempotency_key, payment.account_id, payment.amount))
        # If rowcount == 0: already processed — no-op, safe to continue
```

3. **Offset commit after successful database transaction:**
```python
    # Commit offset only after DB transaction committed
    consumer.commit({
        TopicPartition(record.topic(), record.partition()):
        OffsetAndMetadata(record.offset() + 1)
    })
```

4. **Recovery guarantee:** if the consumer crashes between the DB commit and the offset commit, on restart it reprocesses from the last committed offset. The DB `ON CONFLICT DO NOTHING` ensures the duplicate insert is a no-op. The net result: each payment is applied to the database exactly once, regardless of how many times the Kafka message is reprocessed.

5. **What this achieves:** exactly-once semantics at the database layer (via idempotency), at-least-once Kafka delivery (offset commit after processing). This is the standard production pattern for Kafka-to-database exactly-once — simpler, more portable, and often more performant than Kafka's transactional API for external database outputs.

## Quick Reference

**Delivery Guarantee Decision Tree:**
```
Can your processing tolerate data loss?
├── Yes → at-most-once: commit before processing (or auto-commit + accept risk)
└── No → Can your processing tolerate duplicates?
    ├── Yes (idempotent) → at-least-once: commit after processing (manual commit)
    └── No → exactly-once:
        ├── Output is another Kafka topic → Kafka transactional API
        └── Output is an external DB/API → at-least-once + idempotency key
```

**Offset Commit Cheat Sheet:**

| Commit Type | Blocks poll()? | Retries on failure? | Use Case |
|--- |--- |--- |--- |
| Auto-commit | No (background) | N/A | Low-criticality consumers, fast processing |
| `commitSync()` | Yes | Yes (until success) | Final commit on shutdown; critical checkpoints |
| `commitAsync()` | No | No (callback on failure) | Normal processing loop; high throughput |
| `commitAsync()` + `commitSync()` on close | Mostly no | Final commit retries | Standard production pattern |
| `sendOffsetsToTransaction()` | No | Part of transaction | Exactly-once Kafka-to-Kafka |

**Failure Mode Summary:**

| Configuration | Crash Before Processing | Crash After Processing, Before Commit | Crash After Commit |
|--- |--- |--- |--- |
| Auto-commit (5s interval) | Re-process (at-least-once) | May lose (at-most-once if interval fired) | No re-process |
| Manual commit, after processing | Re-process (at-least-once) | Re-process (at-least-once) | No re-process |
| Manual commit, before processing | No re-process (at-most-once) | No re-process (at-most-once) | No re-process |
| Exactly-once (transactional) | Re-process, idempotent | Re-process, idempotent | No re-process |

**Tip for the interview:** At 5 YOE level, offset management questions are not about API signatures — they're about failure reasoning. The strongest answers trace a specific crash scenario through the offset lifecycle: "if the consumer crashes at this exact point in the processing loop, here is what the committed offset is, here is what gets reprocessed, and here is whether that reprocessing is safe or a bug." Pair that with the fix: "to make reprocessing safe, we added an idempotency key derived from partition + offset to the database insert." The war story version is even better: "we had duplicate payments in production from a consumer that committed offsets inside a try block before the database transaction committed — the commit succeeded but the DB transaction rolled back, so on restart the payment was reprocessed but the offset said it was done. Here's the fix: commit only in the finally block after confirming the DB transaction committed."
