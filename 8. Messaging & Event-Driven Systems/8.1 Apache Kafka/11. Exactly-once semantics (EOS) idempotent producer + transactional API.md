# Exactly-Once Semantics (EOS): Idempotent Producer + Transactional API — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are the three delivery semantics in Kafka and what does each guarantee?**
A: Kafka's delivery guarantees form a hierarchy of increasing strength and increasing cost:

**At-most-once:**
Messages may be lost but are never duplicated. The producer fires and forgets (`acks=0`) or commits offsets before processing. If the producer crashes after sending but before confirmation, or the consumer commits before finishing processing, the message is silently dropped. Appropriate for metrics, logs, or any workload where occasional data loss is acceptable and throughput is paramount.

**At-least-once:**
Messages are never lost but may be duplicated. The producer retries on failure (`acks=1` or `acks=all`, `retries > 0`); the consumer commits offsets only after processing. If the broker ACKs a write but the network drops before the producer receives the ACK, the producer retries — the broker writes the message a second time. If the consumer processes a message but crashes before committing the offset, it reprocesses on restart. The downstream must be idempotent to tolerate duplicates. The default and most common semantic.

**Exactly-once:**
Messages are neither lost nor duplicated. Every message is processed and its effects are applied exactly once, even under retries, crashes, and rebalances. The strongest guarantee. In Kafka, achieved via the idempotent producer (prevents duplicate writes per producer session) and the transactional API (atomic writes across multiple partitions + atomic offset commits). Requires additional broker and consumer configuration, and carries a throughput cost.

**Q2. Why is exactly-once hard to achieve in a distributed system?**
A: The fundamental difficulty: in a distributed system, a sender cannot distinguish between "the receiver got my message and failed before ACKing" and "the message was lost in transit." In both cases, the sender times out and retries. If it doesn't retry, it risks at-most-once. If it does retry, it risks at-least-once. Achieving exactly-once requires a mechanism to detect and discard duplicates without silently dropping legitimate messages.

In Kafka specifically:
- **Network retransmissions:** A producer sends batch B to broker 1. Broker writes B and ACKs — but the network drops the ACK. The producer retries, sending B again. Without deduplication, broker 1 writes B twice.
- **Broker failover:** The partition leader fails after writing a message but before replicating to all ISR members. A new leader is elected that doesn't have the message. The producer retries to the new leader — writes it again. Or the opposite: the new leader does have it, and the retry creates a duplicate.
- **Consumer rebalance:** A consumer processes a message but rebalances before committing the offset. The new owner of the partition reprocesses from the last committed offset — duplicate processing.

**Q3. What is the difference between idempotent producer and transactional producer?**
A: They solve different, complementary problems:

**Idempotent producer:** Prevents duplicate messages within a single partition from a single producer session. Scope: one producer → one partition. Handles the network retry scenario (producer retries a write that the broker already received and wrote). Enabled with `enable.idempotence=true`. Requires no changes to consumers.

**Transactional producer:** Enables atomic writes across multiple partitions and topics, and atomic offset commits. Scope: one producer → multiple partitions + consumer offset commits. Handles the read-process-write scenario (consume from topic A, write to topic B, commit offset — all atomically). Requires `transactional.id` configuration and consumer `isolation.level=read_committed`. Implicitly enables idempotence.

Together they provide end-to-end exactly-once semantics for stream processing:
- Idempotent producer: prevents duplicates at the write layer.
- Transactional API: makes the consume + process + produce + commit atomic.

## Section 2: Idempotent Producer

**Q4. How does the idempotent producer work mechanically?**
A: The idempotent producer uses two identifiers to deduplicate writes at the broker:

**Producer ID (PID):** A unique 64-bit integer assigned by the broker to each producer instance on initialization. When a producer calls `initTransactions()` or simply connects with `enable.idempotence=true`, it sends an `InitProducerId` request to the broker. The broker assigns a PID from a monotonically increasing sequence stored durably (in ZooKeeper / KRaft metadata). The PID is ephemeral per producer session — if the producer restarts without a `transactional.id`, it gets a new PID.

**Sequence number:** A per-partition, per-PID sequence number that the producer increments for every message batch sent to that partition. Starts at 0. The broker tracks the highest sequence number seen from each (PID, partition) pair.

**Deduplication logic at the broker:**
```
Producer sends batch with (PID=42, partition=3, sequence=100)

Broker checks: what's the highest sequence I've seen from PID 42 on partition 3?
  → If highest_seq = 99: this is the next expected batch → accept, write, update to 100
  → If highest_seq = 100: duplicate (already wrote this batch) → discard, return success
  → If highest_seq = 98: out-of-order (gap) → return OutOfOrderSequenceException
  → If sequence > highest_seq + 1: batch was sent out of order → error
```

The broker persists the highest sequence number per (PID, partition) in the partition's log and in memory. On recovery, it reloads sequence state from the log — deduplication survives broker restarts.

**Q5. What producer configuration changes are required to enable idempotence?**
A: Enabling `enable.idempotence=true` automatically adjusts related settings, but understanding the full configuration is important:

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker-1:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

// Enable idempotence — this is the key setting
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

// The following are automatically set when idempotence is enabled,
// but shown explicitly for clarity:
props.put(ProducerConfig.ACKS_CONFIG, "all");            // required for idempotence
props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE); // retry until success
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
// max 5 in-flight batches per partition (broker deduplicates across these)
// Setting > 5 disables idempotence; default with idempotence = 5
```

**Constraints imposed by idempotence:**
- `acks` must be `all` — idempotence requires writes to be committed to the ISR before ACK. With `acks=1`, the leader could crash after ACKing but before replication — the new leader doesn't have the message, and the producer retries, but now the broker has no sequence state to detect the "duplicate" (it's actually a legitimate retry of a lost message).
- `max.in.flight.requests.per.connection` ≤ 5 — the broker tracks up to 5 in-flight sequence numbers per (PID, partition). With more in-flight, the broker cannot guarantee ordering.
- `retries` should be large (or MAX_VALUE) — idempotence is only useful if the producer actually retries on failure.

**Q6. What is the scope of the idempotent producer's guarantee?**
A: The idempotent producer prevents duplicates within a single producer session (one PID lifetime) for writes to a single partition. It does NOT guarantee:

- **Cross-session deduplication:** If the producer crashes and restarts without a `transactional.id`, it gets a new PID. A message sent in the old session that was retried by the broker after crash will appear as a new (non-duplicate) message to the broker with the new PID. The transactional API solves this by fencing old producers (see Q11).
- **Cross-partition atomicity:** Idempotence applies per-partition independently. Writing to partition A and partition B is not atomic — a failure between the two writes leaves an inconsistent state.
- **Consumer deduplication:** The consumer may still reprocess messages if the consumer crashes before committing its offset. Idempotence is a producer-side guarantee; the consumer must still be idempotent or use transactional offset commits.

**Q7. How does the broker maintain sequence state across restarts?**
A: Sequence state is persisted in two ways:

**In the log itself:** Every message batch written to a Kafka partition includes the PID and sequence number in its batch header. When a broker restarts and reloads a partition's log, it can reconstruct the highest sequence number for each PID by scanning the recent log records.

**In-memory cache:** During normal operation, the broker keeps an in-memory map of `(PID, partition) → highest_sequence` for fast deduplication lookup without scanning the log on every request.

**Retention interaction:** Sequence state is only tracked for active PIDs within a window. If no messages have been received from a PID for `transactional.id.expiration.ms` (default 7 days), the broker evicts that PID's state. A producer that was idle for > 7 days and then resumes may need to reinitialize (or will receive a `ProducerFencedException` if using transactions).

## Section 3: Transactional API

**Q8. What problem does the transactional API solve beyond idempotence?**
A: Idempotence prevents duplicate writes per partition per session. But in a stream processing pipeline — consume from topic A, transform, write to topic B, commit consumer offset — multiple things must happen atomically:

```
Without transactions:
1. Consumer reads message M from topic A, offset 5.
2. Producer writes result R to topic B.  ← success
3. Consumer commits offset 6 to __consumer_offsets. ← CRASH before this
4. Consumer restarts, re-reads M from offset 5.
5. Producer writes R again to topic B.   ← DUPLICATE in topic B
```

The transactional API makes steps 2 and 3 atomic: either both succeed or neither does. The offset commit and the output write are wrapped in a single transaction — they commit together or abort together. This is the read-process-write atomic guarantee that completes the EOS story.

**Q9. What is the `transactional.id` and why is it critical?**
A: The `transactional.id` is a stable, user-assigned string that identifies a logical producer across restarts. Unlike the PID (which is ephemeral and changes on restart), the `transactional.id` persists:

```java
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-processor-1");
```

**What it enables:**
- **Cross-session continuity:** The broker maps `transactional.id → PID`. On producer restart, the broker issues a new PID but associates it with the same `transactional.id`. Any in-progress transaction from the old PID is aborted before the new producer can proceed — ensuring no overlap.
- **Zombie producer fencing:** If a producer with `transactional.id=order-processor-1` crashes and a new instance starts with the same `transactional.id`, the broker increments the **producer epoch**. Any subsequent request from the old instance (which may have been in a network partition, not actually dead) is rejected with `ProducerFencedException` — the old producer is "fenced out." Only the latest epoch can write.

**Epoch mechanism:**
```
Old producer: PID=42, epoch=3, transactional.id="order-processor-1"
New producer starts, calls initTransactions():
  → Broker finds existing entry: transactional.id="order-processor-1" → PID=42, epoch=3
  → Broker increments epoch to 4
  → Any request from (PID=42, epoch=3) is now rejected
  → New producer operates as (PID=42, epoch=4)
```

**Q10. Walk through the complete transactional write lifecycle.**
A: A transactional producer goes through a well-defined sequence of steps for every atomic operation:

```java
KafkaProducer<String, String> producer = new KafkaProducer<>(props);

// Step 1: Initialize — establish PID + epoch with the Transaction Coordinator
// Must be called once before any transactions
producer.initTransactions();

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));

    try {
        // Step 2: Begin transaction
        producer.beginTransaction();

        for (ConsumerRecord<String, String> record : records) {
            // Step 3: Produce output messages (multiple partitions allowed)
            ProducerRecord<String, String> output = transform(record);
            producer.send(new ProducerRecord<>("output-topic", output.key(), output.value()));
            producer.send(new ProducerRecord<>("audit-topic", record.key(), "processed"));
        }

        // Step 4: Atomically commit the consumer offsets as part of the transaction
        // This writes the offset to __consumer_offsets within the transaction boundary
        Map<TopicPartition, OffsetAndMetadata> offsets = getCurrentOffsets(records);
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());

        // Step 5: Commit the transaction
        // The Transaction Coordinator writes a COMMITTED marker to all involved partitions
        producer.commitTransaction();

    } catch (ProducerFencedException | OutOfOrderSequenceException e) {
        // Fatal — this producer instance has been fenced or has a sequence gap
        // Do not retry — close and restart the application
        producer.close();
        throw e;
    } catch (KafkaException e) {
        // Abortable — abort the current transaction and retry
        producer.abortTransaction();
        // Seek consumer back to re-read the unprocessed records
        consumer.seek(...);
    }
}
```

**Q11. What is the Transaction Coordinator and what does it do?**
A: The Transaction Coordinator is a broker-side component responsible for managing the lifecycle of transactions. Each `transactional.id` is assigned to one broker as its Transaction Coordinator (via hashing of `transactional.id` to a partition of the internal `__transaction_state` topic, similar to how consumer groups are assigned to a Group Coordinator).

**Transaction Coordinator responsibilities:**
- **Assigns and tracks PID + epoch** for each `transactional.id`.
- **Maintains transaction state machine:** `Empty → Ongoing → PrepareCommit → CompleteCommit / PrepareAbort → CompleteAbort`.
- **Tracks partitions involved in the transaction:** When the producer first writes to a partition within a transaction, it notifies the Transaction Coordinator (`AddPartitionsToTxn` request). The coordinator records all partitions participating in the transaction.
- **Coordinates two-phase commit:** On `commitTransaction()`, the coordinator writes `PrepareCommit` to its own log (durable), then instructs each involved partition's leader to write a `COMMIT` transaction marker. Once all markers are written, the coordinator writes `CompleteCommit`.
- **Handles timeouts:** If a transaction isn't committed or aborted within `transaction.timeout.ms` (default 60 seconds), the coordinator aborts it — preventing indefinitely open transactions from blocking consumers.

**Q12. What is a transaction marker and why is it necessary?**
A: A transaction marker is a special control record written to every partition and to `__consumer_offsets` at the end of a transaction. It signals whether the transaction committed or aborted.

**Why necessary:** During a transaction, messages are written to topic partitions normally (with the producer's batch headers indicating they're part of a transaction, via the `transactional` bit in the batch header). These messages are visible in the partition log immediately after writing — but they should not be consumed by `read_committed` consumers until the transaction is confirmed committed or aborted.

```
Partition log during and after a transaction:

[offset 100] Regular message (non-transactional)
[offset 101] Transactional message (PID=42, epoch=4, txn=in-progress)
[offset 102] Transactional message (PID=42, epoch=4, txn=in-progress)
[offset 103] Regular message (non-transactional)
[offset 104] COMMIT marker (PID=42, epoch=4)   ← written on commitTransaction()

read_committed consumers:
  → See offsets 100, 103 immediately (non-transactional)
  → See offsets 101, 102 only after seeing offset 104 (COMMIT marker)
  → If offset 104 were ABORT marker: skip offsets 101, 102 entirely
```

The `COMMIT` or `ABORT` marker is the atomicity boundary — consumers pause at transactional message boundaries and only deliver them once the fate of the transaction is known.

**Q13. What is `isolation.level` and why must consumers set it correctly for EOS?**
A: `isolation.level` controls what uncommitted transactional messages a consumer sees:

**`read_uncommitted` (default):**
Consumers see all messages as soon as they're written to the partition log, including messages from in-progress or aborted transactions. This is the pre-EOS behavior — high throughput, no awareness of transaction boundaries. A consumer may read messages that are later aborted — the consumer has no way to know.

**`read_committed`:**
Consumers only see:
- Non-transactional messages (written without a `transactional.id`).
- Transactional messages whose transaction has been committed (the COMMIT marker has been written).
- They never see messages from aborted transactions.
- They wait at the Last Stable Offset (LSO) — the highest offset up to which all transactions are resolved — before advancing.

```java
// Consumer must set this for EOS guarantees
props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
```

**Last Stable Offset (LSO):** The LSO is the highest offset such that all transactions whose messages appear at or below this offset have been committed or aborted. Consumers with `read_committed` never read beyond the LSO. This means an open (uncommitted, non-aborted) transaction can block `read_committed` consumers from advancing past its first message, even if many committed messages exist beyond it.

**Practical implication:** Long-running transactions or transactions that are never committed/aborted (zombie producers) cause the LSO to stall — `read_committed` consumers stop advancing. This is one reason `transaction.timeout.ms` exists — the broker aborts stuck transactions to unblock consumers.

## Section 4: Two-Phase Commit and Failure Handling

**Q14. How does Kafka's transactional commit implement two-phase commit (2PC)?**
A: Kafka's transaction commit is a 2PC protocol managed by the Transaction Coordinator:

**Phase 1 — Prepare:**
```
Producer calls commitTransaction()
  → Sends EndTransaction(commit=true) to Transaction Coordinator
  → Coordinator writes PrepareCommit record to __transaction_state (durable)
  → Coordinator knows: "this transaction should commit, even if I crash"
```

**Phase 2 — Commit:**
```
Coordinator sends WriteTxnMarkers request to each partition leader involved
  → Each partition leader writes COMMIT marker to its partition log
  → Each partition leader ACKs the coordinator

Coordinator writes CompleteCommit to __transaction_state
  → Transaction is fully resolved
  → __consumer_offsets partition also receives COMMIT marker
     (the offset commit is just another partition in the transaction)
```

**Crash recovery:**
- If the coordinator crashes after Phase 1 (PrepareCommit written) but before Phase 2: on recovery, the new coordinator reads `PrepareCommit` from `__transaction_state` and completes Phase 2. The transaction eventually commits.
- If the coordinator crashes before Phase 1: the transaction is lost in memory. The producer will timeout and abort. At-least-once at worst for the produce (idempotent producer prevents broker-side duplicates on retry).
- If a partition leader crashes during Phase 2 before writing its marker: the new leader, on startup, checks with the coordinator whether it has a pending unresolved transaction. The coordinator instructs it to write the COMMIT or ABORT marker.

**Q15. What happens when a transaction is aborted?**
A: Abort follows the same 2PC path as commit, but writes ABORT markers instead:

```
Producer calls abortTransaction()
  OR transaction times out (transaction.timeout.ms exceeded)
  OR coordinator detects producer fencing (new epoch for same transactional.id)

  → Coordinator writes PrepareAbort to __transaction_state
  → Coordinator sends WriteTxnMarkers(abort=true) to all involved partitions
  → Each partition writes ABORT marker
  → read_committed consumers skip all messages in the aborted transaction
  → Coordinator writes CompleteAbort

Effect: as if the transaction's messages were never written.
The physical log still contains the transactional messages + ABORT marker,
but read_committed consumers filter them out. Compaction eventually
removes aborted transaction records from the log.
```

**Q16. What is producer fencing and how does it prevent zombie producers?**
A: Producer fencing is the mechanism that prevents a stale producer instance from interfering with a new instance of the same logical producer.

**Zombie scenario without fencing:**
```
t=0:  Producer P1 (transactional.id="order-proc", epoch=3) begins transaction T1.
t=1:  P1 experiences a long GC pause (appears dead to the system).
t=2:  Orchestration detects P1 as failed, starts P2 (same transactional.id).
t=3:  P2 calls initTransactions() → broker increments epoch to 4, fences epoch=3.
t=4:  P2 processes records, commits transaction T2 successfully.
t=5:  P1's GC pause ends. P1 tries to commit transaction T1.
t=6:  Broker rejects P1's commit: (epoch=3) < (current epoch=4) → ProducerFencedException.
      T1 is aborted by the broker. P1 must shut down.
```

Without fencing, P1 and P2 could both successfully commit — writing duplicate output. With fencing, only the latest epoch can commit. Older epochs are silently rejected.

**Epoch increment trigger:** `initTransactions()` always triggers an epoch increment for the `transactional.id`. This means any time a transactional producer is restarted (crashes, rolling deploy), old instances are automatically fenced. This is why `transactional.id` should be stable and unique per logical producer — reusing the same ID across different logical producers would cause them to fence each other.

## Section 5: Kafka Streams and EOS

**Q17. How does Kafka Streams implement exactly-once semantics?**
A: Kafka Streams is built on top of the transactional API and automates the EOS pattern for stream processing applications. When you configure `processing.guarantee=exactly_once_v2` (recommended, introduced in Kafka 2.5):

```java
Properties streamsConfig = new Properties();
streamsConfig.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-processor");
streamsConfig.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "broker-1:9092");
streamsConfig.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG,
    StreamsConfig.EXACTLY_ONCE_V2);  // EOS-v2
```

**What Kafka Streams does under the hood:**
- Creates a transactional producer per task (each task processes one input partition).
- The `transactional.id` is derived from `APPLICATION_ID + task_id` — stable across restarts, unique per task.
- On each commit interval (`commit.interval.ms`, default 30 seconds for EOS), Streams:
  1. Calls `producer.beginTransaction()`.
  2. Flushes all buffered output records via `producer.send()`.
  3. Calls `producer.sendOffsetsToTransaction()` for all input partition offsets.
  4. Calls `producer.commitTransaction()`.
- Output topic consumers must use `isolation.level=read_committed`.

**EOS-v1 vs EOS-v2:**
- **EOS-v1 (`exactly_once`):** One transactional producer per consumer-producer pair. In a Kafka Streams app with 10 input partitions, 10 separate producers are created. High resource overhead.
- **EOS-v2 (`exactly_once_v2`):** One transactional producer per task (same as EOS-v1 for most topologies, but uses thread-level producers shared across tasks processed by the same thread). Uses the newer broker-side epoch fencing to handle rebalances more efficiently. Requires Kafka brokers ≥ 2.5. Lower overhead, faster rebalance recovery.

**Q18. How does EOS interact with Kafka Streams rebalances?**
A: Rebalances (tasks moving between instances) are where EOS is most complex:

**Without EOS:** A rebalance may cause the previous task owner to commit a transaction and the new owner to reprocess the same input, producing duplicates.

**With EOS-v2:** Each task has a `transactional.id` tied to its task ID. When a rebalance moves a task from instance A to instance B:
1. Instance B starts a new transactional producer for the task with the same `transactional.id`.
2. `initTransactions()` increments the epoch — instance A's producer (if still alive) is now fenced.
3. Instance B resumes from the last committed offset (the offset committed atomically in the last successful transaction).
4. Any in-progress transaction from instance A is aborted by the Transaction Coordinator (A is fenced and can't commit; the coordinator eventually aborts the dangling transaction).

The result: no duplicate output, no lost messages, even across rebalances.

## Section 6: Trade-offs and Operational Considerations

**Q19. What is the performance cost of exactly-once semantics?**
A: EOS carries measurable overhead at each layer:

**Producer overhead:**
- `initTransactions()` adds one broker round trip on startup.
- `beginTransaction()` / `commitTransaction()` add two extra broker round trips per commit (one to the Transaction Coordinator for PrepareCommit, one fan-out to all involved partition leaders for markers).
- `acks=all` increases write latency vs `acks=1` (waits for all ISR members).
- In practice: EOS adds ~10–20% latency overhead and ~5–10% throughput reduction compared to at-least-once with `acks=all`.

**Broker overhead:**
- Transaction Coordinator manages `__transaction_state` — additional I/O per transaction.
- Writing COMMIT/ABORT markers to every involved partition — additional I/O fan-out.
- Maintaining in-memory LSO per partition for `read_committed` consumers.

**Consumer overhead:**
- `read_committed` consumers must track LSO per partition — they buffer messages at LSO boundaries until the transaction's fate is known.
- Long-running transactions or stalled transactions block consumer progress. A single stuck transaction can cause consumer lag to grow indefinitely on `read_committed` consumers.
- Additional memory to buffer transactional messages waiting for their COMMIT marker.

**Tuning levers:**
- `transaction.timeout.ms`: reduce from 60 seconds to 15–30 seconds for stream processing workloads where transactions should complete quickly. Shorter timeout means stuck transactions are aborted sooner, unblocking consumers.
- `commit.interval.ms` (Kafka Streams): increase to batch more records per transaction, reducing per-record overhead. Trade-off: larger batches mean more reprocessing on failure.
- Minimize the number of partitions involved per transaction — each additional partition means one more COMMIT marker write.

**Q20. What are the failure modes specific to EOS?**
A: EOS introduces failure modes that don't exist in at-least-once:

**LSO stall:** A `read_committed` consumer stops advancing because an open transaction's first message is at a low offset. The transaction is never committed or aborted (e.g., a zombie producer that holds the transaction open). Fix: `transaction.timeout.ms` — the broker aborts transactions that exceed this timeout. Monitor consumer lag on `read_committed` topics; non-advancing lag at a constant offset indicates an LSO stall.

**ProducerFencedException in normal operation:** A producer is fenced when `initTransactions()` is called by a new instance of the same `transactional.id`. If your deployment strategy restarts the producer frequently (e.g., rolling deploy without draining in-flight transactions), the old instance may get fenced mid-transaction. The fenced instance must shut down — it cannot recover. Mitigation: gracefully close the producer before restarting (`producer.close()`), which aborts any in-progress transaction.

**`transactional.id` collision:** Two different logical producers accidentally share the same `transactional.id`. Each restart of either producer fences the other — random `ProducerFencedException` errors with no apparent cause. Fix: ensure `transactional.id` is globally unique and stable. For Kafka Streams, the framework manages this automatically.

**Transaction log filling disk:** The `__transaction_state` topic retains transaction records for `transactional.id.expiration.ms` (default 7 days). In a cluster with thousands of unique `transactional.id`s, this topic can consume significant disk. Monitor its size separately.

**Q21. When should you use EOS and when is at-least-once sufficient?**
A: EOS is not always necessary — choose based on the consequence of duplicates:

**Use EOS when:**
- Output has financial consequences (payment processing, inventory deduction, billing records) — duplicates cause double charges or double inventory removal.
- Output feeds a system that is not idempotent and cannot be made idempotent (external API calls, non-idempotent DB writes with natural keys).
- Regulatory or audit requirements mandate exactly-once processing (healthcare, financial compliance).
- The pipeline is a Kafka Streams application with complex stateful processing where reprocessing from a checkpoint is expensive or incorrect.

**At-least-once is sufficient when:**
- The consumer is idempotent by design (upserts to a database keyed by message ID, set membership, `INSERT ... ON CONFLICT DO NOTHING`).
- Duplicates are detectable and rare enough that a separate deduplication step is acceptable (a bloom filter or deduplication table in Redis).
- Throughput requirements are extreme and EOS overhead is unacceptable (logging pipelines, metrics aggregation where approximate counts are fine).
- The output is a compacted Kafka topic — duplicate writes with the same key are naturally deduplicated by compaction.

**The pragmatic approach:** Start with at-least-once + idempotent consumers. The combination is simpler to operate and reason about than EOS. Move to EOS when the cost of duplicates exceeds the cost of EOS overhead — financial systems, audit-critical pipelines, or cases where consumer idempotency is genuinely impossible.

## Section 7: Scenario / System Design Style Questions

**Q22. "You're building a payment processing pipeline: consume from a `payment-requests` topic, charge a payment gateway (external API), write result to `payment-results` topic, commit offset. Which delivery semantic do you use and why?"**
A: This is a critical case where EOS alone is NOT sufficient — the external API call is outside Kafka's transaction boundary:

**The core problem:**
```
1. Consume payment request (offset 100).
2. BEGIN TRANSACTION.
3. Call payment gateway API → charge succeeds.
4. Write result to payment-results.
5. COMMIT TRANSACTION (offset 101 committed, result written atomically).
```

Even with EOS, if the process crashes between steps 3 and 4, on retry:
- The Kafka transaction is aborted (incomplete).
- The consumer reprocesses from offset 100.
- Step 3 runs again → second charge to the payment gateway.

**EOS with Kafka only prevents Kafka-internal duplicates** — it cannot make an external API call idempotent.

**Correct approach — idempotency key at the API layer:**
```
1. Consume payment request (offset 100). Request has payment_id = "pay:abc123".
2. Generate idempotency key: hash(payment_id + kafka_partition + kafka_offset).
3. Call payment gateway API with idempotency key.
   → Gateway: if key seen before, return previous result. Never charge twice.
4. BEGIN TRANSACTION.
5. Write result to payment-results.
6. sendOffsetsToTransaction (offset 101).
7. COMMIT TRANSACTION.
```

The idempotency key on the external API call makes step 3 safe to retry. The Kafka transaction makes steps 5–7 atomic. Combined, the full pipeline is effectively exactly-once end-to-end.

**Delivery semantic for the Kafka portion:** EOS (`transactional.id`, `isolation.level=read_committed` on downstream consumers). The external API call requires application-level idempotency via idempotency keys — Kafka's EOS cannot help there.

**Q23. "A Kafka Streams application has consumer lag growing on a read_committed topic. The lag is not advancing and is stuck at offset 8,492. What's happening and how do you fix it?"**
A: Classic LSO stall caused by an open transaction:

**Diagnosis:**
```bash
# Check consumer group lag
kafka-consumer-groups.sh --bootstrap-server broker-1:9092 \
  --describe --group my-streams-app

# If lag is stuck at a constant offset for minutes, suspect LSO stall

# Check LSO for the affected partition
kafka-log-dirs.sh --bootstrap-server broker-1:9092 \
  --topic-list payment-results --describe | grep lastStableOffset

# If lastStableOffset is stuck at 8492, there's an open transaction
# whose first message is at or before 8492

# Find open transactions — check __transaction_state
kafka-transactions.sh --bootstrap-server broker-1:9092 list
# Look for transactions in ONGOING state for an extended period
```

**Root causes:**
- **Zombie producer:** A producer with a `transactional.id` opened a transaction but crashed before committing or aborting. The transaction is stuck in ONGOING state. The broker will abort it after `transaction.timeout.ms`.
- **Long-running transaction:** A legitimate producer is taking longer than expected to process and commit. The transaction is still open — the LSO won't advance until it resolves.
- **Fenced producer that couldn't abort:** A producer was fenced but the abort markers weren't fully written yet (coordinator failover in progress).

**Fixes:**
- **Wait for timeout:** If `transaction.timeout.ms` is set (e.g., 60 seconds), the broker will auto-abort the stuck transaction. The LSO advances and consumers unblock. This is why `transaction.timeout.ms` should be set conservatively short for stream processing.
- **Reduce `transaction.timeout.ms`:** If LSO stalls are frequent, reduce from 60 seconds to 15–30 seconds. Stuck transactions abort sooner.
- **Identify and terminate the zombie producer:** If the stuck transaction belongs to a known producer, terminate or fence it (restart with the same `transactional.id`). The epoch increment causes the broker to fence the old producer and abort its transaction.
- **Emergency:** As a last resort, produce an abort marker manually (no standard Kafka tool for this; requires coordination with the Transaction Coordinator — typically handled by letting the timeout expire).

**Q25. "Explain exactly-once semantics to a skeptical colleague who says 'true exactly-once delivery is impossible in distributed systems — you're just hiding the duplicates.'"**
A: Your colleague is making a subtle but important philosophical point — address it directly rather than dismissing it:

"You're right that in distributed systems, the underlying delivery mechanism is always at-least-once at some layer — the network may deliver a packet twice, or a retry may cause a duplicate send. What 'exactly-once semantics' means in Kafka is not that the network itself delivers each byte exactly once — it means that the *observable effect* on the output appears exactly once, even when the underlying mechanism retries.

Here's how: the idempotent producer gives every message batch a unique (PID, sequence) identity. The broker deduplicates at the write layer — even if the producer sends the same batch twice, the broker writes it only once. At the consumer side, the transactional API makes the write + offset commit atomic. Either both happen or neither does. From the perspective of a downstream reader, the message either appears or it doesn't — no partial state, no duplicate.

So the duplicates don't disappear from the network — they're absorbed by the broker's deduplication logic before they become visible to consumers. The 'hiding' is intentional and well-defined — it's exactly what a database does when you retry a transaction that was committed but whose acknowledgment was lost. You're not 'hiding' the fact that the network retried; you're ensuring the retry has no additional effect.

The caveat you're right to flag: Kafka's EOS only covers the Kafka-internal boundary. Side effects outside Kafka — like calling a payment gateway — are not covered. For those, you still need idempotency keys at the application level. Kafka's EOS is exactly-once for Kafka reads and writes; it's not a magic wand for the entire distributed system."

## Quick Reference: EOS Configuration Checklist

| Layer | Configuration | Value for EOS | Why |
|---|---|---|---|
| Producer | `enable.idempotence` | `true` | Enables PID + sequence deduplication |
| Producer | `transactional.id` | Stable unique string per logical producer | Enables cross-session continuity + fencing |
| Producer | `acks` | `all` | Auto-set by idempotence; required for durability |
| Producer | `retries` | `Integer.MAX_VALUE` | Auto-set; retry until success |
| Producer | `max.in.flight.requests.per.connection` | `≤ 5` | Auto-set; broker tracks 5 in-flight sequences |
| Producer | `transaction.timeout.ms` | 15,000–30,000 | Short timeout unblocks LSO stalls faster |

| Broker | `min.insync.replicas` | `2` (for RF=3) | EOS writes must reach quorum |

| Broker | `transaction.state.log.min.isr` | `2` | Require quorum for transaction log writes |
| Kafka Streams | `processing.guarantee` | `exactly_once_v2` | Automates transactional produce + offset commit |
| Kafka Streams | `commit.interval.ms` | `5000–30000` | Balance throughput vs reprocessing window |

**Tip for the interview:** EOS questions at senior level almost always go deeper than "set enable.idempotence=true." The three depth markers: (1) the scope boundaries — idempotent producer prevents within-session per-partition duplicates, but NOT cross-session or cross-partition; the transactional API handles cross-partition atomicity; neither covers external side effects (Q22 — the payment gateway problem); (2) the LSO mechanism (Q13, Q23) — `read_committed` consumers stall at the LSO when transactions are open, and a zombie producer can stall consumers indefinitely until `transaction.timeout.ms` fires; (3) producer fencing via epoch (Q16) — why `transactional.id` must be stable and unique, and how epoch increment prevents zombie producers. The philosophical pushback question (Q25) is a senior-level signal — knowing that EOS means "observable effect exactly once" (deduplication at the broker layer) rather than "network delivery exactly once" is the distinction that separates deep understanding from surface-level knowledge.
