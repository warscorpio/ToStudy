# Retention Policies: Time-Based, Size-Based — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a retention policy and what problem does it solve?**
A: A retention policy is a rule that governs how long data is kept in a storage system before being automatically discarded. Without one, data accumulates indefinitely — consuming disk, memory, and I/O capacity proportional to all data ever written, not just the data currently useful. Retention policies answer the question: "what is the minimum time (or minimum storage size) for which data must remain available, and what happens when that threshold is crossed?"

Retention solves four distinct problems simultaneously: **storage cost control** (disk is not free), **query performance** (smaller datasets scan faster), **compliance** (regulations require both minimum retention — "keep financial records for 7 years" — and maximum retention — "delete personal data after 2 years per GDPR"), and **operational simplicity** (systems that automatically expire old data require no manual cleanup jobs). The trade-off: once retained data is deleted, it is gone — any reprocessing, reanalysis, or audit that needed it is impossible without a separate backup.

**Q2. What are the three fundamental retention mechanisms and how do they differ?**
A:
- **Time-based retention**: data is deleted after it reaches a certain age. "Discard anything older than 7 days." Age is measured from write time, event time, or ingestion time depending on the system. Simple and predictable — the storage used by old data is automatically reclaimed as time passes, regardless of how much new data arrives.
- **Size-based retention**: data is deleted when the total stored volume exceeds a threshold. "Keep no more than 100GB per partition." When the threshold is crossed, the oldest data is deleted first until the volume falls back within bounds. Storage is bounded by configuration — useful when disk budget is the primary constraint, not time.
- **Log compaction** (Kafka-specific): data is retained indefinitely but deduplicated — only the latest value per key is kept. Old versions of a key are removed; new writes replace them. Not a deletion policy but a space-reduction policy that preserves correctness. Retention is conceptually infinite for active keys; a key is only removed when a tombstone (null value) is written and the tombstone has aged past its own retention window.

Most production systems allow combining mechanisms: in Kafka, `cleanup.policy = compact,delete` applies compaction and then time/size-based deletion to the compacted tail.

**Q3. What is the unit of deletion in Kafka's retention system, and why does this matter?**
A: Kafka's unit of deletion is the **log segment** — not the individual record. A Kafka topic partition's data is written as a sequence of rolling segment files (each segment is an `.log` file containing sequential records plus index files). When a retention policy triggers deletion, it evaluates and deletes entire segments, not individual records within a segment.

This matters because: (1) the **active segment** (the one currently being written to) is never eligible for deletion, regardless of age or size — it must be closed (rolled) before retention applies; (2) a single record that is 1 millisecond past the retention age cannot be deleted unless its entire segment is past the retention age — the effective retention is `configured_retention + (time_since_last_segment_roll_for_that_segment)`; (3) segment size (`log.segment.bytes`, default 1GB) and roll interval (`log.roll.hours`, default 7 days) control how frequently segments are closed and therefore how promptly retention can act on old data. A very large segment size delays when data becomes eligible for deletion.

**Q4. What is `log.retention.check.interval.ms` and why does it affect when data is actually deleted?**
A: `log.retention.check.interval.ms` (default 300,000ms = 5 minutes) is the frequency at which the Kafka log cleaner thread wakes up and checks whether any closed segments are eligible for deletion under the configured retention policy. It is not a real-time process — deletion happens in discrete sweeps at this interval.

Practical implication: data may persist for up to `log.retention.check.interval.ms` beyond its retention expiry before being deleted. For a 5-minute check interval, data may live up to 5 minutes past its retention threshold. Additionally, `file.delete.delay.ms` (default 60,000ms) adds a further delay between when a segment is marked for deletion and when the underlying file is actually removed from disk — allowing in-flight reader references to drain gracefully. The total maximum over-retention window is `check_interval + file_delete_delay = 6 minutes` in the default configuration.

## Section 2: Time-Based Retention

**Q5. How does Kafka's time-based retention work mechanically?**
A: Configured via `log.retention.ms` (or the human-readable aliases `log.retention.minutes`, `log.retention.hours`). The default is 168 hours (7 days). `-1` means unlimited (no time-based deletion).

The retention check evaluates each closed segment: if the segment's **largest timestamp** (the maximum event-time timestamp of all records in the segment) is older than `now - retention.ms`, the segment is eligible for deletion. If no timestamp is available (records were produced without timestamps), the segment's **last modified time** on disk is used as a fallback.

Why the largest timestamp (not the smallest)? Because a segment contains records from a range of time. Using the oldest record's timestamp would delete segments containing recent records. Using the newest record's timestamp ensures every record in the segment has exceeded the retention age before the segment is deleted. A segment is deleted only when its newest record is old enough — guaranteeing every record has lived at least `retention.ms`.

**Q6. What is the difference between event-time and ingestion-time retention, and why does it matter for out-of-order data?**
A: **Event-time retention** uses the timestamp embedded in the record by the producer — when the event actually occurred. **Ingestion-time retention** uses the timestamp assigned by the broker when the record was appended to the log (`LogAppendTime` topic configuration).

The distinction matters for late-arriving data: if a producer sends a record with an event-time 6 days ago (e.g., a mobile device that was offline), a topic configured with 7-day retention using event-time will treat this record as 6 days old upon arrival. If another record in the same segment has a recent timestamp, the segment won't be deleted until that recent record ages out. But if the late record lands in a segment where all other records are also near-expiry, the segment containing the 6-day-old event could be deleted shortly after arrival — effectively giving that record less than its nominal retention.

For topics with `message.timestamp.type = CreateTime` (producer-set timestamps), configure careful validation: brokers can reject records whose timestamps are too far from the broker clock via `message.timestamp.difference.max.ms`. This prevents records with stale or future timestamps from distorting retention behavior.

**Q7. How does time-based retention interact with slow or stopped consumers?**
A: Time-based retention proceeds regardless of consumer state — the broker deletes old segments on schedule even if a consumer hasn't read them yet. A consumer that falls behind by more than the retention period loses access to unconsumed records: the records are deleted from the broker, the consumer's committed offset becomes invalid (it points to a deleted position), and the consumer receives an `OffsetOutOfRangeException` (or, depending on `auto.offset.reset`, resets to `earliest` — which is now after the deleted data — or `latest`).

This is a critical operational risk: **consumer lag exceeding retention causes irrecoverable data loss for that consumer**. Monitoring alerts should fire when `consumer_lag_seconds >= retention_ms * 0.7` — giving the team time to either speed up the consumer or extend retention before the consumer falls off the log. Setting retention longer than needed is cheap insurance against this scenario.

**Q8. How is time-based retention configured at the topic level vs. the broker level?**
A: Broker-level defaults (in `server.properties`) apply to all topics that don't override them:
- `log.retention.hours = 168` (7 days default)
- `log.retention.bytes = -1` (unlimited default)

Topic-level overrides (via `kafka-configs.sh` or the Admin API) apply only to the specific topic:
```bash
kafka-configs.sh --alter --entity-type topics --entity-name my-topic \
  --add-config retention.ms=86400000  # 1 day
```

Topic-level config keys drop the `log.` prefix: `retention.ms`, `retention.bytes`, `segment.bytes`, `segment.ms`, `cleanup.policy`. Topic-level settings take precedence over broker defaults. This allows a multi-tenant Kafka cluster to serve topics with very different retention needs — a transient processing topic might have 1-hour retention while a compliance audit topic has 7-year retention — without separate clusters.

**Q9. What is `log.segment.ms` (or `log.roll.hours`) and how does it affect time-based retention precision?**
A: `log.segment.ms` (default 7 days, configurable via `log.roll.hours`) defines the maximum age of the active segment before it is forcibly rolled (closed and a new active segment opened), even if the segment hasn't reached its byte size limit. This is the primary lever for controlling retention precision.

The interaction: if the active segment rolls every 7 days and retention is set to 7 days, a record written at the beginning of a segment may not become eligible for deletion until the segment rolls (up to 7 days) and then its age exceeds retention (another 7 days) — effectively 14 days of retention for some records. For retention to work as expected, segment roll interval should be significantly shorter than retention. Rule of thumb: `segment.ms ≤ retention.ms / 4`. For a 1-day retention topic, roll segments every 6 hours; for a 7-day retention topic, the default 7-day roll interval is too coarse — set `segment.ms = 3600000` (1 hour) for cleaner retention behavior.

## Section 3: Size-Based Retention

**Q10. How does Kafka's size-based retention work mechanically?**
A: Configured via `log.retention.bytes` (default `-1`, unlimited). This is the maximum total size **per partition** — not the total topic size. When the sum of all closed segment sizes for a partition exceeds `retention.bytes`, the log cleaner deletes the oldest closed segments one at a time until the total falls back below the threshold.

Key detail: the active segment's size does not count toward the `retention.bytes` threshold until it is closed. This means the actual disk usage per partition can temporarily exceed `retention.bytes` by up to one segment's worth of data (`log.segment.bytes`, default 1GB). Total disk usage for a topic at any point is bounded by approximately `(retention.bytes + segment.bytes) × partition_count`.

**Q11. How do you calculate total disk usage for a topic given its retention and partition configuration?**
A: Worst-case disk usage for a topic:

```
disk_per_partition ≈ retention.bytes + segment.bytes (active segment overhead)
                   ≈ retention.bytes × 1.1 (10% buffer for the active segment)

total_topic_disk = disk_per_partition × partition_count × replication_factor
```

Example: a topic with 12 partitions, replication factor 3, `retention.bytes = 10GB`:
```
disk_per_partition ≈ 10GB + 1GB = 11GB
total_topic_disk = 11GB × 12 × 3 = 396GB across the cluster
disk_per_broker = 396GB / broker_count
```

For time-based-only retention (no `retention.bytes`), disk usage is unbounded — it equals `write_rate × retention.ms`. A topic writing 100MB/sec with 7-day retention uses approximately `100MB/s × 604,800s = ~57TB per replica`. Time-based retention without a size bound requires careful capacity planning based on write throughput.

**Q12. What is the interaction when both `retention.ms` and `retention.bytes` are configured?**
A: When both are set, Kafka applies them with **OR semantics**: a segment is eligible for deletion if *either* condition is met — it is old enough (time-based) OR the total partition size exceeds the limit (size-based). The more aggressive constraint "wins" by causing earlier deletion.

This means: on a quiet topic where the partition size stays small, time-based retention governs — data ages out after `retention.ms` regardless of size. On a bursty topic during a write spike, size-based retention may trigger first — segments are deleted to stay under the size limit even if they haven't reached their age threshold. The effective retention is `min(time_before_age_expires, time_before_size_limit_triggers)`.

Design implication: setting both provides a hard storage cap (size) and a minimum freshness guarantee (time). The size cap prevents unexpected disk exhaustion; the time cap ensures data doesn't survive indefinitely if the size cap is never reached. Both are complementary safeguards.

**Q13. Why is `retention.bytes` a per-partition limit rather than a per-topic limit, and what is the operational consequence?**
A: Kafka's storage is partition-level — each partition is an independent ordered log, stored on a specific broker, with no cross-partition coordination. Implementing a per-topic size limit would require coordination across all brokers holding the topic's partitions, which adds complexity and a potential bottleneck.

Operational consequence: when the write load is unevenly distributed across partitions (partition skew), some partitions hit `retention.bytes` and delete data while others remain well under the limit. The per-partition limit does not bound total topic storage to `retention.bytes × partition_count` from below — underloaded partitions use less. However, it does guarantee that **no single partition** exceeds `retention.bytes` (plus one active segment overhead). To bound total topic storage, size the partitions and set `retention.bytes` such that `retention.bytes × partition_count × replication_factor ≤ cluster_disk_budget_for_this_topic`.

## Section 4: Log Compaction

**Q14. What is log compaction and how does it differ from time/size-based deletion?**
A: Log compaction (`cleanup.policy = compact`) is a retention mechanism that removes **duplicate keys** from the log, retaining only the latest value for each key. Unlike time/size-based deletion (which removes entire segments based on age or volume), compaction operates within a segment — it identifies older records whose key has been superseded by a newer record and removes them.

The result: the log can grow indefinitely in terms of distinct keys but never stores redundant history. A compacted log is equivalent to the current state of a key-value store — replaying it from the beginning produces the same result as replaying an uncompacted version, just faster (fewer records to process). Compaction is the foundation for `KTable` and `GlobalKTable` semantics in Kafka Streams, and for database change data capture (CDC) topics where the latest row value per primary key must be retained indefinitely.

**Q15. How does log compaction work mechanically — what is the "head" and "tail" of the log?**
A: A Kafka partition log is divided into two conceptual regions:
- **Head**: the most recently written portion — uncompacted, contains the full history of recent writes including duplicates. The active segment and recently closed segments that haven't been compacted yet. This is where producers write and where consumers reading recent data operate.
- **Tail**: older portions that have been compacted — each key appears at most once, with its latest value. Consumers reprocessing from the beginning read through the compacted tail (efficient — no duplicate keys) and then through the head.

The compaction process (run by the `log.cleaner` background threads) periodically selects segments from the head that have reached the compaction threshold (controlled by `min.cleanable.dirty.ratio`, default 0.5 — compact when at least 50% of records in the segment have been superseded), reads them, deduplicates by key, and writes the compacted result to new segment files in the tail. The original uncompacted segments are deleted after compaction completes.

**Q16. What is a tombstone record and how long does it persist in a compacted topic?**
A: A tombstone is a record with a non-null key and a **null value**. In a compacted topic, a tombstone signals that the key should be deleted — it supersedes all previous values for that key. The compaction process retains the tombstone and removes all prior records for that key.

However, the tombstone itself must eventually be deleted — otherwise the "deleted" key persists as a null-value entry forever. `delete.retention.ms` (default 86,400,000ms = 24 hours) controls how long tombstones are retained after compaction. After `delete.retention.ms` has elapsed since the tombstone was written, subsequent compaction runs will remove it. During the `delete.retention.ms` window, consumers that read the compacted topic will see the tombstone and know the key was deleted. After the tombstone is removed, consumers reading from the beginning will simply not see that key — as if it never existed.

This creates a constraint for consumers of compacted topics: they must read the topic at least once within `delete.retention.ms` after a deletion to observe the tombstone and apply the delete locally. A consumer that was offline for longer than `delete.retention.ms` after a deletion may miss the tombstone and retain the stale value from its local state — a consistency bug.

**Q17. What is `cleanup.policy = compact,delete` and when is it used?**
A: Combining compaction and deletion (`cleanup.policy = compact,delete`) means: first deduplicate by key (compaction), then apply time/size-based deletion to the compacted result. The log retains the latest value per key for as long as the time or size retention allows — after which even the latest value is deleted.

Use case: a topic that represents current state per key (like a `KTable`) but where old keys eventually become irrelevant and should be reclaimed. Example: a user activity status topic — compaction ensures each user's latest status is always available; the combined delete policy ensures that users who haven't been active in 90 days are eventually removed from the log entirely, preventing unbounded growth from inactive users. Without the `delete` component, a compacted topic grows with the cardinality of its key space forever — every user who ever existed occupies one entry, regardless of activity.

## Section 5: Retention in Other Systems

**Q18. How does Elasticsearch Index Lifecycle Management (ILM) implement retention?**
A: Elasticsearch ILM manages index retention through a state machine with four phases: **Hot** (actively indexed, highest performance), **Warm** (read-only, potentially merged and shrunk for efficiency), **Cold** (infrequently accessed, potentially moved to cheaper storage), **Delete** (removed). Retention is enforced in the delete phase.

Transition between phases is triggered by: index age (`min_age`), index size (`max_size`), or document count (`max_docs`). A typical log retention policy: hot for 1 day (recent logs, frequently searched), warm for 7 days (available but optimized for storage), cold for 30 days (rarely searched, frozen), deleted after 90 days. ILM policies are attached to index templates — new indices created matching the template automatically follow the lifecycle. This is fundamentally a time-based retention policy wrapped in a multi-tier storage model, allowing gradual cost reduction rather than abrupt deletion.

**Q19. How does Amazon S3 implement retention, and what are the two mechanisms?**
A: S3 provides two retention mechanisms:
- **S3 Lifecycle Rules**: rules attached to a bucket or prefix that automatically transition objects to cheaper storage classes (Standard → Standard-IA → Glacier → Glacier Deep Archive) or permanently delete them after a specified number of days. Transitions are time-based on object age (days since creation). Deletion rules can target current versions, previous versions (for versioned buckets), and incomplete multipart uploads. This is the primary tool for implementing data retention policy in S3 — archive cold data cheaply, delete after maximum retention expires.
- **S3 Object Lock**: the inverse of deletion — prevents objects from being deleted before a specified retention period or until a legal hold is released. Used for regulatory compliance (WORM — Write Once Read Many). Configured in Governance or Compliance mode; Compliance mode prevents even the root account from deleting objects, making it truly tamper-proof.

Lifecycle rules apply with a granularity of one day (not hours or minutes) — S3 runs lifecycle transitions once per day. An object expires at midnight UTC on the expiry date; actual deletion may lag by a few hours.

**Q20. How do relational databases implement time-based retention, and what is the performance implication of each approach?**
A: Three approaches, each with different performance profiles:
- **Row-level DELETE with a scheduled job**: `DELETE FROM events WHERE created_at < NOW() - INTERVAL '90 days'`. Simple, but at scale: a bulk DELETE acquires row-level locks, generates write-ahead log (WAL) entries for every deleted row, triggers vacuum/autovacuum (PostgreSQL), and may run for hours — impacting production query performance during the deletion window. Not suitable for tables with billions of rows or strict latency SLAs.
- **Partition drop**: partition the table by date (daily or monthly range partitions). Delete old data by dropping the entire partition: `DROP TABLE events_2023_01` (PostgreSQL) — an O(1) metadata operation that reclaims storage instantly without touching individual rows, generating no WAL for row deletions. The fastest approach; requires upfront partitioning schema design.
- **TTL columns with background sweeping**: add a `expires_at` column; a background job deletes rows where `expires_at < NOW()` in small batches, throttled to avoid impacting production. Slow but gentle — doesn't spike I/O or lock contention. Suitable for tables with moderate retention requirements where partition-drop isn't feasible.

**Q21. How does Redis implement retention at the key level?**
A: Redis provides per-key TTL (Time-To-Live) via the `EXPIRE key seconds` or `PEXPIRE key milliseconds` commands. When a key's TTL expires, Redis removes it using one of two mechanisms:
- **Lazy expiry**: the key is not immediately deleted on TTL expiry; it is deleted when the key is next accessed and Redis checks its TTL. No background work, but expired keys consume memory until accessed.
- **Active expiry**: Redis runs a background sweep every 100ms, sampling a fraction of keys with TTLs and deleting any that have expired. This runs until fewer than 25% of sampled keys are expired, then stops — preventing the sweep from consuming excessive CPU. The combination of lazy + active expiry means expired keys are removed within seconds to a few minutes of expiry under normal conditions.

Redis also supports **maxmemory** policies (e.g., `allkeys-lru`, `volatile-lru`) that evict keys under memory pressure — a size-based retention mechanism at the Redis level. `volatile-lru` evicts keys with TTLs first; `allkeys-lru` evicts any key. These are not configurable per-key but apply globally when `maxmemory` is reached.

**Q22. How do time-series databases like Prometheus handle retention?**
A: Prometheus implements both time-based and size-based retention via command-line flags:
- `--storage.tsdb.retention.time` (default 15 days): delete data older than this threshold. Prometheus stores data in 2-hour block files; an entire block is deleted when all its data exceeds the retention age.
- `--storage.tsdb.retention.size` (default 0 = disabled): delete oldest blocks when total TSDB directory size exceeds this value. Acts as a storage cap.

Both flags follow OR semantics: whichever is more restrictive triggers deletion first. Prometheus does not support per-metric retention — retention is global across all metrics. For long-term retention of specific metrics, the common pattern is to remote-write to a long-term storage backend (Thanos, Cortex, VictoriaMetrics) that manages its own retention independently, while Prometheus's local TSDB holds only the short-term window needed for alerting and dashboards.

## Section 6: Failure Modes & Anti-patterns

**Q23. What is "consumer falling off the log" and what are the operational symptoms?**
A: Consumer falling off the log occurs when a Kafka consumer's committed offset points to a position that has been deleted by retention. The consumer attempts to fetch from an offset that no longer exists. Symptoms:
- **`OffsetOutOfRangeException`**: the consumer receives this error from the broker when fetching from a deleted offset.
- **`auto.offset.reset` behavior**: if `auto.offset.reset = earliest`, the consumer resets to the current earliest available offset — silently skipping all deleted data (data loss from the consumer's perspective). If `auto.offset.reset = none`, it throws an exception and the consumer fails.
- **Monitoring blind spot**: many teams only monitor consumer lag in terms of message count (`records-lag`), not in terms of time (`consumer-lag-seconds`). A consumer that was paused for 8 days on a 7-day retention topic shows zero records-lag after the reset (it jumped to earliest) but has permanently lost 8 days of data.

Prevention: monitor `consumer-lag-seconds` (or equivalently, compare the consumer's committed offset timestamp to the current broker high-watermark timestamp). Alert well before lag reaches the retention boundary.

**Q24. What is the "retention cliff" problem when reducing retention on a high-throughput topic?**
A: Reducing `retention.ms` on an existing topic (e.g., from 7 days to 1 day) triggers an immediate mass deletion: the next retention check sweep deletes all segments older than 1 day simultaneously — potentially terabytes of data deleted in minutes. Consequences:
- **Disk I/O spike**: the broker's disk I/O for deletions competes with normal read/write traffic, potentially causing latency spikes for producers and consumers.
- **Filesystem pressure**: deleting many large files rapidly can cause inode exhaustion or OS-level filesystem pressure.
- **Consumer disruption**: slow consumers that were relying on data older than the new retention window suddenly lose access to data they haven't yet processed.

Mitigation: reduce retention gradually in steps (7 days → 3 days → 1 day, with a pause between steps to allow the retention check to run and consumers to catch up). Perform reduction during low-traffic periods. Alert on consumer lag before reducing.

**Q25. What is the "segment too large to retire" problem and how does it manifest?**
A: If `log.segment.bytes` (default 1GB) is larger than the write volume during `retention.ms`, the active segment never fills up and never rolls — it stays open indefinitely as the active segment. Since the active segment is never eligible for deletion, data older than `retention.ms` accumulates in it and is never deleted. Symptom: a topic with a 24-hour retention policy retains days or weeks of data because the single active segment spans the entire history.

Fix: set `log.segment.ms` (or `log.roll.hours`) to force segment rolling by time rather than size. For a 24-hour retention topic: `segment.ms = 3600000` (1-hour rolling). This ensures segments close every hour, allowing retention to delete segments promptly as they age past 24 hours. General rule: `segment.ms ≤ retention.ms / 4` for predictable retention behavior.

**Q26. What is the "compaction stalling" problem and what causes it?**
A: Compaction stalling occurs when a compacted topic's cleaner thread falls behind the write rate — the head of the log grows faster than the cleaner can compact. Symptoms: the `kafka.log:type=LogCleaner,name=max-dirty-percent` metric climbs and stays above `min.cleanable.dirty.ratio`; log size grows without bound; consumers reading from the beginning process more and more duplicate keys.

Causes: (1) **too few cleaner threads** — `log.cleaner.threads` (default 1) is insufficient for the volume of compactable topics; (2) **`min.cleanable.dirty.ratio` too high** — the cleaner only triggers when >50% of records are dirty (superseded); on a slow-write topic, this threshold is never reached so compaction never runs; (3) **`max.compaction.lag.ms` exceeded** — a record in the head that is waiting to be compacted has aged past the maximum lag — the cleaner is too far behind. Fix: increase `log.cleaner.threads`, lower `min.cleanable.dirty.ratio` to trigger more frequent compaction, and monitor `max-dirty-percent`.

**Q27. What is the "tombstone reappearance" bug in consumers of compacted topics?**
A: Tombstone reappearance occurs when a consumer of a compacted `KTable` topic misses a tombstone (null-value delete record) because it was offline for longer than `delete.retention.ms`. The timeline:
1. Record `(key=K, value=V)` is written; consumer reads it and stores the state `K=V`.
2. Tombstone `(key=K, value=null)` is written; consumer is offline and misses it.
3. `delete.retention.ms` expires; the compaction cleaner removes both the tombstone and all prior records for key `K`.
4. Consumer comes back online, reads from its committed offset — the tombstone is gone (deleted), the consumer never learns that `K` was deleted, and its local state still contains `K=V`.
5. The consumer's local view has a "ghost" key that no longer exists in the source of truth.

Prevention: set `delete.retention.ms` long enough that consumers are guaranteed to read it before it expires. Monitor consumer lag against `delete.retention.ms` — if a consumer can be offline for longer than `delete.retention.ms`, this bug is possible. Additionally, periodically rebuild the consumer's local state from a full topic replay (starting from `earliest`) to catch any tombstones that were missed.

**Q28. What is "retention misconfiguration causing compliance violation" and how does it happen?**
A: Compliance violations from retention misconfiguration take two forms:
- **Insufficient retention (data deleted too soon)**: regulations like FINRA require financial trade records to be retained for at least 6 years. If a Kafka topic holding trade records has `retention.ms = 7 days`, 6 years of trades are deleted — a regulatory violation and potential legal liability. Root cause: applying the same retention defaults to all topics without considering the regulatory classification of each topic's data.
- **Excessive retention (data kept too long)**: GDPR's right to erasure requires that personal data is deleted upon request and that data is not kept beyond its stated purpose. A topic retaining personal data for 7 years when the stated purpose is fulfilled in 30 days violates data minimization principles. Root cause: never configuring an explicit retention on topics containing personal data, defaulting to broker-level maximums.

Prevention: tag each topic with its data classification (`PII`, `financial`, `operational`) in a schema registry or metadata catalog. Enforce retention configuration as part of topic provisioning: `PII` topics require an explicit retention ≤ data minimization requirement; `financial` topics require retention ≥ regulatory minimum. Automate compliance checks in CI/CD pipelines that provision Kafka topics.

## Section 7: Trade-offs & Decision-Making

**Q29. How do you choose between time-based and size-based retention for a new topic?**
A: Work backward from what constraint is primary:
- **Business or compliance requirements define the time**: if data must be accessible for at least N days (for reprocessing, audit, consumer catch-up) or at most M days (for GDPR compliance), `retention.ms` is the primary config. Set it to satisfy both the minimum and maximum: `min_required_days ≤ retention_days ≤ max_allowed_days`. Add `retention.bytes` as a secondary cap to prevent unexpected disk exhaustion if the write rate spikes.
- **Disk budget defines the size**: if disk is the binding constraint and the time window is flexible ("as much history as fits in 500GB"), `retention.bytes` is the primary config. The effective retention window varies with write throughput — plan that at minimum it covers the consumer's maximum expected lag.
- **Use both for robustness**: in practice, setting both provides two independent safety nets. Time-based ensures data doesn't accumulate indefinitely on low-volume topics; size-based ensures disk doesn't fill on high-volume topics.

**Q30. What retention length is appropriate for a topic used as a Kafka Streams changelog or KTable source?**
A: Topics used as `KTable` sources or Kafka Streams changelog topics need special retention consideration:
- **`KTable` source topics** should use `cleanup.policy = compact` (not delete) to ensure the full current state is always available for rebuilding the KTable from scratch. Time-based or size-based deletion on a KTable topic risks deleting the latest value for a key — the KTable would have a gap in its state after a consumer group reset or new instance startup. Compacted topics are the correct choice; they retain the latest value per key indefinitely.
- **Changelog topics** (internal Kafka Streams state store backups) should retain data long enough to rebuild the state store from scratch. If standby replicas are used, shorter changelog retention is acceptable (the standby can catch up quickly from its local state). If standby replicas are not used, changelog retention must be at least as long as the maximum expected recovery time to avoid a situation where recovery requires replaying beyond the available log.
- **Never use time-based deletion alone for KTable source topics**: a compacted topic with no delete policy ensures the KTable always has a complete view; adding `compact,delete` is acceptable only if the key space is bounded and old keys genuinely become irrelevant.

**Q31. What is the "data lake vs. Kafka" retention architecture and when do you need both?**
A: Kafka is designed for short-to-medium retention (hours to weeks) of high-throughput streaming data — it is optimized for sequential reads by consumers catching up to the tail. It is not a data lake or long-term archive: storing 7 years of data in Kafka is expensive (Kafka's storage format is not columnar and doesn't compress as efficiently as Parquet), operationally complex (partition count must accommodate total historical volume), and architecturally mismatched (Kafka consumers read sequentially, not via SQL analytics).

The typical architecture: **Kafka for short-term retention** (1–30 days — enough for consumer catch-up, reprocessing after bugs, and real-time stream processing); **data lake (S3, GCS, HDFS)** for long-term retention (months to years, in Parquet or ORC format, queryable by Spark, Athena, BigQuery). A Kafka Connect S3 sink connector streams records from Kafka to S3 in micro-batches as they arrive, maintaining long-term history cheaply while Kafka retains only the recent window. Kafka retention can then be set aggressively short (1–3 days) since S3 has the archive. This separation optimizes each system for what it does best.

**Q32. How does retention interact with Kafka's exactly-once semantics (EOS) and transactional producers?**
A: Transactional producers use a `producer.id` and `epoch` to maintain idempotency across retries, stored in the broker's `__transaction_state` topic. If a topic's retention deletes records that were part of an open transaction, the transaction's state becomes inconsistent — records the producer thinks it committed may no longer exist, and the broker may have lost the idempotency context.

More commonly: the `__consumer_offsets` topic (where consumer group offsets are stored) has its own retention (`offsets.retention.minutes`, default 10,080 = 7 days). If a consumer group is inactive for longer than this, its committed offsets are deleted. When the consumer group becomes active again, it has no committed offset — it resets to `auto.offset.reset`. If the data topic's retention is shorter than `offsets.retention.minutes`, the consumer's saved position may point to already-deleted data even immediately after it resumes. Configure `offsets.retention.minutes ≥ data_topic_retention_days × 1440` (minutes per day) to ensure offsets outlive the data they reference.

## Section 8: Scenario / System Design Style Questions

**Q33. "A Kafka topic for order events is growing faster than expected. The team is running out of disk. They want to reduce retention from 7 days to 1 day immediately. Walk through the risks and a safe execution plan."**
A: Risks of immediate reduction:
1. **Consumers fall off the log**: any consumer more than 1 day behind loses access to data it hasn't yet processed. Audit all consumer groups: `kafka-consumer-groups.sh --describe --all-groups`. Identify any group with lag > 1 day's worth of messages.
2. **Retention cliff disk spike**: deleting 6 days of accumulated data simultaneously stresses broker I/O and potentially disk subsystem. On a 10TB topic, this deletes ~8.5TB in one retention sweep cycle — potentially minutes of heavy deletion I/O.
3. **Irreversibility**: deleted data is gone. If any downstream system needs to reprocess from more than 1 day ago, the data will be unavailable.

Safe execution plan:
1. **Identify slow consumers** and either speed them up (add instances) or snapshot their current position (read remaining data to a separate store before reducing retention).
2. **Reduce in steps**: `7 days → 4 days` (wait 24 hours, monitor I/O and consumers), `4 days → 2 days` (wait 24 hours), `2 days → 1 day`. Each step triggers deletion of only ~3 days, not 6.
3. **Schedule during low-traffic window**: run the final reduction step at night or on a weekend.
4. **Monitor during reduction**: watch broker disk I/O (`BytesInPerSec`, `BytesOutPerSec`), consumer group lag, and topic size metrics.
5. **Consider size-based retention instead**: if the problem is disk growth, set `retention.bytes` per partition (e.g., 50GB/partition) as a storage cap rather than reducing the time window. This bounds disk while preserving data for consumers that are within the size window.

**Q34. "Design the retention configuration for a multi-tenant analytics platform that uses Kafka. Different tenants have different data classification: Tenant A has financial data (5-year regulatory minimum), Tenant B has PII/GDPR-governed data (maximum 90-day retention), Tenant C has operational metrics (short-term, 24 hours is sufficient)."**
A: Per-tenant topic configuration (stored in a topic registry, enforced at provisioning time):

**Tenant A — Financial data**:
```
cleanup.policy = delete
retention.ms = 157,766,400,000  # 5 years (in ms)
retention.bytes = -1            # no size limit — must keep all data
```
But: storing 5 years of data in Kafka is expensive. Architecture: set Kafka retention to 30 days, use Kafka Connect S3 sink to archive to S3 with 5-year S3 lifecycle policy. S3 Object Lock (Compliance mode) prevents premature deletion. Kafka is for recent window processing; S3 is the regulatory archive.

**Tenant B — PII/GDPR**:
```
cleanup.policy = compact,delete
retention.ms = 7,776,000,000    # 90 days
delete.retention.ms = 86,400,000 # tombstone retained 1 day
```
Compaction ensures that when a user exercises the right to erasure (a tombstone is written for their key), the record is removed promptly. The `delete` component ensures data older than 90 days is removed even if no explicit erasure was requested. Additionally: GDPR requires the ability to delete individual users' data — compaction + tombstones enable key-level deletion; ensure `delete.retention.ms` is long enough that all consumers see the tombstone before it expires.

**Tenant C — Operational metrics**:
```
cleanup.policy = delete
retention.ms = 86,400,000       # 24 hours
retention.bytes = 10737418240   # 10GB per partition cap
segment.ms = 3600000            # 1-hour segments for prompt deletion
```
Short retention, size-capped to prevent unexpected spikes from swamping disk. 1-hour segments ensure data is promptly deleted as it ages past 24 hours.

**Q35. "You're designing a Kafka topic for a user-profile CDC stream that will be read by 10 Kafka Streams instances running KTables. What retention policy do you configure and why?"**
A: A CDC stream feeding KTables requires **log compaction** as the primary retention policy. Reasoning:

- **Why compaction**: `KTable` semantics require that replaying the topic from the beginning produces the complete current state. If time-based deletion removes old records, a new Kafka Streams instance rebuilding its KTable misses keys that haven't been updated recently — its state is incomplete. Compaction retains the latest value per key forever, ensuring full state reconstruction is always possible.
- **Why not deletion-only**: a user profile that hasn't changed in 6 months would be deleted by a 7-day retention policy — the KTable would think the user doesn't exist.
- **Combined policy for bounded growth**: if the user base is bounded (users eventually churn and are deleted), `compact,delete` with `retention.ms = 365_days` is appropriate — compaction keeps current profiles indefinitely, but profiles whose last update was more than a year ago (indicating fully churned users who had a final delete tombstone processed long ago) are eventually removed.
- **`delete.retention.ms` tuning**: Kafka Streams KTable consumers may restart and replay from the beginning. Set `delete.retention.ms` long enough to cover the maximum time a KTable might be offline (including planned maintenance): at minimum 7 days. If a KTable is always running with standby replicas, 24 hours is sufficient (standbys replay only the delta).
- **Topic config**:
```
cleanup.policy = compact
min.compaction.lag.ms = 0
delete.retention.ms = 604800000  # 7 days for tombstones
segment.ms = 86400000            # daily segment rolling
```

**Q36. "Prometheus is running out of disk. Local retention is set to 15 days. Walk through your options in order of preference."**
A:
1. **Add size-based retention as an immediate safety valve**: `--storage.tsdb.retention.size = 80%_of_available_disk`. This prevents Prometheus from filling the disk regardless of time-based retention. Prometheus will delete oldest blocks to stay within the size limit.
2. **Reduce local retention for non-critical metrics**: reduce `--storage.tsdb.retention.time` to 7 or 5 days if that's sufficient for your alerting and dashboarding needs. Historical queries beyond that window can use long-term storage.
3. **Offload to long-term storage (Thanos, Cortex, or VictoriaMetrics)**: configure `remote_write` to send all metrics to a long-term store. Once remote_write is confirmed working, reduce local TSDB retention aggressively (2 days is sufficient if remote_write latency is low and the long-term store handles historical queries). Local Prometheus becomes a short-window alerting buffer; the remote store handles analytics.
4. **Apply recording rules to reduce cardinality**: high-cardinality metrics (many label combinations) consume disproportionate storage. Identify the top storage-consuming metrics via `tsdb analyze` and add recording rules that pre-aggregate high-cardinality metrics into lower-cardinality summaries. Drop unused label dimensions that are not queried.
5. **Drop unused metrics via relabeling**: add `metric_relabel_configs` to drop metrics that are scraped but never used in any alert or dashboard. Use `prometheus-unused-metrics` tooling to identify candidates.

**Q37. "A consumer group processing financial transactions fell behind by 9 days. The topic has 7-day retention. The consumer's committed offset now points to deleted data. What do you do?"**
A: This is a data loss incident — the 2 days of transactions between day 7 and day 9 of consumer lag are permanently gone from Kafka. The response:

**Immediate triage**:
1. **Stop the consumer** to prevent it from resetting to `earliest` or `latest` automatically and losing its position metadata.
2. **Determine exact gap**: use `kafka-consumer-groups.sh --describe` to find the consumer's committed offset and `kafka-log-dirs.sh` to find the earliest available offset per partition. The gap = records between earliest_available and committed_offset.
3. **Assess data availability**: are the missing 2 days available elsewhere? Check: the data lake / S3 archive (if a Kafka Connect sink was running), the source system (database transaction logs, upstream API), or any downstream systems that already processed the records (can a downstream processed result be used to reconstruct the missing transactions?).

**Recovery options** (in order of preference):
1. **Replay from archive**: if S3 or another archive has the data, write a one-time job to replay the missing records back into a recovery Kafka topic; the consumer processes the recovery topic, then switches back to the main topic at `earliest` available offset.
2. **Replay from source**: if the source database has transaction logs covering the gap, re-emit the missing transactions from the source.
3. **Acknowledge gap and document**: if no recovery source exists, document the exact gap (offsets, estimated record count, time window) for audit purposes. Reset the consumer to `earliest` (it will start from the oldest available data, skipping the gap). Flag the incident for compliance review if financial records are involved — this may be a regulatory reporting event.

**Prevention**: the fundamental fix is to monitor `consumer-lag-seconds` and alert before lag approaches retention. Set `max_consumer_lag_hours ≤ retention_hours × 0.7` as the alert threshold. For financial topics, set retention to at least 30 days regardless of normal consumer performance.

## Key Concepts Cheat Sheet

| Term                          | One-line definition                                                                                          |
|---                            |---                                                                                                           |
| `retention.ms`                | Maximum age of a segment before deletion; data older than this may be deleted at the next check interval     |
| `retention.bytes`             | Maximum total size of all closed segments per partition; oldest deleted when exceeded                        |
| Log segment                   | Unit of Kafka log storage (one `.log` file); retention acts on whole segments, not individual records        |
| Active segment                | Currently open segment being written to; never deleted by retention regardless of age or size                |
| `log.segment.ms`              | Maximum age before active segment is force-rolled; controls how promptly retention can act on new data       |
| `log.retention.check.interval.ms` | How often the retention check sweep runs (default 5 min); data persists this long past expiry at most  |
| `file.delete.delay.ms`        | Delay between marking a segment for deletion and removing it from disk; allows in-flight readers to drain    |
| `cleanup.policy`              | `delete` (time/size retention), `compact` (deduplication), or `compact,delete` (both)                       |
| Log compaction                | Retains only the latest value per key; removes superseded records; head (recent) is uncompacted             |
| Tombstone                     | Record with null value signaling key deletion in a compacted topic; retained for `delete.retention.ms`      |
| `delete.retention.ms`         | How long tombstones are retained before being removed by compaction; consumers must read within this window  |
| `min.cleanable.dirty.ratio`   | Fraction of log that must be "dirty" (superseded) before compaction triggers (default 0.5)                  |
| Consumer falling off the log  | Consumer's committed offset points to deleted data; data loss for that consumer                              |
| Retention cliff               | Reducing retention dramatically triggers a mass deletion event causing I/O spikes and consumer disruption   |
| `offsets.retention.minutes`   | How long inactive consumer group offsets are retained; should be ≥ data topic retention to avoid offset loss |
| ILM (Elasticsearch)           | Index Lifecycle Management: hot/warm/cold/delete phases with age- or size-based transition triggers         |
| S3 Lifecycle Rules            | Time-based rules transitioning objects to cheaper storage classes or deleting them                          |
| S3 Object Lock                | Prevents deletion before a retention date; Compliance mode is tamper-proof (even root can't delete)         |
| Partition drop                | O(1) deletion of a PostgreSQL/MySQL range partition; replaces `DELETE WHERE date < X` for time-series expiry|
| WORM                          | Write Once Read Many — data can be written but not modified or deleted; S3 Object Lock implements this      |

Name "consumer falling off the log" proactively whenever time-based retention is discussed, and connect it to monitoring (`consumer-lag-seconds` vs `retention.ms`). The segment-as-unit-of-deletion point (active segment is never deleted; effective retention = configured retention + segment roll interval) separates candidates who've operated Kafka from those who've only read about it. For the log compaction section: be precise about tombstones and `delete.retention.ms` — the tombstone reappearance bug is a real production issue that tests deeper understanding. Connecting retention policy to compliance requirements (GDPR maximum retention, financial regulatory minimum retention) shows business-awareness that senior engineers need.
