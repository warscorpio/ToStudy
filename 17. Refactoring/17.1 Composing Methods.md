## Part 1 — Theory & Interview Q&A

## Topic A: Foundations of Composing Methods

### Section A1: Fundamentals

**Q1. What does "Composing Methods" mean in refactoring, and why is it a distinct category?**
A: "Composing Methods" is a family of refactoring techniques focused on how method bodies are structured and sized. Coined by Martin Fowler in *Refactoring: Improving the Design of Existing Software*, composing-method refactorings address the most common low-level problem in production code: methods that try to do too much. They do not change what a method does — only how that work is carved up, named, and expressed.

The category is distinct because its techniques operate at the statement and expression level (within a single method or between a small cluster of methods) rather than at the class or module level. Class-level refactorings (move method, extract class) deal with where responsibility lives; composing-method refactorings deal with whether a single unit of responsibility can be understood in one reading.

The core principle behind every technique in this family: **the code inside a method should be at one level of abstraction.** If a method mixes high-level policy ("process the order") with low-level mechanism ("iterate over the line items array and accumulate the sum"), readers are forced to context-switch mentally — a large source of bugs introduced during maintenance.

```
Before (mixed abstraction levels):
function checkout(cart) {
  let total = 0;
  for (const item of cart.items) {   // low-level loop
    total += item.price * item.qty;  // low-level arithmetic
  }
  if (total > 100) total *= 0.9;     // business rule mixed in
  sendEmail(cart.user, total);       // side effect
  db.save({ user: cart.user, total });
}

After (uniform abstraction level):
function checkout(cart) {
  const total = applyDiscounts(calculateTotal(cart));
  notifyUser(cart.user, total);
  persistOrder(cart.user, total);
}
```

**Q2. What are the most important composing-method refactorings, and how do they relate to each other?**
A: The core techniques and their relationships:

| Technique | Direction | Summary |
|---|---|---|
| **Extract Method** | splitting | Pull a code fragment into a named method |
| **Inline Method** | merging | Replace a trivially-simple method with its body |
| **Extract Variable** | naming | Give a complex expression a descriptive name |
| **Inline Temp** | simplifying | Remove a temp used only once |
| **Replace Temp with Query** | decoupling | Replace a local variable with a method call |
| **Split Temporary Variable** | clarifying | Give distinct variables to distinct assignments |
| **Remove Assignments to Parameters** | safety | Never mutate a parameter; assign to a local instead |
| **Replace Method with Method Object** | escalating | Move a complex method to its own class |
| **Substitute Algorithm** | rewriting | Replace a convoluted algorithm with a cleaner one |
| **Decompose Conditional** | readability | Extract condition and branches into named methods |

The techniques form a directed flow: you typically start with **Extract Method** (the workhorse), which reveals the need for **Extract Variable** (to name intermediate results), which may expose **Replace Temp with Query** (to eliminate temporary variables), which may eventually justify **Replace Method with Method Object** (when a method still has too many locals even after extraction). **Inline Method** and **Inline Temp** are the inverses — used when prior extraction over-decomposed or when a middle-man method adds no value.

**Q3. What is Extract Method, and when should it be applied?**
A: Extract Method takes a code fragment that can be grouped together and turns it into a method whose name explains the fragment's *purpose* (not its mechanics). It is the most widely applicable refactoring technique and the correct response to the most common code smell: a method that is too long.

Apply Extract Method when:
- A block of code requires a comment to explain what it does.
- A block of code is used in more than one place.
- A method is longer than fits on one screen (a rough heuristic: > 10–15 lines).
- A block operates at a noticeably lower level of abstraction than the surrounding code.
- A conditional expression or loop body is non-trivial.

```js
// Before:
function printOwing(order) {
  printBanner();

  // calculate outstanding
  let outstanding = 0;
  for (const d of order.details) {
    outstanding += d.amount;
  }

  // print details
  console.log(`name: ${order.name}`);
  console.log(`amount: ${outstanding}`);
}

// After Extract Method:
function printOwing(order) {
  printBanner();
  const outstanding = calculateOutstanding(order);
  printDetails(order, outstanding);
}

function calculateOutstanding(order) {
  return order.details.reduce((sum, d) => sum + d.amount, 0);
}

function printDetails(order, outstanding) {
  console.log(`name: ${order.name}`);
  console.log(`amount: ${outstanding}`);
}
```

The mechanics: (1) create a new method and name it after the intent; (2) copy the extracted code into it; (3) examine the extracted code for references to variables in the source method — those become parameters (if read-only) or return values (if assigned and used after the fragment); (4) replace the fragment in the source with a call to the new method; (5) run tests.

**Q4. What is the Single Level of Abstraction (SLA) principle, and how does it guide method composition?**
A: The Single Level of Abstraction principle states that all statements inside a method body should be at the same level of abstraction. High-level policy steps ("validate the request", "persist the result") should not be mixed with low-level mechanism steps ("iterate the array", "concatenate the strings", "check `if (x !== null && x !== undefined)`").

SLA is the diagnostic lens behind most composing-method refactorings. When you read a method and feel that some lines are "closer to the metal" than others, that is the SLA violation. The fix is almost always Extract Method — pull the low-level code into a method whose name restores it to the correct abstraction level.

```
Violation:
function handleRequest(req) {
  if (!req.headers['authorization']) throw new Error('Unauthorized'); // level: protocol
  const token = req.headers['authorization'].split(' ')[1];           // level: string parsing
  const user = jwt.verify(token, SECRET);                             // level: domain
  return processUserAction(user, req.body);                           // level: domain
}

SLA-compliant:
function handleRequest(req) {
  const user = authenticateRequest(req);    // level: domain
  return processUserAction(user, req.body); // level: domain
}

function authenticateRequest(req) {
  ensureAuthHeaderPresent(req);
  const token = extractBearerToken(req);
  return jwt.verify(token, SECRET);
}
```

### Section A2: Advanced Patterns

**Q5. When should you use Extract Method versus Replace Method with Method Object?**
A: Use Extract Method first — it handles the vast majority of long-method problems. Promote to Replace Method with Method Object (converting the method into its own class) only when Extract Method cannot fully decompose the method because too many local variables would have to be passed as parameters between the extracted sub-methods.

The diagnostic: count the number of parameters you would need to pass to the extracted helper methods. If extracting produces helpers that need 4+ parameters to do their work, those parameters are a disguised state — they belong together as fields of a class.

```js
// Method with excessive local state — hard to extract cleanly:
function renderChart(data, width, height, padding, colorScheme, fontConfig, gridConfig) {
  const xScale = computeXScale(data, width, padding);
  const yScale = computeYScale(data, height, padding);
  const points = mapDataToPoints(data, xScale, yScale);
  const gridLines = computeGridLines(width, height, padding, gridConfig);
  // ... 60 more lines, all using xScale, yScale, gridLines, colorScheme, fontConfig
}

// After Replace Method with Method Object:
class ChartRenderer {
  constructor(data, width, height, padding, colorScheme, fontConfig, gridConfig) {
    this.data = data;
    this.width = width;
    // ... all locals become fields
    this.xScale = this.computeXScale();
    this.yScale = this.computeYScale();
  }

  render() {
    const points = this.mapDataToPoints();
    const gridLines = this.computeGridLines();
    // ... clean, no argument lists
  }

  computeXScale() { /* uses this.data, this.width, this.padding */ }
  computeYScale() { /* uses this.data, this.height, this.padding */ }
  // ... each sub-method has access to all fields
}

// Caller:
function renderChart(data, width, height, padding, colorScheme, fontConfig, gridConfig) {
  return new ChartRenderer(data, width, height, padding, colorScheme, fontConfig, gridConfig).render();
}
```

**Q6. How does Decompose Conditional relate to Extract Method, and when is it its own technique?**
A: Decompose Conditional is a specialization of Extract Method applied specifically to conditionals. It is called out as a distinct technique because conditionals are the most frequent source of abstraction-level mixing, and because the three-part structure of a conditional (`if`/`then`/`else`) calls for three separate extractions:

1. Extract the **condition** into a method named after what is being tested.
2. Extract the **then-branch** into a method named after what happens when true.
3. Extract the **else-branch** into a method named after what happens when false.

```js
// Before:
if (!plan.isSummer() && usage > 100 || (plan.isSummer() && usage > 300)) {
  charge = usage * plan.summerRate + plan.extraCharge;
} else {
  charge = usage * plan.regularRate;
}

// After Decompose Conditional:
if (isOverUsageLimit(plan, usage)) {
  charge = overageCharge(plan, usage);
} else {
  charge = regularCharge(plan, usage);
}

function isOverUsageLimit(plan, usage) {
  return (!plan.isSummer() && usage > 100) || (plan.isSummer() && usage > 300);
}
function overageCharge(plan, usage) {
  return usage * plan.summerRate + plan.extraCharge;
}
function regularCharge(plan, usage) {
  return usage * plan.regularRate;
}
```

The result is that the top-level code reads as a domain statement ("if over usage limit, charge overage; else charge regular") with implementation details hidden.

## Topic B: Temporary Variables — Management and Elimination

### Section B1: Fundamentals

**Q7. What is Replace Temp with Query, and why is it often a prerequisite for Extract Method?**
A: Replace Temp with Query replaces a local variable that stores the result of an expression with a method call that evaluates the expression on demand. The expression is extracted into its own method; every reference to the temp in the original method is replaced with a call to that method.

It is a prerequisite for Extract Method because local variables are the most frequent obstacle to extraction. When you try to extract a fragment, you find that the fragment reads a temp that was computed earlier — you'd have to pass the temp as a parameter. If you first Replace Temp with Query, the extracted method can call the query method directly — no parameter needed.

```js
// Before — temp blocks extraction of the discount logic:
function itemPrice(item) {
  const basePrice = item.quantity * item.price;   // temp
  if (basePrice > 1000) {
    return basePrice * 0.95;
  } else {
    return basePrice * 0.98;
  }
}

// After Replace Temp with Query:
function itemPrice(item) {
  if (basePrice(item) > 1000) {
    return basePrice(item) * 0.95;
  } else {
    return basePrice(item) * 0.98;
  }
}

function basePrice(item) {
  return item.quantity * item.price;
}

// Now Extract Method on the discount logic is clean:
function itemPrice(item) {
  return discount(item);
}
function discount(item) {
  return basePrice(item) > 1000 ? basePrice(item) * 0.95 : basePrice(item) * 0.98;
}
```

**Caveat — performance**: Replace Temp with Query may call the expression multiple times. If the expression is expensive (a database query, a complex computation), cache the result (memoize the method, or keep the temp in performance-critical paths). Premature optimization is the wrong response; measure first.

**Q8. What is Split Temporary Variable, and what code smell does it fix?**
A: Split Temporary Variable addresses a temp variable that is assigned more than once and carries different meanings across those assignments. Reusing the same variable name for conceptually different values forces the reader to track the variable's "current meaning" throughout the method — a significant cognitive burden.

The fix: identify each distinct role the variable plays and introduce a separate, well-named variable for each.

```js
// Before — 'temp' means three different things:
function calculateDistanceAndForce(scenario) {
  let temp = scenario.primaryForce + scenario.secondaryForce; // role: combined force
  const twoSecs = 2;
  temp = (temp * twoSecs) / scenario.mass;                    // role: acceleration
  temp = scenario.initialVelocity + temp;                     // role: velocity
  return temp;
}

// After Split Temporary Variable:
function calculateDistanceAndForce(scenario) {
  const combinedForce = scenario.primaryForce + scenario.secondaryForce;
  const acceleration = (combinedForce * 2) / scenario.mass;
  const velocity = scenario.initialVelocity + acceleration;
  return velocity;
}
```

The rule: if a variable is assigned a value in one place and is reassigned a different kind of value later (not accumulating — accumulator patterns like `total += x` are the legitimate exception), it should be split. Each variable should be immutable after assignment where possible — assign once, read many times.

**Q9. What is Extract Variable (Introduce Explaining Variable), and when is it preferred over Extract Method?**
A: Extract Variable introduces a new local variable to hold the result of an expression, naming it to convey the expression's intent. It is the localized form of Replace Temp with Query — where Replace Temp with Query promotes the expression to a method, Extract Variable keeps it local.

Prefer Extract Variable (over Extract Method) when:
- The expression is used only in one method and extracting it as a method would create a helper with no reuse value.
- The method already has clean abstraction and you only need to name one intermediate result for clarity.
- The context is a complex conditional where naming the sub-conditions aids reading.

```js
// Before:
if (platform.toUpperCase().indexOf('MAC') > -1
  && browser.toUpperCase().indexOf('IE') > -1
  && wasInitialized() && resize > 0) {
  // ...
}

// After Extract Variable:
const isMacOS = platform.toUpperCase().indexOf('MAC') > -1;
const isIEBrowser = browser.toUpperCase().indexOf('IE') > -1;
const wasResized = resize > 0;

if (isMacOS && isIEBrowser && wasInitialized() && wasResized) {
  // ...
}
```

The reverse technique — Inline Temp — removes the variable if the name adds no clarity or the variable is used exactly once and the expression is already self-explanatory.

**Q10. What is "Remove Assignments to Parameters," and why is it a safety refactoring?**
A: Remove Assignments to Parameters addresses the practice of using a parameter variable as a general-purpose local variable by reassigning it. This is dangerous for two distinct reasons:

1. **Call-by-value confusion**: in most languages (Java, JavaScript, Python for primitives), parameters are passed by value — reassigning the parameter inside the method does not affect the caller's variable. Developers confusing this with pass-by-reference introduce subtle bugs.
2. **Semantic collision**: parameters communicate what was *passed in*; reassigning them erases that information. After the assignment, the variable's meaning has shifted — the reader can no longer trust it represents the original argument.

The fix: introduce a local variable for the new value.

```js
// Before — confusing: does the caller's 'discount' get modified?
function applyDiscount(inputVal, discount) {
  if (inputVal > 50) discount -= 2;   // mutates the parameter
  return inputVal - discount;
}

// After Remove Assignments to Parameters:
function applyDiscount(inputVal, discount) {
  let adjustedDiscount = discount;
  if (inputVal > 50) adjustedDiscount -= 2;
  return inputVal - adjustedDiscount;
}
```

This refactoring has a stronger justification in languages with mutable reference semantics (Java objects, JavaScript objects/arrays) where mutating a parameter's *contents* (not the reference) does affect the caller. Avoiding parameter mutation prevents "action at a distance" bugs that are particularly hard to trace.

### Section B2: Advanced Patterns

**Q11. When does Replace Temp with Query introduce a performance problem, and how do you handle it correctly?**
A: Replace Temp with Query can cause performance regression if the extracted query method is called multiple times and the underlying computation is expensive — a database read, a network call, or an O(n²) calculation. The temp that was eliminated served as a cache.

Handling strategies in order of preference:

1. **Measure first**: micro-optimization instinct is usually wrong. Most expression-to-method conversions have no measurable overhead. Profile before deciding to keep a temp for performance.
2. **Memoize the method**: cache the result at the object level on first call — the method becomes lazy-initialized.
3. **Reintroduce the temp selectively**: if a specific hot path is provably impacted, keep the temp *in that path* with a clear comment, leaving all other call sites using the query method.

```js
// Memoized query method — best of both worlds:
class Order {
  get basePrice() {
    if (this._basePrice === undefined) {
      this._basePrice = this.items.reduce((sum, i) => sum + i.price * i.qty, 0);
    }
    return this._basePrice;
  }
}
// Or with a decorator / WeakMap for stronger encapsulation
```

The key principle: do not sacrifice readability for speculative performance. Apply Replace Temp with Query, then measure, then add caching only where evidence demands it.

## Topic C: Inline Refactorings — Knowing When to Merge

### Section C1: Fundamentals

**Q12. What is Inline Method, and when is it the right choice?**
A: Inline Method is the inverse of Extract Method — it replaces a call to a method with the method's body, then removes the method. Apply it when a method's body is as clear as its name, or when a method is so simple that the indirection adds more cognitive overhead than the name adds clarity.

Specific triggers:
- The method is a one-liner and the line is entirely self-explanatory.
- A group of methods has been badly decomposed (too many tiny methods that do single trivial things).
- The method is only called from one place and you are in the middle of restructuring that code.
- The method's name is not more informative than its body.

```js
// Before — the method adds no value:
function getRating(driver) {
  return moreThanFiveLateDeliveries(driver) ? 2 : 1;
}

function moreThanFiveLateDeliveries(driver) {
  return driver.lateDeliveries > 5;
}

// After Inline Method:
function getRating(driver) {
  return driver.lateDeliveries > 5 ? 2 : 1;
}
```

Caution: do not inline a method that is polymorphic (overridden in subclasses), called from many places, or whose body is genuinely complex. The one-directional heuristic: Extract Method when the method is too long; Inline Method when the extracted pieces are too fragmented.

**Q13. What is Inline Temp, and what is the risk of overusing temporary variables?**
A: Inline Temp removes a temporary variable that is assigned exactly once and used exactly once — replacing the use with the expression directly. It is often a preparatory step before Extract Method (to remove a temp that would otherwise need to be a parameter).

```js
// Before:
const basePrice = order.basePrice();
return basePrice > 1000;

// After Inline Temp:
return order.basePrice() > 1000;
```

The risk of overusing temporaries: excessive temps clutter a method with variables that carry no information the expression itself doesn't carry. They force the reader to mentally track names that are used immediately and then never again. Overuse is a sign that the developer is uncomfortable with expression composition — often a matter of style, but it genuinely hurts readability in methods with many one-use temps.

Counterpoint: do use a temp when the expression is complex, non-obvious, or used more than once — the name adds value. Inline Temp only when the expression is simple enough that the name is redundant.

**Q14. What is Substitute Algorithm, and how does it differ from a refactoring driven by code smell?**
A: Substitute Algorithm replaces the entire body of a method with a cleaner algorithm that achieves the same result. It differs from other composing-method refactorings in that it is not driven by a structural code smell (long method, temp variable, abstraction mismatch) — it is driven by the realization that a better algorithm exists, often one made available by a library, a language feature, or simply clearer thinking.

```js
// Before — manual loop to find a value:
function foundPerson(people) {
  for (let i = 0; i < people.length; i++) {
    if (people[i] === 'Don') return 'Don';
    if (people[i] === 'John') return 'John';
    if (people[i] === 'Kent') return 'Kent';
  }
  return '';
}

// After Substitute Algorithm — using Set intersection:
function foundPerson(people) {
  const candidates = new Set(['Don', 'John', 'Kent']);
  return people.find(p => candidates.has(p)) ?? '';
}
```

Mechanics for safe substitution: (1) decompose the original method as much as possible first (smaller methods are easier to test); (2) write the new algorithm; (3) run tests against both the original and the replacement with the same inputs — confirm equivalent behavior; (4) replace.

## Topic D: Code Smells That Composing Methods Fix

### Section D1: Fundamentals

**Q15. What is the "Long Method" smell, and why is it the canonical target of composing methods?**
A: Long Method is the most prevalent code smell and the primary motivation for the entire composing-methods category. A method is "long" not merely by line count but by cognitive complexity — the number of things a reader must hold in mind simultaneously to understand it. Long methods accumulate because:

- Adding a feature is easier than restructuring: developers append code to existing methods rather than creating new ones.
- Methods grow gradually — no single addition is egregiously long.
- Developers overestimate the cost of method calls and underestimate the cost of comprehension.

The heuristic Martin Fowler popularized: **if you feel the need to write a comment, write a method instead.** The comment describes intent; the method name serves the same purpose while also making the code reusable and independently testable.

```
Signs a method is too long:
- Requires scrolling to read in full
- Contains comments that separate "sections" of work
- Has more than 2–3 levels of indentation
- Requires the reader to understand 5+ local variables simultaneously
- Cannot be unit-tested without setting up complex state for all its branches
- Any change to it requires reading all of it (no safe "this section is unrelated")
```

**Q16. What is the "Temporary Field" smell, and which composing techniques address it?**
A: Temporary Field is a smell at the class level but often rooted in a composing-method problem: an object has an instance variable that is only set and used during a single method's execution (and is null/undefined at all other times). The method is using an instance variable as a way to pass data between extracted sub-methods, rather than using parameters or return values.

The smell signals that the method and its helpers form a coherent unit of computation that has been awkwardly distributed across the class.

```js
// Smell — _inputVal and _discount are only meaningful during applyDiscount():
class PriceCalculator {
  applyDiscount(inputVal, discount) {
    this._inputVal = inputVal;
    this._discount = discount;
    this._computeBaseReduction();
    this._applyLoyaltyBonus();
    return this._inputVal;
  }

  _computeBaseReduction() {
    if (this._inputVal > 50) this._discount -= 2; // uses temporary field
    this._inputVal -= this._discount;
  }
  // ...
}
```

Fixes: (1) **Replace Method with Method Object** — move the method and its temporaries to a dedicated class where they become proper fields; (2) **Replace Temp with Query** combined with parameter passing — eliminate the instance variables and pass values explicitly; (3) **Extract Class** (a class-level refactoring) — extract the cohesive computation into its own class.

**Q17. What are the "Comments" and "Dead Code" smells, and how do composing methods address them?**
A: **Comments as a smell** (not all comments — only compensatory ones): when a comment precedes a block of code to explain what the block does, it is a signal that the block should be an Extract Method. The comment becomes the method name. Well-composed methods are largely self-documenting — comments should explain *why* (business rationale, non-obvious constraints), not *what* (which the code itself should convey).

**Dead Code** — code that is never reached or called — is often introduced by the very practices composing methods fight. When a method does too much, partial refactors leave orphaned helpers. After composing-method refactorings, running coverage tools and removing uncalled methods is a natural cleanup step.

```js
// Comment as smell → Extract Method:
function processOrder(order) {
  // validate order fields
  if (!order.id || !order.items || order.items.length === 0) {
    throw new Error('Invalid order');
  }
  // ... rest of processing
}

// After:
function processOrder(order) {
  validateOrder(order);
  // ... rest of processing
}

function validateOrder(order) {
  if (!order.id || !order.items || order.items.length === 0) {
    throw new Error('Invalid order');
  }
}
// No comment needed — method name is the comment
```

### Section D2: Advanced Patterns

**Q18. "When does Extract Method make things worse?" — the over-extraction trap.**
A: Extract Method can be misapplied in two ways that actively harm readability:

1. **Extracting too small**: methods that contain a single line that was already self-explanatory. `function addOne(n) { return n + 1; }` extracted without reuse creates indirection without reward — readers must jump to a definition to confirm there's nothing surprising inside.

2. **Shogun method design**: "vertical slice" extraction that creates a chain of methods each calling only one other method — `a() → b() → c() → d()` where each is a one-liner. Tracing logic requires visiting every method; the extraction produced navigation overhead without comprehension benefit.

The signal that extraction is appropriate: the extracted method has a name that is meaningfully more informative than its body, and/or the method is (or could be) reused elsewhere. The signal that extraction over-decomposed: you find yourself inlining methods during code review because they're trivially obvious.

```
Over-extracted (no benefit):
function checkout(cart) {
  return computeFinalPrice(cart);
}
function computeFinalPrice(cart) {
  return applyAllDiscounts(cart);
}
function applyAllDiscounts(cart) {
  return cart.items.reduce((s, i) => s + i.price, 0) * 0.9;
}

Better (one meaningful extraction):
function checkout(cart) {
  return subtotal(cart) * MEMBER_DISCOUNT;
}
function subtotal(cart) {
  return cart.items.reduce((s, i) => s + i.price, 0);
}
```

**Q19. "What is the relationship between composing methods and testability?"**
A: Composing methods and testability are deeply coupled — each extracted method is independently testable without setting up the full context required by the original long method.

A long method often requires a large, specific input state to exercise a particular branch deep inside it. After Extract Method, that branch becomes a separate method that can be tested with a minimal, focused input. Coverage becomes more granular, failure messages point to the specific extracted method, and mocking is scoped to the right level.

```js
// Before — testing the discount logic requires a full Order object:
function processOrder(order) {
  // ... 30 lines of validation, normalization ...
  if (order.total > 1000 && order.customer.loyaltyYears > 3) {
    order.discount = 0.15;
  }
  // ... 20 more lines of persistence, notification ...
}

// After Extract Method — discount logic testable in isolation:
function applyLoyaltyDiscount(order) {
  if (order.total > 1000 && order.customer.loyaltyYears > 3) {
    order.discount = 0.15;
  }
}

// Test:
test('applies 15% discount for high-value loyal customers', () => {
  const order = { total: 1500, customer: { loyaltyYears: 5 }, discount: 0 };
  applyLoyaltyDiscount(order);
  expect(order.discount).toBe(0.15);
});
// No need to mock the database, email service, or validation logic
```

The inverse is also true: if a method cannot be tested without an elaborate test fixture, that is a signal — not of poor test infrastructure — but of a method that is doing too much and needs composing-method refactoring.

## Topic E: Cross-Topic & Interview-Style Questions

**Q20. "Explain composing methods in one paragraph to a junior developer."**
A: When methods grow too long or do too many things at once, they become hard to read, test, and change safely. Composing methods is a collection of small, safe transformations — like Extract Method, Rename Variable, or Remove Assignments to Parameters — that break the work into smaller, named pieces. Each piece has one clear job and a name that says what it does. The goal is that every method reads like a short table of contents: you can see the high-level steps at a glance, and if you want the detail of any step, you go to the method it calls. This makes bugs easier to find, code easier to test, and changes easier to make safely.

**Q21. "Walk me through refactoring a long method — what is your process?"**
A: A systematic approach:

1. **Identify sections by comment or visual break.** Comments that precede blocks ("// calculate total", "// validate input") are Extract Method opportunities. The comment becomes the method name.

2. **Identify locals.** For each candidate block, determine which local variables it reads (these become parameters) and which it assigns and uses later (these become return values). If there are many, consider Replace Temp with Query to eliminate them before extracting.

3. **Extract the lowest-abstraction code first.** Start with the lines that are clearly "closer to the machine" than the surrounding code — loops over raw data structures, string parsing, null checks on nested properties.

4. **Verify after each extraction.** Run tests. Each extraction should leave all tests passing — if not, you introduced a bug in the mechanics (wrong variable scope, missing return value).

5. **Name aggressively.** If you cannot name an extracted method in 3–5 words without using "and", the method still does two things. Split it further.

6. **Step back and read the composed method.** The goal is a method that reads like a sentence: a sequence of high-level action calls with no implementation detail visible at the top level.

**Q22. "What is the output / refactored form of this code, and what is the reasoning?"**

```js
function renderPage(page) {
  let html = '';
  // header
  html += `<html><head><title>${page.title}</title></head><body>`;
  // content
  for (const section of page.sections) {
    html += `<div class="section">`;
    html += `<h2>${section.heading}</h2>`;
    html += `<p>${section.body}</p>`;
    html += `</div>`;
  }
  // footer
  html += `<footer>${page.author} &copy; ${new Date().getFullYear()}</footer>`;
  html += '</body></html>';
  return html;
}
```

A: This method has three clear sections (comments reveal them), mixed string-concatenation mechanics with structural HTML semantics, and no separation between page-level and section-level concerns.

Refactored:

```js
function renderPage(page) {
  return renderHeader(page.title)
    + renderContent(page.sections)
    + renderFooter(page.author)
    + '</body></html>';
}

function renderHeader(title) {
  return `<html><head><title>${title}</title></head><body>`;
}

function renderContent(sections) {
  return sections.map(renderSection).join('');
}

function renderSection(section) {
  return `<div class="section"><h2>${section.heading}</h2><p>${section.body}</p></div>`;
}

function renderFooter(author) {
  return `<footer>${author} &copy; ${new Date().getFullYear()}</footer>`;
}
```

Reasoning:
- `renderPage` now reads as a pipeline of named steps — no HTML string mechanics visible at the top level (SLA restored).
- `renderSection` is independently testable with a single section object.
- `renderContent` delegates to `renderSection` for each element — single responsibility.
- Comments replaced by method names — the code is self-documenting.

**Q23. "What is the difference between Extract Method and Extract Function in functional contexts?"**
A: In object-oriented contexts, Extract Method creates a method on a class — it has access to `this` (the object's state) and may use instance variables without being passed them. In functional or procedural contexts (JavaScript modules, Python modules, top-level functions), the equivalent is Extract Function — extracting a pure function that takes all its inputs as explicit parameters and returns its output, with no side effects.

Extract Function is generally preferable when the extracted logic is stateless: it is easier to test (no object to construct), easier to reuse (importable anywhere), and easier to reason about (no hidden state dependency). Extract Method is appropriate when the extracted logic genuinely belongs to a specific object — when it needs access to multiple fields of an object that would be unwieldy to pass as parameters.

```js
// Extract Method — accesses object state:
class OrderProcessor {
  process(order) {
    const tax = this.calculateTax(order); // uses this.taxRate
    return order.subtotal + tax;
  }

  calculateTax(order) {
    return order.subtotal * this.taxRate; // this.taxRate: state dependency
  }
}

// Extract Function — pure, stateless:
function calculateTax(subtotal, taxRate) {  // all inputs explicit
  return subtotal * taxRate;
}

function processOrder(order, taxRate) {
  const tax = calculateTax(order.subtotal, taxRate);
  return order.subtotal + tax;
}
```

**Q24. "How do you handle Extract Method when the target fragment modifies multiple local variables?"**
A: Multiple local variable modifications are the hardest case in Extract Method. Languages that allow only a single return value require a strategy:

- **If one variable is "the result" and others are accumulators not used afterward**: pass the others in by reference (in languages that support it) or restructure so the extraction returns only the meaningful result.
- **If multiple variables are all needed after the extraction**: group them into a small object (a record or a lightweight class) and return that.
- **If it feels wrong to return a multi-field object**: that is a signal that the fragment is doing too much — look for sub-fragments that each produce one result.

```js
// Before — fragment modifies two locals:
function processShipment(order) {
  let primaryBase, discountedBase;

  // fragment start:
  primaryBase = order.quantity * order.price;
  discountedBase = order.loyal ? primaryBase * 0.9 : primaryBase;
  // fragment end

  const tax = discountedBase * 0.1;
  return discountedBase + tax;
}

// Option 1 — return a small object:
function processShipment(order) {
  const { primaryBase, discountedBase } = computePriceBases(order);
  const tax = discountedBase * 0.1;
  return discountedBase + tax;
}

function computePriceBases(order) {
  const primaryBase = order.quantity * order.price;
  const discountedBase = order.loyal ? primaryBase * 0.9 : primaryBase;
  return { primaryBase, discountedBase };
}

// Option 2 — if primaryBase is not needed outside, simplify further:
function processShipment(order) {
  const discountedBase = applyLoyaltyDiscount(order);
  return discountedBase * 1.1; // + 10% tax
}

function applyLoyaltyDiscount(order) {
  const base = order.quantity * order.price;
  return order.loyal ? base * 0.9 : base;
}
```

## Problem 1 — Refactor a Long Method: Order Processing

### Problem
Refactor the following method by applying composing-method techniques. Identify each code smell, name the technique applied, and explain why.

```js
function processOrder(order, customer) {
  // validate
  if (!order || !order.items || order.items.length === 0) {
    throw new Error('Order must have items');
  }
  if (!customer || !customer.email) {
    throw new Error('Customer must have email');
  }

  // calculate subtotal
  let subtotal = 0;
  for (const item of order.items) {
    subtotal += item.price * item.quantity;
  }

  // apply discount
  let discount = 0;
  if (customer.membershipYears > 5 && subtotal > 500) {
    discount = subtotal * 0.15;
  } else if (subtotal > 500) {
    discount = subtotal * 0.10;
  }

  const total = subtotal - discount;

  // save and notify
  db.orders.insert({ orderId: order.id, customerId: customer.id, total });

  return total;
}
```

### Pattern Recognition
Multi-smell method: Long Method (4 distinct phases), comment-separated sections (Extract Method opportunity for each), mixed abstraction levels (validation vs. math vs. persistence vs. notification), implicit conditional structure (Decompose Conditional), and a loop that could be a query (Replace Temp with Query).

### Key Insight
Each comment ("// validate", "// calculate subtotal", etc.) marks an extraction boundary. Each section operates at a different level of abstraction — pulling them out restores SLA and makes every part independently testable. The discount logic is a classic Decompose Conditional target.

### Full Refactoring

```js
// Top-level method: reads as a policy — no mechanics visible
function processOrder(order, customer) {
  validateOrder(order);
  validateCustomer(customer);

  const subtotal = calculateSubtotal(order.items);
  const total = applyDiscount(subtotal, customer);

  persistOrder(order, customer, total);
  notifyCustomer(customer, total);

  return total;
}

// --- Validation ---
function validateOrder(order) {
  if (!order || !order.items || order.items.length === 0) {
    throw new Error('Order must have items');
  }
}

function validateCustomer(customer) {
  if (!customer || !customer.email) {
    throw new Error('Customer must have email');
  }
}

// --- Calculation ---
// Replace Temp with Query: subtotal becomes a query on items
function calculateSubtotal(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

// Decompose Conditional: discount logic extracted and condition named
function applyDiscount(subtotal, customer) {
  const discount = discountAmount(subtotal, customer);
  return subtotal - discount;
}

function discountAmount(subtotal, customer) {
  if (isEliteDiscount(subtotal, customer)) return subtotal * 0.15;
  if (isStandardDiscount(subtotal))        return subtotal * 0.10;
  return 0;
}

function isEliteDiscount(subtotal, customer) {
  return customer.membershipYears > 5 && subtotal > 500;
}

function isStandardDiscount(subtotal) {
  return subtotal > 500;
}

// --- Side effects ---
function persistOrder(order, customer, total) {
  db.orders.insert({ orderId: order.id, customerId: customer.id, total });
}

function notifyCustomer(customer, total) {
  emailService.send(customer.email, `Your order total: $${total.toFixed(2)}`);
}
```

### Technique Map

| Original Section | Technique Applied | Reason |
|---|---|---|
| Entire method | Extract Method (×6) | Comments marked extraction boundaries; SLA violated |
| `subtotal` temp variable | Replace Temp with Query | `calculateSubtotal()` replaces the loop |
| Discount `if/else if` | Decompose Conditional | Condition and branches extracted and named |
| Mixed validation + math + persistence | Extract Method | Different abstraction levels separated |

### Testability Gain
Before: one test per scenario requires constructing a full `order + customer + db mock + emailService mock` context. After: `calculateSubtotal` is a pure function testable with an array literal; `isEliteDiscount` needs only two scalars; `discountAmount` needs two scalars.

### Edge Cases
- `order.items` is empty: caught by `validateOrder` before any calculation.
- `discount` computation is pure (no side effects): can be tested without mocking.
- `persistOrder` and `notifyCustomer` can be individually mocked or replaced without touching the calculation logic.

## Problem 2 — Apply Replace Method with Method Object

### Problem
The following rendering method cannot be cleanly decomposed via Extract Method because of excessive local state. Apply Replace Method with Method Object.

```js
function renderReport(data, config, user) {
  const title = config.reportTitle || 'Report';
  const dateRange = `${config.startDate} – ${config.endDate}`;
  const filteredRows = data.filter(row => row.category === config.category);
  const sortedRows = filteredRows.sort((a, b) => b.value - a.value);
  const topRows = sortedRows.slice(0, config.maxRows || 10);
  const grandTotal = topRows.reduce((s, r) => s + r.value, 0);
  const formattedRows = topRows.map(r =>
    `<tr><td>${r.label}</td><td>${r.value.toFixed(2)}</td></tr>`
  );
  const canExport = user.roles.includes('admin') || user.roles.includes('exporter');
  const exportButton = canExport
    ? `<button onclick="exportReport()">Export</button>` : '';

  return `
    <div class="report">
      <h1>${title}</h1>
      <p>${dateRange}</p>
      <table>${formattedRows.join('')}</table>
      <p>Total: ${grandTotal.toFixed(2)}</p>
      ${exportButton}
    </div>
  `;
}
```

### Pattern Recognition
Long method with excessive local variables — all related to the same rendering computation. Extracting sub-methods would require passing 5–7 variables as parameters. Replace Method with Method Object converts the locals into fields, enabling clean extraction with no parameter lists.

### Solution

```js
class ReportRenderer {
  constructor(data, config, user) {
    this.data = data;
    this.config = config;
    this.user = user;

    // Derived state — computed once in constructor
    this.title = config.reportTitle || 'Report';
    this.dateRange = `${config.startDate} – ${config.endDate}`;
    this.topRows = this._computeTopRows();
    this.grandTotal = this._computeGrandTotal();
  }

  render() {
    return `
      <div class="report">
        <h1>${this.title}</h1>
        <p>${this.dateRange}</p>
        <table>${this._renderRows()}</table>
        <p>Total: ${this.grandTotal.toFixed(2)}</p>
        ${this._renderExportButton()}
      </div>
    `;
  }

  _computeTopRows() {
    return this.data
      .filter(row => row.category === this.config.category)
      .sort((a, b) => b.value - a.value)
      .slice(0, this.config.maxRows || 10);
  }

  _computeGrandTotal() {
    return this.topRows.reduce((s, r) => s + r.value, 0);
  }

  _renderRows() {
    return this.topRows
      .map(r => `<tr><td>${r.label}</td><td>${r.value.toFixed(2)}</td></tr>`)
      .join('');
  }

  _renderExportButton() {
    return this._canExport()
      ? `<button onclick="exportReport()">Export</button>`
      : '';
  }

  _canExport() {
    return this.user.roles.includes('admin') || this.user.roles.includes('exporter');
  }
}

// Preserve the original function signature for callers:
function renderReport(data, config, user) {
  return new ReportRenderer(data, config, user).render();
}
```

### Why This Is Better Than Extract Method Here

```
Extract Method attempt would produce:
function _renderRows(topRows) { ... }            // 1 param — manageable
function _renderExportButton(user, canExport) { ... } // 2 params — growing
function _computeGrandTotal(topRows) { ... }     // 1 param
function render(title, dateRange, topRows, grandTotal, canExport) { ... }
         ↑ 5 parameters — this is the "too many params" smell
```

The parameter lists reveal that all these values belong together — they are the shared state of one coherent rendering task. Making them fields eliminates every parameter.

### Follow-up Questions
- "Is creating a class for a single render call wasteful?" → No — the class is not stored; it is instantiated and garbage-collected per call. Its purpose is structural organization, not stateful lifecycle.
- "Extend to support caching?" → Add `this._cachedRender = null; render() { if (!this._cachedRender) { ... } return this._cachedRender; }`.
- "What if `_computeTopRows` is expensive?" → Memoize: computed once in the constructor, stored as a field, accessed cheaply by all sub-methods.

## Problem 3 — Decompose a Complex Conditional Chain

### Problem
Refactor the following pricing method, which has a deeply nested conditional structure with no named concepts.

```js
function calculateShipping(order, customer, warehouse) {
  let cost = 0;
  if (order.weight < 1) {
    cost = 2.99;
  } else if (order.weight < 5) {
    if (customer.isPremium) {
      cost = 4.99;
    } else {
      cost = 7.99;
    }
  } else if (order.weight < 20) {
    if (customer.isPremium && warehouse.inRegion(customer.region)) {
      cost = 9.99;
    } else if (customer.isPremium) {
      cost = 14.99;
    } else {
      cost = 19.99;
    }
  } else {
    cost = order.weight * 1.25;
  }
  return cost;
}
```

### Pattern Recognition
Decompose Conditional — deeply nested `if/else` chain with no named conditions or branches, mixing weight tiers with customer status with warehouse logic. Each branch is an unnamed business rule.

### Approach
1. Replace the `if/else if` chain with a linear sequence of guard clauses (each returning immediately — "Replace Nested Conditional with Guard Clauses" is a related technique).
2. Extract each condition into a predicate method.
3. Extract each cost calculation into a method.
4. Name each method after the business concept it represents.

### Solution

```js
function calculateShipping(order, customer, warehouse) {
  if (isLightWeight(order))    return lightWeightRate();
  if (isMediumWeight(order))   return mediumWeightRate(customer);
  if (isHeavyWeight(order))    return heavyWeightRate(order, customer, warehouse);
  return bulkWeightRate(order);
}

// --- Weight predicates ---
function isLightWeight(order)  { return order.weight < 1; }
function isMediumWeight(order) { return order.weight < 5; }
function isHeavyWeight(order)  { return order.weight < 20; }

// --- Rate calculations ---
function lightWeightRate() {
  return 2.99;
}

function mediumWeightRate(customer) {
  return customer.isPremium ? 4.99 : 7.99;
}

function heavyWeightRate(order, customer, warehouse) {
  if (isPremiumInRegion(customer, warehouse)) return 9.99;
  if (customer.isPremium)                     return 14.99;
  return 19.99;
}

function bulkWeightRate(order) {
  return order.weight * 1.25;
}

function isPremiumInRegion(customer, warehouse) {
  return customer.isPremium && warehouse.inRegion(customer.region);
}
```

### Before vs. After

```
Before: 20 lines of nested conditionals — reader must trace all branches to find any single rate
After:  calculateShipping() reads as a dispatch table of named cases
        each case is independently readable, testable, and modifiable
```

### Testability
```js
// Each rate function testable with minimal inputs:
test('premium customer in region gets 9.99 for heavy weight', () => {
  const customer = { isPremium: true, region: 'West' };
  const warehouse = { inRegion: (r) => r === 'West' };
  const order = { weight: 15 };
  expect(calculateShipping(order, customer, warehouse)).toBe(9.99);
});

// isPremiumInRegion testable in isolation:
test('isPremiumInRegion false for non-premium', () => {
  expect(isPremiumInRegion({ isPremium: false }, { inRegion: () => true })).toBe(false);
});
```

## Problem 4 — Full Refactoring Sequence: Temp Variables to Query Methods

### Problem
Apply the full composing-method sequence to eliminate temporary variables and make the method compositional.

```js
function invoiceTotal(order) {
  const basePrice = order.quantity * order.itemPrice;
  const quantityDiscount = Math.max(0, order.quantity - 500) * order.itemPrice * 0.05;
  const shipping = Math.min(basePrice * 0.1, 100);
  return basePrice - quantityDiscount + shipping;
}
```

### Pattern Recognition
Replace Temp with Query — each temporary variable (`basePrice`, `quantityDiscount`, `shipping`) names an intermediate computation that is a candidate for a query method. Once promoted to query methods, the `return` statement becomes a clear formula.

### Step-by-Step Transformation

**Step 1 — Extract `basePrice`:**
```js
function basePrice(order) {
  return order.quantity * order.itemPrice;
}
```

**Step 2 — Extract `quantityDiscount`:**
```js
function quantityDiscount(order) {
  return Math.max(0, order.quantity - 500) * order.itemPrice * 0.05;
}
```

**Step 3 — Extract `shipping`:**
```js
function shipping(order) {
  return Math.min(basePrice(order) * 0.1, 100);
}
```

**Step 4 — Replace temps in `invoiceTotal` with query calls:**
```js
function invoiceTotal(order) {
  return basePrice(order) - quantityDiscount(order) + shipping(order);
}
```

### Final Form

```js
function invoiceTotal(order) {
  return basePrice(order) - quantityDiscount(order) + shipping(order);
}

function basePrice(order) {
  return order.quantity * order.itemPrice;
}

function quantityDiscount(order) {
  return Math.max(0, order.quantity - 500) * order.itemPrice * 0.05;
}

function shipping(order) {
  return Math.min(basePrice(order) * 0.1, 100);
}
```

### What Was Gained

| Before | After |
|---|---|
| `invoiceTotal` mixes formula with sub-computations | `invoiceTotal` reads as a pure formula |
| 4 lines → reader must parse each expression | 1 return line → immediately clear intent |
| Sub-computations untestable without calling `invoiceTotal` | Each query function independently testable |
| Adding a new pricing rule requires editing `invoiceTotal` | A new rule is a new query function; `invoiceTotal` may not need changing |

### Performance Note
`basePrice(order)` is now called twice (in `invoiceTotal` and `shipping`). The computation is O(1) arithmetic — no measurable cost. If this were expensive: memoize `basePrice` or pass its result as a parameter to `shipping`.

## Quick Reference — Composing Methods Cheat Sheet

```
TECHNIQUE SELECTION GUIDE:

  [1] METHOD TOO LONG (> ~15 lines, or hard to name in one phrase)?
        → Extract Method — one fragment at a time, starting with the lowest-
          abstraction code or the comment-delimited sections.

  [2] CONDITIONAL LOGIC confusing or deeply nested?
        → Decompose Conditional — extract condition, then-branch, else-branch
          into named methods.

  [3] LOCAL VARIABLES blocking extraction (too many params needed)?
        → Replace Temp with Query — promote the expression to a method.
        → If still too many: Replace Method with Method Object.

  [4] TEMP VARIABLE used for two different things across its lifetime?
        → Split Temporary Variable — one variable per role.

  [5] TEMP VARIABLE used exactly once, expression obvious?
        → Inline Temp — remove the variable.

  [6] METHOD trivially simple — name not more informative than body?
        → Inline Method — remove the indirection.

  [7] PARAMETER reassigned inside the method?
        → Remove Assignments to Parameters — introduce a local.

  [8] ALGORITHM convoluted but a cleaner one exists?
        → Substitute Algorithm — replace the whole body.

KEY RULES:
  ✓ The Promise Executor rule equivalent: a method's body should be at ONE
    level of abstraction — no high-level policy mixed with low-level mechanism.
  ✓ Every comment that says "what" is an Extract Method waiting to happen.
  ✓ If you cannot name an extracted method without "and", split it further.
  ✓ Replace Temp with Query is the unlock for Extract Method when temps block it.
  ✓ Extract Method is the MOST USED technique — it subsumes many others.
  ✓ Inline is the inverse — use it to remove over-extraction, not to avoid extraction.
  ✓ Each extracted method should be independently unit-testable.

SMELL → TECHNIQUE MAP:
  Long Method              → Extract Method (repeatedly)
  Comment before code      → Extract Method (comment becomes method name)
  Deep nesting             → Decompose Conditional + Guard Clauses
  Many local variables     → Replace Temp with Query → Replace Method with Method Object
  Reused temp name         → Split Temporary Variable
  Parameter mutation       → Remove Assignments to Parameters
  Method with one line     → Inline Method
  Redundant temp variable  → Inline Temp
  Algorithm unreadable     → Substitute Algorithm
  Mixed abstraction levels → Extract Method (until SLA is uniform)

WHEN NOT TO EXTRACT:
  ✗ One-liner that is already self-evident (adding indirection without clarity)
  ✗ Deeply sequential logic that forms a single narrative (extraction fragments the story)
  ✗ Performance-critical inner loops where a function call is measurably costly
     (measure first — this is rarely the real constraint)

PARAMETER MANAGEMENT AFTER EXTRACTION:
  0–2 params: ideal — proceed
  3–4 params: warning — consider if they belong together as an object
  5+ params:  stop — use Replace Method with Method Object; these are hidden fields
```

## Common Bugs Checklist

Before submitting any refactored code using composing-method techniques, verify:

1. **Did the extracted method capture the right variables?** — Missing a reference means the extracted method silently uses a different value (a global, or an uninitialized local). Walk through the extracted code and confirm every name resolves to the intended value.

2. **Does a temp variable survive extraction (used after the extracted block)?** — If so, it must be returned from the extracted method and re-captured at the call site. Forgetting to return it means the original method continues with the old (unmodified) value.

3. **Is a parameter being mutated inside the extracted method?** — Parameter mutation in the extracted method does not affect the caller's local variable (for primitives). If the intent was to update the caller's value, return the new value instead.

4. **After Replace Temp with Query, is the expression called multiple times with side effects?** — Promoting an expression with side effects (e.g., `db.query()`, `Math.random()`) to a method that is called multiple times changes behavior. Expressions with side effects should not be extracted as queries; keep them as temps.

5. **After Inline Method, is the inlined method overridden in a subclass?** — Inlining a polymorphic method breaks subclass behavior. Only inline methods that are not overridden and will not be.

6. **After Decompose Conditional, does the renamed condition still mean what the code implies?** — Name the method after *what is true* when the condition is true (not the mechanism). `isOverWeightLimit(order)` not `checkWeight(order)`.

7. **After Split Temporary Variable, is the first variable still assigned correctly?** — Splitting a temp requires careful tracing: the first assignment becomes the first variable; the second becomes the second. Confirm each assignment's value matches its new variable's purpose.

8. **After Replace Method with Method Object, is the original function's public interface preserved?** — Callers should not need to change. Wrap the new class's `render()`/`compute()` method with the original function signature.

9. **After Substitute Algorithm, does the new algorithm handle all edge cases of the original?** — A simpler algorithm often handles the "happy path" but misses boundary conditions (empty arrays, null values, integer overflow) that the convoluted original handled. Diff test with property-based or randomized tests.

10. **Are tests running after every extraction step?** — Each individual extraction should leave the test suite green. Running tests only at the end makes it impossible to identify which step introduced a regression.

---

**Final Tip:** The refactoring question that stumps the most candidates — even experienced ones — is "where do you stop?" The answer is not "when the methods are short enough" but "when every method reads as a coherent statement at one level of abstraction." The test is not line count — it is whether a reader can understand the method's *full intent* without reading any method it calls. When that is true, the composition is right. Pair it with the naming heuristic ("if you can't name the extracted method in 3–5 words without 'and', it's still doing two things") and the testability heuristic ("each extracted method should be testable with a minimal, focused input"), and no decomposition decision should be ambiguous.
