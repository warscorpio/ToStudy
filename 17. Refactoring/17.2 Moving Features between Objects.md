# Refactoring: Moving Features between Objects — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

## Topic A: Move Method / Move Function

### Section A1: Fundamentals

**Q1. What is Move Method, and what is its core motivation?**

A: Move Method (called **Move Function** in Fowler's 2018 second edition for non-OOP or module contexts) relocates a method from its current class to the class whose data and behaviour it interacts with most. After the move, the original class either delegates to the new location or removes the method entirely and updates all callers.

The core motivation is **cohesion**: a class should contain methods that work primarily on its own data. When a method spends most of its time reaching into another class's fields and calling another class's methods, it "belongs" there conceptually. Keeping it in its original host creates **Feature Envy** — a coupling smell where one class is perpetually curious about another's internals.

```js
// BEFORE — Feature Envy: calculateDiscount lives in Order but only touches Customer
class Customer {
  constructor(name, loyaltyYears, isPremium) {
    this.name = name;
    this.loyaltyYears = loyaltyYears;
    this.isPremium = isPremium;
  }
}

class Order {
  constructor(customer, amount) {
    this.customer = customer;
    this.amount = amount;
  }

  // ❌ This method touches only Customer data — it envies Customer
  calculateDiscount() {
    let discount = 0;
    if (this.customer.isPremium) discount += 0.1;
    if (this.customer.loyaltyYears > 5) discount += 0.05;
    return this.amount * discount;
  }
}

// AFTER — Move Method: calculateDiscount moves to Customer
class Customer {
  constructor(name, loyaltyYears, isPremium) {
    this.name = name;
    this.loyaltyYears = loyaltyYears;
    this.isPremium = isPremium;
  }

  // ✅ Now operates on its own data; receives the external value it needs as a param
  discountFor(amount) {
    let rate = 0;
    if (this.isPremium) rate += 0.1;
    if (this.loyaltyYears > 5) rate += 0.05;
    return amount * rate;
  }
}

class Order {
  constructor(customer, amount) {
    this.customer = customer;
    this.amount = amount;
  }

  // ✅ Delegates cleanly — Order is no longer responsible for discount logic
  calculateDiscount() {
    return this.customer.discountFor(this.amount);
  }
}
```

**Q2. What is Feature Envy, and how do you detect it reliably?**

A: **Feature Envy** is a code smell coined by Martin Fowler in which a method in class A is more interested in the data or behaviour of class B than in its own class's data. The method accesses B's fields repeatedly, calls many of B's methods, or performs logic that conceptually belongs to B's domain.

Detection heuristics — look for these patterns inside a method:

- **Repeated `x.field` or `x.method()` chains** — if a method references `this.other.foo`, `this.other.bar`, `this.other.baz` three or more times, the method probably belongs in `other`'s class.
- **Parameters passed through unchanged** — the method receives object `x` as a parameter and just forwards it to another method; the method may belong in `x`'s class instead.
- **The method's name reflects B's domain** — `calculateTaxFor(invoice)`, `renderProfile(user)` — the subject of the name suggests its home.
- **Unit test requires extensive stubs of a different class** — if testing `Order.calculateDiscount()` requires fully constructing and stubbing a `Customer`, the method belongs in `Customer`.

```js
// Strong Feature Envy signal — three accesses into Address from Person
class Person {
  formatShippingLabel() {
    // All three lines touch Address — none touch Person's own data
    return `${this.address.street}, ${this.address.city} - ${this.address.pinCode}`;
  }
}

// Move Method target: Address
class Address {
  toShippingLabel() {
    return `${this.street}, ${this.city} - ${this.pinCode}`;
  }
}
```

**Q3. What are the mechanical steps for safely applying Move Method?**

A: The safe sequence for Move Method avoids breaking callers at any intermediate step:

```
1. EXAMINE the method: list every field and method it references from its current
   class vs. the target class. Confirm the target class is the right destination.

2. CHECK the target class: ensure a method with the same name doesn't already exist.
   If it does, pick a different name or merge the logic.

3. COPY the method body to the target class. Adjust references:
   - References to the source class's own data become parameters (or move those fields too).
   - References to the target class's data become `this.field`.

4. COMPILE & test the new method in isolation.

5. REPLACE the source method body with a delegation call to the new location.
   Do NOT delete the source method yet — this is the "safe bridge" phase.

6. RUN all existing tests. They should still pass (delegation is transparent).

7. FIND all callers of the source method. Update each to call the method directly
   on the target class (if it has a direct reference to the target object).

8. Once all callers are updated, REMOVE the delegating source method (or keep it
   as permanent delegation if callers cannot be changed).
```

```js
// Step 5 — Safe bridge: source method now just delegates
class Order {
  calculateDiscount() {
    // Bridge: existing callers still work; tests still pass
    return this.customer.discountFor(this.amount);
  }
}

// Step 7 — Direct callers updated:
// Before: order.calculateDiscount()
// After:  order.customer.discountFor(order.amount)
// (Or leave the bridge if callers can't all be updated at once)
```

**Q4. What are the main risks when moving a method, and how do you mitigate them?**

A: The key risks and their mitigations:

| Risk | Description | Mitigation |
|------|-------------|------------|
| **Broken callers** | External code calls the method on the original class | Keep a delegating stub on the original; update callers iteratively |
| **Access to private state** | Moved method needs data from the source class it can no longer access | Pass needed data as parameters; or move fields alongside the method |
| **Subclass overrides** | Subclasses of the source class override the method — moving it silently removes polymorphism | Check the inheritance hierarchy; may need to move the method in all subclasses too |
| **Circular dependency** | The target class ends up importing/depending on the source class AND vice versa | If a circular dependency forms, Extract Class into a neutral third class instead |
| **Method name collision** | Target class already has a method of that name | Rename the moved method (pick the best name) and update all callers |

### Section A2: Advanced Patterns

**Q5. How does Move Method interact with inheritance and polymorphism?**

A: Move Method is straightforward for non-polymorphic methods. When the method being moved is **overridden in subclasses**, the refactoring must be applied to the entire hierarchy:

```js
// BEFORE — polymorphic method on source hierarchy
class Animal {
  describe(habitat) {
    // accesses Habitat data three times — Feature Envy
    return `${this.name} lives in ${habitat.biome} at ${habitat.elevation}m (${habitat.climate})`;
  }
}
class Dog extends Animal {}
class Eagle extends Animal {
  describe(habitat) {
    return super.describe(habitat) + ' and can fly at altitude';
  }
}

// Problem: if we move describe() to Habitat, Eagle's override has nowhere to go.
// Solution: move the BASE logic to Habitat; keep animal-specific extension as a
// hook that Habitat calls back into.

class Habitat {
  describeFor(animal) {
    const base = `${animal.name} lives in ${this.biome} at ${this.elevation}m (${this.climate})`;
    // Delegate back for animal-specific additions:
    return animal.additionalDescription
      ? base + ' ' + animal.additionalDescription(this)
      : base;
  }
}

class Eagle extends Animal {
  additionalDescription(_habitat) {
    return 'and can fly at altitude';
  }
}
```

The general rule: move the **common, envious logic** to the target class; retain **class-specific extensions** as hook methods called from the target.

**Q6. When should you NOT move a method despite clear Feature Envy?**

A: Three legitimate reasons to keep a method in its current class even when it envies another:

1. **The method uses data from multiple classes equally.** If `calculateShippingCost()` touches `Order`, `Customer`, and `Address` equally, moving it to any one class would just create Feature Envy toward the other two. Solution: Extract Class (a `ShippingCalculator`) or leave it in a service/use-case layer.

2. **The method is a behaviour of the current class, even if it reads another class's data.** `Order.isFulfillable()` may read `Inventory.stock`, but the question "is this order fulfillable?" conceptually belongs to `Order`, not `Inventory`. The Feature Envy smell can mislead when the data and the behaviour have different natural homes.

3. **Architectural layering prevents the move.** In a layered architecture (Controller → Service → Repository), moving a service-layer method into a domain-model class may violate the layer contract. Respect the architecture over the local code smell.

## Topic B: Move Field

### Section B1: Fundamentals

**Q7. What is Move Field, and what signals indicate a field belongs elsewhere?**

A: Move Field relocates a data field from one class to another — typically to the class that reads or writes it most frequently. It is often the precursor to Move Method: once the field moves to where it's most used, the method that accesses it can also move cleanly.

Signals that a field is in the wrong class:

- **Accessed through a reference** — `this.order.customer.loyaltyYears` inside a `Billing` class means `loyaltyYears` is two hops away; it may belong in `Billing`'s direct collaborator.
- **Passed around as a parameter** — if a field is extracted from one object and passed into many other methods as a raw value, it may be better co-located with those methods.
- **Modified by another class more than the owning class** — if `Account.balance` is only ever changed by `Transaction` methods, `balance` belongs in `Transaction` or a shared aggregate.
- **Used only in a subset of the class's lifecycle** — a field that only matters during one phase (e.g., `order.shipmentTrackingId` that's null until shipped) may belong in a separate `Shipment` class rather than bloating `Order`.

```js
// BEFORE — telephoneNumber field lives in Person but used entirely by ContactInfo logic
class Person {
  constructor(name, telephoneNumber, email) {
    this.name = name;
    this.telephoneNumber = telephoneNumber; // ← used nowhere in Person
    this.email = email;                     // ← used nowhere in Person
  }

  getContactSummary() {
    return `Call: ${this.telephoneNumber} | Email: ${this.email}`;
  }
}

// AFTER — Extract the contact data into ContactInfo; Person delegates
class ContactInfo {
  constructor(telephoneNumber, email) {
    this.telephoneNumber = telephoneNumber;
    this.email = email;
  }

  getSummary() {
    return `Call: ${this.telephoneNumber} | Email: ${this.email}`;
  }
}

class Person {
  constructor(name, contactInfo) {
    this.name = name;
    this.contactInfo = contactInfo; // ← the "field" is now a composed object
  }

  getContactSummary() {
    return this.contactInfo.getSummary(); // delegation
  }
}
```

**Q8. How do you apply Move Field safely when multiple classes access the field?**

A: The safe mechanical steps:

```
1. ENCAPSULATE the field in the source class (if it's public, make it private
   and add getter/setter). All accesses now go through the accessor.

2. CREATE a matching field (and accessor) in the target class.

3. CHANGE the source class's accessor to forward to the target class:
     get telephoneNumber() { return this._contactInfo.telephoneNumber; }
     set telephoneNumber(v) { this._contactInfo.telephoneNumber = v; }
   This is the "bridge" phase — all callers still work.

4. RUN tests.

5. UPDATE callers ONE BY ONE to access the field directly on the target class.

6. Once all callers go through the target, REMOVE the forwarding accessor from the
   source class and the field declaration there.
```

```js
// Step 3 — Bridge accessors on the source class:
class Person {
  get telephoneNumber() {
    return this.contactInfo.telephoneNumber; // forward to target
  }
  set telephoneNumber(value) {
    this.contactInfo.telephoneNumber = value; // forward to target
  }
}

// Callers continue to use person.telephoneNumber without any change
// while individual callers are updated to use person.contactInfo.telephoneNumber
```

**Q9. What is the difference between Move Field and Extract Class?**

A: They are related but operate at different granularities:

- **Move Field** relocates a single field to a class that **already exists**. It is a targeted, minimal change.
- **Extract Class** creates a **new class** to hold a cohesive group of fields (and their associated methods) that were all living in a single bloated class.

Extract Class is the appropriate choice when multiple fields and methods move together as a unit — because they form a coherent responsibility. Move Field is appropriate when one field has clearly drifted into the wrong existing class.

```
Heuristic:
  Moving ONE field to an EXISTING class → Move Field
  Moving SEVERAL related fields + methods into a NEW class → Extract Class
  Extract Class often starts with identifying multiple Move Field candidates
  that cluster around the same responsibility
```

### Section B2: Advanced Patterns

**Q10. How does Move Field apply in JavaScript's module system and closures?**

A: JavaScript modules and closures are the non-OOP equivalent of "class fields." Moving a field means changing which module or closure scope owns the variable:

```js
// BEFORE — cartTotal is computed inside CheckoutService but belongs to CartState
// checkout-service.js
import { getItems } from './cart-state.js';

export function processCheckout(userId) {
  const items = getItems(userId);
  const cartTotal = items.reduce((sum, i) => sum + i.price * i.qty, 0); // ← field-like
  const tax = cartTotal * 0.18;
  const grandTotal = cartTotal + tax;
  // ... use grandTotal
}

// AFTER — cartTotal computation (and its "field") moves to CartState
// cart-state.js
const _cartsByUser = new Map();

export function getItems(userId) { return _cartsByUser.get(userId) ?? []; }

export function getCartTotal(userId) { // ← moved here; this is where the data is
  return getItems(userId).reduce((sum, i) => sum + i.price * i.qty, 0);
}

// checkout-service.js
import { getCartTotal } from './cart-state.js';

export function processCheckout(userId) {
  const cartTotal = getCartTotal(userId); // delegate to the module that owns the data
  const tax = cartTotal * 0.18;
  const grandTotal = cartTotal + tax;
}
```

The principle is identical to OOP Move Field: the "field" (a computed value derived from data) should live in the module that owns the underlying data.

## Topic C: Extract Class and Inline Class

### Section C1: Fundamentals

**Q11. What is Extract Class, and what problem does it solve?**

A: Extract Class splits one class into two by pulling a cohesive subset of fields and methods out of a bloated class and giving them a new home. The original class retains a reference to the new class and delegates to it.

The problem it solves: **low cohesion**. A class with too many responsibilities violates the Single Responsibility Principle — it changes for multiple unrelated reasons, it is hard to test in isolation, and it accumulates methods that don't feel like they belong together.

```
Symptoms that demand Extract Class:
  ✗ The class name is hard to describe without using "and" ("UserAndBillingManager")
  ✗ The class has more than ~7–10 fields
  ✗ Some fields/methods form a natural cluster that's always modified together
  ✗ A subset of the class's tests could be written against a standalone object
  ✗ The class imports libraries from two unrelated domains (e.g. crypto + HTTP)
```

**Q12. Walk through a full Extract Class refactoring with before and after.**

A:

```js
// BEFORE — Person class doing too much: personal identity + contact + address
class Person {
  constructor({ name, dob, telephoneNumber, email, street, city, pinCode }) {
    this.name = name;
    this.dob = dob;
    this.telephoneNumber = telephoneNumber;
    this.email = email;
    this.street = street;
    this.city = city;
    this.pinCode = pinCode;
  }

  getAge() {
    return new Date().getFullYear() - new Date(this.dob).getFullYear();
  }

  getContactInfo() {
    return `${this.telephoneNumber} | ${this.email}`;
  }

  getAddress() {
    return `${this.street}, ${this.city} - ${this.pinCode}`;
  }

  getMailingLabel() {
    return `${this.name}\n${this.getAddress()}`;
  }
}

// AFTER — two new classes extracted; Person delegates
class ContactInfo {
  constructor({ telephoneNumber, email }) {
    this.telephoneNumber = telephoneNumber;
    this.email = email;
  }

  toString() {
    return `${this.telephoneNumber} | ${this.email}`;
  }
}

class Address {
  constructor({ street, city, pinCode }) {
    this.street = street;
    this.city = city;
    this.pinCode = pinCode;
  }

  toString() {
    return `${this.street}, ${this.city} - ${this.pinCode}`;
  }

  toMailingLabel(recipientName) {
    return `${recipientName}\n${this.toString()}`;
  }
}

class Person {
  constructor({ name, dob, contact, address }) {
    this.name = name;
    this.dob = dob;
    this.contact = new ContactInfo(contact);   // composed object
    this.address = new Address(address);       // composed object
  }

  getAge() {
    return new Date().getFullYear() - new Date(this.dob).getFullYear();
  }

  getContactInfo() { return this.contact.toString(); }     // delegation
  getAddress()     { return this.address.toString(); }     // delegation
  getMailingLabel(){ return this.address.toMailingLabel(this.name); }
}
```

**Q13. What are the mechanical steps for Extract Class?**

A:

```
1. IDENTIFY the cluster of fields and methods to extract. Name the new class.

2. CREATE the new class with its extracted fields and constructor.

3. ADD an instance of the new class as a field on the original class
   (in the constructor, initialize it using relevant constructor parameters).

4. MOVE each field: use Move Field (with forwarding accessors as the bridge).

5. MOVE each method that operates on those fields: use Move Method.
   Reduce the source method to a delegating call.

6. RUN tests after each Move Field and each Move Method.

7. REVIEW the interface: decide whether the new class should be public (clients
   interact with it directly) or private (hidden behind the original class's API).

8. REMOVE the forwarding delegators from the original class ONLY IF clients
   can be updated to go directly to the new class — otherwise keep the delegation.
```

**Q14. What is Inline Class, and when should you apply it instead of Extract Class?**

A: **Inline Class** is the inverse of Extract Class — it merges a small class into another by pulling its features back into its single user. Apply it when:

- A class has **too few responsibilities** to justify its existence — it's been over-extracted and is now just a thin shell.
- A class exists only to **delegate to another class** with no added value.
- After a series of refactorings, a class has been emptied of most of its logic and only a few stragglers remain.
- Two classes should be merged before **re-extracting** them into a better split (use Inline Class first to consolidate, then Extract Class to re-divide cleanly).

```js
// BEFORE — TelephoneNumber is barely a class: no behaviour, just a pair of strings
class TelephoneNumber {
  constructor(areaCode, number) {
    this.areaCode = areaCode;
    this.number = number;
  }
}

class Person {
  constructor(name, areaCode, number) {
    this.name = name;
    this._phone = new TelephoneNumber(areaCode, number);
  }

  get telephoneNumber() {
    return `(${this._phone.areaCode}) ${this._phone.number}`;
  }
}

// AFTER (Inline Class) — TelephoneNumber inlined into Person (it adds nothing)
class Person {
  constructor(name, areaCode, number) {
    this.name = name;
    this._areaCode = areaCode;   // fields inlined
    this._number = number;
  }

  get telephoneNumber() {
    return `(${this._areaCode}) ${this._number}`; // logic inlined
  }
}
```

The guideline: a class earns its existence through **behaviour**, not just data. Pure data holders that no methods operate on are candidates for Inline Class.

### Section C2: Advanced Patterns

**Q15. When should you choose Extract Class vs Extract Subclass?**

A: Both refactorings split a class, but they model different relationships:

| | **Extract Class** | **Extract Subclass** |
|---|---|---|
| **Relationship** | Composition ("has-a") | Inheritance ("is-a") |
| **When applicable** | Responsibility cluster that exists across all instances | Behaviour that applies only to *some* instances |
| **Flexibility** | An object can change its composed class at runtime | An object's class is fixed at construction |
| **Coupling** | Weaker — composed class can be tested/replaced independently | Stronger — subclass tightly couples to parent's internals |
| **Example** | `Person` *has a* `ContactInfo` | `Employee` *is a* `Person` |

Prefer **Extract Class (composition)** when:
- The extracted responsibility can vary independently (different `Address` strategies, `ContactInfo` types).
- The host object's type shouldn't change based on whether it has the sub-behaviour.
- You want to share the extracted class across multiple unrelated classes.

Prefer **Extract Subclass** when:
- The variation is truly "a special kind of" the parent.
- The subset of behaviour is fixed at construction and never changes at runtime.

```js
// Extract Subclass is right here — a Manager IS an Employee, not one that HAS management duties
class Employee { /* ... */ }
class Manager extends Employee {
  reports() { /* ... */ }
}

// Extract Class is right here — a Person HAS ContactInfo (can have many formats)
class Person {
  constructor(contactInfo) { this.contactInfo = contactInfo; }
}
```

## Topic D: Hide Delegate and Remove Middle Man

### Section D1: Fundamentals

**Q16. What is Hide Delegate, and what problem does it address?**

A: Hide Delegate adds a method on an intermediate object so that clients don't need to know about the delegate object that the intermediate holds. Instead of calling `person.getDepartment().getManager()`, clients call `person.getManager()` — the `Person` class "hides" its `Department` delegate.

The problem it addresses: **train wrecks** (method chains) that expose an object's internal structure to all callers. Every caller that writes `a.getB().getC()` is coupled to the fact that `A` holds a `B` and `B` holds a `C`. If `A` ever stops holding a `B` directly, every chain in the entire codebase breaks.

```js
// BEFORE — callers reach through Person → Department → Manager
class Department {
  constructor(chargeCode, manager) {
    this.chargeCode = chargeCode;
    this.manager = manager;
  }

  getManager() { return this.manager; }
}

class Person {
  constructor(name, department) {
    this.name = name;
    this._department = department;
  }

  getDepartment() { return this._department; } // exposes delegate
}

// ❌ Every caller is coupled to the Person → Department chain
const manager = employee.getDepartment().getManager();

// AFTER — Person hides its Department delegate
class Person {
  constructor(name, department) {
    this.name = name;
    this._department = department;
  }

  // getDepartment() is REMOVED — clients no longer need to know Department exists
  getManager() {
    return this._department.getManager(); // ← the "hidden delegate" call
  }
}

// ✅ Callers no longer depend on the Person → Department relationship
const manager = employee.getManager();
```

**Q17. What is the Law of Demeter, and how does it relate to Hide Delegate?**

A: The **Law of Demeter** (also "Don't Talk to Strangers") states that a method should only call methods on:

1. `this` — the object itself.
2. Parameters passed to the method.
3. Objects created within the method.
4. Direct fields (components) of `this`.

It does **not** allow calling methods on objects returned by calling another method — which is exactly what `a.getB().getC()` violates. Each `.` beyond the first step is a potential Law of Demeter violation.

Hide Delegate is the refactoring that enforces the Law of Demeter: by adding `a.getC()` as a delegating method, callers only talk to their direct acquaintance `a` — they no longer talk to the "stranger" `b`.

```
Law of Demeter diagnostic — count the dots:
  employee.getManager()                  ✓ one step — OK
  employee.getDepartment().getManager()  ✗ two steps — train wreck
  employee.getDepartment().getOffice().getBuilding().getCity()  ✗✗✗ deeply coupled
```

Note: the Law of Demeter is a guideline, not an absolute rule. It doesn't apply to **fluent APIs** (where method chaining is the designed interface) or **data structures** (where accessing `point.x` and `point.y` is intentional). Apply Hide Delegate when the chain traverses **encapsulated object relationships**, not when reading data properties.

**Q18. What is Remove Middle Man, and when is it the right choice?**

A: Remove Middle Man is the inverse of Hide Delegate. It eliminates an intermediate class that does nothing but delegate every call through to its underlying object. If `Person` has grown so many delegating methods (`getManager`, `getChargeCode`, `getOffice`, ...) that it is nothing more than a thin wrapper around `Department`, the delegation has become **the Middle Man problem**.

Apply Remove Middle Man when:
- The delegate object (`Department`) is exposed through so many methods that hiding it provides no real encapsulation — callers might as well just use `Department` directly.
- The intermediate object (`Person`) has no logic of its own around the delegated calls — it's a pure relay.
- The domain model has changed such that the original encapsulation is no longer warranted.

```js
// BEFORE — Person is just a middle man: everything delegates to Department
class Person {
  getManager()    { return this._department.getManager(); }
  getChargeCode() { return this._department.getChargeCode(); }
  getOffice()     { return this._department.getOffice(); }
  getHeadCount()  { return this._department.getHeadCount(); }
  // ... 8 more delegating methods — Person is just a Department proxy
}

// Callers must go through Person even though they always want Department behaviour
const manager    = person.getManager();
const chargeCode = person.getChargeCode();

// AFTER (Remove Middle Man) — expose Department directly; kill the delegators
class Person {
  constructor(name, department) {
    this.name = name;
    this.department = department; // ← made public (no more hiding)
  }
  // All delegating methods removed
}

// Callers access Department directly — the internal structure is no longer hidden,
// but the middle man indirection is gone
const manager    = person.department.getManager();
const chargeCode = person.department.getChargeCode();
```

### Section D2: Advanced Patterns

**Q19. How do you decide between Hide Delegate and Remove Middle Man?**

A: The decision turns on two factors: **encapsulation value** and **delegation ratio**.

```
                      High encapsulation value?
                           YES        NO
                        ┌──────┐  ┌──────────────┐
 Low delegation ratio   │ Hide │  │  Remove or   │
 (few delegate methods) │Deleg.│  │  do nothing  │
                        └──────┘  └──────────────┘
                        ┌──────┐  ┌──────────────┐
 High delegation ratio  │Both  │  │    Remove    │
 (many delegate methods)│ bad? │  │  Middle Man  │
                        └──────┘  └──────────────┘
```

Ask yourself:
- **Does hiding the delegate protect against structural change?** If `Person` might stop holding `Department` in the future (maybe managers can exist outside departments), Hide Delegate insulates callers from that change. Hiding adds value.
- **Is the intermediate adding any value beyond delegation?** If `Person.getManager()` validates permissions, logs access, or enriches the result — it earns its existence. If it only returns `this._department.getManager()` verbatim — it does not.
- **How many callers exist?** If only one or two callers traverse the chain, a local variable (`const dept = person.getDepartment()`) is simpler than adding delegation methods. If hundreds of callers exist, Hide Delegate (or Remove Middle Man) is worth the change.

The practical rule: **start with Hide Delegate** when first noticing a law-of-Demeter violation; **apply Remove Middle Man** when the delegating class has been hollowed out over time and is no longer adding value.

**Q20. What is the difference between Hide Delegate and the Facade pattern?**

A: They address similar surface symptoms (hiding complexity behind a simpler interface) but at different scopes and for different motivations:

| | **Hide Delegate** | **Facade** |
|---|---|---|
| **Scope** | One class delegating to one other class | One facade class simplifying an entire subsystem (many classes) |
| **Motivation** | Enforce Law of Demeter; prevent callers from depending on internal structure | Simplify complex subsystem API; provide a single entry point |
| **Direction** | Emergent — applied to fix an existing smell | Intentional — designed upfront |
| **Result** | Intermediate class grows delegation methods | A new class with a cohesive high-level API |
| **Example** | `Person.getManager()` hides `Department` | `OrderFacade.placeOrder()` hides `Inventory`, `Payment`, `Shipping` |

Hide Delegate is a **micro-refactoring** (one relationship). Facade is a **structural design pattern** (a subsystem interface). You might apply many Hide Delegate refactorings as part of building a Facade.

## Topic E: Introduce Foreign Method and Introduce Local Extension

### Section E1: Fundamentals

**Q21. What is Introduce Foreign Method, and when is it necessary?**

A: Introduce Foreign Method adds a method to a **client class** that provides functionality you wish the **server class** had — but can't add because you don't own or can't modify the server class (a third-party library, a framework class, a built-in). The method is placed on the client (or a utility module) and takes an instance of the server class as its first parameter.

```js
// Scenario: you want `Date` to have a `nextDay()` method, but you can't modify Date.

// BEFORE — the calculation is inline everywhere it's needed
class BillingService {
  getNextBillingDate(currentDate) {
    // Repeated in-line logic — not reusable
    const next = new Date(currentDate);
    next.setDate(next.getDate() + 1);
    return next;
  }
}

class ReminderService {
  scheduleReminder(currentDate) {
    // Duplicated in-line logic
    const next = new Date(currentDate);
    next.setDate(next.getDate() + 1);
    sendReminder(next);
  }
}

// AFTER — Introduce Foreign Method as a utility function (non-OOP JS style)
// date-utils.js — the "foreign method" for the Date "server class"
/**
 * Foreign Method: nextDay(date)
 * Should be a method on Date, but Date is not modifiable.
 * First parameter is the server class instance — the convention for foreign methods.
 */
export function nextDay(date) {
  const next = new Date(date);
  next.setDate(next.getDate() + 1);
  return next;
}

// Callers use the utility instead of the inline logic
import { nextDay } from './date-utils.js';

class BillingService {
  getNextBillingDate(currentDate) {
    return nextDay(currentDate); // ← clean, reusable
  }
}
```

The key property of a Foreign Method: it should be **commented** (or named in a module) to indicate it is a Foreign Method for a specific server class — so future maintainers know where it would ideally live and don't duplicate it.

**Q22. What is Introduce Local Extension, and when should you subclass vs. wrap?**

A: When a single Foreign Method isn't enough — when you need **many** new behaviours on a server class you can't modify — Introduce Local Extension creates a new class that extends the server class with all the needed additions. There are two forms:

**Subclass form** (extend the server class):

```js
// MutableDate extends Date and adds domain-specific methods
class MutableDate extends Date {
  nextDay() {
    const d = new MutableDate(this);
    d.setDate(d.getDate() + 1);
    return d;
  }

  previousDay() {
    const d = new MutableDate(this);
    d.setDate(d.getDate() - 1);
    return d;
  }

  startOfMonth() {
    return new MutableDate(this.getFullYear(), this.getMonth(), 1);
  }
}

const today = new MutableDate();
console.log(today.nextDay()); // clean extension method
```

**Wrapper form** (hold a reference to the server class instance):

```js
// RichDate wraps Date rather than extending it
class RichDate {
  constructor(date) {
    this._date = date instanceof Date ? date : new Date(date);
  }

  // Expose the original Date's interface where needed:
  toISOString() { return this._date.toISOString(); }
  getTime()     { return this._date.getTime(); }

  // Added extension methods:
  nextDay() {
    return new RichDate(new Date(this._date).setDate(this._date.getDate() + 1));
  }

  format(pattern) {
    // custom formatting unavailable on raw Date
    return pattern
      .replace('YYYY', this._date.getFullYear())
      .replace('MM', String(this._date.getMonth() + 1).padStart(2, '0'))
      .replace('DD', String(this._date.getDate()).padStart(2, '0'));
  }
}

const today = new RichDate(new Date());
console.log(today.format('YYYY-MM-DD'));
console.log(today.nextDay().toISOString());
```

**When to choose subclass vs. wrapper:**

| | **Subclass** | **Wrapper** |
|---|---|---|
| **Passes `instanceof` checks** | Yes (`instanceof Date` still works) | No (it's a different type) |
| **Applicable when server is** | Not `final`/sealed; subclassing is not forbidden | Any class, including sealed or frozen ones |
| **Risk** | Fragile base class problem; server constructor quirks | Wrapper interface can drift; must proxy every needed method |
| **Prefer when** | Strong need for type compatibility | Server class is sealed, or subclassing is unreliable (e.g., built-ins like `Array` in older JS) |

### Section E2: Advanced Patterns

**Q23. How do Foreign Method and Local Extension relate to the Open/Closed Principle?**

A: The **Open/Closed Principle** states that a class should be open for extension but closed for modification. Foreign Method and Local Extension are practical applications: instead of modifying a closed server class, you extend its behaviour without changing it.

The pattern also reveals a design tension: Foreign Methods and Local Extensions are workarounds for a server class that is either literally unmodifiable (third-party) or should be unmodifiable (stable API). They acknowledge that the ideal design — adding the method to the server class — is unavailable.

In modern JavaScript/TypeScript, Local Extension (wrapper form) is the idiomatic choice over inheritance:

```ts
// TypeScript wrapper with full type safety — extends without subclassing
class RichArray<T> {
  constructor(private readonly items: T[]) {}

  groupBy<K extends string>(keyFn: (item: T) => K): Record<K, T[]> {
    return this.items.reduce((acc, item) => {
      const key = keyFn(item);
      (acc[key] ??= []).push(item);
      return acc;
    }, {} as Record<K, T[]>);
  }

  unique(): T[] {
    return [...new Set(this.items)];
  }

  // Proxy essential Array methods:
  map<U>(fn: (item: T, i: number) => U): RichArray<U> {
    return new RichArray(this.items.map(fn));
  }

  toArray(): T[] {
    return [...this.items];
  }
}

const orders = new RichArray([
  { status: 'paid', amount: 100 },
  { status: 'pending', amount: 200 },
  { status: 'paid', amount: 150 },
]);

const byStatus = orders.groupBy(o => o.status);
// { paid: [...], pending: [...] } — functionality Array doesn't provide natively
```

## Topic F: Cross-Topic & Interview-Style Questions

**Q24. "Explain the goal of Moving Features between Objects in one paragraph."**

A: Every class should own the data and behaviour that naturally belong together — this is cohesion. When a feature (a method, a field, a responsibility) ends up in the wrong class, every piece of code that needs it has to reach across class boundaries, coupling unrelated things together and making both classes harder to change. The Move Method, Move Field, Extract Class, Inline Class, Hide Delegate, and Remove Middle Man refactorings all serve the same goal: place each responsibility in the class that knows the most about it, so that each class is self-contained, easy to test in isolation, and insulated from changes in other classes. Done incrementally and with tests running at every step, these refactorings continuously nudge the design toward one where the code reads like a natural description of the problem domain — each class clearly named, clearly bounded, and clearly useful.

**Q25. "Given this code, identify the smell and name the correct refactoring."**

```js
class Invoice {
  constructor(customer, lineItems) {
    this.customer = customer;
    this.lineItems = lineItems;
  }

  // (a)
  getCustomerCity() {
    return this.customer.address.city;
  }

  // (b)
  applyLoyaltyDiscount() {
    if (this.customer.membershipYears > 3 && this.customer.isPremium) {
      return this.lineItems.reduce((sum, i) => sum + i.price, 0) * 0.9;
    }
    return this.lineItems.reduce((sum, i) => sum + i.price, 0);
  }

  // (c)
  getSubtotal() {
    return this.lineItems.reduce((sum, i) => sum + i.price, 0);
  }

  // (d)
  render() {
    const html = `<div>${this.customer.name}</div>`;
    const pdfBytes = this._generatePDF(html);
    this._sendToPrinter(pdfBytes);
  }
}
```

A:

| Method | Smell | Refactoring |
|--------|-------|-------------|
| **(a) `getCustomerCity`** | Train wreck / Law of Demeter violation (`this.customer.address.city`) | **Hide Delegate** — add `Customer.getCity()` that hides the `Address` delegate; or **Move Method** — `Invoice.getCustomerCity()` envies `Customer` and `Address` |
| **(b) `applyLoyaltyDiscount`** | Feature Envy — accesses `customer.membershipYears`, `customer.isPremium` repeatedly | **Move Method** — move to `Customer` as `customer.loyaltyDiscountFor(subtotal)` |
| **(c) `getSubtotal`** | None significant — `Invoice` legitimately owns `lineItems` and this is a true invoice responsibility | No change needed |
| **(d) `render`** | Too many responsibilities — Invoice should NOT know about PDF generation and printing | **Extract Class** — create `InvoiceRenderer` or `InvoicePrinter`; Invoice produces data, renderer formats it |

**Q26. What is the correct order to apply these refactorings, and why does order matter?**

A: Order matters because each refactoring changes the class structure and affects what subsequent refactorings act on. The recommended sequence for a bloated class:

```
1. MOVE FIELD first — fields are the anchor. Misplaced fields pull methods toward
   the wrong class. Moving fields first gives methods a stable, correct home
   to follow. Tests of the field's behaviour don't change — only location changes.

2. MOVE METHOD next — once fields are in the right class, methods that reference
   those fields have a clear target. Feature Envy is easier to resolve when
   the envied data is already correctly placed.

3. EXTRACT CLASS after field + method moves — once you've moved a cluster of
   fields and methods together, Extract Class formalises the new boundary.
   Trying to Extract Class before moving members often moves the wrong things.

4. HIDE DELEGATE / REMOVE MIDDLE MAN last — once class responsibilities are
   correctly assigned, then adjust the inter-class communication protocol.
   Hiding a delegate into an already-bloated class just adds more methods to
   the wrong class.

5. INTRODUCE LOCAL EXTENSION only if server class is truly unmodifiable.
   Prefer adding to the server class directly if you own it.
```

**Q27. "In one sentence each, state the key property of each major refactoring in this topic."**

A:
- **Move Method**: relocates a method to the class it talks to most — coupling follows cohesion.
- **Move Field**: relocates a field to the class that uses it most — data should live where it's modified.
- **Extract Class**: splits a class that has grown multiple responsibilities into two focused, testable classes.
- **Inline Class**: merges a class that has shrunk to near-uselessness back into its only consumer.
- **Hide Delegate**: adds delegation methods to an intermediate class so callers do not depend on its internal structure.
- **Remove Middle Man**: removes an intermediate class that has become a hollow relay, restoring direct access to the underlying object.
- **Introduce Foreign Method**: adds extension behaviour for a server class you cannot modify, as a utility function parameterised on the server class instance.
- **Introduce Local Extension**: creates a subclass or wrapper around an unmodifiable server class to provide a full set of new behaviours as a first-class object.

## Problem 1 — Eliminate Feature Envy with Move Method

### Problem

The following `ReportGenerator` class has a clear Feature Envy smell. Identify it, name the refactoring, and apply it step by step.

```js
class Employee {
  constructor({ name, baseSalary, department, performanceRating, yearsOfService }) {
    this.name = name;
    this.baseSalary = baseSalary;
    this.department = department;
    this.performanceRating = performanceRating; // 1.0–5.0
    this.yearsOfService = yearsOfService;
  }
}

class ReportGenerator {
  generateSalaryReport(employees) {
    return employees.map(emp => {
      // ❌ This block only touches Employee data — Feature Envy
      let bonus = 0;
      if (emp.performanceRating >= 4.5) bonus = emp.baseSalary * 0.2;
      else if (emp.performanceRating >= 3.5) bonus = emp.baseSalary * 0.1;

      const loyaltyBonus = emp.yearsOfService > 5 ? emp.baseSalary * 0.05 : 0;
      const totalComp = emp.baseSalary + bonus + loyaltyBonus;

      return {
        name: emp.name,
        department: emp.department,
        totalCompensation: totalComp,
      };
    });
  }
}
```

### Pattern Recognition

The inner block of `generateSalaryReport` accesses `emp.performanceRating`, `emp.baseSalary`, and `emp.yearsOfService` — three of `Employee`'s own fields — to compute the employee's total compensation. `ReportGenerator` is envying `Employee`'s data. This is a textbook **Move Method** scenario.

### Key Insight

The calculation "what is this employee's total compensation?" is a question about an `Employee`. The answer depends entirely on `Employee`'s data. It belongs in `Employee`. `ReportGenerator` should ask the employee for its compensation, not compute it itself.

### Approach

1. Identify the envious block.
2. Define the method signature on `Employee` — what input does it need (none: all data is already on `this`) and what does it return (the total compensation number).
3. Copy the body to `Employee`, replacing `emp.` with `this.`.
4. Replace the original block with a delegation call to `emp.calculateTotalCompensation()`.
5. Run tests. Remove the old inline block.

### Full Refactoring

```js
// STEP 1 — Identify the Feature Envy block (annotated above)

// STEP 2-3 — Add method to Employee (copy and adjust)
class Employee {
  constructor({ name, baseSalary, department, performanceRating, yearsOfService }) {
    this.name = name;
    this.baseSalary = baseSalary;
    this.department = department;
    this.performanceRating = performanceRating;
    this.yearsOfService = yearsOfService;
  }

  // ✅ Moved here — operates only on own data, no parameters needed
  calculateTotalCompensation() {
    let bonus = 0;
    if (this.performanceRating >= 4.5) bonus = this.baseSalary * 0.2;
    else if (this.performanceRating >= 3.5) bonus = this.baseSalary * 0.1;

    const loyaltyBonus = this.yearsOfService > 5 ? this.baseSalary * 0.05 : 0;
    return this.baseSalary + bonus + loyaltyBonus;
  }
}

// STEP 4 — Replace envious block with delegation
class ReportGenerator {
  generateSalaryReport(employees) {
    return employees.map(emp => ({
      name: emp.name,
      department: emp.department,
      totalCompensation: emp.calculateTotalCompensation(), // ✅ clean delegation
    }));
  }
}
```

### Dry Run

```
Input: [
  { name: 'Priya', baseSalary: 100_000, performanceRating: 4.8, yearsOfService: 7, ... },
  { name: 'Raj',   baseSalary:  80_000, performanceRating: 3.2, yearsOfService: 3, ... },
]

Employee('Priya').calculateTotalCompensation():
  bonus = 100_000 * 0.2 = 20_000     (rating 4.8 >= 4.5)
  loyaltyBonus = 100_000 * 0.05 = 5_000  (7 years > 5)
  total = 100_000 + 20_000 + 5_000 = 125_000

Employee('Raj').calculateTotalCompensation():
  bonus = 0                          (rating 3.2 < 3.5)
  loyaltyBonus = 0                   (3 years ≤ 5)
  total = 80_000

Report:
[
  { name: 'Priya', department: '...', totalCompensation: 125_000 },
  { name: 'Raj',   department: '...', totalCompensation: 80_000  },
]
```

### What We Gained

- `Employee` is now self-contained: it knows how to compute its own compensation. Any future caller (payroll, dashboard, PDF export) asks `emp.calculateTotalCompensation()` — not re-implements the logic.
- `ReportGenerator` has zero knowledge of compensation rules — it only formats data. If bonus percentages change, only `Employee` changes.
- Unit testing the compensation rule requires constructing only an `Employee`, no `ReportGenerator`.

### Edge Cases
- **Multiple callers** that duplicated the inline logic: all of them are now replaced with a single call — a consistency guarantee.
- **Subclasses of Employee** (e.g., `Contractor`) can override `calculateTotalCompensation()` with different rules — polymorphism becomes possible after the move.
- **If the method needs data from multiple classes** (e.g., dept-level multipliers from `Department`): pass the needed value as a parameter: `calculateTotalCompensation(deptMultiplier)`.

### Follow-up Questions
- "What if `ReportGenerator` needs to format differently for different report types?" → Keep `ReportGenerator` as is but pass a formatter strategy. The compensation calculation stays in `Employee` regardless.
- "How would you test `calculateTotalCompensation` after the move?" → Construct an `Employee` directly with known values and assert the computed total. No `ReportGenerator` needed in the test.

## Problem 2 — Decompose a God Class with Extract Class

### Problem

Refactor the bloated `UserAccount` class into focused, cohesive classes. Identify the responsibility clusters, name the resulting classes, and show the before/after with the mechanical steps.

```js
class UserAccount {
  constructor(data) {
    // Identity
    this.userId = data.userId;
    this.username = data.username;
    this.passwordHash = data.passwordHash;
    this.lastLoginAt = data.lastLoginAt;
    this.failedLoginAttempts = data.failedLoginAttempts;
    this.isLocked = data.isLocked;

    // Profile
    this.displayName = data.displayName;
    this.bio = data.bio;

  verifyPassword(plaintext) { return bcryptCompare(plaintext, this.passwordHash); }
```

### Pattern Recognition

**God Class** (also called Blob) — `UserAccount` has at least three unrelated responsibility clusters:
1. **Authentication state** — password, login attempts, lock status.
2. **Public profile** — display name, bio, avatar, timezone.
3. **Billing** — plan, subscription status, payment, billing dates.

Each cluster changes for different reasons: auth changes when the security policy changes; profile changes when UX requires new user-facing fields; billing changes when the pricing model changes. They satisfy the classic **Extract Class** trigger: multiple independent reasons to change.

### Key Insight

`UserAccount` should be an identity anchor — it holds `userId` and references to its sub-responsibilities. The sub-responsibilities are independently testable, independently deployable, and independently evolvable. The class name itself reveals the problem: it manages both *account* security AND *user* data AND billing — "UserAccount" is doing three jobs.

### Approach

1. Identify the three clusters.
2. Create `AuthCredentials`, `UserProfile`, and `BillingInfo` classes.
3. For each cluster: Move Fields using bridge accessors → Move Methods → Run tests.
4. Replace fields on `UserAccount` with composed objects.
5. Decide whether `UserAccount` should delegate (Hide Delegate) or expose the sub-objects.

### Full Refactoring

```js
// ── Step 2-3a: Extract AuthCredentials ──────────────────────────────────────
class AuthCredentials {
  constructor({ passwordHash, lastLoginAt, failedLoginAttempts, isLocked }) {
    this.passwordHash = passwordHash;
    this.lastLoginAt = lastLoginAt;
    this.failedLoginAttempts = failedLoginAttempts;
    this.isLocked = isLocked;
  }

  async verify(plaintext) {
    return bcryptCompare(plaintext, this.passwordHash);
  }

  recordFailedLogin() {
    this.failedLoginAttempts++;
    if (this.failedLoginAttempts >= 5) this.isLocked = true;
  }

  resetFailedLogins() {
    this.failedLoginAttempts = 0;
    this.isLocked = false;
  }
}

// ── Step 2-3b: Extract UserProfile ──────────────────────────────────────────

    this.bio = bio;
    this.avatarUrl = avatarUrl;
    this.timezone = timezone;

  update({ displayName, bio, avatarUrl, timezone }) {
    if (displayName !== undefined) this.displayName = displayName;

    if (avatarUrl  !== undefined) this.avatarUrl   = avatarUrl;
    if (timezone   !== undefined) this.timezone    = timezone;
  }

  toSummary() {
    return { displayName: this.displayName, bio: this.bio, avatarUrl: this.avatarUrl };

}

// ── Step 2-3c: Extract BillingInfo ──────────────────────────────────────────
class BillingInfo {
  constructor({ planId, subscriptionStatus, nextBillingDate, paymentMethodLast4 }) {
    this.planId = planId;
    this.subscriptionStatus = subscriptionStatus;
    this.nextBillingDate = nextBillingDate;
    this.paymentMethodLast4 = paymentMethodLast4;
  }

  isSubscriptionActive() {
    return this.subscriptionStatus === 'active';
  }

  daysUntilNextBilling() {
    const ms = new Date(this.nextBillingDate) - Date.now();
    return Math.ceil(ms / 86_400_000);
  }

  toSummary() {
    return {
      planId: this.planId,
      status: this.subscriptionStatus,
      nextBillingDate: this.nextBillingDate,
    };
  }
}

// ── Step 4-5: Slim UserAccount — identity anchor + composed sub-objects ──────
class UserAccount {
  constructor(data) {
    this.userId   = data.userId;
    this.username = data.username;

    // Composed objects — each owns its responsibility
    this.auth    = new AuthCredentials(data);
    this.profile = new UserProfile(data);
    this.billing = new BillingInfo(data);
  }

  // Decide: expose sub-objects directly (Remove Middle Man)
  // OR provide selective delegation (Hide Delegate) for high-use paths.
  // Here: expose sub-objects (they're part of the public contract),
  // but provide ONE convenience delegation for the most common auth check:
  async verifyPassword(plaintext) {
    return this.auth.verify(plaintext); // high-frequency path — worth delegating
  }
}
```

### Usage Comparison

```js
// BEFORE — one class, mixed concerns
const user = new UserAccount(data);
user.recordFailedLogin();
user.updateDisplayName('New Name');
user.isSubscriptionActive();

// AFTER — each concern clearly owned
const user = new UserAccount(data);
user.auth.recordFailedLogin();        // auth concern
user.profile.update({ displayName: 'New Name' }); // profile concern
user.billing.isSubscriptionActive();  // billing concern

// Testing is now independent:
// Auth tests → new AuthCredentials({ passwordHash, failedLoginAttempts: 0, ... })
// Billing tests → new BillingInfo({ planId: 'pro', subscriptionStatus: 'active', ... })
// No need to construct a full UserAccount for either
```

### Complexity
- Construction: same O(1) — just initialises three inner objects.
- The three sub-classes are individually serialisable, cacheable, and replaceable.

### Edge Cases
- **Serialisation**: `UserAccount.toJSON()` should delegate to `this.auth`, `this.profile`, and `this.billing` — each knows how to serialise itself.
- **Database mapping**: each sub-class maps to its own table row or sub-document — the extraction mirrors the relational/document schema split.
- **Over-extraction risk**: don't create a sub-class for every pair of fields. A `UserPreferences` with one field is premature — wait until the cluster has at least 3–4 cohesive members.

### Follow-up Questions
- "Should `UserAccount` expose its sub-objects or hide them?" → Expose them if callers legitimately work with profile/billing independently (they do here). Hide them only if `UserAccount` controls which parts of the sub-objects are accessible.
- "How do you handle persistence — save `UserAccount` as one record or separate tables?" → Extract Class maps naturally to separate tables; `userId` is the foreign key linking them.

## Problem 3 — Untangle a Delegation Chain with Hide Delegate

### Problem

The following code violates the Law of Demeter. Apply Hide Delegate to the correct level, then identify when Remove Middle Man would be more appropriate.

```js
class Building {
  constructor(address, departments) {
    this.address = address;
    this.departments = departments; // Map<string, Department>
  }

  getDepartment(name) { return this.departments.get(name); }
}

class Department {
  constructor(name, employees) {
    this.name = name;
    this.employees = employees; // Employee[]
  }

  getManager() { return this.employees.find(e => e.isManager); }
  getEmployeeCount() { return this.employees.length; }
}

class Employee {
  constructor({ name, isManager, email }) {
    this.name = name;
    this.isManager = isManager;
    this.email = email;
  }
}

// ❌ Caller traverses a 3-level chain — Law of Demeter violation
function sendManagerEmail(building, deptName) {
  const manager = building
    .getDepartment(deptName)    // Building → Department
    .getManager();               // Department → Employee
  sendEmail(manager.email);     // Employee.email
}
```

### Pattern Recognition

The chain `building.getDepartment(x).getManager()` is a train wreck — `sendManagerEmail` must know about three objects (`Building`, `Department`, `Employee`). Any structural change (e.g., buildings have wings that have departments) would require updating every such chain.

### Key Insight

Apply Hide Delegate at the level where it adds durable encapsulation. The question is: should `Building` know how to find a department's manager? Or should `Department` know how to find a manager's email directly? Apply the principle incrementally — hide the most valuable boundary first.

### Full Refactoring

```js
// ── Step 1: Hide Delegate on Department — manager email is a Department concern
class Department {
  constructor(name, employees) {
    this.name = name;
    this.employees = employees;
  }

  getManager() { return this.employees.find(e => e.isManager); }
  getEmployeeCount() { return this.employees.length; }

  // ✅ New: hides the Employee delegate from callers of Department
  getManagerEmail() {
    return this.getManager()?.email ?? null;
  }
}

// ── Step 2: Hide Delegate on Building — hides the Department delegate
class Building {
  constructor(address, departments) {
    this.address = address;
    this.departments = departments;
  }

  getDepartment(name) { return this.departments.get(name); }

  // ✅ New: hides the Department delegate from callers of Building
  getDepartmentManagerEmail(deptName) {
    return this.getDepartment(deptName)?.getManagerEmail() ?? null;
  }
}

// ✅ Caller now talks only to Building — no knowledge of Department or Employee
function sendManagerEmail(building, deptName) {
  const email = building.getDepartmentManagerEmail(deptName);
  if (email) sendEmail(email);
}
```

### When to Apply Remove Middle Man Instead

```js
// Scenario: Building has accumulated 12 delegating methods for Department
class Building {
  getDepartmentManager(name) { ... }
  getDepartmentManagerEmail(name) { ... }
  getDepartmentHeadCount(name) { ... }
  getDepartmentBudget(name) { ... }
  getDepartmentProjects(name) { ... }
  // ... 7 more delegating methods
  
  // Building has become a Department proxy — it IS the Middle Man
}

// Apply Remove Middle Man: expose getDepartment() and let callers work with Department
class Building {
  constructor(address, departments) {
    this.address = address;
    this.departments = departments;
  }

  getDepartment(name) { return this.departments.get(name); } // only this survives
  // Remove all the delegating methods — they offered no encapsulation benefit
}

// Callers use getDepartment() once (stored in a variable) then work with Department:
function sendManagerEmail(building, deptName) {
  const dept = building.getDepartment(deptName);  // one step, assign to variable
  const email = dept?.getManagerEmail();
  if (email) sendEmail(email);
}
```

### Decision Trace

```
Does hiding the delegate protect against realistic structural change?
  Building → Department relationship is STABLE (unlikely to change) → weaker argument for hiding

Does the intermediate class add logic around the delegation?
  Building adds no logic — pure pass-through → argument FOR Remove Middle Man

How many callers exist for each delegating method?
  If getDepartmentManagerEmail() is called 40 times → Hide Delegate saves 40 updates on change
  If it's called twice → local variable at each callsite is simpler

Result for this example:
  Hide getDepartment(name).getManager() behind Department.getManagerEmail() → YES (high value)
  Hide getDepartment(name) itself behind 12 Building methods → NO (Middle Man)
```

### Follow-up Questions
- "What if `Department` is owned by a different team and you can't add methods to it?" → Use **Introduce Foreign Method** — add `getDepartmentManagerEmail(dept)` as a utility function outside both classes.
- "What about deeply nested chains: `a.b().c().d().e()`?" → Apply Hide Delegate at the most stable boundary; flatten the rest using intermediate variables — not every chain needs delegating wrappers.

## Problem 4 — Introduce Local Extension for an Unmodifiable Dependency

### Problem

Your application uses a third-party `Invoice` class from a library you cannot modify. You need to add three methods: `totalWithTax(rate)`, `toCSVRow()`, and `isPastDue()`. Implement a Local Extension using the **wrapper form** and explain why you chose wrapper over subclass.

```js
// Third-party library — you CANNOT modify this
class Invoice {
  constructor({ invoiceId, customerId, lineItems, dueDate, paidAt }) {
    this.invoiceId = invoiceId;
    this.customerId = customerId;
    this.lineItems = lineItems; // [{ description, amount }]
    this.dueDate = dueDate;
    this.paidAt = paidAt;
  }

  getSubtotal() {
    return this.lineItems.reduce((sum, li) => sum + li.amount, 0);
  }

  isPaid() {
    return this.paidAt !== null;
  }
}
```

### Pattern Recognition

You need **multiple** new behaviours on a class you don't own — the signature use case for **Introduce Local Extension**. Wrapper form is preferred because: (a) third-party classes often have constructor constraints that make subclassing fragile, (b) the library might seal the class in a future version, (c) you don't need `instanceof Invoice` to hold on the wrapper (you control all call sites).

### Key Insight

The wrapper holds a reference to the original `Invoice` and forwards calls to it where needed. New methods operate on the original's data (accessed via the delegated calls). The wrapper is a first-class object — it can be passed, stored, and returned like any other object, with all the original's functionality plus the extensions.

### Solution

```js
class RichInvoice {
  constructor(invoice) {
    if (!(invoice instanceof Invoice)) {
      throw new TypeError('RichInvoice requires an Invoice instance');
    }
    this._invoice = invoice; // wrapped instance
  }

  // ── Proxy essential Invoice methods ───────────────────────────────────────
  get invoiceId()    { return this._invoice.invoiceId; }
  get customerId()   { return this._invoice.customerId; }
  get lineItems()    { return this._invoice.lineItems; }
  get dueDate()      { return this._invoice.dueDate; }
  get paidAt()       { return this._invoice.paidAt; }

  getSubtotal()      { return this._invoice.getSubtotal(); }
  isPaid()           { return this._invoice.isPaid(); }

  // ── Extension methods (the "foreign methods" we need) ─────────────────────

  /**
   * Extension 1: Total with tax applied.
   * Wish this were on Invoice — but it isn't.
   */
  totalWithTax(taxRate) {
    const subtotal = this.getSubtotal();
    return subtotal + subtotal * taxRate;
  }

  /**
   * Extension 2: Serialise to a CSV row string.
   */
  toCSVRow() {
    const subtotal = this.getSubtotal().toFixed(2);
    const dueDate  = new Date(this.dueDate).toISOString().slice(0, 10);
    const status   = this.isPaid() ? 'paid' : 'unpaid';
    return `${this.invoiceId},${this.customerId},${subtotal},${dueDate},${status}`;
  }

  /**
   * Extension 3: Determine if the invoice is past its due date and unpaid.
   */
  isPastDue() {
    if (this.isPaid()) return false;
    return new Date(this.dueDate) < new Date();
  }

  // ── Factory convenience ───────────────────────────────────────────────────
  static wrap(invoice) {
    return new RichInvoice(invoice);
  }

  static wrapAll(invoices) {
    return invoices.map(inv => new RichInvoice(inv));
  }
}
```

### Usage

```js
// Typical usage — wrap at the boundary where you receive the third-party object
const rawInvoices = await invoiceApi.fetchForCustomer(customerId);
const invoices    = RichInvoice.wrapAll(rawInvoices);

// All original behaviour available:
console.log(invoices[0].getSubtotal());   // forwarded to Invoice
console.log(invoices[0].isPaid());         // forwarded to Invoice

// Extension methods:
console.log(invoices[0].totalWithTax(0.18));   // new
console.log(invoices[0].toCSVRow());            // new

// Report: past-due invoices
const pastDue = invoices.filter(inv => inv.isPastDue());
const csv = ['id,customerId,subtotal,dueDate,status',
             ...pastDue.map(inv => inv.toCSVRow())].join('\n');
```

### Why Wrapper Over Subclass Here

```
Subclass form (class RichInvoice extends Invoice):
  ✗ Third-party Invoice constructor might do unexpected side effects
  ✗ Library might make Invoice final/sealed in a future release
  ✗ No guarantee that Invoice's internal methods called by the library work
    with RichInvoice's constructor (super() call may not be safe)
  ✗ Can break if Invoice changes its constructor signature

Wrapper form (this._invoice = invoice):
  ✓ Completely decoupled from Invoice's constructor — we just hold a reference
  ✓ Library updates don't affect the wrapper's structure
  ✓ Easy to mock in tests — pass a fake Invoice with required methods
  ✓ Can wrap instances created by the library's own factory methods
  ✓ Explicit proxy methods make the delegation contract visible
```

### Complexity
- Construction: O(1) — stores a reference.
- All proxied methods: O(1) overhead beyond the delegated call.
- Extension methods: O(L) where L = number of line items for subtotal-based calculations.

### Edge Cases
- **Incomplete proxy**: if callers use a method on `Invoice` that you haven't proxied in `RichInvoice`, it will be `undefined`. Document the proxied surface clearly; add proxies on demand.
- **Library updates `Invoice`**: new methods on `Invoice` won't automatically appear on `RichInvoice` (unlike subclassing). This is a maintenance cost of the wrapper form — accept it when subclassing risks are higher.
- **`JSON.stringify` on wrapper**: since `RichInvoice` doesn't have the raw fields directly, `JSON.stringify` will produce `{}`. Add a `toJSON()` method that delegates to the inner invoice or spreads its own proxied fields.

### Follow-up Questions
- "What if you need `instanceof Invoice` to return `true` on your wrapper?" → Use the subclass form (`extends Invoice`) — type compatibility is the one concrete advantage of subclassing.
- "How do you test the extension methods in isolation?" → Construct a plain `Invoice` (or a mock object with `getSubtotal()`, `isPaid()`, `dueDate`, `paidAt`) and pass it to `new RichInvoice(...)`. No need to hit the API.

## Quick Reference — Moving Features Cheat Sheet

```
REFACTORING DECISION TREE

  Is a method doing work that uses another class's data more than its own?
  ├── YES → Feature Envy → MOVE METHOD to the envied class
  └── NO  → continue

  Is a field accessed/modified by another class more than the owning class?
  ├── YES → MOVE FIELD to the class that uses it most
  └── NO  → continue

  Does a class have multiple unrelated responsibilities (changes for different reasons)?
  ├── YES → EXTRACT CLASS — give each cluster a focused class
  └── NO  → continue

  Has a class shrunk to near-uselessness — just a thin shell delegating everything?
  ├── YES → INLINE CLASS — merge it back into its only consumer
  └── NO  → continue

  Are callers traversing multi-step object chains (train wrecks)?
  ├── YES and chain is worth hiding → HIDE DELEGATE
  ├── YES and intermediate is just a proxy → REMOVE MIDDLE MAN
  └── NO  → continue

  Do you need behaviour on a class you cannot modify?
  ├── ONE new method needed → INTRODUCE FOREIGN METHOD (utility function)
  └── MULTIPLE new methods needed → INTRODUCE LOCAL EXTENSION
        ├── Need instanceof compatibility → SUBCLASS form
        └── Constructor is risky / class may be sealed → WRAPPER form

KEY RULES:
  ✓ Move Field BEFORE Move Method — let data settle first, then move behaviour
  ✓ Test after every individual move — one move per commit is not overkill
  ✓ Leave a delegating stub on the original until ALL callers are updated
  ✓ Hide Delegate adds a method to the INTERMEDIATE class, not the client
  ✓ Remove Middle Man REMOVES delegating methods; it does NOT add new ones
  ✓ Foreign Method → pass the server class instance as the FIRST parameter
  ✓ Local Extension wraps/extends the server class, NOT the client class

SMELLS → REFACTORINGS MAPPING:
  Feature Envy              → Move Method
  Data Clumps               → Extract Class (Move Field)
  Large Class / God Class   → Extract Class (repeated)
  Lazy Class                → Inline Class
  Message Chains / Train Wreck → Hide Delegate
  Middle Man                → Remove Middle Man
  Inappropriate Intimacy    → Move Method + Move Field (bidirectional)
  Incomplete Library Class  → Introduce Foreign Method / Local Extension

SAFETY CHECKLIST — before removing the bridge:
  □ All tests pass with the new method in place
  □ All callers updated to use the new location
  □ No remaining references to the field/method in the old class
  □ Subclass overrides checked and moved if needed
  □ Serialisation/persistence layer updated if fields moved
```

## Common Mistakes Checklist

Before applying or reviewing a Move Features refactoring, verify:

1. **Moving a method when the real fix is Extract Class?** — If a method envies two different classes equally (accessing `customer.x` and `address.y` in equal measure), moving it to either one is wrong. Extract a third class (`ShippingDetails`) that owns both data points — then the method stops envying anyone.

2. **Removing the original method before all callers are updated?** — Always keep the delegating stub until every single call site has been updated and tests pass. Removing the bridge prematurely causes runtime errors that are hard to trace. Delete only after a full test run with zero references to the old location.

3. **Applying Hide Delegate when Remove Middle Man is the correct choice?** — If the intermediate class already has 8+ delegating methods and no logic of its own, adding one more delegation (Hide Delegate) just deepens the Middle Man problem. Audit how many delegating methods exist before adding another.

4. **Moving a method that overrides a parent class method?** — Silently moving an overriding method to the target class removes the polymorphic override from the hierarchy. Always check `grep` / IDE's "find usages" for `super.methodName()` calls before moving a potentially-overriding method.

5. **Creating an Extract Class that immediately becomes a data class?** — If the new class only has fields and getters/setters with no real behaviour, it's not a proper class — it's a struct. Either leave the fields in the original class (wait for behaviour to emerge) or ensure you also move the methods that operate on those fields.

6. **Applying Inline Class to a class that IS doing meaningful work?** — Just because a class is small doesn't mean it should be inlined. A `Money` class with two fields (`amount`, `currency`) and a `toString()` method earns its existence through semantic clarity. Only inline when the class is a *hollow relay* with no identity of its own.

7. **Introducing a Foreign Method using monkey-patching (`Date.prototype.nextDay = ...`)?** — This is the opposite of Foreign Method — it modifies the server class's prototype, affecting every use of `Date` globally. Foreign Method adds behaviour to the *client*, not the server. Monkey-patching violates the Open/Closed Principle and creates hard-to-trace bugs.

8. **Building a Local Extension wrapper that leaks the wrapped object?** — If your wrapper exposes `getRaw()` or `unwrap()` that returns the inner instance, callers will bypass the wrapper for convenience. The internal structure escapes and the encapsulation benefit disappears. Expose only what callers need through explicit proxy methods.

9. **Moving a method without checking its visibility contract?** — A `public` method that moves may need to become `public` on the target class, which changes the target's API surface. A `private` method moving to `public` on another class is an API change. Always consider the visibility implications of the move.

10. **Not updating the class name after Extract Class leaves one class clearly misnamed?** — If `UserAccount` is split into `UserAccount + UserProfile + BillingInfo`, what remains in `UserAccount` should be renamed to something accurate (maybe `UserIdentity` or `UserCredentials`). The name is a contract — leaving a misleading name after a structural change is a maintenance trap.

---

**Final Tip:** The most common pitfall with Moving Features between Objects is applying these refactorings **in isolation** without a cohesive design intent. Move Method to fix Feature Envy, then realise three methods all moved to the same class — that's the signal to Extract Class. Extract Class, then notice the original class barely delegates — that's the signal to apply Hide Delegate or Remove Middle Man. These refactorings form a **chain**: each one reveals the next. The correct mental model is not "which single refactoring fixes this?" but "which refactoring moves the design one step toward high cohesion and low coupling?" — and then repeat until the class boundaries feel natural.
