# Performance Testing Tools: k6, Apache JMeter, Artillery — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is performance testing, and why does it matter in production backend systems?**
A: Performance testing validates that a system meets non-functional requirements — throughput, latency, concurrency, and resilience — under various load conditions. At the 5 YOE level, it's not optional: production systems degrade in non-obvious ways under load (connection pool exhaustion, GC pressure, memory leaks, lock contention). The three core variants:
- **Load testing** — expected peak traffic; does the system hold SLAs?
- **Stress testing** — above peak; where does it break, and how does it fail (gracefully or catastrophically)?
- **Soak / endurance testing** — sustained load over time; catches memory leaks and resource exhaustion that only manifest after hours.

**Q2. What is k6, and what makes it different from traditional tools like JMeter?**
A: k6 is a modern, open-source load testing tool written in Go with scripts authored in JavaScript (ES2015+). Its key differentiators:
- **Script-first** — tests are `.js` files, version-controllable, diffable, reviewable in PRs.
- **Lightweight** — the Go runtime is far more memory-efficient per VU (virtual user) than the JVM; you can push higher concurrency from a single machine.
- **Developer-centric** — outputs structured JSON metrics, integrates with Grafana, Prometheus, InfluxDB natively.
- **No GUI required** — runs from CLI; fits CI/CD pipelines naturally.
JMeter is GUI-first, JVM-based, and uses an XML test plan format that's notoriously hard to diff and review. It has a broader plugin ecosystem and has been the industry standard for 20+ years, but k6 is increasingly the modern default.

**Q3. What is Artillery, and where does it fit?**
A: Artillery is a Node.js-native load testing framework authored in YAML (with optional JS hooks). It's designed with microservices and API testing in mind, supports HTTP, WebSocket, Socket.IO, and gRPC out of the box, and integrates into Node.js CI workflows with minimal friction. Key characteristics:
- Tests defined in YAML — readable by non-engineers, approachable for DevOps/QA.
- JS `before`, `after`, `beforeRequest`, `afterResponse` hooks for custom logic.
- `artillery run` output is structured; `artillery report` generates an HTML report.
- Smaller community than k6/JMeter; plugin ecosystem less mature. Best fit for teams already in the Node/AWS ecosystem (has native AWS Lambda runner support).

**Q4. What is a Virtual User (VU), and how does it map to real concurrency?**
A: A VU simulates a single user session — it executes the test script in a loop, making requests sequentially (by default), waiting for responses before proceeding. 100 VUs ≠ 100 RPS; actual RPS depends on response time. If average response time is 200ms, one VU generates ~5 RPS. For 500 RPS you'd need ~100 VUs at that latency. This is the key mental model: **RPS = VUs / avg_response_time_seconds**. k6 and Artillery both model concurrency as VUs; JMeter calls them "threads."

**Q5. What are the key metrics you capture in a load test?**
A: The standard set:

| Metric | What it tells you |
|---|---|
| **p50 / p90 / p95 / p99 latency** | Distribution of response times; p99 shows tail latency |
| **Throughput (RPS)** | Requests served per second |
| **Error rate (%)** | % of requests returning 4xx/5xx or timing out |
| **VU concurrency** | Active users at any point in time |
| **Time to First Byte (TTFB)** | Network + server processing before first byte received |
| **Iteration duration** | Full script cycle time (useful for VU-based pacing) |
| **Connection time / TLS handshake** | Infrastructure overhead outside application code |

Always look at **percentiles, not averages** — an average of 100ms can hide a p99 of 4 seconds, which is what real users experience.

## Section 2: k6 Deep Dive

**Q6. Walk through the anatomy of a k6 test script.**
A: A k6 script has three layers:

```js
// 1. Init code — runs once per VU, before the test starts
import http from "k6/http";
import { check, sleep } from "k6";

// 2. Options — exported config for the test engine
export const options = {
  stages: [
    { duration: "30s", target: 50 },   // ramp up to 50 VUs
    { duration: "1m",  target: 50 },   // hold at 50 VUs
    { duration: "20s", target: 0  },   // ramp down
  ],
  thresholds: {
    http_req_duration: ["p(95)<500"],  // 95th percentile must be < 500ms
    http_req_failed:   ["rate<0.01"],  // error rate must be < 1%
  },
};

// 3. Default function — the VU's loop, runs repeatedly during the test
export default function () {
  const res = http.get("https://api.example.com/v1/health");
  check(res, {
    "status is 200":          (r) => r.status === 200,
    "response time < 400ms":  (r) => r.timings.duration < 400,
  });
  sleep(1); // think time between iterations
}
```

- **Init code** (module-level) — imports, global config — runs once per VU, not per iteration.
- **`export const options`** — the test engine reads this before starting; stages, thresholds, VU count.
- **`export default function`** — the hot loop, runs repeatedly for each VU.

**Q7. What are k6 Stages vs Scenarios, and when do you use each?**
A:
- **Stages** — a simple ramp-up/hold/ramp-down VU profile for a single script flow. Good for basic load and stress tests. Configured in `options.stages`.
- **Scenarios** — fine-grained control: multiple independent workloads in a single test, each with its own executor, VU count, start time, and entry function. Use scenarios when you need to simulate mixed traffic (e.g., 80% read traffic + 20% write traffic, each with different ramp-up profiles):

```js
export const options = {
  scenarios: {
    read_heavy: {
      executor:   "ramping-vus",
      startVUs:   0,
      stages:     [{ duration: "1m", target: 100 }],
      exec:       "readFlow",
    },
    write_burst: {
      executor:   "constant-arrival-rate",
      rate:       20,         // 20 iterations/s
      timeUnit:   "1s",
      duration:   "1m",
      preAllocatedVUs: 30,
      exec:       "writeFlow",
    },
  },
};
export function readFlow()  { /* GET requests */ }
export function writeFlow() { /* POST requests */ }
```

**Q8. What is the difference between `ramping-vus` and `constant-arrival-rate` executors in k6?**
A:
- **`ramping-vus`** — VU-based; you control the number of concurrent users and k6 runs as many iterations as they can complete. Throughput is a *result* of VU count × response speed. Good for: "can 200 users use this concurrently?"
- **`constant-arrival-rate`** — rate-based; you specify iterations per second and k6 spawns enough VUs to maintain that rate. Throughput is the *input*. Good for: "can the system sustain 500 RPS?" and for isolating latency from VU-count effects.

The practical difference: under `ramping-vus`, if the system slows down, VUs pile up waiting, and effective RPS drops. Under `constant-arrival-rate`, if not enough VUs are available to hit the target rate, k6 emits a warning — this surfaces capacity issues more cleanly.

**Q9. How do k6 thresholds work, and how do you make a CI pipeline fail on a threshold breach?**
A: Thresholds are pass/fail criteria defined in `options.thresholds`. k6 evaluates them at the end of the test and sets its **exit code to non-zero** if any threshold fails — which is all CI systems need to fail the build:

```js
export const options = {
  thresholds: {
    "http_req_duration":          ["p(99)<1000"],  // p99 latency < 1s
    "http_req_failed":            ["rate<0.005"],   // < 0.5% error rate
    "checks":                     ["rate>0.99"],    // > 99% check pass rate
    "http_req_duration{endpoint:login}": ["p(95)<300"], // tagged subset
  },
};
```

In CI (GitHub Actions, GitLab CI, etc.): `k6 run script.js && echo "PASSED" || exit 1`. The `|| exit 1` is redundant — k6 already exits non-zero on threshold failure; the CI runner picks it up automatically.

**Q10. How do you handle authentication tokens and dynamic data in k6?**
A: Two common patterns:

```js
// Pattern 1: Get a token in setup(), share via return value
export function setup() {
  const res = http.post("https://api.example.com/auth/login", JSON.stringify({
    username: "loadtest@example.com",
    password: __ENV.LOAD_TEST_PASSWORD, // read from env, never hardcode
  }), { headers: { "Content-Type": "application/json" } });
  return { token: res.json("access_token") }; // passed to default()
}

export default function (data) {
  http.get("https://api.example.com/v1/profile", {
    headers: { Authorization: `Bearer ${data.token}` },
  });
}

// Pattern 2: SharedArray for parameterized test data (efficient — loaded once)
import { SharedArray } from "k6/data";
const users = new SharedArray("users", function () {
  return JSON.parse(open("./users.json")); // file read at init, shared across VUs
});

export default function () {
  const user = users[Math.floor(Math.random() * users.length)];
  // use user.email, user.token, etc.
}
```

Key rule: never re-authenticate inside the default function loop unless you're explicitly testing auth performance — it adds unnecessary noise to response time metrics.

## Section 3: Apache JMeter Deep Dive

**Q11. What is JMeter's test plan structure?**
A: JMeter tests are composed hierarchically in an XML `.jmx` file, edited via GUI or hand-crafted:

```
Test Plan
├── Thread Group              ← defines VUs, ramp-up, loop count
│   ├── HTTP Request Sampler  ← individual request
│   ├── HTTP Header Manager   ← headers applied to children
│   ├── CSV Data Set Config   ← parameterization (like k6 SharedArray)
│   ├── Response Assertion    ← pass/fail checks
│   └── Constant Timer        ← think time between requests
├── Listeners                 ← Aggregate Report, View Results Tree, etc.
└── Config Elements           ← HTTP Cookie Manager, HTTP Cache Manager
```

Thread Group key settings: **Number of Threads** (VUs), **Ramp-Up Period** (seconds to reach full thread count), **Loop Count** (iterations per thread, or "Forever" + duration).

**Q12. What is the difference between JMeter's Aggregate Report and Summary Report listeners?**
A: Both aggregate request stats, but:
- **Summary Report** — updates in real time during the test; shows live throughput and error rate. Good for watching a running test.
- **Aggregate Report** — shows final aggregated stats per sampler: min, max, average, p90, p95, p99, throughput, error %. More complete for post-test analysis.

For non-GUI / CI runs (`jmeter -n -t test.jmx -l results.jtl`), both write to a `.jtl` file (CSV or XML). Always disable GUI listeners in CI — they add JVM overhead and can skew results at high concurrency.

**Q13. How do you run JMeter in non-GUI mode, and why is it required for real load tests?**
A: GUI mode uses significant memory and CPU for rendering — this competes with the load generator itself and produces inaccurate results at high thread counts. Non-GUI mode is mandatory for any real test:

```bash
jmeter -n \
  -t test_plan.jmx \
  -l results.jtl \
  -e -o ./html-report \
  -Jthreads=200 \
  -Jramp=60 \
  -Jduration=300
```

- `-n` — non-GUI mode
- `-t` — test plan file
- `-l` — log file (`.jtl`)
- `-e -o` — generate HTML dashboard report after test
- `-J` — override JMeter properties/variables from the command line (enables parameterized CI runs)

**Q14. How does JMeter handle distributed load testing?**
A: JMeter has a built-in controller/agent (master/slave) model:
1. Start `jmeter-server` on each agent machine.
2. Run JMeter in GUI or non-GUI mode on the controller with `-R agent1,agent2,agent3` (or configure `remote_hosts` in `jmeter.properties`).
3. The controller distributes the test plan to all agents; each runs its thread group independently. Results stream back to the controller and are merged.

Caveat: All agents run the *same* thread group — if the plan has 100 threads and you have 5 agents, you get 500 total threads. Design thread groups with per-agent count in mind, or use JMeter plugins (e.g., `Stepping Thread Group`) that support distributed-aware scaling.

**Q15. What are JMeter's most common performance pitfalls when used incorrectly?**
A:
- **Running with GUI during load** — massively skews results; always use non-GUI for actual tests.
- **Overusing "View Results Tree" listener** — stores every request/response in memory; causes OOM at scale. Disable in production tests; use only for debugging with small thread counts.
- **Default JVM heap too small** — JMeter ships with `-Xms1g -Xmx1g`; for high thread counts increase in `jmeter.sh`/`jmeter.bat`: `-Xms4g -Xmx4g`.
- **Not parameterizing test data** — all VUs hitting identical URLs/payloads; CDN/cache layers return cached responses, making the backend look far faster than it is.
- **Timers omitted** — no think time between requests means VUs hammer as fast as possible, which rarely resembles real user behaviour.

## Section 4: Artillery Deep Dive

**Q16. Walk through the anatomy of an Artillery test script.**
A: Artillery uses YAML for test definition with optional JS for hooks:

```yaml
# artillery.yml
config:
  target: "https://api.example.com"
  phases:
    - duration: 60
      arrivalRate: 10       # 10 new VUs/s for 60s
    - duration: 120
      arrivalRate: 10
      rampTo: 50            # ramp from 10 to 50 VUs/s over 120s
  defaults:
    headers:
      Authorization: "Bearer {{ $processEnvironment.API_TOKEN }}"
  payload:
    path: "./users.csv"
    fields:
      - "userId"
      - "email"

scenarios:
  - name: "User profile flow"
    flow:
      - get:
          url: "/v1/users/{{ userId }}"
          expect:
            - statusCode: 200
      - think: 1                # 1 second think time
      - post:
          url: "/v1/events"
          json:
            type: "page_view"
            userId: "{{ userId }}"
          expect:
            - statusCode: 201
```

Key concepts: **phases** define load shape; **scenarios** define user flows; **`arrivalRate`** is new VUs per second (not concurrent); **`think`** adds pause between steps.

**Q17. What is `arrivalRate` in Artillery vs concurrent VUs?**
A: Artillery's `arrivalRate` is the rate at which **new virtual users arrive per second** — each virtual user runs the scenario *once* to completion, then exits. This is a **open workload model** (like a real service receiving new requests). `arrivalRate: 50` means 50 new users start every second.

Compare to k6's `ramping-vus` (closed model — fixed pool of VUs that loop indefinitely). Open vs closed matters: under a closed model, slow responses naturally cap throughput (VUs are stuck waiting); under an open model, slow responses cause VU accumulation (arrival rate continues regardless). Artillery's open model more accurately simulates real-world arrival patterns.

**Q18. How do you add custom JS logic to Artillery (before/after hooks)?**
A:

```js
// hooks.js
module.exports = {
  // Runs once before the test starts
  before: async function (context, next) {
    const response = await fetch("https://api.example.com/auth/token", {
      method: "POST",
      body: JSON.stringify({ client_id: process.env.CLIENT_ID }),
      headers: { "Content-Type": "application/json" },
    });
    const { access_token } = await response.json();
    context.vars.token = access_token; // available as {{ token }} in YAML
    return next();
  },

  // Runs after each request
  afterResponse: function (requestParams, response, context, events, next) {
    if (response.statusCode === 429) {
      events.emit("counter", "rate_limited", 1); // custom metric
    }
    return next();
  },
};
```

```yaml
config:
  processor: "./hooks.js"   # wire the hooks file
```

**Q19. How do you run Artillery in CI and interpret its exit code?**
A:

```bash
artillery run \
  --output report.json \
  artillery.yml

artillery report report.json --output report.html
```

Artillery exits with code `1` if **`ensure` conditions** (thresholds) are breached:

```yaml
config:
  ensure:
    p99: 500        # p99 latency < 500ms
    maxErrorRate: 1 # error rate < 1%
```

Without `ensure`, Artillery always exits `0` even if p99 is 10 seconds. This is a common gotcha — always define `ensure` thresholds for CI integration, otherwise the pipeline never fails on degradation.

## Section 5: Choosing the Right Tool

**Q20. When would you choose k6 over JMeter in a greenfield project?**
A: k6 is the default choice for new projects if:
- The team is JavaScript/TypeScript-native and wants tests that live alongside application code in the same repo.
- You need CI/CD integration (k6 exits non-zero on threshold failure out of the box).
- You need Grafana/InfluxDB/Prometheus dashboards — k6 has native output plugins.
- Resource efficiency matters: k6 supports ~10× more VUs per GB RAM than JMeter.
- Tests need to be PR-reviewed — `.js` files diff cleanly; `.jmx` XML does not.

Choose JMeter when: the team has deep JMeter expertise, the project requires its vast plugin ecosystem (JDBC, JMS, SOAP, FTP samplers), or there's an existing test suite that's impractical to migrate.

**Q21. When would you choose Artillery over k6?**
A: Artillery wins when:
- The team is YAML-first (DevOps, QA engineers less comfortable with JS).
- You're testing WebSocket or Socket.IO-heavy services — Artillery has first-class support; k6 requires the `k6/experimental/websockets` module.
- You're deploying to AWS and want native Lambda-based distributed load generation (Artillery Pro/Cloud has direct Lambda integration).
- You want scenario-based test definitions that non-engineers can read and modify.

k6 wins for sheer concurrency at scale and for metric richness. Artillery wins for readability and Node.js ecosystem fit.

**Q22. How do you run distributed load tests when a single machine can't generate enough load?**
A:

| Tool | Distributed approach |
|---|---|
| **k6** | `k6 cloud` (managed service); or `k6-operator` on Kubernetes (runs distributed k6 pods); or manual: split test across multiple instances, aggregate `results.json` |
| **JMeter** | Built-in controller/agent model (`-R agent1,agent2`); or distributed via Docker Compose / Kubernetes |
| **Artillery** | `artillery run --platform aws:lambda` (Artillery Pro); or split scenario files across multiple EC2/ECS tasks and merge reports |

For very high RPS (>50k), cloud-native solutions (k6 Cloud, Gatling Enterprise, Locust on Kubernetes) are more operationally practical than managing a JMeter agent fleet.

## Section 6: Metrics, Analysis & Production Integration

**Q23. What is the difference between p95 and p99 latency, and which should you set SLAs against?**
A: p95 means 95% of requests completed within that time; p99 means 99% did. The remaining 1% (your worst requests) are p99+. For user-facing APIs:
- **p95** — good general-purpose SLA threshold; filters out rare spikes.
- **p99** — better for latency-sensitive flows (payment confirmation, auth); even 1% slow responses affect thousands of users at scale.
- **p99.9 (three nines)** — for SLAs at very high volume (1M+ RPD); one in 1000 requests being slow is still ~1000 slow requests/day.

Never set SLAs on averages — a p50 of 50ms with a p99 of 5000ms looks "fine" in average-based monitoring but represents deeply degraded user experience at the tail.

**Q24. How do you integrate load test results into a Grafana dashboard using k6?**
A:

```bash
# Run k6 and stream metrics to InfluxDB
k6 run --out influxdb=http://localhost:8086/k6 script.js
```

Then in Grafana: add InfluxDB as a data source, import the official k6 dashboard (Grafana dashboard ID `2587`) or build custom panels querying `k6_http_req_duration`, `k6_vus`, `k6_http_reqs` series. For Prometheus, use `--out experimental-prometheus-rw`.

This setup lets you overlay load test runs with APM metrics (CPU, memory, DB connection pool saturation) from the same Grafana instance — critical for correlating latency spikes with infrastructure bottlenecks.

**Q25. How do you use load testing to find connection pool exhaustion in a Node.js/PostgreSQL service?**
A: Classic approach:
1. Run a ramp-up test that steadily increases VUs.
2. Simultaneously watch the PostgreSQL connection count: `SELECT count(*) FROM pg_stat_activity;`.
3. If p99 latency spikes sharply at a specific VU count while DB CPU is low, the app is queueing requests waiting for a connection from the pool (e.g., `pg`'s default pool size is 10 — 10 concurrent queries max; the rest queue).
4. Reproduce by setting `pg` pool max to a tiny value and watching the latency cliff appear in k6's stage graph.
5. Fix: increase pool size, tune `idleTimeoutMillis` / `connectionTimeoutMillis`, or shard the pool across read replicas.

k6 makes this workflow clean: tag requests with `{ tags: { endpoint: 'heavy_query' } }` and filter thresholds per-endpoint to identify which route hits the pool ceiling first.

## Section 7: Scenario / System Design Style Questions

**Q26. "Your team is about to launch a new payment API. How do you design and execute a pre-launch performance test?"**
A: A structured approach:
1. **Define SLAs** — agree on targets with product: e.g., p99 < 800ms, error rate < 0.1%, sustain 500 TPS for 30 minutes.
2. **Identify critical flows** — payment initiation, status polling, webhook delivery confirmation. Model realistic traffic mix (not just happy path).
3. **Parameterize test data** — unique order IDs, real card tokens (test credentials), varied amounts to avoid DB/cache shortcuts on identical payloads.
4. **Baseline test** — 10 VUs, 5 minutes; capture latency distribution and identify obvious bottlenecks before scaling.
5. **Load test** — ramp to target TPS (`constant-arrival-rate` in k6 or Artillery `arrivalRate`); hold for 30 minutes; validate thresholds.
6. **Stress test** — push to 2×–3× target; find the breaking point and verify it fails gracefully (circuit breakers trip, queues back-pressure, no data corruption).
7. **Soak test** — sustained load for 4–8 hours; watch memory, heap, DB connection count for slow leaks.
8. **Analyze and fix** — correlate k6 metrics with APM (Datadog, New Relic), DB slow query logs, Node.js heap snapshots.
9. **Re-test after fixes** — never ship without a green re-run of the full suite.

**Q27. "A PR introduces a new database query to a high-traffic endpoint. How do you use load testing to validate it doesn't regress performance?"**
A: Make load testing part of the PR lifecycle:
1. **Baseline on `main`** — run a fixed k6 script against the current deployed version; save `results_baseline.json`.
2. **Test on the PR branch** (deploy to a staging environment that mirrors production schema and data volume).
3. **Compare** — k6 outputs structured JSON; write a comparison script that diffs p95/p99 latency and RPS between the two runs; fail the PR check if p99 regresses >10%.
4. **Use `constant-arrival-rate`** — ensures both runs receive the same RPS, so latency differences isolate the query change rather than VU-count effects.
5. **Check DB metrics** — query execution time from `pg_stat_statements`, `EXPLAIN ANALYZE` on the new query at representative data volume (often staging has less data than production — size matters for index scans).

This turns load testing from a one-off pre-launch activity into a continuous regression gate.

**Q28. "You run a soak test and notice memory growing steadily in your Node.js service over 4 hours. How do you investigate?"**
A:
1. **Confirm with heap metrics** — if not already done, add `process.memoryUsage()` emission to your metrics endpoint; confirm heap grows, not just RSS (RSS growth can be V8 memory reservation, not a leak).
2. **Take heap snapshots** — use `--inspect` + Chrome DevTools, or `node --heap-prof` during the load test. Take snapshots at 30min, 2hr, 4hr.
3. **Compare snapshots** — look for object types accumulating: closed-over event listeners, uncached `Buffer` allocations, growing `Map`/`Set` used as unbounded caches, or accumulated Promises that never resolve.
4. **Common culprits in fintech services**:
   - Global request logger accumulating log entries in memory (should stream, not buffer).
   - `EventEmitter` listeners added per-request inside middleware, never removed.
   - Redis/Postgres client pools leaking connections (connection count grows, each holds a socket buffer).
   - Unbounded in-memory caches (e.g., `Map` keyed on request correlation IDs that are never evicted).
5. **Fix + re-run soak** — verify the growth line is flat in the next 4-hour run before shipping.

**Tip for the interview:** At 5 YOE, interviewers won't quiz you on JMeter GUI buttons — they want to see that you understand **what to test, how to interpret results, and how to act on them**. Have a concrete story ready: a time you ran a load test that surfaced a real production bottleneck (connection pool, slow query, memory leak), what the k6/Artillery output looked like, what you fixed, and how you verified it.
