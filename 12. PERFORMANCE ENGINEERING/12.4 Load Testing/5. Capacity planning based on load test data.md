# Capacity Planning Based on Load Test Data — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is capacity planning, and why does it go hand-in-hand with load testing?**
A: Capacity planning is the process of determining what compute, memory, storage, and network resources a system needs to meet current and future demand — within acceptable latency and reliability bounds. Load testing is its empirical foundation: without measured data on how the system behaves under load, capacity decisions are guesswork. The workflow is:

1. **Load test** → measure how the system degrades as traffic increases.
2. **Model** → fit a performance curve to that data (throughput vs latency, throughput vs resource utilization).
3. **Project** → apply expected traffic growth to the model to determine when you'll breach SLAs.
4. **Provision** → add capacity before the breach, not after.

Done well, capacity planning prevents two failure modes: under-provisioning (outages) and over-provisioning (wasted cloud spend).

**Q2. What are the key signals you extract from a load test to inform capacity decisions?**
A: Five categories of signal:

| Signal | What it tells capacity planning |
|---|---|
| **Saturation point (RPS / TPS)** | The throughput ceiling before latency or errors degrade — your system's max capacity at current provisioning |
| **p99 latency curve** | How tail latency grows as load increases — identifies the "knee of the curve" where things start breaking |
| **Resource utilization at each load level** | CPU%, memory, DB connections, thread pool occupancy — which resource hits 100% first (the bottleneck) |
| **Error rate vs load** | At what RPS errors appear — circuit breakers, timeouts, queue overflows |
| **Scaling headroom** | Gap between current peak traffic and saturation point — your safety margin |

**Q3. What is the "knee of the curve," and why is it the most important thing to find in a load test?**
A: The knee of the curve is the inflection point on a load-vs-latency (or load-vs-error-rate) graph where the system transitions from linear, predictable behaviour to non-linear degradation. Below the knee, doubling load roughly doubles throughput with minor latency increase. Above the knee, small load increases cause disproportionate latency spikes and error rate jumps — this is where queuing theory (Little's Law) explains the explosion: queues form, wait times compound.

```
Latency (ms)
│                                    ●  ← system saturating
│                                 ●
│                              ●
│                    ●●●●●  ← knee of the curve
│            ●●●●
│    ●●●●
└────────────────────────────────── RPS
```

Capacity planning targets keeping production traffic well to the left of the knee — typically at 60–70% of the saturation RPS — to preserve headroom for traffic spikes.

**Q4. What is Little's Law, and how does it apply to capacity planning?**
A: Little's Law is a fundamental result from queueing theory:

```
L = λ × W
```

Where:
- **L** = average number of requests in the system (concurrency)
- **λ** = average arrival rate (RPS)
- **W** = average time a request spends in the system (latency, in seconds)

Practical application: if your system handles 500 RPS at 200ms average latency, there are **L = 500 × 0.2 = 100** concurrent requests in flight at any moment. To handle 1000 RPS at the same latency, you need capacity for 200 concurrent requests — double the thread pool, connection pool, and processing capacity. Little's Law lets you translate traffic projections directly into concurrency requirements without running a new load test for every scenario.

**Q5. What is the difference between horizontal and vertical scaling, and how does load test data inform which to choose?**
A:
- **Vertical scaling** — more CPU/RAM on the same instance. Simple, no code changes, but has a physical ceiling and doesn't improve fault tolerance.
- **Horizontal scaling** — more instances behind a load balancer. Theoretically unbounded throughput growth, but requires the application to be stateless (or state to be externalized to Redis/DB).

Load test data informs the choice by revealing the bottleneck type:
- **CPU-bound saturation** → vertical scaling gives a linear throughput boost per added core (up to a point); horizontal scaling works if the service is stateless.
- **Memory-bound** (e.g., heap GC pressure in Node.js) → vertical scaling (more RAM); OR reduce per-request memory footprint.
- **I/O-bound** (waiting on DB, external APIs) → horizontal scaling adds more connection capacity; vertical scaling rarely helps.
- **Single-threaded bottleneck** (Node.js main thread CPU spike) → horizontal scaling is the correct answer; a bigger machine doesn't help a process that can't use >1 core per instance.

## Section 2: Reading Load Test Data for Capacity Signals

**Q6. How do you construct a throughput-vs-latency curve from k6 or JMeter output?**
A: Run a series of load tests at increasing RPS (or VU count), record p99 latency at each level, and plot:

```js
// k6: use constant-arrival-rate at stepped rates
const rates = [50, 100, 200, 300, 400, 500]; // RPS steps

export const options = {
  scenarios: {
    stepped_load: {
      executor:        "constant-arrival-rate",
      rate:            __ENV.RATE,   // pass via -e RATE=100
      timeUnit:        "1s",
      duration:        "3m",         // 3 min per step = stable measurement
      preAllocatedVUs: 200,
    },
  },
  thresholds: {
    http_req_duration: ["p(99)<2000"], // just capture, don't gate yet
  },
};
```

Run this 6 times with `k6 run -e RATE=50 script.js`, `RATE=100`, etc. Extract `p(99)` from each JSON output and plot. The resulting curve tells you exactly where the knee is and at what RPS latency breaches your SLA.

**Q7. How do you identify which resource is the bottleneck during a load test?**
A: Watch four dimensions simultaneously during the test — the first one to saturate is the bottleneck:

```
Load test running at increasing RPS →

  CPU%:            ░░░░░░░░▓▓▓▓████  ← hits 100% at 400 RPS → CPU-bound
  Memory (GB):     ░░░░░░░░░░░░░░░░  ← stays flat → not the bottleneck
  DB connections:  ░░░░░░░████████  ← pool exhausted at 300 RPS → DB I/O-bound
  Thread pool:     ░░░░░░░░░░▓▓▓▓██  ← fills at 450 RPS → secondary
```

Tools to watch each:
- **CPU / Memory** — `top`, `htop`, CloudWatch EC2 metrics, Datadog host dashboard.
- **DB connections** — `SELECT count(*) FROM pg_stat_activity;` polled during the test; or `pg_stat_activity` live in psql.
- **Node.js event loop lag** — `perf_hooks.monitorEventLoopDelay()` or Clinic.js flame graphs.
- **Redis** — `INFO stats` → `instantaneous_ops_per_sec`, `connected_clients`.
- **Connection pool** — log pool checkout wait time (`pg` pool emits `connect` events; NestJS TypeORM logs pool timeout errors).

**Q8. What is utilization headroom, and how do you calculate the right buffer?**
A: Utilization headroom is the gap between your current peak observed utilization and 100% (saturation). Capacity planning targets a **utilization ceiling** — the maximum you're willing to run at in steady state — to preserve room for:
- Traffic spikes (flash sales, news events, batch jobs).
- Deployment overhead (rolling deploys temporarily reduce capacity).
- Resource fragmentation (not all instances run at identical load).

Common targets:

| Resource | Recommended ceiling | Rationale |
|---|---|---|
| CPU | 60–70% | Non-linear queuing begins above ~70%; leaves room for GC, spikes |
| Memory | 70–80% | Above 80%, GC pressure / OOM risk increases sharply |
| DB connections | 70% of pool max | Reserve connections for admin queries, health checks |
| Disk I/O | 60% | I/O saturation causes cascading latency across all workloads |

Formula: **Required capacity = Peak observed load / Target ceiling**. If peak load is 350 RPS and you want to run at 70% ceiling, provision for `350 / 0.70 = 500 RPS`.

**Q9. How do you extract per-endpoint capacity signals from k6 when a single service handles multiple routes?**
A: Tag requests by endpoint and apply per-tag thresholds:

```js
export default function () {
  // Tag each request group
  const loginRes = http.post(
    `${BASE_URL}/auth/login`,
    JSON.stringify({ email: user.email, password: user.password }),
    { headers, tags: { endpoint: "login" } }
  );

  const profileRes = http.get(
    `${BASE_URL}/v1/profile`,
    { headers: { Authorization: `Bearer ${token}` }, tags: { endpoint: "profile" } }
  );

  const txRes = http.get(
    `${BASE_URL}/v1/transactions?page=1`,
    { headers: { Authorization: `Bearer ${token}` }, tags: { endpoint: "transactions" } }
  );
}

export const options = {
  thresholds: {
    "http_req_duration{endpoint:login}":        ["p(99)<500"],
    "http_req_duration{endpoint:profile}":      ["p(99)<300"],
    "http_req_duration{endpoint:transactions}": ["p(99)<800"],
  },
};
```

This tells you: the transactions endpoint saturates at 200 RPS while login still has headroom at 400 RPS — so transactions needs a dedicated service or DB index, not more instances of the monolith.

**Q10. What is Amdahl's Law, and how does it set an upper bound on horizontal scaling?**
A: Amdahl's Law states that the maximum speedup from parallelization is bounded by the serial (non-parallelizable) fraction of the workload:

```
Speedup(N) = 1 / (S + (1 - S) / N)
```

Where **S** = fraction of work that must run serially, **N** = number of parallel units (instances).

If 20% of your request processing is serial (single-threaded DB writes, global locks, sequential external API calls), the theoretical max speedup is `1 / 0.20 = 5×` — adding more than ~5–10 instances gives diminishing returns. Load test data reveals S empirically: if throughput stops scaling linearly with added instances, Amdahl's Law is biting you. The fix is to reduce serial bottlenecks — async processing, write batching, sharding — not to keep adding instances.

## Section 3: Translating Load Test Data into Capacity Models

**Q11. How do you build a simple capacity model from load test results?**
A: A capacity model is a mapping from traffic level → resource requirement. Build it in three steps:

**Step 1 — Establish the performance envelope from load tests:**
```
RPS   | p99 latency | CPU% (per instance) | DB connections used
------|-------------|---------------------|--------------------
 100  |    120ms    |        15%          |        8
 200  |    135ms    |        28%          |       16
 300  |    160ms    |        42%          |       24
 400  |    210ms    |        58%          |       32
 500  |    480ms    |        71%          |       40  ← approaching knee
 600  |   1800ms    |        89%          |       48  ← past knee, SLA broken
```

**Step 2 — Fit to your SLA ceiling (e.g., p99 < 400ms → max ~480 RPS per instance, target 70% = 336 RPS/instance).**

**Step 3 — Project traffic growth:**
```
Current peak:       250 RPS
Monthly growth:     15%
Months to plan for: 6

Projected RPS = 250 × (1.15)^6 ≈ 580 RPS

Instances needed = ceil(580 / 336) = 2 instances
Current: 1 instance → need to provision 1 more within ~4 months
```

This gives a concrete, data-driven provisioning roadmap rather than "let's add more servers."

**Q12. How do you model traffic growth when you don't have 6 months of historical data?**
A: Use conservative proxies:
- **Business projections** — if sales expects 3× users in Q4, model 3× peak RPS.
- **Comparable launch benchmarks** — internal launches of similar features; industry benchmarks for your sector.
- **Seasonal patterns** — fintech sees spikes at month-end (salary crediting, EMI deduction); model 2×–3× average for those windows.
- **Worst-case spike estimation** — if a single push notification triggers 10% of your user base to open the app within 60 seconds: `0.10 × DAU / 60 = spike RPS`. Load test to that ceiling.

When growth rate is uncertain, plan to two scenarios: **base case** (expected growth) and **stress case** (2× base). Provision for base, ensure architecture can scale to stress case without code changes (just add instances).

**Q13. How do you use load test data to right-size a database connection pool?**
A: Connection pool sizing is one of the most impactful capacity decisions for Node.js/PostgreSQL services. The formula:

```
Optimal pool size ≈ num_cores × (1 + wait_time / service_time)
```

But in practice, derive it empirically from load test data:

1. Run load tests at target RPS while logging pool checkout wait time and pool exhaustion errors.
2. Watch `pg_stat_activity` — count of active connections vs max.
3. Identify the RPS at which pool wait time jumps (pool queue forming).
4. The pool size at that point is too small — increase until wait time stays near zero at target RPS.

```typescript
// NestJS TypeORM pool config derived from load test results
TypeOrmModule.forRoot({
  type:        "postgres",
  host:        process.env.DB_HOST,
  // Load test showed pool exhaustion above 25 connections at 300 RPS
  // with avg query time 8ms. Set to 30 with overflow buffer.
  extra: {
    max:                30,   // max pool size
    min:                5,    // keep 5 warm (avoid cold-start latency)
    idleTimeoutMillis:  30000,
    connectionTimeoutMillis: 2000, // fail fast if pool exhausted
  },
}),
```

PostgreSQL's own limit: each connection uses ~5–10MB RAM on the DB server. For an RDS db.t3.medium (2GB RAM), safe max total connections ≈ 100–150 across all app instances combined. Plan pool size per instance accordingly: `total_safe_connections / num_app_instances`.

**Q14. How do you capacity plan for auto-scaling groups (ASGs) using load test data?**
A: Auto-scaling needs three inputs from load tests:

1. **Scale-out threshold** — the CPU% or RPS at which a new instance should be added. Set this at your utilization ceiling (e.g., 65% CPU → trigger scale-out). Derived from load test: at what CPU% does p99 start degrading?

2. **Scale-out speed** — time from "threshold breached" to "new instance healthy and receiving traffic." This includes: instance boot time + application warm-up time + load balancer health check time. Measure this during the load test's ramp phase. If it takes 3 minutes to add capacity, and your traffic spikes from 0 to 3× in 2 minutes (e.g., a push notification blast), scale-out alone won't save you — you need pre-warming or predictive scaling.

3. **Min/max instance bounds** — from load test: min instances = instances needed to serve baseline traffic at ceiling utilization; max instances = instances needed to serve worst-case spike without breaching DB connection limits.

```
                     Traffic spike
                     ┌──────────┐
                     │          │
     ────────────────┘          └────────────  ← actual traffic
     ════════════════╗                          ← ASG capacity
                     ╚══════════╗               ← scale-out triggered here
                     [3min lag] ║               ← capacity gap → need buffer
                                ╚══════════════
```

The gap between spike start and new capacity being live is where you shed load — rate limiting, graceful degradation, and pre-warming are the mitigations.

**Q15. What is the "N+1 redundancy" principle, and how does it factor into capacity math?**
A: N+1 means provisioning N instances to handle peak load, plus 1 additional instance for fault tolerance — so that if any one instance fails, the remaining N instances can still absorb full traffic without breaching SLAs.

From load test data:
- Measured: 1 instance handles 350 RPS at p99 < 400ms.
- Target peak: 600 RPS.
- N (instances for load): `ceil(600 / 350) = 2`.
- N+1: provision **3 instances**.
- Validation: run load test at 600 RPS against 2 instances (simulating 1 failure from a 3-instance cluster) — confirm SLAs hold.

For financially critical services (payment processing, settlement), N+2 is common: tolerate 2 simultaneous failures without SLA breach. Load test data tells you what "full traffic on N-2 instances" actually looks like.

## Section 4: Infrastructure Patterns & Cost Optimization

**Q16. How do you use load test data to choose between reserved, on-demand, and spot instances on AWS?**
A: Load test data reveals your **baseline vs spike** traffic ratio, which maps directly to AWS instance purchasing strategy:

- **Baseline (steady load, always-on)** → Reserved Instances (1-year or 3-year). Load tests define what "always needed" means: instances required to handle your p50 traffic week. Reserved gives 30–60% savings over on-demand.
- **Daytime peak (predictable, scheduled)** → Scheduled Auto Scaling. Load tests on time-of-day patterns tell you when to pre-warm (e.g., scale up at 8:55 AM before 9 AM traffic hits).
- **Unexpected spikes** → On-Demand instances spun up by ASG. Load tests determine how many on-demand instances you might need at absolute peak.
- **Stateless batch / background workers** → Spot Instances. Load tests confirm these services are interruption-tolerant (retryable jobs, idempotent operations).

A typical fintech architecture: 3 reserved instances for baseline API traffic + ASG that adds on-demand during peak + spot fleet for nightly batch reconciliation.

**Q17. How do you capacity plan for a Redis cache layer?**
A: Redis capacity has three dimensions:

**Memory:** `key_count × avg_value_size × (1 + overhead_factor)`. Load test with realistic data and run `INFO memory` → `used_memory_human` at peak. Set `maxmemory` to 75% of instance RAM; configure `maxmemory-policy allkeys-lru` for cache use cases.

**Connections:** Each Node.js instance holds a connection to Redis. At 10 instances × 1 connection per instance = 10 connections. Redis default `maxclients` is 10,000 — rarely the bottleneck, but connection pool libraries (ioredis) can open multiple connections per instance. Load test reveals actual `connected_clients` via `INFO clients`.

**CPU (operations/sec):** Redis is single-threaded for command processing. `INFO stats → instantaneous_ops_per_sec` during load test. Redis saturates its core at ~100k–1M ops/sec depending on command complexity. If load test shows ops/sec approaching this, move to Redis Cluster or ElastiCache cluster mode.

**Q18. How do you capacity plan for message queues (e.g., SQS, RabbitMQ) in async workflows?**
A: Queue capacity planning focuses on **consumer throughput vs producer rate** — the queue is a buffer, not a processing unit.

From load test data:
1. **Measure producer rate** — at peak load, how many messages/sec are enqueued? (k6 can measure this if the load test exercises the enqueue path.)
2. **Measure consumer throughput** — a single consumer instance processes N messages/sec (measure with a dedicated consumer load test).
3. **Consumer instances needed** = `ceil(producer_rate / consumer_throughput_per_instance)`.
4. **Queue depth as a health signal** — if queue depth grows during the load test, consumers can't keep up. Target: queue depth should stabilize (not grow unboundedly) at peak load.

For NACH payment processing (batch debit runs): model the peak enqueue burst (e.g., 500k mandates triggered at 6 AM), consumer throughput from load tests, and calculate how long the processing window takes. If SLA requires completion in 2 hours, work backwards: `500,000 / 7200 seconds ≈ 70 messages/sec` sustained throughput required from the consumer fleet.

## Section 5: Capacity Planning for Specific Backend Scenarios

**Q19. How do you capacity plan a Node.js API service behind an AWS ALB?**
A: End-to-end capacity model:

```
Client → ALB → EC2 (Node.js) → RDS PostgreSQL
                    ↑
              This is what load tests measure
```

Key parameters from load test:
- **RPS per instance** at 65% CPU utilization (your scaling ceiling).
- **p99 latency** at target RPS — confirm it meets SLA.
- **DB connection usage** at that RPS — ensure it fits within RDS max connections.
- **Memory per instance** at peak — confirm no OOM risk.

ALB itself handles millions of RPS — it's almost never the bottleneck. The bottleneck is almost always: Node.js event loop (CPU), DB connection pool, or RDS instance CPU/IOPS.

ALB configuration derived from load tests:
- **Health check interval** — set to 10–15s; too-aggressive health checks add noise to small instances.
- **Deregistration delay** — set to match your p99 request duration (e.g., 30s) so in-flight requests complete during rolling deploys.
- **Connection draining** — ensure load tests include a rolling deploy simulation to verify zero-downtime deploys.

**Q20. How do you capacity plan for Elasticsearch in a search-heavy service?**
A: Elasticsearch capacity has four axes:

**Indexing throughput:** Load test the write path — documents/sec at which indexing latency stays below target. Shard count and replica count determine write parallelism. Adding shards increases indexing throughput; adding replicas improves read throughput and fault tolerance but increases write overhead.

**Search throughput:** Measure search RPS at target p99 query latency. Heap sizing is critical: Elasticsearch recommends JVM heap = 50% of RAM, never above 31GB (compressed oops boundary). Load tests at peak search QPS reveal heap pressure via GC pause metrics (`_nodes/stats/jvm`).

**Storage:** `index_size × replication_factor × growth_factor`. For a 6-month projection: current index size × expected document growth × replica count × 1.3 (Lucene segment overhead).

**Node count formula:**
```
data_nodes = max(
  ceil(total_storage / (disk_per_node × 0.85)),   // storage-driven
  ceil(peak_search_qps / search_qps_per_node),    // throughput-driven
  3                                                // minimum for quorum
)
```

## Section 6: Pitfalls & Anti-Patterns

**Q21. What are the most common mistakes in capacity planning derived from load test data?**
A:

- **Testing against non-representative data** — a staging DB with 10k rows behaves nothing like production with 50M rows. Index scans that fit in memory at small scale miss the buffer pool at production scale. Always seed load test environments with production-scale data volumes (or anonymized production snapshots).

- **Ignoring coordinated omission** — a flaw where the load generator pauses requests when the system is slow, masking true latency distribution. k6's `constant-arrival-rate` avoids this; VU-based tools (JMeter thread groups at default settings) can suffer from it. The result: load tests show p99 = 300ms, production shows p99 = 3s under the same RPS.

- **Single-node load testing** — load testing one instance in isolation, then linearly extrapolating ("we need 5× the traffic, so 5 instances"). Real distributed systems have coordination overhead: shared DB, cache stampede on cold starts, inter-service calls. Always test the full distributed system at scale.

- **Not accounting for GC pauses** — Node.js V8 GC pauses are invisible in average latency but visible in p99/p99.9. A 200ms stop-the-world GC pause every 10 seconds manifests as latency spikes. Load tests must run long enough (>30 min) for GC pressure to appear.

- **Capacity planning only for happy path** — sizing for normal requests but forgetting about expensive outliers: large paginated result sets, export-to-CSV endpoints, webhook retry storms. These can saturate a system at 1/10th the normal RPS threshold.

**Q22. What is "cache stampede," and how do you account for it in capacity planning?**
A: A cache stampede (thundering herd) occurs when a cached value expires and many concurrent requests simultaneously find a cache miss, all rushing to recompute the value from the DB. If 1000 RPS hits a key that expires every 60 seconds, the 1-second window of cache miss sends ~1000 requests simultaneously to the DB — a load spike 60× the normal per-key DB rate.

Capacity planning implication: your DB must survive the worst-case stampede, not just average load. Strategies:
- **Mutex/lock-based recomputation** — only one request recomputes; others wait for the cached result.
- **Probabilistic early expiration (PER)** — proactively refresh keys slightly before expiry.
- **Staggered TTLs** — add jitter to TTL: `TTL = base_ttl + rand(0, base_ttl * 0.1)` to prevent synchronized expirations.

Load test for this explicitly: pre-warm the cache, then simultaneously invalidate a hot key and measure the DB spike. Size DB capacity to absorb it.

**Q23. How do you handle the "cold start" problem in capacity planning for auto-scaling?**
A: Cold start is the time between "new instance launches" and "instance is ready to serve traffic at full throughput." Sources of cold start latency:
- **OS boot + Docker container start** — 10–30s.
- **Node.js application startup** — module loading, NestJS DI container initialization, DB connection pool warm-up.
- **JIT compilation warm-up** — V8 optimizes hot paths after several hundred iterations; early requests are slower.
- **Cache warm-up** — a new instance has an empty local cache; first requests hit the DB.

Measure cold start in the load test's ramp-up phase: the time between "scale-out event" and "p99 latency returns to baseline" is your true cold start time.

Capacity planning mitigations:
- **Pre-warming** — scale up before expected spikes (scheduled scaling rules) rather than reactively.
- **Minimum instance count** — keep enough instances warm that auto-scaling additions are supplemental, not critical.
- **Bake DB connections into app startup** — pre-open the full pool on boot (`min: poolMax` in pg config) so the first requests don't pay connection overhead.

## Section 7: Scenario / System Design Style Questions

**Q24. "Your fintech service processes NACH debit mandates. A batch of 1M mandates is triggered every morning at 6 AM. How do you capacity plan for this?"**
A: Structured approach:

1. **Characterize the workload:**
   - 1M mandates over a processing window (regulatory: typically completed by 10 AM = 4 hours = 14,400 seconds).
   - Required throughput: `1,000,000 / 14,400 ≈ 70 mandates/sec` sustained.
   - Each mandate: PAN verification API call (external, ~150ms), deduplication DB check, BRE evaluation, NACH submission.

2. **Load test the mandate processing pipeline** at 70/sec, 100/sec, 150/sec. Find saturation point.

3. **Model bottlenecks:**
   - External PAN verification API: rate limit? SLA? Retry budget?
   - DB: deduplication query at 70 writes/sec — can PostgreSQL handle it? (Load test with production data volume.)
   - BRE: is it CPU-bound? Can it be parallelized?

4. **Capacity model:**
   - If 1 worker instance processes 25 mandates/sec sustainably: `ceil(70 / 25) = 3 worker instances`.
   - Add N+1: **4 instances** for fault tolerance.
   - DB: 4 instances × 10 connections = 40 connections at peak; size RDS accordingly.

5. **Spike model:**
   - What if 200k mandates arrive in the first 5 minutes (bank batch submission lag)? `200,000 / 300 ≈ 667/sec` spike. SQS queue absorbs the burst; consumers process at 70/sec. Queue drains in ~47 minutes. Within window — acceptable.

6. **Monitoring triggers:**
   - Queue depth > 500k at T+1hr → auto-scale consumers.
   - PAN API error rate > 5% → circuit break, retry with backoff.

**Q25. "You're presenting a capacity planning proposal to engineering leadership before a Black Friday-equivalent event. What does the document contain?"**
A: The proposal covers:

**1. Baseline — current system capacity:**
- Load test results: saturation point = 800 RPS per region; current peak = 350 RPS; headroom = 128%.
- Current provisioning: 3 EC2 instances, 1 RDS db.r5.large, Redis `cache.r6g.large`.

**2. Traffic projection:**
- Last Black Friday: 6× normal peak.
- Projected peak this year: `350 × 6 = 2,100 RPS` (30-minute window).
- Additional spike from push notification blast: +400 RPS for ~90 seconds.

**3. Gap analysis:**
- Current capacity (800 RPS) vs projected peak (2,100 RPS): **2.6× gap**.
- Bottleneck from load tests: RDS connection pool exhaustion at 900 RPS (pool max = 100, 3 instances × 30 = 90 connections — too close).

**4. Recommended provisioning changes:**
- Scale from 3 → 8 EC2 instances (8 × 800 = 6,400 RPS theoretical; 70% ceiling = 4,480 RPS; covers 2× projection for safety).
- Upgrade RDS to `db.r5.2xlarge` (supports 3,000 connections; allocate 80 per instance = 640 connections for 8 instances — safe).
- Redis: no change needed (load tests show <30% memory and CPU utilization even at 3× current load).
- Pre-scale at T-1hr (scheduled scaling); do not rely on reactive ASG for the initial spike.

**5. Load test validation plan:**
- Run full-scale load test at 2,500 RPS against the provisioned 8-instance cluster 1 week before the event.
- Gate: all SLA thresholds green; no DB connection errors; Redis p99 < 5ms.

**6. Rollback plan and cost:**
- Post-event: scale back to 3 instances within 48 hours.
- Incremental cost for 7-day pre-scale: `5 instances × 7 days × $/hr` — include the number.

**Q26. "After a production incident where the service fell over at 2× normal peak, how do you do a capacity retrospective and prevent recurrence?"**
A: A structured post-incident capacity review:

**1. Reconstruct the load curve:**
- Pull RPS metrics from the time of the incident (Datadog, CloudWatch).
- Identify the exact RPS at which errors began, p99 started spiking, and the service became unavailable.
- Compare to the last load test results — was the saturation point lower than expected? (Likely: code changes since the last load test degraded capacity.)

**2. Identify root cause of under-capacity:**
- Was the saturation point lower than load tests predicted? → Load tests were run on stale code or non-representative data.
- Did auto-scaling fail to respond in time? → Scale-out lag exceeded the spike duration.
- Did a dependency (DB, external API) fail before the service did? → Single point of failure not covered in capacity model.

**3. Fix the process, not just the numbers:**
- **Establish a load testing cadence** — run load tests on every significant release, not just pre-launch.
- **Add capacity regression checks to CI** — if p99 at 500 RPS degrades >10% vs baseline, block the deploy.
- **Automate the capacity model** — script that reads load test JSON output and updates the capacity projection spreadsheet automatically.
- **Define a capacity review SLA** — review provisioning against projections quarterly, and 4 weeks before any known traffic event.

**4. Short-term provisioning fix:**
- Immediately provision to 2× the observed failure point.
- Load test the new provisioning level before the fix is considered done.

## Quick Reference: Capacity Planning Formulas

| Formula | When to use |
|---|---|
| `RPS = VUs / avg_response_time_s` | Convert VU count to expected RPS |
| `L = λ × W` (Little's Law) | Convert RPS + latency → concurrency requirement |
| `Instances = ceil(target_RPS / (saturation_RPS × ceiling))` | Instance count from load test data |
| `Pool size ≈ cores × (1 + wait_time / service_time)` | DB/Redis connection pool sizing |
| `Projected_RPS = current_peak × (1 + growth_rate)^months` | Traffic growth projection |
| `Required_capacity = peak_load / target_utilization_ceiling` | Headroom buffer calculation |
| `Consumer_instances = ceil(producer_rate / consumer_throughput)` | Queue consumer fleet sizing |

**Tip for the interview:** At 5 YOE, capacity planning questions test whether you can **close the loop between load test numbers and infrastructure decisions**. The weak answer is "I'd add more servers." The strong answer names the bottleneck (CPU, DB connections, event loop lag), references the specific load test metric that revealed it (p99 at 500 RPS, pool exhaustion at 30 connections), applies a formula (Little's Law, utilization ceiling), and gives a concrete provisioning recommendation with a validation plan.
