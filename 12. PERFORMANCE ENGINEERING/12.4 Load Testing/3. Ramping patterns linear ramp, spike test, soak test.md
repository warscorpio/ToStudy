# JavaScript / Performance Testing: Ramping Patterns — Linear Ramp, Spike Test, Soak Test — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a "ramping pattern" in load testing?**
A: A ramping pattern describes how virtual user (VU) count — or request rate — changes over the duration of a load test. Instead of jumping to full load instantly, ramp profiles control the *shape* of the traffic curve: how fast load climbs, whether it holds steady, whether it spikes, and how it winds down. Choosing the right ramp profile is critical because real-world traffic rarely looks like a flat horizontal line.

**Q2. Why does the shape of load matter? Can't you just send max load from the start?**
A: You can, but you learn less and risk false conclusions:
- A cold start under instant full load may trigger initialization failures that wouldn't occur in production (connection pool exhaustion before warm-up completes, cold JVM/V8 compilation, empty caches).
- You can't distinguish "the system degrades at 500 RPS" from "the system crashes because it never had a chance to initialize."
- Gradual ramps surface the *exact threshold* at which latency or error rate bends — information that an instant blast obscures.
- Ramping also mirrors how production traffic actually arrives: server restarts, traffic shifts, marketing campaign bursts.

**Q3. What are the three canonical ramping patterns?**
A:
- **Linear ramp** — VU count (or arrival rate) increases at a constant rate over time, then typically holds at peak for an observation window.
- **Spike test** — load jumps suddenly to a very high level for a short burst, then drops back (or stops). Tests the system's ability to absorb an instantaneous surge.
- **Soak test (endurance test)** — a moderate, sustained load is held for an extended period (hours to days). Tests for memory leaks, connection pool exhaustion, log file bloat, and other time-sensitive degradations.

**Q4. What metrics do you typically capture across all ramp types?**
A: The core set:
- **Response time** — p50, p95, p99, p99.9 (not averages — averages hide tail latency).
- **Throughput** — requests per second (RPS) or transactions per second (TPS) successfully processed.
- **Error rate** — percentage of responses that are 4xx/5xx or timed out.
- **Resource utilization** — CPU %, memory, open file descriptors, DB connection pool saturation, GC pause time.
- **Saturation point** — the load level at which latency starts to climb non-linearly (the "knee of the curve").

## Section 2: Linear Ramp

**Q5. What exactly is a linear ramp test?**
A: A linear ramp is a test profile where the number of virtual users (or arrival rate) increases by a fixed amount per unit of time — forming a straight diagonal line on a VU-vs-time chart. A typical structure:

```
VUs
 ^
200|          /‾‾‾‾‾‾‾‾‾‾‾
 0 |_________/
   0s       60s          180s  → time
   (ramp-up) (steady state)
```

For example: ramp from 0 to 200 VUs over 60 seconds, hold at 200 for 2 minutes, then ramp down.

**Q6. How would you implement a linear ramp in k6?**
A:
```js
import http from "k6/http";
import { sleep } from "k6";

export const options = {
  stages: [
    { duration: "1m", target: 200 },  // ramp up linearly to 200 VUs
    { duration: "2m", target: 200 },  // hold at 200 VUs
    { duration: "30s", target: 0 },   // ramp down
  ],
};

export default function () {
  http.get("https://api.example.com/health");
  sleep(1);
}
```
k6 interpolates VU count linearly between stages, so each second during the first stage adds approximately 3–4 VUs.

**Q7. What does a linear ramp tell you that an instant-load test doesn't?**
A: It pinpoints the *breaking point* — the exact VU count (or RPS) at which:
- p99 latency crosses your SLA threshold.
- Error rate starts climbing above an acceptable baseline.
- A resource (CPU, DB connections, memory) hits saturation.

Because load increases gradually, you can correlate inflection points in the metrics chart with the load level at that moment. An instant-load test only tells you "the system passed or failed at N VUs."

**Q8. What are the common failure modes a linear ramp surfaces?**
A:
- **Throughput ceiling** — RPS plateaus while VUs keep climbing, meaning the server is saturated and queuing requests.
- **Latency cliff** — p99 is flat until ~150 VUs, then spikes sharply at 160 VUs (a common sign of thread pool or connection pool exhaustion).
- **Cascading downstream failures** — a dependent database or microservice becomes the bottleneck before the service under test does.
- **Autoscaling lag** — in cloud environments, you may observe a latency bump as the cluster takes 60–90 seconds to scale out horizontally.

**Q9. How do you choose the ramp duration and target VU count?**
A:
- **Target VU count**: derive from your capacity goal — e.g., "handle 2× peak production traffic" — and convert using Little's Law: `VUs = Throughput × Average Response Time`.
- **Ramp duration**: long enough that the system reaches a steady state before you call "peak" — typically at least 3–5× the system's longest stabilization time (autoscaling time, connection pool warm-up, cache fill). A ramp that's too short hits the server before it's fully initialized.
- **Hold duration**: long enough to accumulate statistically significant samples at peak — usually 2–5 minutes minimum for p99 to stabilize.

## Section 3: Spike Test

**Q10. What is a spike test?**
A: A spike test is a load profile where traffic jumps abruptly from a baseline (or zero) to a very high level for a short duration, then drops back down. The shape on a VU chart looks like a narrow, tall spike:

```
VUs
 ^
1000|     |‾‾|
  50|_____|  |__________
    0s   30s 60s 90s  → time
```

The goal is not sustained performance — it's resilience: can the system survive a sudden, intense burst without cascading failure, data loss, or unacceptable error rates?

**Q11. What real-world scenarios does a spike test model?**
A:
- A celebrity tweets a link to your site and 100,000 users arrive in 60 seconds.
- A cron job triggers 10,000 batch requests at midnight simultaneously.
- A flash sale goes live and checkout traffic multiplies 20× in under a minute.
- A DDoS attack sends a burst of traffic before rate limiting engages.
- A downstream service recovers after an outage and re-drains its retry queue all at once.

**Q12. How do you implement a spike test in k6?**
A:
```js
export const options = {
  stages: [
    { duration: "10s", target: 50 },    // baseline warm-up
    { duration: "1m", target: 50 },     // hold baseline
    { duration: "10s", target: 1000 },  // spike!
    { duration: "1m", target: 1000 },   // hold spike briefly
    { duration: "10s", target: 50 },    // recover to baseline
    { duration: "1m", target: 50 },     // observe recovery
    { duration: "10s", target: 0 },
  ],
};
```
The "observe recovery" phase is often the most important: does the system return to baseline latency and error rate after the spike, or does it remain degraded?

**Q13. What failure modes does a spike test specifically reveal?**
A:
- **Thread pool exhaustion** — the sudden burst consumes all available worker threads; subsequent requests queue up and time out even after the spike ends.
- **Connection pool starvation** — database connections run out mid-spike; error rate spikes and may not recover if the pool doesn't release connections promptly.
- **Circuit breaker thrashing** — if a downstream service opens its circuit breaker during the spike, it may stay open longer than necessary, causing degraded service during the recovery window.
- **Memory pressure / OOM kills** — the spike allocates objects faster than GC can collect; in severe cases the process is killed.
- **Non-idempotent retry storms** — HTTP clients retrying spike-triggered 503s amplify the load further, turning a spike into a sustained surge.
- **Message queue backup** — async systems may survive the spike but suffer a processing lag lasting much longer than the spike itself.

**Q14. How is a spike test different from a stress test?**
A: A **stress test** gradually pushes load beyond expected capacity to find the absolute maximum — it's about finding the ceiling. A **spike test** cares about the *rate of change* in load, not just the level. A system might handle 5,000 RPS sustainably under a stress test but fail at 2,000 RPS if that load arrives in 5 seconds. Spikes test elasticity and shock absorption; stress tests test maximum throughput.

**Q15. What does a "good" spike test result look like?**
A:
- Error rate stays near zero (or within SLA) during the spike, even if latency climbs.
- Latency recovers to pre-spike baseline within a reasonable window after the spike ends (typically ≤60 seconds).
- No process crashes, OOM kills, or database deadlocks.
- Autoscaling (if applicable) triggers and adds capacity before error rate exceeds SLA.
- The system doesn't require a manual restart to recover to normal behavior.

## Section 4: Soak Test

**Q16. What is a soak test?**
A: A soak test (also called an endurance test or longevity test) runs a realistic but moderate load level for an extended period — typically 4–24 hours, sometimes days. The purpose is not to find the breaking point under high load, but to surface *time-dependent* degradation that only manifests after sustained operation:

```
VUs
 ^
100|  /‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\
  0|_/                               \__
   0h                              8h  → time
```

**Q17. What specific failure modes does a soak test catch that shorter tests miss?**
A:
- **Memory leaks** — heap grows steadily; the process may function for hours before it crashes or triggers GC storms. Detectable only with time.
- **Connection leaks** — database or HTTP connections opened but never closed; the pool drains slowly until no connections are available.
- **File descriptor leaks** — open file handles accumulate; the OS limit is typically 65,535 per process.
- **Log rotation issues** — log files fill the disk over hours; the process crashes or stops logging.
- **Session/token expiry edge cases** — JWTs expire mid-test; code that doesn't refresh them correctly starts returning auth errors hours in.
- **Cache poisoning or stale entries** — caches that seemed correct at T+0 surface incorrect data at T+4h when cached entries expire and are incorrectly refreshed.
- **Thread pool drift** — thread pools that don't size correctly over time (growing or shrinking due to bugs in pool management logic).
- **Accumulated technical debt in state** — database tables grow large enough that query plans change, indexes are no longer efficient, and latency climbs.

**Q18. How is soak test load level chosen, relative to production traffic?**
A: Typically 70–80% of the expected peak production load — high enough to exercise all code paths and resource pools realistically, but not so high that you're also stress-testing the system simultaneously. The point is longevity, not extreme load. If you run at 100% peak during a soak test, you can't distinguish time-dependent degradation from load-induced degradation.

**Q19. How would you implement a soak test in k6?**
A:
```js
export const options = {
  stages: [
    { duration: "5m", target: 100 },    // ramp up
    { duration: "8h", target: 100 },    // soak — hold at 70% of peak
    { duration: "5m", target: 0 },      // ramp down
  ],
  thresholds: {
    http_req_duration: ["p(99)<500"],   // p99 must stay under 500ms throughout
    http_req_failed: ["rate<0.01"],     // error rate under 1% throughout
  },
};
```
For very long soak tests, integrate with an external monitoring system (Grafana, Datadog) rather than relying solely on k6's in-memory reporting — k6's memory footprint grows with a very long test run.

**Q20. What monitoring setup do you need for a soak test that you don't need for a 5-minute test?**
A:
- **Heap / memory trending over time** — not just current value; you need a chart of heap growth rate to spot slow leaks.
- **OS-level file descriptor count** — `/proc/<pid>/fd` on Linux, or exported via a metrics agent.
- **DB connection pool utilization over time** — pool metrics from your connection pool library (HikariCP, pg-pool, Sequelize, etc.).
- **Disk usage trending** — especially log and temp directories.
- **Alerting** — for a 4–8 hour test, you won't be watching the dashboard the whole time; set alerts on p99 latency, error rate, and memory so you're paged if thresholds are crossed.
- **Automated test termination** — configure thresholds that abort the test if critical errors exceed acceptable levels, so you don't run 8 hours into a known failure.

## Section 5: Comparing the Three Patterns

**Q21. How do you decide which ramp pattern to use for a given testing objective?**
A:

| Objective                                               | Pattern         |
|---                                                      |---              |
| Find the throughput ceiling / saturation point          | Linear ramp     |
| Verify the system handles expected peak load            | Linear ramp     |
| Test resilience to sudden traffic bursts                | Spike test      |
| Validate autoscaling triggers fast enough               | Spike test      |
| Detect memory leaks, connection leaks, file descriptor leaks | Soak test  |
| Validate SLA compliance over time, not just at peak     | Soak test       |
| Regression test after a deploy                          | Linear ramp (fast) |
| Simulate a flash sale or viral event                    | Spike test      |
| Pre-production sign-off for a long-running service      | Soak test       |

**Q22. Can these patterns be combined? Give an example.**
A: Yes — real test plans often layer them. A common sequence:
1. **Linear ramp** — find the saturation point at ~150 VUs.
2. **Spike test** — confirm the system survives a sudden burst to 3× that level (450 VUs) and recovers.
3. **Soak test** — run at 100 VUs (70% of 150) for 6 hours to check for long-term degradation.

This three-phase plan covers capacity (linear), resilience (spike), and longevity (soak) — the three distinct risk categories in production systems.

**Q23. Quick comparison table:**

| Dimension            | Linear Ramp                          | Spike Test                           | Soak Test                              |
|---                   |---                                   |---                                   |---                                     |
| Duration             | Minutes                              | Minutes                              | Hours–days                             |
| Load level           | Ramps to peak                        | Jumps to extreme peak                | Moderate (70–80% of peak)              |
| Rate of change       | Gradual, constant                    | Instantaneous                        | Flat after initial ramp                |
| Primary question     | Where does the system break?         | Can it absorb a sudden burst?        | Does it degrade over time?             |
| Key metrics to watch | Latency knee, error rate onset       | Error rate during spike, recovery time | Memory trend, connection pool, error drift |
| Common findings      | Thread/pool exhaustion, CPU ceiling  | OOM kills, circuit breaker trips     | Memory leaks, connection leaks, disk fill |
| Frequency            | Every deploy / weekly                | Before major launches                | Monthly / pre-release sign-off         |

## Section 6: Scenario / System Design Style Questions

**Q24. "Your team is launching a flash sale tomorrow. What load test strategy do you run today?"**
A: Prioritize a spike test modeled on the expected traffic shape:
1. Instrument the checkout and product-detail endpoints specifically — those will take the brunt of the sale.
2. Build a spike profile: baseline at normal traffic, then a spike to 10–20× baseline for 60 seconds (matching how quickly a tweet-driven surge arrives), then hold for 5 minutes, then drop.
3. Watch for: connection pool exhaustion on the inventory/payment services, circuit breakers opening on downstream payment gateways, and session store (Redis/Memcached) saturation.
4. Supplement with a brief linear ramp to confirm at what VU count error rate first exceeds 1% — that's your capacity headroom.
5. Make sure autoscaling is enabled *and tested* — the spike test should validate that new instances provision within your acceptable error window.

**Q25. "Your Node.js API has been in production for 3 months. P99 latency is slowly drifting upward week over week, but CPU and RPS are flat. How do you diagnose?"**
A: This is a classic soak-test-catchable symptom — time-dependent degradation, not load-induced. Investigation steps:
1. Run a heap snapshot at T+0 and T+8h (or compare last week's APM heap graphs to this week's). Steadily rising heap with the same traffic is a strong memory leak indicator.
2. Check Node's `process.memoryUsage()` trend — particularly `heapUsed` and `external` (Buffer memory).
3. Audit event listeners and closures added over the app's lifetime — `EventEmitter.listenerCount()` growing is a common Node leak pattern.
4. Check database connection pool utilization — if the pool is slowly being exhausted, queries queue up and inflate p99 even though throughput (RPS) stays flat.
5. Look at GC metrics — if major GC frequency is increasing week over week, the heap is under pressure even if it hasn't OOM'd yet.
6. Run a formal soak test in staging with heap profiling enabled (clinic.js, `--inspect` + Chrome DevTools) to reproduce and isolate the leak.

**Q26. "A junior engineer on your team wants to skip the soak test because 'our unit tests cover all the code paths.' How do you respond?"**
A: Unit tests verify *correctness* of logic at a point in time. Soak tests reveal *behavior under sustained operation* — a fundamentally different class of problem. Memory leaks, connection leaks, and file descriptor exhaustion are not logic bugs; they're resource management bugs that only manifest over time and at production scale. You can have 100% unit test coverage and still OOM in production after 6 hours under load. The right framing: unit tests check "does it do the right thing?"; soak tests check "does it keep doing the right thing after running for hours?" — these are orthogonal questions.

## Quick Reference: k6 Stage Building Blocks

```js
// Linear ramp to peak then hold
stages: [
  { duration: "2m",  target: 200 },   // ramp up
  { duration: "5m",  target: 200 },   // hold
  { duration: "30s", target: 0 },     // ramp down
]

// Spike test
stages: [
  { duration: "1m",  target: 50 },    // baseline
  { duration: "10s", target: 1000 },  // spike
  { duration: "1m",  target: 1000 },  // hold spike
  { duration: "10s", target: 50 },    // recover
  { duration: "2m",  target: 50 },    // observe recovery
  { duration: "10s", target: 0 },
]

// Soak test
stages: [
  { duration: "5m",  target: 100 },   // ramp up to steady state
  { duration: "8h",  target: 100 },   // soak
  { duration: "5m",  target: 0 },     // ramp down
]
```
