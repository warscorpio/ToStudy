# Performance Engineering: Identifying Bottlenecks from Load Test Results — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the goal of a load test, and how does it differ from a stress test and a soak test?**
A: A load test validates that a system meets its performance SLOs under expected (or peak) production traffic. The three are distinct:

| Test type   | Traffic level          | Goal                                                                 | Duration         |
|-------------|------------------------|----------------------------------------------------------------------|------------------|
| Load test   | Expected peak load     | Verify SLOs (latency p99, error rate) are met at target concurrency  | Minutes to hours |
| Stress test | Beyond expected peak   | Find the breaking point — where the system degrades or fails         | Until failure     |
| Soak test   | Sustained normal load  | Surface slow leaks — memory leaks, connection pool exhaustion, GC drift | Hours to days  |

At 5 YOE the important distinction is that a load test tells you "did we pass?" while a stress test tells you "where do we break?" and a soak test tells you "what erodes over time?" — all three produce different bottleneck signatures.

**Q2. What are the key metrics you read first when a load test report lands in your hands?**
A: Read in this order, because each metric contextualises the next:
1. **Throughput (RPS/TPS)** — did the system actually sustain the target request rate, or did it fall behind?
2. **Error rate** — what percentage of requests failed, and what HTTP/gRPC status codes dominate?
3. **Latency percentiles (p50, p95, p99, p999)** — not the mean; the mean hides tail latency. p99 is what your worst 1% of users experience.
4. **Latency over time** — is the p99 flat (steady state) or climbing (leak/saturation)?
5. **Resource utilisation** — CPU, memory, network I/O, disk I/O on every tier (app, DB, cache) correlated against the latency timeline.

The order matters: a high error rate with low latency usually points to a capacity or logic problem; high latency with low error rate points to a saturation or lock contention problem; both together usually means the system is overwhelmed.

**Q3. Why should you never use average (mean) latency as a primary SLO metric?**
A: The mean is dominated by the bulk of fast requests and masked by outliers averaging out. If 95% of requests complete in 10ms but 5% take 5000ms, the mean might be ~260ms — neither representative of the fast majority nor alarming about the slow tail. Users who hit those 5% slow requests experience the system as broken, but the mean doesn't surface that. Use percentiles: p95 bounds the experience for 95% of users, p99 for 99%, p999 for the very tail. For SLOs in production, p99 or p99.9 is standard. Mean latency is acceptable only for rough capacity estimates, never for user-facing SLOs.

**Q4. What is Little's Law, and how does it help you reason about a bottleneck?**
A: Little's Law: `L = λ × W` where L = average number of requests in the system (concurrency), λ = arrival rate (RPS), W = average time a request spends in the system (latency). Rearranged: `W = L / λ`. This tells you that if latency is rising while RPS stays flat, *concurrency inside the system is increasing* — requests are queuing somewhere. If latency rises proportionally with load (W grows as λ grows), you've hit a serialisation bottleneck (a queue, a lock, a single-threaded processor). If latency stays flat until a threshold and then spikes sharply, you've hit a resource ceiling (connection pool exhausted, CPU saturated, memory swapped). The law helps you distinguish "we're queueing" from "we've hit a hard resource limit."

**Q5. What is the Universal Scalability Law (USL), and what does it predict about bottlenecks?**
A: USL (by Neil Gunther) models how throughput scales with concurrency, accounting for two degradation factors: **contention** (σ — the cost of serialising access to a shared resource, e.g., a lock or single DB connection) and **coherence** (κ — the cost of keeping distributed state consistent, e.g., cache invalidation or distributed lock co-ordination). At low concurrency, throughput grows linearly. At medium concurrency, contention dominates and throughput grows sub-linearly. At high concurrency, coherence overhead can cause throughput to *decrease* even as concurrency increases — retrograde scalability. In practice, USL tells you: if your load test shows throughput plateauing or declining as you add threads/connections, you have a contention bottleneck; if latency grows faster than linearly with load, you likely have coherence costs.

## Section 2: Reading the Load Test Report

**Q6. Your load test shows p99 latency of 800ms at 500 RPS but only 60ms at 100 RPS. How do you start diagnosing the cause?**
A: This is a non-linear latency growth pattern — a classic sign of saturation, not just load. Diagnostic steps:
1. **Plot latency vs. RPS as a curve**, not just two points — find the inflection point where latency starts bending upward. That inflection RPS is roughly your saturation point.
2. **Check resource utilisation at 500 RPS vs. 100 RPS** — CPU, memory, DB connection pool utilisation, thread pool queue depth. One of these will be at or near 100% at the inflection point.
3. **Check queue depth metrics** — are requests queueing inside the app server (thread pool), inside the DB connection pool, or inside the DB itself (lock wait queue)?
4. **Drill into slow request traces** — with distributed tracing (Jaeger, X-Ray), compare a fast request trace at 100 RPS with a slow one at 500 RPS. The span that grew explains where time is being spent.

**Q7. Your load test shows p50 = 20ms, p99 = 3000ms. What does this distribution tell you?**
A: A wide p99/p50 gap (150x here) tells you two very different things are happening: most requests are fast, but a small fraction are pathologically slow. This is not a capacity problem (the median is healthy) — it's a **tail latency** problem. Common causes:
- **GC pauses** (JVM / Node.js V8) — GC stops-the-world for the slow requests while the fast majority runs between GC cycles.
- **Lock contention** — a small fraction of requests happen to hit a contested resource (a DB row lock, a Redis SETNX, a mutex in the app).
- **Hot partition** — a specific DB shard, Redis slot, or Kafka partition is overloaded while others are idle.
- **Cold cache** — the slow requests miss cache while the fast majority hits it.
- **Connection pool starvation** — most requests get a pooled connection immediately; the slow requests wait for one to become available.

The fix path differs by cause — GC tuning vs. lock avoidance vs. connection pool sizing vs. cache warming.

**Q8. Your load test shows error rate spiking to 5% at exactly 300 RPS, with no latency increase before the errors appear. What does this pattern suggest?**
A: Errors appearing abruptly at a threshold RPS without a latency precursor usually indicate **hard capacity limits** being hit, not gradual saturation. The most common culprits:
- **Connection pool exhaustion** — at 300 RPS, every connection in the pool is in use; new requests get an immediate timeout/rejection rather than waiting (if the pool's `acquireTimeout` is 0 or very low).
- **OS-level socket/file descriptor limits** — `ulimit` settings hit; new connections are refused.
- **Upstream rate limit** — a third-party API (bureau, UPI gateway, SMS provider) starts returning 429s at this throughput; your service propagates the error.
- **Queue overflow** — an in-memory or SQS queue reaches its max depth and starts dropping messages.
- **Circuit breaker opening** — a downstream dependency is slow enough to trigger the circuit breaker, which then fast-fails all requests.

Diagnosis: check connection pool metrics (pool size, wait queue depth, timeout count), OS metrics (`netstat`, `ss` for connection state), and upstream API error logs.

**Q9. How do you distinguish a CPU bottleneck from an I/O bottleneck in load test results?**
A: The resource utilisation pattern differs:

| Signal                          | CPU bottleneck                                      | I/O bottleneck                                          |
|---------------------------------|-----------------------------------------------------|---------------------------------------------------------|
| CPU utilisation                 | Sustained 90–100% on app nodes                      | Low or moderate (app is waiting, not computing)         |
| Latency shape                   | Grows linearly with load (more work = more time)    | Flat then cliff (I/O completes fast until queue backs up)|
| Thread/goroutine state          | Runnable/running (competing for CPU)                | Blocked/waiting (waiting on I/O, network, lock)         |
| DB/Redis metrics                | DB CPU high, query time up                          | DB CPU low but I/O wait high, or connection wait high   |
| Flame graph                     | Hot CPU functions visible (serialisation, crypto)   | Thin flame graph (app idle, time in syscall/wait)       |

In Node.js services (event loop architecture), a CPU bottleneck manifests as event loop lag — the event loop tick duration increases, delaying all I/O callbacks even though the system isn't doing traditional thread-blocking. Measure with `--perf` or `clinic.js flame`.

**Q10. What does a "sawtooth" latency pattern in a load test timeline indicate?**
A: A sawtooth — periodic spikes in latency followed by recovery to baseline — is almost always a **GC pause pattern** or a **batch job / cron interference**. In JVM services, major GC (full GC or G1 mixed collections) can pause all application threads for 100ms–2s, causing all in-flight requests to stall simultaneously. In Node.js, major V8 GC events create similar spikes. The telltale signs: spike duration correlates with GC pause duration in GC logs; spike frequency correlates with GC cycle frequency. Other causes of sawtooth: a periodic health-check or analytics query that locks a DB table, a cron job that fires every N minutes and saturates the DB or CPU, or a connection pool that periodically recycles idle connections.

**Q11. Your load test tool reports 200 RPS achieved but your DB shows only 50 QPS. How do you interpret this discrepancy?**
A: 200 app-layer RPS but only 50 DB QPS means the database is being hit for only 25% of requests — which is either a sign that **caching is working well** (75% of requests are served from Redis/in-process cache) or a sign of a **measurement gap** (some requests are failing fast before reaching the DB, or the DB metric is sampling incorrectly). Verification steps:
1. Check cache hit rate in Redis/Memcached — if it's ~75%, caching explains the gap and this is healthy.
2. Check error rate — if 75% of requests are erroring before reaching the DB, that explains the gap and is a crisis.
3. Cross-check: `app RPS × (1 - cache hit rate) ≈ DB QPS`. If the math doesn't add up after accounting for errors and cache hits, you have an instrumentation gap.

## Section 3: Bottleneck Localisation by Layer

**Q12. How do you determine whether a bottleneck is in the application layer, the database, or the network?**
A: Localise by correlating latency with per-layer metrics:

1. **Application layer** — is CPU at 100%? Is the thread pool / event loop saturated? Use a profiler (async-profiler for JVM, `clinic.js` for Node) to find the hot function.
2. **Database layer** — check slow query log, `pg_stat_activity` (PostgreSQL) or `SHOW PROCESSLIST` (MySQL) for long-running or waiting queries. Check lock wait time (`pg_locks`, `information_schema.innodb_lock_waits`). Check connection pool saturation (pool size vs. active connections).
3. **Network** — check RTT between app and DB nodes (`ping`, `traceroute`). Check bandwidth utilisation. Check for TCP retransmissions (`netstat -s`). If running on AWS, check ENI metrics for packet drops or throttling.

The practical shortcut: add distributed tracing spans around each layer (DB call, cache call, external API call, internal business logic). The span that accounts for the lost time is the bottleneck layer.

**Q13. What PostgreSQL queries do you run to identify database-level bottlenecks during or after a load test?**
A:
```sql
-- Long-running queries right now
SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC
LIMIT 20;

-- Queries with the highest total execution time (needs pg_stat_statements)
SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- Tables with the most sequential scans (missing index candidates)
SELECT relname, seq_scan, idx_scan,
       seq_scan::float / NULLIF(seq_scan + idx_scan, 0) AS seq_ratio
FROM pg_stat_user_tables
ORDER BY seq_scan DESC
LIMIT 20;

-- Lock waits
SELECT blocked.pid, blocked.query, blocking.pid AS blocking_pid, blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;
```
At 5 YOE, you should be able to run these unprompted during a post-load-test investigation — not just describe them.

**Q14. How do you identify a connection pool bottleneck specifically?**
A: Three signals, checked in combination:
1. **Pool wait time metric** — most connection pool libraries (HikariCP, `pg` for Node, Sequelize) expose `pool.waitingCount` or `pool.pendingAcquires`. If this is non-zero and growing, requests are queuing for a connection.
2. **DB-side connection count** — `SELECT count(*) FROM pg_stat_activity WHERE state != 'idle'` — if this equals your pool max size and stays there, the pool is saturated.
3. **Latency histogram by request type** — if slow requests all have a similar initial delay before any DB span starts (visible in traces), they waited for a connection, not for the query itself.

Fix options: increase pool size (bounded by DB `max_connections`), reduce query duration (fewer connections held for shorter time), or introduce read replicas to spread the load.

**Q15. Your load test shows Node.js event loop lag spiking to 500ms under load. How do you find the cause?**
A: Event loop lag means something is blocking the single-threaded event loop — a CPU-intensive synchronous operation, a very large synchronous I/O operation, or a long `JSON.parse`/`JSON.stringify` on a large payload. Investigation steps:
1. **`clinic.js flame`** — generates a flame graph of CPU time; the widest hot function on the main thread is the culprit.
2. **`--inspect` + Chrome DevTools profiler** — record CPU profile under load; look for synchronous functions with high self-time.
3. **`perf_hooks` `PerformanceObserver`** — measure event loop utilisation programmatically: `const { eventLoopUtilization } = require('perf_hooks').performance;`.
4. Common culprits in fintech Node services: synchronous crypto operations (use `crypto.pbkdf2` async, not `pbkdf2Sync`), large `JSON.parse` on API responses, bcrypt sync hashing, synchronous `fs` calls in a request path.

Fix: move CPU work to worker threads (`worker_threads`), switch sync to async equivalents, or offload to a separate process/Lambda.

## Section 4: Tools & Instrumentation

**Q16. What load testing tools do you know, and how do you choose between them?**
A:

| Tool       | Language / model      | Best for                                                         |
|------------|-----------------------|------------------------------------------------------------------|
| k6         | JS, goroutine-based   | Developer-friendly, scriptable, CI integration, good for APIs    |
| Gatling    | Scala DSL             | High concurrency simulation, detailed HTML reports               |
| JMeter     | GUI + XML             | Legacy teams, complex test plans, plugin ecosystem               |
| Locust     | Python                | Pythonic, easy to extend, good for custom protocols              |
| Artillery  | JS/YAML              | Quick API load tests, good CI integration                        |
| wrk / wrk2 | C, CLI                | Raw HTTP benchmarking, minimal overhead, latency accuracy        |

For a Node.js/NestJS backend, **k6** is the most natural choice — scripts are JS, it integrates with Grafana/InfluxDB, and it produces accurate percentile histograms. For raw baseline benchmarks, `wrk2` is preferred because it uses a coordinated-omission-corrected latency model (unlike most tools that underreport tail latency by not accounting for requests that were never sent during slow periods).

**Q17. What is "coordinated omission" in load testing, and why does it matter?**
A: Coordinated omission is a measurement flaw in most load testing tools: when the system is slow, the tool sends fewer requests (it waits for the previous one to complete before sending the next), so the slow period is under-sampled. The result: the tool reports optimistic latency because it never measured the requests that *would have* arrived during the slow period but didn't — the tool and the system "co-ordinated" to hide the problem. `wrk2` and `HDR Histogram`-based tools correct for this by modelling what a real Poisson-arrival client would have experienced, including the waiting time for requests that were backlogged. At 5 YOE, knowing this exists and citing `wrk2` or HDR Histogram is a strong signal of depth.

**Q18. How do you set up a load test to give useful, comparable results across runs?**
A: Repeatability requires controlling for:
1. **Warm-up period** — exclude the first 30–60 seconds from results; cache cold starts and JIT compilation skew early numbers.
2. **Fixed random seed** — if your test selects random user IDs or payloads, seed the RNG so the same data is accessed across runs.
3. **Stable data volume** — same number of rows in DB, same cache fill ratio at test start. A growing dataset across runs changes query plan performance.
4. **Isolated environment** — no other workloads on the same nodes; disable auto-scaling during the test (or explicitly test with it enabled and note it).
5. **Infrastructure-as-code for test env** — use Terraform/Helm to provision a production-equivalent environment; document instance types and DB tier so results are reproducible.
6. **Result storage** — push metrics to InfluxDB/Prometheus with timestamps; never compare two runs from memory or screenshots.

**Q19. How do you integrate load testing into a CI/CD pipeline for a NestJS service?**
A: A practical setup:
1. **k6 script** in the repo under `tests/load/` — defines target RPS ramp, assertions on p99 and error rate thresholds.
2. **CI stage** (GitHub Actions / GitLab CI) — spins up a staging environment (or uses a dedicated perf environment), runs the k6 script, fails the pipeline if thresholds are breached.
3. **Metrics push** — `k6 run --out influxdb=http://influxdb:8086/k6` sends results to InfluxDB; a Grafana dashboard shows trend across commits.
4. **Baseline tracking** — tag each run with the git commit SHA; alert if p99 regresses more than 20% vs. the last passing run.
5. **Scope** — don't run full load tests on every PR (too slow); run a smoke test (1–5 minutes at moderate RPS) on every merge to main, and run the full load test nightly or pre-release.

## Section 5: Pitfalls & Anti-patterns

**Q20. What is "noisy neighbour" interference in a load test, and how do you control for it?**
A: In a shared cloud environment (same EC2 host, same RDS instance, same EKS node), other workloads can consume CPU, network, or disk I/O on the same physical hardware — making your results non-deterministic. Symptoms: the same load test produces wildly different p99s on consecutive runs with no code change. Mitigations:
- Use **dedicated instances** (AWS Dedicated Hosts, `db.r6g` RDS instance with provisioned IOPS) for perf testing.
- Run multiple identical test runs and take the median p99 (3–5 runs).
- Monitor EC2 `CPUSurplusCreditsCharged` and `NetworkIn` on the host — a spike in either indicates noisy neighbour.
- Time tests to run at off-peak hours if using shared staging infrastructure.

**Q21. Why can a load test that passes in staging fail in production, even with identical code?**
A: Several structural differences between staging and production that aren't visible in code:
- **Data volume** — staging has thousands of rows; production has millions. Query plans change, index range scans become sequential scans, VACUUM takes longer.
- **Data distribution** — staging has uniform test data; production has hot users, hot product IDs, Zipf-distributed access patterns. A "hot row" that gets locked by many concurrent writers doesn't appear in staging.
- **Connection count** — staging has 5 services; production has 50. The aggregate connection count to the DB is 10x, exhausting `max_connections` in production but not staging.
- **Cache warm state** — staging cache is cold or sparsely populated; production cache is warm. Load test against cold cache is a different (usually harder) test.
- **Network topology** — staging may be in the same AZ; production spans multiple AZs with real cross-AZ latency.
- **External dependencies** — staging mocks third-party APIs; production hits real bureau, payment, and UPI APIs that have their own rate limits and tail latencies.

**Q22. What is the "coordinated omission" problem in your own service's instrumentation (not just load tools)?**
A: Your application can also self-report optimistically if it only measures time for requests it successfully processed quickly. If a request queues in the thread pool for 2 seconds before being picked up, and you start your timer when the handler begins executing, you've omitted the 2 seconds of queue wait. The full latency the user experienced was 2s + processing time — your metrics only show processing time. Fix: start the timer at the point the request enters your system — the HTTP server's request event, not the first line of your controller handler. In NestJS, use a middleware (not a guard or interceptor) to timestamp the request at ingress.

## Section 6: Scenario / System Design Style Questions

**Q23. "Your k6 load test shows the loan application submission endpoint handles 200 RPS cleanly but degrades at 250 RPS — p99 goes from 300ms to 4s. Walk me through your full investigation."**
A: Structured approach:

**Step 1 — Characterise the failure:**
- Is it latency-only, or are errors appearing too? Pure latency → saturation, not failure.
- Does it recover if load drops back to 200 RPS? Yes → clean saturation point. No → something is leaking (connections, memory).

**Step 2 — Localise by layer (distributed tracing):**
- Compare a 300ms trace at 200 RPS with a 4s trace at 250 RPS.
- Identify which span holds the extra 3.7 seconds: DB call? External bureau API call? Internal queue wait? App processing?

**Step 3 — Resource metrics at the inflection point:**
- CPU on app pods — if 100%, the app is the bottleneck (scale horizontally or optimise).
- DB connection pool saturation — check `pool.waitingCount`. If >0, the bottleneck is connections (increase pool or reduce query time).
- Redis `instantaneous_ops_per_sec` and latency — Redis hitting limits?
- DB `pg_stat_activity` — are there long-running queries or lock waits at 250 RPS that don't appear at 200 RPS?

**Step 4 — Hypothesis and fix:**
Fintech loan submission typically involves: DB write (application record) + DB reads (eligibility checks) + external API call (bureau check, PAN validation) + async event publish (Kafka). The most likely culprit at this RPS delta: DB connection pool exhaustion (the write + multiple reads hold a connection for the full request duration, and at 250 RPS you run out), or the external API becoming the limiter.

Fix candidates: increase connection pool size, move bureau API call to async (submit → poll), add read replica for eligibility reads, or horizontally scale app pods.

**Q24. "A soak test run for 4 hours shows p99 latency degrading from 200ms to 800ms with stable RPS throughout. No errors. What are you looking for?"**
A: Slow, monotonic degradation over hours with stable load and no errors is the signature of a **slow resource leak**. Investigation checklist:

1. **Memory leak** — plot heap/RSS over time on every app node. Monotonically growing → memory leak. In Node.js, use `--expose-gc` + `v8.getHeapStatistics()`, or heap snapshot diff between T=0 and T=4hr with Chrome DevTools. Objects accumulating in memory eventually trigger GC pressure, which explains the rising latency.
2. **Connection leak** — plot open connections to DB and Redis over time. If they grow without bound, connections are being acquired but not released (missing `await client.release()` in a `finally` block, for example).
3. **Log file / disk pressure** — if the app or DB is logging to disk and the disk fills up, write latency can spike. Check disk utilisation over the 4-hour window.
4. **DB table bloat** — in PostgreSQL, a 4-hour test generating writes causes table bloat (dead tuples from UPDATEs/DELETEs). If VACUUM doesn't run during the test, sequential scans get slower as pages fill with dead tuples. Check `pg_stat_user_tables.n_dead_tup`.
5. **JVM metaspace / PermGen** — in Java services, class loader leaks slowly fill metaspace, increasing GC pause frequency over hours.

**Q25. "You're onboarding as a senior engineer at a fintech startup. The team tells you 'our APIs are slow but we don't know where.' You have no existing load test. How do you start?"**
A: A practical, structured ramp-up:

**Week 1 — Instrument before you test:**
- Ensure every HTTP request logs: timestamp, endpoint, duration, status code, user ID. Without this, load test results have nothing to correlate against.
- Add a distributed tracing library (OpenTelemetry → Jaeger or X-Ray) to the NestJS services. Every request must produce a trace with DB, Redis, and external API spans.
- Add a metrics layer (Prometheus + Grafana or Datadog): CPU, memory, event loop lag (Node.js), DB connection pool metrics, DB query time histogram.

**Week 2 — Baseline load test:**
- Write a k6 script covering the 3–5 highest-traffic endpoints (from access logs or APM).
- Run at very low RPS (10% of expected peak) to establish a clean baseline p99.
- Gradually ramp to expected peak RPS. Record the inflection point.

**Week 3 — Fix the top bottleneck (not all of them):**
- From the traces, identify the single biggest latency contributor (Pareto principle: one fix typically resolves 50–80% of the problem).
- Common findings in a greenfield fintech backend: missing DB indexes on FK columns queried in loan search, synchronous external API calls that should be async, N+1 query patterns in an ORM, no caching on reference data.
- Fix, rerun the load test, compare p99 before and after.

The discipline: **measure first, fix second, validate third**. Never "optimise" without a before-and-after load test comparison.

## Quick Reference: Bottleneck Signatures

| Symptom                                        | Most likely cause                                         | First place to look                                  |
|------------------------------------------------|-----------------------------------------------------------|------------------------------------------------------|
| Latency grows linearly with RPS                | CPU saturation / compute-bound                            | CPU utilisation, flame graph                         |
| Latency flat then cliff at threshold RPS       | Hard resource limit (pool, FD, rate limit)                | Connection pool metrics, OS limits, upstream errors  |
| p99 >> p50 (wide percentile gap)               | Tail latency: GC, lock contention, cache miss             | GC logs, lock wait metrics, cache hit rate           |
| Sawtooth latency pattern                       | GC cycles or periodic batch job                           | GC pause logs, cron job schedule                     |
| Latency degrades over hours (soak)             | Memory/connection leak, table bloat                       | Heap growth, connection count, DB dead tuples        |
| Errors at threshold, no latency precursor      | Pool exhaustion, rate limit, circuit breaker              | Pool wait queue, upstream API error codes            |
| Low app CPU, high latency                      | I/O bound: waiting on DB, Redis, external API             | Distributed trace spans, DB query time               |
| Throughput declining as concurrency increases  | Contention / lock serialisation (USL retrograde)          | DB lock waits, mutex contention, Redis WAIT calls    |
| Staging passes, production fails               | Data volume, hot rows, connection count, cold cache       | Query plans, `pg_stat_activity`, data distribution   |

---

**Tip for the interview:** At the 5 YOE level, "how do you find a bottleneck" is really asking whether you have a *systematic* process — not whether you got lucky once. The answer they want: instrument first (tracing + metrics), load test with realistic data, read percentiles not means, localise by layer (app → DB → network → external), correlate resource metrics against the latency timeline, and fix the top-one thing before re-testing. Have one real war story ready — a soak test that found a connection leak, a p99 investigation that traced back to a missing index, or a stampede you caught with jitter — that's the answer that lands at this level.
