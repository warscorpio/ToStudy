# Performance Metrics: Throughput, Latency (p50/p95/p99), Error Rate & Concurrency — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are the four primary metrics used to characterize a system's performance?**
A: The four pillars are:
- **Throughput (RPS/TPS)** — how much work the system completes per unit of time (requests per second, transactions per second).
- **Latency** — how long a single unit of work takes from the requester's perspective, typically reported as percentile distributions (p50, p95, p99).
- **Error rate** — the fraction of requests that fail (return a 5xx, timeout, or otherwise produce an incorrect result), usually expressed as a percentage or per-mille.
- **Concurrency** — the number of requests being actively handled at the same instant. Not a quality metric on its own, but the context in which throughput and latency are measured.

Together they answer: "How fast? How reliably? Under how much load?"

**Q2. What is throughput, and how is RPS different from TPS?**
A: Throughput is the rate of successful work completed. **RPS (requests per second)** measures HTTP-level request volume — it includes every GET, POST, and polling call. **TPS (transactions per second)** usually refers to logically complete business operations, which may span multiple requests (e.g., a checkout flow is one transaction but fires 4–5 API calls). In database contexts, TPS typically means committed transactions on the DB engine. The distinction matters when you're capacity-planning: a single user action might cause 10 RPS of backend fan-out, so "we handle 1000 RPS" and "we handle 1000 TPS" tell very different stories.

**Q3. What is latency, and why do we report it as percentiles rather than averages?**
A: Latency is the elapsed time between a client sending a request and receiving a complete response. Averages mask the distribution: a service with p50 = 10ms and p99 = 4000ms has an average that looks acceptable (~50ms) while 1 in 100 users waits 4 seconds — an entirely different quality of service. Percentiles expose the *tail* of the distribution, which is where real user pain lives. The canonical set:
- **p50 (median)** — half of requests are faster than this. Represents the typical user experience.
- **p95** — 95% of requests are faster. A good proxy for "almost everyone's experience."
- **p99** — 99% of requests are faster. Captures the worst-case experience at scale; if you have 10M requests/day, p99 still affects 100K users.

**Q4. What is an error rate and how is it calculated?**
A: Error rate = `(failed requests / total requests) × 100%`. "Failed" needs a precise definition agreed upon per service:
- HTTP 5xx responses (server-side errors)
- HTTP 4xx that represent system faults (e.g., 429 from a broken rate limiter) — though client errors (genuine 404s) usually aren't counted
- Successful HTTP responses that carry an application-level error payload
- Timeouts, connection resets, circuit breaker rejections

In SLO contexts, error rate is often reported as the complement: **availability** = `1 - error_rate`. A 99.9% availability target means at most 0.1% of requests can fail in any given window.

**Q5. What is concurrency in the context of a web service?**
A: Concurrency is the number of in-flight requests being processed simultaneously. A request is "in-flight" from the moment the server accepts the connection until the last byte of the response is sent. High concurrency stresses shared resources: thread pools, DB connection pools, memory, CPU. Concurrency is related to throughput and latency by **Little's Law**: `L = λ × W`, where L = concurrent requests (concurrency), λ = throughput (arrival rate), W = latency. Practically: if a service receives 500 RPS and each request takes 200ms on average, it holds ~100 concurrent requests at any moment.

## Section 2: Latency Percentiles In Depth

**Q6. What is Little's Law, and how do you use it to reason about capacity?**
A: Little's Law (`L = λW`) is a fundamental result from queuing theory that holds for any stable system:
- **L** = average number of items in the system (concurrent requests)
- **λ** = throughput (arrival/completion rate)
- **W** = average time an item spends in the system (latency)

Practical uses:
- Given a DB connection pool of 50 connections (L=50) and average query time of 5ms (W=0.005s), the pool can sustain λ = 50/0.005 = **10,000 QPS** before queuing begins.
- If latency climbs (W increases) at the same arrival rate (λ), L grows — you need more capacity or the system backs up.
- Works at every layer: HTTP server, DB pool, message queue, thread pool.

**Q7. Why is p99 latency often far worse than p95, and what typically causes tail latency?**
A: Tail latency explodes because rare, slow events cluster at the high percentiles. Common causes:
- **GC pauses** (JVM/Go stop-the-world) — a GC cycle that takes 200ms turns every request in flight at that moment into a p99+ outlier.
- **Lock contention** — a slow DB write holds a row lock; concurrent readers queue up.
- **Cold caches** — cache eviction or restart leaves certain keys uncached; the next request must go to DB.
- **Resource exhaustion** — a thread pool or connection pool momentarily saturated; requests queue for a worker.
- **Network jitter / retransmits** — packet loss causes TCP retransmit timers (minimum 200ms on many stacks).
- **Fan-out amplification** — a request that fans out to N downstream services sees the *max* latency of those N calls (the "straggler" problem).

**Q8. What is the "staircase" pattern you sometimes see in latency histograms, and what does it indicate?**
A: A staircase — discrete steps at round numbers like 100ms, 250ms, 500ms, 1000ms — usually indicates **timeouts or retries at fixed intervals**. If a downstream call times out at 500ms and the client immediately falls back to a default, you'll see a dense cluster of requests at exactly 500ms in the histogram. Similarly, OS-level TCP retransmit timers (200ms, then 400ms, 800ms in exponential backoff) create clusters. When you see this pattern, the histogram is telling you there's a hard timeout somewhere in the path — investigate whether those timeouts are appropriate or masking a deeper slowness.

**Q9. What is "latency percentile at load" and why does measuring latency in isolation give a false picture?**
A: Latency measured on a single, unloaded instance tells you the best-case floor — it ignores queuing effects, resource contention, and GC pressure that only appear under load. At high concurrency, CPU scheduling latency, lock wait time, and connection pool wait time add up — the same request that took 10ms at 10 RPS may take 200ms at 500 RPS because it spends 190ms waiting for a DB connection. Always measure latency **as a function of concurrency/throughput** — plot a latency-vs-load curve. The "knee" of that curve (where latency starts rising sharply) is your practical throughput ceiling.

**Q10. What is the difference between service-side latency and client-perceived latency?**
A: Service-side latency is measured from first byte received by the server to last byte sent. Client-perceived latency additionally includes:
- **Network RTT** (both directions) — can add 1ms–200ms depending on geography
- **DNS resolution** — typically 20–100ms on first request
- **TLS handshake** — 1–2 RTTs (100–300ms without session resumption)
- **Time to First Byte (TTFB)** vs **Time to Last Byte (TTLB)** — for streaming responses, the gap matters
- **Client-side processing** — JSON parsing, rendering

For user-facing SLOs, client-perceived latency is what matters. Server-side metrics help diagnose; Real User Monitoring (RUM) data (e.g., from the browser's `Performance` API) shows the truth.

## Section 3: Error Rate & SLOs

**Q11. What is an SLO, and how does error rate factor into it?**
A: An **SLO (Service Level Objective)** is an internal target for a measurable reliability indicator — the team commits to hitting it. An **SLA (Service Level Agreement)** is the externally contractual version (usually less strict than the SLO, with financial penalties for breach). Error rate is one of the most common SLO dimensions:

```
SLO: 99.9% of requests over any 30-day rolling window return a non-5xx response
     within 500ms at p99
```

The **error budget** = `(1 - SLO target) × total request volume`. At 99.9% over 30 days (~2.6B seconds of request time), you can afford 0.1% failures — spend that budget on deployments, experiments, and incidents. When the budget is exhausted, freeze risky changes.

**Q12. What is the difference between a hard error and a soft error, and how do you classify them in your error rate?**
A: 
- **Hard errors** — the operation definitively failed: HTTP 500, DB constraint violation, unhandled exception. Always counted in the error rate.
- **Soft errors** — partial success, degraded response, or expected business rejections: 404 "user not found," 429 rate limit, 400 validation failure from malformed client input. These may or may not be counted depending on SLO intent.
- **Latency violations** — a response that arrives but takes 10× the p99 target is sometimes treated as a "good/bad" classification in SLO accounting (a "slow good" can be reclassified as bad).

The important thing is that your team's definition of "error" is **explicit and consistent** — documented in the SLO spec so alerting and dashboards agree.

**Q13. How do you separate your service's errors from upstream dependency errors?**
A: Attribute errors by cause at the point of measurement:
- Tag all outbound calls with dependency name, and log their status separately.
- When a dependency returns 5xx, your service's error rate should count that as an error (from the caller's perspective), but **also** attribute it to the dependency in your observability data.
- Use **dependency error budgets** — track `upstream_error_rate` separately from `own_error_rate`. If 0.08% of your errors are caused by a flaky third-party API and your SLO allows 0.1%, you know how much headroom remains for your own bugs.
- In distributed tracing, tag spans with `error=true` at the point of origin — this lets you distinguish cascading failures (root cause is deep in the trace) from local failures.

## Section 4: Throughput & Concurrency

**Q14. What limits maximum throughput in a typical API service?**
A: Throughput is bounded by the **slowest shared bottleneck** in the request path — often called the "bottleneck resource":
- **CPU** — CPU-bound work (crypto, image processing, tight loops) saturates cores. Throughput ≤ `(cores × utilization_ceiling) / CPU_time_per_request`.
- **I/O** — DB queries, file reads, outbound HTTP calls. If each request waits 50ms for a DB query and you have a 100-connection pool, max DB-bound throughput = 100 / 0.050 = **2,000 RPS**.
- **Network bandwidth** — large response bodies can saturate NIC bandwidth before CPU is maxed.
- **Thread/goroutine pool** — if your server model is one-thread-per-request, max concurrency = thread pool size, capping throughput at `pool_size / avg_latency`.
- **Memory** — large in-flight request state (e.g., streaming large files) can exhaust heap, triggering GC pressure that in turn degrades latency and throughput.

**Q15. What is the difference between horizontal and vertical scaling, and how does each affect these four metrics?**
A:

| Dimension        | Vertical Scaling (bigger machine)               | Horizontal Scaling (more machines)                         |
|--                |--                                               |--                                                          |
| Throughput       | Increases (more CPU/memory per instance)        | Increases linearly (load-balanced across instances)        |
| Latency          | May decrease (faster CPU, lower GC pressure)    | Roughly unchanged per instance; p99 can improve if hot spots are distributed |
| Error rate       | Unchanged unless errors were OOM/timeout        | Can decrease if errors were caused by overload             |
| Concurrency cap  | Higher (more threads/connections per instance)  | Higher overall (distributed across instances)              |
| Limits           | Hard ceiling (biggest VM available); no HA      | Near-unlimited (within coordination overhead); HA by default |

Horizontal scaling is preferred for stateless services; stateful services (DB leaders, session stores) are harder to scale horizontally and often require sharding or read replicas.

**Q16. What is the "thundering herd" problem, and which metric does it most affect?**
A: A thundering herd occurs when a large number of clients simultaneously send requests after a shared trigger — typically a cache expiry, a service restart, or a batch job completion. All requests arrive at once, overwhelm the system's queue, and either time out (error rate spikes) or pile up (concurrency spikes, causing extreme p99 latency). Mitigations:
- **Cache stampede prevention** — probabilistic early recomputation (recalculate before expiry with some probability) or a mutex/promise-coalescing pattern (only one goroutine recomputes; others wait on it).
- **Jitter on retry/backoff** — stagger client retries with random jitter to break synchrony.
- **Rate limiting / request coalescing at the edge** — collapse N identical in-flight requests into one upstream call.

**Q17. How does connection pooling interact with concurrency and throughput?**
A: A DB connection pool sets a hard cap on concurrency at the data layer. If the pool has 20 connections and each query takes 10ms average:
- Throughput ceiling = 20 / 0.010 = **2,000 QPS**
- At 3,000 QPS arrival rate, requests queue for a connection → avg wait time increases → latency climbs → p99 degrades fast
- At extreme overload, connection wait timeouts trigger → error rate rises

Pool tuning: setting the pool too large is also harmful — too many concurrent DB connections cause context-switch overhead and lock contention on the DB side. The right pool size is typically derived empirically: `pool_size ≈ (cores_on_db × 2) + disk_spindle_count` (PgBouncer/HikariCP defaults use similar heuristics).

## Section 5: Measuring & Instrumenting These Metrics

**Q18. How do you instrument an API to emit these four metrics?**
A: With a metrics library (Prometheus client, StatsD, OpenTelemetry SDK), add instrumentation at the request boundary:

```typescript
// Express middleware example (Prometheus)
import { Counter, Histogram, Gauge } from 'prom-client';

const httpRequestDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'Request latency in seconds',
  labelNames: ['method', 'route', 'status_code'],
  buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5], // p50–p99 coverage
});

const httpRequestTotal = new Counter({
  name: 'http_requests_total',
  help: 'Total HTTP requests',
  labelNames: ['method', 'route', 'status_code'],
});

const httpRequestsInFlight = new Gauge({
  name: 'http_requests_in_flight',
  help: 'Concurrent requests being handled',
});

app.use((req, res, next) => {
  const end = httpRequestDuration.startTimer();
  httpRequestsInFlight.inc();

  res.on('finish', () => {
    const labels = { method: req.method, route: req.route?.path ?? 'unknown', status_code: res.statusCode };
    end(labels);
    httpRequestTotal.inc(labels);
    httpRequestsInFlight.dec();
  });

  next();
});
```

Derive in Prometheus:
```promql
# p99 latency over 5m
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

# RPS
rate(http_requests_total[1m])

# Error rate
rate(http_requests_total{status_code=~"5.."}[5m]) / rate(http_requests_total[5m])
```

**Q19. What is the difference between a histogram and a summary in Prometheus, and which should you use for latency?**
A: 
- **Histogram** — buckets count observations in predefined ranges (e.g., `≤10ms`, `≤50ms`, `≤100ms`). Quantiles are computed server-side (in Prometheus) at query time using `histogram_quantile()`. Buckets are aggregatable across instances — you can compute fleet-wide p99 correctly.
- **Summary** — quantiles are computed client-side (in the app process) over a sliding window and exported as-is. Cannot be meaningfully aggregated across instances (you can't average p99s from 10 pods to get the fleet p99).

**Use histograms** for latency in distributed services. The tradeoff: you must define bucket boundaries upfront (poorly chosen buckets lose precision at the tails), and cardinality must be kept low (avoid high-cardinality labels like `user_id` in histogram labels).

**Q20. What are USE and RED methods, and how do they map to these four metrics?**
A:
- **USE (Utilization, Saturation, Errors)** — Brendan Gregg's method, designed for **infrastructure resources** (CPU, disk, network, memory):
  - Utilization = % of time the resource is busy
  - Saturation = queue depth / wait time when resource is at capacity
  - Errors = error events from the resource

- **RED (Rate, Errors, Duration)** — Tom Wilkie's method, designed for **request-driven services** (APIs, microservices):
  - Rate = throughput (RPS)
  - Errors = error rate
  - Duration = latency (percentiles)

Concurrency sits between the two: it's a saturation signal for USE and context for RED. In practice, monitor both layers — RED metrics on every service, USE metrics on every host/container. Alert on RED; investigate with USE when something is wrong.

## Section 6: Scenario / System Design Style Questions

**Q21. "Our p99 latency is 2× higher on Mondays at 9am. Throughput is the same. What's your investigation plan?"**
A: The pattern (predictable spike at business-hours start) suggests a **cold start or cache flush** problem, not a load problem (throughput is unchanged):
1. **Check cache hit rate** — if an in-memory or Redis cache resets overnight (TTL, restart, eviction), Monday 9am sees the first wave of cold-cache requests hitting the DB.
2. **Check scheduled jobs** — a batch job, report generation, or DB VACUUM running at 8:30am could be holding locks or saturating I/O, elevating latency for concurrent API requests.
3. **Check connection pool state** — pool may have shrunk overnight (idle connection timeout), so the first burst of requests must wait for new connections to be established.
4. **Check GC/heap metrics** — if the service had low traffic overnight and GC ran aggressively, the JVM/Go runtime may be in a state where the first burst triggers a stop-the-world.
5. **Correlate with DB slow query logs** — do specific queries appear in the slow log only on Monday mornings?
   
Likely fix: cache warming on startup, scheduled job rescheduling, or raising idle connection minimum in the pool.

**Q22. "How would you design an SLO dashboard for a payments API that surfaces all four metrics clearly?"**
A: A well-structured dashboard has three rows:

**Row 1 — User Impact (RED)**
- RPS over time (split: success vs error), colored by threshold
- p50 / p95 / p99 latency on a single graph with SLO threshold lines
- Error rate % with a burn-rate gauge (how fast the error budget is being consumed)

**Row 2 — Concurrency & Saturation**
- In-flight request count vs max configured concurrency
- DB connection pool: active / idle / wait queue depth
- Thread pool queue depth (if applicable)

**Row 3 — Error Budget**
- Rolling 30-day error budget remaining (bar, burns down)
- Error budget burn rate (1h, 6h windows — multiwindow alerting)
- Recent incidents annotated on the latency graph

Key design choices: latency in log scale (makes p99 outliers visible without p50 becoming invisible), error rate as a ratio not absolute count (so it's meaningful at any throughput), and burn rate alerts rather than static threshold alerts (burn rate fires early when you're heading toward budget exhaustion, not just when you've already missed it).

**Q23. "A load test shows that our service handles 500 RPS at p99 = 80ms, but at 600 RPS p99 jumps to 800ms. Why might there be such a sharp inflection?"**
A: This is the **knee of the latency-throughput curve** — a sign that a shared resource is saturating. Classic causes:
- **Connection pool exhaustion** — at 600 RPS, the pool hits its cap; requests queue for a connection. Queue wait time ≈ `queue_length × avg_query_time`. A queue of just 10 requests × 80ms = 800ms added latency.
- **CPU saturation** — at 600 RPS, CPU > 90% utilization; OS scheduler time-slices less favorably, adding scheduling latency per request.
- **GC wall time** — at higher allocation rate (more concurrent requests in flight), GC frequency and pause duration increase, pausing all in-flight requests simultaneously.
- **Lock hotspot** — a mutex or row lock that's rarely contended at 500 RPS becomes frequently contended at 600 RPS.

Diagnostic: check CPU utilization, DB connection pool `wait_count`, GC logs, and lock wait statistics — all sampled during the load test. The fix is resource-specific: add pool connections, scale horizontally, reduce GC pressure (object pooling), or shard the lock.

**Q24. "You need to set throughput-based autoscaling for a Node.js API. Should you scale on RPS, CPU, or concurrency?"**
A: For a Node.js (single-threaded event loop) service, the best signal depends on the workload:
- **CPU** — right for CPU-bound Node (heavy computation, tight loops). Node saturates a single core; when CPU > 70%, scale out.
- **Concurrency / in-flight requests** — right for I/O-bound Node (most APIs: DB calls, outbound HTTP). Node handles high I/O concurrency efficiently, but if too many requests are in-flight simultaneously, memory grows and event loop lag increases. Scale on `http_requests_in_flight > threshold`.
- **Event loop lag** — the most precise signal for Node health. Lag > 50ms means the event loop is backed up. Expose via `perf_hooks` or `prom-client`'s `collectDefaultMetrics` (includes `nodejs_eventloop_lag_seconds`). Scale when lag exceeds your latency budget.
- **RPS** is useful for predictive (scheduled) scaling but lags for reactive scaling because high RPS alone doesn't mean the service is struggling — it depends on per-request work.

In practice: combine event loop lag + in-flight request count for Node autoscaling; use CPU as a ceiling alert.

**Q25. "Describe how you'd perform a load test that gives you meaningful p99 data — what mistakes do most engineers make?"**
A: Common mistakes and the correct approach:

| Mistake | Correct Approach |
|--|--|
| Running the load test for only 30 seconds | Run for at least **10 minutes** — GC cycles, connection pool warm-up, and cache effects need time to stabilize |
| Ignoring the warm-up phase | Discard the first 60–90 seconds from metrics; cold-start noise contaminates p99 |
| Testing at a single RPS value | Ramp throughput gradually (step or linear ramp) to find the knee of the curve |
| Measuring only on the load generator | The load generator itself can be CPU-bound; measure latency **at the service** (server-side histograms), not just from the client |
| Using a single client thread | A single thread serializes requests; use a tool with async concurrency (k6, Gatling, wrk2, hey) and set concurrency independently of RPS |
| Not coordinating with downstream stubs | If DB or external APIs aren't load-tested too, they become the bottleneck and you measure their limits, not yours |
| Reporting only averages | Report full histogram: p50, p75, p90, p95, p99, p99.9. Averages are meaningless for capacity decisions |

Tool recommendation: **k6** (JavaScript-scriptable, built-in percentile reporting, supports ramping VUs) or **wrk2** (constant-throughput mode, accurate latency histograms using HdrHistogram).

|--             |--                                           |--                               |--                                                |

| p50 latency   | Median request time                         | < 50ms for most APIs            | > 2× normal median → warning                     |

| Concurrency   | In-flight requests at a moment              | < 80% of max pool/thread limit  | Pool wait queue > 0 → investigate                |

**Tip for the interview:** At the 5 YOE level, interviewers won't ask "what is p99?" — they'll embed these metrics in harder problems: "why did our SLO burn through in 4 hours?", "how would you autoscale this?", or "walk me through this load test result graph." Know Little's Law cold (it unlocks capacity reasoning instantly), know the difference between USE and RED, have a concrete story about finding a p99 latency regression (GC pause, pool exhaustion, or thundering herd are the most common causes), and know how to instrument these metrics in code — being able to sketch a Prometheus histogram query on a whiteboard is a strong differentiator at this level.
