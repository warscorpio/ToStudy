## Section 1: Fundamentals and Configuration

**Q1. What is the slow query log, what does it capture, and why is it the starting point for database performance work?**
A: The slow query log is a database-side record of every query that exceeds a configured execution time threshold. It is the authoritative source of truth for query performance because it captures the actual execution time as measured by the database engine — not the network latency, not the application's perception of time, not an aggregate average. Each entry records what ran, how long it took, and enough context to reproduce and diagnose the query.

It is the starting point because:

```
Other observability sources and their blind spots:
  APM traces (Datadog, New Relic):  show which endpoint is slow, not which query
  Application logs:                 show request duration, not database time
  pg_stat_statements:               aggregates across all calls — hides P99 outliers
                                    and loses the exact query text for parameterized queries
  Database CPU graphs:              show that the database is under load, not why
  Error logs:                       only capture failures, not slow successes

The slow query log:
  Captures the exact query text including parameter values (not $1, $2 — the actual values)
  Records execution time, lock wait time, rows examined, rows sent
  Captures the query when it actually runs slowly — P99 behavior, not mean
  Records the user, database, and connection — identifies which application caused it
  In PostgreSQL: captures planning time separately from execution time
  In MySQL: captures bytes_sent, rows_examined, rows_sent — I/O signals
```

The mental model: slow query logs answer "which queries are slow and by how much?" — the question you must answer before you can ask "why is it slow?" (answered by EXPLAIN ANALYZE) or "how do I fix it?" (indexing, query rewriting, schema changes).

**Q2. How do you configure the slow query log in PostgreSQL and MySQL, and what threshold should you use?**
A: Configuration differs between engines. The key settings are the threshold, what gets logged, and where the output goes.

**PostgreSQL:**

```ini
# postgresql.conf

# Minimum execution time in milliseconds to qualify as "slow"
# 0 = log every statement (use only temporarily for profiling)
# 100ms = logs P95+ queries in most OLTP systems
# 1000ms = logs only egregiously slow queries (miss P95-P99 problems)
log_min_duration_statement = 100   # recommended starting point

# Log statements that are cancelled due to conflict or timeout
log_min_duration_sample = -1       # -1 = disabled; set to 0 to sample all statements

# What to include in each log entry
log_duration = off                 # already included in log_min_duration_statement output
log_statement = 'none'             # don't log ALL statements — only slow ones
log_line_prefix = '%t [%p]: [%l-1] user=%u,db=%d,app=%a,client=%h '
# %t = timestamp, %p = PID, %u = user, %d = database, %a = application_name, %h = client IP

# Include query parameters — essential for reproducing the exact query
log_min_duration_statement captures the query with parameters substituted (in most configs)
# For prepared statements, enable:
log_parameter_max_length = -1      # -1 = no limit; logs all parameter values
log_parameter_max_length_on_error = -1

# Lock wait logging
log_lock_waits = on                # log when a query waits > deadlock_timeout for a lock
deadlock_timeout = 1s              # also the threshold for lock wait logging

# Auto-explain: automatically run EXPLAIN ANALYZE for slow queries
# Add to shared_preload_libraries = 'auto_explain'
auto_explain.log_min_duration = 500     # EXPLAIN ANALYZE for queries > 500ms
auto_explain.log_analyze = true         # include actual row counts and timing
auto_explain.log_buffers = true         # include buffer hit/miss statistics
auto_explain.log_format = 'json'        # machine-readable — easier to parse
auto_explain.log_nested_statements = true  # also explain queries inside functions
```

**MySQL / Aurora MySQL:**

```ini
# my.cnf or Aurora parameter group

slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 0.1          # seconds (0.1 = 100ms)

# Log queries that don't use indexes (often the real problem)
log_queries_not_using_indexes = 1
log_throttle_queries_not_using_indexes = 60  # max 60 such entries per minute

# Log queries that examine many rows even if fast
min_examined_row_limit = 10000  # log queries examining > 10K rows regardless of time

# Include the full query (not truncated):
slow_query_log_use_global_control = all

# Performance Schema (modern MySQL — more powerful than slow log):
# performance_schema = ON   (default in MySQL 5.6+)
# Provides: events_statements_history_long — rolling buffer of last N statements
#           with full statistics, no truncation, machine-readable
```

**RDS / Aurora specific configuration:**

```sql
-- In AWS RDS, slow query log is enabled via parameter group
-- Logs are published to CloudWatch Logs for centralized analysis

-- To query slow log directly in RDS:
CALL mysql.rds_rotate_slow_log;   -- rotate to access previous log file

-- For PostgreSQL on RDS:
-- Set log_min_duration_statement in the parameter group
-- Enable log exports to CloudWatch: Logs > Exports in RDS console
-- CloudWatch Insights query for slow queries:
-- fields @timestamp, @message
-- | filter @message like /duration:/
-- | parse @message "duration: * ms" as duration_ms
-- | filter duration_ms > 1000
-- | sort duration_ms desc

-- Threshold recommendation by system type:
-- OLTP (user-facing API, <100ms SLA):    log_min_duration_statement = 50ms
-- Batch processing (minutes acceptable):  log_min_duration_statement = 5000ms
-- Analytics / reporting:                  log_min_duration_statement = 10000ms
-- Initial profiling of unknown system:    log_min_duration_statement = 0 (all queries)
--   → run for 10 minutes, then raise the threshold based on the P90 you observe
```

**Q3. What does a single slow query log entry contain, and how do you extract the signal from it?**
A: A slow query log entry contains more information than most engineers extract. Reading the full entry — not just the query text — is the difference between diagnosing a query problem and diagnosing an infrastructure problem.

**PostgreSQL slow query log entry (auto_explain with JSON):**

```
2024-01-15 02:34:17.234 IST [23847]: user=app,db=loandb,app=loans-api,client=10.0.1.45
  duration: 4823.234 ms
  plan:
  {
    "Node Type": "Limit",
    "Actual Total Time": 4823.1,
    "Actual Rows": 10,
    "Plans": [{
      "Node Type": "Sort",
      "Sort Method": "external merge",
      "Sort Space Used": 184320,         ← disk sort: 180MB spilled to disk
      "Plans": [{
        "Node Type": "Seq Scan",
        "Relation Name": "transactions",
        "Actual Rows": 9847293,
        "Rows Removed by Filter": 152707,
        "Shared Hit Blocks": 1823,
        "Shared Read Blocks": 47382      ← 47K pages read from disk
      }]
    }]
  }
  statement: SELECT id, amount, status FROM transactions
             WHERE user_id = 123456 AND status = 'pending'
             ORDER BY created_at DESC LIMIT 10;
```

```
What to extract from this entry:

1. Timestamp: 02:34:17 IST — 2:34am local time.
   Is this in a nightly batch window? Or is this unexpected for 2am?

2. Client IP: 10.0.1.45
   Which application pod/instance generated this? Cross-reference with app logs.

3. Duration: 4823ms
   This is total time including planning. Check planning_time separately if logged.

4. Plan signals:
   "Sort Method": "external merge", "Sort Space Used": 184320KB (180MB disk sort)
   → work_mem too small for this sort. Immediate fix candidate.

   "Node Type": "Seq Scan" on transactions, Actual Rows: 9,847,293
   → scanning ~10M rows for a query that returns 10 rows. Index needed.

   "Shared Read Blocks": 47382 = 47382 × 8KB = 368MB read from disk
   → heavy disk I/O. This query is a buffer cache pressure source.

5. Query text (with actual parameter values):
   user_id = 123456 — this is a specific user.
   Is this user's data unusually large? Or does this happen for all users?
   Test: run EXPLAIN ANALYZE for a different user_id. If only slow for user 123456,
   that user has outlier data volume — this is a data distribution issue, not a schema issue.
```

**MySQL slow query log entry:**

```
# Time: 2024-01-15T02:34:17.234512Z
# User@Host: app[app] @  [10.0.1.45]  Id: 28473
# Query_time: 4.823423  Lock_time: 0.000234  Rows_sent: 10  Rows_examined: 9847293
# Bytes_sent: 1247
SET timestamp=1705283657;
SELECT id, amount, status FROM transactions
WHERE user_id = 123456 AND status = 'pending'
ORDER BY created_at DESC LIMIT 10;
```

```
MySQL-specific fields:

Query_time: 4.823423s — total execution time
Lock_time: 0.000234s  — time waiting for locks (here: negligible)
  If Lock_time / Query_time > 0.1: this query is being blocked by another
  query holding a lock. The slow query may not be the problem — the blocker is.

Rows_examined: 9,847,293
Rows_sent: 10
Rows_examined / Rows_sent = 984,729 — examined 984K rows to return 10.
  This is the primary inefficiency metric in MySQL slow logs.
  Target: rows_examined / rows_sent < 100 for OLTP queries.
  > 1000: almost certainly needs an index.

Bytes_sent: 1247 — small response. The query is not a bandwidth problem.
  If Bytes_sent is very large (MBs): consider pagination or projection optimization.
```

## Section 2: Log Aggregation and Analysis Tools

**Q4. How do you aggregate slow query logs at scale, and what tools do you use for each phase of analysis?**
A: Raw slow query log files are too large to read manually at production scale. Aggregation tools reduce thousands of entries to ranked patterns — grouping queries by their normalized form (stripping literal values) and computing aggregate statistics.

**Phase 1: Log shipping and aggregation:**

```bash
# For PostgreSQL on a Linux server: ship logs to a central store

# Option A: Filebeat → Elasticsearch
# /etc/filebeat/filebeat.yml:
filebeat.inputs:
  - type: log
    paths:
      - /var/log/postgresql/postgresql-*.log
    fields:
      service: postgresql
      environment: production
    multiline:
      pattern: '^\d{4}-\d{2}-\d{2}'  # new log entry starts with a date
      negate: true
      match: after

output.elasticsearch:
  hosts: ["elasticsearch:9200"]
  index: "postgresql-slow-%{+yyyy.MM.dd}"

# Option B: CloudWatch Logs (AWS RDS/Aurora)
# Enable in RDS parameter group: log exports → PostgreSQL logs
# Query in CloudWatch Insights:
fields @timestamp, @message
| filter @message like /duration:/
| parse @message "duration: * ms  statement: *" as duration_ms, query_text
| filter duration_ms > 500
| stats count() as query_count, avg(duration_ms) as avg_ms,
         max(duration_ms) as max_ms by query_text
```

**Phase 3: Prioritization — which queries to fix first:**

```python
# Prioritization framework: rank by total time consumed, not individual query time

import pandas as pd
from dataclasses import dataclass

@dataclass
class SlowQueryPattern:
    query_fingerprint: str   # normalized query (literals replaced with ?)
    call_count:        int
    total_time_ms:     float
    mean_time_ms:      float
    p95_time_ms:       float
    max_time_ms:       float
    rows_examined:     int   # MySQL
    shared_blks_read:  int   # PostgreSQL
    temp_files:        int   # disk spill indicator

def prioritize_queries(patterns: list[SlowQueryPattern]) -> pd.DataFrame:
    df = pd.DataFrame([vars(p) for p in patterns])

    # Primary sort: total_time_ms DESC
    # This is the most impactful metric — if you optimize one query that runs 100K times,
    # even a 50% improvement saves more time than fixing a query that runs once.
    df["impact_score"] = (
        df["total_time_ms"] * 0.5 +          # total time: most important
        df["p95_time_ms"] * 0.3 +            # p95: user experience
        df["call_count"] * df["mean_time_ms"] * 0.2  # frequency × mean
    )
    df = df.sort_values("impact_score", ascending=False)

    # Categorize fix complexity:
    df["fix_category"] = df.apply(categorize_fix, axis=1)

    return df

def categorize_fix(row) -> str:
    if row["rows_examined"] / max(row["call_count"], 1) > 10000:
        return "MISSING_INDEX"       # high rows_examined per call = no index
    elif row["temp_files"] > 0:
        return "WORK_MEM_OR_REWRITE" # disk spill = increase work_mem or reduce result set
    elif row["mean_time_ms"] > 5000:
        return "QUERY_REWRITE"       # consistently slow even with indexes
    elif row["p95_time_ms"] > row["mean_time_ms"] * 10:
        return "LOCK_CONTENTION"     # high variance = sometimes blocked, sometimes fast
    else:
        return "INVESTIGATE"
```

**Q5. How do you parse and normalize slow query logs programmatically for automated analysis?**
A: Parsing raw log files into structured data is a prerequisite for automated alerting, trend analysis, and CI-based regression detection.

```python
# slow_query_parser.py — production log parser

import re
import json
from dataclasses import dataclass, field
from datetime import datetime
from typing import Optional, Generator
from pathlib import Path

# ── PostgreSQL log parser ─────────────────────────────────────────────────────

PG_SLOW_QUERY_RE = re.compile(
    r'(?P<timestamp>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d+) \w+'  # timestamp
    r'.*?duration: (?P<duration_ms>[\d.]+) ms'                         # duration
    r'(?:.*?plan:\s*(?P<plan>\{.*?\}(?=\s*\n\s*statement:|\s*$)))?'  # optional JSON plan
    r'.*?statement:\s*(?P<query>.+?)$',                                # query text
    re.DOTALL | re.MULTILINE
)

@dataclass
class SlowQueryEntry:
    timestamp:    datetime
    duration_ms:  float
    query:        str
    fingerprint:  str           # normalized query (? replaces literals)
    user:         Optional[str] = None
    database:     Optional[str] = None
    application:  Optional[str] = None
    client_ip:    Optional[str] = None
    plan:         Optional[dict] = None
    lock_time_ms: Optional[float] = None   # MySQL
    rows_examined: Optional[int] = None    # MySQL
    rows_sent:    Optional[int] = None     # MySQL
    temp_files:   int = 0

def normalize_query(query: str) -> str:
    """
    Replace literal values with ? to group queries by pattern.
    'SELECT * FROM users WHERE id = 12345' → 'SELECT * FROM users WHERE id = ?'
    """
    # Replace numeric literals
    q = re.sub(r'\b\d+\b', '?', query)
    # Replace single-quoted string literals
    q = re.sub(r"'[^']*'", "'?'", q)
    # Replace double-quoted string literals (MySQL style)
    q = re.sub(r'"[^"]*"', '"?"', q)
    # Replace IN lists: IN (1, 2, 3) → IN (?)
    q = re.sub(r'IN\s*\([^)]+\)', 'IN (?)', q, flags=re.IGNORECASE)
    # Replace hex literals
    q = re.sub(r'0x[0-9a-fA-F]+', '?', q)
    # Collapse whitespace
    q = re.sub(r'\s+', ' ', q).strip()
    return q

def parse_postgresql_log(log_path: Path) -> Generator[SlowQueryEntry, None, None]:
    """Parse a PostgreSQL slow query log file, yielding SlowQueryEntry objects."""
    current_entry_lines = []

    with open(log_path) as f:
        for line in f:
            # A new log entry starts with a timestamp
            if re.match(r'\d{4}-\d{2}-\d{2} \d{2}:\d{2}', line):
                if current_entry_lines:
                    entry = _parse_pg_entry("".join(current_entry_lines))
                    if entry:
                        yield entry
                current_entry_lines = [line]
            else:
                current_entry_lines.append(line)

    # Process the last entry
    if current_entry_lines:
        entry = _parse_pg_entry("".join(current_entry_lines))
        if entry:
            yield entry

def _parse_pg_entry(raw: str) -> Optional[SlowQueryEntry]:
    """Parse a single multi-line PostgreSQL slow query log entry."""
    # Extract duration
    duration_match = re.search(r'duration: ([\d.]+) ms', raw)
    if not duration_match:
        return None   # not a slow query entry

    duration_ms = float(duration_match.group(1))

    # Extract timestamp
    ts_match = re.match(r'(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d+)', raw)
    timestamp = datetime.strptime(ts_match.group(1), '%Y-%m-%d %H:%M:%S.%f') if ts_match else None

    # Extract context fields from log_line_prefix
    user_match    = re.search(r'user=(\w+)',   raw)
    db_match      = re.search(r'db=(\w+)',     raw)
    app_match     = re.search(r'app=([^,\s]+)', raw)
    client_match  = re.search(r'client=([\d.]+)', raw)

    # Extract query text
    stmt_match = re.search(r'statement:\s*(.+?)(?=\n\d{4}-\d{2}-\d{2}|$)', raw, re.DOTALL)
    if not stmt_match:
        return None
    query = stmt_match.group(1).strip()

    # Extract auto_explain plan (JSON)
    plan = None
    plan_match = re.search(r'plan:\s*(\[.*?\]|\{.*?\})\s*statement:', raw, re.DOTALL)
    if plan_match:
        try:
            plan = json.loads(plan_match.group(1))
        except json.JSONDecodeError:
            pass

    # Detect disk spill from plan
    temp_files = 0
    if plan:
        plan_str = json.dumps(plan)
        if 'external merge' in plan_str.lower() or 'Disk' in plan_str:
            temp_files = 1

    return SlowQueryEntry(
        timestamp=timestamp,
        duration_ms=duration_ms,
        query=query,
        fingerprint=normalize_query(query),
        user=user_match.group(1) if user_match else None,
        database=db_match.group(1) if db_match else None,
        application=app_match.group(1) if app_match else None,
        client_ip=client_match.group(1) if client_match else None,
        plan=plan,
        temp_files=temp_files,
    )

# ── MySQL slow query log parser ───────────────────────────────────────────────

MYSQL_HEADER_RE = re.compile(
    r'# Time: (?P<timestamp>[\d\-T:\.Z]+)\n'
    r'# User@Host: (?P<user>\S+)\s+@\s+\[(?P<client_ip>[\d.]*)\].*\n'
    r'# Query_time: (?P<query_time>[\d.]+)\s+'
    r'Lock_time: (?P<lock_time>[\d.]+)\s+'
    r'Rows_sent: (?P<rows_sent>\d+)\s+'
    r'Rows_examined: (?P<rows_examined>\d+)',
    re.MULTILINE
)

def parse_mysql_log(log_path: Path) -> Generator[SlowQueryEntry, None, None]:
    """Parse a MySQL slow query log file."""
    content = log_path.read_text()
    # Split on the # Time: marker
    entries = re.split(r'(?=# Time:)', content)

    for entry_text in entries:
        m = MYSQL_HEADER_RE.search(entry_text)
        if not m:
            continue

        # Query text is everything after SET timestamp=...; line
        query_match = re.search(r'SET timestamp=\d+;\n(.+?)(?=# Time:|$)', entry_text, re.DOTALL)
        if not query_match:
            continue
        query = query_match.group(1).strip()

        yield SlowQueryEntry(
            timestamp=datetime.fromisoformat(m.group('timestamp').replace('Z', '+00:00')),
            duration_ms=float(m.group('query_time')) * 1000,
            query=query,
            fingerprint=normalize_query(query),
            user=m.group('user'),
            client_ip=m.group('client_ip'),
            lock_time_ms=float(m.group('lock_time')) * 1000,
            rows_sent=int(m.group('rows_sent')),
            rows_examined=int(m.group('rows_examined')),
        )
```

## Section 3: The Optimization Workflow

**Q6. Walk through the complete optimization workflow from log entry to deployed fix.**
A: A systematic workflow prevents the common mistake of immediately writing indexes or rewriting queries without understanding the root cause. The workflow has five phases: characterize, reproduce, diagnose, fix, verify.

```
Phase 1: CHARACTERIZE
  Input: slow query log entries
  Output: prioritized list of query patterns with impact metrics

Phase 2: REPRODUCE
  Input: a specific slow query from the log (with real parameter values)
  Output: confirmed slow execution in a safe environment

Phase 3: DIAGNOSE
  Input: the reproduced slow query
  Output: identified root cause(s)

Phase 4: FIX
  Input: identified root cause
  Output: implemented solution (index, query rewrite, schema change, config change)

Phase 5: VERIFY
  Input: implemented solution
  Output: confirmed improvement with metrics
```

**Phase 1 — Characterize:**

```python
# After parsing, generate a prioritized report:

from collections import defaultdict
from statistics import mean, quantiles

def generate_report(entries: list[SlowQueryEntry]) -> list[dict]:
    # Group by normalized fingerprint
    groups = defaultdict(list)
    for entry in entries:
        groups[entry.fingerprint].append(entry)

    report = []
    for fingerprint, group_entries in groups.items():
        durations = [e.duration_ms for e in group_entries]
        rows_examined_list = [e.rows_examined for e in group_entries if e.rows_examined]

        report.append({
            "fingerprint":      fingerprint[:120],
            "example_query":    group_entries[0].query[:500],
            "call_count":       len(group_entries),
            "total_time_ms":    sum(durations),
            "mean_time_ms":     mean(durations),
            "p95_time_ms":      quantiles(durations, n=20)[18] if len(durations) > 5 else max(durations),
            "max_time_ms":      max(durations),
            "mean_rows_examined": mean(rows_examined_list) if rows_examined_list else None,
            "temp_files":       sum(e.temp_files for e in group_entries),
            "applications":     list(set(e.application for e in group_entries if e.application)),
            "time_range":       f"{min(e.timestamp for e in group_entries)} — {max(e.timestamp for e in group_entries)}",
        })

    return sorted(report, key=lambda r: r["total_time_ms"], reverse=True)
```

**Phase 2 — Reproduce:**

```sql
-- Never run EXPLAIN ANALYZE on production directly for a slow query.
-- Instead: copy the query with real parameter values to a read replica or staging.

-- Step 1: Set up the test environment to match production:
SET work_mem = '4MB';              -- match production setting (check: SHOW work_mem)
SET enable_seqscan = on;           -- start with default settings
SET random_page_cost = 1.1;        -- match production if on SSD

-- Step 2: Confirm the query is slow in this environment:
\timing on
SELECT id, amount, status FROM transactions
WHERE user_id = 123456 AND status = 'pending'
ORDER BY created_at DESC LIMIT 10;
-- Time: 4827.234 ms  ← confirmed slow

-- Step 3: Run EXPLAIN ANALYZE with full instrumentation:
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)
SELECT id, amount, status FROM transactions
WHERE user_id = 123456 AND status = 'pending'
ORDER BY created_at DESC LIMIT 10;

-- Step 4: Test with different parameter values to check for data distribution issues:
-- Is this slow for ALL user_ids or only for user 123456?
\timing on
SELECT id, amount, status FROM transactions
WHERE user_id = 789012 AND status = 'pending'
ORDER BY created_at DESC LIMIT 10;
-- Time: 0.234 ms  ← fast for a different user

-- If different parameters give drastically different performance:
-- → Data distribution issue (user 123456 has millions of transactions)
-- → Needs a different index or pagination strategy for high-volume users
-- Not just an indexing problem — the approach must scale for any user_id

-- Step 5: Check the data distribution for the parameters in the slow query:
SELECT
    user_id,
    COUNT(*) AS tx_count,
    MIN(created_at),
    MAX(created_at)
FROM transactions
WHERE user_id = 123456
GROUP BY user_id;
-- tx_count: 847,293  ← this user has 847K transactions — extreme outlier
-- Most users have <1,000 transactions

-- Step 6: Check table statistics to see if the planner knows about this:
SELECT

    most_common_freqs,

-- But most_common_vals doesn't include user 123456 — it's not common globally
-- → The planner has no idea this specific user has 847K rows
-- → The planner underestimates how many rows WHERE user_id = 123456 will return
```

**Phase 3 — Diagnose:**

```sql
-- Diagnostic decision tree:

-- Node 1: Is there a sequential scan on a large table?
--   YES → Go to Node 2
--   NO  → Look for sort spill, hash spill, or join ordering problems

-- Node 2: Is the seq scan unavoidable (high selectivity)?
--   Check: Rows Removed by Filter / Total Rows
--   If > 80% removed: low selectivity → missing index
--   If < 20% removed: high selectivity → seq scan may be correct; investigate work_mem

-- Node 3: Does an index exist for the filter columns?
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'transactions'
  AND indexdef LIKE '%user_id%';

-- Node 4: If index exists but not used — why?
-- Check for the five inhibitors (from Query Optimization file):
-- function on column, type mismatch, leading column missing, LIKE wildcard, OR

-- Node 5: Estimate vs actual row divergence
-- In the EXPLAIN output:
--   estimated rows=47, actual rows=847293
--   → 18,000x underestimate → planner chose wrong plan
--   → Either stale statistics or correlated columns without extended stats

-- Check statistics freshness:
SELECT last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables WHERE relname = 'transactions';
-- n_mod_since_analyze = 4,234,891 → 4M changes since last ANALYZE → very stale

-- Check if extended statistics would help:
-- If WHERE clause has multiple columns and estimates are wrong even after ANALYZE:
CREATE STATISTICS stats_tx_user_status ON user_id, status FROM transactions;
ANALYZE transactions;

-- Node 6: Sort spill
-- In EXPLAIN output: "Sort Method: external merge  Disk: 184320kB"
-- → work_mem too small for the sort
-- Check current work_mem:
SHOW work_mem;   -- likely '4MB' (default) or '16MB'
-- The disk sort used 180MB → need at least 200MB work_mem for this query
-- But: changing global work_mem affects all queries × all connections
-- Prefer: SET work_mem = '256MB' at the session/transaction level for this workload
-- Or: rewrite the query to sort fewer rows (LIMIT before aggregation)

-- Node 7: Lock waits
-- In MySQL slow log: Lock_time: 2.847s  Query_time: 3.123s
-- 91% of the time was waiting for a lock — the query itself is fast
-- The problem is the holder of the lock
-- Find the lock holder:
SELECT
    waiting.pid         AS waiting_pid,
    waiting.query       AS waiting_query,
    blocking.pid        AS blocking_pid,
    blocking.query      AS blocking_query,
    now() - blocking.query_start AS blocking_duration
FROM pg_stat_activity AS waiting
JOIN pg_stat_activity AS blocking ON blocking.pid = ANY(pg_blocking_pids(waiting.pid))
WHERE waiting.state = 'active'
ORDER BY blocking_duration DESC;
```

## Section 4: Specific Anti-Patterns and Their Fixes

**Q7. What are the most common slow query anti-patterns in ORM-based applications, and how do you identify each in the slow query log?**
A: ORM usage introduces specific patterns that are invisible in application code but appear clearly in slow query logs.

**Anti-pattern 1 — SELECT * (over-fetching columns):**

```sql
-- In the slow query log (MySQL):
# Rows_sent: 1  Rows_examined: 1  Query_time: 0.089
SELECT * FROM users WHERE id = 12345;

-- The query is "fast" (89ms) but:
-- SELECT * fetches all columns including: encrypted_blob (2KB), photo_thumbnail (50KB),
-- audit_json (10KB) = 62KB per row × 1000 requests/sec = 62MB/sec unnecessary data

-- Identify in slow log: query text contains 'SELECT *' and Bytes_sent is large
-- Fix: SELECT only required columns

-- In SQLAlchemy:
# BAD:
user = session.query(User).filter(User.id == user_id).first()
# Generates: SELECT users.id, users.name, users.email, users.encrypted_blob,
#             users.photo_thumbnail, users.audit_json, ... FROM users WHERE id = ?

# GOOD:
user = session.query(User.id, User.name, User.email).filter(User.id == user_id).first()
# Generates: SELECT users.id, users.name, users.email FROM users WHERE id = ?

# Or use .load_only() for partial loading:
from sqlalchemy.orm import load_only
user = session.query(User).options(load_only(User.id, User.name, User.email)).filter(...).first()
```

**Anti-pattern 2 — Pagination without keyset (OFFSET pagination):**

```sql
-- Slow query log: this query appears fast on page 1 but 30 seconds on page 100:
# Page 1:   Query_time: 0.003  Rows_examined: 20
SELECT * FROM transactions ORDER BY created_at DESC LIMIT 20 OFFSET 0;

# Page 100: Query_time: 28.234  Rows_examined: 2020
SELECT * FROM transactions ORDER BY created_at DESC LIMIT 20 OFFSET 2000;

# Page 5000: Query_time: [timeout]  Rows_examined: 100020
SELECT * FROM transactions ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
-- OFFSET 100000 forces PostgreSQL to read and discard 100K rows before returning 20

-- Identify: queries with large OFFSET values in slow log; performance degrades linearly with offset

-- Fix: keyset pagination (cursor-based)
-- Encode the last seen value as the cursor; use WHERE instead of OFFSET

-- Page 1:
SELECT id, amount, created_at FROM transactions
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- Returns rows; save last row: created_at='2024-01-15 10:23:45', id=847293

-- Page 2: (using the cursor)
SELECT id, amount, created_at FROM transactions
WHERE (created_at, id) < ('2024-01-15 10:23:45', 847293)  -- keyset condition
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- Index on (created_at DESC, id DESC) makes this O(log N) regardless of page number
-- Page 5000 is as fast as page 1

-- For this to work: composite index on (created_at DESC, id DESC)
CREATE INDEX idx_tx_keyset ON transactions (created_at DESC, id DESC);
```

**Anti-pattern 3 — Aggregate without filter (unbounded aggregation):**

```sql
-- Slow query log:
# Query_time: 45.234  Rows_examined: 50000000
SELECT user_id, SUM(amount), COUNT(*) FROM transactions GROUP BY user_id;
-- No WHERE clause — aggregates all 50M rows

-- This appears in reporting / dashboard queries that are "run against production"
-- without pagination or date range filtering

-- Identify: GROUP BY without WHERE, or WHERE with a very broad date range
-- Very high Rows_examined with no corresponding filter

-- Fix A: Add a date range filter — most dashboards show last 30/90 days
SELECT user_id, SUM(amount), COUNT(*)
FROM transactions
WHERE created_at > NOW() - INTERVAL '30 days'  -- filter to recent data
GROUP BY user_id;

-- Fix B: Pre-aggregate into a summary table (materialized via nightly batch):
CREATE TABLE transaction_summaries (
    user_id     BIGINT,
    period_date DATE,
    tx_count    INT,
    total_amount DECIMAL(15,2),
    PRIMARY KEY (user_id, period_date)
);
-- Nightly job: INSERT INTO transaction_summaries SELECT ... FROM transactions WHERE date = yesterday
-- Dashboard query: SELECT user_id, SUM(tx_count), SUM(total_amount)
--                  FROM transaction_summaries WHERE period_date > NOW() - 30
--                  GROUP BY user_id
-- Reads from the summary table (365 rows per user) instead of the raw table (millions)

-- Fix C: Materialized view (PostgreSQL):
CREATE MATERIALIZED VIEW tx_user_monthly AS
SELECT
    user_id,
    DATE_TRUNC('month', created_at) AS month,
    COUNT(*) AS tx_count,
    SUM(amount) AS total_amount
FROM transactions
GROUP BY user_id, DATE_TRUNC('month', created_at);

CREATE UNIQUE INDEX ON tx_user_monthly (user_id, month);

-- Refresh on a schedule:
REFRESH MATERIALIZED VIEW CONCURRENTLY tx_user_monthly;
-- CONCURRENTLY: doesn't lock the view for reads during refresh
```

**Anti-pattern 4 — Implicit function call on indexed column:**

```sql
-- Slow query log: this query appears hundreds of times per minute:
# Query_time: 1.234  Rows_examined: 5000000
SELECT * FROM users WHERE DATE(created_at) = '2024-01-15';

-- DATE(created_at) applies a function to an indexed column
-- The index on created_at cannot be used because the index stores the raw timestamp
-- but the query compares DATE(timestamp) = a date

-- Fix: rewrite to use a range predicate on the raw column:
-- BEFORE:
SELECT * FROM users WHERE DATE(created_at) = '2024-01-15';

-- AFTER:
SELECT * FROM users
WHERE created_at >= '2024-01-15 00:00:00'
  AND created_at <  '2024-01-16 00:00:00';
-- Now uses the index on created_at — Range Scan instead of Seq Scan

-- In ORM code (SQLAlchemy):
# BAD:
users = session.query(User).filter(func.date(User.created_at) == date(2024, 1, 15)).all()

# GOOD:
from datetime import date, datetime, timedelta
target_date = date(2024, 1, 15)
users = session.query(User).filter(
    User.created_at >= datetime.combine(target_date, datetime.min.time()),
    User.created_at < datetime.combine(target_date + timedelta(days=1), datetime.min.time())
).all()
```

**Anti-pattern 5 — Non-sargable predicates (cannot use index):**

```sql
-- Sargable = Search ARGument ABLE — a predicate that can use an index

-- Non-sargable patterns in the slow query log:
# Query_time: 8.234  Rows_examined: 10000000
SELECT * FROM loans WHERE amount / 1000 > 100;      -- function on left side
SELECT * FROM users WHERE YEAR(created_at) = 2024;  -- function on left side
SELECT * FROM accounts WHERE CAST(balance AS TEXT) LIKE '1%';  -- cast on column

-- All of these prevent index use even when indexes exist

-- Fix: move the function or transform to the right side:
-- BEFORE: WHERE amount / 1000 > 100
-- AFTER:  WHERE amount > 100 * 1000  (equivalent math, index usable)

-- BEFORE: WHERE YEAR(created_at) = 2024
-- AFTER:  WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'

-- BEFORE: WHERE CAST(balance AS TEXT) LIKE '1%'
-- AFTER: can't rewrite this directly — it means "balance starts with 1 in text form"
--        which is a business logic smell. Consider: WHERE balance >= 1000000 AND balance < 2000000
```

## Section 5: CI/CD Integration and Regression Prevention

**Q8. How do you integrate slow query detection into CI/CD to prevent regressions?**
A: Query performance should be treated like functional correctness — regressions caught in CI rather than discovered in production. Several complementary approaches are possible.

**Approach 1 — EXPLAIN plan regression testing:**

```python
# tests/performance/test_query_plans.py

import pytest
import re
import psycopg2

CONN = psycopg2.connect(os.environ["TEST_DATABASE_URL"])

class QueryPlanAssertion:
    """Assert properties of a query's execution plan without running EXPLAIN ANALYZE."""

    def __init__(self, query: str, params: tuple = ()):
        self.query  = query
        self.params = params

    def get_plan(self) -> str:
        with CONN.cursor() as cur:
            cur.execute(f"EXPLAIN {self.query}", self.params)
            return "\n".join(row[0] for row in cur.fetchall())

    def assert_no_seq_scan(self, table: str):
        plan = self.get_plan()
        assert f"Seq Scan on {table}" not in plan, (
            f"Query performs a sequential scan on {table}.\n"
            f"Plan:\n{plan}\n"
            f"Query:\n{self.query}"
        )

    def assert_uses_index(self, index_name: str):
        plan = self.get_plan()
        assert index_name in plan, (
            f"Expected query to use index '{index_name}' but plan shows:\n{plan}"
        )

    def assert_no_sort_spill(self):
        # Can only check with ANALYZE — skip in pure EXPLAIN tests
        # Use query_plan_cost as proxy: if cost > threshold, may spill
        plan = self.get_plan()
        cost_match = re.search(r'cost=[\d.]+\.\.([\d.]+)', plan)
        if cost_match:
            total_cost = float(cost_match.group(1))
            assert total_cost < 100_000, (
                f"Query cost {total_cost} is unexpectedly high — possible sort spill risk.\n"
                f"Plan:\n{plan}"
            )

# Test examples:
@pytest.mark.performance
def test_user_transaction_query_uses_index():
    """The dashboard transaction query must use an index on user_id."""
    QueryPlanAssertion(
        "SELECT id, amount, status, created_at FROM transactions "
        "WHERE user_id = %s ORDER BY created_at DESC LIMIT 10",
        params=(12345,)
    ).assert_uses_index("idx_tx_user_created")

@pytest.mark.performance
def test_loan_search_no_seq_scan():
    """The loan search query must not seq scan the loans table."""
    QueryPlanAssertion(
        "SELECT * FROM loans WHERE status = 'active' AND next_due_date < %s",
        params=("2024-12-31",)
    ).assert_no_seq_scan("loans")

@pytest.mark.performance
def test_payment_join_no_seq_scan():
    """Payment lookup by loan_id must use an index."""
    qa = QueryPlanAssertion(
        "SELECT * FROM payments WHERE loan_id = %s ORDER BY created_at DESC",
        params=(98765,)
    )
    qa.assert_no_seq_scan("payments")
    qa.assert_uses_index("idx_payments_loan_id")
```

**Approach 2 — Automated slow query detection in staging:**

```python
# scripts/slow_query_check.py
# Runs after a staging deployment; fails the pipeline if new slow queries appear

import subprocess
import json
from datetime import datetime, timedelta

def check_slow_queries_after_deployment(
    pg_conn,
    deployment_time: datetime,
    threshold_ms: int = 500,
    max_allowed: int = 0,
) -> dict:
    """
    Query pg_stat_statements for slow queries that appeared after deployment.
    Returns a report; raises if new slow patterns exceed the allowed count.
    """
    # Reset stats at deployment start — now only queries since deployment are counted
    # (This was done at deployment start)

    result = pg_conn.execute("""
        SELECT
            query,
            calls,
            mean_exec_time,
            max_exec_time,
            total_exec_time
        FROM pg_stat_statements
        WHERE mean_exec_time > %s
          AND calls > 10    -- ignore one-off queries
        ORDER BY total_exec_time DESC
        LIMIT 20
    """, (threshold_ms,)).fetchall()

    slow_queries = [
        {
            "query":          row[0][:200],
            "calls":          row[1],
            "mean_time_ms":   round(row[2], 1),
            "max_time_ms":    round(row[3], 1),
            "total_time_ms":  round(row[4], 1),
        }
        for row in result
    ]

    # Filter out known-acceptable slow queries (background jobs, migrations)
    KNOWN_SLOW_PATTERNS = [
        r"REFRESH MATERIALIZED VIEW",
        r"VACUUM",
        r"REINDEX",
    ]
    unexpected = [
        q for q in slow_queries
        if not any(re.search(p, q["query"], re.IGNORECASE) for p in KNOWN_SLOW_PATTERNS)
    ]

    if len(unexpected) > max_allowed:
        print("❌ SLOW QUERY REGRESSION DETECTED")
        for q in unexpected:
            print(f"  mean={q['mean_time_ms']}ms  calls={q['calls']}  query={q['query'][:100]}")
        raise SystemExit(1)

    print(f"✓ No unexpected slow queries (mean > {threshold_ms}ms) found after deployment")
    return {"slow_queries": unexpected, "passed": True}
```

**Approach 3 — Schema migration slow query check:**

```python
# Pre-migration check: will this migration cause slow queries on the migrated table?

def check_migration_impact(pg_conn, table_name: str, migration_sql: str):
    """
    Before running a migration, check:
    1. Does the migration add/drop an index that current slow queries depend on?
    2. Does the migration add a column that could affect existing plans?
    3. Will the migration take an exclusive lock on a large table?
    """

    # Check table size — large table + exclusive lock = production risk
    row = pg_conn.execute(
        "SELECT pg_size_pretty(pg_total_relation_size(%s)), reltuples::bigint",
        (table_name,)
    ).fetchone()
    size, row_count = row
    print(f"Table {table_name}: {size}, ~{row_count:,} rows")

    if row_count > 1_000_000:
        # Check if migration requires an exclusive lock
        exclusive_lock_ops = ['ADD COLUMN', 'DROP COLUMN', 'ALTER COLUMN', 'ADD CONSTRAINT']
        if any(op in migration_sql.upper() for op in exclusive_lock_ops):
            print(f"⚠️  WARNING: Migration on {table_name} ({row_count:,} rows) takes exclusive lock")
            print(f"   Consider: ADD COLUMN DEFAULT NULL (no lock in PG 11+)")
            print(f"   Or: use pg_repack / online schema change tool")

    # Check if migration drops an index used by top queries
    if 'DROP INDEX' in migration_sql.upper():
        dropped_index = re.search(r'DROP INDEX (?:CONCURRENTLY )?(\w+)', migration_sql, re.IGNORECASE)
        if dropped_index:
            index_name = dropped_index.group(1)
            usage = pg_conn.execute("""
                SELECT indexname, idx_scan, idx_tup_read
                FROM pg_stat_user_indexes
                WHERE indexname = %s
            """, (index_name,)).fetchone()

            if usage and usage[1] > 0:
                print(f"⚠️  WARNING: Dropping index '{index_name}' which has been used {usage[1]:,} times")
                print(f"   Queries using this index will revert to sequential scans")
```

## Section 6: Advanced Patterns

**Q9. How do you analyze slow queries in a multi-tenant fintech application where a single query is slow only for certain tenants?**
A: Multi-tenant slowness is a data distribution problem — the query is correctly written and correctly indexed, but certain tenants have outlier data volumes that make the generic solution inadequate.

```sql
-- Symptom in slow query log:
-- The same query fingerprint appears with wildly different execution times:
-- user_id=12345  Query_time: 0.003s   Rows_examined: 15
-- user_id=67890  Query_time: 28.234s  Rows_examined: 847293

-- Step 1: Identify which tenants (users, accounts) are outliers

SELECT
    user_id,
    COUNT(*) AS tx_count,
    NTILE(100) OVER (ORDER BY COUNT(*)) AS percentile
FROM transactions
GROUP BY user_id
ORDER BY tx_count DESC
LIMIT 20;

-- Result:
-- user_id=67890  tx_count=847,293  percentile=100  ← top 1% in volume
-- user_id=12345  tx_count=15       percentile=1

-- The P99 user has 56,000x more rows than the P1 user.
-- A single index strategy cannot efficiently serve both.
```

```sql
-- Step 2: Detect if the planner makes wrong decisions for high-volume tenants

-- The planner estimates rows using global statistics, not per-user statistics.
-- pg_stats.most_common_vals tracks the most common values globally.
-- A high-volume user (user_id=67890) appearing with unusual frequency
-- may have incorrect row estimates:

SELECT attname, most_common_vals, most_common_freqs, n_distinct
FROM pg_stats
WHERE tablename = 'transactions' AND attname = 'user_id';

-- If user_id=67890 is NOT in most_common_vals (because globally it's not common):
-- → The planner uses n_distinct to estimate rows uniformly
-- → Estimate: total_rows / n_distinct = 10M / 50K unique users = 200 rows per user
-- → Reality: 847,293 rows for user 67890 → planner chose wrong plan

-- Fix A: Increase statistics target for user_id
ALTER TABLE transactions ALTER COLUMN user_id SET STATISTICS 500;
-- Default is 100; 500 captures more most_common_vals → planner learns about high-volume users
ANALYZE transactions;

-- Fix B: Partition the table by user_id range or hash
-- For extreme outliers, partitioning isolates their data:
CREATE TABLE transactions_p0 PARTITION OF transactions
    FOR VALUES IN (67890, 23456, 89012);  -- high-volume tenants on their own partition

-- The planner can now use per-partition statistics — it knows partition p0 has 847K rows
-- and can choose an appropriate plan without global statistics confusion

-- Fix C: Per-tenant summary tables for aggregate queries
-- High-volume tenants need aggregate queries answered from a pre-built summary
CREATE TABLE user_transaction_summary (
    user_id     BIGINT PRIMARY KEY,
    tx_count    BIGINT,
    total_amount DECIMAL(20,2),
    last_tx_at  TIMESTAMPTZ,
    updated_at  TIMESTAMPTZ DEFAULT NOW()
);
-- Maintain via triggers or scheduled jobs
-- The dashboard query for any user: O(1) read from summary, not O(N) scan
```

**Q10. How do you handle slow queries caused by connection pool exhaustion, and how do you distinguish it from slow query execution?**
A: Connection pool exhaustion produces symptoms that look like slow queries in application metrics but do not appear in the database slow query log. Understanding the difference prevents chasing the wrong root cause.

```python
# Symptom pattern that causes confusion:
# - Application metrics show P99 database query time = 8 seconds
# - Database slow query log shows no queries > 200ms
# - pg_stat_statements shows mean_exec_time = 50ms for the suspected query
# - The database itself is healthy; CPU < 20%, no lock contention
#
# Root cause: the 8 seconds includes 7.8 seconds of connection pool wait time
# The query itself is fast (50ms); the application waits 7.8s for a free connection

# Confirm with connection pool metrics:
# PgBouncer stats:
SHOW POOLS;
-- database  user     cl_active  cl_waiting  sv_active  sv_idle  sv_used  maxwait
-- loandb    app      20         47          20         0        0        7834
-- cl_waiting=47: 47 clients waiting for a connection
-- maxwait=7834ms: worst-case wait time = 7.8 seconds → matches the symptom

# SQLAlchemy connection pool stats:
from sqlalchemy import event
from sqlalchemy.pool import Pool

@event.listens_for(Pool, "checkout")
def on_checkout(dbapi_conn, connection_record, connection_proxy):
    # Log when a connection is checked out of the pool
    pass

@event.listens_for(Pool, "checkin")
def on_checkin(dbapi_conn, connection_record):
    pass

# Monitor pool_size, overflow, timeout:
engine = create_engine(
    DATABASE_URL,
    pool_size=20,        # base connections
    max_overflow=10,     # additional connections beyond pool_size
    pool_timeout=5,      # seconds to wait for a connection before raising
    pool_pre_ping=True,  # verify connections are alive before use
)
```

```sql
-- Database-side connection diagnostics:

-- Active vs idle connections:
SELECT
    state,
    COUNT(*) AS connection_count,
    MAX(EXTRACT(EPOCH FROM (NOW() - state_change))) AS max_time_in_state_s,
    array_agg(application_name ORDER BY state_change) AS applications
FROM pg_stat_activity
WHERE datname = 'loandb'
GROUP BY state;
-- state       count   max_time_in_state_s
-- active      20      45.2                ← 20 running queries (some very long?)
-- idle        3       120.5               ← idle connections (wasted)
-- idle in tx  8       230.1               ← DANGER: idle in transaction holds locks

-- "idle in transaction" is a common cause of connection pool exhaustion:
-- Application opened a transaction, ran a query, then crashed or hung
-- The transaction holds locks and a connection indefinitely
-- Other connections pile up waiting

-- Find idle-in-transaction connections:
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    EXTRACT(EPOCH FROM (NOW() - state_change)) AS idle_in_tx_seconds,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND state_change < NOW() - INTERVAL '30 seconds'
ORDER BY idle_in_tx_seconds DESC;

-- Fix: terminate long-running idle-in-transaction connections:
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND state_change < NOW() - INTERVAL '5 minutes';

-- Prevention: set idle_in_transaction_session_timeout:
-- postgresql.conf:
-- idle_in_transaction_session_timeout = '30s'
-- Automatically terminates any connection idle in a transaction for > 30s
-- This is essential for production fintech applications

-- Also set:
-- statement_timeout = '30s'  -- kills queries running longer than 30s
-- lock_timeout = '5s'        -- kills queries waiting on locks longer than 5s
```

## Section 7: Scenario-Based Questions

**Q11. Scenario: "Your on-call alert fires: P99 API latency is 12 seconds. The SLA is 500ms. How do you find and fix the database bottleneck within 30 minutes?"**
A: This is a timed incident response. Every step must produce either the answer or direct the next step. Avoid wide searches — each action should narrow the problem space.

```bash
# T+0: Alert fires. P99 = 12s. SLA = 500ms.

# T+1: Check if it's the database or the application:
# Dashboard: is database CPU/connections elevated?
# If database CPU is 100%: database is the bottleneck
# If database CPU is 10%: database is not the bottleneck (check app, network, downstream)

# T+2: Find the expensive query RIGHT NOW (not historical):
psql -h db-primary.internal -d loandb -U admin -c "
SELECT
    pid,
    now() - pg_stat_activity.query_start AS duration,
    query,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE state != 'idle'
  AND query_start < NOW() - INTERVAL '1 second'
ORDER BY duration DESC
LIMIT 10;
"

# Typical output during an incident:
# pid=23847  duration=00:00:11.234  state=active  wait_event_type=NULL
#   query=SELECT * FROM transactions WHERE user_id=67890 ORDER BY created_at DESC LIMIT 10
# pid=23901  duration=00:00:08.876  state=active  wait_event_type=Lock  wait_event=relation
#   query=UPDATE loans SET status='active' WHERE id=...
# pid=23834  duration=00:00:11.890  state=active  wait_event_type=Lock  wait_event=relation
#   query=SELECT * FROM loans WHERE user_id=12345
# ...
# 18 more active queries, 11 waiting for locks

# T+4: Identify the root cause from pg_stat_activity:
# wait_event_type=Lock for 18 queries = lock contention is the primary problem
# One query (pid=23901) is actively running (no wait_event) and blocking 18 others

# Find the blocking chain:
psql -c "
SELECT
    blocking.pid         AS blocking_pid,
    blocking.query       AS blocking_query,
    blocking.query_start AS blocking_start,
    COUNT(waiting.pid)   AS waiters
FROM pg_stat_activity AS waiting
JOIN pg_stat_activity AS blocking ON blocking.pid = ANY(pg_blocking_pids(waiting.pid))
WHERE waiting.state = 'active'
GROUP BY blocking.pid, blocking.query, blocking.query_start
ORDER BY COUNT(waiting.pid) DESC;
"
# blocking_pid=23901  waiters=18
# blocking_query=UPDATE loans SET status='active' WHERE id IN (SELECT id FROM loans WHERE ...)
# blocking_start=00:00:12 ago

# T+6: The UPDATE is running for 12 seconds and blocking 18 queries.
# Decide: kill it or wait?
# Check: is this a legitimate slow UPDATE or a runaway query?
psql -c "EXPLAIN (ANALYZE, BUFFERS) UPDATE loans SET status='active' WHERE id IN (...);"
# This would have to wait for the lock — check pg_stat_statements instead
psql -c "
SELECT mean_exec_time, calls FROM pg_stat_statements
WHERE query LIKE '%UPDATE loans SET status%';
"
# mean_exec_time=45ms, calls=8392
# This UPDATE normally takes 45ms — the 12-second execution is abnormal
# → The UPDATE itself hit a slow path (likely: missing index, or is waiting on something upstream)

# T+8: Terminate the blocking query:
psql -c "SELECT pg_cancel_backend(23901);"
# pg_cancel_backend: sends SIGINT — the query can be re-run safely
# Use pg_terminate_backend only if pg_cancel_backend doesn't work

# T+9: The 18 waiting queries unblock and complete normally within their SLA.
# P99 drops from 12s back to normal.

# T+10: Post-incident — understand why the UPDATE was slow:
# Check the slow query log for the UPDATE around the incident time
grep "UPDATE loans SET status" /var/log/postgresql/postgresql-*.log | grep "duration: [0-9][0-9][0-9][0-9]"
# duration: 12847.234 ms
# → The UPDATE was slow because it was itself waiting for a lock from a LONG TRANSACTION
# The chain: Long transaction → blocked UPDATE → 18 blocked SELECTs

# Root cause: an idle-in-transaction connection held a lock on the loans table
# The UPDATE waited for that lock, and 18 SELECTs waited for the UPDATE's lock
# Fix: idle_in_transaction_session_timeout = '30s' in postgresql.conf
```

**Q12. Scenario: "Your team is deploying a new feature that adds a WHERE clause filter on a column that has no index. The table has 50M rows. How do you handle this before and after deployment?"**
A:

```sql
-- BEFORE DEPLOYMENT:

-- Step 1: Estimate the query performance without the index
-- Run EXPLAIN (not ANALYZE) on the new query against production to see the plan:
EXPLAIN SELECT * FROM transactions WHERE merchant_category = 'food_delivery'
ORDER BY created_at DESC LIMIT 50;
-- Expected: Seq Scan on transactions (cost=0.00..1284723.00 rows=... width=...)
-- At 50M rows × ~200 bytes/row = 10GB sequential scan → ~10-30 seconds

-- Step 2: Check how selective the new filter is:
SELECT
    merchant_category,
    COUNT(*) AS row_count,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS pct
FROM transactions
GROUP BY merchant_category
ORDER BY count DESC;
-- merchant_category='food_delivery': 3,200,000 rows = 6.4% of table
-- 6.4% selectivity → index scan is beneficial (below the ~10% threshold)

-- Step 3: Create the index BEFORE deploying the application code
-- Use CONCURRENTLY to avoid locking the table during index build:
CREATE INDEX CONCURRENTLY idx_tx_merchant_category
ON transactions (merchant_category, created_at DESC)
INCLUDE (id, amount, status);
-- Estimated build time: 50M rows at ~500K rows/s ≈ 100 seconds
-- Table remains fully available during the build (CONCURRENTLY)
-- Monitor progress:
SELECT
    phase,
    blocks_done,
    blocks_total,
    ROUND(100.0 * blocks_done / NULLIF(blocks_total, 0), 1) AS pct_done,
    tuples_done,
    tuples_total
FROM pg_stat_progress_create_index
WHERE relid = 'transactions'::regclass;

-- Step 4: Verify the index before deployment:
EXPLAIN SELECT * FROM transactions WHERE merchant_category = 'food_delivery'
ORDER BY created_at DESC LIMIT 50;
-- Expected after index: Index Only Scan using idx_tx_merchant_category
-- If still showing Seq Scan: run ANALYZE transactions to update statistics

-- Step 5: Deploy the application code (feature goes live pointing to the indexed column)

-- AFTER DEPLOYMENT:

-- Monitor for the first 30 minutes:
-- 1. Does the new query use the index?
SELECT indexname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
WHERE indexname = 'idx_tx_merchant_category';
-- idx_scan should start incrementing within minutes of deployment

-- 2. Is the query in the slow log?
tail -f /var/log/postgresql/postgresql.log | grep "merchant_category"
-- Should see: duration: 2.345 ms (fast, using index)
-- If you see: duration: 8234.234 ms (slow) → index not being used → investigate

-- 3. Check pg_stat_statements for the new query pattern:
SELECT calls, mean_exec_time, max_exec_time
FROM pg_stat_statements
WHERE query LIKE '%merchant_category%';
-- After 15 minutes: calls should be growing, mean_exec_time should be low

-- If performance is unexpectedly poor after deployment:
-- Step A: Check if index is INVALID (build failed)
SELECT indexname, indisvalid
FROM pg_indexes
JOIN pg_index ON indexrelid = (
    SELECT oid FROM pg_class WHERE relname = indexname
)
WHERE tablename = 'transactions';
-- indisvalid = false → index build failed → must DROP and recreate

-- Step B: Force index use to verify it works (testing only):
SET enable_seqscan = OFF;
EXPLAIN ANALYZE SELECT * FROM transactions
WHERE merchant_category = 'food_delivery' ORDER BY created_at DESC LIMIT 50;
-- If this is fast: the index works but the planner chose not to use it
-- → run ANALYZE transactions to update statistics
-- → check if random_page_cost is set correctly for SSD storage
```

## Quick Reference: Optimization Workflow Checklist

```
STEP 1: CONFIGURE LOGGING
[ ] log_min_duration_statement = 100ms (PostgreSQL) / long_query_time = 0.1 (MySQL)
[ ] auto_explain enabled with log_analyze=true, log_buffers=true (PostgreSQL)
[ ] log_lock_waits = on (PostgreSQL)
[ ] idle_in_transaction_session_timeout = 30s (PostgreSQL)
[ ] statement_timeout set appropriately for the workload
[ ] Logs shipped to centralized storage (CloudWatch, Elasticsearch)

STEP 2: AGGREGATE AND PRIORITIZE
[ ] Run pt-query-digest (MySQL) or pgBadger (PostgreSQL) on log files
[ ] Sort by total_exec_time DESC — not mean time — for maximum impact
[ ] Identify: call_count, mean_time, p95_time, rows_examined/sent ratio
[ ] Flag: queries with temp_files > 0 (disk spill), lock_time high
[ ] Compute rows_examined / rows_sent ratio — > 1000 = missing index

STEP 3: REPRODUCE
[ ] Copy slow query with REAL parameter values from the log
[ ] Run on read replica or staging — never EXPLAIN ANALYZE on production writes
[ ] Confirm slowness is reproducible (not a one-time event)
[ ] Test with multiple parameter values — is it slow for all values or just one?
[ ] Check data distribution for the slow parameter values

STEP 4: DIAGNOSE
[ ] Run EXPLAIN (ANALYZE, BUFFERS) — read bottom-up
[ ] Find node with highest actual time — that's the bottleneck
[ ] Check estimated vs actual rows — large gap = stale statistics
[ ] Check Buffers: shared read — high = disk-bound, index opportunity
[ ] Check Sort Method — "external merge Disk:" = work_mem too small
[ ] Check HashAggregate Batches > 1 = disk spill
[ ] Check Lock_time (MySQL) / wait_event_type=Lock (PostgreSQL) = lock contention
[ ] Compare: is it slow for this specific parameter or universally?

STEP 5: FIX (in order of preference)
[ ] Missing index → CREATE INDEX CONCURRENTLY (no table lock)
[ ] Stale statistics → ANALYZE table (immediate, no lock)
[ ] Work_mem spill → SET work_mem at session level, or rewrite query
[ ] N+1 query → JOIN or batch fetch
[ ] OFFSET pagination → keyset (cursor) pagination
[ ] Function on column → functional index or rewrite predicate
[ ] Type mismatch → fix literal type to match column type
[ ] Lock contention → optimize blocker, or idle_in_transaction_session_timeout
[ ] Idle-in-transaction → pg_terminate_backend, set session timeout

STEP 6: VERIFY
[ ] EXPLAIN shows improved plan (Index Scan vs Seq Scan)
[ ] pg_stat_user_indexes: idx_scan > 0 within 15 minutes of deployment
[ ] pg_stat_statements: mean_exec_time reduced by expected factor
[ ] Slow query log: no entries for this pattern at the configured threshold
[ ] System metrics: database CPU/IO reduced

STEP 7: PREVENT RECURRENCE
[ ] Add EXPLAIN plan assertion to CI test suite
[ ] Add pg_stat_statements regression check to deployment pipeline
[ ] Set autovacuum_analyze_scale_factor = 0.01 for large high-write tables
[ ] Create index BEFORE deploying feature code that requires it
[ ] Document the fix and root cause in the incident/PR for future reference
```

The two things interviewers probe hardest: the prioritization framework (Q4 — sort by total_exec_time, not mean time; a 2ms query called 10M times beats a 10s query called once in terms of impact) and the reproduce-before-you-fix discipline (Q6 Phase 2 — testing with multiple parameter values catches the multi-tenant data distribution case before you write the wrong fix). The anti-pattern list (Q7) signals production experience — especially the OFFSET pagination problem (most candidates know it intellectually but haven't debugged it from a slow log entry) and the sargable predicate patterns. The incident response scenario (Q11) is the most common senior-level close — show that you go to pg_stat_activity first (what is slow right now), not the slow log (what was slow historically), and that you distinguish lock contention from query execution time before choosing an action.
