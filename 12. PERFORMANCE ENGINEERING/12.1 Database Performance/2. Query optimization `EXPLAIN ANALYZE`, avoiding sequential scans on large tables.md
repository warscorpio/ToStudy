---

## Section 1: Fundamentals and the Query Planner

**Q1. What does the PostgreSQL query planner do, and what information does it use to make decisions?**
A: The query planner (also called the query optimizer) transforms a parsed SQL query into an execution plan — a tree of physical operations that the executor carries out. It does not execute the query; it decides *how* to execute it by evaluating alternative plans and estimating their costs. The planner's goal is to find the plan with the lowest estimated total cost, where cost is a dimensionless unit representing relative I/O and CPU effort.

The planner relies on three categories of information to build estimates:

**Table statistics** — maintained by `ANALYZE` (runs automatically via autovacuum):
```sql
-- Statistics PostgreSQL collects per column:
SELECT
    tablename,
    attname          AS column_name,
    n_distinct,      -- estimated distinct values (-1 = all unique, 0.5 = 50% of rows)
    correlation,     -- physical sort order correlation (1.0 = perfectly sorted, 0 = random)
    null_frac,       -- fraction of NULLs
    avg_width,       -- average byte width of the column value
    most_common_vals,  -- most frequent values (array)
    most_common_freqs  -- frequency of each most_common_val
FROM pg_stats
WHERE tablename = 'transactions' AND attname = 'status';

-- Example output:
-- n_distinct = 5 (five distinct statuses)
-- most_common_vals = {completed, pending, failed, cancelled, refunded}
-- most_common_freqs = {0.72, 0.18, 0.06, 0.03, 0.01}
-- The planner uses this to estimate: WHERE status = 'completed' → 72% of rows
```

**Table-level statistics**:
```sql
SELECT
    relname,
    reltuples,   -- estimated row count (updated by ANALYZE)
    relpages     -- estimated page count (8KB pages)
FROM pg_class
WHERE relname = 'transactions';
-- If reltuples = 10,000,000 and relpages = 50,000:
-- average row width = 50,000 × 8192 / 10,000,000 ≈ 41 bytes
```

**Planner cost parameters** — configurable constants that tune the cost model:
```sql
-- Key parameters:
seq_page_cost    = 1.0    -- cost of reading one sequential page
random_page_cost = 4.0    -- cost of reading one random page (default; use 1.1 for SSDs)
cpu_tuple_cost   = 0.01   -- cost of processing one row
cpu_index_tuple_cost = 0.005  -- cost of processing one index entry
cpu_operator_cost    = 0.0025 -- cost of evaluating one operator

-- random_page_cost = 4.0 assumes spinning disks.
-- On SSD-backed RDS or local NVMe, set to 1.1:
ALTER SYSTEM SET random_page_cost = 1.1;
SELECT pg_reload_conf();
-- This makes the planner favor index scans more aggressively — correct for cloud databases.
```

The planner considers: which indexes exist, how selective each predicate is, the join order for multi-table queries (up to `join_collapse_limit`, default 8), and whether to use parallel query execution. When the planner's estimates are far off, its plan choices are poor — this is the root cause of most query performance problems.

**Q2. What is the difference between `EXPLAIN`, `EXPLAIN ANALYZE`, and `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, and when do you use each?**
A: Each variant gives progressively more information, with progressively more cost (since `ANALYZE` actually executes the query).

**`EXPLAIN`** — shows the plan without executing:
```sql
EXPLAIN SELECT * FROM transactions WHERE user_id = 123 AND status = 'pending';

-- Output:
Seq Scan on transactions  (cost=0.00..285432.00 rows=47 width=156)
  Filter: ((user_id = 123) AND (status = 'pending'::text))

-- cost=start..total:
--   start cost: cost before first row can be returned (0.00 for seq scan)
--   total cost: cost to return ALL rows (285432.00 — very high → this is slow)
-- rows=47: planner estimates 47 rows will match
-- width=156: estimated average row width in bytes
```

Use `EXPLAIN` for: quick plan inspection without touching production data, checking if the planner would use an index before creating it, understanding join order decisions.

**`EXPLAIN ANALYZE`** — executes the query and shows actual vs estimated:
```sql
EXPLAIN ANALYZE SELECT * FROM transactions WHERE user_id = 123 AND status = 'pending';

-- Output:
Seq Scan on transactions  (cost=0.00..285432.00 rows=47 width=156)
                          (actual time=0.089..3847.223 rows=143 loops=1)
  Filter: ((user_id = 123) AND (status = 'pending'::text))
  Rows Removed by Filter: 9999857

Planning Time: 0.412 ms
Execution Time: 3848.109 ms
```

The `actual time=start..end` shows real milliseconds. `rows=143` vs estimated `rows=47` reveals a statistics mismatch — the planner underestimated by 3x. `Rows Removed by Filter: 9999857` shows the scan touched ~10M rows to return 143 — the classic sequential scan on a large table.

**`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`** — maximum detail, machine-readable:
```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT * FROM transactions WHERE user_id = 123 AND status = 'pending';

-- BUFFERS output adds:
-- Buffers: shared hit=1240 read=47832 written=0
--   shared hit:  pages served from PostgreSQL's shared_buffers (RAM) — cheap
--   shared read: pages read from disk (or OS page cache) — expensive
--   written:     dirty pages written during query — usually 0 for SELECT
-- A high read count = heavy disk I/O = index or caching opportunity

-- FORMAT JSON: machine-readable, useful for automated plan analysis tools
-- (pgMustard, explain.dalibo.com, pev2)
```

**`EXPLAIN (ANALYZE, BUFFERS, VERBOSE)`** — per-node detail:
```sql
-- VERBOSE adds:
-- Output: column list the node produces
-- Worker n: Actual Rows / Loops for parallel workers
-- Shows intermediate column computations — useful for spotting unnecessary projections
```

Rule of thumb:
- Development / staging: always `EXPLAIN (ANALYZE, BUFFERS)` — you want real numbers.
- Production slow query: copy the query, run `EXPLAIN (ANALYZE, BUFFERS)` in a read replica or off-peak. Never `EXPLAIN ANALYZE` a mutating query in production without `BEGIN`/`ROLLBACK`.
- CI performance regression tests: capture `EXPLAIN` output (no execute) and alert on plan changes.

**Q3. How do you read an `EXPLAIN ANALYZE` output tree, and what are the key numbers to look at first?**
A: A query plan is a tree read from the innermost (indented) node up to the outermost. Each node does one operation and feeds its output to its parent. Reading order: **bottom-up** (inner nodes execute first, outer nodes consume their output).

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.name, SUM(t.amount)
FROM users u
JOIN transactions t ON t.user_id = u.id
WHERE t.created_at > '2024-01-01'
  AND u.country = 'IN'
GROUP BY u.name
ORDER BY SUM(t.amount) DESC
LIMIT 10;
```

```
Limit  (cost=92847.23..92847.25 rows=10 width=48)
       (actual time=1823.44..1823.45 rows=10 loops=1)
  ->  Sort  (cost=92847.23..92997.23 rows=60000 width=48)
            (actual time=1823.44..1823.44 rows=10 loops=1)
        Sort Key: (sum(t.amount)) DESC
        Sort Method: top-N heapsort  Memory: 25kB
        ->  HashAggregate  (cost=87847.23..88447.23 rows=60000 width=48)
                           (actual time=1821.23..1822.89 rows=62341 loops=1)
              Group Key: u.name
              Batches: 1  Memory Usage: 8209kB
              ->  Hash Join  (cost=18234.00..82347.23 rows=300000 width=44)
                             (actual time=234.12..1745.67 rows=1847293 loops=1)
                    Hash Cond: (t.user_id = u.id)
                    Buffers: shared hit=2341 read=18947
                    ->  Seq Scan on transactions t
                              (cost=0.00..58234.00 rows=1847293 width=20)
                              (actual time=0.034..823.45 rows=1847293 loops=1)
                          Filter: (created_at > '2024-01-01'::date)
                          Rows Removed by Filter: 2152707
                          Buffers: shared hit=1823 read=14823
                    ->  Hash  (cost=14234.00..14234.00 rows=320000 width=28)
                              (actual time=233.89..233.89 rows=318472 loops=1)
                          Buckets: 524288  Batches: 1  Memory: 18368kB
                          ->  Seq Scan on users u
                                    (cost=0.00..14234.00 rows=320000 width=28)
                                    (actual time=0.021..143.23 rows=320000 loops=1)
                                Filter: (country = 'IN'::text)
                                Rows Removed by Filter: 80000

Planning Time: 8.234 ms
Execution Time: 1823.892 ms
```

**Reading the plan — what to look at first:**

```
1. Total Execution Time (bottom line): 1823ms — is this acceptable?

2. Find the most expensive node (highest actual time):
   The Hash Join: actual time=234..1745ms — 1511ms spent here
   That's 83% of total execution time → this is where to focus.

3. Estimate vs actual rows — planner accuracy:
   Hash Join: estimated 300,000 rows, actual 1,847,293 — 6x underestimate
   This is why the plan may be suboptimal — bad statistics.

4. Buffers: shared read=18947 — ~18,947 × 8KB = 147MB read from disk
   shared hit=2341 — only 2341 pages served from RAM
   Low cache hit ratio → heavy disk I/O → index could help

5. Rows Removed by Filter (seq scans):
   transactions: 2,152,707 rows removed — read 4M rows to get 1.8M
   Not terrible (created_at filter is 46% selective) but an index would help

6. Sort Method: top-N heapsort Memory: 25kB
   Good — small sort, in-memory, cheap

7. HashAggregate Batches: 1 Memory: 8209kB
   Batches: 1 means it fit in memory — Batches > 1 means disk spill (bad)
```

## Section 2: Sequential Scans — When They Are Correct and When They Are Not

**Q4. When is a sequential scan the correct choice, and when is it a symptom of a problem?**
A: Sequential scans are not inherently bad. The planner chooses a sequential scan when it estimates that reading the entire table is cheaper than the random I/O cost of following index pointers. Understanding when the planner is right vs wrong is the key diagnostic skill.

**Sequential scans are correct when:**

```sql
-- Case 1: High selectivity filter — a large fraction of rows match
-- Table: 100,000 rows. Filter matches 80,000 rows.
-- Index scan would do 80,000 random I/Os — far more expensive than reading 100,000 rows sequentially.
EXPLAIN SELECT * FROM small_lookup_table WHERE status != 'archived';
-- Seq Scan (cost=0.00..2341.00 rows=94000 ...) ← correct choice

-- Case 2: The table is small enough to fit in shared_buffers
-- A table with 500 rows is always faster to seq scan regardless of indexes
-- The planner correctly ignores indexes for small tables

-- Case 3: Aggregate over all rows — full scan is unavoidable
SELECT COUNT(*), AVG(amount) FROM transactions;
-- This must touch every row — a seq scan is the only option

-- The threshold: rough rule of thumb is ~5-10% selectivity
-- Below 5% rows returned → index scan wins
-- Above 10% rows returned → sequential scan often wins
-- Between 5-10% → depends on table size, caching, random_page_cost setting
```

**Sequential scans are a problem when:**

```sql
-- Case 1: Low selectivity filter on a large table with no index
EXPLAIN ANALYZE
SELECT * FROM transactions WHERE user_id = 12345;
-- Seq Scan (rows=47 actual time=0..4823ms) Rows Removed=9999953
-- 10M rows scanned to return 47 — this needs an index on user_id

-- Case 2: The planner uses a seq scan because statistics are stale
-- After bulk loading 5M new rows, ANALYZE has not run yet
-- The planner thinks the table has 100K rows → estimates seq scan is cheap
-- Reality: 5.1M rows → seq scan is very expensive
-- Fix: run ANALYZE manually after bulk loads

-- Case 3: The planner uses a seq scan because an index exists but is not usable
-- These are the "hidden" sequential scan causes — covered in Q5

-- Case 4: enable_seqscan is the only way to get an index scan
-- (this almost always means a different problem, not a config fix)
SET enable_seqscan = OFF;   -- NEVER do this in production
-- If disabling seq scans changes the plan: fix the statistics or the query, not the planner
```

**Q5. What are the five ways a query can prevent index usage and force a sequential scan?**
A: These are the most common "why isn't my index being used?" patterns, each with a specific fix.

**1. Function applied to the indexed column:**
```sql
-- Table: users, index on email
-- WRONG — function on the column prevents index use:
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';
-- Seq Scan: the index stores email values; LOWER(email) is not indexed

-- FIX A: functional index
CREATE INDEX idx_users_email_lower ON users (LOWER(email));
-- Now LOWER(email) is indexed → index scan

-- FIX B: normalize at write time — store emails already lowercased
-- FIX C: use ILIKE with a trigram index (for text search)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_users_email_trgm ON users USING gin (email gin_trgm_ops);
SELECT * FROM users WHERE email ILIKE 'alice@example.com';
```

**2. Implicit type cast mismatch:**
```sql
-- Table: transactions, id is BIGINT, index on id
-- WRONG — passing a string (varchar) when column is bigint:
SELECT * FROM transactions WHERE id = '12345';   -- '12345' is text
-- PostgreSQL must cast id::text for comparison → cannot use the index as-is
-- (In some versions this is resolved; in others it forces a cast and kills the index)

-- More dangerous case: column is varchar, but comparison value is integer
CREATE TABLE accounts (account_no VARCHAR(20));
CREATE INDEX idx_account_no ON accounts (account_no);
SELECT * FROM accounts WHERE account_no = 1234567890;   -- integer literal
-- account_no must be cast to integer → Seq Scan

-- FIX: match the type exactly
SELECT * FROM accounts WHERE account_no = '1234567890';  -- string literal → Index Scan

-- Diagnosis: look for Filter: ((column)::text = 'value') in EXPLAIN output
-- The cast in the Filter line means the index is not usable
```

**3. Leading column of a composite index is not in the predicate:**
```sql
-- Composite index: CREATE INDEX idx_tx ON transactions (user_id, created_at, status)
-- This index can be used for:
--   WHERE user_id = X                          ✓ leading column present
--   WHERE user_id = X AND created_at > Y       ✓ leading + second column
--   WHERE user_id = X AND status = 'pending'   ✓ leading + third (skips created_at OK)

-- This index CANNOT be used efficiently for:
--   WHERE created_at > '2024-01-01'            ✗ leading column missing → Seq Scan
--   WHERE status = 'pending'                   ✗ leading column missing → Seq Scan

-- Fix: create a separate index for queries that don't filter on user_id
CREATE INDEX idx_tx_created_at ON transactions (created_at) WHERE status = 'pending';
-- Partial index: only covers pending transactions — smaller, faster
```

**4. LIKE with a leading wildcard:**
```sql
-- Index on transactions(description)
SELECT * FROM transactions WHERE description LIKE '%payment%';
-- Seq Scan: LIKE with a leading % cannot use a B-tree index
-- The B-tree stores values sorted alphabetically — a leading wildcard means
-- the matching value could start with anything → must scan all entries

-- FIX for contains/suffix search: trigram index
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_tx_desc_trgm ON transactions USING gin (description gin_trgm_ops);
SELECT * FROM transactions WHERE description LIKE '%payment%';
-- GIN index can satisfy LIKE '%payment%' → Index Scan

-- Prefix search (no leading wildcard) DOES use a B-tree index:
SELECT * FROM transactions WHERE description LIKE 'payment%';  -- ✓ uses B-tree index
```

**5. OR across different columns:**
```sql
-- Indexes exist on both user_id and merchant_id separately
SELECT * FROM transactions WHERE user_id = 123 OR merchant_id = 456;
-- May do Seq Scan — OR across different indexed columns is hard to optimize

-- FIX A: BitmapOr — PostgreSQL can combine two bitmap index scans
-- This often works automatically if both indexes exist and are selective enough
-- Verify with EXPLAIN: look for "BitmapOr" and "Bitmap Index Scan" nodes

-- FIX B: Rewrite as UNION ALL (usually faster than BitmapOr):
SELECT * FROM transactions WHERE user_id = 123
UNION ALL
SELECT * FROM transactions WHERE merchant_id = 456
  AND user_id != 123;   -- deduplicate

-- FIX C: For a common "search by X or Y" pattern: composite partial indexes
-- or a covering index on (user_id, merchant_id)
```

## Section 3: Index Types and Selection

**Q6. What are the PostgreSQL index types, and when does each one apply?**
A: PostgreSQL provides eight index types. The correct choice depends on the data type, the query predicates, and the access pattern.

**B-tree — the default, 90% of use cases:**
```sql
-- Supports: =, <, <=, >, >=, BETWEEN, IN, LIKE 'prefix%', IS NULL
-- Optimal for: point lookups, range scans, sorting (index scan = sorted output)

CREATE INDEX idx_tx_user_id ON transactions (user_id);
CREATE INDEX idx_tx_created_at ON transactions (created_at DESC);
-- DESC matters for ORDER BY created_at DESC LIMIT N — avoids a sort node

-- Composite B-tree — column order matters (see Q5 point 3):
CREATE INDEX idx_tx_user_status ON transactions (user_id, status, created_at);
-- Useful for: WHERE user_id = X AND status = Y ORDER BY created_at
```

**Hash — only for equality:**
```sql
-- Hash indexes are smaller than B-tree for pure equality lookups
-- But: B-tree handles equality just as fast and also handles ranges
-- Hash indexes are rarely the right choice; B-tree is almost always better

CREATE INDEX idx_session_token_hash ON sessions USING HASH (token);
-- Only use if: column is very wide (UUID, long text) and only = is ever used
-- Hash indexes are not useful for range queries, sorting, or LIKE
```

**GIN (Generalized Inverted Index) — for composite values:**
```sql
-- GIN indexes store an entry for each element of a composite value
-- Optimal for: arrays, JSONB, full-text search, trigram matching

-- Array containment:
CREATE INDEX idx_user_tags ON users USING gin (tags);  -- tags is TEXT[]
SELECT * FROM users WHERE tags @> ARRAY['premium', 'verified'];  -- uses GIN

-- JSONB:
CREATE INDEX idx_tx_metadata ON transactions USING gin (metadata);
SELECT * FROM transactions WHERE metadata @> '{"channel": "upi"}';

-- Full-text search:
CREATE INDEX idx_tx_description_fts ON transactions
    USING gin (to_tsvector('english', description));
SELECT * FROM transactions
WHERE to_tsvector('english', description) @@ to_tsquery('payment & failed');

-- Trigram (substring / ILIKE):
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_users_name_trgm ON users USING gin (name gin_trgm_ops);
SELECT * FROM users WHERE name ILIKE '%kumar%';
```

**GiST (Generalized Search Tree) — for geometric and range types:**
```sql
-- Optimal for: geometric data (PostGIS), range types (daterange, tsrange),
--              nearest-neighbor searches, full-text search (alternative to GIN)

-- Range type overlap/containment:
CREATE INDEX idx_event_daterange ON events USING gist (event_period);
SELECT * FROM events WHERE event_period && '[2024-01-01, 2024-12-31]'::daterange;

-- PostGIS geometry:
CREATE INDEX idx_merchants_location ON merchants USING gist (location);
SELECT * FROM merchants
WHERE ST_DWithin(location, ST_MakePoint(77.5946, 12.9716)::geography, 5000);
-- Finds merchants within 5km of Bengaluru — gist index makes this <10ms on millions of rows

-- GiST vs GIN for full-text: GIN is faster for reads, GiST is faster to update
-- Use GIN for read-heavy; GiST for write-heavy text search
```

**BRIN (Block Range INdex) — for naturally sorted large tables:**
```sql
-- BRIN stores only the MIN and MAX value per range of pages (128 pages by default)
-- Tiny index size (kilobytes for a table with millions of rows)
-- Only effective when physical row order correlates with the column value

-- Perfect use case: append-only time-series tables
-- created_at values increase monotonically as rows are appended
-- BRIN can skip entire page ranges where created_at is outside the query range

CREATE INDEX idx_tx_created_brin ON transactions USING brin (created_at)
    WITH (pages_per_range = 64);  -- smaller range = more granular, larger index

-- Verify correlation (should be close to 1.0):
SELECT correlation FROM pg_stats WHERE tablename = 'transactions' AND attname = 'created_at';
-- correlation = 0.997 → BRIN will be very effective

-- BRIN is wrong for randomly ordered columns (correlation ≈ 0):
-- a randomly ordered column's BRIN min/max will cover the entire range in every block
-- → BRIN provides no filtering benefit → falls back to seq scan

-- Index size comparison for a 100M row transactions table:
-- B-tree on created_at: ~2.1GB
-- BRIN on created_at:   ~3MB
-- BRIN is 700x smaller and nearly as effective for sequential inserts
```

**Q7. What is a covering index, and when does it eliminate a heap fetch?**
A: A covering index (an index that includes all columns required by a query) allows PostgreSQL to answer a query entirely from the index without visiting the table's heap pages. This eliminates random I/O to the heap — often the most expensive part of an index scan.

```sql
-- Without covering index:
CREATE INDEX idx_tx_user_id ON transactions (user_id);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount, status, created_at
FROM transactions
WHERE user_id = 12345;

-- Plan:
Index Scan using idx_tx_user_id on transactions
  (cost=0.43..4823.12 rows=47 width=44)
  (actual time=0.034..12.234 rows=143 loops=1)
  Index Cond: (user_id = 12345)
  Buffers: shared hit=12 read=134
--                          ↑ 134 heap page reads — each is random I/O

-- With covering index (INCLUDE columns):
CREATE INDEX idx_tx_user_covering ON transactions (user_id)
    INCLUDE (id, amount, status, created_at);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount, status, created_at
FROM transactions
WHERE user_id = 12345;

-- Plan:
Index Only Scan using idx_tx_user_covering on transactions
  (cost=0.43..824.12 rows=47 width=44)
  (actual time=0.021..0.234 rows=143 loops=1)
  Index Cond: (user_id = 12345)
  Heap Fetches: 0    ← no heap access at all
  Buffers: shared hit=4 read=0
--                   ↑ zero disk reads — everything from the index

-- "Index Only Scan" is the plan node that indicates covering index usage
-- "Heap Fetches: 0" means the visibility map confirmed all pages are all-visible
-- If Heap Fetches > 0: run VACUUM to update the visibility map

-- INCLUDE vs composite:
-- (user_id, amount): amount is part of the key — queries can filter/sort by amount
-- (user_id) INCLUDE (amount): amount is stored in leaf pages only — not filterable/sortable
--   but the index is smaller because INCLUDE columns are not part of the B-tree key

-- When to use INCLUDE:
-- The included columns are frequently selected but not filtered/sorted by
-- Adding them to the key would increase index bloat unnecessarily
```

## Section 4: Diagnosing and Fixing Slow Queries

**Q8. Walk through a complete diagnosis of a slow query from `EXPLAIN ANALYZE` output to fix.**
A: A systematic diagnosis process — read the plan, find the bottleneck, identify the cause, apply the correct fix.

```sql
-- Context: a fintech app's loan dashboard query is timing out (>30s in prod)
-- The query:
SELECT
    u.name,
    u.email,
    l.id              AS loan_id,
    l.principal_amount,
    l.status,
    l.emi_amount,
    l.next_due_date,
    COUNT(p.id)       AS payment_count,
    SUM(p.amount)     AS total_paid
FROM users u
JOIN loans l ON l.user_id = u.id
LEFT JOIN payments p ON p.loan_id = l.id
WHERE l.status IN ('active', 'overdue')
  AND l.next_due_date < NOW() + INTERVAL '7 days'
  AND u.country = 'IN'
GROUP BY u.name, u.email, l.id, l.principal_amount, l.status, l.emi_amount, l.next_due_date
ORDER BY l.next_due_date ASC
LIMIT 100;
```

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
-- [output below — reading bottom-up]:

Limit  (cost=284729.45..284729.70 rows=100 width=128)
       (actual time=31482.34..31482.40 rows=100 loops=1)
  ->  Sort  (cost=284729.45..285979.45 rows=500000 width=128)
            (actual time=31482.33..31482.37 rows=100 loops=1)
        Sort Key: l.next_due_date
        Sort Method: external merge  Disk: 184320kB  ← DISK SORT: bad
        ->  HashAggregate  (cost=224729.45..229729.45 rows=500000 width=128)
                           (actual time=28934.23..31123.45 rows=412847 loops=1)
              Group Key: u.name, u.email, l.id, ...
              Batches: 8  Memory: 65536kB  ← DISK SPILL: bad (Batches > 1)
              ->  Hash Left Join  (cost=54729.45..189729.45 rows=5000000 width=88)
                                  (actual time=823.45..24823.45 rows=5182394 loops=1)
                    Hash Cond: (p.loan_id = l.id)
                    Buffers: shared hit=4823 read=84729  ← 84K pages read from disk
                    ->  Hash Join  (cost=18234.00..48234.00 rows=412847 width=80)
                                   (actual time=234.12..1823.45 rows=412847 loops=1)
                          Hash Cond: (l.user_id = u.id)
                          ->  Seq Scan on loans l   ← PROBLEM 1
                                    (cost=0.00..24234.00 rows=412847 width=64)
                                    (actual time=0.034..534.23 rows=412847 loops=1)
                                Filter: ((status = ANY('{active,overdue}')) AND
                                         (next_due_date < (now() + '7 days'::interval)))
                                Rows Removed by Filter: 1587153
                          ->  Hash  (cost=14234.00..14234.00 rows=320000 width=28)
                                    (actual time=233.89..233.89 rows=318472 loops=1)
                                ->  Seq Scan on users u   ← PROBLEM 2
                                          (actual time=0.021..143.23 rows=318472 loops=1)
                                      Filter: (country = 'IN'::text)
                                      Rows Removed by Filter: 81528
                    ->  Hash  (cost=28234.00..28234.00 rows=5182394 width=20)
                              (actual time=587.34..587.34 rows=5182394 loops=1)
                          ->  Seq Scan on payments p   ← PROBLEM 3
                                    (actual time=0.023..312.23 rows=5182394 loops=1)
                                  Buffers: shared read=28473

Planning Time: 12.234 ms
Execution Time: 31483.291 ms
```

**Diagnosis — reading the problems:**

```
PROBLEM 1: Seq Scan on loans (412K rows returned, 1.6M filtered)
  → loans needs an index on (status, next_due_date)
  → These are the filter columns; without an index all 2M loans are scanned

PROBLEM 2: Seq Scan on users (318K rows returned, 82K filtered)
  → 80% of users are country='IN' — high selectivity means seq scan may be correct here
  → But: if this query runs frequently, an index on country is worth trying

PROBLEM 3: Seq Scan on payments (5.2M rows — all of them)
  → payments has no filter but is being hash-joined
  → Need an index on payments(loan_id) to avoid a full table scan in the join

PROBLEM 4: Sort Method: external merge Disk: 184MB
  → The sort spilled to disk because work_mem is too small for the result set
  → Increasing work_mem for this session or using a different query structure

PROBLEM 5: HashAggregate Batches: 8
  → The GROUP BY aggregation also spilled to disk
  → Same root cause: work_mem too small
```

    WHERE status IN ('active', 'overdue');  -- partial index: only active/overdue loans

    INCLUDE (amount);  -- covering index: SELECT amount doesn't need a heap fetch

-- With INCLUDE: Index Only Scan → no heap fetch needed

-- Global work_mem increase affects ALL concurrent queries → memory pressure

-- This eliminates the disk sort and disk spill

-- Fix 4: Rewrite the query to reduce the result set before aggregating
-- Instead of aggregating 5M payments then sorting, aggregate first by loan_id:

    u.name,
    u.email,

    l.emi_amount,

FROM users u

    FROM payments
    WHERE loan_id = l.id

WHERE l.status IN ('active', 'overdue')

**Q9. What is the `pg_stat_statements` extension, and how do you use it to find the worst queries in production?**
A: `pg_stat_statements` tracks execution statistics for every distinct query that PostgreSQL executes — call count, total time, mean time, rows, shared block reads/writes. It is the standard first tool for production query performance investigation.

```sql
-- Enable (requires superuser, adds to postgresql.conf):
-- shared_preload_libraries = 'pg_stat_statements'
-- pg_stat_statements.track = all  (track top-level AND nested queries)
-- pg_stat_statements.max = 10000  (number of distinct queries to track)

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Find the top 10 queries by total time (most impactful to optimize first):
SELECT
    LEFT(query, 120)              AS query_preview,
    calls,
    ROUND(total_exec_time::numeric, 2)  AS total_ms,
    ROUND(mean_exec_time::numeric, 2)   AS mean_ms,
    ROUND(stddev_exec_time::numeric, 2) AS stddev_ms,  -- high stddev = inconsistent
    rows,
    ROUND(rows::numeric / calls, 1)     AS rows_per_call,
    shared_blks_read,
    shared_blks_hit,
    ROUND(
        shared_blks_hit::numeric /
        NULLIF(shared_blks_hit + shared_blks_read, 0) * 100, 1
    )                             AS cache_hit_pct,
    shared_blks_written,
    temp_blks_read + temp_blks_written AS temp_io  -- disk spill indicator
FROM pg_stat_statements
WHERE calls > 100                  -- ignore one-off queries
ORDER BY total_exec_time DESC
LIMIT 10;

-- Find queries with the worst cache hit ratio (most disk-bound):
SELECT
    LEFT(query, 100) AS query_preview,
    calls,
    shared_blks_read,
    shared_blks_hit,
    ROUND(shared_blks_hit::numeric / NULLIF(shared_blks_hit + shared_blks_read, 0) * 100, 1)
        AS cache_hit_pct
FROM pg_stat_statements
WHERE shared_blks_read > 10000     -- queries reading significant data from disk
  AND calls > 10
ORDER BY cache_hit_pct ASC        -- worst cache hit ratio first
LIMIT 20;

-- Find queries with disk spill (temp_blks > 0 → work_mem too small):
SELECT
    LEFT(query, 100)                      AS query_preview,
    calls,
    ROUND(mean_exec_time::numeric, 2)     AS mean_ms,
    temp_blks_read,
    temp_blks_written,
    temp_blks_read + temp_blks_written    AS total_temp_io
FROM pg_stat_statements
WHERE temp_blks_read + temp_blks_written > 0
ORDER BY total_temp_io DESC
LIMIT 10;

-- Find infrequently called but very slow queries (p99 outliers):
SELECT
    LEFT(query, 100)                   AS query_preview,
    calls,
    ROUND(mean_exec_time::numeric, 2)  AS mean_ms,
    ROUND(stddev_exec_time::numeric, 2) AS stddev_ms,
    ROUND(max_exec_time::numeric, 2)   AS max_ms  -- worst case observed
FROM pg_stat_statements
WHERE mean_exec_time > 1000    -- mean > 1 second
ORDER BY max_exec_time DESC
LIMIT 10;

-- Reset after optimization to measure improvement:
SELECT pg_stat_statements_reset();
-- Or reset for a specific query:
SELECT pg_stat_statements_reset(userid, dbid, queryid) FROM pg_stat_statements
WHERE query LIKE '%FROM transactions WHERE user_id%';
```

## Section 5: Advanced Optimization Techniques

**Q10. What are partial indexes, and when do they dramatically outperform full indexes?**
A: A partial index includes only a subset of rows — those satisfying a `WHERE` clause. Partial indexes are smaller, faster to scan, and more effective than full indexes when queries consistently filter on a known subset of data.

```sql
-- Scenario: payments table with 50M rows
-- 95% of payments have status = 'completed'
-- Only 5% are 'pending' or 'failed' — but these are queried constantly

-- Full index approach:
CREATE INDEX idx_payments_status ON payments (status, created_at);
-- Index size: covers all 50M rows → large

-- Partial index approach:
CREATE INDEX idx_payments_pending ON payments (created_at)
    WHERE status IN ('pending', 'failed');
-- Index size: covers only 2.5M rows (5%) → 20x smaller
-- Query performance: faster scan on a much smaller index
-- Maintenance cost: updates to 'completed' payments don't touch this index

-- Example queries that use the partial index:
SELECT * FROM payments
WHERE status = 'pending' AND created_at > NOW() - INTERVAL '24 hours';
-- ✓ Planner uses the partial index — the WHERE clause matches

-- This query does NOT use the partial index:
SELECT * FROM payments WHERE created_at > NOW() - INTERVAL '24 hours';
-- ✗ Partial index doesn't cover all rows — planner uses full scan or another index

-- Real-world partial index patterns in fintech:

-- Pattern 1: Active loans only (bulk of loans are closed)
CREATE INDEX idx_loans_active ON loans (user_id, next_due_date)
    WHERE status = 'active';
-- Loan lifecycle: active → closed; only active loans need fast lookup
-- Partial index is 10-100x smaller than a full index on (user_id, next_due_date)

-- Pattern 2: Unprocessed events in a queue table
CREATE INDEX idx_events_unprocessed ON processing_queue (priority DESC, created_at)
    WHERE processed_at IS NULL;
-- Workers need to find the next unprocessed event quickly
-- Once processed, the row is never queried by this pattern again

-- Pattern 3: High-value transactions (regulatory reporting)
CREATE INDEX idx_tx_high_value ON transactions (user_id, created_at)
    WHERE amount >= 50000;
-- PMLA reporting queries only care about high-value transactions
-- ~2% of transactions; partial index is 50x smaller

-- Verifying partial index usage:
EXPLAIN SELECT * FROM payments
WHERE status = 'pending' AND created_at > NOW() - INTERVAL '24 hours';
-- Must see: Index Scan using idx_payments_pending on payments
--           (not a sequential scan and not the full index)

-- Checking partial index size vs full index:
SELECT
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE tablename = 'payments'
ORDER BY pg_relation_size(indexrelid) DESC;
```

**Q11. What is an index scan vs a bitmap index scan, and when does PostgreSQL choose each?**
A: The choice between index scan, bitmap index scan, and sequential scan reflects a cost calculation about random vs sequential I/O patterns.

```
Index Scan:
  Follows index entries in order, fetching each matching heap page immediately.
  Access pattern: random I/O — jumps around the heap as the index leads.
  Best for: small result sets (< ~1% of table) where rows happen to be
            clustered in a few pages (high correlation).
  Problem: if matching rows are scattered across thousands of heap pages,
           each fetch is a separate random I/O — expensive.

Bitmap Index Scan:
  Two-phase process:
  Phase 1: Scan the entire index (or as much as needed), build a BITMAP of
           matching heap page numbers in memory.
  Phase 2: Sort the heap page numbers, then fetch them in order (sequential I/O).
  Best for: medium result sets where rows are scattered across many heap pages.
  The bitmap sort converts random I/O into sequential I/O.

BitmapAnd / BitmapOr:
  Multiple bitmap index scans combined before the heap fetch.
  Allows PostgreSQL to satisfy multi-condition queries using multiple indexes.

Sequential Scan:
  Reads all heap pages in order.
  Best for: large result sets (> ~10% of table).
```

```sql
-- Observing the difference in EXPLAIN output:

-- Small, selective query → Index Scan:
EXPLAIN SELECT * FROM transactions WHERE id = 12345678;
-- Index Scan using transactions_pkey on transactions
--   Index Cond: (id = 12345678)
-- One heap fetch, one I/O — fast

-- Moderate selectivity, scattered rows → Bitmap Index Scan:
EXPLAIN SELECT * FROM transactions WHERE user_id = 999 AND status = 'pending';
-- Bitmap Heap Scan on transactions
--   Recheck Cond: ((user_id = 999) AND (status = 'pending'))
--   ->  BitmapAnd
--         ->  Bitmap Index Scan on idx_tx_user_id
--               Index Cond: (user_id = 999)
--         ->  Bitmap Index Scan on idx_tx_status
--               Index Cond: (status = 'pending')
-- Two bitmaps built, ANDed, then heap fetched in page order

-- "Recheck Cond" appears when the bitmap is lossy (too large for work_mem):
-- PostgreSQL stores page-level bitmaps (1 bit per page) when the exact
-- row-level bitmap doesn't fit in memory. The heap pages are fetched and
-- the condition is re-evaluated row-by-row on each page.
-- Fix: increase work_mem, or use a more selective index to reduce the bitmap size.

-- Forcing a specific scan type (for testing/comparison only):
SET enable_indexscan = OFF;     -- test without index scans
SET enable_bitmapscan = OFF;    -- test without bitmap scans
SET enable_seqscan = OFF;       -- test without sequential scans (dangerous in production)
-- Always reset after testing: RESET ALL;
```

**Q12. How do you handle the N+1 query problem in ORM-based applications, and what does it look like in `EXPLAIN ANALYZE`?**
A: The N+1 problem is an ORM anti-pattern where fetching a list of N records then fetching a related record for each one generates N+1 separate queries. It is invisible in application code but appears as N identical query executions in `pg_stat_statements` and query logs.

```python
# ORM code exhibiting N+1 (SQLAlchemy / any ORM):

# WRONG: fetches users (1 query), then for each user fetches their loans (N queries)
users = session.query(User).filter(User.country == "IN").all()
for user in users:
    # This triggers a separate SQL query for each user:
    loans = user.loans   # SELECT * FROM loans WHERE user_id = ? [executed N times]
    print(f"{user.name}: {len(loans)} loans")

# In pg_stat_statements this appears as:
# query: SELECT * FROM loans WHERE user_id = $1
# calls: 50,000   ← 50,000 individual executions, one per user
# mean_exec_time: 0.8ms
# total_exec_time: 40,000ms = 40 seconds of DB time for this one pattern
```

```sql
-- What N+1 looks like in EXPLAIN ANALYZE (nested loop with 50,000 iterations):
-- You won't see this directly — each of the 50K queries runs independently
-- Detect in pg_stat_statements instead:

SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
WHERE query LIKE '%FROM loans WHERE user_id%'
  AND calls > 1000;  -- high call count for a parameterized query = N+1 signal
```

```python
# Fix 1: Eager loading (JOIN in one query)
from sqlalchemy.orm import joinedload

users = (
    session.query(User)
    .filter(User.country == "IN")
    .options(joinedload(User.loans))  # adds LEFT OUTER JOIN loans ON loans.user_id = users.id
    .all()
)
# Result: 1 query instead of N+1
# Generated SQL: SELECT users.*, loans.* FROM users LEFT JOIN loans ON ...

# Fix 2: subqueryload (separate query but batched)
users = (
    session.query(User)
    .filter(User.country == "IN")
    .options(subqueryload(User.loans))
    .all()
)
# Generated SQL:
#   SELECT * FROM users WHERE country = 'IN'         [query 1]
#   SELECT * FROM loans WHERE user_id IN (1,2,3,...) [query 2 — batched, not N queries]

# Fix 3: Explicit JOIN in the query (maximum control)
result = (
    session.query(User, func.count(Loan.id).label("loan_count"))
    .outerjoin(Loan, Loan.user_id == User.id)
    .filter(User.country == "IN")
    .group_by(User.id)
    .all()
)
# 1 query, returns tuples of (User, loan_count)
```

```sql
-- Fix 4: Raw SQL with JOIN — when the ORM abstraction obscures the query
SELECT
    u.id,
    u.name,
    COUNT(l.id)        AS loan_count,
    SUM(l.principal_amount) AS total_principal
FROM users u
LEFT JOIN loans l ON l.user_id = u.id
WHERE u.country = 'IN'
GROUP BY u.id, u.name;
-- 1 query, all data, fully indexed via existing indexes on user_id and country
```

## Section 6: Statistics, Vacuuming, and Planner Traps

**Q13. How do stale statistics cause bad query plans, and how do you fix them?**
A: The query planner's estimates are only as good as the statistics `ANALYZE` has collected. After large data changes — bulk inserts, deletes, updates — statistics may be severely outdated, causing the planner to choose the wrong plan.

```sql
-- Scenario: bulk import of 5M transactions overnight
-- Before import: transactions table had 2M rows
-- After import: transactions table has 7M rows
-- pg_class.reltuples still shows ~2M (ANALYZE hasn't run yet)

-- The planner estimates the table has 2M rows
-- It chooses a plan appropriate for 2M rows — perhaps a Hash Join
-- The actual table has 7M rows → the Hash Join uses far more memory than expected
-- → disk spill, slow query

-- Diagnosis: compare estimated vs actual rows at the table-level node
EXPLAIN ANALYZE SELECT COUNT(*) FROM transactions;
-- Seq Scan on transactions (cost=0.00..28234.00 rows=2000000 width=0)
--                          (actual time=0.034..3823.45 rows=7000000 loops=1)
-- Estimated: 2M rows. Actual: 7M rows. 3.5x underestimate → stale statistics.

-- Fix: run ANALYZE immediately after bulk operations
ANALYZE transactions;    -- updates statistics for the transactions table
-- Or: ANALYZE VERBOSE transactions;  -- shows what was collected

-- For the entire database (runs on all tables):
ANALYZE;

-- Checking when a table was last analyzed:
SELECT
    relname,
    last_analyze,
    last_autoanalyze,
    n_live_tup,
    n_dead_tup,
    reltuples::bigint AS planner_estimate
FROM pg_stat_user_tables
JOIN pg_class ON pg_class.relname = pg_stat_user_tables.relname
WHERE pg_stat_user_tables.relname = 'transactions';

-- If last_autoanalyze is NULL or days ago: autovacuum may not be running correctly
-- Autovacuum triggers ANALYZE when:
--   n_mod_since_analyze > autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × reltuples
-- Default: triggers when 20% of rows have changed (scale_factor = 0.2)
-- For a 10M row table: triggers after 2M changes — this can be too infrequent

-- Tune autovacuum for large tables:
ALTER TABLE transactions SET (
    autovacuum_analyze_scale_factor = 0.01,  -- trigger after 1% changes (100K rows)
    autovacuum_analyze_threshold = 1000      -- minimum 1000 changes to trigger
);
```

**Extended statistics — for correlated columns:**
```sql
-- Problem: the planner assumes column values are independent
-- If WHERE status = 'active' AND country = 'IN' returns 1,000 rows,
-- the planner estimates: P(active) × P(IN) × total_rows
-- But if status and country are correlated (Indian users tend to be active),
-- the estimate is wrong

-- Extended statistics capture column correlations:
CREATE STATISTICS stats_loans_status_country
    ON status, country FROM loans;

ANALYZE loans;  -- must run ANALYZE after creating extended statistics

-- Verify extended statistics were used:
EXPLAIN SELECT * FROM loans WHERE status = 'active' AND country = 'IN';
-- Should show improved row estimates after creating extended statistics

-- Types of extended statistics:
-- ndistinct: number of distinct values for column combinations
-- dependencies: column dependency (if A determines B, knowing A tells us about B)
-- mcv: most common value combinations

CREATE STATISTICS stats_tx_status_channel (ndistinct, dependencies, mcv)
    ON status, channel FROM transactions;
```

**Q14. What is table bloat, and how does it affect query performance?**
A: Table bloat is the accumulation of dead rows and unused space in a table's heap pages. PostgreSQL's MVCC model does not delete or update rows in-place — instead, a DELETE marks a row as dead and an UPDATE writes a new row version while leaving the old one. Dead rows accumulate until VACUUM reclaims the space.

```sql
-- Measuring table and index bloat:
SELECT
    schemaname || '.' || tablename AS table_name,
    pg_size_pretty(pg_total_relation_size(schemaname || '.' || tablename)) AS total_size,
    pg_size_pretty(pg_relation_size(schemaname || '.' || tablename))       AS table_size,
    n_live_tup,
    n_dead_tup,
    ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1)     AS dead_pct,
    last_vacuum,
    last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC;

-- A table with 30% dead rows:
-- Seq scans: must read 30% more pages than necessary (dead rows are still on the page)
-- Index scans: may follow pointers to dead rows (visibility check required)
-- The index itself may have bloat — pointers to dead rows remain until VACUUM runs

-- Fix: manual VACUUM for tables with high dead_pct
VACUUM ANALYZE transactions;         -- reclaims dead row space, updates statistics
VACUUM FULL ANALYZE transactions;    -- rewrites the table entirely, reclaims disk space
                                     -- WARNING: VACUUM FULL takes an ACCESS EXCLUSIVE lock
                                     -- Use pg_repack extension instead for online repack

-- pg_repack: online table repack without locking:
-- pg_repack -h host -d dbname -t transactions
-- Rewrites the table in the background, swaps atomically — no downtime

-- Checking index bloat:
SELECT
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan,   -- how many times the index has been used
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE tablename = 'transactions'
ORDER BY pg_relation_size(indexrelid) DESC;

-- An index with very few idx_scan but large size = unused bloat
-- Either: query patterns changed (index no longer used) → DROP IT
-- Or: index is new and just hasn't been used yet → wait and check again
```

## Section 7: Scenario-Based Questions

**Q15. Scenario: "A fintech API that retrieves a user's last 10 transactions has been getting slower as the table grows. It now takes 3 seconds on a 50M row table. Diagnose and fix it."**
A:

```sql
-- The query:
SELECT id, amount, merchant_name, status, created_at
FROM transactions
WHERE user_id = $1
ORDER BY created_at DESC
LIMIT 10;

-- Step 1: Run EXPLAIN ANALYZE:
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount, merchant_name, status, created_at
FROM transactions
WHERE user_id = 1234567
ORDER BY created_at DESC
LIMIT 10;

-- Output (before fix):
Limit  (actual time=2934.23..2934.24 rows=10 loops=1)
  ->  Sort  (actual time=2934.22..2934.22 rows=10 loops=1)
        Sort Key: created_at DESC
        Sort Method: top-N heapsort  Memory: 26kB
        ->  Index Scan using idx_tx_user_id on transactions
                    (actual time=0.034..2831.23 rows=847293 loops=1)
              Index Cond: (user_id = 1234567)
              Buffers: shared hit=234 read=83472
-- Problem: Index Scan on user_id returns 847K rows for this user,
-- then sorts all 847K rows to find the last 10.
-- 847K rows fetched, 847K-10 discarded. Massive waste.
```

```sql
-- Root cause: the index on (user_id) returns all rows for the user in heap order
-- Then all rows are fetched to sort by created_at — no early termination possible

-- Fix: composite index on (user_id, created_at DESC)
CREATE INDEX idx_tx_user_created ON transactions (user_id, created_at DESC)
    INCLUDE (id, amount, merchant_name, status);
-- The (user_id, created_at DESC) key means rows for each user are already sorted
-- by created_at descending within the index. LIMIT 10 terminates after 10 entries.
-- INCLUDE columns allow Index Only Scan — no heap fetch needed.

-- After fix:
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount, merchant_name, status, created_at
FROM transactions
WHERE user_id = 1234567
ORDER BY created_at DESC
LIMIT 10;

Limit  (actual time=0.089..0.123 rows=10 loops=1)
  ->  Index Only Scan Backward using idx_tx_user_created on transactions
                    (actual time=0.087..0.110 rows=10 loops=1)
        Index Cond: (user_id = 1234567)
        Heap Fetches: 0
        Buffers: shared hit=4

Execution Time: 0.145 ms   ← from 3,000ms to 0.1ms: 20,000x improvement
```

**Why it works:** The composite index `(user_id, created_at DESC)` stores entries for each user already sorted by `created_at` in descending order. The LIMIT 10 causes the scan to stop after reading 10 index entries — instead of reading 847K rows. The INCLUDE columns eliminate heap fetches entirely, giving a pure index scan.

**Q16. Scenario: "A reporting query that ran in 2 seconds last month now runs in 45 seconds. No code was changed. What do you investigate?"**
A: When performance degrades without code changes, the causes are almost always: data growth, statistics staleness, index bloat, or a change in data distribution that changed the selectivity of existing predicates.

```sql
-- Investigation checklist — run in order:

-- Step 1: Has the table size grown significantly?
SELECT
    relname,
    pg_size_pretty(pg_total_relation_size(relid))  AS total_size,
    reltuples::bigint AS estimated_rows
FROM pg_stat_user_tables
JOIN pg_class ON pg_class.relname = pg_stat_user_tables.relname
WHERE pg_stat_user_tables.relname IN ('transactions', 'users', 'loans')
ORDER BY pg_total_relation_size(relid) DESC;
-- If the table has grown 10x since last month → query now scans more data

-- Step 2: Are statistics stale?
SELECT relname, last_analyze, last_autoanalyze, n_dead_tup
FROM pg_stat_user_tables
WHERE relname = 'transactions';
-- If last_autoanalyze was several days ago on a fast-growing table → run ANALYZE

-- Step 3: Has the query plan changed? (compare with old plan)
EXPLAIN (ANALYZE, BUFFERS) [the slow query];
-- Look for: Seq Scan where an Index Scan used to appear
-- This means the planner switched plans — likely because selectivity changed

-- Step 4: Has the data distribution changed?
-- Example: last month 50% of transactions were 'pending'; this month only 2% are
-- A query filtering on status='pending' was 50% selective → seq scan was fine
-- Now 2% selective → should use an index but statistics still show 50% → wrong plan
SELECT status, COUNT(*), ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS pct
FROM transactions
GROUP BY status;
-- Compare: do the current percentages match pg_stats.most_common_freqs?
SELECT most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'transactions' AND attname = 'status';
-- If they differ significantly → run ANALYZE transactions;

-- Step 5: Check for index bloat
SELECT indexname, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE tablename = 'transactions';
-- An index that has grown 5x in a month with high write activity may have bloat
-- REINDEX CONCURRENTLY idx_transactions_status;  -- online reindex

-- Step 6: Check for table bloat
SELECT n_dead_tup, ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) dead_pct
FROM pg_stat_user_tables
WHERE relname = 'transactions';
-- dead_pct > 20% → run VACUUM ANALYZE transactions;

-- Step 7: Has autovacuum been running?
SELECT pid, query, state, now() - query_start AS duration
FROM pg_stat_activity
WHERE query LIKE 'autovacuum%';
-- If autovacuum is not running or is blocked → investigate autovacuum configuration

-- Step 8: Check for lock contention (a long-running transaction blocking autovacuum):
SELECT pid, age(clock_timestamp(), query_start) AS duration, query
FROM pg_stat_activity
WHERE state != 'idle'
  AND query_start < NOW() - INTERVAL '5 minutes'
ORDER BY duration DESC;
-- A long-running transaction prevents VACUUM from cleaning dead rows
-- → table bloat accumulates → sequential scans take longer
```

## Quick Reference: EXPLAIN ANALYZE Diagnostic Checklist

```
READING THE PLAN
[ ] Read bottom-up: inner nodes execute first, feed output to parent
[ ] Find the node with highest actual time — that's the bottleneck
[ ] Compare estimated rows vs actual rows — large divergence = stale stats
[ ] Check Rows Removed by Filter — high number on a seq scan = missing index
[ ] Check Buffers: shared read — high number = disk-bound, index or cache needed
[ ] Check Sort Method — "external merge  Disk:" = work_mem too small
[ ] Check HashAggregate Batches — Batches > 1 = disk spill, increase work_mem
[ ] Check Heap Fetches on Index Only Scan — > 0 means VACUUM needed

SEQUENTIAL SCAN CAUSES (fix each specifically)
[ ] No index on the filtered column → CREATE INDEX
[ ] Function on the indexed column (LOWER(), DATE(), etc.) → functional index
[ ] Type cast mismatch (int column = 'string') → fix the literal type
[ ] Leading column of composite index not in predicate → add separate index
[ ] LIKE '%prefix%' → CREATE INDEX USING gin with gin_trgm_ops
[ ] OR across different columns → rewrite as UNION ALL or use BitmapOr

INDEX SELECTION
[ ] B-tree: =, <, >, BETWEEN, LIKE 'prefix%', ORDER BY
[ ] GIN: arrays (@>), JSONB (@>), full-text (@@), ILIKE (%value%)
[ ] GiST: ranges (&&), geometry (PostGIS), nearest-neighbor
[ ] BRIN: append-only time-series (correlation must be near 1.0)
[ ] Partial index: queries always filter on a known subset
[ ] Covering index (INCLUDE): SELECT columns not needed for filtering

QUERY PATTERNS TO FIX
[ ] N+1: high call count for parameterized query → eager load / JOIN
[ ] Sort on large result + LIMIT: composite index with ORDER BY columns
[ ] Group By on large join: LATERAL join to pre-aggregate before joining
[ ] Stale statistics after bulk load: ANALYZE table immediately after
[ ] Index bloat after high writes: REINDEX CONCURRENTLY
[ ] Table bloat (high dead_pct): VACUUM ANALYZE or pg_repack

KEY pg_stat_statements QUERIES
[ ] Top by total_exec_time: most impactful to optimize
[ ] Top by shared_blks_read / low cache_hit_pct: disk-bound queries
[ ] High temp_blks: work_mem candidates
[ ] High calls + parameterized: N+1 detector
[ ] High mean_exec_time + low calls: cold-path outliers

SETTINGS TO TUNE
[ ] random_page_cost = 1.1 (SSD / cloud) vs 4.0 (spinning disk default)
[ ] work_mem: increase per-session for sort/hash operations (not globally)
[ ] statistics target: ALTER TABLE t ALTER COLUMN c SET STATISTICS 500;
    (increase for columns with unusual distributions)
[ ] autovacuum_analyze_scale_factor = 0.01 for large high-write tables
```

**Tip for the interview:** At 5 YOE, query optimization questions almost never stay at "what is EXPLAIN" — they go straight to "read this plan and tell me what's wrong" or "why would the planner choose a sequential scan here?" The two skills interviewers probe most: reading the estimated-vs-actual row divergence to spot stale statistics (Q13), and understanding why a composite index column order matters for LIMIT queries (Q15 — the 20,000x improvement example). Know the five sequential scan causes cold (Q5) — especially the type mismatch and function-on-column patterns, which appear in real codebases constantly. For the disk sort and disk spill patterns (Q8), frame it as "the Sort node shows `external merge Disk:` which means work_mem is too small — this is a session-level fix, not a global one." The `pg_stat_statements` query to find N+1 patterns (Q9 — high call count for a parameterized query) signals production experience. The scenario questions (Q15 and Q16) are common senior-level closes: Q15 tests whether you know that a composite index with LIMIT avoids sorting the full result set, and Q16 tests systematic degradation investigation rather than jumping straight to "add an index."
