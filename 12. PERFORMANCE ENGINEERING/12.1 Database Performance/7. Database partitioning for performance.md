# Performance: Database Partitioning — Interview Q&A (5 YOE Level)

---

## Section 1: Partitioning Fundamentals

**Q1. What is database partitioning, how does it differ from sharding, and what problem does each solve?**
A: Partitioning and sharding are both techniques for dividing large datasets into smaller, more manageable pieces — but they operate at different layers and solve different problems:

**Partitioning** divides a single logical table into multiple physical storage segments within the same database instance. The application sees one table; the database engine routes queries to the relevant partition(s) internally:

```
Logical view (what the application sees):
  ┌─────────────────────────────────┐
  │        transactions             │ ← Single table name in queries
  └─────────────────────────────────┘

Physical storage (what the database actually stores):
  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
  │transactions_2023│  │transactions_2024│  │transactions_2025│
  │  (partition 1)  │  │  (partition 2)  │  │  (partition 3)  │
  └─────────────────┘  └─────────────────┘  └─────────────────┘
  Same PostgreSQL instance; different data files; one logical table
```

**Sharding** distributes data across multiple independent database instances (nodes), each with its own compute, memory, and storage:

```
Shard 1 (DB instance in Mumbai)      Shard 2 (DB instance in Hyderabad)
┌────────────────────────────┐       ┌────────────────────────────┐
│ transactions for users     │       │ transactions for users     │
│ whose userId % 2 == 0      │       │ whose userId % 2 == 1      │
└────────────────────────────┘       └────────────────────────────┘
Application must know which shard to query — routing logic lives in the application
```

**The problems each solves:**

```
Partitioning solves:
  ✓ Query performance on large tables (partition pruning skips irrelevant partitions)
  ✓ Maintenance operations (VACUUM, index rebuild on one partition at a time)
  ✓ Data lifecycle management (drop old partition instead of slow DELETE)
  ✓ I/O parallelism (different partitions can be on different disks)
  ✗ Does NOT solve: single-instance CPU/memory limits (still one DB server)
  ✗ Does NOT solve: write throughput ceiling of one DB server

Sharding solves:
  ✓ Horizontal write scalability (each shard handles a fraction of writes)
  ✓ Total data volume beyond what one server can hold
  ✓ Geographic distribution (shards in different regions)
  ✗ Cross-shard queries are expensive (cannot JOIN across shards without federation)
  ✗ Transactions spanning shards require distributed transactions (2PC)
  ✗ Rebalancing shards when adding new nodes is complex
  ✗ Dramatically increases application complexity

The decision:
  Table has 500GB, slow reads → partition (same instance, smarter storage layout)
  Write throughput exceeds what one instance can handle → shard (multiple instances)
  Most fintech platforms partition first and shard only when truly necessary;
  sharding is operationally expensive and should be a last resort.
```

**Q2. What are the four partitioning strategies, what does each optimize for, and which is appropriate for which data pattern?**
A: PostgreSQL (and most databases) support four fundamental partitioning strategies. The choice of strategy is the single most consequential partitioning decision — the wrong strategy eliminates all benefits:

**Strategy 1 — Range Partitioning:**
```sql
-- Divide rows by a continuous range of values in a column
-- Classic use case: time-series data partitioned by date

CREATE TABLE transactions (
  id          UUID        NOT NULL,
  user_id     UUID        NOT NULL,
  amount      BIGINT      NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL,
  status      TEXT        NOT NULL
) PARTITION BY RANGE (created_at);

-- One partition per month
CREATE TABLE transactions_2024_01
  PARTITION OF transactions
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE transactions_2024_02
  PARTITION OF transactions
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Query with date filter → PostgreSQL reads ONLY the relevant partitions
EXPLAIN SELECT * FROM transactions
WHERE created_at BETWEEN '2024-01-15' AND '2024-01-20';
-- Output: Seq Scan on transactions_2024_01 (NOT transactions_2024_02, _03, etc.)
-- This is "partition pruning" — skipping irrelevant partitions entirely

Optimizes for:
  ✓ Time-series queries with date range filters
  ✓ Rolling data retention (drop oldest partition instead of DELETE WHERE date < ...)
  ✓ Queries that always filter by the partition key
When to use:
  Logs, transactions, audit trails, sensor data — anything with a natural time dimension
```

**Strategy 2 — List Partitioning:**
```sql
-- Divide rows by discrete values in a column
-- Classic use case: multi-tenant data partitioned by tenant ID or country

CREATE TABLE loan_applications (
  id          UUID  NOT NULL,
  tenant_id   TEXT  NOT NULL,
  applicant_id UUID NOT NULL,
  amount      BIGINT NOT NULL
) PARTITION BY LIST (tenant_id);

CREATE TABLE loan_applications_tenant_a
  PARTITION OF loan_applications
  FOR VALUES IN ('TENANT_A', 'TENANT_A_TEST');

CREATE TABLE loan_applications_tenant_b
  PARTITION OF loan_applications
  FOR VALUES IN ('TENANT_B');

-- Country-based partitioning for compliance
CREATE TABLE users (
  id          UUID  NOT NULL,
  country     CHAR(2) NOT NULL,
  pii_data    TEXT   -- Must stay in country of origin
) PARTITION BY LIST (country);

CREATE TABLE users_in PARTITION OF users FOR VALUES IN ('IN');
CREATE TABLE users_sg PARTITION OF users FOR VALUES IN ('SG');
CREATE TABLE users_us PARTITION OF users FOR VALUES IN ('US');
-- Data residency: IN users are physically in the India partition (on India-region disks)

Optimizes for:
  ✓ Queries that always filter by the partition key (WHERE tenant_id = ?)
  ✓ Data isolation between tenants (one partition per tenant)
  ✓ Regulatory data residency (country data in country-specific partition)
When to use:
  Multi-tenant SaaS, geographic compliance, known finite set of partition values
```

**Strategy 3 — Hash Partitioning:**
```sql
-- Divide rows by the hash of a column value, distributing evenly across N buckets
-- Classic use case: distributing large tables evenly when no natural range/list key exists

CREATE TABLE payment_events (
  id          UUID   NOT NULL,
  user_id     UUID   NOT NULL,
  event_type  TEXT   NOT NULL,
  payload     JSONB,
  created_at  TIMESTAMPTZ NOT NULL
) PARTITION BY HASH (user_id);

-- 8 partitions — hash(user_id) % 8 determines which partition
CREATE TABLE payment_events_p0 PARTITION OF payment_events
  FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE payment_events_p1 PARTITION OF payment_events
  FOR VALUES WITH (MODULUS 8, REMAINDER 1);
-- ... p2 through p7

-- Query with user_id filter → PostgreSQL hashes the value → reads 1 partition
SELECT * FROM payment_events WHERE user_id = 'user-abc-123';
-- PostgreSQL computes hash('user-abc-123') % 8 = 3 → reads only p3

Optimizes for:
  ✓ Even distribution of data across partitions (no hot partitions)
  ✓ Point lookups by the hash key (WHERE user_id = ?)
  ✗ Range queries on the partition key are NOT pruned (hash order ≠ value order)
  ✗ Adding partitions requires rehashing all data (unlike consistent hashing)
When to use:
  Large tables with no natural range/list grouping; user-centric data where
  you want per-user queries to be fast; preventing hot spots
```

**Strategy 4 — Composite Partitioning (Sub-partitioning):**
```sql
-- Partition by two dimensions — range on date, then hash on user_id within each month
-- Combines benefits: date pruning + even distribution within each month

CREATE TABLE transactions (
  id         UUID        NOT NULL,
  user_id    UUID        NOT NULL,
  amount     BIGINT      NOT NULL,
  created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

-- Month partition
CREATE TABLE transactions_2024_01
  PARTITION OF transactions
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01')
  PARTITION BY HASH (user_id);  -- Sub-partition by user

-- 4 sub-partitions within January
CREATE TABLE transactions_2024_01_p0
  PARTITION OF transactions_2024_01
  FOR VALUES WITH (MODULUS 4, REMAINDER 0);
-- ... p1, p2, p3

-- Query: WHERE created_at = '2024-01-15' AND user_id = 'user-xyz'
-- → PostgreSQL prunes to transactions_2024_01 (range pruning)
-- → Then prunes to transactions_2024_01_p2 (hash pruning)
-- → Reads 1 sub-partition instead of the entire table

When to use:
  Very large tables (terabytes) where single-level partitioning leaves partitions
  that are still too large; time-series data with high per-user query volume
```

## Section 2: Range Partitioning in Depth (Most Common)

**Q3. Walk through implementing time-based range partitioning on a transactions table in PostgreSQL — including partition creation, automatic partition creation, and query plan verification.**
A: Range partitioning on a date column is the most common and highest-impact partitioning implementation for fintech systems. The implementation spans table creation, partition management, and verification:

```sql
-- Step 1: Create the partitioned parent table
-- The parent table holds NO data itself — it's a routing structure
CREATE TABLE transactions (
  id              UUID            NOT NULL DEFAULT gen_random_uuid(),
  user_id         UUID            NOT NULL,
  loan_id         UUID,
  amount          BIGINT          NOT NULL,  -- in paise
  currency        CHAR(3)         NOT NULL DEFAULT 'INR',
  transaction_type TEXT           NOT NULL,  -- DISBURSEMENT, REPAYMENT, FEE, REFUND
  status          TEXT            NOT NULL,  -- PENDING, SUCCESS, FAILED, REVERSED
  gateway_ref     TEXT,
  created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
  metadata        JSONB
) PARTITION BY RANGE (created_at);

-- Step 2: Create indexes ON THE PARENT — they propagate to all partitions automatically
-- (PostgreSQL 11+: indexes on parent propagate to existing and future partitions)
CREATE INDEX idx_transactions_user_id    ON transactions (user_id);
CREATE INDEX idx_transactions_loan_id    ON transactions (loan_id) WHERE loan_id IS NOT NULL;
CREATE INDEX idx_transactions_status     ON transactions (status);
CREATE INDEX idx_transactions_created_at ON transactions (created_at);
-- Each partition gets its own copy of these indexes — sized to the partition

-- Step 3: Create initial partitions
-- Naming convention: table_YYYY_MM for monthly partitions
CREATE TABLE transactions_2024_01 PARTITION OF transactions
  FOR VALUES FROM ('2024-01-01 00:00:00+00') TO ('2024-02-01 00:00:00+00');

CREATE TABLE transactions_2024_02 PARTITION OF transactions
  FOR VALUES FROM ('2024-02-01 00:00:00+00') TO ('2024-03-01 00:00:00+00');

-- Step 4: Default partition for out-of-range data (safety net)
CREATE TABLE transactions_default PARTITION OF transactions DEFAULT;
-- Rows that don't match any partition range go here
-- Alert if this table grows — it means partition coverage has a gap

-- Step 5: Verify partition structure
SELECT
  child.relname                                    AS partition_name,
  pg_get_expr(child.relpartbound, child.oid, true) AS partition_range,
  pg_size_pretty(pg_total_relation_size(child.oid)) AS size
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child  ON pg_inherits.inhrelid  = child.oid
WHERE parent.relname = 'transactions'
ORDER BY child.relname;

-- Output:
-- partition_name          | partition_range                              | size
-- transactions_2024_01    | FOR VALUES FROM ('2024-01-01') TO ('2024-02-01') | 4821 MB
-- transactions_2024_02    | FOR VALUES FROM ('2024-02-01') TO ('2024-03-01') | 4234 MB
-- transactions_default    | DEFAULT                                          | 0 bytes

-- Step 6: Verify partition pruning with EXPLAIN
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM transactions
WHERE created_at >= '2024-01-01'
  AND created_at <  '2024-02-01'
  AND user_id = 'user-abc-123';

-- Expected output (pruning works):
-- Bitmap Heap Scan on transactions_2024_01  ← Only January partition
--   Filter: (user_id = 'user-abc-123')
-- NOT: Seq Scan on transactions_2024_02, transactions_2024_03, etc.

-- Step 7: Verify pruning FAILS without partition key in WHERE clause
EXPLAIN SELECT * FROM transactions WHERE user_id = 'user-abc-123';
-- Output: Seq Scan on transactions_2024_01 + Seq Scan on transactions_2024_02 + ...
-- ALL partitions scanned — no date filter = no pruning
-- This query should have a different index or be rewritten with a date range
```

**Q4. How do you automate monthly partition creation in a Node.js/PostgreSQL environment to ensure future partitions always exist before data arrives?**
A: Manual partition creation is error-prone — if the partition for next month doesn't exist when data arrives, PostgreSQL will either reject the INSERT (if no default partition) or route data to the default partition (losing the performance benefit). Automation is mandatory:

```typescript
// partition-manager.service.ts
import { Injectable, Logger } from '@nestjs/common';
import { Cron, CronExpression } from '@nestjs/schedule';
import { DataSource } from 'typeorm';
import {
  startOfMonth, endOfMonth, addMonths, format,
  subMonths, parseISO
} from 'date-fns';

@Injectable()
export class PartitionManagerService {
  private readonly logger = new Logger(PartitionManagerService.name);

  // Tables that are range-partitioned by month
  private readonly PARTITIONED_TABLES = [
    'transactions',
    'audit_logs',
    'payment_events',
    'emi_schedules',
  ];

  // How many months ahead to pre-create partitions
  private readonly LOOKAHEAD_MONTHS = 3;

  // How many months of data to retain (older partitions dropped)
  private readonly RETENTION_MONTHS = 24;

  constructor(private readonly dataSource: DataSource) {}

  // Runs on the 1st of every month at 00:05 UTC
  // Creates next 3 months of partitions; drops partitions older than retention period
  @Cron('5 0 1 * *')
  async managePartitions(): Promise<void> {
    this.logger.log('Starting monthly partition management');

    for (const tableName of this.PARTITIONED_TABLES) {
      await this.ensureFuturePartitions(tableName);
      await this.dropExpiredPartitions(tableName);
    }
  }

  // Also expose as a manually triggerable endpoint for operational use
  async ensureFuturePartitions(tableName: string): Promise<void> {
    const now = new Date();

    for (let i = 0; i <= this.LOOKAHEAD_MONTHS; i++) {
      const targetMonth = addMonths(now, i);
      await this.createPartitionIfNotExists(tableName, targetMonth);
    }
  }

  private async createPartitionIfNotExists(
    tableName: string,
    month: Date,
  ): Promise<void> {
    const partitionName = this.getPartitionName(tableName, month);
    const fromDate      = format(startOfMonth(month), 'yyyy-MM-dd');
    const toDate        = format(startOfMonth(addMonths(month, 1)), 'yyyy-MM-dd');

    // Check if partition already exists
    const existsResult = await this.dataSource.query(
      `SELECT EXISTS (
        SELECT 1 FROM pg_class c
        JOIN pg_namespace n ON n.oid = c.relnamespace
        WHERE c.relname = $1
          AND n.nspname = 'public'
      )`,
      [partitionName]
    );

    if (existsResult[0].exists) {
      this.logger.debug(`Partition ${partitionName} already exists — skipping`);
      return;
    }

    // Create the partition
    await this.dataSource.query(`
      CREATE TABLE ${partitionName}
        PARTITION OF ${tableName}
        FOR VALUES FROM ('${fromDate}') TO ('${toDate}')
    `);

    this.logger.log(`Created partition: ${partitionName} (${fromDate} to ${toDate})`);

    // Alert if partition creation happened less than 1 day before its start
    // (means the lookahead job missed a cycle)
    const daysUntilStart = Math.floor(
      (parseISO(fromDate).getTime() - Date.now()) / (1000 * 60 * 60 * 24)
    );
    if (daysUntilStart < 1) {
      this.logger.warn(
        `LATE PARTITION CREATION: ${partitionName} starts in ${daysUntilStart} days!`
      );
      await this.alerting.warn(`Late partition: ${partitionName}`);
    }
  }

  private async dropExpiredPartitions(tableName: string): Promise<void> {
    const cutoffMonth = subMonths(new Date(), this.RETENTION_MONTHS);

    // Find partitions older than retention period
    const oldPartitions = await this.dataSource.query(`
      SELECT child.relname AS partition_name
      FROM pg_inherits
      JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
      JOIN pg_class child  ON pg_inherits.inhrelid  = child.oid
      WHERE parent.relname = $1
        AND child.relname  != $2
        AND child.relname  < $3
      ORDER BY child.relname
    `, [
      tableName,
      `${tableName}_default`,
      `${tableName}_${format(cutoffMonth, 'yyyy_MM')}`,
    ]);

    for (const { partition_name } of oldPartitions) {
      // Safety check: verify partition is truly old before dropping
      const rowCount = await this.dataSource.query(
        `SELECT COUNT(*) FROM ${partition_name}`
      );

      this.logger.log(
        `Dropping expired partition ${partition_name} ` +
        `(${rowCount[0].count} rows, older than ${this.RETENTION_MONTHS} months)`
      );

      // Archive to cold storage before dropping (regulatory requirement)
      await this.archivePartitionToS3(partition_name);

      // DROP is instant — no row-by-row deletion; just removes the data file
      await this.dataSource.query(`DROP TABLE ${partition_name}`);

      this.logger.log(`Dropped partition: ${partition_name}`);
    }
  }

  private getPartitionName(tableName: string, month: Date): string {
    return `${tableName}_${format(month, 'yyyy_MM')}`;
  }

  private async archivePartitionToS3(partitionName: string): Promise<void> {
    // pg_dump the partition to S3 before dropping
    // For RBI compliance: transaction data retained 5 years on cold storage
    const s3Key = `archives/${partitionName}_${Date.now()}.sql.gz`;
    // ... pg_dump implementation
    this.logger.log(`Archived ${partitionName} to s3://archive/${s3Key}`);
  }
}
```

## Section 3: Partition Pruning and Query Optimization

**Q5. What is partition pruning, what conditions must be met for it to work, and what are the common mistakes that silently prevent it?**
A: Partition pruning is the database optimizer's ability to exclude irrelevant partitions from query execution based on the WHERE clause. It is the mechanism that makes partitioning actually improve query performance — without it, partitioning adds overhead with no benefit:

**How partition pruning works:**
```sql
-- Table partitioned by RANGE on created_at (monthly partitions)
-- PostgreSQL's planner inspects the WHERE clause at plan time:

-- Query A: partition pruning WORKS
EXPLAIN SELECT * FROM transactions
WHERE created_at >= '2024-06-01' AND created_at < '2024-07-01';
-- Planner sees: '2024-06-01' to '2024-07-01' → only transactions_2024_06 can match
-- Output: Seq Scan on transactions_2024_06
-- Cost: proportional to June's data only — ignores all other months

-- Query B: partition pruning FAILS
EXPLAIN SELECT * FROM transactions
WHERE DATE_TRUNC('month', created_at) = '2024-06-01';
-- Planner cannot evaluate which partitions match without scanning all rows
-- Output: Seq Scan on transactions_2024_01 + ... + transactions_2024_12
-- Cost: full table scan across all partitions — worse than unpartitioned!

-- Why B fails: DATE_TRUNC transforms the partition key before comparison
-- The planner cannot reverse-engineer which partitions satisfy the transformed condition
```

**The five conditions required for partition pruning:**

```sql
-- Condition 1: Filter must reference the partition key DIRECTLY (not transformed)
-- WORKS:
WHERE created_at >= '2024-06-01'
-- FAILS:
WHERE EXTRACT(YEAR FROM created_at) = 2024  -- function applied to partition key
WHERE created_at::DATE = '2024-06-01'       -- cast applied to partition key
WHERE DATE(created_at) = '2024-06-01'       -- function applied to partition key

-- Condition 2: The comparison value must be a constant or a stable function
-- WORKS:
WHERE created_at >= NOW() - INTERVAL '30 days'  -- NOW() is stable (constant per query)
WHERE created_at >= $1                           -- parameterized (value known at plan time)
-- FAILS (in some Postgres versions):
WHERE created_at >= get_cutoff_date()  -- user-defined function: planner can't evaluate

-- Condition 3: The operator must be compatible with the partition strategy
-- Range partitioning: >, >=, <, <=, BETWEEN, = all work
-- WORKS:
WHERE created_at = '2024-06-15'       -- equality on range partition key
WHERE created_at BETWEEN '2024-06-01' AND '2024-06-30'
-- FAILS:
WHERE created_at != '2024-06-15'      -- inequality: cannot exclude any partition
WHERE created_at IN ('2024-06-01', '2024-12-01')  -- IN on range: Postgres 11+ handles this

-- Condition 4: enable_partition_pruning must be ON (default: on)
SHOW enable_partition_pruning;  -- Verify it's 'on'
SET enable_partition_pruning = on;

-- Condition 5: For dynamic pruning (runtime values), Postgres version matters
-- Static pruning (literal constants): Postgres 10+
-- Dynamic pruning (parameterized queries $1): Postgres 11+
-- Make sure you're on Postgres 11+ for full benefit with application queries
```

**Common mistakes that silently prevent pruning:**

```sql
-- Mistake 1: Implicit type mismatch
-- Table: created_at TIMESTAMPTZ
-- Query comparing against DATE (not TIMESTAMPTZ):
WHERE created_at = '2024-06-15'::DATE
-- PostgreSQL casts created_at to DATE for comparison → function on partition key → no pruning
-- Fix: compare with a TIMESTAMPTZ range
WHERE created_at >= '2024-06-15 00:00:00+00' AND created_at < '2024-06-16 00:00:00+00'

-- Mistake 2: Application-level date transformation before sending to DB
-- In TypeORM:
const result = await repo.find({
  where: {
    createdAt: Raw((col) => `DATE(${col}) = '2024-06-15'`), // DATE() kills pruning
  },
});
-- Fix: use a range condition
const start = new Date('2024-06-15T00:00:00Z');
const end   = new Date('2024-06-16T00:00:00Z');
const result = await repo.find({
  where: { createdAt: Between(start, end) },
});

-- Mistake 3: OR condition with non-partition-key column
WHERE created_at >= '2024-06-01' OR user_id = 'user-123'
-- The OR prevents pruning — user_id might match rows in ANY partition
-- Fix: restructure the query (UNION if truly needed, or reconsider the requirement)

-- Mistake 4: JOIN condition without explicit partition filter
SELECT t.*, u.name
FROM transactions t
JOIN users u ON u.id = t.user_id
WHERE u.email = 'alice@example.com';
-- No filter on created_at → ALL partitions scanned
-- Fix: add a date filter when possible
WHERE u.email = 'alice@example.com'
  AND t.created_at >= NOW() - INTERVAL '1 year'  -- business rule: only recent transactions

-- Verification: always EXPLAIN before deploying partition-dependent queries
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT ... ;
-- Look for: "Partitions: transactions_2024_06" NOT "Partitions: all"
```

**Q6. What is partition-wise JOIN and partition-wise aggregation, and when do they provide additional performance benefits beyond partition pruning?**
A: Partition pruning reduces the data scanned. Partition-wise operations go further — they enable PostgreSQL to parallelize JOINs and GROUP BY operations across partitions independently, then combine the results:

```sql
-- Partition-wise aggregation:
-- Instead of: scan all partitions → merge all rows → GROUP BY
-- Does:       GROUP BY within each partition → merge aggregates → final result
-- Benefit: each partition's aggregation can run in parallel; much less data in final merge

-- Enable in PostgreSQL:
SET enable_partitionwise_aggregate = on;

-- Example: monthly revenue report across all of 2024
SELECT
  DATE_TRUNC('month', created_at) AS month,
  SUM(amount) AS total_amount,
  COUNT(*) AS transaction_count
FROM transactions
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'
  AND status = 'SUCCESS'
GROUP BY DATE_TRUNC('month', created_at)
ORDER BY month;

-- Without partition-wise aggregation:
-- Scan transactions_2024_01 through transactions_2024_12 (sequential)
-- Collect all rows matching status=SUCCESS
-- Perform GROUP BY on the merged result set
-- Memory: must hold all 12 months of SUCCESS rows in working memory

-- With partition-wise aggregation:
-- For each partition in parallel:
--   Scan transactions_2024_01 → partial aggregate {month: Jan, sum: X, count: Y}
--   Scan transactions_2024_02 → partial aggregate {month: Feb, sum: A, count: B}
--   ...
-- Merge 12 partial aggregates into final result
-- Memory: only 12 aggregate rows, not millions of individual transaction rows
-- CPU: distributed across parallel workers

-- Partition-wise JOIN:
SET enable_partitionwise_join = on;

-- When both tables are partitioned by the same key and partition count:
-- transactions partitioned by user_id (HASH, 8 partitions)
-- user_profiles  partitioned by user_id (HASH, 8 partitions, same modulus)

SELECT t.*, p.risk_tier
FROM transactions   t
JOIN user_profiles  p ON p.user_id = t.user_id
WHERE t.created_at >= '2024-01-01';

-- With partition-wise JOIN:
-- joins transactions_p0 with user_profiles_p0 (same hash bucket → matching rows guaranteed)
-- joins transactions_p1 with user_profiles_p1
-- ... 8 independent JOINs that can run in parallel
-- No cross-partition matching needed (hash ensures p0 rows on both sides match)
-- Dramatically reduces the JOIN working set size per worker

-- Checking if partition-wise operations are being used:
EXPLAIN (ANALYZE, FORMAT TEXT)
SELECT DATE_TRUNC('month', created_at), SUM(amount)
FROM transactions
GROUP BY 1;
-- Look for: "Partial Aggregate" nodes within each partition scan
-- vs: "HashAggregate" above all partition scans (non-partition-wise)
```

## Section 4: Indexes on Partitioned Tables

**Q7. How do indexes work on partitioned tables, what is a local versus global index, and how do you design the right index strategy for a partitioned fintech table?**
A: Index design on partitioned tables is more nuanced than on regular tables. PostgreSQL creates local indexes (one per partition) automatically when you create an index on the parent table. Global indexes (spanning all partitions) are not natively supported in PostgreSQL — this is a deliberate trade-off:

**Local indexes (PostgreSQL's approach):**
```sql
-- Index created on parent → one local index created per partition
CREATE INDEX idx_transactions_user_id ON transactions (user_id);

-- What actually exists in storage:
-- idx_transactions_user_id_2024_01 → indexes only transactions_2024_01 rows
-- idx_transactions_user_id_2024_02 → indexes only transactions_2024_02 rows
-- idx_transactions_user_id_2024_03 → indexes only transactions_2024_03 rows
-- ... one index per partition, sized to that partition's data

-- Benefit: each index is small (proportional to one partition)
-- B-tree depth for 10GB partition: ~4 levels
-- vs. B-tree depth for 120GB total table: ~5 levels
-- Each level = 1 disk read; saving 1 level per lookup = significant at scale

-- The critical consequence:
-- Query WITHOUT partition key: must search ALL local indexes
SELECT * FROM transactions WHERE user_id = 'user-abc-123';
-- Plan: index scan on idx_transactions_user_id_2024_01
--     + index scan on idx_transactions_user_id_2024_02
--     + ... N index scans (one per partition)
-- This is "index-union" across partitions — still parallel, but N index seeks

-- Query WITH partition key: one index lookup
SELECT * FROM transactions
WHERE user_id = 'user-abc-123'
  AND created_at >= '2024-01-01'  -- ← partition pruning reduces to relevant months
  AND created_at <  '2025-01-01';
-- Plan: index scan on idx_transactions_user_id_2024_01
--     + index scan on idx_transactions_user_id_2024_02
--     + ... 12 index scans (one per 2024 month)
-- With partition pruning, only 12 scans instead of all-time partitions
```

**Index strategy for a fintech transactions table:**
```sql
-- Strategy: design indexes around the two query patterns

-- Pattern 1: user history (always has user_id + optional date range)
-- Best index: (user_id, created_at) on the partitioned table
CREATE INDEX idx_transactions_user_created
  ON transactions (user_id, created_at DESC);
-- Query: WHERE user_id = ? AND created_at > ? ORDER BY created_at DESC
-- → Index covers the ORDER BY; no sort step needed
-- → With date filter: partition pruning + index lookup in pruned partitions

-- Pattern 2: loan repayment tracking (loan_id + status)
CREATE INDEX idx_transactions_loan_status
  ON transactions (loan_id, status)
  WHERE loan_id IS NOT NULL;  -- Partial index: exclude null loan_id rows
-- Partial index: much smaller; only indexes rows relevant to this query pattern

-- Pattern 3: financial reconciliation (status + date range for bulk processing)
CREATE INDEX idx_transactions_status_created
  ON transactions (status, created_at)
  WHERE status IN ('PENDING', 'FAILED');  -- Only actionable statuses
-- Reconciliation job: WHERE status = 'PENDING' AND created_at < NOW() - INTERVAL '1 hour'
-- Partial index: excludes SUCCESS and REVERSED (the vast majority of rows)

-- What NOT to index:
-- Don't index every column "just in case" — each index adds INSERT/UPDATE overhead
-- Don't create an index on the partition key alone (already used for routing, not lookups)
-- Don't create a unique index on a non-partition-key column (PostgreSQL limitation:
--   unique constraints must include the partition key in partitioned tables)

-- Unique constraint on partitioned tables — the catch:
-- WRONG: unique constraint without partition key
CREATE UNIQUE INDEX ON transactions (id);
-- ERROR: insufficient columns in UNIQUE constraint definition
-- A unique index on a partitioned table must include ALL partition key columns

-- RIGHT: include partition key
CREATE UNIQUE INDEX ON transactions (id, created_at);
-- Now unique within each (id, created_at) combination — across all partitions
-- This means id alone is NOT globally unique in the index sense
-- Workaround: use UUID for id (probability of collision negligible)
--             or enforce uniqueness in application logic
```

## Section 5: Operational Benefits Beyond Query Performance

**Q8. How does partitioning improve data lifecycle management — specifically bulk deletes, archival, and VACUUM performance — and why is this often more valuable than query speed improvement in production?**
A: In production fintech systems, the operational benefits of partitioning often exceed the query performance benefits. Specifically: dropping old data, maintenance operations, and space reclamation are dramatically more efficient with partitioned tables:

**Bulk delete vs. partition drop:**
```sql
-- SCENARIO: purge transactions older than 2 years for storage cost reduction
-- Table: 500GB transactions table, 24 months of data

-- WITHOUT partitioning: DELETE statement
DELETE FROM transactions
WHERE created_at < NOW() - INTERVAL '2 years';

-- What this does:
-- 1. Scans potentially millions of rows to find matches
-- 2. Marks each matching row as dead (PostgreSQL MVCC — rows not immediately removed)
-- 3. Acquires row-level locks for each deleted row
-- 4. Writes WAL (Write-Ahead Log) entries for each deleted row
-- 5. Table bloat: dead rows remain until VACUUM cleans them
-- 6. VACUUM must scan the entire table to find dead rows
-- Cost: hours of DB load, table bloat, VACUUM pressure, locks blocking other queries

-- WITH partitioning: DROP TABLE on the old partition
DROP TABLE transactions_2022_01;  -- Drops the January 2022 partition
DROP TABLE transactions_2022_02;  -- Drops the February 2022 partition
-- ...

-- What this does:
-- 1. Removes the data file from the filesystem (single OS operation)
-- 2. Removes the partition's entry from pg_inherits
-- 3. No individual row processing, no WAL per row, no VACUUM needed
-- Cost: milliseconds per partition, regardless of how many rows it contained
-- Equivalent to: rm /var/lib/postgresql/data/base/transactions_2022_01
-- The data file disappears instantly; space reclaimed immediately

-- For regulatory compliance (RBI: retain 5 years minimum):
-- Archive before dropping (NOT just delete):
-- 1. pg_dump the partition to S3 (compressed)
-- 2. DETACH the partition (makes it an independent table — still queryable if needed)
-- 3. After confirming S3 archive, DROP the detached table

-- DETACH is reversible (useful for audits — re-ATTACH the archived partition temporarily):
ALTER TABLE transactions DETACH PARTITION transactions_2022_01 CONCURRENTLY;
-- CONCURRENTLY: detaches without locking the parent table (Postgres 14+)
-- After detach: transactions_2022_01 is a standalone table, no longer part of transactions
-- Can be re-attached: ALTER TABLE transactions ATTACH PARTITION transactions_2022_01
--   FOR VALUES FROM ('2022-01-01') TO ('2022-02-01');
```

**VACUUM performance on partitioned tables:**
```sql
-- PostgreSQL's VACUUM reclaims space from dead rows (from UPDATEs and DELETEs)
-- AUTOVACUUM runs table-by-table based on dead row thresholds

-- WITHOUT partitioning:
-- AUTOVACUUM on a 500GB table: must scan all 500GB to find dead rows
-- Even if only 1% of rows are dead (5GB), AUTOVACUUM scans the entire 500GB
-- During AUTOVACUUM: table performance degrades slightly (I/O competition)
-- Duration: potentially hours for a very large table

-- WITH partitioning:
-- AUTOVACUUM runs per-partition (each partition is a separate table internally)
-- A busy partition (current month with many updates) is vacuumed frequently
-- An old partition (2022, read-only) is rarely vacuumed (no dead rows accumulate)
-- Each VACUUM run covers only one partition — typically 5-20GB instead of 500GB
-- Duration: minutes per partition

-- The dead row accumulation pattern in fintech:
-- Current month partition: many updates (status changes: PENDING → SUCCESS/FAILED)
--   → High dead row accumulation → AUTOVACUUM runs frequently → partition stays healthy
-- Older partitions: mostly reads (reconciliation, reporting) → few dead rows
--   → AUTOVACUUM runs rarely → no I/O pressure on historical data

-- Monitoring partition-level bloat:
SELECT
  child.relname          AS partition_name,
  pg_size_pretty(pg_relation_size(child.oid)) AS live_size,
  pg_size_pretty(pg_total_relation_size(child.oid) - pg_relation_size(child.oid)) AS index_size,
  n_dead_tup,
  n_live_tup,
  ROUND(n_dead_tup::NUMERIC / NULLIF(n_live_tup, 0) * 100, 1) AS dead_pct,
  last_autovacuum
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child  ON pg_inherits.inhrelid  = child.oid
JOIN pg_stat_user_tables stats ON stats.relname = child.relname
WHERE parent.relname = 'transactions'
ORDER BY dead_pct DESC NULLS LAST;
```

**Q9. How do you safely add a partition to a live production table, backfill historical data into a new partition scheme, and validate the migration?**
A: Migrating an existing unpartitioned table to a partitioned one without downtime is one of the most operationally complex database migrations in production fintech. The correct approach uses a combination of logical replication, gradual cutover, and validation:

```sql
-- SCENARIO: Convert an existing 500GB 'transactions' table to monthly partitioned
-- Constraint: zero downtime; cannot stop writes during migration

-- Phase 1: Create the new partitioned table structure (parallel to the existing table)
CREATE TABLE transactions_partitioned (
  LIKE transactions INCLUDING ALL  -- Copy columns, constraints, defaults
) PARTITION BY RANGE (created_at);

-- Create partitions for all existing data
-- Discover the date range of existing data:
SELECT MIN(created_at), MAX(created_at) FROM transactions;
-- Result: 2022-03-15 to 2024-11-20

-- Create monthly partitions from 2022-03 to 2025-02 (with 3 months lookahead)
-- Run the partition creation script (generated dynamically):
DO $$
DECLARE
  month_start DATE := '2022-03-01';
  month_end   DATE := '2025-03-01';
  current_month DATE;
BEGIN
  current_month := month_start;
  WHILE current_month < month_end LOOP
    EXECUTE format(
      'CREATE TABLE IF NOT EXISTS transactions_partitioned_%s
       PARTITION OF transactions_partitioned
       FOR VALUES FROM (%L) TO (%L)',
      TO_CHAR(current_month, 'YYYY_MM'),
      current_month,
      current_month + INTERVAL '1 month'
    );
    current_month := current_month + INTERVAL '1 month';
  END LOOP;
END $$;

-- Phase 2: Backfill historical data in batches (avoid locking the source table)
-- Copy 1 month at a time to avoid long transactions
INSERT INTO transactions_partitioned
SELECT * FROM transactions
WHERE created_at >= '2022-03-01' AND created_at < '2022-04-01';
-- Repeat for each month up to the last complete month

-- Phase 3: Handle in-flight data (rows written to old table during backfill)
-- Option A: Trigger on old table that dual-writes to new table
CREATE OR REPLACE FUNCTION mirror_to_partitioned()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO transactions_partitioned VALUES (NEW.*);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER mirror_insert
AFTER INSERT ON transactions
FOR EACH ROW EXECUTE FUNCTION mirror_to_partitioned();

-- Phase 4: Cutover
-- 1. Short maintenance window (seconds, not minutes):
BEGIN;
  -- Rename old table
  ALTER TABLE transactions RENAME TO transactions_old;
  -- Rename new partitioned table
  ALTER TABLE transactions_partitioned RENAME TO transactions;
  -- Drop the mirror trigger (no longer needed)
  DROP TRIGGER mirror_insert ON transactions_old;
COMMIT;

-- 2. Verify application queries against the new table
-- 3. Keep transactions_old for 1 week as rollback option
-- 4. After validation: DROP TABLE transactions_old;

-- Phase 5: Validation queries
-- Verify row counts match
SELECT
  'old' AS source, COUNT(*) FROM transactions_old
UNION ALL
SELECT
  'new' AS source, COUNT(*) FROM transactions;
-- Must be equal (or new >= old due to dual-write window)

-- Verify no data in the default partition (coverage gap would route data there)
SELECT COUNT(*) FROM transactions_default;
-- Must be 0; any rows here = partition coverage gap

-- Verify partition pruning works
EXPLAIN SELECT * FROM transactions
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01';
-- Must show only transactions_2024_01 partition
```

## Section 6: Partitioning in Application Code

**Q10. How do partitioning decisions affect TypeORM queries, what mistakes in ORM usage silently defeat partition pruning, and how do you enforce correct query patterns?**
A: ORMs abstract away SQL details — but this abstraction can silently produce queries that defeat partition pruning. Understanding the SQL generated by your ORM is essential for partitioned tables:

```typescript
// TypeORM entity for a partitioned table — no special annotation needed
// TypeORM treats partitioned tables like regular tables
@Entity('transactions')
export class Transaction {
  @PrimaryColumn('uuid')
  id: string;

  @Column({ name: 'user_id' })
  userId: string;

  @Column({ name: 'loan_id', nullable: true })
  loanId: string | null;

  @Column({ type: 'bigint' })
  amount: number;

  @Column({ name: 'created_at', type: 'timestamptz' })
  createdAt: Date;

  @Column()
  status: string;
}

// ─────────────────────────────────────────────────────────
// WRONG patterns — silently defeat partition pruning
// ─────────────────────────────────────────────────────────

// WRONG 1: No date filter → full table scan across all partitions
@Injectable()
export class TransactionService {
  async getUserTransactions(userId: string): Promise<Transaction[]> {
    return this.txRepo.find({ where: { userId } });
    // SQL: SELECT * FROM transactions WHERE user_id = $1
    // → No created_at filter → ALL partitions scanned
    // At 24 monthly partitions: 24 index scans on user_id index
  }

  // WRONG 2: Date function applied to column → no pruning
  async getJanuaryTransactions(userId: string): Promise<Transaction[]> {
    return this.txRepo
      .createQueryBuilder('tx')
      .where('tx.userId = :userId', { userId })
      .andWhere("DATE_TRUNC('month', tx.createdAt) = :month", { month: '2024-01-01' })
      // ↑ DATE_TRUNC on the partition key → no pruning
      .getMany();
  }

  // WRONG 3: Ordering without date filter → full scan then sort
  async getRecentTransactions(userId: string, limit: number): Promise<Transaction[]> {
    return this.txRepo.find({
      where: { userId },
      order: { createdAt: 'DESC' },
      take: limit,
    });
    // SQL: SELECT * FROM transactions WHERE user_id = $1 ORDER BY created_at DESC LIMIT $2
    // → Must scan ALL partitions to find the LIMIT most recent rows
    // → PostgreSQL can optimize with "Merge Append" across partitions but still reads all
  }
}

// ─────────────────────────────────────────────────────────
// CORRECT patterns — enable partition pruning
// ─────────────────────────────────────────────────────────

@Injectable()
export class TransactionService {
  // CORRECT 1: Always include a date range filter
  async getUserTransactions(
    userId: string,
    from: Date,
    to: Date,
  ): Promise<Transaction[]> {
    return this.txRepo.find({
      where: {
        userId,
        createdAt: Between(from, to),  // TypeORM Between → BETWEEN clause → pruning works
      },
      order: { createdAt: 'DESC' },
    });
    // SQL: SELECT * FROM transactions
    //      WHERE user_id = $1 AND created_at BETWEEN $2 AND $3
    //      ORDER BY created_at DESC
    // → Partition pruning: only partitions overlapping [from, to] are scanned ✓
  }

  // CORRECT 2: Range comparison instead of function on column
  async getTransactionsByMonth(userId: string, year: number, month: number) {
    const from = new Date(year, month - 1, 1);        // First day of month
    const to   = new Date(year, month, 1);             // First day of next month

    return this.txRepo.find({
      where: {
        userId,
        createdAt: Between(from, to),
      },
    });
    // SQL: WHERE created_at >= $1 AND created_at < $2
    // → Direct comparison, no function → pruning works ✓
  }

  // CORRECT 3: Recent transactions with explicit lookback window
  async getRecentTransactions(
    userId: string,
    limit: number,
    lookbackDays = 90,  // Default: only look in last 90 days
  ): Promise<Transaction[]> {
    const from = new Date(Date.now() - lookbackDays * 24 * 60 * 60 * 1000);

    return this.txRepo.find({
      where: {
        userId,
        createdAt: MoreThan(from),  // TypeORM MoreThan → > comparison → pruning works
      },
      order: { createdAt: 'DESC' },
      take: limit,
    });
    // SQL: WHERE user_id = $1 AND created_at > $2 ORDER BY created_at DESC LIMIT $3
    // → Pruning: only partitions newer than (NOW - 90 days) ✓
    // → Max 3 monthly partitions scanned regardless of total history
  }

  // Repository method that enforces the partition key contract at the type level
  async findWithDateRange(
    filter: {
      userId?: string;
      loanId?: string;
      status?: string;
    },
    dateRange: { from: Date; to: Date },  // ← Required parameter, not optional
    pagination: { page: number; pageSize: number },
  ): Promise<[Transaction[], number]> {
    // dateRange is required — cannot call this method without a date range
    // Enforces the partition key filter at the API contract level
    const qb = this.txRepo.createQueryBuilder('tx')
      .where('tx.createdAt >= :from AND tx.createdAt < :to', dateRange);

    if (filter.userId) qb.andWhere('tx.userId = :userId', { userId: filter.userId });
    if (filter.loanId) qb.andWhere('tx.loanId = :loanId', { loanId: filter.loanId });
    if (filter.status) qb.andWhere('tx.status = :status', { status: filter.status });

    return qb
      .orderBy('tx.createdAt', 'DESC')
      .skip((pagination.page - 1) * pagination.pageSize)
      .take(pagination.pageSize)
      .getManyAndCount();
  }
}
```

## Section 7: Partitioning Trade-offs and Anti-patterns

**Q11. What are the situations where partitioning hurts performance rather than helping, and how do you decide whether to partition a given table?**
A: Partitioning is not universally beneficial. There are concrete scenarios where it adds overhead without compensating benefits, and the decision to partition should be based on specific criteria rather than applied reflexively to large tables:

```
When partitioning HURTS performance:

Anti-pattern 1 — Queries that never filter by the partition key:
  Table partitioned by created_at; most queries filter by user_id only.
  Result: every query scans ALL partitions (no pruning possible).
  Cost: N partition manager lookups + N index scans instead of 1.
  Overhead: partition routing layer adds latency to every query.
  Fix: don't partition by created_at; partition by user_id HASH, or don't partition.

Anti-pattern 2 — Table is too small:
  Partitioning a 10GB table into 12 monthly partitions = ~833MB per partition.
  The entire table fits in PostgreSQL's shared_buffers (typically 25% of RAM).
  The non-partitioned table never touches disk; partition routing adds overhead.
  Rule: partition tables over 50-100GB; smaller tables benefit from better indexing.

Anti-pattern 3 — High-cardinality partition key with too many partitions:
  Partitioning by user_id LIST with 10 million users = 10 million partitions.
  Each partition is tiny; partition management overhead dominates.
  PostgreSQL struggles with thousands of partitions (planning overhead).
  Rule: aim for 50-500 partitions; use HASH partitioning for high-cardinality keys.

Anti-pattern 4 — Frequent cross-partition queries in reports:
  Finance report: "Total revenue across all months for the past 5 years."
  Must scan all 60 monthly partitions — sequential, no pruning benefit.
  Overhead: 60 partition plan nodes vs. 1 table plan node.
  Fix: maintain a pre-aggregated reporting table (materialized view or summary table)
       updated hourly; reports hit the summary table, not the partitioned base.

Anti-pattern 5 — Partition key updates (rows moving between partitions):
  If a transaction's created_at can change (unlikely but consider status timestamps):
  UPDATE transactions SET created_at = ... WHERE id = ?
  → PostgreSQL must DELETE from old partition + INSERT into new partition
  → More expensive than a simple UPDATE on an unpartitioned table
  → Generates more WAL; holds two partition locks simultaneously
  Rule: the partition key should be an immutable column (creation time, not update time).

Partitioning decision criteria:
```
```typescript
function shouldPartition(table: TableStats): PartitionDecision {
  // Rule 1: Table size threshold
  if (table.sizeGB < 50) {
    return { partition: false, reason: 'Table too small — improve indexing instead' };
  }

  // Rule 2: Query pattern check — partition key must appear in most queries
  const queriesWithPartitionKey = table.queryPatterns
    .filter(q => q.whereClause.includes(table.proposedPartitionKey));
  const pruningCoverage = queriesWithPartitionKey.length / table.queryPatterns.length;

  if (pruningCoverage < 0.5) {
    return {
      partition: false,
      reason: `Only ${Math.round(pruningCoverage * 100)}% of queries filter by ` +
              `${table.proposedPartitionKey} — pruning won't help most queries`,
    };
  }

  // Rule 3: Data distribution — partitions should be roughly equal size
  // (a partition with 90% of data = no pruning benefit for most queries)
  if (table.proposedStrategy === 'RANGE') {
    const monthlyVariance = calculateMonthlyVariance(table.rowsByMonth);
    if (monthlyVariance > 5.0) { // High variance (5× difference between busiest and quietest)
      return {
        partition: true,
        reason: 'Partition but monitor for hot partition imbalance',
        warning: 'High monthly variance — some partitions much larger than others',
      };
    }
  }

  // Rule 4: Lifecycle management benefit
  const hasRetentionRequirement = table.retentionPolicyMonths !== null;
  const deletionCostHigh = table.sizeGB > 100;

  if (hasRetentionRequirement && deletionCostHigh) {
    return {
      partition: true,
      reason: 'DROP PARTITION is dramatically faster than DELETE for retention policy',
    };
  }

  return { partition: true, reason: 'Meets size and query pattern criteria' };
}
```

**Q12. Scenario: "The transactions table in your fintech platform has grown to 800GB and the nightly reconciliation job that aggregates daily totals now takes 4 hours. Design the partitioning strategy end-to-end."**
A: This is a complete design exercise that ties together all the partitioning concepts:

```
Step 1 — Diagnose the current problem:

  Slow reconciliation query:
  SELECT
    DATE(created_at) AS date,
    status,
    SUM(amount)      AS total,
    COUNT(*)         AS count
  FROM transactions
  WHERE created_at >= CURRENT_DATE - INTERVAL '1 day'
    AND created_at <  CURRENT_DATE
    AND status IN ('SUCCESS', 'FAILED')
  GROUP BY DATE(created_at), status;

  EXPLAIN output (current 800GB table):
  Seq Scan on transactions (cost=0..82000000 rows=45000000)
  Filter: (created_at >= ... AND created_at < ... AND status IN ...)
  Rows removed by filter: 43,500,000
  → Full table scan; filter removes 96.7% of rows = mostly wasted I/O

  Root cause: 800GB table with no partitioning; 96.7% of I/O wasted on irrelevant dates.
  Query only needs yesterday's ~21GB of data; reads all 800GB.

Step 2 — Choose the partitioning strategy:

  Option A: Monthly RANGE on created_at
    + Reconciliation job: only scans yesterday's partition (~21GB instead of 800GB)
    + DROP PARTITION for data older than 5 years (RBI retention)
    + Maintenance operations (VACUUM, REINDEX) run per-partition
    - Cross-partition queries (annual reports) scan 12 partitions
    Monthly partition size: 800GB / 48 months ≈ 16-17GB per partition ✓

  Option B: Daily RANGE on created_at
    + Even smaller partitions for reconciliation (~700MB/day)
    - 1,440+ partitions for 4 years → PostgreSQL planning overhead
    - Too many partitions; management complexity excessive
    ✗ Daily partitioning at this scale is an anti-pattern

  Option C: Hash on user_id
    + Even distribution; user-centric queries fast
    - Reconciliation job (date-based aggregate) scans ALL hash partitions
    ✗ Wrong strategy for date-based analytics

  Decision: Monthly RANGE on created_at — best fit for the reconciliation access pattern.

Step 3 — Implementation plan:

  Week 1: Create new partitioned table structure (alongside existing table)
    - CREATE TABLE transactions_v2 PARTITION BY RANGE (created_at)
    - Create monthly partitions from oldest data through current month + 3 months ahead
    - Create all indexes on the partitioned table parent

  Week 2: Backfill historical data (month by month, off-peak hours)
    - INSERT INTO transactions_v2 SELECT * FROM transactions WHERE created_at in [month]
    - One month per night; 48 months total = 48 nights
    - Or: parallelize across multiple months simultaneously if I/O budget allows
    - Add mirror trigger to capture new writes to both tables during backfill

  Week 3: Validation
    - Row count comparison: old vs. new must be equal
    - Sample query: run reconciliation against both; compare results
    - EXPLAIN on key queries: verify partition pruning in execution plan
    - Load test: run application against new table; measure performance

  Week 4: Cutover
    - Maintenance window (2 minutes): RENAME old table; RENAME new table
    - Monitor: query latencies, partition pruning hit rate, DB CPU
    - Keep old table for 1 week as rollback

Step 4 — Post-migration: the reconciliation job improvement:

  Before partitioning:
    Seq Scan on transactions (800GB): ~4 hours
    I/O: 800GB × 4 passes (sort + hash agg) = 3,200GB I/O

  After partitioning (query targeting yesterday):
    Seq Scan on transactions_2024_11 (17GB): ~5 minutes
    Partition pruning: only November partition is relevant
    I/O: 17GB × 2 passes = 34GB I/O
    Improvement: ~48× reduction in I/O → ~48× faster = from 4 hours to 5 minutes

Step 5 — Optimize the query further (compound improvement):

  -- The reconciliation query uses DATE() on the partition key — defeats pruning within partition
  -- Fix: use range instead of DATE()
  SELECT
    created_at::DATE AS date,  -- Cast in SELECT is OK; it's the WHERE that matters
    status,
    SUM(amount) AS total,
    COUNT(*)    AS count
  FROM transactions
  WHERE created_at >= CURRENT_DATE - INTERVAL '1 day'  -- Direct comparison ✓
    AND created_at <  CURRENT_DATE                      -- Direct comparison ✓
    AND status IN ('SUCCESS', 'FAILED')
  GROUP BY created_at::DATE, status;

  -- Add a partial index for the reconciliation access pattern:
  CREATE INDEX idx_tx_reconciliation
    ON transactions (created_at, status)
    WHERE status IN ('SUCCESS', 'FAILED');
  -- With partitioning + this index: reconciliation may use index scan instead of seq scan
  -- Index covers: created_at (pruning), status (filter), both columns in the index = index-only scan
  -- Final estimate: 5 minutes → 30 seconds for yesterday's reconciliation
```

## Quick Reference Table

| Strategy | Partition By | Pruning Works When | Best For | Avoid When |
|---|---|---|---|---|
| **Range** | Continuous values (date, ID range) | WHERE includes range comparison on partition key | Time-series, audit logs, transactions | Queries rarely filter by partition key |
| **List** | Discrete values (country, tenant, status) | WHERE has equality on partition key | Multi-tenant, geographic compliance | Many distinct values (>100 tenants) |
| **Hash** | Any column (hashed to N buckets) | WHERE has equality on partition key | Even distribution, user-centric data | Range queries on partition key |
| **Composite** | Two dimensions (range + hash) | WHERE includes both dimensions | Very large tables needing two-level pruning | Complexity isn't justified by table size |
