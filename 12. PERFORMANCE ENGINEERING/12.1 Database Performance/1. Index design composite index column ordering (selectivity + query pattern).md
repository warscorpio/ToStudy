# Database (Performance): Index Design — Composite Index Column Ordering — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a database index, and what data structure does PostgreSQL use for the default index type?**
A: An index is a separate data structure that the database maintains alongside the table, built from the values of one or more columns. It exists to answer a specific class of question — "which rows have this column value?" — without scanning every row in the table (a sequential scan). The trade-off: indexes consume disk space and must be kept up-to-date on every write (`INSERT`, `UPDATE`, `DELETE`), in exchange for dramatically faster reads on the indexed columns.

PostgreSQL's default index type is a **B-tree** (balanced tree). The B-tree stores index entries in sorted order — each internal node contains key values and pointers to child nodes; each leaf node contains key values and pointers (TIDs — tuple identifiers) to the actual heap rows. Because the keys are sorted, the B-tree supports:
- **Equality** (`=`) — locate a key in O(log n).
- **Range** (`>`, `<`, `>=`, `<=`, `BETWEEN`) — traverse the sorted leaf level.
- **Prefix matching** (`LIKE 'abc%'`) — find the first matching key, then scan forward.
- **`IS NULL`** — B-tree stores NULL values and can satisfy `IS NULL` and `IS NOT NULL`.
- **Ordering** (`ORDER BY`) — if the query's sort order matches the index order, the planner can return rows in order without a sort step.

Other PostgreSQL index types: GIN (for full-text search, arrays, JSONB), GiST (geometric types, full-text), BRIN (very large tables with physical column correlation — e.g., time-series data), Hash (equality only, rarely used).

**Q2. What is a composite index, and why is the order of columns in its definition critical?**
A: A composite index (also called a multi-column index) is an index built on two or more columns together. PostgreSQL's B-tree composite index sorts entries first by the first column, then by the second column within each first-column value, then by the third, and so on — exactly like sorting a table of names: first by last name, then first name within each last name group.

```sql
CREATE INDEX idx_loans_status_user ON loan_applications (status, user_id);
```

This index stores entries sorted as:
```
(approved, user-001)
(approved, user-003)
(approved, user-007)
(pending,  user-002)
(pending,  user-004)
(rejected, user-001)
(rejected, user-005)
```

**Why column order is critical — the leftmost prefix rule:**
A composite index can only be used if the query references the index columns from left to right, with no gaps, until either all columns are referenced or a range condition is encountered. For `idx_loans_status_user (status, user_id)`:

```sql
-- Uses the index fully (equality on both columns)
WHERE status = 'approved' AND user_id = 'user-001'

-- Uses the index partially (equality on first column only)
WHERE status = 'approved'

-- CANNOT use the index at all
WHERE user_id = 'user-001'
-- (skipping 'status' — the leftmost column — makes the index unusable
-- because the B-tree is sorted by status first; without fixing status,
-- matching user_ids are scattered throughout the entire index)

-- Uses the index for status filtering, then filters user_id in memory
WHERE status > 'p' AND user_id = 'user-001'
-- (range on status exhausts the index's ability to narrow by user_id)
```

The leftmost prefix rule is the single most important fact about composite indexes. Column order is not a stylistic choice — it determines which queries the index can serve.

**Q3. What is selectivity, how do you measure it, and why does it matter for index design?**
A: Selectivity is the proportion of rows a condition eliminates — how many rows match the condition relative to the total number of rows. A highly selective condition matches very few rows (eliminates most); a low-selectivity condition matches many rows (eliminates few).

Formally: `selectivity = (distinct values) / (total rows)`, or equivalently `1 / number_of_distinct_values` for a given value. A column with 1,000,000 distinct values in a 1,000,000-row table has selectivity ≈ 1.0 (high — each value appears once on average). A boolean column has selectivity ≈ 0.5 (or heavily skewed — `is_active = true` might match 99% of rows, making it essentially non-selective).

**Measuring selectivity in PostgreSQL:**
```sql
-- Approximate distinct value count (fast — uses statistics)
SELECT n_distinct FROM pg_stats
WHERE tablename = 'loan_applications' AND attname = 'status';
-- Positive value = estimated count; negative value = fraction of total rows

-- Exact selectivity for a specific value
SELECT
  COUNT(*)                                            AS matching_rows,
  (SELECT COUNT(*) FROM loan_applications)            AS total_rows,
  COUNT(*) * 1.0 / (SELECT COUNT(*) FROM loan_applications) AS selectivity
FROM loan_applications
WHERE status = 'approved';

-- MCV (Most Common Values) — shows distribution
SELECT most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'loan_applications' AND attname = 'status';
```

**Why selectivity matters for index design:**

High selectivity columns are good index candidates — using them narrows the result set dramatically. Low selectivity columns are poor candidates — a query on `is_active = true` in a table where 99% of rows are active will still result in a near-full table scan even with an index (the planner will likely choose a sequential scan because fetching 99% of rows via random I/O from an index is slower than reading the table sequentially).

**Selectivity in composite indexes:** the common guidance is "put the most selective column first." This is correct for a specific query pattern but is actually a simplification — the full rule is more nuanced, as Q4 and Q5 explore.

## Section 2: Column Ordering — The Full Decision Framework

**Q4. When should you put the high-selectivity column first vs. the low-selectivity column first in a composite index?**
A: The "put high-selectivity first" rule is a heuristic that holds when all conditions are equality conditions. The complete decision framework depends on the query pattern:

**Case 1 — All equality conditions (`=` on all columns):**
```sql
-- Query
WHERE status = 'approved' AND user_id = 'user-001'
```
For pure equality, either column order works — the planner can use the index regardless of which comes first (because fixing either column lets the B-tree narrow to a contiguous range). Here, putting the higher-selectivity column first (`user_id`) provides a marginally better first-level filter, but the difference is small because both conditions are applied.

**Case 2 — One equality, one range:**
```sql
-- Query A
WHERE status = 'approved' AND created_at > '2025-01-01'

-- Query B
WHERE user_id = 'user-001' AND created_at > '2025-01-01'
```
The equality column must come before the range column in the index. Once a range condition is applied, the index can no longer efficiently filter subsequent columns (they are no longer in a contiguous sorted range):

```sql
-- CORRECT for Query A: equality first, range second
CREATE INDEX idx ON loan_applications (status, created_at);

-- WRONG for Query A: range first
CREATE INDEX idx ON loan_applications (created_at, status);
-- Planner must either: use the index only for the date range (missing status filter),
-- or ignore the index entirely
```

**Case 3 — Equality filter + ORDER BY:**
```sql
-- Query: list a user's loans, newest first
WHERE user_id = 'user-001' ORDER BY created_at DESC
```
Put the equality column first, the ORDER BY column second:
```sql
CREATE INDEX idx ON loan_applications (user_id, created_at DESC);
```
This lets the planner use the index for both filtering (fixed `user_id`) and ordering (the remaining index entries are already sorted by `created_at`) — eliminating a sort step entirely.

**Case 4 — Only a range condition (no equality prefix):**
```sql
WHERE created_at > '2025-01-01'
```
A single-column index on `created_at` is appropriate here. No composite index can help — there's no equality column to put first.

**The unified rule:** equality conditions go first (in descending order of selectivity among equals), range conditions and ORDER BY columns go last. This is the "ESR" rule popularised by the MongoDB documentation but equally applicable to PostgreSQL B-trees: **E**quality, **S**electivity (within equals), **R**ange.

**Q5. Walk through a concrete fintech example — designing a composite index for a loan application query.**
A: Consider a loans platform with this query pattern (a common query from a loan officer's dashboard):

```sql
SELECT id, applicant_name, amount, status, created_at
FROM loan_applications
WHERE
  status        = 'pending'         -- low selectivity: 3 values (pending, approved, rejected)
  AND branch_id = 'branch-mumbai'   -- medium selectivity: ~50 branches
  AND assigned_to = 'officer-raj'   -- higher selectivity: ~200 officers
  AND created_at >= '2025-08-01'    -- range condition
ORDER BY created_at ASC;
```

**Step 1 — Identify condition types:**
- `status = 'pending'` → equality, low selectivity (~33% of rows)
- `branch_id = 'branch-mumbai'` → equality, medium selectivity (~2% of rows)
- `assigned_to = 'officer-raj'` → equality, higher selectivity (~0.5% of rows)
- `created_at >= '2025-08-01'` → range condition
- `ORDER BY created_at ASC` → sort (same column as range)

**Step 2 — Apply the ESR rule:**
All equality conditions come first, in descending selectivity order (most selective first). Then the range/sort column:

```sql
-- Optimal index
CREATE INDEX idx_loans_dashboard ON loan_applications
  (assigned_to, branch_id, status, created_at);
```

Why this order?
- `assigned_to` first — most selective equality; immediately narrows to ~0.5% of rows.
- `branch_id` second — further narrows within `assigned_to`'s result.
- `status` third — further narrows; lowest selectivity among the equality columns.
- `created_at` last — range condition applied after equalities fix a contiguous range; ORDER BY can use the index order without a sort step.

**Step 3 — Verify with EXPLAIN:**
```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, applicant_name, amount, status, created_at
FROM loan_applications
WHERE status = 'pending'
  AND branch_id = 'branch-mumbai'
  AND assigned_to = 'officer-raj'
  AND created_at >= '2025-08-01'
ORDER BY created_at ASC;
```

Expected plan with the correct index:
```
Index Scan using idx_loans_dashboard on loan_applications
  Index Cond: ((assigned_to = 'officer-raj') AND (branch_id = 'branch-mumbai')
               AND (status = 'pending') AND (created_at >= '2025-08-01'))
  Rows Removed by Filter: 0
  Buffers: shared hit=4
```
No sort step, no filter rows removed — the index serves the entire query including the ORDER BY.

**Step 4 — What if the query varies?**
If the same table is also queried as:
```sql
-- Query 2: by branch only
WHERE branch_id = 'branch-mumbai' AND created_at >= '2025-08-01'

-- Query 3: by status only
WHERE status = 'pending' ORDER BY created_at
```
Query 2 can use `idx_loans_dashboard` partially (it starts with `assigned_to` which is missing — index not usable unless `assigned_to` is included). Consider a separate index for Query 2:
```sql
CREATE INDEX idx_loans_branch_date ON loan_applications (branch_id, created_at);
```
Index proliferation is the trade-off — each additional index is a write overhead. Two targeted indexes often beat one index trying to serve all queries.

**Q6. What is the "index skip scan" or "loose index scan," and when does PostgreSQL use it?**
A: A skip scan (called "loose index scan" in MySQL documentation) is an optimisation where the planner scans an index for a range of values in a non-leading column without requiring an equality condition on the leading column. PostgreSQL introduced index skip scans for specific cases in recent versions, but support is limited — understanding when it applies and when it doesn't is the nuance.

**When the planner can avoid full table scans on non-leading columns:**

```sql
-- Index: (status, created_at)
-- Query: only filtering on created_at, not status
WHERE created_at >= '2025-08-01'
```

Without skip scan: the planner ignores the composite index (can't efficiently use it without `status`), does a sequential scan or uses a separate single-column index on `created_at`.

With skip scan (when the planner supports it for this index/query): the planner conceptually treats this as multiple index scans — one for each distinct value of `status`:
```
Scan index for status = 'approved' AND created_at >= '2025-08-01'
UNION ALL
Scan index for status = 'pending'  AND created_at >= '2025-08-01'
UNION ALL
Scan index for status = 'rejected' AND created_at >= '2025-08-01'
```

**PostgreSQL's current reality:** PostgreSQL does not have a general index skip scan as of PostgreSQL 16. It supports a limited form via `VALUES` or `IN` lists that the planner can expand, and for `GROUP BY` on the leading column in specific cases (index-only scans with aggregate functions). MySQL 8.0 introduced a more general skip scan. PostgreSQL's equivalent recommendation is to use a separate index on `created_at` or to include `status` in the query's `IN` clause:

```sql
-- Workaround: make the leading column's values explicit
WHERE status IN ('approved', 'pending', 'rejected') AND created_at >= '2025-08-01'
-- Planner expands this to N index range scans — effectively a skip scan
```

This is important to know in interviews: don't assume PostgreSQL will optimise away a missing leading column. Design indexes for the actual queries, and add separate indexes for access patterns that don't share a leading column.

## Section 3: Selectivity Deep-Dive and the Planner's View

**Q7. How does PostgreSQL's query planner use column statistics to choose between a sequential scan and an index scan?**
A: The planner is a cost-based optimiser — it estimates the cost of each candidate plan in abstract units (proportional to I/O and CPU time) and chooses the cheapest. The key statistics it uses are maintained by `ANALYZE` (run automatically by autovacuum) and stored in `pg_statistic` / `pg_stats`.

**Key statistics used:**
- `n_distinct` — estimated number of distinct values in the column.
- `most_common_vals` / `most_common_freqs` — the top N most common values and their frequencies. Used to estimate selectivity for equality conditions on common values.
- `histogram_bounds` — bucket boundaries for the remaining (non-common) values. Used to estimate selectivity for range conditions.
- `correlation` — correlation between physical row order and column value order (1.0 = perfectly correlated, 0 = random). High correlation means an index scan has low I/O cost (rows are physically close); low correlation means random I/O (index scan may be more expensive than sequential scan even for a selective query).

**Cost estimation for an index scan:**

```
index_scan_cost ≈ (index pages to scan) + (heap pages to fetch × random_page_cost)
seq_scan_cost   ≈ (total table pages × seq_page_cost)
```

`random_page_cost` defaults to 4.0 (4× more expensive than sequential I/O). For SSDs and modern cloud storage, setting `random_page_cost = 1.1` to `1.5` more accurately reflects hardware cost and causes the planner to favour index scans more aggressively:

```sql
-- Session-level (for testing)
SET random_page_cost = 1.1;

-- Server-wide (in postgresql.conf or RDS parameter group)
random_page_cost = 1.1
```

**The breakeven point:** the planner switches from index scan to sequential scan when fetching the index-matched rows requires reading more than roughly 5–10% of the table (with default `random_page_cost = 4.0`). On SSDs this breakeven is higher — an index scan is viable for 20–30% of the table. Mismatched `random_page_cost` is a common cause of the planner choosing sequential scans when indexes exist and are appropriate.

**Q8. What is a covering index, and how does it eliminate heap fetches entirely?**
A: A covering index is one that contains all the columns needed to answer a query — the planner can return the result from the index alone without reading the heap (the main table storage). PostgreSQL calls this an **index-only scan**.

```sql
-- Query
SELECT id, status, created_at, amount
FROM loan_applications
WHERE user_id = 'user-001' AND status = 'pending';

-- Base index (not covering)
CREATE INDEX idx_loans_user_status ON loan_applications (user_id, status);
-- Planner must fetch heap rows to get 'id', 'created_at', 'amount' → Index Scan

-- Covering index (index-only scan possible)
CREATE INDEX idx_loans_user_status_covering ON loan_applications
  (user_id, status)
  INCLUDE (id, created_at, amount);
-- Planner gets 'id', 'created_at', 'amount' from the index leaf pages → Index Only Scan
```

The `INCLUDE` clause (PostgreSQL 11+) adds columns to the leaf level of the B-tree without making them part of the sort key. This means:
- `INCLUDE` columns can be used in index-only scans (covering).
- `INCLUDE` columns cannot be used as filter conditions or for ordering.
- `INCLUDE` columns increase the index size (leaf pages are larger) but have minimal impact on index maintenance cost (they're not in the internal nodes used for navigation).

**Index-only scan prerequisite — visibility map:** PostgreSQL tracks which heap pages have all-visible rows (no dead tuples) in the visibility map. An index-only scan can skip the heap fetch only for tuples on all-visible pages. Pages with recent writes or dead tuples require a heap visit to check visibility. This is why `VACUUM` matters for index-only scan performance — it updates the visibility map after dead tuple cleanup.

```sql
-- Check index-only scan eligibility
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, created_at, amount
FROM loan_applications
WHERE user_id = 'user-001' AND status = 'pending';

-- Look for: "Index Only Scan" vs "Index Scan"
-- Also check: "Heap Fetches: N" — if N > 0, some rows needed heap visibility check
```

**Q9. When does high selectivity not help — the correlation problem?**
A: A column can be highly selective (each value appears only once) but still cause an index scan to be expensive due to low physical correlation between index order and heap storage order.

**Example:** a UUID primary key has perfect selectivity (every value is unique) but near-zero correlation — UUIDs are randomly distributed, so rows with consecutive UUID values are scattered randomly across the heap. Fetching 1,000 rows by UUID may require 1,000 random disk reads (one per row, each on a different page). If the table has 10,000 pages and you need 1,000 rows, that's 1,000 random reads vs. 10,000 sequential reads — the index wins. But if you need 50,000 rows, random reads for 50,000 scattered rows may be slower than a sequential scan of 10,000 pages.

```sql
-- Check correlation
SELECT correlation FROM pg_stats
WHERE tablename = 'loan_applications' AND attname = 'created_at';
-- 0.95: highly correlated — rows were inserted in roughly chronological order
-- 0.02: low correlation — rows for this column are scattered

-- Check correlation for UUID
SELECT correlation FROM pg_stats
WHERE tablename = 'loan_applications' AND attname = 'id';
-- ≈ 0.0 — UUIDs are random; no correlation
```

**Practical implications:**
- `created_at` on an append-only table has high correlation (~1.0) — rows are physically stored in insertion order, which approximates time order. Index scans on `created_at` ranges are efficient because matching rows are in consecutive heap pages.
- `id UUID` with `gen_random_uuid()` has near-zero correlation — if you need many rows by UUID range, a sequential scan may be faster.
- `updated_at` on a frequently-updated table has low correlation — rows are updated in place (or via MVCC) so their physical order has no relationship to `updated_at` value order.

The `CLUSTER` command (or `pg_repack` for online reorganisation) physically reorders the heap to match an index, restoring correlation:
```sql
-- Physically sort the table by created_at order (takes a lock, use pg_repack in production)
CLUSTER loan_applications USING idx_loans_created_at;
```

## Section 4: Practical Index Design Patterns

**Q10. How do you design indexes for a time-series access pattern — e.g., "latest N records for a user"?**
A: Time-series queries are among the most common and most index-sensitive patterns in fintech applications — loan repayment history, transaction history, audit logs, notification logs.

```sql
-- Canonical query: last 20 disbursements for a user
SELECT id, amount, status, created_at
FROM disbursements
WHERE user_id = 'user-001'
ORDER BY created_at DESC
LIMIT 20;
```

**Index design:**
```sql
CREATE INDEX idx_disbursements_user_date ON disbursements
  (user_id, created_at DESC)
  INCLUDE (id, amount, status);
```

Why `DESC` on `created_at`? The B-tree can traverse in both directions, so `DESC` in the index definition is a hint to match the query's sort order, avoiding an implicit sort. If the query uses `ORDER BY created_at ASC`, define the index with `ASC` (or omit — `ASC` is the default). Mismatched sort direction requires a backward index scan which PostgreSQL supports but is slightly less efficient.

```sql
-- Verify: plan should show Index Only Scan + no Sort node
EXPLAIN (ANALYZE)
SELECT id, amount, status, created_at
FROM disbursements
WHERE user_id = 'user-001'
ORDER BY created_at DESC
LIMIT 20;

-- Ideal plan:
-- Limit
--   → Index Only Scan Backward on idx_disbursements_user_date
--       Index Cond: (user_id = 'user-001')
--       Buffers: shared hit=3
```

**Pagination with keyset (cursor-based) pagination:**
```sql
-- Page 1: latest 20
WHERE user_id = 'user-001'
ORDER BY created_at DESC, id DESC
LIMIT 20

-- Page 2: items before the last item of page 1
WHERE user_id = 'user-001'
  AND (created_at, id) < ('2025-08-10 12:00:00', 'last-id-from-page-1')
ORDER BY created_at DESC, id DESC
LIMIT 20
```

The composite sort `(created_at DESC, id DESC)` handles ties (multiple rows with the same `created_at`). Add `id` to the index:
```sql
CREATE INDEX idx_disbursements_user_cursor ON disbursements
  (user_id, created_at DESC, id DESC)
  INCLUDE (amount, status);
```

Keyset pagination is far more index-efficient than `OFFSET` — `OFFSET N` requires scanning and discarding N rows, which degrades linearly as the page number increases. Keyset pagination always reads exactly the next N rows using the index.

**Q11. How do you design indexes for multi-tenant fintech data where tenant isolation is the primary access pattern?**
A: In a multi-tenant lending platform, virtually every query is scoped to a tenant — a lender, an NBFC, or a product vertical. The tenant identifier belongs as the leading column of almost every composite index.

```sql
-- Every query implicitly includes tenant_id
SELECT * FROM loan_applications
WHERE tenant_id = 'nbfc-xyz'
  AND status = 'pending'
  AND assigned_to = 'officer-raj'
ORDER BY created_at DESC;

-- Index design: tenant_id always first
CREATE INDEX idx_loans_tenant_status_officer ON loan_applications
  (tenant_id, status, assigned_to, created_at DESC);
```

**Why tenant_id first despite being low-selectivity?**
`tenant_id` may be low selectivity globally (many rows per tenant) but it is the mandatory equality condition in every query — it's never absent. Putting it first ensures every query can use the index. Even if `tenant_id` is not the most selective column, it must be the leading column because:

1. Without `tenant_id` in the leading position, queries that don't specify `tenant_id` (which shouldn't exist, but bugs happen) would read data across tenants — a data isolation failure.
2. The planner uses the `tenant_id` condition to narrow to one tenant's portion of the index first; subsequent columns then narrow within that tenant's data.
3. If `tenant_id` is put after a higher-selectivity column, a query that only specifies `tenant_id` (e.g., "all pending applications for this tenant") cannot use the index at all.

This is the case where the query pattern overrides the pure selectivity heuristic — the column that appears in every query must be the leading column, regardless of its individual selectivity.

**Q12. How do partial indexes improve index size and query performance for skewed data distributions?**
A: A partial index is an index with a `WHERE` clause — it only indexes rows that satisfy the condition. This is powerful when a small subset of rows is responsible for the majority of queries.

```sql
-- Problem: most queries about loans focus on 'pending' and 'under_review' status
-- 95% of loans are 'closed' or 'rejected' — indexing them is wasted space
-- and slows down writes on those rows

-- Full index — indexes all 1M rows
CREATE INDEX idx_loans_status_full ON loan_applications (status, created_at);

-- Partial index — indexes only the 50K active loans
CREATE INDEX idx_loans_active ON loan_applications (created_at, assigned_to)
WHERE status IN ('pending', 'under_review');
```

**Benefits:**
- Index is 95% smaller (50K vs 1M entries) — fits in memory more readily, fewer I/O operations.
- Write overhead only for rows that satisfy the condition — `INSERT` of a `closed` loan doesn't touch this index at all.
- More targeted statistics — the planner's estimates are based on the active subset only, which is more accurate.

**The query must include the partial index condition for the planner to use it:**
```sql
-- Uses the partial index (condition matches WHERE clause)
SELECT * FROM loan_applications
WHERE status IN ('pending', 'under_review')
  AND created_at > '2025-08-01'
  AND assigned_to = 'officer-raj';

-- CANNOT use the partial index (missing the status condition)
SELECT * FROM loan_applications
WHERE created_at > '2025-08-01'
  AND assigned_to = 'officer-raj';
-- Would need the full index or a separate index
```

**Practical fintech patterns for partial indexes:**
```sql
-- Index only unverified KYC records (the hot set)
CREATE INDEX idx_kyc_unverified ON kyc_records (submitted_at, assigned_verifier)
WHERE verification_status = 'pending';

-- Index only failed NACH transactions for retry processing
CREATE INDEX idx_nach_failed ON nach_transactions (failure_code, next_retry_at)
WHERE status = 'failed' AND retry_count < 3;

-- Index only active TOTP secrets (completed enrollments)
CREATE INDEX idx_totp_active ON user_totp_secrets (user_id)
WHERE is_active = true AND revoked_at IS NULL;
```

**Q13. What is a functional index (expression index), and when is it necessary?**
A: A functional index indexes the result of a function or expression applied to a column, rather than the column value itself. It's necessary when queries filter or sort on a derived value rather than the raw column.

```sql
-- Problem: case-insensitive search on email
-- This cannot use a plain index on email
SELECT * FROM users WHERE LOWER(email) = LOWER('User@Example.COM');

-- Without functional index: sequential scan (function on column bypasses index)
EXPLAIN SELECT * FROM users WHERE LOWER(email) = 'user@example.com';
-- → Seq Scan on users (Filter: lower(email) = 'user@example.com')

-- Solution: index the expression
CREATE INDEX idx_users_email_lower ON users (LOWER(email));

-- Now the query can use the index
EXPLAIN SELECT * FROM users WHERE LOWER(email) = 'user@example.com';
-- → Index Scan using idx_users_email_lower (Index Cond: lower(email) = 'user@example.com')
```

**Common fintech functional index patterns:**

```sql
-- Date truncation for daily aggregation queries
CREATE INDEX idx_loans_created_date ON loan_applications (DATE(created_at));
-- Supports: WHERE DATE(created_at) = '2025-08-12'

-- JSONB field extraction (when storing metadata as JSONB)
CREATE INDEX idx_loans_bureau_score ON loan_applications
  ((metadata->>'bureau_score')::numeric);
-- Supports: WHERE (metadata->>'bureau_score')::numeric > 700

-- PAN last-four for partial display lookup
CREATE INDEX idx_kyc_pan_last4 ON kyc_records (RIGHT(pan_number_hash, 8));
-- Supports suffix lookups on the hashed PAN

-- Normalised phone number for search
CREATE INDEX idx_users_phone_norm ON users (REGEXP_REPLACE(phone, '[^0-9]', '', 'g'));
-- Supports: WHERE REGEXP_REPLACE(phone, '[^0-9]', '', 'g') = '9876543210'
```

**Important constraint:** the query must apply the exact same function or expression as the index definition. `LOWER(email)` in the query matches an index on `LOWER(email)`; `email ILIKE 'user%'` does not use the same index — it would require a GIN index with `pg_trgm` for ILIKE support.

## Section 5: Index Maintenance, Monitoring, and Anti-Patterns

**Q14. How do you identify missing indexes and unused indexes in a production PostgreSQL database?**
A: Both are equally important — missing indexes cause slow queries; unused indexes cause unnecessary write overhead.

**Finding missing indexes — slow query identification:**
```sql
-- Enable pg_stat_statements extension (tracks query statistics)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 10 slowest queries by total time
SELECT
  query,
  calls,
  total_exec_time / 1000                         AS total_seconds,
  mean_exec_time                                  AS mean_ms,
  rows,
  total_exec_time / calls                         AS avg_ms
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

```sql
-- Find sequential scans on large tables (candidates for indexing)
SELECT
  schemaname,
  relname                                         AS table_name,
  seq_scan,
  seq_tup_read,
  idx_scan,
  n_live_tup                                      AS live_rows,
  seq_tup_read / NULLIF(seq_scan, 0)              AS avg_rows_per_seq_scan
FROM pg_stat_user_tables
WHERE n_live_tup > 10000     -- only sizeable tables
  AND seq_scan > 100         -- with meaningful sequential scan activity
ORDER BY seq_tup_read DESC;
```

```sql
-- Tables with high seq_scan but no idx_scan — likely missing indexes
SELECT relname, seq_scan, idx_scan, n_live_tup
FROM pg_stat_user_tables
WHERE seq_scan > 0 AND idx_scan = 0 AND n_live_tup > 1000
ORDER BY seq_scan DESC;
```

**Finding unused indexes:**
```sql
-- Indexes that have never been scanned (index maintenance cost with zero benefit)
SELECT
  schemaname,
  tablename,
  indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan,
  idx_tup_read,
  idx_tup_fetch
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND schemaname NOT IN ('pg_catalog', 'pg_toast')
ORDER BY pg_relation_size(indexrelid) DESC;
-- Note: pg_stat_user_indexes resets on server restart — needs weeks of runtime to be reliable
```

```sql
-- Indexes with low usage relative to their size (candidates for removal or redesign)
SELECT
  i.indexname,
  i.tablename,
  pg_size_pretty(pg_relation_size(i.indexrelid)) AS size,
  s.idx_scan,
  s.idx_tup_read
FROM pg_indexes i
JOIN pg_stat_user_indexes s USING (indexname, tablename)
WHERE s.idx_scan < 50    -- fewer than 50 scans since last stats reset
ORDER BY pg_relation_size(i.indexrelid) DESC;
```

**Q15. What is index bloat, and how do you detect and manage it?**
A: Index bloat occurs when index pages contain many dead tuples (from updated or deleted rows) that haven't been reclaimed. PostgreSQL's MVCC model means that updating a row doesn't modify it in place — it creates a new tuple and marks the old one dead. Dead tuples accumulate in both the heap and the index until `VACUUM` reclaims them.

**Why index bloat matters:** a bloated index is larger than necessary — it takes more memory in `shared_buffers`, requires more I/O to scan, and causes the planner to overestimate the cost of index scans (because it sees more pages than necessary).

```sql
-- Detect index bloat using pgstattuple extension
CREATE EXTENSION pgstattuple;

SELECT *
FROM pgstattuple('idx_loans_user_status');
-- Returns: table_len, tuple_count, dead_tuple_count, dead_tuple_len, free_space, free_percent

-- Simpler estimation from pg_stat_user_indexes
SELECT
  relname,
  indexrelname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan,
  -- Bloat estimate: high n_dead_tup relative to n_live_tup suggests bloat
  n_dead_tup,
  n_live_tup,
  ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct
FROM pg_stat_user_tables t
JOIN pg_stat_user_indexes i ON t.relid = i.relid
WHERE n_live_tup > 1000
ORDER BY dead_pct DESC;
```

**Remediation:**
```sql
-- VACUUM ANALYZE — reclaims dead tuples, updates statistics
-- Runs automatically (autovacuum) but can be triggered manually
VACUUM ANALYZE loan_applications;

-- REINDEX CONCURRENTLY — rebuilds the index without a long lock (PostgreSQL 12+)
REINDEX INDEX CONCURRENTLY idx_loans_user_status;

-- For severe bloat: drop and recreate CONCURRENTLY
DROP INDEX CONCURRENTLY idx_loans_user_status;
CREATE INDEX CONCURRENTLY idx_loans_user_status ON loan_applications (user_id, status);
```

**Autovacuum tuning for high-write tables (loan applications, transactions):**
```sql
-- Per-table autovacuum settings for high-churn tables
ALTER TABLE loan_applications SET (
  autovacuum_vacuum_scale_factor      = 0.01,  -- vacuum when 1% of rows are dead (vs 20% default)
  autovacuum_analyze_scale_factor     = 0.005, -- analyze when 0.5% of rows change (vs 10% default)
  autovacuum_vacuum_cost_delay        = 2      -- milliseconds (reduce I/O throttling on important tables)
);
```

**Q16. What are the most common index anti-patterns, and what does each one cost?**
A: Six patterns worth calling out in a code or schema review:

**1. Index on a low-cardinality boolean/enum without a partial index:**
```sql
-- ANTI-PATTERN: indexes a column where 99% of rows have is_active = true
CREATE INDEX idx_users_active ON users (is_active);

-- Planner ignores this index for is_active = true queries (too many matches)
-- Write overhead on every user insert/update for minimal read benefit

-- CORRECT: partial index on the minority case
CREATE INDEX idx_users_inactive ON users (created_at)
WHERE is_active = false;  -- the small, interesting subset
```

**2. Redundant indexes:**
```sql
-- Both of these exist:
CREATE INDEX idx_a ON loans (user_id);
CREATE INDEX idx_b ON loans (user_id, status);  -- idx_b covers all queries that use idx_a

-- idx_a is redundant — any query using idx_a can use idx_b's leading column instead
-- idx_a only adds write overhead; remove it
```

```sql
-- Find redundant indexes
SELECT
  i1.indexname AS redundant,
  i2.indexname AS covers_it
FROM pg_indexes i1
JOIN pg_indexes i2 ON i1.tablename = i2.tablename
  AND i1.indexname <> i2.indexname
  AND position(replace(i1.indexdef, i1.indexname, '') IN i2.indexdef) > 0;
-- Approximate: check manually; the string match may need tuning
```

**3. Indexing every column individually instead of designing composite indexes:**
```sql
-- ANTI-PATTERN: three separate indexes for a query that always uses all three conditions
CREATE INDEX idx_loans_user    ON loans (user_id);
CREATE INDEX idx_loans_status  ON loans (status);
CREATE INDEX idx_loans_created ON loans (created_at);

-- The planner can only use one index efficiently per table per query
-- (it can do bitmap index scans combining multiple indexes, but this is less efficient
-- than one well-designed composite index)

-- CORRECT: one composite index for the query pattern
CREATE INDEX idx_loans_user_status_created ON loans (user_id, status, created_at);
```

**4. Using a function on an indexed column in the WHERE clause (defeating the index):**
```sql
-- ANTI-PATTERN: function call on column bypasses the index
WHERE YEAR(created_at) = 2025          -- bypasses index on created_at
WHERE UPPER(status) = 'PENDING'        -- bypasses index on status
WHERE created_at::date = '2025-08-12'  -- bypasses index on created_at

-- CORRECT: rewrite to use the indexed form
WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'
WHERE status = 'pending'               -- store normalised values; don't rely on UPPER
WHERE created_at >= '2025-08-12' AND created_at < '2025-08-13'
-- OR: use a functional index if the expression is unavoidable
```

**5. `LIKE '%term%'` (leading wildcard — cannot use B-tree):**
```sql
-- ANTI-PATTERN: leading wildcard bypasses B-tree index entirely
WHERE applicant_name LIKE '%kumar%'

-- B-tree can only serve prefix matches (LIKE 'kumar%')
-- For substring search, use pg_trgm GIN index:
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_loans_name_trgm ON loan_applications
  USING GIN (applicant_name gin_trgm_ops);
-- Supports: WHERE applicant_name ILIKE '%kumar%'
```

**6. Over-indexing on write-heavy tables:**
```sql
-- A table with 15 indexes on a table that receives 10,000 inserts/minute
-- Every insert must update all 15 indexes
-- Write throughput degrades; replication lag increases

-- Audit: if a table has more than 5-6 indexes, evaluate each for actual query usage
-- Remove any index with idx_scan < 100 in the past month
```

## Section 6: Real-World Scenarios and EXPLAIN Analysis

**Q17. How do you read an EXPLAIN ANALYZE output, and what signals indicate an index is not being used effectively?**
A: `EXPLAIN (ANALYZE, BUFFERS)` is the primary diagnostic tool. Reading it fluently is a 5 YOE competency:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, amount, status
FROM loan_applications
WHERE user_id = 'user-001' AND status = 'pending'
ORDER BY created_at DESC
LIMIT 20;
```

**Sample output — BAD plan (sequential scan):**
```
Limit  (cost=15234.56..15234.61 rows=20 width=48) (actual time=234.123..234.127 rows=20 loops=1)
  →  Sort  (cost=15234.56..15236.06 rows=600 width=56) (actual time=234.121..234.122 rows=20 loops=1)
       Sort Key: created_at DESC
       Sort Method: top-N heapsort  Memory: 26kB
       →  Seq Scan on loan_applications  (cost=0.00..15210.00 rows=600 width=56) (actual time=0.041..231.482 rows=587 loops=1)
             Filter: ((user_id = 'user-001') AND (status = 'pending'))
             Rows Removed by Filter: 999413
Buffers: shared hit=4425 read=672
Planning Time: 0.312 ms
Execution Time: 234.198 ms
```

**What to read:**
- `Seq Scan` — sequential scan; no index used. 999,413 rows scanned and discarded.
- `Rows Removed by Filter: 999413` — the filter is applied after a full scan, not before. This is the signal that an index is missing or not being used.
- `Buffers: shared hit=4425 read=672` — 672 pages read from disk (cache miss). High disk reads indicate the working set doesn't fit in `shared_buffers`.
- `Sort` node — the query requires an explicit sort because the data is not coming from an index in the right order.
- `Execution Time: 234.198 ms` — unacceptably slow for a dashboard query.

**Sample output — GOOD plan (index-only scan):**
```
Limit  (cost=0.56..8.21 rows=20 width=48) (actual time=0.082..0.134 rows=20 loops=1)
  →  Index Only Scan Backward using idx_loans_user_status_date on loan_applications
       (cost=0.56..229.21 rows=587 width=48) (actual time=0.079..0.127 rows=20 loops=1)
       Index Cond: ((user_id = 'user-001') AND (status = 'pending'))
       Heap Fetches: 0
Buffers: shared hit=5
Planning Time: 0.198 ms
Execution Time: 0.152 ms
```

**What to read:**
- `Index Only Scan Backward` — using the index in reverse order to serve `ORDER BY created_at DESC`, no heap visit.
- `Heap Fetches: 0` — all data served from the index (covering index, all-visible pages).
- `Buffers: shared hit=5` — only 5 buffer pages accessed. The index is in memory.
- `Execution Time: 0.152 ms` — 1,500× faster than the sequential scan.

**Key signals that an index is not being used effectively:**
- `Seq Scan` on a large table — usually means missing index or planner chose seq scan due to low selectivity / high `random_page_cost`.
- `Rows Removed by Filter: N` — filter applied after index scan (index didn't eliminate these rows). Indicates the index condition wasn't tight enough or the wrong index was chosen.
- `Sort` node when ORDER BY is present — the index isn't being used for ordering; consider adding the sort column to the index.
- High `Heap Fetches` in an `Index Only Scan` — covering index exists but visibility map isn't current (run `VACUUM`).
- `Buffers: read=N` (as opposed to `hit=N`) — index/heap data not in `shared_buffers`; consider increasing `shared_buffers` or using `pg_prewarm`.

**Q18. Scenario: "A NestJS application uses TypeORM's QueryBuilder for loan application queries. A new filter was added for `risk_category` but queries are suddenly 10× slower. Walk through your diagnosis and fix."**
A: This is a typical "added a filter, broke a query" scenario. Systematic diagnosis:

**Step 1 — Reproduce and capture the slow query:**
```typescript
// TypeORM QueryBuilder — what the new code looks like
const loans = await this.repo
  .createQueryBuilder('loan')
  .where('loan.userId = :userId', { userId })
  .andWhere('loan.status = :status', { status })
  .andWhere('loan.riskCategory = :riskCategory', { riskCategory })  // NEW FILTER
  .orderBy('loan.createdAt', 'DESC')
  .limit(20)
  .getMany();
```

Enable query logging to capture the SQL:
```typescript
// In TypeORM DataSource config
logging: ['query', 'slow'],
maxQueryExecutionTime: 100,  // log queries taking > 100ms
```

**Step 2 — Check existing indexes:**
```sql
\d+ loan_applications   -- psql command to show table structure + indexes
-- OR:
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename = 'loan_applications';
```

Suppose you see:
```sql
idx_loans_user_status ON loan_applications (user_id, status, created_at)
-- No index involving risk_category
```

**Step 3 — Run EXPLAIN on the slow query:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM loan_applications
WHERE user_id = 'user-001'
  AND status = 'approved'
  AND risk_category = 'high'
ORDER BY created_at DESC
LIMIT 20;
```

```
-- Likely output:
Index Scan using idx_loans_user_status on loan_applications
  Index Cond: ((user_id = 'user-001') AND (status = 'approved'))
  Filter: (risk_category = 'high')
  Rows Removed by Filter: 8430
  Buffers: shared hit=856
Execution Time: 87ms
```

The index is used for `user_id` and `status` but `risk_category` is applied as a post-scan filter — 8,430 rows fetched from the index, then filtered down. The query is fetching far more rows than it returns.

**Step 4 — Assess `risk_category` selectivity:**
```sql
SELECT
  risk_category,
  COUNT(*) AS count,
  ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS pct
FROM loan_applications
GROUP BY risk_category;
-- Result: low=60%, medium=30%, high=10%
-- risk_category = 'high' selects 10% of rows — meaningful selectivity
```

**Step 5 — Design and create the new index:**
```sql
-- Add risk_category to the composite index, before created_at (it's an equality condition)
-- Order: user_id (highest selectivity for this query) → status → risk_category → created_at (range/sort)
CREATE INDEX CONCURRENTLY idx_loans_user_status_risk_date
  ON loan_applications (user_id, status, risk_category, created_at DESC)
  INCLUDE (amount, applicant_name);  -- cover the SELECT columns

-- CONCURRENTLY: no table lock; safe for production deployment
```

**Step 6 — Verify the new plan:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM loan_applications
WHERE user_id = 'user-001' AND status = 'approved' AND risk_category = 'high'
ORDER BY created_at DESC LIMIT 20;

-- Expected:
-- Index Only Scan Backward using idx_loans_user_status_risk_date
--   Index Cond: (user_id = 'user-001') AND (status = 'approved') AND (risk_category = 'high')
--   Heap Fetches: 0
--   Rows Removed by Filter: 0
-- Execution Time: 0.3ms
```

**Step 7 — Evaluate the old index:**
Check if the old `idx_loans_user_status` is now redundant (the new index covers all its use cases as a prefix):
```sql
SELECT idx_scan FROM pg_stat_user_indexes
WHERE indexname = 'idx_loans_user_status';
-- If idx_scan drops to near-zero after deploying the new index, consider dropping the old one
```

**Q19. Scenario: "Your TypeORM entity uses `@Index()` decorators. A developer added `@Index(['status', 'userId'])` but queries filtering only on `userId` are still slow. Explain why and fix it."**
A: This is the leftmost prefix rule applied to a real code scenario:

```typescript
// TypeORM entity
@Entity()
@Index(['status', 'userId'])  // ← index defined with status first, userId second
export class LoanApplication {
  @Column() status: string;
  @Column() userId: string;
  @Column() createdAt: Date;
}

// The slow query — filters only on userId
const loans = await this.repo.find({
  where: { userId: 'user-001' },
  order: { createdAt: 'DESC' },
});
```

The generated SQL:
```sql
SELECT * FROM loan_application
WHERE user_id = 'user-001'
ORDER BY created_at DESC;
```

The index `(status, user_id)` cannot be used for this query — `user_id` is the second column; without an equality condition on `status` (the first column), the index is not useful. B-tree entries are sorted first by `status`; `user_id` values for a given user are scattered throughout the entire index interleaved with all other users under all status values.

**Fix — reverse the column order in the decorator:**
```typescript
@Entity()
@Index(['userId', 'status'])   // userId first — now queries on userId alone can use the index
@Index(['userId', 'createdAt']) // separate index for the ORDER BY pattern
export class LoanApplication {
  @Column() status: string;
  @Column() userId: string;
  @Column() createdAt: Date;
}
```

Or, better, replace two separate indexes with one composite covering index using TypeORM's `@Index` with the correct order:
```typescript
@Entity()
@Index(['userId', 'status', 'createdAt'])
export class LoanApplication { ... }
```

Alternatively, manage the index in a migration file rather than entity decorators — this gives you full control over `INCLUDE`, partial index conditions, and index naming:

```typescript
// migration file — explicit and controllable
export class AddLoanApplicationIndexes implements MigrationInterface {
  async up(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`
      CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_loans_user_status_date
      ON loan_application (user_id, status, created_at DESC)
      INCLUDE (amount, applicant_name)
    `);
  }

  async down(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`DROP INDEX CONCURRENTLY IF EXISTS idx_loans_user_status_date`);
  }
}
```

**Q20. How do you design indexes for a NestJS application with complex filtering — dynamic WHERE clauses where different combinations of filters are used?**
A: Dynamic filtering (a user can filter by any combination of: status, assigned officer, branch, date range, risk category, loan amount range) is one of the hardest indexing problems. No single composite index can serve all combinations efficiently.

**Strategy 1 — Index the most common combinations:**
Analyse query logs to find the top 3–5 filter combinations by frequency and latency:
```sql
SELECT
  query,
  calls,
  mean_exec_time,
  total_exec_time
FROM pg_stat_statements
WHERE query LIKE '%loan_applications%'
ORDER BY total_exec_time DESC
LIMIT 20;
```
Design composite indexes for the top combinations. Accept sequential scans for rare combinations.

**Strategy 2 — Partial indexes for the high-traffic filtered views:**
```sql
-- "My pending loans" (most common officer view)
CREATE INDEX idx_loans_officer_pending ON loan_applications
  (assigned_to, created_at DESC)
  WHERE status IN ('pending', 'under_review');

-- "Branch dashboard" (branch manager view)
CREATE INDEX idx_loans_branch_active ON loan_applications
  (branch_id, created_at DESC)
  WHERE status NOT IN ('closed', 'rejected');
```

**Strategy 3 — For truly arbitrary filtering: denormalise to a search index:**
When the number of filterable dimensions exceeds what B-tree indexes can efficiently serve, a search engine is the right tool:
```typescript
// Sync loan records to Elasticsearch / OpenSearch for arbitrary filter queries
// Use PostgreSQL B-tree indexes only for transactional queries (by ID, by user)
// Use Elasticsearch for the search/filter UI

// In NestJS: use @nestjs/elasticsearch
// In AWS: use OpenSearch Service (managed Elasticsearch)
```

**Strategy 4 — Index the mandatory filter columns; accept post-scan filtering for optional ones:**
In many applications, some filters are always present (e.g., `tenant_id`) while others are optional. Design the composite index for the mandatory filters plus the most selective optional filter:

```typescript
// QueryBuilder — builds different WHERE clauses based on filters provided
const qb = this.repo.createQueryBuilder('loan')
  .where('loan.tenantId = :tenantId', { tenantId })  // always present
  .orderBy('loan.createdAt', 'DESC');

// Add optional filters
if (filters.status)      qb.andWhere('loan.status = :status', { status: filters.status });
if (filters.assignedTo)  qb.andWhere('loan.assignedTo = :officer', { officer: filters.assignedTo });
if (filters.dateFrom)    qb.andWhere('loan.createdAt >= :from', { from: filters.dateFrom });

// Index design: covers the tenant + most common optional filter + date
// CREATE INDEX idx_loans_tenant_status_date ON loan_applications (tenant_id, status, created_at DESC);
// CREATE INDEX idx_loans_tenant_officer_date ON loan_applications (tenant_id, assigned_to, created_at DESC);
// Two indexes serve the two most common optional filters; rare combinations do a filtered scan
```

## Quick Comparison Table

| Index type | Best for | Cannot serve |
|---|---|---|
| B-tree (default) | Equality, range, ORDER BY, prefix LIKE, IS NULL | `LIKE '%term%'`, full-text, array contains, JSONB deep queries |
| GIN | Array contains, JSONB, full-text search, trgm LIKE/ILIKE | Range queries, ORDER BY |
| GiST | Geometric data, range types, full-text, trgm | Simple equality (use B-tree) |
| BRIN | Very large tables with physical correlation (time-series) | Random access, low-correlation columns |
| Hash | Equality only (rarely worth it — B-tree equality is comparable) | Range, ORDER BY |
| Partial | Filtered subset of rows (skewed data) | Queries not including the partial condition |
| Functional / expression | Queries on computed values (`LOWER(email)`, `DATE(created_at)`) | Different expressions on the same column |

| Composite index column order decision | Rule |
|---|---|
| Equality vs range | Equality columns always before range columns |
| Multiple equality columns | Most selective first (most distinct values) |
| Mandatory filter present | Mandatory filter first regardless of selectivity |
| ORDER BY column | Last position (after all equality conditions) |
| Covering columns | In `INCLUDE` clause — not in key columns |
| ESR mnemonic | **E**quality → **S**electivity (within equality) → **R**ange/sort |

---

**Tip for the interview:** At 5 YOE, index questions almost always include a "look at this slow query and fix it" component — be ready to walk through EXPLAIN output cold. Know the three-sentence answer to "why is column order important in a composite index?": B-trees sort by the first column first; without an equality condition on the leading column, the index can't narrow the search to a contiguous range; therefore the first column must be the one present in every query, and equality conditions must come before range conditions. The leftmost prefix rule, the ESR ordering heuristic, and `INCLUDE` columns for covering indexes are the three concepts that differentiate a 5 YOE answer from a junior one. For fintech interviews: always frame examples in terms of the actual domain (loan status, user_id, tenant_id, created_at) — it shows you understand that real index design is driven by actual query patterns, not theoretical selectivity rankings.
