# Performance: The N+1 Problem — Detection & Solutions — Interview Q&A (5 YOE Level)

---

## Section 1: Understanding the N+1 Problem

**Q1. What is the N+1 query problem, what database behavior causes it, and why does it only become visible at scale?**
A: The N+1 problem occurs when code fetches a list of N parent records, then issues one additional query per parent to fetch related child records — producing N+1 total queries instead of the 1 or 2 that should suffice. The name comes from the query count: 1 query for the list, plus N queries for the N parents' related data.

**The canonical example:**
```typescript
// Fetching loans with their borrower details
// What the code looks like — seems reasonable at first glance
async function getLoansWithBorrowers(): Promise<LoanWithBorrower[]> {
  const loans = await db.query('SELECT * FROM loans');   // Query 1: fetches N loans

  return Promise.all(loans.map(async (loan) => {
    const borrower = await db.query(                     // Query 2..N+1: one per loan
      'SELECT * FROM users WHERE id = $1',
      [loan.userId]
    );
    return { ...loan, borrower: borrower[0] };
  }));
}

// At runtime with 100 loans:
// SELECT * FROM loans                          ← 1 query
// SELECT * FROM users WHERE id = 'user-001'   ← query 2
// SELECT * FROM users WHERE id = 'user-002'   ← query 3
// SELECT * FROM users WHERE id = 'user-003'   ← query 4
// ... 100 times total
// = 101 queries to return 100 loans with borrower names
```

**The database behavior that enables it:**
```
Each query is a separate round trip to the database:
  Application → [network] → Database: "SELECT * FROM loans"
  Database   → [network] → Application: 100 rows returned
  Application → [network] → Database: "SELECT user WHERE id=1"
  Database   → [network] → Application: 1 row returned
  Application → [network] → Database: "SELECT user WHERE id=2"
  ...repeated 100 times

Each round trip costs:
  Network latency:          0.1–1ms (same datacenter)
  Query parse + plan:       ~0.1ms (cached after first run)
  Index lookup:             ~0.05ms
  Result serialization:     ~0.05ms
  Total per query:          ~0.5ms

At 100 loans:  100 × 0.5ms = 50ms overhead, plus 1 query = 51 queries, ~51ms
At 1,000 loans: 1000 × 0.5ms = 500ms + base = over half a second
At 10,000 loans: 5,000ms + base = 5+ seconds — request timeout territory
```

**Why it's invisible at small scale:**
```
Development environment:
  Seeded with 10–50 rows; 51 queries × 0.1ms = 5ms → "fast enough"
  Running locally: network latency = 0 (same machine) → each query costs ~0.01ms
  Result: 51 queries feel like 1 query → problem invisible

Production at scale:
  10,000 customers; pagination at 100 per page
  → 101 queries per request for the loans list page
  → At 100 requests/sec: 10,100 queries/sec hitting the DB
  → DB CPU spikes; connection pool exhausted; P99 latency explodes
  → Problem visible only after user-facing degradation

The invisibility is a property of the linear scaling: 10 rows = fine,
100 rows = noticeable, 1000 rows = unacceptable, 10000 rows = outage.
Most N+1 bugs pass code review because the test data is small.
```

**Q2. How does the N+1 problem manifest differently in REST APIs versus GraphQL APIs, and why is GraphQL particularly susceptible?**
A: In a REST API, N+1 typically comes from explicit code making database calls in loops. In GraphQL, the same problem emerges structurally from the resolver architecture — even when each individual resolver is written correctly:

**N+1 in REST — explicit loop:**
```typescript
// REST endpoint: GET /api/loans
@Get('loans')
async getLoans() {
  const loans = await this.loanRepo.findAll();

  // Explicit loop — visible in code review
  const result = await Promise.all(
    loans.map(async (loan) => ({
      ...loan,
      borrower: await this.userRepo.findById(loan.userId), // N+1 here
      emis:     await this.emiRepo.findByLoanId(loan.id),  // Another N+1
    }))
  );
  return result;
}
// 1 (loans) + N (borrowers) + N (emis) = 2N+1 queries for N loans
```

**N+1 in GraphQL — structural, from resolver composition:**
```typescript
// GraphQL schema
type Loan {
  id: ID!
  amount: Float!
  borrower: User!     ← resolved by a separate resolver
  emis: [EMI!]!       ← resolved by another separate resolver
}

type Query {
  loans: [Loan!]!
}

// Resolvers — each looks correct in isolation
const resolvers = {
  Query: {
    loans: () => loanRepo.findAll(),  // 1 query
  },
  Loan: {
    borrower: (loan) => userRepo.findById(loan.userId),   // Called N times
    emis:     (loan) => emiRepo.findByLoanId(loan.id),    // Called N times
  },
};

// GraphQL query from client:
// query { loans { id amount borrower { name email } emis { amount dueDate } } }
//
// Execution:
// 1. loans resolver fires → 1 DB query → returns 100 loan objects
// 2. For each loan, borrower resolver fires → 100 DB queries
// 3. For each loan, emis resolver fires → 100 DB queries
// Total: 201 queries for 100 loans
```

**Why GraphQL is structurally MORE susceptible:**
```
In REST: the developer controls the data fetching strategy per endpoint.
         They can choose to join or batch — the structure encourages thinking about it.

In GraphQL: resolvers are designed to be composable and independent.
            Each field resolver should ideally not know about its siblings.
            The correct design (independent resolvers) naturally produces N+1.
            A "correct" GraphQL implementation without DataLoader = N+1 by default.

The client-driven query depth makes it worse:
  A client can request: loans { borrower { loans { borrower { ... } } } }
  Each nesting level multiplies the N+1:
  100 loans → 100 borrowers → each borrower's 5 loans = 500 loans → 500 borrowers
  = 1 + 100 + 500 + 500 = 1,101 queries for what looks like one GraphQL query

GraphQL without a batching solution (DataLoader) is almost guaranteed to have N+1.
This is why DataLoader was created by Facebook specifically to solve this problem.
```

## Section 2: Detection

**Q3. How do you detect N+1 queries in a Node.js application — what tools, query logging patterns, and metrics expose the problem?**
A: N+1 bugs are best caught before production through query logging in development and through APM instrumentation in production. The key signal is a large number of structurally identical queries with different parameter values executing within a single request:

**Detection method 1 — Query count logging in development:**
```typescript
// TypeORM: enable query logging and count queries per request
// In development, wrap each request and log the query count

import { DataSource } from 'typeorm';

// Custom query counter logger
class QueryCountLogger {
  private queries: string[] = [];

  logQuery(query: string, parameters?: any[]) {
    this.queries.push(query);
    if (process.env.NODE_ENV === 'development') {
      console.debug(`[SQL] Query #${this.queries.length}: ${query.substring(0, 80)}`);
    }
  }

  logQueryError(error: string, query: string) {}
  logQuerySlow(time: number, query: string) {}
  logSchemaBuild(message: string) {}
  logMigration(message: string) {}
  log(level: string, message: any) {}

  getCount() { return this.queries.length; }
  getQueries() { return this.queries; }
  reset() { this.queries = []; }
}

// NestJS middleware — counts queries per request
@Injectable()
export class QueryCountMiddleware implements NestMiddleware {
  constructor(private readonly dataSource: DataSource) {}

  use(req: Request, res: Response, next: NextFunction) {
    const logger = new QueryCountLogger();
    this.dataSource.setOptions({ logger });
    logger.reset();

    res.on('finish', () => {
      const count = logger.getCount();
      if (count > 10) {  // Threshold: alert if more than 10 queries per request
        console.warn(
          `[N+1 ALERT] ${req.method} ${req.path} executed ${count} queries`,
          logger.getQueries()
            .filter((q, i, arr) => arr.indexOf(q.replace(/\$\d+/g, '?')) === i)
            // Show unique query shapes only
        );
      }
    });

    next();
  }
}

// Output when N+1 is present:
// [N+1 ALERT] GET /api/loans executed 101 queries
// Unique query shapes:
//   SELECT * FROM loans
//   SELECT * FROM users WHERE id = ?   ← this one ran 100 times
```

**Detection method 2 — Knex/pg query event hook:**
```typescript
// For raw pg or Knex, hook into the query event
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// Per-request query tracking using AsyncLocalStorage
import { AsyncLocalStorage } from 'async_hooks';
const queryStore = new AsyncLocalStorage<{ queries: string[]; count: number }>();

pool.on('connect', (client) => {
  const originalQuery = client.query.bind(client);
  client.query = (...args: any[]) => {
    const store = queryStore.getStore();
    if (store) {
      store.count++;
      store.queries.push(args[0]?.text ?? args[0]);
    }
    return originalQuery(...args);
  };
});

// Express middleware to track per-request
app.use((req, res, next) => {
  queryStore.run({ queries: [], count: 0 }, () => {
    res.on('finish', () => {
      const store = queryStore.getStore()!;
      if (store.count > 20) {
        console.warn(`N+1 suspected: ${store.count} queries for ${req.path}`);
      }
    });
    next();
  });
});
```

**Detection method 3 — APM instrumentation (production):**
```typescript
// Using OpenTelemetry — traces make N+1 visible as many identical spans
import { trace, SpanStatusCode } from '@opentelemetry/api';

// In your DataSource, instrument the query execution
// APM tools (Datadog, New Relic, Dynatrace) do this automatically via auto-instrumentation
// What to look for in APM traces:

/*
Trace: GET /api/loans (350ms)
  ├── SELECT * FROM loans (5ms)         ← 1 span
  ├── SELECT * FROM users WHERE id=1    ← span 2
  ├── SELECT * FROM users WHERE id=2    ← span 3
  ├── SELECT * FROM users WHERE id=3    ← span 4
  ...
  └── SELECT * FROM users WHERE id=100  ← span 101
      Total: 100 identical spans = N+1 pattern

APM alert rule:
  If (count of spans with same query shape in one trace) > 10 → alert N+1 suspected
*/

// Datadog APM: use span tags to group by query shape
const tracer = require('dd-trace');
tracer.init({ service: 'loans-api', env: 'production' });

// N+1 shows up automatically in Datadog's trace flame graph as
// a "fan-out" pattern — many identical narrow spans in sequence
```

**Detection method 4 — pg_stat_statements (database-side):**
```sql
-- PostgreSQL: pg_stat_statements extension tracks query frequency
-- Run this after a load test or after suspicious traffic:
SELECT
  query,
  calls,
  mean_exec_time,
  calls * mean_exec_time AS total_time_ms
FROM pg_stat_statements
WHERE query LIKE '%users%'
  AND calls > 100
ORDER BY calls DESC
LIMIT 20;

-- N+1 signal: a parameterized query with thousands of calls
-- that should only have been called once or a few times per business request
-- Example output:
-- query: SELECT * FROM users WHERE id = $1
-- calls: 450,000  ← in 1 hour → suspicious; is this 4,500 requests × 100 each?
-- mean_exec_time: 0.3ms
-- total_time_ms: 135,000ms = 2.25 minutes of CPU in 1 hour on this one query

-- Compare to:
-- query: SELECT * FROM loans
-- calls: 4,500
-- → Ratio of user query to loan query = 100:1 → confirms N+1
```

## Section 3: Solution 1 — Eager Loading / JOIN-based fetching

**Q4. What is eager loading, how does it solve N+1 using SQL JOINs, and what are its limitations that make it unsuitable for all situations?**
A: Eager loading solves N+1 by fetching parent and related child records in a single query using SQL JOINs or a small number of targeted IN-clause queries. Instead of asking "give me each borrower one at a time," it asks "give me all borrowers for these loans at once":

**Approach 1 — SQL JOIN (single query):**
```typescript
// TypeORM eager loading with JOIN
@Injectable()
export class LoanService {
  async getLoansWithBorrowers(): Promise<Loan[]> {
    return this.loanRepo
      .createQueryBuilder('loan')
      .leftJoinAndSelect('loan.borrower', 'borrower')   // JOIN users in the same query
      .leftJoinAndSelect('loan.emis', 'emi')             // JOIN emis in the same query
      .where('loan.status = :status', { status: 'ACTIVE' })
      .getMany();

    // Generates ONE query:
    // SELECT loan.*, borrower.*, emi.*
    // FROM loans loan
    // LEFT JOIN users borrower ON borrower.id = loan.user_id
    // LEFT JOIN emis emi ON emi.loan_id = loan.id
    // WHERE loan.status = 'ACTIVE'
    //
    // → 1 query regardless of N
  }
}

// TypeORM entity relationship definition (needed for JOIN to work)
@Entity('loans')
export class Loan {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column({ name: 'user_id' })
  userId: string;

  // Declare the relationship — TypeORM uses this for JOIN
  @ManyToOne(() => User, (user) => user.loans)
  @JoinColumn({ name: 'user_id' })
  borrower: User;

  @OneToMany(() => EMI, (emi) => emi.loan)
  emis: EMI[];
}
```

**Approach 2 — Two queries with IN clause (often better than JOIN for one-to-many):**
```typescript
// Manual two-query approach — avoids Cartesian product from JOIN on one-to-many
async getLoansWithEmis(): Promise<LoanWithEmis[]> {
  // Query 1: fetch all loans
  const loans = await this.loanRepo.find({ where: { status: 'ACTIVE' } });
  if (!loans.length) return [];

  const loanIds = loans.map(l => l.id);

  // Query 2: fetch ALL emis for ALL loan IDs in one query
  const allEmis = await this.emiRepo.find({
    where: { loanId: In(loanIds) },  // IN clause: one query for all
  });

  // Group emis by loanId in application memory (fast — no DB round trip)
  const emisByLoanId = new Map<string, EMI[]>();
  for (const emi of allEmis) {
    const existing = emisByLoanId.get(emi.loanId) ?? [];
    existing.push(emi);
    emisByLoanId.set(emi.loanId, existing);
  }

  // Assemble result
  return loans.map(loan => ({
    ...loan,
    emis: emisByLoanId.get(loan.id) ?? [],
  }));
  // Total: 2 queries regardless of N
}
```

**Why two-query IN-clause is often better than JOIN for one-to-many:**
```sql
-- JOIN on one-to-many creates a Cartesian product (duplicate parent rows):
SELECT loan.*, emi.*
FROM loans loan
LEFT JOIN emis emi ON emi.loan_id = loan.id
-- If loan L001 has 12 EMIs: L001 appears 12 times in the result
-- Network: 12× more data transferred from DB to application

-- Result set for 100 loans with 12 EMIs each:
-- 100 × 12 = 1,200 rows transferred
-- Application must deduplicate loan fields from 1,200 rows

-- Two queries with IN clause:
-- Query 1: 100 loan rows (compact)
-- Query 2: 1,200 emi rows (correct size, no duplication of loan data)
-- Total data transfer: same, but no deduplication logic needed
-- For deeply nested relations: JOIN explodes geometrically; IN stays linear

-- TypeORM's default for OneToMany relations when using find() with relations:
// TypeORM automatically uses the two-query strategy, not JOIN, for one-to-many
const loans = await loanRepo.find({
  relations: { emis: true },  // TypeORM issues: SELECT loans, then SELECT emis WHERE loan_id IN (...)
});
```

**Limitations of eager loading:**
```
Limitation 1 — Over-fetching:
  JOIN fetches ALL related data even when the caller only needs some fields.
  GET /api/loans → returns borrower name → but JOIN also fetches borrower's address,
  phone, KYC status, internal credit score — unused data transferred from DB
  Fix: SELECT specific columns; use projections/DTOs; avoid SELECT *

Limitation 2 — Inflexible for dynamic relationship depth:
  REST endpoint: always fetches the same set of relations (hardcoded JOIN)
  GraphQL: client specifies which relations they want at query time
  Eager loading in GraphQL means always fetching everything → over-fetching
  Fix: conditional eager loading based on requested fields (DataLoader is better here)

Limitation 3 — Cartesian product for multiple one-to-many relations:
  loans JOIN emis JOIN documents:
  100 loans × 12 emis × 5 documents = 6,000 rows for 100 loans
  TypeORM handles this with multiple queries; raw SQL requires careful deduplication

Limitation 4 — Doesn't work for DataLoader's use case (batching across resolvers):
  Eager loading works when you control the top-level query.
  In GraphQL, individual field resolvers don't know about each other.
  A resolver for `borrower` cannot "eagerly load" because it doesn't know
  which other loans are being resolved at the same time.
  → Need DataLoader for the GraphQL resolver composition case.
```

## Section 4: Solution 2 — DataLoader (Batching)

**Q5. How does DataLoader work mechanically — what is the batching and caching mechanism, and what execution model enables it to collect requests before issuing them?**
A: DataLoader, created by Facebook, solves the GraphQL N+1 problem by exploiting the JavaScript event loop. It collects all load requests made synchronously within a single tick, then batches them into a single database query before the next tick executes:

**The event loop trick — how batching works:**
```
JavaScript event loop model:
  Tick 1: GraphQL resolver executes
    → resolver 1 calls: dataloader.load('user-001')  [registers a request]
    → resolver 2 calls: dataloader.load('user-002')  [registers a request]
    → resolver 3 calls: dataloader.load('user-003')  [registers a request]
    → ... all 100 loan resolvers fire synchronously, registering 100 load() calls
    → Tick 1 ends; all synchronous code complete
    → DataLoader sees: 100 load() calls accumulated during Tick 1
    → Schedules the batch function for Tick 2 (via process.nextTick or Promise.resolve)

  Tick 2: DataLoader batch function executes
    → Calls: batchLoadUsers(['user-001', 'user-002', ..., 'user-100'])
    → Issues ONE query: SELECT * FROM users WHERE id IN ('user-001', ..., 'user-100')
    → Receives 100 user records
    → Resolves each pending Promise from Tick 1 with the corresponding user
    → All 100 resolver Promises now resolve with their user data

Result:
  100 dataloader.load() calls → 1 database query
  The key: load() is synchronous (returns a Promise); the batch runs asynchronously
```

**DataLoader implementation:**
```typescript
import DataLoader from 'dataloader';
import { Injectable, Scope } from '@nestjs/common';

// IMPORTANT: DataLoader must be REQUEST-scoped, not singleton
// Each request gets its own DataLoader instance with its own cache
// A singleton DataLoader would leak data between users (SECURITY BUG)

@Injectable({ scope: Scope.REQUEST })
export class UserDataLoader {
  constructor(private readonly userRepo: UserRepository) {}

  // The batch function: receives array of keys, returns array of values
  // CRITICAL: returned array must be SAME LENGTH and SAME ORDER as keys array
  private readonly batchLoadUsers = async (
    userIds: readonly string[]
  ): Promise<(User | Error)[]> => {
    // ONE query for ALL requested user IDs
    const users = await this.userRepo.findByIds([...userIds]);

    // Build a map for O(1) lookup
    const userMap = new Map<string, User>(
      users.map(u => [u.id, u])
    );

    // Return in the EXACT SAME ORDER as input keys
    // DataLoader matches responses to requests by position
    return userIds.map(
      id => userMap.get(id) ?? new Error(`User ${id} not found`)
      // Return Error instance (not throw) for individual missing items
    );
  };

  // The DataLoader instance — created once per request
  readonly loader = new DataLoader<string, User>(this.batchLoadUsers, {
    // Cache: true by default — within a request, same userId returns cached result
    // Prevents duplicate DB entries even if the same user is requested twice
    cache: true,

    // maxBatchSize: limit batch size to avoid IN clauses with thousands of IDs
    // Postgres handles large IN clauses fine but some DBs have limits
    maxBatchSize: 1000,

    // batchScheduleFn: override when batches are dispatched
    // Default: process.nextTick — collects all loads from current tick
    // Can use setTimeout(fn, 0) to collect across multiple ticks if needed
  });
}

// GraphQL resolver using DataLoader
@Resolver(() => Loan)
export class LoanResolver {
  constructor(private readonly userDataLoader: UserDataLoader) {}

  @ResolveField(() => User)
  async borrower(@Parent() loan: Loan): Promise<User> {
    // This looks like an individual lookup — but DataLoader batches it
    return this.userDataLoader.loader.load(loan.userId);
    // 100 calls to this resolver → DataLoader collects 100 userIds → 1 DB query
  }
}
```

**Q6. What is the critical ordering contract of DataLoader's batch function, and what happens if you violate it?**
A: DataLoader's batch function receives an array of keys and must return a Promise that resolves to an array of values in the **exact same order and same length** as the input keys. This contract is non-negotiable — violating it causes silent data corruption where resolvers receive the wrong data:

```typescript
// WRONG — returns users in DB order, not input key order
const wrongBatchFn = async (userIds: readonly string[]) => {
  const users = await db.query(
    'SELECT * FROM users WHERE id = ANY($1)',
    [userIds]
  );
  return users; // DB may return in any order — user-003 might come before user-001
  // DataLoader assigns users[0] to userIds[0], users[1] to userIds[1], etc.
  // If DB returned [user-003, user-001, user-002], then:
  //   loan-001 (userId: user-001) gets user-003's data ← SILENT DATA CORRUPTION
};

// CORRECT — enforce same-length, same-order response
const correctBatchFn = async (userIds: readonly string[]) => {
  const users = await db.query(
    'SELECT * FROM users WHERE id = ANY($1)',
    [[...userIds]]
  );

  // Build O(1) lookup map — DB can return in any order
  const map = new Map(users.map((u: User) => [u.id, u]));

  // Return in INPUT ORDER — not DB return order
  return userIds.map(id => map.get(id) ?? new Error(`User not found: ${id}`));
  //                ↑ This is the critical constraint
  // Length: userIds.length === returned array length (always)
  // Order:  userIds[i] corresponds to returned[i] (always)
};

// The Error return for missing items:
// return Error instance (not throw!) for individual misses
// DataLoader will reject the specific Promise for that key
// Other keys in the batch still resolve successfully
// throw would reject the ENTIRE BATCH — all 100 loans get an error
```

**Handling the ordering contract with multiple DataLoaders:**
```typescript
@Injectable({ scope: Scope.REQUEST })
export class EMIDataLoader {
  // EMIs are one-to-many: one loanId → many EMIs
  // DataLoader key: loanId; value: EMI[] (array, not single object)

  private readonly batchLoadEmis = async (
    loanIds: readonly string[]
  ): Promise<EMI[][]> => {  // Return type: array of arrays
    const emis = await this.emiRepo.find({
      where: { loanId: In([...loanIds]) },
      order: { dueDate: 'ASC' },
    });

    // Group by loanId
    const emisByLoan = new Map<string, EMI[]>(
      loanIds.map(id => [id, []])  // Initialize empty arrays for all keys
    );
    for (const emi of emis) {
      emisByLoan.get(emi.loanId)!.push(emi);
    }

    // Return in input order — empty array for loans with no EMIs
    return loanIds.map(id => emisByLoan.get(id) ?? []);
    // Note: return [] (empty array), not Error, for "no EMIs" — not an error case
  };

  readonly loader = new DataLoader<string, EMI[]>(this.batchLoadEmis, {
    cache: true,
  });
}
```

**Q7. What is DataLoader's per-request caching, when is it beneficial, and when does it become a problem that requires cache clearing?**
A: DataLoader maintains a per-request in-memory cache: if the same key is requested multiple times within a request, the second and subsequent requests return the cached result without hitting the database. This is beneficial for deduplication but requires careful management:

```typescript
// The caching benefit — same user referenced multiple times
// In a GraphQL query:
// { loans { borrower { id name } emis { paidBy { id name } } } }
// If the borrower IS the person who paid all their own EMIs:
// → borrower resolver calls: loader.load('user-001')  → DB query
// → emi.paidBy resolver calls: loader.load('user-001') × 12 → CACHE HIT × 12
// → 13 load() calls, but only 1 DB query for user-001

// Explicit cache usage
const loader = new DataLoader(batchFn);

loader.load('user-001')  // Miss — queued for batch
loader.load('user-001')  // Cache hit — no additional query
loader.load('user-001')  // Cache hit — no additional query
// Batch runs once: only ONE DB lookup for user-001

// Priming the cache (pre-loading known data)
// If you already have some users from a prior query, prime the cache
// to prevent DataLoader from re-fetching them
const existingUsers = await userRepo.findAll();
const loader = new DataLoader(batchFn);
existingUsers.forEach(user => loader.prime(user.id, user));
// Now loader.load(existingUser.id) → cache hit; no DB query

// When cache becomes a problem — mutation within a request
async function updateAndRefetch(userId: string) {
  // Load user (cached)
  const user = await userLoader.load(userId);
  console.log(user.name); // "Alice"

  // Update the user
  await userRepo.update(userId, { name: 'Alicia' });

  // Load user again — STALE CACHE — still returns "Alice"
  const updatedUser = await userLoader.load(userId);
  console.log(updatedUser.name); // "Alice" ← wrong! cache hit returns old value

  // Fix: clear the cache entry after mutation
  userLoader.loader.clear(userId);
  const freshUser = await userLoader.load(userId);
  console.log(freshUser.name); // "Alicia" ← correct
}

// Clear all cache if you need fresh data throughout the request
userLoader.loader.clearAll();

// For write operations followed by reads: always clear the relevant cache keys
@Mutation(() => Loan)
async updateLoan(@Args('id') id: string, @Args('data') data: UpdateLoanDto) {
  await this.loanService.update(id, data);

  // Clear related DataLoader caches
  this.loanDataLoader.loader.clear(id);
  // If the loan update affects the borrower's data:
  // this.userDataLoader.loader.clear(loan.userId);

  return this.loanDataLoader.loader.load(id); // Fresh load
}
```

## Section 5: Solution 3 — Batch Queries

**Q8. What is the batch query approach for non-GraphQL contexts, and how do you implement it at the repository layer in TypeORM to prevent N+1 across a microservices architecture?**
A: In a microservices context — where services call each other's REST APIs rather than sharing a database — N+1 manifests as N+1 HTTP calls instead of N+1 database queries. The solution is the same principle (batch the requests) applied at the service call layer:

**Pattern 1 — Repository-level batching with IN clause:**
```typescript
// Anti-pattern: service that fetches related data one at a time
@Injectable()

      ...loan,
      borrower: userMap.get(loan.userId),

  }
}
```

**Pattern 2 — Aggregating N+1 HTTP calls with a queue + flush:**
```typescript
// For cases where you cannot restructure the calling code
// but want to prevent N+1 at a lower layer
// Similar to DataLoader but for HTTP calls

class HttpBatchAggregator<TKey, TResult> {
  private queue: Map<TKey, {
    resolve: (result: TResult) => void;
    reject:  (error: Error) => void;
  }> = new Map();

  private flushTimer: NodeJS.Timeout | null = null;

  constructor(
    private readonly batchFn: (keys: TKey[]) => Promise<Map<TKey, TResult>>,
    private readonly maxBatchSize = 100,
    private readonly delayMs = 10,
  ) {}

  async load(key: TKey): Promise<TResult> {
    return new Promise((resolve, reject) => {
      this.queue.set(key, { resolve, reject });

      if (this.queue.size >= this.maxBatchSize) {
        this.flush();
      } else if (!this.flushTimer) {
        this.flushTimer = setTimeout(() => this.flush(), this.delayMs);
      }
    });
  }

  private flush() {
    if (this.flushTimer) {
      clearTimeout(this.flushTimer);
      this.flushTimer = null;
    }

    const currentQueue = new Map(this.queue);
    this.queue.clear();

    const keys = [...currentQueue.keys()];

    this.batchFn(keys).then(results => {
      for (const [key, handlers] of currentQueue) {
        const result = results.get(key);
        if (result !== undefined) {
          handlers.resolve(result);
        } else {
          handlers.reject(new Error(`No result for key: ${key}`));
        }
      }
    }).catch(error => {
      for (const handlers of currentQueue.values()) {
        handlers.reject(error);
      }
    });
  }
}
```

```typescript
// Extended repository with batch-aware loading methods
@Injectable()
export class LoanRepository extends Repository<Loan> {
  // NEVER call this in a loop — only call with the full set of IDs at once
  async findManyWithRelations(
    loanIds: string[],
    options: {
      includeBorrower?: boolean;
      includeEmis?:     boolean;
      includeDocuments?: boolean;
    } = {}
  ): Promise<Loan[]> {
    const qb = this.createQueryBuilder('loan')
      .whereInIds(loanIds);

    // Conditional eager loading based on what's actually needed
    if (options.includeBorrower) {
      qb.leftJoinAndSelect('loan.borrower', 'borrower');
    }
    if (options.includeEmis) {
      // One-to-many: use separate IN query instead of JOIN (avoids Cartesian product)
      // TypeORM handles this automatically via findOptions.relations
    }

    const loans = await qb.getMany();

    // Fetch one-to-many relations using IN queries (not JOINs)
    if (options.includeEmis && loans.length) {
      const ids = loans.map(l => l.id);
      const emis = await this.emiRepo.findBy({ loanId: In(ids) });
      const emisMap = groupBy(emis, 'loanId');
      loans.forEach(l => { l.emis = emisMap[l.id] ?? []; });
    }

    if (options.includeDocuments && loans.length) {
      const ids = loans.map(l => l.id);
      const docs = await this.documentRepo.findBy({ entityId: In(ids), entityType: 'LOAN' });
      const docsMap = groupBy(docs, 'entityId');
      loans.forEach(l => { l.documents = docsMap[l.id] ?? []; });
    }

    return loans;
    // Total queries: 1 (loans) + 1 (borrowers, if requested) +
    //                1 (emis, if requested) + 1 (docs, if requested)
    // = max 4 queries regardless of N
  }
}
```

**Q9. How do you handle N+1 in a NestJS GraphQL API end-to-end — from setting up DataLoader in a request-scoped context to avoiding the common pitfall of sharing DataLoader instances across requests?**
A: The most critical implementation detail for DataLoader in NestJS is scope. A DataLoader instance must be created fresh for each request — sharing it across requests would mean user A's cached data is returned to user B (a serious security and correctness bug):

**Q10. When does DataLoader make things WORSE, and what are the scenarios where eager loading or a different pattern is more appropriate?**
A: DataLoader adds complexity and has cases where it is the wrong tool. Knowing when NOT to use DataLoader is as important as knowing when to use it:

```
Scenario 1 — DataLoader with a tiny result set:
  If the loans query returns 3 loans, eager loading with a JOIN is simpler,
  faster (no event-loop tick delay), and has no implementation complexity.
  DataLoader adds overhead (Promise wrapping, tick delay, cache management)
  that exceeds its benefit for small N.
  Rule: if N is always small (< 10), use eager loading.

Scenario 2 — DataLoader with non-uniform access patterns:
  If 80% of loan borrowers are the same 5 users (a common portfolio pattern),
  a simple Map cache at the service level is more efficient than DataLoader:

  // Service-level cache for this specific request
  async enrichLoans(loans: Loan[]): Promise<EnrichedLoan[]> {
    const uniqueIds = [...new Set(loans.map(l => l.userId))];
    // uniqueIds may have 5 entries for 1000 loans
    const users = await this.userRepo.findByIds(uniqueIds);
    const map = new Map(users.map(u => [u.id, u]));
    return loans.map(l => ({ ...l, borrower: map.get(l.userId) }));
  }
  // 2 queries, simpler than DataLoader, correct result

Scenario 3 — DataLoader in a REST API with no resolver architecture:
  DataLoader's batching relies on the event loop tick accumulation pattern.
  In a simple REST handler that already has all IDs upfront, IN-clause batching
  is cleaner and more predictable than DataLoader:

  @Get('loans')
  async getLoans() {
    const loans = await this.loanRepo.findAll();
    // You already have all loans — use IN clause, not DataLoader
    const userIds = [...new Set(loans.map(l => l.userId))];
    const users = await this.userRepo.findByIds(userIds);
    // Simple, clear, no DataLoader needed
  }

Scenario 4 — DataLoader with aggregations:
  DataLoader loads individual records by key.
  For aggregations (count of EMIs per loan, sum of payments), a single
  GROUP BY query is more efficient than loading all records and counting in JS:

  // WRONG use of DataLoader for aggregation
  const emiCount = (await emiLoader.load(loan.id)).length;

  // CORRECT: aggregation query
  const counts = await db.query(
    'SELECT loan_id, COUNT(*) as count FROM emis WHERE loan_id = ANY($1) GROUP BY loan_id',
    [loanIds]
  );
  // Returns aggregated data in 1 query; no loading individual records

Scenario 5 — DataLoader cache causes stale data in long-lived connections:
  WebSocket subscriptions or Server-Sent Events hold connections open for minutes.
  A DataLoader scoped to the "request" in HTTP is safe.
  In a long-lived WebSocket, a request-scoped DataLoader would cache data
  from the start of the connection — stale for the entire duration.
  Rule: for long-lived connections, use shorter-scoped DataLoaders or disable cache.
```

**Q11. What are the performance characteristics of each N+1 solution, and how do you choose between them for different scenarios in a fintech API?**
A: The choice between eager loading, DataLoader, and batch queries depends on the access pattern, the data model depth, and whether you're in a REST or GraphQL context:

```
Performance comparison at scale (100 loans, each with 12 EMIs, 3 documents):

─────────────────────────────────────────────────────────────────────────────
Approach              Queries  DB time   Net transfer   Code complexity
─────────────────────────────────────────────────────────────────────────────
N+1 (naive)           301      ~150ms    ~5MB (repeated) Low (broken)
JOIN (single query)   1        ~80ms     ~8MB (Cartesian) Medium
2-query IN batch      3        ~20ms     ~4MB (compact)   Low
DataLoader (GraphQL)  3        ~20ms     ~4MB             Medium
DataLoader (bad impl) 301      ~150ms    ~5MB             High (broken)
─────────────────────────────────────────────────────────────────────────────

Decision matrix for fintech API scenarios:

Scenario: GET /api/loans — returns paginated list with borrower name only
  → REST endpoint; fixed data shape; small number of relations
  → Best: 2-query IN batch (loans + users IN clause)
  → Why: simple, predictable, no over-fetching, no framework overhead

Scenario: GraphQL query — arbitrary depth client-specified query
  → GraphQL; client controls which relations to request
  → Best: DataLoader for each relation type
  → Why: handles arbitrary depth; handles per-request deduplication

Scenario: GET /api/loans/{id}/details — full detail view of one loan
  → Single parent record; multiple deep relations
  → Best: eager loading with TypeORM relations or explicit JOINs
  → Why: N=1 means no N+1 possible; JOIN is fast for one record

Scenario: Loan disbursement report — 10,000 loans with financials
  → Large dataset; reporting use case; not user-interactive
  → Best: single SQL query with JOINs, or a raw SQL query with a CTE
  → Why: batch query overhead; JOINs with PostgreSQL CTEs are highly optimized
         DataLoader's async overhead adds latency to a streaming scenario

Scenario: Cross-service enrichment — loans from loan-service, users from user-service
  → Microservices; separate data stores; HTTP between services
  → Best: batch HTTP endpoint + aggregation at service boundary
  → Why: DataLoader only works within a single data source;
         cross-service N+1 requires a batch API contract

Scenario: Real-time loan status feed via GraphQL subscription
  → Long-lived connection; data changes over time
  → Best: eager loading per event + no DataLoader caching
  → Why: stale DataLoader cache would return outdated status
```

**Q12. Scenario: "A performance review finds that the loan listing API takes 3 seconds for pages of 50 loans. The APM trace shows 101 sequential database queries. Walk through how you diagnose and fix this end-to-end."**
A: This is the N+1 problem in production. Walk through a structured diagnosis and fix:

```
Step 1 — Confirm the N+1 pattern from the APM trace:
  101 queries for 50 loans = 1 + 50 + 50 or 1 + 100 (two N+1s)
  Examine the query shapes:
    Query 1:  SELECT * FROM loans WHERE status = $1 LIMIT $2 OFFSET $3
    Query 2:  SELECT * FROM users WHERE id = $1  ← runs 50 times, different $1
    Query 3:  SELECT * FROM emis WHERE loan_id = $1  ← runs 50 times
  → Confirmed: N+1 for users + N+1 for emis

Step 2 — Find the source in code:
  Search the codebase for the pattern: loanRepo.find() followed by map+await in the handler
  Or: TypeORM lazy relation loading (loan.borrower — lazy getter that fires a query)

  // Likely culprit — TypeORM lazy loading
  @Entity()
  export class Loan {
    @ManyToOne(() => User, { lazy: true })  // ← lazy: true = N+1 by default
    borrower: Promise<User>;
  }

  // In the service:
  const loans = await loanRepo.find();
  return loans.map(async loan => ({
    ...loan,
    borrower: await loan.borrower,  // Fires a query per loan
    emis: await loan.emis,          // Fires a query per loan
  }));

Step 3 — Fix: switch to explicit eager loading with IN clause

  // loans.service.ts — before (broken)
  async getLoansPage(page: number, pageSize: number): Promise<LoanDto[]> {
    const loans = await this.loanRepo.find({
      skip: (page - 1) * pageSize,
      take: pageSize,
    });
    return Promise.all(loans.map(async loan => ({
      id:       loan.id,
      amount:   loan.amount,
      borrower: await this.userRepo.findById(loan.userId),  // N+1
      emiCount: (await this.emiRepo.findByLoan(loan.id)).length, // N+1
    })));
  }

  // loans.service.ts — after (fixed)
  async getLoansPage(page: number, pageSize: number): Promise<LoanDto[]> {
    // Query 1: fetch the page of loans
    const loans = await this.loanRepo.find({
      skip: (page - 1) * pageSize,
      take: pageSize,
    });
    if (!loans.length) return [];

    const loanIds = loans.map(l => l.id);
    const userIds = [...new Set(loans.map(l => l.userId))];

    // Query 2: fetch all borrowers for this page in one IN query
    const users = await this.userRepo.findBy({ id: In(userIds) });
    const userMap = new Map(users.map(u => [u.id, u]));

    // Query 3: fetch EMI counts for all loans in one aggregation query
    const emiCounts = await this.emiRepo
      .createQueryBuilder('emi')
      .select('emi.loanId', 'loanId')
      .addSelect('COUNT(*)', 'count')
      .where('emi.loanId IN (:...ids)', { ids: loanIds })
      .groupBy('emi.loanId')
      .getRawMany();
    const emiCountMap = new Map(emiCounts.map(e => [e.loanId, parseInt(e.count)]));

    // Assemble in application memory — no more DB calls
    return loans.map(loan => ({
      id:       loan.id,
      amount:   loan.amount,
      borrower: userMap.get(loan.userId),
      emiCount: emiCountMap.get(loan.id) ?? 0,
    }));
    // Total: 3 queries regardless of page size
  }

Step 4 — Verify the fix:
  Add a test that fails if query count exceeds threshold:

  it('fetches a page of 50 loans in ≤ 5 queries', async () => {
    let queryCount = 0;
    // Hook into dataSource.query to count
    const result = await loanService.getLoansPage(1, 50);
    expect(queryCount).toBeLessThanOrEqual(5);
    expect(result).toHaveLength(50);
  });

Step 5 — Measure the improvement:
  Before: 101 queries × ~30ms avg = ~3s
  After:  3 queries × ~15ms avg = ~45ms
  Improvement: ~67× faster

Step 6 — Add ongoing protection:
  Add query count assertion to CI integration tests (Step 4 pattern)
  Add APM alert: if trace for GET /api/loans has > 10 DB spans → page on-call
  Enable TypeORM logging in staging environment (not production — too verbose)
  Disable lazy loading globally in TypeORM config to prevent future regressions:
    { synchronize: false, lazyRelations: false }  // Force explicit loading always
```

| Approach | Query Count | Memory | Complexity | Best For |
|---|---|---|---|---|
| **N+1 (naive)** | N+1 | Low | Low | Never |

**Tip for the interview:** At 5 YOE, the N+1 question is never just "what is it?" — the examiner wants to see your **diagnostic process** (Q3 and Q12): query count logging, APM traces, `pg_stat_statements`. Know the **DataLoader ordering contract** (Q6) cold — returning values in a different order than input keys causes silent data corruption, and being able to explain this shows you understand the implementation, not just the concept. The **TypeORM lazy loading trap** (Q12) is the most common real-world source of N+1 in NestJS applications — `lazy: true` on a relation looks innocent but fires a query per row; know to disable it globally. In the GraphQL context, know that DataLoader must be **REQUEST-scoped** (Q9) — a singleton DataLoader is a security vulnerability (cross-request cache pollution) and a correctness bug. For fintech specifically, connect N+1 to the **cross-service HTTP call pattern** (Q8) — the same problem manifests when a loans service calls a user service once per loan, and the fix (batch API endpoint) is a design conversation you will have in system design rounds.
