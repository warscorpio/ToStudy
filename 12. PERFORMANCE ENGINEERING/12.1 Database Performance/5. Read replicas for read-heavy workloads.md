# Performance: Read Replicas for Read-Heavy Workloads — Interview Q&A (5 YOE Level)

## Section 1: Replication Fundamentals

**Q1. What is a read replica, and what problem does it solve that vertical scaling cannot?**
A: A read replica is a continuously synchronized copy of a primary database that accepts only read queries. The primary handles all writes; replicas receive a stream of changes and apply them, staying near-current with the primary. Applications route read queries to replicas and write queries to the primary, distributing query load across multiple servers.

```
The problem vertical scaling cannot solve:

  Vertical scaling (bigger machine):
    Primary: 8 vCPU → 32 vCPU → 64 vCPU → 128 vCPU
    Problems:
      1. Cost: each doubling roughly triples the price.
         db.r6g.2xlarge (8 vCPU):   $0.48/hr
         db.r6g.4xlarge (16 vCPU):  $0.96/hr  (2× CPU, 2× cost — linear so far)
         db.r6g.8xlarge (32 vCPU):  $1.92/hr
         db.r6g.16xlarge (64 vCPU): $3.84/hr
         db.r6g.metal   (128 vCPU): no standard offering — you've hit the ceiling
      2. The ceiling: AWS RDS largest instance is ~128 vCPU / 1TB RAM.
         You cannot vertically scale beyond hardware limits.
      3. Single point of failure: one giant machine is still one machine.
      4. Write bottleneck: ALL writes go to one machine regardless of size.
         Vertical scaling helps reads AND writes; read replicas help reads ONLY
         — but that is often sufficient because read:write ratios are typically 10:1 or higher.

  Horizontal read scaling (read replicas):
    Primary:   8 vCPU — handles all writes + some reads
    Replica 1: 8 vCPU — handles read queries only
    Replica 2: 8 vCPU — handles read queries only
    Replica 3: 8 vCPU — handles read queries only

    Total read capacity: 4× the primary alone.
    Cost: 4× individual instance cost (same as vertical but without the ceiling).
    Ceiling: none — add replicas as read load grows.
    Failure: primary fails → promote one replica → writes resume in seconds.

Workloads where read replicas are the correct answer:

  High read:write ratio (the classic case):
    E-commerce: product catalog reads >> order writes.
    Social media: timeline reads >> post writes.
    Financial dashboards: balance/history reads >> transaction writes.
    Analytics: reporting queries >> data entry writes.
    Rule of thumb: if > 70% of query load is reads, read replicas help.

  Long-running analytical queries killing OLTP performance:
    A reporting query scanning 10M rows holds shared locks, consumes CPU,
    and competes with short OLTP queries on the same connection pool.
    Move reporting to a dedicated replica — OLTP performance is isolated.

  Geo-distributed read performance:
    Users in Asia connecting to a primary in us-east-1 → 200ms latency.
    Replica in ap-southeast-1 → 20ms latency for read queries.
    Writes still go to us-east-1 primary (with cross-region replication lag).

  Failover / high availability:
    Replica can be promoted to primary in seconds if primary fails.
    Read replica serves double duty: read scaling + HA.
```

**Q2. How does PostgreSQL streaming replication work — what actually flows from primary to replica?**
A: PostgreSQL uses Write-Ahead Log (WAL) streaming replication. Every change to the database is first written to the WAL — a sequential, append-only log of every operation at the byte level — before it is applied to the actual data files. Replicas continuously receive and replay this WAL stream.

```
PostgreSQL WAL streaming replication — step by step:

  Primary side:

  1. A write query arrives: UPDATE loans SET status = 'approved' WHERE id = 'L-8823'

  2. PostgreSQL writes a WAL record BEFORE modifying the data page:
     WAL record: {
       lsn:       0/1A3F8C20   ← Log Sequence Number — global byte offset in WAL
       xid:       7823419      ← transaction ID
       record_type: HOT_UPDATE
       relation:  loans (OID 16392)
       old_tuple: { id: L-8823, status: pending, ... }
       new_tuple: { id: L-8823, status: approved, ... }
       block:     42           ← which 8KB page this row lives on
       offset:    112          ← offset within the page
     }

  3. WAL is flushed to disk (fsync) — durability guaranteed.

  4. Data page in shared_buffers is modified.
     The modified page is "dirty" — will be written to disk by the background writer.

  5. COMMIT: WAL record written and flushed. Transaction is durable.
     At this point, even if the server crashes, the WAL record exists on disk
     and the change can be replayed on recovery.

  Replica side — WAL receiver process:

  6. Replica's WAL receiver connects to the primary's WAL sender process via TCP.
     Sends its current LSN: "I have WAL up to 0/1A3F8C10; send me the rest."

  7. Primary's WAL sender reads WAL from disk (or in-memory WAL buffer)
     and streams it to the replica over the replication connection.

  8. Replica's WAL receiver writes incoming WAL to its own WAL files.

  9. Replica's startup process (recovery mode) reads WAL and replays it:
     - Locates the 8KB page for the loans table, block 42.
     - Applies the HOT_UPDATE: changes the tuple from pending → approved.
     - The replica's data files now match the primary's at this LSN.

  10. Replica sends acknowledgment back to primary:
      { write_lsn:  0/1A3F8C20   ← WAL written to replica's disk
        flush_lsn:  0/1A3F8C20   ← WAL flushed to replica's disk
        apply_lsn:  0/1A3F8C20   ← WAL applied to replica's data files
        reply_time: ... }

  Monitoring lag:
    SELECT
        client_addr,
        state,
        sent_lsn,
        write_lsn,
        flush_lsn,
        replay_lsn,
        sent_lsn - replay_lsn AS replication_lag_bytes,
        now() - pg_last_xact_replay_timestamp() AS replication_lag_time
    FROM pg_stat_replication;   -- run on PRIMARY

    -- On the REPLICA:
    SELECT
        now() - pg_last_xact_replay_timestamp() AS lag,
        pg_is_in_recovery()                     AS is_replica,  -- should be TRUE
        pg_last_wal_receive_lsn()               AS received_lsn,
        pg_last_wal_replay_lsn()                AS applied_lsn;
```

**Q3. What is replication lag, and what are its causes — physical vs. logical?**
A: Replication lag is the delay between a write being committed on the primary and that write being visible on the replica. It is the fundamental trade-off of read replicas: you gain read scalability at the cost of potentially serving stale data.

```
Sources of replication lag — four distinct delays:

  Delay 1 — Network transit (write_lsn - sent_lsn lag):
    WAL must travel from primary to replica over the network.
    Same-AZ: <1ms. Cross-AZ: 1–5ms. Cross-region: 20–200ms.
    Measured by: sent_lsn - write_lsn in pg_stat_replication.

  Delay 2 — Replica WAL write and flush (flush_lsn - write_lsn lag):
    Replica writes received WAL to its own disk (WAL files).
    SSD: <1ms. Under I/O pressure: 2–10ms.

  Delay 3 — WAL apply (replay_lsn - flush_lsn lag — the most significant):
    The startup process reads flushed WAL and replays each record:
    - Fetches the target 8KB page (from shared_buffers or disk).
    - Applies the change.
    - Marks the page dirty.
    This is I/O bound. Under high write load or during bulk operations:
    replay can fall behind because it is single-threaded in PostgreSQL
    (parallel apply was added in PostgreSQL 16 for large transactions).

    Common causes of apply lag:
    a. Primary has a large write burst (bulk insert, batch update).
       Replay must apply thousands of changes serially.
    b. Replica's shared_buffers are too small → many page fetches from disk.
    c. Replica is running long read queries that compete for I/O.
    d. VACUUM on the replica competing with replay.

  Delay 4 — Application-level staleness (what the user experiences):
    Even after apply, the replica may serve a query from an old snapshot
    if the query started before the WAL was applied (MVCC snapshot isolation).
    Typically adds <1ms — usually negligible.

Typical lag ranges:

  Healthy, same-AZ:         0–50ms   (often <5ms)
  Healthy, cross-AZ:        5–100ms
  Healthy, cross-region:    20–500ms (dominated by network)
  Under heavy write load:   100ms–10s (apply lag)
  After bulk operation:     10s–10min (catching up after a large batch)
  Network partition:        ∞ (replica stops receiving WAL)

Measuring lag:

  # Application-level measurement — compare a known write to replica reads:
  def measure_replication_lag(primary_pool, replica_pool) -> float:
      start = time.time()
      # Write a sentinel value to the primary
      sentinel_id = str(uuid.uuid4())
      async with primary_pool.acquire() as conn:
          await conn.execute(
              "INSERT INTO replication_heartbeat (id, ts) VALUES ($1, NOW())",
              sentinel_id
          )

      # Poll the replica until the write is visible
      deadline = start + 30   # give up after 30 seconds
      async with replica_pool.acquire() as conn:
          while time.time() < deadline:
              exists = await conn.fetchval(
                  "SELECT EXISTS(SELECT 1 FROM replication_heartbeat WHERE id=$1)",
                  sentinel_id
              )
              if exists:
                  return time.time() - start
              await asyncio.sleep(0.01)

      return float("inf")   # replica did not catch up within 30 seconds
```

## Section 2: Routing Logic

**Q4. How do you implement read/write routing in the application — the patterns, their trade-offs, and the correct level of abstraction?**
A: Read/write routing can be implemented at three levels: the database driver, the application code, or an external proxy. Each has different failure modes, operational complexity, and transparency to the application.

```
Level 1 — Application-layer routing (explicit, most common at 5 YOE level):
  The application maintains separate connection pools for primary and replicas.
  Each query is explicitly routed by the developer.
  Maximum control; maximum verbosity.

Level 2 — ORM-layer routing (implicit, Rails/Django pattern):
  The ORM inspects query context (inside a transaction? write model?) and
  routes automatically.
  Convenient but can route incorrectly if context is ambiguous.

Level 3 — Proxy-layer routing (transparent to application):
  ProxySQL, RDS Proxy, PgCat, HAProxy — inspect the SQL and route.
  Application connects to one endpoint; proxy does the routing.
  Reduces application code but adds a network hop and operational complexity.
```

```python
# routing.py — application-layer read/write routing (Level 1)

import asyncpg
from contextlib import asynccontextmanager
from enum import Enum
import random

class RouteTarget(Enum):
    PRIMARY  = "primary"   # read/write
    REPLICA  = "replica"   # read-only (may be stale)
    REPLICA_CONSISTENT = "replica_consistent"  # read-only, staleness bounded

class DatabaseRouter:
    def __init__(
        self,
        primary_dsn:    str,
        replica_dsns:   list[str],
        primary_max:    int = 10,
        replica_max:    int = 10,
        max_lag_ms:     float = 500,   # reject replica if lag > this
    ):
        self._primary_pool:   asyncpg.Pool | None = None
        self._replica_pools:  list[asyncpg.Pool]  = []
        self._replica_health: list[bool]           = []   # per-replica health
        self._replica_lag_ms: list[float]          = []   # per-replica lag in ms

        self._primary_dsn  = primary_dsn
        self._replica_dsns = replica_dsns
        self._primary_max  = primary_max
        self._replica_max  = replica_max
        self._max_lag_ms   = max_lag_ms

    async def initialize(self) -> None:
        self._primary_pool = await asyncpg.create_pool(
            self._primary_dsn,
            min_size = 3,
            max_size = self._primary_max,
            max_inactive_connection_lifetime = 240,
        )
        for dsn in self._replica_dsns:
            pool = await asyncpg.create_pool(
                dsn,
                min_size = 2,
                max_size = self._replica_max,
                max_inactive_connection_lifetime = 240,
            )
            self._replica_pools.append(pool)
            self._replica_health.append(True)
            self._replica_lag_ms.append(0.0)

        # Start background health/lag checker
        asyncio.ensure_future(self._health_check_loop())

    @asynccontextmanager
    async def primary(self):
        """Acquire a connection to the primary. Use for all writes."""
        async with self._primary_pool.acquire() as conn:
            yield conn

    @asynccontextmanager
    async def replica(self, consistent: bool = False):
        """
        Acquire a connection to a healthy replica.
        Falls back to primary if no healthy replica is available.

        consistent=True: only use replicas with lag < max_lag_ms.
        consistent=False: use any available replica, including lagging ones.
        """
        pool = self._select_replica(consistent=consistent)
        if pool is None:
            # No healthy replica — fall back to primary
            async with self._primary_pool.acquire() as conn:
                yield conn
            return

        async with pool.acquire() as conn:
            yield conn

    def _select_replica(self, consistent: bool) -> asyncpg.Pool | None:
        """
        Select a healthy replica using weighted random selection.
        Excludes unhealthy replicas and (if consistent=True) lagging ones.
        """
        candidates = []
        for i, pool in enumerate(self._replica_pools):
            if not self._replica_health[i]:
                continue   # skip unhealthy replicas
            if consistent and self._replica_lag_ms[i] > self._max_lag_ms:
                continue   # skip lagging replicas when consistency matters
            candidates.append(pool)

        if not candidates:
            return None   # caller will fall back to primary

        # Random selection across healthy replicas (even distribution)
        # In production: weight by replica capacity (CPU, current connections)
        return random.choice(candidates)

    async def _health_check_loop(self) -> None:
        """
        Periodically check replica health and lag.
        Runs as a background task — does not affect query latency.
        """
        while True:
            for i, pool in enumerate(self._replica_pools):
                try:
                    async with pool.acquire() as conn:
                        row = await conn.fetchrow("""
                            SELECT
                                pg_is_in_recovery()                       AS is_replica,
                                EXTRACT(EPOCH FROM (
                                    now() - pg_last_xact_replay_timestamp()
                                )) * 1000                                 AS lag_ms
                        """)
                    if not row["is_replica"]:
                        # This "replica" is actually a primary — misconfiguration
                        self._replica_health[i] = False
                        logger.error("Replica %d is not in recovery mode!", i)
                    else:
                        self._replica_health[i] = True
                        self._replica_lag_ms[i]  = row["lag_ms"] or 0.0

                except Exception as exc:
                    self._replica_health[i] = False
                    logger.warning("Replica %d health check failed: %s", i, exc)

            await asyncio.sleep(5)   # check every 5 seconds
```

**Q5. What is the read-your-writes consistency problem, and what are the three correct solutions?**
A: The most common correctness bug with read replicas is returning to the user a stale view of their own recent write. The user updates their profile; the response redirects them to the profile page; the profile page reads from a replica with 200ms of lag; the user sees their old data and thinks the update failed.

```
The problem — illustrated:

  T=0ms:   User submits: PUT /api/users/me { name: "Alice Smith" }
  T=1ms:   Application writes to PRIMARY: UPDATE users SET name='Alice Smith'
  T=2ms:   Application returns HTTP 200. User is redirected to GET /api/users/me.
  T=3ms:   GET /api/users/me reads from REPLICA.
  T=3ms:   Replica lag = 150ms. Replica still has name='Alice Johnson'.
  T=3ms:   Response: { name: "Alice Johnson" }  ← user sees their old name
  T=153ms: Replica catches up. Now has name='Alice Smith'.
  T=153ms: User has already concluded the update failed and submitted again.

This is a violation of "read-your-writes" (RYW) consistency —
a guarantee that a user always sees the effects of their own writes.
RYW is the minimum acceptable consistency level for most user-facing features.
```

```python
# Solution 1 — Route reads to primary after writes (simplest, least scalable)
# Any request in the same session/transaction that follows a write goes to primary.
# Problem: defeats the purpose of replicas for write-heavy users.

class SessionAwareRouter:
    def __init__(self, router: DatabaseRouter):
        self.router = router

    @asynccontextmanager
    async def connection(self, session: dict, requires_write: bool = False):
        """
        Route to primary if the session has had a recent write.
        Route to replica otherwise.
        """
        recent_write = session.get("last_write_at", 0)
        lag_buffer   = self.router._max_lag_ms / 1000   # convert to seconds

        if requires_write or (time.time() - recent_write) < lag_buffer:
            async with self.router.primary() as conn:
                yield conn
        else:
            async with self.router.replica() as conn:
                yield conn

    def record_write(self, session: dict) -> None:
        session["last_write_at"] = time.time()


# Solution 2 — LSN-based "read after write" (precise, scalable)
# The primary returns the LSN of the committed write.
# The application passes that LSN when querying a replica.
# The replica refuses to serve the query until it has applied up to that LSN.

async def write_with_lsn_tracking(router: DatabaseRouter, query: str, *args) -> str:
    """Execute a write and return the LSN of the committed transaction."""
    async with router.primary() as conn:
        await conn.execute(query, *args)
        # pg_current_wal_lsn() returns the LSN immediately after commit
        lsn = await conn.fetchval("SELECT pg_current_wal_lsn()::text")
    return lsn   # e.g., "0/1A3F8C20"

async def read_after_write(
    router:   DatabaseRouter,
    min_lsn:  str,
    query:    str,
    *args,
    timeout_ms: float = 2000,
) -> list:
    """
    Execute a read on a replica, waiting until it has applied min_lsn.
    Falls back to primary if replica does not catch up within timeout.
    """
    deadline = time.time() + (timeout_ms / 1000)

    async with router.replica() as conn:
        while time.time() < deadline:
            # pg_last_wal_replay_lsn() returns the replica's current applied LSN.
            # pg_lsn_diff() returns > 0 if the replica is behind.
            lag = await conn.fetchval(
                "SELECT pg_lsn_diff($1::pg_lsn, pg_last_wal_replay_lsn())",
                min_lsn
            )
            if lag <= 0:
                # Replica has applied at least up to min_lsn — safe to read
                return await conn.fetch(query, *args)
            await asyncio.sleep(0.010)   # poll every 10ms

    # Replica did not catch up — fall back to primary
    logger.warning("Replica did not catch up to LSN %s within %dms; using primary",
                   min_lsn, timeout_ms)
    async with router.primary() as conn:
        return await conn.fetch(query, *args)


# Solution 3 — Synchronous replication for specific writes (strongest guarantee)
# The primary does not return to the application until at least one replica
# has confirmed it has received and written (or applied) the WAL.
# Cost: every write waits for network round-trip to replica → higher write latency.
# Use for: writes that MUST be immediately readable from any replica
# (financial transactions, password changes, permission grants).

# PostgreSQL synchronous_standby_names (server-side configuration):
# synchronous_standby_names = 'FIRST 1 (replica1, replica2)'
# → primary waits for FIRST 1 listed standbys to flush WAL before returning

# Per-transaction synchronous replication (application-side):
async def write_synchronously(conn: asyncpg.Connection, query: str, *args) -> None:
    """Force synchronous replication for this transaction only."""
    await conn.execute("SET LOCAL synchronous_commit = 'on'")
    # 'on'       = wait for primary + at least one replica to flush WAL
    # 'remote_write' = wait for primary + replica to write (not flush) WAL
    # 'remote_apply' = wait for primary + replica to apply WAL (most consistent)
    await conn.execute(query, *args)
    # COMMIT implicit on context manager exit — waits for replica acknowledgment
```

**Q6. How do you handle the fallback from replica to primary — what are the failure modes of getting this wrong?**
A: Automatic fallback to primary when replicas are unavailable or lagging seems safe — but done incorrectly it silently defeats the purpose of replicas or creates unexpected primary load spikes.

```python
# Fallback failure modes and correct implementations

# ── FAILURE MODE 1: Thundering herd on replica failure ────────────────────────
#
# Scenario: a replica goes down. All traffic that was going to it
# simultaneously falls back to the primary. Primary receives 3× normal load.
# Primary starts to slow down. Read queries take longer. More pile up.
# Eventually primary is overloaded.
#
# Fix: circuit breaker on per-replica health, not per-request fallback.
# Mark the replica as unhealthy after N consecutive failures.
# Route around it entirely — do not attempt it per-request.
# This prevents every request from attempting the unhealthy replica,
# timing out, and THEN falling back to primary (N × timeout overhead).

from collections import deque

class CircuitBreaker:
    """Per-replica circuit breaker: open after N failures, probe after cooldown."""

    CLOSED   = "closed"    # replica healthy; send traffic
    OPEN     = "open"      # replica unhealthy; bypass entirely
    HALF_OPEN = "half_open" # cooldown expired; send one probe request

    def __init__(self, failure_threshold: int = 5, cooldown_sec: float = 30.0):
        self.state            = self.CLOSED
        self.failure_count    = 0
        self.failure_threshold = failure_threshold
        self.opened_at:        float | None = None
        self.cooldown_sec      = cooldown_sec

    def record_success(self) -> None:
        self.state         = self.CLOSED
        self.failure_count = 0
        self.opened_at     = None

    def record_failure(self) -> None:
        self.failure_count += 1
        if self.failure_count >= self.failure_threshold:
            self.state     = self.OPEN
            self.opened_at = time.time()
            logger.warning("Replica circuit breaker OPENED after %d failures",
                           self.failure_count)

    def is_available(self) -> bool:
        if self.state == self.CLOSED:
            return True
        if self.state == self.OPEN:
            if time.time() - self.opened_at >= self.cooldown_sec:
                self.state = self.HALF_OPEN
                return True   # allow one probe
            return False
        if self.state == self.HALF_OPEN:
            return True   # allow the probe through


# ── FAILURE MODE 2: Infinite fallback loop ────────────────────────────────────
#
# Scenario: fallback logic uses the same connection pool for replica AND primary.
# When primary is also slow, "fallback" just queues on the same exhausted pool.
#
# Fix: primary and replica pools MUST be separate objects. Always.
# The fallback path must guarantee it reaches the primary pool, not retry replica.

# ── FAILURE MODE 3: Fallback without alerting ─────────────────────────────────
#
# Scenario: fallback is silently happening 40% of the time.
# The engineering team thinks replicas are working.
# The primary is taking 40% extra load. Nobody knows until it falls over.
#
# Fix: always instrument fallbacks with a counter metric.

async def read_with_fallback(router: DatabaseRouter, query: str, *args) -> list:
    replica_pool = router._select_replica(consistent=False)
    if replica_pool is not None:
        try:
            async with replica_pool.acquire() as conn:
                result = await conn.fetch(query, *args)
                metrics.increment("db.read.replica.success")
                return result
        except Exception as exc:
            metrics.increment("db.read.replica.failure", tags={"reason": type(exc).__name__})
            logger.warning("Replica read failed, falling back to primary: %s", exc)

    # Fallback to primary
    metrics.increment("db.read.primary.fallback")   # ← MUST BE MONITORED
    async with router.primary() as conn:
        return await conn.fetch(query, *args)

# Alert if db.read.primary.fallback rate > 5% of total reads.
# This means replicas are unhealthy or lagging beyond your threshold.

# ── FAILURE MODE 4: Routing writes to replica ─────────────────────────────────
#
# Scenario: a developer uses replica() instead of primary() for a write query.
# PostgreSQL replica is read-only: error "cannot execute INSERT on a standby"
# Some replica topologies silently discard writes. Both are catastrophic.
#
# Fix: enforce at the schema level — replica connection user has SELECT only.

# PostgreSQL: create a read-only database user for replicas
# CREATE USER app_readonly WITH PASSWORD '...';
# GRANT CONNECT ON DATABASE loans TO app_readonly;
# GRANT USAGE ON SCHEMA public TO app_readonly;
# GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly;
# -- NOT GRANTED: INSERT, UPDATE, DELETE, CREATE
#
# Now any attempt to write via a replica connection fails with:
# "permission denied for table loans"
# This is a hard guard — no application bug can silently write to a replica.
```

## Section 3: Schema and Query Patterns

**Q7. What SQL and schema patterns enable effective read replica utilization — and which patterns accidentally route reads to the primary?**
A:

```python
# Patterns that correctly use replicas vs. patterns that force primary reads

# ── SAFE FOR REPLICA: pure reads with no write side effects ──────────────────

# Simple SELECT — always safe for replica
async def get_loan(loan_id: str, router: DatabaseRouter) -> dict | None:
    async with router.replica() as conn:
        return await conn.fetchrow(
            "SELECT * FROM loans WHERE id = $1", loan_id
        )

# Aggregate / analytical queries — ideal for replica (keeps primary free)
async def monthly_loan_summary(org_id: str, year: int, month: int,
                                router: DatabaseRouter) -> list:
    async with router.replica() as conn:
        return await conn.fetch("""
            SELECT
                date_trunc('day', created_at)   AS day,
                COUNT(*)                         AS loan_count,
                SUM(amount)                      AS total_amount,
                AVG(amount)                      AS avg_amount
            FROM loans
            WHERE org_id     = $1
            AND   created_at >= make_date($2, $3, 1)
            AND   created_at <  make_date($2, $3, 1) + INTERVAL '1 month'
            GROUP BY 1
            ORDER BY 1
        """, org_id, year, month)

# Long-running report — ALWAYS replica (would kill OLTP on primary)
async def annual_compliance_report(org_id: str, router: DatabaseRouter) -> list:
    async with router.replica() as conn:
        # Set a long statement timeout for this specific query
        await conn.execute("SET LOCAL statement_timeout = '120s'")
        return await conn.fetch("""
            SELECT actor_id, action, COUNT(*), SUM(amount_usd)
            FROM audit_log
            WHERE org_id = $1
            AND   timestamp >= NOW() - INTERVAL '1 year'
            GROUP BY actor_id, action
            ORDER BY SUM(amount_usd) DESC
        """, org_id)


# ── MUST USE PRIMARY: writes and anything depending on write side effects ──────

# Any INSERT / UPDATE / DELETE — always primary

async def claim_job(job_id: str, worker_id: str, router: DatabaseRouter) -> bool:

        async with conn.transaction():

                "SELECT id FROM jobs WHERE id = $1 AND status = 'pending' FOR UPDATE",
                job_id
            )
            if row is None:
                return False
            await conn.execute(
                "UPDATE jobs SET status='running', worker_id=$1 WHERE id=$2",
                worker_id, job_id
            )
            return True
```

**Q8. What indexes should exist on replicas — can replicas have different indexes than the primary?**
A: This is a nuanced area that most developers don't know about. PostgreSQL replicas by default have identical indexes to the primary — indexes are part of the replicated state. But there are legitimate reasons to diverge.

```sql
-- Default behavior: replicas mirror ALL primary indexes exactly.
-- An index created on the primary is automatically created on all replicas.
-- An index dropped on the primary is automatically dropped on all replicas.
-- This is correct for most use cases.

-- ── CREATING INDEXES EXCLUSIVELY ON REPLICAS ─────────────────────────────────
-- Use case: analytical queries on replicas need indexes that would
-- slow down writes on the primary.
--
-- Example: a date-range + amount filter is common in reports (replica)
-- but never used in OLTP (primary). Adding it to the primary costs
-- write overhead on every INSERT/UPDATE to the loans table.

-- PostgreSQL 14+ supports creating indexes on replicas WITHOUT replicating them:
-- 1. Pause replication (briefly)
-- 2. Create index on replica with a special flag
-- 3. Resume replication

-- This is ADVANCED and requires careful coordination.
-- Most teams instead:
--   a. Accept the index on both (write overhead is usually small)
--   b. Use a dedicated analytics replica that is promoted/rebuilt
--      with the extra indexes after the initial sync

-- ── MORE COMMON PATTERN: partial indexes for replica-specific queries ─────────

-- Primary: broad index covering all loan states (OLTP reads)
CREATE INDEX idx_loans_org_created ON loans (org_id, created_at DESC);

-- This index also covers the replica analytical query:
-- WHERE org_id = $1 AND created_at >= $2
-- No replica-specific index needed.

-- If the analytical query also needs:
-- WHERE org_id = $1 AND status = 'approved' AND amount >= 10000
-- Add a partial index to PRIMARY (cost: small write overhead)
-- and it replicates automatically to the replica:
CREATE INDEX idx_loans_approved_large
    ON loans (org_id, amount DESC)
    WHERE status = 'approved' AND amount >= 10000;
-- Partial index: only rows matching the WHERE clause are indexed.
-- Smaller than a full index; write overhead proportional to matching rows only.

-- ── COVERING INDEXES for replica read performance ─────────────────────────────
-- A covering index includes all columns needed by the query — no heap fetch required.
-- Especially valuable on replicas where the heap may not be in buffer cache.

-- Query: SELECT id, status, amount, created_at FROM loans WHERE org_id=$1 ORDER BY created_at DESC LIMIT 20
-- Normal index on (org_id, created_at): index scan + heap fetch for each row.
-- Covering index: includes all needed columns — index scan only, no heap fetch.

CREATE INDEX idx_loans_covering
    ON loans (org_id, created_at DESC)
    INCLUDE (id, status, amount);
-- INCLUDE: add non-key columns to the index leaf pages.
-- PostgreSQL: use INCLUDE (not the same as composite key).
-- Result: the query above is satisfied entirely from the index — no heap access.
-- On a replica with cold buffer cache: this is 10–100× faster.
```

## Section 4: Topology Patterns

**Q9. What are the standard read replica topologies — single replica, replica pool, and cascading replicas — and when does each apply?**
A:

```
Topology 1 — Single primary + single replica (basic HA + read offload):

  Primary ──WAL──► Replica
     │                │
  All writes       All reads
  Critical reads   (can fall back to primary)

  Use when:
    - Read load is 2–5× the primary's capacity.
    - A single replica is sufficient.
    - Also serves as failover target.
  Failure modes:
    - Replica failure: all reads fall back to primary → primary load doubles.
    - Primary failure: promote replica → new primary, no replica (SPOF temporarily).
  RDS implementation: Multi-AZ = synchronous standby (NOT a read replica);
    Read Replica = asynchronous replica for reads (separate resource).


Topology 2 — Primary + replica pool (horizontal read scaling):

  Primary ──WAL──► Replica 1 ┐
                 ──WAL──► Replica 2 ├─── Load balancer / router → Read queries
                 ──WAL──► Replica 3 ┘

  Use when:
    - Read load is 5–20× write load.
    - Multiple replicas provide both capacity and redundancy.
    - One replica fails → router removes it; remaining replicas absorb load.
  Implementation:
    - Application router (Q4): round-robin or weighted across healthy replicas.
    - RDS: 5 read replicas max per primary (Aurora: 15).
  Sizing: each replica sized with the formula for its own hardware.
  Lag consideration: all replicas typically have similar lag (same distance from primary).
    Exception: one slow replica (disk I/O issue) may lag further than others.


Topology 3 — Cascading replicas (replica of a replica):

  Primary ──WAL──► Replica 1 (intermediate) ──WAL──► Replica 2
                                             ──WAL──► Replica 3

  Use when:
    - Primary WAL sender CPU or network bandwidth is a bottleneck.
      Each replica consumes a WAL sender process and bandwidth from the primary.
      With 10 replicas streaming directly from the primary: 10× WAL bandwidth.
      With cascading: primary sends to 1 intermediate; intermediate fans out.
    - Geo-distribution: intermediate replica in another region; final replicas
      in that region are fed by the intermediate (reduced cross-region WAL traffic).
  Trade-off: cascading increases lag. Replica 2's lag = (primary→R1 lag) + (R1→R2 lag).
  Use with caution: the intermediate is a single point of failure for its dependents.


Topology 4 — Aurora / AlloyDB shared storage (different model entirely):

  Aurora: primary + up to 15 Aurora replicas all sharing one distributed storage volume.
  Replication mechanism: NOT WAL streaming. Instead:
    - All nodes share the same storage (redo log, not WAL, is replicated in storage layer).
    - Replicas apply redo entries from the shared volume — not from the primary directly.
    - Result: replica lag is typically <10ms (storage-level, not network WAL streaming).
    - Failover: replica promotion in <30 seconds (no data copying — same storage).

  Aurora implications for routing:
    - Lag is so low that read-your-writes violations are rare in practice.
    - Still possible during replication lag spikes or after large writes.
    - Aurora Global Database: cross-region replica with <1s replication lag.

  When Aurora is the right choice:
    - You need low replica lag consistently (<10ms typical).
    - You need up to 15 read replicas.
    - You need sub-30-second failover.
    - You accept higher cost (Aurora ~20% premium over equivalent RDS).
```

```python
async def search_loans(
    query:    str,
    org_id:   str,
    router:   DatabaseRouter,
    page:     int = 0,
    per_page: int = 20,
) -> dict:
    """
    Full-text search across loan notes and customer names.
    Uses a GIN index on a tsvector column — the index is on the replica too.
    This query scans many rows and is CPU-intensive — never run on primary.
    """
    async with router.replica() as conn:
        # Set a statement timeout specific to search — search should be fast
        await conn.execute("SET LOCAL statement_timeout = '10s'")

        count = await conn.fetchval("""
            SELECT COUNT(*)
            FROM loans
            WHERE org_id = $1
            AND   search_vector @@ plainto_tsquery('english', $2)
        """, org_id, query)

        results = await conn.fetch("""
            SELECT
                id, borrower_name, amount, status, created_at,
                ts_rank(search_vector, plainto_tsquery('english', $2)) AS rank
            FROM loans
            WHERE org_id = $1
            AND   search_vector @@ plainto_tsquery('english', $2)
            ORDER BY rank DESC
            LIMIT $3 OFFSET $4
        """, org_id, query, per_page, page * per_page)

        return {"total": count, "results": [dict(r) for r in results]}


# Use case 2 — Dashboard metrics (cached, from replica)

import asyncio
from datetime import datetime

class DashboardCache:
    """
    Pre-compute expensive dashboard metrics from the replica on a schedule.
    Serve cached results to the UI — never recompute per-request.
    """
    def __init__(self, router: DatabaseRouter, ttl_seconds: int = 60):
        self.router     = router
        self.ttl        = ttl_seconds
        self._cache:    dict = {}
        self._lock:     asyncio.Lock = asyncio.Lock()

    async def get_org_metrics(self, org_id: str) -> dict:
        cache_key = f"metrics:{org_id}"
        cached = self._cache.get(cache_key)
        if cached and time.time() - cached["computed_at"] < self.ttl:
            return cached["data"]

        async with self._lock:
            # Double-check after acquiring lock
            cached = self._cache.get(cache_key)
            if cached and time.time() - cached["computed_at"] < self.ttl:
                return cached["data"]

            data = await self._compute_metrics(org_id)
            self._cache[cache_key] = {"data": data, "computed_at": time.time()}
            return data

    async def _compute_metrics(self, org_id: str) -> dict:
        async with self.router.replica() as conn:
            await conn.execute("SET LOCAL statement_timeout = '30s'")
            row = await conn.fetchrow("""
                SELECT
                    COUNT(*) FILTER (WHERE status = 'pending')    AS pending_count,
                    COUNT(*) FILTER (WHERE status = 'approved')   AS approved_count,
                    COUNT(*) FILTER (WHERE status = 'rejected')   AS rejected_count,
                    SUM(amount) FILTER (WHERE status = 'approved'
                        AND created_at >= date_trunc('month', NOW())) AS month_volume,
                    AVG(amount) FILTER (WHERE status = 'approved') AS avg_loan_amount,
                    COUNT(*) FILTER (WHERE created_at >= NOW() - INTERVAL '24 hours')
                                                                  AS new_today
                FROM loans
                WHERE org_id = $1
            """, org_id)
        return dict(row)

    async def warm_cache_loop(self) -> None:
        """Background task: refresh all org metrics before TTL expires."""
        while True:
            org_ids = await self._get_active_org_ids()
            await asyncio.gather(*[self.get_org_metrics(org_id) for org_id in org_ids])
            await asyncio.sleep(self.ttl * 0.8)   # refresh at 80% of TTL
```

## Quick Reference: Replication Lag Sources and Mitigations

| Lag Source | Typical Magnitude | Detection | Mitigation |
|---|---|---|---|
| Network transit (same-AZ) | <1ms | `sent_lsn - write_lsn` | Minimize; inherent |
| Network transit (cross-region) | 20–200ms | `sent_lsn - write_lsn` | Cascading replica; WAL compression |
| WAL apply: normal load | 1–50ms | `sent_lsn - replay_lsn` | Adequate replica I/O; larger shared_buffers |
| WAL apply: bulk operation | 10s–10min | Lag spike at batch time | Batch in small chunks; off-peak scheduling |
| Hot standby conflict | 1–60s | `max_standby_streaming_delay` | Increase delay tolerance; statement_timeout on replica |
| Replica disk I/O pressure | 100ms–5s | High disk reads, low cache hit ratio | Larger shared_buffers; faster disk; larger instance |

## Quick Reference: What to Route Where

| Query Type | Route To | Reason |
|---|---|---|
| `INSERT` / `UPDATE` / `DELETE` | Primary only | Writes not accepted on replicas |
| `SELECT FOR UPDATE` / `FOR SHARE` | Primary only | Row locks require write access |
| `SELECT nextval(seq)` | Primary only | Sequence state is not replicated the same way |
| `WITH ... INSERT` (writeable CTE) | Primary only | Contains a write |
| `SELECT` immediately after a write | Primary (or LSN check) | Read-your-writes consistency |
| Plain `SELECT` (no write dependency) | Replica | Offload primary |
| Aggregate / reporting query | Replica (dedicated if possible) | High cost; isolate from OLTP |
| Full-text search | Replica | CPU-intensive; read-only |
| `SELECT` in a transaction with writes | Primary | Transaction must be on same connection |
| Health check / `SELECT 1` | Either | Monitoring; no business logic |

## Quick Reference: Topology Selection

| Requirement | Topology | Notes |
|---|---|---|
| HA only (no read scaling needed) | RDS Multi-AZ (synchronous standby) | Not a read replica — failover only |
| Single read replica for offloading reports | Primary + 1 async replica | Simple; replica also serves as failover |
| Read load 3–10× write load | Primary + 2–5 replicas + router | Round-robin; circuit breaker per replica |
| Very low lag requirement (<10ms) | Aurora | Shared storage; near-zero replica lag |
| Many replicas (>5) | Aurora (up to 15) or primary + cascading | Avoids WAL sender bottleneck on primary |
| Cross-region reads | Regional replica via cascading or Aurora Global | Lag = network RTT; acceptable for reads |
| Dedicated analytics | Separate analytics replica, larger work_mem | Isolate from OLTP; different config |
| Reporting + OLTP on same replica | Acceptable only if well separated | Statement timeout; replica-specific indexes |

---

**Tip for the interview:** At 5 YOE, the read replica question is almost never "what is a read replica?" — it's a design question: "your read load is 10× your write load, walk me through your architecture" or "a user updates their profile but sees the old data — what's happening?" Know the read-your-writes consistency problem cold (Q5) — it's the most common correctness bug with replica routing, and the three solutions (route post-write reads to primary, LSN-based read-after-write, synchronous replication for specific writes) are the depth signal. The routing failure modes (Q6) matter as much as the happy path — specifically the thundering herd on replica failure and the silent fallback that overloads the primary without alerting. For schema questions, know that `SELECT FOR UPDATE` must go to the primary even though it "looks like a read" — this trips up many candidates. The replication lag causes (Q3) question rewards candidates who can name all four delay sources (network, WAL write, WAL apply, MVCC snapshot) and explain that bulk operations cause apply lag because apply is single-threaded in PostgreSQL before version 16. The Aurora vs. streaming replication distinction (Q9) is a good senior-level differentiator — Aurora's shared storage architecture means replica lag is measured in milliseconds, not seconds, which changes the read-your-writes analysis significantly.
