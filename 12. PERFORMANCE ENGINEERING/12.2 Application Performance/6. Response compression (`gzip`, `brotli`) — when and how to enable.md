# Performance: Response Compression (gzip, brotli) — Interview Q&A (5 YOE Level)

---

## Section 1: Compression Fundamentals

**Q1. How does HTTP response compression work mechanically — what is the negotiation protocol, and what happens at each layer between client and server?**
A: HTTP response compression is a content negotiation mechanism where the client advertises which compression algorithms it supports, the server chooses one, compresses the response body, and signals which algorithm was used. The raw bytes on the wire are smaller; the client decompresses before handing content to the application:

**The full negotiation and compression flow:**
```
Client (browser / mobile app / API client)
  │
  │  HTTP Request:
  │  GET /api/loans HTTP/1.1
  │  Host: api.myfintech.com
  │  Accept-Encoding: gzip, deflate, br   ← Client announces supported algorithms
  │                                          br = brotli; gzip; deflate (older)
  │
  ▼
Load Balancer / Nginx (TLS termination + compression)
  │
  │  Checks: does this response type benefit from compression?
  │  Checks: is the response large enough to compress? (threshold: typically 1KB)
  │  Checks: is this a compressible content-type? (JSON, HTML yes; JPEG, PNG no)
  │  Selects algorithm: prefer br > gzip (better ratio; if client supports both)
  │
  │  Compresses response body: 45,200 bytes → 3,840 bytes (91.5% reduction)
  │
  ▼
  HTTP Response:
  HTTP/1.1 200 OK
  Content-Encoding: gzip        ← Server signals which algorithm was used
  Content-Type: application/json
  Content-Length: 3840          ← Compressed size
  Vary: Accept-Encoding         ← Critical: tells CDNs/caches to vary by encoding
                                   Without this, a CDN might serve a gzip response
                                   to a client that sent Accept-Encoding: identity
  Transfer-Encoding: chunked    ← Often used with streaming compression
  [3,840 bytes of gzip-compressed JSON body]
  │
  ▼
Client decompresses:
  [45,200 bytes of JSON after decompression]
  JSON.parse(decompressedBody) → application receives full data
```

**What each header means and why it matters:**
```
Accept-Encoding: gzip, deflate, br
  Client → Server: "I can decompress any of these algorithms"
  Multiple values: preference order (br = brotli is listed last in the HTTP spec
  but servers know to prefer it; order doesn't strictly define preference)

Content-Encoding: gzip
  Server → Client: "I compressed the body with gzip; you must decompress with gzip"
  Without this header: client tries to parse compressed bytes as JSON → parse error

Content-Length: 3840
  The compressed byte count, not the original
  Used by client to know when the response is fully received
  Omitted with Transfer-Encoding: chunked (streaming responses)

Vary: Accept-Encoding
  Tells intermediate caches (CDN, reverse proxy, browser cache):
  "Cache this response keyed by the Accept-Encoding header"
  Without Vary: cache stores the gzip response; serves it to a client that
  sent Accept-Encoding: identity → client receives gzip bytes without
  decompression → corrupt response

Transfer-Encoding: chunked (vs. Content-Length)
  Chunked: response is streamed; each chunk prefixed with its size in hex
  Used when: total size is unknown at the start (streaming queries, large files)
  Content-Length: response buffered completely before sending
  Used when: size is known (small to medium responses buffered in app memory)
```

**Q2. What are the algorithmic differences between gzip, deflate, and brotli — what do they each optimize for, and why does brotli consistently outperform gzip for API responses?**
A: The three algorithms represent different generations of compression technology, each with distinct approaches to finding repetitive patterns in data:

**deflate (DEFLATE algorithm, 1993):**
```
Algorithm: LZ77 (Lempel-Ziv 1977) + Huffman coding
LZ77: scans forward in the data; replaces repeated sequences with
      (distance, length) back-references to earlier occurrences
Huffman coding: assigns shorter bit codes to more frequent symbols

Content-Encoding: deflate in practice is unreliably implemented
  (HTTP/1.1 spec says deflate should be raw DEFLATE; some servers send
   zlib-wrapped DEFLATE; some clients expect one, some expect the other)
  Result: interoperability bugs; most modern servers avoid deflate
  Modern usage: essentially replaced by gzip everywhere
```

**gzip (1992, widely standardized):**
```
Algorithm: DEFLATE (LZ77 + Huffman) + gzip framing
  - Same core algorithm as deflate
  - Adds: CRC32 checksum for integrity verification
  - Adds: gzip header (magic bytes, compression level, OS, filename)
  - Standard across ALL clients and servers since the early 2000s

Compression levels (in zlib/gzip):
  Level 1 (fastest): least compression; minimal CPU; ~60-70% of level 9's ratio
  Level 6 (default): good balance; used by most servers
  Level 9 (best):    maximum compression; 5-10× more CPU than level 6

Typical compression ratio for JSON API responses:
  JSON with many repeated keys: 85-92% size reduction
  e.g., 100KB JSON → 8-15KB gzip
  e.g., 10KB JSON → 1-2KB gzip

CPU cost (compression):   Low-medium (well-optimized C library)
CPU cost (decompression): Very low (~3ms for 100KB on modern hardware)
Dictionary size:          32KB sliding window (LZ77 lookback)
```

**brotli (2013, Google, RFC 7932):**
```
Algorithm: LZ77 + Huffman coding + context modeling (similar to gzip core)
Key differences from gzip:

1. Pre-defined static dictionary:
   brotli ships with a 122KB static dictionary of common substrings
   found in web content (HTML element names, HTTP headers, JavaScript
   keywords, CSS properties, JSON structure patterns)
   e.g., "Content-Type", "application/json", "\"status\":", "true", "false",
         "null" are all in the dictionary
   Effect: these common patterns are single-byte back-references instead of
           literal bytes — dramatic size savings for API JSON responses

2. Larger context window:
   Window size: up to 16MB (vs. gzip's 32KB)
   Effect: can find matches for patterns seen much earlier in the data
   For large JSON responses: repeated field names from page 1 can match
   structures from page 10 — gzip's 32KB window has forgotten them

3. Context modeling:
   Models the probability of the next byte given the recent context
   (similar to a simple language model)
   Effect: better Huffman code assignments for structured data like JSON

Compression ratio improvement over gzip:
  HTML:               20-26% smaller than gzip
  JavaScript:         15-25% smaller
  JSON API responses: 20-30% smaller (the static dictionary especially helps)
  Binary data:        Negligible improvement (random bytes have no patterns)

CPU cost (compression):   High — 3-10× more CPU than gzip level 6
                          Only practical at the edge or with pre-compression
                          NOT suitable for dynamic per-request compression at high RPS
CPU cost (decompression): Low — same order as gzip (very fast)
Dictionary size:          16MB + 122KB static dictionary

The asymmetry: brotli is slow to compress but fast to decompress.
This is ideal for servers (compress once or pre-compress; clients decompress fast).
```

**Practical comparison on a typical fintech API response:**
```
Payload: paginated loan list (50 loans, each with ~20 fields), ~45KB JSON

Algorithm        Compressed size   Ratio    Compression time  Decompression time
──────────────────────────────────────────────────────────────────────────────────
None             45,200 bytes     100%      0ms               0ms
deflate          3,920 bytes       8.7%     1.2ms             0.4ms
gzip level 6     3,840 bytes       8.5%     1.4ms             0.4ms
gzip level 9     3,600 bytes       8.0%     6.8ms             0.4ms
brotli level 4   2,980 bytes       6.6%     4.1ms             0.5ms
brotli level 6   2,840 bytes       6.3%     8.2ms             0.5ms
brotli level 11  2,710 bytes       6.0%    215ms              0.5ms

Key insight: brotli level 4-6 beats gzip level 9 in ratio while taking
similar or less time to compress — the static dictionary provides "free" gains
that no amount of extra gzip computation can match.
```

## Section 2: When to Enable Compression

**Q3. What are the conditions under which compression provides a net performance benefit, and what are the scenarios where it actively hurts performance?**
A: Compression is a CPU-for-bandwidth trade-off. It always reduces bytes on the wire and always costs CPU time. The net performance benefit depends on whether the bandwidth savings outweigh the CPU overhead — which depends on response size, content type, network conditions, and server load:

**When compression provides clear net benefit:**
```
Condition 1 — Response body > 1KB:
  Below 1KB, the TCP handshake and HTTP headers dominate transfer time.
  Compressing a 200-byte response saves ~150 bytes but costs 0.3ms of CPU.
  The 150 bytes transfers in ~0.01ms on a 100Mbps link.
  Net: compression costs more in CPU than it saves in transfer time.

  Most middleware uses a 1KB minimum threshold:
    Express compression: threshold=1024 (default)
    Nginx: gzip_min_length 1024 (recommended)

  Above 1KB, savings grow rapidly:
    1KB JSON:   ~800 bytes compressed (20% savings) →  negligible benefit
    10KB JSON:  ~1.2KB compressed (88% savings)     →  clear benefit (7× smaller)
    100KB JSON: ~9KB compressed (91% savings)        →  huge benefit (11× smaller)

Condition 2 — Text-based content types:
  Compression exploits repetition in data. Structured text has extreme repetition:
  JSON: field names repeat in every object; "null", "true", "false" repeat constantly
  HTML: tag names, attributes, class names repeat
  JavaScript: keywords, variable names, common patterns repeat
  CSV: column names repeated across thousands of rows

  Typical compression ratios by content type:
    application/json:    85-93% size reduction  ← excellent
    text/html:           75-85% size reduction
    text/javascript:     75-85% size reduction
    text/css:            80-90% size reduction
    text/plain:          60-80% size reduction (depends on content)

Condition 3 — Network is the bottleneck:
  If clients are on 4G/5G mobile networks, bandwidth is precious.
  A loan application response of 45KB takes:
    Without compression: 45KB ÷ 2Mbps (4G) = 180ms transfer time
    With gzip:           4KB ÷ 2Mbps       =  16ms transfer time
    Savings: 164ms per response — dramatic UX improvement

  If clients are on the same LAN/datacenter:
    45KB ÷ 10Gbps = 0.036ms transfer time
    With gzip: 4KB ÷ 10Gbps = 0.003ms
    Savings: 0.033ms — negligible; compression overhead dominates
```

**When compression hurts or provides no benefit:**
```
Scenario 1 — Already-compressed binary formats:
  JPEG, PNG, WebP, MP4, ZIP, PDF, gzip-already:
    These formats use their own compression internally.
    Trying to gzip a JPEG produces a file LARGER than the original
    (gzip adds header overhead; finds no patterns to exploit).
    Always configure content-type exclusions for these formats.

  Never compress:
    image/jpeg, image/png, image/webp, image/gif
    audio/mpeg, audio/ogg, video/mp4
    application/zip, application/gzip, application/x-tar
    application/octet-stream (arbitrary binary)
    application/pdf (already compressed internally)

Scenario 2 — High RPS + dynamic per-request compression at high CPU load:
  Server already at 80% CPU; adding gzip compression adds 15% CPU per request.
  Result: CPU hits 100% → event loop lag increases → latency rises → no benefit.
  The compression saves 5ms of network transfer but adds 20ms of latency (queue depth).
  Net: compression actively hurts performance when server is CPU-constrained.

  Mitigation: enable compression only at the reverse proxy (Nginx/CDN);
  Node.js process doesn't compress; proxy handles it efficiently in C.

Scenario 3 — Very small responses (< 1KB):
  A 200-byte "health check" response: {"status": "ok"}
    With gzip: adds ~20 bytes of gzip header + header overhead; output ~60 bytes
    Without: 200 bytes transferred + 0 CPU
    Net benefit: negative (gzip output + header overhead ≈ uncompressed)

Scenario 4 — Streaming responses where first-byte latency matters:
  Some compression algorithms (gzip with full buffering) require the entire
  response to be buffered before compression begins.
  For a streaming endpoint (real-time loan status updates via SSE):
    Buffering adds latency to first byte: entire page buffered before sending
    Use: streaming gzip (compress and flush each chunk) or disable compression
    SSE (text/event-stream): gzip streaming works; chunked transfer with flush

Scenario 5 — Already-compressed upstream response being proxied:
  If your Node.js service calls a downstream service that returns gzip,
  and you proxy that response without modifying it:
    Don't decompress → recompress → send
    Instead: pass through the Content-Encoding header; forward compressed bytes
    Recompression: wastes CPU; may produce worse ratio (artifacts from re-encoding)
```

## Section 3: Enabling Compression in Node.js / NestJS

**Q4. How do you enable compression in an Express/NestJS application, what are the correct configuration options, and what is the right layer to do compression at in a production architecture?**
A: Compression in a production Node.js application should almost never be done in the Node.js process itself — it should be handled by Nginx, a CDN, or the load balancer. The Node.js `compression` middleware is appropriate only in specific contexts:

**The production architecture decision:**
```
Development / simple deployment:
  Client → Node.js (handles TLS, compression, routing, app logic)
  Node.js compression middleware: appropriate (no Nginx)
  Downside: CPU-bound compression competes with app logic CPU

Production (recommended for fintech):
  Client → CDN (CloudFront / Akamai) → Nginx (compression) → Node.js (app logic only)
                                             │
                                             ├── Nginx compresses: text/*, application/json
                                             ├── Uses gzip level 6 + brotli level 4
                                             ├── Serves cached compressed responses
                                             └── Node.js process: zero compression CPU

  Node.js process is NOT responsible for compression in this architecture.
  It returns uncompressed responses to Nginx; Nginx compresses efficiently in C.
  Node.js CPU 100% dedicated to business logic.
```

**Option A — Node.js middleware (for development or simple single-server deployment):**
```typescript
// NestJS with Express adapter
// npm install compression @types/compression

import compression from 'compression';
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.use(compression({
    // Level: 1-9 (1=fast/less compression; 9=slow/max compression)
    // Level 6: best balance for dynamic responses
    level: 6,

    // Minimum response size to compress (bytes)
    // Below this: don't compress (overhead exceeds savings)
    threshold: 1024,  // 1KB

    // Custom filter function: control which responses get compressed
    filter: (req, res) => {
      // Never compress responses that the client explicitly opted out of
      if (req.headers['x-no-compression']) return false;

      // Use the default content-type filter for everything else
      // Default: compresses text/*, application/json, application/javascript, etc.
      // Default: skips image/*, video/*, audio/*, application/zip, etc.
      return compression.filter(req, res);
    },

    // Memory level for zlib (1-9; default 8)
    // Higher = more memory used per compression stream; slightly better ratio
    // In high-concurrency scenarios: lower memLevel to reduce memory per connection
    memLevel: 8,

    // windowBits: size of the history buffer (8-15; gzip requires 15+16)
    // Higher = better compression; more memory per stream
    windowBits: 15,
  }));

  await app.listen(3000);
}

// For NestJS with Fastify adapter (more performant):
import { NestFactory } from '@nestjs/core';
import { FastifyAdapter, NestFastifyApplication } from '@nestjs/platform-fastify';
import compressPlugin from '@fastify/compress';

async function bootstrap() {
  const app = await NestFactory.create<NestFastifyApplication>(
    AppModule,
    new FastifyAdapter(),
  );

  await app.register(compressPlugin, {
    global: true,
    encodings: ['br', 'gzip'],    // Prefer brotli; fall back to gzip
    brotliOptions: {
      params: {
        [require('zlib').constants.BROTLI_PARAM_QUALITY]: 4,  // Level 4: good ratio, fast
      },
    },
    zlibOptions: {
      level: 6,                   // gzip level 6
    },
    threshold: 1024,              // Minimum 1KB to compress
    // Fastify uses content-type filter automatically for appropriate types
  });

  await app.listen(3000, '0.0.0.0');
}
```

```nginx
  brotli_types

    text/html
    text/css
    text/javascript
    application/json
    application/javascript
    image/svg+xml;

  # When both gzip and brotli are configured:
  # Nginx selects based on Accept-Encoding: if client sends 'br', use brotli
  # If client sends only 'gzip', use gzip
  # Priority: brotli > gzip (better ratio; all modern browsers support brotli)

  # ─── PROXY TO NODE.JS ─────────────────────────────────────────────────
  location /api/ {

    proxy_http_version 1.1;
    proxy_set_header   Upgrade           $http_upgrade;
    proxy_set_header   Connection        'upgrade';
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;

    # Do NOT pass Accept-Encoding to Node.js backend
    # Node.js returns uncompressed; Nginx handles compression
    proxy_set_header   Accept-Encoding   "";

    # Response buffering (allows Nginx to compress before sending)
    proxy_buffering    on;
    proxy_buffer_size  128k;
    proxy_buffers      4 256k;

    # Timeouts
    proxy_connect_timeout 60s;
    proxy_read_timeout    60s;

  # ─── STATIC ASSETS (pre-compressed) ───────────────────────────────────
  location /static/ {
    root /var/www/myfintech;

    # Serve pre-compressed files if they exist
    # If /static/bundle.js.br exists: serve it for Accept-Encoding: br requests
    # If /static/bundle.js.gz exists: serve it for Accept-Encoding: gzip requests
    gzip_static on;
    brotli_static on;
    # These directives serve pre-compressed files without CPU cost at serve time
  }
}
```

**Q5. How do you implement brotli compression specifically, what are the quality levels, and why is level 4 the recommended default for dynamic API responses?**
A: Brotli has 12 compression levels (0-11), and the choice of level is critical — the ratio between compression ratio improvement and CPU cost becomes highly unfavorable above level 6 for dynamic content:

```
Brotli quality levels — CPU time vs. compression ratio:

Quality  CPU time (relative)  Size vs. gzip level 6  Use case
───────────────────────────────────────────────────────────────
0        0.1×                 Slightly larger         Never (worse than gzip)
1        0.3×                 Similar to gzip 1       Emergency fallback
2        0.5×                 Similar to gzip 4
3        0.8×                 Similar to gzip 6
4        1.0×                 10-15% smaller          ← Dynamic API responses
5        1.5×                 15-18% smaller
6        2.5×                 18-21% smaller          ← CDN pre-compression
7        4.0×                 20-22% smaller
8        8.0×                 22-24% smaller
9        15×                  23-25% smaller
10       30×                  24-26% smaller
11       50-200×              25-30% smaller          ← Static asset pre-compression

Why level 4 for dynamic responses:
  At level 4: CPU cost ≈ gzip level 6 (same order of magnitude)
              Ratio: 10-15% better than gzip level 6
  At level 6: CPU cost = 2.5× gzip level 6; ratio only 4-6% better than level 4
  At level 11: CPU cost = 50-200× gzip level 6; ratio only 15% better than level 4

  For a 45KB JSON response at 1000 req/sec:
    gzip level 6:    1,400ms/req × 1000 req/sec = 1.4 CPU-seconds/sec (1.4 CPUs)
    brotli level 4:  similar CPU cost; 12% smaller output
    brotli level 11: 70,000ms/req equivalent; 70 CPU-seconds/sec (70 CPUs!) ← impossible at scale

  Conclusion: brotli level 4 gives brotli's dictionary benefit (the main advantage
  over gzip) without the extreme CPU cost of higher levels.
  Levels 7-11 are only practical for static assets pre-compressed at build time.
```

```typescript
// Node.js: manual brotli compression with level control
import { createBrotliCompress, createGzip, BrotliOptions, ZlibOptions } from 'zlib';
import { pipeline } from 'stream/promises';

async function compressResponse(
  data: Buffer,
  acceptEncoding: string,
): Promise<{ buffer: Buffer; encoding: string }> {
  // Parse client's Accept-Encoding header
  const supportsBrotli = acceptEncoding.includes('br');
  const supportsGzip   = acceptEncoding.includes('gzip');

  if (supportsBrotli) {
    // Brotli compression — level 4 for dynamic content
    const brotliOptions: BrotliOptions = {
      params: {
        [require('zlib').constants.BROTLI_PARAM_QUALITY]: 4,  // Level 4
        [require('zlib').constants.BROTLI_PARAM_LGWIN]:   22, // Window size 4MB (2^22)
        // Larger window than default (2^22 vs 2^16): better compression for large responses
        // Only beneficial for responses > 64KB; negligible effect below
      },
    };

    const chunks: Buffer[] = [];
    await pipeline(
      Readable.from([data]),
      createBrotliCompress(brotliOptions),
      async function* (source) {
        for await (const chunk of source) chunks.push(chunk);
      },
    );
    return { buffer: Buffer.concat(chunks), encoding: 'br' };
  }

  if (supportsGzip) {
    // gzip compression — level 6 for dynamic content
    const gzipOptions: ZlibOptions = { level: 6 };
    const chunks: Buffer[] = [];
    await pipeline(
      Readable.from([data]),
      createGzip(gzipOptions),
      async function* (source) {
        for await (const chunk of source) chunks.push(chunk);
      },
    );
    return { buffer: Buffer.concat(chunks), encoding: 'gzip' };
  }

  // No compression support
  return { buffer: data, encoding: 'identity' };
}

// NestJS interceptor for selective compression of large responses
@Injectable()
export class CompressionInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler) {
    const req = context.switchToHttp().getRequest<Request>();
    const res = context.switchToHttp().getResponse<Response>();

    return next.handle().pipe(
      switchMap(async (data) => {
        const json     = JSON.stringify(data);
        const byteLen  = Buffer.byteLength(json, 'utf8');

        // Only compress if response is large enough
        if (byteLen < 1024) return data; // Let NestJS handle small responses normally

        const acceptEncoding = req.headers['accept-encoding'] ?? '';
        const { buffer, encoding } = await compressResponse(
          Buffer.from(json, 'utf8'),
          acceptEncoding,
        );

        res.setHeader('Content-Encoding', encoding);
        res.setHeader('Content-Length', buffer.length);
        res.setHeader('Vary', 'Accept-Encoding');
        res.setHeader('Content-Type', 'application/json');
        res.end(buffer);

        return null; // Signal that response has been handled manually
      }),
    );
  }
}
```

## Section 4: Pre-Compression and Caching

**Q6. What is static asset pre-compression, how does it eliminate runtime CPU cost entirely, and how do you integrate it into a Node.js build pipeline?**
A: Pre-compression generates compressed versions of static files at build time, storing them alongside the originals. At runtime, the server simply serves the pre-compressed file — no CPU cost at request time. This is the optimal strategy for any file that doesn't change between requests:

**What can be pre-compressed:**
```
Static assets (ideal for pre-compression):
  ✓ JavaScript bundles (bundle.js, chunk-*.js)
  ✓ CSS files (main.css, vendor.css)
  ✓ HTML files (index.html)
  ✓ SVG images
  ✓ Font files (woff, woff2 — though already compressed)
  ✓ JSON config files (i18n translations, feature flag configs)
  ✓ OpenAPI specs served as JSON/YAML

NOT suitable for pre-compression (change per request):
  ✗ API responses (user-specific data, dynamic queries)
  ✗ Server-sent events (real-time data)
  ✗ Response bodies generated from database queries

The directory layout after pre-compression:
  dist/
    static/
      bundle.js          (original, 850KB)
      bundle.js.gz       (gzip pre-compressed, 210KB)
      bundle.js.br       (brotli pre-compressed, 175KB)
      vendor.js          (original, 1.2MB)
      vendor.js.gz       (298KB)
      vendor.js.br       (250KB)
      styles.css         (original, 120KB)
      styles.css.gz      (18KB)
      styles.css.br      (15KB)
```

**Build-time pre-compression pipeline:**
```typescript
// scripts/compress-assets.ts — run as part of the build process
import { createGzip, createBrotliCompress } from 'zlib';
import { pipeline } from 'stream/promises';
import { createReadStream, createWriteStream } from 'fs';
import { readdir, stat } from 'fs/promises';
import path from 'path';
import { constants as zlibConstants } from 'zlib';

const COMPRESSIBLE_EXTENSIONS = new Set(['.js', '.css', '.html', '.json', '.svg', '.xml']);
const MIN_SIZE_BYTES = 1024; // Don't compress files smaller than 1KB

async function preCompressDirectory(dir: string): Promise<void> {
  const files = await readdir(dir, { recursive: true, withFileTypes: true });

  const compressibleFiles = files.filter(f =>
    f.isFile() &&
    COMPRESSIBLE_EXTENSIONS.has(path.extname(f.name).toLowerCase())
  );

  console.log(`Pre-compressing ${compressibleFiles.length} files in ${dir}...`);

  await Promise.all(compressibleFiles.map(async (file) => {
    const filePath = path.join(dir, file.name);
    const fileStats = await stat(filePath);

    if (fileStats.size < MIN_SIZE_BYTES) {
      console.log(`  Skipping ${file.name} (${fileStats.size} bytes < 1KB threshold)`);
      return;
    }

    // Generate gzip version
    await pipeline(
      createReadStream(filePath),
      createGzip({ level: 9 }), // Level 9: maximum — CPU cost paid once at build time
      createWriteStream(`${filePath}.gz`),
    );

    // Generate brotli version (level 11: maximum quality; build-time only)
    await pipeline(
      createReadStream(filePath),
      createBrotliCompress({
        params: {
          [zlibConstants.BROTLI_PARAM_QUALITY]: 11,  // Maximum quality at build time
          [zlibConstants.BROTLI_PARAM_LGWIN]:   24,  // 16MB window (maximum)
        },
      }),
      createWriteStream(`${filePath}.br`),
    );

    const gzipStats  = await stat(`${filePath}.gz`);
    const brotliStats = await stat(`${filePath}.br`);

    console.log([
      `  ${file.name}:`,
      `  original=${(fileStats.size / 1024).toFixed(1)}KB`,
      `  gzip=${(gzipStats.size / 1024).toFixed(1)}KB (${Math.round(gzipStats.size / fileStats.size * 100)}%)`,
      `  brotli=${(brotliStats.size / 1024).toFixed(1)}KB (${Math.round(brotliStats.size / fileStats.size * 100)}%)`,
    ].join(' '));
  }));

  console.log('Pre-compression complete.');
}

preCompressDirectory('dist/static').catch(console.error);
```

**Q7. How does compression interact with HTTP caching and CDN behavior — what does `Vary: Accept-Encoding` do, and what breaks if you omit it?**
A: The `Vary` header is a critical component of compression correctness. It instructs caches (browser cache, CDN, reverse proxy) to treat responses with different `Accept-Encoding` values as separate cache entries. Omitting it causes cache poisoning — serving a compressed response to a client that cannot decompress it:

**What Vary: Accept-Encoding does:**
```
Without Vary header (WRONG):

  Request 1: Client A (browser, supports gzip)
    GET /api/loans
    Accept-Encoding: gzip
    → Server responds with: Content-Encoding: gzip, body=<compressed>
    → CDN caches this response (no Vary: the CDN doesn't know encoding matters)
    → Cache key: GET /api/loans

  Request 2: Client B (old IoT device, no compression support)
    GET /api/loans
    Accept-Encoding: identity (or no Accept-Encoding header)
    → CDN checks cache: GET /api/loans → HIT!
    → CDN serves the cached gzip response to Client B
    → Client B receives gzip bytes, tries to parse as JSON
    → JSON parse error: {"result": [{"id": "\x1f\x8b..."]} ← garbage
    → Application failure

With Vary: Accept-Encoding (CORRECT):

  Cache key for CDN: GET /api/loans + Accept-Encoding: gzip
    → Separate cache entry for each encoding
  Cache key for CDN: GET /api/loans + Accept-Encoding: identity
    → Different cache entry
  Cache key for CDN: GET /api/loans + Accept-Encoding: br
    → Another separate cache entry

  Client B gets the correct uncompressed response from its own cache entry.
```

**Implementation across all layers:**

## Section 6: Common Mistakes and Edge Cases

**Q9. What are the most common compression configuration mistakes in production, and what symptoms does each produce?**
A: Compression misconfiguration is subtle — the application often appears to work correctly while silently serving incorrect or inefficient responses:

**Mistake 1 — Missing `Vary: Accept-Encoding` header:**
```
Symptom: Intermittent JSON parse errors for some clients
         CDN cache hit rate suddenly drops after enabling compression
         Some users get garbage data; others work fine

Root cause: CDN caches the gzip response without Vary header
            Serves gzip bytes to clients that didn't request compression

Diagnosis:
  curl -sI https://api.myfintech.com/api/loans | grep -i vary
  → (no output) ← Vary header missing!

Fix (Nginx):
  gzip_vary on;  ← This single directive adds Vary: Accept-Encoding automatically

Fix (Node.js middleware):
  The 'compression' npm package sets Vary automatically when it compresses.
  If you're doing manual compression: always set res.setHeader('Vary', 'Accept-Encoding')
```

**Mistake 2 — Compressing already-compressed content:**
```
Symptom: Some responses are LARGER after "compression" is enabled
         JPEG/PNG download size increases by ~20 bytes (gzip header overhead)
         PDF responses arrive corrupted (double-compressed)

Root cause: compression applied to image/video/pdf content-types
            These are already compressed; gzip adds header overhead without reducing size

Diagnosis:
  curl -sI -H "Accept-Encoding: gzip" https://api.myfintech.com/upload/document.pdf
  Content-Encoding: gzip  ← Being compressed unnecessarily
  Content-Length: 152480  ← PDF is 152KB — original might have been 150KB!

Fix (Nginx): Ensure gzip_types does NOT include application/pdf, image/*
  gzip_types text/plain text/html application/json ...;
  # No wildcards; no image/*; no application/pdf

Fix (Node.js compression middleware):
  app.use(compression({
    filter: (req, res) => {
      const contentType = res.getHeader('Content-Type') ?? '';
      // Reject already-compressed types
      if (/image|video|audio|zip|gzip|pdf/i.test(contentType.toString())) {
        return false;
      }
      return compression.filter(req, res);
    },
  }));
```

**Mistake 3 — Compressing small responses (< 1KB) and adding overhead:**
```
Symptom: Health check endpoint response is larger than expected
         Simple {"status":"ok"} response has Content-Encoding: gzip
         But Content-Length is 45 bytes (gzip header = 20 bytes overhead!)

Root cause: no minimum size threshold configured; even tiny responses compressed
            gzip header alone is ~20 bytes; for a 24-byte "ok" response,
            compressed output is ~44 bytes — larger than uncompressed

Diagnosis:
  curl -v -H "Accept-Encoding: gzip" https://api.myfintech.com/health 2>&1 \
    | grep -E "< Content|body"

Fix: set threshold
  app.use(compression({ threshold: 1024 }));      // Node.js
  gzip_min_length 1024;                            // Nginx
  brotli_min_length 1024;                          // Nginx brotli
```

**Mistake 4 — Double compression (app + proxy both compress):**
```
Symptom: Content-Encoding: gzip header present; client receives garbage
         Browser shows: "net::ERR_CONTENT_DECODING_FAILED"
         curl: error: Failed writing body

Root cause: Node.js app compresses response; Nginx also compresses the gzip output
            Client receives gzip(gzip(data)) — not valid gzip; decompression fails

Diagnosis:
  # Check if backend is already sending compressed:
  curl -v http://localhost:3000/api/loans 2>&1 | grep "Content-Encoding"
  Content-Encoding: gzip  ← Node.js IS compressing

  # And check if Nginx is also compressing:
  curl -v -H "Accept-Encoding: gzip" https://api.myfintech.com/api/loans 2>&1 \
    | grep "Content-Encoding"
  Content-Encoding: gzip  ← And Nginx compresses again → double-gzip → broken

Fix: choose ONE layer for compression, not both
  Option A: Remove compression middleware from Node.js; let Nginx handle it
    Nginx: proxy_set_header Accept-Encoding "";  ← Don't forward Accept-Encoding to Node.js
           (Node.js receives no Accept-Encoding → doesn't compress → Nginx compresses)

  Option B: Disable Nginx gzip for proxied responses; let Node.js handle it
    Nginx: gzip_proxied off;  ← Don't compress proxied responses
           (But then: Nginx can't benefit from caching; less efficient)
  
  Option A is strongly preferred.
```

**Mistake 5 — Not setting `Accept-Encoding: ""` when proxying to backend:**
```
Symptom: Node.js process CPU is higher than expected
         Both Nginx AND Node.js are doing compression work

Root cause: Nginx forwards the client's Accept-Encoding header to Node.js
            Node.js sees Accept-Encoding: br → compresses with brotli
            Nginx receives brotli-compressed body
            Nginx cannot further compress it (already compressed)
            But Nginx already did the brotli work; Node.js also did it

Fix in Nginx:
  location /api/ {
    proxy_pass http://nodejs_backend;
    proxy_set_header Accept-Encoding "";  ← Strip Accept-Encoding before proxying
    # Node.js sees no Accept-Encoding → returns uncompressed JSON
    # Nginx receives uncompressed JSON → compresses → sends to client
    # Only Nginx compresses; Node.js CPU is free for business logic
  }
```

**Q10. How do streaming responses (SSE, chunked transfer, WebSockets) interact with compression, and what are the specific considerations for each?**
A: Streaming responses require compression to flush buffers incrementally rather than accumulating the entire response before compressing. Each protocol has different compression requirements:

```typescript
// Server-Sent Events (SSE) with gzip streaming
// SSE is text-based — high compression potential; but flushes frequently

@Controller('events')
export class EventController {
  @Get('loan-status/:loanId')
  @Header('Content-Type', 'text/event-stream')
  @Header('Cache-Control', 'no-cache')
  @Header('Connection', 'keep-alive')
  async streamLoanStatus(
    @Param('loanId') loanId: string,
    @Req() req: Request,
    @Res() res: Response,
  ): Promise<void> {
    const acceptEncoding = req.headers['accept-encoding'] ?? '';

    // Set up compression stream that FLUSHES on each write
    let compressStream: NodeJS.ReadableStream | null = null;

    if (acceptEncoding.includes('gzip')) {
      const gzip = createGzip({
        level: 6,
        flush: require('zlib').constants.Z_SYNC_FLUSH,
        // Z_SYNC_FLUSH: flush the compressor output buffer immediately after each write
        // Without this: gzip buffers data waiting for a "full block" → SSE events delayed!
        // With Z_SYNC_FLUSH: each event is compressed and sent immediately
      });

      res.setHeader('Content-Encoding', 'gzip');
      res.setHeader('Vary', 'Accept-Encoding');
      gzip.pipe(res);
      compressStream = gzip as unknown as NodeJS.ReadableStream;
    } else {
      compressStream = null;
    }

    // Send SSE events
    const write = (data: string) => {
      const chunk = `data: ${data}\n\n`;
      if (compressStream) {
        (compressStream as any).write(chunk);
        // With Z_SYNC_FLUSH, this immediately sends compressed data
      } else {
        res.write(chunk);
      }
    };

    // Subscribe to loan status changes
    const subscription = this.loanEvents
      .filter(event => event.loanId === loanId)
      .subscribe(event => {
        write(JSON.stringify(event));
      });

    // Keep-alive ping every 15 seconds (prevents proxy/load balancer timeout)
    const keepAlive = setInterval(() => write(':ping'), 15000);

    req.on('close', () => {
      subscription.unsubscribe();
      clearInterval(keepAlive);
      if (compressStream) (compressStream as any).end();
    });
  }
}

// Nginx configuration for SSE with compression:
location /events/ {
  proxy_pass         http://nodejs_backend;
  proxy_http_version 1.1;
  proxy_set_header   Connection '';

  # CRITICAL for SSE: disable proxy buffering
  # Without this: Nginx buffers the SSE stream and doesn't send events immediately
  proxy_buffering    off;
  proxy_cache        off;

  # SSE events must arrive at client immediately after each flush
  # gzip_proxied any is OK for SSE if the backend handles Z_SYNC_FLUSH correctly

  # Timeout: SSE connections are long-lived; increase proxy read timeout
  proxy_read_timeout 3600s;  # 1 hour
}

// Chunked transfer with brotli — streaming large report downloads
@Get('reports/loans/download')
async downloadLoanReport(@Req() req: Request, @Res() res: Response): Promise<void> {
  res.setHeader('Content-Type', 'application/json');

  const acceptEncoding = req.headers['accept-encoding'] ?? '';

  if (acceptEncoding.includes('br')) {
    const brotli = createBrotliCompress({
      params: {
        [require('zlib').constants.BROTLI_PARAM_QUALITY]: 4,
        // Streaming brotli: lower quality for faster flushing
        // Level 4 compresses quickly; don't use level 11 for streaming
      },
      flush: require('zlib').constants.BROTLI_OPERATION_FLUSH,
    });

    res.setHeader('Content-Encoding', 'br');
    res.setHeader('Vary', 'Accept-Encoding');
    res.setHeader('Transfer-Encoding', 'chunked');  // Size unknown; stream it

    brotli.pipe(res);

    // Stream the report row by row — never hold entire dataset in memory
    const cursor = this.reportRepo.streamAll();
    let first = true;

    brotli.write('[');
    for await (const loan of cursor) {
      if (!first) brotli.write(',');
      brotli.write(JSON.stringify(loan));
      first = false;
      // Brotli accumulates internally; flushes when buffer is full
      // For very large reports: periodic manual flush
    }
    brotli.write(']');
    brotli.end();
  }
}
```

**Tip for the interview:** At 5 YOE, compression questions are design questions, not configuration lookup exercises. The signal the examiner is looking for: the **layered architecture decision** (Q4) — compression should live at Nginx/CDN, not in the Node.js process, with `proxy_set_header Accept-Encoding ""` stripping the header before forwarding to Node.js — this shows you understand the CPU trade-off and don't want compression competing with business logic on the event loop. Know **why brotli is better for JSON specifically** (Q2) — the static dictionary containing JSON structural patterns ("\"status\":", "true", "false", "null") is the mechanism behind the 20-30% improvement over gzip, not just "it's a newer algorithm." The **Vary: Accept-Encoding omission** (Q9) is the most common real-world production bug — knowing the symptom (intermittent JSON parse errors, CDN cache poisoning) and the fix (a single `gzip_vary on` in Nginx) demonstrates operational experience. For the **pre-compression pattern** (Q6), the key insight is that brotli level 11 (which takes 50-200× more CPU than gzip) only becomes practical at build time — at runtime you use level 4, but static assets get level 11 once and served forever with zero CPU cost.
