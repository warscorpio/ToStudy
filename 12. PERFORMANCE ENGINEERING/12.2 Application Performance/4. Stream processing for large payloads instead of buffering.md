## Section 1: The Buffering Problem

**Q1. What is the difference between buffering and streaming, and why does buffering fail at scale?**
A: Buffering means accumulating the entire payload into memory before processing begins. Streaming means processing data incrementally as it arrives, never holding more than a small window in memory at any time. The difference is not about latency alone — it is about whether memory consumption is proportional to payload size or bounded by a constant.

```
Buffered model — memory grows with payload:

  Client ──[chunk 1]──[chunk 2]──[chunk 3]──[chunk N]──► Server buffer (RAM)
                                                              │
                                                         [full payload]
                                                              │
                                                         processing begins
                                                              │
                                                         response sent

  Memory footprint per request: O(payload_size)
  100 concurrent uploads of 500MB each: 50GB RAM required just for buffers.
  Before processing starts: entire payload must arrive.
  If the server crashes mid-upload: nothing was processed.

Streamed model — memory bounded by window size:

  Client ──[chunk 1]──► [parse] ──► [process] ──► [write to DB/disk/S3]
               ──[chunk 2]──► [parse] ──► [process] ──► [write]
               ──[chunk 3]──► [parse] ──► [process] ──► [write]

  Memory footprint per request: O(window_size) — typically 8KB–64KB
  100 concurrent uploads of 500MB each: 100 × 64KB = 6.4MB RAM
  Processing begins immediately as first chunk arrives.
  If server crashes mid-upload: already-processed chunks are committed.
```

The failure modes of buffering at scale:

```
Failure 1 — Out of Memory (OOM):
  A single large upload or a spike of medium uploads exhausts RAM.
  OS starts swapping → all requests slow to disk speed.
  Kernel OOM killer terminates the process → all in-flight requests lost.
  Symptom: server crashes under load with no CPU bottleneck; memory spikes to 100%.

Failure 2 — Amplified attack surface:
  An attacker sends a 4GB "upload" (HTTP body with Content-Length: 4000000000).
  Buffering server allocates 4GB per connection, then awaits data that trickles in.
  10 such connections = 40GB allocated. Server OOM before any data arrives.
  Streaming server: allocates a 64KB window; the trickle fills only that window.
  No amplification — the attacker gets nothing for free.

Failure 3 — Head-of-line blocking:
  A large buffered upload occupies a connection and memory until fully buffered.
  Other requests wait behind it.
  Streaming: the large upload is processed incrementally; connection handles
  backpressure; other connections are not blocked.

Failure 4 — Time-to-first-byte (TTFB) latency:
  Buffered CSV import: 10,000 rows arrive; processing starts after last byte.
  If the CSV is 100MB at 10MB/s: 10-second wait before row 1 is processed.
  Streamed CSV import: row 1 is processed as soon as it arrives (~50ms).
  For webhook consumers, database importers, ETL pipelines:
  streaming reduces effective latency by orders of magnitude.
```

**Q2. What are the core abstractions of stream processing — sources, transforms, sinks, and backpressure?**
A: Every streaming system, regardless of language or framework, is built from four primitives. Understanding these abstractions lets you reason about any streaming pipeline regardless of the specific library.

```
Source (Producer):
  Generates data incrementally. Knows nothing about consumers.
  Examples:
    - Incoming HTTP request body (chunks arrive from network)
    - File read (OS returns chunks as disk seeks complete)
    - Database cursor (fetches rows in batches)
    - S3 GetObject response body
    - Kafka consumer (messages from a partition)

Transform (Processor):
  Receives chunks from a source, produces transformed chunks downstream.
  May change chunk size, format, or content.
  Must not accumulate the full input — processes per-chunk.
  Examples:
    - Gunzip: compressed chunks → decompressed chunks
    - CSV parser: byte chunks → parsed row objects
    - JSON validator: byte chunks → validated JSON records
    - Encryption/decryption: plaintext chunks → ciphertext chunks
    - Base64 decoder: encoded chunks → binary chunks

Sink (Consumer):
  Receives chunks and terminates the stream. Produces a final result or side effect.
  Examples:
    - File write: chunks → bytes on disk
    - S3 multipart upload: chunks → object in S3
    - Database batch insert: row chunks → rows in DB
    - HTTP response body: chunks → bytes sent to client

Backpressure:
  The mechanism by which a slow sink signals a fast source to slow down.
  Without backpressure: the source produces faster than the sink consumes →
  chunks accumulate in memory between them → OOM.
  With backpressure: sink says "I'm full; pause" → source pauses → memory stays bounded.

  ┌────────┐  "send chunk"   ┌───────────┐  "send chunk"   ┌──────┐
  │ Source │ ──────────────► │ Transform │ ──────────────► │ Sink │
  │        │ ◄────────────── │           │ ◄────────────── │      │
  └────────┘  "I'm ready"    └───────────┘  "I'm ready"    └──────┘
                             ↑                              ↑
                        backpressure                  backpressure
                        propagates upstream           signal (e.g.,
                                                      TCP flow control,
                                                      async generator yield)

Backpressure implementations:
  Node.js Streams: stream.pause() / stream.resume(); 'drain' event.
  Python asyncio: async generators (yield suspends producer until consumer ready).
  HTTP: TCP flow control — if the client's TCP receive buffer fills, the kernel
        stops ACKing bytes, which tells the sender to stop sending.
  S3 multipart: upload the next part only after receiving ETag for the previous.
```

```python
# request_streaming.py — reading HTTP bodies as streams

from fastapi import FastAPI, Request, HTTPException
from fastapi.responses import StreamingResponse
import asyncio, orjson, hashlib

app = FastAPI()

# ── THE WRONG WAY: buffer everything ─────────────────────────────────────────

@app.post("/api/upload/wrong")
async def upload_buffered(request: Request):
    body = await request.body()          # ← reads ENTIRE body into RAM
    # At this point: body is a bytes object of the full payload.
    # If payload is 500MB: 500MB allocated before any processing.
    data = orjson.loads(body)
    return {"size": len(body)}


# ── THE RIGHT WAY: iterate chunks ────────────────────────────────────────────

@app.post("/api/upload/stream")
async def upload_streamed(request: Request):
    """
    Streams the request body in chunks.
    Memory at any point: one chunk (typically 64KB from the OS socket buffer).
    """
    total_bytes = 0
    hasher      = hashlib.sha256()

    async for chunk in request.stream():
        # chunk: bytes — OS-sized (typically 4KB–64KB depending on network conditions)
        if not chunk:
            break
        total_bytes += len(chunk)
        hasher.update(chunk)           # process chunk immediately
        # The chunk is processed and eligible for GC — not accumulated

        # Guard: reject oversized payloads before they finish arriving
        if total_bytes > 100 * 1024 * 1024:   # 100MB limit
            raise HTTPException(413, "Payload too large")

    return {
        "sha256":      hasher.hexdigest(),
        "total_bytes": total_bytes,
    }

import boto3
from botocore.config import Config
import io

s3 = boto3.client("s3", config=Config(max_pool_connections=50))

@app.post("/api/upload/s3/{filename}")
async def upload_to_s3_streamed(request: Request, filename: str):
    """
    Stream upload directly to S3 without buffering the payload in memory.
    Uses S3 multipart upload: each part is 5MB; only one part in RAM at a time.
    """
    PART_SIZE    = 5 * 1024 * 1024   # S3 minimum part size: 5MB
    MAX_SIZE     = 5 * 1024 * 1024 * 1024   # 5GB max (S3 multipart supports up to 5TB)
    BUCKET       = "my-upload-bucket"

    # Initiate multipart upload
    mpu = s3.create_multipart_upload(Bucket=BUCKET, Key=filename)
    upload_id = mpu["UploadId"]
    parts     = []
    part_num  = 1
    buffer    = bytearray()
    total     = 0

    try:
        async for chunk in request.stream():
            if not chunk:
                break

            total += len(chunk)
            if total > MAX_SIZE:
                raise HTTPException(413, "Upload too large")

            buffer.extend(chunk)

            # Once buffer reaches PART_SIZE, upload this part to S3
            while len(buffer) >= PART_SIZE:
                part_data = bytes(buffer[:PART_SIZE])
                buffer    = buffer[PART_SIZE:]

                # Upload part (runs in thread pool — s3.upload_part is sync boto3)
                loop     = asyncio.get_event_loop()
                response = await loop.run_in_executor(
                    None,
                    lambda d=part_data, n=part_num: s3.upload_part(
                        Bucket=BUCKET, Key=filename,
                        UploadId=upload_id, PartNumber=n, Body=d,
                    )
                )
                parts.append({"PartNumber": part_num, "ETag": response["ETag"]})
                part_num += 1
                # part_data is now GC-eligible — only PART_SIZE in memory per part

        # Upload the final (possibly smaller) part
        if buffer:
            loop     = asyncio.get_event_loop()
            response = await loop.run_in_executor(
                None,
                lambda d=bytes(buffer): s3.upload_part(
                    Bucket=BUCKET, Key=filename,
                    UploadId=upload_id, PartNumber=part_num, Body=d,
                )
            )
            parts.append({"PartNumber": part_num, "ETag": response["ETag"]})

        # Complete the multipart upload
        await loop.run_in_executor(
            None,
            lambda: s3.complete_multipart_upload(
                Bucket=BUCKET, Key=filename, UploadId=upload_id,
                MultipartUpload={"Parts": sorted(parts, key=lambda p: p["PartNumber"])},
            )
        )

        return {"key": filename, "size": total, "parts": len(parts)}

    except Exception as exc:
        # Always abort multipart upload on failure to avoid orphaned storage
        await loop.run_in_executor(
            None,
            lambda: s3.abort_multipart_upload(
                Bucket=BUCKET, Key=filename, UploadId=upload_id
            )
        )
        raise

import csv, io

@app.post("/api/import/loans")
async def import_loans_csv(request: Request):
    """
    Stream a CSV file and insert rows into DB without loading the full CSV.
    Memory: one DB batch (1000 rows) + one chunk of CSV bytes at a time.
    """
    BATCH_SIZE = 1000
    MAX_ROWS   = 1_000_000

    batch   = []
    total   = 0
    errors  = []
    remainder = b""   # bytes from previous chunk that didn't form a complete line

    async for chunk in request.stream():
        if not chunk:
            break

        # Prepend any incomplete line from the previous chunk
        data  = remainder + chunk
        lines = data.split(b"\n")

        # The last element may be an incomplete line — save for next chunk
        remainder = lines[-1]
        complete_lines = lines[:-1]

        for line_bytes in complete_lines:
            if not line_bytes.strip():
                continue

            try:
                # Parse each CSV line individually
                row = next(csv.reader([line_bytes.decode("utf-8")]))
                if total == 0:
                    # First row: skip header
                    total += 1
                    continue

                batch.append({
                    "borrower_name": row[0],
                    "amount":        float(row[1]),
                    "status":        row[2],
                })
                total += 1

                if total > MAX_ROWS:
                    raise HTTPException(422, f"Maximum {MAX_ROWS} rows per import")

            except (IndexError, ValueError) as e:
                errors.append({"row": total, "error": str(e)})
                continue

            # When batch is full: flush to DB, yield to event loop
            if len(batch) >= BATCH_SIZE:
                await _insert_loan_batch(batch)
                batch.clear()
                await asyncio.sleep(0)   # yield between batches

    # Process final partial batch
    if remainder.strip():
        try:
            row = next(csv.reader([remainder.decode("utf-8")]))
            batch.append({"borrower_name": row[0], "amount": float(row[1]), "status": row[2]})
        except Exception:
            pass

    if batch:
        await _insert_loan_batch(batch)

    return {
        "total_rows": total - 1,   # subtract header
        "errors":     len(errors),
        "error_sample": errors[:10],
    }


async def _insert_loan_batch(batch: list[dict]) -> None:
    async with db_pool.acquire() as conn:
        await conn.executemany(
            "INSERT INTO loans (borrower_name, amount, status) VALUES ($1, $2, $3)",
            [(r["borrower_name"], r["amount"], r["status"]) for r in batch],
        )
```

```javascript
// node_streaming.js — HTTP request body streaming patterns

const { pipeline, Transform, Writable } = require("stream");
const { pipeline: pipelineAsync }       = require("stream/promises");
const fs   = require("fs");
const zlib = require("zlib");
const csv  = require("csv-parse");   // npm install csv-parse

// ── PATTERN 1: async iteration (cleanest — Node.js 12+) ──────────────────────

// Express/Fastify handler — read request as async iterable
app.post("/api/upload/stream", async (req, res) => {
    let totalBytes = 0;
    const hash     = require("crypto").createHash("sha256");
    const MAX_SIZE = 100 * 1024 * 1024;   // 100MB

    // req is a Readable stream — iterate it directly
    for await (const chunk of req) {
        totalBytes += chunk.length;
        if (totalBytes > MAX_SIZE) {
            // Destroy the request stream — stops reading, sends TCP RST
            req.destroy(new Error("Payload too large"));
            return res.status(413).json({ error: "Payload too large" });
        }
        hash.update(chunk);
        // chunk is processed and eligible for GC immediately
    }

    res.json({ sha256: hash.digest("hex"), totalBytes });
});

//   - Backpressure between stages
//   - Error propagation (error in any stage destroys all stages)
//   - Cleanup (destroys streams on completion or error)
// stream.pipe() does NOT properly handle errors — always prefer pipeline().

        // pipeline() already destroyed all streams — just respond with error
        res.status(500).json({ error: err.message });

// ── PATTERN 3: Transform streams for per-chunk processing ────────────────────

class LoanValidator extends Transform {
    constructor(options = {}) {
        super({ ...options, objectMode: true });   // input: objects, output: objects
        this.rowCount   = 0;
        this.errorCount = 0;
    }

    _transform(record, encoding, callback) {
        this.rowCount++;
        const amount = parseFloat(record.amount);

        if (isNaN(amount) || amount <= 0) {
            this.errorCount++;
            // Skip invalid records — don't push downstream
            return callback();
        }

        if (amount > 1_000_000) {
            this.errorCount++;
            return callback(new Error(`Row ${this.rowCount}: amount exceeds limit`));
        }

        // Valid: push downstream
        this.push({ ...record, amount, validated: true });
        callback();
    }

    _flush(callback) {
        // Called when the upstream source has ended
        // Emit summary as the last item
        this.push({ _summary: true, total: this.rowCount, errors: this.errorCount });
        callback();
    }
}

class DatabaseBatchWriter extends Writable {
    constructor(pool, batchSize = 1000) {
        super({ objectMode: true });
        this.pool      = pool;
        this.batchSize = batchSize;
        this.batch     = [];
    }

    async _write(record, encoding, callback) {
        if (record._summary) {
            // Flush any remaining batch
            if (this.batch.length > 0) await this._flushBatch();
            callback();
            return;
        }

        this.batch.push(record);

        if (this.batch.length >= this.batchSize) {
            try {
                await this._flushBatch();
                callback();
            } catch (err) {
                callback(err);
            }
        } else {
            callback();   // signal: ready for next record (backpressure)
        }
    }

    async _final(callback) {
        // _final is called when all _write() calls are done
        try {
            if (this.batch.length > 0) await this._flushBatch();
            callback();
        } catch (err) {
            callback(err);
        }
    }

    async _flushBatch() {
        const client = await this.pool.connect();
        try {
            const values = this.batch.map((r, i) =>
                `($${i * 3 + 1}, $${i * 3 + 2}, $${i * 3 + 3})`
            ).join(", ");
            const params = this.batch.flatMap(r => [r.borrower_name, r.amount, r.status]);

            await client.query(
                `INSERT INTO loans (borrower_name, amount, status) VALUES ${values}`,
                params
            );
            this.batch = [];
        } finally {
            client.release();
        }
    }
}

        res.status(422).json({ error: err.message });
    }
});
```

```python
# response_streaming.py — streaming HTTP responses

from fastapi.responses import StreamingResponse
import asyncio, orjson, asyncpg

# ── STREAMING A DATABASE QUERY RESULT ─────────────────────────────────────────

@app.get("/api/loans/export")
async def export_loans(org_id: str):
    """
    Stream all loans for an org as NDJSON (newline-delimited JSON).
    Memory: one row at a time — regardless of whether there are 100 or 10 million rows.
    The client receives rows as they're fetched; no waiting for the full query.
    """

    async def generate_rows():
        async with db_pool.acquire() as conn:
            # asyncpg cursor — fetches rows in batches, not all at once
            async with conn.transaction():
                async for row in conn.cursor(
                    "SELECT id, borrower_name, amount, status, created_at "
                    "FROM loans WHERE org_id = $1 ORDER BY created_at DESC",
                    org_id,
                    prefetch=500,   # fetch 500 rows at a time from DB

                    # Yield one row at a time — each yields to event loop
                    yield orjson.dumps(dict(row)) + b"\n"

    return StreamingResponse(
        generate_rows(),
        media_type="application/x-ndjson",
        headers={"X-Accel-Buffering": "no"},   # disable nginx buffering for this response
    )
```

## Section 4: Streaming Parsers

**Q6. How do you implement a streaming JSON parser for large payloads — avoiding loading the full JSON into memory?**
A: Standard JSON parsers (`json.loads`, `JSON.parse`) are "all-or-nothing" — they require the complete document before returning anything. Streaming JSON parsers emit objects as they encounter complete values, processing arbitrarily large documents with bounded memory.

```python
# Streaming JSON parsing with ijson

import ijson
import io, asyncio

# ── PATTERN: stream a JSON array from an HTTP body ───────────────────────────

@app.post("/api/import/bulk")
async def bulk_import_streamed(request: Request):
    """
    Input: {"records": [{"name": "...", "amount": ...}, ...]}
    with potentially millions of records.
    Memory: one record at a time, regardless of total array size.
    """
    BATCH_SIZE = 1000
    batch      = []
    total      = 0
    errors     = []

    # Collect chunks from the HTTP body
    # (ijson requires a synchronous file-like object — we use a custom adapter)
    chunks_received = []
    async for chunk in request.stream():
        chunks_received.append(chunk)

    # Run ijson in a thread pool (it's a C extension, releases GIL)
    def parse_with_ijson() -> list:
        """Parse the JSON stream incrementally, yielding one record at a time."""
        raw    = b"".join(chunks_received)
        stream = io.BytesIO(raw)
        return list(ijson.items(stream, "records.item"))
        # ijson.items() is a generator — internally processes one event at a time
        # The list() call materializes results, but ijson never holds the full JSON
        # tree in memory — it emits each completed record and discards it.

    loop    = asyncio.get_event_loop()
    records = await loop.run_in_executor(None, parse_with_ijson)

    # Process records in batches
    for record in records:
        try:
            validated = LoanRecord(**record)
            batch.append(validated)
            total += 1
        except Exception as e:
            errors.append({"record": total, "error": str(e)})

        if len(batch) >= BATCH_SIZE:
            await _insert_loan_batch(batch)
            batch.clear()
            await asyncio.sleep(0)

    if batch:
        await _insert_loan_batch(batch)

    return {"total": total, "errors": len(errors)}


# ── ASYNC WRAPPER: true chunk-by-chunk ijson parsing ─────────────────────────
# For very large streams where even collecting all chunks is too much:

class AsyncChunkReader:
    """
    Adapts an async request stream into a synchronous file-like object
    for ijson. Used with asyncio.to_thread() to run ijson without buffering
    the entire body first.
    """
    def __init__(self, stream_generator):
        self._gen     = stream_generator
        self._buffer  = b""
        self._loop    = asyncio.get_event_loop()
        self._done    = False

    def read(self, size: int = -1) -> bytes:
        """Called by ijson — runs in a thread, but fetches async chunks via loop."""
        if self._done:
            return b""

        # Fetch chunks until we have enough bytes or the stream ends
        while len(self._buffer) < size or size == -1:
            try:
                chunk = self._loop.run_until_complete(self._gen.__anext__())
                self._buffer += chunk
                if size != -1 and len(self._buffer) >= size:
                    break
            except StopAsyncIteration:
                self._done = True
                break

        if size == -1:
            result, self._buffer = self._buffer, b""
        else:
            result, self._buffer = self._buffer[:size], self._buffer[size:]
        return result
```

**Q7. How do you design an API format for large datasets — why NDJSON beats JSON arrays for streaming?**
A: The choice of wire format determines whether streaming is possible at all. A JSON array `[{...}, {...}, ...]` requires a streaming parser to process without buffering. NDJSON (Newline-Delimited JSON) requires no streaming parser — each line is a standalone, complete JSON document.

```
JSON array format:
  [{
    "id": "L-001", "amount": 5000, "status": "pending"
  },{
    "id": "L-002", "amount": 7500, "status": "approved"
  }]

  Problems for streaming:
    - The parser cannot emit a complete record until it sees the closing "}"
      and the following "," or "]" — any character may continue the object.
    - Requires a stateful streaming parser (ijson, stream-json) with overhead.
    - Total size unknown until the final "]" — cannot stream a count header.
    - Easy to produce a malformed array (unclosed bracket, extra comma).

NDJSON format (also called JSONL, JSON Lines):
  {"id": "L-001", "amount": 5000, "status": "pending"}
  {"id": "L-002", "amount": 7500, "status": "approved"}

  Advantages for streaming:
    - Each line is a complete, independently parseable JSON document.
    - Split on "\n" → parse each line with JSON.parse() / json.loads().
    - No streaming parser library needed — readline() does it.
    - A corrupt line can be skipped without affecting subsequent lines.
    - Easy to append records (just write a new line) — no JSON formatting.
    - Naturally supports schema evolution: different lines can have different fields.
    - Standard tools: jq, grep, awk, split all work line-by-line.
    - Gzip compresses NDJSON efficiently — repeated field names compress well.

  Conventions:
    - One JSON object per line (not arrays, not primitives).
    - Each object on exactly one line (no pretty-printing).
    - Last line may or may not have a trailing newline — handle both.
    - Content-Type: application/x-ndjson or application/jsonl.

NDJSON export implementation:

  async def generate_ndjson(query_result):
      async for row in query_result:
          yield orjson.dumps(dict(row)) + b"\\n"
          # Each row is complete — consumer can parse it immediately

  NDJSON import implementation (far simpler than JSON array streaming):

      lines = data.split(b"\\n")
      remainder = lines[-1]
      for line in lines[:-1]:
          if line.strip():

              await process(record)

Format comparison for a 10M row export:

  Format         Size    Parse memory  Client receives first row  Library required
  ─────────────  ──────  ────────────  ─────────────────────────  ─────────────────
  JSON array     ~2GB    ~2GB          After all 10M rows arrive  streaming parser
  NDJSON         ~2GB    ~1KB          After first row            readline
  NDJSON+gzip    ~400MB  ~1KB          After first decompressed   readline + gunzip
  Parquet        ~200MB  varies        N/A (columnar, not row)    Parquet library
  Arrow IPC      ~300MB  varies        After first batch          Arrow library

  Winner for streaming row-by-row: NDJSON (or NDJSON+gzip for transfer size).
  Winner for analytical queries: Parquet (columnar compression, vectorized reads).
```

## Section 5: Backpressure Implementation

**Q8. How do you implement backpressure correctly — preventing a fast producer from overwhelming a slow consumer?**
A: Backpressure is the mechanism that keeps streaming memory-bounded. Without it, a fast producer fills an unbounded in-memory queue and you've just recreated buffering with extra steps.

```python
# backpressure.py — implementing backpressure in async generators

import asyncio
from typing import AsyncIterator, AsyncGenerator

# ── THE PROBLEM: unbounded queue between producer and consumer ────────────────

async def bad_pipeline(source: AsyncIterator, sink_fn):
    """
    No backpressure: if source is fast and sink is slow,
    'queue' grows without bound → OOM.
    """
    queue = asyncio.Queue()   # unbounded!

    async def produce():
        async for item in source:
            await queue.put(item)   # if queue fills → ??? (it never fills — unbounded)
        await queue.put(None)

    async def consume():
        while True:
            item = await queue.get()
            if item is None:
                break
            await sink_fn(item)   # slow sink — queue grows while this runs

    await asyncio.gather(produce(), consume())
    # If sink_fn takes 1 second per item and source produces 1000 items/second:
    # queue grows by 999 items/second → OOM in minutes.


# ── CORRECT: bounded queue with backpressure ──────────────────────────────────

async def pipeline_with_backpressure(
    source:   AsyncIterator,
    sink_fn,
    buffer_size: int = 10,   # at most 10 items in flight between producer and consumer
):
    """
    Bounded queue: when the queue is full, the producer blocks (backpressure).
    Memory bounded by: buffer_size × item_size.
    """
    queue = asyncio.Queue(maxsize=buffer_size)   # bounded!

    async def produce():
        async for item in source:
            await queue.put(item)   # blocks when queue is full → producer slows down
        await queue.put(None)       # sentinel

    async def consume():
        while True:
            item = await queue.get()
            if item is None:
                break
            await sink_fn(item)
            queue.task_done()

    await asyncio.gather(produce(), consume())
    # If sink is slow: queue fills to 10 items, then produce() blocks on put().
    # Producer only resumes when consumer frees space. Memory stays bounded.


# ── NATURAL BACKPRESSURE: async generators ────────────────────────────────────
# The cleanest Python pattern — async generators have backpressure built in.
# The producer (yield) suspends until the consumer calls __anext__().
# No explicit queue needed.

async def chunked_s3_reader(bucket: str, key: str) -> AsyncGenerator[bytes, None]:
    """Producer: yields chunks from S3. Suspends between yields."""
    session = aiobotocore.session.get_session()
    async with session.create_client("s3") as s3:
        response = await s3.get_object(Bucket=bucket, Key=key)
        async with response["Body"] as stream:
            async for chunk in stream.iter_chunks(65536):
                yield chunk
                # Control returns to consumer here. Producer pauses until
                # consumer calls `async for` again (natural backpressure).

async def write_to_db(chunks: AsyncGenerator[bytes, None], conn):
    """Consumer: reads from the async generator at its own pace."""
    parser  = StreamingCSVParser()
    batch   = []

    async for chunk in chunks:

        for row in parser.feed(chunk):
            batch.append(row)
            if len(batch) >= 1000:
                await conn.executemany("INSERT INTO ...", batch)
                batch.clear()
                # After flush: consumer is ready for more → resumes producer

    if batch:
        await conn.executemany("INSERT INTO ...", batch)

# Usage — natural backpressure, no explicit queue:
async with db_pool.acquire() as conn:
    await write_to_db(chunked_s3_reader("my-bucket", "loans.csv"), conn)


# ── NODE.JS BACKPRESSURE: drain event ─────────────────────────────────────────
// In Node.js: writable.write() returns false when the internal buffer is full.
// Producer must pause and wait for the 'drain' event before writing more.
// pipeline() handles this automatically — a key reason to always use pipeline().

async function writeWithBackpressure(readable, writable) {
    for await (const chunk of readable) {
        const canContinue = writable.write(chunk);
        if (!canContinue) {
            // Writable buffer is full — wait for it to drain before sending more
            await new Promise(resolve => writable.once("drain", resolve));
        }
    }
    writable.end();
}

// stream.pipeline() does this automatically — it wires up 'drain' events
// and pause()/resume() calls between all stages. Always prefer pipeline()
// over manual pipe() or manual drain handling.
```

**Q9. How do you handle errors and partial failures in a streaming pipeline — the challenge of no rollback?**
A: Streaming pipelines process and commit data incrementally. Unlike buffered processing where you can reject the entire payload before touching the database, streaming commits are partial — if the stream fails at 60%, the first 60% is already in the database.

```python
# streaming_error_handling.py — dealing with partial commitment

# ── STRATEGY 1: idempotent writes (preferred) ────────────────────────────────
# Design the write operation so that re-running it produces the same result.
# If the stream fails at 60% and is retried: records 0–60% are re-written
# but produce no duplicate (upsert / INSERT ... ON CONFLICT DO NOTHING).

@app.post("/api/import/idempotent")
async def import_idempotent(request: Request):
    """
    Uses external_id as the idempotency key.
    Re-importing the same file is safe — duplicates are ignored.
    """
    batch       = []
    total       = 0
    duplicates  = 0
    errors      = []
    remainder   = b""

    async for chunk in request.stream():
        data  = remainder + chunk
        lines = data.split(b"\n")
        remainder = lines[-1]

        for line in lines[:-1]:
            if not line.strip():
                continue
            try:
                record = orjson.loads(line)
                batch.append(record)
                total += 1
            except Exception as e:
                errors.append({"line": total, "error": str(e)})

            if len(batch) >= 1000:
                dupes = await _upsert_batch(batch)
                duplicates += dupes
                batch.clear()
                await asyncio.sleep(0)

    if batch:
        dupes = await _upsert_batch(batch)
        duplicates += dupes

    return {"total": total, "duplicates": duplicates, "errors": len(errors)}


async def _upsert_batch(batch: list[dict]) -> int:
    """
    INSERT ... ON CONFLICT DO NOTHING — safe to re-run on the same data.
    Returns the count of records that were skipped (duplicates).
    """
    async with db_pool.acquire() as conn:
        result = await conn.executemany("""
            INSERT INTO loans (external_id, borrower_name, amount, status)
            VALUES ($1, $2, $3, $4)
            ON CONFLICT (external_id) DO NOTHING
        """, [(r["external_id"], r["borrower_name"], r["amount"], r["status"])
               for r in batch])
    # executemany doesn't easily return "skipped" count — use execute with RETURNING
    # for precise duplicate counting if needed.
    return 0   # simplified

# Track progress: record which rows have been committed.
# On retry: skip already-processed rows.

@app.post("/api/import/resumable/{upload_id}")
async def import_resumable(request: Request, upload_id: str):
    """
    Client supplies an upload_id to identify this import session.
    On failure, client can retry with the same upload_id.
    Already-committed rows are skipped.
    """
    # Load or create import session state
    state = await redis.hgetall(f"import:{upload_id}") or {}
    committed_rows = int(state.get(b"committed_rows", 0))

    batch       = []
    row_number  = 0
    remainder   = b""

    async for chunk in request.stream():
        data  = remainder + chunk
        lines = data.split(b"\n")
        remainder = lines[-1]

        for line in lines[:-1]:
            if not line.strip():
                continue

            row_number += 1

            # Skip rows already committed in a previous attempt
            if row_number <= committed_rows:
                continue

            try:
                record = orjson.loads(line)
                batch.append(record)
            except Exception:
                continue   # skip malformed lines

            if len(batch) >= 1000:
                await _insert_batch(batch)
                committed_rows += len(batch)
                batch.clear()

                # Persist progress: survives a crash
                await redis.hset(f"import:{upload_id}", "committed_rows", committed_rows)
                await asyncio.sleep(0)

    if batch:
        await _insert_batch(batch)
        committed_rows += len(batch)
        await redis.hset(f"import:{upload_id}", "committed_rows", committed_rows)

    await redis.hset(f"import:{upload_id}", "status", "completed")
    return {"upload_id": upload_id, "total_committed": committed_rows}


# ── STRATEGY 3: staging table (two-phase commit) ─────────────────────────────
# Stream into a staging table; validate; commit atomically to production table.
# Rollback is possible (truncate staging) without affecting production data.

@app.post("/api/import/staged")
async def import_staged(request: Request):

            CREATE TEMP TABLE import_{import_id} (
                external_id   TEXT,
                borrower_name TEXT,
                amount        NUMERIC,
                status        TEXT,
                row_number    INTEGER

        # Stream into staging (no constraints — fast inserts)
        batch      = []
        row_number = 0

            data  = remainder + chunk
            lines = data.split(b"\n")
            remainder = lines[-1]

                row_number += 1
                try:
                    r = orjson.loads(line)
                    batch.append((r["external_id"], r["borrower_name"],
                                  r["amount"], r["status"], row_number))

                if len(batch) >= 1000:
                    await conn.executemany(
                        f"INSERT INTO import_{import_id} VALUES ($1,$2,$3,$4,$5)", batch

                    batch.clear()
                    await asyncio.sleep(0)

            await conn.executemany(
                f"INSERT INTO import_{import_id} VALUES ($1,$2,$3,$4,$5)", batch
            )

        invalid = await conn.fetch(f"""
            SELECT row_number, external_id, borrower_name
            FROM import_{import_id}
            WHERE amount <= 0 OR amount > 10000000
            OR borrower_name IS NULL OR borrower_name = ''
            LIMIT 100
        """)

        if invalid:
            # Rollback: drop staging table (temp table auto-drops on session end)
            return JSONResponse(
                status_code=422,
                content={
                    "error": f"Validation failed: {len(invalid)} invalid rows",
                    "sample": [dict(r) for r in invalid[:10]],
                }
            )

        # Atomic commit: move from staging to production
        async with conn.transaction():
            await conn.execute(f"""
                INSERT INTO loans (external_id, borrower_name, amount, status)
                SELECT external_id, borrower_name, amount, status
                FROM import_{import_id}
                ON CONFLICT (external_id) DO NOTHING
            """)

        count = await conn.fetchval(f"SELECT COUNT(*) FROM import_{import_id}")
        return {"import_id": import_id, "committed": count}
```

**Q10. How do you stream data through a complete ETL pipeline — from S3 source through transform to database sink?**

```python
# etl_pipeline.py — production streaming ETL

import asyncio, orjson, gzip, csv, io
from dataclasses import dataclass
from typing import AsyncIterator

@dataclass
class LoanRecord:
    external_id:   str
    borrower_name: str
    amount:        float
    status:        str
    org_id:        str

# ── SOURCE: stream gzipped NDJSON from S3 ────────────────────────────────────

async def s3_ndjson_source(
    bucket: str,
    key:    str,
    chunk_size: int = 65536,
) -> AsyncIterator[LoanRecord]:
    """
    Streams a gzipped NDJSON file from S3.
    Yields one LoanRecord at a time.
    Memory: one compressed chunk (64KB) + decompressed lines + one record.
    """
    session = aiobotocore.session.get_session()
    decompressor = zlib.decompressobj(wbits=zlib.MAX_WBITS | 16)   # gzip mode
    remainder    = b""

    async with session.create_client("s3") as s3:
        response = await s3.get_object(Bucket=bucket, Key=key)
        async with response["Body"] as stream:
            async for compressed_chunk in stream.iter_chunks(chunk_size):
                # Decompress chunk — produces more bytes than the input
                decompressed = decompressor.decompress(compressed_chunk)

                # Split into lines, handling boundaries
                data  = remainder + decompressed
                lines = data.split(b"\n")
                remainder = lines[-1]

                for line in lines[:-1]:
                    if not line.strip():
                        continue
                    try:
                        raw = orjson.loads(line)
                        yield LoanRecord(
                            external_id   = raw["external_id"],
                            borrower_name = raw["borrower_name"],
                            amount        = float(raw["amount"]),
                            status        = raw.get("status", "pending"),
                            org_id        = raw["org_id"],
                        )
                    except (KeyError, ValueError, orjson.JSONDecodeError):
                        continue   # skip malformed records; log in production

    # Process any remaining bytes
    final = decompressor.flush()
    if final:
        for line in (remainder + final).split(b"\n"):
            if line.strip():
                try:
                    raw = orjson.loads(line)
                    yield LoanRecord(**raw)
                except Exception:
                    pass


# ── TRANSFORM: validate and enrich ───────────────────────────────────────────

async def validate_and_enrich(
    source: AsyncIterator[LoanRecord],
    org_lookup: dict[str, str],
) -> AsyncIterator[LoanRecord]:
    """
    Validates records and enriches with org data.
    Skips invalid records (could also collect them for error reporting).
    """
    async for record in source:
        # Validate
        if record.amount <= 0 or record.amount > 10_000_000:
            continue
        if not record.borrower_name.strip():
            continue
        if record.org_id not in org_lookup:
            continue

        # Enrich (in-memory lookup — no I/O per record)
        yield record


# ── SINK: batch insert to database ────────────────────────────────────────────

async def db_batch_sink(
    source:     AsyncIterator[LoanRecord],
    pool:       asyncpg.Pool,
    batch_size: int = 1000,
) -> dict:
    """
    Inserts records in batches. Returns summary statistics.
    """
    batch       = []
    total       = 0
    batch_count = 0

    async for record in source:
        batch.append(record)
        total += 1

        if len(batch) >= batch_size:
            await _flush_batch(pool, batch)
            batch_count += 1
            batch.clear()
            await asyncio.sleep(0)   # yield between batches

    if batch:
        await _flush_batch(pool, batch)
        batch_count += 1

    return {"total": total, "batches": batch_count}


async def _flush_batch(pool: asyncpg.Pool, batch: list[LoanRecord]) -> None:
    async with pool.acquire() as conn:
        await conn.executemany("""
            INSERT INTO loans (external_id, borrower_name, amount, status, org_id)
            VALUES ($1, $2, $3, $4, $5)
            ON CONFLICT (external_id) DO UPDATE
                SET status = EXCLUDED.status,
                    amount = EXCLUDED.amount
        """, [(r.external_id, r.borrower_name, r.amount, r.status, r.org_id)
               for r in batch])


# ── ORCHESTRATION: wire source → transform → sink ────────────────────────────

async def run_etl_pipeline(
    bucket:     str,
    key:        str,
    pool:       asyncpg.Pool,
) -> dict:
    """
    Runs the complete streaming ETL pipeline.
    At any point: at most one S3 chunk + one decompressed window + one DB batch in RAM.
    A 10GB gzipped file streams through with ~65MB peak memory.
    """
    # Load org lookup table once (small, fits in memory)
    async with pool.acquire() as conn:
        orgs = await conn.fetch("SELECT id, name FROM organizations WHERE active = true")
    org_lookup = {str(r["id"]): r["name"] for r in orgs}

    # Wire the pipeline — no data flows until we await the sink
    source    = s3_ndjson_source(bucket, key)
    transform = validate_and_enrich(source, org_lookup)
    result    = await db_batch_sink(transform, pool)

    return {
        **result,
        "source": f"s3://{bucket}/{key}",
        "memory": "bounded",   # O(batch_size) not O(file_size)
    }


# ── PARALLEL PIPELINE: process multiple S3 files concurrently ────────────────

async def run_parallel_etl(
    files:        list[tuple[str, str]],   # [(bucket, key), ...]
    pool:         asyncpg.Pool,
    max_parallel: int = 4,
) -> list[dict]:
    """
    Process multiple files in parallel with bounded concurrency.
    max_parallel=4: at most 4 files streaming simultaneously.
    Memory: max_parallel × (chunk_size + batch_memory) — still bounded.
    """
    semaphore = asyncio.Semaphore(max_parallel)

    async def run_one(bucket: str, key: str) -> dict:
        async with semaphore:
            return await run_etl_pipeline(bucket, key, pool)

    results = await asyncio.gather(*[
        run_one(bucket, key) for bucket, key in files
    ], return_exceptions=True)

    return [
        r if not isinstance(r, Exception) else {"error": str(r)}
        for r in results
    ]
```

**Q11. What are the operational trade-offs between streaming and buffering — when is buffering actually the right choice?**
A:

```
Streaming wins when:
  ┌─────────────────────────────────────────────────────────────────────────┐
  │ Payload size is large (> 1MB) or unpredictable                         │
  │ Multiple concurrent clients upload simultaneously                       │
  │ Time-to-first-byte matters (process row 1 before row N arrives)        │
  │ The system must be resilient to slow clients (slow loris attacks)       │
  │ Memory is constrained relative to payload sizes                        │
  │ Processing can begin before the payload is complete (pipeline model)   │
  │ Data comes from an infinite or very long source (event streams, CDC)   │
  └─────────────────────────────────────────────────────────────────────────┘

Buffering wins when:
  ┌─────────────────────────────────────────────────────────────────────────┐
  │ Payload is small and bounded (API requests < 64KB are almost always    │
  │ safe to buffer — a modern server has GB of RAM)                        │
  │                                                                         │
  │ The operation requires the full payload before any processing:         │
  │   - Cryptographic signature verification (HMAC over full body)         │
  │   - Schema validation where any field may reference any other field    │
  │   - JSON parsing for mutation (must see entire doc before writing)     │
  │   - Sorting or deduplication (requires all records before any output)  │
  │                                                                         │
  │ Atomicity is required: all-or-nothing processing where partial state   │
  │ is invalid. Streaming commits partial state; rollback is complex.      │
  │ (Though the staging table pattern — Q9 — mitigates this)               │
  │                                                                         │
  │ The client is trusted and fast (internal service-to-service calls      │
  │ over a LAN with a size cap — slow loris is not a threat)               │
  │                                                                         │
  │ Simplicity of implementation outweighs the memory cost at your scale   │
  └─────────────────────────────────────────────────────────────────────────┘

The pragmatic rule:
  Set a content-length limit (e.g., 1MB) at the reverse proxy (nginx, ALB).
  Below the limit: buffer freely — simpler code, negligible memory impact.
  Above the limit: require streaming; reject anything that doesn't use it.

  nginx configuration:
    client_max_body_size 1m;      # reject requests > 1MB at the proxy layer
                                   # Before reaching your application server.
  For endpoints that legitimately need large payloads:
    location /api/upload {
        client_max_body_size 0;   # unlimited — handle in application
        proxy_request_buffering off;   # DON'T buffer the request body in nginx
        # Without proxy_request_buffering off: nginx buffers the entire upload
        # before forwarding it to your app — defeating application-level streaming.
    }

  proxy_request_buffering off is the most commonly forgotten setting.
  Developers add streaming support in their application but leave nginx buffering
  the request — the application never sees chunks; it gets the full body at once.
  Check nginx config before assuming streaming is working end-to-end.
```

## Quick Reference: Streaming vs. Buffering Decision

| Dimension | Buffer | Stream |
|---|---|---|
| Payload size | < 1MB (bounded, small) | > 1MB or unbounded |
| Memory per request | O(payload size) | O(chunk size) — typically 64KB |
| Time to first processed record | After full payload arrives | Immediately (first chunk) |
| Error handling | Reject before any DB write | Requires idempotency or staging table |
| Code complexity | Lower | Higher |
| Atomic rollback | Trivial (nothing committed yet) | Complex (partial commits) |
| Slow client resilience | Poor (holds connection + memory) | Good (backpressure limits memory) |
| Signature verification | Easy (full body available) | Harder (accumulate HMAC incrementally) |
| Deduplication / sorting | Easy (full set available) | Hard (requires external state) |

## Quick Reference: Backpressure Mechanisms

| Runtime | Mechanism | How Producer Pauses |
|---|---|---|
| Node.js Streams | `writable.write()` returns `false` | Producer checks return value; waits for `drain` event |
| Node.js `pipeline()` | Automatic | `pipeline()` wires `pause()`/`resume()` between stages |
| Python async generator | `yield` suspends until consumer calls `__anext__()` | Natural — no explicit signaling |
| Python `asyncio.Queue(maxsize=N)` | `queue.put()` blocks when full | Producer awaits `put()` — resumes when consumer dequeues |
| HTTP / TCP | TCP flow control (kernel-level) | Kernel stops ACKing → sender pauses at TCP layer |
| S3 multipart | Sequential part uploads | Next part only uploaded after receiving ETag for previous |

## Quick Reference: Format Selection for Large Datasets

| Format | Streaming-friendly? | Parsing library | Gzip? | Best for |
|---|---|---|---|---|
| `NDJSON` | ✓ (split on `\n`) | None (readline) | Yes | Row-oriented streaming export/import |
| JSON array `[...]` | Partial (needs streaming parser) | `ijson`, `stream-json` | Yes | Existing APIs; small-medium arrays |
| CSV | ✓ (split on `\n`) | `csv`, `csv-parse` | Yes | Tabular data, spreadsheet compatibility |
| Gzipped NDJSON | ✓ (decompress → split `\n`) | `zlib` + readline | Built-in | Large row-oriented datasets |
| Parquet | ✗ (columnar, row-group buffered) | `pyarrow`, `parquet-js` | Built-in | Analytical queries, columnar access |
| Apache Arrow IPC | ✓ (record-batch streaming) | `pyarrow`, `arrow-js` | Optional | Zero-copy interprocess pipelines |
| Avro | ✓ (object container file) | `fastavro`, `avsc` | Optional | Schema evolution, Kafka pipelines |
| MessagePack (binary JSON) | Partial (streaming parsers exist) | `msgpack` | Yes | Binary efficiency over JSON |

**Tip for the interview:** At 5 YOE, the streaming question is almost never "what is a stream?" — it's either a design question ("design a CSV import API that handles 10GB files") or a debugging scenario ("your upload endpoint crashes under load — memory spikes to 100% and the process is OOM-killed"). Know the buffering failure modes cold (Q1) — the OOM amplification attack, the head-of-line blocking, and the memory formula (100 concurrent × 500MB = 50GB). The `proxy_request_buffering off` nginx setting (Q11) is a senior-level signal: developers add streaming in application code but nginx buffers the request body before forwarding — streaming is silently disabled at the proxy layer. For Node.js, know that `stream.pipe()` does not correctly handle errors or backpressure and that `pipeline()` from `stream/promises` is always the correct choice. The NDJSON vs. JSON array comparison (Q7) is a common design question — NDJSON requires no streaming parser (readline is sufficient), appends are O(1), and corrupted lines are isolated. For error handling in streaming pipelines (Q9), the three strategies — idempotent upserts, resumable import with progress tracking, and staging tables — cover different points on the atomicity/complexity trade-off, and knowing all three with their trade-offs distinguishes a thoughtful answer from a surface-level one.
