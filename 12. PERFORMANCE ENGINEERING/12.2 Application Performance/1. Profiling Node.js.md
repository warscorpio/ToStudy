# Performance (Node.js): Profiling — `node --prof`, Clinic.js — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why is profiling necessary, and what is the difference between profiling and benchmarking?**
A: **Benchmarking** measures the throughput or latency of a system under a defined load — "how many requests per second can this endpoint handle?" or "what is the p99 latency under 500 concurrent users?" Benchmarking tells you that something is slow; it doesn't tell you why.

**Profiling** is the process of measuring where time (or memory, or I/O) is actually spent during execution. It answers the "why" — which function is consuming CPU, which object is accumulating in the heap, which operation is blocking the event loop. Without profiling, performance optimisation is guesswork: developers fix what looks suspicious rather than what is actually the bottleneck.

The distinction matters operationally: an engineer who benchmarks and finds a 2-second response time might spend a week optimising the wrong function. An engineer who profiles first discovers that 1.8 seconds of the 2 seconds is spent in a JSON parsing step they never suspected, and fixes it in an hour.

**Two categories of profiling in Node.js:**

- **CPU profiling** — records which JavaScript functions are executing (on the CPU) at sampling intervals. Identifies CPU-bound bottlenecks: synchronous code that hogs the event loop, inefficient algorithms, hot functions called millions of times.

- **Memory profiling** — records heap allocation over time. Identifies memory leaks (objects accumulating without being garbage collected), excessive allocation rates (creating and discarding millions of short-lived objects), and bloated in-memory data structures.

A third concern specific to Node.js is **event loop lag** — the event loop being blocked by synchronous work, preventing timers and I/O callbacks from firing on time. Standard CPU profilers don't directly measure this; specialised tools (Clinic.js Doctor, `perf_hooks`) are needed.

**Q2. What is V8's sampling profiler, how does it work, and what does it measure?**
A: V8 (the JavaScript engine powering Node.js) includes a built-in sampling profiler that is exposed via the `--prof` flag. A sampling profiler works by:

1. Setting up a timer that fires at regular intervals — V8's default is every **1 millisecond**.
2. At each timer tick, the profiler captures the current **call stack** — the chain of function calls from the bottom of the stack up to the currently executing function.
3. The captured stack frames are recorded in a log file with their call addresses.
4. After the run, the log is processed to count how many samples each function appears in — functions that appear in many samples are consuming more CPU time.

**What it measures:** CPU time — specifically, the proportion of wall-clock time during which each function is on the call stack. A function that appears in 30% of samples was executing (or waiting for a call it made to return) during 30% of the profiling window.

**What it does not measure:**
- Time spent waiting for I/O — while a `fetch()` or DB query is in flight, the call stack is empty (the event loop is idle). The profiler records nothing for these periods. An endpoint that spends 500ms waiting for a database has almost no CPU profile — the profiler sees idle time, not the DB query.
- Memory allocation patterns.
- Event loop lag.

This is the critical nuance: a sampling CPU profile distinguishes I/O-bound from CPU-bound problems. If the profile is mostly empty (few samples captured relative to wall-clock time), the bottleneck is I/O, not CPU. If the profile is dense (many samples), something is computing heavily.

**Q3. What is the difference between a CPU profile, a flame graph, and a heap snapshot?**
A:

**CPU profile** — the raw data produced by a sampling profiler: a time-series of call stack snapshots. In V8, this is an `.isolate` log file. It's not human-readable in its raw form; it must be processed into something visualizable.

**Flame graph** — a visualisation of CPU profile data. The x-axis represents total time (or sample count); the y-axis represents call stack depth. Each rectangle is a function. Width indicates how much time the function was on the stack. Child functions are stacked above their callers. The "flame" shape emerges because hot paths (wide rectangles near the bottom) taper as they branch into specific callees.

Key reading rules:
- **Wide rectangle at the top** — this function is doing a lot of work itself (not delegating to callees).
- **Wide rectangle at the bottom with narrow children** — the parent spends little time itself but calls many functions.
- **Flat top** — the function at the top of a wide plateau is the actual bottleneck; optimising it will directly reduce CPU time.

**Heap snapshot** — a point-in-time capture of every object in the JavaScript heap: their type, size, references, and the retainer chain (what's keeping them alive). Unlike a CPU profile (which samples over time), a heap snapshot is an instantaneous freeze of memory state. Comparing two heap snapshots (before and after a load test) reveals which objects accumulated — the signature of a memory leak.

The three together form a diagnostic toolkit: flame graph for CPU bottlenecks, heap snapshot for memory leaks, and event loop metrics (from Clinic.js Doctor or `perf_hooks`) for blocking.

## Section 2: `node --prof`

**Q4. How do you use `node --prof` and `node --prof-process` to profile a Node.js application end-to-end?**
A: The `--prof` flag enables V8's tick profiler, which writes samples to an isolate log file as the process runs.

**Step 1 — Run with profiling enabled:**
```bash
# Start the application with profiling
node --prof dist/main.js

# Or for a NestJS app with a specific entrypoint
node --prof -r tsconfig-paths/register dist/main.js

# For a script rather than a server:
node --prof scripts/process-loans.js
```

This creates a file named `isolate-0xNNNNNNNNNNN-NNNNN-v8.log` in the working directory. The file name includes the isolate address and process ID.

**Step 2 — Generate load to profile (for a server):**
```bash
# In another terminal — generate representative traffic
# Using autocannon (npm install -g autocannon)
autocannon -c 50 -d 30 http://localhost:3000/api/loans

# Or Apache Bench
ab -n 10000 -c 50 http://localhost:3000/api/loans

# Or wrk
wrk -t 4 -c 50 -d 30s http://localhost:3000/api/loans
```

Profile under realistic load — idle profiling captures almost nothing useful.

**Step 3 — Stop the server and process the log:**
```bash
# Press Ctrl+C to stop the server (or let the script finish)

# Process the raw log into a human-readable text report
node --prof-process isolate-0x*.log > profile-report.txt
```

**Step 4 — Read the text report:**
```
Statistical profiling result from isolate-0x...log, (50000 ticks, 49000 unaccounted, 0 excluded).

 [Shared libraries]:
   ticks  total  nonlib   name
    512    1.0%          /usr/lib/libstdc++.so.6.0.29

 [JavaScript]:
   ticks  total  nonlib   name
   8234   16.5%   16.5%  LazyCompile: *validateDto /app/src/validation.ts:45:23
   4521    9.0%    9.0%  LazyCompile: *JSON.parse native
   3210    6.4%    6.4%  LazyCompile: *hashApiKey /app/src/auth/api-key.service.ts:82:3
   2891    5.8%    5.8%  LazyCompile: *computeEMI /app/src/loans/emi.service.ts:34:17
```

**Reading the output:**
- `ticks` — how many samples included this function on the stack.
- `total` — percentage of all samples.
- `nonlib` — percentage of non-library samples (excludes V8 internals and native code).
- `*` before a function name — the function was JIT-compiled (optimised). Functions without `*` were not optimised — a potential flag.
- `LazyCompile` — the function was compiled on first call (normal for JS).

In this example: `validateDto` is in 16.5% of samples — it's the top CPU consumer and the first target for optimisation.

**Step 5 — Convert to flame graph for visual analysis:**
```bash
# Using flamebearer (simpler)
npm install -g flamebearer
node --prof-process --preprocess -j isolate-0x*.log | flamebearer

# Or using 0x (wraps --prof automatically)
npm install -g 0x
0x dist/main.js
# (run load in another terminal, then Ctrl+C — 0x auto-generates a flame graph HTML)
```

**Q5. What does the `--prof-process` output's "unaccounted" ticks mean, and why does a large unaccounted percentage change your diagnosis?**
A: The `unaccounted` ticks in the `--prof-process` output represent samples where the profiler could not determine which JavaScript function was executing. This happens when:

1. **The process was idle** — the event loop was waiting for I/O. No JS was executing, so there's nothing to attribute the sample to. This is the most common cause.
2. **Native code was executing** — C++ code inside Node.js internals, a native addon, or libuv. The JS profiler can't attribute these to a JS function.
3. **JIT compilation** — V8 is compiling a function, not executing JS user code.
4. **Garbage collection** — the GC is running; the JS heap is paused.

```
Statistical profiling result from isolate-0x...log, (50000 ticks, 47500 unaccounted, 0 excluded).
```

**What 95% unaccounted means:** if 47,500 out of 50,000 ticks are unaccounted and only 2,500 appear in the JavaScript section, the application is spending only 5% of its time executing JavaScript. The remaining 95% is either:
- Waiting for I/O (the dominant interpretation for a web server) — the bottleneck is the database, a downstream API, or network latency.
- Garbage collection at scale — check the `--prof-process` output's GC section.
- A native addon consuming CPU — check shared libraries section.

**Diagnostic implication:** a high unaccounted percentage tells you NOT to optimise JavaScript. The bottleneck is outside JS — improve database query performance, add an index, reduce I/O round trips, cache upstream calls. Optimising the 5% of JS execution time would yield at most a 5% improvement. The real 95% gain comes from addressing the I/O bottleneck.

Conversely, a low unaccounted percentage (30-40%) and a dense JavaScript section indicates genuine CPU pressure — now the flame graph matters.

**Q6. How do you use `0x` as a more ergonomic alternative to raw `--prof`?**
A: `0x` is a wrapper around `--prof` that automates the log capture and flame graph generation, removing the manual steps of managing isolate log files and running `--prof-process`:

```bash
# Install globally
npm install -g 0x

# Profile a server (runs the server under 0x)
0x dist/main.js

# Profile with additional Node.js flags
0x --node-flags "--max-old-space-size=4096" dist/main.js

# Profile with environment variables
DATABASE_URL=postgres://... 0x dist/main.js

# Profile for a fixed duration then exit
0x --collect-only dist/main.js &
SERVER_PID=$!
sleep 30
autocannon -c 50 -d 20 http://localhost:3000/api/loans
kill -INT $SERVER_PID  # send SIGINT to trigger flame graph generation
```

When you press `Ctrl+C`, `0x`:
1. Stops the process.
2. Processes the isolate log.
3. Generates a self-contained HTML flame graph file (e.g., `0x-xxxxxx/flamegraph.html`).
4. Opens it in your browser (on supported platforms).

**`0x` vs raw `--prof`:**

| Aspect | `--prof` + `--prof-process` | `0x` |
|---|---|---|
| Setup | Manual — manage log files | Automatic |
| Output | Text report (readable) + manual flamegraph | Interactive HTML flame graph |
| Flamegraph quality | Requires extra tooling | Built-in, interactive |
| CI/CD integration | Scriptable | Scriptable with `--collect-only` |
| Customisation | Full control | Limited (opinionated defaults) |

For local development and incident diagnosis, `0x` is faster. For CI performance regression detection, raw `--prof` with scripted processing gives more control.

## Section 3: Clinic.js — Doctor, Flame, and Bubble

**Q7. What is Clinic.js, and how does it differ from `--prof`?**
A: Clinic.js is a suite of profiling and diagnostic tools from NearForm, designed specifically for Node.js. It goes beyond CPU sampling to provide a holistic view of a Node.js process's health — including event loop lag, I/O utilisation, memory growth, and CPU usage simultaneously.

**Clinic.js tools:**
- **`clinic doctor`** — the diagnostic triage tool. Monitors CPU, memory, event loop delay, and active handles over time. Produces a report with recommendations: "Event loop appears blocked", "Memory appears to be growing", "CPU is consistently above 80%." The starting point for any investigation.
- **`clinic flame`** — the CPU flame graph tool. Similar to `0x` but with better filtering, merging, and Node.js-specific annotations.
- **`clinic bubble`** — visualises async operations and I/O wait times as bubbles. Shows where time is spent waiting (the event queue depth and wait times), not just where CPU is spent. The tool for I/O-bound diagnosis.
- **`clinic heapprofiler`** — heap allocation profiling (sampling allocations, not just snapshots). Shows which functions are allocating the most memory over time.

**Key difference from `--prof`:** `--prof` and `0x` are purely CPU sampling tools. Clinic.js Doctor adds event loop lag measurement and memory monitoring, making it effective for:
- Problems that don't show up in a CPU profile (I/O blocking, event loop starvation).
- Establishing whether a problem is CPU-bound, I/O-bound, or memory-driven before choosing the more specific tool.

**Installation:**
```bash
npm install -g clinic
clinic --help
```

**Q8. How do you use `clinic doctor` to triage a performance problem, and how do you interpret its output?**
A: `clinic doctor` is the first tool to reach for when you know something is wrong but don't know why. It runs your process and wraps it with lightweight monitoring.

```bash
# Basic usage — runs the process and monitors it
clinic doctor -- node dist/main.js

# While the process runs, apply load in another terminal
autocannon -c 50 -d 30 http://localhost:3000/api/loans

# Ctrl+C to stop — clinic doctor generates a report
```

`clinic doctor` opens an HTML report in the browser showing four time-series panels:

**Panel 1 — CPU Usage (%):**
- Consistently near 100%: CPU-bound. The event loop is running flat out. Investigate with `clinic flame`.
- Consistently near 0%: I/O-bound. The event loop is idle, waiting for external I/O. Investigate with `clinic bubble` or trace the slow DB queries/API calls.
- Spiky (oscillates between high and low): normal for bursty traffic. Look at the spike timing relative to request timing.

**Panel 2 — Memory (RSS and Heap):**
- Steadily growing without plateau: memory leak. Investigate with `clinic heapprofiler` or V8 heap snapshots.
- Stable plateau: healthy — GC is managing memory.
- Sharp drops followed by growth: GC is cleaning up but can't keep pace — excessive allocation rate.

**Panel 3 — Event Loop Delay (ms):**
- Consistently > 10ms: the event loop is being blocked by synchronous work. Timers and I/O callbacks are delayed by this amount. Investigate with `clinic flame` to find the blocking synchronous code.
- Near 0ms: the event loop is responsive. I/O callbacks and timers fire promptly.
- Spiky with high peaks: occasional synchronous blocking — look for `JSON.parse()` of large payloads, synchronous file I/O, or heavy computation triggered by specific requests.

**Panel 4 — Active Handles:**
- Growing without bound: handle leak — HTTP connections, timers, or other handles are not being closed. Can cause memory growth and eventual process instability.
- Stable: healthy.

**`clinic doctor` diagnosis output (text summary):**
```
Recommendations:
  ⚠️  Event Loop: The event loop appears to be blocked.
      A blocked event loop results in degraded performance.
      Checkout clinic flame for a flamegraph to identify the problem.

  ✓  Memory: No memory issues detected.
  ✓  I/O: No I/O issues detected.
  ✓  CPU: CPU usage is normal.
```

This tells you exactly which tool to use next — `clinic doctor` is the triage, not the diagnosis.

**Q9. What does event loop delay measure, and what are the common Node.js patterns that cause it?**
A: Event loop delay (also called event loop lag) measures how late a timer fires relative to when it was scheduled. Node.js's event loop processes one callback at a time — if the current callback runs for 200ms synchronously, all other callbacks (including a 0ms timer) are delayed by 200ms.

**Measurement:**
```typescript
// How clinic doctor measures event loop delay
let lastMeasured = Date.now();

setInterval(() => {
  const now  = Date.now();
  const lag  = now - lastMeasured - 500;  // scheduled every 500ms; actual delay is the difference
  lastMeasured = now;
  if (lag > 50) console.warn(`Event loop lag: ${lag}ms`);
}, 500);
```

More precisely, using `perf_hooks`:
```typescript
import { monitorEventLoopDelay } from 'node:perf_hooks';

const h = monitorEventLoopDelay({ resolution: 20 });  // sample every 20ms
h.enable();

// Later, read the histogram
console.log('p50 lag:', h.percentile(50), 'ms');
console.log('p99 lag:', h.percentile(99), 'ms');
console.log('max lag:', h.max, 'ms');
h.disable();
```

**Common causes of event loop delay in production NestJS/Node.js applications:**

**1. Synchronous JSON parsing of large payloads:**
```typescript
// ANTI-PATTERN: parsing a 5MB JSON body blocks the event loop
app.use(express.json({ limit: '5mb' }));
// A single 5MB JSON.parse() can take 50-200ms, blocking all other requests
```

**2. Synchronous cryptographic operations on large data:**
```typescript
// ANTI-PATTERN: synchronous hashing of a large buffer
const hash = crypto.createHash('sha256').update(largeBuffer).digest('hex');
// Use crypto.createHash().update(chunk).update(chunk)... in a stream instead
```

**3. `Array.sort()` or heavy computation on large arrays:**
```typescript
// ANTI-PATTERN: sorting 100,000 loan records in-place on every request
const sorted = allLoans.sort((a, b) => b.amount - a.amount);
// Move to a background worker or pre-sort at write time
```

**4. `JSON.stringify()` on deeply nested or large objects:**
```typescript
// ANTI-PATTERN: serializing a huge response object synchronously
res.json(veryLargeObjectWith10000Records);
// Use pagination, streaming, or limit response size
```

**5. Synchronous file I/O:**
```typescript
// ANTI-PATTERN: blocking the event loop while reading a file
const data = fs.readFileSync('/etc/config/large-config.json');
// Use fs.promises.readFile() or streaming
```

**6. bcrypt with high cost factor on a non-worker thread:**
```typescript
// bcrypt with cost factor 12+ blocks the event loop for 200-500ms per hash
// (bcrypt is CPU-intensive by design for passwords)
const hash = await bcrypt.hash(password, 14);  // blocks for ~1 second
// Run in a worker thread or use bcrypt's async version which still blocks — use argon2 with libsodium bindings
```

**Q10. How does `clinic flame` differ from a raw `0x` flame graph, and what Node.js-specific features does it add?**
A: `clinic flame` generates a flame graph from CPU profiling data like `0x`, but adds several Node.js-specific features that make diagnosis faster:

```bash
# Run with clinic flame
clinic flame -- node dist/main.js

# Apply load
autocannon -c 50 -d 30 http://localhost:3000/api/loans

# Ctrl+C — flame graph generated automatically
```

**Differences from `0x`:**

**1. Automatic hot-path detection:** `clinic flame` highlights the hottest functions with colour intensity (darker = more time). Clicking a frame focuses the view on that call subtree.

**2. Node.js frame filtering:** V8 internals, Node.js core internals, and npm package code can be toggled on/off. In a raw flame graph, the majority of frames may be V8 compilation stubs and internal Node.js code. `clinic flame` lets you filter to "application code only" to see your own functions.

**3. Merged vs. unmerged views:** `clinic flame` offers both the standard icicle chart (callers at bottom, callees above) and a merged view that combines identical call paths, reducing visual noise from repeated code.

**4. Source mapping:** if your application uses TypeScript compiled to JavaScript, `clinic flame` can apply source maps to show the original TypeScript line numbers rather than compiled JavaScript locations. Configure this via `--source-map`:
```bash
clinic flame --source-map -- node dist/main.js
```

**5. The "Bubbles" integration:** `clinic flame` can overlay event loop delay information on the flame graph — frames that were executing during high event-loop-delay periods are highlighted. This makes it possible to see which specific function caused the event loop spike.

**Reading a clinic flame graph — practical rules:**
- Look for the **widest rectangle near the top** of the flame — this is the function doing the most self-work.
- Look for **tall, narrow spikes** — deep call stacks that appear frequently indicate recursive or deeply nested call paths.
- Look for your **own module names** — frames from `node_modules` that are wide are library overhead; frames from your `src/` are optimisation targets you control.
- Hover over a frame — the tooltip shows the percentage of total time, file path, and line number.

**Q11. How do you use `clinic bubble` to diagnose I/O-bound problems?**
A: `clinic bubble` is the tool for when `clinic doctor` reports low CPU but high latency — the application is spending most of its time waiting rather than computing. It visualises **asynchronous activity** rather than CPU execution.

```bash
clinic bubble -- node dist/main.js

autocannon -c 50 -d 30 http://localhost:3000/api/loans

# Ctrl+C — bubble chart generated
```

**What the bubble chart shows:**

Each bubble represents an async operation — a database query, an HTTP request to a downstream service, a file read, a DNS lookup. The size of the bubble represents the duration of the async operation. Bubbles cluster by type (database, HTTP, etc.) and by time.

**Reading the bubble chart:**

- **Large bubbles clustered in the DB section**: database queries are the bottleneck. Investigate query plans, add indexes, reduce query complexity.
- **Large bubbles in the HTTP section**: upstream API calls are slow. Add timeouts, caching, or fallbacks.
- **Many small bubbles in rapid succession**: an N+1 query pattern — the application is making many small DB calls rather than one batched call. Combine with a dataloader or a single batch query.
- **Bubbles that overlap**: concurrent async operations — healthy for high throughput. Non-overlapping bubbles (serial async calls) are a parallelism opportunity: `Promise.all()` can convert serial calls to concurrent.

**Concrete N+1 detection with clinic bubble:**
```typescript
// ANTI-PATTERN — N+1 query pattern
// clinic bubble shows: many small identical DB bubbles in rapid succession
async getLoansWithOfficerNames(tenantId: string): Promise<LoanWithOfficer[]> {
  const loans = await this.loanRepo.find({ where: { tenantId } });  // 1 query
  return Promise.all(loans.map(async (loan) => ({
    ...loan,
    officerName: (await this.userRepo.findOne({ where: { id: loan.assignedTo } })).fullName
    // N queries — one per loan
  })));
}

// CORRECT — batch the lookup
async getLoansWithOfficerNames(tenantId: string): Promise<LoanWithOfficer[]> {
  const loans = await this.loanRepo.find({ where: { tenantId } });
  const officerIds = [...new Set(loans.map(l => l.assignedTo))];
  const officers = await this.userRepo.findByIds(officerIds);     // 1 query for all officers
  const officerMap = new Map(officers.map(o => [o.id, o.fullName]));
  return loans.map(loan => ({ ...loan, officerName: officerMap.get(loan.assignedTo) }));
}
```
`clinic bubble` makes the N+1 pattern visually obvious — dozens of identical small bubbles in sequence are unmistakeable.

## Section 4: Memory Profiling

**Q12. How do you detect and diagnose a memory leak in a Node.js application?**
A: Memory leaks in Node.js occur when objects are unintentionally kept alive — something in the root graph of reachable objects holds a reference, preventing the garbage collector from reclaiming the memory. Common causes:

- Event listeners added but never removed.
- Closures that capture large objects, stored in a long-lived data structure.
- A cache or map that grows without bounds.
- Timers (`setInterval`) that are never cleared and capture objects in their callbacks.
- Circular references (less common since modern GCs handle these).

**Step 1 — Confirm the leak with `clinic doctor`:**
```bash
clinic doctor -- node dist/main.js
autocannon -c 50 -d 120 http://localhost:3000/api/loans  # longer test to show growth
```
If the memory panel shows a steady upward trend without plateau, a leak is confirmed.

**Step 2 — Take heap snapshots to find the source:**
```typescript
// In the application — expose a diagnostic endpoint (protect with auth!)
import v8 from 'node:v8';
import fs from 'node:fs';

// GET /debug/heap-snapshot (admin-only endpoint)
app.get('/debug/heap-snapshot', adminGuard, (req, res) => {
  const snapshotPath = `/tmp/heap-${Date.now()}.heapsnapshot`;
  v8.writeHeapSnapshot(snapshotPath);
  res.json({ path: snapshotPath });
});
```

Or using `clinic heapprofiler`:
```bash
clinic heapprofiler -- node dist/main.js
autocannon -c 50 -d 60 http://localhost:3000/api/loans
# Ctrl+C — generates allocation profile
```

**Step 3 — Compare snapshots in Chrome DevTools:**
1. Open Chrome DevTools → Memory tab.
2. Load baseline snapshot (before load test).
3. Load post-load-test snapshot.
4. In the second snapshot, use "Comparison" view — shows objects that exist in the second snapshot but not the first (net new allocations).
5. Sort by `# Delta` (count difference) or `Size Delta` to find the largest leaked object types.

**Common leak signatures in the comparison view:**

```
Constructor               #New  #Deleted  #Delta   Alloc Size  Size Delta
EventEmitter listeners     0    0         +8420    3.2MB       +3.2MB
Array                      0    0         +15000   1.8MB       +1.8MB
Closure                    0    0         +4200    890KB       +890KB
```

8,420 new `EventEmitter` listener entries that weren't cleaned up — a classic leak from `emitter.on()` without a corresponding `emitter.off()` (or `{ once: true }`).

**Step 4 — Find retainer chains:**
Click on a leaked object class in DevTools → expand the "Retainers" section. The retainer chain shows exactly what is keeping the object alive:

```
loan_callback (Closure) ← listeners array ← EventEmitter ← LoanService ← NestJS DI container (root)
```

This trace reveals that the `loan_callback` closure is captured in an EventEmitter's listener array, held by `LoanService`, which is a singleton — so it accumulates listeners forever.

**Fix:**
```typescript
// ANTI-PATTERN — listener added but never removed
class LoanService {
  constructor(private eventEmitter: EventEmitter2) {
    this.eventEmitter.on('payment.received', this.handlePayment.bind(this));
    // 'this.handlePayment.bind(this)' creates a new function object each time
    // — impossible to remove with removeListener
  }
}

// CORRECT — store the bound listener reference; remove on destroy
class LoanService implements OnModuleDestroy {
  private readonly paymentHandler: (data: PaymentEvent) => void;

  constructor(private eventEmitter: EventEmitter2) {
    this.paymentHandler = this.handlePayment.bind(this);
    this.eventEmitter.on('payment.received', this.paymentHandler);
  }

  onModuleDestroy(): void {
    this.eventEmitter.off('payment.received', this.paymentHandler);
  }
}
```

**Q13. What is `--inspect` and the V8 inspector protocol, and how do you use it for live profiling of a running production process?**
A: `--inspect` opens a WebSocket-based debugging and profiling interface on the process, compatible with Chrome DevTools and VS Code. It allows attaching to a running process for CPU profiling, heap inspection, and step-through debugging without restarting.

```bash
# Start with inspector (binds to 127.0.0.1:9229 by default — never 0.0.0.0 in prod)
node --inspect dist/main.js

# Or attach to a running process by sending SIGUSR1 (Linux/macOS)
kill -USR1 <PID>
# This opens the inspector on the running process without restarting

# Check if the inspector is listening
curl http://localhost:9229/json
```

**Connecting from Chrome DevTools:**
1. Open Chrome → `chrome://inspect`.
2. Click "Configure" → add `localhost:9229`.
3. The process appears under "Remote Target" — click "Inspect".
4. Memory tab: take heap snapshots. Profiler tab: start/stop CPU profiling.

**For production processes:** expose the inspector only over a tunnel or SSH port-forward — never expose port 9229 directly:
```bash
# SSH tunnel from local machine to prod server
ssh -L 9229:localhost:9229 prod-server

# Then connect Chrome DevTools to localhost:9229
```

            session.disconnect();

            resolve(Buffer.from(JSON.stringify(profile)));
          });
        }, durationMs);
      });
    });
  });
}

// Admin endpoint to capture a 30-second CPU profile
app.get('/debug/cpu-profile', adminGuard, async (req, res) => {
  const profileBuffer = await captureProfile(30_000);
  res.setHeader('Content-Type', 'application/json');
  res.setHeader('Content-Disposition', 'attachment; filename=profile.cpuprofile');
  res.send(profileBuffer);
  // Download the .cpuprofile file, open in Chrome DevTools Profiler tab

## Section 5: Production Profiling Strategy

**Q14. How do you profile a production Node.js service safely without impacting users?**
A: Profiling in production requires care — `--prof` has overhead, `--inspect` exposes a security surface, and taking heap snapshots pauses the GC temporarily. The correct approach uses a combination of:

**Strategy 1 — Always-on lightweight metrics (zero overhead):**
```typescript
// perf_hooks event loop delay monitoring — minimal overhead, always on
import { monitorEventLoopDelay } from 'node:perf_hooks';

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

// Expose as a metric every 10 seconds
setInterval(() => {
  metrics.gauge('node.event_loop.delay.p50',  histogram.percentile(50));
  metrics.gauge('node.event_loop.delay.p99',  histogram.percentile(99));
  metrics.gauge('node.event_loop.delay.max',  histogram.max);
  histogram.reset();
}, 10_000);

// Memory metrics
setInterval(() => {
  const mem = process.memoryUsage();
  metrics.gauge('node.heap.used',      mem.heapUsed);
  metrics.gauge('node.heap.total',     mem.heapTotal);
  metrics.gauge('node.rss',            mem.rss);
  metrics.gauge('node.external',       mem.external);
}, 10_000);
```

Ship these to Datadog, CloudWatch, or Prometheus. They alert you when a problem develops; you investigate with heavier tools after the alert.

**Strategy 2 — Route profiling traffic to a single instance:**
In a horizontally-scaled deployment (ECS, Kubernetes), remove one instance from the load balancer, enable profiling on it, send representative traffic to it directly, collect the profile, then return it to the pool.

```bash
# Kubernetes: remove one pod from service endpoints
kubectl label pod loans-api-pod-xyz profile=true --overwrite
kubectl patch service loans-api -p '{"spec":{"selector":{"app":"loans-api","profile":"false"}}}'

# SSH into the profiling pod
kubectl exec -it loans-api-pod-xyz -- bash

# Send SIGUSR1 to enable inspector
kill -USR1 1  # PID 1 in a container is typically the Node process

# Tunnel inspector to local machine
kubectl port-forward pod/loans-api-pod-xyz 9229:9229

# Profile via Chrome DevTools on localhost:9229
# When done, restore the pod to service
kubectl patch service loans-api -p '{"spec":{"selector":{"app":"loans-api"}}}'
```

**Strategy 3 — Clinic.js in a staging environment under production-like load:**
```bash
# Replay production traffic against staging using a traffic capture tool
# (goreplay, tcpreplay) while running clinic doctor
clinic doctor -- node dist/main.js

# Or use a load test configured to match production p95 request rate
autocannon -c $(production_concurrency) -d 300 https://staging.example.com/api/loans
```

**Strategy 4 — `--prof` on the production binary with minimal overhead window:**
```bash
# Run with --prof for 60 seconds then SIGUSR1 to stop gracefully
node --prof dist/main.js &
PID=$!

sleep 60

# Process the profile while the server continues running (isolate log is written)
node --prof-process isolate-$PID*.log > /tmp/profile-$(date +%s).txt

# Download and analyse
```

`--prof`'s overhead is approximately 1–3% CPU — acceptable for a short profiling window.

## Section 6: Real-World Scenarios

**Q16. Scenario: "Your NestJS loan disbursement endpoint is at 800ms p99 latency in production. Walk through your complete diagnostic process."**
A: A systematic profiling-driven investigation:

**Step 1 — Characterise the problem with metrics:**
Check the always-on metrics first (Q14):
- Event loop delay: is it high (> 50ms p99)? → blocking synchronous code.
- Heap usage: growing? → memory pressure causing GC pauses.
- RSS: larger than expected? → potential memory issue.
- CPU: consistently high (> 80%)? → CPU-bound.
- CPU: consistently low (< 20%) with high latency? → I/O-bound.

For an 800ms disbursement endpoint: CPU is likely 15%, event loop delay is 2ms → **I/O-bound diagnosis**. The bottleneck is in the waiting, not the computing.

**Step 2 — Trace the I/O with `clinic bubble`:**
```bash
clinic bubble -- node dist/main.js
# Generate representative disbursement requests
autocannon -c 10 -d 30 --method POST \
  -H 'Authorization: Bearer test-token' \
  -H 'Content-Type: application/json' \
  -b '{"loanId":"loan-123","amount":50000}' \
  http://localhost:3000/api/disbursements
```

Bubble chart reveals: the disbursement endpoint makes 4 sequential database queries, each taking 80–120ms, adding up to 400ms of serial DB wait. Plus a synchronous call to a KYC verification service taking 350ms.

**Step 3 — Identify parallelism opportunities:**
```typescript
// CURRENT — serial async calls (visible as sequential bubbles in clinic bubble)
async createDisbursement(dto: CreateDisbursementDto): Promise<Disbursement> {
  const loan    = await this.loanRepo.findOne(dto.loanId);        // 100ms
  const user    = await this.userRepo.findOne(loan.userId);        // 90ms
  const kycStatus = await this.kycService.verify(loan.userId);    // 350ms
  const mandate  = await this.nachRepo.findActive(loan.userId);   // 80ms
  // Total: ~620ms sequential I/O
  return this.disburse(loan, user, kycStatus, mandate);
}

// OPTIMISED — parallel where possible
async createDisbursement(dto: CreateDisbursementDto): Promise<Disbursement> {
  const loan = await this.loanRepo.findOne(dto.loanId);            // 100ms (must be first)

  // These three are independent of each other — run in parallel
  const [user, kycStatus, mandate] = await Promise.all([
    this.userRepo.findOne(loan.userId),                            // ↓
    this.kycService.verify(loan.userId),                           // → 350ms (longest)
    this.nachRepo.findActive(loan.userId),                         // ↓
  ]);
  // Total: 100ms + 350ms = 450ms (vs 620ms sequential)
  return this.disburse(loan, user, kycStatus, mandate);
}
```

**Step 4 — Address the KYC service call:**
350ms is a downstream API call — cannot be made faster by parallelism alone. Options:
- Cache the KYC status with a 5-minute TTL (KYC status changes rarely mid-disbursement).
- Move KYC verification to an earlier step in the disbursement saga (pre-verify before the final disbursement call — by the time disbursement is triggered, KYC is already verified and cached).

**Step 5 — Address the database queries:**
4 separate queries for related data — optimise with a JOIN or covering index:
```sql
-- Instead of 4 separate queries, one query with joins
SELECT la.*, u.full_name, u.email, nm.mandate_id, nm.bank_account_hash
FROM loan_applications la
JOIN users u ON u.id = la.user_id
LEFT JOIN nach_mandates nm ON nm.user_id = la.user_id AND nm.status = 'active'
WHERE la.id = $1;
-- Add appropriate indexes (covered in the index design guide)
```

**Step 6 — Re-profile to validate:**
```bash
clinic doctor -- node dist/main.js
# Expected: p99 drops from 800ms to 120ms (KYC cached) or 450ms (KYC uncached)
```

**Q17. Scenario: "Memory usage on your NestJS service grows by 50MB every hour and never drops. How do you find the leak?"**

# Memory panel shows a steadily rising line — confirmed leak

**Step 2 — Take two heap snapshots with Chrome DevTools:**

// Admin endpoint to trigger a snapshot (Q13)
// Take snapshot 1 at T+0 (baseline, after warm-up)
// Apply load for 30 minutes
// Take snapshot 2 at T+30

**Step 3 — Comparison view in DevTools — find the leak:**
Suppose the comparison shows:

12,000 new `Map` instances. Click `Map` → expand `Retainers`. Trace leads to:

```typescript
// THE LEAK: unbounded in-memory cache
@Injectable()
export class LoanCacheService {
  private readonly cache = new Map<string, LoanDto>();  // grows forever

  async getLoan(id: string): Promise<LoanDto> {
    if (this.cache.has(id)) return this.cache.get(id)!;
    const loan = await this.loanRepo.findOne(id);
    this.cache.set(id, loan);   // added to cache
    // Never evicted!
    return loan;
  }
}
```

**Step 5 — Fix with bounded cache (TTL eviction or LRU):**
```typescript
import { LRUCache } from 'lru-cache';  // npm install lru-cache

@Injectable()
export class LoanCacheService {
  private readonly cache = new LRUCache<string, LoanDto>({
    max:           1000,         // maximum 1,000 entries
    ttl:           5 * 60_000,   // 5-minute TTL per entry
    allowStale:    false,
  });

  async getLoan(id: string): Promise<LoanDto | null> {
    const cached = this.cache.get(id);
    if (cached) return cached;

    const loan = await this.loanRepo.findOne({ where: { id } });
    if (loan) this.cache.set(id, loan);
    return loan;
  }
}
```

**Q18. Scenario: "Your NestJS service's p99 latency spikes to 2 seconds every ~10 minutes but returns to normal immediately. What is the likely cause, and how do you confirm it?"**
A: Periodic latency spikes that self-resolve are a classic symptom of **garbage collection pauses** or **periodic synchronous work** (a scheduled job, a timer-based cleanup task). The 10-minute interval is suspicious — it suggests a scheduled task rather than random GC.

**Step 1 — Check for scheduled jobs:**
```typescript
// Search codebase for: @Cron, setInterval, setTimeout, schedule.scheduleJob
// If any are set to run every 10 minutes (*/10 * * * *), they're suspects
@Cron('*/10 * * * *')  // every 10 minutes
async reconcileLoanCounts(): Promise<void> {
  // This runs a heavy computation — if it blocks the event loop, p99 spikes
  await this.db.query(`
    UPDATE users SET active_loan_count = (
      SELECT COUNT(*) FROM loan_applications WHERE user_id = users.id AND status = 'active'
    )
  `);  // this could take 30-60 seconds on a large table, blocking nothing (it's async)
  // BUT: if there's any CPU-heavy post-processing...
}
```

An async DB query itself doesn't block the event loop (it's non-blocking I/O). The spike is more likely caused by:

```typescript
@Cron('*/10 * * * *')
async expireOldSessions(): Promise<void> {
  // Loading 10,000 session objects into memory and processing them synchronously
  const sessions = await this.sessionRepo.find();       // fetches 10,000 rows into memory
  const now = Date.now();
  const toExpire = sessions.filter(s => s.expiresAt < now);  // synchronous filter in memory
  // JSON.stringify-ing 10,000 objects for logging is synchronous
  this.logger.debug('Expiring sessions', JSON.stringify(toExpire));  // BLOCKS event loop
  await Promise.all(toExpire.map(s => this.sessionRepo.delete(s.id)));
}
```

**Step 2 — Confirm with event loop delay monitoring and timestamp correlation:**
```typescript
// Add timestamp logging around the cron job
@Cron('*/10 * * * *')
async expireOldSessions(): Promise<void> {
  const start = performance.now();
  this.logger.debug('Starting session expiry');
  // ... work ...
  this.logger.debug(`Session expiry completed in ${performance.now() - start}ms`);
}
```

Correlate the log timestamps with the p99 spike times from your APM tool. If they align — confirmed.

**Step 3 — Fix by moving CPU-heavy synchronous work off the event loop:**

For large data processing in a cron job:
```typescript
// CORRECT: process in batches to yield the event loop between batches
@Cron('*/10 * * * *')
async expireOldSessions(): Promise<void> {
  const BATCH_SIZE = 100;
  let offset = 0;

  while (true) {
    // Fetch a small batch
    const sessions = await this.sessionRepo.find({
      where:  { expiresAt: LessThan(new Date()) },
      take:   BATCH_SIZE,
      skip:   offset,
    });

    if (sessions.length === 0) break;

    // Delete the batch
    await this.sessionRepo.delete(sessions.map(s => s.id));
    offset += sessions.length;

    // Yield the event loop between batches — other requests can be served
    await new Promise(resolve => setImmediate(resolve));
  }
}
```

`setImmediate()` yields control back to the event loop at the end of each batch iteration, allowing pending I/O callbacks and timers to fire before the next batch starts. The cron job takes longer in wall-clock time but doesn't block the event loop.

**Q19. What is the `--max-old-space-size` flag, and when should you adjust it?**
A: `--max-old-space-size=N` (where N is megabytes) sets the maximum size of V8's old generation heap — the long-lived object space where objects that survive multiple GC cycles are promoted. The default varies by system RAM: on a 2GB container, the default is approximately 1.5GB; on a 512MB container, approximately 384MB.

**When the default is appropriate:** most NestJS services with reasonable caching and no memory leaks will never approach the default limit. The default is a safety ceiling, not a target.

**When to increase it:**
- The service is doing legitimate in-memory data processing with large datasets (processing a full month of loan repayments in-memory for a report).
- The service caches large amounts of data intentionally and the cache is within `--max-old-space-size`.
- The GC logs show frequent major GC cycles — indicating the heap is too small for the working set.

```bash
# Start with more heap
node --max-old-space-size=4096 dist/main.js   # 4GB max heap
```

**When NOT to increase it:**
- As a first response to a memory leak — increasing the limit just delays the OOM crash while the leak continues growing.
- On containers with limited RAM — if the container has 1GB and you set `--max-old-space-size=2048`, Node may request memory the container doesn't have, causing the container to be OOM-killed by the kernel.
- As a substitute for profiling — `--max-old-space-size` should be set after understanding the legitimate memory needs of the service, not as a workaround.

**Safe configuration for a NestJS fintech service:**
```bash
# Container has 2GB RAM; reserve ~500MB for OS, Node overhead, and buffers
node --max-old-space-size=1536 dist/main.js
```

Also useful: `--max-semi-space-size` (controls the young generation size — increase if you have very high allocation rates of short-lived objects, reducing minor GC frequency) and `--expose-gc` (exposes `global.gc()` for programmatic GC triggering in tests).

**Q20. How do you use `perf_hooks` `PerformanceObserver` to instrument your NestJS application for continuous profiling without external tools?**
A: `perf_hooks` provides built-in performance instrumentation that you can embed permanently in your application, shipping metrics to your observability stack continuously rather than only during a profiling session.

```typescript
// performance.service.ts — permanent instrumentation
import { Injectable, OnModuleInit } from '@nestjs/common';
import { PerformanceObserver, performance, monitorEventLoopDelay } from 'node:perf_hooks';
import { MetricsService } from './metrics.service';

@Injectable()
export class PerformanceService implements OnModuleInit {
  private readonly loopMonitor = monitorEventLoopDelay({ resolution: 20 });

  constructor(private readonly metrics: MetricsService) {}

  onModuleInit(): void {
    this.loopMonitor.enable();
    this.startLoopMetrics();
    this.observeGcMetrics();
    this.observeHttpMetrics();
  }

  private startLoopMetrics(): void {
    setInterval(() => {
      this.metrics.histogram('node.event_loop.delay', {
        p50: this.loopMonitor.percentile(50),
        p99: this.loopMonitor.percentile(99),
        max: this.loopMonitor.max,
      });
      this.loopMonitor.reset();

      const mem = process.memoryUsage();
      this.metrics.gauge('node.heap.used',   mem.heapUsed  / 1024 / 1024);  // MB
      this.metrics.gauge('node.heap.total',  mem.heapTotal / 1024 / 1024);
      this.metrics.gauge('node.rss',         mem.rss       / 1024 / 1024);
    }, 10_000);
  }

  private observeGcMetrics(): void {
    const gcObserver = new PerformanceObserver((list) => {
      for (const entry of list.getEntries()) {
        // entry.name: 'minor' (scavenge), 'major' (mark-sweep), 'incremental', 'weakcb'
        this.metrics.histogram('node.gc.duration', entry.duration, {
          type: entry.name,
        });
        // Alert if a single GC pause exceeds 100ms (impacts p99 latency)
        if (entry.duration > 100) {
          this.metrics.increment('node.gc.long_pause', { type: entry.name });
        }
      }
    });
    gcObserver.observe({ entryTypes: ['gc'] });
  }

  private observeHttpMetrics(): void {
    // Mark-and-measure pattern for custom timing
    // Use in middleware to measure route handler duration
  }

  // Call this in middleware to time individual requests
  measureRequest(routeName: string, durationMs: number): void {
    performance.measure(`http.${routeName}`, { duration: durationMs });
    this.metrics.histogram('http.route.duration', durationMs, { route: routeName });
  }
}
```

**NestJS interceptor for request timing:**
```typescript
// timing.interceptor.ts — measures every request and emits to metrics
@Injectable()
export class TimingInterceptor implements NestInterceptor {
  constructor(private readonly perf: PerformanceService) {}

  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const start = performance.now();
    const route = context.getHandler().name;

    return next.handle().pipe(
      tap(() => this.perf.measureRequest(route, performance.now() - start)),
      catchError((err) => {
        this.perf.measureRequest(`${route}.error`, performance.now() - start);
        throw err;
      }),
    );
  }
}
```

This permanent instrumentation means you have continuous visibility into:
- Event loop delay (ship as a Datadog/CloudWatch metric → alert when p99 > 50ms).
- GC pause frequency and duration (alert on long GC pauses → indicates heap pressure).
- Per-route latency (identify which specific routes are slow, not just aggregate p99).
- Heap usage trend (alert when heap growth rate indicates a leak before OOM).

The pattern complements profiling tools: the metrics tell you *when* a problem exists and *what category* it is; the profiling tools tell you *exactly where* in the code.

**Tip for the interview:** At 5 YOE, profiling questions are almost always scenario-based: "p99 is 800ms, what do you do?" Know the triage order — metrics first (event loop delay, CPU, memory) to identify the category, then the specific tool for that category. The most important conceptual point to convey is the difference between CPU-bound and I/O-bound diagnosis: a high `unaccounted` percentage in `--prof-process` (or low CPU + high latency in `clinic doctor`) means the bottleneck is I/O — optimising JavaScript will accomplish nothing.
