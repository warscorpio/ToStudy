## Section 1: The Event Loop Mental Model

**Q1. What is the event loop, and what does "blocking" it actually mean at the runtime level?**
A: The event loop is the scheduling core of every async runtime — Node.js, Python asyncio, Tokio (Rust), Go's goroutine scheduler. It is a single OS thread running a loop that alternates between two activities: executing application callbacks/coroutines, and waiting for I/O events. The critical constraint: **only one thing executes at a time on the event loop thread**. While your code is running, nothing else can run — not other requests, not timer callbacks, not I/O completions.

```
The event loop — simplified execution model:

  while True:
      # Phase 1: run all callbacks/coroutines that are ready to execute
      for callback in ready_queue:
          callback()          ← YOUR CODE RUNS HERE
                              ← If this takes 500ms, NOTHING ELSE runs for 500ms

      # Phase 2: poll I/O — ask the OS "which file descriptors are ready?"
      events = epoll_wait(timeout=next_timer_deadline)
                              ← Kernel blocks here waiting for I/O
                              ← This is "idle time" — no requests are in-flight

      # Phase 3: queue callbacks for ready events
      for event in events:
          ready_queue.append(event.callback)

Node.js event loop phases (libuv):
  ┌──────────────────────────────────┐
  │           timers                 │  ← setTimeout, setInterval callbacks
  │      pending callbacks           │  ← I/O callbacks deferred to next iteration
  │           idle, prepare          │  ← internal use
  │           poll                   │  ← retrieve new I/O events (blocks here if idle)
  │           check                  │  ← setImmediate callbacks
  │      close callbacks             │  ← socket.on('close', ...) etc.
  └──────────────────────────────────┘
  Each phase runs all its callbacks before moving to the next.

Python asyncio event loop:
  Conceptually identical — a single thread running coroutines cooperatively.
  "await" is the yield point: it pauses the current coroutine and lets others run.
  Code between two "await" statements runs uninterrupted — it is a "tick."
```

"Blocking the event loop" means occupying the event loop thread with synchronous CPU work or a blocking system call for long enough that other work is visibly delayed:

```
What "blocking" looks like to other requests:

  Time 0ms:   Request A arrives. Event loop picks it up.
  Time 0ms:   Request A handler starts executing.
  Time 0ms:   Handler calls JSON.parse(5MB_string) — synchronous, CPU-bound.
  Time 0ms:   CPU begins parsing. Event loop is occupied.

  Time 0ms:   Request B arrives. Sits in the kernel's accept queue.
  Time 50ms:  Request C arrives. Also waiting.
  Time 80ms:  Scheduled timer fires — should have triggered 80ms ago. Queued.

  Time 200ms: JSON.parse() finishes. Request A handler resumes.
  Time 200ms: Event loop is now free. Processes Request B (200ms late).
  Time 200ms: Processes Request C (200ms late).
  Time 200ms: Runs the timer callback (120ms late).

  User-visible: Request B's latency includes 200ms of "queue time" with no apparent
  I/O — the server wasn't "busy," it was stuck. No error is raised. It just waits.
  In latency percentiles: p50 looks fine; p99 spikes to 200ms+ from this single block.
```

The rule: **no single tick of the event loop should take more than 1–10ms**. Anything longer is a blocking operation that must be moved off the event loop thread.

**Q2. How do you measure event loop lag — detecting blocks before they become user-visible?**
A: Event loop lag (also called "event loop delay") is the difference between when a timer was scheduled to fire and when it actually fired. A healthy event loop has near-zero lag; a blocked event loop has lag equal to the duration of the blocking operation.

```javascript
// Node.js — measuring event loop lag

// Method 1: perf_hooks (built-in, low overhead)
const { monitorEventLoopDelay } = require("perf_hooks");

const histogram = monitorEventLoopDelay({ resolution: 10 }); // sample every 10ms
histogram.enable();

setInterval(() => {
    const lagMs = histogram.mean / 1e6;   // nanoseconds → milliseconds
    const p99Ms = histogram.percentile(99) / 1e6;
    console.log(`Event loop lag: mean=${lagMs.toFixed(2)}ms p99=${p99Ms.toFixed(2)}ms`);

    // Alert thresholds:
    if (p99Ms > 100) console.error("CRITICAL: event loop blocked > 100ms");
    else if (p99Ms > 20) console.warn("WARNING: event loop lag > 20ms");

    histogram.reset();
}, 5000);

// Method 2: timer drift (portable — works in any async runtime)
function measureEventLoopLag(intervalMs = 100): void {
    let lastTick = Date.now();
    setInterval(() => {
        const now      = Date.now();
        const expected = lastTick + intervalMs;
        const lag      = now - expected;   // ms later than expected
        lastTick       = now;

        metrics.histogram("event_loop_lag_ms", lag);

        if (lag > 50) {
            logger.warn("Event loop lag spike: %dms", lag);
        }
    }, intervalMs).unref();   // .unref() prevents this timer from keeping the process alive
}

// Method 3: --inspect + Node.js profiler (for root-cause analysis)
// node --inspect app.js
// Open chrome://inspect → CPU profiler → record 30s → look for long synchronous stacks
```

```python
# Python asyncio — measuring event loop lag

import asyncio, time

async def monitor_event_loop_lag(
    interval_sec:  float = 0.1,
    warn_threshold: float = 0.050,   # 50ms
) -> None:
    """
    Runs as a background coroutine. Measures the gap between scheduled
    and actual wake-up time — the event loop lag.
    """
    while True:
        before  = time.monotonic()
        await asyncio.sleep(interval_sec)
        after   = time.monotonic()
        lag_sec = (after - before) - interval_sec
        lag_ms  = lag_sec * 1000

        metrics.histogram("asyncio.event_loop_lag_ms", lag_ms)

        if lag_ms > warn_threshold * 1000:
            logger.warning("Event loop lag: %.1fms", lag_ms)

# Start at application boot:
asyncio.ensure_future(monitor_event_loop_lag())

# Python: asyncio.get_event_loop().slow_callback_duration
# Sets the threshold above which asyncio logs a warning automatically:
import logging
logging.getLogger("asyncio").setLevel(logging.WARNING)
loop = asyncio.get_event_loop()
loop.slow_callback_duration = 0.050   # warn on any coroutine tick > 50ms
# Output: "Executing <Task ...> took 0.123 seconds" — built-in, zero overhead
```

## Section 2: CPU-Bound Operations

**Q3. What makes an operation "CPU-bound," and why does `await` not help for CPU-bound work?**
A: An operation is CPU-bound when the bottleneck is computation — the CPU is actively executing instructions and cannot yield until the computation finishes. `await` is a cooperative yield point: it only suspends a coroutine when the underlying operation voluntarily gives up the CPU (by calling into the I/O polling machinery). CPU-bound code never calls into the I/O poller — it just runs.

```python
# The fundamental misconception — await does NOT make CPU work async

import asyncio, json, hashlib

async def bad_json_handler(request):
    body = await request.body()          # ← genuine I/O: suspends until data arrives ✓

    # This looks async because it's in an async function.
    # It is NOT. json.loads() runs synchronously on the event loop thread.
    data = json.loads(body)              # ← BLOCKS event loop for duration of parse ✗

    # Same problem with CPU-intensive transformations:
    result = expensive_computation(data) # ← BLOCKS event loop ✗

    return JSONResponse(result)


# Why await doesn't fix it — the coroutine model:

async def demonstrates_blocking():
    print("Before")
    result = json.loads("..." * 1_000_000)   # 100ms of CPU work
    print("After")
    # Between "Before" and "After": event loop is stuck for 100ms.
    # No other coroutine can run. No timer can fire. No I/O can complete.
    # Adding "await" in front of json.loads() would be a SyntaxError —
    # json.loads() is not a coroutine and cannot be awaited.

# Contrast: genuine async I/O
async def demonstrates_async():
    print("Before")
    data = await asyncio.sleep(0.1)   # suspends THIS coroutine for 100ms
    print("After")
    # Between "Before" and "After": event loop runs OTHER coroutines.
    # 1000 other requests can be processed while this one sleeps.
    # The difference: sleep() calls into libuv/epoll; json.loads() does not.


# What actually counts as CPU-bound (blocks the event loop):

CPU_BOUND_OPERATIONS = [
    "json.loads() / JSON.parse()  — proportional to payload size",
    "json.dumps() / JSON.stringify() — serialization",
    "hashlib.sha256() on large data — cryptographic hashing",
    "re.compile() / complex regex execution on large strings",
    "PIL/Pillow image processing — resize, convert, compress",
    "pandas DataFrame operations — groupby, merge, apply",
    "numpy matrix operations (depending on BLAS threading)",
    "gzip.compress() / zlib.decompress() on large data",
    "csv.reader() / csv.writer() on large files",
    "XML/HTML parsing — lxml, BeautifulSoup on large documents",
    "Encryption: AES on large payloads",
    "Base64 encoding/decoding of large blobs",
    "Template rendering with complex logic (Jinja2, Handlebars)",
    "ORM query result mapping (iterating thousands of rows in Python)",
    "Protobuf serialization/deserialization of large messages",
    "Sorting / filtering large in-memory collections",
]
```

**Q4. How do you offload CPU-bound work from the event loop — thread pools, process pools, and worker threads?**
A: The solution to CPU-bound blocking is to run the blocking work on a separate OS thread or process, then await the result. The event loop thread is free to process other requests while the worker thread grinds through the CPU work.

```python
# Python asyncio — offloading to a thread pool

import asyncio, json, hashlib, gzip
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor
from functools import partial

# ── THREAD POOL: for I/O-bound blocking calls and GIL-releasing CPU work ──────
# Python's GIL means threads cannot run Python bytecode in parallel.
# BUT: threads CAN run in parallel when they call C extensions that release the GIL.
# json.loads() (implemented in C) releases the GIL → runs truly in parallel in threads.
# hashlib, gzip, numpy — all release the GIL.

_thread_pool = ThreadPoolExecutor(
    max_workers=4,                       # match to CPU cores for CPU work
    thread_name_prefix="cpu-worker",
)

async def parse_json_async(raw: bytes) -> dict:
    """Parse JSON on a thread pool — event loop is free while parsing."""
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(
        _thread_pool,
        json.loads,          # the blocking function
        raw,                 # its argument
    )

async def compress_async(data: bytes, level: int = 6) -> bytes:
    """gzip compression on a thread — releases GIL, runs in parallel."""
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(
        _thread_pool,
        partial(gzip.compress, data, compresslevel=level),
    )

async def hash_file_async(filepath: str) -> str:
    """Hash a large file on a thread — both I/O and CPU offloaded."""
    loop = asyncio.get_event_loop()

    def _hash_file():
        h = hashlib.sha256()
        with open(filepath, "rb") as f:
            for chunk in iter(lambda: f.read(65536), b""):
                h.update(chunk)
        return h.hexdigest()

    return await loop.run_in_executor(_thread_pool, _hash_file)


# ── PROCESS POOL: for pure Python CPU work that holds the GIL ─────────────────
# pandas, scikit-learn, complex Python loops — these hold the GIL.
# Threads are useless here (only one runs at a time due to GIL).
# ProcessPoolExecutor: each worker is a separate OS process — true parallelism.

_process_pool = ProcessPoolExecutor(max_workers=4)

def _compute_loan_risk(loan_data: dict) -> dict:
    """Pure Python computation — must run in a separate process."""
    import pandas as pd
    # Simulate heavy pandas computation
    df = pd.DataFrame(loan_data["history"])
    score = df.groupby("category")["amount"].agg(["mean", "std", "count"])
    return {"risk_score": float(score["mean"].mean()), "details": score.to_dict()}

async def compute_loan_risk_async(loan_data: dict) -> dict:
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(_process_pool, _compute_loan_risk, loan_data)

# ProcessPoolExecutor caveats:
# - Process startup cost: ~50–200ms per new worker (mitigated by the pool — workers
#   are reused across calls; startup is one-time).
# - IPC serialization: arguments and return values are pickled.
#   Large data structures serialized over a pipe → can be slower than expected.
#   For large DataFrames: pass a file path or shared memory reference, not the data.
# - Memory: each worker process has its own memory space — no shared heap.
#   A pool of 4 workers × 200MB each = 800MB baseline.


# ── THREAD POOL SIZING ────────────────────────────────────────────────────────

# For I/O-bound blocking (legacy blocking DB drivers, blocking HTTP clients):
_io_blocking_pool = ThreadPoolExecutor(
    max_workers=32,   # high: threads spend most time waiting, not using CPU
)

# For CPU-bound work (JSON parsing, compression, hashing):
_cpu_bound_pool = ThreadPoolExecutor(
    max_workers=4,    # match to core count: beyond this, threads fight for CPU
)

# Rule: thread pool workers for CPU work should equal CPU cores.
#       thread pool workers for I/O blocking can be much higher (they mostly wait).
```

```javascript
// Node.js — offloading CPU-bound work

// ── WORKER THREADS: the Node.js equivalent of Python's thread pool ────────────
const { Worker, isMainThread, parentPort, workerData } = require("worker_threads");
const { resolve } = require("path");

// worker.js — runs in a separate thread
if (!isMainThread) {
    const { task, payload } = workerData;

    if (task === "parse_json") {
        try {
            const result = JSON.parse(payload);   // runs in worker thread, not event loop
            parentPort.postMessage({ success: true, result });
        } catch (err) {
            parentPort.postMessage({ success: false, error: err.message });
        }
    }
}

// main.js — pool of worker threads
const os = require("os");

class WorkerPool {
    constructor(workerScript, numWorkers = os.cpus().length) {
        this.workers  = [];
        this.queue    = [];
        this.numWorkers = numWorkers;

        for (let i = 0; i < numWorkers; i++) {
            this._addWorker(workerScript);
        }
    }

    _addWorker(script) {
        const worker = new Worker(script);
        worker.on("message", (msg) => {
            const { resolve, reject } = worker._currentTask;
            worker._currentTask = null;
            worker._busy = false;
            if (msg.success) resolve(msg.result);
            else reject(new Error(msg.error));
            this._processQueue(worker);
        });
        worker.on("error", (err) => {
            const { reject } = worker._currentTask || {};
            if (reject) reject(err);
            worker._busy = false;
            this._processQueue(worker);
        });
        worker._busy = false;
        this.workers.push(worker);
    }

    run(task, payload) {
        return new Promise((resolve, reject) => {
            const job = { task, payload, resolve, reject };
            const idle = this.workers.find(w => !w._busy);
            if (idle) {
                this._runOnWorker(idle, job);
            } else {
                this.queue.push(job);
            }
        });
    }

    _runOnWorker(worker, job) {
        worker._busy        = true;
        worker._currentTask = job;
        worker.postMessage({ task: job.task, payload: job.payload });
    }

    _processQueue(worker) {
        if (this.queue.length > 0) {
            this._runOnWorker(worker, this.queue.shift());
        }
    }
}

const pool = new WorkerPool(resolve(__dirname, "worker.js"), os.cpus().length);

// Usage in an Express/Fastify handler:
app.post("/api/process", async (req, res) => {
    const rawBody = req.body.toString();   // already received — now parse off-thread

    const parsed = await pool.run("parse_json", rawBody);   // non-blocking

    res.json({ processed: true, count: Object.keys(parsed).length });
});
```

## Section 3: Large JSON Parsing

**Q5. At what payload size does JSON parsing become a problem, and how do you benchmark it on your runtime?**
A: There is no universal threshold — it depends on the JSON parser, the CPU speed, and your latency budget. The practical question is: does parsing this payload take more than 1–10ms? If yes, it needs to move off the event loop.

```python
# Benchmarking JSON parse time — find your threshold

import json, time, statistics

def benchmark_json_parse(payload_sizes_kb: list[int], iterations: int = 100):
    """
    Measure how long json.loads() takes at various payload sizes.
    Run this on your production hardware to find YOUR threshold.
    """
    results = {}
    for size_kb in payload_sizes_kb:
        # Generate a realistic nested JSON structure of the target size
        payload = _generate_json_payload(size_kb * 1024)
        raw     = json.dumps(payload).encode()

        times = []
        for _ in range(iterations):
            start = time.perf_counter()
            json.loads(raw)
            times.append((time.perf_counter() - start) * 1000)   # ms

        results[size_kb] = {
            "p50_ms": statistics.median(times),
            "p99_ms": statistics.quantiles(times, n=100)[98],
            "max_ms": max(times),
        }
        print(f"{size_kb:6d}KB: p50={results[size_kb]['p50_ms']:.2f}ms "
              f"p99={results[size_kb]['p99_ms']:.2f}ms "
              f"max={results[size_kb]['max_ms']:.2f}ms")

    return results

benchmark_json_parse([1, 10, 50, 100, 500, 1000, 5000])

# Typical results on a 2024 server (CPython 3.12, standard json module):
# Payload    p50      p99      max
#     1KB:  0.01ms   0.02ms   0.04ms  ← negligible; no action needed
#    10KB:  0.05ms   0.08ms   0.12ms  ← fine
#    50KB:  0.25ms   0.35ms   0.50ms  ← acceptable for low-traffic endpoints
#   100KB:  0.50ms   0.70ms   1.00ms  ← approaching threshold
#   500KB:  2.50ms   3.50ms   5.00ms  ← blocks event loop: move to thread
#  1000KB:  5.00ms   7.00ms  10.00ms  ← definitely blocking: thread or stream
#  5000KB: 25.00ms  35.00ms  50.00ms  ← severe: reject or stream parse
#
# Note: orjson (Rust-based JSON library) is 5-10x faster than stdlib json
# at all sizes. With orjson, the "move to thread" threshold shifts right
# (e.g., 500KB becomes acceptable). But the solution is still the same:
# measure, find your threshold, offload beyond it.
```

**Q6. What are the three strategies for handling large JSON payloads — offload, streaming parse, and schema enforcement — and when does each apply?**

```python
    loop = asyncio.get_event_loop()

    return parse

# When: payload is too large to hold in memory all at once (100MB+);

    Input: {"records": [ {...}, {...}, ... ]}  (potentially millions of records)

        body_chunks.append(chunk)

    for i in range(0, len(records), BATCH_SIZE):

        await asyncio.sleep(0)   # yield to event loop between batches (see Q7)
```

**Q7. How does `await asyncio.sleep(0)` ("yielding to the event loop") work, and when should you use it?**
A: `await asyncio.sleep(0)` is a zero-duration sleep that suspends the current coroutine for exactly one event loop iteration, then immediately resumes it. It inserts a voluntary yield point into otherwise long-running synchronous code.

```python
# asyncio.sleep(0) — controlled yielding

# The problem: a coroutine that does a lot of synchronous work in a loop
# holds the event loop for the duration of the loop, even with no I/O.

async def process_10k_records_bad(records: list) -> list:
    results = []
    for record in records:              # 10,000 iterations
        result = transform(record)      # 0.1ms of CPU per record
        results.append(result)
    return results
    # Total blocking time: 10,000 × 0.1ms = 1,000ms (1 second)
    # No other coroutine runs during this entire second.

async def process_10k_records_good(records: list, batch_size: int = 100) -> list:
    results = []
    for i, record in enumerate(records):
        result = transform(record)
        results.append(result)
        # Every `batch_size` iterations, yield to the event loop.
        # Other coroutines can run; then we resume.
        if i % batch_size == 0:
            await asyncio.sleep(0)
    return results
    # Total blocking time: 100 × 0.1ms = 10ms per batch (acceptable)
    # Other requests are processed between batches.
    # Total latency for THIS coroutine: slightly higher (event loop overhead per yield)
    # but other requests are not starved.

# How asyncio.sleep(0) works internally:
# 1. asyncio.sleep(0) schedules a callback for the NEXT event loop iteration.
# 2. The current coroutine is suspended (added to the "pending" queue, not "ready").
# 3. The event loop runs all OTHER ready callbacks (other requests, I/O completions).
# 4. On the next iteration, the current coroutine is moved back to "ready."
# 5. It resumes on the iteration after that.
# Net effect: a 2-iteration pause that allows other work to run.

# When to use sleep(0):
USE_SLEEP_0_WHEN = [
    "Processing a large in-memory collection in a loop (records, rows, items)",
    "Rendering a large template with complex logic",
    "Walking a large tree or graph structure",
    "Accumulating results across many in-memory operations",
    "Any pure-Python loop that takes > 10ms total",
]

# When NOT to use sleep(0):
DO_NOT_USE_SLEEP_0_WHEN = [
    # sleep(0) does not help with a SINGLE blocking call that takes 200ms.
    # You cannot insert sleep(0) inside json.loads() — it's a C function.
    # sleep(0) only helps with loops where YOU control the iterations.
    "Inside a single C-extension call (json.loads, gzip.compress, etc.)",
    "As a substitute for run_in_executor for truly CPU-intensive work",
    "At very high frequency (every iteration of a 1M-item loop) — overhead adds up",
]

# Node.js equivalent: setImmediate() or process.nextTick()
# setImmediate: schedule after the current poll phase (between event loop phases)
# process.nextTick: schedule before any I/O (runs at end of current phase — can starve I/O)

async function processLargeArray(items) {
    const results = [];
    const BATCH_SIZE = 100;

    for (let i = 0; i < items.length; i++) {
        results.push(transform(items[i]));
        if (i % BATCH_SIZE === 0) {
            // Yield to event loop — allow other callbacks to run
            await new Promise(resolve => setImmediate(resolve));
        }
    }
    return results;
}
```

**Q8. Which I/O operations are synchronous by default and will block the event loop — and what is the correct replacement for each?**
A: The most insidious blocking operations are the ones that look like they should be async but are actually synchronous: file system calls, DNS lookups, some database drivers, child processes.

**Q9. How do synchronous logging libraries block the event loop — and what is the correct async logging pattern?**
A: Logging is an invisible event loop blocker. Every `logger.info()` call that writes to a file or flushes to stdout is a synchronous disk write. Under high request volume, logging can contribute meaningfully to event loop lag.

```python
# The problem — stdlib logging is synchronous

import logging

# logging.FileHandler writes to disk on every log call.
# logging.StreamHandler writes to stdout — buffered, but flush() is synchronous.
# Under high load: each log.info() can take 0.1–2ms → cumulative blocking.

logger = logging.getLogger("app")
logger.info("Request processed: user=%s action=%s", user_id, action)
# If this runs 10,000 times per second: 10,000 × 1ms = 10 seconds of blocking per second.

# Solution 1 — QueueHandler (stdlib): non-blocking log dispatch

import logging.handlers
import queue

# Create a queue for log records
log_queue = queue.Queue(maxsize=10_000)

# QueueHandler: puts log records in the queue without blocking
queue_handler = logging.handlers.QueueHandler(log_queue)

# QueueListener: runs in a background thread, actually writes the log records
file_handler   = logging.FileHandler("/var/log/app.log")
stream_handler = logging.StreamHandler()
queue_listener = logging.handlers.QueueListener(
    log_queue,
    file_handler, stream_handler,
    respect_handler_level=True,
)
queue_listener.start()

# Configure root logger to use the queue handler (non-blocking)
logging.basicConfig(handlers=[queue_handler], level=logging.INFO)

# Now logger.info() puts the record in a queue (microseconds) — never blocks the event loop.
# The background thread dequeues and writes to disk at its own pace.


# Solution 2 — structlog with async support:

import structlog

structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.JSONRenderer(),
    ],
    logger_factory=structlog.PrintLoggerFactory(),  # stdout — fast, let log aggregator handle it
)

log = structlog.get_logger()

async def handle_request(request: Request):
    # Bind context variables — available in all subsequent log calls in this coroutine
    structlog.contextvars.bind_contextvars(
        request_id = request.state.request_id,
        user_id    = request.state.user_id,
    )
    log.info("request.started", path=request.url.path)
    # ...
    log.info("request.completed", status=200, duration_ms=42)


# Solution 3 — Write to stdout only; external log shipper handles I/O
# The most common production pattern:
# Application: writes structured JSON to stdout (fast — buffered).
# Container runtime (Docker/Kubernetes): captures stdout.
# Log shipper (Filebeat, Fluentd, Vector): tails the container log files
#   and ships to Elasticsearch/Splunk/Loki.
# Result: application never does disk I/O for logging — stdout is just a memory buffer.

# Caveat: stdout buffer flushes on newline (line-buffered in a terminal,
# fully-buffered when piped). Ensure each log record is one line.
# Force line-buffered output: PYTHONUNBUFFERED=1 or sys.stdout.reconfigure(line_buffering=True)
```

## Section 6: Real-World Patterns

**Q11. How do you design a bulk API endpoint that processes large payloads without blocking — the complete pattern?**
A:

```python
# bulk_endpoint.py — production pattern for large payload processing

import asyncio, orjson, time
from fastapi import FastAPI, Request, HTTPException, BackgroundTasks
from fastapi.responses import JSONResponse

app = FastAPI()

# ── CONFIGURATION ─────────────────────────────────────────────────────────────
MAX_BODY_BYTES       = 50 * 1024 * 1024   # 50MB absolute limit
SYNC_PROCESS_LIMIT   = 100               # process synchronously below this many records
ASYNC_PROCESS_LIMIT  = 10_000            # process async up to this many records
REJECT_ABOVE         = 10_000            # reject requests larger than this

BATCH_SIZE           = 500              # records per DB batch
YIELD_EVERY          = 100              # yield to event loop every N records


# ── REQUEST HANDLING ──────────────────────────────────────────────────────────

@app.post("/api/v1/loans/bulk-import")
async def bulk_import_loans(
    request:          Request,
    background_tasks: BackgroundTasks,
):
    # Step 1: read the raw body (async — doesn't block)
    body = await request.body()

    # Step 2: size check before parsing (cheap — just len())
    if len(body) > MAX_BODY_BYTES:
        raise HTTPException(413, f"Payload exceeds {MAX_BODY_BYTES // 1024 // 1024}MB limit")

    # Step 3: parse JSON off the event loop (if large)
    parse_start = time.monotonic()
    if len(body) > 100 * 1024:   # 100KB threshold
        records_raw = await _parse_json_offloaded(body)
    else:
        records_raw = orjson.loads(body)   # small enough to parse inline
    parse_ms = (time.monotonic() - parse_start) * 1000

    # Step 4: validate top-level structure (cheap — just type checks)
    if not isinstance(records_raw, list):
        raise HTTPException(422, "Body must be a JSON array")

    record_count = len(records_raw)

    if record_count > REJECT_ABOVE:
        raise HTTPException(
            422,
            f"Maximum {REJECT_ABOVE} records per request. "
            f"Got {record_count}. Use the streaming endpoint for larger imports."
        )

    # Step 5: route based on size
    if record_count <= SYNC_PROCESS_LIMIT:
        # Small batch: process inline, return result immediately
        result = await _process_records_inline(records_raw)
        return JSONResponse({
            "status":      "completed",
            "total":       record_count,
            "succeeded":   result["succeeded"],
            "failed":      result["failed"],
            "parse_ms":    round(parse_ms, 1),
        })
    else:
        # Large batch: enqueue as a background job, return job ID immediately
        job_id = await _enqueue_bulk_job(records_raw)
        return JSONResponse(
            status_code=202,   # Accepted — not yet complete
            content={
                "status":    "accepted",
                "job_id":    job_id,
                "total":     record_count,
                "poll_url":  f"/api/v1/jobs/{job_id}",
                "parse_ms":  round(parse_ms, 1),
            },
        )


async def _parse_json_offloaded(raw: bytes) -> list:
    """Parse JSON on a thread pool. Returns the parsed Python object."""
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(_json_thread_pool, orjson.loads, raw)


async def _process_records_inline(records: list) -> dict:
    """
    Process a small batch of records inline (same request lifecycle).
    Yields to event loop between batches to avoid blocking.
    """
    succeeded = 0
    failed    = 0
    errors    = []

    for i, record in enumerate(records):
        try:
            await _validate_and_insert(record)
            succeeded += 1
        except Exception as exc:
            failed += 1
            errors.append({"index": i, "error": str(exc)})

        # Yield to event loop every YIELD_EVERY records
        if i % YIELD_EVERY == 0 and i > 0:
            await asyncio.sleep(0)

    return {"succeeded": succeeded, "failed": failed, "errors": errors[:10]}


async def _validate_and_insert(record: dict) -> None:
    """Validate and insert a single loan record."""
    # Pydantic validation (fast — ~0.1ms per record for simple schemas)
    loan = LoanImportRecord(**record)   # raises ValidationError if invalid

    # Async DB insert — event loop is free while DB processes
    async with db_pool.acquire() as conn:
        await conn.execute("""
            INSERT INTO loans (borrower_name, amount, status, org_id)
            VALUES ($1, $2, $3, $4)
        """, loan.borrower_name, loan.amount, "pending", loan.org_id)


async def _enqueue_bulk_job(records: list) -> str:
    """Serialize records and enqueue as a background job in Redis."""
    import uuid
    job_id = str(uuid.uuid4())

    # Serialize with orjson (fast) — store in Redis with 24h TTL
    serialized = orjson.dumps({"records": records, "status": "pending"})
    await redis.setex(f"bulk_job:{job_id}", 86400, serialized)

    # Enqueue job ID for a worker process to pick up
    await redis.rpush("bulk_import_queue", job_id)

    return job_id


# ── BACKGROUND WORKER (runs in a separate process) ───────────────────────────

async def bulk_import_worker() -> None:
    """
    Separate asyncio process that processes bulk import jobs.
    Runs independently of the API server — no shared event loop.
    """
    while True:
        # Blocking pop with 5s timeout — waits for a job
        job_item = await redis.blpop("bulk_import_queue", timeout=5)
        if not job_item:
            continue

        _, job_id_bytes = job_item
        job_id = job_id_bytes.decode()

        # Fetch job data
        raw = await redis.get(f"bulk_job:{job_id}")
        if not raw:
            logger.error("Job %s not found in Redis", job_id)
            continue

        job_data = orjson.loads(raw)
        records  = job_data["records"]

        # Update status: running
        await redis.setex(
            f"bulk_job:{job_id}", 86400,
            orjson.dumps({**job_data, "status": "running", "started_at": time.time()}),
        )

        # Process in batches — yields between batches
        succeeded = 0
        failed    = 0

        for batch_start in range(0, len(records), BATCH_SIZE):
            batch = records[batch_start:batch_start + BATCH_SIZE]
            try:
                batch_result = await _insert_batch(batch)
                succeeded += batch_result["succeeded"]
                failed    += batch_result["failed"]
            except Exception as exc:
                logger.error("Batch failed: %s", exc)
                failed += len(batch)

            # Yield between batches — keep this worker responsive
            await asyncio.sleep(0)

            # Update progress
            await redis.setex(
                f"bulk_job:{job_id}", 86400,
                orjson.dumps({
                    **job_data,
                    "status":    "running",
                    "processed": batch_start + len(batch),
                    "total":     len(records),
                }),
            )

        # Final status update
        await redis.setex(
            f"bulk_job:{job_id}", 86400,
            orjson.dumps({
                "status":    "completed",
                "total":     len(records),
                "succeeded": succeeded,
                "failed":    failed,
                "completed_at": time.time(),
            }),
        )


async def _insert_batch(records: list) -> dict:
    """Insert a batch of records using executemany — single DB round-trip."""
    succeeded = 0
    failed    = 0
    valid_records = []

    for record in records:
        try:
            loan = LoanImportRecord(**record)
            valid_records.append((loan.borrower_name, loan.amount, "pending", loan.org_id))
            succeeded += 1
        except Exception:
            failed += 1

    if valid_records:
        async with db_pool.acquire() as conn:
            await conn.executemany("""
                INSERT INTO loans (borrower_name, amount, status, org_id)
                VALUES ($1, $2, $3, $4)
            """, valid_records)

    return {"succeeded": succeeded, "failed": failed}
```

**Q12. What are the differences between Node.js, Python asyncio, and Go in how they handle blocking — and what does each runtime provide to mitigate it?**
A:

```
Node.js:
  Model: single-threaded event loop (V8 + libuv).
  All JavaScript runs on one thread — no parallelism in JS.
  Blocking: any synchronous JS code blocks the entire process.

  Mitigations:
    worker_threads: run JS in a separate thread with its own V8 instance.
                    Communicate via postMessage (structured clone — copies data).
                    Use for: CPU-intensive JS (crypto, image processing, JSON).
    child_process:  spawn a separate Node.js process. Higher overhead.
    libuv thread pool: automatically used for fs.*, dns.lookup(), crypto.*
                       Thread pool size: UV_THREADPOOL_SIZE (default 4, max 1024).
                       Increase if file I/O or bcrypt is a bottleneck:
                       UV_THREADPOOL_SIZE=16 node app.js
    cluster module: fork N worker processes (one per CPU core).
                    Each process has its own event loop.
                    OS load-balances incoming connections across workers.
                    For CPU-bound: each worker handles some requests independently.

  Key insight for Node.js: libuv's thread pool is the mechanism behind all
  "async" file system calls. fs.readFile() is NOT kernel-level async I/O —
  it runs blocking open()/read() in a thread pool thread. The event loop is
  free while the thread pool thread blocks on disk. This is different from
  network I/O (sockets), which uses epoll/kqueue — true kernel async I/O.

Python asyncio:
  Model: single-threaded event loop (asyncio). GIL limits true parallelism.
  Blocking: any non-awaited synchronous code blocks the event loop thread.

  Mitigations:
    run_in_executor(ThreadPoolExecutor): runs blocking code in a thread.
      GIL is released by C extensions (json, gzip, hashlib) → true parallelism.
      GIL is NOT released by pure Python → threads take turns → useful for I/O
      blocking (where the GIL IS released during system calls) but not pure Python CPU.
    run_in_executor(ProcessPoolExecutor): separate process, bypasses GIL.
      True parallelism for pure Python CPU work. High IPC overhead.
    asyncio.to_thread() (Python 3.9+): shorthand for run_in_executor with default pool.
      await asyncio.to_thread(json.loads, raw)  ← same as run_in_executor
    uvloop: drop-in replacement for asyncio's event loop.
      Written in Cython, uses libuv under the hood (same as Node.js).
      2–4× faster I/O than stdlib asyncio. Install: pip install uvloop.
      asyncio.set_event_loop_policy(uvloop.EventLoopPolicy())

Go:
  Model: M:N threading — goroutines multiplexed onto OS threads by the Go scheduler.
  NOT a single-threaded event loop — GOMAXPROCS OS threads run simultaneously.
  Blocking: a blocking system call in one goroutine does NOT block others.
    Go's runtime detects blocking syscalls and parks the OS thread,
    creating a new OS thread to continue running other goroutines.
    True parallelism: GOMAXPROCS goroutines run simultaneously on different cores.

  "Blocking" in Go has a different meaning:
    - Goroutine blocking (channel receive, mutex, time.Sleep): fine — goroutine
      is parked; OS thread runs other goroutines.
    - Heavy CPU work IN a goroutine: blocks THAT goroutine's OS thread from
      running other goroutines assigned to it. With GOMAXPROCS > 1, other
      threads continue — usually not a problem.
    - runtime.LockOSThread(): locks a goroutine to one OS thread — can cause
      starvation if that goroutine blocks on CPU.

  Go mitigation for CPU-bound: spread goroutines across worker pool.
    Not because of event loop blocking (Go has no single event loop),
    but to control memory usage (each goroutine starts with 2–8KB stack,
    growing as needed) and to throttle concurrency.

# Summary table:

Runtime     Blocking mechanism          Primary mitigation
──────────  ──────────────────────────  ──────────────────────────────────────
Node.js     Single JS thread            worker_threads; libuv thread pool; cluster
Python      GIL + single event loop     run_in_executor; asyncio.to_thread; uvloop
Go          Goroutine CPU starvation    Worker pool goroutines; GOMAXPROCS tuning
Rust/Tokio  async task starvation       spawn_blocking() for sync work; Rayon for CPU
```

| Workload Type | Pool Type | `max_workers` | Rationale |
|---|---|---|---|
| CPU-bound, GIL-releasing (json, gzip, hashlib) | `ThreadPoolExecutor` | `cpu_count` | Parallel in threads; bound by CPU |
| CPU-bound, GIL-holding (pandas, pure Python) | `ProcessPoolExecutor` | `cpu_count` | True parallelism needs processes |
| I/O-bound blocking (sync DB, sync HTTP, file I/O) | `ThreadPoolExecutor` | `cpu_count * 4–8` | Threads mostly waiting; more = better throughput |
| Mixed workload | Two pools (one per type) | As above | Prevent CPU work from starving I/O workers |
| Node.js libuv (UV_THREADPOOL_SIZE) | libuv | 4 (default) → 16 | Increase if fs or crypto is bottleneck |

**Tip for the interview:** At 5 YOE, the event loop blocking question is almost never "what is the event loop?" — it's a debugging scenario: "your async service handles 5,000 req/s in load tests but p99 latency spikes to 500ms in production — what's happening?" Know the event loop lag measurement pattern cold (Q2) — the timer drift technique works in any async runtime and directly measures the problem. The `await` misconception (Q3) is the most common depth signal: `await json.loads()` is a SyntaxError because `json.loads()` is not a coroutine and `await` does not make synchronous code async — this surprises a lot of candidates who think `async/await` is a magic performance improvement. For JSON specifically (Q5, Q6), know the three strategies (offload to thread, streaming parse, schema enforcement at the gate) and when each applies: thread pool for anything over ~100KB, streaming parse for anything that would exhaust memory. The `await asyncio.sleep(0)` pattern (Q7) is a senior-level signal — know that it only helps with loops you control, not with single blocking C calls. For real-world design (Q11), the correct answer for large bulk imports is always the async job pattern: accept the payload, parse it off-thread, enqueue a job, return 202 Accepted immediately — never make the client wait 30 seconds for a synchronous bulk operation to complete.
