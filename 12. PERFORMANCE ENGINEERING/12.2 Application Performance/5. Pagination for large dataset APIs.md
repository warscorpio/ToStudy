# API Design (Performance): Pagination for Large Dataset APIs — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why is pagination necessary, and what are the failure modes of returning unbounded results?**
A: Pagination is the practice of returning a subset of a large result set in each API response, with a mechanism for the client to retrieve subsequent subsets. It is necessary because returning all matching records in a single response fails at every layer of the stack as data grows:

**Database layer:** a query like `SELECT * FROM loan_applications WHERE tenant_id = 'x'` returning 500,000 rows requires the database to scan, assemble, and transmit the full result set. Memory pressure on the database, lock contention during the scan, and query duration all scale linearly with result set size. A query that takes 50ms for 1,000 rows takes 25 seconds for 500,000.

**Network layer:** a 500,000-row JSON response can easily be 500MB. At 100Mbps, that's 40 seconds of transmission time. Mobile clients on 4G may time out. Load balancers and API gateways have response size limits (AWS ALB default: 1MB for HTTP/2, configurable for HTTP/1.1).

**Application layer:** the NestJS process must hold the entire result set in memory while serialising it to JSON. A 500MB response means 500MB of heap pressure per concurrent request of that type, easily exhausting the process's memory.

**Client layer:** a browser receiving 500MB of JSON must parse and render it. A mobile app holding 500,000 records in memory is likely to be killed by the OS. Even a server-side consumer must allocate memory for the full set before it can begin processing.

**Failure modes without pagination:**
- **OOM crashes** — the Node.js process exhausts `--max-old-space-size` and crashes.
- **Database timeouts** — the query exceeds the connection timeout and returns an error to the client.
- **Gateway timeouts** — the load balancer times out the request (AWS ALB default: 60 seconds).
- **DoS amplification** — a single unauthenticated query can consume gigabytes of server resources.
- **Inconsistent reads** — a long-running query may span multiple transactions, reading data in different states.

The correct default for any list endpoint is: **always paginate, always have a maximum page size, always enforce it regardless of what the client requests.**

**Q2. What are the three main pagination strategies, and what are their fundamental trade-offs?**
A: Three distinct strategies exist, each suited to different data characteristics and client needs:

**1. Offset pagination** — the client specifies how many rows to skip (`OFFSET`) and how many to return (`LIMIT`). The most intuitive model; maps directly to page numbers.

```sql
-- Page 3 of 20 results per page
SELECT * FROM loan_applications
WHERE tenant_id = 'x'
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;
```

Pros: trivial to implement; supports random page access (jump to page 50 directly); maps naturally to UI page numbers.
Cons: performance degrades with large offsets (database must scan and discard all preceding rows); inconsistent results when data is inserted or deleted between page fetches (rows shift between pages); not suitable for real-time feeds or high-write tables.

**2. Keyset pagination (cursor-based)** — the client provides a cursor encoding the last seen value(s) of the sort key. The server fetches rows *after* that point using a `WHERE` clause rather than `OFFSET`.

```sql
-- "Give me records after created_at=2025-08-10T10:00:00 AND id=uuid-xxx (the last seen row)"
SELECT * FROM loan_applications
WHERE tenant_id = 'x'
  AND (created_at, id) < ('2025-08-10T10:00:00', 'uuid-xxx')
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Pros: O(log n) performance regardless of depth (uses an index lookup, never scans preceding rows); stable results — inserted/deleted rows don't shift pages; consistent performance at page 1 and page 10,000.
Cons: no random page access (can't jump to page 50 without traversing pages 1–49); cursor is opaque to clients; requires the sort key to be stable and unique (or made unique with a tiebreaker).

**3. Time-based / seek pagination** — a variant of keyset pagination scoped to time windows. The client specifies a time range (`from`, `to`) rather than a positional cursor.

```sql
SELECT * FROM loan_applications
WHERE tenant_id = 'x'
  AND created_at BETWEEN '2025-08-01' AND '2025-08-07'
ORDER BY created_at DESC
LIMIT 20;
```

Pros: natural for time-series data; supports parallel fetching of different time windows; results for a past window are immutable.
Cons: uneven page sizes (busy periods have more records per time window than quiet periods); requires the client to manage time window advancement.

The choice between these strategies is driven by: data volume (offset degrades, keyset doesn't), access pattern (random page access requires offset; infinite scroll requires keyset), and data mutability (offset is broken for high-write tables; keyset is stable).

**Q3. What is the "page drift" problem with offset pagination, and how serious is it in a fintech context?**
A: Page drift occurs when rows are inserted into or deleted from the result set between two consecutive page requests, causing rows to shift positions across the offset boundary:

```
Initial state (ordered by created_at DESC):
  Row A (newest)
  Row B
  Row C  ← client fetches page 1 (rows A, B, C)
  Row D
  Row E  ← client is about to fetch page 2 (rows D, E, F)
  Row F

Between page 1 and page 2, a new row X is inserted at the top:
  Row X (inserted)
  Row A
  Row B
  Row C  ← OFFSET 3 now points here
  Row D  ← client expects this to be first result on page 2
  Row E  ← but X pushed everything down by 1
  Row F

Client fetches page 2 with OFFSET=3, LIMIT=3:
  Gets: Row C, Row D, Row E
  Row C was already shown on page 1 — DUPLICATE
  Row F is never shown — SKIPPED
```

**In a fintech context, this is serious:**

- A loan officer paginating through pending applications may see the same application twice (Row C) — wasting review time and potentially causing duplicate actions.
- Row F (another pending application) is never shown — a loan goes unreviewed, potentially causing SLA breaches.
- A customer viewing their transaction history may see a duplicate transaction or miss one — triggering a support ticket, confusion, or false fraud reporting.
- A reconciliation report that paginates through all transactions with offset may produce incorrect totals if rows are inserted during the report run — a compliance risk.

The severity scales with write frequency. A table that receives 10,000 inserts per hour will drift significantly during a 30-page traversal. A table that's essentially append-only-historical (closed loan records) may never drift in practice.

**Mitigation for offset pagination when it's unavoidable:**
- Add an explicit `snapshot_id` mechanism (PostgreSQL's `REPEATABLE READ` transaction isolation across page fetches) — complex but eliminates drift at the DB level.
- Use a timestamp filter: `WHERE created_at < $snapshotTime ORDER BY created_at DESC OFFSET $n` — pins results to a point in time.
- Use keyset pagination for all high-write, high-stakes list endpoints.

## Section 2: Offset Pagination — Implementation

**Q4. How do you implement offset pagination in NestJS with TypeORM, including total count and metadata?**
A:
```typescript
// pagination.dto.ts
import { IsInt, IsOptional, Max, Min } from 'class-validator';
import { Type } from 'class-transformer';

export class PaginationDto {
  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  page: number = 1;

  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  @Max(100)          // enforce a hard cap — never let clients request 10,000 rows
  limit: number = 20;

  get offset(): number {
    return (this.page - 1) * this.limit;
  }
}

// paginated-response.ts
export interface PaginatedResponse<T> {
  data:       T[];
  meta: {
    total:       number;   // total matching records (for page count computation)
    page:        number;   // current page (1-indexed)
    limit:       number;   // page size used
    totalPages:  number;   // Math.ceil(total / limit)
    hasNextPage: boolean;
    hasPrevPage: boolean;
  };
}

// loan-applications.service.ts
@Injectable()
export class LoanApplicationService {
  constructor(
    @InjectRepository(LoanApplication)
    private readonly repo: Repository<LoanApplication>,
  ) {}

  async findAll(
    tenantId:      string,
    dto:           PaginationDto,
    filters:       LoanFilterDto,
  ): Promise<PaginatedResponse<LoanApplicationDto>> {
    const qb = this.repo
      .createQueryBuilder('loan')
      .where('loan.tenantId = :tenantId', { tenantId })
      .orderBy('loan.createdAt', 'DESC')
      .addOrderBy('loan.id', 'DESC');   // tiebreaker for stable ordering

    // Apply optional filters
    if (filters.status)
      qb.andWhere('loan.status = :status', { status: filters.status });
    if (filters.assignedTo)
      qb.andWhere('loan.assignedTo = :officer', { officer: filters.assignedTo });
    if (filters.dateFrom)
      qb.andWhere('loan.createdAt >= :from', { from: filters.dateFrom });
    if (filters.dateTo)
      qb.andWhere('loan.createdAt <= :to', { to: filters.dateTo });

    // IMPORTANT: getManyAndCount runs TWO queries:
    // 1. COUNT(*) query — for total
    // 2. SELECT with LIMIT/OFFSET — for the page data
    // Both use the same WHERE clause — efficient with the right index
    const [data, total] = await qb
      .skip(dto.offset)
      .take(dto.limit)
      .getManyAndCount();

    const totalPages = Math.ceil(total / dto.limit);

    return {
      data: data.map(this.toDto),
      meta: {
        total,
        page:        dto.page,
        limit:       dto.limit,
        totalPages,
        hasNextPage: dto.page < totalPages,
        hasPrevPage: dto.page > 1,
      },
    };
  }
}
```

**The response shape:**
```json
{
  "data": [
    { "id": "loan-001", "status": "pending", "amount": 50000 },
    { "id": "loan-002", "status": "pending", "amount": 75000 }
  ],
  "meta": {
    "total": 847,
    "page": 3,
    "limit": 20,
    "totalPages": 43,
    "hasNextPage": true,
    "hasPrevPage": true
  }
}
```

**Q5. What is the COUNT(*) performance problem with offset pagination, and how do you mitigate it?**
A: `getManyAndCount()` runs a `COUNT(*)` query alongside the data query. For small tables this is trivial. For large tables (millions of rows) with complex `WHERE` clauses, the `COUNT(*)` query can be as expensive as a full table scan — sometimes more expensive than the data query itself:

```sql
-- COUNT(*) must scan all matching rows — potentially millions
SELECT COUNT(*) FROM loan_applications
WHERE tenant_id = 'nbfc-xyz'
  AND status = 'pending'
  AND created_at >= '2025-01-01';
-- May take 500ms to 5 seconds on a large table with many matching rows
```

**Mitigation strategies:**

**1. Skip count for non-first pages (most impactful):**
```typescript
async findAll(dto: PaginationDto): Promise<PaginatedResponse<LoanDto>> {
  // Only compute count on page 1 — return cached/stored count for subsequent pages
  if (dto.page === 1) {
    const [data, total] = await qb.skip(0).take(dto.limit).getManyAndCount();
    return buildResponse(data, total, dto);
  } else {
    // Client must pass the total from page 1's response back
    const total = dto.totalHint ?? 0;   // client sends ?totalHint=847 from page 1
    const data  = await qb.skip(dto.offset).take(dto.limit).getMany();
    return buildResponse(data, total, dto);
  }
}
```

**2. Approximate count with PostgreSQL statistics:**
```typescript
// Fast approximate count using pg_class statistics (updated by ANALYZE)
// Accurate to within ~10% for most tables; zero scan cost
async getApproximateCount(tableName: string, whereClause: string): Promise<number> {
  const result = await this.dataSource.query(`
    SELECT reltuples::bigint AS estimate
    FROM pg_class
    WHERE relname = $1
  `, [tableName]);
  return result[0].estimate;
  // Or: use EXPLAIN to extract the planner's row estimate without executing
}
```

**3. Count with a covering index:**
```sql
-- A covering index that includes all WHERE columns allows count-only queries
-- to be answered from the index without touching the heap
CREATE INDEX idx_loans_tenant_status_date ON loan_applications
  (tenant_id, status, created_at);
-- COUNT(*) with WHERE tenant_id = ? AND status = ? can use this index
-- and never reads the actual table rows
```

**4. Pre-computed counts for common filters:**
```typescript
// Materialised count for the most common filter combination
// Update via trigger or periodic job
CREATE TABLE loan_count_cache (
  tenant_id   UUID NOT NULL,
  status      TEXT NOT NULL,
  count       INTEGER NOT NULL,
  computed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (tenant_id, status)
);
```

**5. Use `hasNextPage` without total count (cursor pattern):**
For keyset pagination, you don't need a total count at all — fetch `limit + 1` rows; if `limit + 1` rows returned, `hasNextPage = true`; return only the first `limit` rows to the client. Eliminates the `COUNT(*)` query entirely.

## Section 3: Keyset (Cursor-Based) Pagination — Implementation

**Q6. How do you implement keyset pagination in NestJS with a stable, opaque cursor?**
A: Keyset pagination requires: a stable sort order (including a tiebreaker to handle equal sort keys), a cursor encoding the last seen position, and a `WHERE` clause that seeks directly to that position.

```typescript
// cursor.ts — encode/decode the cursor as a base64url-encoded JSON
export function encodeCursor(values: Record<string, unknown>): string {
  return Buffer.from(JSON.stringify(values)).toString('base64url');
}

export function decodeCursor(cursor: string): Record<string, unknown> {
  try {
    return JSON.parse(Buffer.from(cursor, 'base64url').toString('utf8'));
  } catch {
    throw new BadRequestException('Invalid pagination cursor');
  }
}

// keyset-pagination.dto.ts
export class KeysetPaginationDto {
  @IsOptional()
  @IsString()
  cursor?: string;    // opaque base64url-encoded cursor

  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  @Max(100)
  limit: number = 20;
}

// loan-applications.service.ts
async findAllCursor(
  tenantId: string,
  dto:      KeysetPaginationDto,
): Promise<CursorPaginatedResponse<LoanApplicationDto>> {
  const qb = this.repo
    .createQueryBuilder('loan')
    .where('loan.tenantId = :tenantId', { tenantId })
    .orderBy('loan.createdAt', 'DESC')
    .addOrderBy('loan.id', 'DESC');  // UUID tiebreaker ensures deterministic ordering

  // Apply cursor position if provided
  if (dto.cursor) {
    const { createdAt, id } = decodeCursor(dto.cursor) as { createdAt: string; id: string };

    // Row comparison: (createdAt, id) < (cursorCreatedAt, cursorId)
    // This is the "seek predicate" — uses the composite index efficiently
    qb.andWhere(
      '(loan.createdAt, loan.id) < (:cursorDate, :cursorId)',
      { cursorDate: createdAt, cursorId: id },
    );
  }

  // Fetch limit + 1 to detect whether there's a next page
  const rows = await qb.take(dto.limit + 1).getMany();

  const hasNextPage = rows.length > dto.limit;
  const data        = hasNextPage ? rows.slice(0, dto.limit) : rows;

  // Build the cursor from the last item returned
  const nextCursor = hasNextPage
    ? encodeCursor({
        createdAt: data[data.length - 1].createdAt.toISOString(),
        id:        data[data.length - 1].id,
      })
    : null;

  return {
    data: data.map(this.toDto),
    meta: {
      hasNextPage,
      nextCursor,    // null when on the last page
      limit:         dto.limit,
    },
  };
}
```

**Response shape:**
```json
{
  "data": [
    { "id": "loan-020", "createdAt": "2025-08-10T09:00:00Z", "status": "pending" },
    { "id": "loan-019", "createdAt": "2025-08-10T08:55:00Z", "status": "approved" }
  ],
  "meta": {
    "hasNextPage": true,
    "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI1LTA4LTEwVDA4OjU1OjAwWiIsImlkIjoibG9hbi0wMTkifQ",
    "limit": 20
  }
}
```

**Client usage:**
```typescript
// Fetch page 1
const page1 = await fetch('/api/loans?limit=20');
const { data, meta } = await page1.json();

// Fetch page 2 using the cursor from page 1
const page2 = await fetch(`/api/loans?limit=20&cursor=${meta.nextCursor}`);
```

**Q7. Why is a composite sort key with a tiebreaker mandatory for keyset pagination?**
A: The keyset cursor encodes the position in the sorted result set. If two rows have identical values for the sort key, the cursor is ambiguous — the server can't determine which of the two identical rows the cursor refers to.

**Without a tiebreaker — the bug:**
```sql
-- Sort by created_at only
ORDER BY created_at DESC

-- Suppose rows at the page boundary have the same created_at timestamp:
-- created_at=2025-08-10T09:00:00, id=loan-003
-- created_at=2025-08-10T09:00:00, id=loan-002  ← last row on page 1
-- created_at=2025-08-10T09:00:00, id=loan-001

-- Cursor encodes: { createdAt: "2025-08-10T09:00:00" }
-- Page 2 query: WHERE created_at < '2025-08-10T09:00:00'
-- This SKIPS loan-003 and loan-001 — they have the same timestamp as the cursor
-- but are not fetched because they're not strictly less than the cursor value
```

**With a tiebreaker (UUID or sequential ID):**
```sql
-- Sort by (created_at, id) both DESC
ORDER BY created_at DESC, id DESC

-- Cursor encodes: { createdAt: "2025-08-10T09:00:00", id: "loan-002" }
-- Page 2 query:
-- WHERE (created_at, id) < ('2025-08-10T09:00:00', 'loan-002')
-- This correctly includes loan-001 and loan-003
-- (UUID ordering is consistent — it's alphabetical on the UUID string)
```

The tiebreaker must be:
- **Unique** — guarantees no two rows have identical composite sort keys.
- **Stable** — the value never changes after row creation.
- **Monotonically ordered or at least consistent** — UUIDs produced by `gen_random_uuid()` have no natural order (they're random); use `uuid_generate_v7()` (time-ordered UUID) or a `BIGSERIAL` id as a better tiebreaker. If using a random UUID as tiebreaker, the ordering is consistent within a single query but not semantically meaningful — this is fine for pagination but confusing for humans.

**PostgreSQL row comparison (`(col1, col2) < (:v1, :v2)`):**
This syntax uses row value comparison, which is equivalent to:
```sql
(created_at < :cursorDate)
OR (created_at = :cursorDate AND id < :cursorId)
```
PostgreSQL's query planner can use a composite index `(created_at DESC, id DESC)` for this comparison efficiently — it's a range scan, not a full table scan.

**Q8. How do you handle bidirectional cursor pagination (both next and previous pages)?**
A: Standard keyset pagination is unidirectional — you can only move forward. For bidirectional navigation (required when users can browse backwards through a history view), you need both a `nextCursor` and a `prevCursor`, and the ability to fetch pages in the previous direction.

```typescript
// bidirectional-cursor.dto.ts
export class BidirectionalCursorDto {
  @IsOptional() @IsString()
  after?: string;    // cursor from the last item — fetch next page

  @IsOptional() @IsString()
  before?: string;   // cursor from the first item — fetch previous page

  @IsOptional() @Type(() => Number) @IsInt() @Min(1) @Max(100)
  limit: number = 20;
}

async findBidirectional(
  tenantId: string,
  dto:      BidirectionalCursorDto,
): Promise<BidirectionalPaginatedResponse<LoanDto>> {
  const qb = this.repo.createQueryBuilder('loan')
    .where('loan.tenantId = :tenantId', { tenantId });

  if (dto.after) {
    // Moving forward: fetch rows AFTER the cursor (DESC order, so rows with smaller values)
    const { createdAt, id } = decodeCursor(dto.after);
    qb.andWhere('(loan.createdAt, loan.id) < (:date, :id)', { date: createdAt, id })
      .orderBy('loan.createdAt', 'DESC')
      .addOrderBy('loan.id', 'DESC');

  } else if (dto.before) {
    // Moving backward: fetch rows BEFORE the cursor (DESC order, so rows with larger values)
    // To get the correct N rows, we reverse the order, take N+1, then reverse the result
    const { createdAt, id } = decodeCursor(dto.before);
    qb.andWhere('(loan.createdAt, loan.id) > (:date, :id)', { date: createdAt, id })
      .orderBy('loan.createdAt', 'ASC')   // reversed: ASC to get the rows just before 'before'
      .addOrderBy('loan.id', 'ASC');

  } else {
    // First page
    qb.orderBy('loan.createdAt', 'DESC').addOrderBy('loan.id', 'DESC');
  }

  const rows = await qb.take(dto.limit + 1).getMany();

  let data = rows;
  let hasPrevPage = false;
  let hasNextPage = false;

  if (dto.before) {
    // We fetched in reverse — flip back to the correct order
    data = rows.slice(0, dto.limit).reverse();
    hasPrevPage = rows.length > dto.limit;
    hasNextPage = true;  // we came from somewhere, so there's at least one page ahead
  } else {
    data = rows.slice(0, dto.limit);
    hasNextPage = rows.length > dto.limit;
    hasPrevPage = !!dto.after;  // if we used 'after', there's a previous page
  }

  const firstItem = data[0];
  const lastItem  = data[data.length - 1];

  return {
    data: data.map(this.toDto),
    meta: {
      hasNextPage,
      hasPrevPage,
      nextCursor: hasNextPage && lastItem
        ? encodeCursor({ createdAt: lastItem.createdAt.toISOString(), id: lastItem.id })
        : null,
      prevCursor: hasPrevPage && firstItem
        ? encodeCursor({ createdAt: firstItem.createdAt.toISOString(), id: firstItem.id })
        : null,
    },
  };
}
```

**Response shape:**
```json
{
  "data": [...],
  "meta": {
    "hasNextPage": true,
    "hasPrevPage": true,
    "nextCursor": "eyJj...",
    "prevCursor": "eyJj..."
  }
}
```

The client passes `?after=<nextCursor>` to go forward and `?before=<prevCursor>` to go backward. This matches the GraphQL Relay Cursor Connections spec — a common standard for cursor-based pagination that maps directly to this pattern.

## Section 4: Seek Method and Database-Level Optimisation

**Q9. What is the "seek method" (or keyset seek predicate), and how does it avoid the offset scan problem?**
A: The seek method is the database query technique underlying keyset pagination. Instead of `OFFSET n` (which forces the database to count and skip n rows), the seek method uses a `WHERE` clause that allows the database to seek directly to the first relevant row using an index.

**The fundamental problem with OFFSET:**
```sql
-- PostgreSQL execution with OFFSET 10000
SELECT * FROM loan_applications
WHERE tenant_id = 'x'
ORDER BY created_at DESC, id DESC
LIMIT 20
OFFSET 10000;

-- What PostgreSQL actually does:
-- 1. Scans the index, reading rows in sort order
-- 2. Counts 10,000 rows and discards them (the offset)
-- 3. Returns the next 20 rows
-- Cost scales linearly: OFFSET 10000 is ~500× more work than OFFSET 0
```

**The seek method:**
```sql
-- Seek directly to position (using the composite index)
SELECT * FROM loan_applications
WHERE tenant_id = 'x'
  AND (created_at, id) < ('2025-08-10T09:00:00Z', 'loan-10000')
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- What PostgreSQL actually does:
-- 1. Uses the composite index to seek to the first row satisfying the predicate
-- 2. Reads the next 20 rows in order
-- Cost is O(log n) regardless of how deep into the result set you are
-- Page 500 costs the same as page 1
```

**EXPLAIN comparison:**
```sql
-- OFFSET approach on page 500:
EXPLAIN ANALYZE
SELECT * FROM loan_applications WHERE tenant_id = 'x'
ORDER BY created_at DESC OFFSET 10000 LIMIT 20;

-- Index Scan using idx_loans_tenant_date on loan_applications
--   (cost=0.56..15432.18 rows=20 width=200)
--   (actual time=234.82..234.91 rows=20 loops=1)
-- Rows Removed by Filter: 0
-- Buffers: shared hit=10021  ← reads 10,021 index pages (the offset + page)

-- Seek method on the same position:
EXPLAIN ANALYZE
SELECT * FROM loan_applications
WHERE tenant_id = 'x' AND (created_at, id) < ('2025-08-10T09:00:00Z', 'uuid-xxx')
ORDER BY created_at DESC LIMIT 20;

-- Index Scan using idx_loans_tenant_date on loan_applications
--   (cost=0.56..52.18 rows=20 width=200)
--   (actual time=0.082..0.134 rows=20 loops=1)
-- Buffers: shared hit=5     ← reads only 5 index pages
```

The seek method reads 5 buffer pages instead of 10,021 — a 2,000× reduction in I/O for page 500.

**Q10. How do you handle multi-column sort with filters in keyset pagination without Cartesian product complexity?**
A: Real-world API endpoints often need filtering combined with sorting, and the filter columns may not be the sort columns. This creates a complexity challenge for the seek predicate.

**Scenario:** list loans for a tenant, filterable by `status`, sorted by `created_at DESC, id DESC`.

```typescript
async findFiltered(
  tenantId: string,
  status:   string | undefined,
  cursor:   string | undefined,
  limit:    number,
): Promise<CursorPaginatedResponse<LoanDto>> {
  const qb = this.repo.createQueryBuilder('loan')
    .where('loan.tenantId = :tenantId', { tenantId })
    .orderBy('loan.createdAt', 'DESC')
    .addOrderBy('loan.id', 'DESC');

  // Filters applied independently of the cursor
  if (status) qb.andWhere('loan.status = :status', { status });

  // Cursor is always based on the SORT key, not the filter key
  // The sort key (createdAt, id) is always in the cursor regardless of filters
  if (cursor) {
    const { createdAt, id } = decodeCursor(cursor);
    qb.andWhere('(loan.createdAt, loan.id) < (:date, :id)', { date: createdAt, id });
  }

  const rows = await qb.take(limit + 1).getMany();
  // ... rest of cursor logic
}
```

The cursor encodes only the sort key values — not the filter values. The filter is re-applied on every page request. This keeps the cursor compact and the seek predicate efficient.

**Index needed for this combination:**
```sql
-- Covers both the filter column and the sort columns
CREATE INDEX idx_loans_tenant_status_date ON loan_applications
  (tenant_id, status, created_at DESC, id DESC);
-- Supports: WHERE tenant_id = ? AND status = ? AND (created_at, id) < (?, ?)
```

**Complex sort scenario — sorting by a nullable column:**
```sql
-- Sort by risk_score DESC NULLS LAST, then id DESC
-- NULLs go to the end: NULLS LAST reverses to NULLS FIRST in the seek predicate

-- Cursor must encode whether the last row had a null risk_score:
-- { riskScore: null, id: "loan-xxx" } or { riskScore: 85, id: "loan-xxx" }

-- Seek predicate for non-null:
WHERE (risk_score < :score OR risk_score IS NULL)
   OR (risk_score = :score AND id < :id)
-- This handles the NULLS LAST ordering correctly
```

Nullable sort columns significantly complicate keyset pagination — the cursor must encode nullability and the seek predicate must handle `NULL` comparisons explicitly. For simplicity, avoid nullable sort columns; if they're required, document the complexity carefully.

## Section 5: GraphQL and Relay Cursor Connections

**Q11. What is the GraphQL Relay Cursor Connections specification, and how do you implement it in NestJS?**
A: The Relay Cursor Connections specification is a standard for cursor-based pagination in GraphQL APIs, defined by the Relay framework but widely adopted independently. It standardises the shape of paginated responses and the arguments for page navigation.

**Standard shape:**
```graphql
type LoanConnection {
  edges: [LoanEdge!]!
  pageInfo: PageInfo!
  totalCount: Int   # optional — expensive for large datasets
}

type LoanEdge {
  node:   LoanApplication!
  cursor: String!     # cursor for this specific item (can seek to exactly this position)
}

type PageInfo {
  hasNextPage:     Boolean!
  hasPreviousPage: Boolean!
  startCursor:     String   # cursor of the first item in this page
  endCursor:       String   # cursor of the last item in this page
}

type Query {
  loans(
    first:  Int     # fetch first N items (forward pagination)
    after:  String  # cursor — fetch items after this position
    last:   Int     # fetch last N items (backward pagination)
    before: String  # cursor — fetch items before this position
  ): LoanConnection!
}
```

**NestJS implementation with `@nestjs/graphql`:**
```typescript
// loan.resolver.ts
@Resolver(() => LoanApplication)
export class LoanResolver {
  constructor(private readonly loanService: LoanApplicationService) {}

  @Query(() => LoanConnection)
  async loans(
    @CurrentUser() user: AuthUser,
    @Args('first',  { nullable: true, type: () => Int }) first?: number,
    @Args('after',  { nullable: true })                  after?: string,
    @Args('last',   { nullable: true, type: () => Int }) last?: number,
    @Args('before', { nullable: true })                  before?: string,
  ): Promise<LoanConnection> {
    // Validate: either first/after or last/before, not both
    if (first && last) throw new BadRequestException('Cannot use first and last simultaneously');

    const limit = first ?? last ?? 20;
    if (limit > 100) throw new BadRequestException('Cannot request more than 100 items');

    return this.loanService.findWithRelay({
      tenantId: user.tenantId,
      first, after, last, before,
    });
  }
}

// connection.types.ts
@ObjectType()
export class PageInfo {
  @Field()          hasNextPage:     boolean;
  @Field()          hasPreviousPage: boolean;
  @Field(() => String, { nullable: true }) startCursor: string | null;
  @Field(() => String, { nullable: true }) endCursor:   string | null;
}

@ObjectType()
export class LoanEdge {
  @Field(() => LoanApplication) node:   LoanApplication;
  @Field()                       cursor: string;
}

@ObjectType()
export class LoanConnection {
  @Field(() => [LoanEdge])   edges:    LoanEdge[];
  @Field(() => PageInfo)     pageInfo: PageInfo;
}
```

Each `edge` has its own cursor (not just the page's end cursor), allowing clients to seek to any specific item rather than just page boundaries. This is useful for "scroll to this specific loan" features.

## Section 6: Streaming and Real-Time Pagination

**Q12. When should you use server-sent events or WebSockets instead of paginated REST endpoints for large datasets?**
A: Pagination is appropriate for user-initiated browsing of historical data. For real-time feeds and large data transfers where the client needs all the data (not just a page), different mechanisms are more appropriate.

**Use streaming (Server-Sent Events, WebSockets, HTTP streaming) when:**
- The dataset is large and the client must process all records (data export, report generation, bulk reconciliation).
- Records are being created in real-time and the client must receive updates as they happen (live loan status feed, real-time payment notifications).
- The client will process records as they arrive rather than after receiving all of them (streaming CSV download, real-time dashboard).

**HTTP streaming for large export:**
```typescript
// loans.controller.ts — streaming CSV export (no pagination needed)
@Get('export')
async exportLoans(
  @CurrentUser() user: AuthUser,
  @Res() res: Response,
): Promise<void> {
  res.setHeader('Content-Type', 'text/csv');
  res.setHeader('Content-Disposition', 'attachment; filename=loans.csv');
  res.setHeader('Transfer-Encoding', 'chunked');  // stream without buffering full response

  res.write('id,applicantName,amount,status,createdAt\n');

  // Stream query results in batches — never loads full dataset into memory
  const BATCH_SIZE = 1000;
  let cursor: string | undefined;
  let hasMore = true;

  while (hasMore) {
    const { data, meta } = await this.loanService.findAllCursor(user.tenantId, {
      cursor,
      limit: BATCH_SIZE,
    });

    for (const loan of data) {
      res.write(`${loan.id},${loan.applicantName},${loan.amount},${loan.status},${loan.createdAt}\n`);
    }

    hasMore = meta.hasNextPage;
    cursor  = meta.nextCursor ?? undefined;

    // Yield the event loop between batches to allow other requests to be served
    await new Promise(resolve => setImmediate(resolve));
  }

  res.end();
}
```

**Server-Sent Events for real-time loan status updates:**
```typescript
// loans.controller.ts — real-time feed
@Sse('feed')
loanFeed(@CurrentUser() user: AuthUser): Observable<MessageEvent> {
  return this.loanEventService.getStream(user.tenantId).pipe(
    map(event => ({ data: JSON.stringify(event) } as MessageEvent)),
  );
}
```

The key principle: **pagination for browsing history; streaming for bulk transfer or real-time feeds.** Mixing them (paginating a real-time feed) produces poor UX — by the time the client reaches page 3, the data on page 1 is already stale.

**Q13. How do you implement efficient database streaming for bulk export without loading all records into Node.js memory?**
A: The critical technique is using a database cursor (not an API cursor) to stream results row-by-row from PostgreSQL, rather than fetching all matching rows into memory at once.

```typescript
// bulk-export.service.ts — using TypeORM's streaming query
import { DataSource } from 'typeorm';

@Injectable()
export class BulkExportService {
  constructor(private readonly dataSource: DataSource) {}

  async streamLoansToResponse(
    tenantId: string,
    res:      Response,
  ): Promise<void> {
    // TypeORM's stream() uses a PostgreSQL cursor internally
    // Rows are fetched from the DB in chunks, not all at once
    const stream = await this.dataSource
      .createQueryBuilder(LoanApplication, 'loan')
      .where('loan.tenantId = :tenantId', { tenantId })
      .orderBy('loan.createdAt', 'ASC')
      .stream();  // returns a Node.js Readable stream

    stream.on('data', (row: LoanApplication) => {
      // Called once per row — never holds more than one row in memory at a time
      res.write(this.toCsvRow(row));
    });

    await new Promise<void>((resolve, reject) => {
      stream.on('end',   resolve);
      stream.on('error', reject);
    });

    res.end();
  }

  // Or using pg's native cursor for more control
  async streamWithPgCursor(tenantId: string): Promise<Readable> {
    // pg-cursor: npm install pg-cursor
    const { Cursor } = await import('pg-cursor');
    const client     = await this.dataSource.driver.obtainMasterConnection();

    const cursor = client.query(
      new Cursor(
        'SELECT id, applicant_name, amount, status, created_at FROM loan_applications WHERE tenant_id = $1 ORDER BY created_at ASC',
        [tenantId],
      ),
    );

    // Fetch 500 rows at a time from the DB cursor
    const readable = new Readable({
      objectMode: true,
      async read() {
        cursor.read(500, (err, rows) => {
          if (err)             { this.destroy(err); return; }
          if (rows.length === 0) { this.push(null); return; }  // end of stream
          rows.forEach(row => this.push(row));
        });
      },
    });

    return readable;
  }
}
```

Memory profile comparison:
- **Load all then stream:** peak memory = entire result set (500MB for 500,000 rows × 1KB average row).
- **Stream with cursor:** peak memory ≈ batch size (500 rows × 1KB = 500KB), constant regardless of total result size.

## Section 7: Security, Edge Cases, and Real-World Scenarios

**Q14. What security concerns does pagination introduce, and how do you mitigate them?**
A: Pagination endpoints have several security-specific attack surfaces:

**1. Enumeration via cursor manipulation:**
If the cursor is not opaque (e.g., it directly encodes a row ID or timestamp without signing), an attacker can manipulate it to access data they're not authorised to see:
```
// Insecure cursor: base64("id=loan-999") — attacker changes to base64("id=loan-001")
// to access a different loan without going through the list endpoint
```

Mitigation: always scope cursor-based queries to the authenticated user's tenant/permissions (`WHERE tenant_id = :tenantId AND (created_at, id) < (:date, :id)`) — the cursor only controls position within the authorised result set, not which records are accessible. Never expose raw primary keys in cursors without access control at the query level.

**2. Resource exhaustion via large page sizes:**
```
GET /api/loans?limit=100000  → 100,000 rows in one response
```
Mitigation: enforce a hard maximum on `limit` in the DTO validation (`@Max(100)`) regardless of what the client sends. Also enforce at the service layer as a defence-in-depth:
```typescript
const safeLimit = Math.min(dto.limit, 100);  // never trust client-provided limit alone
```

**3. Deep offset DoS:**
```
GET /api/loans?page=999999  → OFFSET 19999980 → scans and discards 20M rows
```
Mitigation: cap the maximum allowed page number or maximum allowed offset, or switch to keyset pagination for deep traversal. A hard limit of `page <= 1000` prevents the worst cases while still allowing reasonable UI pagination.

**4. Cursor forgery / injection:**
A malicious cursor value could inject SQL if not properly parameterised:
```
cursor = base64('{"createdAt": "2025-01-01\"; DROP TABLE loan_applications; --"}')
```
Mitigation: always use parameterised queries (TypeORM's QueryBuilder does this). Validate that cursor values decode to the expected types before using them in queries:
```typescript
function decodeCursor(cursor: string): { createdAt: string; id: string } {
  const decoded = JSON.parse(Buffer.from(cursor, 'base64url').toString());
  if (typeof decoded.createdAt !== 'string' || typeof decoded.id !== 'string') {
    throw new BadRequestException('Malformed cursor');
  }
  // Validate that createdAt is a valid ISO date string
  if (isNaN(Date.parse(decoded.createdAt))) {
    throw new BadRequestException('Malformed cursor: invalid date');
  }
  return { createdAt: decoded.createdAt, id: decoded.id };
}
```

**5. Information disclosure via cursor:**
A cursor might reveal internal IDs or timestamps that the client shouldn't know outside their authorised view. Mitigation: HMAC-sign the cursor with a server-side secret to prevent tampering and make it opaque:
```typescript
function encodeCursor(values: object, secret: string): string {
  const payload   = JSON.stringify(values);
  const hmac      = crypto.createHmac('sha256', secret).update(payload).digest('base64url');
  return `${Buffer.from(payload).toString('base64url')}.${hmac}`;
}

function decodeCursor(cursor: string, secret: string): object {
  const [payloadB64, hmac] = cursor.split('.');
  const payload    = Buffer.from(payloadB64, 'base64url').toString('utf8');
  const expected   = crypto.createHmac('sha256', secret).update(payload).digest('base64url');

  if (!crypto.timingSafeEqual(Buffer.from(hmac, 'base64url'), Buffer.from(expected, 'base64url'))) {
    throw new UnauthorizedException('Invalid cursor');
  }
  return JSON.parse(payload);
}
```

**Q15. How do you paginate across multiple sorted columns with different directions (e.g., `status ASC, amount DESC, id DESC`)?**
A: Multi-column mixed-direction sorting is the most complex keyset scenario. The seek predicate must encode all three columns and correctly implement the compound comparison.

```sql
-- Sort: status ASC, amount DESC, id DESC
-- "Give me rows after (status='pending', amount=50000, id='loan-100')"
-- This means: rows where status > 'pending'
--             OR status = 'pending' AND amount < 50000
--             OR status = 'pending' AND amount = 50000 AND id < 'loan-100'

WHERE (
  loan.status > :status
  OR (loan.status = :status AND loan.amount < :amount)
  OR (loan.status = :status AND loan.amount = :amount AND loan.id < :id)
)
ORDER BY status ASC, amount DESC, id DESC
```

```typescript
// Build the seek predicate programmatically
if (cursor) {
  const { status, amount, id } = decodeCursor(cursor);
  qb.andWhere(`
    (loan.status > :cs)
    OR (loan.status = :cs AND loan.amount < :ca)
    OR (loan.status = :cs AND loan.amount = :ca AND loan.id < :ci)
  `, { cs: status, ca: amount, ci: id });
}
```

For four or more sort columns, this expansion becomes exponential (2^N terms). In practice:
- Limit real-world sort combinations to 2–3 columns.
- Use `(a, b, c) < (v1, v2, v3)` PostgreSQL row comparison syntax — it handles the compound logic natively and is recognised by the query planner:
  ```sql
  WHERE (status, amount, id) > ('pending', 50000, 'loan-100')
  -- For ASC direction on all columns; adjust < / > per direction
  ```
  Mixed directions require explicit expansion — PostgreSQL row comparison only supports all-same-direction comparisons.

**Q16. Scenario: "A fintech partner API requires you to expose an endpoint that allows them to pull all loan repayments from the last 30 days, and they may call it with different page parameters simultaneously from multiple workers. What pagination strategy do you use and why?"**
A: This scenario has two key requirements that drive the design:
1. Full traversal of the last 30 days of data (could be millions of rows).
2. Concurrent workers calling with different parameters simultaneously — each worker must see a consistent, non-overlapping view.

**Why offset pagination fails here:**
- Concurrent workers using `?page=1`, `?page=2`, `?page=3` with offset pagination will see inconsistent data if any repayments are created during the traversal (page drift).
- Deep offsets (page 500 at 1,000 records/page = OFFSET 499,000) will be extremely slow.
- Two workers requesting `?page=5` simultaneously may duplicate or miss rows depending on inserts between their requests.

**The correct strategy — time-window partitioning with keyset within each window:**

Give each worker a non-overlapping time range to process. The time range is fixed (immutable once assigned) so concurrent workers never conflict:

```typescript
// Partner API endpoint
@Get('repayments')
async getRepayments(
  @Query('from')   fromStr:  string,   // ISO date — worker's time window start
  @Query('to')     toStr:    string,   // ISO date — worker's time window end
  @Query('cursor') cursor?:  string,   // keyset cursor within the window
  @Query('limit')  limitStr: string = '1000',
): Promise<PartnerPaginationResponse> {
  const from  = new Date(fromStr);
  const to    = new Date(toStr);
  const limit = Math.min(parseInt(limitStr), 1000);

  // Validate: window must be within the last 30 days
  const thirtyDaysAgo = new Date(Date.now() - 30 * 24 * 60 * 60 * 1000);
  if (from < thirtyDaysAgo) throw new BadRequestException('Window starts before the 30-day limit');
  if (to > new Date())       throw new BadRequestException('Window end is in the future');
  if ((to.getTime() - from.getTime()) > 7 * 24 * 60 * 60 * 1000)
    throw new BadRequestException('Window cannot exceed 7 days');

  const qb = this.repo.createQueryBuilder('r')
    .where('r.tenantId = :tenantId', { tenantId: this.apiKey.tenantId })
    .andWhere('r.createdAt >= :from', { from })
    .andWhere('r.createdAt < :to',   { to })
    .orderBy('r.createdAt', 'ASC')
    .addOrderBy('r.id', 'ASC');

  if (cursor) {
    const { createdAt, id } = decodeCursor(cursor);
    qb.andWhere('(r.createdAt, r.id) > (:date, :id)', { date: createdAt, id });
  }

  const rows      = await qb.take(limit + 1).getMany();
  const hasMore   = rows.length > limit;
  const data      = rows.slice(0, limit);
  const lastItem  = data[data.length - 1];

  return {
    data:       data.map(this.toPartnerDto),
    nextCursor: hasMore ? encodeCursor({
      createdAt: lastItem.createdAt.toISOString(),
      id:        lastItem.id,
    }) : null,
    windowFrom: from.toISOString(),
    windowTo:   to.toISOString(),
  };
}
```

**Partner's worker distribution:**
```
Worker 1: from=2025-07-19 to=2025-07-26  (days 1-7)
Worker 2: from=2025-07-26 to=2025-08-02  (days 8-14)
Worker 3: from=2025-08-02 to=2025-08-09  (days 15-21)
Worker 4: from=2025-08-09 to=2025-08-16  (days 22-28)
```

Each worker traverses their window with keyset pagination independently. No worker conflicts with another. New repayments added during the traversal are only in the `from=now` to `to=now+period` future window, which isn't being traversed. The 30-day window's past data is stable.

**Q17. How do you implement search-within-paginated-results efficiently, and what are the index implications?**
A: Combining full-text or fuzzy search with pagination introduces specific index design challenges — B-tree indexes support range and equality efficiently but not substring search.

```typescript
// Loan search: find loans by applicant name substring + paginate

// ANTI-PATTERN: LIKE '%kumar%' bypasses B-tree indexes
const loans = await qb.where('loan.applicantName LIKE :name', { name: `%${search}%` }).getMany();
// → full sequential scan on applicant_name; no index usable

// CORRECT: pg_trgm GIN index for trigram-based similarity search
```

```sql
-- Enable trigram extension
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- Create a GIN trigram index on applicant_name
CREATE INDEX idx_loans_name_trgm ON loan_applications
  USING GIN (applicant_name gin_trgm_ops);

-- Also create a composite index for the filtered + sorted query
-- The planner may combine the trigram index with the sort index via bitmap scan
CREATE INDEX idx_loans_tenant_created ON loan_applications
  (tenant_id, created_at DESC, id DESC);
```

```typescript
// TypeORM query with trigram similarity filter
const qb = this.repo.createQueryBuilder('loan')
  .where('loan.tenantId = :tenantId', { tenantId })
  .orderBy('loan.createdAt', 'DESC')
  .addOrderBy('loan.id', 'DESC');

if (search) {
  // Trigram similarity — matches partial strings, case-insensitive
  qb.andWhere('loan.applicantName ILIKE :search', { search: `%${search}%` });
  // The GIN index makes this efficient for strings > 3 characters
  // For shorter strings, pg_trgm falls back to a sequential scan
}

// Combine with keyset cursor
if (cursor) {
  const { createdAt, id } = decodeCursor(cursor);
  qb.andWhere('(loan.createdAt, loan.id) < (:date, :id)', { date: createdAt, id });
}
```

**Important caveat:** when search is combined with pagination, the total count becomes expensive (must count all trigram-matching rows) and keyset pagination becomes tricky because rows may not be distributed evenly (many pages may have zero results for a narrow search term). For sophisticated search pagination, consider Elasticsearch / OpenSearch as the pagination backend:

```typescript
// For complex search + pagination: delegate to Elasticsearch
async searchLoans(
  tenantId: string,
  query:    string,
  from:     number,  // Elasticsearch's offset (acceptable for search results — fresh indexed)
  size:     number,
): Promise<SearchPaginatedResponse<LoanDto>> {
  const result = await this.elasticsearchService.search({
    index: 'loan_applications',
    body: {
      from,
      size,
      query: {
        bool: {
          must: [
            { term:  { tenantId } },
            { match: { applicantName: { query, fuzziness: 'AUTO' } } },
          ],
        },
      },
      sort: [{ createdAt: 'desc' }, { _id: 'desc' }],
    },
  });

  return {
    data:  result.hits.hits.map(h => h._source as LoanDto),
    total: result.hits.total.value,
    from,
    size,
  };
}
```

Elasticsearch's offset pagination (using `from`/`size`) has the same O(n) deep-offset cost as SQL OFFSET, but Elasticsearch has a hard limit of `index.max_result_window = 10000` (configurable) to prevent runaway queries. For deep search pagination, Elasticsearch also supports `search_after` — its equivalent of the keyset seek method.

**Q18. What are the HTTP caching considerations for paginated responses?**
A: Paginated responses can be cached, but the strategy differs by pagination type and data freshness requirements:

**Offset-paginated responses:**
```typescript
// Page 1 — potentially cacheable if the data is stable
res.setHeader('Cache-Control', 'private, max-age=30');  // 30-second cache per client
res.setHeader('ETag', `W/"${hash(responseBody)}"`);     // ETag for conditional requests
res.setHeader('Last-Modified', latestCreatedAt.toUTCString());

// But: any new loan created invalidates page 1 (new row appears at top)
// ETag handles this: client sends If-None-Match; server returns 304 if unchanged
```

**Keyset-paginated responses (historical windows):**
```typescript
// A cursor that encodes a past time range refers to immutable historical data
// This page's data will never change — it can be cached aggressively
if (cursor) {
  // Pages after the first can be cached longer — historical data is stable
  res.setHeader('Cache-Control', 'private, max-age=3600');  // 1 hour
} else {
  // First page — may have new records appear; shorter cache
  res.setHeader('Cache-Control', 'private, max-age=10');
}
```

**CDN caching for public paginated data:**
For public data (e.g., public loan product rates, scheme details):
```typescript
// Public data with a stable cursor can be cached at the CDN layer
res.setHeader('Cache-Control', 'public, max-age=300, stale-while-revalidate=60');
res.setHeader('Vary', 'Accept-Encoding');  // but not Authorization — it's public
```

For private financial data (loan applications, repayments): **never cache at a shared layer** (CDN, proxy) — only client-side caching with `private` directive. Financial data must be served fresh per authenticated user with proper access control; a CDN cache miss of financial data on a cache key collision could expose another user's data.

## Quick Comparison Table

| Aspect | Offset Pagination | Keyset Pagination | Time-window |
|---|---|---|---|
| Query mechanism | `LIMIT n OFFSET k` | `WHERE (col, id) < (v, id) LIMIT n` | `WHERE time BETWEEN a AND b` |
| Performance at depth | O(k) — degrades linearly | O(log n) — constant | O(log n) — constant |
| Random page access | Yes (`?page=50`) | No (must traverse from start) | Yes (specify any time range) |
| Consistency under writes | Poor — rows shift | Excellent — stable position | Excellent — past is immutable |
| Count support | Yes (but expensive) | No (use `limit+1` trick) | Count within window |
| Cursor format | Integer (page number) | Opaque encoded values | ISO date range |
| Implementation complexity | Low | Medium | Low–medium |
| UI: page numbers | Natural | Awkward | Date range picker |
| UI: infinite scroll | Poor (drift) | Excellent | Good |
| Concurrent bulk pull | Problematic (drift) | Good | Excellent (non-overlapping windows) |
| Best for | Admin UIs with page numbers; small stable datasets | Infinite scroll; high-write tables; deep traversal | Time-series; bulk export; partner APIs |

| Anti-pattern | Consequence | Fix |
|---|---|---|
| No `limit` enforcement | Single request fetches millions of rows; OOM | `@Max(100)` in DTO + service-layer cap |
| Deep OFFSET on large table | Scans millions of rows; 30-second queries | Switch to keyset; cap max page |
| Offset on high-write table | Page drift — duplicates and missing rows | Keyset pagination |
| `COUNT(*)` on every page | Expensive query per page request | Skip count after page 1; approximate count |
| Raw IDs in cursor | Enumeration attack; SQL injection risk | Encode with HMAC; validate; use parameterised queries |
| `LIKE '%term%'` without trigram index | Full table scan on every search | `pg_trgm` GIN index |
| Keyset without tiebreaker | Non-deterministic results; skipped rows | Always add `id DESC` as final sort column |
| Returning all results for export | OOM on large datasets | Stream with database cursor; keyset batching |

**Tip for the interview:** At 5 YOE, pagination questions move quickly from "what is cursor pagination?" to "implement it" and "why does offset pagination fail at scale?" Know the seek predicate cold — the `WHERE (created_at, id) < (:date, :id)` pattern and why it's O(log n) while OFFSET is O(n). The tiebreaker requirement (Q7) is the detail that separates someone who's actually debugged pagination bugs from someone who's read the docs — have a concrete example of what breaks without it. The `limit + 1` trick for `hasNextPage` (Q6) eliminates the `COUNT(*)` query entirely and interviewers consistently ask about it. For fintech interviews: the concurrent bulk partner API scenario (Q16) with time-window partitioning is exactly the kind of real-world problem that appears at companies doing B2B data sharing for NACH reconciliation, credit bureau data pulls, or regulatory reporting — knowing that time-window partitioning solves the concurrent-worker consistency problem is the senior-level answer.
