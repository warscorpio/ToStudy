# Performance: Cache Stampede Prevention — Interview Q&A (5 YOE Level)

## Section 1: The Stampede Mechanics

**Q1. What is a cache stampede, exactly — what conditions create one and what does it look like in metrics?**
A: A cache stampede (also called a thundering herd, cache miss storm, or dog-pile effect) is a failure mode where a large number of concurrent requests all miss the same cache key at the same moment, simultaneously query the origin (database, external API, or expensive computation), and compete to write the same result back to cache. The distinguishing feature is not that one request misses — it is that N requests miss the *same key* within the same short window, generating N identical origin queries.

```
The exact sequence:

  State: cache key "products:featured" has TTL=3600s.
  Load: 500 requests/second for this endpoint.
  At T=3600s: the key expires.

  T=3600.000s: Request 1  → GET "products:featured" → MISS
               Request 2  → GET "products:featured" → MISS  (arrives 2ms later)
               Request 3  → GET "products:featured" → MISS
               ...
               Request 47 → GET "products:featured" → MISS  (all arrive within 94ms)
               All 47 dispatch a DB query simultaneously.

  T=3600.094s: DB receives 47 identical queries: "SELECT * FROM products WHERE featured=true"
               DB query cost: 150ms, 200MB data scan.
               Connection pool: max 20 connections → 27 queries queue.
               Queued queries now take 150ms + queue wait.

  T=3600.244s: First DB query completes. Request 1 writes to cache. Returns response.
               Requests 2–47 also complete (redundantly). Also write to cache (47 identical writes).

  T=3600.244s: Request 48 → GET "products:featured" → HIT (cache is warm again).

  Damage window: 244ms of DB overload.
  At 500 req/s: ~122 requests experienced elevated latency.
  DB: 47 identical expensive queries = 47× the normal load for this key.

  Under higher concurrency:
  At 5,000 req/s → 470 concurrent misses in 94ms → 470 DB connections attempted
  Connection pool exhausted → ConnectionPoolExhausted exceptions
  Those exceptions propagate to users as 503 errors.
  DB may fall over entirely → all requests fail → cascade failure.
```

What metrics reveal a stampede in progress:

```
The signature in Prometheus / Datadog:

  1. Cache hit rate:    sudden vertical drop from 95% → 0% for a specific key pattern
                        Recovers after the origin query completes (~150ms).

  2. DB query rate:     sudden spike in query count matching the key's access rate
                        For "products:featured" at 500 req/s: spike of ~470 queries
                        in a 100ms window → visible as a sharp spike on the query chart.

  3. DB connection wait: p99 latency for "SELECT * FROM products WHERE featured=true"
                          spikes from 150ms (baseline) to 2000ms (queued behind 26 others).

  4. API p99 latency:   spike at the moment of cache expiry
                        p50 stays normal (new requests get the repopulated cache);
                        p99 captures the unlucky requests that hit the miss window.

  5. Error rate:        503 spike if connection pool is exhausted
                        Often the first alert that fires — ops investigates DB load next.

  6. The periodicity:   stampedes recur at multiples of the TTL.
                        If TTL=3600s: stampedes at T=3600, T=7200, T=10800, ...
                        Periodic p99 spikes with period exactly equal to the TTL
                        is a near-certain signature of a stampede.
```

**Q2. Why do the standard "solutions" that developers reach for first — catch-and-ignore, short TTLs, longer TTLs — fail or create new problems?**
A:

```
Non-solution 1 — "Catch the miss and return stale data":
  The idea: when a key expires, serve the last known value instead of going to the DB.
  Implementation: store a "stale" copy alongside the live key; on miss, serve stale.

  Why it fails:
    - Requires storing two copies per key (doubles memory).
    - "Stale" is undefined: how old is too old? The key expired because the TTL
      said it was too old — now you're serving it anyway.
    - Doesn't prevent the stampede — all 47 requests still detect a miss,
      still serve stale, AND still all try to refresh simultaneously.
      The stampede happens; users just don't see it directly.
    - In languages without atomic compare-and-swap, multiple writers race
      to update both the live and stale keys → inconsistency.

  When it's actually useful:
    Stale-while-revalidate is a valid pattern but requires a single revalidating
    worker (the lock pattern) — not "every request that sees a stale key refreshes."

Non-solution 2 — Very short TTLs (e.g., 1 second):
  The idea: if the key refreshes every second, the stampede window is small.

  Why it fails:
    - 1-second TTL = 86,400 origin queries per day per key, vs 24 for TTL=3600s.
      A key accessed 500 times/second misses once every second → 500 DB queries/day
      become 500 × 86,400 / 3600 = 12,000 per second on the DB.
    - The stampede occurs just as often (every 1 second instead of every hour);
      each stampede is smaller but you have 3,600 of them per hour instead of 1.
    - Total DB load is higher, not lower.
    - Short TTLs increase Redis churn: more SET operations, more memory fragmentation.

Non-solution 3 — Very long TTLs (e.g., 24 hours):
  The idea: less frequent expiry = less frequent stampede.

  Why it fails:
    - Data becomes stale. A product's price changes at 2pm; the cached price
      reflects yesterday's price until midnight.
    - The occasional stampede (once per 24 hours) is much larger because
      the key has been accumulating traffic for 24 hours.
    - A deployment or Redis restart resets all TTLs simultaneously →
      all keys expire at the same time → massive coordinated stampede.

Non-solution 4 — Jittered TTLs (e.g., 3600 ± random(0, 600)):
  The idea: stagger expiry times so not all keys expire simultaneously.

  Effect: prevents COORDINATED stampedes (all keys expiring at the same time
  after a Redis restart), but does NOT prevent the individual per-key stampede.
  When "products:featured" expires (at a random time, but it DOES expire),
  all concurrent requests for that key still miss simultaneously.

  Jitter is necessary but not sufficient. It solves the "mass expiry" problem,
  not the "single key high-concurrency miss" problem.

  TTL jitter = correct for preventing mass expiry storms.
  XFetch or locking = correct for preventing per-key stampedes.
  You often need both.
```

## Section 2: Locking Solutions

**Q3. How does the mutex (single-population lock) pattern work, and what are the failure modes of each implementation choice?**
A: The mutex pattern designates exactly one request as the "filler" — it acquires a lock, fetches from origin, and writes to cache. All other concurrent requests that see a miss wait for the lock to be released, then read from cache. The origin is queried exactly once per miss, regardless of concurrency.

```
The flow:

  Request 1: GET key → MISS → acquire lock → fetch from DB → SET key → release lock → return
  Request 2: GET key → MISS → try lock → WAIT (lock held by R1) → lock released
                          → GET key → HIT (populated by R1) → return
  Request 3: GET key → MISS → try lock → WAIT → ...same as R2

  DB receives: exactly 1 query.
  Requests 2–47: wait for R1, then served from cache. No DB queries from them.
```

```python
# locking.py — mutex implementations with their trade-offs

import asyncio, time, hashlib
import redis.asyncio as aioredis

redis_client: aioredis.Redis = ...

# ── IMPLEMENTATION 1: In-process asyncio.Lock (single-instance only) ──────────

_local_locks: dict[str, asyncio.Lock] = {}
_local_locks_lock = asyncio.Lock()   # protects the _local_locks dict

async def get_or_populate_local_lock(
    key:      str,
    fetch_fn,
    ttl:      int,
) -> any:
    """
    Uses a process-local asyncio.Lock.
    ONLY correct for single-instance deployments or process-local caches.
    Multiple app instances have separate lock dicts → each instance still stampedes.
    """
    raw = await redis_client.get(key)
    if raw is not None:
        return orjson.loads(raw)

    # Get or create a lock for this specific key
    async with _local_locks_lock:
        if key not in _local_locks:
            _local_locks[key] = asyncio.Lock()
        lock = _local_locks[key]

    async with lock:
        # Double-check: another coroutine may have populated while we waited
        raw = await redis_client.get(key)
        if raw is not None:
            return orjson.loads(raw)

        # We hold the lock and cache is still empty — we are the filler
        result = await fetch_fn()
        await redis_client.setex(key, ttl, orjson.dumps(result))
        return result

    # Memory leak: _local_locks grows indefinitely as new keys are accessed.
    # Fix: use a WeakValueDictionary or LRU-bounded dict for the lock store.


# ── IMPLEMENTATION 2: Redis SET NX (distributed lock — correct for multi-instance) ──

LOCK_TTL      = 5    # seconds — lock expires automatically if holder crashes
LOCK_POLL     = 0.05 # seconds — how often to re-check while waiting
LOCK_TIMEOUT  = 10   # seconds — give up waiting if lock not acquired within this

async def get_or_populate_redis_lock(
    key:       str,
    fetch_fn,
    ttl:       int,
    lock_ttl:  int   = LOCK_TTL,
    timeout:   float = LOCK_TIMEOUT,
) -> any:
    """
    Distributed mutex using Redis SET NX (set if not exists).
    Correct for multi-instance deployments.
    """
    lock_key = f"__lock__:{key}"
    # A unique value per lock acquisition — needed for safe release (see below)
    lock_value = f"{id(asyncio.current_task())}:{time.time()}"

    # Phase 1: try to read from cache first (fast path)
    raw = await redis_client.get(key)
    if raw is not None:
        return orjson.loads(raw)

    deadline = time.monotonic() + timeout

    while True:
        # Phase 2: attempt to acquire the lock
        acquired = await redis_client.set(
            lock_key,
            lock_value,
            nx=True,          # Only SET if the key does NOT exist (atomic)
            ex=lock_ttl,      # Auto-expire the lock if holder crashes
        )

        if acquired:
            # We hold the lock — we are the designated filler
            try:
                # Double-check cache (another instance may have filled it)
                raw = await redis_client.get(key)
                if raw is not None:
                    return orjson.loads(raw)

                # Still empty — fetch from origin
                result = await fetch_fn()
                await redis_client.setex(key, ttl, orjson.dumps(result))
                return result

            finally:
                # Safe release: only delete the lock if we still own it
                # Uses a Lua script for atomic check-and-delete
                await _safe_release_lock(lock_key, lock_value)

        else:
            # Lock held by another instance — wait and retry
            if time.monotonic() > deadline:
                # Timeout: lock held too long (holder may have crashed)
                # Fall back to serving from origin directly (no lock)
                # This is safer than blocking forever
                logger.warning(
                    "Lock timeout for key %s after %.1fs — fetching without lock",
                    key, timeout,
                )
                result = await fetch_fn()
                # Attempt to set cache (may race with the lock holder — acceptable)
                await redis_client.setex(key, ttl, orjson.dumps(result))
                return result

            await asyncio.sleep(LOCK_POLL)

            # Re-check cache before retrying lock acquisition
            # The lock holder may have populated and released
            raw = await redis_client.get(key)
            if raw is not None:
                return orjson.loads(raw)


# Lua script for atomic lock release:
# Check that the lock value matches before deleting — prevents releasing
# another holder's lock if our lock expired and was reacquired.
_RELEASE_SCRIPT = """
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
"""

async def _safe_release_lock(lock_key: str, lock_value: str) -> None:
    await redis_client.eval(_RELEASE_SCRIPT, 1, lock_key, lock_value)
```

**Q4. What are the specific failure modes of the Redis distributed lock — and how do you handle each?**
A:

```python
# lock_failure_modes.py

# ── FAILURE 1: Lock holder crashes mid-fetch ──────────────────────────────────
#
# The lock holder starts fetching from DB. DB query takes 8 seconds (slow).
# lock_ttl = 5 seconds. Lock expires while holder is still fetching.
# Another instance acquires the lock. Also starts fetching.
# Now two instances are fetching simultaneously → partial stampede.
# When the original holder finishes: it tries to SET the key.
# When it tries to release the lock: _safe_release_lock sees wrong value → no-op.
#
# Fix A: Set lock_ttl > expected fetch time.
#         Problem: if the holder crashes, the lock is held for lock_ttl seconds —
#         all other requests are blocked for that entire duration.
#
# Fix B: Lock extension — the holder extends the lock TTL while fetching.
#
async def get_with_lock_extension(key: str, fetch_fn, ttl: int) -> any:
    lock_key   = f"__lock__:{key}"
    lock_value = f"{id(asyncio.current_task())}:{time.time()}"

    acquired = await redis_client.set(lock_key, lock_value, nx=True, ex=5)
    if not acquired:
        # Wait and read from cache (simplified)
        await asyncio.sleep(0.1)
        return orjson.loads(await redis_client.get(key))

    # Start a background task to extend the lock every 3 seconds
    extension_task = asyncio.ensure_future(
        _extend_lock_periodically(lock_key, lock_value, interval=3, extension=5)
    )

    try:
        result = await fetch_fn()
        await redis_client.setex(key, ttl, orjson.dumps(result))
        return result
    finally:
        extension_task.cancel()
        await _safe_release_lock(lock_key, lock_value)

async def _extend_lock_periodically(
    lock_key:   str,
    lock_value: str,
    interval:   float,
    extension:  int,
) -> None:
    EXTEND_SCRIPT = """
    if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("expire", KEYS[1], ARGV[2])
    else
        return 0
    end
    """
    while True:
        await asyncio.sleep(interval)
        extended = await redis_client.eval(EXTEND_SCRIPT, 1, lock_key, lock_value, extension)
        if not extended:
            break   # Lock was released or taken by another holder — stop extending


# ── FAILURE 2: Lock waiting blocks the event loop ────────────────────────────
#
# LOCK_POLL = 0.05s (50ms). If 470 requests are all polling:
# 470 × 50ms = 23.5 seconds of event loop callbacks just for polling.
# (In asyncio: sleep yields the event loop, so this is NOT actually blocking —
# but 470 concurrent sleep tasks do add scheduling overhead.)
#
# Fix: use Redis SUBSCRIBE to be notified when the lock is released,
# instead of polling. Eliminates polling overhead entirely.
#
async def get_with_pubsub_lock(key: str, fetch_fn, ttl: int) -> any:
    lock_key      = f"__lock__:{key}"
    notify_channel = f"__lockdone__:{key}"
    lock_value    = f"{id(asyncio.current_task())}:{time.time()}"

    raw = await redis_client.get(key)
    if raw:
        return orjson.loads(raw)

    acquired = await redis_client.set(lock_key, lock_value, nx=True, ex=10)

    if acquired:
        try:
            raw = await redis_client.get(key)
            if raw:
                return orjson.loads(raw)
            result = await fetch_fn()
            await redis_client.setex(key, ttl, orjson.dumps(result))
            return result
        finally:
            await _safe_release_lock(lock_key, lock_value)
            # Notify all waiters that the cache is now populated
            await redis_client.publish(notify_channel, "done")
    else:
        # Subscribe and wait for notification
        async with redis_client.pubsub() as pubsub:
            await pubsub.subscribe(notify_channel)
            try:
                async for message in pubsub.listen():
                    if message["type"] == "message":
                        break   # notification received
                    # Timeout guard — in production, add a deadline
            finally:
                await pubsub.unsubscribe(notify_channel)

        # Lock holder has finished — read from cache
        raw = await redis_client.get(key)
        if raw:
            return orjson.loads(raw)
        # Fallback: lock holder may have failed — fetch ourselves
        return await fetch_fn()


# ── FAILURE 3: Lock does not prevent stampede across Redis instances ───────────
#
# If using Redis Cluster or multiple Redis instances, SET NX is only atomic
# within one shard. If the lock key and the cache key hash to different shards:
# two instances may both acquire the "lock" simultaneously.
#
# Fix A: use the same key slot for lock and cache key
#   Redis Cluster routes keys based on the hash slot of the key.
#   Keys with the same {hash tag} always go to the same slot.
#
#   cache_key = "products:featured"
#   lock_key  = "{products:featured}:lock"  ← {} forces same slot as cache key
#
# Fix B: use Redlock (multi-node distributed lock)
#   Acquire the lock on the majority of N Redis instances.
#   More complex; only needed if strong consistency across Redis nodes is required.

async def get_with_cluster_safe_lock(key: str, fetch_fn, ttl: int) -> any:
    # Hash tag ensures lock and cache key land on the same cluster shard
    lock_key = f"{{{key}}}:lock"
    lock_val = f"{id(asyncio.current_task())}:{time.monotonic()}"

    raw = await redis_client.get(key)
    if raw:
        return orjson.loads(raw)

    acquired = await redis_client.set(lock_key, lock_val, nx=True, ex=LOCK_TTL)
    if acquired:
        try:
            raw = await redis_client.get(key)
            if raw:
                return orjson.loads(raw)
            result = await fetch_fn()
            await redis_client.setex(key, ttl, orjson.dumps(result))
            return result
        finally:
            await _safe_release_lock(lock_key, lock_val)
    else:
        await asyncio.sleep(LOCK_POLL)
        raw = await redis_client.get(key)
        if raw:
            return orjson.loads(raw)
        return await fetch_fn()   # fallback


# ── FAILURE 4: Waiters pile up while lock is held ────────────────────────────
#
# 470 requests all miss. Request 1 gets the lock.
# Requests 2–470 pile up as sleeping tasks waiting for the lock.
# When Request 1 finishes (150ms later): 469 tasks all wake up simultaneously,
# all check the cache, all find the populated key → all return from cache.
# This is correct behavior: 469 concurrent "wakeups" are harmless because
# they all do a cache GET (fast) and return. No origin queries.
#
# The potential issue: 469 sleeping tasks consume goroutine/coroutine memory.
# At 100 bytes per sleeping coroutine × 470 = 47KB — negligible.
# At 100,000 concurrent requests × 1KB per goroutine = 100MB — significant.
#
# Fix: limit waiter queue depth. If too many are already waiting, return
# an error immediately rather than queuing more.

_waiters: dict[str, int] = {}   # key → number of waiting tasks
MAX_WAITERS = 100

async def get_with_bounded_waiters(key: str, fetch_fn, ttl: int) -> any:
    raw = await redis_client.get(key)
    if raw:
        return orjson.loads(raw)

    if _waiters.get(key, 0) >= MAX_WAITERS:
        raise CacheStampedeError(f"Too many waiters for key {key}")

    _waiters[key] = _waiters.get(key, 0) + 1
    try:
        return await get_or_populate_redis_lock(key, fetch_fn, ttl)
    finally:
        _waiters[key] = _waiters.get(key, 0) - 1
        if _waiters[key] <= 0:
            _waiters.pop(key, None)

class CacheStampedeError(Exception):
    pass
```

**Q5. What is the "stale-while-revalidate" pattern, and how does it combine with locking for zero-latency cache misses?**
A: Stale-while-revalidate serves the expired (stale) value immediately to the waiting request while a single background revalidation fetches the fresh value. Users never wait for the origin — they always get a response, just occasionally slightly stale.

```python
# stale_while_revalidate.py

import asyncio, time, orjson

# Cache entry format: stores value + metadata
# { "v": <value>, "expires_at": <unix_ts>, "fetching": <bool> }

REVALIDATION_LOCK_TTL = 30   # seconds — how long a revalidation can take

async def get_stale_while_revalidate(
    key:         str,
    fetch_fn,
    ttl:         int,
    stale_ttl:   int  = None,  # how long to serve stale (default: ttl)
) -> any:
    """
    Returns immediately:
      - Fresh value if not expired.
      - Stale value if expired, while triggering background revalidation.
      - Fetched value if no stale value exists (cold cache — unavoidable wait).

    Memory layout in Redis:
      key              → the cached value (expires at TTL)
      key:meta         → {"expires_at": ..., "fetching": false}
      key:stale        → the value, with a longer TTL (stale_ttl)
    """
    stale_ttl = stale_ttl or (ttl * 2)   # stale lives for 2× the main TTL

    # Step 1: try the primary key (fast path — not expired)
    raw = await redis_client.get(key)
    if raw is not None:
        return orjson.loads(raw)

    # Primary key expired. Try the stale key.
    stale_raw = await redis_client.get(f"{key}:stale")
    if stale_raw is not None:
        # Serve stale immediately — don't make the user wait
        # Trigger background revalidation (unless one is already in progress)
        asyncio.ensure_future(
            _revalidate_if_not_already(key, fetch_fn, ttl, stale_ttl)
        )
        return orjson.loads(stale_raw)   # ← returns immediately with stale data

    # No stale data — cold cache. Must wait for origin fetch.
    # Use mutex to prevent stampede.
    return await get_or_populate_redis_lock(
        key,
        lambda: _fetch_and_store_with_stale(key, fetch_fn, ttl, stale_ttl),
        ttl,
    )


async def _fetch_and_store_with_stale(
    key:      str,
    fetch_fn,
    ttl:      int,
    stale_ttl: int,
) -> any:
    """Fetch from origin and populate both the primary key and the stale key."""
    result = await fetch_fn()
    serialized = orjson.dumps(result)

    pipe = redis_client.pipeline()
    pipe.setex(key,               ttl,       serialized)
    pipe.setex(f"{key}:stale",   stale_ttl, serialized)
    await pipe.execute()

    return result


_revalidation_in_progress: set[str] = set()

async def _revalidate_if_not_already(
    key:      str,
    fetch_fn,
    ttl:      int,
    stale_ttl: int,
) -> None:
    """
    Background revalidation — called as a fire-and-forget task.
    Only one revalidation per key at a time.
    """
    if key in _revalidation_in_progress:
        return   # already revalidating — don't pile on

    # Use a Redis lock to coordinate across multiple application instances
    lock_key = f"__revalidate__:{key}"
    lock_val = str(asyncio.current_task())

    acquired = await redis_client.set(lock_key, lock_val, nx=True, ex=REVALIDATION_LOCK_TTL)
    if not acquired:
        return   # another instance is revalidating

    _revalidation_in_progress.add(key)
    try:
        result = await fetch_fn()
        serialized = orjson.dumps(result)
        pipe = redis_client.pipeline()
        pipe.setex(key,             ttl,       serialized)
        pipe.setex(f"{key}:stale", stale_ttl, serialized)
        await pipe.execute()
        logger.debug("Background revalidation complete: %s", key)
    except Exception as exc:
        logger.error("Background revalidation failed for %s: %s", key, exc)
        # Stale value remains — users continue to see stale data until next revalidation
    finally:
        _revalidation_in_progress.discard(key)
        await _safe_release_lock(lock_key, lock_val)
```

## Section 3: Probabilistic Early Expiration (XFetch)

**Q6. What is the XFetch algorithm — derive it from first principles, including the math behind the probability function?**
A: XFetch (from the paper "Optimal Probabilistic Cache Stampede Prevention" by Vattani, Chierichetti, and Lowenstein, 2015) is the provably optimal solution to the stampede problem under certain assumptions. Instead of expiring a key at a fixed time, each request that reads the key independently decides whether to refresh it early, with a probability that increases as the key approaches expiry.

```
The intuition:

  Problem: at T=expiry, ALL requests simultaneously see a miss → stampede.
  Goal: have EXACTLY ONE request refresh the key slightly before T=expiry.

  Naive approach — fixed early refresh window:
    "Refresh if TTL < 60 seconds."
    Problem: if 500 req/s and 60-second window → 30,000 requests in the window.
    All 30,000 requests see TTL < 60s and try to refresh. Stampede again.

  XFetch insight:
    The probability of deciding to refresh early should be LOW when the key
    is far from expiry and HIGH when close to expiry.
    The probability should scale with how long the refresh takes (delta):
    a slow fetch (2s) needs to start earlier than a fast fetch (50ms).

  The formula:
    Refresh if: current_time - beta × delta × log(random()) > expiry_time

    Where:
      current_time: now (unix timestamp)
      delta:        time taken to compute/fetch the value (seconds)
                    — the "gap" we need to avoid: start early by at least delta
      beta:         tuning parameter (default 1.0)
                    — > 1 refreshes more aggressively (earlier, more often)
                    — < 1 refreshes more lazily (later, less often)
      random():     uniform random number in (0, 1)
      expiry_time:  when the key will expire (unix timestamp)

    Equivalently: refresh if current_time + gap > expiry_time
    where gap = -beta × delta × log(random()) is exponentially distributed.

  Why exponential distribution?
    We want "exactly one" renewal event before expiry.
    The Poisson process — events occurring at a constant rate — has exponentially
    distributed inter-event times.
    By making gap exponentially distributed with rate 1/(beta×delta),
    we get a Poisson process with at most one renewal in any given window:
    with high probability exactly one request will refresh the key, before expiry,
    and no other request will also decide to refresh it.

  Walk through the probability:
    Suppose delta=0.1s, beta=1, expiry_time=T, current_time=t.
    -1.0 × 0.1 × log(random()) = exponential(mean=0.1) random variable.

    If t = T - 1.0s (1 second before expiry):
      Need: t - 1.0 × 0.1 × log(U) > T
            t + 0.1 × (-log(U)) > T
            0.1 × (-log(U)) > T - t = 1.0
            -log(U) > 10
            log(U) < -10
            U < e^(-10) ≈ 0.000045
      Probability ≈ 0.0045% — nearly never refreshes 1 second before expiry.

    If t = T - 0.1s (100ms before expiry, = delta):
      Need: 0.1 × (-log(U)) > 0.1
            -log(U) > 1
            U < e^(-1) ≈ 0.368
      Probability ≈ 36.8% — high probability of refreshing this close to expiry.

    If t = T (at expiry):
      P(refresh) = 1 — always refreshes (key is expired; must fetch).

    The exponential distribution ensures that at most one request in a given
    window makes the early-refresh decision, in expectation.
```

# xfetch.py — XFetch probabilistic early expiration

import math, random, time, orjson

# ── REDIS STORAGE FORMAT ──────────────────────────────────────────────────────
#
# XFetch needs to store two pieces of metadata alongside the value:
#   delta:       time (seconds) it took to compute the value
#   expiry_time: absolute unix timestamp when the value expires
#
# We cannot use Redis TTL for expiry_time because Redis TTL is an integer
# (seconds) and we need sub-second precision, AND we need to read it
# atomically with the value (a GET + TTL requires two round trips).
#
# Solution: store (value, delta, expiry_time) together as a single JSON blob.
# Set the Redis TTL slightly longer than expiry_time as a cleanup mechanism.

XFETCH_TTL_GRACE = 60   # seconds of extra Redis TTL after the XFetch expiry
                         # ensures Redis auto-evicts even if we never recompute

class XFetchCache:

    def __init__(self, redis_client, beta: float = 1.0):
        self.redis = redis_client
        self.beta  = beta

    async def get(self, key: str, fetch_fn, ttl: int) -> any:
        """
        XFetch get-or-compute.
        Returns fresh or early-refreshed value.
        Only ONE call will trigger a recompute at any given time (probabilistically).
        """
        raw = await self.redis.get(key)

        if raw is not None:
            entry = orjson.loads(raw)
            value       = entry["value"]
            delta       = entry["delta"]           # seconds to compute this value
            expiry_time = entry["expiry_time"]     # absolute unix timestamp

            # XFetch decision function
            now = time.time()
            # gap is drawn from Exponential(1/(beta×delta)):
            # gap = -beta × delta × log(uniform(0,1))
            u   = random.random()
            gap = -self.beta * delta * math.log(u)

            if now + gap < expiry_time:
                # Key is fresh enough — return it without recomputing
                return value
            # else: early refresh triggered — fall through to recompute

        # Either key is missing (cold) or XFetch decided to refresh early
        return await self._recompute(key, fetch_fn, ttl)

    async def _recompute(self, key: str, fetch_fn, ttl: int) -> any:
        """Fetch from origin, measure delta, store with XFetch metadata."""
        t_start = time.time()
        value   = await fetch_fn()
        delta   = time.time() - t_start   # measured compute time

        expiry_time = time.time() + ttl

        entry = {
            "value":       value,
            "delta":       delta,
            "expiry_time": expiry_time,
        }

        # Redis TTL = XFetch TTL + grace period (so Redis cleans up eventually)
        redis_ttl = ttl + XFETCH_TTL_GRACE
        await self.redis.setex(key, redis_ttl, orjson.dumps(entry))

        return value

    async def set(self, key: str, value: any, ttl: int, delta: float = 0.001) -> None:
        """Manually set a value (e.g., during cache warming)."""
        expiry_time = time.time() + ttl
        entry = {"value": value, "delta": delta, "expiry_time": expiry_time}
        await self.redis.setex(key, ttl + XFETCH_TTL_GRACE, orjson.dumps(entry))

    async def invalidate(self, key: str) -> None:
        """Explicitly invalidate a key (e.g., on data change)."""
        await self.redis.delete(key)

# beta = 1.0 (default):
#   Standard probabilistic early refresh.
#   Expected: one refresh every TTL seconds.
#
# beta > 1 (e.g., 2.0):
#   More aggressive — refreshes earlier and more frequently.
#   Use when: origin is slow (delta is large) and you want extra safety margin.
#   Trade-off: more origin queries (still just one at a time, but more often).
#
# beta < 1 (e.g., 0.5):
#   More conservative — refreshes later, closer to actual expiry.
#   Use when: origin is fast (delta is small) and you want to maximize cache efficiency.
#   Trade-off: narrower safety margin — might miss the window under high load.
#
# Practical heuristic:
#   beta = 1 for most use cases.
#   beta = 2 if delta > 1 second (slow origin — analytics, external API).
#   beta = 0.5 if delta < 10ms (fast origin — in-memory computed value).

async def tune_beta_from_delta(delta_seconds: float) -> float:
    """Suggest a beta value based on the typical fetch duration."""
    if delta_seconds > 5.0:

    elif delta_seconds > 1.0:
        return 2.0   # slow origin
    elif delta_seconds > 0.1:
        return 1.0   # moderate origin
    else:

        this.redis = redisClient;
        this.beta  = beta;

        const raw = await this.redis.get(key);

        if (raw !== null) {
            const entry       = JSON.parse(raw);

            const now = Date.now() / 1000;   // unix timestamp in seconds

                return value;   // fresh — return without recomputing
            }
            // Early refresh decision — fall through
        }

        return await this._recompute(key, fetchFn, ttlSeconds);
    }

        await this.redis.setEx(key, ttlSeconds + 60, JSON.stringify(entry));
        return value;
    }

    }

                   no deadlock risk.               handling, and crash recovery.

                   Other requests continue         Other requests are blocked
                   serving stale data.             for lock_ttl seconds.

(10,000 req/s)     each request independently      serialize on lock acquire/release.
                   decides whether to refresh.

(no existing       → mandatory wait for ALL        waits; subsequent requests
value)             requests on first miss.         are held until first completes.

─────────────────────────────────────────────────────────────────────────────────────

Decision guide:

  Use XFetch when:
    - Slight staleness (delta seconds) is acceptable.
    - Very high concurrency on hot keys (10,000+ req/s).
    - Simplicity is valued over strict freshness.
    - The fetch function is idempotent and cheap enough to occasionally run multiple times.
    - You want zero impact on user latency under any circumstances.

  Use Lock when:
    - Zero staleness required (financial data, inventory counts, permission checks).
    - The fetch function has side effects or is expensive enough that running
      it multiple times is unacceptable.
    - Strict consistency matters more than latency for the blocked waiters.
    - The working set is small enough that lock contention is manageable.

  Use both (XFetch for expiry, lock for first population):
    - XFetch works by reading the stale value while refreshing.
      If there is NO stale value (cold cache), XFetch degrades to a stampede.
      Add a lock for the cold-cache case (first population).
    - This is the most robust production pattern.

  Combined implementation:
    GET key:
      If value exists → XFetch logic (serve stale or early refresh)
      If value missing → acquire lock → fetch → set → release
                         ← only the first requester fetches; all others wait, then cache hit

```python
# combined_pattern.py — XFetch for expiry + lock for cold cache

import asyncio, math, random, time, orjson
from contextlib import asynccontextmanager

class RobustCache:
    """
    Combines XFetch and distributed locking for complete stampede prevention:
    - Cold cache (no value): distributed lock prevents stampede on first population.
    - Warm cache (value present): XFetch prevents stampede at expiry time.
    - Background revalidation: lock ensures only one revalidation runs at a time.
    """

    def __init__(self, redis_client, beta: float = 1.0, lock_ttl: int = 30):
        self.redis    = redis_client
        self.beta     = beta
        self.lock_ttl = lock_ttl

    async def get(
        self,
        key:     str,
        fetch_fn,
        ttl:     int,
        timeout: float = 10.0,   # max wait for lock
    ) -> any:
        raw = await self.redis.get(key)

        # ── HOT PATH: value exists in cache ──────────────────────────────────
        if raw is not None:
            entry = orjson.loads(raw)

            # XFetch: should we refresh early?
            now = time.time()
            u   = random.random()
            gap = -self.beta * entry["delta"] * math.log(u)

            if now + gap < entry["expiry_time"]:
                return entry["value"]   # fresh — return immediately

            # XFetch triggered early refresh — revalidate in background
            # Return the stale value NOW; revalidate asynchronously
            asyncio.ensure_future(self._background_revalidate(key, fetch_fn, ttl))
            return entry["value"]   # ← stale but instant; background refreshes it

        # ── COLD PATH: value does not exist — use lock to prevent stampede ────
        return await self._populate_with_lock(key, fetch_fn, ttl, timeout)

    async def _populate_with_lock(
        self,
        key:     str,
        fetch_fn,
        ttl:     int,
        timeout: float,
    ) -> any:
        lock_key = f"{{{key}}}:lock"   # hash tag: ensures same Redis cluster shard
        lock_val = f"{id(asyncio.current_task())}:{time.monotonic()}"
        deadline = time.monotonic() + timeout

        while True:
            # Try to acquire the lock
            acquired = await self.redis.set(lock_key, lock_val, nx=True, ex=self.lock_ttl)

            if acquired:
                try:
                    # Double-check: another instance may have populated while we waited
                    raw = await self.redis.get(key)
                    if raw is not None:
                        return orjson.loads(raw)["value"]

                    # Still empty — we are the filler
                    t_start  = time.time()
                    value    = await fetch_fn()
                    delta    = time.time() - t_start
                    entry    = {
                        "value":       value,
                        "delta":       delta,
                        "expiry_time": time.time() + ttl,
                    }
                    await self.redis.setex(
                        key,
                        ttl + XFETCH_TTL_GRACE,
                        orjson.dumps(entry),
                    )
                    return value

                finally:
                    await _safe_release_lock(lock_key, lock_val)

            else:
                # Lock held by another instance — wait, then check cache
                if time.monotonic() > deadline:
                    # Timeout: fetch without lock as last resort
                    logger.warning("Lock timeout for %s — fetching without lock", key)
                    t_start = time.time()
                    value   = await fetch_fn()
                    delta   = time.time() - t_start
                    # Try to set (may race — acceptable: last write wins)
                    entry = {
                        "value":       value,
                        "delta":       delta,
                        "expiry_time": time.time() + ttl,
                    }
                    try:
                        await self.redis.setex(key, ttl + XFETCH_TTL_GRACE, orjson.dumps(entry))
                    except Exception:
                        pass
                    return value

                await asyncio.sleep(0.05)

                # Check if the lock holder already populated the cache
                raw = await self.redis.get(key)
                if raw is not None:
                    return orjson.loads(raw)["value"]

    async def _background_revalidate(
        self,
        key:     str,
        fetch_fn,
        ttl:     int,
    ) -> None:
        """
        Revalidate in background. Uses a separate revalidation lock to ensure
        only one revalidation runs per key across all instances.
        """
        reval_key = f"{{{key}}}:reval"
        reval_val = f"{id(asyncio.current_task())}"

        acquired = await self.redis.set(
            reval_key, reval_val, nx=True, ex=self.lock_ttl
        )
        if not acquired:
            return   # another instance is already revalidating

        try:
            t_start  = time.time()
            value    = await fetch_fn()
            delta    = time.time() - t_start
            entry    = {
                "value":       value,
                "delta":       delta,
                "expiry_time": time.time() + ttl,
            }
            await self.redis.setex(key, ttl + XFETCH_TTL_GRACE, orjson.dumps(entry))
            logger.debug("Background revalidated: %s (delta=%.3fs)", key, delta)
        except Exception as exc:
            logger.error("Background revalidation error for %s: %s", key, exc)
        finally:
            await _safe_release_lock(reval_key, reval_val)

    async def invalidate(self, key: str) -> None:
        """Invalidate a key immediately (e.g., after a data write)."""
        await self.redis.delete(key)

    async def invalidate_pattern(self, pattern: str) -> int:
        """Invalidate all keys matching a pattern. Use sparingly — SCAN is O(N)."""
        count = 0
        async for key in self.redis.scan_iter(match=pattern):
            await self.redis.delete(key)
            count += 1
        return count

# redis_atomicity.py — the exact Redis commands and their atomicity properties

# ── SET NX (lock acquisition) ─────────────────────────────────────────────────
# SET key value NX EX seconds
# Atomic: sets only if key does not exist AND sets expiry in one operation.
# Without EX: if the process crashes after SET but before EXPIRE → lock never expires.
# Without NX: if two callers race, both succeed → two lock holders → not a mutex.
# The combined SET NX EX is atomic at the Redis server level — no race.

await redis.set("__lock__:my_key", lock_value, nx=True, ex=30)
# Returns True if acquired, None if not (key already exists).


# ── Lua script (lock release) ─────────────────────────────────────────────────
# Atomic check-and-delete: verify we own the lock before deleting.
# Without the Lua script:
#   GET lock_key → compare → DEL lock_key
#   Race: between GET and DEL, our lock might have expired and been re-acquired
#   by another caller. We'd then delete the OTHER caller's lock. ← catastrophic.
# With Lua script: GET and conditional DEL are atomic (Lua scripts run atomically
# in Redis — no other command executes between the GET and DEL).

RELEASE_SCRIPT = """
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
"""
# Returns 1 if released, 0 if we didn't own it (expired and re-acquired by another).


# ── GETEX (atomic get + extend TTL) ──────────────────────────────────────────
# Redis 6.2+: GETEX key EX seconds
# Atomically gets the value AND extends its TTL.
# Use for lock extension without a Lua script.
# (In older Redis, requires a Lua script or two-command sequence with a race.)

await redis.getex("__lock__:my_key", ex=30)   # get value and extend TTL atomically


# ── Pipeline (batching non-interdependent commands) ───────────────────────────
# Multiple Redis commands sent in one round trip.
# NOT atomic: each command executes independently on the server.
# Use when: multiple cache SETs that don't depend on each other's result.

pipe = redis.pipeline()
pipe.setex("product:1", 3600, data1)
pipe.setex("product:2", 3600, data2)
pipe.setex("product:3", 3600, data3)
await pipe.execute()   # 3 commands, 1 round trip, NOT atomic


# ── MULTI/EXEC (transaction — atomic batch) ───────────────────────────────────
# Commands are queued and executed atomically on the server.
# Other clients see either all or none of the changes.
# Use when: updating related keys that must be consistent.
# Limitation: cannot read intermediate values (use Lua for read-modify-write).

async with redis.pipeline(transaction=True) as pipe:
    pipe.setex("product:1234", 3600, new_data)
    pipe.delete("product:1234:stale")   # remove stale copy atomically with live set
    await pipe.execute()


# ── WATCH/MULTI/EXEC (optimistic locking) ────────────────────────────────────
# WATCH key: if key changes between WATCH and EXEC, the transaction aborts.
# Use for compare-and-swap: read a value, compute something, write back only if unchanged.
# Alternative to distributed lock for single-key read-modify-write operations.

async def increment_with_cas(key: str) -> int:
    """Increment a counter without a dedicated lock — optimistic concurrency."""
    async with redis.pipeline(transaction=True) as pipe:
        while True:
            try:
                await pipe.watch(key)
                current = await pipe.get(key)
                new_val = int(current or 0) + 1
                pipe.multi()
                pipe.set(key, new_val)
                await pipe.execute()
                return new_val
            except aioredis.WatchError:
                continue   # key changed — retry


# ── SUBSCRIBE / PUBLISH (lock release notification) ──────────────────────────
# When the lock is released, notify all waiters via Pub/Sub.
# Eliminates polling (LOCK_POLL = 50ms intervals) entirely.
# Waiters subscribe to a channel; lock holder publishes on release.
# Pattern: channel name = "__lockdone__:{cache_key}"

# Lock holder:
await redis.publish(f"__lockdone__:{key}", "done")

# Waiter:
async with redis.pubsub() as pubsub:
    await pubsub.subscribe(f"__lockdone__:{key}")
    async for message in pubsub.listen():
        if message["type"] == "message":
            break   # lock released — re-read cache
    await pubsub.unsubscribe(f"__lockdone__:{key}")
```

## Quick Reference: Stampede Prevention Mechanism Comparison

| Mechanism | Prevents Stampede? | Latency Impact | Staleness | Complexity | Failure Mode |
|---|---|---|---|---|---|
| No protection | ✗ | Baseline | None | None | Full stampede at every expiry |
| Short TTL | ✗ | Higher DB load | Less | None | Frequent small stampedes |
| TTL jitter | Partial (mass expiry only) | None | None | Low | Per-key stampede still occurs |
| Local `asyncio.Lock` | ✓ (single instance) | Waiters block for fetch duration | None | Low | Doesn't work across multiple pods |
| Redis `SET NX` lock | ✓ (multi-instance) | Waiters block for fetch duration | None | Medium | Lock holder crash; Redis failure |
| XFetch | ✓ (warm cache) | Zero (serves stale) | `delta` seconds | Low | Cold cache still stampedes |
| Stale-while-revalidate | ✓ (warm cache) | Zero (serves stale) | Up to `stale_ttl` | Medium | Cold cache still stampedes |
| XFetch + Lock | ✓ (all cases) | Zero when warm; blocked when cold | `delta` when warm | Medium-High | Lock holder crash (mitigated by TTL) |

## Quick Reference: Redis Command Atomicity for Stampede Prevention

| Operation | Command | Atomic? | Notes |
|---|---|---|---|
| Lock acquire | `SET key val NX EX ttl` | ✓ Yes | Must use combined form; separate SET + EXPIRE is not atomic |
| Lock release | Lua script (GET + conditional DEL) | ✓ Yes | Simple `DEL` without checking ownership is unsafe |
| Lock extend | `GETEX key EX ttl` (Redis 6.2+) | ✓ Yes | Older Redis: requires Lua |
| Read + reset TTL | `GETEX key EX ttl` | ✓ Yes | Useful for sliding-window TTLs |
| Batch cache SET | `PIPELINE` | ✗ No (batched, not atomic) | Use MULTI/EXEC if atomicity needed |
| Atomic batch SET | `MULTI` / `EXEC` | ✓ Yes | All commands in transaction execute atomically |
| Compare-and-swap | `WATCH` + `MULTI` / `EXEC` | ✓ Yes (optimistic) | Retries on conflict |
| Lock release notify | `PUBLISH channel msg` | ✓ Yes | Eliminates polling; requires SUBSCRIBE on waiters |

**Tip for the interview:** At 5 YOE, the cache stampede question is almost never "what is a stampede?" — it's a systems design debugging scenario: "every hour on the hour, your p99 latency spikes for 200ms and your DB connection pool shows a brief burst — what's happening?" The periodic signature (spikes at multiples of the TTL) is the tell, and knowing it is the depth signal that separates "heard of stampedes" from "has debugged one in production." For the lock implementation, know the two critical atomicity points: `SET NX EX` must be a single command (separate SET + EXPIRE has a crash window between them), and lock release must use a Lua script (a simple DEL without checking ownership can release another holder's lock if yours expired). The XFetch probability table is worth internalizing — the probability depends only on (time_remaining / delta), not on absolute times, which is why XFetch naturally adapts to both fast and slow origins. The combination of XFetch for warm-cache expiry and mutex for cold-cache population (Q9) is the production-grade answer — XFetch alone stampedes on a cold cache because there's no stale value to serve while one request fetches.
