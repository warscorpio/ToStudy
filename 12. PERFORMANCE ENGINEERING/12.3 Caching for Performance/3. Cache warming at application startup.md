## Section 1: The Cold Start Problem

**Q1. What is a cold cache, and why does it matter for production systems?**
A: A cache is "cold" when it contains no data — every request misses and falls through to the origin (database, external API, or computed result). A cache is "warm" when it contains the working set of data that requests actually need, so the majority of reads are served from cache without touching the origin. The transition from cold to warm is the cold start problem.

```
Cold cache behavior — every request is a cache miss:

  T=0s:   Application starts. Cache is empty.
  T=0s:   Request 1 arrives: GET /api/products/featured
           Cache miss → DB query (200ms) → cache SET → response (200ms)
  T=0s:   Request 2 arrives: GET /api/products/featured (same key)
           Cache miss → DB query (200ms) → response (200ms)
           ← 50 concurrent requests for the same key in the first 200ms:
             50 parallel DB queries fire simultaneously → stampede

  T=30m:  Cache is warm. Hit rate: 95%.
  T=30m:  Request N: GET /api/products/featured
           Cache hit → response (2ms)
           ← 50 concurrent requests: all served from cache → zero DB load

The problem is the 30-minute gap. During that window:
  - DB receives the full traffic load (as if the cache doesn't exist).
  - p99 latency is 100–200ms instead of 2ms.
  - DB connection pool is exhausted under high concurrency.
  - If the DB is already near capacity, this can cause a cascade failure.
```

When cold starts are dangerous:

```
Scenario 1 — Planned deploy:
  Rolling deploy of 10 pods. Each pod restarts one at a time.
  Each restarted pod has a cold cache for ~30 minutes.
  At any given time during a 10-pod rolling deploy:
  1–2 pods are cold → 10–20% of traffic hits the DB for the cold pod's share.
  Manageable, but visible in latency percentiles.

Scenario 2 — Full fleet restart (version bump, config change):
  All 10 pods restart simultaneously.
  100% of traffic hits DB for 30 minutes.
  If normal DB load is 20% (80% served from cache):
  DB suddenly absorbs 5× its normal load → likely overload.

Scenario 3 — Autoscaling event:
  Traffic spike at 9am. HPA scales from 5 pods to 20 pods.
  15 new pods start cold. Each has an empty cache.
  These 15 pods receive traffic immediately from the load balancer.
  15/20 = 75% of traffic hits the DB until caches warm.
  The autoscaling event that was supposed to reduce load temporarily INCREASES it.

Scenario 4 — Redis restart or eviction:
  Redis is restarted (upgrade, failover) or max memory policy evicts keys.
  All applications suddenly have cache misses for keys that were warm.
  Same effect as all pods restarting simultaneously.
  Mitigation: pre-warming after Redis recovery, not just after app start.
```

**Q2. What is the cache stampede (thundering herd) problem, and how does it amplify the cold start?**
A: A cache stampede occurs when many concurrent requests all miss the same cache key at the same time, all simultaneously query the origin, and all try to populate the cache with the same value. It is the specific failure mode that makes cold starts dangerous beyond simple latency degradation.

```
The stampede mechanism:

  Normal warm cache:
    Request 1: cache HIT for "featured_products" → served in 2ms
    Request 2: cache HIT → 2ms
    ...1000 requests: all cache hits → DB receives 0 queries

  Cold cache + 1000 concurrent requests for "featured_products":
    Request 1:   cache MISS → fires DB query → DB processing...
    Request 2:   cache MISS → fires DB query → DB processing...
    Request 3:   cache MISS → fires DB query → DB processing...
    ...
    Request 1000: cache MISS → fires DB query → DB processing...
    → 1000 simultaneous DB queries for identical data
    → DB connection pool: max_connections=50. 950 queries wait in queue.
    → Queue timeout: 950 requests return errors to users.
    → The 50 queries that did connect: DB is under 50× normal load for this query.
    → Query that normally takes 50ms now takes 2500ms (50× slower under load).

  After the stampede:
    Request 1001: cache HIT → 2ms (cache is now warm)
    → The stampede is self-resolving, but the damage is done:
      900+ requests failed or timed out. DB may have fallen over.

  The compounding effect:
    If the DB falls over → cache is never populated → cache stays cold
    → next batch of requests also stampedes → DB falls over again → loop
    This is a death spiral: cold cache → DB overload → cold cache.
```

Standard mitigations for stampede (prerequisite to understanding cache warming):

```python
# Mitigation 1 — Mutex/lock: only one request populates the cache

import asyncio

_cache_locks: dict[str, asyncio.Lock] = {}

async def get_with_lock(key: str, fetch_fn, ttl: int) -> any:
    """
    Only one coroutine fetches from origin for a given key.
    Others wait for the lock, then read from cache.
    """
    value = await redis.get(key)
    if value is not None:
        return orjson.loads(value)

    # Cache miss — acquire a per-key lock
    if key not in _cache_locks:
        _cache_locks[key] = asyncio.Lock()

    async with _cache_locks[key]:
        # Double-check after acquiring lock (another coroutine may have populated)
        value = await redis.get(key)
        if value is not None:
            return orjson.loads(value)

        # We hold the lock — fetch from origin and populate cache
        result = await fetch_fn()
        await redis.setex(key, ttl, orjson.dumps(result))
        return result


# Mitigation 2 — Probabilistic early expiry (XFetch algorithm):
# Refresh the cache slightly before it expires, with probability proportional
# to how close to expiry it is. Avoids the hard expiry boundary entirely.

import math, time, random

async def get_with_xfetch(key: str, fetch_fn, ttl: int, beta: float = 1.0) -> any:
    """
    XFetch: probabilistically refresh before expiry.
    beta > 1: refresh earlier (more conservative); beta < 1: refresh later.
    """
    # Redis stores value + metadata: [value, delta, expiry_time]
    raw = await redis.get(f"xfetch:{key}")
    if raw:
        data = orjson.loads(raw)
        value       = data["value"]
        delta       = data["delta"]          # time taken to compute the value
        expiry_time = data["expiry_time"]   # absolute expiry timestamp

        # Probabilistic check: should we refresh now?
        # Probability increases as we approach expiry
        now = time.time()
        if now - beta * delta * math.log(random.random()) < expiry_time:
            return value   # cache is fresh enough — return it
        # Otherwise: fall through to refresh (below)

    # Cache miss or probabilistic refresh — compute and store
    start  = time.monotonic()
    result = await fetch_fn()
    delta  = time.monotonic() - start   # how long the fetch took

    payload = {
        "value":       result,
        "delta":       delta,
        "expiry_time": time.time() + ttl,
    }
    await redis.setex(f"xfetch:{key}", ttl, orjson.dumps(payload))
    return result
```

## Section 2: Cache Warming Strategies

**Q3. What is cache warming, and what are the four main strategies — eager, lazy with lock, background, and predictive?**
A: Cache warming is the deliberate pre-population of a cache before it receives production traffic. It converts a cold cache into a warm cache as quickly as possible, reducing or eliminating the cold start window.

```
Strategy 1 — Eager warming (synchronous, at startup):
  Load cache data during application initialization, before accepting any traffic.
  The application does not signal readiness (readiness probe returns unhealthy)
  until the cache is sufficiently warm.

  Pros: zero cold-start window for users; simplest to reason about.
  Cons: increases startup time; blocks deployment until warm.
  Use when: cache is small enough to warm in < 30 seconds;
             or when a cold cache would cause a cascade failure.

Strategy 2 — Lazy warming with stampede protection:
  Don't pre-populate; let traffic populate the cache naturally.
  Use mutex/lock to prevent stampede on the first miss for each key.
  Only one request fetches from origin; all others wait for it.

  Pros: no startup overhead; cache contains exactly what traffic requests.
  Cons: first request for each key is slow (mutex wait + origin fetch).
  Use when: the working set is large and unpredictable; startup time matters more
             than first-request latency; traffic pattern determines what to cache.

Strategy 3 — Background warming (async, post-startup):
  Application starts and accepts traffic immediately.
  A background coroutine/job populates the cache concurrently with serving requests.
  Traffic that hits a miss during warming is served from origin (possibly with mutex).

  Pros: no increase in startup time; cache warms while serving traffic.
  Cons: traffic during the warming window is slower; requires stampede protection.
  Use when: startup time is constrained (Kubernetes probes will restart slow pods);
             the working set is moderate; some cold-start degradation is acceptable.

Strategy 4 — Predictive warming (data-driven):
  Analyze access logs or usage patterns to predict what will be requested.
  Pre-populate exactly those keys before any traffic arrives.
  Combines the zero-cold-start benefit of eager warming with selectivity
  (only warm what will actually be requested, not everything).

  Pros: warmest cache with smallest startup overhead; precise.
  Cons: requires historical data and a prediction pipeline; more complex.
  Use when: access patterns are predictable (time-of-day patterns, known hot keys);
             the working set is too large to warm exhaustively but has a hot subset.
```

**Q4. How do you implement eager cache warming — the complete pattern for startup synchronization with readiness probes?**
A:

```python
# eager_warming.py — synchronous cache warming before accepting traffic

import asyncio, time, logging
from dataclasses import dataclass
from typing import Callable, Awaitable

logger = logging.getLogger(__name__)

@dataclass
class WarmupTask:
    name:        str
    fetch:       Callable[[], Awaitable[any]]   # coroutine that fetches the data
    cache_key:   str
    ttl:         int                             # seconds
    required:    bool = True   # if True, a failure aborts startup
    timeout:     float = 10.0  # seconds before this task is considered failed


class CacheWarmer:
    """
    Warms the cache during application startup.
    Integrates with health/readiness probes to block traffic until warm.
    """

    def __init__(self, redis_client, pool_size: int = 10):
        self._redis      = redis_client
        self._pool_size  = pool_size     # concurrent warming tasks
        self._is_warm    = False
        self._warm_stats: dict = {}

    @property
    def is_ready(self) -> bool:
        """Used by readiness probe — returns False until warming is complete."""
        return self._is_warm

    async def warm(self, tasks: list[WarmupTask]) -> dict:
        """
        Execute all warming tasks with bounded concurrency.
        Returns a summary of successes and failures.
        """
        start   = time.monotonic()
        results = {"success": 0, "failed": 0, "skipped": 0, "errors": []}

        # Run tasks in parallel with bounded concurrency
        semaphore = asyncio.Semaphore(self._pool_size)

        async def run_task(task: WarmupTask) -> None:
            async with semaphore:
                task_start = time.monotonic()
                try:
                    # Check if key already exists in cache (warm from previous instance)
                    existing = await self._redis.exists(task.cache_key)
                    if existing:
                        logger.debug("Cache key already warm: %s", task.cache_key)
                        results["skipped"] += 1
                        return

                    # Fetch from origin with timeout
                    data = await asyncio.wait_for(task.fetch(), timeout=task.timeout)

                    # Serialize and store
                    await self._redis.setex(
                        task.cache_key,
                        task.ttl,
                        orjson.dumps(data),
                    )

                    elapsed = (time.monotonic() - task_start) * 1000
                    logger.info("Warmed %s in %.1fms", task.name, elapsed)
                    results["success"] += 1

                except asyncio.TimeoutError:
                    msg = f"Timeout warming {task.name} after {task.timeout}s"
                    logger.error(msg)
                    results["failed"] += 1
                    results["errors"].append(msg)
                    if task.required:
                        raise RuntimeError(msg)

                except Exception as exc:
                    msg = f"Error warming {task.name}: {exc}"
                    logger.error(msg)
                    results["failed"] += 1
                    results["errors"].append(msg)
                    if task.required:
                        raise RuntimeError(msg)

        # Gather all tasks — failures in required tasks will propagate
        await asyncio.gather(*[run_task(t) for t in tasks])

        elapsed_total = (time.monotonic() - start) * 1000
        results["elapsed_ms"] = round(elapsed_total, 1)

        self._is_warm    = True
        self._warm_stats = results
        logger.info(
            "Cache warming complete in %.1fms: %d warmed, %d skipped, %d failed",
            elapsed_total, results["success"], results["skipped"], results["failed"],
        )
        return results


# ── DEFINING WARMUP TASKS ─────────────────────────────────────────────────────

async def make_warmup_tasks(db_pool, config: dict) -> list[WarmupTask]:
    """
    Define what to warm and how.
    Tasks are organized by priority: required first, optional after.
    """
    return [

        # ── REQUIRED: application cannot start correctly without these ────────

        WarmupTask(

            cache_key = "products:featured",

        WarmupTask(

# ── WARMUP DATA FETCHERS ───────────────────────────────────────────────────────

    async with db_pool.acquire() as conn:
        rows = await conn.fetch("""
            SELECT id, name, price, image_url, category_id, stock_count
            FROM products
            WHERE featured = true AND active = true
            ORDER BY display_order ASC
            LIMIT 50
        """)
    return [dict(r) for r in rows]

    async with db_pool.acquire() as conn:
        rows = await conn.fetch("SELECT key, value FROM site_config WHERE active = true")
    return {r["key"]: r["value"] for r in rows}

async def _fetch_active_promotions(db_pool) -> list[dict]:
    async with db_pool.acquire() as conn:
        rows = await conn.fetch("""
            SELECT id, code, discount_type, discount_value, min_order_value,
                   valid_until, applicable_categories
            FROM promotions
            WHERE active = true AND valid_until > NOW()
            ORDER BY priority DESC
        """)
    return [dict(r) for r in rows]

async def _fetch_all_categories(db_pool) -> list[dict]:
    async with db_pool.acquire() as conn:
        rows = await conn.fetch("""
            SELECT id, name, slug, parent_id, display_order, image_url
            FROM categories
            WHERE active = true
            ORDER BY parent_id NULLS FIRST, display_order ASC
        """)
    return [dict(r) for r in rows]

async def _fetch_top_sellers(db_pool, days: int = 30) -> list[dict]:
    async with db_pool.acquire() as conn:
        rows = await conn.fetch("""
            SELECT
                p.id, p.name, p.price,
                SUM(oi.quantity) AS units_sold,
                SUM(oi.quantity * oi.unit_price) AS revenue
            FROM order_items oi
            JOIN products p ON p.id = oi.product_id
            JOIN orders o ON o.id = oi.order_id
            WHERE o.created_at >= NOW() - ($1 || ' days')::INTERVAL
            AND o.status = 'completed'
            GROUP BY p.id, p.name, p.price
            ORDER BY units_sold DESC
            LIMIT 100
        """, str(days))
    return [dict(r) for r in rows]

from fastapi import FastAPI
from contextlib import asynccontextmanager

warmer = CacheWarmer(redis_client=redis, pool_size=10)

@asynccontextmanager
async def lifespan(app: FastAPI):
    """FastAPI lifespan: runs before and after serving requests."""
    # ── STARTUP ──────────────────────────────────────────────────────────────
    logger.info("Starting up: initializing database pool...")
    db_pool = await asyncpg.create_pool(DATABASE_URL, min_size=5, max_size=20)

    logger.info("Starting up: warming cache...")
    tasks = await make_warmup_tasks(db_pool, config={})
    try:
        stats = await warmer.warm(tasks)
        logger.info("Startup complete: %s", stats)
    except RuntimeError as exc:
        # Required task failed — abort startup
        logger.critical("Cache warming failed, aborting startup: %s", exc)
        raise SystemExit(1)

    yield   # ← application serves requests here

    # ── SHUTDOWN ─────────────────────────────────────────────────────────────
    await db_pool.close()

app = FastAPI(lifespan=lifespan)


# ── READINESS PROBE ────────────────────────────────────────────────────────────

@app.get("/health/ready")
async def readiness():
    """
    Kubernetes readiness probe — returns 200 only when cache is warm.
    Kubernetes will not send traffic to this pod until this returns 200.
    """
    if not warmer.is_ready:
        return JSONResponse(
            status_code=503,
            content={"status": "warming", "message": "Cache is not yet warm"},
        )

    # Also check that Redis and DB are reachable
    try:
        await redis.ping()
    except Exception:
        return JSONResponse(
            status_code=503,
            content={"status": "unhealthy", "message": "Redis unreachable"},
        )

    return {"status": "ready", "cache": "warm"}

@app.get("/health/live")
async def liveness():
    """
    Kubernetes liveness probe — always returns 200 if the process is running.
    Does NOT check cache warmth — a warming pod should not be killed.
    """
    return {"status": "alive"}
```

**Q5. How do you implement background warming — starting to serve traffic immediately while populating the cache concurrently?**
A:

```python
# background_warming.py — warm cache while serving traffic

import asyncio, time, logging
from enum import Enum

logger = logging.getLogger(__name__)

class WarmingState(Enum):
    NOT_STARTED  = "not_started"
    IN_PROGRESS  = "in_progress"
    COMPLETE     = "complete"
    FAILED       = "failed"

class BackgroundWarmer:
    """
    Starts the application immediately; warms the cache in the background.
    Tracks per-key warming state so the application can degrade gracefully.
    """

    def __init__(self, redis_client):
        self._redis  = redis_client
        self._state  = WarmingState.NOT_STARTED
        self._warmed_keys: set[str]    = set()
        self._pending_keys: set[str]   = set()
        self._progress: dict[str, any] = {}
        self._task: asyncio.Task | None = None

    def start(self, tasks: list[WarmupTask]) -> None:
        """Start background warming. Returns immediately."""
        self._state       = WarmingState.IN_PROGRESS
        self._pending_keys = {t.cache_key for t in tasks}
        self._task        = asyncio.ensure_future(self._run(tasks))

    def is_key_warm(self, key: str) -> bool:
        return key in self._warmed_keys

    @property
    def warming_complete(self) -> bool:
        return self._state == WarmingState.COMPLETE

    @property
    def warming_progress(self) -> dict:
        total   = len(self._pending_keys) + len(self._warmed_keys)
        warmed  = len(self._warmed_keys)
        return {
            "state":        self._state.value,
            "warmed":       warmed,
            "total":        total,
            "percent":      round(warmed / total * 100, 1) if total else 0,
            "pending_keys": list(self._pending_keys)[:10],
        }

    async def _run(self, tasks: list[WarmupTask]) -> None:
        semaphore = asyncio.Semaphore(5)

        async def warm_one(task: WarmupTask):
            async with semaphore:
                try:
                    # Don't re-warm keys that are already cached
                    if await self._redis.exists(task.cache_key):
                        self._warmed_keys.add(task.cache_key)
                        self._pending_keys.discard(task.cache_key)
                        return

                    data = await asyncio.wait_for(task.fetch(), timeout=task.timeout)
                    await self._redis.setex(task.cache_key, task.ttl, orjson.dumps(data))
                    self._warmed_keys.add(task.cache_key)
                    self._pending_keys.discard(task.cache_key)
                    logger.debug("Background warmed: %s", task.name)

                except Exception as exc:
                    logger.warning("Background warming failed for %s: %s", task.name, exc)
                    self._pending_keys.discard(task.cache_key)

        await asyncio.gather(*[warm_one(t) for t in tasks])
        self._state = WarmingState.COMPLETE
        logger.info("Background cache warming complete. %d keys warmed.", len(self._warmed_keys))


# ── GRACEFUL DEGRADATION DURING WARMING ──────────────────────────────────────
# While the background warmer is running, some cache misses will occur.
# The application should handle these gracefully — not just fetch from DB blindly.

background_warmer = BackgroundWarmer(redis_client=redis)

async def get_featured_products() -> list[dict]:
    """
    Get featured products with graceful degradation during cache warming.
    """
    cache_key = "products:featured"
    raw = await redis.get(cache_key)

    if raw is not None:
        return orjson.loads(raw)

    # Cache miss during warming or after expiry
    if not background_warmer.warming_complete:
        # Still warming — log the miss so we can track warming progress
        logger.info("Cache miss during warming for key: %s", cache_key)

        # If it's a key the background warmer should populate soon:
        # Option A — serve from DB (normal fallback, may cause some load)
        # Option B — return a degraded response (if acceptable)
        # Option C — wait briefly for the background warmer (if key is in progress)

        if not background_warmer.is_key_warm(cache_key):
            # Key not yet warmed — serve from DB with stampede protection
            return await get_with_lock(cache_key, _fetch_featured_products, ttl=3600)

    # Warming complete but cache miss — key expired or was evicted
    return await get_with_lock(cache_key, _fetch_featured_products, ttl=3600)
```

## Section 3: Warming Strategies for Specific Data Patterns

**Q6. How do you warm a large keyspace — when you have thousands of individual cache keys, not just a few shared ones?**
A: The strategies above warm a small set of shared keys. Many applications have per-entity caches: one key per product, per user, per organization. Warming thousands of keys requires a different approach — prioritization, pagination, and rate limiting.

```python
# large_keyspace_warming.py — warming thousands of cache keys

import asyncio, time
from typing import AsyncIterator

# ── APPROACH 1: Warm the hot subset only ──────────────────────────────────────
# Principle: 80% of traffic hits 20% of keys (Pareto distribution).
# Warm the top N most-accessed keys; let the long tail warm lazily.

async def warm_top_products(db_pool, redis_client, top_n: int = 1000) -> int:
    """
    Warm the N most-viewed products from the last 24 hours.
    These are the keys that will be requested immediately on startup.
    Returns the number of keys warmed.
    """
    # Identify hot keys from access logs or analytics
    async with db_pool.acquire() as conn:
        hot_product_ids = await conn.fetch("""
            SELECT product_id, COUNT(*) AS view_count
            FROM product_views
            WHERE viewed_at >= NOW() - INTERVAL '24 hours'
            GROUP BY product_id
            ORDER BY view_count DESC
            LIMIT $1
        """, top_n)

    if not hot_product_ids:
        return 0

    # Fetch and cache in batches of 50 — avoid hammering the DB
    ids     = [r["product_id"] for r in hot_product_ids]
    warmed  = 0
    BATCH   = 50

    for i in range(0, len(ids), BATCH):
        batch_ids = ids[i:i + BATCH]

        # Fetch entire batch in one query
        async with db_pool.acquire() as conn:
            products = await conn.fetch("""
                SELECT id, name, price, description, image_url,
                       category_id, stock_count, average_rating
                FROM products
                WHERE id = ANY($1) AND active = true
            """, batch_ids)

        # Cache each product individually
        pipe = redis_client.pipeline()
        for product in products:
            key  = f"product:{product['id']}"
            data = orjson.dumps(dict(product))
            pipe.setex(key, 3600, data)   # 1-hour TTL
        await pipe.execute()
        warmed += len(products)

        # Rate limit: don't flood the DB or Redis
        await asyncio.sleep(0.05)   # 50ms between batches → 20 batches/sec max

    logger.info("Warmed %d product keys (top %d by views)", warmed, top_n)
    return warmed


# ── APPROACH 2: Paginated full-table warm (when you must warm everything) ──────

async def warm_all_active_products(
    db_pool,
    redis_client,
    page_size:  int   = 500,
    rate_limit: float = 0.1,    # seconds between pages
) -> AsyncIterator[int]:
    """
    Generator that warms ALL active products page by page.
    Yields the number of keys warmed per page.
    Caller controls how many pages to run (can be cancelled at any time).
    """
    offset = 0

    while True:
        async with db_pool.acquire() as conn:
            products = await conn.fetch("""
                SELECT id, name, price, description, image_url, category_id, stock_count
                FROM products
                WHERE active = true
                ORDER BY id
                LIMIT $1 OFFSET $2
            """, page_size, offset)

        if not products:
            break   # no more records

        # Cache this page
        pipe = redis_client.pipeline()
        for product in products:
            pipe.setex(f"product:{product['id']}", 3600, orjson.dumps(dict(product)))
        await pipe.execute()

        yield len(products)
        offset += len(products)

        # Rate limit between pages — don't starve OLTP queries
        await asyncio.sleep(rate_limit)

# Usage:
async def run_full_warm():
    total = 0
    async for page_count in warm_all_active_products(db_pool, redis_client):
        total += page_count
        logger.info("Warming progress: %d products cached", total)
    logger.info("Full product cache warm complete: %d total", total)


# ── APPROACH 3: Redis SCAN-based warming (warm from existing data) ────────────
# When restarting the app but Redis still has data from the previous instance,
# avoid re-fetching from DB — the cache is already warm.
# But if TTLs are short, keys may have expired. Check which are missing.

async def warm_missing_keys(db_pool, redis_client, key_pattern: str = "product:*"):
    """
    Scan Redis for keys matching the pattern. Find which product IDs are MISSING.
    Fetch only the missing ones from DB.
    """
    existing_ids: set[str] = set()

    # SCAN is non-blocking (unlike KEYS) — iterates incrementally
    async for key in redis_client.scan_iter(match=key_pattern, count=100):
        # key = b"product:1234"
        product_id = key.decode().split(":")[1]
        existing_ids.add(product_id)

    # Find all active product IDs from DB
    async with db_pool.acquire() as conn:
        all_ids = await conn.fetch("SELECT id FROM products WHERE active = true")
    all_id_set = {str(r["id"]) for r in all_ids}

    # Missing = in DB but not in cache
    missing_ids = all_id_set - existing_ids
    logger.info("%d products missing from cache (of %d total)", len(missing_ids), len(all_id_set))

    if not missing_ids:
        return 0

    # Warm only the missing ones
    missing_list = list(missing_ids)
    BATCH = 100
    warmed = 0

    for i in range(0, len(missing_list), BATCH):
        batch = missing_list[i:i + BATCH]
        async with db_pool.acquire() as conn:
            rows = await conn.fetch(
                "SELECT id, name, price, image_url FROM products WHERE id = ANY($1)",
                [int(id_) for id_ in batch]
            )
        pipe = redis_client.pipeline()
        for row in rows:
            pipe.setex(f"product:{row['id']}", 3600, orjson.dumps(dict(row)))
        await pipe.execute()
        warmed += len(rows)
        await asyncio.sleep(0.05)

    return warmed
```

```python
# predictive_warming.py — data-driven cache warming

import asyncio
from datetime import datetime, timedelta

# ── PATTERN 1: Time-of-day prediction ────────────────────────────────────────
# Many applications have predictable peak hours.
# Pre-warm before the peak, not during it.

class ScheduledWarmer:
    """
    Warms caches on a schedule, anticipating usage spikes.
    """

    def __init__(self, db_pool, redis_client):
        self.db    = db_pool
        self.redis = redis_client

    async def run_scheduled_warming(self) -> None:
        """Runs continuously, warming ahead of predicted peaks."""
        while True:
            now  = datetime.utcnow()
            hour = now.hour

            # Pre-warm 30 minutes before business hours start (9am UTC)
            if hour == 8 and now.minute == 30:
                logger.info("Pre-warming for morning traffic peak")
                await self.warm_for_business_hours()

            # Pre-warm before evening peak (typically 7–9pm local time)
            elif hour == 18 and now.minute == 30:
                logger.info("Pre-warming for evening traffic peak")
                await self.warm_for_evening_peak()

            # Extend TTLs of frequently-accessed keys during peak hours
            elif 9 <= hour <= 21:
                await self.extend_hot_key_ttls()

            # During off-peak hours: warm the next day's predicted hot keys
            elif hour == 3:
                logger.info("Off-peak warming: pre-computing tomorrow's hot keys")
                await self.warm_predicted_next_day_keys()

            await asyncio.sleep(60)   # check every minute

    async def warm_for_business_hours(self) -> None:
        """Warm data that is typically accessed during business hours."""
        tasks = [
            self._warm_key("config:site",          self._fetch_site_config,       86400),
            self._warm_key("promotions:active",    self._fetch_active_promotions, 1800),
            self._warm_key("products:featured",    self._fetch_featured_products, 3600),
            self._warm_key("categories:all",       self._fetch_all_categories,    7200),
            self._warm_key("shipping:rates",       self._fetch_shipping_rates,    3600),
        ]
        await asyncio.gather(*tasks)

    async def extend_hot_key_ttls(self) -> None:
        """
        During peak hours: extend TTLs of frequently-accessed keys
        to prevent them from expiring mid-peak.
        """
        hot_keys = [
            ("products:featured",  3600),
            ("promotions:active",  1800),
            ("config:site",       86400),
        ]
        for key, ttl in hot_keys:
            current_ttl = await self.redis.ttl(key)
            # If key expires within 10 minutes, refresh it now
            if 0 < current_ttl < 600:
                logger.info("Extending TTL for hot key: %s (current TTL: %ds)", key, current_ttl)
                value = await self.redis.get(key)
                if value:
                    await self.redis.expire(key, ttl)

    async def warm_predicted_next_day_keys(self) -> None:
        """
        At 3am: compute and cache data that will be hot tomorrow.
        Run expensive queries now when load is low.
        """
        # What were the most-viewed products yesterday? They'll likely be hot today too.
        async with self.db.acquire() as conn:
            hot_ids = await conn.fetch("""
                SELECT product_id
                FROM product_views
                WHERE viewed_at >= NOW() - INTERVAL '7 days'
                GROUP BY product_id
                ORDER BY COUNT(*) DESC
                LIMIT 500
            """)

        ids = [r["product_id"] for r in hot_ids]
        if not ids:
            return

        # Pre-compute and cache with a long TTL (expires tomorrow evening)
        async with self.db.acquire() as conn:
            products = await conn.fetch(
                "SELECT * FROM products WHERE id = ANY($1) AND active = true", ids
            )

        pipe = self.redis.pipeline()
        for p in products:
            pipe.setex(f"product:{p['id']}", 86400, orjson.dumps(dict(p)))
        await pipe.execute()

        logger.info("Pre-warmed %d predicted hot products for tomorrow", len(products))

    async def _warm_key(self, key: str, fetch_fn, ttl: int) -> None:
        try:
            data = await fetch_fn()
            await self.redis.setex(key, ttl, orjson.dumps(data))
        except Exception as exc:
            logger.error("Scheduled warm failed for %s: %s", key, exc)


# ── PATTERN 2: ML-based prediction (advanced) ─────────────────────────────────
# Use a simple frequency model to predict what will be accessed next.
# Track access counts in Redis sorted sets; warm the top keys before startup.

async def build_warmup_list_from_access_log(
    redis_client,
    window_hours: int  = 24,
    top_k:        int  = 1000,
) -> list[str]:
    """
    Returns the top-K most-accessed cache keys in the past window_hours.
    These are stored as a Redis sorted set updated on every cache access.
    """
    key = "cache_access_counts"
    cutoff_score = time.time() - (window_hours * 3600)

    # Remove old entries (older than the window)
    await redis_client.zremrangebyscore(key, "-inf", cutoff_score)

    # Get top-K keys by access count
    hot_keys = await redis_client.zrevrange(key, 0, top_k - 1, withscores=True)
    return [(k.decode(), int(score)) for k, score in hot_keys]

async def record_cache_access(redis_client, cache_key: str) -> None:
    """Called on every cache access to build the frequency model."""
    # Increment score for this key (score = last access timestamp)
    # Use ZINCRBY so keys that are accessed often have higher scores
    await redis_client.zincrby("cache_access_counts", 1, cache_key)
```

```yaml
          # Liveness probe: is the process alive?
          # Should NOT check cache warmth — a warming pod should not be killed.
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8000
            initialDelaySeconds: 5    # Give the process time to start
            periodSeconds:       10
            failureThreshold:    3    # Kill after 3 consecutive failures

          # Readiness probe: is the pod ready to receive traffic?
          # MUST check cache warmth — pod should not receive traffic until warm.
          readinessProbe:
            httpGet:
              path: /health/ready     # Returns 503 until cache is warm, then 200
              port: 8000
            initialDelaySeconds: 2    # Start checking after 2s
            periodSeconds:       3    # Check every 3 seconds
            successThreshold:    1    # 1 success = ready
            failureThreshold:    20   # 20 failures × 3s = 60s before giving up
            # If warming takes up to 30s: 30s / 3s = 10 checks.
            # 20 failures gives 60s of headroom — enough for slow warming.

          # Startup probe (Kubernetes 1.18+): separate probe for the startup phase.
          # Allows a longer initialization time without affecting the liveness probe.
          # While startupProbe is active, livenessProbe is disabled.
          startupProbe:
            httpGet:
              path: /health/ready
              port: 8000
            failureThreshold: 30      # 30 × 2s = 60s for startup
            periodSeconds:    2
            # After startupProbe succeeds once, it is disabled and
```

```python
# warming_with_k8s_awareness.py — Kubernetes-aware warming

import os

class KubernetesAwareCacheWarmer(CacheWarmer):
    """
    Extends CacheWarmer with Kubernetes-specific behavior:
    - Reads warmup config from environment variables (set in deployment YAML)
    - Reports warming progress via metrics for observability
    - Handles pod termination gracefully
    """

    def __init__(self, redis_client):
        super().__init__(redis_client)
        self._shutdown_requested = False

        # Register SIGTERM handler — Kubernetes sends SIGTERM before killing the pod
        import signal
        signal.signal(signal.SIGTERM, self._handle_shutdown)

    def _handle_shutdown(self, signum, frame):
        """On SIGTERM: mark shutdown, let in-flight requests complete."""
        logger.info("SIGTERM received. Graceful shutdown initiated.")
        self._shutdown_requested = True

    async def warm(self, tasks: list[WarmupTask]) -> dict:
        """
        Override: abort warming if SIGTERM is received.
        Allows quick pod termination without waiting for warming to complete.
        """
        for i, task in enumerate(tasks):
            if self._shutdown_requested:
                logger.info("Warming aborted due to shutdown signal after %d tasks", i)
                break
            await self._run_single_task(task)

        self._is_warm = True   # Ready even if incomplete — better than refusing traffic
        return self._warm_stats

    async def _run_single_task(self, task: WarmupTask) -> None:
        try:
            if await self._redis.exists(task.cache_key):
                return   # already warm

            data = await asyncio.wait_for(task.fetch(), timeout=task.timeout)
            await self._redis.setex(task.cache_key, task.ttl, orjson.dumps(data))

            # Emit metrics for monitoring
            metrics.increment("cache.warmup.key.success", tags={"key": task.name})
        except Exception as exc:
            metrics.increment("cache.warmup.key.failure", tags={"key": task.name})
            logger.error("Warm failed: %s: %s", task.name, exc)
            if task.required:
                raise


# ── WARMING DURING AUTOSCALE EVENTS ───────────────────────────────────────────
# New pods that start during a traffic spike need to warm quickly.
# The risk: they start cold, receive traffic immediately, hammer the DB.
# Solution: prioritize warming of the highest-traffic keys first.

async def warm_by_priority(tasks: list[WarmupTask], redis_client) -> None:
    """
    Warm tasks in order of expected traffic impact.
    High-priority tasks are warmed first so the pod becomes useful sooner.
    """
    # Sort tasks: required first, then by expected traffic (derived from historical data)
    required = [t for t in tasks if t.required]
    optional = [t for t in tasks if not t.required]

    # Warm required tasks synchronously (must complete before serving)
    for task in required:
        if await redis_client.exists(task.cache_key):
            continue
        try:
            data = await asyncio.wait_for(task.fetch(), timeout=task.timeout)
            await redis_client.setex(task.cache_key, task.ttl, orjson.dumps(data))
            logger.info("Priority warm: %s", task.name)
        except Exception as exc:
            logger.error("Priority warm failed: %s: %s", task.name, exc)
            raise   # required — abort

    # Signal readiness now — serve traffic for required keys
    # Optional tasks warm in background
    asyncio.ensure_future(_warm_optional(optional, redis_client))

async def _warm_optional(tasks: list[WarmupTask], redis_client) -> None:
    for task in tasks:
        try:
            if await redis_client.exists(task.cache_key):
                continue
            data = await asyncio.wait_for(task.fetch(), timeout=task.timeout)
            await redis_client.setex(task.cache_key, task.ttl, orjson.dumps(data))
        except Exception as exc:
            logger.warning("Optional warm failed: %s: %s", task.name, exc)
        await asyncio.sleep(0.1)   # gentle rate limiting between optional tasks
```

```python
# ── ANTI-PATTERN 1: Warming inside the request handler ────────────────────────
# Cache miss → fetch → cache SET all happen during the first request.
# The first user pays the full cost; no pre-warming occurs.
# Under concurrent first requests: stampede (Q2).
# This is "lazy warming" without stampede protection — the worst of both worlds.

@app.get("/api/products/featured")
async def get_featured_bad(request: Request):
    raw = await redis.get("products:featured")
    if raw:
        return orjson.loads(raw)
    # WRONG: every concurrent miss hits DB simultaneously
    products = await db.fetch("SELECT * FROM products WHERE featured = true")
    await redis.setex("products:featured", 3600, orjson.dumps(products))
    return products

# Fix: use get_with_lock() (Q2) or pre-warm at startup.


# ── ANTI-PATTERN 2: Warming with no TTL (SET without EXPIRE) ─────────────────
# Keys never expire. Stale data served indefinitely.
# A product that goes out of stock remains "in stock" in the cache forever.
# Redis memory grows without bound as new keys are added but old ones never removed.

async def warm_bad_no_ttl(key: str, data: any) -> None:
    await redis.set(key, orjson.dumps(data))   # WRONG: no TTL

# Fix: always set a TTL. Use SETEX or SET with EX option.
# Set the TTL based on how stale the data is acceptable to be, not on convenience.


# ── ANTI-PATTERN 3: Warming everything, regardless of access likelihood ────────
# For a product catalog of 1 million products:
# Warming all 1M at startup takes 30+ minutes and consumes enormous Redis memory.
# Most of these products will never be requested in any given session.
# The "warm" cache contains mostly data that will never be read.
# Meanwhile, the truly hot products have the same TTL as the long-tail ones.

async def warm_everything_bad(db_pool, redis_client) -> None:
    offset = 0
    while True:
        products = await db_pool.fetch("SELECT * FROM products LIMIT 500 OFFSET %s", offset)
        if not products:
            break
        # Warming products that will never be accessed for 30 minutes straight
        pipe = redis_client.pipeline()
        for p in products:
            pipe.setex(f"product:{p['id']}", 3600, orjson.dumps(dict(p)))
        await pipe.execute()
        offset += 500
        # 30 minutes later: startup finally "completes" — Redis has 1M keys,
        # most of which will expire before being read.

# Fix: warm only the hot subset (top N by access frequency). See Q6.


# ── ANTI-PATTERN 4: Ignoring the readiness probe ─────────────────────────────
# Application starts, warms cache in the background, accepts traffic immediately.
# Before warming is complete, the cold cache hammers the DB.
# The readiness probe returns 200 from the first second — Kubernetes routes traffic
# to the cold pod.

# WRONG: no warming awareness in health check
@app.get("/health/ready")
async def readiness_bad():
    return {"status": "ok"}   # always returns 200 — doesn't check cache

# Fix: readiness probe checks warmer.is_ready (Q4).


# ── ANTI-PATTERN 5: Warming from cache (circular) ────────────────────────────
# Warming reads from Redis to populate Redis.
# If Redis itself is cold (just restarted), all reads miss and nothing is warmed.
# This pattern works for cache-to-cache replication but not for the initial warm.

async def warm_from_cache_bad(source_redis, dest_redis, key: str) -> None:
    value = await source_redis.get(key)   # source may also be cold!
    if value:
        await dest_redis.set(key, value)
    # If source is cold → nothing is warmed → dest stays cold.

# Fix: always warm from the authoritative source (DB, external API), not from cache.
# Exception: replicating from a warm cache shard to a new shard is valid —
# but requires verifying the source is actually warm first.


# ── ANTI-PATTERN 6: Warming with the application's own cache-aside pattern ────
# Developers "warm" the cache by making requests to their own API.
# This works but has serious problems:
# - Requires the application to be running (chicken-and-egg)
# - Hits the application's own rate limiting, auth, and middleware
# - Sends test traffic through analytics/audit logs
# - Does not bypass the cold start problem — still misses on first request

async def warm_by_self_requests_bad() -> None:
    import httpx
    async with httpx.AsyncClient() as client:
        # "Warming" by calling my own API — runs through auth, rate limits, etc.
        await client.get("http://localhost:8000/api/products/featured")
        await client.get("http://localhost:8000/api/categories")
    # This is cargo-cult warming — it appears to work but misses the point.

# Fix: warm directly from the data source (DB), bypassing the application layer.
# The cache is populated with the exact data that would be generated for a real request,
# without the overhead or side effects of hitting the application itself.


# ── ANTI-PATTERN 7: Not warming after Redis failover ─────────────────────────
# Redis primary fails; replica is promoted; new primary starts empty (or with stale data).
# Application has warm in-process memory or warm connection to old primary.
# Now all application instances suddenly have cache misses on the new primary.
# Same effect as all pods restarting simultaneously.

# Missing: no hook to re-warm when Redis connection is re-established.

# Fix: subscribe to Redis connection events; trigger re-warming on reconnect.
async def on_redis_reconnect(warmer: CacheWarmer) -> None:

    warmer._is_warm = False   # Mark as cold
    tasks = await make_warmup_tasks(db_pool, config={})
    await warmer.warm(tasks)
    logger.info("Re-warm after Redis reconnect complete")
```

## Quick Reference: Cache Warming Strategy Selection

| Scenario | Strategy | Readiness Probe | Warming Source |
|---|---|---|---|
| Small working set (< 100 keys) | Eager (synchronous at startup) | Blocks until warm | DB / API |
| Large working set, startup time constrained | Background (async post-startup) + stampede lock | Returns ready immediately; misses handled by lock | DB / API |
| Predictable hot keys (Pareto distribution) | Predictive (top-N by access frequency) | Blocks until top-N are warm | Access logs → DB |
| Time-of-day traffic patterns | Scheduled (pre-warm before peak) | Returns ready; misses served from origin | DB at off-peak time |
| Redis restart / failover | Re-warm on reconnect event | Return not-ready until re-warm completes | DB |
| Rolling deploy with Redis shared across pods | Warm only missing keys (SCAN + fill gaps) | Blocks until required keys are warm | DB (skip already-warm keys) |
| Full fleet restart (config change) | Eager warming + staggered start | Blocks; stagger pod starts to spread DB load | DB |

## Quick Reference: Readiness vs. Liveness Probes for Warming

| Probe | Checks Warming? | What It Signals | Action on Failure |
|---|---|---|---|
| `startupProbe` | YES | Pod has initialized (including warming) | Kubernetes keeps trying; livenessProbe disabled |
| `readinessProbe` | YES | Pod is ready to serve traffic | Kubernetes stops routing traffic to this pod |
| `livenessProbe` | NO | Process is alive | Kubernetes kills and restarts the pod |

## Quick Reference: Anti-Pattern Checklist

| Anti-Pattern | Symptom | Fix |
|---|---|---|
| Warming inside request handler | DB stampede on first traffic burst | Warm at startup; add stampede lock |
| SET without TTL | Redis memory grows unbounded; stale data served forever | Always use SETEX or SET EX |
| Warming everything blindly | 30+ minute startup; Redis bloated with unread keys | Warm top-N hot keys only |
| Readiness probe ignores warm state | Cold pod receives traffic from Kubernetes immediately | Readiness probe checks `warmer.is_ready` |
| Warming from cache (circular) | No warm if source cache is also cold | Always warm from authoritative DB source |
| Self-request warming | Side effects in logs; auth/rate-limit overhead | Populate cache directly, bypassing app layer |
| No re-warm on Redis failover | Full-fleet stampede after Redis promotion | Subscribe to reconnect events; re-warm |

**Tip for the interview:** At 5 YOE, the cache warming question is almost never "what is a cache?" — it's a systems design question embedded in a scenario: "you deploy a new version and for the first 20 minutes after each deploy, your p99 latency is 10× normal — what's happening and how do you fix it?" Know the cold start → stampede → death spiral chain cold (Q1, Q2) — the mechanism where a cold cache causes DB overload, which prevents the cache from being populated, which keeps the cache cold. The readiness probe integration (Q4, Q8) is the most important implementation detail: a warming pod must return 503 from `/health/ready` until warm, and Kubernetes must be configured with `maxUnavailable: 0` so that old pods are not removed until new pods are ready — without both, rolling deploys still cause cold-start windows. The distinction between liveness and readiness probes matters: warming slowness should never trigger the liveness probe (which kills the pod), only the readiness probe (which just stops traffic). For large keyspaces (Q6), know the three approaches — warm the hot subset by access frequency, paginate through everything with rate limiting, or SCAN for missing keys — and be able to articulate the Pareto principle argument for why warming everything is usually wrong. The anti-patterns (Q10) are the depth signals: warming from the cache itself (circular), self-request warming (cargo-cult), and most critically not re-warming after a Redis failover (the scenario that looks like an outage with no code change).
