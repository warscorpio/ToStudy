# Caching for Performance: TTL Selection Strategy per Data Type — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a TTL in caching, and why does it exist?**
A: TTL (Time-To-Live) is a duration assigned to a cached entry after which the entry is considered stale and either evicted automatically or treated as invalid on the next read. It exists because cached data is a snapshot — the source of truth (database, API, computation) can change, and without expiry, the cache would serve stale data indefinitely. TTL is the primary mechanism that bounds the maximum staleness of a cached value. It's a trade-off knob: longer TTL → higher cache hit rate, lower freshness; shorter TTL → lower hit rate, higher freshness.

**Q2. What is the difference between TTL-based expiry and LRU eviction?**
A: TTL-based expiry is **time-driven** — an entry is expired after a fixed duration regardless of access frequency. LRU (Least Recently Used) eviction is **space-driven** — entries are removed when the cache is full, evicting whichever entry was accessed least recently. They're complementary, not exclusive. Redis, for example, applies both: TTL governs when an entry becomes logically stale, and the LRU/LFU eviction policy governs which entries get physically removed first when memory is under pressure. A key can be evicted before its TTL expires if memory is tight, or it can linger past its TTL in memory until accessed or lazily scanned.

**Q3. What are the two strategies for TTL enforcement — lazy vs. active expiry?**
A:
- **Lazy expiry (passive)** — the entry is not removed proactively. When a read request arrives, the cache checks whether the entry's TTL has elapsed; if yes, it treats it as a miss and deletes it then. Redis does this on every key access. Cost: stale entries can occupy memory until they're accessed.
- **Active expiry (proactive)** — a background process periodically scans entries and evicts expired ones even if they haven't been accessed. Redis runs an active expiry cycle every 100ms, sampling a fraction of keys with TTLs. Cost: CPU overhead for scanning, but keeps memory usage bounded.

In practice, both run together — lazy handles the hot path (reads), active handles the cold/orphaned keys.

**Q4. What is cache stampede (thundering herd) and how does TTL contribute to it?**
A: A cache stampede happens when a popular cached key expires simultaneously for many concurrent requests, all of which then hit the database at once before any of them has repopulated the cache. TTL is the direct trigger: a precise, identical TTL on all instances of a key means they all expire at the same instant. Mitigations include:
- **TTL jitter** — add a small random offset to each TTL (`baseTTL + Math.random() * jitterWindow`) to stagger expirations.
- **Probabilistic early recomputation (PER / XFetch)** — start refreshing a key probabilistically before it expires, based on how long the last computation took.
- **Locking / mutex** — only one process recomputes; others wait or serve stale.
- **Stale-while-revalidate** — serve the stale value immediately while asynchronously refreshing in the background.

**Q5. What is the difference between absolute TTL and sliding TTL?**
A: 
- **Absolute TTL** — the entry expires at a fixed point in time, regardless of access. Set once at insertion: `SETEX key 300 value` in Redis. Suitable for data that has a hard freshness deadline (e.g., OTP tokens, rate limit windows, price snapshots).
- **Sliding TTL** — the TTL resets on each access. The entry stays alive as long as it's being used, and only expires after a period of inactivity. Common in session caches — a user's session stays alive while they're active. Redis doesn't support native sliding TTL; you simulate it by calling `EXPIRE key <ttl>` on every read. Cost: every cache read also triggers a write (the TTL reset), adding latency and write amplification.

## Section 2: TTL by Data Type

**Q6. What TTL would you assign to a user's session token, and why?**
A: Sessions typically use **sliding TTL** — 15–30 minutes of inactivity causes expiry, but activity resets the clock. The exact window depends on the application's security posture: a banking app may use 5–10 minutes absolute (no sliding — the token has a hard expiry regardless of activity), while a consumer app might slide up to 24 hours. In Redis, implement sliding TTL by calling `EXPIRE session:<token> 1800` on every authenticated request. The TTL must also align with the refresh token / re-auth flow — if the session TTL is shorter than the refresh window, ensure the client knows to re-authenticate gracefully rather than getting a hard 401.

**Q7. What TTL would you use for a product catalogue or reference data that changes infrequently?**
A: Reference data (product names, categories, config tables, country lists) is a candidate for **long TTL** — typically 1–24 hours, or even until explicit invalidation. The key questions are: (a) how frequently does the source change? and (b) what is the business cost of serving stale data? For a fintech product catalogue, a stale loan product name or EMI rule shown to a customer for 30 minutes is usually acceptable; a stale interest rate shown on an offer screen is not. Pattern: long TTL (e.g., 1 hour) + event-driven invalidation on mutation (publish a cache-bust event when the admin changes the product) — best of both worlds.

**Q8. What TTL is appropriate for a real-time financial rate — e.g., a currency exchange rate or gold price?**
A: Near-zero or very short TTL — typically **10–60 seconds**, depending on how often the upstream source (exchange feed, market data API) publishes updates and what SLA the product promises. For a lending app showing USD/INR rates for FX loan disbursement, stale rates beyond a few seconds could create real financial exposure. Options:
- **Short absolute TTL (30s)** + poll on miss — simple, bounded staleness.
- **Push-based invalidation** — upstream rate service publishes changes to a Pub/Sub topic; the cache is invalidated on change, not on a timer.
- **No cache / pass-through** for the critical transaction path — cache only for display/estimation; always fetch live for actual booking.

**Q9. What TTL is appropriate for a user's feed or dashboard (aggregated, computed data)?**
A: Computed aggregations (dashboard summaries, analytics widgets, feed rankings) are expensive to recompute but can tolerate short-to-medium staleness — typically **30 seconds to 5 minutes** depending on how frequently the underlying data changes and user expectations. Strategy: cache the computed result with a short TTL, and use background refresh (stale-while-revalidate) so users always get a response immediately even if it's slightly stale. For a fintech lending dashboard showing "total active loans" or "EMI due this week," 1-minute staleness is almost always acceptable. For a real-time risk dashboard shown to an ops team, it may not be.

**Q10. What TTL should OTP (one-time password) tokens use?**
A: OTPs have a **hard, absolute TTL** that directly encodes the business/security rule — typically **3–10 minutes** for phone/email OTPs. The TTL is not a cache performance decision; it's a security constraint. Implementation in Redis: `SET otp:<userId> <hashedOtp> EX 300 NX` — the `NX` (set only if not exists) prevents overwriting a valid OTP before it expires (rate-limiting resend). Considerations: don't use sliding TTL (that would let an attacker keep an OTP alive indefinitely by polling), and ensure the Redis key is deleted on first successful use (not just on expiry) to enforce single-use semantics.

**Q11. What TTL would you use for a rate limiter's sliding window counter?**
A: Rate limiters store counters per user/IP per time window. The TTL should equal the window size — e.g., for a "100 requests per minute" rule, the counter key has TTL = **60 seconds**. With a fixed window counter, this is straightforward: `INCR ratelimit:<userId>:<windowMinute>` with `EXPIRE` set to 60s. With a sliding window log (storing timestamps of each request), the TTL equals the window size on the log key. The TTL must be set at creation, not on every increment (otherwise every request resets the window). With token bucket / leaky bucket implementations, the state key's TTL should be long enough to hold the bucket state across gaps in traffic — often the refill period or a multiple of it.

**Q12. What TTL would you assign to a search autocomplete suggestion list?**
A: Autocomplete suggestions derived from popular queries or product titles can use **medium-to-long TTL** — **5–60 minutes** — since they're usually pre-computed offline and updated in batches. The staleness risk is low (a slightly outdated suggestion is tolerable), but the computation is expensive (involves aggregating query logs or running NLP). Key insight: use a **cache-aside with background refresh** — serve from cache with a long TTL, and have a scheduled job (every 15 minutes) recompute and push new results to cache proactively, so the cache is rarely cold. Avoid relying on TTL expiry to trigger recomputation — that creates latency spikes on the first user who hits a miss.

**Q13. How do you set TTL for cached database query results?**
A: It depends on three factors: (a) **query volatility** — how frequently the underlying rows change; (b) **query cost** — expensive queries (multi-join, aggregation) warrant longer TTL; (c) **staleness tolerance** — what the consumer does with the data.

| Query type                              | Suggested TTL     |
|-----------------------------------------|-------------------|
| User profile / account details          | 1–5 min (or event-invalidated) |
| Loan application status                 | 30s–2 min         |
| Static lookup (state codes, bank IFSCs) | 1–24 hr           |
| Aggregated report / count               | 2–15 min          |
| Real-time balance / ledger              | Do not cache, or <10s |

The universal rule: **never cache without a plan for invalidation**. TTL is the fallback; event-driven invalidation (cache bust on write) is the primary mechanism for mutable data.

## Section 3: Advanced TTL Patterns

**Q14. What is stale-while-revalidate, and when should you use it?**
A: Stale-while-revalidate (SWR) is a pattern where the cache serves the stale (expired) value immediately while asynchronously triggering a background refresh. The user never waits for a cache miss — they always get a response, and the cache self-heals in the background. It's ideal for data where latency matters more than perfect freshness: dashboards, feeds, product listings, and autocomplete. In HTTP, it's expressed as `Cache-Control: max-age=60, stale-while-revalidate=30`. In application-level caches (Redis), you implement it manually: on read, if the key is within a "stale window" beyond its TTL, serve the stale value and fire an async recompute. If it's fully gone from cache, you either lock-and-compute or serve a degraded response.

**Q15. What is probabilistic early expiration (XFetch), and how does it relate to TTL?**
A: XFetch is an algorithm that starts recomputing a cached value before its TTL expires, with a probability that increases as expiry approaches and scales with how long the last computation took. The formula: recompute if `currentTime - (computationTime * β * log(random()))` exceeds the expiry time. The `β` parameter controls aggression. The effect: expensive-to-compute values get refreshed proactively by whichever process first "wins" the probabilistic check, preventing the cold start at the moment of expiry. It's particularly useful for globally popular keys where a simultaneous miss would trigger a stampede.

**Q16. How does TTL interact with cache warming strategies?**
A: Cache warming is the practice of pre-populating the cache before traffic hits it — at deploy time, after a cache flush, or on a schedule. TTL directly affects warming strategy:
- If TTL is very short (seconds to minutes), warming has diminishing value — the cache turns over too fast for a warm-up to matter.
- If TTL is long (hours), warming is valuable but must be timed carefully — you want the warm-up to complete before cached entries start expiring during peak traffic.
- A common pattern in fintech: on service startup, eagerly load high-traffic reference data (loan products, bank list, config) into Redis with a long TTL, so the first user request is never a cold miss on these items.

**Q17. What is a "cache aside" pattern, and how do you pick the TTL for it?**
A: In cache-aside (lazy loading), the application reads from cache first; on miss, reads from the DB, writes to cache, and returns. The TTL choice must balance: (a) recomputation cost on miss, (b) acceptable staleness, (c) write frequency of the underlying record. Rule of thumb: if the record is written frequently (many updates per minute), keep TTL short (seconds to low minutes) or switch to write-through + invalidation. If the record is read-heavy and write-rarely (classic reference data), TTL can be long. Always add jitter to avoid synchronized expiry across replicas: `ttl = baseTtl + Math.floor(Math.random() * jitterMs)`.

**Q18. How does multi-level caching (L1 in-process + L2 Redis) affect TTL strategy?**
A: In a two-level cache (e.g., in-process LRU as L1, Redis as L2), you typically assign **shorter TTL to L1** and **longer TTL to L2**. L1 is faster but not shared across instances and has limited capacity — its TTL bounds how long a single node can serve stale data independently of Redis. L2 (Redis) is shared and authoritative for the cluster. Example: product config — L1 TTL = 30 seconds (each app instance refreshes from Redis every 30s), L2 TTL = 10 minutes (Redis refreshes from DB every 10 minutes). When the DB record changes, you invalidate L2; L1 will pick up the change on its next refresh cycle (up to 30s lag). This "eventual freshness" is acceptable for most reference data but not for financial transactions.

## Section 4: Pitfalls & Anti-patterns

**Q19. What is "TTL drift" and how does it cause subtle bugs in distributed systems?**
A: TTL drift happens when multiple replicas or services set the TTL for the same logical key at slightly different times — e.g., three app servers all cache a user record independently on cache miss, each starting the TTL clock at a different moment. The result: each server's cached copy expires at a different time, leading to inconsistent reads across the cluster for a window of time. Mitigations: use a single authoritative TTL start time (embed expiry timestamp in the value, not just rely on Redis TTL), or use write-through caching (all writes go through one path that sets the TTL centrally).

**Q20. Why is setting TTL = 0 (no expiry) almost always wrong for mutable data?**
A: A key with no TTL lives forever unless explicitly deleted. For immutable data (a computed hash, a static asset's fingerprint), this is fine. For mutable data, no-TTL means you're relying entirely on explicit invalidation — if any code path mutates the data without busting the cache, staleness becomes permanent until a manual flush or restart. It's a correctness time-bomb. Even when you intend to rely on explicit invalidation, always set a long TTL as a safety net (e.g., 24 hours) — it bounds the worst-case staleness in the event of a missed invalidation.

**Q21. What happens when you cache a "not found" (null/empty) result with no TTL, and why is it dangerous?**
A: Caching a miss (negative caching) is actually good practice — without it, repeated lookups for a non-existent key hammer the DB. But a no-TTL negative cache entry means the "not found" result is served forever, even after the record is created in the DB. This is a correctness bug: a user signs up, but the service keeps returning "user not found" from cache. Fix: always set a **short TTL on negative cache entries** (typically 10–60 seconds) — long enough to deflect a burst of repeated misses, short enough that newly created records become visible quickly.

**Q22. What is "hot key" expiry and how do you handle the TTL problem for a single globally popular key?**
A: A hot key is a single cache entry accessed at extremely high RPS (e.g., a homepage banner config, a popular product, the current exchange rate). When it expires, all concurrent requests simultaneously miss and hammer the DB — a stampede by definition. Approaches:
- **Lock-based refresh** — use a distributed lock (Redis `SET NX EX`) so only one process refreshes; others wait or serve stale.
- **Local L1 cache** — each app instance caches the hot key in-process with a short TTL, staggering misses across nodes.
- **Perpetual cache with push invalidation** — never let it expire via TTL; only invalidate when the source actually changes.
- **Read replicas + async refresh** — serve stale from cache while a background job owns the refresh cycle.

## Section 5: Scenario / System Design Style Questions

**Q23. "Design the caching layer for a fintech app's loan eligibility check. The check involves a credit bureau API call, the user's internal credit score, and current product rules. How do you assign TTLs?"**
A: Three distinct data types, three different TTLs:

| Component              | TTL strategy                          | Rationale                                                                 |
|------------------------|---------------------------------------|---------------------------------------------------------------------------|
| Credit bureau report   | 24 hours (keyed by PAN + date)        | Bureau reports are expensive (~₹15–50/call), change slowly, and bureaus themselves rate-limit. Stale within a day is acceptable for eligibility pre-checks; always re-fetch at final sanction. |
| Internal credit score  | 5–15 minutes                         | Computed from recent transactions — can change if user makes a repayment or new delinquency is logged. Short TTL limits exposure. |
| Product rules (interest rates, LTV caps) | 10–60 minutes + event invalidation | Changes via admin action; use long TTL + explicit cache bust on product update event via Kafka/SNS. |

For the final booking/disbursal API, bypass cache entirely and fetch live data — cached eligibility is for UX; real money movement uses authoritative data.

**Q24. "Your Redis memory usage has been growing steadily. On investigation, you find thousands of keys with no TTL. How do you audit and fix this in production without downtime?"**
A: Step-by-step approach:
1. **Audit** — use `redis-cli --scan --pattern "*"` with `TTL <key>` checks, or run `DEBUG SLEEP 0` + `INFO keyspace` to get the count of keys without TTL. For large keyspaces, use `redis-cli --bigkeys` or a sampling script.
2. **Identify categories** — group keys by prefix/naming convention to understand what type of data they represent (sessions, cached queries, feature flags, etc.).
3. **Set TTLs non-destructively** — for keys where you know the right TTL, use `EXPIRE key <seconds>` — this doesn't delete or change the value, just starts the expiry clock. Do this in batches with a Lua script or a small Node.js script to avoid blocking Redis.
4. **Fix the application code** — find all `SET`/`SETEX`/`HSET` calls in the codebase that don't include a TTL and add one.
5. **Monitoring** — alert on `redis_keys_without_ttl` metric going forward; many Redis monitoring setups (Datadog, Prometheus redis_exporter) expose this.

**Q25. "A cache key for a user's KYC status is being read millions of times per day across 50 microservices. The KYC status changes rarely (only when a KYC review completes). How do you set the TTL?"**
A: This is a read-heavy, write-rare scenario — ideal for long TTL + event-driven invalidation:
- **Redis TTL: 1–6 hours** as a safety net (not the primary freshness mechanism).
- **Invalidation on write**: when the KYC service updates a user's status in the DB, it publishes a `kyc.status.updated` event to Kafka/SNS. A cache invalidation consumer deletes (or refreshes) the Redis key immediately.
- **L1 in-process cache**: each microservice can maintain a 30-second in-process cache of recently read KYC statuses to reduce Redis load. The 30-second lag on invalidation is acceptable for KYC (a compliance check completing is not instant).
- **Negative caching**: if the key doesn't exist in cache, cache the "not found" result too, with a short TTL (30s), to protect against a thundering herd on first access for a new user.

The long Redis TTL is purely a correctness backstop — it bounds the worst case if the Kafka consumer goes down or misses an event.

**Tip for the interview:** At the 5 YOE level, "what TTL should I use?" is never the real question — it's always "what is the staleness tolerance, what is the write frequency, what is the cost of a miss, and what is the invalidation strategy?" TTL is one lever in a system that also includes eviction policy, invalidation events, negative caching, stampede protection, and multi-level architecture. Have a concrete example ready — ideally from your own system — where you made a TTL decision and explain the trade-offs you weighed: a bureau API you rate-cached to control cost, an OTP store you built with hard expiry for security, or a rate limiter you debugged when the TTL was reset on every increment instead of at creation.
