# Performance (Caching): Identifying Cache Candidates — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is caching, and what is the fundamental trade-off it makes?**
A: Caching stores the result of an expensive operation in a faster-access medium so that subsequent requests for the same result can be served without repeating the operation. The "faster medium" is almost always memory (Redis, in-process Map, CPU cache) rather than disk or a network call to a database or upstream service.

The fundamental trade-off is **freshness vs. speed**. A cache by definition stores a copy of data — a copy that may diverge from the source of truth at any point after it was written. The longer data lives in the cache (the TTL), the faster the average read, but the greater the risk that the cached value is stale. Every caching decision is a negotiation on this axis.

Three subsidiary trade-offs follow from this:

**Consistency** — in a distributed system with multiple instances, each instance may hold a different cached value for the same key, or may not hold the value at all. Cache invalidation across instances requires coordination.

**Memory pressure** — the cache occupies RAM. A cache that holds too much data evicts useful entries to make room, reducing hit rate. A cache with no eviction policy is an unbounded memory leak.

**Complexity** — every cached value is a potential consistency bug. Uncached code is easy to reason about ("what's in the database is what the code uses"); cached code requires reasoning about when values are populated, when they expire, when they are invalidated, and what happens when they aren't.

The engineering discipline of caching is knowing which operations benefit enough from caching to justify these costs — and knowing the failure modes when the trade-off goes wrong.

**Q2. What two properties together make an operation a good cache candidate?**
A: Two properties must both be present for caching to be beneficial:

**1. Expensive to compute or fetch.** The operation must have a meaningful cost that caching avoids — a slow database query, a CPU-intensive computation, a round-trip to an external API, a complex join across multiple tables. If the operation takes 0.1ms, caching adds more overhead (cache key hashing, Redis round-trip, serialisation) than it saves.

**2. Requested more often than it changes.** If a value changes on every access or changes ten times per second, any cache would have a hit rate of near zero or serve stale data on almost every read. The value must be stable enough that a meaningful proportion of reads happen between updates. This is the **read/write ratio** from the denormalisation discussion — the same logic applies. A value read 1,000 times per write is a far better cache candidate than one read twice per write.

Together these define the **cache benefit equation**:

```
Cache benefit = (read frequency) × (operation cost) - (write frequency) × (invalidation cost)
```

When this is positive, caching reduces total work. When this is negative, caching adds complexity without reducing load — a maintenance liability.

A third property is often required in practice: **the operation must be deterministic or near-deterministic for a given key** — calling the same function with the same input should return the same (or equivalent) output. Operations with significant randomness or side effects are poor cache candidates.

**Q3. What are the distinct categories of data that appear in a typical fintech application, and how do their caching profiles differ?**
A: Categorising data by its change frequency and access pattern is the first step in any caching analysis:

**Category 1 — Static reference data:**
Product configurations, loan scheme parameters, IFSC code lookups, pincode-to-branch mappings, RBI regulatory limits, interest rate tables. Changes: manual deployments or admin panel updates — at most a few times per day. Reads: millions per day (every loan application, every repayment calculation). Cache profile: **ideal candidate** — high read frequency, very low write frequency, broad applicability (the same IFSC lookup is needed by thousands of concurrent users). TTL of hours to days is appropriate.

**Category 2 — User session and authentication data:**
JWT validation results, active session metadata, user roles and permissions. Changes: on logout, role changes, password reset — relatively rare. Reads: every authenticated API request (potentially hundreds per second per user). Cache profile: **strong candidate** — high read frequency, low write frequency, but consistency is critical (a revoked session must not be served from cache). Short TTL (1–5 minutes) or explicit invalidation on change.

**Category 3 — Derived aggregates:**
A user's total outstanding debt, a branch's monthly disbursement count, a portfolio's weighted average interest rate. Changes: on every relevant transaction — potentially high frequency for a busy branch. Reads: dashboard views, credit decisions, reports. Cache profile: **conditional** — depends on whether staleness is acceptable. A dashboard displaying "as of 5 minutes ago" is fine; a credit decision requiring the exact current outstanding balance is not.

**Category 4 — Operational data:**
Active loan applications, pending KYC records, current EMI schedules, NACH mandate status. Changes: frequently — status transitions, officer assignments, repayments. Reads: high, but reads and writes are closely coupled. Cache profile: **poor to risky** — high write frequency relative to read frequency, and staleness directly impacts business logic. Caching this data introduces consistency bugs proportional to TTL length.

**Category 5 — Personalised computed results:**
A user's loan eligibility assessment, their credit score interpretation, their recommended loan products. Changes: on changes to the user's profile, bureau score, or product catalogue — low frequency. Reads: user-triggered — once per session or per application. Cache profile: **per-user conditional** — the computation is expensive (bureau pull + eligibility algorithm), but the result is only read once or twice before it's used and discarded. Cache lifetime must be scoped to one user session.

## Section 2: Identifying Expensive Operations

**Q4. How do you systematically identify expensive queries that are cache candidates in a production PostgreSQL + NestJS application?**
A: Systematic identification requires tools, not intuition. Three layers of evidence:

**Layer 1 — PostgreSQL slow query log:**
```sql
-- postgresql.conf (or RDS parameter group)
log_min_duration_statement = 100   -- log queries taking > 100ms
log_statement_sample_rate  = 1.0   -- log 100% of slow queries (reduce in very high traffic)
```

After a period of collection, analyse the slow query log:
```bash
# pgBadger: generates HTML reports from PostgreSQL logs
pgbadger /var/log/postgresql/postgresql.log -o report.html

# Or: query pg_stat_statements directly
psql -c "
SELECT
  LEFT(query, 80)             AS query_preview,
  calls,
  ROUND(total_exec_time::numeric, 2) AS total_ms,
  ROUND(mean_exec_time::numeric, 2)  AS mean_ms,
  ROUND(stddev_exec_time::numeric, 2) AS stddev_ms,
  rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
"
```

Queries at the top of `total_exec_time` are the highest cumulative cost — they may be fast individually but called so frequently that they dominate overall DB load. Both dimensions matter: a 2-second query called once a day is less important than a 50ms query called 10,000 times a day.

**Layer 2 — Application-level query tracing:**
```typescript
// TypeORM slow query logger — flags queries exceeding a threshold
// In DataSource config:
{
  logging:             true,
  maxQueryExecutionTime: 50,  // log queries taking > 50ms
  logger:              'advanced-console',
}

// Or: custom logger that ships slow query data to your APM
class SlowQueryLogger implements Logger {
  logSlowQuery(time: number, query: string, params?: unknown[]): void {
    if (time > 50) {
      this.metrics.histogram('db.query.duration', time, {
        query: this.fingerprint(query),  // remove literals for grouping
      });
      if (time > 200) {
        this.logger.warn('Slow query detected', { time, query: this.sanitise(query) });
      }
    }
  }
}
```

**Layer 3 — APM distributed traces:**
In a NestJS application with Datadog APM, New Relic, or OpenTelemetry configured, every request shows a waterfall of spans including database calls. Filter traces by p99 latency and examine which spans are the widest — those are the operations worth caching.

```typescript
// OpenTelemetry instrumentation — auto-instruments TypeORM queries
import { TypeormInstrumentation } from '@opentelemetry/instrumentation-typeorm';

// Every query appears as a span in your trace:
// Span: SELECT loan_applications WHERE tenant_id = ?
//   Duration: 340ms
//   Called: 450 times in last hour
//   Accounted for: 153 seconds of total CPU
```

**The prioritisation matrix:**
```
                    High call frequency
                    │
      Tier 1        │  Tier 2
      (Cache first) │  (Optimise query, then cache)
──────────────────────────────────────────────────
High  │             │
cost  │  Tier 3     │  Tier 4
per   │  (Cache if  │  (Low priority)
call  │  infrequent)│
      │             │
                    Low call frequency
```

Tier 1 (high frequency, high individual cost): `SELECT` with multiple joins on a hot endpoint — immediate cache candidate.
Tier 2 (high frequency, low individual cost): a 10ms query called 50,000 times/hour — collectively 500 seconds of DB time; worth caching even though each instance is fast.
Tier 3 (low frequency, high individual cost): a complex report query run once per hour — cacheable but lower urgency.
Tier 4 (low frequency, low cost): no action needed.

**Q5. How do you identify which external API calls are cache candidates in a microservices or third-party integration context?**
A: External API calls introduce network latency, rate limits, and per-call cost — three independent motivations for caching beyond pure performance.

**Latency motivation:** an Aadhaar/DigiLocker API call may take 800ms–2s. If this is called on every loan application page load and the result doesn't change between page loads, caching the result for the session duration eliminates a 1-second latency spike with zero data freshness cost.

**Rate limit motivation:** CIBIL and other credit bureau APIs charge per pull and have daily rate limits. A bureau pull for a given PAN that was done 2 hours ago doesn't need to be redone — the score won't have changed materially. Cache the bureau result for 24 hours (or the bureau's own validity window) to avoid redundant pulls.

**Cost motivation:** NACH gateway API calls to check mandate status cost money per call. A mandate's status (active, pending, cancelled) doesn't change more than once per mandate event. Cache the status with a short TTL (5 minutes) — the cost saving is direct.

```typescript
// Identifying external API cache candidates in code
// Look for: HttpService.get/post, fetch(), axios.get() calls in hot paths

// Signal 1 — called within a request handler (high frequency)
@Get(':id')
async getLoan(@Param('id') id: string): Promise<LoanDto> {
  const loan = await this.loanRepo.findOne(id);

  // This call happens on EVERY loan detail view — cache candidate
  const kycStatus = await this.kycService.getStatus(loan.userId);

  return this.toDto(loan, kycStatus);
}

// Signal 2 — called in a loop (N+1 variant for external APIs)
const loansWithKyc = await Promise.all(
  loans.map(async (loan) => ({
    ...loan,
    // This hits the KYC API N times — each should be cached
    kycStatus: await this.kycService.getStatus(loan.userId),
  }))
);

// Signal 3 — called in a cron job that could be pre-computed
@Cron('*/5 * * * *')
async syncMandateStatuses(): Promise<void> {
  const mandates = await this.nachRepo.findActive();
  for (const mandate of mandates) {
    // Polling external API — if the result is used immediately, cache it
    const status = await this.npciGateway.getMandateStatus(mandate.referenceId);
    await this.nachRepo.update(mandate.id, { status });
  }
}
```

**Assessment questions for each external call:**
1. How long does this call take? (> 100ms → caching saves meaningful latency)
2. How often is it called per unit time? (> 100/minute → significant aggregate cost)
3. How often does the result actually change? (< once per hour → cache lifetime of at least 5 minutes is safe)
4. What is the cost of serving stale data? (Is it a display value or a decision input?)
5. Does the API have a rate limit or per-call cost? (If yes, cache is financially justified)

**Q6. How do you identify CPU-bound computations that are cache candidates?**
A: CPU-bound computations are a less obvious cache category than database queries, but they matter significantly in fintech where eligibility calculations, interest computations, and risk scoring are often non-trivial.

**Identifying CPU-bound operations:**

From the profiling guide: use `clinic flame` or `node --prof` to find wide rectangles at the top of the flame graph — functions consuming CPU with no I/O. If such a function is called frequently and its inputs change infrequently, it's a cache candidate.

**Fintech-specific examples:**

```typescript
// Example 1: EMI calculation — pure computation, called on every display
function calculateEmi(principal: number, rate: number, tenure: number): number {
  // Formula: P × r × (1+r)^n / ((1+r)^n - 1)
  const monthlyRate = rate / 12 / 100;
  return principal * monthlyRate * Math.pow(1 + monthlyRate, tenure)
    / (Math.pow(1 + monthlyRate, tenure) - 1);
}
// Called 50,000 times/hour in a loan calculator endpoint
// Takes ~0.1ms but with 50,000 calls = 5 seconds total CPU/hour
// Input set is finite: principal (discrete values), rate (from a small table), tenure (12–360 months)
// → Cache with key: `emi:${principal}:${rate}:${tenure}` — few thousand possible combinations

// Example 2: Credit risk scoring — expensive multi-factor calculation
async calculateRiskScore(userId: string): Promise<RiskScore> {
  const [bureauData, loanHistory, incomeProfile] = await Promise.all([
    this.bureau.pull(userId),
    this.loanRepo.getHistory(userId),
    this.employmentRepo.getProfile(userId),
  ]);

  // CPU-intensive: multiple weighted formula evaluations
  return this.riskEngine.score(bureauData, loanHistory, incomeProfile);
}
// Takes 1.5 seconds (mostly I/O but 200ms CPU). Called on every application submission.
// Bureau data is fresh for 24 hours. Loan history changes rarely.
// → Cache the result for 24 hours per user: `risk:score:${userId}`

// Example 3: Loan product eligibility matrix evaluation
function evaluateEligibility(userProfile: UserProfile, products: LoanProduct[]): EligibilityResult[] {
  return products.map(product => ({
    product,
    eligible:   this.checkEligibility(userProfile, product),
    maxAmount:  this.computeMaxAmount(userProfile, product),
    rate:       this.computeRate(userProfile, product),
  }));
}
// Called on every product listing page. Products change rarely (admin updates).
// User profile changes rarely (KYC, income update). 
// → Cache per (userId, productCatalogue version)
```

**Identifying CPU-bound cache candidates programmatically:**
```typescript
// Add timing to functions you suspect are expensive
function memoizable<T>(fn: (...args: unknown[]) => T, keyFn: (...args: unknown[]) => string) {
  const times = new Map<string, number[]>();

  return function (...args: unknown[]): T {
    const start = performance.now();
    const result = fn(...args);
    const duration = performance.now() - start;

    const key = keyFn(...args);
    const existing = times.get(key) ?? [];
    existing.push(duration);
    times.set(key, existing);

    if (existing.length === 100) {
      const avg = existing.reduce((a, b) => a + b, 0) / 100;
      if (avg > 5) console.log(`Cache candidate: avg ${avg.toFixed(2)}ms for key pattern ${key}`);
      times.delete(key);
    }

    return result;
  };
}
```

## Section 3: Cache Invalidation Strategies

**Q7. What are the four main cache invalidation strategies, and which is appropriate for each category of fintech data?**
A: Cache invalidation is where most caching complexity lives. The right strategy depends on data change frequency, consistency requirements, and the cost of staleness.

**Strategy 1 — TTL (Time-to-Live) expiry:**
The cache entry automatically expires after a defined duration. The next request after expiry fetches from the source and repopulates the cache.

```typescript
// Redis TTL-based caching
await this.redis.setex(`loan:scheme:${schemeId}`, 3600, JSON.stringify(scheme));
// Expires in 1 hour — the next request after expiry fetches fresh
```

Best for: data that changes periodically on a known schedule, where brief staleness is acceptable. Reference data (product schemes, rate tables), rate limit counters, session tokens. The TTL should be shorter than the typical change interval but long enough to provide meaningful hit rate.

Not appropriate for: data whose changes must be immediately reflected (a revoked session, a loan status change that affects an active disbursement decision).

**Strategy 2 — Write-through invalidation (explicit delete on write):**
When the source data changes, the application that wrote the change also deletes (or updates) the cache entry. The next read repopulates from the new source value.

```typescript
// When a loan scheme is updated by an admin
async updateLoanScheme(schemeId: string, dto: UpdateSchemeDto): Promise<void> {
  await this.schemeRepo.save({ id: schemeId, ...dto });

  // Immediately invalidate the cache so subsequent reads get fresh data
  await this.redis.del(`loan:scheme:${schemeId}`);

  // Also invalidate any computed values that depend on this scheme
  await this.redis.del(`eligibility:scheme:${schemeId}`);
}
```

Best for: data with a clear write path that goes through your application — you can intercept the write and invalidate the cache in the same transaction or immediately after. Most application data: user profiles, loan status, KYC results, session data.

The risk: if the write path is not always through the application (direct DB updates, migrations, external writes), invalidation is missed and the cache serves stale data indefinitely. The TTL serves as the backstop in such cases — even write-through caches should have a TTL as a safety net.

**Strategy 3 — Event-driven invalidation:**
A message (event) is published when data changes. Cache invalidation is a subscriber to that event. In a multi-service architecture, this is often the only way to invalidate caches in services that don't directly perform the write.

```typescript
// Publisher: loan service publishes event when status changes
await this.eventBus.publish(new LoanStatusChangedEvent(loanId, newStatus));

// Subscriber: cache service invalidates affected caches
@EventHandler(LoanStatusChangedEvent)
async handleLoanStatusChanged(event: LoanStatusChangedEvent): Promise<void> {
  await Promise.all([
    this.redis.del(`loan:${event.loanId}:summary`),
    this.redis.del(`user:${event.userId}:active_loans`),
    this.redis.del(`branch:${event.branchId}:dashboard`),
  ]);
}
```

Best for: microservices architectures where writes happen in one service but cache invalidation is needed across multiple services. Decouples the write path from the invalidation logic. Inherently eventually consistent — there is a lag between the write and the cache invalidation equal to the event propagation delay.

**Strategy 4 — Cache-aside with no invalidation (computed from stable inputs):**
Some cache values can be made inherently stable by tying them to immutable inputs. Rather than invalidating when data changes, a new version of the data produces a new cache key.

```typescript
// Cache key includes a version: when the product catalogue version changes,
// the old cache entries are simply never hit again (and expire via TTL)
const cacheKey = `eligibility:${userId}:catalogue-v${catalogueVersion}`;
const cached   = await this.redis.get(cacheKey);
if (cached) return JSON.parse(cached);

const result = await this.computeEligibility(userId, catalogueVersion);
await this.redis.setex(cacheKey, 86400, JSON.stringify(result));
return result;
```

Best for: computed results that depend on versioned inputs (product catalogue version, scheme version). The "old" cached result is naturally orphaned when the version changes. Works well when inputs are versioned or have a natural staleness boundary.

**Q8. What is cache stampede (thundering herd), and how do you prevent it?**
A: Cache stampede occurs when a popular cache entry expires, and a large number of concurrent requests all find a cache miss simultaneously. Every request independently executes the expensive operation (DB query, API call), leading to a sudden spike in load that may be N times the normal load — where N is the number of concurrent requests that arrived between the expiry and the first repopulation.

**Scenario:**
```
Cache key: loan:scheme:home-loan  (TTL = 1 hour, very high traffic endpoint)

T=0: Key expires
T=0 to T+500ms: 200 concurrent requests arrive
All 200: cache miss → all 200 execute the DB query simultaneously
DB: receives 200 identical queries → query load spikes × 200
T+500ms: all 200 queries complete → all 200 write the same value to cache
Result: 200 unnecessary DB queries; brief DB overload
```

**Prevention patterns:**

**1. Mutex / single-worker lock (most robust):**
```typescript
async getCachedScheme(schemeId: string): Promise<LoanScheme> {
  const cached = await this.redis.get(`scheme:${schemeId}`);
  if (cached) return JSON.parse(cached);

  // Only one process acquires the lock and fetches the value
  const lockKey     = `lock:scheme:${schemeId}`;
  const lockAcquired = await this.redis.set(lockKey, '1', 'EX', 10, 'NX');

  if (lockAcquired) {
    // This instance won the lock — fetch and populate
    try {
      const scheme = await this.schemeRepo.findOne(schemeId);
      await this.redis.setex(`scheme:${schemeId}`, 3600, JSON.stringify(scheme));
      return scheme;
    } finally {
      await this.redis.del(lockKey);
    }
  } else {
    // Another instance is populating — wait briefly and retry
    await new Promise(r => setTimeout(r, 50 + Math.random() * 50));  // jitter
    return this.getCachedScheme(schemeId);  // recursive retry
  }
}
```

**2. Probabilistic early expiry (XFetch algorithm):**
```typescript
// Inspired by "Optimal Probabilistic Cache Stampede Prevention"
// Refresh the cache before it expires, with probability proportional to how close to expiry
async getCachedWithEarlyRefresh(key: string, ttl: number, fetch: () => Promise<unknown>) {
  const stored = await this.redis.get(`data:${key}`);
  const meta   = await this.redis.get(`meta:${key}`);  // stores expiry time and computation cost

  if (stored && meta) {
    const { expiresAt, computeTime } = JSON.parse(meta);
    const remaining = expiresAt - Date.now();

    // XFetch: P(refresh) = exp(-remaining / (beta * computeTime))
    // As remaining approaches 0, probability approaches 1
    const beta = 1.0;
    const shouldRefresh = -computeTime * beta * Math.log(Math.random()) > remaining;

    if (!shouldRefresh) return JSON.parse(stored);
    // Refresh proactively — before expiry, so other requests still get the old value
  }

  const start = performance.now();
  const fresh = await fetch();
  const computeTime = performance.now() - start;

  await Promise.all([
    this.redis.setex(`data:${key}`, ttl, JSON.stringify(fresh)),
    this.redis.setex(`meta:${key}`, ttl, JSON.stringify({
      expiresAt: Date.now() + ttl * 1000,
      computeTime,
    })),
  ]);
  return fresh;
}
```

**3. Stale-while-revalidate:**
```typescript
// Serve stale data immediately; refresh in the background
async getCachedWithStaleServing(key: string, ttl: number, fetch: () => Promise<unknown>) {
  const stored = await this.redis.get(`data:${key}`);
  const age    = await this.redis.ttl(`data:${key}`);

  if (stored) {
    const isStale = age < ttl * 0.1;  // in last 10% of TTL — "stale window"
    if (isStale) {
      // Refresh in background — don't await; serve stale immediately
      this.refreshInBackground(key, ttl, fetch).catch(err =>
        this.logger.error('Background refresh failed', err)
      );
    }
    return JSON.parse(stored);
  }

  // Cold miss — must wait for fresh data
  return this.fetchAndCache(key, ttl, fetch);
}

private async refreshInBackground(key: string, ttl: number, fetch: () => Promise<unknown>) {
  const lockKey = `refresh-lock:${key}`;
  const acquired = await this.redis.set(lockKey, '1', 'EX', 30, 'NX');
  if (!acquired) return;  // another instance is already refreshing

  try {
    const fresh = await fetch();
    await this.redis.setex(`data:${key}`, ttl, JSON.stringify(fresh));
  } finally {
    await this.redis.del(lockKey);
  }
}
```

**Q9. How do you implement a generic caching service in NestJS that handles serialisation, TTL, and cache-aside pattern?**
A:
```typescript
// cache.service.ts
import { Injectable, Logger } from '@nestjs/common';
import { InjectRedis }         from '@nestjs-modules/ioredis';
import Redis                   from 'ioredis';

@Injectable()
export class CacheService {
  private readonly logger = new Logger(CacheService.name);

  constructor(@InjectRedis() private readonly redis: Redis) {}

  /**
   * Get a value from cache, or compute and cache it if missing.
   * The core cache-aside pattern.
   */
  async getOrSet<T>(
    key:     string,
    fetch:   () => Promise<T>,
    ttl:     number,            // seconds
    options: {
      skipCache?:     boolean;   // bypass for debugging or forced refresh
      compress?:      boolean;   // compress large values before storing
    } = {},
  ): Promise<T> {
    if (options.skipCache) return fetch();

    const cached = await this.redis.get(key);
    if (cached !== null) {
      try {
        return JSON.parse(cached) as T;
      } catch {
        // Corrupted cache entry — delete and recompute
        this.logger.warn(`Corrupted cache entry for key: ${key}`);
        await this.redis.del(key);
      }
    }

    const value = await fetch();

    // Only cache non-null values (caching null can mask missing-data bugs)
    if (value !== null && value !== undefined) {
      const serialised = JSON.stringify(value);

      // Sanity check: don't cache values that are too large (> 1MB)
      if (Buffer.byteLength(serialised) > 1_048_576) {
        this.logger.warn(`Value too large to cache for key: ${key} (${Buffer.byteLength(serialised)} bytes)`);
        return value;
      }

      await this.redis.setex(key, ttl, serialised);
    }

    return value;
  }

  async invalidate(key: string): Promise<void> {
    await this.redis.del(key);
  }

  async invalidatePattern(pattern: string): Promise<void> {
    // SCAN is non-blocking; use instead of KEYS in production
    const keys = await this.scanKeys(pattern);
    if (keys.length > 0) {
      await this.redis.del(...keys);
    }
  }

  async invalidateMany(keys: string[]): Promise<void> {
    if (keys.length > 0) {
      await this.redis.del(...keys);
    }
  }

  // SCAN-based key listing — safe for production (non-blocking, unlike KEYS)
  private async scanKeys(pattern: string): Promise<string[]> {
    const keys: string[] = [];
    let cursor           = '0';

    do {
      const [nextCursor, batch] = await this.redis.scan(cursor, 'MATCH', pattern, 'COUNT', 100);
      keys.push(...batch);
      cursor = nextCursor;
    } while (cursor !== '0');

    return keys;
  }

  // Atomic get-or-set using Lua script — prevents race conditions on cold miss
  async atomicGetOrSet<T>(key: string, fetch: () => Promise<T>, ttl: number): Promise<T> {
    const lockKey   = `lock:${key}`;
    const lockAcquired = await this.redis.set(lockKey, '1', 'EX', 30, 'NX');

    if (!lockAcquired) {
      // Poll until the other process has written the value
      for (let i = 0; i < 10; i++) {
        await new Promise(r => setTimeout(r, 50 * (i + 1)));
        const cached = await this.redis.get(key);
        if (cached !== null) return JSON.parse(cached) as T;
      }
      // Fallback: compute directly if lock wait times out
      return fetch();
    }

    try {
      const value     = await fetch();
      await this.redis.setex(key, ttl, JSON.stringify(value));
      return value;
    } finally {
      await this.redis.del(lockKey);
    }
  }
}
```

## Section 4: Cache Key Design

**Q10. What are the principles of good cache key design, and what are the common mistakes?**
A: A cache key is the identifier that maps a request to a cached value. Good key design determines whether the cache correctly distinguishes different data (no collisions) while grouping equivalent data (high hit rate).

**Principle 1 — Include all dimensions that affect the result:**
```typescript
// BAD: only includes loanId, missing userId — different users share the same cache entry
const key = `loan:${loanId}`;

// GOOD: includes all cache dimensions
const key = `loan:${tenantId}:${userId}:${loanId}`;

// For reference data that's the same for all users:
const key = `scheme:${schemeId}:v${version}`;  // version makes invalidation explicit

// For user-specific computed results:
const key = `eligibility:${tenantId}:${userId}:bureau:${bureauPullId}`;
// bureauPullId ensures the eligibility result is tied to a specific bureau snapshot
```

**Principle 2 — Include filter and sort parameters for list queries:**
```typescript
// Caching a paginated list — key must include all query dimensions
const key = [
  'loans',
  tenantId,
  `status:${filters.status ?? 'all'}`,
  `officer:${filters.assignedTo ?? 'all'}`,
  `page:${page}`,
  `limit:${limit}`,
].join(':');
// Result: 'loans:tenant-xyz:status:pending:officer:all:page:1:limit:20'
```

**Principle 3 — Namespace to prevent cross-service or cross-tenant collisions:**
```typescript
// In a multi-service Redis cluster, prefix all keys with the service name
const key = `loans-service:scheme:${schemeId}`;

// For multi-tenant applications, tenant isolation in key is mandatory
const key = `${this.SERVICE_NAME}:${tenantId}:scheme:${schemeId}`;
```

**Principle 4 — Keep keys short enough to be efficient:**
Redis keys are stored in memory. Long keys (> 200 bytes) waste memory and slow key comparison. If the natural key would be very long (many filter parameters), hash it:
```typescript
import { createHash } from 'node:crypto';

function hashFilters(filters: object): string {
  return createHash('sha256')
    .update(JSON.stringify(filters))  // deterministic serialisation
    .digest('hex')
    .slice(0, 16);  // 64-bit prefix — collision-resistant for cache purposes
}

const key = `loans:${tenantId}:${hashFilters(filters)}`;
```

**Common mistakes:**

```typescript
// MISTAKE 1: Mutable data in the key (key changes with every write)
const key = `loan:${loanId}:updatedAt:${loan.updatedAt}`;
// This generates a unique key on every update — old keys are never hit; pure writes, no reads

// MISTAKE 2: Non-deterministic serialisation
const key = `filters:${JSON.stringify(req.query)}`;
// req.query parameter order is not deterministic — {a:1, b:2} and {b:2, a:1}
// produce different keys for identical queries
// FIX: sort keys before serialising
const key = `filters:${JSON.stringify(Object.fromEntries(Object.entries(req.query).sort()))}`;

// MISTAKE 3: Including secrets or PII in cache keys
const key = `user:${user.panNumber}:eligibility`;  // PAN number in Redis key — logged, monitored
// FIX: use the user ID (opaque, non-sensitive)
const key = `user:${user.id}:eligibility`;

// MISTAKE 4: Missing tenant isolation
const key = `active-loans:page:1`;  // all tenants share this key — data leakage
// FIX:
const key = `tenant:${tenantId}:active-loans:page:1`;
```

**Q11. How do you design cache keys for multi-dimensional query caches without key explosion?**
A: A list endpoint with N optional filters produces up to 2^N possible filter combinations, each of which is a distinct cache key. With 8 filters, that's 256 possible keys per user — most of which will never be hit, wasting Redis memory.

**Strategy 1 — Cache only the most common filter combinations:**
Analyse actual query patterns from `pg_stat_statements` or APM data. In a loan officer dashboard, 80% of queries might be: `status=pending`, `status=approved`, and `status=all`. Cache these three explicitly; fall through to the database for rare combinations:

```typescript
async getLoans(tenantId: string, filters: LoanFilter): Promise<LoanDto[]> {
  const CACHEABLE_PRESETS = new Set(['pending', 'approved', 'all']);

  // Only cache standard presets; pass unusual filters directly to DB
  if (filters.status && !CACHEABLE_PRESETS.has(filters.status)) {
    return this.loanRepo.findWithFilters(tenantId, filters);  // no cache
  }

  const key = `loans:${tenantId}:status:${filters.status ?? 'all'}`;
  return this.cache.getOrSet(key, () =>
    this.loanRepo.findWithFilters(tenantId, filters), 60
  );
}
```

**Strategy 2 — Hierarchical invalidation with tag-based cache:**
Tag cache entries with the dimensions they depend on. When a dimension changes, invalidate all entries with that tag. This avoids enumerating all possible keys:

```typescript
// Store cache entry with tags
await this.redis.setex(`cache:${key}`, ttl, value);
// Also record the key under each tag for bulk invalidation
await this.redis.sadd(`tag:tenant:${tenantId}`, `cache:${key}`);
await this.redis.sadd(`tag:status:pending`, `cache:${key}`);

// Invalidation: when any loan changes to 'approved', invalidate all 'status:pending' entries
async invalidateByStatus(status: string): Promise<void> {
  const affectedKeys = await this.redis.smembers(`tag:status:${status}`);
  if (affectedKeys.length > 0) {
    await this.redis.del(...affectedKeys);
  }
  await this.redis.del(`tag:status:${status}`);
}
```

**Strategy 3 — Accept lower hit rates for complex filter combinations:**
For endpoints with many optional filters, accept that the cache hit rate will be low for complex filter combinations. Set the TTL short enough that staleness is acceptable but long enough to absorb burst traffic on popular combinations (e.g., a load test or a spike in users opening the same filter preset):

```typescript
// For complex filter combinations: short TTL (30s), high miss rate acceptable
// The benefit is absorbing burst traffic, not long-term caching
const key = `loans:${tenantId}:${hashFilters(filters)}`;
return this.cache.getOrSet(key, () => this.loanRepo.findWithFilters(tenantId, filters), 30);
```

## Section 5: In-Process Caching

**Q12. When is an in-process (in-memory) cache preferable to Redis, and how do you implement one safely?**
A: Redis adds a network round-trip to every cache operation — typically 1–3ms for a local Redis instance, 5–15ms for a cross-AZ Redis in a cloud environment. For data that is read thousands of times per second with very low write frequency, an in-process cache eliminates this overhead entirely.

**When in-process caching is appropriate:**
- The data is the same for all users (reference data, configuration) — no per-user isolation required.
- The data is small enough to hold in process memory without pressure.
- Eventual consistency across multiple application instances is acceptable — each instance may hold a slightly different version during the TTL window.
- The per-operation cost is small but high frequency makes even the Redis round-trip significant.

```typescript
// In-process cache using lru-cache
import { LRUCache } from 'lru-cache';

@Injectable()
export class LoanSchemeCache {
  private readonly store = new LRUCache<string, LoanScheme>({
    max:  500,               // at most 500 scheme entries in memory
    ttl:  5 * 60 * 1000,    // 5-minute TTL (milliseconds for lru-cache)
    allowStale: false,       // don't serve after expiry — wait for fresh value
  });

  constructor(private readonly schemeRepo: LoanSchemeRepository) {}

  async get(schemeId: string): Promise<LoanScheme | null> {
    const cached = this.store.get(schemeId);
    if (cached !== undefined) return cached;

    const scheme = await this.schemeRepo.findOne(schemeId);
    if (scheme) this.store.set(schemeId, scheme);
    return scheme;
  }

  invalidate(schemeId: string): void {
    this.store.delete(schemeId);
    // Note: this only invalidates in THIS process instance
    // Other instances still hold the old value until their TTL expires
    // For immediate cross-instance invalidation, use Redis pub/sub (Q13)
  }
}
```

**Sizing the in-process cache:**
The maximum number of entries (`max`) multiplied by the average entry size must fit comfortably within the process's memory. For a NestJS service with `--max-old-space-size=1536` (1.5GB), the in-process cache should use at most ~100MB — about 6% of available heap. Exceeding this pressures the garbage collector and can cause GC pauses.

**When in-process caching is NOT appropriate:**
- Per-user data — each instance caches its own subset of users, and a user routed to a different instance gets a cache miss. The hit rate is 1/N where N is instance count.
- Data requiring immediate consistency across instances — a revoked session or a changed permission level must be immediately visible everywhere, not within the in-process TTL window.
- Large data sets — 100,000 loan records in memory per instance × 10 instances = significant memory pressure.

**Q13. How do you implement cross-instance cache invalidation for in-process caches in a horizontally-scaled deployment?**
A: When an admin updates a loan scheme, the in-process cache on every running instance must be invalidated — not just the instance that handled the write request. Redis pub/sub provides a lightweight broadcast mechanism for this:

```typescript
// cache-sync.service.ts — Redis pub/sub for cross-instance invalidation
@Injectable()
export class CacheSyncService implements OnModuleInit, OnModuleDestroy {
  private subscriber: Redis;
  private readonly CHANNEL = 'cache:invalidation';

  constructor(
    @InjectRedis() private readonly publisher: Redis,
    private readonly loanSchemeCache: LoanSchemeCache,
    private readonly userPermissionCache: UserPermissionCache,
  ) {
    // Subscriber must be a separate Redis connection (subscribed connections
    // cannot send other commands in ioredis)
    this.subscriber = new Redis(process.env.REDIS_URL!);
  }

  async onModuleInit(): Promise<void> {
    await this.subscriber.subscribe(this.CHANNEL);

    this.subscriber.on('message', (_channel, message) => {
      const { type, id } = JSON.parse(message) as { type: string; id: string };

      switch (type) {
        case 'loan-scheme':
          this.loanSchemeCache.invalidate(id);
          break;
        case 'user-permission':
          this.userPermissionCache.invalidate(id);
          break;
        default:
          this.logger.warn(`Unknown cache invalidation type: ${type}`);
      }
    });
  }

  async broadcast(type: string, id: string): Promise<void> {
    await this.publisher.publish(this.CHANNEL, JSON.stringify({ type, id }));
    // This reaches ALL subscribed instances, including the current one
  }

  async onModuleDestroy(): Promise<void> {
    await this.subscriber.unsubscribe(this.CHANNEL);
    this.subscriber.disconnect();
  }
}

// Usage: when a scheme is updated
async updateScheme(schemeId: string, dto: UpdateSchemeDto): Promise<void> {
  await this.schemeRepo.save({ id: schemeId, ...dto });
  await this.cacheSyncService.broadcast('loan-scheme', schemeId);
  // All 10 running instances receive this and evict their cached scheme entry
}
```

This pattern combines the performance of in-process caching (zero Redis round-trip for reads) with the consistency of centrally-coordinated invalidation (Redis pub/sub ensures all instances are notified). The invalidation message is tiny (a few bytes) and the pub/sub channel handles tens of thousands of messages per second.

## Section 6: Cache Metrics and Observability

**Q14. What metrics must you track for a caching layer, and how do you use them to make cache sizing and TTL decisions?**
A: Cache metrics are the evidence base for tuning decisions. Without them, TTL and eviction policy choices are guesswork.

**Core metrics:**

```typescript
// cache.service.ts — instrument every cache operation
async getOrSet<T>(key: string, fetch: () => Promise<T>, ttl: number): Promise<T> {
  const cached = await this.redis.get(key);

  if (cached !== null) {
    // Cache HIT
    this.metrics.increment('cache.hit', { key_prefix: this.getPrefix(key) });
    return JSON.parse(cached) as T;
  }

  // Cache MISS
  this.metrics.increment('cache.miss', { key_prefix: this.getPrefix(key) });

  const start = performance.now();
  const value = await fetch();
  const fetchDuration = performance.now() - start;

  this.metrics.histogram('cache.fetch_duration', fetchDuration, {
    key_prefix: this.getPrefix(key),
  });

  if (value !== null) {
    await this.redis.setex(key, ttl, JSON.stringify(value));
  }

  return value;
}

// Derived metric: cache hit rate = hits / (hits + misses)
// Target: > 80% for reference data, > 50% for user-specific data
```

**Redis INFO metrics to monitor:**
```bash
redis-cli INFO stats | grep -E 'keyspace_hits|keyspace_misses|evicted_keys|rejected_connections'
redis-cli INFO memory | grep -E 'used_memory_human|mem_fragmentation_ratio|maxmemory'
redis-cli INFO clients | grep 'connected_clients'

# Key metrics to alert on:
# keyspace_hits / (keyspace_hits + keyspace_misses) < 0.7 → cache ineffective
# evicted_keys > 0 → cache is full; entries evicted before TTL → miss rate increases
# used_memory > 80% of maxmemory → approaching eviction threshold; resize the cache
# mem_fragmentation_ratio > 1.5 → memory fragmentation; consider MEMORY PURGE or restart
```

**Using hit rate to tune TTL:**
```
Hit rate < 50% for reference data:
  → TTL may be too short (entries expire before being re-requested)
  → OR the key space is too fragmented (too many unique keys per "entity")
  → Increase TTL; audit key design for unnecessary uniqueness

Hit rate = 95%+ for all data including user-specific:
  → TTL may be too long (serving very stale data)
  → Check staleness complaints in support tickets or data freshness requirements

Evicted keys > 0 consistently:
  → Redis maxmemory is too small for the working set at current TTL
  → Either: increase Redis memory
  → Or: reduce TTL (shorter-lived entries take less space at any moment)
  → Or: add more selective caching (only cache the hot subset)
```

**Using fetch duration to prioritise:**
```
avg fetch duration > 500ms → high-priority cache candidate; even a 30% hit rate
                              eliminates 150ms+ from the average response

avg fetch duration < 10ms  → low priority; Redis round-trip (~3ms) is significant
                              relative to the saved operation
```

**Q15. What is cache poisoning, and how do you prevent it in a multi-tenant application?**
A: Cache poisoning occurs when incorrect, malicious, or adversarially-crafted data is stored in the cache, causing subsequent legitimate requests to receive incorrect responses. In a multi-tenant application, an additional risk is tenant data leakage — Tenant A's data appearing in Tenant B's cache entry.

**Sources of cache poisoning:**

**1. Missing tenant dimension in cache key:**
```typescript
// VULNERABLE: loan endpoint caches by loan ID only
// Tenant A fetches loan-123 → cached as 'loan:loan-123'
// Tenant B requests loan-123 → gets Tenant A's loan data from cache
const key = `loan:${loanId}`;  // WRONG

// SAFE: include tenant in every cache key
const key = `loan:${tenantId}:${loanId}`;  // tenant isolation enforced
```

**2. Caching error responses:**
```typescript
// VULNERABLE: caches the error response permanently
try {
  const user = await this.kycService.getStatus(userId);
  await this.redis.setex(key, 3600, JSON.stringify(user));
} catch (err) {
  await this.redis.setex(key, 3600, JSON.stringify({ error: err.message }));
  // Next request gets the cached error — service recovers but cache still returns error
}

// SAFE: never cache errors; only cache successful responses
try {
  const user = await this.kycService.getStatus(userId);
  await this.redis.setex(key, 3600, JSON.stringify(user));
  return user;
} catch (err) {
  // Don't write to cache on error — next request retries the real service
  throw err;
}
```

**3. Caching with untrusted client input as part of the key:**
```typescript
// VULNERABLE: sort parameter from client is included in the key without sanitisation
// Client sends sort=-__proto__.polluted=injected
const key = `loans:${tenantId}:sort:${req.query.sort}`;

// SAFE: validate all inputs before using them in cache keys
const VALID_SORT_VALUES = new Set(['createdAt', '-createdAt', 'amount', '-amount']);
const sort = VALID_SORT_VALUES.has(req.query.sort) ? req.query.sort : 'createdAt';
const key  = `loans:${tenantId}:sort:${sort}`;
```

**4. Replay attacks using old cache entries:**
```typescript
// A cache entry containing an old JWT or session token could replay an expired credential
// Mitigate: never cache credentials or tokens; cache the validated identity instead

// WRONG: caching the raw JWT result without re-validating on expiry
// CORRECT: cache the verified user profile for the JWT's remaining lifetime only
const jwtExpiry = jwtPayload.exp - Math.floor(Date.now() / 1000);
const cacheTtl  = Math.min(jwtExpiry, 300);  // cache for min(jwt_remaining, 5 minutes)
if (cacheTtl > 0) {
  await this.redis.setex(`auth:${jwtId}`, cacheTtl, JSON.stringify(userProfile));
}
```

```
Total:                      550ms
```

**Q17. Scenario: "A new engineer added Redis caching to the loan application detail endpoint to fix a 300ms query. After the deployment, some loan officers see outdated status for 10 minutes after approving a loan. How do you fix this and prevent recurrence?"**
A: This is the classic cache invalidation miss — the cache was added for reads but the write path was not updated to invalidate the cache.

**Diagnosis:**
```typescript
// What was added (correct idea, incomplete implementation)
@Get(':id')
async getLoan(@Param('id') id: string): Promise<LoanDto> {
  return this.cache.getOrSet(
    `loan:${id}`,
    () => this.loanRepo.findOne(id),
    600,  // 10-minute TTL ← explains the 10-minute stale window
  );
}

// What was NOT updated:
@Patch(':id/status')
async updateStatus(@Param('id') id: string, @Body() dto: UpdateStatusDto): Promise<void> {
  await this.loanRepo.update(id, { status: dto.status });
  // Missing: await this.cache.invalidate(`loan:${id}`);
}
```

**Fix — add invalidation to every write path:**
```typescript
// loan-application.service.ts
async updateStatus(loanId: string, status: string): Promise<void> {
  await this.loanRepo.update(loanId, { status });

  // Invalidate all cache keys that include this loan's data
  await Promise.all([
    this.cache.invalidate(`loan:${loanId}`),                            // detail view
    this.cache.invalidate(`officer:${loan.assignedTo}:pending-count`),  // count cache
    this.cache.invalidate(`user:${loan.userId}:active-loans`),          // user's loan list
  ]);
}
```

**Systematic fix — audit all write paths:**
```typescript
// Create a CacheInvalidationService that centralises the invalidation logic
// and makes it impossible to add a write without considering invalidation

@Injectable()
export class LoanCacheInvalidationService {
  constructor(private readonly cache: CacheService) {}

  // Single method: "when a loan changes, invalidate these keys"
  // Every write path calls this — it's the contract
  async onLoanChanged(loan: LoanApplication): Promise<void> {
    await this.cache.invalidateMany([
      `loan:${loan.tenantId}:${loan.id}`,
      `officer:${loan.tenantId}:${loan.assignedTo}:pending-count`,
      `user:${loan.tenantId}:${loan.userId}:active-loans`,
      `branch:${loan.tenantId}:${loan.branchId}:dashboard`,
    ]);
  }
}

// All write paths inject and call this service:
async updateStatus(loanId: string, status: string): Promise<void> {
  const loan = await this.loanRepo.findOne(loanId);
  await this.loanRepo.update(loanId, { status });
  await this.invalidationService.onLoanChanged({ ...loan, status });
}
```

**Prevention — architectural guideline:**
Add a PR checklist item: "If this PR writes to a database table that has cached reads, does it also invalidate those caches?" Add a test that asserts cache invalidation happens on write:


**Q18. How do you decide whether to cache the raw database result, the DTO, or the serialised HTTP response?**
A: The choice of what to cache determines how much processing is avoided on a cache hit and how broadly the cached value can be reused:

**Cache the raw database entity:**
```typescript
// Cache the TypeORM entity
const loan = await this.cache.getOrSet(`loan:${id}`, () => this.repo.findOne(id), 60);
// Transform to DTO on every request (even cache hits)
return this.mapper.toDto(loan);
```
Pros: the same cached entity can be used by different code paths that need different subsets of fields. Transformation logic changes don't require cache invalidation.
Cons: transformation CPU cost is paid on every request including cache hits. For complex transformations, this can be significant.

**Cache the DTO:**
```typescript
// Cache the already-transformed DTO
const dto = await this.cache.getOrSet(
  `loan:dto:${id}`,
  async () => this.mapper.toDto(await this.repo.findOne(id)),
  60,
);
return dto;
```
Pros: transformation cost is paid only on cache miss. Maximum CPU saving on cache hits.
Cons: if the DTO shape changes (new field, renamed field), cached DTOs may have the wrong shape until TTL expiry. Version the cache key on DTO schema changes: `loan:dto:v2:${id}`.

**Cache the serialised response:**
```typescript
// Cache the JSON string directly (skip JSON.stringify on cache hit)
const json = await this.cache.getOrSet(
  `loan:json:${id}`,
  async () => JSON.stringify(this.mapper.toDto(await this.repo.findOne(id))),
  60,
);
res.setHeader('Content-Type', 'application/json');
res.send(json);  // send pre-serialised JSON
```
Pros: eliminates `JSON.stringify` (can be significant for large objects). The response is served byte-for-byte from cache.
Cons: cannot customise the response per-request (e.g., different field visibility based on user role). Not suitable for any endpoint with per-user response variation.

**Rule of thumb:**
- Simple entities with cheap transformation → cache the DTO.
- Complex transformation with CPU cost → cache the DTO.
- Static public data with zero per-request variation → cache the serialised response.
- Data that must be filtered or shaped per user role → cache the raw entity; transform per-request.
- Never cache at a level that breaks multi-tenancy or per-user visibility rules.

| `evicted_keys` > 0 | Cache is undersized for current TTL |
| `mem_fragmentation_ratio` > 1.5 | Redis memory fragmentation — needs purge or restart |
| Stale data bugs in production | Missing invalidation on a write path |
| Cache stampede | Need mutex / probabilistic expiry / stale-while-revalidate |

**Tip for the interview:** At 5 YOE, caching questions move straight to "how do you decide what to cache?" and "what went wrong when this cache caused stale data?" Know the two-property test cold — expensive to compute AND read/write ratio heavily biased toward reads — and be ready to apply it to a specific example rather than stating it abstractly. The cache invalidation miss scenario (Q17) — caching the read but forgetting to invalidate the write — is by far the most common real-world caching bug; having a concrete fix (centralised `CacheInvalidationService` + test asserting invalidation happens) signals operational experience. For fintech interviews: the distinction between "acceptable staleness" (pending count on a dashboard) and "unacceptable staleness" (outstanding balance for a credit decision or a revoked session for authentication) is the senior-level nuance interviewers are listening for — the same mechanism (Redis + TTL) is appropriate for one and dangerous for the other, and knowing the difference without being told which is which is the senior signal.
