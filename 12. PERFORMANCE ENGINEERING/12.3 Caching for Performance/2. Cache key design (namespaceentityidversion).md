# Performance: Cache Key Design — Interview Q&A (5 YOE Level)

---

## Section 1: Why Cache Key Design Matters

**Q1. What is a cache key, why is its design a critical engineering decision rather than a naming convention, and what are the four failure modes of poorly designed keys?**
A: A cache key is the string identifier used to store and retrieve a cached value. It is the contract between the writer and the reader of cached data — if any part of this contract is wrong, the cache either returns stale data (incorrect behavior) or fails to return cached data at all (wasted performance investment). Key design is a correctness and performance decision, not a cosmetic one.

**What a cache key must encode:**
```
A cache key must capture EVERYTHING that differentiates one cached value from another.
If two requests should return different data, they must have different cache keys.
If two requests should return identical data, they must have the same cache key.

The fundamental question for every key: "What dimensions determine the correct value?"

Example — a loan detail response:
  Dimensions that affect the correct response:
    1. Which loan?          → loan_id
    2. Whose perspective?   → user_id (customer sees masked data; admin sees full data)
    3. Which version?       → schema_version (v1 response shape vs. v2 response shape)
    4. Which tenant?        → tenant_id (multi-tenant: tenant A cannot see tenant B's loans)
    5. Which locale?        → locale (INR formatting vs. USD formatting)

  If you only key on loan_id:
    User A requests loan L001 → cache stores {masked data for user A}
    Admin requests loan L001  → cache HITS on the same key → returns masked data to admin
    → Admin sees customer view (wrong) or customer sees admin view (security breach)
```

**The four failure modes:**

**Failure Mode 1 — Key collision (most dangerous):**
```
Two distinct entities hash to the same key.
Result: one entity's data is returned for another entity's request.

Example:
  User ID "1" and Loan ID "1" both hit the same key: "cache:1"
  user:get stores User{id:1, name:"Alice"} under key "cache:1"
  loan:get checks key "cache:1" → returns User{id:1, name:"Alice"} as a Loan
  → Runtime error or silent data corruption depending on how types are used

Fix: namespace by entity type — "user:1" vs. "loan:1"
```

**Failure Mode 2 — Cache pollution (stale data served as fresh):**
```
A cached value is valid for a subset of requests but served to all requests
matching the key, when those requests should receive different values.

Example:
  Cache key: "loans:list:page:1"
  User A requests page 1 → stores {loans belonging to user A}
  User B requests page 1 → cache HIT → receives user A's loans
  → Privacy violation; data breach

Fix: include user context in key — "loans:user:${userId}:page:1"
```

**Failure Mode 3 — Cache miss storm (thundering herd):**
```
All requests for a resource miss simultaneously because the key was
invalidated (TTL expired, explicit delete) while the value was in high demand.
Result: hundreds of concurrent requests all go to the DB simultaneously.

This is partially a key design problem: if invalidation granularity is wrong,
you invalidate too much at once → all miss → herd.

Example:
  Key: "all:products" (contains ALL 10,000 products)
  TTL expires at 03:00 → 500 concurrent requests all miss → 500 DB queries
  DB dies under load

Fix: granular keys — "product:${id}" — invalidate one product at a time
     + probabilistic early expiry (see Q11) to prevent synchronized expiry
```

**Failure Mode 4 — Phantom invalidation (failing to invalidate what should expire):**
```
A stale value remains cached because the invalidation used a different key
format than the one used to store it.

Example:
  Storage key:      "loan:profile:${loanId}"
  Invalidation key: "loan:${loanId}:profile"  ← different key format
  → Stale data persists indefinitely despite "invalidation"
  → Updates to the loan are never reflected in the cache

Fix: single authoritative key builder function used by both reader and writer
```

## Section 2: The Namespace:Entity:Id:Version Pattern

**Q2. Walk through the `namespace:entity:id:version` pattern — what each segment encodes, why each is necessary, and how they compose for real fintech entities.**
A: The `namespace:entity:id:version` pattern is a hierarchical key structure where each segment narrows the scope of the cached value. Each segment is necessary because it represents an independent dimension along which two cached values can legitimately differ:

**Anatomy of the key:**
```
namespace : entity  : id                    : version
    │           │          │                      │
    │           │          │                      └── Schema/format version
    │           │          │                          Distinguishes v1 response
    │           │          │                          shape from v2 response shape
    │           │          │                          Also: "sub-resource" within entity
    │           │          │
    │           │          └── Unique identifier of the specific instance
    │           │              loan_id, user_id, payment_id, etc.
    │           │              May be composite: userId:loanId for a scoped resource
    │           │
    │           └── Entity type
    │               loan, user, emi, document, tenant, product
    │               Prevents collisions between entities sharing the same ID space
    │
    └── Namespace
        Application, environment, or service scope
        Prevents collisions between services sharing one Redis instance
        myfintech:prod, loans-service, payments-service
```

**Building real keys for a fintech platform:**
```typescript
// Key builder — the single authoritative source of truth for key format
// Every cache read and write goes through this builder
// Ensures storage and invalidation always use identical keys

export class CacheKeyBuilder {
  constructor(
    private readonly namespace: string,  // e.g., 'loanservice'
    private readonly env: string,         // e.g., 'prod', 'staging'
  ) {}

  // ── User entity keys ──────────────────────────────────────────────────

  // Full user profile (all fields; admin view)
  userProfile(userId: string): string {
    return `${this.namespace}:${this.env}:user:${userId}:profile:v2`;
  }

  // Public user summary (masked fields; customer-facing)
  userSummary(userId: string): string {
    return `${this.namespace}:${this.env}:user:${userId}:summary:v1`;
  }

  // ── Loan entity keys ──────────────────────────────────────────────────

  // Loan detail (single loan)
  loanDetail(loanId: string): string {
    return `${this.namespace}:${this.env}:loan:${loanId}:detail:v3`;
  }

  // Loan list for a user (paginated)
  userLoanList(userId: string, page: number, pageSize: number): string {
    return `${this.namespace}:${this.env}:loan:user:${userId}:list:p${page}:ps${pageSize}:v2`;
  }

  // Loan list with filters (status, date range, amount range)
  userLoanListFiltered(
    userId: string,
    filters: LoanListFilters,
    page: number,
  ): string {
    // Filters must be deterministically serialized — same filters = same key
    const filterHash = this.hashFilters(filters);
    return `${this.namespace}:${this.env}:loan:user:${userId}:list:f${filterHash}:p${page}:v2`;
  }

  // Loan eligibility result (expensive computation)
  loanEligibility(userId: string, productId: string, amount: number): string {
    return `${this.namespace}:${this.env}:eligibility:${userId}:${productId}:amt${amount}:v1`;
  }

  // ── Payment/EMI keys ──────────────────────────────────────────────────

  // EMI schedule for a loan
  emiSchedule(loanId: string): string {
    return `${this.namespace}:${this.env}:emi:loan:${loanId}:schedule:v2`;
  }

  // Next EMI due for a user (frequently accessed; short TTL)
  nextEmiDue(userId: string): string {
    return `${this.namespace}:${this.env}:emi:user:${userId}:next:v1`;
  }

  // ── Lender/product configuration keys ────────────────────────────────

  // Lender rules (changes rarely; long TTL)
  lenderRules(lenderCode: string): string {
    return `${this.namespace}:${this.env}:lender:${lenderCode}:rules:v4`;
  }

  // Available loan products for a lender
  lenderProducts(lenderCode: string): string {
    return `${this.namespace}:${this.env}:lender:${lenderCode}:products:v2`;
  }

  // ── Computed/aggregated keys ──────────────────────────────────────────

  // Credit score (fetched from external bureau; expensive; long TTL)
  creditScore(userId: string): string {
    return `${this.namespace}:${this.env}:credit:${userId}:score:v1`;
  }

  // Fraud risk assessment (changes with new signals; short TTL)
  fraudRisk(userId: string): string {
    return `${this.namespace}:${this.env}:fraud:${userId}:risk:v2`;
  }

  // ── Helper: deterministic filter serialization ────────────────────────
  private hashFilters(filters: LoanListFilters): string {
    // Sort keys before hashing — ensures {status:'A',type:'B'} === {type:'B',status:'A'}
    const sorted = Object.keys(filters)
      .sort()
      .filter(k => filters[k as keyof LoanListFilters] !== undefined)
      .map(k => `${k}:${filters[k as keyof LoanListFilters]}`)
      .join('|');
    // For short filter strings: use the string directly (readable in Redis)
    // For long or sensitive filters: use a hash (SHA-256 truncated to 8 chars)
    if (sorted.length <= 40) return sorted.replace(/[^a-zA-Z0-9:|]/g, '_');
    return createHash('sha256').update(sorted).digest('hex').slice(0, 8);
  }
}

// Instantiation — one per service
const keys = new CacheKeyBuilder('loanservice', process.env.NODE_ENV ?? 'prod');

// Usage — identical key regardless of where in the codebase it's called
const loanKey         = keys.loanDetail('loan-abc-123');
const userLoansKey    = keys.userLoanList('user-xyz', 1, 20);
const eligibilityKey  = keys.loanEligibility('user-xyz', 'product-001', 500000);

// Generated key examples:
// loanservice:prod:loan:loan-abc-123:detail:v3
// loanservice:prod:loan:user:user-xyz:list:p1:ps20:v2
// loanservice:prod:eligibility:user-xyz:product-001:amt500000:v1
// loanservice:prod:lender:HDFC001:rules:v4
```

**Q3. What does the version segment in a cache key represent, when do you increment it, and what are the two distinct versioning concerns it addresses?**
A: The version segment serves two separate purposes that happen to share the same mechanism: schema versioning (the shape of the cached value has changed) and intentional mass invalidation (you want to invalidate all keys of a type without individual deletes):

**Purpose 1 — Schema versioning (breaking changes to the cached value format):**
```typescript
// Scenario: you add a required field to the loan response shape

// v2 loan detail response (previously cached):
{
  "id": "loan-abc",
  "amount": 500000,
  "status": "ACTIVE"
}

// v3 loan detail response (new shape):
{
  "id": "loan-abc",
  "amount": 500000,
  "status": "ACTIVE",
  "interestRate": 14.5,        // ← New required field
  "disbursementDate": "2024-01" // ← New required field
}

// If the cache still holds v2 shaped data and the application now expects v3:
const loan = await cache.get(keys.loanDetail(loanId));
// loan.interestRate → undefined (not in cached v2 shape)
// loan.disbursementDate → undefined
// Application tries to display interestRate: shows "NaN%" or crashes

// Fix: increment the version segment at deploy time
// Old key: loanservice:prod:loan:loan-abc:detail:v2 → ignored (new code reads v3 key)
// New key: loanservice:prod:loan:loan-abc:detail:v3 → misses → fetches fresh data

// All v2 keys become orphaned (never read again)
// They expire naturally via their TTL — no mass delete needed
// Zero deployment risk: new code never reads old incompatible format

// Version bump procedure:
// 1. Change the version suffix in CacheKeyBuilder.loanDetail() from 'v2' to 'v3'
// 2. Deploy — new code immediately reads/writes v3 keys
// 3. v2 keys are never read again; expire within their TTL window
// 4. After TTL elapses: v2 keys gone from Redis, no cleanup script needed
```

**Purpose 2 — Intentional mass invalidation (invalidate all instances without enumeration):**
```typescript
// Scenario: lender rules changed globally (all lender rule caches are stale)
// Lender codes: HDFC001, ICICI002, AXIS003, ... (1,000+ lenders)
// Invalidating individually: 1,000 REDIS DEL commands — slow, error-prone

// WITHOUT version segment: must enumerate and delete all matching keys
const lenderKeys = await redis.keys('loanservice:prod:lender:*:rules');
// redis.keys() is O(N) — scans entire keyspace — blocks Redis during scan
// On a Redis instance with 10 million keys: takes seconds; blocks all other ops
await redis.del(...lenderKeys); // Delete all matches

// WITH version segment: bump the version — all old keys become effectively deleted
// Step 1: change lenderRules() in CacheKeyBuilder from 'v4' to 'v5'
// Step 2: store the current version in Redis (or app config):
await redis.set('loanservice:prod:lender:rules:current_version', 'v5');

// OR: embed the version in a config that all services read at startup:
// LENDER_RULES_CACHE_VERSION=v5 (environment variable; change → redeploy)

// After the version bump:
// Old keys: loanservice:prod:lender:*:rules:v4 → never read again → expire naturally
// New keys: loanservice:prod:lender:*:rules:v5 → all miss initially → refill from DB

// This is a LOGICAL DELETE without any Redis write commands
// No KEYS scan, no DEL commands, no blocking Redis operation
// Trade-off: v4 keys remain in Redis until their TTL expires (consuming memory)
// For a 24-hour TTL on lender rules: all v4 keys gone within 24 hours

// Dynamic version stored in Redis (no redeploy needed):
class DynamicVersionedKeyBuilder {
  private versionCache = new Map<string, string>();

  async lenderRules(lenderCode: string): Promise<string> {
    const version = await this.getCurrentVersion('lender:rules');
    return `loanservice:prod:lender:${lenderCode}:rules:${version}`;
  }

  async bumpVersion(scope: string): Promise<void> {
    const newVersion = `v${Date.now()}`; // Timestamp as version
    await redis.set(`versions:${scope}`, newVersion);
    this.versionCache.delete(scope); // Invalidate local version cache
  }

  private async getCurrentVersion(scope: string): Promise<string> {
    if (this.versionCache.has(scope)) return this.versionCache.get(scope)!;
    const version = await redis.get(`versions:${scope}`) ?? 'v1';
    this.versionCache.set(scope, version);
    return version;
  }
}
```

## Section 3: Namespace Design for Multi-Service Systems

**Q4. How do you design cache key namespaces when multiple services share a single Redis cluster, and what are the rules for preventing cross-service key collisions?**
A: In a microservices architecture, multiple services often share a Redis cluster for operational efficiency. Without namespace discipline, service A's key for "user:123" can collide with service B's key for "user:123" — even though they represent different cached data about the same user:

**The namespace hierarchy:**
```
Level 1 — Service namespace: identifies which service owns the key
  loans-service, payments-service, kyc-service, notification-service
  Rule: each service OWNS its namespace; no other service reads or writes to it
  Exception: read-through from a shared "platform" namespace for shared data

Level 2 — Environment namespace: prevents staging from hitting prod cache
  prod, staging, dev, feature-branch-123
  Rule: always include; critical for staging environments that use the same Redis

Level 3 — Entity namespace: identifies the data type within the service
  loan, user, emi, lender, product, config, session, ratelimit

Level 4 — ID: the specific instance
  UUID, composite ID, or hash

Level 5 — Sub-resource or variant (optional)
  profile, summary, list, detail, count, eligibility

Level 6 — Version: schema version for the cached value
  v1, v2, v3

Complete key format:
  {service}:{env}:{entity}:{id}:{sub-resource}:{version}
  loans:prod:loan:loan-abc-123:detail:v3
  payments:prod:payment:pay-xyz:status:v1
  kyc:staging:user:user-abc:kyc-status:v2
```

**Implementing namespace isolation with Redis cluster routing:**
```typescript
// Redis Cluster: keys are distributed across shards by hash slot
// Keys with the same hash tag {tag} always land on the same shard
// This matters for multi-key operations (MGET, pipeline, transactions)

class NamespacedCacheService {
  constructor(
    private readonly redis: Redis,
    private readonly service: string,
    private readonly env: string,
  ) {}

  // Standard key — distributed across cluster by hash of full key
  key(entity: string, id: string, subResource: string, version: string): string {
    return `${this.service}:${this.env}:${entity}:${id}:${subResource}:${version}`;
  }

  // Hash-tagged key — forces all keys with same tag onto the same shard
  // Use when you need MGET / pipeline across multiple keys for the same entity
  taggedKey(entity: string, id: string, subResource: string, version: string): string {
    // Redis hash tag: {content in braces} determines shard assignment
    // All keys with tag {loan:loan-abc-123} land on the same shard
    // Enables: MGET for loan:detail + loan:emis + loan:documents in one round trip
    return `${this.service}:${this.env}:{${entity}:${id}}:${subResource}:${version}`;
  }

  // Scan keys within a namespace (for admin/monitoring, not for invalidation in hot path)
  async scanNamespace(entityPattern: string): Promise<string[]> {
    const keys: string[] = [];
    const pattern = `${this.service}:${this.env}:${entityPattern}:*`;

    // Use SCAN instead of KEYS — non-blocking, cursor-based iteration
    let cursor = '0';
    do {
      const [nextCursor, batch] = await this.redis.scan(
        cursor,
        'MATCH', pattern,
        'COUNT', 100,  // Hint: return ~100 keys per iteration (not a hard limit)
      );
      cursor = nextCursor;
      keys.push(...batch);
    } while (cursor !== '0');

    return keys;
    // Use only for monitoring dashboards, never in the hot request path
  }
}

// Service-specific cache services with their own namespaces
const loansCache    = new NamespacedCacheService(redis, 'loans',    process.env.NODE_ENV!);
const paymentsCache = new NamespacedCacheService(redis, 'payments', process.env.NODE_ENV!);
const kycCache      = new NamespacedCacheService(redis, 'kyc',      process.env.NODE_ENV!);

// Keys generated:
// loans:prod:loan:loan-abc:detail:v3
// payments:prod:payment:pay-xyz:status:v1
// kyc:prod:user:user-abc:kyc-status:v2

// No collisions even though all three services may have a "user" entity:
// loans:prod:user:user-abc:profile:v1    ← loans service view of user
// kyc:prod:user:user-abc:profile:v2      ← KYC service view of user (different shape!)
// These are different keys → different cached values → correct behavior
```

**Q5. How do you design keys for multi-tenant systems to enforce tenant isolation at the cache layer, and what happens if you miss a tenant dimension?**
A: In a multi-tenant fintech platform (multiple lenders or businesses using the same system), the tenant dimension is a security boundary, not just a data organization concern. A cache key that omits the tenant ID can leak one tenant's data to another tenant's requests:

```typescript
// The tenant isolation failure:

// WRONG — tenant not in key
const loanListKey = `loans:prod:loan:list:page:1:v1`;
// Tenant A requests loan list → cache stores tenant A's loans under this key
// Tenant B requests loan list → cache HIT → returns tenant A's loans to tenant B
// → Data breach between tenants

// CORRECT — tenant always in key
class TenantAwareCacheKeyBuilder {
  constructor(
    private readonly service: string,
    private readonly env: string,
  ) {}

  // Tenant ID woven into the key structure — not optional
  loanList(tenantId: string, page: number, pageSize: number): string {
    return `${this.service}:${this.env}:tenant:${tenantId}:loan:list:p${page}:ps${pageSize}:v2`;
  }

  // For cross-tenant shared resources (lender config available to all tenants):
  // These legitimately don't include a tenant segment — they're shared
  lenderConfig(lenderCode: string): string {
    return `${this.service}:${this.env}:shared:lender:${lenderCode}:config:v3`;
    // 'shared' segment signals: this is intentionally cross-tenant
    // Not an omission — a deliberate design choice
  }

  // User scoped to tenant (same userId may exist in multiple tenants):
  userProfile(tenantId: string, userId: string): string {
    return `${this.service}:${this.env}:tenant:${tenantId}:user:${userId}:profile:v2`;
    // Critical: user-123 in tenant-A != user-123 in tenant-B
    // Without tenantId: tenant-A's user profile cached → tenant-B's request
    // returns tenant-A's profile → wrong data; possible PII leak
  }

  // Tenant-wide aggregates:
  tenantDashboardStats(tenantId: string): string {
    return `${this.service}:${this.env}:tenant:${tenantId}:dashboard:stats:v1`;
  }
}

// Enforcing tenant in middleware — extract from JWT; never from request body
@Injectable()
export class CacheKeyMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    // tenantId always comes from the verified JWT claim, not from the URL or body
    // This prevents a caller from supplying a different tenantId to access other tenants
    const tenantId = req.user?.tenantId;
    if (!tenantId) {
      throw new UnauthorizedException('No tenant context');
    }
    req.tenantId = tenantId;
    next();
  }
}

// Service using tenant-aware keys:
@Injectable()
export class LoanCacheService {
  constructor(
    private readonly redis: Redis,
    private readonly keyBuilder: TenantAwareCacheKeyBuilder,
  ) {}

  async getLoanList(
    tenantId: string,  // Always required — not optional
    page: number,
    pageSize: number,
  ): Promise<Loan[] | null> {
    // tenantId cannot be omitted — type signature enforces it
    const key = this.keyBuilder.loanList(tenantId, page, pageSize);
    const cached = await this.redis.get(key);
    return cached ? JSON.parse(cached) : null;
  }
}
```

## Section 4: Handling Query Parameters and Filters

**Q6. How do you design cache keys for endpoints with complex query parameters — filters, sorts, and pagination — and what is the canonical serialization problem?**
A: Query parameter caching is where key design gets genuinely difficult. The same logical request can be expressed in multiple syntactically different ways — and all representations must produce the same cache key. If they don't, identical requests miss the cache when they should hit:

**The canonical serialization problem:**
```
Client A sends:  GET /api/loans?status=ACTIVE&sort=amount&order=desc&page=1
Client B sends:  GET /api/loans?page=1&sort=amount&status=ACTIVE&order=desc
Client C sends:  GET /api/loans?sort=amount&status=ACTIVE&order=desc&page=1

These three requests are IDENTICAL in meaning — same filters, same sort, same page.
They should return the same data and hit the same cache entry.

Naive key from req.query as-is:
  Client A: key = "loans:...?status=ACTIVE&sort=amount&order=desc&page=1"
  Client B: key = "loans:...?page=1&sort=amount&status=ACTIVE&order=desc"
  → Different keys → three cache misses → three DB queries → wasted

The canonical serialization problem: define one canonical form for any set of parameters.
```

**Canonical serialization implementation:**
```typescript
import { createHash } from 'crypto';

interface LoanListQuery {
  status?:    'ACTIVE' | 'CLOSED' | 'DELINQUENT' | 'PENDING';
  sortBy?:    'amount' | 'dueDate' | 'createdAt' | 'disbursementDate';
  sortOrder?: 'asc' | 'desc';
  minAmount?: number;
  maxAmount?: number;
  fromDate?:  string;
  toDate?:    string;
  page:       number;
  pageSize:   number;
}

function canonicalizeQuery(query: LoanListQuery): string {
  // Step 1: Sort parameters alphabetically by key name
  // Ensures: {status:'A',page:1} === {page:1,status:'A'}
  const sortedKeys = (Object.keys(query) as (keyof LoanListQuery)[])
    .sort()
    .filter(k => query[k] !== undefined && query[k] !== null);

  // Step 2: Normalize values (lowercase strings, number formatting)
  const normalized = sortedKeys.map(k => {
    const v = query[k];
    if (typeof v === 'string') return `${k}=${v.toLowerCase().trim()}`;
    if (typeof v === 'number') return `${k}=${v}`;
    return `${k}=${v}`;
  });

  // Step 3: Join into a canonical string
  const canonical = normalized.join('&');

  // Step 4: For short parameter sets (< 60 chars): use directly (readable in Redis)
  if (canonical.length <= 60) {
    return canonical.replace(/[^a-zA-Z0-9&=._-]/g, '_'); // Safe for key characters
  }

  // Step 5: For long parameter sets: hash to fixed-length string
  // Short hash (8 chars of SHA-256) — low collision risk for typical parameter sets
  return 'q' + createHash('sha256').update(canonical).digest('hex').slice(0, 8);
}

// Complete key builder with query canonicalization:
class LoanCacheKeyBuilder {
  private readonly svc: string;
  private readonly env: string;

  constructor(service: string, env: string) {
    this.svc = service;
    this.env = env;
  }

  loanList(userId: string, query: LoanListQuery): string {
    const qPart = canonicalizeQuery(query);
    return `${this.svc}:${this.env}:loan:user:${userId}:list:${qPart}:v2`;
  }
}

const kb = new LoanCacheKeyBuilder('loans', 'prod');

// Test canonical behavior:
const q1 = { status: 'ACTIVE' as const, sortBy: 'amount' as const, page: 1, pageSize: 20 };
const q2 = { page: 1, pageSize: 20, status: 'ACTIVE' as const, sortBy: 'amount' as const };
const q3 = { sortBy: 'amount' as const, page: 1, status: 'ACTIVE' as const, pageSize: 20 };

console.log(kb.loanList('user-abc', q1));
// loans:prod:loan:user:user-abc:list:page=1&pagesize=20&sortby=amount&status=active:v2
console.log(kb.loanList('user-abc', q2));
// loans:prod:loan:user:user-abc:list:page=1&pagesize=20&sortby=amount&status=active:v2
console.log(kb.loanList('user-abc', q3));
// loans:prod:loan:user:user-abc:list:page=1&pagesize=20&sortby=amount&status=active:v2
// All three produce identical keys → cache hit on second and third request ✓
```

**Handling filters that should NOT be part of the cache key:**
```typescript
// Some "filter" values are per-request context, not data selectors:
interface LoanListRequest {
  // These go INTO the cache key (they change which data is correct):
  status?:   string;
  page:      number;
  pageSize:  number;

  // These do NOT go into the cache key:
  requestId:    string; // Unique per request — would make every key unique (all misses)
  traceId:      string; // Same reason
  timestamp:    number; // Millisecond precision → no two requests get same key
  clientVersion: string; // A/B testing dimension — SHOULD be in key if it changes response
                          // Omit only if it changes metadata but not the loan data itself

  // These are ambiguous — need explicit decision:
  locale:   string;  // SHOULD be in key if response contains locale-sensitive formatting
                     // ('₹1,00,000' vs '$10,000') — miss this and you serve wrong currency
  timezone: string;  // SHOULD be in key if response contains formatted dates
                     // ('5 Jan 2025' vs '01/05/2025') — miss this → wrong date format
}

// Decision rule: if changing the value produces a different correct response → include it
//               if changing the value doesn't affect the response body → exclude it
```

## Section 5: Invalidation Strategies

**Q7. What are the three invalidation strategies — TTL expiry, explicit deletion, and version bumping — and how do you choose between them for different data types in a fintech system?**
A: Cache invalidation is the hardest problem in caching. Each strategy has different consistency guarantees, operational complexity, and performance characteristics. The right choice depends on how frequently the underlying data changes and how stale data affects the business:

**Strategy 1 — TTL expiry (time-to-live):**
```typescript
// Data expires automatically after a fixed time period
// Write-once: no invalidation code needed; TTL does the work

await redis.set(key, value, 'EX', ttlSeconds);
// After ttlSeconds: key no longer exists; next request is a cache miss → DB fetch

// TTL selection by data type and staleness tolerance:
const TTL = {
  // Highly dynamic data — short TTL; staleness is costly
  LOAN_STATUS:       30,          // 30 seconds — payment status changes rapidly
  FRAUD_RISK:        60,          // 1 minute — new signals arrive constantly
  NEXT_EMI_DUE:     300,          // 5 minutes — can tolerate 5 min stale

  // Moderately dynamic — medium TTL
  LOAN_DETAIL:       600,          // 10 minutes — loan terms rarely change mid-session
  USER_PROFILE:     1_800,         // 30 minutes — user updates are infrequent
  EMI_SCHEDULE:     3_600,         // 1 hour — schedule fixed after disbursal

  // Slowly changing — long TTL
  LENDER_RULES:     21_600,        // 6 hours — rule changes are planned events
  CREDIT_SCORE:     86_400,        // 24 hours — bureau scores change daily at most
  LOAN_PRODUCTS:    86_400,        // 24 hours — product catalog changes rarely

  // Static reference data — very long TTL
  IFSC_BANK_DATA:   604_800,       // 7 days — bank branch data is stable
  PIN_CODE_DATA:    2_592_000,     // 30 days — effectively static
} as const;

// Pros: simple; self-cleaning; no invalidation code
// Cons: serves stale data up to TTL after the underlying data changes
// Best for: read-heavy data with tolerable staleness; reference data
```

**Strategy 2 — Explicit deletion (event-driven invalidation):**
```typescript
// Invalidate the cache entry exactly when the underlying data changes
// Requires: invalidation code wherever the underlying data is mutated

@Injectable()
export class LoanService {
  async updateLoanStatus(loanId: string, newStatus: LoanStatus): Promise<void> {
    // Step 1: Update the database (source of truth)
    await this.loanRepo.update(loanId, { status: newStatus });

    // Step 2: Immediately invalidate all cache keys that contain this loan's data
    const loan = await this.loanRepo.findById(loanId); // Need userId for list key
    await Promise.all([
      // Delete the loan detail key (directly contains status)
      this.redis.del(this.keys.loanDetail(loanId)),

      // Delete the user's loan list keys (contains status in the list items)
      // Problem: we don't know which pages the user has cached!
      // Solution A: delete all pages (expensive if many pages)
      this.deleteUserLoanListPages(loan.userId),
      // Solution B: include a "list version" in list keys; bump it on any loan update
      // (see Q8 for this pattern)

      // Delete aggregated keys that might include this loan's status
      this.redis.del(this.keys.tenantDashboardStats(loan.tenantId)),
    ]);
  }

  private async deleteUserLoanListPages(userId: string): Promise<void> {
    // SCAN for all list keys for this user — non-blocking but still multiple round trips
    const pattern = `loans:prod:loan:user:${userId}:list:*`;
    let cursor = '0';
    do {
      const [nextCursor, keys] = await this.redis.scan(cursor, 'MATCH', pattern, 'COUNT', 100);
      cursor = nextCursor;
      if (keys.length) await this.redis.del(...keys);
    } while (cursor !== '0');
  }
}

// Pros: strong consistency; stale data window is near-zero
// Cons: requires invalidation code at every mutation point; easy to miss one;
//       complex when one mutation affects many keys
// Best for: financial data where staleness is unacceptable (balance, status)
```

**Strategy 3 — Version bumping (logical mass invalidation):**
```typescript
// Bump a version counter; all old versioned keys become orphaned
// The "delete" is logical: old keys are never read again; expire via TTL

// Stored in Redis: the current version for each scope
// Key: "versions:loans:prod:lender:rules"  Value: "v7"

@Injectable()
export class CacheVersionService {
  // Get current version for a scope (with in-process caching for efficiency)
  async getVersion(scope: string): Promise<string> {
    const localKey = `version:${scope}`;
    // L1: check in-process cache (zero Redis round trips for read-heavy paths)
    if (this.localVersionCache.has(localKey)) {
      return this.localVersionCache.get(localKey)!;
    }
    // L2: check Redis
    const version = await this.redis.get(`versions:${scope}`) ?? 'v1';
    this.localVersionCache.set(localKey, version);
    // Cache locally for 60 seconds (version changes are infrequent planned events)
    setTimeout(() => this.localVersionCache.delete(localKey), 60_000);
    return version;
  }

  // Bump the version for a scope — all keys with old version become unreachable
  async bumpVersion(scope: string): Promise<string> {
    const newVersion = `v${Date.now()}`; // Timestamp-based version (sortable, unique)
    await this.redis.set(`versions:${scope}`, newVersion);
    // Invalidate local caches across all service instances
    await this.pubsub.publish('version-changed', { scope, newVersion });
    return newVersion;
  }
}

// Key builder that fetches version dynamically:
async lenderRules(lenderCode: string): Promise<string> {
  const version = await this.versionService.getVersion('lender:rules');
  return `loans:prod:lender:${lenderCode}:rules:${version}`;
  // When lender rules change globally: bumpVersion('lender:rules')
  // All instances immediately use the new version → all old keys are logical no-ops
}

// Use case: planned configuration changes
await this.versionService.bumpVersion('lender:rules');
// Effect: instantly makes all 1000+ lender rule cache entries unreachable
// Without: 1000 individual SCAN + DEL operations (O(N) Redis blocking)
// With: one SET command; zero scanning; zero blocking

// Pros: O(1) mass invalidation; no Redis key enumeration
// Cons: orphaned keys consume memory until TTL expires; adds latency to cache reads
//       (one extra Redis GET for the version); version state is itself a cache
// Best for: configuration changes; schema migrations; planned data refreshes
```

**Q8. How do you handle cache invalidation for list/collection endpoints when an item within the list changes?**
A: List invalidation is the hardest invalidation problem. A single item change can affect an unknown number of paginated list pages, filtered views, and aggregated counts:

```typescript
// The list invalidation problem:
// User has loan list cached as 5 pages (page 1-5, 20 items each = 100 loans)
// Loan L023 changes status from ACTIVE → DELINQUENT
// This affects:
//   - Page 2 (where L023 appears in the "all loans" list)
//   - The "ACTIVE loans" filtered list (L023 should disappear)
//   - The "DELINQUENT loans" filtered list (L023 should appear)
//   - The dashboard count (ACTIVE count -1, DELINQUENT count +1)
// Total keys to invalidate: unknown until we know which filters the user has applied

// Solution 1: List version tag (recommended for most cases)
// Add a per-user "list version" that increments whenever any loan for that user changes
// All list keys include this version → one version bump invalidates ALL list views

class ListVersionedKeyBuilder {
  async userLoanList(userId: string, page: number, filters: LoanListQuery): Promise<string> {
    // Fetch the current list version for this user's loan list
    const listVersion = await this.redis.get(`loans:prod:list-version:user:${userId}`) ?? 'v1';
    const qPart = canonicalizeQuery(filters);
    return `loans:prod:loan:user:${userId}:list:${listVersion}:${qPart}:p${page}:v2`;
    //                                              ↑ list version embedded in key
  }

  async invalidateUserLoanLists(userId: string): Promise<void> {
    // One operation invalidates ALL list pages AND all filter combinations for this user
    const newVersion = `lv${Date.now()}`;
    await this.redis.set(`loans:prod:list-version:user:${userId}`, newVersion, 'EX', 86400);
    // 24h TTL on the version key itself (if user is inactive, clean up the version key too)
    // Effect: all old list keys are logically deleted; new requests build new keys
    //         with the new list version → all misses → DB refill → fresh data
  }
}

// In the loan update service:
async updateLoanStatus(loanId: string, newStatus: LoanStatus): Promise<void> {
  const loan = await this.loanRepo.update(loanId, { status: newStatus });

  await Promise.all([
    // Precise: invalidate only the specific loan's detail cache
    this.redis.del(this.keys.loanDetail(loanId)),

    // Broad: invalidate ALL list views for this user (one operation)
    this.keys.invalidateUserLoanLists(loan.userId),

    // Aggregates: invalidate dashboard counts
    this.redis.del(this.keys.tenantDashboardStats(loan.tenantId)),
  ]);
  // Total Redis operations: 3, regardless of how many list pages/filters the user has
}

// Solution 2: Cache the list as IDs only; cache items separately
// List cache: stores [loanId1, loanId2, ..., loanId20] (IDs only, no item data)
// Item cache:  stores full loan data per ID: "loan:detail:loanId1" → {full loan}
// On display:  fetch list of IDs → MGET all item caches → combine

// Benefit: when loan L023 changes → only "loan:detail:L023" is invalidated
//           → List ID caches remain valid (IDs haven't changed)
//           → MGET refetches only the changed item from DB
//           → Other 99 items served from cache

// Implemented:
async getUserLoanListWithSeparateItemCaches(
  userId: string,
  page: number,
): Promise<Loan[]> {
  const listKey = `loans:prod:loan:user:${userId}:list-ids:p${page}:v1`;

  // Check list cache (stores IDs only)
  let loanIds = await this.redis.get(listKey);
  if (!loanIds) {
    const loans = await this.loanRepo.findByUser(userId, page, 20);
    loanIds = JSON.stringify(loans.map(l => l.id));
    await this.redis.set(listKey, loanIds, 'EX', 300); // 5-min TTL on ID list
  }
  const ids = JSON.parse(loanIds) as string[];

  // Fetch individual loan caches with MGET (one Redis round trip for all)
  const itemKeys = ids.map(id => this.keys.loanDetail(id));
  const cached   = await this.redis.mget(...itemKeys);

  // For any cache miss: batch fetch from DB
  const misses = ids.filter((_, i) => !cached[i]);
  let fromDb: Loan[] = [];
  if (misses.length) {
    fromDb = await this.loanRepo.findByIds(misses);
    // Cache the DB results for next time
    await Promise.all(
      fromDb.map(loan =>
        this.redis.set(this.keys.loanDetail(loan.id), JSON.stringify(loan), 'EX', 600)
      )
    );
  }

  // Assemble in original ID order
  const dbMap = new Map(fromDb.map(l => [l.id, l]));
  return ids.map((id, i) =>
    cached[i] ? JSON.parse(cached[i]!) : dbMap.get(id)!
  );
}
```

## Section 6: Redis-Specific Patterns

**Q9. How do Redis key naming conventions interact with Redis Cluster's slot assignment, and when do you need hash tags to keep related keys on the same shard?**
A: Redis Cluster distributes keys across 16,384 hash slots. The slot for a key is determined by `CRC16(key) % 16384`. When a key contains a hash tag (`{...}`), only the content inside the braces determines the slot. This matters for multi-key operations that must be atomic or execute in a single round trip:

```typescript
// Without hash tags: keys are distributed randomly across cluster nodes

const key1 = 'loans:prod:loan:loan-abc:detail:v3';
// Slot: CRC16('loans:prod:loan:loan-abc:detail:v3') % 16384 = 7231 → Node A

const key2 = 'loans:prod:loan:loan-abc:emis:v2';
// Slot: CRC16('loans:prod:loan:loan-abc:emis:v2') % 16384 = 11024 → Node B

const key3 = 'loans:prod:loan:loan-abc:documents:v1';
// Slot: CRC16('loans:prod:loan:loan-abc:documents:v1') % 16384 = 3891 → Node C

// Problem: MGET across different slots → cross-slot error in Redis Cluster
await redis.mget(key1, key2, key3);
// Error: CROSSSLOT Keys in request don't hash to the same slot
// → Cannot use MGET; must make 3 individual GET calls (3 round trips instead of 1)

// With hash tags: force all related keys to the same slot
const key1Tagged = 'loans:prod:{loan:loan-abc}:detail:v3';
const key2Tagged = 'loans:prod:{loan:loan-abc}:emis:v2';
const key3Tagged = 'loans:prod:{loan:loan-abc}:documents:v1';
// All three: CRC16('loan:loan-abc') % 16384 = same slot → same node

await redis.mget(key1Tagged, key2Tagged, key3Tagged);
// SUCCESS: all on same slot → single round trip → 3 values returned

// Real performance benefit:
// Without tags: 3 × (network RTT + Redis processing) = ~3ms
// With tags:    1 × (network RTT + Redis processing) = ~1ms
// 3× improvement for loan detail page that needs detail + emis + documents

// When to use hash tags:
// ✓ MGET for related entity data (loan detail + emis + documents)
// ✓ MULTI/EXEC transactions across related keys
// ✓ Lua scripts that touch multiple keys atomically
// ✗ General-purpose keys (random distribution is better for load balancing)
// ✗ Hot keys (all traffic to one slot → one shard becomes the bottleneck)
// ✗ Keys with very different access patterns (one hot + one cold on same slot = wasted)

// Implementation in key builder:
class ClusterAwareKeyBuilder {
  // Standard key: random distribution (load balanced)
  loanDetail(loanId: string): string {
    return `loans:prod:loan:${loanId}:detail:v3`;
  }

  // Hash-tagged key: co-located with other loan keys for this loanId
  // Use when: you'll MGET this alongside other loan entity keys
  loanDetailTagged(loanId: string): string {
    return `loans:prod:{loan:${loanId}}:detail:v3`;
  }

  // Fetch all loan data in one round trip using hash-tagged keys
  async getLoanBundle(loanId: string): Promise<LoanBundle> {
    const detailKey    = this.loanDetailTagged(loanId);
    const emisKey      = `loans:prod:{loan:${loanId}}:emis:v2`;
    const documentsKey = `loans:prod:{loan:${loanId}}:documents:v1`;

    const [detail, emis, documents] = await redis.mget(detailKey, emisKey, documentsKey);
    // ONE round trip for all three values

    return {
      detail:    detail    ? JSON.parse(detail)    : null,
      emis:      emis      ? JSON.parse(emis)      : null,
      documents: documents ? JSON.parse(documents) : null,
    };
  }
}
```

**Q10. What is the thundering herd problem in caching, and what are the three techniques — mutex locking, probabilistic early expiry, and stale-while-revalidate — that prevent it?**
A: The thundering herd occurs when a popular cache entry expires and many concurrent requests simultaneously miss the cache, all rushing to the database. In a fintech system with tens of thousands of concurrent users, a single key expiry can produce hundreds of simultaneous DB queries:

```typescript
// The problem: synchronized cache miss at TTL boundary
// "loanservice:prod:lender:HDFC001:rules:v4" TTL expires at exactly 03:00:00
// 500 in-flight requests all hit the cache at 03:00:01
// All 500 miss → all 500 query the DB simultaneously
// DB: 500 identical queries for HDFC001 rules → CPU spike → latency explosion

// ─────────────────────────────────────────────────────────────────────────
// Technique 1: Mutex locking (cache stampede prevention)
// Only one request fetches from DB; others wait for the lock to release
// ─────────────────────────────────────────────────────────────────────────

async function getWithMutex<T>(
  redis: Redis,
  key: string,
  fetcher: () => Promise<T>,
  ttlSeconds: number,
): Promise<T> {
  // Check cache first (fast path — no locking needed)
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  // Cache miss: acquire a distributed lock
  const lockKey = `lock:${key}`;
  const lockToken = Math.random().toString(36).slice(2); // Unique token for this request
  const lockAcquired = await redis.set(lockKey, lockToken, 'NX', 'EX', 10);
  // NX: only set if not exists (atomic test-and-set)
  // EX 10: lock expires in 10 seconds (prevents deadlock if holder crashes)

  if (lockAcquired === 'OK') {
    // This request won the lock: fetch from DB and populate cache
    try {
      const data = await fetcher();
      await redis.set(key, JSON.stringify(data), 'EX', ttlSeconds);
      return data;
    } finally {
      // Release lock only if we still hold it (check token)
      const currentToken = await redis.get(lockKey);
      if (currentToken === lockToken) await redis.del(lockKey);
    }
  } else {
    // Another request holds the lock: wait briefly and retry
    await new Promise(resolve => setTimeout(resolve, 50 + Math.random() * 50));
    // Retry — the lock holder should have populated the cache by now
    return getWithMutex(redis, key, fetcher, ttlSeconds);
  }
}

// ─────────────────────────────────────────────────────────────────────────
// Technique 2: Probabilistic early expiry (XFetch algorithm)
// Randomly refresh the cache before it expires, spreading the refresh load
// ─────────────────────────────────────────────────────────────────────────

interface CacheValueWithMeta<T> {
  data: T;
  computedAt: number; // Timestamp when the value was computed
  delta: number;      // How long the computation took (milliseconds)
}

async function getWithEarlyExpiry<T>(
  redis: Redis,
  key: string,
  fetcher: () => Promise<T>,
  ttlSeconds: number,
  beta = 1.0, // Eagerness factor: higher = more aggressive early refresh
): Promise<T> {
  const stored = await redis.get(key);

  if (stored) {
    const { data, computedAt, delta } = JSON.parse(stored) as CacheValueWithMeta<T>;

    // XFetch formula:
    // Recompute early if: now - delta * beta * ln(random) > expiry_time
    // The random factor means different requests hit the refresh window at different times
    // → No synchronized stampede; refreshes are spread across multiple requests
    const remainingTtl = await redis.ttl(key);
    const shouldRecompute =
      Date.now() - delta * beta * Math.log(Math.random()) > (Date.now() + remainingTtl * 1000 - ttlSeconds * 1000);

    if (!shouldRecompute) {
      return data; // Cache hit; not yet due for early refresh
    }
    // Fall through to recompute (this specific request refreshes early)
  }

  // Compute fresh value (measuring computation time for the next XFetch decision)
  const startTime = Date.now();
  const freshData = await fetcher();
  const computationTime = Date.now() - startTime;

  const meta: CacheValueWithMeta<T> = {
    data:        freshData,
    computedAt:  Date.now(),
    delta:       computationTime,
  };
  await redis.set(key, JSON.stringify(meta), 'EX', ttlSeconds);
  return freshData;
}

// Effect: for a key with 300s TTL, the XFetch algorithm begins probabilistically
// triggering early refreshes in the last ~30-60 seconds of the TTL
// Each refresh is triggered by exactly ONE request; the rest hit the cache as normal
// → Zero synchronized expiry; DB sees a single refresh query every ~300 seconds
// → Much simpler to implement than mutex locking; no lock contention

// ─────────────────────────────────────────────────────────────────────────
// Technique 3: Stale-while-revalidate
// Serve stale data immediately; refresh in the background
// ─────────────────────────────────────────────────────────────────────────

async function getStaleWhileRevalidate<T>(
  redis: Redis,
  key: string,
  fetcher: () => Promise<T>,
  ttlSeconds: number,         // How long data is "fresh"
  staleSeconds: number,       // How long stale data is still served
): Promise<T> {
  // Two TTLs: 'fresh' and 'stale'
  // Approach: store a logical TTL inside the value; use a longer Redis TTL
  const stored = await redis.get(key);

  if (stored) {
    const { data, freshUntil } = JSON.parse(stored) as { data: T; freshUntil: number };

    if (Date.now() < freshUntil) {
      return data; // Still fresh — return immediately
    }

    // STALE: expired fresh TTL but within stale window
    // Return stale data immediately; trigger background refresh
    if (Date.now() < freshUntil + staleSeconds * 1000) {
      // Background refresh (fire and forget — don't await)
      setImmediate(async () => {
        try {
          const fresh = await fetcher();
          const newEntry = { data: fresh, freshUntil: Date.now() + ttlSeconds * 1000 };
          await redis.set(key, JSON.stringify(newEntry), 'EX', ttlSeconds + staleSeconds);
        } catch (err) {
          // Background refresh failed — stale data continues to be served
          // Next request will also trigger a background refresh attempt
          logger.warn({ key, err, event: 'BACKGROUND_REFRESH_FAILED' });
        }
      });
      return data; // Return stale immediately — user doesn't wait for refresh
    }
  }

  // Complete miss (no stale data either): must wait for fetch
  const fresh = await fetcher();
  const entry = { data: fresh, freshUntil: Date.now() + ttlSeconds * 1000 };
  await redis.set(key, JSON.stringify(entry), 'EX', ttlSeconds + staleSeconds);
  return fresh;
}

// Use cases for each technique:
// Mutex locking:        data that MUST be fresh; DB can handle brief single-query spikes
// Early expiry:         read-heavy hot keys; DB load reduction is the priority
// Stale-while-revalidate: UX priority; user must never wait for a slow refresh
//                        (acceptable: lender rules, loan products, reference data)
//                        Not acceptable: payment status, account balance (must be fresh)
```

## Section 7: Operational Concerns

**Q11. How do you monitor cache effectiveness, detect key design problems, and debug cache issues in production?**
A: A cache that appears to work can silently have a 10% hit rate instead of the expected 90%, serving the same DB load as if caching didn't exist. Operational monitoring is essential:

```typescript
// Metrics every cached service should emit
@Injectable()
export class InstrumentedCacheService {
  async get<T>(key: string, entityType: string): Promise<T | null> {
    const value = await this.redis.get(key);

    if (value !== null) {
      // Cache hit
      metrics.increment('cache.hit', { entity: entityType });
      return JSON.parse(value) as T;
    }

    // Cache miss
    metrics.increment('cache.miss', { entity: entityType });
    return null;
  }

  async set<T>(key: string, value: T, ttl: number, entityType: string): Promise<void> {
    await this.redis.set(key, JSON.stringify(value), 'EX', ttl);
    metrics.increment('cache.write', { entity: entityType });
  }

  async del(key: string, entityType: string): Promise<void> {
    await this.redis.del(key);
    metrics.increment('cache.invalidation', { entity: entityType });
  }
}

// Dashboard metrics to track:
/*
1. Cache hit rate per entity type:
   cache.hit / (cache.hit + cache.miss) by entity_type
   Alert if: hit rate for loan_detail drops below 70% (expected: 90%+)
   Cause: TTL too short; key includes time-varying component; invalidation too aggressive

2. Cache key cardinality:
   redis INFO keyspace → db0:keys=N
   Unexpected growth → key design includes unbounded dimension (requestId, timestamp)
   Alert if: key count > 10M (may indicate key leak)

3. Memory usage per key prefix:
   redis MEMORY USAGE "loans:prod:loan:loan-abc:detail:v3"
   redis DEBUG SLEEP (use sparingly — blocks Redis)
   Better: periodic sample of key sizes

4. TTL distribution:
   OBJECT IDLETIME key — how long since last access
   Keys never accessed since creation → cache is populated but never read
     → Key format mismatch between reader and writer

5. Latency by operation:
   GET p99, SET p99, DEL p99
   Unexpected latency spikes → Redis memory pressure (eviction happening)
*/

// Key design debugging: the "key inspector"
// When a cache isn't hitting as expected, inspect what keys actually exist

    cursor = next;

  } while (cursor !== '0' && keys.length < 100); // Limit scan in production

  console.log(`Keys matching ${pattern} (first 100):`);

    const size = await redis.strlen(key);

    console.log(`    TTL: ${ttl}s | Size: ${size}B | Idle: ${idle}s`);
  }
}
```

**Q12. Scenario: "A code review reveals that the user loan list is cached with the key `loans:list:${userId}:${JSON.stringify(req.query)}`. List every problem with this key and redesign it."**
A: This is a common real-world anti-pattern that contains multiple simultaneous key design failures:

```typescript
// Original (broken) key:
const badKey = `loans:list:${userId}:${JSON.stringify(req.query)}`;

// Generated examples:
// loans:list:user-abc:{"status":"ACTIVE","page":"1","sort":"amount","requestId":"req-xyz-001"}
// loans:list:user-abc:{"page":"1","status":"ACTIVE","sort":"amount","requestId":"req-xyz-002"}

// ─── PROBLEM 1: No service namespace ──────────────────────────────────────────
// Key: "loans:list:user-abc:..."
// If the payments service also caches with user-abc → collision
// Fix: prefix with service name → "loanservice:prod:loan:user:user-abc:..."

// ─── PROBLEM 2: No environment namespace ──────────────────────────────────────
// Key: "loans:list:user-abc:..."
// Staging and production share a Redis instance? Staging pollutes prod cache
// Fix: include env → "loanservice:prod:..." or "loanservice:staging:..."

// ─── PROBLEM 3: JSON.stringify is non-canonical ────────────────────────────────
// {status:'ACTIVE',page:'1'} → '{"status":"ACTIVE","page":"1"}'
// {page:'1',status:'ACTIVE'} → '{"page":"1","status":"ACTIVE"}'
// Same logical request → different JSON string → different cache key → cache miss
// Fix: sort keys before serialization (canonicalizeQuery function from Q6)

// ─── PROBLEM 4: requestId is a per-request unique value ───────────────────────
// Every single request has a unique requestId → every key is unique
// Effective cache hit rate: 0% (every request misses the cache)
// This completely defeats the cache; might as well not have caching at all
// Fix: exclude non-data-determining fields: requestId, traceId, timestamp

// ─── PROBLEM 5: No version segment ────────────────────────────────────────────
// When the response schema changes (add a field), old cached responses
// are returned until their TTL expires → stale shape returned to clients
// Fix: append a version → "...:v2"

// ─── PROBLEM 6: No tenant isolation ──────────────────────────────────────────
// If this is a multi-tenant platform, user-abc might exist in multiple tenants
// Key only includes userId → tenant B's user-abc gets tenant A's loan list
// Fix: include tenantId → "...:tenant:${tenantId}:user:${userId}:..."

// ─── PROBLEM 7: Raw JSON in key contains unsafe characters ────────────────────
// JSON string: {"status":"ACTIVE"} contains: { " : }
// Redis key restriction: no space characters (safe), but { } are technically allowed
// However: some Redis clients, log systems, and monitoring tools struggle with
//           special characters in key names → operational headaches
// Fix: sanitize or hash the query portion

// ─── PROBLEM 8: Key length can be unbounded ───────────────────────────────────
// req.query might contain many parameters with long values
// Redis allows keys up to 512MB — technically unlimited — but:
// Very long keys: higher memory overhead (key stored in Redis too)
//                 slower comparison (longer string to compare)
// Fix: if query serialization > 60 chars, replace with SHA-256 hash (8 chars)

// ─────────────────────────────────────────────────────────────────────────────
// REDESIGNED KEY (addresses all eight problems):
// ─────────────────────────────────────────────────────────────────────────────

function redesignedKey(
  tenantId: string,
  userId: string,
  query: LoanListQuery,  // Typed; excludes non-deterministic fields by type definition
): string {
  const svc = 'loanservice';
  const env = process.env.NODE_ENV ?? 'prod';
  const qPart = canonicalizeQuery(query); // Sorted, normalized, length-capped

  return `${svc}:${env}:tenant:${tenantId}:loan:user:${userId}:list:${qPart}:v2`;
}

// Example outputs:
// loanservice:prod:tenant:tenant-A:loan:user:user-abc:list:page=1&pagesize=20&sortby=amount&status=active:v2
// loanservice:prod:tenant:tenant-A:loan:user:user-abc:list:page=2&pagesize=20&sortby=amount&status=active:v2
// loanservice:prod:tenant:tenant-B:loan:user:user-abc:list:page=1&pagesize=20&sortby=amount&status=active:v2

// Improvements:
// ✓ Service namespace: prevents cross-service collisions
// ✓ Environment: prevents staging/prod pollution
// ✓ Tenant isolation: tenant A and B are separate keys
// ✓ Canonical query: same logical request = same key (cache hits correctly)
// ✓ No requestId: non-data fields excluded (cache hit rate is meaningful)
// ✓ Version segment: schema changes handled by bumping v2 → v3
// ✓ Safe characters: query part sanitized; no raw JSON braces
// ✓ Length bounded: canonicalizeQuery hashes if > 60 chars
```

## Quick Reference Table

| Segment | Purpose | Examples | Omit When |
|---|---|---|---|
| **namespace (service)** | Prevent cross-service collisions | `loans`, `payments`, `kyc` | Single-service app with dedicated Redis |
| **env** | Prevent staging/prod pollution | `prod`, `staging`, `dev` | Dedicated Redis per environment |
| **tenant** | Multi-tenant isolation | `tenant:HDFC`, `tenant:AXIS` | Single-tenant system |
| **entity** | Prevent cross-entity collisions | `loan`, `user`, `emi`, `lender` | Never — always include |
| **id** | Identify specific instance | `loan-abc-123`, `user-xyz` | Tenant-wide aggregates |
| **sub-resource** | Distinguish views of same entity | `detail`, `summary`, `list`, `count` | Only one view cached per entity |
| **query hash** | Cache filtered/paginated lists | `page=1&status=active`, `q8f3a2b1` | Unfiltered single-resource fetches |
| **version** | Schema version / mass invalidation | `v1`, `v2`, `v3` | Extremely short TTL (staleness tolerable) |

**Tip for the interview:** At 5 YOE, cache key questions always arrive as either a code review ("what's wrong with this key?") or a design exercise ("design the caching layer for this API"). The signal the examiner wants: the **canonical serialization problem** (Q6) — knowing that `JSON.stringify(req.query)` is non-canonical and that parameters must be sorted, normalized, and length-capped before becoming a cache key is the detail that separates engineers who've debugged cache misses in production from those who haven't. Know the **version segment's dual purpose** (Q3) — schema migration (bump version when response shape changes) and mass invalidation (bump version to orphan all matching keys without scanning) — as two distinct mechanisms with the same implementation. The **thundering herd solutions** (Q10) matter in fintech context: mutex locking for financial data that must be fresh, stale-while-revalidate for configuration data where serving one request from stale cache is acceptable. For the **redesign scenario** (Q12), being able to enumerate all eight problems with a single bad key, naming each independently, demonstrates the systematic thinking that senior engineers bring to architecture decisions.
