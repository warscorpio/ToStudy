# Security (HTTP): Security Headers & Helmet.js — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What are HTTP security headers, and why are they a necessary complement to application-level security controls?**
A: HTTP security headers are response headers that instruct the browser how to behave when rendering a page or handling resources from your origin. They form a second line of defence at the *transport and rendering layer* — between your application code and the browser's execution environment.

Application-level controls (input validation, parameterised queries, authentication) prevent attacks at the server. Security headers limit what an attacker can *do* if those controls fail or are partially bypassed. Example: even if an XSS vulnerability exists in your app, a well-configured `Content-Security-Policy` can prevent the injected script from executing or exfiltrating data. The XSS bug still needs fixing, but the CSP buys time and limits blast radius.

Headers are also the only way to instruct browsers on transport security (HSTS), framing permissions (X-Frame-Options / `frame-ancestors`), MIME handling (X-Content-Type-Options), and cross-origin resource sharing policies (CORP, COEP, COOP). None of these can be enforced by application code alone — they require the browser to receive and honour the header.

In a regulated fintech context: OWASP ASVS Level 2 (the minimum for financial applications) mandates appropriate security headers. PCI-DSS Requirement 6.4 requires protection of web-facing applications, and missing security headers are a common finding in PCI penetration tests and PCI-DSS QSA assessments.

**Q2. What is Helmet.js, and how does it work in a NestJS/Express application?**
A: Helmet is an Express middleware library (also usable in NestJS via `app.use()`) that sets a collection of security-relevant HTTP response headers. It bundles 15+ individual middleware functions, each responsible for one header or header group, with sensible defaults that you can override.

```typescript
// NestJS main.ts — basic Helmet setup
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
import helmet from 'helmet';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // Apply Helmet with defaults — covers most headers immediately
  app.use(helmet());

  await app.listen(3000);
}
bootstrap();
```

Under the hood, `helmet()` calls each sub-middleware in sequence. Each one adds, modifies, or removes specific headers on every response. The call `helmet()` with no arguments applies all defaults; you can pass an options object to disable or customise individual headers:

```typescript
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc:  ["'self'"],
      scriptSrc:   ["'self'", 'https://cdn.example.com'],
      styleSrc:    ["'self'", "'unsafe-inline'"],  // reluctant but sometimes necessary
      imgSrc:      ["'self'", 'data:', 'https:'],
      connectSrc:  ["'self'", 'https://api.example.com'],
      fontSrc:     ["'self'", 'https://fonts.gstatic.com'],
      objectSrc:   ["'none'"],
      frameAncestors: ["'none'"],
    },
  },
  crossOriginEmbedderPolicy: false,  // disable if you embed third-party content
}));
```

Helmet does not handle CORS (use NestJS's `@nestjs/cors` or Express `cors` middleware for that — it's a different concern). It also does not set `Set-Cookie` attributes — those are handled per-cookie in your session/auth code.

## Section 2: Headers That Prevent Content Injection Attacks

**Q3. What is `Content-Security-Policy` (CSP), and how does it prevent XSS?**
A: CSP is the most powerful and complex security header. It defines a whitelist of approved sources for every type of content the browser is allowed to load and execute: scripts, styles, images, fonts, frames, form submissions, WebSockets, and more. Injected scripts that aren't from an approved source are blocked before execution.

```http
Content-Security-Policy:
  default-src 'self';
  script-src  'self' https://cdn.example.com;
  style-src   'self' 'unsafe-inline';
  img-src     'self' data: https:;
  connect-src 'self' https://api.example.com wss://ws.example.com;
  font-src    'self' https://fonts.gstatic.com;
  object-src  'none';
  base-uri    'self';
  form-action 'self';
  frame-ancestors 'none';
  upgrade-insecure-requests;
```

**Directive breakdown:**
- `default-src 'self'` — fallback for any directive not explicitly set. `'self'` means same origin only.
- `script-src 'self'` — only scripts from your own origin. Inline scripts (`<script>alert(1)</script>`) blocked unless `'unsafe-inline'` is added (avoid this — it defeats XSS protection).
- `object-src 'none'` — blocks Flash and other plugins entirely. Always set this.
- `base-uri 'self'` — prevents base tag injection attacks (injecting `<base href="//attacker.com">` to redirect relative URLs).
- `form-action 'self'` — form submissions only to your own origin.
- `frame-ancestors 'none'` — replaces `X-Frame-Options: DENY` (see Q6). Prevents your page from being embedded in frames on any other origin.
- `upgrade-insecure-requests` — instructs the browser to upgrade `http://` resource loads to `https://` automatically.

**Nonces (the correct way to allow inline scripts):**
```typescript
// Generate a nonce per-request, include it in CSP and in the script tag
const nonce = crypto.randomBytes(16).toString('base64');

res.setHeader('Content-Security-Policy',
  `script-src 'self' 'nonce-${nonce}'; object-src 'none'`
);
// In the HTML template:
// <script nonce="${nonce}">/* trusted inline code */</script>
```
The nonce is unguessable per request. Only inline scripts with the matching nonce attribute execute. XSS-injected inline scripts don't know the nonce and are blocked.

**Report-only mode for safe rollout:**
```http
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-violations
```
Reports violations without blocking anything — essential for discovering what you'd break before enforcing. Roll out in report-only, fix violations, then switch to enforcement.

**Q4. What does `X-Content-Type-Options: nosniff` do, and what attack does it prevent?**
A: This header prevents **MIME type sniffing** — a browser behaviour where the browser ignores the `Content-Type` header and tries to infer the content type from the file's actual bytes. Without `nosniff`, a browser might execute a JavaScript file served as `text/plain` if the bytes look like JavaScript.

```http
X-Content-Type-Options: nosniff
```

**Attack prevented — MIME confusion:** an attacker uploads a file named `avatar.jpg` that is actually a JavaScript file. The server serves it as `image/jpeg`. Without `nosniff`, some browsers (historically IE) sniff the content, detect it's JavaScript, and execute it. With `nosniff`, the browser strictly honours `Content-Type: image/jpeg` and refuses to execute it as JavaScript.

This is particularly relevant for applications that serve user-uploaded files from the same origin as the application. Even with `nosniff`, serving user uploads from a separate domain (`uploads.example.com`) with no session cookies is the more robust defence — but `nosniff` is a mandatory baseline.

Helmet sets this header by default. It has only one valid value (`nosniff`) and no configuration needed. Every response should include it.

**Q5. What does `X-XSS-Protection` do, and why is it largely obsolete?**
A: `X-XSS-Protection` was a header for Internet Explorer and early Chrome that activated the browser's built-in XSS auditor — a heuristic filter that tried to detect reflected XSS payloads in URLs and block them.

```http
X-XSS-Protection: 0          # disable (recommended today)
X-XSS-Protection: 1          # enable, sanitise
X-XSS-Protection: 1; mode=block  # enable, block the page entirely
```

It is now **obsolete and potentially harmful**:
- Chrome removed its XSS auditor in Chrome 78 (2019).
- Firefox never implemented it.
- The XSS auditor in IE/early Chrome had documented bypasses and, paradoxically, could be exploited to *cause* XSS by transforming safe code into a vulnerability through its sanitisation logic.
- Setting `X-XSS-Protection: 1; mode=block` in modern browsers has no effect since the auditor is gone, but setting `0` explicitly signals intent and prevents any legacy browser from activating a potentially harmful auditor.

Helmet 5+ sets `X-XSS-Protection: 0` by default — the correct choice. Rely on CSP (`script-src`) for XSS prevention, not this deprecated mechanism. Mention this in interviews when asked — knowing that this header is obsolete and *why* is a 5 YOE-level signal.

## Section 3: Headers That Control Transport Security

**Q6. What is `Strict-Transport-Security` (HSTS), and how does it prevent SSL stripping?**
A: HSTS tells the browser that this domain must only be accessed over HTTPS — never HTTP — for a defined duration. Once a browser receives an HSTS header, it will refuse to make plain HTTP connections to that domain and will automatically upgrade them to HTTPS internally, before any network request is made.

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

**Directives:**
- `max-age=31536000` — 1 year in seconds. The browser remembers the HSTS policy for this duration after the last response including this header. OWASP recommends at least 6 months; 1 year is standard; 2 years is required for HSTS preload eligibility.
- `includeSubDomains` — applies the policy to all subdomains (`*.example.com`). Without this, `http://sub.example.com` is still accessible in plain HTTP even if the main domain enforces HSTS.
- `preload` — opts into the browser's hardcoded HSTS preload list (submit at hstspreload.org). Before the browser has ever visited your domain (first visit, cleared cache), it will still use HTTPS because your domain is in the preload list burned into the browser binary. This eliminates the "trust on first use" gap.

**SSL stripping attack prevented:** without HSTS, an attacker on the network intercepts the user's initial plain HTTP request to `http://yourbank.com` before the redirect to HTTPS fires. The attacker serves the HTTP version, proxying the HTTPS version upstream — the user sees a valid page but the connection is unencrypted. HSTS eliminates the initial HTTP request entirely — the browser never sends it.

**Critical: only serve HSTS over HTTPS.** If you serve it over HTTP, an attacker can inject a false HSTS header with `max-age=0` to strip HSTS protection. Helmet sets HSTS only if the connection is HTTPS — verify your reverse proxy (nginx, ALB) passes the correct protocol information to Node.

**Q7. What does `Referrer-Policy` control, and which value is appropriate for a fintech application?**
A: `Referrer-Policy` controls how much information is included in the `Referer` request header when a user navigates from your page to another. By default, browsers include the full URL in `Referer` — including path, query string, and hash — which can leak sensitive data.

```http
Referrer-Policy: strict-origin-when-cross-origin
```

**Why it matters in fintech:** URLs in financial applications often contain sensitive parameters:
- `https://loans.example.com/applications/loan_abc123/review?token=xyz` — loan ID and a review token in the URL
- `https://payments.example.com/confirm?amount=50000&account=9876543210` — transaction details in the URL

Without a restrictive `Referrer-Policy`, clicking an external link from these pages sends the full URL (including token and account number) to the external site's server via the `Referer` header. That server may log it, exposing the sensitive parameters.

**Common values:**
- `no-referrer` — never send `Referer`. Maximum privacy but breaks analytics and some legitimate back-navigation patterns.
- `strict-origin-when-cross-origin` (Helmet default, modern browser default) — sends the full URL for same-origin requests; sends only the origin (`https://example.com`) for cross-origin requests; sends nothing for HTTPS → HTTP downgrades. The right balance for most apps.
- `same-origin` — only sends `Referer` for same-origin requests; nothing cross-origin. More private than `strict-origin-when-cross-origin`.
- `no-referrer-when-downgrade` — sends full URL unless navigating from HTTPS to HTTP. Old default, less private.

For fintech: use `strict-origin-when-cross-origin` at minimum. If URLs contain sensitive identifiers (loan IDs, customer IDs in path), consider `same-origin` or `no-referrer` to eliminate cross-origin leakage entirely.

**Q8. What does `Permissions-Policy` (formerly `Feature-Policy`) do?**
A: `Permissions-Policy` lets the server disable browser features and APIs for the current page — including third-party iframes embedded within it. It prevents embedded scripts or compromised third-party content from accessing powerful browser APIs that your application doesn't use.

```http
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), interest-cohort=()
```

**Syntax:** `feature=()` disables entirely; `feature=(self)` allows on your own origin; `feature=(self "https://trusted.com")` allows on your origin and a trusted third party.

**What each restriction prevents:**
- `camera=(), microphone=()` — a compromised ad script or XSS payload can't activate the camera or microphone to spy on the user.
- `geolocation=()` — location data can't be exfiltrated by injected scripts.
- `payment=()` — disables the Payment Request API if you're not using it; prevents a compromised script from intercepting payment flows.
- `interest-cohort=()` — opts out of Google's FLoC (Federated Learning of Cohorts) tracking.
- `usb=()` — prevents WebUSB device access.

For a fintech application that uses none of these APIs: disable everything with `()`. If you use the Payment Request API, allow only `payment=(self)` — not `payment=(*)` (any origin). The principle is the same as network firewall rules: default deny, explicitly allow what you need.

## Section 4: Headers That Control Framing and Cross-Origin Isolation

**Q9. What does `X-Frame-Options` do, and how does it differ from CSP `frame-ancestors`?**
A: `X-Frame-Options` controls whether your page can be embedded in a `<frame>`, `<iframe>`, or `<object>` on another site. It prevents **clickjacking** — an attack where the attacker embeds your page in a transparent iframe over a deceptive page, tricking the user into clicking buttons on your page while thinking they're clicking the attacker's UI.

```http
X-Frame-Options: DENY          # cannot be framed by anyone, including same origin
X-Frame-Options: SAMEORIGIN    # can only be framed by same-origin pages
X-Frame-Options: ALLOW-FROM https://partner.com  # only by a specific origin
```

**CSP `frame-ancestors` is the modern replacement:**
```http
Content-Security-Policy: frame-ancestors 'none'        # equivalent to DENY
Content-Security-Policy: frame-ancestors 'self'         # equivalent to SAMEORIGIN
Content-Security-Policy: frame-ancestors https://partner.com  # specific allowlist
```

Differences:
- `frame-ancestors` supports multiple origins in one directive; `X-Frame-Options: ALLOW-FROM` only accepts a single origin and is not supported in Chrome/Firefox.
- `frame-ancestors` is part of CSP (one consolidated header); `X-Frame-Options` is a separate header.
- `X-Frame-Options` is supported in more legacy browsers (IE8+).
- If both headers are present, CSP `frame-ancestors` takes precedence in modern browsers.

Best practice: set **both** `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'` for maximum coverage. Helmet sets both by default. For fintech apps with no legitimate embedding use case, `DENY` / `'none'` is the correct value — your login page should never be embeddable in an external site.

**Q10. What are the Cross-Origin headers — `CORP`, `COEP`, and `COOP` — and what threat do they address?**
A: These three headers address **Spectre-class side-channel attacks** — hardware-level timing attacks that can read cross-origin memory by exploiting CPU speculative execution. They were introduced after the Spectre/Meltdown disclosures to restrict which cross-origin data can be loaded into a shared process/memory space with your page.

**`Cross-Origin-Resource-Policy: same-origin` (CORP):**
```http
Cross-Origin-Resource-Policy: same-origin  # or same-site, cross-origin
```
Set on *resources* (images, scripts, API responses). Tells the browser that this resource must not be loaded by cross-origin pages. Prevents other sites from reading your resources via `<img src>`, `<script src>`, or `fetch()` even if CORS wouldn't normally block it (CORS controls JS *access* to responses; CORP controls *loading* of the resource into another origin's process).

**`Cross-Origin-Embedder-Policy: require-corp` (COEP):**
```http
Cross-Origin-Embedder-Policy: require-corp
```
Set on *your page*. Requires that every cross-origin resource loaded by the page either has `Cross-Origin-Resource-Policy: cross-origin` set or is served with a CORS header. Prevents your page from loading resources that haven't explicitly opted into cross-origin embedding.

**`Cross-Origin-Opener-Policy: same-origin` (COOP):**
```http
Cross-Origin-Opener-Policy: same-origin
```
Set on *your page*. Ensures your page and any pages it opens (via `window.open()`) cannot share a browsing context group. Prevents a malicious page opened by yours (or vice versa) from accessing your `window` object to mount timing attacks.

**Why COEP + COOP together matter:** when both are set, the browser enables `SharedArrayBuffer` and high-resolution `performance.now()` — APIs that were disabled globally after Spectre. If your app uses WebAssembly or high-performance shared memory (e.g., audio/video processing), you need these headers to re-enable those APIs safely.

For most fintech APIs: set `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin` as defaults. Be careful with `COEP: require-corp` — it will break any third-party content (analytics, CDN assets) that doesn't set `CORP: cross-origin`. Test thoroughly before enforcing.

**Q11. What does `X-Permitted-Cross-Domain-Policies` do, and is it still relevant?**
A: This header controls whether Adobe Flash and Adobe Acrobat (PDF viewer) can make cross-domain requests by loading a `crossdomain.xml` policy file from your server. Setting it to `none` prevents these legacy plugins from loading any cross-domain policy:

```http
X-Permitted-Cross-Domain-Policies: none
```

Flash reached end-of-life in January 2021 and is blocked in all modern browsers. This header is therefore largely irrelevant for new applications. However, Helmet includes it because: some enterprise environments still have legacy Flash content on internal tools; some PDF reader plugins still honour it; and setting it to `none` costs nothing and eliminates a potential attack surface on clients that still run Adobe software.

**Q12. What does `X-DNS-Prefetch-Control` do?**
A: Browsers proactively resolve DNS for links they find on a page — even links the user hasn't clicked — to reduce latency when the user eventually does click. `X-DNS-Prefetch-Control` disables this:

```http
X-DNS-Prefetch-Control: off
```

**Privacy/security concern:** DNS prefetching for links on your page (including any user-generated content with links) can leak to DNS resolvers that the user *intends* to visit those URLs — before they've clicked. In a fintech context where URLs may encode loan IDs or customer reference numbers, prefetching external links could leak those identifiers to DNS resolvers. It also causes DNS lookups for links in private/sensitive contexts (account pages) to leave traces in DNS logs.

The tradeoff: disabling prefetching slightly slows subsequent navigation. For a security-sensitive application, this is acceptable — Helmet disables it by default. You can re-enable it explicitly if performance is a concern and your URLs contain no sensitive identifiers:

```typescript
app.use(helmet({ dnsPrefetchControl: { allow: true } }));
```

## Section 5: Headers That Remove Information

**Q13. What does hiding the `X-Powered-By` header accomplish, and why does it matter?**
A: By default, Express sets `X-Powered-By: Express` on every response. This is an information disclosure — it tells an attacker (and automated scanners) exactly which framework is running, making it easier to target known framework-specific vulnerabilities.

```http
# Default Express response — information disclosure
X-Powered-By: Express

# After Helmet (or app.disable('x-powered-by')) — removed
# (header is absent)
```

Helmet removes this header entirely via `app.disable('x-powered-by')`. This is **security through obscurity** — removing the header doesn't fix underlying vulnerabilities, but it raises the cost of reconnaissance. An automated scanner that fingerprints the framework before targeting known CVEs gets no free information.

This should be complemented with:
- Removing version information from error messages (don't expose `Express 4.18.2` in stack traces).
- Removing server type from nginx/ALB headers (`server_tokens off` in nginx).
- Returning generic error messages from your application (catch all 500s and return `{"error": "Internal server error"}` rather than stack traces).

**Q14. What is the `Server` header, and does Helmet remove it?**
A: The `Server` header is set by the web server or reverse proxy (nginx, Apache, AWS ALB) — not by Express or NestJS. It typically contains the server software name and version: `Server: nginx/1.25.3` or `Server: awselb/2.0`.

Helmet operates at the Express/Node level and cannot remove headers set by upstream infrastructure. To remove or obscure the `Server` header:

```nginx
# nginx.conf
server_tokens off;  # removes version from Server header (shows "nginx" only)
# For complete removal, use headers_more module:
more_clear_headers Server;
```

```hcl
# AWS ALB — cannot remove Server header; it shows "awselb/2.0" and is not configurable
# Mitigate by sitting CloudFront or a WAF in front and stripping/replacing the header there
```

In a NestJS + nginx architecture: disable `server_tokens` in nginx config, remove `X-Powered-By` via Helmet, and strip `X-AspNet-Version` / `X-AspNetMvc-Version` (not applicable to Node, but relevant if you have mixed infrastructure). The goal is minimising the information surface available to a scanner before it sends its first malicious request.

## Section 6: Complete Configuration, Testing, and Real-World Scenarios

**Q15. What is the complete production Helmet configuration for a NestJS fintech API, with rationale for each choice?**
A:
```typescript
// main.ts
import helmet from 'helmet';

app.use(helmet({
  // CSP — the most impactful header; tune to your actual resource sources
  contentSecurityPolicy: {
    useDefaults: false,  // don't use Helmet's defaults — define explicitly
    directives: {
      defaultSrc:  ["'self'"],
      scriptSrc:   ["'self'"],                    // no inline scripts, no CDN unless needed
      styleSrc:    ["'self'"],                    // no unsafe-inline
      imgSrc:      ["'self'", 'data:'],           // data: for base64 images
      fontSrc:     ["'self'"],
      connectSrc:  ["'self'"],                    // XHR/fetch/WebSocket to same origin
      objectSrc:   ["'none'"],                    // no Flash/plugins
      baseUri:     ["'self'"],                    // no base tag injection
      formAction:  ["'self'"],                    // form submissions to same origin
      frameAncestors: ["'none'"],                 // no embedding (clickjacking)
      upgradeInsecureRequests: [],                // upgrade http: → https: loads
    },
  },

  // HSTS — enforce HTTPS for 1 year, all subdomains
  strictTransportSecurity: {
    maxAge:            31536000,  // 1 year
    includeSubDomains: true,
    preload:           true,      // submit to hstspreload.org separately
  },

  // Referrer — origin only on cross-origin requests
  referrerPolicy: { policy: 'strict-origin-when-cross-origin' },

  // Frame options — no embedding anywhere (belt-and-suspenders with CSP frame-ancestors)
  frameguard: { action: 'deny' },

  // MIME sniffing — always nosniff
  noSniff: true,  // default

  // XSS Protection — disable the broken auditor
  xssFilter: false,  // sets X-XSS-Protection: 0

  // DNS prefetch — disabled for privacy
  dnsPrefetchControl: { allow: false },  // default

  // Cross-origin isolation (be careful — can break third-party content)
  crossOriginOpenerPolicy:   { policy: 'same-origin' },
  crossOriginResourcePolicy: { policy: 'same-origin' },
  crossOriginEmbedderPolicy: false,  // disabled unless you need SharedArrayBuffer

  // Feature/Permissions policy — disable all APIs we don't use
  // Note: Helmet doesn't set Permissions-Policy directly (as of v7)
  // Set it manually:
}));

// Permissions-Policy — set manually as Helmet v7 doesn't include it
app.use((req, res, next) => {
  res.setHeader(
    'Permissions-Policy',
    'camera=(), microphone=(), geolocation=(), payment=(), usb=(), interest-cohort=()',
  );
  next();
});

// Remove X-Powered-By (Helmet does this, but explicit is better)
app.disable('x-powered-by');
```

**Q16. How do you tune CSP for a NestJS API that serves only JSON (no HTML) vs. one that serves an SSR application?**
A: The CSP requirements are fundamentally different for a pure API vs. an SSR application:

**Pure JSON API (no HTML responses):**
```typescript
// A JSON API doesn't have a browser rendering context — no scripts, styles, or frames.
// CSP on API responses is minimally useful but still good hygiene.
// The most important directive is restricting what browsers do with API responses
// if they're ever viewed directly.
contentSecurityPolicy: {
  directives: {
    defaultSrc:     ["'none'"],  // block everything
    frameAncestors: ["'none'"],  // prevent API responses from being framed
  },
},
```

**SSR application (renders HTML with assets):**
```typescript
// Full CSP required — scope every directive to actual sources your app uses.
// Start in report-only mode, collect violations for 2 weeks, then enforce.
contentSecurityPolicy: {
  directives: {
    defaultSrc:  ["'self'"],
    scriptSrc:   ["'self'", "'nonce-${nonce}'"],  // nonces for any inline scripts
    styleSrc:    ["'self'", "'nonce-${nonce}'"],   // nonces for inline styles
    imgSrc:      ["'self'", 'data:', 'https://static.example.com'],
    connectSrc:  ["'self'", 'https://api.example.com'],
    fontSrc:     ["'self'", 'https://fonts.gstatic.com'],
    objectSrc:   ["'none'"],
    baseUri:     ["'self'"],
    formAction:  ["'self'"],
    frameAncestors: ["'none'"],
    reportUri:   ['/csp-violations'],   // collect violation reports
  },
},
```

For an NestJS BFF (Backend for Frontend) serving both an API and SSR pages: apply different Helmet configurations per route prefix using route-scoped middleware rather than global middleware:

```typescript
// API routes — minimal CSP
app.use('/api', helmet({ contentSecurityPolicy: { directives: { defaultSrc: ["'none'"] } } }));

// Web routes — full CSP
app.use('/', helmet({ contentSecurityPolicy: { /* full config */ } }));
```

**Q17. How do you test that security headers are correctly set in CI?**
A: Three levels of testing:

**Unit / integration test — assert headers on responses:**
```typescript
// security-headers.e2e-spec.ts
describe('Security Headers', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const module = await Test.createTestingModule({ imports: [AppModule] }).compile();
    app = module.createNestApplication();
    app.use(helmet(/* your config */));
    await app.init();
  });

  it('sets Strict-Transport-Security', async () => {
    const res = await request(app.getHttpServer()).get('/health');
    expect(res.headers['strict-transport-security'])
      .toMatch(/max-age=31536000/);
    expect(res.headers['strict-transport-security'])
      .toContain('includeSubDomains');
  });

  it('sets X-Content-Type-Options: nosniff', async () => {
    const res = await request(app.getHttpServer()).get('/health');
    expect(res.headers['x-content-type-options']).toBe('nosniff');
  });

  it('does not expose X-Powered-By', async () => {
    const res = await request(app.getHttpServer()).get('/health');
    expect(res.headers['x-powered-by']).toBeUndefined();
  });

  it('sets Content-Security-Policy with required directives', async () => {
    const res  = await request(app.getHttpServer()).get('/health');
    const csp  = res.headers['content-security-policy'];
    expect(csp).toContain("default-src 'self'");
    expect(csp).toContain("object-src 'none'");
    expect(csp).toContain("frame-ancestors 'none'");
  });

  it('sets X-Frame-Options: DENY', async () => {
    const res = await request(app.getHttpServer()).get('/health');
    expect(res.headers['x-frame-options']).toBe('DENY');
  });
});
```

**External scanner in CI:**
```yaml
# .github/workflows/security.yml
- name: Security headers scan (securityheaders.com API)
  run: |
    SCORE=$(curl -s "https://securityheaders.com/?q=https://staging.example.com&followRedirects=on" \
      | grep -oP '(?<=grade-)[A-F](?=")' | head -1)
    echo "Security headers grade: $SCORE"
    [ "$SCORE" = "A" ] || [ "$SCORE" = "A+" ] || exit 1
```

**Mozilla Observatory in CI:**
```bash
npx observatory --format json https://staging.example.com | jq '.grade' | grep -E '"A\+?"'
```

**Q18. What happens if you apply Helmet to a NestJS app that proxies through an AWS ALB or nginx — which headers might conflict or be duplicated?**
A: Several headers can be set by both the Node app (via Helmet) and the upstream infrastructure, creating duplicates or conflicts:

**`Strict-Transport-Security`** — AWS ALB can add HSTS headers, and nginx can too. If both ALB and Helmet set HSTS, the response may contain two `Strict-Transport-Security` headers. Browsers typically honour the first one, but it's messy. Solution: set HSTS in exactly one place — either at the ALB/nginx layer (preferred, because it applies even to non-Node error responses) or in Helmet, but not both.

**`X-Frame-Options`** — nginx's `add_header X-Frame-Options DENY` combined with Helmet's `frameguard` will produce duplicate headers. HTTP spec says for response headers that appear multiple times, behaviour is implementation-defined — some clients take the last value, some the first. Solution: remove from one layer.

**`Content-Security-Policy`** — duplicate CSP headers are treated by browsers as if all directives from all headers must be satisfied simultaneously. This is more restrictive than either alone — but it's confusing and hard to audit. Set CSP in one place only.

**General rule:** let Helmet handle application-level security headers (CSP, X-Content-Type-Options, Referrer-Policy). Let nginx/ALB handle infrastructure-level headers (HSTS, Server header, sometimes X-Frame-Options). Document which layer sets which header, and add a CI test that counts occurrences of each security header and fails if any appears more than once.

**Q19. Scenario: "Your fintech frontend loads scripts from a CDN, embeds Google Analytics, and uses inline styles from a UI component library. The security team requires a strict CSP. How do you satisfy both?**
A: This is the most common real-world CSP challenge — a strict policy that accommodates legitimate third-party dependencies. The approach:

**Step 1 — Audit all resource origins (use CSP report-only first):**
```http
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-violations
```
Run for 2 weeks in staging and production. Collect every violation to discover exactly which external origins your app uses.

**Step 2 — Build an explicit allowlist from the audit:**
```typescript
contentSecurityPolicy: {
  directives: {
    defaultSrc:  ["'self'"],
    scriptSrc: [
      "'self'",
      'https://cdn.jsdelivr.net',             // CDN for specific libraries
      'https://www.googletagmanager.com',      // Google Analytics loader
      'https://www.google-analytics.com',
      // Do NOT use 'unsafe-inline' — use nonces instead
    ],
    styleSrc: [
      "'self'",
      // Inline styles from UI library — use nonces if possible
      // If the library injects styles via JS, consider 'unsafe-hashes' with specific hashes
      // Last resort: 'unsafe-inline' with a note that this weakens XSS protection
      "'unsafe-inline'",  // document why this is necessary and plan to remove it
    ],
    imgSrc:     ["'self'", 'data:', 'https://www.google-analytics.com'],
    connectSrc: ["'self'", 'https://www.google-analytics.com', 'https://api.example.com'],
    scriptSrcAttr: ["'none'"],  // no inline event handlers (onclick="...")
    objectSrc:  ["'none'"],
    baseUri:    ["'self'"],
    frameAncestors: ["'none'"],
  },
},
```

**Step 3 — Replace `unsafe-inline` for scripts with nonces or hashes:**
```typescript
// For truly static inline scripts, use a hash instead of a nonce
// Generate: echo -n '<script>var x=1;</script>' | openssl dgst -sha256 -binary | openssl base64
scriptSrc: ["'self'", "'sha256-abc123def456...'"],  // specific inline script hash
```

**Step 4 — Migrate the UI library to avoid inline styles:**
Many component libraries inject inline styles via JavaScript (MUI, Ant Design). Some support nonces:
```typescript
// MUI example — pass nonce to the style engine
<StyleEngineProvider nonce={nonce}>
  <App />
</StyleEngineProvider>
// Then add the nonce to CSP styleSrc
```

**Step 5 — Accept `unsafe-inline` for styles as a temporary, documented exception.** `unsafe-inline` for *styles* is a much lower risk than for *scripts* — CSS injection can cause UI deception (clickjacking-like attacks) but cannot directly exfiltrate data or execute code. Document it as a known exception, track removal as a debt item.

**Q20. Scenario: "A penetration test report flags that your API returns `Content-Security-Policy` headers without `object-src 'none'` and without `base-uri 'self'`. Explain why these specific gaps matter.**
A: Both omissions leave exploitable attack surface even if `default-src 'self'` is set:

**`object-src` not set to `'none'`:**
`<object>`, `<embed>`, and `<applet>` tags can load Flash SWF files, Java applets, and other plugin content. Even though Flash is dead in modern browsers, `object-src` has two remaining risks:
1. Legacy enterprise clients running IE with Flash or Java plugins — still exist in fintech B2B portals.
2. XSS via plugin content — `<object data="javascript:...">` and similar vectors bypass `script-src` because `object-src` is a separate directive. If `default-src 'self'` is set but `object-src` is not explicitly set, the browser inherits `'self'` for `object-src` — meaning `<object data="/some-uploaded-file.swf">` could execute plugin content from your own origin. Setting `object-src 'none'` eliminates this entirely.

**`base-uri` not set:**
Without `base-uri 'self'`, an XSS payload can inject `<base href="https://attacker.com">` into the page. This changes the base URL for all relative URLs on the page — every `<script src="./app.js">`, `<form action="/login">`, and `<a href="/logout">` now resolves relative to `attacker.com`. The attacker's server serves a malicious `app.js`, intercepts login form submissions, and redirects logout links. This is a base tag injection attack, and `base-uri 'self'` is the only CSP directive that prevents it. `default-src 'self'` does not cover `base-uri` — it must be set explicitly.

The correct fix:
```http
Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'self'; ...
```

## Section 7: Header Reference and Trade-offs

**Q21. Which Helmet headers are set by default, and which require explicit configuration?**
A: Helmet v7 defaults (as of 2024):

```
Set by default (no config needed):
  ✓ Content-Security-Policy        (moderate defaults — customize for your app)
  ✓ Cross-Origin-Embedder-Policy   (require-corp)
  ✓ Cross-Origin-Opener-Policy     (same-origin)
  ✓ Cross-Origin-Resource-Policy   (same-origin)
  ✓ Origin-Agent-Cluster           (enabled)
  ✓ Referrer-Policy                (no-referrer)   ← Helmet default; consider strict-origin-when-cross-origin
  ✓ Strict-Transport-Security      (max-age=15552000; includeSubDomains)
  ✓ X-Content-Type-Options         (nosniff)
  ✓ X-DNS-Prefetch-Control         (off)
  ✓ X-Download-Options             (noopen — IE-specific)
  ✓ X-Frame-Options                (SAMEORIGIN)    ← change to DENY if no embedding needed
  ✓ X-Permitted-Cross-Domain-Policies  (none)
  ✓ X-Powered-By                   (removed)
  ✓ X-XSS-Protection               (0)

Require explicit configuration or are disabled by default:
  ✗ Permissions-Policy             (not set by Helmet v7 — add manually)
  ✗ Content-Security-Policy nonces (must implement per-request nonce generation)
  ✗ CSP report-uri / report-to     (must configure your violation endpoint)
  ✗ HSTS preload                   (must add preload: true explicitly)
  ✗ Cross-Origin-Embedder-Policy   (set by default but often needs disabling for third-party embeds)
```

**Q22. What are `Origin-Agent-Cluster` and `X-Download-Options`, and do they matter?**
A: Two lesser-known headers Helmet sets:

**`Origin-Agent-Cluster: ?1`** — a hint to the browser that this origin should be placed in its own agent cluster (isolated process/memory space) separate from other origins. This is a performance and security mechanism — origin isolation makes Spectre-class timing attacks harder by preventing memory sharing with other origins. It's a hint, not a guarantee, and browser support/effect varies. Set it and move on; cost is zero.

**`X-Download-Options: noopen`** — an Internet Explorer 8 specific header. Without it, IE allowed users to directly "Open" (not save) downloaded files, which would run them in the context of your site rather than a sandboxed local context. IE is dead (Edge replaced it, and IE reached end-of-life in June 2022). This header has no effect on any modern browser. Helmet still sets it for completeness on legacy enterprise environments. Zero cost, keep it.

**Q23. How do security headers interact with a React SPA served from a CDN vs. a server-rendered NestJS application?**
A: The serving model fundamentally changes where and how you set security headers:

**React SPA on CDN (S3 + CloudFront):**
- Headers must be set at the CDN layer — CloudFront response headers policies.
- No NestJS involved for HTML/JS serving; NestJS is the API backend only.
- CSP must account for React's runtime behaviour (code splitting, dynamic imports, React DevTools in dev).
- API responses from NestJS still need security headers — Helmet on the API.
- CloudFront supports custom response headers but CSP nonces are very hard to implement (no per-request dynamic headers in standard CloudFront; requires Lambda@Edge).

```json
// CloudFront Response Headers Policy (via console or Terraform)
{
  "SecurityHeadersConfig": {
    "StrictTransportSecurity": { "AccessControlMaxAgeSec": 31536000, "IncludeSubdomains": true },
    "ContentTypeOptions": { "Override": true },
    "FrameOptions": { "FrameOption": "DENY", "Override": true },
    "XSSProtection": { "Protection": false, "Override": true },
    "ReferrerPolicy": { "ReferrerPolicy": "strict-origin-when-cross-origin", "Override": true }
  },
  "CustomHeadersConfig": {
    "Items": [
      { "Header": "Permissions-Policy", "Value": "camera=(), microphone=()", "Override": true }
    ]
  }
}
```

**Server-rendered NestJS application:**
- Helmet runs as Express middleware on every request.
- Per-request nonces are possible — generate a nonce in middleware, set it in CSP header and pass it to the template engine.
- Full control over every response header per route.
- HSTS and other headers are set by Helmet on every HTML and API response.

**Q24. Scenario: "After enabling Helmet with default settings on an existing NestJS application, several frontend features break. How do you diagnose and fix this without weakening security?**
A: Breaking changes from Helmet typically fall into three categories. Diagnose via browser DevTools console (blocked resource errors) and the Network tab (which requests are failing and why):

**1. CSP blocks a resource:**
```
Refused to load the script 'https://cdn.example.com/lib.js' because it violates
the Content Security Policy directive: "script-src 'self'"
```
Fix: add the blocked origin to the appropriate CSP directive. Don't add `'unsafe-inline'` or `'unsafe-eval'` unless you've exhausted all alternatives.

**2. `X-Frame-Options: SAMEORIGIN` breaks a legitimate embed:**
```
Refused to display 'https://yourapp.com/widget' in a frame because it set 
'X-Frame-Options' to 'sameorigin'.
```
Fix: change to `ALLOW-FROM` (limited browser support) or use CSP `frame-ancestors 'https://partner.com'` and remove `X-Frame-Options`. Apply only to the specific route serving the embeddable widget:
```typescript
// Route-specific header override
@Get('widget')
widget(@Res() res: Response) {
  res.removeHeader('X-Frame-Options');
  res.setHeader('Content-Security-Policy', "frame-ancestors 'https://partner.com'");
  // render widget
}
```

**3. `COEP: require-corp` breaks third-party resources:**
```
Cross-Origin-Embedder-Policy blocked loading of resource 'https://widget.example.com/...'
```
Fix: set `crossOriginEmbedderPolicy: false` in Helmet options, or ensure the third-party resource sets `Cross-Origin-Resource-Policy: cross-origin`.

**General approach:** enable Helmet in report-only mode for CSP first, collect violations for a week, fix them, then enforce. For all other headers (not CSP), they either work or they break immediately with a specific browser error — diagnose from DevTools and fix per-route if needed.

**Q25. What is the `Expect-CT` header, and why did Helmet remove it?**
A: `Expect-CT` (Certificate Transparency) was a header that instructed browsers to require that TLS certificates for a domain be logged in public Certificate Transparency (CT) logs. It allowed site operators to detect misissued certificates (e.g., an attacker obtaining a fraudulent certificate for your domain from a compromised CA).

```http
Expect-CT: max-age=86400, enforce, report-uri="https://example.com/ct-report"
```

Helmet removed `Expect-CT` in v7 (2022) because **Chrome made Certificate Transparency mandatory for all publicly trusted certificates** from April 2018 onwards. Every certificate from a publicly trusted CA must be logged in CT logs regardless of whether `Expect-CT` is set — the header is now redundant. Firefox and Safari followed similar policies. Setting the header today has no meaningful security effect on modern browsers.

The broader lesson this illustrates: security headers are not static. The web platform evolves — some headers become unnecessary (`Expect-CT`, `X-XSS-Protection`), some become more important (`COOP`, `COEP`, `CORP` post-Spectre), and some are still emerging (the `Reporting-Endpoints` API replacing `report-uri`). At 5 YOE you're expected to know not just what headers exist today but why they exist and when they become obsolete.

## Quick Comparison Table

| Header | Set by Helmet default | Attack prevented | Notes |
|---|---|---|---|
| `Content-Security-Policy` | Yes (basic) | XSS script execution, data exfiltration | Must customise — defaults are rarely right for your app |
| `Strict-Transport-Security` | Yes | SSL stripping, protocol downgrade | Add `preload` explicitly; submit to hstspreload.org |
| `X-Content-Type-Options: nosniff` | Yes | MIME confusion, content sniffing | Always `nosniff`; no configuration needed |
| `X-Frame-Options` | Yes (`SAMEORIGIN`) | Clickjacking | Change to `DENY` if no framing needed; superseded by CSP `frame-ancestors` |
| `Referrer-Policy` | Yes (`no-referrer`) | URL parameter leakage | Consider `strict-origin-when-cross-origin` for analytics |
| `Permissions-Policy` | No | Sensor/API abuse via injected scripts | Set manually; disable all APIs you don't use |
| `X-XSS-Protection` | Yes (`0`) | Nothing (deprecated) | Setting `0` explicitly disables the broken browser auditor |
| `X-Powered-By` | Removed | Framework fingerprinting | Removed via `app.disable('x-powered-by')` |
| `X-DNS-Prefetch-Control: off` | Yes | DNS-based URL leakage | Re-enable if performance matters and URLs are non-sensitive |
| `Cross-Origin-Opener-Policy` | Yes (`same-origin`) | Spectre-class timing attacks | Can break OAuth popups — may need `same-origin-allow-popups` |
| `Cross-Origin-Resource-Policy` | Yes (`same-origin`) | Cross-origin resource loading | Break third-party embeds if too strict |
| `Cross-Origin-Embedder-Policy` | Yes (`require-corp`) | Spectre via SharedArrayBuffer | Often needs disabling for apps with third-party content |
| `X-Permitted-Cross-Domain-Policies: none` | Yes | Flash/PDF cross-domain requests | Obsolete but costless to set |
| `Expect-CT` | Removed (v7) | Certificate misissuance | Removed because CT is now mandatory — header is redundant |

Know CSP deeply — it's the most complex and most impactful header. The `object-src 'none'` and `base-uri 'self'` omissions (Q20) come up in penetration test reviews and are a strong differentiator. Know the difference between `whitelist` and `forbidNonWhitelisted` for DTOs, and the difference between `X-Frame-Options` and CSP `frame-ancestors` — both distinguish someone who's read the docs from someone who's debugged a broken embedding.
