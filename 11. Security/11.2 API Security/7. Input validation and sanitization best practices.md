# Security: Input Validation & Sanitization Best Practices — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals and Mental Models

**Q1. What is the difference between input validation and input sanitization, and when do you use each?**
A: Validation and sanitization are distinct operations applied at different points in data handling, and conflating them leads to misapplied defenses.

**Validation** is a binary decision: does this input conform to the expected structure, type, range, and format? If not, reject it and return an error. The input is never used. Validation is a gate — either the data passes and continues into the system, or it fails and the request is terminated.

```python
# Validation — accept or reject, nothing in between
def validate_transfer_amount(amount: str) -> Decimal:
    try:
        value = Decimal(amount)
    except InvalidOperation:
        raise ValidationError("Amount must be a valid number")

    if value <= 0:
        raise ValidationError("Amount must be positive")
    if value > Decimal("1000000"):
        raise ValidationError("Amount exceeds single-transfer limit")
    if value.as_tuple().exponent < -2:
        raise ValidationError("Amount cannot have more than 2 decimal places")

    return value   # returns a typed, validated value — not the original string
```

**Sanitization** is a transformation: modify the input to make it safe for a specific context. It does not reject input — it cleans it. Sanitization is appropriate when user-controlled content must be preserved but made safe for rendering, storage, or transmission.

```python
# Sanitization — transform, do not reject
import bleach

def sanitize_bio(raw_html: str) -> str:
    # User's bio may contain HTML formatting — we preserve safe tags, strip dangerous ones
    return bleach.clean(
        raw_html,
        tags=["b", "i", "em", "strong", "p", "br", "ul", "ol", "li"],
        attributes={},
        strip=True,
    )
    # Input:  "<b>Hello</b> <script>steal()</script>"
    # Output: "<b>Hello</b> "  — the safe tag is preserved, script is stripped
```

**When to use which:**

| Scenario | Approach | Reason |
|---|---|---|
| API parameter (user_id, amount, date) | Validation only | These must match exact types — any deviation is an error |
| Search query string (plain text) | Validation (length, charset) + output encoding at render | The raw string is stored; encoding happens at display time |
| User-submitted rich text / bio | Validation (length) + sanitization (HTML allowlist) | User intent to use HTML must be preserved but made safe |
| File upload | Validation (type, size, content) + sanitization (strip metadata) | Accept legitimate files; remove dangerous payloads |
| Username, email, phone | Validation (format, length, charset) | These have strict formats — reject anything that doesn't conform |

The critical rule: **validation is the primary security control; sanitization is for cases where you must accept rich user content**. An API endpoint accepting a `user_id` integer should validate that it's an integer and reject anything else — it should never sanitize it. Sanitization without validation is attempting to make garbage safe, which is far harder than rejecting garbage at the door.

**Q2. What is the "trust no input" principle, and what are all the input sources a backend service must treat as untrusted?**
A: The trust-no-input principle states that any data originating outside the current process's own code must be treated as potentially malicious until validated. The mistake is assuming that because data comes from a "trusted" source — a database, a partner API, another internal service — it is safe to use without validation.

Sources that must be treated as untrusted:

```
HTTP layer:
  request.body              — JSON, XML, form data; attacker controls all of it
  request.query_params      — URL query string; trivially manipulable
  request.path_params       — /users/{id} where id is attacker-controlled
  request.headers           — Content-Type, Authorization, X-Forwarded-For, custom headers
  request.cookies           — all cookie values, including session identifiers
  request.files             — file uploads; filename, MIME type, content are all attacker-controlled

Environment and configuration:
  Environment variables     — if an attacker can influence deployment, they can set env vars
  Config files              — if config is loaded from user-accessible paths
  Command-line arguments    — for CLI tools

Storage-originated data (second-order):
  Database rows             — data stored by users in a previous request
  Cache values (Redis)      — cached user input may have been stored unsafely
  File contents             — files written by users or third-party processes
  Message queue payloads    — Kafka/SQS messages from external publishers

External services:
  Third-party API responses — a compromised vendor API returns malicious data
  Webhook payloads          — partner sends a webhook; payload is attacker-influenced
  OAuth tokens / JWTs       — the token structure is validated cryptographically,
                              but the claims inside must still be validated for business rules
  DNS responses             — SSRF via DNS rebinding; resolved IPs must be validated
  LDAP / Active Directory   — LDAP injection if directory data is used in queries

Inter-service (microservice context):
  Data from other internal services — if service A is compromised, its output
    flowing into service B must not be trusted blindly
  Event bus payloads        — schema validation required even for internal events
  gRPC / Thrift messages    — type safety helps but does not guarantee value safety
```

Second-order untrusted data is the most commonly overlooked. The classic example from SQL injection: a username stored safely (parameterized insert) is retrieved later and concatenated into a new query. The database is a storage mechanism, not a trust boundary. Every time data crosses a processing boundary — from storage to application, from one service to another — it must be re-validated for the context it is entering.

**Q3. What is the validation layering model, and at which layers should validation occur?**
A: Validation should occur at multiple independent layers, each optimized for what it can observe and enforce. No single layer is sufficient.

```
Layer 1: Network / API Gateway
  Enforces:  Rate limiting, request size limits, protocol compliance (valid HTTP),
             TLS, basic auth token presence
  Does NOT enforce: Business logic, data types, field-level constraints
  Tools:     AWS API Gateway, Kong, Nginx, Envoy

Layer 2: Framework / Route Handler
  Enforces:  Content-Type validation, request schema (required fields present,
             correct types), authentication, authorization (can this user call this endpoint?)
  Does NOT enforce: Business logic constraints (e.g., is this amount within the user's limit?)
  Tools:     Pydantic (Python), Zod/Joi (Node.js), Jakarta Bean Validation (Java),
             express-validator, go-playground/validator

Layer 3: Service / Domain Layer
  Enforces:  Business logic validation (transfer limit, account status, duplicate check),
             cross-field validation (start_date < end_date), invariants
  Does NOT enforce: Presentation concerns, persistence mechanics
  This is the most important layer — it owns the domain rules

Layer 4: Persistence / Repository Layer
  Enforces:  Database constraints (NOT NULL, UNIQUE, CHECK, FOREIGN KEY, length limits),
             type coercion at the ORM level
  These are the last line of defense — they should confirm what the service layer
  already guaranteed, not substitute for it

Layer 5: Output Encoding (not validation, but the defense at render time)
  Enforces:  Context-aware encoding before data is written to HTML, SQL, shell, etc.
  This is where sanitization for display happens — not at input time
```

The reason for layering: defense-in-depth. If Layer 2 has a bug that allows a malformed `user_id` through, Layer 3's type assertion catches it before it reaches a database query. If an ORM escape hatch is used at Layer 4, the database constraint still prevents a value that's too long from being stored. No single layer is perfect; each layer independently reduces the blast radius of failures in other layers.

A common mistake is performing all validation only in the framework layer and treating the service layer as unconditionally safe. A developer who calls the service layer directly (from a CLI, a test, a message queue consumer) bypasses the framework layer entirely — the service layer must validate its own inputs independently.

## Section 2: Type Validation and Schema Enforcement

**Q4. How do you implement schema-level validation in Python and Node.js, and what properties should a validation library enforce?**
A: Schema validation libraries convert raw input into typed, validated domain objects. The conversion is the key: after validation, the codebase works with typed Python objects or TypeScript types — not raw strings. A string that passes validation becomes a `Decimal`, a `datetime`, a validated `UUID` — a type that by construction cannot contain certain classes of attack payloads.

**Python — Pydantic:**

```python
from pydantic import BaseModel, Field, field_validator, model_validator
from pydantic import EmailStr, AnyHttpUrl
from decimal import Decimal
from datetime import datetime, timezone
from uuid import UUID
from typing import Optional
import re

class TransferRequest(BaseModel):
    # Field-level validation via type + Field constraints
    source_account_id: UUID               # must be valid UUID — rejects "1 OR 1=1"
    destination_account_id: UUID
    amount: Decimal = Field(
        gt=0,                              # > 0 (not zero, not negative)
        le=Decimal("100000"),              # <= 100,000 per transfer
        decimal_places=2,                  # max 2 decimal places
    )
    currency: str = Field(
        min_length=3,
        max_length=3,
        pattern=r"^[A-Z]{3}$",            # ISO 4217 format: USD, EUR, INR
    )
    reference: Optional[str] = Field(
        default=None,
        max_length=140,                    # length-limited
        pattern=r"^[a-zA-Z0-9\s\-_.,]*$", # explicit charset allowlist
    )
    scheduled_at: Optional[datetime] = None

    @field_validator("scheduled_at")
    @classmethod
    def scheduled_must_be_future(cls, v: Optional[datetime]) -> Optional[datetime]:
        if v is not None and v <= datetime.now(timezone.utc):
            raise ValueError("Scheduled time must be in the future")
        return v

    @model_validator(mode="after")
    def accounts_must_differ(self) -> "TransferRequest":
        if self.source_account_id == self.destination_account_id:
            raise ValueError("Source and destination accounts must be different")
        return self

# Usage in a FastAPI endpoint:
from fastapi import FastAPI, HTTPException
from pydantic import ValidationError

app = FastAPI()

@app.post("/api/transfers")
async def create_transfer(raw_body: dict, user_id: UUID = Depends(get_current_user)):
    try:
        transfer = TransferRequest.model_validate(raw_body)
    except ValidationError as e:
        # Pydantic errors are structured — safe to return field-level messages
        raise HTTPException(status_code=422, detail=e.errors())

    # transfer.amount is now a Decimal — not a string
    # transfer.source_account_id is a UUID — not a string
    # Cannot contain SQL metacharacters, HTML, or other injection payloads by type
    return await transfer_service.execute(transfer, initiator=user_id)
```

**Node.js — Zod:**

```typescript
import { z } from "zod";

const TransferSchema = z.object({
    sourceAccountId: z.string().uuid(),
    destinationAccountId: z.string().uuid(),
    amount: z
        .number()
        .positive()
        .max(100_000)
        .multipleOf(0.01),               // max 2 decimal places
    currency: z
        .string()
        .length(3)
        .regex(/^[A-Z]{3}$/),
    reference: z
        .string()
        .max(140)
        .regex(/^[a-zA-Z0-9\s\-_.,]*$/)
        .optional(),
    scheduledAt: z
        .string()
        .datetime()
        .refine(
            (val) => new Date(val) > new Date(),
            { message: "Scheduled time must be in the future" }
        )
        .optional(),
}).refine(
    (data) => data.sourceAccountId !== data.destinationAccountId,
    { message: "Source and destination accounts must be different", path: ["destinationAccountId"] }
);

// Infer the TypeScript type — no separate interface needed
type TransferRequest = z.infer<typeof TransferSchema>;

// Usage in Express:
app.post("/api/transfers", authenticate, async (req, res) => {
    const result = TransferSchema.safeParse(req.body);

    if (!result.success) {
        // ZodError contains field-level errors — safe to expose
        return res.status(422).json({
            error: "Validation failed",
            details: result.error.flatten().fieldErrors,
        });
    }

    const transfer: TransferRequest = result.data;
    // transfer.amount is a number — not a string
    // transfer.sourceAccountId is a validated UUID string
    await transferService.execute(transfer, req.user.id);
});
```

Properties a good validation library must provide:
- **Type coercion with strictness options** — `"123"` → `123` (number) is acceptable for query params; `"123abc"` → validation error.
- **Nested object and array validation** — validates arrays of items, each to a schema.
- **Custom validators** — business logic rules beyond basic types.
- **Cross-field validation** — `end_date > start_date`, `destination != source`.
- **Error messages that are safe to return** — structured, field-scoped, no internal implementation details.
- **Unknown field handling** — strip extra fields (`passthrough`, `strict` modes) — unknown fields could be parameter pollution or prototype pollution attempts.

**Q5. What is prototype pollution, and how does input validation prevent it in Node.js?**
A: Prototype pollution is a JavaScript-specific attack where an attacker sets properties on `Object.prototype` via user-controlled keys like `__proto__`, `constructor`, or `prototype`. Because every JavaScript object inherits from `Object.prototype`, polluting it affects every object in the application process — potentially escalating to authentication bypass, remote code execution, or denial of service.

```javascript
// The attack — attacker sends JSON body:
// { "__proto__": { "isAdmin": true } }

const body = JSON.parse('{"__proto__": {"isAdmin": true}}');

// In some vulnerable merge/assign patterns:
function mergeConfig(target, source) {
    for (const key of Object.keys(source)) {
        if (typeof source[key] === "object") {
            mergeConfig(target[key], source[key]);
        } else {
            target[key] = source[key];   // ← sets target.__proto__.isAdmin = true
        }
    }
}

mergeConfig(config, body);

// Now every object inherits isAdmin: true
const user = {};
console.log(user.isAdmin);  // true — attacker is now admin
```

Prevention at the validation layer:

```typescript
// Zod: unknown keys are stripped by default in .parse()
// Zod never processes __proto__ as a schema key — it validates against a known schema
const schema = z.object({ name: z.string(), amount: z.number() });
const result = schema.parse({ name: "test", __proto__: { isAdmin: true } });
// result = { name: "test", amount: <error> }  — __proto__ key is dropped

// Additional hardening: parse JSON safely
function safeJsonParse(raw: string): unknown {
    const parsed = JSON.parse(raw);
    // Reject objects containing __proto__, constructor, or prototype as keys
    const forbidden = ["__proto__", "constructor", "prototype"];
    const json = JSON.stringify(parsed);
    for (const key of forbidden) {
        if (json.includes(`"${key}"`)) {
            throw new Error(`Forbidden key in JSON payload: ${key}`);
        }
    }
    return parsed;
}

// Or use Object.create(null) for accumulator objects in manual merges:
const safe = Object.create(null);  // no prototype — __proto__ assignment has no effect
```

```python
# Python is not affected by prototype pollution (no prototype chain)
# but has analogous risks: **kwargs unpacking with user-controlled keys
def create_user(**kwargs):
    User(**kwargs)  # if kwargs contains internal model fields, attacker controls the model

# Prevention: use an explicit schema (Pydantic) — never unpack user input directly
def create_user(body: dict):
    user_data = UserCreateRequest.model_validate(body)  # validates against known fields only
    User.create(name=user_data.name, email=user_data.email)  # explicit field mapping
```

**Q6. How do you validate and handle file uploads securely?**
A: File uploads are one of the highest-risk input types — attackers can craft files with malicious content, dangerous filenames, or incorrect MIME types. Validation must cover multiple independent dimensions:

```python
import magic        # python-magic — reads actual file magic bytes, not MIME header
import hashlib
import re
import os
from pathlib import Path

ALLOWED_MIME_TYPES = {
    "image/jpeg": [b"\xff\xd8\xff"],                       # JPEG magic bytes
    "image/png":  [b"\x89PNG\r\n\x1a\n"],                  # PNG magic bytes
    "image/webp": [b"RIFF", b"WEBP"],                      # WebP
    "application/pdf": [b"%PDF"],                           # PDF
}
MAX_FILE_SIZE  = 10 * 1024 * 1024   # 10 MB
SAFE_FILENAME  = re.compile(r"^[a-zA-Z0-9][a-zA-Z0-9_\-. ]{0,254}$")

def validate_upload(file_bytes: bytes, claimed_filename: str, claimed_mime: str) -> dict:

    # 1. Size validation — before reading content (prevent memory exhaustion)
    if len(file_bytes) > MAX_FILE_SIZE:
        raise ValidationError(f"File exceeds maximum size of {MAX_FILE_SIZE // 1024 // 1024}MB")
    if len(file_bytes) == 0:
        raise ValidationError("File is empty")

    # 2. MIME type validation via magic bytes — NOT the Content-Type header
    # The Content-Type header is attacker-controlled — never trust it alone
    detected_mime = magic.from_buffer(file_bytes, mime=True)
    if detected_mime not in ALLOWED_MIME_TYPES:
        raise ValidationError(f"File type not allowed: {detected_mime}")

    # 3. Magic byte verification — double-check against known signatures
    expected_signatures = ALLOWED_MIME_TYPES[detected_mime]
    if not any(file_bytes.startswith(sig) for sig in expected_signatures):
        raise ValidationError("File content does not match declared type")

    # 4. Extension validation — must match the detected MIME type
    suffix = Path(claimed_filename).suffix.lower()
    mime_to_extensions = {
        "image/jpeg": {".jpg", ".jpeg"},
        "image/png":  {".png"},
        "image/webp": {".webp"},
        "application/pdf": {".pdf"},
    }
    allowed_exts = mime_to_extensions.get(detected_mime, set())
    if suffix not in allowed_exts:
        raise ValidationError(f"Extension {suffix!r} does not match file type {detected_mime}")

    # 5. Filename sanitization — reject path traversal and dangerous names
    basename = Path(claimed_filename).name   # strip any directory components
    if not SAFE_FILENAME.match(basename):
        raise ValidationError("Filename contains invalid characters")
    if basename.startswith("."):
        raise ValidationError("Filename cannot start with a dot")

    # 6. Never preserve the original filename for storage
    # Generate a random, content-addressed name
    content_hash = hashlib.sha256(file_bytes).hexdigest()[:16]
    safe_name = f"{content_hash}{suffix}"

    # 7. For images: re-encode through Pillow to strip polyglot payloads and EXIF metadata
    # A file that is simultaneously a valid JPEG and a valid PHP script
    # (a "polyglot") will survive magic byte checks but can be executed server-side
    from PIL import Image
    import io

    if detected_mime.startswith("image/"):
        img = Image.open(io.BytesIO(file_bytes))
        img.verify()  # raises if the image is structurally corrupt or manipulated
        # Re-encode: this strips EXIF metadata and destroys any embedded payloads
        output = io.BytesIO()
        img = Image.open(io.BytesIO(file_bytes))  # reopen after verify()
        img.save(output, format=img.format, exif=b"")  # strip EXIF
        clean_bytes = output.getvalue()
    else:
        clean_bytes = file_bytes

    return {
        "safe_filename": safe_name,
        "mime_type":     detected_mime,
        "size":          len(clean_bytes),
        "content":       clean_bytes,
    }
```

Storage rules after validation:
- Store uploads outside the web root — never in a directory served directly by the web server. Files in `/var/www/html/uploads/` can be executed if the server is misconfigured. Store in `/var/app/uploads/` and serve via an application endpoint that sets `Content-Disposition: attachment`.
- Use a separate domain or object storage (S3, GCS) for serving uploaded files — a different origin means XSS in the uploaded file cannot access the main app's cookies or DOM.
- Scan with antivirus (ClamAV, or a cloud service) for documents (PDF, DOCX) that may contain macro viruses or embedded payloads.

## Section 3: Allowlists vs Blocklists

**Q7. Why are allowlists fundamentally more secure than blocklists, and when is each appropriate?**
A: An allowlist defines the complete set of acceptable inputs — anything not in the list is rejected. A blocklist defines the set of known-bad inputs — anything not in the list is accepted. The security asymmetry:

```
Allowlist (whitelist):
  Attacker must find a value that:
    (a) is in the allowlist AND
    (b) causes harm
  This is a very small intersection — most allowlists contain only safe values

Blocklist (blacklist):
  Attacker must find a value that:
    (a) is NOT in the blocklist AND
    (b) causes harm
  Attackers have unlimited creativity to find values not yet on the list
  The attacker only needs to find ONE bypass; the defender must anticipate ALL attacks
```

Concrete example — attempting to block XSS with a blocklist:

```python
# Blocklist approach — guaranteed to fail eventually
BLOCKED_PATTERNS = ["<script>", "</script>", "javascript:", "onerror=", "onload="]

def validate_comment(comment: str) -> str:
    for pattern in BLOCKED_PATTERNS:
        if pattern.lower() in comment.lower():
            raise ValidationError("Invalid input")
    return comment  # passes — but is it safe?

# Bypasses an attacker will find:
# Case variation:     <ScRiPt>alert(1)</ScRiPt>          — lowercased match fails
# Encoded:           &#60;script&#62;alert(1)&#60;/script&#62;
# New event handler: <img src=x onerror="alert(1)">       — onerror= IS in blocklist
# Variant event:     <img src=x OnError="alert(1)">       — case bypass
# SVG:               <svg><script>alert(1)</script></svg>  — not in the list
# HTML5 events:      <details ontoggle=alert(1) open>      — not in the list
# CSS injection:     <style>body{background:url(javascript:alert(1))}</style>
# The list grows forever and is always incomplete
```

```python
# Allowlist approach — correct
import re

SAFE_COMMENT_PATTERN = re.compile(r'^[\w\s.,!?\'"\-–—()]{1,1000}$', re.UNICODE)

def validate_comment(comment: str) -> str:
    if not SAFE_COMMENT_PATTERN.match(comment):
        raise ValidationError("Comment contains invalid characters")
    return comment
# Only allows: word characters, spaces, basic punctuation
# <, >, &, ;, (, ), ", ' (unmatched) — none are in the allowlist
# No bypass exists: the attacker cannot construct an XSS payload from [a-z0-9.,!?]
```

**When blocklists are legitimately used:**
Blocklists are appropriate when the set of known-bad values is well-defined, stable, and the input space is too large for an allowlist — for example:
- **Disposable email domain blocklists** — a list of known temporary email providers (mailinator.com, guerrillamail.com). The input space (all possible email addresses) is too large to allowlist, but the known-bad set is manageable and regularly updated.
- **IP reputation blocklists** — blocking known Tor exit nodes, VPN providers, or botnet IPs.
- **Password breach databases** — rejecting passwords found in HaveIBeenPwned's dataset (a specific set of known-compromised passwords).
- **Content moderation** — a list of slurs or prohibited terms in user-generated text (where exact enumeration of allowed words is impractical).

In all these cases, the blocklist is augmented by other controls — it is not the sole defense.

**Q8. How do you design allowlists for common field types, and what are the correct constraints for each?**
A:

```python
import re
from decimal import Decimal
from datetime import date, datetime
from uuid import UUID
from pydantic import BaseModel, Field, field_validator

# ─── Identifiers ───────────────────────────────────────────────────────────────

# UUID — the safest identifier type: fixed format, no SQL or HTML chars
def validate_uuid(raw: str) -> UUID:
    try:
        return UUID(raw)   # UUID() raises ValueError for any non-UUID string
    except ValueError:
        raise ValidationError("Invalid ID format")

# Numeric ID — accept integers only
def validate_numeric_id(raw: str) -> int:
    try:
        value = int(raw)
    except (ValueError, TypeError):
        raise ValidationError("ID must be an integer")
    if value <= 0:
        raise ValidationError("ID must be positive")
    if value > 2**31 - 1:
        raise ValidationError("ID exceeds maximum value")
    return value

# Slug — URL-safe identifier (blog post slugs, usernames in paths)
SLUG_RE = re.compile(r'^[a-z0-9][a-z0-9\-]{0,62}[a-z0-9]$')

def validate_slug(raw: str) -> str:
    if not SLUG_RE.match(raw):
        raise ValidationError("Slug must be lowercase alphanumeric with hyphens, 2-64 chars")
    return raw

# ─── Text Fields ────────────────────────────────────────────────────────────────

# Username — narrow charset, length-bounded
USERNAME_RE = re.compile(r'^[a-zA-Z0-9_\-]{3,32}$')

def validate_username(raw: str) -> str:
    raw = raw.strip()
    if not USERNAME_RE.match(raw):
        raise ValidationError("Username must be 3-32 characters: letters, numbers, _ or -")
    return raw

# Email — delegate to a battle-tested library, don't roll your own regex
from email_validator import validate_email, EmailNotValidError

def validate_email_address(raw: str) -> str:
    try:
        info = validate_email(raw, check_deliverability=False)
        return info.normalized   # returns normalized form: lowercased, IDNA-encoded
    except EmailNotValidError as e:
        raise ValidationError(f"Invalid email: {e}")

# Phone number — E.164 format with libphonenumber
import phonenumbers

def validate_phone(raw: str, region: str = "IN") -> str:
    try:
        parsed = phonenumbers.parse(raw, region)
    except phonenumbers.NumberParseException:
        raise ValidationError("Invalid phone number format")
    if not phonenumbers.is_valid_number(parsed):
        raise ValidationError("Phone number is not valid for the given region")
    return phonenumbers.format_number(parsed, phonenumbers.PhoneNumberFormat.E164)
    # Returns: +911234567890 — normalized, canonical form

# Free text — length and character class validation
def validate_free_text(raw: str, max_length: int = 500) -> str:
    if len(raw) > max_length:
        raise ValidationError(f"Text exceeds {max_length} character limit")
    # Reject null bytes — can truncate strings in C-based code
    if '\x00' in raw:
        raise ValidationError("Text contains invalid characters")
    # Reject non-printable control characters (except newline/tab)
    if re.search(r'[\x01-\x08\x0b\x0c\x0e-\x1f\x7f]', raw):
        raise ValidationError("Text contains non-printable characters")
    return raw.strip()

# ─── Numeric Fields ─────────────────────────────────────────────────────────────

# Financial amount — Decimal for precision, range-bounded
def validate_amount(raw: str | float | Decimal, currency: str = "INR") -> Decimal:
    try:
        value = Decimal(str(raw))
    except Exception:
        raise ValidationError("Amount must be a valid number")

    LIMITS = {
        "INR": (Decimal("0.01"), Decimal("1000000")),
        "USD": (Decimal("0.01"), Decimal("10000")),
    }
    min_val, max_val = LIMITS.get(currency, (Decimal("0.01"), Decimal("100000")))

    if value < min_val:
        raise ValidationError(f"Amount must be at least {min_val}")
    if value > max_val:
        raise ValidationError(f"Amount must not exceed {max_val}")
    if value.as_tuple().exponent < -2:
        raise ValidationError("Amount must have at most 2 decimal places")

    return value

# ─── Date and Time ──────────────────────────────────────────────────────────────

# Date range — bounded to prevent unreasonable inputs
def validate_date(raw: str, allow_past: bool = True, allow_future: bool = True) -> date:
    try:
        value = date.fromisoformat(raw)   # strict ISO 8601: YYYY-MM-DD
    except (ValueError, TypeError):
        raise ValidationError("Date must be in YYYY-MM-DD format")

    today = date.today()
    if not allow_past and value < today:
        raise ValidationError("Date cannot be in the past")
    if not allow_future and value > today:
        raise ValidationError("Date cannot be in the future")
    # Sanity bounds — reject obviously wrong dates
    if value.year < 1900 or value.year > 2100:
        raise ValidationError("Date is outside acceptable range")

    return value

# ─── Enumerated Values ──────────────────────────────────────────────────────────

# Enum — allowlist via Python Enum (the gold standard for enumerated inputs)
from enum import Enum

class TransactionStatus(str, Enum):
    PENDING   = "pending"
    COMPLETED = "completed"
    FAILED    = "failed"
    CANCELLED = "cancelled"

def validate_status(raw: str) -> TransactionStatus:
    try:
        return TransactionStatus(raw.lower())
    except ValueError:
        valid = [s.value for s in TransactionStatus]
        raise ValidationError(f"Status must be one of: {', '.join(valid)}")

# ─── URLs ───────────────────────────────────────────────────────────────────────

# URL — allowlist schemes, validate host against known-safe list for SSRF prevention
from urllib.parse import urlparse

ALLOWED_URL_SCHEMES  = {"https"}
ALLOWED_URL_HOSTS    = {"api.stripe.com", "api.razorpay.com", "hooks.slack.com"}

def validate_callback_url(raw: str) -> str:
    try:
        parsed = urlparse(raw)
    except Exception:
        raise ValidationError("Invalid URL format")

    if parsed.scheme not in ALLOWED_URL_SCHEMES:
        raise ValidationError("URL must use HTTPS")
    if not parsed.netloc:
        raise ValidationError("URL must have a valid host")
    if parsed.netloc not in ALLOWED_URL_HOSTS:
        raise ValidationError(f"URL host is not in the allowed list")

    return raw
```

## Section 4: Context-Specific Sanitization

**Q9. How does output context determine the correct encoding, and why is HTML encoding insufficient for all contexts?**
A: The same user-supplied string must be encoded differently depending on where it appears in the output document. Applying HTML encoding everywhere is the most common mistake — it protects the HTML context but leaves JavaScript, URL, and CSS contexts vulnerable.

```python
import html
import json
import urllib.parse
import re

user_input = """<script>alert("XSS")</script> & "quotes" 'apostrophe'"""

# ── Context 1: HTML body (between tags) ─────────────────────────────────────────
# Encode: & < > " '
html_safe = html.escape(user_input, quote=True)
# Output: &lt;script&gt;alert(&quot;XSS&quot;)&lt;/script&gt; &amp; &quot;quotes&quot; &#x27;apostrophe&#x27;
# Used as: <p>{html_safe}</p>  — renders as visible text

# ── Context 2: HTML attribute ────────────────────────────────────────────────────
# Same encoding, but ALWAYS quote the attribute — unquoted attributes are broken by spaces
attr_value = html.escape(user_input, quote=True)
# Used as: <input value="{attr_value}">
# NEVER: <input value={attr_value}>  — attacker can inject new attributes via spaces

# ── Context 3: JavaScript string literal (inside <script> or .js file) ──────────
# HTML encoding does NOT protect JS context — &lt; is still < after JS processes it
# Use JSON encoding: wraps in quotes, escapes \, ", \n, \r, \u2028, \u2029
js_safe = json.dumps(user_input)
# Output: "\"<script>alert(\\\"XSS\\\")...</script>\""
# Used as: <script>var userInput = {js_safe};</script>
# The value is a valid JS string literal — cannot break out

# Additional concern: </script> inside a JS block closes the script tag
# json.dumps escapes forward slashes by default in some libs — verify yours does
# Or escape explicitly:
js_extra_safe = json.dumps(user_input).replace("</", "<\\/")

# ── Context 4: URL query parameter ──────────────────────────────────────────────
# URL-encode the value before embedding in a URL
url_safe = urllib.parse.quote(user_input, safe="")
# Output: %3Cscript%3Ealert%28%22XSS%22%29%3C%2Fscript%3E%20%26%20%22quotes%22%20%27apostrophe%27
# Used as: /search?q={url_safe}

# ── Context 5: CSS value ─────────────────────────────────────────────────────────
# CSS injection enables: expression(), url(javascript:...), behavior:url()
# Allowlist: only allow safe CSS property values (colors, sizes, font names)
CSS_COLOR_RE = re.compile(r'^#[0-9a-fA-F]{3,6}$|^rgb\(\d{1,3},\s*\d{1,3},\s*\d{1,3}\)$')

def validate_css_color(raw: str) -> str:
    if not CSS_COLOR_RE.match(raw):
        raise ValidationError("Invalid color value")
    return raw
# Never interpolate arbitrary user input into CSS — allowlist specific value types

# ── Context 6: Shell command (avoid this — use subprocess with args list) ────────
# If user input must influence a shell command, use subprocess with a list (no shell=True)
import subprocess

# NEVER:
# os.system(f"convert {user_filename} output.jpg")  # command injection

# CORRECT: shell=False (default), args as list — no shell interpolation
subprocess.run(
    ["convert", validated_filename, "output.jpg"],  # validated_filename from allowlist
    shell=False,   # explicit
    check=True,
    capture_output=True,
    timeout=30,
)
```

The rule: **identify the output context first, then apply the encoding for that context**. A template engine with context-aware auto-escaping (Jinja2 with `autoescape=True`, Go's `html/template`) does this automatically for HTML contexts — but not for JavaScript string contexts or CSS contexts within the template. Those still require explicit encoding.

**Q10. How do you handle Unicode, homoglyph attacks, and bidirectional text injection?**
A: Unicode expands the attack surface beyond ASCII in three ways: homoglyphs (characters that look identical to ASCII), bidirectional control characters (that reverse text rendering order), and encoding normalization issues (the same visual character represented by different byte sequences).

**Homoglyph attacks:**

```python
# Homoglyphs — visually identical Unicode characters that bypass ASCII filters
# Cyrillic 'а' (U+0430) vs Latin 'a' (U+0061) — identical in many fonts
# rnicrosoft.com vs microsoft.com — 'rn' looks like 'm', combined with Cyrillic 'с'

# Attack scenario: username validation passes ASCII filter, but the username
# looks identical to an admin username in the UI
username = "аdmin"  # First char is Cyrillic 'а', not Latin 'a'

# Detection: check if the string is purely ASCII
def require_ascii_only(value: str, field: str) -> str:
    try:
        value.encode("ascii")
    except UnicodeEncodeError:
        raise ValidationError(f"{field} must contain only ASCII characters")
    return value

# For fields that legitimately need Unicode (names, bios):
# Normalize to NFC first (canonical composition) — ensures consistent encoding
import unicodedata

def normalize_unicode(value: str) -> str:
    # NFC normalization: é (U+0065 + U+0301) → é (U+00E9)
    # Ensures the same visual character always has the same byte representation
    normalized = unicodedata.normalize("NFC", value)
    return normalized

# For high-security identifiers (usernames, account IDs, slugs):
# Confusables check — detect if the string contains characters from
# multiple scripts (a strong signal of homoglyph attack)
def detect_mixed_scripts(value: str) -> bool:
    scripts = set()
    for char in value:
        cat = unicodedata.category(char)
        name = unicodedata.name(char, "")
        if "LATIN" in name:       scripts.add("LATIN")
        elif "CYRILLIC" in name:  scripts.add("CYRILLIC")
        elif "GREEK" in name:     scripts.add("GREEK")
        # etc.
    return len(scripts) > 1  # mixed scripts → likely homoglyph attack
```

**Bidirectional text injection (BiDi):**

```python
# The Trojan Source attack (CVE-2021-42574)
# Bidirectional control characters (U+202A, U+202B, U+202D, U+202E, U+2066-2069, U+200F)
# can reverse the visual rendering of text in IDEs and code reviewers
# A comment that looks like: // Check if admin
# Actually contains: // Check if admin \u202e \u2066 /* admin */ \u2069 \u2066 //
# The code executed is different from what the reviewer sees

# In user input: BiDi characters can be used to reverse displayed text
# "<img src=x onerror=alert(1)>" with BiDi chars looks like safe text in the UI
# but the browser processes the actual character sequence, not the visual rendering

BIDI_CONTROL_CHARS = {
    '\u200f',  # RIGHT-TO-LEFT MARK
    '\u200e',  # LEFT-TO-RIGHT MARK
    '\u202a',  # LEFT-TO-RIGHT EMBEDDING
    '\u202b',  # RIGHT-TO-LEFT EMBEDDING
    '\u202c',  # POP DIRECTIONAL FORMATTING
    '\u202d',  # LEFT-TO-RIGHT OVERRIDE
    '\u202e',  # RIGHT-TO-LEFT OVERRIDE
    '\u2066',  # LEFT-TO-RIGHT ISOLATE
    '\u2067',  # RIGHT-TO-LEFT ISOLATE
    '\u2068',  # FIRST STRONG ISOLATE
    '\u2069',  # POP DIRECTIONAL ISOLATE
    '\u061c',  # ARABIC LETTER MARK
}

def reject_bidi_characters(value: str, field: str) -> str:
    for char in value:
        if char in BIDI_CONTROL_CHARS:
            raise ValidationError(
                f"{field} contains bidirectional control characters, which are not allowed"
            )
    return value

# Null byte rejection (affects C/C++ based code, some database drivers)
def reject_null_bytes(value: str, field: str) -> str:
    if '\x00' in value:
        raise ValidationError(f"{field} contains null bytes, which are not allowed")
    return value
```

## Section 5: Validation Architecture Patterns

**Q11. How do you implement a centralized validation middleware in a Node.js/Express service?**
A: Centralizing validation prevents the most common failure mode: individual endpoints implementing their own validation inconsistently. A middleware approach ensures every request is validated before reaching route handlers.

```typescript
// validation/middleware.ts — centralized request validation

import { Request, Response, NextFunction } from "express";
import { ZodSchema, ZodError } from "zod";
import { AnyZodObject } from "zod";

type RequestPart = "body" | "query" | "params";

// Generic validation middleware factory
export function validate(
    schema: AnyZodObject,
    part: RequestPart = "body"
) {
    return (req: Request, res: Response, next: NextFunction): void => {
        const result = schema.safeParse(req[part]);

        if (!result.success) {
            res.status(422).json({
                error:   "Validation failed",
                code:    "VALIDATION_ERROR",
                details: formatZodErrors(result.error),
            });
            return;
        }

        // Replace the raw input with the validated, typed, coerced output
        // This ensures downstream handlers always receive validated data
        req[part] = result.data;
        next();
    };
}

// Multi-part validation (body + query + params in one middleware)
export function validateRequest(schemas: {
    body?:   AnyZodObject;
    query?:  AnyZodObject;
    params?: AnyZodObject;
}) {
    return (req: Request, res: Response, next: NextFunction): void => {
        const errors: Record<string, unknown> = {};

        for (const [part, schema] of Object.entries(schemas)) {
            const result = schema.safeParse(req[part as RequestPart]);
            if (!result.success) {
                errors[part] = formatZodErrors(result.error);
            } else {
                req[part as RequestPart] = result.data;
            }
        }

        if (Object.keys(errors).length > 0) {
            res.status(422).json({ error: "Validation failed", details: errors });
            return;
        }

        next();
    };
}

function formatZodErrors(error: ZodError): Record<string, string[]> {
    return error.flatten().fieldErrors as Record<string, string[]>;
}

// ── Usage in routes ──────────────────────────────────────────────────────────

import { z } from "zod";
import { Router } from "express";

const router = Router();

const CreateTransferBody = z.object({
    sourceAccountId:      z.string().uuid(),
    destinationAccountId: z.string().uuid(),
    amount:               z.number().positive().max(100_000),
    currency:             z.string().length(3).regex(/^[A-Z]{3}$/),
    reference:            z.string().max(140).optional(),
});

const GetTransactionsQuery = z.object({
    page:     z.coerce.number().int().positive().default(1),
    pageSize: z.coerce.number().int().min(1).max(100).default(20),
    status:   z.enum(["pending", "completed", "failed"]).optional(),
    from:     z.string().date().optional(),
    to:       z.string().date().optional(),
});

const AccountParams = z.object({
    accountId: z.string().uuid(),
});

router.post(
    "/transfers",
    authenticate,
    validate(CreateTransferBody, "body"),
    async (req, res) => {
        // req.body is now typed as z.infer<typeof CreateTransferBody>
        // All fields are validated and coerced — no raw string handling needed
        const { sourceAccountId, destinationAccountId, amount, currency } = req.body;
        const result = await transferService.create({ sourceAccountId, destinationAccountId, amount, currency }, req.user.id);
        res.status(201).json(result);
    }
);

router.get(
    "/accounts/:accountId/transactions",
    authenticate,
    validateRequest({
        params: AccountParams,
        query:  GetTransactionsQuery,
    }),
    async (req, res) => {
        const { accountId } = req.params;    // validated UUID string
        const { page, pageSize, status, from, to } = req.query;  // validated query params
        const result = await transactionService.list({ accountId, page, pageSize, status, from, to });
        res.json(result);
    }
);
```

**Q12. How do you implement validation at the service layer independently of the HTTP layer?**
A: Service layer validation is necessary because the service is called from multiple entry points — HTTP handlers, message queue consumers, cron jobs, CLI tools, integration tests. Validating only in the HTTP middleware leaves non-HTTP callers unprotected.

```python
# service/transfer_service.py — validates independently of HTTP

from dataclasses import dataclass
from decimal import Decimal
from uuid import UUID
from typing import Optional
from datetime import datetime

@dataclass(frozen=True)
class TransferCommand:
    """Immutable, validated command object — constructed via class method, not directly."""
    source_account_id:      UUID
    destination_account_id: UUID
    amount:                 Decimal
    currency:               str
    initiator_user_id:      UUID
    reference:              Optional[str] = None

    @classmethod
    def create(
        cls,
        source_account_id:      str | UUID,
        destination_account_id: str | UUID,
        amount:                 str | float | Decimal,
        currency:               str,
        initiator_user_id:      str | UUID,
        reference:              Optional[str] = None,
    ) -> "TransferCommand":
        """Factory method: validates inputs and returns a valid command or raises."""

        # Convert and validate IDs
        try:
            src  = UUID(str(source_account_id))
            dest = UUID(str(destination_account_id))
            user = UUID(str(initiator_user_id))
        except ValueError as e:
            raise ServiceValidationError(f"Invalid account ID format: {e}")

        if src == dest:
            raise ServiceValidationError("Source and destination accounts must differ")

        # Validate amount
        try:
            amt = Decimal(str(amount))
        except Exception:
            raise ServiceValidationError("Amount must be a valid number")
        if amt <= 0:
            raise ServiceValidationError("Amount must be positive")
        if amt > Decimal("100000"):
            raise ServiceValidationError("Amount exceeds single-transfer limit")
        if amt.as_tuple().exponent < -2:
            raise ServiceValidationError("Amount must have at most 2 decimal places")

        # Validate currency
        if not re.match(r'^[A-Z]{3}$', currency):
            raise ServiceValidationError("Currency must be a 3-letter ISO 4217 code")

        # Validate reference
        if reference is not None:
            if len(reference) > 140:
                raise ServiceValidationError("Reference exceeds 140 characters")
            if not re.match(r'^[a-zA-Z0-9\s\-_.,]*$', reference):
                raise ServiceValidationError("Reference contains invalid characters")

        return cls(
            source_account_id=src,
            destination_account_id=dest,
            amount=amt,
            currency=currency,
            initiator_user_id=user,
            reference=reference,
        )

class TransferService:

    async def execute(self, command: TransferCommand) -> TransferResult:
        # command is always a fully-validated TransferCommand at this point
        # Business logic validation (as opposed to input validation):
        source = await self.account_repo.get(command.source_account_id)
        if source is None:
            raise NotFoundError("Source account not found")
        if source.owner_id != command.initiator_user_id:
            raise AuthorizationError("Not authorized to transfer from this account")
        if source.balance < command.amount:
            raise BusinessRuleError("Insufficient funds")
        if source.status != "active":
            raise BusinessRuleError("Source account is not active")

        # ... execute transfer
```

The pattern — command objects constructed via factory methods — enforces that a valid `TransferCommand` object cannot be created without passing all validations. The service method accepts only `TransferCommand` objects — any caller that skips validation simply cannot construct the required input type.

## Section 6: Error Handling and Information Disclosure

**Q13. How do you return validation errors safely without leaking internal details?**
A: Validation error responses have two audiences with conflicting needs: the API client needs enough detail to fix the invalid input; an attacker must not receive information about internal schemas, implementation details, or enumerable resources.

```python
# WRONG — leaks internal field names, stack traces, and implementation details
@app.route("/api/users/<user_id>")
def get_user(user_id: str):
    user = db.query(f"SELECT * FROM users WHERE id = {user_id}")  # also SQLi
    if not user:
        # Reveals that the user does not exist — enables user enumeration
        return jsonify({"error": f"User {user_id} not found in users table"}), 404

# WRONG — returns raw exception message (may contain SQL, schema info, file paths)
except Exception as e:
    return jsonify({"error": str(e)}), 500

# CORRECT — field-level errors for client-fixable validation failures
@app.route("/api/transfers", methods=["POST"])
def create_transfer():
    try:
        command = TransferCommand.create(**request.json)
    except ServiceValidationError as e:
        # Safe to return: field-level validation messages reference only input fields
        return jsonify({
            "error": "Validation failed",
            "code":  "VALIDATION_ERROR",
            "details": str(e),       # "Amount must be positive" — reveals nothing internal
        }), 422

    except AuthorizationError:
        # Return 404 for authorization failures on resources — prevents enumeration
        # Returning 403 confirms the resource exists; 404 is ambiguous
        return jsonify({"error": "Not found"}), 404

    except BusinessRuleError as e:
        # Business rule errors are safe to describe (user needs to understand why)
        return jsonify({
            "error": str(e),        # "Insufficient funds" — expected business message
            "code":  "BUSINESS_RULE_VIOLATION",
        }), 409

    except Exception as e:
        # Internal errors: log with full detail, return nothing useful externally
        logger.error(
            "Unexpected error in create_transfer",
            exc_info=True,
            extra={"request_id": g.request_id}
        )
        return jsonify({
            "error":      "An internal error occurred",
            "request_id": g.request_id,   # safe to return: allows log correlation without detail
        }), 500
```

The error taxonomy that guides response design:

```
Client input error (4xx) — safe to describe:
  ValidationError:      Field-level messages are safe — they only reference input fields
  AuthenticationError:  "Authentication required" — do not say WHY the token is invalid
  AuthorizationError:   Return 404 for resource-scoped auth failures (prevents enumeration)
  BusinessRuleError:    Safe to describe — these are expected domain states

Server error (5xx) — never describe:
  DatabaseError:        Log internally; return generic "internal error" + request_id
  ConfigurationError:   Log internally; return generic message
  UnexpectedException:  Log internally; return generic message

Never reveal:
  Stack traces in API responses
  SQL error messages ("column users.secret does not exist")
  File paths ("/var/app/src/services/transfer.py line 47")
  Internal service names in error messages
  Timing differences that reveal resource existence (constant-time responses)
```

**Q14. How do you prevent timing oracle attacks via validation error responses?**
A: A timing oracle exists when the time taken to process a request reveals information about secret data. If "user not found" returns in 5ms and "user found but wrong password" returns in 250ms (due to the bcrypt comparison), an attacker can enumerate valid usernames by measuring response times — no brute-force of the password is needed.

```python
import time, hmac, hashlib, secrets
from contextlib import contextmanager

@contextmanager
def constant_time_response(target_ms: int = 200):
    """Ensure the block takes at least target_ms milliseconds."""
    start = time.monotonic()
    try:
        yield
    finally:
        elapsed_ms = (time.monotonic() - start) * 1000
        remaining  = (target_ms - elapsed_ms) / 1000
        if remaining > 0:
            time.sleep(remaining)

# Login endpoint with constant-time response
@app.route("/api/auth/login", methods=["POST"])
def login():
    email    = request.json.get("email", "")
    password = request.json.get("password", "")

    with constant_time_response(target_ms=200):
        # Always perform the hash computation — even if user doesn't exist
        # This ensures "user not found" and "wrong password" take the same time
        user = db.get_user_by_email(email)

        if user is None:
            # Perform a dummy hash to normalize timing — don't just return early
            bcrypt.checkpw(
                password.encode(),
                b"$2b$12$dummy_hash_for_timing_normalization_xxxxxxxxxxxxxxxx"
            )
            # Fall through to the same failure response
            return jsonify({"error": "Invalid credentials"}), 401

        if not bcrypt.checkpw(password.encode(), user.password_hash):
            return jsonify({"error": "Invalid credentials"}), 401

    # Successful login — issue tokens
    return issue_tokens(user)

# Token comparison — always use constant-time comparison for secrets
def verify_api_key(provided: str, stored_hash: str) -> bool:
    provided_hash = hashlib.sha256(provided.encode()).hexdigest()
    # hmac.compare_digest: constant-time comparison, prevents timing attacks
    return hmac.compare_digest(provided_hash, stored_hash)

# WRONG — short-circuit evaluation leaks timing information
# return provided == stored  # returns early on first mismatch
```

## Section 7: Scenario-Based Questions

**Q15. Scenario: "A developer opens a PR adding a new internal API that accepts a filename from the request body and reads that file from a directory. What issues do you see, and what do you require before approving?"**
A:

```python
# PR under review:
@app.route("/api/internal/reports", methods=["POST"])
def get_report():
    filename = request.json["filename"]
    filepath = f"/var/app/reports/{filename}"
    with open(filepath) as f:
        return f.read()
```

Issues identified:

**1. Path traversal (critical):**
```
filename = "../../etc/passwd"
filepath = "/var/app/reports/../../etc/passwd"
         = "/etc/passwd"
→ reads /etc/passwd — exposes system user list
filename = "../config/database.yml"
→ reads database credentials
```

**2. No authentication / authorization check** — "internal" API reachable from the network.

**3. No filename validation** — accepts any string, no length limit, no character allowlist.

**4. Information disclosure** — stack trace on `FileNotFoundError` reveals the directory path.

Required changes:

```python
import os
from pathlib import Path

REPORTS_BASE = Path("/var/app/reports").resolve()
SAFE_FILENAME = re.compile(r'^[a-zA-Z0-9_\-]{1,64}\.(pdf|csv|xlsx)$')

@app.route("/api/internal/reports", methods=["POST"])
@require_internal_service_token     # authentication — even "internal" needs auth
@require_role("report_viewer")      # authorization — not all internal callers
def get_report():
    filename = request.json.get("filename", "")

    # 1. Filename format validation — allowlist of safe characters and extensions
    if not SAFE_FILENAME.match(filename):
        return jsonify({"error": "Invalid filename format"}), 422

    # 2. Path traversal prevention — resolve the absolute path and verify it
    # starts with the expected base directory
    requested_path = (REPORTS_BASE / filename).resolve()

    if not str(requested_path).startswith(str(REPORTS_BASE)):
        # Path traversal detected — log as security event
        logger.warning(
            "path_traversal_attempt",
            extra={"filename": filename, "resolved": str(requested_path)}
        )
        return jsonify({"error": "Invalid filename"}), 422

    # 3. Existence check with generic error — don't confirm existence via error type
    if not requested_path.is_file():
        return jsonify({"error": "Report not found"}), 404

    # 4. Serve the file safely with explicit Content-Type
    # Never use the filename's extension as the Content-Type — set it explicitly
    mime_types = {".pdf": "application/pdf", ".csv": "text/csv", ".xlsx": "..."}
    suffix = requested_path.suffix
    content_type = mime_types.get(suffix, "application/octet-stream")

    return send_file(
        requested_path,
        mimetype=content_type,
        as_attachment=True,                 # Content-Disposition: attachment — prevents XSS
        download_name=requested_path.name,
    )
```

**Q16. Scenario: "Your API is receiving malformed JSON, strings where integers are expected, and integers exceeding 64-bit range. Production is throwing 500 errors. How do you harden the input layer systematically?"**
A: Unhandled parsing errors are a denial-of-service surface and an information disclosure risk (stack traces). A systematic hardening approach:

```python
# app.py — global input hardening layer

from flask import Flask, request, jsonify, g
import json, uuid, logging

app = Flask(__name__)
logger = logging.getLogger(__name__)

# ── 1. Request size limit — prevent memory exhaustion via large request bodies ──
app.config["MAX_CONTENT_LENGTH"] = 1 * 1024 * 1024  # 1MB maximum body

@app.errorhandler(413)
def request_too_large(e):

# ── 2. Content-Type enforcement — reject non-JSON where JSON is expected ─────────
@app.before_request
def enforce_content_type():
    if request.method in ("POST", "PUT", "PATCH"):
        if not request.is_json:
            return jsonify({
                "error": "Content-Type must be application/json",
                "code":  "INVALID_CONTENT_TYPE"
            }), 415

# ── 3. JSON parse error handling — catch malformed JSON at the framework level ──
@app.errorhandler(400)
def bad_request(e):
    # Flask raises 400 for malformed JSON in request.get_json(force=True)
    logger.warning("malformed_json", extra={"path": request.path, "error": str(e)})
    return jsonify({"error": "Malformed JSON in request body", "code": "INVALID_JSON"}), 400

# ── 4. Global schema validation with integer bounds ──────────────────────────────
# Pydantic handles these automatically — configure it globally:
from pydantic import ConfigDict

class StrictBaseModel(BaseModel):
    model_config = ConfigDict(
        strict=True,          # no type coercion: "123" is NOT a valid int
        extra="forbid",       # unknown fields raise ValidationError — no parameter pollution
    )

# Integer bounds validator — apply to all integer fields
from pydantic import field_validator
from typing import Annotated
from pydantic import Field

SafeInt   = Annotated[int, Field(ge=-(2**31), le=2**31 - 1)]  # 32-bit int
SafeInt64 = Annotated[int, Field(ge=-(2**63), le=2**63 - 1)]  # 64-bit int

class PaginationQuery(StrictBaseModel):
    page:      SafeInt = Field(default=1, ge=1, le=10_000)
    page_size: SafeInt = Field(default=20, ge=1, le=100)

# ── 5. Global exception handler — ensure 500s never expose internals ─────────────
@app.errorhandler(Exception)
def handle_unexpected(e):
    request_id = str(uuid.uuid4())
    logger.error(
        "unhandled_exception",
        exc_info=True,
        extra={"request_id": request_id, "path": request.path, "method": request.method}
    )

        "error":      "An internal error occurred",
        "request_id": request_id,  # correlates to log — safe to return
    }), 500

# ── 6. Deeply nested JSON — bomb prevention ──────────────────────────────────────
def parse_json_safely(raw: str, max_depth: int = 10) -> dict:
    """Parse JSON with a depth limit to prevent deeply nested object attacks."""
    def check_depth(obj, current_depth=0):
        if current_depth > max_depth:
            raise ValueError(f"JSON nesting exceeds maximum depth of {max_depth}")
        if isinstance(obj, dict):
            for v in obj.values():
                check_depth(v, current_depth + 1)
        elif isinstance(obj, list):
            for item in obj:
                check_depth(item, current_depth + 1)

    parsed = json.loads(raw)
    check_depth(parsed)
    return parsed
```

## Quick Reference: Validation & Sanitization Checklist

```
VALIDATION FUNDAMENTALS
[ ] Validate at every layer: gateway, handler, service, persistence
[ ] Service layer validates independently of HTTP layer (message queues, CLI, tests)
[ ] Reject on validation failure — never silently modify and continue
[ ] Convert to typed objects after validation — downstream code never handles raw strings
[ ] Allowlists over blocklists for character sets and enumerated values
[ ] Unknown fields stripped or rejected (Pydantic extra="forbid", Zod .strict())

TYPE AND FORMAT VALIDATION
[ ] Integers: validated as int (not string), bounds-checked (32-bit or 64-bit range)
[ ] Decimals: use Decimal not float for financial values; decimal_places enforced
[ ] UUIDs: parsed via UUID() constructor — rejects all non-UUID strings
[ ] Dates: parsed via date.fromisoformat() or z.string().date() — no custom regex
[ ] Emails: validated with email-validator library, not a custom regex
[ ] Phone numbers: validated with libphonenumber, normalized to E.164
[ ] Enums: validated against Python Enum or Zod .enum() — not string comparison
[ ] URLs: scheme allowlist (https only), host allowlist for SSRF-sensitive contexts

STRING VALIDATION
[ ] Length limits on ALL string fields (max_length enforced)
[ ] Character set: explicit allowlist regex, not blocklist of bad chars
[ ] Null bytes rejected (\x00)
[ ] Non-printable control characters rejected (except \n, \t where appropriate)
[ ] BiDi control characters rejected for security-sensitive fields
[ ] Unicode normalized to NFC before storage and comparison
[ ] ASCII-only enforced for identifiers (usernames, slugs, account IDs)

FILE UPLOADS
[ ] MIME type detected from magic bytes — never trust Content-Type header
[ ] Extension matches detected MIME type
[ ] Size limit enforced before reading content
[ ] Filename sanitized: safe character allowlist, no path traversal chars
[ ] Original filename never used for storage — generate content-addressed name
[ ] Images re-encoded through Pillow to strip metadata and polyglot payloads
[ ] Files stored outside the web root on a separate origin (S3, separate domain)

SANITIZATION (for rich content only)
[ ] HTML sanitization uses allowlist of tags — not blocklist
[ ] Event handler attributes stripped (onclick, onerror, onload, etc.)
[ ] javascript: and data: schemes stripped from href/src
[ ] Sanitization applied server-side on write, not only client-side
[ ] Client-side DOMPurify used as defense-in-depth for dangerouslySetInnerHTML

OUTPUT ENCODING (context-aware)
[ ] HTML body: html.escape() or template autoescape
[ ] HTML attribute: html.escape(quote=True) + always quoted attributes
[ ] JavaScript context: json.dumps() — not html.escape()
[ ] URL parameter: urllib.parse.quote(safe="")
[ ] CSS context: allowlist specific value types — never interpolate free text
[ ] SQL: parameterized queries (not encoding)

ERROR HANDLING
[ ] Validation errors return field-level messages (safe to expose)
[ ] Internal errors return generic message + request_id only
[ ] Database errors never returned to client
[ ] Stack traces never in API responses
[ ] Auth failures return same message and timing regardless of reason
[ ] Resource auth failures return 404 (not 403) to prevent enumeration
[ ] Constant-time response for auth endpoints (no timing oracle)

TESTING
[ ] Boundary values tested: min-1, min, max, max+1 for all numeric fields
[ ] Empty string and whitespace-only tested for all string fields
[ ] XSS payloads tested for all user-input-to-output paths
[ ] Path traversal sequences tested for all file/path inputs ("../", "..%2F")
[ ] SQL injection probes tested even on ORM-backed endpoints
[ ] Oversized inputs tested: strings at max+1 length, integers at max+1 value
[ ] Wrong content-type tested: send JSON to form endpoint, form to JSON endpoint
[ ] Malformed JSON tested: unclosed braces, invalid escapes, deeply nested objects
```

**Tip for the interview:** At 5 YOE, the input validation question almost never stays abstract — it becomes "show me how you'd validate a specific field" or "what's wrong with this code." The most common depth probes are: the difference between validation and sanitization and when each applies (Q1 — the gate vs. the transformer), why allowlists beat blocklists with a concrete bypass example (Q7), and the output context encoding question (Q9 — why HTML encoding is wrong in a JS context). The file upload question (Q6 — magic bytes over Content-Type, re-encoding through Pillow, separate origin for serving) always impresses because most candidates stop at MIME type and size. The path traversal scenario (Q15) and the global hardening scenario (Q16) are common senior-level closes — show systematic thinking: identify all the failure modes first, then address each layer. The timing oracle prevention (Q14) is a bonus that separates security engineers from developers who know security concepts.
