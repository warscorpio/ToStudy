# Security: OWASP API Security Top 10 (2023) — Interview Q&A (5 YOE Level)

---

## Section 1: API1 — Broken Object Level Authorization (BOLA)

**Q1. What is BOLA, why is it the #1 API vulnerability, and what is the canonical vulnerable code pattern?**
A: BOLA (Broken Object Level Authorization) — also called IDOR (Insecure Direct Object Reference) — occurs when an API accepts a caller-supplied resource identifier and returns or modifies that resource without verifying the caller has rights to it. It is #1 because it requires no special tooling to exploit: change one digit in a URL, get someone else's data. Authentication passes. The access control layer simply doesn't exist.

The canonical vulnerable pattern in a fintech context:

```typescript
// VULNERABLE — trusts caller-supplied loanId unconditionally
@Get('loans/:loanId')
@UseGuards(JwtAuthGuard)  // ← AuthN present; AuthZ absent
async getLoan(@Param('loanId') loanId: string) {
  return this.loanRepo.findById(loanId); // Returns ANY loan
}

// Attacker's request:
// GET /loans/99001          ← belongs to victim
// Authorization: Bearer <valid-token-for-attacker>
// Response: 200 OK + victim's full loan record
```

The root cause is treating AuthN as sufficient. Verifying the token proves who the caller is; it says nothing about whether they can access `loanId=99001`.

**Q2. What is the complete BOLA fix, and what are the three layers at which ownership must be enforced?**
A: BOLA is fixed by scoping every data access operation to the authenticated identity. The fix operates at three layers — each is a backstop for the one above:

**Layer 1 — Database query scoping (primary fix):**
```typescript
// SAFE — ownership enforced at the query level
@Get('loans/:loanId')
@UseGuards(JwtAuthGuard)
async getLoan(
  @Param('loanId') loanId: string,
  @Req() req: RequestWithUser,
) {
  return this.loanService.findByIdForUser(loanId, req.user.userId);
}

// Service: ownership in the WHERE clause — not a post-fetch check
async findByIdForUser(loanId: string, userId: string): Promise<Loan> {
  const loan = await this.db.loans.findOne({
    where: { id: loanId, userId },  // Both conditions required
  });

  // Return 404 for both "not found" and "not yours"
  // Never 403 — that reveals the resource exists
  if (!loan) throw new NotFoundException('Loan not found');
  return loan;
}
```

**Layer 2 — Repository method design (structural prevention):**
```typescript
// Repository interface makes ownership non-optional
class LoanRepository {
  // No findById(id) exists — forces callers to supply userId
  async findByIdAndUser(id: string, userId: string): Promise<Loan | null> {
    return this.db.loans.findOne({ where: { id, userId } });
  }

  // Admin path: explicit separate method, separate guard
  async findByIdAdmin(id: string): Promise<Loan | null> {
    return this.db.loans.findOne({ where: { id } });
  }
}
```

**Layer 3 — Database-level Row Level Security (backstop):**
```sql
-- PostgreSQL RLS: even if application code forgets userId,
-- Postgres enforces it at the storage layer
ALTER TABLE loans ENABLE ROW LEVEL SECURITY;

CREATE POLICY loan_owner_isolation ON loans
  USING (user_id = current_setting('app.current_user_id')::uuid);
```

**Q3. How does BOLA manifest differently for nested resources, batch endpoints, and indirect object references?**
A: The single-resource case is obvious; these three patterns are where BOLA slips through code review:

**Nested resources — parent ownership not checked:**
```typescript
// VULNERABLE — checks loan ownership but not payment ownership within it
@Get('loans/:loanId/payments/:paymentId')
async getPayment(
  @Param('loanId') loanId: string,
  @Param('paymentId') paymentId: string,
  @Req() req,
) {
  // Checks loan belongs to user ✓
  await this.loanService.findByIdForUser(loanId, req.user.userId);
  // But fetches payment by ID alone ✗ — any paymentId works
  return this.paymentRepo.findById(paymentId);
}

// SAFE — payment must belong to the verified loan
return this.paymentRepo.findOne({
  where: { id: paymentId, loanId }  // loanId already verified as owned
});
```

**Batch endpoints — ownership checked for some objects, not all:**
```typescript
// VULNERABLE — only checks first item
@Post('loans/bulk-download')
async bulkDownload(@Body() dto: { loanIds: string[] }, @Req() req) {
  const firstLoan = await this.loanRepo.findByIdAndUser(dto.loanIds[0], req.user.userId);
  if (!firstLoan) throw new NotFoundException();
  // Fetches ALL requested IDs without ownership check
  return this.loanRepo.findByIds(dto.loanIds);
}

// SAFE — ownership enforced for every ID in the batch
return this.loanRepo.findAll({
  where: { id: In(dto.loanIds), userId: req.user.userId }
});
```

**Indirect object references — ID hidden in body or filter:**
```typescript
// VULNERABLE — user controls the filter, can access other users' data
@Get('transactions')
async getTransactions(@Query('accountId') accountId: string) {
  return this.txRepo.findAll({ where: { accountId } });
  // Caller supplies accountId — can supply any account
}

// SAFE — derive accountId from the token, not the request
@Get('transactions')
async getTransactions(@Req() req) {
  return this.txRepo.findAll({ where: { userId: req.user.userId } });
}
```

## Section 2: API2 — Broken Authentication

**Q4. What are the five most exploitable Broken Authentication weaknesses in a Node.js API, and what is the fix for each?**
A: Broken Authentication covers any weakness in the credential verification layer — token validation, password handling, rate limiting, and session management.

**Weakness 1 — Incomplete JWT validation:**
```typescript
// VULNERABLE — only verifies signature; skips critical claims
const payload = jwt.verify(token, publicKey);
// Missing: exp, iss, aud, alg checks

// SAFE — explicit, complete validation
const payload = jwt.verify(token, publicKey, {
  algorithms: ['RS256'],          // Prevent alg:none and algorithm confusion
  issuer: process.env.JWT_ISSUER, // Reject tokens from other services
  audience: process.env.JWT_AUD,  // Reject tokens meant for other audiences
  clockTolerance: 30,             // 30s leeway for clock skew across services
});
// exp is checked automatically by verify() — don't skip it by catching that error
```

**Weakness 2 — Weak password hashing:**
```typescript
// VULNERABLE — MD5, SHA1, SHA256, bcrypt with cost < 10, or plaintext
const hash = crypto.createHash('sha256').update(password).digest('hex');

// SAFE — bcrypt cost ≥ 12 in prod, or Argon2id
import * as bcrypt from 'bcrypt';
const COST = parseInt(process.env.BCRYPT_COST ?? '12');
const hash = await bcrypt.hash(password, COST);
const valid = await bcrypt.compare(candidate, hash); // Constant-time comparison
```

**Weakness 3 — No rate limiting on auth endpoints:**
```typescript
// VULNERABLE — unlimited login attempts → credential stuffing / brute force

// SAFE — rate limit by IP and by username independently
import rateLimit from 'express-rate-limit';
import RedisStore from 'rate-limit-redis';

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 10,              // 10 attempts per 15 min per IP
  standardHeaders: true,
  store: new RedisStore({ client: redisClient }),  // Distributed; survives restarts
  keyGenerator: (req) => `${req.ip}:${req.body.email?.toLowerCase()}`,
  // Key on IP + username — prevents distributed attacks against one account
});

app.post('/auth/login', loginLimiter, loginHandler);
app.post('/auth/refresh', rateLimit({ windowMs: 60000, limit: 20 }), refreshHandler);
```

**Weakness 4 — Predictable or short session/token secrets:**
```typescript
// VULNERABLE — hardcoded or short secret
const secret = 'mysecret'; // or process.env.JWT_SECRET = 'changeme'

// SAFE — minimum 256 bits of entropy, from environment, rotatable
// Generate: node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
// Store in AWS Secrets Manager; rotate annually or on suspected compromise
// For JWT: use RS256/ES256 — asymmetric keys; secret never shared
```

**Weakness 5 — Missing token revocation on security events:**
```typescript
// VULNERABLE — password change doesn't invalidate existing tokens
async changePassword(userId: string, newPassword: string) {
  await this.userRepo.update(userId, { passwordHash: await bcrypt.hash(newPassword, 12) });
  // Existing JWTs are still valid — attacker who stole a token keeps access
}

// SAFE — increment tokenVersion, invalidating all previously issued tokens
async changePassword(userId: string, newPassword: string) {
  await this.userRepo.update(userId, {
    passwordHash: await bcrypt.hash(newPassword, 12),
    tokenVersion: () => 'token_version + 1', // DB-level increment
  });
  // JwtStrategy checks payload.tokenVersion === user.tokenVersion
  // All tokens with old version are immediately rejected
}
```

**Q5. What is credential stuffing, how does it differ from brute force, and how do you detect and mitigate it at the API layer?**
A: Brute force tries many passwords against one account. Credential stuffing tries known username/password pairs (from data breaches) across many accounts — typically one attempt per account to stay under per-account rate limits:

```
Brute force:
  user@example.com : password1
  user@example.com : password2
  user@example.com : password3   ← rate limit triggers on same user

Credential stuffing:
  user1@example.com : leaked-password-1   ← 1 attempt, moves on
  user2@example.com : leaked-password-2
  user3@example.com : leaked-password-3   ← per-user rate limit never triggers
```

Detection and mitigation:

```typescript
// Layer 1 — Rate limit by IP across all accounts (catches volume attacks)
const globalLoginLimiter = rateLimit({
  windowMs: 60 * 1000,
  limit: 30,  // 30 total login attempts per IP per minute
  keyGenerator: (req) => req.ip,
});

// Layer 2 — Anomaly detection signals
async login(email: string, password: string, req: Request) {
  const user = await this.userRepo.findByEmail(email);

  // Always hash-compare even if user not found — prevent user enumeration
  // via timing difference between "user not found" and "wrong password"
  const candidateHash = user?.passwordHash ?? '$2b$12$invalidhashpadding000000000000000';
  const valid = await bcrypt.compare(password, candidateHash);

  if (!valid) {
    // Log signals for anomaly detection
    await this.auditLog.record({
      event: 'LOGIN_FAILURE',
      email,
      ip: req.ip,
      userAgent: req.headers['user-agent'],
      timestamp: new Date(),
    });

    // Check: is this IP behind a known residential proxy or Tor exit node?
    // Check: has this IP had > N failures across different accounts in last hour?
    const isSuspicious = await this.threatIntel.evaluate(req.ip);
    if (isSuspicious) {
      await this.alerting.notify('credential_stuffing_suspected', { ip: req.ip });
      // Optionally: require CAPTCHA for next attempt from this IP
    }

    throw new UnauthorizedException('Invalid credentials');
  }
}

// Layer 3 — Have I Been Pwned integration (Cloudflare's k-anonymity model)
async checkPasswordBreached(password: string): Promise<boolean> {
  const hash = crypto.createHash('sha1').update(password).digest('hex').toUpperCase();
  const prefix = hash.slice(0, 5);
  const suffix = hash.slice(5);

  const response = await fetch(`https://api.pwnedpasswords.com/range/${prefix}`);
  const text = await response.text();
  return text.includes(suffix); // True if password appears in known breach data
}
```

## Section 3: API3 — Broken Object Property Level Authorization

**Q6. What is API3 and how does it combine two distinct sub-problems — mass assignment and excessive data exposure?**
A: API3 covers unauthorized access at the **field level** within an object. It has two directions:

**Sub-problem A — Excessive Data Exposure (server sends too much):**
The server returns internal fields that the caller's role should never see. The frontend filters them — but the fields are in the API response, accessible to anyone who inspects traffic:

```typescript
// VULNERABLE — returns the full DB entity
@Get('users/:id')
async getUser(@Param('id') id: string) {
  return this.userRepo.findById(id);
  // Returns: { id, name, email, passwordHash, internalCreditScore,
  //            fraudRiskLabel, aadhaarNumber, kycDocumentPath, ... }
  // Password hash and PII in the API response — unacceptable
}
```

**Sub-problem B — Mass Assignment (server accepts too much):**
The server binds the entire request body to a DB entity, allowing callers to set fields they shouldn't:

```typescript
// VULNERABLE — user can set their own role, creditLimit, kycStatus
@Put('users/:id')
async updateUser(@Param('id') id: string, @Body() body: any) {
  return this.userRepo.update(id, body);
  // Attacker sends: { "name": "Alice", "role": "admin", "creditLimit": 9999999 }
  // All fields applied to the DB record
}
```

**Q7. How do you fix both sub-problems of API3 using DTOs, class-transformer, and explicit field allowlisting?**
A: The fix is the same principle in both directions: **never pass raw objects between the API boundary and the database**. Use DTOs (Data Transfer Objects) as strict contracts:

```typescript
// Fix for Excessive Data Exposure — role-scoped response DTOs
import { Expose, Exclude, plainToInstance } from 'class-transformer';

@Exclude() // Default: exclude all fields
class UserResponseCustomer {
  @Expose() id: string;
  @Expose() name: string;
  @Expose() email: string;
  @Expose() loanStatus: string;
  // passwordHash, internalCreditScore, fraudRiskLabel → NOT exposed
}

@Exclude()
class UserResponseAdmin {
  @Expose() id: string;
  @Expose() name: string;
  @Expose() email: string;
  @Expose() loanStatus: string;
  @Expose() internalCreditScore: number; // Admin only
  @Expose() fraudRiskLabel: string;      // Admin only
  @Expose() kycStatus: string;           // Admin only
}

@Get('users/:id')
@UseGuards(JwtAuthGuard)
async getUser(@Param('id') id: string, @Req() req) {
  const user = await this.userService.findByIdForUser(id, req.user.userId);
  const DtoClass = req.user.roles.includes('admin')
    ? UserResponseAdmin
    : UserResponseCustomer;

  return plainToInstance(DtoClass, user, { excludeExtraneousValues: true });
  // excludeExtraneousValues: true — any field not decorated with @Expose() is stripped
}

// Fix for Mass Assignment — explicit update DTOs with validation
import { IsString, MaxLength, IsOptional } from 'class-validator';
import { PartialType } from '@nestjs/mapped-types';

class UpdateUserDto {
  @IsOptional()
  @IsString()
  @MaxLength(100)
  name?: string;  // Only name is updatable by the user

  @IsOptional()
  @IsString()
  phone?: string; // Only fields explicitly allowed here

  // role, creditLimit, kycStatus, fraudRiskLabel — not present → cannot be set
}

@Put('users/:id')
@UseGuards(JwtAuthGuard)
async updateUser(
  @Param('id') id: string,
  @Body() dto: UpdateUserDto,  // Validated; only allowed fields present
  @Req() req,
) {
  await this.assertOwnership(id, req.user.userId);
  return this.userRepo.update(id, dto); // Only DTO fields hit the DB
}
```

In NestJS, combine `ValidationPipe` globally with `whitelist: true` and `forbidNonWhitelisted: true` to reject any request body property not declared in the DTO — a framework-level mass assignment prevention:

```typescript
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,            // Strip properties not in DTO
  forbidNonWhitelisted: true, // Throw 400 if unknown properties are sent
  transform: true,            // Transform primitives to TS types
}));
```

## Section 4: API4 — Unrestricted Resource Consumption

**Q8. What is API4, and what are the four resource dimensions an attacker can exhaust through an unprotected API?**
A: API4 covers attacks that drain server resources by exploiting APIs with no limits on the cost, size, or frequency of operations. The four dimensions:

**Dimension 1 — Request rate (CPU/thread exhaustion):**
```typescript
// VULNERABLE — no rate limit; DoS via high-frequency requests
@Get('credit-score/:userId')
async getCreditScore(@Param('userId') userId: string) {
  return this.creditBureauService.fetch(userId); // Expensive external call
}

// SAFE — rate limit by user and globally
@Get('credit-score/:userId')
@UseGuards(JwtAuthGuard)
@UseInterceptors(RateLimitInterceptor({ limit: 5, window: '1m', keyFn: req => req.user.userId }))
async getCreditScore(@Param('userId') userId: string) { ... }
```

**Dimension 2 — Payload size (memory/disk exhaustion):**
```typescript
// VULNERABLE — accepts arbitrarily large request bodies
app.use(express.json()); // Default limit: 100KB but often overridden to unlimited

// SAFE — explicit, conservative limits per route type
app.use('/api/documents', express.json({ limit: '10mb' })); // Document upload
app.use('/api',           express.json({ limit: '50kb' })); // Standard API calls
// Multipart uploads: use multer with fileSize and files limits
upload = multer({
  limits: {
    fileSize: 5 * 1024 * 1024, // 5MB max per file
    files: 3,                   // Max 3 files per request
    fields: 10,                 // Max 10 non-file fields
  }
});
```

**Dimension 3 — Query complexity (DB exhaustion):**
```typescript
// VULNERABLE — caller controls page size and nesting depth
@Get('loans')
async getLoans(
  @Query('limit') limit: number,   // Attacker sends limit=1000000
  @Query('include') include: string // Attacker sends include=payments,emis,documents,kyc
) {
  return this.loanRepo.findAll({ limit, relations: include.split(',') });
}

// SAFE — enforce server-side caps regardless of what caller sends
@Get('loans')
async getLoans(@Query() query: PaginatedQueryDto, @Req() req) {
  const limit  = Math.min(query.limit ?? 20, 100); // Hard cap: 100
  const offset = Math.min(query.offset ?? 0, 10000);
  const allowedRelations = ['status', 'summary']; // Allowlist; no deep nesting
  return this.loanRepo.findAll({ userId: req.user.userId, limit, offset,
                                  relations: allowedRelations });
}
```

**Dimension 4 — Operation cost (external service exhaustion / financial cost):**
```typescript
// VULNERABLE — each API call triggers an expensive downstream operation
// Attacker calls /send-otp 1000 times → ₹1000 in SMS costs + carrier blocking

// SAFE — per-user, per-operation rate limiting with exponential backoff enforcement
async sendOtp(userId: string, phone: string) {
  const key = `otp:${userId}`;
  const attempts = await this.redis.incr(key);
  if (attempts === 1) await this.redis.expire(key, 3600); // 1-hour window

  if (attempts > 5) {
    const lockoutKey = `otp:lockout:${userId}`;
    await this.redis.set(lockoutKey, '1', 'EX', 86400); // 24h lockout after 5 attempts
    throw new TooManyRequestsException('OTP limit reached. Try again in 24 hours.');
  }

  await this.smsService.send(phone, generateOtp());
}
```

**Q9. How do you implement a robust, distributed rate limiter in Node.js that handles burst traffic and returns informative headers?**
A: A production rate limiter uses Redis for distributed state (works across multiple app server instances), a sliding window algorithm (fairer than fixed window), and RFC 7807-compliant error responses:

```typescript
// Sliding window rate limiter using Redis sorted sets
class SlidingWindowRateLimiter {
  constructor(
    private readonly redis: Redis,
    private readonly limit: number,
    private readonly windowSecs: number,
  ) {}

  async check(key: string): Promise<{ allowed: boolean; remaining: number; resetAt: number }> {
    const now = Date.now();
    const windowStart = now - this.windowSecs * 1000;
    const fullKey = `ratelimit:${key}`;

    const pipeline = this.redis.pipeline();
    pipeline.zremrangebyscore(fullKey, 0, windowStart);   // Remove expired entries
    pipeline.zadd(fullKey, now, `${now}-${Math.random()}`); // Add current request
    pipeline.zcard(fullKey);                              // Count in window
    pipeline.expire(fullKey, this.windowSecs);            // TTL housekeeping
    const results = await pipeline.exec();

    const count = results[2][1] as number;
    const allowed = count <= this.limit;
    const resetAt = Math.ceil((now + this.windowSecs * 1000) / 1000);

    return { allowed, remaining: Math.max(0, this.limit - count), resetAt };
  }
}

// NestJS interceptor with RFC 6585 headers
@Injectable()
export class RateLimitInterceptor implements NestInterceptor {
  constructor(private readonly limiter: SlidingWindowRateLimiter) {}

  async intercept(context: ExecutionContext, next: CallHandler) {
    const req = context.switchToHttp().getRequest();
    const res = context.switchToHttp().getResponse();
    const key = `${req.user?.userId ?? req.ip}:${req.path}`;

    const { allowed, remaining, resetAt } = await this.limiter.check(key);

    // Always set headers — even on allowed requests (lets clients self-throttle)
    res.setHeader('X-RateLimit-Limit', this.limiter.limit);
    res.setHeader('X-RateLimit-Remaining', remaining);
    res.setHeader('X-RateLimit-Reset', resetAt);

    if (!allowed) {
      res.setHeader('Retry-After', resetAt - Math.floor(Date.now() / 1000));
      throw new HttpException({
        status: 429,
        error: 'Too Many Requests',
        message: `Rate limit exceeded. Retry after ${new Date(resetAt * 1000).toISOString()}`,
      }, 429);
    }

    return next.handle();
  }
}
```

## Section 5: API5 — Broken Function Level Authorization

**Q10. What distinguishes API5 (Broken Function Level Authorization) from API1 (BOLA), and what patterns does it exploit?**
A: API1 is about accessing the wrong **data object** (user A reading user B's loan). API5 is about accessing the wrong **action or endpoint** (a customer triggering an admin operation). The distinction:

```
API1 — BOLA:   Right endpoint, wrong object
  GET /loans/99001 → customer reads another customer's loan

API5 — BFLA:   Wrong endpoint entirely for this role
  POST /admin/write-off-loan → customer triggers an admin function
  DELETE /users/42           → regular user deletes another user's account
  GET  /internal/audit-log   → customer reads internal audit data
```

Exploitation patterns specific to API5:

```typescript
// Pattern 1 — HTTP method confusion
// DELETE /loans/:id is admin-only, but GET /loans/:id has no method restriction guard
// Attacker changes method: DELETE /loans/99001

// Pattern 2 — Undocumented / legacy admin routes
// POST /api/v1/admin/approve → missing from public docs but still live
// POST /api/v2/admin/approve → secured; v1 was forgotten

// Pattern 3 — Role check on controller but not on related service method
@Post('admin/disburse')
@Roles('admin')              // Guard on the HTTP endpoint
async disburse(@Body() dto) {
  return this.loanService.disburse(dto); // Service method directly callable
}                                        // from other services without guard

// Pattern 4 — Predictable admin route naming
// Public: /api/loans → attacker guesses: /api/admin/loans, /api/internal/loans
```

**Q11. How do you implement function-level authorization that is impossible to accidentally bypass in a NestJS application?**
A: The failure mode of API5 is that authorization is applied inconsistently — some routes have guards, some are forgotten. The fix is a **secure-by-default** architecture where every route requires authorization unless explicitly opted out:

```typescript
// Step 1 — Apply JwtAuthGuard globally; all routes require auth unless decorated
// main.ts / app.module.ts
const app = await NestFactory.create(AppModule);
app.useGlobalGuards(
  app.get(JwtAuthGuard),   // AuthN: every route requires a valid token
  app.get(RolesGuard),     // AuthZ: every route checks required roles
);

// Step 2 — Public routes must explicitly opt out (not the other way around)
export const Public = () => SetMetadata('isPublic', true);

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private reflector: Reflector) { super(); }

  canActivate(context: ExecutionContext) {
    const isPublic = this.reflector.getAllAndOverride<boolean>('isPublic', [
      context.getHandler(), context.getClass(),
    ]);
    if (isPublic) return true; // Explicit opt-out for public routes
    return super.canActivate(context);
  }
}

// Step 3 — Admin controller: role guard at controller level, not just route level
@Controller('admin')
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('admin')               // Applies to ALL routes in this controller
export class AdminController {

  @Post('write-off-loan')
  @Roles('admin', 'credit-manager') // Route-level overrides controller-level
  writeOffLoan(@Body() dto: WriteOffDto) { ... }

  @Get('audit-log')
  @Roles('admin', 'auditor')
  getAuditLog() { ... }

  // A developer adding a new route here CANNOT forget role checks
  // — they inherit the controller-level @Roles('admin') guard
}

// Step 4 — Test that unauthorized roles receive 403 (not 200 or 404)
describe('AdminController BFLA tests', () => {
  const roles = ['customer', 'agent', 'viewer'];
  roles.forEach(role => {
    it(`should return 403 for role=${role} on POST /admin/write-off-loan`, async () => {
      const token = generateTestToken({ role });
      const res = await request(app.getHttpServer())
        .post('/admin/write-off-loan')
        .set('Authorization', `Bearer ${token}`)
        .send({ loanId: 'test-id' });
      expect(res.status).toBe(403);
    });
  });
});
```

## Section 6: API6 — Unrestricted Access to Sensitive Business Flows

**Q12. What is API6, and how does it differ from API4 (Unrestricted Resource Consumption)?**
A: API4 is about resource exhaustion — CPU, memory, bandwidth, external API costs. API6 is about **business logic abuse** — automating flows that were designed for human interaction to gain economic or competitive advantage. The server resources may not be strained at all; the harm is to the business:

```
API4 (Resource Consumption):
  Attacker sends 100,000 requests/sec → server runs out of connections / money
  Intent: degrade availability or inflate costs

API6 (Sensitive Business Flows):
  Attacker sends 500 requests/min to /apply-loan, each with slightly different details
  → Probes credit bureau responses to reverse-engineer credit scoring model
  → Server resources fine; business logic is being harvested
  OR:
  Attacker automates /buy-ticket endpoint → buys all concert tickets in seconds
  → Resells at markup; legitimate users locked out
  → Each request is valid; rate limits not triggered; business harmed
```

Sensitive business flows in fintech: loan application submission (each triggers a credit bureau inquiry), OTP generation, payment initiation, KYC document submission, referral code redemption, cashback claim, account opening.

**Q13. What are the technical controls for protecting sensitive business flows beyond standard rate limiting?**
A: Standard rate limiting (requests per minute) is insufficient — attackers scale horizontally across IPs. The controls for API6 work at the business-logic layer:

```typescript
// Control 1 — Device fingerprinting + behavioral consistency
@Post('apply-loan')
async applyLoan(@Body() dto: LoanApplicationDto, @Req() req) {
  const fingerprint = {
    ip:           req.ip,
    userAgent:    req.headers['user-agent'],
    acceptLang:   req.headers['accept-language'],
    deviceId:     req.headers['x-device-id'],    // Set by mobile SDK
    sessionAge:   Date.now() - req.session.createdAt,
  };

  // Flag: application submitted within 10 seconds of session creation
  // (human users spend time filling the form)
  if (fingerprint.sessionAge < 10000) {
    await this.fraudSignals.record(req.user.userId, 'INSTANT_APPLICATION');
  }

  // Flag: same user, different device fingerprint within 1 hour
  const recentFingerprint = await this.redis.get(`fingerprint:${req.user.userId}`);
  if (recentFingerprint && recentFingerprint !== JSON.stringify(fingerprint)) {
    await this.fraudSignals.record(req.user.userId, 'DEVICE_SWITCH');
  }

  await this.redis.set(`fingerprint:${req.user.userId}`, JSON.stringify(fingerprint), 'EX', 3600);
}

// Control 2 — CAPTCHA / proof-of-work for high-value flows
@Post('apply-loan')
async applyLoan(@Body() dto: LoanApplicationDto & { captchaToken: string }, @Req() req) {
  const captchaValid = await this.recaptchaService.verify(
    dto.captchaToken,
    req.ip,
    0.7, // Score threshold — 0.0 (bot) to 1.0 (human)
  );
  if (!captchaValid) throw new ForbiddenException('Bot activity detected');
}

// Control 3 — Business-level velocity checks (not just request rate)
async applyLoan(userId: string, dto: LoanApplicationDto) {
  // Max 3 loan applications per user per 30 days — business rule, not rate limit
  const recentApps = await this.loanRepo.count({
    where: {
      userId,
      createdAt: MoreThan(subDays(new Date(), 30)),
    },
  });
  if (recentApps >= 3) {
    throw new UnprocessableEntityException(
      'Maximum loan applications reached for this period'
    );
  }
}

// Control 4 — Introduce intentional friction for bot-discouraging flows
// Asynchronous processing: return 202 Accepted, process in background
// Bots expecting synchronous credit score responses get delayed/hidden responses
@Post('apply-loan')
async applyLoan(@Body() dto: LoanApplicationDto, @Req() req) {
  const applicationId = await this.loanApplicationQueue.add(dto);
  return { applicationId, status: 'PROCESSING' }; // 202 — no immediate signal
}
```

## Section 7: API7 — Server Side Request Forgery (SSRF)

**Q14. What is SSRF in an API context, and why is it particularly dangerous in a cloud-hosted fintech environment?**
A: SSRF (Server Side Request Forgery) occurs when an API accepts a URL from the caller and makes a server-side HTTP request to it. The attacker supplies a URL pointing to internal infrastructure — the server's outbound request originates from inside the network perimeter, bypassing external firewalls:

```
Normal intent:
  POST /fetch-kyc-document { "documentUrl": "https://digilocker.gov.in/docs/abc123" }
  Server fetches the external document → returns it to the caller

SSRF attack:
  POST /fetch-kyc-document { "documentUrl": "http://169.254.169.254/latest/meta-data/iam/security-credentials/" }
  Server makes a request to the EC2 instance metadata endpoint (internal)
  → Returns AWS IAM credentials for the instance's role
  → Attacker now has AWS access keys with whatever permissions the EC2 role has

Other SSRF targets in AWS:
  http://169.254.169.254/latest/meta-data/          ← EC2 instance metadata
  http://169.254.170.2/v2/credentials              ← ECS task credentials
  http://localhost:8080/actuator/env               ← Spring Boot actuator (internal)
  http://10.0.0.5:5432/                            ← Internal RDS directly
  http://redis.internal:6379/                      ← Internal Redis
```

In fintech specifically: an instance role with access to S3 (loan documents), Secrets Manager (DB passwords), or DynamoDB (customer data) turns an SSRF into a full data breach via the metadata endpoint.

**Q15. What is the defense-in-depth strategy against SSRF in a Node.js service?**
A: Defense requires multiple layers because any single control can be bypassed via URL obfuscation (`http://①⑦②.⓪.⓪.①` for `172.0.0.1`):

```typescript
// Layer 1 — Allowlist of permitted domains (primary control)
const ALLOWED_DOMAINS = new Set([
  'digilocker.gov.in',
  'api.aadhaar.uidai.gov.in',
  'kyc-partner.myorg.internal',
]);

async fetchExternalDocument(url: string): Promise<Buffer> {
  // Parse and validate BEFORE making any network call
  let parsedUrl: URL;
  try {
    parsedUrl = new URL(url);
  } catch {
    throw new BadRequestException('Invalid URL format');
  }

  // Scheme allowlist — reject file://, ftp://, gopher://
  if (!['https:', 'http:'].includes(parsedUrl.protocol)) {
    throw new BadRequestException('Only HTTP/HTTPS URLs are permitted');
  }

  // Domain allowlist
  if (!ALLOWED_DOMAINS.has(parsedUrl.hostname)) {
    throw new ForbiddenException(`Domain ${parsedUrl.hostname} is not permitted`);
  }

  // Layer 2 — DNS resolution check before request (prevent DNS rebinding)
  const resolved = await dns.promises.resolve4(parsedUrl.hostname);
  for (const ip of resolved) {
    if (isPrivateIp(ip)) {
      throw new ForbiddenException('Resolved to a private IP address');
    }
  }

  return this.httpService.get(url, { timeout: 5000 }).toPromise();
}

// isPrivateIp: checks RFC 1918 + loopback + link-local + metadata addresses
function isPrivateIp(ip: string): boolean {
  const privateRanges = [
    /^127\./,           // Loopback
    /^10\./,            // RFC 1918
    /^172\.(1[6-9]|2\d|3[01])\./,  // RFC 1918
    /^192\.168\./,      // RFC 1918
    /^169\.254\./,      // Link-local (AWS metadata lives here)
    /^::1$/,            // IPv6 loopback
    /^fc00:/,           // IPv6 ULA
  ];
  return privateRanges.some(range => range.test(ip));
}

// Layer 3 — Network-level control: restrict egress from app servers
// via AWS Security Groups / NACLs — app server cannot reach 169.254.x.x
// This is a backstop that works even if application code is bypassed

// Layer 4 — IMDSv2 enforcement (AWS-specific)
// Even if SSRF reaches the metadata endpoint,
// IMDSv2 requires a PUT request with a session token first
// Simple GET to 169.254.169.254 → 401 (not the credentials)
// Configure in Terraform:
resource "aws_instance" "app" {
  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required"    # IMDSv2 only
    http_put_response_hop_limit = 1             # Prevents SSRF from containers
  }
}
```

## Section 8: API8 — Security Misconfiguration

**Q16. What are the highest-impact security misconfigurations in a Node.js/Express API, and how do you systematically prevent them?**
A: Security misconfiguration is the broadest category — any insecure default left unchanged, any unnecessary feature left enabled, any sensitive information leaked in errors or headers. The highest-impact ones:

**Misconfiguration 1 — Verbose error responses in production:**
```typescript
// VULNERABLE — stack traces and internal paths exposed to caller
app.use((err, req, res, next) => {
  res.status(500).json({
    message: err.message,  // "connect ECONNREFUSED 10.0.0.5:5432" → reveals DB IP
    stack: err.stack,      // Full stack trace with file paths
    query: err.query,      // The SQL query that failed
  });
});

// SAFE — opaque errors externally; full detail in structured internal logs
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  const errorId = crypto.randomUUID();

  logger.error({
    errorId,
    message: err.message,
    stack: err.stack,
    path: req.path,
    userId: req.user?.userId,
  });

  const statusCode = err instanceof HttpException ? err.getStatus() : 500;
  const publicMessage = statusCode < 500
    ? err.message  // 4xx: safe to return (validation errors, not found, etc.)
    : 'An internal error occurred'; // 5xx: opaque; use errorId for support

  res.status(statusCode).json({ error: publicMessage, errorId });
});
```

**Misconfiguration 2 — Leaking server information in response headers:**
```typescript
// VULNERABLE — default Express behavior
// X-Powered-By: Express → reveals framework + version → narrows known CVEs for attacker

// SAFE — helmet.js removes fingerprinting headers and sets security headers
import helmet from 'helmet';
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc:  ["'self'"],
      objectSrc:  ["'none'"],
      upgradeInsecureRequests: [],
    },
  },
  hsts: {
    maxAge: 31536000,         // 1 year
    includeSubDomains: true,
    preload: true,
  },
  frameguard:    { action: 'deny' },   // X-Frame-Options: DENY
  noSniff:       true,                 // X-Content-Type-Options: nosniff
  referrerPolicy: { policy: 'strict-origin-when-cross-origin' },
}));
app.disable('x-powered-by'); // Belt-and-suspenders; helmet already does this
```

**Misconfiguration 3 — Overly permissive CORS:**
```typescript
// VULNERABLE — allows any origin with credentials
app.use(cors({ origin: '*', credentials: true }));
// Note: origin:'*' + credentials:true is actually rejected by browsers,
// but many teams set origin to a regex that matches too broadly

// SAFE — explicit allowlist; credentials only for trusted first-party origins
const allowedOrigins = new Set([
  'https://app.myorg.com',
  'https://agent.myorg.com',
  process.env.NODE_ENV === 'development' ? 'http://localhost:3000' : null,
].filter(Boolean));

app.use(cors({
  origin: (origin, callback) => {
    if (!origin || allowedOrigins.has(origin)) {
      callback(null, true);
    } else {
      callback(new Error(`CORS: origin ${origin} not allowed`));
    }
  },
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization', 'X-Request-ID'],
}));
```

**Misconfiguration 4 — Debug/admin endpoints live in production:**
```typescript
// VULNERABLE — /metrics, /health/detail, /actuator left open
app.get('/debug/config', (req, res) => res.json(process.env)); // Entire env exposed

// SAFE — internal endpoints gated by network or secret header
app.get('/metrics', (req, res, next) => {
  const internalToken = req.headers['x-internal-token'];
  if (internalToken !== process.env.INTERNAL_METRICS_TOKEN) {
    return res.status(404).end(); // 404, not 403 — don't reveal the endpoint exists
  }
  next();
}, metricsHandler);
// Or: serve /metrics on a separate internal port (not exposed to the load balancer)
```

## Section 9: API9 — Improper Inventory Management

**Q17. What is API9, and how do shadow APIs and zombie endpoints create exploitable attack surface?**
A: API9 covers attack surface that exists but isn't known, monitored, or maintained. Two categories:

**Shadow APIs** — endpoints that were never documented or intended for production:
```
- Debug routes added during development: GET /debug/db-status
- Admin endpoints added for a one-off fix, never removed: POST /fix-loan-status
- Staging endpoints accidentally deployed to production
- Third-party libraries that register their own routes (Swagger UI, health checks)
  without the team realizing they're publicly accessible
```

**Zombie endpoints** — documented endpoints that are outdated or deprecated but still live:
```
- /api/v1/loans  → deprecated; team uses /api/v2/loans
                   but v1 is still running with old, unpatched validation logic
- /api/v1/login  → old JWT implementation without alg:none protection
                   v2 uses RS256; v1 still accepts HS256 and the old shared secret
- Mobile SDK hardcoded /api/v1/kyc  → team can't remove v1 without breaking old app versions
                                       v1 runs for 2 years without security patches
```

The security consequence: v1 and shadow endpoints are typically the least-maintained code in the codebase — they don't get dependency updates, they don't get security fixes, and they're not covered by the current security review process. An attacker who finds them encounters an older, weaker surface.

**Q18. What does an API inventory management strategy look like in practice for a microservices fintech platform?**
A: Inventory management requires tooling at three levels — discovery, documentation, and governance:

```typescript
// Level 1 — Automated route discovery at startup
// Log all registered routes on application start for audit
function logRegisteredRoutes(app: INestApplication) {
  const server = app.getHttpServer();
  const router = server._events.request._router;

  const routes = router.stack
    .filter(layer => layer.route)
    .map(layer => ({
      method: Object.keys(layer.route.methods)[0].toUpperCase(),
      path: layer.route.path,
    }));

  logger.info({ event: 'ROUTES_REGISTERED', routes, count: routes.length });
  // Ship to your APM / inventory dashboard
}

// Level 2 — OpenAPI spec as the single source of truth
// Every endpoint MUST have an @ApiOperation decorator (enforced by lint rule)
@Get('loans/:loanId')
@ApiOperation({
  summary: 'Get loan by ID',
  description: 'Returns loan details for the authenticated user',
  tags: ['loans'],
  deprecated: false,  // Set to true before removal; remove after deprecation period
})
@ApiResponse({ status: 200, type: LoanResponseDto })
@ApiResponse({ status: 404, description: 'Loan not found' })
async getLoan(@Param('loanId') loanId: string) { ... }

// CI check: fail build if any controller method lacks @ApiOperation
// Prevents undocumented routes from reaching production silently

// Level 3 — Versioning strategy with enforced sunset dates
@Controller({ path: 'loans', version: '1' })
export class LoansControllerV1 {
  // Deprecation header on every v1 response
  @Get(':id')
  async getLoan(@Res() res: Response) {
    res.setHeader('Deprecation', 'true');
    res.setHeader('Sunset', 'Sat, 31 Dec 2025 23:59:59 GMT');
    res.setHeader('Link', '</api/v2/loans/:id>; rel="successor-version"');
    // ...
  }
}

// Level 4 — Unused endpoint detection via traffic monitoring
// Alert if a documented endpoint has zero traffic for 30 days
// → Candidate for removal or investigation (is it a zombie?)
// Prometheus metric:
http_requests_total{path="/api/v1/legacy-kyc", method="POST"} 0  ← 30-day alert
```

## Section 10: API10 — Unsafe Consumption of APIs

**Q19. What is API10, and why do developers underestimate the risk of trusting third-party API responses?**
A: API10 covers vulnerabilities introduced when your service consumes external APIs (payment gateways, credit bureaus, KYC providers, Account Aggregators) and trusts their responses without validation. The assumption is: "it's coming from a trusted partner, so it must be safe." This is wrong for three reasons:

**Reason 1 — Third-party APIs can be compromised:**
```typescript
// VULNERABLE — trusts Razorpay webhook payload without signature verification
app.post('/webhooks/razorpay', (req, res) => {
  const { orderId, status, amount } = req.body;
  // Attacker sends a fake webhook: { orderId: 'real-order', status: 'paid', amount: 1 }
  await this.orderService.markAsPaid(orderId); // Order marked paid for ₹1
});

// SAFE — verify HMAC signature from Razorpay before processing
app.post('/webhooks/razorpay', (req, res) => {
  const signature = req.headers['x-razorpay-signature'];
  const body = JSON.stringify(req.body);
  const expectedSig = crypto
    .createHmac('sha256', process.env.RAZORPAY_WEBHOOK_SECRET)
    .update(body)
    .digest('hex');

  if (!crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expectedSig))) {
    return res.status(400).json({ message: 'Invalid signature' });
  }

  // Now safe to process
  await this.orderService.processWebhook(req.body);
});
```

**Reason 2 — Third-party responses can contain injection payloads:**
```typescript
// VULNERABLE — passes third-party name directly into DB query
const kycData = await this.kycProvider.verify(aadhaarNumber);
// kycData.name = "Robert'); DROP TABLE users;--" (if KYC provider is compromised)
await this.db.query(`UPDATE users SET name = '${kycData.name}'`); // SQL injection

// SAFE — treat all external data as untrusted; use parameterized queries + DTO validation
const kycData = await this.kycProvider.verify(aadhaarNumber);

// Validate and sanitize external response
const validatedName = kycData.name?.substring(0, 100).replace(/[^\w\s\-\.]/g, '');
await this.userRepo.update(userId, { name: validatedName }); // ORM parameterizes
```

**Reason 3 — Third-party responses can contain XSS payloads:**
```typescript
// VULNERABLE — reflects third-party content to a browser
const branchName = await this.bankApi.getBranchName(ifscCode);
res.json({ branch: branchName }); // branchName = "<script>steal(document.cookie)</script>"
// If client renders this in innerHTML → stored XSS via third-party data

// SAFE — sanitize before returning to clients
import DOMPurify from 'isomorphic-dompurify';
res.json({ branch: DOMPurify.sanitize(branchName) });
// Or: ensure the client uses textContent, not innerHTML (defense in depth)
```

**Q20. What is the complete defense checklist when integrating a third-party payment or KYC API in a fintech application?**
A: Third-party integrations require defense at five stages — before the call, during the call, on the response, on persistence, and operationally:

```typescript
// STAGE 1 — Before the call: validate outbound data
async initiatePayment(userId: string, dto: PaymentDto) {
  // Never send raw user input to a third-party API
  // Validate + sanitize locally first
  const validated = await this.validate(dto, PaymentRequestDto);

  // Enforce payload size — prevent exfiltration via oversized requests
  const payload = JSON.stringify(validated);
  if (payload.length > 4096) throw new BadRequestException('Payload too large');
}

// STAGE 2 — During the call: safe HTTP client configuration
const response = await this.httpService.post(url, body, {
  timeout: 5000,       // Don't wait indefinitely — prevents Slowloris against your service
  maxRedirects: 0,     // Never follow redirects from third parties (SSRF vector)
  validateStatus: null,// Handle all status codes explicitly; don't throw on 4xx/5xx
  httpsAgent: new https.Agent({
    rejectUnauthorized: true,  // Verify TLS certificate (default true, but be explicit)
    minVersion: 'TLSv1.2',     // Reject TLS < 1.2
  }),
}).toPromise();

// STAGE 3 — On response: validate structure, types, and ranges
const schema = z.object({
  transactionId: z.string().uuid(),
  status: z.enum(['SUCCESS', 'FAILED', 'PENDING']),
  amount: z.number().positive().max(10_000_000), // Sanity cap on amount
  currency: z.literal('INR'),
  timestamp: z.string().datetime(),
});

const parsed = schema.safeParse(response.data);
if (!parsed.success) {
  logger.error({ event: 'THIRD_PARTY_INVALID_RESPONSE', errors: parsed.error });
  throw new ServiceUnavailableException('Payment provider returned unexpected data');
}

// STAGE 4 — On persistence: never store raw third-party responses
// Extract only the fields you need; discard the rest
await this.paymentRepo.create({
  transactionId: parsed.data.transactionId, // Specific field
  status:        parsed.data.status,
  amount:        parsed.data.amount,
  // NOT: raw: JSON.stringify(response.data) ← unvalidated blob in DB
});

// STAGE 5 — Operational: idempotency and webhook deduplication
async handleWebhook(webhookDto: WebhookDto) {
  // Third-party systems may send the same webhook multiple times (retries)
  const alreadyProcessed = await this.redis.set(
    `webhook:${webhookDto.eventId}`,
    '1',
    'NX',  // Only set if not exists
    'EX',
    86400, // 24h dedup window
  );
  if (!alreadyProcessed) return { status: 'already_processed' };

  await this.processWebhookEvent(webhookDto);
}
```

## Quick Reference Table

| # | Vulnerability | Core Problem | Key Fix | HTTP Code |
|---|---|---|---|---|
| **API1** | Broken Object Level Auth | Missing ownership check on resource access | `WHERE id = ? AND userId = ?` in every query | 404 (not 403) |
| **API2** | Broken Authentication | Weak token validation, no rate limiting | Full JWT claim validation, bcrypt ≥12, login rate limit | 401 |
| **API3** | Broken Object Property Level Auth | Mass assignment + excessive data exposure | Response DTOs with `@Expose()`, `whitelist: true` on ValidationPipe | 200 (wrong fields) |
| **API4** | Unrestricted Resource Consumption | No limits on request rate, size, or cost | Sliding window rate limiter, payload size caps, pagination caps | 429 |
| **API5** | Broken Function Level Auth | Missing role checks on admin/sensitive routes | Global guards, secure-by-default, controller-level `@Roles()` | 403 |
| **API6** | Unrestricted Sensitive Business Flows | Bot automation of business logic | CAPTCHA, device fingerprinting, business-velocity limits | 429 / 422 |
| **API7** | Server Side Request Forgery | Server fetches attacker-controlled URLs | Domain allowlist, private IP blocklist, IMDSv2 enforcement | 400 / 403 |
| **API8** | Security Misconfiguration | Insecure defaults, verbose errors, bad CORS | Helmet.js, opaque error responses, explicit CORS allowlist | 500 (leaks info) |
| **API9** | Improper Inventory Management | Shadow/zombie endpoints with stale security | Route logging, OpenAPI enforcement, sunset headers | Varies |
| **API10** | Unsafe Consumption of APIs | Trusting third-party responses blindly | Webhook signature verification, Zod schema validation, idempotency | Varies |

**Tip for the interview:** At 5 YOE, examiners don't run through the list asking "what is API1?" — they describe an incident or a code snippet and ask what's wrong. Know **API1** deeply: the `WHERE id = ? AND userId = ?` pattern, the 404-not-403 rule, and the three layers of enforcement (query, repository design, RLS). **API3** trips up senior engineers specifically — mass assignment via `whitelist: true` on `ValidationPipe` and the `@Expose()` DTO pattern are the expected answers. **API7 (SSRF)** is a guaranteed question in fintech because of the AWS metadata endpoint — know IMDSv2 and the private IP blocklist cold. For **API10**, webhook signature verification (Razorpay/JusPay HMAC pattern) is directly relevant to your payment gateway experience — lead with it. The examiner will respect an answer that connects the OWASP category to a real production concern you've encountered rather than a textbook definition.
