# Security: CSRF — SameSite Cookies & CSRF Tokens — Interview Q&A (5 YOE Level)

---

## Section 1: Understanding CSRF

**Q1. What is CSRF, what is the browser behavior it exploits, and why does it only affect certain authentication mechanisms?**
A: CSRF (Cross-Site Request Forgery) is an attack where a malicious site tricks a victim's browser into making a state-changing request to a target site — carrying the victim's credentials — without the victim's knowledge or intent. The browser behavior it exploits is **automatic credential attachment**: cookies scoped to `mybank.com` are sent on every request to `mybank.com`, regardless of which site initiated the request.

```
Victim is logged into mybank.com (session cookie in browser)
Victim visits evil.com (attacker-controlled page)

evil.com contains:
  <form action="https://mybank.com/api/transfer" method="POST" id="f">
    <input type="hidden" name="to"     value="attacker-account-number" />
    <input type="hidden" name="amount" value="500000" />
  </form>
  <script>document.getElementById('f').submit();</script>

Browser executes:
  POST https://mybank.com/api/transfer
  Cookie: sessionId=victim-session-abc   ← attached automatically by browser
  Body: to=attacker-account&amount=500000

mybank.com receives a request that looks legitimate:
  ✓ Valid session cookie → user is authenticated
  ✗ No check that the user actually intended this action
  → Transfer executes
```

Why it only affects certain authentication mechanisms:

```
Vulnerable to CSRF:
  ✓ Session cookies (sent automatically by browser)
  ✓ JWT in HttpOnly cookies (sent automatically — same behavior)
  ✓ Basic Auth credentials cached by browser

NOT vulnerable to CSRF:
  ✗ Bearer tokens in Authorization header
    (browser never automatically sets this header — only JavaScript can)
  ✗ API keys in custom headers (X-API-Key)
    (same — custom headers require JS to set them)
  ✗ JWTs stored in localStorage / memory
    (not sent automatically; only JS can read and attach them)
```

The implication: if you move from session cookies to `Authorization: Bearer` header-based auth, you eliminate CSRF entirely — because the attack relies on the browser doing the credential attachment, and the browser only does that automatically for cookies.

**Q2. What makes a request cross-site versus same-site, and what is the difference between cross-site and cross-origin?**
A: These terms are frequently conflated but have different definitions that directly determine CSRF behavior and `SameSite` cookie enforcement:

**Origin** = scheme + host + port:
```
https://app.mybank.com:443   and   https://api.mybank.com:443
→ Different origins (different host)
→ Same site

https://mybank.com   and   http://mybank.com
→ Different origins (different scheme)
→ Depends on SameSite definition
```

**Site** (for cookie purposes) = registrable domain (eTLD+1):
```
eTLD+1 of https://app.mybank.com  = mybank.com
eTLD+1 of https://api.mybank.com  = mybank.com
→ Same site — cookies flow freely between subdomains by default

eTLD+1 of https://mybank.com      = mybank.com
eTLD+1 of https://evil.com        = evil.com
→ Cross-site — this is the CSRF scenario
```

**Schemeful same-site** (Chrome 86+, the modern definition):
```
https://mybank.com  and  http://mybank.com
→ Cross-site under schemeful definition (different scheme)
→ SameSite=Strict/Lax cookies blocked on scheme downgrade
```

Why this matters for CSRF:

```
evil.com → mybank.com:         CROSS-SITE → SameSite blocks cookies
subdomain.mybank.com → mybank.com: SAME-SITE → SameSite does NOT block
                                               Subdomain takeover = CSRF bypass
```

The same-site boundary means that a subdomain XSS or subdomain takeover (`staging.mybank.com` pointing to an expired cloud resource the attacker claims) can still deliver CSRF against `mybank.com` — `SameSite` protection does not apply because both are `mybank.com` sites. This is why defense-in-depth with CSRF tokens is still recommended even when `SameSite` is set.

**Q3. What is the difference between a CSRF attack that reads data and one that modifies state, and which is the primary threat model?**
A: The primary CSRF threat is **state-modifying requests** — actions that change data, trigger transactions, or alter account settings. CSRF does not directly read data:

```
CSRF CAN cause:
  POST /api/transfer           → initiate fund transfer
  POST /api/update-email       → change email to attacker's → account takeover
  POST /api/add-payee          → add attacker's account as a payee
  POST /api/loan/apply         → submit a loan application as the victim
  DELETE /api/sessions         → log victim out of all devices
  PUT /api/notification-prefs  → disable fraud alerts

CSRF CANNOT cause (directly):
  GET /api/account-balance     → attacker cannot read the response
  GET /api/statement           → same-origin policy blocks response reading
```

The same-origin policy (SOP) prevents the attacker's page from reading the response body — `evil.com` can cause the browser to send the request, but the response goes back to the browser and SOP prevents `evil.com`'s JavaScript from reading it. The attacker can trigger actions but cannot exfiltrate data this way.

This is why CSRF protection is focused on **non-idempotent** requests — POST, PUT, PATCH, DELETE. GET requests that cause side effects (a common anti-pattern) are also vulnerable. Safe HTTP methods (GET, HEAD, OPTIONS) should be genuinely read-only, which is a prerequisite for CSRF protection to be effective.

## Section 2: SameSite Cookies

**Q4. Explain the three SameSite values — Strict, Lax, and None — with the exact browser behavior for each.**
A: `SameSite` is a cookie attribute that controls whether the cookie is sent on cross-site requests. It is the modern primary CSRF defense:

**`SameSite=Strict`:**
```
Cookie is sent ONLY when the request originates from the same site as the cookie.
Blocked on ALL cross-site requests — including top-level navigations.

Sent:
  User clicks a link on mybank.com → navigates within mybank.com → cookie sent ✓
  JavaScript on mybank.com makes a fetch() → cookie sent ✓

NOT sent:
  User clicks a link on email.com → navigates TO mybank.com → cookie NOT sent ✗
  User clicks a link on evil.com → any request to mybank.com → cookie NOT sent ✗
  Redirect from payment gateway back to mybank.com → cookie NOT sent ✗

Consequence: user arrives at mybank.com from an external link and appears
  logged out — they must navigate within mybank.com once before the
  Strict cookie is included. Breaks OAuth2 redirects, email confirmation
  links, shared links from messaging apps.
```

**`SameSite=Lax`:**
```
Cookie is sent on same-site requests AND on cross-site top-level GET navigations.
Blocked on cross-site sub-resource requests (fetch, XHR, form POST, iframe).

Sent:
  User clicks a link (GET) on external site → navigates to mybank.com → cookie sent ✓
  JavaScript on mybank.com makes a fetch() → cookie sent ✓
  Top-level GET navigations from anywhere → cookie sent ✓

NOT sent:
  Cross-site POST form submission (the classic CSRF vector) → cookie NOT sent ✗
  Cross-site fetch/XHR regardless of method → cookie NOT sent ✗
  Cross-site iframe loading mybank.com content → cookie NOT sent ✗
  <img src="https://mybank.com/action"> → cookie NOT sent ✗

This is the browser default since Chrome 80 (Feb 2020) if SameSite is unset.
Blocks the most common CSRF attacks. Allows OAuth2 redirects and external links.
```

**`SameSite=None`:**
```
Cookie is sent on ALL requests — same-site and cross-site.
Requires Secure attribute (HTTPS only) — browsers reject None without Secure.

Used for:
  - Third-party widgets (chat, analytics) that need cookie access cross-site
  - OAuth2 / SSO providers where cookies must survive cross-domain redirects
  - Embedded iframes that need authenticated API access

This is the old browser default. Fully vulnerable to CSRF — application must
implement CSRF tokens when using SameSite=None.
```

**Q5. Why is `SameSite=Lax` not sufficient CSRF protection on its own, and what are the four scenarios where it can be bypassed?**
A: `SameSite=Lax` blocks the majority of CSRF vectors but has meaningful gaps:

**Bypass 1 — GET requests with side effects:**
```
SameSite=Lax sends cookies on cross-site top-level GET navigations.
If any of your endpoints perform state-changing actions on GET requests,
they are CSRF-vulnerable even with Lax.

<a href="https://mybank.com/api/confirm-transfer?to=attacker&amount=100000">
  Click here for your prize
</a>

Victim clicks → cross-site GET → Lax cookie sent → transfer executes.

Fix: GET requests must be genuinely read-only. State changes only on
POST/PUT/PATCH/DELETE. This is also required by REST semantics and HTTP spec.
```

**Bypass 2 — 2-minute Lax leniency window (Chrome):**
```
Chrome applies a 2-minute grace period for Lax cookies set WITHOUT an explicit
SameSite attribute. During this window, the cookie is sent even on cross-site
POST requests — to avoid breaking sites that haven't set SameSite but set
short-lived cookies on POST responses (e.g., login forms).

Impact: if you set a session cookie on login response and the attacker triggers
a POST within 2 minutes of cookie issuance, Lax doesn't protect you.

Fix: always set SameSite=Lax (or Strict) EXPLICITLY. The grace period only
applies to cookies with unset SameSite, not to explicitly-set Lax cookies.
```

**Bypass 3 — Subdomain compromise:**
```
SameSite compares eTLD+1, not full origin. If an attacker controls any
subdomain of your domain (staging.mybank.com, old-promo.mybank.com),
they can make same-site requests from that subdomain — Lax/Strict cookies
are sent on same-site requests.

evil subdomain → same-site → CSRF protection bypassed.

Common subdomain takeover: DNS entry for staging.mybank.com points to
a decommissioned Heroku/Netlify/Vercel app. Attacker claims the defunct
deployment → controls staging.mybank.com → delivers CSRF from same-site.

Fix: audit and remove dangling DNS records. CSRF tokens provide defense-in-depth.
```

**Bypass 4 — Browser inconsistencies and old browsers:**
```
SameSite=Lax as browser default: Chrome 80+ (Feb 2020), Safari 13.1+.
Older Android WebViews, older Safari versions, IE11: no SameSite support.
These browsers send cookies on all cross-site requests regardless of SameSite.

In-app browsers (WeChat, Instagram): behavior varies; SameSite support unreliable.

Fix: CSRF tokens work regardless of browser SameSite support.
```

**Q6. How do you set SameSite cookies correctly in Node.js/Express, and what is the `__Host-` prefix and why does it strengthen the defense?**
A: Cookie security requires four attributes working together, plus the optional `__Host-` prefix for maximum hardening:

```typescript
import session from 'express-session';
import RedisStore from 'connect-redis';

// Session cookie with full security attributes
app.use(session({
  store: new RedisStore({ client: redisClient }),
  secret: process.env.SESSION_SECRET,
  name: '__Host-sid',   // __Host- prefix (explained below)
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,       // No JS access — XSS cannot read the cookie
    secure: true,         // HTTPS only — never sent over plain HTTP
    sameSite: 'strict',   // Or 'lax' — never 'none' for session cookies
    maxAge: 24 * 60 * 60 * 1000,  // 1 day
    path: '/',
    // domain: NOT SET — see __Host- explanation below
  },
}));

// JWT refresh token as a secure cookie
res.cookie('refresh_token', refreshToken, {
  httpOnly: true,
  secure: true,
  sameSite: 'strict',
  path: '/auth/refresh',  // Scoped — only sent to /auth/refresh, nowhere else
  maxAge: 30 * 24 * 60 * 60 * 1000,
});
```

**The `__Host-` prefix** (Cookie Prefix):

The `__Host-` prefix is a browser-enforced contract. The browser will only accept a cookie with this name if ALL of the following are true:
```
1. Set with Secure attribute         (HTTPS only)
2. Set with no Domain attribute      (prevents cookie from being scoped to subdomains
                                      — locked to the exact host that set it)
3. Set with Path=/                   (must cover entire site, not a sub-path)

Enforcement: if any condition is violated, the browser silently rejects the cookie.

Effect on CSRF:
  Normal cookie:  Set-Cookie: sid=abc; Secure; SameSite=Strict
    → A subdomain (evil.mybank.com) can set a cookie named 'sid' for .mybank.com
    → Cookie shadowing / session fixation via subdomain

  __Host- cookie: Set-Cookie: __Host-sid=abc; Secure; SameSite=Strict; Path=/
    → No Domain attribute → locked to the exact origin that set it
    → No subdomain can set or override __Host-sid for mybank.com
    → Eliminates the subdomain shadowing CSRF bypass vector
```

The companion prefix `__Secure-` requires only `Secure` (not the `Path=/` and no-`Domain` requirements of `__Host-`). Use `__Host-` for session cookies; `__Secure-` when you genuinely need a domain-wide or path-scoped cookie.

## Section 3: CSRF Tokens

**Q7. How do CSRF tokens work mechanically, and what is the cryptographic property that makes them effective?**
A: A CSRF token is a secret value that:
1. The server knows (stored in session or derivable from a secret)
2. The legitimate client knows (delivered in the page/response)
3. The attacker cannot know (same-origin policy prevents cross-site reading)

The attack is defeated because the forged request cannot include a value only the legitimate client possesses:

```
Legitimate flow:
  1. Server sends HTML page containing a hidden CSRF token
     <input type="hidden" name="_csrf" value="Kx9mR2pL..." />
     OR sets a readable (non-HttpOnly) cookie: csrf_token=Kx9mR2pL...
  2. User submits form → browser includes _csrf field in POST body
  3. Server validates: body._csrf === session.csrfToken → accept

Attack flow:
  1. evil.com cannot read mybank.com's page content (SOP blocks it)
  2. evil.com cannot read mybank.com's non-HttpOnly cookies
     (SOP blocks cross-site cookie reading via document.cookie)
  3. Forged POST from evil.com has no _csrf value (or wrong value)
  4. Server validation fails → request rejected
```

The cryptographic property: CSRF tokens must be:

```
✓ Unpredictable — cryptographically random; not sequential or timestamp-based
✓ Unique per session — or per request for higher security
✓ Sufficient entropy — minimum 128 bits (32 hex characters)
✓ Validated server-side on every state-changing request
✓ NOT in query strings or URLs (logged in access logs, leaked in Referer header)
```

```typescript
import crypto from 'crypto';

// Generate a CSRF token — cryptographically random
function generateCsrfToken(): string {
  return crypto.randomBytes(32).toString('hex'); // 256 bits
}

// Store in session at login
req.session.csrfToken = generateCsrfToken();

// Validate on every mutating request
function validateCsrfToken(req: Request): void {
  const tokenFromRequest =
    req.body._csrf ||
    req.headers['x-csrf-token'] ||
    req.headers['x-xsrf-token'];  // Angular's default header name

  const tokenFromSession = req.session?.csrfToken;

  if (!tokenFromRequest || !tokenFromSession) {
    throw new ForbiddenException('CSRF token missing');
  }

  // Constant-time comparison — prevents timing attacks on token validation
  const requestBuf = Buffer.from(tokenFromRequest);
  const sessionBuf = Buffer.from(tokenFromSession);

  if (requestBuf.length !== sessionBuf.length ||
      !crypto.timingSafeEqual(requestBuf, sessionBuf)) {
    throw new ForbiddenException('CSRF token invalid');
  }
}
```

`crypto.timingSafeEqual` is non-negotiable. A naive `===` string comparison in JavaScript has early-exit behavior — it returns false as soon as the first differing character is found. A timing attacker can measure response time differences to probe the token character by character. `timingSafeEqual` always takes the same amount of time regardless of where the mismatch is.

**Q8. What is the double-submit cookie pattern, how does it work without server-side session storage, and what are its weaknesses?**
A: The double-submit cookie pattern is a stateless CSRF defense — it requires no server-side session to store or retrieve the CSRF token. Instead, it relies on the same-origin policy to enforce that the attacker cannot read the cookie value:

```
Setup (on login or page load):
  1. Server generates a random CSRF token
  2. Server sets it as a NON-HttpOnly cookie (JS must be able to read it)
     Set-Cookie: csrf_token=Kx9mR2pL...; Secure; SameSite=Strict; Path=/
     (NOT HttpOnly — intentionally readable by JavaScript)
  3. Client JavaScript reads the cookie value
  4. On every mutating request, client sends the cookie value in a header:
     X-CSRF-Token: Kx9mR2pL...

Validation:
  Server compares:
    cookie value  (csrf_token cookie — sent automatically by browser)
    header value  (X-CSRF-Token — sent explicitly by JS)
  If they match → legitimate request (only same-site JS could have read the cookie)
  If they differ / header absent → CSRF attack → reject
```

```typescript
// Express implementation — double-submit cookie
app.use((req, res, next) => {
  // Issue CSRF cookie if not present
  if (!req.cookies['csrf_token']) {
    const token = crypto.randomBytes(32).toString('hex');
    res.cookie('csrf_token', token, {
      secure: true,
      sameSite: 'strict',
      path: '/',
      // httpOnly: false — intentionally omitted so JS can read it
    });
    req.csrfToken = token;
  } else {
    req.csrfToken = req.cookies['csrf_token'];
  }
  next();
});

// Client-side (Angular does this automatically for cookies named XSRF-TOKEN)
// For non-Angular clients:
const csrfToken = document.cookie
  .split('; ')
  .find(c => c.startsWith('csrf_token='))
  ?.split('=')[1];

fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': csrfToken,  // Echo the cookie value in a header
  },
  body: JSON.stringify({ to: '...', amount: 100 }),
});

// Server validation
function validateDoubleSubmit(req, res, next) {
  if (!['GET', 'HEAD', 'OPTIONS'].includes(req.method)) {
    const cookieToken  = req.cookies['csrf_token'];
    const headerToken  = req.headers['x-csrf-token'];

    if (!cookieToken || !headerToken) {
      return res.status(403).json({ error: 'CSRF token missing' });
    }

    const a = Buffer.from(cookieToken);
    const b = Buffer.from(headerToken);
    if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
      return res.status(403).json({ error: 'CSRF token mismatch' });
    }
  }
  next();
}
```

**Weaknesses of double-submit:**

```
Weakness 1 — Subdomain cookie injection:
  A compromised subdomain (evil.mybank.com) can set a cookie for .mybank.com:
    Set-Cookie: csrf_token=ATTACKER_KNOWN_VALUE; Domain=.mybank.com; Path=/
  Now attacker knows the csrf_token value AND can forge X-CSRF-Token header.
  Cookie and header match → validation passes → CSRF succeeds.

  Fix: HMAC-signed double-submit (see Q9) — the token is not just random
       but signed with a server secret, so attacker cannot forge a matching pair.

Weakness 2 — Non-HttpOnly cookie readable by XSS:
  If the page has an XSS vulnerability, the attacker reads the csrf_token cookie
  and uses it. But XSS already gives full account control — CSRF is moot at that point.

Weakness 3 — Network attackers on HTTP:
  If any page is served over HTTP, a network attacker can inject a known csrf_token
  cookie into the response. Always enforce HTTPS + HSTS.
```

**Q9. What is the HMAC-signed double-submit (signed cookie) pattern, and how does it address the subdomain injection weakness?**
A: The signed double-submit pattern binds the CSRF token to both a server secret and the user's session — making it impossible for a subdomain attacker to forge a valid token even if they can inject a cookie:

```typescript
import crypto from 'crypto';

const CSRF_SECRET = process.env.CSRF_SECRET; // 32+ random bytes

// Token generation: HMAC of sessionId with server secret
function generateSignedCsrfToken(sessionId: string): string {
  const random  = crypto.randomBytes(16).toString('hex');
  const message = `${sessionId}:${random}`;
  const hmac    = crypto
    .createHmac('sha256', CSRF_SECRET)
    .update(message)
    .digest('hex');

  // Token = random:hmac — both parts sent to client
  return `${random}:${hmac}`;
}

// Token validation: re-derive HMAC, compare
function validateSignedCsrfToken(
  sessionId: string,
  token: string,
): boolean {
  const parts = token.split(':');
  if (parts.length !== 2) return false;

  const [random, receivedHmac] = parts;
  const expectedHmac = crypto
    .createHmac('sha256', CSRF_SECRET)
    .update(`${sessionId}:${random}`)
    .digest('hex');

  // Constant-time comparison
  return crypto.timingSafeEqual(
    Buffer.from(receivedHmac),
    Buffer.from(expectedHmac),
  );
}

// Middleware
app.use((req, res, next) => {
  const sessionId = req.session?.id;
  if (!sessionId) return next();

  // Issue signed token as a non-HttpOnly cookie
  const token = generateSignedCsrfToken(sessionId);
  res.cookie('csrf_token', token, { secure: true, sameSite: 'strict', path: '/' });
  next();
});

// Validation on mutating requests
app.use((req, res, next) => {
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next();

  const cookieToken = req.cookies['csrf_token'];
  const headerToken = req.headers['x-csrf-token'] as string;

  if (!cookieToken || !headerToken) {
    return res.status(403).json({ error: 'CSRF token missing' });
  }

  // Both cookie and header must match — and HMAC must be valid for this session
  if (cookieToken !== headerToken ||
      !validateSignedCsrfToken(req.session.id, headerToken)) {
    return res.status(403).json({ error: 'CSRF token invalid' });
  }

  next();
});
```

Why this defeats the subdomain injection attack:
```
Attacker on evil.mybank.com injects: csrf_token=ARBITRARY_VALUE; Domain=.mybank.com
They can make cookie value == header value (by controlling both).
But HMAC validation fails:
  HMAC(CSRF_SECRET, sessionId:randomPart) ≠ ATTACKER_ARBITRARY_HMAC
Attacker does not know CSRF_SECRET → cannot forge a valid HMAC.
Attack fails.
```

## Section 4: Implementation Patterns

**Q10. How do you implement CSRF protection in a NestJS application end-to-end, including the token delivery mechanism for a SPA?**
A: NestJS doesn't include built-in CSRF protection — the standard approach combines `csurf` (or a custom implementation, since csurf is deprecated) with a cookie-based delivery for SPAs:

```typescript
// csrf.middleware.ts — custom CSRF middleware for NestJS
import { Injectable, NestMiddleware, ForbiddenException } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';
import crypto from 'crypto';

@Injectable()
export class CsrfMiddleware implements NestMiddleware {
  private readonly SAFE_METHODS = new Set(['GET', 'HEAD', 'OPTIONS']);
  private readonly SECRET = process.env.CSRF_SECRET!;

  use(req: Request, res: Response, next: NextFunction): void {
    // Generate and set token on safe requests (SPA fetches it on load)
    if (this.SAFE_METHODS.has(req.method)) {
      const token = this.generateToken(req.session?.id ?? req.ip);
      res.cookie('XSRF-TOKEN', token, {
        // Non-HttpOnly: JS must read this
        secure: true,
        sameSite: 'strict',
        path: '/',
      });
      return next();
    }

    // Validate on mutating requests
    const cookieToken = req.cookies['XSRF-TOKEN'];
    const headerToken = (
      req.headers['x-xsrf-token'] ||      // Angular default
      req.headers['x-csrf-token']          // Axios / manual
    ) as string;

    if (!this.validateToken(req.session?.id ?? req.ip, cookieToken, headerToken)) {
      throw new ForbiddenException('Invalid CSRF token');
    }

    next();
  }

  private generateToken(sessionId: string): string {
    const nonce = crypto.randomBytes(16).toString('hex');
    const mac   = crypto.createHmac('sha256', this.SECRET)
                        .update(`${sessionId}:${nonce}`)
                        .digest('hex');
    return `${nonce}.${mac}`;
  }

  private validateToken(
    sessionId: string,
    cookieToken: string,
    headerToken: string,
  ): boolean {
    if (!cookieToken || !headerToken) return false;

    // Cookie and header must match
    try {
      const cookieBuf = Buffer.from(cookieToken);
      const headerBuf = Buffer.from(headerToken);
      if (cookieBuf.length !== headerBuf.length) return false;
      if (!crypto.timingSafeEqual(cookieBuf, headerBuf)) return false;
    } catch { return false; }

    // HMAC must be valid for this session
    const [nonce, mac] = cookieToken.split('.');
    if (!nonce || !mac) return false;

    const expectedMac = crypto.createHmac('sha256', this.SECRET)
                               .update(`${sessionId}:${nonce}`)
                               .digest('hex');
    return crypto.timingSafeEqual(Buffer.from(mac), Buffer.from(expectedMac));
  }
}

// app.module.ts — apply middleware globally except for the auth endpoints
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(CsrfMiddleware)
      .exclude(
        { path: 'auth/login',   method: RequestMethod.POST },  // Login has no session yet
        { path: 'webhooks/(.*)', method: RequestMethod.ALL },  // Webhooks use HMAC auth
      )
      .forRoutes('*');
  }
}
```

**SPA token delivery — two patterns:**

```typescript
// Pattern A: Dedicated endpoint that delivers the CSRF token
// (SPA calls this once on load, stores token in memory)
@Get('csrf-token')
getCsrfToken(@Req() req: Request, @Res() res: Response) {
  // Middleware already set the cookie on this GET request
  // Also return in body for SPAs that prefer header-based delivery
  const token = req.cookies['XSRF-TOKEN'];
  return res.json({ csrfToken: token });
}

// Pattern B: Embed in the initial page HTML (for server-rendered or hybrid apps)
// <meta name="csrf-token" content="<%= csrfToken %>" />
// JS reads: document.querySelector('meta[name="csrf-token"]').content

// Axios global configuration (reads from cookie — Angular-style):
import axios from 'axios';
axios.defaults.withCredentials = true; // Send cookies cross-origin if needed
axios.interceptors.request.use((config) => {
  const token = document.cookie
    .split('; ')
    .find(c => c.startsWith('XSRF-TOKEN='))
    ?.split('=')[1];

  if (token && !['get', 'head', 'options'].includes(config.method!.toLowerCase())) {
    config.headers['X-XSRF-TOKEN'] = token;
  }
  return config;
});
```

**Q11. How does CSRF protection interact with REST APIs consumed by mobile apps, and do mobile apps need CSRF protection?**
A: Mobile apps (native iOS/Android) are **not vulnerable to CSRF** and do not need CSRF token protection for their API endpoints — with one important caveat:

```
Why mobile API endpoints are CSRF-immune:
  Mobile apps use Authorization: Bearer <token> headers — not cookies.
  The CSRF attack relies on the browser's automatic cookie attachment.
  A malicious website cannot cause a user's native mobile app to make a request.
  A malicious website cannot set Authorization headers on cross-origin requests.
  → No CSRF attack surface for mobile clients using bearer tokens.

The caveat: if your "mobile API" is also consumed by a browser-based SPA
(same endpoints, different client), those endpoints ARE CSRF-vulnerable
for the browser consumers. The authentication mechanism (cookie vs header)
determines CSRF exposure, not the endpoint itself.
```

Practical implementation for APIs serving both mobile and browser clients:

```typescript
// Strategy 1 — Separate endpoint namespaces
// /api/mobile/*  → stateless JWT auth → no CSRF protection needed
// /api/web/*     → session cookie auth → CSRF protection required
// Clean but duplicates route definitions

// Strategy 2 — Single API, authentication-aware CSRF middleware
@Injectable()
export class CsrfMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next();

    // If request uses Bearer token → mobile/API client → no CSRF check needed
    // Bearer token is not automatically attached by browsers → no CSRF risk
    const authHeader = req.headers['authorization'];
    if (authHeader?.startsWith('Bearer ')) {
      return next(); // JWT-authenticated request — CSRF not applicable
    }

    // Cookie-based session → browser client → validate CSRF token
    this.validateCsrf(req);
    next();
  }
}

// Strategy 3 — Custom header requirement (simplified CSRF defense for APIs)
// Require a custom header (e.g., X-Requested-With: XMLHttpRequest) on all API calls.
// Browsers cannot set custom headers on cross-site requests without a CORS preflight.
// CORS preflight from evil.com to mybank.com will be blocked by CORS policy.
// Simple but fragile — doesn't work if your CORS policy is overly permissive.
app.use('/api', (req, res, next) => {
  if (!['GET', 'HEAD', 'OPTIONS'].includes(req.method)) {
    if (!req.headers['x-requested-with']) {
      return res.status(403).json({ error: 'Missing required header' });
    }
  }
  next();
});
```

**Q12. Where should CSRF tokens NOT be placed, and what are the common implementation mistakes that render CSRF protection ineffective?**
A: CSRF protection is frequently implemented incorrectly — these mistakes make it theatrically present but practically absent:

**Mistake 1 — Token in the URL / query string:**
```typescript
// WRONG — token appears in URL
res.redirect(`/dashboard?_csrf=${csrfToken}`);
// GET /dashboard?_csrf=Kx9mR2pL...

Problems:
  ✗ Logged in server access logs → token leaked to log aggregation systems
  ✗ Leaked in Referer header when user clicks a link to external site:
    Referer: https://mybank.com/dashboard?_csrf=Kx9mR2pL...
  ✗ Cached by browser, proxy servers, CDNs
  ✗ Visible in browser history

Correct placement:
  ✓ Hidden form field:  <input type="hidden" name="_csrf" value="..." />
  ✓ Custom request header: X-CSRF-Token (set by JavaScript)
  ✓ Request body for non-form requests: { "_csrf": "..." } in JSON body
```

**Mistake 2 — Validating token but not binding it to the session:**
```typescript
// WRONG — token is globally valid, not session-scoped
const GLOBAL_TOKEN = crypto.randomBytes(32).toString('hex');

// Any authenticated user who learns this token can perform CSRF
// against any other user on the same server (token is shared)
if (req.body._csrf === GLOBAL_TOKEN) {
  // passes — but this is not CSRF protection, it's security theater
}

// CORRECT — token is bound to the specific session
if (!timingSafeEqual(req.body._csrf, req.session.csrfToken)) {
  throw new ForbiddenException('Invalid CSRF token');
}
```

**Mistake 3 — Using HttpOnly for the double-submit cookie:**
```typescript
// WRONG — JS cannot read HttpOnly cookies
res.cookie('csrf_token', token, {
  httpOnly: true,  // ← JS cannot read this; client cannot put it in a header
  // Client sends request without X-CSRF-Token header (can't read it)
  // Validation always fails or is skipped
  // Team adds bypass "if no header, assume ok" → CSRF protection gone
});

// CORRECT — double-submit cookie must be readable by JS
res.cookie('csrf_token', token, {
  httpOnly: false,  // Required for double-submit pattern
  secure: true,     // Still required
  sameSite: 'strict',
});
```

**Mistake 4 — Skipping validation on JSON APIs:**
```typescript
// WRONG — CSRF check only on form submissions, not JSON
app.use((req, res, next) => {
  if (req.headers['content-type']?.includes('application/json')) {
    return next(); // "JSON APIs can't be CSRF'd" — FALSE
  }
  validateCsrfToken(req);
  next();
});

// Modern browsers CAN send cross-site JSON POST requests if:
//   - CORS is misconfigured (allows evil.com with credentials)
//   - The form uses text/plain content type (no preflight) with JSON-parseable body
//   - Flash (legacy) — no longer relevant but demonstrates the class of bypass

// CORRECT — validate CSRF on ALL mutating requests regardless of Content-Type
```

**Mistake 5 — Regenerating token on every request:**
```typescript
// PROBLEMATIC — token changes every request; parallel requests fail
app.use((req, res, next) => {
  req.session.csrfToken = crypto.randomBytes(32).toString('hex'); // New token every time
  next();
});
// SPA sends 3 parallel API calls → each gets a different token
// By the time each response arrives, the session has a different token
// All subsequent requests fail CSRF validation

// CORRECT — generate once per session; rotate on login/logout
req.session.regenerate(() => {
  req.session.userId  = user.id;
  req.session.csrfToken = crypto.randomBytes(32).toString('hex'); // Once per session
});
```

## Section 5: SameSite and CSRF Tokens Together

**Q13. What is the defense-in-depth argument for using both SameSite cookies AND CSRF tokens simultaneously?**
A: Each defense independently blocks different attack vectors. Together they cover each other's gaps:

```
Attack vector                          SameSite=Strict/Lax    CSRF Token
──────────────────────────────────────────────────────────────────────────
Classic cross-site form POST           ✓ Blocks               ✓ Blocks
Cross-site XHR/fetch                   ✓ Blocks               ✓ Blocks
Cross-site GET with side effects       ✗ Sends cookie (Lax)   ✓ Blocks (if checked)
Old browser / no SameSite support      ✗ No protection        ✓ Blocks
Subdomain compromise (same-site POST)  ✗ Sends cookie         ✓ Blocks*
2-min Lax grace period attack          ✗ Sends cookie         ✓ Blocks
Misconfigured CORS + credentialed XHR  ✗ Sends cookie         ✓ Blocks

* Only if CSRF token uses HMAC-signed variant — plain double-submit
  is also defeated by subdomain injection (see Q8)
```

The layered recommendation:

```typescript
// Tier 1 — SameSite (primary, zero application code)
res.cookie('sessionId', sid, {
  sameSite: 'strict',  // Blocks majority of CSRF vectors at browser level
  httpOnly: true,
  secure: true,
});

// Tier 2 — CSRF token (covers SameSite gaps and old browsers)
// Use signed double-submit for stateless services
// Use session-bound token for stateful session services

// Tier 3 — Origin / Referer header validation (cheap extra check)
app.use((req, res, next) => {
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next();

  const origin  = req.headers['origin'];
  const referer = req.headers['referer'];
  const source  = origin ?? (referer ? new URL(referer).origin : null);

  const ALLOWED_ORIGINS = new Set([
    'https://app.mybank.com',
    'https://mybank.com',
  ]);

  // Only check if header is present — don't fail on absent header
  // (some browsers omit Referer for privacy; some requests have no origin)
  if (source && !ALLOWED_ORIGINS.has(source)) {
    logger.warn({ event: 'CSRF_ORIGIN_MISMATCH', source, path: req.path });
    return res.status(403).json({ error: 'Origin not allowed' });
  }

  next();
});
```

The Origin header (not the spoofable `Referer`) is the more reliable signal — it cannot be set by JavaScript (it's a forbidden header name). A missing Origin header should be allowed-through, not rejected — legitimate requests from same-origin navigations may omit it for privacy. Flag and log mismatches; block confirmed foreign origins.

**Q14. How does Angular's built-in CSRF protection work, and how do you configure the server to match its expectations?**
A: Angular's `HttpClientModule` includes automatic CSRF protection via the `HttpClientXsrfModule`. It reads a cookie named `XSRF-TOKEN` (non-HttpOnly) and automatically appends its value as the `X-XSRF-Token` request header on every mutating request — implementing the double-submit cookie pattern transparently:

```typescript
// Angular client — automatic with HttpClientModule
// No code required if cookie is named XSRF-TOKEN and header is X-XSRF-Token

// Optional: customize names if server uses different conventions
import { HttpClientXsrfModule } from '@angular/common/http';

@NgModule({
  imports: [
    HttpClientModule,
    HttpClientXsrfModule.withOptions({
      cookieName: 'XSRF-TOKEN',    // Cookie server sets (non-HttpOnly)
      headerName: 'X-XSRF-Token', // Header Angular sends
    }),
  ],
})
export class AppModule {}
```

```typescript
// NestJS server — must set cookie named XSRF-TOKEN on GET requests
@Injectable()
export class AngularCsrfMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    if (req.method === 'GET' && !req.cookies['XSRF-TOKEN']) {
      const token = this.generateToken(req.session?.id);
      res.cookie('XSRF-TOKEN', token, {
        secure: true,
        sameSite: 'strict',
        path: '/',
        httpOnly: false,  // Angular JS must read this
      });
    }

    if (!['GET', 'HEAD', 'OPTIONS'].includes(req.method)) {
      const cookieToken = req.cookies['XSRF-TOKEN'];
      const headerToken = req.headers['x-xsrf-token'] as string;
      this.validate(cookieToken, headerToken, req.session?.id);
    }

    next();
  }
}
```

Angular does NOT automatically include the CSRF header on cross-origin requests (where `withCredentials: true` is set). For cross-origin Angular apps calling a different-domain API, the CSRF cookie is not sent (SameSite or cross-origin restriction) and Angular's automatic header attachment doesn't work. In this case, fall back to a bearer-token-in-header approach — which is CSRF-immune by construction — rather than trying to make cookie-based CSRF work cross-origin.

## Section 6: Advanced Patterns and Failure Scenarios

**Q15. How do you protect a multipart form file upload endpoint from CSRF?**
A: File upload endpoints are frequently overlooked in CSRF audits because developers assume the `multipart/form-data` content type provides some protection. It does not — browsers can send cross-site multipart form submissions:

```html
<!-- evil.com — cross-site multipart file upload -->
<form action="https://mybank.com/api/kyc/upload" method="POST"
      enctype="multipart/form-data" id="evil-form">
  <input type="file" name="document" />  <!-- pre-populated via JS if possible -->
</form>
<script>document.getElementById('evil-form').submit();</script>
<!-- Cookie attached, multipart sent — file upload triggered without user intent -->
```

Protection requires embedding the CSRF token in the multipart form data or as a query parameter (query parameter only acceptable here because the endpoint validates it explicitly, and attacker cannot read the token to supply it):

```typescript
// Server: accept CSRF token in multipart form field
@Post('kyc/upload')
@UseInterceptors(FileInterceptor('document'))
@UseGuards(JwtAuthGuard)
async uploadDocument(
  @UploadedFile() file: Express.Multer.File,
  @Body('_csrf') csrfToken: string,
  @Req() req: Request,
) {
  // Validate CSRF token from multipart body field
  if (!this.csrfService.validate(req.session.csrfToken, csrfToken)) {
    throw new ForbiddenException('Invalid CSRF token');
  }

  return this.kycService.processDocument(file, req.user.userId);
}

// Client: include CSRF token as a form field in the FormData
const formData = new FormData();
formData.append('document', file);
formData.append('_csrf', getCsrfToken()); // From cookie or meta tag

await axios.post('/api/kyc/upload', formData, {
  headers: {
    'Content-Type': 'multipart/form-data',
    // Can also put it in the header — both approaches valid for multipart
    'X-CSRF-Token': getCsrfToken(),
  },
});
```

Additionally, file upload endpoints need their own resource consumption controls (API4) independent of CSRF — max file size, file type validation, virus scanning — but those don't substitute for CSRF protection.

**Q16. How do you handle CSRF token validation for logout and password-change endpoints specifically, and why are these higher-stakes than regular endpoints?**
A: Logout and password-change are high-stakes targets for CSRF for opposite reasons:

**CSRF logout** — the attacker logs the victim out:
```
Consequence: denial of service, session disruption.
In a trading platform: forced logout during a critical trade window.
In a payment flow: interrupted payment, potential data loss.
Less catastrophic than account takeover but still a real attack.
```

**CSRF on password-change** — the attacker changes the victim's password:
```
Consequence: full account takeover.
Attacker sets the new password to one they know → victim locked out.
Most critical CSRF target in any application.
```

Both must require a CSRF token AND require the current password for the password-change endpoint (defense-in-depth — even with a valid CSRF token, attacker doesn't know the current password):

```typescript
@Post('auth/logout')
@UseGuards(JwtAuthGuard)
@UsePipes(CsrfValidationPipe)  // CSRF required even for logout
async logout(@Req() req) {
  await this.authService.invalidateSession(req.session.id);
  req.session.destroy();
  res.clearCookie('__Host-sid');
  res.json({ message: 'Logged out' });
}

@Patch('account/password')
@UseGuards(JwtAuthGuard)
@UsePipes(CsrfValidationPipe)
async changePassword(
  @Body() dto: ChangePasswordDto,
  @Req() req,
) {
  // Layer 1: CSRF token validation (from CsrfValidationPipe)
  // Layer 2: Current password verification — CSRF bypass doesn't help attacker
  //          without the victim's current password
  const isCurrentPasswordValid = await bcrypt.compare(
    dto.currentPassword,
    req.user.passwordHash,
  );
  if (!isCurrentPasswordValid) {
    throw new UnauthorizedException('Current password incorrect');
  }

  // Layer 3: Invalidate all existing sessions and tokens after password change
  await this.authService.revokeAllSessions(req.user.id);
  await this.userRepo.incrementTokenVersion(req.user.id);

  await this.userRepo.updatePassword(req.user.id, dto.newPassword);
  res.json({ message: 'Password changed. Please log in again.' });
}
```

Re-authentication (requiring current password) for sensitive operations is the strongest defense because it adds a secret the attacker cannot know, independent of CSRF protection. For operations even more sensitive (wire transfers above a threshold, adding new payees, changing 2FA settings), require step-up authentication — re-prompt for password or send an OTP — even mid-session.

**Q17. Scenario: "Your security team finds that CSRF tokens are present in the codebase but a penetration test successfully performed a CSRF attack against the /api/transfer endpoint. Walk through how you would diagnose the failure."**
A: A CSRF token present but bypassable is almost always one of a small set of failure modes. Systematic diagnosis:

```
Step 1 — Reproduce the pentest payload:
  Obtain the exact request the pentester used.
  Did they supply a CSRF token? If yes → validation is broken.
  If no → validation is absent or bypassable for this endpoint.

Step 2 — Check if the endpoint is excluded from CSRF middleware:
  Is /api/transfer in the excluded routes list?
  Common reason: webhook endpoints are excluded, but /api/transfer
  was accidentally added to the same exclude list.

  // app.module.ts
  consumer.apply(CsrfMiddleware)
    .exclude(
      'webhooks/(.*)',
      'api/transfer',  // ← Accidentally excluded during a config change
    )

Step 3 — Check the validation logic for the bypass:
  Does validation short-circuit if token is missing (vs. wrong)?

  // BROKEN — accepts missing token
  if (req.body._csrf && req.body._csrf !== req.session.csrfToken) {
    throw new ForbiddenException('Invalid CSRF token');
  }
  // If _csrf is absent from body → condition is false → proceeds without check

  // CORRECT — rejects both missing and wrong
  if (!req.body._csrf || !timingSafeEqual(req.body._csrf, req.session.csrfToken)) {
    throw new ForbiddenException('CSRF token missing or invalid');
  }

Step 4 — Check if validation runs on JSON body correctly:
  CSRF token in body only works if body is parsed before middleware runs.
  Is body-parser / express.json() registered BEFORE the CSRF middleware?

  // WRONG ordering
  app.use(csrfMiddleware);   // Runs first — req.body is undefined
  app.use(express.json());   // Runs after — too late

  // CORRECT ordering
  app.use(express.json());   // Parse body first
  app.use(csrfMiddleware);   // Then validate CSRF from body

Step 5 — Check Content-Type bypass:
  Does CSRF middleware skip JSON requests?
  Was the pentester's request application/json or text/plain?

Step 6 — Check SameSite cookie attribute:
  Is the session cookie actually sent with SameSite=Strict?
  curl -I https://mybank.com/api/transfer to inspect response headers.
  Is the cookie set on HTTP (downgraded)? SameSite=Strict is ignored on HTTP.

Step 7 — Write regression tests that fail before the fix, pass after:
  it('should reject POST /api/transfer without CSRF token', async () => {
    const res = await request(app)
      .post('/api/transfer')
      .set('Cookie', `__Host-sid=${validSessionCookie}`)
      .send({ to: 'attacker', amount: 1000 }); // No CSRF token
    expect(res.status).toBe(403);
  });
```

## Quick Reference Table

| Aspect | SameSite=Strict | SameSite=Lax | SameSite=None | CSRF Token |
|---|---|---|---|---|
| **Cross-site POST** | ✓ Blocks | ✓ Blocks | ✗ Allows | ✓ Blocks |
| **Cross-site GET** | ✓ Blocks | ✗ Allows (top-level) | ✗ Allows | Blocks if checked |
| **External link navigation** | ✗ Breaks (cookie not sent) | ✓ Works | ✓ Works | N/A |
| **OAuth2 redirect** | ✗ Breaks | ✓ Works | ✓ Works | N/A |
| **Old browsers** | ✗ No protection | ✗ No protection | ✗ No protection | ✓ Blocks |
| **Subdomain compromise** | ✗ Bypassed | ✗ Bypassed | ✗ Bypassed | ✓ Blocks (HMAC) |
| **Lax grace period** | N/A | ✗ Bypassed | N/A | ✓ Blocks |
| **Requires server code** | No | No | No | Yes |
| **Breaks mobile apps** | No | No | No | No (use header) |
| **Best for** | Sensitive internal apps | General web apps | Third-party, OAuth | Defense-in-depth |

**Tip for the interview:** At 5 YOE, the examiner will probe beyond "set `SameSite=Strict` and use CSRF tokens." The signal they're looking for: the **four SameSite=Lax bypass scenarios** (Q5), especially the subdomain-compromise vector — that answer demonstrates you've thought about real-world network topology, not just browser flags. Know the **`__Host-` cookie prefix** (Q6) cold — it's an obscure but high-signal detail. For CSRF token implementation, the **constant-time comparison** (`crypto.timingSafeEqual`) in Q7 and the **HMAC-signed double-submit** in Q9 separate engineers who've shipped auth from those who've read about it. In a fintech context, connect CSRF directly to payment endpoints — the `/api/transfer` and `/account/password` scenarios (Q16) are exactly the business-critical flows that make CSRF a P0 vulnerability rather than a theoretical concern. The diagnosis walkthrough in Q17 is a strong closer — it shows systematic debugging thinking under the pressure of a real security incident.
