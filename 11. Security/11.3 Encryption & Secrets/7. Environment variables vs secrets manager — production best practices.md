# Security (Configuration): Environment Variables vs Secrets Manager — Production Best Practices — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the difference between a configuration value and a secret, and why does the distinction matter?**
A: The terms are often conflated but are meaningfully distinct:

- **Configuration value** — a value that controls application behaviour and varies by environment, but whose exposure does not directly grant access to a system. Examples: `LOG_LEVEL=debug`, `MAX_RETRY_ATTEMPTS=3`, `FEATURE_FLAG_NEW_DASHBOARD=true`, `DATABASE_HOST=rds.ap-south-1.amazonaws.com`. These can be safely committed to a repository (in environment-specific config files), logged, and discussed openly.

- **Secret** — a value whose exposure directly grants access to a protected resource or allows impersonation of a system. Examples: database passwords, API keys, JWT signing secrets, TLS private keys, OAuth client secrets, encryption keys. A secret's value must be kept confidential. Exposure is a security incident requiring immediate rotation and investigation.

The distinction matters operationally because the two categories demand different storage, access control, rotation, and audit requirements. Treating a database password the same as a log level — both as "environment variables" — is the root cause of most credential leakage incidents. The engineering discipline of keeping secrets out of code, out of logs, and out of version control is only possible if developers consciously distinguish between the two categories.

A practical heuristic: if you would be comfortable posting the value in a public Slack channel or committing it to a public GitHub repository, it's configuration. If you would not, it's a secret.

**Q2. What are environment variables, how do processes receive them, and what are their inherent security limitations?**
A: Environment variables are key-value pairs inherited by a process from its parent at launch time. In Unix-like systems they are part of the process environment, accessible via `process.env` in Node.js. They are set:
- By the shell before launching the process: `DB_PASSWORD=secret node app.js`
- In a `.env` file loaded by `dotenv` at runtime
- By a container orchestrator (Docker, ECS, Kubernetes) injecting them into the container spec
- By a CI/CD platform injecting them into a build/deploy job

**Inherent security limitations of environment variables:**

1. **Visible to all processes in the same OS environment** — on a Unix system, any process running as the same user (or root) can read another process's environment via `/proc/<pid>/environ`. In a shared-tenancy environment, this is a lateral movement vector.

2. **Appear in process listings** — `ps aux` or `/proc/<pid>/cmdline` may expose variables if they were passed as command-line arguments rather than environment variables. Even as env vars, some monitoring tools capture and log the full process environment.

3. **Captured in crash dumps and core files** — when a process crashes and produces a core dump, the entire process memory (including the environment) is written to disk. Core dumps are often retained for debugging and may be accessible to more people than the production secrets themselves.

4. **Propagated to child processes automatically** — every subprocess spawned by your Node.js process inherits the full environment. A library that spawns a shell (for example, some native bindings) may expose your secrets to that child process.

5. **Appear in CI/CD logs if mishandled** — `console.log(process.env)` in any code path that runs in CI, or a framework that logs the full configuration on startup, dumps all secrets to the CI log — which is often stored and accessible to many engineers.

6. **No audit trail** — there is no built-in mechanism to record who accessed `process.env.DB_PASSWORD`, when, or how many times. You can't detect if a secret was read by a malicious dependency.

7. **No rotation mechanism** — changing an environment variable typically requires a process restart. There is no native mechanism for rotating a secret and having the running process pick up the new value without downtime.

8. **Version control leakage** — `.env` files containing secrets are the single most common cause of secret exposure in repositories. Despite being in `.gitignore`, they are regularly committed by accident or by developers who don't understand the security model.

**Q3. What is a secrets manager, and what properties does it provide that environment variables cannot?**
A: A secrets manager is a dedicated service for storing, accessing, rotating, and auditing sensitive credentials. AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager, and Azure Key Vault are the main platforms. The properties they provide:

**Access control:** secrets are gated by IAM policies (AWS) or ACL policies (Vault). A service can access only the specific secrets it needs — not all secrets in the account. An engineer can be granted read access to staging secrets but not production secrets, without that control being possible to express with environment variables.

**Audit trail:** every secret access (`GetSecretValue`, `Decrypt`, `read`) is logged with: which principal accessed it, when, from which IP, and whether the access succeeded or was denied. This log is tamper-resistant (CloudTrail, Vault audit log). With environment variables, there is no equivalent — you cannot know which line of code read `process.env.DB_PASSWORD` or whether a compromised dependency did so.

**Automatic rotation:** secrets managers support rotation policies — a rotation Lambda or Vault plugin periodically generates a new secret, updates the downstream system (e.g., rotates the RDS password), and stores the new secret. The application fetches the secret on each use (or with a short cache TTL), so it picks up the rotation without a deployment.

**Versioning and rollback:** multiple versions of a secret are retained. If a rotation produces a broken secret, you can roll back to the previous version in seconds without redeploying anything.

**Encryption:** the secret value is encrypted at rest (using KMS for AWS Secrets Manager) and in transit (HTTPS). The encryption key itself is managed separately with its own access controls and audit trail.

**No static credential storage in config:** the application doesn't store the secret at rest anywhere — it fetches it at runtime using its IAM role (AWS) or a short-lived Vault token. There is nothing to accidentally commit to git because there is no secret to commit — only the IAM role or Vault path, which are not secrets.

## Section 2: Environment Variables — Safe Usage Patterns

**Q4. When are environment variables appropriate, and what is the correct `.env` file discipline?**
A: Environment variables are appropriate for:
- Non-sensitive configuration that varies by environment: `NODE_ENV`, `LOG_LEVEL`, `PORT`, `DATABASE_HOST`, `REDIS_HOST`, feature flags.
- Values that are inherently non-secret: API endpoint URLs, timeout values, queue names, S3 bucket names.
- CI/CD pipeline secrets injected by the platform's secrets mechanism (GitHub Actions secrets, GitLab CI variables marked protected) — these are encrypted by the platform and injected at job runtime, not stored in `.env` files.

Correct `.env` file discipline:

```bash
# .env.example — committed to git; shows the shape, never real values
NODE_ENV=development
LOG_LEVEL=debug
DATABASE_HOST=localhost
DATABASE_PORT=5432
DATABASE_NAME=loans_dev
DATABASE_USER=loans_app
DATABASE_PASSWORD=              # DO NOT put real values here
REDIS_HOST=localhost
REDIS_PORT=6379
JWT_SECRET=                     # fetch from secrets manager in production
AWS_KMS_KEY_ID=                 # fetch from config, not a secret
```

```bash
# .env.local — NOT committed to git (in .gitignore)
# Used only for local development
DATABASE_PASSWORD=localdevpassword   # only a local dev password — no production value
JWT_SECRET=localdevjwtsecret123456  # only for local dev
```

```gitignore
# .gitignore
.env
.env.local
.env.*.local
.env.production
.env.staging
# Never commit any .env file that contains real values
```

The `.env.example` file is committed as documentation of what environment variables the application needs. The actual values are filled in locally (for development) or injected by the deployment platform (for production). Production values are never in any file on any developer's machine.

**Q5. How do you safely inject secrets into a containerised Node.js application in production without environment variables?**
A: The pattern depends on the container orchestration platform, but the principle is consistent: the container spec references a secret by name/ARN, not by value. The secret value is fetched at runtime by the container from the secrets manager using an IAM role — not stored in the container image or task definition.

**AWS ECS with Secrets Manager:**
```json
// ECS Task Definition — secret referenced by ARN, not by value
{
  "containerDefinitions": [{
    "name": "loans-api",
    "image": "123456789.dkr.ecr.ap-south-1.amazonaws.com/loans-api:v2.5.0",
    "secrets": [
      {
        "name":      "DB_PASSWORD",
        "valueFrom": "arn:aws:secretsmanager:ap-south-1:123456789:secret:prod/loans-api/db-password"
      },
      {
        "name":      "JWT_SECRET",
        "valueFrom": "arn:aws:secretsmanager:ap-south-1:123456789:secret:prod/loans-api/jwt-secret"
      }
    ],
    "environment": [
      { "name": "NODE_ENV",      "value": "production" },
      { "name": "DATABASE_HOST", "value": "loans-prod.cluster-abc.ap-south-1.rds.amazonaws.com" },
      { "name": "LOG_LEVEL",     "value": "info" }
    ]
  }]
}
```

ECS resolves the `secrets` entries by calling `secretsmanager:GetSecretValue` using the task's IAM role at container start, then injects the resolved values as environment variables inside the container. The task definition itself contains no secret values — only ARNs. The task definition can be committed to git or stored in Terraform without security risk.

**Kubernetes with External Secrets Operator:**
```yaml
# ExternalSecret CR — references secrets manager, creates a K8s Secret
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: loans-api-secrets
  namespace: loans
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: loans-api-secret     # creates a K8s Secret with this name
    creationPolicy: Owner
  data:
    - secretKey: DB_PASSWORD   # key in the K8s Secret
      remoteRef:
        key: prod/loans-api/db-password   # AWS Secrets Manager key
    - secretKey: JWT_SECRET
      remoteRef:
        key: prod/loans-api/jwt-secret
---
# Deployment references the K8s Secret — not the AWS secret directly
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
        - name: loans-api
          envFrom:
            - secretRef:
                name: loans-api-secret   # injected from the K8s Secret
```

This approach keeps secrets out of the container image, out of the deployment manifest committed to git, and out of the CI/CD pipeline logs. The `ExternalSecret` CR syncs the value from AWS Secrets Manager into a Kubernetes Secret (which is base64-encoded, not encrypted, in etcd — enable etcd encryption at rest separately).

**Q6. What is the risk of `console.log(process.env)` or logging the full configuration object at startup?**
A: Logging the full environment or config object at startup is an extremely common antipattern that causes immediate, comprehensive secret leakage:

```typescript
// DANGEROUS — logs every environment variable including secrets
async function bootstrap() {
  console.log('Starting with config:', process.env);  // leaks DB_PASSWORD, JWT_SECRET, etc.
  // or:
  this.logger.debug('App config', { config: this.configService.getAll() });
}
```

The secrets flow into: application stdout → log aggregator (CloudWatch, Datadog, ELK) → long-term log storage accessible to many engineers → third-party SaaS log tools (if configured) that store data outside your security boundary.

In a regulated environment this is a dual problem: it's a secret exposure incident (immediate security concern) and a compliance violation (PCI-DSS Req 3.3 prohibits storing sensitive authentication data post-authorisation, even in logs; RBI guidelines require equivalent controls).

```typescript
// CORRECT — log a sanitised config that explicitly masks secrets
async function bootstrap() {
  const safeConfig = {
    NODE_ENV:       process.env.NODE_ENV,
    LOG_LEVEL:      process.env.LOG_LEVEL,
    DATABASE_HOST:  process.env.DATABASE_HOST,
    DATABASE_PORT:  process.env.DATABASE_PORT,
    DATABASE_NAME:  process.env.DATABASE_NAME,
    // Secrets: log only presence, never value
    DATABASE_PASSWORD: process.env.DATABASE_PASSWORD ? '[SET]' : '[MISSING]',
    JWT_SECRET:        process.env.JWT_SECRET        ? '[SET]' : '[MISSING]',
    AWS_KMS_KEY_ID:    process.env.AWS_KMS_KEY_ID    ? '[SET]' : '[MISSING]',
  };
  this.logger.log('Application starting', safeConfig);
}
```

A systematic fix: create a `ConfigService` that explicitly categorises every config key as `public` or `secret`, and expose only a `toLogSafe()` method used at startup:

```typescript
// config.service.ts
@Injectable()
export class ConfigService {
  private readonly PUBLIC_KEYS  = new Set(['NODE_ENV', 'LOG_LEVEL', 'DATABASE_HOST', 'PORT']);
  private readonly SECRET_KEYS  = new Set(['DATABASE_PASSWORD', 'JWT_SECRET', 'KMS_KEY_ID']);

  get(key: string): string {
    return process.env[key] ?? '';
  }

  toLogSafe(): Record<string, string> {
    return Object.fromEntries(
      [...this.PUBLIC_KEYS].map(k  => [k, process.env[k] ?? '[NOT SET]']).concat(
      [...this.SECRET_KEYS].map(k  => [k, process.env[k] ? '[SET]' : '[MISSING]'])
      )
    );
  }
}
```

## Section 3: AWS Secrets Manager — Deep-Dive

**Q7. How do you fetch secrets from AWS Secrets Manager in a NestJS application, and where in the startup lifecycle should it happen?**
A: Secrets should be fetched **before** the NestJS application initialises modules — specifically before the DI container builds and before any database connections are established. The pattern is to resolve secrets in `main.ts` before calling `NestFactory.create()`:

```typescript
// secrets.bootstrap.ts
import { SecretsManagerClient, GetSecretValueCommand } from '@aws-sdk/client-secrets-manager';

interface AppSecrets {
  databasePassword:   string;
  jwtSecret:          string;
  jwtRefreshSecret:   string;
  kmsKeyId:           string;
  otpHmacSecret:      string;
  panHmacSecret:      string;
  sessionSecret:      string;
}

export async function loadSecrets(secretId: string): Promise<AppSecrets> {
  const client = new SecretsManagerClient({ region: process.env.AWS_REGION ?? 'ap-south-1' });

  const { SecretString } = await client.send(
    new GetSecretValueCommand({ SecretId: secretId })
  );

  if (!SecretString) {
    throw new Error(`Secret ${secretId} has no string value — check Secrets Manager`);
  }

  const parsed = JSON.parse(SecretString) as Partial<AppSecrets>;

  // Validate all required secrets are present before proceeding
  const required: (keyof AppSecrets)[] = [
    'databasePassword', 'jwtSecret', 'jwtRefreshSecret',
    'kmsKeyId', 'otpHmacSecret', 'panHmacSecret', 'sessionSecret',
  ];

  const missing = required.filter(k => !parsed[k]);
  if (missing.length > 0) {
    throw new Error(`Missing required secrets: ${missing.join(', ')}`);
  }

  return parsed as AppSecrets;
}

// main.ts
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
import { loadSecrets } from './secrets.bootstrap';

async function bootstrap() {
  // Fetch secrets FIRST — before any NestJS initialisation
  const secretId = process.env.SECRET_ID ?? 'prod/loans-api/secrets';
  const secrets  = await loadSecrets(secretId);

  // Inject into process.env so ConfigService can read them normally
  // This avoids threading secrets through module factories
  process.env.DATABASE_PASSWORD = secrets.databasePassword;
  process.env.JWT_SECRET         = secrets.jwtSecret;
  // ... etc

  // Now initialise NestJS — DatabaseModule, JwtModule etc. can read from process.env
  const app = await NestFactory.create(AppModule);
  // ... rest of setup
  await app.listen(3000);
}
bootstrap().catch(err => {
  console.error('Fatal: failed to load secrets', err.message);
  process.exit(1);  // hard fail — never start without secrets
});
```

The `process.exit(1)` on failure is intentional: a service that starts without its secrets is misconfigured and will fail non-deterministically later. Fail fast at startup, emit a clear error, let the orchestrator restart or alert.

**Q8. How does AWS Secrets Manager automatic rotation work, and how do you design your application to handle rotation transparently?**
A: AWS Secrets Manager rotation uses a Lambda function that executes in four steps (the "rotation contract"):

```
Step 1 — createSecret:
  Lambda generates a new credential (e.g., new password) and stores it
  as a new version of the secret with the AWSPENDING label.

Step 2 — setSecret:
  Lambda applies the new credential to the target system
  (e.g., calls ALTER USER in RDS to set the new password).

Step 3 — testSecret:
  Lambda verifies the new credential works
  (e.g., connects to RDS with the new password).

Step 4 — finishSecret:
  Lambda promotes AWSPENDING to AWSCURRENT.
  The previous AWSCURRENT becomes AWSPREVIOUS (retained for 1 rotation cycle).
```

During the window between Step 2 (new password set on RDS) and Step 4 (new password in Secrets Manager as AWSCURRENT), there is a brief period where both the old and new passwords are valid — RDS supports this via a two-password window that Secrets Manager's RDS rotation Lambda exploits. This prevents downtime.

**Application design for transparent rotation:**

The naive approach — fetch secrets once at startup and store them in memory — will break after rotation because the running process holds the old password while the database has the new one:

```typescript
// NAIVE — breaks after rotation
const secrets = await loadSecrets();
const dbPool  = new Pool({ password: secrets.databasePassword });  // stale after rotation
```

Two patterns for rotation resilience:

**Pattern 1 — Fetch on connection error (reconnect with fresh secret):**
```typescript
// database.service.ts — reconnect with fresh secret on auth failure
@Injectable()
export class DatabaseService {
  private pool: Pool;

  async query(sql: string, params: any[]): Promise<QueryResult> {
    try {
      return await this.pool.query(sql, params);
    } catch (err) {
      if (this.isAuthError(err)) {
        // Auth failure may mean the password was rotated — refresh and retry once
        await this.refreshConnection();
        return await this.pool.query(sql, params);
      }
      throw err;
    }
  }

  private async refreshConnection(): Promise<void> {
    const freshSecrets = await loadSecrets(process.env.SECRET_ID!);
    await this.pool.end();  // close all connections in the old pool
    this.pool = new Pool({ password: freshSecrets.databasePassword });
  }

  private isAuthError(err: Error): boolean {
    return err.message.includes('password authentication failed')
        || (err as any).code === '28P01';  // PostgreSQL auth failure code
  }
}
```

**Pattern 2 — Periodic secret refresh with short TTL cache:**
```typescript
// secret-cache.service.ts — refreshes secrets every 5 minutes
@Injectable()
export class SecretCacheService implements OnModuleInit {
  private cache:     AppSecrets | null = null;
  private fetchedAt: number            = 0;
  private readonly TTL_MS = 5 * 60 * 1000;  // 5-minute cache

  async get(): Promise<AppSecrets> {
    const now = Date.now();
    if (!this.cache || (now - this.fetchedAt) > this.TTL_MS) {
      this.cache     = await loadSecrets(process.env.SECRET_ID!);
      this.fetchedAt = now;
    }
    return this.cache;
  }

  async onModuleInit(): Promise<void> {
    // Warm cache on startup
    await this.get();
  }
}
```

The cache TTL should be shorter than the rotation interval (typically 30–90 days) but long enough to avoid excessive Secrets Manager API calls. Secrets Manager pricing is per 10,000 API calls — a 5-minute TTL on a service with 10 instances costs ~`10 * 288 * 30 = 86,400` calls/month, well within the free tier (10,000 calls/month per secret).

**Q9. How do you structure secrets in AWS Secrets Manager for a multi-service, multi-environment fintech platform?**
A: A naming convention that encodes environment, service, and secret category enables fine-grained IAM policies and clear operational ownership:

```
Format: <env>/<service>/<secret-category>

Examples:
  prod/loans-api/database           → { "password": "...", "username": "loans_app" }
  prod/loans-api/jwt                → { "secret": "...", "refreshSecret": "..." }
  prod/loans-api/encryption-keys    → { "panHmac": "...", "otpHmac": "..." }
  prod/kyc-service/digilocker       → { "clientId": "...", "clientSecret": "..." }
  prod/nach-service/npci            → { "merchantId": "...", "apiKey": "..." }
  prod/platform/rds-master          → { "password": "..." }  (used by rotation Lambda)

  staging/loans-api/database        → separate values, separate IAM policy
  dev/loans-api/database            → dev values, accessible to developers
```

**IAM policy for the loans-api ECS task role (prod):**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "LoansApiSecretsAccess",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": [
        "arn:aws:secretsmanager:ap-south-1:123456789:secret:prod/loans-api/*"
      ]
    }
  ]
}
```

The loans-api ECS task role can access only `prod/loans-api/*` — it cannot read `prod/kyc-service/*`, `prod/nach-service/*`, or any staging/dev secrets. This is least-privilege at the secret level: a compromise of the loans-api service doesn't expose the NPCI API key used by the NACH service.

**Cross-service secrets** (e.g., an internal service-to-service API key that Service A uses to call Service B) belong in the consuming service's path — `prod/loans-api/kyc-service-api-key` — not in the producing service's path. The consuming service fetches it; the producing service rotates it.

**Q10. What is the difference between AWS Secrets Manager and AWS Systems Manager Parameter Store, and when do you use each?**
A: Both services store configuration values securely, but they have different price points, feature sets, and intended use cases:

| Aspect | Secrets Manager | Parameter Store |
|---|---|---|
| Primary purpose | Secrets with rotation | Configuration and secrets |
| Cost | $0.40/secret/month + $0.05/10K API calls | Free (Standard); $0.05/parameter/month (Advanced) |
| Automatic rotation | Yes — built-in Lambda rotation | No — manual only |
| Secret versioning | Yes — AWSCURRENT, AWSPENDING, AWSPREVIOUS labels | Yes — parameter versions |
| Cross-account access | Yes | Yes (with resource policies) |
| Max secret size | 65,536 bytes | 4 KB (Standard), 8 KB (Advanced) |
| Encryption | Always encrypted (KMS) | Plaintext (Standard) or encrypted (SecureString with KMS) |
| Reference in ECS/Lambda | Yes (`secrets:` block in task definition) | Yes (`ssm:` reference) |
| Audit trail (CloudTrail) | Yes | Yes |

**When to use Secrets Manager:**
- Database passwords, API keys, OAuth secrets — anything that needs automatic rotation.
- Any secret where you need the AWSPENDING/AWSCURRENT/AWSPREVIOUS rotation lifecycle.
- Secrets that need fine-grained access logging per access.

**When to use Parameter Store:**
- Non-secret configuration that varies by environment: feature flags, endpoint URLs, timeout values, S3 bucket names.
- `SecureString` parameters for secrets that don't need rotation (static API keys for services without rotation support).
- Cost-sensitive environments where `$0.40/secret/month` adds up (a service with 50 secrets = $20/month for Secrets Manager vs essentially free for Parameter Store Standard).

In practice, most mature fintech platforms use both: Secrets Manager for rotatable credentials (database passwords, JWT secrets), Parameter Store for non-rotatable config and lower-sensitivity values. The NestJS bootstrap can load from both:

```typescript
async function loadConfig(): Promise<AppConfig> {
  const [secrets, params] = await Promise.all([
    loadFromSecretsManager('prod/loans-api/secrets'),
    loadFromParameterStore('/prod/loans-api/config'),
  ]);
  return { ...params, ...secrets };  // secrets override config if keys collide
}
```

## Section 4: HashiCorp Vault

**Q11. How does HashiCorp Vault differ from AWS Secrets Manager, and when would you choose it?**
A: Vault is an open-source, self-hosted (or HCP-hosted) secrets management platform. The key differences:

**Vault advantages:**
- **Cloud-agnostic** — Vault works identically across AWS, GCP, Azure, and on-premises. If you have multi-cloud or hybrid infrastructure, Vault provides a single secrets plane rather than managing Secrets Manager + GCP Secret Manager + Azure Key Vault separately.
- **Dynamic secrets** — Vault can generate short-lived, just-in-time credentials on demand. Instead of storing a database password, Vault generates a unique username and password for each service request, valid for (say) 1 hour. When the TTL expires, Vault revokes the credential. No long-lived credentials exist; there's nothing to rotate because credentials are ephemeral.
- **Fine-grained policy engine** — Vault's HCL-based policy language is more expressive than IAM JSON for complex access control scenarios.
- **PKI secrets engine** — Vault can act as a CA and issue short-lived TLS certificates on demand (useful for mTLS in microservices).
- **Database secrets engine** — generates dynamic database credentials for PostgreSQL, MySQL, MongoDB, Cassandra.

**AWS Secrets Manager advantages:**
- **Managed** — no infrastructure to operate. Vault requires a highly-available cluster with storage backend (Consul, DynamoDB, S3), patching, and operational expertise.
- **Native AWS integration** — tight integration with IAM, ECS, Lambda, RDS rotation Lambda. Zero additional infrastructure for AWS-native workloads.
- **Lower operational cost** — no Vault cluster to maintain, scale, and monitor. The $0.40/secret/month cost is well below the engineer-hours cost of operating Vault.

**Choose Vault when:**
- Multi-cloud or hybrid infrastructure where a single secrets plane is essential.
- Dynamic secrets are a hard requirement (ephemeral DB credentials per request).
- You have an existing Vault investment and operational expertise.
- On-premises workloads that cannot reach AWS Secrets Manager.

**Choose AWS Secrets Manager when:**
- AWS-only or AWS-primary infrastructure.
- You want managed, low-operational-overhead secrets management.
- Automatic RDS/Redshift/DocumentDB rotation is sufficient.

**Q12. How do dynamic secrets from Vault work for a database, and what is the security advantage over static passwords?**
A: Vault's database secrets engine connects to your database using a highly-privileged "root" credential (stored in Vault, never exposed to applications) and dynamically creates short-lived credentials on demand:

```
Application requests credentials from Vault:
  GET /v1/database/creds/loans-api-role

Vault (using its stored root DB credential):
  → Generates a unique username: vault-loans-api-a1b2c3d4
  → Generates a random password: Xy8mNp...
  → CREATE ROLE vault-loans-api-a1b2c3d4 WITH PASSWORD '...' VALID UNTIL '2025-08-12 15:30:00';
  → GRANT SELECT, INSERT, UPDATE ON loans_applications TO vault-loans-api-a1b2c3d4;

Vault returns to application:
  { "username": "vault-loans-api-a1b2c3d4", "password": "Xy8mNp...", "lease_duration": 3600 }

Application connects to DB using these credentials.
TTL expires → Vault calls REVOKE ROLE vault-loans-api-a1b2c3d4 in the DB.
Credential no longer works. Application requests fresh credentials.
```

**Security advantages over static passwords:**
- **No long-lived credentials** — the password exists for 1 hour (or whatever TTL is configured). An exfiltrated credential has a self-imposed expiry.
- **Every access is auditable** — each credential request appears in Vault's audit log with which service requested it and when.
- **Blast radius containment per request** — if one instance of the loans-api is compromised, only its unique credential is exposed. All other instances' credentials are different and unaffected.
- **No rotation needed** — there is nothing to rotate because credentials are never long-lived. The problem of "how do you rotate a database password across 10 running service instances without downtime?" simply disappears.
- **Least-privilege per role** — Vault creates the credential with exactly the grants specified in the role definition, no more.

## Section 5: CI/CD Secrets Management

**Q13. How should secrets be handled in a GitHub Actions CI/CD pipeline?**
A: GitHub Actions provides an encrypted secrets store (Settings → Secrets and variables → Actions). Secrets stored here are:
- Encrypted at rest by GitHub.
- Injected into workflow jobs as environment variables — they do not appear in the workflow YAML file.
- Masked in logs — if a secret value appears in any log output, GitHub replaces it with `***`.
- Not accessible to pull requests from forks (by default) — prevents untrusted code from exfiltrating secrets.

```yaml
# .github/workflows/deploy.yml
name: Deploy to Production

on:
  push:
    branches: [main]

# Use OIDC to assume an AWS IAM role — no static AWS credentials stored in GitHub
permissions:
  id-token: write   # required for OIDC token generation
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production   # requires environment approval (manual gate)

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/GitHubActionsDeployRole
          aws-region: ap-south-1
          # No AWS_ACCESS_KEY_ID or AWS_SECRET_ACCESS_KEY stored in GitHub secrets
          # OIDC token is used to assume the IAM role dynamically

      - name: Deploy to ECS
        run: |
          aws ecs update-service \
            --cluster prod-cluster \
            --service loans-api \
            --force-new-deployment

      # Secrets that truly must be in GitHub (non-AWS):
      # store in GitHub Environments secrets, not repository secrets
      # Environment secrets require approval before the job can access them
      - name: Notify deployment
        env:
          SLACK_WEBHOOK: ${{ secrets.SLACK_WEBHOOK_URL }}
        run: curl -X POST -d '{"text":"Deployed"}' $SLACK_WEBHOOK
```

**OIDC-based AWS authentication** is the critical pattern here: instead of storing `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` as GitHub secrets (static long-lived credentials that can be exfiltrated), GitHub Actions generates an OIDC token for each job, which is exchanged for a short-lived AWS IAM role credential via `sts:AssumeRoleWithWebIdentity`. The IAM role policy restricts what that role can do. No static AWS credentials exist anywhere.

**Q14. What is the risk of environment variables in Docker images and how do you prevent them?**
A: Docker images are a particularly dangerous place for secrets due to their distribution model and layer caching:

**Build-time ARG leakage:**
```dockerfile
# DANGEROUS — ARG values are embedded in the image layer history
ARG DB_PASSWORD
ENV DB_PASSWORD=$DB_PASSWORD

# docker history my-image --no-trunc shows:
# /bin/sh -c #(nop)  ENV DB_PASSWORD=actual_password_here
```
`docker history` on any image (including pulled from a registry) shows the commands used to build each layer — including `ENV` instructions with their values. Anyone with read access to the image can recover all `ENV` values, even if those layers have been overwritten in subsequent layers.

```dockerfile
# CORRECT — never put secrets in ENV or ARG in the Dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
# No secrets in the Dockerfile at all
# Secrets are injected at runtime by the orchestrator (ECS secrets:, K8s Secret)
CMD ["node", "dist/main.js"]
```

**Layer caching leakage:**
Even if you delete a file containing a secret in a later layer, the secret is still in the earlier layer's filesystem and accessible via `docker save` + layer extraction. A multi-stage build helps but only if the secret never enters any stage that ends up in the final image.

**Multi-stage build for build-time secrets (e.g., npm private registry token):**
```dockerfile
# syntax=docker/dockerfile:1
FROM node:20-alpine AS builder
# Use BuildKit secret mount — secret available during build but NEVER in the image
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) \
    npm config set //registry.npmjs.org/:_authToken $NPM_TOKEN \
    && npm ci
# Secret is not in any layer — it's a tmpfs mount during the RUN only

FROM node:20-alpine AS runtime
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/main.js"]
```

BuildKit secret mounts are the correct mechanism for any secret needed during `docker build` — the secret is available as a tmpfs mount during that specific `RUN` step and is never written to any layer.

## Section 6: Detection, Rotation, and Incident Response

**Q15. How do you detect secrets that have already leaked into your codebase or git history?**
A: Detection operates at three points: prevention (pre-commit), detection (CI), and retroactive (scanning history):

**Pre-commit hooks (prevent before commit):**
```bash
# Install detect-secrets for pre-commit scanning
pip install detect-secrets

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.4.0
    hooks:
      - id: detect-secrets
        args: ['--baseline', '.secrets.baseline']
        exclude: '(\.example|\.test\.).*'
```

```bash
# Or use git-secrets (simpler, AWS-maintained)
git secrets --install         # install hooks into the repo
git secrets --register-aws    # register AWS credential patterns
git secrets --add 'password\s*=\s*.+'  # add custom patterns
```

**CI scanning (catch what pre-commit misses):**
```yaml
# GitHub Actions — scan every PR
- name: Scan for secrets
  uses: trufflesecurity/trufflehog@main
  with:
    path: ./
    base: ${{ github.event.repository.default_branch }}
    head: HEAD
    extra_args: --only-verified
```

**Retroactive history scan:**
```bash
# Scan entire git history for secrets
docker run --rm -v "$(pwd):/pwd" trufflesecurity/trufflehog:latest \
  git file:///pwd --since-commit HEAD~1000 --only-verified

# gitleaks — another popular tool
gitleaks detect --source . --log-opts="HEAD~1000..HEAD"
```

**GitHub Secret Scanning (automatic, free for public repos):**
GitHub automatically scans all pushes for patterns registered by partner organisations (AWS, Stripe, Twilio, etc.). For private repositories, enable "Secret scanning" in repository settings. When a match is found, GitHub notifies the registered email and can call a webhook to trigger automatic revocation (used by Stripe, GitHub itself, and others).

Register your own key format patterns with GitHub's secret scanning partner program (Q22 in the API keys guide covers this) so your API keys are automatically detected if committed.

**Q16. What is secret sprawl, and how do you prevent it in a growing engineering organisation?**
A: Secret sprawl is the proliferation of copies of secrets across systems — in `.env` files on developer laptops, in CI/CD platform variables, in Slack messages where someone shared a secret for debugging, in Postman collections committed to a shared workspace, in database dump files on an engineer's desktop, in screenshot archives, in old deployment scripts. As an organisation grows, the number of places a secret exists multiplies, and the ability to audit and rotate comprehensively degrades.

**Prevention strategies:**

**1. Single source of truth — secrets manager only:** every service fetches secrets from Secrets Manager at runtime. No secret exists in any other location by policy. Enforced by: not granting engineers direct access to production secret values (only the service IAM role has `GetSecretValue`), requiring new secrets to be created via Terraform (which writes to Secrets Manager, not to `.env` files), and auditing Secrets Manager access patterns to detect any human reading production secrets.

**2. Least-privilege access to secrets:** developers should not have read access to production secrets. In a mature organisation, no human should be able to `GetSecretValue` for a production database password during normal operations — only the ECS task role can. If a developer needs to debug a production issue involving a secret, they use a break-glass procedure (time-limited elevated access with mandatory audit log entry and manager approval).

**3. Short-lived secrets where possible:** dynamic Vault credentials (Q12), short-lived IAM role credentials via OIDC (Q13), short-TTL JWT secrets rotated weekly. The shorter the credential lifetime, the smaller the window of exposure if a secret is inadvertently shared.

**4. Secret inventory and ownership:** every secret in Secrets Manager has a `tags` block with `Owner`, `Service`, `Environment`, and `Rotation` tags. A weekly automated report lists all secrets, their last rotation date, and their owner. Unowned or unrotated secrets are flagged for the security team.

```hcl
# Terraform — every secret has mandatory tags
resource "aws_secretsmanager_secret" "loans_api_db" {
  name = "prod/loans-api/database"

  tags = {
    Owner       = "loans-team"
    Service     = "loans-api"
    Environment = "prod"
    Rotation    = "enabled"
    DataClass   = "confidential"
  }
}
```

**Q17. How do you rotate a JWT signing secret in production without logging out all active users?**
A: JWT secret rotation is one of the more operationally complex rotation scenarios because a new secret invalidates all tokens signed with the old secret — potentially logging out millions of users simultaneously. The correct approach uses a **key rotation with an overlap window**:

```typescript
// jwt-key-store.service.ts — supports multiple active signing keys
@Injectable()
export class JwtKeyStoreService {
  private keys: { id: string; secret: string; validFrom: Date; validUntil: Date }[] = [];

  async loadKeys(): Promise<void> {
    // Secrets Manager stores an array of keys
    const secretValue = await this.sm.getSecretValue('prod/loans-api/jwt');
    this.keys = JSON.parse(secretValue);
    // Example stored value:
    // [
    //   { "id": "v2", "secret": "newSecret...", "validFrom": "2025-08-01", "validUntil": null },
    //   { "id": "v1", "secret": "oldSecret...", "validFrom": "2025-01-01", "validUntil": "2025-09-01" }
    // ]
  }

  getCurrentSigningKey(): { id: string; secret: string } {
    // Sign with the newest key (highest validFrom, no validUntil or future validUntil)
    const current = this.keys
      .filter(k => !k.validUntil || new Date(k.validUntil) > new Date())
      .sort((a, b) => new Date(b.validFrom).getTime() - new Date(a.validFrom).getTime())[0];
    return { id: current.id, secret: current.secret };
  }

  getVerificationKey(keyId: string): string | null {
    // Verify with any non-expired key — allows tokens from the overlap period
    const key = this.keys.find(k =>
      k.id === keyId &&
      (!k.validUntil || new Date(k.validUntil) > new Date())
    );
    return key?.secret ?? null;
  }
}

// Tokens include the key ID in the header for verification lookup
// JWT header: { "alg": "HS256", "kid": "v2" }
// Verification: look up the key by kid, verify with that key
```

**Rotation procedure:**
1. Generate a new JWT secret, add it to the Secrets Manager array with `validFrom: now` and no `validUntil`. The old secret remains with its `validUntil` set to `now + 24h` (the overlap window).
2. Deploy. The service now issues tokens signed with the new key.
3. Old tokens (signed with the old key, presented with `kid: v1`) are still verified using the old key during the overlap window.
4. After the longest possible token lifetime has passed (e.g., `accessToken.expiresIn`), all tokens issued under the old key have expired naturally. No user was logged out.
5. Set `validUntil: now` on the old key (it's already past, so effectively immediately retired). Remove from the array on the next cleanup cycle.

**Q18. How do you manage secrets in a local development environment without exposing production credentials to developers?**
A: The cardinal rule: developers never have access to production secrets. They should not need them. A correctly architected local development environment uses entirely separate, throwaway credentials:

**Approach 1 — Local `.env` with dev-only credentials:**
```bash
# .env.local (gitignored, never shared)
DATABASE_PASSWORD=localdevpassword   # throwaway, not used anywhere else
JWT_SECRET=localdev_jwt_secret_not_used_in_any_other_env
REDIS_PASSWORD=                      # local Redis often has no auth
```
These credentials have zero value if exfiltrated — they only work against a local database running on the developer's machine, not against any shared or production system.

**Approach 2 — Local Secrets Manager / Vault dev instance:**
```bash
# Run a local Vault instance in dev mode (in-memory, no persistence)
vault server -dev -dev-root-token-id="root"

# Or use LocalStack to emulate AWS Secrets Manager locally
docker run -d -p 4566:4566 localstack/localstack
aws --endpoint-url=http://localhost:4566 secretsmanager create-secret \
  --name "dev/loans-api/secrets" \
  --secret-string '{"databasePassword":"localdev","jwtSecret":"localdev"}'
```

**Approach 3 — 1Password / Doppler for team-shared dev secrets:**
Tools like 1Password Teams, Doppler, or Infisical store team-shared development secrets (staging API keys, shared dev database passwords) in a secrets manager that developers can access via CLI, without the secrets ever being in `.env` files:

```bash
# 1Password CLI injection
op run --env-file=.env.op -- node dist/main.js

# Doppler
doppler run -- node dist/main.js

# .env.op (committed to git — no actual values)
DATABASE_PASSWORD=op://dev/loans-api/db/password
JWT_SECRET=op://dev/loans-api/jwt/secret
```

The `op://` URI references a 1Password vault item — the CLI resolves it to the actual value at runtime. The file committed to git contains only URIs, not values. Access to the 1Password vault is controlled by team membership.

## Section 7: Compliance, Auditing, and Real-World Scenarios

**Q19. What do PCI-DSS and RBI guidelines require regarding secret storage and access control?**
A: Both frameworks have concrete requirements that map directly to secrets management practices:

**PCI-DSS v4.0:**
- **Req 8.2.2** — all user IDs and authentication factors must be assigned to individual users. Shared service account passwords must be treated as secrets with controlled access.
- **Req 8.3.9** — passwords must be changed at least every 90 days where passwords are used as authentication factors. Automatic rotation in Secrets Manager satisfies this.
- **Req 8.6.1** — system/application accounts and their authentication factors must be managed per defined policies. Every service credential must have an owner and a rotation schedule.
- **Req 12.3.3** — all cryptographic cipher suites and protocols in use must be documented with a plan for remaining current. This extends to secrets — know what algorithm protects each secret and have a migration plan.
- **Req 10.2.1** — all access to cryptographic keys and secrets must be logged. CloudTrail logging of Secrets Manager access is the mechanism.

**RBI Master Direction on Digital Payment Security Controls:**
- Access to production systems and data must follow the principle of least privilege — no engineer should have standing access to production secrets.
- All privileged access must be logged and reviewed. CloudTrail for Secrets Manager access, reviewed in a SIEM.
- Credentials must be rotated per a documented schedule. Annual for low-risk, quarterly for high-risk (database passwords, payment gateway API keys).
- Separation of duties — the person who creates a secret must not be the same person who approves access to it in production. Terraform + PR review for secret creation; IAM policy review for access grants.

**Q20. Scenario: "A new engineer joins the team and asks you to share the production database password so they can debug an issue. What do you do?**
A: The answer should never be "share the password." This is a test of whether you understand the operational model that secrets management enables, not a test of whether you're unhelpful.

**Why sharing the production password is wrong:**
- It creates a new copy of the secret outside the managed secrets store — on the engineer's laptop, in a Slack message, in their terminal history. Each copy is a new potential exposure point.
- It grants the engineer broader access than they need — they'd have the same database password as the service account, with all its privileges.
- It violates least-privilege and audit trail requirements — database accesses by the engineer won't be distinguishable from service accesses in logs.
- If the engineer ever leaves the company, the password must be rotated to revoke their access — creating operational burden.

**What to do instead:**

```
Option 1 — Grant temporary read access via a separate DB user:
  CREATE USER engineer_raj WITH PASSWORD 'temp_readonly_pass' VALID UNTIL '2025-08-13';
  GRANT SELECT ON loans_applications TO engineer_raj;
  -- Revoke after debugging is complete; change is auditable in DB logs

Option 2 — Use AWS RDS IAM authentication for ad-hoc access:
  aws rds generate-db-auth-token --hostname prod-rds.ap-south-1.rds.amazonaws.com \
    --port 5432 --username engineer_raj --region ap-south-1
  -- Token is valid for 15 minutes; access is logged in CloudTrail
  -- No permanent credential shared

Option 3 — Read-only replica access:
  Direct the engineer to the read replica endpoint (not the primary writer).
  Create a read-only user for them. Revoke after debugging.

Option 4 — Logs and observability instead:
  For most debugging scenarios, the engineer doesn't need direct DB access.
  Provide them with: CloudWatch Logs, X-Ray traces, Datadog APM, or a sanitised
  data export. Resolve the root cause so debugging requires better observability,
  not raw DB access.
```

This scenario comes up in fintech interviews specifically because the regulated environment makes ad-hoc credential sharing both a security violation and a compliance finding.

**Q21. How do you handle secrets for a third-party integration (e.g., a NACH gateway API key) that the vendor can only rotate manually by calling their support team?**
A: Externally-constrained rotation (where the secret owner is outside your control) is a common operational reality. The approach:

**Store in Secrets Manager with a manual rotation Lambda:**
```python
# rotation_lambda.py — alerts instead of rotating automatically
def lambda_handler(event, context):
    if event['Step'] == 'createSecret':
        # Can't auto-generate — send an alert to the operations team
        sns.publish(
            TopicArn=os.environ['ALERT_TOPIC'],
            Subject='[ACTION REQUIRED] NACH API Key rotation due',
            Message=f"""
                The NACH gateway API key (secret: prod/nach-service/npci)
                is due for rotation per the 90-day schedule.

                Action required:
                1. Contact NPCI support to request a new API key
                2. Update the secret: aws secretsmanager put-secret-value \
                   --secret-id prod/nach-service/npci \
                   --secret-string '{{"apiKey":"<new-key>"}}'
                3. Verify the nach-service is using the new key
                4. Confirm rotation complete in Secrets Manager console

                Current key was last rotated: {last_rotation_date}
            """
        )
        raise Exception('Manual rotation required — ops team notified')
```

This gives you the rotation *reminder* and audit trail from Secrets Manager (the rotation event is logged even if it fails), without pretending you can automate what is inherently manual. The SNS alert creates an ops ticket; the engineer coordinates with the vendor and updates the secret manually.

**Compensating controls for slow-rotation keys:**
- Narrow the IAM policy so only the NACH service task role can access this specific secret.
- Enable CloudTrail alerts for any access from an unexpected IAM entity.
- Store the key in Secrets Manager with `rotation_enabled: false` and a `Tags: { RotationConstraint: "manual-vendor" }` tag so the rotation compliance report clearly shows this is an exception, not negligence.
- Document the vendor's rotation procedure in your runbook and review it at least annually.

**Q22. What is the difference between a secret and a service account credential, and how do you manage service-to-service authentication without secrets?**
A: A *secret* is a static credential — a value that must be kept confidential and rotated. A *service account credential* managed by modern IAM systems (AWS IAM roles, Kubernetes service accounts, Workload Identity) is fundamentally different: it's a *short-lived, automatically-refreshed token* issued based on the service's cryptographic identity — no secret to store, no rotation to schedule.

**The modern pattern — no secrets for service-to-service auth:**

```
AWS EC2 / ECS / Lambda:
  Service runs with an IAM role (attached to the EC2 instance, ECS task, or Lambda function).
  AWS metadata service provides temporary credentials: AccessKeyId, SecretAccessKey, SessionToken.
  Credentials rotate automatically every ~1 hour.
  No credential stored anywhere — the IAM role itself is the identity.

Kubernetes:
  Pod runs with a ServiceAccount.
  The service account token is projected into the pod (volumes.projected.serviceAccountToken).
  Token is short-lived (1 hour by default, auto-rotated by kubelet).
  External services authenticate the token via TokenReview API.

GCP:
  Workload Identity binds a Kubernetes ServiceAccount to a GCP Service Account.
  Same zero-secret model.
```

When services use IAM roles rather than static credentials, there are no secrets to manage, rotate, or accidentally commit. The cryptographic identity is the IAM role; access is controlled by IAM policies; audit trail is in CloudTrail. This is the goal state for service-to-service auth in a cloud-native architecture. Static API keys between internal services are a last resort when IAM-based auth is not available.

**Q23. Scenario: "Your Terraform code creates AWS Secrets Manager secrets. A reviewer points out that the `aws_secretsmanager_secret_version` resource in Terraform stores the secret value in plaintext in the Terraform state file. How do you address this?"**
A: This is a real and important Terraform security issue. The Terraform state file records every resource's attributes — including `secret_string` for `aws_secretsmanager_secret_version`. Since state files are stored in S3 (hopefully with SSE-KMS encryption), the secret is in the state file encrypted at rest — but anyone with access to the state file (S3 read access to the state bucket) can recover the plaintext secret, which is a broader access than you'd want.

**Option 1 — Don't put secrets in Terraform at all (preferred):**
```hcl
# Terraform creates the secret shell (metadata) but not the value
resource "aws_secretsmanager_secret" "loans_api_db" {
  name        = "prod/loans-api/database"
  description = "Loans API database credentials"
  kms_key_id  = aws_kms_key.secrets.arn

  tags = { Service = "loans-api", Environment = "prod" }
}
# The actual secret value is set separately — by a rotation Lambda, by a
# manual bootstrap script, or by a CI/CD step that has Secrets Manager write
# access but whose output is not stored in state.
```

This way the Terraform state contains only the secret's ARN and metadata — not its value.

**Option 2 — If you must initialise the secret in Terraform, use a data source or external provider:**
```hcl
# Use Terraform's external data source to read the initial value from a file
# or from another secrets manager — never hardcode it
data "external" "initial_secret" {
  program = ["bash", "-c", "echo '{\"password\": \"'$(vault kv get -field=password secret/bootstrap/db)'\"}'"]
}

resource "aws_secretsmanager_secret_version" "loans_api_db" {
  secret_id     = aws_secretsmanager_secret.loans_api_db.id
  secret_string = jsonencode({ password = data.external.initial_secret.result.password })

  lifecycle {
    ignore_changes = [secret_string]  # don't drift-detect after rotation
  }
}
```

**Option 3 — Restrict state file access to match secret access:**
If the secret value is in state, ensure the state S3 bucket's IAM policy is as restrictive as the Secrets Manager IAM policy — only the CI/CD role and the service role can read the state bucket. State encryption with a separate KMS CMK from the secrets themselves. This doesn't eliminate the exposure but contains it.

**Q24. How do you implement a "break glass" procedure for emergency production access when the normal secrets management path is unavailable?**
A: Break glass is the emergency procedure for accessing production systems when the normal access path is broken — Secrets Manager is unreachable, the rotation Lambda misbehaved, or the IAM role is misconfigured. It must be: difficult enough to discourage casual use, easy enough to execute in an actual emergency, and fully auditable.

```
Break glass procedure design:

1. Break glass IAM role — a role with broader production access, assumable only by:
   - Specific senior engineers (named in the role's trust policy)
   - Requires MFA (Condition: aws:MultiFactorAuthPresent = true)
   - Has a session duration of 1 hour maximum

   {
     "Effect": "Allow",
     "Principal": { "AWS": "arn:aws:iam::123:user/senior-engineer-raj" },
     "Action": "sts:AssumeRole",
     "Condition": {
       "Bool": { "aws:MultiFactorAuthPresent": "true" },
       "DateLessThan": { "aws:CurrentTime": "2025-12-31T00:00:00Z" }
     }
   }

2. CloudTrail alert on assumption — any use of the break glass role fires a
   PagerDuty/Slack alert to the security team immediately.
   The assumption is the alarm, not the post-hoc detection.

3. Physical break glass key — for complete IAM outage scenarios:
   A sealed envelope in a physical safe (at the office, not in a cloud system)
   containing the master DB password and root account credentials.
   Opening the envelope requires two engineers simultaneously (dual control).
   After use: rotate every credential in the envelope and replace the envelope.

4. Post-incident review mandatory — any break glass use triggers a mandatory
   post-incident review: why was it needed, how can the normal path be made
   more resilient so break glass isn't needed again.
```

**Q25. What is the complete secrets management architecture for a production NestJS fintech platform?**
A: End-to-end architecture covering all layers:

**Secret categorisation and storage:**
```
AWS Secrets Manager (rotatable credentials):
  prod/loans-api/database          → DB password (auto-rotation: 90 days)
  prod/loans-api/jwt               → JWT signing keys (manual rotation with overlap: 180 days)
  prod/loans-api/encryption-keys   → PAN HMAC, OTP HMAC secrets (rotation: 180 days)
  prod/kyc-service/digilocker      → OAuth client secret (manual rotation: per vendor)
  prod/nach-service/npci           → NACH API key (manual rotation: per vendor SLA)

AWS Parameter Store (non-rotatable config):
  /prod/loans-api/database-host    → RDS endpoint (not a secret)
  /prod/loans-api/redis-host       → ElastiCache endpoint (not a secret)
  /prod/loans-api/feature-flags    → JSON feature flag config (not a secret)

AWS KMS (encryption keys — never leave KMS):
  prod/loans-api/data-key          → for PAN, Aadhaar field-level encryption
  prod/terraform-state             → for Terraform S3 state bucket encryption
  prod/secrets-manager             → for Secrets Manager secret encryption
```

**Access control:**
```
IAM Roles (no static credentials anywhere):
  LoanApiTaskRole:
    - secretsmanager:GetSecretValue on prod/loans-api/*
    - ssm:GetParameter on /prod/loans-api/*
    - kms:Decrypt, kms:GenerateDataKey on prod/loans-api/data-key
    - (no access to prod/kyc-service/* or prod/nach-service/*)

  GitHubActionsDeployRole (via OIDC):
    - ecs:UpdateService, ecr:GetAuthorizationToken (deploy only)
    - secretsmanager:GetSecretValue on prod/*/rotation-test (smoke test only)
    - NO access to production secret values

  BreakGlassRole (MFA required, CloudTrail alerted):
    - secretsmanager:GetSecretValue on prod/* (emergency only)
    - rds-db:connect (direct DB access in emergency)
```

**Application startup sequence:**
```
1. ECS resolves secrets: ARNs → plaintext values → inject as env vars
2. NestJS bootstrap: loadSecrets() validates all required values present
3. ConfigService: categorises public vs secret keys, toLogSafe() at startup
4. DatabaseModule: connects using DB_PASSWORD from env
5. JwtKeyStoreService: loads current + previous signing keys
6. EncryptionService: validates KMS key accessible (test encrypt/decrypt)
7. Health check endpoint: returns 200 only after all above succeed
8. Load balancer: routes traffic only after health check passes
```

**Rotation schedule and responsibility:**
```
Automated (Secrets Manager rotation Lambda):
  - DB passwords: 90-day rotation (RDS single-user rotation Lambda)
  
Manual with automated reminders (SNS alert at T-14 days):
  - JWT signing keys: 180-day rotation
  - PAN/OTP HMAC secrets: 180-day rotation
  - Third-party API keys: per vendor SLA (documented in runbook)

Never rotate (asymmetric — revoke instead):
  - TLS certificates: managed by ACM (auto-renewal 60 days before expiry)
  - IAM role credentials: ephemeral (auto-refreshed by metadata service)
```

**Audit and monitoring:**
```
CloudTrail → CloudWatch Logs → Metric Filters → CloudWatch Alarms → PagerDuty:
  - Alert: any GetSecretValue from IAM entity other than expected task role
  - Alert: any GetSecretValue for prod secrets from non-prod account
  - Alert: BreakGlassRole assumed (immediate page)
  - Alert: secrets rotation failure (rotation Lambda error)
  - Daily report: all secrets, last rotation date, owner — reviewed by SecOps
```

| Aspect | Environment Variables | AWS Secrets Manager | Parameter Store (SecureString) | HashiCorp Vault |
|---|---|---|---|---|
| Secret at rest | Plaintext in process env | Encrypted (KMS CMK) | Encrypted (KMS CMK) | Encrypted (Vault seal key) |
| Audit trail | None | CloudTrail per access | CloudTrail per access | Vault audit log per access |
| Access control | OS-level only | IAM policies | IAM policies | Vault policies (HCL) |
| Automatic rotation | No | Yes (Lambda) | No | Yes (dynamic secrets) |
| Rotation without restart | No | Yes (with cache refresh) | No | Yes (lease renewal) |
| Dynamic credentials | No | No | No | Yes (DB, PKI, cloud) |
| Cost | Free | $0.40/secret/month | Free (Standard) | Self-hosted infra cost |
| Git commit risk | High (.env files) | None (only ARN/path) | None (only path) | None (only Vault path) |
| Multi-cloud | Yes | AWS only | AWS only | Yes |
| Appropriate for | Local dev only | Production secrets | Config + low-risk secrets | Multi-cloud / dynamic creds |

**Tip for the interview:** At 5 YOE, secrets management questions are rarely theoretical — they're scenario-based: "how would you handle this rotation?", "a developer committed a secret to git — what do you do?", "how do you give an engineer debug access without sharing the production password?" Know the OIDC-based GitHub Actions pattern (Q13) cold — not storing `AWS_ACCESS_KEY_ID` in GitHub is the single highest-impact secret management improvement most teams can make immediately. Know the ECS `secrets:` block vs `environment:` block distinction (Q5) — this is the most common interview question about containerised secrets. The Terraform state file secret exposure (Q23) comes up regularly because it's a real gotcha that catches engineers who think "it's in Secrets Manager" means "it's not in state." For fintech: the break-glass procedure (Q24) and the "engineer asks for production password" scenario (Q20) are strong signals of operational maturity — have clear, principled answers for both.
