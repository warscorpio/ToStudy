## Section 1: Key Management Fundamentals

**Q1. What is key management, and why is it a distinct discipline from cryptography itself?**
A: Cryptography solves the algorithm problem: given a key, how do you encrypt, sign, or authenticate data correctly? Key management solves the operational problem: how do you generate, distribute, store, rotate, revoke, audit, and destroy keys across their entire lifecycle — without the keys ever being exposed to unauthorized parties, including your own engineers.

The distinction matters because cryptographic algorithms are nearly impossible to break directly — AES-256 has no known practical attacks. Real-world cryptographic failures almost always come from key management failures:

```
Real-world key management failures (not algorithm breaks):

  Hardcoded keys in source code:
    Developer commits AWS_SECRET_KEY to a public GitHub repo.
    Bots scan GitHub for leaked credentials — key is used within minutes.
    Algorithm: AES-256 (unbroken). Key management: catastrophic failure.

  Key never rotated:
    API key from 2018 is still active in 2024.
    Former employee who left in 2020 still has a copy.
    A contractor who used the key in 2019 retained it.
    Algorithm: HMAC-SHA256 (unbroken). Key management: failure.

  Key stored in plaintext:
    Database connection string with password in a config file.
    Config file checked into version control.
    Config file included in a Docker image pushed to Docker Hub.
    Algorithm: TLS (unbroken). Key management: failure.

  Key with no access logging:
    Attacker exfiltrates an encryption key.
    The breach goes undetected for 18 months because no audit log exists.
    There is no way to determine what was decrypted or when.

  Single key for everything:
    One master API key used by 15 services.
    When it leaks, all 15 services are compromised simultaneously.
    Blast radius: total. Correct: one key per service per environment.
```

Key management answers six lifecycle questions for every key:

```
1. Generation:  How is the key created? (CSPRNG, HSM, KDF)
                How many bits of entropy? (128 minimum for symmetric, 256 preferred)
                Who can generate a new key?

2. Storage:     Where is the key stored? (HSM, KMS, Vault, encrypted at rest)
                Who has access to the storage system?
                Is the key ever in plaintext outside of a hardware boundary?

3. Distribution: How does a service get the key it needs?
                 Is the key transmitted securely? (TLS, encrypted envelope)
                 Is the key ever logged, cached, or written to disk unintentionally?

4. Usage:       What is the key authorized to do? (encrypt only, decrypt only, sign)
                Which principals (services, users) may use it?
                Are usage events logged?

5. Rotation:    How often is the key rotated?
                What happens to data encrypted with old keys?
                Is rotation automated or manual?

6. Revocation / Destruction:
                How is a key revoked if compromised?
                Is revocation immediate or eventually consistent?
                Are old key materials securely destroyed (NIST SP 800-88)?
```

**Q2. What is the difference between a key, a secret, and a credential — and why does the distinction matter for management strategy?**
A:

```
Cryptographic Key:
  Random bytes used directly as input to a cryptographic algorithm.
  Examples: AES-256 encryption key (32 bytes), HMAC-SHA256 signing key (32 bytes),
            RSA private key (2048–4096 bits), ED25519 key pair.
  Properties:
    - Generated by a CSPRNG or derived from a KDF — never chosen by a human.
    - Has a specific algorithm context: an AES key is useless outside AES.
    - Rotation requires re-encrypting or re-signing data encrypted/signed with the old key.
    - Should never leave the boundary of an HSM or KMS in plaintext form.

Secret:
  Any sensitive string that authenticates or authorizes, but is not a cryptographic key.
  Examples: API keys, webhook signing secrets, OAuth client secrets, database passwords,
            session signing secrets, JWT signing secrets.
  Properties:
    - Often human-readable or human-generated (problematic — use CSPRNG instead).
    - Opaque to the service using them — the value is the credential.
    - Rotation requires coordinating both the issuer (update the stored value)
      and the consumer (update the application's reference to the secret).
    - Stored in a secrets manager (Vault, AWS Secrets Manager) rather than a KMS.

Credential:
  Broader term: any proof of identity or authorization.
  Includes: username/password pairs, TLS client certificates, Kerberos tickets,
            AWS IAM temporary credentials (access key + secret key + session token).
  Properties:
    - Often time-limited (IAM temporary credentials expire in hours).
    - May be derived from another credential (IAM role assumption).
    - Rotation may involve certificate reissuance, password reset, or token refresh.

Why the distinction matters for management strategy:

  Cryptographic keys → AWS KMS, GCP Cloud KMS, Azure Key Vault, HSM.
    The key material ideally never leaves the hardware boundary.
    Operations (encrypt, decrypt, sign) are performed BY the KMS, not by your code.
    Rotation: KMS manages versions; old ciphertext can be decrypted with old key version.

  Secrets → HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager.
    The secret value is retrieved by the application and used directly.
    Rotation: Vault can auto-rotate database passwords; applications re-fetch on TTL.

  Credentials → IAM, OIDC, service accounts, short-lived tokens.
    Prefer time-limited, dynamically issued credentials over static long-lived ones.
    Rotation: issue a new credential rather than rotating the old one.
    Best practice: never use long-lived static credentials where dynamic ones are available.
    (AWS: use IAM roles for EC2/Lambda, not hardcoded access keys)
```

## Section 2: Key Rotation

**Q3. What is key rotation, and what are the two distinct types — cryptographic key rotation vs. secret rotation?**
A: "Key rotation" is used loosely to mean two different operations with different mechanics and risks. Confusing them leads to incomplete rotation strategies.

```
Type 1 — Cryptographic Key Rotation (encryption/signing keys):

  The old key is retired. A new key is generated. Data must be re-encrypted or
  re-signed with the new key, OR the old key must be retained for decryption
  of legacy ciphertext while the new key is used for new encryptions.

  The re-encryption problem:
    If you have 10 million rows encrypted with key_v1, rotating to key_v2 requires:
    - Decrypt each row with key_v1
    - Re-encrypt each row with key_v2
    - Update the stored ciphertext
    This is a large, coordinated operation — not atomic, not instant.

  Envelope encryption solves this (see Q5):
    Rows are encrypted with a Data Encryption Key (DEK), not the master key directly.
    The DEK is encrypted with the master Key Encryption Key (KEK).
    Rotating the KEK: re-encrypt only the DEK (one operation), not all the data.
    The data itself (and its DEK) doesn't change — only the DEK's envelope changes.

  Key version retention:
    Old key versions must be retained for decryption of existing ciphertext.
    They must NOT be used to encrypt new data (only the current version does that).
    Retirement schedule: retain key_v1 until all ciphertext encrypted with it is
    re-encrypted with key_v2 (or that data is deleted).

Type 2 — Secret Rotation (API keys, passwords, tokens):

  The old secret is replaced with a new value. All consumers must update their
  reference to the secret before the old one is revoked.

  The dual-write window:
    Period during which BOTH old and new secret are valid, allowing consumers to
    update their configuration without downtime.

    Time 0:   new_secret generated; both old_secret and new_secret are valid.
    Time 0–T: applications update their references to new_secret (rolling deploy).
    Time T:   old_secret revoked. Only new_secret is valid.
    Window T: should be long enough for all consumers to update (minutes to hours).

  Zero-downtime rotation pattern:
    Step 1: Generate new_secret. Store it alongside old_secret (both active).
    Step 2: Update all consumers via rolling deploy / config push.
    Step 3: Verify all consumers are using new_secret (no auth failures in logs).
    Step 4: Revoke old_secret.
```

**Q4. Why rotate keys at all — what threats does rotation mitigate, and what does it not mitigate?**
A:

```
What rotation mitigates:

  1. Undetected compromise:
     If an attacker exfiltrated key_v1 in January and you rotate to key_v2 in March,
     the attacker's copy of key_v1 becomes useless for decrypting new data from March onward.
     Without rotation: a compromised key remains useful indefinitely.

  2. Limiting blast radius of a future breach:
     Data encrypted with key_v1 (Jan–Mar) is at risk if key_v1 is later compromised.
     Data encrypted with key_v2 (Mar–Jun) is not at risk from the key_v1 compromise.
     Shorter rotation window = smaller window of data exposure per key.

  3. Insider threat and employee departure:
     A departing employee may retain a copy of a secret they had access to.
     Rotating after departure revokes their copy.
     Regular rotation limits the window during which retained copies are useful.

  4. Compliance requirements:
     PCI-DSS: cryptographic keys must be rotated at least annually (more frequently if compromised).
     NIST SP 800-57: recommends cryptoperiods based on algorithm, key size, and usage volume.
     SOC 2 / ISO 27001: rotation policies must be documented and evidenced.

What rotation does NOT mitigate:

  1. A key that is currently compromised and actively being used:
     Rotation helps after the fact. If an attacker has key_v1 NOW, they can decrypt
     key_v1 ciphertext NOW. You must revoke, not just rotate.
     Rotation ≠ revocation. Revocation must be immediate; rotation is scheduled.

  2. A compromised rotation mechanism:
     If the process that generates and distributes new keys is compromised,
     the attacker gets the new key at rotation time.
     Rotation without a secure rotation mechanism is theater.

  3. Data already encrypted/exfiltrated with the old key:
     If an attacker exfiltrated encrypted data in January and gets key_v1 in February,
     rotating to key_v2 in March does not protect the January data.
     The data was encrypted with key_v1; key_v1 still decrypts it.

  4. Secrets stored in places outside the rotation system:
     Rotating a database password in Vault means nothing if the old password is also
     hardcoded in a Dockerfile, a .env file, a Slack message, or a CI environment variable.
     Rotation must be comprehensive or it creates a false sense of security.

Rotation frequency guidelines (NIST SP 800-57, OWASP):

  Type                        Recommended rotation period
  ─────────────────────────── ─────────────────────────────────────────────────
  Symmetric encryption keys   1 year; immediately on suspected compromise
  Asymmetric signing keys     1–2 years (RSA/EC); immediately on compromise
  TLS certificates            1 year (Let's Encrypt: 90 days, auto-renewed)
  Database passwords          90 days; immediately on personnel departure
  API keys / service secrets  90 days; immediately on suspected exposure
  JWT signing secrets         90 days (or use asymmetric keys with JWKS rotation)
  IAM access keys             Never — use IAM roles instead; if unavoidable: 90 days
  Session signing keys        Frequently (30–90 days); old sessions can be invalidated
```

**Q5. What is envelope encryption, and why is it the standard pattern for large-scale key management?**
A: Envelope encryption is a two-tier key hierarchy that separates the keys that protect data (Data Encryption Keys, DEKs) from the keys that protect those keys (Key Encryption Keys, KEKs). It solves the re-encryption problem for large datasets and enables secure key rotation at scale.

```
Without envelope encryption (naive):

  Plaintext → [AES-256 with master_key] → Ciphertext
  Store: ciphertext (in DB), master_key (in KMS)

  Rotating master_key:
    For every row/blob in your database:
      ciphertext_new = AES.encrypt(AES.decrypt(ciphertext_old, key_v1), key_v2)
    10 million rows × 200ms = 2 million seconds = 23 days
    Not feasible. Data is unavailable or at risk during rotation.

With envelope encryption:

  For each record:
    1. Generate a unique DEK: dek = CSPRNG(32 bytes)           ← per-record key
    2. Encrypt the data:      ciphertext = AES.encrypt(data, dek)
    3. Encrypt the DEK:       encrypted_dek = KMS.encrypt(dek, kek_v1)
    4. Store:                 (ciphertext, encrypted_dek) together

  Rotating the KEK (kek_v1 → kek_v2):
    For each record:
      dek = KMS.decrypt(encrypted_dek, kek_v1)
      encrypted_dek_new = KMS.encrypt(dek, kek_v2)
      Store encrypted_dek_new (replace encrypted_dek)
    ← Only the DEK envelope changes. The ciphertext is untouched.
    ← 10 million rows: just re-encrypt 32-byte DEKs. Feasible in minutes.

  At decryption time:
    dek = KMS.decrypt(encrypted_dek, kek)     ← KMS decrypts the DEK
    plaintext = AES.decrypt(ciphertext, dek)  ← application decrypts data with DEK

  Properties:
    - The master KEK never leaves the KMS (hardware boundary).
    - Each record has a unique DEK — compromising one DEK exposes one record.
    - Key rotation = re-wrapping DEKs, not re-encrypting data.
    - The DEK is only in memory during encryption/decryption — never stored plaintext.
```

```python
# Envelope encryption implementation using AWS KMS

import boto3
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from dataclasses import dataclass
import base64

kms = boto3.client("kms", region_name="us-east-1")
KEY_ID = os.environ["KMS_KEY_ID"]   # ARN or alias of the KEK in KMS

@dataclass
class EncryptedRecord:
    ciphertext:    bytes   # AES-GCM encrypted data
    encrypted_dek: bytes   # DEK encrypted by KMS (the "envelope")
    nonce:         bytes   # 12-byte AES-GCM nonce

def encrypt(plaintext: bytes) -> EncryptedRecord:
    # Step 1: Ask KMS to generate a DEK
    # KMS returns two forms: plaintext DEK (for immediate use) and encrypted DEK (for storage)
    # The plaintext DEK is only held in memory — never stored.
    response = kms.generate_data_key(
        KeyId=KEY_ID,
        KeySpec="AES_256",   # 32-byte DEK
    )
    dek_plaintext  = response["Plaintext"]      # 32 bytes — use now, discard after
    dek_encrypted  = response["CiphertextBlob"] # encrypted DEK — store with data

    # Step 2: Encrypt the data with the DEK using AES-256-GCM
    nonce      = os.urandom(12)
    aesgcm     = AESGCM(dek_plaintext)
    ciphertext = aesgcm.encrypt(nonce, plaintext, associated_data=None)

    # Step 3: Zero out the plaintext DEK from memory (best-effort in Python)
    del dek_plaintext

    return EncryptedRecord(
        ciphertext    = ciphertext,
        encrypted_dek = dek_encrypted,
        nonce         = nonce,
    )


def decrypt(record: EncryptedRecord) -> bytes:
    # Step 1: Ask KMS to decrypt the envelope (encrypted DEK → plaintext DEK)
    # KMS enforces IAM policy: only authorized principals can call Decrypt
    response = kms.decrypt(
        CiphertextBlob = record.encrypted_dek,
        KeyId          = KEY_ID,   # optional but recommended for audit clarity
    )
    dek_plaintext = response["Plaintext"]

    # Step 2: Decrypt the data with the recovered DEK
    aesgcm    = AESGCM(dek_plaintext)
    plaintext = aesgcm.decrypt(record.nonce, record.ciphertext, associated_data=None)

    del dek_plaintext
    return plaintext


# Storing the record in a database:
# store: base64(ciphertext) + base64(encrypted_dek) + base64(nonce)
# The encrypted_dek is typically 184 bytes (KMS wraps in its own envelope).
# Together with 12-byte nonce, overhead is ~200 bytes per record — negligible.
```

## Section 3: AWS KMS

**Q6. What is AWS KMS, and what are its core components — keys, key policies, grants, and aliases?**
A: AWS Key Management Service (KMS) is a managed HSM-backed key management service. The master keys (Customer Master Keys / KMS Keys) never leave AWS hardware in plaintext — all cryptographic operations happen inside the service. Your code sends plaintext to KMS and receives ciphertext back (or vice versa); the key material itself is never transmitted.

```
Core components:

KMS Key (formerly Customer Master Key / CMK):
  The master key stored in AWS hardware. Two types:

  Symmetric KMS Key (AES-256-GCM):
    - One key used for both encrypt and decrypt.
    - Most common. Used for S3 SSE-KMS, RDS encryption, EBS encryption, envelope encryption.
    - Key material never leaves AWS.

  Asymmetric KMS Key (RSA, ECC, SM2):
    - Public key / private key pair.
    - Public key is downloadable; private key never leaves KMS.
    - Used for: digital signatures (RSA/ECDSA), asymmetric encryption (RSA-OAEP).
    - Use case: clients encrypt with the public key; only KMS can decrypt.

Key origin options:
  AWS_KMS: KMS generates key material (default, most secure).
  EXTERNAL: you import your own key material into KMS (you manage the key material's origin).
  AWS_CLOUDHSM: key material generated in your dedicated CloudHSM cluster.

Key Policy:
  A resource-based IAM policy attached directly to the KMS key.
  UNLIKE most AWS resources, a KMS key is NOT accessible to the account's root
  by default — the key policy must explicitly grant access.
  The key policy is the primary access control mechanism.

  Every KMS key must have a key policy that grants access to the account root,
  otherwise the key becomes permanently inaccessible (even to AWS support).

Grants:
  Temporary, scoped permissions delegated to a principal without modifying the key policy.
  Used for: AWS services (EC2, ECS, Lambda) that need temporary key access.
  Grants are more granular than key policies and can be revoked programmatically.
  Grant tokens allow using a grant immediately (before IAM eventual consistency).

Aliases:
  Human-readable names for KMS keys: alias/my-app-key.
  An alias points to one key at a time — updating the alias pointer is one
  way to implement key rotation without changing application configuration.
  Applications reference alias/my-app-key; rotation updates which key the alias points to.

Key states:
  Enabled:    can perform cryptographic operations.
  Disabled:   cannot encrypt new data; existing encrypted data cannot be decrypted. ← DANGEROUS
  Pending deletion (7–30 days): scheduled for deletion; cannot be used.
  Deleted:    permanently gone; all data encrypted with this key is permanently inaccessible.
```

**Q7. How do you set up correct IAM and key policy permissions for KMS — least-privilege patterns?**
A:

```json
// Key Policy — the resource-based policy on the KMS key itself

{
  "Version": "2012-10-17",
  "Statement": [
    {
      // Statement 1: account root — required to prevent lockout
      // Without this, the key is permanently inaccessible
      "Sid": "EnableAccountRootAccess",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::123456789012:root" },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      // Statement 2: key administrators — can manage the key, NOT use it for crypto
      "Sid": "AllowKeyAdministration",
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::123456789012:role/SecurityAdmin",
          "arn:aws:iam::123456789012:role/KeyAdmin"
        ]
      },
      "Action": [
        "kms:Create*", "kms:Describe*", "kms:Enable*", "kms:List*",
        "kms:Put*", "kms:Update*", "kms:Revoke*", "kms:Disable*",
        "kms:Get*", "kms:Delete*", "kms:TagResource", "kms:UntagResource",
        "kms:ScheduleKeyDeletion", "kms:CancelKeyDeletion"
      ],
      "Resource": "*"
    },
    {
      // Statement 3: encryption service — can only encrypt (generate DEKs), not decrypt
      "Sid": "AllowEncryptionService",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/EncryptionServiceRole"
      },
      "Action": [
        "kms:GenerateDataKey",   // generate DEK (encrypt new data)
        "kms:DescribeKey"        // describe key metadata
      ],
      "Resource": "*"
      // NOT kms:Decrypt — this service can encrypt but NOT decrypt
    },
    {
      // Statement 4: decryption service — can only decrypt, not generate new DEKs
      "Sid": "AllowDecryptionService",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/DecryptionServiceRole"
      },
      "Action": [
        "kms:Decrypt",          // decrypt existing encrypted DEKs
        "kms:DescribeKey"
      ],
      "Resource": "*",
      "Condition": {
        // Encryption context must match — prevents DEK from being decrypted
        // in a different context (defense-in-depth — see Q8)
        "StringEquals": {
          "kms:EncryptionContext:service": "loans-api",
          "kms:EncryptionContext:environment": "production"
        }
      }
    }
  ]
}
```

```python
# IAM role policy for a Lambda function that encrypts but does not decrypt

encryption_lambda_policy = {
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "kms:GenerateDataKey",
                "kms:DescribeKey",
            ],
            "Resource": "arn:aws:kms:us-east-1:123456789012:key/mrk-abc123...",
            "Condition": {
                "StringEquals": {
                    "kms:ViaService": "s3.us-east-1.amazonaws.com"
                    # Only allow this permission when called via S3 — not direct API
                }
            }
        }
    ]
}

# The least-privilege principle applied to KMS:
# - Separate roles for "can encrypt" vs "can decrypt"
# - Separate roles for "can manage keys" vs "can use keys"
# - kms:GenerateDataKey ≠ kms:Decrypt — a service that writes encrypted data
#   does not need to be able to read it back (write-only services)
# - Use kms:ViaService condition to restrict which AWS service can use the key
# - Use kms:EncryptionContext to bind decryption to the specific data context
```

**Q8. What is KMS Encryption Context, and how does it provide authenticated encryption?**
A: Encryption context is a set of non-secret key-value pairs you provide when encrypting data with KMS. KMS includes them in the encrypted ciphertext metadata and requires the identical context to be provided at decryption time. If the context doesn't match, decryption fails.

```python
# Encryption context binds the ciphertext to its intended purpose and location.
# It is NOT a secret — it appears in CloudTrail logs.
# It provides authentication: the ciphertext can only be decrypted in the right context.

# Encrypting with context:
response = kms.generate_data_key(
    KeyId  = KEY_ID,
    KeySpec = "AES_256",
    EncryptionContext = {
        "service":     "loans-api",      # which service encrypted this
        "environment": "production",     # which environment
        "user_id":     "user_Kp9mXnL2", # OPTIONAL: bind to specific user's data
        "table":       "loan_documents", # which DB table/S3 bucket
    }
)

# Decrypting — must provide IDENTICAL context:
response = kms.decrypt(
    CiphertextBlob = encrypted_dek,
    EncryptionContext = {
        "service":     "loans-api",
        "environment": "production",
        "user_id":     "user_Kp9mXnL2",
        "table":       "loan_documents",
    }
)
# If any context key/value differs → KMS returns InvalidCiphertextException
# Even if the key policy allows the caller to decrypt → context mismatch blocks it

# What encryption context prevents:

# Attack: confused deputy
# Attacker gains access to the decryption API for tax_documents.
# They attempt to decrypt a loan_document ciphertext through it.
# WITHOUT context: KMS decrypts successfully → data from the wrong service leaks.
# WITH context:    KMS checks context["table"] == "loan_documents"
#                  The caller presented context["table"] == "tax_documents"
#                  → InvalidCiphertextException → attack blocked.

# Attack: cross-environment decryption
# Staging service tries to decrypt production ciphertext.
# WITH context["environment"] == "production":
#   Staging service presents context["environment"] == "staging"
#   → KMS rejects → production data never readable from staging.

# CloudTrail logging: context appears in KMS API call logs:
# {
#   "eventName": "Decrypt",
#   "requestParameters": {
#     "encryptionContext": {"service": "loans-api", "environment": "production"}
#   }
# }
# → Full audit trail of what context was used for each decrypt operation.
```

**Q9. How does AWS KMS automatic key rotation work, and what are its limitations?**
A:

```python
# Enabling automatic key rotation:

import boto3
kms = boto3.client("kms")

# Enable annual automatic rotation for a symmetric KMS key
kms.enable_key_rotation(KeyId="alias/my-app-key")

# Check rotation status
status = kms.get_key_rotation_status(KeyId="alias/my-app-key")
print(status["KeyRotationEnabled"])   # True

# Configure rotation period (AWS KMS supports 90–2560 days as of 2023)
kms.enable_key_rotation(
    KeyId=KEY_ID,
    RotationPeriodInDays=365,   # annual
)
```

```
How KMS automatic rotation works:

  When rotation occurs:
    1. KMS generates new key material within the HSM.
    2. The new material is given a new key version (backing key).
    3. The KMS Key ID and ARN remain unchanged.
    4. All new encrypt operations use the new key material.
    5. All old key material versions are retained indefinitely.
    6. Decrypt operations automatically use the correct version based on metadata
       embedded in the ciphertext — no application change needed.

  What changes:      The key material (the actual cryptographic bytes).
  What stays same:   The Key ID, ARN, alias, key policy, and grants.
  Application impact: Zero — applications use the same Key ID before and after rotation.

Limitations of KMS automatic rotation:

  1. Symmetric keys only:
     Asymmetric keys (RSA, ECC) do NOT support automatic rotation.
     Asymmetric rotation requires creating a new key, updating references, and
     re-signing data. Must be done manually.

  2. Annual minimum (recently configurable to 90 days):
     If your compliance requirement is 90-day rotation, you need to configure it
     explicitly (not the default).

  3. Old key material is never deleted:
     KMS retains all historical key material to decrypt old ciphertext.
     "Rotation" limits new encryptions to the new material, but old material
     remains available for decryption indefinitely.
     This is correct behavior — but means rotation alone doesn't limit the
     blast radius of an old key material compromise for old ciphertext.

  4. Imported key material (EXTERNAL origin) cannot be auto-rotated:
     If you imported your own key material, you must manually rotate it
     by re-importing new material and explicitly changing the key version.

  5. Multi-Region Keys require explicit coordination:
     Rotating a primary key in us-east-1 does not automatically rotate replicas.
     Each replica must be rotated separately.

Manual rotation (alias-swap pattern — for asymmetric keys or full replacement):

  Step 1: Create a new KMS key (key_v2).
  Step 2: Update the alias: alias/my-app-key → key_v2.
  Step 3: All new operations via the alias use key_v2.
  Step 4: Re-encrypt all DEKs wrapped with key_v1 (envelope re-wrapping).
  Step 5: Schedule key_v1 for deletion (7–30 day window to detect mistakes).
```

## Section 4: HashiCorp Vault

**Q10. What is HashiCorp Vault, and how does it differ from AWS KMS in purpose and architecture?**
A: HashiCorp Vault is a secrets management platform — it stores, generates, and controls access to secrets, dynamic credentials, and encryption services. AWS KMS is a cryptographic key management service optimized for envelope encryption within the AWS ecosystem. They solve overlapping but distinct problems:

```
AWS KMS:
  Core purpose: manage cryptographic keys for AWS-native encryption.
  Primary use: encrypt S3 objects, RDS data, EBS volumes; generate DEKs for
               envelope encryption; sign with asymmetric keys.
  Key abstraction: the key material NEVER leaves AWS hardware.
  Secret storage: NOT a secrets manager — does not store API keys, passwords, etc.
  Ecosystem: tightly integrated with AWS IAM, S3, RDS, EBS, Lambda.
  Deployment: fully managed; no infrastructure to run.

HashiCorp Vault:
  Core purpose: unified secrets management across any environment (AWS, GCP, Azure,
                on-premises, Kubernetes, bare metal).
  Primary uses:
    - Store and retrieve secrets (API keys, passwords, TLS certs).
    - Generate dynamic credentials (database passwords valid for N hours).
    - Provide encryption-as-a-service (Transit secrets engine — like KMS but cloud-agnostic).
    - Issue and renew PKI certificates.
    - Manage SSH key signing.
  Key abstraction: secrets retrieved by authenticated clients (value leaves Vault).
  Ecosystem: any language, any cloud, any infrastructure.
  Deployment: self-hosted cluster (or HCP Vault — managed cloud offering).

When to use which:

  Use AWS KMS when:
    - All workloads are on AWS.
    - Primary need is encrypting AWS-native resources (S3, RDS, EBS).
    - Envelope encryption for application data.
    - Integration with AWS IAM is sufficient for access control.

  Use Vault when:
    - Multi-cloud or on-premises deployments.
    - Need dynamic secret generation (rotate DB creds every hour).
    - Need PKI / certificate management.
    - Need fine-grained audit logging across all secret access.
    - Teams need self-service secret management with approval workflows.
    - Cannot use AWS IAM as the identity authority.

  Use both:
    - Vault running on AWS, using AWS KMS as its seal (auto-unseal mechanism).
    - Vault storing secrets; KMS protecting data encryption keys.
    - Common production pattern: Vault for application secrets; KMS for data encryption.
```

```
The Seal:
  Vault encrypts ALL data before writing to storage.
  The encryption key (the "root key" or "master key") is protected by the seal.
  On startup, Vault is SEALED — it cannot decrypt its storage and cannot serve secrets.
  Unsealing provides the seal key, allowing Vault to decrypt the root key.

  Shamir Secret Sharing (traditional unseal):
    The root key is split into N shares (e.g., 5 shares, 3 needed = threshold).
    At startup: 3 of 5 key holders must provide their share (Shamir reconstruction).
    Reconstructed root key decrypts Vault's storage.
    Problem: manual, requires multiple humans to be available simultaneously.

  Auto-unseal (production standard):
    Vault delegates seal key protection to an external KMS (AWS KMS, GCP Cloud KMS,
    Azure Key Vault, HSM).
    On startup: Vault calls KMS.Decrypt(encrypted_root_key) → gets root key → unseals.
    No human intervention needed. Works for pod restarts, rolling upgrades, failovers.

    # Vault config for AWS KMS auto-unseal:
    seal "awskms" {
      region     = "us-east-1"
      kms_key_id = "alias/vault-unseal-key"
    }
```

**Q12. How do the Vault KV secrets engine and dynamic secrets work, and when should you use each?**
A:

```
KV Secrets Engine (v2) — static secrets storage:
  Stores arbitrary key-value pairs. Versions are retained (v2 is versioned).
  Use for: API keys, OAuth client secrets, webhook secrets, TLS certificates,
           any secret that doesn't have a native dynamic issuer.

  Path structure: secret/data/{path} (KV v2 inserts "data" in the path)
  Versions: up to N versions retained (configurable max_versions).
  Soft delete: deleted versions are tombstoned, not immediately destroyed.
  Destroy: permanently removes a version's data.
```

```
Dynamic Secrets — credentials generated on demand, valid for a lease duration:
  Instead of storing a static credential, Vault generates a fresh one on each request.
  The credential exists only for the lease duration (e.g., 1 hour).
  When the lease expires, Vault revokes the credential automatically.

  Use for: database credentials, AWS IAM temporary credentials, PKI certificates,
           SSH keys — any credential that can be generated and revoked programmatically.

  Advantages over static secrets:
    - Every service gets a unique credential — no shared passwords between services.
    - Credentials expire automatically — no manual rotation needed.
    - If a service is compromised: revoke its lease, the credential immediately expires.
    - Audit log shows exactly which service requested which credential and when.
    - No credential in Vault to steal — Vault generates a new one on each fetch.
```

**Q14. What is the Vault Transit secrets engine, and how does it work as encryption-as-a-service?**
A: The Transit engine provides cryptographic operations (encrypt, decrypt, sign, verify, HMAC, random) without the application ever managing key material. The key lives in Vault; applications send plaintext and receive ciphertext. This is conceptually similar to AWS KMS but cloud-agnostic.

```python
# Transit secrets engine — Vault as KMS

# Setup (admin, done once):
# vault secrets enable transit
# vault write transit/keys/loans-key type=aes256-gcm96
# vault write transit/keys/signing-key type=ed25519

# Encrypting data (application):
def encrypt_sensitive_field(plaintext: str, client: hvac.Client) -> str:
    import base64
    # Vault requires base64-encoded plaintext
    encoded = base64.b64encode(plaintext.encode()).decode()

    response = client.secrets.transit.encrypt_data(
        name="loans-key",
        plaintext=encoded,
        context=base64.b64encode(b"loans-ssn-field").decode(),
        # context = "associated data" for authenticated encryption (like KMS context)
    )
    return response["data"]["ciphertext"]
    # Returns: "vault:v1:8SDd3WHDOjf..." — versioned ciphertext (v1 = key version 1)

def decrypt_sensitive_field(ciphertext: str, client: hvac.Client) -> str:
    import base64

    response = client.secrets.transit.decrypt_data(
        name="loans-key",
        ciphertext=ciphertext,
        context=base64.b64encode(b"loans-ssn-field").decode(),
    )
    return base64.b64decode(response["data"]["plaintext"]).decode()

# Key rotation in Transit — one API call:
def rotate_transit_key(client: hvac.Client, key_name: str) -> None:
    client.secrets.transit.rotate_key(name=key_name)
    # New key version is created. New encryptions use the latest version.
    # Old ciphertexts (vault:v1:...) can still be decrypted (old version retained).
    # To re-wrap old ciphertexts to the new version:

def rewrap_ciphertext(old_ciphertext: str, client: hvac.Client) -> str:
    """Re-encrypts existing ciphertext under the latest key version."""
    response = client.secrets.transit.rewrap_data(
        name="loans-key",
        ciphertext=old_ciphertext,
    )
    return response["data"]["ciphertext"]   # vault:v2:... — now using key version 2
    # The plaintext was NEVER exposed — Vault decrypted and re-encrypted internally.

# Minimum decryptable version — force retirement of old key versions:
def enforce_key_version_minimum(client: hvac.Client, min_version: int) -> None:
    client.secrets.transit.update_key_configuration(
        name="loans-key",
        min_decryption_version=min_version,   # v1 ciphertexts can no longer be decrypted
        min_encryption_version=min_version,   # only v2+ can be used for new encryptions
    )
    # After setting min_decryption_version=2:
    # vault:v1:... ciphertexts → decryption fails (version retired)
    # vault:v2:... ciphertexts → decryption succeeds
```

**Q15. How do you design a secret injection pattern for containerized applications — the full lifecycle from Vault to a running container?**

```
Pattern 1 — Vault Agent Sidecar (Kubernetes):
```

```python
# Pattern 2 — Direct Vault SDK (simpler for non-Kubernetes, less robust):

import hvac, os, time, threading

class VaultSecretManager:
    """
    Fetches secrets from Vault at startup, caches them, and renews leases.
    For dynamic credentials (DB), re-fetches before expiry.
    """

    def __init__(self, vault_url: str, role: str, ksa_token_path: str):
        self.client = self._login(vault_url, role, ksa_token_path)
        self._secrets: dict = {}
        self._lock = threading.Lock()

    def _login(self, vault_url, role, ksa_token_path) -> hvac.Client:
        with open(ksa_token_path) as f:
            ksa_token = f.read()
        client = hvac.Client(url=vault_url)
        client.auth.kubernetes.login(role=role, jwt=ksa_token)
        return client

    def get_static_secret(self, path: str, key: str) -> str:
        """Fetch a static KV secret (cached for the process lifetime)."""
        with self._lock:
            if path not in self._secrets:
                resp = self.client.secrets.kv.v2.read_secret_version(path=path)
                self._secrets[path] = resp["data"]["data"]
            return self._secrets[path][key]

    def get_db_credentials(self, role: str) -> tuple[str, str, float]:
        """
        Fetch dynamic DB credentials. Returns (username, password, expiry_ts).
        Caller should call this before expiry_ts to refresh.
        """
        resp = self.client.secrets.database.generate_credentials(name=role)
        username  = resp["data"]["username"]
        password  = resp["data"]["password"]
        lease_dur = resp["lease_duration"]   # seconds until expiry
        expiry_ts = time.time() + lease_dur - 60   # 60s buffer before actual expiry
        return username, password, expiry_ts
```

**Q16. What does a complete secret rotation runbook look like — zero-downtime rotation of a database password managed by Vault?**
A:

```
Scenario: rotating the PostgreSQL master password for the loans database.
          50 application pods consuming dynamic credentials via Vault Database engine.

The key insight: with Vault dynamic secrets, you are NOT rotating a shared password.
Each pod has its OWN credential with its OWN expiry. "Rotation" means:
  1. The Vault admin password used by Vault to manage DB users is rotated.
  2. All existing dynamic credentials (already-issued per-pod creds) continue
     to work until their TTL expires.
  3. New credential requests after rotation use the new admin password to create DB users.

Step 1: Rotate Vault's own connection credential for the database.
  # Vault stores the admin DB password it uses to CREATE dynamic users.
  # This is the password that must be rotated.

  vault write -force database/rotate-root/loans-db
  # Vault generates a new password for the vault_admin DB user.
  # Old password: immediately invalid.
  # All existing dynamic credentials (per-pod) are unaffected — they are
  # separate DB users (v-AppRole-abc123), not the vault_admin user.

  Verification:
    vault read database/config/loans-db   # confirm last_rotation_time updated
    vault write database/creds/loans-api-role  # generate a test credential
    psql -h db.myorg.com -U <test_user> -W   # connect with test credential → should work

Step 2: Force-revoke all existing dynamic credentials (optional, for incident response).
  # Only necessary if you suspect existing credentials are compromised.
  # Under normal rotation: let existing credentials expire naturally.

  vault lease revoke -prefix database/creds/loans-api-role
  # All existing per-pod DB credentials are immediately revoked.
  # Vault calls DROP ROLE on the database for each revoked credential.
  # Pods will get authentication errors → will re-request credentials from Vault.
  # This causes a brief disruption (~seconds) while pods re-authenticate.

  # In practice: pods with Vault Agent handle this automatically — Agent detects
  # the lease revocation, re-requests, and restarts the DB connection pool.

Step 3: Rotate the KV secret if a static fallback password also exists.
  # Generate a new password:
  NEW_PASSWORD=$(vault write -field=password sys/policies/password/db-policy generate)

  # Update in Vault KV and in the database simultaneously:
  vault kv put secret/databases/loans-master password="$NEW_PASSWORD"
  psql -h db.myorg.com -U admin -c \
    "ALTER USER app_user WITH PASSWORD '$NEW_PASSWORD';"

  # Dual-write window: keep old password valid for N minutes while services update.
  # After all services have picked up the new secret: revoke old password.

Step 4: Audit log verification.
  # Vault audit log should show:
  #   - database/rotate-root/loans-db write event (step 1)
  #   - database/creds/loans-api-role reads (pods re-fetching after revocation)
  #   - No unexpected principals reading the secrets

  vault audit list   # confirm audit device is enabled and logging

Step 5: Update runbook and rotation timestamp in the key registry.
  # Every key/secret should have a registry entry:
  {
    "secret_id":       "loans-db-master-password",
    "last_rotated":    "2024-07-15T09:00:00Z",

    "rotated_by":      "sre-alice",
    "rotation_method": "vault-rotate-root",
```

## Quick Reference: Key Lifecycle Stages

| Stage | Questions to Answer | Tools |
|---|---|---|
| Generation | CSPRNG or HSM? Entropy source? Who can generate? | AWS KMS, CloudHSM, Vault |
| Storage | Plaintext ever outside hardware boundary? Who has read access? | KMS (never leaves), Vault (retrieved by app), HSM |
| Distribution | How does the service receive the key/secret? Is it logged? | Vault Agent, Secrets Manager SDK, env var injection |
| Usage | Which operations? Which principals? Are calls audited? | KMS key policy, Vault policy, CloudTrail, Vault audit log |
| Rotation | Frequency? Re-encryption needed? Zero-downtime plan? | KMS auto-rotation, Vault rotate-root, Vault rewrap |
| Revocation | Immediate or TTL-based? What happens to encrypted data? | KMS disable (careful!), Vault lease revoke, CRL |
| Destruction | NIST SP 800-88 compliant? What ciphertext is now unreadable? | KMS schedule deletion, Vault key destroy |

## Quick Reference: AWS KMS vs HashiCorp Vault

| Dimension | AWS KMS | HashiCorp Vault |
|---|---|---|
| Primary purpose | Cryptographic key management | Secrets management + encryption-as-a-service |
| Key material exposure | Never leaves AWS hardware | Transit engine: stays in Vault; KV: value retrieved by app |
| Secret storage | Not a secrets manager | KV engine: yes |
| Dynamic credentials | No | Yes (database, AWS, PKI, SSH engines) |
| Cloud portability | AWS only | Any cloud or on-premises |
| Auth mechanisms | AWS IAM | AppRole, Kubernetes, OIDC, AWS IAM, TLS, GitHub, and more |
| Audit logging | CloudTrail | Vault audit log (every request, before response) |
| Rotation | Automatic annual (symmetric) | `rotate-root`, Transit `rotate`, KV versioning |
| Encryption context | Yes (authenticated binding) | Transit context (associated data) |
| HSM backing | FIPS 140-2 Level 3 | Depends on deployment; CloudHSM or external HSM available |
| Managed offering | Fully managed | Self-hosted or HCP Vault (managed) |
| Pricing | Per API call + key storage | Infrastructure cost (self-hosted) or HCP pricing |

## Quick Reference: Rotation Types and Mechanics

| Secret Type | Rotation Mechanism | Re-encryption Needed? | Downtime Risk |
|---|---|---|---|
| KMS symmetric key (AWS auto-rotate) | New backing key generated; old versions retained | No — old ciphertext auto-decrypted with old version | None |
| KMS asymmetric key (manual) | New key created; alias updated | Yes — re-sign all signed artifacts | Low with alias swap |
| Vault Transit key | `vault write transit/keys/NAME/rotate` | No — old versions retained; rewrap to upgrade | None |
| Vault Transit (force min version) | Set `min_decryption_version` | Yes — rewrap before setting minimum | None if rewrapped first |
| Database password (Vault dynamic) | `vault write -force database/rotate-root/NAME` | No — new dynamic creds use new admin creds | None (existing creds unaffected) |
| Static API key (KV) | Generate new value; dual-write window; revoke old | No | Low with dual-write window |
| TLS certificate | Reissue with new key pair; update load balancer | No | Low with rolling deploy |
| JWT signing key (asymmetric) | New key pair; publish new JWKS; retire old kid | No — old tokens expire naturally | None with JWKS |

**Tip for the interview:** At 5 YOE, the key management question is almost never "what is encryption?" — it's a design question: "how would you manage secrets for a new microservice?" or "walk me through rotating a database password with zero downtime." Know envelope encryption cold (Q5) — it's the answer to "how do you handle key rotation without re-encrypting all your data?" and it comes up in both KMS and Vault conversations. The KMS encryption context question (Q8) is a depth signal — most engineers know KMS exists but don't know about context binding, and it's what separates "knows the API" from "understands the security model." For Vault, know the difference between static KV secrets and dynamic secrets (Q12) — the dynamic credentials pattern (each service gets a unique credential that expires automatically) is the answer to "how do you handle the shared DB password problem." The auth method question for Vault (Q13) almost always goes to Kubernetes in 2024 — know that the pod's service account JWT is the identity, Vault validates it via the Kubernetes TokenReview API, and the application never handles Vault tokens directly when using Vault Agent. The KMS vs Vault comparison (Q10) comes up when the interviewer wants to see if you understand *why* you'd use both — Vault for application secrets and dynamic credentials, KMS for data encryption keys, with Vault using KMS for auto-unseal.
