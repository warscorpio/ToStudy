# Security (Cryptography): Encryption at Rest vs In Transit — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the distinction between encryption at rest and encryption in transit, and why do both matter independently?**
A: The terms describe *where* data is when the encryption protects it:

- **Encryption in transit** — protects data while it is moving across a network between two endpoints. The threat it addresses is a network-level attacker: someone intercepting packets on a wire, a compromised router, a man-in-the-middle on a shared Wi-Fi network, or a malicious ISP. The data is encrypted from the sender's process to the receiver's process; in between, all an observer sees is ciphertext. TLS is the dominant mechanism.

- **Encryption at rest** — protects data while it is stored on a medium: a hard disk, SSD, a cloud object store, a database volume, a backup tape. The threat it addresses is a storage-level attacker: someone who physically acquires a decommissioned disk, a cloud provider employee with storage access, a breach that exfiltrates database files or backup archives, or an attacker who gains filesystem access without gaining application access.

The two are **independent and complementary** — neither is a substitute for the other:
- A database protected by TLS during queries (in-transit) but with plaintext disk storage (no at-rest encryption) is exposed if an attacker steals the storage volume.
- A database with full-disk encryption (at-rest) but queries sent over plain HTTP (no in-transit encryption) is exposed to network interception of every query and result set.
- Both must be in place. A breach at the network layer defeats in-transit-only protection; a breach at the storage layer defeats in-transit-only protection. They cover different attack surfaces.

**Q2. What is the threat model each type of encryption addresses — and what threats does neither address?**
A: Precise threat model thinking is what separates a 5 YOE answer from a junior one:

**In-transit encryption threats addressed:**
- Network eavesdropping (passive interception of packets).
- Man-in-the-middle attacks (active interception and relay).
- DNS hijacking (redirecting traffic to a malicious server — certificate validation catches this).
- Protocol downgrade attacks (forcing negotiation to a weaker cipher — mitigated by TLS version pinning and HSTS).

**At-rest encryption threats addressed:**
- Physical theft of storage media (decommissioned disks, stolen laptops, datacenter intrusion).
- Cloud provider internal access to customer storage volumes.
- Backup exfiltration (stolen backup tapes or S3 snapshot access).
- Filesystem-level access without application credentials (e.g., an attacker who gains OS access but not DB credentials).

**Threats neither addresses (important to know):**
- **Compromised application** — if the application itself is breached, it decrypts data as part of normal operation. Both in-transit and at-rest encryption are transparent to the running application. An attacker with code execution in your Node.js process can read decrypted data from memory.
- **Compromised key management** — if the encryption keys are stolen, all encrypted data is exposed regardless of the algorithm. Key management is the hard part of cryptography.
- **Insider threats with legitimate access** — a DBA with credentials can read plaintext data through the application layer even if the disk is encrypted.
- **Logical access vulnerabilities** — SQL injection, mass assignment, broken access control. These bypass encryption entirely by exploiting the application layer that legitimately decrypts data.
- **Metadata and traffic analysis** — encryption hides content but not always the size, timing, or frequency of communications. A passive observer can learn a lot from traffic patterns even without decrypting payloads.

**Q3. What is symmetric vs. asymmetric encryption, and which is used for bulk data encryption and why?**
A: The two paradigms:

**Symmetric encryption** — the same key encrypts and decrypts. Fast. Suitable for bulk data. AES-256 can encrypt gigabytes per second on modern hardware. The problem: key distribution. How do you securely share the key with the other party without the key itself being intercepted?

**Asymmetric encryption** — a mathematically linked key pair: a public key (shareable with anyone) and a private key (secret). Data encrypted with the public key can only be decrypted with the private key; data signed with the private key can be verified with the public key. Solves the key distribution problem. The problem: orders of magnitude slower than symmetric — RSA-2048 can encrypt only a few kilobytes per second.

**Why bulk data uses symmetric (AES), not asymmetric (RSA):** encrypting a 100 GB database backup with RSA-2048 would take hours. Encrypting it with AES-256-GCM takes seconds.

**Hybrid encryption** — the practical solution used everywhere (TLS, PGP, AWS KMS envelope encryption):
1. Generate a random symmetric key (data encryption key, DEK).
2. Encrypt the bulk data with the DEK using AES-256-GCM.
3. Encrypt the DEK with the recipient's public key (RSA or ECDH).
4. Transmit/store the encrypted data + the encrypted DEK.
5. Recipient decrypts the DEK with their private key, then decrypts the data with the DEK.

This combines asymmetric's key distribution benefit with symmetric's speed. TLS does this in the handshake (agree on a session key using asymmetric cryptography, then use symmetric AES for the actual data stream). AWS KMS envelope encryption does this for at-rest data (KMS key encrypts the DEK; DEK encrypts the data).

## Section 2: Encryption in Transit

**Q4. How does TLS work, and what does it actually protect?**
A: TLS (Transport Layer Security) is the protocol that encrypts data in transit. It operates between the TCP layer and the application layer (HTTP, SMTP, database protocols, etc.). The handshake establishes a shared session key; subsequent data is encrypted with that key.

**Simplified TLS 1.3 handshake:**
```
Client                                    Server
  │                                          │
  │── ClientHello ──────────────────────────>│
  │   (supported cipher suites, random,      │
  │    key share for ECDHE)                  │
  │                                          │
  │<── ServerHello ──────────────────────────│
  │    (chosen cipher suite, key share,      │
  │     server certificate)                  │
  │                                          │
  │   [Client verifies certificate:          │
  │    - Signed by a trusted CA?             │
  │    - Hostname matches?                   │
  │    - Not expired or revoked?]            │
  │                                          │
  │   [Both sides compute the same          │
  │    session key from ECDHE key shares]    │
  │                                          │
  │── Finished (encrypted) ────────────────>│
  │<── Finished (encrypted) ────────────────│
  │                                          │
  │ ══ All subsequent data encrypted ══════ │
  │    with symmetric AES-256-GCM session key│
```

**What TLS actually protects:**
- **Confidentiality** — the payload (HTTP request/response body, headers, query parameters) is encrypted. A network observer sees ciphertext.
- **Integrity** — AEAD ciphers (AES-GCM, ChaCha20-Poly1305) include an authentication tag. Any tampering with the ciphertext in transit is detected and the connection is rejected.
- **Authentication** — the server certificate, signed by a trusted CA, proves the server is who it claims to be. This prevents MITM: an attacker between client and server can't impersonate the server without the private key matching the certificate.

**What TLS does NOT protect:**
- Data at the endpoints — once decrypted at the server, the data is plaintext in the server's memory.
- Metadata — the IP addresses and hostname (SNI) are visible to network observers even in TLS 1.3.
- Application-layer vulnerabilities — an SQL injection attack travels over TLS fine; TLS doesn't validate the semantic content of the request.

**Q5. What is TLS certificate validation, and what happens if you disable it?**
A: Certificate validation is the step in the TLS handshake where the client verifies the server's identity. Three checks:

1. **Chain of trust** — the certificate is signed by a CA whose root certificate is in the client's trust store. The signature chain traces back to a trusted root.
2. **Hostname verification** — the domain name in the certificate's `Subject Alternative Name` (SAN) matches the hostname the client is connecting to. Prevents a valid certificate for `evil.com` from being used to impersonate `loans.example.com`.
3. **Validity period** — the certificate has not expired and has not been revoked (checked via OCSP or CRL).

Disabling certificate validation — a common antipattern in development that frequently leaks to production:

```typescript
// DANGEROUS — disables all certificate validation
const response = await fetch('https://api.example.com', {
  // Node.js fetch / undici:
  dispatcher: new Agent({ connect: { rejectUnauthorized: false } }),
});

// Axios equivalent:
const client = axios.create({ httpsAgent: new https.Agent({ rejectUnauthorized: false }) });

// Environment variable that disables validation process-wide:
process.env.NODE_TLS_REJECT_UNAUTHORIZED = '0';  // NEVER in production
```

With `rejectUnauthorized: false`, TLS still encrypts the channel — but you no longer know *who* you're encrypting it to. An attacker can insert a TLS proxy between your service and the upstream, presenting their own certificate. Your service happily encrypts data to the attacker who relays it to the real upstream — a MITM attack that TLS is specifically designed to prevent. You've eliminated TLS's authentication guarantee while keeping a false sense of security from the encryption.

Correct fix for development: install the actual certificate, use a proper CA for internal services (AWS Certificate Manager Private CA, HashiCorp Vault PKI), or add a self-signed CA to your trust store explicitly rather than disabling validation globally.

**Q6. What TLS versions and cipher suites should you enforce, and how do you configure this in Node.js and nginx?**
A: The rule is: disable old versions and weak ciphers, enforce modern ones.

**TLS versions:**
- TLS 1.3 — the current standard. Perfect Forward Secrecy (PFS) is mandatory. Handshake is one round-trip (vs two for TLS 1.2). Obsolete cipher suites have been removed. Use this wherever possible.
- TLS 1.2 — still acceptable with a strong cipher suite. Required for some legacy clients.
- TLS 1.1 and 1.0 — deprecated by RFC 8996 (2021). Vulnerable to POODLE, BEAST, and other attacks. Disable entirely.
- SSL 3.0 and earlier — critically broken (POODLE). Never enable.

**Cipher suites to enforce (TLS 1.2):**
```
ECDHE-ECDSA-AES256-GCM-SHA384
ECDHE-RSA-AES256-GCM-SHA384
ECDHE-ECDSA-CHACHA20-POLY1305
ECDHE-RSA-CHACHA20-POLY1305
ECDHE-ECDSA-AES128-GCM-SHA256
ECDHE-RSA-AES128-GCM-SHA256
```

Key properties: ECDHE (Elliptic Curve Diffie-Hellman Ephemeral) for Perfect Forward Secrecy; GCM or ChaCha20-Poly1305 for authenticated encryption; no RC4, DES, 3DES, CBC without MAC, or export-grade ciphers.

**Node.js configuration:**
```typescript
import https from 'node:https';
import tls from 'node:tls';

const server = https.createServer({
  key:  fs.readFileSync('private-key.pem'),
  cert: fs.readFileSync('certificate.pem'),
  minVersion:   'TLSv1.2',    // reject TLS 1.0 and 1.1
  maxVersion:   'TLSv1.3',
  ciphers: [
    'ECDHE-ECDSA-AES256-GCM-SHA384',
    'ECDHE-RSA-AES256-GCM-SHA384',
    'ECDHE-ECDSA-CHACHA20-POLY1305',
    'ECDHE-RSA-CHACHA20-POLY1305',
    'ECDHE-ECDSA-AES128-GCM-SHA256',
    'ECDHE-RSA-AES128-GCM-SHA256',
  ].join(':'),
  honorCipherOrder: true,     // server picks the cipher, not the client
}, app);
```

**nginx configuration:**
```nginx
ssl_protocols       TLSv1.2 TLSv1.3;
ssl_ciphers         ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256;
ssl_prefer_server_ciphers on;
ssl_session_cache   shared:SSL:10m;
ssl_session_timeout 1d;
ssl_session_tickets off;      # disable session tickets for forward secrecy
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
```

**Q7. What is Perfect Forward Secrecy (PFS), and why is it important for long-term data confidentiality?**
A: Perfect Forward Secrecy means that even if the server's long-term private key is compromised in the future, past session recordings cannot be decrypted retrospectively.

**Without PFS (RSA key exchange):** the client encrypts the session key directly with the server's RSA public key. An adversary who records all encrypted traffic and later obtains the server's private key can decrypt all recorded sessions — past and future.

**With PFS (ECDHE key exchange):** the session key is derived from an ephemeral (temporary, per-session) Diffie-Hellman key exchange. The ephemeral private key is discarded after the session ends. Even if the server's long-term certificate private key is later stolen, it cannot recover the ephemeral session keys — those are gone. Past sessions remain confidential.

In fintech this matters concretely: a nation-state or sophisticated attacker may record encrypted TLS traffic today, expecting to decrypt it later once they obtain the private key (through legal compulsion, theft, or a future cryptographic break). With PFS, that recorded traffic is permanently undecryptable. Without PFS, every session ever recorded becomes vulnerable the moment the private key is compromised. ECDHE cipher suites in TLS 1.2 provide PFS; TLS 1.3 mandates it for all connections.

**Q8. How does mTLS (mutual TLS) differ from standard TLS, and when would you use it in a microservices architecture?**
A: Standard TLS authenticates the *server* to the *client* — the client verifies the server's certificate. The server doesn't verify who the client is (authentication of the client is left to the application layer — cookies, tokens, API keys).

Mutual TLS (mTLS) adds client authentication: the client presents its own certificate during the TLS handshake, and the server verifies it against a trusted CA. Both parties are mutually authenticated at the transport layer before any application data is exchanged.

```
Standard TLS:   Server → presents cert → Client verifies → encrypted channel
mTLS:           Server → presents cert → Client verifies
                Client → presents cert → Server verifies → encrypted channel
                Both sides are cryptographically authenticated
```

**When to use mTLS in microservices:**
- **Service-to-service authentication** — in a zero-trust architecture, every service call requires mutual authentication. Service A calling Service B presents its own certificate; Service B accepts calls only from known service certificates. No shared secrets, no API keys to rotate — the certificate *is* the identity.
- **B2B API integrations** — a lending partner or payment gateway connecting to your API presents a client certificate issued by your internal CA. You accept only requests with a valid certificate from that partner's certificate. This is stronger than API key authentication (a certificate has a shorter lifetime and is cryptographically bound to a private key the partner controls).
- **Database connections** — PostgreSQL, MySQL, and Redis support mTLS for client certificate auth. Configuring this means even if a service's credentials are compromised, the attacker also needs the client certificate private key.

In AWS with a service mesh (AWS App Mesh, Istio): mTLS between pods is typically handled automatically by the service mesh control plane — each pod gets a short-lived certificate (SPIFFE/SVID), and the proxy sidecar handles mutual authentication transparently without the application code doing anything special.

## Section 3: Encryption at Rest

**Q9. What is full-disk encryption (FDE), and what threat does it actually address?**
A: Full-disk encryption encrypts the entire storage volume — every block on disk, including the operating system, swap space, and all data files. The encryption is transparent to the OS and applications once the disk is mounted; reading a block transparently decrypts it and writing a block transparently encrypts it, mediated by a kernel driver.

Common implementations: dm-crypt/LUKS on Linux, BitLocker on Windows, FileVault on macOS, and managed equivalents in cloud providers (AWS EBS encryption, GCP Persistent Disk encryption, Azure Disk Encryption).

**The threat FDE actually addresses:** physical access to the storage device when the system is **powered off**. If an attacker steals a disk from a decommissioned server — or a decommissioned laptop — they cannot read the data without the decryption key, which is not on the disk. The disk contains only ciphertext.

**What FDE does NOT address:**
- A running system — once the disk is mounted and the OS is booted, data is accessible to anyone with OS-level access. FDE does not protect against software breaches, compromised credentials, or OS-level exploits on a running system.
- Cloud storage volumes — AWS EBS encryption uses FDE under the hood, but it protects only against AWS infrastructure compromise (an AWS employee or vendor with physical storage access). It does not protect against an attacker who compromises your EC2 instance and can read the mounted filesystem normally through the OS.

FDE is necessary but not sufficient. It's one layer in the defence stack, specifically targeted at physical media security and decommissioning. It does not replace application-level or field-level encryption for sensitive data like PAN, Aadhaar numbers, or account numbers.

**Q10. What is the difference between full-disk encryption, volume encryption, file-level encryption, and field-level encryption?**
A: Four distinct layers, each with different granularity and different threat coverage:

**Full-disk encryption (FDE)** — encrypts every block on the disk. Granularity: the entire device. The OS and all files are encrypted as one unit. Key is unlocked at boot (TPM, passphrase, or network-based key). Protects against physical theft of powered-off media. Transparent to all applications.

**Volume / filesystem encryption** — encrypts a specific filesystem or volume rather than the raw block device. Examples: eCryptfs (per-directory), ZFS native encryption (per-dataset), AWS EBS encryption (per-volume). More flexible than FDE — different volumes can have different keys and policies. Still transparent to applications.

**File-level encryption** — individual files are encrypted, each potentially with a different key. Examples: PGP-encrypted files, AWS S3 SSE (each object encrypted with a per-object data key). Applications must explicitly decrypt files to use them. Allows fine-grained access control — different keys for different files means access to one file doesn't expose others.

**Field-level encryption (FLE) / column-level encryption** — specific fields within a database record or document are encrypted individually by the application before storage. Examples: encrypting the `pan_number` column in a loans table while leaving `loan_amount` in plaintext. The database stores ciphertext for sensitive fields; the application decrypts them when needed.

```typescript
// Field-level encryption in a NestJS service
async createLoanApplication(dto: CreateLoanApplicationDto): Promise<LoanApplication> {
  return this.repo.save({
    applicantName:   dto.applicantName,        // plaintext — needed for search
    requestedAmount: dto.requestedAmount,       // plaintext — needed for aggregations
    panNumber:       await this.kms.encrypt(dto.panNumber),  // encrypted at field level
    aadhaarNumber:   await this.kms.encrypt(dto.aadhaarNumber),
    bankAccountNumber: await this.kms.encrypt(dto.bankAccountNumber),
    ifscCode:        dto.ifscCode,             // plaintext — needed for NACH processing
  });
}
```

FLE provides the strongest protection — even a full database dump is safe for encrypted fields because the attacker doesn't have the application-layer encryption keys. But it has real trade-offs: you can't query, sort, or aggregate on encrypted fields without decrypting them first (unless using specialised schemes like deterministic encryption or order-preserving encryption, both of which reduce security).

**Q11. What is envelope encryption, how does AWS KMS implement it, and why is it used for at-rest data?**
A: Envelope encryption is the practical pattern for encrypting large amounts of data with a key management service without sending all data through the KMS API.

**The problem without envelope encryption:** KMS API calls have a 4KB payload limit and network latency (~1–5ms per call). Encrypting a 1 GB database backup by calling KMS for every block would be impossibly slow and expensive.

**Envelope encryption pattern:**
```
                        ┌─────────────────────────────────────┐
                        │            AWS KMS                  │
                        │   Customer Master Key (CMK)         │
                        │   (never leaves KMS hardware)       │
                        └─────────────────────────────────────┘
                                         │
                          GenerateDataKey API call
                                         │
                                         ▼
                        ┌─────────────────────────────────────┐
                        │  Data Encryption Key (DEK)          │
                        │  Plaintext DEK ──────► Encrypts data│
                        │  Encrypted DEK ──────► Stored with  │
                        │                         the data    │
                        └─────────────────────────────────────┘
```

```typescript
import { KMSClient, GenerateDataKeyCommand, DecryptCommand } from '@aws-sdk/client-kms';
import crypto from 'node:crypto';

const kms = new KMSClient({ region: 'ap-south-1' });

// Encrypting a sensitive field
async function encryptField(plaintext: string): Promise<string> {
  // Step 1: Ask KMS for a data key — get plaintext + encrypted form
  const { Plaintext: dek, CiphertextBlob: encryptedDek } = await kms.send(
    new GenerateDataKeyCommand({ KeyId: process.env.KMS_KEY_ID, KeySpec: 'AES_256' })
  );

  // Step 2: Encrypt the data locally with the plaintext DEK
  const iv         = crypto.randomBytes(12);   // 96-bit IV for GCM
  const cipher     = crypto.createCipheriv('aes-256-gcm', dek!, iv);
  const ciphertext = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const authTag    = cipher.getAuthTag();

  // Step 3: Discard the plaintext DEK from memory immediately
  dek!.fill(0);  // zero-fill the buffer

  // Step 4: Store: encryptedDek + iv + authTag + ciphertext
  return Buffer.concat([
    Buffer.from([encryptedDek!.length >> 8, encryptedDek!.length & 0xff]),  // 2-byte length prefix
    encryptedDek!,
    iv,
    authTag,
    ciphertext,
  ]).toString('base64');
}

// Decrypting
async function decryptField(stored: string): Promise<string> {
  const buf        = Buffer.from(stored, 'base64');
  const dekLen     = (buf[0] << 8) | buf[1];
  const encDek     = buf.slice(2, 2 + dekLen);
  const iv         = buf.slice(2 + dekLen, 2 + dekLen + 12);
  const authTag    = buf.slice(2 + dekLen + 12, 2 + dekLen + 28);
  const ciphertext = buf.slice(2 + dekLen + 28);

  // Decrypt the DEK using KMS (one API call per field decryption)
  const { Plaintext: dek } = await kms.send(
    new DecryptCommand({ CiphertextBlob: encDek })
  );

  const decipher = crypto.createDecipheriv('aes-256-gcm', dek!, iv);
  decipher.setAuthTag(authTag);
  const plaintext = decipher.update(ciphertext) + decipher.final('utf8');

  dek!.fill(0);  // zero-fill
  return plaintext;
}
```

The CMK (Customer Master Key) never leaves KMS hardware — it exists only in HSMs (Hardware Security Modules) within the KMS service. Your application only ever holds the encrypted DEK (safe to store anywhere — it's ciphertext) and a temporary plaintext DEK (held in memory only during encryption/decryption, immediately zeroed after use).

**Q12. How do you encrypt data at rest in PostgreSQL, and what are the trade-offs between TDE, column-level encryption, and application-level encryption?**
A: Three distinct approaches at different layers:

**Transparent Data Encryption (TDE) at the storage engine level:**
PostgreSQL does not have native TDE (unlike SQL Server or Oracle). The equivalent is OS-level disk encryption (dm-crypt/LUKS) or cloud volume encryption (AWS RDS encrypted volumes with KMS). The database files on disk are ciphertext; the database engine reads plaintext through the OS encryption layer.

Trade-offs: transparent to all SQL queries (no performance penalty on queries, no code changes), but the running database process sees plaintext — a compromised DB instance has full plaintext access. Protects only against storage media theft.

**Column-level encryption (pgcrypto extension):**
```sql
-- PostgreSQL pgcrypto extension
CREATE EXTENSION pgcrypto;

-- Store encrypted values
INSERT INTO loan_applications (applicant_name, pan_number)
VALUES ('Raj Kumar', pgp_sym_encrypt('ABCDE1234F', 'encryption_key_here'));

-- Query encrypted values
SELECT applicant_name,
       pgp_sym_decrypt(pan_number::bytea, 'encryption_key_here') AS pan_number
FROM loan_applications
WHERE id = 'loan_123';
```

Trade-offs: encrypts specific columns while leaving others queryable; encryption key must be passed to PostgreSQL in queries (key travels over the DB connection — use mTLS; key is visible in query logs — disable query logging for these queries or use parameterised queries carefully). Searching or indexing encrypted columns is not possible without decrypting. Key rotation requires re-encrypting every row.

**Application-level encryption (AES-256-GCM via KMS):**
The application encrypts fields before writing to the database, stores ciphertext in `TEXT` or `BYTEA` columns, and decrypts when reading. The database never sees plaintext for encrypted fields.

Trade-offs: strongest isolation (DB compromise doesn't expose plaintext), but no server-side SQL on encrypted fields (no `WHERE pan_number = ?`, no `ORDER BY`, no `SUM()`). Requires application code changes. Key management is the application's responsibility (use KMS). This is the correct approach for PCI-DSS-scoped fields (PAN, CVV) and RBI-mandated sensitive data.

**Q13. How does AWS S3 server-side encryption work, and what are the differences between SSE-S3, SSE-KMS, and SSE-C?**
A: S3 offers three server-side encryption modes, differing in who manages the encryption keys:

**SSE-S3 (S3-Managed Keys):**
```http
PUT /myfile.pdf HTTP/1.1
x-amz-server-side-encryption: AES256
```
S3 generates and manages a per-object data key internally. The master key that encrypts the data keys is AWS-managed and rotated automatically by S3. You have no visibility into or control over the keys. Simplest to enable but weakest key control — AWS manages everything.

**SSE-KMS (KMS-Managed Keys):**
```http
PUT /myfile.pdf HTTP/1.1
x-amz-server-side-encryption: aws:kms
x-amz-server-side-encryption-aws-kms-key-id: arn:aws:kms:ap-south-1:123456789:key/mrk-abc123
```
S3 uses a KMS Customer Master Key (your CMK) to generate per-object data keys. You control the CMK: you can set key policies (who can use the key), enable CloudTrail audit logging for every key usage, rotate the key annually, and revoke access by disabling the key. Every S3 read generates a KMS `Decrypt` API call — logged in CloudTrail. This is the required choice for compliance-sensitive data.

**SSE-C (Customer-Provided Keys):**
```http
PUT /myfile.pdf HTTP/1.1
x-amz-server-side-encryption-customer-algorithm: AES256
x-amz-server-side-encryption-customer-key: <base64-encoded-256-bit-key>
x-amz-server-side-encryption-customer-key-MD5: <md5-of-key>
```
You provide the encryption key with every request. S3 encrypts/decrypts using your key but never stores the key — it's discarded after use. AWS has zero ability to decrypt your data (they never have the key). Maximum control but maximum operational burden — you manage key storage, rotation, and must send the key over HTTPS on every S3 API call (hence HTTPS is mandatory for SSE-C; S3 rejects SSE-C over HTTP).

For fintech: SSE-KMS with a customer-managed CMK is the standard — you get full audit trails of key usage, fine-grained IAM control over who can decrypt, and key revocation capability, without the operational complexity of SSE-C.

## Section 4: Key Management

**Q14. What is a Hardware Security Module (HSM), and when do you need one?**
A: An HSM is a dedicated physical device (or cloud service emulating one) designed to store and operate on cryptographic keys. The defining property: **the key material never leaves the HSM in plaintext form, ever**. All cryptographic operations (sign, encrypt, decrypt) happen inside the tamper-resistant hardware boundary. If someone physically attacks the HSM, it destroys the keys before they can be extracted.

AWS KMS uses HSMs internally — when you use a KMS CMK, you're effectively using a cloud-accessible HSM. AWS CloudHSM is a dedicated HSM instance (FIPS 140-2 Level 3 validated) that you provision in your VPC and exclusively control.

**When do you need dedicated HSMs:**
- **PCI-DSS Level 1 (card data)** — cardholder data encryption and PIN processing require FIPS 140-2 Level 3 HSMs. KMS satisfies this; CloudHSM does too.
- **Digital signing for high-value financial instruments** — certificate signing, code signing, document signing where non-repudiation is legally required.
- **RBI payment system licenses** — the RBI Payment Aggregator and Payment Gateway guidelines explicitly require HSMs for card data processing and key management.
- **eKYC/Aadhaar authentication** — Aadhaar-based OTP and biometric authentication requires UIDAI-approved HSMs for the AUA/KUA (Authentication/KYC User Agency) level encryption.

For most fintech applications: AWS KMS (which uses HSMs internally) is sufficient and far simpler to operate than CloudHSM. CloudHSM makes sense when regulatory requirements mandate exclusive HSM tenancy or FIPS 140-2 Level 3 certification that KMS's shared model doesn't satisfy.

**Q15. What is key rotation, and how do you implement it without decrypting and re-encrypting all existing data?**
A: Key rotation is replacing an encryption key with a new one periodically. The motivation: limit the blast radius if a key is compromised (a compromised key only exposes data encrypted during its validity period, not all historical data), and satisfy compliance requirements (PCI-DSS requires annual cryptoperiod limits for symmetric keys).

**AWS KMS automatic rotation (the correct approach):**
KMS supports automatic annual rotation of CMKs. Crucially, KMS rotation works differently from naive key rotation: when a CMK is rotated, KMS creates a new cryptographic key material but keeps the old key material to decrypt data encrypted under the old key. The `KeyId` (ARN) stays the same — no application changes required. New encryption operations use the new key material; old decryption operations automatically use the correct historical key material.

```bash
# Enable automatic rotation on a KMS key
aws kms enable-key-rotation --key-id arn:aws:kms:ap-south-1:123456789:key/mrk-abc123

# Check rotation status
aws kms get-key-rotation-status --key-id arn:aws:kms:ap-south-1:123456789:key/mrk-abc123
```

**Application-level key rotation (when you manage keys directly):**
The pattern for rotating application-managed encryption keys without a bulk re-encrypt operation:

```typescript
// Each encrypted record stores the key version used to encrypt it
interface EncryptedField {
  keyVersion: string;   // e.g., "v2"
  iv:         string;
  authTag:    string;
  ciphertext: string;
}

// Decryption: look up the correct key by version
async function decrypt(stored: EncryptedField): Promise<string> {
  const key = await this.keyStore.getKeyVersion(stored.keyVersion);
  return aesGcmDecrypt(stored, key);
}

// On write: always use the current (latest) key version
async function encrypt(plaintext: string): Promise<EncryptedField> {
  const { version, key } = await this.keyStore.getCurrentKey();
  return { keyVersion: version, ...aesGcmEncrypt(plaintext, key) };
}

// Background rotation job: re-encrypt records still using old key versions
async function rotateOldRecords(): Promise<void> {
  const oldRecords = await this.repo.findAll({ where: { keyVersion: Not('v3') } });
  for (const record of oldRecords) {
    const plaintext  = await this.decrypt(record.panNumber);
    record.panNumber = await this.encrypt(plaintext);  // now encrypted with v3
    await this.repo.save(record);
  }
}
```

The key version stored alongside each encrypted value allows gradual rotation — new records get the new key immediately; old records are re-encrypted lazily by a background job. No big-bang migration, no downtime.

## Section 5: Practical Implementation Patterns

**Q16. How do you encrypt database connection strings, API credentials, and secrets in a NestJS application?**
A: The hierarchy from worst to best:

**Never:** hardcoded in source code or committed to git.
```typescript
const dbPassword = 'mysecretpassword';  // NEVER
```

**Bad:** plaintext in environment variables on the server (they appear in process listings, crash dumps, and are accessible to any code running in the process).

**Acceptable for non-production:** `.env` file excluded from git (`.gitignore`), loaded via `dotenv`. Better than hardcoded but still plaintext on disk.

**Production standard:** fetch secrets from a secrets manager at startup:

```typescript
// config/secrets.ts — fetch from AWS Secrets Manager
import { SecretsManagerClient, GetSecretValueCommand } from '@aws-sdk/client-secrets-manager';

const smClient = new SecretsManagerClient({ region: 'ap-south-1' });

export async function loadSecrets(): Promise<AppSecrets> {
  const { SecretString } = await smClient.send(
    new GetSecretValueCommand({ SecretId: 'prod/loans-api/secrets' })
  );

  return JSON.parse(SecretString!) as AppSecrets;
}

// main.ts
const secrets = await loadSecrets();
const app = await NestFactory.create(
  AppModule.forRoot({ dbPassword: secrets.dbPassword, ... })
);
```

The secrets manager (AWS Secrets Manager, HashiCorp Vault) stores secrets encrypted at rest (using KMS), controls access via IAM policies, maintains an audit log of every secret access, and supports automatic rotation. The only credential the application needs is an IAM role (for AWS) or a Vault token — and IAM roles require no stored credentials (the EC2/ECS metadata service provides temporary credentials automatically).

**Q17. How do you implement encryption for PAN (card numbers) and Aadhaar numbers in a fintech application, and how does this differ from hashing them?**
A: Both PAN and Aadhaar numbers are sensitive personally identifiable information (PII) regulated by PCI-DSS and UIDAI respectively. The choice between encryption and hashing depends on whether you need to recover the original value:

**When to encrypt (reversible):** when you need to display, process, or transmit the value — e.g., showing the user their linked PAN during KYC review, using the account number for NACH mandate submission to the NPCI, or sending card data to a payment processor.

**When to hash (irreversible):** when you only need to verify or deduplicate — e.g., checking if a PAN is already registered without needing to display it, or de-duplicating loan applications without needing the actual PAN. Use HMAC-SHA256 (not SHA-256 alone, to prevent rainbow table attacks even on structured data like PANs).

```typescript
// PAN handling — store both encrypted (for display) and hashed (for lookup)
async storePan(pan: string, loanId: string): Promise<void> {
  const encryptedPan = await this.kms.encrypt(pan);  // AES-256-GCM via KMS envelope
  const panHash = crypto
    .createHmac('sha256', process.env.PAN_HMAC_SECRET!)
    .update(pan.toUpperCase())   // normalise before hashing
    .digest('hex');

  await this.repo.update(loanId, {
    panEncrypted: encryptedPan,  // for display/processing
    panHash,                     // for duplicate detection — index this column
  });
}

async findByPan(pan: string): Promise<LoanApplication | null> {
  // Look up by hash — never by decrypting all records
  const panHash = crypto
    .createHmac('sha256', process.env.PAN_HMAC_SECRET!)
    .update(pan.toUpperCase())
    .digest('hex');

  return this.repo.findOne({ where: { panHash } });
}
```

**PCI-DSS specific requirements for PAN:**
- PAN stored in a database must be rendered unreadable — acceptable methods include one-way hashes, truncation (storing only last 4 digits), index tokens with a separate token vault, or strong cryptography (AES-256).
- The full 16-digit PAN must never appear in logs, query strings, or error messages.
- Displaying PAN to a user: mask it — show only the last 4 digits (`•••• •••• •••• 1234`).

**Q18. What is tokenisation, and how does it differ from encryption for cardholder data protection?**
A: Tokenisation replaces a sensitive value (like a PAN) with a non-sensitive surrogate value (a token) that has no mathematical relationship to the original. The mapping between token and original value is stored in a separate, highly-secured token vault.

```
Original PAN:   4111 1111 1111 1111
Token:          8271 4729 3827 1928   ← random, no mathematical relationship
                                         Mapping stored in isolated token vault
```

**Encryption vs. tokenisation:**

| Aspect | Encryption | Tokenisation |
|---|---|---|
| Mathematical relationship | Ciphertext is a deterministic transform of plaintext | Token has no mathematical relationship to PAN |
| Reversibility | Reversible with the key | Reversible only by querying the token vault |
| Attack surface | Key compromise exposes all data | Token vault breach exposes all data; no offline attack possible |
| PCI-DSS scope | Encrypted PAN is still in scope | Token is out of PCI-DSS scope if vault is properly isolated |
| Format preservation | Not usually (ciphertext is binary) | Can be format-preserving (same length/format as PAN) |
| Use case | Any sensitive field | Specifically for removing PCI-DSS scope from systems |

The key advantage of tokenisation in fintech: once a PAN is replaced by a token in your application database, your application is no longer processing, storing, or transmitting PANs — it only handles tokens. The PCI-DSS scope shrinks to just the token vault (a heavily controlled, isolated system), not your entire application. Most Indian fintech companies use payment network tokenisation (Visa Token Service, Mastercard Digital Enablement Service) or third-party vault providers (Skyflow, Very Good Security) rather than building their own.

**Q19. How do you handle encryption for data exported to S3 (backups, data pipelines, analytics exports)?**
A:
```typescript
// Uploading encrypted data to S3 — using SSE-KMS
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3';

const s3 = new S3Client({ region: 'ap-south-1' });

async function uploadEncryptedBackup(
  data:       Buffer,
  bucketName: string,
  key:        string,
): Promise<void> {
  await s3.send(new PutObjectCommand({
    Bucket:                        bucketName,
    Key:                           key,
    Body:                          data,
    ServerSideEncryption:          'aws:kms',
    SSEKMSKeyId:                   process.env.BACKUP_KMS_KEY_ARN,

    // Metadata for audit trail
    Metadata: {
      'encrypted-at':  new Date().toISOString(),
      'data-class':    'confidential',
      'key-version':   'v3',
    },
  }));
}
```

For sensitive data in analytics pipelines (Kinesis → S3 → Redshift / Athena), additional considerations:

**Anonymisation before export:** fields like PAN, Aadhaar, phone number should be anonymised or pseudonymised before reaching analytics systems. Use HMAC-based pseudonymisation (consistent but non-reversible token) so you can join on the field without exposing the real value:

```typescript
function pseudonymise(value: string): string {
  return crypto
    .createHmac('sha256', process.env.ANALYTICS_HMAC_SECRET!)
    .update(value)
    .digest('hex')
    .slice(0, 16);  // 16-char pseudonym — consistent per value, not reversible
}
```

**Bucket policies to enforce encryption at upload:**
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyUnencryptedUploads",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::myorg-data-exports/*",
    "Condition": {
      "StringNotEquals": {
        "s3:x-amz-server-side-encryption": "aws:kms"
      }
    }
  }]
}
```
This S3 bucket policy rejects any `PutObject` request that doesn't specify SSE-KMS — even if a developer forgets the encryption header in their code, the upload fails rather than silently storing plaintext.

## Section 6: Compliance and Real-World Scenarios

**Q20. What do PCI-DSS and RBI guidelines specifically require for encryption at rest and in transit?**
A: Both frameworks have concrete, auditable requirements:

**PCI-DSS v4.0 encryption requirements:**

*In transit (Requirement 4):*
- Req 4.2.1 — Strong cryptography is used to safeguard PAN during transmission over open, public networks. TLS 1.2+ is required; TLS 1.0/1.1 must be disabled.
- Req 4.2.2 — An inventory of trusted keys and certificates is maintained. Know every certificate in use, its expiry, and who manages it.
- Req 4.3.1 — Security policies for protecting PAN sent via end-user messaging technologies (email, SMS, chat).

*At rest (Requirement 3):*
- Req 3.5.1 — PAN is secured with strong cryptography (AES-256, TDES-128 minimum) wherever stored.
- Req 3.5.1.1 — Hashes used to render PAN unreadable must use keyed-hash (HMAC) — plain SHA-256 of a PAN is insufficient because PANs have limited range and are susceptible to rainbow tables.
- Req 3.6 — Key management procedures: key generation, distribution, storage, retirement, and destruction. Keys must themselves be protected with at least the same strength as the data they protect.
- Req 3.7 — Key custodians formally acknowledge their key custody responsibilities.

**RBI Master Direction on Digital Payment Security Controls:**
- Payment system operators must use end-to-end encryption for all payment transactions. TLS 1.2+ for all internet-facing APIs.
- Sensitive authentication data (CVV, PIN, OTP) must never be stored post-authorisation — even encrypted.
- Customer financial data (account numbers, Aadhaar linkage details) must be encrypted at rest and in transit.
- Encryption keys must be managed in HSMs — KMS satisfies this for most categories.
- All cryptographic operations must use NIST-approved or equivalent algorithms: AES-256, RSA-2048+, ECDSA P-256+, SHA-256+.

**RBI Data Localisation:** all payment system data must be stored only in India. This has a direct encryption implication — using a KMS key in `ap-south-1` (Mumbai) is compliant; replicating encrypted data to `us-east-1` may not be unless the key material also stays in India.

**Q21. Scenario: "You're designing the encryption architecture for a new NACH (National Automated Clearing House) mandate management system. Walk through your decisions."**
A: NACH mandates contain: bank account number, IFSC code, account holder name, mandate amount, frequency, start/end dates, and a mandate reference ID. The bank account number and account holder name are sensitive; the rest are operational data.

**In-transit encryption:**
- All API calls to NPCI's NACH gateway: TLS 1.2+ with certificate pinning (the NPCI certificate changes rarely; pin to the intermediate CA).
- Internal service-to-service: mTLS between the NACH service and the loans service (each service has a certificate from the internal CA).
- Database connections: TLS to RDS with client certificate (`verify-full` mode in PostgreSQL connection string — reject any certificate the internal CA didn't sign).

**At rest encryption:**
- RDS volume: AWS RDS encrypted with a KMS CMK in `ap-south-1`. Automatic daily snapshots also encrypted with the same CMK.
- Application-level field encryption for `bankAccountNumber` and `accountHolderName`: AES-256-GCM via KMS envelope encryption. Store `bankAccountNumberEncrypted` (ciphertext) and `bankAccountNumberHash` (HMAC-SHA256 for lookup/deduplication) as separate columns.
- NACH mandate XML files archived to S3: SSE-KMS with a separate CMK dedicated to NACH archives (separate key = separate access control and audit trail from the operational DB key).
- Audit logs: append-only table in RDS (no DELETEs, no UPDATEs — enforce via row-level security) shipped to CloudWatch Logs, also encrypted at rest.

**Key management:**
- Two CMKs: one for the NACH operational database (rotated annually, used by the NACH service IAM role only), one for NACH S3 archives (used by the archival Lambda IAM role only). Separate keys = separate blast radius.
- KMS key policies: the NACH ECS task role can `kms:Decrypt` and `kms:GenerateDataKey`; no other role can. Developers cannot decrypt NACH data directly — only the service IAM role can.
- CloudTrail: every KMS API call logged. Alert if `kms:Decrypt` is called by any entity other than the expected IAM role.

**Q22. Scenario: "A developer on your team committed an encryption key to the git repository and pushed it to GitHub 3 days ago. What do you do?"**
A: Treat this as a confirmed key compromise — not a potential one. Any key visible in a git repository (even for seconds) must be considered compromised. GitHub may have scanned it, any collaborator may have cloned it, and git history preserves it permanently even after deletion.

**Immediate response (within the hour):**
1. Rotate the compromised key immediately — generate a new key and update all systems using it. The old key is revoked.
2. Re-encrypt all data that was encrypted under the old key using the new key. This is where the key versioning pattern (Q15) makes rotation tractable — you know which records used the compromised key.
3. Revoke the old key in KMS (disable it) so it can no longer decrypt anything. After confirming all data is re-encrypted, schedule deletion (KMS has a 7–30 day waiting period for key deletion — this is intentional and gives you time to discover missed usage).
4. Audit CloudTrail for any `kms:Decrypt` calls using the old key from unexpected sources during the 3-day exposure window. If any found, assume those decryptions were malicious and treat the exposed data as breached.

**Short-term (within the day):**
5. Remove the key from git history using `git filter-repo`. Force-push to GitHub. This prevents future casual discovery but doesn't help anyone who already cloned the repo.
6. Invalidate all sessions and API tokens that may have been decryptable using the compromised key.
7. Notify your security team and document the incident.

**Prevention going forward:**
8. Add the key pattern to `.gitignore` and pre-commit hooks (`git-secrets`, `detect-secrets`, `truffleHog`).
9. Enable GitHub secret scanning for your organisation — GitHub will automatically alert on future key patterns.
10. Migrate to KMS-based key management so key material never exists as a plaintext string anywhere — you can't accidentally commit a KMS key ID because the key material never leaves KMS.

**Q23. Scenario: "Your application decrypts sensitive data only when needed. A security reviewer flags that you're logging the decrypted values in debug statements. What's the risk and how do you fix it?"**
A: This is **encryption key misuse through logging** — one of the most common ways that correctly-implemented encryption at rest is defeated in practice.

The risk: application logs typically flow to: stdout → log aggregator (Datadog, CloudWatch, ELK) → long-term storage. Logs are often retained for months or years, are accessible to many engineers (much broader access than the encryption key itself), and are rarely encrypted at rest with the same rigour as the primary database. Decrypted PAN, Aadhaar, or bank account numbers in logs effectively bypasses all the at-rest encryption work.

Specific risks:
- Log aggregators are a common breach target — they aggregate logs from many services, making them a high-value target.
- Developers often have read access to logs but not to the encrypted database directly — logging defeats the access control the encryption was meant to enforce.
- Logs may be shipped to third-party SaaS tools (Datadog, Sentry, Papertrail) that store them outside your encryption boundary.

**Fix:**

```typescript
// WRONG — logs decrypted PAN
async processPan(loanId: string): Promise<void> {
  const pan = await this.decrypt(loan.panEncrypted);
  this.logger.debug(`Processing loan ${loanId} for PAN: ${pan}`);  // NEVER
  // ...
}

// CORRECT — log only the masked or tokenised form
async processPan(loanId: string): Promise<void> {
  const pan    = await this.decrypt(loan.panEncrypted);
  const masked = `XXXXX${pan.slice(-4)}`;  // mask before logging
  this.logger.debug(`Processing loan ${loanId} for PAN: ${masked}`);  // safe
  // ...
}

// ALSO CORRECT — log only the reference, not the value
this.logger.debug(`Processing loan ${loanId}, PAN hash: ${loan.panHash.slice(0, 8)}...`);
```

Systematic fix: add a `SensitiveField` wrapper type that overrides `toString()` and `toJSON()` to return a masked representation, making it impossible to accidentally log the plaintext:

```typescript
class SensitiveString {
  constructor(private readonly value: string) {}
  toString(): string { return '[REDACTED]'; }
  toJSON():   string { return '[REDACTED]'; }
  decrypt():  string { return this.value; }  // explicit decryption call required
}
```

**Q25. What are the most common encryption implementation mistakes at the 5 YOE level, and how do you recognise them in a code review?**
A: Seven patterns worth flagging in any security-focused code review:

**1. IV/nonce reuse with AES-GCM:**
```typescript
// WRONG — static IV means identical plaintexts produce identical ciphertexts
//         and allows nonce-reuse attacks that break GCM authentication entirely
const IV = Buffer.alloc(12, 0);  // static zero IV
const cipher = crypto.createCipheriv('aes-256-gcm', key, IV);

// CORRECT — random IV per encryption operation, stored with the ciphertext
const iv = crypto.randomBytes(12);  // fresh random IV each time
```
AES-GCM is catastrophically broken if the same (key, IV) pair is used twice — an attacker who sees two ciphertexts encrypted with the same nonce can recover the keystream.

**2. ECB mode usage:**
```typescript
// WRONG — ECB mode encrypts each block independently; identical plaintext blocks
//         produce identical ciphertext blocks, leaking data patterns
const cipher = crypto.createCipheriv('aes-256-ecb', key, '');  // ECB — NEVER use

// CORRECT — use GCM (authenticated encryption) or CBC with HMAC
const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);
```

**3. Missing authentication tag verification:**
```typescript
// WRONG — decrypts without verifying the authentication tag
//         susceptible to ciphertext tampering (padding oracle, bit-flipping)
const decipher = crypto.createDecipheriv('aes-256-gcm', key, iv);
// Missing: decipher.setAuthTag(authTag)  ← this is mandatory for GCM

// CORRECT
const decipher = crypto.createDecipheriv('aes-256-gcm', key, iv);
decipher.setAuthTag(authTag);  // throws if tag doesn't match — detects tampering
```

**4. Using MD5 or SHA-1 for any security purpose:**
```typescript
// WRONG — MD5 and SHA-1 are cryptographically broken
const hash = crypto.createHash('md5').update(data).digest('hex');   // NEVER for security
const hash = crypto.createHash('sha1').update(data).digest('hex');  // NEVER for security

// CORRECT — SHA-256 minimum; HMAC-SHA256 for keyed contexts
const hash = crypto.createHash('sha256').update(data).digest('hex');
const hmac = crypto.createHmac('sha256', secret).update(data).digest('hex');
```

**5. Storing encryption keys in the same database as encrypted data:**
```typescript
// WRONG — if the DB is breached, attacker gets both key and ciphertext
await this.db.encryptionKeys.insert({ keyId: 'v1', key: rawKeyHex });
// ... later ...
const key = await this.db.encryptionKeys.findOne({ keyId: 'v1' });
const plain = decrypt(ciphertext, key);

// CORRECT — keys in KMS or a separate secrets manager, never in the application DB
```

**6. Predictable random number generation:**
```typescript
// WRONG — Math.random() is not cryptographically secure
const sessionId = Math.random().toString(36).slice(2);  // predictable

// CORRECT
const sessionId = crypto.randomBytes(32).toString('base64url');
```

**7. Disabling TLS verification in production:**
```typescript
// WRONG — disables MITM protection
process.env.NODE_TLS_REJECT_UNAUTHORIZED = '0';

// CORRECT — fix the root cause (install certificate, add CA to trust store)
```

## Quick Comparison Table

| Dimension | Encryption in Transit | Encryption at Rest |
|---|---|---|
| Protects data | While moving across a network | While stored on a medium |
| Primary threat | Network eavesdropping, MITM | Physical storage theft, backup exfiltration |
| Primary mechanism | TLS (X.509 certificates + AES session key) | AES-256-GCM (full-disk, volume, file, or field level) |
| Key management | PKI — CA signs server certificate | KMS — CMK encrypts data keys (envelope encryption) |
| Who manages keys | CA + server certificate private key | Application + KMS |
| Transparent to app? | Yes (handled by OS/runtime) | Partially — FDE yes; field-level encryption requires app changes |
| PCI-DSS requirement | Req 4 — TLS 1.2+ for PAN in transit | Req 3 — AES-256/TDES-128 for stored PAN |
| RBI requirement | TLS 1.2+ for all payment APIs | Encryption + HSM for sensitive payment data |
| Can be bypassed by | Compromised endpoint (data is plaintext at application) | Compromised application (decrypts for normal operations) |
| Failure mode | Expired certificate → connection refused or MITM possible | Compromised key → all data exposed |

| Algorithm | Type | Use for | Avoid for |
|---|---|---|---|
| AES-256-GCM | Symmetric AEAD | Bulk data encryption (at rest and in transit session) | Key exchange |
| ChaCha20-Poly1305 | Symmetric AEAD | TLS cipher suite (good on CPU without AES-NI) | Storage (AES preferred) |
| RSA-2048+ | Asymmetric | Key encapsulation, digital signatures | Bulk data (too slow) |
| ECDH P-256 | Asymmetric | Key exchange in TLS, envelope encryption | Signatures alone |
| ECDSA P-256 | Asymmetric | Digital signatures (certificates, JWTs) | Bulk data |
| HMAC-SHA256 | Keyed hash | Message authentication, CSRF tokens, OTP HMAC | Encryption (not reversible) |
| SHA-256 | Hash | Content addressing, non-keyed integrity | Authentication (use HMAC) |
| bcrypt / Argon2id | KDF | Password hashing | High-entropy API keys (use SHA-256) |
| MD5 / SHA-1 | Broken | Nothing security-related | Everything |

---

**Tip for the interview:** At 5 YOE, encryption questions move from "what is AES?" to "what does encryption at rest protect against that in-transit doesn't?" and "walk me through how you'd encrypt a PAN field in a production database." Know the threat models precisely — encryption at rest does not protect a running application from a code-level breach, and encryption in transit does not protect stored data from a disk theft. Both are necessary and address orthogonal threats. The envelope encryption pattern (Q11) is the most commonly tested deep-dive — know the GenerateDataKey → local encrypt → store encrypted DEK flow cold. For fintech interviews: the PCI-DSS distinction between HMAC (required for stored PAN hashes) vs plain SHA-256 (insufficient — Q17) is a strong differentiator, as is knowing that tokenisation removes PCI scope while encryption only protects within scope (Q18). The seven code review antipatterns (Q25) — especially IV reuse in AES-GCM and missing auth tag verification — are exactly the kind of things a senior engineer is expected to catch without being told to look for them.
