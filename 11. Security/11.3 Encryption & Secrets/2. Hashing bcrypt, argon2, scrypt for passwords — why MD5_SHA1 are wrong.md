# Security: Password Hashing — bcrypt, Argon2, scrypt vs. MD5/SHA1 — Interview Q&A (5 YOE Level)

---

## Section 1: Why MD5 and SHA1 Are Wrong for Passwords

**Q1. Why are MD5 and SHA1 cryptographically broken for password storage, and what is the specific property they lack that makes them unsuitable regardless of whether they are "broken" in the collision sense?**
A: MD5 and SHA1 are broken for password storage for two distinct reasons — one is the well-known cryptographic break; the other is a fundamental design mismatch that applies even to "unbroken" general-purpose hash functions like SHA-256.

**Reason 1 — Collision resistance is broken (MD5 and SHA1 specifically):**
```
MD5 collision:    two different inputs produce the same 128-bit hash
                  demonstrated in 1996 (theoretical), 2004 (practical)
                  cost: seconds on a laptop as of today

SHA1 collision:   demonstrated by Google's SHAttered attack (2017)
                  cost: ~$110,000 in cloud compute at time of demonstration
                  cost today: dramatically lower with improved attacks

For passwords: if two inputs hash to the same value, an attacker can
authenticate with a different input that isn't the real password.
Practically rare but a real cryptographic guarantee violation.
```

**Reason 2 — Speed is the fundamental problem (applies to ALL general-purpose hash functions):**
```
MD5 throughput on modern GPU:   ~200 billion hashes/second (H100 GPU)
SHA1 throughput on modern GPU:  ~40 billion hashes/second
SHA-256 throughput on GPU:      ~10 billion hashes/second
bcrypt (cost=12) on GPU:        ~300 hashes/second

Speed ratio (MD5 vs bcrypt):    ~667 million times faster

An 8-character alphanumeric password has:
  62^8 = ~218 trillion combinations

At 200 billion MD5/sec:
  ~18 minutes to exhaust entire 8-character space

At 300 bcrypt/sec:
  ~23,000 years to exhaust the same space
```

MD5 and SHA256 were designed to be fast — they power TLS, certificate signing, file integrity checks, HMACs, and content-addressed storage. Speed is a feature there. For passwords, speed is a catastrophic liability: every operation you need to perform once (hash at registration, verify at login), the attacker needs to perform billions of times (brute-force the hash dump). The design goal of general-purpose hash functions is the exact opposite of what password hashing requires.

**Q2. What is a rainbow table attack, how does it differ from a brute-force attack, and why do salts defeat rainbow tables but not GPU brute-force?**
A: Both attacks occur after an attacker has obtained the hashed password database — the offline attack scenario.

**Brute-force attack:**
```
For each candidate password from a list or charset:
  compute hash(candidate)
  compare to target hash
  if match → password found

Cost: O(n) hash computations where n = candidate space
Advantage: works against any single target
Disadvantage: must recompute for each target; cannot precompute
```

**Rainbow table attack:**
```
Precomputation phase (done once, offline):
  Build a table mapping: hash(password) → password
  for millions/billions of common passwords and patterns

Attack phase (instant, after precomputation):
  Look up stolen_hash in rainbow table
  → password returned immediately (table lookup, not computation)

Cost: O(1) per lookup after precomputation
Advantage: extremely fast at attack time (lookup vs. compute)
Disadvantage: table is specific to the exact hash function;
              tables are large (gigabytes to terabytes)
```

**Why salts defeat rainbow tables:**
```
Without salt:
  hash('password123') = 5f4dcc3b...  (same for every user with this password)
  rainbow table has: 5f4dcc3b... → 'password123'
  → instant lookup

With unique salt per user:
  hash('xK9mR2' + 'password123') = a7f3c9...  (user A)
  hash('pL4nQ8' + 'password123') = b2e8d1...  (user B)

  The rainbow table has no entry for a7f3c9... or b2e8d1...
  because it was built for unsalted hash('password123') = 5f4dcc3b...
  → Rainbow table is useless. Attacker must brute-force each hash individually.
```

**Why salts do NOT defeat GPU brute-force:**
```
With a salt, the attacker cannot precompute.
But they can still brute-force each user's hash individually:

  for each candidate in wordlist:
    compute hash(user_A_salt + candidate)  → 10 billion MD5/sec
    compare to user_A_hash
  → Still cracks 8-char passwords in minutes per user

Salt defeats precomputation (rainbow tables).
Salt does NOT make each computation slower.
Only a slow hash function (bcrypt, Argon2, scrypt) defeats GPU brute-force
by making each candidate evaluation expensive.
```

The complete defense requires both: a salt (defeats rainbow tables and ensures identical passwords hash differently) AND a slow hash function (makes each GPU computation expensive). bcrypt, Argon2, and scrypt provide both — they have salts built in and are deliberately slow.

**Q3. Demonstrate concretely what an attacker gets from a leaked password database, and why the format of the stored hash determines the severity of the breach.**
A: The format of the stored credential directly determines how long users are protected after a breach — and whether the breach is a catastrophic immediate compromise or a slow, manageable event:

**Scenario: breach of 1 million user records**

```
Format 1 — Plaintext (worst):
  Stored: { email: 'user@example.com', password: 'MyPassword123!' }
  Attacker effort: zero
  Time to full compromise: immediate
  User protection: none

Format 2 — MD5 without salt:
  Stored: { email: 'user@example.com', passwordHash: '5f4dcc3b5aa765d61d8327deb882cf99' }
  Attacker has: GPU cluster doing 200B MD5/sec + rainbow tables
  Common passwords ('password', '123456', 'iloveyou'): instant via rainbow table
  All 8-char lowercase: ~3 seconds
  All 8-char alphanumeric: ~18 minutes
  Time to crack 80% of accounts: < 1 hour
  User protection: essentially none

Format 3 — SHA-256 with salt:
  Stored: { email: '...', salt: 'xK9mR2pL...', hash: sha256(salt + password) }
  Attacker: 10B SHA-256/sec; rainbow tables useless (salted)
  Must brute-force each user separately
  Common passwords: still instant (dictionary attack at 10B/sec)
  8-char alphanumeric: ~6 hours per user
  1M users in parallel on GPU cluster: most cracked within days
  User protection: hours to days for weak passwords; months for strong ones

Format 4 — bcrypt cost=12:
  Stored: { email: '...', hash: '$2b$12$...' } (salt embedded in hash string)
  Attacker: ~300 bcrypt/sec on high-end GPU
  Common passwords: seconds (dictionary still works — slow per hash but small list)
  8-char random alphanumeric: ~23,000 years
  1M users: even weak passwords take hours-days; strong passwords: centuries
  User protection: days to months for weak passwords; practically forever for strong

Format 5 — Argon2id (memory=64MB, t=3, p=4):
  Attacker: ~5 hashes/sec on GPU (memory bandwidth bottleneck defeats GPU parallelism)
  8-char alphanumeric: ~1.4 million years
  User protection: months for weak passwords; practically forever for strong ones
```

The practical consequence in fintech: a bcrypt or Argon2 breach buys time — time for the security team to detect the breach, time to force password resets, time to notify users. A MD5 breach is an immediate full compromise of every weak password (which is most passwords) before the company even knows the breach happened.

## Section 2: bcrypt

**Q4. How does bcrypt work internally, and what does the cost factor actually control?**
A: bcrypt is a password hashing function designed by Niels Provos and David Mazières in 1999, based on the Blowfish cipher. Its design exploits Blowfish's expensive key setup phase to make hashing deliberately slow and memory-resistant.

**Internal mechanics:**
```
bcrypt(password, cost):
  1. Generate a 128-bit random salt (16 bytes)
  2. Perform key setup: EksBlowfishSetup(cost, salt, password)
     This is the expensive step — runs 2^cost iterations of Blowfish key expansion
  3. Encrypt the magic string "OrpheanBeholderScryDoubt" 64 times
     using the key-expanded state
  4. Output format: $2b$<cost>$<22-char-base64-salt><31-char-base64-hash>

Example output:
  $2b$12$LQv3c1yqBWVHxkd0LHAkCOYz6TtxMQJqhN8/lewohvhSJqJxn2VlC
   │   │  │                      │
   │   │  │                      └─ 31-char hash
   │   │  └─ 22-char salt (128 bits in modified base64)
   │   └─ cost factor (12)
   └─ algorithm version (2b = current; 2a = older; 2y = PHP variant)
```

**What the cost factor controls:**
```
cost = N means: 2^N iterations of the key setup loop

cost=10: 2^10 = 1,024   iterations  → ~100ms on a typical server
cost=11: 2^11 = 2,048   iterations  → ~200ms
cost=12: 2^12 = 4,096   iterations  → ~400ms  ← common production default
cost=13: 2^13 = 8,192   iterations  → ~800ms
cost=14: 2^14 = 16,384  iterations  → ~1.6s   ← for high-security contexts

The cost-to-time relationship is exponential:
  Each +1 to cost = 2x more iterations = 2x more time
  Increasing cost from 10 to 12 = 4x slower for attacker
  Increasing cost from 12 to 14 = 4x more protection again

The same relationship that hurts the attacker hurts the server.
At cost=12, 1000 concurrent login requests = 400 seconds of total hashing CPU.
Cost choice is a balance between security and server load.
```

**Q5. How do you implement bcrypt correctly in Node.js/NestJS, including registration, login, and the cost factor tuning process?**
A:

```typescript
import * as bcrypt from 'bcrypt';
import { Injectable, UnauthorizedException, InternalServerErrorException } from '@nestjs/common';

@Injectable()
export class PasswordService {
  // Cost factor: read from config, not hardcoded
  // Allows tuning without code deployment
  private readonly COST: number = parseInt(process.env.BCRYPT_COST ?? '12', 10);

  constructor() {
    // Validate cost at startup — fail fast if misconfigured
    if (this.COST < 10 || this.COST > 31) {
      throw new Error(`Invalid BCRYPT_COST: ${this.COST}. Must be 10–31.`);
    }
    // Log the active cost so it appears in startup logs for auditing
    console.info(`Password hashing: bcrypt cost=${this.COST}`);
  }

  // Registration — hash the password
  async hashPassword(plaintext: string): Promise<string> {
    // bcrypt.hash() generates a fresh random salt automatically
    // No need to generate and store salt separately — it's embedded in the output
    return bcrypt.hash(plaintext, this.COST);
  }

  // Login — verify the password
  async verifyPassword(plaintext: string, storedHash: string): Promise<boolean> {
    // bcrypt.compare() extracts the salt from storedHash, re-hashes plaintext,
    // and compares using constant-time comparison internally
    // Returns false (never throws) on mismatch — safe to use in conditional
    return bcrypt.compare(plaintext, storedHash);
  }

  // Login handler — important: always hash even if user not found (timing attack prevention)
  async login(email: string, plaintext: string): Promise<User> {
    const user = await this.userRepo.findByEmail(email);

    if (!user) {
      // CRITICAL: still run bcrypt.compare() against a dummy hash
      // Without this, a timing attack reveals which emails exist:
      //   user not found: returns in ~0ms (no hash comparison)
      //   user found, wrong password: returns in ~400ms (hash comparison ran)
      // Attacker measures response time → enumerates valid emails
      await bcrypt.compare(plaintext, '$2b$12$invalidhashpaddinginvalidhash00'); // dummy
      throw new UnauthorizedException('Invalid credentials');
    }

    const isValid = await this.verifyPassword(plaintext, user.passwordHash);
    if (!isValid) {
      throw new UnauthorizedException('Invalid credentials');
    }

    return user;
  }
}

// Registration endpoint
@Post('register')
async register(@Body() dto: RegisterDto) {
  const existing = await this.userRepo.findByEmail(dto.email);
  if (existing) throw new ConflictException('Email already registered');

  const hash = await this.passwordService.hashPassword(dto.password);

  const user = await this.userRepo.create({
    email:        dto.email,
    passwordHash: hash,
    // Never store: dto.password, or any transformed version of it
  });

  return { userId: user.id };
}
```

```typescript
  }
}
```

**Q6. What are the three limitations of bcrypt that motivated the development of newer algorithms, and how does each limitation manifest as a practical security weakness?**
A:

**Limitation 1 — Password truncation at 72 bytes:**
```
bcrypt internally uses only the first 72 bytes of the password.
Any characters beyond byte 72 are silently ignored.

Consequence:
  'correct-horse-battery-staple-this-is-a-long-passphrase-more-text-here' (72 chars)
  'correct-horse-battery-staple-this-is-a-long-passphrase-more-text-XXXX' (different ending)
  → Both produce the SAME bcrypt hash

In practice: most users have passwords under 72 bytes.
But for applications encouraging long passphrases, this is a real truncation.

Mitigation: pre-hash the password before bcrypt:
  const prehashed = crypto.createHash('sha256').update(plaintext).digest('hex'); // 64 chars
  return bcrypt.hash(prehashed, COST);
  // sha256 output is always 64 hex chars (under 72) → no truncation
  // sha256 maps any-length input to fixed-length → bcrypt sees full entropy
  // Caveat: sha256 output has no null bytes → safe for bcrypt's null-termination
  //         Do NOT use sha256 binary output → may contain null bytes → truncated early
```

**Limitation 2 — Limited memory hardness (GPU-friendly):**
```
bcrypt uses a fixed 4KB memory footprint (the Blowfish S-boxes).
GPUs have enormous parallelism:
  RTX 4090: 16,384 CUDA cores
  With 4KB per core: 4KB × 16,384 = 64MB total → fits easily in GPU memory

Result: GPU can run thousands of bcrypt instances in parallel.
  GPU bcrypt speed: ~300 hashes/sec (vs ~10/sec on CPU per core)
  Ratio is only ~30x, not millions — bcrypt IS harder to parallelize than MD5
  But dedicated ASICs and GPU farms narrow the gap significantly

Memory-hard algorithms (Argon2, scrypt) require megabytes per hash.
  64MB per hash × 16,384 parallel cores = 1TB required → impossible on GPU
  → Forces attackers to use CPUs with large memory bandwidth → massive slowdown
```

**Limitation 3 — No parallelism parameter:**
```
bcrypt has only one tuning parameter: cost (iteration count).
It cannot exploit multiple CPU cores per hash.

On a modern 16-core server: hashing one password uses 1 core.
Other 15 cores sit idle during the hash.

Argon2id has a parallelism parameter (p):
  p=4: uses 4 threads per hash → 4x more work per hash on attacker's hardware
  The defender's server uses 4 threads (has them); the attacker's GPU
  cannot efficiently parallelize memory-hard operations the same way.

bcrypt at cost=12: ~400ms, 1 core, 4KB memory
Argon2id m=65536,t=3,p=4: ~300ms, 4 cores, 64MB memory
→ Argon2id provides far stronger security per unit of wall-clock time
```

## Section 3: scrypt

**Q7. How does scrypt achieve memory-hardness, and what does "sequentially memory-hard" mean in the context of defeating GPU attacks?**
A: scrypt was designed by Colin Percival in 2009 specifically to address bcrypt's memory limitation. Its core insight: if hashing requires a large amount of memory that must be accessed in a sequential, data-dependent order, the attack cannot be parallelized on memory-bandwidth-limited hardware (GPUs and ASICs).

**The ROMix algorithm — scrypt's core:**
```
scrypt(password, salt, N, r, p):

  Step 1: Generate a large block of pseudorandom data
    BlockSize = 128 * r bytes  (r=8 → 1024 bytes per block)
    Fill N blocks with pseudorandom data derived from password+salt
    Total memory = N × BlockSize = N × 128r bytes

  Step 2: Sequential read-write passes (the memory-hard step)
    for i = 0 to N-1:
      j = integer derived from current block (DATA-DEPENDENT — cannot precompute)
      current_block = mix(current_block XOR blocks[j])
      // j depends on the current state → must have ALL N blocks in memory
      // Cannot know which block j points to until you have the current block
      // → Cannot stream blocks from disk; must have everything in RAM

  Step 3: Final hash of the resulting state

Parameters:
  N: CPU/memory cost (must be a power of 2). Memory = 128 × r × N bytes.
     N=32768 (2^15): 32MB;  N=65536 (2^16): 64MB;  N=1048576 (2^20): 1GB
  r: block size factor (r=8 standard)
  p: parallelization factor — number of independent scrypt instances to run
     (increases CPU cost without increasing memory per instance)
```

**Why "sequentially memory-hard" defeats GPUs:**
```
"Memory-hard": requires a minimum amount of memory to compute at all
"Sequentially": each memory access depends on the result of the previous
                → cannot pipeline or parallelize the memory access pattern

GPU vs. scrypt:
  GPU has: 10,000+ cores, fast arithmetic, but LIMITED memory bandwidth
  GPU memory bandwidth: ~2TB/s (H100)
  One scrypt (N=65536, r=8): needs 64MB, ~2GB/s memory bandwidth for the passes
  Parallel scrypt instances: 2TB/s ÷ 2GB/s = ~1000 simultaneous instances max
    vs. MD5: millions of instances (no memory pressure)

  GPU advantage collapses: 1000 scrypt vs. 1,000,000,000 MD5 simultaneously
  The memory bandwidth is the bottleneck, not arithmetic throughput
  → Memory-hard functions effectively neutralize GPU parallelism advantage

ASIC cost-effectiveness: building an ASIC for scrypt requires the same
  large memory as a CPU. Memory dominates the die area and cost.
  ASIC advantage over CPU for scrypt: ~10x (vs ~1,000,000x for MD5)
  → scrypt's memory-hardness makes custom hardware attacks impractical
```

**Q8. How do you implement scrypt in Node.js, and what are the recommended parameters for different security contexts?**
A: Node.js has scrypt built into the `crypto` module — no third-party dependency required:

```typescript
import crypto from 'crypto';
import { promisify } from 'util';

const scryptAsync = promisify(crypto.scrypt);

@Injectable()
export class ScryptPasswordService {
  // Parameters by security context
  private readonly PARAMS = {
    // Interactive login (web app): balance UX and security
    interactive: { N: 32768, r: 8, p: 1, keylen: 64 },
    // High security (admin, finance operations): slower, stronger
    sensitive: { N: 131072, r: 8, p: 2, keylen: 64 },
    // Offline / background: maximum strength when latency doesn't matter
    offline: { N: 1048576, r: 8, p: 1, keylen: 64 },
  };

  async hashPassword(
    plaintext: string,
    context: keyof typeof this.PARAMS = 'interactive',
  ): Promise<string> {
    const { N, r, p, keylen } = this.PARAMS[context];
    const salt = crypto.randomBytes(32); // 256-bit random salt

    const derivedKey = await scryptAsync(plaintext, salt, keylen, { N, r, p }) as Buffer;

    // Encode everything needed for verification into one storable string
    // Format: scrypt$N$r$p$salt(hex)$hash(hex)
    return [
      'scrypt',
      N,
      r,
      p,
      salt.toString('hex'),
      derivedKey.toString('hex'),
    ].join('$');
  }

  async verifyPassword(plaintext: string, stored: string): Promise<boolean> {
    const parts = stored.split('$');
    if (parts.length !== 6 || parts[0] !== 'scrypt') {
      throw new Error('Invalid hash format');
    }

    const [, N, r, p, saltHex, hashHex] = parts;
    const salt       = Buffer.from(saltHex, 'hex');
    const storedHash = Buffer.from(hashHex, 'hex');

    const derivedKey = await scryptAsync(
      plaintext,
      salt,
      storedHash.length,
      { N: parseInt(N), r: parseInt(r), p: parseInt(p) },
    ) as Buffer;

    // Constant-time comparison — mandatory
    return crypto.timingSafeEqual(derivedKey, storedHash);
  }
}
```

**scrypt vs. bcrypt parameters — equivalence table:**
```
bcrypt cost=10 (~65ms, 4KB)     ≈  scrypt N=16384,  r=8, p=1  (~50ms,  16MB)
bcrypt cost=12 (~260ms, 4KB)    ≈  scrypt N=65536,  r=8, p=1  (~200ms, 64MB)
bcrypt cost=14 (~1040ms, 4KB)   ≈  scrypt N=262144, r=8, p=1  (~800ms, 256MB)

At the same wall-clock time, scrypt provides significantly stronger protection
because an attacker must also pay the memory cost — bcrypt does not impose this.
```

## Section 4: Argon2

**Q9. What are the three Argon2 variants (Argon2d, Argon2i, Argon2id), and which should you use for password hashing and why?**
A: Argon2 won the Password Hashing Competition (PHC) in 2015 and is the current NIST recommended password hashing function. Its three variants address different threat models:

**Argon2d — Data-dependent memory access:**
```
Memory access pattern depends on the password being hashed.
→ Maximum resistance to GPU/ASIC attacks
→ Vulnerable to side-channel timing attacks:
  An attacker with ability to measure cache timing can observe
  which memory addresses are accessed → infer information about the password
  This is a real threat when the attacker can run code on the same machine
  (shared cloud instances, JavaScript in browser, microarchitectural attacks)

Use for: cryptocurrency proof-of-work, server-side KDF where
         side-channel attacks are impossible (isolated server, no code execution)
Not for: general password hashing where attacker might exploit timing
```

**Argon2i — Data-independent memory access:**
```
Memory access pattern is fixed regardless of the password.
→ Immune to side-channel timing attacks
→ Less resistant to GPU attacks than Argon2d (predictable access pattern
  allows some optimization of the memory traversal on GPUs)
→ Requires higher memory and iteration parameters to compensate

Use for: password-based key derivation in contexts where side-channel
         attacks are a concern (client-side, shared hardware)
Not recommended: for standalone password hashing — Argon2id is better
```

**Argon2id — Hybrid (RECOMMENDED for password hashing):**
```
First half of memory pass: data-independent (Argon2i)
Second half of memory pass: data-dependent (Argon2d)

→ Provides side-channel resistance for the first half
  (before a side-channel attacker can observe enough to reconstruct the password)
→ Provides GPU/ASIC resistance for the second half
→ Best of both: practical side-channel resistance + strong memory-hardness

OWASP, NIST, RFC 9106: all recommend Argon2id for password hashing.
This is the correct answer for any interview question about Argon2.
```

**Q10. What are the three tuning parameters of Argon2, and how do you choose them for a production fintech application?**
A: Argon2 has three independently tunable parameters — memory, time, and parallelism — which is its primary advantage over bcrypt's single parameter:

```
m (memory cost): kilobytes of memory required per hash
  m=65536:  64MB  — minimum recommended for interactive login
  m=131072: 128MB — strong for sensitive operations
  m=262144: 256MB — high-security contexts

t (time cost): number of passes over the memory
  t=1: single pass (fastest; less secure for low m)
  t=3: three passes (OWASP minimum recommendation)
  t=4: strong default for most applications

p (parallelism): number of threads used per hash
  p=1: single thread
  p=4: four threads — uses 4 CPU cores; increases work without memory cost
  p=8: eight threads — for servers with many cores
  Note: p does NOT reduce wall-clock time if your server only has 1 core;
        it increases total CPU work per hash, which costs the attacker more
```

**OWASP 2023 recommended minimums:**
```
Argon2id (first choice):
  m=19456 (19MB), t=2, p=1   → minimum (constrained environments)
  m=65536 (64MB), t=3, p=4   → standard recommendation
  m=131072 (128MB), t=4, p=8 → high-security

Argon2id vs. bcrypt (for the same 300ms budget):
  bcrypt cost=12:        300ms, 4KB memory,  1 thread, attacker ~300/sec GPU
  Argon2id m=64MB,t=3,p=4: 300ms, 64MB memory, 4 threads, attacker ~5/sec GPU
  → Argon2id is ~60x harder to crack per unit of defender's time
```

```typescript
import argon2 from 'argon2';

@Injectable()
export class Argon2PasswordService {
  private readonly OPTIONS: argon2.Options = {
    type:        argon2.argon2id,  // Always argon2id
    memoryCost:  65536,            // 64MB in KB
    timeCost:    3,                // 3 iterations
    parallelism: 4,                // 4 threads
    hashLength:  32,               // 32-byte (256-bit) output
    // Salt: auto-generated by argon2 library (16 bytes by default)
    // Version: argon2 library uses latest version (19) by default
  };

  async hashPassword(plaintext: string): Promise<string> {
    // argon2.hash() auto-generates a cryptographically random salt
    // and embeds it in the PHC string format output:
    // $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>
    return argon2.hash(plaintext, this.OPTIONS);
  }

  async verifyPassword(plaintext: string, stored: string): Promise<boolean> {
    try {
      // argon2.verify() parses all parameters from the stored PHC string
      // No need to separately track salt, m, t, p — all embedded
      return await argon2.verify(stored, plaintext);
    } catch {
      return false; // Malformed hash — treat as invalid
    }
  }

  // Check if a stored hash needs rehashing (parameter upgrade)
  needsRehash(stored: string): boolean {
    return argon2.needsRehash(stored, this.OPTIONS);
    // Returns true if stored hash was generated with weaker parameters
    // Use this on successful login to transparently upgrade old hashes
  }
}

// Login flow with transparent parameter upgrade
async login(email: string, plaintext: string): Promise<AuthResult> {
  const user = await this.userRepo.findByEmail(email);
  if (!user) {
    await argon2.hash(plaintext); // Dummy hash — timing attack prevention
    throw new UnauthorizedException('Invalid credentials');
  }

  const isValid = await this.passwordService.verifyPassword(plaintext, user.passwordHash);
  if (!isValid) throw new UnauthorizedException('Invalid credentials');

  // Transparent rehash: if old hash used weaker parameters, upgrade on login
  if (this.passwordService.needsRehash(user.passwordHash)) {
    const newHash = await this.passwordService.hashPassword(plaintext);
    await this.userRepo.update(user.id, { passwordHash: newHash });
    // No user interaction required — happens silently on successful login
  }

  return this.generateAuthTokens(user);
}
```

## Section 5: Salts, Peppers, and Key Stretching

**Q11. What is a pepper, how does it differ from a salt, and when is it an appropriate additional control in a fintech system?**
A: A salt and a pepper solve different problems — they are complementary, not alternatives:

```
Salt:
  - Random value, unique per user
  - Stored in the database alongside the hash
  - Purpose: defeat rainbow tables; ensure identical passwords hash differently
  - If DB is breached: attacker has the salt; it's public information by design
  - Without salt: attacker can precompute; with salt: must brute-force per user

Pepper:
  - Secret value, shared across all users (not unique per user)
  - Stored in application config / secrets manager — NOT in the database
  - Purpose: make password hashes useless even if the database is breached alone
  - If DB is breached but application secret is NOT: attacker has salted hashes
    but cannot crack them without the pepper — cannot even start the attack
  - If both DB and pepper are breached: provides no additional protection
```

**How pepper is applied:**
```typescript
import * as bcrypt from 'bcrypt';
import crypto from 'crypto';

@Injectable()
export class PepperedPasswordService {
  // Pepper: from secrets manager, not .env file ideally
  // Never hardcoded; never in source control
  private readonly PEPPER = process.env.PASSWORD_PEPPER!;
  private readonly COST   = 12;

  private applyPepper(plaintext: string): string {
    // HMAC-pepper: apply pepper via HMAC before bcrypt
    // Why HMAC and not concatenation?
    //   Concatenation: pepper + 'password' = 'SECRETpassword' (64 byte limit risk)
    //   HMAC: always produces fixed-length (32 bytes) regardless of input length
    //   HMAC: the pepper is the KEY, not part of the data — cleaner security model
    return crypto
      .createHmac('sha256', this.PEPPER)
      .update(plaintext)
      .digest('hex');  // 64 hex chars = 32 bytes — safely under bcrypt's 72-byte limit
  }

  async hashPassword(plaintext: string): Promise<string> {
    const pepperedInput = this.applyPepper(plaintext);
    return bcrypt.hash(pepperedInput, this.COST);
  }

  async verifyPassword(plaintext: string, storedHash: string): Promise<boolean> {
    const pepperedInput = this.applyPepper(plaintext);
    return bcrypt.compare(pepperedInput, storedHash);
  }
}
```

**When pepper is appropriate in fintech:**
```
Appropriate:
  - High-value targets: admin accounts, payment processing systems
  - Regulatory environments where defense-in-depth is mandated
  - Multi-tier secrets architecture: DB credentials, app secrets, and HSM
    are separate — a SQL injection doesn't compromise the pepper

Limitations / Operational considerations:
  - Pepper rotation requires rehashing ALL passwords (cannot do lazily per-login
    because old pepper is needed to verify the existing hash first)
  - Rotation procedure: keep old pepper, verify with old pepper,
    rehash with new pepper on successful verification — same as parameter upgrade
  - Pepper in .env file on the same server as DB provides limited benefit
    (server compromise gets both); pepper in HSM or separate secret store is strong
  - Loss of pepper = loss of all password verifications = full re-registration event
    → Pepper must be backed up and disaster-recovery tested
```

**Q12. What is key stretching, and how does it relate to what bcrypt, scrypt, and Argon2 do internally?**
A: Key stretching is the general technique of making a low-entropy input (a password) computationally expensive to process — artificially slowing down the derivation to make brute-force attacks impractical. bcrypt, scrypt, and Argon2 are all key stretching functions designed for passwords, but they stretch along different resource dimensions:

```
PBKDF2 (Password-Based Key Derivation Function 2) — simple key stretching:
  output = HMAC(password, salt, iterations, keylen)
  iterations = 600,000 recommended by OWASP for PBKDF2-SHA256

  How it stretches: runs HMAC 600,000 times (time stretching)
  Memory: negligible (a few bytes of state)
  GPU parallelism: trivially parallelized — GPU runs 600K HMACs fast
  GPU speed: ~600,000 PBKDF2/sec on RTX 4090 (still very fast)
  Use only when bcrypt/Argon2 unavailable (legacy systems, FIPS requirements)

bcrypt — time stretching:
  Runs 2^cost key expansion iterations
  Memory: 4KB (Blowfish S-boxes)
  GPU: harder than PBKDF2 but 4KB fits in GPU cache → still parallelizable
  Stretches: time only

scrypt — time + memory stretching:
  Runs sequential memory-hard operations over N×128r bytes
  Memory: 64MB+ required and must be sequentially accessed
  GPU: memory bandwidth bottleneck → parallelism collapses
  Stretches: time AND memory

Argon2id — time + memory + parallelism stretching:
  Like scrypt but with explicit parallelism parameter
  Memory: configurable megabytes, data-dependent access (second half)
  Parallelism: p threads required → costs attacker p × memory per instance
  Stretches: time AND memory AND parallel work
```

The progression from PBKDF2 → bcrypt → scrypt → Argon2 represents the field learning which resources are hardest for attackers to scale cheaply. CPU time (PBKDF2) is cheap to parallelize on GPUs. Memory (scrypt, Argon2) is harder to scale — memory chips cost money and memory bandwidth is a hard physical limit. Argon2's combination of memory, time, and thread-level parallelism currently provides the best security-to-cost ratio for defenders.

## Section 6: Migration, Operational Concerns, and Failure Scenarios

**Q13. You have a legacy system storing passwords as unsalted MD5. How do you migrate to bcrypt without forcing all users to reset their passwords?**
A: Migrating a live password store from MD5 to bcrypt without user disruption requires a two-phase approach that keeps the system functional throughout. You cannot directly convert MD5 hashes to bcrypt hashes — you need the plaintext to re-hash, which only the user has:

**Phase 1 — Wrap existing MD5 hashes in bcrypt (immediate, no user interaction):**
```typescript
// The key insight: bcrypt the MD5 hash instead of the plaintext
// The MD5 hash IS a string — bcrypt can hash any string, including another hash

// Migration script: run once, transforms all existing records
async function wrapMd5WithBcrypt(): Promise<void> {
  const users = await db.users.findAll({ where: { hashType: 'md5' } });

  for (const user of users) {
    // Existing: user.passwordHash = md5('userpassword') = '5f4dcc3b...'
    // New: user.passwordHash = bcrypt('5f4dcc3b...', 12)
    const bcryptWrapped = await bcrypt.hash(user.passwordHash, 12);

    await db.users.update(user.id, {
      passwordHash: bcryptWrapped,
      hashType:     'bcrypt_over_md5',  // Mark the wrapping type
    });
  }
}

// Updated login flow during Phase 1
async function login_phase1(email: string, plaintext: string): Promise<User> {
  const user = await db.users.findByEmail(email);
  if (!user) { /* dummy compare */ throw new UnauthorizedException(); }

  if (user.hashType === 'bcrypt_over_md5') {
    // Compute MD5 of the plaintext, then compare against the bcrypt-wrapped MD5
    const md5OfPlaintext = crypto.createHash('md5').update(plaintext).digest('hex');
    const isValid = await bcrypt.compare(md5OfPlaintext, user.passwordHash);
    if (!isValid) throw new UnauthorizedException('Invalid credentials');

    // Phase 2 transition: now we have the plaintext — rehash properly
    const properHash = await bcrypt.hash(plaintext, 12);
    await db.users.update(user.id, {
      passwordHash: properHash,
      hashType:     'bcrypt',
    });
    return user;
  }

  if (user.hashType === 'bcrypt') {
    const isValid = await bcrypt.compare(plaintext, user.passwordHash);
    if (!isValid) throw new UnauthorizedException('Invalid credentials');
    return user;
  }
}
```

**Phase 2 — Organic rehash on login (runs over weeks/months):**
```
When user logs in successfully during Phase 1:
  → We have the plaintext password
  → Rehash with proper bcrypt(plaintext) → no more MD5 in the chain
  → Update hashType to 'bcrypt'
  → User never notices anything

After 90 days: check what percentage of users have hashType='bcrypt'
  If >90%: consider forcing the remaining 10% to reset
  (long-inactive accounts unlikely to log in organically)

Users who never log in during the migration window:
  → Still protected by bcrypt_over_md5 (vastly better than raw MD5)
  → Force password reset if they eventually return (or after extended inactivity)
```

**Why bcrypt(md5(password)) is vastly better than md5(password):**
```
md5('password') = 5f4dcc3b...  → crackable in milliseconds on GPU
bcrypt(md5('password'), 12):
  Attacker must:
  1. For each candidate: compute md5(candidate) → then bcrypt(md5candidate, 12)
  2. bcrypt at cost=12 = ~300 hashes/sec on GPU regardless of what's inside
  The MD5 is just a string to bcrypt — its internal weakness is irrelevant here
  GPU speed drops from 200B/sec → ~300/sec immediately
  Protection is as strong as bcrypt alone for practical purposes
```

**Q14. What is a timing attack on password verification, and how does `crypto.timingSafeEqual` prevent it?**
A: A timing attack exploits the fact that string comparison functions return early on the first mismatch — different inputs take different amounts of time to compare, and an attacker can measure these differences to learn about the secret value.

**How a naive timing attack works on a home-rolled token comparison:**
```typescript
// VULNERABLE — early-exit string comparison
function verifyApiKey(supplied: string, stored: string): boolean {
  // JavaScript's === uses short-circuit evaluation:
  // If stored = 'secret_key_abc123'
  // supplied = 'AAAAAAAAAAAAAAAA' → false after ~1ns (first char mismatch)
  // supplied = 'secret_key_abc124' → false after ~17ns (last char mismatch)
  // supplied = 'secret_key_abc123' → true after ~17ns (full comparison)
  return supplied === stored;
}

// Timing attack:
// Attacker tries: 'AAAAAAAAAAAAAAAA', 'BAAAAAAAAAAAAAAA', 'CAAAAAAAAAAAAAAA', ...
// Measures response time for each attempt (requires many samples, statistical analysis)
// When 'SAAAAAAAAAAAAAAA' takes slightly longer → first char is 'S'
// Repeat for each character → full secret reconstructed without brute force
```

**Why bcrypt.compare() is safe from timing attacks (unlike home-rolled):**
```
bcrypt.compare() is implemented in C and uses constant-time comparison internally.
The comparison takes the same amount of time regardless of where the mismatch is.
→ No timing signal leaked for bcrypt comparisons.

But: building your own token or hash comparison in JavaScript? Use timingSafeEqual:
```

```typescript
import crypto from 'crypto';

// SAFE — constant-time comparison for any two buffers/strings
function safeCompare(a: string, b: string): boolean {
  // timingSafeEqual requires equal-length buffers
  // If lengths differ, it reveals length information
  // Solution: hash both values to fixed-length first
  const aHash = crypto.createHash('sha256').update(a).digest();
  const bHash = crypto.createHash('sha256').update(b).digest();

  // Both are always 32 bytes → timingSafeEqual is always constant-time
  return crypto.timingSafeEqual(aHash, bHash);
}

// When to use timingSafeEqual vs. bcrypt.compare():
//
// bcrypt.compare():       for password verification — uses bcrypt's internal comparison
// crypto.timingSafeEqual: for comparing:
//   - API keys / tokens (fixed-length strings where == would leak timing)
//   - CSRF tokens (Q7 in CSRF guide — timingSafeEqual for session-bound tokens)
//   - HMAC signatures (webhook verification)
//   - Any secret string comparison where timing leakage is a concern
//   - scrypt and manual hash comparisons (where bcrypt's built-in isn't used)
```

**Q15. How do you handle the case where bcrypt or Argon2 hashing becomes a bottleneck under high login traffic, and what are the acceptable vs. unacceptable mitigations?**
A: Slow hashing is intentional — it is the entire point of the algorithm. "Fixing" it by lowering the cost factor defeats the security property. The correct mitigations preserve security while managing server load:

**Acceptable mitigations:**

```typescript
// Mitigation 1 — Offload hashing to a dedicated worker pool
// Hash operations are CPU-bound and block the Node.js event loop
// Use worker_threads to run bcrypt/Argon2 without blocking I/O

// worker.ts
import { parentPort, workerData } from 'worker_threads';
import argon2 from 'argon2';

async function hash() {
  const result = await argon2.hash(workerData.plaintext, workerData.options);
  parentPort!.postMessage({ result });
}
hash();

// Main thread — non-blocking hash via worker pool
import { Worker } from 'worker_threads';

function hashInWorker(plaintext: string, options: argon2.Options): Promise<string> {
  return new Promise((resolve, reject) => {
    const worker = new Worker('./worker.js', { workerData: { plaintext, options } });
    worker.on('message', ({ result }) => resolve(result));
    worker.on('error', reject);
  });
}
// piscina is a production-grade worker pool library for this pattern

// Mitigation 2 — Rate-limit login attempts (reduces hashing load AND security benefit)
// If each IP is limited to 10 login attempts/min, total hash operations are bounded
// Rate limiting is a security control independently — it's doubly effective here

// Mitigation 3 — Cache the authentication decision briefly (NOT the hash)
// If a user successfully authenticated, cache the result for 30 seconds
// Subsequent requests within 30s skip rehashing (use the cached decision)
// Only acceptable if: the 30s window is for the same session, not cross-session
// Risk: if password changes, old cache decision is briefly valid
// Mitigation: cache key includes user.updatedAt — invalidated on password change

// Mitigation 4 — Scale horizontally
// Hash operations scale linearly with server count
// 2 servers → 2x login throughput at same latency
// Hashing cost is per-request CPU, not shared state — trivially horizontally scalable
```

**Unacceptable mitigations:**
```
✗ Reduce cost factor to make it faster
  → Directly weakens security; defeats the purpose

✗ Use PBKDF2 or SHA-256 instead "for performance"
  → Catastrophically weaker; trading security for performance is not a trade-off

✗ Hash once and cache the hash result as a short-lived "fast token"
  → Creates a second credential (the fast token) that must itself be secured

✗ Pre-hash with MD5 first, then bcrypt
  → If MD5 is used to reduce input entropy before bcrypt, not to address truncation,
     this weakens security (MD5 output has lower entropy than the original password
     for short passwords)
  → bcrypt's 72-byte truncation should be addressed via SHA-256 prehash (Q6)
     only when passwords exceed 72 bytes in practice

✗ Parallelize a single hash across multiple cores
  → bcrypt is inherently serial; Argon2 has a parallelism parameter for this
     correctly — use Argon2 with p>1 rather than trying to split bcrypt
```
