# Security: TLS 1.2 vs. TLS 1.3 — Handshake, Cipher Suites, Certificate Validation — Interview Q&A (5 YOE Level)

---

## Section 1: The TLS Handshake Compared

**Q1. Walk through the TLS 1.2 full handshake step by step, identifying the round trips, what is negotiated at each step, and where the performance cost comes from.**
A: The TLS 1.2 full handshake requires 2 round trips before any application data flows. Each round trip adds one network latency (RTT) to the connection establishment cost:

```
Client                                          Server
  │                                               │
  │──── ClientHello ──────────────────────────────▶│  RTT 1 begins
  │     - TLS version: 1.2                         │
  │     - Random: 32 bytes (client_random)         │
  │     - Session ID (for resumption)              │
  │     - Cipher suites supported (list)           │
  │     - Compression methods (now always null)    │
  │     - Extensions: SNI, ALPN, supported_groups  │
  │                                               │
  │◀─── ServerHello ──────────────────────────────│
  │     - Chosen TLS version: 1.2                 │
  │     - Random: 32 bytes (server_random)        │
  │     - Session ID                              │
  │     - Chosen cipher suite                     │
  │                                               │
  │◀─── Certificate ──────────────────────────────│
  │     - Server's X.509 certificate chain        │
  │                                               │
  │◀─── ServerKeyExchange (if DHE/ECDHE) ─────────│
  │     - Ephemeral DH parameters                 │
  │     - Server's signature over parameters      │
  │     (omitted for RSA key exchange)            │
  │                                               │
  │◀─── ServerHelloDone ───────────────────────────│  RTT 1 ends
  │                                               │
  │──── ClientKeyExchange ────────────────────────▶│  RTT 2 begins
  │     - DHE/ECDHE: client's DH public value     │
  │     - RSA: encrypted pre-master secret        │
  │                                               │
  │──── ChangeCipherSpec ─────────────────────────▶│
  │     - "Switching to encrypted mode"           │
  │                                               │
  │──── Finished (encrypted) ─────────────────────▶│
  │     - HMAC of all handshake messages          │
  │                                               │
  │◀─── ChangeCipherSpec ──────────────────────────│
  │◀─── Finished (encrypted) ──────────────────────│  RTT 2 ends
  │                                               │
  │──── Application Data ─────────────────────────▶│  Data flows after 2 RTTs
```

**What is negotiated and why it matters:**

```
ClientHello → ServerHello:
  Protocol version: both sides must agree on TLS 1.2
  Cipher suite: one from the client's offered list
    e.g., TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
          │    │      │   │    │   │   │   └── PRF hash (SHA-384)
          │    │      │   │    │   │   └────── MAC algorithm (GCM is AEAD, no separate MAC)
          │    │      │   │    │   └────────── Encryption (AES-256-GCM)
          │    │      │   │    └────────────── Key size (256-bit)
          │    │      │   └─────────────────── Block cipher mode (GCM)
          │    │      └─────────────────────── Authentication (RSA cert)
          │    └────────────────────────────── Key exchange (ECDHE)
          └─────────────────────────────────── Protocol identifier

ServerKeyExchange → ClientKeyExchange:
  Key exchange: establish the pre-master secret
  DHE/ECDHE: Diffie-Hellman ephemeral — provides forward secrecy
  RSA: client encrypts a random pre-master secret with server's public key
       NO forward secrecy — if private key is later compromised, all
       recorded sessions can be decrypted retroactively

Key derivation:
  master_secret = PRF(pre_master_secret, "master secret",
                      client_random + server_random, 48)
  session_keys  = PRF(master_secret, "key expansion",
                      server_random + client_random, key_material_length)
  → Separate keys derived for: client write key, server write key,
    client write IV, server write IV, client MAC key, server MAC key
```

**The performance cost:**
```
2 RTT penalty before any data flows
On a 50ms RTT link: 100ms of TLS handshake overhead before first byte of HTTP response
On a 200ms intercontinental link: 400ms of handshake overhead

Additional CPU cost:
  Certificate chain validation (OCSP, CRL, chain building)
  Asymmetric crypto: RSA-2048 signature verification (~1ms)
                     ECDH point multiplication (~0.1ms)
  These are one-time per connection — session resumption amortizes them
```

**Q2. Walk through the TLS 1.3 handshake, explain why it achieves 1-RTT, and what cryptographic changes enable the reduction.**
A: TLS 1.3 reduces the full handshake to 1 RTT by front-loading key material and eliminating the negotiation steps that required a separate round trip in TLS 1.2:

```
Client                                          Server
  │                                               │
  │──── ClientHello ──────────────────────────────▶│  RTT 1 begins
  │     - Supported versions: [1.3, 1.2]           │
  │     - Random: 32 bytes                         │
  │     - Cipher suites: [AES-256-GCM-SHA384, ...]│
  │     - key_share extension:                     │
  │       Client's ECDH public key (X25519)        │
  │       → Sent speculatively before negotiation  │
  │     - supported_groups, signature_algs, ALPN   │
  │     - (NO session ID — replaced by PSK)        │
  │                                               │
  │◀─── ServerHello ──────────────────────────────│
  │     - Chosen version: 1.3                     │
  │     - Server's ECDH public key (key_share)    │
  │     - Chosen cipher suite                     │
  │     ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │
  │     [All subsequent messages are ENCRYPTED]   │
  │◀─── EncryptedExtensions ──────────────────────│
  │     - ALPN, server name, max fragment length  │
  │◀─── Certificate ──────────────────────────────│
  │◀─── CertificateVerify ─────────────────────────│
  │     - Server's signature over handshake hash  │
  │◀─── Finished ──────────────────────────────────│  RTT 1 ends
  │     - HMAC over entire handshake transcript   │
  │                                               │
  │──── Finished ─────────────────────────────────▶│  Client confirms
  │──── Application Data ─────────────────────────▶│  Data flows after 1 RTT
```

**What enables 1-RTT — three key design changes:**

**Change 1 — Key share sent in ClientHello (speculative key agreement):**
```
TLS 1.2: ClientHello just lists supported groups → ServerHello picks one
          → Second round trip needed for actual key material

TLS 1.3: ClientHello includes the actual ECDH public key for the most likely group
          (usually X25519, since it's universally preferred)
          Server receives key material in the first message → can derive shared secret
          immediately → can encrypt ServerHello's extensions right away

If server doesn't support the client's guessed group (rare):
  Server sends HelloRetryRequest → client sends new ClientHello with correct group
  → Falls back to 2 RTT (the exception, not the rule)
```

**Change 2 — Server encrypts everything after ServerHello:**
```
TLS 1.2: Certificate, ServerKeyExchange, ServerHelloDone → sent in plaintext
          An eavesdropper sees: which certificate, which DH parameters, server identity

TLS 1.3: Server derives handshake_secret from ECDH immediately after ServerHello
          Certificate, CertificateVerify, Finished → all encrypted with handshake key
          An eavesdropper sees: only ServerHello (version, cipher suite, ECDH public key)
          Certificate is hidden from passive observers → improved privacy
```

**Change 3 — Key derivation uses HKDF, not the TLS 1.2 PRF:**
```
TLS 1.2 PRF: HMAC-based PRF with MD5/SHA1 mixed (older) or SHA-256/384 (newer)
             Separate keys derived from a single master_secret

TLS 1.3 key schedule — HKDF extract-and-expand:
  early_secret     = HKDF-Extract(0, PSK or 0)  ← 0-RTT key (if resuming)
  handshake_secret = HKDF-Extract(ECDH_output, derive_secret(early_secret))
  master_secret    = HKDF-Extract(0, derive_secret(handshake_secret))

  Separate traffic keys for:
    client_handshake_traffic_secret
    server_handshake_traffic_secret
    client_application_traffic_secret
    server_application_traffic_secret
    exporter_master_secret
    resumption_master_secret

  Why this matters: each stage has forward secrecy relative to the previous —
  compromising application_traffic_secret does not compromise handshake_secret
```

**Q3. What is 0-RTT (early data) in TLS 1.3, how does it work, and what is the security trade-off that makes it unsuitable for certain requests?**
A: 0-RTT allows the client to send application data in the very first message — before the handshake completes — achieving zero additional RTT for session resumption. It is the most aggressive performance optimization in TLS 1.3:

```
Session establishment (first connection):
  Normal 1-RTT TLS 1.3 handshake
  Server sends a NewSessionTicket after the handshake completes:
    → Contains a PSK (Pre-Shared Key) encrypted with server's ticket key
    → Contains max_early_data_size (how much 0-RTT data is permitted)
    → Client stores this ticket for future connections to the same server

Resumption with 0-RTT (subsequent connection):
Client                                          Server
  │                                               │
  │──── ClientHello ──────────────────────────────▶│
  │     - psk_identity: <ticket from prev session>│
  │     - early_data extension                    │
  │     - key_share (for new handshake keys)      │
  │                                               │
  │──── Application Data (0-RTT) ─────────────────▶│  Sent BEFORE server responds
  │     GET /api/dashboard HTTP/1.1               │
  │     [encrypted with early_traffic_secret]     │
  │                                               │
  │◀─── ServerHello ──────────────────────────────│
  │◀─── ... (rest of normal 1-RTT handshake) ─────│
  │◀─── EndOfEarlyData ────────────────────────────│  Server signals 0-RTT accepted
  │◀─── Application Data (response) ──────────────│
```

**The security trade-off — replay attacks:**
```
Problem: 0-RTT data has no replay protection

In a normal TLS handshake:
  Both client_random and server_random contribute to key derivation
  Each session has a unique server_random → same request encrypted differently
  An attacker who records the ClientHello + 0-RTT cannot replay it —
  the server would generate a different random and the key derivation would differ

With 0-RTT:
  The early_traffic_secret is derived from the PSK alone — no server_random yet
  The 0-RTT data is encrypted with the SAME key material regardless of when replayed
  An attacker who records the ClientHello + 0-RTT can resend it to a different
  server instance (in a load-balanced cluster) — the ticket decrypts on any server,
  and the request replays successfully

Replay scenario in fintech:
  Client sends 0-RTT: POST /api/payments/initiate { amount: 10000, to: "acc-xyz" }
  Attacker records this encrypted 0-RTT data
  Attacker replays to a different server in the cluster (or later, if ticket not expired)
  → Payment initiated twice
  → Each replay costs the victim ₹10,000
```

**Correct usage policy for 0-RTT:**
```typescript
// In Node.js/Express with an HTTPS server:
// Control which routes accept 0-RTT early data

app.use((req, res, next) => {
  // req.socket.earlyData (or equivalent in your TLS library)
  // indicates this request arrived as 0-RTT data

  if (req.isEarlyData) {
    // Safe for 0-RTT: idempotent, read-only, non-sensitive GET requests
    const safeFor0RTT = req.method === 'GET' &&
      !req.path.startsWith('/api/payments') &&
      !req.path.startsWith('/api/transfers') &&
      !req.path.startsWith('/api/auth');

    if (!safeFor0RTT) {
      // Reject 0-RTT for state-changing or sensitive endpoints
      // Client will retry after handshake completes (automatic in HTTP clients)
      return res.status(425).json({ error: 'Too Early — retry after handshake' });
      // HTTP 425 Too Early is the RFC 8470 status code for this case
    }
  }
  next();
});

// NEVER send these as 0-RTT:
// POST /api/payments/  — replay = double payment
// POST /api/loans/apply — replay = double application + double credit bureau query
// POST /api/auth/login — replay leaks timing information about valid users
// PUT/DELETE anything  — state mutations with replay consequences

// Safe for 0-RTT:
// GET /api/loan-products   — read-only, idempotent
// GET /api/exchange-rates  — read-only, same response regardless of replay
// GET /static/*            — assets, definitely safe
```

## Section 2: Cipher Suites

**Q4. What is a cipher suite, how do you read a TLS 1.2 cipher suite name, and what are the components that must all work together?**
A: A cipher suite is a named combination of four cryptographic algorithms that together provide the security properties of a TLS session. In TLS 1.2, the cipher suite name encodes all four components:

```
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
│    │      │        │   │   │   │
│    │      │        │   │   │   └── PRF / MAC hash algorithm (SHA-256)
│    │      │        │   │   └────── Cipher mode (GCM = Galois/Counter Mode)
│    │      │        │   └────────── Key size in bits (128)
│    │      │        └────────────── Symmetric cipher (AES)
│    │      └─────────────────────── Authentication (RSA certificate)
│    └────────────────────────────── Key exchange (ECDHE)
└─────────────────────────────────── Protocol (TLS)

The four components and what each provides:

┌─────────────────┬──────────────────────────────────────────────────────────┐
│ Component       │ Purpose                                                  │
├─────────────────┼──────────────────────────────────────────────────────────┤
│ Key Exchange    │ How client and server establish a shared secret           │
│ (ECDHE/DHE/RSA) │ ECDHE/DHE → ephemeral; provides forward secrecy         │
│                 │ RSA → static; no forward secrecy                         │
├─────────────────┼──────────────────────────────────────────────────────────┤
│ Authentication  │ How the server proves it owns the certificate             │
│ (RSA/ECDSA/DSA) │ RSA: sign handshake with RSA private key                 │
│                 │ ECDSA: sign with elliptic curve private key              │
├─────────────────┼──────────────────────────────────────────────────────────┤
│ Symmetric Cipher│ How application data is encrypted after key exchange      │
│ (AES/ChaCha20)  │ AES-128-GCM, AES-256-GCM: AEAD (no separate MAC)        │
│                 │ AES-256-CBC: block cipher (requires separate MAC)        │
│                 │ ChaCha20-Poly1305: stream cipher (AEAD, no AES hardware) │
├─────────────────┼──────────────────────────────────────────────────────────┤
│ PRF/MAC Hash    │ Pseudorandom function for key derivation; MAC for CBC    │
│ (SHA-256/384)   │ GCM/AEAD modes: hash used only for PRF, not MAC         │
│                 │ CBC modes: hash also used for HMAC message authentication │
└─────────────────┴──────────────────────────────────────────────────────────┘
```

**Reading real cipher suite names:**
```
TLS_RSA_WITH_AES_128_CBC_SHA
  Key exchange: RSA (static — no forward secrecy)
  Auth: RSA
  Cipher: AES-128-CBC (block cipher — requires HMAC separately)
  PRF/MAC: SHA-1 (weak — deprecated)
  Status: PROHIBITED (no FS, weak MAC, weak PRF)

TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
  Key exchange: ECDHE (ephemeral — forward secrecy ✓)
  Auth: RSA certificate
  Cipher: AES-256-GCM (AEAD — authenticated encryption ✓)
  PRF: SHA-384
  Status: RECOMMENDED for TLS 1.2

TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305_SHA256
  Key exchange: ECDHE (forward secrecy ✓)
  Auth: ECDSA (elliptic curve — smaller keys, faster signatures ✓)
  Cipher: ChaCha20-Poly1305 (AEAD — no AES hardware required ✓)
  PRF: SHA-256
  Status: RECOMMENDED — especially for mobile devices without AES-NI
```

**Q5. How does TLS 1.3 simplify cipher suites, and what does removing the key exchange and authentication algorithm from the suite name mean architecturally?**
A: TLS 1.3 radically simplifies cipher suites by separating what was previously bundled together. In TLS 1.3, a cipher suite specifies **only the symmetric encryption algorithm and the hash function for HKDF**. Key exchange and authentication are handled by separate extensions:

```
TLS 1.2 cipher suite encodes ALL FOUR components:
  TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
  (one string must specify: KE + Auth + Cipher + Hash = tightly coupled)

TLS 1.3 cipher suite encodes ONLY TWO components:
  TLS_AES_256_GCM_SHA384
  TLS_AES_128_GCM_SHA256
  TLS_CHACHA20_POLY1305_SHA256
  (only: Cipher + Hash — loosely coupled)

Key exchange in TLS 1.3: negotiated via supported_groups + key_share extensions
  X25519 (Curve25519)   ← preferred, fastest, 128-bit security
  X448                  ← higher security, slower
  P-256 (secp256r1)     ← NIST curve, FIPS compliance
  P-384                 ← higher NIST security
  P-521                 ← rarely used
  FFDHE-2048/3072/4096  ← finite field DH (backward compat)

Authentication in TLS 1.3: negotiated via signature_algorithms extension
  ecdsa_secp256r1_sha256   ← ECDSA with P-256
  ecdsa_secp384r1_sha384   ← ECDSA with P-384
  rsa_pss_rsae_sha256      ← RSA-PSS (modern RSA padding)
  rsa_pss_rsae_sha384
  ed25519                  ← EdDSA (fast, simple, no parameter confusion)
  ed448
```

**Why this separation matters:**

```
TLS 1.2 coupling problem:
  Adding a new key exchange algorithm (X25519) requires defining new cipher suites:
  TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384 → still exists
  TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384 → separate suite for ECDSA
  If you add X448: must define X448_RSA, X448_ECDSA variants → combinatorial explosion

TLS 1.3 independence:
  TLS_AES_256_GCM_SHA384 works with ANY key exchange from supported_groups
  and ANY authentication from signature_algorithms
  Adding a new key exchange: just add it to supported_groups extension
  Adding a new auth algorithm: just add it to signature_algorithms
  No new cipher suite names needed

Total TLS 1.2 cipher suites defined: 300+ (most are combinations and variants)
  Many are insecure (export-grade, NULL, anonymous, RC4, DES, 3DES)
  Server misconfiguration risk: enabling an insecure suite by accident

Total TLS 1.3 cipher suites: 5 (all secure, AEAD-only)
  TLS_AES_128_GCM_SHA256
  TLS_AES_256_GCM_SHA384
  TLS_CHACHA20_POLY1305_SHA256
  TLS_AES_128_CCM_SHA256        (IoT / constrained devices)
  TLS_AES_128_CCM_8_SHA256      (IoT / short authentication tag)
  → No possibility of accidentally enabling a weak cipher in TLS 1.3
```

**Q6. What is forward secrecy (perfect forward secrecy), why does ephemeral Diffie-Hellman provide it, and what is the attack that non-ephemeral RSA key exchange enables?**
A: Forward secrecy means that compromising the server's long-term private key in the future does not allow decryption of past recorded sessions. It is the single most important security property distinguishing modern cipher suites from legacy ones.

**How static RSA key exchange works (no forward secrecy):**
```
TLS 1.2 with TLS_RSA_WITH_AES_256_CBC_SHA:

Client generates a random pre_master_secret (48 bytes)
Client encrypts it: RSA_encrypt(server_public_key, pre_master_secret)
Client sends encrypted pre_master_secret to server
Server decrypts: RSA_decrypt(server_private_key, encrypted_pre_master_secret)
Both derive session keys from pre_master_secret

The attack — passive recording + future key compromise:
  1. Nation-state / attacker records ALL TLS traffic to mybank.com (easy with MITM infra)
     Traffic is encrypted → unreadable at recording time
  2. Five years later: mybank.com's private key leaks (employee mistake, court order,
     cryptographic break, server compromise)
  3. Attacker retroactively decrypts ALL recorded sessions:
     RSA_decrypt(leaked_private_key, each_recorded_pre_master_secret)
     → session keys for every recorded session
     → plaintext of every transaction, credential, PII exchange from those sessions
  4. Every past customer interaction is now readable — retroactively

This is the "record now, decrypt later" attack used by nation-state actors.
```

**How ECDHE provides forward secrecy:**
```
TLS 1.2/1.3 with ECDHE:

Server generates ephemeral ECDH keypair: (server_ephemeral_private, server_ephemeral_public)
Client generates ephemeral ECDH keypair: (client_ephemeral_private, client_ephemeral_public)

Key exchange:
  shared_secret = ECDH(client_ephemeral_private, server_ephemeral_public)
                = ECDH(server_ephemeral_private, client_ephemeral_public)
  [Diffie-Hellman property: both parties arrive at same value without transmitting it]

Session keys derived from shared_secret + randoms
Ephemeral keys discarded immediately after use

The attack fails:
  Attacker records traffic and later obtains server's long-term private key
  Long-term private key: signs the ServerKeyExchange (proves server identity)
  Long-term private key: DOES NOT decrypt the ephemeral key exchange
  The ephemeral server_ephemeral_private never left the server's memory
  It was discarded after use → cannot be obtained retroactively
  Attacker has the recording + the long-term key → still cannot decrypt
  → Forward secrecy: past sessions are protected even after key compromise
```

**Why "perfect" is a misnomer:**
```
"Perfect Forward Secrecy" (PFS) is the common name but somewhat misleading.
"Forward secrecy" is more accurate — it protects past sessions, not future ones.
If the server's long-term key is compromised NOW:
  → Active MITM attacks become possible from NOW on (attacker can impersonate server)
  → Past sessions (before compromise) remain protected

TLS 1.3 mandates forward secrecy: ALL key exchange is ephemeral.
TLS_RSA_ cipher suites are completely removed from TLS 1.3.
Any TLS 1.3 connection has forward secrecy by construction.
```

## Section 3: Certificate Validation

**Q7. What is the X.509 certificate chain, and what are the five checks a TLS client must perform to validate a server certificate?**
A: An X.509 certificate chain is a hierarchy of certificates where each certificate is signed by the one above it, ultimately rooted in a trusted Certificate Authority (CA) whose public key is pre-distributed in the OS or browser trust store. The chain allows an unknown server certificate to be trusted transitively through known CAs.

```
Chain structure (most common: 3 levels):

Root CA Certificate (self-signed)
  Subject: DigiCert Global Root CA
  Issuer:  DigiCert Global Root CA  ← self-signed
  Public Key: RSA-4096
  Valid: 2006-2031
  Stored in: OS trust store / browser trust store
  (Never served by the server — already locally trusted)
        │
        │ signs (Root CA's private key signs Intermediate's public key)
        ▼
Intermediate CA Certificate
  Subject: DigiCert TLS RSA SHA256 2020 CA1
  Issuer:  DigiCert Global Root CA
  Public Key: RSA-2048
  Valid: 2021-2031
  → Served by the server in the Certificate message
        │
        │ signs (Intermediate CA's private key signs End-Entity's public key)
        ▼
End-Entity (Leaf) Certificate
  Subject: CN=mybank.com
  Issuer:  DigiCert TLS RSA SHA256 2020 CA1
  Public Key: RSA-2048 or ECDSA P-256
  Valid: 2024-2025
  SANs: mybank.com, www.mybank.com, api.mybank.com
  → Served by the server
```

**The five validation checks:**

**Check 1 — Chain construction and signature verification:**
```
Client receives: [leaf_cert, intermediate_cert] from server
Client has: root_cert in its local trust store

Verify signatures upward through the chain:
  verify(intermediate_cert.public_key, leaf_cert.signature) → valid ✓
  verify(root_cert.public_key, intermediate_cert.signature) → valid ✓
  root_cert in trust store → trusted ✓

Failure modes:
  Server sends incomplete chain (missing intermediate) → chain cannot be built
  Signature is invalid → certificate was tampered with
  Root not in trust store → untrusted CA
```

**Check 2 — Validity period:**
```
leaf_cert.notBefore ≤ current_time ≤ leaf_cert.notAfter

Common failures:
  Expired certificate: leaf_cert.notAfter < now → TLS error
  Certificate not yet valid: leaf_cert.notBefore > now (misconfigured server clock)
  Intermediate cert expired: entire chain invalid even if leaf is valid
```

**Check 3 — Hostname / Subject Alternative Name (SAN) matching:**
```
Compare the server hostname to:
  1. SAN extension (dNSName entries) — preferred; required by modern clients
  2. CN (Common Name) — deprecated; ignored by Chrome/Firefox since 2017

Matching rules:
  Exact match:    mybank.com matches SAN mybank.com ✓
  Wildcard:       api.mybank.com matches SAN *.mybank.com ✓
  Wildcard scope: sub.api.mybank.com does NOT match *.mybank.com ✗
                  (wildcards only cover one label)
  IP addresses:   must be in SAN iPAddress field, not CN

Failure: user connects to api.mybank.com; certificate has SAN for mybank.com only
→ Hostname mismatch → TLS error (SSL_ERROR_BAD_CERT_DOMAIN)
```

**Check 4 — Revocation status:**
```
A certificate may be revoked before its natural expiry:
  Private key compromise, CA mis-issuance, domain ownership change

Two revocation mechanisms:

CRL (Certificate Revocation List):
  CA periodically publishes a signed list of revoked certificate serial numbers
  Client downloads the CRL from the distribution point in the certificate
  Client checks if leaf_cert.serialNumber is in the CRL
  Problem: CRLs can be megabytes large; cached for days → stale revocation info

OCSP (Online Certificate Status Protocol):
  Client queries the CA's OCSP responder with the certificate's serial number
  Responder returns: "good", "revoked", or "unknown"
  Real-time but: OCSP responder is a single point of failure + latency per handshake
  OCSP Stapling (better): server queries its own OCSP at cert renewal/startup
    and "staples" the signed OCSP response to the TLS handshake
    Client verifies the stapled response — no client-to-OCSP-responder round trip

Hard fail vs. soft fail:
  Hard fail: if revocation check fails (OCSP unreachable) → reject connection
  Soft fail: if revocation check fails → proceed anyway (common browser default)
  Soft fail means: an attacker can block OCSP responses to prevent revocation detection
```

**Check 5 — Key usage and extended key usage extensions:**
```
Key Usage extension: what operations the key is authorized for
  digitalSignature, keyEncipherment, keyAgreement, keyCertSign, cRLSign

Extended Key Usage (EKU): specific application purposes
  serverAuthentication (OID 1.3.6.1.5.5.7.3.1) — MUST be present for TLS server certs
  clientAuthentication                           — for mutual TLS client certs
  codeSigning                                    — for code signing certs
  emailProtection                                — for S/MIME certs

A code-signing certificate must not be accepted for TLS server auth.
A client certificate must not be accepted as a server certificate.
These constraints prevent cross-context certificate abuse.
```

**Q8. What is Certificate Transparency (CT), how does it work, and why is it a critical defense against misissued certificates?**
A: Certificate Transparency is a public, append-only, cryptographically verifiable log of all issued TLS certificates. It was created after a series of CA compromise incidents (DigiNotar 2011, Comodo 2011, ANSSI 2013) demonstrated that a compromised CA could issue fraudulent certificates for any domain without detection.

**How CT works:**
```
Certificate issuance with CT:

1. Domain owner generates a CSR (Certificate Signing Request)
2. CA validates domain ownership (DV) or organization (OV/EV)
3. CA creates the certificate and submits it to one or more CT logs:
   POST https://ct.googleapis.com/logs/argon2024/ct/v1/add-chain
   Body: [leaf_cert + intermediates]

4. CT log returns a Signed Certificate Timestamp (SCT):
   SCT = {
     log_id:    identifier of this CT log
     timestamp: when the log committed to include this cert
     signature: log's digital signature over (cert_hash, timestamp)
   }
   The SCT is a promise: "This cert will appear in our Merkle tree"

5. CA embeds the SCTs in the certificate (or delivers via TLS extension or OCSP staple)

6. Browser receives the certificate + SCTs:
   Verifies SCT signatures against known log public keys
   If valid: certificate was submitted to public logs → CT policy satisfied

7. Anyone can monitor CT logs for certificates issued for their domain:
   facebook.com monitors logs; sees cert for login.facebook.com.evil.com → alerts
   crt.sh, censys.io: public CT log search engines
```

**Why CT defeats misissued certificate attacks:**
```
Attack without CT:
  Attacker compromises a CA (or social-engineers issuance) → gets cert for mybank.com
  No one knows → MITM attack proceeds indefinitely
  Bank cannot detect → customers are deceived

Attack with CT:
  Attacker gets cert for mybank.com from compromised CA
  CA must submit to CT log or browsers reject the cert (Chrome requires 2+ SCTs)
  CT log is public → mybank.com's Certificate Transparency monitoring detects
  the unexpected issuance within minutes/hours
  Bank revokes the fraudulent cert, reports the CA → CA is distrusted

CT properties:
  Append-only: entries cannot be deleted or modified (Merkle tree consistency proof)
  Auditable: anyone can verify all entries are consistent
  Monitored: domain owners can subscribe to alerts for new certs on their domains
```

**Q9. What is OCSP stapling, why is it superior to client-initiated OCSP, and how do you configure it in Nginx for a Node.js backend?**
A: OCSP stapling moves the revocation check from the client to the server, solving the privacy, latency, and reliability problems of client-initiated OCSP:

**Problems with client-initiated OCSP:**
```
Privacy:
  Client contacts the CA's OCSP responder for EVERY TLS connection
  CA learns: which client IP visited which website, at what time
  OCSP responder can track browsing history across all sites using that CA

Latency:
  OCSP query adds a network round trip before TLS completes
  OCSP responder may be slow or geographically distant
  On a 200ms RTT link: +200ms added to every new connection

Reliability:
  OCSP responder is a single point of failure
  If OCSP responder is down: soft-fail browsers proceed anyway (revocation defeated)
  Hard-fail: connection refused → site appears down → DoS via OCSP disruption

OCSP Stapling — server-side solution:
  Server contacts the OCSP responder (server-to-CA network — fast, controlled)
  Server caches the OCSP response (valid for hours)
  Server includes ("staples") the OCSP response in the TLS handshake
  Client verifies the stapled response (signed by CA → trusted)
  Client never contacts the OCSP responder → no privacy leak, no latency, no SPOF
```

**Nginx configuration for OCSP stapling (fronting a Node.js backend):**
```nginx
# /etc/nginx/sites-available/mybank.conf

    listen 443 ssl;
    server_name api.mybank.com;

    # TLS certificate chain
    ssl_certificate     /etc/ssl/certs/mybank_fullchain.pem;  # leaf + intermediates
    ssl_certificate_key /etc/ssl/private/mybank.key;

    # TLS protocol versions — TLS 1.2 minimum; TLS 1.3 preferred
    ssl_protocols TLSv1.2 TLSv1.3;

    # TLS 1.2 cipher suites — forward secrecy only, AEAD only
    ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;

    ssl_stapling_verify on;             # Verify the stapled response
    ssl_trusted_certificate /etc/ssl/certs/mybank_chain.pem;  # CA chain for verification
    resolver 1.1.1.1 8.8.8.8 valid=300s;   # DNS for OCSP responder hostname resolution
```

**Q11. What is mutual TLS (mTLS), how does it differ from one-way TLS, and when do you use it in a microservices fintech architecture?**
A: Standard TLS authenticates only the server. Mutual TLS requires both parties — server and client — to present and validate X.509 certificates. This provides cryptographic service-to-service authentication that cannot be spoofed by network-level access alone.

**One-way TLS (standard) vs. mTLS:**
```
One-way TLS:
  Server → presents certificate → client validates
  Client → presents nothing → server cannot cryptographically verify client identity
  Protection: encryption in transit + server identity assurance
  Authorization: client identity must be established via other means (JWT, API key)

Mutual TLS:
  Server → presents certificate → client validates
  Client → presents certificate → server validates
  Protection: encryption in transit + bidirectional identity assurance
  Authorization: service identity is the certificate's Subject/SAN

Handshake addition for mTLS (after ServerHelloDone in TLS 1.2):
  Server sends:    CertificateRequest  ← asks client for its cert
  Client sends:    Certificate         ← client's cert (signed by trusted CA)
                   CertificateVerify   ← client signs handshake hash with its private key
  Server verifies: client cert chain, validity, signature
```

**When to use mTLS in fintech microservices:**
```
Service mesh (Istio, Linkerd):
  All pod-to-pod communication encrypted and authenticated with mTLS
  Each service gets a SPIFFE SVID (short-lived X.509 cert, rotated every 24h)
  Istio PeerAuthentication: STRICT mode → reject any non-mTLS connection
  No service can impersonate another — certificate is the identity

External payment gateway integration (Razorpay, JusPay):
  Payment processors often require mTLS for outbound webhook delivery
  Your server presents a client cert; their server validates it
  Prevents unauthorized parties from mimicking your service

Internal admin APIs:
  Admin endpoints accessible only to services with an admin client cert
  Even if an attacker gains network access, they cannot call admin APIs
  without the client cert (which is stored in a secrets manager, not on disk)

Kubernetes service-to-service:
  loans-service → payments-service: mTLS via service mesh
  Each service's cert has SAN: spiffe://cluster.local/ns/prod/sa/loans-service
  payments-service validates that only loans-service (by SPIFFE ID) can call it
```

## Section 5: Common Vulnerabilities and Downgrade Attacks

**Q12. What are POODLE, BEAST, SWEET32, and Heartbleed, and what do they demonstrate about the evolution from TLS 1.2 to TLS 1.3?**
A: Each of these attacks exploited specific weaknesses in TLS 1.2 and earlier cipher suites. TLS 1.3 was designed with these attacks in mind, removing the vulnerable components entirely:

**POODLE (Padding Oracle On Downgraded Legacy Encryption) — 2014:**
```
Targets: SSLv3, TLS 1.0/1.1/1.2 with CBC mode cipher suites
Mechanism:
  CBC mode requires padding to fill the last block to the block size
  SSLv3: padding bytes can be any value (the last byte encodes padding length)
  An attacker who can force repeated requests (e.g., via JavaScript in browser)
  and observe whether decryption succeeds or fails (padding oracle)
  can recover one byte of plaintext per ~256 requests

Impact: session cookie theft → account takeover in browser attacks
TLS 1.3 fix: CBC mode cipher suites completely removed
             All TLS 1.3 ciphers are AEAD (no padding oracle possible)
             SSLv3 and TLS 1.0/1.1 completely removed from TLS 1.3
```

**BEAST (Browser Exploit Against SSL/TLS) — 2011:**
```
Targets: TLS 1.0 with CBC mode (IV reuse vulnerability)
Mechanism:
  TLS 1.0 CBC: the IV for each record is the last ciphertext block of the previous record
  This is predictable → chosen-plaintext attack → plaintext recovery
  Requires JavaScript in browser, MitM position, ability to observe ciphertext

Impact: HTTP cookie theft
TLS 1.3 fix: TLS 1.0 removed; AEAD-only → no CBC, no IV reuse issue
TLS 1.2 mitigation: TLS 1.2 CBC uses explicit per-record IVs (not the predictable chained IV)
```

**SWEET32 — 2016:**
```
Targets: 64-bit block ciphers: 3DES (DES-EDE-CBC), Blowfish
Mechanism:
  Birthday bound: after 2^32 blocks (~32GB of data), collisions in 64-bit blocks become likely
  With CBC mode, block collisions leak XOR of plaintexts
  Long-lived HTTPS sessions (days) with high-volume data hit this bound

Impact: plaintext recovery in long-lived connections (e.g., VPN tunnels)
TLS 1.3 fix: 3DES and Blowfish completely removed; AES (128-bit blocks) and ChaCha20 immune
```

**Heartbleed (CVE-2014-0160) — 2014:**
```
Targets: OpenSSL 1.0.1 through 1.0.1f; the TLS heartbeat extension
Mechanism:
  TLS Heartbeat: client sends {type: heartbeat, payload: "hello", length: 65535}
  length field claims 65535 bytes but payload is only 5 bytes
  Vulnerable OpenSSL: reads 65535 bytes from memory starting at the payload buffer
  → Returns 65535 bytes of server memory including:
    private keys, session tokens, passwords, user data from other connections

Impact: catastrophic — private key extraction without server compromise needed
Note: not a TLS protocol flaw — an implementation bug in OpenSSL
TLS 1.3 connection: unaffected IF OpenSSL is patched; the TLS version is irrelevant
Lesson: TLS security depends on BOTH the protocol version AND the implementation
```

**What these attacks demonstrate about the TLS 1.3 design philosophy:**
```
TLS 1.2 accumulated vulnerabilities from:
  - Too many optional cipher suites (some inevitably insecure)
  - Legacy algorithm support for backward compatibility
  - Non-AEAD modes that enable padding oracles and IV reuse
  - Stateful CBC that requires careful IV management

TLS 1.3 response:
  - Remove every algorithm with known practical attacks: RC4, 3DES, CBC, MD5, SHA-1
  - Mandate AEAD-only (GCM, ChaCha20-Poly1305, CCM) — no padding oracles
  - Remove export-grade, anonymous, NULL cipher suites
  - Encrypt more of the handshake — reduces attack surface for downgrade attacks
  - Formal verification of the protocol's security properties (ProVerif, Tamarin)
  → TLS 1.3 is the first TLS version to be formally verified before deployment
```

**Q13. What is a downgrade attack, how does TLS_FALLBACK_SCSV work, and what mechanism in TLS 1.3 prevents version negotiation downgrade?**
A: A downgrade attack tricks the client and server into using an older, weaker protocol version or cipher suite than both support — allowing the attacker to then exploit known weaknesses in the downgraded version.

**How a downgrade attack works against TLS 1.2:**
```
Without protection:
  1. Client sends ClientHello: supported_versions = [TLS 1.2, TLS 1.1, TLS 1.0]
  2. Attacker (MitM) intercepts and modifies to: supported_versions = [TLS 1.0]
  3. Server, seeing only TLS 1.0 offered, accepts: ServerHello version = TLS 1.0
  4. Connection proceeds with TLS 1.0 → BEAST or POODLE attacks now applicable
  5. Neither client nor server can detect that the version list was modified
     (because the ClientHello was not yet authenticated)
```

**TLS_FALLBACK_SCSV (Signaling Cipher Suite Value) — the TLS 1.2 mitigation:**
```
TLS_FALLBACK_SCSV = cipher suite value 0x5600 (not an actual cipher — a signal)

How it works:
  Client: "I support TLS 1.2 but I'm retrying with TLS 1.1 (my ClientHello says 1.1)"
  Client includes TLS_FALLBACK_SCSV in its cipher suite list to signal the downgrade
  Server: "You included FALLBACK_SCSV but you're offering TLS 1.1 and I support 1.2"
  Server responds with: inappropriate_fallback alert → connection aborted

The signal tells the server: "This is a fallback attempt, not the client's best offer."
A legitimate fallback from TLS 1.2 to TLS 1.1 (rare) uses this signal.
An attacker-induced downgrade cannot know to include FALLBACK_SCSV → server detects it.

Limitation: only works if both client and server support FALLBACK_SCSV.
            Does not prevent downgrade attacks against servers that don't implement it.
```

**TLS 1.3's built-in downgrade prevention:**
```
TLS 1.3 uses a cryptographic sentinel in the ServerHello.Random field:

If server supports TLS 1.3 but negotiates TLS 1.2 (with a TLS 1.3-capable client):
  server_random[24:32] = 44 4F 57 4E 47 52 44 00  ("DOWNGRD\x00")

If server supports TLS 1.3 but negotiates TLS 1.1 or lower:
  server_random[24:32] = 44 4F 57 4E 47 52 44 01  ("DOWNGRD\x01")

A TLS 1.3-capable client that receives a TLS 1.2 ServerHello checks:
  if server_random[24:32] == DOWNGRD_SENTINEL:
    → Server signaled it supports TLS 1.3 but we're negotiating 1.2
    → Attacker must have modified the ClientHello to remove TLS 1.3 support
    → Abort: inappropriate_fallback

Why this works:
  The ServerHello.Random is authenticated by the Finished message HMAC
  The HMAC covers all handshake messages including server_random
  An attacker cannot both: modify the sentinel to avoid detection AND
  produce a valid Finished HMAC (they don't have the session keys)
  → Cryptographically enforced downgrade prevention, not just a signal
```

## Section 6: Certificate Management and Operational Concerns

**Q14. What is certificate pinning, when is it appropriate for a fintech mobile app, and what are the operational risks that make it dangerous to implement naively?**
A: Certificate pinning is the practice of hardcoding expected certificate or public key information into a client application, rejecting any TLS connection where the presented certificate doesn't match — even if the certificate is validly issued by a trusted CA.

**How pinning works:**
```
Hash the expected certificate's public key (SPKI — Subject Public Key Info):
  pin = base64(SHA-256(subjectPublicKeyInfo(cert.public_key)))

On each connection:
  Extract the presented certificate's SPKI hash
  Compare against the expected pin(s)
  If no match → reject connection (even if cert is valid, trusted, not expired)

Implementation in Node.js (manual):
```
```typescript
import https  from 'https';
import crypto from 'crypto';
import tls    from 'tls';

// Pre-computed SHA-256 hashes of the public keys we trust
// Include: current cert pin + backup pin (next cert, already generated)
const TRUSTED_PINS = new Set([
  'sha256//Ku7oBqB5kFobB3yTe8FVahlKyJkzQTuoqGN6kzGnVv0=',  // Current
  'sha256//Bjdh8g6Ku7oBqBiJkzQTuoqGN6kzGne8FVahlKyJkz1=',  // Backup (next cert)
]);

function computeSpkiPin(cert: tls.PeerCertificate): string {
  const spki     = cert.raw; // DER-encoded certificate
  const pubKey   = crypto.createPublicKey({ key: spki, format: 'der', type: 'spki' });
  const spkiDer  = pubKey.export({ format: 'der', type: 'spki' });
  const hash     = crypto.createHash('sha256').update(spkiDer).digest('base64');
  return `sha256//${hash}`;
}

const pinnedAgent = new https.Agent({
  checkServerIdentity: (hostname, cert) => {
    // Standard hostname validation still runs
    const standardError = tls.checkServerIdentity(hostname, cert);
    if (standardError) return standardError;

    // Additional pin check
    const pin = computeSpkiPin(cert);
    if (!TRUSTED_PINS.has(pin)) {
      return new Error(`Certificate pin mismatch. Got: ${pin}`);
    }
    return undefined; // Validation passed
  },
});
```

**When pinning is appropriate:**
```
High-value fintech apps:
  Mobile banking apps, payment apps, trading platforms
  The attacker surface: corporate MITM proxies, compromised CA, nation-state interception
  Users may be on networks with transparent SSL inspection (corporate, ISP-level)
  Pinning prevents these even if the inspecting cert is "validly" issued

Appropriate when:
  Certificate rotation is under tight operational control (you control the CA / cert lifecycle)
  The app has a reliable update mechanism (to push new pins before cert rotation)
  You have a tested pin rotation procedure
  The operational risk is acceptable (see below)
```

**Operational risks that make naive pinning dangerous:**
```
Risk 1 — Certificate rotation breaks the app:
  Certificate expires → renewed with a different key pair → new pin needed
  App with old pin: ALL connections fail → app is completely broken for all users
  Until new app version with updated pin is deployed and adopted → days to weeks of breakage

  This happened: PayPal, Snapchat, Twitter have all had pin-related outages

Risk 2 — Pin burns (key compromise):
  Server private key is compromised → must rotate immediately
  Users running old app version: new cert has different pin → app broken

Risk 3 — CA infrastructure pinning vs. leaf cert pinning:
  If you pin the leaf cert: rotate cert → must update app
  If you pin the intermediate CA: more flexibility but pins a CA, not your specific cert
  If you pin your own CA (self-issued): maximum control; most operational burden

Mitigation — backup pins:
  Always include at least 2 pins: current + next (pre-generated key pair)
  Before rotating the cert: deploy app update with both old and new pins
  After cert rotation: deploy app update removing old pin
  This requires coordinated app + cert rotation cycles

Mitigation — Max-Age header (HPKP was the HTTP header version; now deprecated):
  HPKP (HTTP Public Key Pinning) was deprecated because one misconfiguration
  could permanently lock users out → the entire concept of server-sent pin headers
  is now abandoned; client-side pinning in the app is the correct approach

Alternative for most cases — Certificate Transparency monitoring:
  Instead of pinning (rigid), monitor CT logs for unexpected certs on your domain
  If an attacker gets a fraudulent cert: you detect it via CT monitor → revoke
  No app changes needed; more operationally flexible; detects mis-issuance
  Appropriate for: web apps, low-risk APIs; less appropriate for: mobile banking
```

```typescript
  const socket = tls.connect({ host: hostname, port: 443, servername: hostname });
  const cert   = socket.getPeerCertificate();
  const expiry = new Date(cert.valid_to);
  const daysLeft = (expiry.getTime() - Date.now()) / (1000 * 60 * 60 * 24);

  if (daysLeft < 14) {
    await alertingService.critical(`${hostname} cert expires in ${daysLeft.toFixed(0)} days`);
  }

  socket.end();
}
```

## Quick Reference Table

| Aspect | TLS 1.2 | TLS 1.3 |
|---|---|---|
| **Full handshake RTTs** | 2 RTT | 1 RTT |
| **Resumption RTTs** | 1 RTT (session ID / tickets) | 0 RTT (PSK early data, with replay caveat) |
| **Key exchange** | RSA (no FS), DHE, ECDHE | ECDHE / X25519 only (FS mandatory) |
| **Forward secrecy** | Optional (if ECDHE chosen) | Mandatory (always) |
| **Cipher suite count** | 300+ (many insecure) | 5 (all AEAD, all secure) |
| **Cipher modes** | CBC, GCM, CCM, RC4, 3DES | AEAD only (GCM, ChaCha20, CCM) |
| **Handshake encryption** | Certificate sent in plaintext | Certificate encrypted after ServerHello |
| **Key derivation** | PRF (HMAC-based) | HKDF (extract-and-expand) |
| **Server authentication** | In cipher suite (RSA/ECDSA) | Via signature_algorithms extension |
| **Downgrade protection** | TLS_FALLBACK_SCSV (optional) | Cryptographic sentinel in server_random |
| **Removed algorithms** | None (backward compat) | RSA key exchange, CBC, SHA-1, MD5, RC4, 3DES, export |
| **Formal verification** | No | Yes (ProVerif, Tamarin) |
| **POODLE/BEAST/SWEET32** | Possible (if CBC enabled) | Impossible (no CBC, no 3DES) |
| **Session tickets** | Yes (forward secrecy concern) | Yes (PSK — improved key schedule) |

**Tip for the interview:** At 5 YOE, TLS questions go well beyond "1.3 is faster and more secure." The signal the examiner looks for: the **specific mechanism behind 1-RTT** — the speculative key_share in ClientHello (Q2) — that is the precise architectural change, not just "improved negotiation." Know **forward secrecy with the retroactive decryption scenario** (Q6) — the "record now, decrypt later" framing is exactly how nation-state threat models are discussed. For cipher suites, be able to **read a TLS 1.2 cipher suite name** and explain each component (Q4), then explain why TLS 1.3 only specifies two components (Q5) — this shows you understand the design, not just the outcome. In a fintech context, **0-RTT replay attacks on payment endpoints** (Q3 — HTTP 425 Too Early) and **mTLS for service-to-service authentication** (Q11 with SPIFFE IDs) connect the protocol directly to your microservices architecture. The **certificate expiry incident scenario** (Q15) is a favorite senior-level question — the Prometheus alerting rules and ACM auto-renewal answer shows operational maturity beyond just "set up certbot."
