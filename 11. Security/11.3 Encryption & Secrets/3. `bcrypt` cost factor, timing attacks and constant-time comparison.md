## Section 1: Password Hashing Fundamentals

**Q1. Why is password hashing a distinct problem from general-purpose cryptographic hashing, and why do algorithms like SHA-256 fail at it?**
A: General-purpose cryptographic hash functions (SHA-256, SHA-3, MD5) are designed to be **fast** — they process gigabytes per second on commodity hardware. That speed is exactly what makes them catastrophically wrong for password hashing.

```
The threat model for stored passwords:

  Your database is breached. An attacker has a dump of (username, hashed_password) rows.
  They cannot log in directly — they need to reverse the hashes.
  Reversing a cryptographic hash is computationally infeasible... unless they guess.

  Attack: offline dictionary / brute-force attack
    1. Take a wordlist: "password", "123456", "letmein", "Summer2024!", ...
    2. Hash each candidate with the same algorithm as the target system.
    3. Compare against stolen hashes. Match → cracked password.

  How fast is this attack with SHA-256?

    Modern GPU (RTX 4090):      ~22 billion SHA-256 hashes per second
    SHA-256("password123")      → computed in 0.000000045 ms
    10-character password space → ~95^10 = 5.99 × 10^19 combinations
    Time to exhaust at 22B/s    → ~86 years — sounds safe?

  Reality check — humans don't use random passwords:
    RockYou dataset (2009):     14 million real passwords
    50% of users:               password from top 1000 list
    At 22B SHA-256/s:           Top 1 million passwords cracked in < 0.05ms
    Combined with rules:        "Password1!", "p@ssw0rd" → cracked in seconds

  Password hashing requirement:
    The hash function must be SLOW — slow enough that brute-force is impractical
    even with a stolen database and dedicated hardware.
    SHA-256 at 22B/s = wrong tool.
    bcrypt at ~100/s per GPU core = right tool.
```

The second problem with SHA-256 for passwords: it is **deterministic and stateless**. Two users with the same password produce the same hash. An attacker who cracks one hash cracks all identical passwords simultaneously. A **rainbow table** — a precomputed (password → hash) lookup — lets the attacker skip computation entirely: look up the hash, read the plaintext in O(1).

Password hashing requires three properties that SHA-256 lacks:

```
1. Slowness (work factor):
   The hash should take meaningful CPU/memory time, configurable as hardware improves.

2. Salting (uniqueness):
   Each password hash must be unique, even for identical passwords.
   Defeats rainbow tables and cross-user cracking.

3. Memory-hardness (resistance to GPU/ASIC parallelism):
   GPUs win by running millions of parallel threads. Memory-bound operations
   defeat this because GPU memory bandwidth is the bottleneck, not compute.
   bcrypt: moderate memory-hardness (4KB state).
   Argon2id: strong memory-hardness (configurable GB of RAM).
```

**Q2. What are the purpose-built password hashing algorithms, and how do they compare?**
A:

```
bcrypt (1999 — Niels Provos & David Mazières):
  Based on Blowfish cipher's expensive key schedule.
  Cost factor: 2^cost iterations of the key setup (cost = 10 → ~1024 rounds).
  Salt: 128-bit, embedded in the output string.
  Output: 60-character string: $2b$10$<22-char salt><31-char hash>
  Memory: ~4KB state — modest, not memory-hard by modern standards.
  Password length limit: 72 bytes (characters beyond 72 are silently ignored).
  Status: production standard; widely supported; conservative GPU resistance.
  Use when: default choice for new applications; every major language has a
            well-audited library.

scrypt (2009 — Colin Percival):
  Designed to be memory-hard: requires large amounts of RAM, not just CPU time.
  Parameters: N (CPU/memory cost), r (block size), p (parallelism).
  Typical: N=32768, r=8, p=1 → ~32MB RAM per hash.
  GPU resistance: much stronger than bcrypt — GPUs have limited VRAM per core.
  Weakness: parameter tuning is difficult; N, r, p interact in non-obvious ways.
  Status: solid but scrypt's parameter space is less accessible than Argon2.

Argon2id (2015 — winner of Password Hashing Competition):
  Three variants: Argon2d (GPU-resistant), Argon2i (side-channel-resistant),
                  Argon2id (hybrid — recommended for general use).
  Parameters: memory (KB), iterations (time cost), parallelism (threads).
  Typical: memory=65536 (64MB), iterations=3, parallelism=4.
  Memory-hard: large, configurable RAM requirement defeats GPU/ASIC parallelism.
  NIST recommendation (SP 800-63B): preferred algorithm for new systems.
  Status: the modern recommendation; RFC 9106 (2021).

PBKDF2 (2000 — RSA Security):
  Applies a PRF (usually HMAC-SHA256) many times (iterations).
  Parameters: iteration count, salt, PRF.
  Typical: 600,000 iterations (OWASP 2023 recommendation for PBKDF2-HMAC-SHA256).
  No memory-hardness: runs efficiently on GPU — each iteration is cheap.
  Status: acceptable for compliance reasons (FIPS 140-2 certified);
          weaker than bcrypt/Argon2id when attacker has GPU hardware.
  Use when: FIPS compliance is required and Argon2 is not approved yet.

Algorithm       GPU resistance   Memory-hard   Parameter simplicity   Modern recommendation
──────────────  ───────────────  ────────────  ─────────────────────  ─────────────────────
MD5/SHA-256     None             No            N/A                    NEVER for passwords
PBKDF2          Low              No            Medium                 Compliance only
bcrypt          Moderate         Partial       Simple (one number)    YES — default choice
scrypt          High             Yes           Complex                Use if Argon2 unavailable
Argon2id        Very high        Yes           Simple (3 params)      YES — preferred for new systems
```

## Section 2: bcrypt In Depth

**Q3. How does bcrypt work internally, and what makes it inherently slow?**
A: bcrypt is built around EksBlowfish — an "expensive key setup" variant of the Blowfish block cipher. The slowness is not from iterating a fast hash function; it comes from an expensive key schedule that cannot be parallelized or shortcut.

```
bcrypt algorithm structure:

1. Generate a 128-bit random salt.

2. Run EksBlowfishSetup(cost, salt, password):
   a. Initialize Blowfish P-array (18 × 32-bit subkeys) and S-boxes (4 × 256 entries)
      with the digits of π — a "nothing-up-my-sleeve" starting state.
   b. XOR P-array entries with the password bytes (cycling if password < 72 bytes).
   c. Run ExpandKey(salt) — mix the salt into the state.
   d. Repeat 2^cost times:
      ExpandKey(password)   ← expensive: updates all P-entries and S-boxes
      ExpandKey(salt)       ← expensive: same operation with salt
   → This loop is the work factor. cost=10 → 1,024 iterations of two full key setups.
   → Each ExpandKey touches the entire 4KB state — no shortcut, no parallelism.

3. Encrypt the magic plaintext "OrpheanBeholderScryDoubt" 64 times using
   the EksBlowfish state produced in step 2.

4. Encode: $2b$ + cost + $ + base64(salt) + base64(ciphertext)
   Result:   $2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy

Why it cannot be made fast with hardware:
  - The 4KB EksBlowfish state must be held in fast memory (CPU cache).
  - Each ExpandKey reads/writes the entire state — sequential, cache-dependent.
  - The state from step N is the input to step N+1 — inherently serial.
  - GPUs are optimized for parallel, independent operations. bcrypt's serial
    state dependency and cache-size requirement limit GPU parallelism.
  - ASICs can be built for bcrypt (Antminer B3 existed) but are expensive to
    build, and raising the cost factor outpaces their advantage.
```

```python
# bcrypt output format anatomy

hash = "$2b$12$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy"
#       ^^^  ^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#        |    |   |
#        |    |   └─ 53 chars: 22 salt + 31 hash (base64-encoded)
#        |    └───── cost factor (12 → 2^12 = 4096 iterations)
#        └────────── algorithm version ($2b$ is correct modern version)

# Versions:
# $2$   — original; has a bug with passwords containing null bytes
# $2a$  — common; has a bug on some implementations with chars > 127
# $2b$  — correct; use this
# $2y$  — PHP-specific alias for $2b$; safe
```

**Q4. What is the bcrypt cost factor, how do you choose it, and how do you update it over time?**
A: The cost factor (also called work factor or rounds) is the exponent in `2^cost` — the number of times the key schedule iterates. It directly controls how long each hash takes to compute. It is stored in the hash string, so you don't need a separate configuration value to verify an existing hash.

```python
import bcrypt
import time

# Measuring cost factor timing on your hardware:

def benchmark_bcrypt(cost: int, samples: int = 5) -> float:
    """Returns average seconds per hash at the given cost factor."""
    password = b"benchmark_password"
    times = []
    for _ in range(samples):
        start = time.perf_counter()
        bcrypt.hashpw(password, bcrypt.gensalt(rounds=cost))
        times.append(time.perf_counter() - start)
    avg = sum(times) / len(times)
    print(f"cost={cost:2d}  avg={avg*1000:.1f}ms  hashes/sec={1/avg:.1f}")
    return avg

# Typical output on a 2024 server (AMD EPYC, single core):
# cost= 8  avg= 12.3ms  hashes/sec= 81.3
# cost= 9  avg= 24.6ms  hashes/sec= 40.7
# cost=10  avg= 49.2ms  hashes/sec= 20.3   ← common default
# cost=11  avg= 98.5ms  hashes/sec= 10.2
# cost=12  avg=197.0ms  hashes/sec=  5.1
# cost=13  avg=394.0ms  hashes/sec=  2.5
# cost=14  avg=788.0ms  hashes/sec=  1.3
```

**Choosing the right cost factor:**

```
Target: 100–500ms per hash on the server hardware performing login.

Why 100ms+:
  - Human users don't notice 100–300ms added to a login form.
  - A leaked database at cost=12 takes ~197ms per guess on your hardware.
  - An attacker with 100 GPUs, each doing 100 bcrypt/s at cost=12:
    10,000 guesses/second against your hash dump.
  - Top 100 million password list at 10,000/s → 10,000 seconds (~2.8 hours).
    With salting: each hash must be attacked individually → 2.8 hours per hash.
    At 1 million users: impractical to crack all of them.

Why not higher:
  - cost=16 → ~6 seconds per hash → login endpoint takes 6 seconds
  - Under login-flood attack, each request ties up a thread for 6 seconds
  - DoS amplification: attacker sends 100 concurrent login requests
    → 100 threads × 6 seconds = 600 thread-seconds consumed per burst

OWASP recommendation (2023): cost factor 10 minimum; 12 preferred.
Real-world: start at 12, benchmark on your production hardware, adjust.

Key rule: choose the highest cost factor where login latency remains
acceptable (< 300ms) and the server can handle peak concurrent logins
without exhausting the thread pool.
```

**Updating the cost factor over time (hash migration):**

```python
# Strategy: rehash on successful login — no forced password resets required.
# Old hashes (cost=10) remain valid; new logins produce hashes at cost=12.

CURRENT_COST = 12   # updated as hardware improves

def login(username: str, password: str) -> User | None:
    user = User.get_by_username(username)
    if user is None:
        # Perform a dummy bcrypt check to prevent username enumeration via timing
        # (see Q8 — even on "user not found" we spend the same time)
        bcrypt.checkpw(password.encode(), DUMMY_HASH)
        return None

    # Verify the password against the stored hash
    if not bcrypt.checkpw(password.encode(), user.password_hash.encode()):
        return None   # wrong password

    # Rehash if the stored hash uses an outdated cost factor
    stored_cost = _extract_cost(user.password_hash)
    if stored_cost < CURRENT_COST:
        new_hash = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=CURRENT_COST))
        user.update(password_hash=new_hash.decode())
        # Audit log: hash upgraded (no password change — transparent to user)

    return user

def _extract_cost(hash_str: str) -> int:
    # bcrypt hash format: $2b$12$...
    # Cost is the number between the second and third $ signs.
    parts = hash_str.split("$")
    return int(parts[2])   # "12" → 12

# Dummy hash for timing-safe "user not found" path (see Q8)
DUMMY_HASH = bcrypt.hashpw(b"dummy", bcrypt.gensalt(rounds=CURRENT_COST))
```

**Q5. What is bcrypt's 72-byte password truncation, and how do you handle it securely?**
A: bcrypt silently ignores all bytes beyond the 72nd. Two passwords that share their first 72 bytes are indistinguishable to bcrypt:

```python
import bcrypt

password_a = b"A" * 72 + b"different_suffix_1"
password_b = b"A" * 72 + b"different_suffix_2"

hash_a = bcrypt.hashpw(password_a, bcrypt.gensalt())

# Both verify successfully — bcrypt only used the first 72 bytes of each
print(bcrypt.checkpw(password_a, hash_a))   # True
print(bcrypt.checkpw(password_b, hash_a))   # True — WRONG, but bcrypt can't tell

# For most users: not a practical concern. Passwords > 72 bytes are rare.
# For systems accepting passphrases or API-key-length inputs: a real issue.
```

**Mitigation: pre-hash with SHA-256 before bcrypt:**

```python
import bcrypt, hashlib, base64

def _prepare_password(password: str) -> bytes:
    """
    SHA-256 pre-hash before bcrypt to handle passwords > 72 bytes.
    Result is always exactly 44 bytes (base64 of 32-byte digest) — well under 72.

    IMPORTANT: use base64 encoding, not hex, to avoid null bytes.
    bcrypt has a separate bug where some implementations stop at null bytes.
    base64 output contains only [A-Za-z0-9+/=] — no null bytes possible.
    """
    digest = hashlib.sha256(password.encode("utf-8")).digest()
    return base64.b64encode(digest)   # 44 bytes, no nulls

def hash_password(password: str) -> str:
    prepared = _prepare_password(password)
    return bcrypt.hashpw(prepared, bcrypt.gensalt(rounds=12)).decode("utf-8")

def verify_password(password: str, stored_hash: str) -> bool:
    prepared = _prepare_password(password)
    return bcrypt.checkpw(prepared, stored_hash.encode("utf-8"))

# Why base64, not hex?
# hex(sha256) = 64 characters — still under 72, so actually fine.
# base64(sha256) = 44 characters — more conservative.
# Either is correct; the critical requirement is no null bytes.
# Do NOT use raw bytes: hashlib.sha256(p).digest() contains null bytes
# which some bcrypt implementations (notably PHP's password_hash on older
# versions) stop processing at the first null byte.
```

Note: this pre-hashing approach means the SHA-256 output is what bcrypt hashes — not the original password. This is cryptographically sound: SHA-256 is a one-way function; an attacker with the bcrypt hash still cannot reverse bcrypt to get the SHA-256 output, and cannot reverse SHA-256 to get the password.

## Section 3: Timing Attacks

**Q6. What is a timing attack, and how does it apply to string comparison?**
A: A timing attack is a side-channel attack that infers secret information by measuring how long an operation takes. The attacker does not break the cryptography — they observe the execution time of a comparison and use the variance to learn about the secret value.

The vulnerability in naive string comparison:

```python
# How Python's == operator (and most language string comparisons) work:

def naive_equals(a: str, b: str) -> bool:
    if len(a) != len(b):
        return False
    for i in range(len(a)):
        if a[i] != b[i]:
            return False   # ← EARLY EXIT on first mismatch
    return True

# The early exit leaks information:
#
# Attacker is guessing an API key. They know the correct key is 32 chars.
# They measure response time for different guesses:
#
# guess = "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA" → comparison exits at index 0 → 1.2ms
# guess = "XAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA" → X matches first char → exits at 1 → 1.3ms
# guess = "XXAAAAAAAAAAAAAAAAAAAAAAAAAAAAA" → XX match → exits at 2 → 1.4ms
# ...
# guess = "XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX" → all 32 match → 2.1ms → CORRECT
#
# Each correct character adds ~0.1ms (one extra loop iteration before exit).
# 32 characters × 95 printable ASCII values = 3,040 attempts to find the key
# instead of 95^32 brute-force combinations.
#
# In practice: network jitter overwhelms 0.1ms differences.
# But: in a local network, a data center, or with statistical averaging
# over many requests, the signal becomes measurable.
# High-value targets (HMAC tokens, API keys, session IDs) warrant protection
# regardless of the practical exploitability in your specific environment.
```

The timing oracle attack on password hash comparison is different — and more important — than the above:

```python
# Password hash comparison timing vulnerability:
# NOT about the string comparison itself — bcrypt.checkpw is already constant-time.
# The vulnerability is in the CODE PATH around the comparison.

# VULNERABLE: different code paths for "user not found" vs "wrong password"

def login_bad(username: str, password: str) -> bool:
    user = db.get_user(username)

    if user is None:
        return False          # ← returns immediately: ~0.1ms (DB lookup only)

    # bcrypt.checkpw takes ~200ms (cost=12)
    return bcrypt.checkpw(password.encode(), user.hash.encode())
    # "user not found":  ~0.1ms total response time
    # "wrong password":  ~200ms total response time
    # Attacker can enumerate valid usernames by measuring response time!
    # Valid username   → ~200ms (bcrypt ran)
    # Invalid username → ~0.1ms (bcrypt skipped)
```

```python
# CORRECT: same code path regardless of whether user exists

DUMMY_HASH = bcrypt.hashpw(b"dummy_password", bcrypt.gensalt(rounds=12))

def login_safe(username: str, password: str) -> bool:
    user = db.get_user(username)

    if user is None:
        # Always run bcrypt even when user doesn't exist.
        # The result is discarded — we always return False.
        # But the timing is now ~200ms in both cases.
        bcrypt.checkpw(password.encode(), DUMMY_HASH)
        return False

    return bcrypt.checkpw(password.encode(), user.hash.encode())
    # "user not found":  ~200ms (dummy bcrypt ran)
    # "wrong password":  ~200ms (real bcrypt ran)
    # Attacker cannot distinguish the two cases by timing.
```

**Q7. What other code paths in authentication systems leak timing information?**
A: The user-not-found check is the most common, but timing leaks appear throughout auth flows:

**Leak 1 — Token lookup short-circuit:**

```python
# VULNERABLE: returning early when token format is wrong

def verify_api_key(token: str) -> bool:
    if len(token) != 32:
        return False          # ← ~0.01ms — leaks that length is wrong

    key = db.get_api_key(token)
    if key is None:
        return False          # ← ~1ms (DB lookup) — leaks that length was right

    return hmac.compare_digest(token, key.value)   # ~0.01ms constant-time

# Observable: wrong-length token → 0.01ms; right-length wrong token → 1ms
# Attacker learns the expected token length without any valid credentials.

# FIX: always do the DB lookup regardless of format, OR normalize all invalid
# tokens to the same early-exit path with a fixed sleep.
```

**Leak 2 — TOTP / OTP validation:**

```python
# VULNERABLE: checking TOTP codes with == or early-exit loop
import pyotp

def verify_totp_bad(user: User, code: str) -> bool:
    totp = pyotp.TOTP(user.totp_secret)
    expected = totp.now()
    return code == expected   # ← not constant-time

# FIX: use hmac.compare_digest for OTP codes (even though they're short-lived,
# good practice and some implementations allow a longer window for clock drift)
def verify_totp_safe(user: User, code: str) -> bool:
    totp = pyotp.TOTP(user.totp_secret)
    expected = totp.now()
    # compare_digest requires equal-length strings — pad or use library's verify()
    return hmac.compare_digest(
        code.encode("utf-8"),
        expected.encode("utf-8")
    )
```

**Leak 3 — Signature verification order:**

```python
# VULNERABLE: checking expiry before signature
import jwt

def verify_token_bad(token: str) -> dict:
    # Decode without verification to read claims
    unverified = jwt.decode(token, options={"verify_signature": False})

    # Check expiry first — cheap, returns early if expired
    if unverified["exp"] < time.time():
        raise TokenExpired()   # ← ~0.01ms: no signature verification run

    # Verify signature — expensive (RSA or HMAC)
    return jwt.decode(token, PUBLIC_KEY, algorithms=["RS256"])   # ~1ms

# Leak: expired tokens → 0.01ms; valid-but-wrong-signature tokens → ~1ms
# Attacker can distinguish expired vs non-expired tokens by timing.

# FIX: always verify signature first (the library should do this),
# then check claims. Signature verification must always run.
def verify_token_safe(token: str) -> dict:
    # jwt.decode verifies signature AND exp atomically — correct order
    return jwt.decode(token, PUBLIC_KEY, algorithms=["RS256"])
    # Both expired tokens and wrong-signature tokens spend the same time
    # verifying the signature before any claim check fails.
```

**Leak 4 — Password reset token comparison:**

```python
# VULNERABLE: using == to compare reset tokens from the database

def use_reset_token_bad(token: str) -> User | None:
    record = db.get_reset_token(token)   # lookup by token value
    if record and record.token == token and record.expires_at > time.time():
        return record.user

# If the DB lookup uses the token as a WHERE clause key, timing of the DB
# response itself is already a side channel. Additionally, == on the token
# string is not constant-time.

# FIX: look up by user ID (or a non-secret token ID), then compare tokens
# with hmac.compare_digest. Or use a secure token lookup that doesn't
# short-circuit. See Q8 for the full pattern.
```

## Section 4: Constant-Time Comparison

**Q8. How does `hmac.compare_digest` work, and when must you use it?**
A: `hmac.compare_digest` (Python) / `crypto.timingSafeEqual` (Node.js) / `hash_equals` (PHP) perform string comparison in **constant time**: they always examine every byte of both strings before returning, regardless of where the first mismatch occurs. The return value is the same (True/False), but the execution time does not vary with the content of the strings.

```python
import hmac

# hmac.compare_digest — Python 3.3+
# Implemented in C; uses bitwise OR accumulation to avoid branching:

# Conceptual equivalent (actual implementation is in C, not Python):
def compare_digest_conceptual(a: bytes, b: bytes) -> bool:
    if len(a) != len(b):
        # Length check still leaks whether lengths match.
        # For fixed-length secrets (HMAC, bcrypt hashes, API keys of known length),
        # this is acceptable — the length is not secret.
        # For variable-length secrets, pad to a fixed length first.
        return False

    result = 0
    for x, y in zip(a, b):
        result |= x ^ y   # XOR: 0 if equal, non-zero if different
                           # OR accumulation: once non-zero, stays non-zero
                           # but loop ALWAYS runs to completion — no early exit
    return result == 0

# The critical property: result |= x ^ y always runs for all bytes.
# The branch is only on the FINAL result — no intermediate branching on content.
# Every comparison takes the same number of operations regardless of content.
```

```python
# When MUST you use hmac.compare_digest?

# YES — always use constant-time comparison for:
import hmac, hashlib, os, bcrypt

# 1. HMAC signatures / webhook signatures
def verify_webhook_signature(payload: bytes, received_sig: str, secret: str) -> bool:
    expected = hmac.new(secret.encode(), payload, hashlib.sha256).hexdigest()
    # MUST use compare_digest: both are hex strings of equal length (64 chars)
    return hmac.compare_digest(expected, received_sig)

# 2. API keys / bearer tokens stored as hashed values
def verify_api_key(presented_key: str, stored_hash: str) -> bool:
    presented_hash = hashlib.sha256(presented_key.encode()).hexdigest()
    return hmac.compare_digest(presented_hash, stored_hash)

# 3. Password reset tokens / email verification tokens
def verify_reset_token(presented: str, stored: str) -> bool:
    return hmac.compare_digest(
        presented.encode("utf-8"),
        stored.encode("utf-8")
    )

# 4. CSRF tokens
def verify_csrf_token(request_token: str, session_token: str) -> bool:
    return hmac.compare_digest(
        request_token.encode("utf-8"),
        session_token.encode("utf-8")
    )

# 5. Any fixed-length secret comparison where a timing oracle is a concern


# NO — you do NOT need constant-time comparison for:

# Usernames and email addresses — not secret; attacker already knows their own
username_matches = user.username == submitted_username   # fine

# Public identifiers — UUIDs, user IDs — not sensitive to timing
resource_id_matches = resource.id == path_param_id      # fine

# bcrypt hashes — bcrypt.checkpw is already constant-time internally
# (but you still need the dummy hash for user-not-found paths — see Q6)
bcrypt.checkpw(password.encode(), stored_hash.encode())  # already safe internally
```

**Q9. How do you implement a complete, timing-safe API key verification system?**
A: API keys present a compound problem: they must be looked up (requiring some indexable form), compared (must be constant-time), and rotated (must support key versioning). The lookup itself is a timing channel if not handled correctly.

```python
# api_keys.py — timing-safe API key system

import hashlib, hmac, secrets, time
from dataclasses import dataclass

@dataclass
class ApiKey:
    key_id:      str    # public prefix used for DB lookup — not secret
    key_hash:    str    # SHA-256 of the full key — stored in DB
    user_id:     str
    scope:       list[str]
    created_at:  float
    expires_at:  float | None
    revoked:     bool

# Key format: {prefix}_{random_secret}
# prefix: 8 chars (public, used for DB lookup)
# random_secret: 32 bytes → 43 URL-safe base64 chars
# Full key: "ak_Kp9mXnL2_dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"

PREFIX_LENGTH = 8
SECRET_BYTES  = 32

def generate_api_key() -> tuple[str, str]:
    """
    Returns (full_key_for_user, key_id_for_db_lookup).
    The full key is shown ONCE and never stored — only its hash is stored.
    """
    prefix     = secrets.token_urlsafe(6)[:PREFIX_LENGTH]   # 8 chars
    secret     = secrets.token_urlsafe(SECRET_BYTES)         # 43 chars
    full_key   = f"ak_{prefix}_{secret}"
    key_id     = f"ak_{prefix}"   # prefix used as lookup index
    return full_key, key_id

def hash_api_key(full_key: str) -> str:
    """SHA-256 of the full key — stored in the DB, never the key itself."""
    return hashlib.sha256(full_key.encode("utf-8")).hexdigest()

def store_api_key(full_key: str, key_id: str, user_id: str, scope: list[str]) -> ApiKey:
    key_hash = hash_api_key(full_key)
    record   = ApiKey(
        key_id     = key_id,
        key_hash   = key_hash,
        user_id    = user_id,
        scope      = scope,
        created_at = time.time(),
        expires_at = None,
        revoked    = False,
    )
    db.insert("api_keys", record)
    # full_key is NOT stored — only key_hash and key_id
    return record


# Timing-safe verification:

# A dummy hash used when key_id is not found (prevents timing oracle on lookup)
_DUMMY_HASH = hashlib.sha256(b"dummy_key_that_does_not_exist").hexdigest()

def verify_api_key(presented_key: str) -> ApiKey | None:
    """
    Verifies a presented API key. Returns the ApiKey record on success, None on failure.
    Constant-time: does not reveal whether the key_id exists or the key_hash mismatched.
    """
    # Parse the key_id from the presented key
    parts = presented_key.split("_", 2)
    if len(parts) != 3 or parts[0] != "ak":
        # Malformed key format — still run dummy comparison to consume ~constant time
        # (though format check timing leak is minor since format is not secret)
        hmac.compare_digest(_DUMMY_HASH, _DUMMY_HASH)
        return None

    key_id = f"ak_{parts[1]}"

    # DB lookup by key_id (the public prefix) — this is an indexed lookup, not secret
    record = db.get("api_keys", key_id=key_id)

    if record is None:
        # Key ID not found — run dummy comparison anyway
        # This ensures "key not found" and "key found, hash mismatch"
        # take the same amount of time.
        presented_hash = hash_api_key(presented_key)
        hmac.compare_digest(presented_hash, _DUMMY_HASH)
        return None

    # Constant-time comparison of hashes
    presented_hash = hash_api_key(presented_key)
    if not hmac.compare_digest(presented_hash, record.key_hash):
        return None

    # Check revocation and expiry AFTER constant-time comparison
    if record.revoked:
        return None
    if record.expires_at and record.expires_at < time.time():
        return None

    return record


# Middleware usage

async def api_key_middleware(request: Request, call_next):
    auth_header = request.headers.get("Authorization", "")
    if not auth_header.startswith("Bearer "):
        raise HTTP401("Missing API key")

    presented_key = auth_header[7:]   # strip "Bearer "
    key_record    = verify_api_key(presented_key)

    if key_record is None:
        raise HTTP401("Invalid or expired API key")

    request.state.api_key = key_record
    request.state.user_id = key_record.user_id
    return await call_next(request)
```

```javascript
    const bufA = Buffer.from(a, "utf8");
    const bufB = Buffer.from(b, "utf8");
```

## Section 5: HMAC and Webhook Signature Verification

**Q11. How do you implement webhook signature verification correctly — the full pattern used by Stripe, GitHub, and Twilio?**
A: Webhooks arrive from a third-party server — you cannot use session cookies or JWT for authentication. The standard pattern: the webhook sender signs the payload with a shared secret using HMAC-SHA256. The receiver recomputes the HMAC and compares using constant-time comparison.

```python
# Webhook signature verification — production pattern

import hashlib, hmac, time
from typing import Callable

class WebhookVerifier:
    """
    Timing-safe webhook signature verification.
    Compatible with Stripe, GitHub, Shopify webhook signature schemes.
    """

    def __init__(
        self,
        secret:            str,
        signature_header:  str = "X-Hub-Signature-256",
        timestamp_header:  str | None = "X-Webhook-Timestamp",
        max_age_seconds:   int = 300,        # reject webhooks older than 5 minutes
    ):
        self.secret           = secret.encode("utf-8")
        self.signature_header = signature_header
        self.timestamp_header = timestamp_header
        self.max_age_seconds  = max_age_seconds

    def verify(self, payload: bytes, headers: dict[str, str]) -> None:
        """
        Raises WebhookVerificationError on any failure.
        Callers should catch this and return HTTP 400.
        """
        # 1. Extract signature
        received_sig = headers.get(self.signature_header, "")
        if not received_sig:
            raise WebhookVerificationError("Missing signature header")

        # 2. Replay prevention: check timestamp if provided
        if self.timestamp_header:
            ts_str = headers.get(self.timestamp_header, "")
            self._verify_timestamp(ts_str)

        # 3. Compute expected signature
        expected_sig = self._compute_signature(payload, headers)

        # 4. Constant-time comparison — MUST NOT use == or !=
        if not hmac.compare_digest(
            expected_sig.encode("utf-8"),
            received_sig.encode("utf-8"),
        ):
            raise WebhookVerificationError("Signature mismatch")

    def _compute_signature(self, payload: bytes, headers: dict[str, str]) -> str:
        # Stripe pattern: HMAC-SHA256(secret, timestamp + "." + payload_body)
        # GitHub pattern: HMAC-SHA256(secret, payload_body)
        # Here: GitHub-style for simplicity
        digest = hmac.new(self.secret, payload, hashlib.sha256).hexdigest()
        return f"sha256={digest}"

    def _verify_timestamp(self, ts_str: str) -> None:
        try:
            timestamp = int(ts_str)
        except (ValueError, TypeError):
            raise WebhookVerificationError("Invalid or missing timestamp")

        age = abs(time.time() - timestamp)
        if age > self.max_age_seconds:
            raise WebhookVerificationError(
                f"Webhook too old: {age:.0f}s > {self.max_age_seconds}s"
            )


class WebhookVerificationError(Exception):
    pass


# FastAPI endpoint example:

from fastapi import Request, HTTPException

stripe_verifier = WebhookVerifier(
    secret           = os.environ["STRIPE_WEBHOOK_SECRET"],
    signature_header = "Stripe-Signature",
    timestamp_header = None,   # Stripe encodes timestamp in the sig header itself
    max_age_seconds  = 300,
)

@router.post("/webhooks/stripe")
async def stripe_webhook(request: Request):
    payload = await request.body()   # raw bytes — MUST read before any parsing
    headers = dict(request.headers)

    try:
        stripe_verifier.verify(payload, headers)
    except WebhookVerificationError as e:
        raise HTTPException(status_code=400, detail=str(e))

    event = json.loads(payload)
    await process_stripe_event(event)
    return {"received": True}

# CRITICAL: read raw bytes before any JSON parsing.
# JSON re-serialization may produce a different byte sequence (key ordering,
# whitespace) — the signature was computed over the ORIGINAL bytes.
# Always verify the signature over request.body(), not json.dumps(await request.json()).
```

**Stripe's timestamp-in-signature scheme (more complex but common):**

```python
# Stripe embeds the timestamp in the Stripe-Signature header itself:
# Stripe-Signature: t=1492774577,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e6a22...

def verify_stripe_signature(payload: bytes, sig_header: str, secret: str) -> None:
    parts = dict(item.split("=", 1) for item in sig_header.split(","))
    timestamp = parts.get("t", "")
    received_v1 = parts.get("v1", "")

    # Replay prevention
    try:
        ts = int(timestamp)
    except ValueError:
        raise WebhookVerificationError("Invalid timestamp in Stripe-Signature")

    if abs(time.time() - ts) > 300:
        raise WebhookVerificationError("Stripe webhook timestamp too old")

    # Compute expected: HMAC-SHA256(secret, timestamp + "." + payload)
    signed_payload = f"{timestamp}.".encode() + payload
    expected = hmac.new(secret.encode(), signed_payload, hashlib.sha256).hexdigest()

    if not hmac.compare_digest(expected, received_v1):
        raise WebhookVerificationError("Stripe signature mismatch")
```

## Section 6: Real-World Patterns and Trade-offs

**Q12. How do you store and verify passwords end-to-end — the complete production pattern?**
A:

```python
# auth/passwords.py — complete production password handling

import bcrypt, hashlib, base64, hmac, os, re
from zxcvbn import zxcvbn   # password strength estimation

BCRYPT_COST    = int(os.environ.get("BCRYPT_COST", "12"))
MIN_STRENGTH   = 3   # zxcvbn score 0–4; 3 = "good"
MAX_LENGTH     = 1024  # reject absurdly long passwords (DoS via bcrypt)
MIN_LENGTH     = 12

# Dummy hash for constant-time user-not-found path
_DUMMY_HASH = bcrypt.hashpw(
    base64.b64encode(hashlib.sha256(b"dummy").digest()),
    bcrypt.gensalt(rounds=BCRYPT_COST),
)


def validate_password_strength(password: str, user_inputs: list[str] = None) -> None:
    """
    Raises ValueError if the password is too weak or too short.
    Called at registration and password change — NOT at login.
    """
    if len(password) < MIN_LENGTH:
        raise ValueError(f"Password must be at least {MIN_LENGTH} characters")
    if len(password) > MAX_LENGTH:
        raise ValueError("Password is too long")

    result = zxcvbn(password, user_inputs=user_inputs or [])
    if result["score"] < MIN_STRENGTH:
        suggestions = result["feedback"]["suggestions"]
        raise ValueError(
            "Password is too weak. "
            + (suggestions[0] if suggestions else "Please choose a stronger password.")
        )


def hash_password(password: str) -> str:
    """
    Hash a password for storage.
    Returns a bcrypt hash string (60 chars) safe to store in TEXT column.
    """
    if len(password) > MAX_LENGTH:
        raise ValueError("Password exceeds maximum length")

    # Pre-hash to handle > 72 byte passwords and normalize input
    prepared = base64.b64encode(
        hashlib.sha256(password.encode("utf-8")).digest()
    )
    return bcrypt.hashpw(prepared, bcrypt.gensalt(rounds=BCRYPT_COST)).decode("utf-8")


def verify_password(password: str, stored_hash: str) -> bool:
    """
    Verify a password against a stored bcrypt hash.
    Constant-time: always runs bcrypt regardless of outcome.
    Returns True only if the password matches.
    """
    if len(password) > MAX_LENGTH:
        # DoS guard: don't bcrypt a 10MB password string
        # Use dummy comparison to maintain ~constant timing for normal lengths
        bcrypt.checkpw(b"A" * 44, _DUMMY_HASH)
        return False

    prepared = base64.b64encode(
        hashlib.sha256(password.encode("utf-8")).digest()
    )
    try:
        return bcrypt.checkpw(prepared, stored_hash.encode("utf-8"))
    except Exception:
        return False


def login(username: str, password: str) -> "User | None":
    """
    Authenticate a user. Timing-safe: same code path for all failure modes.
    """
    user = db.get_user_by_username(username)

    if user is None:
        # User not found — run dummy bcrypt to equalize timing
        bcrypt.checkpw(
            base64.b64encode(hashlib.sha256(b"dummy").digest()),
            _DUMMY_HASH
        )
        return None

    if not verify_password(password, user.password_hash):
        return None

    # Rehash if cost factor is outdated (transparent migration)
    stored_cost = int(user.password_hash.split("$")[2])
    if stored_cost < BCRYPT_COST:
        new_hash = hash_password(password)
        db.update_user(user.id, password_hash=new_hash)

    return user


def check_password_reuse(password: str, previous_hashes: list[str]) -> bool:
    """
    Returns True if the password matches any previous hash.
    Constant-time: checks ALL previous hashes even after first match.
    """
    matched = False
    for old_hash in previous_hashes:
        # Must check all — early exit would leak how many hashes were checked
        result = verify_password(password, old_hash)
        matched = matched or result
    return matched
```

**Q13. What is the DoS risk of bcrypt, and how do you mitigate it?**
A: bcrypt's intentional slowness creates a denial-of-service vector: an attacker can flood the login endpoint with requests, each consuming 200ms of CPU time. At cost=12, 100 concurrent requests tie up 100 threads for 200ms each — 20 seconds of CPU time per burst.

```python

from slowapi.util import get_remote_address

    ...

    key   = f"login_failures:{username}"
    count = int(await redis.get(key) or 0)
    if count >= 10:
        raise HTTP429("Account temporarily locked. Try again in 15 minutes.")

async def record_login_failure(username: str) -> None:
    key = f"login_failures:{username}"
    await redis.incr(key)
    await redis.expire(key, 900)   # 15-minute window

# 3. Pre-authentication validation — reject obviously invalid requests before bcrypt
async def login_endpoint(request: Request, body: LoginRequest):
```

**Q14. When should you use Argon2id instead of bcrypt, and how do you migrate?**
A:

```python
# Argon2id — for new systems or migration from bcrypt

from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError, VerificationError, InvalidHashError

# OWASP recommended parameters (2023):
#   memory_cost = 19456 (19 MiB) minimum; 64 MiB preferred
#   time_cost   = 2 iterations minimum
#   parallelism = 1 (match to number of available CPUs for your use case)
ph = PasswordHasher(
    time_cost    = 3,       # iterations
    memory_cost  = 65536,   # 64 MiB RAM per hash
    parallelism  = 4,       # parallel threads
    hash_len     = 32,      # output length
    salt_len     = 16,      # random salt length
)

def hash_password_argon2(password: str) -> str:
    return ph.hash(password)
    # Output: $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>
    # Parameters embedded in output — self-describing, like bcrypt

def verify_password_argon2(password: str, stored_hash: str) -> tuple[bool, bool]:
    """
    Returns (is_valid, needs_rehash).
    needs_rehash is True when parameters are outdated.
    """
    try:
        ph.verify(stored_hash, password)
        needs_rehash = ph.check_needs_rehash(stored_hash)
        return True, needs_rehash
    except VerifyMismatchError:
        return False, False
    except (VerificationError, InvalidHashError):
        return False, False


# Migrating from bcrypt to Argon2id — no forced password resets:

def login_with_migration(username: str, password: str) -> "User | None":
    user = db.get_user(username)

    if user is None:
        ph.verify("$argon2id$v=19$m=65536,t=3,p=4$dummy$dummy", "dummy")
        return None

    stored = user.password_hash

    # Detect which algorithm is stored
    if stored.startswith("$2b$") or stored.startswith("$2a$"):
        # Legacy bcrypt hash
        if not verify_password(password, stored):   # bcrypt verify
            return None
        # Upgrade: rehash with Argon2id on successful login
        new_hash = hash_password_argon2(password)
        db.update_user(user.id, password_hash=new_hash)

    elif stored.startswith("$argon2id$"):
        # Modern Argon2id hash
        is_valid, needs_rehash = verify_password_argon2(password, stored)
        if not is_valid:
            return None
        if needs_rehash:
            new_hash = hash_password_argon2(password)
            db.update_user(user.id, password_hash=new_hash)
    else:
        return None   # unknown algorithm — deny

    return user
```

| Version | `$2b$` | Algorithm version; `$2b$` is correct modern form |

## Quick Reference: When to Use Constant-Time Comparison

| Scenario | Use `hmac.compare_digest`? | Reason |
|---|---|---|
| Password hash verification | Library handles it (bcrypt.checkpw) | bcrypt internals are constant-time |
| User-not-found path | Use dummy bcrypt, not compare_digest | Path timing — not value timing |
| HMAC / webhook signature | **YES** | Timing oracle on signature bytes |
| API key comparison | **YES** | Timing oracle on key bytes |
| CSRF token | **YES** | Timing oracle on token bytes |
| Password reset token | **YES** | Timing oracle on token bytes |
| TOTP / OTP code | **YES** | Short-lived but good practice |
| Username / email match | No | Not secret; attacker knows their own |
| UUID / resource ID in path | No | Not a secret value |

**Tip for the interview:** At 5 YOE, the bcrypt question is almost never "what does bcrypt do?" — it's "why is SHA-256 wrong for passwords?" (the speed argument: 22 billion/sec vs 100/sec), followed by "how do you choose the cost factor?" (benchmark to 100–300ms on your hardware; OWASP recommends 12). The timing attack question is a favourite trap: most candidates know about constant-time comparison but miss the **code path** timing leak — the user-not-found case where bcrypt is skipped entirely, making username enumeration trivial by measuring response time. Know the dummy hash pattern cold (Q6, Q12). For `hmac.compare_digest`, the interviewer will ask why `==` is wrong — the early-exit XOR accumulation explanation (Q8) is the depth signal. The bcrypt 72-byte truncation (Q5) and the SHA-256 pre-hash mitigation come up in any discussion of passphrase inputs or API-key-length passwords. The DoS amplification angle (Q13) is a systems design signal: bcrypt's slowness is a feature against offline attacks but a liability against online floods — thread pool caps and rate limiting are the answer, not reducing the cost factor.
