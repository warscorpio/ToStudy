## Section 1: Fundamentals and Mental Models

**Q1. What is the core difference between symmetric and asymmetric encryption, and what problem does each solve?**
A: The difference is in how many keys exist and who holds them. The distinction drives every practical trade-off between the two systems.

**Symmetric encryption** uses a single key for both encryption and decryption. The same secret bytes that lock the data unlock it. This is computationally efficient — symmetric ciphers are fast because they operate on data in bulk using simple mathematical operations (substitution, permutation, XOR). The fundamental problem symmetric encryption does not solve: **key distribution**. If Alice wants to send Bob an encrypted message, she needs to share the key with Bob first. But how does she share the key securely? They would need an already-secure channel to share the key — which is circular.

```
Symmetric encryption:

  Alice                              Bob
    │                                │
    │  Shared secret key K           │
    │<────────────────────────────── │ (problem: how did they agree on K securely?)
    │                                │
    │  ciphertext = Encrypt(K, msg)  │
    │ ─────────────────────────────► │
    │                                │ msg = Decrypt(K, ciphertext)
```

**Asymmetric encryption** uses a mathematically related key pair: a public key and a private key. Data encrypted with the public key can only be decrypted with the corresponding private key. The public key can be distributed openly — posted on a website, sent in an email, embedded in a certificate. The private key never leaves its owner. This solves key distribution: Bob publishes his public key; Alice uses it to encrypt a message that only Bob can decrypt. No prior secure channel is needed.

```
Asymmetric encryption:

  Bob generates key pair: (public_key_B, private_key_B)
  Bob publishes public_key_B openly

  Alice (has Bob's public key):
    ciphertext = Encrypt(public_key_B, msg)
    sends ciphertext to Bob

  Bob (has private_key_B):
    msg = Decrypt(private_key_B, ciphertext)

  Anyone with public_key_B can encrypt for Bob.
  Only Bob can decrypt — private_key_B never leaves Bob.
```

The trade-off: asymmetric encryption solves key distribution but is computationally expensive — 100x to 10,000x slower than symmetric encryption for bulk data. In practice, real systems use both: asymmetric encryption to securely exchange a symmetric key, then symmetric encryption for all data. This hybrid is exactly how TLS works.

**Q2. What is the fundamental mathematical hardness assumption behind each approach?**
A: Security in both families depends on mathematical problems that are easy to compute in one direction and computationally infeasible to reverse.

**Symmetric encryption (AES):**
AES does not rely on a single mathematical hardness assumption — its security comes from the design of the cipher itself: a series of confusion and diffusion operations (SubBytes, ShiftRows, MixColumns, AddRoundKey) applied over multiple rounds. The security assumption is that no structural weakness exists in these operations that allows key recovery or plaintext recovery faster than brute-force.

For AES-256, the key space is 2^256 — at 10^18 guesses per second across all computing power on Earth, brute-forcing a 256-bit key takes longer than the age of the universe. The practical attacks on AES are against its implementation (side-channel attacks, padding oracle attacks, key management failures) — not against the algorithm itself.

**Asymmetric encryption:**

RSA relies on the **integer factorization problem**: it is easy to multiply two large primes p and q to get n = p × q, but computationally infeasible to factor n back into p and q when n is large (~2048+ bits). The private key is derived from p and q; the public key is derived from n. An attacker who can factor n recovers the private key.

```
RSA key generation:
  Choose large primes p, q (each ~1024 bits for 2048-bit RSA)
  n = p × q              ← public modulus (easy to compute)
  φ(n) = (p-1)(q-1)     ← Euler's totient (requires knowing p, q)
  Choose e: gcd(e, φ(n)) = 1  ← public exponent (commonly 65537)
  d = e^(-1) mod φ(n)   ← private exponent (requires knowing φ(n))

  Public key:  (n, e)
  Private key: (n, d)

  Encrypt: ciphertext = plaintext^e mod n
  Decrypt: plaintext  = ciphertext^d mod n

  Security: an attacker with only (n, e) cannot compute d without factoring n
```

ECC (Elliptic Curve Cryptography) relies on the **elliptic curve discrete logarithm problem (ECDLP)**: given points P and Q on an elliptic curve where Q = k × P (k multiplications of P), it is computationally infeasible to determine k. ECC provides equivalent security to RSA with much smaller key sizes (256-bit ECC ≈ 3072-bit RSA), making it the preferred choice for new systems.

```
Comparative key sizes for equivalent security (NIST recommendations):
  Symmetric  │ RSA/DH    │ ECC
  ─────────────────────────────
  80 bits    │ 1024 bits │ 160 bits
  112 bits   │ 2048 bits │ 224 bits
  128 bits   │ 3072 bits │ 256 bits (P-256)
  192 bits   │ 7680 bits │ 384 bits (P-384)
  256 bits   │ 15360 bits│ 521 bits (P-521)

ECC achieves 256-bit security with a 256-bit key.
RSA requires a 15,360-bit key for the same security level.
```

**Q3. What is the hybrid encryption model, and why is it universal in production systems?**
A: Hybrid encryption combines asymmetric and symmetric encryption to get the advantages of both: asymmetric for key distribution (solving the key distribution problem without a prior secure channel), symmetric for bulk data encryption (achieving the performance needed for real workloads).

The pattern is universal — used in TLS, SSH, PGP, Signal, and every other modern secure communication protocol:

```
Hybrid encryption flow:

1. Key encapsulation (asymmetric — slow, tiny data):
   Sender generates a random symmetric key K (32 bytes of CSPRNG output)
   Sender encrypts K with the recipient's public key:
     encrypted_key = RSA_Encrypt(recipient_public_key, K)
   This produces ~256 bytes of ciphertext (for 2048-bit RSA)

2. Data encryption (symmetric — fast, arbitrary data):
   Sender encrypts the actual data with K:
     ciphertext = AES_GCM_Encrypt(K, plaintext)
   AES-GCM processes data at ~10 GB/s on modern hardware

3. Transmission:
   Sender transmits: [encrypted_key || ciphertext]

4. Decryption (recipient):
   Recipient decrypts encrypted_key with private key:
     K = RSA_Decrypt(recipient_private_key, encrypted_key)
   Recipient decrypts data with K:
     plaintext = AES_GCM_Decrypt(K, ciphertext)
```

Why not just use asymmetric encryption for everything? RSA encryption of a 1 GB file directly would take minutes on a modern CPU. AES-GCM encrypts the same file in under 0.1 seconds. The asymmetric operation is used exactly once per session to establish the symmetric key — its cost is amortized over the entire session.

```python
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

def hybrid_encrypt(plaintext: bytes, recipient_public_key) -> dict:
    # Step 1: Generate ephemeral symmetric key
    symmetric_key = os.urandom(32)   # 256-bit AES key

    # Step 2: Encrypt the symmetric key with RSA-OAEP
    encrypted_key = recipient_public_key.encrypt(
        symmetric_key,
        padding.OAEP(
            mgf=padding.MGF1(algorithm=hashes.SHA256()),
            algorithm=hashes.SHA256(),
            label=None
        )
    )

    # Step 3: Encrypt plaintext with AES-GCM
    nonce = os.urandom(12)           # 96-bit nonce for GCM
    aesgcm = AESGCM(symmetric_key)
    ciphertext = aesgcm.encrypt(nonce, plaintext, None)

    return {
        "encrypted_key": encrypted_key,  # RSA-encrypted symmetric key
        "nonce":         nonce,
        "ciphertext":    ciphertext,      # AES-GCM encrypted data + auth tag
    }

def hybrid_decrypt(encrypted_package: dict, recipient_private_key) -> bytes:
    # Step 1: Decrypt the symmetric key with RSA private key
    symmetric_key = recipient_private_key.decrypt(
        encrypted_package["encrypted_key"],
        padding.OAEP(
            mgf=padding.MGF1(algorithm=hashes.SHA256()),
            algorithm=hashes.SHA256(),
            label=None
        )
    )

    # Step 2: Decrypt data with recovered symmetric key
    aesgcm = AESGCM(symmetric_key)
    return aesgcm.decrypt(
        encrypted_package["nonce"],
        encrypted_package["ciphertext"],
        None
    )
```

## Section 2: Symmetric Encryption in Depth

**Q4. What is AES, and what are its modes of operation — which should you use and why?**
A: AES (Advanced Encryption Standard) is a block cipher: it encrypts fixed-size blocks of 128 bits using a key of 128, 192, or 256 bits. A block cipher alone is not a complete encryption scheme — it can only encrypt exactly one 128-bit block. Modes of operation extend AES to encrypt arbitrary-length data and determine the security properties of the resulting scheme.

**ECB (Electronic Codebook) — never use:**
Each block is encrypted independently with the same key. Identical plaintext blocks produce identical ciphertext blocks. This leaks structure — the ciphertext reveals patterns in the plaintext.

```
The ECB penguin: encrypt a bitmap with AES-ECB:
  The penguin's outline is visible in the ciphertext because all-white pixels
  produce the same ciphertext block, and all-black pixels produce another.
  The pattern is preserved even though each block is encrypted.

Input:  [block1][block2][block3][block1]  (block1 repeats)
ECB:    [enc1]  [enc2]  [enc3]  [enc1]   (enc1 repeats — leaks that blocks are identical)
```

**CBC (Cipher Block Chaining) — legacy, avoid for new systems:**
Each block is XORed with the previous ciphertext block before encryption. Requires a random, unpredictable Initialization Vector (IV) — never reuse an IV with the same key. Provides confidentiality but not integrity — ciphertext can be modified without detection (padding oracle attacks on CBC are a real CVE class).

```
CBC encryption:
  ciphertext[0] = Encrypt(K, plaintext[0] XOR IV)
  ciphertext[i] = Encrypt(K, plaintext[i] XOR ciphertext[i-1])

Vulnerabilities:
  - Padding oracle attacks (POODLE, BEAST) if decryption errors are observable
  - Bit-flipping attacks: modifying ciphertext[i] predictably corrupts plaintext[i+1]
  - No authentication — attacker can modify ciphertext without detection
```

**GCM (Galois/Counter Mode) — use this:**
AES-GCM is an Authenticated Encryption with Associated Data (AEAD) mode. It provides:
- **Confidentiality**: CTR mode encryption (AES used as a stream cipher)
- **Integrity + Authenticity**: a 128-bit authentication tag (GHASH over ciphertext and associated data)

Any modification to the ciphertext, IV, or associated data causes the authentication tag verification to fail — decryption is rejected before any plaintext is returned.

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

# Encryption
key   = AESGCM.generate_key(bit_length=256)   # 32 random bytes
nonce = os.urandom(12)                         # 96-bit nonce — never reuse with same key
aad   = b"account_id=12345"                   # Associated Authenticated Data
       # AAD is authenticated but not encrypted — metadata that must not be tampered with

aesgcm    = AESGCM(key)
ciphertext = aesgcm.encrypt(nonce, plaintext, aad)
# ciphertext includes the 16-byte authentication tag appended to the encrypted data

# Decryption
try:
    recovered = aesgcm.decrypt(nonce, ciphertext, aad)
    # If tag verification fails: raises InvalidTag — plaintext is NEVER returned
except Exception:
    raise DecryptionError("Ciphertext is invalid or has been tampered with")
```

**ChaCha20-Poly1305 — modern alternative to AES-GCM:**
ChaCha20 is a stream cipher; Poly1305 is the MAC. The combination is an AEAD mode equivalent in security to AES-GCM. Advantages:
- Faster than AES-GCM on hardware without AES-NI instructions (mobile devices, IoT, older ARM)
- Immune to the GCM nonce reuse catastrophe (AES-GCM nonce reuse completely breaks confidentiality; ChaCha20-Poly1305 nonce reuse is harmful but less catastrophic)
- Used by TLS 1.3 and the Noise protocol framework (used by Signal, WireGuard)

```
Algorithm selection guide:
  AES-256-GCM:       First choice when hardware AES acceleration is guaranteed
                     (servers, modern phones with AES-NI)
  ChaCha20-Poly1305: First choice for mobile, IoT, or when AES-NI is unavailable
  AES-256-CBC:       Legacy interoperability only — add separate HMAC-SHA256 for integrity
  AES-ECB:           Never. No exceptions.
```

**Q5. What is nonce/IV reuse, and why is it catastrophic for AES-GCM?**
A: A nonce (Number Used Once) is a value that must be unique for every encryption operation with the same key. "Nonce reuse" means encrypting two different plaintexts with the same (key, nonce) pair. In AES-GCM, nonce reuse is a critical vulnerability — it reveals the XOR of the two plaintexts and completely breaks the authentication tag.

The mathematics of the attack:

```
AES-GCM in CTR mode:
  keystream = AES(key, nonce || counter)
  ciphertext = plaintext XOR keystream

If nonce is reused:
  ciphertext1 = plaintext1 XOR keystream  (keystream is the same because nonce is the same)
  ciphertext2 = plaintext2 XOR keystream

  ciphertext1 XOR ciphertext2
    = (plaintext1 XOR keystream) XOR (plaintext2 XOR keystream)
    = plaintext1 XOR plaintext2   (keystreams cancel out)

The attacker who observes ciphertext1 and ciphertext2 can compute their XOR.
If either plaintext has known structure (HTTP headers, JSON keys, protocol framing),
the other plaintext can be recovered entirely via known-plaintext XOR.

Authentication tag break:
  The GCM authentication tag is also computed using the keystream.
  If the attacker knows the tag for one message, they can forge valid tags
  for other messages — breaking the integrity guarantee completely.
```

How to prevent nonce reuse:

```python
import os
import struct
from threading import Lock

# Strategy 1: Random nonces (simplest, sufficient for most cases)
# 96-bit random nonce: probability of collision after 2^32 messages is ~10^-9
# For 2^48 messages: probability exceeds 1% — at that scale, rotate the key
nonce = os.urandom(12)  # 96 bits = 12 bytes — never reuse

# Strategy 2: Counter-based nonces (zero collision probability, requires state)
class NonceCounter:
    """Thread-safe monotonic nonce counter — guarantees uniqueness."""
    def __init__(self, prefix: bytes = None):
        self._prefix  = prefix or os.urandom(4)   # 4-byte random prefix per instance
        self._counter = 0
        self._lock    = Lock()

    def next_nonce(self) -> bytes:
        with self._lock:
            nonce_int   = self._counter
            self._counter += 1
            if self._counter >= 2**64:
                raise RuntimeError("Nonce counter exhausted — rotate the key")
        # prefix (4 bytes) + counter (8 bytes) = 12 bytes total
        return self._prefix + struct.pack(">Q", nonce_int)

# Strategy 3: Key rotation — after N encryptions, generate a new key
MAX_ENCRYPTIONS_PER_KEY = 2**32   # conservative limit for AES-GCM with random nonces

class ManagedEncryptor:
    def __init__(self):
        self._rotate_key()

    def _rotate_key(self):
        self._key           = AESGCM.generate_key(bit_length=256)
        self._encryptor     = AESGCM(self._key)
        self._encrypt_count = 0

    def encrypt(self, plaintext: bytes, aad: bytes = None) -> bytes:
        if self._encrypt_count >= MAX_ENCRYPTIONS_PER_KEY:
            self._rotate_key()
        nonce = os.urandom(12)
        self._encrypt_count += 1
        return nonce + self._encryptor.encrypt(nonce, plaintext, aad)
```

**Q6. How do you derive keys from passwords using key derivation functions, and which KDF should you use?**
A: Passwords are low-entropy — a typical user password has ~30–50 bits of entropy, far below the 256-bit keys AES expects. Directly using a password as an AES key is insecure because the key space is effectively the password space, which can be brute-forced rapidly. A Key Derivation Function (KDF) transforms a password into a cryptographic key with three properties:

- **Deterministic** — same password + same salt → same key (needed for symmetric encryption where the key must be reproducible)
- **Slow** — computationally expensive to compute, making brute-force attacks expensive
- **Salt-randomized** — a random salt ensures the same password produces different keys for different users (defeats rainbow tables)

```python
import os
from cryptography.hazmat.primitives.kdf.scrypt import Scrypt
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC
from cryptography.hazmat.primitives import hashes
from argon2.low_level import hash_secret_raw, Type

# ── Argon2id — recommended for new systems ──────────────────────────────────────
# Winner of the Password Hashing Competition (2015)
# Memory-hard: requires significant RAM — defeats GPU/ASIC brute-force
# Argon2id: hybrid of Argon2i (side-channel resistant) and Argon2d (GPU resistant)

def derive_key_argon2id(password: str, salt: bytes = None) -> tuple[bytes, bytes]:
    if salt is None:
        salt = os.urandom(16)    # 128-bit random salt — store alongside ciphertext

    key = hash_secret_raw(
        secret=password.encode("utf-8"),
        salt=salt,
        time_cost=3,             # iterations (increase for higher security)
        memory_cost=65536,       # 64 MB RAM required (defeats GPU parallelism)
        parallelism=4,           # threads
        hash_len=32,             # output: 256-bit AES key
        type=Type.ID,            # Argon2id variant
    )
    return key, salt

# ── Scrypt — strong alternative, widely supported ───────────────────────────────
# Also memory-hard; available in Python's standard library (hashlib.scrypt)

def derive_key_scrypt(password: str, salt: bytes = None) -> tuple[bytes, bytes]:
    if salt is None:
        salt = os.urandom(16)

    kdf = Scrypt(
        salt=salt,
        length=32,               # 256-bit output
        n=2**14,                 # CPU/memory cost (2^14 = 16384; use 2^20 for high security)
        r=8,                     # block size
        p=1,                     # parallelism
    )
    key = kdf.derive(password.encode("utf-8"))
    return key, salt

# ── PBKDF2-HMAC-SHA256 — legacy; use only for compatibility ─────────────────────
# Not memory-hard — GPUs can parallelize freely; 600,000+ iterations needed in 2024
# NIST SP 800-63B recommends 600,000 iterations minimum as of 2023

def derive_key_pbkdf2(password: str, salt: bytes = None) -> tuple[bytes, bytes]:
    if salt is None:
        salt = os.urandom(16)

    kdf = PBKDF2HMAC(
        algorithm=hashes.SHA256(),
        length=32,
        salt=salt,
        iterations=600_000,      # NIST 2023 recommendation
    )
    key = kdf.derive(password.encode("utf-8"))
    return key, salt

# ── Usage pattern — encrypt with password-derived key ───────────────────────────
def encrypt_with_password(plaintext: bytes, password: str) -> bytes:
    key, salt = derive_key_argon2id(password)
    nonce     = os.urandom(12)
    aesgcm    = AESGCM(key)
    ciphertext = aesgcm.encrypt(nonce, plaintext, None)

    # Store: salt + nonce + ciphertext (all needed for decryption)
    return salt + nonce + ciphertext

def decrypt_with_password(stored: bytes, password: str) -> bytes:
    salt, nonce, ciphertext = stored[:16], stored[16:28], stored[28:]
    key, _  = derive_key_argon2id(password, salt=salt)
    aesgcm  = AESGCM(key)
    return aesgcm.decrypt(nonce, ciphertext, None)

# KDF selection summary:
# Argon2id:   Best choice — memory-hard, side-channel resistant, PHC winner
# Scrypt:     Strong choice — memory-hard, widely audited, in stdlib
# bcrypt:     Password hashing only, not for key derivation (fixed 72-byte input limit)
# PBKDF2:     Legacy compatibility only — not memory-hard
# MD5/SHA:    Never — trivially fast, completely inappropriate for KDF
```

## Section 3: Asymmetric Encryption in Depth

**Q7. How does RSA encryption work, and what are its practical failure modes in production?**
A: RSA encryption relies on the mathematical relationship between the public exponent, private exponent, and the modulus. The security comes from the hardness of factoring the modulus.

```
RSA-OAEP encryption (correct usage):

Key generation:
  p, q = two random primes (~1024 bits each for RSA-2048)
  n    = p × q           (2048-bit modulus — the "RSA-2048" in the name)
  e    = 65537           (public exponent — a convention; 65537 = 2^16 + 1, few 1-bits = fast)
  d    = e^(-1) mod (p-1)(q-1)  (private exponent)

  Public key:  (n, e)   → distribute openly
  Private key: (n, d)   → never leaves the owner

Encryption (with OAEP padding):
  1. Encode plaintext with OAEP (Optimal Asymmetric Encryption Padding)
     OAEP adds randomness and structure, preventing several attacks on "textbook RSA"
  2. ciphertext = padded_plaintext^e mod n

Decryption:
  1. plaintext_padded = ciphertext^d mod n
  2. Remove OAEP padding → recover plaintext
```

Production failure modes — the attacks are almost never against the math:

**1. Textbook RSA (no padding) — deterministic and malleable:**
```python
# WRONG — no padding
ciphertext = pow(plaintext_int, e, n)

# Attack 1: Deterministic — same plaintext always → same ciphertext
# An attacker who knows the ciphertext for "YES" can identify all "YES" messages

# Attack 2: Multiplicative malleability
# If attacker knows ciphertext C = M^e mod n, they can compute:
# C' = (2^e × C) mod n = (2 × M)^e mod n
# The decryption of C' gives 2×M — attacker chose a related plaintext without knowing M

# CORRECT — OAEP padding (randomized, non-malleable)
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.hazmat.primitives import hashes

ciphertext = public_key.encrypt(
    plaintext,
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None
    )
)
```

**2. RSA-PKCS1v1.5 padding — Bleichenbacher attack:**
```
PKCS1v1.5 padding is the older padding scheme. If a server reveals whether
decryption produced valid PKCS1v1.5 padding (even via timing differences),
an attacker can mount a Bleichenbacher "million message attack" — sending
~1 million crafted ciphertexts and observing valid/invalid responses to
recover the plaintext without the private key.

CVEs: ROBOT attack (2017) affected F5, Citrix, Cisco, Check Point products.
The attack requires ~1 million chosen ciphertexts but is fully automated.

Mitigation: use OAEP, not PKCS1v1.5, for new systems.
If PKCS1v1.5 is required for legacy compatibility:
  - Use constant-time decryption
  - Never return distinct error messages for padding failures vs. other failures
  - Return a dummy plaintext on failure (constant-time error handling)
```

**3. Small key sizes — factorable:**
```
RSA-512:  Factored in 1999 (~1 month of compute)
RSA-768:  Factored in 2009 (~2 years of distributed compute)
RSA-1024: Within reach of nation-state adversaries (NIST deprecated 2013)
RSA-2048: Safe through ~2030 (NIST recommendation)
RSA-4096: Paranoia-level; ~4x slower than 2048 for marginal security gain

Recommendation: RSA-2048 minimum; prefer ECC (P-256 or X25519) for new systems
```

**4. Poor prime generation:**
```python
# The Fermat attack — if p and q are too close together, n is easy to factor
# p ≈ q means p ≈ √n — try integers near √n until a factor is found

# This happened in practice: some embedded systems with weak RNGs generated
# p and q with the same high bits → n was factored by Fermat's method in seconds

# Prevention: use a cryptographically secure prime generation library
# Never implement RSA key generation yourself — use the platform's library
from cryptography.hazmat.primitives.asymmetric import rsa

private_key = rsa.generate_private_key(
    public_exponent=65537,
    key_size=2048,           # minimum; prefer 4096 for long-lived keys
)
```

**Q8. What is Elliptic Curve Cryptography, and why is it preferred over RSA for new systems?**
A: ECC is a family of asymmetric cryptographic algorithms based on the algebraic structure of elliptic curves over finite fields. An elliptic curve is defined by the equation `y² = x³ + ax + b` over a finite field. The set of points on this curve, together with a point-addition operation, forms a mathematical group — and it is the discrete logarithm problem in this group that provides ECC's security.

```
Elliptic curve point multiplication:
  G = generator point (a specific point on the curve, publicly known)
  k = private key (a random integer)
  Q = k × G = G + G + ... + G (k times) = public key

  Easy:    Given k and G, compute Q = k × G
  Hard:    Given Q and G, find k  (the ECDLP — computationally infeasible for large curves)

ECDH key exchange (how two parties agree on a shared secret):
  Alice: private key a, public key A = a × G
  Bob:   private key b, public key B = b × G

  Alice computes: a × B = a × (b × G) = (a × b) × G
  Bob computes:   b × A = b × (a × G) = (a × b) × G

  Both arrive at the same point (a × b × G) — the shared secret
  Neither transmitted the private key; an eavesdropper sees only A and B
  Computing (a × b × G) from A and B requires solving ECDLP — infeasible
```

Why ECC over RSA for new systems:

```
Property          │ RSA-2048  │ ECC P-256 (equivalent security)
──────────────────┼───────────┼──────────────────────────────────
Security level    │ ~112 bits │ ~128 bits  (P-256 is stronger)
Key size          │ 2048 bits │ 256 bits   (8x smaller)
Public key size   │ 256 bytes │ 32-64 bytes
Signature size    │ 256 bytes │ 64 bytes   (ECDSA P-256)
Key generation    │ Slow      │ Fast
Sign/verify speed │ Slower    │ Faster
TLS handshake     │ Larger    │ Smaller certificates → faster handshake
Power consumption │ Higher    │ Lower (important for mobile, IoT)
```

**Specific ECC curves in production:**

```python
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey

# ECDH key agreement — use X25519 (Curve25519) for key exchange
# X25519: designed for ECDH specifically; immune to several implementation pitfalls
# that affect NIST curves (P-256, P-384); used in TLS 1.3, Signal, WireGuard

private_key = X25519PrivateKey.generate()
public_key  = private_key.public_key()

# Perform ECDH:
peer_public_key = ...  # received from the other party
shared_secret   = private_key.exchange(peer_public_key)
# shared_secret is 32 bytes — run through HKDF to derive an actual symmetric key

# Digital signatures — use Ed25519 (EdDSA on Curve25519)
# Ed25519: deterministic (no nonce needed — avoids the Sony PS3 ECDSA disaster),
# fast, small signatures (64 bytes), immune to side-channel attacks on nonce

signing_key    = Ed25519PrivateKey.generate()
verification_key = signing_key.public_key()

signature = signing_key.sign(message)               # 64 bytes
verification_key.verify(signature, message)         # raises if invalid

# NIST curves (P-256, P-384) — required for government/compliance contexts
# (FIPS 140-2 compliance requires NIST-approved curves)
private_key = ec.generate_private_key(ec.SECP256R1())   # P-256
```

**Q9. What is the difference between encryption and digital signatures in asymmetric cryptography?**
A: Both use asymmetric key pairs but in opposite directions and for different purposes:

```
Encryption — for confidentiality:
  Encrypt with PUBLIC key  → only the private key holder can decrypt
  "Anyone can lock, only the owner can unlock"
  Direction: public key encrypts, private key decrypts

  Use case: sending a secret message to a specific recipient.
  You have Bob's public key → encrypt for Bob → only Bob can decrypt.

Digital signature — for authenticity and integrity:
  Sign with PRIVATE key  → anyone with the public key can verify
  "Only the owner can sign, anyone can verify"
  Direction: private key signs, public key verifies

  Use case: proving that a message came from you and was not modified.
  Alice signs with her private key → anyone with Alice's public key verifies.
```

RSA in both modes (showing the key direction reversal):

```python
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key  = private_key.public_key()

# ── ENCRYPTION (public key encrypts, private key decrypts) ─────────────────────
ciphertext = public_key.encrypt(          # ← public key
    b"secret message",
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None
    )
)

plaintext = private_key.decrypt(          # ← private key
    ciphertext,
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None
    )
)

# ── DIGITAL SIGNATURE (private key signs, public key verifies) ─────────────────
signature = private_key.sign(             # ← private key
    b"message to authenticate",
    padding.PSS(
        mgf=padding.MGF1(hashes.SHA256()),
        salt_length=padding.PSS.MAX_LENGTH
    ),
    hashes.SHA256()
)

public_key.verify(                        # ← public key
    signature,
    b"message to authenticate",
    padding.PSS(
        mgf=padding.MGF1(hashes.SHA256()),
        salt_length=padding.PSS.MAX_LENGTH
    ),
    hashes.SHA256()
)
# verify() raises InvalidSignature if the signature is wrong or message was modified
```

In practice, signatures are never computed directly over large messages — that would be slow and leak message length. Instead, the message is hashed (SHA-256 or SHA-384), and the signature is computed over the hash:

```
Sign:   signature = RSA_Sign(private_key, SHA256(message))
Verify: is RSA_Verify(public_key, SHA256(message), signature) valid?

This is equivalent to signing the message but operates on a fixed 32-byte hash
regardless of message length. The security holds because SHA-256 is collision-resistant:
an attacker cannot find a different message with the same hash.
```

## Section 4: Key Management

**Q10. What is the key hierarchy model, and how do AWS KMS and HashiCorp Vault implement it?**
A: Directly managing raw encryption keys in application code is operationally dangerous — keys stored in config files, environment variables, or source code are frequently leaked. Key management systems implement a hierarchical model that keeps the most sensitive keys in hardware or heavily-protected software, and uses them only to protect less-sensitive keys.

```
Key Hierarchy:

Level 0: Hardware Security Module (HSM) — Root of Trust
  Contains: Root Keys (Master Keys)
  Never exported — operations performed inside the HSM
  HSM is tamper-evident physical hardware (or cloud HSM)

Level 1: Key Encryption Keys (KEKs) — wrapped by Root Keys
  Purpose: encrypt other keys
  Never directly encrypt data
  Examples: AWS KMS Customer Master Keys (CMKs), Vault Transit keys

Level 2: Data Encryption Keys (DEKs) — wrapped by KEKs
  Purpose: directly encrypt application data
  Generated fresh per record or per session
  Stored alongside the data in encrypted form (envelope encryption)

Level 3: Application Data — encrypted by DEKs
  The actual plaintext: credit card numbers, medical records, PII
```

**AWS KMS — envelope encryption pattern:**

```python
import boto3, os
from base64 import b64encode, b64decode

kms = boto3.client("kms", region_name="ap-south-1")
CMK_ARN = "arn:aws:kms:ap-south-1:123456789:key/mrk-abc123"

def encrypt_record(plaintext: bytes, context: dict) -> dict:
    """Envelope encryption: KMS generates a DEK, wraps it, we use it locally."""

    # Step 1: Ask KMS to generate a data key
    # KMS returns: plaintext DEK (for immediate use) + encrypted DEK (for storage)
    response = kms.generate_data_key(
        KeyId=CMK_ARN,
        KeySpec="AES_256",
        EncryptionContext=context,   # authenticated context — must match on decrypt
        # context = {"table": "users", "field": "ssn", "user_id": "123"}
        # Binds the key to a specific purpose — a DEK for SSNs cannot decrypt credit cards
    )

    dek_plaintext  = response["Plaintext"]        # 32 bytes — use immediately, then zero out
    dek_ciphertext = response["CiphertextBlob"]   # ~300 bytes — store alongside encrypted data

    # Step 2: Encrypt the actual data locally with the DEK (no KMS call for data)
    nonce      = os.urandom(12)
    aesgcm     = AESGCM(dek_plaintext)
    ciphertext = aesgcm.encrypt(nonce, plaintext, None)

    # Zero out the plaintext DEK from memory immediately after use
    # Python doesn't guarantee memory zeroing, but this is best practice
    del dek_plaintext

    return {
        "encrypted_dek": b64encode(dek_ciphertext).decode(),  # store in DB
        "nonce":         b64encode(nonce).decode(),           # store in DB
        "ciphertext":    b64encode(ciphertext).decode(),      # store in DB
        "context":       context,
    }

def decrypt_record(encrypted_record: dict) -> bytes:
    # Step 1: Ask KMS to decrypt the DEK (one KMS API call per decryption)
    response = kms.decrypt(
        CiphertextBlob=b64decode(encrypted_record["encrypted_dek"]),
        EncryptionContext=encrypted_record["context"],   # must match what was used to encrypt
    )
    dek_plaintext = response["Plaintext"]

    # Step 2: Decrypt data locally
    aesgcm  = AESGCM(dek_plaintext)
    return aesgcm.decrypt(
        b64decode(encrypted_record["nonce"]),
        b64decode(encrypted_record["ciphertext"]),
        None
    )

# Key rotation — KMS handles CMK rotation automatically (annual, or on-demand)
# For DEK rotation: re-encrypt existing data by decrypting with old DEK, re-encrypting with new
# KMS also supports key aliases and versioning for gradual rotation
```

**HashiCorp Vault Transit — encryption as a service:**

import hvac

**Q11. How do you implement field-level encryption for PII in a database, and what are the key design decisions?**
A: Field-level encryption encrypts specific sensitive columns before they reach the database — the database stores only ciphertext. Even a full database dump reveals no sensitive data.

```python
# models/encrypted_field.py — transparent field-level encryption

from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import boto3, os, json
from functools import lru_cache

class FieldEncryptor:
    """
    Encrypts individual database fields using envelope encryption.
    Each field uses a separate DEK — one compromised DEK exposes only that field.
    """

    def __init__(self, cmk_arn: str, region: str = "ap-south-1"):
        self.kms     = boto3.client("kms", region_name=region)
        self.cmk_arn = cmk_arn

    def encrypt_field(self, plaintext: str, context: dict) -> str:
        """Returns a self-contained encrypted blob suitable for DB storage."""
        # Generate a fresh DEK for this encryption
        dek_response = self.kms.generate_data_key(
            KeyId=self.cmk_arn,
            KeySpec="AES_256",
            EncryptionContext=context,
        )
        dek      = dek_response["Plaintext"]
        dek_enc  = dek_response["CiphertextBlob"]

        nonce    = os.urandom(12)
        aesgcm   = AESGCM(dek)
        ciphertext = aesgcm.encrypt(nonce, plaintext.encode("utf-8"), None)

        # Pack into a self-describing blob: version + encrypted_dek + nonce + ciphertext
        blob = {
            "v":   1,
            "dek": dek_enc.hex(),
            "n":   nonce.hex(),
            "ct":  ciphertext.hex(),
            "ctx": context,
        }
        return "ENC:" + json.dumps(blob, separators=(",", ":"))

    def decrypt_field(self, encrypted_blob: str) -> str:
        if not encrypted_blob.startswith("ENC:"):
            return encrypted_blob   # not encrypted — return as-is (migration period)

        blob = json.loads(encrypted_blob[4:])
        dek_response = self.kms.decrypt(
            CiphertextBlob=bytes.fromhex(blob["dek"]),
            EncryptionContext=blob["ctx"],
        )
        dek = dek_response["Plaintext"]

        aesgcm    = AESGCM(dek)
        plaintext = aesgcm.decrypt(
            bytes.fromhex(blob["n"]),
            bytes.fromhex(blob["ct"]),
            None
        )
        return plaintext.decode("utf-8")


# SQLAlchemy model with transparent encryption
from sqlalchemy import Column, String, event
from sqlalchemy.orm import DeclarativeBase

encryptor = FieldEncryptor(cmk_arn=os.environ["KMS_CMK_ARN"])

class User(DeclarativeBase):
    __tablename__ = "users"

    id    = Column(String, primary_key=True)
    email = Column(String)             # NOT encrypted — used for lookup
    _pan  = Column("pan", String)      # encrypted at rest — PAN card number
    _ssn  = Column("ssn", String)      # encrypted at rest

    @property
    def pan(self) -> str:
        if self._pan is None:
            return None
        return encryptor.decrypt_field(self._pan)

    @pan.setter
    def pan(self, value: str):
        if value is None:
            self._pan = None
            return
        context = {"table": "users", "field": "pan", "user_id": str(self.id)}
        self._pan = encryptor.encrypt_field(value, context)

# Key design decisions:
#
# 1. What granularity for DEKs?
#    Per-record: one DEK per user row — compromise of one DEK exposes one user
#    Per-field:  one DEK per field per user — most isolated, but highest KMS call volume
#    Per-table:  one DEK for all rows in a table — simple, but one DEK compromise = full table
#    Recommendation: per-record for high-sensitivity PII (SSN, PAN); per-table for lower
#
# 2. Searchability: encrypted fields cannot be queried with SQL WHERE
#    Solutions:
#    a. Blind index: store HMAC(secret_key, plaintext) alongside ciphertext
#       Query: WHERE blind_index = HMAC(key, search_term)
#       Reveals only equality — no ordering, no LIKE
#    b. Deterministic encryption (same plaintext → same ciphertext): allows equality search
#       but loses semantic security (patterns visible) — only for low-cardinality fields
#    c. Application-side search: load and decrypt candidate rows in the app layer
#       Only practical for small datasets
#
# 3. Indexing: store the context (table, field, user_id) with the encrypted blob
#    to prevent cross-context decryption — a PAN blob cannot be decrypted in
#    a context expecting a SSN (KMS EncryptionContext enforces this)
```

## Section 5: TLS and Real-World Protocol Application

**Q12. How does TLS 1.3 use both symmetric and asymmetric cryptography, and what changed from TLS 1.2?**
A: TLS 1.3 (RFC 8446) is the clearest real-world example of the hybrid model — asymmetric for key exchange, symmetric for data. TLS 1.3 simplified and hardened the protocol by removing all the weak options that TLS 1.2 accumulated over 20 years.

```
TLS 1.3 Handshake (1-RTT):

Client                                    Server
  │                                          │
  │── ClientHello ──────────────────────────►│
  │   Contains:                              │
  │   - Supported cipher suites             │
  │     (TLS_AES_256_GCM_SHA384,            │
  │      TLS_CHACHA20_POLY1305_SHA256)       │
  │   - Key share: client's ephemeral       │
  │     X25519 public key                   │
  │   - Supported TLS versions: [1.3]       │
  │                                          │
  │◄─── ServerHello ─────────────────────── │
  │     Contains:                            │
  │     - Chosen cipher suite               │
  │     - Server's ephemeral X25519 public  │
  │       key                               │
  │                                          │
  │     [Both sides now compute the shared  │
  │      secret via ECDH(X25519):           │
  │      shared = client_priv × server_pub  │
  │             = server_priv × client_pub  │
  │      HKDF derives handshake keys        │
  │      from shared secret + transcripts]  │
  │                                          │
  │◄─── {Certificate} ─────────────────────│ (encrypted with handshake key)
  │◄─── {CertificateVerify} ───────────────│ (server signs transcript with its private key)
  │◄─── {Finished} ────────────────────────│ (HMAC over transcript)
  │                                          │
  │── {Finished} ──────────────────────────►│
  │                                          │
  │◄══ Encrypted application data ═════════►│ (AES-256-GCM or ChaCha20-Poly1305)
```

**What TLS 1.3 removed from TLS 1.2:**
```
Removed (all were sources of vulnerabilities):
  RSA key exchange       — static; no forward secrecy; ROBOT attack
  DHE with <2048 bits    — Logjam attack
  RSA-PKCS1v1.5 in TLS   — Bleichenbacher/DROWN attacks
  CBC cipher suites       — BEAST, LUCKY13, POODLE attacks
  RC4                     — NOMORE attack, biases known since 1995
  MD5, SHA-1 in signatures— collision attacks
  Renegotiation           — various downgrade attacks
  Compression             — CRIME attack
  Export ciphers          — FREAK attack

What remains in TLS 1.3 cipher suites (only 5, all AEAD):
  TLS_AES_256_GCM_SHA384
  TLS_AES_128_GCM_SHA256
  TLS_CHACHA20_POLY1305_SHA256
  TLS_AES_128_CCM_SHA256
  TLS_AES_128_CCM_8_SHA256

Key exchange: only ECDHE (ephemeral) — mandatory forward secrecy
  - X25519 (most common)
  - P-256, P-384 (FIPS compliance)
  - X448 (ultra-paranoia)
```

**Forward secrecy** — the critical property TLS 1.3 mandates:

```
Without forward secrecy (TLS 1.2 RSA key exchange):
  Client encrypts the session key with the server's RSA public key
  If attacker records encrypted traffic today, and compromises the server's
  private key years later, they can decrypt ALL past sessions retroactively

With forward secrecy (ECDHE in TLS 1.3):
  Session keys are derived from ephemeral key pairs generated fresh per session
  Ephemeral private keys are discarded after the handshake
  Compromising the server's long-term private key later reveals nothing about
  past sessions — each session's key material is permanently gone

"Harvest now, decrypt later" attacks:
  Nation-state adversaries record TLS traffic today with the expectation
  that future quantum computers will break current asymmetric encryption.
  Forward secrecy limits the damage: only data encrypted with static RSA
  keys is vulnerable. ECDHE sessions are safe (the ephemeral keys are gone).
```

**Q13. What is the difference between RSA-PSS and RSA-PKCS1v1.5 for signatures, and which should you use?**
A: Both are RSA signature schemes but with fundamentally different security properties. PSS (Probabilistic Signature Scheme) is the modern standard; PKCS1v1.5 signatures are legacy.

```python
from cryptography.hazmat.primitives.asymmetric import padding, rsa
from cryptography.hazmat.primitives import hashes

private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key  = private_key.public_key()
message     = b"Transfer $50,000 to account 123456789"

# ── RSA-PKCS1v1.5 signatures (legacy) ────────────────────────────────────────
# Deterministic: same key + same message → same signature
# Vulnerable to Bleichenbacher-style attacks in some implementations
# Required by: old X.509 certificates, some legacy protocols

sig_v15 = private_key.sign(message, padding.PKCS1v15(), hashes.SHA256())
public_key.verify(sig_v15, message, padding.PKCS1v15(), hashes.SHA256())

# ── RSA-PSS (Probabilistic Signature Scheme — recommended) ───────────────────
# Randomized: same key + same message → different signature each time
# Provably secure (tight reduction to RSA hardness assumption)
# The random salt is embedded in the signature — verification still works
# Mandated by TLS 1.3 for RSA signatures; recommended by NIST

sig_pss = private_key.sign(
    message,
    padding.PSS(
        mgf=padding.MGF1(hashes.SHA256()),   # Mask Generation Function
        salt_length=padding.PSS.MAX_LENGTH,  # use maximum salt length
    ),
    hashes.SHA256()
)
public_key.verify(
    sig_pss,
    message,
    padding.PSS(
        mgf=padding.MGF1(hashes.SHA256()),
        salt_length=padding.PSS.AUTO,        # AUTO accepts any valid salt length
    ),
    hashes.SHA256()
)

# Recommendation:
# New systems: PSS (or use Ed25519 via ECC — avoids RSA entirely)
# Legacy compatibility: PKCS1v1.5 (but ensure constant-time verification)
# TLS 1.3: PSS is mandatory for RSA — no choice
```

## Section 6: Post-Quantum and Advanced Topics

**Q14. What is the quantum computing threat to current cryptography, and what is post-quantum cryptography?**
A: Quantum computers running Shor's algorithm (1994) can solve the integer factorization problem and the discrete logarithm problem in polynomial time — breaking RSA, ECC, DH, and ECDH. The asymmetric systems that underpin all of modern public-key cryptography would be broken. Grover's algorithm reduces the effective security of symmetric keys by half (256-bit AES becomes ~128-bit effective security against a quantum adversary) — mitigated by doubling key sizes.

```
Cryptographic impact of a cryptographically-relevant quantum computer (CRQC):

Algorithm      │ Classical Security │ Quantum Attack      │ Status
───────────────┼───────────────────┼─────────────────────┼──────────────
RSA-2048       │ ~112 bits         │ Shor's: broken      │ Vulnerable
ECDH P-256     │ ~128 bits         │ Shor's: broken      │ Vulnerable
Ed25519        │ ~128 bits         │ Shor's: broken      │ Vulnerable
AES-128        │ 128 bits          │ Grover's: ~64 bits  │ Upgrade to AES-256
AES-256        │ 256 bits          │ Grover's: ~128 bits │ Acceptable
SHA-256        │ 256 bits          │ Grover's: ~128 bits │ Acceptable
SHA-384        │ 384 bits          │ Grover's: ~192 bits │ Acceptable

Timeline uncertainty: experts estimate a CRQC capable of breaking RSA-2048
is 10-20 years away. "Harvest now, decrypt later" makes this urgent TODAY:
adversaries are recording TLS traffic now to decrypt when quantum computers mature.
Long-lived secrets (private keys, encrypted archives) are the highest risk.
```

**NIST Post-Quantum Cryptography Standardization (finalized 2024):**

```
NIST PQC Standards (FIPS 203, 204, 205):

ML-KEM (CRYSTALS-Kyber) — FIPS 203:
  Type:     Key Encapsulation Mechanism (replaces ECDH/RSA for key exchange)
  Hardness: Module Learning With Errors (MLWE) — unaffected by Shor's algorithm
  Key sizes: ML-KEM-768 has 1184-byte public key, 1088-byte ciphertext
             (larger than ECDH P-256's 32-byte keys — a real operational cost)
  Status:   Primary recommendation for key exchange

ML-DSA (CRYSTALS-Dilithium) — FIPS 204:
  Type:     Digital signature scheme (replaces ECDSA/Ed25519/RSA-PSS)
  Hardness: Module Learning With Errors (MLWE)
  Status:   Primary recommendation for signatures

SLH-DSA (SPHINCS+) — FIPS 205:
  Type:     Digital signature scheme (hash-based — conservative choice)
  Hardness: Security of hash functions only — different assumption from Kyber/Dilithium
  Tradeoff: Very large signatures (~8-50 KB) but minimal assumption set
  Status:   Secondary recommendation; use when diversity of assumptions is required
```

**Migration strategy — hybrid classical + post-quantum:**

```python
# The recommended transition approach: hybrid key exchange
# Combine classical ECDH with ML-KEM — attacker must break BOTH to compromise session
# If classical ECDH is broken by quantum: ML-KEM protects
# If ML-KEM has an undiscovered flaw: ECDH protects

# TLS 1.3 hybrid groups (deployed by Cloudflare, Google, AWS in 2024):
# X25519Kyber768Draft00 — X25519 ECDH + Kyber768

# In Python (using liboqs via oqs-python):
import oqs

# ML-KEM key encapsulation
kem = oqs.KeyEncapsulation("ML-KEM-768")
server_public_key = kem.generate_keypair()

# Client side:
ciphertext, shared_secret_client = kem.encap_secret(server_public_key)

# Server side:
shared_secret_server = kem.decap_secret(ciphertext)

assert shared_secret_client == shared_secret_server   # both derived the same secret

# Hybrid: XOR or HKDF-combine the classical ECDH shared secret with ML-KEM shared secret
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

combined_secret = HKDF(
    algorithm=hashes.SHA256(),
    length=32,
    salt=None,
    info=b"hybrid-key-exchange",
).derive(ecdh_shared_secret + mlkem_shared_secret)
# The combined key is secure if EITHER component is secure
```

**Q15. What is a padding oracle attack, and how does it exploit symmetric encryption improperly?**
A: A padding oracle attack is a chosen-ciphertext attack that exploits an implementation that reveals whether decrypted ciphertext has valid padding. The attacker does not need the key — the decryption oracle (the server's error response or timing difference) acts as a "yes/no" binary signal that enables byte-by-byte recovery of the plaintext.

```
Setup: AES-CBC with PKCS#7 padding
PKCS#7 padding rule: if the last block needs N bytes of padding,
fill with N bytes each of value N:
  [data][data][data][0x04][0x04][0x04][0x04]   ← valid 4-byte padding
  [data][data][data][0x00][0x01][0x02][0x03]   ← invalid (not PKCS#7 format)

The oracle: server returns distinct responses for:
  "Decryption succeeded"              (valid padding)
  "Padding error" or 500 with delay   (invalid padding)

The attack — recovering one byte of plaintext:
  Attacker intercepts: [C1_block][C2_block]
  Goal: determine P2[16] (last byte of second plaintext block)

  In CBC: P2[i] = Decrypt(C2[i]) XOR C1[i]
  Attacker controls C1 — by modifying C1[16], they modify P2[16]

  Trial loop:
    For guess g in 0..255:
      Set C1'[16] = C1[16] XOR g XOR 0x01
      Send [C1'][C2] to server
      If server says "valid padding":
        P2[16] XOR C1'[16] = 0x01  (valid 1-byte padding)
        P2[16] = 0x01 XOR C1'[16] = 0x01 XOR C1[16] XOR g XOR 0x01 = C1[16] XOR g
        Plaintext byte recovered after at most 256 attempts

  Repeat for all bytes: recover entire plaintext with ~256 × 16 × blocks server queries

Real-world attacks:
  POODLE (2014): SSL 3.0 CBC padding oracle — all HTTPS traffic vulnerable
  Lucky13 (2013): TLS CBC timing oracle (0.05ms timing difference exploitable)
  BEAST (2011): TLS 1.0 CBC IV predictability
  ASP.NET padding oracle (2010): ViewState decryption error leaked padding validity
```

Prevention:

```python
# Wrong: decrypt then check padding — leaks timing information
def vulnerable_decrypt(ciphertext: bytes, key: bytes) -> bytes:
    decrypted = aes_cbc_decrypt(ciphertext, key)
    if not valid_pkcs7_padding(decrypted):    # ← branching on padding validity
        raise PaddingError("Invalid padding") # ← distinct error = oracle
    return remove_padding(decrypted)

# Correct: use AEAD (AES-GCM) — authentication failure before any decryption attempt
# AES-GCM verifies the authentication tag BEFORE decrypting
# A modified ciphertext fails the tag check — no padding is ever checked
# No oracle exists because the error path reveals nothing about the plaintext

from cryptography.hazmat.primitives.ciphers.aead import AESGCM

def correct_decrypt(ciphertext: bytes, key: bytes, nonce: bytes) -> bytes:
    aesgcm = AESGCM(key)
    # If tag verification fails: raises InvalidTag immediately
    # The error is: "authentication failed" — not "padding invalid"
    # No timing difference between different types of invalid ciphertext
    return aesgcm.decrypt(nonce, ciphertext, None)
```

The lesson: **always use AEAD modes (AES-GCM, ChaCha20-Poly1305)**. They authenticate before decrypting, eliminating the entire class of padding oracle, bit-flipping, and chosen-ciphertext attacks that plague AES-CBC.

## Section 7: Scenario-Based Questions

**Q16. Scenario: "Your team is designing an API that stores users' bank account numbers (PAN, routing number) in a PostgreSQL database. Design the encryption strategy end-to-end."**
A: This requires field-level encryption with envelope key management, searchability via blind indexes, and audit logging — not just "add AES somewhere."

```
Threat model:
  - Database breach (SQL injection, insider threat, cloud misconfiguration)
  - Application code breach (leaked environment variables, compromised CI/CD)
  - KMS compromise (highly unlikely if using AWS KMS with proper IAM)
  - "Harvest now, decrypt later" (encrypted data recorded, decrypted later)

Encryption strategy:

1. Key hierarchy:
   AWS KMS CMK (never leaves KMS hardware)
     └── Per-record DEK (generated by KMS, stored encrypted in the DB)
            └── Actual field value (encrypted locally with the DEK)

   The CMK is managed by KMS — rotated annually automatically.
   The DEK is generated fresh for each user record — one compromised DEK
   exposes one user's data, not all users.

2. Field selection — what to encrypt:
   Encrypt:   account_number, routing_number, pan_card, aadhaar_number
   Don't encrypt: user_id (primary key — needed for JOINs), email (needed for
   lookup queries), created_at (needed for time-range queries)
   Encrypt separately: each sensitive field uses a different KMS EncryptionContext
   so a DEK for account_number cannot decrypt routing_number.

3. Searchability — encrypted fields can't be WHERE-queried:
   Add a blind index column alongside each encrypted field:
   blind_account_number = HMAC-SHA256(blind_index_secret, normalize(account_number))
   Query: WHERE blind_account_number = HMAC-SHA256(secret, search_term)
   The blind index secret is a separate secret stored in Vault (not KMS) —
   different key hierarchy from the encryption key.
   Blind index reveals only equality — an attacker with the DB dump cannot
   recover account numbers from HMAC values without the blind index secret.

4. Database schema:
   CREATE TABLE bank_accounts (
     id                    UUID PRIMARY KEY,
     user_id               UUID NOT NULL REFERENCES users(id),
     -- Encrypted fields:
     account_number_enc    TEXT NOT NULL,   -- "ENC:{json blob with dek+nonce+ct}"
     routing_number_enc    TEXT NOT NULL,
     -- Blind indexes for searchability:
     account_number_blind  CHAR(64) NOT NULL,  -- HMAC-SHA256 hex
     routing_number_blind  CHAR(64) NOT NULL,
     -- Unencrypted metadata:
     account_type          TEXT NOT NULL,    -- "checking", "savings"
     bank_name             TEXT NOT NULL,
     created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
     -- Audit:
     last_accessed_at      TIMESTAMPTZ,
     access_count          INT DEFAULT 0
   );

   CREATE INDEX idx_account_blind ON bank_accounts(account_number_blind);
   -- No index on the encrypted column itself (unguessable ciphertext is random)

5. Application layer:
   Decrypt only when the value is actually needed for display or processing.
   Never decrypt in batch queries ("load all accounts" should NOT return
   decrypted values — load only the encrypted blob and decrypt on demand).
   Log every decryption event to an audit table:
   INSERT INTO pii_access_log (user_id, field, accessed_by, reason, timestamp)

6. Key rotation plan:
   CMK rotation: AWS KMS handles automatically (annual or on-demand)
   DEK rotation: quarterly job re-encrypts account_number_enc by:
     a. KMS.Decrypt(old DEK)
     b. KMS.GenerateDataKey() → new DEK
     c. AES-GCM.Encrypt(new DEK, plaintext)
     d. Store new encrypted blob
   Blind index secret rotation: requires recomputing all blind indexes —
   coordinated migration, typically done with a blue/green database strategy.

7. Access control:
   IAM policy: only the loans-service IAM role can call KMS:Decrypt for the loans CMK
   DB IAM: application user has SELECT/INSERT/UPDATE on bank_accounts — no DROP
   KMS resource policy: explicit Deny for all principals except loans-service role
```

**Q17. Scenario: "A developer on your team proposes using AES-256-CBC with a hardcoded IV of all zeros for encrypting API tokens stored in Redis. Identify every problem and propose the correct solution."**
A: This proposal has four independent critical vulnerabilities:

```
Problem 1: Hardcoded IV of all zeros — deterministic encryption
  CBC requires a unique, random IV per encryption.
  A hardcoded IV means: Encrypt(key, token_A) always → same ciphertext_A
  Attack: if an attacker learns the ciphertext for one known token, they can
  identify any other occurrence of that token (ciphertext equality = token equality).
  More critically: if two different plaintexts share a common prefix (e.g., all
  tokens start with "tok_"), their CBC ciphertext blocks are identical up to
  the first difference — prefix structure is leaked.

Problem 2: CBC without authentication — malleable ciphertext
  AES-CBC provides confidentiality only — it has no integrity protection.
  An attacker can flip bits in the ciphertext, causing predictable, controlled
  changes to the decrypted plaintext. This enables bit-flipping attacks.
  Example: flip bit 7 of the ciphertext → bit 7 of the plaintext flips →
  attacker may escalate "role=user" to "role=admin" with the right byte position.

Problem 3: Key management — where does the AES-256 key live?
  The proposal doesn't address key storage. If it's an environment variable or
  config file, it's likely committed to git or visible in container definitions.
  A hardcoded key in source code is a Critical severity finding.

Problem 4: Wrong tool for the job — tokens don't need decryptable storage
  API tokens are used for authentication: the server checks "is this a valid token?"
  There is no need to decrypt them — the server issued them and can store a hash.
  Encrypting tokens is the wrong mental model. Hashing is correct.
  If the token must be decryptable (e.g., it contains embedded claims), use JWTs.

Correct solution:

# For API tokens stored in Redis — hash, don't encrypt
import hashlib, hmac, secrets

def generate_api_token() -> tuple[str, str]:
    """Returns (raw_token for client, hashed_token for storage)."""
    raw_token   = "tok_" + secrets.token_urlsafe(32)   # 256 bits entropy
    token_hash  = hashlib.sha256(raw_token.encode()).hexdigest()
    return raw_token, token_hash

def store_token(token_hash: str, user_id: str, expiry: int, redis):
    redis.setex(
        f"api_token:{token_hash}",
        expiry,
        user_id,
    )

def validate_token(raw_token: str, redis) -> str | None:
    token_hash = hashlib.sha256(raw_token.encode()).hexdigest()
    user_id    = redis.get(f"api_token:{token_hash}")
    return user_id.decode() if user_id else None

# If the token genuinely must be encrypted (rare — e.g., embedding a session key):
# Use AES-256-GCM with:
# - Key from KMS (not hardcoded)
# - Random 12-byte nonce per encryption (not hardcoded zero)
# - Prepend nonce to ciphertext for storage

from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

KEY = bytes.fromhex(os.environ["REDIS_ENCRYPTION_KEY_HEX"])  # 32 bytes from KMS
aesgcm = AESGCM(KEY)

def encrypt_for_redis(plaintext: bytes) -> bytes:
    nonce = os.urandom(12)                            # fresh nonce, never reused
    ct    = aesgcm.encrypt(nonce, plaintext, None)    # includes 16-byte GCM tag
    return nonce + ct                                 # prepend nonce for storage

def decrypt_from_redis(stored: bytes) -> bytes:
    nonce, ct = stored[:12], stored[12:]
    return aesgcm.decrypt(nonce, ct, None)            # raises on tampered data
```

## Quick Reference: Algorithm Selection Guide

```
SYMMETRIC ENCRYPTION
  Encrypt data at rest or in transit (known key):
    First choice:  AES-256-GCM (hardware AES-NI available)
    Alternative:   ChaCha20-Poly1305 (no AES-NI, mobile, IoT)
    Never:         AES-ECB, AES-CBC without separate MAC, RC4, DES, 3DES

  Password → key derivation:
    First choice:  Argon2id (memory-hard, PHC winner)
    Alternative:   scrypt (memory-hard, widely supported)
    Legacy only:   PBKDF2-HMAC-SHA256 (600,000+ iterations)
    Never:         MD5, SHA-1, SHA-256 directly (no stretching)

ASYMMETRIC ENCRYPTION / KEY EXCHANGE
  New systems:    X25519 (ECDH) for key agreement
  FIPS required:  ECDH P-256 or P-384
  Legacy compat:  RSA-2048 minimum; RSA-OAEP padding only
  Never:          RSA-PKCS1v1.5 encryption, DH < 2048-bit, RSA < 2048-bit

DIGITAL SIGNATURES
  New systems:    Ed25519 (fast, deterministic, small sigs)
  FIPS required:  ECDSA P-256 with SHA-256, or RSA-PSS
  JWT signing:    RS256 (RSA-PSS) for multi-service; HS256 only for single-service
  Never:          RSA-PKCS1v1.5 for new code, MD5/SHA-1 in signatures

HASHING (non-cryptographic use)
  Data integrity: SHA-256 or SHA-3-256
  Password hash:  Argon2id, bcrypt (work factor ≥ 12), scrypt
  HMAC:           HMAC-SHA256 or HMAC-SHA512 (for blind indexes, API tokens)
  Never:          MD5, SHA-1 for security purposes

KEY SIZES
  AES:  256-bit (128-bit acceptable for non-regulated; avoid for new)
  RSA:  2048-bit minimum; 4096 for long-lived CA keys
  ECC:  P-256 (128-bit security); P-384 (192-bit); X25519 preferred
  HMAC: 256-bit key minimum (match the HMAC output size)

POST-QUANTUM (transition plan)
  Key exchange:   ML-KEM-768 (FIPS 203) — hybrid with X25519 during transition
  Signatures:     ML-DSA-65 (FIPS 204) — hybrid with Ed25519 during transition
  Symmetric:      AES-256 is adequate (Grover's halves it to 128-bit effective)
  Priority:       Long-lived keys and archived data first (highest "harvest now" risk)
```

**Tip for the interview:** At 5 YOE, the symmetric vs asymmetric question almost never stays at the "what is it" level — it goes immediately to "why does TLS use both?" (Q3 — hybrid model, performance trade-off) and "what algorithm would you use for X?" (the selection guide at the end). Know AES-GCM vs CBC cold: AEAD vs confidentiality-only, why nonce reuse is catastrophic for GCM, why CBC's padding oracle class exists (Q15). For asymmetric, the depth probes are: RSA key size and why 1024-bit is broken (Q7), why OAEP over PKCS1v1.5 (Q7), and the encryption vs signature key direction distinction (Q9 — a question that many candidates get backwards). The KMS envelope encryption pattern (Q10) is essential for fintech — know the generate_data_key flow, what EncryptionContext does, and why you store the encrypted DEK alongside the data. The field-level encryption scenario (Q16) and the AES-CBC zero-IV scenario (Q17) are common senior-level closes — Q17 especially tests whether you can identify all four independent vulnerabilities (hardcoded IV, CBC without auth, key management, wrong tool) rather than just the most obvious one.
