## Section 1: Fundamentals and Signal Taxonomy

**Q1. What is a fraud detection signal, and how does the signal taxonomy map to a fintech architecture?**
A: A fraud detection signal is any observable data point that correlates with fraudulent behavior. No single signal is definitive — fraud systems are probabilistic, combining dozens of signals into a risk score that drives a decision (allow, challenge, decline, flag for review). The taxonomy matters because different signal classes arrive at different latencies, have different reliability characteristics, and require different infrastructure to compute.

```
Signal taxonomy by source:

Identity signals         — who is the user claiming to be?
  Device fingerprint, IP, email age, phone number age, biometric match,
  document verification score, selfie liveness, address validation

Behavioral signals       — does this action match the user's normal pattern?
  Transaction velocity, amount deviation, time-of-day pattern, merchant
  category history, typing cadence, mouse movement entropy, session duration

Network / contextual     — what does the environment tell us?
  IP geolocation, ISP type (datacenter vs residential), VPN/Tor detection,
  IP reputation score, browser language vs IP country, timezone mismatch

Transaction signals      — does this specific transaction look suspicious?
  First use of a new account, round-number amounts, high-value threshold
  crossing, merchant MCC risk category, cross-border flag, card-not-present

Velocity signals         — is there unusual frequency or pattern over time?
  Transactions per hour/day, new payees added in a session, failed auth
  attempts, password resets, OTP requests, devices added

Relationship signals     — what does the graph of connections reveal?
  Shared device across accounts, shared phone, shared IP with known-bad accounts,
  money flow to flagged recipients, account age at first high-value transaction

Historical signals       — what is this entity's track record?
  Prior disputes, chargeback rate, account standing, linked account behavior,
  consortium signals from other banks/FIs (shared fraud intelligence)
```

The architecture that consumes these signals in a real system:

```
                     ┌──────────────────────────────────┐
  Transaction        │  Real-time scoring engine         │  Decision
  event ────────────▶│  (<100ms SLA)                    │─────────▶  Allow / Challenge / Decline
                     │  Consumes: precomputed features   │
                     │  from feature store               │
                     └──────────────────┬───────────────┘
                                        │
          ┌─────────────────────────────▼──────────────────────────┐
          │  Feature Store (Redis + Flink)                         │
          │  Precomputed, continuously updated:                    │
          │  tx_count_24h, avg_amount_30d, new_device_flag,       │
          │  ip_country_mismatch, velocity_score, ...              │
          └───────────────────────────────────────────────────────┘
                    ▲                              ▲
          ┌─────────┴──────────┐       ┌──────────┴──────────┐
          │ Stream processor   │       │ Batch processor      │
          │ (Flink/Kafka)      │       │ (Spark, nightly)     │
          │ Real-time feature  │       │ Long-window features │
          │ updates            │       │ (30d, 90d, 365d)     │
          └────────────────────┘       └─────────────────────┘
```

**Q2. What is the difference between rule-based fraud detection and ML-based fraud detection, and why do production systems use both?**
A: Rule-based and ML-based systems have complementary failure modes — one's weakness is the other's strength. Every mature fraud system is a hybrid.

**Rule-based systems:**
```
Structure: IF [condition] THEN [action]

Examples:
  IF amount > 500000 AND account_age_days < 7 THEN block
  IF country(ip) != country(registered_phone) AND amount > 10000 THEN step_up
  IF tx_count_last_hour > 5 AND merchant_category = 'crypto' THEN decline
  IF is_new_payee AND amount > avg_amount_30d * 3 THEN hold_for_review

Strengths:
  + Interpretable — compliance and ops teams can explain every decision to a regulator
  + Instant deployment — a new rule is live in minutes
  + Zero training data required — useful for novel attack patterns
  + Deterministic — the same input always produces the same output
  + Easy to A/B test — turn a rule on/off for a subset of traffic

Weaknesses:
  - Rule explosion — a well-tuned production system has hundreds of rules;
    interactions between rules are hard to reason about
  - Static — attackers learn the rules and craft transactions that barely miss
  - High false positive rate — broad rules block legitimate users
  - Cannot discover complex patterns — a rule for "time between transactions
    correlates with scripted automation" is not expressible as a simple threshold
```

**ML-based systems:**
```
Structure: model(feature_vector) → risk_score ∈ [0, 1]

Common models:
  Gradient Boosted Trees (XGBoost, LightGBM) — tabular data, interpretable feature importance
  Neural networks — sequence models for behavioral patterns (LSTM, Transformer)
  Graph Neural Networks — detect fraud rings via account relationship graphs
  Isolation Forest — anomaly detection without labeled fraud data
  Logistic Regression — fast, highly interpretable baseline

Strengths:
  + Discovers non-obvious feature combinations human analysts wouldn't write rules for
  + Adapts to evolving attack patterns (with retraining)
  + Lower false positive rate than rules at equivalent recall
  + Handles high-dimensional feature spaces naturally

Weaknesses:
  - Black box — "the model scored this 0.94" is not an explanation a regulator accepts
  - Training data dependency — requires labeled historical fraud data to train
  - Model drift — fraud patterns change; a model trained 6 months ago may miss new attacks
  - Cold start — no signal for brand-new users with no history
  - Adversarial fragility — a determined attacker with white-box access to the model
    can craft adversarial inputs that score low while committing fraud
```

**Why both — the ensemble architecture:**
```python
# Scoring pipeline: rules + ML, combined

def score_transaction(tx: Transaction, user: User, context: RequestContext) -> FraudDecision:

    # Layer 1: Hard rules — instant block/allow with no ML cost
    hard_block = evaluate_hard_rules(tx, user, context)
    if hard_block.triggered:
        return FraudDecision(
            action="BLOCK",
            reason=hard_block.rule_name,  # explainable to regulator and user
            score=1.0,
        )

    # Layer 2: Hard allow — known-safe patterns skip ML (reduces latency + cost)
    hard_allow = evaluate_allowlist_rules(tx, user, context)
    if hard_allow.triggered:
        return FraudDecision(action="ALLOW", score=0.0, reason="trusted_pattern")

    # Layer 3: ML risk score — for the ambiguous middle
    features = build_feature_vector(tx, user, context)
    ml_score  = fraud_model.predict_proba(features)[1]  # P(fraud)

    # Layer 4: Soft rules — override ML score for specific conditions
    if context.is_new_device and ml_score > 0.3:
        ml_score = min(ml_score * 1.5, 1.0)   # amplify on new device
    if user.trust_tier == "platinum" and ml_score < 0.7:
        ml_score *= 0.6                         # dampen for trusted users

    # Layer 5: Decision thresholds — tuned for business tolerance
    if ml_score > 0.85:
        action = "BLOCK"
    elif ml_score > 0.50:
        action = "STEP_UP"   # trigger 2FA / OTP challenge
    elif ml_score > 0.25:
        action = "REVIEW"    # flag for human review queue
    else:
        action = "ALLOW"

    return FraudDecision(
        action=action,
        score=ml_score,
        features=features.top_contributors(),   # for explainability
    )
```

## Section 2: Velocity and Behavioral Signals

**Q3. What are velocity signals, how do you compute them in real time, and what attack patterns do they detect?**
A: Velocity signals measure the rate of events over time windows — how many transactions, how many failed attempts, how many new payees, how much money moved, across fixed time windows (1h, 24h, 7d, 30d). They detect scripted automation, account takeover sprints, and money mule activity.

```python
# Velocity feature computation using Redis — O(1) per read, sliding window

import redis
import time
from dataclasses import dataclass
from typing import Optional

r = redis.Redis(host="redis.internal", port=6379, decode_responses=True)

@dataclass
class VelocityFeatures:
    tx_count_1h:        int
    tx_count_24h:       int
    tx_count_7d:        int
    amount_sum_1h:      float
    amount_sum_24h:     float
    distinct_payees_1h: int
    distinct_merchants_24h: int
    failed_attempts_1h: int
    new_devices_7d:     int

def record_transaction(user_id: str, tx_id: str, amount: float, payee_id: str, merchant_id: str):
    now    = int(time.time())
    pipe   = r.pipeline()

    # Sliding window: store event timestamps in a sorted set (score = timestamp)
    # Trim old entries; TTL keeps the key alive only as long as needed

    # Transaction count windows
    for window_s, key_suffix in [(3600, "1h"), (86400, "24h"), (604800, "7d")]:
        key = f"v:tx_count:{user_id}:{key_suffix}"
        pipe.zadd(key, {tx_id: now})
        pipe.zremrangebyscore(key, 0, now - window_s)
        pipe.expire(key, window_s)

    # Amount sum — store (tx_id, amount) pair; sum the values
    for window_s, key_suffix in [(3600, "1h"), (86400, "24h")]:
        key = f"v:amount:{user_id}:{key_suffix}"
        pipe.zadd(key, {f"{tx_id}:{amount}": now})
        pipe.zremrangebyscore(key, 0, now - window_s)
        pipe.expire(key, window_s)

    # Distinct payees — set of payee_ids seen in the window
    payee_key = f"v:payees:{user_id}:1h"
    pipe.sadd(payee_key, payee_id)
    pipe.expire(payee_key, 3600)

    pipe.execute()

def get_velocity_features(user_id: str) -> VelocityFeatures:
    now  = int(time.time())
    pipe = r.pipeline()

    # Counts from sorted sets
    pipe.zcount(f"v:tx_count:{user_id}:1h",  now - 3600,   now)
    pipe.zcount(f"v:tx_count:{user_id}:24h", now - 86400,  now)
    pipe.zcount(f"v:tx_count:{user_id}:7d",  now - 604800, now)

    # Amount sums require fetching and summing amounts from the sorted set values
    pipe.zrangebyscore(f"v:amount:{user_id}:1h",  now - 3600,  now)
    pipe.zrangebyscore(f"v:amount:{user_id}:24h", now - 86400, now)

    # Distinct payees
    pipe.scard(f"v:payees:{user_id}:1h")

    results = pipe.execute()

    # Parse amount sums from "tx_id:amount" strings
    def sum_amounts(entries):
        total = 0.0
        for entry in entries:
            try:
                total += float(entry.split(":")[-1])
            except (ValueError, IndexError):
                pass
        return total

    return VelocityFeatures(
        tx_count_1h=results[0],
        tx_count_24h=results[1],
        tx_count_7d=results[2],
        amount_sum_1h=sum_amounts(results[3]),
        amount_sum_24h=sum_amounts(results[4]),
        distinct_payees_1h=results[5],
        distinct_merchants_24h=0,   # computed similarly
        failed_attempts_1h=0,       # computed from auth events
        new_devices_7d=0,           # computed from device events
    )
```

Attack patterns detected by velocity signals:

```
Account Takeover (ATO) sprint:
  Attacker gains access → immediately drains the account.
  Signal: tx_count_1h spikes from user's baseline (usually 0-2) to 10+
          amount_sum_1h far exceeds 30-day average daily spend
          distinct_payees_1h = many new payees (attacker's mule accounts)
  Rule: IF tx_count_1h > 5 AND (distinct_payees_1h / tx_count_1h) > 0.8 THEN block

Card testing / enumeration:
  Attacker has a list of stolen card numbers; tests small amounts to find valid ones.
  Signal: many low-amount transactions (₹1, ₹10) to the same merchant in short succession
          failed_attempts_1h elevated (invalid cards declined)
  Rule: IF amount < 50 AND tx_count_1h > 3 AND failed_attempts_1h > 2 THEN block + alert

Money mule activity:
  Account receives many small inbound transfers, immediately sends one large outbound.
  Signal: inbound_count_24h high, outbound_sum / inbound_sum close to 1.0 (pass-through),
          time_between_inbound_and_outbound very short
  Rule: IF inbound_count_24h > 3 AND outbound_within_1h_of_inbound = True
           AND outbound_amount > 0.9 * inbound_sum THEN flag_for_review

Credential stuffing:
  Automated bot tries username/password pairs from a breach database.
  Signal: failed_login_attempts per IP very high (100+/minute from one IP)
          failed attempts distributed across many user accounts
  Signal: same device fingerprint across multiple account login attempts
  Rule: IF failed_login_count_1h > 10 FROM same_ip THEN captcha + rate_limit
```

**Q4. What are behavioral biometric signals, and how do they detect account takeover?**
A: Behavioral biometrics capture the unconscious, highly individual patterns in how a person interacts with a device — typing rhythm, mouse movement, touch pressure, scrolling behavior, device orientation. These patterns are nearly impossible for an attacker to replicate, even with the correct credentials. They are collected passively in the browser/app and compared to a stored baseline for the account.

```javascript
// Client-side behavioral signal collection (browser SDK)

class BehavioralSignalCollector {
    constructor(sessionId, userId) {
        this.sessionId   = sessionId;
        this.userId      = userId;
        this.keystroke   = [];
        this.mouseMove   = [];
        this.touchEvents = [];
        this.startTime   = Date.now();
        this._bindEvents();
    }

    _bindEvents() {
        // Keystroke dynamics: time between key down and key up, inter-key interval
        document.addEventListener("keydown", e => {
            this.keystroke.push({
                t:   Date.now() - this.startTime,
                k:   e.key.length === 1 ? "char" : e.key,  // don't capture actual chars
                dn:  Date.now(),   // keydown timestamp
                evt: "dn"
            });
        });

        document.addEventListener("keyup", e => {
            const last = this.keystroke.findLast(k => k.evt === "dn");
            if (last) {
                this.keystroke.push({
                    t:        Date.now() - this.startTime,
                    dwell:    Date.now() - last.dn,   // how long key was held (ms)
                    evt:      "up"
                });
            }
        });

        // Mouse dynamics: movement speed, acceleration, click patterns
        let lastMouseEvent = null;
        document.addEventListener("mousemove", e => {
            const now = Date.now();
            if (lastMouseEvent) {
                const dt = now - lastMouseEvent.t;
                if (dt > 0) {
                    const dx    = e.clientX - lastMouseEvent.x;
                    const dy    = e.clientY - lastMouseEvent.y;
                    const speed = Math.sqrt(dx*dx + dy*dy) / dt;
                    this.mouseMove.push({ t: now - this.startTime, speed, dt });
                }
            }
            lastMouseEvent = { t: now, x: e.clientX, y: e.clientY };
        });

        // Touch pressure and area (mobile) — harder to fake
        document.addEventListener("touchstart", e => {
            if (e.touches[0]) {
                this.touchEvents.push({
                    t:       Date.now() - this.startTime,
                    force:   e.touches[0].force || 0,   // 0-1 (if supported)
                    area:    e.touches[0].radiusX * e.touches[0].radiusY,
                    evt:     "start"
                });
            }
        });
    }

    extractFeatures() {
        // Aggregate raw events into features for transmission
        const keyDwells = this.keystroke
            .filter(k => k.dwell !== undefined)
            .map(k => k.dwell);

        const mouseSpeeds = this.mouseMove.map(m => m.speed);

        return {
            // Typing rhythm features
            keystroke_mean_dwell:    mean(keyDwells),
            keystroke_std_dwell:     std(keyDwells),
            keystroke_count:         keyDwells.length,

            // Mouse movement features
            mouse_mean_speed:        mean(mouseSpeeds),
            mouse_speed_variance:    variance(mouseSpeeds),
            mouse_movement_count:    this.mouseMove.length,

            // Session-level features
            session_duration_ms:     Date.now() - this.startTime,
            page_idle_ratio:         this._computeIdleRatio(),

            // Touch features (mobile)
            touch_mean_force:        mean(this.touchEvents.map(t => t.force)),
            touch_mean_area:         mean(this.touchEvents.map(t => t.area)),
        };
    }

    async submit() {
        const features = this.extractFeatures();
        // Send to backend — do not include raw keystrokes, only aggregated features
        await fetch("/api/behavioral-signals", {
            method: "POST",
            headers: {"Content-Type": "application/json"},
            body: JSON.stringify({
                session_id: this.sessionId,
                user_id:    this.userId,
                features,
            }),
        });
    }

    _computeIdleRatio() {
        // Ratio of time with no keyboard/mouse events — automated bots have near-zero idle
        // Humans naturally pause; bots execute at constant high speed
        const totalDuration = Date.now() - this.startTime;
        const activeTime    = this.keystroke.length * 200 + this.mouseMove.length * 50;
        return Math.max(0, 1 - (activeTime / totalDuration));
    }
}
```

```python
# Server-side: compare session features against stored user baseline

import numpy as np
from sklearn.metrics.pairwise import cosine_similarity
from scipy.spatial.distance import mahalanobis

class BehavioralBaseline:
    """Stores and compares behavioral biometric features for a user."""

    def __init__(self, user_id: str, db):
        self.user_id = user_id
        self.db      = db

    def update_baseline(self, session_features: dict) -> None:
        """Update the rolling baseline with new session features — EMA smoothing."""
        stored = self.db.get_baseline(self.user_id)
        alpha  = 0.1   # exponential moving average — weight for new observation

        if stored is None:
            # First session — establish baseline directly
            self.db.save_baseline(self.user_id, session_features)
            return

        # Smoothed update: new_baseline = alpha * new + (1-alpha) * old
        updated = {}
        for key, new_val in session_features.items():
            old_val = stored.get(key, new_val)
            updated[key] = alpha * new_val + (1 - alpha) * old_val

        self.db.save_baseline(self.user_id, updated)

    def compute_anomaly_score(self, session_features: dict) -> float:
        """
        Compare session features against the stored baseline.
        Returns a score in [0, 1] where 1 = maximally anomalous.

        Uses Z-score distance from stored mean and variance.
        A legitimate user's features cluster around their baseline.
        An attacker using stolen credentials has different behavioral patterns.
        """
        baseline = self.db.get_baseline(self.user_id)
        if baseline is None:
            return 0.5   # no baseline → neutral score (new user)

        z_scores = []
        feature_keys = [
            "keystroke_mean_dwell", "keystroke_std_dwell",
            "mouse_mean_speed", "mouse_speed_variance",
            "page_idle_ratio", "touch_mean_force"
        ]

        for key in feature_keys:
            if key not in session_features or key not in baseline:
                continue
            stored_mean = baseline.get(f"{key}_mean", baseline.get(key, 0))
            stored_std  = baseline.get(f"{key}_std", 1.0)

            if stored_std < 1e-6:
                continue   # avoid division by zero for constant features

            z = abs(session_features[key] - stored_mean) / stored_std
            z_scores.append(z)

        if not z_scores:
            return 0.5

        # Anomaly score: mean Z-score normalized to [0, 1]
        # Z-score of 2 = 2 standard deviations from baseline → high anomaly
        mean_z = np.mean(z_scores)
        score  = 1 - np.exp(-mean_z / 2)   # sigmoid-like mapping
        return float(np.clip(score, 0, 1))
```

Attack patterns detected by behavioral biometrics:

```
Account Takeover via credential stuffing:
  Attacker uses a bot to log in with correct password.
  Signal: keystroke_mean_dwell is 0 (bot doesn't press keys — it fills forms programmatically)
          page_idle_ratio near 0 (bot has no idle time — executes at machine speed)
          mouse_movement_count = 0 or very low (bot doesn't move the mouse)
          session_duration very short (bot navigates directly to transfer page)

Account Takeover via stolen credentials (human attacker):
  Human attacker uses the correct password on a different device.
  Signal: behavioral profile is entirely different from the legitimate owner
          keystroke_mean_dwell outside 3σ of baseline (different typing rhythm)
          device fingerprint mismatch (different OS, browser, screen resolution)
          IP in a different country from the user's normal locations

Session hijacking (cookie theft):
  Attacker replays a stolen session cookie.
  Signal: session picks up mid-flow without any keystroke/mouse events preceding it
          User agent changes within the same session (attacker has different browser)
          IP address changes mid-session (session token used from a different location)
```

## Section 3: Device and Network Signals

**Q5. What is a device fingerprint, how is it constructed, and what fraud patterns does it detect?**
A: A device fingerprint is a composite identifier derived from attributes of a device and its software environment. Unlike cookies (which the user can clear) or IP addresses (which change), a fingerprint is computed from hardware and browser characteristics that are difficult to change and collectively unique.

```javascript
// Device fingerprint construction (client-side)

async function computeDeviceFingerprint() {
    const components = {};

    // ── Hardware signals ──────────────────────────────────────────────────────
    components.screen_resolution = `${screen.width}x${screen.height}`;
    components.screen_depth      = screen.colorDepth;
    components.device_memory     = navigator.deviceMemory || "unknown";   // GB
    components.hardware_concurrency = navigator.hardwareConcurrency || 0; // CPU cores
    components.max_touch_points  = navigator.maxTouchPoints;
    components.platform          = navigator.platform;   // "Win32", "MacIntel", "Linux armv8l"

    // ── Browser signals ───────────────────────────────────────────────────────
    components.user_agent        = navigator.userAgent;
    components.languages         = navigator.languages.join(",");
    components.timezone_offset   = new Date().getTimezoneOffset();
    components.timezone          = Intl.DateTimeFormat().resolvedOptions().timeZone;
    components.do_not_track      = navigator.doNotTrack;

    // ── Plugin and font signals ───────────────────────────────────────────────
    components.plugins = Array.from(navigator.plugins || [])
        .map(p => p.name).sort().join("|");

    // Canvas fingerprint — how the browser renders graphics is GPU/driver specific
    const canvas    = document.createElement("canvas");
    const ctx       = canvas.getContext("2d");
    ctx.textBaseline = "top";
    ctx.font        = "14px Arial";
    ctx.fillStyle   = "#f60";
    ctx.fillRect(125, 1, 62, 20);
    ctx.fillStyle   = "#069";
    ctx.fillText("FP canvas test 👾", 2, 15);
    ctx.fillStyle   = "rgba(102, 204, 0, 0.7)";
    ctx.fillText("FP canvas test 👾", 4, 17);
    components.canvas_fp = canvas.toDataURL();

    // WebGL fingerprint — GPU vendor and renderer string is highly specific
    const gl = canvas.getContext("webgl");
    if (gl) {
        const ext = gl.getExtension("WEBGL_debug_renderer_info");
        if (ext) {
            components.webgl_vendor   = gl.getParameter(ext.UNMASKED_VENDOR_WEBGL);
            components.webgl_renderer = gl.getParameter(ext.UNMASKED_RENDERER_WEBGL);
        }
    }

    // Audio fingerprint — subtle differences in audio processing pipeline
    try {
        const audioCtx  = new (window.AudioContext || window.webkitAudioContext)();
        const oscillator = audioCtx.createOscillator();
        const analyser   = audioCtx.createAnalyser();
        const gain       = audioCtx.createGain();
        gain.gain.value  = 0;   // silent — no audio output
        oscillator.connect(analyser);
        analyser.connect(gain);
        gain.connect(audioCtx.destination);
        oscillator.start(0);
        const data = new Float32Array(analyser.frequencyBinCount);
        analyser.getFloatFrequencyData(data);
        components.audio_fp = data.slice(0, 50).reduce((a, b) => a + Math.abs(b), 0);
        oscillator.stop();
        await audioCtx.close();
    } catch (e) {
        components.audio_fp = "unavailable";
    }

    // Hash the components into a single fingerprint ID
    const fpString = JSON.stringify(components);
    const hashBuffer = await crypto.subtle.digest(
        "SHA-256",
        new TextEncoder().encode(fpString)
    );
    const fingerprint = Array.from(new Uint8Array(hashBuffer))
        .map(b => b.toString(16).padStart(2, "0"))
        .join("");

    return { fingerprint, components };
}
```

```python
# Server-side: device fingerprint fraud signals

class DeviceFingerprintService:

    def __init__(self, db, redis):
        self.db    = db
        self.redis = redis

    def analyze(self, fingerprint: str, user_id: str, components: dict) -> dict:
        signals = {}

        # Signal 1: Is this a new device for this user?
        known_devices = self.db.get_user_devices(user_id)
        signals["is_new_device"] = fingerprint not in known_devices

        # Signal 2: How many accounts has this device been seen with?
        accounts_for_device = self.db.get_accounts_for_fingerprint(fingerprint)
        signals["device_account_count"] = len(accounts_for_device)
        signals["device_is_multi_account"] = len(accounts_for_device) > 1

        # Fraud ring signal: same device logging into many accounts
        # Legitimate: a family shares a device (2-3 accounts is normal)
        # Fraud: a device seen with 10+ accounts = mule farm or enumeration tool

        # Signal 3: Known bad device (from consortium or prior fraud)
        signals["device_is_blocklisted"] = self.redis.sismember(
            "blocked_fingerprints", fingerprint
        )

        # Signal 4: Fingerprint consistency — does the browser lie?
        ua_platform = self._extract_platform_from_ua(components.get("user_agent", ""))
        fp_platform = components.get("platform", "")
        signals["platform_mismatch"] = (
            ua_platform is not None and
            fp_platform and
            ua_platform.lower() not in fp_platform.lower()
        )
        # A bot spoofing a desktop user agent but running on Linux ARM
        # will have a User-Agent saying "Windows" but platform = "Linux armv8l"

        # Signal 5: Headless browser / automation detection
        signals["is_likely_bot"] = self._detect_automation(components)

        # Signal 6: Device fingerprint age
        first_seen = self.db.get_fingerprint_first_seen(fingerprint)
        if first_seen:
            age_days = (datetime.utcnow() - first_seen).days
            signals["device_age_days"] = age_days
        else:
            signals["device_age_days"] = 0  # brand new device

        return signals

    def _detect_automation(self, components: dict) -> bool:
        """Detect Selenium, Puppeteer, Playwright, and other automation tools."""
        ua = components.get("user_agent", "").lower()

        # Automation tool fingerprints
        automation_signals = [
            "headless" in ua,                          # HeadlessChrome in UA
            components.get("webgl_vendor") == "",      # Headless Chrome has no WebGL vendor
            components.get("plugins") == "",           # No plugins in headless
            components.get("hardware_concurrency") == 0,
            components.get("canvas_fp") == "data:,",  # Empty canvas in some headless envs
            components.get("audio_fp") == 0,          # No audio processing in headless
        ]
        return sum(automation_signals) >= 2   # two or more signals = likely automated

    def _extract_platform_from_ua(self, ua: str) -> str | None:
        import re
        patterns = {
            "windows": r"windows nt",
            "mac":     r"macintosh|mac os x",
            "linux":   r"linux(?! arm| android)",
            "android": r"android",
            "ios":     r"iphone|ipad",
        }
        for platform, pattern in patterns.items():
            if re.search(pattern, ua, re.IGNORECASE):
                return platform
        return None
```

**Q6. What are IP-based signals, and what are their limitations?**

```
Limitation 1: Shared IPs (NAT, CGN, corporate proxies)
  A corporate proxy may route 500 employees through one IP.
  Blocking the IP blocks all 500 employees.

Limitation 5: Geolocation accuracy degrades for mobile and IPv6
```

## Section 4: Transaction and Graph Signals

**Q7. What are transaction-level signals, and how do you detect specific fraud patterns using them?**
A: Transaction signals are properties of the individual transaction itself — the amount, the payee, the merchant, the timing, the channel. Unlike velocity signals (which measure rates), transaction signals evaluate a single event.

```python
# Transaction signal computation

from decimal import Decimal
from dataclasses import dataclass
from datetime import datetime, time
import pytz

@dataclass
class TransactionSignals:
    is_round_amount:        bool   # ₹10000, ₹50000 — humans prefer round numbers
    amount_z_score:         float  # how many std devs from user's mean
    is_new_payee:           bool   # first time sending to this account
    days_since_payee_added: int    # payees used immediately after adding are risky
    is_nighttime:           bool   # transactions in 2am-5am local time
    is_weekend:             bool
    is_first_large_transaction: bool  # first tx > X in account history
    amount_exceeds_threshold:   bool  # crosses regulatory reporting threshold
    mcc_risk_level:         str   # "low", "medium", "high", "prohibited"
    is_international:       bool
    is_card_not_present:    bool
    payee_account_age_days: int   # very new payee accounts are risky
    channel:                str   # "mobile_app", "web", "api", "upi"

HIGH_RISK_MCC = {
    "7995",  # Gambling
    "6051",  # Cryptocurrency exchanges
    "5912",  # Drug stores (can be money laundering vector)
    "7273",  # Dating services
    "5999",  # Misc retail (catch-all for unclassified merchants)
}

def compute_transaction_signals(
    tx: dict,
    user: dict,
    user_history: dict,
    payee: dict,
) -> TransactionSignals:

    amount = Decimal(str(tx["amount"]))

    # Round amount detection — fraud amounts are often round to avoid detection
    is_round = (amount % 1000 == 0) or (amount % 500 == 0)

    # Z-score of amount vs user's 30-day history
    hist_mean = Decimal(str(user_history.get("amount_mean_30d", amount)))
    hist_std  = Decimal(str(user_history.get("amount_std_30d", 1)))
    amount_z  = float((amount - hist_mean) / hist_std) if hist_std > 0 else 0.0

    # Payee signals
    payee_added_at = payee.get("added_at")
    days_since_add = (
        (datetime.utcnow() - payee_added_at).days
        if payee_added_at else 999
    )

    # Timing signals — convert to user's local timezone
    user_tz  = pytz.timezone(user.get("timezone", "Asia/Kolkata"))
    tx_local = datetime.fromtimestamp(tx["timestamp"], tz=user_tz)
    tx_hour  = tx_local.hour
    is_night = tx_hour < 5 or tx_hour >= 23  # 11pm to 5am
    is_weekend = tx_local.weekday() >= 5

    # Regulatory threshold — PMLA (Prevention of Money Laundering Act, India)
    # Transactions ≥ ₹50,000 may require additional KYC verification
    # Structuring: multiple transactions just below ₹50,000 is a red flag
    PMLA_THRESHOLD = Decimal("50000")
    is_near_threshold = (
        amount >= PMLA_THRESHOLD * Decimal("0.9") and
        amount < PMLA_THRESHOLD
    )  # ₹45,000–₹49,999 range = potential structuring

    # First large transaction for this account
    is_first_large = (
        amount > Decimal("100000") and
        user_history.get("max_transaction_ever", 0) < 100000
    )

    return TransactionSignals(
        is_round_amount=is_round,
        amount_z_score=amount_z,
        is_new_payee=(days_since_add == 0),
        days_since_payee_added=days_since_add,
        is_nighttime=is_night,
        is_weekend=is_weekend,
        is_first_large_transaction=is_first_large,
        amount_exceeds_threshold=amount >= PMLA_THRESHOLD,
        mcc_risk_level="high" if tx.get("mcc") in HIGH_RISK_MCC else "low",
        is_international=tx.get("currency") != user.get("default_currency"),
        is_card_not_present=tx.get("channel") in ("api", "web"),
        payee_account_age_days=payee.get("account_age_days", 0),
        channel=tx.get("channel", "unknown"),
    )
```

Specific fraud patterns detected by transaction signals:

```
Structuring / Smurfing:
  Splitting a large transaction into many smaller ones just below reporting thresholds.
  Signal: multiple transactions in 24h where each is 90-99% of the threshold
          total_amount_24h > threshold but no single tx exceeds it
  Detection: is_near_threshold=True for multiple transactions in a session

Social Engineering / Authorized Push Payment (APP) Fraud:
  Victim is manipulated into initiating a legitimate-looking transfer to a fraudster.
  Signals: is_new_payee=True, days_since_payee_added=0, amount_z_score > 3,
           is_first_large_transaction=True, payee_account_age_days < 30
  These signals together (not individually) indicate a probable APP fraud pattern.
  Response: step up with an explicit "did you verify this payee?" warning

Refund Fraud / Friendly Fraud:
  User makes a purchase then claims they never received it for a chargeback.
  Signals: high chargeback_rate_90d, purchase_then_dispute_time_days < 3,
           multiple dispute attempts, same merchant multiple chargebacks
```

**Q8. What are graph-based fraud signals, and how do you detect fraud rings?**
A: Graph-based signals model the relationships between entities (users, accounts, devices, phone numbers, IP addresses) as a graph. Fraud rings — coordinated groups of fake or compromised accounts — appear as tightly connected clusters that would not be visible by analyzing any single account in isolation.

```python
# Graph signal computation using NetworkX (production: Apache TinkerPop / Neo4j)

import networkx as nx
from collections import defaultdict

class FraudGraphAnalyzer:
    """
    Constructs a bipartite graph of:
      User nodes ─── edge (shared attribute) ─── Attribute nodes
    where attributes are: devices, phone numbers, email domains,
    IP addresses, bank accounts, referral codes, etc.

    A cluster of users sharing multiple attributes = potential fraud ring.
    """

    def __init__(self, db):
        self.db = db
        self.G  = nx.Graph()

    def build_neighborhood(self, user_id: str, hop_depth: int = 2) -> nx.Graph:
        """Build the local subgraph around a user up to N hops."""
        visited_users = set()
        frontier      = {user_id}

        for _ in range(hop_depth):
            next_frontier = set()
            for uid in frontier:
                if uid in visited_users:
                    continue
                visited_users.add(uid)

                # Fetch all shared attributes for this user
                connections = self.db.get_user_connections(uid)
                # Returns: [{"type": "device", "value": "fp_abc", "connected_users": [...]}]

                for conn in connections:
                    attr_node = f"{conn['type']}:{conn['value']}"
                    self.G.add_edge(uid, attr_node, attr_type=conn["type"])

                    for connected_user in conn["connected_users"]:
                        self.G.add_edge(attr_node, connected_user, attr_type=conn["type"])
                        next_frontier.add(connected_user)

            frontier = next_frontier - visited_users

        return self.G

    def compute_graph_signals(self, user_id: str) -> dict:
        graph = self.build_neighborhood(user_id, hop_depth=2)
        signals = {}

        # Signal 1: How many other user accounts share a device with this user?
        shared_device_users = self._count_shared_attribute_users(
            user_id, "device", graph
        )
        signals["shared_device_account_count"] = shared_device_users
        # Legitimate: 1-2 (household members sharing a tablet)
        # Suspicious: 5+ accounts on the same device fingerprint

        # Signal 2: How many accounts in the neighborhood have been marked as fraud?
        known_fraud_users = {
            n for n in graph.nodes()
            if not n.startswith(("device:", "phone:", "ip:", "email:"))
            and self.db.is_user_fraudulent(n)
        }
        signals["fraud_neighbor_count"] = len(known_fraud_users)
        signals["is_connected_to_known_fraud"] = len(known_fraud_users) > 0

        # Signal 3: Clustering coefficient of the user's neighborhood
        # Fraud rings: very high clustering (everyone knows everyone)
        # Legitimate users: low clustering (connections are diverse)
        try:
            clustering = nx.clustering(graph, user_id)
            signals["neighborhood_clustering"] = clustering
        except Exception:
            signals["neighborhood_clustering"] = 0.0

        # Signal 4: Number of distinct shared attributes
        shared_attrs = [
            n for n in graph.neighbors(user_id)
            if any(n.startswith(t) for t in ["device:", "phone:", "ip:"])
        ]
        signals["shared_attribute_count"] = len(shared_attrs)

        # Signal 5: Account age distribution of neighbors
        neighbor_users = [
            n for n in nx.single_source_shortest_path_length(graph, user_id, cutoff=2)
            if n != user_id and not any(
                n.startswith(t) for t in ["device:", "phone:", "ip:", "email:"]
            )
        ]
        if neighbor_users:
            ages = [self.db.get_account_age_days(u) for u in neighbor_users]
            signals["neighbor_mean_account_age"] = sum(ages) / len(ages)
            # Fraud rings: many newly created accounts clustered together
            signals["neighbor_new_account_ratio"] = sum(1 for a in ages if a < 30) / len(ages)

        return signals

    def _count_shared_attribute_users(
        self, user_id: str, attr_type: str, graph: nx.Graph
    ) -> int:
        shared_users = set()
        for attr_node in graph.neighbors(user_id):
            if attr_node.startswith(f"{attr_type}:"):
                for neighbor in graph.neighbors(attr_node):
                    if neighbor != user_id:
                        shared_users.add(neighbor)
        return len(shared_users)
```

## Section 6: Decision Systems and Feedback Loops

**Q10. How do you handle the false positive vs false negative trade-off in fraud detection thresholds?**
A: Every fraud decision threshold is a business decision, not just a technical one. Lowering the threshold catches more fraud (lower false negative rate) but blocks more legitimate users (higher false positive rate). The optimal threshold depends on the cost of fraud vs the cost of friction/churn.

```python
# Threshold optimization using precision-recall curves

import numpy as np
from sklearn.metrics import precision_recall_curve, roc_auc_score

def find_optimal_threshold(
    y_true:  np.ndarray,   # 1 = fraud, 0 = legitimate
    y_scores: np.ndarray,  # model's predicted P(fraud)
    cost_fn: float,        # cost of a false negative (missed fraud) in ₹
    cost_fp: float,        # cost of a false positive (blocked legitimate tx) in ₹
) -> dict:
    """
    Find the threshold that minimizes total cost:
      Total cost = FN_count × cost_fn + FP_count × cost_fp

    cost_fn = average fraud loss per missed transaction (₹500–₹50,000)
    cost_fp = estimated customer lifetime value lost per false block (₹2,000–₹10,000)
              or just: average revenue per transaction × churn probability

    In a typical fintech:
      cost_fn >> cost_fp for high-value transactions (don't miss fraud)
      cost_fn ≈ cost_fp for low-value transactions (friction is costly)
    """
    thresholds = np.arange(0.05, 0.95, 0.01)
    results    = []

    for t in thresholds:
        predicted  = (y_scores >= t).astype(int)
        TP = np.sum((predicted == 1) & (y_true == 1))
        FP = np.sum((predicted == 1) & (y_true == 0))
        TN = np.sum((predicted == 0) & (y_true == 0))
        FN = np.sum((predicted == 0) & (y_true == 1))

        total_cost  = FN * cost_fn + FP * cost_fp
        precision   = TP / (TP + FP) if (TP + FP) > 0 else 0
        recall      = TP / (TP + FN) if (TP + FN) > 0 else 0
        fpr         = FP / (FP + TN) if (FP + TN) > 0 else 0

        results.append({
            "threshold":   t,
            "total_cost":  total_cost,
            "precision":   precision,
            "recall":      recall,   # = True Positive Rate = fraud catch rate
            "fpr":         fpr,      # False Positive Rate = legitimate block rate
            "TP": TP, "FP": FP, "TN": TN, "FN": FN,
        })

    # Find threshold with minimum total cost
    optimal = min(results, key=lambda r: r["total_cost"])
    return {
        "optimal_threshold":  optimal["threshold"],
        "expected_recall":    optimal["recall"],      # % of fraud caught
        "expected_fpr":       optimal["fpr"],         # % of legit users blocked
        "estimated_cost_saving": results[0]["total_cost"] - optimal["total_cost"],
        "all_results":        results,
    }

# Multi-threshold decision system:
# Don't use one threshold — use a tiered system to match response to risk

DECISION_THRESHOLDS = {
    "BLOCK":    0.85,   # decline outright — high confidence fraud
    "STEP_UP":  0.50,   # trigger OTP/biometric challenge — medium risk
    "REVIEW":   0.25,   # flag for analyst queue — low-medium risk
    "ALLOW":    0.0,    # below REVIEW threshold — allow
}
# Thresholds should be tuned per transaction type:
# High-value transfers: lower thresholds (stricter)
# Small UPI payments: higher thresholds (less friction)
# International transfers: always STEP_UP minimum
```

**Q11. How do you close the feedback loop — training the model on the outcomes of its own decisions?**
A: A fraud model that makes decisions creates survivorship bias in its own training data. Transactions it blocks never complete — so you never know if they were truly fraudulent or false positives. Without correcting for this, the model trains on a biased subset and gradually degrades.

```python
# Feedback loop architecture

class FraudFeedbackPipeline:
    """
    Collects ground truth labels for model retraining.
    Ground truth sources:
      1. Chargebacks and disputes filed by users
      2. Manual review queue decisions by fraud analysts
      3. Law enforcement reports
      4. Account closure for fraud reasons
      5. Consortium data from other banks (shared fraud intelligence)
    """

    def process_chargeback(self, tx_id: str, reason: str) -> None:
        """A user disputed a transaction — label it as fraud (strong signal)."""
        self.db.execute("""
            INSERT INTO fraud_labels (tx_id, label, source, confidence, created_at)
            VALUES (%s, 'fraud', 'chargeback', 0.95, NOW())
            ON CONFLICT (tx_id) DO UPDATE SET label = 'fraud', confidence = 0.95
        """, (tx_id,))

        # Also update velocity features — chargeback_rate_90d for the user
        tx = self.db.get_transaction(tx_id)
        self.feature_store.increment(
            f"features:user:{tx['user_id']}",
            "chargeback_count_90d"
        )

    def process_analyst_decision(self, tx_id: str, decision: str, analyst_id: str) -> None:
        """
        Fraud analyst reviewed a flagged transaction.
        decision: "fraud" | "legitimate" | "uncertain"
        """
        confidence = {"fraud": 0.85, "legitimate": 0.90, "uncertain": 0.50}[decision]
        self.db.execute("""
            INSERT INTO fraud_labels (tx_id, label, source, confidence, analyst_id, created_at)
            VALUES (%s, %s, 'analyst_review', %s, %s, NOW())
        """, (tx_id, decision, confidence, analyst_id))

    def handle_survivorship_bias(self) -> None:
        """
        Counterfactual evaluation: some BLOCKED transactions were legitimate.
        Estimate the false positive rate on blocked transactions by:
        1. Random sampling: allow a small % of transactions that score just above BLOCK threshold
        2. Label them via normal outcome monitoring (chargebacks, account flags)
        This gives ground truth on the blocked population.
        """
        # 1% of transactions scoring 0.85–0.95 are allowed through for evaluation
        # This is the "exploration" portion of the explore-exploit trade-off
        # The cost is real fraud slipping through, but it's necessary for model quality

    def generate_training_dataset(self, lookback_days: int = 90) -> pd.DataFrame:
        """
        Assembles labeled training data for model retraining.
        Joins transactions with their outcomes and feature snapshots.
        """
        return self.db.query("""
            SELECT
                t.id,
                t.user_id,
                t.amount,
                t.created_at,
                fs.feature_snapshot,    -- features AT TIME OF TRANSACTION (not current)
                fl.label,
                fl.confidence
            FROM transactions t
            JOIN feature_snapshots fs ON fs.tx_id = t.id
            LEFT JOIN fraud_labels fl ON fl.tx_id = t.id
            WHERE t.created_at > NOW() - INTERVAL '%s days'
              AND fl.label IS NOT NULL   -- only labeled examples
              AND fl.confidence > 0.7   -- minimum label quality
        """, (lookback_days,))

    # Model retraining schedule:
    # Triggered by: time (weekly), or by drift detection (PSI > threshold)
    # Feature drift: monitor Population Stability Index of each feature
    # Performance drift: monitor precision/recall on the holdout set weekly
    # Concept drift: fraud patterns change — a model trained on card testing
    #   may not catch voice phishing (vishing) scams 6 months later
```

```python
# Step 1: Characterize the attack — pull signals from the last 3 hours

def triage_fraud_spike(db, redis, start_time: datetime) -> dict:
    # How are the fraudulent transactions clustered?
    fraud_txs = db.query("""
        SELECT
            t.*,
            u.account_age_days,
            u.kyc_tier,
            u.last_login_ip,
            d.fingerprint,
            COUNT(*) OVER (PARTITION BY t.user_id) as user_tx_count
        FROM transactions t
        JOIN users u ON u.id = t.user_id
        LEFT JOIN device_sessions d ON d.session_id = t.session_id
        WHERE t.created_at > %s
          AND t.id IN (SELECT tx_id FROM chargebacks WHERE created_at > %s)
        ORDER BY t.created_at DESC
        LIMIT 1000
    """, (start_time, start_time))

    analysis = {
        # Are the source accounts clustered or distributed?
        "unique_source_accounts":    len(set(t["user_id"] for t in fraud_txs)),
        "unique_dest_accounts":      len(set(t["payee_id"] for t in fraud_txs)),

        # Concentration signals
        "top_5_dest_accounts":       Counter(t["payee_id"] for t in fraud_txs).most_common(5),
        "top_5_source_ips":          Counter(t["last_login_ip"] for t in fraud_txs).most_common(5),
        "top_5_device_fingerprints": Counter(t["fingerprint"] for t in fraud_txs).most_common(5),

        # Timing pattern — is this automated?
        "tx_per_minute":             len(fraud_txs) / ((datetime.utcnow() - start_time).seconds / 60),
        "amount_distribution":       [float(t["amount"]) for t in fraud_txs],

        # Account age distribution — newly created accounts?
        "mean_account_age":          np.mean([t["account_age_days"] for t in fraud_txs]),
        "new_account_ratio":         sum(1 for t in fraud_txs if t["account_age_days"] < 7) / len(fraud_txs),
    }
    return analysis
```

**Q13. Scenario: "A product manager asks you to add a new signal: whether the user's registered phone number is active (via telecom lookup). How do you evaluate if this signal is worth the investment?"**
A: Signal evaluation requires measuring lift — does this signal improve the model's ability to distinguish fraud from legitimate traffic, and does the improvement justify the cost and latency?

```python
# Signal evaluation framework

class SignalEvaluationFramework:

    def evaluate_new_signal(
        self,
        signal_name:     str,
        labeled_dataset: pd.DataFrame,  # historical transactions with fraud labels
        signal_values:   pd.Series,     # the new signal computed for historical data
    ) -> dict:
        """
        Evaluates a new signal's contribution to fraud detection.
        labeled_dataset must have: tx_id, label (1=fraud, 0=legit), existing_score
        signal_values: the new signal value for each tx_id
        """
        df = labeled_dataset.copy()
        df[signal_name] = signal_values

        # 1. Mutual Information — how much does the signal reduce uncertainty about fraud?
        from sklearn.feature_selection import mutual_info_classif
        mi_score = mutual_info_classif(
            df[[signal_name]].fillna(df[signal_name].median()),
            df["label"]
        )[0]

        # 2. AUC lift — does adding this signal improve the model?
        baseline_auc = roc_auc_score(df["label"], df["existing_score"])

        # Train a model with and without the new signal on a validation set
        from sklearn.linear_model import LogisticRegression
        from sklearn.model_selection import cross_val_score

        X_base = df[existing_feature_cols].fillna(0)
        X_new  = pd.concat([X_base, df[[signal_name]].fillna(0)], axis=1)

        base_auc = cross_val_score(
            LogisticRegression(), X_base, df["label"], cv=5, scoring="roc_auc"
        ).mean()

        new_auc  = cross_val_score(
            LogisticRegression(), X_new,  df["label"], cv=5, scoring="roc_auc"
        ).mean()

        auc_lift = new_auc - base_auc

        # 3. Distribution analysis — does the signal separate fraud from legit?
        fraud_dist = df[df["label"] == 1][signal_name].describe()
        legit_dist = df[df["label"] == 0][signal_name].describe()

        # 4. Null rate — how often is the signal unavailable (API timeout, missing data)?
        null_rate = df[signal_name].isna().mean()

        # 5. Latency cost — does the signal fit in our real-time budget?
        # Telecom lookup APIs: typically 50-300ms p99
        # Our scoring budget: 100ms total → telecom lookup takes 50-300% of budget
        # → Must be async/precomputed or only triggered for step-up decisions

        return {
            "signal_name":        signal_name,
            "mutual_information": mi_score,
            "baseline_auc":       base_auc,
            "new_auc":            new_auc,
            "auc_lift":           auc_lift,      # > 0.005 = meaningful improvement
            "null_rate":          null_rate,      # > 0.10 = signal has coverage gaps
            "fraud_mean":         fraud_dist["mean"],
            "legit_mean":         legit_dist["mean"],
            "separation":         abs(fraud_dist["mean"] - legit_dist["mean"]),

            # Cost-benefit
            "api_cost_per_call":  0.002,    # USD, example for telecom lookup
            "daily_tx_volume":    500_000,
            "daily_api_cost":     0.002 * 500_000,   # $1,000/day if called on all txs

            # Recommendation
            "recommendation": (
                "ADOPT"       if auc_lift > 0.005 and null_rate < 0.05 else
                "ADOPT_ASYNC" if auc_lift > 0.003 else
                "REJECT"
            ),
        }

# For the phone number liveness signal specifically:
# Typical result:
#   AUC lift: 0.003–0.008 (moderate improvement — phone porting is correlated with ATO)
#   Latency: 80–200ms p99 (too slow for synchronous scoring)
#   Null rate: 5–15% (some numbers not found in telco databases)
#   Cost: $1,000/day at 500k transactions
#
# Recommendation: Adopt as a pre-session signal
#   - Check phone number liveness at LOGIN time, not at transaction time
#   - If phone was recently ported (< 7 days): flag session as elevated risk
#   - Store the result in the feature store → zero latency at transaction scoring
#   - Cost reduction: check only on login, not every transaction (~10x fewer calls)
```
