## Section 1: Fundamentals and Threat Models

**Q1. What is the difference between data masking, tokenization, and field-level encryption, and when is each the right tool?**
A: The three techniques are often conflated but solve distinct problems with different trade-offs. Choosing the wrong one creates either a false sense of security or unnecessary operational complexity.

**Data masking** replaces sensitive values with a visually similar but non-recoverable substitute. The original value is either discarded (static masking) or not stored at all (dynamic masking at display time). Masking is one-way — the original cannot be recovered from the masked value.

```
Input:   4532 1234 5678 9012   (full card number)
Masked:  **** **** **** 9012   (last 4 digits only — useful for "which card did I use?")
         XXXX-XXXX-XXXX-9012   (alternative format)
         4532 **** **** ****   (first 4 for BIN identification)
```

**Tokenization** replaces a sensitive value with a randomly generated, meaningless surrogate (a token). The mapping between the token and the original value is stored in a separate, heavily protected token vault. The token has the same format as the original (a 16-digit number replacing a 16-digit PAN) — it is referentially consistent and can be stored in systems that expect the original format. Tokenization is reversible — authorized parties can detokenize by querying the vault.

```
Input:   4532 1234 5678 9012   (real PAN)
Token:   9173 4821 0034 7651   (random 16-digit surrogate — same format, no mathematical relation)
Vault:   { "9173482100347651": "4532123456789012" }  (stored in HSM-backed vault)

Systems downstream (order management, CRM) store the token.
Only the payment processor (authorized) can detokenize to charge the card.
```

**Field-level encryption (FLE)** encrypts specific fields before they reach the database. The ciphertext is stored in the database; the plaintext only exists in the application layer and in transit. Unlike tokenization, FLE is cryptographic — the original can be recovered by anyone with the key, not by querying a vault. The key management model determines who can decrypt.

```
Input:   4532 1234 5678 9012
Stored:  ENC:v1:3f8a...  (AES-256-GCM ciphertext of the PAN, opaque to the database)

Anyone with the DEK + CMK access can recover the original.
The database server itself cannot decrypt — it only stores ciphertext.
```

**Selection guide:**

| Requirement | Correct tool | Reason |
|---|---|---|
| Display "Card ending in 9012" | Masking | Irreversible — store only the suffix, discard the rest |
| PCI-DSS: remove PAN from application scope | Tokenization | Format-preserving, reversible by vault only, reduces PCI scope |
| GDPR right-to-erasure of PII | Field-level encryption | Rotate/destroy the key → all encrypted fields become irrecoverable without touching rows |
| Non-production database seeding | Static masking | Dev/staging never sees real data — masked copy of production |
| Regulatory audit: "prove you can't read user SSNs" | Tokenization or FLE with HSM | Demonstrate key access controls, not just absence of plaintext |
| Column-level access control (analysts see email, not SSN) | Dynamic masking | Real-time masking based on database role — SSN visible to app, masked for analysts |

**Q2. What are the threat models that field-level encryption defends against, and what does it not protect?**
A: FLE is designed for a specific threat: an attacker who has read access to the database but not to the application layer or key management system. Understanding this boundary prevents both over-reliance and under-use.

**Threats FLE defends against:**

```
1. Database breach (SQL injection, direct DB access, cloud misconfiguration)
   Without FLE:  SELECT ssn FROM users → attacker reads all SSNs
   With FLE:     SELECT ssn FROM users → attacker reads ENC:v1:3f8a... (useless ciphertext)

2. Database backup exposure (backup files on S3, stolen tapes, misconfigured backup bucket)
   Without FLE:  Backup contains all SSNs in plaintext
   With FLE:     Backup contains only ciphertext — useless without the key

3. Nosy DBA or insider threat at the database layer
   A DBA with SELECT privilege on all tables cannot read encrypted fields
   The DBA would also need KMS access (controlled separately with stricter IAM)

4. Third-party analytics tools with direct DB connections
   Metabase, Tableau, Redshift connected to the DB see only ciphertext
   Encrypted fields are excluded from analytics without application-layer decryption

5. Database vendor access (cloud provider support accessing your RDS instance)
   AWS RDS support staff accessing your database see only ciphertext
   Encryption happens before data enters the DB engine — AWS never sees plaintext
```

**Threats FLE does NOT defend against:**

```
1. Application layer breach
   If the application server is compromised, the attacker sees:
   - Plaintext in memory (just decrypted for a response)
   - The DEK in memory (used to decrypt)
   - Potentially the CMK reference (can fetch new DEKs)
   FLE does not protect against owning the application process.

2. Key management system breach
   If KMS is compromised (attacker gets IAM keys for KMS:Decrypt), all FLE is broken.
   The application must have KMS access to function — this is unavoidable.
   Defense: strict IAM, KMS key policies, CloudTrail audit, multi-party approval for CMK.

3. Side-channel attacks on the application
   Memory dumps, process inspection, debugging — all expose plaintext.

4. Legitimate application queries returning decrypted data
   An attacker who can make API calls as an admin user gets decrypted PII
   via the application's own endpoints — FLE is irrelevant at that point.
   FLE is not a substitute for application-layer authorization.

5. Encrypted field search / analytics
   Encrypted fields cannot be queried with SQL predicates, sorted, or aggregated.
   You cannot: WHERE ssn = '123-45-6789' on an FLE column.
   Solutions (blind indexes, deterministic encryption) each have their own limitations.
```

The mental model: FLE moves the trust boundary from "the database" to "the key management system." The attacker must compromise both the database AND the KMS to recover plaintext. This is defense-in-depth — not an impenetrable barrier, but a meaningful additional layer.

## Section 2: Data Masking Patterns

**Q3. What are static vs dynamic masking, and how do you implement each in a fintech context?**
A: Static and dynamic masking differ in when masking is applied and whether the original data is preserved.

**Static masking** is applied once, irreversibly, to create a sanitized copy of a dataset. The original is not stored in the masked dataset. Used for test data seeding — production data is copied to a staging or development database, with sensitive fields replaced before the copy is available to engineers.

```python
# Static masking pipeline — run once to produce dev/staging database

import hashlib, random, re
from faker import Faker
from decimal import Decimal

fake = Faker("en_IN")   # Indian locale for fintech context

class StaticMasker:

    def mask_pan(self, real_pan: str) -> str:
        """Preserve BIN (first 6) and last 4; randomize middle."""
        if not real_pan or len(real_pan) < 13:
            return real_pan
        bin_prefix = real_pan[:6]
        last_four  = real_pan[-4:]
        middle_len = len(real_pan) - 10
        middle     = "".join([str(random.randint(0, 9)) for _ in range(middle_len)])
        return f"{bin_prefix}{middle}{last_four}"

    def mask_aadhaar(self, real_aadhaar: str) -> str:
        """Show only last 4 digits per UIDAI guidelines."""
        digits = re.sub(r'\D', '', real_aadhaar)
        if len(digits) != 12:
            return "XXXX-XXXX-" + digits[-4:] if len(digits) >= 4 else "XXXX-XXXX-XXXX"
        return f"XXXX-XXXX-{digits[-4:]}"

    def mask_email(self, real_email: str) -> str:
        """Replace local part with deterministic fake — same real email → same masked email.
        Determinism allows referential integrity across tables (FK constraints still work)."""
        local, _, domain = real_email.partition("@")
        # Hash-based determinism: same real email always → same fake local part
        seed   = int(hashlib.md5(real_email.encode()).hexdigest(), 16) % (2**32)
        random.seed(seed)
        fake_local = f"user{random.randint(10000, 99999)}"
        return f"{fake_local}@{domain}"

    def mask_phone(self, real_phone: str) -> str:
        """Generate a valid-format but fake Indian mobile number."""
        digits = re.sub(r'\D', '', real_phone)
        prefix = digits[:2] if digits else "98"
        # Valid Indian mobile: starts with 6-9
        return f"+91{random.choice([6,7,8,9])}{random.randint(100000000, 999999999)}"

    def mask_name(self, real_name: str, seed_value: str = None) -> str:
        """Generate a random name; deterministic if seed_value provided."""
        if seed_value:
            Faker.seed(int(hashlib.md5(seed_value.encode()).hexdigest(), 16) % (2**32))
        return fake.name()

    def mask_account_number(self, real_account: str) -> str:
        """Preserve length and format; fully randomize digits."""
        return re.sub(r'\d', lambda m: str(random.randint(0, 9)), real_account)

    def mask_amount(self, real_amount: Decimal, preserve_range: bool = True) -> Decimal:
        """Optionally preserve the order-of-magnitude for realistic test data."""
        if not preserve_range:
            return Decimal(str(round(random.uniform(100, 100000), 2)))
        # Preserve magnitude: ₹12,345 → random value in ₹10,000–₹19,999
        magnitude = 10 ** (len(str(int(real_amount))) - 1)
        return Decimal(str(round(random.uniform(
            float(magnitude),
            float(magnitude * 10 - 1)
        ), 2)))

# Usage: production-to-staging pipeline
def mask_users_table(prod_conn, staging_conn):
    masker  = StaticMasker()
    cursor  = prod_conn.cursor()
    cursor.execute("SELECT id, name, email, phone, pan, aadhaar, created_at FROM users")

    staging_cursor = staging_conn.cursor()
    for row in cursor:
        user_id, name, email, phone, pan, aadhaar, created_at = row
        staging_cursor.execute(
            """INSERT INTO users (id, name, email, phone, pan, aadhaar, created_at)
               VALUES (%s, %s, %s, %s, %s, %s, %s)""",
            (
                user_id,                                  # preserve — needed for FK integrity
                masker.mask_name(name, seed_value=email), # deterministic by original email
                masker.mask_email(email),                 # deterministic
                masker.mask_phone(phone),
                masker.mask_pan(pan) if pan else None,
                masker.mask_aadhaar(aadhaar) if aadhaar else None,
                created_at,                               # preserve — needed for time-based tests
            )
        )
    staging_conn.commit()
```

**Dynamic masking** applies masking at query time based on the requesting user's role, without altering the stored data. The database stores the real value; the masking layer intercepts query results and redacts based on policy.

```sql
-- PostgreSQL: role-based dynamic masking using views and row security

-- Create a masking view that returns masked data for non-privileged roles
CREATE VIEW users_masked AS
SELECT
    id,
    name,
    -- Mask email: show domain only for non-privileged users
    CASE
        WHEN current_user IN ('app_service', 'admin_role') THEN email
        ELSE REGEXP_REPLACE(email, '^[^@]+', 'XXXXX')
    END AS email,
    -- Mask phone: show last 4 digits only
    CASE
        WHEN current_user IN ('app_service', 'admin_role') THEN phone
        ELSE 'XXXXXX' || RIGHT(phone, 4)
    END AS phone,
    -- Mask PAN completely for analysts
    CASE
        WHEN current_user = 'app_service' THEN pan
        ELSE 'XXXX-XXXX-XXXX-' || RIGHT(REGEXP_REPLACE(pan, '[^0-9]', '', 'g'), 4)
    END AS pan,
    account_type,
    created_at
FROM users;

-- Grant analysts access to the view only, not the base table
GRANT SELECT ON users_masked TO analyst_role;
REVOKE SELECT ON users FROM analyst_role;

-- Analysts see: XXXXX@gmail.com, XXXXXX1234, XXXX-XXXX-XXXX-9012
-- App service sees: full values
```

```python
# Application-layer dynamic masking — for API responses
# Mask based on the requesting user's role and the data's sensitivity

from enum import Enum
from dataclasses import dataclass

class MaskingLevel(Enum):
    NONE    = 0   # full value — app service, owner
    PARTIAL = 1   # last 4 digits — customer support
    FULL    = 2   # fully masked — analysts, third parties

def get_masking_level(requester_role: str, data_owner_id: str, requester_id: str) -> MaskingLevel:
    if requester_id == data_owner_id:
        return MaskingLevel.NONE       # users see their own full data
    if requester_role == "support":
        return MaskingLevel.PARTIAL    # support sees partial
    if requester_role == "admin":
        return MaskingLevel.PARTIAL    # admins see partial (principle of least privilege)
    return MaskingLevel.FULL           # everyone else sees nothing

def apply_masking(user_record: dict, level: MaskingLevel) -> dict:
    result = user_record.copy()

    if level == MaskingLevel.NONE:
        return result

    if level == MaskingLevel.PARTIAL:
        result["pan"]     = mask_partial(user_record.get("pan", ""), keep_last=4)
        result["phone"]   = mask_partial(user_record.get("phone", ""), keep_last=4)
        result["aadhaar"] = mask_partial(user_record.get("aadhaar", ""), keep_last=4)
        result["email"]   = mask_email_partial(user_record.get("email", ""))
        return result

    # FULL masking
    result["pan"]     = "XXXX-XXXX-XXXX-XXXX"
    result["phone"]   = "XXXXXXXXXX"
    result["aadhaar"] = "XXXX-XXXX-XXXX"
    result["email"]   = "XXXXX@XXXXX.XXX"
    return result

def mask_partial(value: str, keep_last: int = 4) -> str:
    if not value or len(value) <= keep_last:
        return "X" * len(value) if value else ""
    visible = value[-keep_last:]
    hidden  = "X" * (len(value) - keep_last)
    return f"{hidden}{visible}"

def mask_email_partial(email: str) -> str:
    if "@" not in email:
        return "XXXXX"
    local, domain = email.split("@", 1)
    masked_local  = local[0] + "X" * (len(local) - 1) if local else "X"
    return f"{masked_local}@{domain}"
```

**Q4. What is format-preserving masking, and when is it necessary?**
A: Format-preserving masking produces a masked value that is structurally identical to the original — same length, same character classes, same check-digit validity. It is necessary when downstream systems validate the format of the masked field (a payment processor that validates Luhn check digits, a UI that enforces a 12-digit Aadhaar format, a legacy system with a NOT NULL CHECK constraint on the field).

```python
# Format-Preserving Masking examples

def luhn_checksum(digits: str) -> int:
    """Compute Luhn check digit for a card number."""
    total = 0
    for i, digit in enumerate(reversed(digits)):
        n = int(digit)
        if i % 2 == 1:
            n *= 2
            if n > 9:
                n -= 9
        total += n
    return (10 - (total % 10)) % 10

def mask_pan_luhn_valid(real_pan: str) -> str:
    """
    Produce a fake PAN that:
    - Passes Luhn check (valid card format)
    - Has the same BIN (first 6 digits) — preserves bank identification
    - Has a randomized middle
    - Is different from the original (cannot be reverse-engineered)
    """
    pan_digits = re.sub(r'\D', '', real_pan)
    if len(pan_digits) < 13:
        raise ValueError("Invalid PAN length")

    bin_prefix = pan_digits[:6]
    # Generate random middle digits (all but the last check digit)
    middle_len  = len(pan_digits) - 7   # 6 BIN + middle + 1 check digit
    middle      = "".join([str(random.randint(0, 9)) for _ in range(middle_len)])
    partial     = bin_prefix + middle
    check_digit = luhn_checksum(partial)
    masked_pan  = partial + str(check_digit)

    # Verify the result is not accidentally the same as the original
    if masked_pan == pan_digits:
        return mask_pan_luhn_valid(real_pan)   # retry (astronomically rare)

    # Restore original formatting (spaces, dashes)
    if " " in real_pan:
        return " ".join([masked_pan[i:i+4] for i in range(0, len(masked_pan), 4)])
    return masked_pan

def mask_aadhaar_format_preserving(real_aadhaar: str) -> str:
    """
    12-digit Aadhaar: first digit cannot be 0 or 1 (UIDAI spec).
    Produce a structurally valid fake Aadhaar.
    """
    digits = re.sub(r'\D', '', real_aadhaar)
    # Generate valid fake: first digit 2-9, rest random
    fake_first = str(random.randint(2, 9))
    fake_rest  = "".join([str(random.randint(0, 9)) for _ in range(11)])
    fake       = fake_first + fake_rest
    # Restore spacing if original had it
    if len(real_aadhaar) == 14:   # "XXXX XXXX XXXX" format
        return f"{fake[:4]} {fake[4:8]} {fake[8:]}"
    return fake

def mask_ifsc_format_preserving(real_ifsc: str) -> str:
    """
    IFSC format: 4 alpha (bank code) + 0 + 6 alphanumeric (branch code)
    Preserve the bank code (first 4 chars) — needed for bank identification.
    """
    if len(real_ifsc) != 11:
        raise ValueError("IFSC must be 11 characters")
    bank_code  = real_ifsc[:4].upper()   # preserve — identifies the bank
    fifth_char = "0"                      # always 0 per RBI spec
    branch     = "".join([
        random.choice("ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789")
        for _ in range(6)
    ])
    return f"{bank_code}{fifth_char}{branch}"
```

## Section 3: Field-Level Encryption Implementation

**Q5. What is envelope encryption, and why is it the standard pattern for field-level encryption?**
A: Envelope encryption is a key hierarchy where data is encrypted with a Data Encryption Key (DEK), and the DEK itself is encrypted with a Key Encryption Key (KEK) stored in a key management system. The encrypted DEK is stored alongside the ciphertext. To decrypt, the application first decrypts the DEK (using the KMS), then uses the DEK to decrypt the data.

```
Without envelope encryption (naive approach):
  Application holds AES key K.
  K is in an environment variable or secrets manager.
  All records encrypted with K.

  Problem 1: Rotating K requires re-encrypting ALL records simultaneously — downtime.
  Problem 2: K is a single point of failure — one leak exposes all data.
  Problem 3: No per-record or per-field access differentiation possible.
  Problem 4: Revoking access for one service requires rotating K for all services.

With envelope encryption:
  KMS holds CMK (Customer Master Key) — never exportable, operations inside KMS.
  Per-record: application asks KMS to generate a DEK.
  KMS returns: DEK_plaintext (32 bytes) + DEK_encrypted (by CMK, ~300 bytes).
  Application encrypts record with DEK_plaintext, stores DEK_encrypted alongside.
  DEK_plaintext is discarded after use.

  Rotation: rotate the CMK → re-encrypt only the DEK_encrypted values (fast).
  The actual record ciphertext does not need to change.
  Granularity: different records/fields can use different CMKs (per-service isolation).
  Revocation: remove IAM permission for a service's role → that service can no longer
  decrypt DEKs → cannot access data, without changing any stored values.
```

```
Storage layout (per encrypted field):

  Column: ssn_encrypted (TEXT)
  Value:  "ENC:v1:{json_blob}"

  json_blob:
  {
    "alg":  "AES-256-GCM",
    "cmk":  "arn:aws:kms:ap-south-1:123:key/mrk-abc",   ← which CMK encrypted the DEK
    "dek":  "AQIDAHi...base64...",                        ← DEK encrypted by CMK (~300 bytes)
    "nonce": "3f8a1c2d4e5b",                              ← AES-GCM nonce (hex, 12 bytes)
    "ct":   "a1b2c3...",                                  ← AES-GCM ciphertext + 16-byte tag
    "ctx":  {"table":"users","field":"ssn","uid":"u123"}  ← KMS EncryptionContext
  }

  The blob is self-describing: it carries everything needed for decryption
  (which CMK, which DEK, which nonce, which context). No external lookup needed.
  Key rotation: update "dek" field only — "ct" stays the same.
```

**Q6. Implement a complete field-level encryption layer for a Python/PostgreSQL application using AWS KMS.**
A:

```python
# fle/encryptor.py — production field-level encryption

import boto3
import json
import os
import logging
import time
from base64  import b64encode, b64decode
from typing  import Optional, Any
from threading import Lock
from dataclasses import dataclass, field

from cryptography.hazmat.primitives.ciphers.aead import AESGCM

logger = logging.getLogger(__name__)

FLE_VERSION  = "v1"
FLE_PREFIX   = f"ENC:{FLE_VERSION}:"

@dataclass
class EncryptionContext:
    """KMS EncryptionContext — binds a ciphertext to its intended use.
    A DEK encrypted for table=users,field=ssn cannot decrypt table=users,field=pan."""
    table:  str
    field:  str
    tenant: str = "default"

    def to_dict(self) -> dict[str, str]:
        return {"table": self.table, "field": self.field, "tenant": self.tenant}


class DEKCache:
    """
    Thread-safe, TTL-based cache for decrypted DEKs.
    Avoids a KMS API call on every field decryption.
    Cache TTL must be short: a leaked DEK is valid until cache expires.
    Never cache plaintext DEKs to disk — memory only.
    """
    def __init__(self, ttl_seconds: int = 300):
        self._cache:    dict[str, tuple[bytes, float]] = {}
        self._lock:     Lock = Lock()
        self._ttl:      int  = ttl_seconds

    def get(self, encrypted_dek_b64: str) -> Optional[bytes]:
        with self._lock:
            entry = self._cache.get(encrypted_dek_b64)
            if entry is None:
                return None
            dek_plaintext, expires_at = entry
            if time.monotonic() > expires_at:
                del self._cache[encrypted_dek_b64]
                return None
            return dek_plaintext

    def put(self, encrypted_dek_b64: str, dek_plaintext: bytes) -> None:
        with self._lock:
            self._cache[encrypted_dek_b64] = (
                dek_plaintext,
                time.monotonic() + self._ttl
            )

    def invalidate(self, encrypted_dek_b64: str) -> None:
        with self._lock:
            self._cache.pop(encrypted_dek_b64, None)

    def clear(self) -> None:
        """Call on key rotation to force fresh DEK fetches."""
        with self._lock:
            self._cache.clear()


class FieldEncryptor:
    """
    Production-grade field-level encryption using AWS KMS envelope encryption.

    One instance per CMK — create separate instances for different sensitivity tiers
    (e.g., PII fields use cmk-pii, financial fields use cmk-financial).
    """

    def __init__(
        self,
        cmk_arn:       str,
        region:        str = "ap-south-1",
        dek_cache_ttl: int = 300,
    ):
        self._cmk_arn  = cmk_arn
        self._kms      = boto3.client("kms", region_name=region)
        self._dek_cache = DEKCache(ttl_seconds=dek_cache_ttl)

    # ── Encryption ─────────────────────────────────────────────────────────────

    def encrypt(self, plaintext: str, context: EncryptionContext) -> str:
        """
        Encrypt a single field value.
        Returns a self-describing encrypted blob string.
        Each call generates a fresh DEK — one DEK per field per record.
        """
        if plaintext is None:
            return None

        # 1. Generate a fresh DEK from KMS
        try:
            response = self._kms.generate_data_key(
                KeyId=self._cmk_arn,
                KeySpec="AES_256",
                EncryptionContext=context.to_dict(),
            )
        except Exception as e:
            logger.error("KMS generate_data_key failed", exc_info=True)
            raise EncryptionError("Failed to generate encryption key") from e

        dek_plaintext  = response["Plaintext"]     # 32 bytes — use immediately
        dek_encrypted  = response["CiphertextBlob"]  # ~300 bytes — store

        try:
            # 2. Encrypt field value with the DEK
            nonce      = os.urandom(12)   # 96-bit nonce — fresh per encryption
            aesgcm     = AESGCM(dek_plaintext)
            ciphertext = aesgcm.encrypt(nonce, plaintext.encode("utf-8"), None)
        finally:
            # 3. Zero the DEK from local memory as soon as possible
            # Python doesn't guarantee memory zeroing, but this is best-effort
            dek_plaintext = b"\x00" * 32

        # 4. Pack into a self-describing blob
        blob = {
            "alg":   "AES-256-GCM",
            "cmk":   self._cmk_arn,
            "dek":   b64encode(dek_encrypted).decode(),
            "nonce": b64encode(nonce).decode(),
            "ct":    b64encode(ciphertext).decode(),
            "ctx":   context.to_dict(),
        }
        return FLE_PREFIX + json.dumps(blob, separators=(",", ":"))

    # ── Decryption ─────────────────────────────────────────────────────────────

    def decrypt(self, encrypted_blob: str, context: EncryptionContext) -> Optional[str]:
        """
        Decrypt a single field value.
        Returns None if the input is None or unencrypted (migration period).
        Raises DecryptionError on tampered or invalid ciphertext.
        """
        if encrypted_blob is None:
            return None
        if not encrypted_blob.startswith(FLE_PREFIX):
            # Not encrypted — return as-is during migration period when some
            # rows may have plaintext and others may have ciphertext
            logger.warning(
                "fle_plaintext_field_read",
                extra={"context": context.to_dict()}
            )
            return encrypted_blob

        try:
            blob = json.loads(encrypted_blob[len(FLE_PREFIX):])
        except json.JSONDecodeError:
            raise DecryptionError("Malformed encrypted blob")

        dek_encrypted_b64 = blob["dek"]
        nonce      = b64decode(blob["nonce"])
        ciphertext = b64decode(blob["ct"])
        stored_ctx = blob.get("ctx", {})

        # 1. Verify context matches — prevents cross-field decryption
        if stored_ctx != context.to_dict():
            logger.error(
                "fle_context_mismatch",
                extra={"stored": stored_ctx, "requested": context.to_dict()}
            )
            raise DecryptionError("Encryption context mismatch")

        # 2. Fetch DEK — from cache if available, else from KMS
        dek_plaintext = self._dek_cache.get(dek_encrypted_b64)
        if dek_plaintext is None:
            dek_plaintext = self._decrypt_dek(
                b64decode(dek_encrypted_b64),
                context
            )
            self._dek_cache.put(dek_encrypted_b64, dek_plaintext)

        # 3. Decrypt field value
        try:
            aesgcm    = AESGCM(dek_plaintext)
            plaintext = aesgcm.decrypt(nonce, ciphertext, None)
            return plaintext.decode("utf-8")
        except Exception:
            raise DecryptionError("Ciphertext is invalid or has been tampered with")

    def _decrypt_dek(self, dek_encrypted: bytes, context: EncryptionContext) -> bytes:
        try:
            response = self._kms.decrypt(
                CiphertextBlob=dek_encrypted,
                EncryptionContext=context.to_dict(),
            )
            return response["Plaintext"]
        except self._kms.exceptions.InvalidCiphertextException:
            raise DecryptionError("DEK decryption failed — possible context mismatch or corruption")
        except Exception as e:
            logger.error("KMS decrypt failed", exc_info=True)
            raise DecryptionError("Failed to decrypt encryption key") from e

    # ── Key Rotation ───────────────────────────────────────────────────────────

    def rewrap_dek(self, encrypted_blob: str, context: EncryptionContext) -> str:
        """
        Re-encrypt the DEK using the current CMK key version (after rotation).
        The actual ciphertext (field value) does not change — only the DEK is rewrapped.
        This is dramatically faster than re-encrypting all field values.
        """
        if not encrypted_blob.startswith(FLE_PREFIX):
            return encrypted_blob

        blob          = json.loads(encrypted_blob[len(FLE_PREFIX):])
        dek_encrypted = b64decode(blob["dek"])

        # Ask KMS to re-encrypt the DEK with the latest CMK version
        response = self._kms.re_encrypt(
            CiphertextBlob=dek_encrypted,
            DestinationKeyId=self._cmk_arn,
            SourceEncryptionContext=context.to_dict(),
            DestinationEncryptionContext=context.to_dict(),
        )
        blob["dek"] = b64encode(response["CiphertextBlob"]).decode()
        self._dek_cache.invalidate(b64encode(dek_encrypted).decode())

        return FLE_PREFIX + json.dumps(blob, separators=(",", ":"))


class EncryptionError(Exception): pass
class DecryptionError(Exception): pass
```

## Section 4: Searchability and Blind Indexes

**Q8. How do you make encrypted fields searchable without decrypting them, and what are the trade-offs of each approach?**
A: Encrypted fields cannot be queried with SQL predicates — `WHERE pan = 'ABCD1234E'` on a ciphertext column always returns zero rows. Four approaches exist, each trading different security properties for searchability.

**Approach 1 — Blind Index (HMAC-based equality search):**
Store an HMAC of the plaintext alongside the ciphertext. Queries are against the HMAC. Supports equality search only — no range queries, no LIKE, no ordering.

```python
import hmac, hashlib, os

# Blind index secret — separate from the encryption key, stored in Vault/SSM
BLIND_INDEX_SECRET = bytes.fromhex(os.environ["BLIND_INDEX_SECRET_HEX"])

def compute_blind_index(plaintext: str, field_name: str) -> str:
    """
    Compute a deterministic HMAC for equality search.
    field_name is included to prevent cross-field index reuse:
    HMAC(secret, "ABCD1234E") for PAN ≠ HMAC(secret, "ABCD1234E") for some other field.
    """
    # Normalize before hashing — ensures consistent lookup
    normalized = plaintext.strip().upper()
    message    = f"{field_name}:{normalized}".encode("utf-8")
    digest     = hmac.new(BLIND_INDEX_SECRET, message, hashlib.sha256).hexdigest()
    return digest

# Database schema with blind index column:
# ALTER TABLE users ADD COLUMN pan_blind_index CHAR(64);
# CREATE INDEX idx_users_pan_blind ON users(pan_blind_index);

# Write path — compute blind index alongside encryption:
def save_user_pan(session, user: User, pan: str) -> None:
    user.pan               = pan                                     # triggers encryption
    user.pan_blind_index   = compute_blind_index(pan, "pan")        # for search
    session.commit()

# Read path — search by blind index:
def find_user_by_pan(session, pan: str) -> User | None:
    blind_index = compute_blind_index(pan, "pan")
    return session.query(User).filter(
        User.pan_blind_index == blind_index
    ).first()
    # Returns the row; the actual PAN is decrypted by the property getter when accessed

# Security properties:
# + An attacker with only the DB sees HMAC values — cannot reverse to PAN
# + Cross-field attacks blocked by field_name prefix
# - Attacker with BLIND_INDEX_SECRET can precompute HMAC(secret, all possible PANs)
#   (PANs have ~10^10 possibilities — precomputation is expensive but not impossible)
# - No range search: cannot find "all PANs starting with ABCD"
# - No LIKE search: cannot find "all users with Gmail email addresses"
```

**Approach 2 — Deterministic Encryption (equality search, weaker security):**
Encrypt the same plaintext with the same key to always produce the same ciphertext. Allows equality search (`WHERE pan_enc = encrypt(search_term)`), but leaks frequency patterns — if two rows have the same PAN, their ciphertexts are identical. An attacker can observe which records share values without decrypting.

```python
# Deterministic encryption — use AES-SIV (Synthetic IV) mode
# SIV: nonce is derived from the plaintext — same plaintext = same ciphertext
# Provides authenticated encryption with determinism

from cryptography.hazmat.primitives.ciphers.aead import AESSIV

DETERMINISTIC_KEY = os.urandom(64)  # SIV requires double-length key: 64 bytes for AES-256-SIV

def deterministic_encrypt(plaintext: str, context: bytes = b"") -> str:
    siv        = AESSIV(DETERMINISTIC_KEY)
    ciphertext = siv.encrypt(plaintext.encode("utf-8"), [context])
    return b64encode(ciphertext).decode()

def deterministic_decrypt(ciphertext_b64: str, context: bytes = b"") -> str:
    siv        = AESSIV(DETERMINISTIC_KEY)
    ciphertext = b64decode(ciphertext_b64)
    return siv.decrypt(ciphertext, [context]).decode("utf-8")

# Usage: low-cardinality fields where frequency leak is acceptable
# Good for: account_status (only ~5 possible values — frequency already visible)
# Bad for:  SSN, PAN, Aadhaar (high uniqueness — frequency reveals nothing, but
#           determinism means the same SSN in two places is immediately linkable)

# Security trade-off table:
# Property           │ Blind Index │ Deterministic Enc │ Probabilistic Enc (AES-GCM)
# ───────────────────┼─────────────┼───────────────────┼───────────────────────────
# Equality search    │ Yes         │ Yes               │ No
# Hides duplicates   │ Yes         │ No                │ Yes
# Forward secrecy    │ Yes         │ No                │ Yes (if key is rotated)
# DB sees ciphertext │ HMAC        │ SIV ciphertext    │ GCM ciphertext (different each time)
# Recommended for    │ PAN, SSN    │ Status codes only │ All sensitive fields
```

**Approach 3 — Application-side search (decrypt and filter in code):**
Load encrypted rows in bulk, decrypt in the application, filter in Python/Go. Only feasible for small datasets or infrequent admin operations.

```python
def find_users_by_email_domain(session, domain: str) -> list[User]:
    """
    Find users whose email ends with @domain.
    Email is encrypted — cannot use SQL LIKE.
    Load all users and filter in Python — only acceptable for admin tools on small datasets.
    """
    # Safety check: refuse to scan more than N rows in application code
    total = session.query(User).count()
    if total > 10_000:
        raise OperationNotSupportedError(
            "Application-side search on >10k rows is not supported. "
            "Use a dedicated search index."
        )

    users = session.query(User).all()
    return [u for u in users if u.email.endswith(f"@{domain}")]
    # u.email triggers decryption via the property getter — O(n) KMS calls
    # Mitigation: batch decrypt using DEK cache to reduce KMS calls
```

**Approach 4 — Dedicated search index (Elasticsearch with encrypted index):**
Maintain a separate search index (Elasticsearch, OpenSearch) where the indexed values are tokenized or partially masked — enough for search, not enough to reconstruct the original. The index is a separate system with separate access controls.

```python
# Search index pattern: index only the information needed for search
# PAN search: index only the blind index value
# Email search: index the domain and first-char prefix only

from elasticsearch import Elasticsearch

es = Elasticsearch([os.environ["ELASTICSEARCH_URL"]])

    es.index(
        index="users_search",
        id=user.id,
        body={
            "user_id":         user.id,
            # Searchable: blind index — no PAN is stored in the search index
            "pan_blind":       compute_blind_index(user.pan, "pan") if user.pan else None,
            # Partial email for domain/prefix search
            "email_domain":    user.email.split("@")[1] if "@" in user.email else None,
            "email_prefix":    user.email[:3].lower() if user.email else None,
            # Fully masked — used only for display in search results
            "pan_masked":      f"****{user.pan[-4:]}" if user.pan else None,
            "created_at":      user.created_at.isoformat(),
        }
    )

def search_users_by_pan(pan: str, page: int = 1, size: int = 20) -> list[str]:
    blind_index = compute_blind_index(pan, "pan")
    result = es.search(
        index="users_search",
        body={
            "query": {"term": {"pan_blind": blind_index}},
            "from": (page - 1) * size,
            "size": size,
            "_source": ["user_id", "pan_masked"],
        }
    )
    return [hit["_source"]["user_id"] for hit in result["hits"]["hits"]]
```

## Section 5: Key Rotation and Lifecycle Management

**Q9. How do you rotate encryption keys for field-level encrypted data without downtime?**
A: Key rotation has two components: rotating the CMK in KMS (simple — KMS handles this) and re-wrapping the DEKs stored in the database (the operational challenge). The key insight is that envelope encryption makes CMK rotation nearly free — only the DEK ciphertext changes, not the actual data ciphertext.

```python
# key_rotation/rotate.py — zero-downtime CMK rotation

import logging
from sqlalchemy import text
from fle.encryptor import FieldEncryptor, EncryptionContext

logger = logging.getLogger(__name__)

def rotate_pii_keys(
    session,
    encryptor:       FieldEncryptor,
    table:           str,
    encrypted_fields: list[str],
    batch_size:      int = 100,
) -> dict:
    """
    Re-wrap all DEKs in the encrypted_fields columns of table.
    The actual ciphertext (field data) is unchanged — only the DEK ciphertext is rotated.
    Zero-downtime: old and new DEKs coexist; old ciphertext still decrypts while re-wrapping.

    Precondition: the CMK has been rotated in KMS (via AWS console or API).
    KMS automatically enables both old and new CMK versions during the rotation window.

    Postcondition: all DEKs are wrapped with the new CMK version.
    """
    stats = {"processed": 0, "rotated": 0, "skipped": 0, "errors": 0}

    # Fetch rows in batches — avoid loading entire table into memory
    offset = 0
    while True:
        rows = session.execute(
            text(f"SELECT id, {', '.join(encrypted_fields)} FROM {table} LIMIT :limit OFFSET :offset"),
            {"limit": batch_size, "offset": offset}
        ).fetchall()

        if not rows:
            break

        for row in rows:
            row_id = row[0]
            try:
                updates = {}
                for i, field_name in enumerate(encrypted_fields):
                    encrypted_blob = row[i + 1]
                    if not encrypted_blob or not encrypted_blob.startswith("ENC:"):
                        stats["skipped"] += 1
                        continue

                    context     = EncryptionContext(table=table, field=field_name)
                    new_blob    = encryptor.rewrap_dek(encrypted_blob, context)
                    updates[field_name] = new_blob
                    stats["rotated"] += 1

                if updates:
                    set_clause = ", ".join([f"{k} = :{k}" for k in updates])
                    updates["row_id"] = row_id
                    session.execute(
                        text(f"UPDATE {table} SET {set_clause} WHERE id = :row_id"),
                        updates
                    )
                stats["processed"] += 1

            except Exception as e:
                logger.error(
                    "key_rotation_row_failed",
                    extra={"table": table, "row_id": row_id, "error": str(e)}
                )
                stats["errors"] += 1
                continue   # do not abort — continue rotating other rows

        session.commit()   # commit each batch
        offset += batch_size
        logger.info(f"Key rotation progress: {stats}")

    # Clear DEK cache — all cached plaintext DEKs are now associated with old CMK version
    encryptor._dek_cache.clear()
    logger.info(f"Key rotation complete: {stats}")
    return stats


# Rotation schedule — automate via a cron job or AWS EventBridge
# Step 1 (automated by KMS): rotate CMK — new CMK version active for new DEK generation
# Step 2 (this script):       re-wrap all existing DEKs with new CMK version
# Step 3 (KMS): disable old CMK version — old DEKs are now the only ones using old version
# Step 4 (after all DEKs re-wrapped): delete old CMK version

# Rotation triggering events (beyond scheduled rotation):
#   - Any KMS IAM role compromise
#   - Departure of an engineer with KMS access
#   - Regulatory requirement (annual or on-demand)
#   - Suspected unauthorized decryption (CloudTrail anomaly)
```

**Q10. How do you implement the GDPR right to erasure ("right to be forgotten") using field-level encryption?**
A: Cryptographic erasure is the most operationally practical way to implement GDPR right to erasure for data that is present in backups, replicas, audit logs, and analytics systems. Instead of hunting for and deleting every copy of a user's data — which is operationally complex and often incomplete — you destroy the decryption key. All encrypted copies of the data become permanently unreadable, achieving the erasure effect without modifying storage.

```python
# gdpr/erasure.py — cryptographic erasure via key destruction

class CryptographicErasureService:
    """
    Implements GDPR Art. 17 Right to Erasure via key destruction.
    When the user-specific CMK alias or key material is destroyed,
    all data encrypted under it becomes permanently irrecoverable.
    """

    def __init__(self, kms_client, audit_db):
        self._kms   = kms_client
        self._audit = audit_db

    def erase_user_data(self, user_id: str, reason: str) -> dict:
        """
        Cryptographically erase all PII for a user.
        Returns a verifiable erasure certificate.
        """
        # Step 1: Identify the user's per-user CMK (if using per-user keys)
        # OR: the field-level DEKs for this user's records
        # This design uses per-user KMS key aliases for full cryptographic isolation.

        user_key_alias = f"alias/user-pii/{user_id}"

        # Step 2: Schedule key deletion (KMS enforces minimum 7-day waiting period)
        # During the waiting period: key is disabled but recoverable if needed
        try:
            response = self._kms.schedule_key_deletion(
                KeyId=user_key_alias,
                PendingWindowInDays=7,   # minimum per KMS — gives time to cancel if error
            )
            deletion_date = response["DeletionDate"]
        except self._kms.exceptions.NotFoundException:
            logger.warning(f"No KMS key found for user {user_id} — may already be erased")
            deletion_date = None

        # Step 3: Immediately disable the key (data becomes unreadable now,
        # even before the 7-day deletion window elapses)
        if deletion_date:
            self._kms.disable_key(KeyId=user_key_alias)

        # Step 4: Remove or nullify the user's PII fields in the database
        # The ciphertext is now permanently unreadable, but we clean it up anyway
        # to avoid storing useless ciphertext and to satisfy "delete the data" literally
        self._audit.execute("""
            UPDATE users
            SET pan      = NULL,
                aadhaar  = NULL,
                phone    = NULL,
                name     = '[erased]',
                erased_at = NOW(),
                erasure_reason = %s
            WHERE id = %s
        """, (reason, user_id))

        # Step 5: Issue an erasure certificate — verifiable proof for GDPR compliance
        certificate = {
            "user_id":          user_id,
            "erasure_type":     "cryptographic",
            "kms_key_alias":    user_key_alias,
            "key_disabled_at":  datetime.utcnow().isoformat(),
            "key_deletion_date": deletion_date.isoformat() if deletion_date else "already-deleted",
            "fields_erased":    ["pan", "aadhaar", "phone", "name"],
            "reason":           reason,
            "requested_by":     "user_request",   # or "legal_hold", "account_closure"
            "certificate_id":   str(uuid4()),
        }

        # Store the certificate — needed for audit and regulatory proof
        self._audit.execute("""
            INSERT INTO erasure_certificates (id, user_id, certificate_json, created_at)
            VALUES (%s, %s, %s, NOW())
        """, (certificate["certificate_id"], user_id, json.dumps(certificate)))

        logger.info("gdpr_erasure_complete", extra={"user_id": user_id, "certificate": certificate})
        return certificate

    def verify_erasure(self, user_id: str) -> bool:
        """
        Verify that the user's data is no longer decryptable.
        Attempt to decrypt a stored ciphertext — should fail with KMS exception.
        """
        row = self._audit.fetchone(
            "SELECT pan FROM users WHERE id = %s", (user_id,)
        )
        if row is None or row["pan"] is None:
            return True   # already nullified

        # Attempt to decrypt — should fail because the key is disabled/deleted
        try:
            encryptor.decrypt(row["pan"], EncryptionContext("users", "pan"))
            return False   # ← if this succeeds, erasure failed
        except DecryptionError:
            return True    # ← key is gone — erasure verified
```

**Limitations of cryptographic erasure to understand:**
```
What cryptographic erasure handles:
  - Encrypted fields in the primary database — key gone, data unreadable
  - Encrypted fields in database backups — backups have ciphertext, key is gone
  - Encrypted fields in replicas and read replicas
  - Encrypted fields in S3 data lake exports

What cryptographic erasure does NOT handle automatically:
  - Fields stored in plaintext (e.g., email, name in non-encrypted columns)
    → These must be physically deleted or nullified in every copy
  - Audit log entries that captured the plaintext value (e.g., "user changed PAN to ABCD1234E")
    → Audit logs must themselves be encrypted or the plaintext audit entries found and deleted
  - Application logs that printed the PAN during processing
    → Log management must be designed to avoid logging PII
  - Analytics snapshots taken before encryption was enabled
    → Pre-encryption data must be separately handled

GDPR compliance requires handling all of the above — cryptographic erasure
addresses the encrypted copies but is not a complete erasure solution by itself.
```

## Section 6: Compliance and Regulatory Patterns

**Q11. How do PCI-DSS requirements map to data masking and tokenization for card data?**
A: PCI-DSS (Payment Card Industry Data Security Standard) has specific technical requirements for how cardholder data (CHD) is handled. The standard's primary goal is to reduce the scope of systems that handle raw PANs — and tokenization is the principal mechanism for doing so.

```
PCI-DSS v4.0 relevant requirements:

Requirement 3.3 — Sensitive Authentication Data (SAD) must not be stored after authorization:
  SAD includes: CVV/CVC, full magnetic stripe data, PIN blocks
  Cannot encrypt and store these — must not be stored at all, period.
  Implementation: do not persist CVV in any field; zero it from memory after auth.

Requirement 3.5 — PAN must be secured wherever stored:
  Option A: Do not store PAN → use a payment processor (Stripe, Razorpay) that
            returns a token; your system stores only the token
  Option B: Store PAN with strong cryptography (AES-256, key management per 3.7)
  Option C: Use truncation (store only last 4 or first 6 + last 4)
  Option D: Use tokenization (store surrogate token, PAN in a PCI-compliant vault)

  Masking at display: PAN must be masked when displayed — show only first 6 + last 4:
  "Display: 453212XXXXXX9012" is acceptable
  "Display: 4532123456789012" is a violation when shown to non-authorized personnel

Requirement 3.7 — Cryptographic key management:
  Key custodians: at least two people responsible for key components
  Key rotation: cryptoperiod defined per key type (annual is common for KEKs)
  Key storage: keys not stored in cleartext; separate from the data they protect
  Key destruction: documented procedure for key retirement

Practical PCI-DSS implementation architecture:

  ┌──────────────────────────────────────────────────────────┐
  │  CDE (Cardholder Data Environment) — PCI scope           │
  │                                                          │
  │  ┌────────────────┐     ┌──────────────────────────┐    │
  │  │ Payment Gateway│────▶│ Tokenization Vault (HSM)  │   │
  │  │ (Stripe etc.)  │     │ PAN ↔ Token mapping      │   │
  │  └────────────────┘     └──────────────────────────┘    │
  └──────────────────────────────────────────────────────────┘
              │
              │ Token (not PAN)
              ▼
  ┌──────────────────────────────────────────────────────────┐
  │  Non-CDE systems — outside PCI scope                     │
  │  Order management, CRM, Analytics, Reporting             │
  │  Store: token_9173482100347651 (meaningless surrogate)   │
  │  Cannot access the vault → cannot get the real PAN       │
  │  PCI audit scope is dramatically reduced                 │
  └──────────────────────────────────────────────────────────┘
```

```python
# Payment flow with tokenization — keeping PAN out of application code

class PaymentService:

    def __init__(self, payment_gateway, order_repo):
        self._gateway   = payment_gateway   # Stripe, Razorpay — handles PAN
        self._order_repo = order_repo

    def initiate_payment(self, user_id: str, amount: Decimal, card_details: dict) -> dict:
        """
        card_details = {"number": "4532...", "expiry": "12/26", "cvv": "123"}
        The PAN and CVV touch this function only — they are never logged, never stored.
        """
        # Send PAN directly to payment gateway — never store in our database
        gateway_response = self._gateway.charge(
            amount=int(amount * 100),   # in paise/cents
            currency="INR",
            card={
                "number":    card_details["number"],   # raw PAN — sent to gateway only
                "exp_month": card_details["expiry"].split("/")[0],
                "exp_year":  card_details["expiry"].split("/")[1],
                "cvc":       card_details["cvv"],      # raw CVV — sent to gateway, never stored
            }
        )

        # Gateway returns a token — the PAN is now vaulted by the gateway
        payment_method_token = gateway_response["payment_method_id"]
        last_four            = gateway_response["card"]["last4"]
        card_brand           = gateway_response["card"]["brand"]

        # Store ONLY the token + metadata — no PAN, no CVV
        self._order_repo.create({
            "user_id":              user_id,
            "payment_method_token": payment_method_token,   # e.g., "pm_1OxKJ2..."
            "card_last_four":       last_four,              # for display: "Visa ending in 4242"
            "card_brand":           card_brand,
            "amount":               amount,
            "status":               "completed",
        })

        # Zero the card details from local variables immediately
        card_details.clear()

        return {"status": "success", "last_four": last_four}

    def charge_saved_card(self, user_id: str, payment_method_token: str, amount: Decimal):
        """Re-charge using a stored token — PAN never needed again."""
        # The token is sent to the gateway; the gateway performs the actual charge
        # using the vaulted PAN — our system never sees the PAN
        return self._gateway.charge_token(
            payment_method_id=payment_method_token,
            amount=int(amount * 100),

**Q12. How does RBI's data localization requirement interact with field-level encryption architecture?**
A: The Reserve Bank of India's data localization mandate (2018 circular, reiterated in 2019) requires that payment system data of Indian users be stored only in systems located in India. Field-level encryption must be designed with data residency constraints — the encrypted data and the keys must both reside within Indian data center boundaries.

```
RBI data localization requirements for payment data:

1. All payment system data must be stored only in India.
   "Payment data" includes: the full end-to-end transaction data — customer data,
   payment sensitive data (card number, CVV, PIN), and transaction/usage data.

2. For international transactions: a mirror copy in India is required.
   The primary copy and the key must be in India even if a copy goes abroad.

3. Audit trail: RBI can demand access to data within 6 hours.
   Encryption key access must be possible for regulators under court order.

Architecture implications for FLE:

  ┌───────────────────────────────────────────────────────────────────┐
  │ AWS ap-south-1 (Mumbai) — ALL sensitive data                      │
  │                                                                   │
  │  KMS CMK: ap-south-1 only (key cannot be replicated to other regions) │
  │  RDS PostgreSQL: ap-south-1 (encrypted at rest with KMS)          │
  │  Application servers: ap-south-1 (data never leaves region)       │
  │  CloudTrail: ap-south-1 (audit logs stored locally)               │
  └───────────────────────────────────────────────────────────────────┘

  Cross-region replication of encrypted data is technically permissible
  (ciphertext is not readable without the key) but the KMS key policy
  must ensure decryption is only possible from ap-south-1 endpoints:

  KMS key policy condition:
  {
    "Condition": {
      "StringEquals": {
        "aws:RequestedRegion": "ap-south-1"
      }
    }
  }
  This prevents the key from being used to decrypt if the application
  moves to another region (e.g., if a misconfigured deployment uses us-east-1).
```

        try:
            result = super().encrypt(plaintext, context)

            )
            raise
        finally:

                "fle.encrypt.duration_ms",
                (time.monotonic() - start) * 1000,
                tags=[f"table:{context.table}"]
            )

    def decrypt(self, encrypted_blob: str, context: EncryptionContext) -> str | None:
        start = time.monotonic()
        try:
            result = super().decrypt(encrypted_blob, context)
            datadog.statsd.increment(
                "fle.decrypt.success",
                tags=[f"table:{context.table}", f"field:{context.field}"]

# logging/pii_filter.py — scrub PII before log emission

import re, logging

class PIIRedactionFilter(logging.Filter):
    """
    Logging filter that redacts PII patterns before log records are emitted.
    Applied to ALL log handlers — a defense-in-depth measure alongside FLE.
    """

    PATTERNS = [
        # Aadhaar: 12 digits (possibly spaced XXXX XXXX XXXX)
        (re.compile(r'\b[2-9]\d{3}[\s\-]?\d{4}[\s\-]?\d{4}\b'), "[AADHAAR-REDACTED]"),
        # PAN: 5 alpha + 4 digits + 1 alpha
        (re.compile(r'\b[A-Z]{5}[0-9]{4}[A-Z]\b'), "[PAN-REDACTED]"),
        # Credit card: 13-16 digits (Luhn-like patterns)
        (re.compile(r'\b(?:\d{4}[\s\-]?){3}\d{4}\b'), "[CARD-REDACTED]"),
        # Indian mobile: +91 or 0 prefix + 10 digits
        (re.compile(r'(?:\+91|0)[6-9]\d{9}\b'), "[PHONE-REDACTED]"),
        # Email addresses
        (re.compile(r'\b[A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Za-z]{2,}\b'), "[EMAIL-REDACTED]"),
    ]

    def filter(self, record: logging.LogRecord) -> bool:
        # Redact from the message
        message = str(record.getMessage())
        for pattern, replacement in self.PATTERNS:
            message = pattern.sub(replacement, message)
        record.msg  = message
        record.args = ()

        # Redact from extra fields
        for attr in vars(record):
            value = getattr(record, attr, None)
            if isinstance(value, str):
                for pattern, replacement in self.PATTERNS:
                    value = pattern.sub(replacement, value)
                setattr(record, attr, value)

        return True   # always emit — just redacted

# Apply to root logger:
root_logger = logging.getLogger()
root_logger.addFilter(PIIRedactionFilter())

# Apply to Elasticsearch handler specifically:
es_handler = ElasticsearchHandler(...)
es_handler.addFilter(PIIRedactionFilter())
```

## Quick Reference: Masking and FLE Decision Matrix

```
CHOOSE DATA MASKING WHEN:
[ ] Non-production environments need realistic but non-sensitive data
[ ] User-facing display requires showing partial data ("Card ending in 9012")
[ ] Analysts need aggregate insights without raw PII access
[ ] The original value is not needed for any operational purpose
[ ] Static masking: one-time production → staging/dev copy
[ ] Dynamic masking: same DB, different views per role

CHOOSE TOKENIZATION WHEN:
[ ] PCI-DSS scope reduction is the goal (PAN out of application systems)
[ ] Format-preservation is required (token looks like a card number)
[ ] The original must be recoverable by an authorized system (payment processor)
[ ] Third-party systems store the reference but must not access the original
[ ] Vault-based revocation of access is required (delete mapping = access revoked)

CHOOSE FIELD-LEVEL ENCRYPTION WHEN:
[ ] PII/sensitive data must be stored and recovered by the application
[ ] The threat model includes database-level breach (SQL injection, insider threat)
[ ] GDPR cryptographic erasure is required (destroy key = all copies unreadable)
[ ] Regulatory compliance requires encryption at rest for specific fields
[ ] Per-field access control is needed (different services can decrypt different fields)
[ ] Data residency enforcement is required (KMS key policy restricts region)

FLE IMPLEMENTATION CHECKLIST
[ ] Envelope encryption: per-record DEK, KMS-protected CMK
[ ] KMS EncryptionContext bound to table + field + tenant
[ ] Self-describing blob: version + CMK ARN + encrypted DEK + nonce + ciphertext
[ ] AES-256-GCM (AEAD) — never AES-CBC for FLE
[ ] Fresh nonce per encryption (os.urandom(12))
[ ] DEK zeroed from memory immediately after use
[ ] DEK cache: memory-only, TTL ≤ 5 minutes
[ ] Transparent property getters/setters in ORM model
[ ] Blind index for searchable encrypted fields (HMAC with separate secret)
[ ] Key rotation: KMS re_encrypt for DEK rewrapping (data ciphertext unchanged)
[ ] Cryptographic erasure procedure documented and tested
[ ] CloudTrail alert on unauthorized KMS Decrypt
[ ] Alert on fle.decrypt.tampered > 0
[ ] PII redaction filter on all log handlers
[ ] Audit log of every field decryption (who, what, when)
[ ] RBI/GDPR compliance: key in correct region, retention policy set
```

(Q8 — blind index with HMAC, its limitations, vs. deterministic encryption).
