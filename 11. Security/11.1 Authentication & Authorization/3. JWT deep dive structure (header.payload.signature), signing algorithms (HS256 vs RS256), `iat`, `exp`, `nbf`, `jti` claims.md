# Security: JWT Deep Dive — Interview Q&A (5 YOE Level)

---

## Section 1: Structure and Encoding

**Q1. What is a JWT, and what is its wire format?**
A: A JSON Web Token (JWT) is a compact, URL-safe token format defined by RFC 7519 for representing claims between two parties. The wire format is three Base64URL-encoded strings joined by dots:

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJzdWIiOiJ1c2VyXzEyMyIsImlhdCI6MTcwMDAwMDAwMCwiZXhwIjoxNzAwMDAzNjAwfQ
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

The three parts are: **header**, **payload**, **signature**. The dots are literal — not part of the encoding. Any JWT that doesn't have exactly two dots is malformed. The Base64URL encoding is standard Base64 with `+` replaced by `-`, `/` replaced by `_`, and padding (`=`) stripped. This makes JWTs safe to embed in URLs and HTTP headers without further encoding.

**Q2. What is in the header, and what fields matter?**
A: The header is a JSON object describing the token's cryptographic properties. Decoded:

```json
{
  "alg": "RS256",
  "typ": "JWT"
}
```

- **`alg`** — the signing algorithm. This is the most security-critical field in the header. The server must validate and allowlist this value; it must never accept whatever algorithm the client claims. Common values: `HS256`, `RS256`, `ES256`, `none` (never accept `none` in production).
- **`typ`** — the token type. Almost always `"JWT"`. Some implementations use `"at+JWT"` (RFC 9068) for access tokens to distinguish them from ID tokens in an OAuth2 context.
- **`kid`** — optional Key ID. When a server rotates signing keys, `kid` lets the verifier look up the correct key from a JWKS (JSON Web Key Set) without trying all keys. This is essential for production RS256/ES256 setups where key rotation happens without downtime.

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "2024-q4-primary"
}
```

**Q3. What is in the payload, and what are registered, public, and private claims?**
A: The payload is a JSON object containing claims — assertions about an entity (usually the user) and metadata about the token itself. RFC 7519 defines three categories:

**Registered claims** — standardized names with defined semantics (covered in detail in Sections 2 and 3):
```json
{
  "iss": "https://auth.myorg.com",
  "sub": "user_123",
  "aud": "https://api.myorg.com",
  "exp": 1700003600,
  "iat": 1700000000,
  "nbf": 1700000000,
  "jti": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

**Public claims** — custom claims registered in the IANA JWT Claims Registry to avoid collisions. Examples: `email`, `name`, `roles`. If you define custom claims in a multi-party system, register them or namespace them.

**Private claims** — application-specific claims agreed upon between producer and consumer. Convention is to namespace them to avoid collision with registered or future public claims:
```json
{
  "https://myorg.com/claims/tenant_id": "tenant_456",
  "https://myorg.com/claims/permissions": ["read:loans", "write:loans"]
}
```

The payload is Base64URL encoded, not encrypted. Anyone who has the token can decode and read the payload. Never put secrets, PII beyond what's operationally necessary, or passwords in a JWT payload unless the token is encrypted (JWE, a separate spec).

**Q4. How is the signature constructed, and what does it protect?**
A: The signature is computed over the concatenation of the Base64URL-encoded header and payload:

```
signature = sign(
  algorithm  = header.alg,
  key        = signing_key,
  data       = base64url(header) + "." + base64url(payload)
)
```

For HS256:
```
HMAC-SHA256(secret, base64url(header) + "." + base64url(payload))
```

For RS256:
```
RSA-PKCS1v1.5-SHA256(private_key, base64url(header) + "." + base64url(payload))
```

The signature protects integrity — if any bit of the header or payload is modified after signing, the signature verification fails. It does not protect confidentiality. What the signature guarantees:
- The token was issued by someone holding the signing key.
- The header and payload have not been tampered with since issuance.

What it does not guarantee:
- The payload contents are secret (it's only Base64-encoded, not encrypted).
- The token is currently valid (that's what `exp`, `nbf`, `iat` are for — checked separately after signature verification).

## Section 2: Signing Algorithms — HS256 vs RS256

**Q5. What is HS256, and how does it work?**
A: HS256 is HMAC-SHA256 — a symmetric signing algorithm. The same secret key is used to both sign the token (at issuance) and verify the token (at validation).

```python
import hmac, hashlib, base64, json

header  = base64url_encode(json.dumps({"alg": "HS256", "typ": "JWT"}))
payload = base64url_encode(json.dumps({"sub": "user_123", "exp": 1700003600}))
message = f"{header}.{payload}".encode()

secret = b"my-256-bit-secret"
sig = hmac.new(secret, message, hashlib.sha256).digest()
token = f"{header}.{payload}.{base64url_encode(sig)}"
```

Because it's symmetric, every service that needs to verify JWTs must be given the secret. In a microservices architecture, this means the auth service and all downstream services share the same secret — a significant blast radius if the secret leaks. HS256 is appropriate when:
- You control all services that will verify the token (monolith or small, trusted internal system).
- Key distribution is manageable and secret rotation can be coordinated across all verifiers simultaneously.
- You don't need public verifiability (third parties shouldn't verify your tokens).

**Q6. What is RS256, and how does it differ from HS256?**
A: RS256 is RSA-PKCS1v1.5 with SHA-256 — an asymmetric signing algorithm. The auth server signs with its **private key**; any service verifies with the corresponding **public key**.

```
Auth Server (holds private key) → signs → JWT
API Service  (holds public key) → verifies → JWT valid/invalid
```

The public key can be distributed openly via a JWKS endpoint:
```
GET https://auth.myorg.com/.well-known/jwks.json

{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "kid": "2024-q4-primary",
      "n": "...",   // RSA modulus
      "e": "AQAB"  // Public exponent
    }
  ]
}
```

Any service that needs to verify tokens fetches the JWKS, caches the public key(s), and uses them to verify signatures — without ever seeing the private key. The private key never leaves the auth server. Key rotation requires only updating the JWKS; verifying services pick up the new key by re-fetching JWKS (usually on cache miss triggered by an unknown `kid`).

RS256 is appropriate when:
- Multiple independent services (including third parties) need to verify tokens without sharing a secret.
- You want to rotate keys without coordinating a simultaneous secret update across all services.
- Regulatory requirements mandate asymmetric cryptography for token signing (common in fintech).

**Q7. Compare HS256 and RS256 across the dimensions that matter in production.**
A:

| Dimension | HS256 | RS256 |
|---|---|---|
| Algorithm type | Symmetric (shared secret) | Asymmetric (private key signs, public key verifies) |
| Key distribution | Secret must be shared with every verifier | Public key distributed freely via JWKS; private key stays with auth server |
| Blast radius of key leak | Any service that holds the secret can forge tokens | Compromise of public key: nothing gained. Compromise of private key: attacker can forge tokens |
| Key rotation | All verifiers must update the secret simultaneously | Update JWKS; verifiers pick up new key on next cache miss (zero-downtime rotation) |
| Performance | Fast (single HMAC operation) | Slower (RSA computation ~10–100x vs HMAC, mitigated by caching) |
| Third-party verifiability | Not practical (can't share secret securely) | Yes — publish JWKS; any party can verify without trusting you with a secret |
| Typical use | Internal services, monoliths, dev/test | Microservices, OAuth2/OIDC, any multi-party system |
| Token size | Signature: 32 bytes (256-bit HMAC) | Signature: 256 bytes (2048-bit RSA) or 512 bytes (4096-bit RSA) |

For a fintech microservices platform, RS256 (or ES256 — ECDSA with SHA-256, which gives RS256-level security with smaller signatures and faster computation) is the standard choice.

**Q8. What is the `alg: none` vulnerability, and how do you prevent it?**
A: The JWT spec includes `"alg": "none"` to represent unsigned tokens. A token with `alg: none` has an empty signature. Some early library implementations trusted the `alg` field from the header and, when they saw `none`, skipped signature verification — treating the token as valid. An attacker who intercepts a valid JWT can:
1. Decode the header and payload (trivial — it's Base64).
2. Modify the payload (`"sub": "attacker"` → `"sub": "admin"`).
3. Re-encode with `"alg": "none"` and an empty signature.
4. Submit the forged token — a vulnerable server accepts it.

This was a real CVE class affecting `python-jose`, `node-jsonwebtoken`, `auth0-java`, and others in 2015–2018.

**Prevention:**
```python
# WRONG — trusts the algorithm from the token header
decoded = jwt.decode(token, secret)  # Some libraries do this

# CORRECT — explicitly allowlist accepted algorithms
decoded = jwt.decode(
    token,
    key=public_key,
    algorithms=["RS256"],  # Reject anything not in this list, including "none"
)
```

The fix is always to pass an explicit `algorithms` allowlist to your JWT library. Never pass `algorithms=None` or `algorithms=["*"]`. If your library doesn't accept an allowlist parameter, use a different library.

**Q9. What is the RS256 → HS256 confusion attack?**
A: A subtler variant of the `alg` attack. If a server normally uses RS256 and distributes its public key openly (via JWKS), an attacker can:
1. Obtain the server's RSA public key (it's public, after all).
2. Forge a token with `"alg": "HS256"` in the header.
3. Sign the forged token using HMAC-SHA256 with the RSA *public key* as the HMAC secret.
4. Submit the token — a vulnerable server that doesn't enforce the expected algorithm might try to verify with HS256 using the public key as the HMAC secret, and since the attacker signed it with that exact key, verification succeeds.

The attacker exploited the fact that the library used whatever algorithm the header declared, and the public key was reused as the HMAC secret.

**Prevention:** Same as Q8 — always pass a strict algorithm allowlist. A server configured for RS256 must reject any token claiming `HS256`, `none`, or any other algorithm.

## Section 3: Standard Claims — `iat`, `exp`, `nbf`, `jti`

**Q10. What is `iat`, and what is it used for?**
A: `iat` (Issued At) is a NumericDate — seconds since Unix epoch (not milliseconds) — representing when the token was issued.

```json
{
  "iat": 1700000000
}
// Equivalent to: 2023-11-14T22:13:20Z
```

Primary uses:
- **Token age validation** — even if `exp` is far in the future, you can reject tokens issued too long ago: `if (now - iat) > max_token_age: reject`. Useful for short-lived API keys that embed `iat` but have a long `exp` (or no `exp`).
- **Audit and logging** — `iat` tells you exactly when authentication occurred. Useful for correlating auth events with application logs.
- **Clock skew detection** — if `iat` is in the future (more than a few seconds ahead of the verifier's clock), the token may be forged or the clocks are badly skewed. Some libraries optionally validate this.

`iat` is informational — RFC 7519 does not require servers to validate it, only to include it if needed. In practice, always include it and validate token age server-side for sensitive operations (password reset tokens, payment authorization tokens) where you want a tighter bound than `exp` provides.

**Q11. What is `exp`, and what are the common validation edge cases?**
A: `exp` (Expiration Time) is a NumericDate after which the token must be rejected. The verifier must reject tokens where `now >= exp`.

```json
{
  "iat": 1700000000,
  "exp": 1700003600
}
// Token valid for exactly 1 hour from issuance
```

**Edge case 1 — Clock skew.** The issuer's clock and the verifier's clock are never perfectly synchronized. If the issuer's clock is 30 seconds ahead, a token with a 1-minute lifetime may be considered expired by the verifier immediately upon issuance. Most libraries allow a configurable clock skew tolerance (typically 30–60 seconds):
```python
jwt.decode(token, key, algorithms=["RS256"], leeway=timedelta(seconds=30))
```
Choose the smallest leeway that eliminates clock-skew false positives in your infrastructure — not 5 minutes.

**Edge case 2 — Missing `exp`.** A token with no `exp` claim is valid forever according to the spec. Most production auth systems should always set `exp`. Verify your library's behavior: does it accept exp-less tokens by default? If so, add an explicit check:
```python
payload = jwt.decode(token, key, algorithms=["RS256"])
if "exp" not in payload:
    raise ValueError("Token missing required exp claim")
```

**Edge case 3 — NumericDate is seconds, not milliseconds.** JavaScript's `Date.now()` returns milliseconds. If you accidentally store `Date.now()` (13 digits) in `exp` instead of `Math.floor(Date.now() / 1000)` (10 digits), the token appears to expire 1000x further in the future. Always use integer seconds.

**Q12. What is `nbf`, and when do you actually need it?**
A: `nbf` (Not Before) is a NumericDate before which the token must be rejected. The verifier must reject tokens where `now < nbf`. It's the temporal lower bound, complementing `exp` as the upper bound.

```json
{
  "iat": 1700000000,
  "nbf": 1700000300,
  "exp": 1700003600
}
// Token issued at T=0, but not valid until T+5min, expires at T+60min
```

Common use cases:

**Deferred access** — issue a token now for an action that should only be executable after some future event (e.g., a scheduled maintenance window opens, a payment hold period expires, a document becomes effective).

**Pre-issuance for batch operations** — generate tokens in advance for a cron job that runs at a specific time. The tokens carry `nbf` equal to the job's scheduled start time, so they can't be used if intercepted before the job runs.

**Grace period for distribution** — in systems where token distribution takes time (e.g., sent via email, propagated to a device), setting `nbf` slightly in the future ensures the token isn't valid until it's likely reached the recipient, reducing replay risk from interception in transit.

In practice, `nbf` is used rarely compared to `iat` and `exp`. Most systems achieve deferred access through application logic rather than JWT claims. Include `nbf` when the "not valid until" constraint is a security requirement, not just business logic — e.g., a one-time payment authorization token that must not be usable before the payment window opens.

**Q13. What is `jti`, and how does it enable token revocation?**
A: `jti` (JWT ID) is a unique identifier for the token — typically a UUID or a cryptographically random string. It provides a per-token identity that can be referenced outside the token itself.

```json
{
  "sub": "user_123",
  "jti": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "iat": 1700000000,
  "exp": 1700003600
}
```

**Primary use: JWT revocation.** JWTs are stateless — a valid, non-expired token is accepted by any verifier without consulting the auth server. This makes revocation hard: if a user logs out or their account is suspended, how do you invalidate their outstanding tokens before `exp`? Options:

1. **Blocklist by `jti`** — maintain a set of revoked `jti` values (Redis is the standard store). On each request, after signature and `exp` verification, check if the token's `jti` is in the blocklist. If yes, reject. On logout, add the `jti` to the blocklist with a TTL equal to the token's remaining lifetime (no point keeping it after `exp`).

```python
def verify_token(token: str, redis: Redis) -> dict:
    payload = jwt.decode(token, public_key, algorithms=["RS256"])
    jti = payload.get("jti")
    if not jti:
        raise ValueError("Missing jti claim")
    if redis.get(f"revoked_jti:{jti}"):
        raise ValueError("Token has been revoked")
    return payload

def logout(token: str, redis: Redis):
    payload = jwt.decode(token, public_key, algorithms=["RS256"])
    jti = payload["jti"]
    remaining_ttl = payload["exp"] - int(time.time())
    if remaining_ttl > 0:
        redis.setex(f"revoked_jti:{jti}", remaining_ttl, "1")
```

2. **Allowlist by `jti`** — instead of a blocklist of revoked tokens, maintain an allowlist of valid, currently-active tokens. More storage, but enables "sign out all devices" (invalidate all entries for a `sub`) without knowing each token's `jti` in advance. More operationally complex.

**Secondary use: replay prevention.** For sensitive one-time operations (password reset, email verification, payment authorization), mark the `jti` as used after first consumption. Subsequent requests with the same `jti` are rejected, preventing replay attacks even if the token hasn't expired.

**Q14. What is the `sub` claim, and what should it contain?**
A: `sub` (Subject) identifies the principal the token represents — typically the user's internal ID. RFC 7519 requires it to be unique within the context of the issuer. What to put in `sub`:

```json
{ "sub": "user_123" }        // Internal database ID — good
{ "sub": "usr_a1b2c3d4" }   // Prefixed opaque ID — good
{ "sub": "alice@myorg.com" } // Email — avoid (changes over time, PII in logs)
{ "sub": "alice" }           // Username — avoid (can be reassigned)
```

Use a stable, immutable internal identifier. If a user changes their email or username, `sub` must not change — the user is still the same principal. Using email or username in `sub` creates a class of bugs where reassigning that identifier to a new user lets the new user inherit the previous user's active tokens.

**Q15. What is the `iss` and `aud` claim, and why must you validate both?**
A: `iss` (Issuer) identifies who created the token. `aud` (Audience) identifies the intended recipient(s) of the token.

```json
{
  "iss": "https://auth.myorg.com",
  "aud": "https://loans-api.myorg.com",
  "sub": "user_123"
}
```

**Why validate `iss`:** A well-formed, correctly signed JWT from a *different* auth server is still not valid for your service. Validating `iss` ensures you only accept tokens from your own auth server — not tokens from a compromised or attacker-controlled issuer that happens to have a valid JWKS endpoint.

**Why validate `aud`:** This prevents the "confused deputy" attack. If user_123 obtains a valid JWT for service A (`aud: payments-api`), they should not be able to use that token to authenticate to service B (`aud: admin-api`). Both tokens might be signed by the same auth server with the same key and be structurally valid. Validating `aud` ensures each service only accepts tokens explicitly issued for it:

```python
jwt.decode(
    token,
    key=public_key,
    algorithms=["RS256"],
    issuer="https://auth.myorg.com",        # Validates iss
    audience="https://loans-api.myorg.com",  # Validates aud
)
```

Both validations are required. Skipping either is a real vulnerability pattern found in production systems.

## Section 4: Token Lifecycle and Refresh Patterns

**Q16. What is the access token / refresh token pattern, and why do short-lived access tokens require it?**
A: Short-lived access tokens (5–60 minutes) reduce the window of token misuse after compromise. But they also require the user to re-authenticate frequently. The refresh token pattern separates these concerns:

- **Access token** — short-lived JWT (15 minutes). Sent on every API request. If compromised, expires quickly. Verified offline by the API service (no auth server call per request).
- **Refresh token** — long-lived opaque token (7–30 days). Stored securely server-side. Only sent to the auth server to obtain a new access token. Never sent to API services.

```
Client                   Auth Server                  API
  |                           |                         |
  |── POST /login ───────────>|                         |
  |<── { access_token (15m),  |                         |
  |      refresh_token (7d) } |                         |
  |                           |                         |
  |── GET /loans ─────────────────────────────────────>|
  |     Authorization: Bearer <access_token>            |
  |<── 200 OK ─────────────────────────────────────────|
  |                           |                         |
  | [access_token expires]    |                         |
  |                           |                         |
  |── POST /token/refresh ───>|                         |
  |     { refresh_token }     |                         |
  |<── { new access_token }   |                         |
  |     (refresh_token rotated or reused)               |
```

Refresh tokens should be opaque (not JWTs), stored in the auth server's database, and revocable. When a user logs out or an account is suspended, invalidating the refresh token prevents new access tokens from being issued — effective revocation even if the current access token hasn't expired yet.

**Q17. What is refresh token rotation, and how does it detect theft?**
A: Refresh token rotation means the auth server issues a new refresh token on every `/token/refresh` call and invalidates the old one. If the old refresh token is ever used again after rotation, it signals that it was stolen — the server should invalidate the entire token family.

```
Normal flow:
Client uses RT1 → gets new AT + RT2 (RT1 invalidated)
Client uses RT2 → gets new AT + RT3 (RT2 invalidated)

Theft detection:
Attacker steals RT1 before client uses it.
Client uses RT1 first → gets RT2 (RT1 invalidated)
Attacker tries RT1 → INVALID → server detects replay of revoked token
→ Invalidate RT2 and all tokens in the family (suspicious activity)
```

Token families are tracked by storing `family_id` in the refresh token record. When any token in a family is replayed after rotation, the entire family is invalidated — the legitimate user's RT2 also stops working, forcing re-authentication and alerting the user.

**Q18. Where should JWTs be stored on the client, and what are the XSS vs CSRF trade-offs?**
A:

| Storage | XSS Risk | CSRF Risk | Notes |
|---|---|---|---|
| `localStorage` | High — any JS on the page can read it | None — not sent automatically | Simple to implement; vulnerable to any XSS |
| `sessionStorage` | High — same as localStorage, but scoped to tab | None | Cleared on tab close; still XSS-vulnerable |
| `HttpOnly` cookie | None — JS cannot read `HttpOnly` cookies | High — browser sends cookies automatically | Requires CSRF protection (SameSite, CSRF tokens) |
| `HttpOnly` + `SameSite=Strict` cookie | None | Low — not sent on cross-site requests | Breaks OAuth2 cross-domain flows; safest for same-domain |
| `HttpOnly` + `SameSite=Lax` cookie | None | Medium — not sent on cross-site POST | Good default; allows top-level navigation |

The current best-practice recommendation for web apps: store the access token in memory (a JS variable, not localStorage) for XSS resistance, use `HttpOnly` cookies for the refresh token. The access token is short-lived and in-memory — it's lost on page reload, but the refresh token in the cookie allows silent re-issuance. This gives XSS resistance for the refresh token (an attacker who achieves JS execution can't exfiltrate the refresh token) while keeping the access token available for API calls without CSRF risk (it's sent in the `Authorization` header, not automatically by the browser).

## Section 5: Advanced Patterns and Failure Scenarios

**Q19. Scenario: "Your auth server's private key for RS256 token signing is compromised. What do you do?"**
A: This is a P0 security incident. The attacker can now forge valid tokens for any user.

**Immediate (< 15 minutes):**
1. Generate a new RSA key pair on the auth server.
2. Update the JWKS endpoint to include the new public key with a new `kid` — do not remove the old key yet.
3. Configure the auth server to sign all new tokens with the new private key.
4. Remove the compromised private key from all systems (auth servers, CI secrets, HSMs).

**Short-term (< 1 hour):**
5. After the max access token TTL has passed (e.g., 15 minutes), remove the old public key from JWKS — this forces all outstanding tokens signed with the compromised key to fail verification, as verifiers can no longer find a matching key.
6. Invalidate all refresh tokens in the database — forces all users to re-authenticate, issuing new access tokens signed with the new key.
7. Audit logs for forged token usage: look for requests with valid signatures for users who did not initiate those sessions, or for privilege escalation patterns (`sub` values for admin accounts that have no corresponding login event).

**Post-incident:**
8. Move the private key to an HSM (AWS CloudHSM, GCP Cloud HSM) or a dedicated secrets manager. Private keys should never exist in plaintext on disk or in environment variables in production.
9. Implement key rotation as a routine operational procedure (quarterly or annually) so it's a practiced, non-emergency process.

**Q20. How do you implement JWT validation correctly in a Go microservice?**
A: A complete, production-safe validation flow:

```go
package auth

import (
    "context"
    "errors"
    "fmt"
    "time"

    "github.com/lestrrat-go/jwx/v2/jwk"
    "github.com/lestrrat-go/jwx/v2/jwt"
)

var keyCache *jwk.Cache

func init() {
    keyCache = jwk.NewCache(context.Background())
    keyCache.Register(
        "https://auth.myorg.com/.well-known/jwks.json",
        jwk.WithMinRefreshInterval(15*time.Minute),
    )
}

func ValidateToken(ctx context.Context, tokenString string) (jwt.Token, error) {
    // Fetch cached JWKS (auto-refreshed on kid miss)
    keySet, err := keyCache.Get(ctx, "https://auth.myorg.com/.well-known/jwks.json")
    if err != nil {
        return nil, fmt.Errorf("fetching JWKS: %w", err)
    }

    token, err := jwt.Parse(
        []byte(tokenString),
        jwt.WithKeySet(keySet),
        jwt.WithValidate(true),          // Validates exp, nbf, iat
        jwt.WithIssuer("https://auth.myorg.com"),
        jwt.WithAudience("https://loans-api.myorg.com"),
        jwt.WithAcceptableSkew(30*time.Second),
    )
    if err != nil {
        return nil, fmt.Errorf("invalid token: %w", err)
    }

    // Validate required claims
    if token.JwtID() == "" {
        return nil, errors.New("missing jti claim")
    }

    // Check revocation blocklist
    if err := checkRevocationBlocklist(ctx, token.JwtID()); err != nil {
        return nil, err
    }

    return token, nil
}
```

Key points: the JWKS cache handles `kid`-based key lookup and automatic refresh on cache miss — critical for zero-downtime key rotation. Validation is explicit: algorithm, issuer, audience, clock skew, required claims, and revocation check are all layered. Algorithm allowlisting is implicit here because `jwt.WithKeySet` only allows algorithms present in the JWKS — but verify your library's defaults.

**Q21. What is the "JWT everything" anti-pattern, and when should you use opaque tokens instead?**
A: JWTs are stateless and self-contained — verifiers don't need to call the auth server per request. This is their key advantage. But it's also their key limitation: you can't revoke a JWT before `exp` without maintaining server-side state (the `jti` blocklist from Q13). At that point, you've added per-request state anyway.

**Use opaque tokens (random strings looked up in a database or cache) when:**
- You need instant revocation — the token is invalidated the moment it's deleted from the store, with no waiting for `exp`.
- Token contents must be mutable — if session data changes during a session (e.g., user upgrades their plan mid-session, permissions change), an opaque token can be updated server-side; a JWT cannot.
- You want to limit what's exposed in transit — opaque tokens reveal nothing; JWT payloads reveal everything in the claims.

**Use JWTs when:**
- You want offline, stateless verification — API services verify tokens without a database call, reducing auth server load at scale.
- Tokens cross trust boundaries — JWTs with JWKS-based verification are the standard for OAuth2/OIDC; opaque tokens require a token introspection endpoint.
- Token contents need to be read by the client — a JWT's `roles`, `permissions`, or `tenant_id` claims can be decoded client-side to drive UI decisions, without an extra API call.

In a mature fintech system: refresh tokens are opaque (instant revocation on logout/suspension), access tokens are JWTs (offline verification in every microservice). This hybrid captures both benefits.

**Q22. Scenario: "A JWT `exp` claim is set 1 year in the future on your production access tokens. What is wrong, and how do you fix it without logging out all users?"**
A: A 1-year access token is effectively a permanent credential. If the token is intercepted (network sniff, log leak, XSS), the attacker has valid credentials for up to a year. Revocation requires the `jti` blocklist approach — and you're maintaining state for millions of tokens for a year.

**The fix — rolling token TTL reduction:**
1. Deploy a new auth server config with `exp = now + 15 minutes` for all newly issued tokens.
2. Existing tokens still have 1-year `exp`. You cannot shorten them without invalidating them. Options:
   - **Tolerate the transition period** — existing tokens expire naturally over the next year. New logins get short-lived tokens. Acceptable if you can tolerate the asymmetry for existing sessions.
   - **Force re-authentication** — announce a security maintenance window, invalidate all refresh tokens (database wipe of the refresh token table), forcing all users to re-login. All new access tokens are short-lived. Clean break; user experience impact is one forced logout.
   - **`iat`-based enforcement** — add a server-side policy: regardless of `exp`, reject any access token where `now - iat > 15 minutes`. Deploy this policy to all API services. All existing long-lived tokens start failing immediately after 15 minutes of issuance. Effectively shortens TTL without modifying existing tokens. Test thoroughly — you'll also reject legitimate long-lived tokens issued for specific use cases (batch jobs, service accounts).

Option 3 is the most surgical and avoids a forced logout, but requires coordination across all API services to deploy the new validation policy simultaneously.

## Section 6: JWE, JWKS, and Ecosystem

**Q23. What is the difference between JWT (JWS) and JWE?**
A: Most JWTs you encounter are technically JWS (JSON Web Signature) — signed but not encrypted. JWE (JSON Web Encryption) is the encrypted counterpart.

| Property | JWS (standard JWT) | JWE |
|---|---|---|
| Payload visibility | Readable by anyone with the token (Base64-decoded) | Encrypted; only the intended recipient can read it |
| Structure | `header.payload.signature` (3 parts) | `header.encrypted_key.iv.ciphertext.tag` (5 parts) |
| Use case | Integrity + authenticity | Integrity + authenticity + confidentiality |
| Complexity | Simple | Requires key management for encryption keys, not just signing keys |

JWE is appropriate when the JWT payload contains sensitive data (PII, financial data) that must not be visible to intermediaries (reverse proxies, logging infrastructure) that see the raw token. For most service-to-service auth use cases, JWS with HTTPS is sufficient — the transport layer provides confidentiality for the token in transit, and the payload is only processed at the trusted endpoint.

**Q24. How does JWKS key rotation work in practice, and what is the `kid` cache miss pattern?**
A: Key rotation without downtime requires the verifier to handle `kid` cache misses gracefully:

```
Normal flow (key found in cache):
Verifier receives token with kid="2024-q4-primary"
→ Looks up kid in local JWKS cache
→ Found → verifies signature → accepts token

Rotation flow (new key, cache miss):
Auth server generates new key pair, assigns kid="2025-q1-primary"
Auth server adds new public key to JWKS, keeps old key during overlap period
Verifier receives token with kid="2025-q1-primary"
→ Looks up kid in local JWKS cache
→ NOT FOUND (cache is stale)
→ Re-fetches JWKS from https://auth.myorg.com/.well-known/jwks.json
→ New key found → updates cache → verifies signature → accepts token
```

Key operational details:
- **Overlap period** — keep the old public key in JWKS for at least one max-access-token-TTL (e.g., 15 minutes) after switching to the new signing key. Tokens signed with the old key before rotation are still in circulation; they need the old public key for verification.
- **JWKS cache TTL** — don't cache JWKS aggressively. A 15-minute TTL with kid-miss-triggered refresh balances auth server load against rotation responsiveness.
- **Pre-announce rotation** — in a microservices setup with many verifier instances, trigger a JWKS re-fetch across all instances after rotation to avoid a 15-minute window of kid-miss-triggered fetches at scale. Some service meshes support JWKS push rather than pull.

## Quick Reference: Algorithm Comparison

| Algorithm | Type | Key | Signature Size | Use Case |
|---|---|---|---|---|
| `HS256` | HMAC-SHA256 | Symmetric secret | 32 bytes | Monolith / internal services |
| `HS512` | HMAC-SHA512 | Symmetric secret | 64 bytes | Same as HS256, larger HMAC |
| `RS256` | RSA-SHA256 | Asymmetric (2048-bit RSA) | 256 bytes | Microservices, OAuth2/OIDC |
| `RS512` | RSA-SHA512 | Asymmetric (2048-bit RSA) | 256 bytes | Same as RS256, stronger hash |
| `ES256` | ECDSA-SHA256 | Asymmetric (P-256 curve) | 64 bytes | RS256 security, smaller token |
| `PS256` | RSASSA-PSS-SHA256 | Asymmetric (2048-bit RSA) | 256 bytes | RS256 with randomized padding |
| `none` | None | None | 0 bytes | **Never use in production** |
