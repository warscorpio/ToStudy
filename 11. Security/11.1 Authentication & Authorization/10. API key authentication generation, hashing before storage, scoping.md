# Security (Authentication): API Key Authentication — Generation, Hashing Before Storage, Scoping — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is an API key, and how does it differ from a password or a JWT?**
A: An API key is a long, randomly-generated opaque token that identifies and authenticates a caller to an API — typically a machine-to-machine caller (a service, a script, a third-party integration) rather than a human. The key distinctions:

- **vs. password** — a password authenticates a human identity and is chosen (often weakly) by the user. An API key is machine-generated with full cryptographic entropy, never chosen by a human, and rotated independently of a user account. Passwords authenticate to get a session; API keys *are* the credential for every request.
- **vs. JWT** — a JWT is a *structured*, signed token containing claims (user ID, roles, expiry) that can be verified without a database lookup (stateless). An API key is opaque — it has no inherent structure or embedded claims. Verifying it requires a database lookup to retrieve the associated metadata (who owns it, what scopes it has, is it revoked). JWTs expire automatically; API keys are long-lived until explicitly rotated or revoked.
- **vs. OAuth access token** — OAuth access tokens are issued through a delegation flow (user grants consent) and are typically short-lived. API keys represent direct authorization, are long-lived, and have no concept of a delegating user — they represent the application itself.

**Q2. What are the typical use cases for API keys vs. other auth mechanisms?**
A: API keys fit machine-to-machine scenarios where:
- The caller is a known, trusted service or partner (not an end user) — e.g., a payment gateway calling your webhook, a third-party NACH provider, a data pipeline hitting your internal API.
- Long-lived credentials are acceptable because the caller has a secure secret store.
- Simplicity matters — no OAuth dance, no token refresh, just include the key in every request.
- You need easy revocation per integration — revoking one API key doesn't affect other callers.

API keys are *not* appropriate for: browser-based SPA clients (keys embedded in JS are visible to users), mobile apps where the binary can be reversed, or any scenario requiring user-level identity with delegated access (use OAuth/OIDC instead). In fintech, API keys are common for B2B integrations — a lending partner POSTing loan applications to your origination API, a KYC provider's webhook, or your own internal service-to-service calls in a shared-secret model.

**Q3. What properties must a cryptographically secure API key have?**
A: Four properties:

1. **Sufficient entropy** — the key must be generated from a cryptographically secure random source (CSPRNG), not `Math.random()` or `Date.now()`. The industry standard is at least 128 bits of entropy (16 bytes), typically expressed as 32 hex characters or a base64url-encoded string. 256 bits (32 bytes → 43 base64url characters) is better and costs nothing.
2. **Unpredictability** — no sequential component, no timestamp in the key, no relationship between consecutively generated keys. An attacker who knows 1,000 valid keys must gain zero information about the 1,001st.
3. **Sufficient length** — long enough that brute-force enumeration is computationally infeasible. At 256 bits, exhaustive search is impossible with any foreseeable technology.
4. **URL-safe encoding** — keys appear in HTTP headers and occasionally query strings. Base64url (RFC 4648 §5) — which substitutes `+` → `-` and `/` → `_` and omits padding `=` — is the standard encoding. Hex is simpler but 2× longer for the same bit-strength.

**Q4. How do you generate a cryptographically secure API key in Node.js?**
A:
```js
import crypto from 'node:crypto';

/**
 * Generates a cryptographically secure API key.
 * Returns: "prefix_<32-byte base64url>" — e.g. "lapi_abc123..."
 *
 * The prefix makes keys visually identifiable by their origin service
 * and enables secret scanning tools (GitHub, GitLab) to detect leaks.
 */
function generateApiKey(prefix = 'lapi') {
  const rawBytes = crypto.randomBytes(32);          // 256 bits of entropy
  const encoded  = rawBytes.toString('base64url');  // 43 URL-safe characters
  return `${prefix}_${encoded}`;                    // e.g. lapi_abc123XYZ...
}

// Example output: lapi_4K8mNpQrStUvWxYzAbCdEfGhIjKlMnOpQrStUvWxYz0
```

`crypto.randomBytes()` is Node's interface to the OS CSPRNG (`/dev/urandom` on Linux, `BCryptGenRandom` on Windows). Never use `Math.random()`, `uuid` v1 (timestamp-based), or any deterministic source for security tokens. The prefixed format (`lapi_`, `sk_live_`, `whsec_`) is a pattern popularized by Stripe — it lets secret scanning tools write simple regex rules to detect leaked keys in git commits and CI logs.

## Section 2: Hashing Before Storage

**Q5. Why must API keys be hashed before storage, and why isn't encryption sufficient?**
A: API keys must be stored as hashes — not in plaintext and not encrypted — for the same reason passwords must be hashed: if your database is compromised, an attacker must not be able to recover the raw keys.

Encryption is insufficient because it's *reversible*: whoever holds the encryption key can decrypt all API keys and immediately use them. If the encryption key is compromised (leaked in config, exposed via a misconfigured KMS policy, stolen by a rogue admin), every API key in the database is simultaneously compromised. A hash is a one-way function — there is no decryption step, no key to steal. The attacker gets a table of hashes and must crack each one individually.

The practical security model: a database breach leaks hashed keys. Cracking a properly hashed, high-entropy random key requires `2^256` operations — computationally infeasible. Compare this to a password breach where users chose weak passwords — the entropy is low so cracking is feasible. API keys have full machine-generated entropy, so the hash function choice matters less than for passwords — but using a fast hash (SHA-256) is still acceptable *specifically because* the key has high entropy. The rationale for bcrypt/Argon2 on passwords (key-stretching to slow brute force) doesn't apply to 256-bit random API keys — brute force is infeasible regardless of hash speed.

**Q6. Which hash function should you use for API keys — SHA-256, bcrypt, or Argon2?**
A: **SHA-256** is the correct choice for high-entropy API keys. This surprises engineers who know "always use bcrypt/Argon2 for secrets." The distinction:

- **Passwords** — low entropy (users choose them, often < 30 bits of effective entropy). Must use a slow, memory-hard KDF (bcrypt, Argon2) to make brute force costly. `bcrypt` with cost factor 12 takes ~250ms — intentionally slow.
- **API keys** — high entropy (256 bits of CSPRNG output). Brute force is computationally infeasible regardless of hash speed. Using bcrypt on API keys adds 250ms to *every authenticated request* (every request re-hashes the presented key and compares), which is unacceptable latency for a high-throughput API. SHA-256 hashing takes ~1µs.

The correct decision matrix: if the pre-image has ≥ 128 bits of random entropy → SHA-256 is fine. If the pre-image is human-chosen or low-entropy → use Argon2id.

```js
import crypto from 'node:crypto';

function hashApiKey(rawKey) {
  return crypto
    .createHash('sha256')
    .update(rawKey)
    .digest('hex');  // 64 hex chars — store this in the DB
}

// Usage
const rawKey = generateApiKey('lapi');   // shown to user once
const hashed = hashApiKey(rawKey);       // stored in database

// On authentication
function verifyApiKey(presentedKey, storedHash) {
  const presentedHash = hashApiKey(presentedKey);
  // Constant-time comparison to prevent timing attacks
  return crypto.timingSafeEqual(
    Buffer.from(presentedHash, 'hex'),
    Buffer.from(storedHash, 'hex')
  );
}
```

**Q7. What is a timing attack, and why must you use `crypto.timingSafeEqual` when comparing hashes?**
A: A timing attack exploits the fact that a naive string comparison (`===`) short-circuits — it returns `false` as soon as it finds the first mismatched character. An attacker who can measure response time precisely can determine how many leading characters of their guess are correct: a guess that fails at character 3 takes slightly longer than one that fails at character 1. By incrementally refining guesses, they can recover the stored hash character by character — without needing a database breach.

`crypto.timingSafeEqual` compares two `Buffer`s in constant time — it always examines every byte regardless of where the first mismatch occurs, so response time leaks zero information about the comparison result. Always use it when comparing any security-sensitive value (hashes, HMACs, tokens):

```js
// WRONG — leaks timing information
if (presentedHash === storedHash) { ... }

// CORRECT — constant-time comparison
const a = Buffer.from(presentedHash, 'hex');
const b = Buffer.from(storedHash, 'hex');
if (a.length === b.length && crypto.timingSafeEqual(a, b)) { ... }
```

Note: both buffers must be the same length before calling `timingSafeEqual` — it throws if lengths differ. Always check length equality first (length comparison doesn't need to be constant-time since length is not secret).

**Q8. Should you add a salt to the SHA-256 hash of an API key?**
A: A salt's purpose is to defeat *precomputed* attacks — rainbow tables and batch cracking (hashing one guess and checking it against millions of hashes simultaneously). For passwords, salts are mandatory because low-entropy pre-images are vulnerable to precomputation. For API keys with 256 bits of entropy, precomputation is infeasible regardless — the key space is too large. A rainbow table for 256-bit keys would require more storage than atoms in the universe.

That said, adding an HMAC (Hash-based Message Authentication Code) with a server-side secret key is a common enhancement that goes further than a salt:

```js
function hashApiKey(rawKey) {
  return crypto
    .createHmac('sha256', process.env.API_KEY_HMAC_SECRET)
    .update(rawKey)
    .digest('hex');
}
```

An HMAC ties the hash to a server-side secret. Even if the database is fully exfiltrated, an attacker can't verify candidate keys without also knowing the HMAC secret (which lives outside the database — in an environment variable, AWS Secrets Manager, or Vault). This is defense-in-depth: the database breach alone is not sufficient to mount any offline attack. The HMAC secret must be rotated if compromised, which requires re-hashing all stored keys — plan for this operationally.

**Q9. The user creates an API key. Walk through the complete show-once flow and what gets stored where.**
A:
```
User requests API key creation
         │
         ▼
Backend generates rawKey = "lapi_4K8mNpQrStUvWx..."   (crypto.randomBytes(32))
         │
         ├──► Shown to user ONCE in the response body / UI
         │    "Here is your API key. Copy it now — we will not show it again."
         │
         └──► hashed = SHA-256(rawKey) or HMAC-SHA256(rawKey, secret)
                    │
                    ▼
              Stored in database:
              {
                id:           "key_01J...",
                hash:         "a3f8c2...64 hex chars",
                prefix:       "lapi",          ← for display ("lapi_****abc")
                last_four:    "Wxyz",           ← for user to identify which key
                name:         "Production webhook",
                owner_id:     "user_123",
                scopes:       ["loans:read", "nach:write"],
                created_at:   "2025-08-12T10:00:00Z",
                last_used_at: null,
                expires_at:   "2026-08-12T10:00:00Z",
                revoked_at:   null
              }
```

The raw key never touches the database. The `last_four` field lets users identify which key is which in the dashboard without exposing the full key. The `prefix` lets you display `lapi_••••••••Wxyz` — the masked format Stripe, GitHub, and others use.

**Q10. How do you display existing API keys in a dashboard without storing the raw key?**
A: You store only enough metadata to let the user identify the key — not enough to reconstruct it. The standard pattern:

- **Prefix** — the service/type prefix (`lapi`, `sk_live`) stored as a plain column.
- **Last N characters** — typically 4, stored as a plain column. Shown as `lapi_••••••••abc1` in the UI.
- **Key name** — user-provided label ("Production NACH webhook", "Staging integration test").
- **Fingerprint** — optional: the first 8 chars of the SHA-256 hash of the key (not the key itself), shown to advanced users for verification without storage of anything reversible.
- **Created at, last used at** — operational metadata.

Never store the first N characters of the raw key — combined with the last N characters from above, partial key recovery becomes easier. Storing the last 4 is safe because 4 characters have only `62^4 ≈ 14 million` combinations — an attacker who knows the last 4 still has the full `2^256` key space to search (they must brute-force the rest, not just the missing suffix).

## Section 3: Scoping

**Q11. What is API key scoping, and why is it necessary?**
A: Scoping assigns a set of permissions to an API key, restricting what the caller can do with it. Without scoping, every API key grants full access to everything the owning account can do — a leaked key is a complete account compromise. With scoping, a key created for a specific integration has only the minimum permissions needed for that integration (principle of least privilege). A leaked narrow-scoped key is a limited compromise, not a total one.

In practice: a KYC provider's webhook processing key needs `kyc:write` but not `loans:read` or `user:admin`. A read-only reporting integration needs `reports:read` only. An internal NACH processing service needs `nach:write`. If any of these keys leak, the blast radius is bounded to what the key can actually do.

**Q12. What are common scoping models, and how do you design a scope hierarchy for a fintech API?**
A: Three common models:

**Flat scopes** — a set of named permissions with no hierarchy: `["loans:read", "loans:write", "kyc:read", "nach:write"]`. Simple to implement and reason about. Each scope is independently grantable. Best for APIs with a small, stable set of resources.

**Hierarchical / wildcard scopes** — a namespace-based system where `loans:*` grants all loan permissions: `loans:read`, `loans:write`, `loans:delete`. `*` grants everything. More expressive but harder to audit ("what does `loans:*` actually include?").

**Resource-level scopes** — scopes parameterized by resource ID: `loans:read:loan_abc123`. Grants access to a specific loan, not all loans. Powerful for multi-tenant APIs but complex to implement and store.

A practical fintech scope design:

```
# Format: <domain>:<action>
loans:read          — read loan applications and status
loans:write         — create and update loan applications
loans:disburse      — trigger disbursement (high-privilege, separate from write)
kyc:read            — read KYC results
kyc:write           — submit KYC data (e.g., from a KYC provider webhook)
nach:read           — read NACH mandates
nach:write          — create and cancel NACH mandates
users:read          — read user profiles
users:write         — update user profiles
reports:read        — access reporting and analytics endpoints
admin:*             — full access (only for internal service accounts)
webhooks:read       — read webhook delivery logs
webhooks:write      — configure webhook endpoints
```

Store scopes as a `text[]` array (PostgreSQL) or a JSON array on the API key record. Check them on every request: does the presented key's scope array include the scope required by the endpoint?

**Q13. How do you implement scope checking in a NestJS API using guards?**
A:
```typescript
// scopes.decorator.ts
import { SetMetadata } from '@nestjs/common';
export const SCOPES_KEY = 'required_scopes';
export const RequireScopes = (...scopes: string[]) =>
  SetMetadata(SCOPES_KEY, scopes);

// api-key.guard.ts
import {
  Injectable, CanActivate, ExecutionContext,
  UnauthorizedException, ForbiddenException,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { SCOPES_KEY } from './scopes.decorator';
import { ApiKeyService } from './api-key.service';

@Injectable()
export class ApiKeyGuard implements CanActivate {
  constructor(
    private readonly reflector: Reflector,
    private readonly apiKeyService: ApiKeyService,
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const req = context.switchToHttp().getRequest();

    // Extract key from Authorization header: "Bearer lapi_xxx" or "X-API-Key: lapi_xxx"
    const raw = this.extractKey(req);
    if (!raw) throw new UnauthorizedException('API key required');

    // Look up and validate the key
    const keyRecord = await this.apiKeyService.validate(raw);
    if (!keyRecord) throw new UnauthorizedException('Invalid or revoked API key');

    // Check required scopes
    const required: string[] = this.reflector.getAllAndOverride(SCOPES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]) ?? [];

    const hasAllScopes = required.every(s => keyRecord.scopes.includes(s));
    if (!hasAllScopes) throw new ForbiddenException('Insufficient scope');

    // Attach key record to request for downstream use
    req.apiKey = keyRecord;
    // Update last_used_at asynchronously — don't await, don't block the request
    this.apiKeyService.recordUsage(keyRecord.id).catch(() => {});

    return true;
  }

  private extractKey(req: Request): string | null {
    const auth = req.headers['authorization'];
    if (auth?.startsWith('Bearer ')) return auth.slice(7);
    return req.headers['x-api-key'] ?? null;
  }
}

// Usage on a controller
@Controller('loans')
@UseGuards(ApiKeyGuard)
export class LoansController {
  @Get()
  @RequireScopes('loans:read')
  findAll() { ... }

  @Post(':id/disburse')
  @RequireScopes('loans:read', 'loans:disburse')  // requires both
  disburse(@Param('id') id: string) { ... }
}
```

**Q14. How should scope changes (adding or removing scopes from an existing key) be handled?**
A: Scope changes take effect on the next request — there's no token expiry to wait for (unlike JWTs where a scope change requires waiting for the old token to expire). The database record is the live source of truth; the next request re-validates against it.

Operationally:
- **Narrowing scopes** (removing permissions) is always safe and takes immediate effect. The key holder loses access to that scope on the next request.
- **Broadening scopes** (adding permissions) should require the same approval flow as creating a new key with those scopes — don't allow a self-service scope upgrade without authorization review.
- **Scope change audit log** — every scope modification should be logged with who changed it, when, from what to what. This is a compliance requirement (PCI-DSS req 10, RBI access management controls) — treat scope changes as access control changes.
- **Immutable-scope model** — some teams prefer keys to be immutable post-creation: if scopes need to change, revoke the key and issue a new one with the correct scopes. Simpler audit trail, clearer security model, but operationally noisier (callers must rotate the key).

**Q15. What is scope inheritance or scope escalation, and how do you prevent it?**
A: Scope escalation is when a caller with limited permissions can create an API key (or token) with *more* permissions than they themselves have. Example: a user with only `loans:read` creates a new API key with `loans:write` — the key grants access the creating user doesn't have. This is a privilege escalation vulnerability.

Prevention: enforce that the scopes on any key created by a user or service account are a *subset* of the creator's own scopes at creation time:

```typescript
async createApiKey(creator: AuthenticatedUser, requestedScopes: string[]): Promise<ApiKey> {
  // Validate that requested scopes are a strict subset of creator's own scopes
  const illegalScopes = requestedScopes.filter(s => !creator.scopes.includes(s));
  if (illegalScopes.length > 0) {
    throw new ForbiddenException(
      `Cannot create key with scopes not held by creator: ${illegalScopes.join(', ')}`
    );
  }

  // Proceed with key creation
  const rawKey = generateApiKey('lapi');
  const hash   = hashApiKey(rawKey);
  await this.db.apiKeys.insert({ hash, scopes: requestedScopes, ... });
  return { rawKey }; // shown once
}
```

This is the "scope confinement" principle — you can only delegate what you have. OAuth 2.0 enforces the same principle: an access token can only have scopes that the authorizing user has consented to.

## Section 4: Storage, Transmission, and Lifecycle

**Q16. How should API keys be transmitted — header, query string, or request body?**
A: **Always the `Authorization` header** (preferred) or a custom `X-API-Key` header. Never in the query string.

The `Authorization` header with `Bearer` scheme is the standard:
```
Authorization: Bearer lapi_4K8mNpQrStUvWx...
```

Some APIs use a custom header for clarity (not `Bearer`, just the raw key):
```
X-API-Key: lapi_4K8mNpQrStUvWx...
```

Query strings are problematic because:
- **Server access logs** — virtually every web server, load balancer, CDN, and API gateway logs the full URL including query parameters. An API key in the query string is logged in plaintext across your entire infrastructure stack.
- **Browser history / Referrer header** — if the URL is ever opened in a browser (e.g., during debugging), the key appears in browser history and in the `Referer` header of subsequent navigations.
- **Proxies and caches** — intermediate infrastructure may cache responses based on full URL, including the key.

TLS encrypts the body and headers in transit, so both header and body are protected. Query strings are also encrypted by TLS — but they're still logged before and after decryption at your own infrastructure, which is where the risk lies. Headers are less likely to be logged in full (most systems log headers selectively, not `Authorization`).

**Q17. How do you implement API key lookup efficiently given that you only store the hash?**
A: You can't look up by raw key (you don't store it). You must hash the presented key first, then query by hash:

```typescript
// api-key.service.ts
async validate(rawKey: string): Promise<ApiKeyRecord | null> {
  // 1. Basic format check — reject garbage before hashing
  if (!rawKey.startsWith('lapi_') || rawKey.length < 20) return null;

  // 2. Hash the presented key
  const hash = hashApiKey(rawKey);

  // 3. Lookup by hash — add a DB index on the hash column
  const record = await this.db.apiKeys.findOne({
    where: {
      hash,
      revoked_at: IsNull(),
      expires_at: MoreThan(new Date()),    // or IsNull() for non-expiring keys
    }
  });

  return record ?? null;
}
```

The hash column must be indexed (a B-tree index on a `char(64)` or `varchar(64)` column) for O(log n) lookup. Since SHA-256 hashes are uniformly distributed, the index is well-balanced. Authentication is then: 1µs to hash + ~1ms DB index lookup — well within acceptable latency.

For very high-throughput APIs, add a cache layer:

```typescript
async validate(rawKey: string): Promise<ApiKeyRecord | null> {
  const hash       = hashApiKey(rawKey);
  const cacheKey   = `apikey:${hash}`;

  // Check Redis cache first — TTL of 60 seconds
  const cached = await this.redis.get(cacheKey);
  if (cached !== null) {
    return cached === 'revoked' ? null : JSON.parse(cached);
  }

  const record = await this.db.apiKeys.findOne({ where: { hash, ... } });

  // Cache the result — "revoked" sentinel for invalid/missing keys
  await this.redis.setex(
    cacheKey,
    60,
    record ? JSON.stringify(record) : 'revoked'
  );

  return record;
}
```

Cache TTL is a trade-off: a 60-second TTL means a revoked key may continue to work for up to 60 seconds. For most APIs this is acceptable. For high-security use cases (financial transactions, sensitive data writes), use a shorter TTL or skip the cache for write operations and cache only reads.

**Q18. How do you implement key expiration and rotation?**
A: Keys should have an `expires_at` timestamp. The rotation flow:

```typescript
// Rotation: issue a new key, give a grace period, then revoke the old one
async rotateApiKey(oldKeyId: string, expiresIn: Duration): Promise<RotationResult> {
  const newRaw  = generateApiKey('lapi');
  const newHash = hashApiKey(newRaw);

  await this.db.transaction(async (tx) => {
    // Create the new key
    await tx.apiKeys.insert({
      hash:       newHash,
      scopes:     (await tx.apiKeys.findOne(oldKeyId)).scopes,
      created_at: new Date(),
      expires_at: addDuration(new Date(), expiresIn),
    });

    // Schedule the old key for expiry — grace period lets existing callers migrate
    await tx.apiKeys.update(oldKeyId, {
      expires_at: addMinutes(new Date(), 30),  // 30-minute overlap window
    });
  });

  return { newKey: newRaw }; // shown once
}
```

The grace period (overlap window) allows the key consumer to update their secret store and rotate without a hard cutover — both keys work simultaneously for 30 minutes, then the old one expires. This is critical for zero-downtime rotation in production integrations. For automated rotation (e.g., triggered by AWS Secrets Manager's rotation Lambda), the grace period is essential.

**Q19. How do you handle key revocation, and what's the difference between soft and hard revocation?**
A:
- **Soft revocation** — set `revoked_at = NOW()` on the key record. Lookups check `revoked_at IS NULL`. The row remains in the database for audit trail purposes. Revocation takes effect on the next request (or after cache TTL expires).
- **Hard deletion** — `DELETE FROM api_keys WHERE id = ?`. Immediate, but loses the audit trail. Never do this for security-sensitive revocations (key compromise, terminated employee's key, suspected abuse) — you want the record for forensic investigation.

Always use soft revocation in production. The revoked key record tells you: when was it created, when was it last used, when was it revoked, and why (add a `revocation_reason` column: `user_requested`, `key_compromised`, `employee_offboarding`, `ttl_expired`). This audit trail is a PCI-DSS requirement.

For immediate revocation in high-security scenarios (confirmed key compromise), complement soft revocation with a cache invalidation:

```typescript
async revokeApiKey(keyId: string, reason: string): Promise<void> {
  const key = await this.db.apiKeys.findOne(keyId);
  await this.db.apiKeys.update(keyId, {
    revoked_at: new Date(),
    revocation_reason: reason,
  });
  // Immediately invalidate cache — don't wait for TTL
  await this.redis.del(`apikey:${key.hash}`);
}
```

**Q20. Should API keys expire automatically, and what's the recommended TTL for different key types?**
A: Expiry is best practice but the right TTL varies by use case:

| Key type | Recommended TTL | Rationale |
|---|---|---|
| User-generated integration key | 1 year | Long enough to avoid frequent rotation burden; short enough to enforce periodic hygiene |
| CI/CD pipeline key | 90 days | Frequent rotation aligns with deployment cycles |
| Internal service-to-service key | 30–90 days | Automated rotation via secrets manager; short TTL limits blast radius |
| Webhook signing secret | No expiry (manual rotation) | Rotation requires coordinating with external partner; TTL impractical |
| Short-lived scoped key (e.g., one-time export) | 1–24 hours | Created on demand, expires automatically |

For long-lived keys, send expiry warning emails/notifications at 30 days, 7 days, and 1 day before expiry — many integrations break silently when a key expires in production. Build a job that queries `WHERE expires_at BETWEEN NOW() AND NOW() + INTERVAL '30 days'` and triggers notifications. Never let a key expire without warning — that's a production incident waiting to happen.

## Section 5: Security Hardening and Real-World Scenarios

**Q21. How do you detect and respond to a leaked API key?**
A: Leaked keys are discovered through multiple vectors — GitHub secret scanning, a developer accidentally logging the key, a support ticket with the key in it, or your own proactive scanning.

**Detection:**
- **GitHub secret scanning** — GitHub scans all pushes for secrets matching registered patterns. Register your key format (`lapi_[A-Za-z0-9_-]{43}`) with GitHub's secret scanning partner program. GitHub will alert you (and optionally call a webhook) when a key matching your pattern is pushed to any public repo.
- **Log scanning** — run regex scans over your application logs and CI/CD logs periodically. Keys leaked via `console.log` or curl commands in CI output are common.
- **Canary keys** — generate API keys with no real permissions and distribute them to honeypot locations (a public GitHub gist, a test project). If a canary key is ever used, you know your detection pipeline works (or that a specific location leaked).

**Response (treat as security incident):**
1. Immediately revoke the key and invalidate its cache entry.
2. Check `last_used_at` and audit logs — was the key used after it was leaked? If so, assume the worst and investigate what was accessed.
3. Notify the key owner.
4. If the key had `admin:*` or broad scopes, treat it as a full account compromise and audit all actions taken during the exposure window.
5. Post-incident: enforce key scoping so future leaks have limited blast radius.

**Q22. What is key prefixing (e.g., `sk_live_`, `lapi_`), and how does it help with secret scanning?**
A: Key prefixes serve two purposes:

1. **Operational clarity** — a key starting with `sk_live_` is immediately recognizable as a production secret. `sk_test_` is a test key. `lapi_` is a loans API key. Engineers can visually distinguish key types at a glance in logs, configs, and support tickets.
2. **Automated secret scanning** — secret scanning tools (GitHub, GitLab, TruffleHog, Gitleaks) use regex patterns to detect secrets. A distinctive, consistent prefix makes your keys trivially detectable: pattern `lapi_[A-Za-z0-9_-]{43}` matches your keys with zero false positives and zero false negatives. Without a prefix, detecting a raw 43-character base64url string reliably is much harder (high false positive rate). Stripe, GitHub (`ghp_`, `ghs_`), npm (`npm_`), and Twilio all use this pattern for exactly this reason.

Register your prefix pattern with GitHub's secret scanning partner program (free for organizations) so GitHub automatically revokes leaked keys by calling your webhook. This turns a potential incident into an automated response.

**Q23. How do you implement rate limiting per API key to prevent abuse?**
A: Rate limiting per API key is a first-class concern — a single compromised or misbehaving key shouldn't be able to DoS your API or enumerate data. Implement at two layers:

**At the API gateway / infrastructure layer** (preferred for low latency):
- AWS API Gateway, Kong, or nginx-lua can rate-limit by the `X-API-Key` header value before the request reaches your application. This is cheapest in terms of compute.

**At the application layer** (for fine-grained per-key limits):
```typescript
// Redis-based sliding window rate limiter per API key
async checkRateLimit(keyId: string, limit: number, windowSeconds: number): Promise<void> {
  const redisKey = `ratelimit:${keyId}`;
  const now      = Date.now();
  const window   = now - windowSeconds * 1000;

  await this.redis.zremrangebyscore(redisKey, '-inf', window);    // remove old entries
  const count = await this.redis.zcard(redisKey);                  // count in window

  if (count >= limit) {
    throw new TooManyRequestsException(
      `Rate limit exceeded: ${limit} requests per ${windowSeconds}s`
    );
  }

  await this.redis.zadd(redisKey, now, `${now}-${Math.random()}`); // record this request
  await this.redis.expire(redisKey, windowSeconds);
}
```

Store per-key rate limits on the key record itself (not just a global config) — a trusted partner key might get 10,000 req/min while a default key gets 100 req/min. Return `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `Retry-After` headers so callers can implement proper backoff.

**Q24. Scenario: "A fintech partner reports that API calls with their key are failing with 401 after working for months. How do you diagnose this?"**
A: A systematic debugging approach:

```
1. Is the key revoked?
   SELECT revoked_at, revocation_reason FROM api_keys WHERE id = ?
   → If revoked_at IS NOT NULL: identify who revoked it and why. Likely automated TTL
     expiry or an admin action. Issue a new key.

2. Is the key expired?
   SELECT expires_at FROM api_keys WHERE id = ?
   → If expires_at < NOW(): the key TTL lapsed. Check whether expiry warnings were
     sent (and ignored). Issue a replacement key.

3. Is the hash matching?
   → Ask the partner to send a test request. Log the raw presented key (temporarily,
     in a secure debug mode — never in production logs). Hash it manually and compare
     against the stored hash. Mismatch means the partner is sending a different key
     than they think (encoding issue, copy-paste truncation, environment variable
     misconfiguration — a key with trailing newline (\n) is a common culprit).

4. Is it a cache issue?
   → If the key was recently un-revoked or had scopes restored, is the old "revoked"
     cache entry still valid? Check Redis TTL: redis-cli TTL "apikey:<hash>"
     → Force invalidate: redis-cli DEL "apikey:<hash>"

5. Is it a scope issue?
   → The partner's key may have had scopes narrowed. Check whether the failing
     endpoint requires a scope the key no longer has. 401 vs 403 distinction matters:
     401 = authentication failed (key not found/revoked/expired);
     403 = authenticated but not authorized (scope check failed).
     Confirm your API returns the right status code for each case.

6. Is it an infrastructure issue?
   → Did a deployment change the HMAC secret used for hashing? If the secret
     changed without re-hashing all keys, every existing key suddenly hashes
     to a different value and matches nothing. This is a catastrophic misconfiguration
     — check your secret rotation runbook.
```

**Q25. Scenario: "You're designing the API key system for a new lending platform. Walk through all the decisions you'd make from generation to storage to scoping to lifecycle."**
A: End-to-end design walkthrough:

**Generation:**
- Format: `lapi_<43-char base64url>` for the loans API. Internal service keys: `svc_<43-char>`. Test environment keys: `lapi_test_<43-char>`.
- Source: `crypto.randomBytes(32)` — 256 bits of entropy.
- Never reuse, never derive from user data or timestamps.

**Storage:**
- Hash: HMAC-SHA256 with a server-side secret stored in AWS Secrets Manager. Hash is a `char(64)` column, B-tree indexed, `UNIQUE`.
- Stored metadata: `hash`, `prefix`, `last_four`, `name`, `owner_id`, `scopes` (text array), `created_at`, `expires_at`, `last_used_at`, `revoked_at`, `revocation_reason`, `rate_limit_per_minute`.
- State bucket: soft-delete only (`revoked_at` — never hard delete). Audit log table (`api_key_events`: created, scopes_changed, revoked, used — for compliance).
- Encryption: database at rest encrypted (RDS with KMS CMK). State file (if Terraform-managed) — SSE-KMS.

**Scoping:**
- Domain:action format: `loans:read`, `loans:write`, `loans:disburse`, `kyc:read`, `kyc:write`, `nach:read`, `nach:write`, `reports:read`, `webhooks:write`, `admin:*`.
- Scope confinement: created key scopes ⊆ creator's scopes.
- Immutable post-creation: scope changes require revoke + reissue. Simpler audit trail.
- NestJS guard: `@RequireScopes('loans:disburse')` on controller methods.

**Transmission:**
- `Authorization: Bearer lapi_xxx` header only. Reject if key appears in query string (return 400 with a helpful error: "API keys must be sent in the Authorization header, not as a query parameter").
- TLS 1.2+ enforced at load balancer. HTTP connections rejected (redirect or 400, not silently accepted).

**Lookup:**
- Hash presented key → Redis cache (60s TTL) → DB lookup by hash. Constant-time comparison.
- `last_used_at` update: fire-and-forget async write, never on the critical path.
- Rate limiting: per-key sliding window in Redis, limits stored on key record.

**Lifecycle:**
- Integration keys: 1-year TTL. Expiry warnings at 30d / 7d / 1d via email + webhook notification to the key owner.
- Service-to-service keys: 90-day TTL, automated rotation via AWS Secrets Manager Lambda.
- Rotation: grace-period overlap (30 minutes). Both keys valid during overlap.
- Revocation: immediate soft-revoke + Redis cache invalidation. Reason logged.
- Secret scanning: register `lapi_[A-Za-z0-9_-]{43}` with GitHub scanning. Revocation webhook auto-revokes leaked keys.
- Audit: all key events (creation, use, scope change, revocation) logged to a tamper-evident audit log table (append-only, no updates/deletes, shipped to SIEM). Required for PCI-DSS Req 10 and RBI access management controls.

## Quick Comparison Table

| Aspect | API Key | JWT | OAuth Access Token |
|---|---|---|---|
| Structure | Opaque random string | Signed JSON payload | Opaque or JWT |
| Verification | DB lookup (stateful) | Signature check (stateless) | DB lookup or signature |
| Expiry | Long-lived (months–years) | Short-lived (minutes–hours) | Short-lived (minutes–hours) |
| Revocation | Immediate (DB update) | Must wait for expiry (unless denylist) | Immediate (DB update) |
| Identity | Application / service | User (with claims) | User (delegated) |
| Scoping | Custom, stored in DB | Claims in token payload | OAuth scopes in token |
| Best for | M2M, B2B integrations | User auth in distributed systems | Delegated user access |
| Secret storage | DB (hashed) | Signing key (private key / secret) | DB (hashed) |
| Rotation complexity | Low (issue new, revoke old) | Low (new token on re-auth) | Handled by OAuth server |

| Hash choice | Use case | Why |
|---|---|---|
| SHA-256 / HMAC-SHA256 | High-entropy API keys (≥128 bits random) | Fast (1µs), brute force infeasible at this entropy |
| bcrypt (cost 12) | User passwords | Slow by design, defeats brute force on low-entropy inputs |
| Argon2id | User passwords (modern) | Memory-hard, defeats GPU cracking, OWASP recommended |
| MD5 / SHA-1 | Never for auth | Broken, collision-vulnerable |

**Tip for the interview:** At 5 YOE, API key questions go straight to: "why hash and not encrypt?" (Q5), "why SHA-256 and not bcrypt?" (Q6), "how do you do the lookup if you only store the hash?" (Q17), and "walk me through the full design." Have crisp answers for the hash-vs-encrypt distinction (reversibility = single point of failure vs. one-way = no decryption attack surface) and the bcrypt-vs-SHA-256 choice (bcrypt is for low-entropy inputs; 256-bit random keys are infeasible to brute-force regardless of hash speed). The timing attack question (Q7) always comes up — know `crypto.timingSafeEqual` cold. For the design question (Q25), lead with generation → show-once → hash+store → scope-checked lookup → lifecycle, and weave in the fintech-specific details (RBI audit trail, PCI-DSS soft revocation, AWS Secrets Manager for HMAC secret) — that depth is what separates a 5 YOE answer from a junior one.
