# Security: Session-Based vs. Token-Based Authentication — Interview Q&A (5 YOE Level)

---

## Section 1: The Core Distinction

**Q1. What is the fundamental architectural difference between session-based and token-based authentication, and what problem does each solve?**
A: The difference is about **where state lives**. Session-based auth is server-stateful — the server stores the session; the client holds only a reference (session ID). Token-based auth is client-stateful — the server stores nothing; the client holds the full credential (the token itself).

**Session-based (stateful):**
```
Client                          Server                        Store
  │── POST /login ────────────▶│                              │
  │                             │── create session ──────────▶│ sessions:{sid} = { userId, roles, ... }
  │◀─ Set-Cookie: sid=abc123 ──│                              │
  │                             │                              │
  │── GET /dashboard ──────────▶│                              │
  │   Cookie: sid=abc123        │── lookup session ───────────▶│
  │                             │◀─ { userId: 42, roles: [...] }│
  │◀─ 200 OK ──────────────────│                              │
```

**Token-based (stateless):**
```
Client                          Server
  │── POST /login ────────────▶│
  │                             │── sign JWT with private key
  │◀─ { token: "eyJ..." } ─────│
  │
  │── GET /dashboard ──────────▶│
  │   Authorization: Bearer eyJ │── verify signature (no DB lookup)
  │◀─ 200 OK ──────────────────│
```

Session-based solves the revocation problem — invalidating a session is instantaneous (delete the server-side record). Token-based solves the scale problem — no shared state means any server instance can verify a token independently, which is essential for distributed systems and microservices.

Neither is universally better. Choosing between them is a trade-off between **revocation control** (sessions win) and **horizontal scalability** (tokens win).

**Q2. What does "stateless" actually mean for token-based auth, and what are the hidden costs of that statelesness?**
A: "Stateless" means the server derives all information it needs from the token itself — it makes no network call or database lookup to validate a request. The token is self-describing: identity, roles, expiry, and issuer are all encoded inside it and cryptographically signed.

The hidden costs:

**Cost 1 — Revocation is approximate, not immediate:**
The server cannot unilaterally invalidate a token once issued. A token issued with a 15-minute TTL is valid for 15 minutes even if the user changes their password, gets suspended, or the token is stolen. True statelessness and true revocation are mutually exclusive.

**Cost 2 — Token size grows with claims:**
Each claim you embed (roles, permissions, tenant metadata, feature flags) increases token size. A JWT with 10 claims might be 500–800 bytes vs a 32-byte session ID. This adds up on every HTTP request, especially at high RPS.

**Cost 3 — You can't update in-flight claims:**
If a user's role changes mid-session (promoted to admin, suspended), the change is invisible until the token expires and they re-authenticate. With sessions, the server reads fresh data on every request. With tokens, the claims are frozen at issuance time.

**Cost 4 — Key management:**
Stateless verification requires all verifying services to trust the signing key. Rotating keys without dropping valid tokens requires JWKS endpoints, key versioning, and overlap periods — operationally more complex than rotating a session store password.

These costs are manageable — most production systems accept them — but calling JWTs "stateless" while maintaining a token blacklist, a refresh token table, or a tokenVersion counter is architecturally stateful, just in a different tier.

**Q3. Walk through the complete request lifecycle for each approach — what happens on login, on each subsequent request, and on logout?**
A:

**Session-based lifecycle:**

```
LOGIN:
1. Client sends credentials (username + password)
2. Server validates credentials against DB
3. Server creates session object: { userId, roles, createdAt, expiresAt }
4. Server persists session to store (Redis/DB): SET session:sid-xyz '{ ... }' EX 86400
5. Server generates a cryptographically random session ID (NOT a sequential integer)
6. Server sends: Set-Cookie: sessionId=sid-xyz; HttpOnly; Secure; SameSite=Strict; Path=/

SUBSEQUENT REQUEST:
1. Browser automatically attaches cookie: Cookie: sessionId=sid-xyz
2. Server reads sessionId from cookie
3. Server looks up session in Redis: GET session:sid-xyz → { userId: 42, roles: [...] }
4. If found and not expired → attach to req.session, proceed to handler
5. If not found / expired → 401, redirect to login

LOGOUT:
1. Client calls POST /auth/logout
2. Server deletes session from Redis: DEL session:sid-xyz
3. Session is immediately dead — any subsequent request with that sessionId gets 401
4. Server clears the cookie: Set-Cookie: sessionId=; Max-Age=0; HttpOnly; Secure
```

**Token-based lifecycle:**

```
LOGIN:
1. Client sends credentials
2. Server validates credentials against DB
3. Server generates signed JWT: { sub: userId, roles, exp, iss, jti }
4. Server generates opaque refresh token, stores hash in DB
5. Server returns: { accessToken: "eyJ...", refreshToken: "rand64hex..." }
6. Client stores tokens (memory, HttpOnly cookie, or — worse — localStorage)

SUBSEQUENT REQUEST:
1. Client sends: Authorization: Bearer eyJ...
2. Server extracts token from header
3. Server verifies JWT signature against public key (no network call)
4. Server checks exp, iss, aud claims
5. Optionally: checks jti against Redis blacklist (makes it partially stateful)
6. Attaches decoded payload to req.user, proceeds to handler

LOGOUT:
1. Client calls POST /auth/logout
2. Server adds jti to Redis blacklist with TTL = remaining token lifetime
   OR: server increments user's tokenVersion in DB
3. Client discards tokens from local storage / memory
4. Without blacklist: old token remains valid until exp (up to 15 min)
   With blacklist: token is immediately invalid on next request
```

The logout asymmetry is the sharpest practical difference. Session logout is atomic and guaranteed. Token logout without a blacklist is advisory — the client stops sending the token, but a stolen token remains valid. This matters acutely in fintech where regulatory requirements may mandate immediate session termination on password change or suspicious activity detection.

## Section 2: Session-Based Authentication Deep Dive

**Q4. How do you implement secure session management in a Node.js/Express application using Redis as the session store?**
A: `express-session` with `connect-redis` is the standard stack. The critical configuration options are security-sensitive:

```typescript
import session from 'express-session';
import RedisStore from 'connect-redis';
import { createClient } from 'redis';
import crypto from 'crypto';

const redisClient = createClient({
  url: process.env.REDIS_URL,
  socket: { tls: true },  // TLS to Redis in prod
});
await redisClient.connect();

app.use(session({
  store: new RedisStore({ client: redisClient, prefix: 'sess:' }),

  // Secret used to SIGN the session ID cookie (HMAC)
  // Not used to encrypt session data — that lives in Redis
  secret: process.env.SESSION_SECRET,  // 32+ random bytes; rotate via array
  // secret: [newSecret, oldSecret],   // Array: signs with [0], verifies with any

  name: '__Host-sid',  // __Host- prefix: forces Secure + top-level domain only
  resave: false,       // Don't re-save session on every request if unchanged
  saveUninitialized: false,  // Don't create session until something is stored
                             // Prevents session fixation on unauthenticated requests

  cookie: {
    httpOnly: true,
    secure: true,        // HTTPS only
    sameSite: 'strict',
    maxAge: 24 * 60 * 60 * 1000,  // 1 day in ms
    path: '/',
  },

  // Custom session ID generator — crypto random, not the default uid-safe
  genid: () => crypto.randomBytes(32).toString('hex'),
}));

// Login handler
app.post('/auth/login', async (req, res) => {
  const user = await validateCredentials(req.body.email, req.body.password);
  if (!user) return res.status(401).json({ message: 'Invalid credentials' });

  // Session fixation prevention — ALWAYS regenerate session ID after login
  // The session object carries over; only the ID changes
  req.session.regenerate((err) => {
    if (err) return res.status(500).json({ message: 'Session error' });

    req.session.userId = user.id;
    req.session.roles  = user.roles;

    req.session.save((err) => {
      if (err) return res.status(500).json({ message: 'Session save error' });
      res.json({ message: 'Logged in' });
    });
  });
});

// Logout handler
app.post('/auth/logout', (req, res) => {
  req.session.destroy((err) => {
    if (err) return res.status(500).json({ message: 'Logout error' });
    res.clearCookie('__Host-sid');
    res.json({ message: 'Logged out' });
  });
});
```

`req.session.regenerate()` on login is non-negotiable. Without it, a session fixation attack works: the attacker plants a known session ID in the victim's browser (via XSS or an open redirect before login), the victim logs in, and the attacker now has a valid session ID for an authenticated session they never authenticated. Regenerating the ID after login severs that link.

**Q5. What is session fixation, and how does it differ from session hijacking?**
A: Both attacks result in an attacker using a valid session they shouldn't possess, but they operate at different stages:

**Session Fixation — before authentication:**
```
1. Attacker obtains any valid session ID (often from a login page
   that creates sessions for unauthenticated visitors)
2. Attacker plants that session ID in victim's browser:
   - Via URL parameter: https://myapp.com/login?sessionId=ATTACKER_KNOWN_ID
   - Via XSS: document.cookie = 'sessionId=ATTACKER_KNOWN_ID'
3. Victim logs in using the planted session ID
4. Server authenticates the victim but keeps the same session ID
5. Attacker already knows the session ID → accesses authenticated session

Mitigation: req.session.regenerate() on every successful login.
```

**Session Hijacking — after authentication:**
```
1. Victim is already logged in with a legitimate session ID
2. Attacker steals the session ID via:
   - Network interception (non-HTTPS)
   - XSS: fetch cookie via document.cookie (if not HttpOnly)
   - MITM on non-secure Wi-Fi
   - Server-side log leakage (session ID in access logs)
3. Attacker uses the stolen session ID to impersonate the victim

Mitigation: HttpOnly + Secure + SameSite cookies; HTTPS everywhere;
            bind session to IP or User-Agent (with caveats);
            short session TTL with re-authentication for sensitive actions.
```

A subtle but important point: binding sessions to IP address prevents hijacking from a different IP, but breaks legitimate users on mobile networks where IP changes frequently (CGNAT, handoffs). A pragmatic middle ground: bind to User-Agent string (catches most simple hijacking attempts) and flag IP changes as suspicious events for monitoring without immediately invalidating the session.

**Q6. How does a Redis-backed session store handle session expiry, and what happens if Redis goes down?**
A: Redis handles expiry natively via TTL. When `connect-redis` stores a session, it sets the key with an EX (expiry) value matching `cookie.maxAge`. Redis automatically deletes the key after TTL expires — no background cleanup job needed:

```
SET sess:abc123 '{"userId":42}' EX 86400
# After 86400 seconds, Redis deletes the key automatically
# Next request with sessionId=abc123 → Redis returns nil → 401
```

**What happens if Redis goes down:**

```
                Redis Down
                    │
GET /api/resource ──▶ app.use(session(...))
                       │
                       └── RedisStore.get('sess:abc123')
                               │
                               └── Connection refused / timeout
                                       │
                                       ▼
                               Error propagated to session middleware
                               → req.session = undefined
                               → Subsequent code reading req.session.userId throws
                               → 500 Internal Server Error for all authenticated requests
```

Redis downtime equals **total application outage** for session-based auth. This is the single biggest operational risk of server-side sessions. Mitigations:

```typescript
// 1. Redis Sentinel / Redis Cluster for HA — automatic failover
const redisClient = createClient({
  sentinels: [
    { host: 'sentinel-1', port: 26379 },
    { host: 'sentinel-2', port: 26379 },
  ],
  name: 'mymaster',
});

// 2. Fallback to graceful degradation — redirect to login rather than 500
store.on('error', (err) => {
  logger.error('Session store error', { err });
  // Alert ops; if persistent, circuit-break and serve maintenance page
});

// 3. Read-through fallback — if Redis is down, fall back to a local memory store
//    (loses cross-instance session sharing; accept for short Redis blips)
```

Token-based auth has no equivalent single point of failure — a server can verify a JWT with its in-memory public key even if every external service is down. This resilience is a genuine operational advantage in high-availability requirements.

**Q7. How do you handle concurrent requests in session-based auth — what is the session race condition and how do you prevent it?**
A: When a client sends multiple concurrent requests (parallel API calls from a SPA), they all read and write the same session object in Redis. If two requests modify different session fields simultaneously, one write may overwrite the other:

```
Request A reads session:  { userId: 42, cart: ['item1'] }
Request B reads session:  { userId: 42, cart: ['item1'] }
Request A modifies cart:  { userId: 42, cart: ['item1', 'item2'] } → writes to Redis
Request B modifies cart:  { userId: 42, cart: ['item1', 'item3'] } → writes to Redis (overwrites A)
Result in Redis:          { userId: 42, cart: ['item1', 'item3'] }  ← item2 lost
```

This is the classic last-write-wins race condition. Mitigations:

```typescript
// Option 1 — resave: false + only write session fields that can't conflict
// Authentication data (userId, roles) is written once at login and read-only thereafter
// Never write volatile, request-specific data to the session

// Option 2 — Redis optimistic locking with WATCH/MULTI/EXEC
// connect-redis doesn't support this natively; build a custom store

// Option 3 — Treat session as read-only after login; use separate
//            per-user Redis keys for mutable state
app.use(async (req, res, next) => {
  if (req.session.userId) {
    // Read fresh user data from Redis/DB on every request
    // Don't store volatile data in the session object
    req.user = await userService.findById(req.session.userId);
  }
  next();
});
```

In practice: store only immutable identity data in the session (userId, tenantId, roles at login time). Never use the session as a general-purpose cache for volatile data. This eliminates the race condition entirely — reads are safe; only one write ever happens (at login, via `regenerate`).

## Section 3: Token-Based Authentication Deep Dive

**Q8. What is the difference between opaque tokens and structured tokens (JWTs), and when would you choose each?**
A: The difference is whether the token is self-describing or requires a lookup:

**Opaque tokens** — a random string (e.g., `a3f8b2...`) that has no intrinsic meaning. The server must look it up in a store to retrieve the associated claims:

```typescript
// Opaque token issuance
const token = crypto.randomBytes(64).toString('hex');
await redis.set(`token:${token}`, JSON.stringify({ userId, roles }), 'EX', 3600);

// Opaque token validation — requires network call
const data = await redis.get(`token:${req.token}`);
if (!data) throw new UnauthorizedException();
const { userId, roles } = JSON.parse(data);
```

**Structured tokens (JWTs)** — a base64url-encoded payload that contains claims directly, signed to prevent tampering:

```typescript
// JWT validation — no network call
const payload = jwt.verify(token, publicKey, { algorithms: ['RS256'] });
const { sub: userId, roles } = payload;
```

| | Opaque Token | JWT |
|---|---|---|
| **Validation cost** | Redis/DB lookup per request | Cryptographic verify (CPU, no I/O) |
| **Revocation** | Instant — delete the Redis key | Approximate — wait for expiry or blacklist |
| **Payload visibility** | Payload hidden (server-side only) | Payload visible to anyone (base64 decoded) |
| **Token size** | Small (32–64 bytes) | Medium (200–2000 bytes depending on claims) |
| **Distributed verification** | Requires all services to reach the token store | Any service with the public key verifies locally |
| **Best for** | OAuth2 access tokens (single resource server), high-security contexts | Microservices, federated identity, B2B APIs |

In OAuth2, access tokens issued to third-party clients are typically opaque — the client doesn't need to read the payload, and keeping claims server-side limits exposure. JWTs are appropriate when multiple services need to independently verify and read claims without a shared session store — the microservices pattern.

**Q9. What is JWT token inflation, and how do you prevent it from becoming a performance problem?**
A: Token inflation is when JWTs grow large because too many claims are embedded — roles, permissions, feature flags, tenant config, user preferences, entitlements. Each claim is base64-encoded into the JWT payload and sent on every HTTP request:

```
# Minimal JWT payload (healthy)
{
  "sub": "user-uuid",
  "roles": ["agent"],
  "tenantId": "tenant-uuid",
  "exp": 1723456789,
  "iss": "https://auth.myorg.internal"
}
# → ~250 bytes

# Inflated JWT payload (problematic)
{
  "sub": "user-uuid",
  "roles": ["agent", "viewer", "loan-approver"],
  "tenantId": "tenant-uuid",
  "permissions": ["loans:read", "loans:write", "payments:read", ...18 more],
  "featureFlags": { "newDashboard": true, "betaReports": false, ...12 more },
  "tenantConfig": { "maxLoanAmount": 500000, "currency": "INR", ... },
  "exp": 1723456789,
  "iss": "https://auth.myorg.internal"
}
# → ~1800 bytes
```

At 1000 RPS, an extra 1500 bytes per request is 1.5 MB/s of unnecessary bandwidth on every internal service's ingress. It also increases TLS payload size, Base64 encoding/decoding cost, and HTTP header parsing overhead.

Prevention strategies:

```typescript
// Strategy 1 — Thin JWT + lazy enrichment at the gateway
// JWT carries only: sub, roles, tenantId, exp, iss
// Gateway fetches full permissions/config from a cache-aside layer (Redis TTL: 5 min)
// Injects enriched claims as trusted internal headers before forwarding

// Strategy 2 — Lazy permission resolution in the service
// Don't embed fine-grained permissions in the JWT
// Fetch from a permissions service/cache on first request, memoize in-process
const permissions = await this.permissionsCache.get(userId)
  ?? await this.permissionsService.fetch(userId);

// Strategy 3 — Phantom claims: embed only what changes infrequently
// roles (changes rarely) → in JWT
// specific permissions (may change on ACL edit) → fetch on demand
// featureFlags (changes frequently) → never in JWT, fetch from config service

// Strategy 4 — JWT compression (rarely necessary but available)
// Use jwt-compress library to deflate the payload before signing
// Reduces a 1800-byte JWT to ~900 bytes
// Adds CPU overhead; use only if bandwidth is genuinely constrained
```

The rule of thumb: embed claims that are **stable for the token's lifetime** and **needed on most requests**. Everything else should be fetched lazily.

**Q10. What is the sliding session problem with JWTs, and how do you simulate sliding expiry without re-issuing tokens on every request?**
A: Sessions slide — their expiry extends each time the user is active. Redis does this natively: every read can reset the TTL (`EXPIRE key 86400`). JWTs cannot slide — their `exp` claim is frozen at issuance. A 15-minute access token expires 15 minutes after login even if the user is actively using the app every second.

The naive fix — re-issue a new JWT on every request — is expensive (signing is a CPU operation) and creates race conditions with concurrent requests.

Practical patterns:

```typescript
// Pattern 1 — Refresh before expiry (client-driven sliding)
// Client tracks exp, refreshes when (exp - now) < threshold
// Simulates sliding from the client's perspective

// In an Axios interceptor:
axiosInstance.interceptors.request.use(async (config) => {
  const token = getAccessToken();
  const payload = decodeJWT(token);
  const expiresIn = payload.exp - Math.floor(Date.now() / 1000);

  if (expiresIn < 120) {  // Refresh if < 2 minutes remaining
    const newToken = await refreshAccessToken();
    setAccessToken(newToken);
    config.headers.Authorization = `Bearer ${newToken}`;
  }
  return config;
});

// Pattern 2 — Server-driven refresh hint
// Server includes a Refresh-After header when token is near expiry
// Client uses this hint to proactively refresh
app.use((req, res, next) => {
  if (req.user) {
    const expiresIn = req.user.exp - Math.floor(Date.now() / 1000);
    if (expiresIn < 300) {  // Token expires in < 5 min
      res.setHeader('X-Token-Expiring', 'true');
    }
  }
  next();
});

// Pattern 3 — Short-lived access token + long-lived refresh token (standard)
// access token:  15 min TTL → user re-fetches every 15 min automatically
// refresh token: 30 days TTL, HttpOnly cookie, sent only to /auth/refresh
// Combined effect: user stays "logged in" for 30 days as long as active
//                  but the blast radius of a stolen access token is 15 min max
```

Pattern 3 is the industry standard and is what OAuth2 was designed around. The access token's short TTL limits exposure; the refresh token's long TTL provides the sliding experience. The refresh token is opaque (stored in DB), can be revoked instantly, and is only ever sent to one endpoint — reducing its attack surface dramatically compared to the access token sent on every request.

## Section 4: CSRF, XSS, and the Storage Security Triangle

**Q11. How does CSRF work, and which authentication mechanism is inherently vulnerable — sessions or tokens?**
A: CSRF (Cross-Site Request Forgery) exploits the browser's automatic cookie attachment. When any request is made to `mybank.com`, the browser automatically includes `mybank.com`'s cookies — regardless of which site initiated the request. An attacker on `evil.com` can trigger a state-changing request to `mybank.com` on behalf of a logged-in victim:

```html
<!-- evil.com embeds this in a page the victim visits -->
<form action="https://mybank.com/api/transfer" method="POST" id="csrf-form">
  <input type="hidden" name="to"     value="attacker-account" />
  <input type="hidden" name="amount" value="100000" />
</form>
<script>document.getElementById('csrf-form').submit();</script>

<!-- Browser sends:
  POST /api/transfer
  Cookie: sessionId=victim-session-id  ← attached automatically
  to=attacker-account&amount=100000    ← attacker-controlled body
-->
```

**Session-based auth + cookies → vulnerable to CSRF by default.**
**Token-based auth + Authorization header → immune to CSRF by construction.**

The CSRF immunity of bearer tokens comes from the fact that the browser never automatically attaches the `Authorization` header — only JavaScript can set it. Since the attacker's page on `evil.com` can't read cookies from `mybank.com` (same-origin policy), it can't steal and inject the bearer token either.

However: if you store JWTs in **cookies** (the secure storage recommendation from Q10 in the AuthN/AuthZ guide), you re-introduce CSRF vulnerability. You must then add CSRF protection:

```typescript
// Double-submit cookie CSRF protection for JWT-in-cookie setups
// 1. On login, also set a non-HttpOnly CSRF token cookie (JavaScript CAN read it)
res.cookie('csrf-token', csrfToken, {
  httpOnly: false,  // JS must be able to read this
  secure: true,
  sameSite: 'strict',
});

// 2. Client reads the CSRF token via JS and sends it in a header
// axios.defaults.headers.common['X-CSRF-Token'] = getCookie('csrf-token');

// 3. Server validates that header matches the cookie
app.use((req, res, next) => {
  if (['POST', 'PUT', 'PATCH', 'DELETE'].includes(req.method)) {
    const cookieCsrf = req.cookies['csrf-token'];
    const headerCsrf = req.headers['x-csrf-token'];
    if (!cookieCsrf || cookieCsrf !== headerCsrf) {
      return res.status(403).json({ message: 'CSRF validation failed' });
    }
  }
  next();
});
```

`SameSite=Strict` on the session/JWT cookie alone is sufficient CSRF protection for most applications — it prevents the cookie from being sent on any cross-site request. But `SameSite=Strict` breaks OAuth2 redirect flows and some legitimate cross-site navigations. `SameSite=Lax` (the browser default) is safer than nothing and allows top-level navigations but blocks sub-resource requests — a good pragmatic middle ground.

**Q12. If JWTs stored in localStorage are vulnerable to XSS, and JWTs stored in cookies are vulnerable to CSRF, what is the recommended storage strategy?**
A: The attack matrix:

```
Storage location     │ XSS vulnerability │ CSRF vulnerability
─────────────────────┼───────────────────┼────────────────────
localStorage         │ HIGH — any JS can │ NONE — not auto-sent
                     │ read tokens       │ by browser
─────────────────────┼───────────────────┼────────────────────
SessionStorage       │ HIGH — same as    │ NONE
                     │ localStorage      │
─────────────────────┼───────────────────┼────────────────────
HttpOnly Cookie      │ NONE — JS cannot  │ MEDIUM — mitigated
                     │ read HttpOnly     │ by SameSite=Strict
─────────────────────┼───────────────────┼────────────────────
In-memory (JS var)   │ LOW — survives    │ NONE
                     │ only current tab  │
```

The recommended strategy for high-security applications:

```
Access token:  in-memory (JavaScript variable or React state)
               → short TTL (15 min) limits damage window
               → lost on tab close / page refresh (feature, not bug)
               → immune to both XSS theft (no persistent storage)
                 and CSRF (Authorization header, not cookie)

Refresh token: HttpOnly, Secure, SameSite=Strict cookie
               → JavaScript cannot read it → XSS cannot steal it
               → SameSite=Strict → CSRF cannot trigger refresh
               → sent only to /auth/refresh endpoint (path-scoped cookie)
               → long TTL (30 days) but only ever touches one endpoint
```

```typescript
// On login: return access token in body, set refresh token as HttpOnly cookie
async login(credentials: LoginDto, res: Response) {
  const { user, accessToken, refreshToken } = await this.authService.login(credentials);

  // Refresh token: HttpOnly cookie, scoped to /auth/refresh only
  res.cookie('refresh_token', refreshToken, {
    httpOnly: true,
    secure: true,
    sameSite: 'strict',
    path: '/auth/refresh',  // Cookie only sent to this exact path
    maxAge: 30 * 24 * 60 * 60 * 1000,
  });

  // Access token: returned in body, stored in-memory by the client
  return res.json({ accessToken, expiresIn: 900 });
}

// On page refresh: client silently calls /auth/refresh to get a new access token
// The refresh token cookie is sent automatically (same-origin, correct path)
// Client stores the new access token in-memory
async refresh(req: Request, res: Response) {
  const refreshToken = req.cookies['refresh_token'];
  const { accessToken } = await this.authService.refresh(refreshToken);
  return res.json({ accessToken, expiresIn: 900 });
}
```

This pattern is called the **BFF (Backend For Frontend)** token security model — the refresh token never touches JavaScript, the access token never touches persistent storage. It combines the CSRF-immunity of bearer tokens with the XSS-immunity of HttpOnly cookies.

## Section 5: Scalability, Distributed Systems, and Migration

**Q13. How do sticky sessions work, and why are they considered an anti-pattern in horizontally scaled deployments?**
A: Sticky sessions (session affinity) are a load balancer configuration that routes all requests from a given client to the same backend server instance. This works around the problem that server-side session state is local to a process — if the session lives in memory on server-1, requests routed to server-2 won't find it:

```
Without sticky sessions (problem):
  Request 1 → Server 1 (creates session, stores in local memory)
  Request 2 → Server 2 (no session found → 401)

With sticky sessions (workaround):
  Request 1 → Server 1 (creates session in local memory)
  Request 2 → Server 1 (load balancer routes to same server → session found)
  Request 3 → Server 1 (same)
```

Why they're an anti-pattern:

```
1. Uneven load distribution — one server accumulates all sessions for heavy users
   while others sit idle. The load balancer's job is to distribute load evenly;
   sticky sessions work against that.

2. Zero-tolerance for server failure — if Server 1 goes down, all its sessions
   are lost. Users are logged out abruptly. No graceful failover.

3. Deployment friction — rolling deploys drain sessions from the server being
   restarted. Blue/green deploys require session migration. Zero-downtime
   deploys become complex.

4. Auto-scaling complications — spinning up a new server instance doesn't help
   the overloaded server if all its clients are stuck to it.
```

The correct solution is **centralized session storage** — move sessions out of process memory into Redis. All server instances read from and write to the same Redis cluster. The load balancer becomes session-agnostic: any instance handles any request:

```
                ┌──────────┐
                │  Redis   │  ← shared session store
                │ Cluster  │
                └─────┬────┘
                      │ all servers read/write here
         ┌────────────┼────────────┐
         ▼            ▼            ▼
    ┌─────────┐  ┌─────────┐  ┌─────────┐
    │Server 1 │  │Server 2 │  │Server 3 │
    └─────────┘  └─────────┘  └─────────┘
         ▲            ▲            ▲
         └────────────┼────────────┘
                      │ round-robin, any server
                 Load Balancer
```

This makes server instances truly stateless at the application layer while keeping session state in a dedicated, HA-configured persistence layer.

**Q14. How do you migrate a session-based authentication system to token-based without a big-bang cutover?**
A: Migrating auth is high-risk — a mistake logs out every user simultaneously or creates security gaps. A phased approach with a compatibility bridge:

**Phase 1 — Dual-issue: issue both a session cookie and a JWT on login:**
```typescript
async login(credentials, res) {
  const user = await this.validateCredentials(credentials);

  // Existing: create session
  await new Promise(resolve => req.session.regenerate(resolve));
  req.session.userId = user.id;

  // New: also issue JWT
  const accessToken = this.jwtService.sign({ sub: user.id, roles: user.roles });

  res.json({ accessToken });  // New clients use this
  // Session cookie is also set via express-session middleware
}
```

**Phase 2 — Dual-validation middleware: accept both session and bearer token:**
```typescript
async function dualAuthMiddleware(req, res, next) {
  // Try JWT first (new clients)
  const bearerToken = extractBearerToken(req);
  if (bearerToken) {
    try {
      req.user = await validateJWT(bearerToken);
      return next();
    } catch (e) {
      // JWT invalid — fall through to session check
    }
  }

  // Fall back to session (existing clients)
  if (req.session?.userId) {
    req.user = await userService.findById(req.session.userId);
    return next();
  }

  return res.status(401).json({ message: 'Unauthenticated' });
}
```

**Phase 3 — Migrate clients: deploy updated frontend/mobile apps that use JWTs. Monitor session vs. token usage ratios in metrics.**

**Phase 4 — Deprecate session issuance: stop creating new sessions on login. Existing sessions expire naturally (no forced logout).**

**Phase 5 — Remove session validation: once session traffic drops to near zero (metrics-driven, not time-driven), remove the session fallback path.**

```typescript
// Metrics to track during migration
authMethod.increment({ method: 'jwt' });    // or 'session'
// Watch: session ratio should trend to 0 before Phase 5
```

The phased approach avoids a big-bang cutover, keeps old clients working through natural expiry, and gives you a rollback path at every stage — if JWT adoption stalls, you haven't removed session support yet.

**Q15. How does token-based auth behave differently from session-based auth when a user's permissions change mid-session?**
A: This is one of the most important practical differences between the two approaches:

**Session-based — real-time permission propagation:**
```typescript
// Middleware reads fresh data from DB/cache on every request
async sessionAuthMiddleware(req, res, next) {
  if (!req.session?.userId) return res.status(401).end();

  // Fresh read every request — always reflects current DB state
  const user = await userService.findById(req.session.userId);

  if (!user || user.status !== 'ACTIVE') {
    req.session.destroy();
    return res.status(401).json({ message: 'Account suspended' });
  }

  req.user = user; // Always current roles, always current status
  next();
}

// If an admin suspends userId=42 in the DB:
// → Next request from that user hits this middleware
// → DB returns status='SUSPENDED'
// → User is immediately rejected
// → Effective suspension latency: 0 ms (next request)
```

**Token-based — permission propagation is delayed by TTL:**
```typescript
// JWT payload is frozen at issuance
{
  "sub": "42",
  "roles": ["agent"],       // Frozen at login time
  "status": "ACTIVE",       // Frozen at login time
  "exp": 1723456789         // 15 min from now
}

// If admin suspends userId=42:
// → User's next requests continue to succeed for up to 15 min
// → JWT is valid, signature checks out, status claim says ACTIVE
// → Service has no way to know the DB says SUSPENDED
// → Effective suspension latency: up to TTL (15 min)
```

Closing the gap for token-based auth — for high-security status changes (suspend, role revoke, compromise flag):

```typescript
// Approach 1: Status check against Redis on every request (partial statefulness)
async jwtAuthMiddleware(req, res, next) {
  const payload = verifyJWT(req.token);

  // One fast Redis lookup for revocation/suspension
  const isRevoked = await redis.get(`revoked:${payload.sub}`);
  if (isRevoked) return res.status(401).json({ message: 'Account suspended' });

  req.user = payload;
  next();
}

// On admin suspension:
await redis.set(`revoked:${userId}`, '1', 'EX', 86400); // Outlives any token TTL

// Approach 2: Short TTL (5 min) for high-sensitivity services
// Accept up to 5 min of stale permissions
// Most payment and lending APIs use this — 5 min window is acceptable operationally

// Approach 3: Webhook/event-driven invalidation
// Auth service emits a UserSuspended event
// Downstream services update their local revocation cache
// Converges faster than TTL-based expiry
```

In a regulated fintech context — RBI, PCI-DSS — immediate suspension capability may be a compliance requirement. Pure stateless JWTs don't satisfy it. The pragmatic answer is a hybrid: JWT for normal operation (no lookup), Redis revocation check for the high-sensitivity operations (account suspension, fraud flag, admin-initiated logout).

## Section 6: Advanced Patterns and Failure Scenarios

**Q16. What is the difference between server-side session invalidation and client-side token deletion on logout, and why does it matter for security?**
A: The difference is whether logout is **guaranteed** or **advisory**:

**Session logout — guaranteed:**
```typescript
app.post('/auth/logout', (req, res) => {
  const sessionId = req.cookies['sessionId'];

  // Delete from Redis — happens server-side, under server control
  req.session.destroy();
  // From this moment, sessionId is invalid.
  // Even if an attacker has the cookie value, it maps to nothing in Redis.
  // The server is the arbiter of validity.

  res.clearCookie('sessionId');
  res.json({ message: 'Logged out' });
});
```

**Token logout — advisory (without blacklist):**
```typescript
app.post('/auth/logout', (req, res) => {
  // There is nothing server-side to delete for a stateless JWT
  // The "logout" is only the client discarding its copy of the token
  res.json({ message: 'Logged out' });
  // If the client doesn't discard the token (bug, malicious client,
  // attacker who already copied it), the token remains valid until exp.
});
```

Why it matters in practice — two real scenarios:

**Scenario A — Stolen laptop:**
- Session: user logs out remotely via "log out all devices" → all sessions deleted from Redis → attacker opening the laptop finds invalid sessions.
- Token (no blacklist): user changes password → old access tokens remain valid for up to 15 min → attacker who has the token can continue acting as the user.

**Scenario B — Compromised mobile app:**
- Session: security team revokes the session server-side → app is immediately logged out on next request.
- Token (no blacklist): security team has no mechanism to revoke — must wait for token TTL to expire.

The production pattern that satisfies both security and scalability:

```typescript
// Logout with immediate revocation via jti blacklist
app.post('/auth/logout', async (req, res) => {
  const payload = req.user; // Already verified by auth middleware

  // Add jti to Redis blacklist with TTL = remaining token lifetime
  const remainingTTL = payload.exp - Math.floor(Date.now() / 1000);
  if (remainingTTL > 0) {
    await redis.set(`blacklist:${payload.jti}`, '1', 'EX', remainingTTL);
  }

  // Clear refresh token cookie
  res.clearCookie('refresh_token', { path: '/auth/refresh' });
  res.json({ message: 'Logged out' });
});

// "Log out all devices" — revoke all refresh tokens for user
app.post('/auth/logout-all', async (req, res) => {
  await refreshTokenRepo.revokeAll({ userId: req.user.sub });
  // Also increment tokenVersion to invalidate all current access tokens
  await userRepo.incrementTokenVersion(req.user.sub);
  res.json({ message: 'All sessions terminated' });
});
```

**Q17. How do you implement "remember me" functionality differently in session-based vs. token-based systems?**
A: "Remember me" extends authentication persistence beyond the browser session:

**Session-based "remember me":**
```typescript
app.post('/auth/login', async (req, res) => {
  const { email, password, rememberMe } = req.body;
  const user = await validateCredentials(email, password);

  await new Promise(resolve => req.session.regenerate(resolve));
  req.session.userId = user.id;

  if (rememberMe) {
    // Extend cookie and session TTL from session-only to 30 days
    req.session.cookie.maxAge = 30 * 24 * 60 * 60 * 1000;
    // Also update the Redis key TTL
    await redis.expire(`sess:${req.sessionID}`, 30 * 24 * 60);
  } else {
    // Session cookie — expires when browser closes
    req.session.cookie.expires = false; // session cookie
  }

  res.json({ message: 'Logged in' });
});
```

**Token-based "remember me":**
```typescript
async login(credentials, rememberMe: boolean, res: Response) {
  const user = await this.validateCredentials(credentials);

  // Access token TTL is always short regardless of rememberMe
  const accessToken = this.jwtService.sign(
    { sub: user.id, roles: user.roles },
    { expiresIn: '15m' }
  );

  // Refresh token TTL varies by rememberMe
  const refreshTokenTTL = rememberMe ? '30d' : '1d';
  const refreshToken = await this.generateRefreshToken(user.id, refreshTokenTTL);

  res.cookie('refresh_token', refreshToken, {
    httpOnly: true,
    secure: true,
    sameSite: 'strict',
    path: '/auth/refresh',
    maxAge: rememberMe
      ? 30 * 24 * 60 * 60 * 1000   // 30 days
      : 24 * 60 * 60 * 1000,        // 1 day
  });

  return { accessToken };
}
```

Key principle for both: "remember me" should extend the **refresh token / session TTL**, never the **access credential TTL**. A 30-day access token is a 30-day open window for attackers. A 30-day refresh token that can be revoked immediately and only touches one endpoint is a manageable risk.

**Q18. Scenario: "Your fintech platform uses session-based auth with Redis. During a traffic spike, Redis latency spikes to 500ms. What is the impact on authentication and what are your mitigation options?"**
A: Every authenticated request makes a synchronous Redis read (session lookup). At 500ms Redis latency:

```
Impact:
  Baseline API response time: ~50ms
  With 500ms Redis latency:   ~550ms (session lookup blocks the request)
  P99 response time:          likely > 1s (timeouts, retries)
  User-visible impact:        severe slowdown on every authenticated page load

At scale:
  1000 RPS × 500ms blocked per request = 500 concurrent connections
  waiting on Redis. Thread pool / event loop saturation likely.
  Result: cascading 503s even though the application server is healthy.
```

Mitigation options, in order of implementation complexity:

```typescript
// Option 1 — In-process session cache (fastest to implement)
// Cache the session lookup result in-process for N seconds
// Trade-off: stale session data for N seconds; revocations delayed

const sessionCache = new Map<string, { data: Session; cachedAt: number }>();
const SESSION_CACHE_TTL = 5000; // 5 seconds in ms

async function getSession(sessionId: string): Promise<Session> {
  const cached = sessionCache.get(sessionId);
  if (cached && Date.now() - cached.cachedAt < SESSION_CACHE_TTL) {
    return cached.data;
  }
  const session = await redis.get(`sess:${sessionId}`);
  sessionCache.set(sessionId, { data: session, cachedAt: Date.now() });
  return session;
}

// Option 2 — Redis read replicas
// Route session reads to read replicas; only writes hit the primary
// Redis Sentinel or Cluster handles this at the infrastructure level
// No application code change needed

// Option 3 — Redis connection pooling + pipelining
// Ensure connection pool is large enough to avoid connection contention
const redisClient = createClient({
  socket: { connectTimeout: 200 },  // Fail fast; don't wait 500ms per request
});

// Option 4 — Circuit breaker around Redis
// If Redis P99 latency > threshold, open the circuit:
// - Reject new requests with 503 (honest about degradation)
// - OR: fall back to short-lived signed cookie validation (temporary stateful-to-stateless degradation)

// Option 5 — Hybrid: migrate high-RPS routes to JWT
// Health check endpoints, read-heavy listing APIs: JWT (no Redis)
// Sensitive mutations (payments, profile changes): keep session (Redis)
```

The deeper architectural lesson: session-based auth couples authentication latency to your session store's latency. Token-based auth couples authentication latency to CPU (JWT verification is ~1ms even on a loaded server). For latency-sensitive, high-RPS fintech APIs, this difference matters operationally — not in theory, but at 3am during an incident.

## Quick Comparison Table

| Aspect | Session-Based | Token-Based (JWT) |
|---|---|---|
| **State location** | Server (Redis/DB) | Client (token payload) |
| **Validation cost** | Redis network call per request | CPU crypto verify (~1ms, no I/O) |
| **Revocation** | Instant (delete server-side) | Delayed (TTL) or stateful blacklist |
| **Horizontal scaling** | Requires centralized session store | Any instance verifies independently |
| **CSRF vulnerability** | Yes (mitigate: SameSite, CSRF token) | No (if using Authorization header) |
| **XSS vulnerability** | No (HttpOnly cookie) | Yes if localStorage; No if HttpOnly cookie |
| **Permission updates** | Real-time (fresh DB read per request) | Delayed until token expiry |
| **Single point of failure** | Redis availability | Key management / JWKS availability |
| **"Log out all devices"** | Trivial (delete all sessions by userId) | Requires tokenVersion or jti revocation |
| **Token size** | 32-byte session ID in cookie | 200–2000 bytes depending on claims |
| **Best for** | Monolith, full-stack, B2C web apps | Microservices, SPAs, mobile, B2B APIs |
| **Sliding expiry** | Native (EXPIRE key on each read) | Simulated via refresh token rotation |
| **"Remember me"** | Extend session + cookie TTL | Extend refresh token TTL only |
| **Microservices** | Shared Redis required across services | Any service verifies with public key |
| **Compliance (instant revoke)** | Native | Requires Redis revocation check |
