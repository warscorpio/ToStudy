# Security: OpenID Connect (OIDC) — Interview Q&A (5 YOE Level)

---

## Section 1: OIDC Fundamentals

**Q1. What is OpenID Connect, and why does OAuth 2.0 alone not provide authentication?**
A: OpenID Connect (OIDC) is an identity layer built on top of OAuth 2.0 (RFC 6749) that adds standardized authentication. OAuth 2.0 handles *authorization* — it grants a client permission to access resources — but it has no standard way to represent *who the user is*.

The distinction matters:

```
OAuth 2.0 alone:
  Client receives access_token
  access_token = "this client may perform these scopes"
  access_token says nothing reliable about identity — it has no standard claims format

The /userinfo anti-pattern (OAuth-only "login"):
  Some developers call /userinfo with the access_token to get user data.
  Problem: the access_token was not issued FOR this client specifically.
  An attacker who steals a token from Client A can present it to Client B.
  Client B calls /userinfo, gets a valid user, and grants access — but the token wasn't
  intended for Client B. This is the "confused deputy" / audience problem.

OIDC adds:
  id_token — a signed JWT issued specifically for the client (aud = client_id)
  Standard identity claims: sub, email, name, iss, aud, exp, iat, nonce
  The id_token is cryptographically bound to the client — it cannot be replayed
  by a different client without failing the audience check.
```

OIDC answers: "Who authenticated, when, at which identity provider, and is this assertion meant for me?" OAuth 2.0 alone answers none of those questions in a standardized, secure way.

**Q2. What is the relationship between OIDC and OAuth 2.0? Is OIDC a separate protocol?**
A: OIDC is not a separate protocol — it is a profile of OAuth 2.0. It reuses the OAuth 2.0 Authorization Code flow (and optionally Implicit or Hybrid flows, though Authorization Code + PKCE is the correct modern choice), and adds:

```
1. The openid scope — signals to the authorization server that identity is requested.
   Without openid in the scope list, the server issues only OAuth 2.0 tokens.
   With openid, the server additionally issues an id_token.

2. The ID token — a JWT alongside the access_token in the token response.

3. Standardized claim names — sub (subject identifier), iss (issuer), aud (audience),
   exp (expiry), iat (issued-at), nonce, email, name, given_name, locale, etc.

4. The UserInfo endpoint — a protected resource that returns claims not included
   in the id_token (for size reasons), accessed using the access_token.

5. The Discovery endpoint — /.well-known/openid-configuration — a JSON document
   describing the provider's capabilities, endpoints, and signing keys.
```

```
OAuth 2.0 Authorization Code flow:
  GET /authorize?response_type=code&client_id=...&scope=read:profile
  → Receive code
  → POST /token { code, ... }
  → { access_token, token_type, expires_in, refresh_token }

OIDC Authorization Code flow (identical flow, different scope + response):
  GET /authorize?response_type=code&client_id=...&scope=openid profile email
                                                        ↑ required for OIDC
  → Receive code (same mechanism)
  → POST /token { code, ... }
  → { access_token, token_type, expires_in, refresh_token, id_token }
                                                              ↑ added by OIDC
```

Any OAuth 2.0 authorization server can become an OIDC Provider (OP) by implementing the additional endpoints and issuing ID tokens. The client is called a Relying Party (RP) in OIDC terminology.

**Q3. What is the difference between a Relying Party and an OpenID Provider?**
A:

```
OpenID Provider (OP):
  The identity authority — authenticates the user and issues the id_token.
  Examples: Google (accounts.google.com), Okta, Auth0, Microsoft Entra ID,
  Keycloak, your own OIDC server built with a library like IdentityServer.

  Responsibilities:
    - Authenticate users (via password, MFA, passkeys, SSO, etc.)
    - Issue signed id_tokens and access_tokens
    - Expose the UserInfo endpoint
    - Expose /.well-known/openid-configuration (Discovery)
    - Publish JWKs at the JWKS URI for token verification
    - Validate nonce, redirect_uri, client_id on every authorization request

Relying Party (RP):
  The client application — your app — that relies on the OP to authenticate users.
  Examples: your SaaS application, your mobile app, a CLI tool.

  Responsibilities:
    - Initiate the OIDC flow with correct scopes (openid, profile, email, etc.)
    - Generate and validate the nonce
    - Validate the id_token (signature, iss, aud, exp, nonce)
    - Use the sub claim as the stable user identifier in its own database
    - Optionally call UserInfo for additional claims

The trust direction: RP trusts the OP's assertions. The OP is responsible for
the security of the identity assertion. The RP is responsible for correctly
validating what the OP sends.
```

## Section 2: The ID Token

**Q4. What is the ID token, and what does its structure look like?**
A: The ID token is a JSON Web Token (JWT, RFC 7519) issued by the OpenID Provider that contains a signed assertion of the user's identity. It is not an access credential — it cannot be used to call APIs. Its purpose is to tell the Relying Party "this user authenticated, here is their identity, and this assertion is meant for you."

```
JWT structure: header.payload.signature (base64url-encoded, dot-separated)

Header:
{
  "alg": "RS256",          ← signature algorithm
  "typ": "JWT",
  "kid": "key-id-2024-q2"  ← key ID — tells RP which public key to use for verification
}

Payload (standard OIDC claims):
{
  "iss": "https://accounts.myorg.com",    ← Issuer: the OpenID Provider's identifier
  "sub": "user_Kp9mXnL2qT7v",            ← Subject: stable, unique user identifier
  "aud": "loans_dashboard",              ← Audience: the client_id this token is FOR
  "exp": 1720000900,                     ← Expiry: unix timestamp (short-lived, e.g. 1hr)
  "iat": 1719997300,                     ← Issued At: when the token was minted
  "auth_time": 1719997290,               ← When the user actually authenticated
  "nonce": "h8Kp2mTv9xLq",              ← Replay-prevention (see Q8)
  "acr": "urn:mace:incommon:iap:silver", ← Authentication Context Class Reference
  "amr": ["pwd", "otp"],                 ← Authentication Methods References
  "email": "alice@myorg.com",            ← Standard profile claim (if email scope granted)
  "email_verified": true,
  "name": "Alice Nguyen",
  "given_name": "Alice",
  "family_name": "Nguyen",
  "locale": "en-US"
}

Signature:
  RS256(base64url(header) + "." + base64url(payload), private_key)
  RP verifies using the OP's public key from the JWKS URI.
```

The `sub` claim is the critical identity anchor. It is:
- Stable: the same user always gets the same `sub` at a given OP
- Opaque: often a random identifier, not the user's email or username
- Unique: no two users at the same OP share a `sub`

Use `sub` as the foreign key in your own user database — not `email` (which can change) and not `name` (which is not unique).

**Q5. What must the Relying Party validate on every ID token?**
A: The RP that skips any of these steps has an authentication bypass:

```python
import jwt  # PyJWT library
import time, requests

def validate_id_token(
    raw_token: str,
    expected_issuer: str,
    expected_audience: str,
    expected_nonce: str,
    jwks_uri: str,
) -> dict:
    # 1. Fetch the signing key identified by the 'kid' header
    #    In production: cache the JWKS, refresh only when kid is not found
    header = jwt.get_unverified_header(raw_token)
    kid    = header.get("kid")
    alg    = header.get("alg")

    # 2. Algorithm allowlist — never accept 'none'; be explicit
    ALLOWED_ALGORITHMS = {"RS256", "ES256", "RS384", "ES384"}
    if alg not in ALLOWED_ALGORITHMS:
        raise AuthError(f"Disallowed algorithm: {alg!r}")

    jwks   = fetch_jwks(jwks_uri)          # returns { keys: [...] }
    pubkey = find_key(jwks, kid)           # match by kid, extract public key

    try:
        payload = jwt.decode(
            raw_token,
            pubkey,
            algorithms=[alg],
            audience=expected_audience,    # PyJWT validates aud automatically
            options={"verify_exp": True},
        )
    except jwt.ExpiredSignatureError:
        raise AuthError("ID token has expired")
    except jwt.InvalidAudienceError:
        raise AuthError("ID token audience mismatch — not intended for this client")
    except jwt.InvalidSignatureError:
        raise AuthError("ID token signature verification failed")
    except jwt.DecodeError:
        raise AuthError("Malformed ID token")

    # 3. Issuer check — exact string match
    if payload.get("iss") != expected_issuer:
        raise AuthError(f"Issuer mismatch: expected {expected_issuer!r}, "
                        f"got {payload.get('iss')!r}")

    # 4. Audience check — aud must include client_id
    #    Already validated by PyJWT above, but explicit belt-and-suspenders:
    aud = payload.get("aud", [])
    if isinstance(aud, str):
        aud = [aud]
    if expected_audience not in aud:
        raise AuthError("client_id not in aud claim")

    # 5. Expiry — validated by library; also check iat is not in the future
    now = time.time()
    if payload.get("iat", 0) > now + 300:   # 5 min clock skew tolerance
        raise AuthError("id_token issued in the future — clock skew or replay")

    # 6. Nonce — critical for preventing replay attacks (see Q8)
    if payload.get("nonce") != expected_nonce:
        raise AuthError("Nonce mismatch — possible replay attack")

    # 7. auth_time — if max_age was requested, enforce it
    # (omitted here for brevity — see step-up authentication pattern)

    return payload   # validated claims

class AuthError(Exception):
    pass
```

The two most commonly skipped validations: `aud` (developers assume any id_token is valid for their app) and `nonce` (developers skip replay protection entirely). Both are real attack vectors.

**Q6. What is the `sub` claim, and why should it be used as the user identifier instead of `email`?**
A: `sub` (subject) is the OP's stable, unique, opaque identifier for the user. It is the correct foreign key to store in your application database and use for all internal references.

```
Why NOT email:

  1. Email can change. A user changes their email at the OP — your database now has no
     way to match them to their existing account. They appear as a new user.

  2. Email is not always unique across providers. If you support both Google and GitHub
     as IdPs, alice@company.com at Google and alice@company.com at GitHub could be two
     completely different people — but email-as-identifier conflates them.

  3. Email is a PII field that may be governed by retention and access policies.
     Using it as a primary key embeds PII throughout your schema.

Why NOT name, given_name, etc.:
  Names are not unique, not stable, and not always present.

Correct approach — composite key:

  User in your DB:
  {
    id:         "internal_uuid_123",
    iss:        "https://accounts.google.com",  ← provider identity
    sub:        "117650423185494628391",         ← provider's user identifier
    email:      "alice@company.com",             ← display/contact only, not PK
    created_at: "2024-01-15T09:00:00Z"
  }

  Lookup on login:
  SELECT * FROM users WHERE iss = ? AND sub = ?

  The (iss, sub) pair is globally unique — two different OPs could issue the same sub
  string, so you must scope sub by iss.

  If you want to support account linking (same user, multiple providers),
  keep a separate identity_providers table:
  {
    user_id: "internal_uuid_123",   ← foreign key to your users table
    iss:     "https://accounts.google.com",
    sub:     "117650423185494628391"
  }
  {
    user_id: "internal_uuid_123",
    iss:     "https://github.com",
    sub:     "u:alice:7823641"
  }
```

**Q7. What is the difference between the ID token and the access token in OIDC?**
A: They are issued together but have completely different purposes and audiences:

```
Property            id_token                          access_token
─────────────────── ───────────────────────────────── ─────────────────────────────────
Audience            The Relying Party (client_id)     The Resource Server (API)
Purpose             Identity assertion (who you are)  Authorization credential (what you may do)
Format              Always a signed JWT               JWT or opaque, depends on OP config
Claims              iss, sub, aud, exp, iat, nonce,   scope, client_id, custom claims
                    profile claims
Who validates it    The RP — your application         The Resource Server — your API
Should be sent to   Nobody — validate locally         Resource Server via Authorization header
APIs?               NO — the API is not the audience  YES — that is its purpose
Lifetime            Short (1 hour typical)            Short (5–60 min typical)
Revocation          Expires; no live check needed     Should check introspection for sensitive ops

The audience mismatch attack:
  If your API accepted the id_token as an API credential:
    id_token.aud = "loans_dashboard"   ← the Relying Party
    Your API is "loans_api"
    The API would fail the aud check — or worse, skip it — and grant access based
    on a token that was not issued for the API.

  The correct pattern:
    RP receives id_token → validates locally → extracts identity → stores in session
    RP receives access_token → attaches to API calls → API validates aud and scope
    API never sees id_token. RP never sends access_token to browser storage if avoidable.
```

## Section 3: The UserInfo Endpoint

**Q8. What is the UserInfo endpoint, and when should you use it instead of the ID token?**
A: The UserInfo endpoint is a protected OIDC endpoint (`GET /userinfo`) that returns additional claims about the authenticated user. It is accessed using the access token (not the id_token), and the response is a JSON object or a signed JWT containing identity claims.

```
Why it exists — the ID token size trade-off:

  ID tokens travel in redirect URLs (for Implicit flow), are stored in sessions,
  and are validated on every use. Including every possible claim (profile photo,
  address, phone, custom attributes) would make them large and slow.

  OIDC's design: put the minimal required claims in the id_token; put the rest
  behind the UserInfo endpoint, fetched on demand.

When to use the id_token claims directly:
  - For identity verification on login: sub, email, email_verified, name
  - When you need the claims immediately after authentication
  - When making offline decisions (the user may not be actively connected)
  - Most login flows: validate id_token, extract sub, look up or create user in DB

When to call UserInfo:
  - When you need claims not included in the id_token (e.g., address, phone_number)
  - When you need the most current claim values (id_token claims are frozen at issuance;
    UserInfo reflects the current state in the OP's directory)
  - When the RP requested scopes like profile, email, address, phone — the OP may
    deliver these claims via UserInfo rather than embedding them in the id_token

Example:
  GET https://accounts.myorg.com/userinfo
  Authorization: Bearer eyJhbGci...   ← access_token (NOT id_token)

  Response:
  {
    "sub":            "user_Kp9mXnL2qT7v",
    "name":           "Alice Nguyen",
    "given_name":     "Alice",
    "family_name":    "Nguyen",
    "email":          "alice@myorg.com",
    "email_verified": true,
    "phone_number":   "+1-555-867-5309",
    "address": {
      "street_address": "123 Main St",
      "locality":       "San Francisco",
      "region":         "CA",
      "postal_code":    "94105",
      "country":        "US"
    },
    "picture":        "https://cdn.myorg.com/avatars/user_Kp9mXnL2qT7v.jpg",
    "locale":         "en-US",
    "updated_at":     1719950000
  }
```

```python
# Fetching UserInfo — always validate sub matches the id_token's sub
def fetch_userinfo(access_token: str, userinfo_endpoint: str, expected_sub: str) -> dict:
    resp = requests.get(
        userinfo_endpoint,
        headers={"Authorization": f"Bearer {access_token}"},
        timeout=5,
    )
    resp.raise_for_status()

    content_type = resp.headers.get("Content-Type", "")

    if "application/jwt" in content_type:
        # Some OPs return a signed JWT — validate it the same way as id_token
        claims = validate_userinfo_jwt(resp.text)
    else:
        claims = resp.json()

    # CRITICAL: sub in UserInfo response must match sub from the id_token
    # Without this check, an attacker who swaps access tokens could get a
    # different user's claims delivered to the wrong session
    if claims.get("sub") != expected_sub:
        raise AuthError(
            f"UserInfo sub {claims.get('sub')!r} does not match "
            f"id_token sub {expected_sub!r}"
        )

    return claims
```

The `sub` cross-check is mandatory per the OIDC spec (Section 5.3.2). Skipping it allows a confused deputy scenario where an attacker substitutes their own access token to retrieve a victim's session.

**Q9. What claims are returned by UserInfo, and what OIDC scopes control them?**
A: OIDC defines standard scopes that map to claim sets. Requesting a scope in the authorization request grants access to those claims at the UserInfo endpoint (and optionally in the id_token):

```
Scope         Claims Returned
──────────    ──────────────────────────────────────────────────────────────
openid        sub (required — without this, OIDC is not active)

profile       name, family_name, given_name, middle_name, nickname,
              preferred_username, profile (URL), picture (URL),
              website (URL), gender, birthdate, zoneinfo, locale, updated_at

email         email, email_verified

address       address (JSON object: street_address, locality, region,
                        postal_code, country, formatted)

phone         phone_number, phone_number_verified

offline_access  (no claims — signals that a refresh_token should be issued)

Custom scopes are OP-specific:
  roles          → roles: ["admin", "loan-officer"]  (not in spec, common in enterprise)
  tenant         → tenant_id: "acme-corp"             (common in B2B SaaS)
  groups         → groups: ["engineering", "finance"]  (Okta, Entra ID)
```

```python
# Requesting the right scopes at authorization time
OIDC_SCOPES = [
    "openid",          # required — enables OIDC and the sub claim
    "profile",         # name, picture, locale, etc.
    "email",           # email and email_verified
    "offline_access",  # request a refresh_token for long sessions
]

auth_params = {
    "response_type":         "code",
    "client_id":             CLIENT_ID,
    "redirect_uri":          REDIRECT_URI,
    "scope":                 " ".join(OIDC_SCOPES),
    "state":                 generate_state(),
    "nonce":                 generate_nonce(),   # see Q10
    "code_challenge":        code_challenge,
    "code_challenge_method": "S256",
}
```

Requesting only the scopes you actually use is the principle of least privilege applied to identity claims. Requesting `address` and `phone` when your app only needs `name` and `email` collects more PII than necessary — avoid this.

## Section 4: The `nonce`

**Q10. What is the `nonce` parameter in OIDC, and what attack does it prevent?**
A: The `nonce` is a client-generated, cryptographically random string that is included in the authorization request and must appear verbatim inside the issued id_token's `nonce` claim. The RP validates the nonce on every id_token before trusting its contents.

It prevents the **ID token replay attack**:

```
The attack without nonce:

1. Attacker obtains a valid id_token for themselves:
   - Initiates a legitimate OIDC flow for their own account
   - Receives: id_token { sub: "attacker_sub", iss: "myop.com", aud: "myapp" }

2. The id_token is validly signed, audience is correct, not yet expired.

3. Attacker presents this id_token to the application's login endpoint:
   POST /auth/callback { id_token: "attacker's_token" }

4. Application validates signature ✓, aud ✓, iss ✓, exp ✓ — everything checks out.
   Application logs the attacker in... as the attacker.

So far that's just normal login. The replay threat is more specific:

Replay scenario:
  - Attacker intercepts victim's id_token (via network, logs, XSS, etc.)
  - Victim's id_token is for sub="victim_sub", still within its exp window
  - Attacker replays it at the RP's callback endpoint
  - Without nonce: RP has no way to know this token was meant for a different
    login session — it appears valid in every check
  - Attacker gains access to the victim's account

With nonce:
  1. RP generates nonce="h8Kp2mTv9xLq", stores it in the login session
  2. Authorization request includes nonce="h8Kp2mTv9xLq"
  3. OP embeds the nonce into the issued id_token: { "nonce": "h8Kp2mTv9xLq" }
  4. RP checks: id_token.nonce == session.nonce
  5. Intercepted token has the victim's nonce — does not match the attacker's session nonce
  6. Validation fails → replay blocked
```

The nonce is especially critical in the (now deprecated) Implicit flow, where the id_token was delivered directly in the redirect URL and was therefore more exposed. In the Authorization Code flow, the nonce still matters because the id_token could be intercepted or leaked at the OP level.

**Q11. How do you generate, store, and validate the `nonce`?**
A:

```python
import secrets, hashlib

# --- GENERATING THE NONCE ---

# Option 1: Raw random (simple, recommended for server-side apps)
def generate_nonce() -> str:
    return secrets.token_urlsafe(32)   # 256 bits of entropy
    # e.g. "fK9mPq3rT7vL2nW8xB5hYj4sD1gN6cQ0"

# Option 2: Hashed nonce (recommended for SPAs / when nonce is in sessionStorage)
# Store the verifier locally; send only the hash to the OP.
# If the stored verifier leaks, the hash alone is useless.
def generate_nonce_pair() -> tuple[str, str]:
    verifier  = secrets.token_urlsafe(32)
    nonce     = hashlib.sha256(verifier.encode()).hexdigest()
    return verifier, nonce   # store verifier; send nonce in auth request

# --- STORING THE NONCE ---

# Server-side app: store in the server-side session (HttpOnly cookie)
session["oidc_nonce"] = nonce_verifier   # never in the URL or response body

# SPA without backend: sessionStorage is acceptable for the redirect roundtrip
# (same security posture as PKCE verifier storage — see OAuth 2.0 Q10)
sessionStorage.setItem("oidc_nonce_verifier", nonce_verifier)

# --- VALIDATION ON CALLBACK ---

def validate_nonce(id_token_payload: dict, session_nonce_verifier: str) -> None:
    token_nonce = id_token_payload.get("nonce")
    if not token_nonce:
        raise AuthError("id_token missing nonce claim")

    # If using hashed nonce:
    expected_nonce = hashlib.sha256(session_nonce_verifier.encode()).hexdigest()

    # Use constant-time comparison to prevent timing attacks
    if not hmac.compare_digest(token_nonce, expected_nonce):
        raise AuthError("Nonce mismatch — possible replay or CSRF attack")

    # CRITICAL: after successful validation, clear the nonce from the session.
    # A nonce is single-use — it must never be valid for a second login.
    session.pop("oidc_nonce_verifier", None)
```

**Nonce properties required by the OIDC spec:**
- Must be cryptographically random (not sequential, not predictable)
- Must be unique per authorization request (never reuse)
- Must be validated before any session is established
- Must be cleared after successful validation (single-use)
- Must not be guessable by the OP or any third party (use CSPRNG)

**Q12. How does the `nonce` differ from the `state` parameter?**
A: They look similar — both are random strings generated by the RP — but they protect against different attacks and travel through different channels:

```
Parameter   Location          Validated by        Protects against
─────────── ───────────────── ─────────────────── ──────────────────────────────────────
state       Query string of   RP (OAuth layer)    OAuth CSRF: attacker tricks victim into
            the callback URL                      completing an attacker-initiated flow
            (?state=...)                          (authorization code attached to wrong session)

nonce       Inside the        RP (OIDC layer)     ID token replay: attacker reuses a
            id_token JWT                          previously captured id_token in a new
            (claim)                               or different session

state flow:
  RP generates state → includes in auth request (query param)
  OP returns state unchanged in callback redirect (query param)
  RP validates: callback_state == session_state
  state never enters the id_token

nonce flow:
  RP generates nonce → includes in auth request (query param)
  OP embeds nonce inside the id_token JWT (as a claim)
  RP validates: id_token.nonce == session_nonce
  nonce never appears in the callback URL — it travels inside the signed token

Common mistake: using the same value for both state and nonce.
  This technically satisfies both validations but conflates two independent
  security mechanisms. Generate them separately — they serve different purposes
  and are validated at different points in the flow.

Both are required:
  state → protects the OAuth layer (authorization code binding)
  nonce → protects the OIDC layer (id_token binding)
  Omitting either leaves the corresponding attack open.
```

## Section 5: OIDC Discovery and JWKS

**Q13. What is the OIDC Discovery endpoint, and how should an RP use it?**
A: The Discovery endpoint (`/.well-known/openid-configuration`) is a JSON document at a well-known URL relative to the OP's issuer URI. It describes the OP's capabilities, endpoint URLs, supported algorithms, and claim types. This eliminates hardcoded configuration and enables dynamic client setup.

```python
# Fetching and using the discovery document

def load_oidc_config(issuer: str) -> dict:
    # Normalize: strip trailing slash, append well-known path
    discovery_url = issuer.rstrip("/") + "/.well-known/openid-configuration"
    resp = requests.get(discovery_url, timeout=5)
    resp.raise_for_status()
    config = resp.json()

    # Validate that the issuer in the document matches what we expect
    if config.get("issuer") != issuer:
        raise ValueError(
            f"Issuer mismatch in discovery document: "
            f"expected {issuer!r}, got {config.get('issuer')!r}"
        )
    return config

# Example discovery document (Google):
# GET https://accounts.google.com/.well-known/openid-configuration

{
    "issuer":                                "https://accounts.google.com",
    "authorization_endpoint":               "https://accounts.google.com/o/oauth2/v2/auth",
    "token_endpoint":                        "https://oauth2.googleapis.com/token",
    "userinfo_endpoint":                     "https://openidconnect.googleapis.com/v1/userinfo",
    "revocation_endpoint":                   "https://oauth2.googleapis.com/revoke",
    "jwks_uri":                              "https://www.googleapis.com/oauth2/v3/certs",
    "response_types_supported":              ["code", "token", "id_token", "code token", ...],
    "subject_types_supported":               ["public"],
    "id_token_signing_alg_values_supported": ["RS256"],
    "scopes_supported":                      ["openid", "email", "profile"],
    "token_endpoint_auth_methods_supported": ["client_secret_post", "client_secret_basic"],
    "claims_supported":                      ["sub", "iss", "aud", "iat", "exp", "email", ...]
}
```

In production: cache the discovery document (it changes rarely — refresh daily or on cache miss) and cache the JWKS (refresh only when a `kid` is not found in the cache, to handle key rotation).

**Q14. What is the JWKS URI, and how does it enable key rotation without RP downtime?**
A: The JWKS URI (JSON Web Key Set) is the endpoint where the OP publishes its public signing keys. RPs fetch these keys to verify id_token signatures. The `kid` (Key ID) header in the JWT tells the RP which key to use.

```python
from functools import lru_cache
import jwt, requests
from jwt.algorithms import RSAAlgorithm

@lru_cache(maxsize=None)
def get_jwks(jwks_uri: str) -> dict:
    """Cached JWKS fetch. Call invalidate_jwks_cache() on kid-miss."""
    return requests.get(jwks_uri, timeout=5).json()

def get_public_key(jwks_uri: str, kid: str):
    jwks = get_jwks(jwks_uri)
    keys = {k["kid"]: k for k in jwks["keys"]}

    if kid not in keys:
        # kid not in cache → OP may have rotated keys → force refresh
        get_jwks.cache_clear()
        jwks = get_jwks(jwks_uri)
        keys = {k["kid"]: k for k in jwks["keys"]}

    if kid not in keys:
        raise AuthError(f"Unknown key ID: {kid!r}")

    return RSAAlgorithm.from_jwk(keys[kid])

# Key rotation flow:
# 1. OP generates new key pair, adds new key to JWKS with new kid
# 2. OP starts signing new tokens with the new kid
# 3. RP encounters new kid → cache miss → refreshes JWKS → finds new key → verifies ✓
# 4. Tokens signed with old kid still verify (old key still in JWKS during transition)
# 5. After all old tokens expire, OP removes old key from JWKS
# 6. Zero RP downtime throughout — no RP config change required
```

This is why hardcoding public keys is an operational anti-pattern: when the OP rotates keys (which should happen regularly for security), every RP with a hardcoded key fails. The JWKS URI makes rotation transparent.

## Section 6: Real-World OIDC Patterns

**Q15. How do you implement "Login with Google" correctly using OIDC?**
A:

```typescript
// oidc-google.ts — OIDC Authorization Code + PKCE flow for a React SPA

const GOOGLE_ISSUER    = "https://accounts.google.com";
const CLIENT_ID        = "123456789-abc.apps.googleusercontent.com";
const REDIRECT_URI     = "https://app.myorg.com/auth/callback";
const SCOPES           = "openid profile email";

// Step 1: Load Google's OIDC configuration
async function loadGoogleConfig(): Promise<OIDCConfig> {
    const resp = await fetch(
        `${GOOGLE_ISSUER}/.well-known/openid-configuration`
    );
    return resp.json();
}

// Step 2: Initiate login
export async function loginWithGoogle(): Promise<void> {
    const config       = await loadGoogleConfig();
    const codeVerifier = generateCodeVerifier();      // PKCE (OAuth layer)
    const codeChallenge = await sha256base64url(codeVerifier);
    const state        = crypto.randomUUID();          // CSRF protection (OAuth layer)
    const nonce        = crypto.randomUUID();          // replay protection (OIDC layer)

    sessionStorage.setItem("pkce_verifier", codeVerifier);
    sessionStorage.setItem("oauth_state",   state);
    sessionStorage.setItem("oidc_nonce",    nonce);    // store for later validation

    const params = new URLSearchParams({
        response_type:          "code",
        client_id:              CLIENT_ID,
        redirect_uri:           REDIRECT_URI,
        scope:                  SCOPES,
        state,
        nonce,                                         // included in auth request
        code_challenge:         codeChallenge,
        code_challenge_method:  "S256",
    });

    window.location.href = `${config.authorization_endpoint}?${params}`;
}

// Step 3: Handle callback
export async function handleCallback(): Promise<UserSession> {
    const config = await loadGoogleConfig();
    const params = new URLSearchParams(window.location.search);

    // Error handling
    if (params.get("error")) {
        throw new Error(`Auth error: ${params.get("error_description")}`);
    }

    // CSRF check (OAuth layer)
    const returnedState = params.get("state");
    const savedState    = sessionStorage.getItem("oauth_state");
    if (!returnedState || returnedState !== savedState) {
        throw new Error("State mismatch — CSRF detected");
    }

    // Exchange code for tokens
    const codeVerifier = sessionStorage.getItem("pkce_verifier")!;
    const tokenResp    = await fetch(config.token_endpoint, {
        method: "POST",
        headers: { "Content-Type": "application/x-www-form-urlencoded" },
        body: new URLSearchParams({
            grant_type:    "authorization_code",
            code:          params.get("code")!,
            redirect_uri:  REDIRECT_URI,
            client_id:     CLIENT_ID,
            code_verifier: codeVerifier,
        }),
    });

    const tokens = await tokenResp.json();
    const { id_token, access_token } = tokens;

    // Validate id_token (in a real app, do this server-side or with a library)
    const savedNonce = sessionStorage.getItem("oidc_nonce")!;
    const claims     = await validateIdToken(id_token, {
        issuer:   GOOGLE_ISSUER,
        audience: CLIENT_ID,
        nonce:    savedNonce,
        jwksUri:  config.jwks_uri,
    });

    // Clean up sensitive session state
    ["pkce_verifier", "oauth_state", "oidc_nonce"].forEach(k =>
        sessionStorage.removeItem(k)
    );

    // The session identity: use sub as the stable user ID
    return {
        sub:           claims.sub,
        email:         claims.email,
        emailVerified: claims.email_verified,
        name:          claims.name,
        picture:       claims.picture,
        accessToken:   access_token,   // in memory only — for UserInfo calls
    };
}
```

**Q16. How do you handle OIDC in a server-side web application (BFF pattern)?**
A: For server-side apps or when using the Backend-for-Frontend pattern, all sensitive OIDC artifacts (code verifier, nonce, tokens) stay on the server. The browser only holds a session cookie:

```python
# Flask/Django BFF — OIDC with server-side session
import secrets, hashlib, requests
from flask import Flask, session, redirect, request, jsonify

app = Flask(__name__)

ISSUER      = "https://auth.myorg.com"
CLIENT_ID   = "loans_dashboard"
CLIENT_SECRET = os.environ["OIDC_CLIENT_SECRET"]
REDIRECT_URI  = "https://app.myorg.com/auth/callback"
SCOPES        = "openid profile email offline_access"

oidc_config = load_oidc_discovery(ISSUER)

@app.route("/auth/login")
def login():
    # All sensitive state stored in server-side session — not in the browser
    code_verifier    = secrets.token_urlsafe(96)
    code_challenge   = base64url_sha256(code_verifier)
    state            = secrets.token_urlsafe(32)
    nonce            = secrets.token_urlsafe(32)

    session["pkce_verifier"] = code_verifier   # HttpOnly session cookie
    session["oauth_state"]   = state
    session["oidc_nonce"]    = nonce

    params = urlencode({
        "response_type":         "code",
        "client_id":             CLIENT_ID,
        "redirect_uri":          REDIRECT_URI,
        "scope":                 SCOPES,
        "state":                 state,
        "nonce":                 nonce,
        "code_challenge":        code_challenge,
        "code_challenge_method": "S256",
    })
    return redirect(f"{oidc_config['authorization_endpoint']}?{params}")


@app.route("/auth/callback")
def callback():
    # CSRF check
    if not hmac.compare_digest(request.args.get("state", ""), session.get("oauth_state", "")):
        return "State mismatch", 400

    # Token exchange — client_secret sent server-to-server, never to browser
    token_resp = requests.post(oidc_config["token_endpoint"], data={
        "grant_type":    "authorization_code",
        "code":          request.args["code"],
        "redirect_uri":  REDIRECT_URI,
        "client_id":     CLIENT_ID,
        "client_secret": CLIENT_SECRET,
        "code_verifier": session["pkce_verifier"],
    }).json()

    # Validate id_token
    claims = validate_id_token(
        raw_token       = token_resp["id_token"],
        expected_issuer = ISSUER,
        expected_audience = CLIENT_ID,
        expected_nonce  = session["oidc_nonce"],
        jwks_uri        = oidc_config["jwks_uri"],
    )

    # Establish application session — store only what's needed
    session.clear()
    session["user_sub"]      = claims["sub"]        # stable user ID
    session["user_email"]    = claims.get("email")
    session["user_name"]     = claims.get("name")
    session["access_token"]  = token_resp["access_token"]   # for API calls
    session["refresh_token"] = token_resp.get("refresh_token")

    return redirect("/dashboard")
```

The BFF pattern keeps tokens server-side and eliminates XSS token theft from the browser entirely — the browser only holds a session cookie with a random session ID.

**Q17. How do you map OIDC flows and client types together?**
A:

| Scenario | Flow | OIDC Scopes | Key Consideration |
|---|---|---|---|
| Server-side web app ("Log in with Google") | Authorization Code + PKCE | `openid profile email` | Use `client_secret`; store tokens server-side |
| React/Vue SPA (no backend) | Authorization Code + PKCE | `openid profile email` | Tokens in memory only; BFF preferred for production |
| Mobile app (iOS/Android) | Authorization Code + PKCE | `openid profile email offline_access` | Custom URI scheme or Universal Links; PKCE required |
| Smart TV / CLI / IoT | Device Code + OIDC | `openid profile email offline_access` | Input-constrained; user authorizes on secondary device |
| "Sign up with GitHub" | Authorization Code + PKCE | `openid user:email` | GitHub-specific scope naming; validate `sub` per-provider |
| Enterprise SSO (SAML replacement) | Authorization Code + PKCE | `openid profile email groups roles` | Validate group/role claims for authorization decisions |
| Multi-tenant SaaS | Authorization Code + PKCE | `openid profile email tenant` | Use `iss`+`sub` composite key; custom `tenant_id` claim |
| Session refresh (long-lived login) | Token refresh | N/A | Request `offline_access`; store refresh token server-side only |

## Quick Reference: ID Token Claims

| Claim | Type | Required | Description |
|---|---|---|---|
| `iss` | string | Yes | Issuer — the OP's URL (`https://accounts.google.com`) |
| `sub` | string | Yes | Subject — stable unique user identifier; use as FK in your DB |
| `aud` | string or array | Yes | Audience — must include the RP's `client_id` |
| `exp` | number (unix) | Yes | Expiry timestamp — token invalid after this time |
| `iat` | number (unix) | Yes | Issued At — when the token was minted |
| `auth_time` | number (unix) | Conditional | When the user actually authenticated (required if `max_age` was requested) |
| `nonce` | string | Conditional | Echoed from the auth request — must be validated by RP |
| `acr` | string | Optional | Authentication Context Class Reference (e.g., MFA level) |
| `amr` | array | Optional | Authentication Methods References (`pwd`, `otp`, `hwk`) |
| `azp` | string | Optional | Authorized Party — if `aud` has multiple values, specifies the intended client |
| `email` | string | Optional | Requires `email` scope |
| `email_verified` | boolean | Optional | Whether the OP has verified the email address |
| `name` | string | Optional | Full display name — requires `profile` scope |
| `picture` | string | Optional | URL to profile photo |
| `locale` | string | Optional | BCP 47 language tag (`en-US`) |

## Quick Reference: Nonce vs State

| Property | `state` (OAuth layer) | `nonce` (OIDC layer) |
|---|---|---|
| Generated by | RP | RP |
| Sent in | Authorization request query parameter | Authorization request query parameter |
| Returned in | Callback redirect query parameter | Inside the signed id_token JWT (as a claim) |
| Validated by | RP against session value | RP against session value |
| Protects against | OAuth CSRF (attacker-initiated code injection) | ID token replay (reuse of a captured id_token) |
| Single-use | Yes — clear from session after one validation | Yes — clear from session after one validation |
| Entropy requirement | 256-bit CSPRNG minimum | 256-bit CSPRNG minimum |
| Required in OIDC | Strongly recommended | Yes — required when using Authorization Code + PKCE |

**Tip for the interview:** At 5 YOE, OIDC questions are almost never "what is OAuth?" — they assume that baseline and probe identity-specific depth. Know the difference between id_token and access_token cold (Q7) — conflating them is the most common tell. Be able to explain exactly why nonce prevents replay attacks and how it differs from state (Q10, Q12). Know what claims go in the id_token vs UserInfo and why the split exists (Q8, Q9). The `sub` vs `email` as user identifier question (Q6) comes up in system design interviews as "how do you model users who can log in with multiple providers?" — the `(iss, sub)` composite key is the answer. If asked about implementing "Login with Google," the answer is OIDC Authorization Code + PKCE + `openid` scope, with id_token validation before establishing any session — not raw OAuth 2.0, and not trusting claims without verifying the signature and nonce.
