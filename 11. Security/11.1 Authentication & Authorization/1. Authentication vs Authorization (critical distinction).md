# Security: Authentication vs. Authorization — Interview Q&A (5 YOE Level)

---

## Section 1: The Core Distinction

**Q1. What is the difference between Authentication and Authorization, and why does conflating them cause security bugs?**
A: Authentication (AuthN) answers **"Who are you?"** — it verifies identity. Authorization (AuthZ) answers **"What are you allowed to do?"** — it enforces access control. They are sequential: you must authenticate before you can be authorized, but authentication alone grants nothing.

The classic framing:
- **AuthN:** A user presents a JWT. The server validates the signature, expiry, and issuer. If valid, the server now knows *who* is making the request.
- **AuthZ:** The server checks whether *that identity* has permission to perform the requested action on the requested resource. A valid token for user A doesn't mean user A can access user B's data.

Why conflating them causes bugs: the most common class of exploit here is **Broken Object-Level Authorization (BOLA/IDOR)** — the server verifies the token (AuthN passes), but skips the ownership check (AuthZ absent). The classic example:

```
GET /api/loans/98765
Authorization: Bearer <valid-token-for-user-A>
```

If the server only validates the token and returns loan `98765` without checking whether user A owns that loan, any authenticated user can enumerate and read any other user's loan data. The AuthN layer is working perfectly. The AuthZ layer is missing entirely. In fintech, this is a data breach.

**Q2. Map AuthN and AuthZ to the HTTP layer — where in a request lifecycle does each check happen?**
A: In a typical Node.js/NestJS microservice:

```
Incoming Request
       │
       ▼
┌─────────────────────────────┐
│  AuthN Middleware / Guard   │  ← "Is this token valid?"
│  - Validate JWT signature   │    If no → 401 Unauthorized
│  - Check expiry (exp claim) │
│  - Verify issuer (iss claim)│
│  - Attach req.user          │
└────────────┬────────────────┘
             │ req.user = { userId, roles, tenantId }
             ▼
┌─────────────────────────────┐
│  AuthZ Guard / Policy Layer │  ← "Can THIS user do THIS thing?"
│  - Role check (RBAC)        │    If no → 403 Forbidden
│  - Resource ownership check │
│  - Attribute-based rules    │
└────────────┬────────────────┘
             │
             ▼
      Route Handler / Controller
```

The HTTP status codes are semantically meaningful:
- **401 Unauthorized** — identity could not be established (missing token, invalid signature, expired token). Misleading name — it actually means "unauthenticated."
- **403 Forbidden** — identity is established but the request is not permitted. The server knows who you are; it's refusing the action.

Returning 403 for a missing token, or 401 for a valid-token/wrong-role scenario, is a common mistake that muddies logs and makes debugging harder. Get the codes right — they communicate different things to clients and monitoring systems.

**Q3. Give a concrete fintech example where AuthN succeeds but AuthZ fails at each of the three layers: route, object, and field.**
A: Each layer represents a finer granularity of access control:

**Route-level AuthZ failure:**
```
POST /api/admin/disburse-loan
Authorization: Bearer <valid-token-for-role=customer>
```
The token is valid (AuthN passes). But the `/admin/*` route requires `role=admin`. The customer role should get a `403`. If the route guard is missing or misconfigured and the handler executes — that's a route-level AuthZ failure. Any authenticated user can trigger admin operations.

**Object-level AuthZ failure (BOLA/IDOR):**
```
GET /api/loans/99001         ← loan belonging to user B
Authorization: Bearer <valid-token-for-user-A>
```
The token is valid. The route is accessible to `role=customer`. But the handler fetches loan `99001` without checking `WHERE loan_id = 99001 AND user_id = req.user.userId`. User A reads user B's loan — this is the IDOR pattern, OWASP API Security Top 10 #1.

**Field-level AuthZ failure:**
```
GET /api/loans/12345
Authorization: Bearer <valid-token-for-role=customer>
Response: {
  "loanId": "12345",
  "amount": 500000,
  "userId": "user-A",
  "internalCreditScore": 742,    ← should not be exposed to customer
  "fraudRiskLabel": "LOW",       ← should not be exposed to customer
  "partnerCommission": 1500      ← absolutely should not be exposed
}
```
The route check passed. The ownership check passed. But the response serializer returns internal fields not meant for customer-facing APIs. A `customer` role should receive a projected response; `agent` and `admin` roles may receive more fields. Field-level AuthZ is often the most neglected layer.

## Section 2: Authentication Deep Dive

**Q4. How does JWT-based authentication work, and what must the server validate on every request?**
A: A JWT (JSON Web Token) is a base64url-encoded structure: `header.payload.signature`. The server that issued the token signed it with a secret (HMAC-SHA256 for symmetric) or private key (RS256/ES256 for asymmetric). Any server with the corresponding secret/public key can verify the signature without a database lookup — that's the stateless property of JWTs.

What the server must validate on every incoming request:

```javascript
// NestJS JwtStrategy (Passport.js)
async validate(payload: JwtPayload) {
  // 1. Signature — handled by passport-jwt before this method is called
  //    If signature is invalid, validate() is never reached.

  // 2. Expiry
  const now = Math.floor(Date.now() / 1000);
  if (payload.exp < now) {
    throw new UnauthorizedException('Token expired');
  }

  // 3. Issuer and Audience
  if (payload.iss !== process.env.JWT_ISSUER) {
    throw new UnauthorizedException('Invalid issuer');
  }
  if (!payload.aud?.includes(process.env.JWT_AUDIENCE)) {
    throw new UnauthorizedException('Invalid audience');
  }

  // 4. Token revocation check (for logout/compromise scenarios)
  const isRevoked = await this.tokenBlacklist.has(payload.jti);
  if (isRevoked) {
    throw new UnauthorizedException('Token revoked');
  }

  // 5. Subject exists and is active
  const user = await this.userService.findById(payload.sub);
  if (!user || user.status !== 'ACTIVE') {
    throw new UnauthorizedException('User not found or inactive');
  }

  return { userId: user.id, roles: user.roles, tenantId: user.tenantId };
}
```

Common omissions that create vulnerabilities:
- Skipping `iss`/`aud` validation — lets tokens issued for service A be used against service B.
- No revocation check — a user who logs out or gets compromised can keep using their old token until natural expiry.
- Trusting the `alg` claim from the token header — the `alg: none` attack sets the algorithm to none and removes the signature; libraries that trust the token's own `alg` field will accept any payload. Always specify the expected algorithm explicitly in your JWT library config.

**Q5. What is the difference between symmetric (HS256) and asymmetric (RS256/ES256) JWT signing, and when do you use each?**
A: The difference is in key distribution and who can verify tokens:

| | HS256 (HMAC-SHA256) | RS256 (RSA) / ES256 (ECDSA) |
|---|---|---|
| **Key type** | Single shared secret | Private key (signs) + Public key (verifies) |
| **Who can verify** | Anyone with the secret | Anyone with the public key |
| **Who can forge** | Anyone with the secret | Only the private key holder |
| **Key distribution** | Secret must be shared securely with every verifying service | Public key is freely distributable (JWKS endpoint) |
| **Best for** | Monolith, single-service, or fully trusted internal services | Microservices, third-party verification, public APIs |

In a microservices architecture — like a fintech platform with separate loans-service, payments-service, and notification-service — the auth service signs tokens with its **private key**. Each downstream service fetches the **public key** from the auth service's JWKS endpoint (`/.well-known/jwks.json`) and verifies tokens locally without calling the auth service on every request:

```javascript
// Microservice fetches public key from JWKS endpoint
const jwksClient = require('jwks-rsa');
const client = jwksClient({
  jwksUri: 'https://auth.myorg.internal/.well-known/jwks.json',
  cache: true,
  cacheMaxEntries: 5,
  cacheMaxAge: 600000, // 10 min — rotate key without downtime
});
```

The security property: even if a downstream service is compromised, the attacker cannot forge new tokens — they don't have the private key. With HS256, a compromised downstream service exposes the shared secret and the attacker can forge arbitrary tokens. For any system with more than one verifying service, RS256 or ES256 is the correct choice.

**Q6. What is the difference between access tokens and refresh tokens, and how do you implement secure refresh token rotation?**
A: Access tokens are short-lived credentials presented on every request. Refresh tokens are long-lived credentials used only to obtain new access tokens. They're separate to limit the blast radius of token theft:

```
Access Token:  short-lived (15 min), stateless JWT, sent in every API request header
Refresh Token: long-lived (7–30 days), opaque random string, sent only to /auth/refresh endpoint
```

Secure refresh token rotation — each use of a refresh token invalidates it and issues a new one:

```javascript
// POST /auth/refresh
async refresh(refreshToken: string) {
  // 1. Look up the refresh token in DB (refresh tokens are NOT JWTs — they're opaque)
  const tokenRecord = await this.db.refreshTokens.findOne({
    token: hash(refreshToken),  // Store hash, not plaintext
    revoked: false,
  });

  if (!tokenRecord) {
    // Token not found OR already used — possible replay attack
    // Revoke ALL tokens for this user (family invalidation)
    if (tokenRecord?.userId) {
      await this.db.refreshTokens.revokeAll({ userId: tokenRecord.userId });
    }
    throw new UnauthorizedException('Invalid refresh token');
  }

  if (tokenRecord.expiresAt < new Date()) {
    throw new UnauthorizedException('Refresh token expired');
  }

  // 2. Rotate: revoke old token, issue new pair
  await this.db.refreshTokens.update(
    { id: tokenRecord.id },
    { revoked: true, revokedAt: new Date() }
  );

  const newAccessToken  = this.jwtService.sign({ sub: tokenRecord.userId, ... });
  const newRefreshToken = crypto.randomBytes(64).toString('hex');

  await this.db.refreshTokens.create({
    token: hash(newRefreshToken),
    userId: tokenRecord.userId,
    expiresAt: addDays(new Date(), 30),
    family: tokenRecord.family,  // Track token families for reuse detection
  });

  return { accessToken: newAccessToken, refreshToken: newRefreshToken };
}
```

The **refresh token family** pattern: if a refresh token is reused (an attacker stole it and the legitimate user already rotated it), the server detects the duplicate use. On detecting reuse, revoke the entire family — this logs out both the attacker and the legitimate user, which is the safest response. The legitimate user must re-authenticate, which they can do; the attacker loses access.

## Section 3: Authorization Patterns

**Q7. What is Role-Based Access Control (RBAC), and how do you implement it in a NestJS microservice?**
A: RBAC assigns permissions to roles, and roles to users. Instead of checking `userId === 'admin-uuid'`, you check `user.roles.includes('admin')`. Roles aggregate permissions into named groups (`customer`, `agent`, `admin`, `auditor`).

In NestJS, RBAC is typically implemented with a custom decorator and guard:

```typescript
// roles.decorator.ts
import { SetMetadata } from '@nestjs/common';
export const Roles = (...roles: string[]) => SetMetadata('roles', roles);

// roles.guard.ts
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.getAllAndOverride<string[]>('roles', [
      context.getHandler(),
      context.getClass(),
    ]);

    if (!requiredRoles || requiredRoles.length === 0) {
      return true; // No roles required = any authenticated user
    }

    const { user } = context.switchToHttp().getRequest();
    if (!user) return false;

    const hasRole = requiredRoles.some(role => user.roles?.includes(role));
    if (!hasRole) {
      throw new ForbiddenException(
        `Access denied. Required roles: [${requiredRoles.join(', ')}]`
      );
    }
    return true;
  }
}

// controller usage
@Controller('admin')
@UseGuards(JwtAuthGuard, RolesGuard)
export class AdminController {

  @Post('write-off-loan')
  @Roles('admin', 'credit-manager')
  writeOffLoan(@Body() dto: WriteOffDto, @Req() req) {
    return this.loanService.writeOff(dto.loanId, req.user.userId);
  }

  @Get('audit-log')
  @Roles('admin', 'auditor')
  getAuditLog() {
    return this.auditService.getLogs();
  }
}
```

Guard ordering matters: `JwtAuthGuard` runs first (AuthN), then `RolesGuard` (AuthZ). If `JwtAuthGuard` fails, `RolesGuard` never runs. Apply them globally for all routes via the module or at the controller level for scoped protection.

**Q8. What is Attribute-Based Access Control (ABAC), and when is it more appropriate than RBAC?**
A: ABAC makes access decisions based on attributes of the subject (user), resource, action, and environment — not just the user's role. It handles the cases RBAC can't express cleanly:

```
RBAC: "Can this role perform this action on this resource type?"
ABAC: "Can this user with these attributes perform this action on this specific resource instance given the current context?"
```

RBAC limitation — consider a lending platform:
- An `agent` role can view loan applications.
- But agents should only view applications assigned to them, not all applications in the system.
- They can also approve loans up to ₹100,000, but not above.
- And only during business hours (09:00–18:00 IST).

Encoding all of this in RBAC requires creating increasingly granular roles (`agent-small-loans`, `agent-large-loans`, `senior-agent`), and the rules are scattered across multiple role definitions. ABAC expresses it as a unified policy:

```typescript
// OPA (Open Policy Agent) Rego policy for loan approval
package loans.authz

default allow = false

allow {
  input.action == "approve_loan"
  input.user.role == "agent"
  input.resource.assignedAgentId == input.user.id       # Must be assigned to this agent
  input.resource.amount <= 100000                        # Amount within agent limit
  is_business_hours                                      # Environment attribute
}

is_business_hours {
  hour := time.clock(time.now_ns())[0]
  hour >= 9
  hour < 18
}
```

```typescript
// NestJS service calling OPA for authorization
async canApprove(user: User, loan: Loan): Promise<boolean> {
  const response = await this.opaClient.evaluate('loans/authz', {
    action: 'approve_loan',
    user: { id: user.id, role: user.role, tier: user.agentTier },
    resource: {
      assignedAgentId: loan.assignedAgentId,
      amount: loan.amount,
      status: loan.status,
    },
  });
  return response.result.allow;
}
```

Use ABAC when: authorization rules depend on resource attributes (ownership, amount, status), environmental context (time, IP, device), or combinations that would require an explosion of roles in a pure RBAC system. Most mature systems use RBAC + ABAC together: RBAC for coarse-grained route-level checks, ABAC for fine-grained object-level decisions.

**Q9. What is the BOLA/IDOR vulnerability, and what is the Terraform-agnostic code pattern to prevent it?**
A: BOLA (Broken Object-Level Authorization) / IDOR (Insecure Direct Object Reference) occurs when the server uses a caller-supplied ID to fetch a resource without verifying the caller owns or has access to that resource. It's OWASP API Security Top 10 #1 — the most common API vulnerability.

Vulnerable pattern:
```typescript
// VULNERABLE — trusts the caller-supplied loanId
@Get(':loanId')
async getLoan(@Param('loanId') loanId: string) {
  return this.loanService.findById(loanId); // No ownership check
}

// Service
async findById(loanId: string) {
  return this.db.loans.findOne({ id: loanId }); // ← Fetches ANY loan
}
```

Safe pattern — always scope queries to the authenticated user's identity:
```typescript
// SAFE — scope query to authenticated user
@Get(':loanId')
@UseGuards(JwtAuthGuard)
async getLoan(
  @Param('loanId') loanId: string,
  @Req() req: RequestWithUser
) {
  return this.loanService.findByIdForUser(loanId, req.user.userId);
}

// Service — ownership enforced at the DB query level, not application level
async findByIdForUser(loanId: string, userId: string) {
  const loan = await this.db.loans.findOne({
    id: loanId,
    userId: userId,  // ← The DB enforces ownership; app code can't forget it
  });

  if (!loan) {
    // Return 404, not 403 — don't reveal the resource exists to unauthorized callers
    throw new NotFoundException('Loan not found');
  }

  return loan;
}
```

Two critical details:
1. **Enforce ownership at the database query level**, not after fetching: `findOne({ id, userId })` — if the record doesn't match both conditions, it returns null. Don't do `findOne({ id })` followed by `if (loan.userId !== userId) throw 403` — that's a TOCTOU risk and is also verbose.
2. **Return 404, not 403**, when a resource exists but belongs to someone else. Returning 403 tells the attacker the resource exists; 404 reveals nothing. This is the "security through ambiguity" exception that's actually good practice.

For multi-tenant fintech systems, add `tenantId` as a third scope constraint alongside `userId`.

## Section 4: Token Storage, Transport, and Common Mistakes

**Q10. Where should JWTs be stored on the client side, and what are the security trade-offs of localStorage vs. HttpOnly cookies?**
A: This is one of the most debated frontend security questions. The two options:

**localStorage / sessionStorage:**
- Accessible via JavaScript — vulnerable to XSS. If any script on the page (including a compromised third-party dependency) runs `localStorage.getItem('token')`, the token is stolen.
- Simple to implement — set and read directly.
- Not sent automatically by the browser — developer controls when the token is sent (in the `Authorization: Bearer` header).
- XSS → token theft → account takeover. No mitigation short of preventing all XSS.

**HttpOnly cookies:**
- Not accessible via JavaScript — XSS cannot read the token.
- Sent automatically by the browser on every request to the matching domain.
- Vulnerable to CSRF — if an attacker tricks the victim's browser into making a request to your API, the cookie is sent automatically. Mitigate with `SameSite=Strict` or `SameSite=Lax` cookie attribute, and/or double-submit CSRF tokens.
- Requires `Secure` attribute (HTTPS only) and careful `Domain`/`Path` scoping.

```javascript
// Server setting a secure HttpOnly cookie
res.cookie('access_token', jwt, {
  httpOnly: true,       // Not accessible via document.cookie
  secure: true,         // HTTPS only
  sameSite: 'strict',   // No cross-site requests carry this cookie (blocks CSRF)
  maxAge: 15 * 60 * 1000, // 15 minutes in ms
  path: '/api',         // Only sent to /api/* routes
});
```

The current consensus: **HttpOnly cookies with `SameSite=Strict` and `Secure`** is safer than localStorage for most browser-based applications. XSS is more common and more exploitable than CSRF, and `SameSite=Strict` eliminates the main CSRF attack surface. For SPAs that must call cross-origin APIs, `SameSite=None; Secure` with a CSRF token header is the pragmatic middle ground.

**Q11. What is the `Authorization` header format, and what mistakes are common when reading it in middleware?**
A: The `Authorization` header uses the format: `Authorization: <scheme> <credentials>`. For bearer tokens: `Authorization: Bearer <jwt>`.

Common middleware mistakes:

```typescript
// MISTAKE 1 — Not handling missing header
const token = req.headers.authorization.split(' ')[1]; // TypeError if header is absent

// MISTAKE 2 — Not validating the scheme
const parts = req.headers.authorization.split(' ');
const token = parts[1]; // Would accept "Basic dXNlcjpwYXNz" and try to parse as JWT

// MISTAKE 3 — Case-sensitive header name
const token = req.headers['Authorization']; // HTTP/2 headers are lowercase; this is undefined

// CORRECT
extractToken(req: Request): string | null {
  const header = req.headers['authorization']; // lowercase always
  if (!header) return null;

  const parts = header.split(' ');
  if (parts.length !== 2 || parts[0].toLowerCase() !== 'bearer') {
    return null; // Return null; let AuthN guard throw 401
  }

  return parts[1];
}
```

Additional: don't log the `Authorization` header in access logs or error traces — it's a credential. Mask it before logging: `req.headers.authorization = '[REDACTED]'` before passing to your logger.

**Q12. What is token scope in OAuth2, and how does it differ from roles in RBAC?**
A: OAuth2 scopes and application roles solve overlapping but distinct problems. Scopes are permissions granted to a **client application** (what the app is allowed to do on behalf of the user). Roles are permissions granted to a **user** (what the user is allowed to do).

```
Scope: "payments:read payments:write" — this CLIENT APP can read and write payments
Role: "agent" — this USER has agent-level access

Combined check: "Can this client app (scope: payments:write) perform this action on behalf of
                 this user (role: agent) who owns this resource?"
```

In practice for a fintech B2B API:

```typescript
// JWT payload combining both
{
  "sub": "user-uuid",
  "roles": ["agent"],          // What the user can do
  "scope": "loans:read",       // What this OAuth2 client is allowed to do
  "client_id": "partner-app-x",
  "iss": "https://auth.myorg.internal",
  "exp": 1723456789
}

// AuthZ check must satisfy BOTH
async canReadLoan(user: JwtPayload, loan: Loan): boolean {
  const hasScope = user.scope?.split(' ').includes('loans:read');
  const hasRole  = user.roles?.includes('agent') || user.roles?.includes('admin');
  const ownsLoan = loan.assignedAgentId === user.sub;

  return hasScope && hasRole && ownsLoan;
}
```

If a partner application has `scope: loans:read` but the user only has `role: customer`, the customer cannot read other customers' loans even if the app has the scope. Scopes constrain what the client can request; roles constrain what the user can approve. Both must be satisfied.

## Section 5: Multi-Tenant and Microservice Authorization

**Q13. How do you enforce tenant isolation in a multi-tenant fintech API at the database query level?**
A: In a multi-tenant system (multiple lenders or partners sharing the same deployment), `tenantId` must be a mandatory scope on every query. The safest pattern is to make it structurally impossible to query without it:

```typescript
// Tenant-scoped repository pattern
@Injectable()
export class LoanRepository {
  constructor(private readonly db: Database) {}

  // All public methods require tenantId — no escape hatch
  async findById(tenantId: string, loanId: string): Promise<Loan | null> {
    return this.db.loans.findOne({
      id: loanId,
      tenantId: tenantId,  // Always scoped
    });
  }

  async findByUser(tenantId: string, userId: string): Promise<Loan[]> {
    return this.db.loans.find({
      tenantId: tenantId,
      userId: userId,
    });
  }

  // No public findAll() — would return cross-tenant data
}

// Controller extracts tenantId from the verified JWT, never from the request body or params
@Get(':loanId')
async getLoan(@Param('loanId') loanId: string, @Req() req: RequestWithUser) {
  // tenantId comes from the JWT claim — not from req.query or req.body
  return this.loanRepository.findById(req.user.tenantId, loanId);
}
```

The key principle: **`tenantId` must come from the verified JWT**, not from the request (URL param, query string, or body). If a caller can supply their own `tenantId`, they can access any tenant's data by supplying a different one. The JWT is signed by your auth service — the `tenantId` claim inside it cannot be forged without the private key.

For Postgres specifically, Row Level Security (RLS) provides a database-enforced backstop:

```sql
-- RLS policy: queries only see rows matching the current_setting tenant
ALTER TABLE loans ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON loans
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

-- Application sets the tenant context before querying
SET LOCAL app.current_tenant_id = 'tenant-uuid-here';
SELECT * FROM loans WHERE id = 'loan-uuid'; -- RLS filters to tenant automatically
```

RLS is a defense-in-depth layer — even if the application code forgets `tenantId` in a query, Postgres enforces it. It doesn't replace application-level checks; it catches the mistakes that slip through.

**Q14. How does authorization work across microservices — should each service re-verify the JWT independently, or should a gateway handle it?**
A: Both, at different layers, for different reasons:

```
Client
  │
  ▼
API Gateway (Kong / AWS API GW / custom)
  │  ✓ Verifies JWT signature and expiry      ← Fast rejection of invalid tokens
  │  ✓ Rate limiting, TLS termination
  │  ✓ Injects verified claims as headers      ← Downstream trusts these headers
  │    X-User-ID: user-uuid
  │    X-User-Roles: agent,viewer
  │    X-Tenant-ID: tenant-uuid
  │
  ├──▶ Loans Service
  │       ✓ Trusts gateway-injected headers (no re-verification needed)
  │       ✓ Enforces object-level AuthZ (loan ownership)
  │       ✓ Enforces business rules (agent can only approve assigned loans)
  │
  ├──▶ Payments Service
  │       ✓ Trusts gateway-injected headers
  │       ✓ Enforces payment ownership and limits
  │
  └──▶ Notification Service
          ✓ Trusts gateway-injected headers
          ✓ Only sends to userId matching the notification's target
```

The gateway handles AuthN (signature verification) once. Downstream services handle AuthZ (object-level, business rules) based on the trusted injected headers — they skip re-verifying the JWT cryptographically since that was done at the gateway.

Critical security requirement: **downstream services must not be reachable directly** — only via the gateway. If a service is directly accessible, an attacker can supply fake `X-User-Roles: admin` headers and bypass all authorization. Enforce this with network policy (security groups, service mesh mTLS, private subnets with no public routing). Services that are reachable only from within the cluster VPC via the gateway cannot receive forged headers from external callers.

**Q15. What is mTLS (mutual TLS), and how does it complement AuthN/AuthZ in a microservices mesh?**
A: Standard TLS authenticates the server to the client. mTLS adds client authentication — both parties present certificates. In a microservices context, mTLS answers: "Is this HTTP request actually coming from the loans-service, or could it be a rogue process that gained network access?"

```
Without mTLS:
  Any process that can reach payments-service:8080 can send requests.
  Authorization relies entirely on application-level JWT checks.

With mTLS:
  Only processes with a certificate signed by the internal CA can connect.
  The payments-service rejects TLS handshakes from uncertified callers.
  JWT checks still run — mTLS handles service identity; JWT handles user identity.
```

In a service mesh (Istio, Linkerd), mTLS is enforced transparently:

```yaml
# Istio PeerAuthentication — enforce mTLS for the entire namespace
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: fintech-prod
spec:
  mtls:
    mode: STRICT  # Reject any non-mTLS connection

---
# AuthorizationPolicy — only loans-service can call payments-service
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: payments-allow-loans
  namespace: fintech-prod
spec:
  selector:
    matchLabels:
      app: payments-service
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/fintech-prod/sa/loans-service"]
```

mTLS provides **service-to-service AuthN**. The `AuthorizationPolicy` provides **service-to-service AuthZ**. User-facing JWT handles **user AuthN and AuthZ**. These are three distinct layers that complement rather than replace each other.

## Section 6: Advanced Patterns and Failure Scenarios

**Q16. Scenario: "A user resets their password. How do you immediately invalidate all their existing JWTs without a full token blacklist?"**
A: Pure stateless JWTs have no native revocation mechanism — you'd normally wait for expiry. Three approaches ranked by trade-off:

**Approach 1 — Short access token lifetime (15 min) + refresh token revocation:**
On password reset, revoke all refresh tokens for the user in the database. Existing access tokens continue to work for up to 15 minutes. Acceptable for most applications — the attack window after password reset is small.

**Approach 2 — Per-user secret versioning:**
Add a `tokenVersion` (or `passwordChangedAt` timestamp) to the user record. Embed the version in the JWT at issuance time. Validate on every request:

```typescript
// JWT payload
{ sub: userId, tokenVersion: 3, exp: ... }

// Validation in JwtStrategy
async validate(payload: JwtPayload) {
  const user = await this.userService.findById(payload.sub);

  // If user's version has been incremented (password reset, forced logout),
  // all tokens with old version are immediately invalid
  if (user.tokenVersion !== payload.tokenVersion) {
    throw new UnauthorizedException('Token invalidated — please log in again');
  }

  return user;
}

// On password reset
await this.userService.incrementTokenVersion(userId);
// All issued JWTs with the old tokenVersion are now rejected — no blacklist needed
```

This requires one DB read per request (to check `tokenVersion`) — partially losing the stateless benefit of JWTs. But it's a single indexed primary key lookup — much cheaper than a full blacklist scan.

**Approach 3 — Redis-backed token blacklist by `jti`:**
Every JWT gets a unique `jti` (JWT ID) claim. On revocation event (password reset, logout, compromise), write the `jti` to Redis with TTL set to the token's remaining lifetime. Check Redis on every request:

```typescript
async revokeAllUserTokens(userId: string) {
  const activeJtis = await this.db.activeJtis.findAll({ userId });
  for (const { jti, expiresAt } of activeJtis) {
    const ttl = expiresAt.getTime() - Date.now();
    await this.redis.set(`blacklist:${jti}`, '1', 'PX', ttl);
  }
}
```

This requires tracking issued JTIs — partially stateful — but Redis lookup is sub-millisecond and the key expires automatically when the token would have expired anyway. The blacklist doesn't grow unboundedly. This is the pattern used when immediate, guaranteed revocation is required (financial platforms, security incidents).

**Q17. Scenario: "During a security audit, the auditor finds that your API returns different HTTP status codes for 'resource not found' vs 'resource found but you don't own it'. Why is this a problem and how do you fix it?"**
A: Returning 403 for an existing-but-unauthorized resource and 404 for a non-existent resource leaks information about which resource IDs exist in your system. An attacker can enumerate valid loan IDs, user IDs, or account numbers by observing the difference:

```
GET /api/loans/10001 → 404 (doesn't exist)
GET /api/loans/10002 → 403 (exists, not yours)  ← confirms 10002 is a real loan
GET /api/loans/10003 → 403 (exists, not yours)  ← confirms 10003 is a real loan
GET /api/loans/10004 → 404 (doesn't exist)
```

In fintech, knowing which loan IDs or account numbers exist is itself sensitive — it can reveal customer counts, ID generation patterns, and confirm whether a specific person has a loan with you.

The fix — always return 404 when the caller should not access the resource, whether it doesn't exist or they don't own it:

```typescript
async findByIdForUser(loanId: string, userId: string): Promise<Loan> {
  const loan = await this.db.loans.findOne({
    id: loanId,
    userId: userId,
  });

  // Single query, single branch — both "not found" and "not yours" return 404
  if (!loan) {
    throw new NotFoundException('Loan not found');
  }

  return loan;
}
```

The `WHERE id = ? AND userId = ?` query returns null for both cases — the code path is identical, and the response is identical. This is the correct behavior. The only time to return 403 instead of 404 is when the caller is expected to know the resource exists — for example, an admin viewing a resource they don't have a specific role for. For end-user APIs, 404 is always the safer choice.

**Q18. What are the OWASP API Security Top 10 issues most directly related to AuthN and AuthZ, and how does each manifest in a Node.js API?**
A: Five of the OWASP API Security Top 10 are directly AuthN/AuthZ failures:

**API1: Broken Object-Level Authorization (BOLA)** — covered in Q9. Missing ownership check on resource fetch. Fix: always include the caller's `userId`/`tenantId` in the database query.

**API2: Broken Authentication** — weak tokens, missing expiry validation, `alg: none` vulnerability, no rate limiting on login endpoints, predictable token formats. Fix: RS256 with proper claim validation, bcrypt for passwords, rate limiting on `/auth/login` and `/auth/refresh`.

**API3: Broken Object Property-Level Authorization** — returning fields the caller's role shouldn't see (covered in Q3 field-level example). Fix: response DTOs scoped per role using class-transformer:

```typescript
// Different serialization per role
class LoanResponseCustomer {
  @Expose() loanId: string;
  @Expose() amount: number;
  @Expose() status: string;
  // internalCreditScore, fraudRiskLabel NOT exposed
}

class LoanResponseAdmin {
  @Expose() loanId: string;
  @Expose() amount: number;
  @Expose() status: string;
  @Expose() internalCreditScore: number;  // Admin only
  @Expose() fraudRiskLabel: string;       // Admin only
}

// Controller
const dtoClass = req.user.roles.includes('admin')
  ? LoanResponseAdmin
  : LoanResponseCustomer;
return plainToInstance(dtoClass, loan, { excludeExtraneousValues: true });
```

**API5: Broken Function-Level Authorization** — route-level missing role checks (the `/admin/` route example from Q3). Fix: global AuthN guard + per-route `@Roles()` decorator, with tests that verify 403 responses for each role that should be denied.

**API6: Unrestricted Access to Sensitive Business Flows** — no rate limiting on OTP endpoints, allowing unlimited PIN attempts, mass assignment on loan applications. Fix: Redis-backed rate limiting per IP and per userId, explicit allowlists for mass-assignment (never trust `req.body` directly).

## Quick Reference Table

| Concept | AuthN | AuthZ |
|---|---|---|
| Question answered | Who are you? | What can you do? |
| HTTP status on failure | 401 Unauthorized | 403 Forbidden |
| Happens at | Token/credential validation | Permission/ownership check |
| Handles | Token signature, expiry, issuer | Roles, ownership, attributes |
| Common failure | Missing/invalid token accepted | Valid token, wrong resource accessed |
| OWASP category | API2: Broken Authentication | API1: BOLA, API5: Broken Function-Level AuthZ |
| Implementation | JwtAuthGuard / Passport strategy | RolesGuard, ABAC policy, DB-level ownership filter |
| Token type | JWT (access token) | JWT claims (roles, tenantId, scope) |
| Revocation | Blacklist / tokenVersion / short TTL | N/A (stateless permission model) |
| Microservice pattern | Gateway verifies once | Each service enforces ownership |
