# Security (Authentication): Multi-Factor Authentication — TOTP & SMS OTP — Interview Q&A (5 YOE Level)

---

## Section 1: MFA Fundamentals

**Q1. What is multi-factor authentication, and what threat model does it address?**
A: Multi-factor authentication (MFA) requires a user to present credentials from two or more distinct categories before access is granted:
- **Something you know** — password, PIN.
- **Something you have** — a phone running an authenticator app, a hardware token, a SIM card.
- **Something you are** — biometrics (fingerprint, face).

The threat model MFA addresses is **credential compromise without device compromise**. A password breach (database dump, phishing, credential stuffing) gives an attacker the "something you know" factor but not the "something you have." Without both factors, authentication fails. MFA does *not* protect against: a fully compromised device (attacker has both factors), real-time phishing (attacker relays the OTP before it expires), SIM-swap attacks (transfers the "have" factor to the attacker's SIM), or malware that intercepts the second factor on-device.

In fintech, MFA is mandated for customer-facing login, high-value transaction authorization, and admin access by RBI guidelines (Master Direction on Digital Payment Security Controls) and PCI-DSS Requirement 8.4 — it's not optional for regulated applications.

**Q2. What are the main second-factor mechanisms, and how do they compare on security and usability?**
A:

| Factor | Mechanism | Phishing-resistant | SIM-swap risk | UX friction | Offline capable |
|---|---|---|---|---|---|
| TOTP (authenticator app) | HMAC-based time OTP | Partial (OTP replayable in window) | No | Low | Yes |
| SMS OTP | One-time code via SMS | No | Yes | Medium | No |
| Push notification | Approve/deny on phone | Partial | No | Very low | No |
| FIDO2 / WebAuthn | Hardware key or platform authenticator | Yes (origin-bound) | No | Very low | Yes |
| Hardware TOTP token | Dedicated device (YubiKey OTP mode) | Partial | No | Medium | Yes |

TOTP and SMS OTP are the two most widely implemented factors in consumer-facing fintech products — TOTP for security-conscious users and internal/admin access, SMS OTP for broad consumer reachability (India's mobile-first market). WebAuthn is the gold standard for phishing resistance but has adoption and device coverage constraints. SMS OTP is the weakest but most accessible — understand the trade-offs clearly.

**Q3. What is a one-time password (OTP), and what makes it "one-time"?**
A: An OTP is a code valid for a single use or a single time window, derived from a shared secret and either a counter (HOTP) or the current time (TOTP). It's "one-time" in two senses:
- **Time-bound** (TOTP) — the code is only valid within a short window (30 seconds by default). A captured code is useless after the window expires.
- **Use-once** (enforced by the server) — once a code is successfully verified, the server marks it as used and rejects any replay of the same code within the same window. Both properties together prevent replay attacks.

The OTP is derived from the shared secret — it proves the user possesses the secret without transmitting it. This is fundamentally different from a password, where the credential itself (or its hash) must be stored and compared.

## Section 2: TOTP — How It Works

**Q4. Walk through the TOTP algorithm (RFC 6238) from shared secret to 6-digit code.**
A: TOTP builds on HOTP (RFC 4226), replacing the counter with a time-based counter derived from the current Unix timestamp.

**Step 1 — Time counter:**
```
T = floor(Unix timestamp / time_step)
  = floor(1723456789 / 30)
  = 57448559          ← changes every 30 seconds
```

**Step 2 — HOTP: HMAC-SHA1 of the counter:**
```
HMAC = HMAC-SHA1(secret, T)   ← secret is the raw bytes of the Base32-decoded key
                               ← T is encoded as an 8-byte big-endian integer
```
HMAC-SHA1 produces 20 bytes.

**Step 3 — Dynamic truncation:**
```
offset  = HMAC[19] & 0x0F           ← last nibble of the HMAC
P       = HMAC[offset..offset+3]    ← 4 bytes starting at offset
code    = (P as 31-bit int) % 10^6  ← 6-digit code (0-padded if needed)
```

The truncation is designed so the code is derived from a uniformly distributed subset of the HMAC, reducing bias. The 31-bit mask (`& 0x7FFFFFFF`) strips the sign bit for cross-platform consistency.

**Step 4 — Result:** a 6-digit decimal code that changes every 30 seconds, derived deterministically from the shared secret and the current time window.

**Q5. What is the shared secret in TOTP, how is it generated, and how does it get onto the user's device?**
A: The shared secret is a randomly generated sequence of bytes — typically 20 bytes (160 bits), encoded as a Base32 string for human readability and QR code inclusion. It must come from a CSPRNG:

```typescript
import { authenticator } from 'otplib';
import crypto from 'node:crypto';

function generateTotpSecret(): string {
  // otplib uses crypto.randomBytes internally; you can also generate manually:
  const rawBytes = crypto.randomBytes(20);  // 160 bits
  // Base32-encode: otplib handles this
  return authenticator.generateSecret(20);  // returns a Base32 string like "JBSWY3DPEHPK3PXP"
}
```

The secret reaches the device through a **provisioning URI** (RFC 6238 / Google Authenticator protocol), typically displayed as a QR code:

```
otpauth://totp/MyApp:user@example.com?secret=JBSWY3DPEHPK3PXP&issuer=MyApp&algorithm=SHA1&digits=6&period=30
```

The user scans this QR code with an authenticator app (Google Authenticator, Authy, 1Password, Microsoft Authenticator). The app stores the secret locally and begins generating codes. The server also stores the secret (encrypted in the database) and uses it for verification. After provisioning, the QR code and raw secret are never shown again — they represent a permanent credential.

**Q6. How do you implement TOTP setup (enrollment) in a Node.js/NestJS backend?**
A:
```typescript
// totp.service.ts
import { Injectable } from '@nestjs/common';
import { authenticator } from 'otplib';
import * as qrcode from 'qrcode';
import { InjectRepository } from '@nestjs/typeorm';
import { UsersRepository } from './users.repository';
import { EncryptionService } from '../crypto/encryption.service';

@Injectable()
export class TotpService {
  constructor(
    @InjectRepository(UsersRepository)
    private readonly users: UsersRepository,
    private readonly encryption: EncryptionService,
  ) {}

  /**
   * Step 1 of TOTP enrollment: generate a secret and return the QR code.
   * The secret is NOT yet active — the user must verify a code first (Q7).
   */
  async beginEnrollment(userId: string): Promise<{ qrDataUrl: string; manualKey: string }> {
    const secret = authenticator.generateSecret(20);
    const user   = await this.users.findOneOrFail(userId);

    // Build the provisioning URI
    const otpauthUrl = authenticator.keyuri(user.email, 'LoansPlatform', secret);

    // Generate QR code as a data URL (PNG, base64) for the frontend to display
    const qrDataUrl = await qrcode.toDataURL(otpauthUrl);

    // Store the secret temporarily, encrypted, NOT yet marked as verified
    // Overwrite any previous pending secret
    await this.users.update(userId, {
      totp_secret_pending:  this.encryption.encrypt(secret),
      totp_secret_verified: false,
    });

    // Return the manual entry key for users who can't scan QR codes
    // Format it in groups of 4 for readability: JBSW Y3DP EHPK 3PXP
    const manualKey = secret.match(/.{1,4}/g)!.join(' ');

    return { qrDataUrl, manualKey };
  }
}
```

**Q7. How do you implement TOTP verification (and why do you verify before completing enrollment)?**
A: You verify a code from the user's authenticator app *before* marking TOTP as active on their account. This confirms: (1) the app successfully received and stored the secret, and (2) the user's device clock is reasonably synchronized with the server. Without this step, a typo in the secret or a failed QR scan silently locks the user out — they'd have MFA "enabled" but no working authenticator.

```typescript
// totp.service.ts (continued)

/**
 * Step 2 of enrollment: verify a test code before activating TOTP.
 * Also used for every subsequent TOTP challenge during login.
 */
async verifyAndActivate(userId: string, userCode: string): Promise<boolean> {
  const user = await this.users.findOneOrFail(userId);

  if (!user.totp_secret_pending) {
    throw new BadRequestException('No pending TOTP enrollment found');
  }

  const secret = this.encryption.decrypt(user.totp_secret_pending);

  // otplib checks the current window ± drift window (default ± 1 window = ± 30s)
  const isValid = authenticator.verify({ token: userCode, secret });

  if (!isValid) return false;

  // Promote pending → active
  await this.users.update(userId, {
    totp_secret:          user.totp_secret_pending,  // already encrypted
    totp_secret_pending:  null,
    totp_secret_verified: true,
    totp_enabled_at:      new Date(),
  });

  // Generate and return backup codes (Q11)
  await this.generateBackupCodes(userId);

  return true;
}

/**
 * Verify a TOTP code during login (after password is correct).
 * Includes replay protection.
 */
async verifyLogin(userId: string, userCode: string): Promise<boolean> {
  const user = await this.users.findOneOrFail(userId);

  if (!user.totp_enabled) return false;

  const secret = this.encryption.decrypt(user.totp_secret);

  // Check replay: has this exact code been used in the current window?
  const windowKey = `totp:used:${userId}:${userCode}`;
  const alreadyUsed = await this.redis.exists(windowKey);
  if (alreadyUsed) return false;  // replay attempt

  const isValid = authenticator.verify({ token: userCode, secret });
  if (!isValid) return false;

  // Mark this code as used for the current window (TTL = 1 window = 30s)
  await this.redis.setex(windowKey, 30, '1');

  return true;
}
```

**Q8. What is TOTP clock drift, and how do you handle it without compromising security?**
A: TOTP codes are time-based — the server and the authenticator app must agree on the current time to generate the same code. In practice, device clocks drift. A user whose phone is 45 seconds behind will present a code for the previous time window, which the server (using current time) won't recognize.

The standard mitigation is a **window tolerance** — the server also checks the code against N adjacent time windows (the previous and the next, in addition to the current). `otplib`'s default is `window: 1`, meaning it checks 3 windows: `T-1`, `T`, `T+1` — a ±30-second tolerance:

```typescript
authenticator.options = { window: 1 };  // check current ± 1 window
```

The trade-off: a larger window widens the replay attack surface. At `window: 1`, a code is valid for up to 90 seconds (its own 30s window + 30s of look-ahead). Allowing `window: 2` extends this to 150 seconds — more lenient but longer replay window. Most implementations use `window: 1`. For users with persistently drifted clocks, detect and log the drift delta so you can prompt them to sync their device time rather than silently increasing the window.

**Q9. How do you store the TOTP secret securely in the database?**
A: The TOTP secret is a long-lived symmetric credential — it must never be stored in plaintext. Unlike passwords (hashed one-way), TOTP secrets must be *recoverable* by the server for code verification — so one-way hashing is not an option. The correct approach is authenticated encryption:

```typescript
// encryption.service.ts — AES-256-GCM via AWS KMS Data Key
import { Injectable } from '@nestjs/common';
import { KMSClient, GenerateDataKeyCommand, DecryptCommand } from '@aws-sdk/client-kms';
import crypto from 'node:crypto';

@Injectable()
export class EncryptionService {
  private readonly kms = new KMSClient({ region: 'ap-south-1' });
  private readonly keyId = process.env.KMS_KEY_ID!;

  async encrypt(plaintext: string): Promise<string> {
    // Generate a data key from KMS (envelope encryption)
    const { Plaintext, CiphertextBlob } = await this.kms.send(
      new GenerateDataKeyCommand({ KeyId: this.keyId, KeySpec: 'AES_256' })
    );

    const iv         = crypto.randomBytes(12);            // 96-bit IV for GCM
    const cipher     = crypto.createCipheriv('aes-256-gcm', Plaintext!, iv);
    const encrypted  = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
    const authTag    = cipher.getAuthTag();               // 16-byte GCM auth tag

    // Store: base64(encryptedDataKey):base64(iv):base64(authTag):base64(ciphertext)
    return [
      Buffer.from(CiphertextBlob!).toString('base64'),
      iv.toString('base64'),
      authTag.toString('base64'),
      encrypted.toString('base64'),
    ].join(':');
  }

  async decrypt(stored: string): Promise<string> {
    const [encDataKey, ivB64, authTagB64, ciphertextB64] = stored.split(':');

    // Decrypt the data key using KMS
    const { Plaintext } = await this.kms.send(
      new DecryptCommand({ CiphertextBlob: Buffer.from(encDataKey, 'base64') })
    );

    const decipher = crypto.createDecipheriv(
      'aes-256-gcm',
      Plaintext!,
      Buffer.from(ivB64, 'base64')
    );
    decipher.setAuthTag(Buffer.from(authTagB64, 'base64'));

    return decipher.update(Buffer.from(ciphertextB64, 'base64')) + decipher.final('utf8');
  }
}
```

Key design choices: AES-256-GCM provides authenticated encryption (detects tampering via the auth tag). Envelope encryption (KMS data key) means the raw AES key is never stored anywhere — only the KMS-encrypted form. Even a full database breach gives the attacker only ciphertext they can't decrypt without KMS access. This is mandatory for PCI-DSS (Req 3.5) and RBI data protection requirements.

## Section 3: SMS OTP — How It Works

**Q10. How does SMS OTP work, and what are its architectural components?**
A: SMS OTP is a challenge-response mechanism:

```
User submits phone number / triggers OTP request
         │
         ▼
Backend generates a random N-digit code (typically 6 digits)
         │
         ├──► Stores: hash(code) + phone + expiry + attempt_count in cache (Redis)
         │
         └──► Sends SMS via provider (Twilio, AWS SNS, Kaleyra, MSG91)
                       │
                       ▼
              User receives SMS: "Your OTP is 482917. Valid for 10 minutes."
                       │
                       ▼
              User submits code to backend
                       │
                       ▼
Backend: hash(submitted) == stored hash? + not expired? + attempts < max?
         │                   │
       Valid               Invalid
         │                   │
   Grant access        Increment attempt_count / lock
```

Components: a Redis cache for OTP storage (short TTL, no need for durable DB writes per OTP), an SMS gateway provider with DLR (delivery receipt) support, and rate limiting at the send and verify endpoints.

**Q11. How do you generate and store an SMS OTP securely?**
A:
```typescript
// sms-otp.service.ts
import { Injectable } from '@nestjs/common';
import crypto from 'node:crypto';
import { RedisService } from '../redis/redis.service';
import { SmsGatewayService } from '../sms/sms-gateway.service';

@Injectable()
export class SmsOtpService {
  private readonly OTP_LENGTH      = 6;
  private readonly OTP_TTL_SECONDS = 600;   // 10 minutes
  private readonly MAX_ATTEMPTS    = 3;
  private readonly RESEND_COOLDOWN = 60;    // 1 minute between resends

  constructor(
    private readonly redis: RedisService,
    private readonly sms: SmsGatewayService,
  ) {}

  /**
   * Generate a cryptographically secure numeric OTP.
   * Uses rejection sampling to avoid modulo bias.
   */
  private generateOtp(): string {
    const max    = 10 ** this.OTP_LENGTH;  // 1_000_000 for 6 digits
    let   value: number;

    do {
      // Generate random 4 bytes = 32 bits; max needed is ~20 bits for 6 digits
      // Rejection sampling: retry if value >= floor(2^32 / max) * max
      // to ensure uniform distribution
      const buf = crypto.randomBytes(4);
      value = buf.readUInt32BE(0);
    } while (value >= Math.floor(0xFFFFFFFF / max) * max);

    return String(value % max).padStart(this.OTP_LENGTH, '0');
  }

  /**
   * Hash the OTP before storing — same principle as API keys.
   * Prevents OTP recovery from a Redis breach.
   */
  private hashOtp(otp: string, phone: string): string {
    // Include phone in the hash to prevent cross-account substitution attacks
    return crypto
      .createHmac('sha256', process.env.OTP_HMAC_SECRET!)
      .update(`${phone}:${otp}`)
      .digest('hex');
  }

  async sendOtp(phone: string, purpose: string): Promise<void> {
    // Enforce resend cooldown
    const cooldownKey = `otp:cooldown:${phone}:${purpose}`;
    if (await this.redis.exists(cooldownKey)) {
      throw new TooManyRequestsException('Please wait before requesting another OTP');
    }

    const otp     = this.generateOtp();
    const hash    = this.hashOtp(otp, phone);
    const storeKey = `otp:${purpose}:${phone}`;

    // Store hash, not plaintext OTP
    await this.redis.setex(storeKey, this.OTP_TTL_SECONDS, JSON.stringify({
      hash,
      attempts: 0,
      created_at: Date.now(),
    }));

    // Set resend cooldown
    await this.redis.setex(cooldownKey, this.RESEND_COOLDOWN, '1');

    // Send SMS (fire; handle delivery failures asynchronously)
    await this.sms.send(phone, `Your OTP for ${purpose} is ${otp}. Valid for 10 minutes. Do not share.`);
  }

  async verifyOtp(phone: string, purpose: string, submitted: string): Promise<boolean> {
    const storeKey = `otp:${purpose}:${phone}`;
    const raw      = await this.redis.get(storeKey);

    if (!raw) return false;  // expired or never sent

    const stored = JSON.parse(raw) as { hash: string; attempts: number; created_at: number };

    // Check attempt count before hashing to avoid unnecessary computation
    if (stored.attempts >= this.MAX_ATTEMPTS) {
      await this.redis.del(storeKey);  // invalidate after max attempts
      throw new UnauthorizedException('Too many incorrect attempts. Request a new OTP.');
    }

    const submittedHash = this.hashOtp(submitted, phone);

    const isValid = crypto.timingSafeEqual(
      Buffer.from(submittedHash, 'hex'),
      Buffer.from(stored.hash, 'hex'),
    );

    if (!isValid) {
      // Increment attempt count atomically
      stored.attempts += 1;
      await this.redis.setex(storeKey, this.OTP_TTL_SECONDS, JSON.stringify(stored));
      return false;
    }

    // Valid — consume the OTP (delete to prevent replay)
    await this.redis.del(storeKey);
    return true;
  }
}
```

**Q12. What is modulo bias in OTP generation, and why does it matter?**
A: Modulo bias occurs when you generate a random integer and reduce it with `% N` where `N` does not evenly divide the range of the random source. Example: `crypto.randomBytes(1)` gives values `0–255`. Taking `% 10` for a single digit: values `0–9` each appear 25 or 26 times (256 / 10 = 25 remainder 6, so digits `0–5` appear 26 times vs `6–9` appearing only 25 times). The bias is small but statistically measurable over millions of OTPs — an attacker who knows the generation method can slightly increase the probability of guessing certain digits first.

The rejection-sampling approach in Q11 eliminates this: generate a 32-bit random number, and if it falls in the biased zone (the remainder of `2^32 / N`), discard it and try again. For 6-digit OTPs (N = 1,000,000), the rejection probability is `(2^32 % 1,000,000) / 2^32 ≈ 0.023%` — almost never retries in practice, perfectly uniform distribution when it does accept.

A simpler alternative with zero bias for decimal OTPs: generate each digit independently:
```typescript
function generateOtp(length: number): string {
  return Array.from(crypto.randomBytes(length))
    .map(byte => byte % 10)   // each byte → 0–9; bias is negligible at one digit
    .join('');
}
```
Each byte has values `0–255`; `% 10` means digits `0–5` appear 26/256 times and `6–9` appear 25/256 — a bias of ~0.4% per digit. For OTP purposes this is considered acceptable (the attacker gains negligible advantage), but rejection sampling is the academically correct approach.

**Q13. What are the key rate-limiting controls for SMS OTP, and how do you implement them?**
A: SMS OTP has two distinct abuse surfaces: the **send** endpoint (attackers can use it to SMS-bomb arbitrary phone numbers or exhaust your SMS budget) and the **verify** endpoint (attackers brute-force 6-digit codes). Different controls apply to each:

**Send endpoint controls:**
```typescript
// 1. Per-phone resend cooldown — enforced in OTP store (Q11): 60s between sends
// 2. Per-phone daily limit — cap total OTPs sent to one phone per day
const dailyKey = `otp:daily:${phone}`;
const count    = await this.redis.incr(dailyKey);
await this.redis.expire(dailyKey, 86400);
if (count > 5) throw new TooManyRequestsException('Daily OTP limit reached');

// 3. Per-IP rate limit — prevent one IP from triggering OTPs for many phones
const ipKey = `otp:ip:${clientIp}`;
const ipCount = await this.redis.incr(ipKey);
await this.redis.expire(ipKey, 3600);
if (ipCount > 20) throw new TooManyRequestsException('Too many requests');

// 4. CAPTCHA after N failures — require reCAPTCHA/hCaptcha token on the send
//    endpoint after 2 failed verify attempts from the same IP
```

**Verify endpoint controls:**
```typescript
// Max 3 attempts per OTP (enforced in verifyOtp above — stored in Redis with OTP)
// Exponential backoff: lock the phone for 5 min after 3 wrong OTPs in a session
// Jitter in error responses: always return after a fixed delay (e.g., 200ms)
//   regardless of whether the check hit Redis or returned early — prevents timing oracle
```

**Q14. What SMS OTP-specific attacks exist, and how do you mitigate them?**
A: Four main attack classes:

**1. OTP interception (SS7 attacks, SIM swap):**
The SMS network's SS7 protocol has known vulnerabilities allowing nation-state actors and sophisticated attackers to intercept SMS messages in transit. SIM swapping (social engineering a carrier to reassign a phone number to the attacker's SIM) is more practical. Mitigation: offer TOTP as an alternative (not interceptable); use SMS OTP only for user-initiated flows (not for high-value transaction authorization); implement SIM-swap detection (check if the phone number's SIM changed recently via carrier APIs like Twilio Lookup's `line_type_intelligence` or Jio's MNVR lookup).

**2. OTP enumeration (brute force):**
A 6-digit OTP has 1,000,000 possible values. With no rate limiting, it's brute-forceable in under a second. With 3 attempts and a 10-minute TTL, the effective attack probability per OTP is `3 / 1,000,000 = 0.0003%`. For a 4-digit OTP it's `3 / 10,000 = 0.03%` — meaningfully worse, which is why 6 digits is the minimum. Mitigation: max attempts (Q11), OTP invalidation after max attempts, progressive lockout.

**3. SMS bombing / OTP flooding:**
Attacker uses your send endpoint to send hundreds of unsolicited OTPs to a victim's phone. Beyond harassment, this exhausts your SMS budget. Mitigation: resend cooldown, per-phone daily limit, per-IP rate limit, CAPTCHA (Q13).

**4. Phishing / real-time relay:**
Attacker creates a fake login page that captures the user's credentials and OTP, immediately replaying them to your real API. Since OTPs are short-lived (10 minutes) but not origin-bound, this works within the window. Mitigation: bind OTP to the user's session or device fingerprint at send time; use short TTLs (2–5 minutes for sensitive flows); display the purpose clearly in the SMS ("OTP for login from Chrome on MacOS — if this wasn't you, call us immediately"); consider WebAuthn for phishing-resistant step-up auth on high-value actions.

## Section 4: Backup Codes and Account Recovery

**Q15. What are TOTP backup codes, and how do you implement them?**
A: Backup codes are single-use pre-generated codes given to the user at TOTP enrollment, to be used if they lose access to their authenticator app. They're a recovery mechanism, not a second factor — using a backup code during login should trigger a prompt to re-enroll TOTP.

```typescript
// totp.service.ts
async generateBackupCodes(userId: string): Promise<string[]> {
  const CODE_COUNT  = 8;
  const CODE_LENGTH = 8;  // e.g. "a3f8c291" — 8 hex chars = 32 bits entropy each

  const codes = Array.from({ length: CODE_COUNT }, () =>
    crypto.randomBytes(CODE_LENGTH / 2).toString('hex')  // 4 bytes → 8 hex chars
  );

  // Hash each code before storing — same principle as API keys
  const hashed = codes.map(code => ({
    hash: crypto.createHash('sha256').update(code).digest('hex'),
    used: false,
  }));

  await this.users.update(userId, {
    totp_backup_codes: JSON.stringify(hashed),
    backup_codes_generated_at: new Date(),
  });

  // Return raw codes — shown ONCE for the user to write down / store in password manager
  // Display formatted: "a3f8-c291" for readability
  return codes.map(c => `${c.slice(0, 4)}-${c.slice(4)}`);
}

async verifyBackupCode(userId: string, submitted: string): Promise<boolean> {
  const user   = await this.users.findOneOrFail(userId);
  const codes  = JSON.parse(user.totp_backup_codes) as { hash: string; used: boolean }[];
  const normalized = submitted.replace(/-/g, '').toLowerCase();  // strip display formatting

  const submittedHash = crypto.createHash('sha256').update(normalized).digest('hex');

  const matchIndex = codes.findIndex(c =>
    !c.used &&
    crypto.timingSafeEqual(
      Buffer.from(submittedHash, 'hex'),
      Buffer.from(c.hash, 'hex'),
    )
  );

  if (matchIndex === -1) return false;

  // Mark the specific code as used — single-use enforcement
  codes[matchIndex].used = true;
  await this.users.update(userId, { totp_backup_codes: JSON.stringify(codes) });

  // Flag account: prompt re-enrollment on next login
  await this.users.update(userId, { totp_requires_reenrollment: true });

  return true;
}
```

**Q16. What should happen to MFA state when a user changes their phone number or loses their device?**
A: This is an account recovery flow and it's one of the most security-sensitive operations in your system — it's the target of social engineering attacks (an attacker pretends to have lost their device to bypass MFA). The recovery flow must have a security level at least as strong as what it bypasses:

```
Option A — Email verification recovery:
  User requests MFA reset → backend sends a time-limited (15 min) signed link
  to the registered email → user clicks → MFA is disabled → user must re-enroll.
  Suitable for: consumer apps where email is the primary identity.

Option B — Identity re-verification:
  For fintech accounts: require the user to re-complete KYC/identity verification
  (Aadhaar OTP, PAN verification, video KYC) before resetting MFA.
  Suitable for: high-value accounts, RBI-mandated identity assurance.

Option C — Support-assisted with out-of-band verification:
  User contacts support → support verifies identity via multiple signals (account
  history, registered address, previous transaction details) → support triggers
  MFA reset with mandatory audit log entry.
  Suitable for: accounts where neither email nor KYC re-verification is feasible.
```

Always: log the MFA reset event to the audit log, send a notification to all registered contact channels ("Your MFA was reset — if this wasn't you, contact us immediately"), enforce a 24-hour cooling-off period before the account can be used for high-value transactions after an MFA reset, and never allow MFA reset via SMS to the same phone number the MFA is protecting (defeats the purpose).

## Section 5: MFA in the Login Flow

**Q17. How do you structure the login flow to integrate MFA without exposing the user session prematurely?**
A: The risk with a naive implementation: you issue a full session token after the password check, then ask for MFA — but the full session is already active. If MFA verification fails, you're revoking a session that shouldn't have existed yet. The correct pattern uses a **partial session token** (sometimes called a "challenge token") between the password step and the MFA step:

```
POST /auth/login { email, password }
  → Password correct:
      Issue a short-lived (5 min), limited-scope JWT:
      { sub: userId, scope: "mfa_challenge", exp: now+300 }
      Return 200 with: { mfa_required: true, challenge_token: "eyJ..." }
  → Password wrong:
      Return 401 (with rate limiting and account lockout)

POST /auth/mfa/verify { challenge_token, otp_code }
  → Validate challenge_token (not expired, scope === "mfa_challenge")
  → Verify OTP (TOTP or SMS)
  → Both valid:
      Issue full session token / refresh token pair
      Invalidate the challenge_token
  → OTP invalid:
      Return 401, increment attempt counter on challenge_token
      After 3 failures: invalidate challenge_token, force restart of login flow
```

The challenge token has no privilege — it can only be exchanged for a full session via a successful MFA verify. A leaked challenge token doesn't give an attacker access; they still need the OTP.

**Q18. How do you implement step-up authentication for high-value actions (as opposed to login MFA)?**
A: Step-up auth requires re-verification of a second factor before a sensitive action, even within an active authenticated session. Common triggers in fintech: changing bank account details, initiating a transfer above a threshold, updating the registered phone number, accessing loan documents.

```typescript
// step-up.guard.ts
@Injectable()
export class StepUpGuard implements CanActivate {
  async canActivate(context: ExecutionContext): Promise<boolean> {
    const req     = context.switchToHttp().getRequest();
    const user    = req.user;  // already authenticated via session

    // Check if a recent step-up verification exists in the session
    const stepUpKey = `stepup:${user.id}:${req.path}`;
    const verified  = await this.redis.get(stepUpKey);

    if (verified) return true;  // step-up done recently (within TTL)

    // No step-up — return 403 with a challenge type so the frontend
    // knows to present the MFA challenge dialog
    throw new ForbiddenException({
      code:           'STEP_UP_REQUIRED',
      challenge_type: user.totp_enabled ? 'totp' : 'sms_otp',
      message:        'Re-authentication required for this action',
    });
  }
}

// After the user completes step-up MFA:
async recordStepUp(userId: string, action: string): Promise<void> {
  // Step-up is valid for 5 minutes for the specific action
  await this.redis.setex(`stepup:${userId}:${action}`, 300, '1');
}
```

For RBI-mandated "Additional Factor of Authentication" (AFA) on digital payments: every transaction above ₹2,000 (or per the applicable circular) requires AFA — step-up auth is the implementation mechanism. Log every step-up event (who, what action, when, which factor used) for the audit trail.

**Q19. How do you implement account lockout after repeated MFA failures without creating a denial-of-service vector?**
A: Lockout must balance security (prevent brute force) against availability (attacker can't lock out legitimate users by repeatedly failing MFA on their behalf):

```typescript
async recordMfaFailure(userId: string): Promise<void> {
  const failKey    = `mfa:fail:${userId}`;
  const lockKey    = `mfa:lock:${userId}`;
  const count      = await this.redis.incr(failKey);

  if (count === 1) {
    await this.redis.expire(failKey, 900);  // 15-minute rolling window
  }

  if (count >= 5) {
    // Lock for 15 minutes — exponential backoff for repeat lockouts
    const lockDuration = Math.min(900 * (2 ** (count - 5)), 86400);  // max 24h
    await this.redis.setex(lockKey, lockDuration, '1');
    await this.redis.del(failKey);

    // Notify user via email: "Multiple failed MFA attempts on your account"
    await this.notificationService.sendMfaLockoutAlert(userId);
  }
}

async checkMfaLock(userId: string): Promise<void> {
  const locked = await this.redis.exists(`mfa:lock:${userId}`);
  if (locked) {
    const ttl = await this.redis.ttl(`mfa:lock:${userId}`);
    throw new UnauthorizedException(
      `Account temporarily locked. Try again in ${Math.ceil(ttl / 60)} minutes.`
    );
  }
}
```

The DoS consideration: if lockout is triggered by IP or without any account ownership verification, an attacker can lock any user's account. Mitigations: lock only after failures on the *correct password* (so an attacker must first know the password to trigger MFA lockout), use progressive lockout (5 min → 15 min → 1 hour) rather than permanent, and send the lockout notification so the legitimate user can contact support.

## Section 6: Real-World Scenarios and Trade-offs

**Q20. How do you handle the TOTP secret if a user wants to switch authenticator apps?**
A: Switching apps requires re-provisioning — the secret must be re-shared with the new app. The flow is identical to initial enrollment (Q6–Q7):
1. User initiates "change authenticator" flow.
2. Require the user to verify their *current* TOTP code (proves they still have the old app — prevents an attacker who only has the password from hijacking the TOTP secret).
3. Generate a new secret (or reuse the existing one — generating a new one is more secure: the old secret is no longer usable even if the old app/device is compromised).
4. Display the new QR code. The user scans with the new app.
5. Require the user to verify a code from the new app before activating.
6. Update the stored (encrypted) secret, invalidate the old one, generate fresh backup codes.

Never allow TOTP re-enrollment without first verifying the current factor or requiring a higher assurance method — this is a common vulnerability where an attacker who phished the password can add their own authenticator app.

**Q21. What's the difference between HOTP and TOTP, and when would you use HOTP?**
A: HOTP (HMAC-based OTP, RFC 4226) derives codes from a monotonically increasing counter shared between the authenticator and the server. TOTP (RFC 6238) derives codes from a time-based counter (Unix time / 30 seconds). Key differences:

| | HOTP | TOTP |
|---|---|---|
| Counter | Stateful (synchronized integer) | Stateless (derived from time) |
| Validity | Until the next code is generated | 30-second window |
| Clock sync required | No | Yes (±30s tolerance) |
| Replay risk | Higher (no time expiry) | Lower (30s window) |
| State management | Server must track counter per user | No counter state on server |
| Primary use case | Hardware tokens with no clock | Authenticator apps |

HOTP is used primarily for hardware tokens (RSA SecurID, older YubiKeys in OTP mode) where maintaining an accurate real-time clock is impractical. TOTP is standard for software authenticator apps. HOTP has a look-ahead window problem: if the user generates many codes without submitting them, the server's counter falls behind the device's counter — servers typically allow a look-ahead of 10–50 codes. For almost all modern implementations, use TOTP.

**Q22. Scenario: "Users complain that their TOTP codes are rejected despite being entered correctly and immediately. What do you investigate?"**
A: This is a clock-sync issue first, then a few other candidates:

```
1. Server clock drift — check the server's NTP sync:
   timedatectl status       # on the server
   ntpq -p                  # peer list
   If the server clock drifted > 30s: the server and app are computing different
   time windows. Sync: ntpdate -s time.google.com or configure chrony.

2. App/device clock drift — the user's phone clock is off.
   Ask: does the authenticator app show the same time as a trusted source?
   iOS and Android auto-sync via NTP, but "Automatic date & time" must be enabled.
   Fix on the device: Settings → Date & Time → Enable automatic.

3. Window tolerance — confirm otplib's window is set to at least 1.
   authenticator.options = { window: 1 };  // ± 1 window = ± 30s tolerance

4. Secret encoding mismatch — was the secret stored and retrieved correctly?
   Base32 is case-insensitive; some apps strip spaces/dashes from manual entry.
   Confirm the stored secret (after decryption) matches what was provisioned.

5. Replay protection false positive — confirm the Redis replay-protection key
   (totp:used:userId:code) has the correct 30s TTL. If TTL is too long or the key
   is incorrectly keyed, legitimate codes can be rejected as "already used."

6. Timezone confusion — rare, but if T = floor(timestamp / 30) is computed with
   local time instead of UTC, codes will be wrong. Always use UTC epoch seconds.
```

**Q23. Scenario: "You need to add SMS OTP to a checkout flow for loan disbursement approval in a high-volume (50,000 daily) fintech app. What design decisions do you make?"**
A: At 50,000 daily OTPs, several design concerns become non-trivial:

**SMS provider reliability and fallback:**
Never rely on a single SMS provider. Use a primary (e.g., Kaleyra or MSG91 for India's DLT-registered routes) with automatic failover to a secondary (AWS SNS or Twilio). Route routing logic: attempt primary, if delivery receipt (DLR) not received within 15 seconds, send via secondary. At 50K/day (~0.6 OTPs/second average, higher at peak disbursement windows), provider SLAs and DLT template registration matter.

**DLT compliance (India-specific):**
TRAI's Distributed Ledger Technology (DLT) mandate requires all transactional SMS in India to be pre-registered: the sender ID (e.g., `LNAPLF`), message template, and entity ID must be registered on the DLT platform (Airtel, Jio, Vi). Unregistered SMS are blocked by carriers. Template example:
`"Your OTP for loan disbursement approval of Rs. {1} is {2}. Valid for 10 minutes. Do not share. -LNAPLF"`
The `{1}` and `{2}` are dynamic fields. Template registration takes 24–72 hours — do this before launch, not after.

**Redis OTP store at scale:**
50K OTPs × 600s TTL = up to 50K active keys in Redis at any time. This is trivial for Redis (Redis can hold millions of keys). Use a dedicated Redis cluster (not the same one used for session caching) for OTP storage — isolation ensures an OTP Redis failure doesn't take down sessions, and vice versa.

**Async OTP sending:**
Don't synchronously await the SMS provider API in the request handler. Put the SMS send on a job queue (Bull/BullMQ + Redis). The endpoint returns immediately after storing the OTP hash; the worker handles delivery. This prevents SMS provider latency from affecting the checkout flow's response time and gives you retry semantics for failed sends.

**Cost tracking:**
At 50K/day, SMS costs are material. Track per-phone-number OTP send counts, flag anomalies (one phone getting 20+ OTPs/day — possible SMS bombing), and alert on spend anomalies.

**Q25. What are the RBI and PCI-DSS requirements most directly relevant to MFA implementation?**
A: Both frameworks mandate MFA but differ in specificity:

**PCI-DSS v4.0:**
- **Req 8.4.2** — MFA is required for all non-console access to the cardholder data environment (CDE). Applies to admin dashboards, internal tools, VPN access.
- **Req 8.4.3** — MFA required for all remote network access originating from outside the entity's network. No exceptions.
- **Req 8.5.1** — MFA systems must not be susceptible to replay attacks (directly addressed by OTP window + replay protection). MFA factors must be independent (compromise of one factor doesn't compromise others — SMS and password together are weaker than TOTP and password, because SS7 compromise gives both).
- **Req 10** — All MFA events (success, failure, lockout, bypass) must be logged with sufficient detail for audit and forensic investigation.

**RBI Master Direction on Digital Payment Security Controls (2021):**
- All payment system providers must implement MFA for customer-facing login to payment applications.
- **AFA (Additional Factor of Authentication)** is mandated for every digital payment transaction — OTP (SMS or TOTP) is the primary accepted mechanism. The OTP must be dynamic (time or transaction-bound) and sent to the registered phone number.
- OTPs must not be transmitted via the same channel as the transaction initiation (the "separate channel" requirement — you don't send the OTP on the same webpage/app that's processing the payment; it must come via a separate channel like SMS).
- **Tokenization** — card details used in recurring mandates (NACH) must be tokenized; the token itself requires AFA for registration.
- **Audit trail** — all authentication events must be logged and retained per the RBI record-keeping requirements (generally 5 years for most transaction records).

In practice: for a lending platform, TOTP for internal admin access (PCI-DSS Req 8.4.2), SMS OTP for customer disbursement approval (RBI AFA), and TOTP as an opt-in stronger second factor for customers who prefer it. Never offer only SMS OTP to admins — the SS7/SIM-swap risk is too high for privileged access.

## Quick Comparison Table

| Aspect | TOTP | SMS OTP |
|---|---|---|
| Second factor type | Something you have (authenticator app) | Something you have (phone/SIM) |
| Phishing resistant | Partial (OTP valid for 30s window) | No (valid for minutes) |
| SIM-swap risk | None | Yes — critical weakness |
| SS7 interception risk | None | Yes |
| Works offline | Yes (no network needed) | No (requires cellular/SMS) |
| User setup friction | High (app install + QR scan) | Low (just a phone number) |

| OTP lifetime | 30 seconds | 5–10 minutes (configurable) |
| Clock sync required | Yes (±30s tolerance) | No |
| Replay protection | Redis used-code cache | Delete on use, attempt counter |
| India DLT compliance | N/A | Required (TRAI DLT registration) |
| Recommended for | Admin access, security-conscious users | Consumer-facing flows, broad reach |
| RBI AFA compliant | Yes | Yes (primary mechanism) |

**Tip for the interview:** At 5 YOE, MFA questions go beyond "how does TOTP work" into implementation specifics. Know the HMAC-SHA1 → truncation → 6-digit pipeline (Q4) well enough to describe it without looking it up — interviewers ask you to walk through it. The two most common deep-dives are: "why not bcrypt for OTPs?" (same answer as API keys — high entropy means SHA-256 is fine, and you don't want 250ms per auth request) and "how do you prevent replay attacks?" (Redis used-code cache with 30s TTL for TOTP; delete-on-use for SMS OTP). Have the partial-session challenge-token login flow (Q17) ready — most junior engineers implement a security hole here by issuing the full session after password-only. The RBI AFA requirement (Q25) almost always comes up in fintech interviews — know that it's mandatory for every digital payment, not just login.
