# Security: OAuth 2.0 Flows — Interview Q&A (5 YOE Level)

---

## Section 1: OAuth 2.0 Fundamentals

**Q1. What problem does OAuth 2.0 solve, and what are its four roles?**
A: OAuth 2.0 (RFC 6749) solves the **delegated authorization** problem: how does a third-party application access a user's resources on another service without the user giving it their password? Before OAuth, the common pattern was credential sharing — the user typed their email/password into the third-party app, which stored and used it. This is catastrophically bad: the third party can do anything the user can, there's no scope limitation, and the user can't revoke access without changing their password.

OAuth 2.0 introduces four roles:

```
Resource Owner  — the user. Owns the data. Grants authorization.

Client          — the application requesting access (your SaaS app, mobile app, CLI tool).
                  Does not see the user's credentials.

Authorization   — the server that authenticates the user and issues tokens.
Server            (Google's OAuth server, Okta, Auth0, your own auth service).
                  The user trusts this server — it's where they enter credentials.

Resource Server — the API that holds the user's data (Google Drive API, GitHub API,
                  your own API). Validates access tokens before serving responses.
```

The key guarantee: the client never sees the resource owner's credentials. The resource owner authenticates directly with the authorization server, which issues scoped, revocable access tokens to the client. If the client is compromised, the attacker gets a token — not the user's password — and the token can be revoked and scoped to only the permissions the client needed.

**Q2. What is the difference between authentication and authorization, and why does OAuth 2.0 only do one of them?**
A: OAuth 2.0 is an **authorization** framework — it answers "what is this client allowed to do?" It is explicitly not an authentication protocol — it does not answer "who is this user?" This distinction matters because access tokens in OAuth 2.0 have no standardized format or claims. An access token tells the resource server "this client has been granted these scopes" — it says nothing reliable about the user's identity.

The confusion arises because many developers use OAuth 2.0 for login ("Log in with Google"). Google's OAuth endpoint happens to return user info, but the mechanism for that is **OpenID Connect (OIDC)** — a thin identity layer built on top of OAuth 2.0 that adds the ID token (a JWT with standardized identity claims: `sub`, `email`, `name`, `iss`, `aud`, `exp`).

```
OAuth 2.0 alone:
  Client gets access_token → can call /userinfo endpoint → gets user data
  Problem: access_token was not issued FOR the client — it could be stolen and replayed

OIDC (OAuth 2.0 + identity layer):
  Client gets access_token + id_token
  id_token is a JWT with aud=client_id → binds the identity assertion to this client
  Client validates id_token → can trust the identity without calling /userinfo
```

In an interview: if asked "how do you implement login with Google?", the answer is OIDC (Authorization Code flow + `openid` scope), not raw OAuth 2.0. The distinction signals you understand the actual security model.

**Q3. What are scopes, and how do they implement the principle of least privilege?**
A: Scopes are strings that represent specific permissions the client is requesting. The authorization server includes granted scopes in the access token; the resource server checks them before fulfilling a request.

```
Client requests: scope=read:transactions write:transfers profile

User sees consent screen:
  "MyApp wants to:
   ✓ Read your transaction history
   ✓ Transfer funds on your behalf
   ✓ Access your profile information"

User approves → access_token issued with those scopes
User denies transfers → access_token issued with scope=read:transactions profile only
```

Least privilege in practice: a read-only dashboard client should request only `read:*` scopes. If the token is stolen, the attacker cannot initiate transfers — the token literally cannot authorize that operation. The resource server validates scopes on each request:

```python
def require_scope(required_scope: str):
    def decorator(f):
        @wraps(f)
        def wrapper(*args, **kwargs):
            token = extract_bearer_token(request)
            payload = verify_jwt(token)
            granted_scopes = set(payload.get("scope", "").split())
            if required_scope not in granted_scopes:
                raise HTTP403(f"Insufficient scope. Required: {required_scope}")
            return f(*args, **kwargs)
        return wrapper
    return decorator

@app.route("/api/transfers", methods=["POST"])
@require_scope("write:transfers")
def create_transfer():
    ...
```

Scope granularity is a design decision: too coarse (`admin`) and least privilege is meaningless; too fine (`read:transaction:id:12345`) and the consent screen becomes unusable. The right level: resource-type + operation (`read:transactions`, `write:payments`, `admin:users`).

## Section 2: Authorization Code Flow

**Q4. Walk through the Authorization Code flow step by step, explaining why each step exists.**
A: The Authorization Code flow is the standard flow for server-side and single-page applications that act on behalf of a logged-in user.

```
Step 1 — Client initiates authorization:
  GET https://auth.myorg.com/authorize?
      response_type=code
      &client_id=loans_dashboard
      &redirect_uri=https://app.myorg.com/callback
      &scope=read:transactions+read:profile
      &state=xK9mPq3rT7vL2nW8

  Why:
  - response_type=code → tells the auth server to use Authorization Code flow
  - client_id → identifies which client is requesting (public knowledge)
  - redirect_uri → where to send the user after authorization
  - scope → what permissions are being requested
  - state → opaque CSRF token (client generates, must verify on callback)

Step 2 — Auth server authenticates the user:
  User sees the auth server's login page (not the client's).
  User enters credentials → auth server validates → shows consent screen.
  User approves or denies.

  Why: credentials never leave the auth server. The client is not involved in this step.

Step 3 — Auth server redirects back with authorization code:
  HTTP 302 Location: https://app.myorg.com/callback?
      code=SplxlOBeZQQYbYS6WxSbIA
      &state=xK9mPq3rT7vL2nW8

  Why the code is short-lived and single-use:
  - The code appears in the browser URL — visible in history, referrer headers, logs.
  - It's not the access token; it's a temporary credential that must be exchanged.
  - Short TTL (60–600 seconds) minimizes the exposure window.
  - Single-use: the auth server invalidates it after one exchange attempt.

Step 4 — Client verifies state parameter:
  assert callback_state == session["oauth_state"]  ← CSRF check

  Why: without this, an attacker can trick the user into attaching the attacker's
  authorization code to the victim's session (CSRF on the OAuth callback).

Step 5 — Client exchanges code for tokens (back-channel):
  POST https://auth.myorg.com/token
  Content-Type: application/x-www-form-urlencoded
  Authorization: Basic base64(client_id:client_secret)

  grant_type=authorization_code
  &code=SplxlOBeZQQYbYS6WxSbIA
  &redirect_uri=https://app.myorg.com/callback

  Why back-channel (server-to-server):
  - client_secret is included — must never appear in the browser.
  - The browser never sees the token exchange request or response.
  - Network interception of the code is useless without client_secret.

Step 6 — Auth server returns tokens:
  {
    "access_token":  "eyJhbGci...",
    "token_type":    "Bearer",
    "expires_in":    900,
    "refresh_token": "8xLOxBtZp8",
    "scope":         "read:transactions read:profile"
  }

Step 7 — Client uses access token:
  GET https://api.myorg.com/transactions
  Authorization: Bearer eyJhbGci...
```

The two-step design (code → token) is the entire security model: the authorization code can be in the browser (low-trust channel); the access token never is.

**Q5. What is the `state` parameter, and what attack does it prevent?**
A: The `state` parameter is a client-generated opaque value included in the authorization request and returned unchanged by the auth server in the redirect. The client verifies it matches before proceeding with the token exchange.

It prevents the **OAuth CSRF attack**:

```
Attack without state:

1. Attacker initiates OAuth flow for their own account at IdP:
   GET /authorize?client_id=app&redirect_uri=https://app.com/callback → gets code=ATTACKER_CODE

2. Attacker crafts a URL:
   https://app.com/callback?code=ATTACKER_CODE
   (stops before loading — doesn't use the code themselves)

3. Attacker tricks the victim into loading the crafted URL
   (CSRF via image tag, email link, etc.)

4. Victim's browser loads https://app.com/callback?code=ATTACKER_CODE
   App exchanges ATTACKER_CODE for tokens → attacker's account linked to victim's session

5. Victim is now logged in as the attacker (or attacker's account is linked to victim's)
   → Attacker can log in to app and access victim's data

With state:

1. App generates state="rand_xK9m" when initiating OAuth, stores in session
2. Authorization request includes &state=rand_xK9m
3. Auth server includes state=rand_xK9m in the redirect
4. App checks: callback_state == session_state
5. Attacker's crafted URL has no state or wrong state → verification fails → rejected
```

The `state` value must be:
- Cryptographically random (not sequential, not predictable)
- Bound to the user's session (stored server-side or in a session cookie, not in a URL)
- Validated before any token exchange occurs

```python
import secrets

# Initiating the flow
oauth_state = secrets.token_urlsafe(32)
session["oauth_state"] = oauth_state
redirect_to_auth_server(state=oauth_state)

# Handling the callback
def oauth_callback(request):
    if not hmac.compare_digest(
        request.args["state"],
        session.get("oauth_state", "")
    ):
        raise HTTP400("Invalid state parameter — possible CSRF attack")
    # proceed with token exchange
```

**Q6. What is the `redirect_uri` validation requirement, and what attack does open redirect enable?**
A: The authorization server must validate that the `redirect_uri` in the authorization request exactly matches a URI pre-registered for that `client_id`. Loose matching — prefix matching, wildcard matching, or no validation — enables the **redirect URI manipulation attack**:

```
Legitimate registration: redirect_uri=https://app.myorg.com/callback

Attack scenarios:

1. Open redirect on the target domain:
   Attacker registers nothing. Client app has an open redirect:
   https://app.myorg.com/redirect?to=https://attacker.com
   Attacker uses redirect_uri=https://app.myorg.com/redirect?to=https://attacker.com
   If auth server accepts "same domain, different path" → code sent to attacker

2. Subdomain wildcard:
   Auth server allows *.myorg.com
   Attacker registers a subdomain: attacker.myorg.com (via subdomain takeover)
   Uses redirect_uri=https://attacker.myorg.com/callback → receives code

3. Path traversal:
   Auth server does prefix match on https://app.myorg.com/
   Attacker uses redirect_uri=https://app.myorg.com.attacker.com/callback
   (dot not treated as delimiter) → received by attacker

4. Fragment manipulation:
   redirect_uri=https://app.myorg.com/callback#https://attacker.com
   Some parsers treat #fragment as part of the URI, some don't
```

The correct validation rule: **exact string match** after normalizing (scheme lowercased, port explicit if non-standard). No wildcards, no prefix matching, no regex. For mobile apps that use custom URI schemes (`myapp://callback`), register each scheme+host combination exactly.

If the authorization code is delivered to the attacker, they can exchange it for tokens if they also have the `client_secret`. For public clients (mobile apps, SPAs) there is no `client_secret` — this is exactly why PKCE exists (Q8).

## Section 3: PKCE — Proof Key for Code Exchange

**Q7. What attack does PKCE prevent that the base Authorization Code flow is vulnerable to?**
A: PKCE (RFC 7636, pronounced "pixy") prevents the **authorization code interception attack** against public clients — clients that cannot securely store a `client_secret` (mobile apps, native desktop apps, single-page apps).

The attack on a public client without PKCE:

```
Legitimate OAuth flow on a mobile device:

1. App initiates: opens system browser to /authorize?client_id=myapp&redirect_uri=myapp://callback
2. User authenticates and approves
3. Auth server redirects: myapp://callback?code=SplxlO...
4. OS routes the custom URI scheme to... which app?

On Android/iOS, multiple apps can register the same custom URI scheme.
Malicious App has also registered myapp:// (or the user was tricked into installing it).
OS delivers the redirect to the Malicious App instead of the legitimate app.
Malicious App receives code=SplxlO... and tries to exchange it.

Without PKCE:
  POST /token { grant_type=authorization_code, code=SplxlO..., client_id=myapp }
  No client_secret for public clients — auth server accepts the exchange.
  Malicious App receives access_token and refresh_token.
  Attack succeeds.
```

PKCE ties the token exchange to the specific initiation of the flow. The party that exchanges the code must prove they initiated it — proof that the malicious interceptor cannot provide.

**Q8. How does PKCE work cryptographically? Walk through the code_verifier and code_challenge.**
A: PKCE adds two parameters to the flow: a secret generated at the start, and a hash of that secret sent with the authorization request.

```python
import secrets, hashlib, base64

# --- CLIENT SIDE: flow initiation ---

# Step 1: Generate code_verifier — cryptographically random, 43-128 chars
# RFC 7636: characters from [A-Z a-z 0-9 - . _ ~]
code_verifier = secrets.token_urlsafe(96)  # 96 bytes → 128 URL-safe chars
# e.g. "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk..."

# Step 2: Derive code_challenge = BASE64URL(SHA256(ASCII(code_verifier)))
digest = hashlib.sha256(code_verifier.encode("ascii")).digest()
code_challenge = base64.urlsafe_b64encode(digest).rstrip(b"=").decode()
# e.g. "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"

# Step 3: Send code_challenge in authorization request (NOT the verifier)
auth_url = (
    "https://auth.myorg.com/authorize?"
    f"response_type=code"
    f"&client_id=myapp"
    f"&redirect_uri=myapp://callback"
    f"&scope=read:profile"
    f"&state={state}"
    f"&code_challenge={code_challenge}"
    f"&code_challenge_method=S256"   # SHA-256; never use "plain"
)
# code_verifier stays in memory on the client — never sent to the auth server

# --- AUTH SERVER SIDE: stores code_challenge with the issued code ---
# When code=SplxlO... is issued, auth server records:
# { code: "SplxlO...", code_challenge: "E9Mel...", method: "S256", expires_at: ... }

# --- CLIENT SIDE: token exchange ---
token_response = requests.post("https://auth.myorg.com/token", data={
    "grant_type":    "authorization_code",
    "code":          received_code,
    "redirect_uri":  "myapp://callback",
    "client_id":     "myapp",
    "code_verifier": code_verifier,   # ← the original secret, now revealed
})

# --- AUTH SERVER SIDE: verification ---
# Recompute: BASE64URL(SHA256(received_code_verifier))
# Compare with stored code_challenge
# If match → exchange proceeds; if not → reject
stored_challenge = lookup_challenge_for_code(received_code)
computed = base64.urlsafe_b64encode(
    hashlib.sha256(received_code_verifier.encode()).digest()
).rstrip(b"=").decode()
assert hmac.compare_digest(computed, stored_challenge)
```

Why the interceptor cannot succeed:

```
Malicious app intercepts code=SplxlO...
Malicious app tries: POST /token { code=SplxlO..., code_verifier=??? }

The malicious app never saw code_verifier — it was generated by the legitimate app,
kept in memory, and never transmitted until the token exchange.

The code_challenge was sent in the authorization request (step 3), but:
  - code_challenge is SHA256(code_verifier) — a one-way hash
  - Reversing SHA256 is computationally infeasible
  - Without code_verifier, the token exchange fails

The interceptor is blocked.
```

**Q9. Should PKCE be used only for public clients, or for confidential clients too?**
A: PKCE should be used for **all clients** in all new deployments — RFC 9700 (OAuth 2.1, the security BCP) mandates PKCE universally, not just for public clients. The reasons:

**For public clients (mobile, SPA):** PKCE is the primary protection against code interception (as described in Q7). There is no `client_secret`, so PKCE is the only binding between the code and the initiating party.

**For confidential clients (server-side web apps) too:**
- PKCE additionally prevents **authorization code injection** — an attacker who obtains a valid code from any source (via their own account, via redirect URI manipulation) and tries to inject it into a different user's session. PKCE binds the code to the specific flow initiation, so a code from flow A cannot be replayed in flow B.
- If the `client_secret` is compromised (rotation delay, secret leak in CI logs), PKCE is a second factor of protection.
- OAuth 2.1 removes Implicit flow and requires PKCE for Authorization Code flow regardless of client type. Building to 2.1 now avoids a migration later.

The operational cost of PKCE for confidential clients is minimal: generate a random verifier, hash it, include two extra parameters. The security benefit is defense-in-depth.

**Q10. How do you implement the Authorization Code + PKCE flow for a React SPA?**
A:

```typescript
// auth.ts — OAuth 2.0 + PKCE for a browser SPA

const CLIENT_ID    = "loans_dashboard_spa";
const AUTH_ENDPOINT = "https://auth.myorg.com/authorize";
const TOKEN_ENDPOINT = "https://auth.myorg.com/token";
const REDIRECT_URI  = "https://app.myorg.com/callback";
const SCOPES        = "openid profile read:transactions";

// Crypto utilities — use Web Crypto API (available in all modern browsers)
async function generateCodeVerifier(): Promise<string> {
    const array = new Uint8Array(96);
    crypto.getRandomValues(array);
    return btoa(String.fromCharCode(...array))
        .replace(/\+/g, "-").replace(/\//g, "_").replace(/=/g, "");
}

async function generateCodeChallenge(verifier: string): Promise<string> {
    const encoder = new TextEncoder();
    const data    = encoder.encode(verifier);
    const digest  = await crypto.subtle.digest("SHA-256", data);
    return btoa(String.fromCharCode(...new Uint8Array(digest)))
        .replace(/\+/g, "-").replace(/\//g, "_").replace(/=/g, "");
}

// Initiate login
export async function login(): Promise<void> {
    const codeVerifier  = await generateCodeVerifier();
    const codeChallenge = await generateCodeChallenge(codeVerifier);
    const state         = crypto.randomUUID();

    // Store verifier and state — sessionStorage survives redirect, not XSS-proof
    // but HttpOnly cookie alternative requires a backend endpoint
    sessionStorage.setItem("pkce_verifier", codeVerifier);
    sessionStorage.setItem("oauth_state",   state);

    const params = new URLSearchParams({
        response_type:          "code",
        client_id:              CLIENT_ID,
        redirect_uri:           REDIRECT_URI,
        scope:                  SCOPES,
        state,
        code_challenge:         codeChallenge,
        code_challenge_method:  "S256",
    });

    window.location.href = `${AUTH_ENDPOINT}?${params}`;
}

// Handle callback
export async function handleCallback(): Promise<{ accessToken: string }> {
    const params = new URLSearchParams(window.location.search);
    const code   = params.get("code");
    const state  = params.get("state");
    const error  = params.get("error");

    if (error) throw new Error(`OAuth error: ${error} — ${params.get("error_description")}`);
    if (!code)  throw new Error("No authorization code in callback");

    // Verify state
    const savedState = sessionStorage.getItem("oauth_state");
    if (!savedState || state !== savedState) {
        throw new Error("State mismatch — possible CSRF attack");
    }

    const codeVerifier = sessionStorage.getItem("pkce_verifier");
    if (!codeVerifier) throw new Error("No code verifier found");

    // Clean up
    sessionStorage.removeItem("pkce_verifier");
    sessionStorage.removeItem("oauth_state");

    // Exchange code for tokens
    const resp = await fetch(TOKEN_ENDPOINT, {
        method: "POST",
        headers: { "Content-Type": "application/x-www-form-urlencoded" },
        body: new URLSearchParams({
            grant_type:    "authorization_code",
            code,
            redirect_uri:  REDIRECT_URI,
            client_id:     CLIENT_ID,
            code_verifier: codeVerifier,   // ← proof
        }),
    });

    if (!resp.ok) {
        const err = await resp.json();
        throw new Error(`Token exchange failed: ${err.error}`);
    }

    const tokens = await resp.json();
    // Store access_token in memory only — never localStorage
    return { accessToken: tokens.access_token };
}
```

Note: `sessionStorage` for the PKCE verifier is acceptable for the short duration of the redirect roundtrip, but is readable by JavaScript (XSS risk). For higher-security SPAs, use a backend-for-frontend (BFF) pattern where the PKCE verifier is stored server-side in the user's session cookie, and the SPA never handles raw OAuth artifacts.

## Section 4: Client Credentials Flow

**Q11. What is the Client Credentials flow, and when is it the correct choice?**
A: Client Credentials (RFC 6749 §4.4) is the flow for **machine-to-machine (M2M) communication** — service-to-service calls where there is no user involved. The client authenticates as itself (not on behalf of a user) and receives an access token representing the service's own identity and permissions.

```
When to use: any automated, server-to-server call where a human user is not in the loop.

Examples:
  - Loans microservice calling the Credit Bureau API (batch credit checks at 2am)
  - Payment processor calling the Fraud Detection service to score a transaction
  - CI/CD pipeline calling the Deployment API
  - Cron job calling the Notification service to send daily reports
  - Any backend service calling another backend service's protected API

When NOT to use: any flow where a user is present and delegating access.
  Client Credentials tokens represent the SERVICE — not any user.
  A token from Client Credentials has no `sub` claim (or sub = client_id).
  Using it to represent a user is semantically wrong and loses audit trail.
```

**Q12. Walk through the Client Credentials flow and explain how secrets are managed.**
A:

```
Step 1 — Service authenticates to auth server (no user redirect):
  POST https://auth.myorg.com/token
  Content-Type: application/x-www-form-urlencoded
  Authorization: Basic base64("loans-service:super-secret-client-secret")

  grant_type=client_credentials
  &scope=read:credit-scores write:fraud-signals

Step 2 — Auth server validates client credentials, issues access token:
  {
    "access_token": "eyJhbGci...",
    "token_type":   "Bearer",
    "expires_in":   3600,
    "scope":        "read:credit-scores write:fraud-signals"
  }
  Note: no refresh_token — the service can just re-authenticate when the token expires.

Step 3 — Service calls the resource server with the token:
  GET https://credit-bureau-api.myorg.com/scores/user_123
  Authorization: Bearer eyJhbGci...
```

```python
# Production client credentials implementation with token caching
import time, threading, requests
from dataclasses import dataclass

@dataclass
class TokenCache:
    access_token: str
    expires_at:   float   # unix timestamp

class M2MTokenClient:
    """Thread-safe client credentials token manager with caching."""

    def __init__(self, client_id: str, client_secret: str, token_url: str, scope: str):
        self.client_id     = client_id
        self.client_secret = client_secret
        self.token_url     = token_url
        self.scope         = scope
        self._cache: TokenCache | None = None
        self._lock  = threading.Lock()

    def get_token(self) -> str:
        with self._lock:
            # Return cached token if it has >60s remaining (buffer for clock skew)
            if self._cache and self._cache.expires_at > time.time() + 60:
                return self._cache.access_token
            return self._fetch_new_token()

    def _fetch_new_token(self) -> str:
        resp = requests.post(
            self.token_url,
            data={"grant_type": "client_credentials", "scope": self.scope},
            auth=(self.client_id, self.client_secret),  # HTTP Basic auth
            timeout=5,
        )
        resp.raise_for_status()
        data = resp.json()
        self._cache = TokenCache(
            access_token=data["access_token"],
            expires_at=time.time() + data["expires_in"],
        )
        return self._cache.access_token

# Usage: inject as a singleton into services
credit_bureau_client = M2MTokenClient(
    client_id="loans-service",
    client_secret=os.environ["CREDIT_BUREAU_CLIENT_SECRET"],
    token_url="https://auth.myorg.com/token",
    scope="read:credit-scores",
)

def get_credit_score(user_id: str) -> dict:
    token = credit_bureau_client.get_token()
    resp  = requests.get(
        f"https://credit-bureau-api.myorg.com/scores/{user_id}",
        headers={"Authorization": f"Bearer {token}"},
    )
    resp.raise_for_status()
    return resp.json()
```

**Client secret management — the critical operational concern:**
```
DO:
  Store client_secret in a secrets manager (AWS Secrets Manager, HashiCorp Vault)
  Inject as environment variable at runtime
  Rotate on a schedule (quarterly) and immediately on any suspected exposure
  Use per-service client_ids — loans-service, payments-service, fraud-service each
    have their own client_id/secret pair. Compromise of one doesn't affect others.
  Restrict scopes per client_id — loans-service gets read:credit-scores only,
    not write:payments or admin:users

DON'T:
  Hardcode secrets in source code or Dockerfiles
  Store in .env files committed to git
  Share one client_id/secret across multiple services
  Grant broad scopes to reduce configuration overhead
```

**Q13. How do you implement per-service authorization on the resource server side for Client Credentials tokens?**
A: Client Credentials tokens carry the `client_id` of the caller (either as the `sub` claim or a custom `client_id` claim in the JWT). Resource servers use this to implement service-level authorization:

```python
# Resource server: authorize based on client identity, not user identity

def require_client_scope(required_scope: str):
    def decorator(f):
        @wraps(f)
        def wrapper(*args, **kwargs):
            token   = extract_bearer_token(request)
            payload = verify_jwt(token, algorithms=["RS256"])

            # Distinguish user tokens from service tokens
            client_id  = payload.get("client_id") or payload.get("azp")
            grant_type = payload.get("gty")  # some auth servers include grant type

            granted_scopes = set(payload.get("scope", "").split())

            if required_scope not in granted_scopes:
                raise HTTP403("Insufficient scope")

            # Optional: allowlist which service clients can call this endpoint
            ALLOWED_CLIENTS = {
                "/api/credit-scores": {"loans-service", "risk-service"},
                "/api/fraud-signals": {"payments-service", "fraud-service"},
            }
            allowed = ALLOWED_CLIENTS.get(request.path, set())
            if allowed and client_id not in allowed:
                raise HTTP403(f"Client {client_id!r} not authorized for this endpoint")

            request.client_id = client_id
            return f(*args, **kwargs)
        return wrapper
    return decorator

@app.route("/api/credit-scores/<user_id>")
@require_client_scope("read:credit-scores")
def get_credit_score(user_id: str):
    # request.client_id is available for audit logging
    audit_log(action="credit_score_read", subject=user_id, actor=request.client_id)
    ...
```

This implements service mesh authorization at the application layer — which service called which endpoint, audited per request. For high-compliance environments, pair this with mTLS at the transport layer: the client presents a certificate proving service identity, and the server validates both the mTLS certificate AND the bearer token (defense-in-depth).

## Section 5: Device Code Flow

**Q14. What is the Device Code flow, and what problem does it solve?**
A: The Device Code flow (RFC 8628) solves OAuth authorization for **input-constrained devices** — devices that cannot open a browser or enter text easily: smart TVs, streaming sticks, IoT devices, game consoles, CLI tools, printers.

The constraint: the device cannot redirect the user to an authorization URL (no browser) and cannot capture a username/password (no keyboard or limited input). But a nearby device (phone, laptop) can. The Device Code flow uses that nearby device as a secondary authorization channel:

```
Examples:
  "Sign in to Netflix on your TV" — user goes to netflix.com/activate on their phone
  GitHub CLI: "gh auth login" — CLI prints a code, user visits github.com/device
  AWS IoT device provisioning — device gets code, admin approves on laptop
  Printer configuration — printer displays code, admin enters it at web console
```

**Q15. Walk through the Device Code flow step by step.**
A:

```
Step 1 — Device requests device code (no user involved):
  POST https://auth.myorg.com/device/code
  Content-Type: application/x-www-form-urlencoded

  client_id=smart_tv_app
  &scope=read:watchlist write:playback

  Response:
  {
    "device_code":       "GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",  ← secret, for device
    "user_code":         "WDJB-MJHT",                                    ← human-friendly, for user
    "verification_uri":  "https://auth.myorg.com/activate",
    "verification_uri_complete": "https://auth.myorg.com/activate?user_code=WDJB-MJHT",
    "expires_in":        1800,    ← 30 minutes for user to complete
    "interval":          5        ← device polls every 5 seconds minimum
  }

Step 2 — Device displays the user_code and verification_uri:
  TV screen shows:
  "Visit auth.myorg.com/activate on your phone or computer
   Enter code: WDJB-MJHT
   (Code expires in 30 minutes)"

  If the TV can show a QR code, encode verification_uri_complete into it.

Step 3 — Device polls for the token (loop):
  while True:
      sleep(interval)   # 5 seconds minimum — respect the interval
      POST https://auth.myorg.com/token
      {
        grant_type:  "urn:ietf:params:oauth:grant-type:device_code",
        device_code: "GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",
        client_id:   "smart_tv_app"
      }

      if response.error == "authorization_pending":
          continue  # user hasn't approved yet — keep polling

      if response.error == "slow_down":
          interval += 5  # auth server asking us to back off — increase interval
          continue

      if response.error == "expired_token":
          break  # user_code expired — show error, restart flow

      if response.error == "access_denied":
          break  # user denied — show error

      if response.access_token:
          break  # SUCCESS — store token and proceed

Step 4 — User authorizes on secondary device:
  User visits https://auth.myorg.com/activate on their phone
  Enters "WDJB-MJHT"
  Auth server shows consent screen (which scopes are requested)
  User approves

Step 5 — Next poll after approval succeeds:
  {
    "access_token":  "eyJhbGci...",
    "token_type":    "Bearer",
    "expires_in":    900,
    "refresh_token": "8xLOxBtZp8",
    "scope":         "read:watchlist write:playback"
  }
```

```python
# Device client polling implementation
import time, requests

class DeviceCodeFlow:
    def __init__(self, client_id: str, device_code_url: str, token_url: str):
        self.client_id       = client_id
        self.device_code_url = device_code_url
        self.token_url       = token_url

    def authorize(self, scope: str) -> dict:
        # Step 1: Request device code
        resp = requests.post(self.device_code_url, data={
            "client_id": self.client_id, "scope": scope
        })
        resp.raise_for_status()
        dc = resp.json()

        # Step 2: Display to user
        print(f"\nTo sign in, visit: {dc['verification_uri']}")
        print(f"Enter code: {dc['user_code']}")
        print(f"(Expires in {dc['expires_in'] // 60} minutes)\n")

        # Step 3: Poll
        interval   = dc["interval"]
        deadline   = time.time() + dc["expires_in"]

        while time.time() < deadline:
            time.sleep(interval)
            poll = requests.post(self.token_url, data={
                "grant_type":  "urn:ietf:params:oauth:grant-type:device_code",
                "device_code": dc["device_code"],
                "client_id":   self.client_id,
            })
            body = poll.json()

            match body.get("error"):
                case "authorization_pending":
                    continue
                case "slow_down":
                    interval += 5   # back off
                    continue
                case "expired_token" | "access_denied":
                    raise RuntimeError(f"Authorization failed: {body['error']}")
                case None:
                    return body     # success — contains access_token
                case _:
                    raise RuntimeError(f"Unexpected error: {body['error']}")

        raise TimeoutError("Device authorization timed out")
```

**Q16. What are the security considerations specific to the Device Code flow?**
A:

**User code entropy:** The `user_code` must be short enough for a human to type on a TV remote (6–8 characters), but long enough to resist brute-force. RFC 8628 recommends at least 8 characters from an alphabet that excludes visually ambiguous characters (0/O, 1/I/l). At 8 uppercase chars from a 20-char alphabet (letters excluding ambiguous ones): 20^8 = 25 billion combinations. With a 30-minute window and rate limiting, this is adequate. The auth server must rate-limit `/activate` submissions aggressively — 5 failed attempts per IP per minute maximum.

**Device code entropy:** The `device_code` is machine-to-machine and can be full-entropy random — 32+ bytes. It is never displayed to humans. It identifies the polling request and must be unpredictable to prevent polling enumeration.

**Polling abuse:** A malicious device could poll more aggressively than the specified `interval` to race ahead of the user's approval. The `slow_down` error is the server's mechanism to enforce rate limiting per `device_code`. The server should also enforce an absolute maximum poll rate independent of the error response (e.g., 1 request per second per device_code), rejecting violators with HTTP 429.

**Phishing risk:** The Device Code flow is more phishing-prone than Authorization Code because the user is typing a code at a URL, which an attacker can replicate. An attacker who controls a malicious device could initiate a Device Code flow with the real auth server, display the real `user_code` and a lookalike URL to the victim, and have the victim authorize the attacker's device. Mitigate by: using a well-known, memorable `verification_uri` (e.g., `myorg.com/activate`, not a long URL); educating users never to enter codes they didn't initiate; and for high-risk operations, requiring a secondary confirmation on the authorizing device.

## Section 6: Implicit Flow (Deprecated)

**Q17. What was the Implicit flow, how did it work, and why is it deprecated?**
A: The Implicit flow (RFC 6749 §4.2) was designed for browser-based single-page applications in the early 2010s, before CORS was widely available. The key difference from Authorization Code: the access token is returned directly in the redirect URL fragment, skipping the code-for-token exchange step.

```
Authorization Code:
  Auth server → redirect_uri?code=ABC → client exchanges code for token (back-channel)
  Access token never in the browser URL

Implicit:
  Auth server → redirect_uri#access_token=eyJhbGci...&token_type=bearer&expires_in=3600
  Access token is in the URL fragment (after the #) — directly in the browser
```

The Implicit flow existed because, in 2012, SPAs could not make cross-origin POST requests to the token endpoint (CORS didn't exist). Returning the token in a redirect was the only mechanism. By 2015, CORS was universally supported. By 2019, RFC 8252 and the OAuth Security BCP explicitly deprecated Implicit. OAuth 2.1 removes it entirely.

**Why it was broken — five vulnerabilities:**

**1. Access token in URL fragment:**
```
redirect_uri: https://app.myorg.com/callback#access_token=eyJhbGci...

Problems:
  - Browser history stores the full URL including fragment
  - Referrer header may leak the fragment to third-party resources on the page
  - Server-side logs (nginx, CDN) may log the full URL
  - JavaScript loaded on the page can read window.location.hash
  - Any script on the page — including third-party analytics — can steal the token
```

**2. No client authentication:**
Implicit issues the access token directly to a redirect URI, with no client secret exchange. The auth server cannot verify that the redirect is going to the legitimate client. Anyone who registers the right `client_id` and manipulates the `redirect_uri` receives the token.

**3. No refresh tokens:**
RFC 6749 explicitly prohibits issuing refresh tokens in Implicit flow (because the client cannot securely store them). This forces short-lived access tokens and frequent re-authorization, or use of silent refresh via hidden iframes — which has its own security issues.

**4. Token substitution attacks:**
Without a code-binding mechanism (PKCE) or back-channel exchange, an attacker can substitute a token issued for client A into client B's flow if they can intercept the redirect.

**5. Iframe-based silent refresh:**
The common workaround for refresh tokens in SPAs was a hidden iframe that re-ran the Implicit flow in the background. This bypassed user consent for re-authorization and created a persistent background authentication loop — a CSRF attack surface and a complexity footgun.

**Q18. What should you migrate to if you have an existing Implicit flow implementation?**
A: The migration is Authorization Code + PKCE. The flows are similar enough that migration is mechanical:

```
BEFORE (Implicit):
  response_type=token
  No state validation (often omitted)
  Access token in fragment
  No client_secret, no code_verifier
  Token exchange: none (token returned directly)

AFTER (Authorization Code + PKCE):
  response_type=code
  state= required CSRF protection
  code in query string (not fragment)
  No client_secret (public client), code_verifier required
  Token exchange: POST /token with code + code_verifier
  Access token in response body (never in URL)
```

```javascript
// BEFORE (Implicit — never write this):
const authUrl = `${AUTH_ENDPOINT}?response_type=token&client_id=${CLIENT_ID}&redirect_uri=${REDIRECT_URI}`;
window.location.href = authUrl;
// Then on callback: parse window.location.hash for access_token

// AFTER (Authorization Code + PKCE — correct):
async function login() {
    const verifier   = await generateCodeVerifier();
    const challenge  = await generateCodeChallenge(verifier);
    const state      = crypto.randomUUID();
    sessionStorage.setItem("pkce_verifier", verifier);
    sessionStorage.setItem("oauth_state", state);

    const params = new URLSearchParams({
        response_type: "code", client_id: CLIENT_ID, redirect_uri: REDIRECT_URI,
        scope: SCOPES, state, code_challenge: challenge, code_challenge_method: "S256",
    });
    window.location.href = `${AUTH_ENDPOINT}?${params}`;
}
// Token comes back via POST /token exchange — never in the URL
```

If you encounter an auth server that still requires `response_type=token` (legacy), push to upgrade it. If you are evaluating a vendor and they only support Implicit for SPAs, treat that as a red flag for their security posture.

## Section 7: Token Validation, Security Hardening, and Real-World Patterns

**Q19. What must the resource server validate on every incoming access token?**
A: A resource server that skips any of these checks has a potential authentication bypass:

```python
def validate_access_token(raw_token: str, request_context: dict) -> dict:
    # 1. Parse and verify signature — algorithm must be in explicit allowlist
    try:
        payload = jwt.decode(
            raw_token,
            key=fetch_public_key_from_jwks(raw_token),  # key lookup by kid
            algorithms=["RS256"],  # never ["HS256", "RS256"], never omit
        )
    except jwt.InvalidSignatureError:
        raise HTTP401("Invalid token signature")
    except jwt.ExpiredSignatureError:
        raise HTTP401("Token has expired")
    except jwt.DecodeError:
        raise HTTP401("Malformed token")

    # 2. Issuer — reject tokens from unexpected issuers
    expected_issuer = "https://auth.myorg.com"
    if payload.get("iss") != expected_issuer:
        raise HTTP401(f"Invalid issuer: {payload.get('iss')!r}")

    # 3. Audience — reject tokens not intended for this resource server
    expected_audience = "https://loans-api.myorg.com"
    aud = payload.get("aud", [])
    if isinstance(aud, str):
        aud = [aud]
    if expected_audience not in aud:
        raise HTTP401(f"Token not intended for this audience")

    # 4. Expiry — already checked by the library above, but explicit belt-and-suspenders
    if payload.get("exp", 0) < time.time():
        raise HTTP401("Token expired")

    # 5. Not-before — if present, token not yet valid
    if "nbf" in payload and payload["nbf"] > time.time() + 30:  # 30s clock skew
        raise HTTP401("Token not yet valid")

    # 6. Scopes — checked per-endpoint (see Q3 / Q13)

    # 7. Token type — if your auth server distinguishes access vs ID tokens
    if payload.get("token_use") not in (None, "access"):
        raise HTTP401("Wrong token type")

    return payload
```

The most commonly skipped validations in real codebases: `aud` (teams assume any valid token is valid for any service) and `iss` (teams assume all tokens come from their own auth server). Both are real exploit paths.

**Q20. How do you handle token refresh proactively in a client to avoid 401 errors on API calls?**
A: Reactive refresh (retry on 401) works but creates user-visible latency spikes. Proactive refresh avoids this:

```typescript
class TokenManager {
    private accessToken:   string | null = null;
    private refreshToken:  string | null = null;
    private expiresAt:     number = 0;           // unix timestamp
    private refreshPromise: Promise<void> | null = null;

    // Proactive: refresh when <60s remains, not when expired
    private needsRefresh(): boolean {
        return Date.now() / 1000 > this.expiresAt - 60;
    }

    async getAccessToken(): Promise<string> {
        if (!this.needsRefresh() && this.accessToken) {
            return this.accessToken;
        }
        // Deduplicate concurrent refresh calls — if one is already in-flight, wait for it
        if (!this.refreshPromise) {
            this.refreshPromise = this.doRefresh().finally(() => {
                this.refreshPromise = null;
            });
        }
        await this.refreshPromise;
        return this.accessToken!;
    }

    private async doRefresh(): Promise<void> {
        if (!this.refreshToken) throw new Error("No refresh token — must re-authenticate");

        const resp = await fetch("/auth/token/refresh", {
            method: "POST",
            headers: { "Content-Type": "application/json" },
            body: JSON.stringify({ refresh_token: this.refreshToken }),
        });

        if (resp.status === 401) {
            // Refresh token revoked or expired — force re-login
            this.clear();
            window.location.href = "/login";
            throw new Error("Session expired");
        }

        const data = await resp.json();
        this.accessToken  = data.access_token;
        this.refreshToken = data.refresh_token;   // rotated
        this.expiresAt    = Math.floor(Date.now() / 1000) + data.expires_in;
    }

    clear(): void {
        this.accessToken = this.refreshToken = null;
        this.expiresAt = 0;
    }
}

// Interceptor pattern — wrap fetch so all API calls get a fresh token automatically
const tokenManager = new TokenManager();

async function apiFetch(url: string, options: RequestInit = {}): Promise<Response> {
    const token = await tokenManager.getAccessToken();
    return fetch(url, {
        ...options,
        headers: { ...options.headers, "Authorization": `Bearer ${token}` },
    });
}
```

The deduplication (`refreshPromise`) is critical: without it, multiple concurrent API calls that all see an expired token will all fire simultaneous refresh requests — only one will succeed (the others get a reuse error from token rotation), causing spurious 401s and potential family revocation.

**Q21. How do the four flows map to client types, and which flow should you use for each scenario?**
A:

| Scenario | Client Type | Correct Flow | Reason |
|---|---|---|---|
| Web app with server-side rendering | Confidential (has client_secret) | Authorization Code + PKCE | User present; back-channel token exchange; secret stored server-side |
| React/Vue/Angular SPA | Public (no client_secret) | Authorization Code + PKCE | User present; PKCE replaces client_secret for public clients |
| iOS/Android mobile app | Public (no client_secret) | Authorization Code + PKCE | User present; custom URI scheme redirect; PKCE prevents code interception |
| Microservice calling another microservice | Confidential | Client Credentials | No user; service authenticates as itself |
| CLI tool (developer tool) | Public or Confidential | Authorization Code + PKCE or Device Code | If terminal can open browser: Auth Code + PKCE; if not: Device Code |
| Smart TV / game console | Public | Device Code | Input-constrained; user authorizes on secondary device |
| Batch job / cron | Confidential | Client Credentials | No user; automated; service identity |
| IoT sensor reporting data | Confidential (if possible) | Client Credentials | No user; if client_secret storage is feasible; else mTLS + certificate |
| "Log in with Google" (OIDC) | Either | Authorization Code + PKCE + `openid` scope | User present; need ID token for identity (not just authorization) |
| Legacy SPA (currently Implicit) | Public | **Migrate to Authorization Code + PKCE** | Implicit is deprecated and insecure |

## Quick Reference: Flow Comparison

| Property | Authorization Code + PKCE | Client Credentials | Device Code | Implicit |
|---|---|---|---|---|
| RFC | 6749 §4.1 + 7636 | 6749 §4.4 | 8628 | 6749 §4.2 |
| User interaction | Required | None | Required (on secondary device) | Required |
| Client type | Public or Confidential | Confidential only | Public or Confidential | Public (historical) |
| `client_secret` | Optional (required if confidential) | Required | Optional | None |
| PKCE | Required (all clients per OAuth 2.1) | Not applicable | Optional (recommended) | Not applicable |
| Token in URL | Never | Never | Never | Yes (fragment) — insecure |
| Refresh token issued | Yes | No (re-authenticate) | Yes | No |
| `state` CSRF protection | Required | Not applicable | Not applicable | Required (historical) |
| Status | Current, mandated by OAuth 2.1 | Current | Current | Deprecated, removed in 2.1 |
| Use case | User-delegated access, web/mobile/SPA | M2M, service-to-service | Input-constrained devices | Legacy SPAs — migrate away |

## Quick Reference: PKCE Parameters

| Parameter | Where | Value | Purpose |
|---|---|---|---|
| `code_verifier` | Client memory only (never transmitted until exchange) | 43–128 chars, CSPRNG, URL-safe alphabet | The secret that proves flow initiation |
| `code_challenge` | Authorization request | `BASE64URL(SHA256(code_verifier))` | The hash commitment sent to the auth server |
| `code_challenge_method` | Authorization request | `S256` (always; never `plain`) | Declares the hash algorithm |
| `code_verifier` | Token exchange request | Same value generated at initiation | The proof — auth server hashes and compares to stored challenge |
