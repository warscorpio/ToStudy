## Part 1 — Theory & Interview Q&A

## Topic A: The Core Data Structure

### Section A1: Fundamentals

**Q1. What is an LRU Cache, and what two properties must it simultaneously guarantee?**

A: An LRU (Least Recently Used) Cache is a fixed-capacity key-value store that evicts the *least recently accessed* entry when a new entry would exceed capacity. It must guarantee two properties simultaneously: (1) **O(1) key lookup** — any key's value can be retrieved in constant time; (2) **O(1) recency tracking** — every access and insertion updates the ordering so the LRU element is always identifiable and removable in constant time. No single standard data structure provides both. A HashMap gives O(1) lookup but carries no ordering information. A doubly linked list gives O(1) insertion and removal *at a known node* and maintains insertion/access order, but has no keyed lookup. The LRU Cache is specifically the combination that achieves both by having them reference each other.

```
HashMap alone:       O(1) get/put, but no recency order → can't identify LRU element
Ordered list alone:  O(1) eviction of tail, but O(n) key lookup → too slow
HashMap + DLL:       O(1) lookup via map + O(1) reorder/evict via list → both ✓
```

**Q2. Why is a doubly linked list required rather than a singly linked list?**

A: Removing an arbitrary node from a linked list in O(1) requires updating *both* the previous node's `next` pointer and the next node's `prev` pointer. In a singly linked list, given a pointer to a node, you can set `node.next` but you have no reference to the node *before* it — finding it requires an O(n) traversal from the head. In a doubly linked list, each node carries a `prev` pointer, so `node.prev.next = node.next` is O(1). Since the LRU Cache must be able to remove *any* node (when `get` or `put` is called on it, moving it to the front) in O(1), the `prev` pointer is not optional — it is the precise mechanism that makes O(1) arbitrary removal possible.

```
Singly linked — remove node X:
  Need: predecessor of X to update predecessor.next = X.next
  Problem: finding predecessor requires scanning from head → O(n)

Doubly linked — remove node X:
  X.prev.next = X.next   ← O(1), prev pointer is right there
  X.next.prev = X.prev   ← O(1), next pointer is right there
  Total: O(1) ✓
```

**Q3. Why must the DLL node store the key, and what breaks if it stores only the value?**

A: When the cache evicts the LRU element, it removes the tail node from the DLL *and* must delete the corresponding entry from the HashMap. The HashMap entry is identified by its key. If the tail node stores only the value, there is no way to recover the key needed for `map.delete(key)` — the eviction step becomes O(n) (scan the entire HashMap for the matching node) or impossible. Storing the key in the node creates a constant-time bridge back to the HashMap: `map.delete(tail.prev.key)`. This is the single most commonly missed design detail in LRU Cache interviews — the key lives in the node not as a convenience but as the essential back-reference that enables O(1) eviction cleanup.

```
Node without key:
  DLL tail removal: O(1)
  HashMap cleanup:  O(n) scan to find which key maps to this node ← bottleneck

Node with key:
  DLL tail removal:     tail.prev.key → O(1) lookup for map.delete ✓
  HashMap cleanup:      map.delete(tail.prev.key)                  ← O(1) ✓
```

**Q4. What are sentinel (dummy) head and tail nodes, and what specific code complexity do they eliminate?**

A: Sentinel nodes are permanent, non-data-carrying placeholder nodes at both ends of the DLL — `head` is always the node *before* the MRU element; `tail` is always the node *after* the LRU element. They are never removed and never map to any key. Their value: without sentinels, every insert and remove operation must handle the empty-list edge case (is `head` null? is `tail` null?) and the boundary cases (inserting into an empty list, removing the last node, removing the head node). With sentinels, these cases disappear — the list is never "empty" from the pointers' perspective, and head and tail always have valid neighbors to update. The two primitive operations (`_remove` and `_insertAfterHead`) become four-line, branch-free code regardless of list state.

```
Without sentinels — _insertAtFront must handle:
  if (head == null) { head = tail = node; }   // empty list
  else { node.next = head; head.prev = node; head = node; }  // non-empty

With sentinels — _insertAfterHead is always the same 4 lines:
  node.next = head.next;       // head.next is always valid (at least tail)
  node.prev = head;
  head.next.prev = node;       // head.next.prev is always valid
  head.next = node;
  // No branching, no null checks, correct for 0, 1, or n existing nodes ✓
```

**Q5. What are the two invariants the LRU Cache data structure maintains at all times?**

A: (1) **Recency order invariant**: `head.next` is the MRU node (most recently accessed or inserted); `tail.prev` is the LRU node (least recently accessed or inserted). Every `get` and `put` operation maintains this by moving the touched node to the MRU position immediately. (2) **Map-list consistency invariant**: every key present in the HashMap has exactly one corresponding node in the DLL, and every node in the DLL (excluding sentinels) has exactly one corresponding entry in the HashMap. No key exists in the map without a node in the list, and no non-sentinel node exists in the list without a key in the map. These two invariants together guarantee that the cache is always in a valid, queryable state between operations.

```
Recency invariant:      head ↔ [MRU] ↔ ... ↔ [LRU] ↔ tail
                        any access/insert moves touched node to position after head

Consistency invariant:  map.keys() == {node.key for node in list (excl. sentinels)}
                        maintained by: always insert into both; always delete from both
```

**Q6. What is the `_remove` primitive, and why must its four assignments occur in exactly the right order?**

A: `_remove(node)` detaches a node from the DLL by relinking its neighbors around it. The four required assignments are: `node.prev.next = node.next` (predecessor now points past the removed node); `node.next.prev = node.prev` (successor now points back to predecessor). Order does not technically matter for these two lines since they access `node.prev` and `node.next` before overwriting them — but the critical discipline is to *not* overwrite `node.prev` or `node.next` before they've been read in all necessary assignments. Clearing `node.prev = null; node.next = null` after the relink (optional, for garbage collection hygiene) must come last. The standard safe pattern reads `node.prev` and `node.next` for the relink first, then nullifies them.

```js
_remove(node) {
  node.prev.next = node.next;  // predecessor skips node
  node.next.prev = node.prev;  // successor skips node
  // node.prev and node.next still point outward — safe to null after:
  node.prev = null;            // optional: detach for GC (not required for correctness)
  node.next = null;
}
```

**Q7. What is the `_insertAfterHead` primitive, and what is the required assignment order?**

A: `_insertAfterHead(node)` places a node immediately after the sentinel head, making it the new MRU element. Four assignments are required, and order matters: first read the current first node (`const first = head.next`) or use `head.next` directly, but you must set `node.next` and `node.prev` before modifying `head.next` or `head.next.prev`, since those modifications change what `head.next` refers to. The safe canonical order: (1) `node.next = head.next` — node's forward pointer to old first; (2) `node.prev = head` — node's back pointer to head; (3) `head.next.prev = node` — old first's back pointer to node; (4) `head.next = node` — head's forward pointer to node. Step 4 must be last: if done earlier, `head.next` in step 3 refers to `node` itself, corrupting `node.prev`.

```js
_insertAfterHead(node) {
  node.next = this.head.next;       // (1) node → old first
  node.prev = this.head;            // (2) node ← head
  this.head.next.prev = node;       // (3) old first ← node  [must precede step 4]
  this.head.next = node;            // (4) head → node        [must be last]
}

// WRONG — step 4 before step 3:
  this.head.next = node;            // head → node (now head.next IS node)
  this.head.next.prev = node;       // node.prev = node ← self-loop! ✗
```

**Q8. How do `get` and `put` compose the two primitives, and what is the complete state transition for each?**

A: **`get(key)`**: (1) If key is absent from the map, return -1. (2) Retrieve the node from the map. (3) Call `_remove(node)` to detach it from its current list position. (4) Call `_insertAfterHead(node)` to promote it to MRU. (5) Return `node.val`. The map is not modified — the node stays in the map; only its DLL position changes. **`put(key, value)`** has two sub-cases: *Key exists*: retrieve the node, update `node.val`, then call `_remove` + `_insertAfterHead` to promote it (same as `get` but also updating the value). *Key absent*: create a new node with both key and value, insert into the map (`map.set(key, node)`), call `_insertAfterHead(node)`. Then check if `map.size > capacity` — if so, identify `lru = tail.prev`, call `_remove(lru)`, call `map.delete(lru.key)`. Order matters: check *after* adding the new entry (not before), so the size check reflects the true post-insertion count.

```
get(key):
  map miss?         → return -1
  map hit:          → _remove(node) + _insertAfterHead(node) → return node.val
  Map unchanged. DLL position: node moves to head.next. ✓

put(key, value) — key exists:
  node.val = value  → _remove(node) + _insertAfterHead(node)
  Map unchanged. DLL position: node moves to head.next. ✓

put(key, value) — key new:
  node = new Node   → map.set(key, node) + _insertAfterHead(node)
  Over capacity?    → _remove(tail.prev) + map.delete(tail.prev.key)
  Map grows by 1, then shrinks by 1 if over capacity. DLL grows by 1 then shrinks. ✓
```

**Q9. What is the move-to-front pattern, and why is it the atomic unit of the LRU Cache?**

A: Move-to-front (MTF) is the compound operation `_remove(node)` followed immediately by `_insertAfterHead(node)`. It is the atomic unit of recency tracking — it expresses "this element was just used; it is now the most recently used element." Both `get` and `put` (for existing keys) reduce to MTF plus their specific side effects (returning a value, or updating a value). MTF in O(1) is precisely what the DLL enables: because the HashMap gives you a direct pointer to the node, `_remove` and `_insertAfterHead` each take O(1), making MTF O(1). If the HashMap instead gave you an index into an array, moving to front would require shifting O(n) elements. The DLL's O(1) arbitrary-position removal is the enabling primitive for O(1) MTF.

```
move_to_front(key):
  node = map.get(key)        // O(1): HashMap lookup gives direct node pointer
  _remove(node)              // O(1): DLL detach via node.prev and node.next
  _insertAfterHead(node)     // O(1): DLL insert using head sentinel

Without DLL — array-based ordering:
  Find element at position p  → O(1) via map
  Shift elements [0..p-1] right one position  → O(n) ✗
```

### Section A2: Advanced Patterns

**Q10. Why does eviction check `map.size > capacity` rather than `map.size >= capacity`, and when exactly does eviction fire?**

A: The check is `map.size > capacity` *after* inserting the new node. At the moment of the check, the new entry is already in the map and list. If `map.size` now equals `capacity + 1`, exactly one entry must be evicted to restore the invariant. If the check were `>= capacity` and were done before inserting, it would evict even when there is space remaining — evicting a valid entry unnecessarily. If the check were done before inserting with `> capacity`, a cache of capacity 1 would evict the existing element before knowing whether the new key is the same (which requires only an update, not an eviction). Checking after insertion handles the "same key" case cleanly: when `put` is called with an existing key, the key count doesn't increase (it's a move + update), so `map.size` equals `capacity` or less, and the eviction branch is never entered — correct, no eviction needed for an update.

**Q11. How does the LRU Cache handle concurrent access, and what are the failure modes without synchronization?**

A: The standard implementation is not thread-safe. Two concurrent `get` calls on different keys will both call `_remove` and `_insertAfterHead`, each reading and writing `node.prev`, `node.next`, `head.next`, and `head.next.prev`. Without synchronization, interleaved pointer assignments can leave the DLL in a corrupt state: a node may appear to have two predecessors, the sentinel linkage may be broken, or a node may be simultaneously present and absent. Mitigation approaches: (1) coarse-grained locking — a single mutex wrapping each `get`/`put` call; simple but creates a bottleneck under high concurrency; (2) per-shard locking — partition the key space into N shards, each with its own HashMap + DLL + lock (like Java's `ConcurrentHashMap` sharding model); reduces contention; (3) using language-native thread-safe ordered maps (`LinkedHashMap` with `accessOrder=true` and `Collections.synchronizedMap` in Java). For interview purposes, acknowledging the thread-safety issue and naming the coarse-lock approach demonstrates senior-level awareness even if implementation is single-threaded.

**Q12. What is the `LinkedHashMap` / `OrderedDict` shortcut, and under what interview conditions is it appropriate to use it?**

A: Java's `LinkedHashMap` (with `accessOrder = true`) and Python's `functools.lru_cache` or a manually maintained `OrderedDict` both implement the LRU Cache's data structure natively, making the implementation trivial. In Java: subclass `LinkedHashMap`, override `removeEldestEntry` to return `size() > capacity`. In Python: use `OrderedDict` with `move_to_end(key)` on access. These are correct and production-appropriate. In an interview: using them is acceptable only if the interviewer has *not* asked you to implement the underlying data structure — the entire point of the LRU Cache problem at the 5 YOE level is demonstrating mastery of the HashMap + DLL composition. If an interviewer asks "implement an LRU Cache," they almost always want the explicit node class and pointer manipulation. The shortcut is appropriate only when the LRU Cache is a *component* of a larger problem being solved (e.g., designing a web server caching layer) and the LRU mechanics are not the focus.

```
// Java shortcut — valid when LRU is a component, not the focus
Map<Integer, Integer> cache = new LinkedHashMap<>(capacity, 0.75f, true) {
  protected boolean removeEldestEntry(Map.Entry eldest) {
    return size() > capacity;
  }
};

// Python shortcut
from collections import OrderedDict
class LRUCache:
  def get(self, key):
    if key not in self.cache: return -1
    self.cache.move_to_end(key)  # move to MRU end
    return self.cache[key]
```

**Q13. How does the "move to front" pattern generalize beyond LRU caching, and what class of problems does it solve?**

A: Move-to-front solves any problem requiring: (1) a dynamic ordered collection where access promotes an element to the front; (2) O(1) lookup by key; (3) O(1) access to the "oldest" element (for eviction, for "first unique," for "least used"). The pattern generalizes to: *First Unique Number in a stream* — maintain a DLL of candidate unique numbers; when a number repeats, remove it from the DLL (O(1) via HashMap pointer); the front of the DLL is always the first unique number. *Browser history* — a DLL where the current pointer can move back/forward and visiting a new page truncates the forward history. *All O(1) Data Structure* — a DLL where each node represents a frequency bucket; incrementing a key's count moves it to the next frequency bucket, similar to MTF but with frequency ordering instead of recency ordering. In all cases the structure is: HashMap provides a direct pointer to a node in an ordered sequence; the sequence's ordering encodes the relevant invariant; node manipulation is O(1) because pointer-jumping replaces linear search.

## Topic B: Variants and Extensions

### Section B1: LFU Cache and Frequency-Based Eviction

**Q14. What does the LFU Cache eviction policy guarantee, and how does it differ structurally from LRU?**

A: An LFU (Least Frequently Used) Cache evicts the key with the *lowest access count*, with ties broken by *least recently used among those with the minimum count*. Where LRU's eviction decision is purely temporal ("when was this last accessed?"), LFU's is frequency-based with a temporal tie-breaker. This changes the data structure requirements fundamentally: LRU needs only one ordered sequence (recency order); LFU needs *two levels of ordering*: a frequency level (what is each key's count?) and a recency level within each frequency group (among all keys with count=3, which was used least recently?). This "group by frequency, order within group by recency" structure requires two HashMaps and one DLL-per-frequency-bucket, rather than LRU's single HashMap + single DLL.

```
LRU ordering:  [MRU] ← key_A ↔ key_B ↔ key_C → [LRU]
               one dimension: recency

LFU ordering:  freq=1: [MRU] ← key_C ↔ key_A → [LRU]
               freq=2: [MRU] ← key_D → [LRU]
               freq=5: [MRU] ← key_B → [LRU]
               evict from: freq bucket with min frequency, LRU end of that bucket
               two dimensions: frequency tier + recency within tier
```

**Q15. What data structures does an O(1) LFU Cache require, and what does the `minFreq` pointer do?**

A: An O(1) LFU Cache requires: (1) `keyMap`: HashMap `{key → {value, freq}}` — stores each key's value and current access count; (2) `freqMap`: HashMap `{freq → DLL}` — each frequency value maps to a DLL of all keys currently at that count, ordered by recency within the bucket (MRU at head, LRU at tail); (3) `minFreq`: an integer tracking the current minimum frequency across all cached keys — required to identify the eviction bucket in O(1) without scanning all frequency buckets. On `get(key)`: look up key in `keyMap`, get its current freq, remove it from `freqMap[freq]`, insert it into `freqMap[freq+1]`, increment `keyMap[key].freq`. If `freqMap[minFreq]` is now empty, increment `minFreq`. On `put(key, value)` for a new key: insert at freq=1, set `minFreq = 1`. On eviction: evict the LRU node from `freqMap[minFreq]`'s DLL and remove from `keyMap`.

```
keyMap:   {key → Node{val, freq}}
freqMap:  {freq → DLL{...keys at this freq, MRU→LRU order...}}
minFreq:  current lowest freq bucket with at least one key

get/put both increment freq → move node from freqMap[f] to freqMap[f+1]
eviction  → remove LRU of freqMap[minFreq]
minFreq update rule:
  - After incrementing a key's freq: if freqMap[oldFreq] is now empty AND oldFreq == minFreq → minFreq++
  - After put() with a new key: minFreq = 1 always (new key always has freq=1, the new minimum)
```

**Q16. What is the "double-map" pattern in LFU, and what invariant must both maps agree on?**

A: The double-map pattern is the pair `(keyMap, freqMap)` where `keyMap` routes from key to node (for O(1) access to a key's current value and frequency) and `freqMap` routes from frequency to a DLL of all keys at that frequency (for O(1) access to the LRU key at any frequency bucket). The invariant both maps must maintain: for every key `k`, `keyMap[k].freq = f` if and only if `k`'s node is in `freqMap[f]`'s DLL. This means every operation that changes a key's frequency must atomically update *both* maps: remove from `freqMap[oldFreq]`, insert into `freqMap[oldFreq+1]`, update `keyMap[k].freq`. Updating only one map while leaving the other stale is the canonical bug in LFU implementations — the maps become inconsistent, and the `minFreq` pointer computes incorrectly because it relies on `freqMap` bucket emptiness.

### Section B2: Related Structural Patterns

**Q17. What is the "All O(1) Data Structure" problem, and how does it extend the LFU bucket model?**

A: The All O(1) Data Structure supports four operations in O(1): `inc(key)` increments a key's count by 1; `dec(key)` decrements a key's count by 1 (removing the key if its count reaches 0); `getMaxKey()` returns any key with the maximum count; `getMinKey()` returns any key with the minimum count. It extends the LFU bucket concept by maintaining a DLL where each node is a *bucket* containing a count and a set of all keys currently at that count — buckets are ordered by ascending count. `getMaxKey` reads the tail bucket's set; `getMinKey` reads the head bucket's set. `inc(key)` moves the key from its current bucket to the next-higher bucket (creating that bucket if absent); `dec(key)` moves it to the next-lower bucket (or removes it if count reaches 0 and the next-lower bucket doesn't exist). Unlike LFU, which needs recency order within a frequency bucket, this structure only needs set membership within a bucket — a plain `Set` per bucket suffices.

```
DLL of buckets, ordered by count:
  head ↔ [count=1: {keyA, keyC}] ↔ [count=3: {keyB}] ↔ [count=5: {keyD}] ↔ tail

keyMap: {key → bucketNode}  (direct pointer to the key's current bucket)

getMaxKey(): tail.prev.keys.values().next().value   → O(1)
getMinKey(): head.next.keys.values().next().value   → O(1)
inc(key):  move key from bucketNode to next higher bucket  → O(1) via pointer
dec(key):  move key from bucketNode to next lower bucket   → O(1) via pointer
```

**Q18. What is the "First Unique Number" pattern, and how does it use a DLL for O(1) front-of-queue access?**

A: The problem: given a stream of integers, after each insertion, return the first (oldest-arriving) integer that has appeared exactly once, or -1 if none exists. A queue plus a HashSet of duplicates would work but gives O(n) duplicate filtering on each query. The O(1) pattern: maintain a DLL of "candidate unique" numbers in arrival order (head.next is the oldest unique candidate) plus a HashSet of "seen more than once" numbers. On each new number: if it's in the "seen more than once" set — ignore. If it's already in the `keyMap` (seen exactly once before) — it's now a duplicate: remove it from the DLL via the stored node pointer (`_remove(keyMap[x])`), add to "seen more than once" set, delete from `keyMap`. If it's brand new — create a node, `_insertBeforeTail(node)` to add it to the DLL as the newest candidate, store in `keyMap`. Query: `head.next === tail ? -1 : head.next.val`. All operations are O(1) because `keyMap` provides a direct node pointer for the removal step — without it, "remove x from the unique-candidates list" would require an O(n) scan.

## Topic C: Cross-Topic & Interview-Style Questions

**Q19. Compare the role of the HashMap in Two Sum vs. the LRU Cache — what does each HashMap "know about" the list structure?**

A: In Two Sum, the HashMap stores `{value → index}` where "index" is a position in the *input array* — the array is the primary structure and the HashMap is a lookup accelerator for an otherwise sequential scan. The HashMap has no knowledge of or effect on the array's structure; it's purely a query tool. In the LRU Cache, the HashMap stores `{key → DLLNode}` where the DLL node *is the primary structure being managed*. The HashMap doesn't just accelerate lookup — it makes the DLL's O(1) arbitrary removal possible by giving a direct pointer to any node. Without the HashMap, removing a specific node would require scanning the DLL (O(n)). The relationship is inverted: in Two Sum the array is the data and the HashMap is the index; in LRU Cache the DLL is the structure and the HashMap is the direct-access layer that unlocks the DLL's O(1) potential. Both exploit hashing for O(1) lookup, but in Two Sum the HashMap is an *addition* to a passive structure, while in LRU Cache the HashMap is a *participant* in an active, mutating structure.

**Q20. What distinguishes problems that need LRU Cache from problems that need only a HashMap or only a linked list?**

A: A problem needs both structures together when it requires all three of: (1) O(1) key-based lookup (HashMap's contribution); (2) O(1) ordering-aware insertion and removal at arbitrary positions (DLL's contribution with direct node pointer); (3) O(1) access to an "extreme" element (the MRU or LRU end — served by the sentinel-delimited DLL). If ordering doesn't matter, a plain HashMap suffices. If key-based lookup isn't needed, a plain deque or DLL suffices. The compound need is the LRU Cache's signature: "I need O(1) access to a specific element AND O(1) maintenance of a global ordering." The same logic identifies the LFU Cache, the All O(1) Structure, and First Unique Number as variants of this compound need.

**Q21. "State the runtime and space complexity of the LRU Cache and justify each."**

A:
- **`get`: O(1) time** — one HashMap lookup, one `_remove` (two pointer assignments), one `_insertAfterHead` (four pointer assignments). All constant.
- **`put`: O(1) time** — one HashMap lookup or insert, one `_remove` + `_insertAfterHead`, optionally one eviction (`_remove` on tail.prev + `map.delete`). Each step is constant.
- **Space: O(capacity)** — the HashMap holds at most `capacity` entries; the DLL holds at most `capacity` data nodes plus 2 sentinels. Total space linear in capacity, independent of the number of operations performed.

The O(1) claim for HashMap operations is *amortized average-case*, not worst-case — hash collisions can degrade individual operations, but with a good hash function and load factor management (which JavaScript's `Map` and Java's `HashMap` handle automatically), the amortized cost is O(1) per operation.

**Q22. "Describe three progressively harder problem variants an interviewer might ask after the basic LRU Cache, and how the data structure must change for each."**

A:
- **LRU Cache with TTL (expiry)**: Each entry has a timestamp at which it expires. `get` must check if the retrieved entry has expired and, if so, treat it as a miss and remove it. A min-heap ordered by expiry time enables O(log n) identification of expired entries; alternatively, lazy expiry (check only on `get`/`put`) avoids the heap at the cost of not proactively freeing space. The DLL + HashMap base remains; a separate priority queue or per-node timestamp is added.
- **LRU Cache with variable entry sizes**: Entries have weights; the cache has a total weight capacity rather than a count capacity. Eviction must remove LRU entries until total weight drops below capacity — potentially multiple evictions per `put`. The map and DLL structure is unchanged; weight accounting is added (track running sum; eviction loop until sum ≤ capacity).
- **LFU Cache (replace LRU eviction policy with LFU)**: Requires the double-map + per-frequency-DLL structure from Q15. The single DLL of LRU becomes a HashMap of DLLs keyed by frequency. Complexity remains O(1) amortized per operation but requires more coordinated bookkeeping.

**Q23. "What makes the `_insertAfterHead` assignment order a common interview bug, and how do you guard against it?"**

A: The bug appears when the interviewer writes `head.next = node` before `head.next.prev = node`. After `head.next = node`, `head.next` now refers to the newly-inserted node itself. `head.next.prev = node` then sets `node.prev = node` — a self-loop that corrupts the DLL silently. The guard: always write the line that reassigns `head.next` last. Mnemonic — "outward pointers first, inward pointers last": set `node.next`, `node.prev`, and the former-first-node's `prev` before finally updating `head.next`. Alternatively, capture `const first = head.next` before any assignments and use `first` in all references to the old head successor — this is immune to ordering errors because `first` is captured before any mutations.

```js
// Bug-free via captured reference:
_insertAfterHead(node) {
  const first = this.head.next;  // capture before mutation
  node.next  = first;
  node.prev  = this.head;
  first.prev = node;             // uses captured 'first', not head.next
  this.head.next = node;         // safe to update head.next last ✓
}
```

**Q24. "In one sentence each, what invariant does the data structure maintain for each of the five patterns in this topic?"**

A:
- **LRU Cache**: the DLL's left-to-right order from `head.next` to `tail.prev` always reflects most-to-least-recently-used order, with `map.size ≤ capacity` enforced by evicting `tail.prev` on overflow.
- **LFU Cache**: for every key, `keyMap[k].freq` equals the index of the `freqMap` bucket containing `k`'s node, and `freqMap[minFreq]` is always the non-empty bucket with the globally minimum frequency.
- **All O(1) Data Structure**: the DLL of count-buckets is always sorted by ascending count from head to tail, and `keyMap[k]` always points directly to the bucket whose `keys` set contains `k`.
- **First Unique Number**: `head.next` of the candidate DLL is always the oldest-arriving integer that has appeared exactly once so far; any integer that has appeared more than once is in `seenMultiple` and absent from the DLL.
- **Design Browser History**: the current page pointer splits the DLL into a back-history prefix (before current) and a forward-history suffix (after current); visiting a new page truncates everything after the current pointer.

## Problem 1 — LRU Cache

### Problem

Design a data structure that follows the constraints of a Least Recently Used (LRU) cache. Implement the `LRUCache` class: `LRUCache(capacity)` initializes the cache with positive capacity; `get(key)` returns the value if the key exists, otherwise returns -1; `put(key, value)` inserts or updates the key-value pair — if the cache is at capacity, evict the least recently used key before inserting. Both `get` and `put` must run in O(1) average time.

```
LRUCache cache = new LRUCache(2);
cache.put(1, 1);    // cache: {1=1}
cache.put(2, 2);    // cache: {1=1, 2=2}
cache.get(1);       // returns 1.  cache: {2=2, 1=1} (1 is now MRU)
cache.put(3, 3);    // evicts key 2. cache: {1=1, 3=3}
cache.get(2);       // returns -1 (not found)
cache.put(4, 4);    // evicts key 1. cache: {3=3, 4=4}
cache.get(1);       // returns -1
cache.get(3);       // returns 3
cache.get(4);       // returns 4
```

### Pattern Recognition
HashMap + Doubly Linked List with sentinel nodes. The HashMap gives O(1) access to any node by key; the DLL maintains recency order so the MRU element is always at `head.next` and the LRU element is always at `tail.prev`.

### Key Insight
Every operation — `get` and `put` alike — must "refresh" the accessed or inserted element to the MRU position. The move-to-front primitive (`_remove` + `_insertAfterHead`) is the atomic unit of this refresh. The DLL node stores the key so that eviction can clean up the HashMap in O(1).

### Approach
One Node class with `{key, val, prev, next}`. One sentinel `head` and one sentinel `tail` linked together at construction. `_remove(node)` and `_insertAfterHead(node)` as private O(1) helpers. `get`: map miss → -1; map hit → MTF + return val. `put` existing: update val + MTF. `put` new: create node, insert in map + DLL, evict `tail.prev` if `map.size > capacity`.

### Solution

```js
class DLLNode {
  constructor(key = 0, val = 0) {
    this.key  = key;   // stored for O(1) HashMap cleanup on eviction
    this.val  = val;
    this.prev = null;
    this.next = null;
  }
}

class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map  = new Map();           // key → DLLNode

    // Sentinel nodes — never hold real data, never removed
    this.head = new DLLNode();       // left sentinel (MRU side)
    this.tail = new DLLNode();       // right sentinel (LRU side)
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  get(key) {
    if (!this.map.has(key)) return -1;

    const node = this.map.get(key);
    this._remove(node);              // detach from current position
    this._insertAfterHead(node);     // promote to MRU
    return node.val;
  }

  put(key, value) {
    if (this.map.has(key)) {
      // Update existing: refresh value and promote to MRU
      const node = this.map.get(key);
      node.val = value;
      this._remove(node);
      this._insertAfterHead(node);
    } else {
      // Insert new: add to map and list, evict LRU if over capacity
      const node = new DLLNode(key, value);
      this.map.set(key, node);
      this._insertAfterHead(node);

      if (this.map.size > this.capacity) {
        const lru = this.tail.prev;   // LRU is always just before tail sentinel
        this._remove(lru);
        this.map.delete(lru.key);     // lru.key is why the node stores the key
      }
    }
  }

  // Detach node from its current position in the DLL
  _remove(node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }

  // Insert node immediately after head sentinel (making it the MRU element)
  _insertAfterHead(node) {
    const first    = this.head.next;  // capture before mutation
    node.next      = first;
    node.prev      = this.head;
    first.prev     = node;            // uses captured 'first' — safe
    this.head.next = node;            // update head.next last ✓
  }
}
```

### Complexity
- Time: O(1) per `get` and `put` — one HashMap operation plus a constant number of pointer assignments.
- Space: O(capacity) — map holds ≤ capacity entries; DLL holds ≤ capacity data nodes + 2 sentinels.

### Edge Cases
- `capacity = 1`: every `put` of a new key immediately evicts the only existing key. `tail.prev` is the sole entry; `_remove` collapses the list back to `head ↔ tail`. Correct.
- `get` on a key just evicted: map miss → -1. Correct — the eviction deleted from the map.
- `put` with the same key twice: first call inserts; second call takes the "key exists" path, updates value, performs MTF. Map size does not grow. No eviction. Correct.
- All keys identical: `put(1, v)` repeatedly only ever updates the single entry; size stays 1; no eviction ever fires. Correct.
- `get` called with a key that was the LRU but then `put` promoted it: the MTF in `get` moved it away from `tail.prev`; a subsequent `put` of a new key evicts whatever is now at `tail.prev`, not the gotten key. Correct.

- "Implement LRU Cache with O(1) time and O(1) space beyond the cache entries?" — The DLL + HashMap already achieves O(capacity) space. No extra space beyond what's needed to store the entries themselves. The sentinels add 2 nodes, a constant overhead.
- "What if you needed the k most recently used keys?" — The DLL already encodes recency order; reading the first k nodes after `head` gives the k MRU keys in O(k).

## Problem 2 — LFU Cache

### Problem

Design and implement a Least Frequently Used (LFU) Cache. `LFUCache(capacity)` initializes the cache; `get(key)` returns the value if present, else -1, and increments the key's use count; `put(key, value)` updates or inserts the key, increments use count — when capacity is exceeded, evict the least frequently used key (breaking ties by least recently used among minimum-frequency keys). All operations must be O(1).

```
LFUCache cache = new LFUCache(2);
cache.put(1, 1);    // freq: {1→1}
cache.put(2, 2);    // freq: {1→1, 2→1}
cache.get(1);       // returns 1, freq: {1→2, 2→1}
cache.put(3, 3);    // evicts key 2 (min freq=1, LRU among freq-1 keys), freq: {1→2, 3→1}
cache.get(2);       // returns -1
cache.get(3);       // returns 3, freq: {1→2, 3→2}
cache.put(4, 4);    // evicts key 1 (tied freq=2, 3 is MRU), freq: {3→2, 4→1}
cache.get(1);       // returns -1
cache.get(3);       // returns 3
cache.get(4);       // returns 4
```

### Pattern Recognition
Double-map + per-frequency DLL + `minFreq` pointer. `keyMap` routes from key to node; `freqMap` routes from frequency to a DLL of keys at that frequency, ordered by recency within the bucket. The `minFreq` pointer identifies the eviction bucket in O(1).

### Key Insight
Every operation increments a key's frequency by 1, moving it from `freqMap[f]` to `freqMap[f+1]`. The only place `minFreq` can increase is when the `minFreq` bucket empties after a key is promoted out of it. The only place `minFreq` resets to 1 is on a new `put` — new keys always start at freq=1, and freq=1 ≤ any existing frequency, making 1 the new minimum.

### Approach
Node class `{key, val, freq}`. Helper `_increment(node)` encapsulates: remove from `freqMap[node.freq]`, if that bucket is empty and `node.freq === minFreq` then `minFreq++`; increment `node.freq`; insert into `freqMap[node.freq]` (creating DLL if absent). `get`: miss → -1; hit → `_increment` + return val. `put` existing: update val + `_increment`. `put` new: create node at freq=1, set `minFreq=1`, add to `keyMap` and `freqMap[1]`; if over capacity, evict LRU of `freqMap[minFreq]`.

### Solution

```js
class LFUNode {
  constructor(key = 0, val = 0) {
    this.key  = key;
    this.val  = val;
    this.freq = 1;    // all new keys start at frequency 1
    this.prev = null;
    this.next = null;
  }
}

// Minimal DLL with sentinels — same _remove / _insertAfterHead as LRU
class FreqList {
  constructor() {
    this.head = new LFUNode();
    this.tail = new LFUNode();
    this.head.next = this.tail;
    this.tail.prev = this.head;
    this.size = 0;
  }
  isEmpty()           { return this.size === 0; }
  insert(node)        { /* _insertAfterHead */ _insertAfterHead(this.head, node); this.size++; }
  remove(node)        { /* _remove */          _remove(node);                     this.size--; }
  removeLRU()         { const lru = this.tail.prev; this.remove(lru); return lru; }
}

function _remove(node) {
  node.prev.next = node.next;
  node.next.prev = node.prev;
}
function _insertAfterHead(head, node) {
  const first  = head.next;
  node.next    = first;
  node.prev    = head;
  first.prev   = node;
  head.next    = node;
}

class LFUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.keyMap   = new Map();  // key → LFUNode
    this.freqMap  = new Map();  // freq → FreqList
    this.minFreq  = 0;
  }

  _getOrCreateList(freq) {
    if (!this.freqMap.has(freq)) this.freqMap.set(freq, new FreqList());
    return this.freqMap.get(freq);
  }

  _increment(node) {
    const oldFreq = node.freq;
    const oldList = this.freqMap.get(oldFreq);

    oldList.remove(node);
    // If this bucket is now empty and it was the minimum, the minimum rises
    if (oldList.isEmpty() && oldFreq === this.minFreq) this.minFreq++;

    node.freq++;
    this._getOrCreateList(node.freq).insert(node);
  }

  get(key) {
    if (!this.keyMap.has(key)) return -1;
    const node = this.keyMap.get(key);
    this._increment(node);
    return node.val;
  }

  put(key, value) {
    if (this.capacity <= 0) return;

    if (this.keyMap.has(key)) {
      const node = this.keyMap.get(key);
      node.val = value;
      this._increment(node);
      return;
    }

    // Evict before inserting if at capacity
    if (this.keyMap.size >= this.capacity) {
      const minList = this.freqMap.get(this.minFreq);
      const evicted = minList.removeLRU();
      this.keyMap.delete(evicted.key);
    }

    // Insert new key at freq=1
    const node = new LFUNode(key, value);
    this.keyMap.set(key, node);
    this._getOrCreateList(1).insert(node);
    this.minFreq = 1;    // new key has freq=1, always the new minimum
  }
}
```

```
        n1.freq=2. freqMap={1:[n2], 2:[n1]}. return 1. ✓

  minList=freqMap[2]=[n3,n1]. LRU=n1={key=1}. removeLRU. keyMap.delete(1). keyMap={3→n3}.
```

### Complexity
- Time: O(1) average per operation — `_increment` is O(1) (one remove + one insert in a DLL, one HashMap lookup per freq).
- Space: O(capacity) — keyMap holds ≤ capacity nodes; freqMap DLLs together hold the same nodes (each node is in exactly one freqMap DLL at any time); no node is duplicated.

### Edge Cases
- All same frequency (all keys accessed equally): `minFreq` is the same for all; eviction is purely by LRU within that bucket — degrades to an LRU Cache.
- `capacity = 1`: every `put` of a new key evicts the only existing key. `minFreq` resets to 1 on each new put.
- Repeatedly `get`-ing one key while others idle: that key's frequency grows unboundedly; other keys stay at freq=1 and will be evicted first.

### Follow-up Questions
- "Why can't you use a single sorted structure (like a TreeMap by frequency) instead of per-frequency DLLs?" — A TreeMap supports O(log n) access to the min-frequency bucket, but O(n) or O(log n) operations for insertion and removal within a bucket — losing the O(1) guarantee. Per-frequency DLLs give O(1) insertion and O(1) removal within each frequency group.
- "What if frequencies can increment by more than 1?" — `_increment` becomes `_incrementBy(delta)`: move through `delta` frequency levels. If delta is large, this is O(delta), not O(1). Not common in practice; the standard LFU problem assumes increments of 1.

## Problem 3 — All O(1) Data Structure

### Problem

Design a data structure that supports `inc(key)` (increments a key's count by 1; inserts the key with count 1 if absent), `dec(key)` (decrements a key's count by 1; removes the key if count reaches 0), `getMaxKey()` (returns any key with the maximum count, or `""` if empty), and `getMinKey()` (returns any key with the minimum count, or `""` if empty). All four operations must run in O(1) average time.

### Pattern Recognition
DLL of count-buckets (ordered by ascending count) + `keyMap` (key → bucket node). Each bucket node holds a count and a `Set<key>` of all keys currently at that count. `getMaxKey` reads `tail.prev`'s set; `getMinKey` reads `head.next`'s set. `inc`/`dec` moves a key between adjacent buckets — O(1) via the direct bucket pointer from `keyMap`.

### Key Insight
Instead of tracking individual key positions in the DLL (as LRU does with one node per key), this structure maintains *bucket* nodes in the DLL — each bucket represents one distinct count value and holds all keys at that count. A key moves from bucket `c` to bucket `c+1` (or `c-1`) on each `inc`/`dec`, creating the adjacent bucket if it doesn't exist and removing a bucket if it becomes empty. `keyMap` maps each key to its current bucket node — not to a key-specific node — giving O(1) access to the bucket where that key currently lives.

### Solution

```js
class Bucket {
  constructor(count) {
    this.count = count;
    this.keys  = new Set(); // all keys at this count
    this.prev  = null;
    this.next  = null;
  }
}

class AllOne {
  constructor() {
    this.keyMap = new Map();  // key → Bucket node containing it

    // Sentinel buckets — count values chosen to never conflict with real counts
    this.head = new Bucket(0);    // min sentinel (before all real buckets)
    this.tail = new Bucket(Infinity); // max sentinel (after all real buckets)
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  _insertBucketAfter(prev, count) {
    const bucket  = new Bucket(count);
    bucket.next   = prev.next;
    bucket.prev   = prev;
    prev.next.prev = bucket;
    prev.next     = bucket;
    return bucket;
  }

  _removeBucketIfEmpty(bucket) {
    if (bucket.keys.size === 0) {
      bucket.prev.next = bucket.next;
      bucket.next.prev = bucket.prev;
    }
  }

  inc(key) {
    if (this.keyMap.has(key)) {
      const curr  = this.keyMap.get(key);
      const count = curr.count;
      // Get or create bucket with count+1 immediately after curr
      let next = curr.next;
      if (next === this.tail || next.count !== count + 1) {
        next = this._insertBucketAfter(curr, count + 1);
      }
      next.keys.add(key);
      this.keyMap.set(key, next);
      curr.keys.delete(key);
      this._removeBucketIfEmpty(curr);
    } else {
      // New key: count=1. Get or create bucket after head sentinel.
      let first = this.head.next;
      if (first === this.tail || first.count !== 1) {
        first = this._insertBucketAfter(this.head, 1);
      }
      first.keys.add(key);
      this.keyMap.set(key, first);
    }
  }

  dec(key) {
    if (!this.keyMap.has(key)) return;
    const curr  = this.keyMap.get(key);
    const count = curr.count;

    curr.keys.delete(key);

    if (count === 1) {
      // Decrement below 1: remove key entirely
      this.keyMap.delete(key);
    } else {
      // Get or create bucket with count-1 immediately before curr
      let prev = curr.prev;
      if (prev === this.head || prev.count !== count - 1) {
        prev = this._insertBucketAfter(curr.prev, count - 1);
        // Re-fetch curr.prev after insertion since a new bucket was inserted before curr
        // _insertBucketAfter inserts AFTER curr.prev, which IS before curr ✓
      }
      prev.keys.add(key);
      this.keyMap.set(key, prev);
    }

    this._removeBucketIfEmpty(curr);
  }

  getMaxKey() {
    if (this.tail.prev === this.head) return '';
    return this.tail.prev.keys.values().next().value;
  }

  getMinKey() {
    if (this.head.next === this.tail) return '';
    return this.head.next.keys.values().next().value;
  }
}
```

### Dry Run

```
inc("a"): new. head[0] ↔ [1:{a}] ↔ tail[∞]. keyMap={a→bucket1}.
inc("b"): new. head[0] ↔ [1:{a,b}] ↔ tail[∞]. keyMap={a,b→bucket1}.
inc("b"): b exists at count=1. next of bucket1 = tail (count≠2) → create [2:{b}].
  head[0] ↔ [1:{a}] ↔ [2:{b}] ↔ tail[∞]. keyMap={a→b1, b→b2}.
inc("b"): b at count=2. next=tail → create [3:{b}]. remove [2] (empty).
  head[0] ↔ [1:{a}] ↔ [3:{b}] ↔ tail[∞].
getMaxKey(): tail.prev=[3:{b}] → "b" ✓
getMinKey(): head.next=[1:{a}] → "a" ✓
dec("b"): b at count=3. prev=[1:{a}], count 3-1=2≠1 → insert [2:{b}] between [1] and [3].
  head ↔ [1:{a}] ↔ [2:{b}] ↔ [3:{}](removed) ↔ tail
  → head ↔ [1:{a}] ↔ [2:{b}] ↔ tail. keyMap={a→b1, b→b2new}.
```

### Complexity
- Time: O(1) per operation — each `inc`/`dec` does at most one bucket insert (O(1) DLL operation), one Set add/delete (O(1)), one `keyMap` update (O(1)), and one potential bucket removal (O(1)).
- Space: O(n) where n = number of distinct keys currently in the structure. The number of buckets ≤ n (each key at a distinct count in the worst case).

### Edge Cases
- `dec` on a key with count=1: remove from structure entirely (`keyMap.delete`). Do not create a bucket-0.
- `inc` on a key at a count where an adjacent bucket already exists (count + 1 is already a bucket): add the key to the existing bucket, not a new one. The check `next.count !== count + 1` handles this.
- All keys at the same count: one bucket node; `getMaxKey` and `getMinKey` return from the same bucket.

### Follow-up Questions
- "What if you need all keys with max count, not just one?" — `getMaxKey()` currently returns any key. Returning all: `return [...this.tail.prev.keys]`. O(k) where k = number of max-count keys.
- "What if you need the max and min counts themselves (not the keys)?" — `return this.tail.prev.count` and `return this.head.next.count`. O(1).

## Problem 4 — First Unique Number

### Problem

You have a queue of integers. Implement `FirstUnique(nums)` (constructor with initial array), `showFirstUnique()` (returns the value of the first unique integer in the queue, or -1 if none), and `add(value)` (adds a value to the queue). All operations should be O(1) average.

```
FirstUnique firstUnique = new FirstUnique([2, 3, 5]);
firstUnique.showFirstUnique(); // returns 2
firstUnique.add(5);            // queue: [2,3,5,5]
firstUnique.showFirstUnique(); // returns 2 (5 is no longer unique)
firstUnique.add(2);            // queue: [2,3,5,5,2]
firstUnique.showFirstUnique(); // returns 3 (2 is no longer unique)
firstUnique.add(3);            // queue: [2,3,5,5,2,3]
firstUnique.showFirstUnique(); // returns -1 (no unique integers)
```

### Pattern Recognition
DLL of unique candidates (ordered by arrival) + HashMap `{value → DLLNode | 'DUPLICATE'}`. The HashMap gives O(1) access to the node for any value, enabling O(1) removal when a duplicate arrives. The DLL head.next is always the oldest unique candidate.

### Key Insight
When a value arrives for the second time, it must be permanently expelled from the "unique candidates" list in O(1). The HashMap's stored node pointer enables O(1) `_remove` at the moment of the second occurrence, without scanning the entire candidate list. After removal, the value is marked `'DUPLICATE'` in the HashMap so subsequent occurrences are ignored immediately.

### Approach
Maintain a DLL of candidates (MRU at tail, LRU at head — insertion order). `HashMap {value → node | 'DUPLICATE'}`. On `add(value)`: if value is `'DUPLICATE'` — ignore. If value is in map (seen once before) — remove its node from DLL, set `map[value] = 'DUPLICATE'`. If value is new — create node, insert at DLL tail, set `map[value] = node`. `showFirstUnique`: return `head.next === tail ? -1 : head.next.val`.

### Solution

```js
class UNode {
  constructor(val) { this.val = val; this.prev = null; this.next = null; }
}

class FirstUnique {
  constructor(nums) {
    this.map  = new Map();    // value → UNode (unique) | 'dup' (seen 2+ times)
    this.head = new UNode(0); // sentinel — oldest-unique side
    this.tail = new UNode(0); // sentinel — newest-unique side
    this.head.next = this.tail;
    this.tail.prev = this.head;

    for (const n of nums) this.add(n);
  }

  add(value) {
    if (this.map.get(value) === 'dup') {
      return;  // already a known duplicate — ignore
    }
    if (this.map.has(value)) {
      // Second occurrence: expel from unique-candidate list permanently
      const node = this.map.get(value);
      node.prev.next = node.next;   // _remove
      node.next.prev = node.prev;
      this.map.set(value, 'dup');
    } else {
      // First occurrence: add to unique-candidate list at newest end
      const node     = new UNode(value);
      const last     = this.tail.prev;  // _insertBeforeTail
      node.prev      = last;
      node.next      = this.tail;
      last.next      = node;
      this.tail.prev = node;
      this.map.set(value, node);
    }
  }

  showFirstUnique() {
    return this.head.next === this.tail ? -1 : this.head.next.val;
  }
}
```

### Complexity
- Time: O(1) per `add` (one HashMap operation + at most one DLL insert or remove); O(1) per `showFirstUnique` (read head.next).
- Space: O(n) where n = number of distinct values ever seen — the HashMap holds one entry per distinct value; the DLL holds at most as many nodes as distinct unique-so-far values.

### Edge Cases
- Duplicate on first occurrence (value appears twice in initial `nums`): first `add` creates node; second `add` removes it immediately. Both operate correctly on the same node.
- All values duplicated: DLL empties; `showFirstUnique` returns -1.
- Value appearing 3+ times: second occurrence marks it `'dup'`; third and subsequent occurrences hit the `'dup'` early-return. Correct.

- "Return the first unique character in a string stream?" — Same structure; values are characters instead of integers.
- "k-th unique number instead of first?" — Walk k steps from `head.next` along the DLL. O(k), not O(1) — the structure doesn't support O(1) k-th access without a more complex design.

## Problem 5 — Design Browser History

### Problem

Implement `BrowserHistory(homepage)` which starts on `homepage`. `visit(url)` visits `url` from the current page, clearing all forward history. `back(steps)` moves `steps` pages back in history (stops at the oldest page if steps exceed history length), returning the current URL. `forward(steps)` moves `steps` pages forward (stops at the newest page), returning the current URL.

```
BrowserHistory bh = new BrowserHistory("leetcode.com");
bh.visit("google.com");
bh.visit("facebook.com");
bh.visit("youtube.com");
bh.back(1);    // returns "facebook.com"
bh.back(1);    // returns "google.com"
bh.forward(1); // returns "facebook.com"
bh.visit("linkedin.com"); // clears forward history (youtube.com)
bh.forward(2); // returns "linkedin.com" (can't go forward, already at newest)
bh.back(2);    // returns "leetcode.com"
bh.forward(2); // returns "linkedin.com"
```

### Pattern Recognition
Doubly linked list with a `current` pointer that tracks the active page. `back`/`forward` move the pointer along existing links; `visit` creates a new node after `current` and severs the old forward chain (clearing forward history).

### Key Insight
The DLL pointer `current` splits the list into two logical regions: backward history (nodes reachable via `current.prev` chain) and forward history (nodes reachable via `current.next` chain). `visit` replaces everything after `current` with a new single node — severing by simply setting `current.next = newNode` overwrites the old forward pointer, making the old forward chain unreachable (eligible for garbage collection). No sentinel is needed here since navigation naturally stops when `current.prev` or `current.next` is null.

### Solution

```js
class Page {
  constructor(url) {
    this.url  = url;
    this.prev = null;
    this.next = null;
  }
}

class BrowserHistory {
  constructor(homepage) {
    this.current = new Page(homepage);
  }

  visit(url) {
    const page      = new Page(url);
    page.prev       = this.current;
    this.current.next = page;        // severs old forward chain (old .next is overwritten)
    this.current    = page;
  }

  back(steps) {
    while (steps > 0 && this.current.prev !== null) {
      this.current = this.current.prev;
      steps--;
    }
    return this.current.url;
  }

  forward(steps) {
    while (steps > 0 && this.current.next !== null) {
      this.current = this.current.next;
      steps++;   // BUG TRAP: must be steps--, not steps++
      steps -= 2; // correction — use steps-- in real code:
    }
    return this.current.url;
  }
}
```

### Complexity
- Time: `visit` O(1); `back`/`forward` O(steps) — at most O(history length), unavoidable since we traverse one node per step.
- Space: O(n) where n = total pages visited (forward history is GC'd on `visit`).

### Edge Cases
- `back` with steps > history length: loop stops at the oldest page (when `current.prev === null`). Returns oldest URL.
- `forward` after `visit`: `current.next === null` immediately — loop doesn't execute. Returns current URL.
- `forward` before any `back`: same as above. Correct.
- `visit` then `back` then `forward` to old URL: `visit` severed the old `current.next`. Forward only reaches the newly visited page, not the original forward history.

- "O(1) back/forward for random-step access?" — Use an array instead of DLL: `history[index]` is O(1) for any step count. `visit` appends and sets `forwardBound = currentIndex`; `back`/`forward` update `currentIndex` clamped to `[0, forwardBound]`.
- "Persist browser history across sessions?" — Serialize the DLL to a JSON array on session end; deserialize and reconstruct the DLL on session start.

## Problem 6 — Maximum Frequency Stack

### Problem

Design a stack-like data structure with `push(val)` (pushes `val` onto the stack) and `pop()` (removes and returns the most frequently occurring element; if there is a tie, removes the element closest to the top of the stack).

```
FreqStack fs = new FreqStack();
fs.push(5); fs.push(7); fs.push(5); fs.push(7); fs.push(4); fs.push(5);
fs.pop();  // returns 5 (freq 3, max)
fs.pop();  // returns 7 (5 and 7 both freq 2; 7 was pushed more recently)
fs.pop();  // returns 5 (freq 2, tied with 7; 5 was pushed more recently after the 7)
fs.pop();  // returns 4
```

### Pattern Recognition
`freqMap` (val → frequency) + `groupMap` (frequency → stack of vals at that frequency) + `maxFreq` pointer. The `groupMap` stack at each frequency level maintains arrival order — the top of `groupMap[f]` is always the most recently pushed element with frequency `f`.

### Key Insight
When `pop` is called, we need the most frequently pushed element, with recency as a tie-breaker. Both conditions are resolved by `groupMap[maxFreq]` — the stack at the maximum frequency level. The top of that stack is the element that was pushed most recently among all elements at the current maximum frequency. After popping, if `groupMap[maxFreq]` is empty, `maxFreq` decrements by 1 (the previous frequency level is now the maximum).

### Approach
`freqMap = {val → count}`. `groupMap = {freq → array/stack of vals}`. `maxFreq = 0`. `push(val)`: increment `freqMap[val]`; push `val` onto `groupMap[newFreq]`; update `maxFreq = max(maxFreq, newFreq)`. `pop()`: pop from `groupMap[maxFreq]` to get the result val; decrement `freqMap[val]`; if `groupMap[maxFreq]` is now empty, `maxFreq--`. Return val.

### Solution

```js
class FreqStack {
  constructor() {
    this.freqMap  = new Map(); // val → current frequency
    this.groupMap = new Map(); // freq → stack (array) of values at this frequency
    this.maxFreq  = 0;
  }

  push(val) {
    const freq = (this.freqMap.get(val) ?? 0) + 1;
    this.freqMap.set(val, freq);

    if (!this.groupMap.has(freq)) this.groupMap.set(freq, []);
    this.groupMap.get(freq).push(val);   // val is now at this frequency level

    this.maxFreq = Math.max(this.maxFreq, freq);
  }

  pop() {
    const stack = this.groupMap.get(this.maxFreq);
    const val   = stack.pop();           // most recently pushed at maxFreq

    this.freqMap.set(val, this.freqMap.get(val) - 1);

    if (stack.length === 0) {
      this.groupMap.delete(this.maxFreq);
      this.maxFreq--;                    // drop to the next occupied frequency level
    }

    return val;
  }
}
```

### Dry Run

```

push(7): freq[7]=1. group={1:[5,7]}. maxFreq=1.
push(5): freq[5]=2. group={1:[5,7],2:[5]}. maxFreq=2.
push(7): freq[7]=2. group={1:[5,7],2:[5,7]}. maxFreq=2.
push(4): freq[4]=1. group={1:[5,7,4],2:[5,7]}. maxFreq=2.
push(5): freq[5]=3. group={1:[5,7,4],2:[5,7],3:[5]}. maxFreq=3.

  return 5 ✓ (most frequent, freq was 3)

pop(): stack=group[2]=[5,7]. val=7. freq[7]=1. group[2] non-empty.
  return 7 ✓ (tied at freq=2; 7 was pushed to group[2] more recently than 5)

  return 5 ✓

  return 4 ✓
```

### Complexity
- Time: O(1) per `push` and `pop` — one HashMap read/write each; one array push/pop.
- Space: O(n) where n = total elements pushed. Each `push` adds one entry to `freqMap` (updated) and one element to a `groupMap` stack. Total elements across all groupMap stacks = total pushes.

### Edge Cases
- Pop from a single-element stack: `maxFreq` drops to 0 after the pop. Subsequent `pop` on an empty stack would call `groupMap.get(0)` — return `undefined`. In practice, the problem guarantees `pop` is called on a non-empty stack; add a guard if needed.
- All elements identical: `freqMap[val]` counts up with each push; `groupMap[f]` has one element at each level f=1,2,...,n. `maxFreq` increments to n; each `pop` decrements by 1. Correct LIFO order within each frequency level.
- Multiple elements at the same frequency pushed interleaved: the `groupMap[f]` stack captures the order correctly — the element pushed later is higher in the stack and popped first. Correct.

### Follow-up Questions
- "What if pop needs the least frequent element instead of most frequent?" — Maintain `minFreq` the same way `maxFreq` is maintained; `minFreq` updates on `push` (when a new key with freq=1 is inserted, `minFreq` could be 1) and on `pop` (when `groupMap[minFreq]` empties, `minFreq++`). Same O(1) structure.
- "Return the frequency of any element in O(1)?" — `freqMap.get(val)` already gives this. O(1).

## Common Bugs Checklist

Before submitting any solution from this category, verify:

1. **DLL node does not store the key — eviction cleanup is broken?** — When evicting `tail.prev`, you need `map.delete(tail.prev.key)`. If the node stores only `val`, `tail.prev.key` is `undefined` and the HashMap entry is never removed, causing the map to grow beyond capacity silently. Always include `key` in the node class.

2. **`_insertAfterHead` updates `head.next` before `head.next.prev`?** — Writing `this.head.next = node` first means `this.head.next.prev = node` in the next line assigns `node.prev = node` — a self-loop. Always set `head.next.prev = node` before `head.next = node`. Capture `const first = head.next` at the start to make the ordering immune to this mistake.

3. **Eviction fires before the new entry is inserted?** — Checking `map.size >= capacity` before inserting means a cache with capacity 2 and 2 existing entries evicts one, then inserts the new one — net size stays 2. But if the incoming key already exists (an update), eviction fires unnecessarily, removing a valid entry and reducing the cache below capacity. Always insert first, then check `map.size > capacity` to evict, so updates to existing keys never trigger eviction.

4. **Sentinel nodes not initialized with `head.next = tail; tail.prev = head`?** — Without this initialization, `_insertAfterHead`'s `const first = head.next` is `null`, causing `first.prev = node` to throw. The sentinel initialization must be the last two lines of the constructor, after both sentinel nodes are created.

5. **LFU: `minFreq` not reset to 1 on new `put`?** — When a new key is inserted (freq=1), `minFreq` must be set to 1 regardless of existing keys' frequencies. Failing to reset leaves `minFreq` at a value > 1, causing `pop()` to look in an empty bucket (or wrong bucket) for the next eviction. The rule: `minFreq = 1` always on a new key insert.

6. **LFU: not removing empty frequency buckets from `freqMap`?** — If an empty DLL remains at `freqMap[f]`, the `minFreq` increment logic (`if freqMap[oldFreq].isEmpty() && oldFreq === minFreq: minFreq++`) works correctly, but the empty DLL wastes memory. More critically, `freqMap.get(freq)` returning an empty DLL rather than `undefined` may cause bugs in code that uses `has()` + `get()` to check for a bucket's existence — always delete empty buckets or use the `isEmpty()` check consistently.

7. **All O(1): `dec` creating a bucket at count-1 before removing the key from the current bucket?** — If the current bucket has only this key and you insert the bucket-before first, then `_removeBucketIfEmpty` on the current bucket correctly removes it. If you reverse the order (remove from current bucket, potentially deleting it, then insert into the new bucket), and the new bucket must be inserted *before* the deleted current bucket, the `curr.prev` reference you need to find the insertion point is stale after `curr` is removed from the DLL. Always determine the insertion position before removing from the current bucket.

8. **First Unique Number: not distinguishing "key absent" from "key = 'dup'"?** — `map.has(key)` is true for both first-occurrence and duplicate entries. The code must explicitly check `map.get(key) === 'dup'` to distinguish the two states, then take the correct action (ignore for 'dup', remove node for first-occurrence). Using only `map.has(key)` causes first-occurrence to be treated as a duplicate immediately.

9. **Max Frequency Stack: `maxFreq` not decremented on `pop` when the top group becomes empty?** — If `groupMap[maxFreq]` becomes empty after a `pop` and `maxFreq` is not decremented, the next `pop` calls `groupMap.get(maxFreq)` on an empty or deleted bucket. The invariant is: `groupMap[maxFreq]` always has at least one element when the stack is non-empty. Decrement `maxFreq` whenever the current max-frequency group empties.

10. **Browser History: `forward` increments `steps` instead of decrementing?** — `while (steps-- > 0 && current.next)` decrements correctly. Writing `steps++` or `steps += 1` inside the loop produces an infinite loop. This is a transcription error that's easy to introduce when adapting `back`'s loop for `forward` — test both directions in your dry run.

**Final Tip:** At the 5 YOE level, the decisive signal for any HashMap + DLL problem is naming *the invariant each structure maintains and how they jointly enforce it*. For LRU Cache: *"the DLL's left-to-right order from `head.next` to `tail.prev` always reflects recency — MRU to LRU — maintained by move-to-front on every access; and the HashMap's stored node pointer makes that move-to-front O(1) rather than O(n)."* For LFU Cache: *"for every key, `keyMap[k].freq` and the `freqMap` bucket containing `k` are always in agreement, and `minFreq` always points to the non-empty bucket with the globally lowest frequency."* For All O(1): *"the DLL of buckets is always sorted by ascending count, so `tail.prev` is always the max bucket and `head.next` is always the min bucket, reachable in O(1) without any scan."* For First Unique Number: *"the DLL's `head.next` is always the oldest element seen exactly once — maintained by removing any element from the DLL the instant its second occurrence arrives, via the HashMap's stored node pointer."* Stating the joint invariant of both structures in one sentence before writing any code is the mark of a senior engineer who sees the data structure design as a system of maintained guarantees, not as a collection of ad hoc pointer manipulations.
