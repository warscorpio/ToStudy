# DSA: Collision Resolution — Chaining vs. Open Addressing — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

## Topic A: Why Collisions Are Inevitable

### Section A1: Fundamentals

**Q1. What is a hash collision, and why is it mathematically unavoidable?**
A: A hash collision occurs when two distinct keys produce the same bucket index after hashing. It is unavoidable by the **pigeonhole principle**: a hash table has a finite number of buckets `m`, but the key space is effectively unbounded (any string, for example, is a valid key). Whenever the number of possible keys exceeds `m` — which is always true in any real system — at least two keys must share a bucket. A good hash function minimizes collisions by distributing keys uniformly, but it cannot eliminate them. The hash table's collision resolution strategy is what determines correctness and performance in the presence of collisions, not the hash function alone.

```
Pigeonhole: 10 keys, 8 buckets → at least 2 keys must share a bucket.
Even with a perfect hash function over a known key set, collisions
arise the moment a new, unplanned key arrives.
```

**Q2. What are the two fundamental families of collision resolution?**
A: Every practical collision resolution strategy belongs to one of two families:

- **Separate chaining** (also called *closed addressing*): each bucket holds a pointer to a secondary data structure (typically a linked list, but also trees, dynamic arrays, or skip lists) that stores all entries whose keys hash to that bucket. The table array itself only holds pointers — keys live outside the array.
- **Open addressing**: all entries live *inside* the bucket array itself. On a collision, a deterministic **probing sequence** finds the next available slot within the same array. No pointers to secondary structures are needed — the array is the entire data structure.

The naming is a historical source of confusion: "closed addressing" = keys can only go in their designated bucket's chain (closed/fixed destination), while "open addressing" = keys are free to go in any open slot (open/flexible destination).

## Topic B: Separate Chaining

### Section B1: Fundamentals

**Q3. How does separate chaining work mechanically?**
A: The bucket array is an array of `m` slots, where each slot holds a pointer to the head of a linked list (initially `null`). All entries whose key hashes to bucket `i` are stored in bucket `i`'s linked list, in no particular order (or in insertion order, depending on whether you prepend or append). On `put(key, value)`: compute `i = hash(key) % m`, traverse bucket `i`'s chain looking for a matching key (update if found, prepend a new node if not). On `get(key)`: compute `i`, traverse bucket `i`'s chain comparing keys until a match is found or the chain ends. On `remove(key)`: traverse, unlink the matching node.

```
Bucket array (m=5):
index 0 → null
index 1 → [("apple", 1)] → [("fig", 7)] → null   (both hash to 1)
index 2 → [("banana", 2)] → null
index 3 → null
index 4 → [("cherry", 3)] → null
```

**Q4. What are the time complexities of chaining operations?**
A: Let `n` = number of entries, `m` = number of buckets, `α = n/m` = load factor (average chain length).

- **Average case** (uniform hashing): O(1 + α) per operation. If α is bounded by a constant (i.e., the table resizes to keep α ≤ some threshold like 0.75), this is O(1) amortized.
- **Worst case**: O(n) — if every key hashes to the same bucket, the single chain has length `n` and all operations degrade to linear scans. Java 8+ mitigates this by converting chains to red-black trees at length 8, giving O(log n) worst case per bucket.
- **Space**: O(n + m) — `n` nodes in chains plus `m` slots in the bucket array.

**Q5. Why is separate chaining the default strategy in most high-level language implementations?**
A: Several practical reasons:

1. **Simplicity of deletion**: removing a node from a linked list is O(1) once found — just unlink it. Open addressing makes deletion significantly more complex (see Q17).
2. **Graceful load factor tolerance**: chaining still works correctly at load factors above 1 (more entries than buckets) — chains just get longer. Performance degrades gradually rather than catastrophically. Open addressing *cannot* have a load factor ≥ 1 (the array would be full).
3. **Stable references**: a pointer to a chained entry remains valid after the table resizes (the entry node itself doesn't move). Open addressing rehashes entries to entirely new positions, invalidating any cached index.
4. **Simpler resize logic**: resize just rehashes entries from old chains into new bucket slots — no complications from tombstones or probe sequences.

Java's `HashMap`, Python's `dict` (pre-3.6 internal notes), and most textbook implementations use chaining. Python's `dict` and C++'s `std::unordered_map` in most implementations use chaining with dynamic arrays or lists.

**Q6. What are the drawbacks of separate chaining?**
A: Two main costs:

1. **Memory overhead**: each chained node requires an extra pointer (8 bytes on 64-bit systems) beyond the key-value pair itself. For maps with many small entries, this pointer overhead can dominate the total memory usage. The nodes are also heap-allocated and scattered in memory, causing frequent cache misses when traversing a chain.
2. **Cache unfriendliness**: traversing a linked list follows pointers to non-contiguous heap memory, with poor spatial locality. Every node access is potentially a cache miss. This is the primary reason open addressing can be faster in practice for cache-sensitive workloads, even though chaining has the same asymptotic complexity.

### Section B2: Advanced Patterns

**Q7. What is treeification, and which real implementations use it?**
A: Treeification converts a bucket's linked list into a balanced BST (specifically a red-black tree) when the chain length exceeds a threshold, and converts it back to a list when it shrinks below a lower threshold. Java's `HashMap` introduced this in Java 8 with a treeify threshold of 8 and an untreeify threshold of 6. This changes worst-case per-bucket complexity from O(n) to O(log n), protecting against **hash-flooding denial-of-service attacks** where an adversary crafts inputs that all hash to the same bucket. The trade-off: red-black tree nodes are heavier (two child pointers, a color bit, a parent pointer) than singly-linked list nodes, so treeification incurs more memory overhead per node and is only worth the cost once chains are long enough that O(log n) meaningfully beats O(n).

**Q8. What is a "dynamic array bucket" (also called vector chaining), and when is it preferred over linked list chaining?**
A: Instead of a linked list, each bucket holds a dynamic array (e.g., `ArrayList` in Java or `std::vector` in C++) of entries. Advantages: better cache locality (entries stored contiguously), no per-node pointer overhead, and faster sequential scan within a bucket. Disadvantages: insertion at an arbitrary position requires shifting elements (though appending is O(1) amortized), and the dynamic array may over-allocate (wasting memory for short chains). Vector chaining is preferred when: (a) the expected chain length is short (most entries hit distinct buckets), (b) cache performance is critical, and (c) mid-chain deletions are rare. It is rarely seen in general-purpose standard libraries but appears in performance-sensitive custom hash maps.

**Q9. How does separate chaining's performance scale with load factor?**
A: With uniform hashing, the expected chain length at any bucket is exactly `α = n/m`. Expected operations:
- Successful search: `1 + α/2` comparisons (found on average halfway through the chain).
- Unsuccessful search: `1 + α` comparisons (must traverse the entire chain).

This makes the relationship between load factor and performance linear and predictable. Doubling the load factor doubles the operation cost. This is why most chaining implementations resize at `α = 0.75` — at that point, average chain length is 0.75 (most buckets have 0 or 1 entries), and performance is near-optimal. At `α = 2`, performance is still only 2× slower, not catastrophically degraded — chaining is inherently more **load-factor tolerant** than open addressing.

## Topic C: Open Addressing

### Section C1: Fundamentals

**Q10. How does open addressing work mechanically?**
A: All key-value pairs live directly in the bucket array — no external chains. When `put(key, value)` finds bucket `hash(key) % m` already occupied by a different key, it follows a **probing sequence** to find the next candidate slot: `h(key, 0), h(key, 1), h(key, 2), ...` where `h(key, i)` is the `i`-th slot in the probe sequence for this key. The first empty slot encountered is used. `get(key)` follows the same probe sequence until it finds a matching key (success) or an empty slot (failure — the key is not present). The probe sequence must be deterministic and consistent: the sequence followed during `get` must be the same sequence that was followed during `put`.

```
Array (m=8), linear probing:
put("apple")  → hash=3 → bucket[3] empty → store at 3
put("fig")    → hash=3 → bucket[3] occupied → try 4 → empty → store at 4
put("grape")  → hash=4 → bucket[4] occupied → try 5 → empty → store at 5

State: [..., "apple" at 3, "fig" at 4, "grape" at 5, ...]
```

**Q11. What are the three main probing strategies, and how does each compute the probe sequence?**
A: The three dominant strategies differ in *how* they compute the step size between probes:

**Linear Probing**: step size is a fixed constant (usually 1). Probe sequence: `(h + 0) % m, (h + 1) % m, (h + 2) % m, ...`
```
h(key, i) = (hash(key) + i) % m
```
Simplest, best cache locality (consecutive memory locations), but suffers from **primary clustering** — long runs of occupied slots accumulate, forcing new keys to probe through existing clusters regardless of whether they hash to the same bucket.

**Quadratic Probing**: step size grows quadratically. Probe sequence: `(h + 1²) % m, (h + 2²) % m, (h + 3²) % m, ...`
```
h(key, i) = (hash(key) + c1*i + c2*i²) % m
```
Reduces primary clustering since keys with the same initial hash still follow the same quadratic sequence, but eliminates the linear run-on effect. However, it introduces **secondary clustering**: all keys hashing to the same bucket follow the *identical* probe sequence, so they still compete with each other. Also, quadratic probing is not guaranteed to visit all slots unless `m` is prime or a power of two with carefully chosen constants.

**Double Hashing**: step size is computed by a second hash function `h2(key)`. Probe sequence: `(h + i * h2(key)) % m`
```
h(key, i) = (h1(key) + i * h2(key)) % m
h2(key) must be non-zero and coprime to m (often: h2(key) = p - (key % p) for prime p < m)
```
Best distribution — different keys rarely share the same probe sequence even if they share the same initial bucket. Eliminates both primary and secondary clustering. Worst cache locality (jumps are unpredictable in size). More complex to implement correctly.

```
Comparison of probe sequences for two keys both hashing to bucket 3 (m=8):

Linear:    key1: 3,4,5,6,7,0,1,2   key2: 3,4,5,6,7,0,1,2   (identical → primary clustering)
Quadratic: key1: 3,4,7,4,3,...     key2: 3,4,7,4,3,...     (identical → secondary clustering)
Double:    key1: 3,5,7,1,3,...     key2: 3,6,1,4,7,...     (different → no clustering)
```

**Q12. What is primary clustering, and why does it hurt performance so severely?**
A: Primary clustering is the tendency of linear probing to form long contiguous runs of occupied slots. Once a run forms, any key hashing to *any slot within the run* must probe all the way to the end of the run before finding an empty slot — and then extends the run by one more slot. This means the expected probe length grows not just with load factor but with the *square* of the run length. At high load factors (α → 1), primary clustering causes average probe lengths to grow as O(1/(1-α)²) rather than O(1/(1-α)), making performance degrade much faster than theory would predict for uniform hashing. Empirically, linear probing becomes very slow at α ≥ 0.7.

**Q13. What are the time complexities of open addressing operations?**
A: Let `α = n/m` be the load factor. Open addressing requires `α < 1` strictly (the array must have at least one empty slot).

For **uniform hashing** (theoretical ideal):
- Successful search: approximately `(1/2)(1 + 1/(1-α))` probes.
- Unsuccessful search: approximately `(1/2)(1 + 1/(1-α)²)` probes.

At `α = 0.5`: successful search ≈ 1.5 probes, unsuccessful ≈ 2.5 probes.
At `α = 0.9`: successful search ≈ 5.5 probes, unsuccessful ≈ 50.5 probes.

In practice, **linear probing** degrades faster due to clustering, especially at high load factors. **Double hashing** approaches the theoretical ideal. For this reason, open addressing implementations typically resize at `α = 0.5` to `0.7`, a more conservative threshold than chaining's typical `0.75`.

### Section C2: Advanced Patterns

**Q14. Why must the table capacity `m` be a prime number (or a power of two) in open addressing?**
A: The probe sequence must visit every slot in the array before repeating, or the table may falsely report a key as absent when it actually exists in an unvisited slot.

- **Prime `m`**: with linear probing and step size 1, any prime-size table is guaranteed to visit all `m` slots (gcd(1, m) = 1 trivially). For double hashing with step `h2(key)`, a prime `m` guarantees the probe sequence cycles through all slots as long as `h2(key)` is not a multiple of `m` (which is easy to guarantee by design).
- **Power-of-two `m`**: enables fast modulo via bitwise AND (`hash & (m-1)` instead of `hash % m`). Used in many performance-critical implementations. For linear probing, any power of two works (gcd(1, m) = 1). For double hashing, `h2(key)` must be odd to guarantee full coverage (since `gcd(odd, 2^k) = 1`).

Choosing `m` = non-prime, non-power-of-two with a poorly chosen `h2` can cause the probe sequence to cycle through only a subset of slots — a subtle, hard-to-detect bug that causes `put` to report the table as full when empty slots exist.

**Q15. What is Robin Hood hashing, and how does it improve open addressing?**
A: Robin Hood hashing is a linear-probing variant that enforces a fairness property during insertion: when a new key's probe sequence collides with an existing key, compare their *probe lengths* (how far each has traveled from their home bucket). If the new key has probed *longer* than the existing key (i.e., it is "poorer"), swap them — the new key takes the existing key's slot, and the displaced key continues probing. This "takes from the rich (short probe length), gives to the poor (long probe length)" invariant keeps the *variance* of probe lengths low, dramatically reducing worst-case probe lengths. Benefits: lookup can abort early when the probe length exceeds the maximum expected probe length (the key definitely isn't there); average probe lengths stay shorter than vanilla linear probing at the same load factor. Used in: Rust's `HashMap` (pre-1.36), many high-performance hash map implementations.

```
Without Robin Hood (linear probing):
Probe lengths: [1, 1, 5, 1, 3, 8, 1, 2]  ← high variance, long tails

With Robin Hood:
Probe lengths: [2, 2, 3, 2, 3, 3, 2, 3]  ← low variance, bounded tails
```

**Q16. What is "Swiss Table" (SWAR / SIMD probing), and why is it used in production?**
A: Swiss Table (used in Abseil's `absl::flat_hash_map`, Rust's `hashbrown`, and Go's `map` since 1.19) combines open addressing with SIMD (Single Instruction, Multiple Data) hardware instructions to probe multiple slots in parallel. The table is divided into **groups** of 16 slots. Each group has a separate 16-byte **control byte array** storing one byte per slot: either a special sentinel (empty or deleted) or the low 7 bits of the key's hash (called the "H2" hash). On lookup, a single SIMD instruction compares the target H2 value against all 16 control bytes simultaneously, producing a bitmask of candidates in one CPU instruction — reducing the number of full key comparisons needed. This achieves extremely high throughput on modern CPUs, often 2-4× faster than traditional linear probing in benchmarks. The core idea: use a compact metadata layer (control bytes) to filter out non-matching slots without loading the actual key-value pairs, keeping the hot path in cache.

**Q17. How does deletion work in open addressing, and why is it significantly harder than in chaining?**
A: Deletion in open addressing cannot simply clear the slot. If slot `k` is cleared, a subsequent `get` for a key whose probe sequence passed through `k` will stop at the now-empty slot and incorrectly return "not found" — even if the key is stored in a slot further along the same probe sequence, beyond the cleared slot.

The standard solution is **tombstones** (also called "deleted" markers): instead of clearing a slot, mark it with a special `DELETED` sentinel. During `get`, tombstones are *skipped over* (the probe continues past them). During `put`, tombstones are *reused* (a new entry can be placed in a tombstone slot, since it's logically empty). During `get`, the search continues until an `EMPTY` slot (not a tombstone) is found — an `EMPTY` slot definitively means the key is absent.

```
State after deleting "fig" from bucket 4 (which was probed from bucket 3):

Before delete: [..., "apple"@3, "fig"@4, "grape"@5, EMPTY@6, ...]
After delete:  [..., "apple"@3, DELETED@4, "grape"@5, EMPTY@6, ...]

get("grape"): hash=4 → bucket[4] is DELETED → skip → bucket[5] matches → found ✓
(If we had set bucket[4] to EMPTY instead:)
get("grape"): hash=4 → bucket[4] is EMPTY → return NOT FOUND ✗
```

**Tombstone problems**: over time, tombstones accumulate — they occupy slots and inflate the effective load factor (the probe sequence must traverse them), degrading performance without the table actually being fuller. Periodic **rehashing** (rebuilding the table from scratch, dropping all tombstones) is the cure. This is an operational concern absent from chaining, where deletion is always O(1) and leaves no permanent artifacts.

## Topic D: Head-to-Head Comparison

### Section D1: Direct Comparison

**Q18. When should you choose separate chaining over open addressing?**
A: Chaining is preferable when:

- **Deletion is frequent**: chaining deletion is always O(1) with no tombstone artifacts; open addressing deletion requires tombstones and eventual rehashing.
- **Load factor can exceed 1**: chaining remains correct (just slower) at α > 1; open addressing fails to insert once α = 1.
- **Keys or values are large**: storing entries in external nodes avoids moving large objects during probes; with open addressing, large entries stored inline can cause cache thrashing during probe sequences.
- **Reference stability matters**: external chain nodes don't move during resize; open addressing moves all entries on rehash, invalidating any cached bucket index.
- **The implementation must be simple and robust**: chaining has fewer subtle correctness pitfalls (no tombstone logic, no probe sequence coverage guarantees to verify).

**Q19. When should you choose open addressing over separate chaining?**
A: Open addressing is preferable when:

- **Cache performance is critical**: open addressing stores everything in one contiguous array, exploiting spatial locality and CPU cache lines. Chaining scatters nodes across heap memory, causing frequent cache misses.
- **Memory overhead must be minimized**: no per-node pointer overhead; a well-sized open-addressed table can be more memory-efficient than a chained table at the same load factor.
- **Load factor stays well below 1**: at α ≤ 0.5, open addressing is extremely fast — most probes succeed in 1–2 steps, and the clustering problem barely manifests.
- **Iteration order doesn't need to reflect insertion order**: open addressing in a flat array can be iterated linearly with excellent cache behavior.
- **You control the implementation and can tune it**: Swiss Table, Robin Hood hashing, and similar modern variants squeeze substantially more performance out of open addressing than a naive implementation.

**Q20. What is the key performance crossover between linear probing and chaining as load factor increases?**
A: At **low load factors (α ≤ 0.5)**, linear probing typically outperforms chaining — its cache locality advantage dominates, and clustering is minimal. At **high load factors (α ≥ 0.7–0.8)**, chaining typically outperforms linear probing — clustering degrades probing severely, while chaining's expected cost only grows linearly with α. The exact crossover depends on key/value sizes, hardware cache behavior, and the hash function quality. Double hashing stays competitive with chaining at higher load factors than linear probing (it doesn't cluster), but at the cost of cache locality. This is why:

- Python's `dict` uses open addressing but keeps α ≤ 0.67 (resizes at 2/3 full).
- Java's `HashMap` uses chaining and keeps α ≤ 0.75 (can sustain higher load due to chaining's graceful degradation).
- Modern performance hash maps (Abseil, Rust's `hashbrown`) use open addressing with SIMD control bytes specifically to recover the cache advantage while mitigating clustering.

**Q21. How does each strategy behave under adversarial (worst-case) inputs?**
A: Both strategies degrade under adversarial inputs designed to maximize collisions, but differently:

- **Chaining worst case**: all `n` keys hash to the same bucket → one chain of length `n`, all operations O(n). Mitigated by Java's treeification (O(log n) per bucket) or randomized hash seeds (making the adversary's pre-computed collisions invalid).
- **Open addressing worst case**: all `n` keys hash to the same bucket → probe sequence length grows to `n` → operations O(n). Additionally, once the table is near-full (α → 1), even well-distributed keys experience extremely long probe sequences. Open addressing is more sensitive to adversarial inputs at high load factors because clustering amplifies the damage.

Both are vulnerable to **hash-flooding attacks** without randomized hash seeds. Python has used randomized hash seeds (enabled by default since Python 3.3); Java uses a perturbation step on `hashCode()` values before indexing.

**Q22. "A teammate proposes using open addressing with load factor 0.95 to save memory. How do you respond in a code review?"**
A: I'd flag this as a significant correctness and performance risk. At α = 0.95 with linear probing, the expected number of probes for an unsuccessful search is `(1/2)(1 + 1/(1-0.95)²) = (1/2)(1 + 400) ≈ 200` probes — essentially a near-full-table scan. Even a successful search averages around 10 probes. The "memory saved" is marginal (5% fewer slots) but the performance cost is catastrophic. I'd recommend either: (a) using chaining if high load factors are expected (it degrades linearly, not quadratically), or (b) capping the open-addressing table at α = 0.5–0.7 and accepting the memory trade-off as the cost of using open addressing. If memory is genuinely constrained, Robin Hood hashing or Swiss Table can operate at higher load factors more safely than naive linear probing.

### Section D2: Cross-Topic Scenario / Interview-Style Questions

**Q23. "Walk me through exactly what happens when two keys collide in a HashMap that uses separate chaining — from `put` to `get`."**
A: Assume `HashMap` with capacity `m=8`, and we're inserting `("apple", 1)` and `("fig", 7)`, both of which hash to bucket index `3`.

**Put("apple", 1)**:
1. Compute `hash("apple") % 8 = 3`.
2. Bucket 3 is `null`. Allocate a new node `{key:"apple", value:1, next:null}`.
3. Set `buckets[3]` to this node.

**Put("fig", 7)**:
1. Compute `hash("fig") % 8 = 3`.
2. Bucket 3 is non-null. Traverse the chain: one node, key is `"apple"` ≠ `"fig"`. Reach end of chain.
3. Allocate `{key:"fig", value:7, next:null}` and append (or prepend) to the chain.
4. Bucket 3's chain: `"apple" → "fig" → null`.

**Get("fig")**:
1. Compute `hash("fig") % 8 = 3`.
2. Traverse bucket 3's chain: first node is `"apple"` ≠ `"fig"`. Next node is `"fig"` = `"fig"`. Return `7`. ✓

**Q24. "Walk me through what happens when two keys collide in a HashMap that uses linear probing — including what breaks if you delete the first key naively."**
A: Assume array size `m=8`, and `hash("apple") = hash("fig") = 3`.

**Put("apple", 1)**:
1. `h = 3`. `arr[3]` is EMPTY. Store `("apple", 1)` at index 3.

**Put("fig", 7)** (collision):
1. `h = 3`. `arr[3]` is occupied by `"apple"` ≠ `"fig"`.
2. Probe: `h = (3+1) % 8 = 4`. `arr[4]` is EMPTY. Store `("fig", 7)` at index 4.

**Get("fig")**:
1. `h = 3`. `arr[3]` = `"apple"` ≠ `"fig"`.
2. Probe: `h = 4`. `arr[4]` = `"fig"`. Return `7`. ✓

**Naive delete("apple")** — set `arr[3] = EMPTY`:
1. `arr[3]` = EMPTY, `arr[4]` = `("fig", 7)`.

**Get("fig")** after naive delete:
1. `h = 3`. `arr[3]` is EMPTY → **return null (WRONG)** — `"fig"` was stored at index 4, but the probe stopped at the empty slot 3. ✗

**Correct delete("apple")** — set `arr[3] = DELETED` (tombstone):
1. `arr[3]` = DELETED, `arr[4]` = `("fig", 7)`.

**Get("fig")** after tombstone delete:
1. `h = 3`. `arr[3]` is DELETED → skip (continue probing).
2. `h = 4`. `arr[4]` = `"fig"`. Return `7`. ✓

**Q25. "How would you explain the difference between chaining and open addressing in one sentence each, to a junior developer?"**
A: Chaining: when two keys collide, both live in the *same bucket* — they share a linked list hanging off that bucket, and lookup means traversing the list to find your key. Open addressing: when two keys collide, the latecomer *bounces* to the next available slot in the array itself — lookup means following the same bounce pattern until you find your key or an empty slot.

**Q26. "Your system's HashMap starts performing slowly under load. What questions would you ask to diagnose whether the root cause is a collision resolution issue?"**
A: I'd ask: (1) *What is the current load factor?* — if it's high (>0.75 for chaining, >0.6 for open addressing), resize thresholds may be misconfigured. (2) *Is the hash function producing a uniform distribution?* — check the distribution of bucket occupancies; if one or a few buckets are disproportionately large, the hash function is poor or the keys have a pattern (e.g., all integers that are multiples of `m`). (3) *Is deletion frequent?* — in an open-addressed table, excessive tombstones inflate effective load factor without triggering a resize (since the count of live entries is used for load factor, not the count of non-EMPTY slots). (4) *What are the keys?* — string keys in particular may be vulnerable to hash-flooding if the hash seed is predictable. (5) *Are keys mutable, and are they being modified after insertion?* — this silently corrupts `hashCode`-based bucket routing, making entries permanently invisible regardless of the collision strategy.

## Problem 1 — Implement a HashMap with Separate Chaining

### Problem
Design a `HashMap` class without using any built-in hash table libraries. Implement:
- `put(key, value)`: insert or update
- `get(key)`: return value or -1 if absent
- `remove(key)`: delete the entry if present

Assume integer keys for simplicity.

### Pattern Recognition
Direct implementation of separate chaining — fixed-size bucket array, each bucket is a linked list of `(key, value)` nodes, with standard chain traversal for all three operations.

### Key Insight
The bucket index is computed as `key % capacity` (for integer keys). All correctness follows from: (1) traversing the correct bucket's chain for every operation, and (2) the `equals` check on keys during traversal to distinguish colliding entries within the same chain.

### Approach
Initialize an array of `m` buckets (all `null`). For `put`: traverse bucket `key % m`'s chain; update value if key found, else prepend a new node. For `get`: traverse and return value if found, else -1. For `remove`: traverse keeping a `prev` pointer, unlink the matching node.

### Solution

```js
class Node {
  constructor(key, value, next = null) {
    this.key = key;
    this.value = value;
    this.next = next;
  }
}

class MyHashMap {
  constructor() {
    this.capacity = 1013; // prime to reduce clustering on key % m
    this.buckets = new Array(this.capacity).fill(null);
  }

  _index(key) {
    return key % this.capacity;
  }

  put(key, value) {
    const idx = this._index(key);
    let node = this.buckets[idx];

    // Traverse chain: update if key exists
    while (node) {
      if (node.key === key) { node.value = value; return; }
      node = node.next;
    }

    // Key not found: prepend new node to chain (O(1) prepend vs O(n) append)
    this.buckets[idx] = new Node(key, value, this.buckets[idx]);
  }

  get(key) {
    let node = this.buckets[this._index(key)];
    while (node) {
      if (node.key === key) return node.value;
      node = node.next;
    }
    return -1; // not found
  }

  remove(key) {
    const idx = this._index(key);
    let node = this.buckets[idx], prev = null;
    while (node) {
      if (node.key === key) {
        if (prev) prev.next = node.next;   // unlink mid-chain
        else this.buckets[idx] = node.next; // unlink head
        return;
      }
      prev = node;
      node = node.next;
    }
  }
}
```

### Dry Run

```
capacity = 1013

put(1, 10):  idx = 1%1013 = 1. buckets[1] = null → prepend Node(1,10). buckets[1]→{1,10,null}
put(1014, 20): idx = 1014%1013 = 1. Traverse: key=1 ≠ 1014. End. Prepend Node(1014,20).
              buckets[1] → {1014,20} → {1,10} → null   [collision! both at idx 1]

get(1):    idx=1. Traverse: key=1014 ≠ 1 → next. key=1 = 1 → return 10. ✓
get(1014): idx=1. Traverse: key=1014 = 1014 → return 20. ✓

remove(1014): idx=1. node={1014,20}, prev=null. key matches.
              buckets[1] = node.next = {1,10} → null. ✓

get(1014): idx=1. Traverse: key=1 ≠ 1014 → next=null. return -1. ✓
```

### Complexity
- Time: O(1) average per operation (O(n/m) per chain traversal with uniform distribution).
- Space: O(n + m) — `n` nodes in chains, `m` bucket slots.

### Edge Cases
- Same key inserted twice: the first traversal finds the existing node and updates its value in-place — no duplicate entries in the chain.
- Key 0: `0 % capacity = 0`, correctly routed to bucket 0 — no special casing needed.
- Remove on absent key: the while loop simply exhausts the chain without modifying anything — safe no-op.
- Capacity choice: prime `m` reduces patterns in `key % m` that arise with structured integer keys (e.g., if all keys are multiples of 2, a power-of-two capacity would route them all to even-indexed buckets only).

### Follow-up Questions
- "Add dynamic resizing?" → Track entry count; when `count / capacity > 0.75`, allocate a new array of size `2 * capacity` (or the next prime) and re-`put` all existing nodes.
- "Extend to string keys?" → Replace `_index` with a polynomial rolling hash: `sum(key.charCodeAt(i) * 31^i) % capacity`.

## Problem 2 — Implement a HashMap with Linear Probing (Open Addressing)

### Problem
Same interface as Problem 1 (`put`, `get`, `remove`) but implemented using **linear probing** (open addressing). Assume integer keys; deleted slots must use a tombstone marker so that probe sequences remain intact.

### Pattern Recognition
Open addressing with linear probing and tombstones — all entries live in a flat array; collision resolution is purely arithmetic (probe index advances by 1 each step); deletion marks slots as `DELETED` rather than `EMPTY` to preserve probe sequence integrity.

### Key Insight
Three slot states are required — `EMPTY` (never occupied, terminates a `get` probe), `DELETED` (tombstone, skipped during `get` but can be reused during `put`), and `OCCUPIED` (live entry). The distinction between `EMPTY` and `DELETED` is what makes open addressing deletion correct.

### Approach
Use a flat array of `{state, key, value}` objects. `put`: probe until EMPTY or matching key (reuse first DELETED slot seen). `get`: probe until EMPTY (not found) or matching key; skip DELETED slots. `remove`: probe until EMPTY (not found) or matching key; set state to DELETED.

### Solution

```js
const EMPTY = 0, DELETED = 1, OCCUPIED = 2;

class MyHashMapLP {
  constructor() {
    this.capacity = 1013;
    this.size = 0;
    this.table = Array.from({ length: this.capacity }, () => ({ state: EMPTY }));
  }

  _index(key) { return key % this.capacity; }

  put(key, value) {
    let idx = this._index(key);
    let firstDeleted = -1; // track first tombstone slot for potential reuse

    for (let i = 0; i < this.capacity; i++) {
      const slot = this.table[idx];

      if (slot.state === OCCUPIED && slot.key === key) {
        slot.value = value; // update existing
        return;
      }
      if (slot.state === DELETED && firstDeleted === -1) {
        firstDeleted = idx; // remember first tombstone; keep probing for key update
      }
      if (slot.state === EMPTY) {
        // Key definitely not present; insert at first tombstone (or here)
        const insertAt = firstDeleted !== -1 ? firstDeleted : idx;
        this.table[insertAt] = { state: OCCUPIED, key, value };
        this.size++;
        return;
      }

      idx = (idx + 1) % this.capacity; // linear probe step
    }

    // Table full of OCCUPIED + DELETED slots — insert at first tombstone
    if (firstDeleted !== -1) {
      this.table[firstDeleted] = { state: OCCUPIED, key, value };
      this.size++;
    }
  }

  get(key) {
    let idx = this._index(key);
    for (let i = 0; i < this.capacity; i++) {
      const slot = this.table[idx];
      if (slot.state === EMPTY) return -1;              // definitive "not present"
      if (slot.state === OCCUPIED && slot.key === key) return slot.value;
      // DELETED: skip and continue probing
      idx = (idx + 1) % this.capacity;
    }
    return -1;
  }

  remove(key) {
    let idx = this._index(key);
    for (let i = 0; i < this.capacity; i++) {
      const slot = this.table[idx];
      if (slot.state === EMPTY) return;    // not present
      if (slot.state === OCCUPIED && slot.key === key) {
        slot.state = DELETED; // tombstone; do NOT set to EMPTY
        this.size--;
        return;
      }
      idx = (idx + 1) % this.capacity;
    }
  }
}
```

### Dry Run

```
capacity = 1013

put(1, 10):    idx=1. table[1] is EMPTY → store {OCCUPIED,1,10} at 1. size=1.
put(1014, 20): idx=1. table[1] is OCCUPIED, key=1 ≠ 1014 → probe.
               idx=2. table[2] is EMPTY → store {OCCUPIED,1014,20} at 2. size=2.

get(1):    idx=1. table[1]={OCCUPIED,1,10} key matches → return 10. ✓
get(1014): idx=1. table[1]={OCCUPIED,1,...} key=1 ≠ 1014 → probe.
           idx=2. table[2]={OCCUPIED,1014,20} → return 20. ✓

remove(1): idx=1. key=1 matches → set table[1].state=DELETED. size=1.

get(1014): idx=1. table[1] is DELETED → skip.
           idx=2. table[2]={OCCUPIED,1014,20} → return 20. ✓  (tombstone preserved probe)

get(1):    idx=1. table[1] is DELETED → skip.
           idx=2. key=1014 ≠ 1 → probe.
           idx=3. table[3] is EMPTY → return -1. ✓
```

### Complexity
- Time: O(1) average (probe sequence length ≈ `1/(1-α)` on average for α << 1); O(n) worst case (full table, all keys collide).
- Space: O(m) — one flat array of `m` slots; no external node allocations.

### Edge Cases
- `put` on a key that already exists: must continue probing past tombstones to find the existing entry before concluding it's absent — the `firstDeleted` variable tracks the first reusable slot, but the probe *must* continue until EMPTY to rule out a duplicate key further in the sequence.
- Table accumulates many tombstones: eventually, `get` probes through a long run of DELETED slots even for missing keys. Trigger a full rehash (rebuild array from scratch, all DELETED become EMPTY) when `(size + deletedCount) / capacity > 0.7`.
- Capacity exhaustion: the `for i < capacity` loop guard prevents infinite looping if the table is entirely full of OCCUPIED + DELETED entries (a degenerate state that should not arise with proper resizing).

### Follow-up Questions
- "Why does `put` track `firstDeleted` instead of just inserting at the first DELETED slot immediately?" → Because the key might already exist further along the probe sequence (beyond the tombstone) and needs to be updated in-place, not duplicated. The probe must continue to EMPTY before confirming the key is absent, then reuse the tombstone.
- "How does quadratic probing change the implementation?" → Replace `idx = (idx + 1) % capacity` with `idx = (originalIdx + step*step) % capacity` where `step` increments per probe; also requires careful capacity choice to guarantee full coverage.

## Problem 3 — Find the First Non-Repeating Character (Chaining vs. Open Addressing perspective)

### Problem
Given a string `s`, find the index of the first character that appears only once. If no such character exists, return -1.

```
Input:  s = "leetcode"
Output: 0   ('l' appears once, at index 0)

Input:  s = "loveleetcode"
Output: 2   ('v' appears once, at index 2)

Input:  s = "aabb"
Output: -1
```

### Pattern Recognition
Frequency map — count occurrences of each character in one pass, then scan the string a second time returning the index of the first character whose count equals 1. The "HashMap" here is implemented most efficiently as a direct-address table (a fixed 26-element array for lowercase letters) — an extreme form of open addressing with a perfect hash function (no collisions possible, since each character maps to a unique index).

### Key Insight
A direct-address table (fixed array indexed by character code) is a degenerate open-addressing hash table with a perfect hash function — `index = char - 'a'` always maps to a unique slot, so no probe sequence is ever needed. This is the best case for open addressing: zero collisions, O(1) lookup with no probing overhead, fully cache-local. Recognizing when your key space is small and enumerable (26 letters, 128 ASCII characters, etc.) and substituting a direct-address table for a general HashMap is a common interview performance optimization.

### Approach
Pass 1: fill `count[s.charCodeAt(i) - 'a']++` for each character — O(n). Pass 2: scan `s` left to right; return the index of the first character with count 1. If no such character, return -1.

### Solution

```js
function firstUniqChar(s) {
  // Direct-address table: 26 slots, one per lowercase letter.
  // Perfect hash: index = char - 'a'. No collisions, no probing.
  const count = new Array(26).fill(0);

  // Pass 1: count frequencies
  for (const ch of s) {
    count[ch.charCodeAt(0) - 97]++;
  }

  // Pass 2: find first character with frequency 1
  for (let i = 0; i < s.length; i++) {
    if (count[s.charCodeAt(i) - 97] === 1) return i;
  }

  return -1;
}
```

### Dry Run

```
s = "leetcode"

Pass 1 (count frequencies):
'l' → count[11]++ = 1
'e' → count[4]++  = 1
'e' → count[4]++  = 2
't' → count[19]++ = 1
'c' → count[2]++  = 1
'o' → count[14]++ = 1
'd' → count[3]++  = 1
'e' → count[4]++  = 3

count: [0,0,1,1,3,0,...,1(l),...,1(o),...,1(t),...]
         a b c d e              l      o      t

Pass 2 (first with count=1):
i=0: 'l' → count[11]=1 → return 0 ✓
```

### Complexity
- Time: O(n) — two linear passes over `s`; each pass is O(1) per character (direct array index, no hash computation or probing).
- Space: O(1) — fixed 26-element array regardless of input size (or O(σ) where σ is the alphabet size, a constant).

### Edge Cases
- All characters identical (`"aaaa"`): both passes complete; second pass finds no count-1 character → return -1.
- Single character (`"z"`): count[25]=1; second pass at i=0 returns 0 immediately.
- Mixed case: if problem allows uppercase, normalize first (`s.toLowerCase()`) or expand to 52 slots; alternatively use a general `Map<char, int>` if the key space is not enumerable.

### Follow-up Questions
- "What if the string contained arbitrary Unicode characters, not just lowercase letters?" → A direct-address table is no longer feasible (Unicode has 140,000+ code points). Use a general HashMap (`Map` in JS, `HashMap<Character, Integer>` in Java) — fall back to chaining or open addressing. Time complexity remains O(n); space becomes O(σ) where σ is the number of distinct characters encountered.
- "What if you had to answer multiple 'first unique char' queries on a dynamically changing string?" → Maintain a `LinkedHashMap` of character → count + a queue of characters to track insertion order, updating incrementally on each character add/remove — reduces per-query cost from O(n) to O(1) amortized.

## Problem 4 — Design a Hash Set (Chaining Implementation)

### Problem
Design a `HashSet` without using built-in hash table libraries. Implement:
- `add(key)`: insert the key if not present
- `contains(key)`: return true if present
- `remove(key)`: delete the key if present

Assume non-negative integer keys.

### Pattern Recognition
Separate chaining HashSet — backed by a chained HashMap where keys map to a boolean sentinel (or simply, each bucket holds a linked list of keys with no associated value). The same chain traversal guarantees O(1) average membership with O(1) deletion and no tombstone complexity.

### Key Insight
A HashSet is a HashMap with no values — the same chain traversal logic applies, just comparing keys without returning values. The `contains` operation is the hot path in most HashSet use cases; the chaining implementation ensures it remains O(1) average even with frequent deletions (no tombstone build-up that would slow probing).

### Approach
Array of `m` linked list heads (all `null`). `add`: traverse bucket's chain; if key found, no-op; else prepend new node. `contains`: traverse chain, return true on match. `remove`: traverse with `prev` pointer, unlink matching node.

### Solution

```js
class MyHashSet {
  constructor() {
    this.capacity = 1013;
    this.buckets = new Array(this.capacity).fill(null);
  }

  _index(key) { return key % this.capacity; }

  add(key) {
    const idx = this._index(key);
    let node = this.buckets[idx];
    while (node) {
      if (node.key === key) return; // already present, no-op
      node = node.next;
    }
    // Prepend new node (O(1) insert, maintain chain)
    this.buckets[idx] = { key, next: this.buckets[idx] };
  }

  contains(key) {
    let node = this.buckets[this._index(key)];
    while (node) {
      if (node.key === key) return true;
      node = node.next;
    }
    return false;
  }

  remove(key) {
    const idx = this._index(key);
    let node = this.buckets[idx], prev = null;
    while (node) {
      if (node.key === key) {
        if (prev) prev.next = node.next;
        else this.buckets[idx] = node.next;
        return;
      }
      prev = node;
      node = node.next;
    }
  }
}
```

```
add(1014): idx=1014%1013=1. chain=[1]. key=1≠1014 → end. Prepend {key:1014, next:[1]}.
           buckets[1]→[1014]→[1]→null

contains(1):    idx=1. node={1014}: 1014≠1 → next. node={1}: 1=1 → return true. ✓
contains(1014): idx=1. node={1014}: 1014=1014 → return true. ✓
contains(2):    idx=2. chain=null → return false. ✓

              prev=null → buckets[1] = node.next = {1}. buckets[1]→[1]→null

```

### Complexity
- Time: O(1) average for all operations; O(n) worst case if all keys collide.
- Space: O(n + m) — `n` nodes, `m` bucket array slots.

### Edge Cases
- `add` duplicate: the while loop finds the existing node and returns early — the set remains correct with no duplicates in the chain.
- `remove` absent key: the while loop exhausts the chain without modification — safe no-op.
- Key 0: `0 % capacity = 0`, bucket 0 — handled correctly, no special case needed.

### Follow-up Questions
- "What real problem benefits most from a HashSet over an ArrayList?" → Duplicate detection in O(n) instead of O(n²): checking if a stream of elements contains any repeats — add each element to the set and check if `add` found it already present (or use `contains` before each `add`).
- "How does the chaining HashSet avoid the tombstone problem that open addressing has?" → Deletion simply unlinks a node from the chain — no structural artifact remains. Future `contains` calls traverse a shorter chain with no stale markers to skip, so accumulated deletions never degrade the lookup performance the way tombstones do in open addressing.

## Quick Reference — Strategy Decision Tree

```
Which collision resolution strategy should I use?
│
├── ARE DELETIONS FREQUENT?
│   ├── YES → Separate Chaining
│   │         (deletion = O(1) unlink, no tombstones, no performance artifacts)
│   └── NO  → Either strategy viable; proceed to next question
│
├── IS CACHE PERFORMANCE CRITICAL AND LOAD FACTOR WELL-CONTROLLED (α ≤ 0.5–0.6)?
│   ├── YES → Open Addressing (Linear Probing or Robin Hood / Swiss Table for production)
│   │         (contiguous array = CPU cache friendly, minimal clustering at low load)
│   └── NO  → Separate Chaining (cache misses at high load factor hurt open addressing more)
│
├── CAN THE LOAD FACTOR EXCEED 1?
│   ├── YES → Separate Chaining ONLY
│   │         (open addressing physically cannot have α ≥ 1)
│   └── NO  → Either strategy viable
│
├── DO REFERENCE STABILITY OR POINTER STABILITY MATTER?
│   ├── YES → Separate Chaining
│   │         (chain nodes don't move on resize; open addressing rehashes everything)
│   └── NO  → Either strategy viable
│
├── IS THE KEY SPACE SMALL AND ENUMERABLE (e.g., 26 letters, ASCII)?
│   └── Direct-Address Table (array indexed directly by key)
│       → perfect hash, zero collisions, O(1) with no probing or chaining overhead
│
├── WANT ORDERED ITERATION (sorted keys, range queries)?
│   └── TreeMap / TreeSet (red-black tree) — neither chaining nor open addressing gives ordering
│
└── BUILDING A PRODUCTION HIGH-PERFORMANCE HASH MAP?
    └── Open Addressing + SIMD metadata (Swiss Table / Robin Hood)
        → best cache utilization, operates safely at α ≤ 0.875 with SIMD probing
        → used in: Rust's hashbrown, Go's map, Abseil's flat_hash_map
```

## Common Bugs Checklist

Before submitting any chaining or open-addressing hash table implementation, verify:

1. **Chaining: updating an existing key, not duplicating it?** — The `put` traversal must check for an existing matching key *before* prepending a new node. Prepending unconditionally creates duplicate entries in the chain; subsequent `get` returns the first match (possibly stale) rather than the updated value.

2. **Open addressing: tombstone on delete, not EMPTY?** — Setting a deleted slot to `EMPTY` instead of `DELETED` silently breaks `get` for any key whose probe sequence passed through the deleted slot. This is the single most common open addressing bug and produces incorrect `get` → -1 results for valid keys.

3. **Open addressing: `put` must scan past tombstones before inserting at one?** — When a tombstone is found during `put`, *remember* its index but continue probing. If a matching key is found further in the sequence, update it in-place. Only insert at the tombstone if no matching key exists. Inserting at the first tombstone immediately creates a duplicate if the key already exists later in the probe sequence.

4. **Open addressing: probe sequence visits every slot?** — Verify that your `(capacity, step_size)` combination guarantees full coverage: linear probing with step 1 always works; quadratic probing requires prime or power-of-two capacity with specific constants; double hashing requires `gcd(h2(key), capacity) = 1` for all keys (use a prime capacity).

5. **Both: `equals` check on keys, not reference equality?** — `node.key === key` in JS works for primitives but not objects. For object keys, use a proper `equals` method. Reference equality on object keys produces a map that can never find any previously inserted entry, since a new lookup object is never the same reference as the inserted one.

6. **Both: capacity is a prime (or power-of-two) for good distribution?** — A capacity of 1000 means all keys that are multiples of 8 cluster into the same 125 buckets (since gcd(8,1000)=8). Use a prime near the desired size (997, 1013, 2003) to break such patterns with modulo arithmetic.

7. **Open addressing: load factor threshold is conservative enough?** — For linear probing, set the resize threshold at α ≤ 0.7 to prevent clustering from degrading performance. At α = 0.9, probe lengths become catastrophically long. Chaining can safely go to α = 0.75 or higher before resizing.

8. **Both: correct base case for new tables?** — All bucket slots should be initialized to `null` (chaining) or `{state: EMPTY}` (open addressing). In languages where array allocation does not zero-initialize, explicitly fill the array; an uninitialized slot with garbage data will cause random incorrect behavior.

**Final Tip:** At the 5 YOE level, interviewers expect you to articulate not just *how* each strategy works but *why* you'd choose one over the other for a given context — and the answer is almost never "chaining is always better" or "open addressing is always better." The decisive signal is being able to say: "Given that deletions are frequent and the load factor may exceed 0.8, chaining is safer here because tombstone accumulation in open addressing would degrade probe lengths without triggering a resize — whereas chaining degrades linearly and deletion has no lasting structural artifact." Stating the trade-off in concrete, load-factor-and-access-pattern terms — before being asked — is what separates a textbook answer from a senior engineering answer.
