# Systems Design: Consistent Hashing — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What problem does consistent hashing solve?**
A: Consistent hashing solves the problem of distributing keys (e.g., cache entries, database shards, request routing) across a dynamic set of nodes (servers, cache instances, partitions) such that adding or removing a node causes **minimal remapping** of existing keys. Naive hashing schemes (e.g., `hash(key) % numNodes`) work fine when the node count is fixed, but catastrophically remap nearly *every* key when the node count changes — because the modulus itself changes, shifting almost every key's target node.

```
Naive mod hashing with 4 nodes → 3 nodes:
key A: hash=17, 17%4=1, 17%3=2   → moved
key B: hash=8,  8%4=0,  8%3=2    → moved
key C: hash=23, 23%4=3, 23%3=2   → moved
Nearly every key gets remapped, even though only one node was removed.
```

**Q2. Why does `hash(key) % numNodes` cause near-total remapping when `numNodes` changes?**
A: The modulus operation partitions the hash space based on the *current* node count — changing that count effectively redraws every partition boundary from scratch, since `x % n` and `x % (n-1)` have almost no structural relationship for most values of `x`. There's no way to add or remove a node "locally" — the entire mapping function changes globally, forcing (on average) `(N-1)/N` of all keys to move when going from N to N-1 (or N+1) nodes.

**Q3. What is the core idea behind consistent hashing that avoids this problem?**
A: Instead of hashing keys directly into a range `[0, numNodes)` that depends on the current node count, consistent hashing maps both **nodes** and **keys** onto the same fixed, large circular hash space (commonly visualized as a "hash ring," e.g., `[0, 2^32)` or `[0, 2^160)` for SHA-1). Each key is assigned to the **first node encountered moving clockwise** around the ring from the key's hash position. Because node positions on the ring don't depend on how many other nodes exist, adding or removing a single node only affects the keys that fall in the ring-arc immediately adjacent to that node — every other key's assignment is completely undisturbed.

```
Ring positions (simplified, small range 0-100):
Node A: 10   Node B: 40   Node C: 75

key with hash 55 → next node clockwise from 55 is C(75) → assigned to C
key with hash 5  → next node clockwise from 5 is A(10)  → assigned to A

If node B is removed:
key with hash 25 (was between A and B, went to B) → now goes to C(75) instead
key with hash 5  (assigned to A) → UNCHANGED, still goes to A
key with hash 90 (assigned to A, wrapping around) → UNCHANGED
Only keys that were mapped to the removed node need to move.
```

**Q4. What is the expected fraction of keys remapped when a node is added or removed in consistent hashing, and how does this compare to naive mod hashing?**
A: With N nodes, removing one node remaps only the keys that were assigned to *that specific node* — on average `1/N` of all keys, which then redistribute to the removed node's clockwise neighbor. Adding a node similarly only takes over a `1/N`-ish share of keys from its clockwise neighbor. This is a dramatic improvement over naive mod hashing's near-100% remapping — consistent hashing achieves the theoretical minimum possible remapping for a node change (you can't do better than moving exactly the keys that "belong" to the changed node).

**Q5. What is the time complexity of finding which node owns a given key in a consistent hashing implementation?**
A: If node positions are stored in a sorted structure (sorted array, or a balanced tree / skip list), finding the first node clockwise from a key's hash position is a binary search (or equivalent), giving **O(log N)** time where N is the number of nodes (or node replicas — see virtual nodes below). Adding or removing a node is also O(log N) to insert/delete its position(s) in the sorted structure, plus O(1) amortized for any bookkeeping.

```js
class ConsistentHashRing {
  constructor() {
    this.ring = []; // sorted array of { hash, node }
  }

  hashFn(key) {
    // simple string hash for demonstration; production systems use MD5/SHA-1/MurmurHash
    let h = 0;
    for (let i = 0; i < key.length; i++) {
      h = (h * 31 + key.charCodeAt(i)) >>> 0; // unsigned 32-bit
    }
    return h;
  }

  addNode(node) {
    const hash = this.hashFn(node);
    const idx = this._insertSorted({ hash, node });
    return idx;
  }

  removeNode(node) {
    const hash = this.hashFn(node);
    this.ring = this.ring.filter(entry => !(entry.hash === hash && entry.node === node));
  }

  getNode(key) {
    if (this.ring.length === 0) return null;
    const hash = this.hashFn(key);

    // binary search for the first ring entry with hash >= key's hash
    let lo = 0, hi = this.ring.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.ring[mid].hash < hash) lo = mid + 1;
      else hi = mid;
    }

    // wrap around to the first node if we've gone past the end of the ring
    return lo === this.ring.length ? this.ring[0].node : this.ring[lo].node;
  }

  _insertSorted(entry) {
    let lo = 0, hi = this.ring.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.ring[mid].hash < entry.hash) lo = mid + 1;
      else hi = mid;
    }
    this.ring.splice(lo, 0, entry);
    return lo;
  }
}
```

### Section 2: Virtual Nodes (Replicas)

**Q6. What problem arises from placing only a single point per physical node on the ring, and how do "virtual nodes" fix it?**
A: With only one ring position per physical node, the distribution of keys across nodes depends entirely on the (essentially random) spacing between a small number of points on a large ring — this can be highly **uneven** by chance, since with few points there's no law-of-large-numbers effect smoothing things out (e.g., with only 3-4 nodes, one node's arc could easily be 3x larger than another's purely by hash-function luck). **Virtual nodes** solve this by mapping each physical node to *many* points on the ring (e.g., 100-200 virtual points per physical node, each derived from a different hash of the node's identifier, like `hash(nodeId + "#0")`, `hash(nodeId + "#1")`, etc.). With many small arcs per physical node scattered around the ring, the total arc length owned by each physical node converges toward an even share, by the same statistical smoothing that makes averaging many small random samples more stable than averaging few large ones.

```js
class ConsistentHashRingWithVirtualNodes {
  constructor(virtualNodesPerPhysicalNode = 150) {
    this.ring = [];
    this.replicas = virtualNodesPerPhysicalNode;
  }

  hashFn(key) {
    let h = 0;
    for (let i = 0; i < key.length; i++) h = (h * 31 + key.charCodeAt(i)) >>> 0;
    return h;
  }

  addNode(node) {
    for (let i = 0; i < this.replicas; i++) {
      const virtualKey = `${node}#${i}`;
      const hash = this.hashFn(virtualKey);
      this._insertSorted({ hash, node });
    }
  }

  removeNode(node) {
    this.ring = this.ring.filter(entry => entry.node !== node);
  }

  getNode(key) {
    if (this.ring.length === 0) return null;
    const hash = this.hashFn(key);
    let lo = 0, hi = this.ring.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.ring[mid].hash < hash) lo = mid + 1;
      else hi = mid;
    }
    return lo === this.ring.length ? this.ring[0].node : this.ring[lo].node;
  }

  _insertSorted(entry) {
    let lo = 0, hi = this.ring.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.ring[mid].hash < entry.hash) lo = mid + 1;
      else hi = mid;
    }
    this.ring.splice(lo, 0, entry);
  }
}
```

**Q7. How does the number of virtual nodes per physical node trade off against memory and lookup cost?**
A: More virtual nodes per physical node → more even key distribution (better load balancing), but also → a larger ring data structure (more entries to store, O(N × replicas) total ring size) and a slightly larger constant factor on each O(log(N × replicas)) lookup. In practice, 100-200 virtual nodes per physical node is a common sweet spot — enough to smooth out distribution to within a few percent of perfectly even, without the ring becoming unreasonably large. Systems handling extreme scale or extreme unevenness sensitivity may tune this higher.

**Q8. How do virtual nodes help with heterogeneous node capacity (e.g., some servers have 2x the RAM/disk of others)?**
A: Assign a **proportional number of virtual nodes** to each physical node based on its relative capacity — a server with twice the capacity gets twice as many virtual points on the ring, so it naturally attracts roughly twice the share of keys/load, all while preserving the same minimal-remapping property when any single node is added or removed. This is a key practical advantage of the virtual-node approach: capacity-aware load distribution falls out of the same mechanism used for smoothing distribution, without needing a separate weighting system.

### Section 3: Rebalancing & Failure Handling

**Q9. What exactly happens to the data (not just the routing logic) when a node is added to a consistent hashing ring?**
A: When a new node's virtual points are inserted into the ring, that node becomes responsible for portions of the ring-arc previously owned by its new clockwise neighbors. In a real system (like a distributed cache or database), this means data for the keys in those newly-claimed arcs must be **physically migrated** to the new node — the ring's routing logic alone doesn't move data; the migration is a separate operational step (often handled by a background replication/rebalancing process) that must complete (or be handled gracefully via fallback/miss-then-populate) before the new node can correctly serve those keys.

**Q10. How does consistent hashing handle a node failure (not a graceful removal)?**
A: On detection of a failed node (via heartbeat timeout, health check failure, etc.), the failed node's virtual points are removed from the ring, and its keys' ownership automatically shifts to the next node(s) clockwise — this is purely a routing-table change and happens immediately/locally. However, if the failed node held the *only* copy of certain data (no replication), that data is lost until recovered from a backing store; this is why production consistent hashing systems (e.g., Amazon Dynamo, Cassandra) combine consistent hashing with **replication** — each key is stored on the N nodes encountered walking clockwise from its position (not just the first one), so a single node failure doesn't cause data loss, only a routing/rebalancing adjustment.

**Q11. What is "replication" in the context of consistent hashing, and how does it interact with the ring structure?**
A: Instead of a key being owned by exactly one node (the first one clockwise), each key is replicated to the **next R distinct physical nodes** encountered walking clockwise from the key's position (R = replication factor, e.g., 3 in Cassandra/Dynamo-style systems). This provides fault tolerance (the key survives up to R-1 node failures) and often read/write quorum-based consistency models built on top. The ring lookup logic extends naturally: instead of stopping at the first node found, continue walking clockwise, skipping virtual points that map to a physical node already included, until R distinct physical nodes have been collected.

```js
function getReplicaNodes(ring, key, replicationFactor, hashFn) {
  if (ring.length === 0) return [];
  const hash = hashFn(key);

  let lo = 0, hi = ring.length;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (ring[mid].hash < hash) lo = mid + 1;
    else hi = mid;
  }

  const replicas = [];
  const seen = new Set();
  let idx = lo % ring.length;

  while (replicas.length < replicationFactor && seen.size < ring.length) {
    const candidate = ring[idx].node;
    if (!seen.has(candidate)) {
      seen.add(candidate);
      replicas.push(candidate);
    }
    idx = (idx + 1) % ring.length;
  }

  return replicas;
}
```

**Q12. What is "hotspotting" in consistent hashing, and how can it still occur even with virtual nodes?**
A: Hotspotting occurs when a disproportionate share of *traffic* (not necessarily key *count*) lands on one node — for example, if a small number of extremely popular keys ("celebrity keys," viral content) happen to hash near each other or simply generate outsized request volume regardless of even key-count distribution. Virtual nodes solve *even distribution of key ownership*, but they don't solve *skewed access patterns* to specific keys — that requires separate techniques (e.g., request-level load shedding, key-level replication/caching layers, or "bounded load" consistent hashing variants that cap how much load any single node can absorb before spilling excess to a neighbor).

### Section 4: Advanced Patterns & Alternatives

**Q13. What is "rendezvous hashing" (Highest Random Weight, HRW), and how does it compare to ring-based consistent hashing?**
A: Rendezvous hashing computes, for each key, a weight/score for *every* node (typically `hash(key, nodeId)`), and assigns the key to the node with the **highest score**. This achieves the same minimal-remapping property as ring-based consistent hashing (removing a node only affects keys that were assigned to it, since every other key's highest-scoring node among the remaining nodes is unchanged) — without needing a ring data structure or virtual nodes at all.

```js
function rendezvousHash(key, nodes, hashFn) {
  let bestNode = null, bestScore = -Infinity;

  for (const node of nodes) {
    const score = hashFn(key + node);
    if (score > bestScore) {
      bestScore = score;
      bestNode = node;
    }
  }

  return bestNode;
}
```

Trade-off: rendezvous hashing is **O(N)** per lookup (must score every node), versus ring-based consistent hashing's **O(log N)** (or O(log(N×replicas))) — but it distributes load naturally evenly *without* needing virtual nodes at all, and has a simpler mental model and implementation. It's preferred when N (node count) is small-to-moderate and O(N) per lookup is acceptable; ring-based hashing (with virtual nodes) is preferred at larger scale where O(log N) lookup matters more than implementation simplicity.

**Q14. What is "jump consistent hash," and what specific trade-off does it make compared to ring-based approaches?**
A: Jump consistent hash is an algorithm (from a well-known Google paper) that computes, in O(log N) time and **O(1) space** (no ring data structure at all — just an integer key and node count as input), which of N nodes (numbered `0` to `N-1`) a key should map to, with the same minimal-remapping guarantee as ring-based consistent hashing. Its major limitation: nodes must be numbered **contiguously from 0 to N-1**, meaning arbitrary node removal (removing node 5 out of 10, say) isn't directly supported — only adding/removing from the *end* of the numbering cleanly fits the algorithm's model, or requires an external mapping layer between "logical slot number" and "actual physical node" to handle non-sequential removal. This makes it excellent for scenarios where nodes are added/removed in a stack-like fashion (e.g., autoscaling groups) but less flexible than ring-based hashing for arbitrary membership changes.

```js
function jumpConsistentHash(key, numBuckets) {
  let b = -1, j = 0;
  let k = BigInt(key);

  while (j < numBuckets) {
    b = j;
    k = (k * 2862933555777941757n + 1n) & 0xFFFFFFFFFFFFFFFFn;
    j = Math.floor((b + 1) / (Number(k >> 33n) / Math.pow(2, 31) + 1));
  }

  return b;
}
```

**Q15. What is "bounded-load consistent hashing," and what problem does it solve?**
A: A refinement of ring-based consistent hashing that caps how much load (e.g., request count, or key count) any single node can absorb — once a node's load reaches a configured multiple of the *average* load (e.g., 1.25x average), further keys that would have mapped to it are instead routed to the next node clockwise that still has spare capacity. This directly addresses the "even key distribution doesn't guarantee even load distribution" gap (see Q12's hotspotting discussion) at the cost of slightly more complex lookup logic and needing live load statistics per node.

**Q16. How does consistent hashing relate to sharding strategies used in distributed databases (e.g., range-based vs. hash-based sharding)?**
A: Hash-based sharding (of which consistent hashing is the dynamically-adjustable variant) distributes data based on a hash of the key, which spreads load evenly regardless of key value patterns but sacrifices the ability to do efficient **range queries** (since consecutive keys end up on essentially random, unrelated nodes). Range-based sharding preserves range-query efficiency (consecutive keys live on the same or adjacent shards) but risks uneven load if the key space isn't accessed uniformly (e.g., time-series data where recent timestamps get disproportionate traffic — "hot" shards). Consistent hashing is the standard technique specifically for the hash-based approach when the node count needs to change dynamically without a full reshard.

### Section 5: Scenario / Interview-Style Questions

**Q17. "You're designing a distributed cache layer for a service with frequently scaling server pools (nodes added/removed multiple times per day based on load). Why is consistent hashing the right choice over naive `hash(key) % numServers`?"**
A: Naive mod hashing would remap nearly every cached key on every single scaling event, effectively causing a full cache flush multiple times a day — devastating cache hit rates and hammering the backing data store with the resulting cache-miss traffic. Consistent hashing (with virtual nodes for even distribution) ensures each scaling event only remaps roughly `1/N` of keys, keeping the cache mostly warm across scaling events, which is the entire point of using a cache in a dynamically-scaling environment.

**Q18. "A teammate implements consistent hashing with just one ring position per physical node (no virtual nodes) and notices some servers are getting 3x the traffic of others. What's happening, and how do you fix it?"**
A: With very few points on a large hash ring, the arc lengths (and thus the share of keys) assigned to each node are essentially random and can vary wildly by chance — there's no statistical smoothing with so few samples. The fix is virtual nodes: map each physical node to 100-200 points on the ring instead of just one, which averages out the arc-length randomness across many small segments per node, converging the actual distribution much closer to the theoretical even share.

**Q19. "How would you extend consistent hashing to support replication for fault tolerance, and what does that change about how a client resolves 'the node' for a given key?"**
A: Instead of a client (or router) stopping at the first node found clockwise from a key's hash position, it should continue walking clockwise, collecting the next R **distinct physical nodes** (skipping virtual points belonging to a physical node already collected) to get the full replica set for that key. Reads/writes then typically go to some quorum of that replica set (e.g., write to all R, read from any 1, or various quorum configurations like Dynamo's N/R/W tunable consistency), rather than a single node — the ring's role becomes "compute the ordered replica set for a key," not "compute a single owner."

**Q20. "Compare consistent hashing (ring-based, with virtual nodes) against rendezvous hashing for a system with roughly 20 nodes and very high query volume (millions of lookups per second). Which would you pick, and why?"**
A: With only ~20 physical nodes, rendezvous hashing's O(N) per-lookup cost is trivially cheap (20 hash computations per lookup) and it avoids the ring's O(log(N × virtual nodes)) overhead and the memory cost of maintaining potentially thousands of virtual-node ring entries — for this specific scale, rendezvous hashing is likely the simpler and equally (or more) performant choice, along with a simpler implementation with fewer moving parts (no ring data structure to maintain, no virtual-node-count tuning). Ring-based consistent hashing's O(log N) advantage over rendezvous hashing's O(N) only becomes compelling at much larger node counts (hundreds to thousands of nodes), where scoring every node per lookup would become a real bottleneck.

## Problem 1 — Basic Consistent Hash Ring (Add/Remove Node, Route Key)

### Problem
Implement a consistent hashing ring supporting `addNode(node)`, `removeNode(node)`, and `getNode(key)` — where `getNode` returns the node responsible for a given key, following the "first node clockwise from the key's hash position" rule.

```
ring.addNode("serverA")
ring.addNode("serverB")
ring.addNode("serverC")
ring.getNode("user:1234") → "serverB" (for example, depending on hash values)
```

### Pattern Recognition
Classic ring-based consistent hashing with a single point per physical node — the foundational version before adding virtual nodes for better distribution.

### Key Insight
Maintaining node positions in a **sorted array** (by hash value) allows binary search to find the first node clockwise from any key's hash position in O(log N), and wrapping around to index 0 when the search goes past the end of the array correctly implements the ring's circular nature.

### Approach
Store `{ hash, node }` entries in a sorted array. `addNode`/`removeNode` insert/delete while maintaining sort order. `getNode` binary-searches for the first entry with `hash >= key's hash`, wrapping to index 0 if none is found (the key's hash is past every node's hash, so it wraps to the "first" node on the ring).

### Solution

```js
class ConsistentHashRing {
  constructor() {
    this.ring = []; // sorted by hash
  }

  hashFn(key) {
    let h = 0;
    for (let i = 0; i < key.length; i++) h = (h * 31 + key.charCodeAt(i)) >>> 0;
    return h;
  }

  addNode(node) {
    const hash = this.hashFn(node);
    const idx = this._lowerBound(hash);
    this.ring.splice(idx, 0, { hash, node });
  }

  removeNode(node) {
    const hash = this.hashFn(node);
    const idx = this._lowerBound(hash);
    if (idx < this.ring.length && this.ring[idx].hash === hash && this.ring[idx].node === node) {
      this.ring.splice(idx, 1);
    }
  }

  getNode(key) {
    if (this.ring.length === 0) return null;
    const hash = this.hashFn(key);
    const idx = this._lowerBound(hash);
    return idx === this.ring.length ? this.ring[0].node : this.ring[idx].node;
  }

  _lowerBound(hash) {
    let lo = 0, hi = this.ring.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.ring[mid].hash < hash) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  }
}
```

### Dry Run

```
ring = new ConsistentHashRing()

addNode("serverA") → hashFn("serverA") = (illustrative) 120 → ring=[{120,"serverA"}]
addNode("serverB") → hashFn("serverB") = (illustrative) 45  → ring=[{45,"serverB"},{120,"serverA"}]
addNode("serverC") → hashFn("serverC") = (illustrative) 200 → ring=[{45,"serverB"},{120,"serverA"},{200,"serverC"}]

getNode("keyX") → hashFn("keyX") = (illustrative) 60
  lowerBound(60): find first entry with hash>=60 → index 1 ({120,"serverA"})
  → returns "serverA"

getNode("keyY") → hashFn("keyY") = (illustrative) 250
  lowerBound(250): no entry has hash>=250 → idx=3=ring.length → wrap to ring[0]
  → returns "serverB"

removeNode("serverA") → ring=[{45,"serverB"},{200,"serverC"}]
getNode("keyX") → hashFn=60 → lowerBound(60): first hash>=60 → index 1 ({200,"serverC"})
  → now returns "serverC" instead of the removed "serverA" — correctly re-routed
```

### Complexity
- `addNode`/`removeNode`: O(log N) to find position + O(N) for the array splice/shift (a sorted linked structure or skip list could reduce splice cost, but the array approach is simplest to reason about for interview purposes).
- `getNode`: O(log N) binary search.
- Space: O(N) for N nodes.

### Edge Cases
- Empty ring: `getNode` returns `null` — no nodes exist to route to.
- Single node: every key maps to that one node regardless of hash value (binary search always finds it, or wraps to it).
- Hash collision between a node and a key (exact same hash value): the "first node clockwise" rule handled by `lowerBound`'s `>=` comparison naturally resolves this — the key maps to the node it collided with, which is a reasonable, well-defined choice.
- Removing a node that was never added: the guard check (`ring[idx].hash === hash && ring[idx].node === node`) prevents accidentally removing an unrelated entry that happens to occupy the computed index.

## Problem 2 — Consistent Hash Ring with Virtual Nodes

### Problem
Extend Problem 1's ring so that each physical node is represented by many virtual points on the ring, improving load distribution evenness. Demonstrate the improvement by simulating key distribution with and without virtual nodes.

```
Without virtual nodes (3 physical nodes, 1 point each):
  possible distribution: serverA=52%, serverB=12%, serverC=36%  (uneven, due to few random points)

With virtual nodes (3 physical nodes, 150 points each):
  possible distribution: serverA=34%, serverB=33%, serverC=33%  (much closer to even)
```

### Pattern Recognition
Same ring-based technique as Problem 1, but each physical node contributes many hashed "virtual" entries instead of just one, smoothing distribution via the law-of-large-numbers effect.

### Key Insight
A physical node's total "share" of the ring is the sum of many small arcs (one per virtual point) scattered pseudo-randomly around the ring, rather than one single large (and highly variable) arc. Averaging many small random quantities converges much more tightly around the expected value than averaging few large random quantities.

### Approach
For each physical node, generate `replicas` virtual keys (e.g., `"serverA#0"`, `"serverA#1"`, ..., `"serverA#149"`), hash each independently, and insert all of them into the same sorted ring structure, each tagged with the *physical* node they represent. Lookup logic is unchanged from Problem 1.

### Solution

```js
class ConsistentHashRingVirtual {
  constructor(replicas = 150) {
    this.ring = [];
    this.replicas = replicas;
  }

  hashFn(key) {
    let h = 0;
    for (let i = 0; i < key.length; i++) h = (h * 31 + key.charCodeAt(i)) >>> 0;
    return h;
  }

  addNode(node) {
    for (let i = 0; i < this.replicas; i++) {
      const hash = this.hashFn(`${node}#${i}`);
      const idx = this._lowerBound(hash);
      this.ring.splice(idx, 0, { hash, node });
    }
  }

  removeNode(node) {
    this.ring = this.ring.filter(entry => entry.node !== node);
  }

  getNode(key) {
    if (this.ring.length === 0) return null;
    const hash = this.hashFn(key);
    const idx = this._lowerBound(hash);
    return idx === this.ring.length ? this.ring[0].node : this.ring[idx].node;
  }

  _lowerBound(hash) {
    let lo = 0, hi = this.ring.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.ring[mid].hash < hash) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  }
}

// Simulate distribution evenness
function simulateDistribution(ring, numKeys) {
  const counts = {};
  for (let i = 0; i < numKeys; i++) {
    const node = ring.getNode(`key${i}`);
    counts[node] = (counts[node] || 0) + 1;
  }
  return counts;
}
```

```
{ serverA: 10120, serverB: 9850, serverC: 10030 }
// roughly 33.7%, 32.8%, 33.4% — close to the ideal 33.3% each,
// versus potentially 50%/15%/35% with only 1 point per node
```

### Complexity
- `addNode`: O(replicas × log(N × replicas)) for the insertions (or O(replicas × N × replicas) if using naive array splice repeatedly — a production system would batch-insert and re-sort, or use a more efficient sorted structure).
- `getNode`: O(log(N × replicas)) — slightly larger constant than Problem 1 due to more ring entries, but still logarithmic.
- Space: O(N × replicas).

### Edge Cases
- Very small `replicas` count (e.g., 1): degenerates to Problem 1's behavior — confirms virtual nodes are a generalization, not a different algorithm.
- Very large `replicas` count: distribution keeps improving but with diminishing returns, while ring size and lookup cost keep growing — there's a practical ceiling where more replicas isn't worth the overhead.
- Heterogeneous capacity nodes: giving a higher-capacity node more virtual points than others (see Q8) directly biases the distribution in its favor proportionally.

### Follow-up Questions
- "How do you choose the right number of virtual nodes for a production system?" → Balance desired distribution evenness (more replicas = better) against ring size/memory and lookup latency (more replicas = worse) — 100-200 is a common empirically-good starting point, tunable based on measured distribution skew in practice.
- "Does this fully solve load balancing, or just key-count balancing?" → Just key-count balancing — see Q12's hotspotting discussion for why even key distribution doesn't guarantee even *traffic* distribution.

## Problem 3 — Replication for Fault Tolerance

### Problem
Extend the virtual-node ring so that `getReplicas(key, replicationFactor)` returns the ordered list of distinct physical nodes responsible for storing that key (for fault-tolerant replication), rather than just a single owner.

```
ring.getReplicas("user:1234", 3) → ["serverB", "serverC", "serverA"]
(the 3 distinct physical nodes encountered walking clockwise from the key's position)
```

### Pattern Recognition
Extends the single-owner ring lookup into a "walk clockwise collecting N distinct physical nodes" traversal — the standard technique used by systems like Amazon Dynamo and Cassandra for replica placement.

### Key Insight
Because a single physical node may own multiple virtual points in a row (a physical node's virtual points aren't guaranteed to be evenly interspersed with other nodes' virtual points near any given ring segment), naively taking the next `replicationFactor` *ring entries* could return duplicate physical nodes. The traversal must specifically skip virtual points belonging to a physical node already included in the result set.

### Approach
Binary search for the starting position (same as single-node lookup). Then walk forward (wrapping around the ring as needed), adding each *newly seen* physical node to the result list, skipping virtual points for physical nodes already collected, until `replicationFactor` distinct physical nodes have been gathered (or all physical nodes are exhausted, if there are fewer than `replicationFactor` total).

### Solution

```js
function getReplicas(ring, key, replicationFactor, hashFn) {
  if (ring.length === 0) return [];

  const hash = hashFn(key);
  let lo = 0, hi = ring.length;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (ring[mid].hash < hash) lo = mid + 1;
    else hi = mid;
  }

  const replicas = [];
  const seen = new Set();
  let idx = lo % ring.length;
  let attempts = 0;

  while (replicas.length < replicationFactor && attempts < ring.length) {
    const candidate = ring[idx].node;
    if (!seen.has(candidate)) {
      seen.add(candidate);
      replicas.push(candidate);
    }
    idx = (idx + 1) % ring.length;
    attempts++;
  }

  return replicas;
}
```

### Dry Run

```
Simplified ring (physical nodes A, B, C, each with a few virtual points, sorted by hash):
[ {10,A}, {25,B}, {40,A}, {55,C}, {70,B}, {85,A}, {95,C} ]

key hash = 50, replicationFactor = 2

Binary search: first entry with hash>=50 → index 3 ({55,C})
idx=3, attempts=0, replicas=[], seen={}

idx=3: candidate=C, not seen → replicas=[C], seen={C}, idx=4, attempts=1
idx=4: candidate=B, not seen → replicas=[C,B], seen={C,B}, idx=5, attempts=2

replicas.length(2) === replicationFactor(2) → loop ends

Result: ["C", "B"] ✓ (2 distinct physical nodes, walking clockwise from hash 50)
```

```
Same ring, key hash = 90, replicationFactor = 3

Binary search: first entry with hash>=90 → index 6 ({95,C})
idx=6: candidate=C → replicas=[C], seen={C}, idx=0 (wrapped), attempts=1
idx=0: candidate=A → replicas=[C,A], seen={C,A}, idx=1, attempts=2
idx=1: candidate=B → replicas=[C,A,B], seen={C,A,B}, idx=2, attempts=3

replicas.length(3) === replicationFactor(3) → loop ends

Result: ["C", "A", "B"] ✓ (correctly wrapped around the ring to find all 3 distinct nodes)
```

### Complexity
- Time: O(log(N × replicas)) for the initial binary search + O(replicas_walked) for the traversal, where `replicas_walked` is bounded by the total ring size in the worst case (e.g., requesting more distinct physical nodes than exist) but is typically small (a small multiple of `replicationFactor` in practice, since physical nodes' virtual points are well-interspersed).
- Space: O(replicationFactor) for the result list and the `seen` set.

### Edge Cases
- `replicationFactor` greater than the total number of physical nodes: the `attempts < ring.length` guard prevents an infinite loop, and the function returns however many distinct physical nodes actually exist (fewer than requested) — callers must handle this gracefully (e.g., treat it as reduced fault tolerance rather than crashing).
- `replicationFactor = 1`: degenerates to the same result as Problem 2's single-owner `getNode` lookup.
- All virtual points happen to be clustered such that many consecutive ring entries belong to the same physical node: the `seen` set correctly skips over them without miscounting, though this scenario increases the number of `attempts` needed relative to `replicationFactor`.

### Follow-up Questions
- "How would a client use this replica list for reads and writes?" → Typical patterns: write to all R replicas (strong durability) or a write quorum (majority), read from any 1 replica (fast, eventually consistent) or a read quorum — the exact consistency model (Dynamo-style tunable N/R/W) is a separate design decision layered on top of the replica set computation shown here.
- "What happens during a node failure to the replicas of keys it was responsible for?" → The failed node's virtual points are removed from the ring; recomputing `getReplicas` for affected keys now returns the next available physical node in its place, and a background repair process typically re-replicates the affected data to restore the target replication factor.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve distributing keys/requests across a DYNAMIC set of nodes?
│
├── NODE COUNT IS FIXED, never changes?
│   └── Naive hash(key) % numNodes is fine — consistent hashing's benefit doesn't apply
│
├── NODE COUNT CHANGES DYNAMICALLY, minimal remapping required?
│   │
│   ├── NODE COUNT IS LARGE (hundreds+), lookup latency matters a lot?
│   │   └── Ring-based Consistent Hashing + Virtual Nodes → O(log(N×replicas)) lookup
│   │
│   ├── NODE COUNT IS SMALL-TO-MODERATE (tens), simplicity preferred?
│   │   └── Rendezvous Hashing (HRW) → O(N) lookup, no ring structure needed, naturally even
│   │
│   └── NODES ARE NUMBERED CONTIGUOUSLY 0..N-1, added/removed from the end only?
│       └── Jump Consistent Hash → O(log N) time, O(1) space, no data structure at all
│
├── NEED FAULT TOLERANCE (data survives node failure)?
│   └── Layer REPLICATION on top of any of the above: walk the ring/scoring collecting
│       R distinct physical nodes as the replica set, not just the single first match
│
├── KEY DISTRIBUTION IS EVEN BUT TRAFFIC/LOAD IS SKEWED (hotspotting)?
│   └── Bounded-Load Consistent Hashing — cap per-node load, spill excess to next node
│
└── HETEROGENEOUS NODE CAPACITY (some nodes bigger/faster than others)?
    └── Weight virtual node COUNT proportionally to each physical node's relative capacity
```

## Common Bugs Checklist

Before submitting any consistent hashing implementation, verify:

1. **Wraparound handled correctly at the ring's "end"?** — If binary search returns an index equal to the ring's length (no node found with hash ≥ key's hash), the correct behavior is to wrap to index 0, not to return `null`/throw/crash. Forgetting this breaks routing for keys hashing into the "highest" arc of the ring.

2. **Virtual node insertion uses a distinct hash per replica, not the same hash repeated?** — Each virtual point must be derived from a distinguishable input (e.g., `node + "#" + i`), not just `hash(node)` computed `replicas` times — hashing the same input repeatedly produces identical (duplicate) ring positions, defeating the purpose of virtual nodes entirely.

3. **`removeNode` removes ALL virtual points for that physical node, not just one?** — With virtual nodes, removal must filter out every ring entry tagged with that physical node (potentially 100-200 entries), not just the first one found — a partial removal leaves stale routing entries that could still route keys to a node that's supposed to be gone.

4. **Replica-set traversal skips already-seen physical nodes, not just already-seen ring entries?** — Naively taking the "next K ring entries" for a replication factor of K can return duplicate physical nodes if virtual points for one node are clustered together — must explicitly track *physical* node identity in a `seen` set, not just walk K ring positions blindly.

5. **Hash function has reasonably uniform output distribution?** — A poor-quality hash function (e.g., one with strong clustering or low entropy in the low bits) can undermine even a correctly-implemented ring/virtual-node scheme — production systems use well-vetted hash functions (MD5, SHA-1, MurmurHash) specifically for their uniform distribution properties, not just any hash.

6. **Guarding against `replicationFactor` exceeding the actual number of distinct physical nodes?** — Without a bound on traversal attempts, requesting more replicas than physical nodes exist causes an infinite loop; must cap the walk and return fewer replicas than requested if necessary, with the caller handling that gracefully.

**Final Tip:** At the 5 YOE level, interviewers expect you to state the core motivating problem before any implementation detail: "naive mod-based hashing remaps almost everything when the node count changes; consistent hashing fixes this by mapping nodes and keys onto the same fixed ring, so a node change only affects the keys adjacent to that node." From there, virtual nodes (for even distribution), replication (for fault tolerance), and the various alternatives (rendezvous hashing, jump consistent hash, bounded-load variants) are all answers to specific follow-up problems layered on top of that core idea — being able to state *which specific problem* each refinement solves (uneven distribution, node failure, hotspotting, lookup cost at scale) is what separates a strong systems-design answer from a memorized definition.
