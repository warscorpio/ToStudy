## Topic A: HashMap Internals

### Section A1: Fundamentals

**Q1. What is a HashMap, and what is its core contract?**
A: A HashMap is a data structure that maps keys to values, providing O(1) average-case lookup, insertion, and deletion. Its core contract: given a key, you can retrieve, set, or remove an associated value in expected constant time, regardless of how many entries the map holds. This is achieved by computing a numeric hash from the key, using that hash to locate a "bucket" in an underlying array, and storing the key-value pair there. The two invariants a HashMap must maintain are: (1) equal keys always land in the same bucket, and (2) a key can be retrieved by the same logic used to insert it.

```
Key → hash(key) → bucket index → bucket stores (key, value) pairs
```

**Q2. How does hashing work — what does a hash function actually do?**
A: A hash function takes an arbitrary key (string, integer, object) and returns a fixed-size integer called a hash code. That integer is then reduced to a valid array index via `index = hashCode % bucketCount` (or, in practice, `hashCode & (bucketCount - 1)` when `bucketCount` is a power of two — a faster bitwise equivalent). A good hash function distributes keys uniformly across buckets, minimizing collisions, and runs in O(1) or O(k) time where k is the key size (e.g., string length). It does *not* need to be reversible — hashing is not encryption; the only requirement is that equal keys produce equal hash codes (the reverse is not required and generally not possible to guarantee).

```
"apple" → hashCode = 93029210  → index = 93029210 % 16 = 10
"banana"→ hashCode = -1396355602 → index = (-1396355602 % 16 + 16) % 16 = 2
```

**Q3. What is a hash collision, and why is it unavoidable?**
A: A hash collision occurs when two *different* keys produce the same bucket index. Collisions are unavoidable by the pigeonhole principle: the key space is effectively infinite (any string is a valid key) while the bucket array has a finite size, so multiple keys must share at least one bucket by mathematical necessity. A well-designed HashMap handles collisions gracefully rather than preventing them — both correctness and performance depend on the collision resolution strategy.

**Q4. What are the two main collision resolution strategies?**
A: The two dominant strategies are **separate chaining** and **open addressing**.

- **Separate chaining**: Each bucket holds a linked list (or, in Java's HashMap, a balanced BST/red-black tree when the chain grows long) of all key-value pairs that hash to that bucket. Lookup traverses the chain comparing keys until it finds a match. Average chain length stays near 1 when the load factor is controlled, so lookup is O(1) average and O(n) worst-case (all keys collide into one chain).

- **Open addressing**: All entries live directly in the bucket array itself — no separate chains. On collision, a probing sequence determines the next slot to try. The three common probing strategies are linear probing (try `index+1, index+2, ...`), quadratic probing (try `index+1², index+2², ...`), and double hashing (use a second hash function to determine the step size). Open addressing can suffer from *primary clustering* (linear probing) or *secondary clustering* (quadratic probing) but has better cache locality than chaining.

```
Separate Chaining:
bucket[3] → [(key1, val1)] → [(key2, val2)] → null

Open Addressing (Linear Probing):
bucket[3] = (key1, val1)
bucket[4] = (key2, val2)   ← key2 also hashed to 3, placed at next open slot
```

**Q5. What is the load factor, and why does it matter?**
A: The load factor (`λ = n / capacity`) is the ratio of stored entries (`n`) to the number of buckets (`capacity`). It directly controls the trade-off between time and space. A higher load factor means fewer buckets per entry: collisions increase, chains grow longer (chaining) or probe sequences get longer (open addressing), degrading operations toward O(n). A lower load factor means more empty buckets: fewer collisions, faster operations, but more wasted memory. Java's HashMap uses a default load factor of **0.75** — empirically a good balance between time and space. Most implementations resize (rehash) the table when the load factor exceeds the threshold.

**Q6. What happens during a resize / rehash, and what is its amortized cost?**
A: When the load factor exceeds the threshold, the HashMap allocates a new, larger bucket array (typically 2× the current capacity), then reinserts every existing key-value pair into the new array by recomputing each key's bucket index with the new capacity. This is O(n) work for a single resize event. However, because capacity doubles each time, any individual key is rehashed at most O(log n) times across its entire lifetime in the map. The total rehashing work across all insertions is O(n), making each insertion's *amortized* cost O(1) — the same analysis as dynamic array (ArrayList) appends.

```
Before resize: capacity=8, n=7, load factor = 7/8 = 0.875 > 0.75 → trigger resize
After resize:  capacity=16, all 7 entries reinserted with new index = hashCode % 16
```

**Q7. Why must `hashCode()` and `equals()` be consistent, and what breaks if they're not?**
A: A HashMap's correctness contract requires: if `a.equals(b)` is true, then `a.hashCode() == b.hashCode()` must also be true. This is because the map uses `hashCode` to find the bucket and then `equals` to confirm the key match within that bucket. If two equal objects have different hash codes, they land in different buckets — a `get(b)` after `put(a, value)` would search the wrong bucket and return `null`, silently losing the entry. The reverse direction is not required: unequal objects may have the same hash code (that's just a collision, handled normally). Violating the `hashCode/equals` contract is a common source of subtle, hard-to-debug bugs, especially with mutable objects used as keys.

**Q8. Why should you avoid using mutable objects as HashMap keys?**
A: If a key's state changes after insertion, its `hashCode` may change too — causing the entry to be permanently "lost." Subsequent `get` calls compute the *new* hash, look in the *new* bucket, find nothing, and return `null`, even though the entry is still in the map (still sitting in the *old* bucket, now unreachable). The entry is effectively a memory leak — the map holds it but can never find it. This is why `String`, `Integer`, and other immutable types are the safest HashMap keys, and why mutable keys require extreme care (freezing the key's state for the duration of its use as a map key).

### Section A2: Advanced Patterns

**Q9. How does Java's HashMap handle worst-case collision chains — what is treeification?**
A: In Java 8+, when a single bucket's chain exceeds 8 entries (and the total capacity is ≥ 64), Java converts that chain from a linked list to a **red-black tree**. This reduces worst-case lookup in that bucket from O(n) to O(log n), protecting against deliberate hash collision attacks (where an adversary crafts keys that all hash to the same bucket, degrading a server's HashMap to O(n) per operation). When entries are removed and the tree shrinks below 6 nodes, it's converted back to a linked list. This treeification threshold is a pragmatic engineering choice — trees have higher constant factors than lists, so the crossover point (8 entries) is set where the tree's O(log n) benefit outweighs its overhead.

**Q10. What is the difference between `HashMap`, `LinkedHashMap`, and `TreeMap` in Java?**
A: All three implement the `Map` interface but differ in ordering guarantees and underlying structure:

- **HashMap**: No ordering guarantee on iteration. Pure hash table. O(1) average for all operations. The right default choice when ordering doesn't matter.
- **LinkedHashMap**: Maintains insertion order (or optionally access order) by threading a doubly-linked list through all entries in parallel with the hash table. O(1) average for all map operations, O(n) for iteration (same as HashMap, just in a defined order). Useful for LRU cache implementations (access-order mode + override `removeEldestEntry`).
- **TreeMap**: Uses a red-black tree, not a hash table. Maintains keys in sorted (natural or comparator) order. O(log n) for all operations. Supports range queries (`subMap`, `headMap`, `tailMap`, `floorKey`, `ceilingKey`) that HashMap/LinkedHashMap cannot support at all.

**Q11. How would you implement a basic HashMap from scratch?**
A: The core components: a bucket array (array of linked list heads), a hash function to compute bucket indices, and separate-chaining collision resolution.

```js
class HashMap {
  constructor(capacity = 16, loadFactor = 0.75) {
    this.capacity = capacity;
    this.loadFactor = loadFactor;
    this.size = 0;
    this.buckets = new Array(capacity).fill(null);
  }

  _hash(key) {
    let hash = 0;
    for (let i = 0; i < key.length; i++) {
      hash = (hash * 31 + key.charCodeAt(i)) & 0x7fffffff; // keep positive
    }
    return hash % this.capacity;
  }

  put(key, value) {
    const idx = this._hash(key);
    let node = this.buckets[idx];
    while (node) {
      if (node.key === key) { node.value = value; return; } // update
      node = node.next;
    }
    // prepend new node
    this.buckets[idx] = { key, value, next: this.buckets[idx] };
    this.size++;
    if (this.size / this.capacity > this.loadFactor) this._resize();
  }

  get(key) {
    let node = this.buckets[this._hash(key)];
    while (node) {
      if (node.key === key) return node.value;
      node = node.next;
    }
    return undefined;
  }

  remove(key) {
    const idx = this._hash(key);
    let node = this.buckets[idx], prev = null;
    while (node) {
      if (node.key === key) {
        if (prev) prev.next = node.next;
        else this.buckets[idx] = node.next;
        this.size--;
        return true;
      }
      prev = node; node = node.next;
    }
    return false;
  }

  _resize() {
    const old = this.buckets;
    this.capacity *= 2;
    this.buckets = new Array(this.capacity).fill(null);
    this.size = 0;
    for (const head of old) {
      let node = head;
      while (node) { this.put(node.key, node.value); node = node.next; }
    }
  }
}
```

**Q12. What is a frequency map pattern, and why is it the most common HashMap interview technique?**
A: A frequency map uses a HashMap to count occurrences of each distinct element in O(n) time and O(k) space (where k is the number of distinct elements). It replaces the O(n²) approach of repeatedly scanning the array for each element. The pattern: iterate once, incrementing `map[element]++` for each element; then query counts in O(1). This underlies a huge family of interview problems: finding duplicates, majority elements, anagrams, character frequency comparisons, first non-repeating character, top-k frequent elements, and subarrays with a given sum.

```js
function frequencyMap(arr) {
  const freq = new Map();
  for (const x of arr) freq.set(x, (freq.get(x) ?? 0) + 1);
  return freq;
}
```

## Topic B: HashSet Internals

### Section B1: Fundamentals

**Q13. What is a HashSet, and how does it differ from a HashMap?**
A: A HashSet is a collection of unique elements with O(1) average-case `add`, `contains`, and `remove`. Internally, a HashSet is implemented as a HashMap where the keys are the set's elements and all values are a dummy sentinel (Java literally uses `new Object()` as the value for every entry in `HashSet`'s backing `HashMap`). This means everything known about HashMap internals — hashing, collision resolution, load factor, rehashing — applies identically to HashSet. The only conceptual difference is the interface: HashSet exposes set semantics (membership testing, uniqueness enforcement) rather than key→value mapping semantics.

**Q14. What is the time complexity of `contains` for a HashSet vs. an ArrayList?**
A: HashSet `contains` is O(1) average (hash the element, check its bucket) vs. ArrayList `contains` which is O(n) (linear scan). This is the single most important reason to reach for a HashSet when membership testing is the dominant operation. The trade-off: HashSet uses more memory (overhead per bucket, no guaranteed ordering) while ArrayList is compact and cache-friendly for indexed access. Choosing between them is a classic time-vs-space and access-pattern trade-off.

**Q15. When does a HashSet guarantee O(1) operations, and when can it degrade?**
A: O(1) is an *average-case* guarantee, holding when the hash function distributes keys uniformly and the load factor is controlled. Degradation to O(n) can occur in two scenarios: (1) pathological hash functions that map many distinct keys to the same bucket, creating long chains, and (2) deliberate collision attacks (adversarially chosen inputs that exploit a known hash function). Java's treeification (Q9) mitigates the second scenario. In practice, with reasonable keys (strings, integers) and Java's built-in `hashCode()`, O(1) is the realistic expectation.

**Q16. How does a HashSet enforce uniqueness on `add`?**
A: When you call `add(element)`, the HashSet: (1) computes `element.hashCode()` to find the bucket, (2) traverses the bucket's chain checking `equals()` against each existing entry, (3) if a match is found, the element already exists — the add is a no-op (returns `false`), (4) if no match is found, the element is inserted as a new entry (returns `true`). The uniqueness guarantee comes entirely from the `equals` check in step 2 — this is why `equals` and `hashCode` must be correctly overridden for custom objects used in a HashSet; without it, the set may contain what appear to be duplicate entries.

**Q17. What is the difference between `HashSet`, `LinkedHashSet`, and `TreeSet` in Java?**
A: Mirrors the HashMap family:

- **HashSet**: No ordering. O(1) average operations. Right default when order doesn't matter.
- **LinkedHashSet**: Maintains insertion order via a linked list threading through entries. O(1) operations, O(n) ordered iteration. Useful when you need both uniqueness and insertion-order traversal.
- **TreeSet**: Red-black tree, no hashing. Sorted order (natural or comparator). O(log n) operations. Supports range views (`headSet`, `tailSet`, `subSet`), `floor`, `ceiling`, `first`, `last` — operations HashSet cannot support.

### Section B2: Advanced Patterns

**Q18. What is the two-sum pattern, and why does it canonically use a HashSet/HashMap?**
A: The two-sum problem asks: given an array and a target, find two indices whose values sum to the target. The O(n²) brute force checks all pairs. The O(n) HashMap approach: for each `nums[i]`, check if `target - nums[i]` already exists in a seen-elements map; if yes, the pair is found; if no, store `nums[i]` as seen and continue. The HashMap converts "has the complement been seen?" from an O(n) scan into an O(1) lookup, reducing the overall complexity by one order of magnitude. This "store what you've seen, look up the complement" pattern extends to three-sum (sort + two-pointer, or HashMap with pairs), four-sum, and many sliding-window problems.

```js
function twoSum(nums, target) {
  const seen = new Map(); // value → index
  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];
    if (seen.has(complement)) return [seen.get(complement), i];
    seen.set(nums[i], i);
  }
  return [];
}
```

**Q19. How does the sliding window + HashMap pattern work for subarray problems?**
A: Many subarray problems ask for the longest/shortest subarray satisfying a constraint (e.g., at most k distinct characters, sum equals k). The pattern: maintain a window `[left, right]`, expand `right` one step at a time, use a HashMap to track the current window's state (character counts, element frequencies, prefix sums), and advance `left` whenever the constraint is violated. The HashMap enables O(1) state queries and updates per step, keeping the overall algorithm O(n) instead of O(n²). The prefix sum variant stores `sum → earliest_index` to answer "does a subarray with sum k end here?" in O(1).

```js
// Longest subarray with at most k distinct values
function longestSubarrayKDistinct(arr, k) {
  const freq = new Map();
  let left = 0, best = 0;
  for (let right = 0; right < arr.length; right++) {
    freq.set(arr[right], (freq.get(arr[right]) ?? 0) + 1);
    while (freq.size > k) {
      const lv = arr[left++];
      if (freq.get(lv) === 1) freq.delete(lv);
      else freq.set(lv, freq.get(lv) - 1);
    }
    best = Math.max(best, right - left + 1);
  }
  return best;
}
```

**Q20. How would you implement an LRU Cache using a HashMap and a doubly-linked list?**
A: An LRU Cache combines a HashMap (O(1) key lookup) with a doubly-linked list (O(1) move-to-front on access, O(1) evict-from-tail). The HashMap maps each key to its node in the linked list. On `get`: look up the node, move it to the head (most recently used), return its value. On `put`: if the key exists, update its value and move to head; if new, insert a node at head and, if over capacity, evict the tail node and remove its key from the HashMap. Neither structure alone achieves O(1) for all operations — the HashMap provides O(1) access-by-key, the linked list provides O(1) reordering and eviction.

```js
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map();         // key → node
    this.head = { key: null, val: null }; // dummy head (MRU side)
    this.tail = { key: null, val: null }; // dummy tail (LRU side)
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  _remove(node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }

  _insertFront(node) {
    node.next = this.head.next;
    node.prev = this.head;
    this.head.next.prev = node;
    this.head.next = node;
  }

  get(key) {
    if (!this.map.has(key)) return -1;
    const node = this.map.get(key);
    this._remove(node);
    this._insertFront(node);
    return node.val;
  }

  put(key, value) {
    if (this.map.has(key)) {
      const node = this.map.get(key);
      node.val = value;
      this._remove(node);
      this._insertFront(node);
    } else {
      if (this.map.size === this.capacity) {
        const lru = this.tail.prev;
        this._remove(lru);
        this.map.delete(lru.key);
      }
      const node = { key, val: value };
      this._insertFront(node);
      this.map.set(key, node);
    }
  }
}
```

## Topic C: Cross-Topic & Interview-Style Questions

**Q21. "Why is HashMap O(1) and not O(log n) like a balanced BST?"**
A: A BST's O(log n) comes from navigating a height-log(n) tree by comparing keys at each node. A HashMap bypasses comparison-based search entirely: it computes a direct array index from the key's hash in O(1), then jumps straight to the correct bucket. If the bucket holds one entry (the ideal case with a good hash function and controlled load factor), the lookup is done in O(1). The O(log n) BST bound is a *lower bound for comparison-based structures* — HashMap avoids it by trading comparisons for arithmetic (hashing + modulo), which is why the theoretical complexity model places them in separate categories.

**Q22. "What happens if you put `null` as a key in a HashMap vs. a TreeMap?"**
A: Java's `HashMap` explicitly handles `null` keys by placing them in bucket 0 (a special case in the hash logic), so `null` is a valid key. `TreeMap` attempts to call `compareTo` (or the provided comparator) on the key during insertion — since you can't call a method on `null`, this throws a `NullPointerException`. `HashSet` similarly allows one `null` element (it's backed by HashMap); `TreeSet` throws on `null` for the same reason as `TreeMap`. This is a practical gotcha when switching collection types: code that works with `HashMap` can fail silently at runtime with `TreeMap` if null keys are present.

**Q23. "How would you design a HashMap that preserves insertion order?"**
A: Use a `LinkedHashMap`-style design: maintain a doubly-linked list threading through all entries in insertion order, in addition to the standard bucket array. Each entry node carries both its `next` pointer for the chain within its bucket *and* `before`/`after` pointers for the global insertion-order list. Iteration traverses the doubly-linked list rather than the bucket array (which is sparse and unordered). The overhead is two extra pointers per node and O(n) for the linked list — insertion, lookup, and deletion remain O(1) average; iteration becomes O(n) in insertion order rather than arbitrary bucket order.

**Q24. "You need to find all anagram groups in a list of words. Which HashMap approach do you use?"**
A: Sort each word's characters to produce a canonical key — anagrams share the same sorted form. Use a HashMap from `sortedKey → [list of words]`. One linear pass over the words (plus O(k log k) per word for sorting, where k is word length) groups all anagrams in O(n × k log k) total. This is a "canonical form as key" HashMap pattern: transform each item into a representation that's identical for items that should be grouped together, then use that as the HashMap key.

```js
function groupAnagrams(words) {
  const map = new Map();
  for (const w of words) {
    const key = w.split('').sort().join('');
    if (!map.has(key)) map.set(key, []);
    map.get(key).push(w);
  }
  return [...map.values()];
}
```

**Q25. "How do you detect a cycle in a linked list using a HashSet? And why might you prefer Floyd's algorithm instead?"**
A: HashSet approach: traverse the list, inserting each node into a `visited` set. If a node is already in the set, a cycle exists. This is O(n) time and O(n) space. Floyd's tortoise-and-hare: two pointers, one advancing one step and one advancing two steps per iteration — if they meet, a cycle exists. O(n) time and O(1) space. The HashSet approach is more intuitive and easier to explain in under 30 seconds; Floyd's is space-optimal. In an interview, mentioning both and explaining the O(1)-space trade-off is the expected strong answer, rather than presenting only one.

**Q26. "How does a HashMap handle extremely poor hash functions, and what is the worst case?"**
A: If every key hashes to the same bucket (e.g., a hash function that always returns 0), the HashMap degrades to a single linked list. Every operation — `get`, `put`, `remove` — must traverse the entire chain, making all operations O(n). This is the HashMap's worst case. Java mitigates this via treeification (O(log n) per bucket after 8 entries), but a truly terrible hash function still makes the structure much slower than O(1). This is also the basis of hash-flooding attacks: an adversary sends inputs with deliberately colliding hashes to a server, degrading its HashMap-backed data structures to O(n) per operation, causing a denial of service. Modern implementations counter this with randomized hash seeds per process startup.

**Q27. "In one sentence each, what is the core trade-off for HashMap vs. TreeMap vs. LinkedHashMap?"**
A: **HashMap**: fastest operations (O(1) average) but no ordering — use when you only need lookup/insert/delete and don't care about order. **TreeMap**: O(log n) operations but sorted keys — use when you need range queries, floor/ceiling lookups, or in-order iteration. **LinkedHashMap**: O(1) operations with insertion-order (or access-order) iteration — use when you need both speed and a predictable traversal order (e.g., LRU cache, order-preserving deduplication).

## Problem 1 — Two Sum

### Problem
Given an array `nums` and an integer `target`, return indices of the two numbers that add up to `target`. Each input has exactly one solution; you may not use the same element twice.

```
Input:  nums = [2, 7, 11, 15], target = 9
Output: [0, 1]  (nums[0] + nums[1] = 2 + 7 = 9)

Input:  nums = [3, 2, 4], target = 6
Output: [1, 2]
```

### Pattern Recognition
Complement lookup — for each element, the answer exists if and only if `target - element` has been seen before. HashMap converts that membership check from O(n) to O(1).

### Key Insight
Instead of asking "is there any other element that completes the pair?" (which requires a scan), reformulate as "has the complement already been stored?" The HashMap stores seen values and their indices; the answer is found in O(1) the moment the second half of any valid pair is encountered.

### Approach
Single pass: for each `nums[i]`, compute `complement = target - nums[i]`. If `complement` is in the map, return `[map.get(complement), i]`. Otherwise, store `nums[i] → i` in the map and continue.

### Solution

```js
function twoSum(nums, target) {
  const seen = new Map(); // value → index

  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];

    // If complement was seen earlier, we have our pair
    if (seen.has(complement)) {
      return [seen.get(complement), i];
    }

    // Otherwise, record this element for future complement checks
    seen.set(nums[i], i);
  }

  return []; // guaranteed to find a solution per problem constraints
}
```

### Dry Run

```
nums = [2, 7, 11, 15], target = 9

i=0: complement = 9-2 = 7. seen = {}. 7 not in seen. seen = {2→0}
i=1: complement = 9-7 = 2. seen = {2→0}. 2 IS in seen → return [0, 1] ✓
```

### Complexity
- Time: O(n) — single pass, each HashMap operation O(1) average.
- Space: O(n) — at most n entries in the map before a pair is found.

### Edge Cases
- Negative numbers: complement arithmetic still works correctly — no special casing needed.
- Same value used twice (e.g., `[3, 3]`, target = 6): storing index as the value ensures the two entries are distinct indices — the second `3` finds the first `3` already in the map at a different index.
- No solution: problem guarantees exactly one solution exists; in practice, return `[]` or `-1` to avoid undefined behavior.

### Follow-up Questions
- "What if the array is sorted?" → Two-pointer achieves O(1) space; no HashMap needed since you can binary-search or converge from both ends.
- "Return all pairs, not just the first?" → Collect all valid pairs rather than early-returning; use the same complement-lookup approach.
- "Three sum?" → Fix one element, reduce to two-sum on the remainder. O(n²) total with O(n) HashMap or O(n log n) with sorting + two-pointer.

## Problem 2 — Longest Substring Without Repeating Characters

### Problem
Given a string `s`, find the length of the longest substring without repeating characters.

```
Input:  s = "abcabcbb"
Output: 3   ("abc")

Input:  s = "bbbbb"
Output: 1   ("b")

Input:  s = "pwwkew"
Output: 3   ("wke")
```

### Pattern Recognition
Sliding window + HashMap — expand the window right, shrink it from the left whenever a duplicate is detected, using a HashMap to track the most recent index of each character for O(1) duplicate detection and O(1) window-shrink jumps.

### Key Insight
When `s[right]` is a character already in the current window, the window's left boundary must jump to `max(left, lastSeen[s[right]] + 1)` — past the previous occurrence of the duplicate. The `max` is critical: it ensures `left` never moves backward when the previous occurrence of the duplicate is already outside the current window.

### Approach
Maintain a `left` pointer and a HashMap `lastIndex` mapping each character to its most recent index. For each `right`, look up `lastIndex[s[right]]`; if it falls within the current window (i.e., `>= left`), advance `left` to `lastIndex[s[right]] + 1`. Always update `lastIndex[s[right]] = right` and track the window size.

### Solution

```js
function lengthOfLongestSubstring(s) {
  const lastIndex = new Map(); // char → most recent index seen
  let left = 0, best = 0;

  for (let right = 0; right < s.length; right++) {
    const ch = s[right];

    // If duplicate is within the current window, shrink from the left
    if (lastIndex.has(ch) && lastIndex.get(ch) >= left) {
      left = lastIndex.get(ch) + 1;
    }

    lastIndex.set(ch, right);
    best = Math.max(best, right - left + 1);
  }

  return best;
}
```

### Dry Run

```
s = "abcabcbb"
left=0, best=0, lastIndex={}

right=0 'a': not in window. lastIndex={a:0}. window=[0,0] size=1. best=1
right=1 'b': not in window. lastIndex={a:0,b:1}. window=[0,1] size=2. best=2
right=2 'c': not in window. lastIndex={a:0,b:1,c:2}. window=[0,2] size=3. best=3
right=3 'a': lastIndex[a]=0 >= left=0 → left=1. lastIndex={a:3,b:1,c:2}. window=[1,3] size=3. best=3
right=4 'b': lastIndex[b]=1 >= left=1 → left=2. lastIndex={a:3,b:4,c:2}. window=[2,4] size=3. best=3
right=5 'c': lastIndex[c]=2 >= left=2 → left=3. lastIndex={a:3,b:4,c:5}. window=[3,5] size=3. best=3
right=6 'b': lastIndex[b]=4 >= left=3 → left=5. lastIndex={a:3,b:6,c:5}. window=[5,6] size=2. best=3
right=7 'b': lastIndex[b]=6 >= left=5 → left=7. lastIndex={a:3,b:7,c:5}. window=[7,7] size=1. best=3

Answer: 3 ✓
```

### Complexity
- Time: O(n) — each character is visited at most twice (once by `right`, effectively once by `left` via the jump).
- Space: O(min(n, σ)) — at most one entry per distinct character in the map, where σ is the alphabet size (26 for lowercase letters, 128 for ASCII).

### Edge Cases
- Empty string: loop never executes, returns 0.
- All identical characters (`"aaaa"`): every step jumps `left` to `right`, window size is always 1, correctly returns 1.
- All distinct characters: `left` never moves, correctly returns `n`.
- The `max(left, ...)` guard: without it, `left` could jump backward to before the current window boundary, incorrectly widening the window past a known duplicate.

### Follow-up Questions
- "What if the constraint is 'at most k distinct characters' instead of 'no repeats'?" → Use a frequency map; shrink the window whenever `freq.size > k` rather than when any single character repeats.
- "What if you need to return the actual substring, not just the length?" → Track `bestLeft` alongside `best` and extract `s.slice(bestLeft, bestLeft + best)` at the end.

## Problem 3 — Group Anagrams

### Problem
Given an array of strings `strs`, group the anagrams together. Return the groups in any order.

```
Input:  strs = ["eat","tea","tan","ate","nat","bat"]
Output: [["bat"],["nat","tan"],["ate","eat","tea"]]

Input:  strs = [""]
Output: [[""]]
```

### Pattern Recognition
Canonical form as HashMap key — transform each string into a representation shared by all its anagrams, use it as a grouping key.

### Key Insight
Anagrams contain the same characters in different orders. Sorting a word's characters produces a canonical form that is identical for every word in an anagram group. Using `sortedWord → [group]` as the HashMap reduces grouping to a single linear scan over the input.

### Approach
For each word, compute `key = word.split('').sort().join('')`. Look up `key` in the map and append the word to its group; if absent, initialize a new group. Return all map values at the end.

### Solution

```js
function groupAnagrams(strs) {
  const map = new Map(); // sortedWord → [original words]

  for (const word of strs) {
    const key = word.split('').sort().join(''); // canonical anagram key

    if (!map.has(key)) map.set(key, []);
    map.get(key).push(word);
  }

  return [...map.values()];
}
```

### Dry Run

```
strs = ["eat","tea","tan","ate","nat","bat"]

"eat" → key="aet" → map={aet:["eat"]}
"tea" → key="aet" → map={aet:["eat","tea"]}
"tan" → key="ant" → map={aet:["eat","tea"], ant:["tan"]}
"ate" → key="aet" → map={aet:["eat","tea","ate"], ant:["tan"]}
"nat" → key="ant" → map={aet:["eat","tea","ate"], ant:["tan","nat"]}
"bat" → key="abt" → map={aet:["eat","tea","ate"], ant:["tan","nat"], abt:["bat"]}

Output: [["eat","tea","ate"],["tan","nat"],["bat"]] ✓
```

### Complexity
- Time: O(n × k log k) — n words, each sorted in O(k log k) where k is word length.
- Space: O(n × k) — storing all words across all groups.

### Edge Cases
- Single-character strings: all identical single characters form one group; the sort key is the character itself.
- Empty string `""`: sorts to `""`, valid key — groups with other empty strings.
- Mixed case: if the problem intends case-insensitive grouping, normalize to lowercase before sorting (`word.toLowerCase()`).
- Alternative O(n × k) key: use a character frequency array `[a_count, b_count, ..., z_count]` stringified as the key — avoids the `k log k` sort, replacing it with a linear frequency count.

### Follow-up Questions
- "Can you avoid the O(k log k) sort per word?" → Yes: compute a character frequency vector of length 26, stringify it as the key — O(k) per word, O(n × k) overall.
- "What if the strings can be very long?" → The frequency-vector key is especially valuable here since sorting becomes expensive; the frequency count remains O(k) regardless.

## Problem 4 — Subarray Sum Equals K

### Problem
Given an integer array `nums` and an integer `k`, return the total number of subarrays whose sum equals `k`.

```
Input:  nums = [1, 1, 1], k = 2
Output: 2

Input:  nums = [1, 2, 3], k = 3
Output: 2   (subarrays [3] and [1,2])
```

### Pattern Recognition
Prefix sum + HashMap — count prefix sums seen so far; a subarray `[j+1..i]` has sum `k` iff `prefixSum[i] - prefixSum[j] == k`, i.e., `prefixSum[j] == prefixSum[i] - k`. Looking up `prefixSum[i] - k` in the frequency map answers "how many earlier prefixes complete a valid subarray ending here?" in O(1).

### Key Insight
Any subarray sum is the difference of two prefix sums. By storing the count of each prefix sum seen so far in a HashMap, you can determine in O(1) — for each new prefix sum — how many earlier indices form a valid subarray ending at the current position. This converts an O(n²) two-index scan into a single O(n) pass.

### Approach
Initialize `prefixFreq = {0: 1}` (the empty prefix has sum 0, counted once). Traverse the array maintaining a running `sum`. At each position, check if `sum - k` exists in `prefixFreq` and add its count to the result; then increment `prefixFreq[sum]`.

### Solution

```js
function subarraySum(nums, k) {
  const prefixFreq = new Map();
  prefixFreq.set(0, 1); // empty prefix

  let sum = 0, count = 0;

  for (const num of nums) {
    sum += num;

    // How many earlier prefixes, when subtracted from current sum, give k?
    count += prefixFreq.get(sum - k) ?? 0;

    // Record this prefix sum for future positions
    prefixFreq.set(sum, (prefixFreq.get(sum) ?? 0) + 1);
  }

  return count;
}
```

### Dry Run

```
nums = [1, 1, 1], k = 2
prefixFreq = {0:1}, sum=0, count=0

num=1: sum=1. look up 1-2=-1 → not in map (count stays 0). prefixFreq={0:1, 1:1}
num=1: sum=2. look up 2-2=0 → count=0+1=1. prefixFreq={0:1, 1:1, 2:1}
num=1: sum=3. look up 3-2=1 → count=1+1=2. prefixFreq={0:1, 1:1, 2:1, 3:1}

Answer: 2 ✓
```

### Complexity
- Time: O(n) — single pass, O(1) HashMap operations per step.
- Space: O(n) — at most n distinct prefix sums in the map.

### Edge Cases
- Negative numbers in the array: prefix sums are no longer monotone, which breaks any two-pointer or binary-search approach — the HashMap prefix-sum approach handles negatives correctly without any changes.
- `k = 0`: subarrays with sum 0 are correctly counted — the `{0:1}` initialization correctly handles the case where the entire prefix from index 0 sums to 0.
- Duplicate prefix sums: the frequency map correctly accumulates counts — if `sum - k` has been seen 3 times, all 3 valid subarrays ending at the current position are counted in one O(1) lookup.

### Follow-up Questions
- "What if you need to return the actual subarrays, not just the count?" → Store `sum → [list of indices]` instead of frequencies; reconstruct subarrays from the index pairs.
- "Longest subarray with sum k?" → Store `sum → first_index` (not count); when `sum - k` is found, the subarray length is `current_index - first_index[sum - k]`.

## Quick Reference — Pattern Decision Tree

```
Does the problem need to look something up, count frequencies, or group items — and does O(1) lookup matter?
│
├── FIND COMPLEMENT / PAIR IN O(1)?
│   └── HashMap: store seen elements/indices, look up complement per new element
│       (two-sum, four-sum variants, pair-with-difference, pair-with-product)
│
├── COUNT FREQUENCIES OF ELEMENTS?
│   └── HashMap (frequency map): element → count, single O(n) pass
│       (majority element, top-k frequent, first non-repeating, anagram check)
│
├── GROUP ITEMS WITH SAME "CANONICAL FORM"?
│   └── HashMap: canonical_form → [items], where form = sort(item) or freq_vector(item)
│       (group anagrams, group shifted strings, group equivalent permutations)
│
├── SUBARRAY SUM / RANGE SUM QUERY WITH EXACT TARGET?
│   └── HashMap (prefix sum): prefix_sum → count / first_index
│       (subarray sum = k, longest subarray with sum k, number of zero-sum subarrays)
│       Note: works for negative numbers; two-pointer only works for non-negatives
│
├── SLIDING WINDOW WITH A UNIQUENESS / DISTINCT-COUNT CONSTRAINT?
│   └── HashMap (window frequency map): shrink window when freq.size > k or freq[ch] > 1
│       (longest substring without repeats, at-most-k-distinct, minimum window substring)
│
├── O(1) MEMBERSHIP TESTING — IS THIS ELEMENT IN A SET?
│   └── HashSet: convert reference collection to set, query per new element in O(1)
│       (cycle detection, duplicate detection, word existence, visited tracking)
│
├── NEED ORDERING (sorted keys, range queries, floor/ceiling)?
│   └── TreeMap / TreeSet: O(log n) per operation, supports range views
│       (kth largest after each insert, count of smaller numbers, sliding window max/min)
│
└── NEED INSERTION-ORDER ITERATION + UNIQUENESS?
    └── LinkedHashMap / LinkedHashSet: O(1) operations, insertion-order traversal
        (LRU cache, order-preserving deduplication, first-unique-character)
```

## Common Bugs Checklist

Before submitting any HashMap or HashSet solution, verify:

1. **Initialized the base case in prefix-sum maps?** — `prefixFreq.set(0, 1)` must appear *before* the loop; forgetting it misses subarrays that start from index 0, producing an off-by-one count.

2. **Correct order: lookup before insert in prefix-sum problems?** — Query `map.get(sum - k)` *before* calling `map.set(sum, ...)` on the current prefix sum, or you may accidentally count a subarray of length 0 (the current position pairing with itself).

3. **The `max(left, ...)` guard in sliding-window last-seen problems?** — `left = Math.max(left, lastIndex.get(ch) + 1)` prevents `left` from jumping backward when a duplicate's previous occurrence is already outside the current window.

4. **`equals` and `hashCode` both overridden for custom key objects?** — Overriding only `equals` without `hashCode` (or vice versa) silently breaks correctness: equal objects may land in different buckets, making entries invisible to lookup.

5. **Not using mutable objects as HashMap keys?** — If a key object's state (and therefore its `hashCode`) changes after insertion, the entry becomes permanently unreachable. Either use immutable keys or ensure key state is frozen for the key's entire lifetime in the map.

6. **Handling `null` values vs. missing keys correctly?** — `map.get(key)` returns `null`/`undefined` for both "key exists with value null" and "key does not exist." Use `map.has(key)` when the distinction matters (e.g., storing 0 as a frequency is different from an absent key).

7. **Correct initialization for frequency map increments?** — `map.set(key, (map.get(key) ?? 0) + 1)` — the `?? 0` (or `|| 0`) handles the first occurrence correctly; without it, `undefined + 1 = NaN` silently corrupts all subsequent counts for that key.

8. **HashSet for cycle detection — not comparing node values, comparing node references?** — In linked list cycle detection, the set must store node *references* (object identity), not node *values* — values may repeat in a valid acyclic list, but reference identity is unique per node.

**Final Tip:** At the 5 YOE level, interviewers expect you to instantly recognize which of the five core HashMap/HashSet patterns applies — complement lookup (two-sum family), frequency counting, canonical-form grouping, prefix-sum range query, or sliding-window state tracking — and to state the O(1) HashMap role *before* writing code. The decisive signal separating genuine understanding from memorized solutions is being able to explain in one sentence *what the HashMap key represents* and *what value the lookup returns*, and why that answers the question in O(1) instead of O(n). That justification — "I store X as the key so that when I encounter Y, a single lookup tells me Z" — is the HashMap pattern's equivalent of the two-pointer movement proof in the subarray problems family.
