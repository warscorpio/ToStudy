## Topic A: Singly Linked Lists

### Section A1: Fundamentals

**Q1. What is a singly linked list, and how does it differ structurally from an array?**
A: A singly linked list is a sequence of nodes where each node holds a value and a single pointer (`next`) to the following node, ending in `null`. Unlike an array, elements are **not stored contiguously in memory** — this trades away O(1) random access (`arr[i]`) for O(1) insertion/deletion at a known position (no shifting of subsequent elements required), since insertion/deletion only involves re-pointing a constant number of `next` references.

```
head → [1|next] → [2|next] → [3|next] → null
```

**Q2. What is the standard node structure, and how do you build a linked list from an array?**
A:

```js
class ListNode {
  constructor(val, next = null) {
    this.val = val;
    this.next = next;
  }
}

function buildList(arr) {
  const dummy = new ListNode(0);
  let curr = dummy;
  for (const val of arr) {
    curr.next = new ListNode(val);
    curr = curr.next;
  }
  return dummy.next; // skip the dummy, return the real head
}
```

The **dummy node** pattern (a placeholder node before the real head) is used throughout linked list problems to avoid special-casing "inserting at the head" — every insertion, including the very first one, becomes "insert after some existing node," eliminating a whole class of null-check bugs.

**Q3. What is the time complexity of the core singly linked list operations?**
A:
- **Access by index**: O(n) — must traverse from `head`, no random access.
- **Search by value**: O(n) — linear scan.
- **Insert/delete at the head**: O(1) — just re-point `head`.
- **Insert/delete at a known node (given a pointer to it, or its predecessor)**: O(1) — re-point a constant number of `next` references.
- **Insert/delete at the tail (without a tail pointer)**: O(n) — must traverse to find the last node first.
- **Insert/delete at the tail (with a maintained tail pointer)**: O(1) for insert; O(n) for delete (since removing the tail requires finding the *new* tail, i.e., the second-to-last node, which a singly linked list can't reach backward from the old tail).

**Q4. Why is deleting the tail node O(n) even with a maintained tail pointer, in a singly linked list specifically?**
A: A singly linked list only has forward (`next`) pointers — there's no way to go from the tail node back to its predecessor without traversing from `head`. So while you *know* where the tail is (O(1) access to it via the tail pointer), removing it requires finding the node whose `next` currently points to the tail, which requires an O(n) scan from the head. This is precisely the limitation that motivates doubly linked lists (see Topic B) when frequent tail removal is needed.

**Q5. What is the "dummy head" (sentinel node) pattern, and why is it so commonly used in linked list problems?**
A: A dummy node is a placeholder node created *before* the real head of the list, whose `next` pointer points to the actual first node. Its purpose is to eliminate special-case branching for operations that affect the head itself (e.g., "delete the first node," "insert before the current head") — with a dummy node, *every* node (including the original head) has a predecessor, so the same "modify `predecessor.next`" logic works uniformly everywhere, including at the boundary. Without a dummy, code must special-case "is this the head?" checks throughout, which is a common source of bugs (especially forgetting to update the external `head` reference itself when the head changes).

```js
function deleteValue(head, val) {
  const dummy = new ListNode(0, head);
  let curr = dummy;

  while (curr.next !== null) {
    if (curr.next.val === val) {
      curr.next = curr.next.next; // uniform logic works even if val is at the original head
    } else {
      curr = curr.next;
    }
  }

  return dummy.next;
}
```

### Section A2: Advanced Patterns

**Q6. How do you reverse a singly linked list iteratively, and what is the core three-pointer technique?**
A: Maintain three pointers: `prev` (initially `null`), `curr` (initially `head`), and a temporary `next` to save the node about to be disconnected. At each step: save `curr.next`, re-point `curr.next` to `prev`, then advance both `prev` and `curr` forward.

```js
function reverseList(head) {
  let prev = null, curr = head;

  while (curr !== null) {
    const next = curr.next;  // save before overwriting
    curr.next = prev;        // reverse the pointer
    prev = curr;             // advance prev
    curr = next;             // advance curr
  }

  return prev; // prev is the new head after the loop ends
}
```

Time: O(n). Space: O(1) — no recursion, no auxiliary list.

**Q7. How does the recursive approach to reversing a linked list work, and what's the space trade-off?**
A: Recurse to the end of the list first, then, unwinding back up the call stack, re-point each node's `next.next` back to itself (effectively reversing the direction one link at a time on the way back up) and set the current node's `next` to `null` to avoid a cycle.

```js
function reverseListRecursive(head) {
  if (head === null || head.next === null) return head; // base case: empty or single node

  const newHead = reverseListRecursive(head.next);
  head.next.next = head; // point the next node back at this one
  head.next = null;      // break the old forward link

  return newHead;
}
```

Time: O(n). Space: O(n) due to the recursion call stack (versus O(1) for the iterative version) — an important trade-off to state explicitly in an interview, since "can you do it without extra space?" is a common follow-up that the iterative version already answers.

**Q8. What is the "fast and slow pointer" (tortoise and hare) technique, and what class of problems does it solve?**
A: Two pointers traverse the list at different speeds — typically `slow` advances one node per step, `fast` advances two nodes per step. This technique solves several distinct problems depending on how it's applied:
- **Finding the middle node**: when `fast` reaches the end, `slow` is at the midpoint (in O(n) time, O(1) space, without needing to know the list's length in advance).
- **Cycle detection**: if the list has a cycle, `fast` will eventually "lap" `slow` and they'll meet inside the cycle; if there's no cycle, `fast` reaches `null` first.
- **Finding the k-th node from the end**: advance `fast` k steps ahead first, then move both pointers together — when `fast` reaches the end, `slow` is exactly k nodes from the end.

```js
function findMiddle(head) {
  let slow = head, fast = head;

  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
  }

  return slow; // middle node (the second of two middles, if the list has even length)
}
```

**Q9. How does Floyd's cycle detection algorithm (fast/slow pointers) prove a cycle exists, and how do you find the cycle's starting node?**
A: If a cycle exists, `fast` (moving 2 steps per iteration) will eventually enter the cycle and, since it's moving faster than `slow`, will "catch up" and meet `slow` somewhere inside the cycle — this is guaranteed because the gap between them shrinks by exactly 1 node per iteration once both are inside the cycle, so it must eventually reach 0. To then find the cycle's **starting node**: after `slow` and `fast` meet, reset one pointer to `head` and advance both pointers one step at a time (not two) — they will meet exactly at the cycle's entry point. This works due to a mathematical property relating the distance from `head` to the cycle start, the distance from the meeting point back to the cycle start, and the cycle's total length.

```js
function detectCycleStart(head) {
  let slow = head, fast = head;

  // Phase 1: detect if a cycle exists
  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) break;
  }

  if (fast === null || fast.next === null) return null; // no cycle

  // Phase 2: find the cycle's start
  slow = head;
  while (slow !== fast) {
    slow = slow.next;
    fast = fast.next;
  }

  return slow; // the node where the cycle begins
}
```

**Q10. How do you merge two sorted singly linked lists into one sorted list?**
A: Use a dummy head and a "tail" pointer that always points to the last node of the merged-so-far list. Compare the current nodes of both input lists, attach the smaller one to the merged list's tail, and advance that list's pointer; repeat until one list is exhausted, then attach the remainder of the other list directly (since it's already sorted, no further comparison is needed).

```js
function mergeTwoLists(l1, l2) {
  const dummy = new ListNode(0);
  let tail = dummy;

  while (l1 !== null && l2 !== null) {
    if (l1.val <= l2.val) {
      tail.next = l1;
      l1 = l1.next;
    } else {
      tail.next = l2;
      l2 = l2.next;
    }
    tail = tail.next;
  }

  tail.next = l1 !== null ? l1 : l2; // attach whichever list has leftover nodes

  return dummy.next;
}
```

Time: O(n + m). Space: O(1) extra — reuses existing nodes, no new node allocation.

## Topic B: Doubly Linked Lists

### Section B1: Fundamentals

**Q11. What is a doubly linked list, and what does the extra `prev` pointer enable?**
A: A doubly linked list's nodes hold both a `next` pointer (to the following node) and a `prev` pointer (to the preceding node). This enables **O(1) traversal in both directions**, and critically, **O(1) deletion of a given node** without needing its predecessor separately passed in (since the node itself already knows its predecessor via `prev`) — a capability singly linked lists fundamentally lack.

```
null ← [prev|1|next] ⇄ [prev|2|next] ⇄ [prev|3|next] → null
```

```js
class DoublyListNode {
  constructor(val, prev = null, next = null) {
    this.val = val;
    this.prev = prev;
    this.next = next;
  }
}
```

**Q12. Why does O(1) deletion of an arbitrary given node work for doubly linked lists but not singly linked lists?**
A: Deleting a node requires re-pointing its predecessor's `next` (and, for doubly linked lists, its successor's `prev`) to skip over it. A doubly linked list node already has a direct `prev` reference, so given just a pointer to the node itself, both neighbors are immediately reachable in O(1). A singly linked list node has no way to reach its predecessor — deleting it (properly, by unlinking) requires an O(n) scan from the head to find that predecessor first, unless a clever workaround is used (see Q13).

**Q13. What is the "copy the next node's value" trick for deleting a node from a singly linked list in O(1), and what are its limitations?**
A: Given only a pointer to the node to delete (not the head, and not its predecessor), you can achieve *effective* O(1) deletion by copying the *next* node's value into the current node, then re-pointing `curr.next` to skip over (delete) that next node instead. This works because you're not literally deleting the given node — you're overwriting its value with its successor's and removing the successor instead, which is externally indistinguishable from having deleted the original node.

```js
function deleteNode(node) {
  node.val = node.next.val;
  node.next = node.next.next;
}
```

**Limitation**: this trick fails if `node` is the **last node** in the list (there's no `next` node to copy from), and it also doesn't work if external references to the "deleted" node's identity matter (e.g., other code held a reference to that exact node object expecting it to represent a specific value that's now been overwritten).

**Q14. What is the time complexity of core doubly linked list operations, and how do they compare to singly linked lists?**
A:
- **Insert/delete at head or tail (with maintained head/tail pointers)**: O(1) for both — this is the key improvement over singly linked lists, where tail deletion was O(n).
- **Insert/delete given a direct node reference**: O(1) — no predecessor lookup needed, unlike singly linked lists.
- **Access/search by value**: still O(n) — the bidirectional pointers don't help with locating an arbitrary value, only with modifying structure once a position is known.
- **Space overhead**: each node stores one extra pointer (`prev`) compared to a singly linked list — a real but usually acceptable trade-off for the operational improvements.

### Section B2: Advanced Patterns

**Q15. How is a doubly linked list used to implement an LRU (Least Recently Used) cache in O(1) time for both `get` and `put`?**
A: Combine a doubly linked list (maintaining recency order, most-recently-used at one end) with a hash map (`key → node reference`) for O(1) lookup. On `get`, look up the node via the hash map, then move it to the "most recently used" end of the list (O(1), since doubly linked list node removal/insertion given a direct reference is O(1)). On `put`, if the key exists, update its value and move it to the "most recently used" end; if it's new and the cache is full, evict the "least recently used" end's node (O(1) removal) before inserting the new node.

```js
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map(); // key -> node
    // dummy head/tail sentinels simplify boundary logic, same principle as Q5
    this.head = new DoublyListNode(null); // most-recently-used side
    this.tail = new DoublyListNode(null); // least-recently-used side
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  _remove(node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }

  _insertAtFront(node) {
    node.next = this.head.next;
    node.prev = this.head;
    this.head.next.prev = node;
    this.head.next = node;
  }

  get(key) {
    if (!this.map.has(key)) return -1;
    const node = this.map.get(key);
    this._remove(node);
    this._insertAtFront(node);
    return node.val.value;
  }

  put(key, value) {
    if (this.map.has(key)) {
      this._remove(this.map.get(key));
    }
    const node = new DoublyListNode({ key, value });
    this._insertAtFront(node);
    this.map.set(key, node);

    if (this.map.size > this.capacity) {
      const lru = this.tail.prev;
      this._remove(lru);
      this.map.delete(lru.val.key);
    }
  }
}
```

This is the canonical example of why doubly linked lists exist as a distinct structure from singly linked lists — the O(1) arbitrary-node removal and O(1) tail operations are load-bearing for the entire LRU cache design; a singly linked list could not achieve O(1) `get`+reorder without the `prev` pointer.

**Q16. How do you reverse a doubly linked list, and how does the approach differ from reversing a singly linked list?**
A: Walk through every node, swapping its `next` and `prev` pointers (effectively flipping the direction of traversal for that node), then swap the list's `head` and `tail` references at the end.

```js
function reverseDoublyList(head) {
  let curr = head, temp = null;

  while (curr !== null) {
    temp = curr.prev;
    curr.prev = curr.next;
    curr.next = temp;
    curr = curr.prev; // move to the "next" node, which is now in the prev slot
  }

  return temp !== null ? temp.prev : head; // new head is the old tail
}
```

Unlike a singly linked list's reversal (which must reconstruct the `next` chain from scratch, one link redirected per step), a doubly linked list's reversal is a straightforward pointer-field swap at every node — conceptually simpler, since both directions of traversal already exist and just need to be exchanged.

## Topic C: Circular Linked Lists

### Section C1: Fundamentals

**Q17. What is a circular linked list, and how does it differ from a standard (linear) linked list?**
A: In a circular linked list, the last node's `next` pointer points back to the first node (`head`) instead of `null` — there is no true "end." This can be applied to either a singly circular list (last node's `next` → `head`) or a doubly circular list (additionally, `head.prev` → the last node). Circular lists are useful for representing inherently cyclic data (round-robin scheduling, circular buffers, repeating playlists) where "wrapping back to the start" is a natural operation rather than a special case.

```
Singly circular:
head → [1] → [2] → [3] → (back to [1])

Doubly circular:
[1] ⇄ [2] ⇄ [3] ⇄ (back to [1], and [1].prev → [3])
```

**Q18. What is the key challenge in traversing a circular linked list, and how do you avoid an infinite loop?**
A: Since there's no `null` terminator, a naive `while (curr !== null)` loop never terminates. The standard fix is either: (1) traverse using a `do...while` structure that explicitly stops when `curr` returns to `head` (`do { ... } while (curr !== head)`), or (2) if the list's length is known in advance, use a counted `for` loop instead of a pointer-comparison-based one.

```js
function traverseCircular(head) {
  if (head === null) return [];
  const result = [];
  let curr = head;

  do {
    result.push(curr.val);
    curr = curr.next;
  } while (curr !== head);

  return result;
}
```

**Q19. How do you detect whether a given linked list is circular (as opposed to using Floyd's general cycle-detection algorithm)?**
A: If you already have a direct reference to what should be the "head," circularity can be checked by traversing and testing `curr.next === head` — reaching that condition without ever hitting `null` confirms circularity. If you don't know in advance whether the list is circular (and need to handle both possibilities safely), the same fast/slow pointer technique from Q9 applies unchanged — a circular list is just a specific case of "the list has a cycle," where the cycle happens to include every node.

**Q20. How do you insert or delete a node in a circular linked list, and what special case must be handled when the list has exactly one node?**
A: Insertion/deletion logic is largely the same as a linear list (re-point `next` references around the target position), but two special cases need care: (1) inserting into an **empty** circular list — the new node's `next` must point to *itself*, not to a nonexistent "next" node; (2) deleting the **only remaining node** — the list becomes empty (`head` should become `null`), rather than pointing to itself in a way that looks like a valid 1-node list.

```js
function insertCircular(head, val) {
  const newNode = new ListNode(val);

  if (head === null) {
    newNode.next = newNode; // points to itself — the only node in the list
    return newNode;
  }

  let curr = head;
  while (curr.next !== head) curr = curr.next; // find the last node (the one pointing back to head)
  curr.next = newNode;
  newNode.next = head;

  return head;
}
```

### Section C2: Advanced Patterns

**Q21. What is the classic "Josephus problem," and how does a circular linked list naturally model it?**
A: The Josephus problem: `n` people stand in a circle; starting from a given position, every `k`-th person is eliminated, continuing around the (shrinking) circle until only one person remains — find the position of the survivor. A circular linked list is a natural fit because "counting around the circle, wrapping past the end" is exactly what circular list traversal already does — repeatedly advancing `k-1` steps and removing the `k`-th node, using the list's natural wraparound instead of manually computing modular indices into an array.

```js
function josephus(n, k) {
  // build a circular list of n nodes, values 1..n
  let head = new ListNode(1);
  let curr = head;
  for (let i = 2; i <= n; i++) {
    curr.next = new ListNode(i);
    curr = curr.next;
  }
  curr.next = head; // close the circle

  curr = head;
  while (curr.next !== curr) { // more than one node remains
    for (let i = 0; i < k - 2; i++) curr = curr.next; // advance to just before the k-th node
    curr.next = curr.next.next; // remove the k-th node
    curr = curr.next;
  }

  return curr.val; // the survivor
}
```

**Q22. How do you split a circular linked list into two halves (each also circular), a common variant of the fast/slow pointer technique?**
A: Use fast/slow pointers to find the midpoint (adapted for circular traversal, since the standard `fast !== null` termination condition doesn't apply). Once the midpoint is found, break the list into two circular sublists by re-pointing the appropriate `next` references at the split point and at the original tail.

```js
function splitCircularList(head) {
  if (head === null) return [null, null];

  let slow = head, fast = head;

  while (fast.next !== head && fast.next.next !== head) {
    slow = slow.next;
    fast = fast.next.next;
  }

  const head1 = head;
  const head2 = slow.next;

  slow.next = head1; // close the first half into its own circle
  fast.next = head2; // close the second half into its own circle (handles odd-length correctly)

  return [head1, head2];
}
```

**Q23. How does a circular doubly linked list simplify implementing a "circular buffer" or a UI carousel/playlist with next/previous navigation?**
A: Both directions of navigation (`next` for "skip forward," `prev` for "go back") are O(1) native operations, and wraparound (going past the last item back to the first, or before the first item back to the last) is automatic due to the circular structure — no explicit modular arithmetic or boundary-checking code is needed, unlike an array-backed circular buffer which requires manually computing `(index + 1) % size` and `(index - 1 + size) % size`.

### Section D: Cross-Topic Scenario / Interview-Style Questions

**Q24. "You're asked to implement an LRU cache with O(1) get and put. Why is a doubly linked list specifically required here, rather than a singly linked list or just an array?"**
A: An LRU cache needs O(1) **arbitrary-node removal** (when an existing key is accessed and needs to move from its current position to the "most recently used" end) combined with O(1) hash-map lookup by key. A singly linked list can't remove an arbitrary node in O(1) without also having its predecessor on hand (which the hash map alone doesn't provide, since it maps to the node itself, not its predecessor) — you'd need an O(n) scan to find the predecessor first. A doubly linked list's `prev` pointer makes the predecessor immediately available from the node itself, enabling true O(1) removal-and-reinsertion, which is why the doubly linked list + hash map combination is the standard LRU cache design.

**Q25. "A teammate is deleting a node from a singly linked list given only a pointer to that node (not the head), and uses the 'copy next node's value' trick. What's the failure mode you'd flag in code review?"**
A: That trick fails silently (or throws) if the given node happens to be the **last node** in the list — there's no `next` node to copy from. I'd flag this as needing an explicit guard/error path for that case, and I'd also note the more subtle issue: this technique doesn't literally delete the given node object — it overwrites its value and removes a different (successor) node instead — which is fine for most use cases but could cause bugs if any other code held a separate reference to that same node object expecting its identity (not just its value) to be preserved.

**Q26. "How would you detect if two singly linked lists intersect (share a common tail), and does the fast/slow pointer technique from cycle detection apply here?"**
A: Not directly the same fast/slow technique, but a related two-pointer idea: run two pointers, one starting at each list's head, both advancing one step at a time; when a pointer reaches the end of its list, redirect it to the *other* list's head instead of stopping. Because both pointers then collectively traverse `lengthA + lengthB` nodes total (in different orders), if the lists intersect, both pointers arrive at the intersection node simultaneously (having "swapped" lists exactly once); if they don't intersect, both pointers reach `null` simultaneously after traversing `lengthA + lengthB` steps each. This is a different two-pointer invariant from cycle detection's fast/slow speeds, but the same "no auxiliary data structure needed, O(1) space" philosophy.

**Q27. "You need a data structure supporting O(1) insertion/removal at both ends, plus O(1) 'peek' at both ends, plus the ability to iterate in either direction. Would a circular doubly linked list be a good fit, or is there a simpler choice?"**
A: A (non-circular) doubly linked list already provides all of these — O(1) head/tail insertion and removal via maintained head/tail pointers, O(1) peek at both ends, and native bidirectional traversal via `next`/`prev`. Circularity specifically helps when the domain concept itself is cyclic (round-robin scheduling, wraparound navigation) — if there's no inherent "wrap past the end back to the start" requirement in the use case described, a standard (linear) doubly linked list is simpler and sufficient; adding circularity would be solving a problem that doesn't exist in this scenario.

## Problem 1 — Reverse a Singly Linked List (Iterative)

### Problem
Given the head of a singly linked list, reverse the list and return the new head.

```
Input:  1 → 2 → 3 → 4 → 5 → null
Output: 5 → 4 → 3 → 2 → 1 → null
```

### Pattern Recognition
The canonical three-pointer in-place reversal — no auxiliary list or array needed.

### Key Insight
Each node's `next` pointer must be flipped to point backward instead of forward. Doing this one node at a time requires saving the "next" node *before* overwriting the current node's pointer, or that part of the list becomes unreachable.

### Approach
Maintain `prev` (built-so-far reversed list, starts `null`), `curr` (the node being processed), and a temporary `next` (saved before modification). At each step: save, reverse, advance both `prev` and `curr`.

### Solution

```js
function reverseList(head) {
  let prev = null, curr = head;

  while (curr !== null) {
    const next = curr.next;
    curr.next = prev;
    prev = curr;
    curr = next;
  }

  return prev;
}
```

### Dry Run

```
List: 1 → 2 → 3 → null
prev=null, curr=1(node)

iter1: next=2(node) [saved]
       curr.next=prev → 1.next=null
       prev=1, curr=2
       list so far: 1→null (reversed portion), remaining: 2→3→null

iter2: next=3(node) [saved]
       curr.next=prev → 2.next=1
       prev=2, curr=3
       reversed portion: 2→1→null, remaining: 3→null

iter3: next=null [saved]
       curr.next=prev → 3.next=2
       prev=3, curr=null

loop ends (curr===null)
return prev=3

Result: 3 → 2 → 1 → null ✓
```

### Complexity
- Time: O(n) — single pass.
- Space: O(1) — three pointers, no recursion or auxiliary structure.

### Edge Cases
- Empty list (`head === null`): loop never executes, `prev` remains `null`, correctly returns `null`.
- Single node: loop executes once, `curr.next` set to `null` (unchanged, since it already was `null`), correctly returns that same single node as the new head.
- Already-reversed check: reversing twice should return the original list — a good sanity test for correctness.

### Follow-up Questions
- "Can you do it recursively?" → Yes — see Q7 — but at the cost of O(n) space due to the call stack, an important trade-off to mention proactively.
- "Reverse only a sub-portion of the list (between positions m and n)?" → Requires tracking the nodes just before and after the sub-portion, reversing only that segment with the same three-pointer technique, then re-splicing the reversed segment back into the full list.

## Problem 2 — Detect Cycle and Find Its Starting Node

### Problem
Given the head of a linked list, determine if the list has a cycle, and if so, return the node where the cycle begins. Return `null` if there is no cycle.

```
Input: 3 → 2 → 0 → -4 → (back to node with value 2)
Output: the node with value 2 (where the cycle starts)
```

### Pattern Recognition
Floyd's cycle detection (fast/slow pointers), extended with a second phase to locate the exact cycle entry point.

### Key Insight
Phase 1: a faster pointer (2 steps) will always eventually meet a slower pointer (1 step) if a cycle exists, since once both are inside the cycle, the gap between them shrinks by 1 each iteration. Phase 2: resetting one pointer to `head` and advancing both at equal (1-step) speed causes them to meet exactly at the cycle's start — a consequence of the specific distance relationships between `head`, the cycle start, and the first meeting point.

### Approach
Run fast/slow pointers until they meet (cycle exists) or `fast` hits `null` (no cycle). If they meet, reset one pointer to `head`, then advance both one step at a time until they meet again — that meeting point is the cycle's start.

### Solution

```js
function detectCycle(head) {
  let slow = head, fast = head;

  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) {
      let ptr = head;
      while (ptr !== slow) {
        ptr = ptr.next;
        slow = slow.next;
      }
      return ptr;
    }
  }

  return null; // fast reached the end — no cycle
}
```

### Dry Run

```
List: 3 → 2 → 0 → -4 → (back to node "2")
positions: head=3(idx0), 2(idx1), 0(idx2), -4(idx3), then -4.next=2(idx1) — cycle starts at idx1

Phase 1 (find meeting point):
slow=3(idx0), fast=3(idx0)

step1: slow=2(idx1), fast=0(idx2)
step2: slow=0(idx2), fast=2(idx1) [fast: idx2→idx3→idx1, since -4.next=2]
step3: slow=-4(idx3), fast=0(idx2) [fast: idx1→idx2... wait let's recompute carefully]

(illustrative — exact meeting point depends on precise cycle length and entry distance,
 but Floyd's guarantees they DO meet somewhere inside the cycle)

Say they meet at node "0" (idx2).

Phase 2 (find cycle start):
ptr=head=3(idx0), slow=0(idx2) [from where they met]

ptr!==slow: ptr=2(idx1), slow=-4(idx3)
ptr!==slow: ptr=0(idx2), slow=2(idx1)
ptr!==slow: ptr=-4(idx3), slow=0(idx2)
ptr!==slow: ptr=2(idx1), slow=-4(idx3)
...continues until ptr===slow, which happens exactly at node "2" (idx1), the true cycle start

Result: node with value 2 ✓
```

### Complexity
- Time: O(n) — both phases are linear; Floyd's guarantees the meeting happens within O(n) steps, not requiring multiple laps proportional to cycle length in the worst case beyond a linear bound.
- Space: O(1) — only a constant number of pointers, no visited-set/hash-map needed (an alternative O(n)-space approach using a `Set` to track visited nodes is simpler to reason about but loses the O(1) space advantage).

### Edge Cases
- No cycle: `fast` reaches `null` (or `fast.next` does) before ever meeting `slow` — correctly returns `null`.
- Cycle starts at the head itself (entire list is one cycle): the algorithm still correctly identifies `head` as the cycle start via the same phase-2 logic.
- Very short cycle (e.g., a single node pointing to itself): fast/slow still correctly detect and locate it, since the "gap shrinks by 1 per iteration" argument holds regardless of cycle length.
- Empty list or single non-cyclic node: `fast === null` or `fast.next === null` immediately, loop doesn't execute meaningfully, correctly returns `null`.

### Follow-up Questions
- "Can you find the cycle's length once detected?" → From the first meeting point, keep one pointer fixed and advance the other one step at a time, counting steps until it returns to the fixed pointer's position — that count is the cycle length.
- "What if you're not allowed O(1) space?" → Use a `Set` to track visited node references; the first node encountered a second time is either the cycle start (if using this simpler method to find both existence and start) — simpler to write, O(n) space instead of O(1).

## Problem 3 — LRU Cache (Doubly Linked List + Hash Map)

### Problem
Design a data structure that implements a Least Recently Used (LRU) cache with `get(key)` and `put(key, value)` operations, both in O(1) average time. When the cache reaches capacity, evict the least recently used entry before inserting a new one.

```
cache = new LRUCache(2)
cache.put(1, 'a')
cache.put(2, 'b')
cache.get(1)      → 'a'  (and 1 becomes most-recently-used)
cache.put(3, 'c') → evicts key 2 (least recently used), since capacity is 2
cache.get(2)      → -1  (evicted)
```

### Pattern Recognition
The canonical doubly linked list + hash map combination — the hash map gives O(1) key lookup, and the doubly linked list gives O(1) arbitrary-node removal/reinsertion for recency-order maintenance.

### Key Insight
"Most recently used" and "least recently used" naturally correspond to the two ends of a doubly linked list. Every access (get or put-on-existing-key) needs to move a node to the "most recently used" end in O(1) — only possible because a doubly linked list node can be unlinked from its current position in O(1) using its own `prev`/`next` pointers, without needing to search for its predecessor.

### Approach
Maintain dummy `head` (most-recently-used side) and `tail` (least-recently-used side) sentinel nodes to avoid edge-case branching (same dummy-node principle as Q5). `get`: look up via hash map, unlink and re-insert at the front. `put`: if key exists, unlink old node; create/insert new node at the front; if over capacity, remove the node just before `tail` (the actual least-recently-used entry) and delete it from the hash map too.

### Solution

```js
class DoublyListNode {
  constructor(val) {
    this.val = val;
    this.prev = null;
    this.next = null;
  }
}

class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map();
    this.head = new DoublyListNode(null);
    this.tail = new DoublyListNode(null);
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  _remove(node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }

  _insertAtFront(node) {
    node.next = this.head.next;
    node.prev = this.head;
    this.head.next.prev = node;
    this.head.next = node;
  }

  get(key) {
    if (!this.map.has(key)) return -1;
    const node = this.map.get(key);
    this._remove(node);
    this._insertAtFront(node);
    return node.val.value;
  }

  put(key, value) {
    if (this.map.has(key)) {
      this._remove(this.map.get(key));
    }
    const node = new DoublyListNode({ key, value });
    this._insertAtFront(node);
    this.map.set(key, node);

    if (this.map.size > this.capacity) {
      const lru = this.tail.prev;
      this._remove(lru);
      this.map.delete(lru.val.key);
    }
  }
}
```

### Dry Run

```
cache = new LRUCache(2)
list: head ⇄ tail

put(1,'a'): map has no 1 → create node{1,'a'}, insert at front
  list: head ⇄ [1,'a'] ⇄ tail
  map={1:node1}, size=1, not > capacity(2)

put(2,'b'): create node{2,'b'}, insert at front
  list: head ⇄ [2,'b'] ⇄ [1,'a'] ⇄ tail
  map={1:node1,2:node2}, size=2, not > 2

get(1): map has 1 → remove node1, reinsert at front
  list: head ⇄ [1,'a'] ⇄ [2,'b'] ⇄ tail
  return 'a' ✓

put(3,'c'): create node{3,'c'}, insert at front
  list: head ⇄ [3,'c'] ⇄ [1,'a'] ⇄ [2,'b'] ⇄ tail
  map={1:node1,2:node2,3:node3}, size=3 > capacity(2)
  → lru = tail.prev = node2 (key 2, least recently used)
  → remove node2, delete map[2]
  list: head ⇄ [3,'c'] ⇄ [1,'a'] ⇄ tail
  map={1:node1,3:node3}

get(2): map does NOT have 2 (evicted) → return -1 ✓
```

### Complexity
- `get`: O(1) — hash map lookup + O(1) doubly linked list unlink/reinsert.
- `put`: O(1) — same operations, plus O(1) eviction when over capacity.
- Space: O(capacity) — the hash map and linked list each store at most `capacity` entries.

### Edge Cases
- `capacity = 0`: every `put` would immediately need eviction; typically handled by treating capacity 0 as "cache never actually stores anything," which this implementation would need an explicit guard for (a `put` with capacity 0 would insert then immediately evict the just-inserted node, functionally correct but slightly wasteful — worth mentioning if capacity 0 is a valid input per the problem spec).
- Updating an existing key's value via `put`: correctly removes the old node and inserts a fresh one at the front with the new value, also correctly refreshing its recency.
- Repeated `get` calls on the same key: each call correctly moves that key to the front again, keeping it "fresh" and protected from eviction.
- Cache never reaches capacity: eviction logic (`if (this.map.size > this.capacity)`) simply never triggers — no special handling needed.

### Follow-up Questions
- "How would you make this thread-safe for concurrent access?" → Would need locking (mutex) around the combined map+list mutation in `get`/`put`, since both operations touch shared mutable state across two data structures that must stay in sync.
- "Extend to an LFU (Least Frequently Used) cache instead?" → Structurally more complex — typically requires a hash map of frequency → doubly linked list of nodes at that frequency, plus a pointer to the current minimum frequency bucket, to maintain O(1) operations; a materially different design, not just a small tweak to LRU.

## Problem 4 — Josephus Problem (Circular Linked List Simulation)

### Problem
`n` people (numbered 1 to n) stand in a circle. Starting from person 1, count around the circle and eliminate every `k`-th person; continue counting from the next person after each elimination, until only one person remains. Return the position (original number) of the survivor.

```
Input:  n = 7, k = 3
Output: 4

(Elimination order: 3, 6, 2, 7, 5, 1 — survivor is 4)
```

### Pattern Recognition
Circular linked list traversal with removal — the circle's natural "wrap past the end back to the start" behavior directly models the problem's counting-around-a-circle structure, avoiding manual modular index arithmetic.

### Key Insight
Advancing `k-1` steps from the current position lands on the node *just before* the one to be eliminated (needed so its `next` pointer can be re-pointed to skip the eliminated node) — this mirrors the general "find predecessor before deleting" pattern from singly linked list deletion (Q5), applied within a circular structure.

### Approach
Build a circular linked list of `n` nodes. Repeatedly advance `k-1` steps from the current position, then remove the node that comes next (the k-th person counted), continuing until only one node remains (its `next` points to itself).

### Solution

```js
function josephus(n, k) {
  let head = new ListNode(1);
  let curr = head;
  for (let i = 2; i <= n; i++) {
    curr.next = new ListNode(i);
    curr = curr.next;
  }
  curr.next = head; // close the circle

  curr = head;
  while (curr.next !== curr) {
    for (let i = 0; i < k - 2; i++) curr = curr.next; // advance to just before the k-th
    curr.next = curr.next.next; // eliminate the k-th person
    curr = curr.next; // move to the person just after the eliminated one
  }

  return curr.val;
}
```

### Dry Run

```
n=7, k=3
Circle: 1→2→3→4→5→6→7→(back to 1)
curr=1

Round 1: advance k-2=1 step: curr=2
  eliminate curr.next(3): curr.next=4 → circle: 1,2,4,5,6,7
  curr=curr.next=4

Round 2 (curr=4): advance 1 step: curr=5
  eliminate curr.next(6): curr.next=7 → circle: 1,2,4,5,7
  curr=7

Round 3 (curr=7): advance 1 step: curr=1
  eliminate curr.next(2): curr.next=4 → circle: 1,4,5,7
  curr=4

Round 4 (curr=4): advance 1 step: curr=5
  eliminate curr.next(7): curr.next=1 → circle: 1,4,5
  curr=1

Round 5 (curr=1): advance 1 step: curr=4
  eliminate curr.next(5): curr.next=1 → circle: 1,4
  curr=1

Round 6 (curr=1): advance 1 step: curr=4
  eliminate curr.next(1): curr.next=4 → circle: 4 only
  curr=4

curr.next === curr (4 points to itself) → loop ends
return curr.val = 4 ✓
```

### Complexity
- Time: O(n × k) in the worst case — for each of the n-1 eliminations, up to k-1 steps are taken to find the next elimination target. (More advanced O(n) or O(n log n) solutions exist using different mathematical recurrence-based approaches, but the circular-list simulation is the standard, intuitive interview answer.)
- Space: O(n) — the circular linked list itself.

### Edge Cases
- `k = 1`: every "first" person counted is eliminated immediately each round — degenerates to simply eliminating people in original circle order, survivor is always position `n`.
- `n = 1`: the circle has only one node from the start (`head.next === head` immediately) — loop never executes, correctly returns that single person.
- Large `k` relative to `n`: the modular wraparound (via the circular list's natural structure) correctly handles `k` exceeding the current remaining circle size, since advancing "past the end" simply continues from the front automatically.

### Follow-up Questions
- "Can you solve this without a linked list, just using an array or a formula?" → Yes — a well-known O(n) recurrence exists: `josephus(n, k) = (josephus(n-1, k) + k) % n`, adjusted for 1-indexing at the end; this is more efficient but less intuitively connected to the "circle" framing than the linked-list simulation.
- "What if people can also be added back into the circle (not just removed)?" → The circular linked list approach adapts naturally (insertion is still O(1) given a position), whereas the array/formula-based approach would need significant rework to support dynamic re-insertion.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve a linked list structure?
│
├── NEED TO REVERSE THE LIST (fully or partially)?
│   ├── O(1) space required → Iterative 3-pointer reversal (prev/curr/next)
│   └── Recursion acceptable / more elegant framing preferred → Recursive reversal (O(n) space)
│
├── NEED TO FIND THE MIDDLE, DETECT A CYCLE, OR FIND THE K-TH FROM THE END?
│   └── Fast/Slow (tortoise & hare) two-pointer technique
│       ├── Just detect cycle existence → single-phase fast/slow meeting check
│       └── Also need the cycle's STARTING node → two-phase (meet, then reset+equal-speed walk)
│
├── NEED O(1) DELETION OF AN ARBITRARY NODE, GIVEN ONLY A POINTER TO IT?
│   ├── Doubly linked list available/usable → native O(1) via node's own prev/next
│   └── Only a singly linked list, node is NOT the last node → "copy next value" trick (O(1))
│   └── Only a singly linked list, node COULD be the last → must traverse from head (O(n)),
│       no shortcut exists
│
├── NEED O(1) INSERT/DELETE AT BOTH HEAD AND TAIL?
│   └── Doubly Linked List with maintained head/tail pointers (singly linked list tail-deletion is O(n))
│
├── BUILDING A CACHE/RECENCY-ORDERED STRUCTURE (LRU, MRU)?
│   └── Doubly Linked List + Hash Map combination → O(1) get/put with recency reordering
│
├── DATA IS INHERENTLY CYCLIC (round robin, playlist wraparound, Josephus-style counting)?
│   └── Circular Linked List (singly or doubly, depending on whether backward navigation is needed)
│       — use do-while traversal (stop when back at head), not a null-check loop
│
├── MERGING TWO (OR MORE) SORTED LISTS?
│   └── Dummy head + tail pointer, compare-and-attach-smaller technique → O(total nodes)
│
└── DETECTING WHETHER TWO LISTS INTERSECT (SHARE A COMMON TAIL)?
    └── Two pointers, each switching to the other list's head upon reaching its own list's end
```

## Common Bugs Checklist

Before submitting any linked list solution, verify:

1. **Dummy node used where head-modification logic would otherwise need special-casing?** — Insertion/deletion at the head, or building a list from scratch, benefits from a dummy node to avoid separate "is this the head?" branches that are easy to get subtly wrong.

2. **Reversal: `next` saved BEFORE overwriting `curr.next`?** — Overwriting `curr.next = prev` before saving the original `curr.next` value permanently loses the rest of the list (nothing to advance `curr` to).

3. **Fast/slow pointer loop condition checks BOTH `fast !== null` AND `fast.next !== null`?** — Missing either check risks a null-pointer dereference when `fast` advances two steps at a time on a list with even length (or generally whenever `fast` is one node away from the end).

4. **Cycle detection: comparing NODE REFERENCES (`slow === fast`), not values?** — Comparing `.val` instead of the node objects themselves could produce false positives if duplicate values exist in a genuinely non-cyclic list.

5. **Doubly linked list: BOTH `next` and `prev` pointers updated on every insert/delete?** — Forgetting to update `prev` on the neighboring node (only updating `next`) leaves the list in an inconsistent state that looks correct when traversed forward but breaks backward traversal or subsequent O(1) deletions relying on `prev`.

6. **Circular list traversal: using `do...while (curr !== head)`, not a null-check loop?** — A `while (curr !== null)` loop on a circular list never terminates, since no node's `next` is ever `null`.

7. **Circular list: empty-list and single-node special cases handled explicitly?** — Inserting into an empty circular list requires the new node to point to itself; deleting the last remaining node must correctly result in an empty list (`head = null`), not a node pointing to itself as if it were a valid single-element list, when that's not the intended semantics for "now empty."

8. **LRU cache: hash map and linked list kept in sync on every operation?** — Every node removal/insertion in the linked list must be paired with a corresponding hash map update (or vice versa); letting them drift out of sync (e.g., removing a node from the list but forgetting to `map.delete()` its key) causes stale lookups.

**Final Tip:** At the 5 YOE level, interviewers expect immediate recognition of which linked list variant a problem calls for, based on the *operations* required — not just which variant happens to be mentioned in the prompt. State the operational requirement first: "this needs O(1) arbitrary removal, so I need the `prev` pointer a doubly linked list provides," or "this is inherently cyclic counting, so a circular list's natural wraparound avoids manual modular arithmetic," or "this only needs forward traversal and head insertion, so a singly linked list is sufficient — no need to over-engineer with `prev` pointers I won't use." Justifying the choice of structure by the operations it needs to support, rather than defaulting to the most powerful variant out of habit, is a strong signal of practical engineering judgment.
