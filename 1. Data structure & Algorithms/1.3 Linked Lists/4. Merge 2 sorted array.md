# DSA: Merge Two Sorted Lists — Arrays, Linked Lists & k-Way Merging — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the "merge two sorted lists" problem, and what is the core two-pointer technique that solves it?**
A: Given two sequences (arrays or linked lists) that are each individually already sorted, combine them into a single sorted sequence containing all their elements. The core technique: maintain one pointer into each input sequence, repeatedly compare the two pointers' current elements, append the smaller one to the result, and advance only that pointer — continuing until one input is exhausted, then appending the remainder of the other input directly (since it's already sorted, no further comparison is needed).

```
merge([1,3,5], [2,4,6]) → [1,2,3,4,5,6]

pointers: i=0 (arr1), j=0 (arr2)
compare 1 vs 2 → take 1, i++
compare 3 vs 2 → take 2, j++
compare 3 vs 4 → take 3, i++
compare 5 vs 4 → take 4, j++
compare 5 vs 6 → take 5, i++
arr1 exhausted → append remainder of arr2: [6]
```

**Q2. Why is this two-pointer merge correct — what invariant guarantees the output stays sorted?**
A: At every step, the two candidate "next" elements are `arr1[i]` and `arr2[j]` — the *smallest remaining* element of each respective input, since both inputs are individually sorted and every element before index `i` (or `j`) has already been consumed. Taking the smaller of these two candidates guarantees it's also the smallest remaining element across *both* inputs combined (nothing smaller could exist in either uncomsumed portion), so appending it preserves the sorted order of the output at every step — a simple but powerful invariant: "the next output element is always the minimum of the two current candidates."

**Q3. What is the time and space complexity of the two-pointer merge, for both arrays and linked lists?**
A:
- **Time**: O(n + m) — every element from both inputs is visited and placed exactly once, regardless of underlying structure.
- **Space (arrays, building a new output array)**: O(n + m) for the new array.
- **Space (linked lists, re-linking existing nodes)**: O(1) extra — no new node objects are allocated; only existing nodes are re-pointed, which is a meaningful practical advantage linked lists have over arrays for this specific operation (see Q9).

**Q4. Why does merging two sorted arrays typically require O(n+m) auxiliary space, while merging two sorted linked lists can be done in O(1) extra space?**
A: Arrays are contiguous, fixed-layout memory — you cannot "insert" an element from one array into the middle of another without shifting every subsequent element (expensive, O(n) per insertion) unless you're writing into a *separate* output array. Linked lists, in contrast, are connected via pointers/references — merging simply means re-pointing existing nodes' `next` references to interleave them in the correct order, reusing the exact same node objects rather than copying values into new storage. This is a recurring theme distinguishing array-based and linked-list-based algorithms: linked lists trade away random access for cheap structural rearrangement.

**Q5. How does "merge two sorted arrays" differ when one array has extra trailing space to merge in-place (the classic "merge sorted array" interview variant) versus when you must produce a brand-new output array?**
A: If given a fresh, unused output array (or building a new array from scratch), the standard forward two-pointer merge (Q1) is straightforward. But a common interview variant provides one array with **extra unused trailing capacity** sized to hold both arrays' combined elements, and asks for an in-place merge without auxiliary space — this requires merging **from the back**, comparing the largest remaining elements of each array and placing the larger one at the end of the combined space, working backward, specifically to avoid overwriting not-yet-processed elements in the array with the extra space (see Problem 2 for the full technique and reasoning).

### Section 2: Merging Linked Lists — Iterative & Recursive

**Q6. What is the standard iterative approach to merging two sorted linked lists, and why is a dummy head node used?**
A: Use a dummy head node (see the linked-list guide's Q5 for the general pattern) and a `tail` pointer that always references the last node of the merged-so-far list. At each step, compare the current nodes of both lists, attach the smaller to `tail.next`, advance both the consumed list's pointer and `tail`. The dummy head eliminates the need to special-case "what is the very first node of the merged list" — that first attachment becomes just another `tail.next = ...` operation like any other.

```js
function mergeTwoLists(l1, l2) {
  const dummy = new ListNode(0);
  let tail = dummy;

  while (l1 !== null && l2 !== null) {
    if (l1.val <= l2.val) {
      tail.next = l1;
      l1 = l1.next;
    } else {
      tail.next = l2;
      l2 = l2.next;
    }
    tail = tail.next;
  }

  tail.next = l1 !== null ? l1 : l2;

  return dummy.next;
}
```

**Q7. Why does `tail.next = l1 !== null ? l1 : l2` correctly handle the remainder without any further comparison loop?**
A: Once one list is fully exhausted, every remaining node in the *other* list is, by that list's own sort invariant, still in ascending order relative to each other, and — critically — every remaining node in it is guaranteed to be `>=` the last node already attached to the merged list (since that last-attached node was the smaller of two candidates at the moment it was chosen, and the exhausted list contributed nothing larger after that point to compare against). So simply splicing in the entire remaining chain, without any further per-node comparison, preserves the sorted invariant of the output.

**Q8. What is the recursive approach to merging two sorted linked lists, and how does its structure mirror the iterative version?**
A: The recursive version expresses the exact same decision (`compare heads, take the smaller, recurse on the rest`) without an explicit loop or dummy node — the base cases (one list is `null`) directly return the other list, and the recursive case picks the smaller head, sets its `.next` to the recursive merge of "the rest of this list" and "the other list," and returns that head.

```js
function mergeTwoListsRecursive(l1, l2) {
  if (l1 === null) return l2;
  if (l2 === null) return l1;

  if (l1.val <= l2.val) {
    l1.next = mergeTwoListsRecursive(l1.next, l2);
    return l1;
  } else {
    l2.next = mergeTwoListsRecursive(l1, l2.next);
    return l2;
  }
}
```

**Q9. What is the space complexity trade-off between the iterative and recursive linked-list merge?**
A: Iterative: O(1) extra space (dummy node + a couple of pointers, no growth with input size). Recursive: O(n + m) extra space, due to the call stack — each recursive call adds a frame that persists until the base case is reached, and the total recursion depth equals the combined number of nodes across both lists (in the worst case, e.g., if one list is entirely consumed before the other begins). This mirrors the same iterative-vs-recursive space trade-off seen throughout linked-list and reversal problems — recursion is more concise but not "free."

**Q10. Does the merge operation preserve stability (relative order of equal-valued elements from each original list), and why might that matter?**
A: Yes, as implemented above (`l1.val <= l2.val` favors `l1` on ties) — when values are equal, the element from `l1` is placed before the element from `l2`. This is a **stable merge**: elements that compare equal retain their relative input order (specifically, all of `l1`'s equal elements come before `l2`'s in the output, assuming `l1` is consistently favored on ties). Stability matters when the "value" being compared is only part of a larger record (e.g., merging by a numeric priority while other fields differ) — a stable merge guarantees predictable, non-arbitrary tie-breaking, which downstream code or tests might depend on.

### Section 3: k-Way Merging

**Q11. How do you extend "merge two sorted lists" to "merge k sorted lists," and what are the two standard approaches?**
A: Two standard approaches:
1. **Divide and conquer (pairwise merging)**: repeatedly merge lists in pairs, halving the number of lists each round, until only one remains — directly reuses the two-list merge as a building block, applied `O(log k)` times across all elements.
2. **Min-heap (priority queue)**: maintain a min-heap containing the current head of each of the k lists; repeatedly extract the minimum, append it to the output, and push that extracted node's successor (if any) back into the heap.

```js
// Divide and conquer
function mergeKLists(lists) {
  if (lists.length === 0) return null;

  while (lists.length > 1) {
    const merged = [];
    for (let i = 0; i < lists.length; i += 2) {
      const l1 = lists[i];
      const l2 = i + 1 < lists.length ? lists[i + 1] : null;
      merged.push(mergeTwoLists(l1, l2)); // reuse the standard two-list merge
    }
    lists = merged;
  }

  return lists[0];
}
```

**Q12. What is the time complexity of the divide-and-conquer k-way merge, and why is it better than repeatedly merging one list at a time into a running result?**
A: Divide-and-conquer pairwise merging: **O(N log k)**, where N is the total number of elements across all k lists — each of the `log k` rounds does O(N) total work (every element is touched once per round, across all the pairwise merges happening that round), and there are `log k` rounds since the list count halves each time. A naive "merge list 1 into result, then merge list 2 into result, then list 3, ..." approach is **O(N × k)** in the worst case — each successive merge can touch nearly all N elements again, and this happens k-1 times. The divide-and-conquer approach's key advantage is that merges happen between similarly-sized chunks at each round, rather than one large (ever-growing) result being repeatedly re-merged against each new small list.

**Q13. How does the min-heap approach to k-way merging work, and what is its complexity?**
A: Initialize a min-heap with the head node of each of the k lists (heap ordered by node value). Repeatedly: pop the minimum node from the heap, append it to the output, and if that node has a successor, push the successor into the heap. This continues until the heap is empty.

```js
// Conceptual (using a generic min-heap/priority queue)
function mergeKListsHeap(lists) {
  const heap = new MinHeap((a, b) => a.val - b.val);

  for (const list of lists) {
    if (list !== null) heap.push(list);
  }

  const dummy = new ListNode(0);
  let tail = dummy;

  while (!heap.isEmpty()) {
    const node = heap.pop();
    tail.next = node;
    tail = tail.next;
    if (node.next !== null) heap.push(node.next);
  }

  return dummy.next;
}
```

Time: O(N log k) — each of the N total elements triggers one heap push and one heap pop, each O(log k) since the heap never holds more than k elements at once. Space: O(k) for the heap itself, plus O(1) extra for the linked-list merge itself (reusing existing nodes) — though building/using a heap library typically has some constant-factor overhead not present in the pure divide-and-conquer approach.

**Q14. When would you prefer the divide-and-conquer approach over the min-heap approach for k-way merging, or vice versa?**
A: Both achieve the same O(N log k) time complexity, so the choice often comes down to implementation context: the **min-heap** approach is more natural when lists arrive incrementally or the "k" isn't fixed upfront (e.g., streaming merge scenarios, or merging results from k parallel workers as they complete), and it directly generalizes to any comparator, not just linked-list nodes. The **divide-and-conquer** approach is often simpler to implement from scratch without a heap library/data structure dependency (since it only needs the already-familiar two-list merge as a building block), and can be slightly easier to reason about and test incrementally (merge two things at a time is a well-understood sub-problem).

### Section 4: Advanced Patterns & Related Problems

**Q15. How does "merge two sorted lists" relate to the merge step of merge sort?**
A: It *is* the merge step of merge sort, applied as a standalone operation rather than as part of a full recursive sort — merge sort recursively splits an unsorted array into halves, sorts each half independently, then merges the two sorted halves using exactly this two-pointer technique. Understanding "merge two sorted lists" deeply is foundational to understanding merge sort's O(n log n) complexity, since each of the `log n` levels of merge sort's recursion does O(n) total merge work, directly mirroring the k-way merge complexity analysis in Q12.

**Q16. How would you merge two sorted arrays where one is much larger than the other (e.g., merging a small array of 10 elements into a sorted array of 10 million)?**
A: If the smaller array is significantly smaller than the larger one, a straightforward O(n+m) two-pointer merge is still linear and often perfectly acceptable, but an alternative worth mentioning is inserting each of the smaller array's elements into the larger array via **binary search** for its correct position, achieving O(m log n) instead of O(n+m) where m is the small array's size and n is the large array's size — this can be faster in practice when m is very small relative to n (e.g., m log n could be meaningfully smaller than n+m when m ≪ n), though it still requires O(n) space/shifting if done truly in-place on an array (binary search finds the position in O(log n), but insertion into an array still costs O(n) for the shift, so the full complexity discussion needs care — this optimization is more naturally suited to a linked list or a data structure supporting O(log n) insertion, like a balanced BST).

**Q17. What is the relationship between "merge two sorted lists" and "merge intervals" — are they the same technique?**
A: They are related but distinct problems. "Merge two sorted lists" combines two already-individually-sorted *sequences of values* into one larger sorted sequence, preserving every element. "Merge intervals" takes a single collection of (possibly overlapping) ranges and *combines overlapping ones* into fewer, non-overlapping ranges — it's fundamentally about detecting overlap and collapsing ranges together, not about interleaving two separate sorted sequences. Both problems often begin with a sorting step and use a similar "compare consecutive things, decide whether to merge or emit separately" scanning pattern, but the decision criteria and the shape of the output differ substantially — worth explicitly distinguishing if an interviewer's phrasing is ambiguous.

### Section 5: Scenario / Interview-Style Questions

**Q18. "You're merging two sorted arrays representing search results from two different services, and need to preserve the property that if two results have the same relevance score, the one from Service A should come first. How does this affect your merge implementation?"**
A: This is a direct call for a **stable merge** — the comparison logic must favor Service A's array on ties (`<=` rather than strict `<` when comparing, with Service A's pointer checked first in the tie-breaking condition), ensuring equal-scored results preserve their "Service A before Service B" relative order in the merged output, exactly as shown in Q6's `l1.val <= l2.val` tie-breaking convention.

**Q19. "A teammate implements 'merge k sorted lists' by looping through the k lists and calling the two-list merge function repeatedly, merging the running result with each new list one at a time. What's the complexity concern, and how would you suggest improving it?"**
A: That approach is O(N × k) in the worst case, since the running merged result grows to include almost all N elements early on, and each subsequent merge against a new (small) list still costs O(current result size), repeated k-1 times — a classic case of doing asymptotically more work than necessary due to an imbalanced merge order. I'd suggest switching to divide-and-conquer pairwise merging (merge lists in balanced pairs, halving the list count each round) to bring this down to O(N log k), or a min-heap-based approach with the same complexity — both avoid ever re-merging a large accumulated result against many small inputs sequentially.

**Q20. "How would you merge two sorted linked lists if you were told the merge must happen with zero extra space, not even a dummy head node?"**
A: A dummy head node itself is O(1) extra space (a single fixed node, not growing with input size), so it technically doesn't violate an O(1)-extra-space constraint — but if literally *no* additional node allocation is allowed (not even one), you can achieve the same result by explicitly determining which list's head is smaller first (to use as the real starting point, without a dummy), and handling that one initial comparison as a special case before falling into the same tail-pointer loop used with a dummy node. This trades a small amount of extra special-case code for avoiding the one-node dummy allocation — usually not worth it unless the "zero extra space" constraint is truly strict for the specific problem at hand.

**Q21. "You need to merge two sorted arrays of different data types conceptually (e.g., merging timestamped log entries from two different sources, sorted by timestamp) — does the core technique change?"**
A: No — the two-pointer merge technique is comparator-agnostic; the only thing that changes is the comparison expression itself (comparing `entryA.timestamp` vs `entryB.timestamp` instead of raw numeric values). This generality is exactly why the technique underlies merge sort for arbitrary comparable objects, k-way merging with custom comparators in a heap, and countless real-world "combine two sorted streams" scenarios (log aggregation, combining sorted database query results, etc.) — the invariant ("always take the smaller of the two current candidates") holds regardless of what "smaller" is defined to mean for the specific data being merged.

## Problem 1 — Merge Two Sorted Arrays (Into a New Array)

### Problem
Given two sorted integer arrays `arr1` and `arr2`, merge them into a single new sorted array.

```
Input:  arr1 = [1, 3, 5, 7], arr2 = [2, 4, 6, 8, 10]
Output: [1, 2, 3, 4, 5, 6, 7, 8, 10]
```

### Pattern Recognition
The foundational two-pointer merge — building a brand-new output array, no in-place constraint.

### Key Insight
At every step, comparing the two current pointer positions and taking the smaller guarantees the output stays sorted, since both inputs are individually already sorted and every unconsumed element is `>=` everything already consumed from that same array.

### Approach
Two pointers, one per input array, plus a growing output array. Compare-and-append-smaller until one input is exhausted, then append the remainder of the other input directly.

### Solution

```js
function mergeSortedArrays(arr1, arr2) {
  const result = [];
  let i = 0, j = 0;

  while (i < arr1.length && j < arr2.length) {
    if (arr1[i] <= arr2[j]) {
      result.push(arr1[i]);
      i++;
    } else {
      result.push(arr2[j]);
      j++;
    }
  }

  while (i < arr1.length) result.push(arr1[i++]);
  while (j < arr2.length) result.push(arr2[j++]);

  return result;
}
```

### Dry Run

```
arr1 = [1,3,5,7], arr2 = [2,4,6,8,10]
i=0, j=0, result=[]

1<=2 → push 1, i=1 → result=[1]
3<=2? no → push 2, j=1 → result=[1,2]
3<=4 → push 3, i=2 → result=[1,2,3]
5<=4? no → push 4, j=2 → result=[1,2,3,4]
5<=6 → push 5, i=3 → result=[1,2,3,4,5]
7<=6? no → push 6, j=3 → result=[1,2,3,4,5,6]
7<=8 → push 7, i=4 → result=[1,2,3,4,5,6,7]

i(4)===arr1.length(4) → exit main loop
remainder of arr2 (j=3 onward): push 8, push 10

Result: [1,2,3,4,5,6,7,8,10] ✓
```

### Complexity
- Time: O(n + m) — every element visited and appended exactly once.
- Space: O(n + m) — the new output array.

### Edge Cases
- One array empty: main loop never executes (since one pointer's bound is immediately exceeded), the remainder-append loop for the non-empty array copies it entirely — correctly returns a copy of the non-empty array.
- Both arrays empty: both loops no-op, correctly returns an empty array.
- All elements of one array smaller than all elements of the other: main loop fully consumes the smaller-valued array first, then the remainder loop appends the other array wholesale — correct, though this is functionally equivalent to a simple concatenation in this specific case.
- Duplicate values across arrays: the `<=` comparison correctly handles ties by taking from `arr1` first, preserving a stable, well-defined merge order.

### Follow-up Questions
- "Can you do this in-place if arr1 has extra trailing capacity?" → See Problem 2 — requires a fundamentally different (backward) merge direction.
- "Extend to merging k sorted arrays?" → See Problem 5's linked-list k-way merge — the same divide-and-conquer or heap-based ideas apply directly to arrays as well.

## Problem 2 — Merge Sorted Array In-Place (Merge From the Back)

### Problem
`nums1` has a length of `m + n`, where the first `m` elements are the sorted array's actual values and the last `n` elements are `0` (unused placeholder space). `nums2` has `n` sorted elements. Merge `nums2` into `nums1` in-place so that `nums1` becomes a single sorted array of length `m + n`, without using any extra array.

```
Input:  nums1 = [1,2,3,0,0,0], m = 3, nums2 = [2,5,6], n = 3
Output: nums1 = [1,2,3,4,5,6]... 

Wait, correct example:
Input:  nums1 = [1,2,3,0,0,0], m=3, nums2 = [2,5,6], n=3
Output: [1,2,2,3,5,6]
```

### Pattern Recognition
In-place merge constrained by available space — merging **from the back** (largest elements first) instead of the front, specifically because `nums1`'s "real" elements occupy its front portion and would otherwise be overwritten by a naive forward merge before they're read.

### Key Insight
Since `nums1` has exactly enough trailing empty space to hold the fully merged result, filling that space **from the end backward** — always placing the larger of the two current "largest remaining" candidates — never overwrites a `nums1` element that hasn't been read yet, because the write position is always at or ahead of both read positions.

### Approach
Three pointers: `i` at the last real element of `nums1` (index `m-1`), `j` at the last element of `nums2` (index `n-1`), `writePos` at the very last index of the combined array (`m+n-1`). Compare `nums1[i]` and `nums2[j]`, place the larger at `nums1[writePos]`, decrement the appropriate pointers, moving backward until `nums2` is fully merged in (any remaining `nums1` elements are already correctly positioned and need no further action).

### Solution

```js
function merge(nums1, m, nums2, n) {
  let i = m - 1, j = n - 1, writePos = m + n - 1;

  while (j >= 0) {
    if (i >= 0 && nums1[i] > nums2[j]) {
      nums1[writePos] = nums1[i];
      i--;
    } else {
      nums1[writePos] = nums2[j];
      j--;
    }
    writePos--;
  }

  return nums1;
}
```

### Dry Run

```
nums1 = [1,2,3,0,0,0], m=3, nums2 = [2,5,6], n=3
i=2, j=2, writePos=5

i>=0 && nums1[2]=3 > nums2[2]=6? no → nums1[5]=6, j=1, writePos=4
  nums1=[1,2,3,0,0,6]

i>=0 && nums1[2]=3 > nums2[1]=5? no → nums1[4]=5, j=0, writePos=3
  nums1=[1,2,3,0,5,6]

i>=0 && nums1[2]=3 > nums2[0]=2? yes → nums1[3]=3, i=1, writePos=2
  nums1=[1,2,3,3,5,6]

i>=0 && nums1[1]=2 > nums2[0]=2? no (equal, goes to else) → nums1[2]=2, j=-1, writePos=1
  nums1=[1,2,2,3,5,6]

j(-1) < 0 → loop ends
(remaining nums1[0..1] = [1,2] are already correctly in place — no action needed)

Result: [1,2,2,3,5,6] ✓
```

### Complexity
- Time: O(m + n) — each element from both arrays visited and placed exactly once.
- Space: O(1) extra — genuinely in-place, no auxiliary array.

### Edge Cases
- `nums2` fully smaller than all remaining `nums1` elements: `nums1[i] > nums2[j]` stays true for a stretch, correctly shifting `nums1`'s larger elements rightward before `nums2`'s elements get placed.
- `m = 0` (nums1 has no real elements, only placeholder space): loop always takes the `else` branch (since `i >= 0` is false from the start), correctly copying all of `nums2` into `nums1` directly.
- `n = 0` (nums2 is empty): loop condition `j >= 0` is false immediately, no-op — `nums1`'s first `m` elements are already correctly in place, nothing to merge.
- Why is it safe to stop once `j < 0` without an explicit "copy remaining nums1" step? — Any remaining `nums1[0..i]` elements are already in their correct final positions relative to each other and are all `<=` everything already placed from `writePos+1` onward (by the loop's invariant), so they need no further movement.

### Follow-up Questions
- "Why merge from the back instead of the front?" — Merging from the front would require shifting already-placed `nums1` elements rightward to make room for `nums2` insertions, since `nums1`'s real values occupy the very positions a forward merge would need to write into — merging backward writes into currently-unused trailing space first, never touching not-yet-read `nums1` values.
- "What if nums1 did NOT have extra trailing space (must produce a separate output)?" → Falls back to Problem 1's standard forward two-pointer merge into a new array — the in-place backward technique specifically exploits the guaranteed extra space at the end.

## Problem 3 — Merge Two Sorted Linked Lists (Iterative)

### Problem
Merge two sorted linked lists and return the merged list as a new sorted linked list, formed by splicing together the nodes of the two input lists (no new node values created).

```
Input:  l1 = 1 → 2 → 4,  l2 = 1 → 3 → 4
Output: 1 → 1 → 2 → 3 → 4 → 4
```

### Pattern Recognition
Iterative dummy-head-plus-tail-pointer merge — the direct linked-list analogue of Problem 1's array merge, but re-linking existing nodes instead of copying values into new storage.

### Key Insight
A dummy head node eliminates special-casing "what's the first node of the merged list" — every attachment, including the very first, is handled uniformly as `tail.next = <smaller node>; tail = tail.next`.

### Approach
Dummy head + `tail` pointer. Compare current nodes of both lists, attach smaller to `tail.next`, advance both that list's pointer and `tail`. Once one list is exhausted, attach the other list's remaining chain directly.

### Solution

```js
function mergeTwoLists(l1, l2) {
  const dummy = new ListNode(0);
  let tail = dummy;

  while (l1 !== null && l2 !== null) {
    if (l1.val <= l2.val) {
      tail.next = l1;
      l1 = l1.next;
    } else {
      tail.next = l2;
      l2 = l2.next;
    }
    tail = tail.next;
  }

  tail.next = l1 !== null ? l1 : l2;

  return dummy.next;
}
```

### Dry Run

```
l1 = 1→2→4, l2 = 1→3→4
dummy=[0], tail=dummy

l1.val(1) <= l2.val(1) → tail.next=l1(node "1" from l1), l1=2, tail=that node
  merged so far: 0→1(l1)

l1.val(2) <= l2.val(1)? no → tail.next=l2(node "1" from l2), l2=3, tail=that node
  merged so far: 0→1(l1)→1(l2)

l1.val(2) <= l2.val(3) → tail.next=l1(node "2"), l1=4, tail=that node
  merged so far: 0→1(l1)→1(l2)→2

l1.val(4) <= l2.val(3)? no → tail.next=l2(node "3"), l2=4, tail=that node
  merged so far: 0→1(l1)→1(l2)→2→3

l1.val(4) <= l2.val(4) → tail.next=l1(node "4" from l1), l1=null, tail=that node
  merged so far: 0→1(l1)→1(l2)→2→3→4(l1)

l1===null → main loop ends
tail.next = l2 (remaining: node "4" from l2)
  final: 0→1→1→2→3→4→4

Result (skipping dummy): 1→1→2→3→4→4 ✓
```

### Complexity
- Time: O(n + m).
- Space: O(1) extra — reuses existing nodes, only the one dummy node is newly allocated.

### Edge Cases
- One list empty: main loop never executes, the remainder-attach line directly returns the other (non-empty) list unchanged.
- Both lists empty: `tail.next = null` (since both `l1` and `l2` are `null`), correctly returns `null` (via `dummy.next`).
- Lists of very different lengths: handled naturally — the shorter list gets exhausted first, remainder logic attaches the rest of the longer one.

### Follow-up Questions
- "Show the recursive version and compare space complexity." → See Problem 4 below — O(n+m) call stack space versus this version's O(1).
- "Extend to merging k lists?" → See Problem 5.

## Problem 4 — Merge Two Sorted Linked Lists (Recursive)

### Problem
Same as Problem 3, but implemented recursively.

```
Input:  l1 = 1 → 2 → 4,  l2 = 1 → 3 → 4
Output: 1 → 1 → 2 → 3 → 4 → 4
```

### Pattern Recognition
Direct recursive restatement of the same "take the smaller head, recurse on the rest" decision — no explicit loop or dummy node.

### Key Insight
The base cases handle list exhaustion directly (an empty list simply means "the merged remainder is just the other list, unchanged"). The recursive case picks the smaller current head and defers the rest of the merge entirely to the recursive call, trusting it to correctly handle everything downstream.

### Approach
If either list is `null`, return the other. Otherwise, compare heads, set the smaller one's `.next` to the recursive merge of "its own rest" and "the other list, unchanged," and return that smaller head.

### Solution

```js
function mergeTwoListsRecursive(l1, l2) {
  if (l1 === null) return l2;
  if (l2 === null) return l1;

  if (l1.val <= l2.val) {
    l1.next = mergeTwoListsRecursive(l1.next, l2);
    return l1;
  } else {
    l2.next = mergeTwoListsRecursive(l1, l2.next);
    return l2;
  }
}
```

### Dry Run

```
l1 = 1→2→4, l2 = 1→3→4

call(l1=1,l2=1): l1.val(1)<=l2.val(1) → l1.next = call(l1=2,l2=1); return l1(val=1, from l1)

  call(l1=2,l2=1): l1.val(2)<=l2.val(1)? no → l2.next = call(l1=2,l2=3); return l2(val=1, from l2)

    call(l1=2,l2=3): l1.val(2)<=l2.val(3) → l1.next = call(l1=4,l2=3); return l1(val=2)

      call(l1=4,l2=3): l1.val(4)<=l2.val(3)? no → l2.next = call(l1=4,l2=4); return l2(val=3)

        call(l1=4,l2=4): l1.val(4)<=l2.val(4) → l1.next = call(l1=null,l2=4); return l1(val=4, from l1)

          call(l1=null,l2=4): l1===null → return l2 (val=4, from l2)  [BASE CASE]

        back in call(l1=4,l2=4): l1(val=4,l1).next = l2(val=4,l2) → returns l1(val=4,from l1)

      back in call(l1=4,l2=3): l2(val=3).next = [the val=4-from-l1 node] → returns l2(val=3)

    back in call(l1=2,l2=3): l1(val=2).next = [the val=3 node] → returns l1(val=2)

  back in call(l1=2,l2=1): l2(val=1,from l2).next = [the val=2 node] → returns l2(val=1,from l2)

back in call(l1=1,l2=1): l1(val=1,from l1).next = [the val=1-from-l2 node] → returns l1(val=1,from l1)

Tracing the final chain from the top-level return (val=1 from l1):
1(l1) → 1(l2) → 2(l1) → 3(l2) → 4(l1) → 4(l2)

Result: 1→1→2→3→4→4 ✓
```

### Complexity
- Time: O(n + m).
- Space: O(n + m) — call stack depth equals the total combined number of nodes processed before a base case is hit.

### Edge Cases
- Same as Problem 3's edge cases (empty lists, differing lengths) — base cases (`l1 === null` / `l2 === null`) handle these directly and correctly.
- Very long combined lists: risk of stack overflow due to O(n+m) recursion depth — the key trade-off to mention versus the iterative version.

### Follow-up Questions
- "Which version would you use in production code handling potentially very long lists?" → The iterative version, specifically to avoid the stack-overflow risk inherent to the recursive version's O(n+m) call stack depth on large inputs.
- "Is this recursive merge stable, same as the iterative one?" → Yes — the `l1.val <= l2.val` tie-breaking convention favors `l1` on ties, identical in effect to the iterative version's stability guarantee.

## Problem 5 — Merge k Sorted Linked Lists

### Problem
Given an array of `k` sorted linked lists, merge them into one sorted linked list and return it.

```
Input:  lists = [[1,4,5], [1,3,4], [2,6]]
Output: [1,1,2,3,4,4,5,6]
```

### Pattern Recognition
k-way merge via divide-and-conquer, reusing the two-list merge (Problem 3) as a building block applied in balanced pairs across `log k` rounds.

### Key Insight
Merging lists in balanced pairs each round (rather than sequentially folding each new list into one ever-growing result) keeps every round's total work at O(N) instead of allowing early merges to become increasingly expensive — since the list count halves each round, there are only `log k` rounds total, giving O(N log k) overall instead of the naive O(N × k).

### Approach
While more than one list remains: pair up adjacent lists and merge each pair using the standard two-list merge, producing a new (roughly half-sized) collection of lists; repeat until only one list remains.

### Solution

```js
function mergeTwoLists(l1, l2) {
  const dummy = new ListNode(0);
  let tail = dummy;

  while (l1 !== null && l2 !== null) {
    if (l1.val <= l2.val) {
      tail.next = l1;
      l1 = l1.next;
    } else {
      tail.next = l2;
      l2 = l2.next;
    }
    tail = tail.next;
  }

  tail.next = l1 !== null ? l1 : l2;
  return dummy.next;
}

function mergeKLists(lists) {
  if (lists.length === 0) return null;

  while (lists.length > 1) {
    const merged = [];

    for (let i = 0; i < lists.length; i += 2) {
      const l1 = lists[i];
      const l2 = i + 1 < lists.length ? lists[i + 1] : null;
      merged.push(mergeTwoLists(l1, l2));
    }

    lists = merged;
  }

  return lists[0];
}
```

### Dry Run

```
lists = [[1,4,5], [1,3,4], [2,6]]  (3 lists)

Round 1: lists.length=3 > 1
  pair (i=0,1): merge [1,4,5] and [1,3,4] → [1,1,3,4,4,5]
  pair (i=2, no i+1 since length=3): l2=null → merge([2,6], null) → [2,6] unchanged
  merged = [ [1,1,3,4,4,5], [2,6] ]
  lists = merged, length=2

Round 2: lists.length=2 > 1
  pair (i=0,1): merge [1,1,3,4,4,5] and [2,6] → [1,1,2,3,4,4,5,6]
  merged = [ [1,1,2,3,4,4,5,6] ]
  lists = merged, length=1

lists.length(1) === 1 → loop ends
return lists[0] = [1,1,2,3,4,4,5,6]

Result: [1,1,2,3,4,4,5,6] ✓
```

### Complexity
- Time: O(N log k) — N total elements across all lists, `log k` rounds, each round doing O(N) total work across its pairwise merges.
- Space: O(log k) for the outer loop's recursion-like structure (though implemented iteratively here, so actually O(1) extra beyond the `merged` array being built each round, which itself holds O(k) list-head references, not O(N) element copies) — the underlying linked-list nodes are reused via pointer re-linking, same as the two-list merge.

### Edge Cases
- Empty `lists` array (`k = 0`): explicit early return of `null`.
- `lists` contains some `null` entries (empty individual lists mixed in with non-empty ones): `mergeTwoLists` already handles a `null` input gracefully (returns the other list directly), so no special pre-filtering is required.
- `k = 1`: the `while (lists.length > 1)` loop never executes, directly returns the single list unchanged.
- Odd number of lists in a round: the loop's `i + 1 < lists.length` check correctly handles the final unpaired list by merging it with `null` (a no-op merge that just carries it through to the next round unchanged).

### Follow-up Questions
- "Implement the min-heap version instead, and compare." → See Q13 — same O(N log k) complexity, but processes one element at a time via heap push/pop rather than merging whole list-pairs at once; more naturally suited to streaming/incremental scenarios.
- "What if k is very large (e.g., merging 10,000 small lists)?" → Both approaches remain O(N log k), but the heap's O(k) space for holding one node per list becomes more prominent at large k — worth mentioning as a practical (not asymptotic) consideration when comparing implementations at scale.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve combining two or more already-sorted sequences into one sorted sequence?
│
├── EXACTLY TWO SORTED ARRAYS, building a NEW output array?
│   └── Standard two-pointer merge → O(n+m) time, O(n+m) space
│
├── EXACTLY TWO SORTED ARRAYS, MUST merge IN-PLACE (one array has extra trailing capacity)?
│   └── Merge FROM THE BACK (largest-first) → O(n+m) time, O(1) extra space
│       (forward merge would overwrite not-yet-read values in the array with spare capacity)
│
├── EXACTLY TWO SORTED LINKED LISTS?
│   ├── O(1) space required / large lists → Iterative (dummy head + tail pointer)
│   └── Elegance preferred, lists are bounded in size → Recursive (base case = one list null)
│
├── k SORTED LISTS OR ARRAYS (k > 2)?
│   ├── Want simplicity, reusing the two-list merge as a building block →
│   │     Divide-and-conquer pairwise merging → O(N log k) time
│   └── Lists arrive incrementally / streaming, or k is large and dynamic →
│         Min-heap (priority queue) of current heads → O(N log k) time, O(k) space
│
├── MERGING SMALL SORTED COLLECTION INTO A MUCH LARGER SORTED ONE (m ≪ n)?
│   └── Consider binary-search insertion per small-collection element → O(m log n),
│       though true in-place array insertion still costs O(n) per insert for shifting
│
├── NEED THE MERGE STEP AS PART OF A FULL SORTING ALGORITHM?
│   └── This IS merge sort's core building block — see Kadane's/other guides for
│       the full recursive divide-then-merge sort structure
│
└── "MERGE" REFERS TO COMBINING OVERLAPPING RANGES, NOT INTERLEAVING SORTED VALUES?
    └── Different problem — "merge intervals," not this pattern (see Q17)
```

## Common Bugs Checklist

Before submitting any merge-two-sorted-X solution, verify:

1. **Remainder correctly appended after the main comparison loop ends?** — Forgetting to append whichever input still has leftover elements (`while (i < arr1.length) ...` / `tail.next = l1 !== null ? l1 : l2`) silently drops the tail end of whichever input wasn't fully consumed by the main loop.

2. **Tie-breaking comparison uses `<=`, not `<`, if stability favoring one specific input is required?** — Using strict `<` still produces a *correctly sorted* output, but changes which input's element comes first on exact ties — deliberate, not accidental, tie-breaking is important if stability matters downstream.

3. **In-place backward array merge: all three pointers (`i`, `j`, `writePos`) decremented correctly, and loop condition checks the right pointer (`j >= 0`, not `i >= 0`)?** — The loop must continue until `nums2` (the array being merged IN) is fully consumed — stopping based on `i` instead would leave some of `nums2`'s elements never placed if `nums1`'s real elements run out first.

4. **Linked-list merge: dummy node's `.next` returned, not the dummy node itself?** — Returning `dummy` instead of `dummy.next` includes the placeholder `0`-value node as if it were a real element of the merged list.

5. **Recursive linked-list merge: base cases return the OTHER list, not `null`?** — `if (l1 === null) return l2;` (not `return null`) is essential — the whole point of the base case is to attach whatever remains of the non-exhausted list.

6. **k-way divide-and-conquer: odd number of lists in a round handled (paired with `null`, not skipped or errored)?** — `i + 1 < lists.length ? lists[i+1] : null` ensures a leftover unpaired list at the end of a round is still carried forward (via a no-op merge against `null`), not silently dropped from the final result.

7. **k-way merge: `null`/empty individual lists in the input array handled gracefully?** — The underlying two-list merge already handles a `null` input correctly, but it's worth explicitly confirming (or testing) rather than assuming, especially if the k-way merge implementation is later modified to use a different two-list merge that might not have the same null-handling.

---

**Final Tip:** At the 5 YOE level, interviewers expect immediate recognition of the core two-pointer merge invariant ("always take the smaller of the two current candidates") as the foundation underlying every variant in this family — array merge, linked-list merge, in-place backward merge, and k-way merge via divide-and-conquer or a heap. Stating that invariant explicitly, then explaining *why* a specific variant needs a twist on it (backward direction for in-place array merging, pairwise batching for k-way efficiency, a dummy node for uniform linked-list attachment logic) is what distinguishes genuine understanding from having memorized several superficially different-looking snippets of merge code.
