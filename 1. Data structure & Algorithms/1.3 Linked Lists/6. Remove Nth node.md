## Topic A: The Fixed-Gap Two-Pointer Technique

### Section A1: Fundamentals

**Q1. What is the fixed-gap two-pointer technique for linked lists, and what class of problems does it solve?**

A: The fixed-gap (or "ruler") technique maintains two pointers that traverse a linked list simultaneously with a fixed number of nodes between them. When the leading pointer (fast) reaches the end of the list, the trailing pointer (slow) is at a deterministic position relative to the end — controlled entirely by the initial gap. It solves any problem whose answer is a node at a position defined *relative to the tail* rather than relative to the head: removing the Nth-from-last node, returning the kth-from-last value, splitting a list at the midpoint, and detecting when two differently-positioned pointers converge. The technique transforms "relative to the tail" (which requires knowing the list length) into "where slow lands when fast exits" (which requires only one traversal).

```
Problem:  "Find the node N steps from the end"
Naive:    count length L first, then travel to position L-N    → two traversals
Gap trick: advance fast N steps first, then advance both together → one traversal

When fast reaches null, slow is exactly N steps behind the null → N steps from end ✓
```

**Q2. Why does a gap of N+1 between fast and slow place slow at the predecessor of the Nth-from-end node?**

A: Number the nodes 1 through L from the head. The Nth-from-end node is at 1-indexed position `L - N + 1`. Its predecessor is at position `L - N`. When fast starts N+1 positions ahead of slow (both beginning at the dummy node at position 0), after `L - N` joint steps:
- slow has moved from position 0 to position `L - N` — the predecessor of the target.
- fast has moved from position `N+1` to position `L+1` — one past the last node (null).

Checking `fast == null` as the loop termination condition therefore stops both pointers at exactly the right positions. The key formula: **gap = (position you want fast to be at upon exit) minus (position you want slow to be at upon exit) = (L+1) - (L-N) = N+1**.

```
List: dummy → 1 → 2 → 3 → 4 → 5   (N=2, remove node 4)

Initial:  fast is N+1=3 steps ahead of slow.
           [slow:dummy] → 1 → 2 → [fast:3] → 4 → 5

Advance both until fast reaches null:
  Step 1: slow→1,      fast→4
  Step 2: slow→2,      fast→5
  Step 3: slow→3,      fast→null  ← loop ends

slow is now at node 3, which is the predecessor of node 4 (the 2nd from end).
slow.next = slow.next.next  →  3 → 5  (node 4 deleted) ✓
```

**Q3. What is the dummy node pattern, and why is it essential for linked list deletion problems?**

A: A dummy (sentinel) node is a synthetic head node placed before the real head. Its value is irrelevant; its purpose is structural. It provides three guarantees:

**Guarantee 1 — Uniform predecessor logic**: every real node, including the head, has a predecessor. Without dummy, deleting the head requires a special case (`if N == length: return head.next`); with dummy, the same `slow.next = slow.next.next` rewiring handles all nodes uniformly.

**Guarantee 2 — Clean return**: always `return dummy.next` as the new head, even when the original head was deleted. No conditional return logic needed.

**Guarantee 3 — Valid start position for slow**: slow begins at dummy, which is a real node whose `.next` can be safely reassigned — avoiding an "invalid predecessor" null-pointer situation.

```js
// Without dummy: head deletion is a branch
function removeNth(head, n) {
  let length = 0, curr = head;
  while (curr) { length++; curr = curr.next; }
  if (n === length) return head.next; // SPECIAL CASE for head

  curr = head;
  for (let i = 0; i < length - n - 1; i++) curr = curr.next;
  curr.next = curr.next.next;
  return head;
}

// With dummy: no branch needed at all
function removeNth(head, n) {
  const dummy = new ListNode(0, head); // dummy.next = head
  let slow = dummy, fast = dummy;
  // ... gap logic ...
  slow.next = slow.next.next; // handles head deletion identically to any other node
  return dummy.next;
}
```

**Q4. What is the two-pass approach to "Remove Nth from End," and what are the trade-offs vs the one-pass two-pointer approach?**

A: **Two-pass**: (1) traverse the entire list to compute length L; (2) traverse again to position L-N, then delete `curr.next`. Simple, readable, O(L) time, O(1) space — but requires two full traversals (2L total steps).

**One-pass (fixed-gap two-pointer)**: advance fast N+1 steps ahead of slow from the dummy node; advance both together until fast is null. Slow is now at the predecessor — delete in O(1). O(L) time, O(1) space — and only L+1 total steps for fast, L-N steps for slow. Single traversal, better constant factor.

In interview contexts, always offer the one-pass solution — LeetCode 19 explicitly asks for it. In code review or production, the two-pass version's clarity may outweigh the constant-factor savings unless the list is extremely large or traversal is costly (e.g., network-backed linked structures).

```
Two-pass total steps: L (count) + (L-N) (find position) = 2L - N  ≈ 2L
One-pass total steps: (N+1) (advance fast) + (L-N) (joint advance) = L+1
```

**Q5. How does the initial gap amount control where slow lands when fast reaches null?**

A: The gap is the only tunable parameter, and it precisely controls the semantics of the operation:

- **Gap = N+1, fast terminates at null**: slow lands at the *predecessor* of the Nth-from-end node — use for **deletion** (`slow.next = slow.next.next`).
- **Gap = N, fast terminates at null**: slow lands *on* the Nth-from-end node — use for **returning the node or its value**.
- **Fast advances 2× per step, slow advances 1× per step (not a fixed gap but a fixed rate ratio)**: slow lands at the *middle* node when fast exits — use for **middle-finding**, **palindrome checks**, and **list splitting**.

```
Invariant at exit (fast = null):
  slow_position = (total_list_length) - gap_at_termination

gap = N+1  → slow at L - (N+1) = L-N-1 (0-indexed) = predecessor of Nth-from-end
gap = N    → slow at L - N     (0-indexed) = Nth-from-end node itself
2× speed   → slow at ⌊L/2⌋    = middle node
```

### Section A2: Advanced Patterns

**Q6. What are the two variants of "find the middle" and when does each apply?**

A: For an even-length list, "middle" is ambiguous — there are two center nodes. The variant is controlled by when the fast pointer stops:

**Lower-middle (preferred for splitting before merge)**: `while (fast.next && fast.next.next)` — fast stops when its *next* is null or its *next.next* is null. For `[1→2→3→4]`: slow lands on `2`. The second half `[3→4]` is the same length as the first `[1→2]`.

**Upper-middle (preferred for palindrome / right-biased splits)**: `while (fast && fast.next)` — fast stops when it itself is null or its next is null. For `[1→2→3→4]`: slow lands on `3`. The second half `[3→4]` includes the upper-middle.

For odd-length lists, both variants produce the same result (the exact center node). The distinction only matters for even-length inputs.

```
List: 1 → 2 → 3 → 4
                   slow  fast

Lower-middle (while fast.next && fast.next.next):
Start:  slow=1, fast=1
Step 1: slow=2, fast=3
  fast.next=4 (not null), fast.next.next=null → STOP
  slow=2 (lower-middle) ✓

Upper-middle (while fast && fast.next):
Start:  slow=1, fast=1
Step 1: slow=2, fast=3
Step 2: slow=3, fast=null → STOP
  slow=3 (upper-middle) ✓
```

**Q7. What is Floyd's Cycle Detection algorithm, and how is it a two-pointer technique without a fixed gap?**

A: Floyd's algorithm uses slow (1 step/iteration) and fast (2 steps/iteration) — a fixed *speed ratio* rather than a fixed *gap*. If a cycle exists, fast eventually enters the cycle and "laps" slow. The gap between fast and slow decreases by 1 each iteration once both are inside the cycle (fast gains 1 net step per iteration). They are guaranteed to meet in at most C more iterations after slow enters the cycle (where C is cycle length). If no cycle exists, fast reaches null in at most L/2 iterations.

The mathematical core: inside a cycle of length C, if fast is k steps ahead of slow, it will close that gap by 1 per step and meet slow in k steps (since meeting is mod-C). The meeting is inevitable because the gap is always ≥ 1 inside the cycle (fast never "jumps over" slow — it approaches monotonically mod C).

```js
function hasCycle(head) {
  let slow = head, fast = head;
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) return true; // reference equality — same node object
  }
  return false; // fast exited → no cycle
}
// Key: === compares node identity (memory address), not node value
```

**Q8. How do you find the cycle entry node after detecting a cycle with Floyd's algorithm?**

A: After fast and slow meet inside the cycle, reset slow to the head while keeping fast at the meeting point. Advance both 1 step per iteration. They meet exactly at the cycle entry node. Mathematical proof: let F = distance from head to cycle entry, C = cycle length, k = distance from cycle entry to meeting point (inside cycle). At the time of meeting: slow has traveled F + k steps; fast has traveled 2(F+k) steps. Since fast's extra distance must be a multiple of C: 2(F+k) - (F+k) = F+k = m×C for some integer m. Therefore F = m×C - k. Advancing F more steps from the meeting point (which is k into the cycle) lands at k + F = k + m×C - k = m×C steps into the cycle = cycle entry (since 0 and m×C are the same position mod C). Advancing F steps from head also reaches the entry. Both arrive simultaneously.

```js
function detectCycle(head) {
  let slow = head, fast = head;

  // Phase 1: detect meeting point inside cycle
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) break;
  }

  if (!fast || !fast.next) return null; // no cycle

  // Phase 2: find cycle entry
  slow = head; // reset one pointer to head
  while (slow !== fast) {
    slow = slow.next;
    fast = fast.next; // both move 1 step — no longer 2× speed
  }
  return slow; // cycle entry node
}
```

**Q9. How does the "intersection of two linked lists" problem use pointer reassignment to equalize positions without computing lengths?**

A: Pointer A starts at head of list A; pointer B starts at head of list B. Both advance 1 step per iteration. When pointer A reaches null, redirect it to head B; when pointer B reaches null, redirect it to head A. They will then meet at the intersection node (or both reach null simultaneously if no intersection). This works because both pointers travel exactly `|A| + |B|` total steps, arriving at the intersection at the same iteration. The non-shared prefixes (lengths `a` and `b` where `a + c = |A|`, `b + c = |B|`) are automatically neutralized: pointer A travels `a` non-shared + `c` shared + `b` non-shared = `a + b + c` steps to reach intersection; pointer B travels `b + c + a = a + b + c` steps. Equal total steps → simultaneous arrival.

```
List A:      a1 → a2 ──────────────┐
                                    c1 → c2 → c3
List B: b1 → b2 → b3 ──────────────┘

Pointer A path: a1→a2→c1→c2→c3→null→b1→b2→b3→[c1]  (a=2, b=3, c=3 → 8 steps)
Pointer B path: b1→b2→b3→c1→c2→c3→null→a1→a2→[c1]  (b=3, a=2, c=3 → 8 steps)
Both meet at c1 ✓
```

## Topic B: Edge Cases & Failure Modes

### Section B1: When the Technique Works and When It Breaks

**Q10. What is the "delete a node given only that node" trick, and where does it fail?**

A: Given only a reference to an interior node to delete (no access to head or predecessor), copy the next node's value into the current node and bypass the next node: `node.val = node.next.val; node.next = node.next.next`. This simulates deletion by disguising the current node as its successor, then removing the successor. It fails in two situations: (1) **tail node** — `node.next` is null, so there is no successor to copy from (cannot delete the last node this way); (2) **when node identity matters** — the "deleted" node still exists at the same memory address with different content; any external references still point to it, now seeing the successor's value.

```
List: 1 → 2 → 3 → 4, delete node 2 (no access to predecessor):

Copy successor's value:  node(2).val = node(3).val = 3
Bypass successor:        node.next = node.next.next = node(4)
Result: 1 → 3 → 4  (node 2 still exists in memory, now holds value 3)

Node identity caveat: any reference externally holding "node 2" now sees value 3.
```

**Q11. In what situations does the fixed-gap two-pointer technique require modification or fail entirely?**

A: Three failure modes:

**N > list length**: fast falls off the end before slow even starts moving jointly. Either validate N ≤ L upfront (two-pass length check) or count how many steps fast took and abort if it hits null before N+1 steps. The problem constraints typically guarantee N ≤ L, but production code should handle this.

**Cycle in the list**: fast loops infinitely inside the cycle — the `while (fast && fast.next)` loop never terminates. Must confirm the list is acyclic before applying gap-based traversal (or switch to Floyd's if cycle detection is the problem).

**Ambiguous "middle" for even-length lists**: the two fast-pointer termination conditions produce different nodes. Must choose lower-middle or upper-middle based on whether the downstream algorithm needs the first or second half to be longer.

```
N > length example: list has 3 nodes, N=5
  Advance fast 6 steps: hits null at step 3 — never reached gap of 6.
  Guard: if fast becomes null before gap is established → handle (N > L) case.

N = L (remove head) with dummy:
  fast advances N+1 = L+1 steps from dummy → reaches null exactly
  slow stays at dummy → slow.next = dummy.next = head deleted ✓ (no special case needed)
```

## Topic C: Cross-Topic & Interview-Style Questions

**Q12. "Walk through your thought process when you see a linked list problem involving a position relative to the end."**

A: Five mental checkpoints in order:

1. **Operation type** — deleting a node (need predecessor → gap N+1) or returning a node/value (need the node itself → gap N)?
2. **Dummy node needed?** — if the head could be the target of deletion, always add a dummy node to avoid a special case.
3. **Termination condition** — `fast == null` (slow one behind last node) or `fast.next == null` (slow on last node)? Choose based on whether you need slow one node earlier or later.
4. **Even-length middle ambiguity** — does this problem care about left-middle vs right-middle? Pick the right fast-pointer stop condition.
5. **Edge cases**: N = list length (head deletion), N = 1 (tail deletion), single node, two nodes. Run the invariant mentally on each before coding.

```
Received: "Remove the Nth node from the end in one pass"

→ Need predecessor of target → gap = N+1
→ Head could be deleted → dummy node required
→ Termination: fast == null (slow lands at predecessor)
→ middle ambiguity: N/A for this problem
→ Edge: N = L → fast makes L+1 steps, slow stays at dummy → dummy.next = old head.next ✓
```

**Q13. "When should you prefer the two-pass approach over one-pass for this problem?"**

A: Two legitimate cases for preferring two-pass: (1) **team readability** — if the codebase is maintained by engineers less familiar with the fixed-gap trick, `goToPosition(length - n)` is unambiguous. The one-pass variant requires a comment explaining why the gap is N+1 rather than N. (2) **N needs validation** — the two-pass naturally detects N > L (length is known before the deletion traversal). The one-pass technique must abort mid-advance if fast hits null before the gap is established, adding complexity.

In an interview, state this trade-off, then implement the one-pass version — it demonstrates you know both approaches and can articulate the cost-benefit.

**Q14. "Why is Remove Nth from End O(L) time, not O(N) or O(L-N)?"**

A: Fast advances N+1 steps (depends on N) and then L-N steps jointly with slow (depends on L-N) for a total of N+1 + L-N = L+1 steps. Slow advances 0 + (L-N) steps. The total node visits across both pointers: (L+1) + (L-N) = 2L - N + 1. In the worst cases: N=1 (remove tail) → fast visits L+1 nodes, slow visits L-1 nodes; N=L (remove head) → fast visits L+1 nodes, slow visits 0 nodes. In all cases, total work is Θ(L) — bounded by L, not N or L-N independently. Space is O(1) — only two pointer variables, regardless of L.

**Q15. In one sentence each, state the invariant maintained by each two-pointer variant for linked lists.**

A:
- **Fixed-gap deletion (Remove Nth from End)**: when fast reaches null, slow is at the predecessor of the Nth-from-end node — maintained by initializing fast exactly N+1 steps ahead of slow at the dummy node.
- **Fixed-gap retrieval (Find Kth from End)**: when fast reaches null, slow is at the Kth-from-end node — maintained by initializing fast exactly K steps ahead of slow at the head.
- **2× speed middle-finding**: when fast can no longer advance two steps, slow is at the middle — maintained by fast moving 2 nodes per iteration and slow moving 1.
- **Floyd's cycle detection**: if a cycle exists, fast and slow always meet inside it — maintained by fast closing the intra-cycle gap by 1 node per iteration (gaining 1 step on slow each round).
- **Intersection equalization**: both pointers arrive at the intersection simultaneously — maintained by each pointer traversing exactly `|A| + |B|` total nodes before meeting.

## Problem 1 — Remove Nth Node from End of List

### Problem
Given the head of a linked list, remove the Nth node from the end of the list and return its head. Do it in one pass.

```
Input:  head = [1, 2, 3, 4, 5], n = 2
Output: [1, 2, 3, 5]   (node 4, which is 2nd from end, is removed)

Input:  head = [1], n = 1
Output: []             (only node removed)

Input:  head = [1, 2], n = 1
Output: [1]            (node 2, the tail, is removed)

Input:  head = [1, 2], n = 2
Output: [2]            (node 1, the head, is removed)
```

### Pattern Recognition
Fixed-gap two-pointer with dummy node — establish a gap of N+1 between fast and slow starting at dummy; advance both until fast is null; slow is then at the predecessor of the Nth-from-end node; rewire `slow.next`.

### Key Insight
A gap of N+1 (not N) is the critical choice: it lands slow at the *predecessor* of the target node, not the target itself. The predecessor's `.next` pointer is what needs to be rewired. The dummy node absorbs the head-deletion edge case, making the rewiring logic identical for all positions.

### Approach
Create `dummy.next = head`. Initialize `slow = fast = dummy`. Advance fast N+1 times (establishing the gap). Then advance both 1 step per iteration until `fast == null`. Now `slow.next` is the target; set `slow.next = slow.next.next`. Return `dummy.next`.

### Solution

```js
class ListNode {
  constructor(val = 0, next = null) {
    this.val = val;
    this.next = next;
  }
}

function removeNthFromEnd(head, n) {
  const dummy = new ListNode(0);
  dummy.next = head; // dummy precedes head; absorbs head-deletion edge case

  let slow = dummy;
  let fast = dummy;

  // Step 1: advance fast n+1 steps ahead of slow
  // After this, gap between slow and fast = n+1 nodes
  for (let i = 0; i <= n; i++) {
    fast = fast.next;
  }

  // Step 2: advance both until fast falls off the end
  // Invariant: gap between slow and fast stays n+1
  while (fast !== null) {
    slow = slow.next;
    fast = fast.next;
  }

  // Now slow is at the predecessor of the nth-from-end node
  // slow.next is the node to delete
  slow.next = slow.next.next;

  return dummy.next; // head may have changed if n === list length
}
```

### Dry Run

```
Input: 1 → 2 → 3 → 4 → 5,  n = 2

Setup: dummy → 1 → 2 → 3 → 4 → 5 → null
       slow = dummy, fast = dummy

Step 1: advance fast n+1 = 3 times:
  i=0: fast = dummy.next = 1
  i=1: fast = 1.next = 2
  i=2: fast = 2.next = 3
  After: slow=dummy, fast=3  (gap = 3 nodes: dummy→1→2→3)

Step 2: advance both until fast = null:
  Iteration 1: slow=1,     fast=4
  Iteration 2: slow=2,     fast=5
  Iteration 3: slow=3,     fast=null  ← loop ends

slow = node(3). slow.next = node(4) = 2nd from end ✓

Deletion: slow.next = slow.next.next = node(5)
Result: dummy → 1 → 2 → 3 → 5 → null

Return dummy.next = node(1)
Output: [1, 2, 3, 5] ✓

---
Edge case: head = [1, 2], n = 2 (remove head)

Setup: dummy → 1 → 2 → null
       slow = dummy, fast = dummy

Step 1: advance fast n+1 = 3 times:
  i=0: fast = 1
  i=1: fast = 2
  i=2: fast = null
  After: slow=dummy, fast=null

Step 2: fast is already null → while loop never executes.
  slow remains at dummy.

slow.next = slow.next.next = node(2)
dummy → 2 → null

Return dummy.next = node(2)
Output: [2] ✓  (head correctly deleted without special-case branch)
```

### Complexity
- Time: O(L) — fast travels L+1 total steps (N+1 advance + L-N joint steps); slow travels L-N steps. Total work is O(L) regardless of N.
- Space: O(1) — two pointer variables; dummy node is a single allocation independent of list size.

### Edge Cases
- **N = L (remove head)**: fast reaches null during the initial advance; slow stays at dummy; `dummy.next = old head.next` — head deleted correctly without any branch.
- **N = 1 (remove tail)**: fast advances to the last node +1 = null; slow lands at the second-to-last node; `slow.next = null` — tail deleted.
- **Single node, N = 1**: `dummy → 1 → null`. Fast advances to null in one step; slow stays at dummy; `dummy.next = null`. Returns `dummy.next = null` — empty list.
- **Two nodes**: covered in the dry run above; gap = N+1 may hit null before joint traversal begins — handled correctly by the `while (fast !== null)` condition.

### Follow-up Questions
- "What if N could be larger than the list length?" — Add a guard: count advances during the fast-forwarding phase; if fast hits null before N+1 steps are complete, N > L — return head unchanged (or throw per problem contract).
- "Two-pass version?" — Count length L in pass 1; advance to node at position `L - N` in pass 2; `curr.next = curr.next.next`. Same O(L) time/O(1) space but ~2× more steps. Use when clarity is preferred.
- "Remove all nodes with value X?" — Different problem structure: scan with a single pointer, always checking `curr.next.val`. Dummy node still useful for head-removal uniformity.

## Problem 2 — Find the Middle of a Linked List

### Problem
Given the head of a singly-linked list, return the middle node. If the list has two middle nodes, return the second middle node (upper-middle).

```
Input:  head = [1, 2, 3, 4, 5]
Output: node(3)   (middle of odd-length list)

Input:  head = [1, 2, 3, 4]
Output: node(3)   (second/upper middle of even-length list)
```

### Pattern Recognition
2× speed two-pointer — fast advances 2 steps per iteration while slow advances 1 step. When fast can no longer advance, slow is at the middle. No gap is pre-established; the speed ratio determines the final position.

### Key Insight
Fast covers ground twice as quickly as slow. When fast has traversed the entire list (reaches null), slow has traversed half the list — landing at the middle. For even-length lists, the termination condition (`while fast && fast.next` vs `while fast.next && fast.next.next`) controls whether slow lands on the lower-middle (left of center) or upper-middle (right of center).

### Approach
`slow = fast = head`. While `fast && fast.next`: advance slow 1 step, advance fast 2 steps. When the loop exits, slow is at the middle (upper-middle for even-length).

### Solution

```js
function middleNode(head) {
  let slow = head;
  let fast = head;

  // Termination: fast == null or fast.next == null
  // → fast exits at or past the last node
  // → slow is at the upper-middle (second of two middles for even-length lists)
  while (fast !== null && fast.next !== null) {
    slow = slow.next;       // advance 1 step
    fast = fast.next.next;  // advance 2 steps
  }

  return slow; // upper-middle
}

// Variant: lower-middle (first of two middles for even-length lists)
function middleNodeLower(head) {
  let slow = head;
  let fast = head;

  // Termination: fast.next == null or fast.next.next == null
  // → fast stops one step earlier → slow stops one step earlier
  while (fast.next !== null && fast.next.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
  }

  return slow; // lower-middle
}
```

### Dry Run

```
Upper-middle: head = [1, 2, 3, 4]
slow=1, fast=1

Iteration 1: fast=1 (not null), fast.next=2 (not null) → enter loop.
  slow=2, fast=3
Iteration 2: fast=3 (not null), fast.next=4 (not null) → enter loop.
  slow=3, fast=null (fast.next.next from 3 is 4.next = null)
Iteration 3: fast=null → exit loop.
Return slow = node(3) ✓ (upper-middle of [1,2,3,4])

---
Lower-middle: head = [1, 2, 3, 4]
slow=1, fast=1

Iteration 1: fast.next=2 (not null), fast.next.next=3 (not null) → enter loop.
  slow=2, fast=3
Iteration 2: fast.next=4 (not null), fast.next.next=null → EXIT loop.
Return slow = node(2) ✓ (lower-middle of [1,2,3,4])

---
Odd-length: head = [1, 2, 3, 4, 5]
slow=1, fast=1

Iter 1: slow=2, fast=3
Iter 2: slow=3, fast=5
Iter 3: fast=5 (not null), fast.next=null → exit.
Return slow = node(3) ✓ (exact center — both variants agree on odd-length lists)
```

### Complexity
- Time: O(L) — fast traverses the entire list in L/2 iterations; slow traverses L/2 nodes. Total: O(L) node visits.
- Space: O(1) — two pointers only.

### Edge Cases
- **Single node**: fast = node(1). `fast.next = null` → loop never executes. Returns head = node(1). Correct.
- **Two nodes**: fast = node(1). Iteration 1: `fast.next = node(2)` (not null), `fast.next.next = null` → with upper-middle condition, loop runs once: slow moves to node(2), fast moves to null. Returns node(2) = second node (upper-middle). Correct.
- **Choosing variant**: for "split list in half for merge sort" → lower-middle (first half is same length or longer). For "check palindrome from second half" → upper-middle (second half starts at exact second half start).

### Follow-up Questions
- "Reorder List (LeetCode 143)?" — Find lower-middle, split there, reverse the second half, then interleave the two halves.
- "Palindrome Linked List?" — Find upper-middle, reverse from there to end, compare reversed half with first half.
- "What if fast starts at head.next instead?" — Equivalent to starting both at head with `while fast && fast.next` — produces the same upper-middle but reads differently; the standard formulation above is clearer.

## Problem 3 — Linked List Cycle Detection

### Problem
Given the head of a linked list, determine if the linked list has a cycle in it. A cycle exists if some node can be reached again by continuously following `next` pointers.

```
Input:  head = [3, 2, 0, -4], tail connects to index 1
Output: true    (cycle: -4 → 2 → 0 → -4 → ...)

Input:  head = [1, 2], tail connects to index 0
Output: true    (cycle: 2 → 1 → 2 → ...)

Input:  head = [1]
Output: false   (no cycle)
```

### Pattern Recognition
Floyd's cycle detection — slow advances 1 step, fast advances 2 steps. If they ever meet (same node object), a cycle exists. If fast reaches null, no cycle exists.

### Key Insight
In an acyclic list, fast always reaches null before slow — no meeting is possible. In a cyclic list, once both pointers enter the cycle, fast is "chasing" slow inside a closed loop and must catch up. Fast gains 1 step on slow per iteration (moves 2, slow moves 1, net gain = 1). If fast starts k steps behind slow in the cycle, it catches slow in exactly k iterations. Meeting is always guaranteed within one full cycle traversal after slow enters.

### Approach
`slow = fast = head`. While `fast && fast.next`: advance slow 1, fast 2. If `slow === fast` (reference equality — same node object), return true. If loop exits (fast reached null), return false.

### Solution

```js
function hasCycle(head) {
  if (!head) return false; // empty list — no cycle

  let slow = head;
  let fast = head;

  while (fast !== null && fast.next !== null) {
    slow = slow.next;       // move 1 step
    fast = fast.next.next;  // move 2 steps

    // Reference equality: same node object in memory, not just same value
    if (slow === fast) return true;
  }

  // fast reached null → list terminates → no cycle
  return false;
}
```

### Dry Run

```
No cycle: head = [1 → 2 → 3 → null]
slow=1, fast=1

Iter 1: slow=2, fast=3.   slow===fast? 2===3? No.
Iter 2: fast.next=null → while condition fails → exit.
Return false ✓

---
With cycle: [3 → 2 → 0 → -4 → (back to 2)]
Nodes: A=3, B=2, C=0, D=-4.  D.next = B.

slow=A, fast=A.

Iter 1: slow=B, fast=C.    slow===fast? B===C? No.
Iter 2: slow=C, fast=B.    (fast: C→D→B)  slow===fast? C===B? No.
Iter 3: slow=D, fast=D.    (fast: B→C→D→... wait)

Let me redo:
Iter 1: slow=B(2), fast=C(0).
Iter 2: slow=C(0), fast=B(2).    (fast moves C→D→B: two steps from C)
  Wait: fast is at C. fast.next = D. fast.next.next = D.next = B. So fast→B.
Iter 3: slow=D(-4), fast=D(-4).  (fast at B: B.next=C, B.next.next=D. So fast→D.)
  slow===fast? D===D? YES → return true ✓

Total: 3 iterations to detect the cycle.
```

### Complexity
- Time: O(L + C) where L = distance from head to cycle entry, C = cycle length. Fast detects the cycle within C steps of slow entering it. Total iterations ≤ L + C = total unique nodes.
- Space: O(1) — two pointer variables, no extra data structures.

### Edge Cases
- **Null head**: guard at the start prevents null-pointer dereference. Return false.
- **Single node, no cycle**: fast = head. `fast.next = null` → loop never runs. Returns false.
- **Single node, self-loop**: `head.next = head`. Iter 1: slow = head, fast = head → `slow === fast` immediately → returns true. (Check is AFTER the advance, not before, so this works.)
- **Two-node cycle**: `A → B → A`. Iter 1: slow=B, fast=B (fast: A→B→A = B). `slow===fast` → true.

### Follow-up Questions
- "Using a HashSet instead?" — Store each visited node in a Set; if `set.has(current)` before adding, there's a cycle. O(L) time, O(L) space — correct but uses O(L) extra memory. Floyd's is strictly superior in space.
- "Can you detect a cycle without modifying the list and without extra space?" — Floyd's is the canonical O(1) space solution. Destructive techniques (setting visited nodes to a sentinel value) modify the list.
- "What if fast moves 3 steps instead of 2?" — Still works: if the cycle exists, fast eventually catches slow (the net closing rate becomes 2 per iteration, still always positive). However, detecting the meeting is trickier since fast may "jump over" slow. The standard 2× speed is the simplest that guarantees detection.

## Problem 4 — Linked List Cycle II (Find Cycle Entry Point)

### Problem
Given the head of a linked list, return the node where the cycle begins. If there is no cycle, return `null`.

```
Input:  head = [3, 2, 0, -4], tail connects to index 1
Output: node(2)   (cycle begins at index 1)

Input:  head = [1, 2], tail connects to index 0
Output: node(1)   (cycle begins at head)

Input:  head = [1]
Output: null      (no cycle)
```

### Pattern Recognition
Floyd's cycle detection (Phase 1) + pointer reset (Phase 2) — detect the meeting point inside the cycle using 1×/2× speed pointers, then reset one pointer to head and advance both 1 step at a time until they meet at the cycle entry.

### Key Insight
At the meeting point inside the cycle, the distance from head to the cycle entry (F) equals the distance from the meeting point forward to the cycle entry (C - k), where C is cycle length and k is distance from entry to meeting point. Resetting slow to head and advancing both at 1×/1× speed means they converge after exactly F steps — at the cycle entry. This algebraic property holds for any F and C, not just specific cases.

Proof sketch: slow traveled F + k steps total. Fast traveled 2(F + k) steps total. Since fast's extra distance is a multiple of C: F + k = mC for some integer m ≥ 1. So F = mC - k. Starting from the meeting point (which is k steps into the cycle), F = mC - k more steps = m full cycles minus k steps = lands at cycle entry (since mC ≡ 0 mod C, and −k backs up k steps from k = 0 mod C). Starting from head, F steps also lands at cycle entry by definition.

### Approach
Phase 1: detect meeting point (Floyd's standard detection). Phase 2: reset slow to head; keep fast at meeting point; advance both 1 step until `slow === fast`; return slow (the cycle entry).

### Solution

```js
function detectCycle(head) {
  if (!head || !head.next) return null;

  let slow = head;
  let fast = head;

  // Phase 1: find meeting point inside cycle
  let hasCycle = false;
  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) {
      hasCycle = true;
      break;
    }
  }

  if (!hasCycle) return null; // no cycle detected

  // Phase 2: find cycle entry
  // Reset slow to head; keep fast at meeting point.
  // Both advance 1 step per iteration.
  slow = head;
  while (slow !== fast) {
    slow = slow.next;
    fast = fast.next; // 1 step only — no longer 2×
  }

  return slow; // cycle entry node
}
```

### Dry Run

```
List: A(3) → B(2) → C(0) → D(-4) → (back to B)
F = distance head→entry = 1 (A→B)
C = cycle length = 3 (B→C→D→B)
k = distance entry→meeting = ? Let's compute.

Phase 1:
slow=A, fast=A.
Iter 1: slow=B, fast=C.
Iter 2: slow=C, fast=B.   (fast: C→D→B)
Iter 3: slow=D, fast=D.   (fast: B→C→D)   ← meeting point: D

Verify: slow traveled 3 steps: A→B→C→D. fast traveled 6 steps: A→B→C→D→B→C→D.
k = distance from B (entry) to D (meeting) = 2 steps (B→C→D).
F = 1. Check: F = mC - k → 1 = m×3 - 2 → m=1, 1 = 3-2 = 1 ✓

Phase 2:
slow reset to head=A. fast stays at D (meeting point).
Iter 1: slow=B, fast=B.  (D.next = B)
slow===fast → B ✓

Return node B = node with value 2 ✓
```

### Complexity
- Time: O(F + C) — Phase 1 runs F + C iterations at most; Phase 2 runs F iterations. Total O(F + C) = O(number of unique nodes).
- Space: O(1) — two pointers only.

### Edge Cases
- **No cycle**: Phase 1 exits without `hasCycle = true`; return null immediately.
- **Cycle starts at head (F=0)**: Phase 2 starts with `slow=head, fast=meetingPoint`. If F=0, entry IS head. Advancing: slow=head.next, fast=meetingPoint.next. They will converge at head after 0 steps... wait, actually `slow=head` and the while condition is `slow !== fast`. If slow starts at head and the cycle entry is head, the condition `slow===fast` after resetting means the check happens before any step. Let's verify: after Phase 1, fast is at some meeting point inside the cycle. slow is reset to head = cycle entry. The `while (slow !== fast)` loop: head === meetingPoint? Unlikely. Both advance and meet at head (the cycle entry) after C - k steps... actually the proof still holds. F=0 means F = mC - k → 0 = mC - k → k = mC → meeting point is exactly at the cycle entry itself. So after Phase 2 reset: slow=head=entry, fast=meetingPoint=entry. `slow===fast` immediately → return slow = cycle entry ✓.
- **Single node, self-loop**: head.next = head. Phase 1: slow=head.next=head, fast=head.next.next=head.next=head. slow===fast immediately. Phase 2: slow reset to head. slow===fast already → return head ✓.

### Follow-up Questions
- "Prove that fast and slow must meet inside the cycle (not pass through each other)?" — Inside a cycle of length C, at any moment when both pointers are in the cycle, the distance from fast to slow (going forward) decreases by 1 per step (fast +2, slow +1, gap closes by 1). The distance is always a positive integer from C-1 down to 0 — it reaches 0 (they meet) before it can "wrap around."
- "What if we want the total cycle length?" — After detecting the meeting point in Phase 1, keep fast stationary and advance slow until `slow === fast` again. Count the steps — that's C.

## Problem 5 — Palindrome Linked List

### Problem
Given the head of a singly linked list, return `true` if it is a palindrome or `false` otherwise. Must solve in O(n) time and O(1) space.

```
Input:  head = [1, 2, 2, 1]
Output: true

Input:  head = [1, 2]
Output: false

Input:  head = [1, 2, 3, 2, 1]
Output: true
```

### Pattern Recognition
Three-phase combination: (1) find the middle using 2× speed pointers; (2) reverse the second half in-place; (3) compare the first half and reversed second half node by node. Uses both the middle-finding technique and iterative list reversal.

### Key Insight
A palindrome reads the same forward and backward. For a linked list, this means the first half and the reversed second half are identical sequences. We can't traverse backward (singly-linked), so we reverse the second half in-place and compare. Finding the middle with the lower-middle variant ensures the reversed second half is the same length or one shorter than the first half — the comparison loop driven by the second half pointer naturally terminates at the right time.

### Approach
Phase 1: find lower-middle using `while (fast.next && fast.next.next)`. Phase 2: reverse from `middle.next` to the end. Phase 3: compare `left = head` and `right = reversed head of second half` node by node while `right !== null`. If all values match, it's a palindrome.

### Solution

```js
function isPalindrome(head) {
  if (!head || !head.next) return true; // 0 or 1 node — trivially palindrome

  // Phase 1: find lower-middle
  // After loop: slow is at lower-middle (left of center for even-length lists)
  let slow = head, fast = head;
  while (fast.next !== null && fast.next.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
  }

  // Phase 2: reverse second half (slow.next onwards)
  // slow.next is the start of the second half
  let prev = null;
  let curr = slow.next;
  while (curr !== null) {
    const nextTemp = curr.next;
    curr.next = prev;
    prev = curr;
    curr = nextTemp;
  }
  // prev is now the head of the reversed second half

  // Phase 3: compare first half (from head) and reversed second half (from prev)
  let left = head;
  let right = prev;
  while (right !== null) { // second half drives the loop (may be shorter for odd-length)
    if (left.val !== right.val) return false;
    left = left.next;
    right = right.next;
  }

  return true;
}
```

### Dry Run

```
head = [1, 2, 2, 1]
Nodes: A(1) → B(2) → C(2) → D(1) → null

Phase 1 — Find lower-middle:
slow=A, fast=A.
Check: fast.next=B (not null), fast.next.next=C (not null) → enter loop.
  slow=B, fast=C.
Check: fast.next=D (not null), fast.next.next=null → EXIT loop.
Lower-middle = slow = B(2). Second half starts at slow.next = C(2).

Phase 2 — Reverse C → D → null:
prev=null, curr=C(2).
Iter 1: next=D. C.next=null. prev=C. curr=D.
Iter 2: next=null. D.next=C. prev=D. curr=null.
Reversed second half: D(1) → C(2) → null.
prev = D.

Phase 3 — Compare:
left=A(1), right=D(1).
Iter 1: A.val=1 === D.val=1 ✓. left=B(2), right=C(2).
Iter 2: B.val=2 === C.val=2 ✓. left=C(2), right=null.
right=null → loop ends.

Return true ✓

---
head = [1, 2, 3, 2, 1]
Nodes: A(1)→B(2)→C(3)→D(2)→E(1)→null

Phase 1:
slow=A,fast=A.
Iter 1: slow=B, fast=C.
  fast.next=D(not null), fast.next.next=E(not null) → loop.
Iter 2: slow=C, fast=E.
  fast.next=null → EXIT.

```

### Complexity
- Time: O(n) — Phase 1: O(n/2) to find middle; Phase 2: O(n/2) to reverse second half; Phase 3: O(n/2) to compare. Total: O(n).
- Space: O(1) — all three phases use only a constant number of pointer variables; the reversal is in-place.

### Edge Cases
- **Single node**: `!head.next` guard returns true immediately.
- **Two nodes**: Phase 1 loop never executes (fast.next.next = null from the start), slow stays at head = node(1) (lower-middle). Second half = node(2). Reversed: node(2). Compare: node(1).val vs node(2).val — correct.
- **Odd-length list**: lower-middle is the exact center. Second half (length `(n-1)/2`) is one shorter than the first half (length `(n+1)/2`). Phase 3 terminates when right=null — the center node is never compared to anything (correct, since it matches itself in a palindrome).
- **All identical values**: all comparisons succeed; returns true.
- **Restore list?** — The reversal mutates the original list. If mutation is not allowed, restore the second half by reversing it again after Phase 3, or use O(n) space to store values in an array.

### Follow-up Questions
- "Restore the list to its original state after checking?" — After Phase 3, reverse the reversed second half again and reattach it to the lower-middle: `middle.next = reverse(prev)`. This restores the original list structure.
- "Recursive approach?" — Use a global left pointer starting at head; recurse to the end, then compare `left.val === currentNode.val` while unwinding, advancing left each time. O(n) time, O(n) space (call stack).

## Problem 6 — Intersection of Two Linked Lists

### Problem
Given the heads of two singly linked lists, return the node at which the two lists intersect. If the two linked lists have no intersection, return `null`. The lists must retain their original structure after the function returns.

```
Input:
  listA = [4, 1, 8, 4, 5]
  listB = [5, 6, 1, 8, 4, 5]
  Both share the suffix starting at node(8).

Output: node(8)  (reference to the shared node, not just the value)

Input:
  listA = [2, 6, 4]
  listB = [1, 5]
  No intersection.

Output: null
```

### Pattern Recognition
Pointer reassignment equalization — pointer A traverses list A then list B; pointer B traverses list B then list A. Both travel the same total distance `|A| + |B|` and must arrive at the intersection simultaneously (or both reach null simultaneously if no intersection).

### Key Insight
If two lists intersect, their tails are shared — the non-shared prefixes are the only length difference. Pointer A and pointer B both need to "spend" the same total steps on non-shared portions before reaching the intersection. By having each pointer traverse both lists (in different orders), the non-shared-portion steps cancel out automatically. No length computation required.

Algebraically: let `a` = length of A's non-shared prefix, `b` = length of B's non-shared prefix, `c` = length of shared tail. Pointer A travels `a + c + b` steps total before reaching the intersection on its second journey. Pointer B travels `b + c + a` steps — identical. They arrive at the same iteration.

### Approach
`pA = headA`, `pB = headB`. While `pA !== pB`: advance `pA` (or redirect to `headB` if null); advance `pB` (or redirect to `headA` if null). Return `pA` when the loop exits (either the intersection node or null).

### Solution

```js
function getIntersectionNode(headA, headB) {
  if (!headA || !headB) return null;

  let pA = headA;
  let pB = headB;

  // Both pointers advance 1 step per iteration.
  // When a pointer reaches null (end of its first list), redirect to the other list's head.
  // After at most |A| + |B| steps, both pointers will meet:
  //   - at the intersection node (if one exists), or
  //   - both at null (if no intersection exists).
  while (pA !== pB) {
    pA = (pA === null) ? headB : pA.next; // redirect on null
    pB = (pB === null) ? headA : pB.next;
  }

  return pA; // intersection node or null
}
```

### Dry Run

```
listA: A1(4) → A2(1) → C1(8) → C2(4) → C3(5) → null
listB: B1(5) → B2(6) → B3(1) → C1(8) → C2(4) → C3(5) → null
a=2, b=3, c=3. Intersection at C1(8).

pA=A1, pB=B1.

pA  path: A1→A2→C1→C2→C3→null→B1→B2→B3→[C1]  (10 steps)
pB  path: B1→B2→B3→C1→C2→C3→null→A1→A2→[C1]  (10 steps)

Step-by-step:
Iter 1:  pA=A2,   pB=B2.
Iter 2:  pA=C1,   pB=B3.
Iter 3:  pA=C2,   pB=C1.
Iter 4:  pA=C3,   pB=C2.
Iter 5:  pA=null, pB=C3.
  pA was null → redirect to headB=B1. pA=B1.
Iter 6:  pA=B1→next=B2, pB=C3→next=null.
  Step: pA=B2, pB=null.
  pB was null → redirect to headA=A1. pB=A1.
Iter 7:  pA=B3,   pB=A2.
Iter 8:  pA=C1,   pB=C1.  pA===pB → exit loop ✓

Return pA = C1 = node(8) ✓

Verification: pA and pB are both at node(8) after a+b = 2+3 = 5 steps of "equalization"
beyond the end of the shorter list's non-shared prefix.

---
No intersection:
  listA: [2→6→4], listB: [1→5]
  pA path: 2→6→4→null→1→5→null→[null]  (7 steps)
  pB path: 1→5→null→2→6→4→null→[null]  (7 steps)
  Both reach null simultaneously → pA===pB===null → return null ✓
```

### Complexity
- Time: O(|A| + |B|) — each pointer traverses at most both lists before meeting. Total iterations ≤ `|A| + |B|`.
- Space: O(1) — two pointer variables only.

### Edge Cases
- **No intersection**: both pointers simultaneously reach null after `|A| + |B|` steps. `pA === pB === null` → return null.
- **One list is empty**: `(!headA || !headB)` guard returns null immediately.
- **Same list (entire lists are shared)**: `a = 0, b = 0`. pA and pB both start at the same node → `pA === pB` immediately → return headA (= headB).
- **Lists of equal length with intersection**: the pointers align on the first pass without ever reaching null. They meet at the intersection on the first traversal.

### Follow-up Questions
- "Using a HashSet?" — Traverse all of listA, storing each node in a Set. Traverse listB; return the first node found in the Set. O(|A| + |B|) time, O(|A|) space. Correct but uses O(n) extra space — the two-pointer approach is strictly better.
- "Compute lengths explicitly instead?" — Compute `|A|` and `|B|`; advance the longer list's pointer by `||A| - |B||` steps; then advance both until they meet. O(|A| + |B|) time, O(1) space — same complexity as the pointer-reassignment approach but more verbose.

## Common Bugs Checklist

Before submitting any solution from this category, verify:

1. **Gap is N+1 for deletion, not N?** — A gap of N lands slow on the target itself, giving no predecessor reference. `slow.next` would be the node after the target, not the target. Always use N+1 when the operation requires rewiring `slow.next`.

2. **Dummy node used whenever head could be deleted?** — Without dummy, the case where `n == listLength` (remove head) requires a special-case return. With dummy, `slow.next = slow.next.next` handles head deletion identically to any other node. Never skip the dummy for deletion problems.

3. **`return dummy.next` not `return head`?** — After potential head deletion, `head` still points to the original head node (now removed). Always return `dummy.next`, which reflects the updated head regardless of which node was deleted.

4. **Loop terminates on `fast === null`, not `fast.next === null`?** — For gap = N+1 deletion, fast must reach null (one past the last node) so slow lands at the predecessor. Terminating at `fast.next === null` makes fast stop one node earlier, leaving slow one node too early (at the node before the predecessor, not the predecessor itself).

5. **`slow === fast` check placed AFTER advancing both pointers in Floyd's?** — Checking before advancing exits immediately on the first iteration (slow = fast = head, always "meet" before any movement). The check must come after at least one advance, so the meeting inside a cycle is detected rather than a false positive at the start.

6. **Reference equality (`===`) not value equality (`==` or `.val ===`) for node comparison?** — Two nodes with the same value but different memory addresses are not the same node. Cycle detection (`slow === fast`) and intersection detection (`pA === pB`) both require reference equality — the same node object in memory, not the same stored value.

7. **Phase 2 of cycle entry uses 1× speed for both pointers, not 2×?** — After meeting in Floyd's Phase 1, both pointers must advance 1 step per iteration in Phase 2. Keeping fast at 2× would again produce a meeting point inside the cycle, not the entry. Switch to `fast = fast.next` (not `fast.next.next`) for Phase 2.

8. **Palindrome: using upper-middle instead of lower-middle for the split?** — If slow lands on the upper-middle, `slow.next` points to the *third quarter* of an even-length list instead of the start of the second half. Use `while (fast.next && fast.next.next)` to get the lower-middle; the second half starts at `slow.next`.

9. **Palindrome: comparison loop driven by `right !== null`, not `left !== null`?** — For odd-length lists, the second half (right) is one node shorter than the first half. Driving the loop with `left` would attempt `left.val` vs `right.val` when `right` is already null — a null pointer error. Always use `while (right !== null)`.

10. **Intersection: checking `pA.val === pB.val` instead of `pA === pB`?** — Multiple nodes may share the same value at different positions. The problem asks for the specific node where the lists physically merge — a reference check, not a value check. `pA === pB` confirms identity (same object); `pA.val === pB.val` is a red herring.

11. **Not advancing fast at least once before starting the joint traversal?** — If the fast-forwarding loop runs `for (let i = 0; i < n; i++)` instead of `i <= n`, the gap is N, not N+1. Off-by-one in the advance loop is the most common bug in the Remove Nth problem. Count the iterations carefully: N+1 advances are needed to land slow at the predecessor.

12. **Forgetting the initial advance guard when N > list length?** — If the initial `for` loop tries to advance fast more times than the list has nodes, fast becomes null prematurely. The joint `while (fast !== null)` loop then never runs, slow stays at dummy, and `slow.next` is the original head — an incorrect deletion. Add a guard if the problem doesn't guarantee N ≤ L.

---

**Final Tip:** At the 5 YOE level, the signal that separates confident answers from memorized solutions is immediately stating the *invariant and its proof*. For Remove Nth from End: *"I'll establish a gap of N+1 from the dummy node so that when fast reaches null, slow is exactly at the predecessor of the Nth-from-end node — that's the only node whose .next pointer I need to rewire."* For Floyd's entry: *"after meeting inside the cycle, the distance from the meeting point forward to the entry equals the distance from the head to the entry (by the F = mC - k identity), so resetting one pointer to head and advancing both at 1× speed brings them to the entry simultaneously."* Stating the invariant first — not the code — is the mark of a senior who owns the technique, not the pattern.
