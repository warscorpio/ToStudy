# DSA: Fast/Slow Pointer (Floyd's Tortoise & Hare) — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the fast/slow pointer technique?**
A: The fast/slow pointer technique (also called Floyd's Tortoise and Hare algorithm) uses two pointers that traverse a sequence — typically a linked list — at different speeds. The slow pointer advances one step at a time; the fast pointer advances two steps at a time. The speed differential creates predictable geometric relationships between the pointers' positions that can be exploited to solve problems about cycles, midpoints, and relative positions — all in O(n) time and O(1) space without modifying the structure or using extra memory.

**Q2. What class of problems does the fast/slow pointer solve?**
A: Five canonical problem families:
- **Finding the middle node** of a linked list — when fast reaches the end, slow is at the middle.
- **Cycle detection** — if a cycle exists, fast will eventually lap slow and they'll meet inside the cycle.
- **Cycle entry point** — after detection, a secondary two-pointer technique finds where the cycle begins.
- **Cycle length** — after detection, count steps for fast to lap slow again.
- **k-th node from the end** — advance fast k steps first, then move both together until fast hits null.

These problems all share a common property: they require knowing a relative position within a linked list (midpoint, distance from end, cycle entry) that can't be computed without either traversing the list twice, using extra memory, or using the fast/slow differential.

**Q3. Why does the fast pointer moving at 2× speed place the slow pointer at the middle when fast reaches the end?**
A: When fast reaches the end (or null), it has traveled the full length n of the list. Since fast moves at 2× the speed of slow, slow has traveled n/2 steps — exactly the middle. More precisely:
- **Odd-length list** (n = 2k+1): fast takes k full two-step moves to reach the last node (index 2k). Slow takes k one-step moves → index k, the exact middle.
- **Even-length list** (n = 2k): fast takes k two-step moves to reach null (past the last node at index 2k-1). Slow takes k one-step moves → index k, the second of the two middle nodes.

The even-length behavior — slow landing on the *second* middle node — is a detail interviewers specifically probe. Always clarify which middle is needed before coding.

**Q4. For an even-length list, which "middle" does the standard fast/slow algorithm return, and how do you get the other one?**
A: The standard algorithm (advance fast two steps while `fast !== null && fast.next !== null`) places slow on the **second middle** (index n/2, 0-indexed). For a 4-node list `[1,2,3,4]`, slow lands on node 3 (index 2).

To get the **first middle** (index n/2 - 1), use a slightly different loop condition: advance fast while `fast.next !== null && fast.next.next !== null`. This stops fast one step earlier, leaving slow one step behind — on node 2 (index 1) for a 4-node list.

Which condition to use depends on the problem:
- "Find middle and split the list in half" → first middle (so the left half has ≤ right half length).
- "Find middle for mergesort on linked list" → often first middle for even lists.
- "Find middle node" as stated in LeetCode 876 → second middle (problem guarantees this definition).

**Q5. What is the time and space complexity of the fast/slow pointer technique?**
A: O(n) time — in the worst case both pointers traverse the list once (for linear lists) or at most twice (for cycle-detection problems). O(1) space — only two pointer variables, regardless of list length. This is the primary advantage over approaches that collect all nodes into an array (O(n) space) or count nodes first and traverse again (two passes but still O(1) space — valid but less elegant).

### Section 2: Cycle Detection & Entry

**Q6. How does the fast/slow pointer detect a cycle?**
A: If a cycle exists, both pointers are eventually inside the cycle. Fast laps slow — it gains one node per step on slow (moving 2 vs 1). Because the cycle is finite, fast must eventually occupy the same node as slow. If there's no cycle, fast reaches null and terminates — proving no cycle exists. The key insight: in a cyclic structure, fast can never "escape" past slow indefinitely because the cycle brings it back around.

**Q7. Prove that fast and slow always meet inside the cycle if one exists.**
A: Let the non-cycle portion have length F and the cycle have length C. When slow enters the cycle (after F steps), fast has traveled 2F steps — it is already `2F mod C` steps into the cycle. The "gap" between fast and slow (fast ahead of slow, measuring within the cycle) is `(2F - F) mod C = F mod C` steps. Each subsequent step, fast gains 1 node on slow — the gap decreases by 1 per step. After exactly `C - (F mod C)` more steps (or `F mod C` if the gap is measured as "fast behind slow"), the gap reaches 0 and they meet. Since C is finite and the gap decreases by 1 each step, they are guaranteed to meet in O(C) additional steps after slow enters the cycle.

**Q8. How do you find the entry point of the cycle after detecting it?**
A: After fast and slow meet inside the cycle, reset one pointer (say `fast`) to the head of the list. Keep the other (`slow`) at the meeting point. Now advance both one step at a time. They will meet exactly at the cycle entry node.

**Why it works (Floyd's proof):** Let F = distance from head to cycle entry, C = cycle length, and let the meeting point be distance D from the cycle entry (measuring forward in the cycle). At the time of meeting:
- Slow traveled: F + D steps.
- Fast traveled: F + D + n×C steps (went around the cycle n extra times).
- Fast = 2 × slow: `F + D + nC = 2(F + D)` → `nC = F + D` → `F = nC - D`.

After resetting, the head pointer travels F steps to reach the cycle entry. The meeting-point pointer also travels F steps — it's D steps past the entry, so F more steps means `D + F = D + (nC - D) = nC` steps, which is exactly `n` full loops — landing back at the cycle entry. Both pointers arrive at the cycle entry simultaneously.

**Q9. How do you find the length of the cycle after detecting it?**
A: After fast and slow meet, keep one pointer (say `slow`) fixed and advance the other (`fast`) one step at a time, counting steps until `fast` returns to `slow`'s position. The count is the cycle length C. Alternatively, advance `fast` two steps and `slow` one step again from the meeting point and count until they meet again — also gives C. The simpler one-pointer approach (single stepping from the meeting point back to itself) is more common in interviews.

### Section 3: K-th Node From End

**Q10. How do you find the k-th node from the end of a linked list in one pass?**
A: Advance `fast` k steps from the head (so fast is k nodes ahead of slow). Then advance both pointers one step at a time until `fast.next === null` (fast is at the last node). At this point, `slow` is exactly k nodes from the end.

Why it works: when `fast` is at the last node (index n-1), it is `n-1` steps from the head. Since fast started k steps ahead of slow, slow is at index `n-1-k` — which is the `(k+1)`-th node from the end, or equivalently, slow.next is the k-th node from the end. Adjust the stopping condition based on whether you want the k-th node itself or the node before it (useful for deletion).

**Q11. How does the k-th from end technique extend to "remove the k-th node from the end"?**
A: Use a dummy sentinel node at the head so that deletion works uniformly even for the first node. Advance `fast` k+1 steps from the dummy (or k steps from the real head). Then advance both until `fast === null`. Now `slow` is the node just before the k-th from last. Set `slow.next = slow.next.next` to delete the k-th from last node. The dummy sentinel handles the edge case where the node to delete is the head.

```js
function removeNthFromEnd(head, n) {
  const dummy = new ListNode(0, head);
  let fast = dummy, slow = dummy;

  // advance fast n+1 steps so slow stops one before the target
  for (let i = 0; i <= n; i++) fast = fast.next;

  while (fast !== null) {
    fast = fast.next;
    slow = slow.next;
  }

  slow.next = slow.next.next; // delete the n-th from last
  return dummy.next;
}
```

### Section 4: Fast/Slow on Non-Linked-List Structures

**Q12. How does the fast/slow technique apply to arrays for cycle detection (e.g., "Find the Duplicate Number")?**
A: If array values are in range `[1, n]` for an array of length `n+1`, treat the array as a function `f(x) = nums[x]` that maps indices to indices. Following this function creates a "linked list" where `x → nums[x] → nums[nums[x]] → ...`. A duplicate value means two indices point to the same next index — which is a cycle entry. Apply Floyd's algorithm:
- Slow: `slow = nums[slow]` (one step).
- Fast: `fast = nums[nums[fast]]` (two steps).
- After meeting: reset slow to index 0, advance both one step at a time → they meet at the duplicate value (cycle entry).

**Q13. How does the fast/slow technique apply to "Happy Number" (cycle detection on integers)?**
A: Define `f(n)` = sum of squares of digits of n. A "happy number" eventually reaches 1 under repeated application of f. An "unhappy number" enters a cycle that doesn't include 1. Apply fast/slow: slow = `f(slow)`, fast = `f(f(fast))`. If they meet at 1 → happy. If they meet anywhere else → unhappy (cycle detected, doesn't reach 1).

**Q14. Can the fast/slow technique work on doubly linked lists or circular lists?**
A: For doubly linked lists: cycle detection still works — the fast/slow logic only follows `next` pointers, and the presence of `prev` doesn't affect it. For circular lists (where the last node's `next` points back to a node, not null): the list is entirely a cycle from the beginning. Fast and slow both start inside the cycle and will meet — Floyd's algorithm still terminates and correctly identifies the cycle. The "entry point" detection will find the node that the last node points back to.

### Section 5: Common Variants & Edge Cases

**Q15. What happens when fast/slow is applied to an empty list or single-node list?**
A: Handle as guards before the main loop:
- **Empty list** (`head === null`): return null — no middle, no cycle, nothing to find.
- **Single node** (`head.next === null`): slow = head = the only node = the middle. Fast can't move; loop doesn't execute. Cycle detection immediately returns false (fast is already null or fast.next is null).
- **Two-node list**: fast moves to the second node (or null if checking `fast.next.next`); slow stays at the first node = the first middle, or moves to second = second middle, depending on the stopping condition. Always trace through manually for n=2 when verifying.

**Q16. What is the standard loop condition for finding the middle, and what does each variant do?**
A: Two variants:

```js
// Variant A: stops with slow on the SECOND middle (even lists)
while (fast !== null && fast.next !== null) {
  slow = slow.next;
  fast = fast.next.next;
}
// Result: [1,2,3] → slow at 2 (index 1, correct single middle)
//         [1,2,3,4] → slow at 3 (index 2, second middle)

// Variant B: stops with slow on the FIRST middle (even lists)
while (fast.next !== null && fast.next.next !== null) {
  slow = slow.next;
  fast = fast.next.next;
}
// Result: [1,2,3] → slow at 1 (index 0) — WRONG for single middle!
//         [1,2,3,4] → slow at 2 (index 1, first middle)
```

Variant A is safer for general use — it handles all cases correctly for "find the middle node." Variant B is useful specifically when you need the first middle for even-length lists and the list is guaranteed to have at least 2 nodes (e.g., linked list sort where you need to split without leaving a single-node "left half").

**Q17. What is the "palindrome linked list" check, and how does it combine fast/slow with reversal?**
A: Three-step process:
1. **Find middle** using fast/slow (slow stops at the second middle for odd, second middle for even — leaving the first half shorter or equal).
2. **Reverse the second half** starting from `slow` (or `slow.next` for odd lists to exclude the exact middle).
3. **Compare** the first half (from head) and reversed second half node by node. If all match, it's a palindrome.

This achieves O(n) time, O(1) space — no extra array needed. The original list can be restored by reversing the second half again after comparison (interviewers sometimes ask for this as a follow-up).

**Q18. What are the most common implementation bugs in fast/slow pointer problems?**
A: Five patterns account for most bugs:
1. **Wrong loop condition** — using `while (fast !== null)` instead of `while (fast !== null && fast.next !== null)` causes a null pointer error when fast tries to move two steps from the last node.
2. **Off-by-one in k-th from end** — advancing fast k steps vs k+1 steps determines whether slow stops at the target node or the node before it. Getting this wrong for deletion problems silently removes the wrong node.
3. **Missing null check before cycle entry detection** — after the fast/slow meeting, resetting one pointer to head and advancing assumes the cycle was confirmed; if called on a non-cyclic list, this runs forever.
4. **Not using a dummy node for deletion** — deleting the head node fails if `slow.next = slow.next.next` is the only pattern and there's no previous node to update.
5. **Mutating the list during traversal** — reversing the second half for palindrome check and forgetting to restore it (if the problem requires it), or checking the meeting point after cycle detection but having moved pointers past it.

### Section 6: Scenario / Interview-Style Questions

**Q19. "An interviewer asks you to find the middle of a linked list. You solve it. They ask: what if the list has 1 million nodes — is there a better approach?" How do you respond?**
A: The fast/slow approach is already optimal — O(n) time, O(1) space. There is no better asymptotic complexity since you must read at least n/2 nodes to know where the middle is. The alternative (count nodes, traverse to n/2) is also O(n) time and O(1) space but makes two full passes instead of one. If the interviewer is probing for this distinction, say: "fast/slow visits each node at most once for slow and at most once for fast — it's one pass for slow, one pass for fast, but they run concurrently so the wall-clock traversal is one pass." For a doubly linked list with a known length, you could start from both ends and meet in the middle — also O(n/2) steps, same asymptotic complexity.

**Q20. "You're told a linked list might have a cycle. How do you detect it, find the entry, and remove the cycle — all without extra memory?"**
A: Three phases:
1. **Detect**: fast/slow pointers — if they meet, cycle exists.
2. **Find entry**: reset one pointer to head, advance both one step at a time — they meet at the cycle entry.
3. **Remove**: after finding the entry, traverse the cycle with a single pointer until you find the node whose `next` points back to the entry (the last node in the cycle). Set its `next = null`.

All three phases are O(n) time, O(1) space, no modification to the list structure until the final `next = null` in phase 3.

**Q21. "Design an algorithm to reorder a linked list L0→L1→…→Ln-1→Ln to L0→Ln→L1→Ln-1→…" How do you approach this?"**
A: This is a three-step pattern that tests whether you recognize when fast/slow is a subproblem:
1. **Find middle** with fast/slow — split the list into two halves.
2. **Reverse the second half** in place (three-pointer reversal).
3. **Merge** the two halves by interleaving — take one from each alternately.

All three steps are O(n) time, O(1) space. The fast/slow component is the first step — recognizing it as a building block rather than the whole solution is what distinguishes a 5 YOE answer.

**Q22. "How would you detect a cycle in a directed graph — can you apply fast/slow pointer here?"**
A: Fast/slow pointer as described works on sequences (linked lists, integer-function iteration) where each node has exactly one "next." For a general directed graph (where nodes can have multiple outgoing edges), fast/slow doesn't directly apply — you'd use DFS with a visited/in-stack color scheme (white/gray/black) instead. However, if the graph is a functional graph (each node has exactly one outgoing edge — like the "find duplicate" problem where `f(x) = nums[x]`), it reduces to a linked list with cycles and fast/slow applies directly.

## Problem 1 — Middle of the Linked List

### Problem
Given the head of a singly linked list, return the middle node. If there are two middle nodes, return the **second** middle node.

```
Input:  1 → 2 → 3 → 4 → 5
Output: node 3

Input:  1 → 2 → 3 → 4 → 5 → 6
Output: node 4  (second middle)
```

### Pattern Recognition
Classic fast/slow pointer — the defining use case. Fast moves 2× and reaches the end when slow is at the middle. O(1) space, single pass.

### Key Insight
Fast travels 2n/2 = n nodes when slow travels n/2 nodes. The speed ratio of 2:1 maps "fast at end" directly to "slow at middle."

### Approach
Start both pointers at head. Advance fast two steps and slow one step per iteration. Loop while `fast !== null && fast.next !== null` (fast needs two remaining nodes to take two steps). When the loop exits, slow is at the middle.

### Solution

```js
function middleNode(head) {
  let slow = head;
  let fast = head;

  while (fast !== null && fast.next !== null) {
    slow = slow.next;       // one step
    fast = fast.next.next;  // two steps
  }

  // when fast reaches end, slow is at the middle
  return slow;
}
```

### Dry Run

```
List: 1 → 2 → 3 → 4 → 5  (odd length, n=5)

Start: slow=1, fast=1

Iteration 1: slow=2, fast=3  (fast.next=4, not null → continue)
Iteration 2: slow=3, fast=5  (fast.next=null → loop exits)

Return slow = node(3) ✓


List: 1 → 2 → 3 → 4 → 5 → 6  (even length, n=6)

Start: slow=1, fast=1

Iteration 1: slow=2, fast=3  (fast.next=4, fast.next.next=5 → continue)
Iteration 2: slow=3, fast=5  (fast.next=6, fast.next.next=null → continue)
Iteration 3: slow=4, fast=null (loop condition: fast=null → exit)

Wait — let's retrace iteration 3:
Before: slow=3, fast=5
fast.next = 6 (not null), fast.next.next = null... 
Check condition: fast !== null ✓, fast.next !== null (fast.next=6) ✓ → enter loop
slow = 4, fast = fast.next.next = null

Condition check: fast === null → exit

Return slow = node(4)  (second middle) ✓
```

### Complexity
- Time: O(n) — slow traverses n/2 nodes; fast traverses n nodes; both in one logical pass.
- Space: O(1) — two pointer variables.

### Edge Cases
- Single node (`head.next === null`): `fast = head`, loop condition `fast.next !== null` is false → loop never runs → return head. Correct — single node is its own middle.
- Two nodes: slow stays at node 1; fast moves to node 2 (fast.next = null → loop exits after 1 iteration). Wait — check: start slow=1, fast=1. Condition: fast(1) ≠ null ✓, fast.next(2) ≠ null ✓ → enter loop. slow=2, fast=null. Condition: fast=null → exit. Return node 2 (second middle of [1,2]). Correct.
- Empty list: guard with `if (!head) return null` before the loop.

### Follow-up Questions
- "Return the first middle for even-length lists?" → Change loop condition to `while (fast.next !== null && fast.next.next !== null)`. Slow stops one step earlier.
- "Split the list into two halves at the middle?" → After finding the middle, save `mid.next` as the second half's head, then set `mid.next = null` to sever the first half.
- "Find the middle without fast/slow?" → Count nodes (one pass), then traverse to index n//2 (second pass). O(n) time, O(1) space — valid but two passes.

## Problem 2 — Linked List Cycle Detection

### Problem
Given the head of a linked list, return `true` if the list has a cycle, `false` otherwise. A cycle exists if some node's `next` pointer points back to a previous node.

```
Input:  3 → 2 → 0 → -4 → (back to 2)
Output: true

Input:  1 → 2 → (back to 1)
Output: true

Input:  1
Output: false
```

### Pattern Recognition
Cycle detection — the canonical use of fast/slow. In a linear list, fast reaches null. In a cyclic list, fast and slow are trapped in the cycle and fast eventually laps slow.

### Key Insight
In a cycle of length C, fast gains 1 node per step on slow. After entering the cycle they will meet within C steps. In a linear list, fast exits (reaches null) before any meeting can happen.

### Approach
Advance fast two steps, slow one step. If they ever point to the same node → cycle exists. If fast reaches null → no cycle.

### Solution

```js
function hasCycle(head) {
  let slow = head;
  let fast = head;

  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;

    if (slow === fast) return true; // pointers met — cycle confirmed
  }

  return false; // fast reached end — no cycle
}
```

### Dry Run

```
List: 3 → 2 → 0 → -4 → (→2, cycle at index 1)
Nodes: [3(0), 2(1), 0(2), -4(3)]  -4.next = 2

Start: slow=3, fast=3

Iter 1: slow=2, fast=0   (fast: 3→2→0)  slow≠fast
Iter 2: slow=0, fast=2   (fast: 0→-4→2) slow≠fast
Iter 3: slow=-4, fast=-4 (fast: 2→0→-4) slow===fast → return true ✓


List: 1 → 2 → null (no cycle)

Start: slow=1, fast=1

Iter 1: slow=2, fast=null (fast: 1→2→null)
Loop condition: fast === null → exit → return false ✓
```

### Complexity
- Time: O(n) — in a linear list, fast reaches null in n/2 iterations. In a cyclic list, once slow enters the cycle, they meet within C iterations (cycle length). Total: O(F + C) = O(n).
- Space: O(1).

### Edge Cases
- Empty list (`head === null`): loop condition `fast !== null` is false immediately → return false. Correct.
- Single node, no cycle: `fast.next === null` → exit → return false.
- Single node pointing to itself: `fast.next = head`, `fast.next.next = head.next = head`. After 1 iteration: slow = head, fast = head → `slow === fast` → return true. Correct.
- Cycle at the very first node (head.next = head): detected in first iteration.

### Follow-up Questions
- "Find the node where the cycle begins?" → After detection (slow === fast), reset fast to head. Advance both one step at a time — they meet at the cycle entry.
- "Find the cycle length?" → After detection, keep slow fixed; advance fast one step at a time counting until fast returns to slow.
- "Remove the cycle?" → Find the cycle entry, traverse the cycle until reaching a node whose next is the entry (the "tail"), set tail.next = null.

## Problem 3 — Linked List Cycle II (Find Cycle Entry)

### Problem
Given the head of a linked list that may contain a cycle, return the node where the cycle begins. If there is no cycle, return `null`.

```
Input:  3 → 2 → 0 → -4 → (back to 2)
Output: node(2)   (cycle starts at index 1)

Input:  1 → 2 → (back to 1)
Output: node(1)   (cycle starts at head)

Input:  1
Output: null
```

### Pattern Recognition
Cycle entry detection — extends cycle detection with a second phase. Floyd's entry-point algorithm: after fast/slow meet, reset one pointer to head and advance both one step at a time until they meet again. Meeting point = cycle entry.

### Key Insight
At the meeting point inside the cycle, let F = steps from head to cycle entry, D = steps from entry to meeting point, C = cycle length. Floyd's proof shows `F = nC - D` for some integer n — meaning F steps from head equals F steps from the meeting point (both arrive at the cycle entry simultaneously).

### Approach
Phase 1: detect the meeting point inside the cycle using fast/slow (2:1 speed). If no meeting → return null. Phase 2: reset fast to head, keep slow at meeting point. Advance both one step at a time — first node where they meet again is the cycle entry.

### Solution

```js
function detectCycle(head) {
  let slow = head, fast = head;

  // Phase 1: detect cycle — find any meeting point inside cycle
  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) break; // meeting point found
  }

  // no cycle detected — fast escaped to null
  if (fast === null || fast.next === null) return null;

  // Phase 2: find cycle entry
  // reset one pointer to head, keep other at meeting point
  fast = head;
  while (fast !== slow) {
    slow = slow.next;
    fast = fast.next; // both move ONE step now
  }

  return slow; // both pointers meet at cycle entry
}
```

### Dry Run

```
List: 3(0) → 2(1) → 0(2) → -4(3) → back to 2(1)
F = 1 (steps from head to entry node 2)
C = 3 (cycle: 2→0→-4→2)

Phase 1:
Start: slow=3, fast=3

Iter 1: slow=2, fast=0
Iter 2: slow=0, fast=2
Iter 3: slow=-4, fast=-4  → slow===fast → break

Meeting point: node(-4)
D = 2 (steps from cycle entry 2 to meeting point -4, going 2→0→-4)
Verify: F=1, nC-D: n=1 → C-D = 3-2 = 1 = F ✓

Phase 2:
fast reset to head (node 3), slow stays at node(-4)

Iter 1: fast=2, slow=2  → fast===slow → return node(2) ✓


List: 1(0) → 2(1) → back to 1(0)
F = 0 (cycle starts at head), C = 2

Phase 1:
Start: slow=1, fast=1

Iter 1: slow=2, fast=2  (fast: 1→2→1=2... wait)
Recheck: fast.next.next = node(1).next = node(2)? 
No: fast=1, fast.next=2, fast.next.next=1 (back to head)
After iter 1: slow=2, fast=1

Iter 2: slow=1, fast=1  → slow===fast → break (meeting at node 1)

Phase 2:
fast reset to head (node 1), slow at node(1) — already same!
fast===slow immediately → return node(1) ✓
```

### Complexity
- Phase 1: O(F + C) — slow enters the cycle after F steps, then at most C steps to meet fast.
- Phase 2: O(F) — both pointers travel F steps to reach the entry.
- Total: O(n). Space: O(1).

### Edge Cases
- No cycle: phase 1 exits via `fast === null || fast.next === null`; return null.
- Cycle at head (F=0): phase 2 loop condition `fast !== slow` is immediately false (both start at head); returns head correctly.
- Entire list is a cycle (last node's next = head): F=0, cycle length = n; handled correctly as F=0 case.

### Follow-up Questions
- "What if you only need to know if a cycle exists, not where?" → Stop after phase 1 (simpler hasCycle).
- "How do you remove the cycle once you find the entry?" → Traverse the cycle from entry until you find the node whose next = entry (the tail), set tail.next = null.
- "Prove correctness of phase 2 without memorizing the proof?" → Explain intuitively: "fast has F steps to reach entry; slow also needs exactly F more steps from the meeting point to wrap around and reach entry — they arrive simultaneously."

## Problem 4 — Find the Duplicate Number

### Problem
Given an array `nums` of n+1 integers where each integer is in range `[1, n]`, there is exactly one repeated number. Find it without modifying the array and using only O(1) extra space.

```
Input:  nums = [1, 3, 4, 2, 2]
Output: 2

Input:  nums = [3, 1, 3, 4, 2]
Output: 3

Input:  nums = [3, 3, 3, 3, 3]
Output: 3
```

### Pattern Recognition
Cycle detection on an array interpreted as a linked list. Treat index i as a node whose "next" pointer is `nums[i]`. Since values are in `[1, n]` and there are n+1 elements, by the pigeonhole principle at least one value repeats — creating a cycle in the implicit linked list. The duplicate value is the cycle entry node.

### Key Insight
Model the array as a function `f(i) = nums[i]`. Starting from index 0: `0 → nums[0] → nums[nums[0]] → ...`. The duplicate value means two different indices point to the same value — creating a node with two "predecessors" — which is exactly the cycle entry. Apply Floyd's two-phase algorithm on this implicit linked list.

### Approach
Phase 1: fast = `nums[nums[fast]]` (two function applications), slow = `nums[slow]` (one application). Detect meeting point. Phase 2: reset fast to `nums[0]` (start of the sequence, not index 0 of phase 2 — keep using `nums[]` as the "next" function), advance both one step at a time. First meeting = duplicate.

### Solution

```js
function findDuplicate(nums) {
  // Phase 1: find meeting point inside cycle
  let slow = nums[0];
  let fast = nums[0];

  do {
    slow = nums[slow];           // one step: follow one pointer
    fast = nums[nums[fast]];     // two steps: follow two pointers
  } while (slow !== fast);

  // Phase 2: find cycle entry = duplicate value
  fast = nums[0]; // reset to start of the implicit linked list
  while (slow !== fast) {
    slow = nums[slow];
    fast = nums[fast]; // both advance ONE step now
  }

  return slow; // cycle entry = the duplicate number
}
```

### Dry Run

```
nums = [1, 3, 4, 2, 2]
Implicit linked list: 0→1→3→2→4→2→4→... (cycle: 2↔4)

Index:  0  1  2  3  4
Value:  1  3  4  2  2

Following f(i)=nums[i]:
0→nums[0]=1→nums[1]=3→nums[3]=2→nums[2]=4→nums[4]=2→... cycle at 2

Phase 1 (start both from nums[0]=1):
slow=1, fast=1

Iter 1: slow=nums[1]=3, fast=nums[nums[1]]=nums[3]=2
Iter 2: slow=nums[3]=2, fast=nums[nums[2]]=nums[4]=2
slow(2) === fast(2) → break

Meeting point: 2

Phase 2: fast reset to nums[0]=1, slow stays at 2

Iter 1: slow=nums[2]=4, fast=nums[1]=3
Iter 2: slow=nums[4]=2, fast=nums[3]=2
slow(2) === fast(2) → return 2 ✓
```

### Complexity
- Time: O(n) — Floyd's algorithm on the implicit linked list of length n+1.
- Space: O(1) — two index variables, no extra array.

### Edge Cases
- All duplicates of one value (e.g., `[3,3,3,3,3]`): the "linked list" immediately cycles; fast and slow meet quickly. Phase 2 finds the cycle entry correctly.
- Duplicate appears exactly twice: standard case — exactly one cycle entry.
- n=1 (`nums=[1,1]`): slow=1, fast=1. Iter 1: slow=nums[1]=1, fast=nums[nums[1]]=nums[1]=1. Meet immediately. Phase 2: both at nums[0]=1 → same → return 1. Correct.

### Follow-up Questions
- "What if there could be multiple duplicates?" → Floyd's only finds one cycle entry. For multiple duplicates, this approach doesn't generalize — need sorting or a visited array.
- "Why can't we just use a Set?" → O(n) space — problem requires O(1) space. Set is correct but doesn't meet the constraint.
- "What if we can modify the array?" → Use the array itself as a visited marker (negate values at visited indices) — O(n) time, O(1) space, but destructive.

## Problem 5 — Palindrome Linked List

### Problem
Given the head of a singly linked list, return `true` if it is a palindrome, `false` otherwise. Solve in O(n) time and O(1) space.

```
Input:  1 → 2 → 2 → 1
Output: true

Input:  1 → 2 → 3 → 2 → 1
Output: true

Input:  1 → 2
Output: false
```

### Pattern Recognition
This problem combines three techniques: fast/slow pointer (find middle), in-place reversal (reverse second half), and two-pointer comparison (compare both halves). Recognizing fast/slow as a subcomponent — not the whole solution — is the key 5 YOE signal.

### Key Insight
A palindrome reads the same from both ends. Compare the first half forward with the second half backward. Reverse the second half in place (O(1) space) and compare with the first half using two pointers advancing simultaneously.

### Approach
1. **Find middle**: fast/slow pointer — slow stops at the middle (second middle for even lists).
2. **Reverse second half**: standard three-pointer list reversal starting from `slow` (or `slow.next` for odd lists to exclude the exact middle from the comparison).
3. **Compare**: two pointers — one from head, one from the reversed second half's head — advance together, compare values.
4. **Restore** (optional): reverse the second half again to restore the original list.

### Solution

```js
function isPalindrome(head) {
  if (!head || !head.next) return true; // 0 or 1 nodes

  // Step 1: find middle using fast/slow
  let slow = head, fast = head;
  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
  }
  // slow is now at the second middle (or exact middle for odd)

  // Step 2: reverse second half starting from slow
  let prev = null, curr = slow;
  while (curr !== null) {
    const next = curr.next;
    curr.next = prev;
    prev = curr;
    curr = next;
  }
  // prev is now the head of the reversed second half

  // Step 3: compare first half and reversed second half
  let left = head, right = prev;
  let isPalin = true;
  while (right !== null) { // right half is shorter or equal
    if (left.val !== right.val) {
      isPalin = false;
      break;
    }
    left = left.next;
    right = right.next;
  }

  // Step 4: restore (reverse the second half back) — optional
  // prev = reverse(prev) again — omitted here for brevity

  return isPalin;
}
```

### Dry Run

```
List: 1 → 2 → 2 → 1  (even length, n=4)

Step 1: Find middle
slow=1, fast=1
Iter 1: slow=2(idx1), fast=2(idx2)
Iter 2: slow=2(idx2), fast=null (fast: 2(idx2)→1→null)
slow is at node(2) at index 2 (second middle)

Step 2: Reverse from slow (index 2):
List fragment to reverse: 2(idx2) → 1 → null

prev=null, curr=2(idx2)
Iter 1: next=1, 2.next=null, prev=2(idx2), curr=1
Iter 2: next=null, 1.next=2(idx2), prev=1, curr=null
Reversed: 1 → 2(idx2) → null, prev = node(1) at index 3

Step 3: Compare
left=1(idx0), right=1(idx3)
Iter 1: 1===1 ✓, left=2(idx1), right=2(idx2)
Iter 2: 2===2 ✓, left=2(idx2), right=null
right=null → exit loop

return true ✓


List: 1 → 2 → 3 → 2 → 1  (odd length, n=5)

Step 1: Find middle
Iter 1: slow=2(idx1), fast=3(idx2)
Iter 2: slow=3(idx2), fast=1(idx4) — fast.next=null, exit
slow at node(3), the exact middle

Step 2: Reverse from slow (index 2):
Fragment: 3 → 2 → 1 → null → reversed: 1 → 2 → 3 → null

Step 3: Compare
left=1(idx0), right=1(reversed head, original idx4)
Iter 1: 1===1 ✓, left=2(idx1), right=2(original idx3)
Iter 2: 2===2 ✓, left=3(idx2), right=3(original idx2)
Iter 3: 3===3 ✓, left=2(idx3), right=null → exit

return true ✓
```

### Complexity
- Time: O(n) — find middle O(n/2), reverse O(n/2), compare O(n/2) → total O(n).
- Space: O(1) — three pointer variables for each phase.

### Edge Cases
- Single node: return true immediately (guard).
- Two nodes: slow ends at second node. Reversed second half = [second node]. Compare head.val with second node.val.
- All same values: all comparisons pass → true.
- List of length 2 where values differ (`1→2`): after middle, slow=node(2). Reverse: prev=node(2). Compare: left=1, right=2 → 1≠2 → false. Correct.

### Follow-up Questions
- "Restore the original list after checking?" → Reverse the second half again before returning.
- "O(n) space solution?" → Copy values into an array, use two-pointer check on the array. Simpler but uses O(n) space.
- "What if the list has a cycle?" → Must detect and handle the cycle first; otherwise the middle-finding step loops forever.

## Problem 6 — Reorder List (L0→Ln→L1→Ln-1→…)

### Problem
Given the head of a singly linked list, reorder it in-place so that it follows the pattern: L0 → Ln → L1 → Ln-1 → L2 → Ln-2 → ...

```
Input:  1 → 2 → 3 → 4
Output: 1 → 4 → 2 → 3

Input:  1 → 2 → 3 → 4 → 5
Output: 1 → 5 → 2 → 4 → 3
```

### Pattern Recognition
Three-step pipeline where fast/slow is the first step. Recognize that the final order is: first half forward, second half backward, interleaved. The steps are: find middle, reverse second half, merge two halves by interleaving.

### Key Insight
Split the list at the middle. Reverse the second half. Merge by alternating: take one from the first half, one from the reversed second half, repeat.

### Approach
1. **Find the first middle** using fast/slow with the `fast.next !== null && fast.next.next !== null` condition — so slow stops at the first middle for even lists (left half ≤ right half length).
2. **Sever**: `second = slow.next; slow.next = null` — disconnect the two halves.
3. **Reverse second half** in place.
4. **Merge**: interleave nodes from both halves.

### Solution

```js
function reorderList(head) {
  if (!head || !head.next) return;

  // Step 1: find FIRST middle (slow stops one earlier)
  let slow = head, fast = head;
  while (fast.next !== null && fast.next.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
  }

  // Step 2: sever list into two halves
  let second = slow.next;
  slow.next = null; // first half ends at slow

  // Step 3: reverse second half
  let prev = null, curr = second;
  while (curr !== null) {
    const next = curr.next;
    curr.next = prev;
    prev = curr;
    curr = next;
  }
  second = prev; // head of reversed second half

  // Step 4: merge two halves by interleaving
  let first = head;
  while (second !== null) {
    const firstNext = first.next;
    const secondNext = second.next;

    first.next = second;   // insert second node after first
    second.next = firstNext; // second node points to remainder of first half

    first = firstNext;     // advance in first half
    second = secondNext;   // advance in second half
  }
}
```

### Dry Run

```
List: 1 → 2 → 3 → 4 → 5

Step 1: Find first middle (condition: fast.next && fast.next.next)
slow=1, fast=1
Iter 1: slow=2, fast=3  (fast.next=4, fast.next.next=5 → continue)
Iter 2: slow=3, fast=5  (fast.next=null → STOP)
slow at node(3) — first middle ✓ (for odd list, this is the true middle)

Step 2: Sever
second = node(4), slow(3).next = null
First half:  1 → 2 → 3 → null
Second half: 4 → 5 → null

Step 3: Reverse second half
4 → 5 → null becomes 5 → 4 → null, second = node(5)

Step 4: Merge
first=1, second=5

Iter 1: firstNext=2, secondNext=4
  1.next=5, 5.next=2
  first=2, second=4
  List so far: 1→5→2→...

Iter 2: firstNext=3, secondNext=null
  2.next=4, 4.next=3
  first=3, second=null
  List so far: 1→5→2→4→3→null

second=null → exit

Result: 1 → 5 → 2 → 4 → 3 ✓
```

### Complexity
- Time: O(n) — three O(n) passes (find middle, reverse, merge).
- Space: O(1) — only pointer variables.

### Edge Cases
- Two nodes (`1→2`): first middle = node(1). Second half = `2`. Reversed second = `2`. Merge: 1→2. Correct (already in order).
- Three nodes (`1→2→3`): first middle = node(1) (since fast.next.next = null after first check). Wait — recheck: slow=1, fast=1. Condition: fast.next(2) ≠ null ✓, fast.next.next(3) ≠ null ✓ → enter loop. slow=2, fast=3. Condition: fast.next(null) → stop. Slow=2. Sever: second=3, 2.next=null. First half: 1→2, second half: 3. Reversed: 3. Merge: 1→3→2. Correct (1→3→2 = L0→L2→L1).
- Already in correct order: algorithm still runs all steps; result is correct regardless.

### Follow-up Questions
- "What if the list has a cycle?" → Must detect and remove cycle before reordering; otherwise find-middle loops forever.
- "Do this with O(n) space?" → Collect all values in an array, use two pointers from both ends to rebuild the list by overwriting node values. Simpler but uses O(n) space.

## Quick Reference — Fast/Slow Pointer Variants

```
Problem Type                     | Fast Step | Slow Step | Stopping Condition
---------------------------------+-----------+-----------+-----------------------------
Find middle (second middle)      | 2         | 1         | fast===null || fast.next===null
Find middle (first middle)       | 2         | 1         | fast.next===null || fast.next.next===null
Detect cycle                     | 2         | 1         | slow===fast (cycle) OR fast===null (no cycle)
Find cycle entry (phase 1)       | 2         | 1         | slow===fast
Find cycle entry (phase 2)       | 1         | 1         | slow===fast
Find k-th from end (setup)       | advance fast k steps first, then both move 1
Remove k-th from end             | advance fast k+1 steps first (or use dummy node + k steps)
Find duplicate (array as list)   | f(f(x))   | f(x)      | slow===fast, then reset
```

## Implementation Checklist

Before writing any fast/slow pointer code, answer these five questions:

1. **What is the null-safety condition?**
   Write the loop guard explicitly: `fast !== null && fast.next !== null` for "fast needs to take 2 steps." Skipping this causes null pointer errors on odd-length lists.

2. **Which middle do I need?**
   Second middle → `while (fast && fast.next)`. First middle → `while (fast.next && fast.next.next)`. State which you need before writing the loop.

3. **Is this cycle detection or position finding?**
   Cycle: check `slow === fast` inside the loop. Position: don't check for equality — just let fast/slow run to termination.

4. **Do I need a dummy node?**
   Deletion problems (remove k-th from end, remove cycle) → always use a dummy node before head. Avoids the "deleting the head" edge case without a special branch.

5. **Does the list get modified?**
   Reversal (palindrome, reorder) modifies the list. If the problem requires restoring the original structure, plan a second reversal before returning.

---

**Final Tip:** At the 5 YOE level, the fast/slow pointer pattern is expected to be automatic — you should recognize it and state the invariant ("when fast reaches null, slow is at the middle") before touching code. The signal questions are the ones that combine fast/slow with another technique: palindrome check (fast/slow + reversal + comparison), reorder list (fast/slow + reversal + merge), and find duplicate (array-as-linked-list + Floyd's two-phase). Interviewers use these composite problems to test whether you see fast/slow as a building block inside a larger solution, not just a standalone trick. Always verbalize the phase you're in — "I'm in phase 1 finding the meeting point" vs "now in phase 2 finding the cycle entry" — it shows structured thinking even when the code is similar between phases.
