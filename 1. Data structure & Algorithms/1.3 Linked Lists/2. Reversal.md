# DSA: Reversal — Iterative & Recursive Techniques — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What does "reversal" mean algorithmically, and what are the two broad implementation strategies?**
A: Reversal means producing (or transforming in-place) a sequence so that its elements appear in the opposite order. The two broad strategies are:
1. **Iterative**: use explicit pointers/indices and a loop to swap or re-link elements directly, using O(1) auxiliary space (beyond the input itself) in most cases.
2. **Recursive**: reduce the problem to "reverse everything after the first element, then place the first element at the end," relying on the **call stack** to implicitly hold state that would otherwise need explicit pointers — at the cost of O(n) space for the call stack.

The two strategies always compute the same *result* but differ in space complexity and code structure; interviewers often ask for both to gauge whether a candidate understands the space trade-off, not just whether they can produce a reversed output.

**Q2. What is the standard two-pointer array reversal, and why is it O(1) space?**
A: Two pointers start at opposite ends of the array and swap the elements they point to, moving toward the center until they meet or cross. Since the array is mutated in-place via swaps, no auxiliary array is needed — only two integer index variables.

```js
function reverseArray(arr) {
  let left = 0, right = arr.length - 1;

  while (left < right) {
    [arr[left], arr[right]] = [arr[right], arr[left]];
    left++;
    right--;
  }

  return arr;
}
```

Time: O(n). Space: O(1) extra — this is the baseline "iterative reversal" pattern that most other reversal problems either directly reuse or adapt.

**Q3. Why does the loop condition `left < right` (not `left <= right`) matter, and what happens on an odd-length array?**
A: `left < right` ensures the loop stops exactly when the pointers meet or cross — for an odd-length array, the middle element needs no swap (swapping it with itself is a harmless no-op, but the loop naturally skips it once `left === right`, since the condition becomes false). Using `left <= right` would still work correctly here (self-swap is harmless) but is unnecessary extra work; the distinction matters more in problems where the "self-swap" case isn't harmless (e.g., certain in-place partitioning logic), so it's good practice to reason about the boundary condition explicitly rather than relying on swaps happening to be idempotent.

**Q4. What is the general recursive reversal pattern, and how does it differ across data structures?**
A: The recursive shape is consistent: **base case** = an empty or single-element structure is trivially "already reversed"; **recursive case** = recursively reverse everything *except* the first element, then attach the first element at the correct (now-last) position. What differs across structures is *how* "attach at the end" is implemented — for an array, it might mean an index-based swap after the recursive call returns; for a linked list, it means re-pointing a `next` reference; for a stack, it means popping the first element, recursively reversing the rest, then inserting that popped element at the *bottom* of the now-reversed remainder (itself a nested recursive sub-problem — see Q9).

```js
// Generic shape (illustrated for an array, using index bounds instead of a new array)
function reverseRecursive(arr, left = 0, right = arr.length - 1) {
  if (left >= right) return arr; // base case: 0 or 1 elements remain to swap

  [arr[left], arr[right]] = [arr[right], arr[left]];
  return reverseRecursive(arr, left + 1, right - 1); // recurse toward the center
}
```

**Q5. What is the space complexity trade-off between iterative and recursive reversal, and why does it matter in practice?**
A: Iterative reversal is O(1) extra space (a fixed number of pointers/indices, regardless of input size). Recursive reversal is O(n) extra space due to the call stack — each recursive call adds a stack frame that isn't released until the base case is reached and the calls unwind. For large inputs, this can risk a **stack overflow** in languages/runtimes with limited call stack depth (a very real, practical concern — not just an academic complexity-notation distinction), which is why iterative solutions are generally preferred in production code for structures that could be very large, even though the recursive version is often more concise to write and reason about.

**Q6. When would you deliberately choose a recursive reversal approach despite the O(n) space cost?**
A: When the recursion **naturally models constraints the problem imposes** — most notably, "reverse a stack using only push/pop operations, no other data structure, and no explicit loop-based index manipulation." In that case, the call stack itself becomes the *only* available mechanism for holding intermediate state, making recursion not just a stylistic choice but the mechanism that satisfies the problem's constraints (see Q9, Q10). Recursive approaches are also sometimes preferred when they map unusually cleanly onto a problem's recursive structure (e.g., reversing a binary tree, where the tree itself is inherently a recursive structure) even when an iterative equivalent (e.g., using an explicit stack or queue) exists and would also be valid.

### Section 2: Recursive Reversal Mechanics

**Q7. How does recursive reversal of a singly linked list work, step by step, and why must `head.next = null` be set explicitly?**
A: Recurse to the tail of the list first (this becomes the new head once fully unwound). On the way back up the call stack, each node re-points its *next* node's `next` reference back at itself (`head.next.next = head`), reversing that one link. The original `head.next` must then be explicitly set to `null`, because it still holds the *old* forward-pointing reference — without clearing it, the original second node would point both forward (still, if unmodified) and backward (via the new reversed link), potentially creating a two-node cycle.

```js
function reverseListRecursive(head) {
  if (head === null || head.next === null) return head; // base case

  const newHead = reverseListRecursive(head.next); // recurse to the tail first
  head.next.next = head; // reverse this link: next node now points back at head
  head.next = null;      // clear the old forward pointer to avoid a cycle

  return newHead; // propagated up unchanged from the base case
}
```

**Q8. Why does `newHead` stay the same value throughout every level of the recursive unwind?**
A: `newHead` is set exactly once, at the base case (when the original tail is reached — the node with `next === null`, which becomes the new head of the reversed list). Every subsequent stack frame, as it unwinds, receives that same `newHead` value from its recursive call and simply passes it back up unchanged (`return newHead`), performing its own local pointer-fixing work (`head.next.next = head; head.next = null`) without altering what gets returned. This is a common pattern in recursive solutions: the "answer" is determined at the base case and threaded back up through every frame untouched, while each frame does its own side-effect work independently.

**Q9. How do you reverse a stack using ONLY push and pop operations (no auxiliary array, no explicit second stack, no index-based loop)?**
A: This requires **two mutually-recursive helper operations**: one to reverse the stack itself, and another to insert an element at the very *bottom* of a stack (since stacks natively only support inserting/removing at the top). The reversal recursively pops every element off (down to an empty stack as the base case), then, as the recursion unwinds, inserts each popped element at the bottom of the (already fully reversed, by the recursive call) remaining stack.

```js
function insertAtBottom(stack, item) {
  if (stack.length === 0) {
    stack.push(item);
    return;
  }
  const top = stack.pop();
  insertAtBottom(stack, item); // recurse until the stack is empty, then insert
  stack.push(top);             // restore the popped elements, now above the inserted item
}

function reverseStack(stack) {
  if (stack.length === 0) return; // base case: empty stack is trivially "reversed"

  const top = stack.pop();
  reverseStack(stack);          // recursively reverse everything below the original top
  insertAtBottom(stack, top);   // place the original top at the very bottom
}
```

**Q10. Why does `reverseStack` need `insertAtBottom` as a separate recursive helper, rather than just pushing the popped element back directly?**
A: A plain `stack.push(top)` would place `top` back at the **current top** of the stack — but after the recursive `reverseStack(stack)` call has already reversed everything below it, the original top element needs to end up at the **bottom**, not the top, of the final reversed stack (since it was the first element pushed, conceptually, or rather it needs to become the *last* accessible element after reversal — tracing through a small example clarifies this is the position it belongs at). `insertAtBottom` is itself a recursive procedure because a stack's only native operations are push/pop at the top — "inserting at the bottom" isn't a native stack operation and must be built by recursively popping everything off, inserting at the (now-reached) true bottom, then restoring everything that was popped, in the correct order, via the unwind.

**Q11. What is the combined time complexity of the recursive stack-reversal approach, and why is it worse than the array/linked-list two-pointer reversal?**
A: Reversing a stack of `n` elements this way is **O(n²)** — `reverseStack` makes `n` top-level recursive calls, and each one triggers an `insertAtBottom` call that itself does up to O(n) work (popping down to the bottom and restoring). This is asymptotically worse than the O(n) two-pointer reversal used for arrays and linked lists, but it's the necessary cost of respecting the stack's very restrictive operation set (only push/pop, no direct indexed access) — a good example of how a data structure's *interface constraints*, not just its underlying storage, can dictate an algorithm's achievable complexity.

### Section 3: Advanced Reversal Patterns

**Q12. What is "reverse nodes in k-group" for a linked list, and how does it combine both iterative and recursive ideas?**
A: Given a linked list, reverse the nodes in groups of `k` at a time (if the final group has fewer than `k` nodes, it's typically left as-is, per the standard problem statement). The core sub-routine is the standard iterative linked-list reversal (Q7's non-recursive counterpart from the earlier linked-list guide), but bounded to exactly `k` nodes at a time; this is then either looped iteratively across the whole list, or applied recursively (reverse the first `k` nodes, recursively process the rest of the list, then connect the reversed group's tail to whatever the recursive call returns).

```js
function reverseKGroup(head, k) {
  // check there are at least k nodes remaining before reversing this group
  let node = head, count = 0;
  while (node !== null && count < k) {
    node = node.next;
    count++;
  }
  if (count < k) return head; // fewer than k nodes left — leave this group unreversed

  // reverse exactly k nodes (standard iterative reversal, bounded)
  let prev = null, curr = head;
  for (let i = 0; i < k; i++) {
    const next = curr.next;
    curr.next = prev;
    prev = curr;
    curr = next;
  }

  // head is now the TAIL of this reversed group; connect it to the recursively-processed rest
  head.next = reverseKGroup(curr, k);

  return prev; // prev is the new head of this reversed group
}
```

**Q13. What is "reverse words in a string," and how does it typically combine multiple layers of reversal?**
A: Given a sentence, reverse the *order of the words* while keeping each word's internal character order intact (e.g., `"the sky is blue"` → `"blue is sky the"`). A common two-step technique: (1) reverse the *entire* character sequence of the string first, which flips both word order and each word's internal characters; (2) then reverse the characters *within* each individual word again, which restores correct internal word spelling while leaving the (now-correct) word order intact.

```js
function reverseWords(s) {
  const chars = s.trim().split(/\s+/).join(' ').split(''); // normalize whitespace
  reverseRange(chars, 0, chars.length - 1); // step 1: reverse everything

  // step 2: reverse each word back to correct internal order
  let start = 0;
  for (let i = 0; i <= chars.length; i++) {
    if (i === chars.length || chars[i] === ' ') {
      reverseRange(chars, start, i - 1);
      start = i + 1;
    }
  }

  return chars.join('');
}

function reverseRange(chars, left, right) {
  while (left < right) {
    [chars[left], chars[right]] = [chars[right], chars[left]];
    left++;
    right--;
  }
}
```

**Q14. How do you reverse the digits of an integer, and what overflow consideration is unique to this variant of reversal?**
A: Repeatedly extract the last digit via modulo (`num % 10`) and build up the reversed number (`reversed = reversed * 10 + digit`), while removing that digit from the original number via integer division (`num = Math.trunc(num / 10)`). The overflow consideration: reversing a number near the boundary of a fixed-width integer type (e.g., 32-bit signed integer range) can produce a reversed value that **exceeds that range**, even though the original number was valid — this must be explicitly checked and handled (typically by returning 0 or signaling an error) rather than silently overflowing.

```js
function reverseInteger(num) {
  const INT_MAX = 2147483647, INT_MIN = -2147483648;
  let sign = num < 0 ? -1 : 1;
  num = Math.abs(num);
  let reversed = 0;

  while (num !== 0) {
    const digit = num % 10;
    reversed = reversed * 10 + digit;
    num = Math.trunc(num / 10);

    if (reversed > INT_MAX) return 0; // overflow guard, checked every iteration
  }

  return sign * reversed;
}
```

**Q15. How does reversing a binary tree ("invert a binary tree") relate to the general reversal pattern, and is it more naturally iterative or recursive?**
A: "Inverting" a binary tree means swapping every node's left and right children, recursively, at every level — this is a **mirror reversal**, not a linear-sequence reversal, but it shares the same recursive shape: base case (null node, nothing to invert), recursive case (invert the left subtree, invert the right subtree, then swap them at the current node). Because a binary tree is inherently a recursive data structure (each subtree is itself a tree), the recursive formulation is usually the more natural fit, though an iterative version using an explicit stack or queue (BFS/DFS with manual swapping) is equally valid and avoids the call-stack depth concern for very unbalanced/deep trees.

```js
function invertTree(root) {
  if (root === null) return null;

  const left = invertTree(root.left);
  const right = invertTree(root.right);
  root.left = right;
  root.right = left;

  return root;
}
```

### Section 4: Scenario / Interview-Style Questions

**Q16. "You're asked to reverse a very large array (millions of elements) in a memory-constrained environment. Would you use the iterative or recursive approach, and why?"**
A: Iterative, unambiguously — the two-pointer swap approach is O(1) extra space, while a recursive approach would consume O(n) call-stack space for millions of elements, very likely triggering a stack overflow well before completion in most language runtimes (which typically have call stack depth limits far smaller than millions of frames). This is a case where the recursive version, despite being a valid and arguably elegant expression of the "reverse the rest, then place the first element" idea, is simply impractical at this scale.

**Q17. "A teammate reverses a singly linked list recursively and says it's 'cleaner' than the iterative version. How do you respond in a code review, and is there a scenario where you'd agree with them?"**
A: I'd acknowledge the recursive version is arguably more concise and mirrors the linked list's inherently recursive structure nicely, but I'd flag the O(n) space cost (call stack) versus the iterative version's O(1) space as a real trade-off, not just a stylistic preference — especially if this code might run on very long lists or in a constrained-stack environment (some embedded/server contexts have quite limited default stack sizes). I'd agree the recursive version is a reasonable choice if the lists involved are known to be small/bounded and code clarity is prioritized, but for a general-purpose utility function, I'd lean toward recommending the iterative version as the safer default.

**Q18. "You need to reverse a stack but are told you cannot use any other data structure (no array, no second stack) — only the stack's own push/pop, plus recursion. Walk through your approach and its complexity."**
A: This is the classic "reverse a stack using recursion only" problem. I'd explain the two-part recursive approach: `reverseStack` recursively pops down to empty (base case), then as it unwinds, calls a second recursive helper `insertAtBottom` to place each popped element at the true bottom of the (already-reversed) remaining stack — since a stack can only natively push/pop at the top, "insert at bottom" itself has to be built recursively by popping everything off, inserting, then restoring in order. I'd note upfront that this achieves the required *behavior* (respecting the operation constraints) but at O(n²) time, a real cost of not being allowed direct indexed access or a second explicit structure.

**Q19. "How would you reverse only a sub-portion of a linked list (say, nodes 3 through 7), leaving the rest of the list untouched, and does this change the iterative-vs-recursive trade-off discussion?"**
A: The core reversal logic (three-pointer prev/curr/next) is unchanged, but now bounded to just the target sub-range — you first traverse to the node just before the sub-range's start (to later re-attach the reversed segment correctly), perform the standard reversal within just that bounded range, then re-splice: connect the pre-range node to the (former) end of the sub-range (now its new head after reversal), and connect the (former) start of the sub-range (now its new tail) to whatever came after the original sub-range. The iterative-vs-recursive trade-off is the same as full-list reversal — an iterative bounded reversal is O(1) space; a recursive version would still cost O(k) stack space for a sub-range of length k, smaller than a full-list recursive reversal's O(n) but still worth noting if k could be large.

**Q20. "Reverse words in a string in-place, given a mutable character array, without allocating a new string — how does this build on simpler array reversal?"**
A: It's a direct composition of two applications of the basic two-pointer array-reversal routine: reverse the entire character array once (flips word order and scrambles each word's internal letters), then make a second pass reversing each individual word's character range back to correct internal order (using word-boundary detection via space characters to know where each "reverse this sub-range" call should start and stop). This demonstrates how the simplest O(1)-space two-pointer reversal primitive can be reused as a building block for a more complex transformation, rather than needing a fundamentally different technique.

## Problem 1 — Reverse an Array In-Place (Iterative and Recursive)

### Problem
Given an array, reverse it in-place. Implement both an iterative and a recursive solution.

```
Input:  [1, 2, 3, 4, 5]
Output: [5, 4, 3, 2, 1]
```

### Pattern Recognition
The foundational two-pointer reversal pattern — every other reversal problem in this guide either directly reuses this or adapts its core idea.

### Key Insight
Swapping elements from both ends toward the center, using two converging pointers, reverses the array in exactly `n/2` swaps — no auxiliary storage needed for the iterative version; the recursive version replaces the explicit loop with self-calls that shrink the `[left, right]` bounds each time.

### Approach
**Iterative**: two pointers start at both ends, swap-and-converge until they meet or cross. **Recursive**: same swap logic, but expressed as a base case (`left >= right`) plus a recursive call with narrowed bounds instead of a loop.

### Solution

```js
// Iterative
function reverseArrayIterative(arr) {
  let left = 0, right = arr.length - 1;

  while (left < right) {
    [arr[left], arr[right]] = [arr[right], arr[left]];
    left++;
    right--;
  }

  return arr;
}

// Recursive
function reverseArrayRecursive(arr, left = 0, right = arr.length - 1) {
  if (left >= right) return arr;

  [arr[left], arr[right]] = [arr[right], arr[left]];
  return reverseArrayRecursive(arr, left + 1, right - 1);
}
```

### Dry Run

```
arr = [1, 2, 3, 4, 5]

Iterative:
left=0,right=4: swap → [5,2,3,4,1], left=1,right=3
left=1,right=3: swap → [5,4,3,2,1], left=2,right=2
left(2) < right(2)? no → loop ends

Result: [5,4,3,2,1] ✓

Recursive (same swaps, via call stack instead of a loop):
call(left=0,right=4): swap → [5,2,3,4,1] → call(left=1,right=3)
call(left=1,right=3): swap → [5,4,3,2,1] → call(left=2,right=2)
call(left=2,right=2): left>=right → base case, return arr

Result: [5,4,3,2,1] ✓
```

### Complexity
- Iterative: Time O(n), Space O(1) extra.
- Recursive: Time O(n), Space O(n) — call stack depth is roughly n/2.

### Edge Cases
- Empty array: `left=0, right=-1` → `left >= right` (or `left < right` false) immediately, no-op, correctly returns the empty array unchanged.
- Single element: `left === right` from the start, no swap needed, correctly returns unchanged.
- Even vs. odd length: both handled uniformly by the `left < right` (or `left >= right`) condition — no special-casing needed for the middle element in odd-length arrays, since it's simply never included in a swap pair.

### Follow-up Questions
- "What if you can't mutate the input array?" → Build a new array instead (`arr.slice().reverse()` conceptually, or construct one manually), which costs O(n) space regardless of iterative/recursive choice.
- "Reverse only a sub-range of the array?" → Same technique, just pass in the desired `left`/`right` bounds instead of defaulting to the full array — the function signature shown already supports this directly.

## Problem 2 — Reverse a Singly Linked List (Recursive)

### Problem
Given the head of a singly linked list, reverse it recursively and return the new head.

```
Input:  1 → 2 → 3 → 4 → 5 → null
Output: 5 → 4 → 3 → 2 → 1 → null
```

### Pattern Recognition
Recursive linked-list reversal — recurse to the tail first, then fix pointers on the way back up the call stack.

### Key Insight
The new head of the reversed list is exactly the original *tail* — the node reached at the base case. Every stack frame above the base case is responsible only for reversing its own single link (`head.next.next = head`) and severing its old forward link (`head.next = null`), while passing the already-determined `newHead` back up unchanged.

### Approach
Base case: empty list or single node — already "reversed," return as-is. Recursive case: recurse on `head.next` first, then re-point that returned sub-list's tail-side link back at `head`, clear `head.next`, and return the unchanged `newHead` from the base case.

### Solution

```js
function reverseListRecursive(head) {
  if (head === null || head.next === null) return head;

  const newHead = reverseListRecursive(head.next);
  head.next.next = head;
  head.next = null;

  return newHead;
}
```

### Dry Run

```
List: 1 → 2 → 3 → null

call(head=1): head.next(2)!==null → recurse on head=2
  call(head=2): head.next(3)!==null → recurse on head=3
    call(head=3): head.next===null → BASE CASE, return 3 (newHead=3)
  back in call(head=2): newHead=3
    head.next.next = head → 3.next = 2
    head.next = null → 2.next = null
    return newHead=3
back in call(head=1): newHead=3
  head.next.next = head → 2.next = 1
  head.next = null → 1.next = null
  return newHead=3

Final structure (tracing the links set):
3.next = 2 (set in the head=2 frame)
2.next = 1 (set in the head=1 frame)
1.next = null (set in the head=1 frame)

Result: 3 → 2 → 1 → null ✓
```

### Complexity
- Time: O(n) — each node visited once during the recursive descent and once during the unwind (still linear, not quadratic).
- Space: O(n) — call stack depth equals the list length.

### Edge Cases
- Empty list (`head === null`): base case triggers immediately, returns `null`.
- Single node: base case triggers (`head.next === null`), returns that same node unchanged — correctly already "reversed."
- Very long list: risk of stack overflow due to O(n) call stack depth — worth proactively mentioning as the key trade-off versus the iterative version from the dedicated linked-list guide.

### Follow-up Questions
- "Convert this to an iterative solution and compare space complexity." → See the iterative three-pointer version (prev/curr/next) from the linked-list guide — O(1) space instead of O(n).
- "Reverse only the first k nodes recursively?" → Add a counter parameter, decrementing at each recursive call, and stop recursing (treat as a base case) once k nodes have been processed — see Problem 4's k-group reversal for a fuller treatment of this idea.

## Problem 3 — Reverse a Stack Using Only Recursion (No Loops, No Extra Data Structure)

### Problem
Given a stack (supporting only `push` and `pop`), reverse its contents using recursion only — no explicit loops, no second stack or array.

```
Input stack (top to bottom): [3, 2, 1]
Output stack (top to bottom): [1, 2, 3]
```

### Pattern Recognition
Two mutually-supporting recursive procedures: one to reverse the whole stack, and one to insert an element at the stack's bottom (since stacks don't natively support that operation).

### Key Insight
"Insert at the bottom" must itself be recursive, since a stack only supports top-based push/pop — recursively popping everything off reaches the true bottom, where the new item is pushed first, and then everything popped is pushed back in the same order, restoring the stack above the newly-inserted bottom item.

### Approach
`reverseStack`: pop the top element, recursively reverse the remaining stack, then insert the originally-popped element at the very bottom of that now-reversed remainder. `insertAtBottom`: recursively pop down to an empty stack, push the new item there, then push back everything that was popped, in the same order they were removed.

### Solution

```js
function insertAtBottom(stack, item) {
  if (stack.length === 0) {
    stack.push(item);
    return;
  }

  const top = stack.pop();
  insertAtBottom(stack, item);
  stack.push(top);
}

function reverseStack(stack) {
  if (stack.length === 0) return;

  const top = stack.pop();
  reverseStack(stack);
  insertAtBottom(stack, top);
}
```

### Dry Run

```
stack = [1, 2, 3]  (JS array used as a stack; index 2 = "3" is the top)

reverseStack([1,2,3]):
  top = pop() = 3 → stack=[1,2]
  reverseStack([1,2]):
    top = pop() = 2 → stack=[1]
    reverseStack([1]):
      top = pop() = 1 → stack=[]
      reverseStack([]): length===0 → return (base case)
      insertAtBottom([], 1):
        stack empty → push(1) → stack=[1]
    insertAtBottom([1], 2):
      top=pop()=1 → stack=[]
      insertAtBottom([], 2): stack empty → push(2) → stack=[2]
      push(top=1) → stack=[2,1]
  insertAtBottom([2,1], 3):
    top=pop()=1 → stack=[2]
    insertAtBottom([2], 3):
      top=pop()=2 → stack=[]
      insertAtBottom([], 3): stack empty → push(3) → stack=[3]
      push(top=2) → stack=[3,2]
    push(top=1) → stack=[3,2,1]

Final stack: [3,2,1]  (bottom to top: 3,2,1 — top of stack is now 1)
Original stack (bottom to top) was [1,2,3] with top=3.
Reversed stack (bottom to top) is [3,2,1] with top=1 ✓
(the element that was on top (3) is now on the bottom, and vice versa)
```

### Complexity
- Time: O(n²) — n calls to `reverseStack`, each triggering an `insertAtBottom` call that does up to O(n) work.
- Space: O(n) — recursive call stack depth (both procedures combined, though not simultaneously nested beyond O(n) total at any point).

### Edge Cases
- Empty stack: `reverseStack` immediately hits its base case, no-op — correctly "reverses" an empty stack into itself.
- Single-element stack: `reverseStack` pops the one element, recursively reverses the (now empty) remainder (no-op), then `insertAtBottom` pushes it right back — correctly unchanged, as expected for a single-element reversal.
- Stack with duplicate values: the algorithm operates purely on position, not value uniqueness, so duplicates are handled with no special logic needed.

### Follow-up Questions
- "Why is this O(n²) instead of O(n)?" → Because the stack's interface (only top-based push/pop) doesn't allow direct indexed access the way an array does — "insert at the bottom" fundamentally requires visiting every other element to get there and restore them, unlike an array where any index is directly reachable.
- "If you were allowed one additional stack or array, how would this change?" → Trivial O(n) solution: pop every element from the original stack, push each into a new stack (or array used as a stack) — the act of popping-then-pushing into a new structure naturally reverses order in a single O(n) pass, since a stack's LIFO order applied twice reverses back to original... actually pushing pop order into a new stack correctly reverses once. This highlights how much the "no extra structure" constraint specifically drives the O(n²) cost.

## Problem 4 — Reverse Nodes in k-Group

### Problem
Given the head of a linked list, reverse the nodes of the list `k` at a time, and return the modified list. If the number of nodes remaining is not a multiple of `k`, leave the final group of nodes as-is (unreversed).

```
Input:  1 → 2 → 3 → 4 → 5, k = 2
Output: 2 → 1 → 4 → 3 → 5

Input:  1 → 2 → 3 → 4 → 5, k = 3
Output: 3 → 2 → 1 → 4 → 5
```

### Pattern Recognition
Bounded iterative reversal (exactly `k` nodes at a time), applied recursively across successive groups of the list — combining the standard three-pointer reversal technique with a recursive "process the rest of the list" structure.

### Key Insight
Before reversing a group, you must first verify at least `k` nodes remain — otherwise that final partial group must be left untouched, per the problem's requirement. After reversing exactly `k` nodes, the *original* head of that group becomes its *tail*, and must be connected to whatever the recursive call returns for the rest of the list (which itself is either another reversed group or an untouched partial group).

### Approach
First, walk forward `k` nodes to check enough nodes remain; if not, return `head` unchanged. Otherwise, perform a standard bounded iterative reversal of exactly `k` nodes. Then recursively call the same function on the remainder of the list (starting from where the bounded reversal left off), and connect the original group's head (now its tail) to that recursive result.

### Solution

```js
function reverseKGroup(head, k) {
  let node = head, count = 0;
  while (node !== null && count < k) {
    node = node.next;
    count++;
  }
  if (count < k) return head; // fewer than k nodes remain — leave unreversed

  let prev = null, curr = head;
  for (let i = 0; i < k; i++) {
    const next = curr.next;
    curr.next = prev;
    prev = curr;
    curr = next;
  }

  head.next = reverseKGroup(curr, k); // head is now this group's tail

  return prev; // prev is this group's new head
}
```

### Dry Run

```
List: 1 → 2 → 3 → 4 → 5, k=2

Top-level call, head=1:
  check: walk 2 nodes from 1 → reach node 3, count=2 → count>=k(2), proceed

  bounded reversal of nodes 1,2:
    prev=null, curr=1
    i=0: next=2, curr.next=prev(null) → 1.next=null, prev=1, curr=2
    i=1: next=3, curr.next=prev(1) → 2.next=1, prev=2, curr=3
    (loop ends, k=2 iterations done)
    prev=2 (new head of this group), curr=3 (start of remainder)

  head(1).next = reverseKGroup(3, 2)  ← recursive call on remainder starting at node 3

  [Recursive call, head=3]:
    check: walk 2 nodes from 3 → reach node 5, count=2 → proceed
    bounded reversal of nodes 3,4:
      prev=null,curr=3
      i=0: next=4, 3.next=null, prev=3, curr=4
      i=1: next=5, 4.next=3, prev=4, curr=5
      prev=4 (new head), curr=5 (remainder)
    head(3).next = reverseKGroup(5, 2)

    [Recursive call, head=5]:
      check: walk from 5 → only 1 node available (5→null), count=1 < k(2)
      return head=5 unchanged (leave final partial group as-is)

    back in head=3 frame: 3.next = 5 (the returned unchanged remainder)
    return prev=4 (new head of the 3,4 group)

  back in head=1 frame: 1.next = 4 (the returned head of the next reversed group)
  return prev=2 (new head of the 1,2 group)

Final list, tracing from the top-level return (2):
2 → 1 (from 1.next=null earlier, wait let's retrace: 1.next was set to 4 in the top frame)
2 → 1 → 4 → 3 → 5

Result: 2 → 1 → 4 → 3 → 5 ✓
```

### Complexity
- Time: O(n) — every node is visited a constant number of times across the counting check, the bounded reversal, and the recursive descent.
- Space: O(n/k) — recursive call stack depth is proportional to the number of groups, not the total node count.

### Edge Cases
- `k = 1`: every "group" is a single node; reversing a single-node group is a no-op, so the list is returned unchanged.
- `k` equals the total list length: the entire list is reversed as one group, with the recursive call on the (now-empty) remainder immediately hitting `head === null` implicitly via the count check.
- List length not a multiple of `k`: the final partial group correctly triggers the `count < k` early return, leaving it unreversed, exactly as required.
- Empty list: `node` starts `null`, the counting loop doesn't execute, `count` stays 0, which is `< k` (assuming `k >= 1`), so `head` (`null`) is returned unchanged.

### Follow-up Questions
- "Can you do this iteratively instead of recursively, to avoid the O(n/k) stack space?" → Yes — maintain an explicit "previous group's tail" pointer that gets re-linked to each new group's head as you iterate through the list group by group, replacing the recursive call with a loop; more code but O(1) extra space.
- "What if partial final groups should also be reversed (a common variant)?" → Remove the "leave as-is" early return and simply reverse whatever nodes remain, even if fewer than k — a small but meaningful change to the base-case behavior.

## Quick Reference — Pattern Decision Tree

```
Does the problem require reversing a sequence, structure, or its sub-portions?
│
├── SIMPLE LINEAR SEQUENCE (array, string characters)?
│   ├── O(1) space required / large input → Iterative two-pointer swap
│   └── Recursion explicitly requested / small input → Recursive two-pointer swap (same logic, O(n) stack space)
│
├── SINGLY LINKED LIST (full reversal)?
│   ├── O(1) space required / large list → Iterative 3-pointer (prev/curr/next)
│   └── Elegance/structure-matching preferred, list is bounded in size → Recursive (recurse to tail, fix links on unwind)
│
├── SINGLY LINKED LIST, REVERSE IN BOUNDED GROUPS OF k?
│   └── Bounded iterative reversal (exactly k nodes) + recursive (or iterative) processing of the remainder
│
├── STACK, USING ONLY PUSH/POP + RECURSION (no other structure)?
│   └── Two mutually-recursive procedures: reverseStack + insertAtBottom → O(n²) time, O(n) space
│       (if an extra structure IS allowed, trivial O(n) pop-into-new-stack instead)
│
├── WORDS WITHIN A STRING (reverse word order, preserve internal word spelling)?
│   └── Two-layer reversal: reverse the whole string once, then reverse each word's characters back
│
├── DIGITS OF AN INTEGER?
│   └── Modulo/divide extraction loop, building the reversed number digit by digit — watch for overflow
│
├── BINARY TREE (mirror every subtree)?
│   └── Recursive swap of left/right children at every node (naturally recursive structure)
│       — iterative BFS/DFS with an explicit stack/queue is an equally valid alternative
│
└── SUB-RANGE OF A LARGER STRUCTURE (not the whole thing)?
    └── Same core technique (two-pointer or 3-pointer) bounded to the target range,
        with careful re-splicing to reconnect to the untouched surrounding structure
```

## Common Bugs Checklist

Before submitting any reversal solution, verify:

1. **Iterative array/string reversal: loop condition is `left < right`, not `<=` or unconditional?** — Using the wrong condition can cause an unnecessary extra no-op swap (harmless but sloppy) or, in adapted versions of this pattern, a genuine off-by-one bug.

2. **Recursive linked-list reversal: `head.next = null` set AFTER `head.next.next = head`?** — Setting `head.next = null` first destroys the reference needed to reach `head.next.next` in the first place — order matters here.

3. **Recursive linked-list reversal: `newHead` returned unchanged through every stack frame?** — Only the base case should determine `newHead`'s value; every other frame just does local pointer fixes and passes it through — accidentally reassigning it partway up silently breaks the returned head reference.

4. **Stack reversal: `insertAtBottom` correctly restores popped elements in the right order on unwind?** — The `stack.push(top)` after the recursive call must happen for every popped element, in the reverse order they were popped, to correctly rebuild the stack above the newly-inserted bottom item — skipping this (or reordering it) silently loses or misorders elements.

5. **k-group reversal: count-check performed BEFORE attempting the bounded reversal?** — Reversing first and checking node count after risks partially reversing a group with fewer than k nodes, which then needs to be un-reversed or handled awkwardly — checking first avoids this entirely.

6. **k-group reversal: original group head correctly connected to the recursive call's result, not left dangling?** — After the bounded reversal, the original head (now the group's tail) must have its `.next` explicitly set to `reverseKGroup(curr, k)` — forgetting this disconnects the group from the rest of the list.

7. **Reverse words in a string: whitespace normalized before/after reversal (multiple spaces, leading/trailing spaces)?** — Naively reversing without first collapsing multiple spaces or trimming can produce a result with extra spaces in the wrong places or preserved leading/trailing whitespace that shouldn't be there.

8. **Reverse integer: overflow checked at every iteration, not just at the end?** — Building up `reversed` digit by digit can overflow *during* construction, before the loop even finishes — checking only after the full loop completes may already have triggered undefined/incorrect behavior in a fixed-width integer context (less of a concern in JS's native numbers, but critical to mention for typed-language equivalents, and good practice regardless).

---

**Final Tip:** At the 5 YOE level, interviewers expect you to treat "reversal" not as a single memorized algorithm but as a **space/constraint trade-off decision**: two-pointer iterative swapping is the default, cheapest baseline; recursion is reached for specifically when either the structure is naturally recursive (trees), the problem's constraints force it (stack-only operations), or code clarity is prioritized over the O(n) stack-space cost for a bounded-size input. Being able to state, before writing any code, "I'll do this iteratively for O(1) space, unless the constraints require recursion, in which case here's the space cost that introduces" is a stronger signal than defaulting to whichever approach comes to mind first.
