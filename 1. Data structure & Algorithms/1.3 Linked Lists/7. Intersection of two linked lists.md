# DSA: Intersection of Two Linked Lists — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What does it mean for two linked lists to "intersect," and how is this different from two lists simply having a matching value somewhere?**
A: Two singly linked lists intersect if they share one or more **actual node objects** (by reference) — not merely nodes with equal values. Once two lists reach a shared node, every node from that point onward is identical (the same chain of references), because a singly linked list node has exactly one `next` pointer, so two different paths cannot diverge again after converging. This means the lists typically look like a "Y" shape: two separate chains merging into one shared tail.

```
List A: a1 → a2 → c1 → c2 → c3 → null
List B:      b1 → c1 → c2 → c3 → null
                   ↑
            intersection starts here (c1)
```

**Q2. Why can't you check for intersection by simply comparing node *values* as you traverse both lists?**
A: Two lists could coincidentally contain nodes with equal values without those nodes being the *same object* in memory — e.g., `List A` might have a node with value `5` at some position, and `List B` might independently have an unrelated node that also happens to hold value `5`, without the lists ever actually sharing structure. Correct intersection detection must compare **node identity/reference** (e.g., `nodeA === nodeB` in JavaScript, or pointer/reference equality in other languages), not `nodeA.val === nodeB.val`.

**Q3. What is the brute-force approach to finding the intersection node, and what is its complexity?**
A: For every node in `List A`, scan through the entirety of `List B` checking for a matching node reference; the first match found (scanning `List A` from its head) is the intersection point. This is O(n × m) time (n = length of A, m = length of B) and O(1) space — correct, but inefficient, and it's the natural starting point before optimizing.

```js
function getIntersectionBruteForce(headA, headB) {
  let nodeA = headA;
  while (nodeA !== null) {
    let nodeB = headB;
    while (nodeB !== null) {
      if (nodeA === nodeB) return nodeA;
      nodeB = nodeB.next;
    }
    nodeA = nodeA.next;
  }
  return null;
}
```

**Q4. What is the hash-set approach to finding the intersection, and what is its complexity trade-off?**
A: Traverse `List A` once, storing every node reference in a `Set`. Then traverse `List B`, checking at each node whether it already exists in the `Set` — the first hit is the intersection point. This reduces time to O(n + m) at the cost of O(n) extra space for the set.

```js
function getIntersectionHashSet(headA, headB) {
  const visited = new Set();

  let nodeA = headA;
  while (nodeA !== null) {
    visited.add(nodeA);
    nodeA = nodeA.next;
  }

  let nodeB = headB;
  while (nodeB !== null) {
    if (visited.has(nodeB)) return nodeB;
    nodeB = nodeB.next;
  }

  return null;
}
```

### Section 2: O(1) Space Techniques

**Q5. What is the "align by length difference" approach to finding the intersection in O(1) extra space?**
A: Compute the lengths of both lists first. Advance the pointer of the *longer* list by the difference in lengths (`|lenA - lenB|` steps), so both pointers are now the same distance from the end of their respective lists. Then advance both pointers together, one step at a time — since they're equidistant from the end, and the tails are identical from the intersection point onward (per Q1), the pointers will land on the same node (the intersection) at the same time, or both reach `null` simultaneously if there's no intersection.

```js
function getIntersectionLengthDiff(headA, headB) {
  const lengthOf = (head) => {
    let len = 0, node = head;
    while (node !== null) { len++; node = node.next; }
    return len;
  };

  let lenA = lengthOf(headA), lenB = lengthOf(headB);
  let nodeA = headA, nodeB = headB;

  while (lenA > lenB) { nodeA = nodeA.next; lenA--; }
  while (lenB > lenA) { nodeB = nodeB.next; lenB--; }

  while (nodeA !== nodeB) {
    nodeA = nodeA.next;
    nodeB = nodeB.next;
  }

  return nodeA; // either the intersection node, or null if both reach the end together
}
```

Time: O(n + m) — two passes to compute lengths, plus one more combined pass to find the intersection. Space: O(1) — only a handful of integer/pointer variables.

**Q6. What is the elegant "two-pointer list-switching" technique, and why does it avoid needing to compute lengths upfront?**
A: Run two pointers, one starting at each list's head, both advancing one step at a time. When a pointer reaches the end of its own list (`null`), redirect it to start over at the **other** list's head instead of simply stopping. Because both pointers then collectively traverse `lenA + lenB` total nodes (just in different order — pointer 1 does `A then B`, pointer 2 does `B then A`), if the lists intersect, both pointers arrive at the intersection node **simultaneously** after having each traveled the same total distance; if they don't intersect, both pointers reach `null` simultaneously after traversing `lenA + lenB` steps each.

```js
function getIntersection(headA, headB) {
  if (headA === null || headB === null) return null;

  let pointerA = headA, pointerB = headB;

  while (pointerA !== pointerB) {
    pointerA = pointerA === null ? headB : pointerA.next;
    pointerB = pointerB === null ? headA : pointerB.next;
  }

  return pointerA; // intersection node, or null if both hit the end together
}
```

**Q7. Why does the two-pointer switching technique work — what is the mathematical guarantee that the pointers meet at exactly the intersection node?**
A: Let `lenA` and `lenB` be the lengths of the two lists, and `c` be the length of their shared tail (0 if no intersection). Pointer A travels `lenA` nodes, then (after switching) `lenB - c` more nodes to reach the intersection — total `lenA + (lenB - c)`. Pointer B travels `lenB` nodes, then (after switching) `lenA - c` more nodes to reach the intersection — total `lenB + (lenA - c)`. These two totals are algebraically equal: `lenA + lenB - c = lenB + lenA - c`. So both pointers cover the exact same total distance before reaching the intersection node, guaranteeing they arrive there on the same step. If there's no intersection (`c = 0`), both pointers simply traverse `lenA + lenB` total nodes each and reach `null` simultaneously, at which point the loop condition `pointerA !== pointerB` becomes false (`null === null`) and the function correctly returns `null`.

**Q8. Why is the two-pointer switching technique generally preferred over the length-difference approach, despite both being O(n+m) time and O(1) space?**
A: The two-pointer switching technique is more concise (no separate length-computation pass, no explicit "advance the longer pointer first" alignment step) and arguably more elegant, since the "switching to the other list" mechanism implicitly handles the length-alignment that the other approach computes explicitly. Both are equally correct and equally optimal in asymptotic complexity — the preference is largely about code simplicity and being the more commonly expected "clean" interview answer, though explaining the length-difference approach first (as a more intuitive stepping stone) before presenting the switching technique is often a strong way to demonstrate the reasoning progression in an interview.

### Section 3: Edge Cases & Related Considerations

**Q9. What happens in the two-pointer switching technique if the two lists don't intersect at all?**
A: Both pointers traverse their own list, then the other list, for a combined `lenA + lenB` steps each — since there's no shared node, both pointers independently reach the end of whichever list they're on second and become `null` at the same step (both have now traveled the full `lenA + lenB` distance). At that point `pointerA === pointerB` (`null === null`) is true, and the loop correctly exits, returning `null` — no special-casing is needed for "no intersection," since it naturally falls out of the same mechanism used for the intersecting case.

**Q10. What if the two input lists have a cycle — does the two-pointer switching technique still work?**
A: Not directly — if either list contains a cycle, "switching to the other list's head upon reaching `null`" breaks down, since a cyclic list never reaches `null` in the first place (the pointer would loop within the cycle forever, and the switching condition would never trigger). Handling potential cycles requires first running Floyd's cycle detection (see the dedicated linked-list guide) on both lists independently: if neither has a cycle, proceed with the standard intersection technique; if exactly one has a cycle, the lists cannot intersect in a well-defined "Y-shape" way (a cyclic list can't merge into a non-cyclic list's tail in a consistent single-node-per-next structure) so no valid intersection is typically reported; if both have cycles, a more involved check is needed — determining whether the two lists' cycles are actually the same cycle (by checking if one cycle's detected node is reachable from within the other's cycle), and if so, identifying the appropriate meeting point based on the specific definition of "intersection" being used for cyclic structures.

**Q11. How would you find the intersection of two DOUBLY linked lists — does the `prev` pointer change the approach?**
A: The core intersection concept (shared node references, tails identical from the intersection point onward) and both the hash-set and two-pointer-switching techniques transfer directly and unchanged — the `prev` pointer isn't needed for *detecting* the intersection using `next`-pointer traversal, since the intersection is fundamentally about the forward-chain structure. The `prev` pointer could be useful for a different but related question — e.g., "does the `prev` chain from the intersection point back toward each list's respective head look sensible/consistent" — but for the standard "find where they merge" question, the doubly-linked nature doesn't materially change the algorithm.

**Q12. Can this problem be generalized to more than two lists — finding a node shared by k linked lists?**
A: Yes, conceptually: the hash-set approach generalizes directly (add every node from lists `1` through `k-1` to a set, then scan list `k` for the first node found in that set — or more precisely, incrementally build up the set across all lists and check membership as you go, depending on exact problem semantics). The elegant O(1)-space two-pointer switching technique doesn't generalize as cleanly to k > 2 lists, since its correctness relies specifically on the "two pointers each traveling the sum of both lengths" symmetry — for k lists, achieving O(1) space typically requires either a different technique (e.g., pairwise reduction: find the intersection of lists 1 and 2, then find the intersection of that result with list 3, and so on) or falling back to the O(total length) hash-set approach.

### Section 4: Scenario / Interview-Style Questions

**Q13. "You're asked to find the intersection node of two singly linked lists, and the interviewer immediately follows up with 'can you do it without extra space?' Walk through your approach."**
A: I'd present the two-pointer switching technique: run two pointers starting at each list's head, advance one step at a time, and redirect each pointer to the *other* list's head when it reaches `null` instead of stopping. I'd explain the key guarantee — both pointers travel the exact same total distance (`lenA + lenB`) before either reaching the intersection node or reaching `null` simultaneously if there's no intersection — which is what makes this work in O(1) space without needing to precompute list lengths.

**Q14. "A teammate solves this problem using a hash set and says it's 'simpler to understand.' Do you agree, and would you push back in a code review?"**
A: I'd agree the hash-set approach is more immediately intuitive to read and verify correct — it directly mirrors the problem statement ("find a node that appears in both lists") without requiring the reader to work through the two-pointer switching technique's distance-equalization argument. Whether I'd push back depends on context: if this is a one-off utility function and O(n) extra space is genuinely not a concern, I'd likely leave it as-is, since code clarity has real value. If this runs in a memory-constrained environment or on very large lists where O(n) extra space is meaningfully costly, I'd suggest the O(1)-space alternative, while acknowledging the trade-off in readability it introduces.

**Q15. "How would you test your intersection-finding implementation to make sure it's correct, beyond just the 'happy path' of two lists that clearly intersect?"**
A: Key test cases: (1) two lists that don't intersect at all — confirm `null` is returned, not a crash or an incorrect node; (2) one or both lists empty — confirm graceful handling; (3) lists of very different lengths, both intersecting and non-intersecting, to make sure the length-alignment (or switching) logic is genuinely doing its job rather than only working by coincidence on same-length inputs; (4) the intersection point being the very first node of one or both lists (the lists are identical, or one is a suffix of the other) and the intersection point being the very last node (only the final node is shared) — boundary cases that can reveal off-by-one issues; (5) if applicable, lists containing duplicate *values* but no actual shared *nodes*, to confirm the implementation is correctly comparing references, not values.

**Q16. "Extend this to also return the LENGTH of the shared tail, not just the intersection node itself. How would you modify your approach?"**
A: Once the intersection node is found (via either O(1)-space technique), a simple additional traversal from that node to the end of the list, counting steps, directly gives the shared tail length — this is a trivial O(shared length) addition on top of the existing O(n+m) intersection-finding work, so it doesn't change the overall asymptotic complexity of the combined operation.

## Problem 1 — Intersection of Two Linked Lists (Hash Set Approach)

### Problem
Given the heads of two singly linked lists, return the node at which the two lists intersect. If the lists do not intersect, return `null`.

```
List A: 4 → 1 → 8 → 4 → 5
List B: 5 → 6 → 1 → 8 → 4 → 5
                    ↑
        (nodes 8→4→5 are shared, by reference)

Output: the node with value 8 (the first shared node)
```

### Pattern Recognition
Track every node visited in one list using a hash set, then check the other list against that set — the straightforward O(n+m) time, O(n) space baseline before optimizing to O(1) space.

### Key Insight
Since intersection means *shared node references*, storing every node object from `List A` in a `Set` and then checking `List B`'s nodes against that set (via reference equality, which `Set` naturally uses for object membership) directly identifies the first shared node encountered while scanning `List B`.

### Approach
Traverse `List A` fully, adding every node to a `Set`. Traverse `List B`, returning the first node found already present in that `Set`. If `List B` is fully traversed with no match, return `null`.

### Solution

```js
function getIntersectionNode(headA, headB) {
  const visited = new Set();

  let node = headA;
  while (node !== null) {
    visited.add(node);
    node = node.next;
  }

  node = headB;
  while (node !== null) {
    if (visited.has(node)) return node;
    node = node.next;
  }

  return null;
}
```

### Dry Run

```
List A: 4 → 1 → 8 → 4 → 5  (nodes labeled a1..a5 for clarity, values shown)
List B: 5 → 6 → 8(shared, =a3) → 4(shared,=a4) → 5(shared,=a5)
(assume nodes 8,4,5 in List B are literally the SAME objects as a3,a4,a5 in List A)

Build visited set from List A:
visited = { a1(4), a2(1), a3(8), a4(4), a5(5) }

Scan List B:
node = b1(5): visited.has(b1)? no (b1 is a distinct object from a5, unless explicitly shared — 
  assume b1,b2 are List B's own distinct nodes, not shared)
node = b2(6): visited.has(b2)? no
node = a3(8): visited.has(a3)? YES → return a3

Result: the node with value 8 (object a3) ✓
```

### Complexity
- Time: O(n + m) — one full pass over each list.
- Space: O(n) — the hash set stores every node from `List A`.

### Edge Cases
- No intersection: `List B`'s scan completes without any hit, correctly returns `null`.
- One list empty: the empty list's traversal loop never executes (either building an empty `visited` set, or scanning against a populated one and immediately finding no nodes to check) — correctly returns `null`, since an empty list can't share a node with anything.
- Lists are identical (same head): `visited` set built from `List A` immediately contains `headB`'s very first node (since `headB === headA`), so the first check in the second loop returns it immediately.
- Duplicate values but distinct node objects: since `Set` membership uses reference (object identity) semantics in JavaScript, coincidentally equal values without shared node objects correctly do NOT register as a match.

### Follow-up Questions
- "Can you do this in O(1) extra space?" → See Problem 2 or Problem 3 — the length-difference alignment or two-pointer switching techniques.
- "What if the lists could contain cycles?" → See Q10 — requires a preliminary cycle-detection step and more careful reasoning about what "intersection" means for cyclic structures.

## Problem 2 — Intersection of Two Linked Lists (Length Difference Alignment)

### Problem
Same as Problem 1, but solve it in O(1) extra space by first aligning both list pointers based on their length difference.

```
List A: 4 → 1 → 8 → 4 → 5           (length 5)
List B:      6 → 1 → 8 → 4 → 5      (length 4, shares 8→4→5 with List A)

Output: the node with value 8
```

### Pattern Recognition
Compute both lengths first, advance the longer list's pointer by the difference to equalize remaining distance, then walk both pointers together until they converge.

### Key Insight
Once both pointers are the same distance from the end of their respective lists, and given that intersecting lists share an identical tail from the intersection point onward, advancing both pointers in lockstep guarantees they land on the shared node at the same step.

### Approach
Compute `lengthA` and `lengthB`. Advance whichever pointer belongs to the longer list by `|lengthA - lengthB|` steps. Then advance both pointers together, comparing for equality at each step, until they match (the intersection) or both reach `null` (no intersection).

### Solution

```js
function getIntersectionNode(headA, headB) {
  const getLength = (head) => {
    let len = 0, node = head;
    while (node !== null) {
      len++;
      node = node.next;
    }
    return len;
  };

  let lenA = getLength(headA);
  let lenB = getLength(headB);
  let nodeA = headA, nodeB = headB;

  while (lenA > lenB) {
    nodeA = nodeA.next;
    lenA--;
  }
  while (lenB > lenA) {
    nodeB = nodeB.next;
    lenB--;
  }

  while (nodeA !== nodeB) {
    nodeA = nodeA.next;
    nodeB = nodeB.next;
  }

  return nodeA;
}
```

  nodeA="8"(3rd of A), nodeB="1"(2nd of B)

### Complexity
- Time: O(n + m) — two length-computation passes plus one alignment/walk pass, all linear.
- Space: O(1) — only integer counters and node pointers.

### Edge Cases
- Equal-length lists: the alignment loops (`while lenA > lenB` / `while lenB > lenA`) both immediately skip (no advancement needed), proceeding directly to the lockstep walk.
- No intersection: both pointers reach `null` at the same step (after alignment, they're guaranteed equidistant from each list's true end), so `nodeA === nodeB` becomes `null === null`, correctly returning `null`.
- One list is a "suffix" of the other (e.g., `List B` is exactly the shared tail with no unique prefix): `lenB` is smaller, `nodeA` advances to align, and the very next lockstep comparison correctly identifies `headB` itself as the intersection node.

### Follow-up Questions
- "Can you avoid computing lengths explicitly?" → See Problem 3 — the two-pointer switching technique achieves the same result without a separate length-computation pass.
- "What's the advantage of this approach over the switching technique?" → Arguably more explicit/intuitive for someone unfamiliar with the switching trick's distance-equalization argument — a reasonable stepping-stone explanation before presenting the more concise alternative.

## Problem 3 — Intersection of Two Linked Lists (Two-Pointer Switching Technique)

### Problem
Same as Problems 1 and 2, but using the elegant two-pointer technique that avoids any explicit length computation.

```
List A: 4 → 1 → 8 → 4 → 5
List B:           8 → 4 → 5   (shares the last 3 nodes with List A, by reference)

Output: the node with value 8
```

### Pattern Recognition
Two pointers traverse both lists in a "switched" order such that both cover the exact same total distance before either reaching the intersection node or reaching `null` simultaneously.

### Key Insight
Redirecting each pointer to the *other* list's head upon reaching its own list's end causes both pointers to have traveled `lenA + lenB` total steps by the time they'd naturally meet — this total-distance equality is what guarantees simultaneous arrival at the intersection node (or simultaneous arrival at `null` if there's no intersection), without ever needing to know `lenA` or `lenB` explicitly.

### Approach
Two pointers start at each list's respective head. Advance both one step at a time; whenever a pointer would move past its current list's end (`null`), redirect it to the other list's head instead. Continue until the pointers are equal (either both at the intersection node, or both `null`).

### Solution

```js
function getIntersectionNode(headA, headB) {
  if (headA === null || headB === null) return null;

  let pointerA = headA, pointerB = headB;

  while (pointerA !== pointerB) {
    pointerA = pointerA === null ? headB : pointerA.next;
    pointerB = pointerB === null ? headA : pointerB.next;
  }

  return pointerA;
}
```

### Dry Run

```
List A: 4→1→8→4→5  (a1,a2,a3,a4,a5)
List B: 8→4→5       (SAME objects as a3,a4,a5 — List B is just List A's shared tail, length 3)

pointerA=a1(4), pointerB=a3(8) [List B's head]

pointerA!==pointerB → advance both:
  pointerA=a2(1), pointerB=a4(4)
pointerA!==pointerB → advance both:
  pointerA=a3(8), pointerB=a5(5)
pointerA!==pointerB → advance both:
  pointerA=a4(4), pointerB=null (B reached its end) → switch: pointerB=headA=a1(4)
pointerA!==pointerB → advance both:
  pointerA=a5(5), pointerB=a2(1)
pointerA!==pointerB → advance both:
  pointerA=null (A reached its end) → switch: pointerA=headB=a3(8)
  pointerB=a3(8) [continuing from a2→a3]

pointerA(a3) === pointerB(a3)? YES → loop ends

Result: node a3 (value 8) ✓

Sanity check on total distance traveled:
lenA=5, lenB=3. pointerA traveled: 5 (all of A) + 2 (into B: b1,b2 before reaching a3-as-B's-3rd... )
Both pointers indeed cover lenA+lenB=8 total steps before meeting, confirming the Q7 argument.
```

### Complexity
- Time: O(n + m) — each pointer traverses at most `lenA + lenB` nodes total.
- Space: O(1) — two pointers, no auxiliary structure.

### Edge Cases
- No intersection: both pointers traverse `lenA + lenB` steps and land on `null` simultaneously — `null === null` is true, loop exits, correctly returns `null`.
- Either list empty: explicit early-return guard (`headA === null || headB === null`) handles this directly, since an empty list trivially cannot intersect with anything.
- Equal-length lists that intersect at the very first node (identical lists): `pointerA` and `pointerB` are equal from the very first comparison (`headA === headB`), loop body never executes, immediately returns the shared head.
- Very different length lists: the switching mechanism handles arbitrary length differences without any special-casing — the same code path handles both close-to-equal and wildly different lengths uniformly.

### Follow-up Questions
- "Why is this preferred over the length-difference approach?" → See Q8 — more concise, no separate length-computation pass, though both are equally correct and equally O(n+m) time / O(1) space.
- "Can you adapt this for k > 2 lists?" → Not directly in the same elegant O(1)-space form — see Q12 for why the technique's correctness argument is specifically two-list-shaped, and what alternatives exist for k lists.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve finding a shared node (by reference) between two linked lists?
│
├── O(n) EXTRA SPACE ACCEPTABLE, SIMPLICITY PREFERRED?
│   └── Hash Set: store all of List A's nodes, scan List B for the first match → O(n+m) time, O(n) space
│
├── O(1) EXTRA SPACE REQUIRED?
│   ├── Comfortable computing lengths explicitly first →
│   │     Length-Difference Alignment: advance the longer list's pointer by the difference,
│   │     then walk both pointers together → O(n+m) time, O(1) space
│   └── Prefer the more concise, no-length-computation approach →
│         Two-Pointer Switching: redirect each pointer to the OTHER list's head upon reaching
│         null → O(n+m) time, O(1) space (both achieve identical results)
│
├── EITHER LIST MIGHT CONTAIN A CYCLE?
│   └── Run Floyd's cycle detection on both lists FIRST — the standard intersection techniques
│       assume acyclic (null-terminated) lists and don't directly handle cycles
│
├── MORE THAN TWO LISTS (k lists, find a commonly-shared node)?
│   └── Hash Set generalizes directly; O(1)-space two-pointer switching does NOT generalize
│       cleanly — consider pairwise reduction (intersect list1&2, then that result with list3, etc.)
│
└── DOUBLY LINKED LISTS?
    └── Same techniques apply unchanged via `next`-pointer traversal — the `prev` pointer
        isn't needed for standard intersection detection
```

## Common Bugs Checklist

Before submitting any linked-list-intersection solution, verify:

1. **Comparing node REFERENCES, not values?** — `nodeA === nodeB` (or equivalent reference/pointer equality), never `nodeA.val === nodeB.val` — value-based comparison produces false positives whenever coincidentally-equal values exist without actual shared structure.

2. **Two-pointer switching: redirect condition checks for `null`, and redirects to the OTHER list's head?** — `pointerA = pointerA === null ? headB : pointerA.next` — accidentally redirecting to the same list's head instead of the other list's breaks the distance-equalization guarantee entirely.

3. **Length-difference approach: alignment loop advances the correct (LONGER) list's pointer?** — Advancing the shorter list's pointer instead (or advancing by the wrong number of steps) misaligns the pointers and produces incorrect (or missed) intersection detection.

4. **No-intersection case returns `null` correctly, not a crash or incorrect node?** — Both O(1)-space techniques should naturally produce `null` when both pointers simultaneously reach the end — worth an explicit test case to confirm this isn't accidentally broken (e.g., by an off-by-one in a loop condition).

5. **Empty-list inputs guarded against, if not naturally handled by the main logic?** — Depending on implementation, an empty `headA` or `headB` might need an explicit early check to avoid null-pointer issues before the main algorithm's loop even begins.

6. **Hash-set approach: building the set from the FIRST list before scanning the SECOND, not interleaved incorrectly?** — The two traversal phases (build set, then scan) must be sequential and complete, not accidentally interleaved in a way that could miss a match or check against a partially-built set.
