## Topic A: Cycle Detection Fundamentals

### Section A1: Fundamentals

**Q1. What is cycle detection, and what structures can contain cycles?**
A: Cycle detection is the problem of determining whether a sequence of values produced by repeatedly applying a function eventually repeats — i.e., whether following the structure eventually leads back to a previously visited state. The structures that can contain cycles:

- **Linked lists**: a `next` pointer in some node points back to an earlier node in the list rather than to `null`, creating an infinite loop.
- **Directed graphs**: a path exists from some node back to itself (a cycle in the DFS sense).
- **Functional sequences**: the sequence `x, f(x), f(f(x)), ...` produced by iterating a function `f` on a finite domain — since the domain is finite, the sequence must eventually repeat.
- **Arrays interpreted as graphs**: an array where `arr[i]` is the "next" index — creates an implicit linked structure that may contain cycles.

```
Linked list with cycle:
1 → 2 → 3 → 4 → 5
            ↑       ↓
            8 ← 7 ← 6

Functional sequence (f(x) = x² mod 10):
x=2: 2, 4, 6, 6, 6, ...  (cycle at 6)
x=3: 3, 9, 1, 1, 1, ...  (cycle at 1)
```

**Q2. What is the naive HashSet approach to cycle detection, and what are its trade-offs?**
A: The HashSet approach traverses the structure, inserting each visited node into a set. If a node is encountered that already exists in the set, a cycle has been detected. If traversal reaches a natural end (e.g., `null` in a linked list), no cycle exists.

```js
function hasCycleHashSet(head) {
  const visited = new Set();
  let node = head;
  while (node) {
    if (visited.has(node)) return true; // cycle detected
    visited.add(node);
    node = node.next;
  }
  return false;
}
```

- **Time**: O(n) — each node visited at most once.
- **Space**: O(n) — all visited nodes stored in the set.
- **Trade-off**: simple and intuitive, but O(n) space. Floyd's algorithm solves the same problem in O(1) space. The HashSet approach also gives you the cycle entry point directly (the first repeated node), whereas Floyd's requires a second phase to find the entry point.

**Q3. What is Floyd's Cycle Detection Algorithm ("tortoise and hare"), and what is its core idea?**
A: Floyd's algorithm uses two pointers — a **slow pointer** (tortoise) advancing one step at a time and a **fast pointer** (hare) advancing two steps at a time — both starting at the same position. If a cycle exists, the fast pointer laps the slow pointer inside the cycle, and they are guaranteed to meet. If no cycle exists, the fast pointer reaches the end of the structure (a `null` node) before any meeting occurs.

The core idea is a **relative speed argument**: inside a cycle of length `λ`, the fast pointer gains one step on the slow pointer per iteration. Since the relative speed is 1 step per iteration and the cycle has finite length `λ`, the fast pointer must catch the slow pointer within at most `λ` iterations after both enter the cycle. The meeting is inevitable if — and only if — a cycle exists.

```
No cycle:         fast reaches null before meeting slow → return false
Cycle exists:     fast laps slow inside cycle → they meet → return true
```

**Q4. Prove that if a cycle exists, the two pointers must meet inside the cycle.**
A: Let the list have a "tail" of length `μ` nodes before the cycle entry point, and a cycle of length `λ`. After `μ` steps, the slow pointer has just entered the cycle. At the same moment, the fast pointer has taken `2μ` steps total, placing it at position `2μ - μ = μ` steps *inside* the cycle (i.e., `μ mod λ` steps ahead of the cycle entry).

Now both pointers are inside the cycle. Let `k = μ mod λ` be the fast pointer's head start (in steps) inside the cycle. At each subsequent step, the fast pointer gains 1 step on the slow pointer. The slow pointer must "catch up" to the fast pointer's position from behind — equivalently, the fast pointer must close the gap of `λ - k` remaining steps (the distance the fast pointer is *ahead* of the slow pointer, going forward around the cycle). After `λ - k` more steps, the gap closes to zero and the pointers meet.

Since `λ - k ≤ λ`, the pointers meet within at most `λ` steps after both enter the cycle, which is within at most `μ + λ` total steps — a finite bound, guaranteeing the meeting always occurs.

```
Tail length μ=3, cycle length λ=5:
After μ=3 steps: slow is at cycle entry (position 0 inside cycle)
                 fast is at position 2μ mod λ = 6 mod 5 = 1 inside cycle
Gap to close:    λ - k = 5 - 1 = 4 steps
Pointers meet:   after 4 more steps, at position 4 inside the cycle
Total steps:     μ + (λ - k) = 3 + 4 = 7
```

**Q5. What is the time and space complexity of Floyd's algorithm, and how does it compare to the HashSet approach?**
A:

| Approach | Time | Space | Finds Entry Point? | Handles Modification? |
|---|---|---|---|---|
| HashSet | O(n) | O(n) | Yes (directly) | No (requires adding to set) |
| Floyd's | O(n) | O(1) | Yes (second phase) | Yes (pointer-only) |

Floyd's algorithm is O(n) time: the slow pointer travels at most `μ + λ` steps before meeting (bounded by n, the total node count). Space is O(1): only two pointer variables, regardless of list length. The HashSet approach is O(n) space because it stores every visited node. Floyd's is the optimal approach when space is constrained or when the structure cannot be modified (some cycle detection tricks use node value mutation, which Floyd's avoids entirely).

### Section A2: Advanced Patterns

**Q6. How does Floyd's algorithm find the cycle entry point (not just detect the cycle)?**
A: After the slow and fast pointers meet inside the cycle (Phase 1), a second phase locates the entry point. Reset one pointer to the **head** of the list; leave the other at the **meeting point**. Advance both pointers one step at a time. The point where they meet again is the **cycle entry node**.

**Why this works**: let `μ` be the tail length (distance from head to cycle entry), `λ` be the cycle length, and `d` be the distance from the cycle entry to the meeting point (measured forward around the cycle). At the Phase 1 meeting:
- Slow pointer has traveled `μ + d` steps.
- Fast pointer has traveled `2(μ + d)` steps = `μ + d + n·λ` for some integer n (it has gone around the cycle extra times).
- Subtracting: `μ + d = n·λ`, so `μ = n·λ - d`.

Now reset one pointer to the head. Both pointers advance one step at a time. The head pointer reaches the cycle entry after `μ` steps. The meeting-point pointer, starting at distance `d` inside the cycle, advances `μ = n·λ - d` steps — which lands it exactly at the cycle entry (it travels `n` full laps minus `d` steps, arriving at the entry). Both pointers are at the cycle entry simultaneously. ✓

```js
function detectCycleEntry(head) {
  let slow = head, fast = head;

  // Phase 1: detect cycle
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) break;
  }

  if (!fast || !fast.next) return null; // no cycle

  // Phase 2: find entry point
  slow = head; // reset slow to head; fast stays at meeting point
  while (slow !== fast) {
    slow = slow.next;
    fast = fast.next; // both move one step at a time now
  }

  return slow; // cycle entry node
}
```

**Q7. How does Floyd's algorithm find the cycle length once a cycle is detected?**
A: After Phase 1 (slow and fast meet inside the cycle), keep one pointer fixed at the meeting point and advance the other one step at a time, counting steps until it returns to the meeting point. The count is the cycle length `λ`.

```js
function cycleLength(meetingPoint) {
  let current = meetingPoint.next;
  let length = 1;
  while (current !== meetingPoint) {
    current = current.next;
    length++;
  }
  return length;
}
```

This is O(λ) time — one full traversal of the cycle. Combined with Phase 1's O(μ + λ) detection, the total remains O(n).

**Q8. What is Brent's cycle detection algorithm, and how does it differ from Floyd's?**
A: Brent's algorithm also uses two pointers but moves only one of them at a time — the "teleporter" approach. The slow pointer stays fixed ("teleports" to the fast pointer's position periodically), while the fast pointer advances one step per iteration. The slow pointer teleports whenever the number of fast-pointer steps reaches the next power of two. A cycle is detected when the fast pointer lands on the same node as the slow pointer's current (fixed) position.

```
Brent's key difference from Floyd's:
- Floyd's: both pointers move every step (slow by 1, fast by 2)
- Brent's: only fast pointer moves; slow pointer "teleports" at power-of-two intervals
- Brent's advantage: finds cycle length directly as a byproduct (the interval at which
  teleportation happened when detection occurred equals λ)
- Brent's advantage: requires ~24-36% fewer function evaluations than Floyd's on average
- Floyd's advantage: simpler to implement and explain; more commonly asked in interviews
```

**Q9. How does cycle detection apply to the "happy number" problem (functional sequence cycles)?**
A: A "happy number" is defined by the process: replace the number with the sum of the squares of its digits; repeat until the number equals 1 (happy) or loops forever in a cycle that does not include 1 (not happy). This is an implicit linked list: each number maps to exactly one "next" value via the digit-square-sum function. Cycle detection determines whether the sequence reaches 1 or enters a non-1 cycle. Floyd's algorithm applies directly: slow pointer computes `f(x)` once per step, fast pointer computes `f(f(x))` twice per step. If fast reaches 1, the number is happy. If slow and fast meet at a value ≠ 1, the number is not happy (a non-1 cycle was detected).

```js
function digitSquareSum(n) {
  let sum = 0;
  while (n > 0) {
    const d = n % 10;
    sum += d * d;
    n = Math.floor(n / 10);
  }
  return sum;
}

function isHappy(n) {
  let slow = n, fast = n;
  do {
    slow = digitSquareSum(slow);
    fast = digitSquareSum(digitSquareSum(fast));
  } while (slow !== fast);
  return slow === 1; // met at 1 → happy; met elsewhere → cycle, not happy
}
```

## Topic B: Cycle Detection in Linked Lists

### Section B1: Fundamentals

**Q10. Why does Floyd's algorithm specifically use a 2:1 speed ratio? Would a 3:1 ratio also work?**
A: Any speed ratio `k:1` where `k > 1` and `k` is a positive integer guarantees meeting inside a cycle, but with different behaviors:

**3:1 ratio**: the fast pointer gains 2 steps per iteration on the slow pointer. Inside a cycle of length `λ`, the relative gap closes at rate 2 per step. The pointers meet when `2t ≡ -k (mod λ)` for some initial offset `k` — this has a solution iff `gcd(2, λ) | k`, which is not always guaranteed for even-length cycles (if `λ` is even and `k` is odd, the pointers may never meet — they "skip past" each other). This makes 3:1 unreliable.

**2:1 ratio**: the fast pointer gains exactly 1 step per iteration. The relative gap closes at rate 1, which divides every possible cycle length — the pointers are guaranteed to meet regardless of `λ` or the initial offset. This is the minimum speed ratio that provides the meeting guarantee without cycle-length dependency. Higher-step versions like 3:1 require extra conditions (e.g., `gcd(ratio-1, λ) = 1`) to guarantee a meeting, which cannot be enforced without knowing `λ` in advance.

**Q11. What are the three possible states when running Floyd's algorithm on a linked list, and how does the termination condition capture them?**
A: The three states and their termination signatures:

- **No cycle, finite list**: `fast` reaches `null` (even-length list: `fast == null`) or `fast.next` reaches `null` (odd-length list: `fast.next == null`). The loop guard `while (fast && fast.next)` handles both — the loop exits without the pointers meeting.
- **Cycle detected**: `slow == fast` inside the loop — both pointers are at the same node inside the cycle.
- **Single node, no cycle**: `head.next == null` — the loop guard immediately fails; correctly returns "no cycle" in one check.

The loop guard `while (fast !== null && fast.next !== null)` must check *both* `fast` and `fast.next` because the fast pointer advances *two* steps — if `fast.next` is null, the instruction `fast = fast.next.next` would dereference `null.next`, causing a null pointer exception.

**Q12. What is the "remove nth node from end of list" problem, and how does it use a two-pointer gap technique related to cycle detection?**
A: While not cycle detection itself, it uses the same two-pointer speed-differential insight: maintain a gap of exactly `n` nodes between a fast and slow pointer. Advance both at the same speed (1 step each); when fast reaches the end, slow is exactly at the node before the target. This is a *gap-based* two-pointer rather than a *speed-based* two-pointer, but the same mental model (two pointers with a controlled relationship) applies.

The connection: both Floyd's and the gap technique exploit the fact that when one pointer has a fixed positional or speed advantage over another, their relative position encodes information about the list structure — the cycle entry point in Floyd's, and the (n-from-end) position in the gap technique.

### Section B2: Advanced Patterns

**Q13. How does cycle detection in a linked list relate to detecting a cycle in a directed graph (DFS coloring)?**
A: Both detect cycles, but in structurally different ways suited to different graph types:

**Floyd's (linked list / functional sequence)**: works on structures where each node has exactly one outgoing edge (each node has exactly one `next`). The two-pointer trick exploits the determinism of movement — there is only one path forward from any node.

**DFS with 3-color marking (directed graph)**: nodes are marked `WHITE` (unvisited), `GRAY` (in current DFS stack), or `BLACK` (fully explored). A cycle is detected when a `GRAY` node is encountered during DFS — it means the current path loops back to an ancestor. This handles arbitrary fan-out (multiple outgoing edges from a node), which Floyd's cannot.

```
Floyd's: works when out-degree = 1 for all nodes (linked lists, rho-graphs)
DFS coloring: works for any directed graph (out-degree ≥ 0, any fan-out)

For undirected graphs: DFS + parent tracking (a back edge to a non-parent = cycle)
```

**Q14. What is a "rho-shaped" graph (ρ-graph), and why is it the canonical model for Floyd's algorithm?**
A: A rho-graph (named after the Greek letter ρ) consists of a tail of `μ` nodes leading into a cycle of `λ` nodes — exactly the shape created by iterating a function on a finite domain. The tail nodes have in-degree 0 (nothing points to them except the sequence start) and out-degree 1. The cycle nodes all have in-degree 1 and out-degree 1. Floyd's algorithm is designed precisely for this structure: it requires that every node have exactly one successor, forming a deterministic path from any starting point. The rho-shape is the most general structure where Floyd's applies — a pure cycle (μ=0) is the degenerate case.

```
Rho-graph (μ=3 tail, λ=4 cycle):

head → [T1] → [T2] → [T3] → [C1] → [C2]
                               ↑              ↓
                              [C4] ← [C3]

Floyd's finds: cycle exists (Phase 1), entry = C1 (Phase 2), length = 4 (Phase 3)
```

**Q15. How do you detect a cycle in an undirected graph, and why can't Floyd's algorithm be directly applied?**
A: In an undirected graph, every edge is bidirectional — traversing edge (u, v) from `u` means `v`'s "next" could be `u` (going back). This creates a trivial "cycle" of length 2 at every edge if not handled, making the two-pointer approach meaningless (the fast pointer would immediately oscillate back and forth). Floyd's requires a structure where each node has exactly one determined successor, which undirected graphs don't provide.

**Correct approach — DFS with parent tracking**: during DFS from any node, if a neighbor is already visited and is *not* the node's immediate parent in the DFS tree, a back edge exists and a cycle is detected. The parent check distinguishes a real cycle from the trivial "back along the edge I just came from" traversal.

```js
function hasCycleUndirected(graph, n) {
  const visited = new Array(n).fill(false);

  function dfs(node, parent) {
    visited[node] = true;
    for (const neighbor of graph[node]) {
      if (!visited[neighbor]) {
        if (dfs(neighbor, node)) return true;
      } else if (neighbor !== parent) {
        return true; // back edge to non-parent → cycle
      }
    }
    return false;
  }

  for (let i = 0; i < n; i++) {
    if (!visited[i] && dfs(i, -1)) return true;
  }
  return false;
}
```

## Topic C: Cycle Detection in Arrays and Functional Sequences

### Section C1: Fundamentals

**Q16. How does cycle detection apply to arrays where each element is a "next index"?**
A: An array `arr` of length `n` where each element is a valid index (0 ≤ arr[i] < n) defines an implicit functional graph: starting from any index `i`, the sequence is `i, arr[i], arr[arr[i]], ...`. Since the index space is finite (n values), this sequence must eventually revisit an index — creating a cycle. Floyd's algorithm applies directly: treat index `i` as the "node" and `arr[i]` as the "next" pointer.

```js
function hasCycleInArray(arr) {
  let slow = 0, fast = 0;
  do {
    slow = arr[slow];
    fast = arr[arr[fast]];
  } while (slow !== fast);
  return true; // finite domain guarantees a cycle always exists
}
```

Note: for a finite-domain function, a cycle is always guaranteed to exist (pigeonhole principle). The question becomes not "does a cycle exist?" but "where does the cycle start?" and "what is the cycle length?" — as in the "find the duplicate number" problem (Q24).

**Q17. How does the "find duplicate in array" problem reduce to cycle detection?**
A: Given an array of `n+1` integers where each value is in range `[1, n]`, exactly one value is duplicated. Treat each index as a node and each value `arr[i]` as the "next pointer" — the array defines a functional graph. The duplicate value is the cycle entry point: since two indices point to the same value, two "next pointers" lead to the same node, creating a rho-shaped graph exactly like a linked list with a cycle. Floyd's Phase 1 detects the cycle; Phase 2 finds the entry point — which is the duplicate value.

```
arr = [1, 3, 4, 2, 2]
Index: 0 → 1 → 3 → 2 → 4 → 2 (cycle!)
Value at each step:
  start at index 0 (value=1): 0 → arr[0]=1 → arr[1]=3 → arr[3]=2 → arr[2]=4 → arr[4]=2 → ...
  cycle entry is index 2 (value 2 = the duplicate)
```

**Q18. What is the "circular array loop" problem, and how does Floyd's extend to it?**
A: Given a circular array of non-zero integers (positive = move forward, negative = move backward), determine if a valid cycle exists. A valid cycle must: (1) have all elements moving in the same direction (all positive or all negative), and (2) have length > 1 (a single-element self-loop is invalid). Floyd's algorithm applies per starting index: treat `(currentIndex + arr[currentIndex] + n) % n` as the "next" function. Before following each step, verify the direction is consistent and the step doesn't lead to a self-loop. If the fast and slow pointers meet, a valid cycle is found.

```js
function circularArrayLoop(nums) {
  const n = nums.length;

  function next(idx) {
    return ((idx + nums[idx]) % n + n) % n; // handle negative modulo
  }

  for (let i = 0; i < n; i++) {
    let slow = i, fast = i;

    // Only follow if direction stays consistent
    while (nums[slow] * nums[next(slow)] > 0 &&      // slow and its next: same direction
           nums[fast] * nums[next(fast)] > 0 &&       // fast and its next: same direction
           nums[fast] * nums[next(next(fast))] > 0) { // fast.next and fast.next.next: same direction
      slow = next(slow);
      fast = next(next(fast));

      if (slow === fast) {
        // Verify cycle length > 1 (no self-loop)
        if (slow === next(slow)) break;
        return true;
      }
    }
  }
  return false;
}
```

### Section C2: Advanced Patterns

**Q19. What is the "cycle in a sequence" problem for random number generators, and why does it matter in practice?**
A: A Linear Congruential Generator (LCG) produces a sequence `x_{n+1} = (a·x_n + c) mod m`. Since the state space is finite (0 to m-1), the sequence must cycle — the "period" is the cycle length `λ`. A short period means the generator repeats quickly, making it unsuitable for cryptographic use. Floyd's algorithm (or Brent's, which is faster for this purpose) detects the period by finding the cycle in the functional sequence without storing the entire sequence — critical when `m` is large (e.g., 2^64) and storing all values is infeasible. This is one of the original motivations for Floyd's algorithm.

**Q20. How does Floyd's algorithm apply to detecting cycles in number theory sequences (Pollard's rho factorization)?**
A: Pollard's rho algorithm uses Floyd's cycle detection to factor large integers. Given a number `N` to factor, define a pseudorandom function `f(x) = (x² + c) mod N`. The sequence `x, f(x), f(f(x)), ...` is a functional sequence on a finite domain (0 to N-1). If a non-trivial factor `p` of `N` exists, the sequence `mod p` (which has a smaller domain, 0 to p-1) must cycle sooner than the sequence `mod N`. Floyd's detects this cycle; when the two pointers meet, `gcd(|slow - fast|, N)` is likely a non-trivial factor of `N`. The "rho" in the name comes from the rho-shape of the functional graph when the sequence is visualized modulo `p`. This makes Floyd's cycle detection a core component of one of the most practical integer factorization algorithms.

**Q21. How do you detect a cycle in a directed graph using DFS, and what is the three-color marking scheme?**
A: Assign each node one of three states: `WHITE` (unvisited), `GRAY` (currently in the DFS recursion stack — visited but not fully explored), `BLACK` (fully explored — all descendants visited). Begin DFS from any WHITE node: mark it GRAY, recurse into all outgoing neighbors. If any neighbor is GRAY, a back edge (cycle) is found. If a neighbor is BLACK, it's already fully explored with no cycle from it — skip. When all neighbors are explored, mark the current node BLACK.

```js
function hasCycleDirected(graph, n) {
  const WHITE = 0, GRAY = 1, BLACK = 2;
  const color = new Array(n).fill(WHITE);

  function dfs(node) {
    color[node] = GRAY; // entering DFS subtree
    for (const neighbor of (graph[node] || [])) {
      if (color[neighbor] === GRAY) return true;  // back edge → cycle
      if (color[neighbor] === WHITE && dfs(neighbor)) return true;
    }
    color[node] = BLACK; // fully explored, no cycle from here
    return false;
  }

  for (let i = 0; i < n; i++) {
    if (color[i] === WHITE && dfs(i)) return true;
  }
  return false;
}
```

Time: O(V + E) — each node and edge visited at most once.
Space: O(V) — color array plus O(V) recursion stack depth in the worst case.

## Topic D: Cross-Topic & Interview-Style Questions

**Q22. "How would you explain Floyd's cycle detection to someone in one paragraph, without code?"**
A: Imagine two runners on a track, starting from the same point. One runs at normal speed; the other runs at double speed. If the track is a straight road with a dead end, the faster runner reaches the end first and they never meet again. If the track loops — even if it has a long straight section before the loop — the faster runner will eventually lap the slower runner inside the loop and they'll be at the same point at the same time. The moment they're at the same spot again, you know a loop exists. And with a small additional trick — sending one runner back to the start while the other continues at the same pace — you can determine exactly where the loop begins.

**Q23. "Floyd's algorithm finds that slow and fast meet after n steps. How do you know the meeting point is always inside the cycle, never on the tail?"**
A: By construction: the fast pointer advances two steps per iteration. If the fast pointer were ever on the tail (i.e., fewer than `μ` steps from the head), the slow pointer — which is always behind or equal to the fast pointer — would also be on the tail, having taken fewer steps. The fast pointer can only *exit* the tail once it reaches the cycle entry, at which point it enters the cycle and can never return to the tail (directed structure, no back edges on the tail). Once both pointers are in the cycle, they never leave it. Since the meeting condition requires `slow == fast`, and both pointers are in the cycle when they meet, the meeting point is always inside the cycle.

**Q24. "What if the slow and fast pointers start at different positions — does Floyd's still work?"**
A: Phase 1 (cycle detection) still works as long as both pointers start within the same connected component of the functional graph and both are in the rho-shape (not already inside the cycle exclusively). If both start at arbitrary positions, the detection still holds — the fast pointer gains on the slow pointer at rate 1 per step, and meeting is guaranteed within one cycle length after both enter the cycle. However, Phase 2 (entry point detection) specifically requires the slow pointer to be reset to the *head* of the structure (the defined starting point), because the Phase 2 proof relies on the mathematical relationship `μ = n·λ - d` that is derived from a specific starting position. If the original start is not well-defined (e.g., in a functional graph with multiple entry points), Phase 2 must be adapted accordingly.

**Q25. "Can Floyd's algorithm detect all cycles in a graph with multiple disconnected components?"**
A: No — a single run of Floyd's from one starting node only detects cycles reachable from that node. For a graph with multiple disconnected components (or a graph where some components have cycles and others don't), Floyd's must be run from a starting node in each component. In practice, for the "detect any cycle in a directed graph" problem, DFS with 3-color marking is applied from every unvisited node, naturally handling all components. Floyd's is suited to single-path structures (linked lists, functional sequences with one defined start) rather than general graphs.

**Q26. "Why do we check `fast && fast.next` in the loop guard rather than just `fast`?"**
A: The fast pointer advances two steps per iteration: `fast = fast.next.next`. If we only check `fast != null` before the step, we may attempt to access `fast.next.next` when `fast.next` is already `null` — dereferencing `null.next` causes a null pointer exception. The guard `fast && fast.next` ensures that both `fast` (the current node) and `fast.next` (the intermediate node) are non-null before the double-step is taken. This is a correctness guard, not a performance optimization — on a cycle-free list of even length, `fast` reaches `null` directly; on odd length, `fast.next` reaches `null`; both cases are covered.

**Q27. "In one sentence each, what is the key invariant that each phase of Floyd's algorithm maintains?"**
A:
- **Phase 1 (detection)**: at every step, the fast pointer is exactly twice as far from the head as the slow pointer, and the distance between them inside the cycle strictly decreases by 1 per step once both are in the cycle — guaranteeing they meet within one cycle length.
- **Phase 2 (entry point)**: after resetting the slow pointer to the head, both pointers are always exactly `μ - steps_taken` steps away from the cycle entry, converging to the entry simultaneously because `μ = n·λ - d` ensures the meeting-point pointer reaches the entry in exactly `μ` additional steps.
- **Phase 3 (cycle length)**: the non-advanced pointer is fixed at the meeting point, and the advancing pointer travels the cycle exactly once to return to it, counting a number of steps equal to the cycle length `λ`.

## Problem 1 — Linked List Cycle Detection

### Problem
Given the head of a singly linked list, return `true` if the list has a cycle (some node's `next` pointer points to a previous node), or `false` if it does not.

```
Input:  3 → 2 → 0 → -4
                ↑        ↓
                └─────────┘
Output: true   (tail connects back to node with value 2)

Input:  1 → 2 → null
Output: false
```

### Pattern Recognition
Floyd's tortoise-and-hare cycle detection — two pointers at speeds 1 and 2; meeting inside the list proves a cycle; fast reaching null proves no cycle.

### Key Insight
In a cycle-free list, the fast pointer outruns the slow pointer and exits at null — they can never meet. In a list with a cycle, the fast pointer laps the slow pointer inside the cycle — they must meet. The meeting condition (`slow == fast`) is the binary cycle/no-cycle discriminator.

### Approach
Initialize both `slow` and `fast` to `head`. Loop: advance `slow` by 1, `fast` by 2. If `slow === fast`, a cycle exists — return true. If `fast` or `fast.next` becomes null, no cycle — return false.

### Solution

```js
function hasCycle(head) {
  let slow = head;
  let fast = head;

  while (fast !== null && fast.next !== null) {
    slow = slow.next;       // tortoise: 1 step
    fast = fast.next.next;  // hare: 2 steps

    if (slow === fast) {
      return true; // pointers met inside cycle
    }
  }

  return false; // fast exited the list → no cycle
}
```

### Dry Run

```
List: 3 → 2 → 0 → -4 → (back to node 2)
Nodes by reference: A(3) → B(2) → C(0) → D(-4) → B(2) [cycle]

Initial: slow=A, fast=A

Step 1: slow=B, fast=C.  slow≠fast.
Step 2: slow=C, fast=B.  slow≠fast.  (fast went C→D→B)
Step 3: slow=D, fast=D.  slow===fast → return true ✓

(fast went B→C→D, slow went C→D)
```

### Complexity
- Time: O(n) — in the worst case, slow pointer travels at most `μ + λ` steps (tail length + one cycle). Both `μ` and `λ` are bounded by the total node count `n`.
- Space: O(1) — two pointer variables only.

### Edge Cases
- Empty list (`head = null`): `fast` is immediately null; loop guard fails; return false.
- Single node, no cycle (`head.next = null`): `fast.next` is null; loop guard fails on first check; return false.
- Single node with self-loop (`head.next = head`): Step 1: `slow = head`, `fast = head` (fast goes head.next.next = head). `slow === fast` → return true.
- All nodes in one big cycle (no tail, μ=0): fast starts gaining on slow from step 1; they meet within `λ` steps.

### Follow-up Questions
- "Find the node where the cycle begins?" → Phase 2: reset slow to head, advance both by 1 until they meet — that node is the cycle entry (see Problem 2).
- "Return the cycle length?" → After Phase 1 meeting, keep one pointer fixed, advance the other until it returns; count steps (see Q7).
- "Solve without modifying the list and without extra space?" → This IS the solution — Floyd's algorithm uses no extra space and doesn't modify the list.

## Problem 2 — Linked List Cycle Entry Point

### Problem
Given the head of a linked list that may contain a cycle, return the node where the cycle begins. If no cycle exists, return `null`.

```
Input:  3 → 2 → 0 → -4
                ↑        ↓
                └─────────┘
Output: Node with value 2  (cycle starts at the second node)

Input:  1 → 2 → null
Output: null
```

### Pattern Recognition
Floyd's algorithm Phase 1 (detection) followed by Phase 2 (entry point location) — the mathematical relationship `μ = n·λ - d` guarantees that resetting one pointer to the head and advancing both at speed 1 causes them to converge at the cycle entry.

### Key Insight
At the Phase 1 meeting point, the distance from the head to the cycle entry (`μ`) equals the distance from the meeting point to the cycle entry measured forward around the cycle (`n·λ - d`). So one pointer starting at the head and one starting at the meeting point, both moving at speed 1, travel equal distances to reach the entry — arriving simultaneously.

### Approach
**Phase 1**: run Floyd's detection (slow at speed 1, fast at speed 2). If fast exits the list, return null (no cycle). Note the meeting point. **Phase 2**: reset slow to head (fast stays at meeting point). Advance both at speed 1. The node where they meet again is the cycle entry.

### Solution

```js
function detectCycle(head) {
  let slow = head;
  let fast = head;

  // Phase 1: detect cycle, find meeting point
  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) break; // meeting point found
  }

  // No cycle: fast exited the list
  if (fast === null || fast.next === null) return null;

  // Phase 2: find cycle entry
  // Reset slow to head; fast stays at meeting point
  slow = head;
  while (slow !== fast) {
    slow = slow.next; // both move 1 step at a time
    fast = fast.next;
  }

  return slow; // cycle entry node
}
```

### Dry Run

```
List: head → A(3) → B(2) → C(0) → D(-4) → B(2) [cycle]
μ = 1 (tail length: just node A before cycle entry B)
λ = 3 (cycle: B → C → D → B)

Phase 1 — find meeting point:
slow=A, fast=A
Step 1: slow=B, fast=C
Step 2: slow=C, fast=B  (fast: C→D→B)
Step 3: slow=D, fast=D  (fast: B→C→D, slow: C→D)
Meeting point: D

Verify math: μ=1, λ=3, d=distance from entry B to meeting D = 2
μ = n·λ - d → 1 = 1·3 - 2 = 1 ✓

Phase 2 — find entry point:
slow=A (reset to head), fast=D (stays at meeting point)
Step 1: slow=B, fast=B  (fast: D→B)
slow === fast → return B ✓ (node with value 2)
```

### Complexity
- Time: O(n) — Phase 1 takes at most `μ + λ` steps; Phase 2 takes exactly `μ` steps; both bounded by `n`.
- Space: O(1) — two pointer variables.

### Edge Cases
- No cycle: Phase 1 exits via the loop guard; null check immediately returns null.
- Cycle starts at head (μ=0): Phase 1 meets at some point inside the cycle (d steps from head, which is also the entry). Phase 2: slow resets to head (which is the entry). Fast starts at meeting point, `μ=0` steps from entry — fast is already `λ - d` steps ahead in the cycle. After 0 steps... wait: μ=0 means slow (at head=entry) and fast (at meeting point) will meet when fast travels `n·λ - d = 0·λ - 0 = 0` more steps? Actually μ=0 means slow reaches entry immediately, and fast (at meeting point, which is `d` steps past entry) needs `λ - d` more steps — they meet when fast has gone `λ - d` steps and slow has gone `λ - d = μ - d + λ` steps... reconsidering: when μ=0, Phase 2 terminates immediately (`slow = head = entry`, and fast must eventually reach `head` too, which it does in `λ - d` steps; but slow also advances — they meet at entry after `μ = 0`... the Phase 2 loop condition `slow !== fast` checks if `head === meetingPoint` first; if μ=0, the meeting point is at position `2μ mod λ = 0` inside the cycle, which is the entry itself — so `slow = head = entry = fast` immediately and Phase 2 returns head correctly).
- Single node with self-loop: Phase 1 detects cycle immediately (step 1: slow=head, fast=head.next.next=head; they meet). Phase 2: slow=head, fast=head → already equal → return head.

### Follow-up Questions
- "Why reset slow to head rather than fast?" → Either pointer could be reset; by convention slow is reset (and fast stays) since fast might be several laps ahead and resetting either to head produces the same Phase 2 convergence. Resetting fast to head works identically.
- "Does Phase 2 still work if n > 1 (fast went around the cycle multiple times)?" → Yes — the proof holds for any `n ≥ 1`: `μ = n·λ - d` for the appropriate `n`, and Phase 2 still converges in `μ` steps.

## Problem 3 — Happy Number

### Problem
Write an algorithm to determine if a number `n` is "happy." A happy number is defined by: starting with any positive integer, replace the number by the sum of the squares of its digits, and repeat until the number equals 1 (happy) or it loops endlessly in a cycle that does not include 1 (not happy). Return `true` if `n` is a happy number and `false` if not.

```
Input:  n = 19
Output: true
  19 → 1²+9²=82 → 8²+2²=68 → 6²+8²=100 → 1²+0²+0²=1 ✓

Input:  n = 2
Output: false
  2 → 4 → 16 → 37 → 58 → 89 → 145 → 42 → 20 → 4 (cycle back to 4, never reaches 1)
```

### Pattern Recognition
Floyd's cycle detection on an implicit functional sequence — the digit-square-sum function defines a "next" for every integer; if the sequence doesn't reach 1, it must cycle (finite domain); Floyd's detects the cycle in O(1) space vs. O(n) for a HashSet of seen values.

### Key Insight
Any sequence produced by iterating `digitSquareSum` on a positive integer either terminates at 1 (happy) or enters a cycle not including 1 (not happy). Floyd's algorithm discriminates between these two outcomes: if the fast pointer reaches 1, the number is happy; if slow and fast meet at any value ≠ 1, a non-1 cycle exists — not happy. The meeting at 1 is a fixed point (`digitSquareSum(1) = 1`), so once 1 is reached, both pointers stay there and the meeting condition `slow === fast` is eventually satisfied at 1.

### Approach
Define `getNext(n)` = sum of squares of digits of `n`. Initialize `slow = n`, `fast = getNext(n)` (fast starts one step ahead to handle the `do...while` loop cleanly). Loop: advance slow by 1 application of `getNext`, fast by 2. When `slow === fast`: return `slow === 1`.

### Solution

```js
function isHappy(n) {
  function getNext(num) {
    let sum = 0;
    while (num > 0) {
      const digit = num % 10;
      sum += digit * digit;
      num = Math.floor(num / 10);
    }
    return sum;
  }

  let slow = n;
  let fast = getNext(n); // fast starts 1 step ahead

  // Advance until pointers meet (cycle detected or fixed point at 1 reached)
  while (fast !== 1 && slow !== fast) {
    slow = getNext(slow);       // 1 step
    fast = getNext(getNext(fast)); // 2 steps
  }

  // If fast reached 1, sequence terminates happily
  // If slow === fast (and neither is 1), a non-1 cycle was detected
  return fast === 1;
}
```

### Dry Run

```
n = 19
getNext(19) = 1² + 9² = 1 + 81 = 82

slow=19, fast=82

Iteration 1:
  slow = getNext(19) = 82
  fast = getNext(getNext(82)) = getNext(68) = 100
  slow=82, fast=100. slow≠fast, fast≠1.

Iteration 2:
  slow = getNext(82) = 68
  fast = getNext(getNext(100)) = getNext(1) = 1
  fast === 1 → exit loop

return fast === 1 → true ✓

---

n = 2
slow=2, fast=getNext(2)=4

Iteration 1:  slow=getNext(2)=4,  fast=getNext(getNext(4))=getNext(16)=37
Iteration 2:  slow=getNext(4)=16, fast=getNext(getNext(37))=getNext(58)=89
Iteration 3:  slow=getNext(16)=37, fast=getNext(getNext(89))=getNext(145)=42
Iteration 4:  slow=getNext(37)=58, fast=getNext(getNext(42))=getNext(20)=4
Iteration 5:  slow=getNext(58)=89, fast=getNext(getNext(4))=getNext(16)=37
Iteration 6:  slow=getNext(89)=145, fast=getNext(getNext(37))=getNext(58)=89
Iteration 7:  slow=getNext(145)=42, fast=getNext(getNext(89))=getNext(145)=42
  slow===fast (both=42), fast≠1 → exit loop

return fast === 1 → false ✓
```

### Complexity
- Time: O(log n) per `getNext` call (number of digits = O(log n)); O(log n × cycle_length) overall. For practical integer sizes, this is effectively O(log n) since the cycle length is bounded by the number of distinct values the sequence can take (which is small — all unhappy numbers cycle through a set of at most 8 numbers including 4).
- Space: O(1) — two integer variables only, vs. O(log n) for a HashSet of seen values.

### Edge Cases
- `n = 1`: fast = `getNext(1)` = 1; loop condition `fast !== 1` immediately false; return `fast === 1` → true.
- `n = 4`: fast = `getNext(4)` = 16; eventually slow and fast meet in the unhappy cycle; return false.
- Large `n`: `getNext` rapidly reduces `n` to a small number (e.g., any number < 1000 maps to a value ≤ 3×81 = 243 on the first step); the sequence stabilizes quickly.

### Follow-up Questions
- "Solve with a HashSet instead?" → `const seen = new Set(); while (n !== 1) { if (seen.has(n)) return false; seen.add(n); n = getNext(n); } return true;` — O(n) space where n is the cycle length (bounded by constant for this problem, so also effectively O(1) space in practice, but semantically O(n)).
- "Find the cycle entry (the first number that repeats)?" → Apply Floyd's Phase 2 after Phase 1 meeting — same math as linked list cycle entry, treating `getNext` as the "next pointer."

## Problem 4 — Find the Duplicate Number

### Problem
Given an array `nums` containing `n+1` integers where each integer is in the range `[1, n]` inclusive, there is exactly one repeated number. Find and return this duplicate without modifying the array and using only O(1) extra space.

```
Input:  nums = [1, 3, 4, 2, 2]
Output: 2

Input:  nums = [3, 1, 3, 4, 2]
Output: 3
```

### Pattern Recognition
Floyd's cycle detection on an implicit linked list — treat each index as a node and `nums[index]` as the "next pointer." The duplicate value creates two indices pointing to the same "next" node, forming a rho-shaped graph where the cycle entry is the duplicate value.

### Key Insight
The array indices `0..n` and values `1..n` define a function `f(i) = nums[i]`. Starting from index 0 (the "head" — note index 0 can never be pointed to since all values are in `[1..n]`), the sequence `0, nums[0], nums[nums[0]], ...` forms a rho-graph. The duplicate value `d` is the cycle entry: two different indices `i` and `j` both have `nums[i] = nums[j] = d`, meaning two arrows point to node `d` — exactly the structure that creates a cycle entry. Floyd's Phase 2 finds `d` without modifying the array or using extra space.

### Approach
Treat index traversal as a linked list: `slow = nums[slow]`, `fast = nums[nums[fast]]`. **Phase 1**: run until `slow === fast` (meeting inside cycle). **Phase 2**: reset slow to `nums[0]` (the head's first step — index 0 is the "pre-head," its next is `nums[0]`); advance both slow and fast one step at a time until they meet. The meeting point is the duplicate.

### Solution

```js
function findDuplicate(nums) {
  // Phase 1: find the meeting point inside the cycle
  // Start both pointers at the "head" position (index 0's next = nums[0])
  let slow = nums[0];
  let fast = nums[0];

  do {
    slow = nums[slow];           // one step
    fast = nums[nums[fast]];     // two steps
  } while (slow !== fast);

  // Phase 2: find the cycle entry (= the duplicate value)
  slow = nums[0]; // reset slow to start
  while (slow !== fast) {
    slow = nums[slow]; // both move one step
    fast = nums[fast];
  }

  return slow; // cycle entry = duplicate number
}
```

### Dry Run

```

Indices:  0  1  2  3  4
Values:   1  3  4  2  2

Implicit linked list (index → nums[index]):

                ↑       ↓
                └───────┘
Cycle entry (duplicate): 2

  fast = nums[nums[1]] = nums[3] = 2
  slow(3) ≠ fast(2) → continue

do-while step 2:
  slow = nums[3] = 2
  fast = nums[nums[2]] = nums[4] = 2
  slow(2) === fast(2) → exit

Meeting point: 2

slow = nums[0] = 1  (reset)
fast = 2            (stays at meeting point)

Step 1: slow = nums[1] = 3, fast = nums[2] = 4

```

### Complexity
- Time: O(n) — Phase 1 and Phase 2 each traverse at most O(n) steps (the rho-graph has at most n+1 nodes).
- Space: O(1) — two integer variables. No array modification. Satisfies all constraints.

### Edge Cases
- Duplicate appears more than twice: still a valid rho-graph — multiple indices pointing to the same value still creates exactly one cycle entry. Floyd's finds it correctly.
- Duplicate is the smallest value (1): the cycle entry detection still works — `μ` and `λ` are determined by the structure, not the value.
- Array of size 2 (`[1,1]`): `slow = fast = nums[0] = 1`. Phase 1: `slow = nums[1] = 1`, `fast = nums[nums[1]] = nums[1] = 1`; immediately `slow === fast`. Phase 2: `slow = nums[0] = 1`, `fast = 1`; immediately equal → return 1.

### Follow-up Questions
- "Why can't you use O(n) space?" → The problem explicitly requires O(1) extra space (no hash set, no copy of the array). Floyd's is the canonical O(1)-space solution; the only alternatives (binary search on value range, bit manipulation) are less intuitive.
- "Can you solve it if multiple values are duplicated?" → Floyd's finds exactly one cycle entry. With multiple duplicates, there are multiple cycle entries and the rho-shape assumption breaks — this problem variant requires a different approach (e.g., sort + scan, or counting sort if modification is allowed).
- "What if the values were in range [0, n-1] instead of [1, n]?" → Index 0 could now be pointed to by some node, making 0 a valid cycle participant rather than just the pre-head. The algorithm would need a virtual pre-head (starting at a conceptual index -1), or an adjusted starting point — the same mathematical logic applies with the range shift.

## Quick Reference — Cycle Detection Pattern Decision Tree

```
What kind of cycle detection does this problem require?
│
├── LINKED LIST — does this singly linked list have a cycle?
│   ├── Just detection (true/false) → Floyd's Phase 1 only
│   │   slow=head, fast=head; advance 1/2; return slow===fast on meeting
│   │
│   ├── Find cycle ENTRY NODE → Floyd's Phase 1 + Phase 2
│   │   Phase 2: reset slow to head, advance both by 1 until slow===fast
│   │
│   └── Find cycle LENGTH → Floyd's Phase 1, then count from meeting point
│       Fix one pointer at meeting, advance other until return; count steps
│
├── IMPLICIT LINKED LIST (array, functional sequence)
│   ├── Does sequence f(x), f(f(x)),... cycle? → Floyd's on f as "next pointer"
│   │   (happy number, LCG period detection, Pollard's rho)
│   │
│   ├── Find duplicate in [1..n] array of size n+1 → Floyd's on index→value
│   │   Treat nums[i] as "next pointer" from index i; Phase 2 finds duplicate
│   │
│   └── Circular array loop → Floyd's with direction-consistency check
│       next(i) = (i + nums[i]) % n; validate all steps are same direction
│
├── DIRECTED GRAPH — does this directed graph contain a cycle?
│   └── DFS with 3-color marking (WHITE/GRAY/BLACK)
│       GRAY neighbor during DFS = back edge = cycle
│       Floyd's does NOT apply: nodes may have multiple outgoing edges
│
├── UNDIRECTED GRAPH — does this undirected graph contain a cycle?
│   └── DFS with parent tracking
│       Visited non-parent neighbor = back edge = cycle
│       Floyd's does NOT apply: bidirectional edges create trivial 2-cycles
│
└── WHICH SPACE CONSTRAINT APPLIES?
    ├── O(1) space required → Floyd's algorithm (or Brent's for functional sequences)
    └── O(n) space acceptable → HashSet of visited nodes (simpler, gives entry directly)
```

## Common Bugs Checklist

Before submitting any cycle detection solution, verify:

1. **Loop guard checks both `fast` AND `fast.next`?** — `while (fast && fast.next)` is required for linked list traversal. Checking only `fast` allows `fast.next.next` to dereference `null.next` when the list has even length (fast lands exactly on null) — a null pointer exception that passes some tests and fails others depending on list length parity.

2. **Phase 1 and Phase 2 use different speeds?** — Phase 1: fast moves 2 steps, slow moves 1. Phase 2: *both* move 1 step. A common bug is leaving fast at 2-step speed in Phase 2, which breaks the convergence proof (`μ = n·λ - d` only holds when both pointers move at speed 1 in Phase 2).

3. **The cycle entry check handles the case where the loop exits via the guard vs. via the `break`?** — After the Phase 1 loop, explicitly check `if (fast === null || fast.next === null) return null` before proceeding to Phase 2. If the loop exits because fast reached null (no cycle), attempting Phase 2 with a null `fast` pointer causes a null dereference.

4. **`slow === fast` comparison uses reference equality (node identity), not value equality?** — Two distinct nodes can hold the same value — comparing values would produce false positives. Compare node references/pointers: `slow === fast` in JS (object reference equality), not `slow.val === fast.val`.

5. **Happy number / functional sequence: fast starts at `getNext(n)`, not `n`?** — If both slow and fast start at `n`, the `do...while` loop's condition is checked after the first step, correctly. But using `while (slow !== fast)` as the loop form requires fast to start one step ahead (`fast = getNext(n)`) to avoid immediately exiting with `slow === fast === n` on the first check. The two loop forms (`do...while` vs. `while`) require different initializations — mixing them produces an immediate false exit.

6. **Find duplicate in array: Phase 2 resets slow to `nums[0]`, not `0`?** — In the "find duplicate" problem, the "head" is conceptually index 0, and the first step is `nums[0]`. Resetting slow to `0` (the index) instead of `nums[0]` (the value, which is the first node in the implicit list) puts the pointer one step behind where it should be, causing Phase 2 to return the wrong value. The pre-head is index 0; the actual start of the sequence is `nums[0]`.

7. **Circular array loop: using `%` correctly for negative numbers?** — In languages where `%` can return negative values for negative operands (C, Java, JavaScript), `(i + nums[i]) % n` can be negative. Use `((i + nums[i]) % n + n) % n` to ensure the result is always in `[0, n-1]`.

8. **DFS cycle detection in directed graphs: using 3 colors, not 2?** — A 2-color (visited/unvisited) DFS marks nodes as visited when first encountered and never revisits them. This misses back edges to nodes still on the recursion stack — a node can be "visited" (fully explored in a prior DFS subtree) without being on the current path. The GRAY state specifically tracks "currently on the DFS stack" vs. BLACK ("fully explored, not on current stack"), and only GRAY-to-GRAY edges are cycles.
