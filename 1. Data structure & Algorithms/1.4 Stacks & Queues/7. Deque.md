## Topic A: The Monotonic Deque

### Section A1: Fundamentals

**Q1. What is a monotonic deque, and what invariant does it maintain?**

A: A monotonic deque is a double-ended queue whose elements are kept in strict monotone order at all times — either strictly decreasing (a "max deque," for window maximums) or strictly increasing (a "min deque," for window minimums). For the sliding window maximum: the deque holds indices of *candidate* elements — those that have not yet been permanently eliminated from future window maximums. The invariant is: *every element in the deque is a potential answer for some future window, and they are ordered from largest to smallest value front-to-back*. An element is permanently eliminated not when the window slides past it (that's handled separately by front eviction) but when a newer, larger element arrives — because a later element with a larger or equal value can never be beaten by the older one for any window that contains both, and the later element always expires later.

```
nums = [3, 1, 5, 2, 4], window k=3, using a max deque:

After index 0: deque indices=[0],  values=[3]   ← 3 is candidate
After index 1: deque indices=[0,1],values=[3,1]  ← 1 is candidate (3 might be window max; 1 may be max after 3 expires)
After index 2: deque indices=[2],  values=[5]    ← 5 evicts 3 and 1 from back (both ≤ 5, both permanently useless)
Invariant: deque values are always strictly decreasing front → back ✓
```

**Q2. Why must the deque store indices rather than values?**

A: Two independent reasons. First, window expiry is enforced by *index distance*, not by value — to evict an element that has slid out of a k-wide window, you need to know its position: `i - deque[0] >= k` means the front element is out of range. Storing only the value gives you "there is a 9 somewhere in the deque" but not "that 9 is at index 2 and should be evicted now that i=5 and k=3." Second, some problems require the *position* of the maximum (not just its value) as part of the answer — storing indices makes the value retrievable (`nums[deque[0]]`) while the reverse (recovering the index from the value) is not possible without extra bookkeeping. The rule: *store index; compare by value; evict by index distance*.

```
Storing values:                          Storing indices:
deque = [9, 7, 3]                        deque = [2, 4, 6]   (indices; window k=4)
Window slides to [3..6]:                 Window slides to [3..6]:
  Is 9 still in window? → impossible    Is nums[2]=9 in window? 3-2=1... 1<4 → YES, keep
  Is 7 still in window? → impossible    Is nums[4]=7 in window? 3-4 → wait, 4≥3 → YES, keep
  → cannot enforce window boundary ✗    → front eviction: while deque[0] < 3: shift ✓
```

**Q3. What are the two eviction operations, which end does each occur at, and what does each enforce?**

A: Two evictions, two ends, two separate invariants — never confuse them:

**Back eviction** (enforces monotonicity): before pushing index i, pop from the *back* any index j where `nums[j] ≤ nums[i]`. These elements are *permanently discarded* — for any future window containing both j and i, nums[i] is at least as large as nums[j] and always expires later (since i > j), so nums[j] can never be the maximum. This enforces the decreasing order invariant.

**Front eviction** (enforces window bounds): after pushing i, pop from the *front* any index j where `j < i - k + 1` (equivalently `i - j >= k`). These elements were genuine candidates in their time but have now aged out of the window. Unlike back-evicted elements, they may have been the window maximum during their validity.

The canonical processing order for each index i is strictly: back evict → push → front evict → read answer.

```
For each index i:
  Step 1 (back evict):   while deque.length && nums[deque.at(-1)] <= nums[i]: deque.pop()
  Step 2 (push):         deque.push(i)
  Step 3 (front evict):  while deque[0] < i - k + 1: deque.shift()
  Step 4 (read answer):  deque[0] is the index of the window [i-k+1..i]'s maximum
                         (only emit once i >= k-1, i.e., the window is fully formed)

Back eviction: permanent removal (dominated by newer element)
Front eviction: temporal removal (valid in past, expired now)
```

**Q4. What is the amortized O(n) argument, and why does the inner while loop not produce O(nk) time?**

A: Each element has exactly two events in its lifetime: it is pushed to the deque exactly once, and it is popped from the deque at most once — either via back eviction (dominated by a newer element) or front eviction (aged out of the window), never both. Over n elements processed, the total number of push operations is exactly n, and the total number of pop operations is at most n (no element is popped more than once). The inner while loop in back eviction can run many times for a single element, but the *aggregate* number of iterations of that loop across all n elements is bounded by n — because each iteration removes one element from the deque, and each element was pushed at most once. Therefore total time = O(2n) = O(n). This is the same amortized argument as for a monotone stack.

```
Each element's deque lifetime:
  push:      exactly once
  pop:       at most once (back eviction OR front eviction, never both)

Across n elements:
  Total pushes   = n
  Total pops     ≤ n
  Total ops      = O(2n) = O(n) ✓

Naive per-window scan: O(k) per window × O(n) windows = O(nk)  ✗
Max-heap (lazy):       O(log k) per element × O(n) elements = O(n log k) ✗
Monotone deque:        O(1) amortized per element × n elements = O(n) ✓
```

**Q5. What is the "useless element" insight — the logical reason an element can be permanently discarded on back eviction?**

A: Suppose element at index j (value `v_j`) is in the deque, and a new element at index i > j arrives with value `v_i ≥ v_j`. Consider any future window `[L, R]` where both j and i are included (L ≤ j < i ≤ R). In this window, nums[i] = v_i ≥ v_j = nums[j], so j can never be the window maximum while i is present. Now consider a future window `[L', R']` where j is included but i has already expired (L' > i). But i > j, so if i has expired (L' > i > j), then j has also expired (L' > j) — j cannot appear in such a window. In every possible future window, j is either dominated by i (and thus not the max) or has already expired (and is not in the window at all). Neither scenario allows j to be the window maximum. Therefore j is permanently useless and can be discarded immediately when i arrives.

```
Future window [L, R]:
  Case 1: both j and i in window (L ≤ j < i ≤ R):
    nums[i] ≥ nums[j] → i dominates j → j is not the window max ✗
  Case 2: only j in window (i has expired, L > i):
    i > j and L > i → L > j → j also expired → j not in window ✗
  Case 3: only i in window (j has expired):
    j is not in window → j cannot be the max → j already irrelevant

In NO future window can j be the maximum → permanently discard ✓
```

**Q6. What is the strict-vs-non-strict comparison subtlety in back eviction, and does it matter for correctness?**

A: The back eviction comparison is `nums[deque.at(-1)] <= nums[i]` (evict on ≤) in most implementations. Using `<` (strictly less than) would *keep* equal-valued elements in the deque — two indices with the same value would both remain. This is *technically* correct for the maximum value answer (both give the same maximum), but it causes a subtle issue: the deque can grow larger than necessary, and in problems requiring the *index* of the maximum, the front might hold an older equal-value element that should have been replaced. Using `<=` is standard: it keeps the deque as small as possible by evicting duplicates, and it ensures the front always holds the *most recent* occurrence among tied maximums — which is the better tie-breaking choice for window-expiry purposes (a more recent equal element expires later, keeping the deque valid longer). Use `<=` as the default unless the problem specifically rewards keeping older occurrences.

**Q7. What is the monotone deque for sliding window minimum, and how does it differ from sliding window maximum?**

A: The minimum deque is the exact dual of the maximum deque: maintain an *increasing* order (smallest at the front), and back-evict elements that are *greater than or equal to* the incoming element. The logic mirrors exactly: for any future window containing both an older larger element j and a newer smaller element i (nums[j] ≥ nums[i], j < i), j can never be the window minimum, so j is permanently useless. The implementation changes exactly one comparison: `<=` for max (evict when back value ≤ new value) becomes `>=` for min (evict when back value ≥ new value). Everything else — index storage, front eviction by window bounds, amortized O(n) argument, processing order — is identical. Problems 1438 (Longest Continuous Subarray with Absolute Diff ≤ Limit) maintains both a max deque and a min deque simultaneously to track the window's range in O(1).

```
Max deque invariant: values strictly DECREASING front→back
  Back evict when: nums[back] <= nums[i]   (evict smaller-or-equal values)
  Front = window MAXIMUM

Min deque invariant: values strictly INCREASING front→back
  Back evict when: nums[back] >= nums[i]   (evict larger-or-equal values)
  Front = window MINIMUM
```

**Q8. Deque vs max-heap for sliding window problems — when does each win?**

A: Max-heap: O(log n) per push, O(log n) per lazy pop, O(n log k) total. Handles variable window sizes (window grows and shrinks arbitrarily). Advantage: general-purpose; works when the window is not defined by a fixed index offset. Disadvantage: suboptimal time; lazy deletion requires bookkeeping (storing expiry indices alongside values).

Monotone deque: O(1) amortized per element, O(n) total. Requires that elements are processed in order and window slides uniformly forward — the "permanently useless" argument is valid because the stream is monotonically advancing. Advantage: optimal time; clean code with no lazy deletion needed. Disadvantage: only correct when the window boundary moves monotonically rightward (both left and right boundaries only advance, never retreat).

```
Fixed k-size window, left boundary = i-k+1 (advances each step):
  → Deque ✓ O(n) — both boundaries advance monotonically

Variable window, right expands AND left can retreat:
  → Heap or segment tree — deque front-eviction doesn't apply

Variable window but left boundary only advances (two-pointer style):
  → Deque still works if element comparison order is maintained

Offline, unsorted windows:
  → Segment tree or sparse table for O(1) range max queries
```

**Q9. What is the correct processing order when the window answer is needed immediately at each step (before back eviction)?**

A: This is a subtle ordering trap. The standard order (back evict → push → front evict → read) is designed for *fixed-size windows* where the window has exactly k elements at step i. For some problems, the answer for index i must be available before i is added to the deque (e.g., DP problems where `dp[i]` depends on the max of previous dp values in the window, and then `dp[i]` must be added to the deque for future use). In that case: front evict (remove expired old indices) → read answer from `deque[0]` → compute dp[i] using that answer → back evict based on dp[i] value → push i. The dp value being compared during back eviction is `dp[i]`, which depends on the already-computed answer — so back eviction must come *after* the answer is read and dp[i] is computed. This ordering is the key adaptation for DP + deque optimization.

```
Sliding window max (fixed k-size):          DP + deque optimization:
  back evict (nums comparison)                front evict (index range)
  push i                                      read deque[0] → compute dp[i]
  front evict (index range)                   back evict (dp value comparison)
  read answer (deque[0])                      push i
```

### Section A2: Advanced Patterns

**Q10. What is the "prefix sum + monotone deque" pattern, and what problem does it solve that two pointers cannot?**

A: For "shortest subarray with sum ≥ k" with *negative numbers*, two pointers fail because shrinking the window from the left doesn't reliably decrease the sum (a negative element's removal could increase the sum). The prefix-sum deque approach works for any integer array. Define `P[i] = nums[0] + ... + nums[i-1]` (P[0] = 0). A subarray `[j..i-1]` has sum `P[i] - P[j]`. We want `P[i] - P[j] ≥ k` with minimum `i - j`. The deque maintains indices of prefix sums in *increasing order of P value* (a min deque). For each i: front-evict while `P[i] - P[deque[0]] ≥ k` (recording `i - deque.shift()` as a candidate — shortest window ending at i with valid left boundary j); back-evict while `P[deque.at(-1)] ≥ P[i]` (j' with larger P than P[i] is permanently dominated: any future i'' would get a shorter window from i than from j'). Push i. The two eviction rules maintain different invariants: front eviction answers the query and permanently retires used left boundaries; back eviction prunes dominated left boundaries.

```
Key: P[j'] ≥ P[i] with j' < i means i is STRICTLY BETTER as a left boundary than j':
  For any future i'': P[i''] - P[i] ≥ P[i''] - P[j'] (since P[i] ≤ P[j'])  ← i is more likely to satisfy condition
                       i > j' → i'' - i < i'' - j'                          ← i gives shorter subarray

→ j' is permanently dominated → back-evict from deque ✓
```

**Q11. How does the deque identify when a previously valid left boundary becomes permanently retired (front eviction in the prefix-sum pattern)?**

A: When `P[i] - P[deque[0]] ≥ k`, the leftmost index j = deque[0] provides a valid subarray ending at i. We immediately pop j from the front (not just note it) because for any future index i'' > i: `i'' - j > i - j` — using j as the left boundary would give a strictly *longer* subarray than `i - j`. Since we want the *shortest* subarray, j can never improve upon the answer we just recorded. So j is permanently retired as a useful left boundary. We continue popping additional left boundaries from the front while they also satisfy `P[i] - P[deque.front] ≥ k` — each successive pop gives a smaller `i - j` (since deque indices are in increasing order), narrowing the window further. The last valid pair before the front fails the condition is the globally minimum window ending at i.

**Q12. What makes a DP recurrence "deque-optimizable," and what is the canonical form?**

A: A DP recurrence is deque-optimizable when it has the form `dp[i] = max(dp[j] for j in [i-k..i-1]) + cost(i)`, where (1) the range of valid predecessors `[i-k, i-1]` slides forward by 1 each step (fixed window size k in terms of indices), and (2) `cost(i)` depends only on `i`, not on `j` — so maximizing `dp[i]` reduces purely to finding the maximum `dp[j]` in the sliding window. The deque acts as a running max over dp values in the current valid window, yielding O(1) per step instead of the O(k) scan a naive loop would require. The canonical processing order: front-evict expired indices → read `dp[deque[0]]` → compute `dp[i] = dp[deque[0]] + cost(i)` → back-evict indices with `dp ≤ dp[i]` → push i.

```
Naive DP:   dp[i] = max(dp[j] for j in [i-k..i-1]) + cost[i]  → O(nk)
Deque DP:   same recurrence, but deque maintains running max of dp over [i-k..i-1]
            → O(1) per step, O(n) total

Requirement 1: valid j range is a contiguous sliding window of fixed or bounded size
Requirement 2: cost(i) separates cleanly from dp[j] (no dp[j]*f(i) interaction)
If both hold → deque DP optimization applies ✓
```

**Q13. What is the "monotone deque on a geometric expression" pattern, and what transformation enables it?**

A: Some problems ask to maximize `f(i, j)` over pairs `(i, j)` where `|x[i] - x[j]| ≤ k` and all points are sorted by x. The transformation: decompose `f(i, j)` into `g(i) + h(j)` — a part depending only on i and a part depending only on j. For fixed j (the right endpoint), maximizing `f(i, j)` reduces to maximizing `g(i)` over all valid i (satisfying the proximity constraint). This is exactly a sliding window maximum of `g(i)` values, with the "window" defined by coordinate distance rather than index distance. A max deque on `g(i)` values with front eviction when `x[j] - x[deque[0]] > k` solves it in O(n). The key insight is that the problem is only deque-applicable after algebraic decomposition into separable terms — before decomposition, the expression couples i and j, making deque optimization invisible.

```
Example: maximize y[i] + y[j] + |x[j] - x[i]|  where x[j] - x[i] ≤ k (sorted by x, j > i)
  = (y[i] - x[i]) + (y[j] + x[j])
     ↑ depends only on i    ↑ depends only on j

For fixed j: maximize (y[i] - x[i]) over all i with x[j] - x[i] ≤ k
  → max deque on values (y[i] - x[i]), front-evict when x[j] - x[deque[0]] > k ✓
```

**Q14. What is the 2D sliding window maximum, and how does a single dimension reduce to the 1D case?**

A: Given an m×n matrix and a window of size r×c, find the maximum in each r×c submatrix. Naive: O(m·n·r·c). Optimal: apply the 1D sliding window maximum *twice* — once per axis. Step 1: for each *row*, compute the sliding window maximum over windows of width c (O(n) per row using a deque → O(m·n) total). This produces an intermediate matrix where each cell holds the row-wise max. Step 2: for each *column* of the intermediate matrix, compute the sliding window maximum over windows of height r (O(m) per column → O(m·n) total). The result is the 2D sliding window maximum in O(m·n) overall. The correctness argument: `max over r×c submatrix = max over r rows of (max over c columns)` — the row-wise reduction commutes with the column-wise reduction for the maximum operation.

**Q15. What distinguishes a monotone stack from a monotone deque, and which problems require each?**

A: A monotone stack has one operational end — elements enter and exit the same (top) end in LIFO order. It solves "nearest greater/smaller element" problems where each element is waiting to find its answer (the first later element that is larger/smaller), and is discarded once answered. A monotone deque has two operational ends — elements enter at the back, answers are always read from the front, and eviction happens at both ends. It solves sliding window extremum problems where the window *advances* and each element may be the answer for multiple windows before aging out.

```
Monotone Stack — use when:
  "For each element, find the next/previous greater element" (Daily Temperatures, Next Greater Element)
  "Largest rectangle in histogram" — elements wait for right boundary
  No window sliding; element is answered then permanently gone

Monotone Deque — use when:
  "Window of size k slides forward; find running max/min" (Sliding Window Maximum)
  "DP with sliding window predecessor" (Constrained Subsequence Sum)
  "Prefix sum extremum over advancing window" (Shortest Subarray with Sum ≥ k)
  Window slides; element may answer multiple windows; has two independent expiry conditions
```

## Topic B: DP Optimization with Deques

### Section B1: Sliding Window DP

**Q16. In the Constrained Subsequence Sum recurrence, what goes wrong if you apply a naive max-over-window scan?**

A: The recurrence is `dp[i] = nums[i] + max(0, max(dp[j] for j in [i-k..i-1]))`. Naively, for each i, scanning all j in `[i-k..i-1]` to find the maximum dp value is O(k) per element → O(nk) total. With n and k both up to 10^5, O(nk) = O(10^10) — far too slow. The deque reduces the "find max dp in a sliding window" step to O(1) per element, since: (1) the valid j range slides forward by exactly 1 each step (a fixed-k window); (2) the contribution of any j to future dp values is just dp[j] itself (no coupling with i), so a max deque on dp values applies directly. The deque invariant: elements are kept in decreasing order of dp value, so `dp[deque[0]]` is always the maximum dp in the current window.

**Q17. Why must dp[i] be computed BEFORE it is added to the deque in the DP + deque pattern?**

A: `dp[i]` depends on `max(dp[j] for j in [i-k..i-1])` — the deque's front at the moment before i is pushed. If i were pushed first, `deque[0]` might be i itself (if dp[i] is the largest), and reading `dp[deque[0]]` would compute dp[i] in terms of itself — a circular dependency producing a wrong (too large) value. The correct invariant: at the moment dp[i] is computed, the deque contains only indices from `[i-k..i-1]` — strictly before i. Processing order: (1) front-evict expired indices; (2) read `dp[deque[0]]`; (3) compute dp[i]; (4) back-evict dominated dp values; (5) push i. Steps (2) and (3) are before steps (4) and (5) — i is never in the deque when its own dp[i] is computed.

**Q18. What is the "non-negative dp window" optimization in Constrained Subsequence Sum, and why does it not require a second data structure?**

A: The recurrence includes `max(0, ...)` — we only extend from a previous element if doing so improves the sum. This means we never add a negative dp[j] to dp[i]. In deque terms: since we evict from the back any dp values ≤ dp[i] (back eviction), and dp[i] ≥ nums[i] ≥ min(nums), the deque naturally keeps only positive-contribution predecessors at the front. We do not need a separate check or a second deque — the monotone max deque already discards predecessors with dp values below the current dp through back eviction, and the `max(0, dp[deque[0]])` guards against the case where all valid predecessors have negative dp (start fresh from nums[i] alone). The single deque handles both the window bounds (front eviction) and the optimality selection (back eviction + the max-0 guard at read time).

### Section B2: Geometric and Multi-Deque Patterns

**Q19. When does a problem require two simultaneous monotone deques, and what invariant must they jointly maintain?**

A: Two simultaneous deques are needed when the window boundary condition is defined by a *range constraint on the window's content* rather than a fixed index offset — specifically, when the window is "all indices in a shrinking/expanding range where `max - min ≤ limit`." One max deque tracks the window maximum; one min deque tracks the window minimum. The window is valid when `maxDeque[0] - minDeque[0] ≤ limit`. When the condition is violated, the window's left boundary must advance until it's restored — advance `left` past whichever of `maxDeque[0]` or `minDeque[0]` is `left` itself, evicting from both deques' fronts. The joint invariant: at all times, both deques hold only indices in the current valid window, their fronts give the window's running max and min, and the difference between those fronts determines window validity. Neither deque can be maintained independently because advancing the left boundary based on one deque's front requires synchronizing both deques.

**Q20. What is the "sliding window defined by value distance, not index distance" pattern, and how does front eviction adapt?**

A: In Max Value of Equation and similar problems, the "window" of valid left endpoints i for a given right endpoint j is defined not by `j - i ≤ k` (index distance) but by `x[j] - x[i] ≤ k` (coordinate distance, where x is some property stored in the input, not the array index). Front eviction adapts by checking `x[j] - x[deque[0]] > k` (using coordinate distance) instead of `j - deque[0] >= windowSize` (index distance). Since points are given in sorted order of x, the coordinate-based window boundary still advances monotonically — earlier points have smaller x, so once a left endpoint is outside the coordinate window for the current j, it remains outside for all future j' > j. The monotone deque's "permanently useless" argument still holds; only the eviction comparison changes from index arithmetic to coordinate arithmetic.

## Topic C: Cross-Topic & Interview-Style Questions

**Q21. Compare the complement-lookup pattern (Two Sum family) and the monotone deque pattern — what structural property does each exploit?**

A: Complement lookup exploits the property that for each element, its "needed partner" is a *specific fixed value* (`target - x`), making O(1) exact lookup via hashing possible. The HashMap's value at any key is *static* — it was set when the element was first seen and never changes in the query. Monotone deque exploits the property that for any future window, a dominated element can be *permanently discarded*: it exploits irreversibility of the dominance relationship. The deque's content *changes* actively as elements arrive — it is a dynamically maintained set of candidates. The unifying theme: both replace O(n) or O(k) inner scans with O(1) lookups by exploiting a structural property of the problem (exact-complement for hashing; permanent dominance for deque) that allows discarding "useless" work permanently rather than redoing it.

**Q22. "For a sliding window problem, how do you decide between two pointers, deque, segment tree, and heap?"**

A:

| Condition | Tool |
|---|---|
| All elements non-negative; shrink window when sum/count exceeds threshold | Two pointers — O(n), no auxiliary structure |
| Fixed window size k; running max or min needed | Monotone deque — O(n) |
| Variable window; max/min needed; left boundary advances monotonically | Monotone deque — O(n) with two-pointer left management |
| Window shrinks from *both* ends arbitrarily; range max/min needed | Sparse table (offline) or segment tree (online) — O(n) or O(n log n) |
| Window slides forward; max of *arbitrary function* over window elements needed | Heap with lazy deletion — O(n log n) |
| DP where dp[i] = max dp[j] over j in [i-k, i-1] + cost(i) | Monotone deque on dp values — O(n) |

The deque is the right tool when: the window slides *forward only* (both boundaries only advance), and the optimum-of-window problem exploits a dominance relationship (an element made permanently obsolete by a newer one).

**Q23. "Describe the decision process for identifying the deque's comparison direction (max deque vs min deque) and the eviction condition."**

A: Two questions determine the configuration:

(1) **"What am I tracking?"** — If the problem needs the window maximum (largest value dominates), use a max deque (decreasing front to back; back-evict when `nums[back] ≤ nums[i]`). If it needs the window minimum, use a min deque (increasing; back-evict when `nums[back] ≥ nums[i]`). For DP, replace `nums[...]` with `dp[...]`.

(2) **"When does an element become permanently useless?"** — Enumerate the two eviction conditions: (a) back eviction: "a newer element is at least as good at every future step" — evict when the new element dominates the back; (b) front eviction: "the element is out of the current window" — evict when its index (or coordinate) is outside the window boundary. These two conditions are always present; only their specific comparison changes.

```
Problem:                Max deque or min?  Back-evict condition:        Front-evict condition:
Sliding window max      max (decreasing)   nums[back] ≤ nums[i]         deque[0] < i-k+1
Sliding window min      min (increasing)   nums[back] ≥ nums[i]         deque[0] < i-k+1
Constrained subseq sum  max on dp[]        dp[back] ≤ dp[i]             deque[0] < i-k
Shortest subarray ≥ k   min on P[] (incr.) P[back] ≥ P[i]              (answer-based, not simple expiry)
Max value of equation   max on (y[i]-x[i]) (y-x)[back] ≤ (y-x)[i]     x[j]-x[deque[0]] > k
```

**Q24. "In one sentence each, state the invariant the deque maintains for each problem variant."**

A:
- **Sliding Window Maximum**: the deque holds indices of elements in the current and future windows in *decreasing value order*, so `deque[0]` is always the current window's maximum.
- **Shortest Subarray with Sum ≥ k**: the deque holds indices into the prefix sum array in *increasing P-value order*, ensuring each front is the leftmost valid left boundary for the current right endpoint.
- **Longest Subarray with Abs Diff ≤ Limit**: the max deque's front and min deque's front always give the window's current maximum and minimum, and the window shrinks from the left whenever their difference exceeds the limit.
- **Constrained Subsequence Sum**: the deque holds indices of dp values in the current k-window in *decreasing dp-value order*, so `dp[deque[0]]` is always the best predecessor dp in the valid range.
- **Jump Game VI**: the deque holds indices of dp values in the last-k-positions window in *decreasing dp-value order*, so `dp[deque[0]] + nums[i]` is always the optimal score reaching position i.
- **Max Value of Equation**: the deque holds point indices in *decreasing (y[i]-x[i]) order* with coordinate-distance front eviction, so `(y[deque[0]]-x[deque[0]]) + y[j]+x[j]` is always the maximum equation value with right endpoint j.

**Q25. "A candidate writes `deque.push(i)` before the back-eviction while loop. What breaks, and how do you catch it in a dry run?"**

A: Pushing i before back-eviction means i is inserted into the deque *before* elements ≤ nums[i] are removed from the back. When the back-eviction while loop then runs, it may pop i itself if `nums[i] ≤ nums[i]` — since `deque.at(-1) === i` — producing `deque.pop()` on the element just inserted, leaving an empty deque and losing i permanently. Even if the loop condition uses `<` (not `≤`), i remains in the deque but the elements before it are not evicted, breaking the decreasing-order invariant. In a dry run, catch it by tracing the deque state after the push: if the back element after the push equals the new element, and the loop then immediately pops it, i is lost. The fix is always: back-evict *then* push, in that order, with no exception.

```
WRONG (push before back-evict):
  deque = [3, 1], nums[i] = 5.
  deque.push(i=2): deque = [3, 1, 2]         (index 2, value 5)
  while nums[deque.at(-1)] <= 5: deque.pop()  → pops index 2 (5 ≤ 5!), then index 1, then index 0
  deque = []  ← element i=2 was added then immediately lost ✗

CORRECT (back-evict then push):
  deque = [0, 1], nums[i=2] = 5.
  while nums[deque.at(-1)] <= 5: deque.pop()  → pops 1, then 0. deque = []
  deque.push(2): deque = [2]  ← i=2 correctly remains ✓
```

## Problem 1 — Sliding Window Maximum

### Problem

Given an integer array `nums` and an integer `k`, return an array of the maximum value in each contiguous window of size `k` as the window slides from left to right.

```
Input:  nums = [1, 3, -1, -3, 5, 3, 6, 7], k = 3
Output: [3, 3, 5, 5, 6, 7]
          ↑           ↑
        [1,3,-1]    [5,3,6]

Input:  nums = [1], k = 1
Output: [1]

Input:  nums = [9, 8, 7, 6], k = 2
Output: [9, 8, 7]
```

### Pattern Recognition
Max monotone deque — maintain a decreasing deque of indices. Back-evict smaller elements (they can never be the max while the current element exists). Front-evict expired indices (they've left the window). The front is always the current window maximum.

### Key Insight
When a new element `nums[i]` arrives, any earlier element with value ≤ `nums[i]` is permanently useless: for any future window containing both, `nums[i]` wins; once `nums[i]` has itself expired, the smaller element is even older and has already expired too. So evict them immediately and irreversibly, leaving only elements that could be a future window max in strictly decreasing order.

### Approach
For each index `i`: back-evict while `nums[deque.at(-1)] <= nums[i]`; push `i`. Front-evict while `deque[0] < i - k + 1`. Emit `nums[deque[0]]` once `i >= k - 1` (window is full).

### Solution

```js
function maxSlidingWindow(nums, k) {
  const deque = []; // indices; values are strictly decreasing front → back
  const result = [];

  for (let i = 0; i < nums.length; i++) {
    // Back eviction: remove all indices whose values are ≤ nums[i]
    // They are permanently useless — nums[i] dominates them
    while (deque.length && nums[deque.at(-1)] <= nums[i]) {
      deque.pop();
    }

    deque.push(i); // nums[i] is now the smallest in the deque (at the back)

    // Front eviction: remove the oldest element if it's outside the window
    if (deque[0] < i - k + 1) {
      deque.shift();
    }

    // Emit answer once the first full window is formed
    if (i >= k - 1) {
      result.push(nums[deque[0]]); // deque[0] is always the window maximum
    }
  }

  return result;
}
```

### Complexity
- Time: O(n) — each element is pushed exactly once and popped at most once; O(2n) total deque operations.
- Space: O(k) — the deque holds at most k indices at any moment (front eviction ensures this).

### Edge Cases

- "Running max of the entire array (no window expiry)?" — Remove the front eviction; the deque becomes a pure monotone stack with the global running max always at the front.

## Problem 2 — Shortest Subarray with Sum at Least K

### Problem

Given an integer array `nums` and an integer `k`, return the length of the shortest non-empty contiguous subarray whose sum is at least `k`. If no such subarray exists, return -1. Note: `nums` may contain *negative* numbers.

```
Input:  nums = [1], k = 1         → 1
Input:  nums = [1, 2], k = 4      → -1
Input:  nums = [2, -1, 2], k = 3  → 3  // [2,-1,2] = 3
Input:  nums = [1,-1,5,-2,3], k=3 → 1  // [5]
```

### Pattern Recognition
Prefix sum + min monotone deque (increasing P values front-to-back). For each right endpoint i (index into P), query the deque for the largest valid left endpoint j satisfying `P[i] - P[j] ≥ k` by front-evicting while the condition holds, recording each `i - j` as a candidate answer.

### Key Insight
Prefix sum transforms the subarray problem into: "find the pair (i, j) with j < i, P[i] - P[j] ≥ k, and minimum i - j." The min deque on P values ensures: (a) we always try the *leftmost* valid j first (giving the longest valid window ending at i — pop and try the next, closer j for shorter candidates); (b) any j' with P[j'] ≥ P[i] is permanently dominated by i as a left boundary, since i gives a tighter prefix sum gap and a shorter window for all future right endpoints.

### Approach
Compute prefix sums P[0..n]. Process i from 0 to n: front-evict while `P[i] - P[deque[0]] ≥ k` (recording and popping — each popped j cannot give a shorter window for any future i); back-evict while `P[deque.at(-1)] ≥ P[i]` (j' with larger P than P[i] is permanently dominated); push i. Return min recorded length or -1.

### Solution

```js
function shortestSubarray(nums, k) {
  const n = nums.length;
  const P = new Array(n + 1).fill(0);
  for (let i = 0; i < n; i++) P[i + 1] = P[i] + nums[i]; // prefix sums

  const deque = []; // indices into P; P values are increasing front→back (min deque)
  let ans = Infinity;

  for (let i = 0; i <= n; i++) {
    // Front eviction + answer accumulation:
    // While the leftmost j gives P[i] - P[j] ≥ k, record i-j and retire j permanently
    // (any future i' > i would give a LONGER window using the same j)
    while (deque.length && P[i] - P[deque[0]] >= k) {
      ans = Math.min(ans, i - deque.shift());
    }

    // Back eviction: P[j'] ≥ P[i] means i is a strictly better left boundary than j'
    // (same or smaller prefix sum, more rightward → i gives shorter, at-least-as-valid windows)
    while (deque.length && P[deque.at(-1)] >= P[i]) {
      deque.pop();
    }

    deque.push(i);
  }

  return ans === Infinity ? -1 : ans;
}
```

### Complexity
- Time: O(n) — each prefix sum index is pushed and popped at most once across the entire loop; total deque operations ≤ 2(n+1).
- Space: O(n) — the prefix sum array P has n+1 entries; the deque holds at most n+1 indices.

### Edge Cases
- All negative numbers: no subarray can sum to a positive k → return -1. No front eviction ever fires (P[i] is always decreasing, so P[i] - P[j] ≤ 0 for i > j); ans remains Infinity.
- k = 0 or negative: if k ≤ 0, any single non-negative element (or even a zero-length subarray in some formulations) satisfies it. Standard problem assumes k > 0; guard with immediate return of 1 (any single element ≥ k trivially).
- Entire array sums to k: recorded at i=n when j=0 is front-evicted; length = n.
- Single large element ≥ k: P[1]-P[0] = nums[0] ≥ k at i=1; length = 1.

### Follow-up Questions
- "Why doesn't two pointers work here?" — Two pointers require that adding right elements only increases the sum and removing left elements only decreases it — a property that fails with negatives. A window could become valid only after including a negative that makes a later addition push over k. The prefix sum + deque handles this correctly.
- "Longest subarray with sum ≤ k?" — Reverse roles: look for P[i] - P[j] ≤ k → find the max i-j where P[j] ≥ P[i] - k. This is achievable with a sorted structure (BST or sorted list) rather than a simple deque, since back eviction no longer applies cleanly.

## Problem 3 — Longest Continuous Subarray with Absolute Diff ≤ Limit

### Problem

Given an integer array `nums` and an integer `limit`, return the size of the longest non-empty subarray such that the absolute difference between any two elements is at most `limit`.

```
Input:  nums = [8, 2, 4, 7], limit = 4   → 2    // [2,4] or [4,7] (not [2,4,7]: |7-2|=5>4)
Input:  nums = [10, 1, 2, 4, 7, 2], limit = 5 → 4  // [2,4,7,2]: max=7, min=2, diff=5 ≤ 5
Input:  nums = [4, 2, 2, 2, 4, 4, 2, 2], limit = 0 → 3  // [2,2,2]
```

### Pattern Recognition
Two simultaneous monotone deques (one max deque, one min deque) + two-pointer sliding window. The window `[left, right]` is valid while `maxDeque[0] - minDeque[0] ≤ limit`. When invalid, advance `left` until validity is restored, front-evicting both deques when their front index is evicted.

### Key Insight
The absolute difference between any two elements in a window equals `max(window) - min(window)` — since the extremes bound all pairwise differences. Tracking only the running max and min suffices. The max deque gives O(1) running max; the min deque gives O(1) running min. When their difference exceeds the limit, the window must shrink from the left, incrementing `left` and evicting the front of whichever deque holds the old `left` index.

### Approach
Maintain `maxDeq` (decreasing) and `minDeq` (increasing). For each `right`: update both deques (back-evict, push right). While `nums[maxDeq[0]] - nums[minDeq[0]] > limit`: advance `left` (front-evict from each deque if their front === left). Record `right - left + 1` as a candidate answer.

### Solution

```js
function longestSubarray(nums, limit) {
  const maxDeq = []; // indices; values strictly decreasing → front is window max
  const minDeq = []; // indices; values strictly increasing → front is window min
  let left = 0;
  let ans = 0;

  for (let right = 0; right < nums.length; right++) {
    // Maintain max deque: evict back elements ≤ nums[right]
    while (maxDeq.length && nums[maxDeq.at(-1)] <= nums[right]) maxDeq.pop();
    maxDeq.push(right);

    // Maintain min deque: evict back elements ≥ nums[right]
    while (minDeq.length && nums[minDeq.at(-1)] >= nums[right]) minDeq.pop();
    minDeq.push(right);

    // Shrink window from left until abs diff ≤ limit
    while (nums[maxDeq[0]] - nums[minDeq[0]] > limit) {
      left++;
      if (maxDeq[0] < left) maxDeq.shift(); // max was at evicted left
      if (minDeq[0] < left) minDeq.shift(); // min was at evicted left
    }

    ans = Math.max(ans, right - left + 1);
  }

  return ans;
}
```

## Problem 4 — Constrained Subsequence Sum

### Problem

Given an integer array `nums` and an integer `k`, return the maximum sum of a non-empty subsequence of `nums` such that for every pair of consecutive integers in the subsequence, their indices satisfy `j - i ≤ k`.

```
Input:  nums = [10,2,-10,5,20], k = 2  → 37  // [10,2,5,20]
Input:  nums = [-1,-2,-3], k = 1        → -1  // must take at least one; max single = -1
Input:  nums = [10,-2,-10,-5,20], k = 2 → 23  // [10,-2,-10,-5,20]: nope. [10,20]? |4-0|=4>2. [10,-2,20]? |4-2|=2≤2 → 28? Wait...
                                               // actually: [10,-2,-10,-5,20] with k=2:
                                               // dp[0]=10, dp[1]=max(0,10)+(-2)=8, dp[2]=max(0,8)+(-10)=-2→-2... let's trace
```

### Pattern Recognition
DP + max monotone deque. `dp[i]` = maximum subsequence sum ending at index i. The recurrence `dp[i] = nums[i] + max(0, max(dp[j] for j in [i-k..i-1]))` is a sliding-window maximum of dp values — exactly what a max deque computes in O(1) per step.

### Key Insight
The recurrence says: either start fresh at i (take just nums[i]), or extend from the best predecessor in the last k positions. Since the best predecessor is a *window maximum of dp values* over a sliding window of size k, a max deque on dp values reduces the O(k) predecessor scan to O(1), giving O(n) total instead of O(nk).

### Approach
Initialize `dp` array, `deque = []` of indices into dp. For each i from 0 to n-1: front-evict while `deque[0] < i - k`; compute `dp[i] = nums[i] + max(0, dp[deque[0]] ?? 0)` (if deque is non-empty); back-evict while `dp[deque.at(-1)] <= dp[i]`; push i. Return `max(dp)`.

### Solution

```js
function constrainedSubsetSum(nums, k) {
  const n = nums.length;
  const dp = new Array(n).fill(0);
  const deque = []; // indices into dp; dp values strictly decreasing front→back
  let ans = -Infinity;

  for (let i = 0; i < n; i++) {
    // Front eviction: remove predecessors outside the k-window
    while (deque.length && deque[0] < i - k) deque.shift();

    // Compute dp[i]: extend from best predecessor (if positive), or start fresh
    dp[i] = nums[i] + (deque.length && dp[deque[0]] > 0 ? dp[deque[0]] : 0);

    // Back eviction: dp[i] dominates any predecessor with smaller dp value
    while (deque.length && dp[deque.at(-1)] <= dp[i]) deque.pop();

    deque.push(i);
    ans = Math.max(ans, dp[i]);
  }

  return ans;
}
```

### Complexity
- Time: O(n) — each index pushed and popped from deque at most once.
- Space: O(n) — dp array of size n; deque of at most k indices.

### Edge Cases
- All negative values: the `max(0, ...)` guard means we never extend from a negative predecessor; each `dp[i] = nums[i]`. Answer is the maximum single element.
- `k >= n`: the entire array is within range of any starting point; the problem reduces to "maximum sum subsequence with no gap constraint."
- Single element: `dp[0] = nums[0]`; deque = [0]; answer = nums[0].

### Follow-up Questions
- "Reconstruct the subsequence?" — Alongside dp, maintain `parent[i]` = the index j that maximized dp[i] (-1 if starting fresh). Backtrack from the index achieving the maximum dp.
- "Minimum sum instead of maximum?" — Min monotone deque (increasing), with `min(0, dp[deque[0]])` instead of `max`. Back-evict when back dp >= dp[i].

## Problem 5 — Jump Game VI

### Problem

You are given a 0-indexed integer array `nums` and a positive integer `k`. You start at index 0. In one move you can jump from index `i` to any index in the range `[i+1, min(i+k, n-1)]`. Your score is the sum of all values at visited indices. Return the maximum score you can get.

```
Input:  nums = [1,-1,-2,4,-7,3], k = 2  → 7   // indices 0→1→3→5: 1+(-1)+4+3=7
Input:  nums = [10,-5,-2,4,0,3], k = 3  → 17  // 0→3→5: 10+4+3=17
Input:  nums = [1,-5,-20,4,-1,3,-6,-3], k = 2 → 0 // Forced: 1→3→5→7: 1+4+3+(-3)=5... let me not trace here
```

### Pattern Recognition
DP + max monotone deque. `dp[i]` = maximum score to reach index i. Recurrence: `dp[i] = nums[i] + max(dp[j] for j in [i-k..i-1])`. This is a sliding-window maximum of dp values over a window of size k — structurally identical to Constrained Subsequence Sum but without the `max(0, ...)` guard (you must always jump from somewhere, except at index 0 which is the start).

### Key Insight
The two problems (Jump Game VI and Constrained Subsequence Sum) share the identical DP + deque structure. The difference: in Jump Game VI, you must always jump from a predecessor (the path must be connected — you can't "start fresh" mid-array), so `dp[i] = nums[i] + max(dp[j])` with no `max(0, ...)` guard. In Constrained Subsequence Sum, you could start a new subsequence at any element. The deque structure, processing order, and amortized complexity are identical.

### Approach
`dp[0] = nums[0]`. For i from 1 to n-1: front-evict while `deque[0] < i - k`; `dp[i] = nums[i] + dp[deque[0]]`; back-evict while `dp[deque.at(-1)] <= dp[i]`; push i. Note: push before computing dp[i+1] ensures the window for i+1 includes i.

### Solution

```js
function maxResult(nums, k) {
  const n = nums.length;
  const dp = new Array(n).fill(0);
  dp[0] = nums[0];

  const deque = [0]; // indices; dp values strictly decreasing front→back
  // deque starts with index 0 since dp[0] is the only valid predecessor for i=1..k

  for (let i = 1; i < n; i++) {
    // Front eviction: remove predecessors more than k steps back
    while (deque[0] < i - k) deque.shift();

    // dp[i]: jump from the best reachable predecessor
    dp[i] = nums[i] + dp[deque[0]]; // deque[0] is the index with max dp in [i-k..i-1]

    // Back eviction: new dp[i] dominates any predecessor with dp ≤ dp[i]
    while (deque.length && dp[deque.at(-1)] <= dp[i]) deque.pop();

    deque.push(i);
  }

  return dp[n - 1]; // must reach the last index; return score at the end
}
```

### Complexity
- Time: O(n) — each index pushed and popped at most once.
- Space: O(n) — dp array; deque of at most k indices.

### Edge Cases
- `k >= n - 1`: you can jump directly from 0 to n-1; the problem reduces to choosing the maximum-sum path in one or more jumps across the whole array. The deque window covers the entire previous array.
- All negative values: must traverse the array; pick the path that avoids the worst elements. The deque correctly finds the least-bad predecessor.
- n = 1: return `nums[0]`; start = end; no jumps needed.

### Follow-up Questions
- "Reconstruct the path?" — Maintain `parent[i]` = `deque[0]` at the moment `dp[i]` is computed. Backtrack from n-1 to 0.
- "What if you can also jump backward (to lower indices)?" — The problem structure changes fundamentally; the "window only advances" property breaks, making the deque approach inapplicable. A graph-based approach (e.g., Dijkstra or Bellman-Ford for maximum) would be needed.

## Problem 6 — Max Value of Equation

### Problem

You are given an array `points` containing points on the x-axis, where `points[i] = [x_i, y_i]` and the points are sorted in ascending order of `x_i`. Find the maximum value of `y_i + y_j + |x_i - x_j|` for `i < j` such that `|x_i - x_j| ≤ k`. Return that maximum value or `-1` if no such pair exists.

```
Input:  points = [[1,3],[2,0],[5,10],[6,-10]], k = 1  → 4
  // (i=0,j=1): 3+0+|1-2|=4. (i=2,j=3): 10-10+|5-6|=1. Best=4.
Input:  points = [[0,0],[3,0],[9,2]], k = 3            → 3
  // Only valid pair: (i=0,j=1): 0+0+3=3. (i=1,j=2): 0+2+6>k. Best=3.
```

### Pattern Recognition
Algebraic decomposition + max monotone deque. Decompose `y_i + y_j + (x_j - x_i)` (since `x_j > x_i` for `i < j`, absolute value = `x_j - x_i`) into `(y_i - x_i) + (y_j + x_j)`. For fixed right endpoint j, maximize `(y_i - x_i)` over all valid i with `x_j - x_i ≤ k` using a max deque on `(y - x)` values with coordinate-distance front eviction.

### Key Insight
The expression decouples into a left-side term `(y_i - x_i)` (depends only on i) and a right-side term `(y_j + x_j)` (constant for fixed j). For each j, we need the maximum left-side term among all points i within x-coordinate distance k. This is a sliding window maximum over the `(y - x)` values with window size defined by x-coordinate gap — exactly a max deque with front eviction when `x_j - x_{deque[0]} > k`.

### Approach
For each point j: front-evict while `x_j - x[deque[0]] > k`; if deque non-empty, update `ans = max(ans, (y[deque[0]] - x[deque[0]]) + y_j + x_j)`; back-evict while `(y - x)[deque.at(-1)] <= (y_j - x_j)`; push j. The answer is checked *before* pushing j (j can be the right endpoint but not its own left endpoint).

### Solution

```js
function findMaxValueOfEquation(points, k) {
  // Deque stores indices; values are (y - x), decreasing front→back
  const deque = []; // max deque on (y[i] - x[i])
  let ans = -Infinity;

  for (let j = 0; j < points.length; j++) {
    const [xj, yj] = points[j];

    // Front eviction: left endpoint i must satisfy x_j - x_i ≤ k
    while (deque.length && xj - points[deque[0]][0] > k) deque.shift();

    // If a valid left endpoint exists, update answer
    if (deque.length) {
      const i = deque[0];
      const [xi, yi] = points[i];
      ans = Math.max(ans, (yi - xi) + yj + xj); // (y_i - x_i) + (y_j + x_j)
    }

    // Back eviction: (y_j - x_j) ≥ (y_i - x_i) means i is dominated by j as a left endpoint
    // For any future right endpoint j', using j gives at least as good a (y-x) contribution
    // and j is at least as rightward (so x_{j'} - x_j ≤ x_{j'} - x_i for j > i, but
    // actually j is closer to j', so the coordinate window is LESS restrictive for j too)
    while (deque.length && (points[deque.at(-1)][1] - points[deque.at(-1)][0]) <= (yj - xj)) {
      deque.pop();
    }

    deque.push(j); // j can serve as a left endpoint for future right endpoints
  }

  return ans === -Infinity ? -1 : ans;
}
```

### Complexity
- Time: O(n) — each point pushed and popped from deque at most once; front eviction amortized O(1) per point.
- Space: O(n) — deque holds at most n indices.

### Edge Cases
- No valid pair (all x-distances > k): deque is empty whenever a right endpoint j would query; ans remains -Infinity → return -1.
- All points at the same x-coordinate: all pairs have distance 0 ≤ k (for any k ≥ 0); the deque holds all indices; the front is the index with the largest (y - x) = y (since all x equal).
- `k = 0`: only pairs with `x_i = x_j` are valid, but the problem guarantees strictly increasing x → no valid pair → -1.

### Follow-up Questions
- "Return the pair (i, j) achieving the maximum?" — Record `bestI = deque[0]` alongside updating `ans`. Track `bestJ = j` at the same update.
- "What if points are not sorted?" — Sort by x-coordinate first in O(n log n); then apply the same algorithm. The sort step dominates.

## Quick Reference — Pattern Decision Tree

```
What type of sliding extremum or window-optimum problem is this?
│
├── RUNNING MAX or MIN over a FIXED-SIZE window sliding forward?
│   └── Monotone deque (max or min)
│       Invariant: deque holds indices in strictly decreasing (max) or increasing (min) value order
│       For each index i:
│         back evict: while nums[back] ≤ nums[i] (max) or ≥ (min): pop back
│         push i
│         front evict: while deque[0] < i - k + 1: shift
│         emit: nums[deque[0]] once i ≥ k-1
│
├── VARIABLE window; boundary defined by CONTENT RANGE (max - min ≤ limit)?
│   └── Two simultaneous deques (one max, one min) + two-pointer left boundary
│       max deque front = window max. min deque front = window min.
│       Shrink left while max_front - min_front > limit; front-evict both deques when left passes their front.
│
├── SHORTEST/LONGEST SUBARRAY with SUM CONSTRAINT (array may have negatives)?
│   └── Prefix sum + min monotone deque (increasing P values)
│       P[i] = prefix sum. Want P[i] - P[j] ≥ k with min i-j.
│       front evict: while P[i] - P[deque[0]] ≥ k: record i - shift(), retire j
│       back evict: while P[back] ≥ P[i]: pop (i is a strictly better left boundary)
│       push i
│
├── DP with recurrence dp[i] = max(dp[j] for j in [i-k..i-1]) + cost(i)?
│   └── DP + max deque on dp values
│       Invariant: deque holds indices of dp values in strictly decreasing order
│       For each i:
│         front evict: while deque[0] < i - k: shift
│         read: dp[i] = cost(i) + [max(0, dp[deque[0]]) or dp[deque[0]]]
│         back evict: while dp[back] ≤ dp[i]: pop
│         push i
│       Applications: Constrained Subsequence Sum (max-0 guard), Jump Game VI (no guard)
│
├── MAXIMIZE f(i,j) over pairs with COORDINATE DISTANCE ≤ k?
│   └── Algebraic decomposition + max deque on left-side expression
│       Decompose f(i,j) = g(i) + h(j). For fixed j, maximize g(i) over valid i.
│       Deque on g(i) values; front-evict when x_j - x_{deque[0]} > k.
│       Check answer BEFORE pushing j (j is right endpoint, not its own left endpoint).
│       Applications: Max Value of Equation
│
└── SPACE OPTIMIZATION / ALTERNATIVE approaches:
    ├── Offline, non-sliding windows: sparse table for O(1) RMQ after O(n log n) build
    ├── Window defined by arbitrary intervals: segment tree O(n log n)
    ├── Need max AND frequency: monotone deque + HashMap (rare; problem-specific)
    └── Two pointers instead of deque: only valid when all values ≥ 0 and shrinking window
```

## Common Bugs Checklist

Before submitting any solution from this category, verify:

1. **Back-evict AFTER pushing instead of before?** — Pushing i before back-eviction means i is on the deque when the while loop runs. If `nums[i] ≤ nums[i]` (trivially true), i is immediately popped — the element just added is lost. Always: back-evict → push, in that exact order, no exception.

2. **Front-evict before the push instead of after?** — Front eviction uses the current window bound `i - k + 1`. If front eviction runs before the push of i, the front condition is computed for the window *not yet including i* — this can evict valid elements one step too early, or leave the deque empty when i's answer should reference an element that was evicted prematurely. Standard order: back evict → push → front evict → read answer.

3. **Using `<` instead of `≤` in the back eviction comparison?** — With strict `<`, equal-valued older elements remain in the deque alongside the new element. For sliding window max, this produces a deque with duplicate values — not wrong for the maximum value, but if the *index* of the max matters (e.g., for tie-breaking in specific problems), older indices remain at the front incorrectly. Use `≤` to evict duplicates as standard.

4. **Not initializing `{0: 1}` equivalent for prefix sum problems?** — For Shortest Subarray with Sum ≥ k, the prefix sum P[0] = 0 must be in the deque from the start (push index 0 before the loop, or start the loop at i=0 with the deque initially empty and let i=0 push itself). Missing P[0] means subarrays starting from index 0 are never considered.

5. **In DP + deque: reading dp[deque[0]] AFTER pushing i?** — If i is pushed to the deque before computing dp[i], and dp[i] happens to be the largest in the window (after back-eviction leaves i at the front), then `dp[deque[0]] = dp[i]` is a self-reference — dp[i] depends on itself. Always read the predecessor dp BEFORE the back-evict-and-push sequence.

6. **In two-deque problems (1438): front-evicting from only one deque when left advances?** — When `left` is incremented, both the max deque and the min deque must be checked: if `maxDeq[0] < left`, shift maxDeq; if `minDeq[0] < left`, shift minDeq. Skipping the check on one deque leaves a stale index at its front, giving wrong max or min values for subsequent windows.

7. **Emitting the answer before the window is full (i < k-1)?** — For a k-wide sliding window, the first valid window is complete at index i = k - 1. Emitting `nums[deque[0]]` for i = 0, 1, ..., k-2 is wrong — the deque holds valid monotone order but represents a partial window. Guard with `if (i >= k - 1) result.push(nums[deque[0]])`.

8. **In Max Value of Equation: pushing j before checking the answer for j as right endpoint?** — If j is pushed first, then when deque[0] is read as the best left endpoint, j might itself be the front (if it has the highest y-x value so far), making i = j — the same point used as both left and right endpoint. Always check the answer (using deque[0] as i and j as the right endpoint) BEFORE back-evicting and pushing j.

9. **Off-by-one in front-eviction condition: `deque[0] <= i - k` vs `deque[0] < i - k + 1`?** — These are equivalent (`i - k + 1 = i - k + 1`; the condition evicts index `i-k` which is just outside a window `[i-k+1..i]`). The common mistake is using `deque[0] < i - k` (strict less than i-k), which keeps index i-k in the deque when it should be evicted, allowing a window of size k+1. Double-check: the window `[i-k+1..i]` has exactly k elements; index `i-k` must be gone.

10. **Iterating over `nums` for the prefix-sum deque problem instead of the prefix-sum array P?** — The deque in Shortest Subarray with Sum ≥ k stores indices into P (size n+1, indices 0..n), not into nums (size n, indices 0..n-1). The loop runs `for i from 0 to n` (inclusive), not `for i from 0 to n-1`. Using `nums.length` as the loop bound misses the final prefix sum P[n], which enables checking subarrays that end at the last element.

---

**Final Tip:** At the 5 YOE level, the decisive signal for any monotone deque problem is articulating *why an element can be permanently discarded* — not just *that* it is discarded. For sliding window maximum: *"once a larger or equal element arrives at index i, any older element at index j < i with nums[j] ≤ nums[i] can never be the window maximum — in every window containing both j and i, nums[i] wins; and by the time nums[i] has expired, j has also expired since j < i."* For prefix-sum deque: *"a left boundary j' with P[j'] ≥ P[i] is permanently dominated by i: any future right endpoint would get a tighter prefix-sum gap from i than from j', and a shorter subarray length since i > j'."* For DP + deque: *"once dp[i] ≥ dp[j], any future dp[x] (x in [i+1..i+k]) achieves at least as good a score using i as its predecessor, and i remains valid longer since i > j."* In every case, the back-eviction argument is a formal proof that the evicted element cannot contribute a strictly better answer to any future query — naming that proof in one sentence before writing any code is what separates a senior engineer who understands the structure from a candidate who has memorized the template.
