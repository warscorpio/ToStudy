## Topic A: Stack-Based Expression Evaluation

### Section A1: Fundamentals

**Q1. What is Reverse Polish Notation, and why does a stack perfectly model its evaluation?**

A: Reverse Polish Notation (RPN), also called postfix notation, places operators *after* their operands rather than between them. `3 4 +` means `3 + 4`; `2 3 4 + *` means `2 * (3 + 4)`. The stack models evaluation naturally because of the "last operand pushed, first operand consumed" property of binary operators: when an operator token is encountered, the two most recently pushed operands (stack's top two elements) are exactly the operator's left and right arguments. Push the result back — the stack compresses completed subexpressions into single values, ready for the next operator. This matches the LIFO property of a stack exactly — no coincidence, since Dijkstra designed RPN with this evaluation in mind.

```
Tokens: ["2", "1", "+", "3", "*"]   (means (2+1)*3)

Process "2": stack = [2]
Process "1": stack = [2, 1]
Process "+": pop 1 and 2, push 2+1=3   → stack = [3]
Process "3": stack = [3, 3]
Process "*": pop 3 and 3, push 3*3=9   → stack = [9]

Result = stack.pop() = 9 ✓
```

**Q2. What is the invariant of the operand stack at every step of RPN evaluation?**

A: At any point during evaluation, *the stack contains the results of all fully-evaluated subexpressions whose values have not yet been consumed by an operator*. More precisely: after processing the first `k` tokens, the stack contains exactly the values that would appear as "pending operands" if you were evaluating the expression from left to right by hand. At the very end of a valid RPN expression, the stack has exactly one element — the final result. If the expression is valid, this invariant guarantees that every operator always finds exactly two operands waiting on the stack.

```
Invariant: after processing token k,
  stack.length = (number of operands in tokens[0..k]) - (number of operators in tokens[0..k])

For a valid N-operand RPN expression:
  - N operands, N-1 operators
  - Final stack size = N - (N-1) = 1 ✓

Malformed input signals:
  - Operator with < 2 elements on stack → "not enough operands" error
  - Final stack size > 1 → "too many operands" (missing operators)
```

**Q3. Why does RPN eliminate the need for parentheses and operator precedence rules?**

A: In infix notation, operator precedence and parentheses exist to resolve ambiguity about evaluation order: `2 + 3 * 4` is ambiguous without the convention that `*` binds tighter than `+`. Parentheses override this: `(2 + 3) * 4`. In RPN, the evaluation order is *encoded directly in the token sequence* — the position of operators relative to their operands is unambiguous. `2 3 4 * +` always means `2 + (3 * 4)` because `*` appears before `+` and operates on the most recently available operands. `2 3 + 4 *` always means `(2 + 3) * 4`. No precedence table is needed; the operand stack resolves everything structurally.

```
Infix: 2 + 3 * 4      requires precedence rule: * before +  → 14
RPN:   2 3 4 * +       tokens self-document order: (*) applied first → 14

Infix: (2 + 3) * 4    parentheses override precedence
RPN:   2 3 + 4 *       no parentheses needed; + is before *  → 20
```

**Q4. What is the Shunting-Yard algorithm, and how does it convert infix to RPN?**

A: Dijkstra's Shunting-Yard algorithm converts infix expressions to RPN using an operator stack and an output queue. Rules: (1) number token → append to output; (2) operator token → pop operators from the operator stack to output while the top has equal or higher precedence (and is left-associative), then push the new operator; (3) `(` → push to operator stack; (4) `)` → pop to output until `(` is popped (discard both parentheses). At end: pop all remaining operators to output. The output queue, read in order, is the RPN expression. The algorithm runs in O(n) and is the foundation of most compiler front-ends for parsing arithmetic.

```
Infix: 3 + 4 * 2 / (1 - 5)

Step-by-step:
"3"  → output: [3]
"+"  → op_stack: [+]
"4"  → output: [3, 4]
"*"  → * > + so push: op_stack: [+, *]
"2"  → output: [3, 4, 2]
"/"  → / == *, left-assoc: pop * to output, push /: op_stack: [+, /], output: [3,4,2,*]
"("  → op_stack: [+, /, (]
"1"  → output: [3, 4, 2, *, 1]
"-"  → op_stack: [+, /, (, -]
"5"  → output: [3, 4, 2, *, 1, 5]
")"  → pop until "(": pop - to output, discard (: op_stack: [+, /]
End  → pop remaining: / then + to output.

RPN: 3 4 2 * 1 5 - / +   (= 3 + 4*2/(1-5) = 3 + 8/(-4) = 3 + (-2) = 1)
```

**Q5. How do you handle integer division in RPN evaluation, and why does the truncation direction matter?**

A: The problem specifies division should truncate toward zero — meaning positive results round down, and negative results round up toward zero (not toward negative infinity). JavaScript's `/` operator produces floats; `Math.trunc()` truncates toward zero. Python's `//` truncates toward negative infinity, which is incorrect for negative quotients: `-7 // 2 = -4` in Python but the problem requires `-3` (truncate toward zero). Always use `int(a / b)` in Python or `Math.trunc(a / b)` in JavaScript for this problem.

```
Division cases:
  7 / 2 = 3.5 → truncate toward zero = 3
  -7 / 2 = -3.5 → truncate toward zero = -3  (NOT -4)
  7 / -2 = -3.5 → truncate toward zero = -3  (NOT -4)

JavaScript:
  Math.trunc(7 / 2)   = 3  ✓
  Math.trunc(-7 / 2)  = -3 ✓
  Math.trunc(7 / -2)  = -3 ✓

Python:
  int(-7 / 2)  = int(-3.5) = -3 ✓   (use this)
  -7 // 2      = -4          ✗   (floor division — wrong for negatives)
```

**Q6. What is the minimum and maximum stack depth during a valid RPN evaluation, and what do they tell you about expression structure?**

A: Minimum depth during evaluation is 1 — achieved immediately after any operator, since every binary operator reduces two elements to one. The stack can never reach 0 mid-evaluation in a valid expression (that would mean an operator found an empty stack). Maximum depth equals the number of operands that appear consecutively before any operator. For `[a, b, c, d, +, +, +]`, all four operands are pushed before any operator fires, reaching depth 4. The maximum stack depth reflects the maximum "nesting" or "pending operand" count of the expression — equivalent to the maximum number of simultaneously open subexpressions in the equivalent infix form. For interview problems, this is bounded by the number of operands: O(n).

```
Expression: ["5", "1", "2", "+", "4", "*", "+", "3", "-"]

Depth trace:
"5"  → depth 1
"1"  → depth 2
"2"  → depth 3
"+"  → depth 2  (pop 2,1; push 3 → stack: [5,3])
"4"  → depth 3
"*"  → depth 2  (pop 4,3; push 12 → stack: [5,12])
"+"  → depth 1  (pop 12,5; push 17 → stack: [17])
"3"  → depth 2
"-"  → depth 1  (pop 3,17; push 14 → stack: [14])

Max depth = 3. Final depth = 1 (exactly one result). ✓
```

### Section A2: Advanced Patterns

**Q7. How does the operand-order matter when popping for non-commutative operators?**

A: Addition and multiplication are commutative — the order of operands doesn't affect the result. Subtraction and division are not. The convention in RPN is that the *first-pushed operand* is the *left operand* and the *second-pushed* (stack top) is the *right operand*. So for `a b -`, `a` was pushed first (deeper in stack) and `b` was pushed second (stack top). The operation is `a - b`, so you must pop `b` first and `a` second: `const right = stack.pop(); const left = stack.pop(); push(left - right)`. Reversing the pop order is the most common bug in RPN implementations.

```
Tokens: ["6", "3", "/"]  means 6 ÷ 3 = 2

Stack after "6": [6]
Stack after "3": [6, 3]
Operator "/":
  right = stack.pop() = 3   (top = second operand = divisor)
  left  = stack.pop() = 6   (bottom = first operand = dividend)
  push(left / right) = push(6/3) = push(2) ✓

If reversed: push(3/6) = push(0) ✗
```

**Q8. How would you extend RPN evaluation to support unary operators?**

A: A unary operator (e.g., negation `~`, absolute value, factorial) pops only one operand instead of two, applies the operation, and pushes the result. The stack-based framework extends naturally: `if (token is unary op): push(unaryOp(stack.pop()))`. The invariant adjusts: a unary operator reduces the stack depth by 0 net (pop one, push one) rather than 1 (pop two, push one). In languages with unary minus (e.g., `(~3)` for `-3`), the grammar must distinguish unary from binary minus — typically by context: unary minus follows another operator or opening parenthesis.

**Q9. What is the relationship between an explicit stack and recursion for expression evaluation?**

A: Every recursive algorithm implicitly uses the call stack. For expression trees (AST), a recursive post-order traversal (evaluate left subtree, evaluate right subtree, apply root operator) is identical to the RPN evaluation loop with an explicit stack — both produce the same result by visiting the same nodes in the same order. The explicit stack version is preferred when the expression depth could cause stack overflow (very deeply nested expressions), or when the language doesn't optimize tail recursion. Understanding this equivalence explains why RPN evaluation is O(n) time and O(n) space regardless of implementation: the implicit call stack for a recursive evaluator holds the same pending operands as the explicit operand stack.

```
AST for (2 + 3) * 4:
        *
       / \
      +   4
     / \
    2   3

Recursive post-order: eval(+) → eval(2)=2, eval(3)=3, 2+3=5 → eval(*)=5*4=20
RPN stack:  "2 3 + 4 *" → push 2, push 3, +→push 5, push 4, *→push 20
```

## Topic B: The Monotonic Stack Pattern

### Section B1: Fundamentals

**Q10. What is a monotonic stack, what structural property does it maintain, and what problems does it solve?**

A: A monotonic stack is a stack that is always sorted (either non-decreasing or non-increasing) from bottom to top. Before pushing a new element, pop all elements that would violate the sorted order — those popped elements are processed as part of the problem logic (not discarded). The structural property: at any moment, reading from bottom to top gives either an ascending or descending sequence. This maintenance invariant makes monotonic stacks the canonical O(n) solution for "nearest element satisfying a comparison condition" problems: next greater element, next smaller element, previous greater element, previous smaller element, and their "range" variants (largest rectangle, trapping rainwater).

```
Problem class: "For each element, find the nearest [left/right] element that is [greater/smaller]"
Naive: for each element, scan left or right → O(n²)
Monotonic stack: each element is pushed once and popped at most once → O(n)

Monotonic decreasing stack (top is smallest of active candidates):
  Push x: pop everything LARGER than x before pushing x... wait no.

Actually:
  Monotonic DECREASING stack: elements decrease from bottom to top.
  To maintain: pop everything SMALLER than incoming x (these have found their "next greater" = x).
  Push x.

  Monotonic INCREASING stack: elements increase from bottom to top.
  To maintain: pop everything LARGER than incoming x (these have found their "next smaller" = x).
  Push x.
```

**Q11. What is the "next greater element" pattern, and how does the monotonic stack produce answers in O(n)?**

A: For each element in an array, find the first element to its right that is strictly greater. The monotonic decreasing stack approach: maintain a stack of elements (or indices) in decreasing order. For each new element `x`: while the stack top is less than `x`, pop it — `x` is its "next greater element." Then push `x`. After processing all elements, anything remaining on the stack has no next greater element (answer = -1 or undefined). Every element is pushed exactly once and popped at most once — O(n) total operations, O(n) space for the stack.

```
nums = [2, 1, 2, 4, 3]

stack=[], result=[-1,-1,-1,-1,-1]

i=0, x=2: stack empty → push 2. stack=[2]
i=1, x=1: 1 < 2 (top) → push 1. stack=[2,1]  (1 doesn't beat 2)
i=2, x=2: 2 > 1 (top) → pop 1, result[1]=2. 2 == 2 (top, not strictly greater) → push 2.
  stack=[2,2]
i=3, x=4: 4 > 2 → pop 2, result[2]=4. 4 > 2 → pop 2, result[0]=4. Push 4. stack=[4]
i=4, x=3: 3 < 4 → push 3. stack=[4,3]

Remaining stack (no next greater): result[3]=-1, result[4]=-1.

Result: [4, 2, 4, -1, -1] ✓
```

**Q12. What does the monotonic stack store — values or indices — and when does each apply?**

A: The choice depends on what information is needed when an element is popped:

**Store values** when only the element's value matters for the answer — e.g., Next Greater Element I where the result is the value of the next greater element. Simple and readable.

**Store indices** when position matters — e.g., Daily Temperatures (answer = distance = current index − popped index) or Largest Rectangle in Histogram (answer involves width = current index − popped index − 1). In practice, storing indices is strictly more general since you can always recover the value from the index (`nums[idx]`), but not the other way around. Always store indices when the problem involves counting positions or computing spans.

```
Next Greater Element (value only):
  stack stores values: [2, 1, 2]
  when 4 pops 2: answer for value 2 is 4. ✓

Daily Temperatures (distance needed):
  stack stores indices: [0, 1, 2] (values 73, 74, 75 at those indices)
  when 76 (index 3) pops index 2: answer[2] = 3 - 2 = 1 day. ✓
  without storing index, can't compute distance.
```

### Section B2: Advanced Patterns

**Q13. How does "Largest Rectangle in Histogram" use a monotonic stack, and what is the width-computation invariant?**

A: For each bar, the largest rectangle using that bar's height extends left to the first shorter bar and right to the first shorter bar. A monotonic increasing stack (of indices) maintains bars in non-decreasing height. When bar `i` is shorter than the stack top, bars are popped — each popped bar's rectangle extends: left boundary = new stack top's index + 1 (or 0 if stack is empty), right boundary = i − 1. Width = right − left + 1 = i − (stack.top or -1) − 1. After processing all bars, remaining stack elements extend to the right boundary = n − 1.

```js
function largestRectangleArea(heights) {
  const stack = []; // monotonic increasing: indices of bars in non-decreasing height
  let maxArea = 0;
  const n = heights.length;

  for (let i = 0; i <= n; i++) {
    const currHeight = i === n ? 0 : heights[i]; // sentinel 0 flushes remaining stack

    while (stack.length && heights[stack[stack.length - 1]] > currHeight) {
      const h = heights[stack.pop()];                         // popped bar's height
      const w = stack.length ? i - stack[stack.length-1] - 1 : i; // width of rectangle
      maxArea = Math.max(maxArea, h * w);
    }
    stack.push(i);
  }
  return maxArea;
}
```

**Q14. What is the "previous smaller element" variant, and how does traversal direction change the pattern?**

A: "Next greater/smaller" is found by traversing left-to-right and popping when the incoming element beats the stack top. "Previous greater/smaller" is found by traversing right-to-left (or equivalently, by querying the stack top *before* pushing rather than the popped elements during a push). The direction of traversal controls whether answers refer to the left or right neighbor:

- **Right-to-left traversal + query on push** → previous element satisfying the condition (answers look left).
- **Left-to-right traversal + answer on pop** → next element satisfying the condition (answers look right).

For problems requiring both (e.g., "find the range that a bar is the minimum of"), two passes are run — one left-to-right for next smaller, one right-to-left for previous smaller — and the valid range is computed from both answers.

## Topic C: Stack for Nested & Balanced Structures

### Section C1: Fundamentals

**Q15. What class of problems uses a stack for matching/balancing, and what is the stack's invariant in these problems?**

A: Any problem involving nested, paired delimiters where the most-recently-opened must be the first-closed (LIFO nesting): parentheses/brackets/braces validation, XML/HTML tag matching, function call depth tracking, and undo/redo systems. The stack's invariant: *at any point during a left-to-right scan, the stack contains exactly the unmatched opening delimiters seen so far, in the order they were encountered.* A closing delimiter is valid iff it matches the stack's top (the most recently opened unmatched delimiter). This directly encodes the "last opened, first closed" rule of balanced nesting.

```
"([{}])"  — valid

Scan:
"("  → push (. stack=[ ( ]
"["  → push [. stack=[ (, [ ]
"{"  → push {. stack=[ (, [, { ]
"}"  → top={, matches → pop. stack=[ (, [ ]
"]"  → top=[, matches → pop. stack=[ ( ]
")"  → top=(, matches → pop. stack=[ ]
End: stack empty → valid ✓

"([)]"  — invalid

"("  → push. stack=[(]
"["  → push. stack=[(, []
")"  → top=[, doesn't match ) → invalid ✗
```

**Q16. How does Min Stack achieve O(1) getMin without degrading push/pop performance?**

A: The challenge: when the current minimum is popped, the new minimum must be known in O(1) without scanning the remaining stack. Solution: maintain a parallel "min stack" that tracks the minimum *at each level*. On `push(x)`: push `x` to main stack; push `min(x, minStack.top)` to min stack. On `pop()`: pop from both stacks simultaneously. `getMin()`: return `minStack.top`. The min stack's top always reflects the minimum of the main stack's current contents. No scanning required; each operation remains O(1). Space is O(n) for the auxiliary min stack.

```
Optimization — store only when new min is smaller:
  push(x): if minStack is empty or x <= minStack.top, push x to minStack.
  pop(): if main.top === minStack.top, pop from minStack too.
  getMin(): return minStack.top.

This saves space when many pushes don't set new minimums.
But the simplest correct version stores a min value alongside every push.
```

## Topic D: Cross-Topic & Interview-Style Questions

**Q17. "Walk through your thought process when you see an expression evaluation problem."**

A: Four-step classification: (1) **Notation** — is the expression already in RPN/postfix? If yes, direct stack evaluation. Infix? Need operator precedence handling — either Shunting-Yard to convert first, or a recursive descent parser, or the "stack with precedence rules" approach for simpler variants (no parentheses → linear scan). (2) **Operator set** — binary only? Unary operators? Which operators, and what are the precedence tiers? (3) **Operand type** — integers (truncation for division), floats, variables? (4) **Edge cases** — division by zero, single operand, malformed input.

For interview purposes: RPN → operand stack, O(n) one-pass. Infix with ×÷ only (no parentheses) → linear scan with pending multiplication/division. Infix with +−×÷+parentheses → two-stack approach or Shunting-Yard.

**Q18. "In one sentence each, state the stack invariant for each problem in this family."**

A:
- **RPN Evaluation**: the stack holds the results of all fully-evaluated subexpressions not yet consumed by an operator — exactly one element remains at the end.
- **Valid Parentheses**: the stack holds all unmatched opening delimiters seen so far in arrival order — an empty stack at the end means full balance.
- **Min Stack**: the auxiliary min-stack's top always equals the minimum value currently present in the main stack.
- **Daily Temperatures / Next Greater Element**: the monotonic stack holds indices of elements whose "next greater" answer has not yet been determined — an element is answered (and popped) exactly when a greater element arrives.
- **Largest Rectangle in Histogram**: the monotonic increasing stack holds indices of bars that are candidate left-boundaries for rectangles extending to the right — each popped bar computes the largest rectangle it can be the height of.
- **Basic Calculator**: the stack holds accumulated results and signs from outer parenthesis scopes — popped and combined when a closing parenthesis is encountered.

## Problem 1 — Evaluate Reverse Polish Notation

### Problem
Evaluate the value of an arithmetic expression in Reverse Polish Notation. Valid operators are `+`, `-`, `*`, and `/`. Each operand may be an integer or another expression. Division truncates toward zero.

```
Input:  tokens = ["2","1","+","3","*"]
Output: 9        // ((2 + 1) * 3) = 9

Input:  tokens = ["4","13","5","/","+"]
Output: 6        // (4 + (13 / 5)) = (4 + 2) = 6

Input:  tokens = ["10","6","9","3","+","-11","*","/","*","17","+","5","+"]
Output: 22
```

### Pattern Recognition
Operand stack — scan tokens left to right; push numbers; on operator, pop two operands (right first, then left), apply the operation, push the result. The stack compresses evaluated subexpressions into single values.

### Key Insight
Every binary operator in RPN always finds its two operands as the top two elements of the stack — guaranteed by the RPN format's structural correctness. The stack acts as the "pending operands" buffer, and the invariant "one result remains at the end" is maintained by each operator reducing depth by exactly 1 (pop 2, push 1).

### Approach
Initialize `stack = []`. For each `token`: if it's a number (not an operator), push `parseInt(token)`. If it's an operator: `right = stack.pop(); left = stack.pop()`; compute result; push result. After all tokens: `return stack[0]`.

### Solution

```js
function evalRPN(tokens) {
  const stack = [];
  const ops = {
    '+': (a, b) => a + b,
    '-': (a, b) => a - b,
    '*': (a, b) => a * b,
    '/': (a, b) => Math.trunc(a / b), // truncate toward zero, not floor
  };

  for (const token of tokens) {
    if (ops[token]) {
      // Operator: pop right operand first (top of stack), then left operand
      const right = stack.pop();
      const left  = stack.pop();
      stack.push(ops[token](left, right)); // push result back
    } else {
      // Operand: push as integer (handles negative numbers like "-11")
      stack.push(parseInt(token, 10));
    }
  }

  return stack[0]; // exactly one element remains for a valid RPN expression
}
```

### Dry Run

```
tokens = ["10","6","9","3","+","-11","*","/","*","17","+","5","+"]

token="10":   stack = [10]
token="6":    stack = [10, 6]
token="9":    stack = [10, 6, 9]
token="3":    stack = [10, 6, 9, 3]
token="+":    right=3, left=9. 9+3=12. stack = [10, 6, 12]
token="-11":  stack = [10, 6, 12, -11]
token="*":    right=-11, left=12. 12*(-11)=-132. stack = [10, 6, -132]
token="/":    right=-132, left=6. 6/(-132) = Math.trunc(-0.045...) = 0. stack = [10, 0]
token="*":    right=0, left=10. 10*0=0. stack = [0]
token="17":   stack = [0, 17]
token="+":    right=17, left=0. 0+17=17. stack = [17]
token="5":    stack = [17, 5]
token="+":    right=5, left=17. 17+5=22. stack = [22]

Return stack[0] = 22 ✓
```

### Complexity
- Time: O(n) — one pass through all tokens; each stack operation is O(1).
- Space: O(n) — in the worst case (all operands before any operator), all n/2 + 1 operands are on the stack simultaneously.

### Edge Cases
- **Single token** `["5"]`: no operators; stack = [5]; return 5. Valid — a single number is a valid RPN expression.
- **Negative operands** `["-11"]`: `parseInt("-11", 10) = -11`. The minus sign is part of the number token, not an operator token.
- **Division truncation**: `["7", "-2", "/"]` → `Math.trunc(7 / -2) = Math.trunc(-3.5) = -3`. NOT -4 (floor). Use `Math.trunc`, not `Math.floor`.
- **Division by zero**: not in the problem's test cases per LeetCode constraints, but in production: add a guard `if (right === 0) throw new Error("division by zero")`.
- **Operand-order for subtraction/division**: `["5", "3", "-"]` must produce `5 - 3 = 2`, not `3 - 5 = -2`. Always pop right first, then left.

### Follow-up Questions
- "Extend to support unary negation?" — Add `"~"` as a unary operator: `pop one, push(-val)`. The dispatch table handles it naturally with a special case checking stack depth.
- "What if operands are floats?" — Replace `parseInt` with `parseFloat`; remove `Math.trunc`. The rest is unchanged.
- "Convert infix `(2 + 3) * 4` to RPN first, then evaluate?" — Apply Shunting-Yard to produce `["2","3","+","4","*"]`, then evaluate with this function. Two-phase pipeline: convert → evaluate.

## Problem 2 — Valid Parentheses

### Problem
Given a string `s` containing only the characters `(`, `)`, `{`, `}`, `[`, `]`, determine if the input string is valid. A string is valid if open brackets are closed by the same type of bracket, in the correct order, and every open bracket has a corresponding close bracket.

```
Input:  s = "()"      → true
Input:  s = "()[]{}"  → true
Input:  s = "(]"      → false
Input:  s = "([)]"    → false
Input:  s = "{[]}"    → true
```

### Pattern Recognition
Stack-based bracket matching — push opening brackets; on closing bracket, check if the stack top is the matching opener; pop on match, return false on mismatch. Return true iff stack is empty at the end.

### Key Insight
The LIFO property of a stack directly models the LIFO nesting requirement: the most-recently-opened bracket must be the next one closed. The stack at any point holds the "currently open" brackets in arrival order — the top is always the innermost unclosed bracket.

### Approach
Use a HashMap to map each closing bracket to its corresponding opener. For each character: if it's an opener, push it. If it's a closer, check `stack.top === closerToOpener[char]`; if yes, pop; if no (or stack is empty), return false. After the scan, return `stack.length === 0`.

### Solution

```js
function isValid(s) {
  const stack = [];

  // Map each closing bracket to its corresponding opening bracket
  const match = { ')': '(', '}': '{', ']': '[' };

  for (const ch of s) {
    if (ch === '(' || ch === '{' || ch === '[') {
      stack.push(ch); // opening bracket: push and wait
    } else {
      // closing bracket: must match the most recently opened bracket
      if (stack.length === 0 || stack[stack.length - 1] !== match[ch]) {
        return false; // empty stack or wrong opener at top
      }
      stack.pop(); // matched: remove the opener
    }
  }

  return stack.length === 0; // all openers must have been matched
}
```

### Dry Run

```
s = "([)]"

ch="(":  opener → push. stack=["("]
ch="[":  opener → push. stack=["(", "["]
ch=")":  closer. match[")"]=("(". top="[" ≠ "(" → return false ✗

s = "{[]}"

ch="{":  push. stack=["{"]
ch="[":  push. stack=["{", "["]
ch="]":  match["]"]="[". top="[" ✓ → pop. stack=["{"]
ch="}":  match["}"]= "{". top="{" ✓ → pop. stack=[]

stack empty → return true ✓
```

### Complexity
- Time: O(n) — one pass; each push/pop is O(1).
- Space: O(n) — at most n/2 openers on the stack (a string of all openers fills the stack to n/2 before any closer appears... actually up to n elements for all-opener input).

### Edge Cases
- **Empty string**: loop doesn't execute; stack is empty → return true. (Empty string is vacuously valid.)
- **Odd length**: can never be valid (openers and closers must pair up). An early-exit `if (s.length % 2 !== 0) return false` saves time but isn't required.
- **Only openers** `"((("`: stack = ["(","(","("]; not empty → return false.
- **Only closers** `")))"`: first `")"` finds empty stack → return false immediately.
- **Single pair** `"()"`: push `(`, then `)` matches and pops → stack empty → true.

### Follow-up Questions
- "What if you also need to return the position of the first mismatch?" — Store the index of each opener on the stack; when a mismatch is found, the current index is the mismatch position.
- "Generalize to validate HTML tags?" — Same stack approach but tokens are tag names (`<div>`, `</div>`). Parse tag name; push opening tags; on closing tag, check top; pop on match.
- "Minimum additions to make valid?" — Count unmatched openers remaining on stack at the end; add unmatched closers detected during scanning. Total = unmatched_openers + unmatched_closers.

## Problem 3 — Min Stack

### Problem
Design a stack that supports `push`, `pop`, `top`, and `getMin` operations, all in O(1) time.

```
MinStack minStack = new MinStack();
minStack.push(-2);
minStack.push(0);
minStack.push(-3);
minStack.getMin();  // return -3
minStack.pop();
minStack.top();     // return 0
minStack.getMin();  // return -2
```

### Pattern Recognition
Auxiliary min-tracking stack — maintain a parallel stack that records the current minimum *at each push level*, so that popping from the main stack simultaneously "rolls back" the current minimum.

### Key Insight
The minimum of a stack at any moment depends on which elements are currently in the stack. When the current minimum is popped, the previous minimum (valid before that element was pushed) must be recoverable in O(1). Storing the running minimum *with each element* preserves this history without any scanning.

### Approach
Each entry stores `[value, currentMin]`. On `push(val)`: `currentMin = min(val, this.minSoFar)`. On `pop()`: remove the top pair. `top()`: return `stack.top[0]`. `getMin()`: return `stack.top[1]`.

### Solution

```js
class MinStack {
  constructor() {
    // Each element: [value, minAtThisLevel]
    // minAtThisLevel = minimum of all values from bottom to this position
    this.stack = [];
  }

  push(val) {
    const currentMin = this.stack.length === 0
      ? val
      : Math.min(val, this.stack[this.stack.length - 1][1]);

    this.stack.push([val, currentMin]);
  }

  pop() {
    this.stack.pop(); // removing the top pair also removes its minAtThisLevel
  }

  top() {
    return this.stack[this.stack.length - 1][0];
  }

  getMin() {
    return this.stack[this.stack.length - 1][1]; // min embedded at this level
  }
}
```

### Dry Run

```
push(-2): stack is empty → min = -2. push [-2, -2]. stack=[[-2,-2]]
push(0):  min = min(0, -2) = -2. push [0, -2].    stack=[[-2,-2],[0,-2]]
push(-3): min = min(-3,-2) = -3. push [-3,-3].    stack=[[-2,-2],[0,-2],[-3,-3]]

getMin(): stack.top[1] = -3 ✓

pop():    remove [-3,-3].   stack=[[-2,-2],[0,-2]]

top():    stack.top[0] = 0 ✓

getMin(): stack.top[1] = -2 ✓
(After popping -3, the minimum correctly rolled back to -2)
```

### Complexity
- Time: O(1) for all four operations — push, pop, top, and getMin are all direct array index accesses.
- Space: O(n) — each push stores one extra value (the current min) alongside the actual value.

### Edge Cases
- **Push minimum value repeatedly**: `push(-1), push(-1)`. Each stores `[−1, −1]`. After one pop, `getMin()` = -1 (from the second pair's stored min). Correct — the min is still -1.
- **Pop until one element remains**: stack has one pair; `getMin()` returns that pair's min (the value itself). Correct.
- **getMin on empty stack**: undefined behavior per problem constraints (guaranteed at least one call after at least one push). Add a guard in production.
- **Space optimization**: only push to the auxiliary min-stack when the new value is ≤ the current min. This reduces space when many pushes don't set a new minimum, but the logic becomes more complex; the paired approach above is clearer.

### Follow-up Questions
- "Max Stack instead?" — Replace `Math.min` with `Math.max`; store `[value, maxAtThisLevel]`. Identical structure.
- "Support O(1) pop that pops the minimum element (not just the top)?" — Much harder; requires a sorted structure alongside the stack. Typically solved with a balanced BST + a doubly-linked list, not a simple stack — this is the "Design a Stack With Increment Operation" family.
- "What if values can repeat?" — The paired approach handles duplicates correctly without any modification. Each push independently stores its own min snapshot.

## Problem 4 — Daily Temperatures

### Problem
Given an array of integers `temperatures` representing daily temperatures, return an array `answer` such that `answer[i]` is the number of days you have to wait after day `i` to get a warmer temperature. If there is no future day with a higher temperature, `answer[i] = 0`.

```
Input:  temperatures = [73, 74, 75, 71, 69, 72, 76, 73]
Output: [1, 1, 4, 2, 1, 1, 0, 0]

Input:  temperatures = [30, 40, 50, 60]
Output: [1, 1, 1, 0]

Input:  temperatures = [30, 60, 90]
Output: [1, 1, 0]
```

### Pattern Recognition
Monotonic decreasing stack of indices — maintain a stack of day indices in decreasing temperature order. When a warmer day arrives, it is the "next greater temperature" for all popped indices; the answer is the difference in indices.

### Key Insight
A day's "next warmer day" hasn't been found until a temperature higher than it arrives. The monotonic decreasing stack keeps all indices of days whose "next warmer" is still unknown. When a higher temperature arrives at index `i`, every day on the stack with a temperature lower than `temperatures[i]` has found its answer: `i - stackTop`. Storing indices (not values) enables the direct distance computation.

### Approach
Initialize `stack = []` (stores indices), `answer = new Array(n).fill(0)`. For each `i`: while `temperatures[i] > temperatures[stack.top]`: `j = stack.pop(); answer[j] = i - j`. Then push `i`. Remaining stack indices have no warmer day → answer stays 0.

### Solution

```js
function dailyTemperatures(temperatures) {
  const n = temperatures.length;
  const answer = new Array(n).fill(0); // default 0: no warmer day found
  const stack = []; // monotonic decreasing: indices of days with no answer yet

  for (let i = 0; i < n; i++) {
    // Current day is warmer than all days at top of stack
    while (stack.length > 0 && temperatures[i] > temperatures[stack[stack.length - 1]]) {
      const j = stack.pop();         // j's next warmer day is i
      answer[j] = i - j;            // wait time = distance between indices
    }
    stack.push(i); // push current day's index (its next warmer is still unknown)
  }

  // Remaining stack indices: no warmer day exists → answer[j] stays 0
  return answer;
}
```

### Complexity
- Time: O(n) — each index is pushed exactly once and popped at most once; total stack operations ≤ 2n.
- Space: O(n) — stack holds at most n indices (entire array in non-increasing temperature order); answer array is O(n).

### Edge Cases
- **Strictly decreasing temperatures** `[90, 80, 70]`: nothing is ever popped during the loop; all answers stay 0. Stack drains with no output (stack = [0,1,2] at end). Correct.
- **Strictly increasing temperatures** `[70, 80, 90]`: each new temperature pops the previous one immediately; each answer = 1.
- **All same temperature** `[70, 70, 70]`: `temperatures[i] > temperatures[stack.top]` is never true (strict inequality); nothing is popped; all answers stay 0. Correct — same temperature is not "warmer."
- **Single element**: stack = [0] after loop; answer = [0]. Correct.

### Follow-up Questions
- "What if 'warmer' meant ≥ instead of >?" — Change `>` to `>=` in the while condition. Elements with equal temperature would also trigger a pop.
- "What if you need the next COLDER day?" — Flip to a monotonic increasing stack: pop when `temperatures[i] < temperatures[stack.top]`.
- "Previous warmer day instead of next?" — Traverse right-to-left with the same monotonic stack logic, or use a separate right-to-left pass.

## Problem 5 — Next Greater Element I

### Problem
Given two distinct integer arrays `nums1` and `nums2`, where `nums1` is a subset of `nums2`, find the next greater element for each element in `nums1` in `nums2`. The next greater element of `x` in `nums2` is the first element to the right of `x` in `nums2` that is greater than `x`. If no such element exists, the answer is -1.

```
Input:  nums1 = [4, 1, 2], nums2 = [1, 3, 4, 2]
Output: [-1, 3, -1]
  // 4's next greater in nums2: none → -1
  // 1's next greater in nums2: 3
  // 2's next greater in nums2: none → -1

Input:  nums1 = [2, 4], nums2 = [1, 2, 3, 4]
Output: [3, -1]
```

### Pattern Recognition
Monotonic decreasing stack on `nums2` + HashMap — process `nums2` to build a `{value → nextGreater}` map using the monotonic stack; then answer each `nums1` query in O(1) from the map.

### Key Insight
The next-greater-element relationship is a property of `nums2` alone, not of `nums1`. Precomputing a `{value → next greater}` map from `nums2` in one O(|nums2|) pass allows O(1) answering of each `nums1` query. The monotonic decreasing stack produces the map as a byproduct of its pop-and-answer mechanics: when element `x` is popped by a greater element `y`, `nextGreater[x] = y`.

### Approach
Initialize `map = {}`, `stack = []`. For each `num` in `nums2`: while `stack.top < num`: `map[stack.pop()] = num` (num is the next greater for the popped value). Push `num`. After processing `nums2`, remaining stack elements have no next greater — `map[x] = -1` implicitly (or explicitly). For each element in `nums1`, return `map[element] ?? -1`.

### Solution

```js
function nextGreaterElement(nums1, nums2) {
  const nextGreater = new Map(); // value → next greater element in nums2
  const stack = [];              // monotonic decreasing (values, since nums2 has distinct elements)

  for (const num of nums2) {
    // num is the next greater element for everything on the stack that is smaller
    while (stack.length > 0 && stack[stack.length - 1] < num) {
      nextGreater.set(stack.pop(), num); // popped element's NGE is num
    }
    stack.push(num); // push current; its NGE is still unknown
  }

  // Remaining stack elements: no NGE → implicitly -1 (not in map)
  // Answer nums1 queries using the precomputed map
  return nums1.map(x => nextGreater.get(x) ?? -1);
}
```

### Dry Run

```

num=1: stack empty → push 1. stack=[1]
num=3: 3>1(top) → pop 1; nextGreater.set(1,3).  stack empty → push 3. stack=[3]
num=4: 4>3(top) → pop 3; nextGreater.set(3,4).  push 4. stack=[4]
num=2: 2<4(top) → push 2. stack=[4,2]

End: stack=[4,2] → no NGE (implicitly -1 for 4 and 2).

Query nums1:
  nums1[0]=4: nextGreater.get(4) = undefined → -1 ✓

```

### Complexity
- Time: O(|nums2| + |nums1|) — one monotonic stack pass over `nums2` (each element pushed and popped at most once = O(|nums2|)); one map-lookup pass over `nums1` = O(|nums1|).
- Space: O(|nums2|) — the map and stack each hold at most |nums2| elements.

### Edge Cases
- **nums1 element not in nums2**: problem constraints guarantee nums1 ⊆ nums2, so this can't happen. In a generalized version, handle with `nextGreater.get(x) ?? -1`.
- **Largest element of nums2 always in stack at end**: it has no greater element → -1 correctly returned via `?? -1`.
- **Single-element nums2**: stack = [nums2[0]] at end; answer = -1 for that element.
- **nums2 already decreasing**: nothing is ever popped during the loop; all elements map to -1.

### Follow-up Questions
- "Next Greater Element II (circular array)?" — Process the array twice (indices 0 to 2n−1 mod n) in a single pass; the second pass "wraps around" so elements near the end see elements at the front. Stack stores indices mod n.
- "Previous Greater Element?" — Traverse nums2 right-to-left; same monotonic decreasing stack; pop when stack top ≤ current; the stack top (not the popped element) is the previous greater.
- "Next Greater with duplicates in nums2?" — Store indices instead of values in the stack (since values may repeat); map indices rather than values. Look up nums1 elements by value via an index map.

## Problem 6 — Largest Rectangle in Histogram

### Problem
Given an array of integers `heights` representing the heights of bars in a histogram (each bar has width 1), return the area of the largest rectangle in the histogram.

```
Input:  heights = [2, 1, 5, 6, 2, 3]
Output: 10    // rectangle of height 5, width 2 (bars at indices 2 and 3)

Input:  heights = [2, 4]
Output: 4     // single bar of height 4, width 1
```

### Pattern Recognition
Monotonic increasing stack of indices — maintain bars in non-decreasing height order. When a shorter bar arrives, taller bars are popped; each popped bar is the height of a rectangle that extends from its left boundary (new stack top) to just before the current index. A sentinel height-0 bar at the end flushes all remaining bars.

### Key Insight
A bar at index `i` with height `h` can be the height of a rectangle as wide as the range `[L, R-1]` where L is the index just past the nearest shorter bar to the left, and R is the index of the nearest shorter bar to the right. The monotonic increasing stack simultaneously gives both L (the new top after popping) and R (the current position where the shorter bar triggered the pop). This is the "double answer on single pop" property unique to monotonic stacks.

### Approach
Append a sentinel `0` to force-flush the stack at the end. Maintain `stack = []` (indices, monotonic increasing by height). For each index `i`: while `heights[stack.top] > heights[i]`: `h = heights[stack.pop()]; w = stack.empty ? i : i - stack.top - 1; maxArea = max(maxArea, h*w)`. Push `i`.

### Solution

```js
function largestRectangleArea(heights) {
  const stack = [];  // indices, monotonic non-decreasing height order
  let maxArea = 0;
  const n = heights.length;

  for (let i = 0; i <= n; i++) {
    // Sentinel value 0 at i=n ensures all bars are flushed from the stack
    const currHeight = i === n ? 0 : heights[i];

    while (stack.length > 0 && heights[stack[stack.length - 1]] > currHeight) {
      const h = heights[stack.pop()]; // height of the rectangle

      // Width: extends from (new top + 1) to (i - 1)
      // If stack is empty, left boundary is index 0 → width = i
      const w = stack.length === 0 ? i : i - stack[stack.length - 1] - 1;

      maxArea = Math.max(maxArea, h * w);
    }

    stack.push(i);
  }

  return maxArea;
}
```

## Problem 7 — Basic Calculator II

### Problem
Given a string `s` representing an infix expression with non-negative integers and operators `+`, `-`, `*`, `/` (no parentheses), evaluate and return the result. Division truncates toward zero. The string may contain spaces.

```
Input:  s = "3+2*2"     → 7     // 3 + (2*2) = 7
Input:  s = " 3/2 "     → 1     // 3/2 = 1 (truncate)
Input:  s = " 3+5 / 2 " → 5     // 3 + (5/2) = 3 + 2 = 5
```

### Pattern Recognition
Stack + precedence handling without explicit parsing — scan left-to-right; accumulate a multi-digit number; on each operator (or end of string), apply the previously seen operator. Push `+` and `−` operands directly onto the stack (deferred to final sum); apply `*` and `/` immediately (higher precedence — pop the stack top, compute, push result).

### Key Insight
`+` and `−` have lower precedence: their operands can be deferred and summed at the end. `*` and `/` have higher precedence: they must be resolved immediately with the most recently seen number. Using a stack: push positive/negative values for `+`/`−`; for `*`/`÷`, pop the top, compute with the current number, push the result. Final answer = sum of all stack elements.

### Approach
Track `currNum` (current multi-digit number being parsed) and `lastOp` (operator seen before `currNum`). On each operator/end: apply `lastOp` with `currNum` — push for `+`, push negative for `−`, pop-compute-push for `*`/`÷`. Update `lastOp`, reset `currNum`. Return `stack.reduce((a,b) => a+b, 0)`.

### Solution

```js
function calculate(s) {
  const stack = [];
  let currNum = 0;
  let lastOp = '+'; // implicit '+' before the first number

  for (let i = 0; i < s.length; i++) {
    const ch = s[i];

    if (ch >= '0' && ch <= '9') {
      currNum = currNum * 10 + Number(ch); // build multi-digit number
    }

    // Process when we hit an operator or the last character
    if ((ch === '+' || ch === '-' || ch === '*' || ch === '/') || i === s.length - 1) {
      if (lastOp === '+') {
        stack.push(currNum);              // defer addition: push as positive
      } else if (lastOp === '-') {
        stack.push(-currNum);             // defer subtraction: push as negative
      } else if (lastOp === '*') {
        stack.push(stack.pop() * currNum); // resolve immediately: multiply with previous
      } else if (lastOp === '/') {
        stack.push(Math.trunc(stack.pop() / currNum)); // resolve immediately
      }
      lastOp = ch;   // update operator for next number
      currNum = 0;   // reset number accumulator
    }
    // Spaces are skipped naturally (neither digit nor operator → no action)
  }

  // All + and - results are on the stack as signed values; sum them
  return stack.reduce((sum, val) => sum + val, 0);
}
```

### Dry Run

```
s = "3+5 / 2"
lastOp='+', currNum=0, stack=[]

ch='3': digit. currNum=3.
ch='+': operator. lastOp='+' → push currNum=3. stack=[3].
```

### Complexity
- Time: O(n) — one pass through the string; each character processed in O(1).
- Space: O(n) — in the worst case (all `+` operators), all numbers are pushed onto the stack.

### Edge Cases
- **Multi-digit numbers** `"12+34"`: `currNum = 1*10+2 = 12` after processing `'1'` then `'2'`. Correctly accumulated.
- **Leading/trailing spaces**: spaces are neither digits nor operators — the `if` conditions simply don't trigger, and `currNum` and `lastOp` are unchanged.
- **Expression starts with a negative number** `"-1+2"`: Basic Calculator II's constraints say only non-negative integers; a leading `-` is not in the test cases. For variants with negatives, initialize `lastOp = '+'` and treat the first token as following a virtual `+`.
- **Division producing negative result** `"5-6/2"`: `lastOp='-'` → push `-currNum = -6`. Wait no — `lastOp` at `'/'` is `'+'` from `5`, then `'/'` processes `6/2=3`... Let me reconsider: "5-6/2" → 5 - (6/2) = 5 - 3 = 2. With the algorithm: push 5 (lastOp=+). At `/`, lastOp=`-` → push -6. At end with currNum=2, lastOp=`/` → pop -6, trunc(-6/2)=-3, push -3. stack=[5,-3]. Sum=2 ✓. Correct — the sign of the number is absorbed when it's pushed; division operates on the signed value.

### Follow-up Questions
- "Add parentheses support (Basic Calculator III)?" — When `(` is encountered: push the current result and operator onto an outer-context stack, reset; when `)` is encountered: evaluate the inner stack, then combine with the outer context. Recursive structure maps naturally to a stack.
- "Support exponentiation `^` with right-associativity?" — The `^` operator requires special handling in Shunting-Yard (right-associative: don't pop operators of equal precedence before pushing). The stack approach here handles only left-to-right operators cleanly.

## Quick Reference — Stack Pattern Decision Tree

```
What is the problem's structural shape?
│
├── EVALUATE AN EXPRESSION?
│   ├── Postfix / RPN → operand stack
│   │   Push numbers; on operator, pop right then left, compute, push result.
│   │   Invariant: stack holds all evaluated-but-not-yet-consumed subexpression results.
│   │
│   ├── Infix, no parentheses → linear scan with lastOp tracking
│   │   +/−: push (defer to final sum). */÷: pop and push immediately (resolve now).
│   │   Final answer = sum of stack.
│   │
│   └── Infix, with parentheses → two-stack (operand + operator) or Shunting-Yard
│       On ")": evaluate operator stack until "(" is popped.
│
├── MATCH / BALANCE DELIMITERS?
│   └── Push openers; on closer, check top; pop on match; fail on mismatch or wrong type.
│       Return true iff stack is empty at the end.
│       Invariant: stack holds all unmatched openers in arrival order.
│
├── FIND NEAREST GREATER / SMALLER ELEMENT (left or right)?
│   ├── Next GREATER → monotonic DECREASING stack (pop when incoming > top)
│   │   Each popped element's "next greater" = the incoming element.
│   │   Store indices when distance matters; store values when identity only.
│   │
│   ├── Next SMALLER → monotonic INCREASING stack (pop when incoming < top)
│   │
│   ├── Circular array → process 2× (indices 0..2n-1 mod n)
│   │
│   └── Both left and right boundary → two passes (left-to-right + right-to-left)
│       or single pass storing both boundaries per element.
│
├── MAXIMUM AREA / SPAN PROBLEMS (histogram, skyline)?
│   └── Monotonic increasing stack of INDICES.
│       Pop when shorter bar arrives; compute area using:
│         height = heights[popped index]
│         width  = current_index - new_stack_top - 1  (or current_index if stack empty)
│       Sentinel value 0 at the end flushes all remaining bars.
│
├── AUGMENTED STACK (O(1) min, max, or other aggregate)?
│   └── Store (value, aggregate_so_far) pairs, or maintain a parallel auxiliary stack.
│       On push: compute new aggregate = combine(val, aux_top).
│       On pop: pop both main and auxiliary. Aggregate rolls back automatically.
│
└── NESTED STRUCTURE / DECODE?
    └── On opening delimiter / start token: push current context (accumulated value, multiplier).
        On closing delimiter / end token: pop context; combine inner result with outer.
        Invariant: stack holds the state of all "outer scopes" not yet resolved.
```

## Common Bugs Checklist

Before submitting any stack-based solution, verify:

1. **RPN: popping right before left for non-commutative operators?** — `const right = stack.pop(); const left = stack.pop()` is the correct order. Reversing it gives the wrong result for subtraction and division: `["6","3","/"]` produces `0` (3/6) instead of `2` (6/3) if left and right are swapped.

2. **RPN: using `parseInt` not `Number` for tokens with leading minus signs?** — Token `"-11"` must parse to `-11`. `parseInt("-11", 10)` = -11 ✓. Using `Number("-11")` also works, but `parseInt` is clearer in intent for integer-only problems. Do not check `token === '-'` as the operator condition — a negative number token also starts with `-`. Always check against the four operator strings explicitly: `token === '+' || token === '-' || token === '*' || token === '/'`.

3. **RPN: division truncates toward zero, not floor?** — `Math.trunc(-7/2) = -3` (correct). `Math.floor(-7/2) = -4` (wrong). Always use `Math.trunc` for integer division in JS. In Python, use `int(a/b)` not `a//b`.

4. **Valid Parentheses: checking only character equality, not bracket-type matching?** — `"([)]"` passes if you only check "is top non-empty?" without verifying the type. The top must be the *exact matching opener* for the current closer. Use a map `{')':'(', ']':'[', '}':'{'}` and compare `top === match[closer]`.

5. **Valid Parentheses: returning true without checking stack emptiness at the end?** — `"((("` processes without ever returning false inside the loop, but the stack is not empty — must return `stack.length === 0`, not `true`.

6. **Monotonic stack: storing values when indices are needed?** — Daily Temperatures requires `answer[j] = i - j` — impossible to compute without the stored index `j`. If the problem needs position, span, or distance, always store indices. Recover the value via `nums[idx]` when needed inside the loop.

7. **Monotonic stack: wrong pop condition direction?** — "Next greater" pops when `incoming > top` (decreasing stack). "Next smaller" pops when `incoming < top` (increasing stack). Swapping the condition produces the opposite answer silently — no error, just wrong output.

8. **Histogram: width computation when stack is empty after a pop?** — When `stack.length === 0` after popping, the left boundary is index 0. Width = `i` (not `i - (-1) - 1 = i`, but derived via `i - stack.top - 1` would crash). Always use: `const w = stack.length === 0 ? i : i - stack[stack.length-1] - 1`.

9. **Histogram: forgetting the sentinel value at the end?** — Without a trailing `0` sentinel, bars in the stack at the end of the loop are never processed. Add a sentinel by iterating `i <= n` (not `i < n`) and using `const currHeight = i === n ? 0 : heights[i]`.

10. **Min Stack: only pushing to aux min-stack when new min is strictly smaller, then popping only when value equals min?** — The "push only on new min" optimization requires popping the aux min-stack only when `main.top === minStack.top` — not on every pop. Missing this condition causes the aux stack to underflow when values greater than the min are pushed (they weren't pushed to aux, but we're trying to pop them from it).

11. **Basic Calculator II: not triggering processing on the last character?** — If the loop only processes on operator characters, the final number is never pushed onto the stack. Add `|| i === s.length - 1` to the condition so the last accumulated `currNum` is processed with `lastOp`.

12. **Basic Calculator II: initializing `lastOp` to `'+'`, not `''` or `null`?** — The first number in the expression has an implicit `+` before it. Initializing `lastOp = '+'` ensures the first number is pushed as positive. Any other initialization produces incorrect handling of the first number.

**Final Tip:** At the 5 YOE level, the decisive signal for stack problems is identifying *which of the three stack roles* the data structure plays before writing any code: (1) **deferred evaluation buffer** — elements are pushed and held until an operator or delimiter resolves them (RPN, infix calculator, parentheses matching); (2) **monotonic candidate set** — elements whose "answer" hasn't been determined yet are held on the stack, and are answered and removed the moment a qualifying element arrives (next greater/smaller, histogram); (3) **context snapshot** — the stack preserves the state of an outer scope when entering a nested scope, and restores it when exiting (nested parentheses, Decode String, Basic Calculator with brackets). State this role in one sentence before writing any code: "I'll use a monotonic decreasing stack of indices — each index waits on the stack until a warmer temperature arrives, at which point it's answered and popped." That framing is the mark of a senior who owns the pattern, not just the solution.
