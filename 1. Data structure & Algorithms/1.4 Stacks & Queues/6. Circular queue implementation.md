## Topic A: Circular Queue Fundamentals

### Section A1: The Core Problem and Design

**Q1. What is a circular queue, and what inefficiency in a naive array-based queue does it solve?**

A: A naive array-based queue with a `front` pointer that advances on dequeue and a `rear` pointer that advances on enqueue works correctly — until `rear` reaches the end of the array. Even if the front half of the array is empty (freed by prior dequeues), no new elements can be enqueued because `rear` has no room to advance. The two "fixes" are: (1) shift all elements left on every dequeue — O(n) per dequeue, unacceptable; or (2) treat the array as a ring — wrap both `front` and `rear` around using modular arithmetic, reusing slots freed at the front. The circular queue implements option 2: `nextIndex = (index + 1) % capacity` for both pointers, making enqueue and dequeue O(1) and reusing every freed slot.

```
Naive queue problem:
  arr = [_, _, _, 3, 4, 5]   front=3, rear=5, capacity=6
  rear is at the end → can't enqueue even though 3 slots are free at the front!

Circular queue fix:
  rear advances: (5+1) % 6 = 0 → wraps to slot 0
  arr = [6, _, _, 3, 4, 5]   front=3, rear=0  (logically: [3,4,5,6])
  Free slot at index 1, 2 still available for future enqueues ✓
```

**Q2. What are the three strategies to distinguish "full" from "empty" in a circular queue, and how does each work?**

A: When a circular queue is empty and when it is full, `front` and `rear` can coincide at the same index — ambiguity arises. Three strategies resolve this:

**Strategy 1 — Size counter** (simplest, no wasted slots): Maintain an integer `size` alongside `front` and `rear`. Empty: `size === 0`. Full: `size === capacity`. The `front === rear` coincidence is disambiguated entirely by `size`. This is the most readable approach and wastes no capacity.

**Strategy 2 — One-slot sacrifice**: Allocate `capacity + 1` slots but logically treat the buffer as holding at most `capacity` elements. One slot is permanently "sacrificed" as a separator. Empty: `rear === front`. Full: `(rear + 1) % (capacity + 1) === front`. This avoids storing a separate counter but requires allocating one extra slot.

**Strategy 3 — Boolean flag**: Store an `isEmpty` or `isFull` boolean alongside `front` and `rear`. Empty: `front === rear && isEmpty`. Full: `front === rear && !isEmpty`. Updated on every enqueue/dequeue. Adds one boolean of state but no extra array slot.

```
Comparison for capacity=4:

State       | front | rear | size (S1) | arr size (S2) | flag (S3)
------------|-------|------|-----------|---------------|----------
Empty       |   0   |  0   | 0         | 5 slots       | isEmpty=true
1 element   |   0   |  0   | 1         | 5 slots       | isEmpty=false
Full (4)    |   0   |  3   | 4         | 5 slots (rear=(front-1+5)%5=4≠front) | isFull=true

Strategy 1 is preferred for implementation clarity.
Strategy 2 is preferred in embedded/hardware contexts (no extra state variable).
```

**Q3. How does modular arithmetic serve as the core computational primitive of all circular queue operations?**

A: Every pointer movement in a circular queue is a modular increment or decrement:

- **Advance forward**: `(index + 1) % capacity` — used when enqueueing (advance `rear`) and dequeueing (advance `front`).
- **Step backward**: `(index - 1 + capacity) % capacity` — used in deque operations to insert at the front (step `front` back) or peek/remove from the rear (step `rear` back). The `+ capacity` before the modulo handles negative intermediate values in JavaScript and Python where `(-1) % n` returns `-1` instead of `n-1`.

The circular property is entirely encoded in these two expressions. Every other operation (isEmpty, isFull, Front, Rear) is a direct array lookup at `front` or `rear` — O(1) with no modular arithmetic needed.

```
Forward: enqueue val
  this.arr[this.rear] = val;
  this.rear = (this.rear + 1) % this.capacity;

Backward (deque insertFront):
  this.front = (this.front - 1 + this.capacity) % this.capacity;
  this.arr[this.front] = val;

Why + capacity matters:
  capacity=5, front=0: (0 - 1 + 5) % 5 = 4 ✓
  capacity=5, front=0: (0 - 1) % 5 = -1 ✗ (wrong in JS/Python)
```

**Q4. What are the two "tail pointer conventions," and which is used in standard implementations?**

A: Two conventions exist for what `rear` (or `tail`) points to:

**Convention A — rear points to the LAST FILLED slot** (write-then-advance on enqueue): To enqueue: advance `rear` first (`rear = (rear+1)%cap`), then write (`arr[rear] = val`). To peek rear: read `arr[rear]` directly. Initialization: `front = rear = capacity - 1` (pointing to the imaginary "slot before slot 0") or handled with an isEmpty flag. This is slightly awkward to initialize.

**Convention B — rear points to the NEXT EMPTY slot** (write-at-then-advance on enqueue): To enqueue: write at `rear` (`arr[rear] = val`), then advance (`rear = (rear+1)%cap`). To peek rear: read `arr[(rear - 1 + cap) % cap]`. Initialization: `front = rear = 0`. This is the standard convention — simpler initialization, cleaner symmetry between enqueue and dequeue.

```
Convention B (standard — used throughout this document):

Initial:  front=0, rear=0, size=0
Enqueue(A): arr[0]=A, rear=(0+1)%4=1. front=0, rear=1, size=1
Enqueue(B): arr[1]=B, rear=2.          front=0, rear=2, size=2
Dequeue():  val=arr[0], front=1.       front=1, rear=2, size=1  → returns A
Enqueue(C): arr[2]=C, rear=3.          front=1, rear=3, size=2
Enqueue(D): arr[3]=D, rear=0.          front=1, rear=0, size=3 ← wraparound!
Peek rear:  arr[(0-1+4)%4] = arr[3] = D ✓
```

**Q5. What is the time and space complexity of every circular queue operation?**

A: All operations are O(1) time and O(1) extra space:

| Operation | Time | Implementation |
|---|---|---|
| `enqueue(val)` | O(1) | Write at `arr[rear]`, advance `rear`, increment `size` |
| `dequeue()` | O(1) | Read `arr[front]`, advance `front`, decrement `size` |
| `Front()` | O(1) | Return `arr[front]` |
| `Rear()` | O(1) | Return `arr[(rear - 1 + cap) % cap]` |
| `isEmpty()` | O(1) | Return `size === 0` |
| `isFull()` | O(1) | Return `size === capacity` |

Space: O(capacity) — the array is allocated upfront and never resized. This is the defining property of a circular queue: bounded, constant-time everywhere. Compare to a dynamic queue (e.g., linked list): all operations are still O(1) but with O(1) amortized allocation overhead per enqueue and heap fragmentation.

### Section A2: Advanced Patterns

**Q6. Walk through a complete enqueue/dequeue sequence showing wraparound and disambiguation.**

A: Using a capacity-4 circular queue with the size-counter strategy:

```
Initial: arr=[_,_,_,_], front=0, rear=0, size=0

enqueue(1): arr[0]=1, rear=1, size=1. arr=[1,_,_,_]
enqueue(2): arr[1]=2, rear=2, size=2. arr=[1,2,_,_]
enqueue(3): arr[2]=3, rear=3, size=3. arr=[1,2,3,_]
enqueue(4): arr[3]=4, rear=(3+1)%4=0, size=4. arr=[1,2,3,4]  ← FULL
isFull() → size===capacity → true ✓

dequeue(): val=arr[0]=1, front=(0+1)%4=1, size=3. arr=[_,2,3,4]
dequeue(): val=arr[1]=2, front=2, size=2.           arr=[_,_,3,4]

enqueue(5): arr[rear=0]=5, rear=1, size=3.  arr=[5,_,3,4] ← wraparound!
enqueue(6): arr[rear=1]=6, rear=2, size=4.  arr=[5,6,3,4] ← FULL again

Front() → arr[front=2] = 3 ✓
Rear()  → arr[(rear-1+4)%4] = arr[1] = 6 ✓

Note: front=2, rear=2, but size=4 (not 0) — disambiguated by size counter ✓
```

**Q7. How does a circular queue compare to a linked-list-based queue, and when do you choose each?**

A: Both provide O(1) enqueue and dequeue. The differences are structural:

| Property | Circular Queue (array) | Linked List Queue |
|---|---|---|
| Memory | Fixed upfront allocation | Dynamic per-node allocation |
| Cache performance | Excellent (contiguous array) | Poor (pointer chasing) |
| Memory overhead | Zero per element | One `next` pointer per node |
| Capacity | Fixed — cannot grow | Unbounded |
| Memory wastage | Possible (unused slots) | None |
| Pointer arithmetic | Modular index math | `node.next` dereferences |

Choose circular queue when: capacity is known in advance (OS ring buffers, network I/O queues, DSP audio buffers); cache performance is critical; you need predictable memory usage. Choose linked-list queue when: capacity is unknown or highly variable; memory efficiency for sparse usage matters more than cache performance.

## Topic B: Deque and Monotonic Deque

### Section B1: Fundamentals

**Q8. What is a circular deque, and what four operations does it add over a standard circular queue?**

A: A deque (double-ended queue) supports insertion and removal at both ends. A circular deque adds to the standard queue's `enqueueRear` / `dequeueFront` pair:

- `insertFront(val)` — insert at the front (before current front element)
- `deleteLast()` — remove from the rear (the most recently added element)
- `getFront()` — peek front (same as queue)
- `getRear()` — peek rear (same as queue)

Implementation adds a backward-step operation: `insertFront` steps `front` backward (`front = (front - 1 + cap) % cap`) then writes at `arr[front]`. `deleteLast` reads `arr[(rear - 1 + cap) % cap]` then steps `rear` backward. This is the `+ capacity` operation from Q3 in action.

```
Deque operations on arr=capacity 4:

Initial: front=2, rear=2, size=0 (can start anywhere; 0 is conventional)

insertLast(A): arr[2]=A, rear=3, size=1.  arr=[_,_,A,_]
insertFront(B): front=(2-1+4)%4=1, arr[1]=B, size=2. arr=[_,B,A,_]
insertFront(C): front=(1-1+4)%4=0, arr[0]=C, size=3. arr=[C,B,A,_]
insertLast(D):  arr[3]=D, rear=0, size=4. arr=[C,B,A,D]  ← FULL

getFront() → arr[0] = C ✓
getRear()  → arr[(0-1+4)%4] = arr[3] = D ✓

deleteFront(): val=arr[0]=C, front=(0+1)%4=1, size=3. arr=[_,B,A,D]
deleteLast():  rear=(0-1+4)%4=3, val=arr[3]=D, size=2. arr=[_,B,A,_]
```

**Q9. What is a monotonic deque, and what structural invariant does it maintain at all times?**

A: A monotonic deque is a deque whose elements are always in monotonically increasing or decreasing order from front to rear. The invariant is enforced by pruning from the rear before each insertion: when inserting a new element `x` at the rear, first remove all rear elements that are "dominated" by `x` (i.e., elements that, while `x` is in the window, can never be the answer because `x` is more extreme). The front is separately maintained by evicting elements that have expired (fallen outside the current window). The deque therefore stores only *candidate answers* for the current and future windows.

```
Monotonic decreasing deque (front = maximum of current window):

Invariant: deque[front] ≥ deque[...] ≥ deque[rear]

On new element x at index i:
  PRUNE from rear: while deque not empty AND nums[deque.rear] ≤ x: pop rear
  ADD to rear: push i
  EVICT from front: if deque.front ≤ i - k: pop front
  ANSWER: nums[deque.front] = maximum of current window

Each index is pushed and popped at most once → O(n) total ✓
```

**Q10. Why must eviction (from front) and pruning (from rear) be conceptually and operationally distinct?**

A: They serve entirely different purposes and must never be confused:

**Eviction (from front)** is correctness-driven: an element that has slid out of the k-size window cannot contribute to any future answer. Check: `deque.front <= i - k` → pop front. This is a validity guard.

**Pruning (from rear)** is optimization-driven: an element at the rear that is ≤ the incoming element will never be the answer while the incoming element remains in the window (it's smaller AND older — dominated on both dimensions). It is safe and necessary to discard it permanently. Check: `nums[deque.rear] <= nums[i]` → pop rear.

Mixing them (e.g., evicting from the rear or pruning from the front) produces incorrect results. The two-sided maintenance is what gives the monotonic deque its dual property: the deque stays small (rear pruning) and stays valid (front eviction).

```
What gets removed from each end — and why:

Rear: "Is the current rear element useful in the future?"
  If nums[rear] ≤ nums[incoming]: NO — incoming beats it in value AND will outlast it.
  Action: pop rear. (permanently discarded — will never be an answer)

Front: "Is the front element still within the window?"
  If deque.front <= i - k: NO — it has slid out of scope.
  Action: pop front. (correctly expired, not dominated)
```

### Section B2: Advanced Patterns

**Q11. How does the "two-pointer" nature of the deque front and rear differ from the fixed-gap two-pointer technique for linked lists?**

A: The linked-list two-pointer technique uses a *fixed spatial gap* between two pointers traversing in the same direction at the same speed. The deque's front and rear are *independent endpoints of a window*: front evicts expired elements (controlled by the window size constraint), rear prunes dominated elements (controlled by the monotonic invariant). The gap between front and rear is variable and depends on the input distribution — in the worst case (strictly decreasing input for a max deque), every element is added without pruning and the deque can grow to size k. In the best case (strictly increasing input), every rear element is pruned immediately and the deque always has size 1.

**Q12. How do you compute a moving average using a circular buffer in O(1) per update?**

A: Maintain a circular buffer of the last `k` values and a running `sum`. On each new value `val`: if the buffer is full, subtract the overwritten (oldest) value from `sum` before overwriting. Write `val` at `arr[rear]`, advance `rear`, add `val` to `sum`. Return `sum / min(count, k)`. The O(1) trick is the running sum — instead of re-summing all k elements (O(k) per update), we surgically add the new value and subtract the evicted value.

```
Circular buffer moving average — capacity k=3:

buf=[_,_,_], rear=0, sum=0, count=0

next(1): buf[0]=1, rear=1, sum=1, count=1. avg=1/1=1
next(10): buf[1]=10, rear=2, sum=11, count=2. avg=11/2=5.5
next(3): buf[2]=3, rear=0, sum=14, count=3. avg=14/3=4.67
next(5): buf is full. outgoing = buf[rear=0] = 1. sum -= 1 → 13.
  buf[0]=5, rear=1, sum=13+5=18, count=4. avg=18/3=6

O(1) per update — no recomputation ✓
```

## Topic C: Cross-Topic & Interview-Style Questions

**Q13. "What happens when front === rear in a circular queue, and how do you handle it?"**

A: The answer depends entirely on which disambiguation strategy is in use — and stating this upfront is itself the answer interviewers want:

- **Size counter strategy**: `front === rear` is meaningless on its own. Empty is `size === 0`; full is `size === capacity`. The `front === rear` coincidence may occur in either state without any special handling — `size` resolves all ambiguity.
- **One-slot sacrifice**: `front === rear` unambiguously means the queue is empty. The full condition is `(rear + 1) % (capacity + 1) === front` — front and rear are never equal when full (one sacrificed slot always separates them).
- **Boolean flag**: `front === rear` is ambiguous by itself; the stored flag resolves it.

In an interview, state your strategy in the first sentence: "I'll use a size counter — it's the cleanest approach and wastes no capacity."

**Q14. "Walk me through why a circular queue is not the same as a circular linked list."**

A: A circular queue is an array-based data structure with head/tail index pointers and modular wraparound — the "circular" refers to the logical wrap of the index space, not a physical ring of nodes. A circular linked list is a singly or doubly linked list where the last node's `next` pointer points back to the head. The two share the word "circular" but differ in: memory layout (contiguous array vs heap-allocated nodes), traversal (index arithmetic vs pointer dereference), insertion at arbitrary positions (O(n) with index, O(1) with pointer if you have the node), and use cases (circular queue → bounded FIFO buffer; circular linked list → round-robin scheduling, Josephus problem).

**Q15. "Compare the circular queue to a stack and a plain queue — when do you specifically need a circular queue over the others?"**

A: Use a circular queue specifically when you need: (1) FIFO order, (2) bounded capacity with O(1) operations, and (3) memory reuse (no dynamic allocation). A stack is LIFO — wrong order. A plain (unbounded) queue grows dynamically — wrong for memory-constrained or real-time systems. The circular queue's distinguishing use cases: producer-consumer buffers in OS kernels, audio/network ring buffers, sliding-window aggregation (moving average, hit counters), and any system where "oldest data is overwritten when full" behavior (overwrite mode ring buffers) is acceptable.

**Q16. "What is the relationship between a monotonic deque and a monotonic stack? What does the deque add?"**

A: A monotonic stack handles "nearest greater/smaller element" problems — it processes each element once and pops dominated elements as new elements arrive, giving answers for historical elements. It only removes from the top (one end). A monotonic deque extends this to sliding window problems by adding the ability to remove expired elements from the front — elements that once were candidates but have since slid out of the window. The deque's dual-end maintenance handles the *window constraint* (front eviction) and the *monotonic invariant* (rear pruning) simultaneously. A monotonic stack cannot expire elements from its bottom — making it unable to enforce a fixed-size window.

```
Monotonic stack:
  Removes from one end (top) when incoming dominates.
  Use for: next greater element, largest rectangle (no window size constraint).

Monotonic deque:
  Removes from rear when incoming dominates (same as stack).
  Removes from front when element expires (window constraint — unique to deque).
  Use for: sliding window max/min (fixed-k window).
```

**Q17. "In one sentence each, state the invariant each part of the circular queue maintains."**

A:
- **Size counter**: `size` always equals the number of valid elements currently in the buffer, regardless of `front` and `rear` positions.
- **Front pointer**: `arr[front]` always holds the oldest unconsumed element — the next element to be dequeued.
- **Rear pointer** (Convention B): `rear` always points to the next empty slot where the next enqueue will write.
- **Modular arithmetic**: every pointer advance is `(index + 1) % capacity`, ensuring the index wraps to 0 after reaching `capacity - 1`.
- **Monotonic deque front**: always holds the index of the maximum (or minimum) element currently within the window — the answer for the current window position.
- **Monotonic deque rear**: always holds the index of the most recently added element that has not been pruned — the smallest (for max deque) among current candidates.

**Q18. "What is the time complexity of each operation in a monotonic deque-based sliding window, and why is it O(n) and not O(nk)?"**

A: The naive approach — for each of the n windows, scan all k elements to find the max — is O(nk). The monotonic deque achieves O(n) because each of the n indices is added to the deque exactly once and removed (from either front or rear) at most once. Total enqueue operations = n; total dequeue operations ≤ n (each index removed at most once). The per-element work is O(1) amortized — not O(k) per window. The result is O(n) total, regardless of window size k.

## Problem 1 — Design Circular Queue

### Problem
Design a circular queue that supports the following operations. The circular queue is a linear data structure in which the operations are performed based on FIFO and the last position is connected back to the first.

```
MyCircularQueue(k)  — Initializes the object with size k.
enQueue(value)      — Inserts element into queue. Returns true on success, false if full.
deQueue()           — Deletes from the front of the queue. Returns true on success, false if empty.
Front()             — Gets the front item. Returns -1 if empty.
Rear()              — Gets the last item. Returns -1 if empty.
isEmpty()           — Checks if empty.
isFull()            — Checks if full.

Input:
  ["MyCircularQueue","enQueue","enQueue","enQueue","enQueue","Rear","isFull","deQueue","enQueue","Rear"]
  [[3],[1],[2],[3],[4],[],[],[],[4],[]]
Output: [null,true,true,true,false,3,true,true,true,4]
```

### Pattern Recognition
Array-based ring buffer with size counter — fixed-capacity array, `front` and `rear` indices advanced with modular arithmetic, `size` counter disambiguates full/empty when `front === rear`.

### Key Insight
The two-pointer design (`front` = read head, `rear` = write head) combined with modular index arithmetic creates the illusion of an infinite loop over a finite array. The size counter is the simplest and most readable disambiguation strategy — it avoids wasting array slots and makes isEmpty/isFull self-evident.

### Approach
Allocate `arr` of length `k`. Initialize `front = rear = size = 0`. `enQueue`: if full, return false; write `arr[rear]`; advance `rear = (rear+1)%k`; increment `size`. `deQueue`: if empty, return false; advance `front = (front+1)%k`; decrement `size`. `Front`: if empty, -1; else `arr[front]`. `Rear`: if empty, -1; else `arr[(rear-1+k)%k]`.

### Solution

```js
class MyCircularQueue {
  constructor(k) {
    this.arr = new Array(k); // fixed-size backing array
    this.capacity = k;
    this.front = 0;          // index of the oldest element (next to dequeue)
    this.rear = 0;           // index of the next empty slot (next to enqueue)
    this.size = 0;           // number of valid elements currently stored
  }

  enQueue(value) {
    if (this.isFull()) return false;

    this.arr[this.rear] = value;                    // write at next empty slot
    this.rear = (this.rear + 1) % this.capacity;   // advance rear with wraparound
    this.size++;
    return true;
  }

  deQueue() {
    if (this.isEmpty()) return false;

    this.front = (this.front + 1) % this.capacity; // advance front past consumed element
    this.size--;
    return true;
  }

  Front() {
    return this.isEmpty() ? -1 : this.arr[this.front];
  }

  Rear() {
    if (this.isEmpty()) return -1;
    // rear points to NEXT empty slot; last filled slot is one behind
    return this.arr[(this.rear - 1 + this.capacity) % this.capacity];
  }

  isEmpty() {
    return this.size === 0;
  }

  isFull() {
    return this.size === this.capacity;
  }
}
```

### Dry Run

```
MyCircularQueue(3): arr=[_,_,_], capacity=3, front=0, rear=0, size=0

enQueue(1): !isFull. arr[0]=1, rear=1, size=1. arr=[1,_,_]. return true.
enQueue(2): arr[1]=2, rear=2, size=2. arr=[1,2,_]. return true.
enQueue(3): arr[2]=3, rear=(2+1)%3=0, size=3. arr=[1,2,3]. return true.

enQueue(4): isFull (size===3). return false ✓

Rear():     arr[(rear-1+3)%3] = arr[(0-1+3)%3] = arr[2] = 3. return 3 ✓
isFull():   size===capacity → true ✓

deQueue():  !isEmpty. front=(0+1)%3=1, size=2. arr=[_,2,3]. return true.
  (slot 0 is now "free" — front no longer points to it)

enQueue(4): !isFull. arr[rear=0]=4, rear=1, size=3. arr=[4,2,3]. return true.
  (slot 0 reused — the circular wraparound!)

Rear():     arr[(1-1+3)%3] = arr[0] = 4 ✓

State: front=1, rear=1, size=3 (full)
  front===rear but size=3 → unambiguously full ✓
  arr=[4,2,3], logical order: [2,3,4] (front=1 → 2, then 3, then 4) ✓
```

### Complexity
- Time: O(1) for all six operations — all are direct array accesses or index arithmetic.
- Space: O(k) — fixed array of size k allocated at construction; no dynamic resizing.

### Edge Cases
- **enQueue when full**: `isFull()` guard returns false immediately — array is not modified, `rear` does not advance.
- **deQueue when empty**: `isEmpty()` guard returns false immediately — `front` does not advance (no invalid read).
- **Rear() with one element**: `rear = 1`, `front = 0`. `(1-1+k)%k = 0 = front`. Returns `arr[0]` = the only element. Both Front() and Rear() return the same element — correct.
- **Wraparound at Rear()**: when `rear = 0` (just wrapped), `(0-1+k)%k = k-1`. Returns `arr[k-1]` — the slot just before the imaginary wrap point. Correct.
- **Full with front === rear**: after interleaved enqueues and dequeues, front and rear may coincide at any index. `size === capacity` always correctly identifies this as full regardless of the coincident index value.

### Follow-up Questions
- "Implement using one-slot sacrifice?" — Allocate `k+1` slots. `isFull = (rear+1)%(k+1) === front`. `isEmpty = rear === front`. Drop the `size` counter entirely. Trade-off: one array slot wasted, no size variable.
- "Thread-safe circular queue?" — Wrap `enQueue` and `deQueue` in a mutex lock, or implement a lock-free ring buffer using atomic compare-and-swap (CAS) on the `rear` and `front` indices.
- "Auto-resize when full (amortized O(1))?" — Detect full condition; allocate a new array of double capacity; copy elements in logical order (front to rear, unwinding the wraparound); reset front=0, rear=size.

## Problem 2 — Design Circular Deque

### Problem
Design a circular double-ended queue (deque) that supports insertion and deletion from both ends.

```
MyCircularDeque(k)      — Initialize with max size k.
insertFront(value)      — Add item to front. Returns true if successful.
insertLast(value)       — Add item to rear. Returns true if successful.
deleteFront()           — Delete item from front. Returns true if successful.
deleteLast()            — Delete item from rear. Returns true if successful.
getFront()              — Get front item, or -1 if empty.
getRear()               — Get rear item, or -1 if empty.
isEmpty()               — Check if empty.
isFull()                — Check if full.

Input:
  ["MyCircularDeque","insertLast","insertLast","insertFront","insertFront","getRear","isFull","deleteLast","insertFront","getFront"]
  [[3],[1],[2],[3],[4],[],[],[],[4],[]]
Output: [null,true,true,true,false,2,true,true,true,4]
```

### Pattern Recognition
Array-based ring buffer with bidirectional pointer movement — extends the circular queue by adding backward index stepping `(index - 1 + capacity) % capacity` for front operations, enabling O(1) insertion and deletion at both ends.

### Key Insight
The circular queue only needed `(index + 1) % capacity` (forward step). The deque additionally needs `(index - 1 + capacity) % capacity` (backward step). `insertFront` steps `front` backward before writing; `deleteLast` steps `rear` backward before reading. The `+ capacity` inside the modulo is essential — without it, `(0 - 1) % capacity` returns `-1` in JavaScript and Python, which is a valid (wrong) array index.

### Approach
Same initialization as circular queue. `insertFront`: if full, false; step `front` backward; write `arr[front]`; increment `size`. `insertLast`: same as `enQueue`. `deleteFront`: same as `deQueue`. `deleteLast`: if empty, false; step `rear` backward; decrement `size`. `getFront/getRear`: direct reads with empty guard.

### Solution

```js
class MyCircularDeque {
  constructor(k) {
    this.arr = new Array(k);
    this.capacity = k;
    this.front = 0;
    this.rear = 0;
    this.size = 0;
  }

  insertFront(value) {
    if (this.isFull()) return false;

    // Step front BACKWARD before writing (so arr[front] = new front element)
    this.front = (this.front - 1 + this.capacity) % this.capacity;
    this.arr[this.front] = value;
    this.size++;
    return true;
  }

  insertLast(value) {
    if (this.isFull()) return false;

    this.arr[this.rear] = value;
    this.rear = (this.rear + 1) % this.capacity; // advance rear AFTER writing
    this.size++;
    return true;
  }

  deleteFront() {
    if (this.isEmpty()) return false;

    this.front = (this.front + 1) % this.capacity; // advance front past consumed element
    this.size--;
    return true;
  }

  deleteLast() {
    if (this.isEmpty()) return false;

    // Step rear BACKWARD — it was pointing to NEXT empty slot; one step back = last filled
    this.rear = (this.rear - 1 + this.capacity) % this.capacity;
    this.size--;
    return true;
  }

  getFront() {
    return this.isEmpty() ? -1 : this.arr[this.front];
  }

  getRear() {
    if (this.isEmpty()) return -1;
    return this.arr[(this.rear - 1 + this.capacity) % this.capacity];
  }

  isEmpty() { return this.size === 0; }
  isFull()  { return this.size === this.capacity; }
}
```

```
  (logical order front→rear: arr[2]=3, arr[0]=1, arr[1]=2 → [3,1,2])

  (logical order: arr[2]=3, arr[0]=1 → [3,1])

  front was 2. (2-1+3)%3=1. arr[1]=4. size=3.
```

### Complexity
- Time: O(1) for all eight operations.
- Space: O(k) — same fixed array as circular queue.

### Edge Cases
- **insertFront when front=0**: `(0-1+k)%k = k-1`. Front moves to the last slot — the backward wraparound. Array position `k-1` is written. Correct.
- **deleteLast when size=1**: `rear` steps backward to `front`'s current position. After decrement: `size=0`, `rear === front`. `isEmpty()` returns true. Subsequent `getFront()` and `getRear()` both return -1 correctly.
- **Both ends pointing to same slot (size=1)**: `getFront()` = `arr[front]`; `getRear()` = `arr[(rear-1+k)%k]` = `arr[front]` (since rear = (front+1)%k). Both return the same element. Correct.
- **Interleaved insertFront and insertLast**: the modular arithmetic handles arbitrary interleaving — front and rear chase each other in opposite directions around the ring.

### Follow-up Questions
- "Deque as both stack and queue?" — A deque with only `insertLast`/`deleteLast` behaves as a stack (LIFO). With only `insertLast`/`deleteFront` it behaves as a queue (FIFO). It's the most general data structure in this family.
- "Implement without a separate size counter?" — Use the one-slot sacrifice: allocate `k+1` slots. `isFull = (rear+1)%(k+1) === front`. `isEmpty = rear === front`. Both insertFront and insertLast check `isFull` first. Saves one integer at the cost of one array slot.

## Problem 3 — Sliding Window Maximum

### Problem
Given an integer array `nums` and an integer `k`, find the maximum value in each contiguous subarray of size `k`. Return an array of these maximums.

```
Input:  nums = [1,3,-1,-3,5,3,6,7], k = 3
Output: [3,3,5,5,6,7]
  // Window [1,3,-1] → max 3
  // Window [3,-1,-3] → max 3
  // Window [-1,-3,5] → max 5
  // Window [-3,5,3] → max 5
  // Window [5,3,6] → max 6
  // Window [3,6,7] → max 7

Input:  nums = [1], k = 1
Output: [1]
```

### Pattern Recognition
Monotonic decreasing deque of indices — maintain a deque of candidate indices whose values are in decreasing order from front to rear. The front always holds the maximum of the current window. On each step: prune dominated rear elements, evict expired front elements, record the answer.

### Key Insight
The deque never needs to store more than k indices. More importantly, it stores far fewer in practice because smaller elements at the rear are pruned immediately upon arrival of a larger element. The front is always the maximum: the deque's decreasing order ensures the largest unseen candidate is always at the front, ready as an O(1) answer.

### Approach
`deque = []` (stores indices). For each index `i`: (1) Prune rear: while `deque.rear exists && nums[deque.rear] <= nums[i]`, pop rear. (2) Push `i` to rear. (3) Evict front: while `deque.front <= i - k`, pop front. (4) If `i >= k-1`: record `nums[deque.front]` as the current window's maximum.

### Solution

```js
function maxSlidingWindow(nums, k) {
  const deque = [];   // monotonic decreasing: stores indices, front=max, rear=smallest
  const result = [];

  for (let i = 0; i < nums.length; i++) {
    // Step 1: PRUNE rear — remove indices whose values are ≤ nums[i]
    // They can never be the window maximum while nums[i] is in the window
    while (deque.length > 0 && nums[deque[deque.length - 1]] <= nums[i]) {
      deque.pop(); // pop from rear
    }

    // Step 2: ADD current index to rear
    deque.push(i);

    // Step 3: EVICT front — remove indices that have slid out of the window
    while (deque[0] <= i - k) {
      deque.shift(); // pop from front
    }

    // Step 4: RECORD — only once the first full window is formed
    if (i >= k - 1) {
      result.push(nums[deque[0]]); // front index = index of current window maximum
    }
  }

  return result;
}
```

*Note: `Array.shift()` is O(n) in a standard JavaScript array. For a true O(1)-per-operation implementation, use a doubly-linked list or a fixed-size circular deque (from Problem 2) as the underlying deque. In interviews, the `shift()`-based implementation is acceptable; mention the O(1) alternative if asked.*

### Dry Run

```
  Prune: nums[deque.rear=0]=1 ≤ 3 → pop 0. deque=[]. Push 1. deque=[1].

  i < 2: no record.

  record nums[1] = 3. result=[3,3]. ✓
```

### Complexity
- Time: O(n) — each index is pushed to the deque exactly once and popped (from either end) at most once. Total deque operations ≤ 2n = O(n).
- Space: O(k) — the deque holds at most k indices at any time (elements from the current window).

### Edge Cases
- **k = 1**: every element is its own window maximum. No pruning ever occurs (deque always has one element); no eviction occurs. `result = nums[i]` for all i. Correct.
- **k = n**: one window covering the entire array. The deque accumulates indices; the answer is the global maximum at `i = n-1`.
- **All equal elements**: `nums[deque.rear] <= nums[i]` with equality → prune. The deque always has exactly one element (the most recent index). Maximum is always `nums[i]` for `i >= k-1`. Correct.
- **Strictly decreasing array**: no rear pruning ever occurs (each new element is smaller than the rear). The deque fills to size k, then the oldest element is evicted from the front at each step. The front is always the window maximum (the leftmost element). Correct.
- **Strictly increasing array**: every new element prunes all prior deque entries. The deque always has exactly one element (the current index). The maximum is always `nums[i]`. Correct.

### Follow-up Questions
- "Sliding window minimum?" — Change the prune condition from `<=` to `>=` (pop when `nums[deque.rear] >= nums[i]`). The deque becomes monotonically increasing; the front is the minimum.
- "True O(1) per operation implementation?" — Use the `MyCircularDeque` from Problem 2 as the underlying container. Replace `deque.push/pop` (rear operations) and `deque.shift/deque[0]` (front operations) with O(1) circular deque operations.
- "Return the index of the maximum, not its value?" — Return `deque[0]` (the front index) directly instead of `nums[deque[0]]`.

## Problem 4 — Moving Average from Data Stream

### Problem
Given a stream of integers and a window size `k`, calculate the moving average of all integers in the sliding window.

```
MovingAverage m = new MovingAverage(3);
m.next(1);   // return 1.0           (window: [1])
m.next(10);  // return 5.5           (window: [1,10])
m.next(3);   // return 4.666...      (window: [1,10,3])
m.next(5);   // return 6.0           (window: [10,3,5])
```

### Pattern Recognition
Circular buffer + running sum — a fixed-size array stores the last k values; a running sum is updated by adding the new value and subtracting the overwritten (oldest) value. Average = `runningSum / currentCount`.

### Key Insight
Re-computing the sum of all k elements on each `next()` call would be O(k) per call. The running sum trick makes it O(1): when the buffer is full and a new value overwrites the oldest slot, subtract the old value before overwriting. Only two arithmetic operations per call regardless of k.

### Approach
Allocate `buf[k]`. Track `rear = 0` (next write position), `count = 0` (total elements seen, capped at k for average denominator), `sum = 0`. On `next(val)`: if `count >= k`, subtract `buf[rear]` from sum (the value being overwritten). Write `buf[rear] = val`. Add `val` to sum. Advance `rear = (rear+1)%k`. Increment `count`. Return `sum / min(count, k)`.

### Solution

```js
class MovingAverage {
  constructor(k) {
    this.k = k;
    this.buf = new Array(k).fill(0); // circular buffer
    this.rear = 0;                   // next write position
    this.count = 0;                  // total elements received (unbounded)
    this.sum = 0;                    // running sum of elements in current window
  }

  next(val) {
    // If buffer is full, subtract the value about to be overwritten
    if (this.count >= this.k) {
      this.sum -= this.buf[this.rear]; // outgoing element leaves the window
    }

    // Write new value into the circular buffer
    this.buf[this.rear] = val;
    this.rear = (this.rear + 1) % this.k; // advance write position with wraparound

    // Update running sum and element count
    this.sum += val;
    this.count++;

    // Average over actual window size (< k until buffer fills for first time)
    return this.sum / Math.min(this.count, this.k);
  }
}
```

### Dry Run

```
MovingAverage(3): buf=[0,0,0], k=3, rear=0, count=0, sum=0

next(1):  count(0) < k(3) → no subtract.
  buf[0]=1, rear=1, sum=1, count=1.
  return 1 / min(1,3) = 1.0 ✓

next(10): count(1) < 3 → no subtract.
  buf[1]=10, rear=2, sum=11, count=2.
  return 11 / 2 = 5.5 ✓

next(3):  count(2) < 3 → no subtract.
  buf[2]=3, rear=0, sum=14, count=3.   ← rear wraps!
  return 14 / 3 = 4.666... ✓

next(5):  count(3) >= 3 → subtract buf[rear=0]=1. sum=14-1=13.
  buf[0]=5, rear=1, sum=13+5=18, count=4.
  return 18 / min(4,3) = 18/3 = 6.0 ✓

State: buf=[5,10,3], rear=1.
  Window: elements at indices 1,2,0 (reading from rear-k to rear-1): 10,3,5. sum=18 ✓

next(2):  count(4) >= 3 → subtract buf[rear=1]=10. sum=18-10=8.
  buf[1]=2, rear=2, sum=8+2=10, count=5.
  return 10/3 = 3.333... ✓
  (window: [3, 5, 2])
```

### Complexity
- Time: O(1) per `next()` call — two arithmetic operations (subtract old, add new), one modular advance.
- Space: O(k) — fixed circular buffer of size k.

### Edge Cases
- **k = 1**: every call replaces the single slot. `sum = val` (subtract previous, add current). Returns `val` as the average. Correct.
- **First k-1 calls**: `count < k`, so `min(count, k) = count`. The average is over the actual number of elements seen, not k. Correct — the window isn't "full" yet.
- **Zero values**: `buf[rear] = 0` means subtracting 0 from sum — harmless. Zeroes in the window are handled correctly.
- **Large k with few calls**: `count < k` for all calls; average is over all seen values. The buffer never wraps; only the first `count` slots are meaningful. Correct.

### Follow-up Questions
- "Weighted moving average (newer values weighted more)?" — Replace the equal-weight sum with a weighted sum: `sum += val * weight[rear]` and `sum -= buf[rear] * weight[rear]`. Pre-compute a fixed weight array of size k.
- "Running median instead of mean?" — O(1) median is much harder — requires two heaps (min-heap for upper half, max-heap for lower half) with O(log k) per operation. No circular buffer trick applies.
- "Thread-safe version?" — Guard `next()` with a mutex, or use an atomic running sum with a lock-free circular buffer.

## Problem 5 — Number of Recent Calls

### Problem
You have a `RecentCounter` class which counts the number of recent requests within a certain time frame. Implement `ping(t)` which records a new request at time `t` (in milliseconds) and returns the number of requests in the range `[t - 3000, t]` (inclusive). It is guaranteed that all calls to `ping` are made with strictly increasing values of `t`.

```
Input:  ["RecentCounter","ping","ping","ping","ping"]
        [[],[1],[100],[3001],[3002]]
Output: [null,1,2,3,3]
  // ping(1)    → requests in [1-3000,1]=[-2999,1]: {1} → 1
  // ping(100)  → [−2900,100]: {1,100} → 2
  // ping(3001) → [1,3001]: {1,100,3001} → 3
  // ping(3002) → [2,3002]: {100,3001,3002} → 3  (1 expired)
```

### Pattern Recognition
Queue-based sliding window — enqueue every new timestamp; dequeue timestamps from the front that fall outside the `[t-3000, t]` window. The queue's size at any point is the count of valid requests.

### Key Insight
Timestamps are strictly increasing, so expired timestamps are always at the front of the queue (oldest = smallest = front). A standard queue (FIFO) naturally holds timestamps in arrival order. Evicting from the front removes exactly the expired timestamps, and the queue's remaining size is the answer.

### Approach
Use a queue (array or deque). On `ping(t)`: push `t` to the rear. While `queue.front < t - 3000`: dequeue from front. Return `queue.size`.

### Solution

```js
class RecentCounter {
  constructor() {
    this.queue = []; // timestamps of all requests in [t-3000, current_t]
    this.front = 0;  // use a pointer for O(1) "dequeue" without shifting the array
  }

  ping(t) {
    this.queue.push(t); // new request always goes to the rear

    // Evict timestamps that are older than t - 3000 (outside the window)
    while (this.queue[this.front] < t - 3000) {
      this.front++; // advance front pointer (logical dequeue — O(1), no shift)
    }

    // Number of valid requests = elements from front to rear (inclusive)
    return this.queue.length - this.front;
  }
}
```

### Dry Run

```
RecentCounter: queue=[], front=0

ping(1):    push 1. queue=[1]. front=0.
  Evict while queue[0]=1 < 1-3000=-2999? No.
  return 1 - 0 = 1. ✓

ping(100):  push 100. queue=[1,100]. front=0.
  Evict while queue[0]=1 < 100-3000=-2900? No.
  return 2 - 0 = 2. ✓

ping(3001): push 3001. queue=[1,100,3001]. front=0.
  Evict while queue[0]=1 < 3001-3000=1? No (1 is NOT < 1).
  return 3 - 0 = 3. ✓

ping(3002): push 3002. queue=[1,100,3001,3002]. front=0.
  Evict while queue[0]=1 < 3002-3000=2? Yes (1 < 2). front=1.
  Evict while queue[1]=100 < 2? No.
  return 4 - 1 = 3. ✓  (timestamps {100, 3001, 3002} are in [2, 3002])
```

### Complexity
- Time: O(1) amortized per `ping()` — each timestamp is pushed once and "evicted" (front advanced past it) at most once. Total pointer advances across all n pings ≤ n = O(n) total.
- Space: O(n) total — the queue array grows with each `ping`. In the worst case (all pings within 3000ms of each other), all n timestamps remain in the queue.

### Edge Cases
- **All pings within 3000ms**: no evictions occur; the answer grows monotonically from 1 to n.
- **Large gap between pings**: `t - 3000 > all previous timestamps` → all previous elements are evicted; answer = 1.
- **Boundary exactly at t - 3000**: the condition `< t - 3000` (strictly less than) keeps the boundary timestamp in the window. `ping(3001)` after `ping(1)`: `1 < 3001-3000=1` is false → timestamp 1 is kept. Correct per `[t-3000, t]` inclusive.

### Follow-up Questions
- "Use a true circular queue with fixed capacity?" — If the maximum number of requests per 3001ms is bounded (say at most M), allocate a circular queue of size M. Use modular arithmetic to wrap `rear` and `front` — same as Problem 1 with the timestamp stored as the value.
- "Generalize to window size W instead of 3000?" — Replace `3000` with `W` everywhere. The algorithm is fully parameterized.
- "Memory-efficient version as timestamps grow unbounded?" — Periodically compact the queue array by copying `queue.slice(front)` to a new array and resetting `front = 0`. Amortized O(1) per ping with bounded memory reuse.

## Problem 6 — Design Hit Counter

### Problem
Design a hit counter which counts the number of hits received in the past 5 minutes (i.e., the past 300 seconds). Implement `hit(timestamp)` and `getHits(timestamp)` functions. Hits are recorded with timestamps in seconds (positive integers). Multiple hits can arrive at the same second.

```
HitCounter counter = new HitCounter();
counter.hit(1);       // hit at second 1
counter.hit(1);       // another hit at second 1
counter.hit(2);       // hit at second 2
counter.hit(300);     // hit at second 300
counter.getHits(300); // return 4 (all hits in [1, 300])
counter.hit(301);
counter.getHits(301); // return 3 (hits at seconds 2, 300, 301 — second 1's hits expired)
```

### Pattern Recognition
Circular buffer with timestamp bucketing — use a circular array of exactly 300 slots (one per second in a 5-minute window). Each slot stores `[lastTimestamp, count]`. A slot is valid if its stored timestamp is within 300 seconds of the query. Modular index = `timestamp % 300`.

### Key Insight
Time is naturally circular with period 300: timestamps 1 and 301 map to the same slot (`1 % 300 = 1`; `301 % 300 = 1`). When a slot is written for a new timestamp, it overwrites the data from 300 seconds earlier — exactly the data that is about to expire. This "self-expiring" property means no explicit eviction is needed; stale slots are identified by comparing the stored timestamp to the query timestamp.

### Approach
`timestamps[300]` and `hits[300]`, all initialized to 0. On `hit(t)`: `i = t % 300`. If `timestamps[i] !== t` (new second, different from the one 300 seconds ago): reset `timestamps[i] = t; hits[i] = 0`. Increment `hits[i]`. On `getHits(t)`: sum `hits[i]` for all `i` where `timestamps[i] > t - 300`.

### Solution

```js
class HitCounter {
  constructor() {
    this.timestamps = new Array(300).fill(0); // circular bucket: last timestamp for each slot
    this.hits = new Array(300).fill(0);       // hit count for each slot
  }

  hit(timestamp) {
    const i = timestamp % 300; // circular bucket index

    if (this.timestamps[i] !== timestamp) {
      // This slot was last written by a timestamp 300+ seconds ago → reset it
      this.timestamps[i] = timestamp;
      this.hits[i] = 0;
    }

    this.hits[i]++; // record this hit
  }

  getHits(timestamp) {
    let total = 0;
    for (let i = 0; i < 300; i++) {
      // Only count slots whose timestamp is within the 5-minute window
      if (this.timestamps[i] > timestamp - 300) {
        total += this.hits[i];
      }
    }
    return total;
  }
}
```

### Dry Run

```

           hits[1]++ → 1. (timestamps[1]=1, hits[1]=1)

           hits[1]++ → 2. (timestamps[1]=1, hits[1]=2)

  i=2: timestamps[2]=2 > 0 → add hits[2]=1.
  All other slots: timestamps=0, 0 > 0 is false → skip.

           hits[1]++ → 1.
  (The two hits at second 1 are OVERWRITTEN — they expired: 301-300=1, hits at t=1 expired)
```

### Complexity
- Time: `hit(t)` is O(1) — one modular index, one conditional check, one increment. `getHits(t)` is O(300) = O(1) — fixed 300-slot scan regardless of total hits seen.
- Space: O(300) = O(1) — fixed two-array structure, independent of the number of hits or the time span.

### Edge Cases
- **Multiple hits at the same second**: `timestamps[i] === t` → no reset; `hits[i]` accumulates all hits for that second correctly.
- **No hits in the window**: all 300 slots have `timestamps[i] <= timestamp - 300`; `getHits` returns 0.
- **Timestamp exactly at boundary (t - 299)**: condition is `timestamps[i] > timestamp - 300` (strictly greater). Timestamp `t - 299 > t - 300` → included. Timestamp `t - 300` itself → `t-300 > t-300` is false → excluded. The window is `(t-300, t]` strictly on the left, inclusive on the right. Adjust to `>=` for `[t-299, t]` or `>t-300-1` for `[t-300, t]` depending on whether the boundary second should be included.
- **Sparse hits (large timestamp gaps)**: slots from prior activity are naturally "stale" — their stored timestamps fail the `> timestamp - 300` check in `getHits`. No cleanup needed; the circular overwrite handles it lazily.

### Follow-up Questions
- "Window of W seconds instead of 300?" — Replace both array sizes and the `> timestamp - W` condition with the parameter W. Everything else is identical.
- "High-throughput (millions of hits/sec)?" — This implementation processes each `hit()` in O(1) and `getHits()` in O(W). For very large W, `getHits()` becomes O(W) which may be slow — use a sorted event log with binary search for the window boundary: O(log n) per query.
- "Distributed hit counter across multiple machines?" — Each machine maintains its own local circular buffer; a coordinator aggregates counts across all machines. Alternatively, use a shared atomic increment in Redis with an expiring sorted set.

## Quick Reference — Circular Queue & Deque Pattern Decision Tree

```
What structure does your problem need?
│
├── FIXED-CAPACITY FIFO with O(1) enqueue and dequeue?
│   └── Circular Queue (ring buffer)
│       Array + front + rear + size counter.
│       enQueue: write arr[rear], advance rear = (rear+1)%cap, size++.
│       deQueue: advance front = (front+1)%cap, size--.
│       Front: arr[front]. Rear: arr[(rear-1+cap)%cap].
│       Disambiguate full/empty: size counter (simplest), one-slot sacrifice, or flag.
│
├── FIXED-CAPACITY FIFO that also supports O(1) INSERT AND REMOVE FROM BOTH ENDS?
│   └── Circular Deque
│       Extends circular queue with backward step: (index - 1 + cap) % cap.
│       insertFront: step front backward, write arr[front].
│       deleteLast: step rear backward, read (now) arr[rear].
│       Everything else: same as circular queue.
│
├── MAXIMUM (or MINIMUM) OF A SLIDING WINDOW OF SIZE k?
│   └── Monotonic Deque of indices
│       Decreasing deque for max; increasing deque for min.
│       On new element i:
│         PRUNE rear: pop while nums[rear] ≤ nums[i] (for max; ≥ for min).
│         ADD i to rear.
│         EVICT front: pop while deque[front] ≤ i - k (out of window).
│         ANSWER: nums[deque[front]] = window max/min.
│       O(n) total — each index pushed and popped at most once.
│
├── MOVING AVERAGE (or other aggregate) OF LAST k VALUES?
│   └── Circular buffer + running aggregate
│       On next(val): if buffer full, subtract buf[rear] from sum. Write buf[rear]=val.
│       Advance rear = (rear+1)%k. Add val to sum. Return sum / min(count, k).
│       O(1) per update vs O(k) naive recomputation.
│
├── COUNT EVENTS IN A SLIDING TIME WINDOW (last W seconds)?
│   ├── Small W (≤ a few thousand): circular timestamp array
│   │   Slot i = timestamp % W. Reset slot if stored timestamp ≠ current.
│   │   getCount: sum slots with stored timestamp > (now - W). O(W) = O(1) for small W.
│   │
│   └── Large W or unbounded streams: queue of timestamps
│       Enqueue timestamp; dequeue while front < t - W.
│       Count = queue.size. O(1) amortized per event.
│
└── DISAMBIGUATION: HOW TO TELL FULL FROM EMPTY WHEN front === rear?
    ├── size counter (SIMPLEST): size===0 → empty. size===capacity → full. No wasted slot.
    ├── one-slot sacrifice: allocate cap+1. empty: rear===front. full: (rear+1)%(cap+1)===front.
    └── boolean flag: store isEmpty or isFull. Update on every push/pop.
```

## Common Bugs Checklist

Before submitting any circular queue or deque solution, verify:

1. **Backward step missing the `+ capacity` before modulo?** — `(index - 1 + capacity) % capacity` is required for `insertFront` and `deleteLast`. Without it, `(0 - 1) % 5 = -1` in JavaScript and Python — a valid array index pointing to the last element, which is accidentally correct in Python but semantically wrong. Add `+ capacity` unconditionally for correctness and clarity.

2. **Rear pointing to last filled slot vs next empty slot — which convention are you using?** — In Convention B (next empty): `enQueue` writes at `arr[rear]` then advances `rear`. `Rear()` reads `arr[(rear-1+cap)%cap]`. In Convention A (last filled): `enQueue` advances `rear` then writes. These are mutually incompatible; mixing them (e.g., Convention A's advance-first enQueue with Convention B's Rear() peek) produces off-by-one bugs. Pick one convention and use it everywhere.

3. **isFull check before enQueue and isEmpty check before deQueue?** — Skipping the guard and enqueueing into a full queue silently overwrites the oldest unread element and corrupts `front`/`rear` alignment. Always guard both operations.

4. **Returning `arr[front]` after dequeue (reading stale data)?** — `deQueue` advances `front` and does NOT read the value; `Front()` reads without advancing. Never read from `arr[front]` inside `deQueue` unless you mean to return the dequeued value. The `front` pointer is the only thing modified in `deQueue`.

5. **Monotonic deque: pruning with `<` instead of `<=` for non-strict windows?** — With strict inequality `nums[rear] < nums[i]`: equal elements are both kept in the deque. For maximum problems with duplicates, this is usually fine, but it can cause the deque to grow larger than needed and may produce incorrect answers for strictly-decreasing-or-equal windows. Use `<=` for the "strictly dominated" case (the incoming element is at least as good on every dimension).

6. **Monotonic deque: evicting from front AFTER recording the answer?** — The front eviction must happen BEFORE recording `nums[deque[0]]` as the answer. If you evict after recording, the expired index may be read as the window maximum. Process order for each `i`: prune rear → push i → evict front → record answer.

7. **Hit counter: using `>=` instead of `>` for the boundary check?** — `timestamps[i] > timestamp - 300` includes timestamps from `(timestamp - 300, timestamp]`. Using `>=` would include `timestamp - 300` itself — one second outside the 5-minute window. Verify the problem's window definition (open vs closed boundary) and use the exact comparison operator accordingly.

8. **Hit counter: resetting a slot on EVERY hit vs only on NEW timestamps?** — The check `if (timestamps[i] !== timestamp)` resets the count only when the slot's timestamp differs (a new 300-second cycle). Without this check, the count would be reset to 0 on EVERY hit at slot i, giving counts of 1 for every second regardless of how many hits arrived.

9. **Moving average: subtracting the outgoing value BEFORE overwriting the slot?** — The sequence must be: subtract `buf[rear]`, then write `buf[rear] = val`, then add `val` to sum. If the write happens before the subtraction, `buf[rear]` already holds `val` — you subtract `val` and add `val`, producing a net zero change. Sum is never updated. Always subtract first, then overwrite.

10. **Moving average: using `count` instead of `min(count, k)` as the divisor?** — For the first k-1 calls, `count < k`. Using `count` gives the correct average over the actual number of elements seen. Using `k` unconditionally gives a denominator larger than the number of elements in the window — an artificially small average. Use `Math.min(this.count, this.k)` or check `count >= k` to choose the divisor.

11. **Number of Recent Calls: using `Array.shift()` for dequeue and worrying about O(n) cost?** — `Array.shift()` in JavaScript is O(n) because it shifts all remaining elements. For an interview, this is typically accepted. For a production-quality O(1) solution, use a front pointer (as shown in the solution above) or use a true circular deque from Problem 2 as the underlying container.

12. **Circular deque: applying the wrong step direction for each operation?** — `insertFront` steps the front pointer BACKWARD then writes. `deleteFront` steps the front pointer FORWARD after reading (or without reading for `deQueue`). `insertLast` writes then steps the rear pointer FORWARD. `deleteLast` steps the rear pointer BACKWARD then reads. The pattern: insert always steps before writing (making room); delete always steps after consuming (or just steps, for deQueue). Swapping the step direction produces off-by-one overwrites of adjacent slots.

**Final Tip:** At the 5 YOE level, the signal that separates a confident circular queue answer from a memorized one is the ability to state three things immediately: (1) **The disambiguation strategy** — "I'm using a size counter so full and empty are unambiguous even when front === rear." (2) **The pointer convention** — "rear points to the next empty slot; Rear() is `arr[(rear-1+cap)%cap]`." (3) **The backward step** — "For deque operations going to the front, it's `(front - 1 + capacity) % capacity` — the `+ capacity` is essential to avoid negative indices in JavaScript." Stating these three invariants before writing any code signals ownership of the technique. For monotonic deque problems, the additional signal is distinguishing the two removal operations in one sentence: "I prune smaller elements from the rear when a new element arrives — they're permanently dominated; I evict expired indices from the front when they fall out of the window — they're temporarily valid but now out of scope."
