# DSA: Min Stack / Max Stack — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the "min stack" problem, and why can't you just scan the stack whenever `getMin()` is called?**
A: The min stack problem asks for a stack that supports standard `push`, `pop`, `top` operations, **plus** a `getMin()` operation that returns the current minimum element — all in O(1) time. Scanning the entire stack on every `getMin()` call would be O(n) per call, which fails the O(1) requirement; the challenge is maintaining constant-time access to "the current minimum" even as elements are pushed and popped, without giving up O(1) on the standard operations either.

```
push(-2), push(0), push(-3)
getMin() → -3   (must be O(1), not a fresh O(n) scan every time)
pop()             (removes -3)
getMin() → -2   (must correctly reflect the NEW minimum after the pop)
```

**Q2. What is the core difficulty that makes this harder than just tracking a single "current minimum" variable?**
A: A single variable tracking "the current minimum" breaks the moment that minimum element is **popped** — you'd need to know what the *next* minimum was, which requires either rescanning the remaining stack (O(n)) or having proactively remembered it. The core insight needed is that "the minimum" isn't a single fact about the stack — it's a fact that **changes with the stack's history**, so you need a mechanism that remembers, at every point in the stack's history, what the minimum was *at that point*, not just currently.

**Q3. What is the standard "auxiliary stack" (shadow stack) solution, and why does it correctly handle pops?**
A: Maintain a second stack (`minStack`) that mirrors the main stack's push/pop operations exactly, but each of its entries records "the minimum value considering everything pushed onto the main stack up to and including this point." Because both stacks are pushed and popped in perfect lockstep, popping the main stack automatically "reveals" (via `minStack`'s new top) exactly what the minimum was *before* the just-popped element was ever pushed — no rescanning needed, since that historical information was already recorded at push-time.

```js
class MinStack {
  constructor() {
    this.stack = [];
    this.minStack = [];
  }

  push(val) {
    this.stack.push(val);
    const currentMin = this.minStack.length === 0
      ? val
      : Math.min(val, this.minStack[this.minStack.length - 1]);
    this.minStack.push(currentMin);
  }

  pop() {
    this.stack.pop();
    this.minStack.pop();
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  getMin() {
    return this.minStack[this.minStack.length - 1];
  }
}
```

**Q4. What is the time and space complexity of the auxiliary stack approach?**
A: Time: O(1) for every operation (`push`, `pop`, `top`, `getMin`) — no loops, no scanning. Space: O(n) for the auxiliary `minStack`, which grows in exact lockstep with the main stack — this **doubles** the overall space usage (two O(n) stacks instead of one), which is the primary trade-off this approach makes to achieve O(1) time for `getMin()`.

**Q5. Why must `minStack` be pushed to on EVERY main-stack push, even when the new value isn't a new minimum?**
A: Because `pop()` needs `minStack` and `stack` to always be the exact same length, so that popping both together correctly keeps them synchronized — if `minStack` only recorded genuinely *new* minimums (skipping pushes that don't change the minimum), a `pop()` on the main stack wouldn't have a clear, correct corresponding entry to remove from `minStack`, and the two stacks would drift out of alignment. Recording the *current* minimum (which might just be a repeat of the previous minimum) on every single push, not just on new minimums, is what keeps the two stacks correctly paired at every index.

### Section 2: Space Optimization

**Q6. How can you reduce the auxiliary stack's space usage, given that Q5 shows every push must still add *something* to `minStack`?**
A: Instead of pushing a full min-value entry on every push, push onto `minStack` **only when a genuinely new minimum is reached** (i.e., `val <= currentMin`), and correspondingly, only pop from `minStack` when the value being popped from the main stack **equals** the current minimum. This keeps `minStack` synchronized in *correctness* without needing to be the same *length* as the main stack — it only grows when the minimum actually changes, which can be much smaller than n in practice (though worst-case, e.g., a strictly non-increasing sequence of pushes, it's still O(n)).

```js
class MinStackOptimized {
  constructor() {
    this.stack = [];
    this.minStack = []; // only stores genuinely new minimums
  }

  push(val) {
    this.stack.push(val);
    if (this.minStack.length === 0 || val <= this.minStack[this.minStack.length - 1]) {
      this.minStack.push(val);
    }
  }

  pop() {
    const popped = this.stack.pop();
    if (popped === this.minStack[this.minStack.length - 1]) {
      this.minStack.pop();
    }
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  getMin() {
    return this.minStack[this.minStack.length - 1];
  }
}
```

**Q7. Why must the push condition use `<=` (not strict `<`), and why does the pop condition check for equality rather than tracking indices?**
A: Using `<=` (rather than strict `<`) ensures that **duplicate minimum values** are each individually recorded on `minStack` — if the same minimum value is pushed twice, and only the first occurrence were recorded, then popping the main stack's *second* occurrence of that minimum wouldn't trigger a corresponding `minStack` pop (since `popped === minStack top` would still be checking against a value that's still validly the minimum, but the *count* of how many times it needs to survive pops before truly leaving would be lost) — using `<=` means every occurrence of the current minimum gets its own `minStack` entry, so each pop of that value correctly removes exactly one corresponding `minStack` entry, correctly "revealing" the previous minimum only once all duplicate occurrences have been popped.

**Q8. Can you further optimize `minStack` to use O(1) space per distinct minimum (rather than one entry per occurrence), and what's the trade-off?**
A: Yes — store `(value, count)` pairs on `minStack` instead of one entry per occurrence: when pushing a value equal to the current minimum, increment the count of the top pair instead of pushing a new entry; when popping a value equal to the current minimum, decrement the count, only popping the pair entirely once its count reaches zero. This further reduces space for inputs with many repeated minimum values, at the cost of slightly more complex push/pop logic (checking and updating a count, not just pushing/popping a plain value).

```js
class MinStackWithCounts {
  constructor() {
    this.stack = [];
    this.minStack = []; // stores {value, count} pairs
  }

  push(val) {
    this.stack.push(val);
    if (this.minStack.length === 0 || val < this.minStack[this.minStack.length - 1].value) {
      this.minStack.push({ value: val, count: 1 });
    } else if (val === this.minStack[this.minStack.length - 1].value) {
      this.minStack[this.minStack.length - 1].count++;
    }
  }

  pop() {
    const popped = this.stack.pop();
    const top = this.minStack[this.minStack.length - 1];
    if (popped === top.value) {
      top.count--;
      if (top.count === 0) this.minStack.pop();
    }
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  getMin() {
    return this.minStack[this.minStack.length - 1].value;
  }
}
```

### Section 3: True O(1) Extra Space — The Encoded Difference Trick

**Q9. Is it possible to implement a min stack using only a SINGLE stack and O(1) truly extra space (not even a second, smaller auxiliary structure)?**
A: Yes, via a clever **encoding trick**: instead of storing the actual pushed value when it would become a new minimum, store a specially encoded value that represents the *difference* between the new value and the previous minimum, and separately track only the current minimum in a single variable (not a stack). When popping, the encoding reveals whether the popped value was a "new minimum" marker, and if so, how to reconstruct what the *previous* minimum was — this achieves genuine O(1) extra space (one variable) at the cost of noticeably trickier logic and reduced code readability.

```js
class MinStackEncoded {
  constructor() {
    this.stack = [];
    this.min = null;
  }

  push(val) {
    if (this.stack.length === 0) {
      this.stack.push(val);
      this.min = val;
    } else if (val >= this.min) {
      this.stack.push(val); // no encoding needed, not a new minimum
    } else {
      // encode: store a value that's LESS than val, from which the
      // previous min can be recovered on pop
      this.stack.push(2 * val - this.min);
      this.min = val; // update to the new minimum
    }
  }

  pop() {
    const top = this.stack.pop();

    if (top < this.min) {
      // this was an encoded "new minimum" marker — recover the PREVIOUS min
      const previousMin = 2 * this.min - top;
      this.min = previousMin;
      // note: the actual popped VALUE was this.min (before this line ran),
      // not `top` — `top` was only ever an encoding, never a real value
    }
    // if top >= this.min, it was a genuine value, nothing further to do
  }

  top() {
    const topVal = this.stack[this.stack.length - 1];
    return topVal < this.min ? this.min : topVal; // if encoded, the real top value IS the current min
  }

  getMin() {
    return this.min;
  }
}
```

**Q10. Walk through the math: why does `2 * val - this.min` correctly encode a "new minimum" marker, and how is the previous minimum recovered from it?**
A: When `val` is a new minimum (smaller than the current `this.min`), the encoding stores `2*val - this.min` instead of `val` directly. Since `val < this.min`, this encoded value is **provably less than `val` itself** (specifically, `2*val - this.min < val` simplifies to `val < this.min`, which is true by assumption) — meaning the encoded value stored on the stack is *always* less than the actual current minimum at the time it's stored, which is exactly the signal used later to detect "this stack entry was an encoding, not a real value" (`top < this.min` at pop time). To recover the previous minimum on pop: given `encoded = 2*val - previousMin`, rearranging gives `previousMin = 2*val - encoded`, and since `val` (the new minimum that was set) is exactly `this.min` at the moment of popping (before this pop's logic updates it), the recovery formula becomes `previousMin = 2*this.min - encoded`, exactly as implemented.

**Q11. What is the practical trade-off of the encoded difference trick versus the auxiliary stack approach — is it actually better in practice?**
A: The encoded trick achieves genuine O(1) *extra* space (versus the auxiliary stack's O(n)), which is a real asymptotic improvement — but it comes with meaningfully increased code complexity, reduced readability, and a subtle risk: the encoding arithmetic (`2*val - min`) can **overflow** in fixed-width integer languages if values are large, a concern the simpler auxiliary-stack approach doesn't have at all. In an interview setting, presenting the auxiliary stack approach first (as the clear, correct, easy-to-verify solution) and then mentioning the encoded trick as a "further optimization if truly O(1) extra space is required, with this specific trade-off" is generally the strongest way to demonstrate full command of the problem's solution space.

### Section 4: Max Stack & popMax

**Q12. How does a "max stack" differ from a min stack, and does the same auxiliary-stack technique apply directly?**
A: A max stack supports the same `push`/`pop`/`top` operations plus `getMax()` (or `peekMax()`), tracking the running **maximum** instead of minimum — the auxiliary-stack technique from Q3 applies completely symmetrically, just swapping `Math.min` for `Math.max` in the auxiliary stack's update logic. Nothing about the core mechanism changes; min and max stacks are mirror-image problems.

**Q13. What is `popMax()`, and why is it a fundamentally harder operation than `getMax()`/`peekMax()`?**
A: `popMax()` means removing the **maximum element specifically**, regardless of where it sits in the stack (not necessarily the top) — this is a materially different, harder operation than merely *peeking* at the max, because removing an element from the *middle* of a stack requires either shifting/restructuring the remaining elements, or a fundamentally different underlying data structure that supports efficient arbitrary-position removal, which a plain array/linked-list-backed stack does not provide natively.

**Q14. What is the naive O(n) approach to `popMax()`, and when might it be acceptable?**
A: Pop every element off the main stack into a temporary buffer until the maximum element is found and removed, then push everything else back onto the main stack in the correct original order. This is O(n) time for `popMax()` specifically (though `push`/`pop`/`top`/`peekMax` remain O(1) via the standard auxiliary max-stack technique) — acceptable when `popMax()` is called rarely relative to other operations, or when the input size is small enough that O(n) is a non-issue in practice.

```js
class MaxStackNaive {
  constructor() {
    this.stack = [];
    this.maxStack = [];
  }

  push(val) {
    this.stack.push(val);
    const currentMax = this.maxStack.length === 0
      ? val
      : Math.max(val, this.maxStack[this.maxStack.length - 1]);
    this.maxStack.push(currentMax);
  }

  pop() {
    this.maxStack.pop();
    return this.stack.pop();
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  peekMax() {
    return this.maxStack[this.maxStack.length - 1];
  }

  popMax() {
    const max = this.peekMax();
    const buffer = [];

    while (this.top() !== max) {
      buffer.push(this.pop());
    }
    this.pop(); // remove the max itself

    while (buffer.length > 0) {
      this.push(buffer.pop());
    }

    return max;
  }
}
```

**Q15. How can `popMax()` be improved to O(log n) using a more advanced data structure combination?**
A: Combine a **doubly linked list** (to represent the stack's sequence, supporting O(1) removal of a node given a direct reference to it — see the dedicated linked-list guide's Q12) with a **balanced BST / ordered map** (e.g., a `TreeMap` in Java, or an equivalent sorted-structure in other languages) that maps `value → list of node references at that value`, ordered by value. `push`: add a new node to the end of the linked list, and insert/update its reference in the ordered map (O(log n) for the map insertion). `pop`: remove the linked list's tail node, and remove its corresponding entry from the ordered map (O(log n)). `popMax`: look up the **largest key** in the ordered map (O(log n) for a balanced BST's max-lookup), get one of its node references, remove that specific node from the linked list in O(1) (using the doubly-linked list's direct-removal capability), and remove/update its entry in the ordered map (O(log n)).

```
Conceptual structure (not full implementation, since it requires a balanced-BST-backed
sorted map not natively available in JS — often approximated with a library or a
custom-built structure in practice):

doublyLinkedList: sequence of all current stack elements, in order
sortedMap: value -> [list of node references with that value], kept sorted by value

push(val): append node to list tail; sortedMap[val].push(nodeRef)     — O(log n)
pop():     remove list tail node; sortedMap[tailVal] removes that ref — O(log n)
peekMax(): sortedMap's largest key                                    — O(log n) (or O(1) with a cached pointer)
popMax():  get a node ref from sortedMap's largest key's list;
           remove that node directly from the linked list (O(1));
           remove/update that entry in sortedMap                      — O(log n)
```

This achieves O(log n) for every operation including `popMax()`, a significant improvement over the naive approach's O(n) `popMax()` — at the cost of considerably more implementation complexity and a dependency on a balanced-BST-like sorted structure that isn't a language primitive in every environment.

**Q16. Why is a doubly linked list specifically required for the O(log n) `popMax()` design, rather than a singly linked list or an array?**
A: `popMax()` needs to remove a node from potentially the **middle** of the sequence (wherever the maximum happens to currently be), given only a direct reference to that node (obtained from the sorted map) — a doubly linked list supports this in O(1) via its `prev` pointer (see the dedicated linked-list guide's Q12-Q13), whereas a singly linked list would need an O(n) scan to find that node's predecessor first, and an array would need an O(n) shift to close the gap left by a middle-element removal. This is a direct, practical application of "why does a doubly linked list matter" reasoning from the linked-list guide, now applied to justify a specific advanced stack design.

### Section 5: Scenario / Interview-Style Questions

**Q17. "You're asked to design a min stack, and after presenting the auxiliary-stack solution, the interviewer asks 'can you do it with less space?' Walk through your response."**
A: I'd first clarify what "less space" means — if it means reducing the *practical* size of the auxiliary stack (not its worst-case asymptotic bound), I'd present the "only push on new minimum, with counts for duplicates" optimization (Q6-Q8), which can meaningfully shrink `minStack`'s size for inputs with few genuine minimum changes. If the interviewer specifically wants true O(1) *extra* space (not just a smaller O(n) structure), I'd present the encoded-difference trick (Q9-Q10), while being upfront about its added complexity and the overflow risk in fixed-width-integer contexts — presenting both options and their trade-offs, rather than jumping straight to the cleverest one, demonstrates a fuller understanding of the solution space.

**Q18. "A teammate implements getMin() by keeping a running 'min' variable updated on every push, but doesn't handle pop correctly. What's the bug, and how do you explain it?"**
A: The bug: a single running `min` variable has no way to know what the minimum *was* before the current minimum's element gets popped — once that element is removed, the variable is stale and there's no remaining information to recompute the correct new minimum without a fresh O(n) scan. I'd explain that this is exactly the core difficulty of the problem (Q2) — you need to track the minimum's entire *history* in a way that naturally "unwinds" correctly as pops happen, which is precisely what the auxiliary stack (pushed/popped in lockstep with the main stack) achieves and a single variable fundamentally cannot.

**Q19. "How would you extend a min stack design to also support getMax() simultaneously, without doubling the auxiliary space a second time (i.e., not just bolting on a completely separate max-stack)?"**
A: A single combined auxiliary stack can store `{min, max}` pairs instead of maintaining two fully separate auxiliary stacks — each push computes and stores both the running min and running max together in one entry, and each pop removes one combined entry. This doesn't change the asymptotic space complexity (still O(n) for the combined auxiliary stack, versus O(n) + O(n) = O(n) for two separate ones — same order, just half the constant factor in practice via shared bookkeeping/fewer array allocations), but it's a reasonable practical simplification worth mentioning if asked to support both simultaneously.

**Q20. "You need popMax() to be efficient (not O(n)) for a system processing a very high volume of max-removal operations. What would you propose, and what's the implementation cost of that proposal?"**
A: I'd propose the doubly-linked-list plus sorted-map design (Q15-Q16), bringing `popMax()` down to O(log n) alongside O(log n) for the other operations (a slight regression from O(1) push/pop/peek in the simpler design, but a large improvement for the specifically-frequent `popMax()` operation) — I'd flag upfront that this is meaningfully more complex to implement and maintain correctly than the naive O(n)-`popMax()` version, and would only recommend it if profiling or the stated requirements genuinely show `popMax()` frequency/scale justifies that added complexity; for moderate scale, the simpler naive version is often the more maintainable choice despite its worse asymptotic bound on that one operation.

## Problem 1 — Min Stack (Standard Auxiliary Stack)

### Problem
Design a stack supporting `push(val)`, `pop()`, `top()`, and `getMin()`, all in O(1) time.

```
push(-2); push(0); push(-3);
getMin() → -3
pop()
top()    → 0
getMin() → -2
```

### Pattern Recognition
The canonical auxiliary "shadow stack" technique — a second stack tracks the running minimum in perfect lockstep with the main stack.

### Key Insight
Every push records, in the auxiliary stack, the minimum considering all elements pushed so far (including the just-pushed one) — this means the auxiliary stack's top always correctly reflects the current minimum, and popping both stacks together naturally "reveals" the correct prior minimum without any rescanning.

### Approach
Two parallel stacks, always the same length. `push`: push the value onto the main stack; compute and push the new running minimum onto the auxiliary stack. `pop`: pop both stacks together. `getMin`: peek the auxiliary stack's top.

### Solution

```js
class MinStack {
  constructor() {
    this.stack = [];
    this.minStack = [];
  }

  push(val) {
    this.stack.push(val);
    const currentMin = this.minStack.length === 0
      ? val
      : Math.min(val, this.minStack[this.minStack.length - 1]);
    this.minStack.push(currentMin);
  }

  pop() {
    this.stack.pop();
    this.minStack.pop();
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  getMin() {
    return this.minStack[this.minStack.length - 1];
  }
}
```

### Dry Run

```
minStack = new MinStack()

push(-2): stack=[-2], minStack: min(-2,∅)=-2 → minStack=[-2]
push(0):  stack=[-2,0], min(0,-2)=-2 → minStack=[-2,-2]
push(-3): stack=[-2,0,-3], min(-3,-2)=-3 → minStack=[-2,-2,-3]

getMin() → -3 ✓

pop(): stack=[-2,0], minStack=[-2,-2]

top() → 0 ✓
getMin() → -2 ✓ (correctly reflects the minimum BEFORE -3 was pushed)
```

### Complexity
- Time: O(1) for every operation.
- Space: O(n) — the auxiliary stack matches the main stack's size exactly.

### Edge Cases
- Popping down to empty then pushing again: both stacks correctly reset in lockstep, since they're always modified together.
- All pushes are strictly increasing values: `minStack` still records an entry per push (the first-ever value, repeated), but `getMin()` correctly always returns that original first (smallest) value.
- Single push then immediate pop then getMin() call: after the pop, both stacks are empty — `getMin()` on an empty auxiliary stack is undefined behavior in this implementation (returns `undefined` in JS); real systems typically guard against calling `getMin()` on an empty stack, per the problem's usual stated constraints (often assuming `getMin()` is only called on a non-empty stack).

### Follow-up Questions
- "Reduce the auxiliary space usage?" → See Problem 2 — only push on new minimums.
- "Achieve true O(1) extra space (not just a smaller O(n) structure)?" → See Problem 3 — the encoded-difference trick.

## Problem 2 — Min Stack (Space-Optimized: Push Only on New Minimum)

### Problem
Same as Problem 1, but minimize the auxiliary stack's size by only recording genuinely new minimums (handling duplicate minimum values correctly).

```
push(3); push(1); push(1); push(0);
getMin() → 0
pop()  (removes the 0)
getMin() → 1
pop()  (removes one of the 1s)
getMin() → 1  (the OTHER 1 is still on the stack)
```

### Pattern Recognition
Same auxiliary-stack idea as Problem 1, but with a conditional push/pop that only touches `minStack` when the minimum actually changes — reducing (though not eliminating, worst-case) its space footprint.

### Key Insight
Using `<=` (not strict `<`) when deciding whether to push onto `minStack` ensures every occurrence of a tied minimum value gets its own entry — this is essential so that popping one occurrence of the minimum doesn't incorrectly "forget" that another occurrence of that same minimum value is still present deeper in the stack.

### Approach
`push`: push onto the main stack always; push onto `minStack` only if the new value is `<=` the current minimum (or `minStack` is empty). `pop`: pop the main stack; only pop `minStack` if the popped value equals `minStack`'s current top.

### Solution

```js
class MinStackOptimized {
  constructor() {
    this.stack = [];
    this.minStack = [];
  }

  push(val) {
    this.stack.push(val);
    if (this.minStack.length === 0 || val <= this.minStack[this.minStack.length - 1]) {
      this.minStack.push(val);
    }
  }

  pop() {
    const popped = this.stack.pop();
    if (popped === this.minStack[this.minStack.length - 1]) {
      this.minStack.pop();
    }
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  getMin() {
    return this.minStack[this.minStack.length - 1];
  }
}
```

### Dry Run

```
minStack = new MinStackOptimized()

push(3): stack=[3]. minStack empty → push 3 → minStack=[3]
push(1): stack=[3,1]. 1<=3? yes → push 1 → minStack=[3,1]
push(1): stack=[3,1,1]. 1<=1? yes (equal) → push 1 → minStack=[3,1,1]
push(0): stack=[3,1,1,0]. 0<=1? yes → push 0 → minStack=[3,1,1,0]

getMin() → 0 ✓

pop(): popped=0. 0===minStack top(0)? yes → pop minStack too
  stack=[3,1,1], minStack=[3,1,1]

getMin() → 1 ✓

pop(): popped=1 (one of the two 1s). 1===minStack top(1)? yes → pop minStack too
  stack=[3,1], minStack=[3,1]

getMin() → 1 ✓ (correctly still 1, since the OTHER "1" entry in minStack accounts for the
  remaining "1" still on the main stack)
```

### Complexity
- Time: O(1) for every operation.
- Space: O(n) worst case (e.g., a strictly non-increasing sequence of pushes still records every value), but typically much smaller in practice for inputs with fewer minimum changes.

### Edge Cases
- All pushed values are identical: `minStack` records every single one (since each new push is `<=` the current min via equality), correctly requiring an equal number of pops to fully clear `minStack` — space isn't actually saved in this specific worst case, an important caveat to state explicitly rather than overclaiming the optimization's benefit.
- Strictly increasing pushes: `minStack` only ever holds its very first entry — maximal space savings in this case.
- Mixed pattern (some new minimums, some not): `minStack` grows only on the "new minimum or tied" pushes, correctly staying smaller than the main stack in the general case.

### Follow-up Questions
- "Can you reduce space further using counts instead of one entry per duplicate minimum?" → See Q8 — store `{value, count}` pairs instead of one entry per occurrence.
- "Is this actually better in the worst case?" → No — worst case is still O(n), as shown in the "all identical values" edge case; the benefit is average/practical-case space reduction, not a worst-case asymptotic improvement.

## Problem 3 — Min Stack with O(1) Extra Space (Encoded Difference Trick)

### Problem
Same as Problem 1, but achieve genuine O(1) EXTRA space — not just a smaller O(n) auxiliary stack, but a single additional variable, with all history implicitly encoded within the main stack's own values.

```
push(5); push(3); push(7); push(1);
getMin() → 1
pop()  (removes the encoded "1" entry, correctly restoring min to 3)
getMin() → 3
```

### Pattern Recognition
The encoded-difference trick — store a value that's mathematically less than the true pushed value whenever a new minimum occurs, using that "impossibly small" property as a marker to detect and reverse the encoding on pop.

### Key Insight
`2*val - previousMin` is provably smaller than `val` itself whenever `val` is a new minimum (i.e., `val < previousMin`) — this gives a reliable signal (`stackTop < currentMin`) to detect, at pop time, that the popped entry was an encoded marker rather than a genuine value, and the same formula rearranges to recover the previous minimum exactly.

### Approach
Maintain the main stack plus a single `min` variable (not a stack). On push, if the new value would be a new minimum, store the encoded marker and update `min`; otherwise store the value directly. On pop, check if the popped entry is less than the current `min` (the encoding signal); if so, recover and restore the previous minimum from the encoding.

### Solution

```js
class MinStackEncoded {
  constructor() {
    this.stack = [];
    this.min = null;
  }

  push(val) {
    if (this.stack.length === 0) {
      this.stack.push(val);
      this.min = val;
    } else if (val >= this.min) {
      this.stack.push(val);
    } else {
      this.stack.push(2 * val - this.min);
      this.min = val;
    }
  }

  pop() {
    const top = this.stack.pop();
    if (top < this.min) {
      const previousMin = 2 * this.min - top;
      this.min = previousMin;
    }
  }

  top() {
    const topVal = this.stack[this.stack.length - 1];
    return topVal < this.min ? this.min : topVal;
  }

  getMin() {
    return this.min;
  }
}
```

### Dry Run

```
minStack = new MinStackEncoded()

push(5): stack empty → push 5, min=5 → stack=[5], min=5

push(3): 3 >= min(5)? no → new minimum!
  encode: 2*3 - 5 = 1 → push 1 (the ENCODED marker, not the real value 3)
  min=3
  stack=[5, 1(encoded)], min=3

push(7): 7 >= min(3)? yes → push 7 directly → stack=[5,1,7], min=3

push(1): 1 >= min(3)? no → new minimum!
  encode: 2*1 - 3 = -1 → push -1 (encoded marker)
  min=1
  stack=[5,1,7,-1(encoded)], min=1

getMin() → min = 1 ✓

top(): topVal = stack top = -1. -1 < min(1)? yes → it's encoded → return min(1)
  top() correctly returns 1 (the real top value), not -1 (the internal encoding) ✓

pop(): top = stack.pop() = -1
  -1 < min(1)? yes → this was an encoded marker
  previousMin = 2*1 - (-1) = 2+1 = 3
  min = 3
  stack=[5,1,7]

getMin() → min = 3 ✓ (correctly restored to the minimum BEFORE the "1" was ever pushed)

top(): topVal = stack top = 7. 7 < min(3)? no → return 7 directly (genuine value) ✓
```

### Complexity
- Time: O(1) for every operation.
- Space: O(1) EXTRA (beyond the single main stack itself, which is required regardless) — only one additional `min` variable, no auxiliary stack.

### Edge Cases
- First push (empty stack): explicitly handled as its own case — sets both the stack's first entry and `min` directly, no encoding needed since there's no "previous minimum" to compare against yet.
- Popping back to empty: after the last pop, `min` retains its last computed value (stale, but harmless, since `getMin()` on an empty stack is undefined behavior per usual problem constraints, same caveat as Problem 1).
- Pushing a value exactly equal to the current minimum: `val >= this.min` is true (since `>=` includes equality), so it's pushed directly without encoding — correctly avoids unnecessarily encoding a tied (not strictly smaller) value, and `min` stays correctly unchanged.
- Potential overflow with very large or very small values: `2*val - min` could overflow in fixed-width integer contexts if values are near the type's limits — worth flagging explicitly as a real limitation of this technique, even though JavaScript's native numbers make this less of an immediate concern than in strictly-typed languages.

### Follow-up Questions
- "Why not just always use this approach, since it's more space-efficient?" → The added complexity and reduced readability are real costs — most interviewers and most production contexts value the auxiliary-stack approach's clarity and safety (no overflow risk) unless O(1) extra space is a hard, explicitly stated requirement.
- "Adapt this trick for a max stack instead?" → Symmetric — encode using `2*val - max` when a new maximum occurs (rather than minimum), with the same detection/recovery logic mirrored for the max direction.

## Problem 4 — Max Stack with popMax()

### Problem
Design a stack supporting `push(val)`, `pop()`, `top()`, `peekMax()` (view the maximum without removing it), and `popMax()` (remove AND return the maximum element, regardless of its position in the stack).

```
maxStack.push(5); maxStack.push(1); maxStack.push(5);
maxStack.top()     → 5
maxStack.peekMax() → 5
maxStack.popMax()  → 5   (removes ONE of the two 5s — behavior for ties is implementation-defined,
                           commonly the most-recently-pushed one)
maxStack.top()     → 1   (after popMax removed the top 5, the new top is 1)
maxStack.peekMax() → 5   (the OTHER 5, still in the stack, is still the max)
```

### Pattern Recognition
Auxiliary max-stack (mirroring the min-stack technique) for O(1) `peekMax()`, combined with a "buffer and restore" technique for `popMax()`'s O(n) removal-from-the-middle requirement.

### Key Insight
`popMax()` needs to find and remove the maximum element wherever it sits in the stack — since a plain stack can't directly access or remove a middle element, the naive approach pops everything above the max into a temporary buffer, removes the max itself, then restores the buffered elements back on top in their original relative order.

### Approach
Standard auxiliary max-stack for O(1) `push`/`pop`/`top`/`peekMax`. For `popMax()`: repeatedly pop (using the already-defined `pop()`, which correctly maintains `maxStack` in sync) into a buffer until the popped value equals the current max; remove that max element; then push the buffered elements back in reverse order to restore the original sequence above where the max was removed.

### Solution

```js
class MaxStack {
  constructor() {
    this.stack = [];
    this.maxStack = [];
  }

  push(val) {
    this.stack.push(val);
    const currentMax = this.maxStack.length === 0
      ? val
      : Math.max(val, this.maxStack[this.maxStack.length - 1]);
    this.maxStack.push(currentMax);
  }

  pop() {
    this.maxStack.pop();
    return this.stack.pop();
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  peekMax() {
    return this.maxStack[this.maxStack.length - 1];
  }

  popMax() {
    const max = this.peekMax();
    const buffer = [];

    while (this.top() !== max) {
      buffer.push(this.pop());
    }
    this.pop(); // discard the max itself

    while (buffer.length > 0) {
      this.push(buffer.pop());
    }

    return max;
  }
}
```

### Dry Run

```
maxStack = new MaxStack()

push(5): stack=[5], maxStack=[5]
push(1): stack=[5,1], maxStack: max(1,5)=5 → maxStack=[5,5]
push(5): stack=[5,1,5], maxStack: max(5,5)=5 → maxStack=[5,5,5]

top()     → 5 ✓ (the most recently pushed 5)
peekMax() → 5 ✓

popMax():
  max = peekMax() = 5
  buffer=[]
  top()=5 === max(5)? YES → loop doesn't execute (nothing buffered)
  pop() → removes the top 5 → stack=[5,1], maxStack=[5,5]
  buffer is empty → nothing to restore
  return 5

Result of popMax(): 5 ✓ (removed the most-recently-pushed 5, since it happened to be on top)

top()     → 1 (the new top after removing the 5)
peekMax() → 5 (maxStack top, correctly still reflecting the OTHER remaining 5)
```

```
Second example, where the max is NOT on top:
maxStack2 = new MaxStack()
push(1): stack=[1], maxStack=[1]
push(5): stack=[1,5], maxStack=[1,5]
push(2): stack=[1,5,2], maxStack: max(2,5)=5 → maxStack=[1,5,5]

popMax():
  max = peekMax() = 5
  buffer=[]
  top()=2 === max(5)? no → buffer.push(pop()=2) → stack=[1,5], maxStack=[1,5], buffer=[2]
  top()=5 === max(5)? yes → loop ends
  pop() → removes the 5 → stack=[1], maxStack=[1]

```

### Complexity
- `push`, `pop`, `top`, `peekMax`: O(1) each.
- `popMax`: O(n) worst case — if the maximum is at the very bottom of the stack, every other element must be buffered and restored.
- Space: O(n) — the auxiliary `maxStack`, plus O(n) temporary buffer space during a `popMax()` call (released after the call completes).

### Edge Cases
- Maximum is already on top: `popMax()`'s buffering loop doesn't execute at all, degenerating to a simple `pop()` — efficient in this specific case despite the O(n) worst-case bound.
- Maximum is at the very bottom: `popMax()` must buffer and restore every other element — the true O(n) worst case.
- Multiple occurrences of the maximum value: this implementation's `while (this.top() !== max)` loop stops as soon as it finds ANY occurrence of the max value at the top of the remaining stack, which — depending on push order — typically removes the most-recently-pushed occurrence first; this tie-breaking behavior should be explicitly clarified as implementation-defined if the problem doesn't specify a required behavior for ties.
- Empty stack: `peekMax()` on an empty `maxStack` returns `undefined`; `popMax()` would similarly misbehave — real implementations should guard against calling these on an empty stack, consistent with the same caveat noted for min stack.

### Follow-up Questions
- "How would you make popMax() O(log n) instead of O(n)?" → See Q15-Q16 — combine a doubly linked list with a balanced-BST-backed sorted map, allowing O(1) removal of any specific node once located, with O(log n) location lookup via the sorted map.
- "What if popMax() is called far more often than push/pop — does that change your recommended design?" → Yes — if `popMax()` frequency dominates, the added complexity of the O(log n) doubly-linked-list-plus-sorted-map design becomes much more clearly justified than it would be for a workload where `popMax()` is rare.

## Quick Reference — Pattern Decision Tree

```
Does the problem require O(1) access to the running min/max of a stack, alongside standard operations?
│
├── NEED getMin()/getMax() (PEEK ONLY, not removal) in O(1), space not a tight constraint?
│   └── Auxiliary Stack (shadow stack) — mirrors main stack, tracks running min/max at each point
│       → O(1) all operations, O(n) extra space
│
├── NEED getMin()/getMax() in O(1), want to REDUCE (not eliminate) auxiliary space?
│   ├── Only push to auxiliary stack on a NEW (or tied) min/max →
│   │     smaller in practice, still O(n) worst case
│   └── Further reduce via {value, count} pairs for duplicate min/max values →
│         even smaller in practice for inputs with repeated extremes
│
├── NEED TRUE O(1) EXTRA SPACE (not just a smaller O(n) structure)?
│   └── Encoded Difference Trick — single `min`/`max` variable, no auxiliary stack,
│       using `2*val - previousExtreme` as an in-band "new extreme" marker
│       (trade-off: added complexity, overflow risk in fixed-width integer contexts)
│
├── NEED popMax()/popMin() — REMOVING the extreme element, not just peeking?
│   ├── popMax()/popMin() called rarely, O(n) acceptable →
│   │     Naive buffer-and-restore using the standard auxiliary-stack design
│   └── popMax()/popMin() called frequently, need O(log n) →
│         Doubly Linked List + Balanced-BST-backed Sorted Map
│         (O(1) node removal given a direct reference + O(log n) max/min lookup)
│
└── NEED BOTH getMin() AND getMax() SIMULTANEOUSLY?
    └── Single combined auxiliary stack storing {min, max} pairs — same asymptotic
        space as maintaining two separate auxiliary stacks, fewer allocations in practice
```

## Common Bugs Checklist

Before submitting any min/max stack solution, verify:

1. **Auxiliary stack pushed/popped in EXACT lockstep with the main stack (standard version)?** — Any divergence in length or timing between the two stacks corrupts all future `getMin()`/`getMax()` results.

2. **Space-optimized version: push condition uses `<=`/`>=` (not strict `<`/`>`) to correctly handle duplicate extreme values?** — Using a strict comparison silently mishandles cases where the same minimum/maximum value is pushed multiple times, causing `getMin()`/`getMax()` to return an incorrect value too early after a pop.

3. **Space-optimized version: pop condition checks EQUALITY with the auxiliary stack's current top, not just "was this a min/max at some point"?** — This is what correctly decides whether the auxiliary stack needs a corresponding pop for this specific main-stack pop.

4. **Encoded-difference trick: encoding formula and recovery formula are exact algebraic inverses, and applied at the correct point (encode on push BEFORE updating min/max; recover on pop using the CURRENT min/max before overwriting it)?** — Getting the order of operations wrong (e.g., updating `min` before computing the encoding, or vice versa) silently corrupts the encoding/recovery round-trip.

5. **Encoded-difference trick: `top()` correctly distinguishes an encoded marker from a genuine value using the `< min` (or `> max`) signal, not returning the raw encoded number directly?** — Forgetting this check means `top()` can return an internally-encoded "garbage" value instead of the actual logical top element.

6. **popMax()/popMin(): buffered elements restored in the correct order (reverse of how they were popped) to preserve the original stack's relative sequence?** — Restoring in the wrong order silently scrambles the stack's remaining contents after a `popMax()`/`popMin()` call.

7. **All variants: empty-stack behavior for getMin()/getMax()/popMax() explicitly considered, even if just documented as "undefined behavior, caller must ensure non-empty"?** — Silently returning `undefined`/`NaN` without any guard can propagate confusing bugs downstream if not explicitly acknowledged as a precondition.

For `popMax()` specifically, recognizing that it's a fundamentally different (harder) operation than `peekMax()` — and being able to name both the naive O(n) approach and the more advanced O(log n) doubly-linked-list-plus-sorted-map design, along with when each is actually justified — is what separates a complete answer from a merely correct one.
