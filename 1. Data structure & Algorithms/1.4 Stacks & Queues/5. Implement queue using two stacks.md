## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the core problem — why can't you directly use a stack as a queue?**
A: A stack is LIFO (last-in, first-out) — the most recently pushed element is the first one out. A queue is FIFO (first-in, first-out) — the oldest element is the first one out. Their ordering semantics are exact opposites. If you push `[1, 2, 3]` onto a stack and pop immediately, you get `3, 2, 1`. A queue over the same input should yield `1, 2, 3`. The challenge is reversing the order of a stack without using extra non-stack data structures — and two stacks accomplish this because reversing a stack into another stack reverses the order twice, net effect: original FIFO order.

**Q2. What is the key insight that makes two stacks equivalent to a queue?**
A: Reversing a sequence once gives LIFO → FIFO reversal. A stack reversal transfers elements one by one from Stack A to Stack B, reversing their order. The bottom of A (oldest element) becomes the top of B — the first to be popped. A second reversal (B back to A) restores LIFO order. By using one stack exclusively for enqueue (inbox) and one exclusively for dequeue (outbox), and only transferring when the outbox is empty, you get amortized O(1) per operation with correct FIFO ordering.

**Q3. Describe the two-stack queue design — what are the two stacks, and what does each do?**
A: The design uses two stacks with distinct roles:
- **Inbox (enqueue stack / S1)**: all new elements are pushed here. This is the "write" end.
- **Outbox (dequeue stack / S2)**: all dequeue and peek operations read from here. This is the "read" end.

The transfer rule: when a dequeue or peek is requested and the outbox is empty, pour the entire inbox into the outbox (by popping from inbox and pushing to outbox one by one). This reverses the inbox's order — the oldest element (bottom of inbox) ends up on top of the outbox, ready to be popped first. The outbox is never refilled while it still has elements — existing outbox elements must be fully consumed before the next pour.

**Q4. Why does the transfer happen only when the outbox is empty — why not transfer on every enqueue?**
A: Transferring on every enqueue would give correct results but terrible performance — every enqueue would be O(n) because it would need to move all elements back and forth. By transferring lazily (only when the outbox is empty), each element is transferred at most once in its lifetime: pushed onto the inbox once, popped from the inbox and pushed onto the outbox at most once, and popped from the outbox once. Three operations per element regardless of how many enqueues happen between transfers. This is the amortized O(1) argument.

**Q5. What are the time complexities of each operation?**
A:
- **Enqueue**: O(1) always — just push to inbox.
- **Dequeue**: O(1) amortized, O(n) worst case — O(n) only when the outbox is empty and all n inbox elements must be transferred. But each element is transferred at most once total, so amortized over all operations it's O(1).
- **Peek**: O(1) amortized, O(n) worst case — same reasoning as dequeue (may trigger a transfer).
- **isEmpty**: O(1) always — check if both stacks are empty.
- **Space**: O(n) — all n elements live in one of the two stacks at any time.

**Q6. Prove the amortized O(1) claim for dequeue rigorously.**
A: Use the **accounting method** (a standard amortized analysis technique). Assign each enqueue operation a "credit" of 3 units:
- 1 credit pays for the push onto the inbox.
- 1 credit is stored on the element to pay for the eventual pop from the inbox (during transfer).
- 1 credit is stored to pay for the eventual pop from the outbox (during dequeue).

Every dequeue either pops directly from the outbox (O(1), uses the third credit already stored) or triggers a transfer. The transfer pops n elements from the inbox — each pop is paid for by that element's second stored credit. Then pops from the outbox — each paid for by the third credit. No operation ever needs to "borrow" credits from future operations. Total credit per element: 3 units of O(1) work = O(1) amortized per enqueue and O(1) amortized per dequeue.

**Q7. What is the difference between amortized O(1) and worst-case O(1)?**
A: Worst-case O(1) means every single operation completes in constant time, no exceptions (e.g., a well-implemented hash map lookup with a perfect hash). Amortized O(1) means the *average* cost per operation over any sequence of n operations is O(1) — some individual operations may be expensive (e.g., O(n)), but those are rare enough that the total cost for n operations is O(n). For the two-stack queue, a single dequeue can cost O(n) (when transfer occurs), but this can only happen after at least n enqueues — so the cost is "paid back" by the preceding cheap enqueues. Interviewers at the 5 YOE level expect you to name the amortized analysis explicitly and be able to justify it.

### Section 2: Implementation Variants

**Q8. What are the two main implementation strategies — "lazy transfer" vs "eager transfer on enqueue" — and which is better?**
A: Two strategies:

**Lazy transfer (outbox-empty trigger — preferred)**:
- Enqueue: push to inbox. O(1).
- Dequeue: if outbox is empty, pour inbox to outbox. Pop from outbox.
- Amortized O(1) per operation. Each element transferred at most once.

**Eager transfer on enqueue**:
- Enqueue: pour outbox to inbox, push new element, pour inbox back to outbox.
- Dequeue: pop from outbox. O(1) always.
- Enqueue is O(n) every single time — total cost O(n²) for n enqueues.

Lazy transfer is strictly better. Eager transfer only makes dequeue worst-case O(1) (never triggers a transfer) at the cost of making every enqueue O(n). In practice, queues are read as often as written, so amortized O(1) for both is the right trade-off. Always implement lazy transfer in an interview.

**Q9. What does the implementation look like in code?**
A:

```js
class MyQueue {
  constructor() {
    this.inbox = [];   // enqueue stack — new elements pushed here
    this.outbox = [];  // dequeue stack — elements popped from here
  }

  // O(1) always
  push(val) {
    this.inbox.push(val);
  }

  // O(1) amortized — transfer only when outbox is empty
  pop() {
    this._transfer();
    return this.outbox.pop();
  }

  // O(1) amortized
  peek() {
    this._transfer();
    return this.outbox[this.outbox.length - 1];
  }

  // O(1) always
  empty() {
    return this.inbox.length === 0 && this.outbox.length === 0;
  }

  // Internal: pour inbox into outbox only when outbox is empty
  _transfer() {
    if (this.outbox.length === 0) {
      while (this.inbox.length > 0) {
        this.outbox.push(this.inbox.pop()); // reverses order
      }
    }
  }
}
```

**Q10. Can you implement the inverse — a stack using two queues?**
A: Yes — but the complexity profile is flipped and worse. Two strategies:

**Expensive push (push O(n), pop O(1))**:
- Push: enqueue to Q2. Pour all of Q1 into Q2 (maintaining the new element at the "back" which will be dequeued last in LIFO order). Swap Q1 and Q2 labels. Q1 now has elements in LIFO order — dequeue from Q1 = pop.
- Pop: dequeue from Q1.

**Expensive pop (push O(1), pop O(n))**:
- Push: enqueue to Q1.
- Pop: dequeue n-1 elements from Q1 into Q2 (preserving them), dequeue and return the last element of Q1 (the LIFO top). Swap labels.

Unlike queue-from-two-stacks (amortized O(1) for both), stack-from-two-queues has no amortized trick — one operation is always O(n). This is because reversing a queue costs O(n) every time (no lazy trick available), whereas reversing a stack is free when you have a second stack ready.

**Q11. What if you only have one stack — can you implement a queue?**
A: Yes, using the call stack (recursion) as the implicit second stack. For dequeue, recursively pop all elements from the stack until it's empty, return the last popped element (the bottom = oldest), and push all other elements back in recursive unwind order:

```js
function dequeue(stack) {
  if (stack.length === 1) return stack.pop(); // base: bottom element
  const top = stack.pop();
  const front = dequeue(stack); // recurse to reach the bottom
  stack.push(top);              // restore on the way back up
  return front;
}
```

This is O(n) per dequeue and O(n) recursion stack depth. Mentioned for completeness — in an interview, use the explicit two-stack approach. The recursion approach demonstrates the insight that "the call stack is a stack" — a useful conceptual connection.

### Section 3: Design Decisions & Trade-offs

**Q12. When is the outbox transfer triggered — are there any edge cases in the trigger condition?**
A: The trigger condition is: **transfer only when the outbox is empty AND a dequeue/peek is requested**. Edge cases:
- **Transfer mid-sequence is wrong**: if the outbox has 2 elements and the inbox has 3, triggering a transfer would mix the orderings — the 3 inbox elements (newer) would end up under the 2 outbox elements (older) after transfer, violating FIFO. Never transfer while the outbox has elements.
- **Dequeue on completely empty queue**: both stacks empty after transfer attempt → undefined behavior. Guard with an `empty()` check or throw. LeetCode's version guarantees calls are valid, but production code must handle this.
- **Peek after multiple enqueues with no dequeue**: outbox is empty, inbox has n elements → transfer triggers → correct front is now outbox top. Works correctly.

**Q13. How do you implement peek efficiently — why not just call dequeue and re-enqueue?**
A: Calling `dequeue` and then `enqueue` would work but is wrong — it would move the front element to the back, making subsequent peeks and dequeues incorrect. Peek must look at the front without removing it. The correct implementation: trigger the same transfer as dequeue, but instead of calling `pop()`, just read `outbox[outbox.length - 1]` (the top without removing). The `_transfer()` helper makes this clean — both `pop()` and `peek()` call `_transfer()` first, then one pops and the other reads.

**Q14. How would you implement this in a language with no built-in stack or queue?**
A: Implement both stacks using arrays (or linked lists):
- Array-based stack: push = `arr[size++] = val` (append to end), pop = `return arr[--size]` (read and decrement size). O(1) both.
- Linked-list-based stack: push = prepend a new node (new head), pop = remove and return the head. O(1) both.

The two-stack queue implementation sits on top of whichever stack primitive you choose. For interviews in low-level languages (C, C++), this level of detail is expected. In JS/Python/Java, built-in arrays/lists suffice.

**Q15. What are the practical real-world applications of the two-stack queue pattern?**
A: Three concrete uses:
- **Undo/redo systems**: two stacks — one for undo history (LIFO), one for redo. The undo stack is a queue of states when viewed from the "what was done first" perspective. Two-stack structure naturally separates "recent actions" from "available redos."
- **Browser back/forward navigation**: back stack (LIFO for immediate back) combined with forward queue (what's available to go forward to) — effectively a deque implemented with two stacks.
- **Banker's queue / batched processing**: systems that receive inputs in bursts (inbox fills up) and process them in order during quieter periods (drain outbox) — the lazy transfer mirrors this natural batch-processing pattern.
- **Function call scheduling**: some task schedulers use a two-stack model — new tasks pushed to an inbox stack, execution pulls from the outbox (FIFO order among tasks scheduled in the same batch).

### Section 4: Complexity Deep Dive

**Q16. If we make n enqueues followed by n dequeues, what is the total work done?**
A:
- n enqueues: each pushes to inbox. n × O(1) = O(n) total.
- First dequeue: outbox is empty → transfer all n elements from inbox to outbox → O(n) work. Then pop from outbox → O(1). Total for first dequeue: O(n).
- Remaining n-1 dequeues: outbox has n-1 elements → each pop is O(1). (n-1) × O(1) = O(n-1).

Grand total: O(n) enqueues + O(n) first dequeue + O(n-1) remaining dequeues = O(3n) = O(n). Average per operation: O(n) / 2n operations = O(1) amortized. ✓

**Q17. What is the worst-case sequence for this data structure — when does it perform worst?**
A: The worst-case sequence for any individual operation is one dequeue on a queue that has had n elements enqueued without any intervening dequeues. That single dequeue costs O(n). However, this worst case requires n preceding O(1) enqueues — you can't trigger an O(n) dequeue without having done O(n) enqueues first. So the "worst case" in terms of total work for any sequence of m operations is O(m) total → O(1) amortized. There's no adversarial sequence that makes the total cost superlinear.

**Q18. How does this compare to a proper circular buffer (ring buffer) queue implementation?**
A: A ring buffer queue uses a fixed-size array with head and tail pointers that wrap around. It gives **worst-case O(1)** for enqueue and dequeue (not just amortized) with O(1) space overhead and excellent cache performance (contiguous memory). The trade-off: fixed capacity — resizing requires O(n) copying. The two-stack queue is dynamic (no fixed capacity) and gives amortized O(1). In production systems where latency predictability matters (real-time systems, game engines, audio pipelines), ring buffer queues are preferred because they eliminate the occasional O(n) spike. In general application code where throughput matters more than individual latency, the two-stack approach is elegant and sufficient.

### Section 5: Variants & Extensions

**Q19. How do you implement a double-ended queue (deque) using two stacks?**
A: A deque supports push/pop from both ends. With two stacks (left stack L and right stack R):
- `pushLeft` → push to L.
- `pushRight` → push to R.
- `popLeft` → if L non-empty, pop from L. Else pour R into L, pop from L.
- `popRight` → if R non-empty, pop from R. Else pour L into R, pop from R.

Amortized analysis is more complex — in the worst case, repeatedly alternating `popLeft` and `popRight` on a balanced deque triggers O(n) transfers repeatedly, giving O(n) amortized per operation (not O(1)). For true O(1) amortized deque from two stacks, you need the "banker's deque" or "functional deque" with lazy evaluation — beyond typical interview scope. For interviews, the naive two-stack deque is acceptable with a note that the amortized analysis degrades in adversarial alternating patterns.

**Q20. How would you implement a priority queue using stacks?**
A: Not naturally — a priority queue's dequeue-min/max operation requires finding the minimum/maximum element, which is O(n) with stacks (scan the entire stack). You'd need a sorted stack (maintaining sorted order on push is O(n) per push using a helper stack) to get O(1) peek-min. This gives:
- Push O(n), pop O(1) — sorted stack approach.
Stacks are fundamentally wrong for priority queues. The right structure is a heap: O(log n) push, O(log n) pop, O(1) peek. Two-stack queue is mentioned here to contrast: some data structures adapt naturally to stack primitives (queues do); others don't (priority queues don't).

**Q21. What if the queue needs to support a "size" operation — how do you track it?**
A: Maintain a `size` counter as an instance variable. Increment on `push`, decrement on `pop`. `size()` returns the counter — O(1) always. No need to sum `inbox.length + outbox.length` on each call (though that also works). The counter approach is O(1) and avoids the addition:

```js
push(val) {
  this.inbox.push(val);
  this.size++;
}

pop() {
  this._transfer();
  this.size--;
  return this.outbox.pop();
}
```

**Q22. How do you handle thread safety in a multi-threaded environment?**
A: The basic two-stack implementation is not thread-safe — concurrent pushes and pops on the inbox/outbox arrays without synchronization cause race conditions. Options:
- **Mutex/lock**: wrap each public method in a lock. Simple but creates contention — only one thread can enqueue or dequeue at a time.
- **Lock-free queues**: production systems use Michael-Scott lock-free queue (based on CAS operations and linked lists) for high-concurrency queues. The two-stack approach doesn't adapt cleanly to lock-free implementations because the transfer step requires both stacks to be in consistent states simultaneously.
- **For interviews**: mention thread safety as a concern if asked "what would you change for production use?" — shows senior-level thinking beyond the happy path.

### Section 6: Scenario / Interview-Style Questions

**Q23. "The interviewer asks you to implement a queue using two stacks. You finish. They ask: 'What if push operations are far more frequent than pop? Does that change your design?'"**
A: No design change needed — the lazy transfer already handles this optimally. When pushes dominate, the inbox fills up and the outbox drains slowly or not at all. Transfers are infrequent (only triggered on the rare dequeue). Each element is still pushed and popped at most once from each stack — the amortized cost remains O(1) per operation regardless of the push-to-pop ratio. If anything, a high push-to-pop ratio makes the lazy transfer *more* efficient than a design that transfers on every push — the inbox accumulates many elements before a single O(n) transfer, spreading that cost over many cheap pushes.

**Q24. "You're asked: 'What if pop operations are far more frequent than push — say, 1000 pops per push?' Does amortized O(1) still hold?"**
A: Amortized O(1) requires that each element be dequeued at most once. If pops outnumber pushes, most pop calls will find the outbox non-empty (O(1)) or both stacks empty (which must be guarded). The amortized analysis only accounts for elements that were actually enqueued — you can't dequeue more elements than you enqueued. So if there are m pushes and k ≥ m pops (where k-m pops return "empty"), the total work is still O(m) for the valid pops (each element transferred once) plus O(k-m) for the empty-check pops = O(k). Amortized over k operations: O(1) per operation. The analysis holds.

**Q25. "Design a task scheduler that processes tasks in arrival order, but allows O(1) check of whether a specific task is pending. What data structures would you combine?"**
A: Two-stack queue for FIFO processing + a hash set for O(1) membership lookup. On enqueue: push to inbox AND add to the set. On dequeue: pop from outbox (after transfer if needed) AND remove from the set. `isPending(task)` checks the set — O(1). This is a common pattern: augment the queue with a secondary index structure for fast lookup without affecting the queue's amortized O(1) enqueue/dequeue. Trade-off: O(n) extra space for the set; every enqueue/dequeue does an extra O(1) set operation.

## Problem 1 — Implement Queue Using Two Stacks (LeetCode 232)

### Problem
Implement a first-in-first-out (FIFO) queue using only two stacks. The implemented queue should support `push`, `pop`, `peek`, and `empty` operations.

```
MyQueue queue = new MyQueue();
queue.push(1);
queue.push(2);
queue.peek();  → 1
queue.pop();   → 1
queue.empty(); → false
```

Constraints: only standard stack operations (push to top, peek/pop from top, size, isEmpty) may be used.

### Pattern Recognition
Direct application — this is the canonical two-stack queue problem. Lazy transfer gives amortized O(1) for all operations.

### Key Insight
Inbox receives all new elements (LIFO order). Outbox reverses them (FIFO order). Transfer only when outbox empties. Each element transferred at most once → amortized O(1).

### Approach
Two arrays acting as stacks: `inbox` and `outbox`. Push always goes to inbox. Pop/peek trigger a transfer (inbox → outbox) only when outbox is empty, then operate on outbox. Empty checks both stacks.

### Solution

```js
class MyQueue {
  constructor() {
    this.inbox = [];   // receives all pushes
    this.outbox = [];  // serves all pops and peeks
  }

  // Always O(1) — just append to inbox
  push(val) {
    this.inbox.push(val);
  }

  // Amortized O(1) — transfer only if outbox empty
  pop() {
    this._pour();
    return this.outbox.pop();
  }

  // Amortized O(1) — same transfer logic, no removal
  peek() {
    this._pour();
    return this.outbox[this.outbox.length - 1];
  }

  // Always O(1)
  empty() {
    return this.inbox.length === 0 && this.outbox.length === 0;
  }

  // Transfer inbox → outbox, reversing order
  // Only called when outbox is empty
  _pour() {
    if (this.outbox.length === 0) {
      while (this.inbox.length > 0) {
        // inbox top (newest) → outbox bottom (served last)
        // inbox bottom (oldest) → outbox top (served first)
        this.outbox.push(this.inbox.pop());
      }
    }
  }
}
```

### Dry Run

```
push(1): inbox=[1],     outbox=[]
push(2): inbox=[1,2],   outbox=[]
push(3): inbox=[1,2,3], outbox=[]

peek():
  _pour() — outbox empty → transfer:
    pop 3 from inbox, push to outbox → outbox=[3]
    pop 2 from inbox, push to outbox → outbox=[3,2]
    pop 1 from inbox, push to outbox → outbox=[3,2,1]
    inbox=[]
  outbox top = outbox[2] = 1 → return 1 ✓

pop():
  _pour() — outbox=[3,2,1] non-empty → no transfer
  outbox.pop() → return 1, outbox=[3,2]  ✓ (oldest removed)

push(4): inbox=[4], outbox=[3,2]

pop():
  _pour() — outbox non-empty → no transfer
  outbox.pop() → return 2, outbox=[3] ✓

pop():
  _pour() — outbox=[3] non-empty → no transfer
  outbox.pop() → return 3, outbox=[] ✓

pop():
  _pour() — outbox empty → transfer:
    pop 4 from inbox → outbox=[4], inbox=[]
  outbox.pop() → return 4 ✓

empty(): inbox.length=0, outbox.length=0 → return true ✓

Output order: 1, 2, 3, 4 — FIFO ✓
```

### Complexity

| Operation | Time       | Space |
|-----------|------------|-------|
| push      | O(1)       | O(1)  |
| pop       | O(1) amort | O(1)  |
| peek      | O(1) amort | O(1)  |
| empty     | O(1)       | O(1)  |
| Overall   | O(1) amort | O(n)  |

### Edge Cases
- `peek()` before any `push()` → both stacks empty after `_pour()` → `outbox[outbox.length - 1]` is `undefined`. Problem guarantees no invalid calls — but in production, throw `Error("Queue is empty")`.
- `pop()` on empty queue → same issue; guard with `if (this.empty()) throw new Error(...)`.
- Single element: push(1), pop() → inbox=[1], transfer → outbox=[1], pop → outbox=[], return 1. Correct.
- Interleaved push/pop with varying inbox sizes → transfer triggered multiple times throughout the lifetime; each element still transferred exactly once. Correct.
- `empty()` immediately after construction → both arrays empty → return true. Correct.

### Follow-up Questions
- "Make it thread-safe?" → Add a mutex around each public method. Or use a lock-free queue (Michael-Scott algorithm) for production.
- "Add a `size()` method?" → Maintain a counter; increment on push, decrement on pop. Return counter from `size()`.
- "What if you could use a deque instead of a stack — how would the implementation change?" → A deque (double-ended queue) already supports O(1) push/pop at both ends — you don't need two of them. One deque implements a queue directly.

## Problem 2 — Implement Stack Using Two Queues (LeetCode 225)

### Problem
Implement a LIFO stack using only two queues. Support `push`, `pop`, `top`, and `empty` operations.

```
MyStack stack = new MyStack();
stack.push(1);
stack.push(2);
stack.top();   → 2
stack.pop();   → 2
stack.empty(); → false
```

Constraints: only standard queue operations (push to back, peek/pop from front, size, isEmpty) may be used.

### Pattern Recognition
Inverse of Problem 1 — implement LIFO using FIFO primitives. No amortized trick exists; one operation must be O(n). The design choice is which operation pays the price.

### Key Insight
To get LIFO from FIFO queues: when pushing a new element, it must become the front of the queue (so it's dequeued first). Achieve this by enqueueing the new element to Q2, then moving all of Q1 into Q2 behind it, then swapping labels. Q1 always holds elements in LIFO order (newest at front).

### Approach — Expensive Push (Push O(n), Pop O(1))
Push: enqueue `val` to Q2. Move all elements from Q1 to Q2 (new element is now at the back of Q2, but all old elements follow it... wait, we need new at front).

Corrected: enqueue `val` to Q2. Then move all of Q1's elements into Q2 (they go behind `val` since Q2 already has `val` at its front after being the only element initially... actually, this needs more care). Let's be precise:

- Q1 holds the current stack in LIFO order (front = top).
- To push `val`: enqueue `val` to Q2 (empty). Then dequeue all elements from Q1 and enqueue to Q2. Now Q2 has: `val` at back, rest at front... no.

Actually the correct move: enqueue `val` to the currently empty Q2. Then move all of Q1 into Q2. Q2 now has old elements first, `val` last. That's FIFO order (oldest first) — wrong for LIFO.

Correct approach: use only ONE queue (simpler) — push, then rotate the queue so the new element is at the front:

### Solution — One Queue (Simpler and Better)

```js
class MyStack {
  constructor() {
    this.queue = []; // single queue, maintained in LIFO order at front
  }

  // O(n) — rotate so new element is at front (LIFO top)
  push(val) {
    this.queue.push(val); // enqueue to back first

    // rotate: move all elements except the new one to behind it
    // after rotation, new element is at the front
    let rotations = this.queue.length - 1;
    while (rotations > 0) {
      this.queue.push(this.queue.shift()); // dequeue from front, enqueue to back
      rotations--;
    }
    // new element is now at the front of the queue
  }

  // O(1) — front of queue is the LIFO top
  pop() {
    return this.queue.shift();
  }

  // O(1)
  top() {
    return this.queue[0];
  }

  // O(1)
  empty() {
    return this.queue.length === 0;
  }
}
```

### Two-Queue Solution (For Completeness)

```js
class MyStackTwoQueues {
  constructor() {
    this.q1 = []; // main queue — front = LIFO top
    this.q2 = []; // helper queue for push restructuring
  }

  // O(n) — enqueue to helper, move main behind it, swap
  push(val) {
    this.q2.push(val); // new element alone in q2

    // move all of q1 into q2 (they go behind val)
    while (this.q1.length > 0) {
      this.q2.push(this.q1.shift());
    }

    // swap: q1 becomes the restructured queue
    [this.q1, this.q2] = [this.q2, this.q1];
    // q1 front = val (LIFO top), rest follow in LIFO order
  }

  // O(1) — front of q1 is the top
  pop() {
    return this.q1.shift();
  }

  // O(1)
  top() {
    return this.q1[0];
  }

  // O(1)
  empty() {
    return this.q1.length === 0;
  }
}
```

### Dry Run (Two-Queue Solution)

```
push(1):
  q2=[1], move q1(empty) to q2 → q2=[1], swap → q1=[1], q2=[]
  q1=[1]  ← front=1 (top of stack)

push(2):
  q2=[2], move q1=[1] to q2 → q2=[2,1], swap → q1=[2,1], q2=[]
  q1=[2,1]  ← front=2 (newest = top of stack) ✓

push(3):
  q2=[3], move q1=[2,1] to q2 → q2=[3,2,1], swap → q1=[3,2,1], q2=[]
  q1=[3,2,1]  ← front=3 (LIFO top) ✓

top(): return q1[0] = 3 ✓

pop(): q1.shift() = 3, q1=[2,1] ✓

pop(): q1.shift() = 2, q1=[1] ✓

empty(): q1.length=1 → false ✓
```

### Complexity

| Operation | Time  | Space |
|-----------|-------|-------|
| push      | O(n)  | O(1)  |
| pop       | O(1)  | O(1)  |
| top       | O(1)  | O(1)  |
| empty     | O(1)  | O(1)  |
| Overall   | O(n²) for n pushes | O(n) |

Note: unlike the two-stack queue (amortized O(1) for all ops), the two-queue stack has no amortized trick — push is O(n) every time. This asymmetry is worth stating explicitly in interviews.

### Edge Cases
- `pop()` on empty → `shift()` on empty array returns `undefined`. Guard: `if (this.empty()) throw`.
- `push` then immediate `pop` → push rotates, pop dequeues front = just-pushed element. Correct.
- Single element `push(1), top(), pop()` → q1=[1], top=1, pop=1, q1=[]. Correct.

### Follow-up Questions
- "Why is this worse than the reverse problem (queue from two stacks)?" → For queues from stacks, lazy transfer amortizes the reversal cost. For stacks from queues, there's no lazy trick — every push genuinely needs to restructure the entire queue because FIFO can't lazily maintain LIFO ordering.
- "Is there a way to make both push and pop O(1) for stack-from-queues?" → No, with only queue primitives. Constant-time LIFO requires O(1) access to the back of the queue — which requires a deque, not a pure queue.

## Problem 3 — Moving Average from Data Stream (Sliding Window Queue)

### Problem
Given a stream of integers and a window size `k`, calculate the moving average of the last `k` numbers at each step.

```
MovingAverage m = new MovingAverage(3);
m.next(1)  → 1.0       (window: [1])
m.next(10) → 5.5       (window: [1, 10])
m.next(3)  → 4.66667   (window: [1, 10, 3])
m.next(5)  → 6.0       (window: [10, 3, 5])
```

### Pattern Recognition
Fixed-size queue (sliding window) — maintains the last k elements in arrival order. When the window is full, the oldest element (front of queue) must be removed before the newest is added (enqueued at back). This is a direct application of queue semantics.

### Key Insight
The queue naturally holds the sliding window in FIFO order — the front is always the oldest element (next to be evicted), the back is the newest. Maintain a running sum for O(1) average computation per step.

### Approach
Use a queue (or circular buffer array) of max size k. On each `next(val)`:
1. Enqueue `val` and add to `runningSum`.
2. If queue size exceeds k, dequeue the front (oldest) and subtract from `runningSum`.
3. Return `runningSum / queue.length`.

### Solution

```js
class MovingAverage {
  constructor(size) {
    this.k = size;
    this.queue = [];      // FIFO — front is oldest, back is newest
    this.runningSum = 0;
  }

  next(val) {
    this.queue.push(val);        // enqueue newest
    this.runningSum += val;

    if (this.queue.length > this.k) {
      // window exceeded — evict the oldest element
      this.runningSum -= this.queue.shift(); // dequeue from front
    }

    return this.runningSum / this.queue.length;
  }
}
```

### Dry Run

```
k=3

next(1):  queue=[1], sum=1,       no eviction → 1/1 = 1.0
next(10): queue=[1,10], sum=11,   no eviction → 11/2 = 5.5
next(3):  queue=[1,10,3], sum=14, no eviction → 14/3 = 4.666...
next(5):  queue=[1,10,3,5].length=4 > 3
          evict front=1, sum=14-1+5=18 → wait, let's retrace:
          push 5 → queue=[1,10,3,5], sum=14+5=19
          length=4 > 3 → shift() → evict 1, sum=19-1=18
          queue=[10,3,5] → 18/3 = 6.0 ✓
```

### Complexity
- Time: O(1) per `next()` call — enqueue, dequeue, and sum update are all O(1). (`shift()` on a JS array is O(n) — for true O(1), use a circular buffer or a proper deque. Mention this in interviews.)
- Space: O(k) — queue never exceeds k+1 elements.

### Edge Cases
- `k = 1` → queue always has 1 element; every call evicts the previous → returns `val` always.
- First call: queue has 1 element, no eviction → divide by 1.
- All same values → sum = `val * k`, average = `val`.
- Negative values → running sum handles naturally; no special casing.

### Follow-up Questions
- "Why is `shift()` O(n) in JS arrays, and how do you fix it?" → Arrays shift all elements left after removing index 0. Use a circular buffer (fixed array with head/tail pointers) for O(1) dequeue. Or use a doubly linked list. Mention the implementation detail in interviews — it shows production awareness.
- "What if you need the moving median instead of moving average?" → Significantly harder — use two heaps (max-heap for lower half, min-heap for upper half) maintained in balance. O(log k) per step.

## Problem 4 — Design Hit Counter (Time-Based Queue)

### Problem
Design a hit counter that counts the number of hits received in the past 5 minutes (300 seconds). Implement `hit(timestamp)` and `getHits(timestamp)` where timestamps are in seconds.

```
HitCounter counter = new HitCounter();
counter.hit(1);
counter.hit(2);
counter.hit(3);
counter.getHits(4);   → 3
counter.hit(300);
counter.getHits(300); → 4
counter.getHits(301); → 3  (hit at t=1 expired)
```

### Pattern Recognition
Time-windowed queue — maintain hits in a queue ordered by timestamp. On `getHits`, evict all entries older than `(timestamp - 300)` from the front (FIFO eviction = oldest first). Queue front always holds the oldest hit — the one most likely to have expired.

### Key Insight
FIFO order matches time order — the front of the queue is always the oldest hit. Expiry is always from the front. This is the defining property that makes a queue (not a stack, not a heap) the right structure.

### Approach
Queue of timestamps. `hit(t)`: enqueue `t`. `getHits(t)`: dequeue from front while `front <= t - 300` (expired). Return `queue.length`.

### Solution

```js
class HitCounter {
  constructor() {
    this.queue = []; // timestamps in arrival order (FIFO)
  }

  // O(1) — always append to back
  hit(timestamp) {
    this.queue.push(timestamp);
  }

  // O(k) where k = number of expired hits to evict
  // Amortized O(1) — each hit evicted at most once
  getHits(timestamp) {
    // evict hits older than 300 seconds from the front
    while (
      this.queue.length > 0 &&
      this.queue[0] <= timestamp - 300
    ) {
      this.queue.shift();
    }
    return this.queue.length;
  }
}
```

### Dry Run

```
hit(1):   queue=[1]
hit(2):   queue=[1,2]
hit(3):   queue=[1,2,3]

getHits(4):
  front=1, 1 <= 4-300=-296? No (1 > -296) → no eviction
  return queue.length = 3 ✓

hit(300): queue=[1,2,3,300]

getHits(300):
  front=1, 1 <= 300-300=0? No (1 > 0) → no eviction
  return 4 ✓

getHits(301):
  front=1, 1 <= 301-300=1? Yes → shift → queue=[2,3,300]
  front=2, 2 <= 1? No → stop
  return 3 ✓
```

### Complexity
- `hit`: O(1) — append to back.
- `getHits`: O(k) worst case (k expired hits), O(1) amortized — each hit enqueued and dequeued at most once.
- Space: O(n) — at most n hits in the queue at any time (n = hits in last 300s).

### Edge Cases
- No hits before `getHits` → queue empty → return 0.
- All hits expired → entire queue drained → return 0.
- Hits at same timestamp → multiple entries for same timestamp enqueued; all evicted together when that timestamp expires.
- `getHits` called with `timestamp` exactly 300 seconds after a hit → `hit_time <= timestamp - 300` → that hit is evicted (strictly more than 300 seconds old by the inclusive condition). Clarify with interviewer whether the window is `< 300` or `<= 300`.

### Follow-up Questions
- "What if timestamps can be out of order (concurrent hits)?" → The queue assumption (FIFO = time order) breaks. Use a sorted structure or process hits with a priority queue.
- "Handle massive hit volumes (millions/second)?" → Instead of storing individual timestamps, bucket hits by second using a circular buffer of 300 slots (one per second in the window). Each slot stores a `(second, count)` pair. O(1) per hit and getHits. This is the space-optimized follow-up expected at senior level.

## Problem 5 — Implement Circular Queue (Ring Buffer)

### Problem
Design a circular queue with fixed capacity `k` supporting `enQueue`, `deQueue`, `Front`, `Rear`, `isEmpty`, `isFull`.

```
MyCircularQueue q = new MyCircularQueue(3);
q.enQueue(1); → true
q.enQueue(2); → true
q.enQueue(3); → true
q.enQueue(4); → false  (full)
q.Rear();     → 3
q.isFull();   → true
q.deQueue();  → true
q.enQueue(4); → true
q.Rear();     → 4
```

### Pattern Recognition
Fixed-size queue with O(1) worst-case (not just amortized) enqueue and dequeue. Uses modular arithmetic to wrap head and tail pointers around a fixed array — no shifting, no two-stack complexity.

### Key Insight
Instead of shifting elements (O(n)), use head and tail indices that wrap around using modulo `k`. This makes all operations O(1) worst-case — the gold standard for production queues where latency predictability matters.

### Approach
Array of size k, `head` pointer (front, for dequeue), `tail` pointer (back, where next enqueue goes), `size` counter (distinguishes empty from full when head === tail).

### Solution

```js
class MyCircularQueue {
  constructor(k) {
    this.data = new Array(k);
    this.k = k;
    this.head = 0;   // index of front element
    this.tail = 0;   // index where next element will be inserted
    this.size = 0;   // current number of elements
  }

  enQueue(val) {
    if (this.isFull()) return false;
    this.data[this.tail] = val;
    this.tail = (this.tail + 1) % this.k; // wrap around
    this.size++;
    return true;
  }

  deQueue() {
    if (this.isEmpty()) return false;
    this.head = (this.head + 1) % this.k; // advance front pointer
    this.size--;
    return true;
  }

  Front() {
    if (this.isEmpty()) return -1;
    return this.data[this.head];
  }

  Rear() {
    if (this.isEmpty()) return -1;
    // tail points to NEXT insert position — rear is one before tail
    return this.data[(this.tail - 1 + this.k) % this.k];
  }

  isEmpty() {
    return this.size === 0;
  }

  isFull() {
    return this.size === this.k;
  }
}
```

### Dry Run

```
k=3, data=[_,_,_], head=0, tail=0, size=0

enQueue(1): data=[1,_,_], tail=1, size=1   → true
enQueue(2): data=[1,2,_], tail=2, size=2   → true
enQueue(3): data=[1,2,3], tail=0, size=3   → true (tail wraps to 0)
enQueue(4): isFull (size=3=k) → false ✓
Rear(): (tail-1+3)%3 = (0-1+3)%3 = 2 → data[2] = 3 ✓
isFull(): size=3=k → true ✓

deQueue(): head=(0+1)%3=1, size=2 → true
enQueue(4): data=[4,2,3] wait — tail=0, data[0]=4, tail=1, size=3
  Actually: data=[4,2,3], tail=1, head=1, size=3
Rear(): (tail-1+3)%3=(1-1+3)%3=0 → data[0]=4 ✓
```

### Complexity

| Operation | Time       | Space |
|-----------|------------|-------|
| enQueue   | O(1) worst | O(1)  |
| deQueue   | O(1) worst | O(1)  |
| Front     | O(1)       | O(1)  |
| Rear      | O(1)       | O(1)  |
| isEmpty   | O(1)       | O(1)  |
| isFull    | O(1)       | O(1)  |
| Overall   | O(1) worst | O(k)  |

This is strictly better than two-stack queue for latency-sensitive systems — no amortized spikes.

### Edge Cases
- `Rear()` when size=1: `(tail-1+k)%k` = `(head)` = correct (tail is head+1, rear is at head).
- `deQueue()` on empty → return false (guard with `isEmpty()`).
- Wrap-around: enqueue past index k-1 → tail resets to 0. Head same when dequeuing. Modulo handles this uniformly.
- Full then dequeue then enqueue → `isFull` returns false, enqueue writes to `data[tail]` (old head position), correct.

### Follow-up Questions
- "How does this compare to the two-stack queue?" → Circular buffer: O(1) worst-case, fixed capacity, better cache performance. Two-stack queue: O(1) amortized, dynamic capacity, occasional O(n) spike.
- "Implement a thread-safe version?" → Use a lock (mutex) around enQueue and deQueue. Or use atomic compare-and-swap on head/tail for a lock-free ring buffer (SPSC — single producer, single consumer — lock-free is achievable; MPMC requires more complex synchronization).

## Quick Reference — Stack vs Queue Implementations

```
Goal: Queue from Two Stacks
  Push: inbox.push(val)                              O(1)
  Pop:  if outbox empty, pour inbox→outbox; outbox.pop()  O(1) amortized
  Key:  lazy transfer — each element moved at most once

Goal: Stack from Two Queues
  Push: enqueue to q2, move q1→q2, swap labels       O(n)
  Pop:  q1.shift()                                   O(1)
  Key:  no amortized trick — push is always O(n)

Goal: Queue from One Queue (rotating)
  Push: queue.push(val); rotate n-1 times            O(n)
  Pop:  queue.shift()                                O(1)
  Key:  single queue maintained in LIFO order at front

Goal: Fixed-capacity Queue (ring buffer)
  All ops: O(1) worst-case, modular pointer arithmetic
  Key:  head/tail indices wrap around with % k
```

## Common Bugs Checklist

Before finalizing any two-stack queue solution, verify:

1. **Transfer condition** — transfer only when `outbox.length === 0`. Transferring while outbox has elements breaks FIFO order — newer elements (in inbox) would be served before older ones (in outbox).

2. **Empty queue guards** — `pop()` and `peek()` on an empty queue (both stacks empty after `_pour()`) return `undefined` in JS. Add explicit guards: `if (this.empty()) throw new Error("Queue is empty")` for production; the LeetCode constraint guarantees valid calls.

3. **Circular queue `Rear()` formula** — `(this.tail - 1 + this.k) % this.k`. The `+ this.k` prevents negative modulo when `tail === 0`. Without it, `(0 - 1) % 3 = -1` in JS, giving a wrong index.

4. **Size counter vs length sum** — for `empty()`, checking `inbox.length === 0 && outbox.length === 0` is equivalent to maintaining a `size` counter but requires two property reads. Either is correct; be consistent.

5. **Amortized claim requires lazy transfer** — if you use eager transfer (pour on every push), your push is O(n) and the amortized O(1) claim is wrong. Always verify your trigger condition is `outbox.length === 0`, not "always."

6. **Stack from queues — don't claim amortized O(1) for push** — unlike the reverse problem, there's no lazy trick. State explicitly: "push is O(n) worst-case and every case for the two-queue stack."
