## Topic A: Stacks

### Section A1: Fundamentals

**Q1. What is a stack, and what is the core ordering principle it enforces?**
A: A stack is a **LIFO** (Last-In, First-Out) data structure — the most recently added element is always the first one removed. It supports three core operations: `push` (add to the top), `pop` (remove and return the top), and `peek`/`top` (view the top without removing it), all in O(1) time with a proper implementation.

```
push(1), push(2), push(3) → stack (top to bottom): [3, 2, 1]
pop() → returns 3 → stack: [2, 1]
peek() → returns 2 (unchanged) → stack: [2, 1]
```

**Q2. How is a stack typically implemented, and what are the trade-offs between an array-backed and a linked-list-backed implementation?**
A:
- **Array-backed**: push/pop operate on the array's *end* (not the front, to avoid O(n) shifting) — both O(1) amortized (accounting for occasional resizing when the backing array needs to grow). Simple, cache-friendly due to contiguous memory.
- **Linked-list-backed**: push/pop operate on the list's *head* — both O(1) worst-case (no amortization/resizing concerns), since a linked list grows one node at a time without needing to reallocate a larger contiguous block. Trades away array's cache locality and requires slightly more memory per element (pointer overhead).
In most languages/runtimes, a dynamic array (e.g., JS's native `Array`, used with `push`/`pop` at the end) is the standard practical choice due to simplicity and generally excellent real-world performance.

```js
class ArrayStack {
  constructor() { this.items = []; }
  push(val) { this.items.push(val); }
  pop() { return this.items.pop(); }
  peek() { return this.items[this.items.length - 1]; }
  isEmpty() { return this.items.length === 0; }
}
```

**Q3. What is the time complexity of each core stack operation, and why is `push`/`pop` O(1) amortized rather than strictly O(1) for an array-backed stack?**
A: `push`, `pop`, `peek` are all O(1) amortized for an array-backed stack. The "amortized" qualifier accounts for the occasional O(n) cost of **resizing** the backing array when it's full and needs to grow (typically by doubling capacity) — this expensive resize happens rarely enough (geometrically less frequently as the stack grows) that its cost, spread out ("amortized") over all the pushes since the last resize, averages out to O(1) per operation. A linked-list-backed stack avoids this amortization nuance entirely, achieving strict O(1) worst-case per operation, since no resizing/reallocation is ever needed.

**Q4. What are the classic use cases that make a stack the natural data structure of choice?**
A: Any problem involving **nested structure processing** or needing to "undo" or "backtrack" to a previous state in reverse order of how it was reached: balanced parentheses/bracket matching, expression evaluation (infix-to-postfix conversion, evaluating postfix expressions), function call stacks (literally how recursion is implemented under the hood), undo/redo functionality in applications, browser back-button history, and depth-first search/traversal (either via the implicit call stack of recursion, or an explicit stack for an iterative DFS).

### Section A2: Advanced Stack Patterns

**Q5. What is a "monotonic stack," and what class of problems does it solve?**
A: A monotonic stack maintains its elements in a strictly increasing (or strictly decreasing) order from bottom to top at all times, achieved by **popping off elements that would violate that order** before pushing a new element. This pattern efficiently solves "next greater/smaller element" style problems in O(n) total time (each element is pushed and popped at most once across the whole algorithm, despite the appearance of nested loops), which would otherwise require O(n²) with a naive brute-force scan for each element.

```js
// Next Greater Element: for each element, find the next element to its right that's larger
function nextGreaterElement(nums) {
  const result = new Array(nums.length).fill(-1);
  const stack = []; // stores INDICES, maintained in decreasing order of nums[index]

  for (let i = 0; i < nums.length; i++) {
    // pop every index whose value is smaller than the current element —
    // the current element IS their "next greater element"
    while (stack.length > 0 && nums[stack[stack.length - 1]] < nums[i]) {
      const idx = stack.pop();
      result[idx] = nums[i];
    }
    stack.push(i);
  }

  return result;
}
```

**Q6. Why does the monotonic stack approach achieve O(n) total time despite the `while` loop nested inside the `for` loop?**
A: Although there's a `while` loop inside a `for` loop (which superficially looks like it could be O(n²)), the key observation is that **every index is pushed onto the stack exactly once, and popped at most once** across the *entire* algorithm's execution — the total number of pop operations across all iterations of the outer loop combined is bounded by n (the total number of pushes). This is a classic **amortized analysis** argument: while a single iteration of the outer loop could, in the worst case, trigger many pops, the *total* work across all iterations combined is still O(n), because no element can be popped more than once.

**Q7. How do you design a "min stack" that supports `push`, `pop`, `top`, and `getMin` all in O(1) time?**
A: Maintain a second, auxiliary stack that tracks the **minimum value at each corresponding point** in the main stack's history — every time you push onto the main stack, also push the current minimum (either the new value, if it's smaller than the previous minimum, or the previous minimum unchanged) onto the auxiliary stack. Popping from the main stack is always paired with popping from the auxiliary stack, keeping them in sync. `getMin()` simply peeks at the top of the auxiliary stack — O(1).

```js
class MinStack {
  constructor() {
    this.stack = [];
    this.minStack = [];
  }

  push(val) {
    this.stack.push(val);
    const currentMin = this.minStack.length === 0
      ? val
      : Math.min(val, this.minStack[this.minStack.length - 1]);
    this.minStack.push(currentMin);
  }

  pop() {
    this.stack.pop();
    this.minStack.pop();
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  getMin() {
    return this.minStack[this.minStack.length - 1];
  }
}
```

**Q8. How can you implement a queue using two stacks, and what is the amortized complexity of each operation?**
A: Use two stacks: an "in-stack" for pushes, and an "out-stack" for pops/peeks. Enqueue always pushes onto the in-stack (O(1)). Dequeue: if the out-stack is empty, transfer every element from the in-stack to the out-stack (which reverses their order, since a stack-to-stack transfer via repeated pop/push naturally reverses order) — this transfer converts LIFO order into FIFO order; then pop from the out-stack. Each individual element is transferred from in-stack to out-stack **at most once** over its lifetime, so while a single dequeue call could be O(n) in the worst case (if a big transfer happens right then), the **amortized** cost across a sequence of operations is O(1) per operation.

```js
class QueueViaStacks {
  constructor() {
    this.inStack = [];
    this.outStack = [];
  }

  enqueue(val) {
    this.inStack.push(val);
  }

  dequeue() {
    if (this.outStack.length === 0) {
      while (this.inStack.length > 0) {
        this.outStack.push(this.inStack.pop());
      }
    }
    return this.outStack.pop();
  }
}
```

## Topic B: Queues

### Section B1: Fundamentals

**Q9. What is a queue, and how does its ordering principle differ from a stack's?**
A: A queue is a **FIFO** (First-In, First-Out) data structure — the earliest-added element is always the first one removed. Core operations: `enqueue` (add to the back), `dequeue` (remove and return from the front), `peek`/`front` (view the front without removing it) — all intended to be O(1) with a proper implementation, mirroring a real-world line/queue of people.

```
enqueue(1), enqueue(2), enqueue(3) → queue (front to back): [1, 2, 3]
dequeue() → returns 1 → queue: [2, 3]
peek() → returns 2 (unchanged) → queue: [2, 3]
```

**Q10. Why is a naive array-backed queue (using `array.shift()` for dequeue) inefficient, and what's the standard fix?**
A: `Array.shift()` removes the first element but must then shift every remaining element one position to the left to close the gap — O(n) per dequeue, making a sequence of n dequeues O(n²) total. The standard fix is a **circular buffer** (circular array): maintain `front` and `rear` index pointers into a fixed-size (or dynamically resized) array, wrapping both indices around via modulo arithmetic (`(index + 1) % capacity`) instead of physically shifting elements — this achieves true O(1) enqueue/dequeue.

```js
class CircularQueue {
  constructor(capacity) {
    this.items = new Array(capacity);
    this.capacity = capacity;
    this.front = 0;
    this.size = 0;
  }

  enqueue(val) {
    if (this.size === this.capacity) throw new Error('Queue is full');
    const rear = (this.front + this.size) % this.capacity;
    this.items[rear] = val;
    this.size++;
  }

  dequeue() {
    if (this.size === 0) throw new Error('Queue is empty');
    const val = this.items[this.front];
    this.front = (this.front + 1) % this.capacity;
    this.size--;
    return val;
  }

  peek() {
    if (this.size === 0) throw new Error('Queue is empty');
    return this.items[this.front];
  }
}
```

**Q11. How does a linked-list-backed queue achieve O(1) enqueue and dequeue, and what pointers must be maintained?**
A: Maintain both a `head` pointer (for O(1) dequeue — remove from the front) and a `tail` pointer (for O(1) enqueue — add to the back) — this is precisely why a queue implementation needs to track *both* ends, unlike a stack, which only ever operates on one end. Without a maintained `tail` pointer, enqueue would require an O(n) traversal to find the current last node before appending, defeating the purpose.

```js
class LinkedQueue {
  constructor() {
    this.head = null;
    this.tail = null;
    this.length = 0;
  }

  enqueue(val) {
    const node = { val, next: null };
    if (this.tail === null) {
      this.head = this.tail = node;
    } else {
      this.tail.next = node;
      this.tail = node;
    }
    this.length++;
  }

  dequeue() {
    if (this.head === null) throw new Error('Queue is empty');
    const val = this.head.val;
    this.head = this.head.next;
    if (this.head === null) this.tail = null; // queue just became empty
    this.length--;
    return val;
  }
}
```

**Q12. What are the classic use cases that make a queue the natural data structure of choice?**
A: Any problem involving **processing in strict arrival order**, or level-by-level exploration: breadth-first search/traversal (BFS naturally uses a queue to explore nodes level by level, in contrast to DFS's stack-based "go deep first" approach), task scheduling (round-robin CPU scheduling, print job queues, message queues in distributed systems), buffering data between producers and consumers at different processing rates, and any simulation where "first come, first served" is the required semantic (customer service lines, request handling).

### Section B2: Advanced Queue Patterns

**Q13. What is a "deque" (double-ended queue), and how does it generalize both stacks and queues?**
A: A deque supports O(1) insertion and removal at **both** the front and the back (`pushFront`, `pushBack`, `popFront`, `popBack`). It generalizes a stack (use only one end, consistently) and a queue (use `pushBack` + `popFront`, or symmetrically `pushFront` + `popBack`) as special-case usage patterns of the same underlying structure. Implemented via a doubly linked list (native O(1) at both ends) or a circular buffer with two movable index pointers.

**Q14. How is a deque used to solve the "sliding window maximum" problem efficiently?**
A: Maintain a deque of **indices**, kept in decreasing order of their corresponding values (a monotonic deque) — whenever a new element arrives, pop off (from the back) any indices whose values are smaller than the new element (they can never be the maximum again, since the new element is both larger and more recent), then push the new index. Additionally, pop from the **front** whenever the front index has fallen outside the current window's bounds. The front of the deque is always the index of the current window's maximum.

```js
function maxSlidingWindow(nums, k) {
  const deque = []; // stores indices, values in decreasing order
  const result = [];

  for (let i = 0; i < nums.length; i++) {
    // remove indices outside the current window from the front
    if (deque.length > 0 && deque[0] <= i - k) {
      deque.shift();
    }

    // remove indices with smaller values from the back — they're obsolete
    while (deque.length > 0 && nums[deque[deque.length - 1]] < nums[i]) {
      deque.pop();
    }

    deque.push(i);

    if (i >= k - 1) {
      result.push(nums[deque[0]]); // front of deque = current window's max
    }
  }

  return result;
}
```

Time: O(n) — each index is pushed and popped from the deque at most once, same amortized argument as the monotonic stack (Q6). Space: O(k) for the deque in the worst case.

**Q15. What is a priority queue, and how does it differ fundamentally from a standard FIFO queue?**
A: A priority queue is not a queue in the strict FIFO sense at all — it's typically implemented via a **heap**, and it dequeues elements in order of **priority** (smallest or largest value first, depending on min-heap or max-heap), regardless of insertion order. It's included in "queue" discussions primarily due to naming convention and its role in queue-adjacent problems (e.g., Dijkstra's algorithm, task scheduling by priority, k-way merging via a min-heap as covered in the merge-lists guide), but its underlying implementation and complexity characteristics (O(log n) insert/extract, versus a true queue's O(1)) are fundamentally different from array/linked-list-backed FIFO queues.

**Q16. How do you implement a stack using two queues, and what is its complexity compared to a native stack?**
A: Two approaches exist: (1) make `push` expensive — enqueue the new element into an empty auxiliary queue, then dequeue every element from the main queue and re-enqueue them after the new element (making the new element end up at the front, ready to be the next "pop" target), giving O(n) push and O(1) pop; or (2) make `pop` expensive — always enqueue normally (O(1) push), but implement `pop` by dequeuing all-but-the-last element into an auxiliary queue, returning that last element, then swapping the queues — O(n) pop, O(1) push. Either way, one operation is forced to O(n), unlike a native stack's O(1) for both — this is a case where forcing one structure to emulate another's interface necessarily sacrifices some efficiency (a useful contrast to Q8's queue-via-stacks, which achieves amortized O(1) for both operations, showing the emulation cost isn't symmetric between the two directions).

### Section C: Cross-Topic Scenario / Interview-Style Questions

**Q17. "You need to check whether a string of brackets `()[]{}` is balanced (every opening bracket has a matching closing bracket in the correct order). Why is a stack specifically the right structure, and would a queue work instead?"**
A: A stack is the correct choice because bracket matching is inherently a **LIFO** relationship — the most recently opened (and still unclosed) bracket must be the next one closed, mirroring exactly how a stack's `pop` returns the most recently pushed element. A queue would enforce the wrong order entirely (FIFO would try to match the *oldest* unclosed bracket first, which is incorrect — e.g., `"([)]"` would be wrongly validated or `"()[]"` might fail correctly-nested checks) — this is a clean example of choosing a data structure based on which ordering *semantic* (LIFO vs FIFO) matches the problem's actual structure, not just picking one arbitrarily.

**Q18. "A teammate implements a queue using JavaScript's native array with `push()` for enqueue and `shift()` for dequeue, and the code is running slowly at scale. What's happening, and how do you fix it?"**
A: `Array.shift()` is O(n) because removing the first element requires shifting every subsequent element left by one position — over many dequeues, this degrades to O(n²) total for n operations. I'd recommend either a circular-buffer-backed queue (fixed or dynamically resized array with `front`/`rear` index pointers, avoiding physical shifting entirely) or a linked-list-backed queue (maintaining both `head` and `tail` pointers) — both achieve true O(1) enqueue/dequeue, fixing the quadratic blowup.

**Q19. "How would you find the maximum element in every contiguous window of size k across a large array, efficiently? What's wrong with just scanning each window naively?"**
A: Naively scanning each window for its max is O(n × k) — for each of the (roughly) n windows, an O(k) scan. The efficient approach is a monotonic deque (Q14): maintain window-relevant indices in decreasing order of value, popping obsolete (out-of-window or smaller-and-older) indices as the window slides — this achieves O(n) total time, since each index enters and leaves the deque at most once across the entire algorithm, a significant improvement over the naive approach especially for large k.

**Q20. "You're designing a task scheduler where tasks have different priority levels, and higher-priority tasks should always be processed before lower-priority ones regardless of arrival order. Is a standard queue appropriate here?"**
A: No — a standard FIFO queue only respects arrival order, not priority, so it wouldn't satisfy "higher-priority tasks processed first" regardless of when they arrived. A **priority queue** (heap-backed) is the correct structure here, since it's specifically designed to always surface the highest (or lowest, depending on configuration) priority element next, independent of insertion order — this is a good opportunity to clarify that "priority queue" is a related but fundamentally different structure from a standard queue, despite the shared name.

**Q21. "Compare implementing a queue using two stacks versus implementing a stack using two queues — which emulation is 'cheaper,' and why?"**
A: Queue-via-two-stacks (Q8) achieves **amortized O(1)** for both enqueue and dequeue, because each element is transferred between the two stacks at most once over its entire lifetime, spreading that cost thin across many operations. Stack-via-two-queues (Q16) cannot achieve the same balance — one of `push` or `pop` is forced to be O(n) on *every single call*, not just amortized occasionally, because a queue's FIFO nature doesn't allow the same "lazy, occasional bulk transfer" trick that makes the stacks-based queue emulation cheap; every stack-via-queues operation of the "expensive" type does its full O(n) work immediately, not spread out. This asymmetry is a nice illustration of how the *specific* structural properties of the underlying primitive (not just its big-O operation costs in isolation) determine how cheaply it can emulate a different interface.

## Problem 1 — Valid Parentheses

### Problem
Given a string containing just the characters `(`, `)`, `{`, `}`, `[`, `]`, determine if the input string is valid — every opening bracket must be closed by the same type of bracket, in the correct order.

```
Input:  s = "()[]{}"
Output: true

Input:  s = "(]"
Output: false

Input:  s = "([)]"
Output: false

Input:  s = "{[]}"
Output: true
```

### Pattern Recognition
Classic stack application — bracket matching is inherently LIFO: the most recently opened bracket must be the next one closed.

### Key Insight
Push every opening bracket onto a stack. On encountering a closing bracket, it must match the bracket currently on **top** of the stack (the most recently opened, still-unclosed one) — if it doesn't match (or the stack is empty when a closing bracket appears), the string is invalid.

### Approach
Iterate through the string. Push opening brackets. On a closing bracket, check the stack isn't empty and its top matches the expected opening counterpart; pop if so, otherwise return `false` immediately. After the full scan, the string is valid only if the stack is completely empty (every opened bracket was matched).

### Solution

```js
function isValid(s) {
  const stack = [];
  const pairs = { ')': '(', ']': '[', '}': '{' };

  for (const ch of s) {
    if (ch === '(' || ch === '[' || ch === '{') {
      stack.push(ch);
    } else {
      if (stack.length === 0 || stack.pop() !== pairs[ch]) {
        return false;
      }
    }
  }

  return stack.length === 0;
}
```

### Dry Run

```
s = "{[]}"
stack=[]

ch='{': opening → push → stack=['{']
ch='[': opening → push → stack=['{','[']
ch=']': closing → stack not empty, pop()='[' === pairs[']']='[' ✓ → stack=['{']
ch='}': closing → stack not empty, pop()='{' === pairs['}']='{' ✓ → stack=[]

end of string, stack.length===0 → return true ✓
```

```
s = "([)]"
stack=[]

ch='(': push → stack=['(']
ch='[': push → stack=['(','[']
ch=')': closing → pop()='[' === pairs[')']='(' ? '[' !== '(' → return false ✓
(correctly identifies the mismatched/out-of-order nesting)
```

### Complexity
- Time: O(n) — single pass through the string.
- Space: O(n) — worst case, the stack holds every character if the string is all opening brackets.

### Edge Cases
- Empty string: loop never executes, stack remains empty, correctly returns `true` (vacuously valid).
- String with only opening brackets (e.g., `"((("`): stack ends non-empty, correctly returns `false`.
- String with only closing brackets (e.g., `")))"`): first closing bracket finds an empty stack, immediately returns `false`.
- Odd-length string: cannot possibly be balanced (brackets always close in pairs), and the algorithm naturally catches this via either a leftover non-empty stack or an early empty-stack-on-closing-bracket detection.

### Follow-up Questions
- "What if the string also contains other characters (not just brackets) that should be ignored?" → Add a check to skip/ignore any character not in the opening or closing bracket sets, leaving the core logic unchanged.
- "Can you solve this without a hash map for the pairs lookup?" → Yes, using a chain of if/else comparisons instead, though the hash map version is generally cleaner and more easily extensible to additional bracket types.

## Problem 2 — Min Stack

### Problem
Design a stack that supports `push`, `pop`, `top`, and retrieving the minimum element (`getMin`), all in O(1) time.

```
minStack.push(-2)
minStack.push(0)
minStack.push(-3)
minStack.getMin() → -3
minStack.pop()
minStack.top()    → 0
minStack.getMin() → -2
```

### Pattern Recognition
Auxiliary "shadow" stack technique — track the running minimum at every point in the main stack's history, kept perfectly in sync with the main stack's push/pop operations.

### Key Insight
Instead of recomputing the minimum on every `getMin()` call (which would be O(n) if done naively by scanning), maintain a second stack that always has, at its top, the minimum value considering only the elements currently on the main stack — pushing and popping both stacks in lockstep keeps this invariant true at every point in time.

### Approach
`push`: push onto the main stack; also push onto the min-stack either the new value (if it's a new minimum) or the current minimum unchanged (if the new value isn't smaller). `pop`: pop from both stacks together. `getMin`: simply peek the min-stack's top.

### Solution

```js
class MinStack {
  constructor() {
    this.stack = [];
    this.minStack = [];
  }

  push(val) {
    this.stack.push(val);
    const currentMin = this.minStack.length === 0
      ? val
      : Math.min(val, this.minStack[this.minStack.length - 1]);
    this.minStack.push(currentMin);
  }

  pop() {
    this.stack.pop();
    this.minStack.pop();
  }

  top() {
    return this.stack[this.stack.length - 1];
  }

  getMin() {
    return this.minStack[this.minStack.length - 1];
  }
}
```

### Dry Run

```
minStack = new MinStack()

push(-2): stack=[-2], minStack: currentMin=min(-2,∅)=-2 → minStack=[-2]
push(0):  stack=[-2,0], currentMin=min(0,-2)=-2 → minStack=[-2,-2]
push(-3): stack=[-2,0,-3], currentMin=min(-3,-2)=-3 → minStack=[-2,-2,-3]

getMin() → minStack top = -3 ✓

pop(): stack=[-2,0], minStack=[-2,-2]

top() → stack top = 0 ✓
getMin() → minStack top = -2 ✓
```

### Complexity
- Time: O(1) for every operation (`push`, `pop`, `top`, `getMin`).
- Space: O(n) — the min-stack grows in lockstep with the main stack, doubling the overall space usage but keeping the same asymptotic O(n) order.

### Edge Cases
- Popping down to empty, then pushing again: both stacks correctly track this since they're always modified together — `minStack` correctly resets its "history" naturally as elements are popped off.
- Pushing the same minimum value multiple times in a row: each push correctly re-records that value (or an equal one) as the current min at that point — popping later correctly reveals the previous (equal) minimum still intact underneath.
- Single-element stack: `getMin()` correctly returns that one element, since `minStack` also has exactly one entry equal to it.

### Follow-up Questions
- "Can you do this with O(1) space instead of doubling storage?" → A common optimization: only push onto `minStack` when a *new* minimum is found (not on every push), and pop from `minStack` only when the popped main-stack value equals the current min — this reduces `minStack`'s size in practice (though worst-case is still O(n) if every element is a new minimum, e.g., a strictly decreasing sequence of pushes).
- "Extend to also support `getMax()` in O(1)?" → Maintain a third parallel "max-stack" using the identical technique, tracking running maximums instead of minimums.

## Problem 3 — Next Greater Element (Monotonic Stack)

### Problem
Given an array `nums`, for each element, find the next element to its right that is greater than it. If no such element exists, use `-1`.

```
Input:  nums = [2, 1, 2, 4, 3]
Output: [4, 2, 4, -1, -1]
```

### Pattern Recognition
Classic monotonic (decreasing) stack — efficiently finds, for every element, the next larger element to its right in O(n) total time.

### Key Insight
Maintain a stack of indices whose corresponding values form a decreasing sequence from bottom to top. When a new element arrives that's larger than the stack's top, that new element is exactly the "next greater element" for every index popped off (since they were all smaller and are now confirmed to have found their answer) — pop them all, recording the answer, before pushing the new index.

### Approach
Iterate through the array once. Before pushing the current index, pop off (and resolve) every stack index whose value is smaller than the current element. Push the current index. Any indices still on the stack after the full pass have no next greater element (remain `-1`).

### Solution

```js
function nextGreaterElement(nums) {
  const result = new Array(nums.length).fill(-1);
  const stack = []; // indices, values in decreasing order bottom-to-top

  for (let i = 0; i < nums.length; i++) {
    while (stack.length > 0 && nums[stack[stack.length - 1]] < nums[i]) {
      const idx = stack.pop();
      result[idx] = nums[i];
    }
    stack.push(i);
  }

  return result;
}
```

### Dry Run

```
nums = [2, 1, 2, 4, 3]
stack=[], result=[-1,-1,-1,-1,-1]

i=0 (val=2): stack empty → push → stack=[0]
i=1 (val=1): nums[stack top=0]=2 < 1? no → push → stack=[0,1]
i=2 (val=2): nums[stack top=1]=1 < 2? yes → pop idx=1, result[1]=2 → stack=[0]
             nums[stack top=0]=2 < 2? no (equal, not strictly less) → push → stack=[0,2]
i=3 (val=4): nums[stack top=2]=2 < 4? yes → pop idx=2, result[2]=4 → stack=[0]
             nums[stack top=0]=2 < 4? yes → pop idx=0, result[0]=4 → stack=[]
             stack empty → push → stack=[3]
i=4 (val=3): nums[stack top=3]=4 < 3? no → push → stack=[3,4]

end of array. stack=[3,4] never resolved → result[3] and result[4] remain -1

Result: [4, 2, 4, -1, -1] ✓
```

### Complexity
- Time: O(n) — each index pushed once and popped at most once across the whole algorithm (amortized argument, see Q6).
- Space: O(n) — worst case, the stack holds every index (e.g., a strictly decreasing input array).

### Edge Cases
- Strictly decreasing array (e.g., `[5,4,3,2,1]`): no element ever finds a next-greater element to its right; every index remains on the stack until the end, all results stay `-1`.
- Strictly increasing array (e.g., `[1,2,3,4,5]`): every element immediately resolves the previous one(s) on the stack; only the very last element remains unresolved (`-1`).
- Array with duplicate values: the strict `<` comparison means equal values don't trigger a pop — a later equal value is NOT considered "greater," correctly leaving the earlier equal element's search ongoing (its next greater element, if any, must be strictly larger, found later).
- Single-element array: no next element exists at all; correctly returns `[-1]`.

### Follow-up Questions
- "What if the array is circular (the 'next' element can wrap around to the beginning)?" → Process the array twice (conceptually, iterate `2n` times using `i % n` to index), allowing wraparound comparisons, while still only pushing/popping actual indices (0 to n-1) — a common and clean extension of the same monotonic stack technique.
- "Find the next SMALLER element instead?" → Flip the comparison direction (maintain an increasing stack instead of decreasing) — the rest of the technique is unchanged.

## Problem 4 — Implement Queue Using Two Stacks

### Problem
Implement a FIFO queue using only two stacks. The queue should support `enqueue`, `dequeue`, `peek` (front element), and `empty`, using only stack operations (`push`, `pop`, `top`, `isEmpty`).

```
queue = new QueueViaStacks()
queue.enqueue(1)
queue.enqueue(2)
queue.peek()     → 1
queue.dequeue()  → 1
queue.empty()    → false
```

### Pattern Recognition
Two-stack emulation — an "in-stack" absorbs new elements, an "out-stack" (populated lazily, via a full reversal transfer) serves dequeue/peek requests in correct FIFO order.

### Key Insight
Popping every element off one stack and pushing each onto a second stack **reverses their order** — since a stack naturally reverses insertion order once (LIFO), doing this reversal once converts the in-stack's LIFO order into the correct FIFO order for the out-stack. This transfer only needs to happen when the out-stack is empty (lazy transfer), which is what gives the amortized O(1) guarantee.

### Approach
`enqueue`: always push onto `inStack` (O(1), never needs to look at `outStack`). `dequeue`/`peek`: if `outStack` is empty, transfer everything from `inStack` to `outStack` (reversing order in the process); then operate on `outStack`'s top.

### Solution

```js
class QueueViaStacks {
  constructor() {
    this.inStack = [];
    this.outStack = [];
  }

  enqueue(val) {
    this.inStack.push(val);
  }

  _transferIfNeeded() {
    if (this.outStack.length === 0) {
      while (this.inStack.length > 0) {
        this.outStack.push(this.inStack.pop());
      }
    }
  }

  dequeue() {
    this._transferIfNeeded();
    return this.outStack.pop();
  }

  peek() {
    this._transferIfNeeded();
    return this.outStack[this.outStack.length - 1];
  }

  empty() {
    return this.inStack.length === 0 && this.outStack.length === 0;
  }
}
```

### Dry Run

```
queue = new QueueViaStacks()
inStack=[], outStack=[]

enqueue(1): inStack=[1]
enqueue(2): inStack=[1,2]
enqueue(3): inStack=[1,2,3]

peek(): outStack empty → transfer:
  pop inStack(3), push outStack → inStack=[1,2], outStack=[3]
  pop inStack(2), push outStack → inStack=[1], outStack=[3,2]
  pop inStack(1), push outStack → inStack=[], outStack=[3,2,1]
  return outStack top = 1 ✓ (correctly the FIRST enqueued element)

dequeue(): outStack not empty (no transfer needed) → pop outStack → returns 1
  outStack=[3,2]

enqueue(4): inStack=[4]  (outStack is untouched, still has [3,2])

dequeue(): outStack not empty → pop → returns 2
  outStack=[3]

dequeue(): outStack not empty → pop → returns 3
  outStack=[]

dequeue(): outStack empty → transfer: pop inStack(4), push outStack → outStack=[4]
  pop outStack → returns 4 ✓ (correctly the last-enqueued, now-only remaining element)

empty(): inStack=[], outStack=[] → true ✓
```

### Complexity
- `enqueue`: O(1), always.
- `dequeue`/`peek`: O(1) amortized — a single element is transferred from `inStack` to `outStack` at most once over its entire lifetime in the queue, so while any *individual* call could trigger an O(n) transfer, that cost is "paid for" by all the O(1) enqueues that led up to it, averaging out to O(1) per operation across a sequence.
- Space: O(n) — both stacks combined hold at most n elements at any time.

### Edge Cases
- Dequeue/peek called when both stacks are empty: `outStack.pop()` on an empty array returns `undefined` in JS — real implementations should typically throw or return a sentinel value; worth flagging explicitly as a defensive check to add.
- Interleaved enqueue/dequeue calls (not all enqueues first, then all dequeues): handled correctly, as shown in the dry run — `outStack` is only refilled when it's empty, and `inStack` can keep absorbing new enqueues in the meantime without disturbing `outStack`'s already-correctly-ordered contents.
- Repeated `peek()` calls without an intervening `dequeue()`: each call correctly re-checks `outStack` (already non-empty after the first transfer), returning the same front element without re-transferring or losing state.

### Follow-up Questions
- "What if you needed a stack implemented using two queues instead?" → See Q16 — fundamentally more expensive, since one of `push`/`pop` is forced to O(n) on every single call (not just amortized), due to a queue's FIFO nature not supporting the same lazy-transfer trick.
- "Can this be done with just ONE stack (plus recursion, no second explicit stack)?" → A more advanced variant exists using recursion to simulate the second stack's role via the call stack itself, conceptually similar to the "reverse a stack using recursion" technique from the dedicated reversal guide — more complex and primarily an exercise in recursive thinking rather than a practical implementation choice.

## Problem 5 — Sliding Window Maximum

### Problem
Given an array `nums` and a window size `k`, return an array of the maximum value in each contiguous window of size `k` as it slides from left to right across the array.

```
Input:  nums = [1,3,-1,-3,5,3,6,7], k = 3
Output: [3,3,5,5,6,7]
```

### Pattern Recognition
Monotonic deque — maintains window-relevant indices in decreasing order of value, giving O(1) access to the current window's maximum at all times.

### Key Insight
An index/value can be safely discarded from consideration (popped from the back of the deque) the moment a **larger** value appears later in the array, since that later, larger value will always be preferred as the window's maximum for as long as both remain within the window — the discarded smaller value can never become the max again. Separately, the front of the deque must be evicted once its index falls outside the current window's left boundary.

### Approach
Slide through the array once. Before adding the current index, pop off (from the back) any deque indices whose values are smaller than the current value. Push the current index. Pop off (from the front) any index that's now outside the window. Once the window is fully formed (`i >= k-1`), the front of the deque holds the current window's maximum.

### Solution

```js
function maxSlidingWindow(nums, k) {
  const deque = []; // indices, values in decreasing order
  const result = [];

  for (let i = 0; i < nums.length; i++) {
    if (deque.length > 0 && deque[0] <= i - k) {
      deque.shift(); // evict index that's now outside the window
    }

    while (deque.length > 0 && nums[deque[deque.length - 1]] < nums[i]) {
      deque.pop(); // evict now-obsolete smaller values
    }

    deque.push(i);

    if (i >= k - 1) {
      result.push(nums[deque[0]]);
    }
  }

  return result;
}
```

### Dry Run

```
nums = [1,3,-1,-3,5,3,6,7], k=3
deque=[], result=[]

i=0(1): deque empty, no eviction needed → push 0 → deque=[0]
  i(0) < k-1(2) → no result yet

i=1(3): deque[0]=0 <= 1-3=-2? no → no front eviction
  nums[deque back=0]=1 < 3? yes → pop → deque=[]
  push 1 → deque=[1]
  i(1) < 2 → no result yet

  nums[deque back=1]=3 < -1? no → no back eviction
  push 2 → deque=[1,2]
  i(2)>=2 → result.push(nums[deque[0]=1]=3) → result=[3]

  nums[deque back=2]=-1 < -3? no → no back eviction
  push 3 → deque=[1,2,3]
  result.push(nums[1]=3) → result=[3,3]

  nums[deque back=3]=-3 < 5? yes → pop → deque=[2]
  nums[deque back=2]=-1 < 5? yes → pop → deque=[]

```

### Complexity
- Time: O(n) — each index is pushed once and popped at most once (from either end) across the whole algorithm.
- Space: O(k) — the deque holds at most k indices at any point (bounded by the window size, due to the front-eviction logic).

### Edge Cases
- `k = 1`: every element is its own window; deque logic degenerates to simply reporting each element as-is (no eviction ever needed beyond the immediate current index).
- `k` equals the array length: exactly one window (the whole array); result has exactly one element, the array's overall maximum.
- Strictly decreasing array: back-eviction never triggers (every new element is smaller than what's already in the deque), so the deque grows to hold up to k indices, with the front-eviction logic handling the sliding correctly as old maximums fall out of the window.
- Strictly increasing array: back-eviction triggers on every new element (each is larger than everything before it), keeping the deque very small (often just 1 element) throughout.

### Follow-up Questions
- "Can you solve this with a different data structure, e.g., a balanced BST or a max-heap?" → A max-heap works but requires **lazy deletion** (since a heap doesn't support efficient arbitrary-element removal) — you'd push `(value, index)` pairs and, when peeking the max, discard any popped entries whose index has fallen outside the window, achieving O(n log n) instead of the deque's O(n) — worth mentioning as a valid but less efficient alternative.
- "What if you need the sliding window MINIMUM instead?" → Flip the deque's monotonic direction (maintain increasing order instead of decreasing) — otherwise the technique is identical.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve LIFO or FIFO ordering, or a related structural pattern?
│
├── NEED LIFO PROCESSING (most-recent-first): nested structures, undo, backtracking, DFS?
│   └── STACK
│       ├── Standard push/pop/peek → array-backed (O(1) amortized) or linked-list-backed (O(1) worst-case)
│       ├── Need O(1) getMin/getMax alongside push/pop → Min/Max Stack (auxiliary shadow stack)
│       └── Need "next greater/smaller element" for every position → Monotonic Stack
│
├── NEED FIFO PROCESSING (arrival-order-first): BFS, task scheduling, buffering?
│   └── QUEUE
│       ├── Standard enqueue/dequeue → Circular Buffer (array) or Linked List (both ends tracked)
│       ├── AVOID naive array .shift()-based dequeue — that's O(n) per call, O(n²) total
│       └── Need max/min over a SLIDING WINDOW → Monotonic Deque
│
├── NEED PRIORITY-BASED PROCESSING (not insertion order)?
│   └── Priority Queue (heap-backed) — NOT a true FIFO queue despite the name
│
├── NEED TO EMULATE ONE STRUCTURE USING THE OTHER?
│   ├── Queue using two Stacks → amortized O(1) both ways (lazy transfer trick)
│   └── Stack using two Queues → one operation forced to O(n) EVERY call (no lazy-transfer equivalent)
│
├── NEED BOTH-ENDS O(1) ACCESS (front AND back, both insert and remove)?
│   └── Deque (Double-Ended Queue) — generalizes both stack and queue usage patterns
│
└── NEED BRACKET/PARENTHESES MATCHING OR ANY "MOST RECENT UNCLOSED THING" LOGIC?
    └── STACK — this is the textbook LIFO-shaped problem
```

## Common Bugs Checklist

Before submitting any stack or queue solution, verify:

1. **Stack vs Queue chosen based on the problem's actual ordering need (LIFO vs FIFO), not habit?** — Using a queue for bracket matching (or a stack for BFS) silently produces wrong results, since the ordering semantics are fundamentally mismatched to the problem.

2. **Array-backed queue avoids `.shift()`/`.unshift()` for the O(1)-required end?** — These are O(n) operations; a circular buffer or linked-list-backed queue is required for genuine O(1) enqueue/dequeue.

3. **Min/Max stack: auxiliary stack pushed and popped in EXACT lockstep with the main stack?** — Any divergence (e.g., popping the main stack without popping the auxiliary one) desynchronizes them, corrupting future `getMin()`/`getMax()` results.

4. **Monotonic stack/deque: comparison direction matches the intended "next greater" vs "next smaller" semantics?** — Using `<` when `>` was intended (or vice versa) silently flips the entire algorithm's output.

5. **Monotonic deque (sliding window max/min): front-eviction check uses the correct out-of-window condition (`deque[0] <= i - k`), and happens BEFORE back-eviction/push each iteration?** — Checking front-eviction after already pushing the current index can incorrectly evict the just-pushed index if `k` is very small, or process things in the wrong order relative to the current window's true bounds.

6. **Queue-via-two-stacks: transfer only happens when `outStack` is EMPTY, not unconditionally on every dequeue?** — Transferring unconditionally destroys the amortized O(1) guarantee, degrading every dequeue back to O(n) regardless of whether a transfer was actually necessary.

7. **Circular queue: `front`/`rear` index arithmetic uses modulo correctly, and `size` (or an equivalent full/empty distinguishing mechanism) is tracked to disambiguate a full buffer from an empty one?** — A naive circular buffer using only two index pointers without a separate size counter can't distinguish "completely full" from "completely empty" when `front === rear`, a classic circular-buffer bug.

---

**Final Tip:** At the 5 YOE level, interviewers expect immediate recognition of which ordering semantic (LIFO or FIFO) a problem actually requires — bracket matching, undo/redo, and DFS all scream "stack"; BFS, scheduling, and "first come first served" all scream "queue." From there, the specific variant (monotonic stack/deque, min-stack, circular buffer, two-structure emulation) is a refinement layered on top of that base choice, chosen based on which *additional* operation (O(1) min, O(1) both-ends access, O(1) emulation of the other structure) the problem specifically demands. Naming the base ordering semantic first, out loud, before diving into implementation details, is the strongest signal of clear problem-structure recognition.
