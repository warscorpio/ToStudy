## Topic A: Monotonic Stack Fundamentals

### Section A1: Fundamentals

**Q1. What is a monotonic stack, and what invariant does it maintain?**
A: A monotonic stack is a stack that maintains its elements in either strictly increasing or strictly decreasing order from bottom to top at all times. The invariant is enforced on every push: before pushing a new element, pop all elements that would violate the order. The popped elements are exactly the elements for which the new element is the "answer" — the first element to their right (or left, depending on traversal direction) that breaks the monotone order.

```
Monotonically decreasing stack (bottom → top):
[9, 7, 4, 2]   ← valid: each element < the one below it

Push 5:
  Pop 2 (2 < 5, violates decreasing order — 5 is the answer for 2)
  Pop 4 (4 < 5, violates decreasing order — 5 is the answer for 4)
  Push 5
Stack: [9, 7, 5]

Each popped element has found its "next greater element" = 5.
```

The stack is the data structure; the monotone property is the invariant; the pop events are the answer-delivery mechanism. These three components together are the monotonic stack pattern.

**Q2. What class of problems does the monotonic stack pattern solve, and what is the unifying theme?**
A: The monotonic stack solves problems that ask, for each element in an array, about the **nearest element in a specific direction that satisfies a specific comparison** — the "nearest greater," "nearest smaller," "next greater to the right," "previous smaller to the left," and so on. The unifying theme: these problems share a brute-force O(n²) solution (for each element, scan left or right until the condition is met), and the monotonic stack reduces this to O(n) by observing that elements eliminated during pop events can never be the answer for any future element — making it safe to discard them permanently.

The canonical family:
- **Next Greater Element (NGE)**: for each element, the first element to its right that is strictly greater.
- **Previous Greater Element (PGE)**: for each element, the first element to its left that is strictly greater.
- **Next Smaller Element (NSE)**: for each element, the first element to its right that is strictly smaller.
- **Previous Smaller Element (PSE)**: for each element, the first element to its left that is strictly smaller.
- **Stock Span**: for each day, how many consecutive previous days had prices ≤ today's price.
- **Largest Rectangle in Histogram**: for each bar, how far left and right it can extend as the limiting height.
- **Trapping Rain Water**: per-position bounded water (solvable with two-pass precomputation or two-pointer, but also illuminated by monotonic stack reasoning).

**Q3. What are the two varieties of monotonic stack, and when do you use each?**
A: The two varieties differ in which direction the order runs and which comparison problem they solve:

**Monotonically decreasing stack** (elements decrease from bottom to top): used for **next/previous greater element** problems. When a new element is greater than the stack top, the top has found its "next greater" — pop it. The stack retains only elements that haven't yet found a greater element to their right; these are always in decreasing order because any out-of-order element would have been popped when a larger element arrived.

**Monotonically increasing stack** (elements increase from bottom to top): used for **next/previous smaller element** problems. When a new element is smaller than the stack top, the top has found its "next smaller" — pop it. The stack retains only elements that haven't yet found a smaller element to their right.

```
For NGE (next greater element) → use DECREASING stack:
  Pop when new element > stack top → popped element's NGE = new element

For NSE (next smaller element) → use INCREASING stack:
  Pop when new element < stack top → popped element's NSE = new element

Mnemonic: the stack holds "candidates waiting for their answer."
The condition that triggers a pop IS the answer for the popped element.
```

**Q4. What is the general template for a monotonic stack solution, and how does it adapt for NGE vs. NSE?**
A: The template has three parts: iterate over the array, enforce the monotone invariant on push (pop violating elements and record their answers), then handle any remaining elements in the stack (they have no answer — default to -1 or 0 or the problem's sentinel value).

```js
// General monotonic stack template
function monotonicStack(arr) {
  const n = arr.length;
  const result = new Array(n).fill(-1); // default: no answer found
  const stack = []; // stores INDICES, not values

  for (let i = 0; i < n; i++) {
    // Pop elements that violate the monotone property
    // Condition varies: > for NGE (decreasing stack), < for NSE (increasing stack)
    while (stack.length > 0 && arr[stack[stack.length - 1]] < arr[i]) {
      const idx = stack.pop();
      result[idx] = arr[i]; // arr[i] is the NGE for arr[idx]
    }
    stack.push(i); // push index, not value — enables distance/span calculations
  }
  // Elements remaining in stack have no NGE → result stays -1
  return result;
}
```

Key design decisions baked into this template:
1. **Store indices, not values** — enables computing distances (span, width) in addition to values.
2. **Process left to right for "next" (rightward) queries** — the new element arriving from the right is the candidate answer for stack elements.
3. **Process right to left for "previous" (leftward) queries** — or equivalently, process left to right but query the stack top before pushing (the stack top is the most recent unbeaten candidate to the left).
4. **Remaining elements get a sentinel** — elements left in the stack after the full pass have no answer in the specified direction.

**Q5. Why does a monotonic stack achieve O(n) time despite the inner while loop?**
A: The inner while loop appears to make the algorithm O(n²), but a standard amortized analysis shows it's O(n) total. Each element is pushed onto the stack exactly once and popped from the stack at most once. Therefore, the total number of push operations across all iterations is exactly n, and the total number of pop operations across all iterations is at most n. The inner while loop's total work across the entire outer for loop is bounded by n pops — making the total work O(n), not O(n²). This is the same amortized argument as dynamic array resizing: the expensive operation (pop/resize) happens infrequently enough that the average cost per iteration remains O(1).

**Q6. When should you store indices in the stack vs. values, and why is indices almost always preferable?**
A: Storing indices is almost always preferable because:
1. **The value is always recoverable** from the index: `arr[stack.top()]` gives the value when needed.
2. **Distance calculations require indices**: span problems ("how many days"), histogram width ("how many bars"), and subarray problems all need the positional gap `i - stack.top() - 1` or `stack.top() - prev_stack.top()`.
3. **Duplicate values are handled correctly**: if the array has duplicate values, storing values conflates two distinct positions. Storing indices keeps them separate.

The only case where storing values suffices is when only the value of the next/previous greater/smaller is needed and no positional information is required — but even then, storing indices costs nothing extra and keeps the solution extensible.

### Section A2: Advanced Patterns

**Q7. How do you handle the "previous greater element" using the same stack framework?**
A: For PGE (previous greater element — the nearest element to the *left* that is greater), process left to right but query the stack *before* pushing, rather than popping during push. At each index `i`: while the stack top's value is ≤ `arr[i]`, pop (these are elements that `arr[i]` has surpassed — they cannot be anyone's PGE going forward). The stack top after popping (if non-empty) is the previous greater element for `arr[i]` — it's the most recent element larger than `arr[i]` that survived all previous pops. Then push `i`.

```js
function previousGreaterElement(arr) {
  const n = arr.length;
  const result = new Array(n).fill(-1);
  const stack = []; // decreasing stack (bottom → top: decreasing values)

  for (let i = 0; i < n; i++) {
    // Pop elements smaller than arr[i] — they can't be PGE for arr[i]
    while (stack.length > 0 && arr[stack[stack.length - 1]] <= arr[i]) {
      stack.pop();
    }
    // Stack top (if exists) is the nearest greater element to the LEFT of i
    result[i] = stack.length > 0 ? arr[stack[stack.length - 1]] : -1;
    stack.push(i);
  }
  return result;
}
```

The pattern: NGE delivers answers on pop (the incoming element is the answer for popped elements); PGE delivers answers on push (the stack top at push time is the answer for the incoming element). Both use a decreasing stack.

**Q8. What is the "circular array" extension of next greater element, and how does the doubling trick work?**
A: In the circular NGE problem, the array is treated as circular — elements near the end can have their NGE in the beginning of the array. The standard trick: **virtually double the array** by iterating `2n` times with index `i % n`. This simulates wrapping around: after processing the last real element, the iteration continues from the start, giving elements at the end a second chance to pop their answers from the beginning.

```js
function nextGreaterCircular(nums) {
  const n = nums.length;
  const result = new Array(n).fill(-1);
  const stack = []; // stores indices into the original array

  for (let i = 0; i < 2 * n; i++) {
    const idx = i % n;
    while (stack.length > 0 && nums[stack[stack.length - 1]] < nums[idx]) {
      result[stack.pop()] = nums[idx];
    }
    // Only push indices from the first pass (i < n)
    // Second pass only resolves answers, doesn't add new candidates
    if (i < n) stack.push(idx);
  }
  return result;
}
```

The key constraint: only push during the first `n` iterations (`i < n`). The second `n` iterations serve only to deliver answers to elements still on the stack — adding them again would create duplicate candidates. Elements remaining on the stack after `2n` iterations have no NGE in the entire circular array — they're the global maximum elements.

**Q9. How do you use two monotonic stacks simultaneously, and when is it necessary?**
A: Two simultaneous stacks are needed when an answer depends on both the **nearest greater to the left** and the **nearest greater to the right** at the same time — for example, the largest rectangle in histogram requires both the Previous Smaller Element and Next Smaller Element for each bar. One approach: two separate passes (PSE in a right-to-left pass, NSE in a left-to-right pass). The cleaner single-pass approach: maintain one stack and, when a pop event occurs (NSE found), the new stack top after popping is the PSE — both answers are delivered in a single left-to-right pass.

```js
// Single-pass: pop event delivers NSE; post-pop stack top delivers PSE
function largestRectangle(heights) {
  const n = heights.length;
  const stack = [];
  let maxArea = 0;

  for (let i = 0; i <= n; i++) {
    const h = i === n ? 0 : heights[i]; // sentinel 0 forces all remaining pops
    while (stack.length > 0 && heights[stack[stack.length - 1]] > h) {
      const height = heights[stack.pop()];
      const width = stack.length === 0 ? i : i - stack[stack.length - 1] - 1;
      maxArea = Math.max(maxArea, height * width);
    }
    stack.push(i);
  }
  return maxArea;
}
```

When `heights[stack.top()]` is popped because `h` is smaller (NSE = h), the new stack top is the first element to the left that is also smaller than the popped bar (PSE = stack.top()). The width of the rectangle with the popped bar as the limiting height is `NSE_index - PSE_index - 1`.

**Q10. What is the difference between strict and non-strict monotonic stacks, and when does it matter?**
A: A **strict** monotonic stack pops elements with `<` (for decreasing) or `>` (for increasing), meaning equal elements are retained. A **non-strict** monotonic stack pops elements with `<=` (for decreasing) or `>=` (for increasing), meaning equal elements are also popped.

The choice matters for problems with duplicate values:
- **Next strictly greater**: use strict decreasing stack (pop on `<`, not `<=`). Equal elements stay on the stack waiting for something strictly larger.
- **Next greater or equal**: use non-strict decreasing stack (pop on `<=`). Equal elements are also popped — the equal element is considered a valid "greater or equal" answer.
- **Stock span** (price ≥ previous prices): use non-strict decreasing stack — pop when the new price is ≥ the stack top, because equal-price days are included in the span.
- **Largest rectangle**: use non-strict increasing stack (pop on `>=`) — if two adjacent bars have equal height, popping the earlier one and attributing the full width to the later one gives the correct result without double-counting.

The rule of thumb: if equal elements should share the same answer, use non-strict; if an element's answer must be strictly better, use strict.

## Topic B: Next Greater Element Family

### Section B1: Fundamentals

**Q11. What is the Next Greater Element problem, and what is the exact output for elements with no NGE?**
A: Given an array `nums`, for each element find the first element to its right that is strictly greater. If no such element exists, the answer is -1. The output is an array `result` of the same length where `result[i]` is the NGE of `nums[i]`.

```
nums   = [2, 1, 2, 4, 3]
result = [4, 2, 4, -1, -1]

Explanation:
  2 → first greater to right = 4
  1 → first greater to right = 2
  2 → first greater to right = 4
  4 → no greater element to right → -1
  3 → no greater element to right → -1
```

The -1 sentinel for "no answer" is convention — some problems use 0 or the element's own value. Always confirm the sentinel with the problem statement before coding.

**Q12. What is the two-array NGE variant (LeetCode 496), and how does a HashMap bridge the two arrays?**
A: The two-array NGE variant gives two arrays `nums1` and `nums2` where `nums1` is a subset of `nums2`. For each element in `nums1`, find its NGE in `nums2`. The approach: compute NGE for every element in `nums2` using the standard monotonic stack; store the result in a HashMap `{value → NGE value}`; then for each element in `nums1`, look up its NGE from the HashMap in O(1).

```js
function nextGreaterElementTwoArrays(nums1, nums2) {
  const ngeMap = new Map(); // value → NGE value in nums2
  const stack = [];

  for (const num of nums2) {
    while (stack.length > 0 && stack[stack.length - 1] < num) {
      ngeMap.set(stack.pop(), num); // popped element's NGE = num
    }
    stack.push(num); // store values here since nums2 has unique elements
  }
  // Remaining elements in stack have no NGE → map to -1
  while (stack.length > 0) ngeMap.set(stack.pop(), -1);

  return nums1.map(n => ngeMap.get(n));
}
```

Note: this variant stores values (not indices) in the stack because `nums2` elements are guaranteed unique — no ambiguity from duplicates. For the general case with duplicates, always store indices.

**Q13. How do you find the Next Greater Element in a BST efficiently, and how does it connect to the stack pattern?**
A: In a BST, the "next greater element" for a node is its **in-order successor** — the smallest node with a value greater than the current node. For a balanced BST this is O(log n) per query. The connection to the stack pattern: an iterative in-order BST traversal uses an explicit stack to simulate the recursion; the stack at any point holds the "pending" ancestors that are greater than all currently visited nodes — exactly the "candidates waiting for their answer" mental model of the monotonic stack pattern. The BST's structural ordering guarantees the monotone property automatically.

**Q14. What is the "sum of subarray minimums" problem, and how does it generalize NGE/NSE?**
A: Given an array `arr`, find the sum of `min(subarray)` for every possible contiguous subarray. The key insight: instead of enumerating all O(n²) subarrays, use the contribution technique — for each element `arr[i]`, count how many subarrays have `arr[i]` as their minimum. This count equals `left[i] × right[i]` where `left[i]` = number of subarrays ending at `i` where `arr[i]` is the minimum (= distance to Previous Smaller Element) and `right[i]` = number of subarrays starting at `i` where `arr[i]` is the minimum (= distance to Next Smaller Element). Computing PSE and NSE for all elements in one monotonic stack pass then gives the answer in O(n).

```
For arr = [3, 1, 2, 4]:
  NSE: [1, -1, -1, -1]  (index or sentinel)
  PSE: [-1, -1, 1, 2]   (index or sentinel)

  Contribution of arr[2]=2:
    left[2]  = 2 - PSE_index(2) = 2 - 1 = 1  (subarrays ending at 2: [2])
    right[2] = NSE_index(2) - 2 = 4 - 2 = 2  (subarrays starting at 2: [2], [2,4])
    contribution = 2 × 1 × 2 = 4
```

### Section B2: Advanced Patterns

**Q15. What is the "number of visible people in a queue" problem, and how does it use a decreasing stack?**
A: Given a queue of people with different heights, person `i` can see person `j` (j > i) if everyone between them is shorter than both `heights[i]` and `heights[j]`. For each person, count how many people they can see. The monotonic decreasing stack processes right to left: for each person `i`, pop all people from the stack who are shorter than `heights[i]` — these are visible (each popped person was seen before a taller person blocked the view), plus the new stack top (if non-empty and taller) is also visible. The count of pops plus (1 if stack non-empty after pops) gives the visible count for person `i`.

**Q16. What is the "132 pattern" problem, and why does it require a reverse-pass decreasing stack?**
A: The 132 pattern problem asks: does any triple of indices `i < j < k` exist such that `nums[i] < nums[k] < nums[j]`? The monotonic stack approach: process right to left, maintaining a decreasing stack. Track a variable `third` (the "2" in "132", which is `nums[k]` — the middle value) initialized to -Infinity. When popping from the stack, update `third = max(third, popped_value)`. For each new element (processing right to left), if it is less than `third`, a valid 132 pattern exists — the current element is the "1", `third` is the "2", and the element that caused the last pop is the "3". The decreasing stack on a right-to-left pass maintains the invariant that `third` is always the largest value popped so far, representing the best candidate for the middle value of the pattern.

## Topic C: Stock Span Problem

### Section C1: Fundamentals

**Q17. What is the Stock Span problem?**
A: The stock span for day `i` is the maximum number of consecutive days (ending at and including day `i`) for which the stock price was less than or equal to the price on day `i`. In other words: count backward from day `i` how many consecutive preceding days had prices ≤ `price[i]`, and add 1 (for day `i` itself).

```
prices = [100, 80,  60, 70, 60, 75, 85]
spans  = [  1,  1,   1,  2,  1,  4,  6]

Day 6 (price=85): 85 ≥ 75, 85 ≥ 60, 85 ≥ 70, 85 ≥ 60, 85 ≥ 80, 85 < 100 → span = 6
Day 5 (price=75): 75 ≥ 60, 75 ≥ 60, 75 ≥ 70, 75 < 80 → span = 4
```

**Q18. How does the monotonic stack solve the Stock Span problem, and what exactly is stored in the stack?**
A: The stock span for day `i` equals `i - index_of_previous_greater_price`. The stack maintains a **non-strictly decreasing** sequence of prices (from bottom to top), storing their indices. For each new day `i`: pop all indices whose price is ≤ `prices[i]` (these days are "dominated" and can never be someone's previous-greater going forward). The stack top after popping is the index of the Previous Greater Price for day `i`. The span is `i - stack.top()` (or `i + 1` if the stack is empty — no previous greater price exists, so the span reaches all the way back to day 0).

```js
function stockSpan(prices) {
  const n = prices.length;
  const spans = new Array(n);
  const stack = []; // stores indices; maintains decreasing price order

  for (let i = 0; i < n; i++) {
    // Pop days with prices ≤ today's price (they're dominated)
    while (stack.length > 0 && prices[stack[stack.length - 1]] <= prices[i]) {
      stack.pop();
    }
    // Span = distance from previous greater price (or from day 0 if none)
    spans[i] = stack.length === 0 ? i + 1 : i - stack[stack.length - 1];
    stack.push(i);
  }
  return spans;
}
```

The span formula `i - stack.top()` works because the stack top is the most recent day with a strictly higher price — all days between stack.top() and `i` had prices ≤ `prices[i]` (they were popped) and are included in the span.

**Q19. What is the online (streaming) variant of Stock Span, and how does the stack-based design handle it?**
A: In the online variant, prices arrive one at a time (streaming) and the span must be computed immediately for each new price before the next price arrives. The same stack-based design applies unchanged — the stack is maintained as a running data structure, and each new price triggers the same pop-and-query operation. No lookahead is required because the stack encodes the complete history of "unbeaten" previous prices, which is exactly the information needed to compute the span for any new price.

```js
class StockSpanner {
  constructor() {
    this.stack = []; // [price, span] pairs
  }

  next(price) {
    let span = 1; // at minimum, today counts
    // Accumulate spans of dominated previous days
    while (this.stack.length > 0 && this.stack[this.stack.length - 1][0] <= price) {
      span += this.stack.pop()[1]; // add the dominated day's accumulated span
    }
    this.stack.push([price, span]);
    return span;
  }
}
```

This variant stores `[price, span]` pairs instead of indices because absolute indices are unavailable in the streaming context — only the accumulated span of each stack entry matters. When a dominated entry is popped, its span is added to the current accumulator — collapsing multiple dominated days into their combined span in one operation.

**Q20. Why does the Stock Span problem use a non-strict comparison (≤) while NGE uses strict (<)?**
A: The Stock Span problem asks for days with prices **less than or equal to** today's price — equal prices are included in the span. Using `<=` in the pop condition correctly pops equal-priced days (they don't break the span). The NGE problem asks for the first element **strictly greater** — equal elements do not count. Using `<` in the pop condition correctly retains equal-valued elements on the stack (they're still waiting for something strictly greater). The comparison operator in the pop condition is a direct transcription of the problem's inequality: `≤ today's price` → pop on `≤`; `strictly greater than` → pop on `<`.

### Section C2: Advanced Patterns

**Q21. How does the "sum of subarray ranges" problem extend the stock span / NSE / PSE pattern?**
A: The range of a subarray is `max(subarray) - min(subarray)`. Sum of all subarray ranges = sum of all subarray maxima - sum of all subarray minima. Each half is solved by the contribution technique with a monotonic stack: for the sum of maxima, use a decreasing stack to find each element's PSE (previous smaller) and NSE (next smaller), computing how many subarrays it is the maximum of; for the sum of minima, use an increasing stack similarly. The total is the difference.

**Q22. How does the monotonic stack apply to the "largest rectangle in histogram" — and what makes it the hardest problem in this family?**
A: The largest rectangle problem is the hardest because the "answer" for each bar depends on two directions simultaneously: how far left it extends (until a shorter bar is hit from the left) and how far right it extends (until a shorter bar is hit from the right). The monotonic stack solves both in a single left-to-right pass by exploiting the pop event: when bar `j` is popped because new bar `i` is shorter (NSE found), the current stack top after the pop is the index of the first bar to the left shorter than `j` (PSE found automatically). Width = `NSE_index - PSE_index - 1`. Height = `heights[j]`. Area = height × width. A sentinel value of 0 is appended to force all remaining bars to be popped at the end.

## Topic D: Cross-Topic & Interview-Style Questions

**Q23. "How do you decide whether to use a monotonic stack vs. a two-pointer approach vs. a prefix array approach for a range-query problem?"**
A: The decision hinges on what the query depends on:

- **Two pointers**: when the answer depends on values at *both* ends of a window simultaneously and moving the shorter/smaller pointer never helps (container with most water, trapping rain water with two pointers). Requires a monotone relationship between pointer movement and value.
- **Prefix arrays**: when the answer for each position is an aggregate (sum, max, min) over an entire prefix or suffix. O(n) build, O(1) query. Doesn't find "nearest" anything — just range aggregates.
- **Monotonic stack**: when the answer for each position is the **nearest** element in one direction satisfying a comparison (greater, smaller, ≥, ≤). The "nearest" constraint is what the stack encodes — elements popped early cannot be "nearest" for future elements.

The key distinguishing question: does the problem ask "is there any element satisfying X?" (prefix/two-pointer) or "what is the **nearest** element satisfying X?" (monotonic stack)?

**Q24. "A brute-force O(n²) solution exists for all these problems. Can you articulate exactly what the monotonic stack eliminates?"**
A: The brute-force scans every (element, candidate) pair — O(n²) pairs total. The monotonic stack eliminates pairs that are provably suboptimal: when element `A` at index `i` is popped by element `B` at index `j` (because `B` satisfies the condition relative to `A`), it also means `B` satisfies the condition relative to any element `C` at index `k < i` — so the pair `(C, A)` as a potential answer for C is already beaten by `(C, B)`, since B is closer to C than A is (j > i, so B is farther right than A... wait — this reasoning applies to the **PSE** direction, not NGE. For NGE: when B pops A, B is the answer for A; but for elements C to the left of A, B might also be the answer if B is greater than C and there's nothing between C and B that's greater than C). The core elimination: any element removed from the stack can never be the "nearest" answer for any future element — either it was already answered (popped and recorded), or a closer, better candidate exists between it and all future elements.

**Q25. "In one sentence each, what does the stack represent at any point during the algorithm, for each of the four problem types?"**
A:
- **NGE (next greater, left-to-right pass)**: the stack holds all elements seen so far that have not yet found a greater element to their right — a decreasing sequence of "still-waiting" candidates.
- **PGE (previous greater, left-to-right pass)**: the stack holds a decreasing sequence of all elements that are still "potentially the nearest greater element to the left" for some future element.
- **Stock Span**: the stack holds a decreasing sequence of "unbeaten" price days — days whose price was greater than all days between them and the current day, forming the boundary of what the span can "see back through."
- **Largest Rectangle**: the stack holds a increasing sequence of bars that are still "extendable" — no shorter bar has ended their leftward reach yet, so they remain candidates for the widest possible rectangle at their height.

**Q26. "What happens if all elements in the array are equal? Walk through the NGE and Stock Span behavior."**
A: For **NGE** with a strict decreasing stack (pop on `<`): equal elements are never popped (since `arr[i] < arr[j]` is false when equal). Every element stays on the stack. At the end, all elements remain — result is all -1. Correct: no element has a *strictly* greater neighbor.

For **Stock Span** with a non-strict stack (pop on `≤`): every new element pops all previous elements (since all prices are equal). After each pop, the stack is empty. Span = i + 1 (counting from day 0). So spans are [1, 2, 3, 4, ..., n]. Correct: each day's span extends all the way back to day 0 since all prices are equal (≤ today's price).

The difference in behavior comes entirely from the strict vs. non-strict pop condition — the same array, the same stack structure, but two different answers depending on whether equality counts.

**Q27. "How does the monotonic stack relate to the Cartesian tree data structure?"**
A: A Cartesian tree is a binary tree derived from an array where: (1) it satisfies the BST property on indices (left subtree = earlier indices, right subtree = later indices); (2) it satisfies the heap property on values (a min-Cartesian-tree has the minimum at the root of every subtree). The monotonic stack constructs a Cartesian tree in O(n): processing left to right, the stack always holds the rightmost path from root to current position. When element `arr[i]` is pushed, elements popped from the stack become the left child of `arr[i]` (they were the right spine's "beaten" elements), and `arr[i]` becomes the right child of the new stack top. The "nearest smaller to the left" of each element is its parent in the Cartesian tree. This connection means the monotonic stack implicitly constructs the Cartesian tree's rightmost path — the PSE for each element is its Cartesian tree parent.

## How to Read Each Problem

Every problem uses this structure:
1. **Problem** — exact statement and examples
2. **Pattern recognition** — which technique and why
3. **Key insight** — the invariant being exploited

## Problem 1 — Next Greater Element I

### Problem
Given two distinct integer arrays `nums1` and `nums2` where `nums1` is a subset of `nums2`, for each element in `nums1` find the first greater element to its right in `nums2`. If it does not exist, output -1.

```
Input:  nums1 = [4, 1, 2], nums2 = [1, 3, 4, 2]
Output: [-1, 3, -1]

Input:  nums1 = [2, 4], nums2 = [1, 2, 3, 4]
Output: [3, -1]
```

### Pattern Recognition
Monotonically decreasing stack on `nums2` to compute NGE for all elements, then HashMap lookup for `nums1` elements — separates the O(n) NGE computation from the O(m) answer retrieval.

### Key Insight
The NGE for every element in `nums2` can be computed in one pass and stored in a HashMap. Since `nums2` contains distinct elements, a value-keyed HashMap works without index ambiguity. Each element of `nums1` then gets its answer in O(1) via the HashMap — decoupling the monotonic stack work (done once over `nums2`) from the per-query answering (done once over `nums1`).

### Approach
Pass 1 (monotonic stack over `nums2`): for each element `num`, pop all stack elements smaller than `num` and record `{popped_element → num}` in the HashMap. Push `num`. After the pass, remaining stack elements map to -1. Pass 2 (answer lookup): for each element in `nums1`, return `ngeMap.get(element)`.

### Solution

```js
function nextGreaterElement(nums1, nums2) {
  const ngeMap = new Map(); // element value → its NGE in nums2
  const stack = [];         // monotonically decreasing stack (stores values)

  for (const num of nums2) {
    // Pop all elements smaller than num — num is their NGE
    while (stack.length > 0 && stack[stack.length - 1] < num) {
      ngeMap.set(stack.pop(), num);
    }
    stack.push(num);
  }

  // Remaining elements in stack have no NGE
  while (stack.length > 0) {
    ngeMap.set(stack.pop(), -1);
  }

  // Answer each query in O(1)
  return nums1.map(n => ngeMap.get(n));
}
```

### Dry Run

```
nums1 = [4, 1, 2], nums2 = [1, 3, 4, 2]

--- Process nums2 with monotonic stack ---

num=1: stack=[] → no pops. Push 1. stack=[1].
num=3: stack=[1]. 1 < 3 → pop 1, ngeMap={1→3}. stack=[]. Push 3. stack=[3].
num=4: stack=[3]. 3 < 4 → pop 3, ngeMap={1→3, 3→4}. stack=[]. Push 4. stack=[4].
num=2: stack=[4]. 4 < 2? No. Push 2. stack=[4, 2].

End of nums2. Drain remaining:
  pop 2 → ngeMap={..., 2→-1}
  pop 4 → ngeMap={..., 4→-1}

ngeMap = {1→3, 3→4, 2→-1, 4→-1}

--- Answer nums1 queries ---
nums1[0]=4 → ngeMap.get(4) = -1
nums1[1]=1 → ngeMap.get(1) = 3
nums1[2]=2 → ngeMap.get(2) = -1

```

### Complexity
- Time: O(n + m) — one pass over `nums2` (length n) for the stack, one pass over `nums1` (length m) for lookups. Each element in `nums2` is pushed and popped at most once.
- Space: O(n) — HashMap stores one entry per element of `nums2`; stack holds at most n elements simultaneously.

### Edge Cases
- Element in `nums1` is the global maximum of `nums2`: it's never popped during the stack pass (nothing larger arrives); drained at the end with -1. Correct.
- `nums1` has one element: one HashMap lookup after the full stack pass — O(n) total, O(1) for the lookup itself.
- `nums2` is strictly decreasing: no element is ever popped during the pass (each new element is smaller than the stack top). All elements are drained at the end with -1. Stack reaches maximum size n.
- `nums2` is strictly increasing: every push pops all previous elements. Each element's NGE is the next element. Stack is always size ≤ 1.

### Follow-up Questions
- "What if `nums2` can have duplicates?" → Store indices in the stack instead of values; the HashMap keys become indices rather than values; answer lookup for `nums1` uses `value → [list of indices]` and returns the appropriate index's NGE.
- "What if you need the NGE index, not the NGE value?" → Store indices in the stack from the start: `ngeMap.set(stack.pop(), i)` where `i` is the current index. The HashMap maps element index to NGE index.

## Problem 2 — Daily Temperatures

### Problem
Given an array `temperatures`, for each day find the number of days you have to wait until a warmer temperature. If no future day has a warmer temperature, output 0 for that day.

```
Input:  temperatures = [73, 74, 75, 71, 69, 72, 76, 73]
Output: [1, 1, 4, 2, 1, 1, 0, 0]

Explanation:
  Day 0 (73°): day 1 is warmer (74°) → wait 1 day
  Day 2 (75°): next warmer is day 6 (76°) → wait 4 days
  Day 6 (76°): no warmer day → 0
```

### Pattern Recognition
Monotonically decreasing stack storing indices — the "next greater element" problem rephrased as "how far away is the next greater element," requiring index arithmetic (`i - stack.top()`) at each pop event.

### Key Insight
The number of days to wait is the *distance* to the NGE, not the NGE value itself. Storing indices (not temperatures) in the stack enables computing `i - stack.top()` directly at each pop — the gap between the current day and the day still waiting for a warmer temperature. This is why index storage is almost always preferable to value storage: the value is always available via `temperatures[stack.top()]`, but the position is only available if indices are stored.

### Approach
Maintain a decreasing-temperature stack (storing indices). For each day `i`: while the stack top's temperature < `temperatures[i]`, pop the index `j` and set `result[j] = i - j`. Push `i`. After the loop, remaining stack elements (no warmer day found) stay at 0.

### Solution

```js
function dailyTemperatures(temperatures) {
  const n = temperatures.length;
  const result = new Array(n).fill(0); // default 0: no warmer day
  const stack = [];                    // stores indices; decreasing temperature order

  for (let i = 0; i < n; i++) {
    // Pop all days cooler than today — today is their "next warmer day"
    while (stack.length > 0 && temperatures[stack[stack.length - 1]] < temperatures[i]) {
      const j = stack.pop();
      result[j] = i - j; // days waited = distance from j to i
    }
    stack.push(i);
  }

  // Remaining elements stay 0 (initialized above) — no warmer day found
  return result;
}
```

```
i=2 (75°): temp[1]=74 < 75 → pop 1, result[1]=2-1=1. stack=[]. Push 2. stack=[2].
i=3 (71°): temp[2]=75 < 71? No. Push 3. stack=[2,3].
i=4 (69°): temp[3]=71 < 69? No. Push 4. stack=[2,3,4].
```

### Complexity
- Time: O(n) — each index pushed once and popped at most once; total push+pop operations = 2n.
- Space: O(n) — stack holds at most n indices in the worst case (strictly decreasing temperature array).

### Edge Cases
- Strictly increasing temperatures: every element is popped immediately by the next (each day's result = 1). Stack is always size ≤ 1 at any point.
- Strictly decreasing temperatures: nothing is ever popped during the loop. Stack grows to size n. All results stay 0. Correct: no day has a warmer future day.
- All temperatures equal: nothing is popped (using strict `<`). All results stay 0. Correct: no day is strictly warmer.
- Single element: stack ends with one element; result stays [0].

### Follow-up Questions
- "What if 'warmer' means ≥ instead of strictly >?" → Change `<` to `<=` in the pop condition. Equal-temperature days now satisfy the condition — an equal-temperature day is "at least as warm."
- "Return the actual temperature instead of the number of days?" → Change `result[j] = i - j` to `result[j] = temperatures[i]` — the value at the current index is the NGE value for the popped index.
- "Solve in O(1) space?" → Not possible with this approach (requires O(n) output array). If the question means O(1) extra space beyond the output array, the stack still requires O(n) worst-case space — no known O(1)-extra-space solution exists for this problem in general.

## Problem 3 — Online Stock Span

### Problem
Design a class `StockSpanner` that collects daily stock prices and returns the span of the stock's price for the current day. The span is defined as the maximum number of consecutive days (including today) for which the stock price was less than or equal to today's price.

```
Input:  [100, 80, 60, 70, 60, 75, 85]
Output: [1,   1,  1,  2,  1,  4,  6]

StockSpanner s;
s.next(100) → 1
s.next(80)  → 1
s.next(60)  → 1
s.next(70)  → 2
s.next(60)  → 1
s.next(75)  → 4
s.next(85)  → 6
```

### Pattern Recognition
Online monotonic stack with accumulated span storage — the streaming variant of the stock span problem where absolute indices are unavailable, so each stack entry stores `[price, accumulated_span]` instead of an index. Popped entries contribute their spans to the running total.

### Key Insight
In the offline version, span = `i - previousGreaterIndex`. In the online version, there are no indices — but the same information is available as *accumulated spans*. Each stack entry's span represents "how many consecutive days ending here have prices ≤ this price." When an entry is popped (its price ≤ today's price), its span is added to today's span accumulator — collapsing those days into today's span in O(1) per pop event.

### Approach
The stack stores `[price, span]` pairs. For each new price: initialize `span = 1`. Pop all stack entries with `price ≤ today's price`, adding each entry's span to `span`. Push `[today's price, span]`. Return `span`.

### Solution

```js
class StockSpanner {
  constructor() {
    // Stack of [price, span] pairs
    // Maintains non-increasing price order (bottom → top: prices decrease or stay equal)
    this.stack = [];
  }

  next(price) {
    let span = 1; // today always counts

    // Pop all entries with price ≤ today's price and accumulate their spans
    while (this.stack.length > 0 && this.stack[this.stack.length - 1][0] <= price) {
      span += this.stack.pop()[1]; // add the dominated period's span
    }

    // Push today's consolidated entry
    this.stack.push([price, span]);

    return span;
  }
}
```

### Dry Run

```

next(100): span=1. stack=[]. No pops. Push [100,1]. stack=[[100,1]]. return 1.

next(80):  span=1. top=[100,1]: 100 ≤ 80? No. Push [80,1]. stack=[[100,1],[80,1]]. return 1.

next(60):  span=1. top=[80,1]: 80 ≤ 60? No. Push [60,1]. stack=[[100,1],[80,1],[60,1]]. return 1.

next(70):  span=1. top=[60,1]: 60 ≤ 70? Yes → pop, span+=1=2.
                   top=[80,1]: 80 ≤ 70? No.
           Push [70,2]. stack=[[100,1],[80,1],[70,2]]. return 2.

next(60):  span=1. top=[70,2]: 70 ≤ 60? No. Push [60,1].
           stack=[[100,1],[80,1],[70,2],[60,1]]. return 1.

next(75):  span=1. top=[60,1]: 60 ≤ 75? Yes → pop, span+=1=2.
                   top=[70,2]: 70 ≤ 75? Yes → pop, span+=2=4.
                   top=[80,1]: 80 ≤ 75? No.
           Push [75,4]. stack=[[100,1],[80,1],[75,4]]. return 4.

next(85):  span=1. top=[75,4]: 75 ≤ 85? Yes → pop, span+=4=5.
                   top=[80,1]: 80 ≤ 85? Yes → pop, span+=1=6.
                   top=[100,1]: 100 ≤ 85? No.
           Push [85,6]. stack=[[100,1],[85,6]]. return 6.

Output: [1, 1, 1, 2, 1, 4, 6] ✓
```

### Complexity
- Time: O(1) amortized per `next()` call — each entry is pushed once and popped at most once across all calls. Total push+pop operations across n calls = 2n, giving O(1) amortized per call.
- Space: O(n) — the stack can hold up to n entries in the worst case (strictly decreasing price sequence where nothing is ever popped).

### Edge Cases
- Strictly increasing prices: every new price pops all previous entries and accumulates their spans. Stack always has exactly 1 entry (today's entry with the total accumulated span). Spans = [1, 2, 3, ..., n].
- Strictly decreasing prices: nothing is ever popped. Stack grows by one entry per call. Each span = 1.
- All prices equal: every new price pops all previous entries (≤ comparison). Spans = [1, 2, 3, ..., n].
- Single `next()` call: span = 1, stack has one entry.

### Follow-up Questions
- "What if the span should only count days with prices strictly less than today?" → Change `<=` to `<` in the pop condition. Equal-price days are no longer included — the non-strict boundary is excluded.
- "Support a `reset()` method?" → Add `this.stack = []` to a `reset()` method — clears all accumulated state. The stack is the entire state of the algorithm.
- "What is the maximum possible stack size after n calls?" → n entries, achieved when prices are strictly decreasing. Each call adds one entry and pops none.

## Problem 4 — Largest Rectangle in Histogram

### Problem
Given an array `heights` representing the heights of bars in a histogram (each bar has width 1), find the area of the largest rectangle that can be formed within the histogram.

```
Input:  heights = [2, 1, 5, 6, 2, 3]
Output: 10

Input:  heights = [2, 4]
Output: 4
```

### Pattern Recognition
Monotonically increasing stack with dual-direction NSE/PSE delivery — the pop event simultaneously delivers the Next Smaller Element (the current element, triggering the pop) and the Previous Smaller Element (the new stack top after popping), enabling O(1) width computation for each popped bar.

### Key Insight
For each bar `j`, the largest rectangle with height `heights[j]` extends left until the first bar shorter than `heights[j]` (PSE) and right until the first bar shorter than `heights[j]` (NSE). The width is `NSE_index - PSE_index - 1`. A single left-to-right pass with an increasing stack delivers both NSE (the incoming element that triggers the pop) and PSE (the stack top after popping) simultaneously at each pop event — no second pass needed.

### Approach
Process bars left to right. Maintain an increasing-height stack (stores indices). For each index `i`: while `heights[stack.top()] > heights[i]` (or `heights[i]` is the sentinel 0): pop index `j`; height = `heights[j]`; PSE = new stack top (or -1 if stack empty); NSE = `i`; width = `i - PSE - 1`; update `maxArea`. Push `i`. Append a sentinel height of 0 at the end (or handle in the loop with `i = n`) to force all remaining bars to be popped and processed.

### Solution

```js
function largestRectangleArea(heights) {
  const n = heights.length;
  const stack = []; // increasing-height stack; stores indices
  let maxArea = 0;

  // Iterate n+1 times: index n uses height 0 as a sentinel to flush the stack
  for (let i = 0; i <= n; i++) {
    const h = i === n ? 0 : heights[i]; // sentinel forces remaining pops

    // Pop bars taller than h — h is their NSE (next smaller element)
    while (stack.length > 0 && heights[stack[stack.length - 1]] > h) {
      const j = stack.pop();             // j is the bar being processed
      const height = heights[j];         // height of rectangle = heights[j]
      // PSE index = new stack top (or -1 if stack empty → extends to left edge)
      const pse = stack.length === 0 ? -1 : stack[stack.length - 1];
      const width = i - pse - 1;         // extends from pse+1 to i-1, inclusive
      maxArea = Math.max(maxArea, height * width);
    }

    stack.push(i);
  }

  return maxArea;
}
```

### Dry Run

```

indices:    0  1  2  3  4  5

stack=[], maxArea=0

i=0 (h=2): stack=[] → no pops. Push 0. stack=[0].
i=1 (h=1): heights[0]=2 > 1 → pop 0.
              height=2, pse=-1 (empty), NSE=i=1, width=1-(-1)-1=1. area=2×1=2. maxArea=2.
           stack=[]. Push 1. stack=[1].
i=2 (h=5): heights[1]=1 < 5 → no pop. Push 2. stack=[1,2].
i=3 (h=6): heights[2]=5 < 6 → no pop. Push 3. stack=[1,2,3].
i=4 (h=2): heights[3]=6 > 2 → pop 3.
              height=6, pse=stack.top()=2, NSE=4, width=4-2-1=1. area=6×1=6. maxArea=6.
            heights[2]=5 > 2 → pop 2.
              height=5, pse=stack.top()=1, NSE=4, width=4-1-1=2. area=5×2=10. maxArea=10.
            heights[1]=1 > 2? No. Push 4. stack=[1,4].
i=5 (h=3): heights[4]=2 < 3 → no pop. Push 5. stack=[1,4,5].
i=6 (sentinel h=0):
            heights[5]=3 > 0 → pop 5.
              height=3, pse=stack.top()=4, NSE=6, width=6-4-1=1. area=3×1=3. maxArea=10.
            heights[4]=2 > 0 → pop 4.
```

### Complexity
- Time: O(n) — each index pushed once, popped at most once; total work = O(n) despite the nested while loop (amortized analysis).
- Space: O(n) — stack holds at most n+1 indices.

### Edge Cases
- Single bar: stack ends with one index before sentinel; sentinel pops it; width = `1 - (-1) - 1 = 1`. area = `heights[0] × 1`. Correct.
- All equal heights: every bar stays on the stack until the sentinel. Sentinel pops all of them one by one. Each popped bar has pse = previous stack top; the last bar has pse = -1 and width = n. Correct: the largest rectangle spans the full width.
- Strictly increasing heights: no bar is ever popped during the main loop (each new bar is taller). All bars are popped by the sentinel. The last bar in the stack yields the smallest rectangle (width = n, height = min_height = heights[0] due to it being the bottom of the stack). The correct largest rectangle is computed among all popped entries.
- Heights with zeros: a bar of height 0 effectively resets — it forces all previous bars to be popped (it's their NSE), and nothing can form a rectangle "across" a zero-height bar. Handled naturally by the `>` condition (all bars > 0 are popped when 0 arrives).

### Follow-up Questions
- "Extend to 'maximal rectangle in a binary matrix'?" → For each row of the matrix, compute a histogram where `heights[j]` = number of consecutive 1s above and including row `i` in column `j`. Run the largest rectangle in histogram algorithm on each row's histogram. O(m × n) overall for an m×n matrix.
- "What if bars can have width > 1?" → Store `[height, width]` in the stack; when computing rectangle width, sum the widths of popped bars (contributing to the PSE-to-NSE span) rather than using index arithmetic.
- "Why is the sentinel value 0 specifically?" → The sentinel must be ≤ the minimum possible height so it triggers pops for all remaining bars. 0 works when heights ≥ 0. If heights can be negative, use -Infinity. The sentinel's index (`n`) ensures the width formula `i - pse - 1 = n - pse - 1` gives the correct span to the right edge of the array.

```
│       Pop condition: arr[stack.top()] < arr[i]
│       On pop: result[popped] = arr[i]  (or i - popped for distance)
│       Remaining stack → result = -1
│
├── PREVIOUS GREATER ELEMENT (first larger to the LEFT)?
│   └── Decreasing stack, left → right pass
│       Pop condition: arr[stack.top()] <= arr[i]  (pop before push)
│       On push: result[i] = arr[stack.top()] after pops  (or -1 if empty)
│
├── NEXT SMALLER ELEMENT (first smaller to the RIGHT)?
│   └── Increasing stack, left → right pass
│       Pop condition: arr[stack.top()] > arr[i]
│       On pop: result[popped] = arr[i]
│
├── PREVIOUS SMALLER ELEMENT (first smaller to the LEFT)?
│   └── Increasing stack, left → right pass
│       Pop condition: arr[stack.top()] >= arr[i]  (pop before push)
│       On push: result[i] = arr[stack.top()] after pops  (or -1 if empty)
│
├── STOCK SPAN (consecutive days with price ≤ today)?
│   └── Decreasing stack (non-strict), left → right pass
│       Pop condition: prices[stack.top()] <= prices[i]

│       Online variant: store [price, accumulated_span] pairs
│
├── LARGEST RECTANGLE IN HISTOGRAM?
│   └── Increasing stack, left → right pass, sentinel 0 at end

│               pse = new stack.top() (or -1);
│               width = i - pse - 1;
│               area = height × width
│
├── CIRCULAR ARRAY NGE?
│   └── Decreasing stack, iterate 2n times with idx = i % n
│       Only push when i < n (first pass only)
│       Second pass delivers remaining answers without adding candidates
│
├── EQUAL ELEMENTS — strict vs. non-strict?
│   ├── Answer requires STRICT inequality (NGE, NSE) → strict pop: < or >

│
└── NEED BOTH NSE AND PSE SIMULTANEOUSLY (histogram, subarray min/max sum)?
```

## Common Bugs Checklist

Before submitting any monotonic stack solution, verify:

1. **Storing indices, not values?** — Unless the problem guarantees unique elements and only asks for values (e.g., NGE variant 1 with distinct `nums2`), always store indices. Storing values loses positional information needed for span and distance calculations, and produces incorrect results for arrays with duplicate values.

2. **Correct pop condition: strict `<` / `>` vs. non-strict `<=` / `>=`?** — The pop condition directly encodes the problem's inequality. "Next strictly greater" → pop on `<` (equal elements stay). "Stock span with equal prices counting" → pop on `<=` (equal elements are dominated). Flipping strict vs. non-strict produces wrong results for arrays with duplicates — always derive the condition from the problem statement's exact inequality, not from intuition.

3. **Stack initialized with indices OR values, consistently?** — If you switch between storing indices and values partway through (e.g., pushing an index but comparing `arr[i] < arr[stack.top()]` then popping and assigning `result[stack.pop()] = arr[i]`), ensure the stack always holds the same type. Mixed storage is the most common implementation bug.

4. **Sentinel value added (or loop runs to `n`) for histogram/range problems?** — The largest rectangle problem requires all bars to be popped and processed. Without a sentinel, bars remaining in the stack after the loop are silently ignored — the maximum area may be missed. Either append a `0` to heights or use `i <= n` with `h = i === n ? 0 : heights[i]`.

5. **Remaining stack elements handled after the main loop?** — For NGE/NSE problems, elements left in the stack after the full pass have no answer — they must be assigned the sentinel value (-1 or 0). Forgetting this leaves them at the uninitialized default, which may happen to be 0 (correct for some problems) but is semantically wrong and produces bugs in problems where 0 is a valid answer.

6. **Circular array: only pushing during the first `n` iterations?** — When iterating `2n` times for circular NGE, pushing during the second `n` iterations adds duplicate entries to the stack. These duplicates create spurious pop events and wrong results. Gate the push with `if (i < n) stack.push(i % n)`.

7. **Width formula for histogram is `i - pse - 1`, not `i - pse`?** — The PSE index is exclusive (the PSE bar itself is shorter and not part of the rectangle). The rectangle spans from index `pse + 1` to index `i - 1`, giving width `(i - 1) - (pse + 1) + 1 = i - pse - 1`. Using `i - pse` includes the PSE bar in the width, overcounting by 1.

8. **Online stock span: accumulating popped spans, not counting pops?** — In the streaming `StockSpanner`, `span += this.stack.pop()[1]` (accumulate the popped entry's span) is correct. `span++` per pop (count pops) is wrong — it counts only the "representative" entries in the stack, missing all the days those entries had themselves absorbed from earlier pops.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to recognize a monotonic stack problem from two signals before writing any code: (1) the problem asks for the "nearest" element in one direction satisfying a comparison — not "any" or "all" but specifically the *nearest*; and (2) a brute-force O(n²) solution exists that scans left or right for each element. Stating both signals, then explaining in one sentence why the stack works — "elements popped from the stack have found their answer and can never be the answer for any future element, so discarding them is safe" — is the complete justification for the O(n) complexity. Everything else (which direction to traverse, strict vs. non-strict, index vs. value storage, sentinel for histogram) follows mechanically from reading the problem's inequality carefully and matching it to the pop condition.
