# DSA: DP on Strings — Wildcard Matching & Regex Matching — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What distinguishes wildcard matching and regex matching from simpler string problems, and why does DP apply to both?**
A: Both problems involve matching a string `s` against a **pattern `p`** that contains special characters capable of matching variable-length portions of the input — this variability means you can't decide locally at any one position whether a match succeeds or fails without knowing what choices were made at adjacent positions. This creates **overlapping subproblems**: the answer to "does `s[i:]` match `p[j:]`?" depends on answers to related smaller subproblems, many of which are reused in multiple contexts. DP solves this by computing and caching the answer to every subproblem `(i, j)` — "can the first `i` characters of `s` be matched by the first `j` characters of `p`?" — exactly once, combining those answers into a full solution without redundant recomputation.

**Q2. What are the two types of special characters in the two problems, and how do they differ fundamentally?**
A: The key distinction between the two patterns:
- **Wildcard matching** uses two special characters: `?` matches **exactly one** arbitrary character; `*` matches **any sequence of characters, including the empty sequence**. Every character in the pattern (including `*` and `?`) occupies its own position independently.
- **Regex matching** uses two special characters: `.` matches **exactly one** arbitrary character; `*` is a **quantifier** that must follow a preceding character or `.`, and together the pair (e.g., `a*` or `.*`) matches **zero or more** occurrences of that preceding element. The key difference: in regex, `*` is not a standalone character — it is always bound to the character immediately before it, modifying how many times that character can repeat.

```
Wildcard:  pattern "a*b"   means 'a', then any sequence, then 'b'
           matches "ab", "axyzb", "a___b" but NOT "b" (requires 'a' and 'b')
           
Regex:     pattern "a*b"   means zero-or-more 'a's, then 'b'
           matches "b", "ab", "aab", "aaab" but NOT "axb" (a* only repeats 'a')
```

**Q3. What is the state definition for both problems, and why is `(i, j)` a natural 2D state?**
A: For both problems, define `dp[i][j]` as: **can the first `i` characters of `s` be fully matched by the first `j` characters of `p`?** (boolean). This is a natural 2D state because the match progress in `s` (captured by `i`) and the pattern consumption in `p` (captured by `j`) are independent dimensions that jointly determine the subproblem — you can't determine the answer from just `i` alone (doesn't know pattern progress) or just `j` alone (doesn't know how much of the string has been consumed). The answer to the original problem is `dp[m][n]` where `m = s.length` and `n = p.length`.

**Q4. What do the base cases represent, and why are they the same for both problems?**
A: `dp[0][0] = true` — an empty string is matched by an empty pattern (trivially). `dp[i][0] = false` for `i > 0` — a non-empty string cannot be matched by an empty pattern. The third base case differs between the two problems:
- **Wildcard**: `dp[0][j]` = whether the first `j` characters of the pattern, consisting solely of `*`s so far, can match an empty string. A `*` in wildcard matching matches the empty string, so a run of `*`s at the start of the pattern can still match an empty string: `dp[0][j] = dp[0][j-1] && p[j-1] === '*'`.
- **Regex**: `dp[0][j]` = whether the first `j` characters of the pattern can match an empty string via `x*` pairs. Only even-position characters that are `*` (paired with the character before them) contribute: `dp[0][j] = j >= 2 && p[j-1] === '*' && dp[0][j-2]`.

### Section 2: Wildcard Matching — Deep Dive

**Q5. What is the full recurrence for wildcard matching?**
A: Three cases, based on the current pattern character `p[j-1]` (using 1-indexed DP with `i` characters of `s` and `j` characters of `p` already considered):

1. **`p[j-1] === '*'`**: The `*` can match zero characters (skip it: `dp[i][j-1]`) or one-or-more characters (extend its match by one more character of `s`: `dp[i-1][j]`). So: `dp[i][j] = dp[i][j-1] || dp[i-1][j]`.
2. **`p[j-1] === '?'`**: Matches exactly one character of `s` (whatever it is). So: `dp[i][j] = dp[i-1][j-1]`.
3. **`p[j-1]` is a literal character**: Must match exactly `s[i-1]`. So: `dp[i][j] = (s[i-1] === p[j-1]) && dp[i-1][j-1]`.

```js
function isMatch(s, p) {
  const m = s.length, n = p.length;
  const dp = Array.from({ length: m + 1 }, () => new Array(n + 1).fill(false));

  dp[0][0] = true;

  // base case: empty string matched by leading stars
  for (let j = 1; j <= n; j++) {
    dp[0][j] = dp[0][j - 1] && p[j - 1] === '*';
  }

  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (p[j - 1] === '*') {
        dp[i][j] = dp[i][j - 1] || dp[i - 1][j]; // skip * OR extend *
      } else if (p[j - 1] === '?' || s[i - 1] === p[j - 1]) {
        dp[i][j] = dp[i - 1][j - 1]; // single-char match
      }
      // else dp[i][j] remains false (literal mismatch)
    }
  }

  return dp[m][n];
}
```

**Q6. What is the intuition behind the wildcard `*` recurrence `dp[i][j] = dp[i][j-1] || dp[i-1][j]`?**
A: A `*` in wildcard matching can match **any sequence of characters including the empty sequence**. This creates two choices: (a) the `*` matches nothing — the `i` characters of `s` must be matchable by just the first `j-1` characters of `p` (i.e., `dp[i][j-1]`); (b) the `*` matches at least one character — the first `i-1` characters of `s` must have been matchable by the same `j` characters of `p` (i.e., `dp[i-1][j]`), because if the `*` could "absorb" `i-1` characters of `s`, it can absorb one more character of `s` now. The `dp[i-1][j]` case effectively says "this same `*` is responsible for character `s[i-1]` too — everything before this character was already handled by the first `j` pattern characters including this `*`." This is the "greedy extension" of the `*`'s match without consuming the `*` from the pattern perspective.

**Q7. Why does the wildcard `*` consume characters from `s` using `dp[i-1][j]` (same `j`) rather than advancing `j`?**
A: The `*` in wildcard matching can absorb **multiple** characters of `s` without ever "moving past" the `*` in the pattern — the `*` stays in position `j` while multiple characters of `s` can be consumed one by one. Each individual character `s[i-1]` can be "claimed" by the `*` by checking that `dp[i-1][j]` was true (the `*` at position `j` was already handling everything up through `s[i-2]`). Advancing `j` (to `dp[i-1][j+1]`) would incorrectly move past the `*`, forbidding it from absorbing further characters of `s`. The `j` stays put while `i` decreases — this is why `dp[i-1][j]` (not `dp[i-1][j-1]`) is the "extend the `*`'s match" case.

### Section 3: Regex Matching — Deep Dive

**Q8. What is the full recurrence for regex matching?**
A: Two cases, based on the current pattern character:

1. **`p[j-1] === '*'`**: The `*` is always paired with its preceding character `p[j-2]`. Two sub-choices: (a) use the `x*` pair to match **zero occurrences** of `x` (skip the entire `x*` pair: `dp[i][j-2]`); (b) use the `x*` pair to match **one more occurrence** of `x`, if `s[i-1]` matches `p[j-2]` (either literally or via `.`): `dp[i-1][j] && (s[i-1] === p[j-2] || p[j-2] === '.')`.

2. **`p[j-1] !== '*'`**: Regular character or `.`. Matches exactly one character: `dp[i][j] = dp[i-1][j-1] && (s[i-1] === p[j-1] || p[j-1] === '.')`.

```js
function isMatchRegex(s, p) {
  const m = s.length, n = p.length;
  const dp = Array.from({ length: m + 1 }, () => new Array(n + 1).fill(false));

  dp[0][0] = true;

  // base case: empty string matched by x* patterns (zero occurrences of x)
  for (let j = 2; j <= n; j++) {
    dp[0][j] = p[j - 1] === '*' && dp[0][j - 2];
  }

  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (p[j - 1] === '*') {
        // zero occurrences of p[j-2]: skip the x* pair entirely
        const zeroOccurrence = dp[i][j - 2];
        // one more occurrence: s[i-1] matches the preceding char p[j-2]
        const oneMoreOccurrence = (s[i - 1] === p[j - 2] || p[j - 2] === '.')
          ? dp[i - 1][j]
          : false;
        dp[i][j] = zeroOccurrence || oneMoreOccurrence;
      } else {
        dp[i][j] = dp[i - 1][j - 1] && (s[i - 1] === p[j - 1] || p[j - 1] === '.');
      }
    }
  }

  return dp[m][n];
}
```

**Q9. Why does the regex `*` base case only start at `j = 2` and use `dp[0][j-2]`, while the wildcard `*` base case starts at `j = 1`?**
A: In regex, `*` cannot appear as the very first character — it's always a **quantifier paired with a preceding element** (e.g., `a*`, `.*`). The smallest valid unit is two characters: a character followed by `*`. So the first `j` at which an empty string could match is `j = 2` (the pattern `a*` meaning zero `a`s). `dp[0][j-2]` asks: can the empty string be matched by the pattern excluding the current `x*` pair? If yes, then adding `x*` (meaning zero `x`s) still matches the empty string. For wildcard, a single `*` at any position can match the empty string on its own, which is why `dp[0][j] = dp[0][j-1] && p[j-1] === '*'` works with just `j-1` lookback.

**Q10. What is the key structural difference between how `*` behaves in wildcard vs. regex matching, and how does this manifest in the recurrence?**
A: This is the most important conceptual distinction:
- **Wildcard `*`**: A standalone meta-character. It is consumed in the pattern as its own entity. To "extend" its match over one more character of `s`, you look at `dp[i-1][j]` — same `j` because the `*` is still "in play" as the same pattern character.
- **Regex `*`**: A quantifier bound to the preceding element. The pair `p[j-2]p[j-1]` (e.g., `a*`) acts as a combined unit. To "extend" its match, you look at `dp[i-1][j]` — same `j` because the `x*` unit as a whole is still "in play." But skipping it (zero occurrences) requires jumping back **two** positions (`dp[i][j-2]`) because you must skip both the `*` and its preceding character as a pair.

The recurrence's `dp[i-1][j]` for "extend" looks the same in both, but `dp[i][j-1]` (wildcard skip) versus `dp[i][j-2]` (regex skip) captures the fundamental difference: wildcard `*` is one pattern character; regex `x*` is two.

### Section 4: Comparison & Advanced Patterns

**Q11. What is the comparison table between wildcard and regex matching?**
A:

| Property | Wildcard Matching | Regex Matching |
|---|---|---|
| `*` meaning | Match any sequence (standalone) | Match 0+ of preceding char (quantifier) |
| `.` / `?` | `?` matches exactly 1 char | `.` matches exactly 1 char |
| `*` base case | `dp[0][j] = dp[0][j-1] && p[j-1]==='*'` | `dp[0][j] = p[j-1]==='*' && dp[0][j-2]` |
| `*` skip (0 match) | `dp[i][j-1]` (skip 1 char in pattern) | `dp[i][j-2]` (skip 2 chars: x and *) |
| `*` extend (1+ match) | `dp[i-1][j]` (consume 1 char of s) | `dp[i-1][j]` if `s[i-1]` matches `p[j-2]` |
| Pattern validity constraint | `*` can appear anywhere | `*` must follow a non-`*` character |

**Q12. Why can both problems be solved top-down with memoization as an alternative to bottom-up DP, and which is generally preferred?**
A: Both have the same overlapping-subproblems structure — a recursive function `match(i, j)` that calls `match(i-1, j-1)`, `match(i, j-1)`, `match(i-1, j)` etc. — and memoizing these recursive calls avoids redundant recomputation. Top-down (memoization) is sometimes preferred when:
- The state space is large but only a small fraction of `(i,j)` pairs are ever reachable from the root call (sparse reachability, so many cells are never computed).
- The recursive structure makes the logic more natural to express (some find the conditional branching cleaner in recursive form).

Bottom-up (tabulation) is generally preferred for these problems because:
- It avoids recursion-stack overhead (can process very long strings without stack overflow).
- The fill order is simple and predictable (top-to-bottom, left-to-right).
- Space optimization (rolling rows) is easier to apply to an explicit loop than to memoized recursion.

**Q13. How does the space optimization (O(n) rolling row) apply to these problems?**
A: Both problems' recurrences access only the current row and the previous row of the DP table — specifically `dp[i][j]` depends on `dp[i-1][j-1]`, `dp[i-1][j]`, and `dp[i][j-1]` (or `dp[i][j-2]` for regex). This is the same structure as Edit Distance, and the same rolling-row technique applies: use a single 1D boolean array, updated left-to-right, saving the "diagonal" value in a `prev` variable before overwriting. This reduces space from O(m × n) to O(n).

```js
function isMatchOptimized(s, p) {
  const m = s.length, n = p.length;
  let dp = new Array(n + 1).fill(false);
  dp[0] = true;

  // base case for empty string
  for (let j = 1; j <= n; j++) {
    dp[j] = p[j - 1] === '*' && dp[j - 1]; // wildcard version
  }

  for (let i = 1; i <= m; i++) {
    let prev = dp[0]; // save dp[i-1][0] before overwriting
    dp[0] = false;    // dp[i][0] = false for all i > 0

    for (let j = 1; j <= n; j++) {
      const temp = dp[j]; // save dp[i-1][j] before overwriting
      if (p[j - 1] === '*') {
        dp[j] = dp[j - 1] || dp[j]; // dp[i][j-1] || dp[i-1][j]
      } else if (p[j - 1] === '?' || s[i - 1] === p[j - 1]) {
        dp[j] = prev; // dp[i-1][j-1]
      } else {
        dp[j] = false;
      }
      prev = temp;
    }
  }

  return dp[n];
}
```

**Q14. What makes these matching problems particularly tricky to implement correctly under interview pressure, beyond just recalling the recurrence?**
A: Several interconnected subtleties:
1. **Off-by-one in indexing**: the DP table is `(m+1) × (n+1)` with 1-indexing, so `dp[i][j]` uses `s[i-1]` and `p[j-1]` — consistently applying this 1-index offset (and not accidentally using 0-indexed access) is the #1 implementation bug.
2. **Regex `*` lookback by 2**: the skip case is `dp[i][j-2]`, not `dp[i][j-1]` — using `j-1` silently applies wildcard semantics instead of regex semantics.
3. **Regex `*` extend condition**: the extend case must BOTH check that `dp[i-1][j]` is true AND that `s[i-1]` matches `p[j-2]` (the character before `*`) — either condition alone is insufficient.
4. **Wildcard base case**: `dp[0][j]` must be `dp[0][j-1] && p[j-1] === '*'` — a non-star character in the pattern correctly breaks the run and sets all subsequent `dp[0][j]` to false, even if later characters are stars.
5. **Regex base case starts at `j = 2`**: writing the base case loop starting from `j = 1` risks accessing `p[j-2]` = `p[-1]` when `j = 1`, an out-of-bounds access that silently corrupts results in some languages.

### Section 5: Greedy / Non-DP Alternatives

**Q15. Is there a greedy approach to wildcard matching, and when does it work?**
A: Yes — there is a linear-time O(m + n), O(1)-space greedy approach for wildcard matching (not applicable to regex matching's more complex `x*` semantics). The algorithm tracks two pointers into `s` and `p`, plus a "star index" and a "match index" to record the last seen `*` and `s`'s position when that `*` was encountered. When a mismatch occurs, it backtracks to the last `*`, advances the `match` pointer (letting the `*` consume one more character of `s`), and retries. This works for wildcard because the `*`'s semantics (absorb any sequence) are simple enough for a greedy retry-on-mismatch approach to be exhaustive. For regex, the combined `x*` semantics (must match zero or more of the specific preceding character) defeat simple greedy backtracking since the check involves both the `*` and what it quantifies.

```js
function isMatchGreedy(s, p) {
  let si = 0, pi = 0, starIdx = -1, matchIdx = 0;

  while (si < s.length) {
    if (pi < p.length && (p[pi] === '?' || p[pi] === s[si])) {
      si++; pi++; // matched one character
    } else if (pi < p.length && p[pi] === '*') {
      starIdx = pi; matchIdx = si; pi++; // record star, advance pattern
    } else if (starIdx !== -1) {
      pi = starIdx + 1; matchIdx++; si = matchIdx; // backtrack: star absorbs one more char
    } else {
      return false; // mismatch with no star to backtrack to
    }
  }

  while (pi < p.length && p[pi] === '*') pi++; // trailing stars match empty
  return pi === p.length;
}
```

**Q16. How does the greedy wildcard algorithm's correctness compare to DP — is one strictly better?**
A: The greedy algorithm is **O(m+n) time, O(1) space** versus DP's O(m×n) time and O(n) space (optimized), making it asymptotically faster. However: (1) the greedy algorithm is significantly harder to prove correct and harder to extend to variants (e.g., wildcard matching with different semantics, or with character classes); (2) the DP approach generalizes naturally to regex and many other string pattern matching problems; (3) in interviews, the DP solution is almost always the expected and accepted answer, since it directly demonstrates understanding of the overlapping-subproblems structure. The greedy approach is worth knowing as a follow-up optimization, but presenting the DP solution first and then mentioning the greedy as an improvement is the stronger interview approach.

### Section 6: Scenario / Interview-Style Questions

**Q17. "You see the pattern `.*` in a regex matching problem. What does it match, and how does the DP table encode this?"**
A: `.*` means "zero or more of any character" — effectively the same as wildcard's `*` (matches any sequence including empty). In the DP table, `p[j-1] = '*'` and `p[j-2] = '.'`: the zero-occurrence case gives `dp[i][j] = dp[i][j-2]` (skip the `.*` pair); the extend case checks `p[j-2] === '.'` (which is always true), so it simplifies to `dp[i-1][j]` whenever `dp[i-1][j]` is true. Combined: `dp[i][j] = dp[i][j-2] || dp[i-1][j]` — structurally identical to wildcard's `*` recurrence, but derived from the regex rules rather than hardcoded.

**Q18. "How would you test a wildcard matching implementation to catch the most common bugs?"**
A: Key test cases designed to expose specific bugs:
- `s="", p=""` → `true` (base case dp[0][0]).
- `s="abc", p="*"` → `true` (single wildcard `*` matches anything).
- `s="abc", p="a*"` → `true` (wildcard `*` matches "bc").
- `s="abc", p="a*c"` → `true` (wildcard `*` matches "b").
- `s="abc", p="a*d"` → `false` (wildcard `*` can't bridge the mismatch at 'd').
- `s="", p="***"` → `true` (all-stars match empty — base case propagation).
- `s="abc", p="?b?"` → `true` (two `?` each match one char).
- `s="a", p="??"` → `false` (two `?` require two chars, s has one).
- `s="abc", p="a*b*c"` → `true` (two `*`s, each matching empty).
- `s="aab", p="a*b"` → `true` (wildcard `*` matches second "a").

**Q19. "How would you test a regex matching implementation?"**
A: Key test cases targeting regex-specific semantics:
- `s="aa", p="a"` → `false` (pattern too short).
- `s="aa", p="a*"` → `true` (a* matches two a's).
- `s="aa", p=".*"` → `true` (.* matches anything).
- `s="aab", p="c*a*b"` → `true` (c* matches empty, a* matches "aa", then b).
- `s="", p="a*"` → `true` (a* can match zero a's — empty string).
- `s="", p="a*b*"` → `true` (both match zero occurrences).
- `s="mississippi", p="mis*is*p*."` → `false` (a classic hard case — the final `.` must match exactly one char but the `p*` before it leaves position tricky).
- `s="a", p="ab*"` → `true` (b* matches zero b's).
- `s="a", p=".*..a*"` → `false` (the `..` part requires two chars but only one remains after `.*`).

**Q20. "A colleague argues that since `.*` in regex behaves like `*` in wildcard, you can just implement wildcard matching and substitute `.*` for `*` in the pattern. Is this correct?"**
A: Partially — `.*` in regex does behave identically to `*` in wildcard (match zero or more of any character). However, regex patterns also use `a*` (zero or more `a`s specifically), `b*`, etc. — quantifiers that restrict what the `*` can repeat. In wildcard matching, there is no equivalent: a wildcard `*` always matches anything, never just a specific character. So while `.*` regex → wildcard `*` substitution works for the pure "match any sequence" case, any pattern using `x*` for a specific character `x` (not `.`) has no direct wildcard equivalent, and attempting this substitution would produce wrong results for those patterns. The two problems are genuinely different in their semantics and require distinct recurrences.

## Problem 1 — Wildcard Matching (Bottom-Up DP)

### Problem
Given a string `s` and a pattern `p` containing `?` (matches any single character) and `*` (matches any sequence of characters including empty), determine if `p` matches the entire string `s`.

```
Input:  s = "adceb", p = "*a*b"
Output: true   ('*' matches "", "a" matches 'a', '*' matches "dce", "b" matches 'b')

Input:  s = "acdcb", p = "a*c?b"
Output: false  ('?' must match exactly one char, but the string doesn't fit)
```

### Pattern Recognition
2D boolean DP over the lengths of `s` and `p` — the standard approach when `*` can match a variable-length portion of `s`, requiring tracking of both string position and pattern position simultaneously.

### Key Insight
A `*` in the pattern creates a choice at each step: either "this `*` matches nothing here — move on in the pattern" (`dp[i][j-1]`), or "this `*` absorbs the current character of `s` — stay on this `*`" (`dp[i-1][j]`). The `dp[i-1][j]` case is what allows `*` to absorb multiple characters by keeping `j` fixed while `i` increments.

### Approach
Build a `(m+1) × (n+1)` boolean table. `dp[0][0] = true`. First row: `dp[0][j] = dp[0][j-1] && p[j-1] === '*'` (leading stars can match empty). First column: `dp[i][0] = false` for `i > 0`. Fill the rest using the three-case recurrence.

### Solution

```js
function isMatch(s, p) {
  const m = s.length, n = p.length;
  // dp[i][j]: can the first i chars of s be matched by the first j chars of p?
  const dp = Array.from({ length: m + 1 }, () => new Array(n + 1).fill(false));

  dp[0][0] = true; // empty string matches empty pattern

  // base case: empty string can be matched by a run of leading '*'s
  for (let j = 1; j <= n; j++) {
    dp[0][j] = dp[0][j - 1] && p[j - 1] === '*';
  }

  // fill the table
  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (p[j - 1] === '*') {
        // case 1: '*' matches zero characters (skip it in the pattern)
        // case 2: '*' absorbs s[i-1] (stays at same j, consumes one more s char)
        dp[i][j] = dp[i][j - 1] || dp[i - 1][j];
      } else if (p[j - 1] === '?' || s[i - 1] === p[j - 1]) {
        // '?' or matching literal: consume one char from both s and p
        dp[i][j] = dp[i - 1][j - 1];
      }
      // else: literal mismatch — dp[i][j] stays false
    }
  }

  return dp[m][n];
}
```

```
  j=1 (p[0]='*'): dp[1][0] || dp[0][1] = F||T = T
  j=2 (p[1]='a'): s[0]='a'=p[1]='a' → dp[0][1] = T
  j=3 (p[2]='*'): dp[1][2] || dp[0][3] = T||F = T
  j=4 (p[3]='b'): s[0]='a'≠'b' → F
  dp[1] = [F, T, T, T, F]

i=2 (s[1]='d'):
  j=1 ('*'): dp[2][0]||dp[1][1] = F||T = T
  j=2 ('a'): 'd'≠'a' → F
  j=3 ('*'): dp[2][2]||dp[1][3] = F||T = T
  j=4 ('b'): 'd'≠'b' → F
  dp[2] = [F, T, F, T, F]

i=3 (s[2]='c'):
  j=1 ('*'): F||T = T
  j=2 ('a'): 'c'≠'a' → F
  j=3 ('*'): dp[3][2]||dp[2][3] = F||T = T
  j=4 ('b'): 'c'≠'b' → F
  dp[3] = [F, T, F, T, F]

i=4 (s[3]='e'):
  j=1 ('*'): F||T = T
  j=2 ('a'): 'e'≠'a' → F
  j=3 ('*'): dp[4][2]||dp[3][3] = F||T = T
  j=4 ('b'): 'e'≠'b' → F
  dp[4] = [F, T, F, T, F]

i=5 (s[4]='b'):
  j=1 ('*'): F||T = T
  j=2 ('a'): 'b'≠'a' → F
  j=3 ('*'): dp[5][2]||dp[4][3] = F||T = T
  j=4 ('b'): 'b'='b' → dp[4][3] = T
  dp[5] = [F, T, F, T, T]

Answer: dp[5][4] = true ✓
```

### Complexity
- Time: O(m × n) — fill every cell of the `(m+1) × (n+1)` table once.
- Space: O(m × n) for the full table; reducible to O(n) with rolling rows.

### Edge Cases
- `s = "", p = ""` → `dp[0][0] = true`.
- `s = "", p = "***"` → all `dp[0][j]` are `true` (base case propagation through stars).
- `s = "abc", p = "***"` → `dp[m][n] = true` (multiple stars can still match non-empty strings via the `dp[i-1][j]` path).
- `s = "abc", p = "a*"` → the `*` absorbs "bc"; `dp[3][2] = true`.
- `s = "abc", p = "??"` → needs exactly 2 chars; `s` has 3 → `dp[3][2] = false`.

### Follow-up Questions
- "Can you solve this in O(m+n) time instead of O(m×n)?" → See Q15 — the greedy two-pointer approach with star-index backtracking achieves O(m+n) time and O(1) space for wildcard matching specifically.
- "What changes for regex matching (using `a*` instead of standalone `*`)?" → See Problem 2 — the `*` becomes a quantifier over a preceding character, the skip becomes `dp[i][j-2]` not `dp[i][j-1]`, and the extend checks that `s[i-1]` specifically matches `p[j-2]`.

## Problem 2 — Regular Expression Matching (Bottom-Up DP)

### Problem
Given a string `s` and a pattern `p` containing `.` (matches any single character) and `*` (matches zero or more of the preceding element), determine if `p` matches the entire string `s`.

```
Input:  s = "aa", p = "a*"
Output: true   (a* matches two a's)

Input:  s = "ab", p = ".*"
Output: true   (.* matches any sequence)

Input:  s = "aab", p = "c*a*b"
Output: true   (c* matches "", a* matches "aa", b matches 'b')
```

### Pattern Recognition
2D boolean DP with a two-character quantifier pair — the `*` always pairs with its preceding character, making the recurrence fundamentally different from wildcard matching's standalone `*`.

### Key Insight
When `p[j-1] === '*'`, it governs the pair `p[j-2]p[j-1]`. Skipping the pair (zero occurrences) looks back **two** positions: `dp[i][j-2]`. Extending the pair's match looks at `dp[i-1][j]` only if `s[i-1]` specifically matches `p[j-2]` (the character the `*` quantifies). The base case must handle this two-character granularity by checking `dp[0][j-2]` (not `dp[0][j-1]`).

### Approach
Build `(m+1) × (n+1)` table. `dp[0][0] = true`. Base case for empty string: only `x*` pairs can match empty. Fill interior: branch on whether `p[j-1] === '*'` (two sub-cases) or not (one character match with `.` support).

### Solution

```js
function isMatch(s, p) {
  const m = s.length, n = p.length;
  const dp = Array.from({ length: m + 1 }, () => new Array(n + 1).fill(false));

  dp[0][0] = true;

  // base case: pattern of the form x*y*z*... can match empty string
  for (let j = 2; j <= n; j++) {
    // x* pair at position (j-1, j): skip it (0 occurrences) if dp[0][j-2] is true
    dp[0][j] = p[j - 1] === '*' && dp[0][j - 2];
  }

  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (p[j - 1] === '*') {
        // sub-case A: use x* for ZERO occurrences — skip the x* pair
        const zeroOccurrences = dp[i][j - 2];

        // sub-case B: use x* for ONE MORE occurrence — s[i-1] must match p[j-2]
        const charMatches = p[j - 2] === '.' || s[i - 1] === p[j - 2];
        const oneMoreOccurrence = charMatches ? dp[i - 1][j] : false;

        dp[i][j] = zeroOccurrences || oneMoreOccurrence;
      } else {
        // not a '*': single char match with literal or '.'
        dp[i][j] = dp[i - 1][j - 1] && (p[j - 1] === '.' || s[i - 1] === p[j - 1]);
      }
    }
  }

  return dp[m][n];
}
```

### Dry Run

```
s = "aab" (m=3), p = "c*a*b" (n=5)
p: c(0) *(1) a(2) *(3) b(4)  [0-indexed p chars]
Pattern interpretation: "c*" then "a*" then "b"

Base cases:
dp[0][0] = T
dp[0][1]: j=1, p[0]='c'≠'*' → F (j<2, loop starts at j=2)
dp[0][2]: p[1]='*', dp[0][0]=T → T  (c* matches empty)
dp[0][3]: p[2]='a'≠'*' → F
dp[0][4]: p[3]='*', dp[0][2]=T → T  (a* matches empty; c*a* matches empty)
dp[0][5]: p[4]='b'≠'*' → F
dp[0] = [T, F, T, F, T, F]

i=1, s[0]='a':
  j=1 (p[0]='c'): 'a'≠'c' → F
  j=2 (p[1]='*'): zero=dp[1][0]=F; p[0]='c', 'a'≠'c' so charMatches=F, one=F → F
  j=3 (p[2]='a'): 'a'='a' → dp[0][2]=T ✓
  j=4 (p[3]='*'): zero=dp[1][2]=F; p[2]='a', 'a'='a' so charMatches=T, one=dp[0][4]=T → T
  j=5 (p[4]='b'): 'a'≠'b' → F
  dp[1] = [F, F, F, T, T, F]

i=2, s[1]='a':
  j=1: 'a'≠'c' → F
  j=2 ('*'): zero=dp[2][0]=F; 'a'≠'c' → one=F → F
  j=3 ('a'): 'a'='a' → dp[1][2]=F
  j=4 ('*'): zero=dp[2][2]=F; p[2]='a', 'a'='a', one=dp[1][4]=T → T
  j=5 ('b'): 'a'≠'b' → F
  dp[2] = [F, F, F, F, T, F]

i=3, s[2]='b':
  j=1: 'b'≠'c' → F
  j=2 ('*'): zero=dp[3][0]=F; 'b'≠'c' → one=F → F
  j=3 ('a'): 'b'≠'a' → F
  j=4 ('*'): zero=dp[3][2]=F; p[2]='a', 'b'≠'a' → one=F → F
  j=5 ('b'): 'b'='b' → dp[2][4]=T ✓
  dp[3] = [F, F, F, F, F, T]

Answer: dp[3][5] = true ✓
(Interpretation: c* matched empty, a* matched "aa", b matched 'b')
```

### Complexity
- Time: O(m × n) — each cell computed once with O(1) work.
- Space: O(m × n), reducible to O(n) with rolling rows and a `prev` diagonal variable.

### Edge Cases
- `s = "", p = "a*b*c*"` → every pair matches zero occurrences; `dp[0]` propagates `true` through all even positions → `true`.
- `s = "a", p = "ab*"` → `b*` matches zero `b`s; `dp[1][3] = dp[1][1]` (skip "b*") and `dp[1][1] = true` (just 'a' matches 'a') → `true`.
- `s = "aaa", p = "a"` → only one 'a' in pattern, no `*` to extend → `dp[3][1]` uses `dp[2][0] = false` → `false`.
- `s = "", p = "a"` → `dp[0][1] = false` (non-star char can't match empty); `false`.
- Pattern beginning with `*` (invalid regex): the problem guarantees patterns are valid, so `*` never appears as the first character — but if it did, `dp[0][1]` for `p[0]='*'` would try to access `dp[0][-1]` (out of bounds); real implementations should validate or handle this.

### Follow-up Questions
- "How does this differ from the wildcard version?" → See Q10 and Q11 — in regex, `*` looks back two positions (`j-2`) to skip the pair; in wildcard, `*` looks back one position (`j-1`) to skip itself. The extend case additionally checks `s[i-1]` against `p[j-2]` in regex but not in wildcard.
- "Implement this recursively with memoization instead of bottom-up." → Same recurrence, different execution order — use `memo[i][j]` to cache results of `match(i, j)`, handle the base cases at `i === 0` or `j === 0` directly in the recursive function.

## Problem 3 — Wildcard Matching (Greedy Two-Pointer Approach)

### Problem
Same as Problem 1 — wildcard matching with `?` and `*` — but implement it in O(m+n) time and O(1) space using the greedy two-pointer technique instead of DP.

### Pattern Recognition
The greedy backtracking approach — specific to wildcard matching's simpler `*` semantics where `*` always matches any sequence (no character-specific restriction like regex's `a*`).

### Key Insight
When a mismatch occurs, "backtrack" to the most recent `*` and let it absorb one more character of `s`. Record the position of the last seen `*` (as `starIdx` in `p`) and the position in `s` when that `*` was recorded (as `matchIdx` in `s`). Any future mismatch reverts to `pi = starIdx + 1` and `si = ++matchIdx`, effectively advancing the `*`'s coverage by one more character of `s`.

### Approach
Two pointers `si` into `s` and `pi` into `p`. When characters match or `p[pi] === '?'`, advance both. When `p[pi] === '*'`, record `starIdx = pi` and `matchIdx = si`, advance only `pi`. On mismatch: if a star was seen, backtrack (`pi = starIdx + 1`, `si = ++matchIdx`). If no star, return `false`. After `s` is consumed, skip trailing `*`s in `p`. Valid iff `pi === n`.

### Solution

```js
function isMatchGreedy(s, p) {
  let si = 0, pi = 0;
  let starIdx = -1, matchIdx = 0;

  while (si < s.length) {
    if (pi < p.length && (p[pi] === '?' || p[pi] === s[si])) {
      // direct character match (literal or '?')
      si++;
      pi++;
    } else if (pi < p.length && p[pi] === '*') {
      // found a star: record its position and s's current position
      starIdx = pi;
      matchIdx = si;
      pi++; // advance pattern past the star (try matching zero chars first)
    } else if (starIdx !== -1) {
      // mismatch but we have a previous star to backtrack to
      // let the star absorb one more character of s
      pi = starIdx + 1;
      matchIdx++;
      si = matchIdx;
    } else {
      // mismatch with no star available — no match possible
      return false;
    }
  }

  // consume any trailing stars in the pattern (they all match empty)
  while (pi < p.length && p[pi] === '*') pi++;

  return pi === p.length;
}
```

### Dry Run

```
s = "adceb" (m=5), p = "*a*b" (n=4)

Initial: si=0, pi=0, starIdx=-1, matchIdx=0

pi=0, p[0]='*': record starIdx=0, matchIdx=0, pi=1
  si=0, pi=1

p[1]='a', s[0]='a': match → si=1, pi=2

p[2]='*': record starIdx=2, matchIdx=1, pi=3
  si=1, pi=3

p[3]='b', s[1]='d': MISMATCH. starIdx=2 (exists):
  pi=starIdx+1=3, matchIdx=2, si=2

p[3]='b', s[2]='c': MISMATCH. starIdx=2 exists:
  pi=3, matchIdx=3, si=3

p[3]='b', s[3]='e': MISMATCH. starIdx=2 exists:
  pi=3, matchIdx=4, si=4

p[3]='b', s[4]='b': MATCH → si=5, pi=4

si(5) === s.length(5) → exit while loop

pi(4) === p.length(4) → return true ✓
```

### Complexity
- Time: O(m × n) worst case in theory (a heavily starred pattern on a long string could trigger many backtracks), but O(m + n) in the typical/amortized sense for practical inputs; the true worst case is "adaadaad..." vs "a*a*a*a*" patterns which cause the backtracking to retry many times.
- Space: O(1) — only integer variables, no table.

### Edge Cases
- `s = "", p = "***"` → `si` never enters the while loop; the trailing-star-skipping loop handles all `*`s → returns `true`.
- `s = "abc", p = ""` → `pi = 0 = p.length = 0` but `si = 0 < 3 = s.length` → immediately hits the fallthrough path (no char match, no star, no previous star) → `false`.
- All `*`s pattern: every `*` records a new `starIdx`; after `s` is consumed, trailing stars loop skips remaining `*`s → `true` for any `s`.

### Follow-up Questions
- "Why doesn't this greedy approach work for regex matching?" → In regex, `a*` can only absorb copies of `a`, not arbitrary characters — when a mismatch occurs during backtracking, the greedy "let the star absorb one more character" doesn't verify the character matches what the `*` quantifies. The DP table handles this by checking `s[i-1] === p[j-2]` explicitly at every cell, which a simple greedy backtrack cannot do efficiently.
- "What is the true worst-case complexity of this greedy approach?" → The classic adversarial case is `s = "aaaa...ab"` (many a's then one b) with `p = "a*a*a*a*b"` — in the worst case, O(m×n) backtracks can occur, matching DP's complexity. For most practical patterns (few stars, or stars well-separated), the algorithm runs in O(m+n).

```
Does the problem involve matching a string against a pattern with special characters?
│
├── WHAT ARE THE SPECIAL CHARACTERS?
│   │
│   ├── `?` (match any 1 char) and `*` (match any sequence) → WILDCARD MATCHING
│   │   ├── DP recurrence:
│   │   │   p[j-1]='*':  dp[i][j] = dp[i][j-1] (skip *) || dp[i-1][j] (extend *)
│   │   │   p[j-1]='?':  dp[i][j] = dp[i-1][j-1]
│   │   │   literal:     dp[i][j] = (s[i-1]===p[j-1]) && dp[i-1][j-1]
│   │   └── Base cases: dp[0][j] = dp[0][j-1] && p[j-1]==='*'
│   │
│   └── `.` (match any 1 char) and `*` (quantifier: 0+ of preceding) → REGEX MATCHING
│       ├── DP recurrence:
│       │   p[j-1]='*':  dp[i][j] = dp[i][j-2] (skip x* pair)
│       │              || (charMatches(s[i-1], p[j-2]) && dp[i-1][j]) (extend x*)
│       │   other:     dp[i][j] = dp[i-1][j-1] && (p[j-1]='.' || s[i-1]===p[j-1])
│       └── Base cases: dp[0][j] = p[j-1]==='*' && dp[0][j-2]  (start at j=2)
│
├── WHICH IS MORE EFFICIENT WHEN BOTH APPLICABLE?
│   ├── DP: O(m×n) time, O(n) space (rolling row) — general, works for both
│   └── Greedy: O(m+n) time, O(1) space — wildcard only (not applicable to regex)
│
├── CRITICAL DIFFERENCES BETWEEN THE TWO RECURRENCES:
│   ├── Skip case: wildcard uses dp[i][j-1]; regex uses dp[i][j-2]
│   ├── Extend case: wildcard always allows extending; regex checks s[i-1] vs p[j-2]
│   └── Base case: wildcard uses j-1 lookback; regex uses j-2 lookback, starts at j=2
│
└── SPACE OPTIMIZATION (both problems):
    └── Rolling 1D array with a `prev` variable for the diagonal dp[i-1][j-1]
        → reduces O(m×n) to O(n) space
```

## Common Bugs Checklist

Before submitting any string matching DP solution, verify:

1. **DP table is `(m+1) × (n+1)`, not `m × n`?** — The extra row/column handles the empty-string base cases (`i=0` or `j=0`); using `m × n` shifts all indices by 1 and causes silent off-by-one errors throughout.

2. **1-indexed DP references correct 0-indexed string characters (`s[i-1]` and `p[j-1]`)?** — The most common implementation error: using `s[i]` instead of `s[i-1]` when the DP table uses 1-based counting.

3. **Regex: skip case uses `dp[i][j-2]`, not `dp[i][j-1]`?** — Using `j-1` applies wildcard semantics (skip one pattern character) instead of regex semantics (skip the two-character `x*` pair); this is the single most common semantic bug when implementing regex matching.

4. **Regex: extend case checks `s[i-1]` against `p[j-2]` (the character BEFORE `*`), not `p[j-1]` (the `*` itself)?** — The quantifier applies to the preceding character; checking the `*` position instead of the `x` position in `x*` silently produces wrong results.

5. **Regex base case loop starts at `j = 2`, not `j = 1`?** — Starting at `j = 1` would access `dp[0][j-2] = dp[0][-1]`, an out-of-bounds access.

6. **Wildcard base case: non-`*` character in the pattern BREAKS the chain of leading stars?** — `dp[0][j] = dp[0][j-1] && p[j-1] === '*'` — if `p[j-1]` is 'a' (not `*`), `dp[0][j]` becomes `false`, and all subsequent `dp[0][j+k]` stay `false` even if they're `*`s (because the `&&` chaining propagates the `false` forward). This is correct behavior but easy to accidentally break by using `p[j-1] === '*' ? true : dp[0][j-1]` (which would incorrectly allow stars after non-stars to still match empty).

7. **Wildcard extend case uses `dp[i-1][j]` (same `j`), not `dp[i-1][j-1]` (which would advance the pattern)?** — `dp[i-1][j]` keeps the `*` "in play" to absorb one more character; `dp[i-1][j-1]` would skip past the `*`, incorrectly limiting it to exactly one character instead of zero or more.

---

**Final Tip:** At the 5 YOE level, the single most important signal in these problems is correctly articulating the **difference between wildcard `*` and regex `*`** before any code is written: wildcard `*` is a standalone meta-character that matches any sequence (skip: `j-1`, extend: `dp[i-1][j]`), while regex `*` is a quantifier bound to the preceding element whose skip requires backing up two positions (`j-2`) and whose extend requires the current string character to match that preceding element specifically. Confusing these two — especially the `j-1` vs `j-2` skip difference — is the exact bug that separates a correct implementation from a wrong one that passes simple tests but fails on patterns like `"a*"` (which regex reads as "zero-or-more-a" but someone implementing wildcard semantics would read as "any-sequence-then-nothing").
