# DSA: Dynamic Programming — Top-Down (Memoization) vs Bottom-Up (Tabulation) — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is dynamic programming?**
A: Dynamic programming (DP) is an algorithmic technique for solving problems with two structural properties:
- **Optimal substructure**: the optimal solution to the problem can be constructed from optimal solutions to its subproblems.
- **Overlapping subproblems**: the same subproblems recur many times during the computation — solving them once and reusing the result avoids redundant work.

DP transforms an exponential-time recursive solution into a polynomial-time solution by storing and reusing subproblem results. Without storing results, a naive recursive solution recomputes the same subproblem exponentially many times. With storage, each subproblem is solved exactly once.

**Q2. What is the difference between memoization (top-down) and tabulation (bottom-up)?**
A: Both are techniques to avoid redundant subproblem computation — they are two implementations of the same DP idea:

- **Memoization (top-down)**: start with the original problem. Recursively break it into subproblems. Cache each subproblem's result the first time it's computed; on subsequent calls, return the cached value immediately without recomputing. The call graph is driven by the recursion — only subproblems actually needed are computed.

- **Tabulation (bottom-up)**: identify the smallest subproblems first. Fill a table (array or 2D array) iteratively from base cases upward, computing every subproblem in a predefined order. The original problem's answer is read from the table at the end. All subproblems (even potentially unneeded ones) are computed.

**Q3. What are the structural differences between top-down and bottom-up DP?**
A: Six key dimensions:

| Dimension | Top-Down (Memoization) | Bottom-Up (Tabulation) |
|---|---|---|
| Starting point | Original problem, recurse down | Base cases, iterate up |
| Subproblems solved | Only those reachable from the original | All subproblems in a fixed order |
| Data structure | Hash map or memo array + recursion | Array or 2D array (table) |
| Call overhead | Recursion stack frames | None — pure iteration |
| Stack overflow risk | Yes (deep recursion for large inputs) | No |
| Code structure | Closest to the recursive formulation | Requires knowing dependency order |

**Q4. What are the two prerequisites for applying DP to a problem?**
A:
- **Optimal substructure**: the answer to the problem can be expressed in terms of answers to smaller instances of the same problem. This is the "recurrence relation" — the mathematical definition of how subproblem solutions combine.
- **Overlapping subproblems**: the same subproblems appear multiple times. Without overlap, divide-and-conquer (which also uses optimal substructure) is sufficient — DP's caching only helps when there's overlap.

A quick test: draw the recursion tree. If you see the same node (same input parameters) appearing multiple times in the tree, you have overlapping subproblems and DP is applicable.

**Q5. What is a recurrence relation and why is it the foundation of DP?**
A: A recurrence relation expresses the value of a function in terms of its value at smaller inputs. For DP, it defines how to compute `dp[i]` (or `dp[i][j]`) from previously computed values:

```
Fibonacci:      dp[n] = dp[n-1] + dp[n-2]
Coin Change:    dp[amount] = 1 + min(dp[amount - coin] for coin in coins)
Longest Common Subsequence:
  dp[i][j] = dp[i-1][j-1] + 1              if s1[i] === s2[j]
  dp[i][j] = max(dp[i-1][j], dp[i][j-1])  otherwise
```

Deriving the recurrence relation is the hard part of DP. Once you have it, both memoization and tabulation are mechanical implementations of the same formula. Interviewers test the ability to derive the recurrence, not just implement it.

### Section 2: Top-Down (Memoization) — Deep Dive

**Q6. What is the standard template for top-down memoization?**
A: The template has four components: the memo cache, the base cases, the recursive case using the recurrence relation, and a cache-before-return pattern.

```js
function solve(n) {
  const memo = new Map(); // or array: new Array(n+1).fill(-1)

  function dp(state) {
    // 1. base case — smallest subproblem, no recursion needed
    if (state <= 0) return 0;

    // 2. cache check — return stored result if already computed
    if (memo.has(state)) return memo.get(state);

    // 3. recurrence — compute from subproblems
    const result = dp(state - 1) + dp(state - 2); // example: Fibonacci

    // 4. store before returning — cache the result
    memo.set(state, result);
    return result;
  }

  return dp(n);
}
```

**The critical order**: check cache BEFORE computing, store AFTER computing. Swapping these causes either recomputation (cache check too late) or incorrect storage (store before computing).

**Q7. When does memoization use a Map vs an array for the cache?**
A: The data type of the state determines this:

- **Integer state (`dp(n)`, `dp(i)`)**: use an array. `memo[i]` is O(1) access, zero overhead. Initialize with a sentinel value (`-1`, `null`, `Infinity`) to distinguish "not computed" from a valid result of 0. Space is O(max_state).

- **String state or object state**: use a `Map` with the state serialized as a key. `dp("3,5")` for a 2D state, or `JSON.stringify(state)` for complex states. O(1) average access but with hashing overhead.

- **Multi-dimensional integer state (`dp(i, j)`)**: use a 2D array `memo[i][j]` — more efficient than a Map with key `"${i},${j}"`. For 3+ dimensions, either a nested array or a flattened 1D array with computed indices.

**Q8. What is the time complexity of a memoized solution?**
A: O(number of distinct states × work per state). The cache ensures each distinct state is computed at most once. All subsequent calls to the same state are O(1) cache lookups. So:

- Total time = (number of distinct subproblems) × (time per subproblem excluding recursive calls)
- For Fibonacci: O(n) states × O(1) work per state = O(n)
- For Coin Change: O(amount) states × O(k) work per state (k coins) = O(amount × k)
- For LCS: O(m × n) states × O(1) work per state = O(m × n)

This is identical to the tabulation complexity — both approaches solve the same number of subproblems.

**Q9. What are the risks of top-down memoization and when does it fail?**
A: Three practical risks:

- **Stack overflow**: for large inputs (n > 10,000 in JavaScript), deep recursion exhaust the call stack. `RangeError: Maximum call stack size exceeded`. Switch to bottom-up tabulation for large inputs.

- **Memo key collisions**: if you serialize a multi-dimensional state as a string (`"${i},${j}"`), states like `(1, 23)` and `(12, 3)` produce different strings — safe. But if you concatenate without a separator (`"1" + "23"` vs `"12" + "3"` both give `"123"`), you get silent collisions producing wrong answers. Always use a unique separator or a 2D array.

- **Circular dependencies**: if the recursion can cycle (graph with cycles, not a DAG), memoization without cycle detection loops forever. This is why DP applies to DAG-structured subproblem dependencies — if the subproblem graph has cycles, DP doesn't directly apply.

### Section 3: Bottom-Up (Tabulation) — Deep Dive

**Q10. What is the standard template for bottom-up tabulation?**
A: The template has three components: table initialization with base cases, a filling loop in dependency order, and reading the final answer.

```js
function solve(n) {
  // 1. initialize table — size must cover all subproblems
  const dp = new Array(n + 1).fill(0);

  // 2. base cases — smallest subproblems with known answers
  dp[0] = 0;
  dp[1] = 1;

  // 3. fill table in order — each cell uses only already-filled cells
  for (let i = 2; i <= n; i++) {
    dp[i] = dp[i - 1] + dp[i - 2]; // recurrence
  }

  // 4. answer — read from table
  return dp[n];
}
```

The loop order is critical: `dp[i]` must be computed after all its dependencies (`dp[i-1]`, `dp[i-2]`) are already in the table. For 1D problems, left-to-right usually works. For 2D, the order depends on the recurrence direction.

**Q11. How do you determine the correct filling order for tabulation?**
A: Follow the direction of dependencies in the recurrence:

- **`dp[i]` depends on `dp[i-1]`**: fill left-to-right (i = 0, 1, 2, ..., n).
- **`dp[i][j]` depends on `dp[i-1][j]` and `dp[i][j-1]`**: fill row by row, left-to-right within each row. The dependency points "up and left" — both are filled before the current cell.
- **`dp[i][j]` depends on `dp[i+1][j]` or `dp[i][j+1]`**: fill right-to-left or bottom-to-top.
- **`dp[i][j]` depends on `dp[i-1][j-1]`**: fill diagonally or row-by-row (works since `i-1 < i` and `j-1 < j`).

A general rule: draw the dependency arrows in the table. Fill in an order where every arrow points from an already-filled cell to the current cell.

**Q12. What is space optimization in tabulation, and when is it applicable?**
A: Many DP problems only need a few previous rows/entries, not the entire table. If `dp[i]` only depends on `dp[i-1]` (and `dp[i-2]`), you don't need to store the full array — just the last one or two values:

```js
// Fibonacci — full table: O(n) space
const dp = new Array(n + 1);
dp[0] = 0; dp[1] = 1;
for (let i = 2; i <= n; i++) dp[i] = dp[i-1] + dp[i-2];

// Fibonacci — space optimized: O(1) space
let prev2 = 0, prev1 = 1;
for (let i = 2; i <= n; i++) {
  const curr = prev1 + prev2;
  prev2 = prev1;
  prev1 = curr;
}
return prev1;
```

For 2D problems where `dp[i][j]` only depends on row `i-1`: store only two rows (current and previous) — O(n) instead of O(m × n). This is a common interview optimization to mention after the correct solution.

**Q13. When can tabulation be space-optimized but memoization cannot?**
A: Tabulation naturally exposes what's "no longer needed" — after computing row `i`, row `i-2` is never needed again and can be discarded. You can explicitly shrink the storage. Memoization, by contrast, uses a cache that stores every computed state for the duration of the program (needed for potential future cache hits). You can't easily prune the memo cache without risking cache misses for repeated queries. For algorithms where space optimization is critical (e.g., LCS on long strings), bottom-up tabulation with a rolling array is the right approach.

### Section 4: Comparison & Decision Framework

**Q14. When should you choose top-down memoization over bottom-up tabulation?**
A: Prefer memoization when:
- **Not all subproblems are needed**: the recursion only visits a subset of possible states. For sparse problems (e.g., game tree search where many branches are pruned), memoization avoids computing unused states.
- **The subproblem space is hard to enumerate**: if state depends on complex parameters (sets, sorted tuples) that don't map to a simple array index, a HashMap-based memo is easier than defining a multi-dimensional table.
- **Translating from recursion**: when you already have a correct recursive solution, adding memoization is a two-line change (add cache check and store). Converting to tabulation requires rethinking the loop structure.
- **Prototype quickly**: memoization is faster to write correctly in interviews — fewer chances for off-by-one errors in loop bounds.

**Q15. When should you choose bottom-up tabulation over top-down memoization?**
A: Prefer tabulation when:
- **Large input (n > 10,000)**: avoids stack overflow risk. Tabulation has no recursion depth limit.
- **Space optimization is required**: rolling array technique (O(1) or O(n) space) is only clean to implement in tabulation.
- **All subproblems are needed anyway**: if memoization would compute every possible state, tabulation has lower constant factor (no recursion overhead, no hash map lookup).
- **Strict time/space bounds matter in production**: tabulation's O(1) table lookup is faster than O(1) amortized hash map lookup in practice.
- **The evaluation order is clear**: if the dependency order is obvious (e.g., process items 0 to n), tabulation is straightforward.

**Q16. Are memoization and tabulation always equivalent in complexity?**
A: In most cases, yes — they solve the same set of subproblems with the same recurrence, giving identical time and space complexity (asymptotically). Exceptions:
- **Sparse subproblems**: memoization can be faster if only a fraction of all possible states are reachable from the original problem. Tabulation always fills the full table.
- **Constant factors**: tabulation avoids function call overhead and hash map operations. For tight time limits, tabulation can be 2–5× faster despite identical Big-O.
- **Space**: tabulation enables rolling array optimization (O(1) space); memoization typically requires O(states) space for the cache.

**Q17. What is the "push" vs "pull" model in DP, and how does it relate to top-down vs bottom-up?**
A: Two ways to define how a DP cell gets its value:

- **Pull model (top-down)**: when computing `dp[state]`, pull values from subproblems (`dp[state] = f(dp[smaller_state1], dp[smaller_state2])`). The current state "pulls" from its dependencies. This is the natural recursive model.

- **Push model (bottom-up)**: when a subproblem `dp[state]` is finalized, push its contribution to larger problems that depend on it (`dp[state + delta] += dp[state]`). Used in some tabulation formulations (e.g., counting paths, knapsack variants where you iterate over items and "push" each item's contribution forward).

Both are valid. Pull is easier to reason about; push is natural for problems where the transition is "this item contributes to the next state" (e.g., coin change as "this coin can contribute to amount + coin").

**Q18. How do you convert a recursive solution to memoization in 3 steps?**
A:
1. **Add a cache variable** (array or Map) outside the recursive function (or as a closure).
2. **Check the cache** at the top of the function, before any computation — if found, return immediately.
3. **Store the result** before returning — write to cache, then return.

```js
// Before memoization (exponential)
function fib(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}

// After memoization (linear) — 3 changes marked with ←
function fibMemo(n) {
  const memo = {};                        // ← 1. add cache
  function dp(n) {
    if (n <= 1) return n;
    if (memo[n] !== undefined) return memo[n]; // ← 2. check cache
    memo[n] = dp(n - 1) + dp(n - 2);     // ← 3. store result
    return memo[n];
  }
  return dp(n);
}
```

**Q19. How do you convert memoization to tabulation in 5 steps?**
A:
1. **Identify the state variables** (parameters of the recursive function).
2. **Allocate a table** with dimensions matching the state space.
3. **Fill base cases** (the conditions where the recursive function returns without recursing).
4. **Write the filling loop** in an order where dependencies are satisfied — reverse-engineer from the recurrence.
5. **Return `dp[original_state]`** (the table entry for the problem you were originally asked to solve).

```js
// Memoization version
function climbStairsMemo(n) {
  const memo = {};
  function dp(i) {
    if (i <= 1) return 1;                  // base cases
    if (memo[i]) return memo[i];
    return memo[i] = dp(i-1) + dp(i-2);   // recurrence
  }
  return dp(n);
}

// Tabulation version — same recurrence, different execution model
function climbStairsTab(n) {
  if (n <= 1) return 1;
  const dp = new Array(n + 1);
  dp[0] = 1; dp[1] = 1;                   // base cases
  for (let i = 2; i <= n; i++) {
    dp[i] = dp[i-1] + dp[i-2];            // same recurrence
  }
  return dp[n];                            // answer
}
```

### Section 5: Common Patterns & Pitfalls

**Q20. What are the most common DP problem patterns at the 5 YOE level?**
A: Eight patterns cover 90% of interview DP problems:

1. **Linear DP**: `dp[i]` depends on `dp[i-1]` or a few previous entries. Fibonacci, climbing stairs, house robber.
2. **Knapsack (0/1)**: for each item, include or exclude. `dp[i][w]` = best value using first i items with weight ≤ w.
3. **Unbounded knapsack**: items can be used multiple times. Coin change (minimize coins), rod cutting.
4. **Longest Common Subsequence (LCS) / Edit Distance**: 2D DP on two strings. `dp[i][j]` = answer for prefixes of length i and j.
5. **Interval DP**: `dp[i][j]` = answer for subarray/substring `[i, j]`. Matrix chain multiplication, burst balloons, palindrome partitioning.
6. **Tree DP**: DP on a tree, usually with DFS post-order. House robber III, diameter of tree.
7. **DP on DAG**: memoized DFS on a graph. Longest path in DAG, number of paths.
8. **Bitmask DP**: state includes a bitmask of selected items. Traveling salesman, assignment problems with small n (≤ 20).

**Q21. What is the most common off-by-one error in tabulation and how do you avoid it?**
A: The most common error is **table size**: allocating `n` entries when you need `n+1` (to index from 0 to n inclusive). This causes `dp[n]` to read out of bounds.

```js
// Wrong: dp has n entries, valid indices 0..n-1
const dp = new Array(n).fill(0);
dp[n] = ...; // out of bounds!

// Correct: dp has n+1 entries, valid indices 0..n
const dp = new Array(n + 1).fill(0);
dp[n] = ...; // valid
```

The fix: always allocate `n + 1` for a problem with states 0..n. For 2D: `(m+1) × (n+1)` for states `(0..m, 0..n)`. Drawing the table on paper and labeling the indices before coding eliminates this error.

**Q22. What is the "last mile" mistake in memoization — what subtle bug appears when the valid answer is 0?**
A: If you use `0` as both the "uncomputed" sentinel AND a valid answer, the cache check will treat a correctly computed `0` as "not computed" and recompute it. This causes incorrect behavior (extra computation, potentially wrong answers if the recomputation path differs).

```js
// BUG: 0 is a valid answer, but also the array's default
const memo = new Array(n + 1).fill(0);
// ...
if (memo[i]) return memo[i]; // BUG: if dp[i] = 0, this skips the cache!

// CORRECT: use -1 as the sentinel (no valid answer is -1 for count/min problems)
const memo = new Array(n + 1).fill(-1);
// ...
if (memo[i] !== -1) return memo[i]; // correct: -1 means uncomputed
```

For problems where 0 is a valid answer, always use a sentinel that's outside the valid answer range: `-1` for counts/sums, `null`, or a separate boolean `computed[]` array.

**Q23. How do you handle "reconstruct the solution" (not just compute the optimal value) in DP?**
A: Store "parent pointers" alongside the DP values — tracking which choice led to each optimal state:

```js
// Coin change: track which coin was used at each amount
const dp = new Array(amount + 1).fill(Infinity);
const parent = new Array(amount + 1).fill(-1); // which coin used
dp[0] = 0;

for (let amt = 1; amt <= amount; amt++) {
  for (const coin of coins) {
    if (coin <= amt && dp[amt - coin] + 1 < dp[amt]) {
      dp[amt] = dp[amt - coin] + 1;
      parent[amt] = coin; // record the coin choice
    }
  }
}

// Reconstruct: trace parent pointers backward
function reconstruct(amount, parent) {
  const result = [];
  while (amount > 0) {
    result.push(parent[amount]);
    amount -= parent[amount];
  }
  return result;
}
```

For 2D DP (LCS, edit distance), store the direction of the optimal choice at each `dp[i][j]` and trace back from `dp[m][n]` to `dp[0][0]`.

**Q24. What is "memoization with external state" and what pitfall does it introduce?**
A: Sometimes the recursive function takes mutable external state (e.g., a global variable, a list that changes between calls) in addition to the parameters being memoized. The memo cache key only captures the function parameters — if the external state changes between calls with the same parameters, the cached result from a different external state is returned incorrectly.

Rule: **the cache key must fully characterize the computation**. If the result can differ for the same parameters depending on external state, either include the external state in the cache key, or ensure the external state is immutable (never changes once the memoized function starts running).

### Section 6: Scenario / Interview-Style Questions

**Q25. "An interviewer gives you a recursive Fibonacci function and asks you to optimize it. Walk through your thinking."**
A: The recursive Fibonacci is O(2^n) because it recomputes the same subproblems exponentially. The recursion tree shows `fib(n-2)` computed once directly AND once inside `fib(n-1)` — classic overlapping subproblems.

Step 1 — memoization (easiest change): add a cache. O(n) time, O(n) space, O(n) call stack. Two lines of change.

Step 2 — tabulation: fill `dp[0..n]` iteratively. O(n) time, O(n) space, O(1) call stack.

Step 3 — space optimize: only need `dp[i-1]` and `dp[i-2]`. O(n) time, O(1) space.

State each trade-off explicitly: memoization is easier to code but risks stack overflow for large n; tabulation avoids recursion; the rolling variable approach is optimal in space but slightly harder to generalize.

**Q26. "You have a correct memoized solution that times out on large inputs. The interviewer says 'it's a stack overflow.' What do you do?"**
A: Convert to bottom-up tabulation:
1. Identify the memoized function's parameters — these become the table dimensions.
2. Identify base cases — these initialize the table.
3. Identify the recurrence — this becomes the inner loop body.
4. Determine fill order from the dependency direction.
5. Replace the recursive calls with table lookups.

The conversion is mechanical once you have the recurrence. Mention: "The logic is identical — same recurrence, same answer — but execution shifts from recursion to iteration, eliminating the call stack entirely."

**Q27. "Compare the performance of memoization vs tabulation for a problem where only 1% of subproblems are actually needed."**
A: Memoization wins significantly here. With 1% of subproblems needed and n total states:
- Memoization computes 0.01n states, each with a cache check overhead.
- Tabulation computes all n states even if 99% are unused.

Example: game tree search with aggressive pruning — only nodes on the actual game path are needed. Memoization scales with the actual computation; tabulation always pays the full O(n) cost.

However, if virtually all subproblems are needed (most DP interview problems), the difference is constant-factor only: tabulation is faster in practice (no hash overhead, better cache locality) but asymptotically equivalent.

**Q28. "Walk through how you'd approach a new DP problem in an interview — what's your process?"**
A: A reliable five-step process:

1. **Identify the subproblem structure**: what smaller instance of this problem, if solved, would help me solve the full problem? State this explicitly as "let `dp[i]` = ..."

2. **Write the recurrence**: express `dp[i]` in terms of smaller states. This is the mathematical heart — get this right before writing any code.

3. **Identify base cases**: the smallest subproblems where the answer is trivially known (usually `dp[0]`, `dp[1]`, or `dp[0][0]`).

4. **Choose implementation**: memoization (easier to code from the recursion) or tabulation (needed for large inputs or space optimization). For interviews, start with memoization unless the problem is clearly large-input.

5. **Verify with a small example**: trace through a 3–5 element example by hand before submitting. Catches off-by-one, wrong base cases, and wrong recurrence direction.

State the time and space complexity at the end: O(states × work per state) for time, O(states) for space (or reduced if space-optimized).

## Problem 1 — Climbing Stairs (LeetCode 70)

### Problem
You are climbing a staircase with `n` steps. Each time you can climb 1 or 2 steps. How many distinct ways can you climb to the top?

```
Input:  n=2   → 2   (1+1, 2)
Input:  n=3   → 3   (1+1+1, 1+2, 2+1)
Input:  n=5   → 8
```

### Pattern Recognition
Linear DP — Fibonacci variant. The number of ways to reach step n = (ways to reach step n-1) + (ways to reach step n-2). Classic overlapping subproblems.

### Subproblem Definition
`dp[i]` = number of distinct ways to reach step i.

### Recurrence
```
dp[i] = dp[i-1] + dp[i-2]    for i ≥ 2
dp[0] = 1   (one way to be at the ground: do nothing)
dp[1] = 1   (one way to reach step 1: take one step)
```

### Both Implementations

```js
// ── TOP-DOWN (Memoization) ──────────────────────────────────────
function climbStairsMemo(n) {
  const memo = new Array(n + 1).fill(-1); // -1 = not computed

  function dp(i) {
    if (i <= 1) return 1;           // base cases
    if (memo[i] !== -1) return memo[i]; // cache hit
    memo[i] = dp(i - 1) + dp(i - 2);   // recurrence
    return memo[i];
  }

  return dp(n);
}

// ── BOTTOM-UP (Tabulation) ─────────────────────────────────────
function climbStairsTab(n) {
  if (n <= 1) return 1;
  const dp = new Array(n + 1);
  dp[0] = 1; // base case: 1 way to stay at ground
  dp[1] = 1; // base case: 1 way to reach step 1

  for (let i = 2; i <= n; i++) {
    dp[i] = dp[i - 1] + dp[i - 2]; // fill left-to-right
  }

  return dp[n];
}

// ── SPACE OPTIMIZED (O(1) space) ──────────────────────────────
function climbStairsOpt(n) {
  if (n <= 1) return 1;
  let prev2 = 1, prev1 = 1; // dp[0], dp[1]

  for (let i = 2; i <= n; i++) {
    const curr = prev1 + prev2;
    prev2 = prev1;
    prev1 = curr;
  }

  return prev1;
}
```

### Dry Run — Tabulation

```
n=5

Initialize: dp=[1,1,_,_,_,_]  (indices 0–5)

i=2: dp[2] = dp[1] + dp[0] = 1 + 1 = 2
i=3: dp[3] = dp[2] + dp[1] = 2 + 1 = 3
i=4: dp[4] = dp[3] + dp[2] = 3 + 2 = 5
i=5: dp[5] = dp[4] + dp[3] = 5 + 3 = 8

return dp[5] = 8 ✓

Ways: (1,1,1,1,1),(1,1,1,2),(1,1,2,1),(1,2,1,1),(2,1,1,1),(1,2,2),(2,1,2),(2,2,1) = 8 ✓
```

### Complexity

| Approach | Time | Space |
|---|---|---|
| Memoization | O(n) | O(n) memo + O(n) stack |
| Tabulation | O(n) | O(n) |
| Space-optimized | O(n) | O(1) |

### Edge Cases
- n=0: return 1 (one way to "be at the top" = do nothing). Some problems define this as 0 — clarify with interviewer.
- n=1: return 1. Both base cases cover this before the loop starts.
- n=2: dp[2]=2. Verified: (1+1), (2).

### Follow-up Questions
- "What if you can take 1, 2, or 3 steps?" → Recurrence: `dp[i] = dp[i-1] + dp[i-2] + dp[i-3]`. Same structure.
- "What if each step has a cost and you minimize total cost?" → Min-cost climbing stairs — same recurrence with `min` instead of sum.

## Problem 2 — House Robber (LeetCode 198)

### Problem
You are a robber. Each house has some amount of money `nums[i]`. You cannot rob two adjacent houses. Return the maximum amount you can rob.

```
Input:  nums=[1,2,3,1]   → 4   (rob house 0 and 2: 1+3)
Input:  nums=[2,7,9,3,1] → 12  (rob house 0, 2, 4: 2+9+1)
```

### Pattern Recognition
Linear DP — at each house, binary choice: rob it (can't rob previous) or skip it (can rob previous). Classic "include or exclude" pattern.

### Subproblem Definition
`dp[i]` = maximum money robbed from houses 0..i.

### Recurrence
```
dp[i] = max(dp[i-1],            // skip house i — take best from 0..i-1
             dp[i-2] + nums[i]) // rob house i — add to best from 0..i-2
dp[0] = nums[0]
dp[1] = max(nums[0], nums[1])
```

### Both Implementations

```js
// ── TOP-DOWN (Memoization) ──────────────────────────────────────
function robMemo(nums) {
  const n = nums.length;
  const memo = new Array(n).fill(-1);

  function dp(i) {
    if (i < 0) return 0;          // no houses left
    if (i === 0) return nums[0];  // base case
    if (memo[i] !== -1) return memo[i];

    // choose max of: skip i, or rob i + best of 0..i-2
    memo[i] = Math.max(dp(i - 1), dp(i - 2) + nums[i]);
    return memo[i];
  }

  return dp(n - 1);
}

// ── BOTTOM-UP (Tabulation) ─────────────────────────────────────
function robTab(nums) {
  const n = nums.length;
  if (n === 1) return nums[0];

  const dp = new Array(n);
  dp[0] = nums[0];
  dp[1] = Math.max(nums[0], nums[1]);

  for (let i = 2; i < n; i++) {
    dp[i] = Math.max(dp[i - 1], dp[i - 2] + nums[i]);
  }

  return dp[n - 1];
}

// ── SPACE OPTIMIZED ───────────────────────────────────────────
function robOpt(nums) {
  const n = nums.length;
  if (n === 1) return nums[0];

  let prev2 = nums[0];
  let prev1 = Math.max(nums[0], nums[1]);

  for (let i = 2; i < n; i++) {
    const curr = Math.max(prev1, prev2 + nums[i]);
    prev2 = prev1;
    prev1 = curr;
  }

  return prev1;
}
```

### Dry Run — Tabulation

```
nums=[2,7,9,3,1]

dp[0] = 2
dp[1] = max(2, 7) = 7
dp[2] = max(dp[1], dp[0]+9) = max(7, 2+9) = max(7,11) = 11
dp[3] = max(dp[2], dp[1]+3) = max(11, 7+3) = max(11,10) = 11
dp[4] = max(dp[3], dp[2]+1) = max(11, 11+1) = max(11,12) = 12

return dp[4] = 12 ✓   (rob indices 0,2,4: 2+9+1=12)
```

### Complexity

| Approach | Time | Space |
|---|---|---|
| Memoization | O(n) | O(n) |
| Tabulation | O(n) | O(n) |
| Space-optimized | O(n) | O(1) |

### Edge Cases
- Single house: return `nums[0]`. Guard with `if (n===1)`.
- Two houses: `max(nums[0], nums[1])`. Handled by `dp[1]` base case.
- All zeroes: returns 0. Correct.
- Strictly decreasing: best is robbing first house. Handled by the recurrence.

### Follow-up Questions
- "What if houses are in a circle (first and last are adjacent)?" → House Robber II: run the robber twice — once on `nums[0..n-2]` (exclude last) and once on `nums[1..n-1]` (exclude first). Take the max.
- "What if the houses form a binary tree?" → House Robber III: tree DP with DFS, returning `[rob_root, skip_root]` pair from each node.

## Problem 3 — Coin Change (LeetCode 322)

### Problem
Given an array of coin denominations `coins` and an integer `amount`, return the fewest number of coins needed to make up that amount. If impossible, return -1.

```
Input:  coins=[1,5,6,9], amount=11  → 2  (5+6)
Input:  coins=[2], amount=3         → -1
Input:  coins=[1,2,5], amount=11    → 3  (5+5+1)
```

### Pattern Recognition
Unbounded knapsack — coins can be used multiple times. `dp[amount]` depends on `dp[amount - coin]` for each coin. Classic "minimum operations" pattern.

### Subproblem Definition
`dp[i]` = minimum coins needed to make amount `i`. `Infinity` if impossible.

### Recurrence
```
dp[0] = 0                                           (base: 0 coins for amount 0)
dp[i] = min over all coins c: (dp[i - c] + 1)       for i - c >= 0
dp[i] = Infinity if no coin works
```

### Both Implementations

```js
// ── TOP-DOWN (Memoization) ──────────────────────────────────────
function coinChangeMemo(coins, amount) {
  const memo = new Array(amount + 1).fill(-1);
  memo[0] = 0; // base case pre-filled

  function dp(amt) {
    if (amt < 0) return Infinity;   // can't go negative
    if (memo[amt] !== -1) return memo[amt]; // cache hit

    let best = Infinity;
    for (const coin of coins) {
      const sub = dp(amt - coin);
      if (sub !== Infinity) {
        best = Math.min(best, sub + 1);
      }
    }

    memo[amt] = best;
    return best;
  }

  const result = dp(amount);
  return result === Infinity ? -1 : result;
}

// ── BOTTOM-UP (Tabulation) ─────────────────────────────────────
function coinChangeTab(coins, amount) {
  // dp[i] = min coins for amount i
  const dp = new Array(amount + 1).fill(Infinity);
  dp[0] = 0; // base: 0 coins for amount 0

  for (let amt = 1; amt <= amount; amt++) {
    for (const coin of coins) {
      if (coin <= amt && dp[amt - coin] !== Infinity) {
        dp[amt] = Math.min(dp[amt], dp[amt - coin] + 1);
      }
    }
  }

  return dp[amount] === Infinity ? -1 : dp[amount];
}
```

- "Reconstruct which coins were used?" → Add `parent[amt] = coin` when updating minimum; trace back.
- "Minimum coins but each coin can only be used once?" → 0/1 knapsack variant.

## Problem 4 — Longest Common Subsequence (LeetCode 1143)

### Problem
Given two strings `text1` and `text2`, return the length of their longest common subsequence. A subsequence is a sequence that appears in the same relative order but not necessarily contiguously.

```
Input:  text1="abcde", text2="ace"  → 3  ("ace")
Input:  text1="abc", text2="abc"    → 3
Input:  text1="abc", text2="def"    → 0
```

### Pattern Recognition
2D string DP — LCS is the prototype 2D DP problem. `dp[i][j]` represents the LCS of prefixes.

### Subproblem Definition
`dp[i][j]` = length of LCS of `text1[0..i-1]` and `text2[0..j-1]` (1-indexed for simplicity with base case `dp[0][j] = dp[i][0] = 0`).

### Recurrence
```
dp[i][j] = dp[i-1][j-1] + 1          if text1[i-1] === text2[j-1]  (chars match)
dp[i][j] = max(dp[i-1][j], dp[i][j-1]) otherwise                    (skip one char)
dp[i][0] = 0  for all i  (LCS with empty string = 0)
dp[0][j] = 0  for all j
```

### Both Implementations

```js
// ── TOP-DOWN (Memoization) ──────────────────────────────────────
function lcsMemo(text1, text2) {
  const m = text1.length, n = text2.length;
  // 2D memo: use -1 as sentinel
  const memo = Array.from({length: m + 1}, () => new Array(n + 1).fill(-1));

  function dp(i, j) {
    if (i === 0 || j === 0) return 0; // base: empty prefix

    if (memo[i][j] !== -1) return memo[i][j];

    if (text1[i - 1] === text2[j - 1]) {
      memo[i][j] = dp(i - 1, j - 1) + 1; // characters match
    } else {
      memo[i][j] = Math.max(dp(i - 1, j), dp(i, j - 1)); // skip one
    }

    return memo[i][j];
  }

  return dp(m, n);
}

// ── BOTTOM-UP (Tabulation) ─────────────────────────────────────
function lcsTab(text1, text2) {
  const m = text1.length, n = text2.length;
  // (m+1) × (n+1) table, row 0 and col 0 are base cases (all 0)
  const dp = Array.from({length: m + 1}, () => new Array(n + 1).fill(0));

  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (text1[i - 1] === text2[j - 1]) {
        dp[i][j] = dp[i - 1][j - 1] + 1; // match
      } else {
        dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]); // skip
      }
    }
  }

  return dp[m][n];
}

// ── SPACE OPTIMIZED (two rows) ────────────────────────────────
function lcsOpt(text1, text2) {
  const m = text1.length, n = text2.length;
  let prev = new Array(n + 1).fill(0); // previous row

  for (let i = 1; i <= m; i++) {
    const curr = new Array(n + 1).fill(0);
    for (let j = 1; j <= n; j++) {
      if (text1[i - 1] === text2[j - 1]) {
        curr[j] = prev[j - 1] + 1;
      } else {
        curr[j] = Math.max(prev[j], curr[j - 1]);
      }
    }
    prev = curr;
  }

  return prev[n];
}
```

### Dry Run — Tabulation

```
text1="abcde", text2="ace"
m=5, n=3

        ""  a   c   e
    ""  [0,  0,  0,  0]
    a   [0,  1,  1,  1]
    b   [0,  1,  1,  1]
    c   [0,  1,  2,  2]
    d   [0,  1,  2,  2]
    e   [0,  1,  2,  3]

Trace key cells:
dp[1][1]: text1[0]='a'=text2[0]='a' → dp[0][0]+1=1
dp[1][2]: text1[0]='a'≠text2[1]='c' → max(dp[0][2],dp[1][1])=max(0,1)=1
dp[3][2]: text1[2]='c'=text2[1]='c' → dp[2][1]+1=1+1=2
dp[5][3]: text1[4]='e'=text2[2]='e' → dp[4][2]+1=2+1=3

return dp[5][3] = 3 ✓
```

### Complexity

| Approach | Time | Space |
|---|---|---|
| Memoization | O(m × n) | O(m × n) |
| Tabulation | O(m × n) | O(m × n) |
| Space-optimized | O(m × n) | O(n) |

### Edge Cases
- One string empty: LCS = 0. `dp[0][j] = dp[i][0] = 0` handles this.
- Identical strings: LCS = string length. Diagonal of `dp` fills with 1,2,3,...
- No common characters: all cells stay 0. Return 0.

### Follow-up Questions
- "Reconstruct the actual LCS string?" → Trace back through `dp`: when `text1[i-1]===text2[j-1]`, include the character and go to `dp[i-1][j-1]`. Otherwise go to `dp[i-1][j]` or `dp[i][j-1]` (whichever is larger).
- "What is the edit distance between two strings?" → Related 2D DP — counts insertions, deletions, and substitutions. Recurrence: `dp[i][j] = dp[i-1][j-1]` if chars match; else `1 + min(dp[i-1][j], dp[i][j-1], dp[i-1][j-1])`.

## Problem 5 — 0/1 Knapsack

### Problem
Given `n` items each with weight `weights[i]` and value `values[i]`, and a knapsack capacity `W`, find the maximum value you can carry. Each item can be included at most once.

```
Input:  weights=[1,3,4,5], values=[1,4,5,7], W=7
Output: 9   (items 1 and 2: weight=3+4=7, value=4+5=9)

Input:  weights=[2,3,4,5], values=[3,4,5,6], W=8
Output: 10  (items 0 and 3: weight=2+5=7, value=3+7... wait)
            Actually items 0,1: 2+3=5≤8, 3+4=7; or 0,2: 2+4=6,3+5=8
            Best: items 1,3: 3+5=8, 4+6=10 ✓
```

### Pattern Recognition
0/1 Knapsack — for each item, binary choice: include (if weight allows) or exclude. Classic 2D DP with items on one axis and capacity on the other.

### Subproblem Definition
`dp[i][w]` = maximum value using items from index 0..i with total weight ≤ w.

### Recurrence
```
dp[i][w] = dp[i-1][w]                                   if weights[i] > w (can't include)
dp[i][w] = max(dp[i-1][w],                              otherwise: skip item i
               dp[i-1][w - weights[i]] + values[i])                 or include item i
dp[0][w] = values[0] if weights[0] <= w, else 0         base: only first item available
dp[i][0] = 0                                             base: zero capacity
```

### Both Implementations

```js
// ── TOP-DOWN (Memoization) ──────────────────────────────────────
function knapsackMemo(weights, values, W) {
  const n = weights.length;
  // memo[i][w] = -1 means not computed
  const memo = Array.from({length: n}, () => new Array(W + 1).fill(-1));

  function dp(i, w) {
    if (i < 0 || w === 0) return 0;   // base: no items or no capacity
    if (memo[i][w] !== -1) return memo[i][w];

    let result = dp(i - 1, w); // exclude item i

    if (weights[i] <= w) {
      // include item i if it fits
      result = Math.max(result, dp(i - 1, w - weights[i]) + values[i]);
    }

    memo[i][w] = result;
    return result;
  }

  return dp(n - 1, W);
}

// ── BOTTOM-UP (Tabulation) ─────────────────────────────────────
function knapsackTab(weights, values, W) {
  const n = weights.length;
  // dp[i][w] — (n+1) rows for cleaner base case handling
  const dp = Array.from({length: n + 1}, () => new Array(W + 1).fill(0));
  // dp[0][w] = 0 for all w: no items → no value

  for (let i = 1; i <= n; i++) {
    const wi = weights[i - 1]; // item i-1 (0-indexed)
    const vi = values[i - 1];

    for (let w = 0; w <= W; w++) {
      dp[i][w] = dp[i - 1][w]; // exclude item i
      if (wi <= w) {
        dp[i][w] = Math.max(dp[i][w], dp[i - 1][w - wi] + vi); // include
      }
    }
  }

  return dp[n][W];
}

// ── SPACE OPTIMIZED (1D rolling array) ───────────────────────
function knapsackOpt(weights, values, W) {
  const n = weights.length;
  const dp = new Array(W + 1).fill(0); // dp[w] = max value with capacity w

  for (let i = 0; i < n; i++) {
    // traverse RIGHT-TO-LEFT to prevent using item i twice
    for (let w = W; w >= weights[i]; w--) {
      dp[w] = Math.max(dp[w], dp[w - weights[i]] + values[i]);
    }
  }

  return dp[W];
}
```

### Dry Run — Tabulation (1D optimized)

```
weights=[1,3,4,5], values=[1,4,5,7], W=7
dp=[0,0,0,0,0,0,0,0]  (indices 0–7)

Item 0 (w=1, v=1): traverse w=7 down to 1
  w=7: max(dp[7], dp[6]+1) = max(0,0+1) = 1
  w=6: max(0, dp[5]+1) = 1
  ... all dp[w] for w≥1 become 1
dp=[0,1,1,1,1,1,1,1]

Item 1 (w=3, v=4): traverse w=7 down to 3
  w=7: max(dp[7], dp[4]+4) = max(1, 1+4) = 5
  w=6: max(dp[6], dp[3]+4) = max(1, 1+4) = 5
  w=5: max(dp[5], dp[2]+4) = max(1, 1+4) = 5
  w=4: max(dp[4], dp[1]+4) = max(1, 1+4) = 5
  w=3: max(dp[3], dp[0]+4) = max(1, 0+4) = 4
dp=[0,1,1,4,5,5,5,5]

Item 2 (w=4, v=5): traverse w=7 down to 4
  w=7: max(dp[7], dp[3]+5) = max(5, 4+5) = 9
  w=6: max(dp[6], dp[2]+5) = max(5, 1+5) = 6
  w=5: max(dp[5], dp[1]+5) = max(5, 1+5) = 6
  w=4: max(dp[4], dp[0]+5) = max(5, 0+5) = 5
dp=[0,1,1,4,5,6,6,9]

Item 3 (w=5, v=7): traverse w=7 down to 5
  w=7: max(dp[7], dp[2]+7) = max(9, 1+7) = 9
  w=6: max(dp[6], dp[1]+7) = max(6, 1+7) = 8
  w=5: max(dp[5], dp[0]+7) = max(6, 0+7) = 7
dp=[0,1,1,4,5,7,8,9]

return dp[7] = 9 ✓  (items 1,2: weight=3+4=7, value=4+5=9)
```

### Critical Detail: Why Right-to-Left in Space-Optimized?
Traversing `w` from `W` down to `weights[i]` ensures item `i` is counted at most once. If we traversed left-to-right, `dp[w - weights[i]]` might already include item `i` (just added in this pass), allowing the same item to be selected multiple times — turning 0/1 knapsack into unbounded knapsack. Right-to-left guarantees each item is only "seen" once per pass.

### Complexity

| Approach | Time | Space |
|---|---|---|
| Memoization | O(n × W) | O(n × W) |
| Tabulation (2D) | O(n × W) | O(n × W) |
| Space-optimized | O(n × W) | O(W) |

### Edge Cases
- Zero capacity (W=0): all `dp[0] = 0`. Return 0.
- Item heavier than W: never included; skipped by `if (wi <= w)`.
- All items heavier than W: return 0.
- Single item fitting exactly: dp[W] = values[0].

### Follow-up Questions
- "Unbounded knapsack (items reusable)?" → Change right-to-left to left-to-right in the 1D optimization. Each item can now be used multiple times.
- "Reconstruct which items were selected?" → Use the 2D table: for each row i from n down to 1, if `dp[i][w] !== dp[i-1][w]`, item i was selected; set `w -= weights[i-1]`.

## Problem 6 — Edit Distance (LeetCode 72)

### Problem
Given two strings `word1` and `word2`, return the minimum number of operations (insert, delete, replace) to convert `word1` to `word2`.

```
Input:  word1="horse", word2="ros"   → 3
        horse→rorse (replace h→r), rorse→rose (delete r), rose→ros (delete e)
Input:  word1="intention", word2="execution"  → 5
```

### Pattern Recognition
2D string DP — edit distance is the classic example. Each cell `dp[i][j]` answers "min operations to convert `word1[0..i-1]` to `word2[0..j-1]`."

### Subproblem Definition
`dp[i][j]` = minimum edit distance between `word1[0..i-1]` and `word2[0..j-1]`.

### Recurrence
```
dp[i][j] = dp[i-1][j-1]                          if word1[i-1] === word2[j-1]  (no op needed)
dp[i][j] = 1 + min(dp[i-1][j],                   otherwise: delete from word1
                    dp[i][j-1],                              insert into word1
                    dp[i-1][j-1])                            replace in word1
dp[i][0] = i  (delete all i chars of word1)
dp[0][j] = j  (insert all j chars of word2)
```

### Both Implementations

```js
// ── TOP-DOWN (Memoization) ──────────────────────────────────────
function editDistanceMemo(word1, word2) {
  const m = word1.length, n = word2.length;
  const memo = Array.from({length: m + 1}, () => new Array(n + 1).fill(-1));

  function dp(i, j) {
    if (i === 0) return j; // base: insert all of word2
    if (j === 0) return i; // base: delete all of word1
    if (memo[i][j] !== -1) return memo[i][j];

    if (word1[i - 1] === word2[j - 1]) {
      memo[i][j] = dp(i - 1, j - 1); // no operation needed
    } else {
      memo[i][j] = 1 + Math.min(
        dp(i - 1, j),     // delete word1[i-1]
        dp(i, j - 1),     // insert word2[j-1] into word1
        dp(i - 1, j - 1)  // replace word1[i-1] with word2[j-1]
      );
    }

    return memo[i][j];
  }

  return dp(m, n);
}

// ── BOTTOM-UP (Tabulation) ─────────────────────────────────────
function editDistanceTab(word1, word2) {
  const m = word1.length, n = word2.length;
  // (m+1)×(n+1) table
  const dp = Array.from({length: m + 1}, () => new Array(n + 1).fill(0));

  // base cases: converting to/from empty string
  for (let i = 0; i <= m; i++) dp[i][0] = i; // delete i chars
  for (let j = 0; j <= n; j++) dp[0][j] = j; // insert j chars

  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (word1[i - 1] === word2[j - 1]) {
        dp[i][j] = dp[i - 1][j - 1];           // chars match — no op
      } else {
        dp[i][j] = 1 + Math.min(
          dp[i - 1][j],    // delete
          dp[i][j - 1],    // insert
          dp[i - 1][j - 1] // replace
        );
      }
    }
  }

  return dp[m][n];
}
```

### Dry Run — Tabulation

```
word1="horse", word2="ros"
m=5, n=3

      ""  r   o   s
  ""  [0,  1,  2,  3]
  h   [1,  1,  2,  3]
  o   [2,  2,  1,  2]
  r   [3,  2,  2,  2]
  s   [4,  3,  3,  2]
  e   [5,  4,  4,  3]

Key cells:
dp[1][1]: h≠r → 1+min(dp[0][1],dp[1][0],dp[0][0])=1+min(1,1,0)=1 (replace)
dp[2][2]: o=o → dp[1][1]=1
dp[3][1]: r=r → dp[2][0]=2
dp[3][2]: r≠o → 1+min(dp[2][2],dp[3][1],dp[2][1])=1+min(1,2,2)=2

return dp[5][3] = 3 ✓
```

### Complexity

| Approach | Time | Space |
|---|---|---|
| Memoization | O(m × n) | O(m × n) |
| Tabulation | O(m × n) | O(m × n) |
| Space-optimized (2 rows) | O(m × n) | O(n) |

### Edge Cases
- One string empty: edit distance = length of the other string. Base cases cover this.
- Identical strings: all diagonal cells match → return 0.
- Single character: straightforward 1-step insert/delete/replace.

### Follow-up Questions
- "Return the actual sequence of operations?" → Track direction at each cell (which of delete/insert/replace was chosen). Backtrack from `dp[m][n]` to `dp[0][0]`.
- "What if replace costs 2 instead of 1?" → Change `dp[i-1][j-1]` in the replace branch to `dp[i-1][j-1] + 2`. Weighted edit distance generalizes cleanly.

## Quick Reference — Top-Down vs Bottom-Up

```
Decision Checklist — Which to Use?

Use Top-Down (Memoization) when:
  □ You already have a correct recursive solution (add cache in 2 lines)
  □ Not all subproblems are needed (sparse subproblem space)
  □ State is complex (set, string key, multiple non-integer params)
  □ Prototype quickly — easier to write correctly under interview pressure
  □ Input size is small–medium (n ≤ 10,000 to avoid stack overflow)

Use Bottom-Up (Tabulation) when:
  □ Input is large (n > 10,000) — no stack overflow risk
  □ Space optimization is needed (rolling array: O(1) or O(n))
  □ All subproblems are needed anyway (full table is filled regardless)
  □ The problem has a clear iterative fill order
  □ Performance matters — no recursion overhead, better cache locality

Common DP Patterns and Their Templates:
  Linear 1D:     dp[i] = f(dp[i-1], dp[i-2])       → fill left-to-right
  0/1 Knapsack:  dp[i][w] = max(skip, include)       → fill row-by-row; 1D: right-to-left
  Unbounded:     dp[amt] = min(dp[amt-coin]+1)       → fill left-to-right
  2D String:     dp[i][j] = f(dp[i-1][j], dp[i][j-1], dp[i-1][j-1])
  Interval:      dp[i][j] = f(dp[i][k], dp[k+1][j]) → fill by length
```

## Common Bugs Checklist

Before finalizing any DP solution, verify:

1. **Sentinel value is not a valid answer** — use `-1` for counts/lengths (never a valid result), `Infinity` for minimization (valid result is always finite), `null` for general states. Using `0` as sentinel when `0` is a valid answer causes silent cache misses on correct zero-valued subproblems.

2. **Table size is n+1, not n** — for states `dp[0]` through `dp[n]`, allocate `n+1` entries. `new Array(n)` gives indices `0..n-1` — `dp[n]` is out of bounds. This is the #1 off-by-one in tabulation.

3. **Right-to-left for 0/1 knapsack 1D** — the 1D space-optimized knapsack MUST traverse from `W` down to `weights[i]`. Left-to-right allows an item to be selected multiple times in one pass (unbounded knapsack behavior). Getting this direction wrong silently gives wrong answers.

4. **Base cases fully initialized before the loop** — the loop body assumes `dp[i-1]`, `dp[i-2]`, etc. are already set. If base cases aren't initialized first (e.g., `dp[0]` and `dp[1]` for Fibonacci), the first loop iteration reads garbage.

5. **The recurrence direction matches the fill order** — if `dp[i][j]` depends on `dp[i+1][j]`, you must fill bottom-to-top (not top-to-bottom). Drawing the dependency arrows before coding catches this.

6. **Memoization cache is scoped correctly** — the cache must persist across calls to `dp(i)`. Declaring it inside the recursive function (not in a closure or outer scope) recreates the cache on every call — the memoization does nothing.

**Final Tip:** At the 5 YOE level, the interviewer isn't testing whether you know Fibonacci is O(n) with DP — that's table stakes. The signal questions are: "derive the recurrence from scratch for this problem I've never seen," "which approach would you choose and why," "can you space-optimize your tabulation," and "walk me through the time complexity using the states × work per state formula." The highest-signal move in any DP interview is to state the subproblem definition explicitly before writing a single line — "let `dp[i][j]` = the minimum operations to convert the first i characters of word1 to the first j characters of word2." That sentence, spoken confidently before touching code, tells the interviewer you understand the mathematical structure rather than pattern-matching to a memorized solution.
