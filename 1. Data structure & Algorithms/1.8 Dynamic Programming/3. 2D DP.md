# DSA: 2D Dynamic Programming — Unique Paths, Minimum Path Sum & Edit Distance — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals of 2D DP

**Q1. What distinguishes a 2D DP problem from a 1D DP problem, and what does the "2D" refer to?**
A: In 1D DP, the state space is a single array — each entry `dp[i]` represents the answer for a subproblem parameterized by one dimension (e.g., the first `i` elements, or position `i` in a sequence). In 2D DP, the state space is a **grid/table** — each entry `dp[i][j]` represents the answer for a subproblem parameterized by **two dimensions simultaneously** (e.g., position `(i, j)` in a grid, or the first `i` characters of one string and the first `j` characters of another). The "2D" refers to this two-dimensional state space, not necessarily to the geometric shape of the input. The three canonical problems in this guide span two geometrically different 2D-state interpretations: grid-navigation problems (Unique Paths, Minimum Path Sum) where `(i,j)` is a literal grid position, and string-alignment problems (Edit Distance) where `i` and `j` are indices into two separate sequences.

**Q2. What is the standard recipe for designing a 2D DP solution?**
A: Five steps, applied in order:
1. **Define the state**: what does `dp[i][j]` represent? Be precise — "the answer to the subproblem considering rows 0..i and columns 0..j" or "the answer considering the first i characters of string A and the first j characters of string B."
2. **Write the recurrence**: how does `dp[i][j]` depend on previously computed, smaller subproblems? This is the core mathematical insight.
3. **Identify base cases**: what values of `dp[i][j]` can be filled in directly (without using the recurrence), typically along the edges (first row, first column, or both)?
4. **Choose fill order**: which direction to fill the table so that every cell `dp[i][j]` is computed only after all the cells it depends on have already been computed (typically top-to-bottom, left-to-right for problems depending on `dp[i-1][j]` and `dp[i][j-1]`).
5. **Extract the answer**: which cell(s) of the table contain the final answer? Usually `dp[m][n]` (bottom-right corner) for the three problems in this guide.

**Q3. What is the canonical space optimization for 2D DP tables, and when does it apply?**
A: Many 2D DP recurrences only reference the **current row and the previous row** (e.g., `dp[i][j]` depends only on `dp[i-1][j]` and `dp[i][j-1]`). In such cases, the full `m × n` table can be compressed to just **two 1D arrays** (current row and previous row), or even a single array (updated in-place by carefully choosing the update direction). This reduces space from O(m × n) to O(n) — a significant practical improvement for large inputs. Unique Paths and Minimum Path Sum both support this optimization cleanly; Edit Distance does too, though it requires slightly more care to avoid overwriting values needed later in the same row update (typically handled with a single extra variable to save the "diagonal" value `dp[i-1][j-1]`).

**Q4. How do you recognize that a problem is a 2D DP problem, and what are the tell-tale signals?**
A: Key signals:
- The problem asks for a count, minimum, or maximum over all **paths through a 2D grid** from a start to an end cell.
- The problem involves **two sequences** (strings, arrays) and asks for the minimum cost, maximum similarity, or count of operations to align/transform one into the other.
- The problem has **overlapping subproblems** — the same subproblem recurs in multiple places during a naive recursive solution.
- A brute-force recursive solution has an exponential search space that can be memoized with a 2D table.
- The problem's constraints explicitly involve two lengths/dimensions (e.g., `m × n` grid, strings of lengths `m` and `n`), and the desired answer sits at one "corner" of the resulting state space.

### Section 2: Unique Paths

**Q5. What is the "unique paths" problem, and what is its recurrence?**
A: Count the number of distinct paths from the top-left to the bottom-right corner of an `m × n` grid, where you can only move **right** or **down** at each step. `dp[i][j]` = the number of unique paths to reach cell `(i, j)`. Recurrence: `dp[i][j] = dp[i-1][j] + dp[i][j-1]` — the number of ways to reach `(i,j)` equals the sum of ways to reach the cell directly above it (`dp[i-1][j]`, from which you move down) plus the cell directly to its left (`dp[i][j-1]`, from which you move right). Base cases: the entire first row and first column are all 1 (there's exactly one path to any cell along the top row — always move right — and exactly one path to any cell along the leftmost column — always move down).

```
3×3 grid:
dp[0][0..2] = [1, 1, 1]   (first row: only rightward paths)
dp[1][0]    = 1            (only downward path)
dp[1][1]    = dp[0][1] + dp[1][0] = 1+1 = 2
dp[1][2]    = dp[0][2] + dp[1][1] = 1+2 = 3
dp[2][0]    = 1
dp[2][1]    = dp[1][1] + dp[2][0] = 2+1 = 3
dp[2][2]    = dp[1][2] + dp[2][1] = 3+3 = 6

Answer: dp[2][2] = 6
```

**Q6. Why does Unique Paths have a closed-form mathematical solution, and when is it better to use the DP approach?**
A: The number of unique paths in an `m × n` grid equals the **binomial coefficient C(m+n-2, m-1)** — the number of ways to choose which `m-1` of the `(m-1) + (n-1)` total moves are "down" moves (the rest being "right"). The DP approach is better when there are **obstacles** in the grid (blocked cells that cannot be entered) — the closed form doesn't adapt to obstacles, but the DP recurrence adapts trivially: if cell `(i,j)` is an obstacle, set `dp[i][j] = 0` (no paths lead through it). The closed form is an elegant mathematical shortcut for the obstacle-free variant, but DP is the general-purpose tool.

**Q7. What is the space-optimized O(n) version of the Unique Paths solution?**
A: Since `dp[i][j]` depends only on `dp[i-1][j]` (above) and `dp[i][j-1]` (left), the table can be reduced to a single 1D array of length `n`, updated row by row:

```js
function uniquePaths(m, n) {
  const dp = new Array(n).fill(1); // base case: first row all 1s

  for (let i = 1; i < m; i++) {
    for (let j = 1; j < n; j++) {
      dp[j] += dp[j - 1]; // dp[j] was the "above" value, dp[j-1] is the "left" value
    }
  }

  return dp[n - 1];
}
```

When processing `dp[j]` in-place, the current value of `dp[j]` holds the value from the previous row (the "above" contribution), and `dp[j-1]` holds the already-updated value from the current row (the "left" contribution) — exactly the two needed values, without storing any other row.

### Section 3: Minimum Path Sum

**Q8. What is the "minimum path sum" problem, and how does its recurrence differ from Unique Paths?**
A: Given an `m × n` grid filled with non-negative numbers, find a path from top-left to bottom-right (moving only right or down) that minimizes the **sum of values along the path**. `dp[i][j]` = the minimum path sum to reach cell `(i, j)`. Recurrence: `dp[i][j] = grid[i][j] + Math.min(dp[i-1][j], dp[i][j-1])` — the minimum cost to reach `(i,j)` is the cell's own value plus the minimum of the cheapest paths to the two cells from which `(i,j)` is reachable. The structural shape is identical to Unique Paths (same state definition, same dependency pattern), but the aggregation changes from **sum** (counting paths) to **min + current cost** (optimizing path cost).

**Q9. What are the base cases for minimum path sum, and why do they differ from the Unique Paths base cases?**
A: The first cell `dp[0][0] = grid[0][0]` (path cost to the start is just the start cell's value). The first row: `dp[0][j] = dp[0][j-1] + grid[0][j]` — only reachable by coming from the left, so the cost accumulates leftward. The first column: `dp[i][0] = dp[i-1][0] + grid[i][0]` — only reachable from above. These differ from Unique Paths' all-1s base cases because the first row/column values aren't constant (they depend on the actual grid values being accumulated), whereas Unique Paths counts paths (always exactly 1 along edges regardless of grid content).

**Q10. Can minimum path sum be solved in-place (modifying the input grid directly), and when is this appropriate?**
A: Yes — since `dp[i][j]` depends only on `dp[i-1][j]` and `dp[i][j-1]`, and both of those cells are in positions processed before `(i,j)` in a top-to-bottom left-to-right fill order, the grid can be modified in-place (`grid[i][j] += Math.min(grid[i-1][j], grid[i][j-1])`). This achieves O(1) extra space (no auxiliary array) at the cost of mutating the input. Whether this is acceptable depends on whether the caller expects the input to be unchanged after the call — in a real codebase this would usually be unacceptable (mutating caller-owned data is a bad practice); in an interview, mentioning it as an optimization but noting the mutation side-effect is the appropriate response.

### Section 4: Edit Distance

**Q11. What is the "edit distance" (Levenshtein distance) problem, and what three operations are allowed?**
A: Given two strings `word1` and `word2`, find the minimum number of operations to convert `word1` into `word2`. The three allowed operations (each counts as 1 step) are: **insert** a character, **delete** a character, **replace** a character with a different one. The Levenshtein distance is the fundamental measure of string similarity used in spell-checkers, DNA sequence alignment, fuzzy search, and diff algorithms.

```
word1 = "horse", word2 = "ros"
Operations: horse → rorse (replace h→r) → rose (delete r) → ros (delete e) = 3 operations
Edit distance = 3
```

**Q12. What does `dp[i][j]` represent in the edit distance formulation, and what is the full recurrence?**
A: `dp[i][j]` = the minimum number of operations to convert the **first `i` characters of `word1`** into the **first `j` characters of `word2`**. Recurrence:
- If `word1[i-1] === word2[j-1]` (characters match): `dp[i][j] = dp[i-1][j-1]` — no operation needed for these characters; the cost is the same as without them.
- If they don't match: `dp[i][j] = 1 + Math.min(dp[i-1][j-1], dp[i-1][j], dp[i][j-1])`
  - `dp[i-1][j-1] + 1` = **replace** `word1[i-1]` with `word2[j-1]` (align both strings' current characters at cost 1)
  - `dp[i-1][j] + 1` = **delete** `word1[i-1]` (match the first `i-1` chars of `word1` to all `j` chars of `word2`, then delete the extra)
  - `dp[i][j-1] + 1` = **insert** `word2[j-1]` into `word1` (match all `i` chars of `word1` to the first `j-1` chars of `word2`, then insert the missing char)

**Q13. What are the base cases for edit distance, and what do they represent semantically?**
A: `dp[0][j] = j` for all j: converting an empty string into the first `j` characters of `word2` requires exactly `j` insertions. `dp[i][0] = i` for all i: converting the first `i` characters of `word1` into an empty string requires exactly `i` deletions. These form the "zeroth row" and "zeroth column" of the table, representing the degenerate cases where one string is empty — always solvable by a sequence of pure insertions or pure deletions.

**Q14. Why is the edit distance recurrence's "no operation needed" case (`word1[i-1] === word2[j-1]` → `dp[i][j] = dp[i-1][j-1]`) correct, and why isn't it `dp[i-1][j-1] + 0` (which is the same thing, just more explicit)?**
A: When the current characters match, aligning them costs nothing — the problem reduces to "what's the edit distance of the remaining prefixes," which is exactly `dp[i-1][j-1]`. The `+0` formulation is mathematically identical and sometimes written explicitly to emphasize the parallel structure with the mismatch case's `1 + min(...)`. Either is correct; the cleaner `dp[i-1][j-1]` form is more commonly written in practice. The key correctness argument: if `word1[i-1] === word2[j-1]`, there's never any benefit to using an operation on these two characters — any sequence of operations that doesn't simply match them would be at least as costly, so the recurrence correctly doesn't even consider inserting/deleting/replacing when characters already match.

**Q15. How does the edit distance recurrence correspond geometrically to movements in the DP table?**
A: Each cell `dp[i][j]` depends on three neighbors:
- `dp[i-1][j-1]` (diagonal, up-left) → **match or replace** (consume one character from each string)
- `dp[i-1][j]` (above) → **delete** from `word1` (consume one character from `word1`, none from `word2`)
- `dp[i][j-1]` (left) → **insert** into `word1` (consume one character from `word2`, none from `word1`)

This geometric interpretation makes edit distance a natural grid-DP: filling the table top-to-bottom left-to-right ensures all three needed values are ready when computing each new cell, exactly analogous to the grid-traversal problems.

**Q16. How does the space-optimized O(n) edit distance work, and what extra variable is needed?**
A: Like other 2D DPs, edit distance only needs the current and previous row. The complication: when computing `dp[i][j]`, you need `dp[i-1][j-1]` (the diagonal), but if you've already updated `dp[j-1]` in-place for the current row, you've overwritten the old `dp[i-1][j-1]` value. The fix: save the old `dp[j-1]` value in a variable `prev` **before** overwriting it, and use `prev` wherever `dp[i-1][j-1]` is needed in the current cell's computation.

```js
function minDistance(word1, word2) {
  const m = word1.length, n = word2.length;
  let dp = Array.from({ length: n + 1 }, (_, j) => j); // base case: dp[0][j] = j

  for (let i = 1; i <= m; i++) {
    let prev = dp[0]; // save dp[i-1][0] before overwriting
    dp[0] = i;         // base case: dp[i][0] = i

    for (let j = 1; j <= n; j++) {
      const temp = dp[j]; // save dp[i-1][j] before it gets overwritten
      if (word1[i - 1] === word2[j - 1]) {
        dp[j] = prev;  // diagonal (match): dp[i-1][j-1]
      } else {
        dp[j] = 1 + Math.min(prev, dp[j], dp[j - 1]);
        // prev = dp[i-1][j-1] (replace), dp[j] = dp[i-1][j] (delete), dp[j-1] = dp[i][j-1] (insert)
      }
      prev = temp; // advance prev to dp[i-1][j] for the next column
    }
  }

  return dp[n];
}
```

### Section 5: Advanced Patterns & Extensions

**Q17. How does "Unique Paths with Obstacles" extend the standard recurrence?**
A: Add a check: if `obstacleGrid[i][j] === 1` (obstacle present), set `dp[i][j] = 0` (no paths through this cell). All other cells use the standard recurrence. Also handle the base case carefully: if the start or end cell itself is an obstacle, the answer is immediately 0. A subtlety in the first row and column: even though these normally have value 1 (single path), an obstacle in the first row or column "blocks" all subsequent cells in that row/column (since the only path to them passes through the obstacle) — the base-case fill must propagate this blocking, not just set all border cells to 1 unconditionally.

**Q18. What are common variants of Edit Distance, and how do they modify the recurrence?**
A:
- **Longest Common Subsequence (LCS)**: only deletions and insertions allowed (no replacements) — the recurrence when characters match is still `dp[i-1][j-1]`, but when they don't match, only the `delete`/`insert` moves are considered (no `dp[i-1][j-1]+1` replace option), so `dp[i][j] = Math.min(dp[i-1][j], dp[i][j-1])` on mismatch.
- **Longest Common Substring**: requires the match to be contiguous — `dp[i][j]` represents the longest common suffix ending at `word1[i]` and `word2[j]`, so on mismatch, `dp[i][j] = 0` (no extension), not the `min` of neighbors.
- **Edit Distance with custom operation costs**: if insert, delete, and replace have different costs, simply replace the `+ 1` in the recurrence with `+ insertCost`, `+ deleteCost`, `+ replaceCost` accordingly.
- **Edit Distance with only transpositions (Damerau-Levenshtein)**: adds a fourth operation (swap adjacent characters) with an additional DP state dimension to track transposition eligibility.

**Q19. How does "Maximum Subarray in a 2D Grid" (largest rectangle sum) extend the 2D DP ideas?**
A: Compute **column-wise prefix sums** to collapse each pair of rows into a 1D "bar heights" problem, then apply Kadane's algorithm (from the dedicated Kadane's guide) to find the maximum subarray sum of those bar heights — repeating for all O(m²) row pairs. This uses the same "fix one dimension, reduce to a 1D problem" insight that appears repeatedly across 2D DP problems, and directly reuses the 1D tool (Kadane's) as a building block for the 2D version — an important pattern to recognize beyond the three core problems here.

### Section 6: Scenario / Interview-Style Questions

**Q20. "You're asked to find the number of ways to reach the bottom-right of a grid. Your first instinct is recursion — walk me through why pure recursion is problematic and how DP fixes it."**
A: A pure recursive solution for a 3×3 grid would call `paths(2,2) → paths(1,2) + paths(2,1)`, then `paths(1,2) → paths(0,2) + paths(1,1)` and `paths(2,1) → paths(1,1) + paths(2,0)` — notice `paths(1,1)` is called twice. For larger grids, this explosion of redundant sub-calls grows exponentially. The DP table pre-fills every subproblem exactly once in a bottom-up order, so each result is computed once and reused — turning exponential time into O(m×n).

**Q21. "A product manager asks for the minimum-cost path through a cost grid for a routing algorithm. Walk through how you'd explain the DP approach to a non-technical stakeholder."**
A: "Imagine you're navigating a city grid where each block has a crossing cost. You want to reach the far corner with minimum total cost, moving only right or down. For each intersection, the cheapest way to get there is the cell's own cost plus whichever of the two intersections feeding into it (from above or from the left) was itself cheaper to reach. We precompute this for every intersection from top-left to bottom-right — each computation is just one comparison and one addition — and the answer is waiting in the final cell. The whole thing runs in time proportional to the number of intersections, not the number of routes (which grows exponentially)."

**Q22. "In the edit distance problem, what does a path through the DP table from `dp[0][0]` to `dp[m][n]` actually REPRESENT, and can you reconstruct the specific operations?"**
A: A path from `dp[0][0]` to `dp[m][n]` represents a specific **alignment** of the two strings — an explicit sequence of edit operations that transforms `word1` into `word2`. To reconstruct it: start at `dp[m][n]` and backtrack, at each cell checking which of the three neighbors was used to derive the current value — a diagonal step (from `dp[i-1][j-1]`) means a match (if characters were equal) or a replacement (if they differed); a step from above (`dp[i-1][j]`) means a deletion; a step from the left (`dp[i][j-1]`) means an insertion. Following these backward steps from `dp[m][n]` to `dp[0][0]` and reversing the sequence gives the actual operations. This backtracking adds O(m+n) time and O(m+n) space to record the path, beyond the O(m×n) DP table construction.

## Problem 1 — Unique Paths

### Problem
Given an `m x n` grid, count the number of distinct paths from the top-left corner to the bottom-right corner, moving only right or down.

```
Input:  m = 3, n = 7
Output: 28

Input:  m = 3, n = 2
Output: 3
```

### Pattern Recognition
2D DP on a grid — the number of paths to each cell depends on paths to exactly two predecessors (above and left), and each cell's answer must be computed before the cells that depend on it.

### Key Insight
The number of ways to reach `(i,j)` equals the number of ways to reach `(i-1,j)` plus the number of ways to reach `(i,j-1)` — every path to `(i,j)` came from exactly one of these two cells, so their counts sum exactly.

### Approach
Fill a 2D `dp` table of size `m × n`. Initialize the first row and first column to all 1s (only one path exists to any border cell). Fill the rest using `dp[i][j] = dp[i-1][j] + dp[i][j-1]`. Return `dp[m-1][n-1]`.

### Solution

```js
function uniquePaths(m, n) {
  // Build a full 2D table for clarity; space-optimized version follows
  const dp = Array.from({ length: m }, () => new Array(n).fill(1));
  // base case: first row and first column are already 1s by the fill above

  for (let i = 1; i < m; i++) {
    for (let j = 1; j < n; j++) {
      dp[i][j] = dp[i - 1][j] + dp[i][j - 1];
    }
  }

  return dp[m - 1][n - 1];
}

// Space-optimized O(n): use a single row, updated in place
function uniquePathsOptimized(m, n) {
  const dp = new Array(n).fill(1); // first row: all 1s

  for (let i = 1; i < m; i++) {
    for (let j = 1; j < n; j++) {
      dp[j] += dp[j - 1];
      // dp[j] was the "above" value before this update; dp[j-1] is already the current row's left value
    }
  }

  return dp[n - 1];
}
```

### Dry Run

```
m=3, n=3

Initialize dp (all 1s):
[1, 1, 1]
[1, 1, 1]
[1, 1, 1]

Fill non-border cells (i from 1..2, j from 1..2):
i=1, j=1: dp[1][1] = dp[0][1] + dp[1][0] = 1+1 = 2
i=1, j=2: dp[1][2] = dp[0][2] + dp[1][1] = 1+2 = 3
i=2, j=1: dp[2][1] = dp[1][1] + dp[2][0] = 2+1 = 3
i=2, j=2: dp[2][2] = dp[1][2] + dp[2][1] = 3+3 = 6

dp table:
[1, 1, 1]
[1, 2, 3]
[1, 3, 6]

Answer: dp[2][2] = 6 ✓
```

### Complexity
- Time: O(m × n) — fill every cell once with O(1) work per cell.
- Space: O(m × n) for the full table, or O(n) for the space-optimized single-row version.

### Edge Cases
- `m = 1` or `n = 1`: single row or single column — only one path exists (always move right, or always move down). The table is pre-filled with 1s, so the inner loop never executes and `dp[0][n-1]` or `dp[m-1][0]` correctly returns 1.
- `m = 1, n = 1`: single cell, answer is 1 (already at the destination).

### Follow-up Questions
- "What if some cells have obstacles?" → See Q17 — set `dp[i][j] = 0` for obstacle cells; base cases need to handle blocking propagation along edges.
- "Is there a closed-form formula?" → See Q6 — `C(m+n-2, m-1)`, but DP is more general and handles obstacles.

## Problem 2 — Minimum Path Sum

### Problem
Given an `m x n` grid filled with non-negative integers, find a path from the top-left to the bottom-right (moving only right or down) that minimizes the sum of all numbers along the path.

```
Input:
grid = [[1, 3, 1],
        [1, 5, 1],
        [4, 2, 1]]

Output: 7  (path 1→3→1→1→1 = 7)
```

### Pattern Recognition
2D DP on a weighted grid — same structural shape as Unique Paths (same state definition, same dependency pattern), but the recurrence aggregates by `min + current cost` instead of sum-of-counts.

### Key Insight
The minimum cost to reach `(i,j)` is the cell's own cost plus the minimum of the cheapest cost to reach either predecessor (above or left). Every cell's optimal value depends only on the optimal values of the two cells before it, so the table fills correctly in top-left to bottom-right order.

### Approach
Fill `dp` with base cases: `dp[0][0] = grid[0][0]`, first row accumulates leftward, first column accumulates upward. For the rest: `dp[i][j] = grid[i][j] + Math.min(dp[i-1][j], dp[i][j-1])`. Return `dp[m-1][n-1]`.

### Solution

```js
function minPathSum(grid) {
  const m = grid.length, n = grid[0].length;
  const dp = Array.from({ length: m }, () => new Array(n).fill(0));

  dp[0][0] = grid[0][0];

  // base case: first row (only reachable from the left)
  for (let j = 1; j < n; j++) {
    dp[0][j] = dp[0][j - 1] + grid[0][j];
  }

  // base case: first column (only reachable from above)
  for (let i = 1; i < m; i++) {
    dp[i][0] = dp[i - 1][0] + grid[i][0];
  }

  // fill the rest of the table
  for (let i = 1; i < m; i++) {
    for (let j = 1; j < n; j++) {
      dp[i][j] = grid[i][j] + Math.min(dp[i - 1][j], dp[i][j - 1]);
    }
  }

  return dp[m - 1][n - 1];
}
```

### Dry Run

```

        [1,5,1],
        [4,2,1]]

First col: dp[1][0]=1+1=2, dp[2][0]=2+4=6

dp[2][1] = 2 + min(dp[1][1]=7, dp[2][0]=6) = 2+6 = 8
dp[2][2] = 1 + min(dp[1][2]=6, dp[2][1]=8) = 1+6 = 7

dp[1][2]=6 came from dp[0][2]=5 (above, since 5<7).
dp[0][2]=5 came from dp[0][1]=4 (left). dp[0][1] from dp[0][0]=1.
Path: (0,0)→(0,1)→(0,2)→(1,2)→(2,2) → values 1+3+1+1+1=7 ✓
```

### Complexity
- Time: O(m × n).
- Space: O(m × n), reducible to O(n) with a single-row rolling array.

### Edge Cases
- 1×1 grid: answer is `grid[0][0]` directly.
- Single row: only rightward movement; dp is just a running sum of the row's values.
- Single column: only downward movement; dp is a running sum of the column's values.
- Grid with large values: standard integer arithmetic handles this; no special casing needed.

### Follow-up Questions
- "Can the path go up or left as well?" → Then it's no longer a DP problem in this form — it becomes a shortest-path problem on a graph, solved with Dijkstra's (since weights are non-negative).
- "Find the actual path, not just its cost?" → Backtrack through the filled `dp` table from `dp[m-1][n-1]`, at each cell choosing the predecessor with the smaller dp value, until reaching `dp[0][0]`.

## Problem 3 — Unique Paths II (With Obstacles)

### Problem
An `m x n` grid contains obstacles marked with `1` (blocked) and open cells marked with `0`. Count the number of distinct paths from the top-left to the bottom-right, moving only right or down, avoiding obstacles.

```
Input:
obstacleGrid = [[0,0,0],
                [0,1,0],
                [0,0,0]]

Output: 2
(obstacle at center blocks some paths; 2 paths remain: right→right→down→down and down→down→right→right)
```

### Pattern Recognition
Direct extension of Unique Paths — same recurrence, with an added early-zero for obstacle cells and careful base-case handling when obstacles appear along the first row or column.

### Key Insight
An obstacle cell contributes 0 paths — no path can pass through it. This means `dp[i][j] = 0` when `obstacleGrid[i][j] === 1`. More subtly, an obstacle in the first row or column "blocks" all subsequent cells in that row/column, since the only path to those cells passes through the obstacle.

### Approach
Initialize `dp[0][0] = 1` if not an obstacle, else `0`. Fill the first row: `dp[0][j] = obstacleGrid[0][j] === 1 ? 0 : dp[0][j-1]` (blocked cells and everything after them in the row get 0). Similarly for the first column. Fill interior: if obstacle, 0; otherwise standard recurrence.

### Solution

```js
function uniquePathsWithObstacles(obstacleGrid) {
  const m = obstacleGrid.length, n = obstacleGrid[0].length;
  const dp = Array.from({ length: m }, () => new Array(n).fill(0));

  // start cell
  dp[0][0] = obstacleGrid[0][0] === 1 ? 0 : 1;

  // first row: blocked at obstacle and beyond
  for (let j = 1; j < n; j++) {
    dp[0][j] = obstacleGrid[0][j] === 1 ? 0 : dp[0][j - 1];
  }

  // first column: blocked at obstacle and beyond
  for (let i = 1; i < m; i++) {
    dp[i][0] = obstacleGrid[i][0] === 1 ? 0 : dp[i - 1][0];
  }

  // fill interior
  for (let i = 1; i < m; i++) {
    for (let j = 1; j < n; j++) {
      if (obstacleGrid[i][j] === 1) {
        dp[i][j] = 0;
      } else {
        dp[i][j] = dp[i - 1][j] + dp[i][j - 1];
      }
    }
  }

  return dp[m - 1][n - 1];
}
```

### Dry Run

```
obstacleGrid = [[0,0,0],
                [0,1,0],
                [0,0,0]]

dp[0][0]=1 (no obstacle at start)

First row: j=1: no obs→dp[0][1]=dp[0][0]=1; j=2: no obs→dp[0][2]=dp[0][1]=1
  dp[0] = [1,1,1]

First col: i=1: no obs→dp[1][0]=dp[0][0]=1; i=2: no obs→dp[2][0]=dp[1][0]=1
  dp[i][0] = [1,1,1] (column values)

Interior:
dp[1][1]: obstacleGrid[1][1]=1 → dp[1][1]=0
dp[1][2]: no obs → dp[0][2]+dp[1][1]=1+0=1
dp[2][1]: no obs → dp[1][1]+dp[2][0]=0+1=1
dp[2][2]: no obs → dp[1][2]+dp[2][1]=1+1=2

dp table:
[1, 1, 1]
[1, 0, 1]
[1, 1, 2]

Answer: dp[2][2] = 2 ✓
```

### Complexity
- Time: O(m × n).
- Space: O(m × n), reducible to O(n).

### Edge Cases
- Obstacle at the start `(0,0)`: answer is 0 — no paths can begin.
- Obstacle at the end `(m-1,n-1)`: answer is 0 — no paths can finish.
- Obstacle in the first row at position `(0,k)`: all cells `(0,j)` for `j ≥ k` get `dp=0`, correctly blocking the row beyond the obstacle.
- No obstacles: reduces exactly to the standard Unique Paths problem.

### Follow-up Questions
- "What's the maximum number of obstacles that can exist while still allowing at least one path?" → Problem-specific reasoning; could vary greatly depending on obstacle placement. With `m+n-2` cells on the optimal diagonal path, any obstacle on ALL possible paths (a hard combinatorial question) blocks the answer to 0.

## Problem 4 — Edit Distance (Full Implementation)

### Problem
Given two strings `word1` and `word2`, return the minimum number of operations (insert, delete, replace) required to convert `word1` to `word2`.

```
Input:  word1 = "horse", word2 = "ros"
Output: 3

Input:  word1 = "intention", word2 = "execution"
Output: 5
```

### Pattern Recognition
2D DP over two string lengths — `dp[i][j]` encodes the subproblem for the first `i` chars of `word1` and first `j` chars of `word2`, with three operations corresponding to three predecessor cells (diagonal, above, left).

### Key Insight
When characters match, no operation is needed and the cost equals the already-computed diagonal `dp[i-1][j-1]`. When they differ, take the minimum of three options (replace via diagonal, delete via above, insert via left) and add 1. The table fills naturally top-to-bottom left-to-right since every cell only needs these three already-computed predecessors.

### Approach
Build an `(m+1) × (n+1)` table (the +1 accounts for the empty-string base cases). Fill row 0 with `j` and column 0 with `i`. Fill the rest using the full recurrence. Return `dp[m][n]`.

### Solution

```js
function minDistance(word1, word2) {
  const m = word1.length, n = word2.length;

  // dp[i][j] = min operations to convert word1[0..i-1] to word2[0..j-1]
  const dp = Array.from({ length: m + 1 }, (_, i) =>
    Array.from({ length: n + 1 }, (_, j) => (i === 0 ? j : j === 0 ? i : 0))
  );
  // base cases: dp[0][j]=j (insert j chars), dp[i][0]=i (delete i chars)

  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (word1[i - 1] === word2[j - 1]) {
        dp[i][j] = dp[i - 1][j - 1]; // characters match: no operation needed
      } else {
        dp[i][j] = 1 + Math.min(
          dp[i - 1][j - 1], // replace: align current chars at cost 1
          dp[i - 1][j],     // delete: remove word1[i-1] at cost 1
          dp[i][j - 1]      // insert: add word2[j-1] to word1 at cost 1
        );
      }
    }
  }

  return dp[m][n];
}
```

### Complexity
- Time: O(m × n) — filling every cell of the `(m+1) × (n+1)` table.
- Space: O(m × n) for the full table, reducible to O(n) with the rolling-row technique (Q16).

### Edge Cases
- Either string empty: answer equals the other string's length (pure insertions or deletions).
- Identical strings: no operations needed; every character matches and `dp[i][j] = dp[i-1][j-1]` for all cells, producing `dp[m][n] = 0`.
- Strings with no common characters: every mismatch uses a replacement or insert/delete — the minimum cost approaches `max(m,n)` in the worst case.
- Single-character strings: 0 if equal, 1 if different (one replace operation).

### Follow-up Questions
- "Reconstruct the actual sequence of operations, not just the count?" → See Q22 — backtrack through the dp table, at each step identifying which predecessor was used (diagonal → match/replace, above → delete, left → insert), then reverse the collected operations.
- "How does the space-optimized version work?" → See Q16 — single-row array with a `prev` variable tracking the diagonal value.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve counting, minimizing, or maximizing over structured traversals of a grid or two sequences?
│
├── GRID NAVIGATION (move right/down from top-left to bottom-right)?
│   ├── COUNT distinct paths → Unique Paths
│   │   dp[i][j] = dp[i-1][j] + dp[i][j-1],  base cases all 1s
│   │
│   ├── MINIMIZE total path cost → Minimum Path Sum
│   │   dp[i][j] = grid[i][j] + min(dp[i-1][j], dp[i][j-1]),  base cases accumulate
│   │
│   └── SAME but with OBSTACLES → set dp[i][j]=0 at obstacle cells;
│         propagate blocking along first row/column base cases
│
├── STRING ALIGNMENT / TRANSFORMATION (two sequences)?
│   ├── MINIMUM OPERATIONS to transform one string into another → Edit Distance
│   │   Match: dp[i][j] = dp[i-1][j-1]
│   │   Mismatch: dp[i][j] = 1 + min(dp[i-1][j-1], dp[i-1][j], dp[i][j-1])
│   │   Base cases: dp[0][j]=j, dp[i][0]=i
│   │
│   ├── LONGEST COMMON SUBSEQUENCE → restrict Edit Distance recurrence
│   │   (remove the replace option on mismatch; min of delete/insert only)
│   │
│   └── LONGEST COMMON SUBSTRING → contiguous match, dp[i][j]=0 on mismatch
│
├── SPACE OPTIMIZATION for any 2D DP?
│   └── If dp[i][j] only needs previous row and current row:
│       → Reduce to O(n) single-row array, updating left-to-right
│       → For Edit Distance: save the diagonal with a `prev` variable before overwriting
│
└── RECONSTRUCT THE ACTUAL PATH/OPERATIONS (not just the optimal value)?
    └── Backtrack through the filled dp table from dp[m][n] to dp[0][0],
        at each cell following the predecessor used to derive the current value
```

## Common Bugs Checklist

Before submitting any 2D DP solution, verify:

1. **Base cases fill the ENTIRE first row and first column, not just `dp[0][0]`?** — For Minimum Path Sum, the first row and column must accumulate the grid values along their entire length; leaving them at 0 causes every interior cell that references them to compute incorrect minimums. For Unique Paths, the entire first row/column must be 1.

2. **Edit Distance: table is `(m+1) × (n+1)`, not `m × n`?** — The extra row and column represent the empty-string base cases (converting to/from an empty string); using `m × n` shifts all indices by one and either causes out-of-bounds or silently produces wrong answers.

3. **Edit Distance: `word1[i-1]` and `word2[j-1]` (not `word1[i]` and `word2[j]`) compared in the recurrence?** — Since `i` and `j` are 1-indexed in the DP table (to accommodate the empty-string base cases), the actual characters at position `i` in `word1` are at index `i-1`; using `i` instead silently goes out-of-bounds or compares wrong characters.

4. **Space-optimized version: `prev` variable correctly saved BEFORE the current `dp[j]` is overwritten?** — In the rolling-row Edit Distance, the diagonal value `dp[i-1][j-1]` lives at `dp[j-1]` before the column-j update — `prev` must be set to the OLD `dp[j]` (which holds `dp[i-1][j]`) before the j-th cell is computed, and then prev updated to `temp` (the old `dp[j]`) for the next column.

5. **Unique Paths with obstacles: first row/column base cases stop propagating after an obstacle?** — `dp[0][j] = obstacleGrid[0][j] === 1 ? 0 : dp[0][j-1]` is correct; naively setting all border cells to 1 (as in the obstacle-free version) silently overcounts paths that pass through border obstacles.

6. **Fill ORDER is correct — cells computed AFTER all their dependencies?** — Top-to-bottom, left-to-right is the standard correct order for these three recurrences (each cell depends on `dp[i-1][j]` (above) and `dp[i][j-1]` (left), both of which are filled before `(i,j)` in this order). Any deviation from this order (e.g., column-major order without adjusting which direction to process) produces incorrect results.

7. **Answer extracted from the correct cell?** — For all three problems (and their variants), the answer is at `dp[m-1][n-1]` (for 0-indexed m×n grids) or `dp[m][n]` (for 1-indexed (m+1)×(n+1) tables like Edit Distance) — mixing these up by one is a common off-by-one error.

---

**Final Tip:** At the 5 YOE level, interviewers expect three things from a 2D DP answer: (1) a clear, precise statement of what `dp[i][j]` represents before any code is written — this is the single most important sentence in the solution, since everything else follows from it; (2) a correct recurrence with all three cases for Edit Distance (match, mismatch-replace, mismatch-insert/delete) — memorizing the three arrows (diagonal, above, left) and their corresponding operations (replace/match, delete, insert) makes this mechanical; and (3) proactively mentioning the space optimization (O(n) rolling row) even if not asked — it demonstrates awareness that the O(m×n) table is a design choice, not an immovable constraint. The ability to explain WHY each recurrence case is correct (not just what it computes) is what separates a thorough answer from a memorized one.
