## Topic A: Recursive Tree Thinking & Traversal Orders

### Section A1: Fundamentals

**Q1. What is the fundamental recursive structure of a binary tree, and how does it shape every tree algorithm?**

A: A binary tree is defined recursively: it is either null (empty), or a root node with a *left subtree* (binary tree) and a *right subtree* (binary tree). Every algorithm on a binary tree mirrors this recursive self-similarity — process the root, then recurse into the left subtree, then recurse into the right subtree. The only variable across tree algorithms is *when* the root is processed relative to its children, which defines the traversal order. This recursive decomposition is not just a convenient technique — it is a direct reflection of the data structure's definition.

```
A binary tree IS:
  null
  OR { val, left: BinaryTree, right: BinaryTree }

Every tree function IS:
  base_case(null)
  OR { process(root), recurse(root.left), recurse(root.right) }

The order of the three steps defines the traversal:
  Pre-order:   process → left → right
  In-order:    left → process → right
  Post-order:  left → right → process
```

**Q2. What are the three DFS traversal orders, and which class of problems does each serve?**

A: The three orders differ only in when the root is processed relative to its children — but this timing difference has large consequences for what information is available at each step:

**Pre-order (root → left → right)**: the root is processed before any subtree information is known. Use when: building the problem state as you travel *down* (accumulating path sums, tree serialization, making decisions based on ancestor values). The value at the current node is "handed down" to children.

**In-order (left → root → right)**: the left subtree is fully processed before the root. For BSTs specifically, in-order traversal produces nodes in sorted ascending order — making it the canonical BST traversal for kth-smallest, BST validation, and sorted output.

**Post-order (left → right → root)**: both subtrees are fully processed before the root. Use when: computing a property that depends on children's results (height, balance, diameter, tree deletion). Children "hand up" their results to the parent.

```
Tree:      1
          / \
         2   3

Pre-order:   1, 2, 3    (root before children — top-down)
In-order:    2, 1, 3    (left, then root, then right)
Post-order:  2, 3, 1    (children before root — bottom-up)

Height problem needs post-order:
  height(2) = 1, height(3) = 1  →  height(1) = max(1,1)+1 = 2
  Children computed first, parent uses results.
```

**Q3. What is the "top-down vs bottom-up" recursion pattern for trees, and what does each compute?**

A: Top-down (pre-order style): information flows *from parent to children* — the function receives state from its caller and uses it to make decisions or accumulate results at the current node. Examples: path sum (carry running total downward), symmetric tree check (carry mirror-pair of nodes downward), tree serialization.

Bottom-up (post-order style): information flows *from children to parent* — the function computes and returns a value to its caller that the caller uses to compute its own result. Examples: height, balance, diameter, subtree sum. The key: you cannot compute the parent's result until both children's results are available — forcing post-order.

```
Top-down (path sum to leaf):
  hasPathSum(node, remaining):
    if null: return remaining == 0
    return hasPathSum(left, remaining - val) OR hasPathSum(right, remaining - val)
  Parent passes (remaining - val) DOWN to children.

Bottom-up (height):
  height(node):
    if null: return 0
    leftH = height(left)    // wait for left child's result
    rightH = height(right)  // wait for right child's result
    return max(leftH, rightH) + 1  // combine and return UP to parent
```

**Q4. What are the null-handling rules for tree recursion, and in what order must they be checked?**

A: Null handling is the first thing checked in every tree recursive function — before any value access, before any child traversal. The canonical three-case pattern:

1. **Both null → return the "vacuously true" or base result**: two null nodes match structurally; an empty tree has height 0; no path sum needed for a null node.
2. **Exactly one null → return the "mismatch" result**: one tree has a node where the other doesn't — a structural difference. Return false for comparison problems, or handle appropriately for measurement problems.
3. **Both non-null → check values then recurse**: only reach value comparison after confirming both nodes exist.

Skipping step 1 or 2 causes null-pointer exceptions when accessing `.val` or `.left/.right` on a null node. The order is mandatory: null-safety before value access, always.

```js
// Canonical null-handling pattern for two-tree comparison:
function compare(p, q) {
  if (p === null && q === null) return true;   // (1) both null — match
  if (p === null || q === null) return false;  // (2) one null — mismatch
  // (3) both non-null — safe to access .val and recurse
  return p.val === q.val && compare(p.left, q.left) && compare(p.right, q.right);
}

// Canonical null-handling for single-tree measurement:
function height(node) {
  if (node === null) return 0; // base case: null has height 0
  // safe to access node.left and node.right
  return Math.max(height(node.left), height(node.right)) + 1;
}
```

### Section A2: Advanced Patterns

**Q5. What is the "mirror-pair recursion" pattern that unifies Symmetric Tree and Same Tree?**

A: Both problems check whether two subtrees satisfy a structural and value relationship — the only difference is which children are compared. The pattern: pass a *pair* of nodes `(p, q)` into the recursive function; check null handling for the pair; check `p.val === q.val`; then recurse on the pair's children in the problem-specific order.

- **Same Tree**: children compared in the *same* order — `(p.left, q.left)` and `(p.right, q.right)`. "Does p's left child match q's left child, and p's right match q's right?"
- **Symmetric Tree**: children compared in *mirror* order — `(p.left, q.right)` and `(p.right, q.left)`. "Does p's left child mirror q's right child, and p's right mirror q's left?"

The only structural difference between the two complete algorithms is two variable names in the recursive calls. This is not coincidental — both reduce to "are these two subtrees in the required relationship?", differing only in what "required relationship" means.

```js
// Same Tree: same-order children
isSameTree(p.left, q.left) && isSameTree(p.right, q.right)

// Symmetric Tree: mirror-order children
isMirror(p.left, q.right) && isMirror(p.right, q.left)
//              ↑    ↑                         ↑    ↑
//         outer     inner                 inner     outer
```

**Q6. What is the "global variable + local return value" pattern, and which tree problems require it?**

A: Some bottom-up problems need to compute *two different values simultaneously* at each node: a local value returned to the parent (so the parent can compute its own result), and a global answer that is the maximum/minimum across all nodes. These two values are of different types or serve different purposes — they cannot both be the return value.

The pattern: use a closure variable or class variable as `globalMax`. Each recursive call (1) computes local values from children, (2) updates `globalMax` using the local values, (3) returns the value the parent needs (not the answer).

The canonical example is Diameter: each node returns its HEIGHT to the parent (for parent's diameter), but updates `globalMax = max(globalMax, leftH + rightH)` as the diameter through this node. Without the global, you'd have to choose: return height (parent needs it) or return diameter (the answer) — you cannot return both from a single value.

```js
// Diameter: needs both HEIGHT (for parent) and local DIAMETER (for global answer)
let maxDiameter = 0;  // global answer

function height(node) {
  if (node === null) return 0;
  const leftH  = height(node.left);
  const rightH = height(node.right);

  maxDiameter = Math.max(maxDiameter, leftH + rightH); // update global answer

  return Math.max(leftH, rightH) + 1; // return HEIGHT to parent (not diameter)
}
```

**Q7. What is the "sentinel return value" pattern for early-exit bottom-up problems?**

A: Some bottom-up problems short-circuit as soon as a violation is detected — there is no need to continue computing once the answer is known to be false/invalid. The sentinel pattern uses a special return value (typically `-1`) to signal "this subtree is already invalid." The parent, on receiving `-1` from either child, immediately propagates `-1` upward without further computation.

This is the key optimization in Balanced Binary Tree: if `height()` returns -1 (unbalanced), every ancestor immediately returns -1 without computing heights. Without the sentinel, the naive approach re-computes height from scratch at every node to check balance — O(n log n). With the sentinel, each node is visited once and balance is checked in the same pass — O(n).

```js
// Sentinel pattern for balanced tree:
function checkHeight(node) {
  if (node === null) return 0;

  const leftH = checkHeight(node.left);
  if (leftH === -1) return -1;  // early exit: left subtree already unbalanced

  const rightH = checkHeight(node.right);
  if (rightH === -1) return -1; // early exit: right subtree already unbalanced

  if (Math.abs(leftH - rightH) > 1) return -1; // this node is unbalanced

  return Math.max(leftH, rightH) + 1; // normal: return height
}
// -1 is the sentinel: "somewhere below here is unbalanced; stop computing"
```

## Topic B: BFS vs DFS for Tree Problems

### Section B1: Fundamentals

**Q8. When should you use BFS (level-order traversal) over DFS for tree problems?**

A: The deciding factor is whether the problem's structure is *level-based* or *path-based*:

**Use BFS when**: the answer depends on level-by-level processing (right side view, zigzag level order, level averages, connect next-right pointers); when the answer is expected near the root (minimum depth — BFS finds the first leaf, DFS must explore all paths); when the problem explicitly mentions "level" or "row."

**Use DFS when**: the answer involves root-to-leaf paths (path sum, all paths); structural properties computed bottom-up (height, balance, diameter); structural comparisons (symmetric, same tree — both have natural recursive decompositions); when the call stack naturally mirrors the tree structure.

The right side view is the canonical BFS-vs-DFS decision: BFS processes nodes level by level, so the last node at each level is naturally the rightmost visible node. DFS can also solve it, but requires tracking the first node visited at each depth in a right-first traversal.

```
Problems best solved with BFS:
  Level order traversal, zigzag traversal, right side view,
  connect next-right pointers, minimum depth, average at each level.

Problems best solved with DFS:
  Path sum, all root-to-leaf paths, tree height, diameter,
  symmetric tree, same tree, invert tree, balanced tree check.
```

**Q9. What is the "pair-based BFS" pattern for iterative tree comparison problems?**

A: The recursive mirror-pair pattern (Q5) has a direct iterative BFS equivalent: instead of queuing single nodes, queue *pairs* of nodes `(p, q)` that should satisfy the comparison relationship. Dequeue a pair, perform the null check and value check, then enqueue the pair's children in the problem-specific order. This avoids the call stack entirely and is preferred when the tree may be very deep (call stack overflow risk).

```js
// Iterative pair-based BFS for Symmetric Tree:
function isSymmetric(root) {
  const queue = [[root.left, root.right]]; // queue of pairs

  while (queue.length > 0) {
    const [left, right] = queue.shift();

    if (left === null && right === null) continue; // both null: OK
    if (left === null || right === null) return false; // one null: mismatch
    if (left.val !== right.val) return false; // value mismatch

    // Enqueue children in MIRROR order:
    queue.push([left.left, right.right]); // outer pair
    queue.push([left.right, right.left]); // inner pair
  }

  return true;
}
```

**Q10. What is the height vs depth distinction, and which does each tree problem actually compute?**

A: **Depth** of a node: number of edges from the root DOWN to the node. Root depth = 0. Computed top-down (pass depth as a parameter from parent to child). **Height** of a node: number of edges from the node UP to its farthest descendant leaf. Leaf height = 0. Computed bottom-up (children report their heights; parent = max(children heights) + 1).

Maximum Depth of Binary Tree (LeetCode 104) is confusingly named — it asks for the number of nodes on the longest root-to-leaf path, which equals the *height of the root + 1* (using a convention where height counts nodes, not edges). The "depth" in the problem title refers to the length of the path, but the computation is a bottom-up height calculation. Understanding this prevents confusion about which traversal order to use.

```
Tree:   1
       / \
      2   3
     / \
    4   5

Depth of node 4 = 2  (root→2→4, two edges from root, counted top-down)
Height of node 4 = 0  (leaf, counted bottom-up)
Height of node 2 = 1  (max(height(4), height(5)) + 1 = 0+1 = 1)
Height of node 1 = 2  (max(height(2), height(3)) + 1 = 1+1 = 2)

"Maximum depth" of this tree = 3 (nodes: 1→2→4) = height(root) + 1 = 2+1 = 3
LeetCode's definition counts NODES; mathematical height counts EDGES.
```

### Section B2: Advanced Patterns

**Q11. Why does the right side view problem have both a clean BFS and a clean DFS solution, and when does each apply?**

A: **BFS solution**: process level by level; the last element of each level's queue is the rightmost visible node. Natural — no extra bookkeeping beyond the standard BFS loop. One result per level. **DFS solution (right-first pre-order)**: visit root, then right child, then left child. Maintain a `result` array where `result[depth]` holds the rightmost node seen at that depth. Since right children are visited before left children, the first node visited at each depth is always the rightmost. Condition: `if (depth === result.length) result.push(node.val)` — add to `result` only when visiting a depth for the first time (which is always the rightmost node in right-first DFS).

BFS applies when you also need the full level contents (level order, averages). DFS applies when you need right-side (or left-side) views and want to avoid the O(k) queue memory at each level.

**Q12. How does iterative DFS using an explicit stack relate to recursive DFS, and when do you need it?**

A: Every recursive DFS implicitly uses the call stack. An iterative DFS replaces the call stack with an explicit stack: `stack.push(root)`; while stack non-empty: `node = stack.pop()`; process node; `stack.push(node.right)` then `stack.push(node.left)` (right first so left is processed first after popping — pre-order). The explicit stack is necessary when: (1) the tree can be very deep (skewed tree with n=10,000 nodes causes O(n) call stack depth, risking stack overflow); (2) the language has a small default stack size; (3) the interviewer explicitly asks for an iterative solution.

```js
// Iterative pre-order DFS:
function preorderIterative(root) {
  if (!root) return [];
  const stack = [root], result = [];
  while (stack.length) {
    const node = stack.pop();
    result.push(node.val);
    if (node.right) stack.push(node.right); // right pushed first
    if (node.left)  stack.push(node.left);  // left pushed second → processed first
  }
  return result;
}
// Right is pushed before left because stack is LIFO:
// pushing right first means left is popped first → pre-order: root, left, right ✓
```

## Topic C: Cross-Topic & Interview-Style Questions

**Q13. "Walk through your thought process when you first see a binary tree problem."**

A: Five diagnostic questions, answered in order:

1. **DFS or BFS?** — Level-based or path-based? (See Q8.) Most structural problems → DFS. Level-order/visibility → BFS.
2. **Which traversal order?** — Top-down (pre-order) or bottom-up (post-order)? Does the answer require children's results first? → Post-order. Does the answer require ancestor information passed down? → Pre-order.
3. **Recursive or iterative?** — Is tree depth bounded? Can the call stack hold O(h) frames? For most interviews, recursive is acceptable and preferred for clarity. Mention iterative alternative if asked.
4. **What does the recursive call return?** — Boolean (symmetric, same tree, balanced)? Integer (height, depth, diameter's local value)? Void (when updating a global)? Being explicit about the return type forces clear thinking about the function's contract.
5. **What are the base cases?** — Null node handling (Q4): both null, one null, both non-null. State the null checks *before* writing the recursive case.

**Q14. "What is the time and space complexity of a binary tree recursive traversal?"**

A: Time: O(n) — every recursive tree algorithm visits each node exactly once. Space: O(h) for the call stack, where h is the tree height. In the best case (balanced tree), h = O(log n). In the worst case (completely skewed linear chain), h = O(n). For BFS, space is O(w) where w is the maximum tree width — O(n/2) = O(n) for a complete tree at the last level. In practice: recursive DFS uses O(h) call stack space; BFS uses O(w) queue space; iterative DFS uses O(h) explicit stack space.

**Q15. In one sentence each, state the key invariant or return contract for each tree problem in this document.**

A:
- **Symmetric Tree**: returns true iff `(left, right)` are mirrors — same value, left's left mirrors right's right, left's right mirrors right's left.
- **Same Tree**: returns true iff `(p, q)` are structurally identical with equal values at every corresponding position.
- **Invert Binary Tree**: returns the root after recursively swapping left and right children at every node.
- **Maximum Depth**: returns the number of nodes on the longest root-to-leaf path — `max(depth(left), depth(right)) + 1`.
- **Balanced Binary Tree**: returns the subtree height (≥ 0) if balanced, or -1 as a sentinel if any ancestor is unbalanced — the sentinel propagates instantly up the call stack.
- **Diameter of Binary Tree**: returns the subtree height to the parent while updating a global maximum of `leftH + rightH` — height serves the parent's computation; the global serves the final answer.
- **Binary Tree Right Side View**: records the first node visited at each depth in right-first DFS, or the last node at each BFS level — the rightmost node visible from the right.

## Problem 1 — Symmetric Tree

### Problem
Given the root of a binary tree, check whether it is a mirror of itself (i.e., symmetric around its center).

```
Input:
    1
   / \
  2   2
 / \ / \
3  4 4  3
Output: true

Input:
    1
   / \
  2   2
   \   \
    3    3
Output: false
```

### Pattern Recognition
Mirror-pair recursion — reduce to checking whether `root.left` and `root.right` are mirrors of each other. Mirror check: two nodes are mirrors iff they have equal values AND their children are cross-mirrors (left's left mirrors right's right; left's right mirrors right's left).

### Key Insight
Symmetry is a *pairwise* property between the left and right subtrees — not a property of individual subtrees. The recursive function takes a *pair* of nodes `(left, right)` and checks if they form a mirror. The children are paired in *crossed* order: `(left.left, right.right)` and `(left.right, right.left)` — this is what "mirror" means structurally.

### Approach
Define `isMirror(left, right)`. Base cases: both null → true; one null → false. Recursive case: `left.val === right.val && isMirror(left.left, right.right) && isMirror(left.right, right.left)`. Call `isMirror(root.left, root.right)`.

### Solution

```js
function isSymmetric(root) {
  // A single-node tree (or null) is always symmetric
  if (!root) return true;
  return isMirror(root.left, root.right);
}

function isMirror(left, right) {
  // Base case 1: both null — symmetric vacuously
  if (left === null && right === null) return true;

  // Base case 2: one null — structural mismatch
  if (left === null || right === null) return false;

  // Recursive case: values must match AND children must be cross-mirrors
  return (
    left.val === right.val &&
    isMirror(left.left, right.right) &&  // outer pair: left's left vs right's right
    isMirror(left.right, right.left)     // inner pair: left's right vs right's left
  );
}

// ---
// Iterative version using a queue of pairs:
function isSymmetricIterative(root) {
  if (!root) return true;
  const queue = [[root.left, root.right]];

  while (queue.length > 0) {
    const [left, right] = queue.shift();

    if (left === null && right === null) continue;
    if (left === null || right === null) return false;
    if (left.val !== right.val) return false;

    queue.push([left.left, right.right]); // outer pair for next level
    queue.push([left.right, right.left]); // inner pair for next level
  }

  return true;
}
```

### Dry Run

```
Tree:      1
          / \
         2   2
        / \ / \
       3  4 4  3

isSymmetric(root=1):
  isMirror(left=2, right=2):
    both non-null. 2 === 2 ✓
    isMirror(left.left=3, right.right=3):
      both non-null. 3 === 3 ✓
      isMirror(3.left=null, 3.right=null) → both null → true
      isMirror(3.right=null, 3.left=null) → both null → true
      return true ✓
    isMirror(left.right=4, right.left=4):
      both non-null. 4 === 4 ✓
      isMirror(4.left=null, 4.right=null) → true
      isMirror(4.right=null, 4.left=null) → true
      return true ✓
    return true && true && true = true ✓

Output: true ✓

---
Tree:      1
          / \
         2   2
          \   \
           3    3

isMirror(left=2, right=2):
  2 === 2 ✓
  isMirror(left.left=null, right.right=3):
    left=null, right=3: ONE NULL → return false ✗

Output: false ✓
(Left subtree has no left child where right subtree has a right child — asymmetric)
```

### Complexity
- Time: O(n) — every node is visited exactly once (each node appears in exactly one mirror-pair call).
- Space: O(h) — call stack depth equals tree height h. O(log n) for balanced, O(n) for skewed.

### Edge Cases
- **Single node**: `root.left` and `root.right` are both null → `isMirror(null, null)` → both null → true.
- **Root with one child only**: `root.left = node`, `root.right = null` → `isMirror(node, null)` → one null → false.
- **All same values**: `[1,1,1,1,1,1,1]` — value check always passes; structure determines the result.
- **Values match but structure doesn't** (the second example above): caught by the null check on one side before value comparison.

### Follow-up Questions
- "Iterative version?" — Shown above: queue of pairs; same logic, no call stack.
- "If the tree is very deep (10,000 nodes in a chain), does the recursive version fail?" — Yes: the call stack depth equals the tree height; a linear chain causes O(n) call depth, potentially causing a stack overflow. Use the iterative version for production or for very deep trees.
- "What if node values are objects instead of integers?" — Replace `left.val === right.val` with a deep equality check specific to the object type.

## Problem 2 — Same Tree

### Problem
Given the roots of two binary trees `p` and `q`, write a function to check if they are the same. Two binary trees are the same if they are structurally identical and the nodes have the same values.

```
Input:  p = [1,2,3], q = [1,2,3]   → true
Input:  p = [1,2],   q = [1,null,2] → false
Input:  p = [1,2,1], q = [1,1,2]   → false
```

### Pattern Recognition
Mirror-pair recursion with same-order children — identical structure to Symmetric Tree but children are paired in the same order: `(p.left, q.left)` and `(p.right, q.right)` instead of the crossed order used for symmetry.

### Key Insight
Same Tree is the "base algorithm" that Symmetric Tree's `isMirror` function is a variant of. Same Tree checks: "are these two trees identical?" Symmetric Tree checks: "are these two trees mirrors?" The recursive structure is exactly the same; only the child pairing changes.

### Approach
`isSameTree(p, q)`: both null → true; one null → false; `p.val !== q.val` → false; recurse `isSameTree(p.left, q.left) && isSameTree(p.right, q.right)`.

### Solution

```js
function isSameTree(p, q) {
  // Both null: structurally identical at this position
  if (p === null && q === null) return true;

  // One null: structural mismatch
  if (p === null || q === null) return false;

  // Value mismatch
  if (p.val !== q.val) return false;

  // Recurse on same-order children (NOT crossed — that would be isMirror)
  return isSameTree(p.left, q.left) && isSameTree(p.right, q.right);
}
```

### Dry Run

```
p:   1       q:   1
    / \           / \
   2   3         2   3

isSameTree(1p, 1q): both non-null. 1===1 ✓
  isSameTree(2p, 2q): both non-null. 2===2 ✓
    isSameTree(null, null) → true
    isSameTree(null, null) → true
    return true
  isSameTree(3p, 3q): both non-null. 3===3 ✓
    isSameTree(null, null) → true
    isSameTree(null, null) → true
    return true
  return true && true = true ✓

---
p:   1       q:   1
    /               \
   2                 2

isSameTree(1p, 1q): 1===1 ✓
  isSameTree(2p, null): p=2, q=null → ONE NULL → return false ✗

Output: false ✓
```

### Complexity
- Time: O(min(n, m)) where n, m are the sizes of the two trees — we stop at the first mismatch.
- Space: O(min(h1, h2)) — call stack depth.

### Edge Cases
- **Both empty trees**: both roots null → `isSameTree(null, null)` → true. Two empty trees are the same.
- **One empty, one not**: `isSameTree(null, node)` → one null → false.
- **Structurally same, values differ**: reaches the `p.val !== q.val` check; returns false immediately without recursing further.
- **Subtree check**: LeetCode 572 "Subtree of Another Tree" uses this function: for each node in the main tree, call `isSameTree(node, subRoot)`. If any call returns true, the subtree exists.

### Follow-up Questions
- "Check if tree T is a subtree of tree S?" — For each node in S, call `isSameTree(node, T)`. O(n × m) time where n=|S|, m=|T|. More efficient: serialize both trees (including null markers) and use string search — O(n + m).
- "Leaf-similar trees (same leaf sequence)?" — Collect leaves of both trees via DFS into arrays; compare the arrays. Different structural property than same-tree, but both use DFS.

## Problem 3 — Invert Binary Tree

### Problem
Given the root of a binary tree, invert the tree and return its root.

```
Input:
    4
   / \
  2   7
 / \ / \
1  3 6  9

Output:
    4
   / \
  7   2
 / \ / \
9  6 3  1
```

### Pattern Recognition
Post-order DFS (bottom-up) — invert the left and right subtrees recursively, then swap the root's left and right children. Works with pre-order too, but post-order more clearly reflects "bottom-up inversion."

### Key Insight
Inverting a tree means: at every node, swap its left and right children. The recursive structure: invert the left subtree (making it the mirror of the original left), invert the right subtree, then swap them. After this, the left child is the inverted original-right subtree and vice versa — exactly the mirror of the original tree.

### Approach
`invertTree(node)`: if null, return null. Recurse on both children first (post-order). Swap `node.left` and `node.right`. Return `node`.

### Solution

```js
function invertTree(root) {
  // Base case: null node — nothing to invert
  if (root === null) return null;

  // Post-order: invert subtrees first, then swap at current level
  const left  = invertTree(root.left);  // fully inverted left subtree
  const right = invertTree(root.right); // fully inverted right subtree

  // Swap: inverted left becomes new right, inverted right becomes new left
  root.left  = right;
  root.right = left;

  return root; // root's value unchanged; its subtrees are now swapped
}

// Pre-order alternative (also correct):
function invertTreePreOrder(root) {
  if (root === null) return null;

  // Swap FIRST, then recurse into the now-swapped children
  [root.left, root.right] = [root.right, root.left];
  invertTreePreOrder(root.left);
  invertTreePreOrder(root.right);

  return root;
}
```

### Dry Run

```
Tree:     4
         / \
        2   7
       / \ / \
      1  3 6  9

invertTree(4):
  left  = invertTree(2):
    left  = invertTree(1): null children → swap nulls → return node(1)
    right = invertTree(3): null children → swap nulls → return node(3)
    node(2).left=3, node(2).right=1. return node(2) [now: 2 with {3,1}]
  right = invertTree(7):
    left  = invertTree(6): return node(6)
    right = invertTree(9): return node(9)
    node(7).left=9, node(7).right=6. return node(7) [now: 7 with {9,6}]
```

### Complexity
- Time: O(n) — every node visited once.
- Space: O(h) — call stack depth.

### Edge Cases
- **Null root**: returns null immediately — no tree to invert.
- **Single node**: `root.left` and `root.right` are null; swap two nulls; returns root unchanged. Correct.
- **Already symmetric tree**: inverting it produces the same tree (a symmetric tree is its own mirror). The algorithm still runs correctly — it just happens that the result equals the input.
- **Linear chain (only left children)**: inverting produces a linear chain with only right children. Each node's children are swapped: left becomes right, null becomes null. Correct.

### Follow-up Questions
- "Is there a difference between pre-order and post-order for this problem?" — Both produce the correct result. Post-order: invert children first, then swap at current node. Pre-order: swap at current node first, then recurse into the now-swapped children. The final tree is identical either way.
- "Can you do it iteratively?" — BFS: push root to queue; for each node, swap its children; push non-null children to queue. O(n) time, O(w) space where w is max width.

## Problem 4 — Maximum Depth of Binary Tree

### Problem
Given the root of a binary tree, return its maximum depth. Maximum depth is the number of nodes along the longest path from the root node down to the farthest leaf node.

```
Input:
    3
   / \
  9  20
     / \
    15   7

Output: 3

Input: root = [1, null, 2]  → Output: 2
```

### Pattern Recognition
Bottom-up post-order recursion — compute the depth of both subtrees, return the larger one plus 1 (for the current node). The "+1" accounts for counting nodes (not edges); the base case null = 0 ensures leaf nodes return 1.

### Key Insight
The maximum depth through a node = max depth of its left subtree vs right subtree, plus 1 for the current node itself. This is purely bottom-up: a node's depth cannot be determined until both children's depths are known. Each node's contribution to the answer is exactly "+1" — no other bookkeeping.

### Approach
`maxDepth(node)`: null → 0. Return `max(maxDepth(left), maxDepth(right)) + 1`.

### Solution

```js
function maxDepth(root) {
  // Base case: null node contributes 0 to depth
  if (root === null) return 0;

  // Bottom-up: get depths of both subtrees
  const leftDepth  = maxDepth(root.left);
  const rightDepth = maxDepth(root.right);

  // Current node adds 1 to the deeper subtree's depth
  return Math.max(leftDepth, rightDepth) + 1;
}

// BFS alternative (counts levels):
function maxDepthBFS(root) {
  if (!root) return 0;
  const queue = [root];
  let depth = 0;

  while (queue.length > 0) {
    depth++;
    const levelSize = queue.length; // process entire level before moving to next
    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();
      if (node.left)  queue.push(node.left);
      if (node.right) queue.push(node.right);
    }
  }

  return depth;
}
```

### Dry Run

```
Tree:     3
         / \
        9  20
           / \
          15   7

maxDepth(3):
  leftDepth = maxDepth(9):
    maxDepth(null) = 0
    maxDepth(null) = 0
    return max(0,0)+1 = 1
  rightDepth = maxDepth(20):
    leftDepth = maxDepth(15):
      return max(0,0)+1 = 1
    rightDepth = maxDepth(7):
      return max(0,0)+1 = 1
    return max(1,1)+1 = 2
  return max(1, 2)+1 = 3 ✓
```

### Complexity
- Time: O(n) — every node visited once.
- Space: O(h) — O(log n) balanced, O(n) skewed.

### Edge Cases
- **Null root**: returns 0 — an empty tree has depth 0.
- **Single node**: both children null → `max(0,0)+1 = 1`. A single-node tree has depth 1. Correct.
- **Linear chain (only right children)**: `maxDepth` of n-node chain = n. Each level adds 1 recursively.
- **Minimum depth vs maximum depth**: minimum depth is the shortest path to a leaf. For `[1, null, 2]`, minimum depth = 2 (must reach a leaf; node 1 has a null left child but node 2 is the leaf). Naively using `min` instead of `max` would return 1 for node 1 (the null child = 0 depth). For minimum depth, only take `min` of non-null children.

### Follow-up Questions
- "Minimum depth?" — Same structure but use `Math.min` — with the caveat that if one child is null, you cannot take the minimum with 0 (that would incorrectly count the non-existent null branch as a path to a leaf). Use: `if (!root.left) return maxDepth(root.right) + 1; if (!root.right) return maxDepth(root.left) + 1; return Math.min(minDepth(left), minDepth(right)) + 1`.
- "Count total nodes in a complete binary tree efficiently?" — For a complete binary tree, compute left height and right height from the root. If equal, the tree is a perfect binary tree: count = `2^h - 1`. If unequal, recurse on both subtrees. O(log²n) time — better than O(n).

## Problem 5 — Balanced Binary Tree

### Problem
Given a binary tree, determine if it is height-balanced. A height-balanced tree is one in which the left and right subtrees of every node differ in height by no more than 1.

```
Input:
    3
   / \
  9  20
     / \
    15   7
Output: true

Input:
       1
      / \
     2   2
    / \
   3   3
  / \
 4   4
Output: false
```

### Pattern Recognition
Bottom-up sentinel recursion — compute height from the leaves upward; return -1 as a sentinel if any subtree is already unbalanced. The sentinel propagates instantly up the call stack, avoiding redundant height computations.

### Key Insight
The naive approach calls a separate `height()` function at every node to check balance — O(h) per node, O(n log n) total. The sentinel pattern combines height computation and balance checking in a single pass: if children report a valid height, check balance locally; if any child reports -1, propagate -1 immediately. O(n) total — each node visited exactly once.

### Approach
`checkHeight(node)`: null → 0. Compute `leftH = checkHeight(left)`. If -1, return -1 (early exit). Compute `rightH = checkHeight(right)`. If -1, return -1 (early exit). If `|leftH - rightH| > 1`, return -1 (this node is the violation). Return `max(leftH, rightH) + 1` (valid height). Call `checkHeight(root) !== -1`.

### Solution

```js
function isBalanced(root) {
  return checkHeight(root) !== -1;
}

function checkHeight(node) {
  // Base case: null is vacuously balanced with height 0
  if (node === null) return 0;

  // Check left subtree first; propagate sentinel immediately
  const leftH = checkHeight(node.left);
  if (leftH === -1) return -1; // left subtree is already unbalanced — stop

  // Check right subtree; propagate sentinel immediately
  const rightH = checkHeight(node.right);
  if (rightH === -1) return -1; // right subtree is already unbalanced — stop

  // Both subtrees are balanced; check balance at current node
  if (Math.abs(leftH - rightH) > 1) return -1; // current node is the violation

  // All good: return valid height to parent
  return Math.max(leftH, rightH) + 1;
}
```

### Dry Run

```
Tree:      1
          / \
         2   2
        / \
       3   3
      / \
     4   4

checkHeight(1):
  leftH = checkHeight(2):
    leftH = checkHeight(3):
      leftH = checkHeight(4):
        leftH = checkHeight(null) = 0
        rightH = checkHeight(null) = 0
        |0-0|=0 ≤ 1. return max(0,0)+1 = 1
      rightH = checkHeight(4):
        similarly → return 1
      |1-1|=0 ≤ 1. return max(1,1)+1 = 2
    rightH = checkHeight(3):
      both null children → return 1
    |2-1|=1 ≤ 1. return max(2,1)+1 = 3
  leftH = 3.

  rightH = checkHeight(2):  (root's right child)
    both null children → return 1
  rightH = 1.

  |leftH-rightH| = |3-1| = 2 > 1 → return -1 ✗

checkHeight(root) = -1 ≠ -1 is false → isBalanced = false ✓

The violation is detected at root (node 1): left subtree height 3, right subtree height 1.
```

### Complexity
- Time: O(n) — each node visited exactly once (sentinel prevents re-visiting subtrees below a violation).
- Space: O(h) — call stack depth.

### Edge Cases
- **Empty tree**: `checkHeight(null) = 0 ≠ -1` → `isBalanced = true`. An empty tree is balanced.
- **Single node**: both children null → `|0-0| = 0 ≤ 1` → returns 1. Balanced.
- **Violation at leaf level** (one subtree has one extra node): detected immediately when `|1-0| > 1` is false at height-2 nodes, but detected at the first node where `|2-0| > 1`. Sentinel propagates from there.
- **Already balanced and sentinel never triggered**: all -1 checks pass without triggering; final answer is `checkHeight(root) ≥ 1 ≠ -1` → true.

### Follow-up Questions
- "Naive O(n log n) approach for comparison?" — `isBalanced(node) = |height(node.left) - height(node.right)| <= 1 && isBalanced(left) && isBalanced(right)` with a separate `height()` call — O(h) per node for height, O(n) nodes = O(n log n). Good to mention for contrast.
- "Convert an unbalanced BST to a balanced BST?" — In-order traversal to get sorted array; recursively build balanced BST from sorted array (pick midpoint as root). O(n) time, O(n) space.

## Problem 6 — Diameter of Binary Tree

### Problem
Given the root of a binary tree, return the length of the diameter of the tree. The diameter is the length of the longest path between any two nodes. This path may or may not pass through the root.

```
Input:
    1
   / \
  2   3
 / \
4   5
Output: 3    // path: 4 → 2 → 5  or  4 → 2 → 1 → 3

Input: root = [1, 2]  → Output: 1
```

### Pattern Recognition
Post-order DFS with global maximum — each node returns its HEIGHT to the parent, but simultaneously updates a global `maxDiameter = max(maxDiameter, leftH + rightH)`. The diameter through any node is the sum of the heights of its left and right subtrees.

### Key Insight
The diameter of the tree is the maximum over all nodes of `leftHeight(node) + rightHeight(node)`. This maximum is not known at any single node — it requires checking all nodes. But height is a bottom-up value. Solution: during the bottom-up height computation, at each node also compute the local diameter (`leftH + rightH`) and update the global maximum. Two purposes served in one O(n) pass.

### Approach
Initialize `maxDiameter = 0`. Define `height(node)`: null → 0. Compute `leftH = height(left)`, `rightH = height(right)`. Update `maxDiameter = max(maxDiameter, leftH + rightH)`. Return `max(leftH, rightH) + 1`. Return `maxDiameter`.

### Solution

```js
function diameterOfBinaryTree(root) {
  let maxDiameter = 0; // global maximum: updated at every node during DFS

  function height(node) {
    if (node === null) return 0;

    const leftH  = height(node.left);
    const rightH = height(node.right);

    // Diameter through this node = leftH + rightH (number of edges, not nodes)
    // leftH edges going left + rightH edges going right
    maxDiameter = Math.max(maxDiameter, leftH + rightH);

    // Return HEIGHT (not diameter) to the parent — parent uses it for its own diameter
    return Math.max(leftH, rightH) + 1;
  }

  height(root); // triggers full post-order traversal
  return maxDiameter;
}
```

### Dry Run

```
Tree:     1
         / \
        2   3
       / \
      4   5

height(4): leftH=0, rightH=0. maxDiameter=max(0,0+0)=0. return 1.
height(5): leftH=0, rightH=0. maxDiameter=max(0,0+0)=0. return 1.
height(2): leftH=1(from 4), rightH=1(from 5).
  maxDiameter = max(0, 1+1) = 2.
  return max(1,1)+1 = 2.
height(3): leftH=0, rightH=0. maxDiameter=max(2,0)=2. return 1.
height(1): leftH=2(from subtree 2), rightH=1(from 3).
  maxDiameter = max(2, 2+1) = 3.
  return max(2,1)+1 = 3.

Answer: maxDiameter = 3 ✓
(Path 4→2→5 has length 2; path 4→2→1→3 has length 3; answer is 3)
```

### Complexity
- Time: O(n) — single post-order traversal; each node visited once.
- Space: O(h) — call stack depth.

### Edge Cases
- **Null root**: `height(null) = 0`; `maxDiameter` is never updated; returns 0. Correct — an empty tree has diameter 0.
- **Single node**: both children null; `maxDiameter = max(0, 0+0) = 0`. Diameter 0 — a single node has no edge. Correct.
- **Linear chain**: `1 → 2 → 3 → 4`. At each internal node, one subtree height is 0 (no child on one side). The maximum diameter is the chain length minus 1 (number of edges). Verified: at node 2 (which has 3 and 4 as descendants): leftH=0, rightH=2, diameter=0+2=2. At node 1: leftH=0, rightH=3, diameter=3. Correct.
- **Diameter not through root**: e.g., a perfectly balanced tree where the diameter path goes through a subtree root, not the overall root. The global variable catches it because `maxDiameter` is updated at every node, not just the root.

### Follow-up Questions
- "Longest path with value sum (not just length)?" — Return the maximum-sum path from each node instead of height. More complex — must consider cases where one or both arms are negative (can choose to ignore a subtree).
- "Diameter measured in nodes instead of edges?" — `leftH + rightH + 1` at each node (adding 1 for the node itself). The base case `null → 0` and `leaf → 1`. Check LeetCode problem statement — they use edge count (current solution).
- "Longest path in a general tree (not binary)?" — DFS from any node to find the farthest node; DFS again from that node to find the diameter. Two DFS passes, O(n) total.

## Problem 7 — Binary Tree Right Side View

### Problem
Given the root of a binary tree, imagine yourself standing on the right side of it. Return the values of the nodes you can see, ordered from top to bottom.

```
Input:
    1
   / \
  2   3
   \
    5
Output: [1, 3, 5]
  // Level 0: see 1 (only node)
  // Level 1: see 3 (rightmost: 3 blocks 2)
  // Level 2: see 5 (only node at this level)

Input: root = [1, 2, 3, null, 5, null, 4]
Output: [1, 3, 4]
```

### Pattern Recognition
BFS level-order traversal — process nodes level by level; the last node dequeued at each level is the rightmost visible node. Alternatively: right-first DFS where the first node visited at each depth is the rightmost.

### Key Insight
The right side view shows exactly one node per level — the rightmost node visible from the right. BFS naturally processes all nodes at a given level before moving to the next — recording the last node dequeued at each level gives the right side view. The level boundary is tracked by processing `levelSize` nodes in a batch for each BFS iteration.

### Approach
BFS: queue starts with `[root]`. Each iteration: `levelSize = queue.length`; process all `levelSize` nodes; push their children; after the batch, the last node processed is the rightmost at this level — record its value.

### Solution

```js
// Approach 1: BFS (level-order, record last of each level)
function rightSideView(root) {
  if (!root) return [];

  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length; // number of nodes at this level

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();

      // Record only the LAST node at this level (rightmost visible)
      if (i === levelSize - 1) result.push(node.val);

      if (node.left)  queue.push(node.left);
      if (node.right) queue.push(node.right);
    }
  }

  return result;
}

// Approach 2: DFS right-first (first node at each depth = rightmost)
function rightSideViewDFS(root) {
  const result = [];

  function dfs(node, depth) {
    if (!node) return;

    // First visit to this depth → rightmost node (right children visited first)
    if (depth === result.length) result.push(node.val);

    dfs(node.right, depth + 1); // visit RIGHT child first
    dfs(node.left,  depth + 1); // visit LEFT child second (may overwrite? NO — only first visit recorded)
  }

  dfs(root, 0);
  return result;
}
```

### Edge Cases
- **Null root**: returns `[]` immediately.
- **Single node**: one level; one node; result = `[root.val]`.
- **All left children only**: no right children — the left-most child is also the rightmost at each level. BFS still records the last (only) node per level. DFS visits right children first, but they're null; then left children — first visit at each depth is the left child. Both work correctly.
- **Left subtree deeper than right**: nodes from the left subtree appear in the view for deeper levels (as in the example: node 5 is visible even though it's in the left subtree, because it's the only node at level 2).

### Follow-up Questions
- "Left side view?" — BFS: record the *first* node at each level (`if (i === 0)`). DFS: visit left before right; record first visit at each depth.
- "Level order traversal (all levels)?" — BFS without the `if (i === levelSize - 1)` filter — push all node values per level into a sub-array. Return array of sub-arrays.
- "Zigzag level order?" — BFS with a direction flag; alternate between `push` (left to right) and `unshift` (right to left) per level — or reverse alternate levels.

```
│   ├── Right/Left Side View → BFS (last/first of each level) or right-first DFS
│   │
```

## Common Bugs Checklist

Before submitting any binary tree solution, verify:

1. **Null check before any `.val`, `.left`, or `.right` access?** — Every tree recursive function must check `if (node === null)` as the first line. Accessing `.val` on null causes a runtime error, not a wrong-answer result. The null check is not optional even when the problem states the tree is non-empty — recursive calls naturally produce null nodes as base cases.

2. **For two-tree comparisons: checking both-null and one-null before value comparison?** — The order is mandatory: `if (p===null && q===null) return true` then `if (p===null || q===null) return false` then access `.val`. Checking values before nullability causes a null-pointer error when exactly one tree reaches a leaf but the other has a deeper subtree.

3. **Symmetric Tree: using crossed children `(left.left, right.right)` not same-order `(left.left, right.left)`?** — The most common bug: writing `isMirror(left.left, right.left) && isMirror(left.right, right.right)` tests if left and right are the SAME tree, not mirrors. Symmetry requires CROSSING: outer pair `(left.left, right.right)` and inner pair `(left.right, right.left)`.

4. **Invert Tree: forgetting to store one child before overwriting?** — `root.left = root.right; root.right = root.left` loses the original `root.left`. Always use a temporary: `const left = root.left; root.left = root.right; root.right = left` — or destructuring: `[root.left, root.right] = [root.right, root.left]`.

5. **Maximum Depth base case returning 0 for null — not -1 or 1?** — `height(null) = 0` (null has zero height). A single leaf returns `max(0,0)+1 = 1`. Returning -1 for null breaks the "+1" formula (leaf would return 0 instead of 1). Returning 1 for null means leaves return 2 — off-by-one throughout.

6. **Balanced Tree sentinel: propagating -1 immediately, before the balance check?** — The early-exit `if (leftH === -1) return -1` must come BEFORE the local balance check `if (Math.abs(leftH - rightH) > 1)`. If the local check runs first with `leftH = -1`, `Math.abs(-1 - rightH)` may produce a false "balanced" result or throw off the comparison. Always check for -1 before using the height value.

7. **Diameter: updating the global variable at every node, including leaf nodes?** — At a leaf: `leftH = 0`, `rightH = 0`, `diameter = 0`. The global update `maxDiameter = max(maxDiameter, 0)` is harmless and correct. Skipping the update at leaves is fine (it won't change maxDiameter from 0), but skipping it at non-leaf nodes is a bug. Always update unconditionally inside the `height()` function.

8. **Diameter: returning HEIGHT not diameter from the recursive function?** — The function that updates `maxDiameter` must return `Math.max(leftH, rightH) + 1` (height) to the parent — not `leftH + rightH` (local diameter). The parent needs the height to compute its own diameter. Returning the diameter instead of the height corrupts every ancestor's computation.

9. **Right Side View BFS: using `queue.length` inside the inner loop instead of `levelSize`?** — `queue.length` changes as children are pushed during the inner loop. The variable `levelSize` must be captured BEFORE the inner loop (`const levelSize = queue.length`). Using `queue.length` as the loop bound causes the inner loop to process some nodes from the next level, mixing levels and producing wrong results.

10. **BFS: using `queue.shift()` for dequeue (O(n) per call)?** — JavaScript's `Array.shift()` is O(n) because it shifts all remaining elements. For interview purposes this is acceptable; for production or very large inputs, use a true queue (doubly-ended) or a pointer-based approach (`let head = 0; const node = queue[head++]`) to achieve O(1) dequeue.

11. **Post-order bottom-up: recursing BEFORE processing, not after?** — For post-order problems (height, balance, diameter), both children must be recursed into BEFORE the current node is processed. Writing `process(node); recurse(left); recurse(right)` is pre-order — the current node is processed before children's results are available. For bottom-up problems, the structure must be: `recurse(left); recurse(right); process(node)`.

12. **Symmetric/Same Tree: comparing node values with `==` (loose equality) instead of `===` (strict)?** — `1 == "1"` is true in JavaScript. Tree node values are typically integers, but using `!==` instead of `!=` and `===` instead of `==` is always safer and matches the problem's intent of value equality.

---

**Final Tip:** At the 5 YOE level, the decisive signal for binary tree problems is answering *five questions before writing any code*: (1) DFS or BFS? (2) Pre/in/post-order — which information flows which direction? (3) What does the recursive function RETURN to its caller — and is that different from the final answer? (4) Is there a global variable needed alongside the return value? (5) What are the two or three null-handling base cases, and in what order? For Symmetric Tree: "DFS, any order but simultaneously on both subtrees, returns boolean to caller which is also the answer, no global needed, base cases: both-null=true, one-null=false, then value check." For Diameter: "DFS post-order, returns HEIGHT to caller (not the answer), the answer is tracked in a global maxDiameter updated at every node, base case: null=0." Stating these five answers out loud before writing the first line is the mark of a senior engineer who owns the technique.
