# DSA: Level Order Traversal (BFS) — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is level order traversal, and why is a queue (not a stack) the natural structure to implement it?**
A: Level order traversal visits every node of a tree level by level, left to right within each level, before moving to the next level down. A **queue** is the natural fit because BFS's FIFO ordering exactly matches "process nodes in the order they were discovered" — when a node is dequeued and its children are enqueued, those children are guaranteed to be processed only after every other already-discovered node at the current (or earlier) level, since they entered the queue later. A stack would instead dive deep into one branch immediately (LIFO behavior), producing a depth-first order, not a level-by-level one.

```
Tree:
        3
       / \
      9   20
         /  \
        15   7

Level order: 3, 9, 20, 15, 7
```

**Q2. What is the standard queue-based algorithm for level order traversal, and what is its time and space complexity?**
A: Initialize a queue with the root node. While the queue isn't empty: dequeue a node, process it (e.g., record its value), and enqueue its children (left then right, for a binary tree). Repeat until the queue is empty.

```js
function levelOrder(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const node = queue.shift();
    result.push(node.val);

    if (node.left !== null) queue.push(node.left);
    if (node.right !== null) queue.push(node.right);
  }

  return result;
}
```

Time: O(n) — every node is enqueued and dequeued exactly once. Space: O(n) worst case — the queue can hold up to the width of the tree's widest level, which in the worst case (a very "bushy" tree, or the last level of a complete binary tree) is O(n/2) ≈ O(n).

**Q3. Why is `queue.shift()` a performance concern in JavaScript specifically, and what's the standard fix?**
A: As covered in the dedicated stacks-and-queues guide, `Array.shift()` is O(n) because it must shift every remaining element left by one position — using it repeatedly in a BFS loop degrades what should be an O(n)-total traversal into O(n²). The standard fix is either an index-based approach (track a `front` index into the array instead of physically removing elements) or a proper queue implementation (circular buffer or linked-list-backed), avoiding the O(n) shift entirely.

```js
function levelOrderEfficient(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];
  let front = 0; // index-based "dequeue" — avoids shift()'s O(n) cost

  while (front < queue.length) {
    const node = queue[front++];
    result.push(node.val);

    if (node.left !== null) queue.push(node.left);
    if (node.right !== null) queue.push(node.right);
  }

  return result;
}
```

**Q4. How do you modify the basic level order traversal to group results BY LEVEL (i.e., return a list of lists, one per level) rather than one flat list?**
A: The key technique is capturing the **queue's size at the start of each level's processing** — since at the start of any iteration of the outer loop, the queue contains exactly the nodes of the current level (assuming the previous level was fully processed and only the next level's children have been enqueued since), recording that size and processing exactly that many nodes (before any of their children get enqueued and mixed in) correctly isolates one level at a time.

```js
function levelOrderGrouped(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length; // snapshot BEFORE processing this level
    const currentLevel = [];

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();
      currentLevel.push(node.val);

      if (node.left !== null) queue.push(node.left);
      if (node.right !== null) queue.push(node.right);
    }

    result.push(currentLevel);
  }

  return result;
}
```

**Q5. Why does capturing `queue.length` at the START of each level's loop (not recomputing it inside the inner loop) matter?**
A: If you recomputed or re-read `queue.length` on every iteration of the inner loop (instead of snapshotting it once at the top), the loop would include children just enqueued *during* the current level's processing — since those children get pushed onto the same queue, `queue.length` grows as you go, and a naively-recomputed bound would incorrectly pull in next-level nodes as if they belonged to the current level. Snapshotting `levelSize = queue.length` once, before the inner loop begins, and iterating exactly that many times, is what correctly isolates one level's nodes from the next level's newly-enqueued children.

### Section 2: Variants & Common Adaptations

**Q6. How do you implement "zigzag level order traversal" (alternating left-to-right, then right-to-left, per level)?**
A: Use the same level-grouping BFS structure (Q4), but track a direction flag that toggles each level; when the flag indicates "reverse," reverse the current level's collected values before adding them to the result (or, more efficiently, insert each value at the front of the current level's list instead of the back, avoiding a separate reversal pass).

```js
function zigzagLevelOrder(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];
  let leftToRight = true;

  while (queue.length > 0) {
    const levelSize = queue.length;
    const currentLevel = [];

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();

      if (leftToRight) {
        currentLevel.push(node.val);
      } else {
        currentLevel.unshift(node.val); // insert at front, building the reversed order directly
      }

      if (node.left !== null) queue.push(node.left);
      if (node.right !== null) queue.push(node.right);
    }

    result.push(currentLevel);
    leftToRight = !leftToRight;
  }

  return result;
}
```

**Q7. How do you find the "right side view" of a binary tree (the last node visible from the right at each level), and how does it build on level order traversal?**
A: Perform the same level-grouping BFS, but for each level, only keep the **last** node processed in that level's inner loop (since nodes are processed left to right, the last one is the rightmost, and thus the one "visible" from the right side).

```js
function rightSideView(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length;

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();

      if (i === levelSize - 1) { // last node processed in this level
        result.push(node.val);
      }

      if (node.left !== null) queue.push(node.left);
      if (node.right !== null) queue.push(node.right);
    }
  }

  return result;
}
```

**Q8. How would you compute the average value of each level using BFS?**
A: Same level-grouping structure; instead of collecting individual values, accumulate a running sum and count within each level's inner loop, then divide sum by count once the level's loop completes.

```js
function averageOfLevels(root) {
  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length;
    let sum = 0;

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();
      sum += node.val;

      if (node.left !== null) queue.push(node.left);
      if (node.right !== null) queue.push(node.right);
    }

    result.push(sum / levelSize);
  }

  return result;
}
```

**Q9. Why is BFS specifically well-suited for finding a binary tree's MINIMUM depth, and how does it offer an efficiency advantage over DFS for this specific problem?**
A: Minimum depth means the shortest path from root to any leaf. BFS explores level by level, so the **very first leaf node encountered** during a BFS traversal is guaranteed to be at the minimum possible depth — the algorithm can terminate immediately upon finding it, without needing to explore deeper levels or other branches at all. A DFS approach would need to explore entire branches (potentially very deep ones) before it could be sure it had found the true minimum, since DFS doesn't naturally process shallower nodes before deeper ones. This early-termination advantage is a genuine practical efficiency win for BFS on this specific class of "shortest path / minimum depth" problems.

```js
function minDepth(root) {
  if (root === null) return 0;

  const queue = [[root, 1]]; // pair: node, its depth

  while (queue.length > 0) {
    const [node, depth] = queue.shift();

    if (node.left === null && node.right === null) {
      return depth; // first leaf found via BFS is guaranteed minimum depth
    }

    if (node.left !== null) queue.push([node.left, depth + 1]);
    if (node.right !== null) queue.push([node.right, depth + 1]);
  }

  return 0;
}
```

### Section 3: BFS Beyond Binary Trees

**Q10. How does level order traversal extend to an N-ary tree (nodes with an arbitrary number of children, not just left/right)?**
A: The core algorithm is unchanged — instead of enqueueing exactly `node.left` and `node.right`, enqueue every child in `node.children` (an array). The level-grouping technique (snapshot `queue.length` at the start of each level) works identically regardless of how many children each node has.

```js
function nAryLevelOrder(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length;
    const currentLevel = [];

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();
      currentLevel.push(node.val);

      for (const child of node.children) {
        queue.push(child);
      }
    }

    result.push(currentLevel);
  }

  return result;
}
```

**Q11. How does BFS on a general GRAPH differ from BFS on a tree, and why does a graph traversal need a `visited` set while a tree traversal typically doesn't?**
A: A tree has no cycles and exactly one path from the root to any node, so a tree BFS can never revisit the same node twice — there's no risk of infinite loops or redundant processing. A general graph can have cycles and multiple paths between nodes, so a **graph BFS must explicitly track visited nodes** (typically via a `Set` or boolean array) and skip enqueueing any node that's already been visited or is already queued — without this, the traversal could loop forever (in a cyclic graph) or process the same node multiple times (wasteful, and potentially incorrect for problems that assume each node is processed exactly once).

```js
function bfsGraph(graph, start) {
  const visited = new Set([start]);
  const queue = [start];
  const result = [];

  while (queue.length > 0) {
    const node = queue.shift();
    result.push(node);

    for (const neighbor of graph[node]) {
      if (!visited.has(neighbor)) {
        visited.add(neighbor); // mark visited at ENQUEUE time, not dequeue time
        queue.push(neighbor);
      }
    }
  }

  return result;
}
```

**Q12. Why must a node be marked as `visited` at ENQUEUE time in a graph BFS, rather than at dequeue time?**
A: If marking as visited were deferred until dequeue time, a node with multiple incoming edges from different currently-queued nodes could be enqueued **multiple times** before any of those duplicate entries gets dequeued and marked — since the check `!visited.has(neighbor)` would still pass for every one of those duplicate enqueue attempts, all happening before the node is ever actually dequeued and marked. Marking at enqueue time closes this gap immediately, ensuring each node is added to the queue at most once, preventing redundant processing and keeping the algorithm's complexity properly bounded at O(V + E) instead of potentially much worse.

**Q13. What is "multi-source BFS," and what problem does it solve that single-source BFS doesn't directly address?**
A: Multi-source BFS starts the traversal with **multiple initial nodes already in the queue simultaneously** (rather than just one root/start node), all conceptually at "distance 0." This correctly models problems where multiple starting points spread outward *at the same time* and you need to know, for every other node, the shortest distance to its **nearest** source — a classic example is "rotting oranges" (multiple initially-rotten oranges all start spreading rot simultaneously; a single-source BFS from just one of them wouldn't correctly capture the combined, simultaneous spread from all sources at once).

```js
function multiSourceBFS(grid, sources) {
  const queue = [...sources.map(s => [s, 0])]; // all sources start at distance 0, simultaneously
  const visited = new Set(sources.map(s => `${s[0]},${s[1]}`));
  let maxDistance = 0;

  while (queue.length > 0) {
    const [[row, col], dist] = queue.shift();
    maxDistance = Math.max(maxDistance, dist);

    for (const [dr, dc] of [[0,1],[0,-1],[1,0],[-1,0]]) {
      const nr = row + dr, nc = col + dc;
      const key = `${nr},${nc}`;

      if (isValid(grid, nr, nc) && !visited.has(key)) {
        visited.add(key);
        queue.push([[nr, nc], dist + 1]);
      }
    }
  }

  return maxDistance;
}
```

**Q14. Why does starting all sources in the queue simultaneously (rather than running separate single-source BFS passes for each source and taking the minimum) correctly compute "distance to nearest source" in a single pass?**
A: BFS processes nodes in strictly non-decreasing order of distance from the queue's initial contents — since all sources start at distance 0 simultaneously, every node first discovered at distance `d` is guaranteed to have been reached via the *shortest* possible path from *any* of the sources (not necessarily a specific one), because BFS never processes a distance-`d+1` node before finishing all distance-`d` nodes. Running separate single-source BFS passes and taking the minimum would give the same correct final answer but at O(k × (V+E)) cost for k sources, versus multi-source BFS's single O(V+E) pass — a substantial efficiency improvement that comes directly from correctly modeling "simultaneous spread" rather than serially simulating each source's independent spread.

### Section 4: Recursive (DFS-Based) Level Grouping — An Alternative

**Q15. Can you achieve level-grouped output using DFS (recursion) instead of BFS, and how does that approach work?**
A: Yes — recursively traverse the tree while tracking the current depth as a parameter; maintain a result list indexed by depth, and append the current node's value to `result[depth]` (creating a new empty list at that depth if it doesn't exist yet). Since DFS naturally visits nodes in root-to-leaf order along each branch, and each recursive call carries its own correct depth, this correctly groups values by level even though the traversal order (depth-first) is very different from BFS's actual visitation order.

```js
function levelOrderDFS(root) {
  const result = [];

  function dfs(node, depth) {
    if (node === null) return;

    if (result.length === depth) {
      result.push([]); // first time reaching this depth — create its list
    }
    result[depth].push(node.val);

    dfs(node.left, depth + 1);
    dfs(node.right, depth + 1);
  }

  dfs(root, 0);
  return result;
}
```

**Q16. What is the trade-off between the DFS-based and BFS-based approaches to producing level-grouped output?**
A: Both are O(n) time and O(n) space (output size dominates either way; BFS's queue and DFS's call stack are both bounded by O(n) in the worst case, though the *shape* of that worst case differs — BFS's queue is bounded by the tree's maximum *width*, while DFS's call stack is bounded by the tree's maximum *depth*). For a very wide, shallow tree, BFS's queue could be large while DFS's stack stays small; for a very deep, narrow tree (approaching a linked-list-like shape), DFS's call stack could be large (risking stack overflow) while BFS's queue stays small. Neither is universally better — the "natural" choice is usually BFS for level-order problems (since the traversal order directly mirrors what's being asked for), but it's worth knowing the DFS alternative exists and understanding this width-vs-depth space trade-off, especially if asked to avoid one specific complexity concern (e.g., "avoid deep recursion" → prefer BFS; "avoid a potentially very wide queue" → DFS might be preferable in some memory-constrained contexts).

### Section 5: Scenario / Interview-Style Questions

**Q17. "You need to print a binary tree's nodes level by level, with each level on its own line. Walk through your approach and why you chose it."**
A: I'd use the standard BFS level-grouping technique: a queue initialized with the root, and at the start of each iteration of the outer loop, snapshot the current queue size (`levelSize`) to know exactly how many nodes belong to the current level before any of their children get enqueued and mixed in. I'd explicitly call out why this snapshot timing matters (Q5) as the key correctness detail, since it's the most common point of subtle bugs in this pattern.

**Q18. "A teammate implements level order traversal using `queue.shift()` in a tight loop, and it's noticeably slow on large trees. What's happening, and how do you fix it?"**
A: `Array.shift()` is O(n) per call in JavaScript (it must shift every remaining array element left by one), so a BFS loop calling it once per node turns an intended O(n) traversal into O(n²) overall. I'd recommend switching to an index-based "virtual dequeue" (tracking a `front` pointer into the array instead of physically removing elements) or a proper queue data structure (circular buffer or linked-list-backed), both restoring true O(n) total traversal time.

**Q19. "How would you adapt level order traversal to work on a general graph instead of a tree, and what's the single most important change required?"**
A: The most important change is adding a `visited` set, marking each node as visited **at the moment it's enqueued** (not when it's dequeued) — this is essential because a general graph can have cycles and multiple incoming paths to the same node, unlike a tree, and marking visited only at dequeue time would allow the same node to be enqueued multiple times before any of those duplicates gets processed, breaking both correctness and the algorithm's intended O(V+E) complexity.

**Q20. "You're solving a grid-based problem where multiple 'starting points' all need to spread outward simultaneously (e.g., simultaneous rot spreading from multiple initially-rotten cells), and need the time for the spread to reach every cell. Why not just run BFS separately from each starting point and combine the results?"**
A: Running BFS separately from each source and taking the per-cell minimum across all those runs would give the same correct final answer, but at a cost of O(k × (V+E)) for k sources — multi-source BFS achieves the identical correct result in a single O(V+E) pass by seeding the queue with all sources simultaneously at distance 0, correctly modeling that they're all spreading at the same time rather than serially. I'd choose multi-source BFS specifically for this efficiency reason, not because the separate-runs approach would be incorrect.

**Q21. "How would you find the 'minimum depth' of a binary tree, and why might BFS be preferable to DFS here specifically, even though DFS is often simpler to write for tree problems?"**
A: I'd use BFS with early termination: the very first leaf node encountered during a level-by-level BFS traversal is guaranteed to be at the tree's minimum depth, so the algorithm can return immediately upon finding it, without needing to explore any remaining nodes. A DFS approach, by contrast, would need to fully explore any branch it commits to (potentially a very deep one) before it could be sure that branch doesn't contain an even-shallower leaf elsewhere, making early termination much less natural to express correctly — BFS's level-by-level guarantee is what specifically enables the efficient early exit here.

## Problem 1 — Binary Tree Level Order Traversal

### Problem
Given the root of a binary tree, return the level order traversal of its nodes' values (i.e., from left to right, level by level), grouped as a list of lists — one list per level.

```
Input:
        3
       / \
      9   20
         /  \
        15   7

Output: [[3], [9, 20], [15, 7]]
```

### Pattern Recognition
The foundational BFS level-grouping technique — snapshotting the queue's size at the start of each level to correctly separate one level's nodes from the next's.

### Key Insight
At the moment the outer loop begins a new iteration, the queue contains exactly the current level's nodes (assuming correct processing so far) — capturing that count before enqueueing any children is what allows the inner loop to process exactly one level without accidentally spilling into the next.

### Approach
Queue-based BFS. At the start of each outer-loop iteration, snapshot `levelSize = queue.length`. Process exactly `levelSize` nodes in the inner loop, collecting their values and enqueueing their children. Push the completed level's values onto the result.

### Solution

```js
function levelOrder(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length;
    const currentLevel = [];

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();
      currentLevel.push(node.val);

      if (node.left !== null) queue.push(node.left);
      if (node.right !== null) queue.push(node.right);
    }

    result.push(currentLevel);
  }

  return result;
}
```

### Dry Run

```
Tree:
        3
       / \
      9   20
         /  \
        15   7

queue=[3], result=[]

Outer iter 1: levelSize=1, currentLevel=[]
  i=0: node=3, currentLevel=[3]. enqueue 9, 20 → queue=[9,20]
  result=[[3]]

Outer iter 2: levelSize=2 (queue=[9,20]), currentLevel=[]
  i=0: node=9, currentLevel=[9]. no children to enqueue → queue=[20]
  i=1: node=20, currentLevel=[9,20]. enqueue 15, 7 → queue=[15,7]
  result=[[3],[9,20]]

Outer iter 3: levelSize=2 (queue=[15,7]), currentLevel=[]
  i=0: node=15, currentLevel=[15]. no children → queue=[7]
  i=1: node=7, currentLevel=[15,7]. no children → queue=[]
  result=[[3],[9,20],[15,7]]

queue empty → loop ends

Result: [[3],[9,20],[15,7]] ✓
```

### Complexity
- Time: O(n) — every node enqueued and dequeued exactly once (using an efficient dequeue; O(n²) if naive `shift()` is used repeatedly without the index-based fix).
- Space: O(n) — the queue holds up to the tree's widest level, and the result stores every node's value.

### Edge Cases
- Empty tree (`root === null`): explicit early return of an empty array.
- Single node: one outer iteration, `levelSize=1`, produces `[[rootVal]]`.
- Completely unbalanced tree (e.g., every node has only a left child, forming a linked-list shape): every level has exactly 1 node — still handled correctly, just with `n` outer iterations instead of `log n`.
- Very wide tree (e.g., a complete binary tree's last level): queue size can reach up to `n/2` at its peak — correctly handled, just a reminder that space usage is width-dependent, not just node-count-dependent.

### Follow-up Questions
- "Modify to output a flat list instead of grouped by level?" → Simpler version without the `levelSize` snapshot — just push each value directly as it's dequeued (see Q2).
- "Reverse the order (bottom level first)?" → Collect levels in the same way, then reverse the final `result` array (or use `unshift` to prepend each completed level instead of appending).

## Problem 2 — Zigzag Level Order Traversal

### Problem
Given the root of a binary tree, return the zigzag level order traversal of its nodes' values (left to right for the first level, right to left for the next, alternating).

```
Input:
        3
       / \
      9   20
         /  \
        15   7

Output: [[3], [20, 9], [15, 7]]
```

### Pattern Recognition
Standard BFS level-grouping, with an alternating direction flag controlling whether each level's values are appended in order or effectively reversed.

### Key Insight
Rather than collecting a level's values in the usual left-to-right order and then separately reversing every other level (an extra O(k) pass per reversed level), inserting each value at the **front** of the current level's list (when in "reverse" mode) builds the reversed order directly during collection, avoiding a separate reversal step.

### Approach
Same level-grouping BFS as Problem 1, with a `leftToRight` boolean that toggles after each level. When `false`, use `unshift` instead of `push` to insert each node's value at the front of the current level's array.

### Solution

```js
function zigzagLevelOrder(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];
  let leftToRight = true;

  while (queue.length > 0) {
    const levelSize = queue.length;
    const currentLevel = [];

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();

      if (leftToRight) {
        currentLevel.push(node.val);
      } else {
        currentLevel.unshift(node.val);
      }

      if (node.left !== null) queue.push(node.left);
      if (node.right !== null) queue.push(node.right);
    }

    result.push(currentLevel);
    leftToRight = !leftToRight;
  }

  return result;
}
```

### Dry Run

```
Tree:
        3
       / \
      9   20
         /  \
        15   7

queue=[3], leftToRight=true, result=[]

Level 1: levelSize=1, currentLevel=[]
  node=3, leftToRight → push → currentLevel=[3]
  enqueue 9,20 → queue=[9,20]
  result=[[3]], leftToRight flips to false

Level 2: levelSize=2, currentLevel=[]
  node=9, !leftToRight → unshift → currentLevel=[9]
  enqueue (9 has no children)
  node=20, !leftToRight → unshift → currentLevel=[20,9]
  enqueue 15,7 → queue=[15,7]
  result=[[3],[20,9]], leftToRight flips to true

Level 3: levelSize=2, currentLevel=[]
  node=15, leftToRight → push → currentLevel=[15]
  node=7, leftToRight → push → currentLevel=[15,7]
  result=[[3],[20,9],[15,7]]

Result: [[3],[20,9],[15,7]] ✓
```

### Complexity
- Time: O(n) — same as standard level order traversal; `unshift` on a small per-level array is a minor constant-factor cost (technically O(k) per call for a level of size k, but bounded by the level's own size, not the whole tree, so overall complexity stays O(n) across all levels combined... 

  — Note: `Array.unshift()` is itself O(k) where k is the current array's length, so building a level of size k via repeated `unshift` calls costs O(k²) in the worst case for that one level, not O(k) — a subtlety worth flagging as a real (if often minor) inefficiency, with an alternative being to `push` normally and reverse the completed level array in O(k) afterward instead, which is asymptotically cheaper for very wide levels.
- Space: O(n) — queue plus result storage.

### Edge Cases
- Single node: one level, `leftToRight=true`, straightforward `push`, no zigzag behavior visibly exercised.
- All levels have exactly 1 node (linked-list-shaped tree): zigzag alternation still correctly toggles every level, though with only one element per level, `push` vs `unshift` produce the same single-element array either way.
- Two-level tree: clearly exercises both the `push` and `unshift` code paths, good minimal test case.

### Follow-up Questions
- "Is repeatedly calling `unshift` actually a performance concern here?" → Yes, technically, as noted above — for very wide levels, building via `push` then reversing once per level (O(k) total per level) is more efficient than `unshift`-per-element (O(k²) worst case per level); worth mentioning proactively if asked about performance at scale.
- "Extend to zigzag for an N-ary tree?" → Same technique, just enqueueing `node.children` instead of `node.left`/`node.right` — the zigzag/direction-toggling logic itself is unaffected by branching factor.

## Problem 3 — Right Side View of Binary Tree

### Problem
Given the root of a binary tree, imagine standing on the right side of it — return the values of the nodes visible from that side, ordered from top to bottom.

```
Input:
        1
       / \
      2   3
       \    \
        5    4

Output: [1, 3, 4]
```

### Pattern Recognition
Standard BFS level-grouping, keeping only the LAST node processed at each level — since BFS processes each level left to right, the last node encountered is the rightmost, and thus visible from the right side.

### Key Insight
"Visible from the right" at a given level means "the rightmost node at that level" — which, thanks to BFS's guaranteed left-to-right processing order within a level, is simply whichever node happens to be the last one dequeued during that level's inner loop.

### Approach
Standard level-grouping BFS; within each level's inner loop, check if the current iteration index is the last one (`i === levelSize - 1`), and if so, record that node's value as part of the result.

### Solution

```js
function rightSideView(root) {
  if (root === null) return [];

  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length;

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();

      if (i === levelSize - 1) {
        result.push(node.val);
      }

      if (node.left !== null) queue.push(node.left);
      if (node.right !== null) queue.push(node.right);
    }
  }

  return result;
}
```

### Dry Run

```
Tree:
        1
       / \
      2   3
       \    \
        5    4

queue=[1], result=[]

Level 1: levelSize=1
  i=0 (last): node=1 → result.push(1) → result=[1]
  enqueue 2,3 → queue=[2,3]

Level 2: levelSize=2
  i=0: node=2 (not last) → enqueue 5 (2's right child) → queue=[3,5]
  i=1 (last): node=3 → result.push(3) → result=[1,3]
  enqueue 4 (3's right child) → queue=[5,4]

Level 3: levelSize=2
  i=0: node=5 (not last) → no children
  i=1 (last): node=4 → result.push(4) → result=[1,3,4]
  no children

Result: [1,3,4] ✓ (correctly shows 1, then 3 — NOT 2 — since 3 is rightmost at level 2,
  even though 5 is deeper in the tree via node 2's branch)
```

### Complexity
- Time: O(n) — standard BFS traversal cost.
- Space: O(n) — queue plus result; result itself is only O(height) since it holds one value per level, but the queue can be O(width).

### Edge Cases
- Tree that's entirely left-leaning (no right children at all): the "last node" at each level is still correctly identified via the left subtree's structure, since BFS processes whatever nodes exist at each level regardless of which side they came from.
- Single node: one level, that single node is trivially both first and last, correctly included in the result.
- A node with only a left child at a level where other nodes have right children: this problem cleanly demonstrates why "rightmost node AT THAT LEVEL" (not "follow right children") is the correct definition — a node's own right-child-vs-left-child status doesn't matter, only its left-to-right position among the same level's siblings.

### Follow-up Questions
- "What about the LEFT side view instead?" → Trivial modification — check `i === 0` instead of `i === levelSize - 1`.
- "Can you solve this with DFS instead of BFS?" → Yes — DFS visiting right-before-left, tracking depth, and recording the first node seen at each new depth achieves the same result; a good contrast to explicitly discuss the BFS-vs-DFS trade-off (Q16) for this specific problem.

## Problem 4 — Average of Levels in Binary Tree

### Problem
Given the root of a binary tree, return the average value of the nodes on each level, as a list of floating-point numbers.

```
Input:
        3
       / \
      9   20
         /  \
        15   7

Output: [3.0, 14.5, 11.0]
```

### Pattern Recognition
Standard BFS level-grouping, accumulating a running sum and count per level instead of collecting individual values.

### Key Insight
Since the level-grouping BFS already isolates exactly one level's nodes per outer-loop iteration (via the `levelSize` snapshot technique), computing an aggregate (sum, then divide by count) over that level's nodes is a direct, simple addition to the same core loop structure.

### Approach
Standard level-grouping BFS; within each level's inner loop, accumulate `sum += node.val`; after the inner loop completes, push `sum / levelSize` onto the result.

### Solution

```js
function averageOfLevels(root) {
  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length;
    let sum = 0;

    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();
      sum += node.val;

      if (node.left !== null) queue.push(node.left);
      if (node.right !== null) queue.push(node.right);
    }

    result.push(sum / levelSize);
  }

  return result;
}
```

### Dry Run

```
Tree:
        3
       / \
      9   20
         /  \
        15   7

queue=[3], result=[]

Level 1: levelSize=1, sum=0
  node=3, sum=3. enqueue 9,20 → queue=[9,20]
  result.push(3/1=3.0) → result=[3.0]

Level 2: levelSize=2, sum=0
  node=9, sum=9. no children
  node=20, sum=29. enqueue 15,7 → queue=[15,7]
  result.push(29/2=14.5) → result=[3.0, 14.5]

Level 3: levelSize=2, sum=0
  node=15, sum=15. no children
  node=7, sum=22. no children
  result.push(22/2=11.0) → result=[3.0, 14.5, 11.0]

Result: [3.0, 14.5, 11.0] ✓
```

### Complexity
- Time: O(n) — standard BFS traversal cost, with O(1) additional work per node for the running sum.
- Space: O(n) — queue (bounded by tree width) plus O(height) result storage.

### Edge Cases
- Single node: one level, average equals that single node's value.
- Very large values causing potential sum overflow: worth flagging in fixed-width-integer languages (less of a concern in JavaScript's native numbers, but a real consideration in strictly-typed languages with bounded integer sizes) — could compute a running average incrementally instead of a full sum-then-divide if overflow were a genuine concern.
- Negative values mixed with positive at the same level: summation and division handle this naturally, no special-casing needed.

### Follow-up Questions
- "Extend to find the maximum (not average) value per level?" → Replace the running sum with a running max (`Math.max(currentMax, node.val)`), initialized appropriately (e.g., `-Infinity`) at the start of each level.
- "What if the tree is extremely wide, and level-by-level sums could be a performance concern?" → The per-level work is already O(level size), so total work across all levels is still O(n) — no inherent performance concern beyond the already-discussed O(n) space for the queue itself at its widest point.

## Problem 5 — Minimum Depth of Binary Tree (BFS with Early Termination)

### Problem
Given the root of a binary tree, find its minimum depth — the number of nodes along the shortest path from the root down to the nearest leaf node.

```
Input:
        3
       / \
      9   20
         /  \
        15   7

Output: 2   (path 3 → 9 is the shortest root-to-leaf path)
```

### Pattern Recognition
BFS with early termination — since BFS explores level by level, the very first leaf encountered is guaranteed to be at the minimum depth, allowing immediate return without exploring the rest of the tree.

### Key Insight
DFS would need to fully explore a branch (potentially very deep) before confirming no shallower leaf exists elsewhere; BFS's level-by-level guarantee means the first leaf found is provably the shallowest possible, since every node at a shallower level has already been checked (and found to not be a leaf) before any deeper-level node is even considered.

### Approach
BFS, tracking each queued node's depth alongside it. Upon dequeuing a node with no children (a leaf), immediately return its depth — no need to process any further remaining nodes.

### Solution

```js
function minDepth(root) {
  if (root === null) return 0;

  const queue = [[root, 1]];

  while (queue.length > 0) {
    const [node, depth] = queue.shift();

    if (node.left === null && node.right === null) {
      return depth;
    }

    if (node.left !== null) queue.push([node.left, depth + 1]);
    if (node.right !== null) queue.push([node.right, depth + 1]);
  }

  return 0;
}
```

### Dry Run

```
Tree:
        3
       / \
      9   20
         /  \
        15   7

queue=[[3,1]]

dequeue [3,1]: node=3, depth=1. left(9)!==null, right(20)!==null → not a leaf
  enqueue [9,2], [20,2] → queue=[[9,2],[20,2]]

dequeue [9,2]: node=9, depth=2. left===null, right===null → LEAF!
  return 2 immediately — no need to examine [20,2] or anything beneath it

Result: 2 ✓ (correctly the shortest path, without ever needing to explore the
  20→15/7 subtree, which is deeper and thus irrelevant to the MINIMUM depth)
```

### Complexity
- Time: O(n) worst case (e.g., if the minimum-depth leaf happens to be the very last node explored, such as in a tree where one long branch has no leaf until near the very bottom, while all other branches are even longer) — but often much better in practice due to early termination, especially when a shallow leaf exists.
- Space: O(n) worst case for the queue (bounded by tree width, same as standard level order traversal).

### Edge Cases
- Empty tree: explicit early return of 0.
- Single node (root is also a leaf): first dequeue immediately finds `node.left === null && node.right === null`, returns depth 1.
- Root has only one child (e.g., only a left child, no right child): a common trap — the root itself is NOT a leaf in this case (it has one child), so the algorithm correctly continues to the next level rather than mistakenly treating a single-child node as if a "missing" child branch counts as depth-0 termination; this specific case is a classic bug source if the leaf-check condition is written incorrectly (e.g., checking only `node.left === null` without also checking `node.right === null`).
- Completely unbalanced tree (linked-list shape): minimum depth equals maximum depth equals `n`, and BFS explores the entire tree before finding the single leaf at the very end — no early-termination benefit in this specific worst-case shape, correctly still O(n).

### Follow-up Questions
- "Why not just use DFS here, since DFS is often simpler for tree problems?" → See Q9/Q21 — DFS lacks BFS's natural "shallower nodes are guaranteed processed first" property, making early termination for a MINIMUM (not maximum) depth query much less natural to express correctly with DFS.
- "What if you needed MAXIMUM depth instead?" → BFS loses its early-termination advantage entirely for maximum depth (you'd need to fully explore every level regardless), making a simple recursive DFS (or a BFS that simply tracks the last-seen depth without early exit) equally reasonable choices for that specific variant.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve traversing a tree or graph level by level, or a BFS-shaped exploration?
│
├── STANDARD LEVEL ORDER TRAVERSAL (flat list, or grouped by level)?
│   └── Queue-based BFS; snapshot queue.length at the start of each level's loop
│       to correctly isolate one level from the next
│
├── ALTERNATING DIRECTION PER LEVEL (zigzag)?
│   └── Same level-grouping BFS + a toggling direction flag
│       (build reversed levels via front-insertion, or push-then-reverse for large levels)
│
├── ONLY NEED ONE NODE PER LEVEL (rightmost/leftmost visible node)?
│   └── Same level-grouping BFS; keep only the first (`i===0`) or last
│       (`i===levelSize-1`) node processed per level
│
├── NEED AN AGGREGATE PER LEVEL (average, max, sum)?
│   └── Same level-grouping BFS; accumulate the aggregate within each level's inner loop
│
├── NEED MINIMUM DEPTH / SHORTEST PATH TO ANY TARGET?
│   └── BFS with EARLY TERMINATION — the first qualifying node found via BFS
│       is guaranteed to be at the minimum depth/distance; DFS lacks this guarantee
│
├── TREE HAS MORE THAN 2 CHILDREN PER NODE (N-ARY)?
│   └── Same BFS structure; enqueue `node.children` (an array) instead of left/right
│
├── TRAVERSING A GENERAL GRAPH (not a tree — cycles/multiple paths possible)?
│   └── Same BFS structure, PLUS a `visited` set, marking nodes visited AT ENQUEUE TIME
│       (not dequeue time) to prevent duplicate enqueuing and infinite loops
│
├── MULTIPLE STARTING POINTS SPREADING SIMULTANEOUSLY (e.g., multi-source rot/fire spread)?
│   └── Multi-Source BFS — seed the queue with ALL sources at distance 0 upfront,
│       achieving O(V+E) instead of O(k × (V+E)) for k separate single-source BFS runs
│
└── WANT LEVEL-GROUPED OUTPUT BUT PREFER RECURSION OVER AN EXPLICIT QUEUE?
    └── DFS-based level grouping — recurse while tracking depth, append to result[depth]
        (trades BFS's width-bounded queue space for DFS's depth-bounded call-stack space)
```

## Common Bugs Checklist

Before submitting any level order traversal / BFS solution, verify:

1. **`levelSize` (queue length) snapshotted BEFORE the inner loop begins, not recomputed during it?** — Recomputing `queue.length` inside the inner loop incorrectly pulls in next-level nodes that were just enqueued as children of the current level's nodes.

2. **Efficient dequeue used, not a naive `Array.shift()` in a tight loop (if performance at scale matters)?** — `shift()` is O(n) per call, turning an intended O(n) traversal into O(n²); an index-based front pointer or proper queue structure avoids this.

3. **Graph BFS: `visited` marked at ENQUEUE time, not dequeue time?** — Marking at dequeue time allows the same node to be enqueued multiple times before any of those duplicates is processed, risking both correctness issues and unnecessary work.

4. **Right/left side view: checking the correct index (`i === levelSize - 1` for right, `i === 0` for left), not accidentally checking node structure (e.g., `node.right === null`) instead of level position?** — The "side view" is about a node's position within its level's left-to-right processing order, not about which child pointers it happens to have.

5. **Minimum depth: leaf check requires BOTH `node.left === null` AND `node.right === null`?** — Checking only one side incorrectly treats a node with exactly one child as if it were a leaf, producing a wrong (too-small) minimum depth.

6. **Multi-source BFS: ALL sources added to the queue (and marked visited) BEFORE the main loop begins, not one at a time interleaved with processing?** — Seeding all sources upfront, simultaneously, is what correctly models "spreading at the same time" rather than serially from one source before starting the next.

7. **Zigzag traversal: direction flag toggled exactly once per level (after the inner loop completes), not accidentally toggled per-node inside the inner loop?** — Toggling too frequently (or not at the right point) scrambles the intended alternating pattern.

8. **Empty tree / empty starting queue handled explicitly?** — `root === null` (or an empty sources list for multi-source BFS) should short-circuit to an appropriate empty/default result rather than proceeding into a loop that assumes at least one valid starting node.

---

**Final Tip:** At the 5 YOE level, interviewers expect immediate recognition that "level order traversal" means queue-based BFS, with the `levelSize`-snapshot technique as the load-bearing detail that separates a correct level-grouping implementation from a subtly broken one. From there, nearly every variant covered here — zigzag, side view, level averages, minimum depth, N-ary trees, general graphs, multi-source spread — is the *same* core BFS loop with one targeted modification layered on top. Being able to name that one modification explicitly ("keep only the last node per level," "add a visited set at enqueue time," "seed multiple sources upfront," "terminate early on the first leaf found") is what demonstrates real pattern recognition, rather than treating each variant as an unrelated problem to solve from scratch.
