# DSA: Serialize and Deserialize a Binary Tree — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What does it mean to "serialize" and "deserialize" a binary tree, and why is this non-trivial?**
A: **Serialization** converts a binary tree (an in-memory pointer-based structure) into a flat string (or byte sequence) that can be stored to disk, sent over a network, or cached. **Deserialization** reconstructs the original tree from that string. This is non-trivial because a sequence of node values alone is ambiguous — multiple structurally different trees can produce the same list of values (e.g., inorder traversal of different BSTs can yield the same sequence). The key challenge is encoding **structural information** (specifically, the presence or absence of children, including `null` positions) into the output, so that deserialization can unambiguously reconstruct both the values and the exact shape.

```
Tree A:          Tree B:
    1               1
   /                 \
  2                   2

Both have values [1, 2] in inorder — yet structurally different.
Serialization must distinguish them.
```

**Q2. Why is a single traversal (like inorder) insufficient for unique reconstruction, and what is the minimum information needed?**
A: A single traversal discards structural information about `null` positions. For example, the inorder sequence `[1, 2, 3]` could correspond to multiple tree shapes (a balanced tree with `2` at the root, or a right-skewed chain, etc.), with no way to distinguish them from the sequence alone. The minimum information needed is either:
- **One traversal + explicit `null` markers** (marks where children are absent), which alone is sufficient for unique reconstruction from a single traversal.
- **Two traversals combined** (e.g., preorder + inorder, or postorder + inorder) without null markers — but this only works for trees with **unique node values** and requires both sequences to be stored and matched during deserialization.

For the general case (potentially duplicate values, simplest implementation), a single traversal with explicit null markers is the standard, robust approach.

**Q3. How does preorder traversal with null markers produce a uniquely deserializable encoding, and what is the core insight?**
A: In a preorder traversal (`root → left → right`), the first value encountered is always the root of the current subtree. When `null` children are also recorded as a sentinel (e.g., `"#"` or `"null"`), the encoding contains enough information to unambiguously reconstruct the entire tree recursively: read the first token — if it's a sentinel, the current subtree is empty (base case); otherwise, it's the root's value, and the next tokens (recursively) define the left subtree, followed by the right subtree. This mirrors the exact recursive structure of preorder traversal itself, making deserialization a natural mirror of serialization.

```
Tree:            Preorder with null markers:
    1
   / \           "1,2,#,#,3,4,#,#,5,#,#"
  2   3
     / \
    4   5

Reading left-to-right:
- 1 → root
- 2 → left child of 1
- # → left child of 2 is null
- # → right child of 2 is null (2's subtree done)
- 3 → right child of 1
- 4 → left child of 3
- # → left of 4 is null
- # → right of 4 is null (4's subtree done)
- 5 → right child of 3
- # → left of 5 is null
- # → right of 5 is null (3's and 1's right subtree done)
```

**Q4. What is the time and space complexity of serialize/deserialize using preorder with null markers?**
A: Both serialization and deserialization visit every node exactly once (including null sentinels, of which there are always exactly `n+1` for a tree with `n` nodes), giving O(n) time for both operations. Space is O(n) for the output string and O(h) for the recursion call stack during both operations (where h is the tree height — O(log n) for balanced, O(n) worst case for a skewed tree). Total string length is O(n) — specifically, a tree with `n` nodes produces a string of `2n+1` tokens (n node values + n+1 null markers).

**Q5. Why does the recursive deserializer use a shared mutable index (or iterator) rather than passing substring indices, and what happens if you try to split the string naively instead?**
A: Deserialization is inherently sequential — tokens are consumed one by one in the exact order they were produced by the preorder traversal. A shared mutable index (or an iterator over the token list) correctly models this sequential consumption: each recursive call picks up exactly where the previous one left off, without any token being processed twice or skipped. Attempting to use substring indices naively (e.g., splitting the remaining string at each recursive call) would require knowing in advance how many tokens each subtree consumes — which is precisely the information you don't have until you've recursed through the subtree, making it circular and error-prone. The iterator pattern avoids this entirely by letting the state advance implicitly as recursion proceeds.

```js
// Correct: shared index / iterator advances globally
function deserialize(data) {
  const tokens = data.split(",");
  let idx = 0; // shared, mutates across all recursive calls

  function helper() {
    if (tokens[idx] === "#") { idx++; return null; }
    const node = new TreeNode(parseInt(tokens[idx++]));
    node.left = helper();
    node.right = helper();
    return node;
  }

  return helper();
}

// Incorrect pattern: splitting string per call loses positional state
// and can't know where the left subtree ends and right subtree begins
```

### Section 2: Approaches & Trade-offs

**Q6. What are the main serialization strategies, and what are the trade-offs between them?**
A:

| Strategy | Encoding | Unique reconstruction? | Notes |
|---|---|---|---|
| Preorder + null markers | `"1,2,#,#,3"` | Yes, with any values | Standard choice — simple, no value restrictions |
| Level-order (BFS) + null markers | `"1,2,3,#,#,4,5"` | Yes, with any values | More natural for LeetCode-style input; slightly more complex deserialization |
| Inorder + null markers | `"#,2,#,1,#,3,#"` | Yes, with any values | Less intuitive; left-recursive deserialization more error-prone |
| Preorder + Inorder (no nulls) | Two separate arrays | Only if all values unique | Requires two traversals; breaks with duplicates |
| Postorder + null markers | `"#,#,2,#,#,4,#,#,5,3,1"` | Yes, with any values | Reads right-to-left during deserialization — less natural but valid |

For most interview settings, **preorder with null markers** is recommended: easiest to reason about, clean recursive structure, no restrictions on node values.

**Q7. How does level-order (BFS) serialization differ from preorder, and when might you prefer it?**
A: Level-order serialization uses a queue to visit nodes breadth-first, recording each node's value (or a sentinel for `null` children). The resulting string lists nodes row by row, top to bottom — which is exactly the format used in LeetCode's tree representation. Deserialization pairs each recorded node with its left and right children by consuming the token list with a queue-based approach: for each non-null parent dequeued, the next two tokens become its left and right children (which are themselves enqueued if non-null). This approach is preferred when the input/output format is already expected to be in BFS order (common in competitive programming judges or serialization APIs that need human-readable layer-by-layer layout), or when downstream consumers care about level-by-level ordering for display purposes. Its code is slightly more involved than the preorder version since it requires explicit queue management on both sides.

```js
function serialize(root) {
  if (!root) return "#";
  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const node = queue.shift();
    if (node === null) {
      result.push("#");
    } else {
      result.push(String(node.val));
      queue.push(node.left);   // push even if null — will be recorded as "#"
      queue.push(node.right);
    }
  }

  return result.join(",");
}

function deserialize(data) {
  if (data === "#") return null;
  const tokens = data.split(",");
  const root = new TreeNode(parseInt(tokens[0]));
  const queue = [root];
  let i = 1;

  while (queue.length > 0 && i < tokens.length) {
    const node = queue.shift();

    if (tokens[i] !== "#") {
      node.left = new TreeNode(parseInt(tokens[i]));
      queue.push(node.left);
    }
    i++;

    if (i < tokens.length && tokens[i] !== "#") {
      node.right = new TreeNode(parseInt(tokens[i]));
      queue.push(node.right);
    }
    i++;
  }

  return root;
}
```

**Q8. Can you serialize a BST more compactly than a general binary tree, and why?**
A: Yes. For a BST with all unique values, a preorder traversal **without any null markers** uniquely determines the tree, because the BST's ordering property encodes the structural information implicitly. During deserialization, you know exactly where to insert each value — left subtree values are smaller than the current root, right subtree values are larger — so the BST structure is fully determined by the preorder sequence alone. This saves the `n+1` null sentinel tokens needed for a general binary tree. The trade-off: this compactness only works for BSTs with unique values; any violation (non-BST ordering, or duplicate values) makes reconstruction ambiguous without null markers.

```js
// BST serialization — no null markers needed
function serializeBST(root) {
  const result = [];
  function preorder(node) {
    if (!node) return;
    result.push(node.val);
    preorder(node.left);
    preorder(node.right);
  }
  preorder(root);
  return result.join(",");
}

// BST deserialization — reconstruct using BST insertion
function deserializeBST(data) {
  if (!data) return null;
  const vals = data.split(",").map(Number);

  function insert(node, val) {
    if (!node) return new TreeNode(val);
    if (val < node.val) node.left = insert(node.left, val);
    else node.right = insert(node.right, val);
    return node;
  }

  let root = null;
  for (const val of vals) root = insert(root, val);
  return root;
}
```

**Q9. How would you handle serializing a binary tree with potentially duplicate node values using preorder + inorder (without null markers), and why is this approach more fragile?**
A: Preorder + inorder reconstruction works by locating the root (first element of preorder) within the inorder array to determine the left/right subtree split, then recursing on each portion. This breaks with duplicates because the same value appearing multiple times in the inorder array makes it impossible to reliably locate the boundary between left and right subtrees — you can't tell which occurrence of a value is "the root" in the inorder sequence. Workarounds (like attaching indices to values to distinguish duplicates) add complexity and negate the approach's simplicity advantage. The null-marker approach avoids this entirely by encoding structure explicitly rather than relying on value uniqueness for disambiguation — making it strictly more robust and the preferred general-purpose approach.

### Section 3: Edge Cases & Tricky Scenarios

**Q10. How does your serialization approach handle a null root (empty tree)?**
A: The null root should be handled as its very first case — returning a well-defined empty-tree sentinel (e.g., `""`, `"#"`, or `"[]"` depending on convention) during serialization, and returning `null` immediately when that sentinel is detected during deserialization. Failing to handle this upfront causes either a null-pointer exception during serialization (when the code tries to access `root.val` without checking) or an incorrect reconstruction (interpreting an empty input as a non-empty tree) during deserialization. Always treat the empty-tree case as an explicit and deliberate first check, not an afterthought.

**Q11. What happens if node values themselves contain the delimiter character (e.g., a comma), and how would you defend against this?**
A: If node values are arbitrary strings (rather than guaranteed integers), a value like `"he,llo"` would be split into two tokens `["he", "llo"]` during deserialization, corrupting the token stream. Defenses: (1) choose a delimiter that can't appear in node values (e.g., `|` or a non-printable character if values are printable ASCII); (2) escape the delimiter character within values before serializing and unescape during deserialization; (3) use a length-prefixed encoding (e.g., `"5:hello"` rather than comma-delimited), which is delimiter-agnostic entirely; (4) use a structured format like JSON that handles escaping automatically. In interview settings, this concern is usually sidestepped by stating integer-valued nodes — worth acknowledging the assumption explicitly rather than pretending the problem is trivially delimiter-safe for all cases.

**Q12. How do you serialize a very deep tree (e.g., 10,000+ levels) without hitting a stack overflow from recursion?**
A: The recursive preorder approach uses O(h) call stack depth — fine for h = 30–50 (balanced trees up to ~10^9 nodes), but dangerous for a skewed tree with h = 10,000 (each node has only a right child, for example), which easily blows the default call stack. The solution is an **iterative** implementation using an explicit stack (for DFS/preorder) or queue (for BFS/level-order) to manage traversal state in heap memory rather than the call stack. The level-order (BFS) approach from Q7 is naturally iterative and avoids this concern entirely. For preorder specifically, maintain an explicit stack: push nodes, pop and record values, push right child then left child (so left is processed first, matching preorder order).

```js
// Iterative preorder serialization — safe for deep trees
function serializeIterative(root) {
  if (!root) return "#";
  const result = [];
  const stack = [root];

  while (stack.length > 0) {
    const node = stack.pop();
    if (node === null) {
      result.push("#");
    } else {
      result.push(String(node.val));
      stack.push(node.right); // push right first so left is processed first
      stack.push(node.left);
    }
  }

  return result.join(",");
}
```

**Q13. A colleague claims "just use JSON.stringify on the tree object — that serializes it." What's wrong with this?**
A: `JSON.stringify` on a raw `TreeNode` object works if each node is a plain object with enumerable `val`, `left`, `right` fields — but it has several problems in practice: (1) it preserves field names verbatim, making the output verbose and tied to the exact property naming convention of the class; (2) for class instances with methods, prototype chain, or non-enumerable properties, `JSON.stringify` silently omits them without error, potentially losing data or producing an incomplete representation; (3) cyclic references (theoretically shouldn't exist in a tree, but easy to introduce with parent pointers) will throw; (4) the deserialization side requires `JSON.parse` plus manual reconstruction of `TreeNode` class instances (since `JSON.parse` produces plain objects, not instances with class methods), adding a mapping step. For integers-only trees and quick prototyping it's arguably fine — but it's not a production-grade or interview-correct "serializer" in the full sense because it doesn't produce a compact, self-describing, implementation-agnostic encoding.

### Section 4: Advanced Patterns

**Q14. How would you serialize an N-ary tree (nodes with an arbitrary number of children)?**
A: The core idea remains the same — record values and structural boundaries — but children must now be delimited since their count varies per node. Two common approaches:
- **Child count prefix**: encode each node as `val,childCount` before listing its children recursively. During deserialization, read val and childCount, then recurse exactly `childCount` times to build children.
- **Level-separator sentinel**: use a special sentinel (e.g., `"$"`) to signal "end of this node's children list" during a preorder traversal. During deserialization, collect children until the sentinel is encountered.

```js
// N-ary: child count prefix approach
function serializeNAry(root) {
  if (!root) return "#";
  const result = [];

  function dfs(node) {
    if (!node) return;
    result.push(`${node.val},${node.children.length}`);
    for (const child of node.children) dfs(child);
  }

  dfs(root);
  return result.join(",");
}

function deserializeNAry(data) {
  if (data === "#") return null;
  const tokens = data.split(",");
  let idx = 0;

  function helper() {
    const val = parseInt(tokens[idx++]);
    const childCount = parseInt(tokens[idx++]);
    const node = new Node(val);
    for (let i = 0; i < childCount; i++) {
      node.children.push(helper());
    }
    return node;
  }

  return helper();
}
```

**Q15. How would you serialize ONLY the structure of a binary tree (no values), and reconstruct it exactly?**
A: Encode the tree purely as a sequence of structural decisions: `0` for "null child" and `1` for "non-null child" in a preorder traversal. A tree with `n` internal nodes produces a string of `2n+1` bits (n non-null nodes + n+1 null leaves) — just the structure, no values at all. This is a **succinct representation** of tree topology, useful when values are stored separately or when only the shape needs to be transmitted.

```js
// Structure-only serialization: '1' = node exists, '0' = null
function serializeStructure(root) {
  const bits = [];
  function dfs(node) {
    if (!node) { bits.push('0'); return; }
    bits.push('1');
    dfs(node.left);
    dfs(node.right);
  }
  dfs(root);
  return bits.join('');
}

function deserializeStructure(data, values) {
  // values[] provides the node values in preorder; structure guides the tree shape
  let idx = 0, valIdx = 0;
  function helper() {
    if (data[idx++] === '0') return null;
    const node = new TreeNode(values[valIdx++]);
    node.left = helper();
    node.right = helper();
    return node;
  }
  return helper();
}
```

**Q16. How would you serialize a binary tree to a compact binary (byte-level) format rather than a human-readable string, and what are the trade-offs?**
A: Instead of comma-separated ASCII digits, encode each node's value as a fixed-width integer in binary (e.g., 4 bytes per value) and encode null sentinels as a reserved bit flag or a reserved value (e.g., `INT_MIN = -2^31`). This reduces output size significantly — a tree with integer values produces 4 bytes per node versus potentially many more bytes per node in ASCII (e.g., `"2147483647"` is 10 bytes as ASCII vs. 4 bytes in binary). Trade-off: the binary format is not human-readable, harder to debug, and requires careful handling of endianness for cross-platform compatibility. For interview purposes, the ASCII/string approach is almost always expected — but acknowledging the binary alternative and its space advantages signals deeper systems-level awareness.

**Q17. "Walk me through how you'd serialize and then deserialize the binary tree below, step by step."**
```

   / \
  2   3
     / \
    4   5
```
A: I'd use preorder traversal with `"#"` as the null sentinel, comma-separated.

**Serialization (recursive preorder):**
- Visit 1 → output `"1"`
- Recurse left to 2 → output `"2"`
- 2's left is null → output `"#"`
- 2's right is null → output `"#"`
- Recurse right to 3 → output `"3"`
- 3's left is 4 → output `"4"`
- 4's left is null → output `"#"`
- 4's right is null → output `"#"`
- 3's right is 5 → output `"5"`
- 5's left is null → output `"#"`
- 5's right is null → output `"#"`
- Final string: `"1,2,#,#,3,4,#,#,5,#,#"`

**Deserialization (shared index, consuming tokens left-to-right):**
- tokens: `[1, 2, #, #, 3, 4, #, #, 5, #, #]`, idx=0

    - node(2).right = `helper()`: token[3]=# → return null, idx=4
    - return node(2)
  - node(1).right = `helper()`: token[4]=3 → create node(3), idx=5
    - node(3).left = `helper()`: token[5]=4 → create node(4), idx=6
      - node(4).left = `helper()`: token[6]=# → return null, idx=7
      - node(4).right = `helper()`: token[7]=# → return null, idx=8
      - return node(4)
    - node(3).right = `helper()`: token[8]=5 → create node(5), idx=9
      - node(5).left = `helper()`: token[9]=# → return null, idx=10
      - node(5).right = `helper()`: token[10]=# → return null, idx=11

  - return node(1) ← the root

**Q18. "Your interviewer says the tree could be extremely deep — up to 100,000 nodes in a right-skewed chain. What changes in your implementation?"**
A: The recursive approach breaks here — 100,000 levels of recursion will overflow the call stack (typical limits are ~10,000–15,000 frames). I'd switch to an iterative implementation for both serialize and deserialize. For serialization, an explicit stack handles preorder iteration; for deserialization, an explicit stack simulates the recursion by tracking "which subtree to fill next" — pushing `(parentNode, 'left')` and `(parentNode, 'right')` entries to represent pending children, consuming tokens in order. Alternatively, I'd simply use the BFS/level-order approach (Q7), which is naturally iterative on both sides and handles any depth without concern.

**Q19. "How would you test that your serialize/deserialize implementation is correct?"**
A: The key property is round-trip fidelity: `deserialize(serialize(root))` must produce a tree identical in both structure and values to `root`. I'd write a `treesAreEqual(t1, t2)` helper that recursively checks both structure and values, then test against:
- A null/empty tree.
- A single-node tree.
- A perfect binary tree (all levels full).
- A completely left-skewed and a completely right-skewed tree (stress-tests depth handling and the null-marker count).
- A tree where `p === q` for some nodes (duplicate values) — confirms the encoding handles duplicates without ambiguity.
- A tree with negative values and `0` — confirms the sentinel character `"#"` is not confused with any valid node value.
- Serializing the deserialized result again (`serialize(deserialize(serialize(root)))`) — the output string should be identical to the first serialization, confirming idempotence.

**Q20. "What if you need to serialize the tree in a way that's readable by a system written in a different language (say, Python deserializing a string produced by a Java serializer)?"**
A: This is a cross-language interoperability concern. The key requirements: (1) agree on the exact delimiter and sentinel convention upfront (e.g., comma-separated, `"null"` as the sentinel rather than `"#"`, which is more explicit); (2) use a language-agnostic value encoding — standard decimal integers are universally parseable; (3) avoid any language-specific formatting (e.g., Java's `toString()` on TreeNode objects, or Python-specific repr syntax); (4) document the format contract (preorder? level-order? null sentinel?) explicitly so either language can independently implement it correctly. If the teams are willing to adopt a standard, using JSON (e.g., `[1, 2, 3, null, null, 4, 5]` in LeetCode's level-order convention) is a robust choice — JSON is universally parseable and human-readable, at the cost of slightly more verbosity than a custom delimiter scheme.

**Q21. "The tree has `parent` pointers in addition to `left` and `right`. Do you need to serialize them?"**
A: No — parent pointers are redundant information that can be fully reconstructed during deserialization. A parent pointer for any node `N` is just a reference back to whichever node has `N` as its `left` or `right` child — information that's already encoded in the tree structure itself. Including parent pointers in the serialization would double-count structural information, increase output size, and introduce potential inconsistency (a corrupt or mismatched parent pointer in the serialized output could silently produce a broken deserialized tree). The correct approach: serialize only `val`, `left`, and `right` as usual; during deserialization, reconstruct parent pointers in a second pass (or on-the-fly during recursive construction by passing the current parent reference down into each recursive call as a parameter).

## Problem 1 — Serialize and Deserialize Binary Tree (Preorder, Recursive)

### Problem
Design an algorithm to serialize a binary tree to a string and deserialize that string back to the original tree. No constraints on the format — design your own encoding.

```
Input:
    1
   / \
  2   3
     / \
    4   5

serialize(root) → "1,2,#,#,3,4,#,#,5,#,#"
deserialize("1,2,#,#,3,4,#,#,5,#,#") → original tree
```

### Pattern Recognition
Preorder traversal with null markers — the most direct approach, exploiting preorder's property that the root is always the first token, enabling clean recursive reconstruction.

### Key Insight
Null markers make the token stream self-describing: each subtree's "start" is always the very next unconsumed token, and a `"#"` token unambiguously signals an empty subtree, enabling the deserializer to mirror the serializer's recursive structure exactly without needing any additional boundary markers.

### Approach
Serialize: recursively record the current node's value (or `"#"` if null), then recurse left, then right. Deserialize: maintain a shared index into the token array; consume one token per recursive call — if `"#"`, return null; otherwise create a node with that value and recurse for left and right children.

### Solution

```js
class Codec {
  serialize(root) {
    const result = [];

    function dfs(node) {
      if (node === null) {
        result.push("#");
        return;
      }
      result.push(String(node.val)); // record current node
      dfs(node.left);                // then left subtree
      dfs(node.right);               // then right subtree
    }

    dfs(root);
    return result.join(",");
  }

  deserialize(data) {
    const tokens = data.split(",");
    let idx = 0; // shared index — advances across all recursive calls

    function helper() {
      if (tokens[idx] === "#") {
        idx++;
        return null; // null sentinel — empty subtree
      }

      const node = new TreeNode(parseInt(tokens[idx++]));
      node.left = helper();  // next tokens define left subtree
      node.right = helper(); // tokens after that define right subtree
      return node;
    }

    return helper();
  }
}
```

### Complexity
- **Serialize:** O(n) time — each node visited once. O(n) space — output string, O(h) call stack.
- **Deserialize:** O(n) time — each token consumed once. O(n) space — tree nodes created, O(h) call stack.
- Total tokens in output: `2n + 1` (n node values + n+1 null markers — always exactly one more null marker than nodes in any binary tree).

### Edge Cases
- Null root: `dfs(null)` immediately pushes `"#"`, producing `"#"`. `deserialize("#")` immediately returns `null`. ✓
- Single-node tree (no children): produces `"val,#,#"` — the root value with two null markers for its two absent children. ✓
- All-left-skewed tree: produces `n` values followed by `n+1` consecutive `"#"` markers. Deserialization consumes them correctly via the shared index. ✓
- Negative values and zero: `parseInt` handles negatives (`"-5"`) and zero (`"0"`) correctly. The `"#"` sentinel is not a valid integer and is unambiguously distinguishable. ✓

### Follow-up Questions
- "Can you make this iterative to handle very deep trees?" → See Problem 3 for the iterative preorder approach.
- "What if you had to use BFS order instead?" → See Problem 2 for the level-order approach.

## Problem 2 — Serialize and Deserialize (Level-Order / BFS)

### Problem
Same problem as Problem 1, but the serialized format must be level-order (BFS) — matching the LeetCode tree input convention.

```
Input:
    1
   / \
  2   3
     / \
    4   5

serialize(root) → "1,2,3,#,#,4,5"
```

### Pattern Recognition
BFS serialization with null markers — use a queue to traverse level-by-level, recording null sentinels for missing children; deserialization pairs each parent with its next two tokens from the queue.

### Key Insight
In a BFS encoding, each non-null node at position `i` in the token list corresponds to exactly the `ceil(i/2)`-th node in level-order (1-indexed), and its two children are the next two un-assigned tokens. A queue naturally tracks which node to assign children to next, maintaining this pairing without any explicit index arithmetic.

### Approach
Serialize: use a queue seeded with the root; dequeue each node, record its value (or `"#"` if null), and enqueue its children (only if the parent is non-null). Deserialize: read the first token as root; use a queue of nodes waiting for their children; for each dequeued parent, consume the next two tokens as left and right children, enqueuing any non-null ones.

### Solution

```js
class Codec {
  serialize(root) {
    if (!root) return "#";
    const result = [];
    const queue = [root];

    while (queue.length > 0) {
      const node = queue.shift();

      if (node === null) {
        result.push("#");
        // don't enqueue children of a null node
      } else {
        result.push(String(node.val));
        queue.push(node.left);  // enqueue child regardless — null handled above on dequeue
        queue.push(node.right);
      }
    }

    return result.join(",");
  }

  deserialize(data) {
    if (data === "#") return null;
    const tokens = data.split(",");
    const root = new TreeNode(parseInt(tokens[0]));
    const queue = [root];
    let i = 1;

    while (queue.length > 0) {
      const node = queue.shift();

      // assign left child
      if (tokens[i] !== "#") {
        node.left = new TreeNode(parseInt(tokens[i]));
        queue.push(node.left);
      }
      i++;

      // assign right child
      if (i < tokens.length && tokens[i] !== "#") {
        node.right = new TreeNode(parseInt(tokens[i]));
        queue.push(node.right);
      }
      i++;
    }

    return root;
  }
}
```

### Edge Cases
- Null root: serializes to `"#"`, deserialized by the upfront `if (data === "#") return null` check. ✓
- Tree with only left children (skewed): level-order correctly encodes the alternating node/null pattern; each level has exactly one non-null node and one null. ✓

- "What's the advantage of the BFS approach over the DFS approach for serialization?" → The BFS output matches the natural "layer by layer" intuition and is the most human-readable; it's also naturally iterative (no recursion depth concern), making it safer for very deep trees.

## Problem 3 — Iterative Serialize/Deserialize (Stack-Based, for Deep Trees)

### Problem
Implement an iterative (non-recursive) serialize and deserialize that won't stack-overflow on extremely deep trees (e.g., 100,000 nodes in a right-skewed chain).

### Pattern Recognition
Explicit stack simulating preorder DFS — replace the call stack with a heap-allocated stack, pushing right children before left so left is processed first, exactly mirroring the preorder recursive approach.

### Key Insight
The recursive call stack during a preorder DFS can be exactly replicated by an explicit stack of "tasks" (nodes to visit), where pushing right before left ensures left-first processing. The deserialization direction is trickier: each token consumed must also track whether it belongs to a pending left or right slot, which can be encoded as stack entries of `(parentNode, "left" | "right")`.

### Approach
**Serialize:** push root onto stack; while not empty, pop a node; if null, push `"#"` to output; else push value to output and push right child then left child (so left is processed first next iteration). **Deserialize:** create root from first token; push `(root, "right")` then `(root, "left")` onto a stack; while not empty, pop a `(parent, side)` entry, consume the next token — if `"#"`, assign null to that side; else create a new node, assign it to that side, and push its two `(newNode, side)` entries.

### Solution

```js
// Iterative serialize
function serializeIterative(root) {
  if (!root) return "#";
  const result = [];
  const stack = [root];

  while (stack.length > 0) {
    const node = stack.pop();

    if (node === null) {
      result.push("#");
    } else {
      result.push(String(node.val));
      stack.push(node.right); // push right first so left is popped (processed) first
      stack.push(node.left);
    }
  }

  return result.join(",");
}

// Iterative deserialize
function deserializeIterative(data) {
  const tokens = data.split(",");
  if (tokens[0] === "#") return null;

  const root = new TreeNode(parseInt(tokens[0]));
  // stack entries: [parentNode, side ('left' | 'right')]
  const stack = [
    [root, "right"],
    [root, "left"],   // left is on top → processed first, matching preorder
  ];
  let i = 1;

  while (stack.length > 0 && i < tokens.length) {
    const [parent, side] = stack.pop();

    if (tokens[i] === "#") {
      parent[side] = null; // explicit null assignment
    } else {
      const node = new TreeNode(parseInt(tokens[i]));
      parent[side] = node;
      stack.push([node, "right"]); // right pushed first → left processed first
      stack.push([node, "left"]);
    }

    i++;
  }

  return root;
}
```

- Time: O(n) — each node and null token processed once.

### Edge Cases
- Right-skewed tree with 100,000 nodes: stack grows to O(n) on the heap safely — exactly what this approach is designed to handle. ✓
- Alternating left/right nodes: the push-right-first convention ensures correct preorder ordering regardless of tree shape. ✓

### Follow-up Questions
- "Could you use a generator/coroutine to serialize lazily (one token at a time)?" → Yes — a generator function that `yield`s each token on demand produces the serialization without building the full string in memory first, enabling streaming serialization of very large trees.

## Problem 4 — Deserialize Only (Given a Preorder Sequence, Reconstruct)

### Problem
You are given only a preorder traversal sequence with null markers (as an array of integers/nulls, rather than a string), and asked to reconstruct the binary tree. This tests whether you understand that the shared-index/iterator pattern is the core insight — the "split by comma" step is just a preprocessing detail.

```
Input: [1, 2, null, null, 3, 4, null, null, 5, null, null]
Output: the reconstructed tree
```

### Pattern Recognition
Direct application of the shared-index iterator pattern — the array is already tokenized, so the problem reduces to the core deserialization logic with no string-splitting step.

### Key Insight
Preorder + null markers in an array form is even cleaner: there's no delimiter parsing, just index-stepping. The shared index advancing through the array is a perfect model of "consuming the token stream in the exact order it was produced."

### Approach
Initialize a shared index at 0. Define `helper()`: check `arr[idx] === null`; if so, increment idx and return `null`. Otherwise, create a node with `arr[idx++]`, recurse for left, recurse for right, and return the node.

### Solution

```js
function buildTree(preorder) {
  let idx = 0;

  function helper() {
    if (idx >= preorder.length || preorder[idx] === null) {
      idx++;
      return null;
    }

    const node = new TreeNode(preorder[idx++]);
    node.left = helper();
    node.right = helper();
    return node;
  }

  return helper();
}
```

- Array is `[null]`: `helper()` immediately returns null. ✓
- Array where all non-null values are the same (duplicate values): the null-marker approach handles this — reconstruction is unambiguous since structure comes from the null tokens, not value uniqueness. ✓

### Follow-up Questions
- "How does this change if you're given postorder + null markers instead of preorder?" → The structure is mirrored: read from the END of the array instead of the start, and recurse right-then-left instead of left-then-right. A shared index decrementing from `arr.length - 1` toward 0 models this correctly.

## Quick Reference — Pattern Decision Tree

```
Need to serialize/deserialize a binary tree?
│
├── GENERAL BINARY TREE (no BST ordering, no special constraints)?
│   ├── Single query, recursion depth safe → Preorder + null markers, recursive
│   │     → O(n) time, O(h) space. Simplest implementation.
│   │
│   ├── Very deep tree (risk of stack overflow)? → Preorder + null markers, ITERATIVE
│   │     → O(n) time, O(h) heap space. Explicit stack replaces call stack.
│   │
│   └── Need BFS/level-order format (LeetCode convention, human-readable by level)?
│         → Level-order (BFS) with null markers, naturally iterative
│           → O(n) time, O(n) space (queue). No recursion depth concern.
│
├── BINARY SEARCH TREE (all values unique)?
│   └── Preorder traversal WITHOUT null markers (BST ordering encodes structure)
│         → More compact output (n tokens vs. 2n+1 for general binary tree)
│         → Requires BST insertion for deserialization → O(n log n) for balanced BST
│
├── N-ARY TREE (arbitrary number of children)?
│   └── Child-count prefix per node: "val,childCount" before listing children
│         → O(n) time, O(n) space. Works for any branching factor.
│
├── ONLY STRUCTURE (no values) needs encoding?
│   └── Succinct 1-bit-per-node encoding: '1'=node, '0'=null in preorder
│         → n bits for n nodes (most compact possible representation)
│
└── CROSS-LANGUAGE / INTEROP REQUIREMENT?
      └── Use JSON-compatible level-order format (LeetCode convention)
            → Universally parseable, human-readable, standardized delimiter/escaping
```

## Common Bugs Checklist

Before submitting any serialize/deserialize solution, verify:

1. **Null root handled before any logic that accesses `root.val` or `root.left`?** — A missing null check causes a null-pointer exception on the empty tree, which is the first test case in most judges.

2. **Shared index (or iterator) is genuinely shared across all recursive calls — not a local variable re-initialized per call?** — If the index resets per call, each subtree starts reading from token 0 instead of picking up where the previous call left off, producing a completely wrong tree from any input with more than one node.

3. **Null sentinel character (`"#"`) cannot appear as a valid node value?** — If node values are strings or could be `"#"`, use a different sentinel (e.g., `"null"` spelled out, or a length-prefixed format). State this assumption explicitly.

4. **Right child pushed BEFORE left child onto the stack in the iterative approach?** — Stacks are LIFO: push right first so left is popped and processed first, correctly producing preorder (root → left → right) ordering. Reversing the push order produces reverse-preorder (root → right → left), a silent logic bug that produces a mirror of the correct tree.

5. **BFS deserializer increments `i` for BOTH left and right tokens, even when the token is `"#"` (null)?** — A null child still consumes a token in the stream. Skipping the `i++` for null tokens desynchronizes the token index from the queue of parents, pairing children with the wrong parents for all subsequent nodes.

6. **For the BST-specific approach: deserialization uses BST insertion (not arbitrary node creation)?** — Since no null markers are present, the tree shape must be reconstructed from the BST ordering property. Inserting each value correctly into the BST is the only way to recover the original structure.

7. **Token count matches expected for round-trip: a tree with n nodes should produce exactly 2n+1 tokens with preorder + null markers?** — A quick sanity check: `tokens.length === 2 * nodeCount + 1`. Mismatches indicate a missing null sentinel, a double-written node, or an off-by-one in the null-push logic.

8. **Deserialization for level-order: children enqueued only for NON-null parent nodes?** — Enqueueing children for a null node causes the queue to process phantom nodes, consuming tokens out of sync and producing garbage structure.

**Final Tip:** At the 5–7 YOE level, interviewers expect you to immediately choose the right encoding and articulate *why* — not just produce working code. The clearest signal of depth: explaining that null markers make a single traversal sufficient and uniquely decodable; recognizing that the shared mutable index is the crux of the deserializer (not the string-splitting); noting that the BST variant can shed null markers entirely due to the ordering invariant; and proactively flagging the iterative fallback for deep trees before being asked. Bonus signal: connecting the preorder + null marker token stream to a context-free grammar (`T → "val" T T | "#"`) — the tree's structure is encoded as a regular language over that grammar, and deserialization is simply parsing it.
