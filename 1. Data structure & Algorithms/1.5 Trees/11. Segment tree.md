## Topic A: Segment Tree Fundamentals

### Section A1: Fundamentals

**Q1. What is a segment tree, and what class of problems does it solve efficiently?**

A: A segment tree is a binary tree built over an array where each node stores the result of a *merge operation* (sum, min, max, GCD, XOR, or any associative function) applied to a contiguous subrange of the array. The root covers the full array; each internal node covers the union of its children's ranges; each leaf covers exactly one element. It solves the problem of *dynamic range queries* — answering queries of the form "what is the sum/min/max of elements in range [l, r]?" in O(log n), while also supporting *point updates* (changing one element) in O(log n) and, with lazy propagation, *range updates* (changing all elements in a range) also in O(log n). The key problems that call for a segment tree are: range queries with interleaved point or range updates; offline queries that can't be answered by a simple prefix-sum array because the underlying array changes.

```
Problem class → Right tool:
  Static array, range min/max → sparse table (O(1) query, O(n log n) build)
  Static array, range sum     → prefix sum array (O(1) query, O(n) build)
  Dynamic array, range sum    → BIT/Fenwick tree (O(log n), simpler code)
  Dynamic array, range min/max or range update → segment tree (O(log n), more powerful)
  Dynamic array, complex merge (custom associativity) → segment tree only
```

**Q2. What is the array-based segment tree, and how does the parent-child index mapping work?**

A: The segment tree is stored implicitly in a flat array using 1-based indexing, following the same heap-like layout as a binary heap. Root occupies index 1; for any internal node at index `i`: its left child is at `2*i` and its right child is at `2*i+1`. Conversely, the parent of node `i` is at `Math.floor(i/2)`. Leaf nodes (individual elements) occupy the deepest level. This layout eliminates the need for explicit `left`/`right` pointers and makes cache access more predictable. The array must be sized at `4*n` — not `2*n` — to safely accommodate the worst-case tree structure when `n` is not a power of 2 (explained in Q7).

```
Array: [3, 1, 4, 1, 5]  (0-indexed input, n=5)
Segment tree (1-indexed nodes):

        node 1 [0..4] = 14 (sum)
       /                    \
  node 2 [0..2]=8      node 3 [3..4]=6
  /          \           /         \
node 4[0..1]=4  node 5[2..2]=4  node 6[3..3]=1  node 7[4..4]=5
  /      \
node 8[0..0]=3  node 9[1..1]=1

Parent of node i: i >> 1
Left child of i: 2*i     Right child of i: 2*i+1
```

**Q3. What is the "associative merge" property, and why is it the necessary and sufficient condition for a segment tree to work?**

A: The merge function `f(a, b)` must be **associative**: `f(f(a, b), c) = f(a, f(b, c))`. This is necessary because the segment tree computes a range's result by merging sub-results from the left and right children — so the order of internal merges must not affect the final answer. It is also sufficient: any associative function can be the merge operation, and the segment tree will correctly answer range queries for it. Commutativity (`f(a,b) = f(b,a)`) is *not* required — the tree always queries in left-to-right order, so non-commutative operations (like matrix multiplication or string concatenation) are also supported. Correct identity elements (the value returned for an out-of-range node that doesn't affect the final answer) must also be chosen: 0 for sum, +∞ for min, −∞ for max, 0 for XOR, 1 for product.

```
Operation   Associative?  Identity element  Works as merge?
sum (+)         ✓              0                  ✓
min             ✓             +∞                  ✓
max             ✓             −∞                  ✓
GCD             ✓              0                  ✓
XOR             ✓              0                  ✓
average         ✗              —                  ✗ (need sum + count separately)
arbitrary fn?   must verify   must choose         only if associative
```

**Q4. How is a segment tree built from an array, and what is the invariant after build?**

A: Build is a recursive post-order traversal: recurse to both children first, then assign the current node's value as `merge(left child, right child)`. Leaf nodes (where `start === end`) are assigned `arr[start]` directly. The build is O(n) — each of the at most 4n nodes is visited exactly once. The invariant after build: *`tree[node]` equals the result of applying the merge function to all elements in the range `[start, end]` that node covers*. This invariant is maintained by every subsequent update operation.

```js
function build(arr, node, start, end, tree) {
  if (start === end) {
    tree[node] = arr[start];        // leaf: direct element
    return;
  }
  const mid = (start + end) >> 1;
  build(arr, 2*node, start, mid, tree);       // build left subtree
  build(arr, 2*node+1, mid+1, end, tree);     // build right subtree
  tree[node] = tree[2*node] + tree[2*node+1]; // merge: replace + with Math.min/Math.max for those variants
}
// Call: build(arr, 1, 0, n-1, tree)
```

**Q5. How does a range query traverse the tree, and why is it O(log n)?**

A: For a range query `[l, r]`, each node's range `[start, end]` falls into exactly one of three cases: (1) **No overlap** — `r < start || end < l` — return the identity element immediately; (2) **Complete containment** — `l <= start && end <= r` — return `tree[node]` immediately without recursing; (3) **Partial overlap** — recurse into both children and merge their results. The O(log n) guarantee: at each level of the tree, at most four nodes can be "partially overlapping" (the two left-boundary nodes and two right-boundary nodes of the query range). All other nodes at that level return immediately via case 1 or case 2. Since there are O(log n) levels, at most O(4 log n) = O(log n) nodes are visited in total.

```js
function query(node, start, end, l, r, tree) {
  if (r < start || end < l) return 0;           // case 1: no overlap → identity
  if (l <= start && end <= r) return tree[node]; // case 2: fully covered → return immediately
  const mid = (start + end) >> 1;
  const leftAns  = query(2*node, start, mid, l, r, tree);    // case 3: partial
  const rightAns = query(2*node+1, mid+1, end, l, r, tree);
  return leftAns + rightAns; // merge
}
// Call: query(1, 0, n-1, l, r, tree)
```

**Q6. How does a point update propagate through the tree, and what invariant does it maintain?**

A: A point update at index `idx` with new value `val` follows the root-to-leaf path (O(log n) nodes). At the leaf `start === end === idx`, set `tree[node] = val`. On the way back up (post-order), recompute each ancestor as `tree[node] = merge(tree[2*node], tree[2*node+1])`. The invariant maintained: after the update, every ancestor of the updated leaf reflects the correct merge of its entire range, incorporating the new value. Nodes on other branches of the tree are unaffected and remain correct — the structural property that makes point updates O(log n) rather than O(n).

```js
function update(node, start, end, idx, val, tree) {
  if (start === end) {         // reached the leaf
    tree[node] = val;
    return;
  }
  const mid = (start + end) >> 1;
  if (idx <= mid) update(2*node, start, mid, idx, val, tree);
  else            update(2*node+1, mid+1, end, idx, val, tree);
  tree[node] = tree[2*node] + tree[2*node+1]; // recompute after child update ← MUST NOT FORGET
}
```

**Q7. Why does the segment tree array need 4n space rather than 2n?**

A: In a *perfect* binary tree (all levels completely filled), n leaves require exactly `2n − 1` total nodes — so `2n` space suffices for a power-of-2 input size. But when n is not a power of 2, the last level of the tree is partially filled. The tree height is `h = ⌈log₂(n)⌉`, and the maximum number of nodes at the deepest level that the 1-indexed layout might access is `2^h`, which can be up to `4n − 5` in the worst case (e.g., n = 2^k + 1 requires nearly `4 × 2^k` entries). The safe rule: *always allocate `4n` entries*. Some implementations allocate `2 × (next power of 2 ≥ n)`, which is equivalent but less portable. Using `2n` silently causes out-of-bounds writes for non-power-of-2 inputs — one of the most common subtle bugs.

```
n=5 (not a power of 2):
  Tree height h = ⌈log₂(5)⌉ = 3. Max node index accessed = 2^(h+1) - 1 = 15.
  But 2n = 10. Node 15 accessed → out-of-bounds if array size is 10! ✗
  4n = 20. Node 15 → safe. ✓

Safe formula: allocate new Array(4 * n).fill(identity)
```

**Q8. What changes structurally between range sum, range min, and range max — and what does not change?**

A: Exactly one thing changes: the merge operation and its identity element. The tree structure, the build algorithm, the query traversal (three-case descent), and the update propagation are all identical. For sum: merge = `(a, b) => a + b`, identity = `0`. For min: merge = `Math.min`, identity = `Infinity`. For max: merge = `Math.max`, identity = `-Infinity`. The key insight for interviews: a segment tree is parameterized by its merge function. Recognizing that a problem's "combine partial results" step is associative immediately unlocks the segment tree as a valid tool, regardless of what the merge function computes.

```
Range sum:  tree[node] = tree[left] + tree[right]      identity = 0
Range min:  tree[node] = Math.min(tree[left], tree[right]) identity = Infinity
Range max:  tree[node] = Math.max(tree[left], tree[right]) identity = -Infinity
Range GCD:  tree[node] = gcd(tree[left], tree[right])  identity = 0
Range XOR:  tree[node] = tree[left] ^ tree[right]      identity = 0
                                    ↑
              Only this line changes between variants. Everything else is identical.
```

**Q9. When is a segment tree the wrong tool, and what are the lighter-weight alternatives?**

A: Segment trees are powerful but complex — choose a lighter tool when it suffices. If the array is *static* (no updates): a prefix sum array answers range sum in O(1) after O(n) build; a sparse table answers range min/max in O(1) after O(n log n) build. If updates are *point-only* and the merge is sum (or XOR, or any operation with an inverse): a BIT (Fenwick tree) is half the code, same O(log n) complexity, and cache-friendlier. The segment tree is the right tool only when: (a) the merge has no inverse (so BIT can't do range queries); (b) range updates are needed (lazy propagation, not possible in a BIT without tricks); or (c) the merge is non-standard (e.g., storing min and max together, or a custom associative structure). Reaching for a segment tree when a prefix sum suffices is a common interview over-engineering mistake.

```
Update type → Query type → Recommended:
  None          Range sum            Prefix sum array O(1)
  None          Range min/max        Sparse table O(1)
  Point         Range sum/XOR        BIT O(log n) — simpler
  Point         Range min/max        Segment tree O(log n)
  Range         Any                  Segment tree + lazy O(log n)
  Complex merge Any                  Segment tree O(log n)
```

### Section A2: Advanced Patterns

**Q10. What is lazy propagation, and what problem does it solve that the basic segment tree cannot?**

A: Without lazy propagation, a *range update* (e.g., "add 5 to all elements in [l, r]") requires updating each individual leaf in the range — O(n) in the worst case. Lazy propagation solves this by *deferring* updates: when a range update completely covers a node's range, update that node's stored value immediately (to reflect the aggregate effect of the update on its range) but *mark* the node with a "lazy" pending value rather than recursing into its children. The children only receive the pending update when they are actually *accessed* — either for a future query or a future update that partially overlaps them. Since a node's correct aggregate value can be computed directly from the pending lazy value (e.g., add 5 to all n elements → tree[node] += 5 * n), range updates become O(log n) rather than O(n).

**Q11. What is the "pending update" invariant in lazy propagation, and what does `pushDown` enforce?**

A: The invariant has two parts: (1) `tree[node]` always holds the *correct aggregate value for its range*, fully incorporating any lazy values stored at node itself or any of its ancestors; (2) `lazy[node]` holds a pending operation that has been applied to `tree[node]` but *not yet propagated to its children*. Concretely: if `lazy[node] = k` (pending "add k to every element in this range"), then `tree[node]` already reflects the sum/min/max after adding k to every element in the range, but `tree[2*node]` and `tree[2*node+1]` do not. `pushDown(node)` enforces this invariant by propagating the pending value to both children before any recursive access: it updates `tree[child]` and accumulates into `lazy[child]`, then clears `lazy[node] = 0`. `pushDown` must be called before *every* recursive descent into children — both for queries and for updates.

```
Invariant after lazy update on node [0..4] with lazy=5 (range add):
  tree[node]    = correct sum for [0..4] (already includes +5 per element)   ✓
  lazy[node]    = 5  (pending, not yet in children)
  tree[2*node]  = stale sum for [0..2] (does NOT include +5 yet)             ← pushDown fixes this
  tree[2*node+1]= stale sum for [3..4]                                       ← pushDown fixes this

After pushDown(node):
  tree[2*node]  += 5 * 3 = 15   (3 elements in [0..2])
  lazy[2*node]  += 5
  tree[2*node+1]+= 5 * 2 = 10   (2 elements in [3..4])
  lazy[2*node+1]+= 5
  lazy[node]     = 0             (pending cleared)
```

**Q12. What are the two main types of lazy operations — additive vs assignment — and how does composition differ?**

A: **Additive lazy** (e.g., "add val to all elements in range"): lazy values *accumulate* — if a range already has pending +3 and receives another +5, the combined lazy is +8. Composition: `lazy[child] += parent_lazy`. Effect on tree: `tree[node] += lazy * rangeSize`. Identity (no pending operation): `lazy[node] = 0`. **Assignment lazy** (e.g., "set all elements in range to val"): a later assignment *overwrites* an earlier one — if a range has pending "set to 3" and receives "set to 7", the result is "set to 7". Composition: `lazy[child] = parent_lazy` (overwrite, not accumulate). Effect on tree: `tree[node] = lazy * rangeSize` (for sum) or `tree[node] = lazy` (for min/max, since all elements are the same). Identity (no pending): `lazy[node] = null` or a sentinel like `-Infinity`. **Mixed lazy** (both add and assign coexist) requires careful ordering: applying an assign *after* an add replaces both; applying an add *after* an assign only increments the assign's value — handled by checking which type is pending before composition.

```js
// Additive lazy — pushDown:
function pushDownAdd(node, start, end) {
  if (lazy[node] !== 0) {
    const mid = (start + end) >> 1;
    const leftSize = mid - start + 1, rightSize = end - mid;
    tree[2*node]   += lazy[node] * leftSize;  lazy[2*node]   += lazy[node];
    tree[2*node+1] += lazy[node] * rightSize; lazy[2*node+1] += lazy[node];
    lazy[node] = 0;
  }
}

// Assignment lazy — pushDown (for range max query):
function pushDownAssign(node) {
  if (lazy[node] !== -Infinity) { // -Infinity = no pending assignment
    tree[2*node] = tree[2*node+1] = lazy[node];
    lazy[2*node] = lazy[2*node+1] = lazy[node];
    lazy[node] = -Infinity;
  }
}
```

**Q13. What is coordinate compression in the segment tree context, and when is it required?**

A: Coordinate compression remaps a sparse set of values to a dense range `[0..m-1]` so a segment tree of size m (not the original value range, which could be huge) can be built. Required when: (a) values can be up to 10^9 but there are only n ≤ 10^5 distinct values — building a tree of size 10^9 is impossible; (b) the segment tree is keyed on *values* rather than *indices* (e.g., "count how many inserted values are less than x" — the tree is indexed by value, not array position). Implementation: collect all values that will ever appear (from the input), sort and deduplicate them into `coords`, then map each original value to its index in `coords` via binary search. All segment tree operations then use the compressed index instead of the raw value.

```js
// Coordinate compression setup:
const coords = [...new Set(values)].sort((a, b) => a - b);
const compress = v => {
  let lo = 0, hi = coords.length - 1;
  while (lo < hi) { const mid = (lo + hi) >> 1; coords[mid] < v ? lo = mid+1 : hi = mid; }
  return lo; // compressed index for value v
};
// Segment tree is now size coords.length, not max(values).
// Rule: compress values BEFORE any segment tree operation.
```

**Q14. What is a dynamic (implicit) segment tree, and when is it needed?**

A: A dynamic segment tree creates nodes only when they are first accessed, rather than pre-allocating all 4n nodes. Each node is explicitly created as an object with `{val, left, right, lazy}`, with children initialized to `null` and created on demand. This is needed when: (a) the coordinate space is enormous (e.g., [0..10^18]) and even coordinate compression isn't possible because the set of accessed values is unknown in advance (online queries); (b) memory is the bottleneck and most of the 4n range is never touched. The trade-off: pointer-based traversal is cache-unfriendly; node creation overhead per access; the savings materialize only when the number of distinct accessed coordinates m is much smaller than the full range N. Total nodes created is O(m log N) where m is the number of update operations.

**Q15. What is a segment tree keyed on values (not indices), and what counting problems does it solve?**

A: When the segment tree's leaves represent *values* (after coordinate compression) rather than array positions, the tree can answer "how many inserted values fall in the range [a, b]?" in O(log m) — a frequency/counting query. Common problems: "count of smaller numbers after self" (for each element, count already-processed elements with smaller value — insert right-to-left, query [0, val-1] for each element); "count inversions" (same pattern — count elements already seen that are larger than the current); "rank queries" (for a dynamically changing multiset, find the k-th smallest element via binary descent on the segment tree). The key: the tree is built on the *value axis*, each leaf represents one possible value, and `tree[node]` = count of inserted elements whose value falls in that node's range.

## Topic B: Related Data Structures and the Decision Framework

### Section B1: BIT vs Segment Tree

**Q16. What is a Binary Indexed Tree (Fenwick tree), and what operations does it support?**

A: A BIT (also called Fenwick tree) is a compact array-based structure that supports *point update* and *prefix query* in O(log n) with extremely simple code — about 5 lines per operation. Each index `i` in the BIT array stores the aggregate of a specific set of elements determined by the lowest set bit of `i`. The prefix query `[0, r]` is answered by summing O(log n) BIT entries; a range query `[l, r]` decomposes as `prefix(r) - prefix(l-1)`. Point update propagates to O(log n) BIT entries. The BIT works for operations with an *inverse* (so that `query(l, r) = query(r) - query(l-1)` is meaningful): sum (inverse = subtraction), XOR (inverse = XOR itself), product if no zeros (inverse = division). It does *not* support range min/max (no inverse), non-prefix queries, or range updates without additional structure.

**Q17. When should you choose a BIT over a segment tree?**

A: Choose a BIT when: the operation has an inverse (primarily sum or XOR); only point updates and range queries are needed (no range updates); code simplicity and constant-factor speed matter; competitive programming time limits are tight. BIT is roughly 2–3× faster in practice (better cache locality, no recursion, fewer memory accesses) and takes half the code. The rule of thumb: **try BIT first for sum-with-point-updates; fall back to segment tree for everything else**. A common interview trap is implementing a full segment tree for "range sum with point updates" — a BIT suffices and is noticeably simpler. Demonstrating knowledge of when *not* to use a segment tree is itself a positive signal.

**Q18. What operations require a segment tree that a BIT cannot handle?**

A: BITs cannot handle:
- **Range min or range max** — no inverse operation exists; `prefix_min(r) - prefix_min(l-1)` is meaningless
- **Range updates** — BITs can simulate range updates for sum via the "difference BIT" trick, but this doesn't extend to min/max
- **Non-prefix queries for non-invertible operations** — any query that can't be expressed as `prefix(r) XOR prefix(l-1)` or similar
- **Custom associative merge functions** — e.g., tracking both min and max simultaneously, or segment tree DP on ranges
- **Lazy propagation** — BITs have no concept of deferred propagation; range updates over non-invertible operations require a segment tree

### Section B2: Sparse Table vs Segment Tree

**Q19. What is a sparse table, and what does it trade for O(1) range queries?**

A: A sparse table precomputes answers for all ranges of the form `[i, i + 2^k - 1]` (power-of-2-length ranges starting at every position). For an idempotent operation (one where `f(a, a) = a` — specifically min and max), any range `[l, r]` can be answered in O(1) by overlapping two precomputed ranges: `f(sparse[log(r-l+1)][l], sparse[log(r-l+1)][r - 2^log + 1])`. The build is O(n log n) time and space. The trade: the array must be **static** (no updates — the precomputed table becomes stale on any modification); the operation must be **idempotent** (so overlapping ranges don't double-count — min/max are idempotent; sum is not). Sparse table is the optimal tool for offline, static range min/max queries (e.g., RMQ problems, LCA after Euler tour transformation).

**Q20. Summary decision framework: sparse table vs segment tree vs BIT vs prefix sum?**

A:

| Condition | Best Tool | Time per Op |
|---|---|---|
| Static array, range sum | Prefix sum | O(1) query |
| Static array, range min/max (idempotent) | Sparse table | O(1) query |
| Dynamic array, range sum, point update | BIT | O(log n) |
| Dynamic array, range min/max, point update | Segment tree | O(log n) |
| Dynamic array, range update + range query | Segment tree + lazy | O(log n) |
| Custom associative merge, any updates | Segment tree | O(log n) |
| Enormous value domain, sparse access | Dynamic segment tree | O(log N) |
| Offline, values compressible | Coordinate-compressed seg tree | O(log n) |

## Topic C: Cross-Topic & Interview-Style Questions

**Q21. Compare the prefix-sum array to the segment tree — same invariant, different trade-offs?**

A: Both maintain an invariant that enables range queries. A prefix sum array: `P[i]` = sum of `arr[0..i-1]`; range query = `P[r+1] - P[l]` in O(1); update = O(n) (must recompute all subsequent prefix sums). A segment tree: `tree[node]` = merge of its range; range query = O(log n); point update = O(log n). The prefix sum is the O(1)-query extreme with O(n)-update; the segment tree is the O(log n)-both extreme. The segment tree can be seen as a hierarchy of partial prefix sums — instead of one flat accumulation, the tree provides O(log n) levels of cached partial results, each recomputed in O(log n) on update. Prefix sum wins for static arrays or read-heavy workloads; segment tree wins when updates are as frequent as queries.

**Q22. How does the segment tree relate to divide-and-conquer?**

A: The segment tree is a *precomputed divide-and-conquer tree*. In classic divide-and-conquer for range problems, you'd recursively split the array in half, solve each half, and merge — O(n) per query. The segment tree precomputes and caches all possible subproblem answers (for all O(n) contiguous ranges representable as tree nodes), so a query only pays for the merging along O(log n) boundary nodes, not for recomputing subproblems from scratch. Updates are O(log n) because only the O(log n) ancestors of the changed element's cached result need to be recomputed. This is the "trade precomputation space for query speedup" pattern — the same insight as the BIT, sparse table, and LCA preprocessing.

**Q23. What is the "merge at a node" invariant, stated precisely for each standard operation?**

A: The invariant is: `tree[node]` = the result of applying the merge function to every element in the range `[start(node)..end(node)]`, as if it were computed directly from the original array at this moment. Specifically:

- **Range sum**: `tree[node]` = `arr[start] + arr[start+1] + ... + arr[end]`
- **Range min**: `tree[node]` = `Math.min(arr[start], ..., arr[end])`
- **Range max**: `tree[node]` = `Math.max(arr[start], ..., arr[end])`
- **With additive lazy**: `tree[node]` = the above value *after* all pending lazy additions at node and all its ancestors have been applied — i.e., the correct answer for the current array state, even though children haven't been updated yet
- **With assignment lazy**: `tree[node]` = the above value assuming every element in [start..end] has been set to `lazy[node]` if the lazy is pending, or is fully propagated downward otherwise

**Q24. What are the three cases in a range query, and what is the precise condition for each?**

A: For query range `[l, r]` at node covering `[start, end]`:
- **Case 1 — No overlap**: `r < start || end < l` → return identity. The query range doesn't touch this node's range at all.
- **Case 2 — Complete containment**: `l <= start && end <= r` → return `tree[node]` directly, without recursing. The query range fully covers this node's range — the precomputed `tree[node]` is the exact answer for this subrange.
- **Case 3 — Partial overlap**: everything else → recurse into both children, merge. The query boundary cuts through this node's range somewhere.

The asymmetry between cases 2 and 3 is the source of O(log n) efficiency: only O(log n) nodes undergo case 3 total (the boundary nodes at each level); all others hit case 1 or case 2 and return immediately.

**Q25. "In one sentence each, state the invariant for each variant."**

A:
- **Range sum, point update**: `tree[node]` always equals the sum of all current array values in its range, recomputed bottom-up after every point change.
- **Range min, point update**: `tree[node]` always equals the minimum current array value in its range, propagated upward from whichever child holds the smaller value.
- **Range max, point update**: `tree[node]` always equals the maximum current array value in its range, with the root always holding the global maximum.
- **Additive lazy (range add, range sum)**: `tree[node]` reflects the correct current sum for its range including all unapplied ancestor lazy values, while `lazy[node]` quantifies the pending per-element addition due to this node's children — a debt owed to the children but not yet delivered.
- **Assignment lazy (range set, range max)**: `tree[node]` equals the maximum of all elements in its range assuming `lazy[node]` has been assigned to every element if the lazy is active, and every child has been updated if the lazy is cleared.

## Problem 1 — Range Sum Query - Mutable

### Problem

Given an integer array `nums`, handle multiple queries of the following types: `update(index, val)` — sets `nums[index]` to `val`; `sumRange(left, right)` — returns the sum of elements between indices `left` and `right` inclusive. Both operations must be O(log n).

```
NumArray na = new NumArray([1, 3, 5]);
na.sumRange(0, 2); // returns 9
na.update(1, 2);   // nums = [1, 2, 5]
na.sumRange(0, 2); // returns 8
```

### Pattern Recognition
Segment tree with sum merge and point update — the canonical use case. `tree[node]` = sum of its range; update propagates up; query uses three-case descent.

### Key Insight
The `tree[node]` invariant (sum of range) is maintained by recomputing each ancestor on the root-to-leaf path after a point update. No lazy propagation needed — only single-element updates, so no range-update optimization is required.

### Approach
Build the tree in O(n) using post-order recursion. For `update`: recurse to the leaf, set its value, recompute ancestors. For `sumRange`: three-case descent, merging left + right child results.

### Solution

```js
class NumArray {
  constructor(nums) {
    this.n = nums.length;
    this.tree = new Array(4 * this.n).fill(0);
    this._build(nums, 1, 0, this.n - 1);
  }

  _build(nums, node, start, end) {
    if (start === end) {
      this.tree[node] = nums[start];
      return;
    }
    const mid = (start + end) >> 1;
    this._build(nums, 2*node,   start, mid);
    this._build(nums, 2*node+1, mid+1, end);
    this.tree[node] = this.tree[2*node] + this.tree[2*node+1]; // sum merge
  }

  update(index, val, node = 1, start = 0, end = this.n - 1) {
    if (start === end) {         // reached the target leaf
      this.tree[node] = val;
      return;
    }
    const mid = (start + end) >> 1;
    if (index <= mid) this.update(index, val, 2*node,   start, mid);
    else              this.update(index, val, 2*node+1, mid+1, end);
    this.tree[node] = this.tree[2*node] + this.tree[2*node+1]; // recompute ancestor ← critical
  }

  sumRange(left, right, node = 1, start = 0, end = this.n - 1) {
    if (right < start || end < left) return 0;             // case 1: no overlap → identity
    if (left <= start && end <= right) return this.tree[node]; // case 2: fully covered
    const mid = (start + end) >> 1;
    return this.sumRange(left, right, 2*node,   start, mid)  // case 3: partial — recurse both
         + this.sumRange(left, right, 2*node+1, mid+1, end);
  }
}
```

### Dry Run

```
    _build(2, 0, 1): mid=0
      _build(4, 0, 0): leaf → tree[4] = 1
      _build(5, 1, 1): leaf → tree[5] = 3
      tree[2] = tree[4]+tree[5] = 4
    _build(3, 2, 2): leaf → tree[3] = 5
    tree[1] = tree[2]+tree[3] = 9

  node=1 [0,2]: 0≤0 && 2≤2 → return tree[1]=9. ✓

  node=1 [0,2]: mid=1. index=1≤1 → go left.
  node=2 [0,1]: mid=0. index=1>0 → go right.

  Back at node=2: tree[2]=tree[4]+tree[5]=1+2=3.
```

### Complexity
- Build: O(n) — each node visited exactly once.
- Update / Query: O(log n) — root-to-leaf path has length log n; query visits at most 4 log n nodes.
- Space: O(n) — tree array of size 4n.

### Edge Cases
- Single element (n=1): tree has one leaf = root; update sets it directly; query of [0,0] returns it.
- Update to same value: no special case needed; recompute ancestors correctly.
- Query [l, r] = [0, n-1]: the root is fully covered; returns tree[1] in O(1).
- All elements identical: tree[root] = n * value; updates change exactly the ancestors of the updated leaf.

### Follow-up Questions
- "Switch to range min?" — Change `tree[node] = tree[left] + tree[right]` to `Math.min(...)` throughout, and the identity from `0` to `Infinity`. No other change.
- "Add range update support?" — Requires lazy propagation (Q10–Q12); see Problem 2.
- "What if n is very large but queries are sparse?" — Use a dynamic segment tree (Q14) to avoid allocating 4n upfront.

## Problem 2 — My Calendar III

### Problem

A `k`-booking happens when `k` events have overlapping time ranges. Implement `MyCalendarThree()` and `book(startTime, endTime)` — returns an integer `k` representing the maximum `k`-booking after adding the new event. The time range is `[startTime, endTime)` (half-open interval).

```
MyCalendarThree cal = new MyCalendarThree();
cal.book(10, 20); // returns 1
cal.book(50, 60); // returns 1
cal.book(10, 40); // returns 2
cal.book(5, 15);  // returns 3
cal.book(5, 10);  // returns 3
cal.book(25, 55); // returns 3
```

### Pattern Recognition
Dynamic segment tree with **additive lazy** (range add +1 for each booking) and **range max query** (maximum overlap count at any instant). A dynamic tree (nodes created on demand) is needed because time values can be up to 10^9.

### Key Insight
Each `book(s, e)` is a range update: "add 1 to every point in [s, e-1]." The answer is the maximum value anywhere in the tree — a range max query over the entire domain. The segment tree stores at each node the maximum overlap count in its range, and lazy propagation defers the +1 increments. After each update, the root holds the global maximum.

### Approach
Implicit tree (nodes created on demand as objects). Range update `[l, r]`: add 1 to range, update tree[node] = max in range after pending lazy; push down before recursing. Query: return tree[root]. Since we always query the entire domain, the root's value is the answer after each book.

### Solution

```js
class MyCalendarThree {
  constructor() {
    // Dynamic segment tree — nodes created on demand
    // Each node: { val: max overlaps in range, lazy: pending add }
    this.root = { val: 0, lazy: 0, left: null, right: null };
  }

  book(start, end) {
    this._update(this.root, 0, 1e9, start, end - 1, 1); // half-open [s,e) → closed [s,e-1]
    return this.root.val; // root always holds global max overlap count
  }

  _pushDown(node) {
    if (node.lazy !== 0) {
      for (const child of [node.left, node.right]) {
        if (child) {
          child.val  += node.lazy; // max of range [lo..hi] increases by lazy (all elements +lazy)
          child.lazy += node.lazy; // accumulate: child's pending now includes parent's pending
        }
      }
      node.lazy = 0;
    }
  }

  _update(node, lo, hi, l, r, val) {
    if (r < lo || hi < l) return;              // no overlap
    if (l <= lo && hi <= r) {
      node.val  += val;                        // fully covered: apply directly
      node.lazy += val;                        // mark pending for children
      return;
    }
    this._pushDown(node);                      // partial overlap: push down before recursing
    const mid = Math.floor((lo + hi) / 2);

    if (!node.left)  node.left  = { val: 0, lazy: 0, left: null, right: null };
    if (!node.right) node.right = { val: 0, lazy: 0, left: null, right: null };

    this._update(node.left,  lo,    mid, l, r, val);
    this._update(node.right, mid+1, hi,  l, r, val);
    node.val = Math.max(node.left.val, node.right.val); // merge: max of children
  }
}
```

### Dry Run

```
book(10, 20) → update [10, 19] with +1:
  root [0..1e9]: partial → pushDown (lazy=0, no-op). Create children.
  ... (recurse down) ... Eventually covers [10,19].
  Nodes covering [10,19] get val=1, lazy=1.
  Root.val = max in tree = 1. Return 1. ✓

book(10, 40) → update [10, 39] with +1:
  Range [10,19] already has lazy=1. When [10,39] update hits these nodes:
    If fully covered by [10,39]: val += 1 → val=2, lazy=2.
  Nodes in [20,39]: val=1, lazy=1 (newly covered).
  Root.val = max = 2. Return 2. ✓

book(5, 15) → update [5, 14] with +1:
  [10,14] was already at val=2. After +1: val=3.
  [5,9]: val=1.
  Root.val = max = 3. Return 3. ✓
```

### Complexity
- Time: O(log M) per `book`, where M = 10^9 (the time domain size). Each update/query visits O(log M) ≈ 30 nodes.
- Space: O(n log M) total nodes created across n bookings — each booking creates at most O(log M) new nodes.

### Edge Cases
- Non-overlapping bookings: all values stay at 1; max = 1.
- All bookings at same time: each adds 1 to the same range; max = number of bookings.
- Half-open interval: [startTime, endTime) → adjust to closed [startTime, endTime - 1] when calling update.
- `_pushDown` on a node with null children: guard with `if (child)` before accessing child fields.

### Follow-up Questions
- "Return whether a k-booking would be created before adding it (My Calendar II)?" — Store the max-overlap tree; before inserting, query max in [start, end-1]; return false if it would exceed 2.
- "Use coordinate compression instead of dynamic tree?" — Collect all unique start/end values first, compress to [0..m-1], build a static tree of size m. Simpler per-operation code; requires knowing all booking values ahead of time (offline).

## Problem 3 — Count of Smaller Numbers After Self

### Problem

Given an integer array `nums`, return an integer array `counts` where `counts[i]` is the number of smaller elements to the right of `nums[i]`.

```
Input:  nums = [5, 2, 6, 1]
Output: [2, 1, 1, 0]
  // 5: [2,6,1] → 2 smaller (2 and 1)
  // 2: [6,1]   → 1 smaller (1)
  // 6: [1]     → 1 smaller (1)
  // 1: []      → 0 smaller

Input:  nums = [-1, -1]
Output: [1, 0]
```

### Pattern Recognition
Segment tree on coordinate-compressed values + right-to-left processing. Process `nums` from right to left; for each `nums[i]`, query the count of already-inserted values in `[minVal, nums[i]-1]` (values strictly less), then insert `nums[i]` into the segment tree.

### Key Insight
The segment tree is indexed by *value* (after coordinate compression), not by position. Each leaf `v` holds the count of already-processed elements with compressed value `v`. A range sum query `[0, compress(nums[i]) - 1]` directly answers "how many processed elements are smaller than nums[i]?" Processing right-to-left ensures that when we query for `nums[i]`, all already-inserted elements are to its right.

### Approach
Collect and sort all unique values in `nums` to create a coordinate map. Build a segment-tree of size m (number of unique values). Process right-to-left: for each `nums[i]`, let `ci = compress(nums[i])`; query sum in `[0, ci-1]` → count of smaller; point-update `ci` by +1 (insert this value); record count.

### Solution

```js
function countSmaller(nums) {
  // Coordinate compression
  const sorted = [...new Set(nums)].sort((a, b) => a - b);
  const rank = new Map(sorted.map((v, i) => [v, i]));
  const m = sorted.length;

  const tree = new Array(4 * m).fill(0);

  function update(node, start, end, idx) {
    if (start === end) { tree[node]++; return; }
    const mid = (start + end) >> 1;
    if (idx <= mid) update(2*node, start, mid, idx);
    else            update(2*node+1, mid+1, end, idx);
    tree[node] = tree[2*node] + tree[2*node+1]; // count merge = sum
  }

  function query(node, start, end, l, r) {
    if (r < start || end < l || l > r) return 0; // guard: l > r when querying [0, -1]
    if (l <= start && end <= r) return tree[node];
    const mid = (start + end) >> 1;
    return query(2*node, start, mid, l, r)
         + query(2*node+1, mid+1, end, l, r);
  }

  const counts = new Array(nums.length).fill(0);
  for (let i = nums.length - 1; i >= 0; i--) {
    const ci = rank.get(nums[i]);
    counts[i] = query(1, 0, m-1, 0, ci-1); // count of values with rank < ci
    update(1, 0, m-1, ci);                   // insert this value
  }
  return counts;
}
```

```
sorted unique = [1, 2, 5, 6] → ranks: {1→0, 2→1, 5→2, 6→3}. m=4.

  query [0, -1]: l>r → return 0. counts[3]=0.
  update rank=0: tree[leaf_0]++. tree propagated.

i=2, nums[2]=6, rank=3:
  query [0, 2]: counts 1 (only rank=0 inserted). counts[2]=1.
  update rank=3.

  query [0, 0]: count ranks [0,0] → 1 (the "1" we inserted). counts[1]=1.
  update rank=1.

  query [0, 1]: count ranks [0,1] → 2 (values 1 and 2). counts[0]=2.
  update rank=2.

```

### Complexity
- Time: O(n log n) — coordinate compression O(n log n); n iterations each with O(log n) update + query.
- Space: O(n) — coordinate map O(n); segment tree O(m) ≤ O(n).

### Edge Cases
- All identical elements: all ranks equal; query `[0, rank-1]` is always empty; counts all zero.
- Negative numbers: coordinate compression handles negatives identically — they get non-negative ranks.
- Two equal adjacent elements (e.g., `[-1, -1]`): same rank, query `[0, rank-1]` for the first processed element (right one) returns 0; correct.
- Query with `ci = 0` (minimum element, nothing smaller): `query(1, 0, m-1, 0, -1)` → `l > r` guard returns 0 immediately.

### Follow-up Questions
- "Count of larger numbers after self?" — Query `[ci+1, m-1]` instead of `[0, ci-1]`.
- "Count inversions in the array?" — Same pattern: process left-to-right, query `[0, ci-1]` (count smaller elements already seen, i.e., to the left). Total inversions = sum of counts.
- "Replace segment tree with BIT?" — BIT on coordinate-compressed values gives the same O(n log n) with simpler code (sum with point update → BIT applies directly). This is the preferred approach when counting inversions or smaller elements, since BIT handles prefix-sum queries natively.

## Problem 4 — Falling Squares

### Problem

Several squares are dropped one at a time from the top. `positions[i] = [left_i, sideLen_i]` describes each square's left edge and side length (occupying columns `[left_i, left_i + sideLen_i - 1]`). Each square falls until it lands on the ground or on top of a previously fallen square. After each square lands, return the height of the tallest stack of squares currently present.

```
Input:  positions = [[1,2],[2,1],[1,5]]
Output: [2,3,8]  // After sq1: height 2. After sq2: rests on sq1 → height 3. After sq3: tallest 8.
```

### Pattern Recognition
Coordinate compression + segment tree with **assignment lazy** (range assign to new height) + **range max query** (tallest column in a range). Each square: (1) range max query to find the highest existing column in its footprint; (2) range assign to set all columns in its footprint to `queryMax + sideLen`.

### Key Insight
After a square lands, every column in its footprint is set to the *same* height (`landingHeight + sideLen`), regardless of prior varying heights. This is a range-set (assignment) operation, not a range-add. The lazy stores the assigned value; children are overwritten on pushDown.

### Approach
Collect all unique x-coordinates (left edges and right edges of all squares) for coordinate compression. For each square `[l, sLen]`: let `r = l + sLen - 1`; query max in compressed range `[compress(l), compress(r)]`; let `newHeight = queryMax + sLen`; range assign `newHeight` to `[compress(l), compress(r)]`; global max = Math.max(globalMax, newHeight).

### Solution

```js
function fallingSquares(positions) {
  // Coordinate compression: collect all unique x-coordinates
  const coords = [...new Set(positions.flatMap(([l, s]) => [l, l + s - 1]))].sort((a, b) => a - b);
  const compress = x => {
    let lo = 0, hi = coords.length - 1;
    while (lo < hi) { const mid = (lo + hi) >> 1; coords[mid] < x ? lo = mid+1 : hi = mid; }
    return lo;
  };
  const m = coords.length;

  const tree = new Array(4 * m).fill(0);
  const lazy = new Array(4 * m).fill(-1); // -1 = no pending assignment

  function pushDown(node) {
    if (lazy[node] !== -1) {
      // Assign the lazy value to both children (overwrite, not accumulate)
      tree[2*node]   = lazy[node];  lazy[2*node]   = lazy[node];
      tree[2*node+1] = lazy[node];  lazy[2*node+1] = lazy[node];
      lazy[node] = -1;
    }
  }

  function rangeSet(node, start, end, l, r, val) {
    if (r < start || end < l) return;
    if (l <= start && end <= r) {
      tree[node] = val; lazy[node] = val; // assign: overwrite stored max and mark pending
      return;
    }
    pushDown(node);            // partial overlap: push assignment to children first
    const mid = (start + end) >> 1;
    rangeSet(2*node,   start, mid, l, r, val);
    rangeSet(2*node+1, mid+1, end, l, r, val);
    tree[node] = Math.max(tree[2*node], tree[2*node+1]); // merge: max
  }

  function rangeMax(node, start, end, l, r) {
    if (r < start || end < l) return 0;
    if (l <= start && end <= r) return tree[node];
    pushDown(node);
    const mid = (start + end) >> 1;
    return Math.max(rangeMax(2*node, start, mid, l, r),
                    rangeMax(2*node+1, mid+1, end, l, r));
  }

  const result = [];
  let globalMax = 0;

  for (const [l, sLen] of positions) {
    const cl = compress(l), cr = compress(l + sLen - 1);
    const landingHeight = rangeMax(1, 0, m-1, cl, cr);  // tallest column in footprint
    const newHeight = landingHeight + sLen;
    rangeSet(1, 0, m-1, cl, cr, newHeight);             // set entire footprint to new height
    globalMax = Math.max(globalMax, newHeight);
    result.push(globalMax);
  }

  return result;
}
```

### Dry Run

```

Square [1,2] → footprint [1..2], compressed [0..1]:
  rangeMax([0,1]) = 0 (empty). newHeight = 0+2 = 2.
  rangeSet([0,1], 2): tree over [0..1] set to 2.
  globalMax = 2. result = [2].

Square [2,1] → footprint [2..2], compressed [1..1]:
  rangeMax([1,1]) = 2 (already set from previous square). newHeight = 2+1 = 3.
  rangeSet([1,1], 3): column 1 (x=2) set to 3. [0..0] stays at 2.
  globalMax = 3. result = [2,3].

Square [1,5] → footprint [1..5], compressed [0..3]:
  rangeMax([0,3]) = max(2,3,...) = 3. newHeight = 3+5 = 8.
  rangeSet([0,3], 8): all columns in [0..3] set to 8.
  globalMax = 8. result = [2,3,8]. ✓
```

### Complexity
- Time: O(n log n) — coordinate compression O(n log n); n squares each with O(log n) query and O(log n) range-set.
- Space: O(n) — tree and lazy arrays of size 4m where m ≤ 2n.

### Edge Cases
- Non-overlapping squares: each lands at height 0; stack grows only in its own footprint.
- Identical squares at the same position: each finds the previous square's top as its landing height; heights increase linearly.
- `lazy = -1` sentinel conflict: if a square's height could be -1 (impossible, sideLen ≥ 1 and ground height ≥ 0, so newHeight ≥ 1), the sentinel is safe.

### Follow-up Questions
- "What if heights can be set to 0 by a 'clear' operation?" — Need a different sentinel; use `null` or a separate boolean array `hasAssignment[node]`.
- "Use additive lazy instead?" — Assignment and add have different composition semantics (Q12); using additive lazy for range-set would require setting an element to a fixed value, which doesn't accumulate — assignment lazy is the correct choice here.

## Problem 5 — Number of Longest Increasing Subsequence

### Problem

Given an integer array `nums`, return the number of longest increasing subsequences. The answer is guaranteed to fit in a 32-bit integer.

```
Input: nums = [1, 3, 5, 4, 7]  → 2   // [1,3,5,7] and [1,3,4,7]
Input: nums = [2, 2, 2, 2, 2]  → 5   // each single [2] is an LIS of length 1
```

### Pattern Recognition
DP + segment tree with **custom merge** on coordinate-compressed values. For each element `nums[i]`, query the segment tree for the pair `(maxLen, countOfMaxLen)` over all values `< nums[i]`, extend to get `(maxLen+1, count)`, and update the tree at `nums[i]`'s position. The merge function combines two `(len, count)` pairs: keep the longer LIS length, accumulating counts if equal.

### Key Insight
The segment tree stores `(maxLISLen, count)` at each value-indexed leaf. For each `nums[i]`, we need: "among all previously processed elements with value strictly less than `nums[i]`, what is the maximum LIS length ending there, and how many such LIS exist?" A range query returns this `(len, count)` pair using the custom merge. The segment tree on values (not indices) makes this O(log n) per element instead of O(n).

### Approach
Coordinate-compress values. For each `nums[i]`: let `ci = compress(nums[i])`; query `[0, ci-1]` for `(prevLen, prevCount)`; `myLen = prevLen + 1`, `myCount = max(1, prevCount)`; update leaf `ci` with `(myLen, myCount)` — but *merge* with what's already there (same value might have appeared before). Final answer: query entire range `[0, m-1]` for global `(maxLen, totalCount)`.

### Solution

```js
function findNumberOfLIS(nums) {
  const sorted = [...new Set(nums)].sort((a, b) => a - b);
  const rank = new Map(sorted.map((v, i) => [v, i]));
  const m = sorted.length;

  // Each tree node stores [maxLen, countOfMaxLen] for its range
  const tree  = new Array(4 * m).fill(null).map(() => [0, 0]);

  // Merge two (len, count) pairs: take the longer LIS; tie-break by summing counts
  function merge(a, b) {
    if (a[0] > b[0]) return [a[0], a[1]];
    if (b[0] > a[0]) return [b[0], b[1]];
    return [a[0], a[1] + b[1]]; // equal lengths: sum the counts
  }

  function update(node, start, end, idx, val) {
    // val = [len, count] to store at leaf idx
    if (start === end) {
      tree[node] = merge(tree[node], val); // merge with existing: may already have (len, count) from same value
      return;
    }
    const mid = (start + end) >> 1;
    if (idx <= mid) update(2*node, start, mid, idx, val);
    else            update(2*node+1, mid+1, end, idx, val);
    tree[node] = merge(tree[2*node], tree[2*node+1]);
  }

  function query(node, start, end, l, r) {
    if (r < start || end < l || l > r) return [0, 0]; // identity: len=0, count=0
    if (l <= start && end <= r) return tree[node];
    const mid = (start + end) >> 1;
    return merge(query(2*node, start, mid, l, r),
                 query(2*node+1, mid+1, end, l, r));
  }

  for (const x of nums) {
    const ci = rank.get(x);
    const [prevLen, prevCount] = query(1, 0, m-1, 0, ci-1); // best LIS ending with value < x
    const myLen   = prevLen + 1;
    const myCount = Math.max(prevCount, 1); // if no predecessor, count = 1
    update(1, 0, m-1, ci, [myLen, myCount]);
  }

  const [, totalCount] = query(1, 0, m-1, 0, m-1); // get count of global max LIS
  return totalCount;
}
```

### Complexity
- Time: O(n log n) — n elements, each with O(log n) query + O(log n) update.
- Space: O(n) — tree of size 4m, m ≤ n.

### Edge Cases
- All identical elements (e.g., `[2,2,2]`): coordinate-compressed to rank 0; query `[0,-1]` → `[0,0]` (empty, no predecessor); each element starts a new LIS of length 1 with count 1; but the update merges with existing at rank 0, accumulating counts: `[1,1]`, `[1,2]`, `[1,3]`. Final answer: 3. Correct — each individual element is an LIS of length 1.
- Strictly decreasing: each element queries an empty range; every LIS has length 1; total count = n.
- Merging with existing at same leaf: the `merge` in `update`'s leaf case handles the "same value appears multiple times" scenario correctly — we don't overwrite, we merge.

### Follow-up Questions
- "Length of LIS only (not count)?" — Replace `(len, count)` pairs with plain integers; merge = max; use a BIT (simpler). This problem specifically requires the count, which is why the segment tree with custom merge is needed.
- "What if values are in range [0, 10^5]?" — No coordinate compression needed; build the segment tree directly over [0, 10^5].

## Problem 6 — Count of Range Sum

### Problem

Given an integer array `nums` and two integers `lower` and `upper`, return the number of range sums that lie in `[lower, upper]` (inclusive). A range sum `S(i, j)` is the sum of elements between indices `i` and `j` (where `i ≤ j`).

```
Input:  nums = [-2, 5, -1], lower = -2, upper = 2  → 3
  // Range sums: S(0,0)=-2 ✓, S(0,1)=3 ✗, S(0,2)=2 ✓,
  //             S(1,1)=5 ✗, S(1,2)=4 ✗, S(2,2)=-1 ✓

Input:  nums = [0], lower = 0, upper = 0  → 1
```

### Pattern Recognition
Prefix sum + coordinate-compressed segment tree (counting). For each right endpoint i (prefix sum `P[i]`), count how many previous prefix sums `P[j]` satisfy `lower ≤ P[i] - P[j] ≤ upper`, i.e., `P[i] - upper ≤ P[j] ≤ P[i] - lower`. Process left-to-right: for each `P[i]`, query count of already-inserted prefix sums in the window `[P[i]-upper, P[i]-lower]`, then insert `P[i]`.

### Key Insight
Computing `S(i, j) = P[j] - P[i-1]` reduces the count-of-range-sums problem to a counting problem on prefix sums: "for each j, how many already-processed P[i] (i < j) fall in [P[j]-upper, P[j]-lower]?" A segment tree keyed on prefix sum values (after coordinate compression) answers range count queries in O(log n). Processing left-to-right guarantees that only prefix sums P[0..j-1] are in the tree when querying for P[j].

### Approach
Compute all prefix sums `P[0..n]` (P[0]=0). Collect all values that could appear as left or right query bounds — specifically all `P[i]`, `P[i]-lower`, and `P[i]-upper` — into the coordinate compression set. For each P[i] (i from 0 to n): query count in `[P[i]-upper, P[i]-lower]`; then insert P[i].

### Solution

```js
function countRangeSum(nums, lower, upper) {
  const n = nums.length;
  const P = new Array(n + 1).fill(0);
  for (let i = 0; i < n; i++) P[i+1] = P[i] + nums[i];

  // Coordinate compression: all values we'll ever query or insert
  const allVals = [];
  for (const p of P) { allVals.push(p, p - lower, p - upper); }
  const coords = [...new Set(allVals)].sort((a, b) => a - b);
  const m = coords.length;
  const rank = new Map(coords.map((v, i) => [v, i]));

  const tree = new Array(4 * m).fill(0);

  function update(node, start, end, idx) {
    if (start === end) { tree[node]++; return; }
    const mid = (start + end) >> 1;
    if (idx <= mid) update(2*node, start, mid, idx);
    else            update(2*node+1, mid+1, end, idx);
    tree[node] = tree[2*node] + tree[2*node+1];
  }

  function query(node, start, end, l, r) {
    if (l > r || r < start || end < l) return 0; // guard l > r when window is empty
    if (l <= start && end <= r) return tree[node];
    const mid = (start + end) >> 1;
    return query(2*node, start, mid, l, r)
         + query(2*node+1, mid+1, end, l, r);
  }

  let count = 0;
  for (const p of P) {
    // Query: how many already-inserted prefix sums fall in [p-upper, p-lower]?
    const ql = rank.get(p - upper);
    const qr = rank.get(p - lower);
    count += query(1, 0, m-1, ql, qr);

    // Insert current prefix sum
    update(1, 0, m-1, rank.get(p));
  }

  return count;
}
```

### Dry Run

```

P    = [0, -2, 3, 2]
```

### Complexity
- Time: O(n log n) — coordinate compression O(n log n); n+1 iterations each with O(log n) query + update.
- Space: O(n) — prefix sums O(n); coordinate set O(n); tree O(n).

### Edge Cases
- `lower > upper`: impossible range → count = 0. The `l > r` guard in query handles this.
- Very large prefix sums (overflow risk): JavaScript numbers handle up to 2^53 safely; for very large inputs, BigInt may be needed.
- All zeros with `lower=0, upper=0`: every prefix sum P[j] - P[i] = 0 qualifies; count = n(n+1)/2.

### Follow-up Questions
- "Can this be solved with merge sort?" — Yes: a modified merge sort counts cross-half pairs satisfying the range condition during the merge step, also O(n log n). The segment tree approach is more general (works for online queries); merge sort is more cache-efficient for offline.
- "What if lower = upper = k (exact sum)?" — Simplifies to the "subarray sum equals k" prefix-sum + HashMap problem from the Two Sum family guide, which counts in O(n) rather than O(n log n).

## Quick Reference — Pattern Decision Tree

```
What type of range query problem is this?
│
├── STATIC array — no updates at all?
│   ├── Range sum             → Prefix sum array: O(1) query, O(n) build
│   └── Range min / max       → Sparse table: O(1) query, O(n log n) build
│
├── DYNAMIC array — point updates only?
│   ├── Range sum or XOR      → BIT (Fenwick tree): O(log n), simpler code
│   └── Range min / max       → Segment tree: O(log n)
│
├── DYNAMIC array — range updates + range queries?
│   ├── Range add, range sum  → Segment tree + additive lazy
│   │     tree[node] += lazy * rangeSize; lazy[child] += parent_lazy
│   ├── Range set, range max  → Segment tree + assignment lazy
│   │     tree[node] = lazy; lazy[child] = parent_lazy  (overwrite)
│   └── Mixed add + set       → Segment tree + careful lazy composition
│
├── SEGMENT TREE indexed on VALUES (not positions)?
│   ├── Count elements in value range [l, r]     → Range sum query on value axis
│   ├── Need to handle large value domain         → Coordinate compression first
│   └── Value domain unknown / huge at query time → Dynamic segment tree
│
├── CUSTOM MERGE function?
│   └── If associative + has identity element → Segment tree with custom merge
│         (GCD, XOR, (max, count), matrix product, etc.)
│
├── DP OPTIMIZATION?
│   └── dp[i] = merge(dp[j] for j in [0..i-1] with val[j] < val[i]) + cost(i)
│       → Segment tree on value axis; query before insert; update after
│
├── MULTIDIMENSIONAL range queries?
│   └── 2D range sum/max → Segment tree of segment trees (2D seg tree): O(log²N)
│       Or: 2D BIT for sum: O(log²N) simpler
│
└── TRICKY PROBLEM SIGNALS → probably segment tree:
    "After each insertion, query the maximum/minimum/sum in a range"
    "Count elements satisfying a value condition among those seen so far"
    "Update a contiguous range, then answer range queries"
    "Track intervals or bookings with arbitrary overlap queries"
```

## Common Bugs Checklist

Before submitting any segment tree solution, verify:

1. **Array sized at 4n, not 2n?** — For n not a power of 2, the 1-indexed array representation accesses node indices up to `4n`. Using `2n` causes silent out-of-bounds writes and wrong values with no error. Always: `new Array(4 * n).fill(identity)`.

2. **Wrong identity element for the merge operation?** — Using `0` as identity for range min returns wrong answers (0 may be larger than real elements); using `0` for range max gives wrong answers (0 may be smaller). Correct: `Infinity` for min, `-Infinity` for max, `0` for sum, `0` for XOR, `1` for product.

3. **Forgetting to recompute the parent after a recursive update?** — After `update(2*node, ...)` and `update(2*node+1, ...)`, the line `tree[node] = merge(tree[2*node], tree[2*node+1])` is mandatory. Omitting it leaves the parent stale — queries passing through it return wrong values silently.

4. **Calling `pushDown` AFTER recursing into children in lazy propagation?** — `pushDown` must be called BEFORE recursing into children in both `rangeUpdate` and `rangeQuery`. Pushing down after the recursion means children received stale data during their computation. The invariant requires children to reflect all pending updates before they are accessed.

5. **Calling `pushDown` on a leaf node?** — Leaf nodes have no children; calling `pushDown` on a leaf attempts to write to `tree[2*n]` and `tree[2*n+1]` which may be uninitialized or out-of-bounds. Guard with `if (start !== end) pushDown(node)` before recursing, OR call `pushDown` only when `start < end` (not at leaves).

6. **Additive lazy using `=` instead of `+=` for child lazy accumulation?** — Multiple pending additions to the same node must accumulate: `lazy[child] += parent_lazy`, not `lazy[child] = parent_lazy`. Overwriting with `=` discards any previously pending add on the child.

7. **Assignment lazy using `+=` instead of `=` for child lazy?** — Assignment lazy must overwrite: `lazy[child] = parent_lazy`. Using `+=` produces nonsensical "accumulated assignment" values rather than the correct final assigned value.

8. **Missing `l > r` guard in range query when `ci = 0`?** — When querying `[0, ci-1]` and `ci = 0` (the minimum element, nothing smaller), `l=0, r=-1` — an invalid range. The standard `r < start` check alone may not catch this; add `if (l > r) return identity` as the first line of the query function.

9. **Not pushing down before reading `tree[node]` for a partially overlapping query in lazy propagation?** — Even for a query (not an update), if the node is partially overlapping (case 3), you must push down before recursing, so children have correct values before they're queried. A query that skips pushDown in the partial-overlap case reads stale child values and produces wrong results.

10. **Coordinate compression mismatched between update and query keys?** — If `update` uses `rank.get(v)` and `query` uses `rank.get(v - lower)`, both must refer to the same coordinate map. If `v - lower` was not included in the coordinate set during setup, `rank.get(...)` returns `undefined`, silently indexing `tree[NaN]`. Always include ALL values that will ever appear as a query bound (both left and right) in the coordinate set before building the rank map.

---

**Final Tip:** At the 5 YOE level, the decisive signal for any segment tree problem is first identifying the *merge function and its identity element* — not the code structure. For range sum: "merge = +, identity = 0." For range min: "merge = Math.min, identity = Infinity." For LIS counting: "merge(a, b) = take the longer LIS; sum counts on tie — identity = (0, 0)." Once the merge function is named, the entire segment tree structure (build, query, update) follows as boilerplate with only those two lines changing. The second signal is identifying *whether lazy propagation is needed*: "point updates only → no lazy; range updates → lazy, and then: is the update additive (accumulate lazy) or assignment-based (overwrite lazy)?" Naming the lazy type in one sentence before writing any code — *"this is an additive lazy because adding 5 and then 3 to a range means adding 8 total"* vs. *"this is assignment lazy because setting a range to 7 after setting it to 3 just means setting it to 7"* — is the mark of an engineer who understands the structure rather than pattern-matching to a memorized template. Every bug in segment tree lazy propagation ultimately traces back to confusing these two lazy types or forgetting that `pushDown` is mandatory before accessing children in *both* updates and queries.
