## Topic A: Trie Fundamentals

### Section A1: Structure & Core Operations

**Q1. What is a Trie, and what class of problems does it solve more efficiently than a HashSet?**

A: A Trie (from re*trie*val, pronounced "try") is a tree where each node represents a character and each root-to-marked-node path spells a complete word. Every node holds: a children map or array (one slot per possible next character), and an `isEndOfWord` boolean flagging whether the path from the root to this node forms a complete word in the dictionary. A HashSet stores words as opaque strings and handles exact lookups in O(L) average (where L = word length). A Trie handles the same lookups but additionally enables prefix queries — "does any stored word start with prefix P?" — in O(|P|) rather than O(N × L) (scanning all N stored words). The Trie's structural advantage: shared prefixes are stored once, not once per word, so prefix traversal finds the entire equivalence class in one O(|P|) path walk rather than a full dictionary scan.

```
Problem class where Trie wins over HashSet:

HashSet for "words starting with 'app'":
  Scan all N words, check each: O(N × L). For N=100,000, L=10: 1,000,000 checks.

Trie for "words starting with 'app'":
  Walk root→a→p→p (3 steps), then DFS from 'p' node. O(|prefix| + output). ✓

Trie wins when:
  - Prefix search / autocomplete
  - Longest matching prefix (Replace Words)
  - Wildcard matching (WordDictionary)
  - Lexicographic enumeration of stored words
  - Multiple prefix queries on the same dictionary
```

**Q2. What are the two implementations of Trie node children, and when do you choose each?**

A: The children structure is the single most important design choice for a Trie:

**Array of size σ** (fixed alphabet size, e.g., 26 for lowercase letters): `children = new Array(26).fill(null)`. Access by index: `children[char.charCodeAt(0) - 97]`. O(1) access, zero hash overhead, excellent cache locality. Cost: σ null slots per node regardless of how many children actually exist — O(σ) space per node even for nodes with one child. Best for small fixed alphabets.

**HashMap** `{character → TrieNode}`: `children = new Map()`. Access: `children.get(char)`. O(1) average access. Cost: hash computation overhead, O(actual children) space per node — memory-efficient for sparse nodes or large alphabets (Unicode, alphanumeric, multi-byte). Best when the key space is large or sparse.

```
Array (26-slot):            HashMap:
children: [null, null, ..., TrieNode('p'), ..., null]  → fixed 26 entries
children: Map{'a' → TrieNode}                          → only actual children

Choose array when:   lowercase letters only (σ=26), performance critical
Choose HashMap when: uppercase+lower+digits (σ=62), Unicode, or memory-constrained

Space per node:
  Array: O(σ) = O(26) ≈ constant per node (but 26 pointers even for 1 child)
  HashMap: O(k) where k = number of distinct children at this node
```

**Q3. Walk through insert, search, and startsWith — state the invariant each maintains.**

A: All three operations traverse from the root character by character. They differ only in what they do at each node and what they return at the end:

**insert(word)**: create missing nodes along the path; mark `isEndOfWord = true` at the final node. Invariant: after insert, every prefix of `word` has a node, and the terminal node is marked as a word ending.

**search(word)**: follow the path character by character. If any character is missing (null child), return false. If the full path exists, return `node.isEndOfWord` — it must be a word ending, not just a prefix node. Invariant: search returns true iff `word` was previously inserted (not just a prefix of an inserted word).

**startsWith(prefix)**: same traversal as search. If any character is missing, return false. If the full prefix path exists, return true unconditionally — do not check `isEndOfWord`. Invariant: startsWith returns true iff any previously inserted word begins with `prefix`.

```
Illustrative difference:
  Trie contains: "apple"
  Nodes: root → a → p → p → l → e* (e has isEndOfWord=true)

  search("apple"):    traverse to e → isEndOfWord=true  → true ✓
  search("app"):      traverse to p (third node) → isEndOfWord=false → false ✓
  startsWith("app"):  traverse to p (third node) → path exists → true ✓
  startsWith("apz"):  traverse to a→p→ no 'z' child → false ✓

The isEndOfWord flag is what distinguishes search from startsWith.
```

**Q4. How does the `isEndOfWord` flag prevent false positives in search, and how does it handle overlapping words?**

A: Without the flag, any inserted word's prefix would falsely match as a complete word. With the flag, the Trie distinguishes between "a node that exists because some longer word passes through here" and "a node that is itself the end of a stored word." The flag also handles the case where one stored word is a prefix of another: inserting both `"app"` and `"apple"` sets `isEndOfWord = true` at both the `p` node (for `"app"`) and the `e` node (for `"apple"`). A single path can have multiple end-of-word markers — one at each stored word's terminal node.

```
Insert "app":    root→a→p→p*  (p marked isEndOfWord=true)
Insert "apple":  root→a→p→p→l→e*  (nodes p, l, e created; e marked)

After both inserts:
  Node 'p' (3rd): isEndOfWord=true  (end of "app")
  Node 'l' (4th): isEndOfWord=false (internal)
  Node 'e' (5th): isEndOfWord=true  (end of "apple")

search("app")   → reaches 3rd 'p', isEndOfWord=true  → true ✓
search("apple") → reaches 'e',    isEndOfWord=true  → true ✓
search("appl")  → reaches 'l',    isEndOfWord=false → false ✓
```

**Q5. What is the time complexity of each Trie operation, and how does it depend on the word length rather than the dictionary size?**

A: All three core operations — insert, search, startsWith — are O(L) where L is the length of the word or prefix, completely independent of N (the number of words stored in the Trie). This is the Trie's defining property: querying a dictionary of 1 word and a dictionary of 1 million words take the same time if the query word has the same length. The path length is bounded by L; no part of the algorithm scans the rest of the dictionary. Building a Trie from N words of average length L is O(N × L) — N insert operations, each O(L).

```
Operation  | Time      | Space (per call)
-----------|-----------|------------------
insert(w)  | O(|w|)    | O(|w|) new nodes in worst case
search(w)  | O(|w|)    | O(1) — just traversal, no new nodes
startsWith | O(|p|)    | O(1)
autocomplete| O(|p| + output) | O(depth) for DFS call stack

Contrast with HashSet:
  search:     O(|w|) average (hash + string comparison) — similar
  startsWith: O(N × |w|) — must scan all N words — much worse
```

### Section A2: Advanced Structural Properties

**Q6. How do you implement autocomplete — collecting all words with a given prefix — and what is its complexity?**

A: Autocomplete is a two-phase algorithm: (1) **Prefix traversal** — walk the Trie following the prefix characters, arriving at the prefix's terminal node; if any character is missing, return empty (no words with this prefix). (2) **DFS from the terminal node** — collect all words reachable from this node via DFS; whenever a node with `isEndOfWord = true` is reached, the current accumulated string is a complete word.

The DFS carries a growing string (the prefix + characters accumulated during DFS). Complexity: O(|prefix|) for phase 1, O(total characters in all matching words) for phase 2. For k matching words averaging length L, total = O(|prefix| + k × L).

```js
function autocomplete(root, prefix) {
  // Phase 1: walk to prefix terminal node
  let node = root;
  for (const ch of prefix) {
    const idx = ch.charCodeAt(0) - 97;
    if (!node.children[idx]) return []; // no words with this prefix
    node = node.children[idx];
  }

  // Phase 2: DFS from terminal node, collecting all words
  const results = [];
  function dfs(node, current) {
    if (node.isEndOfWord) results.push(current); // found a complete word
    for (let i = 0; i < 26; i++) {
      if (node.children[i]) {
        dfs(node.children[i], current + String.fromCharCode(97 + i));
      }
    }
  }
  dfs(node, prefix);
  return results;
}
// DFS visits children in index order (0=a, 1=b, ...) → results are lexicographically sorted ✓
```

**Q7. Why does DFS on a Trie naturally produce words in lexicographic order?**

A: The children array uses indices 0–25 corresponding to 'a'–'z'. Iterating children from index 0 to 25 visits them in alphabetical order. The DFS therefore builds words left-to-right, exploring 'a' children before 'b' children at every level — which is exactly lexicographic order. This property is free: no sorting step is needed. It directly enables features like "return the top-k suggestions in lexicographic order" without a sort on the output.

```
Trie contains: "can", "car", "cat", "dog"

DFS from root (visiting children in order a→b→...→z):
  Visit 'c' subtree:
    Visit 'a' subtree:
      Visit 'n' → "can"* ← first result
      Visit 'r' → "car"* ← second result
      Visit 't' → "cat"* ← third result
  Visit 'd' subtree:
    Visit 'o' → 'g' → "dog"* ← fourth result

Output order: ["can", "car", "cat", "dog"] — lexicographic, no sort needed ✓
```

**Q8. How do you implement Trie deletion, and why is it more complex than insert?**

A: Insert only creates nodes — a straightforward top-down traversal. Deletion must: (1) verify the word exists; (2) unmark the terminal `isEndOfWord`; (3) remove nodes that are no longer needed — nodes with no other children and no `isEndOfWord` flag. This requires a bottom-up (post-order) traversal to determine, after visiting children, whether the current node can be pruned.

Three cases when recursing back up from a deletion:
- **Node has other children**: cannot delete — other words pass through this node.
- **Node has `isEndOfWord = true`**: cannot delete — this node marks a different stored word.
- **Node has no children and `isEndOfWord = false`**: safe to delete — it serves no purpose.

```js
function deleteWord(node, word, depth = 0) {
  if (!node) return false;

  if (depth === word.length) {
    if (!node.isEndOfWord) return false; // word doesn't exist
    node.isEndOfWord = false;
    // Return true if node has no children (can be deleted by parent)
    return node.children.every(c => c === null);
  }

  const idx = word.charCodeAt(depth) - 97;
  const shouldDelete = deleteWord(node.children[idx], word, depth + 1);

  if (shouldDelete) {
    node.children[idx] = null; // prune the child
    // Can this node itself be deleted?
    return !node.isEndOfWord && node.children.every(c => c === null);
  }
  return false;
}
```

**Q9. What is the space complexity of a Trie, and when does prefix sharing provide a real space saving?**

A: Worst-case Trie space: O(N × L × σ) with array children — N words, L chars each, σ = 26 slots per node, no shared prefixes (all words start with distinct characters). Practically: shared prefixes are stored once. The space saving is largest when: many words share long common prefixes (e.g., a dictionary of medical terms sharing prefixes like "cardio-", "neuro-"). The space saving is zero when all words share only the root (e.g., all words start with a different letter). A HashMap-children Trie uses O(N × L) space regardless of σ, matching the space of a HashSet — but with the prefix-sharing benefit when words share prefixes.

## Topic B: Trie Patterns & Extensions

### Section B1: Wildcard and Pattern Matching

**Q10. How does wildcard matching (with '.' matching any character) extend the basic Trie traversal into a DFS with branching?**

A: For a literal character, Trie search follows one specific child — deterministic, O(1) per step. For a '.' wildcard, the search must try all existing children at that node — branching into up to 26 sub-searches. Each branch continues the pattern matching from the next character. This is DFS with branching at wildcard positions: if any branch returns true (the remaining pattern matches some word in the Trie), the overall result is true.

Time complexity: O(26^k × L) in the worst case where k = number of wildcards and L = word length. For typical inputs with few wildcards, performance is much better. The key invariant: at each node, if the current query character is '.', try all non-null children; otherwise follow only the matching child.

```js
function searchWithWildcard(node, word, idx) {
  if (idx === word.length) return node.isEndOfWord;

  const ch = word[idx];

  if (ch === '.') {
    // Wildcard: try all children — branch on all 26 possibilities
    for (const child of node.children) {
      if (child && searchWithWildcard(child, word, idx + 1)) return true;
    }
    return false;
  } else {
    // Literal: follow exactly one child
    const child = node.children[ch.charCodeAt(0) - 97];
    return child ? searchWithWildcard(child, word, idx + 1) : false;
  }
}
```

**Q11. How does Word Search II combine a Trie with grid backtracking, and what pruning does the Trie enable?**

A: Build a Trie from the word list. Then DFS/backtrack on every cell of the grid: at each cell, follow the corresponding Trie path from the current Trie node. If the character at the grid cell doesn't exist as a child in the current Trie node, immediately prune (don't recurse into this cell's neighbors) — the current path cannot lead to any dictionary word. If a Trie node has `isEndOfWord = true`, record the word (accumulated along the DFS path). The Trie enables O(1) prefix checking at every grid step: the DFS carries both a grid position and a Trie node; the Trie node's children structure confirms in O(1) whether the next character extends any valid prefix.

Critical optimization: after finding a word, mark its Trie terminal node's `isEndOfWord = false` (deduplication — avoid adding the same word multiple times if it appears multiple times in the grid). Further optimization: if a Trie node has no remaining words beneath it (all `isEndOfWord` markers cleared below), prune it from the Trie to prevent future exploration of exhausted branches.

**Q12. What is the "prefix count" extension of a Trie, and what queries does it enable in O(L)?**

A: Add a `prefixCount` integer to each node, incremented on every insert that passes through this node. On delete, decrement along the path. This enables: (1) "how many stored words start with prefix P?" — traverse to P's terminal node, return its `prefixCount`. O(|P|). (2) "how many stored words exactly equal word W?" — traverse to W's terminal node, return its `wordCount` (a separate counter incremented only when `isEndOfWord` is set). O(|W|). These queries would require O(N × L) with a HashSet (count all words with the given prefix/exact match). Both become O(L) with the augmented Trie.

```js
class CountingTrieNode {
  constructor() {
    this.children = new Array(26).fill(null);
    this.wordCount   = 0; // words ending exactly at this node
    this.prefixCount = 0; // words passing through this node (including ending here)
  }
}

// insert: prefixCount++ at every node, wordCount++ at terminal
// countWordsStartingWith(prefix): traverse to terminal, return prefixCount
// countWordsEqualTo(word): traverse to terminal, return wordCount
```

### Section B2: Compressed Tries and Comparative Analysis

**Q13. When does a Trie outperform a sorted array with binary search, and when does it lose?**

A: **Trie wins**: prefix search — Trie is O(|prefix|); sorted array binary search finds the first word with the prefix in O(L × log N) (log N comparisons, each O(L) string comparison). Trie also wins for autocomplete (collect all matches) — Trie is O(|prefix| + output); sorted array requires scanning forward from the binary-search result until the prefix no longer matches. **Trie loses**: space overhead — a sorted array of words uses O(N × L) space with excellent cache locality (contiguous memory); a Trie uses O(N × L × σ / sharing_factor) space with poor cache locality (pointer-based tree). For read-only dictionaries with infrequent updates, a sorted array + binary search is often preferred in practice for its cache performance.

**Q14. What is a compressed Trie (Radix Tree), and what space improvement does it provide?**

A: A standard Trie can produce long chains of nodes with only one child — "interview" creates 9 nodes, each with one non-null child. A compressed Trie merges these single-child chains into a single node labeled with the full string segment rather than one character. Each node either: has multiple children (branching point), or is a leaf (word ending). The node count reduces from O(total characters in all words) to O(number of distinct words × 2) — at most 2N nodes for N words. Trade-off: each node stores a variable-length string label (substring of inserted words) rather than a single character; prefix operations require partial string matching at each node (comparing character by character against the label). Used in routing tables (Linux's radix tree for IP routing) and autocomplete engines.

## Topic C: Cross-Topic & Interview-Style Questions

**Q15. "Walk through your thought process when you see a problem involving a dictionary of words and prefix queries."**

A: Four diagnostic questions:
1. **Is the key operation prefix-based?** — "starts with", "autocomplete", "longest matching prefix" → Trie. Exact lookup only → HashSet (simpler).
2. **Is the dictionary static (built once, queried many times) or dynamic (insertions interleaved with queries)?** — Both are O(L) per operation in a Trie; both are O(L) in a HashSet. For prefix queries, Trie wins either way.
3. **Is wildcard matching needed?** — '.' matching any character → Trie + DFS branching. Regex patterns → more complex automata.
4. **Is the alphabet small and fixed?** — Lowercase letters → 26-slot array children (O(1), cache-friendly). Arbitrary characters → HashMap children.

If all queries are exact (no prefix), just use HashSet — don't over-engineer. If any prefix query exists, the Trie is almost always the right tool.

**Q16. "What is the time complexity of building a Trie from N words of average length L, and how does it compare to building a sorted array?"**

A: Building a Trie: N insert operations, each O(L) — total O(N × L). Each insert traverses at most L nodes, creating at most L new nodes. No sorting or comparison between words is involved; words are independent. Building a sorted array: O(N × L × log N) — comparison sort, each comparison O(L). For the specific purpose of enabling prefix queries, the Trie build cost of O(N × L) is strictly better than sorting O(N × L × log N). The payoff: Trie prefix queries are O(|prefix| + output) vs sorted array prefix queries at O(|prefix| × log N + output).

**Q17. "What are the three ways to represent a Trie node's children, and what are the exact trade-offs for each?"**

A: Three representations:

**26-slot array** (`children[26]`): O(1) read/write (direct index). O(26 × pointer_size) = 208 bytes per node (64-bit system, 8 bytes/pointer). Best for: performance-critical, lowercase-only workloads. Worst for: large alphabets, memory-constrained systems.

**HashMap** (`Map<char, TrieNode>`): O(1) average read/write with hash overhead. O(actual children × entry_size) — sparse nodes use little memory. Best for: alphanumeric keys, Unicode, mixed character sets. Worst for: write-heavy workloads (HashMap resizing) or when constant-factor performance matters.

**Sorted array of (char, TrieNode) pairs**: O(log k) read (binary search on k children), O(k) write (insert into sorted array). O(actual children × entry_size). Best for: read-heavy, memory-constrained, when k is always very small. Rarely used in interviews.

**Q18. In one sentence each, state the invariant for each Trie operation.**

A:
- **insert(word)**: after completion, a continuous path of nodes from the root spells `word`, with the final node's `isEndOfWord = true`; all intermediate nodes' `isEndOfWord` values are unchanged.
- **search(word)**: returns true iff a path from root spells `word` AND the final node's `isEndOfWord` is true; a path existing without the flag means `word` is only a prefix of some longer stored word.
- **startsWith(prefix)**: returns true iff a path from root spells `prefix` regardless of any `isEndOfWord` flags; the existence of the path is the only condition.
- **autocomplete(prefix)**: reaches the prefix's terminal node, then DFS visits all descendants, recording accumulated strings at every `isEndOfWord` node — visiting children in index order guarantees lexicographic output without sorting.
- **wildcard search**: DFS through the Trie, branching into all 26 children at each '.' position and following exactly one child at literal positions; returns true iff any branch reaches a terminal `isEndOfWord` node after consuming all characters.
- **delete(word)**: clears `isEndOfWord` at the terminal node, then prunes all nodes on the path that have zero children and `isEndOfWord = false` — bottom-up, stopping at the first node that still has purpose.

## Problem 1 — Implement Trie (Prefix Tree)

### Problem
Implement a Trie with `insert`, `search`, and `startsWith` operations.

```
Trie trie = new Trie();
trie.insert("apple");
trie.search("apple");    // return true
trie.search("app");      // return false
trie.startsWith("app");  // return true
trie.insert("app");
trie.search("app");      // return true
```

### Pattern Recognition
Array-children Trie node with `isEndOfWord` flag — each node holds 26 child slots and a boolean; all three operations traverse from root following character indices; insert creates nodes, search and startsWith only read.

### Key Insight
The entire design hinges on one distinction: `search` checks `isEndOfWord` at the terminal node; `startsWith` does not. Everything else — the traversal loop, the null check for missing characters — is identical between them. The flag encodes "this path is a complete word" vs "this path is only a prefix of some stored word."

### Approach
Define `TrieNode` with `children[26]` and `isEndOfWord`. All three operations share the same traversal loop: for each character, compute `idx = ch.charCodeAt(0) - 97`; check `children[idx]`; advance. `insert` creates nodes when `children[idx]` is null; `search` and `startsWith` return false when null. After the loop: `insert` sets `isEndOfWord = true`; `search` returns `node.isEndOfWord`; `startsWith` returns `true`.

### Solution

```js
class TrieNode {
  constructor() {
    this.children = new Array(26).fill(null); // index 0='a', 1='b', ..., 25='z'
    this.isEndOfWord = false; // true iff some inserted word terminates at this node
  }
}

class Trie {
  constructor() {
    this.root = new TrieNode(); // root represents the empty prefix
  }

  insert(word) {
    let node = this.root;
    for (const ch of word) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) {
        node.children[idx] = new TrieNode(); // create node if absent
      }
      node = node.children[idx];
    }
    node.isEndOfWord = true; // mark end of word at the terminal node
  }

  search(word) {
    const node = this._traverse(word);
    // Must reach the terminal AND that node must be a word ending (not just a prefix)
    return node !== null && node.isEndOfWord;
  }

  startsWith(prefix) {
    // Existence of the path is sufficient — no isEndOfWord check
    return this._traverse(prefix) !== null;
  }

  // Shared traversal: returns the terminal node of `str`, or null if path breaks
  _traverse(str) {
    let node = this.root;
    for (const ch of str) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) return null; // path doesn't exist
      node = node.children[idx];
    }
    return node; // terminal node of str
  }
}

// --- Alternative: HashMap children (for arbitrary character sets) ---
class TrieNodeMap {
  constructor() {
    this.children = new Map();
    this.isEndOfWord = false;
  }
}

class TrieMap {
  constructor() { this.root = new TrieNodeMap(); }

  insert(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children.has(ch)) node.children.set(ch, new TrieNodeMap());
      node = node.children.get(ch);
    }
    node.isEndOfWord = true;
  }

  search(word) {
    const node = this._traverse(word);
    return node !== null && node.isEndOfWord;
  }

  startsWith(prefix) {
    return this._traverse(prefix) !== null;
  }

  _traverse(str) {
    let node = this.root;
    for (const ch of str) {
      if (!node.children.has(ch)) return null;
      node = node.children.get(ch);
    }
    return node;
  }
}
```

### Dry Run

```

  node = root
  'a'(0): root.children[0]=null → create nodeA. node=nodeA.
  'p'(15): nodeA.children[15]=null → create nodeP1. node=nodeP1.
  'p'(15): nodeP1.children[15]=null → create nodeP2. node=nodeP2.
  'l'(11): nodeP2.children[11]=null → create nodeL. node=nodeL.
  'e'(4): nodeL.children[4]=null → create nodeE. node=nodeE.
  nodeE.isEndOfWord = true.

  Trie path: root→a→p→p→l→e* (5 nodes created, e is marked)

search("apple"):
  _traverse("apple"): follows a→p→p→l→e → returns nodeE.
  nodeE.isEndOfWord = true → return true ✓

search("app"):
  _traverse("app"): follows a→p→p → returns nodeP2.
  nodeP2.isEndOfWord = false → return false ✓

startsWith("app"):
  _traverse("app"): follows a→p→p → returns nodeP2 (not null).
  return true ✓

insert("app"):
  _traverse already visits a→p→p → nodeP2. nodeP2.isEndOfWord = true.

search("app"):
  nodeP2.isEndOfWord = true → return true ✓

Final Trie:
root → [a:nodeA]
nodeA → [p:nodeP1]
nodeP1 → [p:nodeP2*]   ← isEndOfWord=true (for "app")
nodeP2 → [l:nodeL]
nodeL → [e:nodeE*]      ← isEndOfWord=true (for "apple")
```

### Complexity
- Time: insert O(L), search O(L), startsWith O(L) — where L = word/prefix length.
- Space: O(N × L × σ) worst case for the entire Trie — each of the N words creates at most L new nodes, each with σ = 26 child slots. Shared prefixes reduce the actual node count.

### Edge Cases
- **Empty string insert**: loop doesn't execute; `root.isEndOfWord = true`. `search("")` → `_traverse("") = root`, `root.isEndOfWord=true` → true. `startsWith("")` → root not null → true. Semantically valid — the empty string is a word.
- **Single character words**: one node created. `search("a")` checks `root.children[0].isEndOfWord`.
- **Word is a prefix of another**: handled by the `isEndOfWord` flag at each node independently.
- **Duplicate insert**: inserting the same word twice re-traverses the existing path and sets `isEndOfWord = true` again (harmless idempotent operation).
- **Case sensitivity**: the implementation assumes lowercase only. For mixed case, use HashMap children or adjust the index formula.

### Follow-up Questions
- "What if the alphabet includes digits, uppercase, and lowercase?" — Switch to HashMap children. Replace `ch.charCodeAt(0) - 97` with `node.children.get(ch)`.
- "Return all words in the Trie in lexicographic order?" — DFS from root, accumulating the current path; push to result at every `isEndOfWord` node. Children visited in index order (0 to 25) guarantees lexicographic order.
- "Count total number of distinct words stored?" — Either maintain a `wordCount` counter incremented on each `insert` (skip if `isEndOfWord` is already true to avoid counting duplicates), or DFS and count `isEndOfWord` nodes.

## Problem 2 — Design Add and Search Words Data Structure

### Problem
Design a data structure that supports adding new words and finding if a string matches any previously added word. The `search(word)` method should support `'.'` as a wildcard matching any single letter.

```
WordDictionary wd = new WordDictionary();
wd.addWord("bad");
wd.addWord("dad");
wd.addWord("mad");
wd.search("pad");   // false (no word matching "pad")
wd.search("bad");   // true
wd.search(".ad");   // true  (matches "bad", "dad", "mad")
wd.search("b..");   // true  (matches "bad")
```

### Pattern Recognition
Trie + DFS branching at wildcard positions — standard Trie insert for `addWord`; for `search`, follow literal characters deterministically and branch into all non-null children at each `.` position.

### Key Insight
The standard Trie `_traverse` is deterministic — one path per query character. Wildcards introduce non-determinism: a `.` at position i means "try all 26 children at this node and see if any branch leads to a complete match." This turns the iterative O(L) traversal into a recursive DFS that branches only at `.` positions.

### Approach
`addWord`: standard Trie insert. `search(word)`: recursive DFS from the root, passing the current Trie node and the current character index. At each step: if the index equals word length, return `node.isEndOfWord`. If `word[idx] === '.'`, try all non-null children recursively — return true if any succeeds. If literal character, follow the specific child — return false if null.

### Solution

```js
class WordDictionary {
  constructor() {
    this.root = new TrieNode(); // reuse TrieNode from Problem 1
  }

  addWord(word) {
    let node = this.root;
    for (const ch of word) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) node.children[idx] = new TrieNode();
      node = node.children[idx];
    }
    node.isEndOfWord = true;
  }

  search(word) {
    return this._dfs(this.root, word, 0);
  }

  _dfs(node, word, idx) {
    // Base case: consumed all characters — check if this is a word ending
    if (idx === word.length) return node.isEndOfWord;

    const ch = word[idx];

    if (ch === '.') {
      // Wildcard: try every non-null child — branch into all possibilities
      for (let i = 0; i < 26; i++) {
        if (node.children[i] && this._dfs(node.children[i], word, idx + 1)) {
          return true; // short-circuit: one successful branch is enough
        }
      }
      return false; // no child led to a match
    } else {
      // Literal: follow exactly one child
      const childIdx = ch.charCodeAt(0) - 97;
      if (!node.children[childIdx]) return false; // no path for this character
      return this._dfs(node.children[childIdx], word, idx + 1);
    }
  }
}
```

## Problem 3 — Replace Words

### Problem
In English, the root of a word can form derivatives. Given a dictionary of roots and a sentence, replace all words in the sentence with their shortest matching root from the dictionary. If a word has multiple matching roots, replace it with the shortest one.

```
Input:  dictionary = ["cat","bat","rat"], sentence = "the cattle was rattled by the battery"
Output: "the cat was rat by the bat"

Input:  dictionary = ["a","b","c"], sentence = "aadsfasf absbs bbab cadsfafs"
Output: "a a b c"
```

### Pattern Recognition
Trie for shortest prefix lookup — insert all roots into a Trie; for each word in the sentence, traverse the Trie character by character; return at the first `isEndOfWord` encountered (shortest matching root). If no root matches, keep the original word.

### Key Insight
The Trie's path structure guarantees that prefixes are found in increasing length order: the root-to-first-`isEndOfWord` path is always the *shortest* matching root. No sorting or length comparison is needed — the first `isEndOfWord` encountered during traversal is definitionally the shortest match.

### Approach
Build Trie from all dictionary roots (short-circuit on `isEndOfWord` during insert if a prefix of this root is already stored). For each word in the sentence: traverse the Trie; at each step, if the current node's `isEndOfWord` is true, the current prefix is the shortest root — stop and use it. If traversal reaches a null child or completes without finding `isEndOfWord`, use the original word.

### Solution

```js
function replaceWords(dictionary, sentence) {
  // Build Trie from all roots
  const root = new TrieNode();
  for (const word of dictionary) {
    let node = root;
    for (const ch of word) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) node.children[idx] = new TrieNode();
      node = node.children[idx];
      // Optimization: if a shorter root already exists along this path, stop
      // (the existing shorter root already covers any longer root's matches)
      if (node.isEndOfWord) break;
    }
    node.isEndOfWord = true;
  }

  // Replace each word in the sentence
  return sentence.split(' ').map(word => {
    let node = root;
    let prefix = '';

    for (const ch of word) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) break;       // no root matches this word
      node = node.children[idx];
      prefix += ch;
      if (node.isEndOfWord) return prefix;  // shortest matching root found
    }

    return word; // no root was a prefix of this word — keep original
  }).join(' ');
}
```

## Problem 4 — Search Suggestions System

### Problem
Given an array of products and a search `searchWord`, design a system that suggests at most 3 product names from `products` after each character is typed. Suggested products should share a common prefix with `searchWord`. If more than 3 products have the same common prefix, return the 3 lexicographically minimum products.

```
Input:  products = ["mobile","mouse","moneypot","monitor","mousepad"], searchWord = "mouse"
Output: [
  ["mobile","moneypot","monitor"],   // prefix "m"
  ["mobile","moneypot","monitor"],   // prefix "mo"
  ["mouse","mousepad"],              // prefix "mou"
  ["mouse","mousepad"],              // prefix "mous"
  ["mouse","mousepad"]               // prefix "mouse"
]
```

### Pattern Recognition
Trie with autocomplete (collect up to 3 words per prefix) — insert all products; for each prefix of `searchWord` (character by character), collect up to 3 lexicographically smallest words with that prefix using the Trie's natural DFS order.

### Key Insight
The Trie's DFS order is lexicographic — children are visited in alphabetical order (index 0='a' first). The first 3 words found during DFS are automatically the 3 lexicographically smallest. No sorting is needed at query time. The prefix traversal re-uses the node from the previous character's traversal — progressive prefix extension doesn't require re-traversing from the root each time.

### Approach
Build Trie from all products. Maintain a `currentNode` starting at root. For each character `ch` of `searchWord`: advance `currentNode` along `ch` (if null, all subsequent prefixes have 0 suggestions — short-circuit). From `currentNode`, run a DFS collecting up to 3 words. Accumulate results per prefix.

### Solution

```js
function suggestedProducts(products, searchWord) {
  const root = new TrieNode();

  // Build Trie (products already sorted for lexicographic DFS — or DFS handles it)
  // Sort products first to ensure lexicographic order during DFS
  products.sort(); // O(P × L × log P)
  for (const product of products) {
    let node = root;
    for (const ch of product) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) node.children[idx] = new TrieNode();
      node = node.children[idx];
    }
    node.isEndOfWord = true;
  }

  const results = [];
  let node = root;
  let prefix = '';
  let dead = false; // once a null child is hit, all further prefixes yield []

  for (const ch of searchWord) {
    prefix += ch;

    if (!dead) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) {
        dead = true; // no word has this prefix — all future extensions also have 0 matches
      } else {
        node = node.children[idx];
      }
    }

    if (dead) {
      results.push([]); // no suggestions for this prefix
      continue;
    }

    // Collect up to 3 suggestions from current prefix node via DFS
    const suggestions = [];
    function dfs(n, word) {
      if (suggestions.length === 3) return; // stop early once 3 found
      if (n.isEndOfWord) suggestions.push(word);
      for (let i = 0; i < 26 && suggestions.length < 3; i++) {
        if (n.children[i]) {
          dfs(n.children[i], word + String.fromCharCode(97 + i));
        }
      }
    }
    dfs(node, prefix);
    results.push(suggestions);
  }

  return results;
}
```

## Problem 5 — Longest Word in Dictionary

### Problem
Given an array of strings `words`, return the longest word that can be built one character at a time, where each intermediate word also exists in the dictionary. If there are multiple results of the same length, return the lexicographically smallest one.

```
Input:  words = ["w","wo","wor","worl","world"]
Output: "world"   // each prefix: "w","wo","wor","worl","world" — all in words

Input:  words = ["a","banana","app","appl","ap","apply","apple"]
Output: "apple"   // "apply" also builds incrementally, but "apple" < "apply" lex.
```

### Pattern Recognition
Trie with BFS (level-order) or DFS — insert all words; then find the longest path where every node along the way has `isEndOfWord = true` (every prefix is itself a word). BFS from the root, expanding only nodes with `isEndOfWord = true` — the last level with valid nodes gives the longest word.

### Key Insight
A word is "buildable" iff every prefix of length 1, 2, ..., L-1 is also in the dictionary — meaning every ancestor node in the Trie has `isEndOfWord = true`. BFS from the root, expanding only `isEndOfWord` nodes, naturally explores only buildable prefixes layer by layer. The last node reached is part of the longest buildable word. Among ties (same length), the first discovered in BFS order (which, using a sorted queue or alphabetical children traversal, is the lexicographically smallest) is the answer.

### Approach
Build Trie from all words. BFS starting from the root: queue initially contains all direct children of root that have `isEndOfWord = true`. At each step: dequeue a node; if its `isEndOfWord` is true, update `best` answer (longer string wins; lexicographically smaller wins on ties); enqueue all its children with `isEndOfWord = true`.

### Solution

```js
function longestWord(words) {
  const root = new TrieNode();
  // Store the word at each terminal node for easy retrieval (avoids reconstructing from path)
  root.word = '';

  for (const word of words) {
    let node = root;
    for (const ch of word) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) node.children[idx] = new TrieNode();
      node = node.children[idx];
    }
    node.isEndOfWord = true;
    node.word = word; // store the complete word at the terminal node
  }

  let best = '';

  // BFS: expand only nodes with isEndOfWord=true (every prefix is a word)
  const queue = [root]; // root represents the empty prefix (always "valid")

  while (queue.length > 0) {
    const node = queue.shift();

    for (let i = 0; i < 26; i++) {
      const child = node.children[i];
      if (child && child.isEndOfWord) {
        // This child's word has every prefix in the dictionary → it's buildable
        queue.push(child);

        // Update best: longer is better; same length → lexicographically smaller
        if (child.word.length > best.length ||
           (child.word.length === best.length && child.word < best)) {
          best = child.word;
        }
      }
    }
  }

  return best;
}
```

## Problem 6 — Word Search II

### Problem
Given an `m × n` board of characters and a list of strings `words`, return all words on the board. Each word must be constructed from sequentially adjacent cells (horizontally or vertically), and the same letter cell may not be used more than once for a single word.

```
Input:
  board = [["o","a","a","n"],
           ["e","t","a","e"],
           ["i","h","k","r"],
           ["i","f","l","v"]]
  words = ["oath","pea","eat","rain"]

Output: ["eat","oath"]
```

### Pattern Recognition
Trie + grid backtracking — build a Trie from all target words; DFS/backtrack on every cell; at each step, check whether the current cell's character is a valid child in the current Trie node; if so, continue exploring; if the current Trie node is a word ending, record the found word. The Trie enables O(1) prefix pruning at every grid step.

### Key Insight
Without a Trie, searching for each word independently is O(W × m × n × 4^L) — one full grid search per word. With a Trie, all words are searched simultaneously in a single grid traversal: the Trie node at each DFS step simultaneously represents "which subset of all words could still match the current path." When a grid cell's character is not a child of the current Trie node, the entire subtree of words is pruned in O(1) — no further exploration in this direction for any word.

### Approach
Build Trie from `words`. For each cell `(i, j)` on the board: if `board[i][j]` is a child of root, start DFS from `(i, j)` with that Trie child node. DFS: mark cell as visited (set to '#'); for each of the 4 neighbors, if in bounds, not visited, and the neighbor's character exists in the current Trie node's children — recurse with that Trie child. On backtrack: restore the cell character. On entering a DFS call: if the Trie node is a word ending, record the word.

### Solution

```js
function findWords(board, words) {
  const root = new TrieNode();

  // Build Trie; store word at terminal nodes for easy retrieval
  for (const word of words) {
    let node = root;
    for (const ch of word) {
      const idx = ch.charCodeAt(0) - 97;
      if (!node.children[idx]) node.children[idx] = new TrieNode();
      node = node.children[idx];
    }
    node.word = word; // store complete word (avoids reconstructing path)
  }

  const result = [];
  const m = board.length, n = board[0].length;
  const dirs = [[0,1],[0,-1],[1,0],[-1,0]];

  function backtrack(row, col, trieNode) {
    const ch = board[row][col];
    const idx = ch.charCodeAt(0) - 97;

    // Current cell's character not in Trie at this position → prune
    if (idx < 0 || !trieNode.children[idx]) return;

    const nextNode = trieNode.children[idx];

    // Found a complete word at this Trie node
    if (nextNode.word) {
      result.push(nextNode.word);
      nextNode.word = null; // deduplicate: clear to avoid re-adding if visited again
    }

    board[row][col] = '#'; // mark as visited (in-place, O(1) space)

    for (const [dr, dc] of dirs) {
      const nr = row + dr, nc = col + dc;
      if (nr >= 0 && nr < m && nc >= 0 && nc < n && board[nr][nc] !== '#') {
        backtrack(nr, nc, nextNode);
      }
    }

    board[row][col] = ch; // restore on backtrack
  }

  for (let i = 0; i < m; i++) {
    for (let j = 0; j < n; j++) {
      backtrack(i, j, root);
    }
  }

  return result;
}
```

### Complexity
- Time: O(m × n × 4^L) in the absolute worst case (L = max word length, all characters identical). In practice, Trie pruning dramatically reduces the search space — when a cell's character is not in the current Trie node's children, no further DFS from that cell in that direction is explored.
- Space: O(W × L) for the Trie (W words, average length L); O(L) call stack for DFS; O(1) extra for in-place board marking.

### Edge Cases
- **Word appears multiple times on board**: `nextNode.word = null` after first find deduplicates — same word never added twice.
- **Single cell board**: check if the single character matches any single-character word in the Trie.
- **Word not on board**: Trie pruning ensures the backtracking never finds the word; it is simply not added to `result`.
- **Same cell used twice for a word**: the `board[row][col] = '#'` marking prevents revisiting the same cell within one word's DFS path. The marking is restored on backtrack, allowing other words to use the same cell.

### Follow-up Questions
- "Trie optimization: prune Trie nodes with no remaining words?" — After clearing `nextNode.word`, if `nextNode` has no children and no word, remove it from its parent's children array. This prevents exploring already-exhausted branches in future DFS calls — effective when the board has many repeat visits to the same cells.
- "What is the exact time complexity with the Trie vs without?" — Without Trie (search each word independently): O(W × m × n × 4^L). With Trie: O(m × n × 4^L) — independent of W, since all W words are checked simultaneously via the shared Trie traversal.

## Quick Reference — Trie Pattern Decision Tree

```
What does the problem involve?
│
├── A dictionary of words + PREFIX queries (startsWith, autocomplete)?
│   └── Build a Trie.
│       search(word): traverse + check isEndOfWord.
│       startsWith(prefix): traverse only (no flag check).
│       autocomplete(prefix): traverse to prefix node, then DFS collecting words.
│       DFS visits children in index order → lexicographic output, no sort needed.
│
├── REPLACE each word with its SHORTEST MATCHING PREFIX from a dictionary?
│   └── Trie with early-exit on isEndOfWord during traversal.
│       First isEndOfWord hit = shortest root. Return prefix immediately.
│       No length comparison needed — Trie path order guarantees shortest-first.
│
├── WILDCARD matching ('.' = any character)?
│   └── Trie + DFS branching.
│       Literal char: follow one specific child — O(1).
│       '.' wildcard: try all 26 children — branch into up to 26 sub-searches.
│       DFS returns true if any branch succeeds.
│
├── LONGEST incrementally buildable word (every prefix also in dictionary)?
│   └── Trie + BFS expanding only isEndOfWord nodes.
│       Track the farthest (longest) isEndOfWord node reached.
│       BFS order: children 0-25 → naturally lexicographic among ties.
│
├── FIND ALL words from a dictionary on a 2D grid?
│   └── Trie + grid backtracking.
│       Build Trie from word list. DFS from each cell.
│       Trie node travels with DFS: O(1) prefix pruning at each cell.
│       Mark visited cells in-place; restore on backtrack.
│       Clear found words from Trie to deduplicate.
│
├── TOP-K suggestions per typed character (autocomplete system)?
│   └── Trie + DFS with early stop after k results.
│       Maintain current prefix node (carry forward, don't re-traverse from root).
│       dead flag: once a null child is encountered, all further prefixes yield [].
│
└── CHOOSING CHILDREN STRUCTURE:
    ├── Lowercase letters only (σ=26): children[26] array — O(1), cache-friendly.
    ├── Alphanumeric (σ=62) or Unicode: HashMap children — O(1) avg, space-efficient.
    └── Disambiguating full vs empty vs isEndOfWord:
        isEndOfWord=false → internal prefix node (no word ends here)
        isEndOfWord=true  → this path spells a complete stored word
        Both can be true simultaneously only if a word AND one of its extensions are stored.
```

## Common Bugs Checklist

Before submitting any Trie-based solution, verify:

1. **search checks `isEndOfWord`; startsWith does not?** — The most common confusion: `search("app")` on a Trie containing only `"apple"` should return `false` — the node for 'p' exists but `isEndOfWord` is false. `startsWith("app")` on the same Trie returns `true` — the path exists. If you return `node !== null` for both, search produces false positives for every prefix of every stored word.

2. **`_traverse` returning `null` vs the terminal node — which is used where?** — A shared `_traverse(str)` helper returns the terminal node of `str` or `null` if the path breaks. `search` checks `node !== null && node.isEndOfWord`; `startsWith` checks `node !== null`. Never check `node.isEndOfWord` without first confirming `node !== null`.

3. **Children array index uses `ch.charCodeAt(0) - 97` for lowercase only?** — The index formula `ch.charCodeAt(0) - 97` maps 'a'→0, 'z'→25. For uppercase letters or digits, this formula produces negative or out-of-range indices. If the problem includes uppercase or digits, switch to HashMap children or adjust the index formula.

4. **Character index for access (`- 97`) must be consistent between insert and search** — If insert uses `ch.charCodeAt(0) - 97` and search uses `ch.charCodeAt(0) - 65` (for uppercase), nodes are stored at different indices and lookups always miss. Use a single formula or a shared utility function for the index calculation.

5. **Forgetting to restore the board cell after backtracking in Word Search II?** — `board[row][col] = '#'` marks a cell as visited; after the recursive call, `board[row][col] = ch` must restore it. Omitting the restore makes the cell permanently blocked, preventing other DFS paths from using it. The restore must happen in all exit paths — after the loop over directions, unconditionally.

6. **Deduplication in Word Search II: clearing `nextNode.word` after finding it?** — If the same word appears multiple times on the board (multiple grid paths spell the same word), and you don't clear `nextNode.word` after the first find, the word is added to `result` multiple times. Set `nextNode.word = null` immediately after pushing to `result`.

7. **Autocomplete DFS: not stopping early after k results?** — Collecting all words under a prefix and then returning the first k is correct but wasteful — the DFS may visit thousands of words. Add an early-stop condition: `if (results.length === k) return` before recursive calls. This makes the DFS O(k × L) instead of O(total matching words × L).

8. **`dead` flag not set in Search Suggestions System?** — Once a character in `searchWord` has no Trie child, all subsequent characters also have no matches (they extend the already-absent prefix). Without a `dead` flag: each subsequent character re-checks the same null child — harmless but redundant. With `dead`: skip all further Trie traversal once the prefix is determined to have no matches.

9. **Wildcard DFS iterating all 26 slots including null children?** — `for (const child of node.children)` iterates all 26 slots, most null. Always guard with `if (child && ...)`. Calling `_dfs(null, word, idx+1)` would immediately crash on `null.isEndOfWord` or `null.children[idx]`.

10. **Insert into Trie using a shared root without resetting `node`?** — Every `insert(word)` must start with `let node = this.root`. If `node` is inadvertently shared across inserts (e.g., a class-level cursor variable not reset), subsequent inserts start from wherever the previous insert ended — building a single long chain rather than branching from root.

11. **Replace Words: returning the word when no root matches instead of returning `word` unchanged?** — When the traversal loop exits via `break` (null child), the early-return `if (node.isEndOfWord) return prefix` was never hit. The `return word` statement after the loop handles the "no root found" case. Missing this final return causes `undefined` in the output.

12. **Longest Word in Dictionary: expanding non-`isEndOfWord` children in BFS?** — The BFS must only enqueue children that have `isEndOfWord = true`. Enqueueing all children would include nodes for words whose intermediate prefixes are not in the dictionary — words that cannot be built one character at a time. The `if (child && child.isEndOfWord)` guard in the BFS loop is mandatory for correctness.

**Final Tip:** At the 5 YOE level, the decisive signal for Trie problems is stating three things immediately: (1) **Which operation the Trie is being used for** — "I'll build a Trie from the dictionary and for each word in the sentence, traverse character by character, returning at the first `isEndOfWord` hit — the shortest matching root." (2) **Children structure choice and its justification** — "I'll use a 26-slot array since the input is lowercase letters only — O(1) per character, no hash overhead." (3) **The `isEndOfWord` flag's role** — "The flag distinguishes a node that completes a word from a node that merely lies on the path to a longer word — without it, search and startsWith become the same operation." For wildcard or grid problems, additionally state the branching invariant: "At each '.' I try all 26 children; at a literal character I follow exactly one — the DFS terminates at the first branch that reaches a word-ending node." Stating these three decisions before any code is the mark of a senior who owns the data structure, not just the solution pattern.
