# DSA: Lowest Common Ancestor (LCA) — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the "lowest common ancestor" of two nodes in a tree, and why is it called "lowest," not "highest"?**
A: The lowest common ancestor (LCA) of two nodes `p` and `q` is the **deepest** node in the tree that has both `p` and `q` as descendants (a node is considered a descendant of itself, per the standard convention). It's called "lowest" because, among all the common ancestors of `p` and `q` (the root is always a common ancestor of everything, for instance), the LCA is the one **farthest from the root** — i.e., lowest in the tree's visual hierarchy, closest to `p` and `q` themselves.

```
        3
       / \
      5   1
     / \  / \
    6  2 0  8
      / \
     7   4

LCA(6, 4) = 5   (5 is the deepest node that has both 6 and 4 as descendants)
LCA(6, 2) = 5   (special case: 2 is on the direct path, and 6's ancestor is 5)
LCA(7, 8) = 3   (only the root is common to both)
```

**Q2. What is the naive approach to finding the LCA, and what is its complexity?**
A: Find the full root-to-node path for both `p` and `q` (two separate O(n) traversals), then compare the two paths from the start (root) to find the last node at which they're still identical — that node is the LCA. This is O(n) time (dominated by the two path-finding traversals) and O(h) space for storing each path (where h is the tree's height).

```js
function findPath(root, target, path) {
  if (root === null) return false;
  path.push(root);

  if (root === target) return true;

  if (findPath(root.left, target, path) || findPath(root.right, target, path)) {
    return true;
  }

  path.pop(); // backtrack: this branch didn't contain the target
  return false;
}

function lcaNaive(root, p, q) {
  const pathP = [], pathQ = [];
  findPath(root, p, pathP);
  findPath(root, q, pathQ);

  let lca = null;
  for (let i = 0; i < Math.min(pathP.length, pathQ.length); i++) {
    if (pathP[i] === pathQ[i]) {
      lca = pathP[i];
    } else {
      break;
    }
  }

  return lca;
}
```

**Q3. What is the elegant single-pass recursive approach to finding the LCA of a general binary tree (no ordering/BST assumption), and what is its core insight?**
A: Recursively search both the left and right subtrees for `p` and `q`. The key insight: if `p` is found somewhere in the left subtree AND `q` is found somewhere in the right subtree (or vice versa), the **current node** must be the LCA — since that's precisely the point where their paths from the root diverge into different subtrees. If both are found in the same subtree, the LCA must be somewhere deeper within that subtree, and the recursive call handles finding it further down.

```js
function lowestCommonAncestor(root, p, q) {
  if (root === null || root === p || root === q) return root;

  const left = lowestCommonAncestor(root.left, p, q);
  const right = lowestCommonAncestor(root.right, p, q);

  if (left !== null && right !== null) {
    return root; // p and q found in different subtrees — this node is the LCA
  }

  return left !== null ? left : right; // both in one subtree, or neither found
}
```

**Q4. Why does the base case `root === p || root === q` (returning `root` immediately upon finding either target) correctly handle the case where one node is an ANCESTOR of the other?**
A: If `p` is itself an ancestor of `q` (or vice versa), the recursion will encounter `p` first (since it's higher in the tree) and immediately return `p` from that point, without needing to continue searching deeper for `q` explicitly within that specific call — this returned `p` then propagates up as a "found" signal, and since the *other* target (`q`) is never separately found in the sibling subtree (because it's a descendant living inside `p`'s own subtree), the algorithm correctly concludes that `p` itself is the LCA (matching the standard convention that a node is considered its own ancestor/descendant).

**Q5. What is the time and space complexity of the single-pass recursive LCA algorithm?**
A: Time: O(n) — every node is visited at most once in the worst case (though with early termination once both targets are found and their paths merge, it can terminate earlier in practice, similar in spirit to other early-termination BFS/DFS patterns). Space: O(h) — the recursion call stack, bounded by the tree's height, same as other DFS-based tree algorithms.

### Section 2: LCA in a Binary Search Tree (BST) — Exploiting Ordering

**Q6. How does the BST property enable a more direct LCA algorithm than the general binary tree approach, without needing to search both subtrees?**
A: In a BST, every node's value is greater than everything in its left subtree and less than everything in its right subtree. This means you can determine which subtree the LCA must be in **purely by comparing values**, without needing to actually search both subtrees for `p` and `q`: if both `p` and `q` are smaller than the current node's value, the LCA must be in the left subtree; if both are larger, it must be in the right subtree; otherwise (one is smaller and the other is larger, or one equals the current node), the **current node itself** is the LCA — since that's precisely the point where their values "split" across the current node.

```js
function lowestCommonAncestorBST(root, p, q) {
  let node = root;

  while (node !== null) {
    if (p.val < node.val && q.val < node.val) {
      node = node.left;
    } else if (p.val > node.val && q.val > node.val) {
      node = node.right;
    } else {
      return node; // split point (or one of p/q equals node) — this IS the LCA
    }
  }

  return null;
}
```

**Q7. What is the time and space complexity of the BST-optimized LCA algorithm, and how does it compare to the general binary tree approach?**
A: Time: O(h) — at each step, the algorithm moves directly toward the LCA by following exactly one path down the tree (no need to explore both subtrees, unlike the general case), where h is the tree's height (O(log n) for a balanced BST, O(n) worst case for a completely unbalanced one). Space: O(1) for the iterative version shown (or O(h) if written recursively, due to the call stack) — a meaningful improvement over the general binary tree algorithm's requirement to potentially visit **every** node in the worst case, since the BST's ordering property lets the algorithm discard an entire subtree at each step without needing to search it at all.

**Q8. Why can't the BST-optimized technique be applied to a general (non-BST) binary tree, even though both use similar-looking recursive/iterative structures?**
A: The BST technique's efficiency comes entirely from being able to decide "which subtree must contain the LCA" using **only a value comparison**, without any actual searching — this is only valid because of the BST's specific ordering guarantee (everything left is smaller, everything right is larger). A general binary tree has no such ordering guarantee, so there's no way to determine which subtree contains `p` or `q` without actually searching within it — this is precisely why the general algorithm (Q3) must recursively search both subtrees and combine the results, rather than being able to skip one side based on a simple comparison.

### Section 3: LCA with Parent Pointers

**Q9. How does having a `parent` pointer on each node change the LCA problem, and what technique does it directly reuse?**
A: With parent pointers, finding the LCA of `p` and `q` becomes structurally identical to the **"intersection of two linked lists"** problem (see the dedicated linked-list-intersection guide) — walking from `p` upward via `parent` pointers, and separately from `q` upward via `parent` pointers, are exactly like traversing two linked lists that are guaranteed to "merge" (at the LCA) and share an identical "tail" (the path from the LCA up to the root) from that merge point onward.

```js
function lowestCommonAncestorParentPointers(p, q) {
  let ancestors = new Set();

  let node = p;
  while (node !== null) {
    ancestors.add(node);
    node = node.parent;
  }

  node = q;
  while (node !== null) {
    if (ancestors.has(node)) return node;
    node = node.parent;
  }

  return null; // no common ancestor (shouldn't happen in a valid single tree)
}
```

**Q10. How would you adapt the O(1)-space "two-pointer switching" technique from the linked-list-intersection problem to solve this WITHOUT a hash set?**
A: Run two pointers, one starting at `p` and one at `q`, both walking upward via `parent` pointers. When a pointer reaches the root (`parent === null`), redirect it to start over from the **other** target node (`p`'s pointer switches to start from `q`, and vice versa) instead of stopping. Exactly as in the linked-list-intersection problem, both pointers then traverse the same total distance before meeting — guaranteeing they converge at the LCA simultaneously, using O(1) extra space instead of the hash-set approach's O(h).

```js
function lowestCommonAncestorTwoPointer(p, q) {
  let ptrP = p, ptrQ = q;

  while (ptrP !== ptrQ) {
    ptrP = ptrP.parent === null ? q : ptrP.parent;
    ptrQ = ptrQ.parent === null ? p : ptrQ.parent;
  }

  return ptrP; // the LCA (or null, if both simultaneously reach a shared "past-root" null state)
}
```

**Q11. Why does this two-pointer technique correctly converge at the LCA, using the same mathematical argument as the linked-list intersection problem?**
A: Let `depthP` and `depthQ` be the depths of `p` and `q` respectively, and `depthLCA` be the LCA's depth. Pointer starting at `p` travels `(depthP - depthLCA)` steps to reach the LCA the first time, then (after "switching" to start from `q`) needs `(depthQ - depthLCA)` more steps to reach the LCA again via that path — total `(depthP - depthLCA) + (depthQ - depthLCA)`. By symmetry, the pointer starting at `q` travels the same total distance via the mirrored route. Since both totals are algebraically equal, both pointers arrive at the LCA simultaneously — this is structurally the exact same distance-equalization argument used for linked list intersection (see that guide's Q7), just with "walking up to the root via parent pointers" playing the role of "walking through a linked list."

### Section 4: Advanced Patterns — Multiple Queries & N-ary Trees

**Q12. If you need to answer MANY LCA queries on the SAME static tree, why is repeating the O(n) or O(h) single-query algorithm for each query potentially inefficient, and what's the standard solution?**
A: Repeating a per-query O(n) or O(h) algorithm for each of `q` queries costs O(q × n) or O(q × h) total — acceptable for a handful of queries, but potentially very wasteful if there are many queries on a large, static tree, since the tree's structure never changes between queries and yet each query redoes similar work from scratch. The standard solution is **preprocessing**: spend some upfront time and space building an auxiliary data structure that then allows each individual query to be answered much faster, typically O(log n) per query — the classic technique for this is **Binary Lifting**.

**Q13. What is "Binary Lifting," and how does it enable O(log n)-per-query LCA after O(n log n) preprocessing?**
A: Binary Lifting precomputes, for every node, its **2^k-th ancestor** for every power of 2 up to the tree's height (e.g., 1st ancestor, 2nd ancestor, 4th ancestor, 8th ancestor, ...) — this table has O(n log n) entries total (n nodes × O(log n) powers of 2 each) and can be built in O(n log n) time using the relationship `ancestor(node, 2k) = ancestor(ancestor(node, k), k)` (the 2k-th ancestor is the k-th ancestor of the k-th ancestor). To answer an LCA query: first, bring both `p` and `q` to the **same depth** by jumping the deeper node upward using the precomputed powers-of-2 table (any depth difference can be expressed as a sum of powers of 2, so this takes O(log n) jumps); then, jump both nodes upward together in decreasing powers of 2, stopping just before they'd become equal — the LCA is one step above wherever they end up.

```js
// Simplified illustrative sketch (full implementation requires careful indexing)
function buildBinaryLiftingTable(n, parent, LOG) {
  const up = Array.from({ length: LOG }, () => new Array(n).fill(-1));
  up[0] = parent; // up[0][v] = direct parent of v

  for (let k = 1; k < LOG; k++) {
    for (let v = 0; v < n; v++) {
      if (up[k - 1][v] !== -1) {
        up[k][v] = up[k - 1][up[k - 1][v]];
      }
    }
  }

  return up;
}

function lcaBinaryLifting(u, v, depth, up, LOG) {
  if (depth[u] < depth[v]) [u, v] = [v, u]; // ensure u is the deeper node

  let diff = depth[u] - depth[v];
  for (let k = 0; k < LOG; k++) {
    if ((diff >> k) & 1) u = up[k][u]; // jump u up by 2^k if that bit is set in the depth difference
  }

  if (u === v) return u; // v was an ancestor of the original u

  for (let k = LOG - 1; k >= 0; k--) {
    if (up[k][u] !== up[k][v]) {
      u = up[k][u];
      v = up[k][v];
    }
  }

  return up[0][u]; // one step above where they converge
}
```

**Q14. Why does bringing both nodes to the same depth FIRST, before jumping them together, matter for correctness?**
A: If `p` and `q` start at different depths, jumping them "together" by the same power-of-2 amounts wouldn't correctly track whether they've converged, since they'd be comparing ancestors at mismatched depths — equalizing depth first ensures that any subsequent "jump both by the same amount" step is comparing nodes that are genuinely at the same level, so "do they match yet" is a meaningful, correctly-interpretable check. This mirrors the same depth/length-equalization principle seen in the "length-difference" linked-list-intersection technique (that guide's Q5) — bringing two paths to comparable starting positions before doing a synchronized walk.

**Q15. Why does the second loop (jumping both nodes together) iterate from the LARGEST power of 2 down to the smallest, rather than the other way around?**
A: The goal of that loop is to jump both nodes as far up as possible **without them becoming equal** (since jumping "too far" past the LCA would overshoot and lose the answer) — checking from the largest jump size downward greedily takes the biggest safe jump at each step, guaranteeing that by the time the loop finishes, `u` and `v` are exactly one step below their LCA (both pointing at distinct children of the LCA), so `up[0][u]` (one more step up) correctly lands exactly on the LCA itself. Iterating smallest-to-largest instead wouldn't have this "always safe to take the biggest possible jump" greedy guarantee and wouldn't correctly converge to the right position.

**Q16. How does LCA generalize to an N-ary tree, and does the general recursive technique from Q3 change at all?**
A: The same core recursive idea directly generalizes: instead of checking exactly two children (left and right) for whether they each contain one of `p`/`q`, check **all** of a node's children, counting how many of them return a non-null "found" result — if two or more children each report finding one of the targets, the current node is the LCA (analogous to "found in both left AND right" in the binary case); if the current node itself is one of the targets, or exactly one child reports a find, propagate that result upward, same as before.

```js
function lcaNAry(root, p, q) {
  if (root === null || root === p || root === q) return root;

  const foundInChildren = [];
  for (const child of root.children) {
    const result = lcaNAry(child, p, q);
    if (result !== null) foundInChildren.push(result);
  }

  if (foundInChildren.length >= 2) return root; // found in 2+ different children's subtrees
  return foundInChildren.length === 1 ? foundInChildren[0] : null;
}
```

### Section 5: Scenario / Interview-Style Questions

**Q17. "You're asked to find the LCA of two nodes in a plain binary tree — no BST ordering, no parent pointers available. Walk through your approach."**
A: I'd use the single-pass recursive technique (Q3): recursively search both the left and right subtrees for `p` and `q`; if one is found in each subtree, the current node is the LCA (since that's exactly where their paths diverge); if both are found in the same subtree, the LCA is deeper within that subtree, handled by that recursive call's own return value; if the current node itself matches `p` or `q`, return it immediately, correctly handling the case where one target is an ancestor of the other.

**Q18. "The tree you're working with is specifically a BST. Does your LCA approach change, and why would you change it?"**
A: Yes — I'd switch to the BST-optimized approach (Q6), which uses simple value comparisons to determine which single subtree the LCA must be in, avoiding the need to actually search both subtrees the way the general algorithm does. This brings the complexity down to O(h) — proportional to the tree's height, following one direct path — rather than potentially visiting every node in the tree, specifically because the BST's ordering guarantee lets the algorithm discard an entire subtree at each step without inspecting it.

**Q19. "Each node in your tree has a `parent` pointer. How would you find the LCA, and how does this connect to a problem you might have solved before?"**
A: This is structurally identical to the "intersection of two linked lists" problem — walking upward from `p` and from `q` via `parent` pointers is exactly like traversing two lists that are guaranteed to merge at some point (the LCA) and share an identical tail from there to the root. I'd apply the same two-pointer switching technique from that problem (Q10-Q11): redirect each pointer to start over from the *other* target node upon reaching the root, guaranteeing both pointers travel the same total distance and converge at the LCA simultaneously, in O(1) extra space.

**Q20. "You need to answer thousands of LCA queries on the same very large, static tree. Repeating your single-query algorithm for each one is too slow. What would you propose?"**
A: I'd propose Binary Lifting: precompute, for every node, its ancestors at every power-of-2 distance (O(n log n) preprocessing time and space), then answer each individual query in O(log n) by first equalizing the depth of the two query nodes via precomputed jumps, then jumping both nodes upward together in decreasing powers of 2 until they're just about to converge — landing one step above that point gives the LCA. I'd note this trades a one-time O(n log n) preprocessing cost for a dramatic per-query speedup, which is exactly the right trade-off when query volume is high relative to how often the tree itself changes (ideally, not at all, since Binary Lifting's preprocessing assumes a static tree).

**Q21. "How would you verify your LCA implementation is correct, beyond the 'happy path' of two clearly-related nodes?"**
A: Key test cases: (1) one target node is a direct ancestor of the other — confirm the ancestor itself is correctly returned as the LCA, not some node further up; (2) the two target nodes are siblings or cousins at the same depth — confirm their actual common parent/ancestor is found, not the root by mistake; (3) the two target nodes are on completely opposite sides of the tree — confirm the root (or whatever the true topmost common point is) is correctly identified; (4) for a BST specifically, test with values that are numerically close together versus far apart, to make sure the comparison-based traversal doesn't have an off-by-one in the strict-vs-non-strict inequality checks; (5) a single-node tree where `p === q === root` — confirm this trivial case returns the root correctly rather than erroring.

## Problem 1 — Lowest Common Ancestor of a Binary Tree (General, Recursive)

### Problem
Given the root of a binary tree and two nodes `p` and `q` within it, find their lowest common ancestor.

```
Input:
        3
       / \
      5   1
     / \  / \
    6  2 0  8
      / \
     7   4

LCA(5, 1) = 3
LCA(5, 4) = 5
```

### Pattern Recognition
The single-pass recursive technique — search both subtrees, and use "found in different subtrees" as the signal that the current node is the LCA.

### Key Insight
If `p` is found in the left subtree and `q` is found in the right subtree (or vice versa), the current node is exactly the point where their paths from the root diverge — making it the LCA by definition. Finding either target directly at the current node short-circuits the search for that branch immediately.

### Approach
Base case: `null`, or the current node itself matches `p` or `q` — return the current node. Recursive case: search both children; if both return non-null (found in different subtrees), the current node is the LCA; otherwise, propagate whichever single non-null result (if any) was found.

### Solution

```js
function lowestCommonAncestor(root, p, q) {
  if (root === null || root === p || root === q) return root;

  const left = lowestCommonAncestor(root.left, p, q);
  const right = lowestCommonAncestor(root.right, p, q);

  if (left !== null && right !== null) return root;

  return left !== null ? left : right;
}
```

### Dry Run

```
Tree:
        3
       / \
      5   1
     / \  / \
    6  2 0  8
      / \
     7   4

Find LCA(5, 4):

lca(3, 5, 4):
  root(3) !== 5 and !== 4 → recurse
  left = lca(5, 5, 4):
    root(5) === 5 → return 5 immediately (base case)
  left = 5

  right = lca(1, 5, 4):
    root(1) !== 5, !== 4 → recurse
    left = lca(0, 5, 4): root(0)!==5,!==4, no children → return null
    right = lca(8, 5, 4): root(8)!==5,!==4, no children → return null
    both null → return null
  right = null

  left(5) !== null, right(null) === null → return left = 5

Result: LCA(5,4) = 5 ✓
(the search for "4" never even needed to descend into node 5's subtree from THIS level's
perspective — it was resolved as soon as node 5 itself was matched as one of the targets,
since 4 is indeed inside 5's subtree, which the algorithm doesn't need to separately verify)
```

### Complexity
- Time: O(n) worst case — every node potentially visited once.
- Space: O(h) — recursion call stack.

### Edge Cases
- One target is a direct ancestor of the other (e.g., `LCA(5, 4)` above): correctly returns the ancestor itself, via the immediate base-case match.
- `p` and `q` are the same node: base case matches immediately, correctly returns that node as its own LCA.
- `p` and `q` are on completely opposite sides of the root: correctly returns the root, since that's where `left` and `right` both become non-null simultaneously.
- Single-node tree where `p === q === root`: base case triggers immediately, returns `root`.

### Follow-up Questions
- "What if the tree is a BST specifically?" → See Problem 2 — a much more direct approach exploiting the ordering property.
- "What if nodes have parent pointers instead of being found via root-down search?" → See Problem 3 — reduces to the linked-list-intersection technique.

## Problem 2 — Lowest Common Ancestor of a Binary Search Tree

### Problem
Given the root of a BST and two nodes `p` and `q`, find their lowest common ancestor, exploiting the BST's ordering property for efficiency.

```
Input (BST):
        6
       / \
      2   8
     / \  / \
    0  4 7  9
      / \
     3   5

LCA(2, 8) = 6
LCA(2, 4) = 2
```

### Pattern Recognition
BST-specific optimization — use value comparisons to determine which single subtree must contain the LCA, avoiding the need to search both subtrees.

### Key Insight
If both `p.val` and `q.val` are less than the current node's value, the LCA must be in the left subtree (both targets are "smaller," so their common ancestor can't be to the right); symmetrically for both being greater. The moment this "both on the same side" condition breaks — one is smaller, the other is greater (or equal) — the current node is the split point, and thus the LCA.

### Approach
Iterative walk down from the root: compare both target values against the current node; move left or right accordingly, or return the current node the moment the values "split" across it.

### Solution

```js
function lowestCommonAncestorBST(root, p, q) {
  let node = root;

  while (node !== null) {
    if (p.val < node.val && q.val < node.val) {
      node = node.left;
    } else if (p.val > node.val && q.val > node.val) {
      node = node.right;
    } else {
      return node;
    }
  }

  return null;
}
```

### Dry Run

```
BST:
        6
       / \
      2   8
     / \  / \
    0  4 7  9
      / \
     3   5

Find LCA(2, 4)  [p.val=2, q.val=4]:

node=6: p(2)<6 and q(4)<6? yes → node = node.left = 2
node=2: p(2)<2? no (equal, not strictly less). q(4)<2? no.
        p(2)>2? no. q(4)>2? yes, but p is NOT >2 → condition "both >" fails too
        → falls to else → return node(2)

Result: LCA(2,4) = 2 ✓ (correctly: 2 is itself an ancestor of 4, and the split-detection
  correctly identifies this since p itself equals the current node)
```

```
Find LCA(2, 8):

node=6: p(2)<6 and q(8)<6? q is NOT <6 → condition fails
        p(2)>6? no → condition fails
        → else → return node(6)

Result: LCA(2,8) = 6 ✓ (correctly: 2 is smaller than 6, 8 is larger — they split at 6)
```

### Complexity
- Time: O(h) — follows a single path down the tree, where h is the BST's height (O(log n) balanced, O(n) worst-case skewed).
- Space: O(1) — iterative, no recursion call stack.

### Edge Cases
- One target is a direct ancestor of the other (e.g., `LCA(2,4)` above): correctly detected via the equality check within the split condition.
- Completely skewed BST (effectively a linked list): O(h) degrades to O(n) in this specific worst-case shape, same as any BST operation's worst case.
- `p` and `q` are the same node: the loop immediately hits the "else" branch at that node (since neither strict inequality holds when values are equal to the current node and to each other), correctly returning that node.
- Values with ties/duplicates (if the BST variant allows them): worth clarifying the exact tie-breaking convention expected, since standard BSTs are often assumed to have unique values.

### Follow-up Questions
- "Why is this more efficient than the general binary tree algorithm?" → See Q8 — the BST's ordering allows discarding an entire subtree via a simple comparison, without needing to search it, unlike the general case which must search both subtrees to determine where the targets are.
- "What if you're not given actual node references, just values, and need to find the nodes first?" → Would require an initial O(h) search to locate each node by value before proceeding — though in many BST problem formulations, `p` and `q` are already given as direct node references, avoiding this extra step.

## Problem 3 — LCA with Parent Pointers (Two-Pointer Technique)

### Problem
Given two nodes `p` and `q` in a binary tree, where each node has a `parent` pointer (but no direct access to the root or an explicit tree structure otherwise), find their lowest common ancestor.

```
Given parent pointers such that:
p → parentP1 → parentP2 → ... → root
q → parentQ1 → ... → root

Find the LCA using only these upward parent pointers.
```

### Pattern Recognition
Directly reuses the "two-pointer switching" technique from the linked-list-intersection problem — walking upward via `parent` pointers is structurally identical to traversing two linked lists guaranteed to merge and share an identical tail.

### Key Insight
Both pointers, if redirected to the *other* starting node upon reaching the root, will have traveled the exact same total distance by the time they converge — guaranteeing simultaneous arrival at the LCA, without needing to know either node's depth in advance.

### Approach
Two pointers start at `p` and `q` respectively. Advance both one step at a time via `.parent`. When a pointer reaches `null` (past the root), redirect it to start over from the *other* original target node. Continue until both pointers are equal.

### Solution

```js
function lowestCommonAncestorParentPointers(p, q) {
  let ptrP = p, ptrQ = q;

  while (ptrP !== ptrQ) {
    ptrP = ptrP === null ? q : ptrP.parent;
    ptrQ = ptrQ === null ? p : ptrQ.parent;
  }

  return ptrP;
}
```

```
  ptrQ = 2.parent = 5

ptrP(5) === ptrQ(5)? YES → loop ends
```


### Complexity
- Time: O(depthP + depthQ) — each pointer traverses at most the combined depth of both nodes.
- Space: O(1) — two pointers, no auxiliary hash set or path storage.

### Edge Cases
- `p` is a direct ancestor of `q` (or vice versa): the pointers converge quickly, correctly identifying the ancestor itself as the LCA.
- `p === q`: both pointers start equal, loop body never executes, immediately returns that shared node.
- `p` and `q` at very different depths: the switching mechanism naturally compensates for the depth difference without needing to compute it explicitly upfront, mirroring the linked-list-intersection technique's core advantage.

### Follow-up Questions
- "Why not just use a hash set of ancestors instead?" → Valid alternative (Q9), simpler to reason about, but O(h) space instead of this technique's O(1) — a direct parallel to the hash-set-vs-two-pointer trade-off discussion in the linked-list-intersection guide.
- "What if there's no guaranteed single root (multiple disconnected trees)?" → The technique assumes both `p` and `q` are in the same tree (share a common root eventually) — if they might belong to entirely disconnected trees, an explicit check (e.g., comparing final root references) would be needed to detect and handle "no common ancestor exists" correctly.

## Problem 4 — Lowest Common Ancestor in an N-ary Tree

### Problem
Given the root of an n-ary tree (nodes with an arbitrary number of children) and two nodes `p` and `q`, find their lowest common ancestor.

```
Input (n-ary tree):
        1
      / | \
     2  3  4
    /|     |
   5 6     7

LCA(5, 6) = 2
LCA(5, 7) = 1
```

### Pattern Recognition
Direct generalization of the general binary tree LCA technique — instead of checking exactly two children, check all of a node's children and count how many report finding one of the targets.

### Key Insight
If two or more of a node's children each independently report finding one of `p`/`q` within their respective subtrees, the current node is the point where those paths converge — the LCA. If only one child reports a find, that result propagates upward unchanged, same as the binary case.

### Approach
Base case: `null` or a direct match with `p`/`q` — return immediately. Recursive case: check every child, collecting non-null results; if 2 or more children found something, the current node is the LCA; otherwise propagate the single found result (or `null` if none).

### Solution

```js
function lcaNAry(root, p, q) {
  if (root === null || root === p || root === q) return root;

  const found = [];
  for (const child of root.children) {
    const result = lcaNAry(child, p, q);
    if (result !== null) found.push(result);
  }

  if (found.length >= 2) return root;
  return found.length === 1 ? found[0] : null;
}
```

### Dry Run

```
Tree:
        1
      / | \
     2  3  4
    /|     |
   5 6     7

Find LCA(5, 6):

lca(1, 5, 6):
  root(1)!==5,!==6 → check children [2,3,4]

  lca(2, 5, 6):
    root(2)!==5,!==6 → check children [5,6]
    lca(5,5,6): root(5)===5 → return 5
    lca(6,5,6): root(6)===6 → return 6
    found=[5,6], length>=2 → return root(2)
  child result for 2: node 2 (the LCA found within this subtree)

  lca(3, 5, 6):
    root(3)!==5,!==6, no children → found=[] → return null
  child result for 3: null

  lca(4, 5, 6):
    root(4)!==5,!==6 → check children [7]
    lca(7,5,6): root(7)!==5,!==6, no children → return null
    found=[] → return null
  child result for 4: null

  found (at root level) = [2] (only node 2's subtree reported anything)
  found.length === 1 → return found[0] = 2

Result: LCA(5,6) = 2 ✓
```

### Complexity
- Time: O(n) — every node visited once in the worst case.
- Space: O(h) for the recursion call stack, plus O(branching factor) temporary space per call for the `found` array.

### Edge Cases
- Node with a very large number of children: the `for` loop and `found` array scale naturally with however many children exist, no special-casing needed for high branching factor.
- One target is a direct ancestor of the other: same immediate base-case handling as the binary tree version.
- `p` and `q` are both direct children of the same parent: that parent's `found` array collects both results directly (each child's recursive call immediately returns itself via the base case), correctly identifying the parent as the LCA.

### Follow-up Questions
- "How would Binary Lifting adapt to an N-ary tree?" → The core binary-lifting technique (precomputing 2^k-th ancestors) is actually branching-factor-agnostic — it only cares about each node's single parent chain upward, regardless of how many children a node has, so it applies to N-ary trees without modification.
- "What if you needed the LCA of MORE than two nodes simultaneously?" → Generalize further: collect results from all children for the full set of target nodes, and a node is the LCA of the whole set once results covering find across at least 2 distinct children (or more careful bookkeeping to ensure ALL target nodes are collectively accounted for, not just "at least 2 found something").

## Problem 5 — LCA with Binary Lifting (Multiple Queries)

### Problem
Given a large static tree and many `(u, v)` LCA queries to answer efficiently, preprocess the tree so each query can be answered in O(log n) rather than repeating an O(n) or O(h) algorithm per query.

```
Tree with n=7 nodes, edges forming a hierarchy; given 1000 LCA queries to answer.
Naive: 1000 × O(n) — potentially slow for large n and many queries.
Binary Lifting: O(n log n) preprocessing once, then O(log n) per query.
```

### Pattern Recognition
Binary Lifting — precompute each node's 2^k-th ancestors for all relevant powers of 2, enabling any "jump up by an arbitrary amount" to be decomposed into O(log n) precomputed jumps.

### Key Insight
Any integer distance can be expressed as a sum of distinct powers of 2 (its binary representation) — so if you've precomputed "jump up by exactly 2^k" for every k, you can jump up by ANY amount using at most O(log n) of these precomputed jumps combined, rather than walking one step at a time.

### Approach
Precompute `up[k][v]` = the 2^k-th ancestor of node `v`, using `up[k][v] = up[k-1][up[k-1][v]]`. To answer a query `(u, v)`: first equalize depths by jumping the deeper node up by their depth difference (decomposed into powers of 2); then, if they're not already equal, jump both nodes up together by decreasing powers of 2, taking each jump only if it doesn't make them equal (to avoid overshooting past the LCA); the answer is one more step up from wherever they land.

### Solution

```js
function buildLCAStructure(n, adjacencyList, root) {
  const LOG = Math.ceil(Math.log2(n)) + 1;
  const up = Array.from({ length: LOG }, () => new Array(n).fill(-1));
  const depth = new Array(n).fill(0);
  const visited = new Array(n).fill(false);

  // BFS to compute direct parents and depths
  const queue = [root];
  visited[root] = true;
  up[0][root] = -1;

  while (queue.length > 0) {
    const node = queue.shift();
    for (const neighbor of adjacencyList[node]) {
      if (!visited[neighbor]) {
        visited[neighbor] = true;
        up[0][neighbor] = node;
        depth[neighbor] = depth[node] + 1;
        queue.push(neighbor);
      }
    }
  }

  // fill in binary lifting table
  for (let k = 1; k < LOG; k++) {
    for (let v = 0; v < n; v++) {
      if (up[k - 1][v] !== -1) {
        up[k][v] = up[k - 1][up[k - 1][v]];
      }
    }
  }

  return { up, depth, LOG };
}

function queryLCA(u, v, structure) {
  const { up, depth, LOG } = structure;

  if (depth[u] < depth[v]) [u, v] = [v, u];

  let diff = depth[u] - depth[v];
  for (let k = 0; k < LOG; k++) {
    if ((diff >> k) & 1) u = up[k][u];
  }

  if (u === v) return u;

  for (let k = LOG - 1; k >= 0; k--) {
    if (up[k][u] !== -1 && up[k][u] !== up[k][v]) {
      u = up[k][u];
      v = up[k][v];
    }
  }

  return up[0][u];
}
```

### Dry Run

```
Tree (0-indexed):
      0
     / \
    1   2
   /
  3

adjacencyList: 0:[1,2], 1:[0,3], 2:[0], 3:[1]
root=0

depth[0]=0, up[0][0]=-1

process 1: neighbor 3 (0 already visited) → depth[3]=2,up[0][3]=1
process 2: neighbor 0 already visited
process 3: neighbor 1 already visited

  up[1][0] = up[0][-1] → treat as -1 (0 has no parent)
  up[1][1] = up[0][up[0][1]=0] = up[0][0] = -1
  up[1][2] = up[0][0] = -1

  up[2][3] = up[1][up[1][3]=0] = up[1][0] = -1

```

### Complexity
- Preprocessing: O(n log n) time and space for the `up` table.
- Per query: O(log n) — depth equalization takes O(log n) jumps, and the synchronized-jump loop takes O(log n) iterations.
- Total for q queries: O(n log n + q log n) — a significant improvement over O(q × n) for large q.

### Edge Cases
- `u` and `v` at the same depth from the start: the depth-equalization loop's `diff = 0`, so no jumps occur there, proceeding directly to the synchronized-jump phase.
- One node is a direct ancestor of the other: after depth equalization, `u === v` is detected immediately, and that node is returned directly as the LCA without needing the second loop at all.
- `u === v` (same node queried against itself): depths are equal, `diff=0`, and the `u === v` check immediately returns that node.
- Very deep, skewed tree (linked-list-shaped): `LOG` still only needs to be O(log n), and the technique's efficiency advantage over a naive per-query walk becomes even more pronounced in this specific shape, where h (height) would otherwise be O(n).

### Follow-up Questions
- "Why is this preprocessing only worthwhile for MULTIPLE queries, not a single one?" → The O(n log n) preprocessing cost is strictly more expensive than a single O(n) or O(h) direct query for just one lookup — the investment only pays off when amortized across enough subsequent queries that the per-query O(log n) savings outweigh the upfront cost.
- "What if the tree can be MODIFIED between queries (nodes added/removed)?" → Binary Lifting's precomputed table assumes a static tree; any structural change would require rebuilding some or all of the table, which could be expensive if changes are frequent — a genuinely dynamic tree with both updates and LCA queries would need a different, more specialized data structure (e.g., link-cut trees) to handle both efficiently.

## Quick Reference — Pattern Decision Tree

```
Does the problem ask for the lowest common ancestor of two (or more) nodes in a tree?
│
├── PLAIN BINARY TREE (no BST ordering, no parent pointers, single query)?
│   └── Single-Pass Recursive Search — search both subtrees, "found in both" = LCA
│       → O(n) time, O(h) space
│
├── BINARY SEARCH TREE (ordering property available)?
│   └── Value-Comparison Traversal — no need to search both subtrees,
│       just compare values to pick ONE direction → O(h) time, O(1) space (iterative)
│
├── NODES HAVE PARENT POINTERS (no need to search down from a root)?
│   ├── O(h) space acceptable → Hash Set of ancestors, walk up from one node,
│   │     then check membership walking up from the other
│   └── O(1) space preferred → Two-Pointer Switching (same technique as
│         linked-list intersection) — walk up both, redirect to the OTHER
│         node upon reaching the top, converge simultaneously
│
├── N-ARY TREE (more than 2 children per node)?
│   └── Same single-pass recursive idea as plain binary tree, generalized:
│       "2 or more children report a find" = LCA, instead of checking left/right specifically
│
├── MANY LCA QUERIES ON THE SAME STATIC TREE?
│   └── Binary Lifting — O(n log n) one-time preprocessing (2^k-th ancestor table),
│       then O(log n) per query (equalize depth, then jump together in decreasing powers of 2)
│
└── TREE CAN CHANGE BETWEEN QUERIES (dynamic structure)?
    └── Binary Lifting's static assumption breaks down — would need a more specialized
        dynamic tree structure (e.g., link-cut trees), well beyond standard interview scope
```

## Common Bugs Checklist

Before submitting any LCA solution, verify:

1. **General binary tree: base case checks `root === p || root === q` BEFORE recursing, not after?** — Checking after recursing into children could miss correctly short-circuiting when the current node itself is one of the targets, and could cause incorrect results when one target is an ancestor of the other.

2. **General binary tree: "found in both subtrees" condition checked using the ACTUAL recursive return values (`left !== null && right !== null`), not some other proxy?** — This exact condition is what correctly identifies the LCA as the divergence point; any deviation risks incorrect results.

3. **BST version: comparisons use the correct direction (`<` for left, `>` for right), and the "else" branch correctly catches BOTH the split case and the exact-match case?** — Miswriting the comparison direction silently traverses the wrong subtree; forgetting that equality also belongs in the "else" (return current node) branch misses the case where `p` or `q` equals the current node exactly.

4. **Parent-pointer two-pointer technique: redirect condition checks for reaching the END (null/root), and redirects to the OTHER original target node, not back to the same starting point?** — Redirecting incorrectly breaks the distance-equalization guarantee entirely, exactly as in the linked-list-intersection problem.

5. **Binary Lifting: depth equalization performed BEFORE the synchronized-jump phase, not interleaved or skipped?** — Jumping two differently-deep nodes "together" without first equalizing their depths compares nodes at mismatched levels, producing meaningless or incorrect results.

6. **Binary Lifting: synchronized-jump loop iterates from the LARGEST power of 2 down to the smallest, and only jumps when `up[k][u] !== up[k][v]` (not when they're already equal)?** — Iterating in the wrong order, or jumping even when already-equal, causes overshooting past the true LCA.

7. **N-ary LCA: counting children that report a "found" result correctly (2+ means current node is LCA), not miscounting due to `null` vs. a legitimate found node being conflated?** — Ensure the `found` collection genuinely filters out `null` results, not accidentally counting every child regardless of whether they actually found something.

8. **All variants: single-node or `p === q` edge case explicitly handled or naturally falls out of the base case correctly?** — A quick mental (or actual) test with `p === q` is a cheap sanity check that many implementations get right "by accident" via their base case, but it's worth explicitly confirming rather than assuming.

---

**Final Tip:** At the 5 YOE level, interviewers expect immediate recognition of which LCA variant applies based on what's given: no ordering and no parent pointers → single-pass recursive search; BST ordering available → value-comparison traversal, no need to search both sides; parent pointers available → direct connection to the linked-list-intersection technique, ideally citing that connection explicitly; many queries on a static tree → Binary Lifting. Explicitly drawing the connection between the parent-pointer LCA technique and linked-list intersection, in particular, is a strong signal of transferring a learned pattern to a new context rather than treating every problem as requiring an entirely fresh technique.
