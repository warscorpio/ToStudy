## Part 1 — Theory & Interview Q&A

### Section 1: Fundamentals

**Q1. What does "balanced" mean in the context of a binary tree, and why does the definition matter?**
A: "Balanced" is not a single universal definition — it varies by context, and misreading which definition applies is the most common source of wrong answers on this class of problems. The three most important definitions:

- **Height-balanced (AVL-style)**: for every node in the tree, the heights of its left and right subtrees differ by at most 1. This is the definition used in LeetCode 110 ("Balanced Binary Tree") and is the most common interview definition.
- **Perfect balance**: every level of the tree is completely full. This is a strictly stronger condition — a perfect binary tree is always height-balanced, but a height-balanced tree is not necessarily perfect.
- **Weight-balanced**: for every node, the sizes (number of nodes) of its left and right subtrees are within some ratio of each other. This appears in research and advanced data structures but rarely in interviews.

Always confirm the definition before coding. In most interview settings, "balanced" means height-balanced unless stated otherwise.

```
Height-balanced (valid):       NOT height-balanced:
        1                              1
       / \                            /
      2   3                          2
     / \                            /
    4   5                          3

At node 1: left height=2,          At node 1: left height=3,
right height=1. Diff=1 ✓          right height=0. Diff=3 ✗
```

**Q2. What is the height of a binary tree node, and what is the standard base-case convention?**
A: The height of a node is the number of edges on the longest path from that node down to a leaf. Two conventions exist and both are valid — the critical thing is to pick one and use it consistently:

- **Edge-based height**: a leaf node has height 0; a null node has height -1. This is the more mathematically precise convention and makes the balanced condition `|leftHeight - rightHeight| <= 1` clean to check.
- **Node-count height**: a leaf node has height 1; a null node has height 0. This matches the intuition of "how many nodes tall is this subtree" and is slightly more natural for some people.

The two conventions are interchangeable — they differ by exactly 1 at every node — but mixing them within a single implementation causes off-by-one errors in the balance check. This guide uses the edge-based convention (`null → -1`) throughout.

```js
// Edge-based: null=-1, leaf=0, height grows with depth
function height(node) {
  if (node === null) return -1;
  return 1 + Math.max(height(node.left), height(node.right));
}

// Node-count: null=0, leaf=1
function height(node) {
  if (node === null) return 0;
  return 1 + Math.max(height(node.left), height(node.right));
}
// Both are correct — just don't mix them.
```

**Q3. What is the naive O(n²) approach to checking if a binary tree is height-balanced, and exactly where does the inefficiency come from?**
A: The naive approach makes two separate passes at each node: first compute the height of the left subtree, then compute the height of the right subtree, check the difference, then recurse into both children to check balance there too.

```js
function isBalancedNaive(root) {
  if (root === null) return true;

  const leftH = height(root.left);   // O(n) traversal
  const rightH = height(root.right); // O(n) traversal

  if (Math.abs(leftH - rightH) > 1) return false;

  return isBalancedNaive(root.left) && isBalancedNaive(root.right);
}

function height(node) {
  if (node === null) return -1;
  return 1 + Math.max(height(node.left), height(node.right));
}
```

The inefficiency: `height()` is called once for every node in the tree, and each `height()` call itself traverses the entire subtree below that node. A node at depth `d` is involved in height computations for all `d` of its ancestors — giving O(n) work per level and O(n × h) = O(n²) total for a skewed tree. For a balanced tree it's O(n log n) — still suboptimal.

**Q4. What is the efficient O(n) approach, and what is its core insight?**
A: The core insight: compute height and check balance **in the same single DFS pass**, rather than as two separate operations. Instead of returning just a height, the recursive function returns a sentinel value (conventionally `-1` or any impossible height value) to signal "this subtree is already unbalanced" — propagating early termination upward so that no further work is done once imbalance is detected anywhere in the tree.

```js
function isBalanced(root) {
  return checkHeight(root) !== -1;
}

// Returns the height of the subtree rooted at `node`,
// or -1 if the subtree is NOT height-balanced (using -1 as a sentinel).
function checkHeight(node) {
  if (node === null) return 0; // null node has height 0 (using node-count convention here)

  const leftH = checkHeight(node.left);
  if (leftH === -1) return -1; // left subtree already unbalanced — short-circuit

  const rightH = checkHeight(node.right);
  if (rightH === -1) return -1; // right subtree already unbalanced — short-circuit

  if (Math.abs(leftH - rightH) > 1) return -1; // this node violates balance

  return 1 + Math.max(leftH, rightH); // balanced: return actual height
}
```

Each node is visited exactly once — the height and balance check are computed in a single bottom-up pass. Time: O(n). Space: O(h) for the call stack.

**Q5. Why is bottom-up (post-order) the correct traversal order for the O(n) solution, and what goes wrong with top-down (pre-order)?**
A: The balance check at any node depends on the heights of its children. Heights can only be computed after visiting the children — making this inherently a **post-order** computation (process children first, then the current node). A top-down (pre-order) approach would compute heights by re-descending into subtrees from each node, duplicating work. The bottom-up approach propagates results upward: each node receives already-computed heights from its children, checks balance, and passes its own height up to its parent — each piece of information computed exactly once, used immediately, never recomputed.

```
Post-order traversal order for the O(n) check:
        1          ← checked 4th (last)
       / \
      2   3        ← 2 checked 2nd, 3 checked 3rd
     / \
    4   5          ← 4 and 5 checked 1st (leaves, base cases)

Each node's height arrives from its children before it's needed.
```

### Section 2: Sentinel Design & Variants

**Q6. The O(n) solution uses -1 as both a valid "impossible height" sentinel and potentially as an actual height value under some conventions. How do you make this unambiguous?**
A: Under the **edge-based height convention** (`null = -1`), a valid height is always ≥ -1 — so -1 is a valid height (for the null node itself) and cannot serve unambiguously as an "unbalanced" sentinel. Under the **node-count convention** (`null = 0`), all valid heights are ≥ 0, so -1 is genuinely impossible as a real height, making it a clean sentinel. This is the primary reason many implementations switch to the node-count convention specifically for the balanced-check problem — it makes the sentinel unambiguously distinct from any valid return value. Alternatively, you can use a structured return type (a pair/object) instead of encoding two different meanings in a single integer:

```js
// Option 1: node-count convention (null=0), -1 as sentinel — clean and simple
function checkHeight(node) {
  if (node === null) return 0;
  const L = checkHeight(node.left);  if (L === -1) return -1;
  const R = checkHeight(node.right); if (R === -1) return -1;
  if (Math.abs(L - R) > 1) return -1;
  return 1 + Math.max(L, R);
}

// Option 2: return a pair {balanced, height} — no sentinel ambiguity
function checkHeight(node) {
  if (node === null) return { balanced: true, height: -1 };
  const L = checkHeight(node.left);
  if (!L.balanced) return { balanced: false, height: -1 };
  const R = checkHeight(node.right);
  if (!R.balanced) return { balanced: false, height: -1 };
  const balanced = Math.abs(L.height - R.height) <= 1;
  return { balanced, height: 1 + Math.max(L.height, R.height) };
}
```

Option 1 is more concise and is the standard interview answer. Option 2 is safer and more readable for production code.

**Q7. How would you check whether a tree is balanced if you're ONLY given a function that returns a node's height (as a black box), and can't modify the height function?**
A: With only a black-box `height()` function, you're forced back toward the O(n²) approach for a strict implementation — or you can approximate with a two-phase approach: first check if `|height(root.left) - height(root.right)| <= 1` at the root, then recursively call your balance checker on both children. This is exactly the naive O(n²) algorithm from Q3. To do better, you'd need to either modify the height function or add memoization (cache height results per node in a Map keyed by node reference), reducing repeated work at the cost of O(n) extra space. In an interview, this constraint is worth flagging explicitly — it's a signal to discuss the trade-off between reusing given interfaces versus exposing more internal structure for efficiency.

**Q8. What is a "perfectly balanced" tree, and how does checking for it differ from checking height-balance?**
A: A perfectly balanced (also called "complete" or "full") binary tree has every level completely filled, except possibly the last level, which is filled left-to-right. Checking for it requires verifying not just height differences but also node counts — a height-balanced tree can still be "lopsided" within the permitted ±1 height difference. The standard check uses BFS (level-order traversal): once a null child is encountered, all subsequent nodes in the BFS queue must also be null (no gaps allowed); a non-null node encountered after a null node signals an incomplete level that violates the complete-tree property.

```js
function isCompleteTree(root) {
  if (!root) return true;
  const queue = [root];
  let foundNull = false;

  while (queue.length > 0) {
    const node = queue.shift();

    if (node === null) {
      foundNull = true; // once we see a null, all subsequent must also be null
    } else {
      if (foundNull) return false; // non-null after null: not complete
      queue.push(node.left);
      queue.push(node.right);
    }
  }
  return true;
}
```

**Q9. How do you check if a binary tree is balanced when nodes have PARENT pointers (no direct root-to-leaf recursion needed)?**
A: Parent pointers allow computing depth (distance from a node to the root) by walking upward — but for balance checking, you still need heights (distance from a node downward to its deepest leaf), which parent pointers alone don't provide. So the parent-pointer availability doesn't fundamentally change the algorithm — you still need a downward DFS to compute heights. Where parent pointers help is if you need to walk back up after finding an imbalance (e.g., to report the shallowest unbalanced node), but for the simple boolean check they add no algorithmic advantage. The O(n) post-order DFS remains the right approach.

### Section 3: Extensions and Related Problems

**Q10. How does the balanced tree check relate to the problem of computing a tree's height, and can you solve both in a single pass?**
A: Height computation is a strict sub-problem of the balanced check — the O(n) balanced checker already computes the height of every subtree as a by-product of its single DFS pass. If both the height and the balance result are needed, simply expose the height from the same function:

```js
function heightAndBalance(root) {
  let isBalanced = true;

  function dfs(node) {
    if (node === null) return 0;
    const L = dfs(node.left);
    const R = dfs(node.right);
    if (Math.abs(L - R) > 1) isBalanced = false;
    return 1 + Math.max(L, R);
  }

  const h = dfs(root);
  return { height: h - 1, isBalanced }; // adjust to edge-based if needed
}
```

This produces both results in a single O(n) pass — useful when downstream code needs the height (e.g., to plan a BFS level count) and the balance result simultaneously.

**Q11. Given a sorted array, how do you construct a height-balanced BST from it, and what does this reveal about balanced trees?**
A: The standard approach: recursively pick the **middle element** of the current array segment as the root (ensuring left and right subtrees are as equal in size as possible), then recurse on the left half for the left subtree and the right half for the right subtree.

```js
function sortedArrayToBST(nums) {
  function helper(left, right) {
    if (left > right) return null;
    const mid = Math.floor((left + right) / 2);
    const node = new TreeNode(nums[mid]);
    node.left = helper(left, mid - 1);
    node.right = helper(mid + 1, right);
    return node;
  }
  return helper(0, nums.length - 1);
}
```

What this reveals: a height-balanced BST of n nodes has height O(log n), and its structure — the exact positions of nodes — is determined by repeatedly halving the input. This is why binary search works in O(log n): a balanced BST is the tree equivalent of binary search on a sorted array. The construction also shows that a height-balanced tree need not be unique: choosing `mid = floor((left+right)/2)` vs. `ceil` produces different but equally valid balanced trees.

**Q12. How do you check balance in an N-ary tree (nodes with an arbitrary number of children)?**
A: The height-balance definition generalizes: for every node, the maximum and minimum heights among all its children must differ by at most 1. The post-order single-pass approach extends directly — compute the heights of all children, check that `max(childHeights) - min(childHeights) <= 1`, and return `1 + max(childHeights)` to the parent (or the sentinel if imbalanced).

```js
function isBalancedNAry(root) {
  return checkHeightNAry(root) !== -1;
}

function checkHeightNAry(node) {
  if (node === null) return 0;
  if (node.children.length === 0) return 1; // leaf

  const childHeights = [];
  for (const child of node.children) {
    const h = checkHeightNAry(child);
    if (h === -1) return -1; // already unbalanced below
    childHeights.push(h);
  }

  const maxH = Math.max(...childHeights);
  const minH = Math.min(...childHeights);
  if (maxH - minH > 1) return -1;

  return 1 + maxH;
}
```

**Q13. How would you find the MINIMUM number of nodes required to construct a height-balanced binary tree of height h?**
A: Let `N(h)` be the minimum number of nodes in a height-balanced tree of height h. To minimize nodes at height h, one subtree should have height `h-1` (the minimum to reach height h from one child) and the other should have height `h-2` (the minimum for the other subtree while maintaining the ±1 balance constraint — giving exactly height difference 1, the maximum allowed). This gives the recurrence:

```
N(-1) = 0   (null tree)
N(0)  = 1   (single node)
N(h)  = 1 + N(h-1) + N(h-2)   for h >= 1
```

This is structurally identical to the Fibonacci recurrence — the minimum-node height-balanced tree at each height is called a **Fibonacci tree** or **AVL tree worst case**. The values grow as O(φ^h) where φ ≈ 1.618 (the golden ratio), which means the height of any height-balanced tree with n nodes is at most O(log_φ n) ≈ O(1.44 log₂ n) — confirming that height-balanced trees have logarithmic height even in the worst case.

```
Height 0: 1 node
Height 1: 1 + 1 + 0 = 2 nodes (minimum)
Height 2: 1 + 2 + 1 = 4 nodes
Height 3: 1 + 4 + 2 = 7 nodes
Height 4: 1 + 7 + 4 = 12 nodes
```

**Q14. How does the AVL tree maintain balance after insertions and deletions, and what is a "rotation"?**
A: An AVL tree is a height-balanced BST that actively maintains the height-balance property after every mutation. After inserting or deleting a node, the tree walks back up from the mutation point to the root, recomputing heights and checking balance at each ancestor. If a node becomes unbalanced (height difference > 1), it applies a **rotation** — a local structural rearrangement that restores balance without violating the BST ordering property. There are four rotation cases:

- **Left rotation**: fixes a "right-heavy" imbalance where the right child itself is right-heavy (RR case).
- **Right rotation**: fixes a "left-heavy" imbalance where the left child is left-heavy (LL case).
- **Left-Right rotation**: left child is right-heavy (LR case) — first rotate left at the child, then right at the current node.
- **Right-Left rotation**: right child is left-heavy (RL case) — first rotate right at the child, then left at the current node.

Each rotation runs in O(1) time (pointer rewiring only), and at most O(log n) rotations are needed after any single insertion or deletion — giving O(log n) total time for AVL insertions and deletions. This is the payoff for maintaining the balance invariant: all BST operations (search, insert, delete) remain O(log n) guaranteed, rather than degrading to O(n) in the unbalanced worst case.

### Section 4: Iterative Approaches

**Q15. Can you check balance iteratively (without recursion), and what data structure enables this?**
A: Yes — an iterative post-order traversal using an explicit stack replaces the recursive call stack. The challenge with post-order iteration is that a node must be processed only after both its children have been processed; a common technique is to use two stacks (one for traversal, one for post-order result) or a single stack with a "last visited" pointer to track whether the right child has been processed yet.

```js
function isBalancedIterative(root) {
  if (!root) return true;

  const heightMap = new Map(); // node → computed height
  const stack = [];
  let current = root;
  let lastVisited = null;

  while (current !== null || stack.length > 0) {
    while (current !== null) {
      stack.push(current);
      current = current.left;
    }

    const peekNode = stack[stack.length - 1];

    // if right child exists and hasn't been processed yet, process it first
    if (peekNode.right !== null && lastVisited !== peekNode.right) {
      current = peekNode.right;
    } else {
      stack.pop();

      const leftH = heightMap.get(peekNode.left) ?? -1;
      const rightH = heightMap.get(peekNode.right) ?? -1;

      if (Math.abs(leftH - rightH) > 1) return false;

      heightMap.set(peekNode, 1 + Math.max(leftH, rightH));
      lastVisited = peekNode;
    }
  }

  return true;
}
```

The `heightMap` stores computed heights keyed by node reference — queried when a parent processes its children's results, exactly as the recursive version reads return values from child calls. The iterative version avoids call-stack overflow for very deep trees (h > ~10,000 levels), at the cost of O(n) extra space for the height map (the recursive version uses O(h) call stack space implicitly).

**Q16. When would you choose the iterative approach over the recursive approach in a real codebase?**
A: The recursive approach is almost always preferred in interviews and most production code — it's concise, readable, and directly mirrors the problem's recursive structure. The iterative approach is warranted when:
- The tree can be extremely deep (tens of thousands of levels), risking call-stack overflow in languages with limited stack size (JavaScript's default stack limit is ~10,000–15,000 frames).
- The language or runtime enforces a strict recursion limit (Python's default `sys.setrecursionlimit` is 1,000).
- Profiling shows that function-call overhead is a meaningful bottleneck (rare for tree problems of typical interview scale).

In an interview, always start with the recursive solution and proactively mention the iterative fallback as a follow-up: "For a very deep or degenerate tree, the recursive approach could hit the call-stack limit — I'd convert it to an iterative post-order traversal using an explicit stack in that case."

### Section 5: Scenario / Interview-Style Questions

**Q17. "Walk me through how you'd check if a binary tree is balanced, from first principles."**
A: First, I'd confirm the definition of "balanced" — I'll assume height-balanced (AVL-style: every node's left and right subtree heights differ by at most 1). Then I'd note the key insight: checking balance requires knowing subtree heights, and computing heights bottom-up in a single DFS pass lets me check balance at every node simultaneously — giving O(n) instead of the O(n²) naive approach that calls a separate `height()` function per node.

My implementation uses a helper that returns the actual height on balance success, or a sentinel (`-1`) on imbalance — so the parent immediately short-circuits without further work. The main function just checks whether the helper returned the sentinel.

I'd also call out two correctness details upfront: the leaf base case correctly returns 0 (not -1), and the sentinel -1 is unambiguous under the node-count height convention since all valid heights are ≥ 0.

**Q18. "Your O(n) solution uses -1 as a sentinel. What if node values in the tree could be -1? Does that cause a problem?"**
A: No — and this is an important distinction worth stating clearly. The `-1` sentinel is a return value from the **height-checking helper function**, not a node value. Node values and subtree heights are completely separate quantities. The helper returns the **height of the subtree** (always ≥ 0 for a valid subtree, since even a single node has height 0 or 1 depending on convention), or `-1` to signal imbalance. Node values never flow into the height computation — so a node with value `-1` is processed identically to a node with value `42`: its value is irrelevant to the height/balance check, and the sentinel logic is entirely unaffected.

**Q19. "The tree you're given is a BST. Does that change your balance-checking algorithm?"**
A: No — the balance check is purely structural and depends only on subtree heights, not on node values or their ordering. A BST's ordering property gives no information about subtree heights (a BST can be perfectly balanced or completely skewed), so the same O(n) post-order DFS applies unchanged to a BST. The BST property would be relevant if the problem were "find the balance factor" using inorder traversal structure — but for a standard height-balance check, the BST property is irrelevant and can be ignored.

**Q20. "How would you check balance across an entire forest (a collection of disconnected trees)?"**
A: Check each tree in the forest independently and return true only if all trees are balanced. If the forest is represented as a list of root nodes, iterate over the list and call `isBalanced(root)` on each — the overall result is the logical AND of all individual results. If any tree is unbalanced, short-circuit and return false immediately without checking the remaining trees. Time: O(total nodes across all trees). Space: O(max height across all trees) for the call stack.

```js
function isForestBalanced(roots) {
  for (const root of roots) {
    if (!isBalanced(root)) return false; // short-circuit on first unbalanced tree
  }
  return true;
}
```

**Q21. "How would you test your balanced tree checker beyond the obvious cases?"**
A: Key test cases, in order of subtlety:

- **Null root**: must return `true` (an empty tree is trivially balanced) without crashing on null dereference.
- **Single node**: height 0, no children — must return `true`.
- **Perfect binary tree (all levels full)**: all height differences are 0 — must return `true`.
- **Exactly at the limit (height diff = 1 everywhere)**: e.g., a tree where every left subtree is one level deeper than its right — must return `true` (difference is 1, within the allowed range).
- **Minimally unbalanced tree** (height diff = 2 at exactly one node): must return `false`, specifically at the node where the violation occurs.
- **Unbalanced deep in the right subtree, balanced at the root**: confirms the check is not only applied at the root — the algorithm must descend into both subtrees and check every node.
- **Left-skewed and right-skewed trees (degenerate BSTs)**: unbalanced at every level — must return `false` quickly (the sentinel propagates upward as soon as imbalance is first detected at a leaf's parent).
- **Fibonacci tree (minimum-node height-balanced tree)**: must return `true` — confirms the boundary case where height diff is exactly 1 at every node.
- **Height difference of exactly 2 at the root only**: a tree that looks locally unbalanced at the root but has balanced children — must return `false` at the root.

## Problem 1 — Balanced Binary Tree (LeetCode 110)

### Problem
Given the root of a binary tree, determine if it is height-balanced. A binary tree is height-balanced if, for every node, the heights of the left and right subtrees differ by no more than 1.

```
Input:
        3
       / \
      9  20
        /  \
       15   7

Output: true

Input:
       1
      / \
     2   2
    / \
   3   3
  / \
 4   4

Output: false
```

### Pattern Recognition
Single-pass bottom-up DFS with a sentinel return — compute height and check balance simultaneously, returning -1 to signal imbalance and short-circuit further computation.

### Key Insight
Separating the height computation from the balance check (the naive approach) causes every subtree to be traversed multiple times — once for the height call at the current node, and again when the current node's height is used by its parent. Merging them into a single post-order pass eliminates all redundant traversals: each node is processed once, producing its height (if balanced) or the sentinel (if not) for immediate use by its parent.

### Approach
Define `checkHeight(node)`: returns the node-count height of the subtree if it is balanced, or `-1` if it is not. Base case: null returns 0. Recursive case: get left and right heights; if either is -1, immediately return -1; if their difference exceeds 1, return -1; otherwise return `1 + max(L, R)`. The outer function just checks whether the result is not -1.

### Solution

```js
function isBalanced(root) {
  return checkHeight(root) !== -1;
}

function checkHeight(node) {
  // base case: null subtree has height 0 (node-count convention; sentinel -1 is unambiguous)
  if (node === null) return 0;

  // post-order: process left child first
  const leftH = checkHeight(node.left);
  if (leftH === -1) return -1; // left subtree unbalanced — propagate immediately

  // then right child
  const rightH = checkHeight(node.right);
  if (rightH === -1) return -1; // right subtree unbalanced — propagate immediately

  // check balance at this node
  if (Math.abs(leftH - rightH) > 1) return -1; // this node violates the invariant

  // balanced: return actual height for the parent to use
  return 1 + Math.max(leftH, rightH);
}
```

### Complexity
- Time: O(n) — each node visited exactly once in the post-order traversal. Short-circuit via the sentinel means imbalance detection stops further DFS into the subtree below an imbalanced node.
- Space: O(h) — recursion call stack. O(log n) for a balanced tree, O(n) worst case for a completely skewed tree.

### Edge Cases
- Null root: `checkHeight(null) = 0`, which is `!== -1`, so `isBalanced` correctly returns `true`. ✓
- Single-node tree: `checkHeight(leaf)` gets `L=0, R=0`; `|0-0|=0 ≤ 1`; returns 1. `isBalanced = true`. ✓
- Imbalance deep in one subtree, balanced at root level: the sentinel -1 propagates all the way up, correctly overriding the root-level balance check. ✓
- Tree with exactly height diff = 1 at every node (Fibonacci tree): all nodes pass the `≤ 1` check; returns `true`. ✓
- Height diff = 2 at one node only: returns -1 at that node; sentinel propagates to root; returns `false`. ✓

### Follow-up Questions
- "What if you also need to return the height?" → Return a pair or use a closure variable alongside the sentinel approach — the height is computed anyway, so exposing it adds zero extra cost.
- "Can you do this iteratively?" → Yes — see Problem 4 for the iterative post-order approach with an explicit stack and height map.

## Problem 2 — Minimum Depth vs. Maximum Depth (Balance-Adjacent)

### Problem
Given the root of a binary tree, find both its **minimum depth** (shortest root-to-leaf path, in number of nodes) and its **maximum depth** (longest root-to-leaf path). Return whether the tree is "depth-balanced" — meaning max depth minus min depth is at most 1.

```
Input:
        1
       / \
      2   3
     /
    4

Min depth = 2 (path 1→3)
Max depth = 3 (path 1→2→4)
Max - Min = 1 → balanced ✓

Input:
        1
       /
      2
     /
    3

Min depth = 3 (only one root-to-leaf path)
Max depth = 3
Max - Min = 0 → trivially balanced
(but height-balanced check would return false — note the difference)
```

### Pattern Recognition
Combined DFS computing both min-depth and max-depth simultaneously — the minimum depth has a subtle non-obvious base case that makes it distinct from a simple recursive minimum.

### Key Insight
Minimum depth is **not** simply `1 + min(minDepth(left), minDepth(right))` — this formula incorrectly picks the null child's depth (0) for a node with only one child, counting the null as a valid leaf. A leaf is a node with **no children**; a node with one null child is not itself a leaf and the null child must not be counted as the shortest path. The correct rule: if only one child exists, the minimum depth must go through the existing child (not the null one).

### Approach
DFS returning `{minD, maxD}` per node. Base case: null → `{min: Infinity, max: 0}` (Infinity for min ensures it never "wins" over a real child path). Leaf node: `{min: 1, max: 1}`. Internal node with one child: min and max both come from the existing child. Internal node with both children: min is `1 + min(L.min, R.min)`, max is `1 + max(L.max, R.max)`.

### Solution

```js
function isDepthBalanced(root) {
  const { minD, maxD } = getDepths(root);
  return maxD - minD <= 1;
}

function getDepths(node) {
  if (node === null) return { minD: Infinity, maxD: 0 };

  const L = getDepths(node.left);
  const R = getDepths(node.right);

  // if one child is null (Infinity min), only use the real child's min
  const minD = 1 + Math.min(L.minD, R.minD);
  const maxD = 1 + Math.max(L.maxD, R.maxD);

  return { minD, maxD };
}
```

### Dry Run

```

       / \
      2   3
     /
    4

  getDepths(2):
    getDepths(4):
      getDepths(null) → {min:Inf, max:0}
      getDepths(null) → {min:Inf, max:0}
      minD = 1+min(Inf,Inf) → 1+Inf... 

      Wait: node 4 has no children — it IS a leaf.
      getDepths(null) returns {minD:Infinity, maxD:0}
      minD = 1 + min(Infinity, Infinity) = 1 + Infinity = Infinity?

      That's a problem. Let's fix: for a leaf, both children are null,
      so minD = 1 + min(Inf, Inf). We need to handle leaf specifically,
      or adjust the null base case.

      Better null base case for minimum: use Infinity only for minD 
      when the null is a "missing" child of a one-child parent.
      For a leaf (both null), min(Inf, Inf) = Inf, then 1+Inf = Inf — wrong.

      Correct approach: leaf detection or clamping.
      
      Simplest fix — detect leaf before recursing:
```

- Time: O(n) — each node visited once.

- Leaf node (both children null): explicitly detected and returned as `{minD:1, maxD:1}` before recursing — avoids the `1 + Infinity` arithmetic issue. ✓
- Completely skewed tree: `minD` equals `maxD` equals n (every root-to-leaf path is the same length, since there's only one leaf) — difference is 0, depth-balanced is true, but height-balanced check would return false. ✓ (highlights that these two balance definitions differ)

A fully skewed tree has both min-depth and max-depth equal to n (only one leaf), so it's trivially depth-balanced (difference = 0) but maximally height-unbalanced.

## Problem 3 — Convert Sorted Array to Height-Balanced BST

### Problem
Given an integer array `nums` sorted in ascending order, convert it to a height-balanced binary search tree (each node's left subtree contains only smaller values, right subtree only larger values, and the height difference at every node is at most 1).

```
Input: [-10, -3, 0, 5, 9]
Output (one valid answer):
       0
      / \
    -3   9
    /   /
  -10  5
```

### Pattern Recognition
Recursive mid-point selection — choosing the array midpoint as the root guarantees the left and right halves are as equal in size as possible, ensuring the resulting BST is height-balanced by construction.

### Key Insight
A sorted array is the inorder traversal of a BST. Picking the midpoint as the root ensures left and right subtrees have sizes `floor((n-1)/2)` and `ceil((n-1)/2)` — differing by at most 1. Since the balance invariant holds at every level of recursion (each subproblem also picks the midpoint of its segment), the resulting tree is height-balanced at every node by induction. No explicit balance check is needed — the construction guarantees it.

### Approach
Recursive `helper(left, right)` over array indices. If `left > right`, return null. Pick `mid = floor((left + right) / 2)`, create a node with `nums[mid]`, recurse on `[left, mid-1]` for the left subtree, and `[mid+1, right]` for the right subtree.

### Solution

```js
function sortedArrayToBST(nums) {
  function helper(left, right) {
    if (left > right) return null; // base case: empty segment

    // midpoint becomes root — ensures roughly equal left/right sizes
    const mid = Math.floor((left + right) / 2);
    const node = new TreeNode(nums[mid]);

    node.left = helper(left, mid - 1);   // left half → left subtree
    node.right = helper(mid + 1, right); // right half → right subtree

    return node;
  }

  return helper(0, nums.length - 1);
}
```

### Dry Run

```

  mid = floor(4/2) = 2 → node(0)
  left = helper(0, 1):
    mid = floor(1/2) = 0 → node(-10)... 
    
    wait: floor((0+1)/2) = 0 → node(nums[0]) = node(-10)
    left = helper(0, -1): left > right → null
    right = helper(1, 1):
      mid = floor(2/2) = 1 → node(nums[1]) = node(-3)
      left = helper(1, 0): null
      right = helper(2, 1): null
      return node(-3)
    node(-10).left = null, node(-10).right = node(-3)
    return node(-10)

  right = helper(3, 4):
    mid = floor(7/2) = 3 → node(nums[3]) = node(5)
    left = helper(3, 2): null
    right = helper(4, 4):

      right = helper(5, 4): null

    node(5).left=null, node(5).right=node(9)
    return node(5)

```

### Complexity
- Time: O(n) — each element becomes exactly one node, created in one recursive call.
- Space: O(n) for the output tree, O(log n) for the recursion call stack (the recursion depth is the height of the balanced tree, which is O(log n)).

### Edge Cases
- Empty array: `helper(0, -1)` immediately returns null. ✓
- Single element: `helper(0, 0)`: mid=0, create node, both recursive calls return null. ✓
- Even-length array: `mid = floor((left+right)/2)` gives a slightly left-biased split — left subtree has one more element than right. Valid and balanced. Alternatively, `mid = ceil((left+right)/2)` gives a right-biased split, also valid. Both produce correct height-balanced BSTs. ✓
- Array with duplicates: the BST property requires a convention for handling duplicates (e.g., equal elements go right); the midpoint selection is unaffected. ✓

### Follow-up Questions
- "Is the answer unique?" → No — for even-length arrays, both floor and ceiling midpoints produce different but equally valid height-balanced BSTs. Multiple valid outputs are acceptable.
- "How would you solve this for a sorted linked list instead of an array?" → Random access (by index) is O(n) for a linked list — instead, use the slow/fast pointer technique to find the midpoint in O(n), split the list, recurse. Total time becomes O(n log n) since each level of recursion scans the list.

## Problem 4 — Check Balance Iteratively (Explicit Stack)

### Problem
Implement the height-balanced check for a binary tree **iteratively**, without using recursion, to handle trees deep enough to risk call-stack overflow.

```
Input: same as Problem 1 — any binary tree
Output: boolean indicating height-balance

Constraint: use an iterative post-order traversal (no recursion)
```

### Pattern Recognition
Iterative post-order traversal with a height map — explicitly simulate the DFS call stack using a data structure on the heap, storing computed heights in a Map keyed by node reference.

### Key Insight
The recursive solution's elegance comes from the call stack implicitly holding "height computed so far for this subtree" as a return value. In the iterative version, this implicit storage must be made explicit: a `heightMap` (node → height) stores each node's computed height once its children have been processed, exactly mimicking the bottom-up propagation of return values in the recursive version.

### Approach
Iterative post-order with the "last visited" technique: push nodes leftward onto the stack; when the top node's right child has been processed (tracked via `lastVisited`), process the node itself — read its children's heights from `heightMap`, check balance, store its own height. Return `false` immediately if any node's height difference exceeds 1.

### Solution

```js
function isBalancedIterative(root) {
  if (root === null) return true;

  const heightMap = new Map(); // node reference → computed height
  const stack = [];
  let current = root;
  let lastVisited = null;

  while (current !== null || stack.length > 0) {
    // go as far left as possible
    while (current !== null) {
      stack.push(current);
      current = current.left;
    }

    const peek = stack[stack.length - 1];

    // if right child exists and hasn't been visited yet, process it first
    if (peek.right !== null && lastVisited !== peek.right) {
      current = peek.right;
    } else {
      // post-order processing: both children already handled
      stack.pop();

      // retrieve children's heights (0 if null, since null isn't in the map)
      const leftH = heightMap.get(peek.left) ?? 0;
      const rightH = heightMap.get(peek.right) ?? 0;

      if (Math.abs(leftH - rightH) > 1) return false; // imbalance detected

      // store this node's height for its parent to read later
      heightMap.set(peek, 1 + Math.max(leftH, rightH));
      lastVisited = peek;
    }
  }

  return true;
}
```

### Dry Run

```

       / \
      9  20
        /  \
       15   7

Push 9, go left → current=null.

  pop 9. leftH=0 (null), rightH=0 (null). |0-0|=0 ✓
  heightMap: {9→1}. lastVisited=9.

peek=3. right=20, lastVisited=9≠20 → go right: current=20.
```

### Complexity
- Time: O(n) — each node processed once in the iterative post-order.
- Space: O(n) — the `heightMap` stores a height entry for every node (O(n) total). The explicit stack holds O(h) entries at any time. The recursive solution uses O(h) call-stack space implicitly — the iterative version trades the implicit O(h) call stack for an explicit O(n) height map, so it uses strictly more space. This is the cost of avoiding recursion.

### Edge Cases
- Null root: handled by the upfront `if (root === null) return true` check before the loop. ✓
- Single-node tree: loop runs once; `leftH=0, rightH=0`; no imbalance; returns `true`. ✓
- Deeply skewed tree (the primary motivation for this approach): the explicit stack grows to O(n), but on the heap — no call-stack overflow. The `heightMap` also stores O(n) entries. ✓
- Imbalance detected early (near the leaves): `return false` fires immediately, exiting the loop without processing the entire tree — the iterative version preserves the short-circuit behavior of the recursive sentinel approach. ✓

### Follow-up Questions
- "Can you reduce the O(n) space of the heightMap?" → In some tree representations, you can store height directly in the node (if you're allowed to mutate the input), reducing the map to O(1) extra space. In read-only settings, the map cannot be avoided without recursion.
- "Is there a way to use BFS (level-order) for the balance check instead of DFS?" → BFS processes nodes top-down, but balance checking requires bottom-up information (children's heights before parents). Naively, BFS doesn't support this ordering — you'd need to store all node heights in a map populated bottom-up, then do a second BFS top-down to check balance. This is more complex than the iterative DFS approach and offers no complexity advantage.

## Problem 5 — Minimum Nodes in a Height-Balanced Tree / Maximum Height Given N Nodes

### Problem
**Part A**: Given a target height `h`, find the minimum number of nodes required to construct a height-balanced binary tree of height exactly `h`.
**Part B**: Given `n` nodes, find the maximum height a height-balanced binary tree with exactly `n` nodes can have.

```
Part A:
h=0 → 1 node
h=1 → 2 nodes
h=2 → 4 nodes
h=3 → 7 nodes

Part B:
n=1 → max height 0
n=2 → max height 1
n=4 → max height 2
n=7 → max height 3
```

### Pattern Recognition
Fibonacci-like recurrence — the minimum-node height-balanced tree at each height is constructed by combining minimum-node trees of heights `h-1` and `h-2`, mirroring the Fibonacci recurrence.

### Key Insight
To build the "tallest possible balanced tree with n nodes" (Part B) or "least-node tree of height h" (Part A), you want one subtree as tall as possible (height `h-1`) and the other as short as possible while maintaining balance (height `h-2`, since height difference must be ≤ 1). This greedy principle produces the Fibonacci-tree recurrence, and the answer to Part B is found by precomputing the minimum-node sequence until it exceeds `n`.

### Approach
**Part A**: Use the recurrence `N(h) = 1 + N(h-1) + N(h-2)` with base cases `N(-1)=0, N(0)=1`. Either iterative (bottom-up) or recursive with memoization.

**Part B**: Precompute the sequence of minimum node counts `[N(0), N(1), N(2), ...]` until the count exceeds `n`. The maximum height is the largest `h` such that `N(h) ≤ n`.

### Solution

```js
// Part A: minimum nodes for height h
function minNodes(h) {
  if (h === -1) return 0;
  if (h === 0) return 1;

  // iterative bottom-up: avoid recursion overhead for large h
  let prev2 = 0; // N(h-2) = N(-1) = 0
  let prev1 = 1; // N(h-1) = N(0) = 1

  for (let i = 1; i <= h; i++) {
    const current = 1 + prev1 + prev2;
    prev2 = prev1;
    prev1 = current;
  }

  return prev1;
}

// Part B: maximum height for n nodes
function maxHeight(n) {
  if (n === 0) return -1;

  let h = 0;
  let prev2 = 0; // N(-1)
  let prev1 = 1; // N(0)

  // grow h until the minimum nodes needed exceeds n
  while (1 + prev1 + prev2 <= n) {
    const next = 1 + prev1 + prev2;
    prev2 = prev1;
    prev1 = next;
    h++;
  }

  return h;
}
```

### Dry Run

```
Part A — minNodes(3):
h=0 baseline: prev2=0 (N(-1)), prev1=1 (N(0))
i=1: current = 1+1+0 = 2.  prev2=1, prev1=2   [N(1)=2]
i=2: current = 1+2+1 = 4.  prev2=2, prev1=4   [N(2)=4]
i=3: current = 1+4+2 = 7.  prev2=4, prev1=7   [N(3)=7]
return 7 ✓

Part B — maxHeight(6):
Start: h=0, prev2=0, prev1=1
Check: 1+1+0=2 ≤ 6 → enter loop
  next=2, prev2=1, prev1=2, h=1  [N(1)=2 ≤ 6]
Check: 1+2+1=4 ≤ 6 → continue
  next=4, prev2=2, prev1=4, h=2  [N(2)=4 ≤ 6]
Check: 1+4+2=7 > 6 → stop

return h=2 ✓
(A height-balanced tree of height 3 needs at least 7 nodes — 6 nodes can only reach height 2)
```

### Complexity
- Time: O(h) for Part A; O(log n) for Part B (since N(h) grows as Fibonacci, h grows as O(log n) before N(h) exceeds n).
- Space: O(1) — only two rolling variables needed; no array or memoization table required.

### Edge Cases
- `h = -1` for Part A: the empty tree has 0 nodes by definition; handled as the base case. ✓
- `n = 0` for Part B: no nodes means no tree; return height -1 (empty tree convention). ✓
- `n = 1` for Part B: only the root, height 0; loop condition `1+1+0=2 > 1` never enters, returns h=0. ✓
- Very large `h` for Part A: the iterative approach avoids stack overflow and deep recursion; Fibonacci-like values grow exponentially so overflow can occur for h > ~85 in 64-bit integers — worth noting for completeness. ✓

### Follow-up Questions
- "What is the relationship between these minimum-node trees and Fibonacci numbers?" → The minimum node counts follow `N(h) = F(h+3) - 1` where F is the Fibonacci sequence (with F(1)=F(2)=1). The trees themselves are called Fibonacci trees or AVL-worst-case trees — they are the "most skewed" possible height-balanced trees and represent the adversarial input for AVL tree performance analysis.
- "What is the maximum number of nodes in a height-balanced tree of height h?" → A perfect binary tree: `2^(h+1) - 1` nodes (all levels completely filled). This is the upper bound; the Fibonacci tree count is the lower bound. Any height-balanced tree of height h has a node count in `[N(h), 2^(h+1) - 1]`.

## Common Bugs Checklist

Before submitting any balanced tree solution, verify:

1. **Sentinel value is -1 and height convention uses node-count (null=0), NOT edge-based (null=-1)?** — Under the edge-based convention, -1 is a valid height (for the null node), making it ambiguous as a sentinel. If you use edge-based heights, either switch to a different sentinel (e.g., `Number.MIN_SAFE_INTEGER`) or use the pair-return approach. Mixing conventions within a single function causes silent off-by-one errors in the balance check.

2. **Children processed BEFORE the current node (post-order), not before?** — The entire correctness of the O(n) approach depends on having children's heights available when processing the parent. If you check balance at the current node before recursing into children (pre-order), you'll have no height information to compare — the check will always see 0 vs. 0 and incorrectly return true for every node.

3. **Short-circuit after detecting sentinel: `if (leftH === -1) return -1` appears BEFORE computing `rightH`?** — If you compute both `leftH` and `rightH` before checking either for the sentinel, you waste time traversing the right subtree even when the left subtree is already confirmed unbalanced. More importantly, if you skip the sentinel check entirely and proceed to `Math.abs(leftH - rightH) > 1`, the comparison `Math.abs(-1 - rightH)` may accidentally pass (e.g., if `rightH = 0`, then `|-1 - 0| = 1 ≤ 1` — incorrectly reporting balance), or may accidentally fail (e.g., `rightH = 5`, `|-1-5|=6>1` — returns -1 for the wrong reason). Always check sentinels before using the values.

4. **`isBalanced` checks `checkHeight(root) !== -1`, not `checkHeight(root) > 0`?** — A single-node tree returns `checkHeight = 1` (positive), but an empty tree returns 0, which is also not -1 and should correctly return `true`. The check `> 0` incorrectly rejects the empty tree. The check `!== -1` correctly handles 0 (empty tree, balanced), any positive integer (balanced subtree), and -1 (imbalanced).

5. **Minimum depth computation handles single-child nodes via leaf detection or Infinity sentinel?** — The formula `1 + min(minDepth(left), minDepth(right))` picks null children as the minimum (depth 0 from a null) for any node that has only one real child. Explicitly detecting leaves before recursing, or using Infinity as the null base case for minD, prevents null children from being counted as valid leaf paths. This is the single most common bug in minimum-depth / depth-balanced problems.

6. **`sortedArrayToBST` uses index-based recursion (not array slicing) for O(n) time?** — Slicing the array at each recursive call (`nums.slice(0, mid)`) creates O(n) new arrays per level, giving O(n log n) time and O(n log n) space total. Using `left` and `right` index parameters instead keeps all recursion in O(log n) space and O(n) total time.

7. **Iterative balance check: `heightMap.get(node) ?? 0` for null children, not `heightMap.get(node) || 0`?** — `|| 0` incorrectly replaces a stored height of `0` (valid for a leaf) with `0` (correct by coincidence) but silently replaces any stored height that is falsy — in JavaScript, `0 || 0 = 0` happens to be fine, but `heightMap.get(node.left) || 0` fails if the left child has height 0 stored in the map and you accidentally treat its absence the same way. Using `?? 0` (nullish coalescing) correctly returns the stored value if present (even if 0), and 0 only when the key is absent (null child not in the map).

8. **`minNodes` / `maxHeight` Fibonacci recurrence: base cases are `N(-1)=0` and `N(0)=1`, NOT `N(0)=0` and `N(1)=1`?** — The Fibonacci tree recurrence starts from the empty tree (height -1, 0 nodes) and the single-node tree (height 0, 1 node). Using Fibonacci-style bases `N(0)=0, N(1)=1` shifts all height-to-node-count mappings by one, producing an off-by-one error throughout the sequence (e.g., incorrectly reporting that height 2 requires 3 nodes instead of the correct 4).

9. **Complete-tree BFS check: `foundNull` flag set for null children of real nodes, and checked for every subsequently dequeued node?** — The common bug is setting `foundNull` but only checking it when dequeuing — if you enqueue only non-null nodes, you never dequeue a null and never trigger the check. The correct approach is to enqueue all children (including nulls) and check `foundNull` when dequeuing, so that any non-null node dequeued after the first null immediately triggers `return false`.

10. **All variants: confirmed the balance definition with the interviewer before coding?** — Height-balanced, complete, and depth-balanced are three distinct properties, and a tree satisfying one may violate another. Coding the wrong check produces a solution that passes obvious test cases but fails subtle ones. Thirty seconds of clarification saves five minutes of debugging.

---

**Final Tip:** At the 5–7 YOE level, the interviewer expects you to immediately dismiss the O(n²) naive approach and articulate *why* — "calling a separate height function per node re-traverses subtrees already visited, giving O(n²)" — before presenting the O(n) single-pass sentinel approach as the target solution. The two non-obvious correctness points to proactively state are: (1) why the sentinel is -1 and why node-count convention (null=0) makes it unambiguous, and (2) why the children must be fully processed before the current node (post-order, not pre-order). Proactively naming the Fibonacci-tree recurrence when asked about minimum nodes, and connecting it to the AVL tree's O(log n) height guarantee, signals the depth of understanding expected at senior level.
