## Part 1 — Theory & Interview Q&A

### Section 1: Fundamentals — Definitions & Core Computation

**Q1. What is the precise difference between a node's "depth" and a node's "height," and how do these relate to the tree's overall "height"?**
A: A node's **depth** is the number of edges from the **root down to that node** (the root itself has depth 0). A node's **height** is the number of edges on the **longest path from that node down to a leaf** (a leaf itself has height 0). The tree's overall height is simply the height of the root node — the longest root-to-leaf path in the entire tree. These two measurements go in opposite directions (depth counts from the top down to a node; height counts from a node down to the bottom), which is a very common source of confusion and mixed-up terminology in casual usage — precise, careful definitions matter especially when a problem statement uses these terms.

```
        A          depth(A)=0, height(A)=2 (longest path A→B→D)
       / \
      B   C        depth(B)=1, height(B)=1;  depth(C)=1, height(C)=0
     /
    D              depth(D)=2, height(D)=0

Tree height = height(root) = height(A) = 2
```

**Q2. Note on terminology inconsistency: some sources define height/depth using NODE COUNT instead of EDGE COUNT — why does this matter, and how should you handle it in an interview?**
A: Some textbooks and problem statements define a single node's height/depth as the **number of nodes** on the relevant path (so a single-node tree has height 1, not 0), rather than the **number of edges** (which would give a single-node tree height 0). Both conventions are used in practice, and the "correct" one is whichever the specific problem statement or interviewer intends — the best practice is to **explicitly clarify which convention is being used** before implementing (e.g., "should an empty tree have height 0 or -1? Should a single-node tree have height 0 or 1?"), and then be consistent throughout your solution, since mixing conventions mid-solution is a common source of off-by-one bugs.

**Q3. What is the standard recursive approach to computing a binary tree's height (maximum depth), and what edge-case convention does it use?**
A: Recursively compute the height of the left and right subtrees, take the larger of the two, and add 1 for the current node's own edge to whichever subtree is taller. The base case (an empty/null node) returns `-1` if using the edge-count convention (so a single leaf correctly computes `1 + max(-1,-1) = 0`), or returns `0` if using the node-count convention (so a single leaf computes `1 + max(0,0) = 1`).

```js
// Edge-count convention (empty tree/node has height -1)
function heightEdges(node) {
  if (node === null) return -1;
  return 1 + Math.max(heightEdges(node.left), heightEdges(node.right));
}

// Node-count convention (empty tree has height 0, single node has height 1)
function heightNodes(node) {
  if (node === null) return 0;
  return 1 + Math.max(heightNodes(node.left), heightNodes(node.right));
}
```

Time: O(n) — every node visited exactly once. Space: O(h) — recursion call stack depth equals the tree's height (best case O(log n) for a balanced tree, worst case O(n) for a completely unbalanced/linked-list-shaped tree).

**Q4. How would you compute a binary tree's height iteratively (without recursion), and what technique does this reuse?**
A: This directly reuses the BFS level-order traversal technique (see the dedicated level-order-traversal guide) — perform a standard level-grouping BFS, and simply count how many complete levels are processed; that count (adjusted by the height/depth convention in use) is the tree's height. This avoids recursion's O(h) call-stack space in exchange for O(width) queue space — the same fundamental BFS-vs-DFS space trade-off discussed in that guide.

```js
function heightIterative(root) {
  if (root === null) return -1; // edge-count convention

  let height = -1;
  let queue = [root];

  while (queue.length > 0) {
    height++;
    const nextLevel = [];
    for (const node of queue) {
      if (node.left !== null) nextLevel.push(node.left);
      if (node.right !== null) nextLevel.push(node.right);
    }
    queue = nextLevel;
  }

  return height;
}
```

### Section 2: Diameter of a Tree

**Q5. What is the "diameter" of a binary tree, and why is it NOT simply "the tree's height doubled"?**
A: The diameter is the length of the **longest path between any two nodes** in the tree — this path may or may not pass through the root, and may or may not correspond to the root's own height calculation. It's tempting to assume the diameter is related to the root's height, but the longest path in the tree could easily be entirely contained within a subtree that doesn't include the root at all (e.g., a long path connecting two leaves deep within the left subtree, never touching the root or the right subtree whatsoever).

```
        1
       /
      2
     / \
    3   4
   /     \
  5       6

The longest path is 5→3→2→4→6 (length 4), which DOES pass through node 2 —
but node 2 is NOT the root; the root (node 1) isn't part of the longest path at all.
```

**Q6. What is the naive O(n²) approach to computing diameter, and why is it inefficient?**
A: For every single node in the tree, compute "the height of its left subtree + the height of its right subtree" (this sum represents the longest path that passes *through* that specific node), and track the maximum such sum across all nodes. This is correct, but computing height freshly for every node (via a separate O(n) height computation call at each of the n nodes) results in O(n²) total time — a classic case of redundant, repeated sub-computation.

```js
// Naive O(n²): recomputes height from scratch at every node
function diameterNaive(root) {
  if (root === null) return 0;

  const height = (node) => {
    if (node === null) return -1;
    return 1 + Math.max(height(node.left), height(node.right));
  };

  const heightThroughNode = height(root.left) + height(root.right) + 2; // +2 for the two edges connecting to root
  const leftDiameter = diameterNaive(root.left);
  const rightDiameter = diameterNaive(root.right);

  return Math.max(heightThroughNode, leftDiameter, rightDiameter);
}
```

**Q7. How does the optimized O(n) approach compute diameter and height SIMULTANEOUSLY in a single traversal, avoiding the naive approach's redundant recomputation?**
A: Use a single post-order (bottom-up) recursive traversal that, at each node, computes and returns that node's height AND, as a side effect, updates a shared/tracked "maximum diameter seen so far" variable using the current node's left-height + right-height sum — since this single traversal already naturally computes every node's height exactly once (needed for the height computation itself), reusing those already-computed height values to also check "would this node's left+right height sum be a new diameter record" comes at zero additional asymptotic cost.

```js
function diameterOfBinaryTree(root) {
  let maxDiameter = 0;

  function height(node) {
    if (node === null) return -1; // edge-count convention

    const leftHeight = height(node.left);
    const rightHeight = height(node.right);

    // diameter THROUGH this node = leftHeight + rightHeight + 2 (edges down to each side)
    maxDiameter = Math.max(maxDiameter, leftHeight + rightHeight + 2);

    return 1 + Math.max(leftHeight, rightHeight);
  }

  height(root);
  return maxDiameter;
}
```

**Q8. Why does computing diameter "through each node" as `leftHeight + rightHeight` (plus an edge-count adjustment) correctly capture EVERY possible longest path in the tree, not just paths through the root?**
A: Every possible path between two nodes in a tree has a unique **highest point** — the node closest to the root that both endpoints' paths pass through (their lowest common ancestor). Since the single-pass traversal visits *every* node in the tree and checks "what's the longest path that uses THIS node as its highest point" (via that node's own left-height + right-height), and every possible path in the tree has exactly one such highest point somewhere, checking this quantity at every single node exhaustively covers every possible path in the tree — including paths entirely within a subtree, never touching the root, since that subtree's own "highest point" node still gets visited and checked during the traversal.

**Q9. What is the time and space complexity of the optimized single-pass diameter algorithm, and how does it compare to the naive approach?**
A: Time: O(n) — a single traversal visiting every node exactly once, with O(1) work per node (computing a max and updating a tracked variable). Space: O(h) for the recursion call stack (same as standard height computation). This is a significant improvement over the naive approach's O(n²) — the key insight enabling this improvement is recognizing that height and diameter can be computed **together in one traversal**, rather than treating "compute height at this node" as a separate, independently-callable O(n) sub-routine invoked repeatedly.

### Section 3: Balanced Tree Checking

**Q10. What does it mean for a binary tree to be "height-balanced," and what is the naive O(n²) approach to checking this?**
A: A tree is height-balanced if, for **every node** in the tree, the height difference between its left and right subtrees is at most 1 (this is the standard AVL-tree-style balance definition). The naive approach: for every node, compute the height of its left and right subtrees (each a separate O(n) computation), check if their difference exceeds 1, and recurse to check the same condition for every other node — this results in the same O(n²) redundant-recomputation problem as the naive diameter approach (Q6), for the same underlying reason.

**Q11. How does the optimized O(n) approach check balance using a single post-order traversal, similar to the diameter optimization?**
A: Compute height bottom-up (post-order), but have the height-computing function return a special **sentinel value (e.g., `-2` or some clearly-invalid marker)** the moment any subtree is found to be unbalanced — this sentinel then propagates immediately back up through every remaining recursive call (each level checks for the sentinel and, if found, immediately returns it too without doing any further height computation), allowing the entire check to short-circuit and avoid unnecessary work once imbalance is detected anywhere in the tree.

```js
function isBalanced(root) {
  const UNBALANCED = -2;

  function checkHeight(node) {
    if (node === null) return -1; // edge-count convention

    const leftHeight = checkHeight(node.left);
    if (leftHeight === UNBALANCED) return UNBALANCED; // propagate immediately, skip further work

    const rightHeight = checkHeight(node.right);
    if (rightHeight === UNBALANCED) return UNBALANCED;

    if (Math.abs(leftHeight - rightHeight) > 1) return UNBALANCED;

    return 1 + Math.max(leftHeight, rightHeight);
  }

  return checkHeight(root) !== UNBALANCED;
}
```

**Q12. Why is a sentinel value (like `-2`) used here, rather than throwing an exception or using a separate boolean flag variable, to signal "unbalanced" up the call stack?**
A: A sentinel value that's clearly outside the range of any *legitimate* height value (heights are always `>= -1` under the edge-count convention, so `-2` can never be a genuine height) allows the single return value to serve **double duty** — carrying either a real height (if everything checked so far is balanced) or an unambiguous "stop, we're already unbalanced" signal, using the function's existing return channel rather than needing a second output mechanism. A separate boolean flag variable (e.g., a shared mutable "found imbalance" variable checked at each step) would also work and is a reasonable alternative, but risks slightly more subtle bugs around exactly when to check/set that flag relative to the recursive calls; throwing an exception is also viable in languages/contexts where that's idiomatic, but early-return-via-sentinel is generally considered the cleanest approach for this specific pattern in most interview contexts.

**Q13. What is the time and space complexity of the optimized balance-check, and specifically how does the early-termination sentinel affect the practical (not just asymptotic) running time?**
A: Time: O(n) worst case (a perfectly balanced tree, or one where the imbalance is only detected very late/deep in the traversal, still requires visiting every node) — but **in practice**, the sentinel-based early termination means an unbalanced tree with the imbalance near the root can return almost immediately, without visiting the rest of the tree at all, a real practical speedup even though the worst-case asymptotic bound remains O(n) (unlike the diameter optimization, which has no early-termination benefit and always visits every node regardless of the answer). Space: O(h) for the recursion call stack, same as standard height computation.

### Section 4: Advanced Patterns

**Q14. How does the diameter/height single-pass technique generalize to an N-ary tree (nodes with an arbitrary number of children)?**
A: The core idea is unchanged, but instead of tracking just two subtree heights (left and right), you need to track the **two LARGEST** child-subtree heights among however many children a node has — since the longest path through a node in an N-ary tree still only ever uses at most two of its children's branches (a path can't fork three ways and still be a single simple path), finding the top-two heights among all children (rather than assuming exactly two children exist) correctly generalizes the binary-tree formula.

```js
function diameterNAry(root) {
  let maxDiameter = 0;

  function height(node) {
    if (node === null || node.children.length === 0) return 0;

    let tallest = 0, secondTallest = 0;

    for (const child of node.children) {
      const childHeight = height(child) + 1; // +1 for the edge to this child

      if (childHeight > tallest) {
        secondTallest = tallest;
        tallest = childHeight;
      } else if (childHeight > secondTallest) {
        secondTallest = childHeight;
      }
    }

    maxDiameter = Math.max(maxDiameter, tallest + secondTallest);

    return tallest;
  }

  height(root);
  return maxDiameter;
}
```

**Q15. How does finding the "diameter" of a general (not necessarily rooted, possibly cyclic-looking-but-actually-tree-structured) undirected TREE graph differ from the rooted binary-tree diameter technique, and what is the "BFS twice" technique?**
A: When a tree is given as a general undirected graph (edges between nodes, no inherent "root" or "left/right child" structure), a different, elegant technique applies: run BFS (or DFS) from **any arbitrary starting node** to find the node **farthest** from it — call this node `A`. Then run BFS again, this time starting from `A`, and find the node farthest from `A` — call this node `B`. The distance between `A` and `B` is guaranteed to be the tree's diameter. This works due to a graph-theoretic property specific to trees: the farthest node from *any* starting point is always one endpoint of *some* longest path (diameter path) in the tree, so starting a second search specifically from that farthest node is guaranteed to find the true diameter's other endpoint.

```js
function treeDiameterBFSTwice(graph, anyStartNode) {
  const bfsFarthest = (start) => {
    const visited = new Set([start]);
    const queue = [[start, 0]];
    let farthestNode = start, maxDist = 0;

    while (queue.length > 0) {
      const [node, dist] = queue.shift();
      if (dist > maxDist) {
        maxDist = dist;
        farthestNode = node;
      }
      for (const neighbor of graph[node]) {
        if (!visited.has(neighbor)) {
          visited.add(neighbor);
          queue.push([neighbor, dist + 1]);
        }
      }
    }

    return [farthestNode, maxDist];
  };

  const [nodeA] = bfsFarthest(anyStartNode);
  const [, diameter] = bfsFarthest(nodeA);

  return diameter;
}
```

**Q16. Why does the "BFS twice" technique work — what is the underlying property that guarantees starting the second BFS from the first BFS's farthest node finds the true diameter?**
A: This relies on a specific property of trees (proven via a short case-based argument, though the intuition is straightforward): for any starting node `S`, the node farthest from `S` — call it `A` — is guaranteed to be **one of the two endpoints of some longest path in the tree**. This holds even though `S` itself might not be anywhere near the actual diameter path. Once you have `A` (a genuine diameter-path endpoint), running BFS from `A` and finding the farthest node from *it* is guaranteed to find `A`'s corresponding diameter-path partner, since by definition the diameter is the longest path in the tree, and `A` being a true endpoint means the farthest node from `A` cannot be anything other than the diameter's other end. This technique is notably different in character from the rooted binary-tree single-pass technique (Q7) — it's specific to unrooted, general-tree-as-graph representations, and wouldn't directly apply (or wouldn't be necessary) if the tree already has an explicit root and parent-child structure.

**Q17. How would you compute the diameter of a WEIGHTED tree (edges have varying lengths/costs, not just unit length), and does the single-pass technique still apply?**
A: Yes, directly — replace "+1 for an edge" with "+ this specific edge's weight" throughout the height computation, and the same core single-pass logic (rooted tree) or BFS-twice logic (unrooted tree, using weighted shortest-path BFS/Dijkstra instead of unweighted BFS) still correctly finds the diameter, now measured in total edge weight rather than edge count. The structural insight (longest path through a node = its two tallest weighted subtree "reaches," or "farthest weighted node from an arbitrary start is a true diameter endpoint") is weight-agnostic and carries over unchanged.

### Section 5: Scenario / Interview-Style Questions

**Q18. "You're asked to find the diameter of a binary tree, and your first instinct is to compute, for every node, height(left) + height(right), calling a separate height() function each time. What's the complexity concern, and how do you fix it?"**
A: Calling a separate O(n) height computation at each of the n nodes results in O(n²) total time — a classic redundant-recomputation inefficiency. I'd fix this by combining the height computation and the diameter-tracking into a **single post-order traversal**: compute each node's height bottom-up once, and as a side effect of that same computation, check and update a running "max diameter seen so far" value using the already-computed left/right heights at each node — this achieves O(n) total time instead of O(n²), since every node's height is now computed exactly once.

**Q19. "A teammate's balanced-tree-check implementation seems correct but is noticeably slow on very unbalanced trees. What might be happening, and how would you fix it?"**
A: If their implementation calls a separate height-computation function at every node to check the balance condition (the naive O(n²) approach), I'd recommend switching to the single-pass, sentinel-based early-termination technique (Q11) — this not only fixes the asymptotic complexity (O(n) instead of O(n²)) but also gives a genuine practical speedup on trees where the imbalance is detected early/near the root, since the sentinel value propagates up and short-circuits the remaining traversal immediately rather than continuing to needlessly check already-doomed subtrees.

**Q20. "How would you find the diameter of a tree that's given to you as an adjacency list (undirected graph edges), with no designated root or parent/child structure?"**
A: I'd use the "BFS twice" technique (Q15-Q16): run BFS from any arbitrary starting node to find the farthest node from it, then run BFS again from that farthest node to find the true diameter (the distance to the new farthest node from that second BFS). I'd explain that this works specifically because of a property unique to trees — the farthest node from any starting point is guaranteed to be an endpoint of some longest path in the tree — and note that this is a genuinely different technique from the rooted-tree single-pass height/diameter computation, since there's no natural "left/right subtree" structure to exploit here.

**Q21. "Extend your diameter solution to also return the actual PATH (the sequence of nodes), not just its length. How would you modify the single-pass technique?"**
A: Alongside tracking `maxDiameter` (the length), also track which specific node was the "highest point" of the current best diameter path found so far, plus which of its children contributed the two tallest subtree heights used in that best diameter calculation. Once the traversal completes, you'd need a follow-up step: from that recorded highest-point node, walk down its two tallest branches (following whichever child pointers led to those tallest heights at each step) to reconstruct the full path node-by-node — this is a meaningful additional complexity on top of just tracking the diameter's length, since the length calculation alone doesn't retain enough information to trivially reconstruct the path without this extra bookkeeping.

## Problem 1 — Maximum Depth (Height) of Binary Tree

### Problem
Given the root of a binary tree, return its maximum depth — the number of nodes along the longest path from the root down to the farthest leaf node.

```
Input:
        3
       / \
      9   20
         /  \
        15   7

Output: 3   (using the NODE-COUNT convention: 3 → 20 → 15 is 3 nodes)
```

### Pattern Recognition
Simple recursive post-order computation — each node's depth is 1 more than the deeper of its two subtrees.

### Key Insight
A node's maximum depth (using the node-count convention here, per the problem's typical phrasing) is `1 + max(depth of left subtree, depth of right subtree)`, with an empty node contributing 0 — this recursive relationship directly mirrors the definition itself.

### Approach
Base case: `null` node returns 0. Recursive case: return 1 plus the larger of the two recursively-computed subtree depths.

### Solution

```js
function maxDepth(root) {
  if (root === null) return 0;
  return 1 + Math.max(maxDepth(root.left), maxDepth(root.right));
}
```

### Dry Run

```
Tree:
        3
       / \
      9   20
         /  \
        15   7

maxDepth(3):
  maxDepth(9):
    maxDepth(null) = 0
    maxDepth(null) = 0
    return 1 + max(0,0) = 1
  maxDepth(20):
    maxDepth(15):
      maxDepth(null)=0, maxDepth(null)=0 → return 1+max(0,0)=1
    maxDepth(7):
      maxDepth(null)=0, maxDepth(null)=0 → return 1+max(0,0)=1
    return 1 + max(1,1) = 2
  return 1 + max(1, 2) = 3

Result: 3 ✓ (path 3→20→15 or 3→20→7, both length 3 in node-count)
```

### Complexity
- Time: O(n) — every node visited exactly once.
- Space: O(h) — recursion call stack, where h is the tree's height (O(log n) balanced, O(n) worst-case unbalanced).

### Edge Cases
- Empty tree: base case immediately returns 0.
- Single node: `1 + max(0,0) = 1` — correct under the node-count convention.
- Completely unbalanced (linked-list-shaped) tree: depth equals the total number of nodes, and the recursion depth (O(n)) risks stack overflow for very large such trees — worth mentioning the iterative BFS alternative (Q4) as a mitigation.

### Follow-up Questions
- "Compute this iteratively instead, to avoid deep recursion risk?" → See Q4 — BFS level-counting achieves the same result with O(width) space instead of O(height) call-stack space.
- "What convention are you using — is a single node depth 0 or 1?" → Worth proactively clarifying (Q2) rather than assuming, since problem statements vary.

## Problem 2 — Diameter of Binary Tree (Optimized Single-Pass)

### Problem
Given the root of a binary tree, return the length of the diameter — the length of the longest path between any two nodes, measured in the number of edges. This path may or may not pass through the root.

```
Input:
        1
       / \
      2   3
     / \
    4   5

Output: 3   (path 4→2→5, or path 4→2→1→3, both have length 3... 

Actually let's verify: 4→2→5 has 2 edges (length 2). 4→2→1→3 has 3 edges (length 3).
Output: 3  (the path 4→2→1→3)
```

### Pattern Recognition
The optimized single-pass technique — compute height bottom-up, and at every node, check whether the sum of its left and right subtree heights (i.e., the longest path passing through that node) sets a new diameter record.

### Key Insight
Every possible path in the tree has a unique "highest point" (its nodes' lowest common ancestor) — checking `leftHeight + rightHeight` at every single node during a bottom-up height computation exhaustively covers every possible path's length, since every path is accounted for at its own specific highest-point node.

### Approach
Post-order recursive height computation. At each node, after recursively computing left and right subtree heights, update a shared `maxDiameter` tracker using `leftHeight + rightHeight + 2` (using the edge-count convention where a null node has height -1), then return this node's own height (`1 + max(leftHeight, rightHeight)`).

### Solution

```js
function diameterOfBinaryTree(root) {
  let maxDiameter = 0;

  function height(node) {
    if (node === null) return -1;

    const leftHeight = height(node.left);
    const rightHeight = height(node.right);

    maxDiameter = Math.max(maxDiameter, leftHeight + rightHeight + 2);

    return 1 + Math.max(leftHeight, rightHeight);
  }

  height(root);
  return maxDiameter;
}
```

### Dry Run

```
Tree:
        1
       / \
      2   3
     / \
    4   5

height(1):
  height(2):
    height(4): height(null)=-1, height(null)=-1 → maxDiameter=max(0,-1+-1+2=0)=0 → return 1+max(-1,-1)=0
    height(5): height(null)=-1, height(null)=-1 → maxDiameter=max(0,0)=0 → return 0
    maxDiameter = max(0, leftHeight(0)+rightHeight(0)+2=2) = 2
    return 1 + max(0,0) = 1
  height(3):
    height(null)=-1, height(null)=-1 → maxDiameter=max(2, -1+-1+2=0)=2 → return 1+max(-1,-1)=0
  maxDiameter = max(2, leftHeight(1)+rightHeight(0)+2=3) = 3
  return 1 + max(1,0) = 2

Result: maxDiameter = 3 ✓ (the path 4→2→1→3, using edges: 4-2, 2-1, 1-3 = 3 edges)
```

### Complexity
- Time: O(n) — single traversal, O(1) work per node.
- Space: O(h) — recursion call stack.

### Edge Cases
- Single node: `height(root)` computes `leftHeight=-1, rightHeight=-1`, `maxDiameter = max(0, -1+-1+2=0) = 0` — correctly, a single node has no path at all (diameter 0).
- Completely linear (linked-list-shaped) tree: the diameter equals `n-1` (the total path from one end to the other), and the single node where `leftHeight+rightHeight` is maximized is wherever the "middle" of that line happens to sit relative to the root's specific structure — still correctly found by checking every node.
- Diameter path entirely within one subtree (not touching the root): correctly captured, since the traversal checks the diameter-through-node condition at EVERY node, including all non-root nodes deep within either subtree.

### Follow-up Questions
- "Show the naive O(n²) version and explain why it's slower." → See Q6 — recomputing height via a fresh O(n) call at every node.
- "Extend to also return the actual longest path (list of nodes), not just its length?" → See Q21 — requires additional bookkeeping of which node/children produced the current best diameter, plus a reconstruction step afterward.

## Problem 3 — Balanced Binary Tree (Optimized Single-Pass with Early Termination)

### Problem
Given the root of a binary tree, determine if it is height-balanced — for every node, the height difference between its left and right subtrees is at most 1.

```
Input:
        1
       / \
      2   2
     / \
    3   3
   / \
  4   4

Output: false  (the subtree rooted at the first "2" has left-height 2, right-height 0 — 
                difference of 2, exceeding 1)
```

### Pattern Recognition
Optimized single-pass post-order height computation with a sentinel value used to signal and immediately propagate "already found unbalanced" up through the recursion, avoiding redundant work.

### Key Insight
The moment any subtree is found to be unbalanced, there's no need to continue computing exact heights for the rest of the tree — returning a distinctive sentinel value (outside the range of any legitimate height) lets every enclosing recursive call detect this immediately and short-circuit its own remaining work, rather than needlessly computing (and then discarding) further height values.

### Approach
Post-order recursion returning either a genuine height or the sentinel `-2` (chosen because legitimate heights are always `>= -1` under the edge-count convention). At each node: if either child's returned value is the sentinel, immediately propagate it up without further computation; otherwise, check the current node's own balance condition, returning the sentinel if violated, or the correct height otherwise.

### Solution

```js
function isBalanced(root) {
  const UNBALANCED = -2;

  function checkHeight(node) {
    if (node === null) return -1;

    const leftHeight = checkHeight(node.left);
    if (leftHeight === UNBALANCED) return UNBALANCED;

    const rightHeight = checkHeight(node.right);
    if (rightHeight === UNBALANCED) return UNBALANCED;

    if (Math.abs(leftHeight - rightHeight) > 1) return UNBALANCED;

    return 1 + Math.max(leftHeight, rightHeight);
  }

  return checkHeight(root) !== UNBALANCED;
}
```

### Complexity
- Time: O(n) worst case (a genuinely balanced tree, or imbalance detected only very late, requires visiting every node) — but with real practical savings when imbalance is detected early/near the root, since the sentinel short-circuits remaining recursive calls.
- Space: O(h) — recursion call stack.

### Edge Cases
- Empty tree: base case immediately returns -1 (a valid height, not the sentinel), so `isBalanced` correctly returns `true` (an empty tree is trivially balanced).
- Single node: both children are `null` (height -1 each), difference 0, correctly returns `true`.
- Imbalance at the very root's immediate children: detected essentially immediately, minimal wasted work.
- Imbalance deep in a leaf-level subtree, with the rest of the tree otherwise huge and balanced: the sentinel is generated deep in the recursion and propagates all the way back up through every enclosing call efficiently (O(1) check-and-return at each level), rather than needing special handling to "bubble up" — this is exactly what the sentinel design is for.

### Follow-up Questions
- "Show the naive O(n²) version." → See Q10 — recomputing height via a separate O(n) call at every node to check its own balance condition.
- "Why use a sentinel instead of a separate boolean flag?" → See Q12 — a sentinel keeps everything in a single return-value channel; a flag variable is also valid but has slightly more surface area for order-of-operations bugs.

## Problem 4 — Maximum Depth of N-ary Tree

### Problem
Given a root of an n-ary tree (each node can have any number of children, stored in a `children` array), find its maximum depth — the number of nodes along the longest path from the root to the farthest leaf.

```
Input (n-ary tree, root has 3 children, one of which has 2 children of its own):
        1
      / | \
     3  2  4
    / \
   5   6

Output: 3  (path 1→3→5 or 1→3→6, both 3 nodes)
```

### Pattern Recognition
Direct generalization of binary tree depth computation — instead of `max(left, right)`, take the max depth across ALL children.

### Key Insight
A node's maximum depth is `1 + max(depth of each child)`, generalizing the binary case's `1 + max(left, right)` to an arbitrary number of children — if there are no children at all, the node is a leaf, contributing depth 1 on its own (or 0, depending on convention, mirroring Q2's discussion).

### Approach
Base case: `null` node (or one with no children) returns the appropriate base value. Recursive case: compute the depth of every child, take the maximum, add 1.

### Solution

```js
function maxDepthNAry(root) {
  if (root === null) return 0;

  if (root.children.length === 0) return 1;

  let maxChildDepth = 0;
  for (const child of root.children) {
    maxChildDepth = Math.max(maxChildDepth, maxDepthNAry(child));
  }

  return 1 + maxChildDepth;
}
```

### Dry Run

```

        1
      / | \
     3  2  4
    / \
   5   6

  children = [3, 2, 4]

  maxDepthNAry(3):
    children = [5, 6]
    maxDepthNAry(5): children=[] → return 1
    maxDepthNAry(6): children=[] → return 1
    maxChildDepth = max(1,1) = 1
    return 1 + 1 = 2

  maxDepthNAry(2): children=[] → return 1
  maxDepthNAry(4): children=[] → return 1

  maxChildDepth = max(2, 1, 1) = 2
  return 1 + 2 = 3

Result: 3 ✓ (path 1→3→5 or 1→3→6, 3 nodes total)
```

### Complexity
- Time: O(n) — every node visited exactly once, with O(children count) work per node, summing to O(n) total across the whole tree (since the sum of all nodes' children counts equals the total number of edges, which is n-1 for a tree).
- Space: O(h) — recursion call stack, where h is the tree's height.

### Edge Cases
- Empty tree: explicit early return of 0.
- Root with no children (single node): explicit check `root.children.length === 0` returns 1 directly.
- A node with a very large number of children, all shallow: the `for` loop correctly handles any branching factor uniformly, no special-casing needed for "how many children" beyond just iterating the array.

### Follow-up Questions
- "Extend to also find the DIAMETER of this n-ary tree?" → See Q14 — track the top-TWO tallest child-subtree heights (not just the single tallest) at each node, since a path through a node in an n-ary tree still only uses at most two of its branches.
- "Compute this iteratively via BFS instead?" → Same level-counting BFS technique as the binary-tree case (Q4), just enqueueing `node.children` instead of `node.left`/`node.right`.

## Problem 5 — Diameter of a Tree (Given as an Undirected Graph, No Root)

### Problem
Given a tree represented as an undirected graph (a connected, acyclic graph with `n` nodes and `n-1` edges, no designated root), find its diameter — the longest path between any two nodes, measured in number of edges.

```
Input graph (adjacency list):
0: [1]
1: [0, 2, 3]
2: [1]
3: [1, 4]
4: [3]

(This represents: 0-1, 1-2, 1-3, 3-4)

Output: 3   (the path 0→1→3→4, or 2→1→3→4, both length 3)
```

### Pattern Recognition
"BFS twice" — a technique specific to unrooted trees represented as graphs, exploiting the property that the farthest node from any arbitrary starting point is guaranteed to be an endpoint of some longest (diameter) path.

### Key Insight
Starting BFS from ANY node and finding its farthest node guarantees that farthest node is a genuine diameter-path endpoint — this non-obvious but provable property is what allows finding the diameter in exactly two BFS passes, without needing to check paths between all possible pairs of nodes (which would be much more expensive).

### Approach
Run BFS from an arbitrary starting node (e.g., node 0), tracking the farthest node found. Run BFS again, this time starting from that farthest node, and find the new farthest node's distance — that distance is the tree's diameter.

### Solution

```js
function treeDiameter(edges, n) {
  const graph = Array.from({ length: n }, () => []);
  for (const [a, b] of edges) {
    graph[a].push(b);
    graph[b].push(a);
  }

  function bfsFarthest(start) {
    const visited = new Set([start]);
    const queue = [[start, 0]];
    let farthestNode = start, maxDist = 0;

    while (queue.length > 0) {
      const [node, dist] = queue.shift();
      if (dist > maxDist) {
        maxDist = dist;
        farthestNode = node;
      }
      for (const neighbor of graph[node]) {
        if (!visited.has(neighbor)) {
          visited.add(neighbor);
          queue.push([neighbor, dist + 1]);
        }
      }
    }

    return [farthestNode, maxDist];
  }

  const [nodeA] = bfsFarthest(0); // start from any arbitrary node
  const [, diameter] = bfsFarthest(nodeA); // second BFS from the found endpoint

  return diameter;
}
```

### Complexity
- Time: O(n) — two BFS passes, each O(V+E) = O(n) for a tree (since a tree has exactly n-1 edges).
- Space: O(n) — adjacency list storage, visited sets, and queues.

### Edge Cases
- Single node, no edges: both BFS passes trivially stay at the start node with distance 0 — correctly returns diameter 0.
- Two nodes, one edge: first BFS finds the other node at distance 1; second BFS confirms distance 1 back — correctly returns diameter 1.
- A "star" graph (one central node connected to many leaves, no other edges): first BFS from the center finds any leaf at distance 1; second BFS from that leaf correctly finds the diameter is 2 (leaf → center → another leaf), demonstrating that starting from an arbitrary non-endpoint node still correctly leads to finding a genuine endpoint on the first pass.
- Starting the first BFS from a node that's ALREADY a diameter endpoint: the technique still works correctly — the first BFS would find the true diameter's other endpoint directly, and the second BFS from there would simply confirm the same distance.

### Follow-up Questions
- "Why does this technique specifically require the graph to be a TREE (no cycles)? Would it work on a general graph?" → No — the "farthest node is guaranteed to be a diameter endpoint" property relies specifically on tree structure (a unique path between any two nodes); general graphs with cycles don't have this guarantee, and finding the diameter of a general graph typically requires a full all-pairs-shortest-path computation instead (e.g., running BFS from every node, O(V × (V+E)) total, or more advanced techniques).
- "Extend to a WEIGHTED tree?" → Replace BFS with a weighted shortest-path approach (e.g., Dijkstra's algorithm, or a straightforward weighted DFS/BFS variant since it's still a tree with unique paths) — the same two-pass "farthest node" property still holds, now measured in total path weight rather than edge count (see Q17).

## Quick Reference — Pattern Decision Tree

```
Does the problem involve computing height, depth, or diameter of a tree?
│
├── SIMPLE HEIGHT/DEPTH OF A ROOTED BINARY (OR N-ARY) TREE?
│   ├── Recursive preferred → 1 + max(subtree heights), base case for null/leaf per convention
│   └── Iterative / avoid deep recursion → BFS level-counting (see level-order-traversal guide)
│
├── DIAMETER OF A ROOTED BINARY TREE (longest path, any two nodes)?
│   └── Single-pass post-order: compute height bottom-up, track max(leftHeight+rightHeight)
│       at EVERY node simultaneously → O(n), NOT O(n²) (avoid naive per-node height recomputation)
│
├── DIAMETER OF A ROOTED N-ARY TREE?
│   └── Same single-pass idea, but track the TOP TWO tallest child-subtree heights per node
│       (not just one), since a path through a node still only uses at most 2 branches
│
├── DIAMETER OF AN UNROOTED TREE (given as a graph, no designated root)?
│   └── "BFS Twice" — BFS from any node to find a genuine diameter endpoint,
│       then BFS again from THAT node to find the actual diameter distance
│
├── IS THE TREE HEIGHT-BALANCED (left/right height difference ≤ 1 at every node)?
│   └── Single-pass post-order with a SENTINEL value (e.g., -2) that immediately propagates
│       "unbalanced" up the call stack, short-circuiting further unnecessary work
│
├── WEIGHTED TREE (edges have non-unit costs)?
│   └── Same core techniques (single-pass rooted, or BFS-twice unrooted), replacing
│       "+1 per edge" with "+ this edge's specific weight" throughout
│
└── NEED THE ACTUAL PATH/NODES, NOT JUST THE DIAMETER'S LENGTH?
    └── Extend the single-pass technique with extra bookkeeping (which node/children produced
        the current best result), then a separate reconstruction pass after the main traversal
```

## Common Bugs Checklist

Before submitting any height/depth/diameter/balance solution, verify:

1. **Height/depth convention (edge-count vs node-count) chosen deliberately and applied CONSISTENTLY?** — Mixing conventions mid-solution (e.g., base case returns 0 in one place but -1 in another) produces silently wrong off-by-one results.

2. **Diameter: computed in a SINGLE pass alongside height, not via a separate O(n) height() call at every node?** — The latter is the classic O(n²) inefficiency that a strong solution should proactively avoid, not just accidentally stumble into a correct-but-slow version.

3. **Diameter: `maxDiameter` checked/updated at EVERY node during the traversal, not just at the root?** — The longest path frequently does NOT pass through the root; only checking the root's own left+right height misses paths entirely contained within a subtree.

4. **Balanced check: sentinel value chosen OUTSIDE the range of any legitimate height, and checked/propagated correctly at EVERY level of recursion (both after the left AND after the right recursive call)?** — Forgetting to check for the sentinel after just one of the two recursive calls (e.g., checking after the left call but not after the right) can miss propagating an already-found imbalance, corrupting the final result.

5. **N-ary diameter: tracking the top TWO tallest child heights, not just the single tallest?** — Using only the single tallest child height misses that a path through a node can use two DIFFERENT branches simultaneously, which is exactly what "diameter through this node" means.

6. **BFS-twice technique: second BFS genuinely started from the FIRST BFS's farthest node, not from the original arbitrary starting node again?** — Restarting from the same original node twice doesn't exploit the "farthest node is a genuine diameter endpoint" property at all, and would not reliably find the true diameter.

7. **Empty tree / single-node edge cases explicitly handled per the chosen convention?** — An empty tree's height, a single node's height, and a single node's diameter (which should be 0, since there's no path at all with only one node) are common places for off-by-one mistakes if not explicitly reasoned through.

---

**Final Tip:** At the 5 YOE level, interviewers expect immediate, precise use of height/depth/diameter terminology (and proactive clarification of the edge-count vs node-count convention, rather than silently assuming one), plus recognition that **height and diameter should be computed together in one traversal**, not as separate O(n) sub-routines called repeatedly — this single insight is what separates a correct-but-O(n²) answer from the expected O(n) one across nearly every problem in this family. For the balanced-tree check specifically, the sentinel-value early-termination technique is the analogous "expected optimization" — proactively presenting it, rather than waiting to be asked "can you avoid the O(n²) version," is the strongest signal of genuine fluency with this problem family.
