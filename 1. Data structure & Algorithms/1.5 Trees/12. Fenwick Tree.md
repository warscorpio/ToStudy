## Topic A: Fenwick Tree Fundamentals

### Section A1: Fundamentals

**Q1. What is a Fenwick Tree (Binary Indexed Tree), and what problem does it solve?**
A: A Fenwick Tree (also called a Binary Indexed Tree or BIT) is a data structure that maintains an array of values and supports two operations efficiently:
- **Point update**: change the value at a single index.
- **Prefix query**: compute an aggregate (sum, min, max) over a prefix `[1..i]`.

Both operations run in O(log n) time and the structure uses O(n) space — the same space as the original array. This makes it the go-to choice when an array is being modified while range aggregate queries must also be answered, a scenario where a plain prefix sum array fails (updates require O(n) rebuild) and a segment tree works but carries higher constant factors and more implementation overhead.

```
Problem: given array A of n integers, support:
  - update(i, delta): add delta to A[i]
  - prefixSum(i): return A[1] + A[2] + ... + A[i]
  - rangeSum(l, r): return A[l] + ... + A[r] = prefixSum(r) - prefixSum(l-1)

Naive array:    update O(1),    prefixSum O(n)   → too slow for many queries
Prefix array:   update O(n),    prefixSum O(1)   → too slow for many updates
Fenwick Tree:   update O(log n), prefixSum O(log n) → optimal for both
Segment Tree:   update O(log n), prefixSum O(log n) → also works, higher constant
```

**Q2. What is the key structural insight that makes a Fenwick Tree work?**
A: Every positive integer can be written in binary, and every binary number has a lowest set bit (LSB) — the rightmost `1` bit. The Fenwick Tree exploits this: `BIT[i]` stores the aggregate (sum) of a specific range of the original array, where the range length is exactly `lowbit(i) = i & (-i)` — the value of the lowest set bit of `i`. Specifically, `BIT[i]` stores the sum of `A[i - lowbit(i) + 1 .. i]` — the `lowbit(i)` elements ending at index `i`.

```
i in binary → lowbit(i) = i & (-i) → range stored in BIT[i]

i=1  (0001): lowbit=1  → BIT[1]  = A[1]
i=2  (0010): lowbit=2  → BIT[2]  = A[1] + A[2]
i=3  (0011): lowbit=1  → BIT[3]  = A[3]
i=4  (0100): lowbit=4  → BIT[4]  = A[1] + A[2] + A[3] + A[4]
i=5  (0101): lowbit=1  → BIT[5]  = A[5]
i=6  (0110): lowbit=2  → BIT[6]  = A[5] + A[6]
i=7  (0111): lowbit=1  → BIT[7]  = A[7]
i=8  (1000): lowbit=8  → BIT[8]  = A[1] + ... + A[8]
```

This decomposition is not arbitrary — it mirrors how binary numbers decompose into powers of 2. Any prefix `[1..i]` can be expressed as the union of at most `O(log n)` non-overlapping ranges, each stored in a BIT cell, enabling O(log n) prefix queries by summing the right BIT cells.

**Q3. How does the prefix sum query work, and why does it take O(log n) time?**
A: To compute the prefix sum `[1..i]`, start at index `i` and repeatedly strip the lowest set bit: sum `BIT[i]`, then set `i = i - lowbit(i)`, until `i` reaches 0. Each step removes one set bit from `i`'s binary representation. Since `i` has at most `floor(log₂ i)` set bits, the loop runs at most O(log n) times.

```js
function prefixSum(i) {
  let sum = 0;
  while (i > 0) {
    sum += BIT[i];
    i -= i & (-i); // strip lowest set bit: move to the parent's left boundary
  }
  return sum;
}
```

```
prefixSum(7):  i=7 (0111): sum += BIT[7]. i = 7 - 1 = 6.
               i=6 (0110): sum += BIT[6]. i = 6 - 2 = 4.
               i=4 (0100): sum += BIT[4]. i = 4 - 4 = 0. Stop.
sum = BIT[7] + BIT[6] + BIT[4]
    = A[7] + (A[5]+A[6]) + (A[1]+A[2]+A[3]+A[4])
    = A[1]+A[2]+A[3]+A[4]+A[5]+A[6]+A[7]  ✓
```

The path from `i` to 0 by stripping LSBs is exactly the path from a leaf to the root in an implicit binary tree — the structure of that implicit tree is what gives the Fenwick Tree its name and its O(log n) behavior.

**Q4. How does the point update work, and why does it also take O(log n) time?**
A: To add `delta` to `A[i]`, start at index `i` and repeatedly add the lowest set bit: update `BIT[i] += delta`, then set `i = i + lowbit(i)`, until `i` exceeds `n`. Each step moves to the next index that is "responsible" for covering index `i` — i.e., the next BIT cell whose stored range includes position `i`. This is the mirror image of the query: query goes up the tree by stripping LSBs (toward the root), update goes up by adding LSBs (toward the parent in the update direction).

```js
function update(i, delta) {
  while (i <= n) {
    BIT[i] += delta;
    i += i & (-i); // add lowest set bit: move to the next responsible ancestor
  }
}
```

```
update(3, +5):  i=3 (0011): BIT[3] += 5. i = 3 + 1 = 4.
                i=4 (0100): BIT[4] += 5. i = 4 + 4 = 8.
                i=8 (1000): BIT[8] += 5. i = 8 + 8 = 16 > n=8. Stop.

BIT cells updated: BIT[3], BIT[4], BIT[8] — all cells whose ranges include index 3. ✓
```

The number of cells updated per operation equals the number of bits that need to be set to reach the next "covering ancestor" — at most O(log n) steps.

**Q5. How do you build a Fenwick Tree from an initial array, and what is the most efficient construction method?**
A: Two approaches:

**Approach 1 — Naive (O(n log n))**: initialize `BIT` to all zeros, then call `update(i, A[i])` for each index `i`. Each update is O(log n), so total construction is O(n log n).

**Approach 2 — O(n) construction**: for each index `i` from 1 to n, set `BIT[i] += A[i]`, then propagate to the parent: `parent = i + lowbit(i); if (parent <= n) BIT[parent] += BIT[i]`. This builds the BIT bottom-up in a single pass:

```js
function build(A) {
  const n = A.length;
  const BIT = new Array(n + 1).fill(0); // 1-indexed

  for (let i = 1; i <= n; i++) {
    BIT[i] += A[i - 1]; // A is 0-indexed, BIT is 1-indexed
    const parent = i + (i & -i);
    if (parent <= n) BIT[parent] += BIT[i];
  }
  return BIT;
}
```

The O(n) construction works because each cell's value is propagated to exactly one parent — each cell is touched at most twice (once as a child, once as the target of a propagation), giving O(n) total work. In interviews, the O(n log n) naive construction is acceptable and clearer to explain; the O(n) version demonstrates deeper understanding.

**Q6. What does 1-indexed vs. 0-indexed mean for a Fenwick Tree, and why is 1-indexing required?**
A: Fenwick Trees are inherently 1-indexed. The reason: the entire structure relies on `lowbit(i) = i & (-i)`. When `i = 0`, `lowbit(0) = 0`, and the query/update loops `while (i > 0)` and `while (i <= n)` would either never execute or loop forever. Index 0 has no meaningful binary representation in the LSB framework — it would create an infinite loop in the update (0 + 0 = 0 forever) and is the loop termination condition in the query.

In practice: if the problem uses 0-indexed arrays, shift all indices by +1 when interfacing with the Fenwick Tree. This is a constant-factor implementation detail but a correctness-critical one — using 0 as an index is the most common source of subtle bugs.

```js
// 0-indexed input → 1-indexed BIT
function update(BIT, i, delta) {
  i++; // shift: 0-indexed → 1-indexed
  while (i < BIT.length) {
    BIT[i] += delta;
    i += i & (-i);
  }
}

function query(BIT, i) {
  i++; // shift: 0-indexed → 1-indexed
  let sum = 0;
  while (i > 0) {
    sum += BIT[i];
    i -= i & (-i);
  }
  return sum;
}
```

### Section A2: Advanced Patterns

**Q7. How do you compute a range sum `[l..r]` using a Fenwick Tree?**
A: A range sum `[l..r]` decomposes into two prefix sums: `prefixSum(r) - prefixSum(l-1)`. This works because `prefixSum(r) = A[1] + ... + A[r]` and `prefixSum(l-1) = A[1] + ... + A[l-1]`, so their difference gives `A[l] + ... + A[r]`. Both prefix queries are O(log n), so the range query is also O(log n).

```js
function rangeSum(BIT, l, r) {
  // l and r are 1-indexed
  return prefixSum(BIT, r) - prefixSum(BIT, l - 1);
}
// prefixSum(BIT, 0) must return 0 — the while loop handles this: i=0 → loop skipped.
```

The special case `l = 1`: `prefixSum(l-1) = prefixSum(0) = 0` (the while loop body never executes when `i = 0`), so the formula handles it correctly without a special-case guard.

**Q8. How do you extend a Fenwick Tree to support range updates (adding delta to all elements in `[l..r]`) alongside point queries?**
A: The standard Fenwick Tree supports point updates and prefix queries. To support range updates and point queries, use a **difference array** Fenwick Tree: instead of storing values directly, store differences `D[i] = A[i] - A[i-1]`. A range update `[l..r] += delta` becomes two point updates: `D[l] += delta` and `D[r+1] -= delta`. A point query for `A[i]` becomes a prefix sum of `D`: `A[i] = D[1] + D[2] + ... + D[i]`.

```js
// Range update: A[l..r] += delta
function rangeUpdate(BIT, l, r, delta) {
  update(BIT, l, delta);          // D[l] += delta
  update(BIT, r + 1, -delta);     // D[r+1] -= delta
}

// Point query: get A[i]
function pointQuery(BIT, i) {
  return prefixSum(BIT, i);       // sum of differences = A[i]
}
```

The insight: range updates on the original array become point updates on the difference array, and point queries on the original array become prefix sum queries on the difference array. The two operations are swapped in complexity.

**Q9. How do you support both range updates AND range queries simultaneously?**
A: Use two Fenwick Trees together. Let `D[i] = A[i] - A[i-1]` be the difference array. The prefix sum of `A` can be expressed in terms of `D`:

```
A[1] + A[2] + ... + A[i]
= sum_{k=1}^{i} sum_{j=1}^{k} D[j]
= sum_{j=1}^{i} D[j] * (i - j + 1)
= (i+1) * sum_{j=1}^{i} D[j]  -  sum_{j=1}^{i} D[j]*j
```

Maintain two BITs: `BIT1` stores `D[j]` values, `BIT2` stores `D[j] * j` values. A range update `[l..r] += delta` updates both BITs with the difference-array approach. A prefix sum query uses the formula above.

```js
// Range update [l..r] += delta:
function rangeUpdate(BIT1, BIT2, l, r, delta, n) {
  update(BIT1, l, delta);      update(BIT2, l, delta * l);
  update(BIT1, r+1, -delta);   update(BIT2, r+1, -delta * (r+1));
}

// Prefix sum query [1..i]:
function prefixQuery(BIT1, BIT2, i) {
  return prefixSum(BIT1, i) * (i + 1) - prefixSum(BIT2, i);
}

// Range sum query [l..r]:
function rangeQuery(BIT1, BIT2, l, r) {
  return prefixQuery(BIT1, BIT2, r) - prefixQuery(BIT1, BIT2, l - 1);
}
```

This is the most powerful single-dimensional Fenwick Tree variant — O(log n) for both range updates and range queries, using only 2× the memory of a single BIT.

**Q10. What is the Fenwick Tree's "find kth element" (order-statistic) operation, and how does binary lifting achieve it in O(log n)?**
A: Given a BIT where `BIT[i]` stores the count of elements at index `i` (a frequency BIT), find the smallest index `i` such that `prefixSum(i) >= k` — the kth smallest element's position. Binary lifting descends through the BIT tree level by level, choosing left or right at each level, in O(log n) without calling `prefixSum` repeatedly (which would be O(log² n) with binary search):

```js
function findKth(BIT, k, n) {
  let pos = 0;
  let bitMask = 1 << Math.floor(Math.log2(n)); // highest power of 2 ≤ n

  while (bitMask > 0) {
    const next = pos + bitMask;
    if (next <= n && BIT[next] < k) {
      // The kth element is NOT in the left half — move right
      pos = next;
      k -= BIT[next]; // subtract the count in the left half
    }
    // else: kth element IS in the left half (or next > n) — stay left
    bitMask >>= 1; // halve the step size
  }

  return pos + 1; // pos is the 0-indexed predecessor; +1 gives the 1-indexed answer
}
```

The binary lifting approach treats the BIT as an implicit binary search tree: at each level, check if the count in the current "left subtree" is ≥ k. If yes, go left (the answer is in this half). If no, subtract the left count from k and go right. This is O(log n) — one step per bit of `n`.

**Q11. How does a 2D Fenwick Tree work, and what does it support?**
A: A 2D Fenwick Tree extends the 1D structure to a 2D grid: `BIT2D[i][j]` stores a sum over a 2D subgrid determined by the lowest set bits of both `i` and `j`. Point update and 2D prefix query both become nested loops — one loop over the row dimension, one over the column dimension — each running O(log n) times, giving O(log² n) per operation.

```js
function update2D(BIT, r, c, delta, rows, cols) {
  for (let i = r; i <= rows; i += i & (-i)) {
    for (let j = c; j <= cols; j += j & (-j)) {
      BIT[i][j] += delta;
    }
  }
}

function query2D(BIT, r, c) {
  let sum = 0;
  for (let i = r; i > 0; i -= i & (-i)) {
    for (let j = c; j > 0; j -= j & (-j)) {
      sum += BIT[i][j];
    }
  }
  return sum;
}

// 2D range query [r1,c1]..[r2,c2] using inclusion-exclusion:
function rangeQuery2D(BIT, r1, c1, r2, c2) {
  return query2D(BIT, r2, c2)
       - query2D(BIT, r1-1, c2)
       - query2D(BIT, r2, c1-1)
       + query2D(BIT, r1-1, c1-1);
}
```

Use cases: 2D prefix sums with updates, counting points in a rectangle with online insertions, competitive programming problems with 2D range queries.

**Q12. When should you use a Fenwick Tree vs. a Segment Tree?**
A: Both solve the point-update + range-query problem in O(log n). The trade-offs:

| | Fenwick Tree | Segment Tree |
|---|---|---|
| Implementation | ~10 lines | ~40 lines |
| Space | O(n) | O(2n) to O(4n) |
| Constant factor | Smaller | Larger |
| Range update + range query | Needs two BITs (complex) | Built-in with lazy propagation |
| Non-invertible operations (min, max) | Cannot support min/max prefix | Supports any associative operation |
| Order-statistic (kth element) | Yes, via binary lifting | Yes, slightly more complex |
| 2D extension | O(log² n), simple | O(log² n), heavier code |

**Choose Fenwick Tree when**: the operation is invertible (sum, XOR — not min/max), point updates only (or range updates via difference array), and code brevity matters. **Choose Segment Tree when**: lazy range updates are needed, the operation is non-invertible (min, max, GCD), or the problem requires more complex range operations (range set, range multiply).

The critical limitation: **Fenwick Trees cannot support range minimum or range maximum queries** because the minimum operation has no inverse — `prefixMin(r) - prefixMin(l-1)` is meaningless since subtraction doesn't recover the range minimum from prefix minima.

## Topic B: Fenwick Tree Applications

### Section B1: Fundamentals

**Q13. What is the "count of inversions" problem, and how does a Fenwick Tree solve it?**
A: An inversion in an array is a pair `(i, j)` where `i < j` but `A[i] > A[j]`. The total count of inversions measures how far the array is from being sorted (0 inversions = sorted; `n*(n-1)/2` inversions = reverse sorted). The brute-force O(n²) approach checks all pairs. The Fenwick Tree approach:

1. **Coordinate compress**: map all values to the range `[1..n]` (handles duplicates and large values).
2. **Process right to left**: for each element `A[i]`, query the BIT for the count of elements in `[1..A[i]-1]` — these are elements smaller than `A[i]` that appear to its right (already inserted into the BIT) — add this count to the inversion total. Then update the BIT at `A[i]` by 1 (mark this element as seen).

```js
function countInversions(arr) {
  const n = arr.length;
  // Coordinate compression: map values to [1..n]
  const sorted = [...arr].sort((a, b) => a - b);
  const rank = new Map(sorted.map((v, i) => [v, i + 1]));

  const BIT = new Array(n + 1).fill(0);
  let inversions = 0;

  for (let i = n - 1; i >= 0; i--) {
    const r = rank.get(arr[i]);
    // Count elements smaller than arr[i] already seen (to the right of i)
    inversions += prefixSum(BIT, r - 1, n);
    update(BIT, r, 1, n);
  }
  return inversions;
}
```

Time: O(n log n) — coordinate compression O(n log n), then n BIT operations each O(log n). Space: O(n).

**Q14. What is the "range sum query with updates" (mutable array) problem, and why is it the canonical Fenwick Tree problem?**
A: Given an array, support: `update(i, val)` — set `A[i] = val`; `sumRange(l, r)` — return `A[l] + ... + A[r]`. This is the direct application of the Fenwick Tree: update becomes a point-delta-update (`delta = val - A[i]`, update BIT, then update the stored array); range sum becomes `prefixSum(r) - prefixSum(l-1)`. It is canonical because it is the simplest case that distinguishes the Fenwick Tree from simpler structures — a plain prefix sum array handles range queries in O(1) but breaks on updates; a plain array handles updates in O(1) but requires O(n) per query. The Fenwick Tree is the minimum-complexity structure that achieves O(log n) for both.

```js
class NumArray {
  constructor(nums) {
    this.n = nums.length;
    this.nums = new Array(this.n + 1).fill(0); // 1-indexed copy
    this.BIT = new Array(this.n + 1).fill(0);
    for (let i = 0; i < this.n; i++) this._update(i + 1, nums[i]);
  }

  _update(i, delta) {
    for (; i <= this.n; i += i & -i) this.BIT[i] += delta;
  }

  _query(i) {
    let s = 0;
    for (; i > 0; i -= i & -i) s += this.BIT[i];
    return s;
  }

  update(i, val) {
    const delta = val - this.nums[i + 1]; // +1 for 1-indexing
    this.nums[i + 1] = val;
    this._update(i + 1, delta);
  }

  sumRange(left, right) {
    return this._query(right + 1) - this._query(left); // +1 for 1-indexing shift
  }
}
```

**Q15. How does a Fenwick Tree help count elements in a range during a streaming / online insertion scenario?**
A: When elements are inserted one at a time (online) and you need to answer "how many elements inserted so far fall in range `[l, r]`?", a Fenwick Tree over the value domain provides: `update(value, 1)` on each insertion, and `rangeCount(l, r) = prefixSum(r) - prefixSum(l-1)` for each query. This works when the value domain is bounded (or can be coordinate-compressed). The Fenwick Tree maintains a frequency array dynamically — `BIT[i]` encodes the count of inserted values that contribute to prefix sums up to `i` — enabling O(log n) per operation compared to O(n) for a sorted array insert + binary search.

### Section B2: Advanced Patterns

**Q16. What is coordinate compression, and why is it almost always paired with Fenwick Trees in interview problems?**
A: Coordinate compression maps a set of values with large range (e.g., values up to 10⁹) to a compact range `[1..k]` where `k` is the number of distinct values (often k ≤ n). This is necessary because a Fenwick Tree of size `10⁹` is infeasible (10⁹ memory cells), but a Fenwick Tree of size `n` is fine. The compression: sort all relevant values, assign rank `1, 2, ..., k` to the distinct values in sorted order, then replace every value with its rank.

```js
function coordinateCompress(arr) {
  const sorted = [...new Set(arr)].sort((a, b) => a - b);
  const rank = new Map(sorted.map((v, i) => [v, i + 1]));
  return { compressed: arr.map(v => rank.get(v)), size: sorted.length, rank };
}
```

Coordinate compression is paired with Fenwick Trees whenever: the values can be large (frequency BIT over values), the problem involves counting or ranking elements (inversion count, kth smallest in stream), or the problem involves offline queries (sort queries by value, process in order). The compression turns an infeasible direct-indexed structure into a feasible one.

**Q17. What is the "number of smaller elements to the right" problem, and how does a BIT solve it?**
A: Given an array `nums`, for each index `i`, count the number of indices `j > i` where `nums[j] < nums[i]`. The brute-force is O(n²). The BIT approach (right-to-left sweep):
1. Coordinate-compress the values to `[1..n]`.
2. Process right to left: for element `nums[i]` with rank `r`, query `prefixSum(r - 1)` to count how many elements to the right (already inserted) are smaller. Record as the answer for `i`. Then `update(r, 1)` to mark `nums[i]` as inserted.

```js
function countSmaller(nums) {
  const n = nums.length;
  const sorted = [...nums].sort((a, b) => a - b);
  const rank = new Map();
  let r = 1;
  for (const v of sorted) if (!rank.has(v)) rank.set(v, r++);

  const BIT = new Array(n + 1).fill(0);
  const result = new Array(n);

  const update = (i) => { for (; i <= n; i += i & -i) BIT[i]++; };
  const query  = (i) => { let s = 0; for (; i > 0; i -= i & -i) s += BIT[i]; return s; };

  for (let i = n - 1; i >= 0; i--) {
    const rk = rank.get(nums[i]);
    result[i] = query(rk - 1); // count of inserted elements with rank < rk
    update(rk);
  }
  return result;
}
```

Time: O(n log n). This is the building block for merge-sort-based inversion count and is also solvable with merge sort in the same complexity.

**Q18. How does the Fenwick Tree support the "longest increasing subsequence" (LIS) problem in O(n log n)?**
A: The standard LIS algorithm uses binary search + patience sorting in O(n log n). The BIT-based approach is an alternative that naturally extends to LIS with constraints (e.g., LIS with specific value bounds). The BIT stores `BIT[v]` = length of the longest increasing subsequence ending with a value that maps to rank `v`. Processing left to right: for each element `nums[i]` with rank `r`, the LIS length ending at `nums[i]` is `1 + maxPrefixQuery(r - 1)` (longest IS ending with something strictly smaller). Update `BIT[r] = max(BIT[r], LIS_length)` and record the answer.

```js
function lisLength(nums) {
  const sorted = [...new Set(nums)].sort((a, b) => a - b);
  const rank = new Map(sorted.map((v, i) => [v, i + 1]));
  const m = sorted.length;

  const BIT = new Array(m + 1).fill(0); // BIT for range max query

  const updateMax = (i, val) => { for (; i <= m; i += i & -i) BIT[i] = Math.max(BIT[i], val); };
  const queryMax  = (i) => { let mx = 0; for (; i > 0; i -= i & -i) mx = Math.max(mx, BIT[i]); return mx; };

  let ans = 0;
  for (const v of nums) {
    const r = rank.get(v);
    const len = 1 + queryMax(r - 1); // best LIS ending with something < v
    updateMax(r, len);
    ans = Math.max(ans, len);
  }
  return ans;
}
```

Note: this uses a **range maximum** BIT, not a range sum BIT. Range maximum is supported by Fenwick Trees because maximum is "prefix-decomposable" (unlike range maximum where you need arbitrary ranges, prefix maximum can be maintained). However, range maximum BITs only support updates that increase values (not decrease), since max has no inverse — update is `BIT[i] = max(BIT[i], val)`, and only increasing updates preserve correctness.

**Q19. What is an "offline" Fenwick Tree technique, and when is it used?**
A: An offline technique processes all queries after seeing all of them, rather than answering each query as it arrives. For Fenwick Trees, offline processing enables handling queries whose answer depends on future updates (impossible online) by reordering operations. The classic example: "count pairs `(i, j)` where `i < j` and `A[i] + A[j] = target`" can be processed offline by sorting elements, then using a BIT to count valid complements seen so far. Another example: Mo's algorithm on trees uses offline BFS order to minimize the cost of BIT updates when answering subtree queries.

## Topic C: Cross-Topic & Interview-Style Questions

**Q20. "Explain the Fenwick Tree to someone who only knows arrays and prefix sums."**
A: A prefix sum array answers "sum of A[1..i]" in O(1) after O(n) preprocessing — but if `A[i]` changes, you must rebuild the entire prefix array in O(n). A Fenwick Tree is a smarter prefix array where each cell stores a partial sum covering a specific range — not the full prefix, just a chunk. The chunk sizes are powers of two, chosen so that any prefix sum can be assembled from at most log(n) chunks. When you update one element, you only need to update log(n) chunks that cover it, not all n prefixes. The trade-off: queries and updates both take O(log n) instead of O(1) and O(n). For any problem with many updates and many queries, O(log n) for each beats O(1)/O(n) or O(n)/O(1).

**Q21. "What is `i & (-i)`, and how does two's complement make it work?"**
A: In two's complement representation, `-i` is the bitwise complement of `i` plus 1. For any integer `i`, the bits of `-i` are: all bits above the lowest set bit of `i` are flipped, and the lowest set bit and everything below it remain. ANDing `i` with `-i` zeros out all bits except the lowest set bit:

```
i  = 0b...1 0 1 1 0 0   (example: 12 = 0b1100)
-i = 0b...0 1 0 1 0 0   (two's complement of 12)
i & (-i) = 0b...0 0 0 1 0 0   = 4 (the lowest set bit of 12)

i=6  (0110): -i = 1010. i & (-i) = 0010 = 2. ✓ (6's lowest set bit is the 2-bit)
i=12 (1100): -i = 0100. i & (-i) = 0100 = 4. ✓ (12's lowest set bit is the 4-bit)
```

This operation isolates the lowest set bit in O(1), which is the core arithmetic operation of every Fenwick Tree traversal. Its elegance — a single bitwise operation replacing a loop that would search for the lowest set bit — is why Fenwick Trees are so concise despite their sophisticated structure.

**Q22. "What are the failure modes of a Fenwick Tree — what queries can it NOT answer efficiently?"**
A: Three important limitations:

1. **Non-invertible range queries (min, max)**: `rangeMax(l, r) = prefixMax(r) - prefixMax(l-1)` is meaningless — max has no inverse. A Fenwick Tree can answer "prefix max" queries (max of `A[1..i]`) but NOT "range max" queries (`max of A[l..r]` for arbitrary `l > 1`). For range max/min with updates, use a Segment Tree.

2. **Arbitrary range updates without the difference-array trick**: directly updating a range `[l..r]` in a standard sum BIT requires n point updates — O(n log n). The difference-array trick (Q8) recovers O(log n) per range update but only for sum, not for more complex operations.

3. **Predecessor/successor queries**: "find the largest element ≤ x in the current set" — a Fenwick Tree cannot answer this directly. An order-statistic tree (augmented BST) or a Segment Tree over the value domain is needed.

**Q23. "How would you find the prefix maximum using a Fenwick Tree, and why does it only work for prefix (not range) maximum?"**
A: A "prefix max BIT" stores `BIT[i] = max(A[i - lowbit(i) + 1 .. i])`. Query: the same loop as prefix sum, replacing `+=` with `Math.max`. Update: the same loop as point update, replacing `+=` with `Math.max`. The key constraint: updates can only **increase** values. If `A[i]` decreases, the BIT cannot correctly propagate the decrease because max has no inverse — you cannot "un-max" a previously seen maximum. This makes prefix-max BIT valid only when values are non-decreasing (e.g., the LIS problem where LIS lengths only increase) or when the structure is rebuilt from scratch after decreases.

Range max fails because decomposing `max(A[l..r])` requires both a "left boundary" prefix max and a "right boundary" suffix max — the prefix-based decomposition used in sum queries doesn't generalize to arbitrary range maxima.

**Q24. "How does a Fenwick Tree relate to a Segment Tree structurally?"**
A: Both store partial aggregates over ranges indexed by powers of two. The differences:
- **Segment Tree**: explicit binary tree with 2n to 4n nodes; each node stores the aggregate for exactly the interval `[l, r]`; the root stores the full array's aggregate; queries and updates traverse root-to-leaf paths.
- **Fenwick Tree**: implicit tree embedded in a flat array of size n; each cell `BIT[i]` stores the aggregate for a range ending at `i` whose length is `lowbit(i)`; there is no explicit root; the tree structure emerges from the LSB arithmetic.

The Fenwick Tree can be seen as a compressed, implicit Segment Tree where: nodes cover only suffix-aligned intervals (intervals that end at index `i` and have power-of-two length), the "tree traversal" is replaced by LSB arithmetic, and the implicit structure eliminates pointer overhead and reduces memory by 2×-4×. This compression is what makes Fenwick Trees faster in practice despite identical asymptotic complexity.

**Q25. "In one sentence each, describe the role of `i -= i & (-i)` in query and `i += i & (-i)` in update."**
A:
- **`i -= i & (-i)` in query**: strips the lowest set bit from `i`, moving from the current cell to the next cell whose range immediately precedes (and does not overlap) the current cell's range — assembling non-overlapping prefix chunks that together cover exactly `[1..original_i]`.
- **`i += i & (-i)` in update**: adds the lowest set bit to `i`, moving from the current cell to the next cell whose stored range subsumes the updated index — propagating the change upward to every cell that is "responsible for" covering the updated position.

**Q26. "When an interviewer says 'you need O(log n) updates and O(log n) range queries on an array' — what is your thought process for choosing between Fenwick Tree and Segment Tree?"**
A: I ask three questions: (1) Is the aggregate operation **invertible**? Sum and XOR: yes → Fenwick Tree viable. Min, max, GCD: no → Segment Tree required. (2) Do I need **range updates** (update a contiguous subarray at once)? If yes and the operation is sum: Fenwick Tree with difference-array trick or two BITs. If yes and the operation is non-sum: Segment Tree with lazy propagation. (3) Is **code brevity** critical (e.g., competitive programming under time pressure)? Fenwick Tree is ~10 lines vs. ~40 lines for Segment Tree. Answering these three questions in sequence always leads to the correct choice. For most standard interview problems (range sum with updates), Fenwick Tree is the answer — simpler, faster in practice, same asymptotic complexity.

**Q27. "Walk me through the complete Fenwick Tree solution for 'count inversions' — from the insight to the final code."**
A: An inversion is a pair where a larger element appears before a smaller one. Processing right to left, when I encounter element `A[i]`, all previously seen elements (to the right of `i`) that are smaller than `A[i]` form inversions with `A[i]`. I need: "how many of the already-seen elements have value < `A[i]`?" — a prefix count query. A Fenwick Tree over the value space answers this in O(log n): insert each value by incrementing its frequency, query prefix sum up to `A[i]-1` to count smaller values. Coordinate compression maps large values to `[1..n]` to make the BIT size feasible. The total is O(n log n) for processing, which matches the optimal merge-sort-based solution but with a simpler implementation structure.

## Problem 1 — Range Sum Query — Mutable (LeetCode 307)

### Problem
Given an integer array `nums`, handle multiple queries of the following types:
- `update(index, val)`: update `nums[index]` to be `val`.
- `sumRange(left, right)`: return the sum of `nums[left..right]` (inclusive).

```
Input:
  NumArray([-2, 0, 3, -5, 2, -1])
  sumRange(0, 2)  → 1     (-2 + 0 + 3)
  update(1, 2)
  sumRange(0, 2)  → 3     (-2 + 2 + 3)
  sumRange(2, 5)  → -1    (3 + (-5) + 2 + (-1))
```

### Pattern Recognition
Standard Fenwick Tree (sum BIT) — the canonical mutable range sum problem. Point updates and prefix sum queries both O(log n). Range sum = prefix sum difference.

### Key Insight
The delta-update pattern: when `nums[i]` changes from `oldVal` to `newVal`, the BIT only needs to know the *difference* `delta = newVal - oldVal`. The BIT stores cumulative sums, so adding `delta` to all affected cells correctly adjusts every prefix sum that includes index `i`. This avoids rebuilding the BIT or querying the old value from it — only the original array (stored separately) needs to track the old value.

### Approach
Store the original array in `this.nums` (1-indexed) and a BIT array in `this.BIT` (1-indexed). Constructor: build BIT via n `_update` calls. `update(i, val)`: compute `delta = val - this.nums[i+1]`, update `this.nums[i+1] = val`, call `_update(i+1, delta)`. `sumRange(l, r)`: return `_query(r+1) - _query(l)` (converting 0-indexed input to 1-indexed BIT).

### Solution

```js
class NumArray {
  constructor(nums) {
    this.n = nums.length;
    this.nums = new Array(this.n + 1).fill(0); // 1-indexed shadow of input
    this.BIT  = new Array(this.n + 1).fill(0); // 1-indexed Fenwick Tree

    // Build BIT: treat each initial element as a point update
    for (let i = 0; i < this.n; i++) {
      this._update(i + 1, nums[i]); // shift 0-indexed → 1-indexed
      this.nums[i + 1] = nums[i];   // record in shadow array
    }
  }

  // Add delta to BIT at position i (1-indexed), propagate to ancestors
  _update(i, delta) {
    for (; i <= this.n; i += i & (-i)) {
      this.BIT[i] += delta;
    }
  }

  // Return prefix sum BIT[1..i] (1-indexed)
  _query(i) {
    let sum = 0;
    for (; i > 0; i -= i & (-i)) {
      sum += this.BIT[i];
    }
    return sum;
  }

  // Set nums[index] = val (0-indexed input)
  update(index, val) {
    const i = index + 1;                    // convert to 1-indexed
    const delta = val - this.nums[i];       // compute change
    this.nums[i] = val;                     // update shadow array
    this._update(i, delta);                 // propagate change to BIT
  }

  // Sum of nums[left..right] (0-indexed input, inclusive)
  sumRange(left, right) {
    // Convert 0-indexed [left, right] → 1-indexed prefix sums
    return this._query(right + 1) - this._query(left);
  }
}
```

### Dry Run

### Complexity
- Time: Constructor O(n log n); `update` O(log n); `sumRange` O(log n).
- Space: O(n) — shadow array and BIT array each of size n+1.

### Edge Cases
- `sumRange(i, i)` (single element): `_query(i+1) - _query(i)` = `A[i+1]` (a single prefix-sum difference). Correct.
- `sumRange(0, n-1)` (full array): `_query(n) - _query(0)` = full prefix sum - 0. Correct.
- `update(0, val)` (first element): `i=1`, BIT cells updated are `1, 2, 4, 8, ...` — all powers of 2 that are ≤ n. Correct.
- Negative values: BIT supports negative integers without modification — sums can be negative. Correct.

- "Implement with a Segment Tree instead?" → Segment Tree handles the same problem with slightly more code but supports range-set and range-multiply operations that BIT cannot.
- "What if we also need range maximum queries?" → BIT cannot answer this. Use a Segment Tree with lazy propagation.
- "O(n) build instead of O(n log n)?" → Use the O(n) build from Q5: propagate each cell's value to its BIT parent in a single left-to-right pass.

## Problem 2 — Count of Smaller Numbers After Self (LeetCode 315)

### Problem
Given an integer array `nums`, return a new array `counts` where `counts[i]` is the number of smaller elements to the right of `nums[i]`.

```
Input:  nums = [5, 2, 6, 1]
Output: [2, 1, 1, 0]

Explanation:
  5: [2, 6, 1] → 2 elements smaller (2 and 1)
  2: [6, 1]    → 1 element smaller (1)
  6: [1]       → 1 element smaller (1)
  1: []        → 0 elements smaller
```

### Pattern Recognition
Coordinate compression + right-to-left BIT sweep — process elements from right to left; for each element, query the BIT for the count of smaller elements already inserted (those to the right); then insert the current element. The BIT acts as a frequency array over the compressed value domain.

### Key Insight
Processing right to left means "elements already in the BIT" = "elements to the right in the original array." A BIT prefix sum query at rank `r-1` gives the count of inserted elements with rank < r — exactly the count of smaller elements to the right. Coordinate compression makes this feasible even for values in range `[-10⁴, 10⁴]` or larger.

### Approach
1. **Coordinate compress**: assign ranks 1..k to the distinct values in sorted order.
2. **Initialize BIT** of size k+1.
3. **Right to left**: for each `nums[i]` with rank `r`: record `query(r-1)` as `counts[i]`; call `update(r, 1)`.
4. Return `counts`.

### Solution

```js
function countSmaller(nums) {
  const n = nums.length;

  // Step 1: Coordinate compression
  const sorted = [...new Set(nums)].sort((a, b) => a - b);
  const rank = new Map(sorted.map((v, i) => [v, i + 1])); // value → 1-indexed rank
  const m = sorted.length; // size of compressed domain

  // Step 2: Fenwick Tree over [1..m]
  const BIT = new Array(m + 1).fill(0);

  const update = (i) => {
    for (; i <= m; i += i & (-i)) BIT[i]++;
  };

  const query = (i) => {
    let s = 0;
    for (; i > 0; i -= i & (-i)) s += BIT[i];
    return s;
  };

  // Step 3: right to left sweep
  const counts = new Array(n);
  for (let i = n - 1; i >= 0; i--) {
    const r = rank.get(nums[i]);
    counts[i] = query(r - 1); // count of elements with rank < r (value < nums[i])
    update(r);                 // mark nums[i] as inserted
  }

  return counts;
}
```

## Problem 3 — Count of Range Sum (LeetCode 327)

### Problem
Given an integer array `nums` and two integers `lower` and `upper`, return the number of range sums that lie in `[lower, upper]` inclusive. A range sum `S(i, j)` is defined as the sum of `nums[i..j]` (0-indexed, `i ≤ j`).

```
Input:  nums = [-2, 5, -1], lower = -2, upper = 2
Output: 3
Explanation: S(0,0)=-2, S(2,2)=-1, S(0,2)=2  → 3 range sums in [-2, 2]
```

### Pattern Recognition
Prefix sums + coordinate-compressed BIT — a range sum `S(i,j) = prefix[j+1] - prefix[i]` lies in `[lower, upper]` iff `prefix[j+1] - upper ≤ prefix[i] ≤ prefix[j+1] - lower`. For each `j`, count how many earlier prefix sums fall in this window — a range count query on the BIT over prefix sum values.

### Key Insight
Reframe as: for each new prefix sum `prefix[j+1]`, how many previously seen prefix sums `prefix[i]` (for `i ≤ j`) satisfy `prefix[j+1] - upper ≤ prefix[i] ≤ prefix[j+1] - lower`? This is a range count query `[lo, hi]` on the set of seen prefix sums — exactly what a BIT over the prefix-sum value domain answers in O(log n). Coordinate compress all prefix sums (including the window boundaries) before processing.

### Approach
1. Compute all `n+1` prefix sums (including `prefix[0] = 0`).
2. Coordinate-compress all prefix sums plus all window boundary values (`prefix[j] - upper`, `prefix[j] - lower` for each j) — all values that will ever be queried or inserted.
3. Process prefix sums left to right: for `prefix[j+1]`, query BIT for range `[prefix[j+1]-upper, prefix[j+1]-lower]`; add to count. Then insert `prefix[j+1]` into BIT. Start with `prefix[0]` already inserted.

### Solution

```js
function countRangeSum(nums, lower, upper) {
  const n = nums.length;

  // Step 1: compute all prefix sums
  const prefix = new Array(n + 1);
  prefix[0] = 0;
  for (let i = 0; i < n; i++) prefix[i + 1] = prefix[i] + nums[i];

  // Step 2: coordinate compression over all relevant values
  // Include prefix sums AND all window boundary values
  const allVals = new Set();
  for (const p of prefix) {
    allVals.add(p);
    allVals.add(p - lower);  // upper boundary for query window
    allVals.add(p - upper);  // lower boundary for query window
  }
  const sorted = [...allVals].sort((a, b) => a - b);
  const rank = new Map(sorted.map((v, i) => [v, i + 1]));
  const m = sorted.length;

  // Fenwick Tree helpers
  const BIT = new Array(m + 1).fill(0);
  const update = (i) => { for (; i <= m; i += i & -i) BIT[i]++; };
  const query  = (i) => { let s = 0; for (; i > 0; i -= i & -i) s += BIT[i]; return s; };
  const rangeQ = (l, r) => l > r ? 0 : query(r) - query(l - 1);

  // Step 3: sweep prefix sums, query then insert
  let count = 0;
  update(rank.get(prefix[0])); // insert prefix[0] = 0 first

  for (let j = 1; j <= n; j++) {
    const p = prefix[j];
    // Count prefix[i] in [p - upper, p - lower] for i < j
    // (range sum S(i,j-1) = p - prefix[i] ∈ [lower, upper]
    //  iff prefix[i] ∈ [p - upper, p - lower])
    const lo = rank.get(p - upper); // rank of lower bound of window
    const hi = rank.get(p - lower); // rank of upper bound of window
    count += rangeQ(lo, hi);
    update(rank.get(p));             // insert current prefix sum
  }

  return count;
}
```

### Edge Cases
- All prefix sums equal: all range sums are 0; count = number of `[lower, upper]` intervals that contain 0.
- `lower = upper = 0`: count subarrays with sum exactly 0 — a standard prefix-sum + HashMap problem; BIT works here too.
- Single element `nums = [x]`: only S(0,0)=x; count = 1 if `lower ≤ x ≤ upper`, else 0.

### Follow-up Questions
- "Solve with merge sort instead?" → Merge sort can count valid pairs (prefix[i], prefix[j]) during the merge step — O(n log n) with O(n) space, but harder to implement correctly than the BIT approach.
- "What if lower and upper can change per query?" → Process offline: sort queries, maintain a BIT that evolves as prefix sums are inserted, answer each query at the right moment.

## Problem 4 — Count Inversions in an Array

### Problem
Given an integer array `arr`, count the number of inversions. An inversion is a pair `(i, j)` such that `i < j` and `arr[i] > arr[j]`.

```
Input:  arr = [2, 4, 1, 3, 5]
Output: 3
Inversions: (2,1), (4,1), (4,3)

Input:  arr = [5, 4, 3, 2, 1]
Output: 10   (every pair is an inversion: C(5,2)=10)

Input:  arr = [1, 2, 3, 4, 5]
Output: 0    (sorted — no inversions)
```

### Pattern Recognition
Right-to-left BIT sweep with coordinate compression — process elements from right to left; for each element `arr[i]`, query the BIT for the count of already-inserted elements (those to the right) with value strictly less than `arr[i]`; accumulate as the inversion count contribution of `arr[i]`.

### Key Insight
An inversion pair `(i, j)` where `i < j` and `arr[i] > arr[j]` means: when processing `arr[i]` from right to left, every element already in the BIT (from positions `i+1, ..., n-1`) that has value `< arr[i]` forms an inversion with `arr[i]`. The BIT prefix sum at rank `r-1` (one below `arr[i]`'s rank) gives this count in O(log n). Summing over all `i` gives the total inversion count.

### Approach
1. Coordinate-compress `arr` values to `[1..k]`.
2. Initialize BIT of size k+1.
3. Right to left: for each `arr[i]` with rank `r`, add `query(r-1)` to `inversions`, then `update(r, 1)`.
4. Return `inversions`.

### Solution

```js
function countInversions(arr) {
  const n = arr.length;

  // Step 1: coordinate compression
  const sorted = [...arr].sort((a, b) => a - b);
  const rank = new Map();
  let r = 1;
  for (const v of sorted) {
    if (!rank.has(v)) rank.set(v, r++); // assign rank only to distinct values
  }
  const m = rank.size; // number of distinct values

  // Step 2: Fenwick Tree over [1..m]
  const BIT = new Array(m + 1).fill(0);

  const update = (i) => {
    for (; i <= m; i += i & (-i)) BIT[i]++;
  };

  const query = (i) => {
    let s = 0;
    for (; i > 0; i -= i & (-i)) s += BIT[i];
    return s;
  };

  // Step 3: right-to-left sweep
  let inversions = 0;
  for (let i = n - 1; i >= 0; i--) {
    const rk = rank.get(arr[i]);
    inversions += query(rk - 1); // count elements to right with value < arr[i]
    update(rk);                   // insert arr[i] into BIT
  }

  return inversions;
}
```

### Complexity
- Time: O(n log n) — sorting for compression O(n log n); n BIT operations each O(log n).
- Space: O(n) — BIT size k ≤ n; rank map; sorted array.

### Edge Cases
- Already sorted: for every `i`, `query(rk-1) = 0` (all inserted elements are ≥ arr[i] since arr is increasing and right-to-left means smaller elements have already been inserted for... wait: sorted ascending means arr[i] < arr[j] for i < j. Processing right to left: at index i, elements to the right (j > i) are larger. So query(rk-1) counts elements with rank < rk already inserted — but all inserted elements are larger (higher rank). query(rk-1) = 0 for all i. inversions = 0. Correct.
- Reverse sorted: at each step, all previously inserted elements are smaller than the current. `query(rk-1)` equals the number of already-inserted elements. inversions = 0 + 1 + 2 + ... + (n-1) = n(n-1)/2. Correct.
- Duplicates: duplicate values get the same rank; `query(rk-1)` counts elements strictly smaller (rank < rk). Duplicates are not inversions — correct, since we need `arr[i] > arr[j]` strictly.

### Follow-up Questions
- "Solve with merge sort?" → Merge sort counts inversions by counting cross-partition pairs during merge — same O(n log n) complexity. BIT approach is simpler to implement and extend (e.g., weighted inversions, threshold inversions).
- "Count inversions where arr[i] - arr[j] > k (threshold inversions)?" → Change `query(rk-1)` to `query(rank(arr[i]-k-1))` — count elements to the right with value ≤ arr[i]-k-1. Same O(n log n) BIT approach.
- "Minimum swaps to sort an array?" → Minimum swaps to sort = number of inversions (each adjacent swap fixes exactly one inversion). The count-inversions answer directly gives the minimum swaps for bubble sort.

## Quick Reference — Fenwick Tree Pattern Decision Tree

```
Does the problem require dynamic range aggregation (updates + queries)?
│
├── YES — what is the aggregate operation?
│   │
│   ├── SUM (or XOR, or other INVERTIBLE operation)?
│   │   │
│   │   ├── POINT update + PREFIX/RANGE query → Standard BIT
│   │   │   update(i, delta); query(i) = prefixSum(1..i)
│   │   │   rangeSum(l,r) = query(r) - query(l-1)
│   │   │
│   │   ├── RANGE update + POINT query → Difference Array BIT
│   │   │   rangeUpdate(l, r, delta): update(l, delta), update(r+1, -delta)
│   │   │   pointQuery(i) = prefixSum(1..i) of difference array
│   │   │
│   │   └── RANGE update + RANGE query → Two-BIT technique
│   │       Maintain BIT1 (D[j]) and BIT2 (D[j]*j)
│   │       prefixQuery(i) = BIT1.query(i)*(i+1) - BIT2.query(i)
│   │
│   ├── MAX or MIN (non-invertible)?
│   │   ├── PREFIX max/min only → BIT with max (updates must be non-decreasing)
│   │   └── RANGE max/min → Use Segment Tree with lazy propagation
│   │
│   └── 2D GRID (matrix updates + subgrid queries)?
│       → 2D BIT: nested update/query loops, O(log²n) per operation
│
├── COUNTING / FREQUENCY with large value domain?
│   → Coordinate compress values to [1..k], use BIT as frequency array
│   → update(rank(val), 1) on insert
│   → rangeCount(l, r) = query(rank(r)) - query(rank(l)-1)
│   Examples: count inversions, count smaller to right,
│             count range sums, streaming rank queries
│
├── ORDER STATISTIC (find kth smallest element)?
│   → BIT with binary lifting (findKth operation)
│   → O(log n) per query without binary search
│   → Requires frequency BIT over value domain
│
├── NO UPDATES (static array)?
│   → Prefix sum array: O(n) build, O(1) query — BIT unnecessary
│
└── NEED SEGMENT TREE INSTEAD?
    ├── Range min/max with updates → Segment Tree
    ├── Range set (assign all elements in range) → Segment Tree + lazy
    ├── Multiple simultaneous aggregate types → Segment Tree
    └── Non-prefix range queries without invertibility → Segment Tree
```

## Common Bugs Checklist

Before submitting any Fenwick Tree solution, verify:

1. **Array is 1-indexed, not 0-indexed?** — The BIT requires 1-indexed positions. Index 0 causes an infinite loop in `update` (`0 + 0 = 0` forever) and never enters the loop in `query` (`0 > 0` is false). Always allocate `BIT = new Array(n + 1)` and shift input indices by `+1` when the problem is 0-indexed.

2. **BIT size is `n+1`, not `n`?** — The update loop can reach index `n` (for `i = n`, `i += i & (-i)` goes to `n + lowbit(n)`, which exceeds `n` and correctly exits). But `BIT[n]` must be a valid index — allocating size `n` leaves `BIT[n]` out of bounds. Always allocate `n+1`.

3. **`query(0)` returns 0 without entering the loop?** — The loop condition `i > 0` correctly handles `i=0`: the loop body never runs, `sum` stays 0. This matters for `rangeSum(l, r) = query(r) - query(l-1)` when `l=1`: `query(0) = 0`, giving `query(r) - 0 = query(r)` — correct. No special case needed.

4. **Delta computed correctly in point-set updates?** — When the operation is "set `A[i] = val`" (not "add delta to `A[i]`"), the BIT update must use `delta = val - oldVal`. Store the original array separately (the BIT cannot tell you the current value at a position), compute `delta`, then call `update(i, delta)`. Calling `update(i, val)` directly adds `val` to the existing value — wrong.

5. **Coordinate compression covers all query boundary values, not just array values?** — In problems like Count of Range Sum, the query windows involve `prefix[j] - upper` and `prefix[j] - lower` — these values must be in the compression map even if they don't appear in the original array. Compress *all values that will ever be used as query boundaries or insertions*, not just the input array values.

6. **Right-to-left vs. left-to-right sweep direction matches the problem's "right of" vs. "left of" semantics?** — "Count smaller elements to the RIGHT of i" → process right to left (elements already in BIT = elements to the right). "Count smaller elements to the LEFT of i" → process left to right (elements already in BIT = elements to the left). Reversing the sweep direction gives the wrong answer for the wrong side.

7. **`query(r-1)` not `query(r)` for "strictly less than" counts?** — `query(r)` counts elements with rank ≤ r (value ≤ arr[i]). `query(r-1)` counts elements with rank ≤ r-1 (value < arr[i]). For strict inequality problems (inversions, smaller to right), use `r-1`. For ≤ problems, use `r`. Off-by-one in rank here is the most common logic error.

8. **Two-BIT range-update-range-query: updating BOTH BITs on every range update?** — The two-BIT technique requires both `BIT1` and `BIT2` to be updated on every range update. Forgetting to update one of them silently corrupts all subsequent range queries. Always update both: `update(BIT1, l, delta); update(BIT2, l, delta*l); update(BIT1, r+1, -delta); update(BIT2, r+1, -delta*(r+1))`.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to recognize a Fenwick Tree problem from two signals before writing any code: (1) the problem requires dynamic prefix or range aggregation — some combination of updates and queries where neither a static prefix array nor a brute-force scan is fast enough; and (2) the aggregate operation is invertible (sum, XOR) — ruling out Segment Tree as the only option and making BIT viable. The decisive signal of genuine mastery is explaining *why* `i & (-i)` works in one sentence — "two's complement makes `-i` flip all bits above the lowest set bit and preserve everything at and below it, so ANDing with `i` isolates exactly the lowest set bit" — and then connecting it to the tree structure: "stripping the LSB in the query moves up the implicit tree toward the root, and adding the LSB in the update propagates changes to all ancestors that cover the updated index." That connection between the bit arithmetic and the tree semantics, stated without hesitation, is what separates a Fenwick Tree practitioner from someone who has memorized the template.
