# DSA: Path Sum Problems — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is a "path" in a binary tree, and why does the definition matter so much for path sum problems?**
A: A **path** in a binary tree is a sequence of nodes where each consecutive pair is connected by an edge, and no node appears more than once. The exact definition of "path" varies critically across problem variants:

- **Root-to-leaf path**: starts at the root and ends at a leaf (a node with no children). This is the most constrained variant — the path must start and end at specific structural positions.
- **Root-to-any-node path**: starts at the root but can end at any node, not necessarily a leaf. Less common but appears in prefix-sum style problems.
- **Any-node-to-any-node path**: the most general — can start and end anywhere in the tree, and crucially, does not need to pass through the root at all. This is the hardest variant and requires a fundamentally different algorithm.

Misreading which definition a problem uses is the single most common source of wrong answers on path sum problems. Always clarify upfront.

```
Tree:
       5
      / \
     4   8
    /   / \
   11  13  4
  /  \      \
 7    2       1

Root-to-leaf paths:
  5→4→11→7   sum=27
  5→4→11→2   sum=22
  5→8→13     sum=26
  5→8→4→1    sum=18

Any-node-to-any-node path (e.g., 7→11→4→5→8→13):
  sum=48 — this path exists but is NOT a root-to-leaf path
```

**Q2. What is the naive approach to the root-to-leaf path sum problem, and what is its complexity?**
A: Recursively traverse the tree, carrying a running sum downward. At each node, subtract the node's value from the target (or add the node's value to a running total); when a leaf is reached, check whether the accumulated sum equals the target. This is O(n) time — every node is visited exactly once — and O(h) space for the recursion call stack (h = tree height; O(log n) balanced, O(n) worst case for a skewed tree).

```js
function hasPathSum(root, targetSum) {
  if (root === null) return false;

  // at a leaf: check if this node's value exactly completes the target
  if (root.left === null && root.right === null) {
    return root.val === targetSum;
  }

  // recurse, subtracting current node's value from the remaining target
  return hasPathSum(root.left, targetSum - root.val) ||
         hasPathSum(root.right, targetSum - root.val);
}
```

**Q3. Why must the leaf check be `root.left === null && root.right === null` rather than simply `root === null`?**
A: The problem requires the path to **end at a leaf** — a node with no children. If you check `root === null`, you'd incorrectly return `true` for a path that ends at a non-leaf internal node whose left or right child happens to be null (e.g., a node with only a right child — its missing left child is null, but the path ended at the parent, not at a true leaf). The two-condition check `root.left === null && root.right === null` ensures the terminating node genuinely has no children, correctly encoding the "end at a leaf" requirement.

```
Counterexample without the proper leaf check:

Tree:        targetSum = 5
    1
     \
      2       (2 is NOT a leaf — it has no children... wait, actually it IS a leaf)

Let's use a clearer counterexample:
    1
   / \
  2   3

targetSum = 1. Path "just the root" is NOT a valid root-to-LEAF path.
If you check `root === null` only, and root(1).left is not null and right is not null,
you'd recurse into left(2) with remaining=0, then check left(2)===null → false,
left(2).left===null → true? No, that's still reached via the leaf check.

Clearer bug: A node with ONE child. targetSum=1, tree: 1→left:2
  hasPathSum(root=1, 1):
    root != null. root.left(2) != null, so not a leaf.
    recurse left: hasPathSum(2, 0):
      root(2) != null. root(2).left=null, root(2).right=null → LEAF, return 2===0? false.
    recurse right: hasPathSum(null, 0): return false.
  Correctly returns false. ✓

Bug if we used `root === null` as termination AND checked remaining===0:
  hasPathSum(root=1, 1):
    root != null, remaining=1 → recurse
    hasPathSum(null, 0): return 0===0? TRUE ← WRONG.
    (This would incorrectly report a path through a null child as valid.)
```

**Q4. What is the "path sum II" variant (find all root-to-leaf paths with a given sum), and how does backtracking fit into the solution?**
A: Path Sum II asks you to collect every root-to-leaf path whose values sum to the target, not just check existence. The algorithm is the same DFS as the existence check, but instead of returning a boolean, you maintain a running `currentPath` list, add the current node on the way down, check the leaf condition and record the path if the sum matches, then **remove the current node on the way back up** (backtracking) before exploring the sibling subtree. Without backtracking, the `currentPath` list accumulates nodes from sibling subtrees that don't belong to the current path being explored.

```js
function pathSum(root, targetSum) {
  const result = [];

  function dfs(node, remaining, currentPath) {
    if (node === null) return;

    currentPath.push(node.val); // add node on the way DOWN

    if (node.left === null && node.right === null && remaining === node.val) {
      result.push([...currentPath]); // snapshot — don't push the live reference
    }

    dfs(node.left, remaining - node.val, currentPath);
    dfs(node.right, remaining - node.val, currentPath);

    currentPath.pop(); // remove node on the way BACK UP (backtrack)
  }

  dfs(root, targetSum, []);
  return result;
}
```

**Q5. Why must you push a snapshot (`[...currentPath]`) into `result`, rather than the `currentPath` reference itself?**
A: `currentPath` is a single shared list that is mutated throughout the entire DFS — nodes are pushed and popped as traversal proceeds. If you push the reference itself into `result`, every entry in `result` points to the same underlying array, which will have been emptied by the end of the DFS (all nodes backtracked out), leaving `result` as a collection of empty arrays. Spreading into a new array (`[...currentPath]`) or calling `.slice()` creates an independent copy of the path at that moment in time, capturing the correct values before backtracking removes them.

### Section 2: The Prefix Sum / HashMap Technique

**Q6. What is the "path sum III" variant, and why does the simple root-to-leaf DFS approach fail for it?**
A: Path Sum III asks: count the number of paths in the tree (not necessarily root-to-leaf, and not necessarily starting at the root) where the values along the path sum to a given target. The root-to-leaf DFS fails because it only searches paths that start at the root — any path that starts at an internal node or ends at a non-leaf is invisible to that approach. You'd need to restart the search from every possible starting node, giving a naive O(n²) solution (DFS from each of the n nodes). The efficient solution applies the **prefix sum + HashMap** technique.

**Q7. What is the prefix sum technique for trees, and what is its core insight?**
A: The core insight: during a root-to-node DFS, maintain the **cumulative sum from root to the current node**. If the current prefix sum is `S`, and some earlier prefix sum was `S - target`, then the path segment between that earlier node and the current node sums to exactly `target`. This is the exact same prefix sum insight used in the "subarray sum equals k" problem for arrays, adapted to trees by using the DFS call stack as the "array" of prefix sums encountered along the current root-to-node path.

A HashMap counts how many times each prefix sum has been seen so far along the current root-to-node path. At each node, look up `(currentSum - target)` in the map — each occurrence represents one valid path ending at the current node.

```
Prefix sum on a tree path (root to current node):
  root → A → B → C → (current)
  prefixSums: [0, root.val, root.val+A.val, root.val+A.val+B.val, ...]

If prefixSum[current] - prefixSum[i] = target
  → path from node (i+1) to current sums to target

The HashMap stores {prefixSum → count} for all nodes on the
current root-to-node path, seeded with {0: 1} to handle paths
that start at the root itself.
```

**Q8. Walk through the full prefix sum solution for Path Sum III, including why the HashMap must be updated before recursing and cleaned up after.**
A: The HashMap must reflect only the prefix sums along the **current root-to-node path** — not all nodes visited in the entire DFS. Because DFS backtracks up to a parent before exploring a sibling subtree, any prefix sums from one subtree must be removed before the sibling is explored (they'd otherwise appear as "earlier" prefix sums on paths that can't actually reach back into the first subtree). This is why the HashMap entry is decremented after both recursive calls complete — mirroring the `currentPath.pop()` backtracking in Path Sum II.

```js
function pathSumIII(root, targetSum) {
  const prefixCounts = new Map();
  prefixCounts.set(0, 1); // base case: one "empty" path with sum 0 (starts at root)

  function dfs(node, currentSum) {
    if (node === null) return 0;

    currentSum += node.val;

    // how many earlier prefix sums, when subtracted from currentSum, give targetSum?
    let count = prefixCounts.get(currentSum - targetSum) || 0;

    // record currentSum BEFORE recursing into children
    prefixCounts.set(currentSum, (prefixCounts.get(currentSum) || 0) + 1);

    count += dfs(node.left, currentSum);
    count += dfs(node.right, currentSum);

    // backtrack: remove currentSum from the map before returning to parent
    prefixCounts.set(currentSum, prefixCounts.get(currentSum) - 1);

    return count;
  }

  return dfs(root, 0);
}
```

**Q9. Why is the HashMap seeded with `{0: 1}` before DFS begins, and what does it represent?**
A: The seed `{0: 1}` represents a conceptual "empty prefix" — a path of length zero starting just before the root, with sum 0. Without it, paths that start at the root itself would be missed: if `currentSum` at some node equals `target` exactly, then `currentSum - target = 0`, and looking up `0` in the map would return `undefined` (or 0), failing to count this valid path. The `{0: 1}` seed ensures this lookup succeeds and contributes a count of 1, correctly capturing the "path from the root to this node" case. It plays the same role as prepending a 0 to the prefix sum array in the analogous "subarray sum equals k" linear-array problem.

**Q10. What is the time and space complexity of the prefix sum / HashMap approach compared to the naive O(n²) approach?**
A:

| Approach | Time | Space | Notes |
|---|---|---|---|
| Naive (DFS from every node) | O(n²) | O(h) | n starting nodes × O(n) DFS each |
| Prefix sum + HashMap | O(n) | O(n) | Each node visited once; HashMap ≤ h entries at any time during DFS, but up to n unique prefix sums overall |

The HashMap holds at most O(h) entries at any given moment during the DFS (only the prefix sums of the current root-to-node path are active), but in the worst case O(n) distinct prefix sums accumulate across the entire DFS (for a skewed tree where every node has a unique prefix sum). The time improvement from O(n²) to O(n) is substantial — for a tree with 10,000 nodes, that's the difference between ~10^8 and ~10^4 operations.

### Section 3: Maximum Path Sum — The Hardest Variant

**Q11. What makes the "maximum path sum" problem (any-node-to-any-node) fundamentally harder than root-to-leaf variants?**
A: In root-to-leaf problems, the path has a fixed direction: always downward from parent to child. This means the contribution of each subtree to a path is simple — you recurse into the subtree and carry the result upward, and the path either continues through a child or doesn't. In the maximum path sum problem (LeetCode 124), a path can go **upward through a parent and back down into a sibling subtree** — forming an inverted-U or "arch" shape that passes through any node as the "peak." This breaks the simple parent→child direction assumption and requires a split between what a subtree can **contribute to its parent** (must be a single-direction downward path) versus what constitutes the **best path entirely within the subtree** (can be the arch shape, which cannot extend further upward).

```
Tree:
    -10
    /  \
   9   20
      /  \
     15   7

Best path: 15 → 20 → 7, sum = 42.
This path's "peak" is 20. It can't be extended upward through -10
(that would require backtracking and going down 9 simultaneously,
which is not a valid path). The path terminates at 20 as the arch peak.
```

**Q12. How does the recursive solution for maximum path sum handle the "arch" vs. "single-direction contribution" distinction?**
A: Each recursive call serves a dual purpose:
1. **Updates the global maximum** with the best "arch" path that has `node` as its peak — this can include contributions from both left and right children simultaneously, forming the arch.
2. **Returns only the best single-direction downward path** from `node` to a descendant — because only a single-direction path can extend further upward to the parent without branching back down into a sibling.

Negative subtree contributions are clamped to 0 — including a subtree that sums to a negative value would decrease the path sum, so it's always better to not extend into it (equivalent to starting the path at the current node instead).

```js
function maxPathSum(root) {
  let globalMax = -Infinity;

  function dfs(node) {
    if (node === null) return 0;

    // clamp to 0: don't extend into a subtree that hurts the sum
    const leftGain = Math.max(0, dfs(node.left));
    const rightGain = Math.max(0, dfs(node.right));

    // best arch passing through this node (updates global answer)
    const archSum = node.val + leftGain + rightGain;
    globalMax = Math.max(globalMax, archSum);

    // return only single-direction contribution to parent
    return node.val + Math.max(leftGain, rightGain);
  }

  dfs(root);
  return globalMax;
}
```

**Q13. What happens when all node values in the tree are negative, and does the algorithm handle this correctly?**
A: When all values are negative, the maximum path sum is the largest (least-negative) single node value — a path of just one node, with no extensions into children. The algorithm handles this correctly because:
- `leftGain` and `rightGain` are clamped to `Math.max(0, ...)`, so both evaluate to 0 for negative children.
- `archSum = node.val + 0 + 0 = node.val`.
- `globalMax` is initialized to `-Infinity`, so even a single very negative value will correctly update it.
- The recursion correctly finds the largest single value across all nodes.

The common mistake is initializing `globalMax = 0` instead of `-Infinity` — this causes the algorithm to return 0 for an all-negative tree (as if an empty path were allowed), which is incorrect.

**Q14. A subtlety: why is it wrong to return `node.val + leftGain + rightGain` (the arch sum) to the parent instead of `node.val + Math.max(leftGain, rightGain)` (single direction)?**
A: If you return the arch sum to the parent, the parent would treat the full arch (going left AND right from the child) as a single segment that can be further extended upward or combined with the parent's other subtree. But the arch is a **branching path** — it goes in two directions simultaneously from its peak. A valid path cannot branch; it must be a contiguous sequence of edges with no splits. Returning the arch to the parent would allow the algorithm to construct an invalid "forked" path that splits at two different nodes, overcounting the sum. The single-direction return enforces the no-branching invariant: the parent can extend the path in one more direction (upward to its own parent or into its other child), but cannot attach both of the current node's arms as a single chain.

### Section 4: Path Sum with Diameter and Coordinate Variations

**Q15. How is the "diameter of a binary tree" problem structurally identical to maximum path sum, and what is the shared algorithmic pattern?**
A: The diameter problem (find the longest path between any two nodes, measured in number of edges) uses the exact same "dual purpose" DFS pattern as maximum path sum:
1. Each recursive call **updates a global maximum** with the "arch" through the current node — in this case, `leftDepth + rightDepth` edges (the path going through the current node from its deepest left descendant to its deepest right descendant).
2. Each recursive call **returns only single-direction depth** to its parent — `1 + max(leftDepth, rightDepth)` — so the parent can correctly compute its own arch.

The global maximum for diameter is in edge count (or node count minus 1) rather than sum of values, but the recursive structure is identical. Recognizing this structural identity — "any-node-to-any-node through a peak" — and applying the same arch/single-direction split immediately gives the correct algorithm for both problems.

```js
function diameterOfBinaryTree(root) {
  let globalMax = 0;

  function dfs(node) {
    if (node === null) return 0;
    const left = dfs(node.left);
    const right = dfs(node.right);
    globalMax = Math.max(globalMax, left + right); // arch through this node
    return 1 + Math.max(left, right);              // single-direction to parent
  }

  dfs(root);
  return globalMax;
}
```

**Q16. How would you find the maximum path sum in a binary tree where the path must include at least K nodes?**
A: This is a constrained variant that complicates the clean `max(0, childGain)` clamping — you can't freely discard subtrees if you need to include a minimum number of nodes. Approach: carry `k` as a constraint; at each node, the DFS returns `(maxSum, length)` pairs for the best downward path, and only clamps to "don't extend" if the path already meets the length requirement. For the arch, combine left and right paths as long as their combined length is ≥ k. This variant is significantly more complex and typically falls outside standard interview scope — worth flagging the constraint explicitly and asking if k=1 (simplifying back to the standard problem) or k=2 (must include at least one child) for clarification.

**Q17. How does the prefix sum approach extend to graphs (not trees), and what additional concern arises?**
A: In a tree, there is exactly one path between any two nodes, and the DFS naturally explores each root-to-node path without revisiting nodes. In a general graph, there can be multiple paths between nodes, and cycles exist — the "prefix sum on the current path" idea still applies, but you need an explicit `visited` set to avoid counting the same node twice in a single path. The DFS proceeds similarly: maintain a `visited` set, track prefix sums along the current DFS path, query and update the HashMap at each step, and backtrack both the `visited` set and the HashMap when unwinding. This is substantially more complex than the tree version and isn't a standard interview problem — it comes up in competitive programming contexts.

### Section 5: Scenario / Interview-Style Questions

**Q18. "Walk me through how you'd approach a path sum problem you haven't seen before."**
A: My first step is always to clarify the **path definition**: does it have to start at the root? End at a leaf? Or can it start and end anywhere? This single question determines which of the three main algorithms applies — root-to-leaf DFS (simplest), prefix sum + HashMap (for any-node-to-any-node count), or the arch DFS (for any-node-to-any-node maximum). Second, I clarify whether values can be **negative** — negative values mean I can't assume "longer paths always have larger sums" and can't prune subtrees early. Third, whether to return a **boolean, count, or the actual paths** — existence uses early-exit DFS, counting uses prefix sums, collecting paths uses backtracking. With these three questions answered, the algorithm falls out almost mechanically.

**Q19. "Your prefix sum approach uses a HashMap. Can you implement it without one?"**
A: Yes — the naive O(n²) approach: at every node, run a separate DFS that counts paths starting from that node, then sum across all nodes as the "outer" traversal visits them. This avoids the HashMap entirely at the cost of O(n²) time.

```js
function pathSumNaive(root, target) {
  if (!root) return 0;

  function countFrom(node, remaining) {
    if (node === null) return 0;
    const hit = node.val === remaining ? 1 : 0;
    return hit +
           countFrom(node.left, remaining - node.val) +
           countFrom(node.right, remaining - node.val);
  }

  // count paths starting AT this node + paths starting in each subtree
  return countFrom(root, target) +
         pathSumNaive(root.left, target) +
         pathSumNaive(root.right, target);
}
```

The trade-off: O(n²) time (acceptable for n ≤ 1000) versus the O(n) HashMap approach. I'd choose the naive version if the interviewer asks to avoid extra data structures, or as a starting point before optimizing to the HashMap approach.

**Q20. "There are negative numbers in the tree. Does your solution still work?"**
A: For **root-to-leaf path sum** (existence or collection): yes — the DFS carries the remaining target downward, subtracting each node's value; negative values simply increase the remaining target rather than decreasing it, and the logic is identical. For **prefix sum / Path Sum III**: yes — the HashMap approach makes no assumptions about sign; it correctly handles negative prefix sums and negative targets. For **maximum path sum**: yes — the `Math.max(0, childGain)` clamping is specifically designed for negative values; a negative child gain is clamped to 0 (don't extend into that subtree), and `globalMax` is initialized to `-Infinity` (not 0) to correctly handle all-negative trees. The one pitfall to call out explicitly: initializing `globalMax = 0` breaks the all-negative case — this is a very common bug worth flagging proactively.

**Q21. "How would you verify your path sum implementation beyond the basic happy path?"**
A: Key test cases:

- **All negative values**: for maximum path sum, confirms `globalMax` is initialized to `-Infinity`, not 0.
- **Single-node tree**: every variant should return a result based on that node's value alone — no null-pointer errors, and the leaf check or arch computation degenerates correctly.
- **Null root**: should return `false`/`0`/`-Infinity` appropriately depending on the variant, without crashing.
- **Target equals 0 with positive and negative values that cancel**: confirms the prefix sum HashMap correctly counts paths where `currentSum - target = currentSum - 0 = currentSum`, which must map to an earlier occurrence of `currentSum` in the map — a subtle case where the `{0: 1}` seed matters.
- **Path passes through the root (any-to-any variant)**: confirms the arch computation correctly uses both left and right children simultaneously at the root.
- **Left-skewed or right-skewed tree with a matching path**: confirms the single-direction code path (where one of `leftGain`/`rightGain` is always 0) works correctly without relying on the balanced-tree "both children non-null" assumption.
- **Duplicate paths with same sum**: for Path Sum II (collect all paths), confirms that separate paths producing the same numerical sum are both collected (not deduplicated).

## Problem 1 — Path Sum (Root-to-Leaf Existence Check)

### Problem
Given the root of a binary tree and an integer `targetSum`, return `true` if the tree has a root-to-leaf path such that adding up all node values along the path equals `targetSum`.

```
Input: targetSum = 22
       5
      / \
     4   8
    /   / \
   11  13  4
  /  \      \
 7    2       1

Output: true (path 5→4→11→2 = 22)
```

### Pattern Recognition
Root-to-leaf DFS with a decreasing remainder — carry the remaining target downward, checking for exact match only at leaves.

### Key Insight
By subtracting each node's value from the target as you descend, the problem at each node reduces to: "does any root-to-leaf path in MY subtree sum to `remaining`?" When you reach a leaf, the question becomes simply "is this leaf's value exactly `remaining`?" — a single comparison.

### Approach
Base case: null node → `false`. Leaf node → check if `node.val === targetSum`. Recursive case: recurse left and right with `targetSum - node.val`; return `true` if either subtree finds a matching path.

### Solution

```js
function hasPathSum(root, targetSum) {
  // null node: no path possible
  if (root === null) return false;

  // leaf node: path ends here — check if this node exactly uses up the remainder
  if (root.left === null && root.right === null) {
    return root.val === targetSum;
  }

  // recurse: subtract current node's value, search both subtrees
  const remaining = targetSum - root.val;
  return hasPathSum(root.left, remaining) || hasPathSum(root.right, remaining);
}
```

### Dry Run

```
Tree (partial, relevant branch):
       5
      /
     4
    /
   11
  /  \
 7    2
targetSum = 22

hasPathSum(5, 22):
  not null, not leaf (has children)
  remaining = 22 - 5 = 17
  try left: hasPathSum(4, 17):
    not leaf
    remaining = 17 - 4 = 13
    try left: hasPathSum(11, 13):
      not leaf
      remaining = 13 - 11 = 2
      try left: hasPathSum(7, 2):
        LEAF. 7 === 2? NO → false
      try right: hasPathSum(2, 2):
        LEAF. 2 === 2? YES → true ← ✓
      returns true (short-circuits left result)
    returns true
  returns true

Result: true ✓ (path 5→4→11→2 sums to 22)
```

### Complexity
- Time: O(n) — every node visited at most once. Short-circuit (`||`) provides early termination once a matching path is found, but worst case visits all nodes (no matching path exists).
- Space: O(h) — recursion call stack. O(log n) for balanced, O(n) for skewed.

### Edge Cases
- Null root: returns `false` immediately. ✓
- Single-node tree: the node is both root and leaf; returns `node.val === targetSum`. ✓
- Target equals 0 with a leaf whose value is 0: correctly returns `true` (0 === 0). ✓
- All negative values with a matching path: subtraction correctly drives the remainder through negative values; leaf check works identically. ✓
- Node with only one child: `root.left === null && root.right === null` is false (one child exists), so we correctly do NOT treat this as a leaf and continue recursing into the existing child. ✓

### Follow-up Questions
- "What if you need to return all matching paths, not just check existence?" → See Problem 2 — backtracking replaces the boolean return.
- "What if the path doesn't have to start at the root or end at a leaf?" → See Problem 3 — prefix sum + HashMap.

## Problem 2 — Path Sum II (Collect All Root-to-Leaf Paths)

### Problem
Given the root of a binary tree and an integer `targetSum`, return all root-to-leaf paths where the sum of node values in the path equals `targetSum`. Each path should be returned as a list of node values.

```
Input: targetSum = 22
       5
      / \
     4   8
    /   / \
   11  13  4
  /  \    / \
 7    2  5   1

Output: [[5,4,11,2], [5,8,4,5]]
```

### Pattern Recognition
DFS with explicit path tracking and backtracking — maintain a mutable path list; add on the way down, snapshot on success, remove on the way back up.

### Key Insight
A single shared mutable list tracks the current path. The **backtracking step** (`.pop()`) is what makes the shared list correctly represent "the path from root to the current node" at every point during the DFS — without it, nodes from completed branches pollute the path being built for sibling branches.

### Approach
Carry a `currentPath` list into the DFS. At each node, push the current value. At a matching leaf, push a copy (snapshot) of `currentPath` into results. After recursing into both children, pop the current value (backtrack). This produces every root-to-leaf path whose sum equals target.

### Solution

```js
function pathSum(root, targetSum) {
  const result = [];

  function dfs(node, remaining, currentPath) {
    if (node === null) return;

    currentPath.push(node.val); // add this node to the current path

    if (node.left === null && node.right === null && remaining === node.val) {
      // found a valid path — snapshot the current path (not a reference!)
      result.push([...currentPath]);
    }

    dfs(node.left, remaining - node.val, currentPath);
    dfs(node.right, remaining - node.val, currentPath);

    currentPath.pop(); // backtrack: remove this node before returning to parent
  }

  dfs(root, targetSum, []);
  return result;
}
```

### Dry Run

```
targetSum = 22, Tree:
       5
      / \
     4   8
    /   / \
   11  13  4
```

## Problem 3 — Path Sum III (Any-Start Any-End Count, Prefix Sum)

### Problem
Given the root of a binary tree and an integer `targetSum`, return the number of paths where the sum of the values along the path equals `targetSum`. The path does not need to start or end at the root or a leaf, but must go downward (from parent to child nodes only).

```
Input: targetSum = 8
       10
      /  \
     5   -3
    / \    \
   3   2   11
  / \   \
 3  -2   1

Output: 3
(paths: 5→3, 5→2→1, -3→11)
```

### Pattern Recognition
Prefix sum + HashMap — translate the "subarray sum equals k" technique from arrays to trees, using the DFS path as the analogue of the linear array.

### Key Insight
As you DFS from root to a node, the cumulative sum `currentSum` forms a prefix sum. Any path ending at the current node and summing to `target` corresponds to an earlier node on the same root-to-current path whose prefix sum equals `currentSum - target`. The HashMap counts how many times each prefix sum has appeared on the current root-to-node path — enabling O(1) lookup per node instead of O(n) re-traversal.

### Approach
Seed the HashMap with `{0: 1}`. At each node, compute `currentSum`. Look up `currentSum - targetSum` in the map — add the count to the answer. Insert `currentSum` into the map. Recurse left and right. After both children return, decrement `currentSum`'s count in the map (backtrack). Return the accumulated count.

### Solution

```js
function pathSum(root, targetSum) {
  const prefixCounts = new Map();
  prefixCounts.set(0, 1); // seed: one empty path with sum 0

  function dfs(node, currentSum) {
    if (node === null) return 0;

    currentSum += node.val;

    // how many prefix sums on the current path equal (currentSum - targetSum)?
    // each such prefix sum corresponds to one valid path ending here
    let count = prefixCounts.get(currentSum - targetSum) || 0;

    // add currentSum to the map BEFORE recursing (it's now on the path)
    prefixCounts.set(currentSum, (prefixCounts.get(currentSum) || 0) + 1);

    count += dfs(node.left, currentSum);
    count += dfs(node.right, currentSum);

    // backtrack: remove currentSum from the map (no longer on the active path)
    prefixCounts.set(currentSum, prefixCounts.get(currentSum) - 1);

    return count;
  }

  return dfs(root, 0);
}
```

## Problem 4 — Maximum Path Sum (Any Node to Any Node)

### Problem
A **path** in a binary tree is a sequence of nodes where each pair of adjacent nodes has an edge, and each node appears at most once. The path does not need to pass through the root. Given the root of a binary tree, return the **maximum sum** of any path.

```
Input:
    -10
    /  \
   9   20
      /  \
     15   7

Output: 42 (path 15 → 20 → 7)
```

### Pattern Recognition
Arch DFS — dual-purpose recursive function: update a global maximum with the arch (both children) at each node, but return only the single-direction contribution (one child) to the parent.

### Key Insight
Every path has a unique "peak" — the highest node through which it passes. At the peak, the path can include contributions from both left and right subtrees (forming an arch). Above the peak, the path can't branch in two directions simultaneously. The algorithm processes each node as the potential peak of the globally optimal path, while returning only the single-direction value that the parent can safely extend.

### Approach
Recurse into both children, clamping their contributions to 0 if negative (don't extend into loss-making subtrees). Compute `archSum = node.val + leftGain + rightGain` and update the global maximum. Return `node.val + max(leftGain, rightGain)` — the best single-direction extension for the parent to use.

### Solution

```js
function maxPathSum(root) {
  let globalMax = -Infinity; // must be -Infinity, not 0, for all-negative trees

  function dfs(node) {
    if (node === null) return 0;

    // clamp negative contributions to 0 — never extend into a losing subtree
    const leftGain = Math.max(0, dfs(node.left));
    const rightGain = Math.max(0, dfs(node.right));

    // treat this node as the peak: arch sums both children
    const archSum = node.val + leftGain + rightGain;
    globalMax = Math.max(globalMax, archSum);

    // return single-direction contribution: parent can extend in one direction only
    return node.val + Math.max(leftGain, rightGain);
  }

  dfs(root);
  return globalMax;
}
```

```
      /  \

  dfs(9):

    leftGain=0, rightGain=0

    return 9+max(0,0) = 9

  dfs(20):
    dfs(15):
      dfs(null)=0, dfs(null)=0

```

### Complexity
- Time: O(n) — every node visited exactly once.
- Space: O(h) — recursion call stack. O(log n) balanced, O(n) skewed.

### Edge Cases
- All negative values: `globalMax = -Infinity` ensures the least-negative single node is correctly returned. Clamping to 0 still prevents extension into worse subtrees — at each node, the arch is just `node.val + 0 + 0 = node.val`. ✓
- Single-node tree: `leftGain = rightGain = 0`; `archSum = node.val`; `globalMax = node.val`. ✓
- Null root: the problem typically guarantees a non-null root, but `dfs(null) = 0` and `globalMax = -Infinity` still handles it gracefully. ✓
- Long path through the root (root IS the peak): the root's `archSum` correctly combines both subtree gains. ✓
- A very negative root connecting two large positive subtrees: the arch through the root includes root's negative value — if the arch sum is still positive, it's correctly compared to individual subtree maxima. ✓

### Follow-up Questions
- "What if you need to return the actual path, not just the sum?" → Track the path alongside the max sum; at each node that updates `globalMax`, record the full path by reconstructing it from the left/right gains. This is significantly more complex — worth flagging the overhead.
- "How does this relate to the diameter problem?" → Structurally identical — see Q15. The "arch" pattern (dual-purpose DFS: update global with both children, return single direction to parent) is the unifying template.

## Problem 5 — Sum Root to Leaf Numbers

### Problem
You are given a binary tree where each node contains a single digit (0–9). Each root-to-leaf path represents a number (e.g., root→1, left→2, leaf→3 represents 123). Return the **total sum** of all root-to-leaf numbers.

```
Input:
    1
   / \
  2   3

Paths: 12, 13. Output: 25.

Input:
    4
   / \
  9   0
 / \
5   1

Paths: 495, 491, 40. Output: 1026.
```

### Pattern Recognition
Root-to-leaf DFS carrying a running number — the "path sum" technique generalized: instead of accumulating a sum, accumulate a decimal number by `runningNum = runningNum * 10 + node.val`.

### Key Insight
Building a number digit-by-digit as you descend (multiplying by 10 and adding the new digit) is structurally identical to carrying a running sum — the DFS structure is unchanged, only the accumulation formula differs. At each leaf, the running number is a complete number representing that root-to-leaf path; add it to the total.

### Approach
DFS carrying `currentNum` (initialized to 0). At each node, update `currentNum = currentNum * 10 + node.val`. At a leaf, add `currentNum` to the result. Recurse into both children. Return the accumulated sum.

### Solution

```js
function sumNumbers(root) {
  function dfs(node, currentNum) {
    if (node === null) return 0;

    currentNum = currentNum * 10 + node.val; // build number digit by digit

    // at a leaf: this node contributes a complete number
    if (node.left === null && node.right === null) {
      return currentNum;
    }

    // recurse: sum contributions from both subtrees
    return dfs(node.left, currentNum) + dfs(node.right, currentNum);
  }

  return dfs(root, 0);
}
```

```
  currentNum = 0*10+4 = 4
  not leaf → recurse

  dfs(9, 4):
    currentNum = 4*10+9 = 49
    not leaf → recurse

    dfs(5, 49):
      currentNum = 49*10+5 = 495
      LEAF → return 495

    dfs(1, 49):
      currentNum = 49*10+1 = 491
      LEAF → return 491

    return 495 + 491 = 986

  dfs(0, 4):
    currentNum = 4*10+0 = 40
    LEAF → return 40

  return 986 + 40 = 1026

Result: 1026 ✓
```

### Complexity
- Time: O(n) — each node visited once.
- Space: O(h) — recursion call stack. No explicit path list needed since `currentNum` encodes the path as an integer.

### Edge Cases
- Node with value 0 in the middle of a path: correctly multiplied into the running number (e.g., `49 * 10 + 0 = 490`). ✓
- Very deep tree: numbers grow as `10^h`, potentially overflowing a 32-bit integer for h > 9. Use 64-bit integers or BigInt for deep trees; worth flagging this assumption explicitly in an interview. ✓
- Single-node tree: `currentNum = node.val`, LEAF condition immediately returns `node.val`. ✓

### Follow-up Questions
- "What if paths can have more than one digit per node?" → The problem would need to clarify the encoding — the same `runningNum * base + node.val` approach generalizes to any base, or you'd need to shift by the number of digits in `node.val` if nodes store multi-digit values.
- "How would you reconstruct the actual numbers (not just their sum)?" → Carry the current number and record it at each leaf — identical to the backtracking approach in Path Sum II, but pushing the number instead of a path copy.

```
Path sum problem — which algorithm applies?
│
├── PATH DEFINITION: root-to-leaf (must start at root, end at leaf)?
│   │
│   ├── EXISTENCE only (boolean): does any path sum to target?
│   │   └── Root-to-leaf DFS with decreasing remainder
│   │         if (leaf && node.val === remaining) return true
│   │         → O(n) time, O(h) space
│   │
│   ├── COLLECT all matching paths (list of lists)?
│   │   └── Root-to-leaf DFS + backtracking
│   │         push on descend, snapshot at matching leaf, pop on ascend
│   │         → O(n) time, O(n×h) space for results
│   │
│   └── SUM ROOT-TO-LEAF NUMBERS (path as decimal digits)?
│       └── Root-to-leaf DFS, carry runningNum = runningNum*10 + node.val
│             return runningNum at leaf, sum across subtrees
│             → O(n) time, O(h) space
│
├── PATH DEFINITION: any node to any node, downward only (no upward edges)?
│   │
│   ├── COUNT paths summing to target?
│   │   └── Prefix sum + HashMap (DFS, seed {0:1}, backtrack map entries)
│   │         → O(n) time, O(n) space
│   │
│   └── COUNT paths — but okay with O(n²)?
│       └── Naive: for each node, DFS counting paths starting there
│             countFrom(node) + pathSum(left) + pathSum(right)
│             → O(n²) time, O(h) space
│
├── PATH DEFINITION: any node to any node, any direction (can form arch)?
│   │
│   ├── MAXIMUM sum path?
│   │   └── Arch DFS — dual purpose:
│   │         update globalMax with (node.val + leftGain + rightGain)
│   │         return to parent: node.val + max(leftGain, rightGain)

│   │         globalMax initialized to -Infinity (NOT 0)
│   │         → O(n) time, O(h) space
│   │
│   └── LONGEST path (diameter, by edge count)?
│       └── Same arch DFS structure as maximum sum:
│             update globalMax with leftDepth + rightDepth
│             return to parent: 1 + max(leftDepth, rightDepth)
│             → O(n) time, O(h) space
│
└── NEED TO HANDLE VERY DEEP TREES (risk of stack overflow)?

          → Same asymptotic complexity, O(h) heap stack instead of call stack
```

## Common Bugs Checklist

Before submitting any path sum solution, verify:

1. **Leaf check uses `node.left === null && node.right === null`, NOT just `node === null`?** — A node with exactly one child is not a leaf; returning a result there would count paths that end prematurely at a non-leaf, silently producing wrong answers for trees with nodes having a single child.

2. **Backtracking `.pop()` (Path Sum II) is always called after BOTH recursive calls, not conditionally?** — If pop is inside an `if` block or only called on success, sibling subtrees inherit stale path entries from their sibling's traversal, corrupting all subsequently collected paths.

3. **Snapshot with `[...currentPath]` (or `.slice()`), NOT a direct reference push?** — Pushing the live `currentPath` reference puts the same array into every result slot; all entries will be empty at DFS completion since backtracking has removed everything. This is the single most common bug in Path Sum II.

4. **HashMap seeded with `{0: 1}` BEFORE starting DFS (Path Sum III)?** — Without this seed, paths that start at the root (where `currentSum === targetSum`) are completely missed, since `prefixCounts.get(0)` returns `undefined` instead of 1.

5. **HashMap entry decremented AFTER both recursive calls return (Path Sum III)?** — Decrementing before recursing removes the current node's prefix sum while its subtree is still being explored; decrementing only on one side leaves the entry active for the sibling's traversal. Both errors cause prefix sums from one part of the tree to be visible when processing an unrelated part, causing overcounting.

6. **`globalMax` initialized to `-Infinity`, NOT `0` (maximum path sum)?** — Initializing to 0 causes the algorithm to return 0 for all-negative trees (as if an empty path with sum 0 were valid), which is incorrect. The maximum path sum in an all-negative tree is the single least-negative node value.

7. **Arch returns single-direction to parent: `node.val + max(leftGain, rightGain)`, NOT `node.val + leftGain + rightGain`?** — Returning the arch sum to the parent allows the parent to build a "forked" path that branches at two different nodes simultaneously, which is not a valid path. Only one direction can be passed upward.

8. **Negative child gains clamped to 0 before computing the arch (maximum path sum)?** — Including a negative-gain subtree in the arch would reduce the path sum; clamping ensures the arch computation always reflects the best possible path through the current node without being dragged down by losing subtrees. Forgetting this clamp produces wrong results for any tree with negative node values.

9. **`Sum Root to Leaf Numbers`: running number overflow for deep trees?** — A tree of depth 20 produces numbers up to 10^20, exceeding a 64-bit integer. For very deep trees, use `BigInt` in JavaScript or an equivalent large-integer type, or ask the interviewer whether overflow is a concern.

10. **All variants: single-node tree and null root tested?** — The null root case (`root === null`) must be handled before accessing `root.val` or `root.left`. The single-node tree (root is a leaf) must not fall through to recursive calls; the leaf check must fire correctly for a root with no children.

---

**Final Tip:** At the 5–7 YOE level, the key signal is recognizing **which of the three path definitions** applies before writing a single line of code — root-to-leaf, downward-from-anywhere, or any-direction. Then mapping that directly to the right algorithmic pattern: backtracking DFS for collection, prefix sum + HashMap for counting anywhere-paths in O(n), and the arch/dual-purpose DFS for any-direction extrema. The strongest candidates also immediately call out the `globalMax = -Infinity` initialization, the `{0: 1}` HashMap seed, and the single-direction return constraint as non-obvious correctness invariants — rather than arriving at them through trial and error when edge cases fail.
