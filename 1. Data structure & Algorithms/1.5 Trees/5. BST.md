# DSA: Binary Search Trees — Insert, Delete, Search & Validate — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the defining property of a Binary Search Tree (BST), and what does it guarantee about traversal order?**
A: A BST is a binary tree where, for **every** node, all values in its left subtree are less than the node's own value, and all values in its right subtree are greater (assuming no duplicates, a common simplifying convention). This property holds **recursively at every node**, not just between a node and its immediate children — a critical distinction explored further in Section 4. A direct consequence: an **in-order traversal** of a BST always visits nodes in strictly ascending sorted order, since in-order traversal (left, then node, then right) naturally respects the BST's left-smaller/right-larger structure at every level.

```
        8
       / \
      3   10
     / \    \
    1   6    14
       / \   /
      4   7 13

In-order traversal: 1, 3, 4, 6, 7, 8, 10, 13, 14  (always sorted, by the BST property)
```

**Q2. How does the BST property enable O(h) search, insertion, and deletion, where h is the tree's height?**
A: At every node during a search (or during insertion/deletion's initial "find the right spot" phase), comparing the target value against the current node's value immediately tells you which single subtree (left or right) could possibly contain it — there's no need to search both sides, unlike a general (non-BST) binary tree. This means each step moves you one level down a single path, so the total work is bounded by the tree's height, not its total node count — O(h), which is O(log n) for a balanced BST, but degrades to O(n) for a completely unbalanced (linked-list-shaped) BST.

**Q3. What is the standard recursive search algorithm for a BST?**
A: Compare the target value to the current node; if equal, found; if smaller, recurse into the left subtree; if larger, recurse into the right subtree; if you reach a `null` node, the value isn't present.

```js
function search(root, target) {
  if (root === null || root.val === target) return root;

  if (target < root.val) return search(root.left, target);
  return search(root.right, target);
}
```

Time: O(h). Space: O(h) for the recursive call stack (or O(1) if written iteratively, since BST search doesn't need to backtrack or explore multiple branches).

### Section 2: Insertion

**Q4. What is the standard algorithm for inserting a new value into a BST, and where does the new node always end up?**
A: Walk down from the root using the same comparison logic as search, but instead of stopping at a `null` node with "not found," **insert the new node exactly at that null position**. A newly inserted value always becomes a **leaf** in the resulting tree (a new node never gets inserted in the middle of the tree, displacing existing nodes) — the search naturally terminates at the first empty spot consistent with the BST property, and that's precisely where the new value belongs.

```js
function insert(root, val) {
  if (root === null) return { val, left: null, right: null };

  if (val < root.val) {
    root.left = insert(root.left, val);
  } else if (val > root.val) {
    root.right = insert(root.right, val);
  }
  // if val === root.val, typically a no-op (standard BSTs assume unique values)

  return root;
}
```

Time: O(h). Space: O(h) for the recursive call stack.

**Q5. Why does the recursive insertion function need to return the (possibly newly-created) node at each level, rather than just navigating and mutating in place?**
A: The return-and-reassign pattern (`root.left = insert(root.left, val)`) is what correctly **attaches** a newly created node into the tree — when the recursion reaches a `null` spot and creates a new node object, that new object needs to be connected to its parent's `left` or `right` pointer; simply returning from a `null` base case without the parent reassigning its child pointer would leave the new node created but disconnected from the tree entirely. This pattern (return the node, let the caller reassign its own child pointer) is a common and important idiom across recursive tree-modification functions, not unique to BST insertion.

**Q6. How would you implement BST insertion iteratively instead of recursively?**
A: Walk down from the root using an explicit loop, tracking the current node's **parent** as you go (since you need a reference to the parent in order to attach the new node once you reach the correct `null` spot) — once the loop finds where the null spot would be, directly set the parent's `left` or `right` pointer to the newly created node.

```js
function insertIterative(root, val) {
  const newNode = { val, left: null, right: null };
  if (root === null) return newNode;

  let current = root;
  while (true) {
    if (val < current.val) {
      if (current.left === null) {
        current.left = newNode;
        break;
      }
      current = current.left;
    } else if (val > current.val) {
      if (current.right === null) {
        current.right = newNode;
        break;
      }
      current = current.right;
    } else {
      break; // duplicate value, no-op per standard convention
    }
  }

  return root;
}
```

### Section 3: Deletion

**Q7. What are the three distinct cases that must be handled when deleting a node from a BST, and why does deletion require more careful casework than insertion?**
A: Insertion always adds a new leaf, which is a single, simple case. Deletion, by contrast, must remove an **existing** node that could be anywhere in the tree's structure, with three fundamentally different situations depending on how many children it has:
1. **Leaf node (no children)**: simply remove it — no restructuring needed beyond clearing the parent's reference to it.
2. **One child**: replace the node with its single child directly — the child "takes the place of" its removed parent.
3. **Two children**: the hardest case — the node can't simply be removed or replaced by a single child without breaking the BST property, so instead its value is replaced by its **in-order successor** (or equivalently, its in-order predecessor), and that successor/predecessor node is then recursively deleted from its own (simpler) position.

```
Case 1 (leaf):           Case 2 (one child):        Case 3 (two children):
    5                         5                            5
   / \        delete 3       / \      delete 3            / \      delete 5
  3   8    →     8          3   8   →    8               3   8   →  6   8
                              \                \           / \    /
                               4                4         2   7  ...(6 replaces 5,
                                                                    then 6 itself
                                                                    is removed from
                                                                    its original spot)
```

**Q8. Why must the two-children case use the in-order SUCCESSOR (or predecessor), specifically, rather than just picking any arbitrary descendant to replace the deleted node's value?**
A: The in-order successor (the smallest value in the node's right subtree) or in-order predecessor (the largest value in the node's left subtree) is specifically guaranteed to be a value that can validly take the deleted node's place **without violating the BST property anywhere in the tree** — the successor is larger than everything in the deleted node's left subtree (since it's still within the deleted node's own right subtree, and the BST property already guarantees the right subtree is entirely larger than the left) and smaller than everything else remaining in the right subtree (by definition of "smallest in the right subtree"). Picking an arbitrary, non-successor/predecessor value could easily violate this ordering somewhere else in the tree.

**Q9. How do you find the in-order successor of a node that HAS a right subtree, and why is this specific sub-procedure simple (O(h) with no further complex casework)?**
A: The in-order successor of a node with a right subtree is simply the **leftmost node of that right subtree** (keep going left as far as possible, starting from the right child) — this is guaranteed to be the smallest value greater than the current node's value. Finding the leftmost node of any subtree is a simple, single-direction walk (no comparisons or branching needed, just "keep going left until you can't anymore"), making this sub-procedure a clean O(h) operation with none of the case-based complexity of the deletion problem as a whole.

```js
function findMin(node) {
  while (node.left !== null) {
    node = node.left;
  }
  return node;
}
```

**Q10. Write out the full recursive BST deletion algorithm, combining all three cases.**
A:

```js
function deleteNode(root, key) {
  if (root === null) return null;

  if (key < root.val) {
    root.left = deleteNode(root.left, key);
  } else if (key > root.val) {
    root.right = deleteNode(root.right, key);
  } else {
    // found the node to delete
    if (root.left === null) return root.right;  // 0 or 1 child (right side)
    if (root.right === null) return root.left;  // 1 child (left side)

    // two children: replace value with in-order successor, then delete successor
    const successor = findMin(root.right);
    root.val = successor.val;
    root.right = deleteNode(root.right, successor.val);
  }

  return root;
}
```

**Q11. Why do the checks `if (root.left === null) return root.right;` and `if (root.right === null) return root.left;` correctly handle BOTH the leaf case AND the one-child case together, without needing a separate explicit leaf check?**
A: If a node is a leaf, both `root.left` and `root.right` are `null` — the first check (`root.left === null`) triggers and returns `root.right`, which is simply `null` (correctly removing the leaf entirely, replacing it with "nothing"). If the node has exactly one child (say, only a right child), the same check correctly returns that one existing child, replacing the deleted node with it. This elegant unification means the leaf case doesn't need its own separate branch — it naturally falls out of the "0 or 1 child on this side" check already needed for the one-child case.

**Q12. What is the time and space complexity of BST deletion?**
A: Time: O(h) for the two-children case's `findMin` call (an additional O(h) walk down the right subtree), combined with the O(h) initial search to locate the node to delete in the first place — both bounded by the tree's height, so overall still O(h), not O(h²) or worse (since these are two separate, sequential O(h) walks, not nested). Space: O(h) for the recursive call stack.

### Section 4: Validating a BST

**Q13. What is the SUBTLE BUG in a naive BST validation approach that only checks each node against its IMMEDIATE children, and why does this fail to catch all invalid BSTs?**
A: A naive check like "for every node, is `node.left.val < node.val` and `node.right.val > node.val`?" only verifies the BST property **locally**, between a node and its direct children — but the BST property must hold **globally**, for every node relative to its entire left or right subtree, not just its immediate children. A tree can satisfy the local, immediate-children check at every single node while still being an invalid BST overall, if a deeper descendant violates the ordering relative to a more distant ancestor.

```
        5
       / \
      3   8
         / \
        6   9

Local check passes at every node: 3<5, 8>5, 6<8, 9>8 — all locally consistent!
But this is NOT a valid BST: node 6 is in node 5's RIGHT subtree, yet 6 > 5 is fine...
wait let's use a genuinely broken example:

        5
       / \
      3   8
         / \
        4   9

Local check: 3<5 ✓, 8>5 ✓, 4<8 ✓, 9>8 ✓ — every immediate parent-child check passes!
But node 4 is in node 5's RIGHT subtree, and 4 < 5 — this VIOLATES the BST property,
since everything in 5's right subtree must be greater than 5. The naive check misses
this because it only ever compares a node to its DIRECT parent/children, never to
more distant ancestors like the original root (5) that a deep descendant must still respect.
```

**Q14. What is the correct approach to validating a BST, using propagated MIN/MAX bounds?**
A: Recursively validate each node against a **valid range** (a lower and upper bound) that gets progressively narrowed as you descend — the root starts with an unbounded range (`-Infinity` to `Infinity`), and each recursive call into a left child narrows the **upper bound** to the current node's value (everything in the left subtree must be less than it), while each call into a right child narrows the **lower bound** to the current node's value (everything in the right subtree must be greater than it). This correctly enforces the property globally, since the bounds accumulate and tighten with every level of descent, carrying forward constraints from ALL ancestors, not just the immediate parent.

```js
function isValidBST(root, lower = -Infinity, upper = Infinity) {
  if (root === null) return true;

  if (root.val <= lower || root.val >= upper) return false;

  return isValidBST(root.left, lower, root.val) &&
         isValidBST(root.right, root.val, upper);
}
```

**Q15. Walk through why the min/max bounds approach correctly catches the Q13 counterexample (the tree that passes the naive local check but is actually invalid).**
A: Starting at the root (5) with bounds `(-Infinity, Infinity)` — valid. Recursing into the right child (8), the bounds narrow to `(5, Infinity)` (lower bound now 5, since everything in 5's right subtree must exceed 5) — 8 is within `(5, Infinity)`, valid. Recursing from 8 into ITS left child (4), the bounds narrow further to `(5, 8)` (lower bound stays 5, inherited from the ancestor constraint; upper bound becomes 8, from the immediate parent) — but `4 <= 5` (the lower bound), so this check **correctly fails**, catching the violation that the naive immediate-children-only check missed, precisely because the bounds approach carries forward the constraint from the more distant ancestor (5), not just the immediate parent (8).

**Q16. What is the alternative approach to BST validation using in-order traversal, and why does it work?**
A: Perform a standard in-order traversal and check that the resulting sequence of values is **strictly increasing** — since a valid BST's in-order traversal is always sorted (Q1), any violation of the sorted order during the traversal directly indicates an invalid BST, without needing to explicitly track bounds at all.

```js
function isValidBSTInorder(root) {
  let prev = -Infinity;
  let isValid = true;

  function inorder(node) {
    if (node === null || !isValid) return;

    inorder(node.left);

    if (node.val <= prev) {
      isValid = false;
      return;
    }
    prev = node.val;

    inorder(node.right);
  }

  inorder(root);
  return isValid;
}
```

**Q17. What is the trade-off between the min/max bounds approach and the in-order traversal approach for BST validation?**
A: Both are O(n) time and O(h) space, and both are entirely valid, commonly-accepted solutions. The bounds approach is arguably more directly tied to the BST property's actual definition (explicitly encoding "everything in this subtree must be within this range"), while the in-order approach leverages a *consequence* of that property (sortedness) rather than checking the definition directly — some find the in-order version more intuitive to derive on the spot (since "check if sorted" is an easy mental leap once you recall the sortedness property), while others find the bounds version more directly expressive of what's actually being verified. Either is a strong answer; being able to explain *why* the naive local-only check fails (Q13) is the more important signal than which of these two correct approaches you happen to reach for first.

### Section 5: Advanced Patterns

**Q18. What happens to BST operations' complexity if the tree becomes severely unbalanced (e.g., built by inserting already-sorted data), and what's the standard fix?**
A: Inserting data in already-sorted order into a plain BST produces a completely skewed tree (effectively a linked list), degrading search/insert/delete from the expected O(log n) to O(n) — the BST property alone says nothing about balance, only about ordering. The standard fix is a **self-balancing BST** variant (AVL trees, Red-Black trees, etc.), which perform additional restructuring operations (rotations) during insertion/deletion specifically to maintain a height bound of O(log n) regardless of insertion order — a substantial topic in its own right, generally covered as a distinct, more advanced data structure beyond the scope of "plain BST" fundamentals.

**Q19. How would you find the in-order successor of a GIVEN node (not necessarily the one just deleted), covering both the case where it has a right subtree and the case where it doesn't?**
A: If the node has a right subtree, its successor is the leftmost node of that right subtree (Q9's `findMin` logic). If it does NOT have a right subtree, the successor is the **nearest ancestor for which the given node is in the left subtree** — found by walking up from the node (if parent pointers are available) or by tracking the "last node where you turned left" during a root-to-node search (if parent pointers aren't available, requiring a fresh O(h) search from the root rather than an upward walk).

**Q20. What is a "BST iterator," and what's the standard technique to implement one with O(1) amortized `next()` calls and O(h) space?**
A: A BST iterator provides `next()` (return the next smallest element) and `hasNext()` in a way that mimics performing a full in-order traversal, but **incrementally**, without precomputing the entire traversal upfront. The standard technique uses an explicit stack: initialize it by pushing every left-child ancestor from the root down to the smallest node; `next()` pops the stack's top (the current smallest unvisited value), and if that popped node has a right child, pushes that right child and then every one of ITS left-child descendants onto the stack (preparing the next batch of "smallest remaining" candidates). This achieves O(h) space (the stack never holds more than the tree's height's worth of nodes at once) and O(1) amortized time per `next()` call (each node is pushed and popped exactly once across the iterator's entire lifetime, same amortized argument as other stack-based techniques covered in the stacks-and-queues guide).

### Section 6: Scenario / Interview-Style Questions

**Q21. "You're asked to validate whether a binary tree satisfies the BST property, and your first instinct is to check `node.left.val < node.val && node.right.val > node.val` at every node. What's wrong with this, and how do you fix it?"**
A: This only checks the BST property locally, between a node and its immediate children — it can pass at every single node while still being an invalid BST overall, if a deeper descendant violates ordering relative to a more distant ancestor (see Q13's concrete counterexample). I'd fix this using the min/max bounds technique (Q14): recursively validate each node against a valid range that narrows as you descend, correctly carrying forward constraints from every ancestor, not just the immediate parent.

**Q22. "A teammate implements BST deletion but only handles the leaf and one-child cases, throwing an error for nodes with two children. What's the missing piece, and how would you complete it?"**
A: The two-children case requires replacing the deleted node's value with its in-order successor (the smallest value in its right subtree, found via a simple leftmost-node walk) or equivalently its in-order predecessor, and then recursively deleting that successor/predecessor from its own (now simpler, since it has at most one child by definition of being the leftmost node) position — I'd explain why the successor/predecessor specifically preserves the BST property everywhere (Q8), rather than an arbitrary replacement value that could break ordering elsewhere in the tree.

**Q23. "You built a BST by inserting a large dataset that happened to already be sorted, and now search operations are unexpectedly slow. What happened, and what would you recommend for future implementations?"**
A: Inserting already-sorted data into a plain BST produces a completely skewed, linked-list-shaped tree, since every new value is either always greater or always less than everything already present — this degrades search/insert/delete from the expected O(log n) to O(n), since the tree's height equals its node count in this worst case. I'd recommend either randomizing insertion order if the dataset is static and known upfront, or — for a more robust general solution — using a self-balancing BST variant (AVL or Red-Black tree) that actively maintains O(log n) height regardless of insertion order.

**Q24. "How would you find the k-th smallest element in a BST, and how does this connect to the BST's core sortedness property?"**
A: Since an in-order traversal of a BST visits nodes in strictly ascending order, the k-th smallest element is simply the k-th node visited during an in-order traversal — this can be done with a standard in-order traversal that stops (early termination) once the k-th node is reached, avoiding the need to traverse the entire tree if k is small relative to the tree's total size; this is a direct, practical application of the same sortedness property that underlies the in-order-traversal BST validation technique (Q16).

**Q25. "Compare the min/max-bounds and in-order-traversal approaches to BST validation — is one strictly better than the other?"**
A: Both achieve the same O(n) time and O(h) space, and both are fully correct — neither is strictly asymptotically better. The bounds approach directly encodes the BST's definitional property (every node's value constrained by an accumulated valid range from all its ancestors), while the in-order approach leverages a *derived consequence* of that property (global sortedness) as a simpler-to-state check. In practice, I'd present whichever comes to mind first as the primary solution, but mentioning the other as an equally valid alternative — and being able to articulate the naive local-check pitfall (Q13) that motivates needing either of these more careful approaches in the first place — demonstrates the fuller understanding an interviewer is looking for.

## Problem 1 — Search in a Binary Search Tree

### Problem
Given the root of a BST and an integer `val`, find the node in the BST whose value equals `val`, and return that subtree rooted there. If no such node exists, return `null`.

```
Input:
        4
       / \
      2   7
     / \
    1   3
val = 2

Output: the subtree rooted at node 2:
      2
     / \
    1   3
```

### Pattern Recognition
Direct BST traversal exploiting the ordering property — at each node, the comparison against `val` tells you exactly which single subtree (if any) could contain it.

### Key Insight
Because every node in a BST enforces "left subtree smaller, right subtree larger," a mismatch between `val` and the current node's value immediately and correctly rules out searching the "wrong" side entirely — no backtracking or exploring both branches is ever needed.

### Approach
Compare `val` to the current node. Equal → found, return it. Smaller → recurse left. Larger → recurse right. `null` reached → not found, return `null`.

### Solution

```js
function searchBST(root, val) {
  if (root === null || root.val === val) return root;

  if (val < root.val) return searchBST(root.left, val);
  return searchBST(root.right, val);
}
```

### Dry Run

```
Tree:
        4
       / \
      2   7
     / \
    1   3

searchBST(4, val=2):
  root(4)!==2, val(2)<4 → recurse left
  searchBST(2, val=2):
    root(2)===2 → return root (the subtree rooted at 2)

Result: the subtree [2,[1],[3]] ✓
```

### Complexity
- Time: O(h) — follows a single path down the tree.
- Space: O(h) recursive call stack (or O(1) iterative).

### Edge Cases
- Empty tree (`root === null`): base case immediately returns `null`.
- Value not present anywhere in the tree: recursion correctly reaches a `null` child and returns `null`.
- Value is at the root itself: immediately matched and returned, no recursion needed.
- Severely unbalanced BST: O(h) degrades to O(n) in this worst-case shape, same caveat as any BST operation.

### Follow-up Questions
- "Implement this iteratively." → Straightforward loop replacing the recursive calls, same comparison logic, O(1) space instead of O(h).
- "What if the tree allows duplicate values?" → The standard BST convention typically disallows duplicates (or defines a specific tie-breaking rule, e.g., duplicates always go right) — worth clarifying this assumption explicitly if the problem doesn't specify.

## Problem 2 — Insert into a Binary Search Tree

### Problem
Given the root of a BST and a value to insert, insert the value into the BST such that the resulting tree is still a valid BST. Return the root of the tree after insertion.

```
Input:
        4
       / \
      2   7
     / \
    1   3
val = 5

Output:
        4
       / \
      2   7
     / \  /
    1   3 5
```

### Pattern Recognition
Standard BST insertion — navigate down using the same comparison logic as search, inserting the new node at the first `null` spot reached.

### Key Insight
A newly inserted value always ends up as a new leaf — the search-like descent naturally terminates at exactly the correct empty position consistent with the BST property, requiring no further restructuring of the rest of the tree.

### Approach
Recursively descend: if `val` is smaller than the current node, recurse left (creating a new node if `null` is reached); if larger, recurse right similarly. Reassign the recursive call's return value to the current node's `left`/`right` pointer to correctly attach the new node.

### Solution

```js
function insertIntoBST(root, val) {
  if (root === null) return { val, left: null, right: null };

  if (val < root.val) {
    root.left = insertIntoBST(root.left, val);
  } else if (val > root.val) {
    root.right = insertIntoBST(root.right, val);
  }

  return root;
}
```

### Dry Run

```
Tree:
        4
       / \
      2   7
     / \
    1   3
val = 5

insertIntoBST(4, 5):
  root(4)!==null, 5>4 → root.right = insertIntoBST(7, 5)
    insertIntoBST(7, 5):
      root(7)!==null, 5<7 → root.left = insertIntoBST(null, 5)
        insertIntoBST(null, 5): root===null → return {val:5,left:null,right:null}
      root(7).left = {val:5,...}
      return root(7)  [now 7 has a left child, 5]
  root(4).right = 7 (with its new left child 5)
  return root(4)

Result tree:
        4
       / \
      2   7
     / \  /
    1   3 5
✓
```

### Complexity
- Time: O(h).
- Space: O(h) recursive call stack.

### Edge Cases
- Empty tree: base case directly creates and returns the new node as the tree's sole root.
- Inserting a duplicate value: per the standard no-duplicates convention, neither `val < root.val` nor `val > root.val` triggers, so no insertion happens and the tree is returned unchanged — worth confirming this is the intended behavior for the specific problem variant.
- Inserting into a severely unbalanced tree: O(h) degrades to O(n), same general BST caveat.

### Follow-up Questions
- "Implement this iteratively, tracking the parent explicitly." → See Q6 — loop down tracking the current node, attach the new node to the last-visited node's appropriate child pointer once a `null` spot is found.
- "What if duplicates should be allowed, going to the right by convention?" → Change the duplicate-handling branch to explicitly recurse right (`val >= root.val` triggers the right-recursion condition) instead of being a silent no-op.

## Problem 3 — Delete Node in a BST

### Problem
Given the root of a BST and a key, delete the node with that key from the BST, maintaining the BST property. Return the (possibly new) root after deletion.

```
Input:
        5
       / \
      3   6
     / \    \
    2   4    7
key = 3

Output:
        5
       / \
      4   6
     /      \
    2        7
(3 replaced by its in-order successor, 4; then 4 is removed from its original position)
```

### Pattern Recognition
The full three-case BST deletion algorithm — leaf, one child, and two children (via in-order successor replacement).

### Key Insight
The two-children case can't simply remove the node or splice in an arbitrary replacement without risking a BST violation — the in-order successor (leftmost node of the right subtree) is specifically guaranteed to preserve ordering correctly when it takes the deleted node's place.

### Approach
Recursively locate the node to delete (using standard BST comparison navigation). Upon finding it: if it has no left child, return its right child directly (handles both leaf and right-child-only cases); if it has no right child, return its left child directly (handles left-child-only case); otherwise (two children), find the in-order successor, copy its value into the current node, then recursively delete the successor from the right subtree.

### Solution

```js
function findMin(node) {
  while (node.left !== null) node = node.left;
  return node;
}

function deleteNode(root, key) {
  if (root === null) return null;

  if (key < root.val) {
    root.left = deleteNode(root.left, key);
  } else if (key > root.val) {
    root.right = deleteNode(root.right, key);
  } else {
    if (root.left === null) return root.right;
    if (root.right === null) return root.left;

    const successor = findMin(root.right);
    root.val = successor.val;
    root.right = deleteNode(root.right, successor.val);
  }

  return root;
}
```

### Dry Run

```
Tree:
        5
       / \
      3   6
     / \    \
    2   4    7
key = 3 (has TWO children: 2 and 4)

deleteNode(5, 3):
  3 < 5 → root.left = deleteNode(3, 3)
    deleteNode(3, 3): key===root.val(3) → found it
      root.left(2)!==null → skip first return
      root.right(4)!==null → skip second return
      → TWO CHILDREN case:
        successor = findMin(root.right=4): 4.left===null → successor = node(4)
        root.val = 4  → the node ORIGINALLY holding "3" now holds value 4
        root.right = deleteNode(4, 4):
          deleteNode(4,4): key===root.val(4) → found
            root.left===null → return root.right (which is null, since 4 was a leaf)
          returns null
        root.right = null  → the (renamed) node's right child is now null
      return root (this node, now valued 4, with left child 2, right child null)
  root(5).left = the above (node valued 4, left=2, right=null)

Final tree:
        5
       / \
      4   6
     /      \
    2        7
✓ (matches expected output — 3 was replaced by successor 4, and 4's original leaf
   position was correctly cleared)
```

### Complexity
- Time: O(h) — one O(h) walk to find the node to delete, plus (in the two-children case) another O(h) walk to find the successor and delete it — two sequential O(h) operations, not nested, so still O(h) overall.
- Space: O(h) recursive call stack.

### Edge Cases
- Deleting a leaf node: `root.left === null` triggers immediately, returning `root.right` (which is also `null` for a true leaf) — correctly removes it entirely.
- Deleting a node with only a left child: `root.right === null` triggers, correctly returning `root.left` to take its place.
- Deleting a node with only a right child: `root.left === null` triggers first, correctly returning `root.right`.
- Deleting the root itself: handled uniformly by the same logic — the function's return value becomes the new root, correctly propagated back to the caller.
- Deleting a key not present in the tree: recursion reaches a `null` node and returns `null` at that point, leaving the rest of the tree structurally unchanged (no accidental deletion of an unrelated node).

### Follow-up Questions
- "Use the in-order PREDECESSOR instead of successor — does it still work?" → Yes, symmetric — find the rightmost node of the LEFT subtree instead, and the same replace-then-recursively-delete logic applies, still correctly preserving the BST property.
- "What if the BST needs to remain balanced after deletion (AVL/Red-Black tree)?" → Would require additional rebalancing logic (rotations) after the standard deletion, a substantially more involved topic specific to self-balancing BST variants (see Q18).

## Problem 4 — Validate Binary Search Tree

### Problem
Given the root of a binary tree, determine if it is a valid binary search tree.

```
Input:
        5
       / \
      3   8
         / \
        4   9

Output: false  (node 4 is in node 5's right subtree, but 4 < 5, violating the BST property)
```

### Pattern Recognition
Min/max bounds propagation — recursively validate each node against a valid range that narrows as you descend, correctly enforcing the BST property globally (not just against immediate children).

### Key Insight
A naive check comparing each node only to its immediate children can pass even on an invalid tree, since it never checks a node against more distant ancestors — propagating and narrowing bounds as you descend correctly carries forward every ancestor's constraint.

### Approach
Recursive function taking a node plus a `(lower, upper)` valid range, initially unbounded. At each node, verify its value falls strictly within the current range; recurse left with the upper bound tightened to the current value, and recurse right with the lower bound tightened to the current value.

### Solution

```js
function isValidBST(root, lower = -Infinity, upper = Infinity) {
  if (root === null) return true;

  if (root.val <= lower || root.val >= upper) return false;

  return isValidBST(root.left, lower, root.val) &&
         isValidBST(root.right, root.val, upper);
}
```

### Dry Run

```
Tree:
        5
       / \
      3   8
         / \
        4   9

isValidBST(5, -Inf, Inf):
  5 <= -Inf? no. 5 >= Inf? no. → valid so far
  left: isValidBST(3, -Inf, 5):
    3 <= -Inf? no. 3 >= 5? no. → valid
    left: isValidBST(null,...) → true (base case)
    right: isValidBST(null,...) → true
    return true && true = true
  left subtree returns true

  right: isValidBST(8, 5, Inf):
    8 <= 5? no. 8 >= Inf? no. → valid so far
    left: isValidBST(4, 5, 8):
      4 <= 5? YES → return false
    (short-circuits: right side of 8's check isn't even evaluated due to && short-circuit,
     though in this trace we'll note it's skipped)
    right subtree of 8's validation already returns false due to the left check failing
  right subtree (8's) returns false

  return true && false = false

Result: false ✓ (correctly caught, unlike a naive immediate-children-only check would)
```

### Complexity
- Time: O(n) — every node visited once.
- Space: O(h) — recursion call stack.

### Edge Cases
- Empty tree: base case immediately returns `true` (vacuously a valid BST).
- Single node: no children to recurse into, both recursive calls hit the `null` base case and return `true`, correctly validating trivially.
- Tree with duplicate values: using strict `<=`/`>=` comparisons means a duplicate value anywhere relative to an ancestor correctly fails validation — worth confirming this matches the intended "no duplicates allowed" convention, or adjusting to non-strict comparisons if duplicates should be permitted on one specific side by convention.
- Using `Infinity`/`-Infinity` as sentinel bounds: works cleanly in JavaScript's native number system; in strictly-typed/fixed-width-integer languages, using the actual min/max representable integer values (or nullable bounds) would be the equivalent approach, since there's no native infinity concept there.

### Follow-up Questions
- "Show the in-order-traversal alternative approach." → See Q16 — track the previous value visited and confirm strictly increasing order throughout the traversal.
- "What's wrong with checking only `node.left.val < node.val && node.right.val > node.val`?" → See Q13 — this only validates locally between immediate parent/child pairs, missing violations against more distant ancestors.

## Problem 5 — Kth Smallest Element in a BST

### Problem
Given the root of a BST and an integer `k`, return the k-th smallest value among all the values in the tree.

```
Input:
        5
       / \
      3   6
     / \
    2   4
k = 3

Output: 4   (sorted order: 2,3,4,5,6 — the 3rd smallest is 4)
```

### Pattern Recognition
In-order traversal with early termination — directly exploits the BST's guarantee that in-order traversal visits nodes in strictly ascending order.

### Key Insight
Since in-order traversal of a BST always produces sorted order, the k-th value encountered during that traversal IS the k-th smallest element — no separate sorting step is needed, and the traversal can stop as soon as the k-th node is reached, rather than needing to visit the entire tree.

### Approach
Perform an in-order traversal (left, node, right), maintaining a counter of how many nodes have been visited so far. The moment the counter reaches `k`, record that node's value as the answer and stop further traversal.

### Solution

```js
function kthSmallest(root, k) {
  let count = 0;
  let result = null;

  function inorder(node) {
    if (node === null || result !== null) return; // early termination once found

    inorder(node.left);

    if (result !== null) return; // check again after returning from left recursion
    count++;
    if (count === k) {
      result = node.val;
      return;
    }

    inorder(node.right);
  }

  inorder(root);
  return result;
}
```

### Dry Run

```
Tree:
        5
       / \
      3   6
     / \
    2   4
k=3

inorder(5):
  inorder(3):
    inorder(2):
      inorder(null) → return
      count=1. 1===3? no.
      inorder(null) → return
    (back from inorder(2), result still null)
    count=2. 2===3? no.
    inorder(4):
      inorder(null) → return
      count=3. 3===3? YES → result=4. return.
    (back from inorder(4))
  (back from inorder(3), result is now 4 — but check happens at the TOP of the next
   inorder call, so no further unnecessary work happens once result is set)
  result!==null → return immediately (skip processing node 5 and node 6 entirely)

Result: 4 ✓ (correctly found without visiting nodes 5 or 6, thanks to early termination)
```

### Complexity
- Time: O(h + k) — in the best/average case, only needs to traverse down to find the k-th node without visiting the entire tree; worst case (k close to n, or a skewed tree) approaches O(n).
- Space: O(h) — recursion call stack.

### Edge Cases
- `k = 1`: finds the very first (smallest) node visited, which is the leftmost node of the entire tree.
- `k` equals the total number of nodes: effectively must traverse the entire tree (the last node in-order), no early-termination benefit in this specific case.
- `k` larger than the total number of nodes: `result` remains `null` after the full traversal completes — real implementations should typically guard against or explicitly define behavior for this invalid input, per the problem's stated constraints (often assumed to guarantee `k` is always valid).
- Single-node tree, `k=1`: immediately finds and returns that single node's value.

### Follow-up Questions
- "What if there are MANY kthSmallest queries on the same tree — how would you optimize?" → Augment each node with a count of nodes in its left subtree (maintained during insertions/deletions), allowing each query to navigate directly toward the k-th node in O(h) without a full in-order traversal each time — a common "order statistics tree" augmentation.
- "Find the Kth LARGEST instead?" → Mirror the traversal order (right, node, left — a "reverse in-order" traversal) instead of the standard left-node-right order, otherwise the same early-termination counting logic applies.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve a Binary Search Tree's core operations or validity?
│
├── SEARCH FOR A VALUE?
│   └── Standard BST comparison descent → O(h) time, follows exactly one path
│
├── INSERT A NEW VALUE?
│   └── Same descent logic, insert at the first NULL spot reached (always becomes a leaf)
│       → O(h) time; remember to return-and-reassign child pointers to attach the new node
│
├── DELETE A VALUE?
│   ├── Node is a leaf → remove directly (falls out of the "0/1 child" checks naturally)
│   ├── Node has exactly ONE child → replace node with that child directly
│   └── Node has TWO children → replace its value with its in-order SUCCESSOR
│         (leftmost node of right subtree) or PREDECESSOR, then recursively delete
│         that successor/predecessor from its own (simpler) position
│
├── VALIDATE WHETHER A TREE IS A VALID BST?
│   ├── DO NOT just check node vs. immediate children only — this misses violations
│   │     against more distant ancestors (see the classic counterexample)
│   ├── Min/Max Bounds Propagation → narrow (lower, upper) range at every recursive step
│   └── In-Order Traversal Check → confirm values are strictly increasing throughout
│
├── FIND THE Kth SMALLEST/LARGEST ELEMENT?
│   └── In-order traversal (or reverse in-order for Kth largest) with a counter,
│       early-terminating once the Kth node is reached
│
├── TREE MIGHT BECOME SEVERELY UNBALANCED (e.g., sorted-order insertions)?
│   └── Consider a self-balancing BST variant (AVL, Red-Black) if O(log n) guarantees
│       are required regardless of insertion order — beyond plain-BST scope
│
└── NEED TO ITERATE THROUGH BST VALUES INCREMENTALLY (not all at once)?
    └── BST Iterator using an explicit stack of left-spine ancestors,
        O(h) space, O(1) amortized time per next() call
```

## Common Bugs Checklist

Before submitting any BST search/insert/delete/validate solution, verify:

1. **Insertion/deletion: recursive calls' return values reassigned to the correct child pointer (`root.left = ...` / `root.right = ...`), not just called and discarded?** — Forgetting this reassignment leaves newly created nodes disconnected from the tree, or leaves deleted nodes still referenced by their former parent.

2. **Deletion: two-children case replaces the VALUE with the successor, then separately recursively deletes the successor from ITS position — not just splicing subtrees together directly?** — Directly splicing without this two-step "copy value, then delete the original successor node" process risks corrupting the tree structure or losing nodes.

3. **Deletion: `findMin` correctly walks only LEFT (not checking values, just structure) to find the leftmost/smallest node of a subtree?** — Using a value-comparison-based search instead of a simple "keep going left" walk is unnecessary and could introduce bugs if implemented incorrectly.

4. **Validation: bounds propagated and narrowed correctly — left recursion narrows the UPPER bound to the current value, right recursion narrows the LOWER bound?** — Mixing these up (narrowing the wrong bound on the wrong side) silently produces incorrect validation results.

5. **Validation: strict inequality (`<=`/`>=` triggering failure) used consistently, matching whichever duplicate-handling convention the problem intends?** — Using non-strict comparisons when duplicates should be disallowed (or vice versa) causes validation to incorrectly accept or reject trees with duplicate values.

6. **Kth smallest: early termination correctly implemented, checking the `result !== null` (or equivalent) flag at the right points to avoid unnecessary further traversal after the answer is found?** — Missing an early-termination check in one of the recursive call sites (e.g., checking before the left recursion but forgetting to check again before the right recursion) can cause unnecessary extra work, though it wouldn't produce an incorrect final answer — a performance issue rather than a correctness one, but still worth catching.

7. **All BST operations: comparison direction correct (smaller goes left, larger goes right), consistently throughout the entire implementation?** — A single flipped comparison anywhere silently breaks the BST property for that portion of the tree, an easy-to-miss but tree-corrupting bug.

**Final Tip:** At the 5 YOE level, interviewers expect fluent, correct recall of all three core BST operations (search, insert, delete) including the full three-case handling for deletion — the two-children case with in-order successor replacement is the detail that most separates a complete answer from an incomplete one. For validation specifically, proactively naming and explaining the naive "immediate children only" pitfall (Q13), before presenting either the min/max-bounds or in-order-traversal fix, is a strong signal that you understand *why* the correct approaches are necessary, not just that you've memorized one of them.
