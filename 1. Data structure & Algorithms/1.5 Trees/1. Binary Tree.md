## Topic A: Traversal Fundamentals

### Section A1: Fundamentals

**Q1. What is a binary tree traversal, and why are there multiple orderings?**
A: A binary tree traversal is a systematic procedure for visiting every node in the tree exactly once. Unlike a linear data structure (array, linked list) where only one natural traversal order exists (left to right), a binary tree branches at every node — at each node you have three things to visit: the node itself (N), its left subtree (L), and its right subtree (R). The order in which you visit these three components defines the traversal:

- **Preorder (NLR)**: visit the node, then recurse left, then recurse right.
- **Inorder (LNR)**: recurse left, then visit the node, then recurse right.
- **Postorder (LRN)**: recurse left, then recurse right, then visit the node.
- **Level-order (BFS)**: visit all nodes at depth 0, then depth 1, then depth 2, etc. — a separate family covered in the BFS guide.

The three DFS orderings exist because different applications need the data in different arrangements: inorder gives sorted output for BSTs, preorder gives a serialization order useful for reconstructing the tree, and postorder computes subtree-dependent results (like subtree sizes or expression tree evaluation) before their parent.

```
        1
       / \
      2   3
     / \
    4   5

Preorder  (NLR): 1, 2, 4, 5, 3
Inorder   (LNR): 4, 2, 5, 1, 3
Postorder (LRN): 4, 5, 2, 3, 1
```

**Q2. What is the node structure for a binary tree, and what does a minimal tree look like in code?**
A: Each node stores a value and optional left and right child pointers. A leaf node has both children as `null`. The root is the single entry point — no node points to it as a child.

```js
class TreeNode {
  constructor(val, left = null, right = null) {
    this.val = val;
    this.left = left;
    this.right = right;
  }
}

// Building the example tree:
//        1
//       / \
//      2   3
//     / \
//    4   5
const root = new TreeNode(1,
  new TreeNode(2,
    new TreeNode(4),
    new TreeNode(5)
  ),
  new TreeNode(3)
);
```

**Q3. What are the recursive implementations of all three traversals, and why are they so concise?**
A: The recursive implementations are concise because the traversal's structure maps directly onto the function call structure — the call stack implicitly handles the "where to go next after finishing a subtree" bookkeeping. The only difference between the three is where the `visit(node)` call appears relative to the two recursive calls:

```js
// Preorder: visit BEFORE recursing into children
function preorder(node, result = []) {
  if (!node) return result;
  result.push(node.val);        // N: visit node first
  preorder(node.left, result);  // L: then left subtree
  preorder(node.right, result); // R: then right subtree
  return result;
}

// Inorder: visit BETWEEN the two recursive calls
function inorder(node, result = []) {
  if (!node) return result;
  inorder(node.left, result);   // L: left subtree first
  result.push(node.val);        // N: then visit node
  inorder(node.right, result);  // R: then right subtree
  return result;
}

// Postorder: visit AFTER both recursive calls
function postorder(node, result = []) {
  if (!node) return result;
  postorder(node.left, result);  // L: left subtree first
  postorder(node.right, result); // R: then right subtree
  result.push(node.val);         // N: visit node last
  return result;
}
```

The base case `if (!node) return result` handles both leaf nodes (their children are null) and empty trees (root is null). The recursive calls are tail-free — no work happens after the recursive calls in preorder, but work happens between them in inorder and after them in postorder.

**Q4. What are the time and space complexities of recursive traversals?**
A: For all three recursive traversals:
- **Time**: O(n) — every node is visited exactly once. The work per node is O(1) (push to result). Total: O(n).
- **Space**: O(h) for the call stack, where `h` is the height of the tree. In the best case (balanced tree), `h = O(log n)`. In the worst case (completely skewed tree — a linked list shape), `h = O(n)`. The output array itself requires O(n) space but is typically not counted as "extra" space since it's the required return value.

```
Balanced tree (h = log n):    Space = O(log n) call stack
Skewed tree (h = n):          Space = O(n) call stack  ← stack overflow risk
```

The O(n) call stack depth on skewed trees is why iterative implementations matter: they replace the implicit call stack with an explicit stack on the heap, where memory is far larger and stack overflow is not a concern.

**Q5. What is the fundamental challenge of converting recursive tree traversals to iterative ones?**
A: The recursive implementations use the call stack to remember "where to return to" after finishing a subtree. Converting to iterative means explicitly managing this memory with a stack data structure. The challenge differs by traversal:

- **Preorder** is the easiest: visit a node immediately on encounter, then push right child before left (so left is processed first — LIFO). The "return address" is just the pending children.
- **Inorder** is harder: you cannot visit a node until its entire left subtree is exhausted. You must push the node itself onto the stack, descend as far left as possible, then on the way back up, visit each node and switch to its right subtree.
- **Postorder** is the hardest: you cannot visit a node until both its left and right subtrees are exhausted. The standard approaches either use a two-stack trick (preorder variant reversed) or a `prev` pointer to track whether the right subtree has already been visited.

The mental model: the explicit stack replaces the call stack; each stack entry represents a "suspended" function call waiting to resume.

### Section A2: Advanced Patterns

**Q6. What is the iterative preorder traversal, and why is right pushed before left?**
A: Iterative preorder uses one stack. Initialize with the root. At each step: pop a node, visit it, push its right child, then push its left child. The right child is pushed first so the left child ends up on top — the LIFO stack processes left before right, matching the NLR order.

```js
function preorderIterative(root) {
  if (!root) return [];
  const result = [];
  const stack = [root];

  while (stack.length > 0) {
    const node = stack.pop();
    result.push(node.val);         // N: visit node immediately on pop

    if (node.right) stack.push(node.right); // push right first
    if (node.left)  stack.push(node.left);  // push left second (processed first)
  }
  return result;
}
```

The invariant: at every iteration, the stack contains exactly the nodes that are roots of subtrees yet to be visited, in the correct preorder order (top of stack = next node to visit). The push-right-before-left rule maintains this invariant.

**Q7. What is the iterative inorder traversal, and what does the stack represent at each step?**
A: Iterative inorder uses one stack and a `curr` pointer. The algorithm has two modes: **descend** (follow left children, pushing each node onto the stack) and **process** (pop a node, visit it, then switch to its right subtree). The switch from descend to process happens when `curr` becomes null (no more left children to follow).

```js
function inorderIterative(root) {
  const result = [];
  const stack = [];
  let curr = root;

  while (curr !== null || stack.length > 0) {
    // Descend: push all left children
    while (curr !== null) {
      stack.push(curr);
      curr = curr.left;
    }
    // Process: pop, visit, switch to right subtree
    curr = stack.pop();
    result.push(curr.val);   // N: visit node after left subtree is exhausted
    curr = curr.right;       // R: switch to right subtree (may be null → triggers pop again)
  }
  return result;
}
```

At any moment, the stack holds all ancestors of `curr` for which the left subtree is still being processed (or has been processed up to the current descent). The stack top is always the node whose left subtree was most recently exhausted — it is the next node to be visited. The outer loop condition `curr !== null || stack.length > 0` handles both "still descending" and "still have nodes to process" states.

**Q8. What are the two standard approaches for iterative postorder traversal?**
A: Postorder is the hardest to implement iteratively because a node must be visited after both subtrees. Two clean approaches:

**Approach 1 — Two-stack (or reverse-preorder)**: observe that the reverse of a "NRL" traversal (preorder but right-before-left) is "LRN" = postorder. Run a modified preorder that visits NRL (push left before right, so right is processed first), collect the result, then reverse it.

```js
function postorderTwoStack(root) {
  if (!root) return [];
  const result = [];
  const stack = [root];

  while (stack.length > 0) {
    const node = stack.pop();
    result.push(node.val);          // collect in NRL order

    if (node.left)  stack.push(node.left);   // push left first
    if (node.right) stack.push(node.right);  // push right second (processed first)
  }
  return result.reverse(); // NRL reversed = LRN = postorder
}
```

**Approach 2 — One-stack with `prev` pointer**: track the previously visited node (`prev`). A node can be visited when: (a) it has no right child, or (b) its right child was the last node visited (`prev === node.right` — right subtree already done). Otherwise, push the node back (or leave it on the stack) and descend into the right subtree.

```js
function postorderOneStack(root) {
  const result = [];
  const stack = [];
  let curr = root, prev = null;

  while (curr !== null || stack.length > 0) {
    // Descend left
    while (curr !== null) {
      stack.push(curr);
      curr = curr.left;
    }

    curr = stack[stack.length - 1]; // peek (don't pop yet)

    // Visit if: no right child OR right subtree already processed
    if (curr.right === null || curr.right === prev) {
      stack.pop();
      result.push(curr.val); // N: visit after both subtrees done
      prev = curr;
      curr = null;           // force next iteration to pop from stack
    } else {
      curr = curr.right;     // right subtree not yet processed — descend
    }
  }
  return result;
}
```

The two-stack approach is easier to explain and implement; the one-stack approach is more space-efficient (uses one stack instead of two) and demonstrates deeper understanding.

**Q9. What is Morris Traversal, and how does it achieve O(1) space for inorder traversal?**
A: Morris Traversal achieves O(1) extra space (no stack, no recursion) by temporarily modifying the tree's `right` pointers to create "threads" — links from the rightmost node of a subtree back to the subtree's root — and then restoring them after use. The key insight: for any node `curr`, the inorder predecessor (rightmost node of its left subtree) has a `right` pointer that is `null` by default. Morris Traversal uses that null `right` pointer to store a thread back to `curr`, allowing traversal without a stack.

```js
function morrisInorder(root) {
  const result = [];
  let curr = root;

  while (curr !== null) {
    if (curr.left === null) {
      // No left subtree: visit curr and move right
      result.push(curr.val);
      curr = curr.right;
    } else {
      // Find inorder predecessor (rightmost node of left subtree)
      let pred = curr.left;
      while (pred.right !== null && pred.right !== curr) {
        pred = pred.right;
      }

      if (pred.right === null) {
        // Thread not yet created: create it and descend left
        pred.right = curr;   // thread: predecessor → curr
        curr = curr.left;
      } else {
        // Thread already exists: we've returned from the left subtree
        pred.right = null;   // restore: remove the thread
        result.push(curr.val); // visit curr
        curr = curr.right;
      }
    }
  }
  return result;
}
```

Time: O(n) — each node is visited at most twice (once to create the thread, once to follow it back). Space: O(1) — no call stack, no explicit stack, only two pointer variables. The tree is temporarily modified but fully restored by the end of the traversal. Morris Traversal is the gold-standard O(1)-space tree traversal and is expected knowledge at senior level.

**Q10. How do you perform all three traversals in a single unified iterative pass?**
A: A unified iterative approach uses a stack of `[node, state]` pairs where `state` tracks how many of the node's three components (N, L, R) have been processed. Each node starts at state 0 (nothing processed) and advances through 3 states. This mirrors the recursive call exactly — the state encodes where in the NLR/LNR/LRN sequence the "suspended function call" is paused.

```js
function unifiedTraversal(root, order = 'inorder') {
  const result = [];
  if (!root) return result;

  // Stack stores [node, visitStage]
  // visitStage 0 = not yet processed, 1 = left done, 2 = right done
  const stack = [[root, 0]];

  while (stack.length > 0) {
    const [node, stage] = stack[stack.length - 1];

    if (stage === 0) {
      // First visit: decide whether to visit now (preorder)
      stack[stack.length - 1][1] = 1; // advance stage
      if (order === 'preorder') result.push(node.val);
      if (node.left) stack.push([node.left, 0]);
    } else if (stage === 1) {
      // Left done: decide whether to visit now (inorder)
      stack[stack.length - 1][1] = 2;
      if (order === 'inorder') result.push(node.val);
      if (node.right) stack.push([node.right, 0]);
    } else {
      // Right done: visit now (postorder), then pop
      stack.pop();
      if (order === 'postorder') result.push(node.val);
    }
  }
  return result;
}
```

This unified approach is rarely used in practice (separate implementations are cleaner), but it's an excellent interview answer when asked to "implement all three traversals in one framework" — demonstrating that the three traversals differ only in the position of the visit step, not in the traversal logic.

## Topic B: Traversal Properties and Applications

### Section B1: Fundamentals

**Q11. Why does inorder traversal of a BST produce a sorted sequence?**
A: In a BST, for every node: all values in its left subtree are strictly less than the node's value, and all values in its right subtree are strictly greater. Inorder traversal visits: left subtree (all values less than current) → current node → right subtree (all values greater than current). This exactly matches the sorted order. Recursively, the left subtree itself is a BST and its inorder traversal is sorted; same for the right subtree. The three sorted sequences (left subtree values, current value, right subtree values) concatenated in order produce a globally sorted sequence.

```
BST:        4
           / \
          2   6
         / \ / \
        1  3 5  7

Inorder: 1, 2, 3, 4, 5, 6, 7  ← sorted ✓
```

This property makes inorder traversal the standard tool for BST validation (check that inorder output is strictly increasing), BST-to-sorted-array conversion, and finding the kth smallest element in a BST.

**Q12. How does preorder traversal uniquely define a tree when combined with inorder traversal?**
A: Preorder traversal visits the root first, making `preorder[0]` always the root of the current subtree. Inorder traversal visits the root between left and right subtrees — so finding `preorder[0]` in the inorder array splits it into left-subtree elements (all indices before the root in inorder) and right-subtree elements (all after). Recursively applying this logic reconstructs the entire tree. A preorder+inorder pair uniquely determines a binary tree (assuming distinct values). Inorder+postorder also works (postorder's last element is the root). Preorder+postorder alone does not uniquely determine a binary tree when nodes have only one child (ambiguity between left-only and right-only child).

```
Preorder: [3, 9, 20, 15, 7]
Inorder:  [9, 3, 15, 20, 7]

preorder[0] = 3 → root
In inorder, 3 is at index 1:
  left subtree inorder = [9]         → 1 node
  right subtree inorder = [15, 20, 7] → 3 nodes

preorder[1..1] = [9]       → left subtree preorder
preorder[2..4] = [20, 15, 7] → right subtree preorder

Recurse: build left from ([9], [9]) and right from ([20,15,7], [15,20,7])
```

**Q13. What are the canonical use cases for each traversal in real applications?**
A:

**Preorder**:
- Tree serialization / copying — preorder visits each node before its children, so reconstructing the tree requires only the preorder sequence plus null markers.
- Prefix expression trees — `operator` before `operands` matches NLR order.
- Directory traversal — visit a directory before its contents.
- Generating a "path from root" — preorder naturally records the path as it descends.

**Inorder**:
- BST operations — sorted output, validation, kth-smallest, range queries.
- Expression tree evaluation for infix expressions (with parentheses).
- Flattening a BST to a sorted linked list.
- Threaded binary trees — inorder threads connect each node to its inorder successor.

**Postorder**:
- Deleting a tree — delete children before parent (cannot delete a node that has live children pointing to it in a reference-counted system).
- Expression tree evaluation for postfix (RPN) expressions.
- Computing subtree aggregates — subtree size, subtree sum, height — all require children's results before the parent's computation.
- Dependency resolution — process dependencies before the node that depends on them.

**Q14. How do you reconstruct a binary tree from preorder and inorder traversals?**
A: The recursive reconstruction uses the root-finding property of preorder and the left/right-split property of inorder. Use a HashMap for O(1) inorder index lookup.

```js
function buildTree(preorder, inorder) {
  const inMap = new Map();
  for (let i = 0; i < inorder.length; i++) {
    inMap.set(inorder[i], i); // value → index in inorder
  }

  let preIdx = 0; // global pointer into preorder array

  function build(left, right) {
    // left/right define the current subtree's range in the inorder array
    if (left > right) return null;

    const rootVal = preorder[preIdx++]; // next preorder element = root
    const node = new TreeNode(rootVal);

    const mid = inMap.get(rootVal); // root's position in inorder

    // Build left subtree first (consumes preorder elements before right subtree)
    node.left  = build(left, mid - 1);
    node.right = build(mid + 1, right);

    return node;
  }

  return build(0, inorder.length - 1);
}
```

Time: O(n) — each node processed once; HashMap lookup is O(1). Space: O(n) for the HashMap and O(h) for the recursion stack.

### Section B2: Advanced Patterns

**Q15. What is an iterative inorder traversal used for in BST problems, and what is the "lazy iterator" pattern?**
A: Many BST problems require processing inorder elements one at a time without materializing the full sorted array — for example, finding the kth smallest element (stop after k pops) or merging two BSTs (interleave two inorder streams). The lazy iterator pattern: initialize the stack and `curr` pointer as in standard iterative inorder, but expose `hasNext()` and `next()` methods that advance the traversal by exactly one step per call.

```js
class BSTIterator {
  constructor(root) {
    this.stack = [];
    this.curr = root;
  }

  hasNext() {
    return this.curr !== null || this.stack.length > 0;
  }

  next() {
    // Descend as far left as possible from curr
    while (this.curr !== null) {
      this.stack.push(this.curr);
      this.curr = this.curr.left;
    }
    // Pop, visit, switch to right subtree
    const node = this.stack.pop();
    this.curr = node.right;
    return node.val;
  }
}
```

Time: O(1) amortized per `next()` call (each node pushed and popped at most once across all calls). Space: O(h) — the stack holds at most one path from root to a leaf at any time, not all n nodes. This is the critical efficiency advantage over precomputing the full inorder array: O(h) space instead of O(n).

**Q16. How does postorder traversal compute the height of a binary tree, and what does "returning a value from a traversal" mean generally?**
A: The height of a tree rooted at a node is `1 + max(height(left), height(right))`. This computation requires the heights of both children before the parent's height can be determined — postorder (children before parent) is the natural fit. "Returning a value from a traversal" means the recursive function returns a computed result for the current subtree rather than just visiting nodes:

```js
function height(node) {
  if (!node) return 0;             // base case: empty tree has height 0
  const leftH  = height(node.left);   // postorder: compute left first
  const rightH = height(node.right);  // then right
  return 1 + Math.max(leftH, rightH); // then compute current node's result
}
```

This pattern — compute left result, compute right result, combine at current node — underlies almost every tree DP problem: diameter, balanced-tree check, lowest common ancestor, path sum, subtree sum, and more. Recognizing "I need children's results before I can compute the parent's result" is the signal to use postorder structure.

**Q17. What is the vertical order traversal of a binary tree, and how does it combine traversal with coordinate tracking?**
A: Vertical order traversal assigns each node a horizontal distance (HD) from the root: root = 0, left child = parent HD - 1, right child = parent HD + 1. Nodes with the same HD are in the same vertical column, listed top-to-bottom (by depth), left-to-right for ties at the same depth. Implementation: BFS or DFS, tracking (node, HD, depth) triples, then grouping by HD and sorting within each HD by (depth, value). The traversal itself is standard (preorder or BFS), augmented with coordinate bookkeeping — a common interview pattern of "standard traversal + extra state per node."

**Q18. What is the difference between depth-first traversals (pre/in/post) and breadth-first (level-order), and when does each class apply?**
A: Depth-first traversals follow one branch as far as possible before backtracking — using a stack (implicit in recursion or explicit). Breadth-first traversal visits all nodes at the same depth before going deeper — using a queue. The choice:

- **DFS (pre/in/postorder)**: naturally suited to problems where the answer for a node depends on the structure of its subtree — subtree aggregates, path problems, reconstruction, BST operations. DFS space is O(h) (stack depth = tree height).
- **BFS (level-order)**: naturally suited to problems where level/depth is significant — level averages, zigzag order, minimum depth, right side view, connecting nodes at the same level. BFS space is O(w) (queue width = max tree width, up to O(n) for complete trees).

The boundary: if the problem mentions "level," "depth," "row," or "nearest" in a tree context → BFS. If it mentions "subtree," "path," "ancestor," "leaf-to-root" → DFS.

## Topic C: Cross-Topic & Interview-Style Questions

**Q19. "You're asked to implement inorder traversal iteratively. Walk through your thought process before writing code."**
A: I start from the recursive structure: the function descends left, visits, then descends right. The call stack's job is to remember "return here after finishing the left subtree." I need to replicate this manually. My explicit stack will hold nodes that are "waiting to be visited" — their left subtrees are being (or have been) processed. The pointer `curr` tracks where I'm actively descending. When `curr` hits null, I've exhausted one left branch — time to pop, visit, and switch to the right. The outer loop continues as long as either `curr` is non-null (still descending) or the stack is non-empty (still have pending nodes). I always push before descending left and pop to visit — this is the exact inversion of the call stack's implicit push-on-call, pop-on-return behavior.

**Q20. "Can you reconstruct a binary tree from only its preorder or only its inorder traversal? Why or why not?"**
A: Neither preorder nor inorder alone uniquely determines a binary tree.

**Preorder alone**: `preorder[0]` is the root, but without knowing where the left subtree ends and the right subtree begins (which inorder provides), the left/right split is ambiguous. Example: preorder `[1, 2]` could be a tree with root 1 and left child 2, or root 1 and right child 2 — both produce the same preorder.

**Inorder alone**: the position of the root in the inorder sequence is unknown (could be anywhere), so the root itself cannot be identified. Any permutation that is consistent with the BST property would be valid, but for a general binary tree there are no such constraints.

**Preorder + inorder together**: uniquely determines the tree because preorder identifies the root and inorder identifies the left/right split — together they eliminate all ambiguity (assuming distinct values).

**Preorder + postorder**: uniquely determines the tree only for full binary trees (every node has 0 or 2 children). For trees where some nodes have exactly one child, ambiguity remains about whether the single child is a left or right child.

**Q21. "How do you detect if a binary tree is a BST using traversal?"**
A: The cleanest approach: run an inorder traversal and check that the sequence is strictly increasing. If any element is ≤ its predecessor in the inorder sequence, the tree violates the BST property. This can be done without materializing the full array by tracking a `prev` variable (the previously visited node's value) updated during inorder traversal and checking `curr.val > prev` at each visit:

```js
function isValidBST(root) {
  let prev = -Infinity;

  function inorder(node) {
    if (!node) return true;
    if (!inorder(node.left)) return false;    // left subtree invalid?
    if (node.val <= prev) return false;       // current violates BST property?
    prev = node.val;                          // update prev
    return inorder(node.right);              // check right subtree
  }

  return inorder(root);
}
```

This is O(n) time, O(h) space. An alternative is the range-propagation approach (each node must have value in a valid `(min, max)` range passed down from its parent), which is more direct but requires careful range bookkeeping. Both are valid; the inorder approach is the more elegant connection between traversal theory and BST validation.

**Q22. "In one sentence each, what is the core mechanical difference between preorder, inorder, and postorder iterative implementations?"**
A:
- **Preorder**: pop a node from the stack and visit it immediately, then push right before left — the stack is a queue of roots of unvisited subtrees.
- **Inorder**: use a `curr` pointer to descend left (pushing to stack), and switch to pop-visit-right mode only when `curr` hits null — the stack holds a pending ancestor chain waiting for their left subtrees to finish.
- **Postorder**: either reverse a right-first preorder traversal (two-stack approach), or peek at the stack top and use a `prev` pointer to determine whether the right subtree has already been visited before committing to a pop-and-visit (one-stack approach).

**Q23. "What happens to each traversal on a single-node tree, an empty tree, and a tree that is a linked list (all left children)?"**
A:

**Empty tree (root = null)**:
All three traversals: base case triggers immediately, return empty array. O(1) time, O(1) space.

**Single-node tree (root, no children)**:
- Preorder: [root.val] — visit root, left recursion on null returns, right recursion on null returns.
- Inorder: [root.val] — same sequence of calls, same result.
- Postorder: [root.val] — same.
All three return the same single-element array for a single-node tree.

**Left-skewed tree (n nodes, all left children — linked list shape)**:
- Preorder: visits root, then descends left chain. Result: [1, 2, 3, ..., n] (top-down).
- Inorder: descends all the way to the leftmost leaf first, then visits on the way back up. Result: [n, n-1, ..., 2, 1] (bottom-up, since the deepest node is visited first).
- Postorder: same as inorder for a left-skewed tree with no right subtrees. Result: [n, n-1, ..., 2, 1].
- Call stack depth: O(n) — dangerous for very deep trees, motivating iterative implementations.

**Q24. "How does the choice of traversal affect the output order for expression trees?"**
A: An expression tree stores operators at internal nodes and operands at leaves. The three traversals produce the three standard expression notations:
- **Preorder (NLR)**: operator visited before operands → **prefix notation** (Polish notation). `+ 3 * 4 5` means `3 + (4 × 5)`.
- **Inorder (LNR)**: operator visited between operands → **infix notation** (standard math). `3 + 4 * 5` (parentheses needed to resolve ambiguity for complex expressions).
- **Postorder (LRN)**: operator visited after operands → **postfix notation** (Reverse Polish Notation). `3 4 5 * +` — directly evaluable by a stack-based calculator without parentheses.

```
Expression tree for (3 + (4 × 5)):
        +
       / \
      3   ×
         / \
        4   5

Preorder:  +, 3, ×, 4, 5  → prefix:  + 3 × 4 5
Inorder:   3, +, 4, ×, 5  → infix:   3 + 4 × 5
Postorder: 3, 4, 5, ×, +  → postfix: 3 4 5 × +
```

**Q25. "When would you choose Morris Traversal over a stack-based iterative traversal?"**
A: Morris Traversal is preferable when O(1) extra space is a hard constraint — embedded systems, memory-constrained environments, or problems that explicitly prohibit additional data structures. It is also used in the threaded binary tree construction (the threads it creates temporarily are exactly the inorder threading). The cost: Morris Traversal temporarily modifies the tree (though it restores it), making it unsafe in concurrent read scenarios or when the tree is immutable. Stack-based iterative traversal is preferable in most production code: it's simpler to reason about, doesn't modify the tree, and O(h) stack space is usually negligible. The decision: if the interviewer says "O(1) space" → Morris; otherwise → iterative with stack.

**Q26. "How do you find the kth smallest element in a BST in O(h + k) time?"**
A: Use the iterative inorder traversal (BST Iterator pattern from Q15). The inorder traversal of a BST produces elements in sorted order; the kth element popped is the kth smallest. Because the iterator is lazy (advances one step at a time), it stops after exactly k `next()` calls — doing O(h) work to initialize the stack (descend to the leftmost node) and O(k) work to pop k elements. Total: O(h + k). This is strictly better than O(n) (materializing the full sorted array) when k is small and h is small (balanced BST: h = O(log n)).

```js
function kthSmallest(root, k) {
  const iter = new BSTIterator(root);
  let result;
  for (let i = 0; i < k; i++) result = iter.next();
  return result;
}
```

**Q27. "In one sentence each, state the key insight that makes each of the three iterative traversals work."**
A:
- **Preorder**: visiting a node immediately upon popping and pushing right-before-left onto a LIFO stack ensures left subtrees are always processed before right subtrees, replicating NLR order without any deferred work.
- **Inorder**: a `curr` pointer descends left (pushing ancestors to the stack) until it hits null, at which point the stack top is provably the next node in inorder — the leftmost unvisited node in the remaining tree.
- **Postorder**: the `prev` pointer records the last visited node; if the stack top's right child is either null or equals `prev`, both subtrees are confirmed done and the node can be safely visited; otherwise, `curr` must descend into the right subtree first.

## Problem 1 — Binary Tree Inorder Traversal (Iterative)

### Problem
Given the root of a binary tree, return the inorder traversal of its nodes' values.

```
Input:
    1
     \
      2
     /
    3

Output: [1, 3, 2]

Input:  root = null
Output: []

Input:  root = [1]
Output: [1]
```

### Pattern Recognition
Iterative inorder traversal using a stack and a `curr` pointer — the explicit simulation of the recursive call stack, where the stack holds pending ancestors and `curr` tracks the active descent.

### Key Insight
The inorder traversal visits nodes in LNR order, meaning a node can only be visited after its entire left subtree is exhausted. The stack stores "I was here and need to come back to visit this node and then go right" — exactly the suspended state of a recursive call. The two-phase loop (descend-left phase and pop-visit-right phase) replicates this suspension and resumption.

### Approach
Maintain a `stack` and a `curr` pointer initialized to `root`. The outer loop runs while either `curr` is non-null (actively descending) or the stack is non-empty (pending ancestors exist). Inner while: push `curr` and go left until `curr` is null. Then pop, visit, switch `curr` to the popped node's right child.

### Solution

```js
function inorderTraversal(root) {
  const result = [];
  const stack = [];
  let curr = root;

  while (curr !== null || stack.length > 0) {

    // Phase 1: descend as far left as possible, pushing each node
    while (curr !== null) {
      stack.push(curr);  // "suspended call": will visit this node after left subtree
      curr = curr.left;
    }

    // Phase 2: left subtree exhausted — pop, visit, switch to right subtree
    curr = stack.pop();
    result.push(curr.val);  // LNR: visit after left subtree done
    curr = curr.right;      // will descend left again from here (or pop if null)
  }

  return result;
}
```

### Dry Run

```
Tree:   1
         \
          2
         /
        3

curr=1, stack=[]

--- Outer iteration 1 ---
Phase 1 (descend left):
  curr=1: push 1. curr=1.left=null. stack=[1].
  curr=null: inner while exits.
Phase 2 (pop, visit, go right):
  pop 1. result=[1]. curr=1.right=2.

--- Outer iteration 2 ---
Phase 1:
  curr=2: push 2. curr=2.left=3. stack=[2].
  curr=3: push 3. curr=3.left=null. stack=[2,3].
  curr=null: exits.
Phase 2:
  pop 3. result=[1,3]. curr=3.right=null.

--- Outer iteration 3 ---
Phase 1: curr=null → inner while skipped.
Phase 2:
  pop 2. result=[1,3,2]. curr=2.right=null.

--- Check outer condition: curr=null, stack=[] → exit.

Output: [1, 3, 2] ✓
```

### Complexity
- Time: O(n) — each node is pushed once and popped once; O(1) work per node.
- Space: O(h) — the stack holds at most one root-to-leaf path at any time (h nodes). Best case O(log n) for balanced trees; worst case O(n) for skewed trees.

### Edge Cases
- Empty tree (`root = null`): `curr` is null and stack is empty; outer while immediately false; return `[]`.
- Single node (no children): Phase 1 pushes root, Phase 2 pops and visits; `curr` becomes null; loop exits. Returns `[root.val]`.
- Right-skewed tree (no left children): Phase 1 always immediately exits (curr.left is null for every node); Phase 2 pops one node per outer iteration. Stack size is always ≤ 1. Returns nodes in top-down order (which is inorder for a right-skewed tree with no left children — same as preorder here).
- Left-skewed tree (all left children): Phase 1 pushes all n nodes onto the stack before any pop. Stack reaches maximum size n. Nodes visited in reverse order (deepest first). Correct inorder for this degenerate structure.

### Follow-up Questions
- "Implement with Morris Traversal for O(1) space?" → See Q9 — temporarily thread the tree to avoid the explicit stack.
- "Return nodes in reverse inorder (RNL — right, then node, then left)?" → Swap `curr = curr.left` with `curr = curr.right` in Phase 1, and switch `curr` to `curr.left` in Phase 2. Produces descending order for a BST.
- "Stop early after finding a target value?" → Add `if (curr.val === target) return result` after `result.push(curr.val)` in Phase 2 — the lazy traversal naturally supports early termination.

## Problem 2 — Binary Tree Preorder Traversal (Iterative)

### Problem
Given the root of a binary tree, return the preorder traversal of its nodes' values iteratively (without recursion).

```
Input:
    1
   / \
  2   3
 / \
4   5

Output: [1, 2, 4, 5, 3]
```

### Pattern Recognition
Iterative preorder traversal using a single stack — visit a node immediately on pop, then push right child before left child so the left child is processed first (LIFO order).

### Key Insight
Preorder visits the current node before its subtrees — the node is "answered" immediately on encounter, with no deferred work. This makes preorder the simplest iterative traversal: the stack is a pure "queue of subtree roots to visit," and no state about partially-processed nodes needs to be stored. The push-right-before-left rule is the entire algorithm.

### Approach
Initialize `stack = [root]`. While stack is non-empty: pop `node`, visit it, push `node.right` (if exists), push `node.left` (if exists). The left child is pushed last so it is popped (processed) first.

### Solution

```js
function preorderTraversal(root) {
  if (!root) return [];

  const result = [];
  const stack = [root]; // start with root on the stack

  while (stack.length > 0) {
    const node = stack.pop();
    result.push(node.val); // N: visit node immediately on pop

    // Push right first so left is on top (processed first — LIFO)
    if (node.right) stack.push(node.right);
    if (node.left)  stack.push(node.left);
  }

  return result;
}
```

### Dry Run

```
Tree:   1
       / \
      2   3
     / \
    4   5

stack=[1], result=[]

--- Iteration 1 ---
pop 1. result=[1]. push right(3), push left(2). stack=[3,2].

--- Iteration 2 ---
pop 2. result=[1,2]. push right(5), push left(4). stack=[3,5,4].

--- Iteration 3 ---
pop 4. result=[1,2,4]. 4 has no children. stack=[3,5].

--- Iteration 4 ---
pop 5. result=[1,2,4,5]. 5 has no children. stack=[3].

--- Iteration 5 ---
pop 3. result=[1,2,4,5,3]. 3 has no children. stack=[].

Stack empty → exit.

Output: [1, 2, 4, 5, 3] ✓
```

### Complexity
- Time: O(n) — each node pushed once and popped once.
- Space: O(w) where w is the maximum width of the tree (maximum number of nodes at any level). At any moment the stack holds nodes at the "frontier" — at most one full level in the worst case. For a complete binary tree, max width = O(n/2) = O(n). For a skewed tree, stack size is always ≤ 2. This is O(h) for the path-depth argument; O(n) in the worst-case width argument.

### Edge Cases
- `root = null`: early null check returns `[]` before the stack is initialized.
- Leaf node: pop, visit, no children to push, stack remains empty after this node.
- Right-skewed tree: the right child is pushed and immediately available for the next pop; left children are never pushed (they don't exist). Stack size is always ≤ 1. Produces nodes in top-down order.
- Complete binary tree: at each level, the stack briefly holds all nodes from the previous level (worst-case O(n/2) stack size at the leaf level).

### Follow-up Questions
- "Is there a way to implement preorder without using a stack at all?" → Morris Preorder Traversal — create and destroy threads from the inorder predecessor, but visit the node when the thread is *created* (first visit) rather than when destroyed. O(1) space, O(n) time.
- "What changes to get a right-to-left preorder (NRL)?" → Push left before right. Produces: root, rightmost branch, then other subtrees.
- "Modify to return only leaf nodes in preorder order?" → Add `if (!node.left && !node.right) result.push(node.val)` instead of always pushing — same traversal, filtered visit.

## Problem 3 — Binary Tree Postorder Traversal (Iterative)

### Problem
Given the root of a binary tree, return the postorder traversal of its nodes' values iteratively.

```
Input:
    1
   / \
  2   3
 / \
4   5

Output: [4, 5, 2, 3, 1]
```

### Pattern Recognition
Two-stack approach (reverse of NRL preorder) — the insight that LRN (postorder) is the exact reverse of NRL (right-first preorder), allowing an elegant reduction to a simple preorder-variant followed by an array reversal.

### Key Insight
Postorder (LRN) reversed is (NRL) — a preorder traversal that visits the right subtree before the left. Running a right-first preorder (push left before right, so right is on top and processed first) and reversing the collected result gives postorder. This reduces the hard problem (postorder: must defer visiting until both subtrees done) to the easy problem (preorder: visit immediately on pop), with a single reversal at the end.

### Approach
Use the iterative preorder structure but push left before right (to process right first — NRL order). Collect the NRL result. Return it reversed (LRN = postorder).

### Solution

```js
function postorderTraversal(root) {
  if (!root) return [];

  const result = [];
  const stack = [root];

  while (stack.length > 0) {
    const node = stack.pop();
    result.push(node.val); // collect in NRL order (will be reversed to LRN)

    // Push left first so right is on top (right processed first — NRL)
    if (node.left)  stack.push(node.left);
    if (node.right) stack.push(node.right);
  }

  return result.reverse(); // NRL reversed = LRN = postorder
}
```

### Dry Run

```
Tree:   1
       / \
      2   3
     / \
    4   5

stack=[1], result=[]

--- Iteration 1 ---
pop 1. result=[1]. push left(2), push right(3). stack=[2,3].

--- Iteration 2 ---
pop 3. result=[1,3]. 3 has no children. stack=[2].

--- Iteration 3 ---
pop 2. result=[1,3,2]. push left(4), push right(5). stack=[4,5].

--- Iteration 4 ---
pop 5. result=[1,3,2,5]. 5 has no children. stack=[4].

--- Iteration 5 ---
pop 4. result=[1,3,2,5,4]. 4 has no children. stack=[].

result = [1, 3, 2, 5, 4]  (NRL order)
result.reverse() = [4, 5, 2, 3, 1]  (LRN = postorder) ✓
```

### Complexity
- Time: O(n) — each node pushed and popped once; reversal is O(n). Total O(n).
- Space: O(n) — the result array (size n) plus the stack (O(h) at most). The result array is mandatory for the reversal, so this approach inherently uses O(n) space beyond the output.

### Edge Cases
- `root = null`: early return `[]`.
- Single node: pushed, popped, added to result, reversed — `[root.val]`. Same for all three traversals on a single node.
- Left-skewed tree: NRL order visits root, then all right children (none), then descends left — result before reversal is [root, root.left, root.left.left, ...]. Reversed: [..., root.left.left, root.left, root]. This is the correct postorder for a left-skewed tree (deepest first).
- All nodes have both children: the two-stack approach visits NRL cleanly; reversal gives the correct LRN postorder.

### Follow-up Questions
- "Implement postorder without reversing (one-stack with `prev` pointer)?" → See Q8 Approach 2 — peek at stack top, use `prev` to detect whether the right subtree was already visited, then pop and visit when safe. O(1) extra space beyond the stack.
- "What if you need to process nodes in postorder but cannot store all results (streaming output)?" → The one-stack `prev`-pointer approach visits and outputs nodes one at a time without storing all of them — use it instead of the two-stack approach.
- "Why does reversing NRL give postorder specifically?" → NRL visits: Node, Right subtree, Left subtree. Reversing the full sequence: Left subtree (reversed), Right subtree (reversed), Node. Since each subtree's reversed NRL is itself postorder (by induction), the reversal of the full NRL is the full postorder. The reversal "flips" the traversal ordering at every level simultaneously.

## Problem 4 — Construct Binary Tree from Preorder and Inorder Traversal

### Problem
Given two integer arrays `preorder` and `inorder` where `preorder` is the preorder traversal and `inorder` is the inorder traversal of the same binary tree, construct and return the binary tree.

```
Input:  preorder = [3, 9, 20, 15, 7]
        inorder  = [9, 3, 15, 20, 7]
Output: Tree:
            3
           / \
          9  20
             / \
            15   7

Input:  preorder = [-1]
        inorder  = [-1]
Output: Tree: [-1]  (single node)
```

### Pattern Recognition
Recursive tree construction using preorder's root-first property and inorder's left-right split property — each recursive call processes one subtree, with the HashMap enabling O(1) root-position lookup to eliminate the O(n) linear scan per level.

### Key Insight
Two complementary properties: (1) `preorder[preIdx]` is always the root of the current subtree — preorder visits root first. (2) The root's position in `inorder` splits the array into left subtree elements (to the left) and right subtree elements (to the right) — inorder visits left subtree before root. Using a HashMap from value to inorder index makes the split O(1) per recursive call, giving O(n) total instead of O(n²).

### Approach
Build a HashMap: `{inorder[i] → i}` for all i. Maintain a global `preIdx` pointer into `preorder`. Recursive function `build(left, right)` processes the subarray `inorder[left..right]`: the root is `preorder[preIdx++]`; find root's inorder index `mid`; recursively build left subtree from `inorder[left..mid-1]` and right subtree from `inorder[mid+1..right]`. Return the constructed node.

### Solution

```js
function buildTree(preorder, inorder) {
  // HashMap for O(1) inorder index lookup
  const inMap = new Map();
  for (let i = 0; i < inorder.length; i++) {
    inMap.set(inorder[i], i);
  }

  let preIdx = 0; // tracks the next root in preorder

  function build(left, right) {
    // Base case: empty subtree (left boundary exceeds right)
    if (left > right) return null;

    // The next preorder element is the root of this subtree
    const rootVal = preorder[preIdx++];
    const node = new TreeNode(rootVal);

    // Find root in inorder — splits into left and right subtrees
    const mid = inMap.get(rootVal);

    // Build left subtree FIRST (preorder elements for left come next)
    node.left  = build(left, mid - 1);
    // Build right subtree after (remaining preorder elements)
    node.right = build(mid + 1, right);

    return node;
  }

  return build(0, inorder.length - 1);
}
```

### Dry Run

```
preorder = [3, 9, 20, 15, 7]
inorder  = [9, 3, 15, 20,  7]
indices:    0  1   2   3   4

inMap = {9→0, 3→1, 15→2, 20→3, 7→4}
preIdx = 0

build(left=0, right=4):
  rootVal = preorder[0] = 3. preIdx=1. mid = inMap[3] = 1.
  node(3).left  = build(0, 0):   [inorder[0..0] = [9]]
    rootVal = preorder[1] = 9. preIdx=2. mid = inMap[9] = 0.
    node(9).left  = build(0, -1) → null.
    node(9).right = build(1, 0) → null.  [left=1 > right=0 → null]
    return node(9).
  node(3).right = build(2, 4):   [inorder[2..4] = [15, 20, 7]]
    rootVal = preorder[2] = 20. preIdx=3. mid = inMap[20] = 3.
    node(20).left  = build(2, 2):  [inorder[2..2] = [15]]
      rootVal = preorder[3] = 15. preIdx=4. mid = inMap[15] = 2.
      node(15).left  = build(2, 1) → null.
      node(15).right = build(3, 2) → null.
      return node(15).
    node(20).right = build(4, 4):  [inorder[4..4] = [7]]
      rootVal = preorder[4] = 7. preIdx=5. mid = inMap[7] = 4.
      node(7).left  = build(4, 3) → null.
      node(7).right = build(5, 4) → null.
      return node(7).
    return node(20).

    3
   / \
  9  20
     / \
    15   7   ✓
```

### Complexity
- Time: O(n) — each of the n nodes is processed exactly once in the recursion (one `preIdx++` per call); the HashMap makes each lookup O(1). Total O(n).
- Space: O(n) for the HashMap; O(h) for the recursion stack. Overall O(n).

### Edge Cases
- Single node: `preorder = [x]`, `inorder = [x]`. `build(0, 0)`: root = x, mid = 0, left = `build(0, -1)` = null, right = `build(1, 0)` = null. Returns leaf node `x`. Correct.
- Left-skewed tree: each build call has `right = mid - 1` going one step left (because root is always the rightmost element of the inorder subarray). Recursion depth = n. Stack space = O(n).
- Right-skewed tree: each build call has `left = mid + 1` going one step right. Same O(n) recursion depth.
- Duplicate values: the HashMap approach assumes distinct values (as guaranteed by the problem). With duplicates, the HashMap would overwrite entries, causing incorrect splits. The solution must be redesigned using positional information rather than value keys.

### Follow-up Questions
- "Construct from inorder and postorder instead?" → Same logic: postorder's last element is the root (`postIdx` starts at `n-1` and decrements); build right subtree before left (postorder visits right before left in reverse). Swap the `node.left`/`node.right` build order and traverse `postIdx` from right to left.
- "Construct from preorder and postorder?" → Only possible for full binary trees (every node has 0 or 2 children). The second element of the preorder subarray is the left subtree's root; find it in the postorder subarray to determine left subtree size.
- "Iterative construction?" → Maintain a stack of nodes awaiting their right child; parse preorder with inorder boundary checks. Complex — the recursive solution is strongly preferred for clarity.

## Common Bugs Checklist

Before submitting any binary tree traversal solution, verify:

1. **Base case handles both null root AND null children?** — `if (!node) return` (recursive) or `if (!root) return []` (iterative entry point) must handle the empty tree. For recursive solutions, the base case triggers on leaf nodes' null children — without it, the recursion dereferences null.

2. **Iterative inorder: outer loop condition is `curr !== null || stack.length > 0`, not just one?** — Using only `curr !== null` exits prematurely when `curr` is null but the stack still has pending ancestors (e.g., after visiting a node with no right child). Using only `stack.length > 0` fails to enter the loop initially for a non-null `curr` with an empty stack.

3. **Iterative preorder: right pushed before left (not left before right)?** — Pushing left first puts right on top, which is processed first — producing NRL order (right-first preorder), not NLR (correct preorder). Always push right first so left ends up on top.

4. **Postorder two-stack: left pushed before right (not right before left)?** — The NRL traversal (for later reversal) requires right to be on top (processed first), which means pushing left first. Pushing right first gives NLR preorder, whose reversal is RLN — not postorder.

5. **Tree construction (`buildTree`): left subtree built before right?** — `preIdx` (or `postIdx`) advances as nodes are allocated. The left subtree's nodes come immediately after the root in preorder, so `node.left = build(...)` must be called before `node.right = build(...)`. Reversing the order uses the wrong preorder indices for the left subtree.

6. **Morris Traversal: predecessor search terminates on `pred.right === curr`, not just `pred.right === null`?** — The inner while loop must check `pred.right !== null && pred.right !== curr`. Without the second condition, the predecessor search follows the thread created in a previous iteration and loops back to `curr`, running forever.

7. **Iterative postorder (one-stack): using `peek` (not `pop`) before deciding to visit?** — The stack top must be inspected without removal first. Popping immediately loses the ability to push the node back if the right subtree still needs processing. Use `stack[stack.length - 1]` (peek) and only call `stack.pop()` after confirming the node is ready to be visited.

8. **`preIdx` / `postIdx` in tree construction is a shared mutable variable, not a local?** — If `preIdx` is declared inside the recursive function, it resets to 0 on every call — each recursive invocation starts from the beginning of the preorder array. Declare it outside (in the closure) or pass it by reference so all recursive calls share the same advancing index.

**Final Tip:** At the 5 YOE level, interviewers expect you to recognize that the three traversals differ only in *when* the visit step occurs relative to the recursive calls — and that the iterative implementations are mechanical translations of that single difference into explicit stack management. The decisive signal separating deep understanding from memorized templates is being able to say: "Preorder is trivial iteratively because the visit is immediate — no deferred state needed; inorder requires deferring the visit until the left subtree is exhausted, which is why I need a `curr` pointer descending left while the stack holds the suspended ancestors; postorder requires deferring until both subtrees are done, which the two-stack approach handles by reducing it to preorder + reversal." Being able to derive any of the three iterative implementations from this single principle — rather than recalling three separate patterns — is what demonstrates genuine mastery.
