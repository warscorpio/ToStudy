## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is a spanning tree, and what makes it "minimum"?**
A: A **spanning tree** of a connected, undirected graph is a subgraph that includes every vertex exactly once and connects them all with exactly `V - 1` edges (the minimum number of edges needed to keep a connected component of V vertices connected) — forming a tree (connected, acyclic) that "spans" every vertex. A **Minimum Spanning Tree (MST)** is the spanning tree whose total edge weight is as small as possible among all possible spanning trees of the graph. There can be multiple MSTs (when edge weights are not all distinct), but they all share the same minimum total weight.

```
Graph:
  A --1-- B
  |       |
  4       2
  |       |
  C --3-- D

MST: A-B (1) + B-D (2) + C-D (3) = weight 6
(edges A-C (4) and A-D are not included — they'd form cycles or aren't minimum)
```

**Q2. What real-world problems does the MST model?**
A: Any problem of **connecting all nodes at minimum total cost**: network cable layout (connect all offices with minimum cable length), road/pipe infrastructure design (build minimum-cost road network connecting all cities), cluster analysis in machine learning (minimum-cost connections between data points), approximation algorithms for NP-hard problems like the Travelling Salesman Problem (MST provides a 2-approximation). The unifying property is: connect all vertices, use minimum total weight, no cycles (a cycle always contains a redundant edge that adds cost without adding connectivity).

**Q3. What are the two foundational theoretical properties that both Kruskal's and Prim's algorithms rely on?**
A:
1. **Cut Property**: Given any partition of the graph's vertices into two non-empty sets (a "cut"), the minimum-weight edge crossing the cut is always part of some MST. This is why both algorithms can safely include edges greedily — they always pick the lightest edge crossing some relevant cut.
2. **Cycle Property**: Given any cycle in the graph, the maximum-weight edge in that cycle is never in any MST (it can always be replaced by the other edges of the cycle). This is why Kruskal's safely skips edges that would form cycles — they'd be the "heaviest" in that cycle.

Both algorithms are **greedy** — they make locally optimal choices (lightest available safe edge) and the Cut Property guarantees this greedily-chosen edge is globally optimal (part of a true MST), without needing to backtrack or reconsider earlier choices.

**Q4. What assumptions must the input graph satisfy for an MST to be well-defined?**
A: The graph must be **undirected** (edges have no direction), **connected** (every vertex is reachable from every other), and **weighted** (edges have numeric costs). For a disconnected graph, no spanning tree exists — instead, you'd compute a **Minimum Spanning Forest** (one MST per connected component, handled by simply running either algorithm and collecting the resulting edges). If edge weights are not all distinct, multiple MSTs may exist but the algorithms still correctly find one.

### Section 2: Kruskal's Algorithm

**Q5. How does Kruskal's algorithm work, and what data structure makes it efficient?**
A: Kruskal's algorithm:
1. Sort all edges by weight (ascending).
2. Initialize each vertex as its own separate component (using a **Union-Find / Disjoint Set Union** structure).
3. Iterate through edges in sorted order: for each edge `(u, v, weight)`, if `u` and `v` are in different components (checked via `find`), include this edge in the MST and merge their components (via `union`). Skip the edge if `u` and `v` are already in the same component (including it would form a cycle).
4. Stop when `V - 1` edges have been included (a complete spanning tree) or all edges have been processed.

The **Union-Find (Disjoint Set Union)** data structure is the key enabler — it provides near-O(1) amortized `find` (which component does a vertex belong to?) and `union` (merge two components) operations, making the cycle-check and merge at each edge essentially free beyond the sorting step.

```js
class UnionFind {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank = new Array(n).fill(0);
  }

  find(x) {
    if (this.parent[x] !== x) {
      this.parent[x] = this.find(this.parent[x]); // path compression
    }
    return this.parent[x];
  }

  union(x, y) {
    const px = this.find(x), py = this.find(y);
    if (px === py) return false; // already same component — would form cycle

    // union by rank: attach smaller-rank tree under larger-rank root
    if (this.rank[px] < this.rank[py]) this.parent[px] = py;
    else if (this.rank[px] > this.rank[py]) this.parent[py] = px;
    else { this.parent[py] = px; this.rank[px]++; }

    return true; // successfully merged
  }
}

function kruskal(numVertices, edges) {
  edges.sort((a, b) => a[2] - b[2]); // sort by weight
  const uf = new UnionFind(numVertices);
  const mst = [];
  let totalWeight = 0;

  for (const [u, v, weight] of edges) {
    if (uf.union(u, v)) { // returns true only if they were in different components
      mst.push([u, v, weight]);
      totalWeight += weight;
      if (mst.length === numVertices - 1) break; // MST complete
    }
  }

  return { mst, totalWeight };
}
```

**Q6. What is the time and space complexity of Kruskal's algorithm?**
A: Time: **O(E log E)** dominated by the edge sorting step (where E = number of edges); the Union-Find operations across all edges add only O(E α(V)) where α is the inverse Ackermann function (effectively O(1) per operation for all practical inputs), which is negligible compared to sorting. Since E ≤ V², `O(E log E)` and `O(E log V)` are equivalent here. Space: **O(V + E)** — the Union-Find structure (O(V)) plus the sorted edge list (O(E)).

**Q7. What is the Union-Find "path compression" optimization, and why does it matter?**
A: Without path compression, repeated `find` calls on a deep chain of nodes (caused by a series of `union` operations forming a linear chain) each take O(depth) time, potentially O(V) per `find` in the worst case. **Path compression** flattens the tree during `find`: after finding the root, it directly sets every node along the traversed path to point to the root, so future `find` calls on those nodes are O(1). Combined with **union by rank** (always attach the shallower tree under the deeper root, preventing extreme tree growth), these two optimizations together achieve an amortized time per operation of O(α(V)) — effectively constant for all practical purposes.

**Q8. When is Kruskal's algorithm particularly well-suited compared to Prim's?**
A: Kruskal's is well-suited for **sparse graphs** (where E is close to V, not V²) — because its complexity is O(E log E), a small E makes sorting cheap. It's also naturally suited when the **edge list is already sorted or nearly sorted** (avoiding or reducing the sorting cost), and when the graph might be disconnected (Kruskal's naturally computes a Minimum Spanning Forest — it simply processes all edges and whatever MST edges are found form the forest's components, without needing any modification for the disconnected case).

### Section 3: Prim's Algorithm

**Q9. How does Prim's algorithm work, conceptually and mechanically?**
A: Prim's algorithm grows the MST one vertex at a time from a starting vertex:
1. Initialize with any single vertex in the MST. All other vertices are "outside" the MST.
2. Among all edges with exactly one endpoint inside the MST and one outside, pick the minimum-weight one.
3. Add that edge and its outside endpoint to the MST.
4. Repeat until all vertices have been added to the MST.

The algorithm maintains a "frontier" of candidate edges (edges crossing the MST boundary), always picking the cheapest one — this is the Cut Property in action at every step: the cut is "MST vertices vs. non-MST vertices," and the minimum edge crossing that cut is guaranteed to belong to a valid MST.

**Q10. How does a min-heap (priority queue) enable efficient Prim's algorithm?**
A: A naive implementation of Prim's (checking all remaining edges at every step to find the minimum) takes O(V²) time. Using a min-heap: maintain a priority queue of `(weight, vertex)` pairs representing the minimum-weight edge currently known to connect each not-yet-included vertex to the existing MST. When a vertex is added to the MST, push all its adjacent edges to not-yet-included vertices into the heap. The heap always surfaces the globally-minimum crossing edge in O(log V) per extraction.

```js
function prim(numVertices, adjList, start = 0) {
  const inMST = new Array(numVertices).fill(false);
  const minCost = new Array(numVertices).fill(Infinity);
  const parent = new Array(numVertices).fill(-1);

  minCost[start] = 0;

  // min-heap: [cost, vertex]
  // (using a simple sorted approach here for clarity; production uses a proper heap)
  const minHeap = [[0, start]];
  const mst = [];
  let totalWeight = 0;

  while (minHeap.length > 0) {
    minHeap.sort((a, b) => a[0] - b[0]); // in a real solution: proper min-heap extraction
    const [cost, u] = minHeap.shift();

    if (inMST[u]) continue; // already included via a cheaper edge found earlier
    inMST[u] = true;
    totalWeight += cost;

    if (parent[u] !== -1) {
      mst.push([parent[u], u, cost]);
    }

    for (const [v, weight] of adjList[u]) {
      if (!inMST[v] && weight < minCost[v]) {
        minCost[v] = weight;
        parent[v] = u;
        minHeap.push([weight, v]);
      }
    }
  }

  return { mst, totalWeight };
}
```

**Q11. What is the time complexity of Prim's algorithm with a binary min-heap vs. a Fibonacci heap?**
A:
- **Binary min-heap**: O((V + E) log V) — V extractions from the heap each costing O(log V), plus E edge relaxations each potentially pushing to the heap at O(log V). For dense graphs (E ≈ V²), this is O(V² log V).
- **Fibonacci heap**: O(E + V log V) — a theoretical improvement where decrease-key operations are O(1) amortized instead of O(log V), reducing the total to this better bound. Fibonacci heaps are rarely used in practice (high constant factors, complex implementation) but are important to know theoretically as the optimal complexity for Prim's.
- **Simple adjacency matrix + linear scan**: O(V²) — for dense graphs where E ≈ V², this actually beats the binary heap approach and is a perfectly valid Prim's implementation.

**Q12. When is Prim's algorithm particularly well-suited compared to Kruskal's?**
A: Prim's is well-suited for **dense graphs** (where E is close to V²) — with a simple O(V²) adjacency-matrix implementation, it outperforms Kruskal's O(E log E) = O(V² log V) for dense graphs. It's also naturally suited when the graph is given as an **adjacency matrix** (common in competitive programming and certain applications), and when you need to grow the MST from a **specific starting vertex** (Prim's naturally does this, while Kruskal's global edge-sorting has no concept of a start vertex).

### Section 4: Comparing Kruskal's vs. Prim's

**Q13. What is the most important structural difference between how Kruskal's and Prim's build the MST?**
A: Kruskal's builds the MST **globally edge-by-edge** — it doesn't maintain a connected MST-so-far; at intermediate steps, the MST edges collected so far may form a disconnected forest, and the algorithm gradually connects these forest components by adding cross-component edges. Prim's builds the MST **locally vertex-by-vertex** — it always maintains a single connected component (the "growing MST"), expanding it one vertex at a time by adding the cheapest edge crossing the boundary. Both correctly produce a valid MST, but the internal intermediate states look very different.

**Q14. Do Kruskal's and Prim's always produce the SAME MST, or can they differ?**
A: If all edge weights are **distinct**, there is exactly one unique MST, and both algorithms must produce it. If some edges share the same weight, multiple valid MSTs exist — Kruskal's and Prim's may produce **different but equally valid** MSTs (with the same total weight), depending on tie-breaking choices made during sorting (Kruskal's) or priority queue ordering (Prim's). Both are correct; the problem statement usually only requires "find AN MST," not "find THE specific MST."

**Q15. Can either algorithm handle negative edge weights?**
A: Yes — both Kruskal's and Prim's work correctly with negative edge weights. This is in sharp contrast to algorithms like Dijkstra's shortest path algorithm, which fails on negative edges. MST algorithms only care about **relative ordering of edge weights** (pick the minimum), not about the absolute values or path sums — negative edges simply mean those edges are strongly "preferred" and will likely appear in the MST.

### Section 5: Union-Find Deep Dive

**Q16. What are the core Union-Find operations, and what are their complexities with and without optimizations?**
A:
- **`find(x)`**: returns the root (representative) of the set containing `x`. Without path compression: O(n) worst case (degenerate linear chain). With path compression: O(α(n)) amortized.
- **`union(x, y)`**: merges the sets containing `x` and `y`. Without union by rank: O(n) worst case. With union by rank: O(α(n)) amortized.
- **`isConnected(x, y)`**: equivalent to `find(x) === find(y)` — same complexity as `find`.

With both path compression and union by rank: O(α(n)) amortized per operation, where α is the inverse Ackermann function — grows so slowly that it's effectively O(1) for all input sizes encountered in practice (α(n) ≤ 4 for n ≤ 2^65536).

**Q17. What is "union by rank" and why is it used alongside path compression?**
A: **Union by rank** always attaches the tree with the smaller rank (approximate depth) under the root of the tree with the larger rank, preventing the formation of very deep trees. The rank of a tree increases only when two trees of equal rank are merged (one rank step up). Without this, naive union could create a linked-list chain with O(n) `find` depth even after path compression helps individual paths — union by rank ensures the maximum tree depth is O(log n) before path compression even kicks in, and together with path compression achieves the near-constant O(α(n)) amortized bound.

**Q18. Can Union-Find be used for problems beyond MST computation?**
A: Yes — Union-Find is a general-purpose "dynamic connectivity" structure, useful wherever you need to efficiently track which elements belong to the same group and merge groups:
- **MST construction** (Kruskal's — the primary use case covered here)
- **Connected components** in an undirected graph (incrementally as edges are added)
- **Cycle detection** in an undirected graph (if `union(u, v)` returns false, edge u-v would create a cycle)
- **Social network friends/groups** (are two people in the same friend group?)
- **Percolation problems** (physics/science simulations of connected paths)
- **Dynamic graph problems** where edges are added (but not removed — Union-Find doesn't support edge deletion without significant modification)

### Section 6: Scenario / Interview-Style Questions

**Q19. "You're building a network connecting n offices at minimum cost. Some offices are already connected by existing cables. How do you model and solve this?"**
A: Model offices as vertices and potential connections as weighted edges (cost to run each cable). Existing connections are free edges (weight 0) — include them directly in the Union-Find structure's initial state (call `union` on each existing connection before processing any new edges). Then run Kruskal's algorithm on the remaining candidate edges, which naturally builds on top of the already-merged components representing existing cables. The resulting MST gives the minimum-cost set of new cables to add.

**Q20. "A teammate implements Kruskal's algorithm but forgets to check whether two vertices are in the same component before adding an edge, just accepting the first V-1 edges in sorted order. What's wrong?"**
A: Without the cycle-check, the algorithm would add the V-1 cheapest edges globally, regardless of whether any of them form cycles — the result could be a multigraph with cycles (not a tree), specifically failing the "no cycle" property of a spanning tree. For example, if the two cheapest edges happen to connect the same pair of components (forming a cycle), both get added under this broken approach, consuming one of the V-1 edge "slots" on a useless duplicate connection while missing a different edge needed to connect some other pair of components. The Union-Find check (`union` returning false when two vertices are already in the same component) is exactly the guard that prevents this.

**Q21. "How would you find the MAXIMUM spanning tree instead of the minimum spanning tree, using these algorithms?"**
A: Two simple modifications work: (1) for Kruskal's, sort edges in **descending** order instead of ascending (greedily picking the heaviest safe edge at each step), or equivalently, negate all edge weights and run the standard minimum algorithm; (2) for Prim's, use a **max-heap** instead of a min-heap. Both approaches correctly produce a spanning tree with maximum total weight — the Cut Property symmetrically applies to maximum spanning trees (the maximum-weight edge crossing any cut belongs to some maximum spanning tree).

**Q22. "How does the MST relate to the solution of the Travelling Salesman Problem (TSP), and why is it useful even though TSP is NP-hard?"**
A: The MST provides a **lower bound** and a **2-approximation** for the TSP: the MST's weight ≤ the optimal TSP tour's weight (since any TSP tour contains a Hamiltonian path that is itself a spanning tree minus one edge, so it must weigh at least as much as the MST). The classical 2-approximation algorithm for TSP on metric spaces is: (1) compute the MST, (2) double every MST edge to make an Eulerian circuit (which then visits every vertex), (3) shortcut the circuit to avoid revisiting vertices — the result is a valid tour costing at most 2× the MST weight, thus at most 2× the optimal TSP tour. This makes MST computation a practically important subroutine even for problems far beyond simple network connectivity.

## Problem 1 — Minimum Cost to Connect All Points (Prim's)

### Problem
You are given an array `points` where `points[i] = [xi, yi]`. The cost to connect two points is their Manhattan distance: `|xi - xj| + |yi - yj|`. Return the minimum cost to make all points connected (i.e., the total weight of the MST).

```
Input:  points = [[0,0],[2,2],[3,10],[5,2],[7,0]]
Output: 20

(MST connects all 5 points with 4 edges totaling Manhattan distance 20)
```

### Pattern Recognition
MST on a complete graph (every pair of points is connected by an edge with weight = Manhattan distance) — Prim's O(V²) adjacency-based approach is ideal here since the graph is dense (E = V²/2) and edge weights are computed on-the-fly rather than pre-stored.

### Key Insight
For a dense complete graph, Prim's with an explicit `minDist[]` array (tracking the minimum-cost edge from each not-yet-included point to the current MST) and a linear scan to find the next minimum is O(V²) total — **better than Kruskal's O(E log E) = O(V² log V)** for this specific input shape.

### Approach
Initialize `minDist[]` with Infinity, set `minDist[0] = 0` (start from point 0). Maintain an `inMST[]` boolean array. At each of V iterations: find the not-yet-included point with minimum `minDist` (linear scan), add it to the MST, and update `minDist` for all remaining points based on the newly-added point's distances.

### Solution

```js
function minCostConnectPoints(points) {
  const n = points.length;
  const inMST = new Array(n).fill(false);
  const minDist = new Array(n).fill(Infinity);
  minDist[0] = 0;

  let totalCost = 0;

  for (let iter = 0; iter < n; iter++) {
    // find the not-yet-included point with minimum distance to the current MST
    let u = -1;
    for (let i = 0; i < n; i++) {
      if (!inMST[i] && (u === -1 || minDist[i] < minDist[u])) {
        u = i;
      }
    }

    inMST[u] = true;
    totalCost += minDist[u];

    // update minDist for all remaining points based on the newly-added point u
    for (let v = 0; v < n; v++) {
      if (!inMST[v]) {
        const dist = Math.abs(points[u][0] - points[v][0]) +
                     Math.abs(points[u][1] - points[v][1]);
        if (dist < minDist[v]) {
          minDist[v] = dist;
        }
      }
    }
  }

  return totalCost;
}
```

### Complexity
- Time: O(V²) — V iterations of the outer loop, each doing a O(V) linear scan for the minimum plus an O(V) update pass.
- Space: O(V) — the `inMST` and `minDist` arrays; no explicit edge list needed since distances are computed on-the-fly.

### Edge Cases
- Single point: `n=1`, the outer loop runs once (adds point 0 with cost 0), returns 0.
- Two points: one edge connecting them; cost = their Manhattan distance.
- All points at the same location: all pairwise distances are 0; total cost is 0.

### Follow-up Questions
- "When would you use Kruskal's instead here?" → If the graph were sparse (not a complete graph), Kruskal's sorting-based approach would be more efficient since E << V² — but for this specific complete-graph problem structure, Prim's O(V²) is optimal.
- "What if the cost metric were Euclidean distance instead of Manhattan distance?" → Change the distance formula; the MST algorithm itself is identical.

## Problem 2 — Minimum Spanning Tree via Kruskal's Algorithm

### Problem
Given `n` vertices (0 to n-1) and a list of weighted undirected edges, find the total weight of the minimum spanning tree. Return -1 if the graph is not connected (no spanning tree exists).

```
Input:  n = 4, edges = [[0,1,10],[0,2,6],[0,3,5],[1,3,15],[2,3,4]]
Output: 19

MST edges: (2,3,4), (0,3,5), (0,1,10) — total weight 19
```

### Pattern Recognition
Classic Kruskal's — sort edges by weight, use Union-Find to detect/avoid cycles, greedily include the cheapest safe edges until V-1 are collected.

### Key Insight
Every edge considered in sorted order is the minimum-weight edge between two not-yet-connected components at that moment (by the Cut Property), making greedily including it provably correct. Union-Find's near-O(1) per-operation cost means the bottleneck is purely the sort.

### Approach
Sort edges ascending by weight. Initialize Union-Find with n individual components. Iterate: for each edge `(u, v, w)`, if `find(u) !== find(v)` (different components), include it in the MST, call `union(u, v)`, accumulate weight. Stop after V-1 edges. If fewer than V-1 edges were collected, the graph is disconnected.

### Solution

```js
class UnionFind {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank = new Array(n).fill(0);
    this.components = n;
  }

  find(x) {
    if (this.parent[x] !== x) {
      this.parent[x] = this.find(this.parent[x]);
    }
    return this.parent[x];
  }

  union(x, y) {
    const px = this.find(x), py = this.find(y);
    if (px === py) return false;

    if (this.rank[px] < this.rank[py]) this.parent[px] = py;
    else if (this.rank[px] > this.rank[py]) this.parent[py] = px;
    else { this.parent[py] = px; this.rank[px]++; }

    this.components--;
    return true;
  }
}

function minimumSpanningTree(n, edges) {
  edges.sort((a, b) => a[2] - b[2]); // sort by weight ascending
  const uf = new UnionFind(n);
  let totalWeight = 0;
  let edgesUsed = 0;

  for (const [u, v, weight] of edges) {
    if (uf.union(u, v)) {
      totalWeight += weight;
      edgesUsed++;
      if (edgesUsed === n - 1) break; // MST is complete
    }
  }

  return edgesUsed === n - 1 ? totalWeight : -1;
}
```

### Complexity
- Time: O(E log E) — sorting dominates; Union-Find operations add O(E α(V)) ≈ O(E).
- Space: O(V + E) — Union-Find arrays plus sorted edge list.

### Edge Cases
- Disconnected graph: after processing all edges, `edgesUsed < n-1` — correctly returns -1.
- Graph with only one vertex (n=1): no edges needed, `edgesUsed=0=n-1=0` — returns `totalWeight=0`. (Edge case: need to handle n=1 carefully since n-1=0 and the loop body may never execute, but the condition `edgesUsed === n-1` would be `0 === 0` which is true, so returns 0 correctly.)
- Edges with duplicate weights: sort is stable enough for correctness (any tie-breaking is valid since all MSTs with the same weight are equally valid answers).
- Graph already forms a tree (exactly n-1 edges): every edge passes the Union-Find check (none form a cycle), all get included.

### Follow-up Questions
- "What if you also need the actual MST edges, not just the total weight?" → Collect `[u, v, weight]` into a `mst` array every time `union` returns `true`; the same algorithm otherwise.
- "How would you modify this to find the minimum spanning FOREST for a disconnected graph?" → Simply remove the disconnection check — the algorithm naturally produces the MST for each connected component, and the collected edges form the minimum spanning forest.

## Problem 3 — Find the City With the Smallest Number of Reachable Cities (MST Application: Detecting Network Bottlenecks)

### Problem
Given `n` cities and `edges` where `edges[i] = [from, to, weight]` represents a bidirectional road, and a `distanceThreshold`, find the city with the smallest number of other cities reachable within `distanceThreshold` distance (using shortest paths, not MST edges only). Return the city with the fewest reachable cities; break ties by returning the city with the greatest index.

```
Input:  n=4, edges=[[0,1,3],[1,2,1],[1,3,4],[2,3,1]], distanceThreshold=4
Output: 3

Shortest distances from each city to all others:
City 0: 0→1=3, 0→2=4, 0→3=5. Within threshold 4: {1,2} → 2 cities
City 1: 1→0=3, 1→2=1, 1→3=2. Within threshold 4: {0,2,3} → 3 cities
City 2: 2→1=1, 2→0=4, 2→3=1. Within threshold 4: {0,1,3} → 3 cities
City 3: 3→2=1, 3→1=2, 3→0=5. Within threshold 4: {1,2} → 2 cities
Tie between cities 0 and 3, return greatest index → 3
```

### Pattern Recognition
This specific problem uses **all-pairs shortest paths** (Floyd-Warshall), not MST directly — it's included here as an example of how weighted graph problems can superficially resemble MST problems but actually require a different approach, demonstrating the importance of recognizing which tool applies.

### Key Insight
MST finds the minimum-cost tree to **connect** all cities, but this problem asks about **reachability within a distance constraint** using shortest paths — these are fundamentally different questions. The MST's edges don't capture all shortest paths (they only keep the tree structure), so Floyd-Warshall (computing actual shortest paths between all pairs) is correct here.

### Approach
Run Floyd-Warshall to compute all-pairs shortest distances. For each city, count how many other cities are reachable within `distanceThreshold`. Return the city with the fewest reachable others (ties broken by largest index).

### Solution

```js
function findTheCity(n, edges, distanceThreshold) {
  // initialize distance matrix
  const dist = Array.from({ length: n }, (_, i) =>
    Array.from({ length: n }, (_, j) => (i === j ? 0 : Infinity))
  );

  for (const [u, v, w] of edges) {
    dist[u][v] = w;
    dist[v][u] = w;
  }

  // Floyd-Warshall: O(V³)
  for (let k = 0; k < n; k++) {
    for (let i = 0; i < n; i++) {
      for (let j = 0; j < n; j++) {
        if (dist[i][k] + dist[k][j] < dist[i][j]) {
          dist[i][j] = dist[i][k] + dist[k][j];
        }
      }
    }
  }

  let bestCity = -1, bestCount = Infinity;
  for (let i = 0; i < n; i++) {
    let count = 0;
    for (let j = 0; j < n; j++) {
      if (i !== j && dist[i][j] <= distanceThreshold) count++;
    }
    if (count <= bestCount) { // <= to prefer larger index on tie
      bestCount = count;
      bestCity = i;
    }
  }

  return bestCity;
}
```

### Dry Run

```
n=4, edges=[[0,1,3],[1,2,1],[1,3,4],[2,3,1]], distanceThreshold=4

Initial dist matrix (Inf = unreachable before Floyd-Warshall):
     0    1    2    3
0  [ 0,   3, Inf, Inf]
1  [ 3,   0,   1,   4]
2  [Inf,  1,   0,   1]
3  [Inf,  4,   1,   0]

After Floyd-Warshall (k=0,1,2,3 passes, updates shortest paths):
     0    1    2    3
0  [ 0,   3,   4,   5]
1  [ 3,   0,   1,   2]
2  [ 4,   1,   0,   1]
3  [ 5,   2,   1,   0]

Count cities within threshold 4 per city:
City 0: {1:3✓, 2:4✓, 3:5✗} → 2 cities. bestCount=2, bestCity=0
City 1: {0:3✓, 2:1✓, 3:2✓} → 3 cities. 3>2 → no update
City 2: {0:4✓, 1:1✓, 3:1✓} → 3 cities. 3>2 → no update
City 3: {0:5✗, 1:2✓, 2:1✓} → 2 cities. 2<=2 (tie) → bestCity=3 (largest index wins)

Result: 3 ✓
```

### Complexity
- Time: O(V³) for Floyd-Warshall + O(V²) for the count pass = O(V³).
- Space: O(V²) for the distance matrix.

### Edge Cases
- No edges at all: all inter-city distances remain Infinity (> threshold), every city has 0 reachable others, the greatest-index city (n-1) is returned.
- All cities directly connected: after Floyd-Warshall, direct edge weights dominate; standard computation applies.

### Follow-up Questions
- "What if the graph were directed?" → Floyd-Warshall works equally well for directed graphs with no modifications.
- "When would Kruskal's or Prim's be relevant to a similar problem?" → If the question were "build a minimum-cost network so all cities can reach each other" (minimum connectivity, not minimum-distance counting), then MST would apply directly.

## Problem 4 — Connecting Cities with Minimum Cost (Union-Find Application: Detecting Connected Components)

### Problem
Given `n` cities and `connections` where `connections[i] = [city1, city2, cost]`, find the minimum cost to connect all cities (directly or indirectly), or return -1 if it's impossible.

```
Input:  n=3, connections=[[1,2,5],[1,3,6],[2,3,1]]
Output: 6

MST: connect 2-3 (cost 1) and 1-2 (cost 5) = total 6.
Edge 1-3 (cost 6) is skipped since 1 and 3 are already connected via 2.
```

### Pattern Recognition
Direct Kruskal's MST application — "minimum cost to connect all nodes" is exactly the MST problem, with the additional possible output of -1 when the graph is disconnected.

### Key Insight
Kruskal's naturally handles both the "find the minimum spanning tree" core problem AND the "impossible if disconnected" case — if fewer than n-1 edges are added by the time all edges are processed, the graph had disconnected components that no edge could bridge.

### Approach
Sort connections by cost. Use Union-Find with n+1 capacity (cities are 1-indexed). Greedily add cheapest edges that don't form cycles until n-1 edges are collected or all edges are processed.

### Solution

```js
function minimumCost(n, connections) {
  class UnionFind {
    constructor(size) {
      this.parent = Array.from({ length: size + 1 }, (_, i) => i);
      this.rank = new Array(size + 1).fill(0);
    }

    find(x) {
      if (this.parent[x] !== x) this.parent[x] = this.find(this.parent[x]);
      return this.parent[x];
    }

    union(x, y) {
      const px = this.find(x), py = this.find(y);
      if (px === py) return false;
      if (this.rank[px] < this.rank[py]) this.parent[px] = py;
      else if (this.rank[px] > this.rank[py]) this.parent[py] = px;
      else { this.parent[py] = px; this.rank[px]++; }
      return true;
    }
  }

  connections.sort((a, b) => a[2] - b[2]);
  const uf = new UnionFind(n);
  let totalCost = 0, edgesUsed = 0;

  for (const [city1, city2, cost] of connections) {
    if (uf.union(city1, city2)) {
      totalCost += cost;
      edgesUsed++;
      if (edgesUsed === n - 1) return totalCost; // MST complete
    }
  }

  return -1; // not all cities could be connected
}
```

### Dry Run

```
n=3, connections=[[1,2,5],[1,3,6],[2,3,1]]

Sort by cost: [[2,3,1],[1,2,5],[1,3,6]]
UnionFind: parent=[0,1,2,3], rank=[0,0,0,0]

Edge (2,3,1): find(2)=2, find(3)=3. Different → union!
  parent=[0,1,2,2] (or 3's parent=2), rank[2]=1
  totalCost=1, edgesUsed=1

Edge (1,2,5): find(1)=1, find(2)=2. Different → union!
  rank[1]=0 < rank[2]=1 → parent[1]=2
  parent=[0,2,2,2]
  totalCost=6, edgesUsed=2

edgesUsed(2)===n-1(2) → return totalCost=6 ✓

(Edge (1,3,6) was never even examined — early exit after MST completion)
```

### Complexity
- Time: O(E log E) — sorting dominates.
- Space: O(V) — Union-Find arrays.

### Edge Cases
- Only one city (n=1): no edges needed, `edgesUsed=0=n-1=0`, early exit returns `totalCost=0` immediately (or the loop processes nothing and returns -1... careful: `edgesUsed === n-1` when n=1 means `0===0` is true on the first iteration before any edges are processed — add a special case or handle via the `break` logic carefully).
- Impossible to connect (disconnected components): loop exhausts all edges, `edgesUsed < n-1`, correctly returns -1.
- Graph already forming a tree (E = n-1, all edges needed): all edges pass the cycle check, all are included.

### Follow-up Questions
- "What if you need to minimize the MAXIMUM edge weight in the spanning tree, not the total weight?" → This is the "minimax spanning tree" or "bottleneck spanning tree" problem — for this specific objective, the MST (minimizing total weight) happens to also minimize the maximum edge weight, so the same Kruskal's algorithm applies.
- "What if some city pairs have multiple roads between them?" → Kruskal's handles this naturally — duplicate/parallel edges are simply all included in the edge list; the cheapest one connecting two otherwise-disconnected components will be picked first, and any subsequent parallel edges between the same pair will be skipped (since `union` returns false after the first merge).

## Quick Reference — Pattern Decision Tree

```
Does the problem involve connecting all nodes of a weighted undirected graph at minimum total cost?
│
├── CONFIRM IT'S AN MST PROBLEM:
│   ├── All vertices must be connected? ✓
│   ├── No cycles (spanning tree)? ✓
│   └── Minimize total edge weight? ✓
│   (If "shortest path between specific nodes" → use Dijkstra's instead, not MST)
│
├── WHICH ALGORITHM TO USE?
│   │
│   ├── GRAPH IS SPARSE (E close to V, few edges)?
│   │   └── KRUSKAL'S — sort edges O(E log E), Union-Find for cycle check
│   │       also preferred when edges are pre-sorted, or graph may be disconnected
│   │
│   ├── GRAPH IS DENSE (E close to V², many edges) OR given as adjacency matrix?
│   │   └── PRIM'S with O(V²) linear-scan — beats Kruskal's O(E log E) = O(V² log V) here
│   │       also preferred when starting from a specific vertex, or for complete graphs
│   │
│   └── NEITHER IS CLEARLY DOMINANT (medium density)?
│       └── Either works; Kruskal's is often simpler to implement and explain in interviews
│
├── VARIANTS:
│   ├── Maximum spanning tree → sort descending (Kruskal's) or use max-heap (Prim's)
│   ├── MST with some edges pre-required → include required edges in Union-Find first
│   ├── Disconnected graph → MST algorithm on each component = Minimum Spanning Forest
│   └── Need actual edges (not just total weight) → collect [u,v,w] on each union/add
│
└── RELATED BUT DIFFERENT PROBLEMS:
    ├── Shortest path (single source) → Dijkstra's, Bellman-Ford
    ├── All-pairs shortest paths → Floyd-Warshall
    ├── Connected components (unweighted) → BFS/DFS or Union-Find without weights
    └── Cycle detection in directed graph → Topological sort / DFS coloring
```

## Common Bugs Checklist

Before submitting any MST / Kruskal's / Prim's solution, verify:

1. **Kruskal's: edges sorted by weight BEFORE starting the Union-Find loop?** — Processing edges in unsorted order destroys the greedy correctness guarantee — the algorithm might include heavier edges before cheaper ones become eligible, producing a non-minimum spanning tree.

2. **Kruskal's: Union-Find's `union` return value checked (returns `false` when already in the same component)?** — Failing to skip edges that would form cycles silently produces a result with cycles, not a valid spanning tree.

3. **Kruskal's: connectivity check at the end (`edgesUsed === n-1`) to detect a disconnected input graph?** — Without this check, a disconnected graph silently returns an incomplete (partial) spanning forest's weight as if it were a valid full MST.

4. **Prim's with min-heap: the `inMST` check on dequeue (skip if already included)?** — A vertex can be pushed into the heap multiple times (with different costs, as shorter paths are discovered via different neighbors) — without checking `inMST[u]` at dequeue time, the same vertex gets processed multiple times, potentially adding its cost multiple times and incorrectly updating neighbors redundantly.

5. **Union-Find path compression: recursive `find` with reassignment (`this.parent[x] = this.find(this.parent[x])`) applied EVERY time, not just once?** — Applying path compression only on the first call misses the ongoing optimization for future calls; it should be applied on every `find` call.

6. **1-indexed vs 0-indexed vertices: Union-Find initialized with the correct size?** — A common off-by-one error is initializing Union-Find with size `n` when vertices are labeled `1` to `n` (needing size `n+1` to safely use index `n`); initializing with `n` causes an out-of-bounds on vertex n's entry.

7. **Prim's O(V²) variant: `minDist` updated for ALL remaining (not-yet-included) neighbors, not just immediate neighbors?** — Since the graph is complete (all points connected), all `n` points must be checked against the newly added point each time; restricting to "immediate adjacency list neighbors" only applies for sparse-graph Prim's using an adjacency list representation.

8. **Maximum spanning tree variant: comparison direction flipped throughout (descending sort for Kruskal's, or max-heap for Prim's)?** — A single remaining `<` comparison in the wrong direction silently produces a minimum spanning tree instead of a maximum one.

---

**Final Tip:** At the 5 YOE level, interviewers expect immediate recognition that "connect all nodes at minimum total cost" maps to MST, followed by a clear, justified choice between Kruskal's and Prim's based on graph density — and specifically, Prim's O(V²) for dense/complete graphs (like the "minimum cost to connect all points" problem), Kruskal's O(E log E) for sparse graphs. The Union-Find implementation — with both path compression and union by rank — is a load-bearing part of the Kruskal's answer: being able to write it correctly and explain why both optimizations matter is what separates a complete answer from a partial one. For Prim's, clearly articulating the "frontier of minimum crossing edges" mental model, and why the `inMST` check at dequeue time is necessary when using a heap, demonstrates the same depth of understanding.
