## Topic A: Graph Cycle Detection Fundamentals

### Section A1: Fundamentals

**Q1. What is a cycle in a graph, and why does detecting one matter?**
A: A cycle is a path that starts and ends at the same vertex, visiting at least one edge — a closed loop in the graph. In a directed graph, the edges must be followed in their specified direction; in an undirected graph, any edge can be traversed in either direction. Cycle detection matters because:

- **Topological sort** requires a DAG (directed acyclic graph) — a cycle makes topological ordering impossible.
- **Deadlock detection** in operating systems models resource dependencies as a directed graph; a cycle = deadlock.
- **Dependency resolution** (package managers, build systems) fails on circular dependencies.
- **Shortest path algorithms** like Bellman-Ford detect negative-weight cycles; Dijkstra assumes no negative cycles.
- **Course scheduling problems** reduce directly to "is this prerequisite graph a DAG?" — which is cycle detection.

```
Undirected cycle:          Directed cycle:
1 — 2                      1 → 2
|   |                      ↑   ↓
4 — 3                      4 ← 3
(cycle: 1-2-3-4-1)         (cycle: 1→2→3→4→1)
```

**Q2. What are the four primary algorithms for cycle detection, and what structure does each target?**
A: The four algorithms, matched to their target structure:

- **DFS with 3-color marking** (WHITE/GRAY/BLACK): directed graphs. Detects back edges — edges from a node to an ancestor currently on the DFS recursion stack. A back edge proves a directed cycle.
- **DFS with parent tracking**: undirected graphs. Detects back edges that do not lead to the immediate parent (distinguishes a real cycle from the trivial "return along the same edge" traversal).
- **Union-Find (Disjoint Set Union)**: undirected graphs only. Processes edges one at a time; a cycle is detected when both endpoints of an edge already belong to the same connected component.
- **BFS / Kahn's algorithm (topological sort)**: directed graphs. A cycle is detected when the BFS terminates with fewer than n nodes processed — the unprocessed nodes form cycles.

```
Directed graph  → DFS 3-color  OR  Kahn's BFS (topological sort)
Undirected graph → DFS + parent  OR  Union-Find
```

**Q3. What is a "back edge," and why is it the universal signal for a cycle?**
A: During a DFS traversal of any graph, edges fall into four categories: tree edges (DFS tree edges, leading to unvisited nodes), back edges (leading to an ancestor on the current DFS path), forward edges (leading to a descendant already fully explored — directed graphs only), and cross edges (leading to a node in a different DFS subtree — directed graphs only). Only a **back edge** signals a cycle: it creates a path from a descendant back to an ancestor, completing a cycle together with the tree path from ancestor to descendant. Forward and cross edges do not create cycles in directed graphs; in undirected DFS, forward and cross edges don't occur (every non-tree edge is a back edge to the parent or an ancestor).

```
DFS tree:   A → B → C → D
Back edge:  D → B  ← this creates the cycle B→C→D→B

Forward edge (directed only): A → C (C already visited, but not an ancestor)
Cross edge  (directed only):  D → E (E in a different DFS subtree)
Only back edges indicate cycles.
```

**Q4. Why do directed and undirected graphs need different cycle detection approaches?**
A: In an undirected graph, every edge `(u, v)` can be traversed as both `u→v` and `v→u`. During DFS from `u`, when we visit `v` via the edge `(u, v)`, the edge `(v, u)` is also present — but following it back to `u` does not constitute a real cycle (it's just "going back the way you came"). The parent-tracking trick in undirected DFS specifically ignores the edge back to the immediate parent, preventing this false positive. The condition for a real undirected cycle is: a neighbor is already visited AND is not the immediate parent.

In a directed graph, the edge `(u, v)` is one-directional. Finding a visited node `v` during DFS from `u` is only a cycle if `v` is currently on the active DFS stack (GRAY) — meaning there's a directed path from `v` back to itself through `u`. A visited but fully-explored (BLACK) node `v` is not a cycle: it just means `v` was explored in a prior DFS subtree and there's no directed path from `v` back to any ancestor of `u`. This distinction requires the 3-color marking scheme.

```
Directed graph — must use 3 colors:
  GRAY (on stack) neighbor → cycle
  BLACK (done) neighbor → no cycle (cross/forward edge)

Undirected graph — parent tracking suffices:
  visited non-parent neighbor → cycle
  visited parent → ignore (same edge, not a cycle)
```

### Section A2: Advanced Patterns

**Q5. How does Kahn's algorithm (BFS-based topological sort) detect cycles in directed graphs?**
A: Kahn's algorithm processes nodes with in-degree 0 first, reducing in-degrees of their neighbors. If the graph is a DAG, every node eventually reaches in-degree 0 and gets processed — all n nodes are output. If a cycle exists, the nodes in the cycle never reach in-degree 0 (each node in the cycle has at least one predecessor still in the cycle), so they are never processed. The cycle detection check: after BFS terminates, if the count of processed nodes < n, at least one cycle exists.

```js
function hasCycleKahn(graph, n) {
  const inDegree = new Array(n).fill(0);
  for (let u = 0; u < n; u++)
    for (const v of (graph[u] || []))
      inDegree[v]++;

  const queue = [];
  for (let i = 0; i < n; i++)
    if (inDegree[i] === 0) queue.push(i);

  let processed = 0;
  while (queue.length > 0) {
    const u = queue.shift();
    processed++;
    for (const v of (graph[u] || [])) {
      inDegree[v]--;
      if (inDegree[v] === 0) queue.push(v);
    }
  }

  return processed < n; // true → cycle exists
}
```

Kahn's is often preferred over DFS 3-color when topological ordering is also needed — it produces the topological order as a byproduct. DFS 3-color is preferred when only cycle detection is needed (no output order required) or when the graph is given as an adjacency list and DFS is already being used for other purposes.

**Q6. What is the Union-Find approach to undirected cycle detection, and when is it preferable to DFS?**
A: Union-Find (Disjoint Set Union) maintains a partition of nodes into connected components. For each edge `(u, v)`: find the roots of `u` and `v`. If they share the same root, both are already in the same component — adding this edge creates a cycle. If they have different roots, union the two components (no cycle yet).

```js
class UnionFind {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank = new Array(n).fill(0);
  }

  find(x) {
    if (this.parent[x] !== x)
      this.parent[x] = this.find(this.parent[x]); // path compression
    return this.parent[x];
  }

  union(x, y) {
    const rx = this.find(x), ry = this.find(y);
    if (rx === ry) return false; // same component → cycle
    // Union by rank
    if (this.rank[rx] < this.rank[ry]) this.parent[rx] = ry;
    else if (this.rank[rx] > this.rank[ry]) this.parent[ry] = rx;
    else { this.parent[ry] = rx; this.rank[rx]++; }
    return true;
  }
}

function hasCycleUnionFind(edges, n) {
  const uf = new UnionFind(n);
  for (const [u, v] of edges)
    if (!uf.union(u, v)) return true; // union failed → same component → cycle
  return false;
}
```

Union-Find is preferable when: (a) the graph is given as an edge list (not adjacency list), (b) edges are processed online (one at a time, cycle check after each), (c) you also need the connected components after processing. DFS is preferable when: (a) the graph is given as an adjacency list, (b) you need to identify which specific nodes form the cycle, (c) the graph is directed (Union-Find doesn't apply directly).

**Q7. How do you find and return the actual cycle nodes (not just detect existence), for both directed and undirected graphs?**
A: Returning the cycle requires tracking the path, not just detecting the back edge.

**Directed graph — DFS with path stack**: maintain an explicit path stack alongside the color array. When a GRAY node is found, the cycle is the portion of the path stack from that GRAY node to the current node (inclusive). Reconstruct by slicing the path stack from `indexOf(grayNode)` onward.

```js
function findCycleDirected(graph, n) {
  const color = new Array(n).fill(0); // 0=WHITE, 1=GRAY, 2=BLACK
  const path = [];

  function dfs(u) {
    color[u] = 1; path.push(u);
    for (const v of (graph[u] || [])) {
      if (color[v] === 1) { // back edge → cycle found
        const cycleStart = path.indexOf(v);
        return path.slice(cycleStart); // cycle nodes
      }
      if (color[v] === 0) {
        const result = dfs(v);
        if (result) return result;
      }
    }
    path.pop(); color[u] = 2;
    return null;
  }

  for (let i = 0; i < n; i++)
    if (color[i] === 0) {
      const result = dfs(i);
      if (result) return result;
    }
  return null; // no cycle
}
```

**Undirected graph — DFS with parent chain**: track the parent of each node during DFS. When a back edge `(u, v)` is found (v is visited and not u's parent), reconstruct the cycle by following parent pointers from `u` back up to `v`.

**Q8. What is the "find eventual safe states" problem, and how does it relate to cycle detection?**
A: A node in a directed graph is "safe" if every path from it eventually leads to a terminal node (a node with no outgoing edges) — equivalently, it is not part of a cycle and cannot reach any node in a cycle. The solution: a node is safe if and only if it is not on a cycle and has no path to any cycle node. DFS 3-color: a node is safe if it is BLACK (fully explored with no GRAY descendant found — meaning no back edge reachable from it). This transforms cycle detection into a reachability classification problem — every non-safe node is either in a cycle or can reach a cycle.

**Q9. What is a "back edge" in undirected DFS, and how does it differ from a cross edge?**
A: In undirected DFS, every non-tree edge is a back edge — there are no cross edges or forward edges. This is because undirected DFS imposes a "visited" marker, and any edge to an already-visited node must be to an ancestor in the DFS tree (since all descendants of the current node are either unvisited or currently being visited). A cross edge (connecting two nodes in different DFS subtrees) cannot exist in undirected DFS: if node `u` has an edge to node `v` in a different subtree, `v` would have been visited as a neighbor of `u` during `u`'s DFS, putting it in `u`'s subtree — a contradiction. So the only non-tree edges in undirected DFS are back edges to ancestors (or the immediate parent), and the parent-tracking filter distinguishes trivial parent-return from real cycles.

**Q10. How does cycle detection extend to weighted graphs and graphs with self-loops?**
A: **Self-loops** (an edge from a node to itself) are the simplest cycle — length 1. In directed DFS, a self-loop `(u, u)` means `u` is GRAY when its neighbor `u` is checked — the GRAY check catches it immediately. In undirected DFS with parent tracking, a self-loop is detected because the neighbor equals the current node itself (not just its parent) — most implementations handle this by checking `v !== parent` which is true when `v === u`. In Union-Find, `find(u) === find(v)` when `u === v` — the self-loop is detected on the first `union(u, u)` call.

**Weighted graphs**: the weight values don't affect the topological structure for cycle detection. All four algorithms apply unchanged — weights are ignored during cycle detection traversal. Negative-weight cycles (relevant for Bellman-Ford) are a separate concern: they are cycles where the sum of edge weights is negative, detected by checking if relaxation is still possible after `n-1` iterations.

## Topic B: Directed Graph Cycle Detection

### Section B1: Fundamentals

**Q11. Walk through the DFS 3-color algorithm for directed graphs step by step.**
A: Three states track each node's status:
- **WHITE (0)**: unvisited — not yet encountered by DFS.
- **GRAY (1)**: in progress — on the current DFS recursion stack (active).
- **BLACK (2)**: done — all descendants fully explored, no cycle found from this node.

Algorithm: for each unvisited node, start DFS. On entering a node, color it GRAY. For each neighbor: if GRAY → cycle found (back edge to an ancestor on the stack). If WHITE → recurse. If BLACK → skip (already fully explored, no cycle). On leaving (after all neighbors processed), color BLACK.

```js
function hasCycleDirected(graph, n) {
  const color = new Array(n).fill(0); // 0=WHITE, 1=GRAY, 2=BLACK

  function dfs(u) {
    color[u] = 1; // GRAY: on recursion stack
    for (const v of (graph[u] || [])) {
      if (color[v] === 1) return true;  // GRAY neighbor → back edge → cycle
      if (color[v] === 0 && dfs(v)) return true; // WHITE → recurse
      // BLACK neighbor → cross/forward edge → no cycle from here
    }
    color[u] = 2; // BLACK: fully explored, no cycle
    return false;
  }

  for (let u = 0; u < n; u++)
    if (color[u] === 0 && dfs(u)) return true;

  return false;
}
```

**Q12. Why is "visited" (2-color) insufficient for directed graphs, and what false negative does it produce?**
A: A 2-color (visited/unvisited) approach only tracks whether a node has ever been seen — it doesn't distinguish between "currently on the stack" (GRAY) and "fully explored in a prior subtree" (BLACK). This produces false positives: consider a diamond-shaped DAG `A→B, A→C, B→D, C→D`. When DFS visits D via B, it marks D as visited. When DFS later visits D via C, it finds D already visited and — if using 2-color — incorrectly reports a cycle. But there's no cycle: D is a cross-edge destination, not an ancestor. The 3-color scheme correctly handles this: D is marked BLACK after its exploration via B; when reached via C, BLACK means "safe, no cycle" — not a GRAY ancestor.

```
DAG (no cycle):   A → B → D
                  A → C → D   ← D visited twice, but via different paths

2-color DFS: visits D via B, marks visited. Later visits D via C → "already visited" → FALSE cycle report ✗
3-color DFS: visits D via B, marks BLACK. Later visits D via C → BLACK = safe → correct no-cycle ✓
```

**Q13. How does the iterative DFS implementation for directed cycle detection work, and why is it trickier than recursive?**
A: The recursive DFS naturally uses the call stack to track GRAY nodes — a node is GRAY for exactly the duration of its recursive call. The iterative version must explicitly replicate this: a node must be grayed on entry and blackened after all its neighbors are processed. This requires a two-phase approach: push a node, process its neighbors one at a time (pushing unvisited ones), and only blacken it when the stack frame is "returning." The standard technique uses a pair `[node, iterator]` or a `visited` set for GRAY and a separate `done` set for BLACK:

```js
function hasCycleDirectedIterative(graph, n) {
  const color = new Array(n).fill(0); // 0=WHITE, 1=GRAY, 2=BLACK

  for (let start = 0; start < n; start++) {
    if (color[start] !== 0) continue;

    // Stack stores [node, neighborIndex] — simulates recursive DFS state
    const stack = [[start, 0]];
    color[start] = 1; // GRAY on entry

    while (stack.length > 0) {
      const [u, idx] = stack[stack.length - 1];
      const neighbors = graph[u] || [];

      if (idx < neighbors.length) {
        stack[stack.length - 1][1]++; // advance neighbor pointer
        const v = neighbors[idx];

        if (color[v] === 1) return true;  // GRAY → cycle
        if (color[v] === 0) {
          color[v] = 1;                   // GRAY on entry
          stack.push([v, 0]);
        }
        // BLACK → skip
      } else {
        stack.pop();           // all neighbors done
        color[u] = 2;          // BLACK on exit
      }
    }
  }
  return false;
}
```

The key: `color[u] = 2` (BLACK) happens when all neighbors are exhausted — only when the stack frame for `u` is fully "returned from." The neighbor index stored in the stack frame (`idx`) replaces the implicit loop counter in the recursive version.

### Section B2: Advanced Patterns

**Q14. What is the relationship between directed cycle detection and topological sort?**
A: Topological sort is only possible on a DAG. Conversely, if a directed graph has a cycle, no topological ordering exists — there is no node in the cycle with all predecessors before it. The two algorithms are dual:
- **DFS-based topological sort**: runs DFS, appends each node to the result in BLACK order (post-order). If a GRAY neighbor is found → cycle → topological sort impossible.
- **Kahn's BFS topological sort**: processes in-degree-0 nodes iteratively. If all n nodes are processed → no cycle → valid topological order. If fewer than n nodes processed → cycle.

Both algorithms solve cycle detection as a byproduct of topological sort. In interviews, when asked "is this directed graph acyclic?", answering with a topological sort attempt and checking its completeness is equally valid as pure cycle detection.

**Q15. How does cycle detection apply to the "course schedule" family of problems?**
A: Course schedule problems model courses as nodes and prerequisites as directed edges `(prereq → course)`. Taking all courses is possible iff the prerequisite graph is a DAG (no circular prerequisites). The reduction: build a directed graph from the `prerequisites` array; run cycle detection. Extensions:
- **Course Schedule I** (can you finish all courses?): pure cycle detection.
- **Course Schedule II** (return a valid order): topological sort — return the order if DAG, empty array if cycle.
- **Course Schedule III** (maximum courses with deadlines): greedy + priority queue, not graph cycle detection.
- **Build Order** (system design): same directed graph + topological sort with cycle detection.

The pattern: any "can task A depend on task B which depends on task A?" problem is directed cycle detection.

## Topic C: Undirected Graph Cycle Detection

### Section C1: Fundamentals

**Q16. Walk through the DFS with parent-tracking algorithm for undirected graphs step by step.**
A: For each unvisited node, run DFS tracking the parent (the node we came from). On visiting a node `u` with parent `p`, check all neighbors `v`: if `v` is already visited and `v ≠ p`, a cycle is detected (back edge to an ancestor). If `v` is unvisited, recurse with `p = u`. If `v === p`, skip (this is the edge we just traversed — not a cycle).

```js
function hasCycleUndirected(graph, n) {
  const visited = new Array(n).fill(false);

  function dfs(u, parent) {
    visited[u] = true;
    for (const v of (graph[u] || [])) {
      if (!visited[v]) {
        if (dfs(v, u)) return true; // recurse into unvisited neighbor
      } else if (v !== parent) {
        return true; // visited non-parent neighbor → back edge → cycle
      }
      // v === parent → skip (just the edge we came from)
    }
    return false;
  }

  // Handle disconnected graphs: check every component
  for (let u = 0; u < n; u++)
    if (!visited[u] && dfs(u, -1)) return true;

  return false;
}
```

The initial call uses `parent = -1` (a sentinel that no node equals), so the first node's neighbors are checked without any parent exclusion.

**Q17. What is the multi-edge problem with parent tracking, and how is it handled?**
A: Consider a multigraph (multiple edges between the same pair of nodes). If nodes `u` and `v` have two edges between them, DFS from `u` via one edge visits `v`, then sees the other edge back to `u`. With simple parent tracking (`v !== parent`), this other edge is treated as a non-parent visited neighbor — incorrectly reported as a cycle. But having two edges between `u` and `v` does constitute a cycle (of length 2) in graph theory, so the detection is actually correct for multigraphs. For simple graphs (at most one edge between any pair), this situation doesn't arise. If the problem guarantees a simple graph, standard parent tracking is sufficient. If the problem has a multigraph, track the **parent edge index** (not the parent node) to correctly distinguish the two edges:

```js
// Multigraph: track parent edge index to avoid false positives
function dfs(u, parentEdgeIdx, graph, visited) {
  visited[u] = true;
  for (let i = 0; i < graph[u].length; i++) {
    const { to: v, edgeIdx } = graph[u][i];
    if (edgeIdx === parentEdgeIdx) continue; // skip the exact edge we came from
    if (visited[v]) return true;             // different edge to visited node → cycle
    if (dfs(v, edgeIdx, graph, visited)) return true;
  }
  return false;
}
```

**Q18. How does BFS-based cycle detection work for undirected graphs?**
A: BFS traversal uses a queue and tracks each node's parent (the node that first enqueued it). For each dequeued node `u`, check all its neighbors `v`: if `v` is visited and `v !== parent[u]`, a cycle exists. If `v` is unvisited, enqueue it and record `parent[v] = u`.

```js
function hasCycleUndirectedBFS(graph, n) {
  const visited = new Array(n).fill(false);
  const parent  = new Array(n).fill(-1);

  for (let start = 0; start < n; start++) {
    if (visited[start]) continue;

    const queue = [start];
    visited[start] = true;

    while (queue.length > 0) {
      const u = queue.shift();
      for (const v of (graph[u] || [])) {
        if (!visited[v]) {
          visited[v] = true;
          parent[v] = u;
          queue.push(v);
        } else if (v !== parent[u]) {
          return true; // visited non-parent → cycle
        }
      }
    }
  }
  return false;
}
```

BFS cycle detection is equivalent to DFS for undirected graphs in terms of correctness and complexity. DFS is more commonly taught; BFS is useful when you want level-by-level processing or when the graph is very deep (DFS risks stack overflow on deep graphs).

### Section C2: Advanced Patterns

**Q19. How does Union-Find cycle detection handle disconnected graphs and forest structures?**
A: Union-Find naturally handles disconnected graphs — each component starts as its own singleton. Processing edges one by one: each `union(u, v)` call either merges two components (no cycle yet) or finds they're already in the same component (cycle detected). There is no need to handle connectivity separately — the algorithm implicitly tracks all components simultaneously. After all edges are processed, the number of distinct roots equals the number of connected components. If any `union` call returned false (same root), a cycle exists in some component.

```
Graph with 2 components: {1,2,3}, {4,5}
Edges: (1,2), (2,3), (1,3), (4,5)

union(1,2): roots differ → merge. Components: {1,2}, {3}, {4}, {5}
union(2,3): roots differ → merge. Components: {1,2,3}, {4}, {5}
union(1,3): find(1)=find(3)=same root → CYCLE in component {1,2,3}
union(4,5): roots differ → merge. Components: {1,2,3}, {4,5}

Result: cycle detected ✓
```

**Q20. How do you detect cycles in an undirected graph represented as a 2D grid?**
A: A 2D grid is an implicit graph where each cell `(r, c)` is a node and adjacent cells are neighbors. DFS or BFS applies directly, using `(r, c)` as the node and `(prevR, prevC)` as the parent. A cycle is detected when a visited neighbor that is not the immediate parent is found. For grid problems with labels (e.g., "find cycle of same value"), add the constraint that the neighbor must also have the same label.

```js
function hasCycleGrid(grid) {
  const rows = grid.length, cols = grid[0].length;
  const visited = Array.from({ length: rows }, () => new Array(cols).fill(false));
  const dirs = [[0,1],[0,-1],[1,0],[-1,0]];

  function dfs(r, c, pr, pc) {
    visited[r][c] = true;
    for (const [dr, dc] of dirs) {
      const nr = r + dr, nc = c + dc;
      if (nr < 0 || nr >= rows || nc < 0 || nc >= cols) continue;
      if (nr === pr && nc === pc) continue; // skip parent cell
      if (visited[nr][nc]) return true;     // visited non-parent → cycle
      if (dfs(nr, nc, r, c)) return true;
    }
    return false;
  }

  for (let r = 0; r < rows; r++)
    for (let c = 0; c < cols; c++)
      if (!visited[r][c] && dfs(r, c, -1, -1)) return true;

  return false;
}
```

## Topic D: Cross-Topic & Interview-Style Questions

**Q21. "What is the time and space complexity of each cycle detection algorithm?"**
A:

| Algorithm | Graph Type | Time | Space | Notes |
|---|---|---|---|---|
| DFS 3-color | Directed | O(V + E) | O(V) | Color array + call stack |
| Kahn's BFS | Directed | O(V + E) | O(V) | In-degree array + queue |
| DFS + parent | Undirected | O(V + E) | O(V) | Visited array + call stack |
| BFS + parent | Undirected | O(V + E) | O(V) | Visited + parent arrays + queue |
| Union-Find | Undirected | O(E · α(V)) | O(V) | α = inverse Ackermann ≈ O(1) |

All graph traversal algorithms are O(V + E) — each vertex and edge is visited at most once. The Union-Find approach is technically O(E · α(V)) which is effectively O(E) since α(V) ≤ 5 for any practical input. Space is O(V) for the auxiliary arrays (color, visited, parent, union-find structure); the call stack adds O(V) in the worst case (for DFS on a skewed graph), but this is already bounded by O(V).

**Q22. "If an interviewer says 'detect a cycle in a graph' without specifying direction, what do you clarify?"**
A: I ask two questions immediately: (1) **Is the graph directed or undirected?** — This determines the algorithm entirely. Directed graphs require the GRAY/BLACK distinction or Kahn's; undirected graphs use parent tracking or Union-Find. (2) **Is it represented as an adjacency list, adjacency matrix, or edge list?** — This affects implementation: adjacency list naturally supports DFS/BFS traversal; edge list is the natural input for Union-Find; adjacency matrix requires iterating all n neighbors per node (O(n) per node instead of O(degree)). I would also ask whether to detect the cycle's existence or return the actual cycle nodes, and whether the graph may be disconnected (answer: always assume disconnected and iterate over all unvisited nodes).

**Q23. "How do you handle disconnected graphs in each algorithm?"**
A: Each algorithm requires a different adaptation for disconnected graphs:

- **DFS 3-color / DFS + parent**: wrap the DFS in an outer loop over all nodes: `for (let u = 0; u < n; u++) if (color[u] === WHITE) dfs(u)`. Each DFS call explores one connected component.
- **Kahn's BFS**: enqueue all nodes with in-degree 0 initially (across all components). The algorithm naturally handles all components simultaneously.
- **Union-Find**: processes edges, not nodes. Isolated nodes (no edges) are never unioned — they remain singleton components. No adaptation needed.
- **BFS + parent**: same outer loop as DFS: `for (let u = 0; u < n; u++) if (!visited[u]) bfs(u)`.

Forgetting the outer loop for DFS/BFS is the most common interview bug — it causes only one component to be checked, missing cycles in other components.

**Q24. "Compare DFS 3-color and Kahn's algorithm — when would you choose one over the other?"**
A: Both detect cycles in directed graphs in O(V + E). The choice depends on what else is needed:

**Choose DFS 3-color when**:
- Only cycle detection is needed (no topological order required).
- You need to identify which specific nodes form the cycle (path tracking).
- The graph is modified during traversal (DFS handles this more naturally).
- Recursive style is preferred for cleaner code.

**Choose Kahn's BFS when**:
- A topological ordering of non-cycle nodes is also needed as output.
- Iterative (non-recursive) implementation is required (no stack overflow risk).
- The problem naturally provides in-degrees (e.g., from a prerequisites list).
- You want to process nodes in topological order while detecting cycles simultaneously.

In interview practice, both are equally valid answers. Stating both options and explaining the trade-off — rather than presenting only one — is the senior-level response.

**Q25. "Can Union-Find detect cycles in directed graphs?"**
A: Not directly. Union-Find treats edges as undirected — `union(u, v)` merges the components of `u` and `v` regardless of edge direction. In a directed graph, a cycle requires that all edges in the cycle are followed in their specified direction. Union-Find ignores direction: consider the directed acyclic graph `1→2, 2→3, 3→1` (actually a cycle) vs. `1→2, 2→3` (no cycle) — Union-Find would treat both the same way if the underlying undirected structure is the same. More precisely: Union-Find would detect the cycle `1→2→3→1` correctly, but it would also falsely detect a "cycle" in `1→2, 3→2, 1→3` (which is a DAG shaped like a diamond). The false positive arises because Union-Find sees the undirected version of the edge set, and the undirected version may have cycles even when the directed version does not. **Conclusion**: Union-Find applies only to undirected cycle detection. Use DFS 3-color or Kahn's for directed graphs.

**Q26. "In one sentence each, state the key invariant that makes each algorithm correct."**
A:
- **DFS 3-color**: a back edge (GRAY→GRAY) is detected if and only if a directed cycle exists — because GRAY marks exactly the nodes currently on the active DFS path, and a GRAY neighbor means there is a directed path from that neighbor back to itself through the current node.
- **Kahn's BFS**: if any node is never enqueued (in-degree never reaches 0), it must be in a cycle — because only a cycle prevents a node's in-degree from eventually reaching 0 when all its predecessors are processed.
- **DFS + parent**: a visited non-parent neighbor means there exists a second path to that neighbor (via the current DFS path), which together with the DFS tree path from that neighbor to the current node forms a cycle.
- **Union-Find**: two nodes in the same component already have a path between them, so adding another edge between them creates a second path — a cycle.

**Q27. "You're given a list of courses and prerequisites. How do you detect a circular dependency, and what do you return?"**
A: Model courses as nodes `0..n-1` and each prerequisite pair `[a, b]` as a directed edge `b → a` (to take course `a`, you must first take course `b`). Build an adjacency list. Run DFS 3-color or Kahn's BFS. If a cycle is detected: return `false` (cannot complete all courses) or return the cycle nodes (the circular dependency chain). If no cycle: return `true` or the topological order. The implementation: Kahn's is slightly cleaner here since prerequisites directly provide in-degrees (count how many prerequisites each course has). Full code in Problem 3.

## Problem 1 — Detect Cycle in an Undirected Graph (DFS + Parent Tracking)

### Problem
Given an undirected graph with `n` nodes (labeled `0` to `n-1`) represented as an adjacency list, determine if the graph contains a cycle. Return `true` if a cycle exists, `false` otherwise.

```
Input:  n=5, graph = [[1,2],[0,3],[0,3],[1,2,4],[3]]
Output: true
        (cycle: 1-3-2-0-1 ... wait — let's verify)
        Edges: 0-1, 0-2, 1-3, 2-3, 3-4
        Cycle: 0-1-3-2-0  ✓

Input:  n=4, graph = [[1],[0,2],[1,3],[2]]
Output: false  (linear path 0-1-2-3, no cycle)
```

### Pattern Recognition
DFS with parent tracking for undirected graphs — the visited-non-parent detection identifies back edges (real cycles) while the parent exclusion prevents the trivial "return along the traversed edge" from being misidentified as a cycle.

### Key Insight
Every non-tree edge in undirected DFS is a back edge to an ancestor. The parent node is the only ancestor that can be reached via a single "trivial" backward step — it is not a cycle. Any other visited neighbor is a genuine back edge to a non-parent ancestor, proving a cycle exists. The parent parameter carries this single-node exclusion through the recursion.

### Approach
Mark each node visited on entry. For each neighbor: if unvisited → recurse with current node as parent; if visited and not parent → cycle. Run the outer loop over all nodes to handle disconnected components.

### Solution

```js
function hasCycle(n, graph) {
  const visited = new Array(n).fill(false);

  function dfs(u, parent) {
    visited[u] = true;

    for (const v of (graph[u] || [])) {
      if (!visited[v]) {
        // Unvisited neighbor: recurse, passing u as the parent
        if (dfs(v, u)) return true;
      } else if (v !== parent) {
        // Visited neighbor that is NOT our parent → back edge → cycle
        return true;
      }
      // v === parent: the edge we just came from — skip, not a cycle
    }
    return false;
  }

  // Outer loop: handle disconnected components
  for (let u = 0; u < n; u++) {
    if (!visited[u]) {
      if (dfs(u, -1)) return true; // -1 = no parent (root of component)
    }
  }

  return false;
}
```

### Dry Run

```

Outer loop: u=0, not visited → dfs(0, parent=-1)

dfs(0, -1): visited[0]=true
  neighbor v=1: not visited → dfs(1, parent=0)
    dfs(1, 0): visited[1]=true
      neighbor v=0: visited, v===parent(0) → skip
      neighbor v=3: not visited → dfs(3, parent=1)
        dfs(3, 1): visited[3]=true
          neighbor v=1: visited, v===parent(1) → skip
          neighbor v=2: not visited → dfs(2, parent=3)
            dfs(2, 3): visited[2]=true
              neighbor v=0: not visited? No, visited[0]=true.
                            v(0) !== parent(3) → CYCLE DETECTED → return true
          ← dfs(2,3) returns true
        ← dfs(3,1) returns true
      ← dfs(1,0) returns true
    ← dfs(0,-1) propagates true
  ← hasCycle returns true ✓
```

### Complexity
- Time: O(V + E) — each vertex visited once, each edge examined at most twice (once from each endpoint).
- Space: O(V) — visited array of size n; call stack depth at most V in the worst case (linear graph).

### Edge Cases
- No edges (`graph` all empty): DFS visits each node with no neighbors; no cycle found. Returns `false`.
- Single node with self-loop (`graph[0] = [0]`): DFS from 0, neighbor v=0. visited[0]=true, v(0)≠parent(-1) → returns `true`. Correct: self-loop is a cycle.
- Disconnected graph: the outer `for` loop ensures every unvisited node starts a new DFS. A cycle in any component is detected.
- Graph is a tree (n-1 edges, connected): every edge is a tree edge; no non-parent visited neighbor is ever found. Returns `false`.
- Two nodes, one edge (0-1): DFS(0,-1) visits 1, DFS(1,0) sees neighbor 0 = parent → skips. Returns `false`.

### Follow-up Questions
- "Implement iteratively?" → Use a stack of `[node, parent]` pairs. Push `[start, -1]`; each iteration pops a node and checks neighbors with the same parent-exclusion logic.
- "Return the actual cycle nodes, not just true/false?" → Track a path array during DFS. When a cycle-triggering back edge `(u, v)` is found, the cycle is `path[indexOf(v)..u] + v`.
- "Use Union-Find instead?" → See Problem 2 — process edges, cycle when `find(u) === find(v)` before `union`.

## Problem 2 — Detect Cycle in Undirected Graph (Union-Find)

### Problem
Same as Problem 1: given `n` nodes and a list of undirected edges, return `true` if the graph contains a cycle.

```
Input:  n=4, edges = [[0,1],[1,2],[2,3],[3,0]]
Output: true   (cycle: 0-1-2-3-0)

Input:  n=4, edges = [[0,1],[1,2],[2,3]]
Output: false  (path 0-1-2-3, no cycle)
```

### Pattern Recognition
Union-Find (Disjoint Set Union) — process edges one at a time; a cycle is detected the moment both endpoints of an edge already belong to the same connected component (a path between them already exists; adding this edge creates a second path = cycle).

### Key Insight
A graph has a cycle if and only if some edge connects two nodes that are already in the same connected component. Union-Find tracks components dynamically — each `union(u, v)` either merges two components (no cycle) or finds they share a root (cycle). The `find` operation with path compression makes root queries nearly O(1), enabling efficient edge-by-edge processing without DFS traversal.

### Approach
Initialize Union-Find with n singleton components. For each edge `[u, v]`: if `find(u) === find(v)`, cycle detected — return `true`. Otherwise `union(u, v)` and continue. If all edges processed without a cycle, return `false`.

### Solution

```js
function hasCycleUnionFind(n, edges) {
  const parent = Array.from({ length: n }, (_, i) => i); // parent[i] = i initially
  const rank   = new Array(n).fill(0);

  // Find root with path compression
  function find(x) {
    if (parent[x] !== x)
      parent[x] = find(parent[x]); // path compression: flatten the tree
    return parent[x];
  }

  // Union by rank: attach smaller tree under larger tree's root
  function union(x, y) {
    const rx = find(x), ry = find(y);
    if (rx === ry) return false; // same root → same component → cycle

    if (rank[rx] < rank[ry])      parent[rx] = ry;
    else if (rank[rx] > rank[ry]) parent[ry] = rx;
    else { parent[ry] = rx; rank[rx]++; }

    return true; // merged two distinct components
  }

  for (const [u, v] of edges) {
    if (!union(u, v)) return true; // union returned false → same component → cycle
  }

  return false;
}
```

### Dry Run

```
n=4, edges = [[0,1],[1,2],[2,3],[3,0]]
parent = [0,1,2,3], rank = [0,0,0,0]

Edge [0,1]: find(0)=0, find(1)=1. Different → union. parent=[0,0,2,3], rank=[1,0,0,0].
            (rank[0]=0 = rank[1]=0, so parent[1]=0, rank[0]++)

Edge [1,2]: find(1)=find(1)→parent[1]=0→find(0)=0. find(2)=2. Different → union.
            rank[0]=1 > rank[2]=0 → parent[2]=0. parent=[0,0,0,3], rank=[1,0,0,0].

Edge [2,3]: find(2)→parent[2]=0→find(0)=0. find(3)=3. Different → union.
            rank[0]=1 > rank[3]=0 → parent[3]=0. parent=[0,0,0,0], rank=[1,0,0,0].

Edge [3,0]: find(3)→parent[3]=0→find(0)=0. find(0)=0. SAME ROOT (0=0) → CYCLE → return true ✓
```

### Complexity
- Time: O(E · α(V)) ≈ O(E) — each edge processed once; `find` with path compression is O(α(V)) ≈ O(1).
- Space: O(V) — parent and rank arrays of size n.

### Edge Cases
- Self-loop `[u, u]`: `find(u) === find(u)` always true (same root) → cycle detected immediately. Correct: a self-loop is a cycle.
- Single edge: one `union` call, two distinct nodes merged. Returns `false`.
- Multiple disconnected components: Union-Find handles them naturally — each component is a separate subtree in the forest.
- All nodes isolated (no edges): no `union` calls; returns `false`. Correct.

### Follow-up Questions
- "What does the Union-Find structure look like after all unions without a cycle?" → A forest of trees — one tree per connected component, rooted at the representative node. The `parent` array encodes these trees (with path compression flattening them).
- "Can you count the number of connected components at the same time?" → Yes — initialize a counter `components = n`; decrement by 1 on every successful `union`. After all edges, `components` = number of connected components.
- "What if edges are added online (one at a time with cycle queries between additions)?" → Union-Find handles this perfectly — each `union` call is independent and the state persists between calls. DFS would require re-traversal after each addition.

## Problem 3 — Course Schedule (Directed Cycle Detection via Kahn's Algorithm)

### Problem
There are `numCourses` courses labeled `0` to `numCourses-1`. Given an array `prerequisites` where `prerequisites[i] = [a, b]` means you must take course `b` before course `a`, return `true` if you can finish all courses, `false` otherwise.

```
Input:  numCourses=2, prerequisites=[[1,0]]
Output: true   (take 0 then 1)

Input:  numCourses=2, prerequisites=[[1,0],[0,1]]
Output: false  (0 requires 1, 1 requires 0 → cycle)

Input:  numCourses=4, prerequisites=[[1,0],[2,0],[3,1],[3,2]]
Output: true   (order: 0,1,2,3 or 0,2,1,3)
```

### Pattern Recognition
Kahn's BFS topological sort on a directed graph — build the prerequisite graph, compute in-degrees, process in-degree-0 nodes via BFS; if all courses are processed, no cycle exists (can finish all). If fewer courses are processed, a cycle blocks the remaining ones.

### Key Insight
Courses blocked by a circular prerequisite chain can never have their in-degree reduced to 0 — each course in the cycle is waiting for another course in the cycle. Kahn's naturally identifies these: after BFS terminates, any course with in-degree > 0 is in or downstream of a cycle. The count of processed courses is the exact discriminator: `processed == numCourses` ↔ no cycle.

### Approach
Build adjacency list and in-degree array from prerequisites. Enqueue all courses with in-degree 0. BFS: dequeue a course, increment processed count, decrement in-degree of its neighbors, enqueue any neighbor whose in-degree reaches 0. After BFS: return `processed === numCourses`.

### Solution

```js
function canFinish(numCourses, prerequisites) {
  // Build adjacency list and in-degree array
  const graph    = Array.from({ length: numCourses }, () => []);
  const inDegree = new Array(numCourses).fill(0);

  for (const [course, prereq] of prerequisites) {
    graph[prereq].push(course); // prereq → course (must take prereq first)
    inDegree[course]++;         // course has one more prerequisite
  }

  // Initialize queue with all courses that have no prerequisites
  const queue = [];
  for (let i = 0; i < numCourses; i++)
    if (inDegree[i] === 0) queue.push(i);

  let processed = 0;

  while (queue.length > 0) {
    const course = queue.shift();
    processed++;

    // "Take" this course: reduce in-degree of dependent courses
    for (const next of graph[course]) {
      inDegree[next]--;
      if (inDegree[next] === 0) {
        queue.push(next); // all prerequisites satisfied → can now take this course
      }
    }
  }

  // If all courses were processed, no cycle exists
  return processed === numCourses;
}
```

```
  [2,0]: graph[0]=[1,2], inDegree[2]=1
  [3,1]: graph[1]=[3], inDegree[3]=1
  [3,2]: graph[2]=[3], inDegree[3]=2

  inDegree[2]-- → 0 → enqueue 2.

processed=2. Neighbors of 1: [3].
  inDegree[3]-- → 1.  (not 0, don't enqueue yet)

```

### Complexity
- Time: O(V + E) — each course and prerequisite processed once.
- Space: O(V + E) — adjacency list O(E), in-degree array O(V), queue O(V).

### Edge Cases
- No prerequisites: all in-degrees are 0; all courses enqueued immediately; all processed; returns `true`.
- Single course, self-prerequisite `[[0,0]]`: `inDegree[0]=1`; never enqueued; `processed=0 ≠ 1`; returns `false`. Correct: self-cycle.
- Disconnected prerequisite graph: courses with no prerequisites from their component are enqueued first; all non-cycle courses are processed; only cycle courses remain with in-degree > 0.
- All courses in one big cycle: no course has in-degree 0; queue is empty from the start; `processed=0 ≠ numCourses`; returns `false`.

### Follow-up Questions
- "Return the course order instead of true/false?" → Collect each dequeued course into a `result` array. If `result.length === numCourses`, return `result`; otherwise return `[]` (cycle detected). This is Course Schedule II.
- "Use DFS instead of Kahn's?" → Run DFS 3-color: GRAY a course on entry, BLACK on exit. If a GRAY neighbor is found → cycle → return `false`. Otherwise all courses turn BLACK → return `true`.
- "What if the same prerequisite appears multiple times?" → Duplicate edges inflate in-degrees incorrectly. Deduplicate prerequisites before building the graph, or handle in-degree reduction carefully.

## Problem 4 — Detect Cycle in Directed Graph (DFS 3-Color)

### Problem
Given a directed graph with `n` nodes (labeled `0` to `n-1`) and a list of directed edges, determine if the graph contains a directed cycle. Return `true` if a cycle exists.

```
Input:  n=4, edges = [[0,1],[0,2],[1,3],[2,3]]
Output: false  (DAG: 0→1→3, 0→2→3)

Input:  n=4, edges = [[0,1],[1,2],[2,3],[3,1]]
Output: true   (cycle: 1→2→3→1)
```

### Pattern Recognition
DFS 3-color (WHITE/GRAY/BLACK) on a directed graph — the GRAY state tracks nodes currently on the active DFS stack; a GRAY neighbor during DFS proves a back edge and therefore a directed cycle.

### Key Insight
The GRAY state is the distinguishing factor between directed and undirected cycle detection. It marks "currently being processed — on the recursion stack right now." A GRAY neighbor means: there is a directed path from that neighbor to the current node (via the DFS tree), and now we've found an edge from the current node back to that neighbor — completing a directed cycle. A BLACK neighbor is safe: it was fully explored in a prior DFS call with no back edge found — no cycle through it.

### Approach
Initialize all nodes WHITE. For each unvisited node, run DFS: mark GRAY on entry. For each neighbor: GRAY → return `true` (cycle). WHITE → recurse. BLACK → skip. Mark BLACK on exit (all neighbors processed, no cycle from here).

### Solution

```js
function hasCycleDirected(n, edges) {
  // Build adjacency list from edge list
  const graph = Array.from({ length: n }, () => []);
  for (const [u, v] of edges) graph[u].push(v);

  const WHITE = 0, GRAY = 1, BLACK = 2;
  const color = new Array(n).fill(WHITE);

  function dfs(u) {
    color[u] = GRAY; // mark as "on the current DFS stack"

    for (const v of graph[u]) {
      if (color[v] === GRAY)  return true;  // back edge → directed cycle
      if (color[v] === WHITE && dfs(v)) return true; // recurse into unvisited
      // color[v] === BLACK → cross/forward edge → safe, skip
    }

    color[u] = BLACK; // fully explored: no cycle found from u
    return false;
  }

  // Check every node: handles disconnected directed graphs
  for (let u = 0; u < n; u++) {
    if (color[u] === WHITE && dfs(u)) return true;
  }

  return false;
}
```

### Dry Run

```
  neighbor 1: WHITE → dfs(1)
    dfs(1): color[1]=GRAY. color=[G,G,W,W]
      neighbor 2: WHITE → dfs(2)
        dfs(2): color[2]=GRAY. color=[G,G,G,W]
          neighbor 3: WHITE → dfs(3)
            dfs(3): color[3]=GRAY. color=[G,G,G,G]
              neighbor 1: color[1]=GRAY → CYCLE DETECTED → return true
            ← dfs(3) returns true
          ← dfs(2) propagates true
        ← dfs(1) propagates true
      ← dfs(0) propagates true
    ← hasCycleDirected returns true ✓

Cycle: 1→2→3→1 (detected when 3's neighbor 1 is found GRAY on the stack)
```

### Complexity
- Time: O(V + E) — each node colored once (WHITE→GRAY→BLACK); each edge examined once.
- Space: O(V) — color array; O(V) call stack depth in worst case.

### Edge Cases
- DAG (no cycle): all nodes turn BLACK after DFS. Returns `false`.
- Single node, self-loop `edges=[[0,0]]`: `dfs(0)`: color[0]=GRAY. Neighbor 0: color[0]=GRAY → return `true`. Correct.
- Node with no outgoing edges: enters `dfs(u)`, inner loop has no neighbors, immediately colors BLACK. Returns `false` from this node.
- Multiple cycles: the first cycle found triggers an early return; remaining cycles are not enumerated (not needed for detection).
- Disconnected directed graph: outer loop visits each unvisited node, starting a new DFS for each component.

### Follow-up Questions
- "Return the nodes in the cycle, not just true/false?" → Maintain a `path` stack alongside the color array. When a GRAY neighbor `v` is found during `dfs(u)`, the cycle is `path[indexOf(v)..end] + v`. See Q7 for full implementation.
- "Implement iteratively to avoid stack overflow on large graphs?" → See Q13 for the iterative 3-color DFS using explicit `[node, neighborIndex]` stack entries.
- "Solve using Kahn's algorithm instead?" → Build in-degrees, BFS from in-degree-0 nodes, return `processedCount < n`. Either approach is valid; Kahn's additionally produces the topological order for non-cycle nodes.

## Common Bugs Checklist

Before submitting any cycle detection solution, verify:

1. **Outer loop handles disconnected graphs?** — A single DFS/BFS call from one node only explores its connected component. If the graph has multiple components, cycles in other components are missed. Always wrap the traversal in `for (let u = 0; u < n; u++) if (not_visited(u)) run_traversal(u)`.

2. **Directed graph: using 3 colors (WHITE/GRAY/BLACK), not 2 (visited/unvisited)?** — A 2-color scheme produces false positives (reports a cycle on cross/forward edges). The GRAY state is essential to distinguish "currently on stack" from "already fully explored." Omitting it is the most common directed cycle detection bug.

3. **Undirected graph: checking `v !== parent`, not `!visited[v]`?** — `!visited[v]` alone misses the case where `v` is visited but is the parent — it would recursively visit the parent again or incorrectly trigger a cycle. The condition must be `visited[v] && v !== parent` for a cycle.

4. **Kahn's BFS: checking `processed === n` at the end, not `queue.isEmpty()` mid-BFS?** — The queue being empty just means no more in-degree-0 nodes exist right now — not that all nodes were processed. Count processed nodes explicitly and compare to `n` after the BFS loop exits.

5. **Union-Find: path compression applied in `find`, not just `union`?** — Without path compression, `find` is O(n) per call in the worst case (linear chain), making the algorithm O(n·E) instead of O(E·α(n)). Always flatten the path in `find`: `parent[x] = find(parent[x])`.

6. **Union-Find: returning early on `find(u) === find(v)` BEFORE calling `union`?** — Some implementations call `union(u, v)` and check its return value (false = same component). Both patterns work, but if `union` modifies state before checking, it might corrupt the structure. The safest pattern: `if (find(u) === find(v)) return true; union(u,v);`.

7. **Directed cycle DFS: coloring BLACK on RETURN (post-order), not on entry?** — `color[u] = BLACK` must happen after all neighbors are processed — i.e., at the end of the DFS function, not at the start. Coloring BLACK on entry means all subsequent neighbors immediately see BLACK (skipped), missing legitimate cycle detection within the subtree.

8. **Kahn's BFS: initializing in-degrees from the prerequisite list correctly?** — The edge `[a, b]` means "b is a prerequisite of a" → directed edge `b → a` → `inDegree[a]++`. Reversing this (setting `inDegree[b]++`) builds the wrong graph and produces incorrect cycle detection results. Always verify the edge direction matches the problem's definition.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to immediately identify whether the graph is directed or undirected — because that single distinction determines the entire algorithm family. The decisive signal of genuine mastery is explaining *why* directed graphs need 3 colors in one sentence: "A visited neighbor in directed DFS is only a cycle if it's currently on the recursion stack (GRAY) — a BLACK neighbor is just a node we explored earlier via a different path, a cross or forward edge, which is perfectly fine in a DAG." Then immediately contrasting with undirected: "In undirected DFS, every visited neighbor is either our parent (trivial back-step, ignore) or a genuine ancestor (real cycle) — we only need the parent check, not a full three-state machine, because the undirected structure prevents cross edges entirely." That contrast — stated cleanly before writing a single line of code — is what separates a senior answer from a memorized template.
