## Part 1 — Theory & Interview Q&A

### Section 1: Fundamentals

**Q1. What does "cloning a graph" mean precisely, and why is it harder than copying a tree or a linked list?**
A: Cloning a graph means producing a **deep copy** — an entirely new set of node objects with the same values and the same adjacency structure as the original, but with no shared node references between the original and the clone (modifying the clone must not affect the original, and vice versa). This is harder than cloning a tree or a linked list for one fundamental reason: **graphs can contain cycles and nodes with multiple incoming edges**. In a linked list or tree, every node is reached by exactly one traversal path, so a simple recursive copy works naturally. In a general graph, a node might be reachable via many different paths — without tracking which nodes have already been cloned, a naive recursive approach would create infinitely many duplicate copies (once it enters a cycle) or create multiple independent copies of the same node (for nodes reachable via multiple paths), breaking the graph's structural integrity.

```
Original:         Naive recursive copy breaks because:
1 -- 2            cloning 1 visits 2, then from 2 visits 1 again,
|  × |            creating a SECOND, separate clone of 1 — now clone(1)
3 -- 4            has a neighbor pointing to a different "clone 1" than the root,
                  and the cycle causes infinite recursion.
```

**Q2. What is the single key data structure that makes graph cloning tractable, and what problem does it solve?**
A: A **hash map from original node → clone node** (`visited` map). Before recursing into or visiting a node's neighbors, check whether it's already been cloned (present in the map). If it has, return the existing clone immediately instead of creating a new one or recursing further. This solves both problems: it prevents infinite loops (returning the existing clone when a cycle is detected) and guarantees each original node maps to exactly one clone (preserving structural identity — two edges in the original pointing to the same node both point to the same clone in the copy, not two different copies).

**Q3. What are the two standard implementation approaches to graph cloning, and which data structure does each rely on?**
A: Both approaches use the visited hash map described in Q2, but differ in traversal strategy:
1. **DFS (recursive or iterative with an explicit stack)**: recursively clone the current node, then recursively clone each of its unvisited neighbors, returning already-cloned nodes immediately from the map when revisited.
2. **BFS (iterative with a queue)**: enqueue the start node, create its clone, and enter a loop — for each dequeued node, iterate its neighbors, creating clones for not-yet-visited ones and enqueuing them, while always linking the current clone's neighbor list to the existing or newly-created neighbor clone.

Both produce identical correct results — the traversal order differs (DFS explores one path deep before backtracking, BFS explores level by level) but the cloned graph structure is the same regardless.

**Q4. What is the time and space complexity of graph cloning?**
A: Time: **O(V + E)** — every vertex is visited exactly once (the hash map ensures no vertex is processed twice), and every edge is traversed exactly once (when processing each vertex's adjacency list). Space: **O(V)** — the hash map stores one entry per vertex (O(V)), plus O(V) for the recursion call stack (DFS) or queue (BFS) in the worst case (e.g., a path-shaped graph for DFS depth, or a star-shaped graph for BFS width). The total output (the cloned graph itself) is O(V + E) but this is required by the problem, not extra overhead.

**Q5. Why does the "return the existing clone from the hash map" step need to happen BEFORE recursing into the node's neighbors, not after?**
A: The visited-map check must happen as the **very first step** upon encountering any node, before any neighbor recursion. Consider a cycle: node A is adjacent to node B, and B is adjacent back to A. If you create a clone for A, then recurse into B, then try to recurse into B's neighbor A — if you haven't recorded A in the map yet at this point, you'd create a second clone for A. The correct order: (1) check the map, (2) if already there, return the existing clone immediately, (3) only then create a new clone for this node and add it to the map, (4) recurse into neighbors. This ordering guarantees the clone exists in the map before any of its neighbors are processed — so when any neighbor tries to "come back" to this node via a cycle or shared edge, the existing clone is already found and returned rather than a new one being created.

### Section 2: DFS vs. BFS Implementation Details

**Q6. Walk through the DFS-based clone algorithm step by step.**
A: The recursive DFS approach:
1. If `node` is `null`, return `null` (empty graph).
2. If `node` is already in `visited`, return `visited.get(node)` immediately (prevents re-cloning and breaks cycles).
3. Create a new clone node with `node.val` and an empty neighbors list.
4. Store it in the map: `visited.set(node, clone)`.
5. For each neighbor of `node`, recursively clone it and add the result to `clone.neighbors`.
6. Return `clone`.

```js
function cloneGraph(node, visited = new Map()) {
  if (node === null) return null;
  if (visited.has(node)) return visited.get(node);

  const clone = new Node(node.val, []);
  visited.set(node, clone);           // store BEFORE recursing into neighbors

  for (const neighbor of node.neighbors) {
    clone.neighbors.push(cloneGraph(neighbor, visited));
  }

  return clone;
}
```

**Q7. Walk through the BFS-based clone algorithm step by step.**
A: The iterative BFS approach avoids recursion-depth concerns:
1. If `node` is `null`, return `null`.
2. Create the clone for the starting node, store it in `visited`, and enqueue the original start node.
3. While the queue is not empty: dequeue the current original node.
4. For each neighbor of the current original node:
   - If the neighbor hasn't been visited, create its clone, store in `visited`, enqueue the original neighbor.
   - Add the existing (or just-created) clone of the neighbor to the current clone's neighbors list.
5. Return `visited.get(startNode)`.

```js
function cloneGraphBFS(node) {
  if (node === null) return null;

  const visited = new Map();
  const queue = [node];
  visited.set(node, new Node(node.val, []));

  while (queue.length > 0) {
    const current = queue.shift();
    const currentClone = visited.get(current);

    for (const neighbor of current.neighbors) {
      if (!visited.has(neighbor)) {
        visited.set(neighbor, new Node(neighbor.val, []));
        queue.push(neighbor);
      }
      currentClone.neighbors.push(visited.get(neighbor));
    }
  }

  return visited.get(node);
}
```

**Q8. What is the key difference in when neighbor edges are "wired up" between the DFS and BFS approaches?**
A: In the **DFS approach**, neighbor wiring happens naturally during the recursive unwinding — `clone.neighbors.push(cloneGraph(neighbor, visited))` both triggers the recursive clone creation AND wires the edge in a single step, so by the time the top-level call returns, the entire graph is fully wired. In the **BFS approach**, wiring happens in the main loop's inner `for` loop — when processing the dequeued `current` node, the clone for each of its neighbors may already exist (if it was enqueued and cloned earlier via a different path) or may be freshly created at that moment, but either way, the neighbor's clone is always already in `visited` before being pushed to `currentClone.neighbors`. The BFS approach naturally separates "create all clone nodes" from "wire all edges" into a single interleaved loop, rather than DFS's more implicit recursive wiring.

**Q9. Can graph cloning be done without a hash map — for example, by using the clone's node structure itself to record "visited" state?**
A: There is a clever alternative for graphs where nodes have predictable integer labels (0 to n-1): use a simple array indexed by node value instead of a hash map. However, this only works cleanly when node values are unique and known upfront — for a general graph with arbitrary or non-unique node values, the hash map keyed by node **reference** (not value) is the only reliable approach. Some implementations try to store the clone as a special "marker" field directly on the original node (temporarily modifying the original to track visited state) — this works but mutates the input, which is generally unacceptable unless explicitly permitted.

### Section 3: Extensions & Variations

**Q10. How does cloning extend to a DIRECTED graph, and what changes about the algorithm?**
A: The core algorithm is identical — the visited map and the traversal (DFS or BFS) are unchanged. The only difference is that for a directed graph, each edge `u → v` appears only in `u`'s adjacency list (not in `v`'s), so the traversal follows directed edges only. This means: some nodes might not be reachable from the given start node (if the graph isn't strongly connected), and those unreachable nodes simply won't appear in the clone (since they can't be discovered by any traversal from the start). If you need to clone the entire directed graph including unreachable-from-start nodes, you'd need to iterate over all known nodes (if given the full node list) rather than just traversing from a single start.

**Q11. How would you clone a WEIGHTED graph (edges have associated weights), and what changes?**
A: The conceptual approach is unchanged — the visited map and traversal stay the same. What changes is the node/edge representation: instead of a simple `neighbors[]` array of node references, you'd typically have `neighbors[]` of `[node, weight]` pairs (or a separate adjacency list structure). The clone step creates new `[cloneNode, weight]` pairs instead of just new node references, preserving the weight values alongside the structural clone. The key invariant — "use the map to reuse an existing clone rather than creating a new one" — applies identically regardless of whether edges carry weights.

**Q12. How would you verify that a graph clone is correct — i.e., that it's a true deep copy with no shared references?**
A: Three properties must all hold:
1. **Same structure**: every node in the clone has the same `val` and the same number of neighbors as its corresponding original node — and the neighbors' values match, with the same adjacency pattern.
2. **No shared node references**: no node object in the clone should be reference-equal to any node object in the original (`cloneNode !== originalNode` for every pair, even nodes with the same value).
3. **Correct identity mapping**: if two edges in the original both point to the same node object X, both corresponding edges in the clone must point to the same clone object Y (not two different clones that happen to have the same value as X).

A BFS/DFS traversal over both graphs simultaneously, checking these conditions with a second mapping from original to clone, can systematically verify all three.

**Q13. Why is "cloning a graph" conceptually important beyond being an isolated interview problem — where does deep-copy-of-graph logic appear in real systems?**
A: Deep-copying a graph (or graph-like structure) appears in: **undo/redo systems** (need to save a snapshot of a state graph for restoration), **compiler intermediate representations** (IR graphs are cloned when creating specialized versions or performing transformations), **game state management** (save a full copy of the game's entity-relationship graph before a risky action), **configuration/dependency graphs** in build systems (clone the dependency graph before speculative modifications), and **machine learning computation graphs** (cloning a neural network's computation graph for parallel training or transfer learning). In all these cases, the fundamental challenge is the same — correctly handling cycles and shared-reference identity in a pointer/reference-based graph structure.

### Section 4: Scenario / Interview-Style Questions

**Q14. "Your first instinct is to write a simple recursive copy: `node.neighbors.map(n => cloneNode(n))`. What goes wrong on a graph with a cycle?"**
A: Without the visited map, encountering a cycle causes infinite recursion — cloning node A triggers cloning its neighbor B, which triggers cloning B's neighbor A again, which triggers cloning A's neighbor B again, and so on indefinitely until the call stack overflows. Even without a cycle, a node reachable via two different paths would be cloned twice, creating two separate clone objects that should be the same object — so any edge pointing to that node in the original would incorrectly point to two different (but value-equal) clones in the copy, breaking the structural identity of the graph.

**Q15. "In the DFS clone, why must `visited.set(node, clone)` happen BEFORE the `for (neighbor of node.neighbors)` loop, not after?"**
A: Because a cycle means one of those neighbors might recursively come back to `node` before the loop finishes. If the map entry for `node` hasn't been set yet when that recursive call checks `visited.has(node)`, it won't find it, will create a second clone for `node`, and will wire that second clone into the graph — producing structural corruption. Setting the map entry immediately after creating the clone (before recursing into any neighbors) ensures the clone is findable the moment any future call checks for it, regardless of cycles in the graph.

**Q16. "A teammate uses node values as hash map keys instead of node references. When does this break, and what's the correct key?"**
A: Using node values as keys breaks whenever the graph contains **two distinct nodes with the same value** — both would map to the same hash-map entry, and cloning the second would incorrectly return the first's clone (or overwrite the mapping). The correct key is the **node reference itself** (the object identity), not the value — in JavaScript, Map objects naturally support object references as keys with correct reference equality semantics, so `visited.set(node, clone)` where `node` is the object reference is correct. Using node value is only safe if the problem explicitly guarantees all node values are unique (which LeetCode's classic "Clone Graph" problem does guarantee — but relying on this without acknowledging the assumption is a gap in general understanding).

**Q17. "How would you approach cloning a very large graph (millions of nodes) where deep recursion in the DFS approach risks a stack overflow?"**
A: Switch to the **BFS-based iterative approach** (Q7), which uses an explicit queue (heap-allocated) instead of the implicit call stack — no recursion depth limit applies. Alternatively, convert the DFS to an **iterative DFS using an explicit stack** (same O(V) space, but heap-allocated like BFS). The hash map and the overall O(V + E) complexity remain the same; only the traversal mechanism changes from implicit-call-stack to explicit-data-structure, which is entirely safe for arbitrarily large graphs.

## Problem 1 — Clone Graph (DFS, Recursive)

### Problem
Given a reference to a node in a connected undirected graph, return a **deep copy** (clone) of the graph. Each node contains an integer `val` and a list of its neighbors.

```
Input graph (adjacency list):
Node 1: neighbors [2, 4]
Node 2: neighbors [1, 3]
Node 3: neighbors [2, 4]
Node 4: neighbors [1, 3]

Output: a deep copy of the same graph structure,
with entirely new node objects having no references to the original nodes.
```

### Pattern Recognition
Graph traversal (DFS or BFS) with a visited hash map that maps original node references to their corresponding clone nodes — the canonical approach to deep-copying a graph with cycles.

### Key Insight
The visited map serves two roles simultaneously: it prevents infinite recursion on cycles (returning an already-existing clone immediately, without re-processing), and it guarantees structural identity (each original node maps to exactly one clone, so multiple edges pointing to the same original node all correctly point to that one clone in the copied graph).

### Approach
Recursive DFS. Base cases: null input returns null; already-visited node returns its existing clone. For an unvisited node: create its clone, store it in the map BEFORE recursing, then recursively clone each neighbor and append to the clone's neighbors list.

### Solution

```js
function cloneGraph(node, visited = new Map()) {
  // base case 1: empty graph
  if (node === null) return null;

  // base case 2: already cloned — return the existing clone (handles cycles)
  if (visited.has(node)) return visited.get(node);

  // create the clone for this node
  const clone = new Node(node.val, []);

  // store in map BEFORE recursing — critical for correct cycle handling
  visited.set(node, clone);

  // recursively clone each neighbor and wire into this clone's neighbor list
  for (const neighbor of node.neighbors) {
    clone.neighbors.push(cloneGraph(neighbor, visited));
  }

  return clone;
}
```

### Complexity
- Time: O(V + E) — each node visited exactly once (map check prevents re-processing), each edge processed once (when iterating each node's neighbors).
- Space: O(V) — the visited map (one entry per node) plus O(V) recursion call stack depth in the worst case (e.g., a path-shaped graph with V nodes).

### Edge Cases
- `null` input: explicitly returned as `null` — empty graph, no cloning needed.
- Single node with no neighbors: clone created with empty neighbors list, returned directly; no recursion beyond the initial call.
- Self-loop (node is its own neighbor): visited map check catches this on the second encounter (`visited.has(node)` is true since the node was added before processing neighbors), correctly returning the same clone rather than creating a second one.
- Fully disconnected component given as a single starting node: by definition of "connected undirected graph" (the problem's assumption), all nodes are reachable from any starting node — if the graph were disconnected, only the component containing the given node would be cloned.

### Follow-up Questions
- "Implement this iteratively using BFS to avoid recursion-depth concerns on large graphs." → See Problem 2.
- "What if the graph were directed — what changes?" → Conceptually nothing changes in the algorithm; the traversal follows directed edges only, so only nodes reachable from the start via directed paths are cloned (which is the correct semantic for a directed graph deep copy from a given start node).

## Problem 2 — Clone Graph (BFS, Iterative)

### Problem
Same as Problem 1 — deep-copy a connected undirected graph — but implement it iteratively using BFS, to avoid the recursion depth risk inherent in the DFS approach for large graphs.

### Pattern Recognition
BFS traversal (queue-based) with the same visited hash map — the iterative analog of Problem 1's recursive DFS, sharing the same key invariant (map stores original→clone mapping) but using an explicit queue instead of the call stack.

### Key Insight
Creating the clone for a node and recording it in the visited map must happen **at the moment the node is first enqueued** (not when it's dequeued for processing) — this ensures the clone already exists in the map when any of its neighbors are processed and need to reference it, exactly analogous to the DFS approach's "store in map before recursing."

### Approach
Create and map the start node's clone; enqueue the start node. Loop: dequeue a node, iterate its neighbors — for each unvisited neighbor, create and map its clone and enqueue it; add the (existing or newly-created) neighbor clone to the current node's clone's neighbor list.

### Solution

```js
function cloneGraphBFS(node) {
  if (node === null) return null;

  const visited = new Map();
  // Create start node's clone and record it BEFORE entering the loop
  visited.set(node, new Node(node.val, []));
  const queue = [node];

  while (queue.length > 0) {
    const current = queue.shift();
    const currentClone = visited.get(current);

    for (const neighbor of current.neighbors) {
      if (!visited.has(neighbor)) {
        // Clone the neighbor and record it before enqueuing
        visited.set(neighbor, new Node(neighbor.val, []));
        queue.push(neighbor);
      }
      // Always wire the edge: currentClone → neighborClone
      // (whether neighborClone was just created or already existed)
      currentClone.neighbors.push(visited.get(neighbor));
    }
  }

  return visited.get(node);
}
```

### Complexity
- Time: O(V + E) — every node enqueued and dequeued exactly once, every edge processed once.
- Space: O(V) — the visited map plus the queue, both bounded by V at any point.

### Edge Cases
- Same as Problem 1 — null input, single node, self-loops.
- Very deep path-shaped graph (e.g., 1→2→3→...→1,000,000 in a chain with a back edge): BFS processes level by level and the queue never exceeds the graph's maximum width — for a path, width is 1-2 at any point, and no stack overflow risk. This is the main practical advantage over the recursive DFS for pathological input shapes.

### Follow-up Questions
- "Which is preferable in production — DFS or BFS?" → BFS for large graphs (no stack overflow risk); DFS recursive for small-to-medium graphs where code clarity matters most. The iterative DFS (using an explicit stack instead of a queue in the BFS) is a hybrid that avoids recursion depth but processes nodes in depth-first order, if that matters for some application-specific reason.
- "How would you verify the clone is correct programmatically?" → See Q12 — BFS over both graphs simultaneously, checking node identity (original nodes not reference-equal to clone nodes), value equality, neighbor count equality, and consistent neighbor identity mapping.

## Problem 3 — Clone Graph with Node Value Mapping (Variation)

### Problem
Clone a directed graph where nodes are given as a list (not just a single start node), and node values are not necessarily unique. Return the list of cloned root nodes in the same order.

```
Input:  nodes = [A(1), B(1), C(2)]  with edges A→B, A→C, B→C
(node A and node B both have value 1, but are distinct objects)

Output: [cloneA(1), cloneB(1), cloneC(2)]
with edges cloneA→cloneB, cloneA→cloneC, cloneB→cloneC
```

### Pattern Recognition
Same DFS/BFS clone-graph technique, but emphasizing two key points: (1) the visited map must be keyed by **node reference** (not value), since values are not unique; and (2) the entry point is a list of nodes rather than a single start node, requiring iteration over all provided nodes to ensure full coverage.

### Key Insight
Non-unique node values make the "use value as map key" shortcut (Q16's anti-pattern) completely unusable here — distinguishing the two nodes both with value 1 requires object identity as the key. The same `new Map()` with object-reference keys handles this correctly without any extra effort in JavaScript (and equivalent languages with reference-based equality for map keys).

### Approach
For each node in the input list, run the DFS clone (same as Problem 1) with a shared `visited` map across all starting nodes — this ensures nodes reachable from multiple starting points are still only cloned once.

### Solution

```js
function cloneNodes(nodes) {
  if (nodes === null || nodes.length === 0) return [];

  const visited = new Map();

  function dfsClone(node) {
    if (node === null) return null;
    if (visited.has(node)) return visited.get(node);

    const clone = new Node(node.val, []);
    visited.set(node, clone);

    for (const neighbor of node.neighbors) {
      clone.neighbors.push(dfsClone(neighbor));
    }

    return clone;
  }

  // clone each node in the input list, sharing the visited map across all calls
  return nodes.map(n => dfsClone(n));
}
```


### Complexity
- Time: O(V + E) total across all `dfsClone` calls — the shared `visited` map ensures each node is processed at most once, regardless of how many starting nodes reference it.
- Space: O(V) for the shared visited map plus O(V) recursion depth.

### Edge Cases
- Empty input list: immediately returns an empty array.
- A node appears multiple times in the input `nodes` list: the visited map ensures it's only cloned once; subsequent calls for the same node return the existing clone via the map.
- Graph with no edges (isolated nodes in a directed graph): each node is cloned independently with an empty neighbors list; no recursion beyond each initial call.

### Follow-up Questions
- "What if nodes had unique IDs separate from their values?" → Use the unique ID as the map key instead of the object reference — functionally identical; the ID plays the same role as object identity.
- "What if the graph could contain null nodes in the neighbors list?" → Add a `if (neighbor === null) { clone.neighbors.push(null); continue; }` check inside the neighbor loop — preserving null entries in the adjacency list as part of the structural deep copy.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve deep-copying a graph (or graph-like structure with cycles)?
│
├── IS THE GRAPH KNOWN TO BE ACYCLIC (a tree or DAG)?
│   └── Standard recursive copy is safe — no cycle risk, no need for a visited map
│       (though the map still works correctly for DAGs — it's just unnecessary overhead)
│
├── CAN THE GRAPH CONTAIN CYCLES (undirected, or directed with back edges)?
│   └── MUST use a visited map (original node reference → clone node)
│       checking BEFORE any recursive call or neighbor traversal
│       │
│       ├── GRAPH IS SMALL-TO-MEDIUM, recursion depth not a concern?
│       │   └── DFS recursive — concise, natural, easy to reason about
│       │
│       ├── GRAPH COULD BE VERY LARGE / DEEP (risk of stack overflow)?
│       │   └── BFS iterative (queue) or DFS iterative (explicit stack)
│       │       — same visited map, no recursion depth limit
│       │
│       └── MULTIPLE STARTING NODES or full node list given?
│           └── Share ONE visited map across all starting-node DFS/BFS calls
│               — prevents duplicate clones for nodes reachable from multiple starts
│
├── NODE VALUES ARE NOT UNIQUE?
│   └── Map key MUST be the node reference (object identity), not the value
│       (JS Map naturally supports object reference keys — no special handling needed)
│
└── VERIFICATION: Is the clone correct?
    ├── No original node references in any clone's neighbor list
    ├── Same value and neighbor count at every corresponding node
    └── Two original edges to the same node → two clone edges to the SAME (not two different) clone
```

## Common Bugs Checklist

Before submitting any clone-graph solution, verify:

1. **Visited map checked as the FIRST action upon encountering any node, before creating a clone or recursing?** — Checking after creating a clone but before recursing can still cause infinite loops in deeply nested cycles; checking before ANY processing is the only safe order.

2. **Visited map populated (node → clone stored) BEFORE the neighbor-iteration loop begins, not after?** — Storing after the loop means any cycle back to this node during the loop's recursive calls won't find the entry in the map and will create a duplicate clone.

3. **Map keyed by NODE REFERENCE, not node value?** — Using values as keys silently breaks for graphs with non-unique values; always use the node object reference itself as the key.

4. **BFS variant: neighbor clone created and mapped AT ENQUEUE TIME, not at dequeue time?** — Deferring clone creation to dequeue means when another already-dequeued node processes the same neighbor, it won't find a clone in the map and will create a duplicate.

5. **`null` input handled explicitly before accessing any node properties?** — Calling `node.val` or `node.neighbors` on a `null` input immediately throws; the null check must come first.

6. **Self-loops (a node is its own neighbor) handled correctly?** — The visited map check at the top of DFS handles this naturally (returns the existing clone on re-encounter), but worth explicitly tracing through to confirm for interview confidence.

7. **Multi-component graphs: all components cloned when a full node list is given?** — When iterating over a list of starting nodes, sharing the visited map across all calls ensures each node is cloned exactly once, even if reachable from multiple starting nodes in the list.

---

**Final Tip:** At the 5 YOE level, the most important thing to communicate immediately when presented with this problem is **why** a simple recursive copy fails (cycles cause infinite recursion; shared nodes get duplicated) and **what the visited map specifically prevents** (both infinite recursion AND structural identity violation). Stating those two failure modes clearly, before writing a single line of code, is the signal that separates someone who understands the problem from someone who has merely memorized the solution. The implementation itself is short — the depth of understanding is what the interview is testing.
