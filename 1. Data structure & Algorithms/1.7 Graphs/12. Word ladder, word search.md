## Topic A: Word Ladder Fundamentals

### Section A1: Fundamentals

**Q1. What is the Word Ladder problem, and what graph does it implicitly define?**
A: The Word Ladder problem asks: given a `beginWord`, an `endWord`, and a dictionary of words, find the shortest sequence of single-character transformations that converts `beginWord` into `endWord`, where every intermediate word must exist in the dictionary. Each transformation changes exactly one character.

The problem implicitly defines an **unweighted undirected graph** where:
- Each node is a word (from the dictionary plus `beginWord`).
- An edge exists between two words if they differ by exactly one character.
- The shortest word ladder = shortest path from `beginWord` to `endWord` in this graph.

```
beginWord="hit", endWord="cog", wordList=["hot","dot","dog","lot","log","cog"]

Implicit graph:
hit — hot — dot — dog — cog
              |         |
             lot — log ——
              
Shortest path: hit→hot→dot→dog→cog (length 5, 4 edges)
```

Since the graph is unweighted, BFS finds the shortest path in O(V + E) — no weighted shortest path algorithm needed. Recognizing "shortest path in an unweighted graph" → BFS is the single most important insight for Word Ladder.

**Q2. Why is BFS the correct algorithm for Word Ladder, and why not DFS or Dijkstra's?**
A: BFS finds the shortest path in an unweighted graph by exploring nodes level by level — level k contains all words reachable in exactly k transformations. The first time `endWord` is reached, it is guaranteed to be via the shortest path (fewest transformations). DFS explores deeply before backtracking — it would find *a* path but not necessarily the *shortest* path, requiring exhaustive exploration and producing O(V!) worst-case complexity. Dijkstra's works on weighted graphs — here all edges have weight 1, so BFS is strictly equivalent but simpler (no priority queue needed) and runs in O(V + E) vs. Dijkstra's O((V + E) log V).

**Q3. What is the key implementation challenge in Word Ladder, and how does the "generic state" pattern solve it?**
A: The key challenge is **efficiently finding all words in the dictionary that differ from a given word by exactly one character**. The naive approach compares the current word against every dictionary word — O(L · N) per BFS level (L = word length, N = dictionary size), giving O(L · N²) total — too slow for large dictionaries.

The **generic state (wildcard) pattern** solves this: for each word, generate all L "generic" forms by replacing each character with `*`. Preprocess the dictionary into a map from generic form → list of words. When expanding a node, generate its L generic forms and look up all neighbors in O(1) per lookup.

```
Word "hot" → generic forms: "*ot", "h*t", "ho*"
"dot" also maps to "*ot" and "d*t" and "do*"
"*ot" → ["hot", "dot", "lot"] — these are all neighbors via position 0

Map: { "*ot": ["hot","dot","lot"], "h*t": ["hot"], "ho*": ["hot"],
       "d*t": ["dot"], "do*": ["dot","dog"], ... }
```

This preprocessing is O(N · L) time and space. Each BFS step generates L wildcard keys and performs L O(1) lookups — total BFS cost O(N · L).

**Q4. How does the visited/seen set work in Word Ladder BFS, and why must words be removed from the word list (or a seen set maintained)?**
A: Without tracking visited words, BFS would revisit the same word multiple times, creating infinite loops (e.g., hot→dot→hot→dot...) and failing to terminate. The seen set (or removing words from the dictionary as they're visited) ensures each word is processed at most once. Two approaches:

**Approach 1 — Seen set**: maintain a `Set<String>` of visited words. On expanding a node, skip any neighbor already in the seen set. The seen set starts containing `beginWord`.

**Approach 2 — Mutate wordList**: remove each word from the word list (or the adjacency map) as it is enqueued. More cache-friendly (one fewer data structure) but modifies the input — acceptable when the input dictionary is a `Set` that supports O(1) deletion.

Both approaches are equivalent in correctness and complexity. The seen set is preferred in interviews (doesn't mutate inputs).

**Q5. What is Bidirectional BFS, and how does it improve Word Ladder performance?**
A: Bidirectional BFS runs two simultaneous BFS searches — one from `beginWord` forward and one from `endWord` backward — and terminates when the two frontiers meet. Standard BFS explores a ball of radius r around the source; at the meeting point, each frontier has radius r/2. If the branching factor is b, standard BFS explores O(b^r) nodes; bidirectional BFS explores O(2 · b^(r/2)) = O(b^(r/2)) nodes — an exponential improvement.

```
Standard BFS:       explores up to b^r nodes
Bidirectional BFS:  explores up to 2·b^(r/2) nodes

For b=5, r=10:
Standard:    5^10 ≈ 10 million nodes
Bidirectional: 2·5^5 ≈ 6,250 nodes  ← ~1600x fewer
```

Implementation: maintain two sets (forward and backward frontier). At each step, expand the smaller frontier (reduces total work). When any word in the new frontier already exists in the other frontier, the path is complete — length = forward_steps + backward_steps.

**Q6. What is the Word Ladder II variant, and how does it differ algorithmically from Word Ladder I?**
A: Word Ladder II asks for **all** shortest transformation sequences (not just the length). This is significantly harder:

- **Word Ladder I**: BFS, return the level count when `endWord` is first reached. Stop immediately — no need to enumerate paths.
- **Word Ladder II**: BFS to build a layered DAG (directed acyclic graph) of parent pointers — for each word, record all predecessors at the previous BFS level. Then DFS/backtrack through the parent DAG from `endWord` back to `beginWord` to enumerate all paths.

The key constraint: during BFS, do not mark a word as visited until the entire level where it first appears is processed. Multiple words at the same level may reach the same target word — all such predecessors must be recorded.

```
BFS builds parent DAG:
hit → hot → dot → dog → cog
             ↓         ↑
            lot → log ——

DFS on parent DAG (reversed) from cog:
  cog←dog←dot←hot←hit  ✓
  cog←log←lot←hot←hit  ✓
  cog←log←dot←hot←hit  ✓ (if log is reachable from dot — depends on wordList)
```

Word Ladder II is O(N · L + paths · path_length) — the path enumeration can be exponential in the worst case (all paths of minimal length), which is why it's a harder problem.

### Section A2: Advanced Patterns

**Q7. How does Word Ladder generalize to the "minimum genetic mutation" and "open the lock" problems?**
A: These problems share the same structure: a state space where each state has a fixed number of "neighbors" (reachable in one operation), and the goal is the fewest operations to reach a target state. BFS applies directly — the graph is implicit (neighbors computed on-the-fly, not stored), and the "dictionary" constraint (valid intermediate states) filters which neighbors are enqueued.

- **Minimum genetic mutation**: each gene string has 8 characters from {A, C, G, T}. Neighbors = all strings differing by one character that exist in the gene bank. Identical to Word Ladder with alphabet size 4.
- **Open the lock**: 4 dials, each 0-9, each dial can move ±1. Neighbors = 8 states (4 dials × 2 directions). Invalid states (deadends) are filtered. Goal = reach "0000" → target. BFS on the implicit state graph — no dictionary needed, all 10^4 = 10,000 states are the "dictionary."

The unifying pattern: **BFS on an implicit graph where neighbors are computed by a transformation rule and filtered by a validity constraint**.

**Q8. How do you reconstruct the actual word ladder path (not just its length)?**
A: Track the predecessor of each word during BFS. When a word `v` is first reached via neighbor `u`, record `prev[v] = u`. After BFS terminates, backtrack from `endWord` using `prev` pointers.

```js
function reconstructPath(prev, beginWord, endWord) {
  const path = [];
  let curr = endWord;
  while (curr) {
    path.push(curr);
    curr = prev[curr];
  }
  return path.reverse(); // beginWord → ... → endWord
}
```

This works for Word Ladder I (single shortest path). For Word Ladder II (all shortest paths), maintain `prev[v]` as a list of all predecessors at the same BFS level — then DFS through the predecessor DAG.

**Q9. What is the time and space complexity of the standard BFS Word Ladder solution?**
A: Let N = number of words in the dictionary, L = word length.

- **Preprocessing** (build generic-form map): O(N · L) time, O(N · L) space.
- **BFS**: each word is visited at most once (O(N) words). Per word, generate L wildcard keys (O(L)) and look up each in the map (O(1) average). Total BFS: O(N · L).
- **Overall**: O(N · L) time, O(N · L) space.

Without the generic-form map (naive neighbor-finding): O(N² · L) time — for each of N words, compare against all N words character by character (O(L) each).

## Topic B: Word Search Fundamentals

### Section B1: Fundamentals

**Q10. What is the Word Search problem, and what algorithm naturally solves it?**
A: Given a 2D character grid and a target word, determine whether the word exists as a path in the grid — where each step moves to an adjacent (up/down/left/right) cell, no cell is used twice in the same path. This is a **backtracking / DFS** problem: explore all possible paths from each grid cell, pruning early when the current prefix doesn't match the word.

```
Grid:          Word: "ABCCED"
A B C E
S F C S        Path: A(0,0)→B(0,1)→C(0,2)→C(1,2)→E(1,3)→D(2,3)? 
A D E E        Let's verify: grid[0][0]=A, grid[0][1]=B, grid[0][2]=C,
               grid[1][2]=C, grid[1][3]=S? No — need to re-examine.
               Actual: A(0,0)→B(0,1)→C(0,2)→C(1,2)→E(2,2)→D(2,1)? ✓
```

The algorithm: for each cell `(r, c)` in the grid, attempt to find the word starting at `(r, c)` using DFS. DFS tries all 4 directions at each step, checking that: (1) the next cell is within bounds; (2) the next cell's character matches the next character in the word; (3) the next cell hasn't been visited on the current path. Backtracking: mark a cell as visited before recursing; unmark it after returning.

**Q11. How is the visited state managed in Word Search, and why is in-place marking preferred?**
A: The visited state prevents using the same cell twice on the same path (the word must follow distinct cells). Two approaches:

**Approach 1 — Separate visited array**: maintain a `boolean[][] visited` array. Mark `visited[r][c] = true` before recursing into `(r, c)`, unmark after.

**Approach 2 — In-place marking (preferred)**: temporarily replace `grid[r][c]` with a sentinel character (e.g., `'#'` or `'\0'`) before recursing, then restore it afterward. This avoids the O(m·n) extra space of a separate visited array.

```js
function dfs(grid, word, r, c, idx) {
  if (idx === word.length) return true; // entire word matched
  if (r < 0 || r >= grid.length || c < 0 || c >= grid[0].length) return false;
  if (grid[r][c] !== word[idx]) return false; // character mismatch

  const temp = grid[r][c];
  grid[r][c] = '#'; // mark as visited (in-place)

  const found =
    dfs(grid, word, r+1, c, idx+1) ||
    dfs(grid, word, r-1, c, idx+1) ||
    dfs(grid, word, r, c+1, idx+1) ||
    dfs(grid, word, r, c-1, idx+1);

  grid[r][c] = temp; // restore (backtrack)
  return found;
}
```

In-place marking is preferred for interviews: O(1) extra space (beyond the recursion stack), cleaner code, and no initialization overhead.

**Q12. What is the time and space complexity of Word Search?**
A: Let m = rows, n = columns, L = word length.

- **Time**: O(m · n · 4^L) in the worst case. For each of m·n starting cells, the DFS explores at most 4 directions at each of L steps. In practice, early termination (character mismatch) dramatically reduces the search space. The tighter bound is O(m · n · 3^L) since after the first step, one of 4 directions leads back to the parent (already visited) — only 3 new directions remain.
- **Space**: O(L) — the recursion stack depth equals the word length (at most L frames). The in-place visited marking uses O(1) extra space beyond the stack.

**Q13. What is Word Search II, and how does a Trie change the approach?**
A: Word Search II asks to find all words from a given list that exist in the grid. The brute-force approach — run Word Search I for each word separately — is O(W · m · n · 4^L) where W = number of words, too slow when W is large.

The **Trie-based approach** solves all words simultaneously:
1. Build a Trie from all words in the list.
2. DFS from each cell, traversing the Trie alongside the grid — at each cell, check if the current character leads to a valid Trie node. If not, prune immediately.
3. When a Trie node marked as a complete word is reached, record that word as found.
4. **Pruning optimization**: remove found words from the Trie (`delete node.word` after recording) to prevent duplicate entries and allow further pruning.

```js
function findWords(board, words) {
  // Build Trie
  const root = {};
  for (const word of words) {
    let node = root;
    for (const ch of word) {
      if (!node[ch]) node[ch] = {};
      node = node[ch];
    }
    node.word = word; // mark end of word
  }

  const result = [];
  const m = board.length, n = board[0].length;

  function dfs(r, c, node) {
    if (r < 0 || r >= m || c < 0 || c >= n) return;
    const ch = board[r][c];
    if (ch === '#' || !node[ch]) return; // visited or no Trie path

    const next = node[ch];
    if (next.word) {
      result.push(next.word);
      delete next.word; // prevent duplicates
    }

    board[r][c] = '#'; // mark visited
    dfs(r+1, c, next); dfs(r-1, c, next);
    dfs(r, c+1, next); dfs(r, c-1, next);
    board[r][c] = ch; // restore
  }

  for (let r = 0; r < m; r++)
    for (let c = 0; c < n; c++)
      dfs(r, c, root);

  return result;
}
```

The Trie enables shared prefix processing — all words with the same prefix share the same Trie traversal path, avoiding redundant work.

**Q14. What additional pruning can be applied to Word Search II to improve practical performance?**
A: Beyond the basic Trie traversal, three additional pruning techniques:

1. **Delete exhausted Trie nodes**: after fully exploring a Trie node (all its children are processed or deleted), remove the node from its parent. This prevents revisiting dead Trie branches in future DFS calls — the Trie shrinks as words are found.

2. **Word length bounds**: before starting DFS from any cell, check if the remaining grid cells (unvisited) are sufficient to spell any remaining word. If the longest remaining word length exceeds the number of unvisited cells, skip.

3. **Character frequency filter**: before DFS from cell `(r, c)`, check if the character `grid[r][c]` exists in the Trie's root children. If the character doesn't start any remaining word, skip this cell immediately — O(1) check, saves starting entire DFS subtrees.

### Section B2: Advanced Patterns

**Q15. How does Word Search relate to Hamiltonian path problems, and why is it generally NP-complete?**
A: Word Search on an arbitrary grid with an arbitrary word is NP-complete in the general case because it reduces to the Hamiltonian path problem: if the word uses every cell in the grid exactly once, finding the word is equivalent to finding a Hamiltonian path through the grid visiting cells in a specific character sequence order. The standard interview version (small fixed grids, L << m·n) is tractable because: (a) early termination on character mismatch prunes the vast majority of paths, and (b) the practical grid sizes (typically ≤ 6×6 in interviews, ≤ 200×200 in LeetCode) keep the backtracking tractable.

**Q16. How do you handle the Word Search problem when the word can wrap around the grid edges (toroidal grid)?**
A: Replace the boundary check `r < 0 || r >= m || c < 0 || c >= n` with modular arithmetic: `r = ((r % m) + m) % m` and `c = ((c % n) + n) % n`. All other logic (in-place marking, backtracking, character matching) remains identical. The modular indices ensure that moving off one edge wraps to the opposite edge. The key constraint: the visited/in-place marking is more critical here because cycles are possible (paths can wrap around and revisit a cell) — the `'#'` sentinel correctly prevents this.

**Q17. What is the "number of distinct paths" variant of Word Search, and how does it change the algorithm?**
A: Instead of returning a boolean (does the word exist?), count all distinct paths in the grid that spell the word. The backtracking structure is identical, but: (a) don't terminate early on finding the first complete path — continue to find all paths; (b) at the base case (`idx === word.length`), return 1 instead of `true`; (c) sum the results from all 4 directions instead of short-circuiting with `||`.

```js
function countPaths(grid, word, r, c, idx) {
  if (idx === word.length) return 1; // found one complete path
  if (out_of_bounds || grid[r][c] !== word[idx]) return 0;

  const temp = grid[r][c];
  grid[r][c] = '#';

  // SUM all paths (don't short-circuit)
  const count =
    countPaths(grid, word, r+1, c, idx+1) +
    countPaths(grid, word, r-1, c, idx+1) +
    countPaths(grid, word, r, c+1, idx+1) +
    countPaths(grid, word, r, c-1, idx+1);

  grid[r][c] = temp;
  return count;
}
```

This variant has no pruning advantage from early termination — must explore all valid paths — making it strictly O(m · n · 4^L) in the worst case.

**Q18. How does the Knight's tour problem relate to Word Search, and what is the structural difference?**
A: Both Knight's tour and Word Search use backtracking DFS on a 2D grid where each step must land on a valid, unvisited cell. The differences: (a) Knight's tour uses chess knight moves (L-shaped, up to 8 neighbors) instead of 4-directional moves; (b) Knight's tour must visit every cell (Hamiltonian path), while Word Search only needs to match a word of length L ≤ m·n; (c) Word Search has a character-matching pruning condition that drastically reduces the search space — Knight's tour has no equivalent early termination, making it harder in practice. The Warnsdorff heuristic (choose the next cell with the fewest onward moves) speeds up Knight's tour by pruning; Word Search uses character matching as its primary pruning mechanism.

## Topic C: Shared Patterns — Graph Search on Implicit Graphs

### Section C1: Fundamentals

**Q19. What is the "implicit graph" pattern, and how do Word Ladder and Word Search both exemplify it?**
A: An implicit graph is one where nodes and edges are defined by a transformation rule rather than an explicit adjacency list — the graph is too large to store explicitly (or doing so would be unnecessary). Both problems use this pattern:

- **Word Ladder**: the graph has N nodes (words) and edges between words differing by one character. Building the full adjacency list is O(N² · L) — too expensive. Instead, neighbors are computed on-the-fly using the wildcard map. The graph is implicit — it exists conceptually but is never fully materialized.
- **Word Search**: the graph has m·n nodes (grid cells) and edges between adjacent cells with matching characters. The character-matching constraint changes per query — the "graph" is re-built implicitly for each DFS path attempt. Pre-computing all valid edges for all possible words is infeasible.

The general pattern for implicit graph search:
1. Define the **state** (a word, a grid cell + index, a lock combination).
2. Define the **neighbor function** (one-character change, one grid step, one dial turn).
3. Define the **validity filter** (in dictionary, matches character, not a deadend).
4. Apply BFS (for shortest path) or DFS/backtracking (for existence/enumeration).

**Q20. What is the "state space search" mental model, and how does it unify Word Ladder, Word Search, and related problems?**
A: State space search models a problem as: start state, goal state, state transition function, and goal test. BFS/DFS explore the state space systematically. This unifies:

| Problem | State | Transitions | Goal |
|---|---|---|---|
| Word Ladder | Current word | All 1-char changes in dict | Reach endWord |
| Word Search | (row, col, charIdx) | 4-directional moves | charIdx = word.length |
| Open the Lock | 4-digit combo | ±1 on any digit | Reach "0000" |
| Sliding Puzzle | Board configuration | Slide adjacent tile | Reach solved config |
| Knight's tour | (row, col, visited) | 8 knight moves | visited = all cells |

BFS finds shortest paths in state spaces with uniform edge costs. DFS + backtracking enumerates all paths or checks existence. The choice of BFS vs. DFS depends on whether the goal is "shortest" (BFS) or "exists/all" (DFS).

### Section C2: Advanced Patterns

**Q21. How does A* search improve on BFS for Word Ladder when the state space is large?**
A: A* search augments BFS with a heuristic function `h(word)` that estimates the remaining distance to `endWord`. The priority queue sorts by `f(word) = g(word) + h(word)` where `g` = actual distance from source and `h` = heuristic distance to target. For Word Ladder, a natural heuristic: `h(word)` = number of characters that differ between `word` and `endWord` (Hamming distance). This heuristic is admissible (never overestimates) because each transformation can change at most one character.

A* with an admissible heuristic is guaranteed to find the shortest path and typically explores far fewer nodes than BFS — it focuses the search toward the goal rather than exploring uniformly in all directions. For large word lists where BFS explores thousands of words, A* can reduce the search to the most promising candidates. In interviews, BFS is the expected answer — A* is a bonus discussion point for "how would you optimize this?"

**Q22. What is the "word break" problem, and how does it relate to Word Ladder's state graph structure?**
A: Word Break asks: given a string `s` and a dictionary, can `s` be segmented into dictionary words? This is a DP problem, not a graph search — but the structural connection: the implicit DAG where node `i` represents "successfully matched the first `i` characters of `s`" and edges exist when `s[i..j]` is a dictionary word. DP on this DAG finds whether a path from node 0 to node `len(s)` exists. Word Ladder also uses an implicit graph, but the graph's structure (word-to-word transformations) differs from Word Break's structure (string segmentation). The shared theme: both build and traverse an implicit graph defined by a dictionary, rather than an explicitly listed graph.

## Topic D: Cross-Topic & Interview-Style Questions

**Q23. "You're given a Word Ladder problem with a large dictionary (100,000 words). What optimizations do you apply?"**
A: Four optimizations in priority order:

1. **Wildcard map preprocessing**: build `generic_form → [words]` map in O(N·L). Eliminates O(N) neighbor comparison per word, reducing BFS to O(N·L).

2. **Bidirectional BFS**: expand from both `beginWord` and `endWord` simultaneously, always expanding the smaller frontier. Reduces explored nodes from O(b^r) to O(b^(r/2)) — exponential improvement for large r (long ladders).

3. **Early termination in bidirectional BFS**: when generating the new frontier, check if any new word exists in the opposite frontier before adding it to the current frontier. The first intersection is the shortest path — stop immediately.

4. **Frontier set (not queue)**: bidirectional BFS works best with sets (HashSets) rather than queues — membership testing in the opposite frontier is O(1) vs. O(N) for a queue scan.

```
Combined complexity: O(N·L) preprocessing + O(b^(r/2) · L) BFS
For N=100,000, L=5, b=5, r=10: significantly better than naive O(N²·L)
```

**Q24. "How do you handle Word Search when the grid is very large (e.g., 200×200) and the word is long?"**
A: Three practical optimizations:

1. **Character frequency pre-filter**: before any DFS, count character frequencies in the grid and in the word. If the word requires more of any character than the grid contains, immediately return `false` — O(m·n + L) check.

2. **Start from the rarer end**: if `word[0]` appears many times in the grid but `word[L-1]` appears rarely, reverse the word and search for the reversed word (same answer — the path is valid in reverse too). Starting DFS from the rarer endpoint dramatically reduces the number of DFS starting points.

3. **Constraint propagation**: for each potential starting cell `(r, c)` where `grid[r][c] === word[0]`, check if the surrounding cells have sufficient characters to spell the rest of the word (rough bound check). Skip starting cells that clearly can't lead to a solution.

**Q25. "What is the relationship between Word Ladder and BFS on graphs? Can you frame it as a graph problem precisely?"**
A: Word Ladder is exactly BFS for single-source shortest path on an unweighted undirected graph `G = (V, E)` where:
- `V` = `{beginWord} ∪ wordList` (every valid word is a node).
- `E` = `{(u, v) : Hamming_distance(u, v) = 1}` (words differing by one character).
- Source = `beginWord`, Target = `endWord`.
- All edge weights = 1 (unweighted).
- Query: shortest path length from source to target in G.

BFS on unweighted graphs finds shortest paths in O(V + E). Here V = N (dictionary size), E = O(N · L · 26) in the worst case (each word has at most L·25 neighbors — for each of L positions, 25 possible character substitutions). The wildcard map makes neighbor lookup efficient without explicitly building E.

**Q26. "What are the common bugs in Word Ladder and Word Search implementations, and how do you avoid them?"**
A: The most common bugs:

**Word Ladder**:
- Not adding `beginWord` to the seen set before BFS starts — causes `beginWord` to be re-enqueued as a neighbor of one of its own neighbors.
- Not handling the case where `endWord` is not in the dictionary — standard BFS returns 0 (not found), but the off-by-one in the level counter can cause returning 1 instead.
- Level counting: returning the queue level vs. the number of transformations. A transformation sequence of length k has k-1 edges — decide upfront whether "length" means nodes or edges.
- Forgetting to handle `beginWord === endWord` — should return 1 (the sequence is just the word itself, 0 transformations).

**Word Search**:
- Forgetting to restore `grid[r][c]` after the DFS returns — the grid remains permanently modified, corrupting future DFS calls from other starting cells.
- Not checking all starting cells — only checking cells where the first character matches, but forgetting the outer double loop over all `(r, c)`.
- Off-by-one in the termination condition: `if (idx === word.length) return true` vs. `if (idx === word.length - 1 && grid[r][c] === word[idx]) return true`. The former is cleaner — check bounds first, then the character match for the current index.
- Using `==` for character comparison in languages where strings and characters are different types.

**Q27. "In one sentence each, state the core algorithmic insight for Word Ladder, Word Search, and Word Search II."**
A:
- **Word Ladder**: the word transformation graph is unweighted, so BFS finds the shortest ladder in O(N·L) using wildcard-keyed neighbor maps that avoid the O(N²·L) naive pairwise comparison.
- **Word Search**: the existence of a path through the grid is checked by backtracking DFS with in-place visited marking — the character mismatch at any step is the pruning condition that makes it tractable despite the 4^L worst-case bound.
- **Word Search II**: all words are found simultaneously by traversing a Trie alongside the grid DFS — shared prefixes are explored once, and found words are removed from the Trie to enable dead-branch pruning.

## Problem 1 — Word Ladder I (BFS + Wildcard Map)

### Problem
Given a `beginWord`, an `endWord`, and a `wordList`, return the number of words in the shortest transformation sequence from `beginWord` to `endWord`. Each transformed word must exist in `wordList`. If no such sequence exists, return 0.

```
Input:  beginWord="hit", endWord="cog",
        wordList=["hot","dot","dog","lot","log","cog"]
Output: 5   (hit→hot→dot→dog→cog)

Input:  beginWord="hit", endWord="cog",
        wordList=["hot","dot","dog","lot","log"]
Output: 0   (cog not in wordList, unreachable)
```

### Pattern Recognition
BFS on an unweighted implicit graph — shortest path from `beginWord` to `endWord` where edges connect words differing by one character. The wildcard map provides O(1) neighbor lookup.

### Key Insight
BFS level = number of transformations applied. The moment `endWord` is dequeued, its BFS level + 1 equals the sequence length (including both endpoints). The wildcard map converts O(N) neighbor comparison per node into O(L) map lookups — reducing total complexity from O(N²·L) to O(N·L).

### Approach
1. Build wildcard map: for each word in `wordList`, generate L wildcard patterns (`*it`, `h*t`, `hi*` for "hit") and map each pattern to the list of words matching it.
2. BFS from `beginWord`: enqueue `[beginWord, level=1]`. For each dequeued `[word, level]`: if `word === endWord`, return `level`. Generate L wildcard keys, look up neighbors, enqueue unseen neighbors at `level+1`. Mark words as seen when enqueued.
3. If BFS exhausts without finding `endWord`, return 0.

### Solution

```js
function ladderLength(beginWord, endWord, wordList) {
  const wordSet = new Set(wordList);
  if (!wordSet.has(endWord)) return 0; // endWord unreachable

  const L = beginWord.length;

  // Build wildcard map: pattern → list of matching words
  const wildcardMap = new Map();
  for (const word of wordList) {
    for (let i = 0; i < L; i++) {
      const pattern = word.slice(0, i) + '*' + word.slice(i + 1);
      if (!wildcardMap.has(pattern)) wildcardMap.set(pattern, []);
      wildcardMap.get(pattern).push(word);
    }
  }

  // BFS: queue stores [word, sequenceLength]
  const queue = [[beginWord, 1]];
  const seen = new Set([beginWord]); // prevent revisiting

  while (queue.length > 0) {
    const [word, level] = queue.shift();

    // Try all L wildcard patterns of current word
    for (let i = 0; i < L; i++) {
      const pattern = word.slice(0, i) + '*' + word.slice(i + 1);

      for (const neighbor of (wildcardMap.get(pattern) || [])) {
        if (neighbor === endWord) return level + 1; // found shortest path

        if (!seen.has(neighbor)) {
          seen.add(neighbor);
          queue.push([neighbor, level + 1]);
        }
      }
    }
  }

  return 0; // endWord not reachable
}
```

### Complexity
- Time: O(N·L²) — preprocessing: N words × L patterns × L-length pattern construction. BFS: O(N·L) node expansions.

### Edge Cases
- `endWord` not in `wordList`: return 0 immediately before BFS.
- `beginWord === endWord`: the problem guarantees they differ, but if equal, BFS level starts at 1 and the endWord check on the first dequeue returns 1.
- `beginWord` has no neighbors in `wordList`: queue empties after first dequeue, returns 0.
- `wordList` contains `beginWord`: works correctly — `beginWord` is in `seen` set, so it's skipped as a neighbor.

### Follow-up Questions

- "Return the actual path, not just its length?" → Track `prev[word] = predecessor` during BFS. After finding `endWord`, backtrack through `prev` from `endWord` to `beginWord` and reverse.
- "What if words can have different lengths?" → This changes the problem — a "transformation" would need to allow insertions/deletions (edit distance). Standard Word Ladder assumes fixed-length words.

## Problem 2 — Word Ladder II (BFS DAG + DFS Backtracking)

### Problem
Given `beginWord`, `endWord`, and `wordList`, return all shortest transformation sequences. Each sequence is a list of words `[beginWord, ..., endWord]`.

```
Input:  beginWord="hit", endWord="cog",
        wordList=["hot","dot","dog","lot","log","cog"]
Output: [["hit","hot","dot","dog","cog"],
         ["hit","hot","lot","log","cog"]]

Input:  beginWord="hit", endWord="cog",
        wordList=["hot","dot","dog","lot","log"]
Output: []
```

### Pattern Recognition
BFS to build a layered predecessor DAG (records all shortest-path predecessors for each word), then DFS/backtracking on the predecessor DAG to enumerate all shortest paths.

### Key Insight
Standard BFS marks words as visited immediately — but multiple words at the same level may all lead to the same target word. To capture all shortest paths, delay marking a word as globally visited until the entire level where it first appears is fully processed. Track `parents[word]` = set of all predecessors at the previous BFS level. Then DFS through the predecessor DAG from `endWord` back to `beginWord`.

### Approach
1. BFS with level-by-level processing: expand an entire level before marking any of its words as visited. For each newly reached word, record all its parents (predecessors at the current level).
2. If `endWord` was reached, DFS from `endWord` through the `parents` DAG, building paths in reverse and reversing at the base case.
3. Return all collected paths.

### Solution

```js
function findLadders(beginWord, endWord, wordList) {
  const wordSet = new Set(wordList);
  if (!wordSet.has(endWord)) return [];

  const L = beginWord.length;

  // Build wildcard map
  const wildcardMap = new Map();
  for (const word of [beginWord, ...wordList]) {
    for (let i = 0; i < L; i++) {
      const p = word.slice(0, i) + '*' + word.slice(i + 1);
      if (!wildcardMap.has(p)) wildcardMap.set(p, []);
      wildcardMap.get(p).push(word);
    }
  }

  // BFS: build parents DAG
  // parents[word] = set of all words that directly precede word on a shortest path
  const parents = new Map();
  parents.set(beginWord, new Set());

  let currentLevel = new Set([beginWord]);
  const visited = new Set([beginWord]);
  let found = false;

  while (currentLevel.size > 0 && !found) {
    const nextLevel = new Set();

    for (const word of currentLevel) {
      for (let i = 0; i < L; i++) {
        const pattern = word.slice(0, i) + '*' + word.slice(i + 1);
        for (const neighbor of (wildcardMap.get(pattern) || [])) {
          if (visited.has(neighbor)) continue; // already in a previous level

          if (!parents.has(neighbor)) parents.set(neighbor, new Set());
          parents.get(neighbor).add(word); // word is a parent of neighbor

          nextLevel.add(neighbor);
          if (neighbor === endWord) found = true;
        }
      }
    }

    // Mark ALL words in nextLevel as visited AFTER processing the full level
    // (ensures multiple words at same level can all be parents of same next-level word)
    for (const word of nextLevel) visited.add(word);
    currentLevel = nextLevel;
  }

  if (!found) return [];

  // DFS: reconstruct all paths from endWord back to beginWord using parents DAG
  const result = [];

  function dfs(word, path) {
    if (word === beginWord) {
      result.push([...path].reverse()); // path was built backwards
      return;
    }
    for (const parent of (parents.get(word) || [])) {
      path.push(parent);
      dfs(parent, path);
      path.pop(); // backtrack
    }
  }

  dfs(endWord, [endWord]);
  return result;
}
```

## Problem 3 — Word Search (Backtracking DFS)

### Problem
Given a 2D board of characters and a word, return `true` if the word can be constructed from letters of sequentially adjacent cells (horizontally or vertically adjacent). The same letter cell may not be used more than once.

```
Input:  board = [["A","B","C","E"],
                 ["S","F","C","S"],
                 ["A","D","E","E"]],
        word = "ABCCED"
Output: true   (A→B→C→C→E→D)

Input:  board = same, word = "SEE"
Output: true   (S(1,3)→E(2,3)→E(2,2)  or  S→E→E path)

Input:  board = same, word = "ABCB"
Output: false  (B can't be used twice)
```

### Pattern Recognition
Backtracking DFS — try every possible starting cell, explore all 4-directional paths, prune immediately on character mismatch, restore in-place visited marking on backtrack.

### Key Insight
The character at `grid[r][c]` must match `word[idx]` — this is the pruning condition. The in-place sentinel `'#'` marks visited cells without a separate array. The backtrack (restoring `grid[r][c]`) is essential: after a failed DFS subtree, the cell must be available for other starting cells or path continuations.

### Approach
Outer loop: try each `(r, c)` as starting cell. DFS: base case `idx === word.length` → return `true`. Check bounds, character match, and not-visited. Mark, recurse in 4 directions (short-circuit on first `true`), unmark. Return `false` if no direction succeeds.

### Solution

```js
function exist(board, word) {
  const m = board.length;
  const n = board[0].length;

  function dfs(r, c, idx) {
    // Base case: matched all characters
    if (idx === word.length) return true;

    // Bounds check
    if (r < 0 || r >= m || c < 0 || c >= n) return false;

    // Character mismatch or already visited (sentinel '#')
    if (board[r][c] !== word[idx]) return false;

    // Mark as visited (in-place: replace with sentinel)
    const temp = board[r][c];
    board[r][c] = '#';

    // Explore all 4 directions (short-circuit: return true on first success)
    const found =
      dfs(r + 1, c, idx + 1) ||
      dfs(r - 1, c, idx + 1) ||
      dfs(r, c + 1, idx + 1) ||
      dfs(r, c - 1, idx + 1);

    // Restore (backtrack): unmark the cell
    board[r][c] = temp;

    return found;
  }

  // Try every cell as a potential starting point
  for (let r = 0; r < m; r++) {
    for (let c = 0; c < n; c++) {
      if (dfs(r, c, 0)) return true;
    }
  }

  return false;
}
```

## Problem 4 — Word Search II (Trie + Backtracking)

### Problem
Given a 2D board of characters and a list of words, return all words on the board. Each word must be constructed from letters of sequentially adjacent cells. The same cell may not be used more than once per word.

```
Input:  board = [["o","a","a","n"],
                 ["e","t","a","e"],
                 ["i","h","k","r"],
                 ["i","f","l","v"]],
        words = ["oath","pea","eat","rain"]
Output: ["eat","oath"]
```

### Pattern Recognition
Trie + backtracking DFS — build a Trie from all words, then DFS from every cell traversing the Trie simultaneously. When a complete word is found in the Trie, record it. Prune when no Trie path exists for the current character.

### Key Insight
Multiple words share prefixes — the Trie ensures that shared prefixes are explored only once. When DFS reaches a cell whose character has no corresponding child in the current Trie node, the entire subtree is pruned (no word can start with this prefix). Deleting found words from the Trie prevents duplicates and enables further dead-branch pruning.

### Approach
1. Build Trie from `words` — each leaf node stores the complete word.
2. DFS from every `(r, c)`: traverse both the board and the Trie simultaneously. On entering `(r, c)`, check if `board[r][c]` is a child of the current Trie node. If not → prune. If yes → descend into that Trie child.
3. At each Trie node: if it has a `word` property → record the word, delete the property (prevent future duplicates).
4. In-place sentinel marking + restoration for visited cells.
5. After all starting cells are tried, return the result list.

### Solution

```js
function findWords(board, words) {
  const m = board.length, n = board[0].length;

  // Build Trie
  const root = {};
  for (const word of words) {
    let node = root;
    for (const ch of word) {
      if (!node[ch]) node[ch] = {};
      node = node[ch];
    }
    node.word = word; // mark complete word at leaf/intermediate node
  }

  const result = [];

  function dfs(r, c, trieNode) {
    // Bounds check or visited sentinel
    if (r < 0 || r >= m || c < 0 || c >= n) return;
    const ch = board[r][c];
    if (ch === '#') return; // visited on current path

    // No Trie child for this character → prune entire subtree
    if (!trieNode[ch]) return;

    const nextNode = trieNode[ch];

    // Found a complete word
    if (nextNode.word) {
      result.push(nextNode.word);
      delete nextNode.word; // remove to prevent duplicate entries
    }

    // Mark visited (in-place sentinel)
    board[r][c] = '#';

    // Explore all 4 directions with updated Trie node
    dfs(r + 1, c, nextNode);
    dfs(r - 1, c, nextNode);
    dfs(r, c + 1, nextNode);
    dfs(r, c - 1, nextNode);

    // Restore (backtrack)
    board[r][c] = ch;
  }

  // Launch DFS from every cell
  for (let r = 0; r < m; r++) {
    for (let c = 0; c < n; c++) {
      dfs(r, c, root);
    }
  }

  return result;
}
```


### Complexity
- Time: O(m·n·4·3^(L-1)) per DFS start, but Trie pruning dramatically reduces this in practice. Preprocessing: O(W·L) to build Trie (W = number of words, L = average word length). Overall: O(m·n·3^L + W·L).
- Space: O(W·L) for the Trie; O(L) recursion stack depth; O(k) result where k = number of found words.

### Edge Cases
- No words found: result remains empty; all DFS subtrees are pruned.
- Same word appears multiple times: `delete nextNode.word` after first find prevents duplicates in result.
- Word longer than board: the DFS naturally fails when the word length exceeds the traversable path length.
- All words share a single character prefix: the Trie's root has one child — all DFS calls from cells matching that character traverse the shared prefix once, then diverge.

### Follow-up Questions
- "Optimize by pruning dead Trie branches?" → After all children of a Trie node become empty (no more words reachable through it), delete it from its parent. Add after the recursive DFS calls: `if (Object.keys(nextNode).length === 0) delete trieNode[ch]`. This gradually shrinks the Trie as words are found, pruning future DFS calls.
- "What if the board changes between queries?" → Rebuild the Trie only when `words` changes. The DFS is re-run for each new board since the board is the dynamic component.
- "Return the paths (cell coordinates) for each found word?" → Track the current path `[(r,c)]` in the DFS alongside the Trie node. When a word is found, record the path.

## Quick Reference — Word Ladder & Word Search Pattern Decision Tree

```
Is the problem about transforming strings step by step through a dictionary?
│
└── WORD LADDER FAMILY
    │
    ├── Shortest number of transformations? → BFS on implicit word graph
    │   Build wildcardMap: word → L patterns → neighbors
    │   BFS level = transformation count
    │   Return level+1 when endWord is first reached
    │
    ├── All shortest transformation sequences? → BFS (build parent DAG) + DFS backtrack
    │   BFS: delay visited-marking until end of each level
    │   Record all parents per word (multiple parents allowed at same level)
    │   DFS: enumerate all paths from endWord through parent DAG to beginWord
    │
    ├── Large dictionary / long ladders? → Bidirectional BFS
    │   Two frontiers (forward from beginWord, backward from endWord)
    │   Always expand the smaller frontier
    │   Stop when frontiers intersect
    │
    └── Minimum mutations / open lock / sliding puzzle?
        → BFS on implicit state graph
        State = current configuration
        Neighbors = all states reachable in one operation, filtered by validity
        BFS level = minimum operations

Is the problem about finding words/paths in a 2D grid?
│
└── WORD SEARCH FAMILY
    │
    ├── Does single word exist in grid? → Backtracking DFS
    │   Try each cell as start
    │   DFS: check char match, mark visited (in-place '#'), recurse 4 dirs
    │   Backtrack: restore cell on return
    │   Short-circuit: return true on first complete match
    │
    ├── Find all words from a list? → Trie + Backtracking DFS
    │   Build Trie from word list
    │   DFS: traverse Trie alongside grid
    │   Prune when no Trie child for current char
    │   Record word on reaching Trie leaf; delete to prevent duplicates
    │   Prune dead Trie branches after exhausting for further speedup
    │
    ├── Count all distinct paths? → Backtracking DFS (no short-circuit)
    │   Sum results across all 4 directions instead of || (OR)
    │   Must explore all paths — no early termination
    │
    ├── Word wraps around grid (toroidal)? → Same DFS with modular indices
    │   Replace bounds check with modular arithmetic
    │
    └── Very large grid, long word? → Pre-filter + Optimized DFS
        1. Character frequency check (O(m·n + L))
        2. Start DFS from rarer endpoint of word
        3. Prune from cells that can't extend to viable paths

CHOOSING BFS vs DFS:
  BFS → "shortest", "minimum", "fewest steps"
  DFS → "exists", "all paths", "enumerate", "count paths"

IMPLICIT GRAPH PATTERN:
  State + Transition function + Validity filter → BFS or DFS
  Word Ladder: state=word, transition=1-char change, filter=in dictionary
  Word Search: state=(r,c,idx), transition=adjacent cell, filter=char match+unvisited
```

## Common Bugs Checklist

Before submitting any Word Ladder or Word Search solution, verify:

1. **Word Ladder: `endWord` in `wordList` check before BFS?** — If `endWord` is not in the word list, it can never be reached via valid transformations. Return 0 immediately. Without this check, BFS runs to completion and returns 0 anyway, but the early check saves the preprocessing step and clarifies intent.

2. **Word Ladder: `beginWord` added to `seen` set before BFS starts?** — Without this, `beginWord` can be re-enqueued as a neighbor of one of its own neighbors (the reverse edge exists in the undirected word graph), causing incorrect path lengths and infinite loops.

3. **Word Ladder: off-by-one in sequence length?** — "Sequence length" includes both endpoints. A ladder `A→B→C` has length 3 (3 words) but uses 2 transformations. BFS level starts at 1 (not 0) when `beginWord` is enqueued — or start at level 0 and add 1 at the return. Be consistent and test with a direct transformation (beginWord and endWord differ by 1 character → expected output 2).

4. **Word Ladder II: marking visited at end of level, not during expansion?** — If a word is marked visited immediately when added to `nextLevel`, other words at the same current level can't also add it as a parent. Must mark visited only after the full level is processed — after the inner `for (word of currentLevel)` loop completes.

5. **Word Search: restoring `grid[r][c]` after DFS regardless of success or failure?** — The in-place `'#'` marker must be restored whether the DFS succeeded or failed. If a successful DFS short-circuits (`return true`) without restoring, subsequent searches for other words (or other starting cells) will find `'#'` in cells that should be available. In JavaScript, the `||` short-circuit means the `board[r][c] = temp` line is NOT reached if `found` is returned early. Fix: assign `found` first, then restore, then return — or use try-finally.

   ```js
   // BUG: short-circuit bypasses restoration
   const found = dfs(...) || dfs(...) || ...;
   board[r][c] = temp;   // ← only reached if none returned true? NO — always reached.
   return found;
   // Actually in this pattern: board[r][c] = temp runs AFTER found is computed.
   // The || evaluates lazily but the assignment happens after all evaluation.
   // This is CORRECT — the bug is only if you write `return dfs() || dfs()` directly
   // without the intermediate `found` variable.
   ```

   The safest pattern: always assign to `found` first, then restore, then return `found`.

6. **Word Search: outer loop tries all starting cells, not just `(0,0)`?** — A common optimization bug: only starting DFS from cells where `board[r][c] === word[0]`. This is correct as an optimization but be careful: if the outer loop is missing entirely (single DFS from `(0,0)`), most words will not be found.

7. **Word Search II: `delete nextNode.word` after recording, not before?** — If the deletion happens before `result.push`, the word is lost. Delete only after successfully recording: `result.push(nextNode.word); delete nextNode.word`.

8. **Wildcard map includes `beginWord` patterns?** — `beginWord` may not be in `wordList` but its wildcard patterns are needed to find its neighbors. Ensure `beginWord` is added to the wildcard map (or handle separately) when building the map from `wordList` only.
