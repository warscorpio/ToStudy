## Part 1 — Theory & Interview Q&A

### Section 1: Fundamentals

**Q1. What problem does Union-Find solve, and why is it the right data structure for it?**
A: Union-Find (also called Disjoint Set Union, DSU) solves the **dynamic connectivity** problem: given a set of elements, efficiently support two operations —

- **Union(u, v)**: merge the set containing u with the set containing v (connect two elements).
- **Find(x)**: determine which set x belongs to (which "component" contains x), typically by returning a canonical **representative** (root) of that set.

And answer queries:
- **Connected(u, v)**: are u and v in the same set? Equivalent to `Find(u) === Find(v)`.

The structure is ideal when connectivity is **built incrementally** (edges added one at a time, never removed) and you need to answer "same component?" queries efficiently after each addition. BFS/DFS can answer connectivity in O(V + E) but must restart from scratch after each new edge — Union-Find amortizes this to near-O(1) per operation via two optimizations: **path compression** and **union by rank** (or size).

```
Initial: {0}, {1}, {2}, {3}, {4}   — 5 singletons

Union(0,1): {0,1}, {2}, {3}, {4}
Union(1,2): {0,1,2}, {3}, {4}
Union(3,4): {0,1,2}, {3,4}

Connected(0,2)? → Find(0)=Find(2)? → same root → TRUE
Connected(0,3)? → Find(0)=Find(3)? → different roots → FALSE

Union(2,3):  {0,1,2,3,4}

Connected(0,4)? → TRUE
```

**Q2. What is the naive implementation of Union-Find (no optimizations), and what are its complexities?**
A: The naive implementation uses a `parent` array where `parent[i] = i` initially (every element is its own root). `Find(x)` walks up the parent chain until it reaches a root (a node where `parent[x] === x`). `Union(u, v)` calls `Find` on both and sets one root's parent to the other.

```js
class UnionFindNaive {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
  }

  find(x) {
    while (this.parent[x] !== x) {
      x = this.parent[x]; // walk up
    }
    return x; // root
  }

  union(u, v) {
    const rootU = this.find(u);
    const rootV = this.find(v);
    if (rootU !== rootV) {
      this.parent[rootU] = rootV; // arbitrarily attach u's root to v's root
    }
  }

  connected(u, v) {
    return this.find(u) === this.find(v);
  }
}
```

The worst case is a degenerate chain: if you always union in the "wrong" order, the tree becomes a linked list of length n. `Find` then takes O(n) per call — O(n) per operation, O(n²) for n union operations. This is unacceptably slow for large inputs and is why both optimizations are necessary.

```
Worst case after Union(0,1), Union(1,2), Union(2,3):
parent: [0, 0, 1, 2]

Tree:      0
           |
           1
           |
           2
           |
           3

find(3): 3→2→1→0 — walks 3 steps
```

**Q3. What is path compression, and how does it work?**
A: Path compression is an optimization applied during `Find(x)`: after walking up the parent chain to find the root, go back and set every node along that path to point **directly to the root**. This flattens the tree so future `Find` calls on any of those nodes cost O(1). There are two variants:

- **Full path compression** (two-pass): first walk up to find the root, then walk up again to update all parents. Cleaner iterative version. Standard in interviews.
- **Path halving / path splitting** (one-pass): during the single walk up, point each node to its grandparent instead of its ultimate root. Slightly fewer writes but same asymptotic complexity. Often preferred in practice.

```js
// Full path compression (recursive — elegant, one-liner)
find(x) {
  if (this.parent[x] !== x) {
    this.parent[x] = this.find(this.parent[x]); // set parent to root recursively
  }
  return this.parent[x];
}

// Full path compression (iterative — safe for very deep trees, no stack overflow)
find(x) {
  // Step 1: find the root
  let root = x;
  while (this.parent[root] !== root) {
    root = this.parent[root];
  }
  // Step 2: compress — point all nodes on path directly to root
  while (this.parent[x] !== root) {
    const next = this.parent[x];
    this.parent[x] = root; // point directly to root
    x = next;
  }
  return root;
}

// Path halving (one-pass — same amortized complexity, fewer writes)
find(x) {
  while (this.parent[x] !== x) {
    this.parent[x] = this.parent[this.parent[x]]; // skip one level (grandparent)
    x = this.parent[x];
  }
  return x;
}
```

```
Before find(3) with path compression:
  0←1←2←3   (chain)

After find(3):
  parent[3]=0, parent[2]=0, parent[1]=0
  All point directly to root 0.
  Next find(3): one step. find(2): one step. find(1): one step.
```

**Q4. What is union by rank, and how does it prevent degenerate trees?**
A: **Union by rank** ensures that when merging two trees, the **shorter tree** (by rank — a proxy for height) is always attached **under the taller tree's root**. This prevents the "chain" worst case: by always attaching smaller trees under larger ones, the maximum height of any tree is bounded by O(log n) without path compression.

A **rank** starts at 0 for each node (a singleton has rank 0). When merging two trees of different ranks, the root with lower rank is attached under the root with higher rank — rank doesn't change. When merging two trees of equal rank, either root can become the new root — the new root's rank is incremented by 1.

```js
class UnionFindRank {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank   = new Array(n).fill(0); // all singletons start at rank 0
  }

  find(x) {
    if (this.parent[x] !== x) {
      this.parent[x] = this.find(this.parent[x]); // path compression
    }
    return this.parent[x];
  }

  union(u, v) {
    const rootU = this.find(u);
    const rootV = this.find(v);
    if (rootU === rootV) return false; // already same component

    // Attach smaller rank under larger rank
    if (this.rank[rootU] < this.rank[rootV]) {
      this.parent[rootU] = rootV;           // u's root under v's root
    } else if (this.rank[rootU] > this.rank[rootV]) {
      this.parent[rootV] = rootU;           // v's root under u's root
    } else {
      this.parent[rootV] = rootU;           // equal rank: either works; increment winner
      this.rank[rootU]++;
    }

    return true; // union performed (they were in different components)
  }
}
```

```
Rank evolution:
Union(0,1): rank[0]=rank[1]=0 → attach 1 under 0, rank[0]++ → rank[0]=1
            tree: 0←1

Union(0,2): rank[0]=1 > rank[2]=0 → attach 2 under 0
            tree: 0←1, 0←2

Union(0,3): rank[0]=1 > rank[3]=0 → attach 3 under 0
            tree: 0←1, 0←2, 0←3   (balanced star, height 1)

Union(4,5): rank[4]=rank[5]=0 → attach 5 under 4, rank[4]++ → rank[4]=1
Union(0,4): rank[0]=rank[4]=1 → attach 4 under 0, rank[0]++ → rank[0]=2
            Final tree: height 2, not O(n) chain.
```

**Q5. What is the amortized complexity of Union-Find with both path compression AND union by rank, and how is it described?**
A: With both optimizations together, the amortized cost per operation is **O(α(n))**, where α is the **inverse Ackermann function**. For all practical values of n (including n = 10^80, the estimated number of atoms in the observable universe), α(n) ≤ 4. It is effectively a constant — O(α(n)) is described as "nearly O(1)" or "practically O(1)" in every real context.

The formal proof uses a potential function argument and is outside interview scope — but the key points to state are:

- **Path compression alone**: O(log n) amortized per operation.
- **Union by rank alone**: O(log n) worst case per operation (guaranteed, not just amortized).
- **Both together**: O(α(n)) amortized per operation — the gold standard.

```
Summary table:
Optimization          | Find (worst) | Find (amortized) | Union
None                  | O(n)         | O(n)             | O(n)
Path compression only | O(n)         | O(log n)         | O(1)*
Union by rank only    | O(log n)     | O(log n)         | O(log n)
Both together         | O(log n)     | O(α(n)) ≈ O(1)   | O(α(n)) ≈ O(1)

*Union itself is O(1) after find — the find cost dominates.
```

### Section 2: Implementation Variants

**Q6. Should you use union by rank or union by size? What are the trade-offs?**
A: Both achieve O(log n) height bounds and O(α(n)) amortized complexity when combined with path compression. The practical differences:

- **Union by rank**: tracks an upper bound on tree height. Rank is an approximation — after path compression, the actual height may be less than the rank. Rank is never decremented even when path compression flattens the tree. Slightly more conservative.
- **Union by size**: tracks the exact number of nodes in each component. More directly useful when component sizes are needed for queries (e.g., "how many nodes in x's component?"). Size is always accurate; rank is an approximation.

```js
// Union by SIZE — preferred when component size queries are needed
class UnionFind {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.size   = new Array(n).fill(1); // all singletons have size 1
    this.components = n;                // track component count
  }

  find(x) {
    if (this.parent[x] !== x) {
      this.parent[x] = this.find(this.parent[x]); // path compression
    }
    return this.parent[x];
  }

  union(u, v) {
    const rootU = this.find(u);
    const rootV = this.find(v);
    if (rootU === rootV) return false;

    // Attach smaller component under larger component
    if (this.size[rootU] < this.size[rootV]) {
      this.parent[rootU] = rootV;
      this.size[rootV] += this.size[rootU]; // size of new root increases
    } else {
      this.parent[rootV] = rootU;
      this.size[rootU] += this.size[rootV];
    }

    this.components--; // one fewer component after successful union
    return true;
  }

  connected(u, v) { return this.find(u) === this.find(v); }

  getSize(x)      { return this.size[this.find(x)]; } // size of x's component
  getComponents() { return this.components; }          // total component count
}
```

In interviews, **union by size is generally preferred** because component size queries appear frequently in problems (e.g., "find the largest island," "count nodes in each group") and size is accurate while rank is approximate. Either is acceptable — state your choice and reason explicitly.

**Q7. How do you handle Union-Find when elements are strings or non-integer identifiers?**
A: The standard array-based DSU requires contiguous integer indices. For string or arbitrary identifiers, add a **coordinate compression** step: assign each unique identifier a sequential integer via a Map, then use the integer-indexed array internally.

```js
class UnionFindGeneric {
  constructor() {
    this.parent = new Map(); // id → parent id
    this.size   = new Map(); // id → component size
    this.components = 0;
  }

  // Add a new element (idempotent — safe to call even if already added)
  add(x) {
    if (!this.parent.has(x)) {
      this.parent.set(x, x); // x is its own parent (root)
      this.size.set(x, 1);
      this.components++;
    }
  }

  find(x) {
    if (!this.parent.has(x)) this.add(x); // auto-add unseen elements
    if (this.parent.get(x) !== x) {
      this.parent.set(x, this.find(this.parent.get(x))); // path compression
    }
    return this.parent.get(x);
  }

  union(u, v) {
    this.add(u); this.add(v);
    const rootU = this.find(u), rootV = this.find(v);
    if (rootU === rootV) return false;

    if (this.size.get(rootU) < this.size.get(rootV)) {
      this.parent.set(rootU, rootV);
      this.size.set(rootV, this.size.get(rootV) + this.size.get(rootU));
    } else {
      this.parent.set(rootV, rootU);
      this.size.set(rootU, this.size.get(rootU) + this.size.get(rootV));
    }
    this.components--;
    return true;
  }

  connected(u, v) { return this.find(u) === this.find(v); }
}

// Usage:
const uf = new UnionFindGeneric();
uf.union('alice', 'bob');
uf.union('bob', 'charlie');
uf.connected('alice', 'charlie'); // true
```

**Q8. How does the "weighted" or "bipartite" Union-Find work for problems that need to track relative relationships (not just group membership)?**
A: A **weighted Union-Find** augments each node with a weight relative to its parent, encoding a relationship (e.g., ratio, offset, or parity). This enables answering queries like "what is the ratio between x and y?" or "are x and y in different partitions of a bipartite graph?" The weight is propagated during `find` (path compression must also update weights along the path) and during `union` (the edge weight is used to compute the new relative weight to the root).

```js
// Bipartite / parity Union-Find:
// parity[x] = 0 if x is in the same partition as its root
// parity[x] = 1 if x is in the opposite partition from its root
class BipartiteUnionFind {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.parity = new Array(n).fill(0); // parity relative to parent
  }

  find(x) {
    if (this.parent[x] === x) return [x, 0]; // [root, parity to root]
    const [root, parentParity] = this.find(this.parent[x]);
    this.parent[x] = root;                          // path compression
    this.parity[x] ^= parentParity;                 // XOR accumulates parity
    return [root, this.parity[x]];
  }

  // Union u and v with the assertion that they are in DIFFERENT partitions
  union(u, v) {
    const [rootU, parU] = this.find(u);
    const [rootV, parV] = this.find(v);
    if (rootU === rootV) {
      // already in same component: check if parity contradicts the assertion
      return parU !== parV; // true if valid bipartite, false if contradiction
    }
    this.parent[rootU] = rootV;
    // parU XOR parity[rootU] should equal parV XOR 1 (opposite partitions)
    this.parity[rootU] = parU ^ parV ^ 1;
    return true;
  }
}
```

### Section 3: Classic Applications

**Q9. How does Union-Find power Kruskal's Minimum Spanning Tree algorithm?**
A: Kruskal's algorithm builds an MST by greedily adding the cheapest edge that doesn't form a cycle. Union-Find is the cycle-detection engine: an edge (u, v) creates a cycle if and only if u and v are already in the same component — i.e., `Find(u) === Find(v)`. If they're in different components, the edge is safe to add — call `Union(u, v)` to merge the components.

```js
function kruskal(n, edges) {
  // Sort edges by weight ascending — O(E log E)
  edges.sort((a, b) => a[2] - b[2]);

  const uf = new UnionFind(n);
  const mst = [];
  let totalWeight = 0;

  for (const [u, v, w] of edges) {
    if (uf.union(u, v)) {      // union returns true only if u and v were disconnected
      mst.push([u, v, w]);     // safe to add — no cycle created
      totalWeight += w;
      if (mst.length === n - 1) break; // MST complete (n-1 edges)
    }
    // else: u and v already connected — adding this edge would create a cycle, skip
  }

  return { mst, totalWeight };
}

// Example: n=4, edges=[[0,1,1],[1,2,2],[0,2,3],[2,3,4],[1,3,5]]
// Sorted: [[0,1,1],[1,2,2],[0,2,3],[2,3,4],[1,3,5]]
// Union(0,1): different components → add. MST: [0,1,1]
// Union(1,2): different components → add. MST: [0,1,1],[1,2,2]
// Union(0,2): SAME component (0-1-2 already connected) → skip.
// Union(2,3): different components → add. MST: [0,1,1],[1,2,2],[2,3,4]. Done.
// Total weight: 7
```

**Q10. How is Union-Find used to detect cycles in an undirected graph?**
A: For each edge (u, v) in the graph: if `Find(u) === Find(v)`, u and v are already in the same component — adding this edge would create a cycle. If `Find(u) !== Find(v)`, call `Union(u, v)` and continue. If any edge fails the check (both endpoints already connected), the graph has a cycle.

```js
function hasCycle(n, edges) {
  const uf = new UnionFind(n);

  for (const [u, v] of edges) {
    if (!uf.union(u, v)) {
      // union returned false: u and v were already connected — cycle detected
      return true;
    }
  }

  return false; // no cycle found
}
// Note: this works for UNDIRECTED graphs only.
// For directed graphs, cycle detection requires DFS with a recursion stack.
```

**Q11. How does Union-Find solve the "number of islands" / connected components problem, and how does it compare to BFS/DFS?**
A: For a static grid (all cells known upfront), iterate over every `1`-cell and union it with its adjacent `1`-cells (right and down, to avoid double-counting). Count distinct components at the end using the `components` counter maintained in the DSU.

```js
function numIslands(grid) {
  const rows = grid.length, cols = grid[0].length;
  const uf = new UnionFind(rows * cols);
  let landCells = 0;

  for (let r = 0; r < rows; r++) {
    for (let c = 0; c < cols; c++) {
      if (grid[r][c] === '1') {
        landCells++;
        // Union with right neighbor
        if (c + 1 < cols && grid[r][c+1] === '1') {
          uf.union(r * cols + c, r * cols + (c+1));
        }
        // Union with bottom neighbor
        if (r + 1 < rows && grid[r+1][c] === '1') {
          uf.union(r * cols + c, (r+1) * cols + c);
        }
      }
    }
  }

  // Count distinct roots among land cells
  const roots = new Set();
  for (let r = 0; r < rows; r++) {
    for (let c = 0; c < cols; c++) {
      if (grid[r][c] === '1') roots.add(uf.find(r * cols + c));
    }
  }
  return roots.size;
}
```

**Comparison with BFS/DFS**: for static grids, both are O(V + E) and equally valid — choose BFS/DFS if only the count is needed (simpler code), Union-Find if subsequent connectivity queries will be made or if cells are revealed dynamically (online processing). Union-Find shines in the **dynamic** variant: "cells are revealed one at a time, and after each reveal, report how many islands exist" — BFS/DFS would require O(V + E) per reveal; Union-Find handles each reveal in O(α(n)).

**Q12. What is the "accounts merge" problem, and how does Union-Find solve it?**
A: The accounts merge problem: given a list of accounts where each account is `[name, email1, email2, ...]`, merge accounts that share any email address (transitivity applies — if account A and B share an email, and B and C share a different email, all three merge into one).

Union-Find models emails as nodes: for each account, union all its emails together (they're all connected). After all unions, group emails by their root representative. This naturally handles transitive merging — a direct application of the core Union-Find "union and query components" capability.

```js
function accountsMerge(accounts) {
  const uf = new UnionFindGeneric();
  const emailToName = new Map(); // email → account name

  // Union all emails within each account
  for (const account of accounts) {
    const name = account[0];
    const firstEmail = account[1];
    for (let i = 1; i < account.length; i++) {
      emailToName.set(account[i], name);
      uf.union(firstEmail, account[i]); // connect all emails to the first email
    }
  }

  // Group emails by their root representative
  const rootToEmails = new Map();
  for (const email of emailToName.keys()) {
    const root = uf.find(email);
    if (!rootToEmails.has(root)) rootToEmails.set(root, []);
    rootToEmails.get(root).push(email);
  }

  // Build result: [name, sorted emails]
  const result = [];
  for (const [root, emails] of rootToEmails) {
    emails.sort();
    result.push([emailToName.get(root), ...emails]);
  }

  return result;
}
```

### Section 4: Advanced Patterns

**Q13. How does Union-Find handle the "redundant connection" problem — finding the edge that, when removed, makes a tree?**
A: In a tree with n nodes, there are exactly n-1 edges and no cycles. A graph with n nodes and n edges contains exactly one cycle — one edge is "redundant." Process edges one by one using Union-Find: for each edge (u, v), if `Find(u) === Find(v)`, this edge creates a cycle and is the redundant connection — return it. Otherwise, `Union(u, v)` and continue.

```js
function findRedundantConnection(edges) {
  const n = edges.length; // n edges, n nodes (nodes labeled 1..n)
  const uf = new UnionFind(n + 1); // 1-indexed

  for (const [u, v] of edges) {
    if (!uf.union(u, v)) {
      return [u, v]; // this edge connects already-connected nodes — redundant
    }
  }

  return []; // problem guarantees a redundant edge exists
}
```

**Q14. What is "offline" Union-Find with rollback (persistent DSU), and when do you need it?**
A: Standard Union-Find only supports union operations — once merged, two components cannot be separated (no "undo"). Some problems require processing queries in a specific order that involves **removing** edges or splitting components — requiring the ability to roll back union operations to a previous state.

**DSU with rollback** uses **union by rank WITHOUT path compression** (path compression is incompatible with rollback since it modifies the parent array non-reversibly). Instead, each union records the exact changes made (`{node, oldParent, oldRank}`) on a stack. Rolling back simply pops from the stack and restores the recorded values.

```js
class DSUWithRollback {
  constructor(n) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank   = new Array(n).fill(0);
    this.history = []; // stack of {node, oldParent, oldRank}
  }

  find(x) {
    // NO path compression — must preserve tree structure for rollback
    while (this.parent[x] !== x) x = this.parent[x];
    return x;
  }

  union(u, v) {
    let rootU = this.find(u), rootV = this.find(v);
    if (rootU === rootV) {
      this.history.push(null); // push sentinel: union was a no-op
      return false;
    }
    if (this.rank[rootU] < this.rank[rootV]) [rootU, rootV] = [rootV, rootU];
    // Record state BEFORE modification
    this.history.push({ node: rootV, oldParent: this.parent[rootV],
                        rankNode: rootU, oldRank: this.rank[rootU] });
    this.parent[rootV] = rootU;
    if (this.rank[rootU] === this.rank[rootV]) this.rank[rootU]++;
    return true;
  }

  rollback() {
    const record = this.history.pop();
    if (record === null) return; // was a no-op union
    this.parent[record.node] = record.oldParent;
    this.rank[record.rankNode] = record.oldRank;
  }
}
// Used in: offline dynamic connectivity, divide-and-conquer on edges,
// Codeforces-style competitive programming problems.
```

Without path compression, `find` is O(log n) per call (union by rank alone guarantees O(log n) height). This is the known trade-off: rollback capability costs the path-compression speedup, but O(log n) is still acceptable for most applications.

**Q15. How does Union-Find enable solving "number of operations to make network connected" and similar network problems?**
A: The "network connected" problem: given n computers, some connected by cables, add the minimum number of cables to make all computers connected. Union-Find directly answers both sub-questions:
- **How many extra cables exist?** — edges that union already-connected nodes (union returns false). These cables are "redundant" and can be reused.
- **How many additional connections are needed?** — (number of components - 1). You need exactly one cable per component boundary to merge all components into one.

```js
function makeConnected(n, connections) {
  const uf = new UnionFind(n);
  let redundant = 0;

  for (const [u, v] of connections) {
    if (!uf.union(u, v)) redundant++; // already connected — redundant cable
  }

  const needed = uf.getComponents() - 1; // need this many more connections
  return redundant >= needed ? needed : -1; // -1 if not enough spare cables
}
```

### Section 5: Scenario / Interview-Style Questions

**Q16. "Walk me through implementing Union-Find from scratch, with both optimizations."**
A: I'll build it with union by size (preferred over rank — gives exact component sizes) and path compression (recursive for conciseness, iterative for safety on very deep trees).

```js
class UnionFind {
  constructor(n) {
    this.parent     = Array.from({ length: n }, (_, i) => i);
    this.size       = new Array(n).fill(1);
    this.components = n;
  }

  find(x) {
    if (this.parent[x] !== x) {
      this.parent[x] = this.find(this.parent[x]); // path compression
    }
    return this.parent[x];
  }

  union(u, v) {
    const rootU = this.find(u);
    const rootV = this.find(v);
    if (rootU === rootV) return false; // same component — no-op

    // Union by size: smaller under larger
    if (this.size[rootU] >= this.size[rootV]) {
      this.parent[rootV] = rootU;
      this.size[rootU] += this.size[rootV];
    } else {
      this.parent[rootU] = rootV;
      this.size[rootV] += this.size[rootU];
    }

    this.components--;
    return true;
  }

  connected(u, v)  { return this.find(u) === this.find(v); }
  getSize(x)       { return this.size[this.find(x)]; }
  getComponents()  { return this.components; }
}
```

I'd note the four implementation decisions I made and why: (1) size over rank — size queries are useful and size is accurate; (2) path compression via recursion — clean and direct; (3) `union` returns a boolean — callers often need to know if a union actually happened (Kruskal's, cycle detection); (4) `components` counter — maintained in O(1) per union, avoids O(n) counting afterward.

**Q17. "Union-Find only supports merging, not splitting. How would you handle a problem where edges can be removed?"**
A: Standard Union-Find doesn't support edge removal — once merged, components can't be split. Three strategies depending on constraints:

- **Offline reversal**: if all removals are known in advance (offline queries), process events in reverse chronological order — a removal becomes a union when reversed. Use standard Union-Find on the reversed sequence.
- **DSU with rollback**: use union-by-rank without path compression to support explicit undo operations (see Q14). Each union is O(log n); rollback is O(1).
- **Link-Cut Trees**: a fully dynamic data structure supporting both link (union) and cut (split) in O(log n) amortized. Significantly more complex to implement — competitive programming territory, not standard interviews.
- **Restart approach** (simple but slow): rebuild the DSU from scratch after each deletion — O(V + E) per deletion. Acceptable only for very small graphs or few deletions.

In an interview, the offline reversal approach is the most elegant and interview-appropriate answer when applicable. Mention link-cut trees to signal awareness, but don't implement unless explicitly asked.

**Q18. "Your Union-Find uses recursion for path compression. When would you switch to the iterative version?"**
A: Switch to the iterative version when:
- **The graph could have chains of length >> 10,000**: JavaScript's default call stack is ~10,000–15,000 frames. A deeply skewed tree (built by unioning in a bad order before rank takes effect, or by intentionally adversarial input) could trigger a stack overflow in the recursive `find`. The iterative two-pass version (find root first, then compress) eliminates this risk entirely.
- **The runtime environment has a small stack limit**: some embedded environments or serverless functions have stricter stack limits.
- **Performance profiling shows function-call overhead is significant**: for very high-frequency `find` calls (millions per second), eliminating recursion can reduce overhead.

In interviews, always mention both versions and note this trade-off proactively — it demonstrates awareness of stack-overflow risks in production code that most candidates miss.

**Q19. "How would you use Union-Find to solve the problem: given n elements, process q queries of the form 'connect x and y' and 'are x and y connected?' — but x and y are given as strings."**
A: Use the string-keyed `UnionFindGeneric` from Q7, with auto-add semantics so unseen strings are initialized on first encounter:

```js
function processQueries(queries) {
  const uf = new UnionFindGeneric();
  const results = [];

  for (const query of queries) {
    if (query[0] === 'connect') {
      uf.union(query[1], query[2]);
    } else { // 'query'
      results.push(uf.connected(query[1], query[2]));
    }
  }

  return results;
}

// queries = [
//   ['connect', 'alice', 'bob'],
//   ['connect', 'bob', 'charlie'],
//   ['query', 'alice', 'charlie'],  → true
//   ['query', 'alice', 'dave'],     → false
// ]
```

The Map-based approach handles arbitrary string keys with O(1) average-case hash map operations, plus O(α(n)) for the DSU operations themselves. Total: O(q × α(n)) amortized for q queries.

**Q20. "Explain why path compression doesn't break the correctness of Find, even though it changes the tree structure."**
A: Path compression only changes which node is the **parent** of each compressed node — it sets each node on the path to point directly to the root instead of its intermediate parent. It does NOT change the **root** of any component. Since `Find(x)` is defined as "return the root of x's component," and path compression only changes intermediate parent pointers while leaving the root itself unchanged, every `Find` call still returns the same, correct root before and after compression.

More formally: path compression is a correctness-preserving optimization because it maintains the **component membership invariant**: for any node x, `Find(x)` returns r if and only if r is the root of x's component. Before compression, walking up the chain eventually reaches r. After compression, `parent[x] = r` directly — the answer is the same (r), just reached in one step instead of many. No component is split or merged by path compression; it's purely a structural flattening of the tree.

**Q21. "How would you test a Union-Find implementation for correctness?"**
A: Key test cases that probe both correctness and the optimizations:

- **Basic union and connectivity**: Union(0,1), Union(1,2) → Connected(0,2)=true, Connected(0,3)=false. Tests core functionality.
- **Self-connection**: Connected(x,x) must always return true before and after any unions. Find(x) must always return the same root as long as x's component doesn't change.
- **Union of already-connected elements**: Union(0,1), Union(0,1) again — must return false on the second call and not corrupt the structure. Component count must not decrease twice.
- **Transitivity across many unions**: Union(0,1), Union(2,3), Union(4,5), Union(1,3), Union(3,5) → Connected(0,5)=true. Tests that transitive connections are correctly tracked.
- **Component count accuracy**: after k successful unions (union returns true), component count should be n-k. After all elements are connected, component count = 1.
- **Component size accuracy**: after Union(0,1), getSize(0) = getSize(1) = 2. After Union(0,1), Union(1,2), getSize(0) = 3.
- **Path compression actually compresses**: after find(deepNode) on a chain, check that parent[deepNode] === root directly (not an intermediate node). Verifies compression happened.
- **Rank/size invariant**: after many unions, verify that the root of each component has the largest rank/size among all nodes in that component.
- **Large n stress test**: n = 100,000, random unions and queries — verify correctness against a naive O(n) implementation and measure performance is near-linear.
- **All elements as their own component**: n=5, no unions — every Connected(i,j) for i≠j returns false; every Connected(i,i) returns true; component count = 5.

## Problem 1 — Number of Connected Components in an Undirected Graph

### Problem
Given `n` nodes labeled 0 to n-1 and a list of undirected edges, return the number of connected components.

```
Input: n=5, edges=[[0,1],[1,2],[3,4]]
Output: 2

Input: n=5, edges=[[0,1],[1,2],[2,3],[3,4]]
Output: 1
```

### Pattern Recognition
Union-Find component counting — each successful union reduces the component count by 1. Start with n components (all singletons), subtract successful unions, return the remainder.

### Key Insight
The `components` counter maintained inside the DSU answers the question directly: start at n, decrement on each successful union (where the two endpoints were in different components). No post-processing or root-counting needed.

### Approach
Initialize Union-Find with n nodes (n components). For each edge, call `union(u, v)` — if it returns true (they were in different components), the component count decrements automatically. Return `getComponents()`.

### Solution

```js
class UnionFind {
  constructor(n) {
    this.parent     = Array.from({ length: n }, (_, i) => i);
    this.size       = new Array(n).fill(1);
    this.components = n; // starts at n (all singletons)
  }

  find(x) {
    if (this.parent[x] !== x) {
      this.parent[x] = this.find(this.parent[x]); // path compression
    }
    return this.parent[x];
  }

  union(u, v) {
    const rootU = this.find(u);
    const rootV = this.find(v);
    if (rootU === rootV) return false; // already connected — no change

    // Union by size: smaller component merges under larger
    if (this.size[rootU] >= this.size[rootV]) {
      this.parent[rootV] = rootU;
      this.size[rootU] += this.size[rootV];
    } else {
      this.parent[rootU] = rootV;
      this.size[rootV] += this.size[rootU];
    }

    this.components--; // successful union reduces component count
    return true;
  }

  getComponents() { return this.components; }
}

function countComponents(n, edges) {
  const uf = new UnionFind(n);
  for (const [u, v] of edges) {
    uf.union(u, v); // return value ignored — components counter handles it
  }
  return uf.getComponents();
}
```

### Dry Run

```

edge [0,1]:
  find(0)=0, find(1)=1. Different → union.
  size[0](1) >= size[1](1) → parent[1]=0, size[0]=2. components=4.
  parent=[0,0,2,3,4], size=[2,1,1,1,1]

edge [1,2]:

  find(2)=2. Different → union.

  parent=[0,0,0,3,4], size=[3,1,1,1,1]

edge [3,4]:
```

### Complexity
- Time: O(n + E × α(n)) ≈ O(n + E) — initialization O(n), each union O(α(n)).
- Space: O(n) — parent, size arrays.

### Edge Cases
- No edges: all singletons, return n. ✓
- All nodes connected in a line: n-1 successful unions, components=1. ✓
- Duplicate edges in input: second union of same pair returns false, components unchanged. ✓
- n=1, no edges: components=1. ✓

### Follow-up Questions
- "How does this compare to BFS/DFS?" → BFS/DFS is also O(n + E) but builds the adjacency list first (O(n + E) space). Union-Find skips the adjacency list — directly processes the edge list. For the count-only problem, Union-Find is simpler and uses less space. BFS/DFS is necessary if you need the actual component membership or graph traversal.
- "What if edges are added dynamically (one at a time, with a query after each)?" → Union-Find handles this naturally — each edge addition is one `union` call, each query is one `getComponents()` call, both O(α(n)). BFS/DFS would need to rebuild from scratch each time — O(n + E) per query.

## Problem 2 — Redundant Connection

### Problem
You are given a tree (n nodes, n-1 edges) with one extra edge added, creating exactly one cycle. Find and return the redundant edge — the one that can be removed to restore the tree. If multiple answers exist, return the one that appears last in the input.

```
Input: edges = [[1,2],[1,3],[2,3]]
Output: [2,3]
(Removing [2,3] leaves 1-2, 1-3 — a valid tree)

Input: edges = [[1,2],[2,3],[3,4],[1,4],[1,5]]
Output: [1,4]
```

### Pattern Recognition
Union-Find cycle detection — process edges in order; the first edge whose endpoints are already connected is the one that creates the cycle and is therefore redundant.

### Key Insight
A tree has n nodes and n-1 edges, all reachable from one root — no cycles. The input has n edges, so exactly one edge is redundant. Processing edges sequentially with Union-Find: the redundant edge is uniquely identified as the first edge (u, v) where `Find(u) === Find(v)` — meaning u and v were already connected through the other n-1 edges before this edge was encountered.

### Approach
Initialize Union-Find with n+1 nodes (1-indexed — nodes labeled 1 to n). Process each edge: if union returns false (both endpoints share a root), this is the redundant edge — return it. Problem guarantees exactly one redundant edge exists.

### Solution

```js
function findRedundantConnection(edges) {
  const n = edges.length;
  // Nodes are 1-indexed: allocate n+1 slots
  const parent = Array.from({ length: n + 1 }, (_, i) => i);
  const size   = new Array(n + 1).fill(1);

  function find(x) {
    if (parent[x] !== x) parent[x] = find(parent[x]); // path compression
    return parent[x];
  }

  function union(u, v) {
    const rootU = find(u), rootV = find(v);
    if (rootU === rootV) return false; // already connected — this edge is redundant
    if (size[rootU] >= size[rootV]) {
      parent[rootV] = rootU; size[rootU] += size[rootV];
    } else {
      parent[rootU] = rootV; size[rootV] += size[rootU];
    }
    return true;
  }

  for (const [u, v] of edges) {
    if (!union(u, v)) return [u, v]; // first edge that creates a cycle
  }

  return []; // problem guarantees this is never reached
}
```

### Dry Run

```
edges = [[1,2],[1,3],[2,3]]
n=3. parent=[0,1,2,3], size=[1,1,1,1]

edge [1,2]: find(1)=1, find(2)=2. Different → union. parent[2]=1, size[1]=2.
  parent=[0,1,1,3]

edge [1,3]: find(1)=1, find(3)=3. Different → union. parent[3]=1, size[1]=3.
  parent=[0,1,1,1]

edge [2,3]: find(2): parent[2]=1, parent[1]=1 → root=1.
            find(3): parent[3]=1 → root=1.
  rootU=1, rootV=1. SAME → return false.
Return [2,3] ✓
```

### Complexity
- Time: O(E × α(n)) ≈ O(E) — E edges, each processed with O(α(n)) union/find.
- Space: O(n) — parent and size arrays.

### Edge Cases
- Last edge is redundant: algorithm processes all n-1 valid edges first, then correctly identifies the last one. ✓
- First edge is redundant (impossible for a valid input — at least n-1 edges needed to connect n nodes before a cycle can form): problem guarantees exactly one redundant edge in a valid n-node, n-edge input. ✓
- Self-loop `[u, u]`: `find(u) === find(u)` always, so it's immediately identified as redundant. ✓

### Follow-up Questions
- "What if the graph is directed?" → The problem changes fundamentally — cycle detection in a directed graph requires DFS with a "currently in recursion stack" flag (the three-color DFS approach). Union-Find cannot detect directed cycles because it treats edges as undirected (Find ignores direction).
- "What if there are multiple redundant edges?" → Return the last one in the input order. The current algorithm returns the first redundant edge found when processing left-to-right. To find the last, collect all redundant edges and return the last, or process edges in reverse and find the first redundant in that order.

## Problem 3 — Accounts Merge

### Problem
Given a list of accounts where `accounts[i] = [name, email1, email2, ...]`, merge accounts that share any email. Return the merged accounts where each account's emails are sorted. Two accounts belong to the same person if they share at least one email (transitive).

```
Input:
  [["John","johnsmith@mail.com","john_newyork@mail.com"],
   ["John","johnsmith@mail.com","john00@mail.com"],
   ["Mary","mary@mail.com"],
   ["John","johnnybravo@mail.com"]]

Output:
  [["John","john00@mail.com","john_newyork@mail.com","johnsmith@mail.com"],
   ["Mary","mary@mail.com"],
   ["John","johnnybravo@mail.com"]]
```

### Pattern Recognition
Union-Find on email nodes — emails are vertices; each account declares that all its emails belong to the same person (union them all). After all unions, group emails by their root representative to get merged accounts.

### Key Insight
Union-Find models transitivity perfectly: if email A and email B appear in one account, and email B and email C appear in another account, then Union(A,B) and Union(B,C) make all three reachable from the same root — no explicit graph traversal needed. The root of each email's component becomes the "canonical" identifier for that merged account.

### Approach
For each account, union its first email with every other email (anchoring all emails to the first creates a star — efficient and correct). Build a `emailToName` map. After all unions, group emails by root into `rootToEmails` map. Build result: for each root, sort emails and prepend the name.

### Solution

```js
function accountsMerge(accounts) {
  const parent     = new Map();
  const size       = new Map();
  const emailToName = new Map();

  function add(x) {
    if (!parent.has(x)) { parent.set(x, x); size.set(x, 1); }
  }

  function find(x) {
    if (parent.get(x) !== x) parent.set(x, find(parent.get(x)));
    return parent.get(x);
  }

  function union(u, v) {
    const rootU = find(u), rootV = find(v);
    if (rootU === rootV) return;
    if (size.get(rootU) >= size.get(rootV)) {
      parent.set(rootV, rootU);
      size.set(rootU, size.get(rootU) + size.get(rootV));
    } else {
      parent.set(rootU, rootV);
      size.set(rootV, size.get(rootV) + size.get(rootU));
    }
  }

  // Step 1: union all emails within each account
  for (const account of accounts) {
    const name = account[0];
    for (let i = 1; i < account.length; i++) {
      add(account[i]);
      emailToName.set(account[i], name);
      if (i > 1) union(account[1], account[i]); // union to first email as anchor
    }
  }

  // Step 2: group emails by root
  const rootToEmails = new Map();
  for (const email of emailToName.keys()) {
    const root = find(email);
    if (!rootToEmails.has(root)) rootToEmails.set(root, []);
    rootToEmails.get(root).push(email);
  }

  // Step 3: build result (sorted emails, prepend name)
  const result = [];
  for (const [root, emails] of rootToEmails) {
    emails.sort();
    result.push([emailToName.get(root), ...emails]);
  }

  return result;
}
```

```
  A1: ["John","johnsmith@mail.com","john00@mail.com"]

Abbreviate emails: js=johnsmith, jny=john_newyork, j00=john00,
```

### Edge Cases

- All accounts share one email: all emails union into one giant component under one root. One merged account in output. ✓
- Emails shared transitively across three accounts (A shares with B, B shares with C, A and C have no common email): union(A_email, B_email) and union(B_email, C_email) transitively connects all three. ✓

### Follow-up Questions

The anchor choice is arbitrary; using the first email is a simple convention. Unioning consecutive pairs (0,1), (1,2), (2,3) also works but creates a chain before path compression flattens it.
- "What if the same email appears under different names?" → Problem guarantees this doesn't happen (each email belongs to exactly one person). If it could happen, the `emailToName` map's last write wins — which name to use would need an explicit conflict resolution strategy.

## Problem 4 — Satisfiability of Equality Equations

### Problem
You are given a list of strings `equations` where each equation is either `"a==b"` or `"a!=b"` (variables are single lowercase letters). Return true if all equations can be satisfied simultaneously, false otherwise.

```
Input: ["a==b","b!=c","b==c"]
Output: false  (b==c and b!=c contradict)

Input: ["c==c","b==d","x!=z"]
Output: true
```

### Pattern Recognition
Union-Find for equality propagation — process `==` equations first (union the two variables), then check `!=` equations for contradictions (if two variables that must be unequal are in the same component, return false).

### Key Insight
Equality is transitive: if a==b and b==c, then a==c. Union-Find models transitivity automatically — after processing all `==` equations, `find(x) === find(y)` if and only if x and y must be equal. A `!=` equation is violated exactly when its two variables are in the same component.

### Approach
Two-pass: Pass 1 — process all `==` equations, unioning the two variables. Pass 2 — process all `!=` equations; if any pair has the same root, return false. Return true if no contradiction found.

### Solution

```js
function equationsPossible(equations) {
  // 26 variables: 'a'=0, 'b'=1, ..., 'z'=25
  const parent = Array.from({ length: 26 }, (_, i) => i);
  const size   = new Array(26).fill(1);

  function find(x) {
    if (parent[x] !== x) parent[x] = find(parent[x]);
    return parent[x];
  }

  function union(u, v) {
    const rootU = find(u), rootV = find(v);
    if (rootU === rootV) return;
    if (size[rootU] >= size[rootV]) {
      parent[rootV] = rootU; size[rootU] += size[rootV];
    } else {
      parent[rootU] = rootV; size[rootV] += size[rootU];
    }
  }

  // Pass 1: process all '==' equations — build equality components
  for (const eq of equations) {
    if (eq[1] === '=') { // eq[1]==='=' means it's "a==b" (eq[1] and eq[2] are '=')
      const u = eq[0].charCodeAt(0) - 97; // 'a'→0, 'b'→1, etc.
      const v = eq[3].charCodeAt(0) - 97;
      union(u, v);
    }
  }

  // Pass 2: check all '!=' equations — contradiction if same component
  for (const eq of equations) {
    if (eq[1] === '!') { // "a!=b"
      const u = eq[0].charCodeAt(0) - 97;
      const v = eq[3].charCodeAt(0) - 97;
      if (find(u) === find(v)) return false; // must be unequal but are in same group
    }
  }

  return true;
}
```

### Dry Run

```
equations = ["a==b","b!=c","b==c"]
Indices: a=0, b=1, c=2

parent=[0,1,2,...,25], size=[1,1,1,...,1]

Pass 1 (== equations):
  "a==b": union(0,1). size[0]>=size[1] → parent[1]=0, size[0]=2.
  "b==c": union(1,2).
    find(1): parent[1]=0, parent[0]=0 → root=0.
    find(2): root=2. Different → parent[2]=0, size[0]=3.
  parent: [0,0,0,3,4,...], size: [3,1,1,1,...]

Pass 2 (!= equations):
  "b!=c": find(1)=0, find(2)=0. SAME → return false ✓

Result: false (b==c and b!=c contradict) ✓
```

### Complexity
- Time: O(E × α(26)) = O(E) — at most 26 variables, so DSU operations are bounded by constant (α of any constant is ≤ 4). Effectively O(E).
- Space: O(26) = O(1) — fixed 26-element arrays for 26 possible variables.

### Edge Cases
- Self-equality `"a==a"`: union(a, a) — `find(a) === find(a)`, rootU === rootV, no-op. ✓
- Self-inequality `"a!=a"`: pass 1 skips it; pass 2 checks `find(a) === find(a)` → true → returns false immediately. A variable can't be unequal to itself. ✓
- Only `!=` equations (no `==`): pass 1 does nothing (all singletons); pass 2 checks each pair — since no unions happened, all pairs are in different components → returns true. ✓
- Transitive equality chain: `a==b, b==c, c==d, a!=d` — all four are in one component after pass 1; `a!=d` contradiction found in pass 2. ✓

### Follow-up Questions
- "Why must `==` equations be processed BEFORE `!=` equations?" → If you processed them interleaved, a `!=` check might pass before all `==` constraints have been applied, missing a transitivity-induced contradiction. By processing all `==` first, the equality components are fully built when `!=` checks run — no contradiction can be missed.
- "What if variables are arbitrary strings, not single letters?" → Replace the fixed 26-element array with the Map-based `UnionFindGeneric` from Q7. Same two-pass logic applies.

## Problem 5 — Largest Component After Connecting Points by Shared Factor

### Problem
Given an array `nums` of distinct integers, connect two numbers if they share a common factor greater than 1. Return the size of the largest connected component.

```
Input: nums = [4,6,15,35]
Output: 4
(4-6 share factor 2; 6-15 share factor 3; 15-35 share factor 5 → all connected)

Input: nums = [20,50,9,63]
Output: 2
```

### Pattern Recognition
Union-Find on prime factors — instead of connecting pairs of numbers directly (O(n²) pairs to check, each pair requiring GCD computation), union each number with each of its prime factors. Two numbers connected through a shared prime factor will end up in the same component.

### Key Insight
Two numbers share a common factor if and only if they share a common **prime** factor (since every composite factor is a product of primes). By treating prime factors as "connector" nodes — unioning each number with its prime factors — transitivity does the rest: if 6 and 15 both union with prime 3, they end up in the same component, implicitly connected.

### Approach
For each number, factorize it. Union the number with each of its prime factors. After all unions, find the maximum component size among the input numbers (ignore prime factor nodes — we care about the numbers only). The `getSize(x)` query gives the component size — but since prime factors and numbers share components, take the max size across the number nodes only.

### Solution

```js
function largestComponentSize(nums) {
  const maxVal = Math.max(...nums);
  // parent/size arrays sized to cover both number values AND prime factors
  const parent = Array.from({ length: maxVal + 1 }, (_, i) => i);
  const size   = new Array(maxVal + 1).fill(1);

  function find(x) {
    if (parent[x] !== x) parent[x] = find(parent[x]);
    return parent[x];
  }

  function union(u, v) {
    const rootU = find(u), rootV = find(v);
    if (rootU === rootV) return;
    if (size[rootU] >= size[rootV]) {
      parent[rootV] = rootU; size[rootU] += size[rootV];
    } else {
      parent[rootU] = rootV; size[rootV] += size[rootU];
    }
  }

  // For each number, union it with all its prime factors
  for (const num of nums) {
    let n = num;
    for (let p = 2; p * p <= n; p++) {
      if (n % p === 0) {
        union(num, p);         // num and prime p are in the same component
        while (n % p === 0) n = Math.floor(n / p); // remove all occurrences of p
      }
    }
    if (n > 1) union(num, n); // n is a prime factor greater than sqrt(original num)
  }

  // Find the maximum component size among the input numbers
  let maxSize = 0;
  for (const num of nums) {
    maxSize = Math.max(maxSize, size[find(num)]);
  }

  return maxSize;
}
```

```js
// Corrected final step: count input numbers per component
function largestComponentSize(nums) {
  const maxVal = Math.max(...nums);
  const parent = Array.from({ length: maxVal + 1 }, (_, i) => i);
  const rankArr = new Array(maxVal + 1).fill(0);

  function find(x) {
    if (parent[x] !== x) parent[x] = find(parent[x]);
    return parent[x];
  }

  function union(u, v) {
    const rootU = find(u), rootV = find(v);
    if (rootU === rootV) return;
    if (rankArr[rootU] >= rankArr[rootV]) {
      parent[rootV] = rootU;
      if (rankArr[rootU] === rankArr[rootV]) rankArr[rootU]++;
    } else {
      parent[rootU] = rootV;
    }
  }

  for (const num of nums) {
    let n = num;
    for (let p = 2; p * p <= n; p++) {
      if (n % p === 0) { union(num, p); while (n % p === 0) n = Math.floor(n / p); }
    }
    if (n > 1) union(num, n);
  }

  // Count input numbers per component root
  const count = new Map();
  for (const num of nums) {
    const root = find(num);
    count.set(root, (count.get(root) || 0) + 1);
  }

  return Math.max(...count.values());
}
```

### Complexity
- Time: O(N × √M × α(M)) where N = len(nums), M = max(nums). The factorization of each number takes O(√M); each union/find is O(α(M)).
- Space: O(M) — parent and rank arrays sized to maxVal.

### Edge Cases
- All numbers are prime: no two primes share a factor (assuming all distinct primes). Each number is in its own component. Returns 1. ✓
- nums = [1]: 1 has no prime factors; the inner loop doesn't execute; 1 is in its own component. Returns 1. ✓ (1 shares no factors > 1 with anything)
- Two numbers sharing multiple prime factors (e.g., 12 and 18 share both 2 and 3): multiple union calls, but the second union of already-connected nodes is a no-op. ✓

### Follow-up Questions
- "Why union numbers with their prime factors rather than directly with each other?" → Direct pairwise approach: O(n²) pairs, each requiring O(√M) GCD computation = O(n²√M). Prime factor approach: O(n√M) total factorizations + O(n log M) union operations = O(n√M). The key reduction: instead of comparing all pairs, we use prime factors as indirect connectors — the DSU handles transitivity automatically.

```
Union-Find problem — when and how to use DSU?
│
├── RECOGNITION SIGNALS (any of these → likely a DSU problem):
│   ├── "connected components" / "number of groups"
│   ├── "are X and Y in the same group?"
│   ├── "merge X and Y" / "connect X and Y"
│   ├── "cycle detection in undirected graph"
│   ├── "minimum spanning tree" (Kruskal's)
│   └── Edges added dynamically, queries after each addition
│
├── CORE IMPLEMENTATION (always use both optimizations):
│   ├── Path compression: parent[x] = find(parent[x]) in find()
│   ├── Union by SIZE (preferred): smaller.size merges under larger.size
│   │     → Also gives exact component sizes via size[find(x)]
│   └── Union by RANK (alternative): same O(α(n)) — use if size not needed
│
├── WHICH VARIANT?
│   ├── Integer nodes 0..n-1 → array-based DSU (fastest)
│   ├── String/object nodes → Map-based DSU (UnionFindGeneric)
│   ├── Need component sizes → union by SIZE + size[find(x)]
│   ├── Need component count → maintain components counter in union()
│   ├── Need to undo unions → DSU with rollback (rank, NO path compression)
│   └── Relative relationships (parity, ratio) → Weighted/Bipartite DSU
│
├── COMMON PATTERNS:
│   ├── Count components: init n components, union edges, return components
│   ├── Cycle detection: union edges; if union returns false → cycle exists
│   ├── Redundant edge: first edge where union returns false
│   ├── Dynamic connectivity: union each new edge; query after each addition
│   ├── Kruskal's MST: sort edges by weight; union if different components
│   ├── Two-pass (equality/inequality): union == first, check != second
│   └── Indirect connection (shared factor): union nodes with their "keys"
│         (prime factors, common attributes) as intermediate nodes
│
├── COMPLEXITY:
│   ├── O(α(n)) ≈ O(1) amortized per operation with both optimizations
│   ├── O(n) initialization (unavoidable)
│   └── Total for n nodes, E operations: O(n + E × α(n)) ≈ O(n + E)
│
└── DSU vs. BFS/DFS:
      Use DSU when:  edges added dynamically; only connectivity queries needed;
```

## Common Bugs Checklist

Before submitting any Union-Find solution, verify:

1. **`parent` array initialized with `parent[i] = i` for all i (each node is its own root)?** — Any uninitialized entry causes `find` to follow a garbage parent pointer, reading random array values and potentially looping infinitely or returning incorrect roots. The initialization `Array.from({ length: n }, (_, i) => i)` is the only correct form — never use `new Array(n).fill(0)` which sets every parent to 0 (node 0 becomes the false root of everything).

2. **`find` with path compression calls `find(parent[x])` recursively, NOT `find(x)` again?** — `this.parent[x] = this.find(this.parent[x])` is correct. `this.parent[x] = this.find(x)` is an infinite loop — x's parent is set to x's root, which `find(x)` then re-evaluates, looping forever. Verify the argument to the recursive call is `parent[x]`, not `x`.

3. **`union` checks for `rootU === rootV` BEFORE modifying the parent/size/rank?** — Without this guard, unioning a node with itself (or two already-connected nodes) decrements the component count incorrectly and corrupts the size array. The guard `if (rootU === rootV) return false` must be the first thing after the two `find` calls.

4. **`union` returns a boolean indicating whether a merge actually happened?** — Many DSU applications (Kruskal's, redundant connection, cycle detection, network connectivity) depend on knowing whether the union was a no-op. Returning `void` forces callers to compare find results themselves, which is error-prone. Always return `true` for a successful union (different components merged) and `false` for a no-op (same component).

5. **`size` updated on the NEW root only, not both nodes?** — After `parent[rootV] = rootU`, only `size[rootU] += size[rootV]` is correct. Updating `size[rootV]` as well creates double-counted sizes. `size[rootV]` becomes stale (it's no longer a root) and should never be read again via `getSize` — `getSize` always calls `find` first to get the current root.

6. **Two-pass problems process ALL `==` (union) equations before ANY `!=` (check) equations?** — Interleaved processing misses transitive equalities: if a==b and b==c have been declared but b==c was processed after a!=c was already checked, the contradiction is missed. Always complete pass 1 (all unions) before pass 2 (all inequality checks).

7. **Rollback DSU (DSU with rollback) omits path compression?** — Path compression irreversibly modifies the parent array in ways that the history stack can't undo. Without path compression, `find` is O(log n) per call (union by rank guarantees O(log n) height) — this is the accepted trade-off for rollback support. Any attempt to add path compression to a rollback DSU silently breaks rollback correctness.

8. **Weighted/bipartite DSU updates parity during path compression in `find`, not just at union time?** — In the bipartite DSU, each node's `parity` is relative to its **current** parent, which changes during path compression. When `parent[x]` is set to the root, `parity[x]` must be updated to be relative to the root (by XOR-accumulating parities along the compressed path). Forgetting to update parities during compression causes incorrect parity lookups on subsequently compressed nodes.

9. **Indirect-connection problems (prime factor approach): counting nodes per component using a frequency map over INPUT NODES only, not all DSU nodes?** — The DSU's internal `size` array counts all nodes in the component, including intermediate "connector" nodes (prime factors, shared attributes) that are not input elements. For "largest group of input elements," always re-count by iterating only over the input elements and grouping by `find(x)`, not by reading `size[find(x)]` directly.

10. **Large value ranges allocate arrays of the correct size?** — If node values go up to `maxVal`, the parent/size arrays must have length `maxVal + 1` (to accommodate index `maxVal`). Off-by-one: `new Array(maxVal)` is length `maxVal` with max valid index `maxVal - 1` — accessing index `maxVal` returns `undefined`, and `find(maxVal)` reads `undefined` as a parent, immediately diverging from correct behavior. Always use `maxVal + 1`.

The clearest articulation: "BFS/DFS answers connectivity in O(V + E) but must restart after each structural change; Union-Find amortizes this to O(α(n)) per operation by maintaining a precomputed summary of connectivity — at the cost of not knowing actual paths." Explicitly naming both optimizations (path compression and union by size/rank), explaining what each prevents (deep chains), and stating the resulting O(α(n)) amortized complexity with the "α(10^80) ≤ 4" observation demonstrates the depth of understanding expected at senior level.
