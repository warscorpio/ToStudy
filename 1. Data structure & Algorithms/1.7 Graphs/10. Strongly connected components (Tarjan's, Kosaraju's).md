## Topic A: SCC Foundations

### Section A1: Fundamentals

**Q1. What is a strongly connected component, and what makes it "maximal"?**

A: A strongly connected component (SCC) is a maximal subset S of vertices in a directed graph such that for every ordered pair (u, v) in S × S, there is a directed path from u to v AND a directed path from v to u — the two vertices can "reach each other." Every single vertex is trivially its own SCC (a path of length 0 exists from any vertex to itself). "Maximal" means you cannot add any additional vertex to S while preserving strong connectivity — if you add any vertex outside S, the reachability property breaks for at least one pair. Every vertex belongs to exactly one SCC, making SCCs a partition of the vertex set.

```
Directed graph:
  0 → 1 → 2 → 0   (0,1,2 form a cycle → SCC {0,1,2})
  1 → 3 → 4 → 3   (3 and 4 can reach each other → SCC {3,4})
  5              (no edges → SCC {5})

SCC partition: {0,1,2}, {3,4}, {5}

Check maximality of {0,1,2}:
  Can we add 3? 3 can't reach 0,1,2 → {0,1,2,3} is NOT strongly connected. ✓
  Can we add 5? 5 can reach nothing → {0,1,2,5} is NOT strongly connected. ✓
```

**Q2. What is the condensation graph, and what structural property does it always have?**

A: The condensation (or condensation DAG) is constructed by collapsing each SCC to a single super-node, then adding an edge between super-nodes whenever any edge crossed between the corresponding SCCs in the original graph. The condensation is **always a DAG** (directed acyclic graph) — it contains no cycles. Proof by contradiction: if the condensation had a cycle between super-nodes C₁ → C₂ → ... → Cₖ → C₁, then every vertex in C₁ could reach every vertex in Cₖ and vice versa, meaning C₁ through Cₖ are all strongly connected — they would all be part of the same SCC, contradicting the assumption that they are distinct SCCs. This DAG structure is what makes SCC decomposition powerful: it transforms an arbitrary directed graph into a DAG that admits topological processing.

```
Original:          Condensation DAG:
0 → 1 → 2 → 0
1 → 3             {0,1,2} → {3,4}
3 → 4 → 3                ↗
0 → 5             {0,1,2} → {5}

Any problem solvable on DAGs (reachability, longest path, coverage)
can be solved on SCCs via the condensation.
```

**Q3. What is the key structural observation — about DFS finish times — that both Tarjan's and Kosaraju's exploit?**

A: In a DFS on graph G, define the finish time of a vertex as the DFS timestamp when it is fully explored (all reachable descendants visited). The key observation: **in the condensation DAG, if SCC C has an edge to SCC C', then the vertex in C with the latest finish time finishes after all vertices in C'.** Why: since C can reach C' but C' cannot reach C (they are separate SCCs), the DFS entering C will eventually explore all of C' as part of C's subtree or from a prior DFS call. Either way, C' finishes before C. Kosaraju's exploits this directly — the latest-finishing vertex is processed first on the reversed graph. Tarjan's exploits a local per-vertex version of the same insight through the low-link value, which tracks how "early" in the DFS each vertex's component can reach back.

**Q4. What is the discovery time and low-link value in Tarjan's algorithm, and what does each represent?**

A: **Discovery time `disc[v]`**: the DFS timestamp when vertex v is first visited. Incremented globally with each new visit. Represents how early in the DFS v was encountered — a lower `disc` value means v is an "older" ancestor in the DFS tree.

**Low-link value `low[v]`**: the minimum discovery time reachable from v's DFS subtree using tree edges plus *at most one* back edge to a vertex currently on the DFS stack. More precisely: `low[v] = min(disc[v], min(disc[w])` for all w reachable from v's subtree via one non-tree edge where w is on the Tarjan stack). The "on-stack" restriction is critical: cross edges to already-completed SCCs are excluded.

```
DFS on: 0→2, 2→1, 1→0, 1→3, 3→4, 4→5, 5→3

       disc  low
  0:    0     0    ← low=0: can reach itself (the root)
  2:    1     0    ← can reach 0 via 1's back edge 1→0
  1:    2     0    ← back edge 1→0 → low=disc[0]=0
  3:    3     3    ← SCC root: can't escape past disc=3
  4:    4     3    ← via 5's back edge 5→3: low=disc[3]=3
  5:    5     3    ← back edge 5→3: low=disc[3]=3

SCC roots: vertices where disc[v] == low[v].
  disc[3]==low[3]==3 → SCC root. Pop {5,4,3} as an SCC.
  disc[0]==low[0]==0 → SCC root. Pop {1,2,0} as an SCC.
```

**Q5. How does Tarjan's algorithm detect SCC roots, and why must the `onStack` flag be used for updating low-link values?**

A: A vertex v is an **SCC root** iff `disc[v] == low[v]` after its DFS subtree is fully explored. This means no vertex in v's subtree can reach any ancestor of v via a back edge — v is the "highest reachable point" from its own subtree. When this condition holds, v and all vertices currently above it on the Tarjan stack (placed there since v was first visited) form exactly one SCC.

The `onStack` flag is critical for the low-link update rule: when processing edge (u, v), the update `low[u] = min(low[u], disc[v])` is performed **only if v is currently on the stack** — not merely visited. If v has already been popped (its SCC is complete), it belongs to a different SCC, and using its disc time would incorrectly "pull" u's low-link backward into a completed SCC, merging u with a finished component.

```
WRONG (update for any visited v):
  low[u] = min(low[u], disc[v])  ← even if v's SCC is complete

  Counter-example:
    Graph: 0→1→2→1, 0→2.
    After {1,2} is found as an SCC:
    Processing 0→2: v=2 is visited. low[0] = min(0, disc[2]) incorrectly.
    disc[0]=0=low[0] still, but the update is semantically wrong.

CORRECT (update only if v is on-stack):
  if (onStack[v]): low[u] = min(low[u], disc[v])
  else: skip (v is in a completed, separate SCC)
```

## Topic B: Tarjan's Algorithm Deep Dive

### Section B1: The Algorithm

**Q6. Walk through the complete Tarjan's algorithm — pseudocode, invariants, and the SCC-extraction step.**

A: Tarjan's runs a single DFS, maintaining: `disc[v]` (discovery time), `low[v]` (low-link), `onStack[v]` (in current DFS path), and a global stack. After fully exploring vertex v's subtree, check `disc[v] == low[v]` — if true, v is an SCC root: pop the stack until v is reached, and all popped vertices form one SCC.

```
Global: timer = 0, stack = [], onStack = false[], disc = -1[], low = 0[]

DFS(u):
  disc[u] = low[u] = timer++
  stack.push(u); onStack[u] = true

  for each neighbor v of u:
    if disc[v] == -1:                    // unvisited: tree edge
      DFS(v)
      low[u] = min(low[u], low[v])       // propagate low-link upward
    else if onStack[v]:                  // visited AND on stack: back edge
      low[u] = min(low[u], disc[v])      // use disc[v], NOT low[v]

  if disc[u] == low[u]:                  // u is SCC root
    scc = []
    loop:
      w = stack.pop(); onStack[w] = false
      scc.push(w)
      break if w == u
    record scc

for each unvisited vertex u: DFS(u)

Key invariants:
  (1) stack contains vertices whose SCC has not yet been fully identified
  (2) low[v] ≤ disc[v] always
  (3) disc[v] == low[v] iff v is the first-visited vertex in its SCC
  (4) When an SCC is found, its vertices are contiguous at the top of the stack
```

**Q7. Why does the low-link update use `disc[v]` (not `low[v]`) for back edges, and when does this distinction matter?**

A: For an on-stack neighbor v (a back edge in the DFS), the update is `low[u] = min(low[u], disc[v])`. Using `disc[v]` anchors the low-link to the *specific* ancestor v represents — the discovery time of the oldest vertex directly reachable via this one back edge. Using `low[v]` instead would say "u can reach wherever v's entire subtree can reach," which would transitively include even further ancestors — potentially pulling u's low-link all the way back to the root, collapsing unrelated SCCs. The distinction becomes critical in bridge and articulation point detection (Topic D), where `low[v] > disc[u]` (strictly greater than) determines whether an edge is a bridge. If `low[v]` were used for back edges, the low-link values would be incorrectly lowered for back-edge targets, causing bridges to be missed.

```
Graph: 0→1, 1→2, 2→0 (SCC), 1→3.
  disc=[0,1,2,3], low should be:
  low[2]=disc[0]=0 (back edge 2→0), low[1]=0, low[0]=0 → SCC root at 0.

Using low[v] for 2→0 back edge: low[2]=min(2,low[0])=min(2,0)=0. Same result here.

Difference matters for:
  Graph: 0→1, 1→2, 2→1, 1→3.
  DFS: visit 0, visit 1, visit 2. Back edge 2→1: using disc[1]=1 → low[2]=1.
  If we also had 3→0 back edge: using disc[0]=0 → low[3]=0.
  low[1] = min(low[2], low[3]) = min(1, 0) = 0.
  disc[1]=1 ≠ low[1]=0 → 1 is NOT an SCC root → correct (0→1→2→1 is wrong SCC).
  But if we naively used low[v] for back edges everywhere, we'd need to verify
  on-stack flags independently — the two update rules are not interchangeable.
```

**Q8. What is the difference between a back edge and a cross edge in Tarjan's, and how are they handled?**

A: In a DFS on a directed graph, edges fall into four categories: tree edges (to unvisited vertices), back edges (to proper ancestors on the current DFS stack), forward edges (to already-finished descendants), and cross edges (to vertices in different DFS subtrees). In Tarjan's algorithm, only back edges meaningfully affect low-link values — they indicate that part of the current SCC can "escape" to an ancestor. Cross edges (to an already-fully-explored vertex, i.e., `onStack[v] == false && disc[v] != -1`) are ignored for low-link updates: the target belongs to an already-identified SCC, and the current vertex's SCC is distinct. Forward edges to already-visited descendants in the same DFS tree branch also don't need special handling — the descendant's low-link is already captured via the tree-edge path.

### Section B2: Kosaraju's & Comparison

**Q9. Walk through Kosaraju's two-pass algorithm and explain why running DFS on the reversed graph in reverse-finish order finds SCCs.**

A: Kosaraju's uses two full DFS passes:

**Pass 1** — DFS on G, collect vertices in finish order (push to a stack after all descendants are explored). The last vertex pushed has the latest finish time.

**Pass 2** — DFS on the reversed graph G^R, processing vertices in reverse finish order (latest finisher first). Each DFS call in Pass 2 explores exactly one SCC.

**Why it works**: In the condensation of G, if SCC C has an edge to SCC C', then C finishes after C' in Pass 1 (C can reach C', so C fully explores C' before finishing). In G^R, the edge direction reverses: C' can reach C, but C cannot reach C'. Processing in reverse finish order means we process C before C'. When we DFS from C's root in G^R, we can only reach C (since C's edges in G^R go back to sources, not forward) — C' cannot be reached from C in G^R. So each Pass 2 DFS precisely explores one SCC.

```
Kosaraju's pseudocode:
  Pass 1:
    visited = [], order = []
    for each unvisited u: dfs1(u)   // marks visited, appends u to order at finish

  dfs1(u):
    visited[u] = true
    for v in adj[u]: if !visited[v]: dfs1(v)
    order.push(u)                  // push AFTER all descendants — critical

  Build G^R: for each edge (u→v) in G, add (v→u) to reverse adj.

  Pass 2:
    comp = new Array(n).fill(-1)
    sccId = 0
    for i from order.length-1 to 0:  // reverse finish order
      if comp[order[i]] == -1:
        dfs2(order[i], sccId++)

  dfs2(u, id):
    comp[u] = id
    for v in radj[u]: if comp[v] == -1: dfs2(v, id)
```

**Q10. What are the practical trade-offs between Tarjan's and Kosaraju's?**

A: Both algorithms are O(V + E) time and O(V) space. The differences are:

| Property | Tarjan's | Kosaraju's |
|---|---|---|
| DFS passes | 1 | 2 |
| Reversed graph | Not needed | Required |
| State per vertex | disc, low, onStack (3 values) | visited (pass 1), comp (pass 2) |
| Implementation complexity | Higher (low-link update rules) | Lower (two standard DFS) |
| Memory | O(V) stack + O(V) arrays | O(V) + O(V + E) for G^R |
| Interview preference | More impressive | Easier to verify |

For interviews: Tarjan's demonstrates deeper algorithmic knowledge; Kosaraju's is safer to implement bug-free under time pressure. Both are acceptable. Tarjan's is preferred for bridge/articulation-point variants (same algorithm, minor modification).

## Topic C: Low-Link Applications

### Section C1: Bridges and Articulation Points

**Q11. How does Tarjan's low-link value extend to finding bridges (critical edges) in undirected graphs?**

A: In an undirected graph, an edge (u, v) is a **bridge** if removing it disconnects the graph. Tarjan's DFS computes `disc` and `low` as before, but on an undirected graph. After DFS from u into v (tree edge), check: **if `low[v] > disc[u]`, then (u, v) is a bridge**. The intuition: `low[v]` is the earliest disc time reachable from v's subtree via back edges. If `low[v] > disc[u]`, v's entire subtree cannot "escape" past u through any back edge — the only way to reach u from v's subtree is through the single tree edge (u, v). Removing it disconnects v's subtree.

Critical implementation detail: in undirected graphs, each edge (u, v) appears in both adj[u] and adj[v]. When at vertex v (reached from u), the edge back to u must not be treated as a back edge — it's the same tree edge, not a cycle. Pass the parent into the recursion and skip the parent edge: `if v == parent: continue`.

```
Bridge condition: low[v] > disc[u]  (strictly greater — if equal, u is the lowest ancestor v can reach)
Articulation condition: low[v] >= disc[u]  (greater or equal — if equal, u is the lowest but still required)
                        OR: u is DFS root with ≥ 2 tree-edge children

Note: bridge uses > but articulation uses >= for non-root vertices.
```

**Q12. What is an articulation point, and how does its detection condition differ from bridge detection?**

A: An **articulation point** (cut vertex) is a vertex whose removal increases the number of connected components. In Tarjan's DFS, vertex u is an articulation point in two cases:

**Case 1 — u is the DFS root**: u is an articulation point iff it has ≥ 2 children in the DFS tree. Removing the root disconnects the DFS tree into separate subtrees.

**Case 2 — u is NOT the DFS root**: u is an articulation point iff it has at least one child v with `low[v] >= disc[u]`. If `low[v] >= disc[u]`, v's subtree cannot reach any ancestor of u via back edges — removing u disconnects v's subtree. The `>=` (vs `>` for bridges) accounts for the vertex itself: even if v can reach u (via a back edge to u, meaning `low[v] = disc[u]`), removing u still disconnects v's subtree from u's ancestors.

```
Bridge (edge removal): low[v] > disc[u]
  v's subtree cannot even reach u. Removing edge (u,v) disconnects.

Articulation point (vertex removal): low[v] >= disc[u]
  v's subtree can reach at most u (low[v] = disc[u] means a back edge to u).
  But if u is removed, v can no longer reach u's ancestors. Disconnected.

Root special case: DFS root is AP iff it has ≥ 2 DFS tree children.
  (low[child] is always ≤ disc[root] for children, so the standard check is vacuous at root)
```

## Topic D: SCC Applications & Interview-Style Questions

**Q13. What is the condensation DAG property, and how does it directly answer certain graph problems?**

A: After finding all SCCs and building the condensation DAG, several graph properties become immediately computable:

- **Number of source SCCs** (in-degree 0 in condensation): the minimum number of starting vertices needed to reach all vertices in the graph. If there is exactly one source SCC, the graph has a Hamiltonian-like reachability structure.
- **Number of sink SCCs** (out-degree 0 in condensation): the set of SCCs that, once entered, cannot be escaped. These are the "strongly connected components that are eventual states."
- **Reachability between SCCs**: use topological sort on the condensation + DP. O(V + E) after condensation.
- **2-SAT**: solvability is determined by SCC membership of variable literals; assignments are determined by topological order.

**Q14. What is the relationship between SCCs and 2-SAT, and how do you read the satisfying assignment from the condensation?**

A: 2-SAT (boolean satisfiability with 2 literals per clause) maps to an SCC problem. For each clause `(a OR b)`, add implications `NOT a → b` and `NOT b → a` as directed edges. The formula is **unsatisfiable iff any variable x and its negation NOT x appear in the same SCC**. For a satisfying assignment (when formula is satisfiable): in the condensation DAG, if SCC(x) comes topologically AFTER SCC(NOT x), set x = TRUE. If SCC(NOT x) comes after SCC(x), set x = FALSE. The topological order of SCCs guarantees consistency: if we set x = true (SCC(x) comes later), and x implies y via an edge, then SCC(y) is reachable from SCC(x) in the condensation, so SCC(y) comes even later — y is also set consistently.

**Q15. "Walk through your thought process when you see a directed graph problem involving cycles or reachability."**

A: Four diagnostic questions:

1. **Is the problem about reachability within cycles?** — "can u reach v through possibly cyclic paths?" → SCC decomposition + condensation. The condensation makes reachability tractable.

2. **Is the problem about critical structural elements?** — "which edges or vertices, if removed, disconnect the graph?" → Tarjan's low-link for bridges (edges) or articulation points (vertices).

3. **Is the problem about which vertices are "safe" (not on any cycle)?** — "which vertices are not part of any cycle?" → SCC decomposition: vertices in SCCs of size 1 with no self-loops are safe. Or reverse-graph DFS from sink nodes.

4. **Is the problem about minimum coverage or path lengths on a directed graph?** — Condense SCCs → work on the resulting DAG → topological sort + DP.

**Q16. "What goes wrong in Tarjan's if you update `low[u]` with `low[v]` instead of `disc[v]` for back-edge (on-stack) neighbors?"**

A: Using `low[v]` instead of `disc[v]` for on-stack neighbors gives a lower (more aggressive) bound on how far back the current SCC can "reach." This makes more vertices appear to reach further back in the DFS, causing their `low` values to be smaller than they should be. The consequence: fewer vertices satisfy `disc[v] == low[v]`, so SCC root detection is delayed or wrong — vertices that should be identified as SCC roots are not, causing multiple SCCs to be merged into one. The resulting SCCs would be larger than correct (over-merging). In bridge detection specifically, this causes bridges to be missed: `low[v] > disc[u]` is less likely to be true if `low[v]` was over-reduced.

**Q17. "What is the space complexity of Tarjan's, and can the DFS stack cause a stack overflow?"**

A: Tarjan's uses O(V) space for the disc, low, onStack arrays, O(V) for the Tarjan stack (at most V vertices on it simultaneously), and O(V) for the recursive call stack (DFS depth at most V for a path graph). Total: O(V). For graphs with V = 100,000+ vertices in a linear chain (worst case), the recursive DFS stack depth can cause a stack overflow in languages with limited call stacks (JavaScript default ~10,000–15,000 frames). Fix: convert the recursion to iterative DFS using an explicit stack that simulates the call stack. This is non-trivial for Tarjan's because the low-link propagation (`low[u] = min(low[u], low[v])` after dfs(v) returns) requires post-processing upon "return" from each simulated recursive call.

**Q18. In one sentence each, state the key invariant or contract for each algorithm/problem in this document.**

A:
- **Tarjan's SCC**: at all times, the Tarjan stack contains exactly the vertices whose SCC has not yet been fully identified; `disc[v] == low[v]` after full exploration identifies v as the oldest vertex in its SCC (the SCC root).
- **Kosaraju's SCC**: Pass 1 orders vertices so that SCC sources finish last; Pass 2's DFS on G^R from each unvisited vertex explores exactly one SCC, since G^R reverses the inter-SCC reachability direction.
- **Bridges (Critical Connections)**: edge (u,v) is a bridge iff `low[v] > disc[u]` — v's subtree has no back edge that bypasses u, making the single tree edge (u,v) the only connection.
- **Articulation Points**: vertex u is a cut vertex iff it is the DFS root with ≥ 2 tree children, or it is a non-root with a child v satisfying `low[v] >= disc[u]` — v's subtree cannot escape past u.
- **Find Eventual Safe States**: a node is safe iff it is not on any directed cycle — equivalently, it is not part of any SCC of size ≥ 2 and has no self-loop; reachable from terminal nodes via reverse-graph traversal.
- **Minimum Vertices to Reach All Nodes**: in the condensation DAG of a directed graph, the answer is the number of source SCCs (SCCs with in-degree 0) — every other SCC is reachable from some source.

## Problem 1 — Strongly Connected Components (Tarjan's Algorithm)

### Problem
Given a directed graph with `n` vertices and a list of directed edges, find all strongly connected components and return them as a list of groups.

```
Input:  n=6, edges=[[0,2],[2,1],[1,0],[1,3],[3,4],[4,5],[5,3]]
Output: [[3,4,5], [0,1,2]]   (order may vary)

Input:  n=3, edges=[[0,1],[1,2]]
Output: [[2],[1],[0]]   (each vertex is its own SCC — no cycles)
```

### Pattern Recognition
Tarjan's single-pass DFS — assign `disc` and `low` to each vertex; maintain an explicit stack with `onStack` flags; extract SCCs whenever `disc[v] == low[v]` at a vertex after full exploration.

### Key Insight
The Tarjan stack captures "pending SCC members" — vertices visited but not yet assigned to a complete SCC. When a vertex v satisfies `disc[v] == low[v]`, it is the oldest vertex in its SCC (the root, visited first). Every vertex pushed onto the stack after v (and still on the stack) must be in the same SCC — pop them all.

### Approach
For each unvisited vertex, run DFS: assign `disc[u] = low[u] = timer++`, push to stack, mark `onStack[u] = true`. For each neighbor v: if unvisited, recurse then `low[u] = min(low[u], low[v])`; if on-stack, `low[u] = min(low[u], disc[v])`. After neighbors: if `disc[u] == low[u]`, pop stack until u (inclusive) as one SCC.

### Solution

```js
function findSCCs(n, edges) {
  const adj = Array.from({ length: n }, () => []);
  for (const [u, v] of edges) adj[u].push(v);

  const disc    = new Array(n).fill(-1);   // -1 = unvisited
  const low     = new Array(n).fill(0);    // low-link values
  const onStack = new Array(n).fill(false);
  const stack   = [];
  const sccs    = [];
  let timer = 0;

  function dfs(u) {
    disc[u] = low[u] = timer++; // discovery time and initial low-link
    stack.push(u);
    onStack[u] = true;

    for (const v of adj[u]) {
      if (disc[v] === -1) {
        // Tree edge: recurse, then propagate low-link upward
        dfs(v);
        low[u] = Math.min(low[u], low[v]);
      } else if (onStack[v]) {
        // Back edge to an ancestor on the stack: update with disc (NOT low!)
        low[u] = Math.min(low[u], disc[v]);
      }
      // If disc[v] != -1 && !onStack[v]: cross edge to completed SCC — ignore
    }

    // Check if u is the root of an SCC
    if (disc[u] === low[u]) {
      const scc = [];
      while (true) {
        const w = stack.pop();
        onStack[w] = false;
        scc.push(w);
        if (w === u) break; // u is the last popped (oldest vertex in this SCC)
      }
      sccs.push(scc);
    }
  }

  for (let i = 0; i < n; i++) {
    if (disc[i] === -1) dfs(i); // handles disconnected graphs
  }

  return sccs;
}
```

### Dry Run

```
adj: 0:[2], 1:[0,3], 2:[1], 3:[4], 4:[5], 5:[3]

Start dfs(0): disc[0]=low[0]=0, stack=[0], onStack[0]=T.

  dfs(2) [0→2 tree edge]: disc[2]=low[2]=1, stack=[0,2], onStack[2]=T.

    dfs(1) [2→1 tree edge]: disc[1]=low[1]=2, stack=[0,2,1], onStack[1]=T.

      dfs(3) [1→3 tree edge]: disc[3]=low[3]=3, stack=[0,2,1,3], onStack[3]=T.

        dfs(4) [3→4 tree edge]: disc[4]=low[4]=4, stack=[0,2,1,3,4], onStack[4]=T.

          dfs(5) [4→5 tree edge]: disc[5]=low[5]=5, stack=[0,2,1,3,4,5], onStack[5]=T.
            Edge 5→3: onStack[3]=T → low[5]=min(5,disc[3])=min(5,3)=3.
            disc[5]=5 ≠ low[5]=3 → NOT SCC root.

      disc[1]=2 ≠ low[1]=0 → NOT SCC root.
    ← return dfs(1)

    Back at 2: low[2]=min(1,low[1])=min(1,0)=0.
    disc[2]=1 ≠ low[2]=0 → NOT SCC root.
  ← return dfs(2)

  Back at 0: low[0]=min(0,low[2])=min(0,0)=0.
  disc[0]=0 = low[0]=0 → SCC ROOT!
    Pop until 0: pop 1 (onStack[1]=F), pop 2 (onStack[2]=F), pop 0 (onStack[0]=F).
    SCC #2: [1,2,0]. stack=[].

Result: [[5,4,3], [1,2,0]] ✓
Verify: {3,4,5} is a cycle (3→4→5→3). {0,1,2} is a cycle (0→2→1→0). ✓
```

### Complexity
- Time: O(V + E) — each vertex is visited once (DFS), each edge traversed once.
- Space: O(V) — disc, low, onStack arrays + Tarjan stack (at most V vertices) + call stack (depth ≤ V).

### Edge Cases
- **Disconnected graph**: the outer `for` loop over all vertices handles disconnected components by starting new DFS trees.
- **Self-loops** `u → u`: `disc[u] != -1 && onStack[u]` → `low[u] = min(low[u], disc[u])`. No change (low[u] is already disc[u] initially). The self-loop creates a trivial cycle — u's SCC is {u} if no other cycle involves it.
- **Single vertex, no edges**: immediately after `dfs(u)`: `disc[u] == low[u]` → SCC = {u}. Correct.
- **All vertices in one SCC** (complete directed graph): the entire vertex set is popped when the DFS root satisfies `disc == low`.

### Follow-up Questions
- "Return the condensation DAG?" — Assign each SCC an ID (as returned). For each original edge (u,v) where sccId[u] != sccId[v], add an edge between those SCC IDs in the condensation. Deduplicate edges. O(V + E).
- "Iterative Tarjan's to avoid stack overflow?" — Simulate the call stack with an explicit stack of `(vertex, iterator_over_neighbors)` tuples. Post-processing steps (low-link propagation and SCC-root check) execute when a vertex's iterator is exhausted.

## Problem 2 — Strongly Connected Components (Kosaraju's Algorithm)

### Problem
Same problem as Problem 1 — find all SCCs — implemented with Kosaraju's two-pass DFS.

```
Input:  n=6, edges=[[0,2],[2,1],[1,0],[1,3],[3,4],[4,5],[5,3]]
Output: comp = [0,0,0,1,1,1]   (vertices 0,1,2 share comp=0; vertices 3,4,5 share comp=1)
```

### Pattern Recognition
Two-pass DFS on original graph + reversed graph — Pass 1 records finish order; Pass 2 assigns SCC IDs on G^R in reverse finish order. The finish-order/reversed-graph combination guarantees each Pass-2 DFS explores exactly one SCC.

### Key Insight
The latest-finishing vertex in Pass 1 belongs to a source SCC in the condensation (a component with no incoming edges from other SCCs). Running DFS from it on G^R explores only its SCC (G^R has no path from this SCC to any other source). Repeating for the next unvisited latest-finisher finds the next SCC, and so on.

### Approach
Pass 1: DFS on G; push each vertex to `order` *after* all its neighbors are processed (post-order). Pass 2: build G^R; iterate `order` in reverse; for each unvisited vertex, DFS on G^R assigning the same `sccId` to all reachable vertices.

### Solution

```js
function kosarajuSCC(n, edges) {
  const adj  = Array.from({ length: n }, () => []);
  const radj = Array.from({ length: n }, () => []); // reversed graph G^R

  for (const [u, v] of edges) {
    adj[u].push(v);
    radj[v].push(u); // reverse every edge
  }

  // Pass 1: DFS on G, collect vertices in finish (post-order) sequence
  const visited = new Array(n).fill(false);
  const order   = []; // order[0] = first to finish, order[n-1] = last to finish

  function dfs1(u) {
    visited[u] = true;
    for (const v of adj[u]) {
      if (!visited[v]) dfs1(v);
    }
    order.push(u); // push AFTER all descendants — post-order is essential
  }

  for (let i = 0; i < n; i++) {
    if (!visited[i]) dfs1(i);
  }

  // Pass 2: DFS on G^R in reverse finish order (latest finisher first)
  const comp = new Array(n).fill(-1); // comp[v] = SCC id of vertex v
  let sccId = 0;

  function dfs2(u, id) {
    comp[u] = id;
    for (const v of radj[u]) {
      if (comp[v] === -1) dfs2(v, id); // explore all of this SCC in G^R
    }
  }

  // Process in REVERSE finish order: last element of order first
  for (let i = order.length - 1; i >= 0; i--) {
    const u = order[i];
    if (comp[u] === -1) {
      dfs2(u, sccId++); // each call covers exactly one SCC
    }
  }

  return comp; // comp[v] = SCC id; group by id for the SCC lists
}
```

Later SCC IDs correspond to SCCs downstream in the condensation. This is reverse topological order.
- "Can you detect if the original graph is already a DAG using Kosaraju's?" — Yes: if every SCC has size 1 (and no self-loops), the graph is a DAG. A DAG has no cycles, so no SCC contains more than one vertex.

## Problem 3 — Critical Connections in a Network

### Problem
There are `n` servers numbered `0` to `n-1` connected by undirected server-to-server connections. A critical connection (bridge) is an edge that, if removed, will make some servers unable to reach some other server. Return all such connections in any order.

```
Input:  n=4, connections=[[0,1],[1,2],[2,0],[1,3]]
Output: [[1,3]]   (removing [1,3] disconnects server 3 from the rest)

Input:  n=2, connections=[[0,1]]
Output: [[0,1]]   (the only edge; removing it disconnects the graph)
```

### Pattern Recognition
Tarjan's low-link bridge detection on an undirected graph — compute `disc` and `low` via DFS; after exploring child v from parent u, check `low[v] > disc[u]`. If true, edge (u,v) is a bridge. Track parent to avoid re-traversing the tree edge.

### Key Insight
`low[v]` is the earliest disc time reachable from v's DFS subtree via back edges. If `low[v] > disc[u]`, v's entire subtree is "trapped" — the only connection to u's ancestors is the single tree edge (u,v). Cutting this edge disconnects v's subtree. The bridge condition is strict inequality: if `low[v] == disc[u]`, v's subtree can reach u itself via a back edge, so cutting (u,v) leaves v's subtree still connected to u through that back edge.

### Approach
Build adjacency list. DFS from an arbitrary vertex (connected graph assumed). At each vertex u, for each neighbor v: if v is the parent, skip. If unvisited, recurse, propagate `low[u] = min(low[u], low[v])`, then check `low[v] > disc[u]`. If already visited (back edge), update `low[u] = min(low[u], disc[v])`.

### Solution

```js
function criticalConnections(n, connections) {
  const adj = Array.from({ length: n }, () => []);
  for (const [u, v] of connections) {
    adj[u].push(v);
    adj[v].push(u); // undirected: add both directions
  }

  const disc    = new Array(n).fill(-1);
  const low     = new Array(n).fill(0);
  const bridges = [];
  let timer = 0;

  function dfs(u, parent) {
    disc[u] = low[u] = timer++;

    for (const v of adj[u]) {
      if (v === parent) continue; // skip the edge we came from (not a back edge)

      if (disc[v] === -1) {
        // Tree edge: recurse into v
        dfs(v, u);
        low[u] = Math.min(low[u], low[v]); // v's subtree may reach ancestors of u

        // Bridge check: if v's subtree cannot reach above u, (u,v) is critical
        if (low[v] > disc[u]) {
          bridges.push([u, v]);
        }
      } else {
        // Back edge: v is already visited — update low directly with disc[v]
        low[u] = Math.min(low[u], disc[v]);
      }
    }
  }

  dfs(0, -1); // start DFS from vertex 0, no parent
  return bridges;
}
```

### Edge Cases
- **Graph with a cycle only**: no bridges (every edge is part of the cycle — `low[v] <= disc[u]` for all tree edges). Returns `[]`.
- **Tree graph** (no cycles): every edge is a bridge — `low[v] = disc[v]` for every leaf v, and `low[v] > disc[u]` for every parent u. Returns all n-1 edges.
- **Parallel edges** (multiple edges between same pair): a "bridge" in a multigraph is an edge whose removal disconnects. - "Handle parallel edges without edge-index tracking?" — Pass a "parent edge count" rather than the parent vertex. Decrement the count when skipping back to the parent. More robust for multigraphs.

## Problem 4 — Articulation Points

### Problem
Given an undirected connected graph with `n` vertices and `edges`, find all articulation points (vertices whose removal disconnects the graph). Return a list of such vertices.

```
Input:  n=7, edges=[[0,1],[1,2],[2,0],[1,3],[3,4],[4,5],[5,3],[3,6]]
Output: [1, 3]

Explanation:
  Removing 1: {0,2} disconnects from {3,4,5,6}. Cut vertex ✓
  Removing 3: {4,5} stays connected; {0,1,2} stays; but 6 disconnects. ✓
  Removing others: graph stays connected.
```

### Pattern Recognition
Tarjan's low-link with DFS-root special case — same DFS as bridges but the check uses `low[v] >= disc[u]` (not strict `>`) for non-root vertices; the root vertex is a cut vertex iff it has ≥ 2 DFS-tree children.

### Key Insight
Bridge condition (`low[v] > disc[u]`): v's subtree cannot reach u or above at all. Articulation condition (`low[v] >= disc[u]`): v's subtree can reach at most u itself. Removing u still disconnects v's subtree from u's ancestors — because u is the gateway. The root is special because `low` of its children always satisfies `<= disc[root] = 0`, but the root still disconnects the graph if it has multiple DFS-tree children.

### Approach
DFS with `disc`, `low`, `parent`. Track `dfsChildren[u]` (number of DFS-tree children of each vertex). Non-root u is an articulation point if any child v has `low[v] >= disc[u]`. Root u is an articulation point if `dfsChildren[u] >= 2`.

### Solution

```js
function articulationPoints(n, edges) {
  const adj = Array.from({ length: n }, () => []);
  for (const [u, v] of edges) {
    adj[u].push(v);
    adj[v].push(u);
  }

  const disc     = new Array(n).fill(-1);
  const low      = new Array(n).fill(0);
  const isAP     = new Array(n).fill(false);
  let timer = 0;

  function dfs(u, parent) {
    disc[u] = low[u] = timer++;
    let dfsChildren = 0; // count of DFS-tree children (not all neighbors)

    for (const v of adj[u]) {
      if (v === parent) continue;

      if (disc[v] === -1) {
        dfsChildren++;
        dfs(v, u);
        low[u] = Math.min(low[u], low[v]);

        // Non-root articulation check: v's subtree can reach at most u
        if (parent !== -1 && low[v] >= disc[u]) {
          isAP[u] = true;
        }
      } else {
        // Back edge: update low with disc (not low) of ancestor
        low[u] = Math.min(low[u], disc[v]);
      }
    }

    // Root articulation check: root with multiple DFS-tree children
    if (parent === -1 && dfsChildren >= 2) {
      isAP[u] = true;
    }
  }

  dfs(0, -1); // start from vertex 0 for a connected graph
  return isAP.map((ap, i) => ap ? i : -1).filter(i => i !== -1);
}
```

## Problem 5 — Find Eventual Safe States

### Problem
There is a directed graph with `n` nodes and `graph[i]` is a list of nodes that node `i` goes to. A node is a **terminal** if it has no outgoing edges. A node is **safe** if every possible path from it leads to a terminal (i.e., it doesn't participate in or lead to any cycle). Return all safe nodes in ascending order.

```
Input:  graph = [[1,2],[2,3],[5],[0],[5],[],[]]
Output: [2,4,5,6]

Input:  graph = [[1,2,3,4],[1,2],[3,4],[0,4],[]]
Output: [4]
```

### Pattern Recognition
Reverse-graph BFS from terminals — reverse all edges; start BFS from nodes with out-degree 0 (terminals in original = in-degree 0 in reversed); propagate "safe" status backward through the reversed graph. A node is safe when all its original neighbors (reversed in-degree 0) have been confirmed safe. Equivalently: detect and exclude nodes on or leading to cycles.

### Key Insight
A node is unsafe iff it can reach a cycle. In the reversed graph, a node is safe iff it is reachable from a terminal — because "reachable from terminal in G^R" means "can reach a terminal in G." Starting BFS from all terminals and propagating backward through G^R identifies all safe nodes in O(V + E).

### Approach
Build reversed graph `radj`. Compute out-degree (in original) for each node — this becomes the "pending safe-neighbor count." Initialize queue with all terminal nodes (out-degree 0). BFS: for each safe node u, iterate over its reversed neighbors v; decrement `pending[v]`; if `pending[v] == 0` (all of v's original out-edges lead to safe nodes), add v to queue. Collect all nodes reached by BFS.

### Solution

```js
function eventualSafeNodes(graph) {
  const n = graph.length;
  const rgraph = Array.from({ length: n }, () => []); // reversed graph
  const outDeg = new Array(n).fill(0); // out-degree in original = "pending" safe count

  for (let u = 0; u < n; u++) {
    for (const v of graph[u]) {
      rgraph[v].push(u); // reverse edge: v → u in reversed graph
      outDeg[u]++;       // u has one more out-edge to satisfy
    }
  }

  const queue = [];
  // Terminals (out-degree 0) are trivially safe — start from them
  for (let u = 0; u < n; u++) {
    if (outDeg[u] === 0) queue.push(u);
  }

  const safe = new Array(n).fill(false);
  let head = 0;

  while (head < queue.length) {
    const u = queue[head++];
    safe[u] = true;

    // For each node v that originally points to u:
    // one of v's out-edges now leads to a safe node → decrement pending
    for (const v of rgraph[u]) {
      outDeg[v]--;
      if (outDeg[v] === 0) {
        // All of v's out-edges lead to safe nodes → v is safe
        queue.push(v);
      }
    }
  }

  const result = [];
  for (let i = 0; i < n; i++) {
    if (safe[i]) result.push(i);
  }
  return result; // already in ascending order since we iterate 0..n-1
}
```

### Complexity
- Time: O(V + E) — reversed graph build O(V + E); BFS visits each vertex once and each edge once.
- Space: O(V + E) for the reversed graph; O(V) for outDeg, safe, queue.

### Edge Cases
- **All terminals**: no edges → all nodes are safe. outDeg = all 0 → queue initialized with all n nodes. All marked safe.
- **Cycle with no terminal reachable**: nodes in a pure cycle never get added to the queue (outDeg never reaches 0). Correctly marked unsafe.
- **Node leading to a cycle then a terminal**: if v has two out-edges — one to a cycle node and one to a terminal — v is NOT safe (some paths from v lead to a cycle). outDeg[v] will never reach 0 because the edge to the cycle node never decrements (cycle nodes are never marked safe).
- **Self-loop**: node u has an out-edge to itself. outDeg[u] ≥ 1 always; u is never added to the queue. Correctly marked unsafe.

### Follow-up Questions
- "SCC-based approach?" — Find all SCCs. Nodes in SCCs of size ≥ 2 are unsafe. Nodes in SCCs of size 1 are safe iff they have no self-loop and all their out-edges lead to safe SCCs. Traverse condensation DAG in topological order. O(V + E) same complexity, more code.
- "What if the graph is undirected?" — Every edge on a cycle makes both endpoints unsafe. Use DFS cycle detection or Tarjan's SCC (SCCs of size ≥ 2 in undirected = biconnected components with cycles).

## Problem 6 — Minimum Number of Vertices to Reach All Nodes

### Problem
Given a directed acyclic graph with `n` vertices and a list of `edges`, find the smallest set of vertices from which all nodes in the graph are reachable. A vertex is in the result if it cannot be reached from any other vertex.

```
Input:  n=6, edges=[[0,1],[0,2],[2,5],[3,4],[4,2]]
Output: [0,3]   (from 0: reach 0,1,2,5. from 3: reach 3,4,2,5. Together cover all 6.)

Input:  n=5, edges=[[0,1],[2,1],[3,1],[1,4],[2,4]]
Output: [0,2,3]
```

### Pattern Recognition
Condensation property — in a DAG, the minimum set of vertices to reach all others is exactly the set of vertices with in-degree 0. Vertices with in-degree > 0 are reachable from some other vertex; vertices with in-degree 0 are not reachable from anywhere and must be in the starting set.

### Key Insight
In the condensation DAG, source nodes (in-degree 0) are the "entry points" — no other node leads into them. They must be included in any covering set. Non-source nodes are reachable from some source through the DAG paths; including them in the starting set is redundant. Since the problem guarantees the input is a DAG, the condensation IS the input graph, and the answer is simply all vertices with in-degree 0.

### Approach
Count in-degree for each vertex. Return all vertices with in-degree 0. O(V + E) — one pass to build in-degree counts.

### Solution

```js
function findSmallestSetOfVertices(n, edges) {
  const inDeg = new Array(n).fill(0);

  // Count how many edges point INTO each vertex
  for (const [, v] of edges) {
    inDeg[v]++;
  }

  // All vertices with no incoming edges must be in the starting set
  // They cannot be reached from any other vertex — only they can "start" traversal
  const result = [];
  for (let i = 0; i < n; i++) {
    if (inDeg[i] === 0) result.push(i);
  }

  return result;
}
```

### Complexity
- Time: O(V + E) — single pass over edges for in-degree computation; single pass over vertices for result.
- Space: O(V) — in-degree array.

### Edge Cases
- **All vertices have in-degree 0** (no edges): every vertex must be a starting point. Return all n vertices.
- **One source vertex** (root of a tree/DAG): only vertex 0 has in-degree 0; from it all other vertices are reachable. Return [0].
- **Problem guarantees no cycles**: if cycles existed, the in-degree-0 heuristic would not necessarily work. For a general directed graph (with cycles), condense SCCs first, then find source SCCs (in-degree 0 in the condensation). This problem's DAG constraint makes condensation trivial (each vertex is its own SCC).
- **Isolated vertex** (no edges at all, n=1): inDeg[0]=0 → result=[0]. Correct.

### Follow-up Questions
- "What if the graph has cycles (general directed graph)?" — Build the condensation DAG (Tarjan's or Kosaraju's to find SCCs). Find all source SCCs (in-degree 0 in condensation). The answer is one representative vertex from each source SCC (any vertex from that SCC suffices — all vertices in an SCC can reach each other).
- "What if you want all vertices in the minimum set, including non-sources?" — Not possible to reduce further than in-degree-0 vertices. Any non-in-degree-0 vertex is reachable from someone else — including it is redundant.

## Quick Reference — SCC & Low-Link Pattern Decision Tree

```
What does the problem require?
│
├── FIND ALL STRONGLY CONNECTED COMPONENTS (directed graph)?
│   ├── Tarjan's (single pass, more elegant):
│   │   disc[u] = low[u] = timer++. Push to stack, onStack[u]=true.
│   │   Tree edge (u,v): recurse, then low[u]=min(low[u],low[v]).
│   │   Back edge (onStack[v]): low[u]=min(low[u],disc[v]). NOT low[v].
│   │   SCC root: disc[u]==low[u] → pop stack until u.
│   │
│   └── Kosaraju's (two passes, easier to verify):
│       Pass 1: DFS on G, push to order AFTER all descendants (post-order).
│       Pass 2: DFS on G^R in reverse order. Each DFS = one SCC.
│
├── FIND BRIDGES (critical edges) in UNDIRECTED graph?
│   └── Tarjan's low-link with parent tracking.
│       Tree edge (u,v): recurse, then check low[v] > disc[u] → bridge.
│       Back edge (v ≠ parent): low[u] = min(low[u], disc[v]).
│       Skip parent edge: if v == parent → continue.
│
├── FIND ARTICULATION POINTS (cut vertices) in UNDIRECTED graph?
│   └── Same DFS as bridges, but two conditions:
│       Non-root u: if any child v has low[v] >= disc[u] → u is AP.
│       Root u: if DFS tree has ≥ 2 children → u is AP.
│       (Bridge: >, Articulation: >=. Subtle but critical.)
│
├── FIND SAFE NODES (not on or leading to any cycle)?
│   └── Reverse-graph BFS from terminals.
│       outDeg[u] = number of outgoing edges.
│       Queue: all terminals (outDeg=0). Propagate: decrement outDeg for predecessors.
│       Safe when outDeg reaches 0 (all paths lead to safe nodes).
│
├── MINIMUM STARTING SET TO REACH ALL NODES (DAG)?
│   └── In-degree 0 vertices in the DAG.
│       For general digraph: condense SCCs → find source SCCs (in-deg 0 in condensation).
│       Return one representative from each source SCC.
│
└── WHICH ALGORITHM TO CHOOSE?
    Tarjan's wins when:   Single pass needed; bridges/APs also required; elegant.
    Kosaraju's wins when: Easier correctness verification under time pressure.
    Both:                 O(V+E) time, O(V) space (excluding G^R for Kosaraju's).
```

## Common Bugs Checklist

Before submitting any SCC or low-link solution, verify:

1. **Tarjan's back-edge update uses `disc[v]`, not `low[v]`?** — `low[u] = min(low[u], low[v])` for on-stack v would transitively pull low[u] further back than the direct ancestor, potentially merging SCCs that should be separate. Always use `disc[v]` for on-stack neighbors; `low[v]` is used only for tree-edge propagation after recursive return.

2. **Tarjan's checks `onStack[v]` not just `disc[v] != -1`?** — `disc[v] != -1 && !onStack[v]` means v is in a completed SCC (cross edge). Using `disc[v] != -1` alone would update low[u] using v's disc time even for cross edges to finished SCCs, incorrectly merging the current SCC with a completed one.

3. **Tarjan's pops the stack correctly — until v == u (inclusive), not until stack is empty?** — The SCC root u must be popped last (it's deepest in the stack among its SCC). Popping until `w == u` (inclusive break) is correct. Popping all elements or stopping before u leaves wrong vertices in the wrong SCCs.

4. **Kosaraju's Pass 1 pushes to `order` AFTER the recursive call (post-order), not before?** — Pre-order push records arrival times, not finish times. The algorithm requires finish order — vertices that finish later (all their descendants explored) come later in `order`. Pre-order would produce the wrong relative ordering between SCC source nodes and their targets.

5. **Kosaraju's Pass 2 processes `order` in REVERSE (from the end), not forward?** — `order[order.length-1]` is the last-finishing vertex (the SCC source). Processing forward would start with the earliest-finishing vertex (in a sink SCC), which then DFS-explores back through G^R to source SCCs, merging all reachable SCCs incorrectly.

6. **Bridge detection skips the parent edge using `v === parent`, not `disc[v] < disc[u]`?** — `disc[v] < disc[u]` would skip all back edges to ancestors, not just the parent edge. In an undirected graph, only the specific edge used to arrive at u should be skipped; other edges to ancestors are legitimate back edges that should update `low[u]`. Pass `parent` into the recursion and check `v === parent`.

7. **Bridge condition uses strict `>` while articulation point uses `>=`?** — `low[v] > disc[u]`: v's subtree can't even reach u — removing edge (u,v) disconnects. `low[v] >= disc[u]`: v's subtree can reach at most u — removing vertex u disconnects v's subtree from u's proper ancestors. Using `>=` for bridges misses the case where the edge (u,v) still has v connected to u via a back edge (not a bridge).

8. **Articulation point root check counts DFS-tree children, not total neighbors?** — The root check is: DFS-tree children ≥ 2. DFS-tree children are only those reached via tree edges (unvisited at the time of the visit from root). Counting all neighbors of the root (including back-edge targets) inflates the count. Increment `dfsChildren` only when `disc[v] === -1` at the time of the recursive call.

9. **Eventual Safe States: decrementing `outDeg[v]` for each INCOMING safe neighbor (in reversed graph), not for each outgoing?** — When node u is confirmed safe, all nodes v that had u as a destination (edge v→u in original = u→v in G^R) should have `outDeg[v]` decremented. The reversed graph edges `rgraph[u]` give exactly these v's — iterate `rgraph[u]` and decrement `outDeg[v]`.

10. **Minimum Vertices: the problem guarantees a DAG — using in-degree 0 works only on DAGs?** — For general directed graphs (with cycles), in-degree 0 is insufficient — a vertex in a cycle but with no incoming edges from outside the cycle still needs to be included. Always check the problem constraints: if a general digraph, condense SCCs first, find source SCCs, then return representatives.

11. **Tarjan's on disconnected graphs: outer loop runs DFS on ALL unvisited vertices?** — A single `dfs(0)` only handles the connected component containing vertex 0. The outer `for (let i = 0; i < n; i++) if (disc[i] === -1) dfs(i)` is mandatory to cover all components. Same for Kosaraju's both passes.

12. **Kosaraju's building G^R: for each edge (u,v) in G, add (v,u) in G^R — not (u,v) again?** — Adding the same edge to a "reversed" graph is a common copy-paste error. `radj[v].push(u)` is correct; `radj[u].push(v)` would just duplicate the original graph.

**Final Tip:** At the 5 YOE level, the decisive signal for SCC and low-link problems is articulating **the specific invariant being maintained** before touching code. For Tarjan's: *"I maintain `disc[u] == low[u]` as the SCC-root condition — it holds iff u is the first-visited vertex in its SCC, meaning u's subtree has no back edge escaping to a proper ancestor of u. I update low using `disc[v]` (not `low[v]`) for on-stack back edges, and I exclude cross edges to completed SCCs entirely."* For bridges: *"Edge (u,v) is a bridge iff `low[v] > disc[u]` — strict inequality means v's subtree has no back edge that bypasses u, so the single tree edge is the only connection. I pass parent into the recursion to skip the arrival edge — treating it as a back edge would spuriously lower `low[v]` and hide real bridges."* Stating the invariant, the update rule, and the one critical distinction (disc vs low for back edges; > vs >= for bridge vs AP; on-stack vs visited for Tarjan's) in two sentences is the mark of a senior who has internalized the algorithm rather than memorized the code.
