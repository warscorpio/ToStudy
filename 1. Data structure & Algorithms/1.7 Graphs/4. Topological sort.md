---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is topological sorting, and what type of graph does it apply to?**
A: Topological sorting produces a **linear ordering of the vertices** of a directed graph such that for every directed edge `u → v`, vertex `u` appears before vertex `v` in the ordering. It applies only to **Directed Acyclic Graphs (DAGs)** — directed graphs with no cycles. If a cycle exists, no valid topological order can exist (because a cycle creates a circular dependency where each node in the cycle would need to appear before all the others simultaneously, which is impossible in any linear ordering).

```
DAG:
  5 → 0 ← 4
  5 → 2 ← 4
  2 → 3
  3 → 1

Valid topological orders: [5, 4, 2, 3, 1, 0]  or  [4, 5, 2, 3, 1, 0]  (multiple valid orderings possible)
```

**Q2. What real-world problems does topological sorting model?**
A: Any problem involving **dependency resolution** — where some tasks must be completed before others — maps directly to topological sorting: build system compilation order (a source file must be compiled before files that depend on it), package dependency installation order, course prerequisite scheduling (take prerequisite courses before advanced ones), spreadsheet formula evaluation order, and Makefile target resolution. In each case, the vertices are tasks/items and directed edges represent "must come before" dependency relationships.

**Q3. Why can topological sort only apply to DAGs — what fundamentally breaks in the presence of a cycle?**
A: A directed cycle creates a circular dependency: if `A → B → C → A`, then A must come before B (by the A→B edge), B must come before C (by B→C), and C must come before A (by C→A) — all simultaneously, which is impossible for any linear ordering. So a cycle makes the problem infeasible, not just harder. This is why both standard topological sort algorithms use **cycle detection as a natural byproduct**: Kahn's algorithm produces a partial ordering shorter than the total vertex count if a cycle exists (the nodes in the cycle can never have their in-degree reduced to 0 and thus are never enqueued), and the DFS-based method detects cycles by finding a back edge (an edge that leads to a node already on the current recursion path).

**Q4. Is a topological ordering unique, and what determines how many valid orderings exist?**
A: A topological ordering is **unique** only when the graph is a simple directed path (a chain where every node has exactly one incoming and one outgoing edge, forming a total order). In general, multiple valid topological orderings exist for a DAG — any ordering that respects all dependency edges is valid. The number of valid orderings grows with the number of "independent" vertices that can be scheduled in any relative order (vertices with no dependency relationship between them). Kahn's algorithm at each step can enqueue multiple zero-in-degree vertices in any order, and each such ordering choice produces a distinct (but equally valid) topological sort.

### Section 2: Kahn's Algorithm (BFS-Based)

**Q5. What is Kahn's algorithm, and what is its core insight?**
A: Kahn's algorithm builds the topological order iteratively using the following insight: **a vertex with in-degree 0 has no remaining predecessors, so it can safely be placed next in the ordering** — all its dependencies (which are zero in number) have already been satisfied. Starting with all zero-in-degree vertices, placing each one, reducing the in-degree of its successors (simulating "removing" it from the graph), and then enqueueing any newly-zeroed-in-degree successors, repeats this process until either all vertices have been placed (a valid DAG) or some vertices remain stuck at positive in-degree due to a cycle.

```
Steps:
1. Compute in-degree for every vertex.
2. Enqueue all vertices with in-degree = 0.
3. While queue is not empty:
   a. Dequeue a vertex u, append it to the topological order.
   b. For every outgoing edge u → v: decrement in-degree[v].
      If in-degree[v] becomes 0, enqueue v.
4. If the topological order contains all vertices, it's valid.
   Otherwise, the graph has a cycle.
```

```js
function kahnsTopologicalSort(numVertices, edges) {
  const adj = Array.from({ length: numVertices }, () => []);
  const inDegree = new Array(numVertices).fill(0);

  for (const [u, v] of edges) {
    adj[u].push(v);
    inDegree[v]++;
  }

  const queue = [];
  for (let i = 0; i < numVertices; i++) {
    if (inDegree[i] === 0) queue.push(i);
  }

  const order = [];
  while (queue.length > 0) {
    const u = queue.shift();
    order.push(u);

    for (const v of adj[u]) {
      inDegree[v]--;
      if (inDegree[v] === 0) queue.push(v);
    }
  }

  return order.length === numVertices ? order : []; // [] signals a cycle was detected
}
```

**Q6. What is the time and space complexity of Kahn's algorithm?**
A: Time: **O(V + E)** — each vertex is enqueued and dequeued exactly once (O(V)), and each edge is processed exactly once when its source vertex is dequeued (O(E)). Space: **O(V + E)** — the adjacency list (O(V + E)), the in-degree array (O(V)), and the queue (O(V) in the worst case, if all vertices are enqueued simultaneously). This is asymptotically optimal — a correct topological sort algorithm must inspect every vertex and every edge at least once, making O(V + E) a lower bound.

**Q7. How does Kahn's algorithm detect a cycle as a natural byproduct, without any extra cycle-detection code?**
A: If the graph contains a cycle, every vertex inside the cycle has at least one incoming edge from within the cycle itself — so their in-degree can never reach 0 (the edges from the cycle are never "removed," since the cycle's vertices are never enqueued and thus never processed). After the queue empties, `order.length < numVertices` — some vertices remain with positive in-degree, stranded in the cycle. This count comparison (`order.length === numVertices`) is all that's needed to distinguish "valid DAG, full ordering found" from "cycle present, partial ordering only."

**Q8. Why is Kahn's algorithm specifically BFS-based, and does using DFS for the queue give a different result?**
A: Kahn's algorithm uses a standard FIFO queue (BFS-style) to process zero-in-degree vertices. Using a stack (LIFO) instead would also produce a valid topological ordering — the fundamental correctness guarantee ("only place a vertex when all its predecessors have been placed") doesn't depend on whether the queue is FIFO or LIFO; what matters is only that every vertex placed was at in-degree 0 at the time it was processed. Different queue disciplines simply produce different (but equally valid) topological orderings of the same DAG — a **min-heap** instead of a queue produces the **lexicographically smallest** valid topological ordering, which is a commonly-asked interview variant.

### Section 3: DFS-Based Topological Sort

**Q9. How does the DFS-based topological sort algorithm work, and why does it produce a valid order?**
A: Perform a standard DFS, but **push each fully-finished vertex onto a stack** (after all its descendants in the DFS tree have been fully explored, i.e., in "post-order"). The topological ordering is the stack's contents read top-to-bottom (reversing the post-order finish sequence). This works because: if there's an edge `u → v`, DFS will fully finish exploring `v` (and all of v's descendants) before finishing `u` (since u's DFS explores v as part of its own exploration), so `v` gets pushed onto the stack before `u`, and thus `u` appears before `v` when the stack is read — respecting the required ordering.

```js
function dfsTopologicalSort(numVertices, adj) {
  const UNVISITED = 0, IN_STACK = 1, DONE = 2;
  const state = new Array(numVertices).fill(UNVISITED);
  const stack = [];
  let hasCycle = false;

  function dfs(u) {
    if (hasCycle) return;
    state[u] = IN_STACK;

    for (const v of adj[u]) {
      if (state[v] === IN_STACK) {
        hasCycle = true;
        return;
      }
      if (state[v] === UNVISITED) {
        dfs(v);
      }
    }

    state[u] = DONE;
    stack.push(u);
  }

  for (let i = 0; i < numVertices; i++) {
    if (state[i] === UNVISITED) dfs(i);
  }

  return hasCycle ? [] : stack.reverse();
}
```

**Q10. Why does the DFS method use THREE states (UNVISITED, IN_STACK, DONE) rather than just two (visited/not visited)?**
A: Two states (visited/not-visited) would allow DFS to correctly avoid revisiting already-fully-processed vertices, but would **silently miss cycles** — if DFS encounters a vertex that's been previously visited, it can't tell whether that vertex was visited during the current DFS path (indicating a back edge and thus a cycle) or during a completely separate earlier DFS call (indicating a cross-edge, perfectly fine in a DAG). The three-state distinction — `IN_STACK` (currently on the active DFS recursion path) versus `DONE` (previously fully processed but not currently on the path) — is exactly what enables cycle detection: encountering an `IN_STACK` vertex means a back edge exists (a cycle), while encountering a `DONE` vertex is safe to skip without any cycle implication.

**Q11. What is the time and space complexity of the DFS-based topological sort?**
A: Time: **O(V + E)** — each vertex is visited at most once by DFS across all starting-vertex calls (since once a vertex is marked DONE, no further DFS work is done on it), and each edge is traversed at most once. Space: **O(V + E)** — the adjacency list, the state array, the recursion call stack (O(h) deep, where h is the DFS tree's maximum depth, bounded by V), and the output stack (O(V)). Same asymptotic complexity as Kahn's algorithm.

**Q12. In the DFS approach, why must you push a vertex onto the output stack AFTER (not before) recursing into its neighbors?**
A: Pushing before recursing would record the vertex before its dependents (successors) have been fully processed — when the stack is reversed, this would place the vertex too early in the ordering (before all its successors, which is correct), but the reason it works is precisely the post-order placement: all successors of `u` are guaranteed to be pushed before `u` is pushed (since they're reached by recursing from within `u`'s DFS call), ensuring they all end up deeper in the stack than `u`, and thus appear AFTER `u` when the stack is reversed. Pushing before recursing would create a pre-order placement, producing an ordering that doesn't respect the dependency direction.

### Section 4: Comparing Kahn's vs DFS

**Q13. What are the key practical differences between Kahn's algorithm and the DFS method, and when might you prefer one over the other?**
A:

| Property | Kahn's (BFS-based) | DFS-based |
|---|---|---|
| **Core mechanism** | Iteratively places zero-in-degree vertices | Post-order recursion with stack reversal |
| **Cycle detection** | `order.length < V` after processing | Detecting a back edge (IN_STACK state) |
| **Ease of understanding** | More intuitive — direct dependency simulation | Slightly less intuitive — relies on post-order reasoning |
| **Iterative implementation** | Naturally iterative (uses a queue explicitly) | Naturally recursive; iterative version requires explicit stack simulation |
| **Stack overflow risk** | None | O(V) recursion depth — risk on very large dense graphs |
| **Lexicographically smallest sort** | Replace queue with min-heap — straightforward | Harder to guarantee without significant changes |
| **Parallelism insight** | Queue contents at each "round" = vertices that can be processed in parallel | Not as directly visible |

Kahn's is generally preferred in interview contexts for its explicitness and direct connection to the "dependency resolution" mental model. DFS is often covered because it arises naturally from DFS/post-order traversal concepts, and because many interviewers ask for it specifically as a variant.

**Q14. How does Kahn's algorithm's queue contents reveal which tasks could be processed in PARALLEL?**
A: All vertices in the queue at any given moment represent tasks whose dependencies have all been satisfied — they could all be started simultaneously in a parallel/concurrent execution model. Processing Kahn's algorithm in "rounds" (where a round = processing all currently-queued vertices together, then enqueuing their newly-zeroed successors as the next round's queue) directly produces the **critical path** / **level-by-level** structure of the dependency graph, analogous to BFS level-grouping in a tree. The number of rounds (not the total number of vertices) is the minimum possible parallel execution time — a useful insight for scheduling problems.

### Section 5: Advanced Patterns

**Q15. How does the "course schedule" / "can all courses be taken?" variant reduce to cycle detection in a directed graph, and why is topological sort the standard approach?**
A: A valid course completion order exists if and only if the prerequisite dependency graph is a DAG (no circular prerequisites). Finding whether a valid order exists is exactly "does a topological sort exist?" which reduces to cycle detection. Kahn's algorithm is ideal: run it, and if `order.length === numCourses`, all courses can be taken (no cycle); otherwise, some cycle of circular prerequisites prevents full completion. If the actual order is needed (not just whether one exists), Kahn's naturally produces it.

**Q16. What is the "minimum number of semesters" / "course scheduling with parallelism" variant, and how does it extend Kahn's algorithm?**
A: This variant asks: given prerequisites and a limit on how many courses can be taken per "semester" (or assuming unlimited parallel capacity), what's the minimum number of semesters to complete all courses? This maps directly to the "rounds" insight from Q14: process Kahn's algorithm in rounds (one round = one semester), where each round processes all currently-zero-in-degree courses; the number of rounds is the answer. With an unlimited parallel capacity per round, this gives the critical-path length of the DAG (the longest dependency chain), the true minimum. With a limited-capacity-per-round constraint (e.g., at most k courses per semester), you must greedily pick the best k available courses each round (e.g., those with the fewest remaining dependents, or according to some other prioritization) — still a BFS/Kahn's-style approach but with a priority-queue-based selection within each round.

**Q17. How does topological sort apply to detecting deadlock in operating systems?**
A: Model resources and processes as vertices, and resource-holding/waiting relationships as directed edges. A deadlock exists if and only if this "resource allocation graph" contains a cycle — which is precisely what cycle detection (via topological sort's cycle-detection byproduct) detects. Kahn's algorithm run on this graph: if any vertices are left with positive in-degree after the algorithm completes, those vertices form a cycle representing a deadlocked set of processes.

**Q18. Can topological sort be applied to an undirected graph?**
A: No — topological sort fundamentally requires directed edges (which encode "A must come before B" directionality). An undirected graph's edges have no inherent direction, so "A before B" vs "B before A" is undefined. Additionally, any undirected edge between two vertices creates a path in both directions, making the graph structurally equivalent to having both directed edges (u→v and v→u), which would make it impossible for any topological ordering to satisfy both simultaneously — the graph would be considered to have a "cycle" in this directed-edge interpretation.

### Section 6: Scenario / Interview-Style Questions

**Q19. "You're given a list of build tasks where some tasks depend on others — design a system to determine a valid build order, and what if circular dependencies exist?"**
A: Model each task as a vertex and each dependency (A must complete before B) as a directed edge A→B. Run Kahn's algorithm: initialize in-degrees from the edge list, start with all zero-in-degree tasks, repeatedly place the next task and reduce successors' in-degrees, enqueueing newly-zeroed ones. The output is the valid build order. If `order.length < total tasks`, a circular dependency exists — I'd report which tasks couldn't be reached (those with remaining positive in-degree) as part of the cycle, helping the user diagnose and fix the dependency configuration.

**Q20. "A teammate implements topological sort by just running DFS and using the order nodes are FIRST visited (pre-order), not the order they finish. What's wrong?"**
A: Pre-order DFS visits a vertex before any of its descendants — exactly the opposite timing from what topological sort needs. A vertex's position in the topological order should come before all its dependents (correct), but pre-order places it before exploring its neighbors at all, which doesn't guarantee anything about whether those neighbors' own dependencies have already been fully resolved. Specifically, consider a vertex `u` with edge `u→v→w`: pre-order would record `u` first (correct), then `v` second (correct), then `w` third (correct for this chain) — but for a graph where `u` also has an edge `u→x` where `x→v` exists, pre-order might record `v` before `x` even though `x→v` means x must precede v. Post-order (record when finished, then reverse) correctly resolves this by ensuring every dependent is processed before the vertex itself is recorded.

**Q21. "How would you find all possible topological orderings of a given DAG, not just one?"**
A: Adapt Kahn's algorithm into a backtracking/recursive exploration: at each step, instead of picking one zero-in-degree vertex, try every available zero-in-degree vertex as the next choice, recursing into each option, restoring in-degrees on backtrack, and collecting all complete orderings when the current path length reaches the total vertex count. This is exponentially expensive in the worst case (a completely independent graph has n! orderings), so it's only practical for small graphs — the question tests whether you recognize this as a backtracking extension of Kahn's, not as a fundamentally different algorithm.

**Q22. "How would you find the lexicographically smallest topological ordering?"**
A: Replace Kahn's standard FIFO queue with a **min-heap** (priority queue ordered by vertex value/label). At each step, the min-heap always surfaces the smallest-label zero-in-degree vertex next, greedily building the lexicographically smallest valid prefix at each position. This works because, by Kahn's correctness argument, any zero-in-degree vertex is valid to place next — and among all valid choices, the min-heap always picks the globally-smallest available one, guaranteeing the lexicographically smallest overall ordering.

## Problem 1 — Course Schedule (Can All Courses Be Finished?)

### Problem
There are `numCourses` courses labeled `0` to `numCourses - 1`. You are given an array `prerequisites` where `prerequisites[i] = [a, b]` means you must take course `b` before course `a`. Return `true` if it is possible to finish all courses, `false` if a cycle makes this impossible.

```
Input:  numCourses = 2, prerequisites = [[1, 0]]
Output: true   (take 0, then 1)

Input:  numCourses = 2, prerequisites = [[1, 0], [0, 1]]
Output: false  (circular: 0 requires 1 and 1 requires 0)
```

### Pattern Recognition
Cycle detection in a directed graph — the ability to finish all courses is equivalent to the prerequisite dependency graph being a DAG. Kahn's algorithm determines this as a direct byproduct.

### Key Insight
A valid course-completion order exists if and only if the prerequisite graph has no cycles. Running Kahn's and checking whether the resulting order covers all `numCourses` vertices is a clean, single-pass answer to both "does a cycle exist?" and "what is the valid order?" simultaneously.

### Approach
Build an adjacency list and in-degree array from the prerequisites (edge `b → a` for each `[a, b]` prerequisite pair — "b must come before a"). Run Kahn's algorithm. If `order.length === numCourses`, return `true`; otherwise, return `false`.

### Solution

```js
function canFinish(numCourses, prerequisites) {
  const adj = Array.from({ length: numCourses }, () => []);
  const inDegree = new Array(numCourses).fill(0);

  for (const [a, b] of prerequisites) {
    adj[b].push(a); // b must be taken before a  →  edge b → a
    inDegree[a]++;
  }

  const queue = [];
  for (let i = 0; i < numCourses; i++) {
    if (inDegree[i] === 0) queue.push(i);
  }

  let count = 0;
  while (queue.length > 0) {
    const u = queue.shift();
    count++;

    for (const v of adj[u]) {
      inDegree[v]--;
      if (inDegree[v] === 0) queue.push(v);
    }
  }

  return count === numCourses;
}
```

### Dry Run

```
numCourses=4, prerequisites=[[1,0],[2,0],[3,1],[3,2]]
Edges: 0→1, 0→2, 1→3, 2→3

Build adjacency list and in-degrees:
adj = { 0:[1,2], 1:[3], 2:[3], 3:[] }
inDegree = [0, 1, 1, 2]  (course 0: no prereqs; 1 and 2: one prereq each; 3: two prereqs)

Initial queue (in-degree 0): [0]

Iteration 1: dequeue 0, count=1
  Process neighbors 1 and 2: inDegree[1]=0→enqueue, inDegree[2]=0→enqueue
  queue=[1,2]

Iteration 2: dequeue 1, count=2
  Process neighbor 3: inDegree[3]=1 (not yet 0)
  queue=[2]

Iteration 3: dequeue 2, count=3
  Process neighbor 3: inDegree[3]=0→enqueue
  queue=[3]

Iteration 4: dequeue 3, count=4
  No neighbors
  queue=[]

count(4) === numCourses(4) → return true ✓
```

### Complexity
- Time: O(V + E) where V = numCourses, E = prerequisites.length.
- Space: O(V + E) for the adjacency list, in-degree array, and queue.

### Edge Cases
- No prerequisites at all: every course has in-degree 0, all are immediately enqueued, count reaches `numCourses` trivially → `true`.
- Single course, no prerequisites: count reaches 1 = numCourses immediately → `true`.
- Direct self-loop (`[0, 0]`): course 0's in-degree starts at 1 (from its own prerequisite), never reaches 0, never gets enqueued → count never reaches `numCourses` → `false`.
- Multiple disconnected components (some courses completely independent of others): Kahn's handles this naturally since every zero-in-degree node across all components gets enqueued in the initialization step.

### Follow-up Questions
- "Return the actual course order, not just true/false?" → See Problem 2 — trivially extends by collecting the order array during Kahn's processing.
- "What if a course can have at most k prerequisites taken simultaneously per semester?" → See Q16 — process Kahn's in rounds, limiting each round to k courses.

## Problem 2 — Course Schedule II (Return the Ordering)

### Problem
Same setup as Problem 1, but return a valid ordering of all courses to finish them all (any valid topological ordering), or an empty array if it's impossible.

```
Input:  numCourses = 4, prerequisites = [[1,0],[2,0],[3,1],[3,2]]
Output: [0, 2, 1, 3]  (or [0, 1, 2, 3], or other valid orderings)

Input:  numCourses = 2, prerequisites = [[0,1],[1,0]]
Output: []  (cycle detected)
```

### Pattern Recognition
Kahn's algorithm in its full form — not just cycle detection, but collecting the actual topological ordering built during execution.

### Key Insight
The order in which Kahn's algorithm dequeues vertices IS a valid topological ordering (by construction — each dequeued vertex had in-degree 0 at the time it was placed, meaning all its predecessors had already been placed). The output array simply accumulates these placements.

### Approach
Same as Problem 1, but build and return the `order` array. If `order.length < numCourses` when processing ends, return `[]` to signal the cycle.

### Solution

```js
function findOrder(numCourses, prerequisites) {
  const adj = Array.from({ length: numCourses }, () => []);
  const inDegree = new Array(numCourses).fill(0);

  for (const [a, b] of prerequisites) {
    adj[b].push(a);
    inDegree[a]++;
  }

  const queue = [];
  for (let i = 0; i < numCourses; i++) {
    if (inDegree[i] === 0) queue.push(i);
  }

  const order = [];
  while (queue.length > 0) {
    const u = queue.shift();
    order.push(u);

    for (const v of adj[u]) {
      inDegree[v]--;
      if (inDegree[v] === 0) queue.push(v);
    }
  }

  return order.length === numCourses ? order : [];
}
```

### Dry Run

```
numCourses=4, prerequisites=[[1,0],[2,0],[3,1],[3,2]]
(same graph as Problem 1's dry run)

adj={ 0:[1,2], 1:[3], 2:[3], 3:[] }
inDegree=[0,1,1,2]

queue=[0]

Dequeue 0 → order=[0]. Reduce neighbors: inDegree[1]=0→queue, inDegree[2]=0→queue
queue=[1,2]

Dequeue 1 → order=[0,1]. Reduce: inDegree[3]=1 (not 0)
queue=[2]

Dequeue 2 → order=[0,1,2]. Reduce: inDegree[3]=0→queue
queue=[3]

Dequeue 3 → order=[0,1,2,3]. No neighbors.

order.length(4)===numCourses(4) → return [0,1,2,3] ✓
(Valid: 0 before 1 and 2; 1 and 2 both before 3)
```

### Complexity
- Time: O(V + E).
- Space: O(V + E).

### Edge Cases
- Graph with a cycle: `order` is shorter than `numCourses`, correctly returns `[]`.
- Multiple valid orderings exist: the specific ordering returned depends on the order nodes were enqueued (typically determined by how the adjacency list was built and the FIFO queue order) — any valid ordering is an accepted answer.
- `numCourses = 1`, no prerequisites: single course with in-degree 0 immediately enqueued and placed → returns `[0]`.

### Follow-up Questions
- "Return the lexicographically smallest valid ordering?" → Replace the FIFO queue with a min-heap; the rest of the algorithm is unchanged (see Q22).
- "How many distinct valid orderings are there?" → Requires backtracking from Kahn's framework (see Q21) — exponential in the worst case.

## Problem 3 — Topological Sort via DFS (Alien Dictionary)

### Problem
Given a sorted list of words from an "alien language" (which uses the same letters as English but in a different alphabetical order), determine the order of characters in the alien alphabet. Return a valid ordering of the characters, or an empty string if a contradiction (cycle) exists.

```
Input:  words = ["wrt", "wrf", "er", "ett", "rftt"]
Output: "wertf"

Reasoning:
Comparing adjacent pairs gives directed edges between letters:
"wrt" vs "wrf": first difference at index 2 → t comes before f  (t→f)
"wrf" vs "er":  first difference at index 0 → w comes before e  (w→e)
"er" vs "ett":  first difference at index 1 → r comes before t  (r→t)
"ett" vs "rftt": first difference at index 0 → e comes before r  (e→r)

Edges: t→f, w→e, r→t, e→r
DFS topological sort gives: w, e, r, t, f → "wertf"
```

### Pattern Recognition
Graph construction from problem domain + DFS-based topological sort — each pair of adjacent words yields at most one directed edge (from the first differing character in the shorter-comes-first position), and the alien alphabet ordering is a topological sort of the resulting directed character graph.

### Key Insight
Comparing adjacent words in the sorted list gives exactly the ordering constraints between characters — but only the FIRST position of difference per pair (everything before the first difference is already known-consistent from earlier comparisons, and there's no information about positions after the first difference since the remaining characters could be in any relative order). From these edge constraints, a topological sort gives a consistent character ordering, if one exists.

### Approach
1. Collect all unique characters. Build an adjacency list and in-degree map from adjacent word comparisons.
2. Run Kahn's algorithm (or DFS-based sort) on the character graph.
3. If the result covers all unique characters, it's the valid alien alphabet order; otherwise, a cycle contradicts the input.

(Using Kahn's here to demonstrate the contrast with the DFS solution in the dry run — then showing the DFS-based solution code.)

### Solution

```js
function alienOrder(words) {
  // collect all unique characters
  const adj = new Map();
  const inDegree = new Map();

  for (const word of words) {
    for (const ch of word) {
      if (!adj.has(ch)) adj.set(ch, []);
      if (!inDegree.has(ch)) inDegree.set(ch, 0);
    }
  }

  // derive edges from adjacent word comparisons
  for (let i = 0; i < words.length - 1; i++) {
    const w1 = words[i], w2 = words[i + 1];

    // edge case: w1 is a prefix of w2 but longer — invalid input
    if (w1.length > w2.length && w1.startsWith(w2)) return '';

    for (let j = 0; j < Math.min(w1.length, w2.length); j++) {
      if (w1[j] !== w2[j]) {
        adj.get(w1[j]).push(w2[j]);
        inDegree.set(w2[j], inDegree.get(w2[j]) + 1);
        break; // ONLY the first differing character gives information
      }
    }
  }

  // Kahn's topological sort on the character graph
  const queue = [];
  for (const [ch, deg] of inDegree) {
    if (deg === 0) queue.push(ch);
  }

  let result = '';
  while (queue.length > 0) {
    const ch = queue.shift();
    result += ch;

    for (const neighbor of adj.get(ch)) {
      inDegree.set(neighbor, inDegree.get(neighbor) - 1);
      if (inDegree.get(neighbor) === 0) queue.push(neighbor);
    }
  }

  return result.length === inDegree.size ? result : '';
}
```

### Complexity
- Time: O(C + E) where C is the total number of characters across all words (for building the character set and adjacency list), and E is the number of derived edges (bounded by min(words.length - 1, total unique chars²)).
- Space: O(1) extra beyond the adjacency structure (only 26 possible unique characters for English-alphabet problems, making this effectively O(1) space in character-bounded scenarios, or O(C + E) in the general case).

### Edge Cases
- A word is a prefix of the next but comes AFTER it (e.g., `["abc", "ab"]`): this is an impossibility — in a valid sorted language, a prefix always comes BEFORE words that extend it; detecting this via `w1.startsWith(w2) && w1.length > w2.length` and returning `''` immediately is required.
- All words share the same characters in the same order: no edges are derived; every character remains at in-degree 0; multiple valid orderings of the character set exist (any ordering is valid) — the algorithm correctly returns one.
- Cyclic character ordering implied by the word list: Kahn's cycle detection naturally catches this via `result.length < inDegree.size`.

- "Implement this using the DFS-based topological sort instead of Kahn's." → Same edge-construction logic; replace Kahn's processing with the three-state DFS from Q9 on the character graph.
- "What if words can repeat?" → Duplicate adjacent words produce no edge (no differing character found at any position) — the loop simply finds no `j` where `w1[j] !== w2[j]`, and the `break` is never reached, effectively skipping that pair without side effects.

## Problem 4 — Minimum Number of Semesters (Parallel Course Scheduling)

### Problem
You have `n` courses and `relations` where `relations[i] = [prevCourse, nextCourse]` means you must complete `prevCourse` before `nextCourse`. In each semester, you can take **any number** of courses as long as their prerequisites have all been completed. Return the minimum number of semesters to complete all courses.

```
Input:  n = 3, relations = [[1, 3], [2, 3]]
Output: 2
(Semester 1: take courses 1 and 2 simultaneously.
 Semester 2: take course 3 after both are done.)

Input:  n = 3, relations = [[1, 2], [2, 3]]
Output: 3
(Linear chain: semester 1→course 1, semester 2→course 2, semester 3→course 3)
```

### Pattern Recognition
BFS-level Kahn's algorithm — processing in "rounds" where each round represents one semester, directly yielding the minimum number of semesters as the number of BFS levels processed.

### Key Insight
With unlimited courses per semester, the minimum number of semesters equals the **length of the longest dependency chain** in the DAG — the "critical path." Kahn's algorithm naturally computes this by processing the graph in rounds (all currently-available zero-in-degree nodes per round = one semester), with the round count as the answer.

### Approach
Run Kahn's level by level (round by round). Each round: take the entire current set of zero-in-degree courses, reduce their successors' in-degrees, and count one semester. The total number of rounds is the answer. If any node remains un-taken at the end (cycle detected), return -1.

### Solution

```js
function minNumberOfSemesters(n, relations) {
  const adj = Array.from({ length: n + 1 }, () => []);
  const inDegree = new Array(n + 1).fill(0);

  for (const [prev, next] of relations) {
    adj[prev].push(next);
    inDegree[next]++;
  }

  let queue = [];
  for (let i = 1; i <= n; i++) {
    if (inDegree[i] === 0) queue.push(i);
  }

  let semesters = 0;
  let taken = 0;

  while (queue.length > 0) {
    semesters++;
    const nextQueue = [];

    for (const course of queue) {
      taken++;
      for (const next of adj[course]) {
        inDegree[next]--;
        if (inDegree[next] === 0) nextQueue.push(next);
      }
    }

    queue = nextQueue;
  }

  return taken === n ? semesters : -1;
}
```

```
  nextQueue=[2,3], queue=[2,3]

  Process course 2: taken=2

  Process course 3: taken=3
    adj[3]=[4]: inDegree[4]=0→nextQueue
  nextQueue=[4], queue=[4]

Semester 3: queue=[4], semesters=3, taken=3
  Process course 4: taken=4. No neighbors.

taken(4)===n(4) → return semesters=3 ✓
(Semester 1: {1}, Semester 2: {2,3} simultaneously, Semester 3: {4})
```

### Complexity
- Time: O(V + E) — same as standard Kahn's.
- Space: O(V + E).

### Edge Cases
- No relations (all courses independent): every course has in-degree 0, all are taken in semester 1 → return 1.
- Pure linear chain (each course requires the previous): n semesters needed — correctly computed as n rounds of exactly one course each.
- Cycle present: some courses never reach in-degree 0 and are never taken; `taken < n` → return -1.

### Follow-up Questions
- "What if there's a LIMIT of k courses per semester?" → Within each round, take only the best k available courses (by some criterion) and leave the rest for the next round — requires a priority-based selection within each BFS level, adding O(V log V) overhead for the heap-based selection.
- "Find the actual schedule (which courses in each semester), not just the count?" → Collect the `queue` contents at each round into a list of lists instead of just counting rounds.

## Problem 5 — Topological Sort via DFS (Full Implementation)

### Problem
Given a directed graph as an adjacency list, return a valid topological ordering of all its vertices, or an empty array if the graph contains a cycle.

```
Input:  numVertices=6, adj=[[2,3],[3,4],[5],[4],[],[]]
(edges: 0→2, 0→3, 1→3, 1→4, 2→5, 3→4)

Output: one valid topological order, e.g., [1, 0, 3, 2, 5, 4]
        (or [0, 1, 2, 3, 5, 4] or other valid orderings)
```

### Pattern Recognition
DFS-based topological sort — post-order vertex collection with stack reversal, using three-state coloring to detect cycles.

### Key Insight
A vertex can only be appended to the output (pushed to the stack) after ALL its reachable descendants have been fully explored — post-order placement guarantees every vertex appears after all vertices that depend on it having already been "confirmed safe" and placed in the stack first, so the final stack-reversed order has each vertex before all its dependents.

### Approach
Maintain a state array: UNVISITED (0), IN_STACK (1), DONE (2). For each unvisited vertex, launch a DFS; during DFS, mark entering as IN_STACK and exiting as DONE, pushing to the output stack at exit. If a neighbor is found IN_STACK during DFS, a cycle is detected. Final answer is the reversed stack.

### Solution

```js
function topologicalSortDFS(numVertices, adj) {
  const UNVISITED = 0, IN_STACK = 1, DONE = 2;
  const state = new Array(numVertices).fill(UNVISITED);
  const stack = [];
  let hasCycle = false;

  function dfs(u) {
    if (hasCycle) return;
    state[u] = IN_STACK;

    for (const v of adj[u]) {
      if (state[v] === IN_STACK) {
        hasCycle = true;
        return;
      }
      if (state[v] === UNVISITED) {
        dfs(v);
      }
    }

    state[u] = DONE;
    stack.push(u);
  }

  for (let i = 0; i < numVertices; i++) {
    if (state[i] === UNVISITED) dfs(i);
  }

  return hasCycle ? [] : stack.reverse();
}
```

### Complexity
- Time: O(V + E) — each vertex visited once, each edge traversed once.
- Space: O(V + E) — adjacency list, state array, recursion call stack (O(V) deep in worst case), output stack.

### Edge Cases
- Graph with a cycle (e.g., add edge 4→0): the DFS from 0 would reach 4 (UNVISITED → mark IN_STACK), then follow 4→0 and find 0 is IN_STACK → `hasCycle=true`, return `[]`.
- Disconnected graph (multiple components): the outer `for` loop launches DFS from every unvisited vertex, ensuring all components are covered regardless of connectivity.
- DAG where some vertices have no outgoing edges (sinks): these are the first to be pushed onto the stack (they finish immediately after being marked IN_STACK with no neighbors), correctly ending up at the "end" of the topological ordering (they have no dependents, so they belong last).

### Follow-up Questions
- "Convert this to an iterative DFS (avoid recursion depth concerns)?" → Maintain an explicit stack of `[vertex, neighborIndex]` pairs, advancing the neighbor index at each step and simulating the push-to-output at "pop/exhausted-neighbors" time — more code but avoids the O(V) recursion depth risk.
- "Why does the outer loop's starting order matter (or not matter) for correctness?" → The starting order doesn't affect correctness (any unvisited vertex can be the next DFS root, and the final reversed stack will still represent a valid topological order) but does affect which specific valid ordering is produced among all the possible valid ones.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve ordering tasks, courses, or operations with dependency constraints?
│
├── DOES A VALID ORDER EXIST? (cycle detection only, no need to output the order)
│   └── Run Kahn's algorithm, check if order.length === numVertices → O(V+E)
│
├── WHAT IS A VALID ORDER? (output the full topological ordering)
│   ├── PREFER ITERATIVE or need parallel-execution insight → Kahn's algorithm (BFS-based)
│   │   → naturally iterative, cycle detected by count check, queue = current "available" set
│   └── PREFER DFS or interviewer asks specifically for DFS → DFS post-order + stack reversal
│       → three-state coloring needed (UNVISITED/IN_STACK/DONE) for cycle detection
│
├── NEED THE LEXICOGRAPHICALLY SMALLEST VALID ORDER?
│   └── Kahn's with a MIN-HEAP instead of a plain queue → O((V+E) log V)
│
├── MINIMUM PARALLEL EXECUTION TIME (e.g., min semesters)?
│   └── Kahn's processed in ROUNDS (BFS-level-by-level) → round count = critical path length
│
├── ALL VALID TOPOLOGICAL ORDERINGS (enumerate, not just one)?
│   └── Kahn's-style BACKTRACKING — at each step try every available zero-in-degree vertex,
│       recurse, restore in-degrees → exponential O(V!) worst case, small graphs only
│
└── INFER ORDERING FROM SORTED EXAMPLES (alien dictionary, language inference)?
    └── Extract edges from adjacent-pair comparisons, then run standard topological sort
        on the inferred character/element graph
```

## Common Bugs Checklist

Before submitting any topological sort solution, verify:

1. **Edge direction built correctly from the problem's "A must come before B" semantics?** — A `[a, b]` prerequisite often means "b before a" (b is the prereq of a), so the directed edge is `b → a`, not `a → b`; getting this backward silently produces a reversed ordering that looks plausible but violates every dependency.

2. **Kahn's: cycle detection via `order.length === numVertices`, not via checking whether the queue is empty?** — The queue naturally empties at the end of both cyclic and acyclic graphs; only the final count comparison distinguishes the two cases correctly.

3. **DFS: three states (UNVISITED/IN_STACK/DONE), not just two (visited/not-visited)?** — A two-state DFS misses cycles entirely (it confuses a revisit of a previously fully-processed node with a genuine back edge), silently producing an incorrect topological ordering or failing to detect an existing cycle.

4. **DFS: vertex pushed to the output stack AFTER all neighbors are recursed into (post-order), not before (pre-order)?** — Pre-order placement produces an invalid ordering that violates the dependency direction for many graph shapes.

5. **DFS-based reversal applied at the END, not incrementally during traversal?** — The stack accumulates vertices in reverse topological order during DFS; reversing once at the end is what produces the correct final ordering.

6. **Alien dictionary / inferred-edge problems: BREAK after the first differing character per adjacent word pair, not continuing to extract more edges?** — Positions after the first difference give no ordering information (the first difference already fully determines which word comes first), and extracting "edges" from later positions can silently introduce false, incorrect ordering constraints.

7. **Alien dictionary: checking for the invalid prefix case (longer word appearing before its prefix in the sorted list)?** — Missing this check silently produces an incorrect (or non-empty) result when the input itself is a contradiction.

8. **Multi-component graphs in DFS: outer loop visits ALL unvisited vertices, not just vertex 0?** — Without iterating over all vertices as potential DFS roots, disconnected components (vertices unreachable from vertex 0) are silently omitted from the topological ordering.

**Final Tip:** At the 5 YOE level, interviewers expect immediate recognition that "ordering with dependencies" maps to topological sort, and fluent recall of both Kahn's and DFS approaches with their respective cycle-detection mechanisms — the count-check for Kahn's and the three-state coloring for DFS. The detail that most separates strong answers: proactively stating *why* only directed acyclic graphs admit a topological ordering, connecting the cycle-detection byproduct of each algorithm to this foundational reason. For Kahn's specifically, recognizing that the queue's contents at any point in time represent "tasks that can execute in parallel right now" is the insight that unlocks the minimum-semesters and critical-path extensions — presenting that connection unprompted is a meaningful signal of genuinely understanding the algorithm, not just having memorized its steps.
