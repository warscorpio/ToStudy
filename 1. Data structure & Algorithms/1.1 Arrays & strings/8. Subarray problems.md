## Topic A: Product of Array Except Self

### Section A1: Fundamentals

**Q1. What is the "product of array except self" problem, and why can't you just divide by the total product?**
A: Given an array `nums`, return an array `answer` where `answer[i]` equals the product of every element except `nums[i]`. The naive division approach (`totalProduct / nums[i]`) breaks in two ways: (1) division is often explicitly disallowed by the problem statement, and (2) it fails outright if any element is zero (division by zero), and produces wrong answers if there are two or more zeros (every `answer[i]` should be 0, but division can't distinguish "one zero" from "multiple zeros" cleanly). The standard solution avoids division entirely using prefix and suffix products.

```
Input:  nums = [1, 2, 3, 4]
Output: [24, 12, 8, 6]
```

**Q2. What is the prefix/suffix product approach?**
A: `answer[i]` = (product of everything to the left of `i`) × (product of everything to the right of `i`). Build a `left[i]` array where `left[i]` = product of `nums[0..i-1]`, and a `right[i]` array where `right[i]` = product of `nums[i+1..n-1]`. Then `answer[i] = left[i] * right[i]`.

```js
function productExceptSelf(nums) {
  const n = nums.length;
  const left = new Array(n), right = new Array(n), answer = new Array(n);

  left[0] = 1;
  for (let i = 1; i < n; i++) left[i] = left[i - 1] * nums[i - 1];

  right[n - 1] = 1;
  for (let i = n - 2; i >= 0; i--) right[i] = right[i + 1] * nums[i + 1];

  for (let i = 0; i < n; i++) answer[i] = left[i] * right[i];

  return answer;
}
```

This is the multiplicative analogue of the prefix-sum technique — instead of subtracting sums, you're excluding a single factor from a running product by combining a left-to-right pass with a right-to-left pass.

**Q3. How do you optimize the prefix/suffix approach to O(1) extra space (excluding the output array)?**
A: Compute the left products directly into the `answer` array on the first pass. On the second pass, fold in the right products using a single running variable instead of a full `right[]` array.

```js
function productExceptSelfOptimized(nums) {
  const n = nums.length;
  const answer = new Array(n);

  answer[0] = 1;
  for (let i = 1; i < n; i++) answer[i] = answer[i - 1] * nums[i - 1];

  let rightProduct = 1;
  for (let i = n - 1; i >= 0; i--) {
    answer[i] *= rightProduct;
    rightProduct *= nums[i];
  }

  return answer;
}
```

**Q4. What is the time and space complexity of the optimized approach?**
A: Time: O(n) — two linear passes. Space: O(1) extra (the output array itself doesn't count toward extra space per the problem's usual convention, since it's a required part of the return value).

**Q5. How does this approach handle zeros in the input array without any special-casing?**
A: The running product naturally propagates zeros: if `nums[k] = 0`, then every `left[i]` for `i > k` becomes 0 (since it includes `nums[k]` as a factor), and every `right[i]` for `i < k` becomes 0. So `answer[i]` for any `i ≠ k` correctly becomes 0 (it includes the zero factor from the other side), while `answer[k]` itself correctly excludes the zero and reflects the product of all non-zero-position elements. No explicit zero-counting or branching is needed — the arithmetic handles it automatically. If there are two or more zeros, every position's product is forced to 0 (each position's "except self" product still includes at least one of the other zeros), which the running-product approach also gets right without any special logic.

### Section A2: Advanced Patterns

**Q6. How would you extend "product except self" to "sum except self," "max except self," or "min except self"?**
A: The same two-pass left/right scaffold generalizes directly — replace multiplication with the target operation. Sum-except-self also has a division-free trick unique to sums (`totalSum - nums[i]`), but max/min genuinely require the two-pass approach since neither operation is invertible the way subtraction inverts addition.

```js
// max except self — no simple "inverse" trick exists, must use left/right passes
function maxExceptSelf(nums) {
  const n = nums.length;
  const leftMax = new Array(n), rightMax = new Array(n), answer = new Array(n);

  leftMax[0] = -Infinity;
  for (let i = 1; i < n; i++) leftMax[i] = Math.max(leftMax[i - 1], nums[i - 1]);

  rightMax[n - 1] = -Infinity;
  for (let i = n - 2; i >= 0; i--) rightMax[i] = Math.max(rightMax[i + 1], nums[i + 1]);

  for (let i = 0; i < n; i++) answer[i] = Math.max(leftMax[i], rightMax[i]);

  return answer;
}
```

**Q7. What is the relationship between "product except self" and prefix sums conceptually?**
A: Both are instances of the same general pattern: precompute a running aggregate from the left, a running aggregate from the right, and combine them at each index to answer an "exclude this position" or "range between these positions" query in O(1) per position after an O(n) build. Prefix sum uses subtraction to exclude a range; product-except-self uses two directional passes because division isn't safely usable (due to zeros) the way subtraction is for sums.

## Topic B: Trapping Rain Water

### Section B1: Fundamentals

**Q8. What is the "trapping rain water" problem?**
A: Given an array of non-negative integers representing an elevation map where each bar has width 1, compute how much water can be trapped after raining. Water at any position `i` is bounded above by the shorter of the tallest bar to its left and the tallest bar to its right — water "spills over" the shorter side otherwise.

```
Input:  height = [0,1,0,2,1,0,1,3,2,1,2,1]
Output: 6
```

**Q9. What is the key insight that determines how much water sits above each position?**
A: The water level at position `i` equals `min(maxLeft[i], maxRight[i]) - height[i]`, where `maxLeft[i]` is the tallest bar anywhere in `[0..i]` and `maxRight[i]` is the tallest bar anywhere in `[i..n-1]`. Water can only be trapped up to the height of the *shorter* boundary, since the taller boundary alone doesn't prevent overflow on the shorter side. If this value is negative or the bar itself is the tallest on one side, no water sits there (clamped to 0, though the formula naturally produces ≥0 for any valid `i` since `height[i] <= max(maxLeft[i], maxRight[i])` always holds — the constraint is on the *min* of the two, which can equal `height[i]` exactly when `i` is a local peak).

**Q10. What is the brute-force approach, and what's its complexity?**
A: For each position `i`, scan leftward to find `maxLeft[i]` and rightward to find `maxRight[i]`, then apply the formula. This is O(n) work per position, O(n²) overall — the inefficiency comes from recomputing the left/right maxima from scratch at every position instead of reusing previous computation.

**Q11. How does precomputing `maxLeft[]` and `maxRight[]` arrays improve this to O(n)?**
A: Build `maxLeft[i]` in a single left-to-right pass (`maxLeft[i] = max(maxLeft[i-1], height[i])`) and `maxRight[i]` in a single right-to-left pass, both O(n). Then a final O(n) pass applies the formula at every position using the precomputed arrays — O(n) time, O(n) space total.

```js
function trap(height) {
  const n = height.length;
  if (n === 0) return 0;

  const maxLeft = new Array(n), maxRight = new Array(n);

  maxLeft[0] = height[0];
  for (let i = 1; i < n; i++) maxLeft[i] = Math.max(maxLeft[i - 1], height[i]);

  maxRight[n - 1] = height[n - 1];
  for (let i = n - 2; i >= 0; i--) maxRight[i] = Math.max(maxRight[i + 1], height[i]);

  let water = 0;
  for (let i = 0; i < n; i++) {
    water += Math.min(maxLeft[i], maxRight[i]) - height[i];
  }

  return water;
}
```

**Q12. How does the two-pointer approach reduce trapping rain water to O(1) extra space?**
A: Maintain two pointers (`left`, `right`) starting at the array's ends, and two running maxima (`leftMax`, `rightMax`). At each step, advance whichever pointer points to the *smaller* current bar — this is safe because if `height[left] < height[right]`, then `leftMax` (which is ≤ the true max-left-so-far, since it's a running max computed only up to `left`) is guaranteed to be the binding (smaller) constraint at position `left`, regardless of what lies further right beyond the current `right` pointer — so the water above `left` can be finalized immediately without needing the exact `maxRight[left]` value.

```js
function trapTwoPointer(height) {
  let left = 0, right = height.length - 1;
  let leftMax = 0, rightMax = 0;
  let water = 0;

  while (left < right) {
    if (height[left] < height[right]) {
      leftMax = Math.max(leftMax, height[left]);
      water += leftMax - height[left];
      left++;
    } else {
      rightMax = Math.max(rightMax, height[right]);
      water += rightMax - height[right];
      right--;
    }
  }

  return water;
}
```

**Q13. Why is it safe to finalize the water above `left` using only `leftMax`, without knowing the exact `maxRight[left]`?**
A: Because `height[left] < height[right]` at the moment of the decision, and `rightMax >= height[right]` (it's a running max that includes at least the current `right` bar), we know `rightMax > height[left]`. Since `rightMax` is a lower bound on the true maximum to the right of `left` (there could be even taller bars further right that haven't been scanned yet, but `rightMax` only makes the true right-max *larger*, never smaller), we know the true `maxRight[left] >= rightMax > height[left] > ... `. Combined with `leftMax` being the exact true maximum to the left of `left` (since every bar from 0 to `left` has already been scanned), the binding constraint `min(maxLeft[left], maxRight[left])` is guaranteed to equal `leftMax`, because `maxRight[left]` is provably larger. This is the crux of why two-pointer works without ever computing the exact right-max array.

**Q14. What is the time and space complexity comparison across the three trapping rain water approaches?**
A:
- **Brute force**: O(n²) time, O(1) space.
- **Precomputed left/right max arrays**: O(n) time, O(n) space.
- **Two-pointer**: O(n) time, O(1) extra space — the optimal solution on both axes.

### Section B2: Advanced Patterns

**Q15. How does "trapping rain water" generalize to a 2D grid (trapping rain water II)?**
A: The 1D two-pointer insight (always process from the side with the smaller boundary) generalizes to a **min-heap (priority queue) + BFS-like boundary expansion** in 2D: start by pushing all border cells into a min-heap (their heights act as the initial "walls"), then repeatedly pop the shortest wall cell, examine its unvisited neighbors, compute trapped water as `max(0, currentWallHeight - neighborHeight)`, and push each neighbor into the heap with height `max(currentWallHeight, neighborHeight)` (the neighbor becomes part of the boundary going forward, and its effective wall height is at least as tall as the wall that let us reach it). This is conceptually the "always expand from the currently-shortest boundary" idea from the 1D two-pointer solution, generalized to work when "left" and "right" become "the entire surrounding boundary of a growing lake."

**Q16. How does "trapping rain water" relate to the "container with most water" problem — are they the same technique?**
A: They both use two pointers converging from the array's ends and both involve heights/elevations, but they solve different questions: trapping rain water sums up *all* the water trapped across *every* position between bars, while container-with-most-water finds the single *best pair* of two lines that, combined with the distance between them, maximizes one rectangular area. The two-pointer *movement rule* differs subtly too — container-with-most-water always moves the pointer at the *shorter* line (to search for a potentially taller replacement), reasoning about area trade-offs, whereas trapping rain water processes (finalizes) the pointer at the *shorter current max* boundary and accumulates trapped water incrementally. See Topic C for the full breakdown.

**Q17. What's a common bug when translating the precomputed-arrays version of trapping rain water into the two-pointer version?**
A: Forgetting that `leftMax`/`rightMax` in the two-pointer version are *initialized to 0*, not to `height[left]`/`height[right]` — the running max must include the current bar via `Math.max(leftMax, height[left])` *before* computing water at that position, not after; getting this order backward causes the first bar processed on each side to incorrectly compute negative or wrong water using a stale (zero) max instead of including itself.

## Topic C: Container With Most Water

### Section C1: Fundamentals

**Q18. What is the "container with most water" problem?**
A: Given an array `height` where `height[i]` represents a vertical line at position `i`, find two lines that, together with the x-axis, form a container that holds the maximum amount of water. The area is `min(height[i], height[j]) × (j - i)` — bounded by the shorter of the two lines (water spills over the shorter side) and the horizontal distance between them.

```
Input:  height = [1,8,6,2,5,4,8,3,7]
Output: 49   (lines at index 1 (height 8) and index 8 (height 7): min(8,7)*(8-1) = 7*7 = 49)
```

**Q19. What is the brute-force approach, and why is it insufficient?**
A: Check every pair `(i, j)` and compute the area, tracking the maximum — O(n²) time. This is correct but too slow for large inputs; the two-pointer approach achieves the same result in O(n).

**Q20. What is the two-pointer approach, and what is the key greedy insight that makes moving the shorter pointer safe?**
A: Start with `left = 0`, `right = n-1` (the widest possible container). At each step, compute the current area, then move whichever pointer points to the *shorter* line inward. The insight: keeping the shorter line fixed while moving the other pointer can never increase the area, because the shorter line remains the limiting factor (`min(...)`) regardless of which direction you'd move the other pointer, while the width can only shrink. So there is no benefit to ever moving the taller pointer while the shorter one stays put — the only way to potentially find a larger area is to replace the shorter line with a (hopefully taller) one, which requires moving the shorter pointer.

```js
function maxArea(height) {
  let left = 0, right = height.length - 1;
  let maxArea = 0;

  while (left < right) {
    const area = Math.min(height[left], height[right]) * (right - left);
    maxArea = Math.max(maxArea, area);

    if (height[left] < height[right]) {
      left++;
    } else {
      right--;
    }
  }

  return maxArea;
}
```

**Q21. Why is it safe to discard all pairs `(left, right-1), (left, right-2), ..., (left, left+1)` when moving the `right` pointer inward (assuming `height[right] <= height[left]`)?**
A: Every one of those discarded pairs has width strictly less than `(right - left)` and is still bounded above by `height[left]` at best (since `height[right]` is the current limiting factor and any bar between `left` and `right` that's ≤ `height[right]` would be an even worse limiting factor, while any bar taller than `height[right]` still can't exceed `height[left]` as the container's bound if `left` remains the pointer). Since width has strictly decreased and the height bound cannot improve beyond what's already been considered, none of those pairs can produce a larger area than what's already been computed or what remains reachable by continuing the two-pointer sweep. This exhaustive elimination argument is what guarantees two-pointer explores an implicit search space of all O(n²) pairs while only doing O(n) actual work.

**Q22. What is the time and space complexity of the two-pointer approach for container with most water?**
A: Time: O(n) — each pointer moves inward monotonically, and the pointers can collectively take at most n total steps before meeting. Space: O(1) — two pointers and a running maximum, no auxiliary array.

### Section C2: Advanced Patterns

**Q23. How does "container with most water" differ from "trapping rain water" in terms of what each pointer-movement decision represents?**
A: In container-with-most-water, moving the shorter pointer is a **search for a better single pair** — you're not accumulating anything at the position you move away from; you're simply discarding it as sub-optimal and looking for a replacement. In trapping rain water, moving the pointer at the smaller running-max boundary **finalizes and accumulates** the water trapped at that exact position before moving on — every position visited contributes to the final answer, rather than being discarded. This is the conceptual crux of why the two problems, despite superficially similar two-pointer-on-heights setups, require different mental models.

**Q24. Can container-with-most-water be solved with the same "precompute left-max/right-max" style approach used in trapping rain water?**
A: Not directly in a way that improves on two-pointer — trapping rain water needs `min(maxLeft[i], maxRight[i])` at *every* position because it sums contributions from every position, which naturally decomposes into two directional passes. Container-with-most-water only cares about the single *best pair*, and the "best pair" isn't decomposable into independent per-position contributions the same way — the two-pointer greedy elimination argument is the standard efficient technique here, not a precompute-and-scan approach.

### Section D: Cross-Topic Scenario / Interview-Style Questions

**Q25. "You're asked to compute product-except-self, but the interviewer then says 'what if the array can contain zero, or even multiple zeros?' How do you respond?"**
A: I'd point out that the prefix/suffix product approach handles this automatically without any special-casing — a zero at position `k` naturally zeroes out `left[i]` for all `i > k` and `right[i]` for all `i < k`, so `answer[i] = left[i] * right[i]` correctly becomes 0 for every position except possibly `k` itself, and multiple zeros correctly zero out every position including `k`. This is in contrast to the naive division approach (`totalProduct / nums[i]`), which breaks entirely on any zero and can't be patched without explicit zero-counting logic — a good opportunity to proactively contrast the two approaches' robustness.

**Q26. "A teammate implements trapping rain water using the brute-force O(n²) approach and says it's 'fine because interview problems are usually small.' How do you respond in a code review context?"**
A: I'd note that while O(n²) is correct and might pass small test cases, elevation maps in real applications (terrain analysis, flood simulation) can be very large, and the O(n) precomputed-array or O(1)-space two-pointer approaches aren't meaningfully more complex to implement — they just require recognizing the left-max/right-max insight. I'd suggest the two-pointer version specifically, since it achieves optimal time *and* space with a similar line count to the brute-force version once the core insight (process from the side with the smaller running max) is understood.

**Q27. "How would you explain, in one sentence each, the core trick behind product-except-self, trapping rain water, and container with most water, to distinguish them for someone who keeps mixing them up?"**
A: Product-except-self: combine a left-running product and a right-running product to exclude exactly one factor at each position. Trapping rain water: at each position, water is capped by the *shorter* of the tallest bar to the left and the tallest bar to the right, and two-pointer safely finalizes each position by always processing from the side whose running max is currently smaller. Container with most water: the area between any two lines is capped by the *shorter* line, so two-pointer greedily discards the shorter line at each step, searching for a taller replacement, because keeping it while narrowing the width could never help.

**Q28. "Can you combine ideas from these problems to solve a novel variant — e.g., 'maximum water trapped between exactly two selected bars, not summed across the whole array'?"**
A: That variant is actually just container-with-most-water restated — "maximum water between exactly two bars" is precisely `min(height[i], height[j]) × (j - i)` maximized over all pairs, which is the container problem's exact definition, not trapping rain water's (which sums contributions from *every interior position*, not just two chosen endpoints). Recognizing that a novel-sounding restatement maps onto an already-known pattern — rather than assuming it needs a new technique — is a valuable interview instinct.

## Problem 1 — Product of Array Except Self

### Problem
Given an integer array `nums`, return an array `answer` where `answer[i]` is the product of all elements of `nums` except `nums[i]`. Must run in O(n) time without using division.

```
Input:  nums = [1, 2, 3, 4]
Output: [24, 12, 8, 6]

Input:  nums = [-1, 1, 0, -3, 3]
Output: [0, 0, 9, 0, 0]
```

### Pattern Recognition
Exclude-one-position aggregate query across the whole array — the multiplicative analogue of prefix sums, solved with a left-product pass and a right-product pass.

### Key Insight
`answer[i]` = (product of everything strictly left of `i`) × (product of everything strictly right of `i`). Computing the left products directly into the output array, then folding in right products via a single running variable, achieves O(1) extra space.

### Approach
Pass 1 (left to right): `answer[i]` = product of `nums[0..i-1]`, with `answer[0] = 1` (nothing to the left). Pass 2 (right to left): multiply `answer[i]` by a running `rightProduct`, updating `rightProduct` after each step.

### Solution

```js
function productExceptSelf(nums) {
  const n = nums.length;
  const answer = new Array(n);

  answer[0] = 1;
  for (let i = 1; i < n; i++) {
    answer[i] = answer[i - 1] * nums[i - 1];
  }

  let rightProduct = 1;
  for (let i = n - 1; i >= 0; i--) {
    answer[i] *= rightProduct;
    rightProduct *= nums[i];
  }

  return answer;
}
```

### Dry Run

```
nums = [1, 2, 3, 4]

Pass 1 (left products):
answer[0] = 1
answer[1] = answer[0]*nums[0] = 1*1 = 1
answer[2] = answer[1]*nums[1] = 1*2 = 2
answer[3] = answer[2]*nums[2] = 2*3 = 6
answer = [1, 1, 2, 6]

Pass 2 (fold in right products, rightProduct starts at 1):
i=3: answer[3] *= 1 → 6;  rightProduct = 1*4 = 4
i=2: answer[2] *= 4 → 8;  rightProduct = 4*3 = 12
i=1: answer[1] *= 12 → 12; rightProduct = 12*2 = 24
i=0: answer[0] *= 24 → 24; rightProduct = 24*1 = 24

answer = [24, 12, 8, 6] ✓
```

### Complexity
- Time: O(n) — two linear passes.
- Space: O(1) extra (output array not counted).

### Edge Cases
- Single zero in the array: the position of the zero gets the product of all other elements; every other position gets 0.
- Two or more zeros: every position's answer becomes 0, handled automatically by the running products.
- Negative numbers: multiplication naturally handles sign — no special casing needed.
- Array of length 2: `answer = [nums[1], nums[0]]`, both passes correctly handle this minimal case.

### Follow-up Questions
- "What if division were allowed?" → `totalProduct / nums[i]`, but requires explicit handling for zero-count (0 zeros → divide normally; exactly 1 zero → only that position is nonzero; 2+ zeros → all positions are 0) — messier despite looking simpler at first glance.
- "Extend to a 2D matrix — product of matrix except the current row and column?" → Combine row-product and column-product prefix arrays; more involved but the same left/right-style aggregation principle applies per dimension.

## Problem 2 — Trapping Rain Water (Two-Pointer, O(1) Space)

### Problem
Given `n` non-negative integers representing an elevation map where the width of each bar is 1, compute how much water it can trap after raining.

```
Input:  height = [0,1,0,2,1,0,1,3,2,1,2,1]
Output: 6
```

### Pattern Recognition
Per-position trapped water bounded by `min(maxLeft, maxRight) - height[i]`, computed via a converging two-pointer sweep that always finalizes the side with the smaller running maximum.

### Key Insight
When `height[left] < height[right]`, the true maximum to the right of `left` is guaranteed to be at least `rightMax >= height[right] > height[left]`, so `leftMax` (the true, fully-known maximum to the left) is provably the binding constraint at position `left` — its water can be finalized immediately without ever computing the exact right-side maximum.

### Approach
Two pointers converge from both ends, tracking `leftMax` and `rightMax` running maxima. At each step, process (finalize) whichever side currently has the smaller running max, accumulate the trapped water there, and advance that pointer inward.

### Solution

```js
function trap(height) {
  let left = 0, right = height.length - 1;
  let leftMax = 0, rightMax = 0;
  let water = 0;

  while (left < right) {
    if (height[left] < height[right]) {
      leftMax = Math.max(leftMax, height[left]);
      water += leftMax - height[left];
      left++;
    } else {
      rightMax = Math.max(rightMax, height[right]);
      water += rightMax - height[right];
      right--;
    }
  }

  return water;
}
```

### Dry Run

```

left=0, right=11, leftMax=0, rightMax=0, water=0

height[0]=0 < height[11]=1 → leftMax=max(0,0)=0, water+=0-0=0 (water=0), left=1
height[1]=1 < height[11]=1? no (equal, goes to else) → rightMax=max(0,1)=1, water+=1-1=0 (water=0), right=10
height[1]=1 < height[10]=2 → leftMax=max(0,1)=1, water+=1-1=0 (water=0), left=2
height[2]=0 < height[10]=2 → leftMax=max(1,0)=1, water+=1-0=1 (water=1), left=3
height[3]=2 < height[10]=2? no → rightMax=max(1,2)=2, water+=2-2=0 (water=1), right=9
height[3]=2 < height[9]=1? no → rightMax=max(2,1)=2, water+=2-1=1 (water=2), right=8
height[3]=2 < height[8]=2? no → rightMax=max(2,2)=2, water+=2-2=0 (water=2), right=7
height[3]=2 < height[7]=3 → leftMax=max(1,2)=2, water+=2-2=0 (water=2), left=4

Answer: 6 ✓
```

### Complexity
- Time: O(n) — each pointer moves inward monotonically, total steps bounded by n.
- Space: O(1) — running maxima and pointers only.

### Edge Cases
- Strictly increasing or strictly decreasing elevation: no water can be trapped (one side always has no taller bound) — the algorithm correctly accumulates 0 throughout.
- All bars the same height: `leftMax`/`rightMax` immediately equal every bar's height, so `water += leftMax - height[...] = 0` at every step — correctly 0.
- Empty array or single bar: loop condition `left < right` is false immediately (or the array has fewer than 2 elements to begin with) — correctly returns 0, since at least 2 bars are needed to trap any water.
- Very tall single spike in the middle with low bars on both sides: the spike itself never gets "processed" as a low point contributing water (it would only ever be the taller boundary), correctly contributing 0 to the sum at its own position.

### Follow-up Questions
- "Show the precomputed-array version instead?" → See Q11 — O(n) time, O(n) space using explicit `maxLeft[]`/`maxRight[]` arrays; useful to present as a stepping stone toward the two-pointer optimization.
- "Extend to a 2D grid?" → See Q15 — min-heap + boundary expansion (BFS-like), a materially different technique from the 1D two-pointer sweep.

## Problem 3 — Trapping Rain Water (Precomputed Left/Right Max Arrays)

### Problem
Same as Problem 2, but the interviewer specifically asks for the precomputed-array approach first, as a stepping stone before optimizing to two-pointer.

```
Input:  height = [4,2,0,3,2,5]
Output: 9
```

### Pattern Recognition
Direct application of the `min(maxLeft[i], maxRight[i]) - height[i]` formula at every position, using two full auxiliary arrays built via forward and backward passes.

### Key Insight
Rather than recomputing the left/right maximum from scratch for every position (which would be O(n) work per position, O(n²) total), a single forward pass and a single backward pass compute all `maxLeft[i]` and `maxRight[i]` values in O(n) total, after which a final pass applies the formula in O(1) per position.

### Approach
Build `maxLeft[]` left to right, `maxRight[]` right to left, then sum `min(maxLeft[i], maxRight[i]) - height[i]` across all positions.

### Solution

```js
function trapPrecomputed(height) {
  const n = height.length;
  if (n === 0) return 0;

  const maxLeft = new Array(n), maxRight = new Array(n);

  maxLeft[0] = height[0];
  for (let i = 1; i < n; i++) {
    maxLeft[i] = Math.max(maxLeft[i - 1], height[i]);
  }

  maxRight[n - 1] = height[n - 1];
  for (let i = n - 2; i >= 0; i--) {
    maxRight[i] = Math.max(maxRight[i + 1], height[i]);
  }

  let water = 0;
  for (let i = 0; i < n; i++) {
    water += Math.min(maxLeft[i], maxRight[i]) - height[i];
  }

  return water;
}
```

### Complexity
- Time: O(n) — three linear passes (build maxLeft, build maxRight, sum).
- Space: O(n) — two full auxiliary arrays.

### Edge Cases
- Same as Problem 2's edge cases — the formula and its correctness are identical; only the implementation strategy (precompute vs. two-pointer) differs.

### Follow-up Questions
- "Can you reduce the space to O(1)?" → Yes — see Problem 2's two-pointer approach, which eliminates the need for explicit `maxLeft[]`/`maxRight[]` arrays entirely.
- "Which version would you actually write first in an interview?" → Presenting the precomputed-array version first (simpler to reason about and verify) and then optimizing to two-pointer once correctness is established is often a stronger interview narrative than jumping straight to the more clever two-pointer version, since it demonstrates the reasoning progression.

## Problem 4 — Container With Most Water

### Problem
Given `n` non-negative integers `height` where each represents a point at coordinate `(i, height[i])`, find two lines that together with the x-axis form a container that holds the most water. Return the maximum area.

```
Input:  height = [1,8,6,2,5,4,8,3,7]
Output: 49
```

### Pattern Recognition
Maximize `min(height[i], height[j]) × (j - i)` over all pairs — two-pointer greedy elimination, always discarding the shorter boundary in search of a taller replacement.

### Key Insight
With the shorter line fixed as one boundary, moving the *other* pointer inward can never help (width shrinks, height bound can't improve past the shorter line), so the only productive move is to advance the pointer at the currently shorter line, searching for a potentially taller replacement.

### Approach
Two pointers start at the widest possible span (`0` and `n-1`). At each step, compute the current area, update the running max, then move the pointer at the shorter line inward.

### Solution

```js
function maxArea(height) {
  let left = 0, right = height.length - 1;
  let best = 0;

  while (left < right) {
    const width = right - left;
    const boundedHeight = Math.min(height[left], height[right]);
    best = Math.max(best, width * boundedHeight);

    if (height[left] < height[right]) {
      left++;
    } else {
      right--;
    }
  }

  return best;
}
```

### Dry Run

```

  height[1]=8 < height[8]=7? no → right=7

  height[1]=8 < height[7]=3? no → right=6

  height[1]=8 < height[6]=8? no (equal→else) → right=5

  height[1]=8 < height[5]=4? no → right=4

```

### Complexity
- Time: O(n) — pointers move inward monotonically, total steps bounded by n.
- Space: O(1) — two pointers and a running max.

### Edge Cases
- Strictly increasing or strictly decreasing heights: the widest pair (`0`, `n-1`) is often — though not always — close to optimal, but the algorithm still correctly explores all necessary pairs via the elimination argument rather than assuming this.
- All bars the same height: every pair's area is determined purely by width, so the algorithm correctly finds the widest pair (`0`, `n-1`) as optimal, since bounded height never changes.
- Two bars only (`n=2`): loop runs exactly once, computing the only possible area — correctly returned.
- One very tall bar and one very short bar far apart vs. two medium bars close together: the two-pointer sweep correctly compares both scenarios as it progresses, since it doesn't stop after finding the widest pair's area — it continues checking successively narrower pairs.

### Follow-up Questions
- "Why does moving the taller pointer never help?" → See Q21's elimination argument — width strictly decreases while the height bound can't improve past the (unmoved) shorter line, so every pair reachable that way is provably no better than what's already been considered.
- "How does this differ from trapping rain water, since both use two pointers on heights?" → See Q23 — container-with-most-water discards the shorter line each step (searching for one best pair), while trapping rain water finalizes and accumulates water at the smaller-running-max side (summing contributions from every position).

## Quick Reference — Pattern Decision Tree

```
Does the problem involve an aggregate (product/max/water) computed relative to EVERY position, or a SINGLE BEST PAIR across an array?
│
├── EXCLUDE-SELF AGGREGATE AT EVERY POSITION (product, sum, max, min except self)?
│   └── Left-pass + Right-pass combination → O(n) time, O(1) extra space
│       (division-based shortcut only safe for SUM, and even then only without float/edge concerns;
│        PRODUCT needs the two-pass approach specifically to handle zeros correctly)
│
├── WATER TRAPPED ACROSS THE WHOLE ELEVATION MAP (sum of per-position trapped water)?
│   ├── O(n) space acceptable / want simplest correctness → Precomputed maxLeft[]/maxRight[] arrays
│   └── O(1) space required → Two-pointer, finalize the side with the smaller running max
│
├── WATER TRAPPED IN A 2D GRID (not a 1D elevation array)?
│   └── Min-heap + boundary expansion (BFS-like growing lake) — generalizes the two-pointer insight
│
├── SINGLE BEST PAIR OF LINES MAXIMIZING area = min(h[i],h[j]) × (j-i)?
│   └── Two-pointer, always discard the SHORTER line, search for a taller replacement → O(n)
│
└── MAXIMUM CONTIGUOUS SUM (not a pair, not exclude-self) — different problem entirely
    └── Kadane's Algorithm (see the dedicated Kadane's guide)
```

## Common Bugs Checklist

Before submitting any product-except-self, trapping-rain-water, or container-with-most-water solution, verify:

1. **Product except self: seeded with 1, not 0?** — `answer[0] = 1` and `rightProduct = 1` are the multiplicative identity, analogous to a prefix sum's `pre[0] = 0`. Seeding with 0 would zero out every product immediately.

2. **Product except self: right-product fold-in happens in the correct order?** — Must multiply `answer[i] *= rightProduct` *before* updating `rightProduct *= nums[i]` for that same index — reversing the order includes `nums[i]` in its own "except self" product, which is wrong.

3. **Trapping rain water: `leftMax`/`rightMax` include the current bar before computing water?** — `leftMax = Math.max(leftMax, height[left])` must happen *before* `water += leftMax - height[left]`, not after — otherwise the first bar processed on a side uses a stale (too-small) max.

4. **Trapping rain water: two-pointer movement condition uses strict `<`, and the else-branch correctly handles equal heights?** — When `height[left] === height[right]`, the implementation shown routes to the `else` (right-side) branch — this is a valid, safe choice, but should be a deliberate one, not an accidental fallthrough.

5. **Container with most water: moving the correct (shorter) pointer?** — Must move the pointer at the *smaller* of `height[left]`/`height[right]`, since keeping the shorter line fixed while moving the taller one can never improve the area — moving the wrong pointer silently produces an incorrect (too-small) maximum.

6. **Container with most water: recomputing width and height correctly at each step, not reusing stale values?** — `width = right - left` and `boundedHeight = min(height[left], height[right])` must be recomputed fresh every iteration after any pointer moves — easy to accidentally cache and forget to update in a hastily-written loop.

7. **All three problems: correct behavior on arrays too small to have a meaningful answer?** — Product-except-self needs at least 1 element (edge case: single-element array's "except self" product is conventionally 1, the empty product); trapping rain water and container-with-most-water both need at least 2 elements to produce any nonzero result, and should return 0 gracefully otherwise, not crash on an out-of-bounds access.

---

**Final Tip:** At the 5 YOE level, interviewers expect you to recognize that "product except self," "trapping rain water," and "container with most water" all superficially involve arrays of numbers and directional passes or pointers — but the underlying invariant differs in each case: exclude-one-factor aggregation (product-except-self), per-position bounded-by-the-shorter-side accumulation (trapping rain water), and single-best-pair greedy elimination (container with most water). State which of these three invariants applies *before* writing code, and be ready to explain — in one sentence — why the two-pointer movement rule you're using is provably safe (nothing better is being discarded). That justification is the single strongest signal separating genuine understanding from memorized code in this problem family.
