## Topic A: Anagram Detection

### Section A1: Fundamentals

**Q1. What is an anagram, and what does "anagram detection" mean algorithmically?**
A: Two strings are anagrams if one can be rearranged into the other — they contain exactly the same characters with exactly the same frequencies, just in a different order. Algorithmically, anagram detection reduces to comparing the **character frequency multiset** of two strings, not their character order.

```
"listen" and "silent" → anagrams (same letters: e,i,l,n,s,t)
"rat" and "car"       → not anagrams (different letters)
```

**Q2. What are the two standard approaches to checking if two strings are anagrams?**
A:
1. **Sort and compare**: sort both strings' characters and check if the sorted results are equal. O(n log n) time, O(n) space (for the sorted copies).
2. **Frequency count and compare**: build a character-count map (or fixed-size array for a known alphabet) for both strings and compare counts. O(n) time, O(k) space where k is the alphabet size (often treated as O(1) for a fixed alphabet like lowercase English letters).

```js
// Approach 1: sort and compare
function isAnagramSort(s, t) {
  if (s.length !== t.length) return false;
  return s.split('').sort().join('') === t.split('').sort().join('');
}

// Approach 2: frequency count (single array, since only s needs incrementing
// and t needs decrementing — net zero means anagram)
function isAnagramCount(s, t) {
  if (s.length !== t.length) return false;
  const counts = new Array(26).fill(0);

  for (let i = 0; i < s.length; i++) {
    counts[s.charCodeAt(i) - 97]++;
    counts[t.charCodeAt(i) - 97]--;
  }

  return counts.every(c => c === 0);
}
```

**Q3. Why is the length check (`s.length !== t.length`) essential before doing any comparison work?**
A: Anagrams must have identical length by definition (they're rearrangements of the same multiset of characters). Checking length first is an O(1) short-circuit that avoids unnecessary O(n) or O(n log n) work on strings that can never be anagrams — a cheap, easy-to-forget optimization that's also a correctness safeguard (without it, a naive frequency-diff approach on unequal-length strings could still coincidentally sum to zero on overlapping characters and produce a false positive if not guarded).

**Q4. When should you use a fixed-size array (e.g., size 26) vs. a hash map for character counting?**
A: Use a fixed-size array when the alphabet is small and known in advance (e.g., lowercase English letters, digits) — array indexing is O(1) with a very small constant factor and no hashing overhead. Use a hash map when the character set is unknown, large, or includes Unicode/multi-byte characters (emoji, accented characters, CJK text) — a fixed array sized for ASCII would either overflow, waste space, or silently mishandle characters outside its assumed range.

```js
function isAnagramUnicode(s, t) {
  if (s.length !== t.length) return false;
  const counts = new Map();

  for (const ch of s) counts.set(ch, (counts.get(ch) || 0) + 1);
  for (const ch of t) {
    if (!counts.has(ch)) return false;
    counts.set(ch, counts.get(ch) - 1);
    if (counts.get(ch) === 0) counts.delete(ch);
  }

  return counts.size === 0;
}
```

**Q5. What is the time and space complexity of each anagram-detection approach?**
A:
- **Sort and compare**: O(n log n) time, O(n) space (for the sorted string copies; some languages allow in-place sorting of mutable char arrays, reducing this).
- **Frequency count**: O(n) time, O(k) space where k is the distinct character count (O(1) for a fixed small alphabet, O(min(n, alphabet size)) in general).
- Frequency counting is asymptotically better and is the preferred interview answer when the alphabet is bounded; sorting is simpler to state and sometimes preferred for its brevity when performance isn't the focus.

**Q6. How do you group a list of strings into anagram groups efficiently (not just check a single pair)?**
A: Use each string's **canonical form** (sorted characters, or a frequency-count signature) as a hash map key, and bucket all strings sharing that key together. This generalizes pairwise anagram detection to grouping in a single pass.

```js
function groupAnagrams(strs) {
  const groups = new Map();

  for (const s of strs) {
    const key = s.split('').sort().join(''); // canonical form
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(s);
  }

  return Array.from(groups.values());
}
```

Time: O(n × k log k) where n is the number of strings and k is the max string length (sorting dominates per string). Using a frequency-count tuple as the key instead of a sorted string reduces this to O(n × k).

### Section A2: Advanced Patterns

**Q7. What is the "anagram substring search" problem, and how does it extend frequency counting?**
A: Given a string `s` and a pattern `p`, find all starting indices in `s` where a substring is an anagram of `p`. This combines frequency counting with a **sliding window** of fixed size `p.length`: maintain a running character-count difference between the current window and `p`, sliding one character at a time (removing the character leaving the window, adding the one entering), checking for a zero-difference match at each position.

```js
function findAnagrams(s, p) {
  const result = [];
  if (s.length < p.length) return result;

  const need = new Array(26).fill(0);
  const window = new Array(26).fill(0);
  for (const ch of p) need[ch.charCodeAt(0) - 97]++;

  for (let i = 0; i < s.length; i++) {
    window[s.charCodeAt(i) - 97]++;

    if (i >= p.length) {
      window[s.charCodeAt(i - p.length) - 97]--; // slide window: remove leftmost
    }

    if (i >= p.length - 1 && window.every((c, idx) => c === need[idx])) {
      result.push(i - p.length + 1);
    }
  }

  return result;
}
```

Time: O(n × 26) if comparing full count arrays each time (effectively O(n) since 26 is constant), or O(n) with a running "matches" counter instead of a full array comparison per position — the optimized version avoids the O(26) comparison at every index.

**Q8. Why is checking `window.every(...)` at every window position considered a minor inefficiency, and how do you optimize it?**
A: Comparing two 26-length arrays at every single window position adds a constant-factor O(26) cost per index, which — while still technically O(n) overall since 26 is a fixed constant — is wasteful in practice. The optimization tracks a single integer `matches` counter: increment it when a character's count in `window` first reaches its `need` count, decrement it when it moves away from matching. A full window match is then just `matches === 26` (or the count of distinct characters in `p`), checked in O(1) instead of O(26) per position.

**Q9. How does anagram detection connect to the "valid anagram with character deletions allowed" variant?**
A: If up to `k` character deletions/substitutions are allowed to make two strings anagrams of each other, the frequency-count-difference approach still applies, but instead of requiring all counts to net to zero, you sum the *absolute differences* between the two frequency profiles and check whether that sum is within the allowed budget (specific budget semantics depend on whether deletions, substitutions, or both are allowed).

## Topic B: String Compression

### Section B1: Fundamentals

**Q10. What is string compression, and what is the classic "run-length encoding" (RLE) approach?**
A: String compression reduces a string's representation by replacing consecutive repeated characters ("runs") with the character followed by its run length. Run-Length Encoding (RLE) is the canonical technique for this — it's most effective on strings with long runs of repeated characters and can *expand* strings with no repetition, which is why implementations typically return the original string if compression doesn't actually shrink it.

```
Input:  "aaabbbccd"
Output: "a3b3c2d1"  (or "a3b3c2d" if single-count runs omit the "1")
```

**Q11. What is the standard single-pass algorithm for run-length encoding?**
A: Walk the string with a pointer, and for each new character, count how many consecutive identical characters follow it (including itself), append `character + count` to the result, then jump the pointer past the entire run.

```js
function compress(s) {
  let result = '';
  let i = 0;

  while (i < s.length) {
    const ch = s[i];
    let count = 0;

    while (i < s.length && s[i] === ch) {
      count++;
      i++;
    }

    result += ch + count;
  }

  return result.length < s.length ? result : s; // only compress if it actually shrinks
}
```

**Q12. What is the time and space complexity of run-length encoding?**
A:
- **Time**: O(n) — each character is visited exactly once across the outer and inner loop combined (the inner `while` loop never re-visits a character the outer loop already consumed).
- **Space**: O(n) in the worst case for the output string (e.g., a string with no repeated characters at all produces an output roughly 2x the input length before the "return original if longer" check kicks in).

**Q13. Why must implementations check whether the compressed result is actually shorter before returning it?**
A: RLE is a heuristic, not a guaranteed compression — a string with no repeated adjacent characters (e.g., `"abcdef"`) produces a *longer* encoded string (`"a1b1c1d1e1f1"`), since every character needs its count appended. Returning the compressed form unconditionally could make output larger than input, defeating the purpose of "compression." The standard fix is comparing lengths and returning whichever is shorter (typically the original if compression doesn't help).

**Q14. How do you implement string compression in-place (modifying a character array directly, not building a new string), which is a common interview variant?**
A: Use two pointers: a `write` pointer for where the next compressed character/count goes, and a `read` pointer that scans through runs. Because compressed output is always the same length or shorter for runs of length ≥ 2 (and equal length for runs of length 1... actually for single characters, writing "a1" is longer than "a" — so the true in-place LeetCode variant specifically omits the "1" for single-character runs to guarantee the write pointer never overtakes the read pointer within a run):

```js
function compressInPlace(chars) {
  let write = 0, read = 0;

  while (read < chars.length) {
    const ch = chars[read];
    let count = 0;

    while (read < chars.length && chars[read] === ch) {
      count++;
      read++;
    }

    chars[write++] = ch;

    if (count > 1) {
      for (const digit of String(count)) {
        chars[write++] = digit;
      }
    }
    // count === 1: omit the digit entirely (this is what keeps write <= read)
  }

  return write; // new logical length of the array
}
```

**Q15. Why does omitting the digit for single-character runs matter for the in-place variant specifically?**
A: The in-place approach relies on `write` never overtaking `read` while overwriting the array as it goes. A run of length 1 writes only the character itself (1 output element for 1 input element consumed) — a wash. A run of length ≥ 2 always writes strictly fewer output elements than input elements consumed (e.g., "aaaa" → "a4": 2 output chars for 4 input chars). If single-character runs also wrote a trailing "1", the compressed output could — in the worst case of alternating single characters — become as long as or longer than the remaining unread input, risking `write` catching up to or passing `read` and corrupting unread data.

### Section B2: Advanced Patterns

**Q16. What is "string compression with a length limit" (e.g., counts capped at 9, requiring multi-digit splitting), and how does it change the approach?**
A: Some compression variants (especially LeetCode's in-place version) require splitting counts into individual digit characters if the count is a multi-digit number (e.g., a run of 12 identical characters becomes `"a12"`, written as three separate characters `'a'`, `'1'`, `'2'`). The core run-detection logic is unchanged — only the digit-writing step needs to iterate over each digit of the count rather than assuming a single-digit count.

**Q17. How does string compression relate to more general compression algorithms (Huffman coding, LZ77/LZ78)?**
A: RLE is the simplest possible compression scheme, effective only for data with long runs of repeated symbols (it's used in practice for things like fax transmission and simple image formats with large uniform color areas). General-purpose compressors like Huffman coding exploit *frequency skew* (assigning shorter codes to more frequent symbols) rather than run length, and LZ77/LZ78-family algorithms (used in gzip, PNG) exploit *repeated substrings* anywhere in the data, not just adjacent repeats. RLE is a useful building block and a common interview warm-up, but it's not competitive with these general algorithms on typical text or binary data.

**Q18. What is the "decompress a run-length encoded string" problem, and what's the approach?**
A: The inverse operation: given a string like `"a3b2c1"` (or `"3[a]2[b]"` style nested-bracket encodings), reconstruct the original expanded string. For simple flat RLE, parse alternating character/number tokens and repeat each character by its count using string repetition. For nested bracket encodings (e.g., LeetCode's "Decode String": `"3[a2[c]]"` → `"accaccacc"`), a stack-based approach is needed to handle nesting — pushing the current string and repeat count onto a stack when encountering `[`, and popping/repeating when encountering `]`.

## Topic C: Palindrome Checks

### Section C1: Fundamentals

**Q19. What is a palindrome, and what is the standard two-pointer approach to check one?**
A: A palindrome reads identically forwards and backwards. The standard check uses two pointers starting at opposite ends of the string, moving toward the center, comparing characters at each step — if any pair mismatches, it's not a palindrome; if the pointers meet or cross without a mismatch, it is.

```js
function isPalindrome(s) {
  let left = 0, right = s.length - 1;

  while (left < right) {
    if (s[left] !== s[right]) return false;
    left++;
    right--;
  }

  return true;
}
```

Time: O(n). Space: O(1) — no extra string is built, just two index pointers.

**Q20. Why is the two-pointer approach preferred over reversing the string and comparing?**
A: Reversing the string (`s === s.split('').reverse().join('')`) is O(n) time but also O(n) *extra* space to build the reversed copy, and it always processes the *entire* string even if a mismatch occurs at the very first character pair. The two-pointer approach is O(1) space and can **short-circuit** — it returns `false` immediately on the first mismatch, without needing to build any reversed copy or scan the rest of the string.

**Q21. How do you handle "valid palindrome" problems that require ignoring non-alphanumeric characters and case?**
A: Preprocess the comparison logic (not necessarily the string itself) to skip non-alphanumeric characters and normalize case as the two pointers move, rather than building a separate cleaned string first (which would be simpler but costs extra space).

```js
function isPalindromeAlphanumeric(s) {
  let left = 0, right = s.length - 1;
  const isAlnum = (ch) => /[a-z0-9]/i.test(ch);

  while (left < right) {
    while (left < right && !isAlnum(s[left])) left++;
    while (left < right && !isAlnum(s[right])) right--;

    if (s[left].toLowerCase() !== s[right].toLowerCase()) return false;

    left++;
    right--;
  }

  return true;
}
```

Time: O(n) — each pointer still only traverses its half of the string once, even with the inner skip-loops (their combined iterations across the whole function are bounded by n). Space: O(1).

**Q22. What is the time and space complexity of palindrome checking, and can it go below O(n) time?**
A: O(n) time is a hard lower bound for verifying an *arbitrary* string is a palindrome, since in the worst case (a true palindrome, or a near-palindrome that mismatches only at the very center) every character must be examined to confirm no mismatch exists. O(1) extra space is achievable and standard via the two-pointer approach — no algorithm can do better than O(n) time in the general case, since skipping any character risks missing a mismatch.

### Section C2: Advanced Patterns

**Q23. What is the "longest palindromic substring" problem, and what is the standard "expand around center" approach?**
A: Find the longest substring within a string that is itself a palindrome. The "expand around center" technique treats every index (and every gap between two indices, to handle even-length palindromes) as a potential center, expanding outward while characters match, tracking the longest match found.

```js
function longestPalindrome(s) {
  let start = 0, maxLen = 0;

  function expand(left, right) {
    while (left >= 0 && right < s.length && s[left] === s[right]) {
      left--;
      right++;
    }
    return right - left - 1; // length of the palindrome found
  }

  for (let i = 0; i < s.length; i++) {
    const len1 = expand(i, i);       // odd-length palindromes, center at i
    const len2 = expand(i, i + 1);   // even-length palindromes, center between i, i+1
    const len = Math.max(len1, len2);

    if (len > maxLen) {
      maxLen = len;
      start = i - Math.floor((len - 1) / 2);
    }
  }

  return s.substring(start, start + maxLen);
}
```

Time: O(n²) — n possible centers, each expansion can take up to O(n) in the worst case (e.g., a string of all identical characters). Space: O(1) extra (excluding the output substring).

**Q24. How does Manacher's algorithm improve on "expand around center" for longest palindromic substring?**
A: Manacher's algorithm achieves O(n) time by reusing previously computed palindrome-length information — when expanding around a new center that falls within a previously found palindrome's span, it can infer a lower bound on that center's palindrome length from its "mirror" position (already computed) instead of re-expanding from scratch, only expanding further when necessary. It's a significant complexity improvement but is rarely expected to be implemented from memory in a standard interview — "expand around center" at O(n²) is usually the accepted answer, with Manacher's mentioned as the theoretically optimal follow-up.

**Q25. What is the "palindromic substring count" problem, and how does it relate to "longest palindromic substring"?**
A: Instead of finding the single longest palindromic substring, count *how many* palindromic substrings exist in total (including overlapping and single-character ones, which are always trivially palindromic). The same "expand around center" technique applies — instead of tracking the max length found, increment a counter every time an expansion step finds a valid (matching) palindrome, since every successful expansion step corresponds to one more valid palindromic substring.

```js
function countSubstrings(s) {
  let count = 0;

  function expand(left, right) {
    while (left >= 0 && right < s.length && s[left] === s[right]) {
      count++;
      left--;
      right++;
    }
  }

  for (let i = 0; i < s.length; i++) {
    expand(i, i);       // odd-length centers
    expand(i, i + 1);   // even-length centers
  }

  return count;
}
```

**Q26. What is "valid palindrome II" (allowing at most one character deletion), and how does two-pointer adapt?**
A: Given a string, determine if it can become a palindrome by deleting **at most one** character. Run the standard two-pointer check; on the *first* mismatch, branch into two possibilities — skip the left character or skip the right character — and check if either resulting substring is a palindrome using the standard (no-deletion-allowed) check. If either branch succeeds, the answer is true.

```js
function validPalindromeOneDelete(s) {
  function isPalin(l, r) {
    while (l < r) {
      if (s[l] !== s[r]) return false;
      l++; r--;
    }
    return true;
  }

  let left = 0, right = s.length - 1;
  while (left < right) {
    if (s[left] !== s[right]) {
      return isPalin(left + 1, right) || isPalin(left, right - 1);
    }
    left++;
    right--;
  }
  return true;
}
```

Time: O(n) — the initial scan is O(n), and at most one branch-check (also O(n)) is triggered, since a true palindrome never triggers branching and a non-palindrome-fixable-by-one-deletion triggers exactly one branching event.

**Q27. How do palindrome checks apply to linked lists, where two-pointer index access isn't directly available?**
A: Since a singly linked list doesn't support O(1) random/reverse access, the standard approach is: (1) use slow/fast pointers to find the middle of the list in one pass, (2) reverse the second half of the list in-place, (3) compare the first half and reversed second half node-by-node with two pointers, and (4) optionally reverse the second half back to restore the original list structure. This achieves O(n) time and O(1) extra space, mirroring the array two-pointer technique despite the list's lack of direct indexing.

### Section D: Cross-Topic Scenario / Interview-Style Questions

**Q28. "Given two strings, determine if one is an anagram of the other, but the strings may contain Unicode characters (not just lowercase English letters). What changes in your approach?"**
A: Switch from a fixed-size array (sized for a known small alphabet like 26 lowercase letters) to a hash map keyed by character, since Unicode text has a far larger and less predictable character set. The core logic — increment counts for one string, decrement for the other, check all counts return to zero — is unchanged; only the counting structure changes. Also worth noting: some Unicode characters are represented by multiple UTF-16 code units (surrogate pairs, e.g., certain emoji), so iterating with `for...of` (which iterates by code point) rather than indexed access is safer than naive character-by-character indexing.

**Q29. "You need to compress a very long string (e.g., a DNA sequence with only 4 possible characters) and are told the compressed form must always be no longer than the original. How do you guarantee this?"**
A: Run standard run-length encoding, but explicitly compare the compressed length to the original length before returning, falling back to the original string (or a trivial "no compression" marker) if RLE would produce a longer result. This guarantees the output is never larger than the input, at the cost of sometimes not compressing at all — a required trade-off since RLE cannot guarantee compression on all inputs (e.g., a string with no repeated adjacent characters).

**Q30. "A teammate suggests checking if a string is a palindrome by comparing it to its reverse using string reversal and equality check (`s === reverse(s)`). What's the trade-off versus two-pointer, and would you push back in a code review?"**
A: Both are O(n) time, but string reversal requires O(n) extra space to build the reversed copy, while two-pointer is O(1) space. Two-pointer also short-circuits on the first mismatch, potentially avoiding a full scan, whereas the reversal approach always does the full reversal work regardless of where a mismatch would occur. In a code review, I'd flag this as a minor but real inefficiency — for a single palindrome check on a small string it's harmless, but if this runs in a hot path or on large strings (e.g., repeated calls in a loop, or DNA/text sequences), the extra allocation and lack of short-circuiting add up. I'd suggest the two-pointer version as the more idiomatic and efficient standard.

**Q31. "How would you check if a string can be rearranged into a palindrome (not whether it already is one)?"**
A: A string can be rearranged into a palindrome if and only if **at most one character has an odd frequency count** (that character, if it exists, sits in the middle; every other character must pair up symmetrically around it). Build a frequency count (array or hash map, same technique as anagram detection), then count how many characters have an odd count — the string is palindrome-rearrangeable if that count is ≤ 1. This is a direct application of the anagram-detection frequency-counting technique repurposed for a palindrome-feasibility check, showing how these three topics (anagram, compression-adjacent counting, palindrome) share the same frequency-analysis foundation.

```js
function canFormPalindrome(s) {
  const counts = new Map();
  for (const ch of s) counts.set(ch, (counts.get(ch) || 0) + 1);

  let oddCount = 0;
  for (const c of counts.values()) {
    if (c % 2 !== 0) oddCount++;
  }

  return oddCount <= 1;
}
```

## Problem 1 — Valid Anagram

### Problem
Given two strings `s` and `t`, return `true` if `t` is an anagram of `s`, and `false` otherwise.

```
Input:  s = "anagram", t = "nagaram"
Output: true

Input:  s = "rat", t = "car"
Output: false
```

### Pattern Recognition
Classic character-frequency comparison — exactly the fundamental anagram-detection pattern.

### Key Insight
Two strings are anagrams if and only if every character appears the same number of times in both. Incrementing counts for `s` and decrementing for `t` in a single pass means all counts should net to exactly zero if and only if the strings are anagrams.

### Approach
Length-check first as an O(1) short circuit. Then use a fixed-size 26-element array (assuming lowercase English letters) to track the net frequency difference in a single combined pass.

### Solution

```js
function isAnagram(s, t) {
  if (s.length !== t.length) return false;

  const counts = new Array(26).fill(0);

  for (let i = 0; i < s.length; i++) {
    counts[s.charCodeAt(i) - 97]++;
    counts[t.charCodeAt(i) - 97]--;
  }

  return counts.every(c => c === 0);
}
```

### Dry Run

```
s = "anagram", t = "nagaram"  (length 7 each — passes length check)

i=0: s[0]='a'→counts[0]++, t[0]='n'→counts[13]--
i=1: s[1]='n'→counts[13]++, t[1]='a'→counts[0]--
i=2: s[2]='a'→counts[0]++, t[2]='g'→counts[6]--
i=3: s[3]='g'→counts[6]++, t[3]='a'→counts[0]--
i=4: s[4]='r'→counts[17]++, t[4]='r'→counts[17]--
i=5: s[5]='a'→counts[0]++, t[5]='a'→counts[0]--
i=6: s[6]='m'→counts[12]++, t[6]='m'→counts[12]--

Every index nets to 0 → counts.every(c => c===0) = true
Answer: true ✓
```

### Complexity
- Time: O(n) — single combined pass over both strings.
- Space: O(1) — fixed 26-element array, independent of input length.

### Edge Cases
- Different lengths: caught immediately by the length check, O(1).
- Empty strings: both length 0, loop doesn't execute, all counts remain 0 → correctly returns true (two empty strings are trivially anagrams of each other).
- Identical strings: every count increments then decrements to exactly the same value → nets to 0 → correctly true.
- Case sensitivity: this implementation is case-sensitive by design (`'A'` and `'a'` map to different — or in this ASCII-lowercase-only scheme, invalid — indices); real-world use would need explicit `.toLowerCase()` normalization if case-insensitivity is required.

### Follow-up Questions
- "What if inputs can be Unicode?" → Switch to a `Map` keyed by character instead of a fixed 26-array (see Q4/Q28).
- "What if you need to find all anagram groups in a list of strings?" → See Problem 2 (Group Anagrams).

## Problem 2 — Group Anagrams

### Problem
Given an array of strings `strs`, group the anagrams together. Return the groups in any order.

```
Input:  strs = ["eat","tea","tan","ate","nat","bat"]
Output: [["eat","tea","ate"],["tan","nat"],["bat"]]
```

### Pattern Recognition
Multiple strings need to be bucketed by "same character multiset" — generalizes pairwise anagram checking into a hash-map-based grouping problem.

### Key Insight
Two strings belong in the same group if and only if they share the same **canonical form**. Sorting each string's characters produces a canonical form that's identical for all anagrams of each other and different otherwise — perfect as a hash map key.

### Approach
For each string, compute its sorted-character key. Use that key to bucket the original (unsorted) string into a hash map of lists. Return the map's values.

### Solution

```js
function groupAnagrams(strs) {
  const groups = new Map();

  for (const s of strs) {
    const key = s.split('').sort().join('');

    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(s);
  }

  return Array.from(groups.values());
}
```

### Dry Run

```
strs = ["eat","tea","tan","ate","nat","bat"]

"eat" → sorted "aet" → groups={"aet":["eat"]}
"tea" → sorted "aet" → groups={"aet":["eat","tea"]}
"tan" → sorted "ant" → groups={"aet":[...], "ant":["tan"]}
"ate" → sorted "aet" → groups={"aet":["eat","tea","ate"], "ant":["tan"]}
"nat" → sorted "ant" → groups={"aet":[...], "ant":["tan","nat"]}
"bat" → sorted "abt" → groups={"aet":[...], "ant":[...], "abt":["bat"]}

Answer: [["eat","tea","ate"], ["tan","nat"], ["bat"]] ✓ (order may vary)
```

### Complexity
- Time: O(n × k log k) — n strings, each sorted in O(k log k) where k is the max string length.
- Space: O(n × k) — storing all strings across the map's buckets.

### Edge Cases
- Empty input array: returns an empty array — no groups.
- All strings are anagrams of each other: single group containing everything.
- No two strings are anagrams: each string forms its own singleton group.
- Empty string in the input: sorts to `""`, forming its own group (or grouping with other empty strings) — handled naturally, no special case needed.

### Follow-up Questions
- "Can you avoid the O(k log k) sort per string?" → Use a frequency-count tuple/string (e.g., `"1a0b2c..."` for 26 letters) as the key instead of a sorted string — reduces to O(k) per string, giving O(n × k) total.
- "What if the strings are extremely long but the alphabet is small?" → The count-tuple key optimization above becomes especially valuable, since sorting cost grows with string length while counting cost only grows with (length + alphabet size).

## Problem 3 — String Compression (In-Place)

### Problem
Given an array of characters `chars`, compress it in-place using the counts of repeated characters. Each group of consecutive repeating characters is replaced by the character followed by the group's length (as separate characters), only if the length is greater than 1. Return the new length of the array after compression.

```
Input:  chars = ["a","a","b","b","c","c","c"]
Output: 6, chars = ["a","2","b","2","c","3"]

Input:  chars = ["a"]
Output: 1, chars = ["a"]

Input:  chars = ["a","b","b","b","b","b","b","b","b","b","b","b","b"]
Output: 4, chars = ["a","b","1","2"]
```

### Pattern Recognition
Classic in-place run-length encoding using a two-pointer (read/write) technique.

### Key Insight
For any run of length ≥ 2, the compressed output (character + digit(s)) is always shorter than the run itself, so a `write` pointer trailing behind (or equal to) a `read` pointer never gets overtaken. Single-character runs write only the character (no trailing "1"), keeping the invariant `write <= read` intact throughout.

### Approach
`read` scans through the array identifying runs. For each run, `write` the character, then (if the run length exceeds 1) write each digit of the count individually. Return the final `write` position as the new logical length.

### Solution

```js
function compress(chars) {
  let write = 0, read = 0;

  while (read < chars.length) {
    const ch = chars[read];
    let count = 0;

    while (read < chars.length && chars[read] === ch) {
      count++;
      read++;
    }

    chars[write++] = ch;

    if (count > 1) {
      for (const digit of String(count)) {
        chars[write++] = digit;
      }
    }
  }

  return write;
}
```

### Dry Run

```
chars = ["a","b","b","b","b","b","b","b","b","b","b","b","b"]  (1 'a', 12 'b's)

read=0: ch='a', count=1 (only one 'a'), read advances to 1
  write 'a' at index 0 → write=1
  count(1) not > 1 → no digits written

read=1: ch='b', count runs from index 1 to 12 → count=12, read advances to 13
  write 'b' at index 1 → write=2
  count(12) > 1 → write digits '1','2' at indices 2,3 → write=4

read(13) >= chars.length(13) → loop ends

Result: chars[0..3] = ['a','b','1','2'], return write=4 ✓
```

### Complexity
- Time: O(n) — `read` visits each character exactly once across the outer and inner loops combined; `write` never exceeds `read`.
- Space: O(1) extra — compression happens in-place within the input array (aside from the O(digits) temporary string conversion for multi-digit counts, which is O(log count) and typically treated as O(1) for this problem's purposes).

### Edge Cases
- Single character: `count = 1`, writes just the character, no digit — correctly returns length 1.
- All identical characters: one giant run, writes the character plus however many digits the total count needs.
- No repeated characters at all: every run has length 1, output equals input exactly (no digits added anywhere) — correctly returns the original length.
- Run length requiring multiple digits (e.g., 12, 100): the digit-splitting loop (`for (const digit of String(count))`) correctly writes each digit as a separate array element, as required by the in-place array format.

### Follow-up Questions
- "What if you need to return a new compressed string instead of modifying in-place?" → Simpler version without the write/read invariant concerns — just build a result string directly (see Q11's `compress` function).
- "What if the count for a single-character 'run' should always include the digit '1' (i.e., non-standard variant)?" → The `write <= read` invariant would need re-examination, since writing "a1" for a single 'a' costs 2 output slots for 1 input slot — this specific in-place approach relies on the "omit 1" rule to guarantee no overwrite corruption; a variant requiring the "1" would need to build a separate output buffer instead of compressing truly in-place.

## Problem 4 — Valid Palindrome (Ignoring Non-Alphanumeric Characters)

### Problem
Given a string `s`, determine if it is a palindrome after converting all uppercase letters to lowercase and removing all non-alphanumeric characters.

```
Input:  s = "A man, a plan, a canal: Panama"
Output: true

Input:  s = "race a car"
Output: false

Input:  s = " "
Output: true  (empty after filtering — vacuously a palindrome)
```

### Pattern Recognition
Two-pointer palindrome check, with an added filtering/normalization step handled inline rather than via a separate cleaning pass.

### Key Insight
Rather than building a separate cleaned string (extra O(n) space), advance each pointer past non-alphanumeric characters *as part of* the same two-pointer walk, comparing only when both pointers rest on valid alphanumeric characters.

### Approach
Two pointers start at the string's ends. Before each comparison, both pointers skip forward/backward past any non-alphanumeric characters. Compare the (case-normalized) characters; mismatch means not a palindrome. Continue until pointers meet or cross.

### Solution

```js
function isPalindrome(s) {
  let left = 0, right = s.length - 1;
  const isAlnum = (ch) => /[a-zA-Z0-9]/.test(ch);

  while (left < right) {
    while (left < right && !isAlnum(s[left])) left++;
    while (left < right && !isAlnum(s[right])) right--;

    if (s[left].toLowerCase() !== s[right].toLowerCase()) return false;

    left++;
    right--;
  }

  return true;
}
```

### Dry Run

```
s = "A man, a plan, a canal: Panama"
left=0 ('A'), right=30 ('a')

left=0: 'A' is alnum, stop
right=30: 'a' is alnum, stop
compare: 'a' === 'a' (case-normalized) ✓ → left=1, right=29

left=1: ' ' not alnum → left=2 ('m'), alnum, stop
right=29: 'm' is alnum, stop
compare: 'm' === 'm' ✓ → left=3, right=28

... (continues skipping spaces/commas/colons and comparing alphanumerics) ...

Eventually left and right meet in the middle without any mismatch found.
Answer: true ✓
```

### Complexity
- Time: O(n) — each pointer traverses at most its half of the string once; the inner skip-loops' total iterations across the whole run are bounded by n, not multiplicative with the outer loop.
- Space: O(1) — no cleaned copy of the string is built.

### Edge Cases
- String with no alphanumeric characters at all (e.g., `"!!!"` or `" "`): pointers skip everything and cross without ever comparing — loop exits via `left < right` becoming false, correctly returns `true` (vacuous palindrome).
- Single alphanumeric character surrounded by punctuation (e.g., `".a."`): pointers converge to the same single character, loop condition `left < right` becomes false before any mismatch could occur — correctly `true`.
- Mixed case: `.toLowerCase()` normalization ensures `'A'` and `'a'` are treated as equal.
- Numbers mixed with letters (e.g., `"0P"`): the regex `[a-zA-Z0-9]` correctly treats digits as valid alphanumeric characters to compare.

### Follow-up Questions
- "What if up to one character deletion is allowed to make it a palindrome?" → See Q26 (Valid Palindrome II) — branch into two sub-checks on the first mismatch.
- "What if the input is a stream and you can't index backward from the end?" → Would require buffering the stream first (defeating O(1) space) or a fundamentally different algorithm (e.g., hashing-based rolling comparison) — two-pointer inherently needs random access to both ends.

## Problem 5 — Longest Palindromic Substring

### Problem
Given a string `s`, return the longest substring of `s` that is a palindrome.

```
Input:  s = "babad"
Output: "bab"  (or "aba" — both are valid length-3 answers)

Input:  s = "cbbd"
Output: "bb"
```

### Pattern Recognition
Finding the longest palindrome *within* a string (not checking the whole string) — the "expand around center" technique, trying every possible center position.

### Key Insight
Every palindrome has a center — either a single character (odd-length palindrome) or a gap between two characters (even-length palindrome). Trying both center types at every index and expanding outward while characters match covers every possible palindromic substring.

### Approach
For each index `i`, run two expansions: one treating `i` as the center of an odd-length palindrome, one treating the gap between `i` and `i+1` as the center of an even-length palindrome. Track the longest match found across all expansions.

### Solution

```js
function longestPalindrome(s) {
  if (s.length < 1) return "";

  let start = 0, maxLen = 1;

  function expand(left, right) {
    while (left >= 0 && right < s.length && s[left] === s[right]) {
      left--;
      right++;
    }
    return right - left - 1; // length of palindrome found (after the failed final step)
  }

  for (let i = 0; i < s.length; i++) {
    const lenOdd = expand(i, i);
    const lenEven = expand(i, i + 1);
    const len = Math.max(lenOdd, lenEven);

    if (len > maxLen) {
      maxLen = len;
      start = i - Math.floor((len - 1) / 2);
    }
  }

  return s.substring(start, start + maxLen);
}
```

### Dry Run

```
s = "babad"

i=0 ('b'): expand(0,0)→'b' alone, left=-1 stop → len=1
           expand(0,1)→'b'≠'a' → len=0
           max=1, not > maxLen(1)

i=1 ('a'): expand(1,1)→center 'a', expand: left=0,right=2 → s[0]='b'≠s[2]='b'? 
           wait s[0]='b', s[2]='b' → match! left=-1,right=3 stop → len=3 ("bab")
           expand(1,2)→'a'≠'b' → len=0
           max=3 > maxLen(1) → maxLen=3, start=1-1=0 → "bab"

i=2 ('b'): expand(2,2)→center 'b', left=1,right=3: s[1]='a'≠s[3]='a'? match!
           left=0,right=4: s[0]='b'≠s[4]='d' → stop → len=3 ("aba")
           expand(2,3)→'b'≠'a' → len=0
           max=3, not > maxLen(3) → no update (keeps "bab" from before)

i=3 ('a'): expand(3,3)→len=1; expand(3,4)→'a'≠'d'→len=0 → no update
i=4 ('d'): expand(4,4)→len=1; expand(4,5) out of bounds→len=0 → no update

Answer: "bab" ✓ (or "aba" is an equally valid length-3 answer depending on tie-breaking)
```

### Complexity
- Time: O(n²) — n centers, each expansion up to O(n) in the worst case (e.g., a string of all identical characters like `"aaaaaa"`).
- Space: O(1) extra (excluding the returned substring itself).

### Edge Cases
- Single character: trivially its own palindrome, `maxLen` starts at 1, correctly returned.
- Empty string: explicit early return of `""`.
- All identical characters (e.g., `"aaaa"`): the entire string is the longest palindrome — expansion from any center eventually covers the whole string.
- No palindrome longer than length 1 exists (e.g., `"abcde"`): `maxLen` stays at its initial value of 1, and the returned substring is just the first single character encountered that never gets beaten — still a valid (trivial) palindrome answer.

### Follow-up Questions
- "Can you do this in O(n) instead of O(n²)?" → Yes, via Manacher's algorithm (see Q24) — rarely required to implement from scratch in an interview but good to mention as the theoretically optimal approach.
- "What if you need to count all palindromic substrings instead of just the longest?" → Same expand-around-center scaffold, but increment a counter on every successful expansion step instead of tracking a max (see Q25).

## Quick Reference — Pattern Decision Tree

```
Does the problem involve comparing/analyzing character composition or symmetry of strings?
│
├── ARE TWO STRINGS ANAGRAMS OF EACH OTHER (single pair)?
│   └── Frequency Count (array for small fixed alphabet, hash map for Unicode) → O(n)
│
├── GROUP A LIST OF STRINGS BY ANAGRAM EQUIVALENCE?
│   └── Canonical form (sorted string OR frequency tuple) as hash map key → O(n·k log k) or O(n·k)
│
├── FIND ANAGRAM SUBSTRINGS WITHIN A LARGER STRING?
│   └── Sliding window + frequency-count diff, fixed window size = pattern length → O(n)
│
├── COMPRESS A STRING (collapse repeated runs)?
│   ├── Need a NEW compressed string → simple single-pass RLE, compare length before returning
│   └── Need IN-PLACE compression (array of chars) → two-pointer (read/write), omit "1" for single runs
│
├── DOES A STRING READ THE SAME FORWARDS/BACKWARDS?
│   └── Two-pointer from both ends inward → O(n) time, O(1) space
│       (add inline skip-logic for "ignore non-alphanumeric" variants)
│
├── FIND THE LONGEST PALINDROMIC SUBSTRING?
│   ├── O(n²) acceptable → Expand Around Center (try every center, odd + even)
│   └── O(n) required → Manacher's Algorithm
│
├── COUNT ALL PALINDROMIC SUBSTRINGS?
│   └── Expand Around Center, increment counter per successful expansion step → O(n²)
│
├── PALINDROME CHECK WITH ONE ALLOWED DELETION?
│   └── Two-pointer; on first mismatch, branch into two sub-checks (skip left / skip right)
│
└── CAN A STRING BE REARRANGED INTO A PALINDROME?
    └── Frequency count; valid iff at most one character has an odd count
```

## Common Bugs Checklist

Before submitting any anagram / compression / palindrome solution, verify:

1. **Length check before frequency comparison (anagrams)?** — Skipping the `s.length !== t.length` short-circuit can, in careless implementations, allow strings of different lengths to falsely appear as anagrams if the diff-counting logic isn't airtight.

2. **Correct alphabet-size structure chosen?** — Fixed-size array for known small alphabets (fast, O(1) space); hash map for Unicode or unknown character sets. Using a 26-element array on Unicode input silently corrupts or crashes.

3. **Compression: comparing lengths before returning?** — Returning an RLE result unconditionally can produce output *longer* than the input on strings with no repeated runs — always compare and fall back to the original when appropriate.

4. **In-place compression: digit-splitting for multi-digit counts?** — A run of 12+ identical characters needs each digit of "12" written as a separate array element, not the two-character numeral treated as one unit — forgetting this corrupts the output format.

5. **In-place compression: omitting the "1" for single-character runs?** — Required to guarantee the `write` pointer never overtakes `read`; including it breaks the in-place invariant and can corrupt unread data.

6. **Palindrome: off-by-one in pointer loop condition?** — Must be `left < right`, not `left <= right` — using `<=` on an odd-length palindrome would compare the middle character to itself unnecessarily (harmless but wasteful) or, in filtering variants, can cause an infinite loop if skip-logic isn't guarded correctly against `left === right`.

7. **Expand around center: both odd AND even center types tried?** — Forgetting the even-length center check (`expand(i, i+1)`) silently misses all even-length palindromes (e.g., `"bb"`, `"abba"`).

**Final Tip:** At the 5 YOE level, all three of these topics reduce to the same handful of core techniques — frequency counting (anagrams, palindrome-rearrangement feasibility), two-pointer traversal (palindrome checks, in-place compression), and center-expansion (longest palindromic substring). Interviewers are listening for you to name the technique and state its core invariant *before* writing code: "anagrams means matching frequency counts," "in-place compression means write never outpaces read because every multi-character run always shrinks," "palindrome check means two pointers converging with zero mismatches." Recognizing which of these three techniques applies — and being explicit about the invariant driving it — is the strongest signal of real understanding.
