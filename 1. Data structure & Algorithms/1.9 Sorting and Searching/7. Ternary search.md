## Topic A: Ternary Search Fundamentals

### Section A1: Core Mechanics

**Q1. What is ternary search, and what structural property of the input does it require?**

A: Ternary search is an algorithm for finding the extremum (maximum or minimum) of a **unimodal function** over a search domain. Unlike binary search — which requires a *monotone* property ("if the condition holds at mid, it holds for all elements to the left or right") — ternary search requires a *unimodal* property: the function strictly increases up to a single peak, then strictly decreases (or vice versa). It works by placing two probe points `m1` and `m2` that divide the domain into thirds, evaluating the function at both, and eliminating the third that *cannot* contain the extremum. The key requirement: the function must have **exactly one local extremum** in the search range. Without unimodality, ternary search may converge to the wrong answer or diverge.

```
Binary search requires:  monotone property
  [F F F F T T T T T]  ← find the first T
  or
  [sorted array]        ← find a specific value

Ternary search requires: unimodal property
  [↑ ↑ ↑ ↑ peak ↓ ↓ ↓]  ← find the peak
  or
  [↓ ↓ ↓ valley ↑ ↑ ↑]  ← find the valley

Non-unimodal: ternary search FAILS
  [↑ peak ↓ ↑ peak ↓]  ← multiple peaks: no guarantee
```

**Q2. What is a unimodal function, and what are its precise mathematical properties?**

A: A function `f` is **unimodal on [lo, hi]** if there exists a point `p ∈ [lo, hi]` (the peak) such that `f` is *strictly increasing* on `[lo, p]` and *strictly decreasing* on `[p, hi]`. For minimum-finding (a "valley"), the condition is reversed: strictly decreasing then strictly increasing. The three critical implications: (1) the peak `p` is the *unique global maximum* on `[lo, hi]` — no other point can equal it; (2) for any two points `a < b` both to the *left* of `p`, `f(a) < f(b)`; for any two points both to the *right*, `f(a) > f(b)`; (3) for any `a < b`, if `f(a) < f(b)`, the peak is strictly to the right of `a` (not at or before `a`). These implications are exactly what the two-midpoint elimination exploits. A weakly unimodal function (with a flat plateau at the peak) complicates ternary search and requires special handling.

```
Strictly unimodal: unique peak, strict monotone on each side
  f(x) = -(x-3)² + 9   (quadratic)
  f(x) = sin(x) on [0, π]
  f(x) = -|x - 5| + 10 (triangle, but only weakly — plateau at peak is a point)

Convex function (for minimization): strictly decreasing then increasing
  f(x) = (x-3)² + 1    (parabola opening up)
  f(x) = |x - 5|       (absolute value — weakly convex, plateau at valley)

NOT unimodal:
  f(x) = sin(x) on [0, 3π]  (three peaks: ternary search fails)
  f(x) = x² - 4x + 3        (parabola opening up: unimodal for MINIMIZATION on any range)
```

**Q3. How does the two-midpoint elimination mechanism work, and what makes the elimination valid?**

A: Place two probe points at the one-third and two-thirds marks of the current search range: `m1 = lo + ⌊(hi - lo) / 3⌋` and `m2 = hi - ⌊(hi - lo) / 3⌋`. Compare `f(m1)` and `f(m2)`:

**If `f(m1) < f(m2)`**: eliminate `[lo, m1]`. Proof: if the peak were at or before `m1`, then since `m2 > m1` and we would be in the strictly decreasing region past the peak, `f(m2) < f(m1)` — contradicting `f(m2) > f(m1)`. So the peak is strictly to the right of `m1`. Set `lo = m1 + 1` (discrete) or `lo = m1` (continuous).

**If `f(m1) > f(m2)`**: eliminate `[m2, hi]`. By symmetric reasoning, the peak is strictly to the left of `m2`. Set `hi = m2 - 1` (discrete) or `hi = m2` (continuous).

**If `f(m1) == f(m2)`**: for a strictly unimodal function, this means `m1 < p < m2` (peak lies strictly between them — both midpoints are on opposite sides of the peak). Eliminate both outer thirds: `lo = m1 + 1, hi = m2 - 1`.

```
Search range [lo ............. hi]
              ↑       ↑       ↑
              lo      p(peak) hi

Place:   [lo ... m1 ... m2 ... hi]
              (1/3)    (2/3)

If f(m1) < f(m2): peak NOT in [lo, m1]
  New range: [m1+1 ........ hi]  (eliminated left third)

If f(m1) > f(m2): peak NOT in [m2, hi]
  New range: [lo ........ m2-1]  (eliminated right third)

Each step eliminates exactly 1/3 of the range.
```

**Q4. Why are thirds specifically used — what happens with other split ratios?**

A: The choice of thirds is the *optimal fixed-ratio split* that eliminates the maximum possible fraction of the search space per function evaluation, given two evaluations per step. With thirds, exactly 1/3 is eliminated per step, leaving 2/3. Any other symmetric ratio `(r, 1-r)` where `r < 1/3` eliminates less than 1/3. A ratio of exactly 1/3 minimizes the *worst-case* remaining search space. However, using two evaluations to eliminate 1/3 is actually less efficient than binary search (one evaluation eliminates 1/2). This is the core insight that motivates Golden Section Search (Q10): it eliminates the same 1/3 fraction but reuses one evaluation per step, needing only one *new* evaluation — achieving 1/φ² ≈ 38.2% elimination per evaluation rather than ternary search's 1/3 elimination per *two* evaluations.

```
Ternary search:       2 evaluations → eliminate 1/3 → 1/6 of range per evaluation
Golden section:       1 evaluation  → eliminate 38.2% → 38.2% of range per evaluation
Binary search (f'):   1 evaluation  → eliminate 1/2 → 1/2 of range per evaluation

Binary search on derivative is most efficient when derivative is available.
Golden section is most efficient when function evaluations dominate.
Ternary search is simplest to implement but least efficient per evaluation.
```

**Q5. What is the time complexity of ternary search, and how does its total comparison count compare to binary search?**

A: Each ternary search step reduces the range by a factor of 2/3. To reduce from size n to 1: `(2/3)^k ≤ 1/n` → `k ≥ log_{3/2}(n) = log(n) / log(3/2) ≈ 1.71 × log₂(n)`. So ternary search takes ~71% more *iterations* than binary search. With 2 evaluations per iteration, total evaluations = `2 × 1.71 × log₂(n) ≈ 3.42 × log₂(n)`. Binary search on the derivative (comparing `f(mid)` with `f(mid+1)` for discrete, or using the sign of `f'(mid)` for continuous) takes `log₂(n)` iterations with 1-2 evaluations each. **Verdict**: ternary search is asymptotically O(log n) but has a larger constant — it uses roughly 3× more function evaluations than binary search on the derivative. The tradeoff: ternary search doesn't require knowledge of the derivative or monotone ordering relationship, only the ability to compare two function values.

```
Algorithm              Iterations          Evals/iter   Total evals
Binary search          log₂(n)    ≈ 1.00k  1            log₂(n)    ≈ 1.00k
Golden section search  1.44·log₂n ≈ 1.44k  1            1.44·log₂n ≈ 1.44k
Ternary search         1.71·log₂n ≈ 1.71k  2            3.42·log₂n ≈ 3.42k

k = log₂(n). Ternary search is asymptotically O(log n) but ≈3× more evaluations.
```

**Q6. What is the invariant maintained by ternary search at every iteration?**

A: The invariant is: *at the start of every iteration, the peak (or valley) of the unimodal function is guaranteed to lie within the current search range `[lo, hi]`.* This invariant holds initially (the entire domain `[lo, hi]` contains the peak by assumption) and is preserved by each elimination step (the proof in Q3 shows that the eliminated third cannot contain the peak). When the range narrows to 1, 2, or 3 elements (discrete) or becomes smaller than ε (continuous), the invariant guarantees the peak is among the remaining candidates — a linear scan finds it. The invariant's strength: it is maintained *unconditionally* — every step either preserves the range containing the peak or produces a smaller range that still contains it. The eliminated elements are provably sub-optimal.

**Q7. How does ternary search on a discrete (integer) domain differ from a continuous domain in implementation and termination?**

A: On a **discrete domain** (integer indices): the probe points are integer-valued; the search terminates when `hi - lo ≤ 2` (at most 3 remaining elements), at which point a linear scan of `[lo, hi]` identifies the peak. The update rules use `lo = m1 + 1` and `hi = m2 - 1` to avoid re-evaluating points that have already been compared. Edge case: when `hi - lo == 2` exactly, the thirds formula gives `m1 = lo + 0 = lo` and `m2 = hi - 0 = hi`, which makes no progress — the `hi - lo ≤ 2` termination guard prevents this.

On a **continuous domain** (real-valued): the probe points are real numbers; the search terminates when the range `hi - lo < ε` (some precision tolerance, typically 10⁻⁹) or after a fixed number of iterations (100–300 iterations reduces the range to `(2/3)^200 ≈ 10⁻³⁵` of the original). The update rules use `lo = m1` and `hi = m2` (no `±1`, since there are no distinct integer positions). The fixed-iteration approach (`for (let i = 0; i < 200; i++)`) is preferred over epsilon-comparison because it avoids floating-point precision issues in the termination check.

```js
// Discrete ternary search — finds index of maximum in arr
function ternarySearchDiscrete(arr, lo, hi) {
  while (hi - lo > 2) {
    const m1 = lo + Math.floor((hi - lo) / 3);
    const m2 = hi - Math.floor((hi - lo) / 3);
    if (arr[m1] < arr[m2]) lo = m1 + 1;  // peak in (m1, hi]
    else                   hi = m2 - 1;  // peak in [lo, m2)
  }
  // Linear scan remaining ≤3 elements
  let best = lo;
  for (let i = lo + 1; i <= hi; i++) if (arr[i] > arr[best]) best = i;
  return best;
}

// Continuous ternary search — finds x maximizing f(x)
function ternarySearchContinuous(f, lo, hi) {
  for (let i = 0; i < 200; i++) { // 200 iterations → (2/3)^200 ≈ 10^-35 precision
    const m1 = lo + (hi - lo) / 3;
    const m2 = hi - (hi - lo) / 3;
    if (f(m1) < f(m2)) lo = m1;  // no ±1: continuous range
    else               hi = m2;
  }
  return (lo + hi) / 2; // midpoint of tiny remaining interval
}
```

**Q8. What breaks when ternary search is applied to a non-unimodal function?**

A: The elimination step's correctness proof (Q3) relies on strict unimodality. For a function with multiple peaks: `f(m1) < f(m2)` does NOT guarantee the global maximum is in `[m1+1, hi]` — there could be a higher peak in `[lo, m1]`. Ternary search would eliminate it, converging to a local maximum or the wrong peak entirely. The failure mode is silent: the algorithm terminates with an answer that appears valid (it's a local peak) but is not the global optimum. The practical diagnostic: if you're unsure whether a function is unimodal, test on a few instances where the answer is known — ternary search giving a sub-optimal answer is the signature of non-unimodality. When in doubt, verify the problem guarantees unimodality explicitly (e.g., "the function has exactly one peak").

**Q9. How does the handling of equal values at m1 and m2 affect correctness?**

A: For a strictly unimodal function, `f(m1) == f(m2)` can only occur when `m1 < peak < m2` (the peak lies strictly between the two midpoints). In this case, both outer thirds are safely eliminable: set `lo = m1 + 1, hi = m2 - 1`. For a *weakly* unimodal function with a flat plateau at the peak (e.g., `arr = [1, 3, 5, 5, 5, 4, 2]`), `f(m1) == f(m2)` could occur when both m1 and m2 are on the plateau. Setting `lo = m1 + 1, hi = m2 - 1` still preserves the plateau within `[lo, hi]` as long as the plateau isn't entirely between m1 and m2 (which cannot happen if the plateau is at least one position wide and m1, m2 are interior probe points). The implementation: treating `f(m1) == f(m2)` as either the `f(m1) < f(m2)` case or the `f(m1) > f(m2)` case also works for strictly unimodal functions — the peak is to the right of m1 (or left of m2), and eliminating one outer third is correct.

### Section A2: Variants and Optimizations

**Q10. What is Golden Section Search, and how does it require only one new evaluation per step?**

A: Golden Section Search (GSS) eliminates the same fraction per step as ternary search (~38.2% vs ternary's 33.3%) but requires only **one new function evaluation per step** by reusing the probe point from the previous step. The key: place probe points at positions `lo + (hi-lo)/φ²` and `lo + (hi-lo)/φ` where `φ = (1+√5)/2 ≈ 1.618` (the golden ratio). After eliminating one third, one of the two probe points falls exactly where the new probe point for the next iteration would be placed — so only one new evaluation is needed. Total evaluations after `n` steps: `n + 1` (initial 2, then 1 per subsequent step). This makes GSS about 2× more efficient per evaluation than ternary search, converging to `φ^{-n}` of the original range — roughly 38.2% reduction per evaluation vs ternary's 33.3% per evaluation.

```
Ternary search (per iteration):
  Range [lo .....|m1|....|m2|..... hi]
  Evaluate f(m1) and f(m2): 2 evaluations. Eliminate 1/3.
  Next iteration: 2 completely new evaluations.
  Total for k iterations: 2k evaluations.

Golden section search (per iteration):
  Range [lo .|m1|..|m2|. hi]   (placed at golden ratio positions)
  Evaluate f(m1) and f(m2): 2 evaluations (first iteration).
  Eliminate [lo, m1] or [m2, hi]. New m1 or m2 = old m2 or m1 (reuse!).
  Next iteration: 1 NEW evaluation only.
  Total for k iterations: k + 1 evaluations.

Golden section: same convergence quality, ~2× fewer evaluations.
```

**Q11. What is the binary-search-on-derivative approach, and when does it replace ternary search?**

A: For a differentiable unimodal function, the peak is where the derivative `f'(x) = 0` changes sign from positive to negative. The derivative is itself monotone (positive then negative for a maximum), so binary search applies: if `f'(mid) > 0`, the peak is to the right; if `f'(mid) < 0`, the peak is to the left. This eliminates half the range per step (vs ternary's one-third) with one evaluation per step. For discrete arrays, compare `f(mid)` with `f(mid + 1)`: if `f(mid) < f(mid + 1)`, the function is still increasing at mid, so the peak is to the right. This is the standard approach for Find Peak Element (LC 162). The binary-on-derivative approach uses O(log₂ n) evaluations vs O(1.71 × log₂ n) iterations for ternary search — making it about 3× more efficient overall when adjacent comparisons (the "discrete derivative") are O(1). Use ternary search when: (1) the derivative isn't available or is expensive to compute; (2) the function is defined on a non-differentiable but still unimodal domain.

```
Discrete function peak finding:
  Ternary search: f(m1) vs f(m2), 2 comparisons/iter, O(log_{3/2} n) iters
  Binary on derivative: f(mid) vs f(mid+1), 1 comparison/iter, O(log₂ n) iters

Binary on derivative is strictly better for discrete unimodal arrays.
Ternary search is preferred when derivative computation costs as much as a function call.
```

**Q12. What is the connection between convex functions and ternary search?**

A: A **convex function** on an interval has a single global minimum (its "valley") with no other local minima — it is unimodal for *minimization*. Concave functions have a single global maximum — unimodal for maximization. Ternary search applies directly: to minimize a convex function, use `if (f(m1) > f(m2)) lo = m1 + 1; else hi = m2 - 1` (take from the side with smaller value). Many optimization problems produce convex cost functions: sum of squared distances (quadratic, convex), regularized loss functions (convex), piecewise linear functions with one minimum (convex). Convexity is stronger than unimodality — it guarantees global optimality, not just local. The practical check: if the second derivative `f''(x) ≥ 0` everywhere (or if the function "looks like a bowl"), ternary search converges to the true global minimum.

**Q13. What is 2D ternary search, and what class of problems does it solve?**

A: 2D ternary search finds the extremum of `f(x, y)` when the function is unimodal in `x` for any fixed `y`, AND unimodal in `y` for any fixed `x`. The approach: outer ternary search over `x` values; for each probe `x` in the outer search, an inner ternary search over `y` computes `g(x) = max_y f(x, y)`; the outer search then finds the `x` maximizing `g(x)`. Total complexity: O(log²(n)) evaluations for an n×n grid. 2D ternary search requires the function's unimodality structure to hold in *both* dimensions independently — a condition that holds for quadratic functions (elliptic paraboloids), distance-based objectives with a single optimal location, and separable convex functions. If the function is not jointly unimodal (e.g., saddle points exist), 2D ternary search may fail.

```
f(x, y) = -(x-3)² - (y-4)² + 25    (paraboloid, maximum at (3,4))

Outer ternary on x: for each probe x_probe,
  Inner ternary on y: find y* = argmax_y f(x_probe, y)
  → g(x_probe) = f(x_probe, y*) = -(x_probe-3)² + 25
Outer search: find x* = argmax_x g(x) = 3.
Answer: (x*, y*) = (3, 4). ✓

Complexity: O(log n × log n) = O(log² n) function evaluations.
```

**Q14. How do you determine if a problem's search space is unimodal — the practical test?**

A: Three practical checks: (1) **Derivative sign test**: if you can show the function's derivative is positive then negative (for maximum) or negative then positive (for minimum) exactly once across the domain, it's unimodal. (2) **Plot/sample test**: evaluate the function at several uniformly spaced points; if values rise then fall monotonically, it's likely unimodal — though this is not a proof. (3) **Structural argument**: "the function = (increasing part) + (decreasing part)" → if you can decompose the cost as one term that grows and one that shrinks as the parameter increases, the sum has a single minimum. Example: total cost = fixed cost × k (grows) + work per person / k (shrinks) → sum has one valley. The failure case: optimization over a non-convex search space (e.g., integer variables that interact non-linearly) — ternary search may give a local optimum. Verify unimodality before applying ternary search; it is a non-trivial assumption that must be justified for each problem.

**Q15. How many iterations are needed for a given precision ε on a continuous domain?**

A: After `k` iterations, the range shrinks to `(2/3)^k × (hi_0 - lo_0)`. For precision `ε`: `(2/3)^k ≤ ε / (hi_0 - lo_0)` → `k ≥ log(ε / (hi_0 - lo_0)) / log(2/3)`. Practically: for a range of width 1 and `ε = 10⁻⁹`: `k ≥ log(10⁻⁹) / log(2/3) = 9 / log_{10}(3/2) = 9 / 0.176 ≈ 51` iterations suffice. Using 100–200 iterations provides 15–30 digits of precision — far beyond double-precision floating point (which has ~15 significant digits). The standard competitive programming implementation uses exactly 100 or 200 iterations (never fewer than the theoretical bound), eliminating any need to think about ε explicitly.

```
Iterations needed for precision ε = 10^(-p) on a unit interval:
  p=6  (10^-6):  k ≥ 34 iterations
  p=9  (10^-9):  k ≥ 51 iterations
  p=12 (10^-12): k ≥ 68 iterations
  p=15 (10^-15): k ≥ 85 iterations (double precision limit)
  100 iterations: precision ≈ (2/3)^100 ≈ 2.5 × 10^-18 (safe for all practical purposes)
```

## Topic B: Analysis, Comparison, and Applications

### Section B1: Ternary vs Binary Search

**Q16. What is the fundamental distinction: when does a problem call for binary search vs ternary search?**

A: The distinction is in the **shape of the objective function** over the search space: **Binary search** applies when the predicate is *monotone* — there's a clear "transition point" from False to True (or from one behavior to another). The goal is to find the boundary of that transition. Examples: finding the leftmost index satisfying a condition, finding a value in a sorted array. **Ternary search** applies when the objective function is *unimodal* — it rises to a single peak then falls (or falls to a valley then rises). The goal is to find the extremum. The litmus test: if you can say "if the answer is ≥ k then it's easier/harder for any larger k," use binary search. If you can say "there's an optimal k and things get worse in both directions," use ternary search.

```
Binary search signal: "The condition is monotone in the parameter"
  "If we can do it with speed k, we can do it with speed k+1" → binary search

Ternary search signal: "There's a sweet spot — too little and too much both hurt"
  "If too few workers: overtime cost; if too many workers: idle cost" → ternary search
  "If too small radius: penalty; if too large radius: material cost" → ternary search

Boundary cases:
  Unimodal AND monotone on half domain: both work, binary search is faster
  Strictly monotone: binary only (no peak to find)
  Bimodal or multimodal: neither works reliably
```

**Q17. When is "ternary search on the answer space" the right pattern for optimization problems?**

A: "Ternary search on the answer" applies when: (1) the decision space is a single continuous or integer parameter `k`; (2) the objective cost `C(k)` is a unimodal (specifically convex) function of `k`; (3) the goal is to minimize (or maximize) `C(k)`. Template: compute `C(m1)` and `C(m2)` for two candidate parameter values; if `C(m1) > C(m2)` (for minimization), eliminate the third containing `m1` (the cost is lower toward `m2`); otherwise eliminate the `m2` side. Common cost function structures that guarantee convexity: `A × k + B / k` (total cost with linear scaling and inverse component), `A × k + B × ceil(n/k)` (resource allocation), quadratic expressions like `(k - k*)²`. For *monotone* cost functions (e.g., "as k increases, cost always decreases until a threshold"), use binary search instead — it's faster.

**Q18. What is the "Find Peak Element" problem, and why does binary search on the derivative solve it instead of ternary search?**

A: LC 162 (Find Peak Element) guarantees: `nums[-1] = nums[n] = -∞` and asks to find any index where `nums[i] > nums[i-1]` and `nums[i] > nums[i+1]`. The array may have multiple peaks. Ternary search would only work if the array were strictly unimodal (single peak) — for multiple peaks it could eliminate a valid peak. Binary search on the discrete derivative works for *any* peak: if `nums[mid] < nums[mid+1]`, the function is still rising at `mid`, so a peak exists in `[mid+1, hi]` (by the boundary condition: the function must eventually start descending before `n`). If `nums[mid] > nums[mid+1]`, a peak exists in `[lo, mid]`. This is O(log n) with one comparison per iteration — strictly better than ternary search's two comparisons and log_{3/2} n iterations. For arrays that are *guaranteed* unimodal (Find in Mountain Array, LC 1095), both approaches work, but binary on derivative remains more efficient.

**Q19. What are the three most common implementation mistakes in ternary search?**

A: (1) **Wrong midpoint formula — integer overflow or non-convergence**: using `(lo + hi) / 3` for m1 is wrong (should be `lo + (hi - lo) / 3`). The correct formula ensures m1 is in the lower third and m2 is in the upper third, always leaving a range strictly smaller than `hi - lo`. Using `Math.floor` correctly for discrete domains and avoiding integer division for continuous domains. (2) **Wrong termination for discrete domains**: using `while (lo < hi)` can cause an infinite loop when `hi - lo == 2` because the formula gives `m1 = lo` and `m2 = hi`, making no progress. Always terminate at `hi - lo ≤ 2` and do a linear scan. (3) **Wrong update direction**: for *maximization*, `f(m1) < f(m2)` means `lo = m1 + 1` (eliminate the lower third); for *minimization*, `f(m1) < f(m2)` means `hi = m2 - 1` (eliminate the higher third, since the valley is toward m1). Swapping these silently converges to the wrong extremum.

```
Bug 1 — wrong midpoint:
  const m1 = (lo + hi) / 3;        // ✗ Not guaranteed to be in [lo, (lo+hi)/2)
  const m1 = lo + (hi - lo) / 3;   // ✓ Correctly in the lower third

Bug 2 — infinite loop on discrete:
  while (lo < hi) { ... }           // ✗ Hangs when hi - lo == 2
  while (hi - lo > 2) { ... }       // ✓ Terminates, then linear scan

Bug 3 — direction flip (maximization vs minimization):
  // MAXIMIZATION: f(m1) < f(m2) → peak is toward m2 → eliminate left third
  if (f(m1) < f(m2)) lo = m1 + 1;  // ✓

  // MINIMIZATION: f(m1) < f(m2) → valley is toward m1 → eliminate right third
  if (f(m1) < f(m2)) hi = m2 - 1;  // ✓
```

**Q20. What is the exact update logic for the equal case in discrete ternary search, and when can you omit it?**

A: When `f(m1) == f(m2)` on a discrete strictly unimodal array, the peak is strictly between m1 and m2. The correct update is `lo = m1 + 1; hi = m2 - 1`. However, in most implementations, the equal case is handled by treating it as one of the two non-equal cases: `else hi = m2 - 1` (or `else lo = m1 + 1`). This is correct because: if the peak is between m1 and m2, eliminating the outer third that we assign it to will still keep the peak within `[lo, hi]` (the peak is interior to both thirds). The only correctness concern is for weakly unimodal functions with extended plateaus — but in competitive programming, strictly unimodal is usually assumed. When implementing ternary search, collapse the three cases into two: `if (f(m1) < f(m2)) lo = m1 + 1; else hi = m2 - 1` (for maximization) covers all scenarios.

### Section B2: Advanced Patterns

**Q21. How does ternary search apply to geometric optimization problems?**

A: Many geometric optimization problems have a unimodal cost function over a spatial parameter. Classic applications: (1) **Minimum distance from a point to a curve**: the distance from a fixed point `P` to a parametric curve `C(t)` as a function of `t` is often unimodal (single closest point) → ternary search on `t`. (2) **Optimal facility location on a line**: given customer locations, find the warehouse position minimizing total travel distance (sum of absolute differences, a convex function). (3) **Smallest enclosing circle**: the center's x-coordinate can be found by ternary search in the x-direction, then y-direction. (4) **Rotating calipers problems**: for convex polygons, quantities like minimum width or maximum distance often change unimodally as an angle parameter rotates → ternary search on angle. The geometric insight: convexity of the distance function (or the constraint function) implies unimodality, which ternary search exploits.

**Q22. What is the practical performance comparison between ternary search and built-in optimization methods?**

A: For numerical optimization on a smooth unimodal function, ternary search is competitive but not optimal: Newton's method converges *quadratically* (doubles significant digits per step) if the derivative and second derivative are available; Brent's method combines bisection, secant, and parabolic interpolation for robust O(log n) convergence; Golden section search is the optimal choice when only function evaluations are available (no derivatives). In competitive programming, ternary search is preferred over these because it is simpler to implement correctly under time pressure and handles non-smooth functions that Newton's method would fail on. The practical rule: if the function is smooth and the derivative is cheap, use binary search on the derivative; if only function values are available and the function is smooth, use Golden Section Search; if implementation simplicity matters most, use ternary search.

**Q23. What is the "ternary search on answer" pattern's cost function structure, and how do you verify convexity?**

A: The pattern applies when you have a parameter `k` (the "answer") and a cost `C(k)` that you want to minimize (or maximize). Convexity verification: (1) **Algebraic**: show `C(k) = f(k) + g(k)` where `f` is monotonically increasing and `g` is monotonically decreasing. The sum has a single minimum. (2) **Second derivative**: if `C''(k) > 0` for all k in the domain, C is convex. (3) **Spot check**: compute C at 5–10 evenly spaced k values and verify the values form a unimodal sequence. Common structures: `C(k) = A×k + B/k` (min at k = √(B/A)), `C(k) = A×k² + B×(1/k)` (min near k = (B/2A)^(1/3)), `C(k) = cost_of_more + cost_of_less` where each term moves monotonically in opposite directions. The failure diagnostic: if the spot check shows two local minima, the cost function is not convex and ternary search gives the wrong answer.

**Q24. How does ternary search relate to the "binary search on answer" pattern for decision problems?**

A: Binary search on answer applies when: given a target value T, there exists a threshold k* such that the condition `feasible(k) = True` for all k ≥ k* and `False` for k < k* (or the reverse). This is a *monotone* predicate → binary search. Ternary search on answer applies when: the "quality" of choosing k is unimodal — neither too small nor too large is optimal, and there's a sweet spot k* that maximizes (or minimizes) quality. The key structural difference: in binary search on answer, each candidate k is either "feasible" or "infeasible"; in ternary search on answer, every k produces a numerical quality score, and the function of scores is unimodal. Many problems that appear to need ternary search actually have a *monotone* feasibility condition and should use binary search (Koko Eating Bananas, Minimize Maximum Distance — the feasibility condition, not the optimal value itself, is monotone).

**Q25. State the invariant, termination condition, and update rules for ternary search in one sentence each.**

A:
- **Invariant (maximization)**: at the start of every step, the global maximum of the unimodal function is guaranteed to lie within the current range `[lo, hi]` — the eliminated thirds are proven to contain only sub-optimal points.
- **Invariant (minimization)**: same structure, but the global minimum lies within `[lo, hi]`.
- **Termination**: on a continuous domain, stop after a fixed number of iterations (100–200); on a discrete domain, stop when `hi - lo ≤ 2` and scan the remaining elements.
- **Update (maximization)**: if `f(m1) < f(m2)`, set `lo = m1 + 1` (discrete) or `lo = m1` (continuous); otherwise set `hi = m2 - 1` (discrete) or `hi = m2` (continuous).
- **Update (minimization)**: if `f(m1) > f(m2)`, set `lo = m1 + 1` (discrete) or `lo = m1` (continuous); otherwise set `hi = m2 - 1` (discrete) or `hi = m2` (continuous).

## Problem 1 — Find Peak Element

### Problem

A peak element is an element strictly greater than its neighbors. Given a 0-indexed array `nums` where `nums[-1] = nums[n] = -∞`, find any peak element's index. Must run in O(log n).

```
Input:  nums = [1, 2, 3, 1]        → 2    // nums[2]=3 > nums[1]=2 and nums[3]=1
Input:  nums = [1, 2, 1, 3, 5, 6, 4] → 5 // nums[5]=6 is a peak
Input:  nums = [1]                  → 0
```

### Pattern Recognition
Two approaches: **(A) Ternary search** — valid if the array is strictly unimodal; **(B) Binary search on discrete derivative** — valid for any array (finds any one of potentially many peaks). Approach B is superior for the general case of LC 162 (multiple peaks), using O(log₂ n) comparisons vs ternary search's O(log_{3/2} n) iterations.

### Key Insight
**Ternary search approach**: valid when the array has exactly one peak. Invariant: the peak lies in `[lo, hi]`. Compare `arr[m1]` vs `arr[m2]`; the smaller side cannot contain the global peak. **Binary search approach**: uses the sign of the discrete derivative at `mid` — if `nums[mid] < nums[mid+1]`, the slope at `mid` is positive, so the function is still rising, and a peak must exist to the right. The boundary condition `nums[-1] = -∞` guarantees a peak always exists in whichever half we recurse into.

### Solution

```js
// Approach A: Ternary search — works when array is STRICTLY unimodal (one peak)
function findPeakTernary(nums) {
  let lo = 0, hi = nums.length - 1;

  while (hi - lo > 2) {
    const m1 = lo + Math.floor((hi - lo) / 3);
    const m2 = hi - Math.floor((hi - lo) / 3);

    if (nums[m1] < nums[m2]) lo = m1 + 1; // peak is in (m1, hi]
    else                     hi = m2 - 1; // peak is in [lo, m2)
    // Equal case: lo = m1 + 1; hi = m2 - 1; (peak strictly between m1 and m2)
  }

  // Linear scan the ≤3 remaining elements
  let peak = lo;
  for (let i = lo + 1; i <= hi; i++) if (nums[i] > nums[peak]) peak = i;
  return peak;
}

// Approach B: Binary search on derivative — works for ANY array (LC 162's actual test)
function findPeakElement(nums) {
  let lo = 0, hi = nums.length - 1;

  while (lo < hi) {
    const mid = (lo + hi) >> 1;

    if (nums[mid] < nums[mid + 1]) {
      lo = mid + 1; // rising slope at mid → peak is to the right
    } else {
      hi = mid;     // falling slope at mid → peak is here or to the left
    }
  }

  return lo; // lo === hi: converged to a peak
}
// Invariant: at every step, a peak exists in [lo, hi].
// When nums[mid] < nums[mid+1]: the sequence rises from mid to mid+1.
// Since nums[n-1] > nums[n] = -∞, the sequence must eventually fall before n.
// Therefore a peak exists in [mid+1, hi]. Set lo = mid+1.
```

### Dry Run

```

lo=0, hi=3.

hi-lo=3>2: m1=0+1=1, m2=3-1=2.
  nums[m1]=nums[1]=2. nums[m2]=nums[2]=3. 2<3 → lo=m1+1=2.

hi-lo=1≤2: linear scan [2,3].
  nums[2]=3 vs nums[3]=1 → peak=2.
Return 2. ✓

Binary search: nums = [1,2,1,3,5,6,4]
lo=0, hi=6.

mid=3: nums[3]=3 < nums[4]=5 → lo=4.
mid=5: nums[5]=6 > nums[6]=4 → hi=5.
lo=hi=5 → return 5. ✓ (nums[5]=6 > nums[4]=5 and nums[6]=4 ✓)
```

### Complexity
- **Ternary search**: O(log_{3/2} n) iterations ≈ O(1.71 log₂ n), 2 comparisons each.
- **Binary search**: O(log₂ n) iterations, 1 comparison each.
- Space: O(1) for both.

### Edge Cases
- Length 1: `hi - lo = 0 ≤ 2` → linear scan returns 0 immediately.
- Monotone increasing: binary search converges at `hi`; ternary search converges at `hi`.
- Two elements: `hi - lo = 1 ≤ 2` → linear scan compares 2 elements.

### Follow-up Questions
- "What if there are multiple peaks and you need ALL of them?" — Linear scan O(n); binary search finds only one.
- "What if the array is circular (wrap-around)?" — Binary search still works; add modular index arithmetic.

## Problem 2 — Maximum of Unimodal Function on Continuous Domain

### Problem

Given a unimodal function `f(x)` on a closed interval `[lo, hi]` (first strictly increasing, then strictly decreasing), find the x value that maximizes f(x) to within precision 10⁻⁹.

```
f(x) = -(x - 3)² + 9  on  [0, 6]   →  x ≈ 3.000000000,  f(x) = 9
f(x) = sin(x)          on  [0, π]   →  x ≈ 1.570796327 (π/2),  f(x) = 1
f(x) = -x² + 6x - 5   on  [1, 5]   →  x ≈ 3.000000000,  f(x) = 4
```

### Pattern Recognition
Continuous-domain ternary search — the canonical application. No discrete indexing; probe at real-valued one-third and two-thirds positions; iterate a fixed number of times for precision.

### Key Insight
Each iteration multiplies the interval width by 2/3. After 200 iterations: `(2/3)^200 ≈ 10^{-35}` of the original width — far beyond double-precision floating point (10^{-15}). Using a fixed number of iterations (not an epsilon comparison) avoids floating-point termination bugs. The answer is the midpoint of the final `[lo, hi]` interval (which has width ~10^{-35}).

### Solution

```js
function maximizeUnimodal(f, lo, hi, iterations = 200) {
  for (let iter = 0; iter < iterations; iter++) {
    const m1 = lo + (hi - lo) / 3;
    const m2 = hi - (hi - lo) / 3;

    if (f(m1) < f(m2)) {
      lo = m1; // maximum is NOT in [lo, m1): move lo to m1
    } else {
      hi = m2; // maximum is NOT in (m2, hi]: move hi to m2
    }
    // No ±1: continuous domain, m1 and m2 are real-valued
  }

  return (lo + hi) / 2; // midpoint of tiny remaining interval
}

// Example: f(x) = -(x-3)² + 9
const f = x => -(x - 3) ** 2 + 9;
const xOpt = maximizeUnimodal(f, 0, 6);
const fOpt = f(xOpt);
// xOpt ≈ 3.0000000000 (within 10^-35 of true value 3)
// fOpt ≈ 9.0000000000

// Minimization: flip comparison to f(m1) > f(m2) → lo = m1
function minimizeConvex(f, lo, hi, iterations = 200) {
  for (let iter = 0; iter < iterations; iter++) {
    const m1 = lo + (hi - lo) / 3;
    const m2 = hi - (hi - lo) / 3;
    if (f(m1) > f(m2)) lo = m1; // minimum is not in [lo, m1)
    else               hi = m2; // minimum is not in (m2, hi]
  }
  return (lo + hi) / 2;
}
```

```
  m2 = 6 - 6/3 = 4.  f(4) = -(4-3)²+9 = -1+9 = 8.
```

- Time: O(iterations) = O(200) = O(1) iterations, each with 2 function evaluations.
- Space: O(1).
- Precision: `(2/3)^200 × (hi_0 - lo_0) ≈ 10^{-35} × initial_width`.

### Edge Cases
- Plateau at peak (weakly unimodal): both f(m1) and f(m2) equal the plateau value → the `else` branch shrinks `hi`, eventually narrowing to the plateau. The midpoint lands on the plateau. ✓
- Very narrow initial range: fewer iterations needed; 200 is always safe.
- Maximizing a function with very large values: floating-point arithmetic works correctly as long as the function values don't overflow or underflow.

### Follow-up Questions
- "How would you use Golden Section Search instead?" — Initialize m1 and m2 at `lo + (hi-lo)/φ²` and `lo + (hi-lo)/φ`; on each step, reuse the surviving midpoint and compute only one new one. Requires tracking which midpoint is reused.
- "100 or 200 iterations — which?" — 100 iterations gives `(2/3)^100 ≈ 2×10^{-18}` precision, already beyond double precision. 200 is overkill but harmless. Use 100 if the function is cheap, 50 if it's expensive.

## Problem 3 — Minimum Sum of Distances to Points

### Problem

Given `n` points on a number line with values `p[i]`, find the real number `x` that minimizes `f(x) = sum of |x - p[i]|` over all `i`.

```
Input:  p = [1, 3, 7, 9]   → x = 5.0 (median of 3 and 7), f(5) = 4+2+2+4 = 12
Input:  p = [2, 2, 2, 2]   → x = 2.0, f(2) = 0
Input:  p = [1, 10]        → any x in [1,10], f(x) = 9 (constant on the segment)
```

### Pattern Recognition
Convex function minimization via ternary search — `f(x) = sum |x - p[i]|` is a sum of absolute values, which is piecewise linear and convex. Its minimum is at the *median* of the points (known analytically), but ternary search finds it numerically in O(n log(range/ε)).

### Key Insight
`f(x) = sum |x - p[i]|` is convex: the derivative `f'(x) = count(p[i] < x) - count(p[i] > x)` is non-decreasing (transitions from negative to positive exactly at the median). Ternary search on `x ∈ [min(p), max(p)]` finds the minimum because f is unimodal (convex = unimodal for minimization). For even n, any x in `[p[n/2-1], p[n/2]]` achieves the minimum (flat region) — ternary search converges to any point in this flat region, which is correct.

### Solution

```js
function minSumDistances(points) {
  const n = points.length;

  // Cost function: sum of absolute distances to all points
  function cost(x) {
    return points.reduce((sum, p) => sum + Math.abs(x - p), 0);
  }

  // Ternary search on x ∈ [min(points), max(points)]
  let lo = Math.min(...points);
  let hi = Math.max(...points);

  for (let iter = 0; iter < 200; iter++) {
    const m1 = lo + (hi - lo) / 3;
    const m2 = hi - (hi - lo) / 3;

    if (cost(m1) > cost(m2)) lo = m1; // minimum is not in [lo, m1): move lo up
    else                     hi = m2; // minimum is not in (m2, hi]: move hi down
  }

  const xOpt = (lo + hi) / 2;
  return { x: xOpt, minCost: cost(xOpt) };
}

// Each cost() evaluation: O(n). Total: O(200n) = O(n × iterations).
// Alternatively, pre-sort and use the analytical median solution:
function minSumDistancesAnalytical(points) {
  const sorted = [...points].sort((a, b) => a - b);
  const median = sorted[Math.floor(sorted.length / 2)]; // lower median for even n
  return { x: median, minCost: sorted.reduce((sum, p) => sum + Math.abs(p - median), 0) };
}
```

### Dry Run

```

cost(x) = |x-1| + |x-3| + |x-7| + |x-9|.
Analytical minimum: median of [1,3,7,9] is any x in [3,7]. f(5) = 4+2+2+4 = 12.

Ternary search iteration 1: lo=1, hi=9.
  m1 = 1 + 8/3 ≈ 3.667.  cost(3.667) = 2.667+0.667+3.333+5.333 = 12.
  m2 = 9 - 8/3 ≈ 6.333.  cost(6.333) = 5.333+3.333+0.667+2.667 = 12.
  cost(m1) = cost(m2): else branch → hi = m2 ≈ 6.333.
  [1, 6.333], width ≈ 5.333.

Iteration 2: lo=1, hi≈6.333.

  m2 ≈ 6.333 - 1.778 ≈ 4.556. cost(4.556) = 3.556+1.556+2.444+4.444 = 12.
```

### Complexity
- Time: O(n × iterations) = O(200n) — each of 200 iterations evaluates cost in O(n).
- Space: O(1).

### Edge Cases
- All same points: `lo = hi`, loop doesn't execute → any x = lo is optimal.
- Two points: minimum anywhere in `[min, max]` — ternary search converges to the midpoint (valid).
- One point: minimum at that point.

### Follow-up Questions
- "Why not just compute the median?" — The median is the analytical answer for sum of |x - p_i|, O(n log n) to find. Ternary search is useful when the cost function is more complex (weighted distances, or when points are in a 2D plane where no clean analytic formula exists).
- "For sum of (x - p_i)² (squared distances)?" — Minimum is the *mean*, not the median. Still convex → ternary search works. But the mean is O(n) to compute analytically.

## Problem 4 — Find in Mountain Array

### Problem

A mountain array first strictly increases then strictly decreases. Given a `MountainArray` interface with `get(index)` and `length()`, find the index of a `target` value. If not found, return -1. Minimize calls to `get()`.

```
mountain = [1,2,3,4,5,3,1], target = 3  → 2  (also at index 5, but return smaller)
mountain = [0,1,2,4,2,1],   target = 3  → -1
mountain = [1,5,2],         target = 5  → 1  (the peak)
```

### Pattern Recognition
Two-phase algorithm: (1) ternary search to find the peak index; (2) binary search in the ascending left half; (3) if not found, binary search in the descending right half.

### Key Insight
The mountain array is strictly unimodal — ternary search finds the unique peak. Once the peak is found, the left half is a standard sorted (ascending) array and the right half is a reverse-sorted (descending) array — both support binary search. Return the smaller index if target is found in both halves (left half contains smaller indices).

### Solution

```js
/**
 * MountainArray interface: { get(idx) → value, length() → n }
 * Minimize calls to get().
 */
function findInMountainArray(target, mountainArr) {
  const n = mountainArr.length();

  // Phase 1: Find the peak using ternary search
  let lo = 0, hi = n - 1;
  while (hi - lo > 2) {
    const m1 = lo + Math.floor((hi - lo) / 3);
    const m2 = hi - Math.floor((hi - lo) / 3);
    if (mountainArr.get(m1) < mountainArr.get(m2)) lo = m1 + 1;
    else                                            hi = m2 - 1;
  }
  // Linear scan remaining ≤3 elements to find exact peak
  let peak = lo;
  for (let i = lo + 1; i <= hi; i++) {
    if (mountainArr.get(i) > mountainArr.get(peak)) peak = i;
  }

  // Phase 2: Binary search in ascending left half [0, peak]
  lo = 0; hi = peak;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    const val = mountainArr.get(mid);
    if      (val === target) return mid;   // found! return smaller index first
    else if (val < target)   lo = mid + 1;
    else                     hi = mid - 1;
  }

  // Phase 3: Binary search in descending right half [peak+1, n-1]
  lo = peak + 1; hi = n - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    const val = mountainArr.get(mid);
    if      (val === target) return mid;
    else if (val > target)   lo = mid + 1; // descending: larger values are to the left
    else                     hi = mid - 1;
  }

  return -1;
}
```

### Dry Run

```

lo=0, hi=6. hi-lo=6>2.
  m1=0+2=2, m2=6-2=4.
  get(2)=3, get(4)=5. 3<5 → lo=3.
lo=3, hi=6. hi-lo=3>2.
  m1=3+1=4, m2=6-1=5.
  get(4)=5, get(5)=3. 5>3 → hi=4.
lo=3, hi=4. hi-lo=1≤2. Linear scan [3,4].
  get(3)=4, get(4)=5. peak=4. ✓

Phase 2 — Binary search in [0,4] (ascending: [1,2,3,4,5]):
lo=0, hi=4.
  mid=2. get(2)=3 == target → return 2. ✓
```

### Complexity
- Phase 1 (ternary search): O(log_{3/2} n) calls to `get`.
- Phase 2 (binary search left): O(log n) calls.
- Phase 3 (binary search right): O(log n) calls.
- Total: O(log n) calls to `get`. With the constraint that `get` is expensive, this is optimal.

### Edge Cases
- Target is the peak: Phase 2 binary search finds it at exactly the peak index.
- Target only in right half: Phase 2 returns nothing, Phase 3 finds it.
- Target not present: both binary searches fail, return -1.
- Mountain of length 3 (minimum valid): `[a, peak, b]` — ternary search with initial `hi-lo=2` immediately does linear scan.

### Follow-up Questions
- "Use binary search on derivative instead of ternary for peak finding?" — Yes: compare `get(mid)` with `get(mid+1)`; if `get(mid) < get(mid+1)`, peak is to the right. O(log₂ n) calls vs ternary's O(log_{3/2} n) — fewer calls to the expensive `get`.
- "What if target appears multiple times?" — Return any valid index. For the smallest index, prioritize Phase 2 (left half) then Phase 3 (right half), returning the first match found.

## Problem 5 — Minimize Total Cost with Convex Function (Ternary on Answer)

### Problem

You manage a warehouse with `n = 100` tasks. Hiring `k` teams costs `A × k` (linear team overhead). Each team handles `n/k` tasks at a processing cost of `B × (n/k)` per task. Total cost: `C(k) = A × k + B × n / k`. Given `A = 5`, `B = 3`, `n = 100`, find the integer `k ∈ [1, 100]` minimizing `C(k)`.

```
C(k) = 5k + 300/k

C(1)  = 305.   C(5) = 85.   C(8) = 77.5   C(9) = 78.3   C(10) = 80.
Optimal: k=8, C(8)=77.5 (analytically: k*=√(300/5)=√60≈7.75, round to 7 or 8)
C(7) = 35+300/7 ≈ 35+42.86 = 77.86.   C(8) = 40+37.5 = 77.5. → k=8. ✓
```

### Pattern Recognition
Ternary search on a discrete answer space — the cost function `C(k) = A×k + B×n/k` is convex (first decreasing then increasing) because the team overhead increases linearly while the per-task cost decreases. The function is unimodal for minimization → ternary search on k ∈ [1, 100].

### Key Insight
`C(k) = A×k + B×n/k` is convex: its derivative `dC/dk = A - B×n/k²` equals zero at `k* = √(B×n/A)` and is negative for `k < k*` (C is decreasing) and positive for `k > k*` (C is increasing). This makes C unimodal with a single minimum — ternary search on integers finds it. The comparison `C(m1) > C(m2)` means the valley is toward m2 → eliminate the m1 side.

### Solution

```js
function minTotalCost(A, B, n) {
  // C(k) = A*k + B*n/k — convex in k, minimized at k = sqrt(B*n/A)
  function cost(k) {
    return A * k + B * n / k; // continuous approximation; use Math.ceil(n/k) for exact
  }

  let lo = 1, hi = n; // k must be in [1, n]

  // Ternary search for minimum of convex function on integers
  while (hi - lo > 2) {
    const m1 = lo + Math.floor((hi - lo) / 3);
    const m2 = hi - Math.floor((hi - lo) / 3);

    if (cost(m1) > cost(m2)) lo = m1 + 1; // valley is NOT in [lo, m1]
    else                     hi = m2 - 1; // valley is NOT in [m2, hi]
  }

  // Linear scan remaining ≤3 candidates
  let bestK = lo, bestC = cost(lo);
  for (let k = lo + 1; k <= hi; k++) {
    if (cost(k) < bestC) { bestC = cost(k); bestK = k; }
  }

  return { k: bestK, cost: bestC };
}

// With A=5, B=3, n=100:
const result = minTotalCost(5, 3, 100);
// result.k ≈ 8, result.cost ≈ 77.5
```

```
  C(15)=75+20=95. C(30)=150+10=160. C(m1)<C(m2): hi=29. [1,29].

```

### Complexity
- Time: O(log_{3/2}(hi - lo)) = O(log 100) ≈ O(12) iterations, each with 2 cost evaluations.
- Space: O(1).

### Edge Cases
- k* is exactly an integer: ternary search converges precisely.
- Multiple k values with equal cost: the linear scan finds the leftmost (smallest k).
- `n = 1`: only k=1 is valid; loop never executes; linear scan returns k=1.

### Follow-up Questions
- "What if `cost(k)` uses `Math.ceil(n/k)` (integer tasks)?" — The cost function becomes piecewise constant and still convex (stepwise, but with the same unimodal shape). Ternary search still works correctly.
- "Why can't we use binary search here?" — The cost function is NOT monotone; it decreases then increases. Binary search requires a monotone predicate ("is C(k) ≤ target?"). Ternary search handles the unimodal structure.
- "Analytic formula instead?" — `k* = round(√(B×n/A))`; check both `floor` and `ceil` values. O(1) but only works for this specific cost structure, not general unimodal functions.

## Problem 6 — Minimize Sum of Distances to Intervals (Generalized Ternary Search)

### Problem

Given `n` intervals `[a_i, b_i]` on the real line, find the real number `x` that minimizes `f(x) = sum of max(0, a_i - x) + max(0, x - b_i)` — the total "gap" between x and each interval (0 if x is inside the interval).

```
intervals = [[1,3],[5,7],[10,12]], target x minimizes total gap.
f(4) = 0 + max(0,5-4) + 0 = 1 + 0 + 0 = 1.   (inside [1,3] and [10,12]? No: 4>3, 4<5 so gap to [5,7] is 1)
f(4) = max(0,1-4)+max(0,4-3) + max(0,5-4)+max(0,4-7) + max(0,10-4)+max(0,4-12)
     = 0+1 + 1+0 + 6+0 = 8.  Hmm, let me recalculate.
f(x) = distance from x to interval = max(0, a-x) if x<a; max(0, x-b) if x>b; 0 if a≤x≤b.
f(4) = max(0,4-3)=1 + max(0,5-4)=1 + 0 = 2.   f(5) = 0 + 0 + max(0,10-5)=5 → 5.
f(4) is better. Optimal x is around 4-5 (between first two intervals).
```

### Pattern Recognition
Sum of convex distance functions → sum is convex → ternary search minimizes it. Each `max(0, a_i - x) + max(0, x - b_i)` is a convex piecewise linear "hinge" function. The sum of convex functions is convex → unimodal for minimization.

### Key Insight
`f(x)` is convex because it is a sum of convex functions. Its derivative is piecewise constant, transitioning from negative to positive at the optimal x. Ternary search finds the minimum of this convex function over any containing interval `[lo, hi]` (choose `lo = min(a_i)`, `hi = max(b_i)` or extend slightly).

### Solution

```js
function minSumGapToIntervals(intervals) {
  // f(x) = sum of distance from x to each interval [a_i, b_i]
  function distToInterval(x, [a, b]) {
    if (x < a) return a - x;
    if (x > b) return x - b;
    return 0;
  }

  function totalCost(x) {
    return intervals.reduce((sum, iv) => sum + distToInterval(x, iv), 0);
  }

  // Search over the range of all interval endpoints
  let lo = Math.min(...intervals.map(([a]) => a));
  let hi = Math.max(...intervals.map(([, b]) => b));

  // Ternary search for minimum of convex f(x)
  for (let iter = 0; iter < 200; iter++) {
    const m1 = lo + (hi - lo) / 3;
    const m2 = hi - (hi - lo) / 3;

    if (totalCost(m1) > totalCost(m2)) lo = m1; // minimum not in [lo, m1]
    else                               hi = m2; // minimum not in [m2, hi]
  }

  const xOpt = (lo + hi) / 2;
  return { x: xOpt, minCost: totalCost(xOpt) };
}
```

### Dry Run

```
  x=5: dist([1,3])=5-3=2. dist([5,7])=0. dist([10,12])=10-5=5. Total=7.
  x=6: dist([1,3])=6-3=3. dist([5,7])=0. dist([10,12])=10-6=4. Total=7.
```

### Complexity
- Time: O(n × 200) = O(200n) — each cost evaluation is O(n).
- Space: O(1).

### Edge Cases
- Single interval: optimal x is any point in `[a, b]`. Ternary search converges to the midpoint.
- Overlapping intervals: the optimal x may be inside all intervals (cost = 0).
- Intervals on a line with gaps: ternary search converges to the "center of mass" of the gap structure.

### Follow-up Questions
- "What if x must be an integer?" — Discrete ternary search on integer range `[lo, hi]`, then linear scan.
- "What if the intervals are 2D rectangles?" — Use 2D ternary search: minimize total gap in x-direction, then y-direction independently (valid if the 2D function is separable).

## Problem 7 — Optimal Meeting Point (2D Ternary Search)

### Problem

Given `n` people at 2D coordinates `(x_i, y_i)`, find the location `(x, y)` minimizing the maximum Euclidean distance from `(x, y)` to any person (the minimax problem).

```
points = [(0,0),(6,0),(3,4)]
Optimal location: (3, 1.33...) approximately — the circumcenter of the triangle.
```

### Pattern Recognition
2D ternary search — for a fixed x, the function `g(x) = min_y max_i dist((x,y),(x_i,y_i))` is unimodal in y (for any fixed x). The outer function `h(x) = min_y g(x,y)` is unimodal in x. Apply ternary search on y (inner) for each probe x in the outer ternary search on x.

### Key Insight
The minimax distance function `f(x, y) = max_i sqrt((x-x_i)² + (y-y_i)²)` is *convex* in (x, y) — it is the maximum of convex (linear in squared sense) functions. A convex function on a compact convex domain has a unique minimum. For a fixed x, the optimal y can be found by ternary search on y; the resulting one-dimensional function of x is also unimodal. The 2D ternary search applies because of this joint unimodality structure.

### Solution

```js
function optimalMeetingPoint(points) {
  // f(x, y) = maximum Euclidean distance from (x,y) to any point
  function maxDist(x, y) {
    return Math.max(...points.map(([px, py]) =>
      Math.sqrt((x - px) ** 2 + (y - py) ** 2)
    ));
  }

  // Inner ternary search: for fixed x, find y minimizing maxDist(x, y)
  function bestY(x) {
    let lo = Math.min(...points.map(([, y]) => y));
    let hi = Math.max(...points.map(([, y]) => y));
    for (let i = 0; i < 200; i++) {
      const m1 = lo + (hi - lo) / 3;
      const m2 = hi - (hi - lo) / 3;
      if (maxDist(x, m1) > maxDist(x, m2)) lo = m1;
      else                                  hi = m2;
    }
    return (lo + hi) / 2;
  }

  // Outer ternary search: find x minimizing the best-y cost
  let xLo = Math.min(...points.map(([x]) => x));
  let xHi = Math.max(...points.map(([x]) => x));

  for (let i = 0; i < 200; i++) {
    const xm1 = xLo + (xHi - xLo) / 3;
    const xm2 = xHi - (xHi - xLo) / 3;

    // For each probe x, find its optimal y and compute the resulting cost
    const cost1 = maxDist(xm1, bestY(xm1));
    const cost2 = maxDist(xm2, bestY(xm2));

    if (cost1 > cost2) xLo = xm1;
    else               xHi = xm2;
  }

  const xOpt = (xLo + xHi) / 2;
  const yOpt = bestY(xOpt);
  return { x: xOpt, y: yOpt, minMaxDist: maxDist(xOpt, yOpt) };
}
// Complexity: O(200 × 200 × n) outer_iters × inner_iters × cost_eval
// = O(40000n) ≈ O(n) for fixed iteration counts
```


### Complexity
- Time: O(200 × 200 × n) = O(40000n) — outer loop × inner loop × cost evaluation.
- Space: O(1).

### Edge Cases
- All points at the same location: optimal meeting point is that location, min-max distance = 0.
- Two points: optimal is the midpoint, min-max distance = half the Euclidean distance.
- Points form a regular polygon: optimal center is the centroid.

### Follow-up Questions
- "Minimize *sum* of distances instead of *maximum* distance?" — Sum of Euclidean distances is convex but not separable; 2D ternary search still applies (the function is jointly convex), but the optimal point is generally not the centroid (unlike sum of squared distances, whose minimum is the centroid).
- "Weighted meeting point (person i costs w_i per unit distance)?" — Replace the objective with weighted max: `max_i w_i × dist((x,y), (x_i,y_i))`. Still convex → 2D ternary search applies unchanged; just update the cost function.

## Quick Reference — Pattern Decision Tree

```
Is ternary search the right tool?
│
├── FUNCTION IS MONOTONE (always increasing OR always decreasing)?
│   └── Binary search — not ternary search.
│       Monotone predicate → binary search on the boundary.
│       Monotone derivative → binary search on the sign of derivative.
│
├── FUNCTION IS UNIMODAL (rises to a single peak then falls, or vice versa)?
│   ├── On a CONTINUOUS domain [lo, hi]?
│   │   └── Ternary search: iterate 100–200 times.
│   │       m1=lo+(hi-lo)/3; m2=hi-(hi-lo)/3.
│   │       max: if f(m1)<f(m2): lo=m1  else hi=m2.
│   │       min: if f(m1)>f(m2): lo=m1  else hi=m2.
│   │       Answer: (lo+hi)/2 at termination.
│   │
│   ├── On a DISCRETE domain [lo, hi] (integers)?
│   │   └── Ternary search: loop while hi-lo>2.
│   │       m1=lo+floor((hi-lo)/3); m2=hi-floor((hi-lo)/3).
│   │       max: f(m1)<f(m2)→lo=m1+1  else hi=m2-1.
│   │       min: f(m1)>f(m2)→lo=m1+1  else hi=m2-1.
│   │       Linear scan remaining ≤3 elements.
│   │
│   └── Derivative is AVAILABLE (compare adjacent elements or evaluate f')?
│       └── Binary search on derivative: faster than ternary search.
│           Discrete: f(mid)<f(mid+1)→lo=mid+1  else hi=mid.
│           Continuous: f'(mid)>0→lo=mid  else hi=mid.
│
├── CONVEX COST FUNCTION C(k) with unimodal shape?
│   ├── "Too few → high cost. Too many → high cost." → ternary search on k.
│   │   C(k)=A×k+B/k, or sum of increasing+decreasing components.
│   ├── Is C(k) monotone?  → binary search instead (simpler, faster).
│   └── Is C(k) bimodal?   → ternary search fails; use exhaustive search.
│
├── ARRAY PROBLEM: find peak in a unimodal array?
│   ├── Strictly unimodal (one peak) → ternary search OR binary on derivative.
│   └── Any peak in arbitrary array (LC 162) → binary on derivative only.
│
├── 2D UNIMODAL FUNCTION f(x,y)?
│   └── Outer ternary on x; inner ternary on y for each probe x.
│       O(log²n) evaluations total.
│       Valid only if f is unimodal in x for fixed y, AND in y for fixed x.
│
└── HOW MANY ITERATIONS?
    Continuous domain:  100–200 iterations (always safe).
    Discrete domain:    ~log_{3/2}(n) = 1.71×log₂(n) iterations.
    Precision:          (2/3)^100 ≈ 10^-18 — beyond double precision.
```

## Common Bugs Checklist

Before submitting any ternary search solution, verify:

1. **Using binary search when the function is monotone (not unimodal)?** — Binary search is for monotone functions (transition from "no" to "yes"); ternary search is for unimodal functions (single peak or valley). Applying ternary search to a monotone function may return a sub-optimal answer, converging to the wrong extreme. If `C(k)` only ever decreases as `k` increases, use binary search (`if feasible(k): hi=k else lo=k+1`), not ternary.

2. **Wrong midpoint formula causing no progress?** — The correct formulas are `m1 = lo + floor((hi - lo) / 3)` and `m2 = hi - floor((hi - lo) / 3)`. Using `(lo + hi) / 3` for m1 (not offset from lo) is wrong — it can place m1 outside `[lo, hi]`. On continuous domains, omit `Math.floor`. The check: after computing m1 and m2, verify `lo < m1 < m2 < hi` (strictly for continuous).

3. **Infinite loop on discrete domain when `hi - lo == 2`?** — With `hi - lo = 2`, the formula gives `m1 = lo + 0 = lo` and `m2 = hi - 0 = hi`. Comparing f(lo) and f(hi) sets `lo = lo + 1` or `hi = hi - 1`, making progress — but the *next* iteration will also stall. The safe fix: terminate when `hi - lo ≤ 2` and do a linear scan of the remaining (at most 3) elements. Never use `while (lo < hi)` for discrete ternary search.

4. **Update direction swapped for minimization vs maximization?** — For **maximization**: if `f(m1) < f(m2)`, the peak is toward m2 → `lo = m1 + 1` (eliminate left third). For **minimization**: if `f(m1) > f(m2)`, the valley is toward m2 → wait — actually: if `f(m1) > f(m2)`, the valley is closer to m2 (m2 has lower cost) → eliminate the m1 side: `lo = m1 + 1`. So: **minimization and maximization use the SAME comparison direction** but the cost interpretation differs. Concretely: `if (f(m1) [worse than] f(m2)): eliminate m1 side (lo = m1+1)`. "Worse" means larger for minimization OR smaller for maximization.

5. **Not handling the equal case `f(m1) == f(m2)` for weakly unimodal functions?** — For strictly unimodal functions, `f(m1) == f(m2)` implies the peak is strictly between m1 and m2. Treating this as either `f(m1) < f(m2)` or `f(m1) > f(m2)` (i.e., the `else` branch) is correct and converges. For weakly unimodal functions with extended flat peaks, the equal case should set `lo = m1 + 1; hi = m2 - 1` to prevent stalling. Omitting this special case causes infinite loops on flat-peaked discrete arrays.

6. **Applying ternary search to a non-unimodal function and trusting the result?** — Ternary search converges silently even on non-unimodal functions — it just converges to the *wrong* answer. If the function has multiple local optima, ternary search returns one of them (whichever the initial search range happens to converge to) without any indication of failure. Always verify unimodality before applying ternary search; a spot check at 5–10 evenly spaced values revealing a non-monotone pattern is a warning sign.

7. **Using epsilon comparison instead of fixed iterations on continuous domains?** — `while (hi - lo > 1e-9)` can fail to terminate if floating-point arithmetic causes `hi - lo` to stagnate at a value just above `1e-9` due to precision limits. Use a fixed iteration count (100–200) instead — it always terminates and provides far more precision than double-precision floating point can represent.

8. **2D ternary search on a non-separable non-unimodal function?** — 2D ternary search requires the function to be unimodal in x for every fixed y AND in y for every fixed x. If the function has a saddle point or multiple local optima, 2D ternary search may converge to the wrong point. Verify the mathematical property (e.g., convexity of the objective) before applying 2D ternary search.

9. **Wrong search range for ternary search on answer?** — The search range `[lo, hi]` must contain the optimal answer k*. Using `lo = 0` (when k must be ≥ 1) or `hi = n - 1` (when the optimal k can equal n) causes the algorithm to converge to the boundary rather than the true optimum. Always set `lo` and `hi` to include all valid candidate values of k, including the boundaries.

10. **Confusing "ternary search on the answer" with binary search on answer?** — If the cost function is *monotone* (always decreasing or always increasing), binary search applies ("find the threshold"). If the cost function is *unimodal* (decreases then increases, or vice versa — a sweet spot exists), ternary search applies. Applying binary search to a unimodal function: the binary search would converge to a boundary of the search range, giving the wrong answer. Applying ternary search to a monotone function: ternary search would also converge, but in O(log_{3/2} n) evaluations instead of O(log₂ n) — slower and more complex for no benefit.

---

**Final Tip:** At the 5 YOE level, the decisive signal for any ternary search question is naming *what makes the function unimodal and why the elimination is valid*. For a peak in an array: *"if f(m1) < f(m2), the peak cannot be at or before m1 — because if it were, then m2 > m1 is in the strictly decreasing region, making f(m2) < f(m1), contradicting our observation. Therefore the peak is strictly in (m1, hi], and eliminating [lo, m1] is safe."* For a convex cost function C(k) = A×k + B/k: *"C is convex because its second derivative is positive, meaning C decreases then increases with a single minimum at k* = √(B/A) — the sum of a linearly increasing term and a hyperbolically decreasing term creates exactly one valley. Ternary search correctly converges to this valley because the elimination logic exploits the unimodal structure: the third containing the higher-cost probe is always sub-optimal."* And the critical distinction from binary search: *"binary search finds where a monotone predicate transitions from false to true; ternary search finds where a unimodal function achieves its extremum — the structural difference is a slope that reverses direction once (unimodal) vs a condition that flips exactly once (monotone). When you can write 'too small hurts, too large hurts, there's a sweet spot,' think ternary; when you can write 'once it becomes feasible, it stays feasible,' think binary."*
