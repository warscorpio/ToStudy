## Topic A: Heap Fundamentals

### Section A1: Fundamentals

**Q1. What is a binary heap, and what two structural properties define it?**
A: A binary heap is a complete binary tree that satisfies the heap property. Two structural invariants define it:

- **Shape property (structural completeness)**: all levels are completely filled except possibly the last level, which is filled from left to right with no gaps. This ensures the tree height is always `floor(log₂ n)` — a heap of n elements is always O(log n) tall.
- **Heap property (ordering)**: in a **max-heap**, every node's value is ≥ the values of its children. In a **min-heap**, every node's value is ≤ the values of its children. This property holds for every node recursively — the root is always the maximum (max-heap) or minimum (min-heap) of the entire collection.

```
Valid max-heap:          Invalid (violates heap property):
        9                         5
       / \                       / \
      7   6                     9   6    ← 9 > 5 violates max-heap
     / \ /                     / \
    4  5 2                    4   3

Valid (shape correct, property correct)   Shape correct, property violated at root
```

**Q2. How is a binary heap represented as an array, and what are the index relationships?**
A: A binary heap is stored in a 1D array (0-indexed) without any pointers. The complete binary tree structure maps directly to array positions via these index formulas:

For a node at index `i`:
- **Left child**: `2*i + 1`
- **Right child**: `2*i + 2`
- **Parent**: `floor((i - 1) / 2)` (or `(i - 1) >> 1` using bitwise shift)

```
Array: [9, 7, 6, 4, 5, 2, 3]
Index:  0  1  2  3  4  5  6

Tree representation:
            9 (idx 0)
           / \
      7 (1)   6 (2)
      / \     / \
   4(3) 5(4) 2(5) 3(6)

Left child of 0: 2*0+1 = 1 (value 7) ✓
Right child of 0: 2*0+2 = 2 (value 6) ✓
Parent of 3: (3-1)/2 = 1 (value 7) ✓
```

This array representation is cache-friendly (contiguous memory), eliminates pointer overhead (no left/right/parent pointers per node), and makes the parent-child relationship purely arithmetic — a key reason heap operations are fast in practice despite O(log n) theoretical complexity.

**Q3. What are the two fundamental heap operations, and what is each one's time complexity?**
A: The two atomic operations are:

**Sift-down (heapify-down)**: fix a heap where only the root (or a specific node) may violate the heap property — its subtrees are valid heaps. Compare the node with its children; if it's smaller than the larger child (max-heap), swap with that child and recurse. Traverses downward toward leaves. O(log n) — at most one comparison per level, and the tree has log n levels.

```js
function siftDown(arr, n, i) {
  let largest = i;
  const left = 2*i + 1, right = 2*i + 2;

  if (left < n && arr[left] > arr[largest])   largest = left;
  if (right < n && arr[right] > arr[largest])  largest = right;

  if (largest !== i) {
    [arr[i], arr[largest]] = [arr[largest], arr[i]]; // swap
    siftDown(arr, n, largest);  // recurse down
  }
}
```

**Sift-up (heapify-up)**: fix a heap where a newly inserted leaf may violate the heap property. Compare the node with its parent; if it's larger (max-heap), swap and continue upward. Traverses upward toward root. O(log n) — at most log n levels.

```js
function siftUp(arr, i) {
  while (i > 0) {
    const parent = (i - 1) >> 1;
    if (arr[parent] < arr[i]) {
      [arr[i], arr[parent]] = [arr[parent], arr[i]];
      i = parent;
    } else break;
  }
}
```

**Q4. What is the difference between building a heap via repeated insertion (top-down) vs. Floyd's algorithm (bottom-up), and why does Floyd's achieve O(n)?**
A: Two strategies for building a heap from an unsorted array of n elements:

**Top-down (repeated insertion)**: insert elements one by one, each requiring a sift-up of O(log n). Total: O(n log n) — n insertions × O(log n) each.

**Floyd's algorithm (bottom-up)**: start from the last internal node `floor(n/2) - 1` and sift-down each node to its correct position, working right-to-left toward the root. Total: O(n) — counterintuitively faster.

The O(n) proof: most nodes are near the leaves and require very few sift-down steps. Specifically, at height `h` (from the bottom), there are at most `n/2^(h+1)` nodes, each requiring O(h) sift-down work. Total work = `Σ_{h=0}^{log n} (n/2^(h+1)) * h = n * Σ_{h=0}^{∞} h/2^(h+1) = n * 1 = O(n)` (the series converges to 1).

```js
// Floyd's algorithm: O(n) heap construction
function buildHeap(arr) {
  const n = arr.length;
  // Start from last internal node, sift down each node
  for (let i = Math.floor(n / 2) - 1; i >= 0; i--) {
    siftDown(arr, n, i);
  }
}
// Leaf nodes (indices n/2 to n-1) are trivially valid heaps — skip them.
```

**Q5. What is heap sort, and what are its key properties compared to other O(n log n) sorts?**
A: Heap sort is a comparison-based sorting algorithm that works in two phases:
1. **Build phase**: transform the input array into a max-heap in O(n) using Floyd's algorithm.
2. **Sort phase**: repeatedly extract the maximum (swap root with last element, reduce heap size by 1, sift-down the new root) to produce a sorted array in O(n log n).

Key properties and comparisons:

| Property | Heap Sort | Merge Sort | Quick Sort |
|---|---|---|---|
| Time (worst) | O(n log n) | O(n log n) | O(n²) |
| Time (average) | O(n log n) | O(n log n) | O(n log n) |
| Space | O(1) | O(n) | O(log n) avg |
| Stable | ❌ No | ✅ Yes | ❌ No (typical) |
| Cache friendly | ❌ Poor | ✅ Good | ✅ Good |
| In-place | ✅ Yes | ❌ No | ✅ Yes |

Heap sort's guaranteed O(n log n) worst case with O(1) extra space is its defining advantage. Its practical disadvantage is poor cache locality — sift-down accesses array elements far apart in memory (parent at index i, children at 2i+1, 2i+2), causing frequent cache misses. This makes heap sort slower than quick sort and merge sort in practice despite identical asymptotic complexity.

### Section A2: Advanced Patterns

**Q6. Walk through the complete heap sort algorithm on a concrete example.**
A: Sorting `[4, 10, 3, 5, 1]` in ascending order using a max-heap:

**Phase 1 — Build max-heap** (Floyd's, starting from last internal node = index 1):

```
Initial array: [4, 10, 3, 5, 1]
Tree:     4
         / \
       10    3
      / \
     5    1

Last internal node: floor(5/2)-1 = 1 (value 10)

Sift-down index 1 (value 10):
  children: left=3 (val 5), right=4 (val 1). 10 > both → no swap.

Sift-down index 0 (value 4):
  children: left=1 (val 10), right=2 (val 3). 10 is largest → swap 4 and 10.
  Array: [10, 4, 3, 5, 1]
  Recurse at index 1 (value 4):
    children: left=3 (val 5), right=4 (val 1). 5 > 4 → swap 4 and 5.
    Array: [10, 5, 3, 4, 1]

Max-heap built: [10, 5, 3, 4, 1]
```

**Phase 2 — Sort** (extract max n-1 times):

```
Iteration 1: swap arr[0]=10 with arr[4]=1. Reduce heap size to 4.
  Array: [1, 5, 3, 4 | 10]. Sift-down [1,5,3,4]:
  1 < 5 → swap. [5, 1, 3, 4 | 10]. Sift-down at idx 1: 1 < 4 → swap. [5, 4, 3, 1 | 10]

Iteration 2: swap arr[0]=5 with arr[3]=1. Reduce to 3.
  Array: [1, 4, 3 | 5, 10]. Sift-down [1,4,3]:
  1 < 4 → swap. [4, 1, 3 | 5, 10]. Sift-down at idx 1: no children to swap.

Iteration 3: swap arr[0]=4 with arr[2]=3. Reduce to 2.
  Array: [3, 1 | 4, 5, 10]. Sift-down [3,1]: 3 > 1 → no swap.

Iteration 4: swap arr[0]=3 with arr[1]=1. Reduce to 1.
  Array: [1 | 3, 4, 5, 10]. Heap size 1 → done.

Final sorted array: [1, 3, 4, 5, 10] ✓
```

**Q7. Why is heap sort not stable, and can it be made stable?**
A: Heap sort is not stable because the sift-down and swap operations move elements to distant positions, breaking the relative order of equal elements. When two equal elements exist, the swap in the sort phase (moving the root to the end) can place one equal element before the other in any order — there is no mechanism to preserve original relative order.

Making heap sort stable: one approach is to augment each element with its original index, treating `(value, originalIndex)` as the comparison key. Two elements with equal values are ordered by their original index — this enforces stability. The cost: O(n) extra space for the augmented pairs and slightly higher comparison overhead. In practice, if stability is required, merge sort is the standard choice — stable heap sort is a theoretical curiosity, not a practical technique.

**Q8. What is a d-ary heap, and how does it trade off between sift-up and sift-down costs?**
A: A d-ary heap generalizes the binary heap to d children per node instead of 2. The index formulas for a 0-indexed d-ary heap:
- **Children of node i**: `d*i + 1, d*i + 2, ..., d*i + d`
- **Parent of node i**: `floor((i - 1) / d)`

Trade-offs:
- **Sift-up**: O(log_d n) comparisons — fewer levels (height = log_d n instead of log₂ n). Faster for insertion-heavy workloads.
- **Sift-down**: O(d · log_d n) comparisons — fewer levels but d comparisons per level (find the maximum among d children). Slower for extract-max-heavy workloads.
- **Cache behavior**: d=4 (4-ary heap) often outperforms binary heap in practice because of better cache line utilization — all children of a node fit in one or two cache lines.

Dijkstra's algorithm benefits from d-ary heaps: it performs many decrease-key operations (sift-up) and relatively fewer extract-min operations (sift-down). A 4-ary or higher-arity heap reduces the total sift-up cost.

**Q9. What is the relationship between heap sort and the selection problem?**
A: The selection problem asks: find the kth largest (or smallest) element in an unsorted array. Heap sort directly solves this: build a max-heap in O(n), then extract the maximum k times — the kth extraction gives the kth largest element. Total: O(n + k log n).

For k = 1 (find the maximum): O(n) — just scan the array (or read the heap root).
For k = n (find the minimum in a max-heap): O(n log n) — extract all elements.
For k = O(n/log n): O(n) — building the heap dominates.

The quickselect algorithm (partition-based) achieves O(n) average for fixed k, but heap-based selection is simpler to implement and gives O(n + k log n) worst-case — useful when k is small and worst-case guarantees matter.

**Q10. What is a "heap-ordered" property violation, and how does sift-down restore it?**
A: A heap-ordered property violation occurs when a node's value is smaller than one or both of its children (in a max-heap) — it's in the "wrong" position relative to its subtree. Sift-down restores the heap property by:

1. Identifying the largest among the node and its children.
2. If the node is already the largest, it's in the right place — stop.
3. Otherwise, swap the node with its largest child — the violation moves one level down.
4. Repeat at the child's position until no violation exists or a leaf is reached.

The invariant maintained: after sift-down at node `i`, the subtree rooted at `i` satisfies the heap property. This invariant is what Floyd's algorithm exploits: by sifting down from the last internal node upward, each sift-down operation assumes both subtrees of the current node are already valid heaps (established by previous sift-down calls on their subtree roots) — making the sift-down correct by induction.

## Topic B: Heap Sort Implementation Details

### Section B1: Fundamentals

**Q11. What is the iterative vs. recursive implementation of sift-down, and which is preferred?**
A: Both are correct, but the iterative version is preferred in production for two reasons: (1) no call stack overhead (each sift-down traverses O(log n) levels — n sift-down calls in the sort phase → O(n log n) recursive calls), and (2) easier to optimize with compiler/JIT.

```js
// Recursive sift-down (clean, educational):
function siftDownRecursive(arr, n, i) {
  let largest = i;
  const l = 2*i+1, r = 2*i+2;
  if (l < n && arr[l] > arr[largest]) largest = l;
  if (r < n && arr[r] > arr[largest]) largest = r;
  if (largest !== i) {
    [arr[i], arr[largest]] = [arr[largest], arr[i]];
    siftDownRecursive(arr, n, largest);
  }
}

// Iterative sift-down (preferred in practice):
function siftDownIterative(arr, n, i) {
  while (true) {
    let largest = i;
    const l = 2*i+1, r = 2*i+2;
    if (l < n && arr[l] > arr[largest]) largest = l;
    if (r < n && arr[r] > arr[largest]) largest = r;
    if (largest === i) break; // heap property satisfied — stop
    [arr[i], arr[largest]] = [arr[largest], arr[i]];
    i = largest; // move down and continue
  }
}
```

**Q12. What is the exact number of comparisons performed during heap sort, and how does it compare to merge sort?**
A: Heap sort performs approximately:
- **Build phase**: at most `2n` comparisons (Floyd's algorithm).
- **Sort phase**: at most `2n log₂ n` comparisons (n-1 extract-max operations, each requiring at most 2 log₂ n comparisons — 2 per level, one to find the largest child, one to compare with parent).
- **Total**: approximately `2n log₂ n + 2n` comparisons.

Merge sort performs approximately `n log₂ n` comparisons — roughly half as many. This 2× overhead in heap sort comes from the two comparisons per sift-down level (one to find the larger child, one to compare with the parent). This is a key practical disadvantage of heap sort that its O(n log n) notation doesn't reveal. Some implementations use a "tournament tree" structure to reduce comparisons to `n log₂ n + O(n)`, but at the cost of implementation complexity.

**Q13. How does heap sort behave on already-sorted or reverse-sorted input?**
A: Unlike quicksort (which degrades to O(n²) on sorted input with naive pivot selection), heap sort maintains O(n log n) in all cases:

**Already-sorted input** `[1, 2, 3, ..., n]`:
- Build phase: many sift-down operations needed (the min-to-max order is far from a max-heap). Still O(n).
- Sort phase: same as any other input — O(n log n).

**Reverse-sorted input** `[n, n-1, ..., 2, 1]`:
- Build phase: nearly a max-heap already — few sift-down operations needed. Still O(n).
- Sort phase: same O(n log n).

Heap sort has no "best case" in the usual sense — the constant factor in the O(n log n) doesn't significantly improve on special inputs. This is both a strength (predictable performance) and a weakness (can't exploit existing structure like Timsort does with nearly-sorted input).

**Q14. What is the "bottom-up heap sort" optimization, and how does it reduce comparisons?**
A: Standard sift-down performs 2 comparisons per level: (1) find the larger child, (2) compare the larger child with the parent. The bottom-up optimization defers step (2): during sift-down, always promote the larger child (skip the parent comparison), then when a leaf is reached, perform a single sift-up from the leaf to find where the element truly belongs.

This halves the number of comparisons in the sift-down path: instead of 2 comparisons per level for log n levels (2 log n per sift-down), the descent uses 1 comparison per level (log n total), then the sift-up uses 1 comparison per level for a few levels (typically very few, since elements usually settle near the bottom). In practice, this reduces the sort phase from ~2n log n to ~n log n comparisons — matching merge sort's comparison count.

```js
function siftDownBottomUp(arr, n, i) {
  // Descend to leaf, always taking the larger child:
  let j = i;
  while (2*j+1 < n) {
    const l = 2*j+1, r = 2*j+2;
    j = (r < n && arr[r] > arr[l]) ? r : l; // no comparison with parent — just take larger child
  }
  // j is now a leaf. Sift UP from this leaf to find correct position for arr[i]:
  const val = arr[i];
  while (j > i && arr[j] < val) j = (j-1) >> 1; // wait: this needs to sift val up, not arr[j]
  // Actual bottom-up: place val at correct position along path from leaf to root
  // (The implementation details vary — this is the concept)
}
```

### Section B2: Advanced Patterns

**Q15. How is heap sort used to implement an in-place priority queue, and what operations does this enable?**
A: The heap data structure underlying heap sort directly implements a priority queue — a queue where elements are dequeued in priority order (highest priority first). In-place heap operations on an array:

- **Insert** (push): append to end, sift-up. O(log n).
- **Extract-max** (pop): swap root with last element, reduce size, sift-down. O(log n).
- **Peek-max**: read `arr[0]`. O(1).
- **Decrease-key**: update value, then either sift-up (if increased) or sift-down (if decreased). O(log n).
- **Build from unsorted array**: Floyd's algorithm. O(n).

The connection to heap sort: heap sort's sort phase is exactly "extract-max n times from the priority queue formed in the build phase." The sorted output lands in the same array as the heap — the "sorted region" grows from right to left as elements are extracted.

**Q16. What is the "heap sort + insertion sort" hybrid approach (Introsort), and why is it used in practice?**
A: Introsort (introspective sort) is a hybrid used in C++ STL (`std::sort`), .NET, and other standard libraries:
1. Start with quicksort (fast in practice due to cache locality and small constant).
2. Monitor the recursion depth. If depth exceeds `2 * log₂ n`, switch to heap sort for the current partition.
3. For small subarrays (size ≤ 16), switch to insertion sort (low overhead for tiny arrays).

This hybrid gets: quicksort's average-case speed (O(n log n) with excellent cache behavior), heap sort's worst-case guarantee (prevents O(n²) degeneration), and insertion sort's efficiency for small arrays. Introsort achieves O(n log n) worst case with near-quicksort practical performance — the best of all three algorithms.

## Topic C: Heap Applications Beyond Sorting

### Section C1: Fundamentals

**Q17. What is the "kth largest element" problem, and what is the optimal heap-based solution?**
A: Find the kth largest element in an unsorted array. Three heap-based approaches:

**Approach 1 — Max-heap, extract k times**: build max-heap in O(n), extract-max k times in O(k log n). Total: O(n + k log n). Best when k is small.

**Approach 2 — Min-heap of size k**: maintain a min-heap of the k largest elements seen so far. For each element: if heap size < k, insert. If element > heap minimum (root), replace root with element and sift-down. After processing all n elements, the heap root is the kth largest. O(n log k) time, O(k) space. Best when k is much smaller than n and memory matters.

**Approach 3 — Quickselect**: partition-based, O(n) average. Best average case but O(n²) worst case without randomization.

```js
// Approach 2: min-heap of size k
function findKthLargest(nums, k) {
  // Simulate min-heap using max-heap on negated values, or use a proper min-heap
  // Here: maintain k largest in a max-heap, then pop n-k times
  heapSort(nums); // sort ascending
  return nums[nums.length - k]; // kth from end = kth largest
  // Real solution uses a size-k min-heap for O(n log k)
}
```

**Q18. What is the "top k frequent elements" problem, and how does a heap solve it efficiently?**
A: Given an array, find the k elements that appear most frequently. Two steps:
1. Build a frequency map in O(n).
2. Find the k entries with highest frequency — use a min-heap of size k over `(frequency, element)` pairs. Process each distinct element: if heap size < k, insert; if frequency > heap minimum's frequency, replace heap minimum and sift-down. Final heap contains the top-k frequent elements.

Total: O(n + d log k) where d = number of distinct elements. For the special case where all elements are distinct (d = n), this is O(n log k) — better than O(n log n) when k << n.

Alternative: bucket sort by frequency achieves O(n) — see the guide on frequency counting patterns.

**Q19. What is the "merge k sorted arrays" problem, and how does a heap solve it optimally?**
A: Given k sorted arrays with a total of n elements, merge them into one sorted array. Heap approach:
1. Build a min-heap of size k containing the first element from each array (along with its array index and element index within that array).
2. Repeatedly: extract the minimum element from the heap, add it to the output, then insert the next element from the same array (if any) into the heap.
3. Repeat until the heap is empty.

Total: O(n log k) — n extractions × O(log k) per extraction. Space: O(k) for the heap + O(n) for the output. This is optimal for this problem — any comparison-based merge of k sorted arrays must do Ω(n log k) comparisons.

```js
function mergeKSortedArrays(arrays) {
  // Min-heap entries: [value, arrayIdx, elementIdx]
  const heap = [];
  for (let i = 0; i < arrays.length; i++) {
    if (arrays[i].length > 0) heap.push([arrays[i][0], i, 0]);
  }
  buildMinHeap(heap); // or insert one by one with sift-up

  const result = [];
  while (heap.length > 0) {
    const [val, ai, ei] = extractMin(heap);
    result.push(val);
    if (ei + 1 < arrays[ai].length) {
      insertMin(heap, [arrays[ai][ei + 1], ai, ei + 1]);
    }
  }
  return result;
}
```

**Q20. What is the "sliding window maximum" problem, and why is a monotonic deque preferred over a heap?**
A: Find the maximum in every sliding window of size k over an array. A max-heap approach: maintain a max-heap of (value, index) pairs. For each new window, insert the new element and remove elements whose indices fall outside the window. O(n log k) time.

However, a monotonic deque achieves O(n) — strictly better. The deque maintains indices in decreasing order of their values. For each new element: remove indices from the back while the back's value ≤ new element (they can never be the maximum while the new element is in the window). Remove indices from the front that fall outside the current window. The front is always the maximum.

The deque beats the heap because: the heap must explicitly remove out-of-window elements (O(log k) each), while the deque lazily removes them from the front in O(1) amortized. The deque's monotonic property also eliminates the need to search for elements to remove — expired elements naturally fall off the front. This is a general lesson: O(n log k) heap solutions can often be beaten by O(n) deque solutions for sliding window problems when the window slides monotonically.

### Section C2: Advanced Patterns

**Q21. What is a Fibonacci heap, and how does it improve on binary heaps for graph algorithms?**
A: A Fibonacci heap is a lazy heap structure that supports all standard heap operations plus decrease-key in O(1) amortized time (vs. O(log n) for binary heaps). Key operations:

| Operation | Binary Heap | Fibonacci Heap |
|---|---|---|
| Insert | O(log n) | O(1) amortized |
| Extract-min | O(log n) | O(log n) amortized |
| Decrease-key | O(log n) | O(1) amortized |
| Merge | O(n) | O(1) |

The decrease-key improvement makes Dijkstra's algorithm run in O(V log V + E) with a Fibonacci heap vs. O((V + E) log V) with a binary heap — a significant improvement for dense graphs where E >> V. Similarly, Prim's MST algorithm improves from O(E log V) to O(E + V log V).

In practice, Fibonacci heaps have high constant factors and implementation complexity — they're rarely used in production despite their theoretical superiority. Pairing heaps and rank-pairing heaps are simpler alternatives with similar amortized bounds.

**Q22. What is the "find the median from a data stream" problem, and how does a two-heap approach solve it?**
A: Maintain a max-heap for the lower half of the data and a min-heap for the upper half. Balance invariant: both heaps differ in size by at most 1. The median is either the max of the lower heap, the min of the upper heap, or the average of both roots (for even total count).

```js
class MedianFinder {
  constructor() {
    this.lower = new MaxHeap(); // lower half: max-heap, root = median candidate
    this.upper = new MinHeap(); // upper half: min-heap, root = median candidate
  }

  addNum(num) {
    // Always insert into lower first
    this.lower.push(num);

    // Balance: ensure lower.top() <= upper.top()
    if (this.upper.size() > 0 && this.lower.top() > this.upper.top()) {
      this.upper.push(this.lower.pop());
    }

    // Balance sizes: lower can have at most 1 more element than upper
    if (this.lower.size() > this.upper.size() + 1) {
      this.upper.push(this.lower.pop());
    } else if (this.upper.size() > this.lower.size()) {
      this.lower.push(this.upper.pop());
    }
  }

  findMedian() {
    if (this.lower.size() > this.upper.size()) return this.lower.top();
    return (this.lower.top() + this.upper.top()) / 2;
  }
}
```

Each `addNum` is O(log n) — at most 2 heap operations. `findMedian` is O(1). This is optimal for the streaming median problem: any comparison-based streaming median algorithm requires Ω(log n) per insertion.

## Topic D: Cross-Topic & Interview-Style Questions

**Q23. "Walk through exactly why heap sort is O(n log n) worst case and O(1) space."**
A: O(n log n) worst case:
- **Build phase**: Floyd's algorithm performs O(n) sift-down operations. Each sift-down is O(log n) in the worst case, but most are on subtrees of height < log n — the total work sums to O(n) (not O(n log n)) as shown by the convergent series analysis.
- **Sort phase**: n-1 extract-max operations, each O(log n) sift-down on a shrinking heap. The heap shrinks by 1 each time, but the sift-down on a heap of size m is O(log m) ≤ O(log n). Total: Σ_{m=2}^{n} O(log m) = O(n log n).
- **Combined**: O(n) + O(n log n) = O(n log n). This holds for all inputs — there is no "lucky" input that makes heap sort faster, unlike quicksort.

O(1) space: heap sort operates entirely on the input array. The build phase rearranges elements in-place. The sort phase grows a sorted region at the end of the array (the "sorted" and "heap" regions together always occupy exactly n cells). No auxiliary array, no recursion stack (with iterative sift-down), no extra memory of any kind beyond O(1) variables. This is the strongest space guarantee among O(n log n) comparison sorts.

**Q24. "What is the one scenario where you would choose heap sort over quicksort and merge sort?"**
A: Heap sort is the preferred choice when **both** of the following constraints apply simultaneously:
1. **Guaranteed O(n log n) worst case is required** — quicksort's O(n²) worst case is unacceptable (e.g., adversarial inputs, real-time systems with latency requirements).
2. **O(1) extra space is required** — merge sort's O(n) auxiliary space is unacceptable (e.g., embedded systems, very large arrays with memory constraints).

In practice, this scenario arises in: embedded systems sorting large arrays, real-time systems where latency spikes (quicksort's worst case) are unacceptable, and Introsort's fallback mode (when quicksort's recursion depth indicates worst-case behavior). For most other scenarios, quicksort (randomized) or Timsort (nearly-sorted data) outperforms heap sort in practice.

**Q25. "Why does heap sort have poor cache performance, and how does this affect real-world usage?"**
A: During the sort phase's sift-down, the algorithm accesses elements at indices `i`, `2i+1`, `2i+2` — for large heaps, these indices are far apart in memory. Specifically, the root (index 0) is accessed in every sift-down, but its children (indices 1, 2) and grandchildren (3, 4, 5, 6) and so on progressively get further from the top of the array. In a heap of 10^6 elements, sifting down the root accesses elements at approximately: 0, 1, 3, 7, 15, 31, ..., 2^19 — spanning the entire array in O(log n) accesses.

Each of these accesses to distant memory locations is likely a cache miss on modern CPUs (L1 cache holds ~16-64KB, L2 ~256KB-1MB; a 10^6-element int array is 4MB — far exceeds L1). In contrast, quicksort and merge sort operate on contiguous subarrays, keeping most accesses in cache. In benchmarks, heap sort is typically 2–5× slower than quicksort on random data despite identical O(n log n) complexity.

**Q26. "How do you verify that an array represents a valid max-heap?"**
A: Check the heap property for every internal node: for each index `i` from 0 to `floor(n/2) - 1`, verify that `arr[i] >= arr[2*i+1]` (if left child exists) and `arr[i] >= arr[2*i+2]` (if right child exists). O(n) time, O(1) space.

```js
function isMaxHeap(arr) {
  const n = arr.length;
  for (let i = 0; i <= Math.floor(n/2) - 1; i++) {
    const l = 2*i+1, r = 2*i+2;
    if (l < n && arr[i] < arr[l]) return false; // left child larger → violation
    if (r < n && arr[i] < arr[r]) return false; // right child larger → violation
  }
  return true; // all nodes satisfy heap property
}
```

Leaf nodes (indices `floor(n/2)` to `n-1`) have no children — no property to check. The loop only covers internal nodes. A common interview question asks to check this, testing whether the candidate knows which nodes are leaves.

**Q27. "In one sentence each, state the key insight for the build-heap O(n) proof, the sort phase O(n log n), and heap sort's cache disadvantage."**
A:
- **Build-heap O(n)**: most nodes are near the leaves and require only a few sift-down steps each — the total work is bounded by `Σ (h × n/2^h)` over all heights h, a series that converges to 2n.
- **Sort phase O(n log n)**: each of n-1 extract-max operations costs O(log m) for a shrinking heap of size m, and summing log 2 + log 3 + ... + log n = log(n!) ≈ n log n by Stirling's approximation.
- **Cache disadvantage**: sift-down accesses array elements at indices that double each level (0, ~n/2, ~3n/4, ...), spanning the entire array in O(log n) random-access jumps that consistently miss the CPU cache, unlike quicksort and merge sort which process contiguous memory regions.

## Problem 1 — Heap Sort (Full Implementation)

### Problem
Implement heap sort to sort an array of integers in ascending order in-place. The implementation must use O(1) extra space and O(n log n) time in all cases.

```
Input:  [12, 11, 13, 5, 6, 7]
Output: [5, 6, 7, 11, 12, 13]

Input:  [4, 10, 3, 5, 1]
Output: [1, 3, 4, 5, 10]
```

### Pattern Recognition
Direct application of heap sort — two phases: build max-heap (Floyd's O(n) algorithm), then repeatedly extract the maximum (swap to end, sift-down) to produce a sorted result in the same array.

### Key Insight
A max-heap's invariant (root is always the largest element) means the array's maximum is always at index 0. By swapping `arr[0]` with `arr[heapSize-1]` and shrinking the heap by 1, the extracted maximum lands at its final sorted position (the rightmost unsorted slot). Sifting down restores the heap property for the remaining elements. Repeating this n-1 times sorts the array — the sorted region grows from right to left while the heap region shrinks from right to left.

### Approach
1. **Build phase**: call `siftDown` for every internal node from `floor(n/2)-1` down to 0.
2. **Sort phase**: for `i` from `n-1` down to 1: swap `arr[0]` with `arr[i]`, call `siftDown(arr, i, 0)` — where the second argument `i` is the current heap size (elements at indices `i` through `n-1` are already sorted and excluded from the heap).

### Solution

```js
function heapSort(arr) {
  const n = arr.length;

  // ─── Phase 1: Build max-heap (Floyd's algorithm) ───
  // Start from the last internal node and sift down each one.
  // Leaf nodes (indices n/2 to n-1) are trivially valid heaps.
  for (let i = Math.floor(n / 2) - 1; i >= 0; i--) {
    siftDown(arr, n, i);
  }

  // ─── Phase 2: Extract elements one by one ───
  // The root (arr[0]) is always the heap's maximum.
  // Swap it to the current end of the heap, shrink the heap by 1,
  // and restore the heap property by sifting down the new root.
  for (let i = n - 1; i > 0; i--) {
    // Swap max (root) to its sorted position at the end
    [arr[0], arr[i]] = [arr[i], arr[0]];

    // Restore max-heap property for heap of size i (elements 0..i-1)
    siftDown(arr, i, 0);
  }
}

// Sift-down: restore heap property in arr[0..heapSize-1] starting at node i.
// Assumes both subtrees of node i are valid max-heaps.
function siftDown(arr, heapSize, i) {
  while (true) {
    let largest = i;             // assume current node is the largest
    const l = 2 * i + 1;        // left child index
    const r = 2 * i + 2;        // right child index

    // Check if left child exists and is larger than current largest
    if (l < heapSize && arr[l] > arr[largest]) largest = l;

    // Check if right child exists and is larger than current largest
    if (r < heapSize && arr[r] > arr[largest]) largest = r;

    // If current node is already the largest, heap property is satisfied
    if (largest === i) break;

    // Swap current node with the largest child
    [arr[i], arr[largest]] = [arr[largest], arr[i]];

    // Move down to the swapped child and continue
    i = largest;
  }
}
```

### Edge Cases
- Empty array (`n=0`): `floor(0/2)-1 = -1` → build loop doesn't execute. Sort loop condition `i>0` immediately false. Return unchanged (empty) array.

- All equal elements: sift-down never swaps (no element is strictly larger than another). Build phase: no swaps. Sort phase: swap root with last in each iteration, but sift-down immediately stops. Result: array in same order as input (but this is sorted since all equal). O(n log n) time but O(n) actual work since sift-down terminates immediately.
- Already sorted ascending `[1,2,3,4,5]`: build phase creates a valid max-heap (may involve swaps). Sort phase proceeds normally. No performance advantage — O(n log n) always.

### Follow-up Questions
- "Implement in descending order?" → Use a min-heap instead of max-heap: change `arr[l] > arr[largest]` to `arr[l] < arr[largest]` in sift-down. The sort phase places the minimum at the end each time, building ascending order from right — wait, this produces descending order from left. Alternatively: sort ascending with max-heap (as above), then reverse the array. Or: use max-heap but reverse the comparison in sift-down.
- "Make it stable?" → Augment each element with its original index: sort `[val, originalIdx]` pairs, comparing by `val` first, then `originalIdx` for ties. O(n) extra space. See Q7.
- "What's the minimum and maximum number of swaps in the build phase?" → Minimum: 0 (input already a max-heap). Maximum: O(n) swaps — every internal node may need to swap exactly once (actually, total swaps in build phase ≤ n/2 for a completely "wrong" input). See the O(n) build-heap analysis.

## Problem 2 — Kth Largest Element in an Array

### Problem
Given an integer array `nums` and an integer `k`, return the kth largest element in the array. Note: the kth largest is the kth element in sorted descending order — not the kth distinct element.

```
Input:  nums = [3, 2, 1, 5, 6, 4], k = 2
Output: 5

Input:  nums = [3, 2, 3, 1, 2, 4, 5, 5, 6], k = 4
Output: 4
```

### Pattern Recognition
Min-heap of size k — maintain a min-heap containing the k largest elements seen. The heap's minimum (root) is always the kth largest. After processing all elements, return the root. O(n log k) time, O(k) space.

### Key Insight
The kth largest element is the smallest element among the top-k largest. A min-heap of size k always has the current kth largest at its root — if a new element is larger than the root, it enters the top-k (replace the root). After processing all n elements, the root is the kth largest of the entire array. This O(n log k) approach beats full sorting (O(n log n)) when k << n.

### Approach
Simulate a min-heap of size k using the array: build a min-heap from the first k elements. For each remaining element: if it exceeds the heap root, replace the root and sift-down. After processing all elements, return the root (`heap[0]`).

### Solution

```js
function findKthLargest(nums, k) {
  // Build a min-heap of the first k elements
  // We simulate a min-heap using negation with our max-heap siftDown,
  // OR implement a dedicated min-heap siftDown.
  // Here: clean min-heap implementation.

  const heap = nums.slice(0, k); // first k elements form initial heap

  // Build min-heap from first k elements (Floyd's algorithm on k elements)
  for (let i = Math.floor(k / 2) - 1; i >= 0; i--) {
    minSiftDown(heap, k, i);
  }

  // Process remaining elements
  for (let i = k; i < nums.length; i++) {
    if (nums[i] > heap[0]) {
      // New element is larger than current kth largest (heap root)
      // Replace root with new element and restore min-heap
      heap[0] = nums[i];
      minSiftDown(heap, k, 0);
    }
    // If nums[i] <= heap[0]: this element is not in the top k — skip
  }

  // Root of min-heap = kth largest element
  return heap[0];
}

// Min-heap sift-down: ensures smallest is at root
function minSiftDown(arr, heapSize, i) {
  while (true) {
    let smallest = i;
    const l = 2 * i + 1, r = 2 * i + 2;

    if (l < heapSize && arr[l] < arr[smallest]) smallest = l;
    if (r < heapSize && arr[r] < arr[smallest]) smallest = r;

    if (smallest === i) break;

    [arr[i], arr[smallest]] = [arr[smallest], arr[i]];
    i = smallest;
  }
}
```

### Complexity
- Time: O(k + (n-k) log k) = O(n log k) — building the initial heap is O(k), processing each of the remaining n-k elements is O(log k).
- Space: O(k) — the min-heap contains exactly k elements.

### Edge Cases
- `k = 1`: find the maximum. The heap has size 1 — every element larger than `heap[0]` replaces it. After processing all elements, `heap[0]` is the maximum.
- `k = n`: find the minimum. Build a min-heap of all n elements. No replacement phase. Return `heap[0]` — the minimum.
- Duplicate elements: handled correctly. If `nums[i] > heap[0]`, replace. Equal elements don't replace, maintaining exactly k elements with the k largest values (duplicates included).
- `nums.length = k`: build the heap, no replacement phase. Return the minimum of the k elements = kth largest.

### Follow-up Questions
- "Achieve O(n) average time?" → Quickselect — partition-based median-of-medians or randomized partition. O(n) average, O(n²) worst case without randomization.
- "Stream of integers (can't store all)?" → The min-heap of size k approach works perfectly for streaming — process each incoming element with the O(log k) replace operation. The heap always contains the top-k elements seen so far.
- "What if k is very large (close to n)?" → Build a max-heap of all n elements and extract-max k times: O(n + k log n). For k > n/2, this beats the min-heap approach (O(n log k) vs O(n + k log n)).

## Problem 3 — Merge K Sorted Lists

### Problem
You are given an array of k linked lists, each sorted in ascending order. Merge all the lists into one sorted linked list and return it.

```
Input:  lists = [[1→4→5], [1→3→4], [2→6]]
Output: 1→1→2→3→4→4→5→6

Input:  lists = []
Output: []

Input:  lists = [[]]
Output: []
```

### Pattern Recognition
Min-heap of size k (one entry per list) — always extract the globally smallest current list head, advance that list, insert the next element. O(n log k) where n = total elements across all lists. The heap maintains the "frontier" of each list.

### Key Insight
The minimum of k sorted lists' current heads is the next element in the merged output. A min-heap of size k gives this minimum in O(1) (read root) and can be updated in O(log k) (replace root, sift-down). Each of n elements is inserted and extracted exactly once — O(n log k) total.

### Approach
Initialize the heap with the first node of each non-empty list. Repeatedly: extract the minimum node (heap root), append it to the result, push its `next` node into the heap (if it exists). Continue until the heap is empty.

### Solution

```js
// ListNode definition:
// class ListNode { constructor(val, next=null) { this.val=val; this.next=next; } }

function mergeKLists(lists) {
  // Min-heap: stores [nodeValue, listIndex, node]
  // Heap ordered by nodeValue (smallest at root)
  const heap = [];

  // Initialize heap with first node of each non-empty list
  for (let i = 0; i < lists.length; i++) {
    if (lists[i]) {
      heapPush(heap, [lists[i].val, i, lists[i]]);
    }
  }

  const dummy = new ListNode(0); // dummy head for result list
  let curr = dummy;

  while (heap.length > 0) {
    const [val, listIdx, node] = heapPop(heap); // extract min

    curr.next = node;  // append to result
    curr = curr.next;

    // Push the next node from the same list
    if (node.next) {
      heapPush(heap, [node.next.val, listIdx, node.next]);
    }
  }

  return dummy.next;
}

// ── Min-heap helper operations ──
function heapPush(heap, entry) {
  heap.push(entry);
  // Sift up
  let i = heap.length - 1;
  while (i > 0) {
    const parent = (i - 1) >> 1;
    if (heap[parent][0] > heap[i][0]) {
      [heap[parent], heap[i]] = [heap[i], heap[parent]];
      i = parent;
    } else break;
  }
}

function heapPop(heap) {
  const min = heap[0];
  const last = heap.pop();
  if (heap.length > 0) {
    heap[0] = last;
    // Sift down
    let i = 0;
    while (true) {
      let smallest = i;
      const l = 2*i+1, r = 2*i+2;
      if (l < heap.length && heap[l][0] < heap[smallest][0]) smallest = l;
      if (r < heap.length && heap[r][0] < heap[smallest][0]) smallest = r;
      if (smallest === i) break;
      [heap[i], heap[smallest]] = [heap[smallest], heap[i]];
      i = smallest;
    }
  }
  return min;
}
```

### Edge Cases
- Empty `lists` array: heap initialization finds no non-null lists; heap stays empty; while loop never executes; return `dummy.next = null`.

- Single list (`k=1`): heap has one entry; each iteration extracts and re-inserts; effectively traverses the single list. Result is the original list (O(n log 1) = O(n)).
- All lists of size 1: heap initialized with k elements; each extraction inserts nothing (no `next` nodes); k extractions total. O(k log k).

### Follow-up Questions
- "Solve with divide-and-conquer (merging pairs)?" → Merge lists in pairs iteratively: round 1 merges k/2 pairs → k/2 lists; round 2 merges k/4 pairs → k/4 lists; ... log k rounds total. - "What if lists are given as arrays instead of linked lists?" → Same approach with array indices as pointers; push `(value, listIdx, elementIdx)` tuples. Update: increment `elementIdx` and push the next element if available.
- "Minimize total space including output?" → The linked list approach reuses existing nodes — no new node allocation beyond the heap's k entries and the dummy head. Already O(k) extra space.

## Problem 4 — Find Median from Data Stream

### Problem
Implement the `MedianFinder` class to find the median of a data stream:
- `MedianFinder()` initializes the object.
- `void addNum(int num)` adds an integer from the data stream.
- `double findMedian()` returns the median of all elements inserted so far.

```
Input:  addNum(1), addNum(2), findMedian() → 1.5
        addNum(3), findMedian() → 2.0

Input:  addNum(6), addNum(5), findMedian() → 5.5
        addNum(4), findMedian() → 5.0
```

### Pattern Recognition
Two-heap approach (max-heap for lower half + min-heap for upper half) — the median is either the top of one heap or the average of both tops. Each `addNum` is O(log n); `findMedian` is O(1).

### Key Insight
Partition the stream into two halves: `lower` (max-heap of smaller half) and `upper` (min-heap of larger half). Invariants:
1. Every element in `lower` ≤ every element in `upper` (proper partition).
2. `|lower.size - upper.size| ≤ 1` (balanced sizes — differ by at most 1).

With these invariants: if sizes are equal, median = average of both tops. If `lower` has one more, median = `lower.top()`. If `upper` has one more (disallowed by our rebalancing), we move the min of upper to lower.

### Approach
On `addNum(num)`: always push to `lower` first, then pop from `lower` and push to `upper` (ensures partition invariant), then if `upper.size > lower.size`, pop from `upper` and push back to `lower` (ensures balance invariant). On `findMedian()`: if sizes equal, return average of both tops; otherwise return the top of the larger heap.

### Solution

```js
class MedianFinder {
  constructor() {
    // lower: max-heap (stores smaller half); simulated by negating values in a min-heap
    // upper: min-heap (stores larger half)
    this.lower = new MinHeap(); // max-heap via negation
    this.upper = new MinHeap(); // true min-heap
  }

  addNum(num) {
    // Step 1: push to lower (max-heap via negation)
    this.lower.push(-num); // negate to simulate max-heap in min-heap

    // Step 2: ensure partition: lower.max <= upper.min
    // (Move lower's max to upper if it exceeds upper's min)
    if (this.upper.size() > 0 && -this.lower.top() > this.upper.top()) {
      this.upper.push(-this.lower.pop());
    }

    // Step 3: balance sizes (lower can have at most 1 more than upper)
    if (this.lower.size() > this.upper.size() + 1) {
      this.upper.push(-this.lower.pop());
    } else if (this.upper.size() > this.lower.size()) {
      this.lower.push(-this.upper.pop());
    }
  }

  findMedian() {
    if (this.lower.size() === this.upper.size()) {
      // Even count: average of both tops
      return (-this.lower.top() + this.upper.top()) / 2;
    }
    // Odd count: lower has one more — its max is the median
    return -this.lower.top();
  }
}

// Simple MinHeap implementation for illustration:
class MinHeap {
  constructor() { this.data = []; }
  size() { return this.data.length; }
  top() { return this.data[0]; }

  push(val) {
    this.data.push(val);
    let i = this.data.length - 1;
    while (i > 0) {
      const p = (i-1) >> 1;
      if (this.data[p] > this.data[i]) {
        [this.data[p], this.data[i]] = [this.data[i], this.data[p]];
        i = p;
      } else break;
    }
  }

  pop() {
    const min = this.data[0];
    const last = this.data.pop();
    if (this.data.length > 0) {
      this.data[0] = last;
      let i = 0;
      while (true) {
        let s = i;
        const l = 2*i+1, r = 2*i+2;
        if (l < this.data.length && this.data[l] < this.data[s]) s = l;
        if (r < this.data.length && this.data[r] < this.data[s]) s = r;
        if (s === i) break;
        [this.data[i], this.data[s]] = [this.data[s], this.data[i]];
        i = s;
      }
    }
    return min;
  }
}
```

### Dry Run

```
Using notation: lower=max-heap (shown as actual values), upper=min-heap

addNum(1):
  Push to lower: lower=[-1] → represents {1}. upper=[].
  Partition check: upper empty → skip.
  Balance: lower.size(1) > upper.size(0)+1? No (1 ≤ 1). upper.size(0) > lower.size(1)? No.
  State: lower={1}, upper={}

addNum(2):
  Push to lower: lower={1,2} (max-heap: [−2,−1] internally). upper={}.
  Partition: upper empty → skip.
  Balance: lower.size(2) > upper.size(0)+1=1? Yes (2>1).
    Move lower.max(2) to upper. lower={1}, upper={2}.
  State: lower={1}, upper={2}

findMedian():
  lower.size(1) == upper.size(1) → even.
  Return (lower.top() + upper.top()) / 2 = (1 + 2) / 2 = 1.5 ✓

addNum(3):
  Push to lower: lower={1,3}. upper={2}.
  Partition: lower.max(3) > upper.min(2)? Yes → move 3 to upper.
    lower={1}, upper={2,3}.
  Balance: upper.size(2) > lower.size(1)? Yes → move upper.min(2) to lower.
    lower={1,2}, upper={3}.
  State: lower={1,2}, upper={3}

findMedian():
  lower.size(2) > upper.size(1) → odd. lower has more.
  Return lower.top() = 2 ✓
```

### Complexity
- Time: O(log n) per `addNum` — at most 3 heap operations (push + 2 possible pops/pushes), each O(log n). O(1) per `findMedian` — read the heap tops.
- Space: O(n) — both heaps together store all n elements.

### Edge Cases
- Single element: after `addNum(x)`, lower={x}, upper={}. `findMedian()` returns `lower.top() = x`. Correct.
- Two equal elements `addNum(5), addNum(5)`: lower={5}, upper={5}. `findMedian()` = (5+5)/2 = 5.0. Correct.
- Monotonically increasing stream: each new element goes to upper (after partition check), then might get moved back to balance — the two-heap structure adapts dynamically. Always correct.
- Negative numbers: the negation trick (simulating max-heap in a min-heap by negating values) works correctly for all integers including negatives.

### Follow-up Questions
- "What if 99% of numbers are between 0 and 100?" → Use a frequency array of size 101 for numbers in that range, and two heaps for outliers. The median query scans the frequency array (O(101) = O(1)) for common cases. This is a bucket-based median optimization for known-range streams.
- "What if you need the median at every step?" → `addNum` + `findMedian` after each insertion. Same O(log n) per step — the two-heap maintains the median incrementally. Store the median after each `addNum` in O(n) total.
- "Support deletion from the stream?" → Maintain lazy-deletion sets: when deleting element x, add x to a "pending deletions" set. On each heap operation, check if the top is in the pending set — if so, pop it and continue. O(log n) amortized per operation with careful bookkeeping.

## Quick Reference — Heap Pattern Decision Tree

```
Does the problem involve repeatedly finding the minimum or maximum
from a dynamically changing collection?
│
├── FIND K LARGEST / K SMALLEST ELEMENTS?
│   ├── K largest from array → min-heap of size k
│   │   Process each element: if > heap.min, replace min and sift-down
│   │   O(n log k) time, O(k) space
│   │   Better than sort (O(n log n)) when k << n
│   │
│   └── K largest from stream → same min-heap of size k
│       Each new element: compare with heap.min, replace if larger
│
├── MERGE K SORTED STRUCTURES?
│   └── Min-heap of size k (one entry per structure)
│       Each extraction: append min to result, push next from same source
│       O(n log k) time, O(k) space
│       (k sorted arrays, k sorted linked lists, k sorted generators)
│
├── SLIDING WINDOW MINIMUM / MAXIMUM?
│   ├── Need exact O(n): Monotonic Deque (not heap)
│   │   Deque maintains indices in monotone order
│   │   O(n) total, O(k) space
│   │
│   └── O(n log k) acceptable: Max/Min-Heap with lazy deletion
│       Store (value, index) pairs; on query, pop expired indices from top
│
├── MEDIAN / PERCENTILE FROM STREAM?
│   └── Two heaps (max-heap for lower half + min-heap for upper half)
│       Invariants: lower.max ≤ upper.min, |sizes| ≤ 1
│       O(log n) per addNum, O(1) per findMedian
│
├── SORT AN ARRAY?
│   ├── Heap sort:
│   │   Phase 1: Build max-heap (Floyd's) O(n)
│   │   Phase 2: Extract max n-1 times O(n log n)
│   │   Total: O(n log n), O(1) space, NOT stable
│   │   Use when: O(1) space + worst-case O(n log n) both required
│   │
│   └── Prefer quicksort (average speed) or Timsort (nearly-sorted)
│       for general sorting when stability or cache performance matters
│
├── SCHEDULING / TASK PROCESSING IN PRIORITY ORDER?
│   └── Max-heap (or min-heap for urgent = low number)
│       Push tasks with priority, always process highest-priority first
│       O(log n) per push/pop
│
├── SHORTEST PATH / MST WITH DECREASE-KEY?
│   ├── Dense graph (E ≈ V²): binary heap sufficient
│   │   Dijkstra: O((V+E) log V) with binary heap
│   │
│   └── Very sparse graph, decrease-key dominated:
│       Fibonacci heap → O(V log V + E) Dijkstra
│       (rarely used in practice due to implementation complexity)
│
└── BUILD HEAP FROM ARRAY?
    ├── Floyd's (bottom-up): O(n) — preferred
    │   Start from last internal node (floor(n/2)-1), sift-down each
    │
    └── Repeated insertion (top-down): O(n log n) — avoid
        Only use when elements arrive one-at-a-time (online)
```

## Common Bugs Checklist

Before submitting any heap or heap sort solution, verify:

1. **Sift-down uses heap size as the bound, not array length?** — In heap sort's sort phase, the heap shrinks by 1 each iteration. The sift-down call must use the current heap size (the parameter `i` in `siftDown(arr, i, 0)`) not `arr.length`. Using `arr.length` includes already-sorted elements in the heap, corrupting the sorted region.

2. **Build-heap starts at `floor(n/2) - 1`, not `n - 1`?** — Leaf nodes (indices `floor(n/2)` to `n-1`) have no children and are trivially valid heaps — they need no sift-down. Starting sift-down from `n-1` wastes O(n/2) sift-down calls on leaves and is still correct, but starting from `floor(n/2)-1` is the O(n) Floyd's algorithm. Forgetting the `-1` offset (using `floor(n/2)` instead) misses the last internal node — potential heap property violation.

3. **Sift-down termination: checking both children exist before comparing?** — `arr[l]` is only valid if `l < heapSize`. `arr[r]` is only valid if `r < heapSize`. Accessing out-of-bounds indices gives undefined values that may accidentally pass comparisons. Always guard: `if (l < heapSize && arr[l] > arr[largest])`.

4. **Swap in sort phase uses index 0 (root) and index i (last of heap), not i and i-1?** — The sort phase extracts the maximum by swapping `arr[0]` (the heap root, which is the maximum) with `arr[i]` (the last element in the current heap). A common mistake: swapping `arr[i]` with `arr[i-1]` — this doesn't extract the maximum, just moves the last two elements.

5. **Min-heap sift-down uses `<` not `>`?** — Max-heap: find the `largest` child; promote it if larger than parent. Min-heap: find the `smallest` child; promote it if smaller than parent. Mixing the comparison directions produces a mixed structure that is neither a valid min-heap nor a max-heap — all queries return wrong results without obvious errors.

6. **Two-heap MedianFinder: rebalancing after BOTH partition and size checks?** — Two separate conditions must be checked after each `addNum`: (1) partition correctness (lower.max ≤ upper.min), and (2) size balance (sizes differ by at most 1). Checking only one allows the other to drift, producing incorrect median values after many insertions.

7. **Kth largest with min-heap: pushing the new element ONLY if it exceeds the heap minimum?** — If `nums[i] <= heap[0]`, skip it — it's not in the top k. Inserting it and then removing the minimum is equivalent, but the guard `if (nums[i] > heap[0])` saves the push + pop on small elements. Without this guard, the algorithm is still correct but performs unnecessary work.

8. **Heap sort is in-place — the sort phase swaps INTO the sorted region, not out of the array?** — After swapping `arr[0]` with `arr[i]`, element `arr[i]` is the (n-i)th largest element in its final sorted position. Subsequent sift-down operations must NOT touch index i or beyond (they're already sorted). The heap size parameter ensures this — always pass `i` (not `n`) as the heap size to sift-down in the sort phase.

**Final Tip:** At the 5 YOE level, interviewers expect you to explain heap sort's two phases before touching code — "Phase 1 uses Floyd's bottom-up construction in O(n) because most nodes are near the leaves and require minimal sift-down work; Phase 2 exploits the max-heap invariant to extract the maximum in O(1) and restore the heap in O(log n), repeated n times for O(n log n) total — giving the algorithm its defining property: O(n log n) worst case with O(1) extra space, the strongest combined guarantee among comparison sorts." The decisive signal of genuine mastery is then explaining the sift-down direction immediately when asked about the inner loop: "Right-to-left through the heap levels, because sift-down assumes both subtrees are already valid heaps — processing right-to-left from the last internal node upward establishes this assumption inductively for each node before it's processed." Connecting the algorithm's correctness to the inductive invariant it maintains — not just reciting the procedure — is what separates a senior answer from a memorized template.
