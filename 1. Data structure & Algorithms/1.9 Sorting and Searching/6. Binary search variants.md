## Topic A: Binary Search Invariants & Templates

### Section A1: The Core Invariant

**Q1. What is the fundamental binary search invariant, and what does "maintain the answer in the search space" mean?**

A: Binary search's core invariant is: **at the start of every iteration, the answer (if it exists) lies within the current search range `[lo, hi]`.** Every update rule must preserve this invariant — it can never discard the position of the answer. This is what distinguishes correct from incorrect binary search: a wrong update rule moves lo or hi past the answer, violating the invariant and producing a wrong result. The invariant also guarantees termination: if the range strictly shrinks each iteration, the algorithm must eventually finish. Verifying a binary search implementation means verifying: (1) the invariant holds at the start, (2) every branch of the update preserves it, and (3) the range strictly shrinks.

```
Invariant: answer ∈ [lo, hi] at the start of every iteration.

To verify:
  (1) Initial: lo=0, hi=n-1. Array has n elements. Answer is somewhere in [0, n-1]. ✓
  (2) After hi = mid-1: if nums[mid] < target, answer cannot be at mid or left.
      So discarding [lo, mid] is safe. ✓
  (3) After lo = mid+1: if nums[mid] > target, answer cannot be at mid or right.
      So discarding [mid, hi] is safe. ✓
  (4) Each iteration: mid is always in (lo, hi] range — the range shrinks. ✓
```

**Q2. What are the two primary binary search templates, when is each appropriate, and how do termination conditions differ?**

A: Two templates exist, suited to different goals:

**Template 1 — Exact match with `lo <= hi`**: terminates when the range is empty (`lo > hi`). Requires every update to strictly shrink the range: both `lo = mid + 1` and `hi = mid - 1`. Best for: standard search (return index or -1), any problem with a clear "found" vs "not found" distinction. Uses a `result` variable to track the best valid candidate seen so far.

**Template 2 — Boundary search with `lo < hi`**: terminates when `lo == hi`, at which point `lo` is the answer. The range never becomes empty — it shrinks to a single element. Update rules: `hi = mid` (keeps mid as a candidate) or `lo = mid + 1` (discards mid). Best for: first/last occurrence, find minimum, find peak — problems where you're converging on a boundary, not a specific value.

```
Template 1 (lo <= hi):
  while (lo <= hi) {
    mid = floor((lo + hi) / 2);
    if (nums[mid] === target) return mid;       // found
    else if (nums[mid] < target) lo = mid + 1;  // target is right
    else hi = mid - 1;                           // target is left
  }
  return -1; // not found

Template 2 (lo < hi, bisect-left):
  while (lo < hi) {
    mid = floor((lo + hi) / 2);  // left-biased mid
    if (cond(mid)) hi = mid;      // mid is a candidate — keep it
    else lo = mid + 1;            // mid cannot be the answer
  }
  // lo == hi: the answer is lo (or check if nums[lo] is valid)
```

**Q3. What is mid-computation bias, when does it matter, and how does it prevent infinite loops?**

A: When `lo = hi - 1`, two mid values are possible: `lo` (left-biased) or `hi` (right-biased). **Left bias** (`Math.floor((lo + hi) / 2)`) gives `mid = lo`. **Right bias** (`Math.floor((lo + hi + 1) / 2)`) gives `mid = hi`. The bias matters when one of the update paths can set `lo = mid` or `hi = mid` — if the update path for the "advance lo" case is `lo = mid`, and mid is left-biased (mid = lo), then `lo = mid = lo` — no progress, infinite loop. The fix: use right-biased mid whenever `lo = mid` is a possible update.

```
Infinite loop scenario (left bias with lo = mid update):
  lo=3, hi=4. mid=floor((3+4)/2)=3=lo.
  If condition keeps lo=mid=3 → loop forever ✗

Fix: right-biased mid = floor((3+4+1)/2)=4=hi.
  lo=mid=4 > lo=3 → range shrinks ✓

Rule: if "lo = mid" is a possible update → use right-biased mid.
      if "hi = mid" is a possible update → use left-biased mid (default).
      Never use both "hi = mid" and left bias with "lo = mid" simultaneously.
```

**Q4. What is the "lower bound" (bisect-left) and "upper bound" (bisect-right) abstraction, and how do they unify all first/last occurrence variants?**

A: **Lower bound** (bisect-left): the first index where `nums[i] >= target`. All elements to the left are strictly less than target. **Upper bound** (bisect-right): the first index where `nums[i] > target`. All elements to the left are ≤ target. These two functions derive all occurrence variants:

- **First occurrence of target**: `lowerBound(target)`, then verify `nums[result] == target`.
- **Last occurrence of target**: `upperBound(target) - 1`, then verify `nums[result] == target`.
- **Count of target**: `upperBound(target) - lowerBound(target)`.
- **Insertion position** (maintaining sort): `lowerBound(target)` for insert-before-first, `upperBound(target)` for insert-after-last.

```js
// Lower bound: first index where nums[i] >= target
function lowerBound(nums, target) {
  let lo = 0, hi = nums.length; // hi = n (one past last)
  while (lo < hi) {
    const mid = (lo + hi) >> 1; // left-biased
    if (nums[mid] >= target) hi = mid; // mid could be the answer
    else lo = mid + 1;                 // mid is too small
  }
  return lo; // in [0, n]: lo == n means all elements < target
}

// Upper bound: first index where nums[i] > target
function upperBound(nums, target) {
  let lo = 0, hi = nums.length;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (nums[mid] > target) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

// First occurrence: lowerBound(target) if valid
// Last occurrence:  upperBound(target) - 1 if valid
// Count:           upperBound(target) - lowerBound(target)
```

### Section A2: Variant Design

**Q5. What is the "find-boundary" abstraction that all binary search variants reduce to?**

A: Every binary search problem can be framed as: given a predicate P(i) that is false for small i and true for large i (or vice versa), find the boundary — the first index where P flips. The array doesn't need to be numerically sorted; it needs to be *monotone* in the predicate. Examples: first occurrence → P(i) = `nums[i] >= target`; find minimum in rotated array → P(i) = `nums[i] <= nums[last]` (true in the minimum's half); peak element → P(i) = `nums[i] > nums[i+1]` (true on the descending side of a peak). Framing the problem as "find the first True" or "find the last True" immediately tells you which template and update rule to use.

```
All variants as "find first True" problems:

First occurrence of target:    P(i) = nums[i] >= target
  (first True where P(first) has nums[first] == target)

Find minimum in rotated array: P(i) = nums[i] <= nums[n-1]
  (the minimum is at the first True position)

Peak element:                  P(i) = nums[i] > nums[i+1]
  (peak is at the last True, or equivalently "first descent")

Search rotated array:          not a simple monotone predicate —
  requires identifying which half is sorted (see Q11)
```

**Q6. What is "binary search on the answer" and what problem property enables it?**

A: Instead of searching an index in an array, search over possible *answer values* in a range. Requires: **monotonicity of feasibility** — if answer value `v` is feasible (satisfies the constraint), then all values `v' > v` are also feasible (for minimization problems), or all `v' < v` (for maximization). Binary search finds the boundary between feasible and infeasible in O(log V) feasibility checks, each costing O(f(n)). Total: O(f(n) × log V). Examples: "find the k-th smallest element in a sorted matrix" (binary search over the value range, count elements ≤ mid to check feasibility), "minimum speed to eat all bananas in H hours."

```
Binary search on answer template:
  lo = minimum possible answer
  hi = maximum possible answer

  while (lo < hi):
    mid = floor((lo + hi) / 2)
    if isFeasible(mid):
      hi = mid     // mid works, but maybe smaller works too
    else:
      lo = mid + 1 // mid doesn't work, need larger

  return lo  // smallest feasible answer
```

## Topic B: First/Last Occurrence Patterns

### Section B1: Update Rule Mechanics

**Q7. What exactly causes the asymmetry between the first-occurrence and last-occurrence update rules?**

A: When `nums[mid] == target`, both variants find a valid occurrence, but they differ in *what to do next*: first occurrence searches **left** (there may be an earlier occurrence), so it records `result = mid` and sets `hi = mid - 1` to exclude mid and search left. Last occurrence searches **right**, so it records `result = mid` and sets `lo = mid + 1`. This is the only difference — the two "not-found" branches (`nums[mid] < target → lo = mid+1`, `nums[mid] > target → hi = mid-1`) are identical.

```
First occurrence (search LEFT on match):
  if nums[mid] == target: result = mid; hi = mid - 1  ← exclude mid, search left
  if nums[mid] < target:  lo = mid + 1
  if nums[mid] > target:  hi = mid - 1

Last occurrence (search RIGHT on match):
  if nums[mid] == target: result = mid; lo = mid + 1  ← exclude mid, search right
  if nums[mid] < target:  lo = mid + 1
  if nums[mid] > target:  hi = mid - 1

The "result" variable stores the best candidate seen so far.
It is returned at the end (or -1 if never updated).
```

**Q8. How do you find the count of a target in a sorted array using binary search, and what is the time complexity?**

A: Run two binary searches: `first = firstOccurrence(target)` and `last = lastOccurrence(target)`. If `first == -1`, count = 0. Otherwise count = `last - first + 1`. Two O(log n) searches = O(log n) total. Alternatively, use `upperBound(target) - lowerBound(target)` for the count in a single unified framework. This is strictly better than scanning from first to last occurrence (which is O(count) for the range), especially when the target appears O(n) times.

```
nums = [2,2,2,2,2,3,4,5,5,5], target=2.
firstOccurrence(2) = 0. lastOccurrence(2) = 4.
count = 4 - 0 + 1 = 5. ✓

Using bounds: lowerBound(2) = 0. upperBound(2) = 5 (first index > 2).
count = 5 - 0 = 5. ✓
```

**Q9. What is the correct way to find the "insertion position" for a target that may or may not already exist in the array?**

A: Insertion position = the index where target should be inserted to keep the array sorted. This is exactly the lower bound: first index where `nums[i] >= target`. If target exists, this is its first occurrence. If target doesn't exist, this is where it would be inserted. The lower bound always returns a value in `[0, n]` (never -1): 0 means insert before all elements; n means insert after all elements. This is what Python's `bisect.bisect_left` and Java's `Arrays.binarySearch` (when not found, returns `-(insertionPoint) - 1`) compute.

## Topic C: Rotated Array Patterns

### Section C1: The Sorted-Half Observation

**Q10. What is the key structural observation about rotated sorted arrays that makes O(log n) search possible?**

A: A rotated sorted array has at most one "break point" where the order is violated. This means: **for any split at mid, at least one of the two halves [lo, mid] or [mid+1, hi] is always contiguously sorted.** This is provable: if neither half were sorted, there would need to be two break points — impossible with a single rotation. This guarantee enables the following strategy: (1) determine which half is sorted (by comparing endpoints), (2) check if the target lies within the sorted half's value range, (3) search that half (or the other). Each step eliminates half the remaining elements.

```
[4, 5, 6, 7, 0, 1, 2], target=0.   lo=0, hi=6, mid=3.
  nums[0]=4, nums[3]=7.  4 <= 7 → LEFT half [4,5,6,7] is sorted.
  Is 0 in [4, 7]? No (0 < 4) → search RIGHT half.

[6, 7, 0, 1, 2, 4, 5], target=6.  lo=0, hi=6, mid=3.
  nums[0]=6, nums[3]=1.  6 > 1 → RIGHT half [1,2,4,5] is sorted.
  Is 6 in [1, 5]? No (6 > 5) → search LEFT half.

In every case, one half is sorted and we can check membership in O(1).
```

**Q11. What are the exact conditions for determining which half is sorted and whether the target belongs to it?**

A: Compare `nums[lo]` with `nums[mid]`:

**Left half `[lo, mid]` is sorted** when `nums[lo] <= nums[mid]`. Target is in this half iff `nums[lo] <= target < nums[mid]` (within the sorted range, exclusive on right because `nums[mid]` is already checked). If not in this range: search right half (`lo = mid + 1`).

**Right half `[mid+1, hi]` is sorted** when `nums[lo] > nums[mid]`. Target is in this half iff `nums[mid] < target <= nums[hi]` (within the sorted range). If not in this range: search left half (`hi = mid - 1`).

```
Both conditions use "nums[lo] <= target < nums[mid]" form — compare with endpoints.

Critical: use nums[lo] (not lo's value) and nums[hi] (not hi's value).
Why nums[lo] not nums[hi] for left-half check: if rotation happened in the right half,
nums[hi] may be less than nums[lo] (the break point is on the right),
so checking nums[lo] <= nums[mid] correctly identifies the sorted left half.

Strict inequality for hi side (target <= nums[hi]) handles target == nums[hi] correctly:
if target equals nums[hi], it's in the right half range.
```

**Q12. How do duplicates break the rotated array binary search, and what is the minimal fix?**

A: With duplicates, the condition `nums[lo] == nums[mid]` (and potentially `== nums[hi]`) prevents determining which half is sorted — both halves could appear sorted. Example: `[1,1,1,2,1]`, `lo=0, hi=4, mid=2`: `nums[0]=1, nums[2]=1` — is left `[1,1,1]` or right `[1,2,1]` sorted? Can't tell from endpoints. Minimal fix: when `nums[lo] == nums[mid]` (and `nums[mid] == nums[hi]` for full safety), increment `lo` and decrement `hi` — shrink by 1 from each side. This eliminates the ambiguous case at the cost of potentially O(n) time for arrays with many duplicates.

```js
// Duplicates fix inside the while loop:
if (nums[lo] === nums[mid] && nums[mid] === nums[hi]) {
  lo++; hi--; // can't determine sorted half — shrink by 1 from each side
  continue;
}
// Now at least one side's sorted-half determination is reliable.

// Worst case: [1,1,1,1,...,1,2,1,1,1,1] — the 2 is near one end.
// Must peel duplicates one by one → O(n) worst case.
```

**Q13. How do you find the minimum element in a rotated sorted array, and why do you compare mid with hi (not lo)?**

A: The minimum is the element where the "rotation break" occurs — the first element of the originally sorted array. Key observation: the minimum is always in the half that is NOT sorted relative to the array's end. Binary search: if `nums[mid] > nums[hi]`, the minimum is in the right half (the left half appears sorted and its minimum is `nums[lo]`, but the true minimum is on the right). If `nums[mid] <= nums[hi]`, the minimum is in the left half or at mid (the right half is sorted, and its minimum is `nums[mid]` or something to its left).

Why compare with `hi` not `lo`: comparing `nums[mid]` with `nums[lo]` is ambiguous when `nums[lo] == nums[mid]` (both appear sorted). Comparing with `nums[hi]` gives a reliable signal: if `nums[mid] > nums[hi]`, the sorted order is broken somewhere between mid and hi, so the minimum is in the right half.

```
[4, 5, 6, 7, 0, 1, 2]:
  lo=0, hi=6, mid=3. nums[3]=7, nums[6]=2. 7 > 2 → min in RIGHT half. lo=4.
  lo=4, hi=6, mid=5. nums[5]=1, nums[6]=2. 1 < 2 → min in LEFT half. hi=5.
  lo=4, hi=5, mid=4. nums[4]=0, nums[5]=1. 0 < 1 → min in LEFT half. hi=4.
  lo=4 == hi=4. Return nums[4]=0. ✓

Never [lo, mid] comparison for find-min:
  If nums[lo]==nums[mid], can't tell if the break is within or beyond mid.
  nums[mid] vs nums[hi] comparison is always unambiguous.
```

## Topic D: 2D Matrix Patterns & Interview-Style Questions

**Q14. What is the structural difference between LeetCode 74 and 240, and which algorithm applies to each?**

A: **LeetCode 74** ("Search a 2D Matrix"): each row is sorted left-to-right AND the first element of each row is greater than the last element of the previous row. This means if you "flatten" the matrix into a 1D array by reading row by row, you get a perfectly sorted array of m×n elements. Apply standard binary search with index mapping: `mid` maps to `matrix[floor(mid/n)][mid % n]`. O(log(m×n)) = O(log m + log n).

**LeetCode 240** ("Search a 2D Matrix II"): each row sorted left-to-right AND each column sorted top-to-bottom, but the first element of each row is NOT necessarily greater than the last element of the previous row. Cannot be flattened to 1D. Use the **staircase search**: start at top-right corner; if current value equals target, found; if greater, move left (eliminate this column position for this row); if less, move down (eliminate this row for this column). O(m + n) — at most m+n steps, each eliminating one row or column.

```
LeetCode 74:  [1,3,5,7]        → flattens to [1,3,5,7,10,11,16,20,23,30,34,60]
              [10,11,16,20]    → binary search O(log(mn))
              [23,30,34,60]

LeetCode 240: [1, 4, 7,11]     → NOT flattenable ([1,4,7,11,2,5,8,...] is not sorted)
              [2, 5, 8,12]     → staircase from top-right O(m+n)
              [3, 6, 9,16]
              [10,13,14,17]
```

**Q15. Why does the staircase (top-right corner) search work, and what invariant does it maintain?**

A: The staircase works because the top-right corner has a unique property: it is the **maximum in its row** (row is sorted left-to-right, so rightmost = maximum) AND the **minimum in its column** (column is sorted top-to-bottom, so topmost = minimum). This gives us a decisive comparison: if `matrix[r][c] > target`, the entire column c below row r is also > target (no need to look down) — eliminate by `c--`. If `matrix[r][c] < target`, the entire row r to the left of c is also < target (no need to look left) — eliminate by `r++`. The invariant: the target (if it exists) is always in the submatrix `[r..m-1][0..c]`.

```
Search for 8 in:
    1  4  7  11
    2  5  8  12
    3  6  9  16

Start: (0, 3) = 11. 11 > 8 → col-- → (0, 2).
  (0, 2) = 7. 7 < 8 → row++ → (1, 2).
  (1, 2) = 8. Found! ✓

Each step eliminates one row or one column from consideration.
Total steps ≤ m + n.
```

**Q16. "Walk through your thought process when you encounter a binary search variant problem."**

A: Four diagnostic questions in order:

1. **Is the search space sorted / monotone?** — If yes, binary search is applicable. What is the predicate? Does it transition from False-to-True or True-to-False?

2. **What am I searching for?** — An exact match (Template 1, `lo <= hi`)? A boundary / first-True / last-True (Template 2, `lo < hi`)? The minimum / maximum satisfying a condition?

3. **What are the update rules, and do they always shrink the range?** — Write out all three branches (mid is answer, mid is too small, mid is too large). Verify each shrinks the range. For the edge case `lo = hi - 1`, trace which mid value is computed and which branch fires.

4. **What are the edge cases?** — Empty array? Single element? Target at lo or hi? Target not present? Duplicate elements? For rotated arrays: no rotation? Rotation by 1? All same elements?

**Q17. "What is the most common binary search bug, and how do you systematically test for it?"**

A: The most common bug is an **infinite loop** caused by an update rule that doesn't shrink the range when `lo = hi - 1`. Systematic test: trace the algorithm with `nums = [a, b]` (two elements) and target = a, b, and a value between them. With left-biased mid: `mid = lo = 0`. If the condition sends `hi = mid = 0` but doesn't advance `lo`, and the next iteration still has `lo=0, hi=1, mid=0` → infinite loop. Fix: use right-biased mid when `lo = mid` is a possible update.

The second most common: **using `lo < hi` but also `hi = mid - 1`** — this can skip the answer at position `mid` when `lo = hi - 1`. In `lo < hi` template, only use `hi = mid` (not `hi = mid - 1`) to preserve the candidate.

**Q18. In one sentence each, state the condition at mid and the update rules for each binary search variant.**

A:
- **Standard search**: if `nums[mid] == target` return mid; if `nums[mid] < target` advance `lo = mid+1`; else retreat `hi = mid-1`.
- **First occurrence**: if `nums[mid] == target` record and search left (`result=mid, hi=mid-1`); if `nums[mid] < target` advance `lo=mid+1`; else retreat `hi=mid-1`.
- **Last occurrence**: if `nums[mid] == target` record and search right (`result=mid, lo=mid+1`); if `nums[mid] < target` advance `lo=mid+1`; else retreat `hi=mid-1`.
- **Search rotated (no dupes)**: identify the sorted half by comparing `nums[lo]` with `nums[mid]`; if target is in sorted half's value range, search there; else search the other half.
- **Find minimum in rotated**: if `nums[mid] > nums[hi]`, minimum is right (`lo=mid+1`); else minimum is left or at mid (`hi=mid`).
- **Find peak element**: if `nums[mid] > nums[mid+1]`, peak is at mid or left (`hi=mid`); else peak is right (`lo=mid+1`).
- **Search 2D Matrix (LeetCode 74)**: treat as 1D array with `matrix[mid/n][mid%n]`; standard binary search.
- **Search 2D Matrix II (LeetCode 240)**: start top-right; if greater move left; if less move down; staircase eliminates one row/column per step.

## Problem 1 — Find First and Last Position of Element in Sorted Array

### Problem
Given an array of integers `nums` sorted in non-decreasing order, find the starting and ending position of a given `target`. If `target` is not found, return `[-1, -1]`. Must run in O(log n).

```
Input:  nums = [5,7,7,8,8,10], target = 8   → Output: [3,4]
Input:  nums = [5,7,7,8,8,10], target = 6   → Output: [-1,-1]
Input:  nums = [], target = 0               → Output: [-1,-1]
```

### Pattern Recognition
Two separate binary searches — one searching left on match (first occurrence), one searching right on match (last occurrence). Both use Template 1 (`lo <= hi`) with a `result` variable that records each valid candidate; the search continues in the direction that might yield a better candidate.

### Key Insight
Both searches share the same structure; only the "found" branch differs: first occurrence sets `hi = mid - 1` after recording (search left), last occurrence sets `lo = mid + 1` (search right). The not-found branches are identical. Running two independent O(log n) searches is still O(log n) overall.

### Approach
`firstOcc(nums, target)`: standard binary search; when `nums[mid] == target`, record `result = mid` and set `hi = mid - 1` to keep searching left. Return result (or -1). `lastOcc(nums, target)`: same but set `lo = mid + 1` on match. Return `[firstOcc, lastOcc]`.

### Solution

```js
function searchRange(nums, target) {
  return [firstOccurrence(nums, target), lastOccurrence(nums, target)];
}

function firstOccurrence(nums, target) {
  let lo = 0, hi = nums.length - 1;
  let result = -1; // best candidate for first occurrence found so far

  while (lo <= hi) {
    const mid = (lo + hi) >> 1; // left-biased: floor((lo+hi)/2)

    if (nums[mid] === target) {
      result = mid;    // mid is a valid first occurrence candidate
      hi = mid - 1;   // but there might be an earlier one — search LEFT
    } else if (nums[mid] < target) {
      lo = mid + 1;   // target must be to the right
    } else {
      hi = mid - 1;   // target must be to the left
    }
  }

  return result;
}

function lastOccurrence(nums, target) {
  let lo = 0, hi = nums.length - 1;
  let result = -1;

  while (lo <= hi) {
    const mid = (lo + hi) >> 1;

    if (nums[mid] === target) {
      result = mid;    // mid is a valid last occurrence candidate
      lo = mid + 1;   // but there might be a later one — search RIGHT
    } else if (nums[mid] < target) {
      lo = mid + 1;
    } else {
      hi = mid - 1;
    }
  }

  return result;
}
```

```
  lo=3, hi=3, mid=3. nums[3]=8 == 8 → result=3, hi=2.
  lo=3 > hi=2. Loop ends. Return 3. ✓

Last occurrence:
  lo=0, hi=5, mid=2. nums[2]=7 < 8 → lo=3.
  lo=3, hi=5, mid=4. nums[4]=8 == 8 → result=4, lo=5.
  lo=5, hi=5, mid=5. nums[5]=10 > 8 → hi=4.
  lo=5 > hi=4. Loop ends. Return 4. ✓

Output: [3, 4]. ✓

---

  lo=1>hi=0. result=-1. Return -1. ✓
```

### Complexity
- Time: O(log n) — two binary searches, each O(log n).
- Space: O(1) — only scalar variables.

### Edge Cases
- **Empty array**: `lo=0, hi=-1` → loop never executes. Returns -1. ✓
- **Single element equal to target**: both searches return index 0. Result: [0, 0].
- **Target at boundary (index 0 or n-1)**: first-occurrence search will keep going left until `lo > hi`; correctly finds index 0. Last-occurrence similar for index n-1.
- **All elements equal to target**: first occurrence searches all the way to index 0; last to index n-1. Returns [0, n-1].
- **Target between two values but absent**: all branches follow `lo = mid+1` or `hi = mid-1`; result stays -1.

### Follow-up Questions
- "Count of target?" — `lastOccurrence - firstOccurrence + 1` (if `firstOccurrence != -1`).
- "Lower bound / upper bound instead?" — `lowerBound(target)` gives insertion point of first occurrence; `upperBound(target)` gives insertion point after last. Count = upper - lower.
- "What if the array is not sorted?" — Binary search doesn't apply; must use a linear scan or a HashMap for frequency counting. O(n).

## Problem 2 — Search in Rotated Sorted Array

### Problem
Given an integer array `nums` sorted in ascending order and possibly rotated at some pivot, and a `target`, return the index of `target` or -1 if not in `nums`. No duplicates; must run in O(log n).

```
Input:  nums = [4,5,6,7,0,1,2], target = 0   → Output: 4
Input:  nums = [4,5,6,7,0,1,2], target = 3   → Output: -1
Input:  nums = [1], target = 0                → Output: -1
```

### Pattern Recognition
Modified binary search — at each step, identify the sorted half by comparing `nums[lo]` with `nums[mid]`; check if target lies within that sorted half's value range; recurse into the correct half. The rotated array's "always one sorted half" property preserves O(log n).

### Key Insight
The rotation creates at most one "break" in the sorted order. For any split at mid, one half is guaranteed to be contiguously sorted. Checking target membership in a sorted range is O(1): `lo_val <= target < mid_val` (left half) or `mid_val < target <= hi_val` (right half). This gives a definitive "search here" or "search there" at each step.

### Approach
Template 1 (`lo <= hi`). At each iteration: if `nums[mid] == target`, return mid. Else determine sorted half: `nums[lo] <= nums[mid]` means left is sorted; else right is sorted. Check if target is in the sorted half's range; if yes, search that half; if no, search the other.

### Solution

```js
function search(nums, target) {
  let lo = 0, hi = nums.length - 1;

  while (lo <= hi) {
    const mid = (lo + hi) >> 1;

    if (nums[mid] === target) return mid; // found

    if (nums[lo] <= nums[mid]) {
      // Left half [lo, mid] is sorted (no rotation break in left half)
      if (nums[lo] <= target && target < nums[mid]) {
        hi = mid - 1; // target is within the sorted left range
      } else {
        lo = mid + 1; // target must be in the right half
      }
    } else {
      // Right half [mid, hi] is sorted (rotation break is in the left half)
      if (nums[mid] < target && target <= nums[hi]) {
        lo = mid + 1; // target is within the sorted right range
      } else {
        hi = mid - 1; // target must be in the left half
      }
    }
  }

  return -1;
}
```

### Dry Run

```
nums = [4,5,6,7,0,1,2], target = 0.

lo=0, hi=6. mid=3. nums[3]=7 ≠ 0.
  nums[lo=0]=4 <= nums[mid=3]=7 → LEFT half [4,5,6,7] is sorted.
  Is 0 in [4, 7)? → 4 <= 0? NO → search RIGHT half. lo=4.

lo=4, hi=6. mid=5. nums[5]=1 ≠ 0.
  nums[lo=4]=0 <= nums[mid=5]=1 → LEFT half [0,1] is sorted.
  Is 0 in [0, 1)? → 0 <= 0 AND 0 < 1? YES → search LEFT half. hi=4.

lo=4, hi=4. mid=4. nums[4]=0 == 0. Return 4. ✓

---
nums = [4,5,6,7,0,1,2], target = 3.

lo=0,hi=6,mid=3. nums[3]=7≠3. Left sorted. 3 in [4,7)? 4<=3? NO → lo=4.
lo=4,hi=6,mid=5. nums[5]=1≠3. Left [0,1] sorted. 3 in [0,1)? 0<=3 but 3<1? NO → right. lo=6.
lo=6,hi=6,mid=6. nums[6]=2≠3. Left [2,2] sorted. 3 in [2,2)? 2<=3 but 3<2? NO → right. lo=7.
lo=7 > hi=6. Return -1. ✓

---
Boundary case: nums=[6,7,0,1,2,4,5], target=6.

lo=0,hi=6,mid=3. nums[3]=1≠6. nums[0]=6 > nums[3]=1 → RIGHT half [1,2,4,5] is sorted.

lo=0,hi=2,mid=1. nums[1]=7≠6. nums[0]=6 <= nums[1]=7 → LEFT sorted.
  6 in [6, 7)? 6<=6 AND 6<7? YES → search LEFT half. hi=0.
lo=0,hi=0,mid=0. nums[0]=6==6. Return 0. ✓
```

### Complexity
- Time: O(log n) — each iteration halves the search space.
- Space: O(1).

### Edge Cases
- **No rotation** (perfectly sorted array): `nums[lo] <= nums[mid]` is always true. Reduces to standard binary search. ✓
- **Rotation by 1** (last element moved to front): the break is at index 0; one half is always the full remaining range. ✓
- **Target at rotation point**: the condition `nums[lo] <= nums[mid]` correctly identifies which half is sorted regardless of where the rotation point is. ✓
- **Single element**: `lo=hi=0, mid=0`. If `nums[0] == target`, return 0. Else return -1.

### Follow-up Questions
- "Find the rotation index (number of positions rotated)?" — The rotation index is the index of the minimum element. Use the "find minimum in rotated array" technique (Problem 4).
- "With duplicates?" — Problem 3 below.

## Problem 3 — Search in Rotated Sorted Array II (With Duplicates)

### Problem
Same as Problem 2 but `nums` may contain duplicates. Return `true` if target exists, `false` otherwise.

```
Input:  nums = [2,5,6,0,0,1,2], target = 0  → true
Input:  nums = [2,5,6,0,0,1,2], target = 3  → false
Input:  nums = [1,0,1,1,1], target = 0      → true
```

### Pattern Recognition
Modified binary search with degenerate-case handling — same as Problem 2, but when `nums[lo] == nums[mid] == nums[hi]`, neither half can be identified as sorted. Shrink from both sides (`lo++, hi--`) to resolve the ambiguity.

### Key Insight
The single addition over Problem 2: when `nums[lo] == nums[mid]`, we can't tell if `[lo, mid]` is sorted (no break) or if the break is in it. Adding the check `nums[mid] == nums[hi]` catches the fully ambiguous case. Shrinking both pointers by 1 preserves the invariant (target can't be at these duplicate extremes since we haven't eliminated any unique positions) while resolving the ambiguity.

### Approach
Same as Problem 2 with one extra branch at the top: `if (nums[lo] === nums[mid] && nums[mid] === nums[hi]): lo++; hi--; continue`. All other branches identical.

### Solution

```js
function searchII(nums, target) {
  let lo = 0, hi = nums.length - 1;

  while (lo <= hi) {
    const mid = (lo + hi) >> 1;

    if (nums[mid] === target) return true;

    // Degenerate case: duplicates at both ends prevent determining sorted half
    if (nums[lo] === nums[mid] && nums[mid] === nums[hi]) {
      lo++;    // shrink left boundary: nums[lo] is not the answer (nums[mid]==target already checked)
      hi--;    // shrink right boundary: same reasoning
      continue;
    }

    if (nums[lo] <= nums[mid]) {
      // Left half [lo, mid] is sorted
      if (nums[lo] <= target && target < nums[mid]) {
        hi = mid - 1;
      } else {
        lo = mid + 1;
      }
    } else {
      // Right half [mid, hi] is sorted
      if (nums[mid] < target && target <= nums[hi]) {
        lo = mid + 1;
      } else {
        hi = mid - 1;
      }
    }
  }

  return false;
}
```

### Dry Run

```
nums = [1,0,1,1,1], target = 0.

lo=0,hi=4,mid=2. nums[2]=1≠0. nums[lo=0]=1, nums[mid=2]=1, nums[hi=4]=1.
  All equal → lo=1, hi=3. continue.

lo=1,hi=3,mid=2. nums[2]=1≠0. nums[lo=1]=0, nums[mid=2]=1, nums[hi=3]=1.
  Not all equal.
  nums[1]=0 <= nums[2]=1 → LEFT half [0,1] is sorted.
  Is 0 in [0, 1)? 0<=0 AND 0<1? YES → search LEFT. hi=1.

lo=1,hi=1,mid=1. nums[1]=0==0. Return true. ✓

---
Worst case: nums=[1,1,1,1,2,1,1,1,1], target=2.

All iterations with lo<hi and nums[lo]==nums[mid]==nums[hi]:
  Each peel reduces range by 2 total (lo++, hi--).
  Until target=2 is exposed at mid.
  Worst case: O(n) if target is at exactly the center surrounded by duplicates.
```

### Complexity
- Time: O(n) worst case (all duplicates with target hidden near edge), O(log n) average.
- Space: O(1).

### Edge Cases
- **All same elements, target not present**: every iteration hits the degenerate case. lo++ and hi-- until lo > hi. Returns false. ✓
- **All same elements, target present**: `nums[mid] === target` at any iteration returns true before degenerate case is fully triggered. ✓
- **Duplicates only at one end**: degenerate case fires fewer times; still worst-case O(n).

### Follow-up Questions
- "Can you guarantee O(log n) with duplicates?" — No. For `[1,1,...,1,2]` with O(n) ones, every iteration is degenerate until the 2 is exposed. O(n) is unavoidable for this input.
- "What if duplicates are bounded (at most k duplicates of any element)?" — Still O(n) worst case in the degenerate scenario.

## Problem 4 — Find Minimum in Rotated Sorted Array

### Problem
Given a sorted array that has been rotated between 1 and n times, find the minimum element. No duplicates; must run in O(log n).

```
Input:  nums = [3,4,5,1,2]      → Output: 1
Input:  nums = [4,5,6,7,0,1,2]  → Output: 0
Input:  nums = [11,13,15,17]     → Output: 11  (no rotation / full rotation)
```

### Pattern Recognition
Template 2 binary search (`lo < hi`) — compare `nums[mid]` with `nums[hi]` to determine which half contains the minimum; converge on `lo == hi` which is the minimum's index.

### Key Insight
The minimum is always on the "downhill" side of the rotation. Compare `nums[mid]` with `nums[hi]`: if `nums[mid] > nums[hi]`, the array dips down somewhere between mid+1 and hi — the minimum is in the right half (`lo = mid + 1`). If `nums[mid] <= nums[hi]`, the minimum is at mid or in the left half (`hi = mid`). Termination: `lo == hi` — both converged on the minimum's index.

### Approach
Template 2 (`lo < hi`), left-biased mid (safe because `hi = mid` is used, not `lo = mid`). Compare `nums[mid]` with `nums[hi]`: if `>`, go right (`lo = mid + 1`); else go left (`hi = mid`). Return `nums[lo]`.

### Solution

```js
function findMin(nums) {
  let lo = 0, hi = nums.length - 1;

  while (lo < hi) {
    const mid = (lo + hi) >> 1; // left-biased mid (safe: hi = mid is used, not lo = mid)

    if (nums[mid] > nums[hi]) {
      // Mid is greater than the rightmost — the dip (minimum) is in the RIGHT half
      // mid cannot be the minimum (something smaller exists to its right)
      lo = mid + 1;
    } else {
      // Mid is ≤ rightmost — the minimum is at mid or in the LEFT half
      // mid could be the minimum — keep it
      hi = mid;
    }
  }

  // lo == hi: converged on the minimum's index
  return nums[lo];
}
```

### Dry Run

```
nums = [4,5,6,7,0,1,2].

lo=0, hi=6. mid=3. nums[3]=7, nums[6]=2. 7 > 2 → min in RIGHT. lo=4.
lo=4, hi=6. mid=5. nums[5]=1, nums[6]=2. 1 < 2 → min in LEFT (or at mid). hi=5.
lo=4, hi=5. mid=4. nums[4]=0, nums[5]=1. 0 < 1 → min in LEFT. hi=4.
lo=4 == hi=4. Return nums[4]=0. ✓

---
nums = [11,13,15,17] (no rotation / identity rotation).

lo=0, hi=3. mid=1. nums[1]=13, nums[3]=17. 13 < 17 → hi=1.
lo=0, hi=1. mid=0. nums[0]=11, nums[1]=13. 11 < 13 → hi=0.
lo=0 == hi=0. Return nums[0]=11. ✓
(The minimum of an unrotated array is always the first element, correctly found.)

---
nums = [2,1] (rotated by 1).

lo=0, hi=1. mid=0. nums[0]=2, nums[1]=1. 2 > 1 → lo=1.
lo=1 == hi=1. Return nums[1]=1. ✓
```

### Complexity
- Time: O(log n) — each iteration halves the range; `lo < hi` template converges at `lo == hi`.
- Space: O(1).

### Edge Cases
- **Single element**: `lo=hi=0` → loop doesn't execute. Return `nums[0]`. ✓
- **Two elements**: one iteration. Mid=0 (left-biased). If `nums[0] > nums[1]`: lo=1. `lo==hi=1`, return nums[1]. Else hi=0, `lo==hi=0`, return nums[0]. ✓
- **No rotation (or full n rotation)**: the minimum is always found at index 0. The algorithm correctly converges on it since `nums[mid] < nums[hi]` will always send `hi` leftward.
- **With duplicates** (LeetCode 154): add degenerate case `if nums[mid] == nums[hi]: hi--`. Same O(n) worst case as Problem 3.

### Follow-up Questions
- "Also find the rotation count?" — The rotation count = index of the minimum. Return `lo` (the index), not `nums[lo]`.
- "Find maximum in rotated array?" — The maximum is always just to the left of the minimum: index `(findMinIndex - 1 + n) % n`.
- "With duplicates (LeetCode 154)?" — Add `else if (nums[mid] === nums[hi]): hi--` as an extra branch.

## Problem 5 — Search a 2D Matrix

### Problem
Given an `m × n` integer matrix where each row is sorted left-to-right and the first integer of each row is greater than the last integer of the previous row, return `true` if `target` is in the matrix, `false` otherwise. Must run in O(log(m × n)).

```
Input:
  matrix = [[1, 3,  5,  7],
            [10,11, 16, 20],
            [23,30, 34, 60]]
  target = 3   → true

Input:  same matrix, target = 13  → false
```

### Pattern Recognition
Binary search on a flattened 1D view — the matrix's structure guarantees it is a fully sorted 1D array when read row by row. Map a 1D index `mid` to `(row, col)` using integer division and modulo. Standard binary search on 0 to m×n-1.

### Key Insight
The property "each row's first element > previous row's last element" means if you flatten the matrix row by row, you get a perfectly sorted array of length m×n. A 1D index `i` maps to `matrix[floor(i/n)][i % n]`. This allows standard binary search without any special logic.

### Approach
`lo = 0`, `hi = m*n - 1`. Standard binary search: `mid = floor((lo+hi)/2)`; `row = floor(mid/n)`, `col = mid % n`; compare `matrix[row][col]` with target. Update `lo` or `hi` accordingly.

### Solution

```js
function searchMatrix(matrix, target) {
  const m = matrix.length, n = matrix[0].length;
  let lo = 0, hi = m * n - 1;

  while (lo <= hi) {
    const mid = (lo + hi) >> 1;

    // Map 1D index to 2D coordinates
    const row = Math.floor(mid / n); // which row
    const col = mid % n;             // which column within that row
    const val = matrix[row][col];

    if (val === target) return true;
    else if (val < target) lo = mid + 1;  // target is in the "right" portion
    else hi = mid - 1;                    // target is in the "left" portion
  }

  return false;
}
```

### Dry Run

```
matrix = [[1,3,5,7],[10,11,16,20],[23,30,34,60]], n=4 (cols), m=3 (rows).
target = 3. Total elements: m*n = 12. lo=0, hi=11.

Iteration 1: mid=5. row=5/4=1, col=5%4=1. matrix[1][1]=11. 11>3 → hi=4.
Iteration 2: mid=2. row=2/4=0, col=2%4=2. matrix[0][2]=5. 5>3 → hi=1.
Iteration 3: mid=0. row=0/4=0, col=0%4=0. matrix[0][0]=1. 1<3 → lo=1.
Iteration 4: mid=1. row=1/4=0, col=1%4=1. matrix[0][1]=3. 3==3 → return true. ✓

---
target = 13.

lo=0,hi=11. mid=5. val=11. 11<13 → lo=6.
lo=6,hi=11. mid=8. row=2,col=0. val=23. 23>13 → hi=7.
lo=6,hi=7. mid=6. row=1,col=2. val=16. 16>13 → hi=5.
lo=6>hi=5. Return false. ✓

Flattened view: [1,3,5,7,10,11,16,20,23,30,34,60]. 13 is not present. ✓
```

### Complexity
- Time: O(log(m×n)) = O(log m + log n) — binary search over m×n elements.
- Space: O(1).

### Edge Cases
- **Single row**: `m=1`. All mid values have `row=0`. Reduces to standard 1D binary search.
- **Single column**: `n=1`. All mid values have `col=0`. Row-by-row binary search.
- **Single element**: `lo=hi=0`, one iteration.
- **Target smaller than matrix minimum** or **larger than maximum**: search naturally exhausts to `lo > hi`. Returns false.

### Follow-up Questions
- "What if the matrix is only row-sorted and column-sorted (LeetCode 240)?" — Cannot flatten to 1D (the 1D view is NOT sorted). Use the staircase search: start at top-right `(0, n-1)`; if `matrix[r][c] > target`: `c--`; if `< target`: `r++`. O(m+n). See the Q&A discussion (Q14-Q15).
- "What is the staircase algorithm for LeetCode 240?" — `let row=0, col=n-1; while (row<m && col>=0): if (matrix[row][col]==target) return true; else if (matrix[row][col]>target) col--; else row++;`
- "Can you do LeetCode 240 in O(log(m+n))?" — No provable O(log(m+n)) algorithm is known; O(m+n) is essentially optimal for the row+column sorted structure without full-sort constraints.

## Problem 6 — Find Peak Element

### Problem
A peak element is an element strictly greater than its neighbors. Given `nums` where `nums[-1] = nums[n] = -∞`, find the index of any peak element. Must run in O(log n).

```
Input:  nums = [1,2,3,1]   → Output: 2  (nums[2]=3 is a peak)
Input:  nums = [1,2,1,3,5,6,4] → Output: 1 or 5  (multiple peaks allowed)
```

### Pattern Recognition
Template 2 binary search (`lo < hi`) on a local property — the array doesn't need to be sorted globally. The predicate: if `nums[mid] > nums[mid+1]`, we are on the "descending side" of some peak at or before mid; else we are on the "ascending side" and a peak is strictly to the right.

### Key Insight
The mountain property guarantees: if `nums[mid] > nums[mid+1]`, a peak exists in `[lo, mid]` (the descending slope means the slope was ascending before mid, so a peak exists at mid or to its left). If `nums[mid] < nums[mid+1]`, the slope is ascending at mid, so a peak exists in `[mid+1, hi]` (must ascend and eventually descend). This binary elimination works even on non-monotone arrays.

### Approach
Template 2 (`lo < hi`), left-biased mid (safe because `hi = mid` keeps mid as candidate). Compare `nums[mid]` with `nums[mid+1]`: if `>`, peak is at mid or left (`hi = mid`); else peak is right (`lo = mid + 1`). Termination: `lo == hi == peak index`.

### Solution

```js
function findPeakElement(nums) {
  let lo = 0, hi = nums.length - 1;

  while (lo < hi) {
    const mid = (lo + hi) >> 1; // left-biased: when lo=hi-1, mid=lo (safe with hi=mid)

    if (nums[mid] > nums[mid + 1]) {
      // Descending at mid: peak is at mid or to the LEFT of mid
      hi = mid; // mid is still a candidate — don't exclude it
    } else {
      // Ascending at mid: peak is strictly to the RIGHT of mid
      lo = mid + 1; // mid cannot be the peak
    }
  }

  // lo == hi: converged on a peak
  return lo;
}
```

### Dry Run

```
nums = [1,2,1,3,5,6,4]. n=7.

lo=0,hi=6. mid=3. nums[3]=3, nums[4]=5. 3 < 5 → ascending → lo=4.
lo=4,hi=6. mid=5. nums[5]=6, nums[6]=4. 6 > 4 → descending → hi=5.
lo=4,hi=5. mid=4. nums[4]=5, nums[5]=6. 5 < 6 → ascending → lo=5.
lo=5 == hi=5. Return 5. ✓ (nums[5]=6 > nums[4]=5 and nums[5]=6 > nums[6]=4)

---
nums = [1,2,3,1].

lo=0,hi=3. mid=1. nums[1]=2, nums[2]=3. 2 < 3 → lo=2.
lo=2,hi=3. mid=2. nums[2]=3, nums[3]=1. 3 > 1 → hi=2.
lo=2 == hi=2. Return 2. ✓ (nums[2]=3 > nums[1]=2 and nums[2]=3 > nums[3]=1)

---
Edge: nums=[1] (single element). lo=hi=0, loop doesn't execute. Return 0.
  nums[0]=1 > nums[-1]=-∞ and nums[0]=1 > nums[1]=-∞ → peak by definition ✓

Edge: nums=[1,2] (ascending). lo=0,hi=1. mid=0. nums[0]=1<nums[1]=2 → lo=1. Return 1.
  nums[1]=2 > nums[0]=1 and nums[1]=2 > nums[2]=-∞ ✓
```

### Complexity
- Time: O(log n) — Template 2 halves the range each iteration.
- Space: O(1).

### Edge Cases
- **Single element**: loop never executes; returns 0. Valid peak by boundary convention (`nums[-1] = -∞`).
- **Monotone increasing** `[1,2,3,4]`: every iteration sends `lo = mid + 1`; converges at index n-1. `nums[n-1]` is always a peak (its right boundary is -∞). ✓
- **Monotone decreasing** `[4,3,2,1]`: first iteration: `nums[mid] > nums[mid+1]` → `hi = mid`. Converges at 0. `nums[0]` is a peak. ✓
- **Why `mid+1` is always a valid access**: `lo < hi` guarantees `mid < hi <= n-1`, so `mid+1 <= hi <= n-1` — always within bounds. Never access out-of-bounds.

### Follow-up Questions
- "Find ALL peaks?" — Linear scan: check `nums[i] > nums[i-1] && nums[i] > nums[i+1]` for each i. O(n). Binary search only finds one.
- "What if the array has flat regions (plateaus)?** — `nums[i] == nums[i+1]` breaks the strict mountain property. Either cannot use binary search or need additional logic to handle equality. Most implementations either go right on equality (`lo = mid+1`) and may miss a peak in the plateau, or require a problem constraint that all elements are distinct.
- "Find local minimum instead of local maximum?" — Reverse the condition: `if nums[mid] < nums[mid+1]: hi = mid; else lo = mid+1`. The same asymptotic argument applies.

## Quick Reference — Binary Search Variant Decision Tree

```
What am I searching for?
│
├── EXACT MATCH in sorted array?
│   └── Template 1 (lo <= hi). Standard update: lo=mid+1 or hi=mid-1.
│       Return mid on match, -1 if loop exits.
│
├── FIRST OCCURRENCE (leftmost) of target?
│   └── Template 1 with result variable.
│       On match: result=mid; hi=mid-1  (keep searching LEFT).
│       On exit: return result (or -1).
│       Equivalently: lowerBound(target) — first index where nums[i] >= target.
│
├── LAST OCCURRENCE (rightmost) of target?
│   └── Template 1 with result variable.
│       On match: result=mid; lo=mid+1  (keep searching RIGHT).
│       On exit: return result (or -1).
│       Equivalently: upperBound(target) - 1.
│
├── COUNT of target?
│   └── lastOccurrence - firstOccurrence + 1  (if firstOccurrence != -1 else 0).
│       Or: upperBound(target) - lowerBound(target).
│
├── SEARCH in ROTATED sorted array (no duplicates)?
│   └── Template 1. At each step: identify sorted half (nums[lo] <= nums[mid] → left sorted).
│       Check if target in sorted half's range. Search that half or the other.
│
├── SEARCH in ROTATED sorted array (WITH duplicates)?
│   └── Same as above PLUS: if nums[lo]==nums[mid]==nums[hi]: lo++; hi--; continue.
│       O(n) worst case, O(log n) average.
│
├── MINIMUM in ROTATED sorted array?
│   └── Template 2 (lo < hi). Left-biased mid.
│       if nums[mid] > nums[hi]: lo=mid+1  (min is right).
│       else: hi=mid                        (min is at mid or left).
│       Return nums[lo].
│
├── PEAK ELEMENT?
│   └── Template 2 (lo < hi). Left-biased mid.
│       if nums[mid] > nums[mid+1]: hi=mid  (peak at mid or left).
│       else: lo=mid+1                       (peak strictly right).
│       Return lo.
│
├── SEARCH in 2D MATRIX (row-sorted AND prev row last < next row first)?
│   └── Flatten to 1D: mid maps to matrix[floor(mid/n)][mid%n]. Standard binary search.
│       O(log(m*n)).
│
└── SEARCH in 2D MATRIX (row-sorted AND column-sorted only)?
    └── Staircase from top-right corner (0, n-1).
        if matrix[r][c] > target: c--  (eliminate this column here).
        if matrix[r][c] < target: r++  (eliminate this row here).
        O(m+n).
```

## Common Bugs Checklist

Before submitting any binary search solution, verify:

1. **Mid computation overflows for large lo and hi?** — `(lo + hi) / 2` can overflow a 32-bit integer when both lo and hi are near `Integer.MAX_VALUE`. Safe: `lo + (hi - lo) / 2` or bit-shift `(lo + hi) >> 1` (JS uses 32-bit signed for bitwise ops, safe for typical array sizes). In JavaScript, standard numbers are 64-bit floats — overflow is not a practical issue for array indices, but the bit-shift form is idiomatic.

2. **Infinite loop when `lo = hi - 1`?** — With left-biased mid: `mid = lo`. If the code can set `lo = mid = lo` (no progress), infinite loop. Trace: `lo=3, hi=4, mid=3`. If the update is `lo = mid = 3`, infinite loop. Fix: use right-biased mid `(lo + hi + 1) >> 1` when `lo = mid` is a possible update path. Alternatively, change the update to `lo = mid + 1` so lo always advances past mid.

3. **Template 2 (`lo < hi`) using `hi = mid - 1`?** — In `lo < hi` template, `hi = mid - 1` can skip the answer when `mid` is the correct answer. Always use `hi = mid` (keeps mid as a candidate) in this template. Only `lo = mid + 1` is safe for the advancing-lo branch.

4. **Rotated array: checking `nums[lo] <= nums[mid]` with `<=` not `<`?** — When `nums[lo] == nums[mid]`, the left half may still be sorted (all elements equal, or nums[lo] happens to equal nums[mid] without a rotation). The `<=` correctly includes this case as "left half is sorted." Using `<` would misclassify the equal case as "right sorted," potentially missing the target in a sorted equal-left-half.

5. **Rotated array: boundary condition `nums[lo] <= target < nums[mid]` uses strict `<` for mid?** — Target at `nums[mid]` is already checked before this (`nums[mid] === target` returns immediately). So `target < nums[mid]` (strict) is correct — if `target == nums[mid]`, it was already returned. Using `<=` would include mid in the left-search range, which is fine but redundant.

6. **Find minimum rotated: comparing `nums[mid]` with `nums[hi]` not `nums[lo]`?** — Using `nums[lo]` for the find-minimum direction is unreliable: when `nums[lo] < nums[mid]`, the left half appears sorted, but the minimum could still be at lo (if the whole array is sorted). Comparing with `nums[hi]` is reliable: `nums[mid] > nums[hi]` definitively means the minimum is in [mid+1, hi].

7. **Peak element: `mid+1` access is safe only when `lo < hi`?** — When `lo < hi`, we have `mid = floor((lo+hi)/2) < hi <= n-1`, so `mid+1 <= n-1` — always valid. If the template were `lo <= hi`, mid could equal hi = n-1, making `nums[mid+1]` an out-of-bounds access. The `lo < hi` template guarantees safety.

8. **2D matrix index mapping: dividing by `n` (columns), not `m` (rows)?** — `mid / n` gives the row, `mid % n` gives the column. Using `m` instead of `n` would give wrong (row, col) pairs when m ≠ n. Always divide by the column count (`n = matrix[0].length`) for row computation.

9. **First/last occurrence: initializing `result = -1`, not `result = 0`?** — If result is initialized to 0 and the target is not found, it incorrectly returns 0 (pointing to the first element). Always initialize to -1 as the sentinel for "not found." Only update result when `nums[mid] === target`.

10. **Rotated array with duplicates: not using `continue` after `lo++; hi--`?** — After shrinking both boundaries for the degenerate case, the loop should restart from the top (re-evaluate mid with new lo/hi). Without `continue`, the code falls through to the sorted-half logic with the same stale mid value, potentially reading out-of-bounds or making a wrong decision.

11. **Lower bound returning `n` (not -1) when target is absent?** — `lowerBound` returns an index in `[0, n]`. When target > all elements, it returns `n` (past the end). This is CORRECT for the lower bound abstraction (target would be inserted at position n). But when used to find a specific occurrence, always check `result < n && nums[result] === target` before using the result.

12. **Template 2 starting `hi = nums.length` (not `n-1`) for lower/upper bound?** — Lower and upper bound searches need `hi = n` (one past the last index) to allow the answer to be "insert at the end." The final answer `lo` is in `[0, n]`. This is different from standard binary search where `hi = n-1`. Using `hi = n-1` would miss the "insert at end" case when target is larger than all elements.

---

**Final Tip:** At the 5 YOE level, the decisive signal for binary search is framing the problem as a predicate and stating the invariant before touching code. For first occurrence: *"I'm looking for the leftmost index where nums[i] == target. My invariant is that the first occurrence, if it exists, is in [lo, hi]. On a match at mid, I record mid as a candidate and set hi = mid - 1 to search left — the invariant is preserved because the first occurrence can only be at mid or further left."* For rotated array: *"I identify which half is sorted by comparing nums[lo] with nums[mid]; if nums[lo] <= nums[mid] the left half is sorted, and I can O(1)-check if target is in [nums[lo], nums[mid]) — if yes, search left; otherwise search right. The key invariant: in a singly-rotated array, at least one half is always contiguously sorted."* Stating the invariant, the "found" update, and the "not-found" update in three sentences before writing any code is the mark of a senior who cannot be tripped by off-by-one errors.
