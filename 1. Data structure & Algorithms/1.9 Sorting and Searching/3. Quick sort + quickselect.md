## Part 1 — Theory & Interview Q&A

### Section 1: Fundamentals

**Q1. What is Quick Sort, and what is its defining structural idea?**
A: Quick Sort is a **divide-and-conquer** comparison-based sorting algorithm. Its defining idea: pick a **pivot** element, **partition** the array into three regions (elements less than the pivot, elements equal to the pivot, elements greater than the pivot), then recursively sort the two "less than" and "greater than" sub-arrays. The pivot is already in its correct final position after partitioning — this is the key property that makes the algorithm work. Unlike Merge Sort, Quick Sort sorts **in-place** (no auxiliary array for the merge step), and unlike Heap Sort, its cache performance is excellent due to sequential array access during partitioning.

**Q2. What is the difference between the Lomuto and Hoare partition schemes, and which is more commonly taught?**
A: The two classic partition schemes differ in how they maintain the pivot's invariant:
- **Lomuto**: uses a single scan pointer `i` and a "less-than boundary" pointer `j`. Places the pivot at the end of the array, sweeps `i` from left to right, swapping elements less than the pivot to the left side as they're encountered. Simple to implement and reason about. Pivot ends up at its correct final position after partitioning (index `j`).
- **Hoare**: uses two converging pointers starting at opposite ends of the array, advancing inward until they find a mis-ordered pair, then swapping. Faster in practice (fewer swaps on average), but the pivot does NOT necessarily end up at its correct position — it ends up somewhere in the left partition, requiring the partition to return a split point (not the pivot's index). More subtle to implement correctly.

Lomuto is more commonly taught in interviews due to its straightforward invariant; Hoare is faster in practice and what most production sorting libraries use.

```js
// Lomuto partition scheme
function partitionLomuto(arr, low, high) {
  const pivot = arr[high]; // pivot placed at the end
  let i = low - 1;         // i tracks the boundary of the "less than" region

  for (let j = low; j < high; j++) {
    if (arr[j] <= pivot) {
      i++;
      [arr[i], arr[j]] = [arr[j], arr[i]];
    }
  }

  [arr[i + 1], arr[high]] = [arr[high], arr[i + 1]]; // place pivot in its final position
  return i + 1; // return pivot's final index
}

function quickSortLomuto(arr, low = 0, high = arr.length - 1) {
  if (low < high) {
    const pivotIdx = partitionLomuto(arr, low, high);
    quickSortLomuto(arr, low, pivotIdx - 1);
    quickSortLomuto(arr, pivotIdx + 1, high);
  }
}
```

**Q3. What is Quick Sort's time complexity in the best, average, and worst cases, and what drives each?**
A:
- **Best case O(n log n)**: the pivot always lands exactly in the middle of the array, producing two equal-sized sub-arrays at every level of recursion — log n levels, each doing O(n) partition work.
- **Average case O(n log n)**: with a randomly chosen pivot, the expected split is close enough to even that the recursion tree has O(log n) expected depth — this holds over all possible input permutations, making O(n log n) the **expected** time even though individual instances may be worse.
- **Worst case O(n²)**: the pivot is always the smallest or largest element, producing maximally unbalanced splits (one sub-array of size 0, one of size n-1). This happens deterministically on already-sorted (or reverse-sorted) input with a naive first-or-last-element pivot choice — precisely why random pivot selection or median-of-three pivot selection is used in practice.

**Q4. What are the standard strategies for avoiding Quick Sort's O(n²) worst case?**
A: Three common strategies, often combined:
1. **Random pivot selection**: choose a random index as the pivot (or swap a random element into the `high` position before a Lomuto partition). Makes the worst case **highly improbable** (exponentially unlikely for any fixed input), turning the worst case into an expected-O(n log n) algorithm against adversarial inputs.
2. **Median-of-three pivot**: choose the median of the first, middle, and last elements as the pivot. Eliminates the worst case on pre-sorted or reverse-sorted inputs specifically (the most common real-world adversarial inputs), with minimal overhead.
3. **Introsort**: begin with Quick Sort, but switch to **Heap Sort** when recursion depth exceeds O(log n). This guarantees O(n log n) worst case while retaining Quick Sort's excellent average-case performance. Used in many production sort implementations (C++ `std::sort`, Rust's `slice::sort_unstable`).

**Q5. Why is Quick Sort's average-case performance better than Merge Sort in practice despite both being O(n log n)?**
A: Quick Sort typically outperforms Merge Sort in practice for three reasons:
1. **Cache efficiency**: Quick Sort's partition step accesses array elements **sequentially** (scanning left-to-right), which is extremely cache-friendly. Merge Sort's merge step accesses two separate sub-arrays and writes to a third auxiliary array, causing more cache misses.
2. **No auxiliary space**: Quick Sort sorts in-place (O(log n) stack space only). Merge Sort requires O(n) extra space for the auxiliary merge array, which both costs memory and adds copying overhead.
3. **Small constant factor**: the partition step does very little work per element (a comparison and occasional swap), giving Quick Sort a smaller constant factor than Merge Sort's merge step even at the same asymptotic level.

The trade-off: Quick Sort's worst case is O(n²), while Merge Sort's worst case is O(n log n); and Merge Sort is **stable** (preserves relative order of equal elements) while Quick Sort (with standard schemes) is not.

### Section 2: Partitioning Details

**Q6. What exactly is the invariant maintained by the Lomuto partition, and why does it guarantee the pivot lands in its correct sorted position?**
A: Lomuto's invariant after the `for` loop: `arr[low..i]` are all ≤ `pivot`, `arr[i+1..high-1]` are all > `pivot`, and `arr[high]` is the pivot itself. After the final swap (`arr[i+1]` ↔ `arr[high]`), the pivot moves from index `high` to index `i+1`. Everything to its left is ≤ pivot, everything to its right (from `i+2` onward) is > pivot — exactly the partition-around-pivot invariant. Since no element less than the pivot can appear to the pivot's right, and no element greater can appear to its left, the pivot is now in its correct final sorted position regardless of what further sorting happens to the two sub-arrays.

**Q7. How does the Hoare partition scheme work, and what is the key subtlety about its return value?**
A: Hoare starts two pointers at the extreme ends of the array (`lo` and `hi`), moves them toward each other, swapping elements that are on the wrong side (a large element on the left, a small element on the right), until the pointers cross. The pivot (typically `arr[low]`) is not explicitly moved — it ends up somewhere in the left partition.

```js
function partitionHoare(arr, low, high) {
  const pivot = arr[low]; // pivot from the left end
  let lo = low - 1, hi = high + 1;

  while (true) {
    do { lo++; } while (arr[lo] < pivot);
    do { hi--; } while (arr[hi] > pivot);
    if (lo >= hi) return hi; // return the split point, NOT necessarily the pivot's index
    [arr[lo], arr[hi]] = [arr[hi], arr[lo]];
  }
}

function quickSortHoare(arr, low = 0, high = arr.length - 1) {
  if (low < high) {
    const splitIdx = partitionHoare(arr, low, high);
    quickSortHoare(arr, low, splitIdx);     // NOTE: includes splitIdx in the left partition
    quickSortHoare(arr, splitIdx + 1, high);
  }
}
```

The critical subtlety: the return value is a **split index**, not the pivot's final position. Both recursive calls include the split index in one of their sub-arrays (the left call uses `low..splitIdx`, not `low..splitIdx-1` as in Lomuto). This is an easy source of bugs — using Lomuto's recursive call structure with Hoare's partition causes infinite recursion.

**Q8. What is 3-way partitioning (Dutch National Flag), and when is it important for Quick Sort?**
A: Standard 2-way partitioning splits around the pivot into "≤ pivot" and "> pivot" regions, putting elements equal to the pivot on the left side — these equal elements get repeatedly re-sorted in sub-calls even though they're already in their correct relative position. **3-way partitioning** (from the Dutch National Flag guide in this series) explicitly creates three regions: `< pivot`, `== pivot`, `> pivot`, and recurses only into the `< pivot` and `> pivot` sub-arrays, skipping the `== pivot` region entirely. This makes Quick Sort **O(n)** on arrays of all identical elements (instead of the O(n²) that standard 2-way partitioning suffers on such inputs) and O(n k / n-k) style improvements when there are many duplicate values — crucial for datasets with low value cardinality (e.g., sorting by a boolean field, or by a 2-value enum).

```js
function quickSort3Way(arr, low = 0, high = arr.length - 1) {
  if (low >= high) return;

  const pivot = arr[low];
  let lt = low, gt = high, i = low + 1;

  while (i <= gt) {
    if (arr[i] < pivot) {
      [arr[lt], arr[i]] = [arr[i], arr[lt]]; lt++; i++;
    } else if (arr[i] > pivot) {
      [arr[i], arr[gt]] = [arr[gt], arr[i]]; gt--;
    } else {
      i++;
    }
  }
  // arr[low..lt-1] < pivot, arr[lt..gt] == pivot, arr[gt+1..high] > pivot
  quickSort3Way(arr, low, lt - 1);
  quickSort3Way(arr, gt + 1, high);
}
```

### Section 3: Quickselect

**Q9. What is Quickselect, and how does it find the k-th smallest element in O(n) average time?**
A: Quickselect is a **selection algorithm** derived from Quick Sort — it finds the k-th smallest element (or equivalently, the element that would be at index `k` in the sorted array) without fully sorting the array. After each partition step, the pivot lands at its correct sorted position `p`. If `p === k`, the pivot is the answer. If `p > k`, the k-th smallest is in the left sub-array; if `p < k`, it's in the right sub-array. Crucially, only ONE sub-array is recursed into (unlike Quick Sort which recurses into both), reducing the expected work from O(n log n) to **O(n) average case**.

```js
function quickSelect(arr, k, low = 0, high = arr.length - 1) {
  if (low === high) return arr[low];

  const pivotIdx = partitionLomuto(arr, low, high);

  if (pivotIdx === k) {
    return arr[pivotIdx];
  } else if (pivotIdx > k) {
    return quickSelect(arr, k, low, pivotIdx - 1); // k-th is in the left partition
  } else {
    return quickSelect(arr, k, pivotIdx + 1, high); // k-th is in the right partition
  }
}

// Usage: find the k-th smallest (1-indexed) element
// quickSelect(arr, k - 1) for 0-indexed (k-th smallest = index k-1 in sorted order)
```

**Q10. Why is Quickselect's average case O(n) and not O(n log n) like Quick Sort?**
A: In Quick Sort, after each partition, BOTH sub-arrays are sorted recursively — the total work across all recursive calls sums to O(n log n) because every element participates in O(log n) partition steps on average. In Quickselect, after each partition, only ONE sub-array is processed further (the one containing the k-th element). On average (with random pivots), each partition step reduces the problem size by roughly half, giving a geometric series of work: `n + n/2 + n/4 + ... = 2n = O(n)` total work in expectation. The key is that discarded sub-arrays require zero further work.

**Q11. What is Quickselect's worst-case time complexity, and how does it arise?**
A: O(n²) worst case — same pathological scenario as Quick Sort: always picking the minimum or maximum element as pivot causes every partition to produce one empty sub-array and one of size n-1, requiring n recursive calls each doing O(n) work. With random pivot selection, this worst case is extremely improbable. The **deterministic O(n) worst-case** selection algorithm is **Median of Medians** (also called BFPRT), which cleverly picks a pivot guaranteed to split the array at least 30/70, ensuring O(n) worst-case time — but with a much larger constant factor than Quickselect's average case, making it primarily of theoretical interest (Quickselect is faster in practice).

**Q12. How does Quickselect differ from Quick Sort in terms of what it returns and what it does to the array?**
A: Quickselect **modifies the input array** (it partitions in-place, same as Quick Sort) and returns the k-th smallest value. After Quickselect completes, the k-th smallest element is at index `k`, all elements before index `k` are less than or equal to it (but not necessarily sorted among themselves), and all elements after index `k` are greater than or equal to it (but also not sorted). If you need the actual k-th value without modifying the array, you'd need to work on a copy. This is distinct from a pure "find the value" operation — Quickselect is fundamentally a partial-sorting algorithm.

### Section 4: Advanced Patterns

**Q13. How does "find the k-th largest element" differ from "find the k-th smallest," and what is the index translation?**
A: The k-th largest element in an array of `n` elements is the `(n - k + 1)`-th smallest element (1-indexed), or equivalently at sorted index `n - k` (0-indexed). So `quickSelect(arr, n - k)` finds the k-th largest using the k-th-smallest Quickselect. Alternatively, many implementations of "k-th largest" simply use a **max-heap** approach (build a max-heap, extract max k times, O(n + k log n)) or a **min-heap of size k** (maintain the k largest seen so far in a min-heap, O(n log k)) — both are valid and often simpler than Quickselect for small k. Quickselect is preferred when k is of the same order as n (neither very small nor very large relative to n).

**Q14. How does "sort colors" (0/1/2 sort) relate to the 3-way partition step of Quick Sort?**
A: The Dutch National Flag problem (sort an array of 0s, 1s, and 2s) is exactly the 3-way partition step of Quick Sort with pivot = 1: partition into `< 1` (0s), `== 1` (1s), `> 1` (2s) regions in O(n) time using three pointers. This connection shows that 3-way Quick Sort's partition step is a generalizable primitive that solves the "sort k distinct values in O(n)" problem for any fixed k, not just 3 — and the Dutch National Flag guide in this series covers this in detail as a standalone algorithm.

**Q15. When is Quick Sort NOT the right choice, and what should be used instead?**
A:
- **Stability required**: Quick Sort (with standard schemes) is not stable — equal elements may be reordered. Use Merge Sort or Timsort for stable sorting.
- **Guaranteed O(n log n) worst case required**: Quick Sort's O(n²) worst case may be unacceptable in real-time systems or security contexts (where adversarial inputs could exploit worst-case behavior — a "quicksort DoS" attack). Use Merge Sort, Heap Sort, or Introsort.
- **Linked lists**: Quick Sort's random access into an array (to implement efficient partition with swaps) doesn't translate well to linked lists. Merge Sort is the standard O(n log n) sort for linked lists.
- **External sorting (data too large for RAM)**: Merge Sort's sequential access pattern makes it ideal for external sorting; Quick Sort's random partition step causes excessive I/O seeks.
- **Very small k out of large n (find k-th element)**: A min-heap or max-heap of size k is O(n log k) and simpler than Quickselect; for very small k (like k=1, i.e., finding the minimum), a single linear scan suffices.

### Section 5: Scenario / Interview-Style Questions

**Q16. "Implement an in-place Quick Sort. Your interviewer asks: what happens on an already-sorted array with your implementation?"**
A: With a naive last-element pivot choice (Lomuto) on an already-sorted array, every partition step picks the largest remaining element as the pivot — each partition produces one empty sub-array and one of size n-1, causing O(n) levels of recursion each doing O(n) work, giving O(n²) time. I'd mention three fixes: (1) random pivot — swap a randomly chosen element into the `high` position before partitioning, making this worst case exponentially unlikely; (2) median-of-three — pick the median of `arr[low]`, `arr[mid]`, `arr[high]` as the pivot, which avoids worst-case on sorted/reverse-sorted inputs; (3) switch to Insertion Sort for small sub-arrays (a standard optimization that also avoids deep recursion on tiny sub-arrays that are likely nearly-sorted).

**Q17. "Explain why Quickselect is O(n) average case using an informal recurrence argument."**
A: With a random pivot, the partition splits the array somewhere in the "middle half" (between the 25th and 75th percentile) at least half the time. Each such split reduces the problem to at most 3n/4 of its original size. Even in the pessimistic case where we only make progress half the time, the expected total work is bounded by: n (current level) + 3n/4 (next level) + (3/4)²n + ... = n × (1/(1 - 3/4)) = 4n = O(n). More precisely, the exact expected number of comparisons is around 3.4n, well within O(n). The intuition: unlike Quick Sort where both halves must be processed (paying for the sum of all levels), Quickselect throws away the half that doesn't contain the target, so the total work is dominated by the first (largest) partitioning step.

**Q18. "A colleague says 'just use `Array.sort()` for finding the k-th largest — why bother with Quickselect?' How do you respond?"**
A: For small arrays or one-off queries, `Array.sort()` is perfectly fine — simple, correct, battle-tested. But for large arrays or performance-critical code, Quickselect is materially better: `Array.sort()` is O(n log n) while Quickselect is O(n) average — for n = 10 million, that's a 20-30× difference in the number of operations. Additionally, `Array.sort()` modifies the sort order of the entire array (a side effect that callers may not want), while Quickselect's modification (partial sort around the k-th element) is more limited. The right choice depends on context: correctness-first code → `sort()`; performance-critical selection from large arrays → Quickselect.

**Q19. "How would you find the top k elements (not just the k-th one) efficiently?"**
A: Three approaches depending on constraints:
1. **Quickselect + scan**: run Quickselect to place the k-th largest at index `n-k` (0-indexed). All elements from `n-k` onward are the top k, already partially partitioned. O(n) average time. Doesn't return them in sorted order.
2. **Min-heap of size k**: scan the array maintaining a min-heap of the k largest seen so far. O(n log k) time, O(k) space. Returns the top k but not in sorted order.
3. **Sort + take last k**: O(n log n). Simple, returns top k in sorted order. Overkill if k << n.

For k << n, the min-heap approach is excellent. For k close to n, Quickselect is better. For a one-liner where performance isn't critical, sort and slice.

## Problem 1 — Quick Sort (Full Implementation with Random Pivot)

### Problem
Implement Quick Sort to sort an array of integers in-place in ascending order, using a random pivot to avoid the worst case on sorted inputs.

```
Input:  [3, 6, 8, 10, 1, 2, 1]
Output: [1, 1, 2, 3, 6, 8, 10]
```

### Pattern Recognition
Divide-and-conquer: pick a pivot, partition around it (pivot moves to its final sorted position), recursively sort the two resulting sub-arrays.

### Key Insight
After each partition, the pivot is permanently placed in its correct sorted position — no further work is needed for that element. The recursive calls handle only the strict left and right sub-arrays, excluding the pivot. This is what makes Quick Sort correct: every element eventually becomes a pivot and is placed in its final position.

### Approach
1. Base case: sub-array of size 0 or 1 is already sorted.
2. Pick a random pivot index, swap it to the `high` position (Lomuto variant).
3. Partition: scan left-to-right, maintaining a boundary `i` such that everything at `arr[low..i]` is ≤ pivot. Place pivot at `i+1` after the scan.
4. Recursively sort `arr[low..pivotIdx-1]` and `arr[pivotIdx+1..high]`.

### Solution

```js
function quickSort(arr, low = 0, high = arr.length - 1) {
  if (low >= high) return; // base case: 0 or 1 elements, already sorted

  // random pivot: swap a randomly chosen element into the high position
  const randomIdx = low + Math.floor(Math.random() * (high - low + 1));
  [arr[randomIdx], arr[high]] = [arr[high], arr[randomIdx]];

  const pivotIdx = partition(arr, low, high);

  // pivot is now at its final sorted position — exclude it from both recursive calls
  quickSort(arr, low, pivotIdx - 1);
  quickSort(arr, pivotIdx + 1, high);
}

function partition(arr, low, high) {
  const pivot = arr[high]; // pivot is now at the end after the random swap
  let i = low - 1;         // i is the boundary: arr[low..i] <= pivot

  for (let j = low; j < high; j++) {
    if (arr[j] <= pivot) {
      i++;
      [arr[i], arr[j]] = [arr[j], arr[i]]; // bring arr[j] into the "<=pivot" region
    }
    // if arr[j] > pivot: leave it where it is, the ">pivot" region grows implicitly
  }

  // place the pivot at the boundary between the two regions
  [arr[i + 1], arr[high]] = [arr[high], arr[i + 1]];
  return i + 1; // the pivot's final index
}
```


### Complexity
- Time: O(n log n) expected with random pivot (O(n²) worst case is exponentially unlikely).
- Space: O(log n) average stack depth (O(n) worst case without tail-call optimization or explicit stack limiting).

### Edge Cases
- Empty array or single element: `low >= high` base case triggers immediately, no-op.
- All identical elements: standard 2-way Lomuto still works correctly (all elements are "≤ pivot," pivot ends at the rightmost position after each partition) but runs in O(n²) time. Use 3-way partitioning (Q8, Problem 5) if many duplicates are expected.
- Already sorted ascending: random pivot makes this no worse than average on expectation.
- Two-element sub-array: one comparison, one possible swap, immediate return after one partition level.

### Follow-up Questions
- "Implement this without recursion (iteratively)?" → Use an explicit stack pushing `[low, high]` pairs instead of recursive calls; process pairs until the stack is empty.
- "Add the small-sub-array optimization (switch to Insertion Sort for sub-arrays below a threshold)?" → Add `if (high - low + 1 <= 10) { insertionSort(arr, low, high); return; }` at the top of `quickSort`. Insertion Sort outperforms Quick Sort on small arrays due to lower overhead.

## Problem 2 — Kth Largest Element in an Array (Quickselect)

### Problem
Given an integer array `nums` and an integer `k`, return the k-th largest element in the array. Note: the k-th largest is the k-th element in sorted descending order — not the k-th distinct element.

```
Input:  nums = [3,2,1,5,6,4], k = 2
Output: 5

Input:  nums = [3,2,3,1,2,4,5,5,6], k = 4
Output: 4
```

### Pattern Recognition
Quickselect — finding the k-th order statistic in O(n) average time by partitioning and recursing into only the relevant sub-array.

### Key Insight
The k-th largest is at index `n - k` in 0-indexed sorted ascending order. After partitioning, if the pivot lands exactly at `n - k`, we're done. Otherwise, recurse into only the sub-array containing index `n - k`.

### Approach
Translate "k-th largest" to a target index: `targetIdx = n - k`. Partition around a random pivot. If `pivotIdx === targetIdx`, return `arr[pivotIdx]`. If `pivotIdx > targetIdx`, the answer is to the left; if `pivotIdx < targetIdx`, it's to the right. Repeat in only the relevant sub-array.

### Solution

```js
function findKthLargest(nums, k) {
  const targetIdx = nums.length - k; // k-th largest = targetIdx-th smallest (0-indexed)
  return quickSelect(nums, 0, nums.length - 1, targetIdx);
}

function quickSelect(arr, low, high, targetIdx) {
  if (low === high) return arr[low]; // only one element — must be the answer

  // random pivot
  const randomIdx = low + Math.floor(Math.random() * (high - low + 1));
  [arr[randomIdx], arr[high]] = [arr[high], arr[randomIdx]];

  const pivotIdx = partition(arr, low, high);

  if (pivotIdx === targetIdx) {
    return arr[pivotIdx];              // pivot is at the exact target index
  } else if (pivotIdx > targetIdx) {
    return quickSelect(arr, low, pivotIdx - 1, targetIdx);   // target is in the left partition
  } else {
    return quickSelect(arr, pivotIdx + 1, high, targetIdx);  // target is in the right partition
  }
}

function partition(arr, low, high) {
  const pivot = arr[high];
  let i = low - 1;

  for (let j = low; j < high; j++) {
    if (arr[j] <= pivot) {
      i++;
      [arr[i], arr[j]] = [arr[j], arr[i]];
    }
  }

  [arr[i + 1], arr[high]] = [arr[high], arr[i + 1]];
  return i + 1;
}
```

```
j=4: 5<=6 → i=4, swap(4,4) → no change
swap arr[5]↔arr[5] → no change
pivotIdx=5

pivotIdx(5) > targetIdx(4) → recurse left: quickSelect(arr, 4, 4, 4)

low==high → return arr[4] = 5 ✓
```

### Complexity
- Time: O(n) average (expected) with random pivot. O(n²) worst case.
- Space: O(log n) average stack depth, O(n) worst case.

### Edge Cases
- `k = 1` (maximum element): `targetIdx = n-1`; quickselect finds the element that would be at the last position in sorted order.
- `k = n` (minimum element): `targetIdx = 0`; quickselect finds the minimum.
- All identical elements: every partition results in a pivot at one position, all elements equal → O(n²) with 2-way partition; use 3-way partition for better performance.
- `k > n`: invalid input by problem constraints; typically guaranteed `1 ≤ k ≤ n`.

### Follow-up Questions
- "What if the array cannot be modified?" → Work on a copy (`[...nums]`) before calling Quickselect, adding O(n) space overhead.
- "What if you need to call this many times with different k values on the same large array?" → Pre-sort once (O(n log n)) and then each query is O(1) indexed access — better than O(n) × (number of queries) from repeated Quickselect.

## Problem 3 — Sort an Array (Pure Quick Sort, No Library)

### Problem
Given an array of integers `nums`, sort it in ascending order and return it. You must not use any built-in sort functions.

```
Input:  nums = [5, 2, 3, 1]
Output: [1, 2, 3, 5]

Input:  nums = [5, 1, 1, 2, 0, 0]
Output: [0, 0, 1, 1, 2, 5]
```

### Pattern Recognition
Direct Quick Sort implementation — the interviewer wants to verify you can implement the full algorithm cleanly, handle edge cases, and ideally mention the random-pivot optimization.

### Key Insight
Same as Problem 1, but framed as a standard LeetCode-style problem where the expected answer demonstrates knowledge of Quick Sort internals rather than using a black-box sort.

### Approach
Identical to Problem 1. The duplicate elements (`[5,1,1,2,0,0]`) test whether your partition correctly handles equals (Lomuto's `≤ pivot` condition handles this without requiring 3-way partitioning, though 3-way would be asymptotically better for high-duplicate inputs).

### Solution

```js
function sortArray(nums) {
  quickSort(nums, 0, nums.length - 1);
  return nums;
}

function quickSort(arr, low, high) {
  if (low >= high) return;

  // random pivot to avoid worst-case on sorted inputs
  const randIdx = low + Math.floor(Math.random() * (high - low + 1));
  [arr[randIdx], arr[high]] = [arr[high], arr[randIdx]];

  const p = partition(arr, low, high);
  quickSort(arr, low, p - 1);
  quickSort(arr, p + 1, high);
}

function partition(arr, low, high) {
  const pivot = arr[high];
  let i = low - 1;

  for (let j = low; j < high; j++) {
    if (arr[j] <= pivot) {
      i++;
      [arr[i], arr[j]] = [arr[j], arr[i]];
    }
  }

  [arr[i + 1], arr[high]] = [arr[high], arr[i + 1]];
  return i + 1;
}
```

### Dry Run

```
nums = [5,1,1,2,0,0], low=0, high=5

Suppose pivot chosen = index 3 (val=2), swap arr[3]↔arr[5]: [5,1,1,0,0,2]

partition([5,1,1,0,0,2], 0, 5), pivot=2, i=-1:
j=0: 5>2 → skip
j=1: 1<=2 → i=0, swap(0,1): [1,5,1,0,0,2]
j=2: 1<=2 → i=1, swap(1,2): [1,1,5,0,0,2]
j=3: 0<=2 → i=2, swap(2,3): [1,1,0,5,0,2]
j=4: 0<=2 → i=3, swap(3,4): [1,1,0,0,5,2]

Swap arr[4]↔arr[5]: [1,1,0,0,2,5]
pivotIdx=4

arr = [1,1,0,0,2,5], 2 is at index 4 — correct final position ✓

Recurse:
  quickSort(arr, 0, 3) → sorts [1,1,0,0] → [0,0,1,1]
  quickSort(arr, 5, 5) → single element, no-op

Final: [0,0,1,1,2,5] ✓
```

### Complexity
- Time: O(n log n) expected, O(n²) worst case.
- Space: O(log n) average stack depth.

### Edge Cases
- Already sorted: random pivot makes this not a worst case.
- All identical: Lomuto's `≤` still works correctly (all elements go into the "≤ pivot" region), but is O(n²) — for inputs known to have many duplicates, 3-way Quick Sort is preferred.
- Single element or empty: base case `low >= high` handles immediately.

### Follow-up Questions
- "How would you switch to 3-way partitioning for duplicate-heavy inputs?" → See Problem 5, which covers 3-way Quick Sort with the Dutch National Flag partition.
- "What's your space complexity?" → O(log n) expected for the recursion stack (from balanced partitions with random pivot). Explicitly adding a tail-call optimization (always recurse into the smaller sub-array first, then handle the larger one iteratively or via tail recursion) guarantees O(log n) stack space in the worst case.

## Problem 4 — Top K Frequent Elements

### Problem
Given an integer array `nums` and an integer `k`, return the `k` most frequent elements. The answer may be returned in any order.

```
Input:  nums = [1,1,1,2,2,3], k = 2
Output: [1, 2]

Input:  nums = [1], k = 1
Output: [1]
```

### Pattern Recognition
Frequency counting + Quickselect on the frequency array — an application of Quickselect to a derived problem (select by frequency rather than by value).

### Key Insight
Build a frequency map from `nums`, then run Quickselect on the array of unique elements sorted by their frequencies (in descending order), finding the k-th most frequent element. Everything at index ≤ k-1 in the frequency-sorted order is part of the answer.

### Approach
1. Count frequencies using a hash map.
2. Create an array of unique values.
3. Run Quickselect on this array with a custom comparator: compare by frequency (descending). After Quickselect, the first `k` elements (indices 0 to k-1) are the top k most frequent.

### Solution

```js
function topKFrequent(nums, k) {
  // step 1: build frequency map
  const freq = new Map();
  for (const num of nums) {
    freq.set(num, (freq.get(num) || 0) + 1);
  }

  // step 2: array of unique values
  const unique = Array.from(freq.keys());

  // step 3: quickselect to put the k most frequent at indices 0..k-1
  quickSelectByFreq(unique, 0, unique.length - 1, k - 1, freq);

  return unique.slice(0, k);
}

function quickSelectByFreq(arr, low, high, targetIdx, freq) {
  if (low >= high) return;

  // random pivot
  const randIdx = low + Math.floor(Math.random() * (high - low + 1));
  [arr[randIdx], arr[high]] = [arr[high], arr[randIdx]];

  const pivotIdx = partitionByFreq(arr, low, high, freq);

  if (pivotIdx === targetIdx) {
    return; // top-k elements are now at indices 0..k-1
  } else if (pivotIdx > targetIdx) {
    quickSelectByFreq(arr, low, pivotIdx - 1, targetIdx, freq);
  } else {
    quickSelectByFreq(arr, pivotIdx + 1, high, targetIdx, freq);
  }
}

function partitionByFreq(arr, low, high, freq) {
  const pivotFreq = freq.get(arr[high]);
  let i = low - 1;

  for (let j = low; j < high; j++) {
    if (freq.get(arr[j]) >= pivotFreq) { // descending: higher freq goes to the left
      i++;
      [arr[i], arr[j]] = [arr[j], arr[i]];
    }
  }

  [arr[i + 1], arr[high]] = [arr[high], arr[i + 1]];
  return i + 1;
}
```

### Dry Run

```
nums = [1,1,1,2,2,3], k=2

freq: {1→3, 2→2, 3→1}
unique = [1, 2, 3]
targetIdx = k-1 = 1

quickSelectByFreq([1,2,3], 0, 2, 1, freq):
  pivot: choose index 1 (val=2, freq=2), swap arr[1]↔arr[2]: [1,3,2]
  partitionByFreq([1,3,2], 0, 2):
    pivotFreq = freq(2) = 2, i=-1
    j=0: freq(1)=3 >= 2 → i=0, swap(0,0): [1,3,2]
    j=1: freq(3)=1 >= 2? NO → skip
    swap arr[i+1=1]↔arr[2]: [1,2,3]
    return pivotIdx=1

  pivotIdx(1) === targetIdx(1) → done!

unique = [1, 2, 3], slice(0,2) = [1, 2]

Result: [1, 2] ✓ (the two most frequent elements)
```

### Complexity
- Time: O(n) average for counting + O(m) average Quickselect where m = number of unique elements (m ≤ n) = O(n) average overall. O(n²) worst case for the select step.
- Space: O(n) for the frequency map and unique array.

### Edge Cases
- All elements identical: one unique element, `k = 1` → trivially returned.
- All elements distinct: `freq` maps every element to 1; Quickselect by frequency on all-equal frequencies still correctly finds some k elements (which k depends on partition outcomes, but the problem states elements are as frequent as the given values).
- `k` equals the number of unique elements: return all unique elements; Quickselect with `targetIdx = unique.length - 1` effectively processes the whole array.

### Follow-up Questions
- "What if you need the top k elements in SORTED order (by frequency)?" → After Quickselect places the k most frequent at indices 0..k-1, sort just those k elements by frequency — O(k log k) additional cost, still O(n) overall for small k.
- "Use a heap-based approach instead?" → Maintain a min-heap of size k (keyed by frequency). Process all unique elements, keeping the k largest by frequency. O(m log k) time. For small k, this can be faster and simpler in code.

## Problem 5 — Quick Sort with 3-Way Partition (Duplicate-Heavy Inputs)

### Problem
Implement Quick Sort using 3-way (Dutch National Flag) partitioning, which efficiently handles arrays with many duplicate values — achieving O(n) performance on arrays of all identical elements instead of O(n²).

```
Input:  [2, 0, 2, 1, 1, 0]
Output: [0, 0, 1, 1, 2, 2]

Input:  [4, 4, 4, 4, 4]
Output: [4, 4, 4, 4, 4]  (in O(n) time, unlike standard Quick Sort's O(n²) here)
```

### Pattern Recognition
3-way Quick Sort — partition into three regions (`< pivot`, `== pivot`, `> pivot`), recurse only into the `< pivot` and `> pivot` regions (the `== pivot` region is already fully sorted).

### Key Insight
Standard 2-way Lomuto partition includes equal elements in the left region, causing them to be re-sorted in sub-calls even though they're already in their correct relative positions. 3-way partitioning explicitly isolates all equal elements into their own region — excluded from both recursive calls — enabling O(n) performance on inputs with many repeated values.

### Approach
Use three pointers: `lt` (boundary of `< pivot` region), `gt` (boundary of `> pivot` region), `i` (current scan). Elements are classified and swapped to the correct region as `i` sweeps from `lt` to `gt`. Recurse into `arr[low..lt-1]` and `arr[gt+1..high]`, skipping `arr[lt..gt]` (all equals).

### Solution

```js
function sortArrayThreeWay(arr) {
  quickSort3Way(arr, 0, arr.length - 1);
  return arr;
}

function quickSort3Way(arr, low, high) {
  if (low >= high) return;

  // random pivot
  const randIdx = low + Math.floor(Math.random() * (high - low + 1));
  [arr[randIdx], arr[low]] = [arr[low], arr[randIdx]]; // pivot goes to low for DNF
  const pivot = arr[low];

  let lt = low, gt = high, i = low + 1;

  while (i <= gt) {
    if (arr[i] < pivot) {
      [arr[lt], arr[i]] = [arr[i], arr[lt]];
      lt++; i++;
    } else if (arr[i] > pivot) {
      [arr[i], arr[gt]] = [arr[gt], arr[i]];
      gt--;
      // i does NOT advance: the swapped-in value from gt is not yet examined
    } else {
      i++;
    }
  }
  // arr[low..lt-1] < pivot, arr[lt..gt] == pivot, arr[gt+1..high] > pivot

  quickSort3Way(arr, low, lt - 1);  // sort the "< pivot" region
  quickSort3Way(arr, gt + 1, high); // sort the "> pivot" region
  // arr[lt..gt] == pivot is already in its final sorted position, skip it
}
```

### Dry Run

```

i=1: arr[1]=0<2 → swap(lt=0,i=1): [0,2,2,1,1,0], lt=1, i=2

i=4: arr[4]=1<2 → swap(lt=2,i=4): [0,1,1,2,2,0], lt=3, i=5
i=5: arr[5]=0<2 → swap(lt=3,i=5): [0,1,1,0,2,2], lt=4, i=6
```

### Complexity
- Time: O(n log n) average for general inputs; **O(n)** for arrays of all identical elements (one partition step covers everything, both recursive calls have empty sub-arrays).
- Space: O(log n) average stack depth.

### Edge Cases
- All identical elements: single partition identifies all as `== pivot`, both recursive calls have `low > high`, total work is O(n).
- Only two distinct values (like the 0/1 case): at most O(log 2) = O(1) levels of recursion needed after the first partition separates 0s from 1s.
- Fully general distinct values: degenerates to standard Quick Sort behavior (no elements equal to pivot in the `== pivot` region), still O(n log n) average.

### Follow-up Questions
- "Isn't the Dutch National Flag problem exactly this partition step?" → Yes — see the dedicated DNF guide in this series; 3-way Quick Sort's partition is exactly the DNF algorithm applied with the pivot as the "middle value" and the three regions as the three "colors."
- "Why does `i` NOT advance after a swap with `gt`?" → Because the element swapped in from position `gt` hasn't been examined yet — it could be less than, equal to, or greater than the pivot, and must be re-classified on the next iteration.

## Quick Reference — Pattern Decision Tree

```
Does the problem involve sorting or finding order statistics (k-th element, top k)?
│
├── NEED TO FULLY SORT AN ARRAY?
│   ├── General purpose, in-place preferred → Quick Sort (O(n log n) avg, O(n²) worst)
│   │   → Use random pivot or median-of-three to avoid worst case
│   ├── Guaranteed O(n log n) worst case required → Merge Sort or Introsort
│   ├── Stability required → Merge Sort or Timsort (NOT Quick Sort)
│   └── Many duplicate values → 3-Way Quick Sort (avoids O(n²) on all-identical arrays)
│
├── NEED THE K-TH SMALLEST / LARGEST ELEMENT ONLY (not full sort)?
│   ├── k is small (k << n) → Min/Max Heap: O(n + k log n), simple to implement
│   ├── General k → Quickselect: O(n) average, O(n²) worst case, modifies input array
│   └── Guaranteed O(n) worst case needed → Median of Medians (complex, rarely needed)
│
├── NEED THE TOP K ELEMENTS (not just the k-th)?
│   ├── Any order acceptable → Quickselect: partial sort, all top-k at indices 0..k-1
│   ├── Sorted order needed → Quickselect + sort those k elements: O(n + k log k)
│   └── Frequency-based top k → Frequency map + Quickselect on unique elements
│
├── NEED K-TH ON A STREAM (elements arriving one at a time)?
│   └── Min-Heap of size k: maintain the k largest seen; top of heap = k-th largest
│       → O(log k) per element, works for infinite streams
│
└── ARRAY IS KNOWN TO HAVE FEW DISTINCT VALUES (e.g., 0/1/2 sort)?
    └── 3-Way Quick Sort or Counting Sort → O(n) time, handles duplicates naturally
```

## Common Bugs Checklist

Before submitting any Quick Sort or Quickselect solution, verify:

1. **Lomuto recursive calls exclude the pivot index: `quickSort(arr, low, pivotIdx-1)` and `quickSort(arr, pivotIdx+1, high)`?** — Including the pivot in either recursive call causes it to be re-partitioned unnecessarily (harmless for correctness since it's already in its final position, but wasteful) or, if the partition always places it at the same spot, leads to infinite recursion.

2. **Hoare partition recursive calls include the split index: `quickSort(arr, low, splitIdx)` and `quickSort(arr, splitIdx+1, high)`?** — Using Lomuto's `pivotIdx-1` / `pivotIdx+1` structure with Hoare's return value causes an off-by-one that can lead to infinite recursion (the left call `arr[low..splitIdx-1]` might exclude the element Hoare placed at `splitIdx`, leaving it unprocessed forever).

3. **Base case correctly handles sub-arrays of size 0 AND 1: `if (low >= high) return`?** — Using `low > high` only misses the single-element case, but since the single element is trivially sorted, both `>` and `>=` are correct here — using `===` is subtly wrong if `low` somehow exceeds `high` (e.g., if the recursive call passes `pivotIdx+1` when `pivotIdx === high`).

4. **Quickselect target index correctly translated from k-th LARGEST to 0-indexed SMALLEST: `targetIdx = n - k`?** — Off-by-one here (e.g., `n - k + 1` or `k - 1`) returns the wrong element without any obvious error message.

5. **3-way partition: `i` does NOT advance after swapping with `gt`?** — Advancing `i` after swapping with `gt` causes the newly-swapped-in element (which hasn't been examined yet) to be skipped, potentially placing it in the wrong region and producing an incorrect sort.

6. **Random pivot swap goes into the correct position BEFORE partition is called?** — For Lomuto, the pivot must be at index `high` before `partition` runs (since it reads `arr[high]` as the pivot). Swapping the random element to `high` (not `low` or some other position) is required.

7. **Partition's `<= pivot` condition (not strict `<`) handles elements equal to the pivot correctly?** — Using strict `<` excludes equal elements from the "left" region, potentially clustering them all in the "right" region and causing O(n²) behavior on arrays with many duplicates (though 3-way partitioning is a better fix for this case).

---

**Final Tip:** At the 5 YOE level, interviewers expect fluent recall of the Lomuto partition invariant (the `i` pointer tracks the right edge of the "≤ pivot" region; after the loop, pivot swaps to `i+1`) and the Quickselect branching logic (recurse into only ONE sub-array based on whether `pivotIdx` is above or below `targetIdx`). The distinction between `dp[i][j-1]` and `dp[i][j-2]` in DP problems is the analogue of the distinction between Lomuto's `pivotIdx±1` and Hoare's `splitIdx` / `splitIdx+1` recursive boundaries in Quick Sort — getting the exact boundary condition right is the difference between a correct implementation and one that silently produces wrong output or infinite recursion on edge cases. State the pivot-placement invariant out loud before coding: "after partition, the pivot is at its exact final sorted position, and I recurse into everything strictly to its left and everything strictly to its right."
