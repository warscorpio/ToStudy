# DSA: Counting Sort, Radix Sort & Bucket Sort (Non-Comparison Sorts) — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. Why do comparison-based sorts have an Ω(n log n) lower bound, and how do non-comparison sorts escape it?**
A: Any comparison-based sorting algorithm works by asking "is element A less than element B?" and branching on the answer. The decision tree for sorting n elements has at least n! leaves (one for each possible permutation). A binary tree of height h has at most 2^h leaves, so height ≥ log₂(n!) ≈ n log n (by Stirling's approximation). This means any comparison-based sort must make Ω(n log n) comparisons in the worst case — a provable lower bound, not just the best we've achieved.

Non-comparison sorts escape this bound by exploiting the **structure of the keys** — specifically, that keys are integers (or can be mapped to integers) within a bounded range. Instead of comparing elements to each other, they count occurrences, distribute into buckets, or process digit by digit. The information about ordering is extracted directly from the key values, bypassing the comparison decision tree entirely.

**Q2. What are the three main non-comparison sorts and what is each suited for?**
A:
- **Counting Sort**: keys are non-negative integers in a known range `[0, k]`. Count occurrences, accumulate counts, place elements. O(n + k) time. Best when k is small relative to n (e.g., sorting exam scores 0–100, sorting ages 0–120).
- **Radix Sort**: keys are integers (or strings) with a fixed maximum number of digits/characters. Sort digit by digit (LSD — least significant digit first, or MSD — most significant digit first) using a stable sub-sort (usually counting sort) at each digit position. O(d × (n + k)) where d = digits, k = base. Best for large n with many-digit integers or fixed-length strings.
- **Bucket Sort**: keys are floating-point numbers (or integers) uniformly distributed in a range `[0, 1)` (or any mapped range). Distribute into n buckets, sort each bucket individually (insertion sort or comparison sort), concatenate. O(n) expected when input is uniform. Best for real-valued, uniformly distributed data.

**Q3. What is the key prerequisite each sort requires that comparison sorts do not?**
A:
- **Counting Sort**: requires knowing the range `[0, k]` of values upfront. Keys must be non-negative integers (or mappable to them). The range `k` must be "reasonable" — if k = 10^9 and n = 1000, the counting array would waste 10^9 space for 1000 elements.
- **Radix Sort**: requires keys to have a bounded number of digits `d` in a fixed base `b`. Works naturally for fixed-width integers (32-bit, 64-bit) and fixed-length strings. Variable-length keys require padding or a different approach.
- **Bucket Sort**: requires knowledge of the key distribution — specifically, that keys are roughly uniformly distributed in a range. Without uniformity, all elements might land in one bucket, degrading to O(n²) for that bucket's sort.

**Q4. What does "stable sort" mean, and which of these three sorts are stable?**
A: A sort is **stable** if elements with equal keys appear in the output in the same relative order as in the input. Stability matters when sorting by a secondary key after a primary sort (e.g., sort by name, then by age — a stable age sort preserves the name ordering among people of the same age).

- **Counting Sort**: stable if implemented correctly — iterate the input right-to-left when placing elements, using the accumulated count array to determine positions. This preserves the relative order of equal elements.
- **Radix Sort**: stable if and only if the sub-sort at each digit position is stable. The standard implementation uses stable counting sort at each level — so radix sort is stable overall. Stability is essential for correctness of LSD radix sort (later digit sorts must not disturb the ordering established by earlier digit sorts).
- **Bucket Sort**: depends on the sort used within each bucket. If you use a stable sort (insertion sort is stable), bucket sort is stable. Unstable within buckets → unstable overall.

### Section 2: Counting Sort — Deep Dive

**Q5. Walk through the counting sort algorithm step by step.**
A: Four phases:

**Phase 1 — Count**: create a count array of size `k+1` (where k = max value). Increment `count[arr[i]]` for each element.

**Phase 2 — Accumulate (prefix sum)**: transform `count` so `count[v]` = number of elements ≤ v. This gives the "ending position" of each value group in the output.

**Phase 3 — Place (right-to-left for stability)**: iterate the input array from right to left. For each element `arr[i]`, place it at position `count[arr[i]] - 1` in the output, then decrement `count[arr[i]]`.

**Phase 4 — Copy back**: write the output array back to the original.

```js
function countingSort(arr, k) {
  // k = maximum value in arr
  const n = arr.length;
  const count = new Array(k + 1).fill(0);
  const output = new Array(n);

  // Phase 1: count occurrences
  for (const val of arr) count[val]++;

  // Phase 2: accumulate — count[v] = number of elements <= v
  for (let v = 1; v <= k; v++) count[v] += count[v - 1];

  // Phase 3: place elements (right-to-left for stability)
  for (let i = n - 1; i >= 0; i--) {
    const val = arr[i];
    output[count[val] - 1] = val; // place at final position
    count[val]--;                  // next equal element goes one position left
  }

  // Phase 4: copy back
  for (let i = 0; i < n; i++) arr[i] = output[i];

  return arr;
}
```

**Q6. Why do we iterate right-to-left in Phase 3 for stability?**
A: Consider two equal elements at positions `i < j` in the input (i appears before j). For stability, element at `i` should appear before element at `j` in the output. By iterating right-to-left (j first, then i), we place j at position `count[v]-1`, decrement to `count[v]-2`, and then place i there. Element i (earlier in input) ends up at the lower index — before j — in the output. Right-to-left iteration combined with decrement achieves this. Left-to-right iteration would produce the correct sorted order but reverse the relative order of equal elements — making the sort unstable.

**Q7. What are the time and space complexities of counting sort?**
A:
- **Time: O(n + k)** — Phase 1: O(n) to count. Phase 2: O(k) to accumulate. Phase 3: O(n) to place. Phase 4: O(n) to copy. Total: O(n + k).
- **Space: O(n + k)** — O(k+1) for the count array, O(n) for the output array.

When k = O(n), counting sort is O(n) time and O(n) space — optimal for sorting integers in a bounded range. When k ≫ n (e.g., k = 10^9, n = 100), the O(k) cost dominates and counting sort is impractical.

**Q8. Can counting sort handle negative integers?**
A: Not directly, but with a simple offset. Find the minimum value `min_val` in the array. Shift all values by `-min_val` to map the range `[min_val, max_val]` to `[0, max_val - min_val]`. Run counting sort on the shifted values. The shifted range `k = max_val - min_val` determines the count array size. After sorting, optionally shift back (not needed if you just need sorted order).

```js
function countingSortGeneral(arr) {
  const minVal = Math.min(...arr);
  const maxVal = Math.max(...arr);
  const shifted = arr.map(x => x - minVal); // shift to [0, k]
  countingSort(shifted, maxVal - minVal);
  return shifted.map(x => x + minVal); // shift back
}
```

### Section 3: Radix Sort — Deep Dive

**Q9. What is LSD radix sort and how does it work?**
A: LSD (Least Significant Digit) radix sort processes digits from the rightmost (least significant) to the leftmost (most significant). At each digit position, it applies a stable sort (typically counting sort) on just that digit. After processing all digits, the array is fully sorted.

Why LSD works: stability is the key. When sorting by digit position `d`, a stable sort preserves the ordering established by all less-significant digits (already processed). After d passes, elements are sorted by the last d digits. The final pass (most significant digit) gives the globally correct order, with ties broken by previous passes.

```js
function radixSortLSD(arr, base = 10) {
  if (arr.length === 0) return arr;

  const maxVal = Math.max(...arr);
  let exp = 1; // current digit place value (1, 10, 100, ...)

  while (Math.floor(maxVal / exp) > 0) {
    countingSortByDigit(arr, exp, base);
    exp *= base;
  }

  return arr;
}

function countingSortByDigit(arr, exp, base) {
  const n = arr.length;
  const output = new Array(n);
  const count = new Array(base).fill(0);

  // count occurrences of each digit at this position
  for (const val of arr) {
    const digit = Math.floor(val / exp) % base;
    count[digit]++;
  }

  // accumulate
  for (let i = 1; i < base; i++) count[i] += count[i - 1];

  // place right-to-left (stable)
  for (let i = n - 1; i >= 0; i--) {
    const digit = Math.floor(arr[i] / exp) % base;
    output[count[digit] - 1] = arr[i];
    count[digit]--;
  }

  // copy back
  for (let i = 0; i < n; i++) arr[i] = output[i];
}
```

**Q10. What is MSD radix sort, and when would you prefer it over LSD?**
A: MSD (Most Significant Digit) radix sort processes digits from the leftmost (most significant) to the rightmost. Unlike LSD, MSD is naturally recursive — after sorting by the most significant digit, each bucket is independently sorted by the next digit (recursively). MSD can terminate early for short strings or when sub-buckets have ≤ 1 element.

Prefer MSD when:
- Keys have variable lengths (e.g., strings of different lengths) — MSD handles this naturally by processing each string only up to its length.
- The sorted data needs to be produced in lexicographic order — MSD produces it directly.
- Early termination is beneficial — elements with the same prefix are sorted together without processing irrelevant suffix digits.

Prefer LSD when:
- Keys have fixed lengths (integers, fixed-length strings) — simpler iterative implementation.
- Stability with a simple counting sort sub-routine is important.
- Parallelization is desired — each LSD pass is independent and can be pipelined.

**Q11. What is the time and space complexity of radix sort?**
A:
- **Time: O(d × (n + b))** — d passes (one per digit), each pass is O(n + b) counting sort where b is the base (number of distinct digit values).
- **Space: O(n + b)** — the counting sort at each pass needs O(b) count array and O(n) output array.

For 32-bit integers with base 256 (byte-level radix sort): d = 4 passes (4 bytes), b = 256. Time: O(4 × (n + 256)) = O(n). For n large, this is effectively O(n) — linear!

Choosing the base b: larger b means fewer digits (passes) but larger count arrays. Smaller b means more passes but smaller count arrays. The optimal b ≈ n gives O(n) time with O(n) space.

**Q12. How does radix sort handle signed integers or floats?**
A: Signed integers and floats require special handling:

**Signed integers (two's complement)**: the sign bit causes issues — negative numbers have their high bit set to 1, which would sort them after positive numbers in unsigned LSD sort. Fix: after the LSD sort, the last pass (most significant byte/digit) can be split — sort 0x80 through 0xFF (negatives in two's complement) first, then 0x00 through 0x7F (positives). Or: XOR all values with `0x80000000` (for 32-bit) to flip the sign bit, sort as unsigned, then XOR back.

**Floats (IEEE 754)**: IEEE 754 positive floats sort in the same order as their integer bit representations (the exponent-mantissa arrangement is designed for this). Negative floats have inverted bit patterns — sort negatives separately in reverse order. The simplest fix: for each float, check if the sign bit is 0 (positive → XOR with `0x80000000` to ensure correct order among all values) or 1 (negative → XOR with `0xFFFFFFFF`). Then sort as unsigned integers.

### Section 4: Bucket Sort — Deep Dive

**Q13. Walk through the bucket sort algorithm step by step.**
A: Three phases:

**Phase 1 — Distribute**: create n buckets covering the range `[min, max)`. For each element, compute which bucket it belongs to and append it to that bucket.

**Phase 2 — Sort each bucket**: sort each bucket individually. For uniform distributions, each bucket has O(1) elements on average, so insertion sort (O(1) per bucket) is efficient.

**Phase 3 — Concatenate**: collect elements from all buckets in order.

```js
function bucketSort(arr, bucketCount = arr.length) {
  if (arr.length <= 1) return arr;

  const minVal = Math.min(...arr);
  const maxVal = Math.max(...arr);
  const range = maxVal - minVal;

  if (range === 0) return arr; // all elements equal

  // Phase 1: create buckets and distribute elements
  const buckets = Array.from({length: bucketCount}, () => []);

  for (const val of arr) {
    // map val to bucket index [0, bucketCount-1]
    const idx = Math.min(
      Math.floor(((val - minVal) / range) * bucketCount),
      bucketCount - 1 // clamp maxVal to last bucket
    );
    buckets[idx].push(val);
  }

  // Phase 2: sort each bucket (insertion sort for small buckets)
  const result = [];
  for (const bucket of buckets) {
    insertionSort(bucket); // or any stable sort
    for (const val of bucket) result.push(val);
  }

  // Phase 3: copy back (concatenation already done above)
  for (let i = 0; i < arr.length; i++) arr[i] = result[i];

  return arr;
}

function insertionSort(arr) {
  for (let i = 1; i < arr.length; i++) {
    const key = arr[i];
    let j = i - 1;
    while (j >= 0 && arr[j] > key) {
      arr[j + 1] = arr[j];
      j--;
    }
    arr[j + 1] = key;
  }
}
```

**Q14. What is the time complexity of bucket sort, and when does the O(n) average case hold?**
A:
- **Average case: O(n)** — when elements are uniformly distributed, each of the n buckets receives O(1) elements on average. Sorting O(1) elements is O(1). Total: O(n) distribution + O(n) × O(1) bucket sorts + O(n) concatenation = O(n).
- **Worst case: O(n²)** — when all elements fall into one bucket, that bucket must be sorted with whatever algorithm you chose. If insertion sort: O(n²). If a comparison sort: O(n log n).
- **Space: O(n + k)** — k buckets + n elements distributed across them.

The O(n) average holds when:
1. Elements are uniformly distributed in the range.
2. The number of buckets equals n (or is proportional to n).
3. The within-bucket sort is O(expected_bucket_size²) ≤ O(1) for uniform distribution.

For non-uniform distributions, adaptive bucket sizing (more buckets in dense regions) can restore efficiency — this is the basis of more sophisticated distribution sorts.

**Q15. How do you choose the number of buckets and their boundaries?**
A: Two strategies:

**Fixed n buckets with uniform range split**: divide `[min, max]` into n equal-width intervals. Simple, works well for uniformly distributed data. Bucket index formula: `floor((val - min) / (max - min) * n)`, clamped to `[0, n-1]`.

**Adaptive bucket boundaries**: if you know the distribution is non-uniform (e.g., exponential, Gaussian), place bucket boundaries to equalize expected occupancy. Requires either sampling the data first or knowing the distribution analytically. Rare in interviews but relevant in production data pipelines.

General guidance for interviews: use n buckets for n elements and uniform range split. State the uniformity assumption explicitly and mention that worst case degrades to O(n²) if the distribution is skewed.

### Section 5: Comparison & Decision Framework

**Q16. When should you use counting sort vs radix sort vs bucket sort vs comparison sort?**
A:

| Use Case | Recommended Sort | Reason |
|---|---|---|
| Small integer range (k ≈ n), e.g. scores 0–100 | Counting Sort | O(n+k) with k small |
| Large integers, many-digit numbers | Radix Sort | O(d·n) where d is small |
| Real-valued, uniformly distributed floats | Bucket Sort | O(n) average |
| Unknown distribution or arbitrary objects | Merge/Quick Sort | O(n log n) guaranteed |
| Need in-place sort with no extra memory | Heap/Quick Sort | O(1) or O(log n) space |
| Need stable sort for general objects | Merge Sort | O(n log n), stable |
| Characters/bytes (k=256) | Radix Sort (byte-level) | O(n) for fixed-width data |

**Q17. Are non-comparison sorts always faster than comparison sorts in practice?**
A: Not always. Several factors favor comparison sorts in practice:

- **Constant factors**: radix sort with base 256 and 4 passes does 4 sweeps over the data. Quicksort does ~n log₂ n ≈ 32n comparisons for n=10^9. Each radix pass touches every element's bytes — cache misses are frequent. Modern CPUs can do comparison sorts with excellent cache utilization, making O(n log n) comparison sorts faster than theoretical O(n) radix sorts for moderate n.

- **Generality**: comparison sorts work on any type with a total order. Non-comparison sorts require integer or float keys — can't sort arbitrary objects.

- **In-place**: counting and radix sort need O(n) extra space. Quicksort is in-place (O(log n) stack space). For memory-constrained environments, this matters.

- **Implementation complexity**: comparison sorts (especially introsort, used in C++ `std::sort`) are highly optimized. A naive radix sort may be slower than an optimized comparison sort even for large n.

Rule of thumb: for n ≥ 10^6 with integer/float keys and O(n) extra memory available, radix sort or counting sort is likely faster. For smaller n or when memory is constrained, use a well-optimized comparison sort.

**Q18. How do these sorts compare on stability, in-place property, and adaptivity?**
A:

| Sort | Stable | In-Place | Adaptive | Time | Space |
|---|---|---|---|---|---|
| Counting Sort | Yes (with right-to-left) | No | No | O(n+k) | O(n+k) |
| Radix Sort (LSD) | Yes | No | No | O(d(n+b)) | O(n+b) |
| Radix Sort (MSD) | Yes | No | Yes (early termination) | O(d(n+b)) | O(n+b+d) |
| Bucket Sort | Depends on inner sort | No | No | O(n) avg | O(n+k) |
| Merge Sort | Yes | No | No | O(n log n) | O(n) |
| Quicksort | No | Yes | No | O(n log n) avg | O(log n) |
| Heapsort | No | Yes | No | O(n log n) | O(1) |
| Timsort | Yes | No | Yes | O(n log n) | O(n) |

### Section 6: Scenario / Interview-Style Questions

**Q19. "Sort 1 million integers in the range [0, 1000]. What algorithm do you use and why?"**
A: Counting sort. k = 1000 ≈ n^(1/3) — far smaller than n = 10^6. Counting sort runs in O(n + k) = O(10^6 + 1000) ≈ O(10^6) = O(n). Space: O(n + k) ≈ O(n). Comparison sort would be O(n log n) ≈ O(10^6 × 20) = O(2 × 10^7) — already 20× more operations, plus larger constant factors. Counting sort is the clear choice when k ≪ n.

**Q20. "Sort 1 billion 32-bit integers stored on disk (external sort). Which approach applies?"**
A: This is an external sort problem — the data doesn't fit in RAM. Standard approach: merge sort-based external sort (read chunks into RAM, sort each chunk in RAM, write sorted chunks to disk, merge sorted runs). Non-comparison sorts are less natural here because:
- Counting sort requires a count array of size 2^32 ≈ 4 billion entries — doesn't fit in RAM.
- Radix sort can be adapted for external sort: multiple passes over the data, one per digit — but each pass requires reading and writing the entire dataset from/to disk. For d=4 passes with byte-level radix: 4 disk reads + 4 disk writes (8 passes total). External merge sort requires ~log(N/M) disk passes where M = RAM size — typically 2–4 passes for practical sizes. They're comparable, but external merge sort is more standard.

For RAM-bound sorting of 32-bit integers: radix sort (byte-level, 4 passes over n elements) is typically the fastest approach, running in O(n) with O(n) extra memory.

**Q21. "Your sorting algorithm is producing wrong results for negative numbers. You're using counting sort. What's the issue?"**
A: Counting sort as naively implemented handles only non-negative integers — it uses element values as array indices, and negative indices don't exist. Two symptoms: (1) accessing `count[negative_value]` throws an array index out of bounds error, or (2) in JavaScript (where array access with negative index returns `undefined`), count accumulates incorrectly.

Fix: compute the minimum value in the array (`minVal = Math.min(...arr)`). Shift all values by `-minVal` to map the range `[minVal, maxVal]` to `[0, maxVal - minVal]`. Build the count array with the shifted values. After placing elements in the output, shift back. The count array size becomes `maxVal - minVal + 1` instead of `maxVal + 1`.

**Q22. "Explain why LSD radix sort must use a stable sub-sort, with a concrete counterexample showing what goes wrong with an unstable sub-sort."**
A: After sorting by the units digit, the ordering within each digit group reflects the ordering from previous (non-existent, for the first pass) or subsequent passes. When the tens-digit pass runs, it must not disturb the units-digit ordering within each tens-digit group.

Counterexample:
```
Input: [32, 12, 21, 31]
Units digit sort → 21, 31, 32, 12   (groups: {1: 21,31}, {2: 32,12})
Tens digit sort (STABLE) → 12, 21, 31, 32 ✓ ({1: 12}, {2: 21,31}, {3: 32})
  Within group '2' (tens=2): 21 comes before 31 — correct (from units pass)

Tens digit sort (UNSTABLE) — might give:
  {1: 12}, {2: 31, 21}, {3: 32}  → 12, 31, 21, 32 ✗
  (31 and 21 swapped within the '2' group — units digit ordering lost)
```

The correctness of LSD radix sort relies entirely on stability of the per-digit sort. Without stability, earlier digit information is destroyed by later passes.

**Q23. "Can you sort strings with radix sort? How?"**
A: Yes — strings are sequences of characters, and characters are integers (ASCII/Unicode code points). Two approaches:

**LSD for fixed-length strings**: if all strings have the same length L, apply LSD radix sort with L passes — one per character position, right to left. Each pass is a stable counting sort on the character at position `L-1-pass`. O(L × (n + 256)) = O(L × n) for ASCII strings.

**MSD for variable-length strings**: apply MSD radix sort recursively. Sort by first character, then recursively sort each group by second character, and so on. Shorter strings terminate early (treated as having a "null" character before the next character, which sorts before 'a'). This is the basis of most efficient string sorting algorithms (e.g., 3-way radix quicksort).

## Problem 1 — Sort Array by Frequency / Counting Sort Foundation

### Problem
Given an array of non-negative integers where each element is in the range `[0, k]`, sort the array in O(n + k) time without using any comparison-based sort.

```
Input:  arr=[4,2,2,8,3,3,1], k=8
Output: [1,2,2,3,3,4,8]

Input:  arr=[0,1,0,1,2,1,0], k=2
Output: [0,0,0,1,1,1,2]
```

### Pattern Recognition
Direct application of counting sort — elements are non-negative integers in a bounded range, and the problem explicitly requires O(n + k).

### Key Insight
Count how many times each value appears. Then reconstruct the array by placing each value `v` exactly `count[v]` times in sequence. For sorting (not just counting), the stable version (Phase 3 right-to-left traversal) is needed when elements carry satellite data. For pure integer sorting with no satellite data, the simplified "reconstruct from counts" version suffices.

### Approach
Two variants:

**Simple (no satellite data)**: count occurrences, then iterate through count array and emit each value count[v] times. O(n + k) time, O(k) space.

**Stable (with satellite data)**: full counting sort with accumulation and right-to-left placement. O(n + k) time, O(n + k) space.

### Solution — Simple Variant

```js
function countingSortSimple(arr, k) {
  // Step 1: count occurrences of each value
  const count = new Array(k + 1).fill(0);
  for (const val of arr) {
    count[val]++; // count[v] = number of times v appears
  }

  // Step 2: reconstruct sorted array from counts
  let idx = 0;
  for (let v = 0; v <= k; v++) {
    while (count[v] > 0) {
      arr[idx++] = v; // place v exactly count[v] times
      count[v]--;
    }
  }

  return arr;
}
```

### Solution — Stable Variant (Full Counting Sort)

```js
function countingSortStable(arr, k) {
  const n = arr.length;
  const count = new Array(k + 1).fill(0);
  const output = new Array(n);

  // Phase 1: count
  for (const val of arr) count[val]++;

  // Phase 2: accumulate prefix sums
  // After this, count[v] = number of elements with value <= v
  // = the 1-based ending position of value v in the sorted output
  for (let v = 1; v <= k; v++) {
    count[v] += count[v - 1];
  }

  // Phase 3: place elements right-to-left (stability)
  // Placing right-to-left means equal elements maintain their
  // original left-to-right order in the output
  for (let i = n - 1; i >= 0; i--) {
    const val = arr[i];
    output[count[val] - 1] = arr[i]; // place at position count[val]-1
    count[val]--;                     // next equal element goes one left
  }

  // Phase 4: copy output back to arr
  for (let i = 0; i < n; i++) arr[i] = output[i];

  return arr;
}
```

### Dry Run — Stable Variant

```

Phase 1 — Count:

count value: 0  1  2  2  1  0  0  0  1
(value 1 appears once, 2 appears twice, 3 appears twice, 4 once, 8 once)

Phase 2 — Accumulate prefix sums:
count[0]=0
count[1]=0+1=1
count[2]=1+2=3
count[3]=3+2=5
count[4]=5+1=6
count[5]=6+0=6
count[6]=6+0=6
count[7]=6+0=6
count[8]=6+1=7

count: [0, 1, 3, 5, 6, 6, 6, 6, 7]
Meaning: count[v] = last valid 1-based position for value v
e.g. count[3]=5 means the two 3s occupy positions 4 and 5 (1-based) = indices 3,4 (0-based)

Phase 3 — Place right-to-left:
output = [_, _, _, _, _, _, _]  (7 slots)

i=6: arr[6]=1, count[1]=1 → output[0]=1, count[1]=0
i=5: arr[5]=3, count[3]=5 → output[4]=3, count[3]=4

```

### Complexity
- Time: O(n + k) — Phase 1: O(n), Phase 2: O(k), Phase 3: O(n), Phase 4: O(n).
- Space: O(n + k) — count array O(k+1), output array O(n).

### Edge Cases
- All same value: count[v] = n, all placed in sequence. Correct.
- k = 0: all values are 0, count[0] = n, output is all zeros. Correct.
- Single element: n=1, trivially sorted.
- Sparse values (e.g., arr=[0, 1000000], k=1000000): count array is large (1M+1 entries) but only 2 are non-zero. Works but wastes space — consider a hash map for sparse distributions.

### Follow-up Questions
- "Sort objects by an integer key field?" → Use the stable variant; instead of `output[pos] = arr[i]` (value), store the whole object: `output[pos] = objects[i]`.
- "What if k is not given?" → Scan once to find `max(arr)`. O(n) extra pass — still O(n + k) total.
- "What if values can be negative?" → Find `minVal`, shift all values by `-minVal`, run counting sort on shifted array. Count array size = `maxVal - minVal + 1`.

## Problem 2 — Sort Colors (Dutch National Flag / Counting Sort Variant) (LeetCode 75)

### Problem
Given an array `nums` with values 0, 1, or 2, sort it in-place in one pass. (Values represent red=0, white=1, blue=2.)

```
Input:  nums=[2,0,2,1,1,0]   → [0,0,1,1,2,2]
Input:  nums=[2,0,1]          → [0,1,2]
```

### Pattern Recognition
Counting sort with k=2 — only 3 distinct values. Can be solved with a simple count and reconstruct (O(n) time, O(1) space for counts). The optimal one-pass version is the Dutch National Flag algorithm (three-pointer), but counting sort is the natural non-comparison sort answer.

### Key Insight
With only 3 values (0, 1, 2), counting sort's count array has just 3 entries. Count each value, then overwrite the array with the correct number of 0s, then 1s, then 2s. O(n) time, O(1) extra space (the 3-entry count array is O(1)).

### Approach — Counting Sort (Two-Pass)

```js
function sortColors(nums) {
  // Count occurrences of 0, 1, 2
  const count = [0, 0, 0];
  for (const val of nums) count[val]++;

  // Overwrite array: count[0] zeros, count[1] ones, count[2] twos
  let idx = 0;
  for (let v = 0; v <= 2; v++) {
    while (count[v] > 0) {
      nums[idx++] = v;
      count[v]--;
    }
  }
}
```

### Approach — Dutch National Flag (One-Pass, O(1) Space — Optimal)

```js
function sortColorsDNF(nums) {
  let lo = 0;          // boundary: everything left of lo is 0
  let mid = 0;         // current element under examination
  let hi = nums.length - 1; // boundary: everything right of hi is 2

  while (mid <= hi) {
    if (nums[mid] === 0) {
      [nums[lo], nums[mid]] = [nums[mid], nums[lo]]; // swap 0 to front
      lo++;
      mid++;
    } else if (nums[mid] === 1) {
      mid++; // 1 is already in the right region
    } else { // nums[mid] === 2
      [nums[mid], nums[hi]] = [nums[hi], nums[mid]]; // swap 2 to back
      hi--;  // don't advance mid — swapped element is unexamined
    }
  }
}
```

### Dry Run — Counting Sort

```
Reconstruct:
  v=0: write 0 twice → nums=[0,0,_,_,_,_]
  v=1: write 1 twice → nums=[0,0,1,1,_,_]
  v=2: write 2 twice → nums=[0,0,1,1,2,2] ✓
```

### Dry Run — Dutch National Flag

```

mid=0(0): swap nums[0]↔nums[0]: [0,0,2,1,1,2], lo=1, mid=1
mid=1(0): swap nums[1]↔nums[1]: [0,0,2,1,1,2], lo=2, mid=2

```

|---|---|---|---|

| Dutch National Flag | O(n) | O(1) | 1 pass |

### Edge Cases
- All same value: count has one non-zero entry; reconstruct trivially.
- Already sorted: counting sort still runs in O(n); DNF terminates early when lo and hi converge quickly.
- Two values only: handled naturally by both approaches.

### Follow-up Questions
- "Do it in one pass?" → Dutch National Flag (three-pointer approach).
- "Generalize to k colors (not just 3)?" → Counting sort scales naturally to k colors in O(n + k). DNF only works for exactly 3 partitions.
- "What if values are strings ('red', 'white', 'blue') not integers?" → Map strings to integers (HashMap), sort integers, map back. Or use a comparison sort.

## Problem 3 — Maximum Gap (LeetCode 164) — Bucket Sort Application

### Problem
Given an unsorted array of non-negative integers, return the maximum difference between successive elements in its sorted form. You must run in O(n) time and O(n) space. Return 0 if fewer than 2 elements.

```
Input:  nums=[3,6,9,1]   → 3  (sorted: [1,3,6,9], max gap = 6-3 or 9-6 = 3)
Input:  nums=[10]         → 0
Input:  nums=[1,10000000] → 9999999
```

### Pattern Recognition
Bucket sort application — exploit the pigeonhole principle. If n numbers span a range of R, any gap ≥ R/(n-1) (the average gap). By creating n-1 buckets of size R/(n-1), the maximum gap must come from elements in different buckets (not within the same bucket). Therefore, we only need to track the minimum and maximum of each bucket, and scan between consecutive non-empty buckets.

### Key Insight — Pigeonhole Principle
Place n elements into n-1 buckets. By the pigeonhole principle, at least one bucket must be empty. The maximum gap cannot be within a single bucket (bucket width = average gap ≤ maximum gap). Therefore, the maximum gap must span across at least one empty bucket — we find it by comparing the minimum of each bucket with the maximum of the previous non-empty bucket.

### Approach
1. Find min and max of the array.
2. Create `n-1` buckets, each spanning range `(max - min) / (n - 1)`.
3. Place each element in its bucket, tracking bucket min and max.
4. Scan consecutive non-empty buckets: gap = bucket[i].min - bucket[i-1].max. Return the maximum such gap.

### Solution

```js
function maximumGap(nums) {
  const n = nums.length;
  if (n < 2) return 0;

  const minVal = Math.min(...nums);
  const maxVal = Math.max(...nums);

  if (minVal === maxVal) return 0; // all elements equal

  // bucket width: each bucket covers this range
  // n-1 buckets for n elements (pigeonhole: one will be empty)
  const bucketWidth = Math.ceil((maxVal - minVal) / (n - 1));
  const bucketCount = n - 1;

  // each bucket tracks {min, max} of elements in it
  const buckets = Array.from({length: bucketCount}, () => ({
    min: Infinity,
    max: -Infinity,
    hasElement: false
  }));

  // distribute elements into buckets
  for (const num of nums) {
    if (num === minVal || num === maxVal) continue; // handle boundaries separately

    const idx = Math.floor((num - minVal) / bucketWidth);
    const bucket = buckets[Math.min(idx, bucketCount - 1)];
    bucket.min = Math.min(bucket.min, num);
    bucket.max = Math.max(bucket.max, num);
    bucket.hasElement = true;
  }

  // scan buckets: maximum gap is between consecutive non-empty buckets
  // or between minVal/maxVal and the nearest bucket
  let maxGap = 0;
  let prevMax = minVal; // track the max of the previous non-empty "slot"

  for (const bucket of buckets) {
    if (!bucket.hasElement) continue; // skip empty buckets

    maxGap = Math.max(maxGap, bucket.min - prevMax);
    prevMax = bucket.max;
  }

  // final gap: last non-empty bucket's max to overall maxVal
  maxGap = Math.max(maxGap, maxVal - prevMax);

  return maxGap;
}
```

### Dry Run

```

n=4, minVal=1, maxVal=9, range=8
bucketWidth=ceil(8/3)=3, bucketCount=3

Buckets cover:
  bucket[0]: [1+0×3, 1+1×3) = [1, 4)
  bucket[1]: [1+1×3, 1+2×3) = [4, 7)
  bucket[2]: [1+2×3, 1+3×3) = [7, 10)

Skip minVal=1 and maxVal=9 (handled separately)

  num=3: idx=floor((3-1)/3)=0 → bucket[0]: min=3, max=3
  num=6: idx=floor((6-1)/3)=1 → bucket[1]: min=6, max=6
  (9 is maxVal — skipped)
  (1 is minVal — skipped)

buckets:
  [0]: {min:3, max:3, hasElement:true}
  [1]: {min:6, max:6, hasElement:true}
  [2]: {min:∞, max:-∞, hasElement:false}  ← empty!

Scan buckets with prevMax=1 (=minVal):
  bucket[0] (hasElement): gap=3-1=2, prevMax=3
  bucket[1] (hasElement): gap=6-3=3, prevMax=6
  bucket[2] (empty): skip

```

### Complexity
- Time: O(n) — finding min/max: O(n), distributing: O(n), scanning: O(n).
- Space: O(n) — n-1 buckets, each storing 3 values.

### Edge Cases
- All equal elements: min === max → return 0.
- Two elements: gap = abs(nums[1] - nums[0]).
- Elements already sorted: buckets fill predictably; max gap found correctly.
- Large range, small n: buckets may be large; still O(n).

### Follow-up Questions
- "What if you need the actual pair of elements forming the maximum gap?" → Track which elements constitute `bucket.min` and `prevMax` when updating `maxGap`.
- "Why can't you just sort and scan?" → Sorting is O(n log n). The problem requires O(n) — hence bucket sort trick.
- "Why does the maximum gap always span a bucket boundary?" → Bucket width ≥ average gap. Any within-bucket gap ≤ bucket width ≤ average gap ≤ maximum gap. So the maximum gap can never be a within-bucket gap — it must cross a bucket boundary.

## Problem 4 — Sort Characters By Frequency (LeetCode 451) — Counting Sort on Characters

### Problem
Given a string `s`, sort it in decreasing order based on character frequency. Characters with the same frequency can be in any order.

```
Input:  s="tree"   → "eert" or "eetr"  (e appears twice, t and r once)
Input:  s="cccaaa" → "aaaccc" or "cccaaa"
Input:  s="Aabb"   → "bbAa" or "bbaA"  (case-sensitive: 'A'≠'a')
```

### Pattern Recognition
Counting sort applied to character frequencies — count frequencies, then sort characters by frequency in descending order. The "sort by frequency" is itself a counting sort problem (sort small integers = frequencies).

### Key Insight
Count each character's frequency. Then use bucket sort on frequencies: create buckets indexed by frequency (1 to n). Place each character into the bucket matching its frequency. Collect from highest-frequency bucket down — this gives characters in decreasing frequency order. Build output by repeating each character its frequency number of times.

### Approach
1. Count character frequencies (O(n)).
2. Create frequency buckets (indices 1 to n) — each bucket holds characters with that frequency (O(n) buckets, O(1) per character for placement).
3. Collect from bucket n down to 1, appending each character repeated freq times.

```js
function frequencySort(s) {
  // Step 1: count character frequencies
  const freq = new Map();
  for (const ch of s) freq.set(ch, (freq.get(ch) || 0) + 1);

  // Step 2: bucket sort by frequency
  // bucket[f] = list of characters with frequency f
  const maxFreq = s.length; // max possible frequency
  const buckets = Array.from({length: maxFreq + 1}, () => []);

  for (const [ch, f] of freq) {
    buckets[f].push(ch); // place character in its frequency bucket
  }

  // Step 3: collect from highest frequency to lowest
  const result = [];
  for (let f = maxFreq; f >= 1; f--) {
    for (const ch of buckets[f]) {
      // append this character f times
      for (let i = 0; i < f; i++) result.push(ch);
    }
  }

  return result.join('');
}
```

### Dry Run

```

n=4

  freq: {t:1, r:1, e:2}

Step 2 — Bucket sort by frequency:
  buckets[1] = ['t', 'r']
  buckets[2] = ['e']
  buckets[3] = []  (empty)
  buckets[4] = []  (empty)

Step 3 — Collect highest to lowest:
  f=4: buckets[4]=[] → skip
  f=3: buckets[3]=[] → skip
  f=2: buckets[2]=['e'] → append 'e' twice → result=['e','e']
  f=1: buckets[1]=['t','r'] → append 't' once, 'r' once → result=['e','e','t','r']

return "eetr" ✓
```

### Complexity
- Time: O(n) — counting: O(n), bucketing: O(k) where k = distinct chars ≤ n, collecting: O(n) total characters output.
- Space: O(n) — frequency map + buckets + result.

### Edge Cases
- Single character: freq map has one entry; output = that character.
- All same character: one bucket with that character at freq = n.
- All distinct characters: all go in bucket[1]; output is those characters in any order.
- Case sensitivity: 'A' and 'a' are distinct characters with separate frequency counts.

### Follow-up Questions
- "Sort in increasing frequency order?" → Collect from f=1 upward instead of downward.
- "For ties (same frequency), sort lexicographically?" → Within each bucket, sort the characters before collecting.
- "Return all valid orderings?" → Collect from buckets in all permutations — exponential; typically not asked.

## Problem 5 — Radix Sort for 32-bit Integers

### Problem
Implement radix sort for an array of non-negative 32-bit integers. Return the sorted array.

```
Input:  arr=[170, 45, 75, 90, 802, 24, 2, 66]
Output: [2, 24, 45, 66, 75, 90, 170, 802]
```

### Pattern Recognition
Direct radix sort application — integers with up to 3 decimal digits (or 4 bytes for 32-bit). LSD (least significant digit first) with stable counting sort per digit position.

### Key Insight
Process one decimal digit at a time (or one byte at a time for efficiency). After d passes (one per digit position), the array is fully sorted. Each pass uses stable counting sort on just the current digit — preserving the ordering from previous passes.

### Approach — Decimal Radix (Base 10)

```js
function radixSort(arr) {
  if (arr.length === 0) return arr;

  const maxVal = Math.max(...arr);

  // process one digit at a time starting from units place
  for (let exp = 1; Math.floor(maxVal / exp) > 0; exp *= 10) {
    stableCountByDigit(arr, exp);
  }

  return arr;
}

function stableCountByDigit(arr, exp) {
  const n = arr.length;
  const BASE = 10;
  const output = new Array(n);
  const count = new Array(BASE).fill(0);

  // Phase 1: count digit occurrences at position exp
  for (const val of arr) {
    const digit = Math.floor(val / exp) % BASE;
    count[digit]++;
  }

  // Phase 2: accumulate
  for (let d = 1; d < BASE; d++) count[d] += count[d - 1];

  // Phase 3: place right-to-left (stable!)
  for (let i = n - 1; i >= 0; i--) {
    const digit = Math.floor(arr[i] / exp) % BASE;
    output[count[digit] - 1] = arr[i];
    count[digit]--;
  }

  // Phase 4: copy back
  for (let i = 0; i < n; i++) arr[i] = output[i];
}
```

### Approach — Byte-Level Radix (Base 256, 4 Passes for 32-bit)

```js
function radixSort256(arr) {
  // 4 passes: bytes 0, 1, 2, 3 (LSB to MSB)
  for (let bytePos = 0; bytePos < 4; bytePos++) {
    stableCountByByte(arr, bytePos);
  }
  return arr;
}

function stableCountByByte(arr, bytePos) {
  const n = arr.length;
  const BASE = 256;
  const shift = bytePos * 8; // bit shift to extract the relevant byte
  const output = new Array(n);
  const count = new Array(BASE).fill(0);

  for (const val of arr) {
    const byte = (val >>> shift) & 0xFF; // extract byte at position bytePos
    count[byte]++;
  }

  for (let b = 1; b < BASE; b++) count[b] += count[b - 1];

  for (let i = n - 1; i >= 0; i--) {
    const byte = (arr[i] >>> shift) & 0xFF;
    output[count[byte] - 1] = arr[i];
    count[byte]--;
  }

  for (let i = 0; i < n; i++) arr[i] = output[i];
}
```

## Problem 6 — H-Index (LeetCode 274) — Counting Sort Application

### Problem
Given an array `citations` where `citations[i]` is the number of citations of paper i, return the researcher's h-index: the maximum value h such that at least h papers have ≥ h citations.

```
Input:  citations=[3,0,6,1,5]   → 3
        (3 papers with ≥3 citations: 3,6,5)

Input:  citations=[1,3,1]        → 1
Input:  citations=[0,0]          → 0
```

### Pattern Recognition
Counting sort approach — citation counts are non-negative integers bounded by n (the total number of papers, since having more than n citations still only contributes to the h-index up to n). Counting sort in O(n) is faster than the O(n log n) sort-then-binary-search approach.

### Key Insight
Cap citation counts at n (citations[i] > n means the paper has "at least n citations" — enough for h=n). Build a count array of size n+1. Scan from the right (highest h) to find the largest h where cumulative count ≥ h.

### Solution

```js
function hIndex(citations) {
  const n = citations.length;
  const count = new Array(n + 1).fill(0);

  // count[i] = number of papers with exactly i citations
  // cap at n: citations > n are treated as n
  for (const c of citations) {
    count[Math.min(c, n)]++;
  }

  // scan from right: find largest h where
  // sum(count[h..n]) >= h (at least h papers with >= h citations)
  let papers = 0; // running total of papers with >= h citations
  for (let h = n; h >= 0; h--) {
    papers += count[h];
    if (papers >= h) return h; // h papers have >= h citations
  }

  return 0; // fallback (never reached since h=0 always works)
}
```

### Dry Run

```

  3: count[3]++
  0: count[0]++
  6→5: count[5]++  (capped at n=5)
  1: count[1]++
  5: count[5]++

count: [1, 1, 0, 1, 0, 2]
  (1 paper with 0 citations, 1 with 1, 0 with 2, 1 with 3, 0 with 4, 2 with 5+)

Scan right-to-left:
  h=5: papers += count[5]=2 → papers=2. 2 >= 5? No
  h=4: papers += count[4]=0 → papers=2. 2 >= 4? No
  h=3: papers += count[3]=1 → papers=3. 3 >= 3? Yes → return 3 ✓
```

### Complexity
- Time: O(n) — one pass to count, one pass to scan. No sorting needed.
- Space: O(n) — count array of size n+1.

### Edge Cases
- All zeros: count[0]=n, scan reaches h=0 with papers=n ≥ 0 → return 0.
- All very high citations (> n): all capped to n; count[n]=n; h=n: papers=n ≥ n → return n.
- Single paper with 0 citations: h=0.
- Single paper with ≥1 citation: h=1.

### Follow-up Questions
- "Citations are already sorted in descending order (H-Index II)?" → Binary search: find the largest h where `citations[n-h] >= h`. O(log n) — even better.
- "Why cap citations at n?" → h-index can be at most n (number of papers). A paper with 1000 citations when n=5 contributes to h ≤ 5 just the same as one with 5 citations.

## Quick Reference — Non-Comparison Sorts

```
COUNTING SORT
  When:    Integer keys in [0, k], k small (k ≈ O(n))
  Time:    O(n + k)
  Space:   O(n + k)
  Stable:  Yes (right-to-left placement)
  Steps:   Count → Accumulate → Place (right-to-left) → Copy back
  Pitfall: k >> n wastes space; negative values need offset

RADIX SORT (LSD)
  When:    Fixed-width integers or fixed-length strings
  Time:    O(d × (n + b))   d=digits, b=base
  Space:   O(n + b)
  Stable:  Yes (requires stable sub-sort)
  Steps:   For each digit LSB→MSB: stable counting sort by that digit
  Pitfall: Must use STABLE counting sort; negative numbers need special handling

BUCKET SORT
  When:    Uniformly distributed real values in [0, 1) or mapped range
  Time:    O(n) average, O(n²) worst case
  Space:   O(n + k)
  Stable:  Depends on inner sort
  Steps:   Map to buckets → Sort each bucket → Concatenate
  Pitfall: Non-uniform distribution → unbalanced buckets → O(n²) worst case

DECISION TREE
  Keys in small integer range? → Counting Sort
  Fixed-width integers, large n? → Radix Sort
  Uniformly distributed floats? → Bucket Sort
  Otherwise? → Comparison Sort (O(n log n))
```

## Common Bugs Checklist

Before finalizing any non-comparison sort, verify:

1. **Counting sort: count array size is k+1, not k** — if max value is k, valid indices are 0..k, requiring `k+1` entries. Allocating size `k` causes out-of-bounds access at `count[k]`.

2. **Right-to-left for stability in counting sort Phase 3** — iterating left-to-right produces a sorted array but is NOT stable (equal elements are placed in reverse of their input order). Any code that claims counting sort is stable must iterate right-to-left during placement.

3. **Radix sort: sub-sort MUST be stable** — using an unstable sort at any digit level corrupts the ordering from previous levels. Always verify the per-digit sort is stable before claiming the overall radix sort is stable.

4. **Radix sort termination condition** — `while (Math.floor(maxVal / exp) > 0)` terminates when `exp` exceeds `maxVal`. If `maxVal = 0`, the loop never runs — guard with `if (maxVal === 0) return arr` or handle this as a special case.

5. **Bucket sort: clamp to last bucket for the maximum value** — the formula `floor((val - min) / range * n)` gives index `n` for `val = max`, which is out of bounds. Use `Math.min(idx, n-1)` to clamp the maximum element to the last bucket.

6. **Negative numbers in counting sort** — accessing `count[negative_value]` in JavaScript silently creates an array property with a negative key (not a valid array index), corrupting the count. Always shift by `minVal` or assert values are non-negative before running counting sort.

---

**Final Tip:** At the 5 YOE level, non-comparison sorts are rarely the primary question — they're almost always embedded in a harder problem ("sort this in O(n)," "find the maximum gap," "sort by frequency"). The signal answer is to immediately name the sort type and justify it: "since keys are integers in range [0, k] with k = O(n), I'll use counting sort for O(n) time instead of O(n log n)." The highest-value thing to demonstrate is knowing the tradeoffs — when O(n) is achievable and why, why comparison sorts can't break Ω(n log n), and when non-comparison sorts degrade (k >> n for counting sort, non-uniform distribution for bucket sort). Being able to derive the bucket sort insight for maximum gap (pigeonhole principle → maximum gap must span a bucket boundary) without having memorized it specifically is what separates a 5 YOE answer from a 2 YOE answer.
