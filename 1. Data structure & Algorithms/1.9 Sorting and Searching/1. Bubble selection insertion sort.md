### Section 1: Fundamentals

**Q1. What are the three elementary sorting algorithms, and what is the single most important thing to know about each before any other detail?**
A: The three elementary sorting algorithms — bubble sort, selection sort, and insertion sort — are O(n²) comparison-based sorts that operate in-place with O(1) extra space. The single most important fact about each:

- **Bubble sort**: repeatedly swaps adjacent out-of-order pairs, "bubbling" the largest unsorted element to its final position each pass. Almost never used in production — it has the worst constant factors of the three and no situation where it clearly beats insertion sort. Its value is pedagogical and as an interview discussion topic.
- **Selection sort**: finds the minimum of the unsorted region and places it at the front each pass. Makes exactly n-1 swaps total (one per pass) — the minimum possible for an in-place sort. Useful when swap cost is extremely high (e.g., writing to flash memory) and comparison cost is negligible.
- **Insertion sort**: maintains a sorted prefix and inserts each new element into its correct position. Exceptionally efficient on nearly-sorted data (O(n) best case) and small arrays. Used as the base case in hybrid sorts (timsort, introsort) for subarrays of size ≤ 16–32.

```
All three: O(n²) average and worst case (except insertion sort: O(n) best case)
All three: O(1) space (in-place)
Key differentiator: stability, swap count, best-case behavior, and practical constant factors
```

**Q2. What does "stable sort" mean, and which of the three algorithms are stable?**
A: A sort is **stable** if elements with equal keys appear in the output in the same relative order as they appeared in the input. Stability matters when sorting objects by one key when the data was already sorted (or partially sorted) by another key — an unstable sort can destroy a prior sort's order for equal elements.

- **Bubble sort**: stable. Adjacent swaps only occur when `arr[j] > arr[j+1]` (strict inequality) — equal elements are never swapped, preserving their original order.
- **Selection sort**: **not stable**. The selection of the minimum and its swap with the current front element can move a later-occurring equal element ahead of an earlier-occurring one.
- **Insertion sort**: stable. Elements are shifted right only when strictly greater than the element being inserted — equal elements are never moved past each other.

```
Stability example:
Input: [(3,A), (1,B), (3,C), (2,D)]   (value, original-label)

Stable sort by value:
  [(1,B), (2,D), (3,A), (3,C)]   ← A before C (original order preserved)

Selection sort (unstable) might produce:
  [(1,B), (2,D), (3,C), (3,A)]   ← C before A (original order violated)

Why: if (3,A) is at index 0 and (3,C) is at index 2, selecting the minimum from
[0..3] finds (1,B) at index 1, swaps it with (3,A) → (3,A) moved to index 1.
Later passes may swap (3,A) and (3,C) depending on their relative positions.
```

**Q3. Walk through bubble sort step by step — what invariant does each pass establish?**
A: Bubble sort invariant: after pass k (k starting from 1), the k largest elements are in their correct final positions at the end of the array. Each pass compares adjacent pairs and swaps if out of order — the largest unsorted element "bubbles up" to its correct position.

```js
function bubbleSort(arr) {
  const n = arr.length;

  for (let pass = 0; pass < n - 1; pass++) {
    // After this pass, arr[n-1-pass] is in its final sorted position
    let swapped = false; // early termination optimization

    for (let j = 0; j < n - 1 - pass; j++) {
      if (arr[j] > arr[j + 1]) {
        [arr[j], arr[j + 1]] = [arr[j + 1], arr[j]];
        swapped = true;
      }
    }

    if (!swapped) break; // array is sorted — no swaps in this pass
  }

  return arr;
}

// Trace on [64, 34, 25, 12, 22]:
// Pass 1: compare all adjacent pairs
//   [64,34] → swap → [34,64,25,12,22]
//   [64,25] → swap → [34,25,64,12,22]
//   [64,12] → swap → [34,25,12,64,22]
//   [64,22] → swap → [34,25,12,22,64]  ← 64 in final position
// Pass 2: compare arr[0..2]
//   [34,25] → swap → [25,34,12,22,64]
//   [34,12] → swap → [25,12,34,22,64]
//   [34,22] → swap → [25,12,22,34,64]  ← 34 in final position
// Pass 3: [25,12,22]
//   [25,12] → swap → [12,25,22,34,64]
//   [25,22] → swap → [12,22,25,34,64]  ← 25 in final position
// Pass 4: [12,22]
//   no swap needed ← early termination if swapped=false
// Result: [12,22,25,34,64] ✓
```

**Q4. Walk through selection sort — what invariant does each pass establish, and what makes it distinct from bubble sort?**
A: Selection sort invariant: after pass k (k starting from 0), the k smallest elements are in their correct final positions at the beginning of the array. Each pass scans the entire unsorted region to find its minimum, then places it at the front with a single swap.

```js
function selectionSort(arr) {
  const n = arr.length;

  for (let i = 0; i < n - 1; i++) {
    // Find the minimum in arr[i..n-1]
    let minIdx = i;
    for (let j = i + 1; j < n; j++) {
      if (arr[j] < arr[minIdx]) {
        minIdx = j;
      }
    }

    // Place it at arr[i] with one swap
    if (minIdx !== i) {
      [arr[i], arr[minIdx]] = [arr[minIdx], arr[i]];
    }
  }

  return arr;
}

// Trace on [64, 25, 12, 22, 11]:
// Pass 0 (i=0): find min in [64,25,12,22,11] → 11 at idx 4. Swap arr[0] and arr[4].
//   [11, 25, 12, 22, 64]   ← 11 in final position
// Pass 1 (i=1): find min in [25,12,22,64] → 12 at idx 2. Swap arr[1] and arr[2].
//   [11, 12, 25, 22, 64]   ← 12 in final position
// Pass 2 (i=2): find min in [25,22,64] → 22 at idx 3. Swap arr[2] and arr[3].
//   [11, 12, 22, 25, 64]   ← 22 in final position
// Pass 3 (i=3): find min in [25,64] → 25 at idx 3. No swap (minIdx === i).
//   [11, 12, 22, 25, 64]   ← 25 in final position
// Result: [11,12,22,25,64] ✓

// Key distinctions from bubble sort:
// - Makes exactly n-1 swaps (vs. up to n²/2 for bubble)
// - Number of comparisons is always n(n-1)/2 — no early termination
// - NOT stable (the swap can jump over equal elements)
```

**Q5. Walk through insertion sort — what invariant does each step establish, and what makes it fundamentally different from the other two?**
A: Insertion sort invariant: after step k (k starting from 1), `arr[0..k]` is a sorted permutation of the first k+1 elements. Each step takes the next unsorted element (the "key") and inserts it into its correct position within the already-sorted prefix by shifting larger elements one position right.

```js
function insertionSort(arr) {
  const n = arr.length;

  for (let i = 1; i < n; i++) {
    const key = arr[i]; // element to insert into sorted prefix arr[0..i-1]
    let j = i - 1;

    // Shift elements greater than key one position to the right
    while (j >= 0 && arr[j] > key) {
      arr[j + 1] = arr[j]; // shift right (not a swap — one assignment per shift)
      j--;
    }

    arr[j + 1] = key; // place key in its correct position
  }

  return arr;
}

// Trace on [12, 11, 13, 5, 6]:
// i=1, key=11: arr[0]=12 > 11 → shift. arr=[12,12,13,5,6]. j=-1. Place at j+1=0.
//   [11, 12, 13, 5, 6]
// i=2, key=13: arr[1]=12 < 13 → no shift. Place at j+1=2.
//   [11, 12, 13, 5, 6]
// i=3, key=5: 13>5 shift, 12>5 shift, 11>5 shift. arr=[11,11,12,13,6]. j=-1. Place at 0.
//   [5, 11, 12, 13, 6]
// i=4, key=6: 13>6 shift, 12>6 shift, 11>6 shift, 5<6 stop. j=0. Place at j+1=1.
//   [5, 6, 11, 12, 13] ✓

// Fundamental difference: insertion sort is ADAPTIVE
// - On already-sorted input: inner while loop never executes → O(n) total
// - On nearly-sorted input: inner while runs only a few steps per element → near-O(n)
// - Bubble and selection sort are always O(n²) comparisons regardless of input order
```

### Section 2: Complexity Analysis

**Q6. Provide the complete complexity analysis for all three algorithms across best, average, and worst cases.**
A:

| Algorithm | Best Case | Average Case | Worst Case | Space | Stable | Adaptive |
|---|---|---|---|---|---|---|
| Bubble Sort | O(n) | O(n²) | O(n²) | O(1) | Yes | Yes (with flag) |
| Selection Sort | O(n²) | O(n²) | O(n²) | O(1) | No | No |
| Insertion Sort | O(n) | O(n²) | O(n²) | O(1) | Yes | Yes |

**Bubble sort best case**: O(n) with the `swapped` flag optimization. If the array is already sorted, the first pass makes zero swaps — `swapped` remains false — and the algorithm terminates. Without the flag, bubble sort is always O(n²) even on sorted input.

**Selection sort**: always O(n²) comparisons. The inner loop always scans the entire unsorted region to find the minimum — there's no way to terminate early even if the array is already sorted. This makes selection sort non-adaptive.

**Insertion sort best case**: O(n). On a sorted array, for each element the inner `while` loop's condition `arr[j] > key` is immediately false — zero shifts per element, n-1 iterations of the outer loop = O(n) total.

**Insertion sort worst case**: O(n²), achieved on a reverse-sorted array. Each new element must be shifted past all previously sorted elements — element at index i requires i shifts, giving 0 + 1 + 2 + ... + (n-1) = n(n-1)/2 shifts.

**Q7. How many comparisons and swaps does each algorithm make, and why does this matter?**
A: The exact operation counts reveal why each algorithm suits different hardware and data profiles:

**Bubble sort**:
- Comparisons: O(n²) worst/average, O(n) best (with flag — one pass to verify sortedness).
- Swaps: O(n²) worst/average (up to n(n-1)/2), O(0) best (sorted array, no swaps).
- Each swap is a three-operation exchange (temp assignment). High swap cost → avoid bubble sort.

**Selection sort**:
- Comparisons: always exactly n(n-1)/2 — no early termination possible.
- Swaps: exactly n-1 swaps (one per pass) — the minimum possible for a general in-place sort.
- Optimal when swaps are extremely expensive (e.g., physically moving large data blocks, writing to NAND flash with limited write cycles) and comparisons are cheap.

**Insertion sort**:
- Comparisons: O(n²) worst, O(n) best. On nearly-sorted data: proportional to the number of inversions.
- Shifts (not full swaps): each "shift" is one assignment (`arr[j+1] = arr[j]`) rather than three-way exchange. In practice, shifts cost about 1/3 of full swaps — insertion sort has better constant factors than bubble sort even though both are O(n²).
- Number of shifts = number of inversions in the array. An inversion is a pair (i, j) with i < j but arr[i] > arr[j]. Fully sorted: 0 inversions = 0 shifts. Reverse sorted: n(n-1)/2 inversions = maximum shifts.

```
Inversion count → insertion sort performance:
Array [1,2,3,4,5]: 0 inversions → O(n) (best case)
Array [1,2,3,5,4]: 1 inversion → O(n) (nearly sorted)
Array [3,1,2,4,5]: 2 inversions → O(n) (nearly sorted)
Array [5,4,3,2,1]: n(n-1)/2 inversions → O(n²) (worst case)

This is why insertion sort is the algorithm of choice for "almost sorted" data.
```

**Q8. What is the "number of inversions" and why is it the exact measure of insertion sort's performance?**
A: An **inversion** in an array is a pair of indices (i, j) where i < j but `arr[i] > arr[j]` — an out-of-order pair. The number of inversions precisely measures "how unsorted" an array is: 0 inversions means fully sorted; n(n-1)/2 inversions (maximum) means reverse sorted.

Insertion sort's total number of shifts equals the number of inversions in the original array. This is because each shift eliminates exactly one inversion: when element `key` is shifted from position i to position j+1, it moves past elements arr[j+1..i-1] — each of which formed an inversion with `key` — and each shift removes exactly one such inversion. Since each shift removes exactly one inversion and we start with k inversions total, insertion sort performs exactly k shifts.

This makes insertion sort **optimal for nearly-sorted data**: if the array is "almost sorted" (few inversions — each element is at most d positions from its correct position), insertion sort runs in O(n × d) — linear for constant d.

```js
// Count inversions (useful for estimating insertion sort performance)
function countInversions(arr) {
  let inversions = 0;
  for (let i = 0; i < arr.length; i++) {
    for (let j = i + 1; j < arr.length; j++) {
      if (arr[i] > arr[j]) inversions++;
    }
  }
  return inversions;
}
// O(n²) — for actual counting use merge sort's divide-and-conquer: O(n log n)

// [3,1,2]: inversions = (3,1), (3,2) = 2. Insertion sort makes 2 shifts. ✓
// [5,4,3,2,1]: inversions = C(5,2) = 10. Insertion sort makes 10 shifts. ✓
```

### Section 3: When to Use Each Algorithm

**Q9. In what specific, real-world situations is insertion sort the correct choice over O(n log n) algorithms?**
A: Insertion sort is genuinely better than O(n log n) algorithms in five concrete situations:

**1. Very small arrays (n ≤ 16–32)**: the O(n log n) constant factors of merge sort and quicksort (recursive call overhead, cache misses from divide-and-conquer) make them slower than O(n²) insertion sort for tiny inputs. This is why Java's `Arrays.sort` for primitive types (introsort) switches to insertion sort for subarrays of size ≤ 47, and Python's timsort uses insertion sort for runs of size ≤ 64.

**2. Nearly-sorted data (few inversions)**: if an array is "almost sorted" — each element is at most k positions from its final destination — insertion sort runs in O(n × k). For k = O(1) or k = O(log n), this is faster than O(n log n) sorts' non-adaptive behavior.

**3. Online sorting (elements arrive one at a time)**: insertion sort naturally handles this — each new element is immediately inserted into the correct position in the already-sorted prefix. Merge sort and quicksort require all elements upfront.

**4. Small memory / embedded systems**: insertion sort's O(1) space and tiny code size (the entire algorithm is a handful of lines) make it suitable for microcontrollers where code space is measured in bytes.

**5. Linked lists** (with modified implementation): insertion sort on a linked list avoids the shifting cost — just rewire pointers to insert at the correct position. Merge sort is even better for linked lists (O(n log n)), but insertion sort is the simplest correct approach.

```
Real usage in standard libraries:
Python timsort:  insertion sort for runs ≤ 64 elements
Java introsort:  insertion sort for subarrays ≤ 47 elements
C++ std::sort:   insertion sort for subarrays ≤ 16 elements (implementation-dependent)
glibc qsort:     insertion sort below a threshold
V8 (JavaScript): timsort-based, uses insertion sort for small subarrays
```

**Q10. When is selection sort genuinely preferable to insertion sort?**
A: Selection sort is preferable in exactly one concrete situation: **when the cost of a swap is dramatically higher than the cost of a comparison**, and the number of swaps must be minimized.

Selection sort makes exactly n-1 swaps regardless of input — the theoretical minimum for a general in-place sort. Insertion sort can make O(n²) shifts, and although each shift is cheaper than a full swap (one assignment vs. three), the total write count is much higher.

Concrete scenarios:
- **NAND flash memory**: flash cells have limited write cycles (10,000–100,000 writes before failure). Minimizing writes extends hardware lifetime. Selection sort's n-1 swaps vs. insertion sort's O(n²) shifts directly translates to hardware longevity.
- **Physically large records**: if each "element" is a large data block (megabytes) and swapping means physically moving data, n-1 block moves vs. O(n²) is a meaningful difference.
- **External storage with seek cost**: if swap requires expensive random seeks on a physical disk, minimizing swap count matters more than minimizing comparisons.

Outside these narrow scenarios, insertion sort beats selection sort in virtually every metric: it's adaptive (O(n) best case vs. O(n²) always), stable (selection sort is not), and has lower constant factors on modern hardware for random data.

**Q11. Is there any situation where bubble sort is the best choice?**
A: Practically speaking, no — bubble sort is almost never the correct choice in production code. For every scenario where bubble sort might seem appropriate, a better alternative exists:

- **Simple to implement**: insertion sort is equally simple and strictly better.
- **Stable sort**: insertion sort is also stable and faster.
- **Detect if already sorted**: the `swapped` flag optimization makes bubble sort O(n) on sorted input — but insertion sort achieves the same O(n) best case with better average-case performance.
- **Parallelizable sorting networks**: odd-even transposition sort (a parallel variant of bubble sort) has niche uses in hardware sorting networks, but this is a hardware design context, not a software one.

Bubble sort's primary value is **pedagogical**: its mechanism is visually intuitive ("heavy elements sink, light elements float"), making it excellent for teaching comparison-based sorting. It also serves as an interview discussion topic — a strong candidate can articulate exactly why it's inferior and name the specific scenarios where insertion sort or selection sort are the actual correct choices.

```
Definitive ranking for practical use:
1. O(n log n) sorts (merge sort, quicksort, heapsort, timsort) — for n > 32
2. Insertion sort — for small n, nearly-sorted data, online sorting
3. Selection sort — when swap cost >> comparison cost
4. Bubble sort — pedagogical purposes only
```

**Q12. How do these algorithms compare on different data distributions — random, nearly sorted, reverse sorted, and all equal?**
A:

| Input distribution | Bubble Sort | Selection Sort | Insertion Sort |
|---|---|---|---|
| Random | O(n²) | O(n²) | O(n²) |
| Already sorted | O(n)* | O(n²) | O(n) |
| Nearly sorted (k inversions) | O(n + k)* | O(n²) | O(n + k) |
| Reverse sorted | O(n²) | O(n²) | O(n²) |
| All equal | O(n)* | O(n²) | O(n) |

*With the `swapped` flag optimization.

The takeaway: insertion sort and bubble sort (with flag) are both adaptive — they benefit from existing order. Selection sort is completely non-adaptive — it always performs the same number of comparisons regardless of input. On random and reverse-sorted data, all three perform similarly (O(n²)). The distinction emerges on structured input, particularly nearly-sorted arrays where insertion sort's inversion-proportional behavior becomes a significant practical advantage.

### Section 4: Implementation Details and Optimizations

**Q13. What is the "binary insertion sort" optimization, and when does it help?**
A: Standard insertion sort uses linear search to find the insertion position — O(i) comparisons for the i-th element. Since the prefix is always sorted, **binary insertion sort** uses binary search instead — O(log i) comparisons per element, O(n log n) total comparisons.

However, binary insertion sort doesn't reduce the number of **shifts**: even after finding the insertion position in O(log i) time, all elements between that position and the current position must still be shifted right — O(i) shifts per element, O(n²) total shifts. So binary insertion sort reduces comparisons to O(n log n) but keeps shifts at O(n²).

This optimization helps specifically when comparisons are expensive (e.g., comparing long strings, complex objects) and shifts are cheap (contiguous memory, small element size). In practice, the improvement is modest — the shift cost dominates for large arrays, and for small arrays (where insertion sort is used as a base case in hybrids) the O(n log n) comparison cost isn't the bottleneck.

```js
function binaryInsertionSort(arr) {
  for (let i = 1; i < arr.length; i++) {
    const key = arr[i];

    // Binary search for insertion position in arr[0..i-1]
    let lo = 0, hi = i;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (arr[mid] <= key) lo = mid + 1; // stable: equal elements keep key to right
      else hi = mid;
    }
    // lo is the insertion position

    // Shift elements arr[lo..i-1] one position right
    for (let j = i; j > lo; j--) {
      arr[j] = arr[j - 1];
    }
    arr[lo] = key;
  }
  return arr;
}
// Comparisons: O(n log n)   ← improvement
// Shifts:      O(n²)        ← unchanged
// Useful when: comparison >> shift cost (string sorting, complex comparisons)
```

**Q14. How can bubble sort be optimized beyond the basic `swapped` flag?**
A: Two additional optimizations beyond the standard `swapped` flag:

**Cocktail shaker sort (bidirectional bubble sort)**: instead of always passing left-to-right, alternate direction each pass — left-to-right on odd passes (bubbles the max to the right), right-to-left on even passes (bubbles the min to the left). This reduces the number of passes needed for elements that need to move a long distance in both directions.

```js
function cocktailShakerSort(arr) {
  let start = 0, end = arr.length - 1;
  let swapped = true;

  while (swapped) {
    swapped = false;

    // Left to right: bubble max to end
    for (let i = start; i < end; i++) {
      if (arr[i] > arr[i + 1]) {
        [arr[i], arr[i + 1]] = [arr[i + 1], arr[i]];
        swapped = true;
      }
    }
    end--;

    // Right to left: bubble min to start
    for (let i = end; i > start; i--) {
      if (arr[i] < arr[i - 1]) {
        [arr[i], arr[i - 1]] = [arr[i - 1], arr[i]];
        swapped = true;
      }
    }
    start++;
  }
  return arr;
}
```

**Last-swap optimization**: track the index of the last swap in each pass. All elements after the last swap position are already in their correct positions — the next pass only needs to go up to that index, not to `n - 1 - pass`. This can significantly reduce comparisons when a few elements are far out of place.

```js
function bubbleSortOptimized(arr) {
  let end = arr.length - 1;
  while (end > 0) {
    let lastSwap = 0;
    for (let j = 0; j < end; j++) {
      if (arr[j] > arr[j + 1]) {
        [arr[j], arr[j + 1]] = [arr[j + 1], arr[j]];
        lastSwap = j + 1; // last swapped position
      }
    }
    end = lastSwap - 1; // next pass only goes up to lastSwap-1
  }
  return arr;
}
```

**Q15. How do these algorithms perform on linked lists vs. arrays, and does the data structure change which algorithm is preferred?**
A: The data structure significantly affects algorithm choice:

**Arrays**: random access is O(1). All three algorithms work naturally. Insertion sort's "shift" operation is fast for contiguous memory. Cache prefetching makes sequential access (as in insertion sort's inner loop) very efficient.

**Linked lists**: random access is O(n) — you must traverse from the head. Swapping is O(1) (rewire two pointers) but finding the j-th element is O(j). This changes the analysis:

- **Bubble sort on linked list**: comparing and swapping adjacent nodes is O(1) — no positional lookup needed since we traverse sequentially. Adjacent swaps = pointer rewiring. Still O(n²) comparisons, but constant factor is reasonable.
- **Selection sort on linked list**: finding the minimum each pass requires a full traversal — O(n) per pass = O(n²) total comparisons. Swapping the minimum to the front is O(1) pointer operation. Still works but comparisons are expensive per pass since no benefit from contiguous layout.
- **Insertion sort on linked list**: maintaining a sorted prefix, inserting each new element requires scanning the sorted prefix from the head — O(i) per element = O(n²) total. But the actual insertion (pointer rewiring) is O(1) — no shifting needed. This is actually an advantage: insertion sort's "shift" cost disappears on linked lists.

For linked lists, **merge sort** is strongly preferred: O(n log n) time, O(log n) stack space (or O(1) with iterative merge sort), and the split/merge operations work naturally with pointer manipulation.

### Section 5: Scenario / Interview-Style Questions

**Q16. "Your interviewer asks you to sort a small array of 10 integers. What do you use and why?"**
A: Insertion sort — for three reasons specific to this context:

First, n=10 is well within the range (≤ 32) where insertion sort's low overhead beats O(n log n) algorithms' recursion and partition costs. For 10 elements, O(n²) and O(n log n) differ by a factor of roughly 10/log₂(10) ≈ 3 — but the constant factors of merge sort or quicksort (function calls, stack frames, partition bookkeeping) are high enough to make insertion sort faster in practice.

Second, insertion sort is stable — if any two elements are equal, their original order is preserved — which is often the correct default behavior.

Third, insertion sort's code is minimal and easy to verify correct at a glance — for a small fixed-size sort, code clarity matters.

If the interviewer asks about sorted-order guarantees, I'd also mention that insertion sort runs in O(n) if the 10 elements happen to already be in order — gracefully handling the trivial case.

**Q17. "You have a nearly-sorted array of 1 million elements, where each element is at most 5 positions from its final sorted position. What do you use?"**
A: Insertion sort — this is its exact best-case scenario. Each element is at most 5 positions from its correct position, meaning at most 5 inversions per element, so the total number of inversions is at most 5n = 5,000,000. Since insertion sort performs exactly one shift per inversion, total shifts = at most 5,000,000 — O(n) work. The result is effectively linear.

By contrast, a generic O(n log n) sort like merge sort would take n × log₂(n) ≈ 10^6 × 20 = 2 × 10^7 operations — 4× more work, with additional overhead for recursion and auxiliary arrays.

No other sort achieves O(n) on this specific input without knowing the structure of the data in advance. Insertion sort naturally exploits the sorted structure through its inversion-elimination mechanism.

**Q18. "You need to sort an array but swaps are extremely expensive (e.g., each swap physically moves a 1GB data block). What do you use?"**
A: Selection sort — it makes exactly n-1 swaps, the minimum possible for a general in-place comparison sort. No other comparison-based sort guarantees fewer than n-1 swaps for all inputs.

However, I'd also note two important alternatives:
- **Cycle sort**: an O(n²) algorithm that performs the absolute minimum number of writes — writes each element to its final position by following cycles in the permutation. Achieves the theoretical minimum of n - (number of cycles) writes. More complex to implement than selection sort but optimal for write-minimization.
- **Sort indices, then permute**: instead of sorting the data in-place, sort an array of indices (cheap, data stays stationary) and then apply the permutation with minimum physical moves. This separates the comparison work from the swap work.

For the specific scenario described (1GB data blocks), building an index array of n integers, sorting the indices with an O(n log n) sort, and then applying the permutation in-place (which requires at most n swaps, following cycles) is probably the best overall approach — O(n log n) for cheap index comparisons, then n physical block moves.

**Q19. "Implement a sort that works correctly for nearly-sorted streams of data arriving in real time."**
A: Insertion sort — it's the canonical online sorting algorithm. "Online" means elements arrive one at a time and must be incorporated into the sorted structure before the next element arrives. Insertion sort naturally operates in this mode: maintain a sorted prefix; when a new element arrives, insert it into its correct position in the prefix via binary search (position) and shifting (placement).

```js
class OnlineSorter {
  constructor() {
    this.sorted = []; // maintained in sorted order at all times
  }

  insert(element) {
    // Binary search for the insertion position
    let lo = 0, hi = this.sorted.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (this.sorted[mid] <= element) lo = mid + 1;
      else hi = mid;
    }

    // Insert at position lo (shift elements right)
    this.sorted.splice(lo, 0, element); // O(n) shift cost
  }

  getSorted() {
    return [...this.sorted];
  }
}

// Each insert: O(log n) for position, O(n) for shift → O(n) per element
// n inserts: O(n²) total
// But for nearly-sorted streams (each element close to its final position):
// shift cost is O(k) where k = distance from current position → near-O(n) total
```

For truly real-time sorted output with O(log n) insert and O(1) access to any rank, a balanced BST or a skip list would be better — but for simple "I need a sorted array and elements arrive in order," insertion sort's simplicity is compelling.

**Q20. "Compare insertion sort to shell sort — what problem does shell sort solve?"**
A: Insertion sort's weakness is that it can only eliminate one inversion per shift — an element that's far from its final position requires many shifts to travel there. Shell sort generalizes insertion sort by allowing elements to jump multiple positions at a time using a "gap sequence."

Shell sort performs multiple passes of insertion sort with decreasing gap sizes. In the first pass, elements separated by gap g are compared and sorted relative to each other (a "g-sort"). Subsequent passes use smaller gaps. The final pass is a standard insertion sort (gap=1) — but by then, the array is nearly sorted (each element is close to its final position), so the gap-1 pass is fast.

```js
function shellSort(arr) {
  let gap = Math.floor(arr.length / 2);

  while (gap > 0) {
    // Insertion sort with current gap
    for (let i = gap; i < arr.length; i++) {
      const key = arr[i];
      let j = i - gap;
      while (j >= 0 && arr[j] > key) {
        arr[j + gap] = arr[j];
        j -= gap;
      }
      arr[j + gap] = key;
    }
    gap = Math.floor(gap / 2);
  }

  return arr;
}
// Gap sequence [n/2, n/4, ..., 1]: O(n²) worst case
// Ciura gap sequence [701,301,132,57,23,10,4,1]: O(n^(4/3)) empirically
// Shell sort bridges the gap between O(n²) and O(n log n) sorts
```

**Q21. "Given the three algorithms, which would you choose if you couldn't use a library sort and had to implement from scratch in a high-stakes production environment?"**
A: Insertion sort, without hesitation — for four practical reasons:

**Correctness**: insertion sort is easy to implement correctly. The invariant (sorted prefix grows by one each step) is immediately verifiable. Bubble sort and selection sort have subtler off-by-one risks in their loop bounds.

**Performance**: insertion sort is O(n) on already-sorted and nearly-sorted data (the most common real-world case), which means it degrades gracefully when input structure exists. Selection sort is always O(n²). Bubble sort without the flag is always O(n²).

**Stability**: insertion sort is stable, which is the correct default — if stability isn't needed, that's fine; if it is needed, you haven't introduced a bug. Selection sort's instability has historically caused subtle bugs in production systems where multi-key sorts relied on stability.

**Memory model**: insertion sort's access pattern (sequential shifts in a sorted prefix) is cache-friendly. Modern CPUs' prefetchers handle sequential writes well. Bubble sort's adjacent swaps are also cache-friendly, but selection sort's random minimum-finding scan across unsorted regions is less predictable.

The one caveat: for truly adversarial inputs or large n in production, O(n²) is too slow — a library sort (timsort, introsort) is always the real answer. But if forced to implement from scratch: insertion sort.

## Problem 1 — Sort a Nearly-Sorted Array

### Problem
Given a "k-sorted" array where each element is at most k positions away from its correct sorted position, sort it efficiently.

```
Input: arr=[6, 5, 3, 2, 8, 10, 9], k=3
Output: [2, 3, 5, 6, 8, 9, 10]

Input: arr=[10, 9, 8, 7, 4, 70, 60, 50], k=4
Output: [4, 7, 8, 9, 10, 50, 60, 70]
```

### Pattern Recognition
This problem has two solutions: insertion sort (O(n × k)) for small k, and a min-heap of size k+1 (O(n log k)) for larger k. The problem directly tests whether you recognize insertion sort's natural advantage on nearly-sorted data.

### Key Insight
If each element is at most k positions from its correct position, then when insertion sort processes element at index i, it needs to shift at most k elements — the inner while loop runs at most k iterations. Total shifts ≤ n × k. For small k (constant or O(log n)), this is effectively O(n). For large k, a min-heap of size k+1 gives O(n log k) — see the heap sort guide for that approach.

### Approach
Use insertion sort as-is. The k-sortedness property automatically limits each element's inner loop to k iterations — no code change needed. The algorithm is the same; the performance guarantee comes from the input structure, not from algorithmic modification.

### Solution

```js
// Solution 1: Insertion Sort — O(n*k) time, O(1) space
// Natural choice when k is small (O(1) or O(log n))
function sortKSortedInsertion(arr, k) {
  // Standard insertion sort — k-sortedness automatically limits inner loop
  for (let i = 1; i < arr.length; i++) {
    const key = arr[i];
    let j = i - 1;

    // Inner loop runs at most k times because arr[i] is ≤ k positions from correct spot
    // If arr[j] > key and j >= i - k, we must shift; at j = i - k - 1, arr[j] ≤ key guaranteed
    while (j >= 0 && arr[j] > key) {
      arr[j + 1] = arr[j];
      j--;
      // In a k-sorted array, this loop body executes at most k times per outer iteration
    }

    arr[j + 1] = key;
  }
  return arr;
}

// Solution 2: Min-Heap of size k+1 — O(n log k) time, O(k) space
// Better when k is large (e.g., k = O(sqrt(n)) or larger)
function sortKSortedHeap(arr, k) {
  // Using a simple array-based min-heap (or use a library PriorityQueue)
  const heap = arr.slice(0, Math.min(k + 1, arr.length));
  buildMinHeap(heap);

  const result = [];
  for (let i = k + 1; i < arr.length; i++) {
    result.push(extractMin(heap));
    insertHeap(heap, arr[i]);
  }
  while (heap.length > 0) result.push(extractMin(heap));
  return result;
}
```

## Problem 2 — Sort by Parity (Stable Partition)

### Problem
Given an array of integers, rearrange it so all even numbers come before all odd numbers. Preserve the relative order of even numbers among themselves and odd numbers among themselves (stable partition).

```
Input: [3, 1, 2, 4, 7, 5, 6]
Output: [2, 4, 6, 3, 1, 7, 5]
```

### Pattern Recognition
Insertion sort's stability property — this is a stable partition problem. The goal is to sort by a binary key (even=0, odd=1) while preserving relative order within each group. Insertion sort with a custom comparator achieves this because it's stable: equal "key" elements (both even or both odd) are never reordered relative to each other.

### Key Insight
Treating even numbers as "smaller" (key=0) and odd as "larger" (key=1), insertion sort's stability guarantees that all elements with key=0 precede all elements with key=1, and within each group the original relative order is preserved. The inner loop shifts odd numbers right to make room for an even number — exactly the "bubble even numbers to the front" operation, performed stably.

### Approach
Insertion sort with comparator: "even < odd, equal parity = equal (don't swap)." Insertion sort's strict inequality in the shift condition (`arr[j] > key` where comparison is by parity) ensures equal-parity elements are never reordered.

### Solution

```js
function sortByParity(arr) {
  // Insertion sort with parity-based comparator
  // parity(x) = 0 for even, 1 for odd → even elements sort before odd elements
  const parity = (x) => x % 2 !== 0 ? 1 : 0;

  for (let i = 1; i < arr.length; i++) {
    const key = arr[i];
    const keyParity = parity(key);
    let j = i - 1;

    // Shift elements with HIGHER parity (odd, parity=1) past the current element (parity=0)
    // STRICT inequality: equal parity → do NOT shift → stable behavior preserved
    while (j >= 0 && parity(arr[j]) > keyParity) {
      arr[j + 1] = arr[j]; // shift odd element right to make room for even
      j--;
    }

    arr[j + 1] = key; // place even element in correct position
  }

  return arr;
}

// Alternative: two-pointer (unstable but O(n))
function sortByParityUnstable(arr) {
  let even = 0, odd = arr.length - 1;
  while (even < odd) {
    while (even < odd && arr[even] % 2 === 0) even++;
    while (even < odd && arr[odd] % 2 !== 0) odd--;
    if (even < odd) {
      [arr[even], arr[odd]] = [arr[odd], arr[even]];
      even++;
      odd--;
    }
  }
  return arr;
}
// Two-pointer: O(n) time, O(1) space, but NOT stable
```

## Problem 3 — Find the Minimum Number of Swaps to Sort an Array

### Problem
Given a permutation of integers from 1 to n, find the minimum number of swaps needed to sort it.

```
Input: arr=[4, 3, 2, 1]
Output: 2

Input: arr=[2, 3, 4, 1]
Output: 3
```

### Pattern Recognition
Selection sort's exact swap count — the minimum number of swaps to sort a permutation equals n minus the number of cycles in the permutation's cycle decomposition. Each cycle of length k requires k-1 swaps. This directly connects to selection sort's structure: selection sort performs swaps that follow the permutation cycles, and counting those swaps gives the minimum.

### Key Insight
Any permutation decomposes uniquely into disjoint cycles. A cycle of length 1 (fixed point) requires 0 swaps. A cycle of length k requires exactly k-1 swaps to sort it — each swap moves one element to its correct position. The minimum total swaps = sum over all cycles of (cycle_length - 1) = n - number_of_cycles.

Selection sort naturally performs these minimal swaps: in each pass, it finds the minimum of the unsorted region and places it correctly — this is exactly following the permutation cycle.

### Approach
Build a visited array. For each unvisited element, trace its cycle (follow element → its correct position → that element's correct position → ..., until you return to start). Each cycle of length k contributes k-1 swaps. Sum over all cycles.

### Solution

```js
function minSwapsToSort(arr) {
  const n = arr.length;
  // Create array of [value, originalIndex] pairs sorted by value
  // to determine where each element should go
  const sorted = arr.map((val, idx) => [val, idx]).sort((a, b) => a[0] - b[0]);

  // pos[i] = where element currently at correct position i is currently located
  // (which original index holds the element that should be at position i)
  const pos = new Array(n);
  for (let i = 0; i < n; i++) {
    pos[i] = sorted[i][1]; // the original index of the element that belongs at position i
  }

  const visited = new Array(n).fill(false);
  let swaps = 0;

  for (let i = 0; i < n; i++) {
    if (visited[i] || pos[i] === i) {
      // Already visited or already in correct position (cycle of length 1)
      visited[i] = true;
      continue;
    }

    // Trace the cycle starting at i
    let cycleLength = 0;
    let j = i;
    while (!visited[j]) {
      visited[j] = true;
      j = pos[j]; // follow the cycle
      cycleLength++;
    }

    // A cycle of length k requires k-1 swaps
    swaps += cycleLength - 1;
  }

  return swaps;
}

// Alternative: directly simulate selection sort and count swaps
function minSwapsSelectionSort(arr) {
  const a = [...arr]; // don't mutate input
  let swaps = 0;

  for (let i = 0; i < a.length - 1; i++) {
    let minIdx = i;
    for (let j = i + 1; j < a.length; j++) {
      if (a[j] < a[minIdx]) minIdx = j;
    }
    if (minIdx !== i) {
      [a[i], a[minIdx]] = [a[minIdx], a[i]];
      swaps++;
    }
  }

  return swaps;
}
// Selection sort version: O(n²) time (always), O(n) space for copy
// Cycle decomposition: O(n log n) for sort, O(n) for cycle tracing
```

### Follow-up Questions

- "Can you do it with fewer swaps using a different algorithm?" → No — n minus the number of cycles in the permutation is provably the theoretical minimum. Any algorithm that sorts by swaps cannot do fewer than this, regardless of what swaps it chooses.

## Problem 4 — Count Inversions in an Array

### Problem
Given an array, count the total number of inversions — pairs (i, j) where i < j but arr[i] > arr[j]. This directly measures how "unsorted" an array is and is the exact number of shifts insertion sort would perform.

```
Input: arr=[2, 4, 1, 3, 5]
Output: 3 (pairs: (2,1), (4,1), (4,3))

Input: arr=[5, 4, 3, 2, 1]
Output: 10 (every pair is an inversion: C(5,2)=10)
```

### Pattern Recognition
Two approaches: O(n²) brute force (exactly mimics insertion sort's shift count) and O(n log n) merge-sort-based counting. This problem directly connects insertion sort to the concept of inversions — showing that insertion sort's shift count is not arbitrary but precisely tracks the disorder in the input.

### Key Insight
The O(n²) approach is identical to insertion sort: for each element, count how many earlier elements are greater than it — this is exactly the number of shifts insertion sort would make to place this element. The sum over all elements equals the total inversions. The O(n log n) approach uses merge sort: when merging two sorted halves, every time an element from the right half is placed before elements from the left half, those left-half elements all form inversions with the right-half element.

### Approach
O(n²): for each pair (i, j) with i < j, check if arr[i] > arr[j]. Count matches. This is the "insertion sort shift count" computed explicitly.

O(n log n): modified merge sort. During the merge step, when the right element is smaller than a left element, add (leftArrayLength - leftPointer) to the inversion count — all remaining left elements form inversions with this right element.

### Solution

```js
// O(n²) — direct insertion sort simulation (exact shift count)
function countInversionsN2(arr) {
  let inversions = 0;
  for (let i = 1; i < arr.length; i++) {
    const key = arr[i];
    let j = i - 1;
    // Count how many elements insertion sort would shift past for arr[i]
    while (j >= 0 && arr[j] > key) {
      inversions++; // this shift eliminates one inversion
      j--;
    }
    // Note: we're COUNTING, not actually sorting
    // (don't modify arr — just count)
  }
  return inversions;
}
// This is insertion sort with the modification step replaced by a counter.
// Demonstrates: inversions == insertion sort shift count, exactly.

// Wait: the above modifies the array mentally but doesn't shift. But j just counts
// backwards from i-1, checking arr[j] > key. Let's be precise — we're not doing
// actual sorting, just counting how many arr[j] > arr[i] for j < i.

// Cleaner O(n²):
function countInversionsN2Clean(arr) {
  let inversions = 0;
  for (let i = 0; i < arr.length; i++) {
    for (let j = i + 1; j < arr.length; j++) {
      if (arr[i] > arr[j]) inversions++;
    }
  }
  return inversions;
}

// O(n log n) — merge sort based (counts during merge step)
function countInversionsNLogN(arr) {
  let totalInversions = 0;

  function mergeSort(arr) {
    if (arr.length <= 1) return arr;

    const mid = Math.floor(arr.length / 2);
    const left  = mergeSort(arr.slice(0, mid));
    const right = mergeSort(arr.slice(mid));

    return merge(left, right);
  }

  function merge(left, right) {
    const result = [];
    let i = 0, j = 0;

    while (i < left.length && j < right.length) {
      if (left[i] <= right[j]) {
        result.push(left[i++]);
        // No inversion: left[i] is in correct order relative to right[j]
      } else {
        result.push(right[j++]);
        // left[i] > right[j]: ALL remaining left elements > right[j]
        // Each forms an inversion with right[j]
        totalInversions += left.length - i;
      }
    }

    while (i < left.length) result.push(left[i++]);
    while (j < right.length) result.push(right[j++]);
    return result;
  }

  mergeSort([...arr]); // sort a copy; totalInversions accumulated as side effect
  return totalInversions;
}
```

```
    right = mergeSort([1,3,5]):
      left2 = mergeSort([1]) = [1]
      right2 = mergeSort([3,5]) → merge([3],[5]) = [3,5], 0 inversions.
      merge([1],[3,5]): 1≤3 → [1]. 3→[1,3]. 5→[1,3,5]. 0 inversions.
    merge([2,4],[1,3,5]):
      left[0]=2, right[0]=1: 2>1 → take right[0]=1. inversions += left.length-i = 2-0 = 2.
        result=[1], j=1
      left[0]=2, right[1]=3: 2≤3 → take left[0]=2. result=[1,2], i=1

      left[1]=4, right[2]=5: 4≤5 → take left[1]=4. result=[1,2,3,4], i=2
      take right[2]=5. result=[1,2,3,4,5].
    Total inversions: 0+0+0+2+1 = 3 ✓
```

### Complexity
- O(n²): time O(n²), space O(1).
- O(n log n): time O(n log n), space O(n) for merge sort auxiliary arrays.

### Edge Cases
- Already sorted: 0 inversions. Insertion sort O(n). ✓
- Reverse sorted n=k: C(k,2) = k(k-1)/2 inversions. Insertion sort O(k²). ✓
- All equal: 0 inversions (no strict `>` inversions). Insertion sort O(n). ✓
- Single element: 0 inversions. ✓

### Follow-up Questions
- "How does the inversion count relate to bubble sort?" → Bubble sort also eliminates exactly one inversion per swap (adjacent swaps eliminate one adjacent inversion each). So bubble sort's swap count also equals the number of inversions. However, insertion sort's shifts are cheaper than bubble sort's swaps (1 assignment vs. 3), which is why insertion sort is preferred despite both O(n²) algorithms taking the same number of "elimination steps."
- "Can you count inversions in O(n log n) without extra space?" → The merge sort approach requires O(n) auxiliary space for merging. An in-place merge sort exists but is very complex. A BIT (Binary Indexed Tree / Fenwick Tree) also counts inversions in O(n log n) time with O(n) space (useful when values are bounded integers, using coordinate compression).

## Problem 5 — Implement a Hybrid Sort (Insertion Sort as Base Case)

### Problem
Implement a hybrid merge sort that uses insertion sort for subarrays below a threshold size. This directly demonstrates when and why insertion sort is used in production hybrid algorithms.

```
Input: any array of comparable elements
Threshold: arrays of size ≤ THRESHOLD use insertion sort; larger use merge sort
Output: sorted array

Goal: outperform pure merge sort for typical inputs by avoiding merge sort's overhead on small subarrays.
```

### Pattern Recognition
This is the exact structure of timsort (Python), introsort (C++ STL), and Java's Arrays.sort. The insight: merge sort's O(n log n) is asymptotically better, but its recursive overhead (function calls, array allocations for merging) makes it slower than insertion sort for small n. A hybrid captures both advantages.

### Key Insight
For subarrays of size ≤ THRESHOLD, the constant factor of insertion sort beats merge sort's asymptotically-better but overhead-heavy algorithm. The threshold (typically 16–32 for integers) is the crossover point where insertion sort's actual running time becomes less than merge sort's. Above the threshold, merge sort's O(n log n) scaling wins.

### Approach
Recursive merge sort that checks subarray size before recursing: if size ≤ THRESHOLD, apply insertion sort directly on the subarray in-place. Otherwise, split, recurse on each half, and merge. The insertion-sorted subarrays feed into merge sort's merging phase exactly as leaf nodes would.

### Solution

```js
const THRESHOLD = 16; // experimentally tuned; adjust based on hardware

function hybridSort(arr, lo = 0, hi = arr.length - 1) {
  if (hi - lo < THRESHOLD) {
    // Subarray is small — insertion sort in-place
    insertionSortRange(arr, lo, hi);
    return;
  }

  const mid = Math.floor((lo + hi) / 2);
  hybridSort(arr, lo, mid);      // sort left half
  hybridSort(arr, mid + 1, hi);  // sort right half
  merge(arr, lo, mid, hi);       // merge two sorted halves
}

// Insertion sort operating on arr[lo..hi] in-place
function insertionSortRange(arr, lo, hi) {
  for (let i = lo + 1; i <= hi; i++) {
    const key = arr[i];
    let j = i - 1;
    while (j >= lo && arr[j] > key) {
      arr[j + 1] = arr[j];
      j--;
    }
    arr[j + 1] = key;
  }
}

// Standard merge of arr[lo..mid] and arr[mid+1..hi]
function merge(arr, lo, mid, hi) {
  const left  = arr.slice(lo, mid + 1);
  const right = arr.slice(mid + 1, hi + 1);
  let i = 0, j = 0, k = lo;

  while (i < left.length && j < right.length) {
    // Stable: left[i] <= right[j] → take from left (preserves relative order)
    if (left[i] <= right[j]) arr[k++] = left[i++];
    else arr[k++] = right[j++];
  }
  while (i < left.length) arr[k++] = left[i++];
  while (j < right.length) arr[k++] = right[j++];
}

// Usage:
function sortArray(arr) {
  hybridSort(arr);
  return arr;
}
```

### Complexity
- Worst case: O(n log n) — same as pure merge sort (insertion sort on leaves doesn't change the asymptotic merge sort complexity).
- Best case: O(n) if entire array ≤ THRESHOLD (single insertion sort call).
- Space: O(n) for merge step auxiliary arrays, O(log n) recursion stack (same as merge sort).
- Practical improvement: avoids ~log₂(THRESHOLD) levels of merge recursion and their associated overhead for small subarrays, reducing total constant factor by 20–30% for typical inputs.

### Edge Cases
- Empty array: `hi - lo = -1 < THRESHOLD` → insertionSortRange(arr, 0, -1): outer loop `i = lo+1 = 1 > hi = -1` never runs. Returns immediately. ✓
- Single element: same — insertionSortRange never executes its loop body. ✓
- All same elements: both insertion sort (strict `>` never triggers) and merge (takes left on tie) handle correctly — result is stable. ✓
- THRESHOLD=1: degrades to pure merge sort. THRESHOLD=n: degrades to pure insertion sort. Both are correct edge cases. ✓

### Follow-up Questions
- "How would you choose the optimal THRESHOLD?" → Empirically: benchmark both pure merge sort and pure insertion sort on your hardware for arrays of size 1..64 and find the crossover. Alternatively: since insertion sort's constant factor is roughly 10–30× faster per operation than merge sort's for modern CPUs (due to cache efficiency and no recursion), the crossover typically falls in the range 16–32.
- "How does timsort differ from this basic hybrid?" → Timsort adds two refinements: (1) it detects existing "runs" (already-sorted sequences, either ascending or descending) and uses them as the insertion-sorted base, adapting to nearly-sorted input more aggressively; (2) it uses a sophisticated merge order (merge stack with invariant) to ensure at most O(log n) merges happen at any stack level, improving cache behavior for large inputs. This basic hybrid is a simplified version that captures the core idea without these refinements.

## Common Bugs Checklist

Before submitting any elementary sort solution, verify:

1. **Bubble sort uses strict inequality `arr[j] > arr[j+1]` (not `>=`) in the swap condition?** — Using `>=` swaps equal elements, breaking stability. Two equal elements in their original order would be swapped on the first pass, reversing their positions. Stability requires that only strictly out-of-order pairs are swapped.

2. **Bubble sort inner loop bound is `n - 1 - pass` (shrinking each pass), not always `n - 1`?** — Without the shrinking bound, you re-compare already-sorted elements at the end of the array on every pass. This wastes O(n × pass) comparisons — making the algorithm effectively no better than the O(n²) baseline, and causing index-out-of-bounds if the outer loop and inner loop aren't coordinated.

3. **Selection sort swaps only when `minIdx !== i` (the minimum isn't already in place)?** — Unconditionally swapping `arr[i]` with `arr[minIdx]` when they're the same index is a no-op that's harmless for correctness but needlessly performs a self-swap. More importantly for stability: swapping even when `minIdx === i` can confuse implementations that track element identities. Always check before swapping.

4. **Insertion sort inner loop condition is `arr[j] > key` (strict, not `>=`) AND includes `j >= 0`?** — Using `>=` makes insertion sort unstable (equal elements are unnecessarily shifted, reversing their relative order). Missing the `j >= 0` bound causes an out-of-bounds read at `arr[-1]` — JavaScript returns `undefined`, and `undefined > key` is `false`, accidentally terminating the loop correctly but producing wrong results when the key should be placed at index 0 (the comparison evaluates false too early in some cases).

5. **Insertion sort assigns `arr[j + 1] = key` after the while loop (at `j + 1`, not `j`)?** — The while loop terminates with `j` pointing to the last element that was NOT shifted — either because `arr[j] <= key` or because `j < 0`. The correct insertion position is `j + 1` (one past the stopping point). Assigning at `j` places the key one position too far left, duplicating the element at `j` and losing the key.

6. **When sorting a subarray (e.g., in a hybrid sort), loop bounds use `lo` and `hi`, not `0` and `arr.length - 1`?** — Using hardcoded 0 and arr.length-1 when the sort is meant to operate only on arr[lo..hi] will overwrite elements outside the target range, corrupting the rest of the array. The inner while loop's stopping condition must also be `j >= lo`, not `j >= 0`.

7. **Selection sort's instability is accounted for when equal elements are present?** — If the problem requires stable output (preserving relative order of equal elements), selection sort is incorrect regardless of implementation. Its swap-with-front structure can move a later-occurring equal element before an earlier-occurring one. Don't use selection sort when stability is required.

8. **Bubble sort's `swapped` flag is reset to `false` at the START of each pass (inside the outer loop), not once before all passes?** — If the flag is declared outside the outer loop and set to true on any swap but never reset, the second pass will see `swapped = true` from the first pass and incorrectly continue even if no swaps occurred. The flag must be reset to `false` at the beginning of every pass.

9. **Binary insertion sort's binary search finds the leftmost valid position for stable behavior?** — For stability, equal elements should be placed to the right of existing equal elements (the new element is "after" the existing ones in the original order). The binary search stopping condition should be `arr[mid] <= key` → `lo = mid + 1` (place key after any equal elements) rather than `arr[mid] < key` (which would incorrectly place key before equal elements).

10. **Hybrid sort threshold applied correctly as `hi - lo < THRESHOLD` (subarray size check), not `hi < THRESHOLD` (absolute index check)?** — `hi < THRESHOLD` checks whether the right boundary is small, not whether the subarray is small. A subarray arr[100..110] has hi=110, so `hi < 16` is false and it would never use insertion sort — even though the subarray has only 10 elements. The correct check is `hi - lo + 1 <= THRESHOLD` (or equivalently `hi - lo < THRESHOLD`), measuring the subarray's length.

**Final Tip:** At the 5–7 YOE level, the interviewer doesn't expect you to implement bubble sort as a production sort — they expect you to know *exactly* when each of the three algorithms is the right choice and to articulate why. The three key talking points that separate senior from mid-level: (1) insertion sort is the default for small arrays and nearly-sorted data — it's what timsort, introsort, and Java's Arrays.sort all use as their base case; (2) selection sort is uniquely optimal only when physical swap cost dominates all other costs — a real but narrow hardware constraint; (3) bubble sort has essentially no production use case that insertion sort doesn't handle better. Demonstrating that you know the inversion count is the precise measure of insertion sort's work — and connecting it to the decision to use insertion sort on nearly-sorted data — is the clearest signal that you understand these algorithms at the mechanism level, not just the pseudocode level.
