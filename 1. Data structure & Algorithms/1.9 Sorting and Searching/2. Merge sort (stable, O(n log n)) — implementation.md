## Topic A: Merge Sort Core

### Section A1: The Algorithm

**Q1. What is merge sort's divide-and-conquer strategy, and what are its three phases?**

A: Merge sort decomposes the sorting problem recursively into three phases: **Divide** — split the array at the midpoint into two halves of roughly equal size; **Conquer** — recursively sort each half (the base case is a single element, which is trivially sorted); **Combine** — merge the two individually-sorted halves back into one sorted array. The crucial insight is that the *combine* step (merging two sorted arrays) is O(n) — linear in the size of the combined array. Since the recursion has O(log n) levels and each level performs O(n) total merge work across all calls at that level, the overall time is O(n log n). The merge step is the algorithmic heart: sorting is structurally trivial (split and recurse) while merging carries all the interesting work.

```
mergeSort([5,2,8,1,9,3]):
  Divide:   [5,2,8]        |        [1,9,3]
  Divide:   [5,2] | [8]    |    [1,9] | [3]
  Divide:   [5]|[2]|[8]   |   [1]|[9]|[3]
  Conquer:  trivially sorted (size 1)
  Combine:  [2,5]  [8]    |    [1,9]  [3]
  Combine:  [2,5,8]       |       [1,3,9]
  Combine:  [1,2,3,5,8,9]
```

**Q2. What is the merge operation, what invariant does it maintain, and why is it O(n)?**

A: The merge takes two sorted subarrays (say `left[0..m]` and `right[0..n]`) and produces one sorted output. It uses two pointers `i` and `j`, starting at the beginning of each half. At each step, compare `left[i]` and `right[j]` — place the smaller into the output and advance that pointer. Drain any remaining elements once one half is exhausted. The invariant: *at every step, the output prefix contains exactly the smallest elements from the combined pool, in sorted order, and every element in `left[i..]` and `right[j..]` is ≥ every element already placed.* O(n) follows because each of the n total elements is placed exactly once — two pointers each advance at most n/2 times, processing one element per step with no repetition.

```js
function merge(aux, arr, lo, mid, hi) {
  // aux[] holds the source; arr[] receives the merged result
  let i = lo, j = mid + 1;
  for (let k = lo; k <= hi; k++) {
    if      (i > mid)          arr[k] = aux[j++]; // left half exhausted
    else if (j > hi)           arr[k] = aux[i++]; // right half exhausted
    else if (aux[j] < aux[i])  arr[k] = aux[j++]; // right is strictly smaller
    else                       arr[k] = aux[i++]; // left ≤ right → take left (STABILITY)
  }
}
// Invariant maintained: arr[lo..k-1] contains the k-lo smallest elements from
// aux[lo..mid] ∪ aux[mid+1..hi], in sorted order.
```

**Q3. Why is merge sort stable, and what single character in the code enforces it?**

A: A sort is *stable* if elements with equal keys maintain their original relative order. In merge sort, when `aux[i] == aux[j]` (equal elements, one from each half), the code takes from the *left* half by using `aux[j] < aux[i]` (strict `<`) — on ties, the condition is false, so the left element `aux[i]` is taken. Since the left half contains elements that appeared at *earlier indices* in the original array, taking from the left on ties preserves their original order relative to equal elements in the right half. The single character enforcing stability: `<` (strict less-than) in the condition `aux[j] < aux[i]`. Changing to `<=` would take from the right on ties, reversing the order of equal elements and breaking stability. This is why "take from left on tie" is the canonical phrasing — it's both the implementation rule and the proof of stability.

```
Original: [3a, 1, 3b, 2]  (subscripts distinguish equal 3s; 3a appeared before 3b)

After splitting and sorting halves:
  left:  [1, 3a]
  right: [2, 3b]

Merge step at 3a vs 3b:
  aux[i]=3a, aux[j]=3b. aux[j] < aux[i]? 3b < 3a? No (equal). Take left: place 3a.
  Result: [..., 3a, 3b]  ← 3a still precedes 3b ✓

If using <=: 3b <= 3a? No. Same result here. But consider [3b, 1] vs [3a, 2]:
  aux[i]=1, aux[j]=3a. Take 1. aux[i]=3b, aux[j]=3a. 3a < 3b? Yes → take 3a.
  Result: [1, 3a, 2, 3b] — but originally 3b came BEFORE 3a if left was right-half. 
  The key: left half = earlier indices → always take left on ties.
```

**Q4. What is the recurrence relation for merge sort, and how does the Master theorem resolve it to O(n log n)?**

A: The recurrence is `T(n) = 2T(n/2) + O(n)` — two subproblems of half the size, plus O(n) work to merge. Applying the Master theorem with `a = 2`, `b = 2`, `f(n) = n`: the critical exponent is `log_b(a) = log_2(2) = 1`, so `n^(log_b a) = n^1 = Θ(n)`. Since `f(n) = Θ(n) = Θ(n^(log_b a))`, we are in Case 2: `T(n) = Θ(n log n)`. Intuitively: there are `log₂ n` levels of recursion, and at each level the total merge work across all calls at that level is exactly O(n) — every element is touched once per level. The O(n log n) bound is also tight — it equals the information-theoretic lower bound for comparison-based sorting (Ω(n log n)), meaning merge sort is asymptotically optimal.

```
Level 0 (root):  merge n elements             → O(n)
Level 1:         two merges of n/2 each        → O(n/2) + O(n/2) = O(n)
Level 2:         four merges of n/4 each       → 4×O(n/4) = O(n)
...
Level log₂n:     n merges of 1 element each    → n×O(1) = O(n)

Total: log₂n levels × O(n) per level = O(n log n) ✓
```

**Q5. What is the space complexity of merge sort, why does O(n) auxiliary space seem unavoidable, and what does bottom-up change?**

A: Standard merge sort requires O(n) auxiliary space for the temporary array used during merging, plus O(log n) space for the recursion call stack (top-down). The O(n) auxiliary is essentially unavoidable for efficient merging: in-place merging (without auxiliary array) can be done, but naive in-place merge is O(n²) (rotating elements), and sophisticated in-place merge achieving O(n) time is extremely complex to implement correctly. Bottom-up iterative merge sort eliminates the O(log n) stack space (no recursion), reducing total extra space to O(n) from the auxiliary array alone — an improvement over top-down's O(n + log n) = O(n) (same asymptotically but better constant). For linked lists specifically, the merge step needs no auxiliary array (pointers are rearranged in-place), and bottom-up merge sort achieves O(n log n) time and O(1) extra space — which is why merge sort is uniquely well-suited to linked lists (see Q14).

**Q6. How does top-down recursive merge sort work, and what are the implementation details to get right?**

A: The top-down implementation: a `sort(lo, hi)` function that splits at `mid = (lo + hi) >> 1`, recurses on `[lo, mid]` and `[mid+1, hi]`, then calls merge. The key implementation detail: use *one global auxiliary array* (allocated once before sorting begins, not in every merge call) to avoid O(n log n) memory allocations. Before each merge, copy the current subarray from `arr` to `aux`; then merge from `aux` back into `arr`. This single pre-allocation makes the merge amortized O(1) for array allocation overhead. The base case `if (hi <= lo) return` handles both single-element subarrays and empty subarrays.

```js
function mergeSort(arr) {
  const aux = arr.slice(); // one allocation of O(n) space

  function sort(lo, hi) {
    if (hi <= lo) return;              // base case: 0 or 1 element
    const mid = (lo + hi) >> 1;       // floor division, avoids overflow
    sort(lo, mid);                     // sort left half
    sort(mid + 1, hi);                 // sort right half
    // Optional optimization: skip merge if already in order
    if (arr[mid] <= arr[mid + 1]) return; // ← O(n) speedup for nearly-sorted input
    mergeStep(lo, mid, hi);            // combine sorted halves
  }

  function mergeStep(lo, mid, hi) {
    for (let k = lo; k <= hi; k++) aux[k] = arr[k]; // copy to aux
    let i = lo, j = mid + 1;
    for (let k = lo; k <= hi; k++) {
      if      (i > mid)          arr[k] = aux[j++];
      else if (j > hi)           arr[k] = aux[i++];
      else if (aux[j] < aux[i])  arr[k] = aux[j++];
      else                       arr[k] = aux[i++]; // ← <= comparison: stability
    }
  }

  sort(0, arr.length - 1);
  return arr;
}
```

**Q7. How does bottom-up iterative merge sort work, and what boundary conditions must be handled carefully?**

A: Bottom-up merge sort eliminates recursion entirely: start by treating every individual element as a sorted subarray of size 1, then repeatedly merge adjacent pairs, doubling the subarray size each pass. The outer loop iterates over sizes `1, 2, 4, 8, ...`; the inner loop processes non-overlapping adjacent pairs of that size. The critical boundary conditions: (1) the `mid` must be clamped to `n-1` (the right half may not exist if the array size isn't a power of 2); (2) the `hi` must also be clamped to `n-1`; (3) skip the merge if `mid >= hi` (no right half exists for this pair). These edge cases make bottom-up slightly more code than top-down but eliminate all function call overhead and the recursion stack.

```js
function mergeSortBottomUp(arr) {
  const n = arr.length;
  const aux = arr.slice(); // one allocation

  function mergeStep(lo, mid, hi) {
    for (let k = lo; k <= hi; k++) aux[k] = arr[k];
    let i = lo, j = mid + 1;
    for (let k = lo; k <= hi; k++) {
      if      (i > mid)         arr[k] = aux[j++];
      else if (j > hi)          arr[k] = aux[i++];
      else if (aux[j] < aux[i]) arr[k] = aux[j++];
      else                      arr[k] = aux[i++];
    }
  }

  for (let size = 1; size < n; size <<= 1) { // size: 1, 2, 4, 8, ...
    for (let lo = 0; lo < n; lo += size << 1) {
      const mid = Math.min(lo + size - 1,       n - 1); // clamp: left half may not be full
      const hi  = Math.min(lo + (size << 1) - 1, n - 1); // clamp: right half may not exist
      if (mid < hi) mergeStep(lo, mid, hi); // skip if no right half
    }
  }

  return arr;
}
// No recursion stack → O(n) space total (aux array only).
// Iterates log₂n passes × n/pass work = O(n log n) total. ✓
```

**Q8. What is the "skip merge" early-termination optimization, and why does it matter for nearly-sorted inputs?**

A: After sorting the left and right halves, check if `arr[mid] <= arr[mid + 1]` — if the last element of the left half is ≤ the first element of the right half, the combined array is *already sorted* and the merge can be skipped entirely. This is a constant-time check that saves O(n) merge work for that call. For already-sorted input, every level's merge is skipped → O(n) total. For nearly-sorted input with k inversions, this optimization significantly reduces work. It's a key component of Natural Merge Sort (Q10) and TimSort (Q11). The optimization preserves correctness because both halves are individually sorted, and if the boundary element condition holds, their concatenation is globally sorted.

**Q9. What is the "small subarray" optimization, and what does it reveal about merge sort's practical performance?**

A: Merge sort has higher constant factors than insertion sort for very small arrays due to function call overhead, auxiliary array copying, and pointer bookmarking. For subarrays smaller than a threshold (typically 7–32 elements), switching to insertion sort is faster in practice. The optimization: `if (hi - lo < CUTOFF) { insertionSort(arr, lo, hi); return; }`. This reveals an important truth: asymptotic complexity is not the whole story. O(n²) insertion sort beats O(n log n) merge sort for small n because the hidden constants dominate. TimSort (Q11) formalizes this: it uses insertion sort for all "runs" shorter than a minimum run length (32–64), achieving the best of both worlds.

### Section A2: Variants and Applications

**Q10. What is Natural Merge Sort, and when does it outperform standard merge sort?**

A: Natural Merge Sort detects *naturally occurring sorted runs* in the input instead of assuming each element is a sorted run of length 1. A run is a maximal ascending sequence (descending runs are reversed to ascending). The algorithm collects and merges runs rather than splitting into fixed halves. For random data, performance is similar to standard merge sort (average run length ~2, so similar number of passes). For nearly-sorted data, natural merge sort is dramatically faster: a nearly-sorted array of n elements with k runs takes O(n log k) time — O(n) when k = O(1) (almost sorted), vs O(n log n) for standard merge sort regardless of input order. Natural merge sort is the conceptual precursor to TimSort.

**Q11. What are TimSort's key innovations over standard merge sort, and why is it the default sort in Python and Java?**

A: TimSort (Python's `list.sort()`, Java's `Arrays.sort()` for objects) builds on natural merge sort with three key innovations: (1) **Minimum run size**: runs shorter than `MIN_RUN` (32–64) are extended using insertion sort — insertion sort is O(n²) but with tiny constants on small data, and the resulting runs are individually sorted before any merging begins; (2) **Run stack and balanced merging**: pending runs are pushed onto a stack; a merge is triggered when the stack violates the invariant `|run[i]| > |run[i+1]| + |run[i+2]|` (preventing O(n²) behavior from unbalanced runs) — this guarantees the number of active runs is O(log n); (3) **Galloping mode**: when one run is consistently winning many comparisons in a row (one side dominates), switch to exponential search + bulk-copy instead of element-by-element comparison, dramatically speeding up cases with large identical-run segments. TimSort achieves O(n) on already-sorted or reverse-sorted data and O(n log n) worst case, with excellent real-world performance on the partially-sorted data that commonly appears in practice.

**Q12. What is external merge sort, and why is merge sort specifically chosen for sorting data larger than RAM?**

A: External merge sort handles data sets too large to fit in memory, storing intermediate results on disk (or distributed storage). **Phase 1 — Run creation**: repeatedly read a memory-fitting chunk, sort it in memory (using any in-memory algorithm), and write the sorted chunk to disk. If data is N total and memory holds M elements, this produces ⌈N/M⌉ sorted runs on disk. **Phase 2 — K-way merge**: simultaneously merge all K runs using a min-heap of size K, reading one disk block per run at a time and writing merged output in streaming fashion. Total I/O: O(N/B × log_{M/B}(N/B)) block transfers (B = block size). Merge sort is uniquely suited because: (1) the merge step accesses each run sequentially — exactly the access pattern that disk I/O is efficient for (no random seeks); (2) quicksort requires random access for pivot swapping, which is catastrophically expensive on disk. Every major database engine (PostgreSQL, MySQL, Oracle) uses external merge sort as the foundation of its sort operator.

**Q13. What is K-way merge, and how does a min-heap implement it in O(N log K)?**

A: K-way merge combines K sorted sequences into one sorted output. Naive approach: merge sequences pairwise, log₂K rounds, O(N log K) total — same asymptotic but more sequential passes. Heap-based approach: initialize a min-heap with the first element from each of the K sequences (heap entry: (value, sequence index, element position)). Repeat: pop the minimum element, add it to the output, push the next element from that same sequence (if it exists). Invariant: *the heap always contains the current front element of each non-exhausted sequence; its minimum is the globally smallest unprocessed element.* Each of the N total elements is pushed and popped from the heap exactly once: O(log K) per operation × N elements = O(N log K). Heap size never exceeds K. This is exactly the pattern for Merge K Sorted Lists (LC 23), finding the smallest range across K sorted lists, and external merge sort's second phase.

**Q14. Why is merge sort preferred over quicksort for linked lists, and what implementation advantage does bottom-up give?**

A: Quicksort on linked lists suffers two structural weaknesses: (1) pivot selection — good pivot strategies (median-of-three, random) require random access (`O(n)` to reach an arbitrary node) rather than the `O(1)` random access arrays provide; (2) partitioning — swapping elements in a linked list requires pointer manipulation rather than index swapping, destroying the in-place advantage that makes quicksort fast on arrays. Merge sort, by contrast, has a natural linked-list implementation: splitting at the midpoint requires only a slow/fast pointer scan (`O(n)`), and merging two linked lists rearranges `next` pointers in `O(n)` with *zero auxiliary nodes* (just pointer updates). Bottom-up linked-list merge sort starts by merging adjacent single nodes, then adjacent pairs, etc. — it never needs to find the midpoint, needs no auxiliary storage, and uses O(1) space with O(log n) iterations. Result: O(n log n) time, O(1) space, O(1) extra nodes — uniquely optimal for linked lists.

**Q15. What is the "counting during merge" pattern, and what class of problems does it solve?**

A: The counting-during-merge pattern exploits the fact that during a merge, the relative order of elements between the left and right halves is known: when an element from the right half is placed before remaining elements of the left half, it means those remaining left elements are *all greater* than the right element. This global ordering insight — valid *only* because both halves are sorted — allows counting pairs satisfying cross-half conditions in O(n) per merge call, with O(n log n) total across the entire sort. The canonical application: **counting inversions** (pairs (i,j) where i < j but arr[i] > arr[j]) — when right element `r` is placed, all remaining left elements form inversions with `r`, so `count += (remaining left elements)`. Extended applications include counting pairs satisfying other monotone conditions (Reverse Pairs, Count of Range Sum). The pattern's power: a condition that would take O(n²) to check naively becomes O(n log n) because merge sort provides sorted sub-states that make counting exact and cheap.

## Topic B: The Merge Operation and Comparative Analysis

### Section B1: Merge Mechanics

**Q16. What are the two approaches to the auxiliary array in the merge step, and what are their trade-offs?**

A: **Copy-into-aux-then-merge-back** (standard): before merging `[lo..hi]`, copy `arr[lo..hi]` into `aux[lo..hi]`, then merge from `aux` back into `arr`. Advantage: simple two-pointer logic, `arr` holds the in-progress result, no risk of overwrites. Disadvantage: the copy step is O(hi-lo+1) — not avoidable but unavoidable for correctness anyway. **Alternate-buffer trick** (Sedgewick's optimization): instead of always treating `arr` as destination, alternate which array is the source and which is the destination at each recursion level. The bottom-most level copies from `arr` to `aux`; the next level merges from `aux` to `arr`; alternating up the call tree eliminates the copy step. Saves roughly half the total data movement (O(n log n) → O(n log n/2)), but requires careful bookkeeping of which array holds the "current" sorted state at each level. For practical interviews, the copy-then-merge approach is simpler and preferred.

**Q17. How does the two-pointer merge compare to the "rotate-to-merge" in-place approach?**

A: Standard two-pointer merge uses O(n) auxiliary and runs in O(n) time — the merge of size-n inputs takes exactly n steps. In-place merge without auxiliary: one classical approach is to find where the right half's first element should go in the left half, then rotate — but rotation itself is O(n), and must be repeated O(n) times total, giving O(n²) for a single merge of size n. Sophisticated in-place algorithms (Kronrod 1969, subsequently refined) achieve O(n) merging with O(1) extra space but are extremely complex (15+ pages of careful analysis). For interviews: if asked about O(1)-space merge sort, acknowledge the in-place merge exists but is impractical; mention that the standard approach uses O(n) auxiliary and that linked-list merge sort achieves O(1) space by restructuring pointers.

**Q18. What is the exact merge operation for linked lists, and how do dummy nodes simplify it?**

A: Merging two sorted linked lists rearranges `next` pointers with no new node allocation. Using a dummy head node eliminates special-casing the first merged node: `dummy.next` is the result head. Maintain a `curr` pointer starting at dummy; compare the current heads of both lists; attach the smaller to `curr.next`; advance `curr` and the selected list's head. When one list is exhausted, attach the other's remaining tail directly. Time: O(m+n) where m and n are list lengths. Space: O(1) — no auxiliary array, just pointer updates.

```js
function mergeLists(l1, l2) {
  const dummy = { val: 0, next: null };
  let curr = dummy;
  while (l1 && l2) {
    if (l1.val <= l2.val) { curr.next = l1; l1 = l1.next; }
    else                  { curr.next = l2; l2 = l2.next; }
    curr = curr.next;
  }
  curr.next = l1 ?? l2; // attach non-exhausted tail in O(1)
  return dummy.next;
}
// Stability: l1.val <= l2.val → takes from left on tie (l1 has earlier original indices) ✓
```

### Section B2: Comparative Analysis

**Q19. Compare merge sort to quicksort across every significant dimension.**

A:

| Dimension | Merge Sort | Quicksort |
|---|---|---|
| Time (worst) | O(n log n) — guaranteed | O(n²) — rare with randomization |
| Time (average) | O(n log n) | O(n log n) |
| Space | O(n) auxiliary | O(log n) stack (in-place) |
| Stability | Yes — takes left on tie | No — standard pivot swaps break stability |
| Cache behavior | Poor — non-local reads from two halves | Good — sequential partition traversal |
| Linked lists | Excellent — O(1) extra space | Poor — needs random access |
| External sort | Excellent — sequential disk access | Poor — random disk access |
| Nearly-sorted | Adaptive (with early-termination opt) | O(n²) without shuffle |
| Parallel | Highly parallelizable (independent halves) | Harder to parallelize (partition is sequential) |
| Constant factor | Higher (copying, pointer bookmarking) | Lower (in-place swaps) |

In practice, quicksort typically outperforms merge sort on random arrays of primitive types in RAM due to better cache behavior and lower constants. Merge sort wins when: stability is required; sorting linked lists; data exceeds RAM; the comparison function is expensive (fewer comparisons in merge sort's worst case isn't better, but merge sort's access patterns suit expensive comparisons better).

**Q20. Compare merge sort to heapsort — same O(n log n) worst case, different trade-offs.**

A: Both guarantee O(n log n) worst case. Heapsort uses O(1) extra space (in-place) vs merge sort's O(n) — a meaningful advantage when memory is constrained. However, heapsort has severe cache disadvantages: heap operations (sink-down) involve non-sequential memory accesses (parent → children at index 2i and 2i+1), causing cache misses on large arrays. Merge sort's sequential array traversal is cache-friendly. Additionally, heapsort is not stable, while merge sort is. In practice, heapsort is rarely used as a primary sort (it's often slower than quicksort despite the same asymptotic bound) but appears as a fallback in IntroSort (the algorithm behind C++'s `std::sort`): quicksort initially, but switch to heapsort if recursion depth exceeds O(log n) to guarantee the worst-case bound while avoiding O(n²) quicksort degradation.

**Q21. What is the comparison-sort lower bound, and how does O(n log n) achieve optimality?**

A: Any comparison-based sorting algorithm must make at least Ω(n log n) comparisons in the worst case. The information-theoretic proof: there are n! possible permutations of n elements, and each comparison eliminates at most half the remaining permutations (binary decision). A binary decision tree with n! leaves has height ≥ log₂(n!) = Ω(n log n) by Stirling's approximation. Merge sort achieves this bound exactly: each merge of m and n elements makes at most m+n-1 comparisons, and summing across all merges at each level gives Θ(n log n) comparisons total. Merge sort is not just O(n log n) — it is *comparison-optimal* (among comparison-based sorts). This optimality cannot be improved by any comparison-based algorithm, no matter how clever. Non-comparison-based sorts (radix sort, counting sort) evade this bound by exploiting the structure of keys.

**Q22. How does the "counting during merge" pattern count inversions exactly, and what is the precise invariant?**

A: An inversion is a pair `(i, j)` with `i < j` and `arr[i] > arr[j]`. During the merge of sorted left half `[lo..mid]` and right half `[mid+1..hi]`: when `aux[j]` (right element) is placed because `aux[j] < aux[i]` (left pointer at i), the left pointer's current index means elements `aux[i], aux[i+1], ..., aux[mid]` are ALL greater than `aux[j]` (since the left half is sorted). Each of these left elements formed an inversion with `aux[j]` in the *original, pre-sorted* arrangement. Invariant: *when element `aux[j]` (from the right half, original index somewhere in `[mid+1..hi]`) is placed before `aux[i..mid]`, add `mid - i + 1` to the inversion count.* This counts exactly because: (1) only cross-half inversions are counted (within-half inversions were counted during recursive calls); (2) both halves are sorted, so comparison of `aux[j]` with `aux[i]` determines its position relative to ALL remaining left elements simultaneously.

**Q23. How does the "modified condition during merge" extend counting to arbitrary cross-pair conditions?**

A: The counting-during-merge pattern generalizes beyond inversions to any condition on (left element, right element) pairs that is *monotone* in both pointers when both halves are sorted. For Reverse Pairs (nums[i] > 2 * nums[j] for i < j): after sorting both halves, use a two-pointer scan *before* the merge to count: advance a pointer `j` through the right half while `nums[i] > 2 * nums[j]`; when `j` stops, all elements `nums[mid+1..j-1]` form reverse pairs with `nums[i]`; add `j - (mid+1)` and advance `i`. Critically: **counting must happen before merging** — after the merge, the two halves are interleaved and the cross-half structure is destroyed. The general template: (1) sort left, (2) sort right, (3) count cross-half pairs using two-pointer in O(n), (4) merge to restore sorted order. Any condition `f(left[i], right[j])` that is monotone (if `f(i,j)` holds then `f(i',j)` holds for all i' > i) admits this O(n log n) treatment.

**Q24. What is the bottom-up approach to sorting a linked list, and how does it achieve O(1) space?**

A: Bottom-up linked list merge sort avoids finding the midpoint (which takes O(n) per recursive call in top-down). Instead: (1) count the list length n; (2) for size = 1, 2, 4, ..., up to n: scan the list, chopping off pairs of `size`-length sublists, merging each pair, and connecting the merged results. No auxiliary nodes are allocated — existing nodes are relinked. Space: O(1) (only a constant number of pointer variables, no recursion stack). The tricky part is cleanly severing exactly `size` nodes at a time and reconnecting the merged tail to the next pair's head. This requires tracking the `prev` node (to attach merged results) and carefully advancing through the list. Time: O(n log n) — log₂n passes of O(n) work each.

**Q25. State the merge operation's invariant, the stability invariant, and the counting invariant each in one sentence.**

A:
- **Merge invariant**: at any point during the merge, `arr[lo..k-1]` contains exactly the `k - lo` smallest elements from the union of both sorted halves, in sorted order, and no element in the remaining left or right portion is smaller than any element already placed.
- **Stability invariant**: when `left[i] == right[j]`, left element `left[i]` is placed before `right[j]` — because the left half contains elements from earlier original indices, this ensures equal elements preserve their relative arrival order throughout all merge levels.
- **Counting invariant**: when right element `right[j]` is placed before left elements `left[i..mid]` during merging (because `right[j] < left[i]`), the count `mid - i + 1` is exactly the number of cross-half inversions involving `right[j]`, because the sorted left half guarantees that `left[i] > right[j]` implies `left[i'], left[i+1], ..., left[mid]` all also > `right[j]`.

## Problem 1 — Sort an Array

### Problem

Given an array of integers `nums`, sort it in ascending order and return it. (Use merge sort; do not use built-in sort.)

```
Input:  nums = [5, 1, 1, 2, 0, 0]  → [0, 0, 1, 1, 2, 5]
Input:  nums = [5, 2, 3, 1]         → [1, 2, 3, 5]
```

### Pattern Recognition
Canonical merge sort — show both top-down recursive and bottom-up iterative implementations. Top-down is more readable; bottom-up avoids recursion stack overflow for very large arrays.

### Key Insight
One pre-allocated auxiliary array eliminates O(n log n) allocation overhead (no new array per merge call). The stability-enforcing `<=` comparison in the merge step takes from the left on ties, preserving original element order. The early-termination check `arr[mid] <= arr[mid+1]` turns already-sorted inputs from O(n log n) to O(n).

### Solution

```js
// Top-down recursive merge sort — O(n log n) time, O(n) space
function sortArray(nums) {
  const n = nums.length;
  const aux = nums.slice(); // one auxiliary array allocation

  function sort(lo, hi) {
    if (hi <= lo) return; // base case: single element or empty
    const mid = (lo + hi) >> 1;
    sort(lo, mid);       // sort left half
    sort(mid + 1, hi);   // sort right half
    if (nums[mid] <= nums[mid + 1]) return; // already merged: skip
    merge(lo, mid, hi);
  }

  function merge(lo, mid, hi) {
    for (let k = lo; k <= hi; k++) aux[k] = nums[k]; // copy to aux

    let i = lo, j = mid + 1;
    for (let k = lo; k <= hi; k++) {
      if      (i > mid)           nums[k] = aux[j++]; // left exhausted
      else if (j > hi)            nums[k] = aux[i++]; // right exhausted
      else if (aux[j] < aux[i])   nums[k] = aux[j++]; // right strictly smaller
      else                        nums[k] = aux[i++]; // left ≤ right → stability
    }
  }

  sort(0, n - 1);
  return nums;
}

// Bottom-up iterative merge sort — same O(n log n), O(n); no recursion stack
function sortArrayBottomUp(nums) {
  const n = nums.length;
  const aux = nums.slice();

  function merge(lo, mid, hi) {
    for (let k = lo; k <= hi; k++) aux[k] = nums[k];
    let i = lo, j = mid + 1;
    for (let k = lo; k <= hi; k++) {
      if      (i > mid)          nums[k] = aux[j++];
      else if (j > hi)           nums[k] = aux[i++];
      else if (aux[j] < aux[i])  nums[k] = aux[j++];
      else                       nums[k] = aux[i++];
    }
  }

  for (let size = 1; size < n; size <<= 1) {         // pass size: 1, 2, 4, 8...
    for (let lo = 0; lo < n; lo += size << 1) {       // step by 2*size
      const mid = Math.min(lo + size - 1,       n - 1); // clamp left half end
      const hi  = Math.min(lo + (size << 1) - 1, n - 1); // clamp right half end
      if (mid < hi) merge(lo, mid, hi);               // only merge if right half exists
    }
  }

  return nums;
}
```

## Problem 2 — Count Inversions

### Problem

Given an array `nums`, count the number of inversions — pairs `(i, j)` where `i < j` and `nums[i] > nums[j]`.

```
Input:  nums = [2, 4, 1, 3, 5]  → 3   // (2,1), (4,1), (4,3)
Input:  nums = [5, 4, 3, 2, 1]  → 10  // every pair is an inversion: C(5,2) = 10
Input:  nums = [1, 2, 3, 4, 5]  → 0   // already sorted: no inversions
```

### Pattern Recognition
Merge sort with counting during the merge step — when a right-half element is placed before remaining left-half elements, all those remaining left elements form inversions with it. O(n log n) vs O(n²) naive brute force.

### Key Insight
During the merge of sorted halves, when element `aux[j]` (from right half) is taken before `aux[i..mid]` (remaining left elements), all of `aux[i], ..., aux[mid]` are > `aux[j]`. Each forms an inversion with `aux[j]` in the original un-merged order. Adding `mid - i + 1` counts all these inversions in O(1). This works because both halves are sorted: knowing `aux[i] > aux[j]` implies all subsequent left elements are also > `aux[j]`.

### Approach
Standard merge sort; add `count += (mid - i + 1)` exactly when a right-half element is taken (i.e., when `aux[j] < aux[i]`). Recursive calls handle within-half inversions; the merge step handles cross-half inversions. Each inversion is counted exactly once.

### Solution

```js
function countInversions(nums) {
  let inversions = 0;
  const aux = nums.slice();

  function sort(lo, hi) {
    if (hi <= lo) return;
    const mid = (lo + hi) >> 1;
    sort(lo, mid);       // count within-left inversions
    sort(mid + 1, hi);   // count within-right inversions
    merge(lo, mid, hi);  // count cross-half inversions
  }

  function merge(lo, mid, hi) {
    for (let k = lo; k <= hi; k++) aux[k] = nums[k];
    let i = lo, j = mid + 1;
    for (let k = lo; k <= hi; k++) {
      if      (i > mid)           nums[k] = aux[j++]; // left exhausted, no new inversions
      else if (j > hi)            nums[k] = aux[i++]; // right exhausted, no inversions
      else if (aux[j] < aux[i]) {
        // aux[j] goes before aux[i..mid]: those (mid-i+1) left elements are each > aux[j]
        inversions += (mid - i + 1); // ← count cross-half inversions here
        nums[k] = aux[j++];
      }
      else                        nums[k] = aux[i++]; // no inversion: left ≤ right
    }
  }

  sort(0, nums.length - 1);
  return inversions;
}
```

## Problem 3 — Sort List

### Problem

Given the head of a linked list, return the list sorted in ascending order. Must be O(n log n) and O(1) memory (not counting recursion).

```
Input: 4→2→1→3  → 1→2→3→4
Input: -1→5→3→4→0 → -1→0→3→4→5
```

### Pattern Recognition
Merge sort on a linked list — top-down (simpler code, O(log n) stack) or bottom-up (O(1) space, O(1) recursion depth). For the strict O(1) space requirement, bottom-up is necessary.

### Key Insight
Finding the midpoint uses slow/fast pointers: start `slow = head, fast = head.next`; advance slow by 1 and fast by 2 until fast reaches the end. Cut the list at `slow.next = null` to produce two independent halves. The linked-list merge requires only pointer reassignment — no auxiliary nodes needed, making it genuinely O(1) extra space per merge operation.

### Solution

```js
// Approach A: Top-down recursive — O(n log n), O(log n) stack space
function sortList_topDown(head) {
  if (!head || !head.next) return head; // base case: 0 or 1 nodes

  // Find middle: slow/fast pointer split
  let slow = head, fast = head.next;   // fast starts at head.next (not head)
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
  }
  const mid = slow.next;
  slow.next = null;                    // cut: left half is head..slow, right is mid..end

  const left  = sortList_topDown(head);
  const right = sortList_topDown(mid);
  return mergeLists(left, right);
}

// Approach B: Bottom-up iterative — O(n log n), O(1) space
function sortList(head) {
  if (!head || !head.next) return head;

  // Count list length
  let n = 0, curr = head;
  while (curr) { n++; curr = curr.next; }

  const dummy = { next: head };        // dummy head simplifies tail attachment

  for (let size = 1; size < n; size <<= 1) {
    let prev = dummy;
    curr = dummy.next;

    while (curr) {
      // Cut off 'size' nodes as the left half
      const left = curr;
      let  right = cut(curr, size);    // right = start of right half; left has 'size' nodes
      curr = cut(right, size);         // curr = start of next pair; right has 'size' nodes

      // Merge left and right; attach merged result after prev
      prev.next = mergeLists(left, right);

      // Advance prev to the tail of the merged segment
      while (prev.next) prev = prev.next;
    }
  }

  return dummy.next;
}

// Helper: cut the first 'k' nodes from the list; return the head of the rest
function cut(head, k) {
  let curr = head;
  while (--k > 0 && curr) curr = curr.next;
  const rest = curr ? curr.next : null;
  if (curr) curr.next = null;           // sever the connection
  return rest;
}

function mergeLists(l1, l2) {
  const dummy = { next: null };
  let curr = dummy;
  while (l1 && l2) {
    if (l1.val <= l2.val) { curr.next = l1; l1 = l1.next; }
    else                  { curr.next = l2; l2 = l2.next; }
    curr = curr.next;
  }
  curr.next = l1 ?? l2;
  return dummy.next;
}
```

- Top-down: O(n log n) time, O(log n) space (recursion stack).
- Bottom-up: O(n log n) time, O(1) space (only pointer variables, no extra nodes).

### Edge Cases
- Empty list: `!head` → return null.
- Single node: `!head.next` → return head.
- Two nodes: slow/fast pointer — fast starts at head.next, immediately null → mid = head.next, slow.next = null. Correctly splits into two single nodes.

### Follow-up Questions
- "Why start fast at head.next instead of head?" — Starting fast at head.next ensures slow stops one node before the midpoint, allowing the split to leave the left half at most one node larger than the right (correct split). Starting fast at head would leave slow one node past the midpoint.
- "Bottom-up without counting length?" — Find length by traversal (one extra O(n) pass) before the size-doubling loop. Or: find the end-of-list in the cut helper (when cut returns null, you've reached the end of the current pass).

## Problem 4 — Merge K Sorted Lists

### Problem

Given `k` linked lists where each is sorted in ascending order, merge all into one sorted linked list and return it.

```
Input:  lists = [1→4→5, 1→3→4, 2→6]   → 1→1→2→3→4→4→5→6
Input:  lists = []                       → []
Input:  lists = [[]]                     → []
```

### Pattern Recognition
K-way merge using a min-heap — the canonical application of the K-way merge pattern (Q13). Each heap entry carries `(value, listIndex, nodePointer)` to enable O(1) retrieval of the next element from the same list.

### Key Insight
The min-heap maintains the invariant: its top is always the globally smallest unprocessed element across all K lists. Popping gives the next output element; pushing the popped node's successor maintains the invariant. Heap size ≤ K at all times, so each push/pop is O(log K). With N total elements, total time is O(N log K).

### Solution

```js
class MinHeap {
  constructor(cmp = (a, b) => a - b) { this.data = []; this.cmp = cmp; }
  size()  { return this.data.length; }
  top()   { return this.data[0]; }
  push(v) { this.data.push(v); this._up(this.data.length - 1); }
  pop()   {
    const top = this.data[0], last = this.data.pop();
    if (this.data.length) { this.data[0] = last; this._down(0); }
    return top;
  }
  _up(i) {
    while (i > 0) {
      const p = (i-1) >> 1;
      if (this.cmp(this.data[i], this.data[p]) < 0) {
        [this.data[i], this.data[p]] = [this.data[p], this.data[i]]; i = p;
      } else break;
    }
  }
  _down(i) {
    const n = this.data.length;
    while (true) {
      let s=i, l=2*i+1, r=2*i+2;
      if (l<n && this.cmp(this.data[l],this.data[s])<0) s=l;
      if (r<n && this.cmp(this.data[r],this.data[s])<0) s=r;
      if (s!==i) { [this.data[i],this.data[s]]=[this.data[s],this.data[i]]; i=s; }
      else break;
    }
  }
}

function mergeKLists(lists) {
  // Min-heap keyed on node value; entries = [value, listIndex, node]
  const heap = new MinHeap((a, b) => a[0] - b[0]);
  const dummy = { val: 0, next: null };
  let curr = dummy;

  // Initialize: push first node of each non-empty list
  for (let i = 0; i < lists.length; i++) {
    if (lists[i]) heap.push([lists[i].val, i, lists[i]]);
  }

  while (heap.size()) {
    const [, i, node] = heap.pop();  // extract minimum
    curr.next = node;                 // attach to output
    curr = curr.next;
    if (node.next) {
      heap.push([node.next.val, i, node.next]); // push successor from same list
    }
  }

  return dummy.next;
}
```

### Complexity
- Time: O(N log K) — N total nodes, each pushed/popped from a heap of size ≤ K.

### Edge Cases

- Lists with null entries: guard `if (lists[i])` on initialization.

- Lists of unequal length: when a list is exhausted (node.next is null after popping), nothing is pushed; the heap shrinks and continues.

### Follow-up Questions

- "K-way merge on arrays instead of linked lists?" — Same heap structure; entries = (value, arrayIndex, elementIndex). On pop at (i, j), push (arrays[i][j+1], i, j+1) if j+1 < arrays[i].length.

## Problem 5 — Reverse Pairs

### Problem

Given an integer array `nums`, return the number of *reverse pairs* — pairs `(i, j)` where `i < j` and `nums[i] > 2 * nums[j]`.

```
Input: nums = [1, 3, 2, 3, 1]   → 2   // (3,1) and (3,1): pairs at indices (1,4),(3,4)
Input: nums = [2, 4, 3, 5, 1]   → 3   // (2,1),(4,1),(3,1)
```

### Pattern Recognition
Modified merge sort — count cross-half pairs satisfying a condition during sorting. The key difference from counting inversions: the counting condition (`nums[i] > 2*nums[j]`) and the merge condition (`nums[i] <= nums[j]`) are *different*, so counting must happen **before** the merge step (while both halves are still separately sorted).

### Key Insight
Separate the counting from the merging: (1) after recursively sorting both halves, use two pointers to count cross-half reverse pairs in O(n) — advance a right pointer `j` while `nums[i] > 2*nums[j]`, add `j - (mid+1)` for each `i`; then advance `i` (the left pointer never needs to retreat because both pointers are monotone). (2) Then merge the two sorted halves. If we merged first, the two halves would be interleaved and the cross-half structure used for counting would be destroyed. The monotone two-pointer scan is valid because: when `nums[i] > 2*nums[j]` holds, it also holds for all `i' > i` in the left half (left half is sorted); so `j` only ever advances, giving O(n) total for the two-pointer scan.

### Solution

```js
function reversePairs(nums) {
  let count = 0;

  function sort(lo, hi) {
    if (lo >= hi) return;
    const mid = (lo + hi) >> 1;
    sort(lo, mid);
    sort(mid + 1, hi);
    countPairs(lo, mid, hi); // COUNT before merge (while halves are separately sorted)
    merge(lo, mid, hi);      // then merge
  }

  function countPairs(lo, mid, hi) {
    // Two-pointer: for each left[i], find how many right[j] satisfy nums[i] > 2*nums[j]
    let j = mid + 1;
    for (let i = lo; i <= mid; i++) {
      while (j <= hi && nums[i] > 2 * nums[j]) j++; // advance j as far as possible for this i
      count += j - (mid + 1); // all right[mid+1..j-1] satisfy the condition with left[i]
    }
    // Note: j never retreats — since left is sorted, if nums[i] > 2*nums[j] fails,
    // nums[i+1] >= nums[i] makes it fail for all j' <= j too. O(n) total.
  }

  function merge(lo, mid, hi) {
    const temp = [];
    let p = lo, q = mid + 1;
    while (p <= mid && q <= hi) {
      nums[p] <= nums[q] ? temp.push(nums[p++]) : temp.push(nums[q++]);
    }
    while (p <= mid) temp.push(nums[p++]);
    while (q <= hi)  temp.push(nums[q++]);
    for (let k = lo; k <= hi; k++) nums[k] = temp[k - lo];
  }

  sort(0, nums.length - 1);
  return count;
}
```

```

    sort(0,1): mid=0.
      sort(0,0), sort(1,1).
      countPairs(0,0,1): j=1. i=0: nums[0]=2 > 2*nums[1]=8? No. count+=0. count=0.
      merge(0,0,1): [2,4].
    sort(2,2).
    countPairs(0,1,2): j=2. i=0: 2>2*3=6? No. i=1: 4>6? No. count+=0.
    merge(0,1,2): [2,3,4].
  sort(3,4): mid=3.
    sort(3,3), sort(4,4).
    countPairs(3,3,4): j=4. i=3: 5>2*1=2? Yes → j=5>hi=4 → stop. count+=5-4=1. count=1.
    merge(3,3,4): [1,5].

  countPairs(0,2,4): left=[2,3,4], right=[1,5]. j=3.
    i=0(val=2): 2>2*1=2? No (not strictly greater). count+=j-3=0.
    i=1(val=3): 3>2? Yes→j=4. 3>2*5=10? No→stop. count+=4-3=1. count=2.
    i=2(val=4): 4>2? Yes (j already=4, advance: 4>10? No→stop). count+=4-3=1. count=3.
  merge(0,2,4): [1,2,3,4,5].

Return 3. ✓
```

### Complexity
- Time: O(n log n) — merge sort with O(n) two-pointer counting per level.
- Space: O(n) for the temp array in merge + O(log n) stack.

### Edge Cases
- All equal elements: `nums[i] > 2*nums[j]` is always false (equal elements: `x > 2x` is false for positive values) → 0 pairs.
- Sorted descending: maximum pairs. The two-pointer scan efficiently counts all cross-half pairs.

### Follow-up Questions
- "Count pairs where nums[i] > nums[j] + k for arbitrary k?" — Replace `2*nums[j]` with `nums[j] + k` in the condition. The monotone two-pointer structure still holds (since left is sorted, if `nums[i] > nums[j] + k`, then `nums[i+1] >= nums[i]` also satisfies it for the same j and beyond).
- "Why must counting happen before merging?" — After merging, the two-half structure is destroyed — we can no longer distinguish "left-half elements before right-half elements." The cross-half condition relies on both halves being intact and sorted.

## Problem 6 — Queue Reconstruction by Height

### Problem

You have people standing in a queue where `people[i] = [hi, ki]`: `hi` is their height, and `ki` is the number of people in front of them who have height ≥ `hi`. Reconstruct the queue.

```
Input:  people = [[7,0],[4,4],[7,1],[5,0],[6,1],[5,2]]
Output: [[5,0],[7,0],[5,2],[6,1],[4,4],[7,1]]
```

### Pattern Recognition
Greedy with stable sort property — sort taller people first (so that inserting shorter people later doesn't disturb shorter people's k-values), then insert each person at position k. The stable sort property ensures correct tie-breaking: among equal-height people, smaller k must be processed first.

### Key Insight
Sort by height descending; for equal heights, sort by k ascending. Then greedily insert each person at position `k` in the result. Why this works: when inserting person `[h, k]`, all previously inserted people are ≥ h in height (since we process tallest first). So inserting at position `k` places exactly k people of height ≥ h in front — satisfying the constraint. Shorter people inserted later don't affect the k-values of taller people already placed. The stability of the sort for equal heights ensures that `[h, 0]` is inserted before `[h, 1]`, so after insertion at their respective k-values, their relative order is correct.

### Solution

```js
function reconstructQueue(people) {
  // Sort: taller first; among equal height, smaller k first
  people.sort((a, b) => a[0] !== b[0] ? b[0] - a[0] : a[1] - b[1]);
  // Note: this sort is stable in modern JavaScript engines (ECMAScript 2019+)
  // guarantees stability, so equal-height people maintain their pre-sort relative order

  const result = [];
  for (const person of people) {
    result.splice(person[1], 0, person); // insert at index k
    // splice is O(n) per operation → O(n²) total for this greedy step
  }
  return result;
}
// Why stable sort matters: people with equal height processed in k-ascending order
// ensures that inserting [h,0] before [h,1] before [h,2]... gives correct final positions.
```

```

  [7,0],[7,1],[6,1],[5,0],[5,2],[4,4]

Insert one by one:
  [7,0]: result=[] → insert at 0: [[7,0]]
  [7,1]: insert at 1: [[7,0],[7,1]]
  [6,1]: insert at 1: [[7,0],[6,1],[7,1]]
  [5,0]: insert at 0: [[5,0],[7,0],[6,1],[7,1]]
  [5,2]: insert at 2: [[5,0],[7,0],[5,2],[6,1],[7,1]]
  [4,4]: insert at 4: [[5,0],[7,0],[5,2],[6,1],[4,4],[7,1]]

Verify [6,1]: people before [6,1] with height≥6: [7,0]. Count=1 ✓
Verify [5,2]: people before [5,2] with height≥5: [5,0],[7,0]. Count=2 ✓
Verify [4,4]: people before [4,4] with height≥4: [5,0],[7,0],[5,2],[6,1]. Count=4 ✓
```

### Complexity
- Time: O(n²) — O(n log n) sort + O(n²) for n splice operations each O(n).
- Space: O(n) — result array.

### Edge Cases
- All same height: sort by k ascending; insert at positions 0, 1, 2, ... → result is the sorted input. ✓
- One person: result is that person at position 0.

### Follow-up Questions
- "Can you do better than O(n²) for the insertion step?" — Use a balanced BST or a Fenwick tree to find the k-th empty position efficiently, achieving O(n log n) total. Conceptually: maintain a list of empty positions; for each person, find the k-th empty position and fill it. With a BIT/segment tree, each query is O(log n).
- "What if the sort were unstable?" — Among people with equal height, wrong k-ordering would cause incorrect insertions: inserting [h,1] before [h,0] would place [h,0] in position 0 of a list where [h,1] is already at position 1, shifting [h,0] to position 1 — but [h,0]'s k=0 requires 0 people of height ≥ h in front of it, which would be violated. Stable sort is essential.

## Problem 7 — Smallest Range Covering Elements from K Lists

### Problem

Given `k` sorted integer lists, return the smallest range `[a, b]` such that at least one number from each of the k lists is contained in `[a, b]`. The range `[a₁, b₁]` is smaller than `[a₂, b₂]` if `b₁ - a₁ < b₂ - a₂`, or if equal, `a₁ < a₂`.

```
Input:  nums = [[4,10,15,24,26],[0,9,12,20],[5,18,22,30]]
Output: [20, 24]   // 20 is from list 2, 24 from list 1, 22 from list 3; range = 4

Input:  nums = [[1,2,3],[1,2,3],[1,2,3]]
Output: [1, 1]
```

### Pattern Recognition
K-way merge with range tracking — extend the K-way merge pattern (Problem 4) by tracking the *current range* spanned by all K front elements. The minimum always anchors one end of the current range; the current maximum tracks the other.

### Key Insight
At any point during K-way merge, the heap contains exactly one element from each list. The current range spans from `heap.top()` (the global minimum among current elements) to `currentMax` (the maximum among current elements). To cover all K lists, at least one element from each must fall in `[min, max]` — which is exactly the heap's current state. Pop the minimum (shrink the range's left end), push the next element from the same list (potentially extend the right end), and track the best range seen. The range can only potentially improve when we pop (reduce the min) — so we stop when any list is exhausted (cannot cover all K lists).

### Solution

```js
function smallestRange(nums) {
  // Min-heap: [value, listIndex, elementIndex]
  const heap = new MinHeap((a, b) => a[0] - b[0]);
  let currentMax = -Infinity;
  let rangeStart = 0, rangeEnd = Infinity;

  // Initialize with first element from each list
  for (let i = 0; i < nums.length; i++) {
    heap.push([nums[i][0], i, 0]);
    currentMax = Math.max(currentMax, nums[i][0]);
  }

  while (heap.size() === nums.length) { // all K lists still represented
    const [minVal, listIdx, elemIdx] = heap.pop();

    // Current range [minVal, currentMax] covers all K lists
    if (currentMax - minVal < rangeEnd - rangeStart
        || (currentMax - minVal === rangeEnd - rangeStart && minVal < rangeStart)) {
      rangeStart = minVal;
      rangeEnd   = currentMax;
    }

    // Push next element from same list; if exhausted, loop ends (heap.size() < k)
    if (elemIdx + 1 < nums[listIdx].length) {
      const next = nums[listIdx][elemIdx + 1];
      heap.push([next, listIdx, elemIdx + 1]);
      currentMax = Math.max(currentMax, next);
    }
    // If list is exhausted, don't push; heap.size() drops below k → loop ends
  }

  return [rangeStart, rangeEnd];
}
```

## Quick Reference — Pattern Decision Tree

```
Is merge sort the right algorithmic choice?
│
├── NEED A STABLE SORT (equal elements must preserve original order)?
│   └── Merge sort ✓ (takes left on tie: aux[j] < aux[i], not <=)
│       Quicksort ✗ (pivot swaps destroy relative order of equal elements)
│
├── SORTING A LINKED LIST?
│   ├── O(log n) extra space acceptable → top-down merge sort
│   │     Find mid: slow=head, fast=head.next; slow/fast while fast&&fast.next
│   │     Cut: slow.next=null. Recurse. Merge (O(1) auxiliary — just pointers).
│   └── O(1) space required → bottom-up merge sort
│         Count length; merge adjacent pairs of size 1,2,4,8...
│         Only pointer variables — no auxiliary nodes or arrays.
│
├── DATA DOESN'T FIT IN RAM (external sorting)?
│   └── External merge sort ✓
│         Phase 1: sort memory-fitting chunks → write sorted runs to disk.
│         Phase 2: K-way merge runs with min-heap, reading one block per run.
│         Merge sort is natural: merge step = sequential disk access (no random I/O).
│
├── COUNT OR DETECT SOMETHING DURING SORTING?
│   ├── Inversions (i<j, arr[i]>arr[j]):
│   │     count += (mid - i + 1) when right element is taken in merge.
│   └── Cross-pair condition (arr[i] > f(arr[j]), i in left, j in right):
│         Separate counting (two-pointer scan) from merge.
│         Count BEFORE merge (after both halves sorted, before interleaving).
│         Both pointers monotone → O(n) per level → O(n log n) total.
│
├── MERGE K SORTED SEQUENCES?
│   └── K-way merge: min-heap of size K.
│         Entry = (value, sequenceIndex, position). O(N log K) total.
│         Pop minimum → push its successor from the same sequence.
│         Invariant: heap top = globally smallest unprocessed element.
│
├── FIND SMALLEST RANGE COVERING K LISTS?
│   └── K-way merge + track currentMax.
│         Range = [heap.top(), currentMax]. Update on each pop.
│         Stop when any list exhausted (can't cover all K lists).
│
└── OTHERWISE (random in-memory data, no stability requirement)?
    └── Quicksort (lower constants, better cache behavior)
        or Heapsort (O(1) space + O(n log n) worst case guarantee)
        or IntroSort (quicksort with heapsort fallback for worst-case safety)
```

## Common Bugs Checklist

Before submitting any merge sort solution, verify:

1. **Mid calculation causes infinite recursion: `(lo + hi) / 2` without floor?** — In JavaScript, `(lo + hi) / 2` can produce a non-integer (e.g., `3/2 = 1.5`). Array access with `1.5` converts to 1 in most contexts but the recursive bounds may not converge correctly. Always use `(lo + hi) >> 1` (arithmetic right shift = floor) or `Math.floor((lo + hi) / 2)`. Also: always use `lo + (hi - lo) / 2` in languages where integer overflow is possible (not JavaScript, but good practice for cross-language consistency).

2. **Stability broken: using `<` vs `<=` in merge comparison?** — For stability, the condition for taking the *right* element is `aux[j] < aux[i]` (strictly less than). If you write `aux[j] <= aux[i]`, equal elements from the right half are taken first — breaking stability by reversing the relative order of equal elements. The rule: take from the left on ties (`aux[j] < aux[i]` means right is taken only when strictly smaller, not equal).

3. **Forgetting to copy back from auxiliary to original array?** — The merge reads from `aux` and writes to `arr`. If you copy `arr` to `aux` correctly but then write the merged result back to `aux` (instead of `arr`), the original array is never updated. Always: copy `arr[lo..hi]` → `aux[lo..hi]`; merge from `aux` → `arr`.

4. **Bottom-up: mid or hi not clamped to n-1?** — If the array length is not a power of 2, the last "pair" of subarrays in a pass may not be full-sized. Without `Math.min(lo + size - 1, n - 1)` and `Math.min(lo + 2*size - 1, n - 1)`, `mid` and `hi` may exceed `n-1`, causing out-of-bounds array accesses. Always clamp both.

5. **Bottom-up: not guarding against merge when right half is empty?** — If `mid >= hi` after clamping (the right half doesn't exist), attempting to merge would access `aux[mid+1]` out of bounds. Guard: `if (mid < hi) mergeStep(lo, mid, hi)`.

6. **Linked list: starting fast pointer at head instead of head.next?** — If `fast = head`, then after the while loop, `slow` stops one position past the intended midpoint — the left half gets one extra node, and for a 2-node list, `slow` ends at the second node with `slow.next = null`, making the left half the entire list and causing infinite recursion. Always: `fast = head.next` so that for even-length lists, `slow` stops at the *last* node of the first half.

7. **Linked list: not severing the list at the midpoint?** — After finding `mid = slow.next`, you must set `slow.next = null` to cut the list in two. Without this, the left half still points to the right half — `sortList(head)` would process the entire original list, not just the left half, causing infinite recursion.

8. **Counting inversions: forgetting `mid - i + 1` (counting only 1 instead of many)?** — When right element `aux[j]` is taken before left elements `aux[i..mid]`, the count to add is `mid - i + 1` (the number of *remaining* left elements — not 1, not `mid - lo + 1`). Using `1` undercounts; using `mid - lo + 1` overcounts (includes already-placed left elements). The formula is `mid - i + 1` where `i` is the *current* left pointer position.

9. **Reverse pairs: counting after instead of before the merge?** — The cross-half pair counting must happen when both halves are separately sorted but *before* they are merged. After merging, the "left half" and "right half" no longer exist as distinct regions. Counting after the merge produces incorrect results because elements from the left half may now precede elements from the right half (they're interleaved), and the monotone two-pointer scan is no longer valid.

10. **K-way merge: not checking if next element exists before pushing?** — After popping `(val, listIdx, elemIdx)`, pushing the next element requires `elemIdx + 1 < lists[listIdx].length` (or `node.next !== null` for linked lists). Pushing an out-of-bounds access causes `undefined` to enter the heap, corrupting the heap invariant and producing incorrect output. Always guard: `if (node.next) heap.push(...)` or `if (elemIdx + 1 < nums[listIdx].length) heap.push(...)`.

**Final Tip:** At the 5 YOE level, the decisive signals for merge sort interviews are naming *three invariants precisely* rather than just describing the algorithm. The merge invariant: *"at step k of the merge, arr[lo..k-1] contains the k-lo smallest elements from the union of both sorted halves, in sorted order — established because we always take the globally smaller of the two front elements, and a sorted half guarantees that its front is the smallest remaining in that half."* The stability invariant: *"equal elements from the left half precede those from the right half in the output, because the merge condition takes from the left on ties (aux[j] < aux[i], strict less-than) — the single character `<` instead of `<=` is the complete proof of stability."* The counting invariant: *"when right-half element aux[j] is taken before left-half elements aux[i..mid], exactly `mid - i + 1` inversions are discovered — because the left half is sorted, so aux[i] > aux[j] implies aux[i+1] > aux[j], ..., aux[mid] > aux[j], and all cross-half inversions involving aux[j] are counted in O(1) total rather than individually."* And for linked lists: *"merge sort is preferred over quicksort because the merge step rearranges next-pointers in O(n) with O(1) auxiliary nodes (no array needed), while quicksort requires random access for pivot selection (O(n) per access on a linked list) and destroys merge sort's key advantage."*
