## Topic A: N-Queens Fundamentals

### Section A1: Core Mechanics

**Q1. What is the N-Queens problem, and why does placing one queen per row reduce the search space?**

A: The N-Queens problem asks: place n non-attacking queens on an n×n chessboard, where two queens attack each other if they share a row, column, or diagonal. Finding all valid placements is the canonical constraint satisfaction problem (CSP) in algorithms education. The critical structural insight enabling efficiency: since queens attack entire rows and columns, any valid solution must have exactly one queen per row and exactly one per column. Placing queens row by row — one per row, choosing only the column — enforces the row constraint automatically and reduces the search space from O(n²) choose n (placing n queens on n² cells) to O(n^n) (n choices per row for n rows), further pruned to far fewer with column and diagonal constraint checking. This row-by-row column assignment is the standard representation: `queens[row] = col` means row `row` has its queen in column `col`.

```
Naive placement: C(n², n) ≈ huge, then validate
Row-by-row assignment: n choices × n rows = n^n candidates before pruning
With constraint tracking: practical search tree much smaller
n=8: 92 solutions found among billions of potential permutations

Key reduction: 3 constraints
  Row: automatic (one per row by construction)
  Column: tracked with a set — O(1) check per candidate
  Diagonal: tracked with two sets — O(1) check per candidate
```

**Q2. What is backtracking, and why is it the natural algorithm for N-Queens?**

A: Backtracking is a systematic search strategy that builds a solution incrementally, abandoning a partial solution ("pruning") as soon as it is determined that the current partial state cannot lead to any valid complete solution, and retreating to try a different choice. It is natural for N-Queens because: (1) the problem has a recursive structure — placing a queen in row `row` reduces to placing queens in rows `row+1` through `n-1` with updated constraints; (2) constraints can be checked cheaply at each step, not just at the end (O(1) with the right data structures); (3) early pruning eliminates entire subtrees — detecting a column or diagonal conflict in row 2 avoids exploring all possible placements in rows 3 through n-1. The alternative — generating all permutations of columns and validating — is O(n! × n²) instead of the backtracking algorithm's O(n!) with O(1) per-step constraint checking.

**Q3. What three constraint structures does the standard N-Queens implementation track, and how are they maintained?**

A: Three sets track all constraint violations: **`cols`** — the set of column indices already occupied by placed queens; **`diag1`** — the set of `(row - col)` values for placed queens (primary diagonal \\ direction); **`diag2`** — the set of `(row + col)` values for placed queens (anti-diagonal / direction). When placing a queen at `(row, col)`: add `col` to `cols`, `row - col` to `diag1`, and `row + col` to `diag2`. A candidate placement at `(row, col)` is invalid if `col ∈ cols`, `row - col ∈ diag1`, or `row + col ∈ diag2` — three O(1) set lookups. When backtracking, remove those same values from all three sets — restoring the constraint state precisely. This three-set approach gives O(1) per-step constraint checking, far better than the O(row) scan of previously placed queens that naive implementations use.

```
Queen at (r, c):
  cols  ← c        (column r-c blocks same column for all future rows)
  diag1 ← r - c    (primary \\ diagonal: all cells where row-col = r-c)
  diag2 ← r + c    (anti   // diagonal: all cells where row+col = r+c)

Why r-c for primary diagonal?
  (2, 3) and (3, 4) share primary diagonal: 2-3 = -1 = 3-4 ✓
Why r+c for anti-diagonal?
  (2, 3) and (3, 2) share anti-diagonal: 2+3 = 5 = 3+2 ✓

Conflict check at (row, col): O(1) with sets
  invalid = cols.has(col) || diag1.has(row-col) || diag2.has(row+col)
```

**Q4. What does the choose-explore-unchoose template look like for N-Queens, and what is each step doing?**

A: The three-part template structures every backtracking call:

**Choose**: select a candidate column `col` for the current row. Check all three constraints — skip if any is violated. If no candidate passes, the function returns (pruning the entire subtree rooted here).

**Explore**: assume the placement is valid, record it (`queens[row] = col`), add to all three constraint sets, and recurse into `row + 1`. Any queens placed in deeper rows will see the updated constraint sets.

**Unchoose**: after the recursive call returns (whether it found a solution or was pruned), undo the placement: remove `col`, `row-col`, and `row+col` from the three sets. This restores the constraint state exactly, allowing the outer `for` loop to try the next candidate column. The unchoose step is the defining feature of backtracking — without it, constraint sets would accumulate invalid state and the algorithm would incorrectly prune valid placements in sibling branches.

```js
function backtrack(row) {
  if (row === n) { result.push(buildBoard(queens)); return; }

  for (let col = 0; col < n; col++) {
    // Check: is (row, col) conflict-free?
    if (cols.has(col) || diag1.has(row-col) || diag2.has(row+col)) continue;

    // CHOOSE: place queen at (row, col)
    queens[row] = col;
    cols.add(col); diag1.add(row-col); diag2.add(row+col);

    // EXPLORE: place queens in remaining rows
    backtrack(row + 1);

    // UNCHOOSE: remove queen — restore state for sibling branches
    queens[row] = -1;
    cols.delete(col); diag1.delete(row-col); diag2.delete(row+col);
  }
}
```

**Q5. What is the backtracking invariant, and what does it guarantee at every recursive call?**

A: The invariant: *when `backtrack(row)` is called, queens have been validly placed in rows 0 through row-1 — no two queens in those rows attack each other — and the constraint sets `cols`, `diag1`, `diag2` exactly reflect all conflicts imposed by those placed queens.* Establishing the invariant: at `backtrack(0)`, no queens have been placed and all sets are empty — trivially satisfied. Preserving the invariant: the choose step verifies the new placement doesn't conflict (checking against the current sets) and the unchoose step restores the sets to their pre-placement state, so when control returns to the caller the invariant holds again. The invariant guarantees two things: (1) every complete solution found (at `row == n`) is genuinely valid — all queens are non-attacking; (2) every pruned branch was correctly identified as leading only to invalid completions — the constraint check was sound.

**Q6. What is the diagonal conflict condition expressed mathematically, and why does it unify two diagonal directions?**

A: Two queens at `(r1, c1)` and `(r2, c2)` share a diagonal if and only if `|r1 - r2| == |c1 - c2|` — the absolute row difference equals the absolute column difference (they moved equal steps diagonally). This single condition decomposes into exactly two diagonal types: (1) `r1 - c1 == r2 - c2` (primary \\ diagonal — row-col is constant); (2) `r1 + c1 == r2 + c2` (anti / diagonal — row+col is constant). Proof: `|r1-r2| == |c1-c2|` ↔ `r1-r2 == ±(c1-c2)` ↔ `(r1-c1 == r2-c2)` OR `(r1+c1 == r2+c2)`. The two sets `diag1` and `diag2` store exactly these two values (row-col and row+col) for each placed queen, enabling O(1) conflict detection without iterating over all previously placed queens.

```
Mathematical equivalence:
  |r1-r2| == |c1-c2|
  ↔ (r1-c1 == r2-c2) [same \ diagonal]
    OR (r1+c1 == r2+c2) [same / diagonal]

Example: queens at (0,0) and (2,2):
  |0-2| = 2 = |0-2| → diagonal conflict ✓
  0-0 = 0 = 2-2 → same \ diagonal ✓

Example: queens at (0,1) and (2,3):
  |0-2| = 2 = |1-3| → diagonal conflict ✓
  0+1 = 1 ≠ 2+3 = 5 → NOT same / diagonal
  0-1 = -1 = 2-3 = -1 → same \ diagonal ✓
```

**Q7. What is the time complexity of N-Queens backtracking, and what makes it hard to express precisely?**

A: The worst-case time complexity is O(n!) — at the first row there are n candidate columns, at the second row at most n-1 (one column is blocked), and so on, giving at most n × (n-1) × ... × 1 = n! leaf nodes in the search tree. But this is a very loose upper bound: diagonal constraints eliminate many branches far more aggressively than column constraints alone. The actual number of nodes visited grows much slower than n!. For small n, it's feasible to compute exactly: n=8 visits about 15,720 nodes; n=13 visits about 2,900,000. No known closed-form expression captures the exact pruning benefit. Each node does O(1) work (three set operations), so total time ≈ O(n! × amortized_pruning_factor). In competitive programming, n ≤ 15 is typically solvable in under a second; n=20 requires the bit-manipulation optimization and is at the feasibility limit.

**Q8. What space does the N-Queens algorithm require, and what dominates at scale?**

A: Three space costs: (1) **Recursion stack**: O(n) — the stack is at most n levels deep (one per row), each holding O(1) local variables. (2) **Constraint structures**: O(n) — `cols`, `diag1`, `diag2` each hold at most n elements (one per placed queen). `diag1` values span `[-(n-1), n-1]`, `diag2` values span `[0, 2n-2]`. (3) **Output**: O(n! × n) — the number of solutions grows roughly as n!/exponential-factor, and each solution requires n strings of length n. For n=12, there are 14,200 solutions × 12 rows × 12 chars = ~2MB of output. The output space dominates for large n. The working space during search is O(n) regardless of n — only the output list grows with the number of solutions.

**Q9. What is the "early termination with constraint propagation" optimization, and when does it apply?**

A: Standard backtracking only checks constraints at the *current* row. An optimization called **forward checking** extends constraint propagation: after placing a queen in row `row`, scan all future rows `row+1` through `n-1` and count how many columns remain available in each. If any future row has **zero** available columns, the current placement cannot possibly lead to a complete solution — prune immediately without recursing deeper. This adds O(n²) work per node but can dramatically reduce the number of nodes explored. For N-Queens specifically, forward checking reduces the search tree by a significant factor at large n. The more advanced **arc consistency** propagation pre-prunes even more aggressively. In practice, the simple three-set approach (without forward checking) is the standard interview solution; forward checking is mentioned to demonstrate awareness of CSP optimization techniques.

### Section A2: Optimizations and Variants

**Q10. How does bit manipulation optimize N-Queens II, and what is the bitmask invariant?**

A: Instead of three `Set` objects, use three integers where each bit represents a column position. **`cols`**: bit `i` set means column `i` is occupied. **`diag1`**: bit `i` set means the primary diagonal passing through column `i` in the *current* row is blocked. **`diag2`**: bit `i` set means the anti-diagonal passing through column `i` in the current row is blocked. Key: when moving to the next row, `diag1` shifts *left* by 1 (the blocked column increases by 1 on the primary diagonal going downward) and `diag2` shifts *right* by 1 (the blocked column decreases by 1 on the anti-diagonal going downward). Available columns = `mask & ~(cols | diag1 | diag2)` where `mask = (1 << n) - 1` keeps only the n valid bits. Extracting and clearing the lowest set bit (`pos = available & -available; available &= available - 1`) processes each available position in O(1). Total evaluations per recursive call: O(1) vs O(n) set operations, with better cache performance.

```js
function totalNQueens(n) {
  const mask = (1 << n) - 1; // all n bits set
  let count = 0;

  // cols, diag1, diag2 are bitmasks of blocked columns at current row
  function backtrack(cols, diag1, diag2) {
    if (cols === mask) { count++; return; } // all n columns used → valid solution

    let available = mask & ~(cols | diag1 | diag2); // unblocked columns

    while (available) {
      const pos = available & (-available); // lowest set bit: picks one available column
      available &= available - 1;            // clear that bit for next iteration

      backtrack(
        cols  | pos,           // mark column as used
        (diag1 | pos) << 1,   // shift: primary diag moves right one col in next row
        (diag2 | pos) >> 1    // shift: anti-diag moves left one col in next row
      );
    }
  }

  backtrack(0, 0, 0);
  return count;
}

// Bitmask invariant: (diag1 | pos) << 1 at row r becomes the blocked positions at row r+1
// because a queen at (r, c) blocks (r+1, c+1) on the primary diagonal.
// Similarly, (diag2 | pos) >> 1 blocks (r+1, c-1) on the anti-diagonal.
```

**Q11. Why does `(cols === mask)` correctly detect a complete solution without tracking the current row?**

A: Each bit in `cols` represents one occupied column. Since we place exactly one queen per row (by construction — each recursive call handles exactly one row), `cols` has exactly as many set bits as rows processed. When `cols === mask` (all n bits set), all n columns have been used, which means exactly n queens have been placed across all n rows — a complete, valid placement. The row number is implicit: the recursion depth equals the row number. This also means `diag1` and `diag2` do not need to be masked when `cols === mask` — no further placement will use them. The bit trick is elegant precisely because it eliminates the `row` parameter entirely, reducing function arguments from 4 to 3.

**Q12. What is the N-Queens II problem, and how does counting solutions differ from enumerating them?**

A: N-Queens II (LC 52) asks for the count of distinct solutions, not their board configurations. The algorithmic change is trivial: replace `result.push(buildBoard(queens))` with `count++`. But this reveals a profound performance difference: the board-building step is O(n²) per solution and the output list requires O(S × n²) space where S is the number of solutions. Counting requires O(1) per solution and O(1) extra space (beyond the constraint structures). For n=14 (365,596 solutions) or n=15 (2,279,184 solutions), the difference between "count only" and "return all boards" is the difference between milliseconds and gigabytes. The bit manipulation approach (Q10) is particularly powerful for counting because it eliminates set overhead, making the per-node work almost purely arithmetic — no dynamic memory allocation during the search.

**Q13. How does symmetry reduce the N-Queens search space, and what is the implementation trade-off?**

A: The N-Queens problem has 8-fold symmetry: any valid placement can be rotated 90°, 180°, 270°, or reflected to produce other valid placements (for most n; n=1 is a degenerate case). This means roughly 1/8 of solutions are "fundamentally distinct" up to symmetry. The optimization: only explore `⌈n/2⌉` choices for the first row's column position, then generate the symmetric counterparts by reflection. In code, this halves the first-row branching factor. The trade-off: the mirroring/rotation logic adds implementation complexity (handling the case when the first queen is at the center column, which only has a left-right reflection, not a rotation pair), and the multiplier can be 1, 2, 4, or 8 depending on placement. For interview purposes, mention symmetry as an optimization but implement the straightforward approach — correctness without symmetry is easier to verify.

**Q14. What is the connection between N-Queens and the permutation generation problem?**

A: Since every valid N-Queens solution has exactly one queen per row AND one queen per column, the column assignments `queens[0], queens[1], ..., queens[n-1]` form a **permutation** of `{0, 1, ..., n-1}`. N-Queens is therefore a *constrained permutation generation* problem: generate all permutations of column indices such that no two queens share a diagonal. The `cols` set enforces the permutation property (no column reuse); the `diag1` and `diag2` sets enforce the diagonal constraints. The total number of permutations is n!, but the number of valid N-Queens solutions is much smaller (92 for n=8 out of 8! = 40320 permutations — about 0.23%). This connection is useful for understanding the search space: backtracking explores the permutation tree with diagonal pruning, effectively doing a DFS over permutations.

**Q15. How do you implement N-Queens iteratively without recursion, and when would you choose this?**

A: The iterative approach maintains an explicit stack of states: each state is (current row, current column index to try next). Simulate the recursion: push a state for row 0 starting at col 0; at each step, try columns in order for the current row — if a valid column is found, push a state for the next row; if no valid column exists, pop back (backtrack) and increment the column index in the popped state. In JavaScript, iterative implementation avoids call-stack depth limits (though n-deep recursion for n ≤ 20 is safe in practice). The iterative version is preferred when: (1) the call stack depth limit is genuinely a concern (rare for n ≤ 20); (2) you need to pause and resume the search (e.g., generators or lazy evaluation); (3) you want to produce solutions one at a time on demand rather than all at once. The recursive version is cleaner and preferred for interviews.

## Topic B: Backtracking Patterns and Generalizations

### Section B1: The Backtracking Template

**Q16. What is the general backtracking template, and how do N-Queens, Sudoku, and combinations each instantiate it?**

A: Every backtracking algorithm follows the same abstract structure:

```
backtrack(state):
  if terminal(state): record solution; return
  for each candidate c in candidates(state):
    if is_valid(state, c):
      choose(state, c)      // modify state
      backtrack(next(state, c))
      unchoose(state, c)    // restore state
```

N-Queens instantiation: state = row index; candidates = columns 0..n-1; valid = no column/diagonal conflict; choose = add to three sets; terminal = row == n.

Sudoku instantiation: state = next empty cell; candidates = digits 1-9; valid = not in same row/column/box; choose = fill cell; terminal = no empty cells.

Combination Sum instantiation: state = (current sum, start index); candidates = numbers from start index onward; valid = sum + candidate ≤ target; choose = add to current combination; terminal = sum == target.

The template is identical — what changes is the definition of "state," "candidates," "valid," "choose/unchoose," and "terminal." This is why understanding N-Queens deeply transfers directly to solving Sudoku, Word Search, Permutations, and other backtracking problems.

**Q17. What is the "pruning at the choice point" principle, and why is it the difference between O(n!) and O(n^n)?**

A: Pruning at the choice point means checking validity *before* recursing — as part of the candidate selection loop — not *after* all placements are complete (at the leaf). Without pruning at the choice point: try all n^n combinations of column assignments across n rows, then validate at the end — O(n^n × n) total. With pruning at the choice point (standard backtracking): immediately skip any column that violates a constraint, avoiding recursion into entire subtrees. For N-Queens, if row 0 places a queen at column 2, row 1 can't use columns 2, 1, or 3 (column conflict and two diagonal conflicts) — pruning 3 out of n candidates before any further work. Across the entire search tree, pruning eliminates the majority of candidates at every level, transforming the effective branching factor from n to roughly n/3 for typical rows, reducing the tree from O(n^n) to O(n!) and in practice much better.

```
Validation at leaf (wrong approach):
  Generate ALL n^n combinations → validate → O(n^n × n) total
  n=8: 8^8 = 16,777,216 × 8 = 134M operations

Pruning at choice point (backtracking):
  At each row, skip invalid columns immediately
  n=8: ~15,720 nodes actually explored
  Speedup: 134M / 15,720 ≈ 8,500× faster
```

**Q18. What is forward checking in constraint satisfaction, and how does it differ from standard N-Queens backtracking?**

A: Standard N-Queens backtracking checks only the *current* row for conflicts ("constraint checking"). Forward checking extends this: after placing a queen at `(row, col)`, scan all *future* rows and identify which columns are still available in each. If any future row has zero available columns, the current placement leads to a dead end — prune immediately without recursing. Implementation: after choosing `(row, col)`, for each future row `r > row`, compute its remaining available columns as `allCols - (cols ∪ {col that diag1 or diag2 would conflict at r})`. If any such count is 0, backtrack immediately. The trade-off: forward checking adds O(n²) work per node (scanning all future rows) but can dramatically reduce the number of nodes explored by detecting dead ends earlier. For N-Queens at n=15+, forward checking reduces the node count by 10-100×, outweighing its per-node overhead.

**Q19. What is the Minimum Remaining Values (MRV) heuristic, and why doesn't it apply to the row-by-row N-Queens formulation?**

A: MRV (also called the "fail-first" heuristic) selects the *variable* with the fewest remaining valid values next — the one most likely to cause failure quickly, so failures are detected earlier. In a pure CSP formulation of N-Queens where variable order is free (not forced to go row-by-row), MRV would choose the row with the fewest available columns to process next. This can reduce the search tree compared to fixed row-by-row ordering. However, in the standard row-by-row formulation, the variable order is fixed (row 0, then row 1, etc.), so MRV doesn't apply. MRV becomes valuable in 2D constraint problems like Sudoku (where cells can be processed in any order) — always fill the cell with fewest legal digit choices next, dramatically pruning dead branches before they grow large.

**Q20. What are the key structural differences between N-Queens and Sudoku as backtracking problems?**

A: Both are CSPs solved by backtracking, but they differ in three key ways:

**Variable structure**: N-Queens has n variables (rows), each with a domain of n column values. Sudoku has 81 variables (cells), each with a domain of 9 digits. The asymmetry: N-Queens assigns one variable per recursion level (one row at a time); Sudoku chooses which cell to fill next, and MRV heuristic determines the order.

**Constraint density**: N-Queens constraints only arise on diagonals (column constraints are handled structurally). Sudoku constraints are denser: each cell participates in 3 constraint groups (row, column, 3×3 box), and placing a digit blocks it in 20 other cells. This makes constraint propagation more powerful in Sudoku.

**Solution structure**: N-Queens may have multiple solutions (all sought); most Sudoku puzzles have exactly one solution (confirmed when found). For Sudoku, return immediately on the first valid solution.

**Box index computation** (Sudoku-specific): the 3×3 box containing cell `(r, c)` has index `(Math.floor(r/3)) × 3 + Math.floor(c/3)`, a formula that causes bugs when implemented incorrectly.

**Q21. How does the "choose-explore-unchoose" pattern differ between N-Queens and Word Search?**

A: In Word Search (LC 79), the "choose" step marks a cell as visited (e.g., swap the character with a sentinel or use a `visited[r][c]` boolean), the "explore" step recurses in 4 directions, and the "unchoose" step restores the cell's original character (or clears the visited flag). The critical difference from N-Queens: N-Queens maintains *global* constraint sets (cols, diag1, diag2) that persist across the entire search; Word Search maintains *local* state (which path cells are currently in use), restored precisely by the unchoose step. The visited marking in Word Search must happen *before* recursing (so deeper calls see the cell as used) and be restored *after* recursing (so sibling paths can reuse the cell). A bug unique to Word Search: marking visited *after* recursing means the recursive DFS can revisit the same cell, causing wrong answers or infinite recursion.

**Q22. What is the "count vs enumerate" distinction, and how does it affect implementation?**

A: Many backtracking problems have two variants: "find all solutions" (enumerate) and "count solutions." The implementation differs in exactly one way: whether to build and store the solution or just increment a counter. "Find all" requires: (1) a data structure to build the solution (e.g., `queens[]` array), (2) a method to serialize it (e.g., `buildBoard(queens)`), (3) appending to a result list. "Count only" requires: increment a counter when `row == n`. The count-only version is strictly faster in practice: no memory allocation per solution, no string building (O(n²) per solution), no list growth. For N-Queens: if n is large enough that the solution count is sought but the board configurations aren't needed, the bit manipulation counting approach (Q10) is optimal. The heuristic: when the problem says "return the number of distinct solutions," use count-only mode with bit manipulation; when it says "return all board configurations," use the full string-building version.

**Q23. How do you handle the "first valid solution only" variant of backtracking problems?**

A: Return a boolean from the backtracking function. If recursion finds a valid complete solution, return `true` immediately — propagate this `true` back up the call stack, stopping all sibling exploration. Implementation: `if (backtrack(row + 1)) return true;` after the explore step — if the sub-problem succeeds, don't unchoose, don't try more candidates, just return true. This converts the exhaustive search into a short-circuited search that exits at the first valid leaf. This pattern applies to: Sudoku Solver (find any valid completion), N-Queens existence check (does any valid placement exist?), Knight's Tour (find any valid path). Key invariant: the `unchoose` step is only executed if the recursive call returned `false` — if it returned `true`, we're done and cleanup is unnecessary.

```js
// First-solution-only pattern:
function backtrack(row) {
  if (row === n) return true;  // found a valid solution!

  for (let col = 0; col < n; col++) {
    if (isConflict(row, col)) continue;
    choose(row, col);
    if (backtrack(row + 1)) return true; // short-circuit on success
    unchoose(row, col);                  // only unchoose if we must try more
  }
  return false; // no valid placement in this row
}
```

**Q24. What is the "constraint-as-pruning" pattern, and how does it generalize across backtracking problems?**

A: The constraint-as-pruning pattern means: encode problem constraints as efficient data structures that support O(1) "is this candidate valid?" queries, maintained incrementally during search. For N-Queens: three sets (cols, diag1, diag2) — O(1) add/remove/check. For Sudoku: three boolean arrays (rowUsed[row][digit], colUsed[col][digit], boxUsed[box][digit]) — O(1) checks. For Combination Sum: a running sum — compare with target before recursing. For Generate Parentheses: two counters (open, close) — check against n and open before choosing. The pattern: identify the minimum-sufficient-state that determines future validity, encode it compactly, and update it incrementally rather than recomputing from scratch. The more compactly the constraint state is encoded, the faster each node is processed, and the better the pruning behavior.

**Q25. State the invariant, the pruning condition, and the termination condition for N-Queens in one sentence each.**

A:
- **Invariant**: when `backtrack(row)` is called, the queens in rows 0 through row-1 are all mutually non-attacking, and the sets `cols`, `diag1`, `diag2` exactly encode all column and diagonal positions blocked by those queens.
- **Pruning condition**: candidate column `col` in row `row` is skipped if `cols.has(col)` OR `diag1.has(row-col)` OR `diag2.has(row+col)` — any one constraint violation makes the current partial placement irrecoverable for all future column choices in rows row through n-1.
- **Termination condition**: when `row === n`, all n queens have been successfully placed with mutual non-attack guarantees (the invariant holds for all rows 0 through n-1), and the current state of the `queens[]` array represents one complete valid solution.

## Problem 1 — N-Queens

### Problem

The N-Queens puzzle places n queens on an n×n chessboard such that no two queens attack each other. Return all distinct solutions in any order. Each solution is represented as a list of strings, where `'Q'` marks a queen and `'.'` marks an empty cell.

```
Input:  n = 4
Output: [[".Q..", "...Q", "Q...", "..Q."],
         ["..Q.", "Q...", "...Q", ".Q.."]]

Input:  n = 1
Output: [["Q"]]
```

### Pattern Recognition
Classic backtracking with three constraint sets (cols, diag1, diag2). Place queens row by row; prune at each step using O(1) constraint checks; build board representations only at valid leaf nodes.

### Key Insight
The invariant — queens placed in rows 0..row-1 are mutually non-attacking — is maintained by the choose-explore-unchoose structure. The three sets encode the invariant compactly, giving O(1) per-step constraint checking. Building the board (`queens.map(...)`) is deferred until a complete solution is found to avoid O(n²) work on pruned branches.

### Solution

```js
function solveNQueens(n) {
  const result  = [];
  const queens  = new Array(n).fill(-1); // queens[row] = column of queen in that row
  const cols    = new Set();             // occupied columns
  const diag1   = new Set();             // occupied r-c diagonals (\)
  const diag2   = new Set();             // occupied r+c diagonals (/)

  function backtrack(row) {
    if (row === n) {
      // Build board only at leaf: O(n²) work, not incurred for pruned branches
      result.push(
        queens.map(col =>
          '.'.repeat(col) + 'Q' + '.'.repeat(n - col - 1)
        )
      );
      return;
    }

    for (let col = 0; col < n; col++) {
      // Pruning: skip if any constraint is violated
      if (cols.has(col) || diag1.has(row - col) || diag2.has(row + col)) continue;

      // CHOOSE
      queens[row] = col;
      cols.add(col);
      diag1.add(row - col);
      diag2.add(row + col);

      // EXPLORE
      backtrack(row + 1);

      // UNCHOOSE — restore state exactly
      queens[row] = -1;
      cols.delete(col);
      diag1.delete(row - col);
      diag2.delete(row + col);
    }
  }

  backtrack(0);
  return result;
}
```

## Problem 2 — N-Queens II

### Problem

Given n, return the number of distinct solutions to the N-Queens puzzle. Must be efficient for n up to 15.

```
Input: 1  → 1
Input: 4  → 2
Input: 8  → 92
Input: 14 → 365,596
```

### Pattern Recognition
Bit manipulation variant of N-Queens backtracking — replace three Sets with three integers (bitmasks). O(1) arithmetic operations instead of O(1) hash set operations; critically faster per-node due to no memory allocation and better cache behavior.

### Key Insight
The bitmask `cols` tracks occupied columns; `diag1` and `diag2` track which columns are blocked by diagonal constraints *at the current row*. Shifting `diag1` left by 1 and `diag2` right by 1 on each recursive call "moves" the diagonal constraints to the next row's column positions. When `cols === mask`, all n bits are set, meaning all n columns are used (one per row), confirming a complete valid solution.

### Solution

```js
function totalNQueens(n) {
  const mask = (1 << n) - 1; // n bits set: 0b1111...1
  let count = 0;

  // cols, diag1, diag2: bitmasks of blocked columns AT the current row
  function backtrack(cols, diag1, diag2) {
    if (cols === mask) { count++; return; } // all n columns filled → valid solution

    // Available column positions: not blocked by cols, diag1, or diag2
    let available = mask & ~(cols | diag1 | diag2);

    while (available) {
      const pos = available & (-available); // isolate lowest set bit (pick one column)
      available &= available - 1;            // remove that bit (iterate over all available)

      backtrack(
        cols  | pos,            // mark this column as used
        (diag1 | pos) << 1,    // diag1 shifts left: primary diagonal moves one col right
        (diag2 | pos) >> 1     // diag2 shifts right: anti-diagonal moves one col left
      );
    }
  }

  backtrack(0, 0, 0);
  return count;
}

// Why shift directions:
// Queen at (row, col): primary diag \\ blocks (row+1, col+1) → col+1 = shift left
// Queen at (row, col): anti diag  // blocks (row+1, col-1) → col-1 = shift right
```

## Problem 3 — Sudoku Solver

### Problem

Write a program to solve a Sudoku puzzle by filling empty cells (`'.'`). Each digit 1-9 must appear exactly once in each row, column, and 3×3 box.

```
Input:
  [["5","3",".",  ".","7",".",  ".",".","."],
   ["6",".",  ".",  "1","9","5",  ".",".","."],
   ...
   [".", "6",".",  ".",".",  ".",  "2","8","."]]
```

### Pattern Recognition
2D constraint satisfaction via backtracking: find the next empty cell, try digits 1-9, check three constraint groups (row, column, 3×3 box) in O(1) with boolean arrays, recurse. Return `true` on the first complete valid solution.

### Key Insight
Three boolean arrays — `rowUsed[row][digit]`, `colUsed[col][digit]`, `boxUsed[box][digit]` — give O(1) validity checks. Box index = `Math.floor(row/3) × 3 + Math.floor(col/3)`. MRV heuristic: always fill the cell with fewest valid digits next (not implemented here for simplicity, but powerful in practice). Return immediately on the first valid solution via `if (solve()) return true` — this short-circuits all backtracking as soon as one solution is found.

### Solution

```js
function solveSudoku(board) {
  // Initialize constraint arrays from given values
  const rowUsed = Array.from({length:9}, () => new Array(10).fill(false));
  const colUsed = Array.from({length:9}, () => new Array(10).fill(false));
  const boxUsed = Array.from({length:9}, () => new Array(10).fill(false));

  const boxIdx = (r, c) => Math.floor(r/3) * 3 + Math.floor(c/3);

  for (let r = 0; r < 9; r++)
    for (let c = 0; c < 9; c++)
      if (board[r][c] !== '.') {
        const d = parseInt(board[r][c]);
        rowUsed[r][d] = colUsed[c][d] = boxUsed[boxIdx(r,c)][d] = true;
      }

  function solve() {
    // Find next empty cell
    for (let r = 0; r < 9; r++) {
      for (let c = 0; c < 9; c++) {
        if (board[r][c] !== '.') continue;

        const box = boxIdx(r, c);
        for (let d = 1; d <= 9; d++) {
          if (rowUsed[r][d] || colUsed[c][d] || boxUsed[box][d]) continue;

          // CHOOSE: place digit d at (r, c)
          board[r][c] = String(d);
          rowUsed[r][d] = colUsed[c][d] = boxUsed[box][d] = true;

          // EXPLORE: if the rest solves, we're done
          if (solve()) return true; // short-circuit: propagate success upward

          // UNCHOOSE: restore state
          board[r][c] = '.';
          rowUsed[r][d] = colUsed[c][d] = boxUsed[box][d] = false;
        }

        return false; // no valid digit for this cell → backtrack
      }
    }
    return true; // all cells filled → solution found
  }

  solve();
}
```

## Problem 4 — Word Search

### Problem

Given an `m×n` grid of characters and a word, return `true` if the word exists in the grid, formed by sequentially adjacent (horizontally/vertically) cells, not reusing any cell.

```
board = [["A","B","C","E"],
         ["S","F","C","S"],
         ["A","D","E","E"]]
word = "ABCCED" → true  // A(0,0)→B(0,1)→C(0,2)→C(1,2)→E(2,2)→D(2,1)
word = "ABCB"   → false // can't reuse B
```

### Pattern Recognition
DFS backtracking on a grid — mark cells as visited before recursing, unmark after. Try all starting cells; at each step try 4 directions. The "visit/unvisit" is the N-Queens equivalent of choose/unchoose.

### Key Insight
Mark the current cell as visited (e.g., temporarily replace its character with `'#'`) *before* the recursive DFS calls, so deeper calls don't revisit it. Restore it *after* the recursive calls return — the unchoose step. The mark-before/unmark-after ordering is the most critical correctness requirement in Word Search; getting it backward causes cells to be used twice.

### Solution

```js
function exist(board, word) {
  const m = board.length, n = board[0].length;
  const dirs = [[1,0],[-1,0],[0,1],[0,-1]];

  function dfs(r, c, idx) {
    if (idx === word.length) return true; // all characters matched
    if (r < 0 || r >= m || c < 0 || c >= n) return false; // out of bounds
    if (board[r][c] !== word[idx]) return false; // character mismatch

    // CHOOSE: mark visited before recursing
    const temp = board[r][c];
    board[r][c] = '#'; // sentinel: prevent reuse in this path

    // EXPLORE: try all 4 neighbors for the next character
    let found = false;
    for (const [dr, dc] of dirs) {
      if (dfs(r + dr, c + dc, idx + 1)) { found = true; break; }
    }

    // UNCHOOSE: restore — allow other paths to use this cell
    board[r][c] = temp;

    return found;
  }

  // Try every cell as a starting point
  for (let r = 0; r < m; r++)
    for (let c = 0; c < n; c++)
      if (dfs(r, c, 0)) return true;

  return false;
}
```

## Problem 5 — Combination Sum

### Problem

Given distinct integers `candidates` and a `target`, return all unique combinations that sum to `target`. Numbers may be used multiple times. Order of combinations doesn't matter.

```
Input:  candidates=[2,3,6,7], target=7
Output: [[2,2,3],[7]]

Input:  candidates=[2,3], target=6
Output: [[2,2,2],[2,4? no], [3,3]]  // [[2,2,2],[3,3]]
```

### Pattern Recognition
Backtracking with a "start index" to avoid duplicates — only consider candidates at the current index or later (not earlier) to prevent reordering of the same combination. Prune when the running sum exceeds target.

### Key Insight
The `start` index parameter enforces a canonical ordering: once we decide not to use candidate `i`, we never revisit it. Since each candidate can be reused, we recurse with the *same* start index (not start+1). Sorting candidates first enables early pruning: if `candidates[start] > remaining`, all subsequent candidates are also too large — break immediately.

### Solution

```js
function combinationSum(candidates, target) {
  candidates.sort((a, b) => a - b); // sort for early pruning
  const result = [];

  function backtrack(start, current, remaining) {
    if (remaining === 0) { result.push([...current]); return; } // found a valid combination

    for (let i = start; i < candidates.length; i++) {
      if (candidates[i] > remaining) break; // pruning: sorted → all further candidates too large

      // CHOOSE: add candidates[i] to current combination
      current.push(candidates[i]);

      // EXPLORE: allow reuse (same i, not i+1)
      backtrack(i, current, remaining - candidates[i]);

      // UNCHOOSE: remove last element
      current.pop();
    }
  }

  backtrack(0, [], target);
  return result;
}
```

## Problem 6 — Generate Parentheses

### Problem

Given n pairs of parentheses, generate all combinations of well-formed parentheses.

```
Input: 3
Output: ["((()))","(()())","(())()","()(())","()()()"]

Input: 1
Output: ["()"]
```

### Pattern Recognition
Constrained backtracking — build the string character by character, maintaining `open` (count of `(` placed) and `close` (count of `)` placed). At each step, choose to add `(` or `)` only if it keeps the string potentially valid.

### Key Insight
A partial string is valid-so-far if: `open ≤ n` (can't exceed n open brackets) AND `close ≤ open` (can't close what hasn't been opened). At any point, if `open < n`: can add `(`; if `close < open`: can add `)`. No explicit "unchoose" needed — strings are immutable in JavaScript, so passing `current + '('` creates a new string, and backtracking is implicit (the parent's `current` is unchanged). This demonstrates that not all backtracking requires explicit state restoration.

### Solution

```js
function generateParenthesis(n) {
  const result = [];

  function backtrack(current, open, close) {
    if (current.length === 2 * n) { result.push(current); return; }

    if (open < n)     backtrack(current + '(', open + 1, close); // add '(' if not at limit
    if (close < open) backtrack(current + ')', open, close + 1); // add ')' only if valid
    // Constraints ensure current is always a valid prefix — no explicit pruning needed
  }

  backtrack('', 0, 0);
  return result;
}
```

```
  Add '(': backtrack('((', 2, 0):
    Can't add '(' (open=2=n).
    Add ')': backtrack('(()', 2, 1):
      Add ')': backtrack('(())', 2, 2): length=4=2n → push "(())". ✓
  Add ')': backtrack('()', 1, 1):
    Add '(': backtrack('()(', 2, 1):
      Add ')': backtrack('()()', 2, 2): push "()()". ✓

```

### Complexity
- Time: O(4^n / √n) — the nth Catalan number counts valid sequences; this is the exact number of leaf nodes.
- Space: O(n) for the recursion stack (depth 2n, but each level adds one character).

### Edge Cases
- n=0: return `[""]` (empty string is valid with 0 pairs — or `[]` depending on interpretation).
- n=1: return `["()"]`.
- Immutability: since `current + '('` creates a new string, no explicit unchoose is needed.

### Follow-up Questions
- "Generate all valid sequences of n pairs using mutable array?" — Use `push`/`pop` for explicit choose/unchoose on a character array, then `arr.join('')` at the leaf.
- "Count only (not enumerate)?" — Return the nth Catalan number: `C(n) = C(2n, n) / (n+1)`. No backtracking needed.

## Problem 7 — Palindrome Partitioning

### Problem

Given a string `s`, partition it into substrings such that every substring is a palindrome. Return all possible palindrome partitionings.

```
Input: "aab"  → [["a","a","b"],["aa","b"]]
Input: "a"    → [["a"]]
Input: "aba"  → [["a","b","a"],["aba"]]
```

### Pattern Recognition
Backtracking over all possible first-cut positions — at each step, choose a prefix of the remaining string that is a palindrome, add it to the current partition, and recurse on the suffix. Precompute palindrome status for all substrings with DP to avoid O(n) palindrome checks during backtracking.

### Key Insight
Precompute `isPalin[i][j]` = true if `s[i..j]` is a palindrome (DP in O(n²), O(n²) space). During backtracking, checking `isPalin[start][end]` is O(1) instead of O(n) per candidate, reducing total work from O(n × 2^n) to O(n² + 2^n). This precomputation-then-backtrack pattern is important: separate the "hard work" (palindrome checking) from the "search work" (backtracking), doing each once.

### Solution

```js
function partition(s) {
  const n = s.length;
  const result = [];

  // Precompute: isPalin[i][j] = true if s[i..j] is a palindrome
  const isPalin = Array.from({length: n}, () => new Array(n).fill(false));
  for (let i = n - 1; i >= 0; i--) {
    for (let j = i; j < n; j++) {
      if (s[i] === s[j] && (j - i <= 2 || isPalin[i+1][j-1])) {
        isPalin[i][j] = true;
      }
    }
  }

  function backtrack(start, current) {
    if (start === n) { result.push([...current]); return; } // full string partitioned

    for (let end = start; end < n; end++) {
      if (!isPalin[start][end]) continue; // prune: not a palindrome, skip

      // CHOOSE: take s[start..end] as the next partition
      current.push(s.substring(start, end + 1));

      // EXPLORE: partition the rest starting at end+1
      backtrack(end + 1, current);

      // UNCHOOSE
      current.pop();
    }
  }

  backtrack(0, []);
  return result;
}
```

### Dry Run

```

  i=1,j=1: 'a'='a' → true.
  i=1,j=2: 'a'≠'b' → false.
  i=0,j=0: 'a'='a' → true.
  i=0,j=1: 'a'='a', j-i=1≤2 → true.  // "aa" is palindrome
  i=0,j=2: 'a'≠'b' → false.

  end=0: isPalin[0][0]=true. push "a". backtrack(1, ["a"]):
    end=1: isPalin[1][1]=true. push "a". backtrack(2, ["a","a"]):
      end=2: isPalin[2][2]=true. push "b". backtrack(3, ["a","a","b"]):
        start=3=n → push ["a","a","b"]. ✓
      pop "b".
    pop "a".
    end=2: isPalin[1][2]=false. Skip.
  pop "a".
  end=1: isPalin[0][1]=true. push "aa". backtrack(2, ["aa"]):
    end=2: isPalin[2][2]=true. push "b". backtrack(3, ["aa","b"]):

```

### Complexity
- Time: O(n² + n × 2^n) — O(n²) for DP precomputation + O(n × 2^n) for backtracking (at most 2^n partitions, each requiring O(n) to copy).
- Space: O(n²) for the palindrome table; O(n) for the recursion stack and current partition.

### Edge Cases
- Single character: isPalin[0][0] = true; result = [["a"]].
- All same characters (e.g., "aaa"): all substrings are palindromes; exponential number of partitions.
- No palindrome prefix longer than 1 (impossible — single chars are always palindromes): backtracking takes all single-character cuts.

### Follow-up Questions
- "Minimum cuts to partition into all palindromes (LC 132)?" — DP: `minCut[i]` = min cuts for `s[0..i]`. `minCut[i] = min(minCut[j-1] + 1)` for all j where `s[j..i]` is a palindrome. O(n²) with the isPalin precomputation.
- "Return only the minimum-cut partition?" — Combine the DP from above with backtracking to reconstruct the actual partition.

## Quick Reference — Pattern Decision Tree

```
Is this a backtracking problem? Which template applies?
│
├── PLACE N NON-ATTACKING QUEENS (or similar n-in-n grid constraint)?
│   └── N-Queens backtracking:
│       - queens[row] = col assignment (one per row by construction)
│       - Three sets: cols, diag1 (r-c), diag2 (r+c) for O(1) conflict checks
│       - backtrack(row): try cols 0..n-1; skip conflicts; choose/explore/unchoose
│       - Termination: row == n → record solution
│       - Counting only: use bit manipulation (mask, cols, diag1, diag2 as integers)
│
├── FILL A GRID WITH CONSTRAINTS (Sudoku, Latin squares)?
│   └── CSP backtracking:
│       - Find next empty cell (or use MRV: cell with fewest valid values)
│       - Try each valid value; check row/col/box constraints in O(1) with arrays
│       - Return true on first valid solution (no need to enumerate all)
│       - Key: boxIdx = floor(r/3)*3 + floor(c/3)
│
├── SEARCH FOR A PATH/SEQUENCE IN A GRID (Word Search, Island shapes)?
│   └── DFS backtracking with visited marking:
│       - Mark cell as visited (sentinel char or visited[][]): BEFORE recursing
│       - Unmark after recursive call returns: AFTER recursing
│       - Try all valid neighbors matching next constraint
│       - Return true/false for existence; collect results for enumeration
│
├── BUILD A COMBINATION/SUBSET/PERMUTATION?
│   ├── Combinations (no reorder, each element used once):
│   │   backtrack(start, current): for i from start to n: add nums[i], recurse(i+1), pop
│   ├── Combinations with repetition:
│   │   backtrack(start, current): for i from start to n: add, recurse(i), pop
│   ├── Permutations (all orders, each element used once):
│   │   backtrack(current, used[]): for all i: skip if used[i]; mark, add, recurse, unmark, pop
│   └── Constrained generation (parentheses, valid sequences):
│       Track validity constraints (open, close counters); add only valid next choices
│
├── PARTITION A STRING WITH VALIDITY CHECK?
│   └── Palindrome/valid partitioning:
│       Precompute validity (isPalin[i][j]) in O(n²).
│       backtrack(start, current): try all end positions; if valid: add substr, recurse, pop
│
└── KEY INVARIANTS for all backtracking:
    1. State: what decisions have been made so far?
    2. Constraint: what makes the current partial state invalid?
    3. Termination: when is a complete valid solution found?
    4. Choose/Explore/Unchoose: modify state → recurse → restore state exactly
    5. Pruning: CHECK CONSTRAINTS BEFORE RECURSING (not at the leaf)
```

## Common Bugs Checklist

Before submitting any backtracking solution, verify:

1. **Forgetting the unchoose step entirely?** — Every `choose` (adding to a set, modifying an array, marking a cell) must have a corresponding `unchoose` (removing from the set, restoring the array, unmarking the cell) after the recursive call. Without unchoose, the constraint state bleeds into sibling branches: a column blocked by one path remains blocked when trying other columns in the same row, eliminating valid solutions. The invariant "constraint state reflects exactly the queens placed in the current path" is broken.

2. **Only tracking columns but not both diagonal types?** — A queen at `(r1, c1)` conflicts with `(r2, c2)` if `|r1-r2| == |c1-c2|`. This requires two separate diagonal checks: `(r1-c1 == r2-c2)` for the `\` diagonal AND `(r1+c1 == r2+c2)` for the `/` diagonal. Tracking only one type misses half the diagonal conflicts, producing invalid boards where queens on the untracked diagonal type attack each other silently.

3. **Word Search: marking cells as visited AFTER recursing instead of BEFORE?** — `board[r][c] = '#'` must happen before any `dfs(r+dr, c+dc, ...)` calls. If the mark happens after, the DFS can immediately revisit the same cell (since it's still its original character), allowing the word to "loop back" through cells already in the current path. This produces false positives (finding words by reusing cells).

4. **Not restoring the visited cell in Word Search?** — After `dfs` returns, `board[r][c] = temp` must restore the original character. Without this, the cell remains marked `'#'` for all subsequent starting-cell iterations and path explorations, causing false negatives (valid paths are pruned because the cell appears visited even when it isn't on the current path).

5. **Wrong box index formula in Sudoku?** — The 3×3 box containing `(r, c)` is `Math.floor(r/3) * 3 + Math.floor(c/3)`. Common bugs: using `r*3 + c` (wrong — gives 81 boxes instead of 9), or `Math.floor(r/3) + Math.floor(c/3)*3` (transposes rows and columns in box indexing). Verify: `(0,0)→0, (0,3)→1, (0,6)→2, (3,0)→3, (6,6)→8`.

6. **Incorrect termination: comparing `row === n-1` instead of `row === n`?** — The backtrack function represents "place a queen in row `row`" (future tense). After successfully placing in row `n-1` (0-indexed last row) and recursing, the call `backtrack(n)` is what detects the complete solution. Using `row === n-1` as the termination condition tries to record a solution when the last row's queen is being placed, before it has been fully verified as valid.

7. **Combination Sum: not using a `start` index, generating duplicate combinations?** — Without the `start` parameter, choosing `[2, 3]` and `[3, 2]` would both be generated (different orderings of the same combination). The `start` index ensures that each recursive call only considers candidates at index `start` or later, giving a canonical increasing-index ordering that avoids duplicate subsets.

8. **Palindrome Partitioning: checking palindromes on the fly (O(n) per check) instead of precomputing?** — For a string of length n, at most 2^(n-1) substrings are tried as partition candidates, and naive palindrome checking is O(n) each — total O(n × 2^n). With the `isPalin[i][j]` DP table precomputed in O(n²), each check becomes O(1) — a significant practical speedup for longer strings.

9. **N-Queens bit manipulation: wrong shift directions?** — A queen at column `c` in row `r` blocks column `c+1` in row `r+1` on the primary `\` diagonal (shift `diag1` LEFT by 1) and column `c-1` on the anti `/` diagonal (shift `diag2` RIGHT by 1). Swapping the shift directions makes the algorithm converge to wrong solutions silently: diagonals are detected as column-blocked positions but in the wrong column relative to the next row.

10. **Forgetting to AND with `mask` when computing available columns in bit manipulation?** — After `~(cols | diag1 | diag2)`, the result has all non-blocked bits set — but this includes bits above position `n-1` (since `~` inverts all 32 bits). Without `& mask` (where `mask = (1 << n) - 1`), the `while (available)` loop iterates over phantom "columns" beyond the board's width, exploring invalid placements that generate a wrong solution count.

---

**Final Tip:** At the 5 YOE level, the decisive signal for any backtracking problem is identifying and naming *three things* before writing a single line of code: the **state** (what partial decisions have been made), the **constraint check** (what makes a partial state immediately invalid, checked in O(1)), and the **termination condition** (what constitutes a complete valid solution). For N-Queens: *"state = queens placed in rows 0..row-1; constraint = cols.has(col) || diag1.has(row-col) || diag2.has(row+col), each O(1) via sets; termination = row == n."* The choose-explore-unchoose structure then follows mechanically from these three definitions. The key invariant: *"when backtrack(row) is called, the constraint sets precisely encode all conflicts from the queens in rows 0..row-1 — neither over-counting (stale old constraints) nor under-counting (missing current constraints) — so any column that passes the constraint check at this row is genuinely safe to place a queen."* The insight that separates N-Queens from O(n^n) brute force: *pruning happens at the choice point, not at the leaf* — detecting a column conflict in row 2 eliminates the entire (n-2)-deep subtree without exploring it, transforming O(n^n) to O(n!) and in practice far better.
