# DSA: Merge K Sorted Lists — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the "merge K sorted lists" problem, and why is it a generalization worth studying separately from merging two sorted lists?**
A: The problem asks: given K sorted linked lists (or arrays), produce a single sorted list containing all elements from all input lists. The two-list merge (a building block of merge sort) is a special case with K=2 — linear in the total number of elements and trivially solved with two pointers. The K-list generalization is non-trivial because a naive extension of the two-pointer technique requires choosing the minimum among K candidates at each step, and doing this naively (scanning all K list heads) costs O(K) per element — giving O(NK) total for N total elements across all lists, which degrades badly when K is large. The interesting engineering challenge is reducing that per-element decision cost from O(K) to O(log K), bringing the total to O(N log K). This reduction is what the heap and divide-and-conquer approaches achieve, and understanding when and why each applies is the core interview signal.

**Q2. What are the four main approaches to merging K sorted lists, and what are their complexities?**
A:

| Approach | Time | Space | Notes |
|---|---|---|---|
| Naive: merge one list at a time sequentially | O(NK) | O(1) extra | Simple but poor — each merge is O(current size + next list size), total grows quadratically |
| Min-heap (priority queue) | O(N log K) | O(K) | Optimal for general K; standard interview answer |
| Divide and conquer (tournament merge) | O(N log K) | O(log K) stack | Same time, less heap space; easier to reason about correctness |
| Brute force: collect all values, sort | O(N log N) | O(N) | Correct but ignores the sorted structure; N log N > N log K when K < N |

Where N = total number of elements across all K lists. For most interview settings, the **min-heap** approach is the expected answer; the **divide-and-conquer** approach is a strong alternative that demonstrates deeper pattern recognition (connecting to merge sort).

**Q3. Walk through the min-heap approach in detail — what exactly is stored in the heap, and why?**
A: The heap stores **one entry per active list** — specifically, a tuple of `(currentValue, listIndex, nodeReference)`. At any moment, each list contributes exactly its current "frontier" element (the smallest unprocessed element of that list) to the heap. The global minimum across all lists is always the heap's root — extractable in O(1). After extracting it, the next element from the same list is inserted into the heap (O(log K) cost), advancing that list's frontier. The `listIndex` and `nodeReference` are needed to know which list to advance after an extraction. Using node references directly (for linked lists) avoids re-traversal; using `listIndex` plus an external pointer array is the array-based equivalent.

```js
// Heap entry structure: [value, listIndex, nodeReference]
// Example: three lists at their starting positions
// List 0: 1 → 4 → 7
// List 1: 2 → 5 → 8
// List 2: 3 → 6 → 9

// Initial heap contents (before any extraction):
// [1, 0, node(1)]  ← minimum: will be extracted first
// [2, 1, node(2)]
// [3, 2, node(3)]

// After extracting [1, 0, node(1)]:
// Insert next from list 0: [4, 0, node(4)]
// Heap now: [2, 1, node(2)], [4, 0, node(4)], [3, 2, node(3)]
// → heapified to: [2, 1, node(2)], [4, 0, node(4)], [3, 2, node(3)]
```

**Q4. What is the time and space complexity of the min-heap approach, and how do you derive them rigorously?**
A: **Time:** Initialization inserts one element per list — K insertions at O(log K) each = O(K log K). Each of the N total elements is extracted exactly once (O(log K)) and potentially triggers one insertion (O(log K)) when the next element of the same list is added. Total extraction cost: N × O(log K) = O(N log K). Total: O(K log K + N log K) = O(N log K) since N ≥ K (there's at least one element per list; if some lists are empty they're skipped). **Space:** The heap holds at most K entries simultaneously — one per active list. O(K) extra space. The output list itself is O(N), but that's output space, not auxiliary space. This O(K) heap space is a meaningful advantage over the brute-force O(N) approach when K << N.

**Q5. What is the divide-and-conquer approach, and how does it achieve O(N log K) without a heap?**
A: The divide-and-conquer approach mirrors merge sort: split the K lists into two halves, recursively merge each half down to a single list, then merge the two resulting lists with the standard two-pointer O(N) merge. The recursion tree has O(log K) levels (halving K at each level), and at each level the total work is O(N) (every element is processed once per level across all merges at that level). Total: O(N log K).

```
K=8 lists → split into two groups of 4
  → each group of 4 splits into two groups of 2
    → each group of 2 splits into single lists (base case)
    → merge pairs of single lists: 4 two-way merges, O(N) total
  → merge pairs of two-list results: 2 four-way merges, O(N) total
→ merge the two eight-list results: 1 eight-way merge, O(N) total
Total levels: log₂(8) = 3. Total work: 3 × O(N) = O(N log K).
```

Space: O(log K) recursion stack. No heap or auxiliary array needed — all merging is done in-place on the linked list nodes (or with pointer rewiring for arrays).

**Q6. When should you choose the min-heap approach over divide-and-conquer, and vice versa?**
A: Both achieve O(N log K) time, so the choice depends on secondary factors:

- **Min-heap** is preferred when: the lists are provided as streams or iterators (elements arrive lazily, so you can't split them into halves upfront); the number of lists K is very large (heap handles arbitrary K cleanly with one entry per list); you need the output to be produced incrementally (each heap extraction yields the next output element in order, enabling streaming output).
- **Divide and conquer** is preferred when: all K lists are available upfront as a complete collection; you want to avoid the overhead of a heap data structure (especially in languages without a built-in priority queue); the recursive structure is more natural for the codebase (e.g., already using merge sort elsewhere). It also has a smaller constant factor in practice since the two-pointer merge is extremely cache-friendly.
- **Tie-breaking**: in interviews, the min-heap approach is usually expected first (it's the more "natural" generalization of the K-way selection problem). Offering divide-and-conquer as an alternative — and correctly identifying it as the same asymptotic complexity — is a strong signal of pattern recognition depth.

### Section 2: Implementation Details & Tricky Cases

**Q7. How do you handle the comparison of heap entries when two lists have equal-valued elements, to avoid a "TypeError" or incorrect ordering?**
A: In JavaScript (and most languages), comparing tuples or objects directly with `<` or `>` doesn't work as expected for objects. The heap comparator must compare by value first. If values are equal, using `listIndex` as a tie-breaker ensures a consistent ordering (required for a valid heap) even when values are identical across lists. Without a stable tie-breaker, equal-valued comparisons may behave non-deterministically depending on how the heap implementation handles ties.

```js
// Comparator for the min-heap: compare by value, break ties by listIndex
function compare(a, b) {
  if (a[0] !== b[0]) return a[0] - b[0]; // sort by value ascending
  return a[1] - b[1];                     // tie-break by list index (stable)
}

// In practice: when using a custom MinHeap class, this comparator
// is passed to the heapify and siftUp operations.
// When using JavaScript's lack of a built-in heap, implement a MinHeap:
class MinHeap {
  constructor(comparator = (a, b) => a - b) {
    this.heap = [];
    this.compare = comparator;
  }

  push(val) {
    this.heap.push(val);
    this._siftUp(this.heap.length - 1);
  }

  pop() {
    const top = this.heap[0];
    const last = this.heap.pop();
    if (this.heap.length > 0) {
      this.heap[0] = last;
      this._siftDown(0);
    }
    return top;
  }

  peek() { return this.heap[0]; }
  size() { return this.heap.length; }

  _siftUp(i) {
    while (i > 0) {
      const parent = Math.floor((i - 1) / 2);
      if (this.compare(this.heap[i], this.heap[parent]) < 0) {
        [this.heap[i], this.heap[parent]] = [this.heap[parent], this.heap[i]];
        i = parent;
      } else break;
    }
  }

  _siftDown(i) {
    const n = this.heap.length;
    while (true) {
      let smallest = i;
      const l = 2 * i + 1, r = 2 * i + 2;
      if (l < n && this.compare(this.heap[l], this.heap[smallest]) < 0) smallest = l;
      if (r < n && this.compare(this.heap[r], this.heap[smallest]) < 0) smallest = r;
      if (smallest === i) break;
      [this.heap[i], this.heap[smallest]] = [this.heap[smallest], this.heap[i]];
      i = smallest;
    }
  }
}
```

**Q8. How do you correctly skip null or empty lists during initialization, and what goes wrong if you don't?**
A: During initialization, each non-null, non-empty list head is inserted into the heap. If a null list reference or an empty list head is inserted, the heap will contain a null entry. When this null entry is later extracted and you attempt to access `node.val` or `node.next`, it throws a null-pointer exception. The guard is simple — check `if (lists[i] !== null)` before inserting — but it's easy to omit when focused on the main logic. Similarly, during the extraction loop, after extracting a node and advancing to `node.next`, check `if (node.next !== null)` before inserting the next node into the heap. The pattern: **never insert null into the heap**.

```js
// Initialization — skip null and empty lists
for (let i = 0; i < lists.length; i++) {
  if (lists[i] !== null) {           // guard: skip null list references
    heap.push([lists[i].val, i, lists[i]]);
  }
}

// During extraction — advance only if next exists
const [val, listIdx, node] = heap.pop(); // extract minimum
result.next = new ListNode(val);         // or: rewire node directly
if (node.next !== null) {               // guard: only insert if next exists
  heap.push([node.next.val, listIdx, node.next]);
}
```

**Q9. Should you create new ListNode instances for the output, or rewire the existing nodes' `next` pointers directly? What are the trade-offs?**
A: Both approaches produce a correct sorted linked list, but they differ in space usage and whether the input lists are mutated:

- **Rewiring existing nodes** (in-place): set `node.next = null` after extraction to detach from the original list, then link the extracted node directly into the output. Uses O(1) extra node space. Mutates the input lists (which may be unacceptable if the original lists need to be preserved). This is the standard approach for linked list problems where in-place pointer manipulation is expected.
- **Creating new nodes**: allocate a fresh `ListNode(val)` for each element. Uses O(N) extra node space. Leaves the original lists intact. Less idiomatic for linked-list problems but safer if the caller needs the original lists afterward.

In an interview, rewiring is preferred — it demonstrates understanding of linked list pointer manipulation and avoids unnecessary allocation. Always mention "this mutates the input lists" when rewiring, and ask whether that's acceptable.

```js
// Rewiring approach (preferred in interviews):
const dummy = new ListNode(0);
let current = dummy;

while (heap.size() > 0) {
  const [val, listIdx, node] = heap.pop();
  current.next = node;          // rewire: attach the existing node
  current = current.next;
  if (node.next !== null) {
    heap.push([node.next.val, listIdx, node.next]);
  }
  current.next = null;          // detach: sever the old next pointer
}
return dummy.next;
```

**Q10. What is the "dummy head" (sentinel node) pattern and why is it useful here?**
A: The dummy head is a `ListNode` with an arbitrary value (conventionally 0 or -1) that serves as the placeholder start of the result list. Without it, the first node added to the result requires special-casing (the result head must be set to the first extracted node, and all subsequent nodes are appended via `current.next`). With the dummy head, every node is appended uniformly via `current.next = node` and `current = current.next` — no special case for the first element. At the end, `dummy.next` is the true head of the result list (skipping the placeholder). This pattern appears in virtually every linked list construction problem and should be the automatic first step.

```js
const dummy = new ListNode(0); // sentinel; dummy.val doesn't matter
let current = dummy;

// Every node appended uniformly, no special-casing:
current.next = extractedNode;
current = current.next;

return dummy.next; // skip the sentinel, return the real head
```

**Q11. How does the divide-and-conquer implementation avoid the O(NK) pitfall of naive sequential merging?**
A: Naive sequential merging processes lists one at a time: merge list 0 and list 1 (O(N/K × 2) work), then merge the result with list 2 (O(N/K × 3) work), and so on. The total work is O(N/K × (2 + 3 + ... + K)) = O(N/K × K²/2) = O(NK) — quadratic in K. Divide-and-conquer avoids this by always merging lists of approximately equal size. At each recursion level, every element participates in exactly one merge, so each level costs O(N) total. With O(log K) levels, the total is O(N log K). The key insight: equal-size merging prevents any single element from being processed many more times than others, which is exactly what unbalanced sequential merging causes.

```
Sequential (bad):        Divide and conquer (good):
L1+L2 = result1  O(2n)  L1+L2 → A  O(n)     Level 1: O(4n) total
result1+L3 = r2  O(3n)  L3+L4 → B  O(n)
result2+L4 = r3  O(4n)  L5+L6 → C  O(n)     Level 2: O(4n) total
...                      L7+L8 → D  O(n)
Total: O(nK)             A+B → E    O(2n)
                         C+D → F    O(2n)     Level 3: O(4n) total
                         E+F → result O(4n)
                         Total: O(n log K)    [n=total, K=8 here]
```

### Section 3: Edge Cases & Correctness

**Q12. How does your implementation handle the case where all K lists are empty, or the input array of lists is itself empty?**
A: Both cases must be handled before the main loop. If `lists` is empty or null, return null immediately (no lists to merge). If all lists are empty (all elements of `lists` are null or empty), the initialization loop inserts nothing into the heap; the main while loop never executes; `dummy.next` is null; return null. Both cases are naturally handled by the dummy-head + heap structure without special casing — the heap starts empty, the loop exits immediately, and `dummy.next` correctly returns null. Always verify with a null/empty test before submitting.

```js
function mergeKLists(lists) {
  if (!lists || lists.length === 0) return null; // guard: empty input

  const heap = new MinHeap((a, b) => a[0] - b[0]);
  const dummy = new ListNode(0);
  let current = dummy;

  // initialization: skip null lists (all-empty case → heap stays empty)
  for (let i = 0; i < lists.length; i++) {
    if (lists[i] !== null) heap.push([lists[i].val, i, lists[i]]);
  }

  // main loop: exits immediately if heap is empty (all lists were empty)
  while (heap.size() > 0) {
    const [, listIdx, node] = heap.pop();
    current.next = node;
    current = current.next;
    if (node.next !== null) heap.push([node.next.val, listIdx, node.next]);
    current.next = null;
  }

  return dummy.next; // null if all lists were empty ✓
}
```

**Q13. What happens with duplicate values across multiple lists, and does your algorithm handle them correctly?**
A: Duplicate values across lists are handled correctly — the heap treats each node as a distinct entity regardless of value. If two lists both have a node with value 5, both are inserted into the heap as separate entries. When one is extracted, the other remains in the heap and will be extracted in a subsequent step. The output correctly contains both 5s. The only subtlety: if the comparator doesn't have a stable tie-breaker (e.g., using `listIndex` when values are equal), the heap may produce a valid but non-deterministic ordering of equal elements. For correctness (not stability), this doesn't matter — both 5s will appear in the output. For stability (preserving the original list's relative order among equals), a `listIndex` tie-breaker ensures the element from the earlier-indexed list is extracted first.

**Q14. How would you merge K sorted arrays (rather than linked lists), and what changes?**
A: The algorithm is structurally identical — the min-heap approach works directly with arrays by replacing linked list node references with `(arrayIndex, elementIndex)` pairs. The heap entry becomes `[value, arrayIndex, elementIndex]`. After extracting an entry, the next element from the same array is `arrays[arrayIndex][elementIndex + 1]` — inserted into the heap if `elementIndex + 1 < arrays[arrayIndex].length`. The divide-and-conquer approach also works, using a standard two-pointer array merge instead of linked-list pointer rewiring.

```js
function mergeKArrays(arrays) {
  const heap = new MinHeap((a, b) => a[0] - b[0]);
  const result = [];

  // Initialize: insert first element of each non-empty array
  for (let i = 0; i < arrays.length; i++) {
    if (arrays[i].length > 0) {
      heap.push([arrays[i][0], i, 0]); // [value, arrayIdx, elementIdx]
    }
  }

  while (heap.size() > 0) {
    const [val, arrIdx, elemIdx] = heap.pop();
    result.push(val);
    if (elemIdx + 1 < arrays[arrIdx].length) {
      heap.push([arrays[arrIdx][elemIdx + 1], arrIdx, elemIdx + 1]);
    }
  }

  return result;
}
```

### Section 4: Advanced Variants

**Q15. How would you merge K sorted streams (elements arrive lazily, not all available upfront)?**
A: Lazy streams require the heap-based approach — divide-and-conquer needs the full input available upfront to split into halves. With streams, you treat each stream as a list whose "head" is the most recently fetched value. The heap holds one entry per active stream. When a stream's entry is extracted, call `stream.next()` to fetch its next value — if the stream is exhausted, don't re-insert. This is architecturally identical to the linked-list version (where `node.next` is the "next value" of a stream). The heap-based approach is the canonical choice for stream merging because it processes one element at a time and requires no buffering of future elements.

```js
// Merging K iterators/generators (streams)
function* mergeKStreams(iterators) {
  const heap = new MinHeap((a, b) => a[0] - b[0]);

  // Initialize with first value from each stream
  for (let i = 0; i < iterators.length; i++) {
    const { value, done } = iterators[i].next();
    if (!done) heap.push([value, i, iterators[i]]);
  }

  while (heap.size() > 0) {
    const [val, idx, iter] = heap.pop();
    yield val; // output one element at a time (streaming output)
    const { value, done } = iter.next();
    if (!done) heap.push([value, idx, iter]);
  }
}
```

**Q16. How would you extend the algorithm to merge K sorted lists in DESCENDING order?**
A: Invert the heap comparator: use a **max-heap** instead of a min-heap (compare `b[0] - a[0]` instead of `a[0] - b[0]`). Every other part of the algorithm is unchanged — the max-heap's root always holds the current maximum across all list heads, which is extracted first and produces a descending result. No reversal step needed. Alternatively, reverse each input list first, merge ascending using the standard algorithm, then reverse the result — but this requires three extra passes and is clearly inferior to simply inverting the comparator.

**Q17. What is the "external sort" problem, and how does merge K sorted lists relate to it?**
A: External sort is the problem of sorting a dataset too large to fit in memory, typically stored across multiple disk files or distributed across machines. The standard approach is:
1. **Sort phase**: load chunks that fit in memory, sort each chunk, write back to disk — producing K sorted "runs" (files or partitions).
2. **Merge phase**: merge the K sorted runs into a single sorted output — this is exactly the "merge K sorted files" problem, with the constraint that you can only hold O(K) elements in memory at once (one from each run).

The min-heap merge is the standard algorithm for the merge phase of external sort. Each "list" is a file handle; each "node" is one buffered block from that file. The heap holds one buffered value per file — O(K) memory usage, regardless of total data size N. This is precisely why the O(K) heap space of the min-heap approach is important — it makes the algorithm viable even when N >> available memory.

**Q18. How would you efficiently merge K sorted lists where K itself is very large (e.g., K = 1,000,000)?**
A: A heap of size K=1,000,000 is still technically correct — heap operations are O(log K) ≈ O(20) for K=10^6, and the total time is O(N × 20) which is very fast. However, a heap with 10^6 entries has poor cache behavior (heap operations access random memory locations within a large array). A practical optimization for very large K is to use a **tournament tree** (a complete binary tree of size K with "winner" propagation) — structurally similar to a heap but with better cache locality for fixed-K scenarios. Alternatively, if the K lists can be batched (e.g., they're organized by region, time window, or source), process them in batches of size B (merge B lists at a time using the heap), then merge the resulting K/B sorted outputs — reducing the effective K by a factor of B per round.

### Section 5: Scenario / Interview-Style Questions

**Q19. "Walk me through your approach to merging K sorted linked lists, starting from scratch."**
A: First, I'd note that the core challenge is efficiently finding the minimum element among K list heads at each step. Naively scanning all K heads costs O(K) per element — O(NK) total. A min-heap reduces the per-element decision to O(log K), giving O(N log K) total.

My implementation: use a dummy head node to avoid special-casing the result list's head. Initialize a min-heap with the first node of each non-null list. Then: while the heap is non-empty, extract the minimum (heap root), append it to the result list, and insert that node's `next` into the heap (if non-null). The heap always holds exactly one node per active list — at most K entries at any time.

I'd also mention the alternative: divide-and-conquer with pair-wise merging, which achieves the same O(N log K) time with O(log K) stack space instead of O(K) heap space — useful when K is very small or a heap data structure isn't available.

**Q20. "Your min-heap approach is O(N log K). Can you do better — is O(N) possible for this problem?"**
A: O(N) is not achievable for arbitrary input in the comparison model. A lower bound argument: merging K sorted lists of total size N is at least as hard as sorting N elements given K "buckets" of pre-sorted information. Specifically, if K = N (N lists of 1 element each), merging reduces exactly to sorting N elements — which requires Ω(N log N) comparisons in the comparison model. Since N log N > N log K when K = N, the general lower bound for merge K sorted lists is Ω(N log K) in the comparison model. So O(N log K) is optimal, and O(N) is not achievable without additional constraints (e.g., bounded integer values enabling counting sort).

**Q21. "How would you test your merge K sorted lists implementation?"**
A: Key test cases, in order of what they verify:

- **Empty input** (`lists = []`): should return null immediately without crashing.
- **All lists empty** (`lists = [null, null, null]`): heap stays empty; returns null.
- **Single non-empty list** (`lists = [1→2→3]`): should return the list unchanged — tests that a single-list case doesn't corrupt the output.
- **K=2 lists** (the base case): verifies the algorithm reduces correctly to the two-list merge for minimal K.
- **Lists of unequal lengths**: one list with 1 element, another with 100 — tests that the heap correctly handles one list exhausting early and the other continuing.
- **Duplicate values within and across lists**: `[1→1→2]` and `[1→2→2]` — verifies both duplicates appear in output and the comparator handles ties without error.
- **All lists with a single element**: K elements total — tests the "N = K" case where the heap does exactly K-1 rounds of extract+insert then K drain steps.
- **Already globally sorted lists**: `[1→4→7]`, `[2→5→8]`, `[3→6→9]` — the heap correctly interleaves them.
- **Negative and mixed-sign values**: `-5 → -1 → 3` — verifies no sign-specific assumptions in the comparator.
- **Very long lists with K=2**: stress-tests that the algorithm terminates correctly and doesn't have an off-by-one in the loop termination condition.

## Problem 1 — Merge K Sorted Linked Lists (Min-Heap)

### Problem
You are given an array of `k` linked lists, each sorted in ascending order. Merge all the linked lists into one sorted linked list and return it.

```
Input:
  lists = [
    1 → 4 → 5,
    1 → 3 → 4,
    2 → 6
  ]
Output: 1 → 1 → 2 → 3 → 4 → 4 → 5 → 6
```

### Pattern Recognition
Min-heap with one entry per list — at each step, the heap root gives the global minimum across all list fronts in O(1); extracting and re-inserting advances the winning list's frontier in O(log K).

### Key Insight
The heap maintains a invariant: it always contains exactly one node per active (non-exhausted) list — the current frontier of that list. Extracting the minimum and inserting the next node from the same list preserves this invariant after every step, guaranteeing the output is produced in globally sorted order.

### Approach
Build a dummy head. Initialize the heap with the head node of each non-null list. While the heap is non-empty: extract the minimum node, append it to the result, insert its `next` (if non-null) into the heap. Return `dummy.next`.

### Solution

```js
class MinHeap {
  constructor() {
    this.heap = [];
  }

  push(node) {
    this.heap.push(node);
    this._siftUp(this.heap.length - 1);
  }

  pop() {
    const top = this.heap[0];
    const last = this.heap.pop();
    if (this.heap.length > 0) {
      this.heap[0] = last;
      this._siftDown(0);
    }
    return top;
  }

  size() { return this.heap.length; }

  _siftUp(i) {
    while (i > 0) {
      const parent = Math.floor((i - 1) / 2);
      // compare by node value
      if (this.heap[i].val < this.heap[parent].val) {
        [this.heap[i], this.heap[parent]] = [this.heap[parent], this.heap[i]];
        i = parent;
      } else break;
    }
  }

  _siftDown(i) {
    const n = this.heap.length;
    while (true) {
      let smallest = i;
      const l = 2 * i + 1, r = 2 * i + 2;
      if (l < n && this.heap[l].val < this.heap[smallest].val) smallest = l;
      if (r < n && this.heap[r].val < this.heap[smallest].val) smallest = r;
      if (smallest === i) break;
      [this.heap[i], this.heap[smallest]] = [this.heap[smallest], this.heap[i]];
      i = smallest;
    }
  }
}

function mergeKLists(lists) {
  if (!lists || lists.length === 0) return null;

  const heap = new MinHeap();
  const dummy = new ListNode(0); // sentinel head — avoids special-casing first node
  let current = dummy;

  // Initialize heap with the head of each non-null list
  for (const head of lists) {
    if (head !== null) heap.push(head);
  }

  while (heap.size() > 0) {
    const node = heap.pop();    // extract current global minimum
    current.next = node;        // append to result (rewire, no new allocation)
    current = current.next;

    if (node.next !== null) {
      heap.push(node.next);     // advance this list's frontier in the heap
    }
    current.next = null;        // detach: sever old next pointer to avoid cycles
  }

  return dummy.next;
}
```

## Problem 2 — Merge K Sorted Lists (Divide and Conquer)

### Problem
Same as Problem 1 — merge K sorted linked lists — but implement it using divide and conquer rather than a heap.

```
Input: lists = [1→4→5, 1→3→4, 2→6]
Output: 1→1→2→3→4→4→5→6
```

### Pattern Recognition
Divide and conquer — recursively halve the set of K lists, merge pairs at each level, mirror the structure of merge sort applied to lists-of-lists.

### Key Insight
Any single level of the recursion does O(N) total work (every element participates in exactly one merge at each level). With O(log K) levels, the total is O(N log K) — identical to the heap approach but achieved through repeated two-way merges instead of a K-way heap.

### Approach
Base cases: zero lists → null; one list → return it unchanged. Recursive case: split the lists array in half, recursively merge each half to a single list, then merge the two resulting lists with the standard O(N) two-pointer merge.

### Solution

```js
function mergeKLists(lists) {
  if (!lists || lists.length === 0) return null;
  return divideAndConquer(lists, 0, lists.length - 1);
}

function divideAndConquer(lists, left, right) {
  if (left === right) return lists[left]; // base case: single list
  if (left + 1 === right) return mergeTwoLists(lists[left], lists[right]); // base: pair

  const mid = Math.floor((left + right) / 2);
  const leftMerged  = divideAndConquer(lists, left, mid);       // merge left half
  const rightMerged = divideAndConquer(lists, mid + 1, right);  // merge right half
  return mergeTwoLists(leftMerged, rightMerged);                 // combine
}

// Standard O(N) two-pointer merge of two sorted linked lists
function mergeTwoLists(l1, l2) {
  const dummy = new ListNode(0);
  let current = dummy;

  while (l1 !== null && l2 !== null) {
    if (l1.val <= l2.val) {
      current.next = l1;
      l1 = l1.next;
    } else {
      current.next = l2;
      l2 = l2.next;
    }
    current = current.next;
  }

  // attach remaining nodes (at most one list is non-null here)
  current.next = l1 !== null ? l1 : l2;
  return dummy.next;
}
```

- Empty `lists`: upfront guard returns null. ✓
- K=1: `divideAndConquer(lists, 0, 0)` returns `lists[0]` directly — no merging. ✓

- "Which approach (heap or divide-and-conquer) would you use in production?" → Divide-and-conquer for batch merging of a fixed set of lists (simpler, no heap implementation needed, better cache behavior from sequential two-pointer merges). Heap for streaming/online merging where lists arrive over time or outputs must be produced incrementally.

## Problem 3 — Smallest Range Covering Elements from K Lists

### Problem
You have `k` lists of sorted integers. Find the smallest range `[a, b]` such that there is at least one number from each of the k lists within the range `[a, b]`.

```
Input: nums = [[4,10,15,24,26],[0,9,12,20],[5,18,22,30]]
Output: [20, 24]

Explanation: list0 has 24, list1 has 20, list2 has 22 — all within [20,24].
```

### Pattern Recognition
Min-heap with simultaneous tracking of current maximum — maintain one pointer per list (as in merge K lists), but instead of just tracking the minimum, also track the current maximum among all active pointers. The answer is the window `[currentMin, currentMax]` at the step where `currentMax - currentMin` is minimized.

### Key Insight
At any moment, the K "frontier" elements (one per list) form a window `[min, max]`. This window always contains at least one element from each list (by definition — each list contributes exactly its frontier element). The minimum of this window is the heap root (cheaply accessible), and the maximum must be tracked separately as elements are inserted and extracted. Advancing the minimum pointer (extracting the heap root and inserting the next element from the same list) is the only move that can shrink the window — moving any other pointer only increases the minimum or doesn't help. This greedy choice is provably optimal.

### Approach
Initialize the heap with the first element of each list (as `[value, listIndex, elementIndex]`) and track the current maximum. While all K lists are represented in the heap: record the window if it's smaller than the best seen. Extract the minimum, update the best window if needed. Insert the next element from the same list; update the current maximum. If any list is exhausted, stop (no valid window exists that includes an element from the exhausted list).

### Solution

```js
function smallestRange(nums) {
  const heap = new MinHeap((a, b) => a[0] - b[0]);
  let currentMax = -Infinity;
  let rangeStart = 0, rangeEnd = Infinity;

  // Initialize: insert first element of each list, track initial max
  for (let i = 0; i < nums.length; i++) {
    heap.push([nums[i][0], i, 0]);
    currentMax = Math.max(currentMax, nums[i][0]);
  }

  while (heap.size() === nums.length) { // all K lists still active
    const [minVal, listIdx, elemIdx] = heap.pop();

    // current window: [minVal, currentMax] — check if it's the best so far
    if (currentMax - minVal < rangeEnd - rangeStart) {
      rangeStart = minVal;
      rangeEnd = currentMax;
    }

    // advance the list that contributed the minimum
    if (elemIdx + 1 < nums[listIdx].length) {
      const nextVal = nums[listIdx][elemIdx + 1];
      heap.push([nextVal, listIdx, elemIdx + 1]);
      currentMax = Math.max(currentMax, nextVal); // max can only increase or stay
    } else {
      break; // list exhausted — no valid window possible anymore
    }
  }

  return [rangeStart, rangeEnd];
}

// MinHeap implementation (same as Problem 1, with custom comparator)
class MinHeap {
  constructor(compare) {
    this.heap = [];
    this.compare = compare;
  }
  push(val) {
    this.heap.push(val);
    this._siftUp(this.heap.length - 1);
  }
  pop() {
    const top = this.heap[0];
    const last = this.heap.pop();
    if (this.heap.length > 0) { this.heap[0] = last; this._siftDown(0); }
    return top;
  }
  size() { return this.heap.length; }
  _siftUp(i) {
    while (i > 0) {
      const p = Math.floor((i - 1) / 2);
      if (this.compare(this.heap[i], this.heap[p]) < 0) {
        [this.heap[i], this.heap[p]] = [this.heap[p], this.heap[i]]; i = p;
      } else break;
    }
  }
  _siftDown(i) {
    const n = this.heap.length;
    while (true) {
      let s = i;
      const l = 2*i+1, r = 2*i+2;
      if (l < n && this.compare(this.heap[l], this.heap[s]) < 0) s = l;
      if (r < n && this.compare(this.heap[r], this.heap[s]) < 0) s = r;
      if (s === i) break;
      [this.heap[i], this.heap[s]] = [this.heap[s], this.heap[i]]; i = s;
    }
  }
}
```

- "What if you needed the smallest range containing at least one element from at least M of the K lists (not necessarily all K)?" → Significantly harder — the "all lists active" termination condition must be replaced with a count of how many lists are currently represented in the heap window. This requires a frequency map alongside the heap.

## Problem 4 — Find K Pairs with Smallest Sums

### Problem
You are given two sorted integer arrays `nums1` and `nums2`. Define a pair `(u, v)` where `u` is from `nums1` and `v` is from `nums2`. Return the `k` pairs `(u1, v1), (u2, v2), ..., (uk, vk)` with the smallest sums `u + v`.

```
Input: nums1 = [1,7,11], nums2 = [2,4,6], k = 3
Output: [[1,2],[1,4],[1,6]]

Input: nums1 = [1,1,2], nums2 = [1,2,3], k = 2
Output: [[1,1],[1,1]]
```

### Pattern Recognition
Min-heap treating each row of the pair matrix as a sorted "virtual list" — `nums1[i]` paired with each element of `nums2` forms a sorted list `[(nums1[i]+nums2[0], i, 0), (nums1[i]+nums2[1], i, 1), ...]`. This is exactly merging K sorted lists (one per `nums1` index) to extract the K smallest elements.

### Key Insight
The pair `(nums1[i], nums2[j])` has sum `nums1[i] + nums2[j]`. For a fixed `i`, as `j` increases, the sum increases (since `nums2` is sorted). So the "lists" to merge are: for each `i` from 0 to `nums1.length-1`, the sorted sequence of sums `nums1[i]+nums2[0], nums1[i]+nums2[1], ...`. Merging these K virtual lists with a min-heap and stopping after K extractions gives exactly the K smallest pair sums.

### Approach
Initialize the heap with the first pair from each of the first `min(k, nums1.length)` rows — `(nums1[i]+nums2[0], i, 0)`. Extract the minimum k times: each extraction gives one result pair; insert the next pair from the same row `(nums1[i]+nums2[j+1], i, j+1)` if `j+1 < nums2.length`.

### Solution

```js
function kSmallestPairs(nums1, nums2, k) {
  if (nums1.length === 0 || nums2.length === 0) return [];

  const heap = new MinHeap((a, b) => a[0] - b[0]);
  const result = [];

  // Initialize: first pair from each nums1 element
  // Only need min(k, nums1.length) initial entries — can't need more than k results
  for (let i = 0; i < Math.min(k, nums1.length); i++) {
    // [sum, nums1 index, nums2 index]
    heap.push([nums1[i] + nums2[0], i, 0]);
  }

  while (result.length < k && heap.size() > 0) {
    const [sum, i, j] = heap.pop();
    result.push([nums1[i], nums2[j]]); // record the pair, not the sum

    // advance nums2 index for this nums1[i] row
    if (j + 1 < nums2.length) {
      heap.push([nums1[i] + nums2[j + 1], i, j + 1]);
    }
  }

  return result;
}
```

## Problem 5 — Merge K Sorted Arrays (Iterative / Non-Recursive Divide and Conquer)

### Problem
Given K sorted arrays, merge them into a single sorted array. Implement using iterative (bottom-up) divide-and-conquer — no recursion, no heap.

```
Input: [[1,4,7],[2,5,8],[3,6,9]]
Output: [1,2,3,4,5,6,7,8,9]
```

### Pattern Recognition
Iterative bottom-up merge — process all arrays in passes, merging adjacent pairs each pass, until one sorted array remains. Mirrors iterative merge sort's bottom-up structure.

### Key Insight
In iterative divide-and-conquer, pairs of arrays are merged in each "round": round 1 merges arrays 0+1, 2+3, 4+5, ... producing K/2 arrays. Round 2 merges those K/2 arrays in pairs, producing K/4. After ceil(log K) rounds, one array remains. Each round does O(N) total work (every element processed once); ceil(log K) rounds gives O(N log K) total — identical to the recursive version and the heap version, but with O(1) extra space (no recursion stack, no heap, just index arithmetic).

### Approach
Start with the input array of arrays. Repeatedly pass over the current set of arrays, merging each adjacent pair using the standard two-array merge. Replace each pair with its merged result. Repeat until only one array remains.

### Solution

```js
function mergeKArrays(arrays) {
  if (!arrays || arrays.length === 0) return [];
  if (arrays.length === 1) return arrays[0];

  let current = arrays.slice(); // shallow copy — don't mutate input

  // Each pass halves the number of arrays by merging adjacent pairs
  while (current.length > 1) {
    const nextRound = [];

    for (let i = 0; i < current.length; i += 2) {
      if (i + 1 < current.length) {
        // merge adjacent pair
        nextRound.push(mergeTwoArrays(current[i], current[i + 1]));
      } else {
        // odd one out — carry forward without merging
        nextRound.push(current[i]);
      }
    }

    current = nextRound;
  }

  return current[0];
}

// Standard O(N) two-pointer merge of two sorted arrays
function mergeTwoArrays(a, b) {
  const result = [];
  let i = 0, j = 0;

  while (i < a.length && j < b.length) {
    if (a[i] <= b[j]) {
      result.push(a[i++]);
    } else {
      result.push(b[j++]);
    }
  }

  // append remaining elements
  while (i < a.length) result.push(a[i++]);
  while (j < b.length) result.push(b[j++]);

  return result;
}
```

### Complexity
- Time: O(N log K) — ceil(log K) rounds, each round doing O(N) total merge work.
- Space: O(N) — the merged arrays from each round must be stored. No recursion stack, no heap. At any point, at most two "rounds" of arrays are in memory simultaneously (current and nextRound), each holding O(N) elements total.

### Edge Cases
- K=1: while condition `current.length > 1` is false immediately; returns `arrays[0]`. ✓
- K=0 or empty: upfront guard returns `[]`. ✓
- Odd K: the "odd one out" at the end of each pass is carried forward without merging — correctly handled by the `i+1 < current.length` check. ✓
- K is a power of 2: every pass produces exactly K/2 arrays with no odd-one-out; the algorithm terminates in exactly log K passes. ✓
- Some arrays empty: `mergeTwoArrays([], [1,2,3])` correctly returns `[1,2,3]` — the while loop exits immediately when `i >= a.length`, and the remaining-elements loop appends b entirely. ✓

### Follow-up Questions
- "How does this compare to the recursive divide-and-conquer from Problem 2?" → Identical time and correctness; the iterative version avoids O(log K) call-stack space but uses O(N) space for intermediate merged arrays. In practice both use O(N) space for the arrays themselves; the stack space difference is negligible for typical K.
- "Can you make this in-place (O(1) extra space)?" → For arrays, in-place merging requires an in-place merge algorithm (e.g., rotation-based merge), which is O(N²) — eliminating the log K improvement. For linked lists, in-place pointer rewiring is O(1) extra space, making the Problem 2 (divide and conquer on linked lists) truly O(log K) extra space.

```
Merge K sorted lists/arrays problem — which algorithm?
│
├── INPUT TYPE?
│   ├── Linked lists → heap (rewire pointers in-place, O(K) heap space)
│   │                   OR divide-and-conquer (O(log K) stack space)
│   └── Arrays → heap (index-based) OR iterative D&C (O(N) intermediate space)
│
├── WHICH APPROACH?
│   │
│   ├── STREAMING / LAZY INPUT (lists arrive over time, can't split upfront)?
│   │   └── Min-heap ONLY — one entry per active stream, O(K) space
│   │         Extract minimum, advance that stream, repeat
│   │         → O(N log K) time, O(K) space
│   │
│   ├── ALL LISTS AVAILABLE UPFRONT?
│   │   ├── Min-heap: O(N log K) time, O(K) space (heap)
│   │   │   Best when: K is large, need incremental output, heap available in stdlib
│   │   │
│   │   └── Divide-and-conquer: O(N log K) time, O(log K) stack space
│   │       Best when: K is small-moderate, no heap stdlib, batch processing
│   │       Iterative D&C: same time, O(N) intermediate, O(1) stack
│   │
│   └── NAIVE (avoid): sequential merge one-by-one → O(NK), not O(N log K)
│
├── VARIANTS — all use the heap-with-frontier pattern:
│   │
│   ├── K LARGEST from K sorted lists?
│   │   └── Max-heap instead of min-heap; same structure
│   │
│   ├── SMALLEST RANGE covering all K lists?
│   │   └── Min-heap + track currentMax separately
│   │         Advance min-frontier each step; window = [heapRoot, currentMax]
│   │         Stop when any list exhausted
│   │         → O(N log K) time, O(K) space
│   │
│   ├── K SMALLEST PAIRS (two sorted arrays)?
│   │   └── Min-heap of K virtual "rows" (one per nums1 index)
│   │         Each row: nums1[i] + nums2[j] sorted by j
│   │         Initialize with j=0 for first min(k, m) rows
│   │         → O(k log k) time, O(k) space
│   │
│   └── EXTERNAL SORT (data doesn't fit in memory)?
│         └── Min-heap merge with one buffered element per sorted run
│               O(N log K) time, O(K) memory regardless of N
│
└── COMPLEXITY SUMMARY:
      O(NK):    naive sequential merge — avoid
      O(N log K): heap or D&C — always target this
```

## Common Bugs Checklist

Before submitting any merge K sorted lists solution, verify:

1. **Never insert null into the heap — guard both at initialization and during the main loop?** — Initialization: `if (head !== null) heap.push(head)`. Main loop: `if (node.next !== null) heap.push(node.next)`. Inserting null causes a null-pointer exception on the next extraction when `node.val` is accessed. Both guards are required; omitting either one causes failures on empty-list inputs or when any list is exhausted.

2. **Dummy head used, and `dummy.next` returned (not `dummy` itself)?** — Returning `dummy` returns the sentinel node with value 0 prepended to the result. The sentinel's only purpose is to make the first-node attachment uniform; the actual result starts at `dummy.next`. This is the most common single-character mistake in linked-list construction problems.

3. **`current.next = null` (detach) after rewiring each node?** — When rewiring existing nodes into the result list, each node's original `.next` pointer still points to the rest of its original list. Without detaching, the result list has the correct values in order but has "dangling" sub-lists branching off at every node (the original list's remaining nodes). Setting `current.next = null` after `current = current.next` ensures each node's `.next` is overwritten by the next attachment step or left as null at the tail.

4. **Heap size passed to `heapify`/`siftDown` is the current heap size, not the array length?** — When implementing a custom MinHeap backed by an array, siftDown must be bounded by the current logical heap size (`this.heap.length` after the pop shrinks it). Using a stale or incorrect `n` value allows the sift to compare with garbage elements beyond the logical heap boundary.

5. **Divide-and-conquer: `mergeTwoLists(null, someList)` returns `someList` correctly?** — In the recursive or iterative D&C approach, after the recursion reduces to a single remaining list and it's paired with "nothing" (an empty slot), the merge must return the non-null list unchanged. The standard two-pointer merge loop exits immediately when either pointer is null, and the tail-attachment `current.next = l1 !== null ? l1 : l2` correctly attaches the surviving pointer. Verify this isn't accidentally treated as an error.

6. **Iterative D&C: odd-numbered groups carry the last array forward without merging?** — When the current set of arrays has an odd count, the last array has no pair in that round. It must be pushed into `nextRound` directly without being merged into anything. Missing this check causes the last array to be dropped entirely from the output.

7. **Smallest Range: `currentMax` tracked via `Math.max` on each insertion, never decremented?** — As elements are inserted into the heap (when a list's frontier advances), `currentMax` may increase (new element is larger than current max) or stay the same (new element is not the new max). It never decreases — the extracted minimum's value cannot be the max unless all elements are equal. Attempting to track the max by scanning the heap on every step is O(K) per step, negating the O(log K) advantage.

8. **K Smallest Pairs: only initialize `min(k, nums1.length)` rows, not all rows?** — Initializing all `nums1.length` rows when `nums1.length >> k` wastes O(nums1.length) heap space and O(nums1.length × log(nums1.length)) initialization time. Since at most k results are needed, at most k rows can contribute, so only the first `min(k, nums1.length)` rows need to be initialized.

9. **K Smallest Pairs: the heap stores `[sum, i, j]` (sum first for comparison), not `[i, j, sum]`?** — The heap's comparator sorts by the first element of the tuple. If the sum is not the first element, the heap will order by array index (which is meaningless) rather than by sum, producing incorrect results. Tuple ordering: `[sum, nums1Index, nums2Index]`.

10. **Stability clarified if required: `listIndex` used as tie-breaker in the comparator?** — When two heap entries have equal values, the heap comparator must produce a consistent ordering to avoid non-deterministic behavior. Without a tie-breaker, JavaScript's sort and heap implementations may behave differently across runs or engines. Using `listIndex` as a secondary sort key ensures ties are broken consistently (earlier-indexed list wins), which also happens to produce a stable merge when list indices reflect original input order.

**Final Tip:** At the 5–7 YOE level, the key signal is immediately recognizing that naive sequential merging is O(NK) — not O(N log K) — and articulating exactly why: "each element in the first list gets processed in every subsequent merge, so elements from early lists are touched K times total." Then the pivot to the heap approach should be automatic: "instead of re-scanning all K heads each step, maintain one heap entry per list head — O(log K) per step instead of O(K)." The strongest answers also name the divide-and-conquer alternative and correctly identify both as O(N log K) but with different space constants (O(K) vs O(log K)), then choose between them based on whether input is streaming or batch. Recognizing that "smallest range across K lists" and "K smallest pairs" are both disguised merge-K-lists problems — with the heap-with-frontier pattern at their core — is the pattern-transfer signal that separates senior from mid-level responses.
