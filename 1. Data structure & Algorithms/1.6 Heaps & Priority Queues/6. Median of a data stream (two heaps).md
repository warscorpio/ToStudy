## Topic A: The Two-Heap Invariant — Derivation & Mechanics

### Section A1: Why Two Heaps

**Q1. What is the two-heap pattern for streaming median, and why does it reduce O(n) per query to O(log n) per insertion?**

A: A sorted array supports O(1) median lookup but O(n) insertion (shifting). A balanced BST supports O(log n) insertion and O(log n) median, but median lookup requires tracking a pointer that can drift across structural rotations. The two-heap pattern exploits a simpler structural invariant: split all seen elements into a lower half and an upper half, each maintained as a heap. The lower half's maximum and the upper half's minimum — O(1) to access as heap tops — are the two "middle elements." With size balance, the median is always one or the other of these two tops.

The crucial insight: you don't need to maintain the *entire* sorted order — you only need the *boundary between halves*. Two heaps maintain this boundary with O(log n) per insertion and O(1) median retrieval.

```
Naive sorted array: [1, 3, 5, 7, 9]
  Median = arr[2] = 5. O(1) lookup.
  Insert 4: shift [5,7,9] right → [1,3,4,5,7,9]. O(n) insertion.

Two-heap structure after [1,3,5,7,9]:
  lower (max-heap): [5, 3, 1]  ← everything ≤ median
  upper (min-heap): [7, 9]     ← everything ≥ median
  Median = lower.top = 5. O(1).
  Insert 4: push to lower heap. O(log n). Rebalance. O(log n).
```

**Q2. What are the two invariants of the two-heap structure, and what property does each guarantee?**

A: The two-heap structure maintains two invariants simultaneously after every insertion:

**Invariant 1 — Order**: `lower.top ≤ upper.top`. Every element in the lower half is ≤ every element in the upper half. This guarantees that the lower heap truly represents the lower half of all seen elements and the upper heap the upper half — without which the "tops" have no meaning as median candidates.

**Invariant 2 — Size balance**: `lower.size == upper.size` (even total n) OR `lower.size == upper.size + 1` (odd total n, with lower holding the extra). This ensures the median is exactly at the boundary between the two halves. When sizes differ by more than 1, the heaps don't represent balanced halves.

Together these two invariants uniquely determine the median: if sizes are equal, median = `(lower.top + upper.top) / 2`; if lower is larger by 1, median = `lower.top`. If either invariant is broken, the returned value is wrong.

```
Valid states after n=5 elements:
  lower=[5,3,1], upper=[7,9]   → 5≤7 ✓, sizes 3 vs 2 (differ by 1) ✓ → median=5 ✓
  lower=[3,1],   upper=[5,7,9] → 3≤5 ✓, sizes 2 vs 3 (upper LARGER) ✗ → wrong!
  lower=[7,5,3,1], upper=[9]   → 7≤9 ✓, sizes 4 vs 1 (differ by 3) ✗ → wrong!
  lower=[5,3,1], upper=[4,9]   → 5>4 ✗ → order violated → wrong!
```

**Q3. Walk through the three-step addNum algorithm and prove why each step is necessary and why ORDER fix must precede SIZE fix.**

A: The three steps are:

**Step 1 — Push to lower**: always push `num` to the lower (max) heap first. This temporarily may violate either invariant — the new element might belong in the upper half (violating order), or lower might now be too large (violating size balance).

**Step 2 — Fix ORDER**: if upper is non-empty and `lower.top > upper.top`, the element just pushed (or an element displaced by the push via sift-up) is too large for the lower half. Pop lower's top and push it to upper.

**Step 3 — Fix SIZE**: after the order fix, check size balance. If `lower.size > upper.size + 1`: lower has one too many → pop lower's top and push to upper. If `upper.size > lower.size`: upper has one too many → pop upper's top and push to lower.

**Why order before size**: suppose `num = 10` is pushed to lower (which currently has top = 8) and upper has top = 6. After Step 1: lower.top = 10, upper.top = 6 — order violated (10 > 6). If we fix size first (lower is too big → move lower.top = 10 to upper): upper now has top = 6 but contains 10 — chaos. If we fix order first (move lower.top = 10 to upper, then move upper.top = 6 to lower to fix size): lower.top = 8, upper.top = 10. Order and size both correct.

```
addNum(10) with lower=[8,3,1], upper=[12,15]:
  Step 1: push 10 to lower. lower=[10,8,3,1].
  Step 2: lower.top(10) > upper.top(12)? NO → skip. ← 10 < 12, already in order.
  Step 3: lower.size(4) > upper.size(2)+1=3 → YES → pop lower.top=10, push to upper.
    lower=[8,3,1], upper=[10,12,15].
  sizes: 3 vs 3 ✓. order: 8 ≤ 10 ✓.

addNum(5) with lower=[8,3,1], upper=[12,15]:
  Step 1: push 5 to lower. lower=[8,5,3,1].
  Step 2: lower.top(8) > upper.top(12)? NO → skip.
  Step 3: lower.size(4) > upper.size(2)+1=3 → YES → pop 8, push to upper.
    lower=[5,3,1], upper=[8,12,15].
  sizes: 3 vs 3 ✓. order: 5 ≤ 8 ✓.
```

**Q4. Why do we always push to the lower (max) heap first, rather than branching based on the new element's value?**

A: A branching approach — "if `num ≤ lower.top` push to lower, else push to upper" — appears more targeted but introduces subtle failure modes. If upper is empty and `num > lower.top`, pushing to upper is correct; but if lower is also empty, `lower.top` is undefined. After pushing to upper, size rebalancing may still need to move it back to lower (if upper becomes too large). The "always push to lower first" approach eliminates all branching: every possible state (upper empty, lower empty, value anywhere in the range) is handled uniformly by the three steps. The order fix in Step 2 serves as the conditional logic — it only fires when the element truly belongs in the upper half.

```
Branching approach failure case:
  lower=[], upper=[]. Add num=5:
  "if num ≤ lower.top" — lower.top is undefined! Need null check.
  "else push to upper" — upper=[5]. Then size fix: upper.size(1) > lower.size(0) → move 5 to lower. lower=[5].
  Correct, but required an extra conditional for the null case.

Three-step approach:
  Step 1: push 5 to lower. lower=[5].
  Step 2: upper empty → skip.
  Step 3: sizes 1 vs 0 (differ by 1) → OK.
  Done. No null checks needed. ✓
```

### Section A2: Invariant Maintenance Costs & Edge Cases

**Q5. How many heap operations does addNum perform in the best and worst case?**

A: Each "push to heap + sift-up" and each "pop from heap + sift-down" is one heap operation, each O(log n). Step 1 always performs 1 push. Step 2 performs 0 or 2 operations (pop + push, if order is violated). Step 3 performs 0 or 2 operations (pop + push, for size rebalancing). Total: minimum 1 operation (Step 1 only, no violations), maximum 5 operations (Step 1 push + Step 2 pop+push + Step 3 pop+push). All operations are O(log n), so addNum is O(log n) in all cases. The constant factor is at most 5 — better than it looks, since in practice Steps 2 and 3 rarely both fire together.

```
Best case (element clearly in lower half, sizes already balanced):
  num=3, lower=[5,1], upper=[7,9]:
  Step 1: push 3. lower=[5,3,1]. 1 op.
  Step 2: 5 ≤ 7 → skip. 0 ops.
  Step 3: sizes 3 vs 2 (differ by 1) → OK. 0 ops.
  Total: 1 op.

Worst case (element in wrong half AND size imbalanced):
  num=20, lower=[5,1], upper=[7,9]:
  Step 1: push 20. lower=[20,5,1]. 1 op.
  Step 2: 20 > 7 → pop 20, push to upper. 2 ops. lower=[5,1], upper=[7,9,20]→[7,9,20].
  Step 3: upper.size(3) > lower.size(2) → pop 7, push to lower. 2 ops. lower=[7,5,1], upper=[9,20].
  Total: 5 ops.
```

**Q6. What is the "alternative insertion" approach (decide heap before pushing), and how does it compare to the three-step approach?**

A: The alternative: decide which heap to push to based on the new element's relationship to the boundary, then only rebalance sizes. Push to lower if `num ≤ lower.top` (or upper is empty); push to upper otherwise. Then fix sizes with one rebalance step. This eliminates Step 2 (order fix) entirely — since the push decision already maintains order — reducing the maximum operations from 5 to 3 (1 push + 0 or 2 for size rebalance). Both approaches are O(log n); the alternative has a better constant factor. The tradeoff: the alternative requires careful null-handling for the empty-heap case and is slightly more complex to reason about. Both are correct and acceptable in interviews.

```js
// Alternative approach: decide before pushing
addNum(num) {
  // Push to the heap that "owns" this number
  if (this.upper.size() === 0 || num > this.upper.peek()) {
    this.upper.push(num);
  } else {
    this.lower.push(num);
  }

  // Fix sizes only — order is maintained by the push decision
  if (this.upper.size() > this.lower.size() + 1) {
    this.lower.push(this.upper.pop()); // upper too big → move minimum of upper to lower
  } else if (this.lower.size() > this.upper.size() + 1) {
    this.upper.push(this.lower.pop()); // lower too big → move maximum of lower to upper
  }
}
// Max: 3 operations. Simpler size check. Requires null guard for upper.peek().
```

**Q7. What happens if the median is needed between elements that are equal (ties)?**

A: Ties are handled correctly without any special logic. Identical elements can exist in both heaps — the invariant `lower.top ≤ upper.top` still holds when `lower.top == upper.top` (the boundary is the tie value itself). For an even number of elements where both halves have the same maximum/minimum: median = `(lower.top + upper.top) / 2 = tieValue`. For an odd number with ties: median = `lower.top = tieValue`. No modification to the algorithm is needed.

```
Stream: [5, 5, 5]:
  add(5): lower=[5], upper=[]. median=5.
  add(5): lower=[5,5], upper=[]. Step 3: lower too big → push 5 to upper.
    lower=[5], upper=[5]. median=(5+5)/2=5. ✓
  add(5): lower=[5,5] (after push), upper=[5]. Step 2: lower.top(5)>upper.top(5)? NO.
    Step 3: lower.size(2) > upper.size(1)+1=2? No. OK.
    lower=[5,5], upper=[5]. median=lower.top=5. ✓
```

## Topic B: Lazy Deletion — The Sliding Window Extension

### Section B1: The Lazy Deletion Pattern

**Q8. What is lazy deletion, and why is it needed for Sliding Window Median?**

A: Standard heaps support O(log n) push and pop-minimum/maximum, but not O(log n) deletion of arbitrary elements. The sliding window median requires removing the element that just left the window — an arbitrary element at an unknown position in the heap. Lazy deletion defers this removal: instead of immediately removing the element from the heap, add it to an "invalid" map `{value → count of pending deletions}`. When the heap's top is polled, check whether it appears in the invalid map; if so, it was already "deleted" — discard it (decrement its count in the map) and check the next top. This "prune stale tops" operation runs whenever the heap top is needed: before `peek()`, before rebalancing comparisons.

The critical property: the effective size of a heap (number of logically valid elements) differs from its actual size (including invalidated elements). Size-based rebalancing must use effective sizes, not actual sizes.

```
Heap contains: [3, 5, 7, 9]. Window slides out 5.
  invalid = {5: 1}

getMedian():
  Prune lower heap's top: top = 9 (max-heap). invalid.has(9)? No → valid top.
  Prune upper heap's top: top = 3. invalid.has(3)? No → valid.

Later, heap needs to pop:
  pop() from lower (max-heap = [9,7,5,3]): top = 9. invalid.has(9)? No → pop 9.
  Next pop from lower: top = 7. invalid.has(7)? No → pop 7.
  Next pop from lower: top = 5. invalid.has(5)? count=1 → DISCARD (lazy delete). invalid.delete(5).
  Continue: top = 3 → pop 3.

The heap "forgets" about 5 only when it naturally floats to the top.
```

**Q9. How do you track effective heap sizes during lazy deletion for the sliding window?**

A: Maintain a separate `lowerSize` integer representing the number of *logically valid* elements in the lower heap. The actual heap size includes invalidated elements that haven't been pruned yet. When adding an element to the lower heap, `lowerSize++`. When an element that belongs to the lower heap is invalidated (window slides it out), `lowerSize--`. The upper heap's effective size is derived: `effectiveUpper = window_size - lowerSize` (since the window contains exactly k elements). Rebalancing compares `lowerSize` against the target split (⌊k/2⌋ for even k, ⌊k/2⌋+1 for odd k), not the raw heap sizes.

```
Window size k=5. Target split: lowerSize = 3 (ceil(5/2) = 3).

Heaps: lower(actual=[8,6,5,3,1]), upper(actual=[9,10]) with invalid={5:1,3:1}.
lowerSize = 3  (actual lower has 5 elements but 2 are invalid → 3 effective).

getMedian(): prune lower top:
  top=8 → valid. lower effective top = 8.
  prune upper top: 9 → valid. upper effective top = 9.
  lowerSize=3 (odd k target → median = lower.top = 8). ✓

Rebalance check: lowerSize(3) == target(3) → no rebalance needed.
```

**Q10. Why must the "prune stale tops" step happen BEFORE checking heap tops for rebalancing?**

A: Rebalancing decisions are based on comparing `lower.top` and `upper.top` (for order) and effective sizes (for balance). If the heap's actual top is an invalidated element, its value is meaningless — comparing it for order or using it as the median produces wrong results. Pruning must clear all invalidated tops before any comparison. Specifically: before Step 2 (order fix: "is lower.top > upper.top?"), prune both heaps' tops. Before `getMedian()`, prune both tops. Before any `pop()` that feeds into rebalancing, prune. The pruning itself is O(p) where p = number of consecutive invalid tops — amortized O(1) since each element is invalidated and pruned at most once.

## Topic C: Heap Scheduling & Greedy Patterns

### Section C1: The "Two-Priority-Queue" Greedy

**Q11. What is the "two-heap greedy" pattern (as in IPO), and how does it differ from the median two-heap?**

A: The median two-heap splits elements by value into two halves that must be balanced in size. The "two-heap greedy" (e.g., IPO) uses two heaps to separate elements by one attribute (e.g., affordability) while selecting by another attribute (e.g., profitability). The structure: a min-heap ordered by "eligibility threshold" holds all elements; when you become eligible for some elements (your capital grows), move all newly eligible elements from the min-heap to a max-heap ordered by "value gain." Then greedily select the max-value element. Repeat k times. This achieves: O(n log n) for initial sort/heapify + O(k log n) for k selections.

```
IPO pattern:
  capHeap  = min-heap by capital required    (all projects, unaffordable first)
  profHeap = max-heap by profit              (all affordable projects)

  for k rounds:
    move all capHeap entries with capital ≤ current_w to profHeap
    if profHeap empty: break (no affordable projects left)
    w += profHeap.pop()  (take the highest-profit affordable project)

The two heaps serve completely different roles:
  capHeap: "waiting room" — projects you can't yet afford
  profHeap: "selection pool" — projects currently affordable, sorted by value
```

**Q12. What is the "evict the worst to admit the better" greedy heap pattern (Course Schedule III)?**

A: When greedily building an optimal subset under a constraint, sometimes a new element cannot be added without violating the constraint — but it might be better to evict a previously admitted element and add the new one instead. Pattern: maintain a max-heap of the "worst quality metric" of admitted elements. When a new element can't be added (constraint violated), compare it against the heap's top (the worst admitted element). If the new element has a better quality metric: evict the heap top, admit the new element. Otherwise: skip the new element. This "swap the worst" technique appears in Course Schedule III (swap longest course), Minimum Cost to Hire k Workers, and many scheduling problems.

```
Course Schedule III:
  max-heap of durations of courses taken so far.
  totalTime = 0.

  for each (duration, deadline) sorted by deadline:
    totalTime += duration; heap.push(duration)
    if totalTime > deadline:
      totalTime -= heap.pop()  // evict the longest course taken — best gives the most slack
      // Note: if new course IS the longest, it gets evicted too (same effect as not adding it)
```

## Topic D: Cross-Topic & Interview-Style Questions

**Q13. "Describe the three failure modes if either the order or size invariant is broken."**

A:

**Broken order (lower.top > upper.top)**: the heaps don't represent lower/upper halves. The median formula `(lower.top + upper.top)/2` returns the average of a lower-half minimum and upper-half maximum — not the true median. Example: lower=[9], upper=[3] → formula gives 6 but true median of {3, 9} is 6 by accident; for {3, 9, 15}: lower=[9, 3], upper=[15] → median=9 ✓, but lower=[15, 3], upper=[9] → formula gives 15 ✗.

**Broken size (lower too large by 2+)**: the lower heap contains elements that should be in the median zone or upper zone. Lower.top is too deep into the lower half — it's not the median. Example: lower=[7,5,3,1], upper=[9] → lower.top=7 reported as median for n=5 elements, but true median of [1,3,5,7,9] is 5 ✗.

**Broken size (upper too large)**: upper.top is the lower of the two medians — should be in lower's top. `lower.top` as returned is a below-median element. Example: lower=[3,1], upper=[5,7,9] for n=5 → lower.top=3 but true median is 5 ✗.

**Q14. "How does the static 'Median of Two Sorted Arrays' relate to the streaming problem, and why is it O(log(min(m,n))) instead of O(log n)?"**

A: The static problem (given two sorted arrays of sizes m and n, find the overall median) is a completely different algorithm — binary search on the partition point rather than heap maintenance. We binary search over all possible ways to split the *smaller* array into a left and right part; the corresponding split in the larger array is determined by the total-size constraint. At each candidate split, O(1) boundary comparisons check if the partition is valid. O(log(min(m,n))) — we binary search the smaller array's indices, which range from 0 to min(m,n). The streaming problem cannot use this technique because data arrives online; the static approach requires knowing both arrays in advance.

**Q15. "When would you choose a sorted structure (e.g., a balanced BST or sorted array with binary search) over two heaps for median?"**

A: Two heaps win when: (1) data arrives dynamically (streaming); (2) only the median is needed, not arbitrary percentile queries; (3) simpler implementation is preferred. A sorted structure (e.g., a self-balancing BST like a sorted array with `bisect.insort` in Python, or a policy-based tree in C++) wins when: (1) you need arbitrary-percentile queries, not just the median — a single traversal pointer in the BST answers any percentile; (2) you need rank queries ("how many elements are ≤ x?"); (3) you need to remove arbitrary elements efficiently (BST: O(log n); lazy deletion for heaps has amortized overhead). In JavaScript, the two-heap approach is strongly preferred since no native balanced BST is available.

**Q16. "Why does the sliding window median require O(n log k) time — why can't it be done in O(n)?"**

A: Each of the n window positions requires at least one heap insertion and one heap deletion. Both operations are Ω(log k) for a k-element heap — no heap structure can insert or delete arbitrary elements in sublinear time. An O(n log k) lower bound holds for comparison-based sliding window median. Some approximate solutions (e.g., reservoir sampling) achieve O(n) but do not return exact medians. For the exact problem: O(n log k) with two heaps + lazy deletion is optimal among comparison-based approaches.

**Q17. "In one sentence each, state the invariant and the key implementation detail for each problem in this document."**

A:
- **Find Median from Data Stream**: lower (max-heap) holds ≤ median, upper (min-heap) holds ≥ median; sizes differ by at most 1; order-fix precedes size-fix in addNum.
- **Sliding Window Median**: same two-heap split plus a lazy-deletion invalid-map; effective sizes (not raw sizes) govern rebalancing; both heap tops are pruned before any comparison.
- **IPO**: a min-heap by required capital holds unaffordable projects; a max-heap by profit holds affordable ones; at each round, drain newly affordable into the profit heap and greedily take the top.
- **Median of Two Sorted Arrays**: binary search on the partition of the smaller array; the partition point in the larger array is derived; O(1) boundary comparisons validate each candidate partition.
- **Task Scheduler**: a max-heap by frequency schedules the most urgent task; a cooldown queue re-introduces tasks after n+1 time units; idle slots are filled when the heap is empty.
- **Course Schedule III**: a max-heap of durations of admitted courses enables O(log n) eviction of the longest course when a deadline constraint is violated by a new course.

**Q18. "What is the space complexity of the two-heap structure, and how does it change for the sliding window variant?"**

A: The standard two-heap for streaming median uses O(n) space — both heaps together hold all n elements seen so far. No element is ever discarded. The sliding window median uses O(k) effective space — only the k elements currently in the window are logically present — but due to lazy deletion, invalidated elements accumulate in the heap until they float to the top. In the worst case (every element is immediately invalidated upon entry), the actual heap size can reach O(n) even though only O(k) effective elements exist. The invalid map uses O(k) space — at most k elements per window can be pending deletion. Combined: O(n) worst-case actual heap size, O(k) invalid map, O(k) effective logical elements.

## MinHeap / MaxHeap Implementation Reference

All problems below use this MinHeap. A MaxHeap uses comparator `(a, b) => b - a`.

```js
class MinHeap {
  constructor(cmp = (a, b) => a - b) {
    this.h = [];
    this.cmp = cmp;
  }
  size()  { return this.h.length; }
  peek()  { return this.h[0]; }
  push(v) { this.h.push(v); this._up(this.h.length - 1); }
  pop() {
    if (this.h.length === 1) return this.h.pop();
    const top = this.h[0];
    this.h[0] = this.h.pop();
    this._down(0);
    return top;
  }
  _up(i) {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.cmp(this.h[i], this.h[p]) < 0) {
        [this.h[i], this.h[p]] = [this.h[p], this.h[i]]; i = p;
      } else break;
    }
  }
  _down(i) {
    const n = this.h.length;
    while (true) {
      let s = i, l = 2*i+1, r = 2*i+2;
      if (l < n && this.cmp(this.h[l], this.h[s]) < 0) s = l;
      if (r < n && this.cmp(this.h[r], this.h[s]) < 0) s = r;
      if (s === i) break;
      [this.h[i], this.h[s]] = [this.h[s], this.h[i]]; i = s;
    }
  }
}

// MaxHeap: new MinHeap((a, b) => b - a)
// Custom comparator: new MinHeap((a, b) => a[0] - b[0])  ← sort by first element
```

## Problem 1 — Find Median from Data Stream

### Problem
Design a data structure that supports `addNum(num)` (add a number from the data stream to the data structure) and `findMedian()` (return the median of all elements so far). If the total number of elements is even, the median is the mean of the two middle values.

```
MedianFinder mf = new MedianFinder();
mf.addNum(1);    // stream = [1]
mf.findMedian(); // return 1.0
mf.addNum(2);    // stream = [1, 2]
mf.findMedian(); // return 1.5
mf.addNum(3);    // stream = [1, 2, 3]
mf.findMedian(); // return 2.0
```

### Pattern Recognition
Two-heap split — `lower` (max-heap) holds the smaller half, `upper` (min-heap) holds the larger half. The boundary between them gives the median in O(1). Both invariants (order and size) are maintained by a three-step protocol on every `addNum`.

### Key Insight
The median only depends on the top elements of each heap — O(1) access regardless of heap size. The three-step `addNum` maintains both invariants with at most 5 heap operations per call. Order fix must come before size fix to avoid moving the wrong element between heaps.

### Approach
`lower` = max-heap, `upper` = min-heap. `addNum(num)`: (1) push num to lower; (2) if `lower.peek() > upper.peek()` (and upper non-empty): move lower's top to upper; (3) if `lower.size > upper.size + 1`: move lower's top to upper; else if `upper.size > lower.size`: move upper's top to lower. `findMedian()`: if sizes equal → `(lower.peek() + upper.peek()) / 2`; else → `lower.peek()`.

### Solution

```js
class MedianFinder {
  constructor() {
    this.lower = new MinHeap((a, b) => b - a); // max-heap: lower half
    this.upper = new MinHeap((a, b) => a - b); // min-heap: upper half
  }

  addNum(num) {
    // Step 1: always push to lower (max-heap) first
    this.lower.push(num);

    // Step 2: fix ORDER — lower's max must not exceed upper's min
    if (this.upper.size() > 0 && this.lower.peek() > this.upper.peek()) {
      this.upper.push(this.lower.pop());
    }

    // Step 3: fix SIZE — lower holds the extra element for odd totals
    if (this.lower.size() > this.upper.size() + 1) {
      this.upper.push(this.lower.pop()); // lower too big → move top to upper
    } else if (this.upper.size() > this.lower.size()) {
      this.lower.push(this.upper.pop()); // upper too big → move top to lower
    }
    // Post-condition: |lower.size - upper.size| ≤ 1 AND lower.peek() ≤ upper.peek()
  }

  findMedian() {
    if (this.lower.size() === this.upper.size()) {
      return (this.lower.peek() + this.upper.peek()) / 2; // even count: average of tops
    }
    return this.lower.peek(); // odd count: lower holds the extra (middle) element
  }
}
```

### Dry Run

```
addNum(1):
  Step 1: push(1) to lower. lower=[1], upper=[].
  Step 2: upper empty → skip.
  Step 3: lower.size(1) > upper.size(0)+1? No. upper.size(0) > lower.size(1)? No.
  State: lower=[1], upper=[]. Sizes: 1, 0.

findMedian(): sizes differ → return lower.peek() = 1.0 ✓

addNum(2):
```

- Time: `addNum` O(log n) — at most 5 heap operations, each O(log n). `findMedian` O(1) — two peek calls.
- Space: O(n) — all n elements stored across both heaps.

### Edge Cases
- **Single element**: lower=[x], upper=[]. findMedian = x. No division by 2.
- **Two equal elements**: add(5), add(5): lower=[5], upper=[5]. findMedian = (5+5)/2 = 5.0. Correct.
- **Large positive and negative mix**: comparisons are integer-accurate; no special handling needed for negatives.

- "Can you implement this without two heaps using a single sorted data structure?" — Yes: a sorted list (Python `SortedList` from `sortedcontainers`) supports O(log n) insert and O(1) median by index. In JavaScript, no native sorted list exists.

## Problem 2 — Sliding Window Median

### Problem
Given a sliding window of size `k` moving across an integer array `nums`, return the median of each window position.

```
Input:  nums = [1,3,-1,-3,5,3,6,7], k = 3
Output: [1.0,-1.0,-1.0,3.0,5.0,6.0]
  // Windows: [1,3,-1]→1, [3,-1,-3]→-1, [-1,-3,5]→-1, [-3,5,3]→3, [5,3,6]→5, [3,6,7]→6

Input:  nums = [1,2,3,4,2,3,1,4,2], k = 3
Output: [2.0,3.0,3.0,3.0,2.0,3.0,2.0]
```

### Pattern Recognition
Two heaps + lazy deletion — same two-heap split as Problem 1, extended with an `invalid` map for O(log k) deferred removal of the outgoing window element. Effective size tracking drives rebalancing instead of raw heap sizes.

### Key Insight
When the window slides, one element must be logically "removed" from a heap without an O(n) scan. Lazy deletion marks it invalid in a map; the actual heap removal is deferred until the invalid element naturally floats to a heap top. `lowerSize` tracks the lower heap's *effective* count — this, not the raw heap size, drives all rebalancing decisions.

### Approach
Maintain `lower` (max-heap), `upper` (min-heap), `invalid` map, `lowerSize` (effective count in lower). For each right index `i`:

**Add `nums[i]`**: if `nums[i] <= lower.peek()` (or lower empty): push to lower, `lowerSize++`; else push to upper. Then rebalance.

**If window is full (i >= k)**: the outgoing element is `nums[i-k]`. Mark `invalid[nums[i-k]]++`. If `nums[i-k] <= lower.peek()` (it was in lower): `lowerSize--`. Else it was in upper. Then rebalance.

**Rebalance**: while `lowerSize < ceil(k/2)`: prune upper top, move to lower, `lowerSize++`; while `lowerSize > ceil(k/2)`: prune lower top, move to upper, `lowerSize--`.

**Prune**: while heap top is in `invalid`, pop and decrement `invalid`.

**Get median**: prune both tops; if k odd → `lower.peek()`; else `(lower.peek() + upper.peek()) / 2`.

### Solution

```js
function medianSlidingWindow(nums, k) {
  const lower = new MinHeap((a, b) => b - a); // max-heap: lower half
  const upper = new MinHeap((a, b) => a - b); // min-heap: upper half
  const invalid = new Map();                   // value → count of pending removals
  let lowerSize = 0;                           // effective element count in lower
  const results = [];

  function prune(heap) {
    // Remove stale (invalidated) elements from the heap top
    while (heap.size() > 0 && (invalid.get(heap.peek()) ?? 0) > 0) {
      const val = heap.pop();
      invalid.set(val, invalid.get(val) - 1);
      if (invalid.get(val) === 0) invalid.delete(val);
    }
  }

  function rebalance() {
    const target = Math.ceil(k / 2); // lower should hold this many effective elements

    // Lower too small → move from upper to lower
    while (lowerSize < target) {
      prune(upper);
      lower.push(upper.pop());
      lowerSize++;
    }
    // Lower too big → move from lower to upper
    while (lowerSize > target) {
      prune(lower);
      upper.push(lower.pop());
      lowerSize--;
    }
  }

  function getMedian() {
    prune(lower);
    prune(upper);
    if (k % 2 === 1) return lower.peek();
    return (lower.peek() + upper.peek()) / 2;
  }

  for (let i = 0; i < nums.length; i++) {
    // Add incoming element to the appropriate heap
    const num = nums[i];
    if (lower.size() === 0 || num <= lower.peek()) {
      lower.push(num);
      lowerSize++;
    } else {
      upper.push(num);
    }

    // Remove outgoing element (left side of window)
    if (i >= k) {
      const out = nums[i - k];
      invalid.set(out, (invalid.get(out) ?? 0) + 1);

      // Determine which heap the outgoing element logically belonged to
      // Prune lower top first so lower.peek() is valid for comparison
      prune(lower);
      if (lower.size() > 0 && out <= lower.peek()) {
        lowerSize--; // outgoing element was in lower (or at the boundary)
      }
      // else: outgoing element was in upper (no lowerSize change)
    }

    // Rebalance to maintain lowerSize = ceil(k/2)
    rebalance();

    // Record median once the first full window is formed
    if (i >= k - 1) {
      results.push(getMedian());
    }
  }

  return results;
}
```

## Problem 3 — IPO (Maximize Capital)

### Problem
Given `n` projects with `profits[i]` and `capital[i]` (minimum capital required to start), initial capital `w`, and the ability to do at most `k` projects, return the maximized capital after at most `k` projects. Finishing a project adds its profit to your capital.

```
Input:  k=2, w=0, profits=[1,2,3], capital=[0,1,1]
Output: 4    // take project 0 (profit=1, capital→1), then take project 2 (profit=3, capital→4)

Input:  k=3, w=0, profits=[1,2,3], capital=[0,1,2]
Output: 6    // take all three in order: 0→1→2
```

### Pattern Recognition
Two-heap greedy — a min-heap by required capital holds all projects; a max-heap by profit holds currently affordable ones. At each of the k rounds, drain newly affordable projects into the profit heap and take the most profitable one.

### Key Insight
The greedy choice is: among all projects you can afford right now, take the one with the highest profit. This greedy is optimal because taking the highest-profit affordable project maximizes your capital after each step, which only expands the set of affordable future projects. The two heaps enable O(log n) per round: the capital min-heap efficiently surfaces newly affordable projects, and the profit max-heap efficiently returns the best available.

### Approach
Push all projects as `[capital, profit]` into `capHeap` (min-heap by capital). Repeat k times: pop all `capHeap` entries with `capital <= w` into `profHeap` (max-heap by profit); if `profHeap` empty, break (no affordable project); `w += profHeap.pop()`. Return `w`.

### Solution

```js
function findMaximizedCapital(k, w, profits, capital) {
  // Min-heap ordered by capital required: surfaces cheapest projects first
  const capHeap = new MinHeap((a, b) => a[0] - b[0]);

  // Max-heap ordered by profit: surfaces most profitable affordable project
  const profHeap = new MinHeap((a, b) => b[1] - a[1]);

  // Load all projects into the capital heap
  for (let i = 0; i < profits.length; i++) {
    capHeap.push([capital[i], profits[i]]);
  }

  for (let round = 0; round < k; round++) {
    // Unlock all projects now affordable with current capital w
    while (capHeap.size() > 0 && capHeap.peek()[0] <= w) {
      profHeap.push(capHeap.pop()); // [capital, profit] — comparator uses profit for profHeap
    }

    if (profHeap.size() === 0) break; // no affordable project exists — stop early

    // Greedily take the highest-profit affordable project
    w += profHeap.pop()[1]; // [1] is the profit field
  }

  return w;
}
```

### Complexity
- Time: O(n log n) to build `capHeap` + O(k log n) for k rounds (each round: drain O(n) projects from capHeap amortized over all rounds total = O(n log n), take one from profHeap = O(log n) per round). Total: O(n log n + k log n) = O((n+k) log n).
- Space: O(n) — both heaps together hold all n projects.

### Edge Cases
- **k = 0**: loop never executes. Return initial w.
- **w = 0, all projects require capital > 0**: capHeap drains nothing in Round 1; profHeap empty → break immediately. Return w = 0.
- **All projects affordable from the start**: all projects drain into profHeap on Round 1. Subsequent rounds just pop the most profitable. Effectively: sort by profit descending, take top k.
- **k > n**: at most n projects can be taken. If k > n, the loop runs at most n effective rounds (capHeap empties, then profHeap empties).

### Follow-up Questions
- "Prove the greedy is optimal?" — Exchange argument: suppose an optimal solution at some step takes project A while we take B (higher profit, both affordable). Swap B for A in the optimal: total capital after this step is at least as high (B profit ≥ A profit), and everything after is at least as good (more capital = more options). Induction gives greedy is optimal.
- "What if you can redo projects?" — Each project can be taken multiple times. The greedy still applies: greedily take the highest-profit affordable project at each step. The only change: don't remove projects from the heap after taking them (or allow duplicates).

## Problem 4 — Find Median of Two Sorted Arrays

### Problem
Given two sorted arrays `nums1` and `nums2` of sizes `m` and `n`, return the median of the combined sorted array. Must run in O(log(m + n)) time.

```
Input:  nums1 = [1,3], nums2 = [2]           → Output: 2.0
Input:  nums1 = [1,2], nums2 = [3,4]         → Output: 2.5
Input:  nums1 = [],    nums2 = [1]            → Output: 1.0
```

### Pattern Recognition
Binary search on partition — binary search over all possible splits of the smaller array; the corresponding split in the larger array is determined by the total size. Check O(1) boundary conditions to validate each partition candidate.

### Key Insight
The median partitions the combined array into two equal halves (or one element more in the left for odd total). We need to find a partition `(i, j)` — `i` elements from `nums1` in the left half, `j = half - i` elements from `nums2` — such that `max(left) ≤ min(right)`. Binary search on `i` (from 0 to m). The partition is valid when `nums1[i-1] ≤ nums2[j]` AND `nums2[j-1] ≤ nums1[i]`. This is O(log m) where m = min(|nums1|, |nums2|).

### Approach
Ensure `nums1` is the smaller array (swap if needed). Binary search `i` in `[0, m]`. For each `i`: `j = half - i`. Check boundary conditions with sentinel ±Infinity for out-of-bounds. If `nums1[i-1] > nums2[j]`: `hi = i - 1` (i too large). If `nums2[j-1] > nums1[i]`: `lo = i + 1` (i too small). Else: valid partition → compute median from the four boundary elements.

### Solution

```js
function findMedianSortedArrays(nums1, nums2) {
  // Ensure nums1 is the smaller array for binary search efficiency
  if (nums1.length > nums2.length) return findMedianSortedArrays(nums2, nums1);

  const m = nums1.length, n = nums2.length;
  const half = Math.floor((m + n + 1) / 2); // size of the left combined half

  let lo = 0, hi = m; // binary search: i = number of nums1 elements in left half

  while (lo <= hi) {
    const i = Math.floor((lo + hi) / 2); // elements from nums1 in left half
    const j = half - i;                   // elements from nums2 in left half

    // Boundary values with sentinels for out-of-bounds
    const nums1Left  = i === 0 ? -Infinity : nums1[i - 1];
    const nums1Right = i === m ?  Infinity : nums1[i];
    const nums2Left  = j === 0 ? -Infinity : nums2[j - 1];
    const nums2Right = j === n ?  Infinity : nums2[j];

    if (nums1Left > nums2Right) {
      // nums1's left part is too large → shrink i
      hi = i - 1;
    } else if (nums2Left > nums1Right) {
      // nums2's left part is too large → grow i (take more from nums1)
      lo = i + 1;
    } else {
      // Valid partition found: max(left) ≤ min(right)
      const maxLeft  = Math.max(nums1Left, nums2Left);
      const minRight = Math.min(nums1Right, nums2Right);

      if ((m + n) % 2 === 1) return maxLeft;            // odd total: median = max of left half
      return (maxLeft + minRight) / 2;                   // even total: average of boundary elements
    }
  }
}
```

- **All of nums1 < all of nums2**: partition at i=m (all of nums1 in left half). The search finds this because `nums2Left` will always exceed `nums1Right` until i=m.
- **Overlapping arrays**: binary search correctly navigates to the valid partition regardless of element distribution.
- **Odd vs even total**: the formula `half = floor((m+n+1)/2)` ensures the left half has one extra element for odd totals — `maxLeft` is the median. For even totals, `(maxLeft + minRight)/2`.

### Follow-up Questions
- "Why binary search on the smaller array?" — Binary search on an array of size m takes O(log m). Choosing m = min(|nums1|, |nums2|) minimizes this. Both give correct results, but smaller is faster.
- "Generalize to kth element of two sorted arrays?" — Binary search on which array provides the kth element's left boundary. More complex indexing but same O(log(min(m,n))) time.

## Problem 5 — Task Scheduler

### Problem
Given a list of CPU tasks (each letter A–Z) and a cooldown period `n`, return the minimum number of intervals the CPU will take to finish all tasks. Between two same tasks there must be at least `n` intervals.

```
Input:  tasks = ["A","A","A","B","B","B"], n = 2
Output: 8    // A→B→idle→A→B→idle→A→B

Input:  tasks = ["A","A","A","B","B","B"], n = 0
Output: 6    // Any order works with no cooldown

Input:  tasks = ["A","A","A","A","A","A","B","C","D","E","F","G"], n = 2
Output: 16
```

### Pattern Recognition
Greedy + max-heap + cooldown queue — at each time slot, schedule the most frequent available task (max-heap); put it on cooldown for n intervals (queue stores `[frequency-1, availableTime]`); reintroduce it to the heap when its cooldown expires.

### Key Insight
Always scheduling the most frequent task minimizes idle time — the more frequent a task is, the higher the cost of deferring it. A max-heap by frequency provides the greedy choice in O(log 26) = O(1). A queue models the cooldown: entries are reintroduced to the heap in FIFO order (the first task to enter the queue has the earliest available time). When the heap is empty but the queue is non-empty, the CPU is idle.

### Approach
Build a frequency map; push all non-zero frequencies to a max-heap. Initialize `time = 0`, `cooldown = []` queue. While heap or queue is non-empty: `time++`. If queue front is available (`cooldown[0][1] <= time`): push its frequency back to heap. If heap non-empty: pop the most frequent task; if `frequency > 1`, push `[frequency-1, time+n+1]` to cooldown. Else: CPU is idle (counted by `time++`).

### Solution

```js
function leastInterval(tasks, n) {
  // Frequency map → max-heap by frequency
  const freq = new Map();
  for (const t of tasks) freq.set(t, (freq.get(t) ?? 0) + 1);

  const heap = new MinHeap((a, b) => b - a); // max-heap by frequency
  for (const cnt of freq.values()) heap.push(cnt);

  let time = 0;
  const cooldown = []; // queue: [remainingFreq, availableAtTime]

  while (heap.size() > 0 || cooldown.length > 0) {
    time++;

    // Re-introduce any task whose cooldown has expired
    if (cooldown.length > 0 && cooldown[0][1] <= time) {
      heap.push(cooldown.shift()[0]); // move back to available heap
    }

    if (heap.size() > 0) {
      const cnt = heap.pop(); // schedule the most frequent task
      if (cnt > 1) {
        cooldown.push([cnt - 1, time + n + 1]); // re-available after cooldown
      }
    }
    // else: CPU is idle this slot (time already incremented)
  }

  return time;
}
```

### Dry Run

### Complexity
- Time: O(T × log 26) = O(T) where T = total intervals (bounded by `tasks.length + idle slots`). The log factor is O(log 26) = O(1) since at most 26 distinct tasks.
- Space: O(26) = O(1) — heap and cooldown queue both bounded by the alphabet size.

### Edge Cases
- **n = 0**: no cooldown. The CPU runs without idle slots. Total time = `tasks.length`. Heap empties immediately after each pop without pushing to cooldown.
- **All tasks are the same**: only one type with frequency f. Sequence: A, idle×n, A, idle×n, ..., A. Total = `(f-1) × (n+1) + 1`. The heap always has one element, cooldown has at most one entry.
- **Formula shortcut**: total time = `max(tasks.length, (maxFreq-1)×(n+1) + countOfMaxFreq)`. Demonstrates the math behind the greedy without simulation. Both approaches give the same answer.

- "Tasks have different durations?" — Each task duration D means the cooldown must wait until `time + D + n`. Adjust the `availableAtTime` formula accordingly.

## Problem 6 — Course Schedule III

### Problem
There are `n` online courses. Each course `i` has a duration `t[i]` days and a deadline `d[i]` (must be finished no later than `d[i]`). Starting from day 1, you can only take one course at a time. Return the maximum number of courses you can take.

```
Input:  courses = [[100,200],[200,1300],[1000,1250],[2000,3200]]
Output: 3     // Take courses 1,2,4 (deadlines 200,1300,3200) with durations 100,200,2000

Input:  courses = [[1,2]]    → Output: 1
Input:  courses = [[3,2],[4,3]] → Output: 0  (both deadlines impossible)
```

### Pattern Recognition
Greedy "evict the worst to admit the better" — sort by deadline; greedily add courses; if the total duration exceeds a deadline, evict the longest-duration course taken so far (max-heap). This swap always improves the schedule: the evicted course had the largest duration cost, so removing it frees the most time.

### Key Insight
Sorting by deadline ensures we never add a course that "reaches into the future" of earlier deadlines — a course with a later deadline never conflicts with an earlier deadline. The greedy choice when the constraint is violated: evict the longest course taken so far. This is optimal because: (1) we still keep the same number of courses (swapped one for one); (2) the evicted course had the highest duration cost — removing it minimally impacts our ability to take future courses; (3) if the new course is the longest, it effectively evicts itself (no change to total duration or count — correct, since the new course was too long anyway).

### Approach
Sort courses by deadline. Initialize `maxHeap` (by duration), `totalDuration = 0`. For each `[t, d]`: `totalDuration += t`, push `t` to maxHeap. If `totalDuration > d`: `totalDuration -= maxHeap.pop()` (evict the longest course — possibly the one just added). Return `maxHeap.size()`.

### Solution

```js
function scheduleCourse(courses) {
  // Sort by deadline — earliest deadlines processed first
  courses.sort((a, b) => a[1] - b[1]);

  const heap = new MinHeap((a, b) => b - a); // max-heap by duration
  let totalDuration = 0;

  for (const [t, d] of courses) {
    totalDuration += t;
    heap.push(t); // tentatively add this course

    // If the current schedule exceeds this course's deadline, evict the longest
    if (totalDuration > d) {
      totalDuration -= heap.pop(); // remove the costliest course taken so far
      // Note: if current course is the longest, it evicts itself — no net change
    }
  }

  return heap.size(); // each remaining entry in the heap represents a taken course
}
```

### Dry Run

```
courses = [[100,200],[200,1300],[1000,1250],[2000,3200]]
Sorted by deadline: [[100,200],[200,1300],[1000,1250],[2000,3200]] (already sorted).

[100,200]: total=100. heap=[100]. total(100) ≤ d(200) → OK.
  heap=[100], total=100. Courses taken: 1.

[200,1300]: total=300. heap=[200,100]. total(300) ≤ d(1300) → OK.
  heap=[200,100], total=300. Courses taken: 2.

[1000,1250]: total=1300. heap=[1000,100,200]. total(1300) ≤ d(1250)? NO (1300>1250).
  Evict max: heap.pop()=1000. total=1300-1000=300. heap=[200,100].
  heap=[200,100], total=300. Courses taken still 2 (evicted the 1000-duration course).
  Note: the 1000-duration course evicted itself (it was the longest — adding it exceeded the deadline).

  heap=[2000,200,100], total=2300. Courses taken: 3.

```

### Complexity
- Time: O(n log n) for sorting + O(n log n) for n heap operations (each course added and possibly removed = O(log n)). Total: O(n log n).
- Space: O(n) — heap holds at most n course durations.

### Edge Cases
- **Impossible course** (duration > deadline): immediately after adding it, `totalDuration > d`. It will be evicted (it's the longest duration just added, since its duration = t > d ≥ all previously taken courses' end times — wait, this isn't always true). If it's not the longest, another course is evicted. Either way, the heap size stays the same — this course is effectively skipped in the schedule.
- **All courses infeasible**: every course violates its own deadline (`t > d`). Each is immediately evicted. heap.size() = 0 at the end.
- **Greedy optimality with the swap**: Suppose we have courses A (already in heap) and B (new, causing violation). If duration(B) >= duration(A): we evict B (itself). We keep the same set. Correct — B doesn't fit. If duration(B) < duration(A): we evict A. Now we have B instead of A. total decreases by duration(A) - duration(B) ≥ 0 → constraint more easily satisfied for future courses. Optimal swap. ✓

### Follow-up Questions
- "What if you can take courses in any order (deadline is absolute)?" — Same problem. The greedy's correctness doesn't depend on the specific order courses are taken — only that the total duration of chosen courses fits within the latest deadline.
- "Return the actual course schedule?" — Store course indices alongside durations in the heap. When the heap is returned, extract the course indices.

```
What structure does the problem need?
│
├── STREAMING MEDIAN (elements arrive one at a time, find median after each)?
│   └── Two-heap: lower (max-heap) + upper (min-heap).
│       addNum: push to lower → fix order (lower.top > upper.top?) → fix size.
│       Order fix BEFORE size fix — mandatory.
│       findMedian: sizes equal → (lower.top+upper.top)/2; else → lower.top.
│
├── SLIDING WINDOW MEDIAN (fixed-size window slides, find median per position)?
│   └── Two-heap + lazy deletion.
│       invalid map: deferred removal of outgoing elements.
│       lowerSize: effective (not raw) count in lower heap.
│       Prune stale tops BEFORE any peek/compare/rebalance operation.
│       rebalance targets lowerSize = ceil(k/2).
│
├── GREEDY SELECTION WITH TWO CONFLICTING PRIORITIES?
│   ├── "Affordable now, highest value later" (IPO) →
│   │   min-heap by threshold (gates access) + max-heap by value (drives selection).
│   │   Drain eligible from gate-heap to value-heap each round; pop max value.
│   │
│   └── "Evict worst to admit better" (Course Schedule III) →
│       Sort by constraint. max-heap of quality metric for eviction.
│       On constraint violation: pop the worst (costliest/lowest-value) admitted item.
│       New item may evict itself (it IS the worst) — still correct.
│
├── STATIC MEDIAN OF TWO SORTED ARRAYS?
│   └── Binary search on partition of smaller array.
│       half = floor((m+n+1)/2). Binary search i in [0, m].

│       Return maxLeft (odd n) or (maxLeft+minRight)/2 (even n).
│
├── TASK SCHEDULING WITH COOLDOWN?
│   └── max-heap by frequency + cooldown queue.
│       Greedily schedule the most frequent available task.
│       Cooldown queue re-introduces tasks at availableTime = currentTime + n + 1.
│       When heap empty but queue non-empty: CPU idles.
│
└── KEY DISTINCTIONS:
    Two-heap median:       ORDER fix → SIZE fix (both invariants, this order)
    Lazy deletion:         Prune BEFORE compare. lowerSize = effective count.
    IPO:                   Two separate heaps with different sort keys.
    Course schedule:       Single max-heap for eviction; sort input by deadline first.
```

## Common Bugs Checklist

Before submitting any two-heap or heap-scheduling solution, verify:

1. **Two-heap addNum: order fix BEFORE size fix?** — Fixing sizes before order can move a non-boundary element between heaps, breaking the invariant. The order: (1) push to lower, (2) if `lower.top > upper.top`, move lower's top to upper, (3) then rebalance sizes. Never swap steps 2 and 3.

2. **Two-heap addNum: checking `upper.size() > 0` before comparing tops?** — `upper.peek()` on an empty heap is undefined/crashes. Step 2 must guard: `if (upper.size() > 0 && lower.peek() > upper.peek())`. Missing this causes a crash on the first `addNum` call.

3. **Two-heap findMedian: using `lower.size() > upper.size()` not `!==` for the odd-count branch?** — If a bug elsewhere allows sizes to differ by 2, using `!== ` would select `lower.peek()` when the true median is elsewhere. Use `lower.size() > upper.size()` to explicitly confirm lower holds the extra element.

4. **Sliding window: pruning AFTER comparison instead of before?** — `lower.peek()` returns the stale/invalidated top, which may be the element we just marked invalid. Comparing an invalid top to the outgoing element to determine which heap it was in produces wrong lowerSize adjustments. Prune before any comparison that depends on the heap top.

5. **Sliding window: tracking `lowerSize` (effective) not `lower.size()` (raw)?** — Raw heap size includes invalidated elements that haven't been pruned yet. Using `lower.size()` for rebalancing triggers spurious moves because the heap appears larger than it logically is. Always rebalance based on `lowerSize`.

6. **Sliding window: determining which heap the outgoing element belongs to?** — The check `out <= lower.peek()` uses the current valid lower top. If the outgoing element IS the lower top (currently at the top and about to be invalidated), pruning first changes `lower.peek()` — the check fails even though the element WAS in lower. Perform the heap-membership check BEFORE pruning the lower top.

7. **IPO: comparing `capHeap.peek()[0]` (capital) not `[1]` (profit)?** — The capHeap is ordered by capital required (index 0). Draining condition: `capHeap.peek()[0] <= w`. Adding to profHeap: push the whole `[capital, profit]` pair (profHeap's comparator uses index 1 for profit ordering). Confusing indices produces wrong heap ordering.

8. **IPO: not breaking early when profHeap is empty?** — If all remaining projects require more capital than you'll ever have (profHeap stays empty for the rest of the k rounds), the loop must break: `if (profHeap.size() === 0) break`. Without this, the loop runs k times doing nothing — correct but wasteful, and could be infinite if k is large.

9. **Task Scheduler: cooldown condition `cooldown[0][1] <= time` not `<`?** — A task with `availableAt = time + n + 1` becomes re-available when `currentTime >= availableAt`. Using `< time` instead of `<= time` delays re-introduction by one slot, causing one extra idle or wrong scheduling.

10. **Course Schedule III: not sorting by deadline before greedy?** — The greedy's correctness relies on processing courses in deadline order. Without sorting, a course with a far-future deadline could be processed before one with a nearby deadline, making valid schedules appear to violate constraints.

11. **Course Schedule III: forgetting that evicting the heap top may evict the just-added course itself?** — When `totalDuration > d` and the just-added course has the largest duration (which it may, especially if it's much longer than previous courses), `heap.pop()` removes it. `totalDuration` reverts to what it was before adding this course. The heap size stays constant. This is correct — the course can't fit — but some implementations try to avoid adding it in the first place (incorrect: you must add-then-possibly-evict to handle the case where it displaces a worse previously-taken course).

12. **Median of two sorted arrays: using `Math.floor((lo+hi)/2)` not `lo + Math.floor((hi-lo)/2)` (integer overflow)?** — For JavaScript with 64-bit floating-point numbers, overflow is unlikely, but in languages with 32-bit integers (Java, C++), `(lo + hi) / 2` overflows for large inputs. The safe formula: `lo + Math.floor((hi - lo) / 2)` prevents overflow regardless of language.

**Final Tip:** At the 5 YOE level, the decisive signal for two-heap problems is articulating **both invariants and their maintenance order** in one sentence before writing any code: "I'll maintain a max-heap for the lower half and a min-heap for the upper half, with lower.top ≤ upper.top (order) and sizes differing by at most 1 (balance); in addNum I fix order before size because fixing size first can propagate a mis-categorized element — the order fix moves the boundary element to its correct half, after which the size fix always moves the correct new boundary." For the sliding window variant, add: "I track lowerSize separately from the raw heap size because lazy deletion means the heap contains stale elements; I prune stale tops before any comparison that reads heap.peek()." Stating both invariants, their maintenance order, and the one gotcha (order before size; prune before peek) is the mark of someone who has derived the algorithm rather than memorized it.
