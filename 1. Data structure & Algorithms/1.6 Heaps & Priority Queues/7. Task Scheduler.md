## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is the task scheduler problem class?**
A: The task scheduler problem class covers problems where you must sequence a set of tasks under one or more constraints — cooldown periods between identical tasks, ordering dependencies, deadlines, processing times, or resource limits — and optimize a goal: minimize total time, maximize throughput, minimize idle time, or meet all deadlines. The unifying tool is a **max-heap (priority queue)** that always surfaces the highest-priority task greedily, combined with a cooldown queue (usually a regular queue or sorted structure) that tracks when tasks become eligible again. The class spans from pure scheduling (LeetCode 621) to simulation-heavy variants with timestamps and dependencies.

**Q2. Why is a max-heap the natural data structure for task scheduling?**
A: Task scheduling problems almost always involve a greedy strategy: at each time slot, execute the task that is most beneficial to do right now — typically the most frequent remaining task (to minimize future idle time), the highest-priority task (to meet deadlines), or the task with the earliest deadline. A max-heap provides O(log k) access to this "best" task at any moment, where k is the number of distinct task types. Without a heap, finding the best task requires O(k) linear scan per time slot — degrading the overall solution from O(n log k) to O(n × k).

**Q3. What is the "cooldown" constraint and why does it complicate scheduling?**
A: A cooldown of `n` means the same task type cannot be executed again for at least `n` time slots after its last execution. This prevents simply running the most frequent task back-to-back. The complication: the globally optimal task (most frequent) may be on cooldown, forcing you to choose a suboptimal task or insert an idle slot. Managing cooldowns requires tracking when each task type becomes available again — typically with a "waiting queue" that holds (task_frequency, next_available_time) pairs and re-enqueues tasks into the max-heap when their cooldown expires.

**Q4. What are the two main algorithmic approaches to the basic task scheduler problem?**
A:
- **Simulation with max-heap + cooldown queue**: Step through time slot by slot. At each slot, extract the highest-frequency available task from the max-heap, execute it, reduce its count, and push it to a cooldown queue with its next-available time. When the cooldown queue's front becomes available, push it back to the heap. Count idle slots when the heap is empty but the cooldown queue is non-empty. Time: O(n log k), Space: O(k).

- **Mathematical formula**: Derive the answer directly from the frequency counts without simulation. The minimum time = `max(total_tasks, (max_freq - 1) * (n + 1) + count_of_max_freq)`. The formula computes the "frame" structure of the schedule: `(max_freq - 1)` full frames of size `(n + 1)` each, plus a final partial frame. Time: O(n), Space: O(1) (after counting frequencies). This is more elegant but harder to generalize to variants.

**Q5. Why does the greedy "always run the most frequent task" strategy minimize total time?**
A: The intuition: idle slots are wasted time. Every idle slot occurs because the most constrained tasks (those with the highest remaining counts) are all on cooldown simultaneously. By always running the highest-frequency task when available, we reduce the count of the most constrained task as fast as possible — minimizing the number of future idle slots that task forces. If we instead ran a less frequent task when the most frequent was available, we'd defer reducing the most constrained task's count, potentially creating more idle slots later. More formally: this is a greedy exchange argument — any schedule that doesn't prioritize the most frequent available task can be improved by swapping task executions to match the greedy order, without increasing total time.

### Section 2: The Simulation Approach — Deep Dive

**Q6. Describe the simulation approach step by step.**
A: The simulation models time explicitly, processing one time slot per iteration:

```
1. Count frequencies of all task types.
2. Build a max-heap of frequencies.
3. Initialize a cooldown queue (FIFO) of (frequency, next_available_time) pairs.
4. Set time = 0.
5. While heap is not empty OR cooldown queue is not empty:
   a. If cooldown queue's front is ready (front.next_available_time <= time):
      - Pop from cooldown queue, re-enqueue its frequency to the max-heap.
   b. If heap is not empty:
      - Extract max frequency from heap.
      - Execute the task (time += 1).
      - Decrement frequency; if > 0, push (freq-1, time + n) to cooldown queue.
   c. Else (heap empty but tasks on cooldown):
      - Idle (time += 1).
6. Return time.
```

**Q7. What does the cooldown queue store, and why is a regular queue sufficient for it (not another heap)?**
A: The cooldown queue stores `(remaining_frequency, next_available_time)` pairs for tasks that have been executed but are still in their cooldown window. A regular FIFO queue is sufficient — not a priority queue — because tasks enter the cooldown queue in the order they were executed (time order), and their next-available times are non-decreasing (each task's cooldown expires `n` time units after it was run, and time only moves forward). The queue front is always the task with the earliest next-available time — no sorting needed. This is an important insight: the cooldown queue is ordered by time of entry, which corresponds to ordering by next-available time.

**Q9. How does the simulation handle the "idle" decision correctly?**
A: Idle occurs when the max-heap is empty but the cooldown queue is non-empty — there are tasks waiting but all are on cooldown. The simulation advances time by 1 (one idle slot) and loops back. On the next iteration, it checks if the cooldown queue's front has become ready (next_available_time ≤ new time) and re-enqueues it. A common optimization: instead of idling one step at a time, jump time directly to `cooldown_queue.front.next_available_time` when the heap is empty — this turns O(total_idle_time) idle steps into O(1) per gap.

**Q10. What is the "jump-to-next-available" optimization and when does it matter?**
A: When the heap is empty and the cooldown queue is non-empty, instead of incrementing time by 1 per idle slot, set `time = cooldown_queue.front.next_available_time` directly and continue. This skips idle slots in O(1) regardless of how many there are.

Why it matters: if `n` is large and task frequencies are low, there can be many consecutive idle slots. Without the optimization, the simulation runs in O(total_time) — which can be O(n × max_freq) in the worst case. With the optimization, the simulation runs in O(total_tasks × log k) — strictly proportional to actual work, not idle time.

In interviews, mentioning this optimization signals that you think about practical performance beyond asymptotic complexity.

### Section 3: The Mathematical Approach

**Q11. Derive the mathematical formula for minimum scheduling time.**
A: The formula is: `answer = max(total_tasks, (max_freq - 1) * (n + 1) + count_of_max_freq)`.

Derivation: Visualize the schedule as a grid of frames, each of width `n + 1`:

```
Frame structure for tasks=["A","A","A","B","B","B","C","C"], n=2:
(max_freq=3, tasks A,B,C)

Frame 1: [A, B, C]    ← n+1 = 3 slots
Frame 2: [A, B, C]
Frame 3: [A, B, _]    ← last frame: only max_freq tasks fit, rest are idle
```

- `(max_freq - 1)` complete frames, each requiring `n + 1` slots.
- Final partial frame: contains all tasks with the maximum frequency — `count_of_max_freq` slots.
- Minimum time from frame structure: `(max_freq - 1) * (n + 1) + count_of_max_freq`.

But: if there are so many distinct task types that they fill all frames without any idle slots, the total tasks themselves determine the answer. Hence the `max(...)`.

**Q12. When does the formula give `total_tasks` vs the frame formula?**
A: The frame formula gives the result when idle slots are necessary — when tasks can't be packed densely enough to fill every frame. This happens when `n` is large relative to the number of distinct task types. When `n = 0` (no cooldown), no idle slots are needed and the answer is simply `total_tasks`. When `n` is large and only a few distinct task types exist, the frame structure dominates and idle slots appear. The `max(...)` handles both cases: if enough distinct tasks exist to fill every frame slot, `total_tasks` wins; otherwise the frame formula wins.

**Q13. What are the limitations of the mathematical formula for interview variants?**
A: The formula is elegant but brittle — it only works for the simplest version of the problem (minimize total time, uniform task duration of 1, single processor, cooldown between same tasks). It breaks down when:
- Tasks have different processing times (weights).
- There are ordering dependencies between tasks.
- Deadlines must be met (or missed penalties apply).
- Multiple processors run tasks in parallel.
- The problem asks for the actual schedule (not just the time).

For all these variants, the simulation approach generalizes naturally. The formula is useful to quote as a sanity check or as the optimal solution for the base case, but simulation is the implementation skill interviewers actually test.

### Section 4: Variants & Extensions

**Q14. How does the problem change with multiple processors (CPUs)?**
A: With `p` processors and cooldown `n` per task type per processor: in each time slot, up to `p` tasks can run simultaneously (one per processor), subject to the cooldown constraint (same task can't run on any processor within `n` slots of its last run). The simulation extends naturally: in each time slot, extract up to `p` tasks from the max-heap (the p most frequent available tasks), execute them all, push them to the cooldown queue. Idle slots occur when fewer than `p` tasks are available. The formula also generalizes: `answer = max(total_tasks / p rounded up, (max_freq - 1) * (n + 1) / p ... )` — but this gets complex. Use simulation for multi-processor variants.

**Q15. How do you handle tasks with different processing times (weighted tasks)?**
A: The problem becomes a weighted job scheduling problem. The simple greedy "most frequent first" no longer applies because a less frequent task with a long processing time might block the schedule more than a frequent short task. For the single-processor case with deadlines, sort by deadline (EDF — Earliest Deadline First) or by processing time. For the case without deadlines, just minimize total weighted completion time: sort by processing time ascending (Shortest Job First — SJF). For the cooldown variant with weights, simulation is necessary: the max-heap orders by (remaining_count × processing_time) or a custom priority function.

**Q16. How do you handle task dependencies (topological ordering)?**
A: Tasks with dependencies form a Directed Acyclic Graph (DAG). A task can only be scheduled after all its prerequisites are done. Use a modified BFS (Kahn's algorithm for topological sort) where the queue is replaced by a max-heap ordered by task priority:
- Initialize the heap with all tasks that have in-degree 0 (no prerequisites).
- Extract the highest-priority task, execute it, decrement in-degrees of its dependents.
- When a dependent's in-degree reaches 0, enqueue it to the heap.
- This is "topological sort with priority" — O((V + E) log V).

**Q17. What is the "CPU Scheduling" problem variant with arrival times?**
A: Tasks arrive at different times and have a burst time (processing duration). Variants:
- **Shortest Job First (SJF)**: at each scheduling decision, run the shortest available job. Use a min-heap of (burst_time, task_id) for available tasks. When a task arrives, enqueue it. Preemptive SJF (SRTF — Shortest Remaining Time First) re-evaluates at every arrival.
- **Priority Scheduling**: tasks have explicit priorities. Max-heap of (priority, task_id). Tasks arriving later can preempt the current task if they have higher priority (preemptive variant).
- In all variants: maintain an event queue sorted by arrival time + a ready-queue heap sorted by the scheduling criterion.

**Q18. What is the "reorganize string" problem and how does it relate to task scheduling?**
A: "Reorganize string" asks: rearrange a string so that no two adjacent characters are the same. If impossible, return "". This is task scheduling with `n = 1` (cooldown of 1 between identical characters) and `total_time = string_length` (no idle allowed). The max-heap greedy applies: always place the most frequent remaining character that isn't the same as the just-placed character. If the most frequent character is the same as the last placed one, use the second most frequent instead.

The impossibility condition: if any character's frequency exceeds `(length + 1) / 2`, no valid arrangement exists (the character would need adjacent positions). This is the `(max_freq - 1) * 2 + 1 > length` check — directly from the scheduling formula with `n = 1`.

**Q19. How do you handle the "minimum number of machines" variant?**
A: Given a list of jobs with `[start, end]` times, find the minimum number of machines (processors) needed to run all jobs without conflict. This is an interval scheduling variant:
- Sort jobs by start time.
- Use a min-heap of end times of currently running jobs.
- For each new job: if the heap top (earliest ending running job) ends before the new job starts, pop it (machine is freed). Push the new job's end time.
- The heap size at any point = number of machines currently in use.
- Answer = maximum heap size over the entire process.

O(n log n) — sort + heap operations. This is the "meeting rooms II" problem reframed as machine allocation.

### Section 5: Complexity Analysis & Trade-offs

**Q20. Compare the simulation and mathematical approaches on time and space complexity.**
A:

| Approach         | Time             | Space   | Generalizes? | Gives actual schedule? |
|------------------|------------------|---------|--------------|------------------------|
| Simulation       | O(n log k)       | O(k)    | Yes          | Yes                    |
| Math formula     | O(n)             | O(1)*   | No           | No                     |

*O(k) to count frequencies, but O(1) for the formula itself given the counts.

`n` = total tasks, `k` = distinct task types (≤ 26 for letter tasks).

The simulation is O(n log k) because each of the n tasks is pushed and popped from the heap once (O(log k) each), and each re-enqueue from cooldown is O(log k). The mathematical formula scans all tasks once for frequencies (O(n)) and then computes in O(k) — effectively O(n).

**Q21. What is the worst-case time for the naive simulation (without the jump optimization) and when does it occur?**
A: Without the jump-to-next-available optimization, the simulation runs in O(total_time) where total_time = `(max_freq - 1) * (n + 1) + count_of_max_freq`. In the worst case (one task with frequency f and cooldown n): total_time = `(f - 1) * (n + 1) + 1` = O(f × n). If f and n are both large (e.g., f = 10^4, n = 10^4), this is O(10^8) operations — too slow. With the jump optimization: O(total_tasks × log k) = O(n log k), much better.

**Q22. When would you choose a different data structure over a heap for task scheduling?**
A: Three cases where heaps are not optimal:
- **Very few distinct task types (k is small)**: a sorted array or simple counting suffices. If k ≤ 26 (letter tasks), a bucket sort of frequencies + a simple scan beats the heap's log factor in practice (O(k) per slot vs O(log k), but k is constant).
- **Tasks have arrival times and deadlines with complex preemption**: a more sophisticated structure like a Fibonacci heap (O(1) amortized decrease-key) may be needed if decrease-key operations dominate. In practice, binary heaps are used because Fibonacci heaps have high constant factors.
- **Offline scheduling (all tasks known upfront, minimize makespan)**: dynamic programming or graph-based approaches may be optimal depending on the constraint structure. The heap-greedy works for the single-machine cooldown variant but not for all scheduling problems.

### Section 6: Scenario / Interview-Style Questions

**Q23. "The interviewer gives you task scheduler (LeetCode 621) and asks you to solve it. You give the simulation. They say 'can you do it in O(n) without simulation?' Walk through the formula."**
A: The formula approach:
1. Count frequencies of all task types → O(n).
2. Find max frequency `max_freq` and count how many tasks share it `count_max` → O(k).
3. Compute `frame_result = (max_freq - 1) * (n + 1) + count_max`.
4. Return `max(total_tasks, frame_result)`.

Explain the frame intuition: we build `(max_freq - 1)` complete frames of width `(n + 1)`. In each frame, the max-frequency tasks go first; remaining slots fill with other tasks or idle. The last partial frame contains only the max-frequency tasks. If we have enough tasks to fill every frame slot, idle disappears and the answer is just `total_tasks`.

Then offer: "The formula is elegant for this exact problem, but the simulation generalizes to weighted tasks, dependencies, and multiple processors — which is why I typically implement simulation and quote the formula as a sanity check."

**Q24. "Design a real-time job scheduler for a cloud service. Jobs arrive with a priority and must complete within a deadline. Processors are limited. How do you structure this?"**
A: Multi-component design:
1. **Arrival queue**: jobs arrive in a stream. An event loop or timer triggers scheduling decisions on each job arrival or completion.
2. **Ready queue (max-heap by priority)**: jobs that have arrived and are waiting for a processor. Priority = job priority field; tiebreak by earliest deadline.
3. **Running set**: currently executing jobs, one per processor. On completion, remove from running set and trigger a new scheduling decision.
4. **Deadline monitor**: a min-heap of (deadline, job_id) for running and waiting jobs. Periodically check if any job has missed its deadline — trigger an alert or preemption.
5. **Preemption policy**: if a new high-priority job arrives while all processors are busy, optionally preempt the lowest-priority running job (insert it back into the ready queue) and start the high-priority job.

This is essentially a priority-queue-driven event simulation — the core of every real operating system scheduler.

**Q25. "You have tasks with dependencies (DAG). Some tasks can run in parallel. You have k processors. Minimize total completion time." How do you approach this?"**
A: This is the "parallel task scheduling with dependencies" problem — a generalization of topological sort:
1. **Build the DAG** from dependency list. Compute in-degrees.
2. **Initialize max-heap** with all zero-in-degree tasks (ordered by task duration descending — longer tasks first to minimize makespan via critical path heuristics).
3. **Simulate time**: at each step, assign the top min(available_tasks, k) tasks to processors. Track their completion times.
4. **On task completion**: decrement in-degrees of dependents; add newly available tasks (in-degree 0) to the heap.
5. **Advance time** to the earliest completion time among running tasks.

Exact optimality for this problem is NP-hard in general (related to job shop scheduling). The greedy heap approach gives a good approximation. For the special case of unit-duration tasks with no priorities, it's solvable optimally in polynomial time.

**Q26. "A candidate implements task scheduler with a heap but gets wrong answers for n=0. What's the bug?"**
A: When `n = 0`, there's no cooldown — every task is always available. The cooldown queue is never populated (or always immediately ready), so the simulation degenerates to: extract max, decrement, re-enqueue immediately if count > 0. With n=0, tasks cycle through the heap many times. Common bugs:
- Forgetting to push a task with remaining count back to the heap (or pushing it with `next_available_time = current_time + 0 = current_time`, which means it's immediately available but the check `time >= next_available` might use `>` instead of `>=`, preventing re-enqueue).
- Off-by-one in the cooldown check: `time + n` vs `time + n + 1` vs `time + n - 1`. For n=0, the task should be re-available at `time + 1` (next slot), not `time + 0` (same slot — would cause infinite loop) and not `time + 2` (would introduce phantom idle).

Always trace through n=0 as the first edge case. Answer should be `total_tasks` exactly.

## Problem 1 — Task Scheduler (LeetCode 621)

### Problem
Given a list of tasks `tasks` (uppercase letters) and a non-negative cooldown `n`, return the minimum number of intervals needed to finish all tasks. The same task type must be separated by at least `n` intervals. CPU may idle between tasks.

```
Input:  tasks=["A","A","A","B","B","B"], n=2   → 8
Input:  tasks=["A","A","A","B","B","B"], n=0   → 6
Input:  tasks=["A","A","A","A","A","A","B","C","D","E","F","G"], n=2 → 16
```

### Pattern Recognition
Single-processor task scheduling with cooldown — the canonical problem. Two valid approaches: greedy simulation with max-heap + cooldown queue, or the mathematical frame formula. Implement simulation (generalizes) and derive the formula as a cross-check.

### Key Insight
**Simulation**: At each time slot, execute the highest-frequency available task. When no task is available, idle. A max-heap gives O(log k) access to the best task; a cooldown queue tracks when tasks become re-available.

**Formula**: `max(total_tasks, (max_freq - 1) * (n + 1) + count_of_max_freq)`. The frame structure gives the minimum time needed when idle slots are unavoidable.

### Solution — Simulation

```js
function leastInterval(tasks, n) {
  // Step 1: count frequencies
  const freq = new Map();
  for (const t of tasks) freq.set(t, (freq.get(t) || 0) + 1);

  // Step 2: build max-heap of frequencies
  // Simulate max-heap with array + sift operations
  const maxHeap = [...freq.values()];
  buildMaxHeap(maxHeap);

  // Step 3: cooldown queue — stores [remaining_count, next_available_time]
  const cooldownQueue = []; // FIFO — times are non-decreasing

  let time = 0;

  while (maxHeap.length > 0 || cooldownQueue.length > 0) {

    // re-enqueue tasks whose cooldown has expired
    if (
      cooldownQueue.length > 0 &&
      cooldownQueue[0][1] <= time
    ) {
      const [count] = cooldownQueue.shift();
      insertMax(maxHeap, count); // back into the heap
    }

    if (maxHeap.length > 0) {
      // execute the highest-frequency available task
      const count = extractMax(maxHeap);
      time++;

      if (count - 1 > 0) {
        // task still has remaining executions — put on cooldown
        // next available at: current_time + n
        // (executed at time-1, so next available at time-1+n+1 = time+n)
        cooldownQueue.push([count - 1, time + n]);
      }
    } else {
      // all tasks on cooldown — jump to next available time
      // (optimization: skip idle slots in O(1))
      time = cooldownQueue[0][1];
    }
  }

  return time;
}
```

### Heap Helper Functions

```js
function buildMaxHeap(arr) {
  for (let i = Math.floor(arr.length / 2) - 1; i >= 0; i--) {
    siftDownMax(arr, i);
  }
}

function siftDownMax(heap, i) {
  const n = heap.length;
  while (true) {
    let largest = i;
    const l = 2 * i + 1, r = 2 * i + 2;
    if (l < n && heap[l] > heap[largest]) largest = l;
    if (r < n && heap[r] > heap[largest]) largest = r;
    if (largest === i) break;
    [heap[largest], heap[i]] = [heap[i], heap[largest]];
    i = largest;
  }
}

function extractMax(heap) {
  if (heap.length === 1) return heap.pop();
  const max = heap[0];
  heap[0] = heap.pop();
  siftDownMax(heap, 0);
  return max;
}

function insertMax(heap, val) {
  heap.push(val);
  let i = heap.length - 1;
  while (i > 0) {
    const p = (i - 1) >> 1;
    if (heap[p] >= heap[i]) break;
    [heap[p], heap[i]] = [heap[i], heap[p]];
    i = p;
  }
}
```

### Solution — Mathematical Formula (O(n) time, O(1) space)

```js
function leastIntervalFormula(tasks, n) {
  // Step 1: count frequencies in a fixed-size array (26 letters)
  const freq = new Array(26).fill(0);
  for (const t of tasks) freq[t.charCodeAt(0) - 65]++;

  // Step 2: find max frequency and how many tasks share it
  const maxFreq = Math.max(...freq);
  const countOfMax = freq.filter(f => f === maxFreq).length;

  // Step 3: frame formula
  const frameResult = (maxFreq - 1) * (n + 1) + countOfMax;

  // Step 4: total tasks wins if tasks are dense enough (no idle needed)
  return Math.max(tasks.length, frameResult);
}
```

- "Minimize idle slots (not total time)?" → Equivalent problem — minimizing total time = minimizing idle time since `total_time = total_tasks + idle_slots`.

## Problem 2 — Reorganize String (LeetCode 767)

### Problem
Given a string `s`, rearrange its characters so that no two adjacent characters are the same. Return any valid rearrangement, or `""` if impossible.

```
Input:  s = "aab"    → "aba"
Input:  s = "aaab"   → ""   (impossible — 'a' frequency 3 > (4+1)/2=2)
Input:  s = "vvvlo"  → "vlvov" or "vovlv" etc.
```

### Pattern Recognition
Task scheduling with `n=1` (no two identical adjacent characters = cooldown of 1). Greedy: always place the most frequent character that isn't the same as the last placed. Max-heap gives O(log k) access to the most frequent.

### Key Insight
A valid rearrangement exists if and only if `max_frequency ≤ ⌈length/2⌉`. If valid, greedily placing the most frequent available character always produces a valid arrangement. After placing a character, it's on "cooldown" for 1 slot — hold the previous character and re-insert it into the heap on the next step.

### Approach
Max-heap of (frequency, character) pairs. Maintain `prev` (the character placed in the immediately preceding slot — it's on cooldown). Each step: extract the most frequent available character (≠ prev character), append to result, re-insert `prev` into the heap, set new `prev`.

### Solution

```js
function reorganizeString(s) {
  // Step 1: count frequencies
  const freq = new Map();
  for (const c of s) freq.set(c, (freq.get(c) || 0) + 1);

  // Step 2: impossibility check
  const maxFreq = Math.max(...freq.values());
  if (maxFreq > Math.ceil(s.length / 2)) return ""; // impossible

  // Step 3: build max-heap of [frequency, character] pairs
  const heap = [...freq.entries()].map(([c, f]) => [f, c]);
  buildMaxHeap(heap); // max-heap by frequency (heap[i][0])

  const result = [];
  let prev = null; // [frequency, character] of the previously placed char

  while (heap.length > 0 || prev !== null) {
    if (prev !== null && heap.length === 0) return ""; // stuck — shouldn't happen after validity check

    // extract most frequent available character
    const [freq, char] = extractMaxPair(heap);
    result.push(char);

    // re-insert previous character into heap (cooldown expired)
    if (prev !== null && prev[0] > 0) {
      insertMaxPair(heap, prev);
    }

    // set current as the new "prev" with decremented count
    prev = [freq - 1, char];
    if (prev[0] === 0) prev = null; // fully used — don't re-insert
  }

  return result.join('');
}
```

### Heap Helpers (Pair-Based Max-Heap by First Element)

```js
function buildMaxHeap(heap) {
  for (let i = Math.floor(heap.length / 2) - 1; i >= 0; i--) {
    siftDownPair(heap, i);
  }
}

function siftDownPair(heap, i) {
  const n = heap.length;
  while (true) {
    let largest = i;
    const l = 2*i+1, r = 2*i+2;
    if (l < n && heap[l][0] > heap[largest][0]) largest = l;
    if (r < n && heap[r][0] > heap[largest][0]) largest = r;
    if (largest === i) break;
    [heap[largest], heap[i]] = [heap[i], heap[largest]];
    i = largest;
  }
}

function extractMaxPair(heap) {
  if (heap.length === 1) return heap.pop();
  const max = heap[0];
  heap[0] = heap.pop();
  siftDownPair(heap, 0);
  return max;
}

function insertMaxPair(heap, val) {
  heap.push(val);
  let i = heap.length - 1;
  while (i > 0) {
    const p = (i - 1) >> 1;
    if (heap[p][0] >= heap[i][0]) break;
    [heap[p], heap[i]] = [heap[i], heap[p]];
    i = p;
  }
}
```

- Time: O(n log k) — n characters, each heap operation O(log k), k ≤ 26.
- Space: O(k) — heap holds at most k pairs.

### Edge Cases
- Single character: frequency 1, `ceil(1/2)=1`, `1≤1` → valid. Heap has 1 entry. Extracted immediately. Result = the character.
- Two same characters (`"aa"`): maxFreq=2, `ceil(2/2)=1`, `2>1` → return `""`. Correct.
- All distinct characters: every frequency is 1; heap cycles through them; any ordering is valid.
- Two characters equal frequency: alternating arrangement; greedy produces correct alternation.

- "Return all valid rearrangements?" → Backtracking with the greedy choice as a heuristic pruning — exponential in the worst case.

## Problem 3 — Process Tasks Using Servers (LeetCode 1882)

### Problem
You have `servers[i]` = weight of server `i` and `tasks[j]` = time units task `j` takes. Task `j` arrives at time `j` (0-indexed). Assign each task to the available server with the smallest weight (tiebreak by smallest index). A server becomes free after it finishes its current task.

Return `ans[j]` = index of server that processes task `j`.

```
Input:  servers=[3,3,2], tasks=[1,2,3,2,1,2]
Output: [2,2,0,2,1,2]

Input:  servers=[5,1,4,3,2], tasks=[2,1,2,4,5,2,1]
Output: [1,4,1,4,1,3,2]
```

### Pattern Recognition
Simulation with two priority queues: one for free servers (min-heap by weight, then index), one for busy servers (min-heap by release time, then weight, then index). At each task arrival, free any servers whose tasks have completed, then assign the task to the smallest-weight free server.

### Key Insight
Two separate heaps manage the two server states:
- **Free heap (min-heap by [weight, index])**: always yields the best available server.
- **Busy heap (min-heap by [release_time, weight, index])**: tracks when servers become free — the front always holds the server finishing soonest.

At each time step, pop from the busy heap all servers with `release_time ≤ current_time` and move them to the free heap.

### Approach
Initialize: all servers in the free heap. For each task `j` arriving at time `j`:
1. Free servers: pop from busy heap while `release_time ≤ max(j, current_time)`, push to free heap.
2. If free heap is non-empty: assign task to top of free heap (best available). Push to busy heap with `release_time = max(j, current_time) + tasks[j]`.
3. If free heap is empty: no server available at time `j` — jump time to `busy_heap.front.release_time`, free that server, assign the task.

### Solution

```js
function assignTasks(servers, tasks) {
  // Free servers: min-heap by [weight, index]
  const freeHeap = servers.map((w, i) => [w, i]);
  buildMinHeap(freeHeap); // min by first element

  // Busy servers: min-heap by [release_time, weight, index]
  const busyHeap = [];

  const ans = new Array(tasks.length);
  let time = 0;

  for (let j = 0; j < tasks.length; j++) {
    time = Math.max(time, j); // time is at least task arrival time

    // free servers whose tasks have completed by current time
    while (
      busyHeap.length > 0 &&
      busyHeap[0][0] <= time
    ) {
      const [, weight, idx] = extractMinTriple(busyHeap);
      insertMinPair(freeHeap, [weight, idx]);
    }

    // if no free server, jump to the earliest release time
    if (freeHeap.length === 0) {
      const [releaseTime, weight, idx] = extractMinTriple(busyHeap);
      time = releaseTime;
      insertMinPair(freeHeap, [weight, idx]);
    }

    // assign task j to the best free server
    const [weight, serverIdx] = extractMinPair(freeHeap);
    ans[j] = serverIdx;
    // server becomes busy until time + tasks[j]
    insertMinTriple(busyHeap, [time + tasks[j], weight, serverIdx]);
  }

  return ans;
}
```

## Problem 4 — Find Servers That Handled Most Number of Requests (LeetCode 1606)

### Problem
You have `k` servers (0-indexed). The `i`-th request arrives at time `arrival[i]` and takes `load[i]` time. Requests are assigned to the first available server with index `≥ i % k` (circular). If no such server, assign to any available server. If none, drop the request. Return all servers that handled the maximum number of requests.

```
Input:  k=3, arrival=[1,2,3,4,5], load=[5,2,3,3,3]
Output: [1]

Input:  k=3, arrival=[1,2,3,4], load=[1,2,1,2]
Output: [0]
```

### Pattern Recognition
Simulation with two heaps plus a sorted structure for the free servers (to efficiently find the first available server with index ≥ i%k). The "first available with index ≥ target" requirement is the twist — a sorted set (or simulated with a sorted array) is needed for the free servers, not just any min-heap.

### Key Insight
Two structures: a **min-heap of busy servers** ordered by release time (to free them efficiently) and a **sorted set of free server indices** (to find the first free server with index ≥ `i % k` using binary search). In JS, simulate the sorted set with a sorted array + binary search or use a heap with custom ordering.

### Approach
- Busy heap: [release_time, server_index].
- Free set: sorted array of free server indices (or a balanced BST in other languages).
- For each request `i`:
  1. Free all busy servers with release_time ≤ arrival[i] → add to free set.
  2. Find first free server with index ≥ `i%k` (binary search on free set). If not found, use the smallest index free server (wrap around). If no free servers, drop request.
  3. Assign, increment count, add to busy heap.

### Solution

```js
function busiestServers(k, arrival, load) {
  const count = new Array(k).fill(0);
  // Sorted array of free server indices (all start free)
  const freeServers = Array.from({length: k}, (_, i) => i);

  // Min-heap: [release_time, server_index]
  const busyHeap = [];

  const n = arrival.length;

  function lowerBound(arr, target) {
    // find first index in arr with value >= target
    let lo = 0, hi = arr.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (arr[mid] < target) lo = mid + 1;
      else hi = mid;
    }
    return lo; // returns arr.length if no such element
  }

  function insertSorted(arr, val) {
    const pos = lowerBound(arr, val);
    arr.splice(pos, 0, val); // O(n) — acceptable for k ≤ 10^5 with small ops
  }

  // Heap helpers for [release_time, server_index] min-heap
  function siftDownBusy(i) {
    while (true) {
      let s = i;
      const l = 2*i+1, r = 2*i+2;
      if (l < busyHeap.length && busyHeap[l][0] < busyHeap[s][0]) s = l;
      if (r < busyHeap.length && busyHeap[r][0] < busyHeap[s][0]) s = r;
      if (s === i) break;
      [busyHeap[s], busyHeap[i]] = [busyHeap[i], busyHeap[s]];
      i = s;
    }
  }
  function extractMinBusy() {
    if (busyHeap.length === 1) return busyHeap.pop();
    const min = busyHeap[0];
    busyHeap[0] = busyHeap.pop();
    siftDownBusy(0);
    return min;
  }
  function insertBusy(val) {
    busyHeap.push(val);
    let i = busyHeap.length - 1;
    while (i > 0) {
      const p = (i-1)>>1;
      if (busyHeap[p][0] <= busyHeap[i][0]) break;
      [busyHeap[p], busyHeap[i]] = [busyHeap[i], busyHeap[p]];
      i = p;
    }
  }

  for (let i = 0; i < n; i++) {
    const t = arrival[i];

    // free servers whose tasks completed by arrival[i]
    while (busyHeap.length > 0 && busyHeap[0][0] <= t) {
      const [, serverIdx] = extractMinBusy();
      insertSorted(freeServers, serverIdx);
    }

    if (freeServers.length === 0) continue; // no free server — drop

    const target = i % k;
    let pos = lowerBound(freeServers, target);

    if (pos === freeServers.length) {
      pos = 0; // wrap: use smallest free server index
    }

    const serverIdx = freeServers[pos];
    freeServers.splice(pos, 1); // remove from free set
    count[serverIdx]++;
    insertBusy([t + load[i], serverIdx]);
  }

  const maxCount = Math.max(...count);
  return count.reduce((acc, c, i) => {
    if (c === maxCount) acc.push(i);
    return acc;
  }, []);
}
```

## Problem 5 — Minimum Machines to Schedule Jobs (Meeting Rooms II Variant)

### Problem
Given `n` jobs with `start[i]` and `end[i]` times, find the minimum number of machines (processors) needed to run all jobs without any job overlapping on the same machine.

```
Input:  intervals=[[0,30],[5,10],[15,20]]  → 2
Input:  intervals=[[7,10],[2,4]]           → 1
Input:  intervals=[[1,5],[2,6],[3,7]]      → 3
```

### Pattern Recognition
Interval scheduling / resource allocation — min-heap of end times. Sort by start time; greedily assign each job to any machine that's already free (its end time ≤ new job's start time). If no machine is free, add a new machine.

### Key Insight
The minimum machines needed = maximum number of simultaneously overlapping jobs at any point. Equivalently: sort by start time; for each job, if the earliest-ending machine is free (end ≤ start), reuse it. Otherwise, add a new machine. The heap of end times always gives O(log n) access to the earliest-ending machine.

### Approach
Sort intervals by start time. Min-heap of end times of currently allocated machines. For each job: if heap top (earliest end) ≤ job's start, pop (machine is free) and push new end time. Otherwise, push new end time (new machine). Max heap size = answer.

### Solution

```js
function minMeetingRooms(intervals) {
  if (intervals.length === 0) return 0;

  // sort by start time
  intervals.sort((a, b) => a[0] - b[0]);

  // min-heap of end times of allocated machines
  const endHeap = [];

  function siftDownMin(i) {
    const n = endHeap.length;
    while (true) {
      let s = i;
      const l = 2*i+1, r = 2*i+2;
      if (l < n && endHeap[l] < endHeap[s]) s = l;
      if (r < n && endHeap[r] < endHeap[s]) s = r;
      if (s === i) break;
      [endHeap[s], endHeap[i]] = [endHeap[i], endHeap[s]];
      i = s;
    }
  }
  function extractMin() {
    if (endHeap.length === 1) return endHeap.pop();
    const min = endHeap[0];
    endHeap[0] = endHeap.pop();
    siftDownMin(0);
    return min;
  }
  function insertMin(val) {
    endHeap.push(val);
    let i = endHeap.length - 1;
    while (i > 0) {
      const p = (i-1)>>1;
      if (endHeap[p] <= endHeap[i]) break;
      [endHeap[p], endHeap[i]] = [endHeap[i], endHeap[p]];
      i = p;
    }
  }

  for (const [start, end] of intervals) {
    if (endHeap.length > 0 && endHeap[0] <= start) {
      // earliest-ending machine is free — reuse it
      extractMin();
    }
    // allocate this machine for the current job
    insertMin(end);
  }

  // heap size = number of machines in use = answer
  return endHeap.length;
}
```

```
[2,6]: heap top=5, 5≤2? No → new machine. insertMin(6). endHeap=[5,6]
[3,7]: heap top=5, 5≤3? No → new machine. insertMin(7). endHeap=[5,6,7]

return endHeap.length = 3 ✓


intervals=[[0,30],[5,10],[15,20]] → sorted: same
endHeap=[]

[0,30]: insertMin(30). endHeap=[30]
[5,10]: 30≤5? No → new machine. insertMin(10). endHeap=[10,30]
[15,20]: 10≤15? Yes → extractMin(10). insertMin(20). endHeap=[20,30]

return 2 ✓
```

### Complexity
- Time: O(n log n) — sort + n heap operations of O(log n) each.
- Space: O(n) — heap holds at most n end times.

### Edge Cases
- Single interval → 1 machine.
- No overlaps → 1 machine (reused for each interval).
- All intervals start at the same time → n machines needed.
- Adjacent intervals (end = start) → `end ≤ start` check allows reuse. E.g., [1,5] then [5,10]: `5 ≤ 5` → reuse same machine. Correct.

### Follow-up Questions
- "Return the assignment of jobs to machines?" → Track machine IDs; instead of just end times, store [end_time, machine_id] in the heap. Map each job to the machine_id it reused or the new machine_id assigned.
- "Minimize the total waiting time across all machines?" → Different objective — this becomes a scheduling optimization problem with a different greedy rule.
- "What if jobs can be preempted?" → Preemptive scheduling — a job can pause and resume. Different algorithm: Earliest Deadline First (EDF) with preemption.

## Decision Tree — Which Approach to Use

```
Is the problem asking for minimum time to complete all tasks?
│
├── Single processor, uniform task duration, cooldown constraint
│   ├── Need actual schedule → Simulation (max-heap + cooldown queue)
│   └── Just the time → Math formula: max(total, (f-1)*(n+1)+count_f)
│
├── Multiple processors
│   └── Simulation with rounds: extract top-p tasks per round
│
├── Tasks with dependencies (DAG)
│   └── Topological sort + max-heap by priority
│
└── Is the problem asking for resource allocation (how many machines)?
    └── Sort by start + min-heap of end times (Meeting Rooms II pattern)
```

## Common Bugs Checklist

Before finalizing any task scheduler solution, verify:

1. **Cooldown boundary condition** — next available time should be `current_time + n` (not `n-1` or `n+1`). If a task runs at time `t`, it can next run at time `t + n + 1` (n slots must pass before it's eligible). In the simulation where `time` increments after execution: next_available = `time_after_increment + n = (t+1) + n = t + n + 1`... or equivalently `executed_at + n + 1`. Off-by-one here causes incorrect idle slot counts.

2. **Jump optimization and idle accuracy** — when jumping `time = cooldownQueue[0][1]`, ensure this is the exact re-availability time (not `+1`). Jumping to the wrong time either skips a valid execution slot or idles one extra.

3. **Re-enqueueing zero-count tasks** — after decrementing a task's frequency, check `count - 1 > 0` before pushing to the cooldown queue. Pushing a task with count 0 causes it to be extracted from the heap later and executed again (count becomes -1, causing incorrect behavior).

4. **Formula `countOfMax` definition** — `countOfMax` counts how many distinct task types share the maximum frequency, not the total occurrences of those tasks. E.g., `["A","A","A","B","B","B"]` → `countOfMax = 2` (both A and B have max freq 3), not 6 (total occurrences).

5. **n=0 edge case** — with zero cooldown, the cooldown queue is never used. Simulate by immediately re-enqueuing tasks with decremented frequency. Answer = `total_tasks` exactly. Verify `(maxFreq-1)*(0+1)+countOfMax = maxFreq-1+countOfMax` — this should ≤ `total_tasks` for valid inputs (it will be, since `max(total, formula) = total` when n=0).

6. **Multiple heaps staying in sync** — for problems with both a free heap and a busy heap (Problem 3, 4), ensure every server is in exactly one of the two heaps at all times. Moving a server from busy to free must be an atomic pop-then-insert; a bug where the pop succeeds but the insert fails (or vice versa) causes servers to disappear.

**Final Tip:** At the 5 YOE level, task scheduler is one of the most common "heap" problems that escalates across 3–4 follow-ups in a single interview session. The escalation path is almost always: basic cooldown → return actual schedule → add weighted tasks → add dependencies or multiple processors. Know the simulation cold (not just the formula) because the formula breaks at every follow-up. The single most important thing to verbalize before coding: "At each time slot I greedily choose the highest-frequency available task — the max-heap gives me this in O(log k). The cooldown queue tracks when tasks are eligible again — it's always a regular FIFO queue, not another heap, because tasks are enqueued in time order and dequeue in the same order." Saying this out loud takes 15 seconds and shows exactly the level of structured thinking expected at this level.
