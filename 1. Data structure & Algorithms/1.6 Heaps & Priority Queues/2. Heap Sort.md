## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is a heap, and what are the two heap variants? Why does heap sort use a max-heap rather than a min-heap?**
A: A **heap** is a complete binary tree (every level fully filled except possibly the last, which is filled left-to-right) that satisfies the **heap property**: every node's value bears a consistent ordering relationship to its children's values. Two variants:

- **Max-heap**: every node's value is ≥ both its children's values. The root holds the maximum element.
- **Min-heap**: every node's value is ≤ both its children's values. The root holds the minimum element.

Heap sort uses a **max-heap** because the algorithm works by repeatedly extracting the largest element and placing it at the end of the array — the sorted output grows from right to left. Using a max-heap lets you extract the maximum in O(1) (it's always at the root) and maintain the heap in O(log n) after each extraction. A min-heap would give you the minimum at the root, which would build the sorted array from left to right but require an additional reversal step or an auxiliary array — breaking the in-place guarantee that makes heap sort attractive.

```
Max-heap (valid):          Min-heap (valid):
        16                         1
       /  \                       / \
      14   10                    3   6
     /  \  / \                  / \  / \
    8   7 9   3                5   9 8  10

Root = maximum (16)          Root = minimum (1)
Heap sort uses this one.
```

**Q2. How is a binary heap stored in an array, and what are the index relationships between parent and children?**
A: A binary heap is stored in a flat array using **level-order (BFS) indexing** — the root is at index 0, its left child at index 1, its right child at index 2, and so on level by level. This works because the complete-binary-tree structure guarantees no gaps in the array (no wasted space for missing nodes). The index relationships for a node at index `i` (0-indexed) are:

```
Parent:      floor((i - 1) / 2)
Left child:  2*i + 1
Right child: 2*i + 2
```

These formulas replace pointer dereferencing entirely — no `node.left` or `node.right` fields needed. The last non-leaf node is at index `floor(n/2) - 1`, which is where the heapification phase starts (all nodes at index `floor(n/2)` and beyond are leaves and already satisfy the heap property trivially).

```
Array: [16, 14, 10, 8, 7, 9, 3]
Index:   0   1   2  3  4  5  6

Visually:
           16 (0)
          /       \
       14 (1)    10 (2)
       /  \      /  \
     8(3) 7(4) 9(5) 3(6)

Parent of index 3: floor((3-1)/2) = 1 ✓ (node 14)
Left child of index 1: 2*1+1 = 3 ✓ (node 8)
Right child of index 1: 2*1+2 = 4 ✓ (node 7)
```

**Q3. What is "heapify" (also called "sift-down"), and what is its time complexity?**
A: **Heapify** (sift-down) is the operation that restores the heap property at a given node, assuming both its left and right subtrees already satisfy the heap property. It works by comparing the node's value with its children's values: if the node is smaller than either child (in a max-heap), swap it with the larger child, then recursively heapify the affected subtree. This "sifts" the violating node downward until it finds its correct position.

```js
function heapify(arr, n, i) {
  // n = heap size (portion of arr being treated as the heap)
  // i = index of the node to sift down
  let largest = i;
  const left  = 2 * i + 1;
  const right = 2 * i + 2;

  // find the largest among node and its children
  if (left < n && arr[left] > arr[largest])   largest = left;
  if (right < n && arr[right] > arr[largest]) largest = right;

  if (largest !== i) {
    [arr[i], arr[largest]] = [arr[largest], arr[i]]; // swap
    heapify(arr, n, largest); // recursively fix the affected subtree
  }
}
```

Time complexity of a single heapify call: O(log n) — the node descends at most the height of the tree, which is O(log n) for a complete binary tree with n elements. Each level requires O(1) work (one comparison and at most one swap).

**Q4. What is "build heap" (also called "heapify the entire array"), and why is it O(n) rather than O(n log n)?**
A: **Build heap** converts an arbitrary array into a valid max-heap in place, without any extra space. The algorithm applies `heapify` to every non-leaf node, starting from the last non-leaf (`floor(n/2) - 1`) and working upward to the root:

```js
function buildHeap(arr) {
  const n = arr.length;
  // start from last non-leaf, go up to root
  for (let i = Math.floor(n / 2) - 1; i >= 0; i--) {
    heapify(arr, n, i);
  }
}
```

The seemingly paradoxical O(n) complexity (applying an O(log n) operation n/2 times looks like O(n log n)) is explained by the fact that nodes at different levels have different heapify costs. Nodes near the bottom (most nodes) have very short sift-down distances — the vast majority of nodes are leaves or near-leaves with sift-down cost O(1) or O(2). The mathematical analysis sums `height × count` over all levels:

```
Level (from bottom)  |  Node count       | Sift-down cost
         0 (leaves)  |  ~n/2             |  0
         1           |  ~n/4             |  1
         2           |  ~n/8             |  2
         ...         |  ...              |  ...
         log n (root)|  1                |  log n

Total: sum_{k=0}^{log n} (n / 2^(k+1)) * k = O(n)
```

This sum converges to O(n) because the number of nodes at each level decreases geometrically faster than the sift-down cost increases linearly.

**Q5. Walk through the complete heap sort algorithm from start to finish.**
A: Heap sort has two phases:

**Phase 1 — Build heap:** Convert the input array into a valid max-heap in O(n) time using the bottom-up `buildHeap` procedure.

**Phase 2 — Extract max repeatedly:** The maximum element is always at index 0 (the heap root). Swap it with the last element in the heap, shrink the heap size by 1 (the swapped element is now in its final sorted position at the end), then call `heapify(arr, n, 0)` to restore the max-heap property. Repeat until the heap size reaches 1.

```js
function heapSort(arr) {
  const n = arr.length;

  // Phase 1: build max-heap (O(n))
  for (let i = Math.floor(n / 2) - 1; i >= 0; i--) {
    heapify(arr, n, i);
  }

  // Phase 2: extract max n-1 times (O(n log n))
  for (let i = n - 1; i > 0; i--) {
    [arr[0], arr[i]] = [arr[i], arr[0]]; // move current max to its final position
    heapify(arr, i, 0);                  // restore heap property over arr[0..i-1]
  }

  return arr;
}

function heapify(arr, n, i) {
  let largest = i;
  const left  = 2 * i + 1;
  const right = 2 * i + 2;

  if (left < n && arr[left] > arr[largest])   largest = left;
  if (right < n && arr[right] > arr[largest]) largest = right;

  if (largest !== i) {
    [arr[i], arr[largest]] = [arr[largest], arr[i]];
    heapify(arr, n, largest);
  }
}
```

**Q6. What are the time and space complexities of heap sort, and how does it compare to merge sort and quicksort?**
A:

| Property | Heap Sort | Merge Sort | Quicksort (avg) |
|---|---|---|---|
| Best case | O(n log n) | O(n log n) | O(n log n) |
| Average case | O(n log n) | O(n log n) | O(n log n) |
| Worst case | O(n log n) | O(n log n) | O(n²) |
| Space | O(1) in-place | O(n) auxiliary | O(log n) avg stack |
| Stable | No | Yes | No (typical) |
| Cache efficiency | Poor | Good | Good |

Heap sort is the only comparison-based sort that guarantees O(n log n) worst case **and** O(1) space simultaneously — merge sort guarantees O(n log n) but requires O(n) auxiliary space; quicksort achieves O(1) in-place but has O(n²) worst case. However, heap sort has poor cache performance in practice because heapify accesses array elements at indices `2i+1` and `2i+2` — for large arrays, these are far apart in memory, causing frequent cache misses. This is why quicksort, despite its theoretical worst-case disadvantage, often outperforms heap sort on real hardware.

### Section 2: Correctness & Invariants

**Q7. What is the loop invariant of the extraction phase, and how does it prove correctness?**
A: At the start of each iteration of the extraction loop (with loop variable `i`), the invariant is:

1. `arr[i+1 .. n-1]` contains the `(n-1-i)` largest elements of the original array, in sorted (ascending) order.
2. `arr[0 .. i]` is a valid max-heap containing the remaining `i+1` elements.

**Initialization**: before the first extraction (`i = n-1`), no elements have been placed in the sorted region — the invariant holds vacuously.

**Maintenance**: at each step, swapping `arr[0]` (the current max of the heap) with `arr[i]` places the current max at index `i`, extending the sorted region by one element. Then `heapify(arr, i, 0)` restores the heap property over the remaining `arr[0..i-1]` elements, maintaining invariant condition 2 for the next iteration.

**Termination**: when `i = 0`, the heap has size 1 (a single-element heap is trivially sorted), and `arr[1..n-1]` is fully sorted. Since `arr[0]` is the smallest remaining element (the last one), the entire array is sorted.

**Q8. Why does heap sort produce a sorted array in ascending order when it uses a max-heap, which extracts the maximum?**
A: The extraction phase places elements in sorted order by building the sorted portion of the array **from right to left**. Each extracted maximum goes to the rightmost unsorted position — so the largest element ends up at index `n-1`, the second-largest at `n-2`, and so on. After all n-1 extractions, the array reads smallest-to-largest from left to right — ascending order. This is the reverse of the intuition that "max-heap extracts the maximum" might suggest: the maximum element is repeatedly banished to the rightmost position, and when the rightmost position is index 0 (the last extraction), the smallest element has naturally become the heap's only remaining element. The result is ascending order without any reversal step.

**Q9. Is heap sort stable? Why or why not, and does it matter?**
A: Heap sort is **not stable** — equal elements may appear in a different relative order in the output than they had in the input. The instability arises from the `heapify` sift-down operation: when a node is swapped with its larger child, an equal-valued sibling might have appeared earlier in the original array but ends up after the swapped element, breaking the original relative ordering. For example, sorting `[2a, 2b, 1]` (where `a` and `b` are two distinct items with value 2) might produce `[1, 2b, 2a]` instead of `[1, 2a, 2b]`. In practice, instability matters when sorting objects with multiple fields — if a secondary sort order needs to be preserved from a prior sort pass, an unstable sort invalidates it. In purely numeric contexts (sort integers, return sorted array) it's irrelevant.

**Q10. What is the "sift-up" operation (as opposed to sift-down/heapify), and when is it used?**
A: **Sift-up** (also called "bubble-up" or "percolate-up") moves a node upward from its current position toward the root, restoring the heap property when a node's value is larger than its parent (in a max-heap). It is used when **inserting** a new element into a heap: append the element at the end (the next available position in the level-order indexing), then repeatedly swap it with its parent while it's larger than the parent.

```js
function siftUp(arr, i) {
  while (i > 0) {
    const parent = Math.floor((i - 1) / 2);
    if (arr[i] > arr[parent]) {
      [arr[i], arr[parent]] = [arr[parent], arr[i]];
      i = parent;
    } else {
      break; // heap property restored
    }
  }
}
```

Heap sort's build-heap phase does NOT use sift-up — it uses sift-down (heapify) in a bottom-up pass, which achieves O(n) total cost. Building a heap by repeatedly inserting elements and calling sift-up would cost O(n log n) instead (n insertions × O(log n) each) — a common misconception about the build-heap phase's complexity.

### Section 3: Variants & Extensions

**Q11. How do you sort in descending order using heap sort without modifying the core algorithm?**
A: Two approaches:

- **Use a min-heap instead of a max-heap**: extract the minimum n-1 times, placing minimums at the end from right to left, producing a descending-order array. Implement by inverting the comparison in `heapify` (`arr[left] < arr[largest]` instead of `>`).
- **Use the standard max-heap sort (ascending) and reverse the result**: O(n) extra pass after sorting. Simpler to implement correctly since no logic changes are needed.

The min-heap approach is slightly more elegant (no extra pass) but requires carefully inverting all comparisons in heapify — a source of bugs if any comparison is missed. In an interview, state both options and your preference clearly.

```js
// Min-heap heapify (for descending sort)
function heapifyMin(arr, n, i) {
  let smallest = i;
  const left  = 2 * i + 1;
  const right = 2 * i + 2;

  if (left < n && arr[left] < arr[smallest])   smallest = left;
  if (right < n && arr[right] < arr[smallest]) smallest = right;

  if (smallest !== i) {
    [arr[i], arr[smallest]] = [arr[smallest], arr[i]];
    heapifyMin(arr, n, smallest);
  }
}
```

**Q12. How would you find the k largest elements in an array efficiently using a heap, and what is the complexity?**
A: Two approaches:

**Approach 1 — Sort with heap sort, take the last k:**
Apply heap sort in O(n log n), return the last k elements. Simple but does more work than necessary.

**Approach 2 — Min-heap of size k (optimal):**
Maintain a min-heap of size k. For each element in the array: if the heap has fewer than k elements, insert it; otherwise, if the element is larger than the heap's minimum (the root), replace the minimum with the element and heapify. After processing all n elements, the heap contains the k largest elements.

```js
function kLargest(arr, k) {
  // Use a min-heap of size k (simulated here with a sorted array for clarity)
  const minHeap = arr.slice(0, k);
  buildMinHeap(minHeap); // O(k)

  for (let i = k; i < arr.length; i++) {
    if (arr[i] > minHeap[0]) {
      minHeap[0] = arr[i];     // replace the minimum
      heapifyMin(minHeap, k, 0); // restore min-heap property
    }
  }

  return minHeap; // contains the k largest elements (not necessarily sorted)
}
```

Time: O(k + (n-k) log k) — O(k) to build the initial min-heap, O(log k) per subsequent element for at-most n-k heapify operations. This is O(n log k) overall — much better than O(n log n) when k is small.

Space: O(k) — only the heap of size k is maintained.

**Q13. What is an "iterative heapify" and why might you prefer it over the recursive version?**
A: The recursive `heapify` has a call stack depth of O(log n) — one frame per level of sifting. For very large heaps this is fine (log₂(10^9) ≈ 30 frames), but in environments with strict stack limits or where every function call has significant overhead, an iterative version eliminates the recursion:

```js
function heapifyIterative(arr, n, i) {
  while (true) {
    let largest = i;
    const left  = 2 * i + 1;
    const right = 2 * i + 2;

    if (left < n && arr[left] > arr[largest])   largest = left;
    if (right < n && arr[right] > arr[largest]) largest = right;

    if (largest === i) break; // heap property satisfied — stop

    [arr[i], arr[largest]] = [arr[largest], arr[i]];
    i = largest; // move down to the swapped child position
  }
}
```

The iterative version replaces the recursive call `heapify(arr, n, largest)` with simply updating `i = largest` and continuing the loop — since `heapify` is tail-recursive (the recursive call is the last operation), this is a direct tail-call elimination. Time and correctness are identical; the iterative version avoids O(log n) stack frames.

**Q14. How does heap sort behave on already-sorted, reverse-sorted, and all-equal input arrays?**
A:

- **Already sorted (ascending)**: The build-heap phase rearranges the array into a max-heap (potentially reordering it significantly), then extraction re-sorts it. Time is O(n log n) regardless — heap sort has no best-case optimization for pre-sorted input (unlike insertion sort's O(n) best case or timsort's adaptive behavior). This is a notable disadvantage of heap sort.

- **Reverse sorted (descending)**: The input happens to be a valid max-heap already (each parent is larger than both children in a descending array... actually this depends on the specific values, but a reverse-sorted array is generally a valid max-heap). The build-heap phase does minimal work. Extraction still takes O(n log n). No meaningful performance difference from the average case.

- **All equal elements**: Every heapify comparison results in "no swap needed" (since all values are equal, no element is strictly larger than another). Build-heap does O(n) comparisons but 0 swaps. Extraction still does O(n) sift-down operations but again 0 swaps. Time is still O(n log n) in terms of comparisons, but in practice runs faster due to branch prediction (the "no swap" branch is taken consistently). The result is correct (a trivially sorted all-equal array).

**Q15. What is "bottom-up heap sort" and what problem does it address?**
A: Standard heap sort performs two comparisons per level during sift-down: one to find the larger child, and one to check if a swap is needed. **Bottom-up heap sort** (also called "heapsort with sentinel") optimizes this by separating the sift-down into two phases:

1. **Descend without comparison to parent**: follow the path of larger children all the way down to a leaf, making only one comparison per level (find larger child) instead of two.
2. **Sift back up**: from the leaf reached, sift upward until the correct position for the displaced element is found.

This approximately halves the number of comparisons during extraction — giving roughly `n log n` comparisons instead of `2n log n`. The savings matter most for large n where comparison cost is significant (e.g., comparing long strings or complex objects). For integer arrays, the improvement is measurable but usually dominated by cache miss effects. Bottom-up heap sort is rarely asked about in interviews but appears in discussions of cache-efficient sorting and competitive programming.

### Section 4: Heap Applications Beyond Sorting

**Q16. What is a priority queue, and how does a heap implement it? How does this relate to heap sort?**
A: A **priority queue** is an abstract data type supporting: `insert(element, priority)`, `extractMax()` (or `extractMin()`), and optionally `peek()` (view the max/min without removing it) and `changePriority(element, newPriority)`. A binary heap implements all of these efficiently:

| Operation | Time | Mechanism |
|---|---|---|
| insert | O(log n) | append + sift-up |
| extractMax | O(log n) | swap root with last, shrink, sift-down |
| peek | O(1) | return arr[0] |
| buildHeap (n inserts) | O(n) | bottom-up heapify |

Heap sort is essentially "build a priority queue from all n elements, then extract all n elements" — it's the priority queue's `buildHeap` followed by n `extractMax` calls. Recognizing this connection clarifies why heap sort is O(n log n): O(n) build + O(n log n) for n extractions.

**Q17. How is a heap used to efficiently merge k sorted arrays?**
A: Insert the first element of each of the k sorted arrays into a min-heap, along with a pointer to which array it came from and its index within that array. Then repeatedly extract the minimum, add it to the output, and insert the next element from the same array into the heap. When an array is exhausted, simply stop inserting from it.

```js
function mergeKSorted(arrays) {
  const result = [];
  // min-heap entries: [value, arrayIndex, elementIndex]
  const heap = [];

  // initialize with the first element of each array
  for (let i = 0; i < arrays.length; i++) {
    if (arrays[i].length > 0) {
      heapInsert(heap, [arrays[i][0], i, 0]);
    }
  }

  while (heap.length > 0) {
    const [val, arrIdx, elemIdx] = heapExtractMin(heap);
    result.push(val);
    if (elemIdx + 1 < arrays[arrIdx].length) {
      heapInsert(heap, [arrays[arrIdx][elemIdx + 1], arrIdx, elemIdx + 1]);
    }
  }

  return result;
}
```

Time: O(N log k) where N is the total number of elements across all arrays and k is the number of arrays — each of the N elements is inserted and extracted from the heap once, at O(log k) cost. Space: O(k) for the heap.

**Q18. How would you implement a "median finder" (streaming median) using two heaps?**
A: Maintain two heaps: a **max-heap for the lower half** of seen elements and a **min-heap for the upper half**. Keep them balanced (sizes differ by at most 1). The median is then the root of the max-heap (if total count is odd — lower half has one more element) or the average of both roots (if total count is even).

```js
class MedianFinder {
  constructor() {
    this.maxHeap = []; // lower half (max-heap)
    this.minHeap = []; // upper half (min-heap)
  }

  addNum(num) {
    // always insert into max-heap first
    heapInsertMax(this.maxHeap, num);

    // balance: if maxHeap's max > minHeap's min, move it up
    if (this.minHeap.length > 0 && this.maxHeap[0] > this.minHeap[0]) {
      heapInsertMin(this.minHeap, heapExtractMax(this.maxHeap));
    }

    // rebalance sizes (maxHeap can have at most 1 more element than minHeap)
    if (this.maxHeap.length > this.minHeap.length + 1) {
      heapInsertMin(this.minHeap, heapExtractMax(this.maxHeap));
    } else if (this.minHeap.length > this.maxHeap.length) {
      heapInsertMax(this.maxHeap, heapExtractMin(this.minHeap));
    }
  }

  findMedian() {
    if (this.maxHeap.length > this.minHeap.length) return this.maxHeap[0];
    return (this.maxHeap[0] + this.minHeap[0]) / 2;
  }
}
```

Time: O(log n) per `addNum`, O(1) per `findMedian`. Space: O(n) total.

### Section 5: Scenario / Interview-Style Questions

**Q19. "Walk me through how you'd sort this array using heap sort: [4, 10, 3, 5, 1]."**
A: I'll trace both phases — build-heap and extraction.

**Phase 1 — Build max-heap:**
Array: `[4, 10, 3, 5, 1]`, n=5. Last non-leaf: `floor(5/2)-1 = 1`.

- `heapify(arr, 5, 1)`: node=10 at index 1. Left=5 (idx 3), Right=1 (idx 4). 10 > 5 > 1 → 10 is already largest. No swap.
- `heapify(arr, 5, 0)`: node=4 at index 0. Left=10 (idx 1), Right=3 (idx 2). Largest = 10 at idx 1. Swap 4 and 10 → `[10, 4, 3, 5, 1]`. Recurse: `heapify(arr, 5, 1)`: node=4. Left=5 (idx 3), Right=1 (idx 4). Largest=5 at idx 3. Swap 4 and 5 → `[10, 5, 3, 4, 1]`. Recurse: `heapify(arr, 5, 3)`: node=4. No children in bounds. Stop.

Max-heap built: `[10, 5, 3, 4, 1]`.

**Phase 2 — Extract max 4 times:**

- i=4: swap arr[0]=10 with arr[4]=1 → `[1, 5, 3, 4, 10]`. heapify(arr, 4, 0): 1→largest child 5 (idx1). Swap → `[5, 1, 3, 4, 10]`. Recurse idx 1: 1→largest child 4 (idx3). Swap → `[5, 4, 3, 1, 10]`. Heap: `[5,4,3,1]`.
- i=3: swap arr[0]=5 with arr[3]=1 → `[1, 4, 3, 5, 10]`. heapify(arr, 3, 0): 1→4 (idx1). Swap → `[4, 1, 3, 5, 10]`. Recurse idx1: 1, children idx3 and 4 both out of bounds (heap size=3). Stop. Heap: `[4,1,3]`.
- i=2: swap arr[0]=4 with arr[2]=3 → `[3, 1, 4, 5, 10]`. heapify(arr, 2, 0): 3 vs left=1 (idx1). 3>1, no swap. Heap: `[3,1]`.
- i=1: swap arr[0]=3 with arr[1]=1 → `[1, 3, 4, 5, 10]`. heapify(arr, 1, 0): heap size 1, no children. Stop.

Final sorted array: `[1, 3, 4, 5, 10]` ✓

**Q20. "Heap sort is O(n log n) worst case, but in practice quicksort is faster. Why would you ever choose heap sort?"**
A: The primary reason to choose heap sort is the **guaranteed O(n log n) worst case with O(1) space** — a combination no other common sorting algorithm achieves. Specific scenarios:

- **Hard real-time systems**: where worst-case latency bounds must be guaranteed, not just average-case performance. Quicksort's O(n²) worst case (even with randomization, adversarial inputs exist) is unacceptable in contexts like medical devices, avionics, or safety-critical embedded systems.
- **Memory-constrained environments**: where O(n) auxiliary space for merge sort is unavailable and only in-place sorting is feasible.
- **Adversarial input environments**: where an attacker might craft input to degrade quicksort to O(n²) (relevant for hash tables and sort-based algorithms exposed to user input).
- **Priority queue use cases that also need sorting**: if you already have a heap for priority queue operations, sorting it in-place with heap sort adds negligible extra cost.

In general-purpose programming without these constraints, quicksort (with random pivot) or timsort (the adaptive hybrid used in Python, Java, and most standard libraries) will outperform heap sort due to better cache behavior and adaptive optimization for partially-sorted data.

**Q21. "How would you test a heap sort implementation for correctness?"**
A: Key test cases, in order of what they verify:

- **Empty array**: should return `[]` without crashing — tests the `n = 0` case where the build-heap loop and extraction loop both execute 0 times.
- **Single element**: `[42]` → `[42]`. Tests the trivial case where extraction loop runs 0 times (`i > 0` starts false).
- **Two elements**: `[2, 1]` → `[1, 2]` and `[1, 2]` → `[1, 2]`. Tests the minimal non-trivial extraction step and the already-sorted case.
- **Already sorted input**: `[1, 2, 3, 4, 5]` — heap sort should not produce a different result but the build-heap step will rearrange it significantly; verifies the algorithm doesn't exploit "already sorted" assumptions incorrectly.
- **Reverse sorted input**: `[5, 4, 3, 2, 1]` → `[1, 2, 3, 4, 5]`. Tests that extraction correctly handles an already-valid max-heap.
- **All equal elements**: `[7, 7, 7, 7]` → `[7, 7, 7, 7]`. Verifies the `>` comparison (strict, not `>=`) in heapify doesn't cause infinite loops or incorrect swaps.
- **Negative numbers**: `[-3, -1, -4, -2]` → `[-4, -3, -2, -1]`. Verifies no sign-specific assumptions in comparisons.
- **Duplicates mixed with distinct values**: `[3, 1, 4, 1, 5, 9, 2, 6, 5]` — verifies stability is not assumed and all duplicates appear in output.
- **Large n with random input**: confirms O(n log n) performance (time it; quadratic behavior is detectable at n=100,000).
- **Off-by-one in heap size**: trace that `heapify(arr, i, 0)` uses `i` (current heap size, shrinking), not `n` (original array size) — accidentally using `n` would re-include already-sorted elements in heapify comparisons, potentially corrupting the sorted suffix.

## Problem 1 — Heap Sort (Core Implementation)

### Problem
Implement heap sort to sort an integer array in ascending order in-place, using O(1) extra space.

```
Input:  [12, 11, 13, 5, 6, 7]
Output: [5, 6, 7, 11, 12, 13]
```

### Pattern Recognition
Two-phase in-place sort: bottom-up max-heap construction followed by repeated root extraction — both phases use the `heapify` sift-down as the fundamental primitive.

### Key Insight
The array serves double duty: the left portion `arr[0..heapSize-1]` is a live max-heap; the right portion `arr[heapSize..n-1]` is the growing sorted result. The heap shrinks by one and the sorted region grows by one per extraction step — no auxiliary array needed.

### Approach
Phase 1: `buildHeap` — apply heapify bottom-up from the last non-leaf to the root. Phase 2: n-1 times, swap `arr[0]` (max) with `arr[i]` (last heap element), decrement heap size, call `heapify(arr, i, 0)` to restore the max-heap over the reduced heap.

### Solution

```js
function heapSort(arr) {
  const n = arr.length;

  // Phase 1: build max-heap from the entire array — O(n)
  // Start from the last non-leaf node and work up to root
  for (let i = Math.floor(n / 2) - 1; i >= 0; i--) {
    heapify(arr, n, i);
  }

  // Phase 2: extract elements from the heap one by one — O(n log n)
  for (let i = n - 1; i > 0; i--) {
    // Move the current maximum (root) to its final sorted position
    [arr[0], arr[i]] = [arr[i], arr[0]];

    // Restore heap property over the remaining heap arr[0..i-1]
    // Note: heap size is now i, not n
    heapify(arr, i, 0);
  }

  return arr;
}

function heapify(arr, n, i) {
  let largest = i;           // assume current node is largest
  const left  = 2 * i + 1;  // left child index
  const right = 2 * i + 2;  // right child index

  // update largest if left child is within heap and larger than current largest
  if (left < n && arr[left] > arr[largest]) largest = left;

  // update largest if right child is within heap and larger than current largest
  if (right < n && arr[right] > arr[largest]) largest = right;

  // if largest is not the current node, swap and recurse
  if (largest !== i) {
    [arr[i], arr[largest]] = [arr[largest], arr[i]];
    heapify(arr, n, largest); // fix the subtree rooted at `largest`
  }
}
```

### Complexity
- Time: O(n log n) in all cases — O(n) for build-heap, O(n log n) for n-1 extractions (each heapify is O(log n)).
- Space: O(log n) for the recursion call stack during heapify (O(1) if heapify is implemented iteratively). No auxiliary arrays.

### Edge Cases
- Empty array (n=0): `Math.floor(0/2)-1 = -1`, the build-heap loop condition `i >= 0` is false immediately; the extraction loop `i > 0` is also false. Returns `[]`. ✓
- Single element (n=1): build-heap loop runs with `i = -1` (never enters); extraction loop `i = 0, 0 > 0` is false. Returns `[arr[0]]`. ✓
- All equal elements: every heapify finds `largest === i` (strict `>` comparison, no ties cause swaps); no swaps occur. Result is correct (identical array). ✓
- Heap size `i` passed to heapify, NOT `n`: using `n` instead of `i` in the extraction phase would include already-sorted elements (`arr[i..n-1]`) in heapify's comparison range, potentially displacing sorted elements. Always pass the current heap size. ✓

### Follow-up Questions
- "Can you make heapify iterative to eliminate recursion overhead?" → Yes — see Q13 for the iterative version replacing `heapify(arr, n, largest)` with `i = largest; continue`.
- "How does this change if you want descending order?" → Invert all `>` comparisons in heapify to `<` (min-heap), or call the standard ascending sort and reverse the result.

## Problem 2 — K Largest Elements in an Array

### Problem
Given an integer array `nums` and an integer `k`, return the `k` largest elements in any order.

```
Input: nums = [3, 2, 1, 5, 6, 4], k = 2
Output: [5, 6]

Input: nums = [3, 2, 3, 1, 2, 4, 5, 5, 6], k = 4
Output: [4, 5, 5, 6]
```

### Pattern Recognition
Min-heap of size k — maintain a sliding window of the k largest elements seen so far, using the heap's minimum (root) as the threshold for inclusion.

### Key Insight
The k largest elements are exactly those that survive a "tournament" against the current k-th largest. A min-heap of size k always has the current k-th largest element at its root. Any new element larger than this threshold displaces the root — the threshold rises. Elements smaller than the threshold are discarded. After processing all n elements, the heap holds exactly the k largest.

### Approach
Build a min-heap from the first k elements. For each remaining element: if it exceeds the heap's minimum, replace the minimum with the new element and heapify. Return the heap contents.

### Solution

```js
function kLargest(nums, k) {
  // Build a min-heap from the first k elements
  const heap = nums.slice(0, k);
  buildMinHeap(heap);

  // Process the remaining elements
  for (let i = k; i < nums.length; i++) {
    if (nums[i] > heap[0]) {
      // New element beats the current k-th largest — replace it
      heap[0] = nums[i];
      heapifyMin(heap, k, 0); // restore min-heap property
    }
    // else: nums[i] <= heap[0] — it's not in the top k, discard
  }

  return heap; // contains the k largest elements (not sorted)
}

function buildMinHeap(arr) {
  for (let i = Math.floor(arr.length / 2) - 1; i >= 0; i--) {
    heapifyMin(arr, arr.length, i);
  }
}

function heapifyMin(arr, n, i) {
  let smallest = i;
  const left  = 2 * i + 1;
  const right = 2 * i + 2;

  if (left < n && arr[left] < arr[smallest])   smallest = left;
  if (right < n && arr[right] < arr[smallest]) smallest = right;

  if (smallest !== i) {
    [arr[i], arr[smallest]] = [arr[smallest], arr[i]];
    heapifyMin(arr, n, smallest);
  }
}
```

### Complexity
- Time: O(k + (n-k) log k) — O(k) to build the initial min-heap, O(log k) for each of at-most (n-k) replacement operations. Simplifies to O(n log k).
- Space: O(k) for the heap.
- Comparison: O(n log n) if you fully sort the array — the heap approach is strictly better when k << n.

### Edge Cases
- `k = n`: the heap is initialized with all elements, no iteration over remaining elements. Returns all elements. ✓
- `k = 1`: returns the single maximum element — heap has one element, any element larger than it replaces it. ✓
- Duplicates in top k: min-heap correctly handles duplicates — if the k-th and (k+1)-th largest are equal, elements equal to the threshold are correctly excluded (strict `>` comparison). ✓
- All elements equal: no replacements occur after initial heap build (no element strictly exceeds the root). Returns any k elements, all equal. ✓

### Follow-up Questions
- "What if you also need the k largest elements in sorted order?" → After the heap is built, run heap sort on it (O(k log k) additional cost) or return `heap.sort((a,b) => b-a)` for simplicity. Total: O(n log k + k log k) = O(n log k).
- "What if k is very large (close to n)?" → The k-largest heap approach gives O(n log k) ≈ O(n log n). An alternative: use a max-heap of the full array and extract k times for O(n + k log n) — better when k is small relative to n (build O(n) once, extract O(log n) × k times).

## Problem 3 — Sort a Nearly Sorted Array (K-Sorted)

### Problem
Given an array where each element is at most `k` positions away from its sorted position (a "k-sorted" or "nearly sorted" array), sort it efficiently.

```
Input: arr = [6, 5, 3, 2, 8, 10, 9], k = 3
(Element 6 is at most 3 positions from its sorted position, etc.)
Output: [2, 3, 5, 6, 8, 9, 10]
```

### Pattern Recognition
Min-heap of size k+1 — exploit the near-sortedness: the smallest element in the final sorted output must be within the first `k+1` elements of the input (since it can be at most k positions away from index 0).

### Key Insight
Because each element is at most k positions from its correct position, the globally minimum element among `arr[0..k]` must be the correct first element of the sorted output. After placing it, the next minimum must be among `arr[1..k+1]`, and so on. A min-heap of size k+1 maintains exactly the window of candidates for each output position, advancing the window one step at a time.

### Approach
Insert the first `k+1` elements into a min-heap. For each subsequent element: extract the minimum from the heap (it's the next output element), insert the new element. After the main loop, drain the heap to produce the remaining output elements.

### Solution

```js
function sortKSorted(arr, k) {
  const n = arr.length;
  const result = [];

  // Initialize min-heap with first k+1 elements
  const heap = arr.slice(0, Math.min(k + 1, n));
  buildMinHeap(heap);

  // Process remaining elements
  for (let i = k + 1; i < n; i++) {
    result.push(heapExtractMin(heap));  // minimum of current window → output
    heapInsertMin(heap, arr[i]);        // slide window: include next element
  }

  // Drain remaining elements from heap
  while (heap.length > 0) {
    result.push(heapExtractMin(heap));
  }

  return result;
}

// Simplified extract and insert (using the heapifyMin from Problem 2)
function heapExtractMin(heap) {
  const min = heap[0];
  heap[0] = heap[heap.length - 1];
  heap.pop();
  if (heap.length > 0) heapifyMin(heap, heap.length, 0);
  return min;
}

function heapInsertMin(heap, val) {
  heap.push(val);
  let i = heap.length - 1;
  // sift-up
  while (i > 0) {
    const parent = Math.floor((i - 1) / 2);
    if (heap[i] < heap[parent]) {
      [heap[i], heap[parent]] = [heap[parent], heap[i]];
      i = parent;
    } else break;
  }
}
```

### Complexity
- Time: O(n log k) — each of the n elements is inserted and extracted from a heap of size k+1 at most once, each operation costing O(log k).
- Space: O(k) for the heap, O(n) for the result array. If sorting in-place is required, the result can be written back to the input array.
- When k is small (e.g., k=3 for a nearly-sorted array), this is effectively O(n) — dramatically faster than O(n log n) heap sort on random arrays.

### Edge Cases
- `k = 0`: array is already sorted. Heap size is 1; each element is extracted and inserted individually with no reordering. ✓
- `k >= n`: equivalent to a full sort; heap size is n; falls back to standard O(n log n) behavior. ✓
- `k + 1 > n`: `Math.min(k+1, n)` prevents building a heap larger than the array. ✓

### Follow-up Questions
- "What if k is unknown?" → Estimate k by scanning the array for the maximum displacement from the sorted position — but this requires knowing the sorted order. Alternatively, use a standard O(n log n) sort. The k-sorted optimization is only applicable when k is given or can be determined cheaply.

## Problem 4 — Merge K Sorted Arrays

### Problem
Given `k` sorted arrays, merge them into a single sorted array.

```
Input: [[1, 4, 7], [2, 5, 8], [3, 6, 9]]
Output: [1, 2, 3, 4, 5, 6, 7, 8, 9]
```

### Pattern Recognition
Min-heap with source tracking — maintain a heap of size k, one entry per array, each entry encoding the current candidate value, which array it came from, and its index within that array.

### Key Insight
At any point, the next output element is the minimum among all current "frontier" elements (the earliest unprocessed element of each array). A min-heap of size k always exposes this minimum at its root in O(1), and advancing to the next element of the winning array costs O(log k). The heap maintains exactly one entry per array — the frontier — at all times.

### Approach
Initialize the heap with the first element of each non-empty array (as `[value, arrayIndex, elementIndex]` tuples). Repeatedly extract the minimum, push it to output, and insert the next element from the same array (if any). Continue until the heap is empty.

### Solution

```js
function mergeKSorted(arrays) {
  const result = [];
  // heap stores [value, arrayIndex, elementIndex] tuples
  const heap = [];

  // Initialize: insert first element of each array
  for (let i = 0; i < arrays.length; i++) {
    if (arrays[i].length > 0) {
      heapInsertTuple(heap, [arrays[i][0], i, 0]);
    }
  }

  while (heap.length > 0) {
    const [val, arrIdx, elemIdx] = heapExtractMinTuple(heap);
    result.push(val);

    // If this array has more elements, insert the next one
    if (elemIdx + 1 < arrays[arrIdx].length) {
      heapInsertTuple(heap, [arrays[arrIdx][elemIdx + 1], arrIdx, elemIdx + 1]);
    }
  }

  return result;
}

// Min-heap operations on tuples (compare by first element)
function heapInsertTuple(heap, tuple) {
  heap.push(tuple);
  let i = heap.length - 1;
  while (i > 0) {
    const parent = Math.floor((i - 1) / 2);
    if (heap[i][0] < heap[parent][0]) {
      [heap[i], heap[parent]] = [heap[parent], heap[i]];
      i = parent;
    } else break;
  }
}

function heapExtractMinTuple(heap) {
  const min = heap[0];
  heap[0] = heap[heap.length - 1];
  heap.pop();
  heapifyMinTuple(heap, heap.length, 0);
  return min;
}

function heapifyMinTuple(arr, n, i) {
  let smallest = i;
  const left = 2 * i + 1, right = 2 * i + 2;
  if (left < n && arr[left][0] < arr[smallest][0])   smallest = left;
  if (right < n && arr[right][0] < arr[smallest][0]) smallest = right;
  if (smallest !== i) {
    [arr[i], arr[smallest]] = [arr[smallest], arr[i]];
    heapifyMinTuple(arr, n, smallest);
  }
}
```

- "What if k is very large (thousands of arrays)?" → The algorithm scales naturally. O(log k) heap operations remain efficient even for large k. The bottleneck becomes the N element insertions/extractions, not k itself.

## Problem 5 — Find Median from a Data Stream

### Problem
Design a data structure that supports adding integers one at a time and querying the current median at any point.

```
MedianFinder mf = new MedianFinder();
mf.addNum(1);   // stream: [1]
mf.addNum(2);   // stream: [1, 2]
mf.findMedian() → 1.5
mf.addNum(3);   // stream: [1, 2, 3]
mf.findMedian() → 2
```

### Pattern Recognition
Two-heap partition — maintain a max-heap for the lower half and a min-heap for the upper half of seen elements, keeping them balanced so the median is always accessible at either root.

### Key Insight
The median is either the middle element (odd count) or the average of the two middle elements (even count). By maintaining two heaps where `maxHeap.root ≤ minHeap.root` always holds and their sizes differ by at most 1, the median is always `maxHeap.root` (odd total) or `(maxHeap.root + minHeap.root) / 2` (even total) — an O(1) query with O(log n) insertions.

### Approach
On `addNum`: always insert into `maxHeap` first. If the new root of `maxHeap` exceeds `minHeap`'s root (the partition boundary is violated), move `maxHeap`'s root to `minHeap`. Then rebalance sizes: if `maxHeap` has more than 1 extra element, move its root to `minHeap`; if `minHeap` is larger, move its root to `maxHeap`. On `findMedian`: compare sizes; if equal, average both roots; else return `maxHeap`'s root (which holds the extra element when odd).

### Solution

```js
class MedianFinder {
  constructor() {
    // maxHeap holds the lower half (negated values to simulate max-heap using min-heap ops)
    this.lowerMax = []; // max-heap (conceptually): stores elements in lower half
    this.upperMin = []; // min-heap: stores elements in upper half
  }

  addNum(num) {
    // Step 1: always add to lower max-heap first
    this._insertMax(this.lowerMax, num);

    // Step 2: enforce lower ≤ upper (the partition invariant)
    // If the new max of lower exceeds the min of upper, move it up
    if (
      this.upperMin.length > 0 &&
      this._peekMax(this.lowerMax) > this._peekMin(this.upperMin)
    ) {
      this._insertMin(this.upperMin, this._extractMax(this.lowerMax));
    }

    // Step 3: rebalance sizes (lower can have at most 1 more element than upper)
    if (this.lowerMax.length > this.upperMin.length + 1) {
      this._insertMin(this.upperMin, this._extractMax(this.lowerMax));
    } else if (this.upperMin.length > this.lowerMax.length) {
      this._insertMax(this.lowerMax, this._extractMin(this.upperMin));
    }
  }

  findMedian() {
    if (this.lowerMax.length > this.upperMin.length) {
      return this._peekMax(this.lowerMax); // odd total: median is the extra element
    }
    return (this._peekMax(this.lowerMax) + this._peekMin(this.upperMin)) / 2;
  }

  // ---- Heap helpers (using negation trick for max-heap via min-heap arrays) ----
  _insertMax(heap, val) { this._siftUp(heap, -val); }
  _extractMax(heap)     { return -this._extractMin(heap); }
  _peekMax(heap)        { return -heap[0]; }

  _insertMin(heap, val) { this._siftUp(heap, val); }
  _extractMin(heap) {
    const min = heap[0];
    heap[0] = heap[heap.length - 1];
    heap.pop();
    if (heap.length > 0) this._siftDown(heap, 0);
    return min;
  }
  _peekMin(heap) { return heap[0]; }

  _siftUp(heap, val) {
    heap.push(val);
    let i = heap.length - 1;
    while (i > 0) {
      const p = Math.floor((i - 1) / 2);
      if (heap[i] < heap[p]) { [heap[i], heap[p]] = [heap[p], heap[i]]; i = p; }
      else break;
    }
  }

  _siftDown(heap, i) {
    const n = heap.length;
    while (true) {
      let smallest = i;
      const l = 2*i+1, r = 2*i+2;
      if (l < n && heap[l] < heap[smallest]) smallest = l;
      if (r < n && heap[r] < heap[smallest]) smallest = r;
      if (smallest === i) break;
      [heap[i], heap[smallest]] = [heap[smallest], heap[i]];
      i = smallest;
    }
  }
}
```

### Dry Run

```
addNum(1):
  insert 1 into lowerMax. lowerMax=[1], upperMin=[].
  upperMin empty → skip partition check.
  sizes: lower=1, upper=0. lower ≤ upper+1 ✓. No rebalance.

addNum(2):
  insert 2 into lowerMax. lowerMax=[2,1].
  peek lower=2, peek upper=∞ (empty) → no violation.
  sizes: lower=2, upper=0. 2 > 0+1 → move max(2) to upper.
  lowerMax=[1], upperMin=[2].

findMedian():
  sizes equal (1,1). return (1+2)/2 = 1.5 ✓

addNum(3):
  insert 3 into lowerMax. lowerMax=[3,1].
  peek lower=3, peek upper=2. 3 > 2 → move 3 to upper.
  lowerMax=[1], upperMin=[2,3].
  sizes: lower=1, upper=2. upper > lower → move min(2) to lower.
  lowerMax=[2,1], upperMin=[3].

findMedian():
  lower.size=2, upper.size=1. lower > upper → return peekMax(lower)=2 ✓
```

### Complexity
- Time: O(log n) per `addNum` (two heap operations, each O(log n)), O(1) per `findMedian`.
- Space: O(n) — all n added elements are stored across the two heaps.

### Edge Cases
- Single element added: only `lowerMax` holds it; `findMedian` returns it directly (odd count, max-heap root). ✓
- All elements equal: both heaps eventually hold equal values; the partition invariant (`lower ≤ upper`) holds trivially; median is always that value. ✓
- Alternating very large and very small values: the two-step process (insert into lower, check partition, rebalance) correctly handles any ordering of insertions. ✓
- Even vs. odd count: `findMedian` correctly returns the root of the larger heap (always `lowerMax` by the rebalancing invariant) for odd count, and the average of both roots for even count. ✓

### Follow-up Questions
- "What if you need the median at every step as a stream?" → Call `findMedian()` after each `addNum()`. Each call is O(1); total cost is O(n log n) for n insertions, O(n) for n median queries.
- "What if values are bounded (e.g., integers from 1–100)?" → Use a counting sort array of size 101 and maintain a running count and median pointer updated in O(1) per insertion — dramatically faster than the heap approach when the value range is small.

## Quick Reference — Pattern Decision Tree

```
Heap / Heap Sort problem — which algorithm applies?
│
├── SORTING an unordered array, O(1) space required?
│   └── Heap Sort: buildHeap (O(n)) + n-1 extractions (O(n log n))
│         Guaranteed O(n log n) worst case, in-place, not stable
│         → Use when: memory constrained, worst-case guarantee required
│         → Avoid when: cache performance matters or stability required
│
├── SORTING needed but O(n) space acceptable?
│   ├── Stability required → Merge Sort (O(n log n), O(n) space)
│   └── Average-case performance prioritized → Quicksort (O(n log n) avg)
│         (Both outperform heap sort in practice due to cache behavior)
│
├── K LARGEST / K SMALLEST elements?
│   ├── k << n → Min-heap of size k: O(n log k) time, O(k) space
│   │   (insert first k, for each remaining: if > heap root, replace and heapify)
│   └── k ≈ n → Full heap sort + slice: O(n log n)
│
├── NEARLY SORTED (k-sorted) array?
│   └── Min-heap of size k+1, sliding window extraction
│         O(n log k) time, O(k) space
│         Degrades to O(n log n) as k→n
│
├── MERGE k SORTED arrays/lists?
│   └── Min-heap of size k with source tracking
│         O(N log k) where N = total elements across all arrays
│         O(k) heap space + O(N) output
│
├── STREAMING MEDIAN (dynamic insert + query)?
│   └── Two-heap partition: max-heap (lower half) + min-heap (upper half)
│         O(log n) per insert, O(1) per median query
│         Invariants: maxHeap.root ≤ minHeap.root, |sizes| ≤ 1
│
├── PRIORITY QUEUE operations (insert, extractMax, peek)?
│   └── Binary max-heap: O(log n) insert/extract, O(1) peek
│         buildHeap from n elements: O(n) (NOT O(n log n))
│         Sift-up for insert, sift-down for extract
│
└── SORTED array → height-balanced structure?
      Midpoint selection (not a heap problem — see Balanced Tree guide)
```

## Common Bugs Checklist

Before submitting any heap / heap sort solution, verify:

1. **`heapify` called with current heap size `i` (shrinking), NOT the original array size `n`, during the extraction phase?** — Using `heapify(arr, n, 0)` instead of `heapify(arr, i, 0)` in the extraction loop includes already-sorted elements at `arr[i..n-1]` in the heapify comparison range, potentially displacing them from their correct sorted positions. The heap size must decrease by 1 after each extraction.

2. **Build-heap starts from `floor(n/2) - 1` (last non-leaf), NOT from `n-1` (last element)?** — Starting from `n-1` applies heapify to leaves (which trivially satisfy the heap property and need no processing), wastes time, and is harmless but signals a misunderstanding of the algorithm. Starting from beyond `floor(n/2)-1` toward the root is the correct and efficient approach.

3. **`heapify` checks BOTH children before deciding the largest/smallest?** — Only checking the left child misses cases where the right child is larger (or smaller for min-heap); only checking the right child makes the left child inaccessible. Both children must be compared against the current node to correctly identify the extremum.

4. **Child index bounds check `left < n` and `right < n` present BEFORE accessing `arr[left]` or `arr[right]`?** — Accessing `arr[left]` without checking `left < n` causes an out-of-bounds read for leaf nodes (whose children don't exist within the heap). The bounds check must precede the value comparison, not follow it.

5. **`heapify`'s recursive call (or iterative update) uses `largest` (the child index), NOT `i` (the current node)?** — After swapping, the violation has moved to the child at `largest`. Recursing at `i` again would re-check the same node (now holding the smaller swapped value), causing an infinite loop or incorrect result. The recursive call must be `heapify(arr, n, largest)`.

6. **Min-heap comparisons use `<` consistently (not `>`), and max-heap uses `>` consistently?** — Mixing comparison directions within a single heapify function produces a broken heap that satisfies neither the max-heap nor min-heap property. Any problem combining both (e.g., two-heap median finder) must clearly separate the two heap implementations.

7. **`globalMax` (or result variable) initialized correctly for the k-largest problem: heap built from first k elements, NOT from all n?** — Building the initial heap from all n elements wastes O(n) space and O(n) build time compared to the O(k) build from the first k elements. More critically, the comparison in the main loop (`nums[i] > heap[0]`) must start from index `k`, not from index 0 (which would re-process the initial heap elements).

8. **Two-heap median finder: new element added to `lowerMax` first, THEN partition invariant checked, THEN sizes rebalanced (in that order)?** — Adding directly to `upperMin` first can violate the partition invariant (lower's max > upper's min) in the opposite direction. The three-step order (insert lower → fix partition → fix sizes) is not arbitrary — it ensures both invariants are correctly restored after every insertion.

9. **`findMedian` returns `lowerMax.root` (not `upperMin.root`) when sizes are unequal?** — The rebalancing invariant keeps `lowerMax` as the heap that holds the extra element when the total count is odd. If the size check is accidentally inverted (`upperMin.length > lowerMax.length`), the returned root is always from the wrong heap, giving an incorrect median.

10. **K-sorted merge: initial heap built from `min(k+1, n)` elements, not exactly `k+1`?** — For arrays shorter than `k+1` elements, slicing `arr.slice(0, k+1)` reads beyond the array end (silently returning `undefined` values in JavaScript, which corrupt the heap comparisons). The `Math.min(k+1, n)` guard prevents this.

---

**Final Tip:** At the 5–7 YOE level, the key signal is understanding **why** build-heap is O(n) (the geometric series argument over levels — most nodes are near the bottom with short sift-down distances) rather than the naive O(n log n) estimate. Equally important: proactively acknowledging heap sort's practical weakness (poor cache locality due to non-sequential memory access patterns in heapify) and naming the conditions under which it genuinely beats alternatives (hard real-time worst-case guarantees, strict O(1) auxiliary space constraints). Connecting heap sort to priority queues — "heap sort is just buildHeap followed by n extractMax calls" — shows fluency with the underlying abstraction rather than treating heap sort as an isolated algorithm.
