# DSA: Min-Heap & Max-Heap Construction — Theory, Interview Q&A & Practical Problems

---

## Part 1 — Theory & Interview Q&A

---

### Section 1: Fundamentals

**Q1. What is a heap?**
A: A heap is a complete binary tree stored implicitly in an array that satisfies the **heap property** — a structural invariant about the relationship between every parent node and its children. "Complete binary tree" means all levels are fully filled except possibly the last, which is filled left to right. The implicit array storage works because the tree's shape is predictable: for a node at index `i` (0-indexed), its left child is at `2i + 1`, its right child at `2i + 2`, and its parent at `Math.floor((i - 1) / 2)`. No pointers needed — the structure lives entirely in arithmetic.

**Q2. What is the difference between a min-heap and a max-heap?**
A: The difference is the direction of the heap property:
- **Min-heap**: every parent is ≤ both its children. Consequence: the minimum element is always at index 0 (the root). Extracting the minimum is O(log n).
- **Max-heap**: every parent is ≥ both its children. Consequence: the maximum element is always at index 0 (the root). Extracting the maximum is O(log n).

Both have identical structure and identical operation complexity — the only difference is the comparison direction in the `sift-up` and `sift-down` operations. Min-heap is used for priority queues serving smallest-first; max-heap for largest-first.

**Q3. What does the heap property guarantee and what does it NOT guarantee?**
A: The heap property guarantees:
- The root is the global minimum (min-heap) or maximum (max-heap).
- Every subtree rooted at any node also satisfies the heap property locally.

It does NOT guarantee:
- Any sorted order among siblings — a left child can be larger or smaller than a right child.
- Any relationship between elements on the same level beyond the parent constraint.
- Efficient search — finding an arbitrary element requires O(n) linear scan because there's no ordering across subtrees.

This is a common misconception to flag in interviews: heaps are not sorted arrays. They only guarantee the extremum at the root.

**Q4. What is the array representation of a heap, and why is it space-efficient?**
A: A heap is stored as a flat array with the following index relationships (0-indexed):

```
Parent of node i:      Math.floor((i - 1) / 2)
Left child of node i:  2 * i + 1
Right child of node i: 2 * i + 2
```

For a heap of n elements, the array has exactly n entries — no null pointers, no left/right pointer fields, no overhead per node. A pointer-based binary tree needs 3 fields per node (value, left pointer, right pointer); an array heap needs 1 (value). This makes heaps extremely cache-friendly — array traversal is sequential memory access, which CPUs prefetch efficiently. For 1-indexed heaps (some textbooks): parent = `i >> 1`, left = `2i`, right = `2i + 1` — slightly simpler arithmetic.

**Q5. What is a complete binary tree, and why must a heap be one?**
A: A complete binary tree is one where all levels are fully filled except possibly the last, and the last level is filled left to right with no gaps. Heaps must be complete binary trees because:
- The completeness property is what allows the implicit array storage (the index arithmetic only works without gaps).
- It bounds the height to O(log n) — a complete binary tree of n nodes has height ⌊log₂ n⌋. This height bound is what makes insert and extract O(log n).
- A non-complete tree with gaps would require sentinel values or pointer-based storage, losing the space efficiency.

### Section 2: Core Operations

**Q6. What is sift-up (bubble-up), and when is it used?**
A: Sift-up restores the heap property after an element is added at the bottom (the end of the array). The new element may violate the heap property with its parent. Fix: compare the element with its parent; if the heap property is violated (e.g., new element < parent in a min-heap), swap them. Repeat with the new parent position. Continue until the element reaches the root or the heap property is satisfied.

```js
function siftUp(heap, i) {
  while (i > 0) {
    const parent = Math.floor((i - 1) / 2);
    if (heap[parent] <= heap[i]) break; // min-heap property satisfied
    [heap[parent], heap[i]] = [heap[i], heap[parent]]; // swap
    i = parent; // move up
  }
}
```

Time: O(log n) — at most height swaps, one per level.

**Q7. What is sift-down (bubble-down), and when is it used?**
A: Sift-down restores the heap property after the root is removed and replaced with the last element (or after an arbitrary element is decreased/increased in priority). The element at the current position may violate the heap property with its children. Fix: find the smaller child (min-heap); if that child is smaller than the current element, swap. Repeat at the new position. Continue until no child is smaller or the element is a leaf.

```js
function siftDown(heap, i, size) {
  while (true) {
    let smallest = i;
    const left = 2 * i + 1;
    const right = 2 * i + 2;

    if (left < size && heap[left] < heap[smallest]) smallest = left;
    if (right < size && heap[right] < heap[smallest]) smallest = right;

    if (smallest === i) break; // heap property satisfied

    [heap[smallest], heap[i]] = [heap[i], heap[smallest]];
    i = smallest; // move down
  }
}
```

Time: O(log n) — at most height swaps.

**Q8. What is the difference between sift-up and sift-down in terms of when each is called?**
A:
- **Sift-up**: called after inserting a new element at the end. The tree structure is already valid (complete), but the heap property may be violated on the path from the new node to the root. Sift-up walks upward.
- **Sift-down**: called after replacing the root with the last element (during extract-min/max) or after heapify-in-place. The element at the top may be too large (min-heap) — it needs to sink to its correct position. Sift-down walks downward, always swapping with the smaller (min-heap) or larger (max-heap) child.
- **Key asymmetry**: sift-down is used in heap construction (heapify) because it's more efficient — applying sift-down from n/2 to 0 is O(n), whereas applying sift-up from 0 to n-1 is O(n log n).

**Q9. How do you insert an element into a heap?**
A: Append the element to the end of the array (maintaining the complete tree shape), then sift-up from the last index:

```js
function insert(heap, val) {
  heap.push(val);            // append to end — complete tree maintained
  siftUp(heap, heap.length - 1); // restore heap property
}
```

Time: O(log n). The append is O(1) amortized (dynamic array); sift-up is O(log n).

**Q10. How do you extract the minimum (or maximum) from a heap?**
A: The minimum (min-heap) or maximum (max-heap) is always at index 0 (the root). To extract it while maintaining the heap:
1. Save the root value (the answer).
2. Move the last element to the root position (maintains complete tree shape).
3. Remove the last element (shrink the array).
4. Sift-down from the root to restore the heap property.

```js
function extractMin(heap) {
  if (heap.length === 0) return null;
  const min = heap[0];
  heap[0] = heap[heap.length - 1]; // move last to root
  heap.pop();                       // shrink
  if (heap.length > 0) siftDown(heap, 0, heap.length);
  return min;
}
```

Time: O(log n). Critically: you cannot just delete the root and re-heapify from scratch — that would be O(n). The swap-with-last + sift-down technique maintains O(log n).

### Section 3: Heap Construction

**Q11. What are the two ways to build a heap from an unsorted array, and what are their complexities?**
A: Two approaches:

**Approach 1 — Repeated insertion (n × sift-up)**:
Start with an empty heap. Insert each of the n elements one by one, sift-up after each insertion.
- Time: O(n log n) — n insertions × O(log n) each.
- This is the naive approach. Correct but suboptimal.

**Approach 2 — Floyd's heapify algorithm (n/2 × sift-down)**:
Treat the entire array as an already-placed complete binary tree (ignoring the heap property). Then, starting from the last non-leaf node (index `Math.floor(n/2) - 1`) down to the root (index 0), sift-down each node. Leaf nodes (indices n/2 to n-1) are trivially valid heaps by themselves. Working bottom-up ensures each sift-down has a valid heap below it.

```js
function buildHeap(arr) {
  const n = arr.length;
  // start from last non-leaf node, work up to root
  for (let i = Math.floor(n / 2) - 1; i >= 0; i--) {
    siftDown(arr, i, n);
  }
  return arr; // arr is now a valid heap in-place
}
```

- Time: O(n) — counterintuitive but provably linear (see Q12).
- Space: O(1) — in-place, no extra array.

**Q12. Why is Floyd's heapify O(n) and not O(n log n)?**
A: The O(n) result is non-obvious and worth explaining carefully. The key observation: most nodes are near the bottom of the tree and have small subtrees — sift-down on them is cheap.

Level analysis (for a heap of height h = log n):
- Level h (leaves): n/2 nodes, each sifts down 0 levels. Cost: 0.
- Level h-1: n/4 nodes, each sifts down at most 1 level. Cost: n/4 × 1.
- Level h-2: n/8 nodes, each sifts down at most 2 levels. Cost: n/8 × 2.
- Level k from bottom: n/2^(k+1) nodes, each sifts down at most k levels. Cost: n × k/2^(k+1).

Total cost = n × Σ(k=0 to h) k/2^(k+1) = n × Σ(k=1 to ∞) k/2^k = n × 2 = O(n).

The series Σ k/2^k converges to 2 — this is the mathematical reason heapify is O(n). The intuition: you do a lot of cheap sift-downs near the bottom (many small trees) and only a few expensive sift-downs near the top (one large tree rooted at the root). The bottom-heaviness of the binary tree is what makes this work.

**Q13. Why does Floyd's heapify start from index `Math.floor(n/2) - 1` and not from `n - 1`?**
A: Nodes from index `Math.floor(n/2)` to `n-1` are all leaf nodes — they have no children and trivially satisfy the heap property (nothing to violate it against). Sifting them down would be a no-op. The last non-leaf node is at index `Math.floor(n/2) - 1` — this is the parent of the last leaf (the last element, at index `n-1`). Starting there ensures we process every node that has at least one child. Starting at `n-1` would waste time calling sift-down on leaves.

**Q14. Can you build a heap top-down (sift-up from index 0 to n-1) in O(n)?**
A: No — the top-down approach (inserting elements one by one with sift-up) is inherently O(n log n). The O(n) linear bound is specific to the bottom-up sift-down approach. The asymmetry: sift-down costs O(k) for a node at height k from the bottom (cheap for low nodes). Sift-up costs O(log n - k) for a node at depth k from the top (cheap for deep nodes but there are many of them proportionally). The bottom-up sift-down approach exploits the fact that most nodes are near the bottom (cheap to sift-down), while the top-down sift-up approach does expensive sift-ups on the many deep nodes.

**Q15. When would you use O(n log n) insertion vs O(n) heapify?**
A: Use O(n) heapify when all elements are known upfront — batch construction. Use O(n log n) repeated insertion when elements arrive one at a time (streaming) and you need the heap to be valid after each insertion. In interviews: if given an array and asked to build a heap, always use Floyd's O(n) heapify and explicitly name the complexity. If given a stream, use repeated insertion and note the amortized O(1) insertion with O(log n) sift-up.

### Section 4: Advanced Heap Concepts

**Q16. What is a `decrease-key` operation and how is it implemented?**
A: Decrease-key (for min-heap) reduces the value of an element at a known position. Since the new value is smaller, it may now violate the heap property with its parent — sift-up to restore it. Increase-key does the reverse — sift-down. These operations require knowing the element's current index — standard array heaps don't support O(log n) arbitrary-element updates unless an index map is maintained alongside the heap. This is how Dijkstra's algorithm with a binary heap works: maintain a `position` map from node ID to heap index, update on every swap during sift operations. O(log n) time. Without the map, finding the element first is O(n), making the total O(n) — which defeats the purpose.

**Q17. What is a d-ary heap, and when is it better than a binary heap?**
A: A d-ary heap generalizes the binary heap by giving each node d children instead of 2. The index relationships: child j of node i is at `d*i + j + 1` (for j in 0..d-1); parent of node i is at `Math.floor((i-1)/d)`.

Trade-offs vs binary heap:
- **Sift-up**: O(log_d n) — faster (shallower tree). Good when insertions dominate.
- **Sift-down**: O(d × log_d n) — slower (d children to compare per level). Bad when extractions dominate.
- **Cache performance**: higher d means more siblings fit in one cache line — better locality for sift-down comparisons in practice.

A 4-ary heap is often faster in practice than a binary heap for Dijkstra's algorithm (many decrease-key operations, few extract-min operations) due to cache effects. The Fibonacci heap achieves O(1) amortized decrease-key but has high constant factors — rarely faster in practice despite theoretical superiority.

**Q18. What is heap sort, and how does it use heap construction?**
A: Heap sort is an O(n log n) in-place comparison sort built on heap operations:
1. **Build max-heap** in-place using Floyd's algorithm: O(n).
2. **Extract max n times**: swap root (max) with last element, shrink heap size by 1, sift-down the new root. Repeat n-1 times.

After step 2, the array is sorted in ascending order (largest elements placed at the end first, left to right). Total: O(n) + O(n log n) = O(n log n). In-place with O(1) extra space. Not stable (equal elements may swap relative order during sift-down).

In practice, heap sort is rarely used vs quicksort (better cache performance) or mergesort (stable). It's theoretically important: guaranteed O(n log n) worst case (unlike quicksort's O(n²) worst case) with O(1) space (unlike mergesort's O(n) space).

**Q19. What are the time complexities of all heap operations?**
A: Summary table:

| Operation          | Time Complexity         | Notes                                          |
|--------------------|-------------------------|------------------------------------------------|
| Build (heapify)    | O(n)                    | Floyd's bottom-up sift-down                    |
| Build (n inserts)  | O(n log n)              | Naive — use only for streaming input           |
| Insert             | O(log n)                | Append + sift-up                               |
| Extract min/max    | O(log n)                | Swap root with last + sift-down                |
| Peek min/max       | O(1)                    | `heap[0]` — always                             |
| Delete arbitrary   | O(log n)                | Requires index map; decrease-key + extract     |
| Decrease-key       | O(log n)                | Requires index map; sift-up                    |
| Search             | O(n)                    | No ordering — must scan                        |
| Merge two heaps    | O(n)                    | Concatenate + heapify; Fibonacci heap: O(1)    |

**Q20. What is the difference between a heap and a binary search tree (BST) for the same use case?**
A: This is a common comparison question at 5 YOE:

| Aspect               | Heap                          | BST (balanced)                  |
|----------------------|-------------------------------|----------------------------------|
| Find min/max         | O(1) — always at root         | O(log n) — leftmost/rightmost    |
| Extract min/max      | O(log n)                      | O(log n)                         |
| Insert               | O(log n)                      | O(log n)                         |
| Search arbitrary     | O(n) — no ordering            | O(log n) — ordered               |
| Space                | O(n) — array, no pointers     | O(n) — nodes with pointers       |
| In-order traversal   | Not meaningful                | O(n) sorted output               |
| Build from array     | O(n) heapify                  | O(n log n) successive inserts    |
| Use case             | Priority queue, k-th element  | Ordered set, range queries       |

Use a heap when you only care about repeatedly extracting the extremum. Use a BST when you need ordered traversal, range queries, or O(log n) search.

### Section 5: Common Patterns

**Q21. What is the "k-th largest element" pattern using a heap?**
A: Maintain a min-heap of size k. For each element in the array: push to the heap. If the heap exceeds size k, extract the minimum. After processing all elements, the min-heap's root (`heap[0]`) is the k-th largest element (it's the smallest among the k largest).

Why min-heap for k-th largest? The heap keeps the k largest elements seen so far. The minimum of those k elements is the k-th largest overall. O(n log k) time — much better than O(n log n) sort when k ≪ n.

**Q22. What is the "merge k sorted lists" pattern using a heap?**
A: Use a min-heap of size k storing (value, list_index, element_index) tuples. Initialize with the first element from each of the k lists. Repeatedly extract the minimum, add it to the result, and push the next element from the same list (if any). O(n log k) where n is total elements — each of the n elements is pushed and popped once, each operation O(log k).

**Q23. What is the "top k frequent elements" pattern?**
A: Count frequencies with a hash map. Then use a min-heap of size k on (frequency, element) pairs. For each (element, freq) pair: push to heap; if heap size exceeds k, extract min. After processing, the heap contains the k most frequent elements. O(n + m log k) where m is the number of distinct elements. The min-heap keeps the k highest frequencies — same logic as k-th largest but applied to frequencies.

**Q24. What is the two-heap pattern for median finding?**
A: Maintain two heaps:
- **Max-heap** (lower half): stores the smaller half of numbers seen so far. Root = median candidate from below.
- **Min-heap** (upper half): stores the larger half. Root = median candidate from above.

Invariant: max-heap size is equal to or one more than min-heap size. The median is the max-heap root (odd count) or average of both roots (even count).

On insert:
1. Push to max-heap.
2. If max-heap root > min-heap root (order violated), move max-heap root to min-heap.
3. Rebalance sizes: if size difference > 1, move root of larger heap to smaller heap.

O(log n) per insert, O(1) for median. This pattern appears in "Find Median from Data Stream" (LeetCode 295).

**Q25. How does a heap implement a priority queue, and what operations does a PQ support?**
A: A heap is the standard underlying data structure for a priority queue. The PQ interface:
- `enqueue(val, priority)` → heap insert, O(log n).
- `dequeue()` → extract min/max, O(log n).
- `peek()` → read root, O(1).
- `changePriority(val, newPriority)` → decrease-key/increase-key with index map, O(log n).

Most language built-ins (Python's `heapq`, Java's `PriorityQueue`, C++'s `priority_queue`) implement this with a binary heap. JavaScript has no built-in — you implement it manually or use a library. Python's `heapq` is a min-heap; for max-heap behavior, negate values.

### Section 6: Scenario / Interview-Style Questions

**Q26. "You're given an array of 1 million integers and need to find the 100 largest. You have very limited memory. What's your approach?"**
A: Min-heap of size 100. Iterate through the array: push each element; if heap size exceeds 100, extract the minimum. After the full pass, the heap contains the 100 largest elements. O(n log k) time (n=1M, k=100) — roughly 1M × 7 = 7M operations. Space: O(k) = O(100) — only 100 elements in memory at any time (plus the input stream, which can be processed sequentially without loading into RAM). This is the streaming-compatible approach — you never need more than k+1 elements in memory simultaneously.

**Q27. "A colleague built a heap by inserting elements one by one and says it's O(n). You disagree. Explain why and what the correct complexity is."**
A: Inserting n elements one by one, each with sift-up, is O(n log n) — not O(n). Each insertion is O(log n) in the worst case (new element must sift all the way to the root); n such insertions give O(n log n) total. The O(n) bound applies specifically to Floyd's bottom-up heapify — treating the entire array as an unordered complete tree and sifting-down from n/2-1 to 0. The two approaches are not equivalent in complexity: O(n) heapify vs O(n log n) repeated insertions. The correct approach when all elements are known upfront is always Floyd's heapify.

**Q28. "Design a system that always returns the k-th smallest element from a dynamic stream of numbers in O(log k) per insertion. Walk through the data structure."**
A: Use a max-heap of size k. On each new element:
- Push to the max-heap.
- If heap size exceeds k, extract the maximum.
- The k-th smallest is the root of the max-heap (the largest of the k smallest seen so far).

Why max-heap for k-th smallest? The heap keeps the k smallest elements. The maximum of those k elements is the k-th smallest overall. `heap[0]` (the root of the max-heap) is always the current k-th smallest — O(1) peek. Each insertion is O(log k). This is LeetCode 703 "Kth Largest Element in a Stream" reversed.

**Q29. "An interviewer asks you to implement Dijkstra's shortest path algorithm. Where does the heap fit in, and what complexity does it give?"**
A: Dijkstra's algorithm uses a min-heap (priority queue) ordered by tentative distance from the source. The heap always yields the unvisited node with the smallest known distance — the greedy choice. Operations:
- Initialize: push (0, source) to the heap. O(1).
- Main loop: extract-min from heap → O(log V). For each neighbor: if new distance is shorter, push (new_dist, neighbor) → O(log V). At most E such pushes total.
- Total: O((V + E) log V) with a binary heap.

With a Fibonacci heap: O(V log V + E) — decrease-key is O(1) amortized instead of O(log V). In practice, binary heap Dijkstra is used because Fibonacci heaps have high constant factors. The heap is the core of Dijkstra's efficiency — without it (using a linear scan for minimum), Dijkstra is O(V²).

## Problem 0 — Heap Implementation From Scratch

### Problem
Implement a min-heap class from scratch supporting: `insert(val)`, `extractMin()`, `peek()`, `size()`, and `buildHeap(arr)`.

### Pattern Recognition
Foundation problem — every heap-based problem rests on these primitives. At 5 YOE, you're expected to implement sift-up, sift-down, and Floyd's heapify cleanly and quickly.

### Key Insight
The heap lives in an array. The two operations — sift-up (after insert) and sift-down (after extract and during heapify) — use the index arithmetic `parent = (i-1)>>1`, `left = 2i+1`, `right = 2i+2`.

### Solution

```js
class MinHeap {
  constructor() {
    this.heap = [];
  }

  size() {
    return this.heap.length;
  }

  peek() {
    return this.heap.length > 0 ? this.heap[0] : null;
  }

  // O(log n) — append then sift up
  insert(val) {
    this.heap.push(val);
    this._siftUp(this.heap.length - 1);
  }

  // O(log n) — swap root with last, shrink, sift down
  extractMin() {
    if (this.heap.length === 0) return null;
    if (this.heap.length === 1) return this.heap.pop();

    const min = this.heap[0];
    this.heap[0] = this.heap.pop(); // move last element to root
    this._siftDown(0);
    return min;
  }

  // O(n) — Floyd's bottom-up heapify
  buildHeap(arr) {
    this.heap = [...arr];
    const n = this.heap.length;

    // start from last non-leaf node, sift-down each node
    for (let i = Math.floor(n / 2) - 1; i >= 0; i--) {
      this._siftDown(i);
    }
    return this;
  }

  // Restore heap property upward from index i
  _siftUp(i) {
    while (i > 0) {
      const parent = (i - 1) >> 1; // Math.floor((i-1)/2)
      if (this.heap[parent] <= this.heap[i]) break; // heap property ok
      this._swap(parent, i);
      i = parent;
    }
  }

  // Restore heap property downward from index i
  _siftDown(i) {
    const n = this.heap.length;

    while (true) {
      let smallest = i;
      const left  = 2 * i + 1;
      const right = 2 * i + 2;

      if (left < n && this.heap[left] < this.heap[smallest]) {
        smallest = left;
      }
      if (right < n && this.heap[right] < this.heap[smallest]) {
        smallest = right;
      }

      if (smallest === i) break; // both children are >= current, stop

      this._swap(i, smallest);
      i = smallest; // continue sifting down
    }
  }

  _swap(i, j) {
    [this.heap[i], this.heap[j]] = [this.heap[j], this.heap[i]];
  }
}
```

### Max-Heap Variant
Only one line changes — the comparison direction in `_siftUp` and `_siftDown`:

```js
class MaxHeap extends MinHeap {
  _siftUp(i) {
    while (i > 0) {
      const parent = (i - 1) >> 1;
      if (this.heap[parent] >= this.heap[i]) break; // max-heap property
      this._swap(parent, i);
      i = parent;
    }
  }

  _siftDown(i) {
    const n = this.heap.length;
    while (true) {
      let largest = i;
      const left  = 2 * i + 1;
      const right = 2 * i + 2;

      if (left < n && this.heap[left] > this.heap[largest]) largest = left;
      if (right < n && this.heap[right] > this.heap[largest]) largest = right;

      if (largest === i) break;

      this._swap(i, largest);
      i = largest;
    }
  }
}
```

### Edge Cases
- `extractMin()` on empty heap → return null (guard `heap.length === 0`).

- Already min-heap ordered → sift-downs are all no-ops. O(n) time but O(1) actual work.

- "How do you convert this to a max-heap?" → Reverse comparison in `_siftUp` and `_siftDown` (shown above).
- "How do you support arbitrary deletion?" → Maintain an index map (value/ID → heap index); on every swap, update the map. Then decrease-key or increase-key plus sift appropriately.
- "Is this heap stable (preserves insertion order for equal elements)?" → No. The heap property only specifies the parent-child relationship by value; equal elements can swap relative order. For stable priority, include an insertion sequence number as a tiebreaker in the comparison.

## Problem 1 — Kth Largest Element in an Array (LeetCode 215)

### Problem
Given an integer array `nums` and integer `k`, return the k-th largest element. Note: it is the k-th largest in sorted order, not the k-th distinct element.

```
Input:  nums=[3,2,1,5,6,4], k=2    → 5
Input:  nums=[3,2,3,1,2,4,5,5,6], k=4  → 4
```

### Pattern Recognition
K-th extremum from an array — canonical min-heap of size k problem. Keep the k largest elements; the root is the k-th largest. O(n log k) time, O(k) space.

### Key Insight
A min-heap of size k holds the k largest elements seen so far. The minimum of those k elements (the root) is the k-th largest overall. When a new element arrives: if it's larger than the root (i.e., it belongs in the top k), push it and pop the old minimum.

### Approach
Iterate through `nums`. For each element: push onto the min-heap. If heap size exceeds k, extract the minimum (evict the smallest of the top-k). After the full pass, `heap[0]` is the k-th largest.

### Solution

```js
function findKthLargest(nums, k) {
  // Min-heap of size k — keeps k largest elements
  // Using MinHeap class from Problem 0
  const heap = new MinHeap();

  for (const num of nums) {
    heap.insert(num);

    if (heap.size() > k) {
      heap.extractMin(); // evict the smallest — it's not in the top k
    }
  }

  return heap.peek(); // root = smallest of the k largest = k-th largest
}
```

### Inline Array Heap (No Class)

function findKthLargest(nums, k) {
  const heap = [];

  function siftUp(i) {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (heap[p] <= heap[i]) break;
      [heap[p], heap[i]] = [heap[i], heap[p]];
      i = p;
    }
  }

  function siftDown(i) {
    const n = heap.length;
    while (true) {
      let s = i;
      const l = 2*i+1, r = 2*i+2;
      if (l < n && heap[l] < heap[s]) s = l;
      if (r < n && heap[r] < heap[s]) s = r;
      if (s === i) break;
      [heap[s], heap[i]] = [heap[i], heap[s]];
      i = s;
    }
  }

  for (const num of nums) {
    heap.push(num);
    siftUp(heap.length - 1);
    if (heap.length > k) {
      heap[0] = heap.pop();
      siftDown(0);
    }
  }

  return heap[0]; // k-th largest
}

## Problem 2 — K Closest Points to Origin (LeetCode 973)

### Problem
Given an array of points `[xi, yi]` and integer `k`, return the `k` closest points to the origin (0,0). Distance = `sqrt(xi² + yi²)`. You may return the answer in any order.

```
Input:  points=[[1,3],[-2,2]], k=1   → [[-2,2]]
Input:  points=[[3,3],[5,-1],[-2,4]], k=2  → [[3,3],[-2,4]]
```

### Pattern Recognition
K-th smallest distance — max-heap of size k keeps k closest points. The heap is ordered by distance; the maximum-distance point in the heap is evicted when a closer one arrives.

### Key Insight
Keep the k closest points seen so far in a max-heap ordered by distance. When a new point arrives: push it; if the heap exceeds size k, extract the maximum (farthest point in the heap — it's not in the k closest). After the full pass, the heap contains exactly the k closest points.

### Approach
Avoid `sqrt` (unnecessary for comparison — compare squared distances). Max-heap on squared distance. Extract when size > k.

### Solution

```js
function kClosest(points, k) {
  // Max-heap ordered by squared distance
  // Simulate with negated distances on a min-heap
  // OR implement a max-heap comparator directly

  // Using a max-heap via negated distance trick:
  const heap = []; // stores [-dist², x, y]

  function siftUp(i) {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (heap[p][0] >= heap[i][0]) break; // max-heap: parent ≥ child
      [heap[p], heap[i]] = [heap[i], heap[p]];
      i = p;
    }
  }

  function siftDown(i) {
    const n = heap.length;
    while (true) {
      let largest = i;
      const l = 2*i+1, r = 2*i+2;
      if (l < n && heap[l][0] > heap[largest][0]) largest = l;
      if (r < n && heap[r][0] > heap[largest][0]) largest = r;
      if (largest === i) break;
      [heap[largest], heap[i]] = [heap[i], heap[largest]];
      i = largest;
    }
  }

  for (const [x, y] of points) {
    const dist2 = x*x + y*y; // squared distance — no sqrt needed
    heap.push([dist2, x, y]);
    siftUp(heap.length - 1);

    if (heap.length > k) {
      // remove farthest point from heap (max distance)
      heap[0] = heap.pop();
      if (heap.length > 0) siftDown(0);
    }
  }

  return heap.map(([_, x, y]) => [x, y]);
}
```

## Problem 3 — Find Median from Data Stream (LeetCode 295)

### Problem
Implement `MedianFinder` with `addNum(num)` and `findMedian()`. `findMedian()` returns the median of all numbers added so far.

```
MedianFinder mf = new MedianFinder();
mf.addNum(1);  mf.findMedian(); → 1.0
mf.addNum(2);  mf.findMedian(); → 1.5
mf.addNum(3);  mf.findMedian(); → 2.0
```

### Pattern Recognition
Two-heap pattern — the most important advanced heap pattern. Max-heap (lower half) and min-heap (upper half) maintained in balance. The median is at the boundary between the two halves.

### Key Insight
Divide numbers into two halves: lower half (max-heap, root = largest in lower half) and upper half (min-heap, root = smallest in upper half). Invariant: `lower.size === upper.size` (even count → average of both roots) or `lower.size === upper.size + 1` (odd count → lower root is median). The median is always reachable in O(1) by peeking at one or both roots.

### Approach
On `addNum(num)`:
1. Push to `lower` (max-heap) first.
2. If `lower.peek() > upper.peek()` (order violated: a lower-half element is bigger than upper-half elements) → move `lower.root` to `upper`.
3. Rebalance sizes: if `lower.size > upper.size + 1` → move `lower.root` to `upper`. If `upper.size > lower.size` → move `upper.root` to `lower`.

On `findMedian()`:
- If `lower.size > upper.size` → return `lower.peek()`.
- Else → return `(lower.peek() + upper.peek()) / 2`.

### Solution

```js
class MedianFinder {
  constructor() {
    this.lower = new MaxHeap(); // max-heap for lower half
    this.upper = new MinHeap(); // min-heap for upper half
  }

  addNum(num) {
    // Step 1: always add to lower first
    this.lower.insert(num);

    // Step 2: fix ordering — lower's max must be ≤ upper's min
    if (
      this.upper.size() > 0 &&
      this.lower.peek() > this.upper.peek()
    ) {
      this.upper.insert(this.lower.extractMax());
    }

    // Step 3: rebalance sizes (lower can have at most 1 more than upper)
    if (this.lower.size() > this.upper.size() + 1) {
      this.upper.insert(this.lower.extractMax());
    } else if (this.upper.size() > this.lower.size()) {
      this.lower.insert(this.upper.extractMin());
    }
  }

  findMedian() {
    if (this.lower.size() > this.upper.size()) {
      return this.lower.peek(); // odd total — median is top of lower
    }
    // even total — median is average of both tops
    return (this.lower.peek() + this.upper.peek()) / 2;
  }
}
```

### Complexity

### Edge Cases

- Two equal elements: lower=[1], upper=[1] → median=1.0. Correct.
- All same values: both heaps fill with equal values; ordering step never triggers a move (equal values don't violate `lower.peek() > upper.peek()` if strictly greater). Correct.
- Alternating large and small: rebalancing keeps sizes within 1; median tracks correctly.

- "Thread-safe version?" → Lock around both heap operations in `addNum` — they must be atomic as a unit (both heaps must be in consistent state before releasing the lock).

## Problem 4 — Merge K Sorted Lists (LeetCode 23)

### Problem
Given an array of `k` linked-list heads, each sorted in ascending order, merge all lists into one sorted linked list and return it.

```
Input:  lists = [[1→4→5], [1→3→4], [2→6]]
Output: 1→1→2→3→4→4→5→6
```

### Pattern Recognition
Merge k sorted sequences — min-heap of size k. Always extract the global minimum from the k current frontrunners, then push the next element from the same list. O(n log k) where n is total elements.

### Key Insight
At any point, the minimum of the k lists' current heads is the next element of the merged output. A min-heap of the k heads gives O(log k) access to this minimum and O(log k) update when the next element from that list is pushed.

### Approach
Initialize min-heap with the head of each non-null list (store node value + list index). Repeatedly extract the minimum node, append to the result list, and push that list's next node (if it exists) into the heap.

### Solution

```js
function mergeKLists(lists) {
  // Min-heap: [value, listIndex, node]
  const heap = [];

  function siftUp(i) {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (heap[p][0] <= heap[i][0]) break;
      [heap[p], heap[i]] = [heap[i], heap[p]];
      i = p;
    }
  }

  function siftDown(i) {
    const n = heap.length;
    while (true) {
      let s = i;
      const l = 2*i+1, r = 2*i+2;
      if (l < n && heap[l][0] < heap[s][0]) s = l;
      if (r < n && heap[r][0] < heap[s][0]) s = r;
      if (s === i) break;
      [heap[s], heap[i]] = [heap[i], heap[s]];
      i = s;
    }
  }

  // Initialize: push head of each non-empty list
  for (let i = 0; i < lists.length; i++) {
    if (lists[i] !== null) {
      heap.push([lists[i].val, i, lists[i]]);
      siftUp(heap.length - 1);
    }
  }

  const dummy = new ListNode(0);
  let curr = dummy;

  while (heap.length > 0) {
    // extract the node with minimum value
    const [val, listIdx, node] = heap[0];
    heap[0] = heap.pop();
    if (heap.length > 0) siftDown(0);

    curr.next = node;       // append to result
    curr = curr.next;

    // push the next node from the same list
    if (node.next !== null) {
      heap.push([node.next.val, listIdx, node.next]);
      siftUp(heap.length - 1);
    }
  }

  return dummy.next;
}
```

- "What if k is very large (k = 10,000 lists)?" → O(n log k) is still efficient. The heap stores k elements; each operation is O(log 10000) ≈ 13 comparisons. For n=1M total elements: 1M × 13 = 13M operations — fast.

- "Can you do better than O(n log k)?" → No lower bound is known to be better for comparison-based merging. This is optimal.

## Problem 5 — Task Scheduler (LeetCode 621)

### Problem
Given a list of tasks (characters) and a cooldown `n`, find the minimum number of intervals needed to finish all tasks. Same tasks must be at least `n` intervals apart. CPU can be idle between tasks.

```
Input:  tasks=["A","A","A","B","B","B"], n=2
Output: 8   (A→B→idle→A→B→idle→A→B)

Input:  tasks=["A","A","A","B","B","B"], n=0
Output: 6   (any order, no cooldown)
```

### Pattern Recognition
Greedy scheduling with a max-heap — always execute the most frequent remaining task first (to minimize idle time). A max-heap on task frequencies gives O(1) access to the most frequent task.

### Key Insight
Always run the task with the highest remaining count — this minimizes idle slots because the most constrained task (highest frequency) is given priority. Use a max-heap of frequencies. Process in rounds of `n+1` slots: in each round, take up to `n+1` most frequent tasks (one of each to respect cooldown within the round). If fewer than `n+1` tasks remain, pad with idle slots.

### Approach
Count frequencies. Build a max-heap of frequencies. Each round: extract up to `n+1` frequencies, decrement by 1, collect non-zero remainders, reinsert. Count `n+1` per full round or `remaining_tasks` for the last partial round.

### Solution

```js
function leastInterval(tasks, n) {
  // count task frequencies
  const freq = new Map();
  for (const t of tasks) freq.set(t, (freq.get(t) || 0) + 1);

  // max-heap of frequencies (negate for min-heap simulation)
  const heap = [...freq.values()].sort((a, b) => b - a); // sort descending
  // build as max-heap using negation trick on a min-heap
  // For clarity, use direct max-heap logic:

  const maxHeap = [...freq.values()];
  buildMaxHeap(maxHeap);

  let intervals = 0;

  while (maxHeap.length > 0) {
    const round = []; // tasks executed this round (up to n+1)

    // execute up to n+1 most frequent tasks this round
    for (let i = 0; i <= n; i++) {
      if (maxHeap.length > 0) {
        round.push(extractMax(maxHeap)); // take most frequent
      }
    }

    // re-insert tasks that still have remaining count
    for (const count of round) {
      if (count - 1 > 0) {
        insertMax(maxHeap, count - 1);
      }
    }

    // add time for this round:
    // if tasks remain after this round → full n+1 slots
    // if no tasks remain → only the actual tasks executed (no trailing idle)
    intervals += maxHeap.length > 0 ? n + 1 : round.length;
  }

  return intervals;
}

// Helper max-heap operations (max-heap with negation on standard min-heap):
function buildMaxHeap(arr) {
  for (let i = Math.floor(arr.length / 2) - 1; i >= 0; i--) {
    siftDownMax(arr, i, arr.length);
  }
}
function siftDownMax(heap, i, n) {
  while (true) {
    let largest = i;
    const l = 2*i+1, r = 2*i+2;
    if (l < n && heap[l] > heap[largest]) largest = l;
    if (r < n && heap[r] > heap[largest]) largest = r;
    if (largest === i) break;
    [heap[largest], heap[i]] = [heap[i], heap[largest]];
    i = largest;
  }
}
function extractMax(heap) {
  const max = heap[0];
  heap[0] = heap.pop();
  if (heap.length > 0) siftDownMax(heap, 0, heap.length);
  return max;
}
function insertMax(heap, val) {
  heap.push(val);
  let i = heap.length - 1;
  while (i > 0) {
    const p = (i-1) >> 1;
    if (heap[p] >= heap[i]) break;
    [heap[p], heap[i]] = [heap[i], heap[p]];
    i = p;
  }
}
```

### Complexity
- Time: O(n × k log k) where k = number of distinct tasks, n = cooldown. In practice O(total_tasks) since the heap is small (≤ 26 for letter tasks).
- Space: O(k) — heap and round buffer.

### Edge Cases
- `n = 0` → no cooldown → all tasks back-to-back → answer = `tasks.length`.
- Single task type with high frequency → maximum idle slots: `(freq-1) * n + 1`.
- All tasks distinct → no cooldown needed regardless of n → answer = `tasks.length`.

### Follow-up Questions
- "Mathematical formula instead of simulation?" → `answer = max(tasks.length, (maxFreq - 1) * (n + 1) + countOfMaxFreq)`. Derived from the idle-slot formula. O(n) time, O(1) space for counting. Worth mentioning as an optimization.
- "Return the actual schedule?" → Store task names (not just frequencies) in the heap and reconstruct the schedule in the round loop.

## Common Bugs Checklist

Before finalizing any heap solution, verify:

1. **siftDown boundary check** — always check `left < n` and `right < n` before comparing `heap[left]` or `heap[right]`. Accessing out-of-bounds silently returns `undefined` in JS — the comparison `undefined < heap[smallest]` is `false`, which happens to be correct, but relying on this is fragile and wrong in other languages.

2. **extractMin/Max on size-1 heap** — `heap[0] = heap.pop()` on a one-element array: `heap.pop()` returns the element and leaves the array empty. Then `heap[0] = undefined` sets index 0 of an empty array — which in JS creates `[undefined]` (a single-element array with `undefined`). Always guard: `if (heap.length === 1) return heap.pop()`.

3. **Floyd's heapify start index** — `Math.floor(n/2) - 1`, not `n/2` and not `n-1`. Off-by-one here processes leaves (wasted work) or skips the last non-leaf (incorrect heap).

4. **Max-heap vs min-heap comparison direction** — in `_siftDown`, the line `if (heap[left] < heap[smallest])` (min-heap) becomes `if (heap[left] > heap[largest])` (max-heap). Copy-pasting and forgetting to flip the comparison is the #1 heap bug.

5. **K-th largest uses min-heap, k-th smallest uses max-heap** — this counterintuitive pairing trips up many candidates. Repeat: "I want to keep the k largest, so I evict the smallest when the heap overflows → min-heap" until it's automatic.

6. **Heap for custom objects** — when heap elements are objects (e.g., `[dist, x, y]`), the comparison in sift operations must access the correct field (`heap[left][0]`), not compare the arrays directly (JS array comparison is by reference, not by value).
