## Topic A: The Top K Selection Problem

### Section A1: Fundamentals

**Q1. What is the top K selection problem, and what are the three canonical algorithmic approaches?**

A: The top K selection problem asks: "given n elements and a ranking criterion, find the K elements that rank highest (largest, smallest, most frequent, closest, etc.) without necessarily sorting all n elements." Three canonical approaches:

(1) **Sort + take K**: Sort all n elements by the ranking criterion; take the first K. O(n log n) time, O(1) extra space. Simple and universally applicable but ignores the fact that a full sort produces far more information (a complete ordering) than the problem requires.

(2) **Min-heap of size K**: Maintain a min-heap containing exactly the K best elements seen so far. For each new element, push it; if the heap exceeds size K, pop the minimum (evicting the weakest among the current top K). After all n elements: the heap holds the top K. O(n log k) time, O(k) space. Strictly better than sorting when k ≪ n; works for streaming inputs where all n elements aren't available at once.

(3) **Quickselect**: Partition the array around a pivot (the same step as in quicksort) — elements better than the pivot on one side, worse on the other — then recurse only on the half that contains the Kth element. O(n) average time, O(n²) worst case, O(1) extra space. Optimal average-case complexity but mutates the array and has poor worst-case behavior without randomized pivot selection.

```
Approach         Time        Space   Works streaming?  Mutates input?
Sort + take K    O(n log n)  O(1)    No                Optional
Min-heap size K  O(n log k)  O(k)    Yes               No
Quickselect      O(n) avg    O(1)    No                Yes
Bucket sort      O(n)        O(n)    No                No (frequency only)
```

**Q2. Why is a MIN-heap used to maintain the K LARGEST elements, and what is the invariant it preserves?**

A: The invariant is: *the min-heap holds exactly the K largest elements seen so far; its top (the minimum of those K) is the Kth largest element seen so far.* The minimum of the top K is kept at the heap's top because it is the "eviction candidate" — the weakest element among the current top K, the one that should be replaced first if a better element arrives. For each new element x: if x > heap.top(), then x belongs in the top K and the current Kth-largest does not — pop the top, push x. If x ≤ heap.top(), x cannot improve the top K — ignore it. A max-heap would place the largest at the top, giving no fast access to the weakest element in the top K — to find the weakest, we'd need to inspect all K elements, yielding O(nk) total, not O(n log k).

```
Min-heap of size K for top K LARGEST:
  heap.top() = SMALLEST of the top K = the "weakest" element = eviction candidate

  New element x arrives:
    x > heap.top(): x beats the current weakest → pop weakest, push x → O(log k)
    x ≤ heap.top(): x ≤ Kth largest → cannot enter top K → skip → O(1)

Max-heap of size K for top K LARGEST (wrong):
  heap.top() = LARGEST of the top K = tells us nothing about the weakest
  To evict the weakest: scan all K elements → O(k) per new element → O(nk) total ✗
```

**Q3. What is the expected O(n) argument for quickselect, and what causes the O(n²) worst case?**

A: Quickselect's expected cost analysis: if the pivot is chosen uniformly at random, there is a 1/2 probability it falls in the middle 50% of the array (positions n/4 to 3n/4). In that case, the remaining search space is at most 3n/4. Expected total comparisons across all recursion levels: n + (3/4)n + (3/4)²n + ... = n × 1/(1 − 3/4) = 4n = O(n). The O(n²) worst case arises when the pivot is always the minimum or maximum of the subarray — the search space shrinks by only 1 element per level, giving n + (n−1) + (n−2) + ... + 1 = O(n²) comparisons. A sorted (or reverse-sorted) array triggers this worst case with the common "choose last element as pivot" strategy. Randomized pivot selection (shuffle the array first, or randomly select the pivot index) restores the O(n) expected bound regardless of input order.

**Q4. What is the "frequency map then K-select" two-phase pattern, and why is it universal for "top K by computed score" problems?**

A: Any "top K by frequency / by some aggregated score" problem follows two phases: (1) **Aggregation**: build a HashMap `{element → score}` in O(n) — counting frequency, summing weights, etc.; (2) **K-selection**: apply one of the three K-selection algorithms to the (element, score) pairs, treating score as the ranking key. The two-phase separation cleanly decouples counting from selection, and each phase uses the simplest tool for its job. Most top-K-by-frequency problems are identical in structure — the only variation is the score function (raw count, inverse count, log-probability) and which K-selection algorithm best fits the given constraints (streaming → heap; O(n) time required → bucket sort; k ≪ n, arbitrary n → heap).

```
Phase 1 — Aggregation:  [1,1,2,2,2,3] → {1:2, 2:3, 3:1}    O(n)
Phase 2 — K-selection on scores:
  Option A: min-heap of size k on (score, element) pairs      O(n log k)
  Option B: bucket sort on scores (if bounded domain)          O(n)
  Option C: sort by score, take first k                        O(n log n)
```

**Q5. What is the bucket sort approach for "top K frequent," and why is it O(n)?**

A: Create an array of buckets indexed by frequency: `buckets[f]` = list of all elements whose frequency is exactly f. Frequencies are bounded: every element appears between 1 and n times, so bucket indices range from 0 to n — the array is of size n+1. After building the frequency map (O(n)), each element is placed into its frequency bucket (O(n) total placements). To find the top K frequent: scan buckets from index n down to 1, collecting elements into the result until K elements are accumulated. Since the scan visits at most n+1 buckets and collects at most n elements total, this step is also O(n). The crucial property that enables O(n): frequencies are *bounded integers in a known range* [1, n], making count-sort applicable. No comparison-based sorting is involved — the ordering is established by the bucket index directly.

```
nums = [1,1,1,2,2,3], k = 2

Step 1 — freq map:   {1:3, 2:2, 3:1}
Step 2 — buckets:    buckets[1]=[3], buckets[2]=[2], buckets[3]=[1]
                     index:   0    1    2    3
Step 3 — collect k=2 from high to low:
  bucket[3] = [1] → result = [1], need 1 more
  bucket[2] = [2] → result = [1, 2], done ✓

O(n) time: each step scans n elements total across all buckets.
Key: bucket index = frequency, so no comparison sort needed.
```

**Q6. What is the "bounded domain" insight that enables O(n) bucket sort, and when does it fail?**

A: Bucket sort achieves O(n) by exploiting a *bounded integer domain* for the sort key — here, frequencies are integers in [1, n], so we can use the frequency as a direct array index. This gives "free" sorting (the array position is the order). It fails when: (a) the sort key is not an integer (e.g., floating-point scores or custom string keys — no direct index); (b) the sort key range is too large relative to n (e.g., sorting by raw value when values can be up to 10^9 — an array of size 10^9 is infeasible); or (c) the key can be negative (requires offset adjustment, and may still have a huge range). The decision rule: *bucket sort is applicable when sort-key range ≤ O(n) and keys are non-negative integers.*

**Q7. What is the "Kth" (single element) vs "top K" (K elements) distinction, and how do the algorithms differ?**

A: "Kth largest" asks for one specific element — the element at rank K in descending order. "Top K largest" asks for the set of K elements at ranks 1 through K. For the min-heap approach, both are solved identically: maintain a heap of size K, and after processing all elements, the heap's top is the Kth largest (one element), and the entire heap contents are the top K elements. For quickselect: finding the Kth largest stops as soon as the pivot lands at position k-1; finding the top K largest additionally requires returning all elements at positions 0 through k-1 — but after quickselect completes (the pivot is at k-1), the elements in positions 0..k-1 are exactly the top K (in unsorted order within that partition). Bucket sort always produces the top K, not just the Kth — stopping as soon as K elements are collected gives the complete set.

**Q8. What custom comparator patterns appear in top K problems, and how do secondary sort keys work?**

A: Many top K problems require a primary sort key (e.g., frequency) with a tie-breaking secondary key (e.g., lexicographic order for words, or Euclidean distance for points). In a min-heap comparator, a pair `(a, b)` is ordered as: compare by primary key first; if equal, compare by secondary key. For "top K frequent words" where ties are broken lexicographically (alphabetically earlier = higher rank): the min-heap evicts the "worst" word first — among words with equal frequency, the lexicographically *later* word is "worse" (it ranks lower among ties). So the min-heap comparator for `[freqA, wordA]` vs `[freqB, wordB]`: if `freqA !== freqB`, return `freqA - freqB` (lower frequency is evicted first); if equal frequency, return `wordB.localeCompare(wordA)` (later word is evicted first, since later words are "worse" and should leave first).

```
Tie-breaking rule: "among equal-frequency words, alphabetically earlier is better"
Min-heap comparator (evicts worst first):
  (a, b) => freq[a] !== freq[b]
            ? freq[a] - freq[b]              // lower freq → evicted first (smaller in min-heap)
            : b.localeCompare(a)             // same freq: later word → evicted first

Example: freq={love:2, i:2, ...}. Comparing "love" and "i":
  Same freq. b.localeCompare(a) = "i".localeCompare("love") = negative ("i" < "love" alphabetically)
  → "love" > "i" in comparator → "love" is more evictable → "i" stays ✓ ("i" comes first alphabetically)
```

**Q9. What is the space complexity trade-off between the heap and bucket sort approaches for top K frequent?**

A: Heap approach: O(k) space for the heap itself (holds at most k+1 elements at any moment); plus O(n) for the frequency map. Total: O(n + k). Since k ≤ n, this is O(n). Bucket sort approach: O(n) for the frequency map plus O(n) for the buckets array (n+1 entries, each holding a list — total list entries = n, since each element appears in exactly one bucket). Total: O(n). Both approaches are O(n) space overall, but the heap approach has a smaller constant factor for the selection phase (O(k) active working memory vs O(n) bucket array). When k ≪ n and memory is constrained beyond just Big-O, the heap approach uses less working memory for the selection step.

### Section A2: Advanced Patterns

**Q10. What is the K-way merge pattern using a heap, and what does each heap entry store?**

A: K-way merge solves: "given K sorted lists, find the K smallest (or largest) elements across all of them." Each heap entry stores `(value, listIndex, elementIndex)` — the current value being considered, which list it came from, and where in that list it sits. Initialize the heap with the first element from each of the K lists. On each pop: the popped element is the next smallest overall; push the next element from the same list (at elementIndex + 1), if it exists. The heap maintains the invariant: *its top is always the globally smallest unextracted element across all K lists*. Time: O(K log K) to initialize + O(m log K) to extract m elements, where m is the total number of elements extracted. Crucial: "lazy expansion" means we never load all elements into the heap — only one element per list is in the heap at any moment.

```
K sorted lists: [1,4,7], [2,5,8], [3,6,9]
Initial heap: [(1,list0,idx0), (2,list1,idx0), (3,list2,idx0)]

Pop (1,0,0) → output 1. Push (4,0,1). Heap: [(2,1,0),(3,2,0),(4,0,1)]
Pop (2,1,0) → output 2. Push (5,1,1). Heap: [(3,2,0),(4,0,1),(5,1,1)]
... and so on. Each heap entry = (val, whichList, posInList).
```

**Q11. What is "lazy expansion" in the context of heap-based K-selection, and when is it necessary?**

A: Lazy expansion is the principle of *not pre-loading all possible candidates into the heap* — instead, loading only an initial frontier of candidates and expanding (generating new candidates) only when a candidate is actually extracted. It is necessary when: (a) the total candidate space is too large to pre-load (e.g., all n² pairs in "Find K Pairs with Smallest Sums" — loading all n² pairs would be O(n²) space); (b) the candidates follow a structured order (e.g., sorted rows/columns, or pairs where both components are sorted) that allows generating "the next candidate" from a just-extracted candidate without exploring the full space. The pattern: initialize heap with a small frontier; on each pop, generate and push the "successors" of the popped candidate — at most a constant number per pop, so total heap operations = O(k log(frontier size)).

**Q12. What is the online/streaming top K problem, and how does a min-heap of size K solve it?**

A: In the streaming version, elements arrive one at a time and after each arrival the Kth largest (or top K) must be answerable in O(1). The min-heap of size K is maintained incrementally: on each `add(val)`, push `val`; if heap size exceeds K, pop the minimum. The heap's top is always the current Kth largest. Total cost: O(log k) per `add`, O(1) per `getKthLargest`. This is impossible to achieve with sorting (every new element would require re-sorting) or bucket sort (not defined for unbounded streaming input). The heap is the uniquely correct tool for streaming top K — it processes each element exactly once, uses O(k) memory regardless of stream length, and answers queries in O(1).

**Q13. What is the "sort key must be precomputed, not stored raw" insight for heap efficiency?**

A: When the ranking criterion is an expensive-to-compute function of an element (e.g., Euclidean distance, frequency count), each heap comparison would need to recompute it — a potential O(distance_computation_cost) multiplied by O(log k) comparisons per element. The fix: precompute the sort key once per element and store `(key, element)` pairs in the heap, so comparisons are O(1). For "K closest points to origin": store `(x²+y², [x,y])` — squared distance avoids the sqrt (which is monotone and unnecessary for comparison), and the key is computed once per point. This is also why heap entries for "top K frequent" store `(frequency, element)` rather than just the element with a frequency-map lookup per comparison.

```
Expensive comparator — BAD:
  heap.push(point)
  // comparator: (a,b) => dist(a) - dist(b)  ← recomputes sqrt on EVERY comparison

Precomputed key — GOOD:
  heap.push([x*x + y*y, point]) // key computed ONCE per element
  // comparator: (a,b) => a[0] - b[0]        ← O(1) comparison using stored key ✓
```

**Q14. What is the "choose pivot + partition" structure of quickselect, and how does the Lomuto scheme implement it for Kth largest?**

A: Lomuto partition for Kth LARGEST: choose pivot = arr[right]; scan left-to-right, placing elements ≥ pivot before position `i` and elements < pivot after. After the pass, swap pivot into position `i`. The array is now: `[... ≥ pivot ... | pivot | ... < pivot ...]` where pivot is at index `i`. If `i === k-1`: pivot is the Kth largest (there are exactly k-1 elements to its left, each ≥ pivot). If `i < k-1`: the Kth largest is in the right (smaller) portion — recurse on `[i+1..right]`. If `i > k-1`: the Kth largest is in the left (larger) portion — recurse on `[left..i-1]`. The key directional choice: elements ≥ pivot go LEFT (we want the K largest, so larger elements accumulate from the left boundary), and the pivot's position in the left-heavy ordering gives its rank directly.

```js
function partition(arr, lo, hi) {
  const pivot = arr[hi];
  let i = lo;
  for (let j = lo; j < hi; j++) {
    if (arr[j] >= pivot) {   // ≥ pivot → left side (the "large" side)
      [arr[i], arr[j]] = [arr[j], arr[i]];
      i++;
    }
  }
  [arr[i], arr[hi]] = [arr[hi], arr[i]]; // place pivot at its final position
  return i;  // elements at [lo..i-1] ≥ pivot; elements at [i+1..hi] < pivot
}
// i === k-1: arr[i] is Kth largest ✓
// i <  k-1: Kth largest is in [i+1..hi] (smaller values, but we need deeper)
// i >  k-1: Kth largest is in [lo..i-1] (larger values, closer to rank 1)
```

**Q15. What is the "median-of-three" pivot strategy, and why does it matter for top K interviews?**

A: Median-of-three picks the pivot as the median of three candidates: `arr[left]`, `arr[mid]`, `arr[right]`. This avoids the worst case on already-sorted or reverse-sorted inputs (where "always pick last element" degrades to O(n²)) without requiring a full array shuffle. At the 5 YOE interview level, mentioning this demonstrates awareness of the practical weakness of naive quickselect and signals that you'd write production-safe code. The tradeoff: slightly more code complexity, reduced (though not eliminated) worst-case risk. True O(n) worst case requires the "median of medians" algorithm — correct but rarely asked to implement; naming it and knowing it exists is sufficient in an interview.

## Topic B: Heap Mechanics and Custom Keys

### Section B1: Binary Heap Operations

**Q16. What are the core binary heap operations, their complexities, and the heap property?**

A: A binary min-heap stores elements in an array with the invariant: *every node's value is ≤ its children's values* — the minimum is always at the root. Implemented as a 0-indexed array: for node at index `i`, left child = `2i+1`, right child = `2i+2`, parent = `(i-1) >> 1`. Core operations: **push** (add element at end, bubble-up until heap property restored) — O(log n); **pop** (remove root, move last element to root, sink-down until property restored) — O(log n); **peek top** (read root) — O(1); **build** (heapify n elements bottom-up, calling sink-down on internal nodes from bottom to top) — O(n). The O(n) build is asymptotically better than n individual pushes (which would be O(n log n)), because most nodes are near the leaves (where sink-down is cheap) and only a few near the root (where it's expensive) — a geometric series argument.

**Q17. What is the difference between building a heap with n individual pushes vs. `heapify`, and when does it matter?**

A: n individual pushes: each push bubbles up from a leaf to potentially the root — O(log n) per push — total O(n log n). Heapify: call sink-down on every internal node from the bottom up; nodes near the bottom have short sink-down paths (O(1) for leaf parents), so total work = Σ height(i) for all nodes = O(n). In top K problems, heapify matters for the "full heapify all n elements then pop K times" variant: O(n) build + O(k log n) pops = O(n + k log n). Compare to the min-heap-of-size-K approach: O(n log k). When k ≈ n: `O(n + k log n) = O(n log n)` vs `O(n log k) = O(n log n)` — comparable. When k ≪ n: `O(n + k log n)` is worse than `O(n log k)`. Conclusion: *maintain heap of size K* wins when k ≪ n; *heapify all then pop K* wins when k ≈ n or you already need the full heap.

**Q18. How do you implement a min-heap in JavaScript, and how does a custom comparator simulate a max-heap?**

A: JavaScript lacks a built-in priority queue. The standard interview implementation is a class wrapping an array with `_up` (bubble-up) and `_down` (sink-down). A custom comparator enables any ordering: passing `(a, b) => b - a` to a min-heap makes it behave as a max-heap (because the comparator flips the comparison direction, making what was "larger" appear "smaller" to the heap). For complex keys, the comparator handles the full multi-field ordering logic.

```js
class MinHeap {
  constructor(cmp = (a, b) => a - b) { this.data = []; this.cmp = cmp; }
  size()  { return this.data.length; }
  top()   { return this.data[0]; }

  push(v) { this.data.push(v); this._up(this.data.length - 1); }
  pop() {
    const top = this.data[0];
    const last = this.data.pop();
    if (this.data.length) { this.data[0] = last; this._down(0); }
    return top;
  }
  _up(i) {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.cmp(this.data[i], this.data[p]) < 0) {
        [this.data[i], this.data[p]] = [this.data[p], this.data[i]]; i = p;
      } else break;
    }
  }
  _down(i) {
    const n = this.data.length;
    while (true) {
      let s = i, l = 2*i+1, r = 2*i+2;
      if (l < n && this.cmp(this.data[l], this.data[s]) < 0) s = l;
      if (r < n && this.cmp(this.data[r], this.data[s]) < 0) s = r;
      if (s !== i) { [this.data[i], this.data[s]] = [this.data[s], this.data[i]]; i = s; }
      else break;
    }
  }
}

// Min-heap by default:  new MinHeap()
// Max-heap:             new MinHeap((a, b) => b - a)
// By frequency:         new MinHeap((a, b) => freq[a] - freq[b])
// By squared distance:  new MinHeap((a, b) => a[0] - b[0])  where a = [dist², point]
```

### Section B2: Heap Patterns

**Q19. What is the "heap of size K" invariant, and what exact comparison guards the push-or-skip decision?**

A: The invariant at every step: *the min-heap contains exactly min(elementsProcessed, K) of the K largest elements seen so far, with `heap.top()` being the smallest of those — i.e., the current Kth largest.* For each new element x: if `heap.size() < k`: always push (haven't seen K elements yet — the heap isn't full). If `heap.size() === k` and `x > heap.top()`: push x, then pop the new minimum (which is the old Kth largest, now displaced). If `heap.size() === k` and `x ≤ heap.top()`: skip (x can't enter the top K; heap.top() is already ≤ every element in the heap, and x ≤ heap.top() means x is even smaller). The strict `>` (not `≥`) comparison for equal elements: equal elements should also be skipped because they don't improve the top K — the existing heap.top() is as good as x.

```js
// Maintain top-K largest in a min-heap of size K:
function addToTopK(heap, k, x) {
  if (heap.size() < k) {
    heap.push(x);          // heap not full yet — always add
  } else if (x > heap.top()) {
    heap.push(x);          // x beats current Kth largest
    heap.pop();            // evict the old Kth largest
  }
  // x <= heap.top(): x can't enter top K — do nothing
}
// After all elements: heap.data = top K largest (unsorted); heap.top() = Kth largest.
```

**Q20. What does each heap entry store in the K-way merge pattern, and how does lazy expansion prevent the O(nm) space blowup?**

A: For K-way merge of K sorted sequences: each heap entry stores `[value, rowIndex, colIndex]` — the element's value (for comparison), which sequence it came from (rowIndex), and where in that sequence it sits (colIndex). Only one element per sequence is in the heap at any time → heap size ≤ K at all times, not O(nm). Lazy expansion: when an entry `[val, r, c]` is popped, push `[sequences[r][c+1], r, c+1]` if `c+1 < sequences[r].length` — generating exactly one new candidate per pop. This is essential when K = n and m = n (generating all n² pairs upfront would be O(n²) space); with lazy expansion, space is O(K) = O(n), and time is O(K + extracted × log K).

## Topic C: Cross-Topic & Interview-Style Questions

**Q21. Compare "top K by frequency" vs "top K by value" — what changes structurally?**

A: Top K by value (e.g., K largest integers): the element *is* the sort key — no frequency map needed. Apply K-selection directly to the raw values. Top K by frequency: the element and its rank are separate — must first aggregate (build the frequency map), then K-select on `(element, frequency)` pairs treating frequency as the sort key. The underlying K-selection logic (heap, quickselect, bucket sort) is structurally identical in both cases; what changes is the key used for comparison. The frequency map step adds O(n) time and O(n) space to every "top K by frequency" problem — it is always phase 1, not optional, and is a prerequisite to any K-selection algorithm that ranks by frequency.

**Q22. In one sentence each, state the invariant maintained by each approach at any point during processing.**

A:
- **Min-heap of size K** (top K largest): the heap holds exactly the K largest elements seen so far, with the top being the smallest of those (the current Kth largest), so any new element exceeding the top deserves to displace it.
- **Quickselect**: after each partition, the pivot is in its final position — all elements to its left are ≥ pivot and all to its right are < pivot — so the Kth element's location is known to be entirely within the left or right partition, eliminating the other half from further consideration.
- **Bucket sort** (frequency): buckets[f] holds all elements with frequency exactly f; scanning from high f to low f and collecting elements until K are gathered gives the top K by frequency, since higher-indexed buckets have higher frequency by construction.
- **K-way merge (lazy expansion)**: the heap top is always the globally smallest unextracted element across all K source sequences — guaranteed by the heap invariant and the property that each source sequence is sorted.

**Q23. "Describe the decision process for choosing between a heap, quickselect, and bucket sort for a top K problem."**

A: Ask three questions in order: (1) *Is the input a stream (online), or must the answer be given after each new element?* If yes → heap of size K is the only viable approach. (2) *Is the ranking by frequency (or some other bounded integer computed from the input)?* If yes and O(n) time is required or preferable → bucket sort (requires the key domain to be bounded and enumerable). (3) *Is k ≪ n and memory is a concern?* Heap of size K — O(n log k) time, O(k) space. Otherwise: if average O(n) is acceptable and the array can be mutated → quickselect. If simplicity matters more than optimal complexity → sort. The override: *if a custom comparator with complex tie-breaking logic is needed*, heap is easier to implement correctly than quickselect (which would need the custom comparator in the partition step).

```
Is input a stream? → Heap of size K (only option)
Else: Is ranking by bounded integer (frequency, etc.)? → Bucket sort (O(n))
Else: Is k ≪ n and O(n log k) good enough? → Heap of size K
Else: Can array be mutated? O(n) average acceptable? → Quickselect
Else: → Sort (simplest, always correct)
```

**Q24. What is the common mistake with the heap comparator direction for "top K frequent words with lexicographic tie-breaking"?**

A: The trap: the problem asks for the K most frequent words, alphabetically earliest for ties. The min-heap evicts the "worst" word (lowest priority), so the comparator must define "worse" as: lower frequency OR (equal frequency AND lexicographically later). A common mistake is reversing the lexicographic comparison direction — using `a.localeCompare(b)` instead of `b.localeCompare(a)` in the tie-breaking. With `a.localeCompare(b)`: the heap marks lexicographically *earlier* words as "smaller" → earlier words are evicted first → result contains alphabetically *later* words in the tie group → wrong. With `b.localeCompare(a)`: lexicographically *later* words are "smaller" → later words evicted first → earlier words survive → correct. The mnemonic: "later goes out first" — the comparator should express "b is worse than a when b comes later alphabetically."

**Q25. "A candidate's solution produces the correct K elements but in the wrong order. When is this a bug and when is it acceptable?"**

A: "Top K frequent elements" problems — LeetCode 347 specifically — explicitly state "the answer may be returned in any order." So an unordered result from a heap or bucket scan is correct. "Top K frequent words" — LeetCode 692 — requires output in *frequency-descending, lexicographic-tie-break* order. Returning the correct K words unordered is wrong. "Kth largest element" — a single element, order is irrelevant. The pattern: when the problem says "top K" without specifying output order, unordered is fine (heap output directly). When the problem says "sorted by X" or "in descending/ascending order," sort the heap's output after extraction — O(k log k), a minor addition. When the problem asks for "Kth" (singular), the heap's top is the answer, no ordering needed. Always re-read whether the output must be ordered; the distinction is frequently the source of a "97% correct" submission that fails on ordering edge cases.

## Problem 1 — Top K Frequent Elements

### Problem

Given an integer array `nums` and an integer `k`, return the `k` most frequent elements. The answer may be in any order.

```
Input:  nums = [1,1,1,2,2,3], k = 2  → [1, 2]
Input:  nums = [1], k = 1            → [1]
```

### Pattern Recognition
Two approaches: (A) HashMap + min-heap of size k on frequencies — O(n log k); (B) HashMap + bucket sort — O(n). Both begin with a frequency map as phase 1. Approach A is more general; Approach B is O(n) and elegant but specific to frequency ranking.

### Key Insight
**Approach A**: a min-heap keyed on frequency maintains exactly the k most frequent elements seen so far; its top is the least frequent of the k, ready to be evicted if a more frequent element arrives. **Approach B**: frequencies are bounded by [1, n], enabling direct bucket indexing — scanning from bucket n down to bucket 1 collects elements in frequency-descending order without any comparison-based sort.

### Approach
**Heap**: build `freq` map; push `[freq, element]` pairs into a min-heap; once heap exceeds size k, pop. After all elements, extract heap contents. **Bucket**: build `freq` map; create `buckets[0..n]`; for each `(element, count)` in freq, append element to `buckets[count]`; scan buckets from n down to 1, collect until k elements gathered.

### Solution

```js
// Approach A: HashMap + min-heap of size k — O(n log k)
function topKFrequent_heap(nums, k) {
  const freq = new Map();
  for (const x of nums) freq.set(x, (freq.get(x) ?? 0) + 1);

  // Min-heap keyed on frequency: top = least frequent among top-k candidates
  const heap = new MinHeap((a, b) => a[0] - b[0]); // compare by freq

  for (const [num, cnt] of freq) {
    heap.push([cnt, num]);          // push [frequency, element]
    if (heap.size() > k) heap.pop(); // evict least frequent if over k
  }

  return heap.data.map(([, num]) => num); // extract elements from heap
}

// Approach B: HashMap + bucket sort — O(n)
function topKFrequent_bucket(nums, k) {
  const freq = new Map();
  for (const x of nums) freq.set(x, (freq.get(x) ?? 0) + 1);

  // buckets[f] = list of elements with frequency exactly f
  const buckets = Array.from({ length: nums.length + 1 }, () => []);
  for (const [num, cnt] of freq) buckets[cnt].push(num);

  const result = [];
  for (let f = buckets.length - 1; f >= 1 && result.length < k; f--) {
    for (const num of buckets[f]) {
      result.push(num);
      if (result.length === k) return result; // collected k elements
    }
  }
  return result;
}
```

### Dry Run

```
nums = [1,1,1,2,2,3], k = 2

Heap approach:
  freq = {1:3, 2:2, 3:1}

  Push [3,1]: heap=[[3,1]]. size=1≤2.
  Push [2,2]: heap=[[2,2],[3,1]]. size=2≤2.
  Push [1,3]: heap=[[1,3],[3,1],[2,2]]. size=3>2 → pop [1,3].
  heap=[[2,2],[3,1]]. Return [2,1] (any order). ✓

Bucket approach:
  freq = {1:3, 2:2, 3:1}
  buckets[3]=[1], buckets[2]=[2], buckets[1]=[3]

  f=6: empty. f=5: empty. f=4: empty.
  f=3: [1] → result=[1]. need 1 more.
  f=2: [2] → result=[1,2]. len=2=k → return [1,2]. ✓
```

### Complexity
- **Heap**: Time O(n log k) — freq map O(n), n/unique elements × O(log k) heap ops. Space O(n + k).
- **Bucket**: Time O(n) — freq map O(n), bucket fill O(n), bucket scan O(n). Space O(n).

### Edge Cases
- All elements unique: every frequency = 1; all in bucket[1]; first k elements collected are arbitrarily chosen (all tied at freq=1).
- k = number of unique elements: return all unique elements (bucket scan collects all, heap fills exactly to k).
- Single element repeated: freq map has one entry; immediately forms the answer.
- k = 1: heap approach pushes all unique elements, popping until only the most frequent remains.

### Follow-up Questions
- "What if k = n?" — All elements are in the top n; return all unique elements. Both approaches still O(n).
- "Must elements with equal frequency maintain relative order from the input?" — Not required by the problem, but if needed, process freq map in insertion order and use stable bucket iteration.
- "Top k least frequent?" — Heap approach: reverse comparator to max-heap (`(a,b) => b[0]-a[0]`); evict the most frequent (not the least). Bucket approach: scan from bucket[1] upward.

## Problem 2 — Kth Largest Element in an Array

### Problem

Given an integer array `nums` and an integer `k`, return the `k`th largest element in the array (not the kth distinct element). Must run in O(n) on average.

```
Input:  nums = [3,2,1,5,6,4], k = 2  → 5
Input:  nums = [3,2,3,1,2,4,5,5,6],  k = 4  → 4
```

### Pattern Recognition
Two approaches: (A) min-heap of size k — O(n log k); (B) quickselect — O(n) average. The O(n) requirement hints at quickselect; the "in a stream" variant would require the heap. Both are worth knowing — interviews often ask you to implement both.

### Key Insight
**Heap**: the min-heap of size k's top is always the Kth largest seen so far — a single O(1) read after O(n log k) processing. **Quickselect**: the Kth largest is at 0-indexed position k-1 in descending sort. Partition around a random pivot; if pivot lands at exactly position k-1, it's the answer; otherwise recurse only on the half containing position k-1 — discarding the other half entirely. The partition step places larger elements on the left, so a pivot at position k-1 has exactly k-1 elements larger than it to its left.

### Solution

```js
// Approach A: Min-heap of size k — O(n log k)
function findKthLargest_heap(nums, k) {
  const heap = new MinHeap(); // standard numeric min-heap
  for (const x of nums) {
    heap.push(x);
    if (heap.size() > k) heap.pop(); // maintain size k
  }
  return heap.top(); // top of min-heap = kth largest
}

// Approach B: Quickselect — O(n) average, O(n²) worst case
function findKthLargest_quickselect(nums, k) {
  const target = k - 1; // 0-indexed rank in descending order

  function partition(lo, hi) {
    // Random pivot to avoid O(n²) on sorted inputs
    const pivotIdx = lo + Math.floor(Math.random() * (hi - lo + 1));
    [nums[pivotIdx], nums[hi]] = [nums[hi], nums[pivotIdx]]; // move pivot to end

    const pivot = nums[hi];
    let i = lo;
    for (let j = lo; j < hi; j++) {
      if (nums[j] >= pivot) {          // ≥ pivot → left (larger elements side)
        [nums[i], nums[j]] = [nums[j], nums[i]];
        i++;
      }
    }
    [nums[i], nums[hi]] = [nums[hi], nums[i]]; // place pivot at final position
    return i; // pivot's position: [lo..i-1] ≥ pivot; [i+1..hi] < pivot
  }

  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const p = partition(lo, hi);
    if (p === target) return nums[p];  // pivot is exactly the kth largest
    if (p < target)   lo = p + 1;     // kth largest is in right (smaller) portion
    else              hi = p - 1;     // kth largest is in left (larger) portion
  }
  return -1; // unreachable (problem guarantees 1 ≤ k ≤ n)
}
```

### Dry Run

```
Quickselect: nums = [3,2,1,5,6,4], k=2, target=1

Iteration 1: lo=0, hi=5. Suppose random pivot=4 (index 5, value 4).
  pivot=4. Scan [3,2,1,5,6,4]:
    j=0: 3<4 → skip.   j=1: 2<4 → skip.   j=2: 1<4 → skip.
    j=3: 5≥4 → swap nums[0]↔nums[3]: [5,2,1,3,6,4]. i=1.
    j=4: 6≥4 → swap nums[1]↔nums[4]: [5,6,1,3,2,4]. i=2.
  Place pivot: swap nums[2]↔nums[5]: [5,6,4,3,2,1]. p=2.
  p=2 > target=1 → hi = 1. Search [5,6] for rank 1.

Iteration 2: lo=0, hi=1. Suppose pivot=5 (index 0, value 5).
  Swap pivot to end: [6,5]. pivot=5.
  j=0: 6≥5 → swap nums[0]↔nums[0]: [6,5]. i=1.
  Place pivot: swap nums[1]↔nums[1]: [6,5]. p=1.
  p=1 === target=1 → return nums[1] = 5. ✓
```

### Complexity
- **Heap**: O(n log k) time, O(k) space.
- **Quickselect**: O(n) expected time (with random pivot), O(n²) worst case, O(1) extra space (in-place). Recursion stack: O(log n) expected depth.

### Edge Cases
- k = 1: return the maximum. Quickselect finds it after one or two partitions.
- k = n: return the minimum.
- All equal elements: partition places all elements on the pivot's left (≥ pivot), pivot ends at index 0; quickselect terminates immediately when k=1, or recurses right for any other k — eventually returning the same value (all elements equal).
- Duplicate values: quickselect is correct — partitioning on ≥ pivot groups equal elements consistently; the Kth element at position k-1 is found correctly even with many duplicates.

### Follow-up Questions
- "Kth largest in a stream?" — Heap approach only; quickselect requires all elements at once. See Problem 6.
- "Median of an array?" — Special case k = n/2 (or two middle elements). Quickselect finds one median in O(n); both medians require two passes or a min+max-heap pair.
- "Guaranteed O(n) worst case?" — Implement median-of-medians as the pivot selection strategy. Correct but complex; mention it without full implementation.

## Problem 3 — K Closest Points to Origin

### Problem

Given an array of `points` where `points[i] = [xi, yi]`, return the `k` closest points to the origin `(0, 0)`. The answer may be returned in any order. Distance is Euclidean.

```
Input:  points = [[1,3],[-2,2]], k = 1    → [[-2,2]]
  // dist([1,3])   = √10 ≈ 3.16
  // dist([-2,2])  = √8  ≈ 2.83 ← closer

Input:  points = [[3,3],[5,-1],[-2,4]], k = 2 → [[3,3],[-2,4]]
```

### Pattern Recognition
Min-heap of size k with a custom sort key — squared Euclidean distance. Squared distance is monotone with actual distance (preserves ordering), avoids the `sqrt` operation, and is an integer (avoids floating-point issues). Store `[squaredDist, point]` in the heap.

### Key Insight
This is the "top K smallest" problem (not largest), so we use a **max-heap of size k** keyed on squared distance: the top is the farthest among the current k closest — the eviction candidate. When a new point is closer than the current farthest-in-the-k, evict the farthest and add the new point. Equivalently: use a min-heap with a negated key (simulating max-heap), or use the direct max-heap comparator `(a,b) => b[0]-a[0]`.

### Approach
Build a max-heap (using the custom comparator `(a,b) => b[0]-a[0]` on squared distances) of size k. For each point: push `[x²+y², [x,y]]`; if heap size exceeds k, pop the max (the farthest point). After all points, extract the k remaining points from the heap.

### Solution

```js
function kClosest(points, k) {
  // MAX-heap on squared distance: top = farthest among k closest (eviction candidate)
  const heap = new MinHeap((a, b) => b[0] - a[0]); // reversed comparator = max-heap

  for (const [x, y] of points) {
    const dist2 = x*x + y*y;            // squared distance: no sqrt needed, preserves order
    heap.push([dist2, [x, y]]);
    if (heap.size() > k) heap.pop();    // evict the farthest point among current top-k
  }

  return heap.data.map(([, point]) => point); // extract points from heap entries
}
```

### Dry Run

```
points = [[1,3],[-2,2],[5,1],[0,2]], k = 2.
dist²: [1,3]=10, [-2,2]=8, [5,1]=26, [0,2]=4.

Push [10,[1,3]]:    heap=[[10,...]], size=1≤2.
Push [8,[-2,2]]:    heap=[[10,...],[8,...]], size=2≤2.
Push [26,[5,1]]:    heap=[[26,...],[8,...],[10,...]], size=3>2 → pop [26,[5,1]].
                    heap=[[10,...],[8,...]], size=2. ✓ [5,1] evicted (farthest).
Push [4,[0,2]]:     heap=[[10,...],[8,...],[4,...]], size=3>2 → pop [10,[1,3]].
                    heap=[[8,...],[4,...]], size=2. ✓ [1,3] evicted.

Extract: [[-2,2], [0,2]]. ✓ The two closest to origin.
```

### Complexity
- Time: O(n log k) — n points, each with O(log k) heap push/pop.
- Space: O(k) — heap holds at most k+1 entries.

### Edge Cases
- All points equidistant from origin: any k of them is a valid answer; the heap holds whichever k were processed most recently (without eviction after the first k fill the heap).
- k = n: no eviction ever fires; all points are returned.
- Points with negative coordinates: squared distance is always non-negative; `(-2)² + (2)² = 8` is correct regardless of sign.
- Overflow risk: `xi, yi` up to 10⁴ → `xi² + yi²` up to 2 × 10⁸ < 2^31 — safe in 32-bit integers. JavaScript numbers handle this without overflow.

### Follow-up Questions
- "Return the k closest in sorted order (nearest first)?" — Extract all k from heap, then sort by squared distance: O(k log k).
- "Use quickselect instead?" — Quickselect on squared distances in-place: O(n) average, but mutates the points array. For this problem, heap is preferred for its non-mutating property.
- "What if distance is not Euclidean (e.g., Manhattan)?" — Replace `x*x + y*y` with `Math.abs(x) + Math.abs(y)` in the key computation. Everything else remains identical.

## Problem 4 — Top K Frequent Words

### Problem

Given an array of strings `words` and an integer `k`, return the `k` most frequent words sorted by frequency from highest to lowest. Words with the same frequency should be sorted lexicographically (alphabetical order).

```
Input:  words = ["i","love","leetcode","i","love","coding"], k = 2
Output: ["i","love"]   // "i"→2, "love"→2: equal freq → alphabetical: "i" < "love"

Input:  words = ["the","day","is","great","the","day","of","the","great","love"], k = 4
Output: ["the","great","day","is"]
  // "the"→3, "great"→2, "day"→2, "is"→1, "love"→1, "of"→1
  // "day" < "great" alphabetically but "great" appears 2× vs "day" 2× → tie → "day" before "great"? 
  // Wait: "day"→2, "great"→2. Alphabetically: "day" < "great" → "day" before "great" in output ✓
```

### Pattern Recognition
HashMap + min-heap of size k with a **custom comparator** that handles both frequency (primary sort key, descending) and lexicographic order (secondary sort key, ascending) for tie-breaking. The min-heap's top is the "worst" word among the current top-k candidates — the one to evict first.

### Key Insight
The min-heap evicts the "worst" candidate: among current top-k, worst = lowest frequency OR (equal frequency AND lexicographically later). The comparator expresses "which of a, b is evicted first" — the one that's "smaller" in min-heap order: lower frequency (evicted first) or, on a tie, lexicographically later (evicted first, since later words are lower priority). This counterintuitive use of `b.localeCompare(a)` (not `a.localeCompare(b)`) is the critical tie-breaking direction.

### Approach
Build frequency map. Min-heap with comparator: if frequencies differ, lower frequency is "smaller" (evicted first); if equal, lexicographically later word is "smaller" (evicted first). Push each word; pop when heap exceeds k. Extract heap contents; sort by frequency descending then alphabetically (needed because heap gives the k correct words but not in the required output order).

### Solution

```js
function topKFrequent(words, k) {
  const freq = new Map();
  for (const w of words) freq.set(w, (freq.get(w) ?? 0) + 1);

  // Min-heap: top = "worst" word among current top-k (first to be evicted)
  // "worse" = lower frequency, OR (same frequency AND lexicographically later)
  const heap = new MinHeap((a, b) =>
    freq.get(a) !== freq.get(b)
      ? freq.get(a) - freq.get(b)        // lower freq → smaller → at heap top → evicted first
      : b.localeCompare(a)               // same freq: later word → smaller → evicted first
  );

  for (const word of freq.keys()) {
    heap.push(word);
    if (heap.size() > k) heap.pop();    // evict the "worst" word
  }

  // Heap holds exactly k words — but in min-heap order, not the required output order
  // Extract all and sort for output: frequency descending, then alphabetically ascending
  return heap.data.sort((a, b) =>
    freq.get(a) !== freq.get(b)
      ? freq.get(b) - freq.get(a)        // higher freq first
      : a.localeCompare(b)               // same freq: alphabetically earlier first
  );
}
```

### Dry Run

```
words = ["i","love","leetcode","i","love","coding"], k = 2
freq = {"i":2, "love":2, "leetcode":1, "coding":1}

Comparator: by freq asc, then by word desc (b.localeCompare(a)):

Push "i":        heap=["i"].
Push "love":     cmp("love","i") = freq equal → "love".localeCompare("i")>0 → "love">"i"
                 heap order: "love" < "i" in min-heap (love is worse, evicted first if needed)
                 heap=["love","i"] (love at top as it's lexicographically later = worse).
Push "leetcode": heap.size=3>2 → pop "leetcode"? Wait:
                 First push "leetcode": heap=["leetcode","i","love"] reheapified.
                 freq["leetcode"]=1 < freq["love"]=2 → "leetcode" is smaller (lower freq, evicted first).
                 After push: top should be "leetcode". Pop "leetcode". heap=["love","i"].
Push "coding":   freq["coding"]=1. Push → size=3 > 2. Top is whichever of "love","i","coding" is worst.
                 "coding"(1) < "love"(2) → "coding" is top. Pop "coding". heap=["love","i"].

Final heap = ["love","i"].
Sort: both freq=2. "i".localeCompare("love")<0 → "i" before "love".
Output: ["i","love"]. ✓
```

### Complexity
- Time: O(n + m log k) where n = total words, m = unique words. Freq map O(n); heap ops O(m log k); final sort O(k log k).
- Space: O(m) — freq map + heap holds at most k+1 words.

### Edge Cases
- All words with same frequency: sorted purely alphabetically — heap evicts lexicographically later words, keeping earlier ones.
- k = total unique words: return all unique words sorted by freq desc then alphabetically.
- Words with uppercase: `localeCompare` handles case per locale settings; for ASCII-safe comparison, use `a < b` if guaranteed lowercase.

### Follow-up Questions
- "What if we must return words with the same frequency in the original order (stable sort)?" — Add a third sort key: original insertion index. Store `(word, freq, firstSeenIndex)` in the heap; tie-break on firstSeenIndex ascending.
- "k = 1 (just the most frequent word)?" — Linear scan of freq map, track max. O(n) time, O(1) extra space beyond the freq map.

## Problem 5 — Find K Pairs with Smallest Sums

### Problem

Given two integer arrays `nums1` and `nums2` (both sorted in ascending order), return the `k` pairs `[nums1[i], nums2[j]]` with the smallest sums. The answer may be in any order.

```
Input:  nums1=[1,7,11], nums2=[2,4,6], k=3  → [[1,2],[1,4],[1,6]]
Input:  nums1=[1,1,2],  nums2=[1,2,3], k=2  → [[1,1],[1,1]]
```

### Pattern Recognition
K-way merge with lazy expansion. The n "sorted lists" are: list i = `(nums1[i] + nums2[0], nums1[i] + nums2[1], ...)` — all sums starting from `nums1[i]`, paired with each `nums2[j]` in order. Since `nums2` is sorted, each virtual list is also sorted ascending. Use a min-heap to merge these lists lazily, expanding only the next element of a list when the current one is extracted.

### Key Insight
Pre-loading all possible pairs (up to n² pairs) into the heap is O(n²) space — too much. Lazy expansion: initialize the heap with only the first pair from each nums1 row `(nums1[i] + nums2[0], i, 0)`. When pair `(sum, i, j)` is extracted, push `(nums1[i] + nums2[j+1], i, j+1)` if `j+1 < nums2.length`. Each extracted pair generates at most one new candidate — heap size stays ≤ min(k, n) at all times. Total heap operations = O(k log(min(k,n))).

### Approach
Initialize heap with `(nums1[i]+nums2[0], i, 0)` for i from 0 to min(k-1, n1-1) (no need to add more than k rows initially). Extract k times: on each extraction of `(sum, i, j)`, record `[nums1[i], nums2[j]]` as a result; push `(nums1[i]+nums2[j+1], i, j+1)` if `j+1 < n2`.

### Solution

```js
function kSmallestPairs(nums1, nums2, k) {
  if (!nums1.length || !nums2.length) return [];

  // Min-heap: each entry = [sum, i (index into nums1), j (index into nums2)]
  const heap = new MinHeap((a, b) => a[0] - b[0]); // min-heap on sum
  const result = [];

  // Initialize: first element of each "row" (nums1[i] paired with nums2[0])
  // Only need min(k, nums1.length) rows — can't extract more than k pairs total
  for (let i = 0; i < Math.min(k, nums1.length); i++) {
    heap.push([nums1[i] + nums2[0], i, 0]);
  }

  while (result.length < k && heap.size()) {
    const [, i, j] = heap.pop();             // extract smallest-sum pair
    result.push([nums1[i], nums2[j]]);        // record the pair

    if (j + 1 < nums2.length) {              // expand: next element in same row
      heap.push([nums1[i] + nums2[j+1], i, j+1]);
    }
  }

  return result;
}
```

### Dry Run

```
nums1=[1,7,11], nums2=[2,4,6], k=3.
Initialize heap: [1+2=3,0,0], [7+2=9,1,0], [11+2=13,2,0].
heap = [[3,0,0],[9,1,0],[13,2,0]]

Pop [3,0,0]: result=[[1,2]]. Push [1+4=5,0,1]. heap=[[5,0,1],[9,1,0],[13,2,0]].
Pop [5,0,1]: result=[[1,2],[1,4]]. Push [1+6=7,0,2]. heap=[[7,0,2],[9,1,0],[13,2,0]].
Pop [7,0,2]: result=[[1,2],[1,4],[1,6]]. j+1=3=nums2.length → no push.

result.length=3=k. Return [[1,2],[1,4],[1,6]]. ✓
```

### Complexity
- Time: O(k log k) — initialization O(min(k,n) log min(k,n)); each of k extractions is O(log k) since heap size ≤ k + initial size ≤ 2k.
- Space: O(min(k, n)) — heap size at most min(k,n1) initially + k entries added, bounded by min(k,n1)+k.

### Edge Cases
- nums2 exhausted for row i: `j+1 >= nums2.length` → no push; that row is finished.
- k > n1 × n2: return all possible pairs (loop terminates when heap empties).
- Duplicate sums: heap correctly returns all pairs with those sums in any order — both are valid.
- Large nums1, small k: initialization only adds min(k, nums1.length) rows — doesn't unnecessarily load the entire nums1.

### Follow-up Questions
- "What if both arrays are unsorted?" — Sort both first: O(n log n + m log m) + O(k log k) for the heap.
- "Find K pairs with largest sums?" — Use a max-heap; initialize with nums1[-1] + nums2[-1] (last elements); expand backward (j-1, i-1 when j=0).
- "Count all pairs with sum ≤ T (not just K)?" — Two-pointer on sorted arrays: O(n + m).

## Problem 6 — Kth Largest Element in a Stream

### Problem

Design a class to find the `k`th largest element in a stream. `KthLargest(k, nums)` initializes the object with the integer `k` and the initial stream `nums`. `add(val)` appends `val` to the stream and returns the element representing the `k`th largest.

```
KthLargest kthLargest = new KthLargest(3, [4,5,8,2]);
kthLargest.add(3);  // stream=[4,5,8,2,3] → kth largest (k=3) = 4. returns 4.
kthLargest.add(5);  // stream=[4,5,8,2,3,5] → kth largest = 5. returns 5.
kthLargest.add(10); // stream=[...,10]       → kth largest = 5. returns 5.
kthLargest.add(9);  // stream=[...,9]        → kth largest = 8. returns 8.
kthLargest.add(4);  // stream=[...,4]        → kth largest = 8. returns 8.
```

### Pattern Recognition
Online/streaming top K using a min-heap of size K. The heap's top is always the current Kth largest element in the entire stream seen so far — accessible in O(1). Each `add` is O(log k).

### Key Insight
The invariant "min-heap of size k holds the k largest elements seen so far; its top = kth largest" is maintained continuously across all `add` calls without access to the full stream history. After every `add`, either the new element was not in the top k (ignored or already displaced) or it entered the top k and displaced the old kth largest. Either way, `heap.top()` is the updated answer.

### Approach
Constructor: build the heap by processing each element in `nums` with the add-to-top-k logic. `add(val)`: push val; if heap size exceeds k, pop; return `heap.top()`.

### Solution

```js
class KthLargest {
  constructor(k, nums) {
    this.k    = k;
    this.heap = new MinHeap(); // min-heap of size k: top = kth largest
    for (const x of nums) this.add(x); // build incrementally
  }

  add(val) {
    this.heap.push(val);
    if (this.heap.size() > this.k) {
      this.heap.pop();          // evict the smallest (no longer in top k)
    }
    return this.heap.top();     // O(1): top is always the kth largest
  }
}
```

### Dry Run

```
KthLargest(3, [4,5,8,2])  (k=3)

Constructor — process initial nums:
  add(4): heap=[4]. size=1≤3.
  add(5): heap=[4,5]. size=2≤3.
  add(8): heap=[4,5,8]. size=3≤3.
  add(2): heap=[2,5,8,4] → size=4>3 → pop min=2. heap=[4,5,8].
  heap=[4,5,8]. heap.top()=4 = 3rd largest of {4,5,8,2}. ✓

add(3):  push 3 → heap=[3,5,8,4]. size=4>3 → pop 3 → heap=[4,5,8]. top=4. return 4. ✓
add(5):  push 5 → heap=[4,5,8,5,5]. size=5>3 → pop 4 → heap=[5,5,8]. top=5. return 5. ✓
add(10): push 10 → size=4>3 → pop 5 → heap=[5,8,10]. top=5. return 5. ✓
add(9):  push 9 → size=4>3 → pop 5 → heap=[8,9,10]. top=8. return 8. ✓
add(4):  push 4 → size=4>3 → pop 4 → heap=[8,9,10]. top=8. return 8. ✓
```

### Complexity
- Constructor: O(n log k) — n initial elements, each O(log k) heap op.
- `add`: O(log k) — one push + at most one pop.
- Space: O(k) — heap holds exactly k elements after the constructor.

### Edge Cases
- Initial stream has fewer than k elements: the heap never fills to size k during construction; `add` will still work but `heap.top()` before k elements have been seen would give the current minimum, not the true kth largest (the problem guarantees there will always be ≥ k elements when `add` is called).
- Adding the same element repeatedly: heap correctly handles duplicates — equal elements are treated as distinct entries.
- val < heap.top(): push then immediately pop (since push brings size to k+1, pop removes the new min = val itself). heap unchanged, returns same top. O(log k) — slightly wasteful but correct; can be short-circuited: `if (heap.size() === k && val <= heap.top()) return heap.top()`.

### Follow-up Questions
- "Kth smallest in a stream?" — Use a max-heap of size k; its top = kth smallest. Evict the maximum when size exceeds k.
- "Median in a stream?" — Two heaps: max-heap (lower half) and min-heap (upper half); maintain sizes differ by ≤ 1; median is average of the two tops or the larger half's top.

## Problem 7 — Sort Characters By Frequency

### Problem

Given a string `s`, sort it in decreasing order based on the frequency of the characters. Return any valid answer (multiple valid orderings exist when frequencies are equal).

```
Input: s = "tree"   → "eert" or "eetr"  (e:2, t:1, r:1)
Input: s = "cccaaa" → "aaaccc" or "cccaaa"  (both c and a appear 3 times)
Input: s = "Aabb"   → "bbAa" or "bbaA"  (b:2, A:1, a:1 — 'A' ≠ 'a')
```

### Pattern Recognition
Frequency map + bucket sort for O(n) construction, then character concatenation in frequency-descending order. Alternatively, frequency map + max-heap. The bucket sort approach is O(n) and demonstrates the bounded-domain insight clearly.

### Key Insight
Character frequencies are bounded by the string length n — each character appears between 1 and n times. This makes bucket sort directly applicable: `buckets[f]` = list of characters with frequency f. Scanning from `buckets[n]` down to `buckets[1]`, appending each character freq times to the result, produces the string in frequency-descending order without any comparison-based sort.

### Approach
(A) **Bucket sort**: freq map → bucket array → scan high-to-low, append each character × its frequency. (B) **Max-heap**: freq map → push (freq, char) pairs → pop k times, appending each char × its frequency.

### Solution

```js
// Approach A: Bucket sort — O(n)
function frequencySort_bucket(s) {
  const freq = new Map();
  for (const ch of s) freq.set(ch, (freq.get(ch) ?? 0) + 1);

  // buckets[f] = all characters with frequency exactly f
  const buckets = Array.from({ length: s.length + 1 }, () => []);
  for (const [ch, cnt] of freq) buckets[cnt].push(ch);

  const parts = [];
  for (let f = buckets.length - 1; f >= 1; f--) {
    for (const ch of buckets[f]) {
      parts.push(ch.repeat(f)); // append this character f times
    }
  }
  return parts.join('');
}

// Approach B: Max-heap — O(n log n) due to n distinct characters in worst case
function frequencySort_heap(s) {
  const freq = new Map();
  for (const ch of s) freq.set(ch, (freq.get(ch) ?? 0) + 1);

  // Max-heap on frequency (negate for min-heap simulation)
  const heap = new MinHeap((a, b) => b[0] - a[0]); // max-heap on freq
  for (const [ch, cnt] of freq) heap.push([cnt, ch]);

  const parts = [];
  while (heap.size()) {
    const [cnt, ch] = heap.pop();
    parts.push(ch.repeat(cnt));
  }
  return parts.join('');
}
```

### Dry Run

```
s = "tree", n = 4.
freq = {t:1, r:1, e:2}

Bucket sort:
  buckets[1] = ['t','r'], buckets[2] = ['e']

  f=4: empty. f=3: empty.
  f=2: ['e'] → append 'ee'. parts=['ee'].
  f=1: ['t','r'] → append 't', 'r'. parts=['ee','t','r'].
  Join: "eetr". ✓ (or "eetr", "eetr" — valid)

s = "cccaaa", n = 6.
freq = {c:3, a:3}
  buckets[3] = ['c','a']
  f=3: append 'ccc' then 'aaa'. → "cccaaa". ✓
```

### Complexity
- **Bucket sort**: Time O(n) — freq map O(n), bucket fill O(unique chars ≤ n), scan O(n). Space O(n).
- **Max-heap**: Time O(n + m log m) where m = unique chars ≤ min(n, alphabet size). Space O(m).

### Edge Cases
- Single character string: freq map has one entry at count n; `buckets[n]=[ch]`; result = `ch.repeat(n)`.
- All characters identical: same as above.
- Case-sensitive: `'A'` and `'a'` are distinct characters; freq map tracks them separately. The output `"bbAa"` is correct for `"Aabb"`.
- Tie in frequency (`"cccaaa"`): either order is valid since the problem says "any valid answer." Bucket scan order depends on insertion order into `buckets[3]`, which varies — both are correct.

### Follow-up Questions
- "Return all valid orderings sorted lexicographically?" — After building frequency groups, sort characters within each frequency group alphabetically; but across groups, higher-frequency characters always come first. Return the unique lexicographically smallest valid ordering.
- "Custom frequency ranking (e.g., tie-break by original character order)?" — Add a third key to the heap comparator or to the bucket's ordering.

## Quick Reference — Pattern Decision Tree

```
What type of "top K" or "Kth element" problem is this?
│
├── INPUT IS A STREAM (online — elements arrive one at a time)?
│   └── Min-heap of size k: O(log k) per element, O(k) space
│       add(x): push x; if size > k: pop; return top.
│       Invariant: heap holds k largest elements seen so far; top = kth largest.
│
├── TOP K BY FREQUENCY (count occurrences, return k most common)?
│   ├── O(n) time required or preferred → HashMap + bucket sort
│   │     freq map → buckets[f] = elements with freq f → scan high-to-low
│   │     Key requirement: frequencies are bounded integers in [1, n]
│   │
│   └── k << n, general purpose → HashMap + min-heap of size k
│         Push [freq, element]; pop when size > k; extract remaining k elements.
│
├── TOP K LARGEST / SMALLEST (by raw value)?
│   ├── O(n) average, array mutable     → Quickselect (Lomuto or Hoare partition)
│   │     Partition so larger elements on left; recurse on half containing rank k-1
│   │
│   ├── O(n log k), no mutation         → Min-heap of size k (top k largest)
│   │                                     Max-heap of size k (top k smallest)
│   └── Simplicity / small n            → Sort + take first k
│
├── TOP K BY CUSTOM KEY (distance, score, multi-field comparison)?
│   └── Precompute key once per element → Min or max heap with custom comparator
│         Store [key, element]; heap compares by key in O(1).
│         Custom tie-breaking: primary key first, secondary key second in comparator.
│
├── K PAIRS / K COMBINATIONS with smallest/largest sum?
│   └── K-way merge with lazy expansion: O(k log k)
│         Init heap with first element of each sorted "virtual list" (one per nums1[i]).
│         On pop (sum, i, j): push (nums1[i]+nums2[j+1], i, j+1) if j+1 valid.
│         Heap size stays ≤ min(k, n) throughout.
│
├── FULL FREQUENCY-BASED SORT (sort all elements by frequency)?
│   └── HashMap + bucket sort (O(n)) or HashMap + max-heap (O(n log n))
│         Scan buckets high-to-low, appending each element × its frequency.
│
└── TRICKY SIGNALS → which heap orientation:
    "k largest" or "k most frequent"  → MIN-heap of size k  (min = eviction candidate)
    "k smallest" or "k closest"       → MAX-heap of size k  (max = eviction candidate)
    Tie-breaking ascending (earlier)  → heap evicts lexicographically LATER elements first
    Tie-breaking descending (later)   → heap evicts lexicographically EARLIER elements first
```

## Common Bugs Checklist

Before submitting any top-K solution, verify:

1. **Using max-heap when min-heap is needed (or vice versa) for top K?** — For top K *largest*: use a MIN-heap of size k. The heap's top (minimum) is the weakest element, ready to be evicted when something better arrives. Using a max-heap means the top is always the strongest — it never signals "evict me," making it useless for maintaining the top K efficiently. Mnemonic: *"the heap's top is the eviction candidate — for top K largest, the weakest survives longest, so we want the weakest at the top, which is a min-heap."*

2. **Comparing elements directly instead of their frequencies?** — In "top K frequent" heap problems, the comparator must key on `freq.get(word)`, not on the word itself. Writing `(a, b) => a - b` on raw word strings fails silently (compares by unicode, not frequency). Always verify the comparator reads from the frequency map: `(a, b) => freq.get(a) - freq.get(b)`.

3. **Heap size check: `> k` vs `>= k+1` vs `=== k+1`?** — After every push, the heap has at most k+1 elements. The eviction check `if (heap.size() > k) heap.pop()` correctly fires exactly when heap.size() is k+1. Using `>= k` fires when size is k (before the (k+1)th push), incorrectly evicting an element too early, leaving the heap with k-1 elements. Using `=== k+1` is equivalent to `> k` and also correct, but less idiomatic.

4. **Bucket scan direction: scanning from low bucket to high?** — For "top K most frequent," the scan must go from `buckets[n]` DOWN to `buckets[1]` — high frequency to low frequency. Scanning upward collects the least frequent elements first, producing the bottom K instead of the top K.

5. **Quickselect partition direction wrong for kth largest vs kth smallest?** — For kth largest: elements ≥ pivot go LEFT (position 0 = largest). For kth smallest: elements ≤ pivot go LEFT (position 0 = smallest). Using the kth-smallest partition for a kth-largest problem inverts the ordering and gives the wrong answer. Verify by tracing: after partitioning with pivot at index `p`, positions `[0..p-1]` should all be ≥ pivot for the kth-largest variant.

6. **Lexicographic tie-breaking in "top K frequent words" comparator: `a.localeCompare(b)` vs `b.localeCompare(a)`?** — The heap evicts the "worst" word (its minimum). Among equal-frequency words, "worse" = lexicographically later (alphabetically later words rank lower). So the comparator should mark lexicographically later words as "smaller" (evicted first): use `b.localeCompare(a)`, not `a.localeCompare(b)`. Using `a.localeCompare(b)` marks earlier words as "smaller" — earlier words evicted first — the result contains alphabetically later words, which is wrong.

7. **Heap output not sorted for problems that require ordered output?** — A min-heap extraction gives elements in no guaranteed order (only the minimum is returned first on each `pop`). For "top K frequent words" which requires output sorted by frequency then alphabetically, extract the k words from the heap and then sort them explicitly: `heap.data.sort(outputComparator)`. The heap determined *which* k words are correct; the sort determines *their order in the output*.

8. **K-way merge: pushing next element without checking bounds?** — After popping `(sum, i, j)`, attempting `heap.push([nums1[i] + nums2[j+1], i, j+1])` without first checking `j+1 < nums2.length` causes `nums2[j+1]` to be `undefined`, producing `NaN` sums and corrupting the heap. Always guard: `if (j + 1 < nums2.length) heap.push(...)`.

9. **Streaming Kth largest: short-circuit not applied?** — When `val ≤ heap.top()` and heap is already full (size k), the element cannot enter the top K — push + pop is correct but redundant. Some implementations forget this and push unconditionally, doing two O(log k) operations instead of the O(1) skip. The optimized check: `if (heap.size() < k || val > heap.top()) { heap.push(val); if (heap.size() > k) heap.pop(); }`. This matters for performance but not correctness.

10. **Bucket sort: including elements that appear 0 times in the scan?** — The frequency map contains only elements that actually appear in the input. When filling buckets, only `(element, freq)` pairs from the map are inserted — elements not in the input don't appear in any bucket. The bucket scan from n down to 1 naturally skips empty buckets (`for (const ch of buckets[f])` iterates zero times for an empty list). No explicit guard is needed, but verify that `buckets[0]` is never pushed into (an element with freq 0 doesn't exist in the input and should never be in the map).

---

**Final Tip:** At the 5 YOE level, the decisive signal for any top-K problem is immediately identifying the **correct heap orientation and the invariant it maintains**, not just reaching for "use a heap." For top K largest: *"a min-heap of size k holds exactly the k largest elements seen so far; its top is the Kth largest — the eviction candidate — because the minimum of the k largest is the least deserving of its spot and should be replaced first when a better element arrives."* For top K frequent with tie-breaking: *"the heap's comparator expresses which element is most evictable — lower frequency means more evictable; among equal frequencies, lexicographically later means more evictable — so `b.localeCompare(a)` in the tie-breaking position marks later words as 'smaller' in the heap, keeping them at the top ready for eviction."* For K-way merge: *"each heap entry encodes not just the current candidate but also where to find the next candidate (the row and column index), so popping generates exactly one new candidate from the same sorted sequence — the heap size stays bounded while the total candidate space is explored lazily."* Naming the invariant before writing any code, and then verifying that every operation preserves it, is what distinguishes a senior engineer who understands *why* the structure works from a candidate who has memorized *that* it works.
