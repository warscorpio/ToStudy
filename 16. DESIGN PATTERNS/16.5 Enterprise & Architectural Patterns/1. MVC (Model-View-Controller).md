# Enterprise & Architectural Patterns: MVC (Model-View-Controller) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is MVC?**
A: MVC (Model-View-Controller) is an architectural pattern that separates an application into three interconnected components — Model, View, and Controller — each with a distinct responsibility. The separation ensures that changes to one component (e.g., switching the database) have minimal impact on the others (e.g., the UI doesn't need to change). Trygve Reenskaug introduced MVC in 1979 at Xerox PARC for Smalltalk-80; it has since become the dominant pattern for UI-driven applications and REST APIs.

- **Model** — represents the application's data, business rules, and state. Knows nothing about how it is displayed or how user input is received. In a backend context: entities, repositories, domain services, validation logic.
- **View** — renders data from the Model for presentation. Has no business logic; it receives data and displays it. In a backend context: response serializers, templates, JSON DTOs. In a frontend context: HTML templates, React components.
- **Controller** — receives input (HTTP requests, user gestures), invokes the appropriate Model operations, selects the View to render, and returns the response. It is the orchestrator — thin, containing only routing and delegation logic.

**Q2. What is the flow of a request through MVC?**
A: The canonical request-response cycle:

```
Client Request
      │
      ▼
  Controller  ──────────────────────▶  Model
  (receives input,                    (business logic,
   validates request,                  data access,
   calls model)                        state change)
      │                                    │
      │◀──────────── data/result ──────────┘
      │
      ▼
    View
  (serializes data
   into response format)
      │
      ▼
Client Response
```

Step by step:
1. Client sends an HTTP request — `POST /loans/approve`.
2. **Router** matches the URL to a `LoanController.approve()` method.
3. **Controller** parses the request (path params, body, headers), performs basic validation, and calls `LoanService.approveLoan(loanId)`.
4. **Model** (service + repository) executes business logic, updates state, and returns a result.
5. **Controller** passes the result to the **View** (a response serializer or template engine).
6. **View** formats the data as JSON (or HTML) and the Controller sends the HTTP response.

**Q3. What is the Single Responsibility of each MVC component?**
A:
- **Model's responsibility** — *what the application knows and does*. It owns: data structure definitions, validation rules, business logic, persistence (via repositories), and state transitions. The Model should be testable without any HTTP framework or UI involvement.
- **View's responsibility** — *how data is presented*. In a REST API, the View serializes model data to JSON (a DTO/response class). In a server-rendered app, it renders HTML templates. The View should be swappable without changing the Model or Controller.
- **Controller's responsibility** — *bridging input to model and model to view*. It should: parse and validate the HTTP request format, call the appropriate service method, handle errors by mapping them to HTTP status codes, and return the View's output. Controllers must be kept thin — business logic belongs in the Model.

**Q4. What is the difference between MVC in a server-rendered web app vs. a REST API backend?**
A: The roles are the same but the View changes significantly:

| Aspect           | Server-Rendered (Express + Handlebars)               | REST API (NestJS + JSON)                             |
|---               |---                                                   |---                                                   |
| View             | HTML template rendered on the server                 | JSON serializer / Response DTO                       |
| View output      | Complete HTML page sent to browser                   | JSON body consumed by a client app                   |
| View selection   | Controller picks a template name                     | Controller returns a typed DTO / class-transformer  |
| State management | Session, cookies, server-side state                  | Stateless — each request carries its own context    |
| Navigation       | Browser follows redirects                            | Client handles navigation based on response          |
| MVC boundary     | Entire request-response in one process               | Controller + Model in server; View in client (React) |

In a modern SPA + REST API architecture, the "View" layer is effectively split: the server provides JSON (the data view), and a separate React/Vue/Angular app is responsible for rendering. The server-side MVC becomes MC — Model and Controller — with the View living in the frontend.

**Q5. What are the most common violations of MVC and why are they harmful?**
A: The two most prevalent violations are Fat Controller and Smart View:

**Fat Controller** — the controller contains business logic that belongs in the Model:
```ts
// FAT CONTROLLER — business logic in the wrong layer
@Post(":id/approve")
async approveLoan(@Param("id") loanId: string, @Body() dto: ApproveDto): Promise<void> {
  const loan = await this.loanRepo.findById(loanId);
  if (!loan) throw new NotFoundException();

  // Business logic — should be in LoanService (Model layer)
  if (loan.status !== "PENDING") throw new BadRequestException("Only pending loans can be approved");
  if (loan.amount > 500_000 && dto.approverId === loan.createdBy) {
    throw new ForbiddenException("Self-approval not allowed for large loans");
  }
  const creditResult = await this.creditService.check(loan.userId);
  if (creditResult.score < 650) throw new UnprocessableEntityException("Credit score insufficient");

  loan.status = "APPROVED";
  loan.approvedBy = dto.approverId;
  loan.approvedAt = new Date();
  await this.loanRepo.save(loan);
  await this.emailService.sendApprovalEmail(loan.userId);
}
```
Harm: the controller cannot be reused (a Kafka consumer that also approves loans must duplicate this logic), the business rules are untestable without an HTTP stack, and adding a new approval channel (CLI, event consumer) means duplicating logic.

**Smart View** — the view contains formatting, calculation, or conditional logic:
```ts
// SMART VIEW — business logic leaking into the serializer
class LoanResponseDto {
  @Transform(({ obj }) => {
    // Calculating EMI in the view layer — business logic
    const rate = obj.interestRate / 12 / 100;
    return Math.round(obj.amount * rate * Math.pow(1 + rate, obj.tenure) / (Math.pow(1 + rate, obj.tenure) - 1));
  })
  monthlyEmi: number;

  @Transform(({ obj }) => obj.status === "APPROVED" && new Date() > obj.disbursementDate ? "OVERDUE" : obj.status)
  displayStatus: string; // business rule about overdue status in the view
}
```
Harm: the business logic (EMI formula, overdue status rule) is buried in the serialization layer, invisible to tests of the Model, duplicated if the API has multiple response formats, and unavailable to non-HTTP consumers.

## Section 2: MVC in NestJS

**Q6. How does NestJS implement MVC?**
A: NestJS's architecture maps directly to MVC, with the addition of a Service layer that is the practical home of the Model's business logic:

```
Controller     →    Service (Model)    →    Repository (Model)
@Controller        @Injectable              TypeORM/Mongoose
@Get/@Post         Business logic           DB access
Input parsing      Domain rules             Data persistence
Response DTO       State transitions        Query building
```

NestJS's component mapping:
- **Controller** (`@Controller`, `@Get`, `@Post`, `@Body`, `@Param`) — the C in MVC.
- **Service** (`@Injectable`) — the business logic portion of the M in MVC.
- **Entity / Schema** (TypeORM `@Entity`, Mongoose `Schema`) — the data model portion of M.
- **Repository** (TypeORM `Repository`, Mongoose `Model`) — the persistence portion of M.
- **DTO + class-transformer + class-validator** — the V in MVC for REST APIs (input validation + output serialization).
- **Interceptors + `@UseInterceptors(ClassSerializerInterceptor)`** — enforce the View layer (automatically serialize responses via DTOs).

```ts
// Controller — thin, orchestrates only
@Controller("loans")
@UseInterceptors(ClassSerializerInterceptor) // enforces DTO serialization (View)
export class LoanController {
  constructor(private readonly loanService: LoanService) {}

  @Post(":id/approve")
  @UseGuards(JwtAuthGuard, RolesGuard)
  @Roles("RISK_MANAGER", "ADMIN")
  async approveLoan(
    @Param("id", ParseUUIDPipe) loanId: string,
    @Body() dto: ApproveLoanDto,
    @Request() req: AuthenticatedRequest,
  ): Promise<LoanResponseDto> {
    // Controller does: parse input, call model, return view
    const loan = await this.loanService.approveLoan(loanId, req.user.id);
    return new LoanResponseDto(loan); // View — serializes model data to response shape
  }
}

// Service — Model layer, owns all business logic
@Injectable()
export class LoanService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly creditService: CreditService,
    private readonly eventEmitter: EventEmitter2,
  ) {}

  async approveLoan(loanId: string, approverId: string): Promise<Loan> {
    const loan = await this.loanRepo.findById(loanId);
    if (!loan) throw new LoanNotFoundException(loanId);

    // All business logic lives here — not in the controller
    loan.approve(approverId); // domain method on the entity
    await this.loanRepo.save(loan);
    this.eventEmitter.emit("loan.approved", new LoanApprovedEvent(loan));
    return loan;
  }
}

// DTO — View layer for REST APIs
export class LoanResponseDto {
  @Expose() id: string;
  @Expose() status: string;
  @Expose() amount: number;
  @Expose() @Type(() => Date) approvedAt?: Date;

  @Exclude() // never exposed — sensitive internal field
  internalRiskScore: number;

  constructor(loan: Loan) {
    Object.assign(this, loan);
  }
}
```

**Q7. What is the role of DTOs in NestJS MVC, and how do they relate to View and Model?**
A: DTOs (Data Transfer Objects) serve double duty in NestJS:

- **Input DTOs (Request)** — validate and shape incoming data. They belong at the boundary between the Controller and the Model — the Controller receives them via `@Body()`, validates them with `class-validator` Pipes, and passes clean data to the Service. They protect the Model from receiving malformed input.
- **Output DTOs (Response)** — shape outgoing data. They belong at the boundary between the Model and the external consumer — they are the **View** in a REST API. They control exactly what fields are exposed, their format, and their names.

```ts
// Input DTO — protects the Model from invalid data
export class CreateLoanDto {
  @IsUUID()
  userId: string;

  @IsNumber()
  @Min(10_000)
  @Max(1_000_000)
  amount: number;

  @IsInt()
  @Min(6)
  @Max(60)
  tenureMonths: number;

  @IsEnum(LoanPurpose)
  purpose: LoanPurpose;
}

// Output DTO — the View for REST API responses
export class LoanResponseDto {
  @Expose()
  id: string;

  @Expose()
  @Transform(({ value }) => value.toUpperCase()) // view-level formatting only — no business logic
  status: string;

  @Expose()
  @Transform(({ value }) => `₹${value.toLocaleString("en-IN")}`) // display formatting
  formattedAmount: string;

  @Expose()
  amount: number;

  @Expose()
  @Type(() => UserSummaryDto)
  user: UserSummaryDto; // nested DTO — view controls nesting shape

  @Exclude()
  internalCreditScore: number; // model field — hidden from external view

  @Exclude()
  rawRiskFlags: string[];      // compliance-sensitive — excluded from API response
}
```

The separation matters: if the API needs a v2 response format (renamed fields, different nesting), only the Output DTO changes — the Model and Controller are untouched. This is the View layer's purpose: insulate the Model from presentation concerns.

**Q8. How do you keep NestJS controllers thin in practice?**
A: A controller should do exactly five things and nothing else: parse input, validate request format, call a service, handle cross-cutting concerns (auth, guards, logging via decorators), and return a response. Every line beyond that is a code smell:

```ts
// THIN CONTROLLER — reference implementation
@Controller("loans")
@ApiTags("Loans")
@UseInterceptors(ClassSerializerInterceptor)
export class LoanController {
  constructor(
    private readonly commandBus: CommandBus,   // CQRS Mediator
    private readonly queryBus: QueryBus,
  ) {}

  @Post()
  @UseGuards(JwtAuthGuard)
  @HttpCode(HttpStatus.CREATED)
  async createLoan(
    @Body() dto: CreateLoanDto,
    @CurrentUser() user: AuthUser,
  ): Promise<LoanResponseDto> {
    return this.commandBus.execute(new CreateLoanCommand(dto, user.id));
    // One line. All business logic in the command handler.
  }

  @Get(":id")
  @UseGuards(JwtAuthGuard)
  async getLoan(
    @Param("id", ParseUUIDPipe) loanId: string,
    @CurrentUser() user: AuthUser,
  ): Promise<LoanResponseDto> {
    return this.queryBus.execute(new GetLoanQuery(loanId, user.id));
    // One line. Authorization and data fetching in the query handler.
  }

  @Post(":id/approve")
  @UseGuards(JwtAuthGuard, RolesGuard)
  @Roles("RISK_MANAGER", "ADMIN")
  async approveLoan(
    @Param("id", ParseUUIDPipe) loanId: string,
    @Body() dto: ApproveLoanDto,
    @CurrentUser() user: AuthUser,
  ): Promise<LoanResponseDto> {
    return this.commandBus.execute(new ApproveLoanCommand(loanId, user.id));
    // One line. Approval logic in the command handler.
  }
}
```

The smell test: if you need to mock more than one or two things to test a controller method, the controller is too fat. A controller test should only verify that the right command/query was dispatched with the right parameters.

**Q9. How does NestJS handle the View layer for server-rendered HTML (not REST APIs)?**
A: NestJS supports traditional server-rendered MVC via template engines:

```ts
// main.ts — configure template engine
async function bootstrap() {
  const app = await NestFactory.create<NestExpressApplication>(AppModule);
  app.useStaticAssets(join(__dirname, "..", "public"));
  app.setBaseViewsDir(join(__dirname, "..", "views"));
  app.setViewEngine("hbs"); // Handlebars — or "pug", "ejs"
  await app.listen(3000);
}

// Controller — returns template name + data (not a DTO)
@Controller("loans")
export class LoanViewController {
  constructor(private readonly loanService: LoanService) {}

  @Get(":id")
  @Render("loan-detail") // View name — renders views/loan-detail.hbs
  async getLoanPage(@Param("id") loanId: string): Promise<object> {
    const loan = await this.loanService.findById(loanId);
    // Return plain object — template receives it as context
    return {
      loan: {
        id: loan.id,
        status: loan.status,
        amount: loan.amount,
        formattedAmount: `₹${loan.amount.toLocaleString("en-IN")}`,
      },
      pageTitle: `Loan Details — ${loan.id}`,
    };
  }
}

// views/loan-detail.hbs — the View
// <h1>{{pageTitle}}</h1>
// <p>Status: {{loan.status}}</p>
// <p>Amount: {{loan.formattedAmount}}</p>
// {{#if loan.approvedAt}}
//   <p>Approved on: {{loan.approvedAt}}</p>
// {{/if}}
```
The template is the View — it receives a context object (plain data, not a domain entity) and renders HTML. The controller is the C. The service is the M. The boundaries are identical to the REST API case; only the View format changes.

## Section 3: MVC Variants — MVP, MVVM, MVC+S

**Q10. What is MVP (Model-View-Presenter) and how does it differ from MVC?**
A: MVP is a variant of MVC that makes the View completely passive. The Presenter replaces the Controller but takes on more responsibility — it handles all the logic for updating the View:

| Aspect              | MVC                                              | MVP                                                   |
|---                  |---                                               |---                                                    |
| View intelligence   | View can observe Model directly in some variants | View is completely passive — knows nothing of Model   |
| Who updates View?   | Controller or direct Model-View binding          | Presenter updates View explicitly via interface       |
| View-Model coupling | May exist (especially in classic Smalltalk MVC)  | Zero — View interface is the boundary                 |
| Testability         | Controller testable; View harder                 | Presenter fully testable; View is a dumb stub         |
| Common in           | Web frameworks, REST APIs                        | Android (legacy), WinForms, some desktop UIs          |

```ts
// MVP — View is a pure interface the Presenter talks to
interface LoanDetailView {
  showLoanStatus(status: string): void;
  showAmount(formatted: string): void;
  showError(message: string): void;
  showLoading(visible: boolean): void;
}

class LoanDetailPresenter {
  constructor(
    private readonly view: LoanDetailView,
    private readonly loanService: LoanService,
  ) {}

  async loadLoan(loanId: string): Promise<void> {
    this.view.showLoading(true);
    try {
      const loan = await this.loanService.findById(loanId);
      this.view.showLoanStatus(loan.status);
      this.view.showAmount(`₹${loan.amount.toLocaleString("en-IN")}`);
    } catch (err) {
      this.view.showError("Failed to load loan details");
    } finally {
      this.view.showLoading(false);
    }
  }
}
```
MVP's passive View means the View can be a mock in tests — testing the Presenter requires no DOM, no browser, no HTTP. This made MVP dominant in legacy Android development and WinForms desktop apps.

**Q11. What is MVVM (Model-View-ViewModel) and how does it differ from MVC?**
A: MVVM replaces the Controller/Presenter with a ViewModel — an abstraction of the View's state that the View binds to declaratively. Instead of the Presenter pushing data to the View's interface, the View observes the ViewModel's state directly via data binding:

| Aspect              | MVC                                   | MVVM                                            |
|---                  |---                                    |---                                              |
| Who drives the View?| Controller actively pushes data       | View declaratively binds to ViewModel state     |
| Communication       | Controller → View (imperative)        | ViewModel ↔ View (reactive binding)             |
| View-ViewModel link | No direct link — Controller mediates  | Two-way data binding                            |
| Testability         | Controller testable independently     | ViewModel testable; binding logic tested by UI  |
| Common in           | Web frameworks, REST APIs             | React, Vue, Angular, WPF, SwiftUI               |

```ts
// MVVM — React as the View binding to a ViewModel (custom hook)
// ViewModel — manages state, exposes it reactively
function useLoanViewModel(loanId: string) {
  const [loan, setLoan] = useState<Loan | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  // Commands — actions the View can invoke
  const approveLoan = async (approverId: string) => {
    try {
      const updated = await loanService.approve(loanId, approverId);
      setLoan(updated);
    } catch (err) {
      setError("Approval failed. Please try again.");
    }
  };

  useEffect(() => {
    loanService.findById(loanId)
      .then(setLoan)
      .catch(() => setError("Failed to load loan"))
      .finally(() => setLoading(false));
  }, [loanId]);

  // Derived state — computed in ViewModel, not in View
  const formattedAmount = loan ? `₹${loan.amount.toLocaleString("en-IN")}` : null;
  const canApprove = loan?.status === "PENDING";

  return { loan, loading, error, formattedAmount, canApprove, approveLoan };
}

// View — binds to ViewModel state declaratively; zero business logic
function LoanDetailView({ loanId }: { loanId: string }) {
  const { loan, loading, error, formattedAmount, canApprove, approveLoan } = useLoanViewModel(loanId);

  if (loading) return <Spinner />;
  if (error) return <ErrorMessage message={error} />;

  return (
    <div>
      <h1>Loan {loan!.id}</h1>
      <p>Amount: {formattedAmount}</p>
      <p>Status: {loan!.status}</p>
      {canApprove && (
        <button onClick={() => approveLoan(currentUser.id)}>Approve</button>
      )}
    </div>
  );
}
```
The ViewModel is where business logic moves in MVVM — the View is a pure rendering function. This is exactly the React hooks model: hooks are ViewModels.

**Q12. What is the MVC+S (MVC + Service Layer) pattern and why is it the standard in modern backend frameworks?**
A: Pure MVC puts all business logic in the Model. In practice, Models in REST API backends become too broad — a `LoanModel` would contain DB schema, validation, business rules, external service calls, and event publishing. MVC+S introduces a **Service layer** between the Controller and the Model's persistence layer:

```
Controller  →  Service  →  Repository  →  Database
     ↑              ↑
  (thin C)    (business M)    (persistence M)
                    ↓
             External APIs
             Event Bus
             Cache
```

- **Controller** — HTTP parsing, routing, input validation, response formatting.
- **Service** — business logic, orchestration, domain rules, transaction boundaries.
- **Repository** — data access abstraction, query building, ORM interaction.
- **Entity** — data shape, domain methods, business invariants.

This is what NestJS, Spring Boot, Laravel, and Django all implement in practice — MVC+S, not pure MVC. The "Model" in "MVC" maps to the Service + Repository + Entity stack collectively. Interviews sometimes call this "layered architecture" or "N-tier architecture" — it's the same concept.

## Section 4: MVC and Testing

**Q13. How does MVC separation enable each layer to be tested independently?**
A: The separation of concerns is the primary enabler of fast, isolated unit tests:

```ts
// Model (Service) test — no HTTP, no DB, pure business logic
describe("LoanService.approveLoan", () => {
  let service: LoanService;
  let mockRepo: jest.Mocked<LoanRepository>;
  let mockEventEmitter: jest.Mocked<EventEmitter2>;

  beforeEach(() => {
    mockRepo = { findById: jest.fn(), save: jest.fn() } as any;
    mockEventEmitter = { emit: jest.fn() } as any;
    service = new LoanService(mockRepo, mockEventEmitter);
  });

  it("approves a pending loan", async () => {
    const loan = Loan.create({ status: "PENDING", amount: 50_000 });
    mockRepo.findById.mockResolvedValue(loan);

    await service.approveLoan("loan-1", "approver-1");

    expect(loan.status).toBe("APPROVED");
    expect(mockRepo.save).toHaveBeenCalledWith(loan);
    expect(mockEventEmitter.emit).toHaveBeenCalledWith(
      "loan.approved",
      expect.objectContaining({ loanId: loan.id })
    );
  });

  it("throws when approving a non-pending loan", async () => {
    const loan = Loan.create({ status: "APPROVED" });
    mockRepo.findById.mockResolvedValue(loan);

    await expect(service.approveLoan("loan-1", "approver-1"))
      .rejects.toThrow(InvalidLoanStateError);
    expect(mockRepo.save).not.toHaveBeenCalled();
  });
});

// Controller test — no business logic, just routing verification
describe("LoanController.approveLoan", () => {
  let controller: LoanController;
  let mockCommandBus: jest.Mocked<CommandBus>;

  beforeEach(() => {
    mockCommandBus = { execute: jest.fn() } as any;
    controller = new LoanController(mockCommandBus);
  });

  it("dispatches ApproveLoanCommand with correct params", async () => {
    const mockLoan = buildLoanDto();
    mockCommandBus.execute.mockResolvedValue(mockLoan);

    const result = await controller.approveLoan(
      "loan-uuid",
      { reason: "Credit check passed" },
      { user: { id: "approver-uuid" } } as any,
    );

    expect(mockCommandBus.execute).toHaveBeenCalledWith(
      expect.objectContaining({
        loanId: "loan-uuid",
        approverId: "approver-uuid",
      })
    );
    expect(result).toBe(mockLoan);
  });
});

// View (DTO) test — serialization and field exclusion
describe("LoanResponseDto", () => {
  it("exposes public fields and excludes sensitive ones", () => {
    const loan = buildLoan({ id: "L1", status: "APPROVED", internalRiskScore: 42 });
    const dto = plainToClass(LoanResponseDto, loan, { excludeExtraneousValues: true });
    const serialized = instanceToPlain(dto);

    expect(serialized.id).toBe("L1");
    expect(serialized.status).toBe("APPROVED");
    expect(serialized.internalRiskScore).toBeUndefined(); // excluded
  });
});
```
Each layer's test is independent: Service tests have no HTTP overhead; Controller tests have no DB; DTO tests have no business logic. All three are millisecond-speed unit tests.

**Q14. How do you write integration tests that exercise the full MVC stack?**
A:
```ts
// Integration test — exercises Controller → Service → Repository → DB
describe("POST /loans/:id/approve (integration)", () => {
  let app: INestApplication;
  let dataSource: DataSource;

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({
      imports: [
        AppModule,
        TypeOrmModule.forRoot({ ...testDbConfig }), // test DB
      ],
    }).compile();

    app = moduleRef.createNestApplication();
    app.useGlobalPipes(new ValidationPipe({ transform: true }));
    app.useGlobalInterceptors(new ClassSerializerInterceptor(app.get(Reflector)));
    await app.init();

    dataSource = moduleRef.get(DataSource);
  });

  afterEach(async () => {
    await dataSource.query("TRUNCATE loans CASCADE");
  });

  afterAll(() => app.close());

  it("approves a pending loan and returns 200 with updated status", async () => {
    // Arrange — seed DB
    const loan = await dataSource.getRepository(LoanEntity).save(
      buildLoanEntity({ status: "PENDING", amount: 50_000 })
    );

    // Act — full HTTP request through the MVC stack
    const response = await request(app.getHttpServer())
      .post(`/loans/${loan.id}/approve`)
      .set("Authorization", `Bearer ${buildJwt({ roles: ["RISK_MANAGER"] })}`)
      .send({ reason: "All checks passed" })
      .expect(200);

    // Assert — View (response shape)
    expect(response.body.status).toBe("APPROVED");
    expect(response.body.id).toBe(loan.id);
    expect(response.body.internalRiskScore).toBeUndefined();

    // Assert — Model (DB state)
    const updated = await dataSource.getRepository(LoanEntity).findOne({ where: { id: loan.id } });
    expect(updated!.status).toBe("APPROVED");
    expect(updated!.approvedAt).toBeDefined();
  });

  it("returns 403 when a LOAN_OFFICER attempts to approve", async () => {
    const loan = await dataSource.getRepository(LoanEntity).save(
      buildLoanEntity({ status: "PENDING" })
    );

    await request(app.getHttpServer())
      .post(`/loans/${loan.id}/approve`)
      .set("Authorization", `Bearer ${buildJwt({ roles: ["LOAN_OFFICER"] })}`)
      .send({})
      .expect(403);
  });
});
```

## Section 5: MVC at Scale — Layered Architecture & Domain-Driven Design

**Q15. How does MVC evolve into a layered architecture for complex domains?**
A: Pure MVC works for simple CRUD applications. As domain complexity grows, the Service layer in MVC+S expands into multiple well-defined layers:

```
┌─────────────────────────────────────┐
│         Presentation Layer          │  Controllers, DTOs, Guards,
│         (MVC's Controller + View)   │  Interceptors, Pipes
├─────────────────────────────────────┤
│         Application Layer           │  Services, Command/Query Handlers,
│         (MVC's Model — orchestration│  Sagas, Use Cases
├─────────────────────────────────────┤
│         Domain Layer                │  Entities, Value Objects,
│         (MVC's Model — business     │  Domain Services, Domain Events,
│          rules and invariants)      │  Aggregates, Repository Interfaces
├─────────────────────────────────────┤
│       Infrastructure Layer          │  Repository Implementations,
│       (MVC's Model — persistence    │  ORM, External APIs, Kafka,
│        and external systems)        │  Cache, Email, SMS
└─────────────────────────────────────┘
```

The layering enforces dependency direction: upper layers depend on lower layers; lower layers never depend on upper layers. The Domain layer (business rules) depends on nothing else — it is testable without DB, without HTTP, without any framework.

In NestJS this maps to:
- **Presentation** — `@Controller`, `@UseGuards`, `@Body`, DTOs, interceptors.
- **Application** — `@CommandHandler`, `@QueryHandler`, `@Injectable` service orchestrators.
- **Domain** — plain TypeScript classes with no framework decorators: `Loan`, `LoanStatus`, `LoanApprovalPolicy`.
- **Infrastructure** — `TypeOrmLoanRepository implements LoanRepository`, `RazorpayGateway implements PaymentGateway`.

**Q16. What is the Repository pattern's role in MVC, and why does it matter for testability?**
A: The Repository pattern provides an abstraction over the persistence mechanism — it is the data-access portion of the Model layer in MVC. By depending on a `LoanRepository` interface rather than a TypeORM `Repository<LoanEntity>` directly, the Service layer becomes decoupled from the database:

```ts
// Repository interface — part of the Domain layer
export interface LoanRepository {
  findById(id: string): Promise<Loan | null>;
  findByUserId(userId: string, filters?: LoanFilters): Promise<Loan[]>;
  save(loan: Loan): Promise<void>;
  delete(id: string): Promise<void>;
  existsByPanAndStatus(pan: string, status: LoanStatus): Promise<boolean>;
}

// Infrastructure implementation — TypeORM-specific
@Injectable()
export class TypeOrmLoanRepository implements LoanRepository {
  constructor(
    @InjectRepository(LoanEntity)
    private readonly ormRepo: Repository<LoanEntity>,
  ) {}

  async findById(id: string): Promise<Loan | null> {
    const entity = await this.ormRepo.findOne({ where: { id }, relations: ["user"] });
    return entity ? LoanMapper.toDomain(entity) : null;
  }
  // ...
}

// In-memory implementation — for tests
export class InMemoryLoanRepository implements LoanRepository {
  private store = new Map<string, Loan>();

  async findById(id: string): Promise<Loan | null> {
    return this.store.get(id) ?? null;
  }
  async save(loan: Loan): Promise<void> {
    this.store.set(loan.id, loan);
  }
  // ...
}

// Service test uses InMemoryLoanRepository — no DB needed
const service = new LoanService(
  new InMemoryLoanRepository(),
  mockEventEmitter,
);
```
Without the Repository abstraction, Service tests require either a real database or a TypeORM mock — both slow and brittle. The interface boundary (part of MVC's Model layer) makes the Service's business logic independently testable.

**Q17. How does the Data Mapper pattern relate to MVC's Model layer?**
A: The Data Mapper pattern separates the domain object (Model) from its persistence representation (database row or document). In MVC, the Model should represent the domain — not the database schema. A Mapper handles the translation:

```ts
// Domain entity — Model layer, pure business object
export class Loan {
  private constructor(
    public readonly id: string,
    public status: LoanStatus,
    public readonly amount: number,
    public readonly userId: string,
    public approvedBy?: string,
    public approvedAt?: Date,
  ) {}

  static create(props: CreateLoanProps): Loan { /* ... */ }

  approve(approverId: string): void {
    if (this.status !== LoanStatus.PENDING) {
      throw new InvalidLoanStateError("Only pending loans can be approved");
    }
    this.status = LoanStatus.APPROVED;
    this.approvedBy = approverId;
    this.approvedAt = new Date();
  }

  isExpired(): boolean {
    const expiryDays = 30;
    const created = this.createdAt;
    return Date.now() - created.getTime() > expiryDays * 24 * 60 * 60 * 1000;
  }
}

// Database entity — Infrastructure layer, ORM-specific
@Entity("loans")
export class LoanEntity {
  @PrimaryGeneratedColumn("uuid") id: string;
  @Column() status: string;
  @Column("decimal") amount: number;
  @Column() user_id: string;           // snake_case in DB
  @Column({ nullable: true }) approved_by: string;
  @Column({ nullable: true }) approved_at: Date;
  @CreateDateColumn() created_at: Date;
}

// Data Mapper — translates between domain and persistence representations
export class LoanMapper {
  static toDomain(entity: LoanEntity): Loan {
    return Loan.reconstitute({
      id: entity.id,
      status: entity.status as LoanStatus,
      amount: Number(entity.amount),
      userId: entity.user_id,
      approvedBy: entity.approved_by,
      approvedAt: entity.approved_at,
      createdAt: entity.created_at,
    });
  }

  static toPersistence(domain: Loan): Partial<LoanEntity> {
    return {
      id: domain.id,
      status: domain.status,
      amount: domain.amount,
      user_id: domain.userId,
      approved_by: domain.approvedBy,
      approved_at: domain.approvedAt,
    };
  }
}
```
Without Data Mapper, the domain object is polluted by ORM decorators (`@Column`, `@Entity`) and is tightly coupled to the database schema. Changing a column name in the DB would require changing the Model class — a violation of the Model's isolation. The Mapper keeps the Model pure.

## Section 6: Pitfalls & Anti-patterns

**Q18. What is "Anemic Domain Model" and how does it relate to MVC?**
A: Anemic Domain Model (Martin Fowler's term) is when domain entities are pure data containers — getters/setters with no behavior — and all business logic lives in the Service layer instead. This is the most common MVC anti-pattern in enterprise backends:

```ts
// ANEMIC — entity is a data bag, no behavior
export class Loan {
  id: string;
  status: string;
  amount: number;
  approvedBy?: string;
  approvedAt?: Date;
  // No methods — just properties
}

// Service does EVERYTHING — fat service, thin model
@Injectable()
export class LoanService {
  async approveLoan(loanId: string, approverId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);
    // Business rules scattered across service methods
    if (loan.status !== "PENDING") throw new Error("Invalid state");
    if (!approverId) throw new Error("Approver required");
    // More rules...
    loan.status = "APPROVED";
    loan.approvedBy = approverId;
    loan.approvedAt = new Date();
    await this.loanRepo.save(loan);
  }
}
```

Problems: business rules are not co-located with the data they govern, rules can be bypassed by calling `repo.save()` with raw data, the domain model has no invariants, and the Service becomes a dumping ground.

Fix — rich domain model with business methods:
```ts
// RICH — entity owns its behavior and invariants
export class Loan {
  private status: LoanStatus;
  // ...

  approve(approverId: string): void {
    if (this.status !== LoanStatus.PENDING) {
      throw new InvalidLoanStateError(`Cannot approve a ${this.status} loan`);
    }
    if (!approverId) throw new Error("Approver ID is required");
    this.status = LoanStatus.APPROVED;
    this.approvedBy = approverId;
    this.approvedAt = new Date();
  }
}

// Service becomes thin — orchestrates, doesn't implement rules
async approveLoan(loanId: string, approverId: string): Promise<void> {
  const loan = await this.loanRepo.findById(loanId);
  loan.approve(approverId); // business logic is in the Model where it belongs
  await this.loanRepo.save(loan);
}
```

**Q19. What is "God Controller" and what causes it?**
A: God Controller is when a controller accumulates business logic, data access calls, external service orchestration, and response formatting all in one place. It is the Controller-layer equivalent of God Object:

```ts
// GOD CONTROLLER — does everything
@Post(":id/approve")
async approveLoan(@Param("id") loanId: string, @Body() dto: any): Promise<object> {
  // 1. Data access — belongs in repository
  const loan = await this.dataSource.query(`SELECT * FROM loans WHERE id = '${loanId}'`);

  // 2. Business validation — belongs in domain/service
  if (loan[0].status !== "PENDING") throw new BadRequestException("Invalid status");
  if (dto.amount > 500000) {
    const approver = await this.dataSource.query(`SELECT role FROM users WHERE id = '${dto.approverId}'`);
    if (approver[0].role !== "ADMIN") throw new ForbiddenException("Only admins can approve large loans");
  }

  // 3. External call — belongs in service
  const credit = await axios.get(`${process.env.CREDIT_URL}/check/${loan[0].user_id}`);
  if (credit.data.score < 650) throw new UnprocessableEntityException("Credit score too low");

  // 4. State mutation — belongs in domain
  await this.dataSource.query(`UPDATE loans SET status='APPROVED', approved_by='${dto.approverId}' WHERE id='${loanId}'`);

  // 5. Side effects — belongs in service/event handler
  await this.emailService.send(loan[0].user_email, "Your loan is approved");
  await this.smsService.send(loan[0].phone, "Loan approved");

  // 6. Response formatting mixed with data access
  return { id: loan[0].id, status: "APPROVED", message: "Loan has been successfully approved" };
}
```

Causes: insufficient architectural guidance, deadline pressure leading to the "just put it in the controller" shortcut, lack of code review enforcement. Consequence: impossible to test without a DB + email server + SMS server + credit API, impossible to reuse in non-HTTP contexts, impossible to change the approval logic without touching the controller.

**Q20. What is "View Logic Leakage" and how do you prevent it?**
A: View Logic Leakage is when business rules or domain computations are placed in the serialization layer (Response DTO, template, or JSON transformer) instead of in the Model:

```ts
// LEAKAGE — business rule in the View (DTO transformer)
class LoanResponseDto {
  @Transform(({ obj }) => {
    // This is a BUSINESS RULE about when a loan is considered "at risk"
    // It belongs in the Loan domain class or a domain service — not in the DTO
    const daysSinceApproval = (Date.now() - obj.approvedAt.getTime()) / 86_400_000;
    if (daysSinceApproval > 30 && obj.status === "DISBURSED" && !obj.firstRepaymentDate) {
      return "AT_RISK";
    }
    return obj.status;
  })
  displayStatus: string;
}
```

The problem: if the "at risk" logic needs to be evaluated in a Kafka consumer (for alerting), a cron job (for reporting), or a CLI tool (for ops), it must be duplicated from the DTO. The DTO is not reachable from non-HTTP code.

Fix — compute in the Model, expose in the View:
```ts
// Model — business rule lives here
export class Loan {
  get isAtRisk(): boolean {
    if (this.status !== LoanStatus.DISBURSED || this.firstRepaymentDate) return false;
    const daysSinceApproval = (Date.now() - this.approvedAt!.getTime()) / 86_400_000;
    return daysSinceApproval > 30;
  }

  get displayStatus(): string {
    return this.isAtRisk ? "AT_RISK" : this.status;
  }
}

// View — reads computed value from Model, no logic
class LoanResponseDto {
  @Expose() displayStatus: string; // populated from loan.displayStatus — no computation here

  constructor(loan: Loan) {
    this.displayStatus = loan.displayStatus; // Model computed it; DTO just exposes it
  }
}
```

## Section 7: Scenario / System Design Style Questions

**Q21. "You're reviewing a PR where a junior developer has added direct `axios` calls to a third-party credit bureau inside a NestJS controller. What feedback do you give?"**
A: The feedback addresses three MVC violations simultaneously:

**Violation 1 — Wrong layer:** HTTP calls to external services are infrastructure concerns. They belong in a service class (Application layer) or a dedicated gateway/adapter class (Infrastructure layer). Controllers handle HTTP *in*, not HTTP *out*.

**Violation 2 — Testability destroyed:** To test this controller, you now need the credit bureau to be available (or you need `axios` to be mocked globally — brittle). Extracting to a `CreditBureauGateway` service means the controller test simply mocks `creditBureauGateway.check()`.

**Violation 3 — Reusability broken:** If a Kafka consumer also needs to check credit scores, it can't reuse the controller's logic. An extracted `CreditBureauGateway` can be injected anywhere.

**Proposed fix:**
```ts
// Infrastructure layer — wraps the external HTTP call
@Injectable()
export class CreditBureauGateway {
  async checkScore(userId: string): Promise<CreditCheckResult> {
    const { data } = await this.http.get(`${this.config.creditUrl}/check/${userId}`);
    return { score: data.score, bureau: data.bureau };
  }
}

// Application layer — orchestrates
@Injectable()
export class LoanEligibilityService {
  constructor(private readonly creditGateway: CreditBureauGateway) {}

  async checkEligibility(userId: string): Promise<EligibilityResult> {
    const credit = await this.creditGateway.checkScore(userId);
    return { eligible: credit.score >= 650, creditScore: credit.score };
  }
}

// Controller — thin, delegates
@Post(":id/check-eligibility")
async checkEligibility(@Param("id") loanId: string): Promise<EligibilityResponseDto> {
  return this.loanEligibilityService.checkEligibility(loanId);
}
```

**Q22. "Your team is building a multi-channel lending platform — the same loan approval logic must work over REST API, a Kafka consumer, a gRPC service, and a CLI admin tool. How does proper MVC separation make this possible?"**
A: Proper MVC separation means the business logic (Model/Service layer) has no dependency on any transport mechanism. The same `LoanService.approveLoan()` can be called from any channel:

```ts
// Model — transport-agnostic business logic
@Injectable()
export class LoanService {
  async approveLoan(loanId: string, approverId: string): Promise<Loan> {
    // Pure business logic — no HTTP, no Kafka, no gRPC
    const loan = await this.loanRepo.findById(loanId);
    loan.approve(approverId);
    await this.loanRepo.save(loan);
    this.eventEmitter.emit("loan.approved", new LoanApprovedEvent(loan));
    return loan;
  }
}

// Channel 1 — REST API Controller
@Post(":id/approve")
async approveLoan(@Param("id") loanId: string, @Body() dto: ApproveLoanDto): Promise<LoanResponseDto> {
  const loan = await this.loanService.approveLoan(loanId, dto.approverId);
  return new LoanResponseDto(loan);
}

// Channel 2 — Kafka Consumer
@EventPattern("loan-commands")
async handleLoanCommand(@Payload() msg: LoanCommandMessage): Promise<void> {
  if (msg.type === "APPROVE_LOAN") {
    await this.loanService.approveLoan(msg.loanId, msg.approverId);
    // No response DTO — ack the Kafka message
  }
}

// Channel 3 — gRPC Service
async ApproveLoan(data: ApproveLoanRequest, metadata: Metadata): Promise<ApproveLoanResponse> {
  const loan = await this.loanService.approveLoan(data.loanId, data.approverId);
  return { loanId: loan.id, status: loan.status }; // gRPC response — different "View"
}

// Channel 4 — CLI Command
async run(passedParams: string[]): Promise<void> {
  const [loanId, approverId] = passedParams;
  const loan = await this.loanService.approveLoan(loanId, approverId);
  console.log(`Loan ${loan.id} approved successfully`); // console output is the "View"
}
```
Each channel is a thin "Controller" with its own "View" format (JSON DTO, Kafka ack, Protobuf response, console output). The Model is shared and tested once. This is the architectural proof of MVC's value at scale.

**Q23. "Your NestJS app has a `LoanController` with 15 injected services. A simple `GET /loans/:id` endpoint takes 6ms just in the controller before any DB query. How do you diagnose and fix this?"**
A: The symptoms — many injected services + overhead before DB — indicate a Fat Controller with initialization-time work or cross-cutting concerns mixed in. Diagnostic steps:

1. **Profile the controller constructor** — if 15 services are being injected, their constructors run on app initialization (for singletons) or per-request (for request-scoped providers). Check if any service constructor makes network calls or heavy initialization.

2. **Count what each injection actually does** — if 10 of the 15 services are only used in 2 of 15 endpoints, the controller has too broad a scope. Split into feature-focused controllers (`LoanReadController`, `LoanWriteController`, `LoanApprovalController`).

3. **Check for synchronous cross-cutting work in the controller method** — logging, audit calls, metrics recording that should be in interceptors:
   ```ts
   // BEFORE — controller does cross-cutting work
   async getLoan(@Param("id") id: string): Promise<LoanResponseDto> {
     this.auditService.log("READ", id);       // should be interceptor
     this.metricsService.increment("read");   // should be interceptor
     this.rateLimiter.check(id);              // should be guard
     const loan = await this.loanService.findById(id);
     return new LoanResponseDto(loan);
   }
   ```

4. **Move to CQRS** — replace 15 service injections with one `QueryBus`:
   ```ts
   // AFTER — controller has one dependency
   constructor(private readonly queryBus: QueryBus) {}

   async getLoan(@Param("id") id: string): Promise<LoanResponseDto> {
     return this.queryBus.execute(new GetLoanQuery(id));
   }
   ```

**Q24. "How do you implement versioned API responses (v1 and v2) without duplicating business logic?"**
A: API versioning is a View concern, not a Model concern. The same Model serves both versions; different DTOs format the response differently:

```ts
// Model — unchanged across versions
@Injectable()
export class LoanService {
  async findById(id: string): Promise<Loan> { /* ... */ }
}

// V1 DTO — original response shape
export class LoanResponseDtoV1 {
  @Expose() id: string;
  @Expose() status: string;
  @Expose() amount: number;
  @Expose() user_id: string; // v1 used snake_case
}

// V2 DTO — revised response shape
export class LoanResponseDtoV2 {
  @Expose() id: string;
  @Expose() status: string;
  @Expose() amount: number;
  @Expose() userId: string;       // v2 uses camelCase
  @Expose() formattedAmount: string; // v2 adds formatted field
  @Expose() @Type(() => UserSummaryDto) user: UserSummaryDto; // v2 nests user object
}

// Versioned controllers — same service, different View
@Controller({ path: "loans", version: "1" })
export class LoanControllerV1 {
  constructor(private readonly loanService: LoanService) {}

  @Get(":id")
  async getLoan(@Param("id") id: string): Promise<LoanResponseDtoV1> {
    const loan = await this.loanService.findById(id);
    return plainToClass(LoanResponseDtoV1, loan, { excludeExtraneousValues: true });
  }
}

@Controller({ path: "loans", version: "2" })
export class LoanControllerV2 {
  constructor(private readonly loanService: LoanService) {}

  @Get(":id")
  async getLoan(@Param("id") id: string): Promise<LoanResponseDtoV2> {
    const loan = await this.loanService.findById(id);
    return plainToClass(LoanResponseDtoV2, loan, { excludeExtraneousValues: true });
  }
}
```
Business logic in `LoanService` is written and tested once. V1 and V2 are pure View differences — different DTOs, different field names, different nesting. Adding V3 means adding a new DTO class, not touching any business logic.

**Q25. "A post-mortem reveals that a critical business rule — 'loans above ₹5L require dual approval' — was implemented in three different places: the REST controller, a Kafka consumer, and a cron job. Each has slightly different logic, and the cron job had the bug that caused the incident. How does proper MVC prevent this class of bug?"**
A: This is a direct consequence of violating MVC's Model isolation — business logic placed in the Controller (and equivalent layers in other channels) instead of in the Model where it can be shared.

**Root cause:** the "dual approval" rule was not expressed in the domain model. It was a procedural check written independently by three developers in three different contexts.

**The MVC fix — express the rule in the Model:**
```ts
// Domain — the rule lives here, owned by the Loan entity or domain service
export class Loan {
  requiresDualApproval(): boolean {
    return this.amount > 500_000;
  }
}

// Domain service — enforces the invariant
@Injectable()
export class LoanApprovalPolicy {
  canApprove(loan: Loan, approvals: LoanApproval[]): ApprovalCheckResult {
    if (!loan.requiresDualApproval()) {
      return { canApprove: approvals.length >= 1, requiredApprovals: 1 };
    }
    // Large loan — dual approval required, and approvers must be distinct
    const distinctApprovers = new Set(approvals.map(a => a.approverId));
    return {
      canApprove: distinctApprovers.size >= 2,
      requiredApprovals: 2,
      currentApprovals: distinctApprovers.size,
    };
  }
}

// Application service — applies the policy; called by ALL channels
@Injectable()
export class LoanApprovalService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly approvalRepo: LoanApprovalRepository,
    private readonly policy: LoanApprovalPolicy,
  ) {}

  async approveLoan(loanId: string, approverId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);
    const existingApprovals = await this.approvalRepo.findByLoanId(loanId);

    const check = this.policy.canApprove(loan, existingApprovals);
    if (!check.canApprove) {
      throw new InsufficientApprovalsError(
        `Loan requires ${check.requiredApprovals} approvals; has ${check.currentApprovals}`
      );
    }

    await this.approvalRepo.save({ loanId, approverId, approvedAt: new Date() });
    if (this.policy.canApprove(loan, [...existingApprovals, { approverId }]).canApprove) {
      loan.approve(approverId);
      await this.loanRepo.save(loan);
    }
  }
}
```

Now the rule is expressed once in `LoanApprovalPolicy` (Model layer). The REST Controller calls `loanApprovalService.approveLoan()`. The Kafka consumer calls `loanApprovalService.approveLoan()`. The cron job calls `loanApprovalService.approveLoan()`. The bug can only exist in one place. Fixing it fixes all three channels simultaneously.

| Aspect                   | MVC (Classic)                             | MVP                                         | MVVM                                          | MVC+S (Modern Backend)                        |
|---                       |---                                        |---                                          |---                                            |---                                            |
| Components               | Model, View, Controller                   | Model, View, Presenter                      | Model, View, ViewModel                        | Controller, Service, Repository, Entity       |

**Tip for the interview:** At the 5 YOE level, MVC questions are almost never "explain the three components." They arrive as code review problems ("this controller does too much — how do you fix it?"), architectural decisions ("how do you share loan approval logic across REST, Kafka, and gRPC?"), and post-mortems ("how did the same bug end up in three places?"). The strongest answers treat MVC as a principle of *responsibility boundary enforcement* — not a folder structure. Know the two most common violations (Fat Controller and Anemic Model) cold, know how MVC+S maps to NestJS's actual component hierarchy, and be ready to explain why the multi-channel scenario (Q22) is the clearest proof of MVC's value: a properly isolated Model layer runs on REST, Kafka, gRPC, and CLI without modification. That's the answer that lands at 5 YOE.
