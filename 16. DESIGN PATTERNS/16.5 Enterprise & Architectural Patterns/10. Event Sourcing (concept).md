## 1. Core Concept

### What Is Event Sourcing?

Traditional systems store **current state** — a `loan_applications` row holds today's status, overwriting whatever it was yesterday.

Event Sourcing flips this: instead of storing current state, you store an **immutable, append-only log of every event** that caused the state to change. Current state is **derived** by replaying those events in order.

```
Traditional:  UPDATE loan_applications SET status = 'APPROVED' WHERE id = 42

Event Sourcing:
  APPEND → { type: 'LoanApplicationCreated',  aggregateId: 42, ... }
  APPEND → { type: 'KYCVerified',              aggregateId: 42, ... }
  APPEND → { type: 'CreditScoreChecked',       aggregateId: 42, ... }
  APPEND → { type: 'LoanApproved',             aggregateId: 42, ... }

Current state = replay all 4 events.
```

### Why It Matters

| Capability | Traditional DB | Event Sourcing |
|---|---|---|
| Audit trail | Needs extra audit table | Built-in — events ARE the audit trail |
| Temporal query ("state at T") | Hard / impossible | Replay up to timestamp T |
| Debugging production issues | Lost once overwritten | Full history always available |
| Business intelligence | Needs change data capture | Project events into any read model |
| Undo / compensate | Manual rollback logic | Replay without the bad event |

## 2. Event Store — The Heart of Event Sourcing

The **Event Store** is an append-only database/table. Two absolute rules:
1. **Never update** an existing event.
2. **Never delete** an existing event (use compensating events instead).

### Minimal Schema (PostgreSQL)

```sql
CREATE TABLE event_store (
  id            BIGSERIAL    PRIMARY KEY,
  aggregate_id  UUID         NOT NULL,
  aggregate_type VARCHAR(100) NOT NULL,          -- 'LoanApplication', 'NachMandate', etc.
  event_type    VARCHAR(150) NOT NULL,           -- 'LoanApproved', 'MandateRegistered'
  event_version INT          NOT NULL DEFAULT 1, -- schema version of this event type
  sequence_no   INT          NOT NULL,           -- per-aggregate ordering
  payload       JSONB        NOT NULL,
  metadata      JSONB        NOT NULL DEFAULT '{}', -- correlationId, causationId, userId
  occurred_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW(),

  UNIQUE (aggregate_id, sequence_no)             -- optimistic concurrency guard
);

CREATE INDEX idx_event_store_aggregate ON event_store (aggregate_id, sequence_no);
CREATE INDEX idx_event_store_type      ON event_store (event_type);
CREATE INDEX idx_event_store_occurred  ON event_store (occurred_at);
```

### TypeScript Event Interface


### Append to Event Store (TypeScript + pg)

```typescript
import { Pool } from 'pg';
import { v4 as uuid } from 'uuid';
import { DomainEvent } from './types';

export class EventStore {
  constructor(private readonly pool: Pool) {}

  async append<T>(
    events: DomainEvent<T>[],
    expectedSequence: number,  // optimistic concurrency
  ): Promise<void> {
    const client = await this.pool.connect();
    try {
      await client.query('BEGIN');

      for (const event of events) {
        const result = await client.query(
          `INSERT INTO event_store
             (aggregate_id, aggregate_type, event_type, event_version,
              sequence_no, payload, metadata, occurred_at)
           VALUES ($1, $2, $3, $4, $5, $6, $7, $8)`,
          [
            event.aggregateId,
            event.aggregateType,
            event.eventType,
            event.eventVersion,
            event.sequenceNo,
            JSON.stringify(event.payload),
            JSON.stringify(event.metadata),
            event.metadata.occurredAt,
          ],
        );
        // UNIQUE(aggregate_id, sequence_no) violation = concurrency conflict
      }

      await client.query('COMMIT');
    } catch (err: any) {
      await client.query('ROLLBACK');
      if (err.constraint === 'event_store_aggregate_id_sequence_no_key') {
        throw new ConcurrencyError(
          `Concurrency conflict on aggregate ${events[0].aggregateId}`,
        );
      }
      throw err;
    } finally {
      client.release();
    }
  }

  async load(aggregateId: string, fromSequence = 0): Promise<DomainEvent[]> {
    const { rows } = await this.pool.query(
      `SELECT * FROM event_store
        WHERE aggregate_id = $1
          AND sequence_no  > $2
        ORDER BY sequence_no ASC`,
      [aggregateId, fromSequence],
    );
    return rows.map(this.rowToEvent);
  }

  private rowToEvent(row: any): DomainEvent {
    return {
      eventId:       row.id.toString(),
      aggregateId:   row.aggregate_id,
      aggregateType: row.aggregate_type,
      eventType:     row.event_type,
      eventVersion:  row.event_version,
      sequenceNo:    row.sequence_no,
      payload:       row.payload,
      metadata:      row.metadata,
    };
  }
}

export class ConcurrencyError extends Error {}
```

## 3. Rebuilding State via Replay

The **Aggregate** is the domain object. It starts empty and applies events one by one to build its current state.

```typescript
// LoanApplication Aggregate
export class LoanApplication {
  id!:          string;
  status!:      'PENDING' | 'KYC_VERIFIED' | 'CREDIT_CHECKED' | 'APPROVED' | 'REJECTED' | 'DISBURSED';
  approvedAmount?: number;
  interestRate?:   number;
  sequenceNo:      number = 0;

  private pendingEvents: DomainEvent[] = [];

  // --- Command handlers (generate events) ---

  static create(id: string, applicantId: string, requestedAmount: number): LoanApplication {
    const app = new LoanApplication();
    app.apply({
      eventId:       uuid(),
      aggregateId:   id,
      aggregateType: 'LoanApplication',
      eventType:     'LoanApplicationCreated',
      eventVersion:  1,
      sequenceNo:    1,
      payload:       { applicantId, requestedAmount },
      metadata:      { correlationId: uuid(), causationId: '', occurredAt: new Date().toISOString() },
    });
    return app;
  }

  approve(approvedAmount: number, interestRate: number, tenureMonths: number, approvedBy: string): void {
    if (this.status !== 'CREDIT_CHECKED') {
      throw new Error(`Cannot approve loan in status ${this.status}`);
    }
    this.apply({
      eventId:       uuid(),
      aggregateId:   this.id,
      aggregateType: 'LoanApplication',
      eventType:     'LoanApproved',
      eventVersion:  1,
      sequenceNo:    this.sequenceNo + 1,
      payload:       { approvedAmount, interestRate, tenureMonths, approvedBy },
      metadata:      { correlationId: uuid(), causationId: '', occurredAt: new Date().toISOString() },
    });
  }

  // --- Event application (mutate state) ---

  private apply(event: DomainEvent): void {
    this.when(event);           // mutate state
    this.pendingEvents.push(event);
  }

  // Called both during replay and for new events
  when(event: DomainEvent): void {
    switch (event.eventType) {
      case 'LoanApplicationCreated':
        this.id     = event.aggregateId;
        this.status = 'PENDING';
        break;

      case 'KYCVerified':
        this.status = 'KYC_VERIFIED';
        break;

      case 'CreditScoreChecked':
        this.status = 'CREDIT_CHECKED';
        break;

      case 'LoanApproved':
        this.status          = 'APPROVED';
        this.approvedAmount  = event.payload.approvedAmount;
        this.interestRate    = event.payload.interestRate;
        break;

      case 'LoanRejected':
        this.status = 'REJECTED';
        break;

      default:
        // Unknown event — future version; ignore gracefully
        break;
    }
    this.sequenceNo = event.sequenceNo;
  }

  // --- Replay from event store ---

  static reconstitute(events: DomainEvent[]): LoanApplication {
    const app = new LoanApplication();
    for (const event of events) {
      app.when(event);
    }
    return app;
  }

  flushPendingEvents(): DomainEvent[] {
    const events = [...this.pendingEvents];
    this.pendingEvents = [];
    return events;
  }
}
```

### Repository Pattern

```typescript
export class LoanApplicationRepository {
  constructor(private readonly eventStore: EventStore) {}

  async findById(id: string): Promise<LoanApplication> {
    const events = await this.eventStore.load(id);
    if (events.length === 0) throw new Error(`LoanApplication ${id} not found`);
    return LoanApplication.reconstitute(events);
  }

  async save(aggregate: LoanApplication): Promise<void> {
    const pendingEvents = aggregate.flushPendingEvents();
    if (pendingEvents.length === 0) return;

    const expectedSequence = aggregate.sequenceNo - pendingEvents.length;
    await this.eventStore.append(pendingEvents, expectedSequence);
  }
}
```

## 4. Snapshots — Performance Optimization

Replaying 10,000 events every time you load an aggregate is expensive. **Snapshots** cache the aggregate state at a point in time.

```
Snapshot at event #500  →  load events #501 – #current  →  apply
```

### Snapshot Table

```sql
CREATE TABLE aggregate_snapshots (
  id             BIGSERIAL   PRIMARY KEY,
  aggregate_id   UUID        NOT NULL,
  aggregate_type VARCHAR(100) NOT NULL,
  sequence_no    INT         NOT NULL,           -- snapshot taken after this event
  state          JSONB       NOT NULL,           -- serialized aggregate state
  schema_version INT         NOT NULL DEFAULT 1,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (aggregate_id, sequence_no)
);
```

### Snapshot-Aware Repository

```typescript
const SNAPSHOT_THRESHOLD = 50; // take snapshot every 50 events

export class SnapshottingLoanRepository {
  constructor(
    private readonly eventStore: EventStore,
    private readonly snapshotStore: SnapshotStore,
  ) {}

  async findById(id: string): Promise<LoanApplication> {
    // 1. Try to load latest snapshot
    const snapshot = await this.snapshotStore.latest(id);

    let aggregate: LoanApplication;
    let fromSequence = 0;

    if (snapshot) {
      aggregate   = LoanApplication.fromSnapshot(snapshot.state);
      fromSequence = snapshot.sequenceNo;
    } else {
      aggregate = new LoanApplication();
    }

    // 2. Load only events AFTER the snapshot
    const events = await this.eventStore.load(id, fromSequence);
    for (const event of events) {
      aggregate.when(event);
    }

    return aggregate;
  }

  async save(aggregate: LoanApplication): Promise<void> {
    const pendingEvents = aggregate.flushPendingEvents();
    if (pendingEvents.length === 0) return;

    const expectedSequence = aggregate.sequenceNo - pendingEvents.length;
    await this.eventStore.append(pendingEvents, expectedSequence);

    // 3. Take snapshot if threshold crossed
    if (aggregate.sequenceNo % SNAPSHOT_THRESHOLD === 0) {
      await this.snapshotStore.save({
        aggregateId:   aggregate.id,
        aggregateType: 'LoanApplication',
        sequenceNo:    aggregate.sequenceNo,
        state:         aggregate.toSnapshot(),
        schemaVersion: 1,
      });
    }
  }
}
```

## 5. Event Sourcing + CQRS

Event Sourcing and CQRS are independent patterns but pair naturally:

```
Command Side (Write)                     Query Side (Read)
────────────────────                     ─────────────────
  Command Handler                          Projection Builder
       │                                        │
       ▼                                        │
  Aggregate (reconstitute + apply)         Reads event stream
       │                                        │
       ▼                                        ▼
  Event Store ──────────────────────►  Read Model (PostgreSQL view /
  (append-only)                         Redis cache / Elasticsearch)
```

- **Write side** cares only about correctness, invariants, and domain logic.
- **Read side** cares only about query performance. Can be rebuilt anytime from the event log.
- The event store is the **single source of truth**; read models are **disposable**.

## 6. Projections

A **Projection** listens to the event stream and builds a denormalized read model optimised for queries.

```typescript
// Projection: build a "loan_summary" table for the dashboard
export class LoanSummaryProjection {
  constructor(private readonly db: Pool) {}

  async handle(event: DomainEvent): Promise<void> {
    switch (event.eventType) {
      case 'LoanApplicationCreated':
        await this.db.query(
          `INSERT INTO loan_summary (id, applicant_id, status, requested_amount, created_at)
           VALUES ($1, $2, 'PENDING', $3, $4)`,
          [event.aggregateId, event.payload.applicantId,
           event.payload.requestedAmount, event.metadata.occurredAt],
        );
        break;

      case 'LoanApproved':
        await this.db.query(
          `UPDATE loan_summary
              SET status = 'APPROVED', approved_amount = $2, interest_rate = $3, updated_at = $4
            WHERE id = $1`,
          [event.aggregateId, event.payload.approvedAmount,
           event.payload.interestRate, event.metadata.occurredAt],
        );
        break;

      case 'LoanRejected':
        await this.db.query(
          `UPDATE loan_summary SET status = 'REJECTED', updated_at = $2 WHERE id = $1`,
          [event.aggregateId, event.metadata.occurredAt],
        );
        break;
    }
  }
}

// Projection runner — polls event store or consumes Kafka topic
export class ProjectionRunner {
  private checkpoint = 0; // last processed event id

  constructor(
    private readonly eventStore: EventStore,
    private readonly projection: LoanSummaryProjection,
  ) {}

  async run(): Promise<void> {
    // In production: use Kafka consumer with committed offsets as checkpoint
    const events = await this.eventStore.loadSince(this.checkpoint);
    for (const event of events) {
      await this.projection.handle(event);
      this.checkpoint = Number(event.eventId);
    }
  }
}
```

### Projection Rebuild

Because read models are derived, they can always be **rebuilt from scratch**:

```typescript
async function rebuildProjection(
  eventStore: EventStore,
  projection: LoanSummaryProjection,
  db: Pool,
): Promise<void> {
  // 1. Truncate the read model
  await db.query('TRUNCATE TABLE loan_summary');

  // 2. Replay ALL events from the beginning
  let offset = 0;
  const batchSize = 500;

  while (true) {
    const events = await eventStore.loadAll(offset, batchSize);
    if (events.length === 0) break;

    for (const event of events) {
      await projection.handle(event);
    }

    offset += events.length;
    console.log(`Replayed ${offset} events...`);
  }

  console.log('Projection rebuild complete');
}
```

## 7. Event Schema Design & Versioning

Events are **immutable** and stored forever — schema versioning is non-negotiable.

### Versioning Strategy: Upcasting

```typescript
// Old event (v1) — payload had flat fields
// { type: 'LoanApproved', version: 1, payload: { amount: 50000, rate: 12 } }

// New event (v2) — richer payload
// { type: 'LoanApproved', version: 2, payload: { approvedAmount: 50000, interestRate: 12, tenureMonths: 24 } }

// Upcaster: transform v1 → v2 on read
export class LoanApprovedUpcaster {
  upcast(event: DomainEvent): DomainEvent {
    if (event.eventType !== 'LoanApproved') return event;

    if (event.eventVersion === 1) {
      return {
        ...event,
        eventVersion: 2,
        payload: {
          approvedAmount: event.payload.amount,        // renamed field
          interestRate:   event.payload.rate,          // renamed field
          tenureMonths:   24,                          // default for old events
        },
      };
    }

    return event; // already v2
  }
}

// Upcaster registry — applied automatically when loading events
export class UpcasterChain {
  private upcasters: Map<string, ((e: DomainEvent) => DomainEvent)[]> = new Map();

  register(eventType: string, upcaster: (e: DomainEvent) => DomainEvent): void {
    const chain = this.upcasters.get(eventType) ?? [];
    chain.push(upcaster);
    this.upcasters.set(eventType, chain);
  }

  upcast(event: DomainEvent): DomainEvent {
    const chain = this.upcasters.get(event.eventType) ?? [];
    return chain.reduce((e, fn) => fn(e), event);
  }
}
```

### Event Naming Conventions

```
✅ Past tense, business language:
   LoanApplicationCreated
   CreditScoreChecked
   MandateRegistrationSucceeded
   EMIDeductionFailed

❌ Avoid:
   LoanUpdated          (too generic — what changed?)
   MandateEvent         (not specific)
   UpdateLoan           (command, not event)
```

## 8. Event Sourcing in a Microservices Architecture

```
┌────────────────────────────────────────────────────────────────┐
│                    Loan Service                                  │
│  Commands → Aggregate → Event Store (PostgreSQL)                │
│                             │                                    │
│                     Outbox Publisher                             │
│                             │                                    │
└─────────────────────────────┼────────────────────────────────── ┘
                              ▼
                       Kafka Topic: loan-events
                       ┌────────┬────────────┐
                       │        │            │
                 KYC Service  BRE Service  Notification
                 (consumer)   (consumer)     Service
                       │        │            │
                 Updates own  Runs rules   Sends SMS
                 read model   & fires      / Email
                              events
```

- Each service maintains its **own event store** for aggregates it owns.
- Cross-service integration uses **domain events published to Kafka** — not shared databases.
- **Transactional Outbox Pattern** ensures events are published reliably alongside the event store append.

### Outbox Pattern Integration

```typescript
// Append event + outbox record in one transaction
async function appendWithOutbox(
  client: PoolClient,
  event: DomainEvent,
): Promise<void> {
  await client.query(
    `INSERT INTO event_store (...) VALUES (...)`,
    [/* event fields */],
  );

  await client.query(
    `INSERT INTO outbox (event_type, payload, status, created_at)
     VALUES ($1, $2, 'PENDING', NOW())`,
    [event.eventType, JSON.stringify(event)],
  );
}

// Outbox relay (separate process / cron) → Kafka
async function relayOutbox(kafka: Producer, db: Pool): Promise<void> {
  const { rows } = await db.query(
    `SELECT * FROM outbox WHERE status = 'PENDING' ORDER BY created_at LIMIT 100`,
  );

  for (const row of rows) {
    await kafka.send({
      topic:    'loan-events',
      messages: [{ key: row.payload.aggregateId, value: JSON.stringify(row.payload) }],
    });

    await db.query(
      `UPDATE outbox SET status = 'PUBLISHED', published_at = NOW() WHERE id = $1`,
      [row.id],
    );
  }
}
```

## 9. Event Sourcing with Kafka

Kafka can serve as the **event store** itself for high-throughput use cases, with infinite retention.

```typescript
import { Kafka } from 'kafkajs';

const kafka = new Kafka({ clientId: 'loan-service', brokers: ['kafka:9092'] });
const producer = kafka.producer({ idempotent: true }); // exactly-once semantics

// Publish domain event to Kafka
async function publishEvent(event: DomainEvent): Promise<void> {
  await producer.send({
    topic: `${event.aggregateType.toLowerCase()}-events`,
    messages: [
      {
        key:     event.aggregateId,      // partition by aggregate = ordered per aggregate
        value:   JSON.stringify(event),
        headers: {
          'event-type':    event.eventType,
          'event-version': String(event.eventVersion),
          'correlation-id': event.metadata.correlationId,
        },
      },
    ],
  });
}

// Consumer-based projection builder
const consumer = kafka.consumer({ groupId: 'loan-summary-projection' });

async function startProjectionConsumer(projection: LoanSummaryProjection): Promise<void> {
  await consumer.subscribe({ topic: 'loanapplication-events', fromBeginning: true });

  await consumer.run({
    eachMessage: async ({ message }) => {
      const event: DomainEvent = JSON.parse(message.value!.toString());
      await projection.handle(event);
      // Kafka offset commit = checkpoint; rebalance triggers replay from last committed offset
    },
  });
}
```

### Kafka vs PostgreSQL Event Store Trade-offs

| Concern | PostgreSQL Event Store | Kafka as Event Store |
|---|---|---|
| Query by aggregate | Fast (indexed) | Must scan topic or maintain index |
| Retention | Forever (disk-bound) | Configurable log retention |
| Throughput | ~10K events/s | Millions/s |
| Aggregate reconstitution | Native (query by aggregate_id) | Needs KTable (Kafka Streams) |
| Best for | Domain-rich aggregates, DDD | High-volume streaming, analytics |

**Recommendation:** Use **PostgreSQL as the primary event store** + **Kafka as the integration bus**. The Outbox pattern bridges them.

## 10. Pitfalls & Anti-Patterns

### ❌ Mutating or Deleting Events

```typescript
// NEVER do this — events are immutable
await db.query('UPDATE event_store SET payload = $1 WHERE id = $2', [...]);
await db.query('DELETE FROM event_store WHERE aggregate_id = $1', [...]);

// ✅ Instead — append a compensating event
const compensatingEvent: DomainEvent = {
  eventType: 'LoanApprovalRevoked',
  payload:   { reason: 'Data entry error', originalEventId: '...' },
  // ...
};
await eventStore.append([compensatingEvent], currentSequence);
```

### ❌ Storing Commands Instead of Events

```typescript
// ❌ Wrong — this is a command, not an event
{ type: 'ApproveLoan', payload: { amount: 50000 } }

// ✅ Correct — past tense, fact that happened
{ type: 'LoanApproved', payload: { approvedAmount: 50000 } }
```

### ❌ Coupling Events to Internal Implementation

```typescript
// ❌ Bad — leaks internal model details
{ type: 'DatabaseRowUpdated', table: 'loans', column: 'status', value: 'approved' }

// ✅ Good — business language
{ type: 'LoanApproved', payload: { approvedAmount, interestRate } }
```

### ❌ GDPR / Right-to-Erasure Problem

Events are immutable — you cannot delete PII from the event log. Solutions:

```typescript
// Crypto-shredding approach:
// 1. Encrypt sensitive PII fields with a per-user encryption key
// 2. Store the key in a separate "key store"
// 3. On erasure request: delete the key → ciphertext becomes unreadable

interface EncryptedEvent {
  encryptedPayload: string;  // AES-256-GCM encrypted blob
  keyId:            string;  // reference to per-user key in key store
  iv:               string;  // initialization vector
}

// When user requests deletion: delete key from key store.
// Old events are now permanently unreadable without breaking immutability.
```

### ❌ Using Event Sourcing for Everything

Event Sourcing adds significant complexity. Use it when:

- ✅ Audit trail is a hard requirement (fintech, healthcare, legal)
- ✅ Temporal queries needed ("what was the loan status on 1 Jan?")
- ✅ Complex domain logic with many state transitions
- ✅ Need to build multiple different read models from the same data

Avoid for:
- ❌ Simple CRUD (user profile, config tables)
- ❌ High-write-low-read with no history requirement

## 11. Fintech Domain Application — NACH / Lending

### NACH Mandate Lifecycle via Event Sourcing

```typescript
// NACH Mandate Aggregate events
type NachMandateEventType =
  | 'MandateRegistrationInitiated'
  | 'MandateRegistrationSubmittedToBank'
  | 'MandateRegistrationSucceeded'
  | 'MandateRegistrationFailed'
  | 'MandateDeactivationRequested'
  | 'MandateDeactivated';

class NachMandate {
  id!:     string;
  status!: 'INITIATED' | 'PENDING_BANK' | 'ACTIVE' | 'FAILED' | 'DEACTIVATED';
  umrn?:   string;   // Unique Mandate Reference Number from NPCI
  sequenceNo = 0;

  when(event: DomainEvent): void {
    switch (event.eventType) {
      case 'MandateRegistrationInitiated':
        this.id     = event.aggregateId;
        this.status = 'INITIATED';
        break;
      case 'MandateRegistrationSubmittedToBank':
        this.status = 'PENDING_BANK';
        break;
      case 'MandateRegistrationSucceeded':
        this.status = 'ACTIVE';
        this.umrn   = event.payload.umrn;
        break;
      case 'MandateRegistrationFailed':
        this.status = 'FAILED';
        break;
      case 'MandateDeactivated':
        this.status = 'DEACTIVATED';
        break;
    }
    this.sequenceNo = event.sequenceNo;
  }
}
```

### EMI Deduction Audit Trail

```
Events for EMI Deduction (aggregateId: emi-deduction-2024-03-01-loan-42):
```

## 12. Interview Q&A

### Q1: What is the difference between Event Sourcing and traditional state storage?

**A:** Traditional systems store the **current state** of an entity — past states are lost once overwritten. Event Sourcing stores an **immutable log of all events** that led to the current state. Current state is derived by replaying those events. This gives you a built-in audit trail, temporal queries ("what was the state at time T?"), and the ability to build new read models by replaying history. The trade-off is increased complexity: you need to manage event schemas, versioning, and projection rebuilds.

---

### Q2: How do you handle optimistic concurrency in Event Sourcing?

**A:** When appending events, you pass the **expected sequence number** (the last sequence_no you saw for that aggregate). The event store has a `UNIQUE(aggregate_id, sequence_no)` constraint. If two processes try to append event #5 simultaneously, the second one gets a unique constraint violation, which you translate into a `ConcurrencyError`. The caller retries by reloading the aggregate (which now includes the other process's event) and re-executing the command. This is equivalent to an optimistic lock without holding a database lock.

---

### Q3: How do you prevent an Event Store from growing indefinitely?

**A:** Three strategies:
1. **Snapshots** — Periodically serialize the aggregate state after N events. On load, restore from snapshot + replay only events after the snapshot. This keeps replay fast without deleting events.
2. **Archival** — Move events older than X months to cold storage (S3 + Parquet). Recent events stay in hot PostgreSQL for fast access.
3. **Event expiry with projection safety net** — For events that are no longer needed for reconstitution (because projections have processed them), mark as archived. Note: you still cannot delete them if you may need to rebuild projections.

---

### Q4: What is the GDPR right-to-erasure problem with Event Sourcing, and how do you solve it?

**A:** GDPR requires the ability to delete a user's personal data on request, but Event Sourcing events are immutable. You can't just `DELETE FROM event_store`. The solution is **crypto-shredding**: encrypt PII in event payloads with a per-user encryption key stored in a separate Key Management Service (KMS/Vault). When a user requests erasure, you delete their encryption key. All encrypted event payloads for that user become permanently unreadable without deleting the events themselves, preserving event log immutability.

---

### Q5: How do you version event schemas when events are immutable?

**A:** Using **upcasters** — functions that transform old event versions into the latest version on read. Each event carries a `version` field. When you load events from the store, an upcaster chain checks each event's version and transforms it up to the current version before passing it to the aggregate's `when()` method. Old events stay unchanged on disk; the transformation happens in memory. For breaking changes, you increment the version number and write an upcaster for the migration.

---

### Q6: What's the difference between an Event and a Command in Event Sourcing?

**A:** A **Command** is an *instruction* to do something — it can be rejected. A **Command** is in the imperative ("ApproveLoan"). An **Event** is a *fact* that already happened — it cannot be rejected. Events are in the past tense ("LoanApproved"). Commands go to the aggregate's command handler, which validates business rules and either rejects the command or creates events. Events are then applied to update the aggregate's state and persisted to the event store.

---

### Q7: How do you rebuild a projection that has a bug?

**A:** Since the event store is the source of truth, projections are disposable. To rebuild:
1. Drop/truncate the broken read model table.
2. Reset the consumer's checkpoint/offset to the beginning of the event stream.
3. Let the fixed projection handler replay all events from the beginning.
4. Once caught up, resume normal operation.

With Kafka, this means resetting the consumer group offset to the earliest position. With a database-backed event store, you replay from `sequence_no = 0`. During the rebuild, you can serve reads from an old snapshot or show a "data refreshing" message.

---

### Q8: Can you use Event Sourcing with Kafka as the event store?

**A:** Yes, with caveats. Kafka works well as the **integration bus** but has limitations as the primary event store:
- **Query by aggregate**: Kafka topics are log-structured, not indexed by aggregate ID. To reconstitute an aggregate, you need a Kafka Streams KTable (compacted topic) or a separate projection that maps aggregate IDs to current state.
- **Retention**: Kafka log retention is configurable but typically not "forever" by default.
- **Best practice**: Use **PostgreSQL as the event store** for domain aggregates (easy querying, infinite retention) and **Kafka as the integration bus** to distribute events to other services. Use the Outbox Pattern to bridge them atomically.

---

### Q9: How does Event Sourcing complement the Saga pattern?

**A:** Sagas coordinate multi-step distributed transactions using events. Event Sourcing makes this natural:
- Each step of a saga publishes domain events to Kafka.
- The Saga Orchestrator or Choreography handler reacts to those events and issues the next command.
- If a compensating transaction is needed, it appends a compensating event.
- The full audit trail of the saga (which steps succeeded, which failed, what compensation was applied) is automatically captured in the event logs of the participating services.

---

### Q10: What are the observability implications of Event Sourcing?

**A:** Event Sourcing improves observability significantly:
- **Correlation ID**: Pass a correlation ID in every event's metadata → trace a business transaction across services.
- **Causation ID**: Each event stores the ID of the event that caused it → build a complete causal graph.
- **Replay for debugging**: Reproduce any production bug by replaying the exact events on a staging environment.
- **Metrics from events**: Derive business metrics directly from the event stream (approval rates, bounce rates) without needing separate analytics pipelines.
