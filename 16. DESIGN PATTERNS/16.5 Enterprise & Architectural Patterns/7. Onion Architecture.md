# Enterprise & Architectural Patterns: Onion Architecture — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Onion Architecture?**
A: Onion Architecture is a software architectural pattern introduced by Jeffrey Palermo in 2008 that organises a codebase into concentric layers — like the rings of an onion — where the innermost layers represent the core domain and the outermost layers represent infrastructure and delivery mechanisms. The defining rule is the **Dependency Rule**: source code dependencies always point *inward* — outer layers know about inner layers, but inner layers know nothing about outer layers. The domain model at the centre is isolated from all infrastructure concerns: databases, HTTP frameworks, message queues, third-party APIs, and UI frameworks are all in the outer rings and can be changed without touching the core. The result is a system where the business rules can be understood, tested, and evolved independently of the technology choices that surround them.

**Q2. What problem does Onion Architecture solve, and what breaks without it?**
A: It solves the *infrastructure coupling* problem — the tendency of business logic to become entangled with the technology stack over time. Without an architectural discipline that enforces inward-only dependencies, this happens naturally:
- A service method directly instantiates a `TypeOrmRepository` or `PrismaClient` — now every test of that business rule needs a live database.
- An entity has `@Column()` decorators — now the domain model is coupled to the ORM; switching ORMs requires editing domain classes.
- A business rule calls `sendgrid.send()` — now testing the rule requires either a live SendGrid connection or fragile monkey-patching.
- Domain logic calls `new Date()` or `Math.random()` directly — now temporal or randomness-dependent rules are non-deterministic in tests.

When infrastructure leaks into the domain, the codebase develops what Martin Fowler calls an "Anemic Domain Model" — domain objects are data bags with no behaviour, because the behaviour is scattered through services that are themselves coupled to infrastructure. Onion Architecture prevents this by making infrastructure dependencies physically impossible at the domain layer: the domain has no `import` statements that reach outward.

**Q3. What are the layers of Onion Architecture and what does each contain?**
A: From innermost to outermost:

**1. Domain Model (Core — innermost ring):**
- Pure domain entities, value objects, aggregates, and domain events.
- Encapsulates business invariants and rules as methods on the objects themselves.
- Has zero dependencies on anything — no framework imports, no ORM annotations, no external library calls.
- Examples: `Loan`, `LoanApplication`, `MoneyAmount`, `PanNumber`, `LoanStatus`, `LoanApprovedEvent`.

**2. Domain Services:**
- Domain logic that spans multiple entities or aggregates and doesn't naturally belong on one of them.
- Still pure domain — no infrastructure. Operates only on domain objects.
- Examples: `LoanEligibilityService` (computes eligibility across applicant, product, and credit score), `InterestCalculationService`.

**3. Application Services (Use Cases):**
- Orchestrates the domain to fulfil a specific use case or user story.
- Coordinates domain entities, domain services, and infrastructure interfaces (repositories, external service ports).
- Has no knowledge of *how* the infrastructure works — only of the *interface* it provides.
- Examples: `ApplyForLoanUseCase`, `RepayEmiUseCase`, `InitiateKycUseCase`.

**4. Infrastructure (outermost ring):**
- Concrete implementations of the interfaces defined by the application layer.
- Contains all framework-specific code: TypeORM repositories, NestJS modules, HTTP controllers, Kafka consumers, Redis adapters, SendGrid clients, Prisma clients.
- Depends on the inner layers; inner layers never depend on this layer.
- Examples: `TypeOrmLoanRepository`, `RazorpayPaymentGateway`, `KafkaLoanEventPublisher`, `NestJsLoanController`.

**Q4. What is the Dependency Rule, and how is it enforced in a TypeScript codebase?**
A: The Dependency Rule states: *a source code module in an inner layer must not import anything from an outer layer.* It is the single invariant that defines Onion Architecture. In TypeScript, it is enforced through:

**1. Interfaces defined in the inner layer, implemented in the outer layer:**
```typescript
// Domain layer — defines what it needs, not how it gets it
// src/domain/repositories/loan-repository.interface.ts
export interface ILoanRepository {
  findById(loanId: LoanId): Promise<Loan | null>;
  save(loan: Loan): Promise<void>;
  findActiveByCustomer(customerId: CustomerId): Promise<Loan[]>;
}

// Infrastructure layer — implements the interface
// src/infrastructure/repositories/typeorm-loan.repository.ts
import { ILoanRepository } from "../../domain/repositories/loan-repository.interface";
// ✅ Outer imports inner — allowed
// ❌ Inner never imports from src/infrastructure — enforced by tooling
```

**2. Dependency Inversion Principle (DIP) via constructor injection:**
```typescript
// Application layer — depends on interface, not concrete class
class ApplyForLoanUseCase {
  constructor(
    private readonly loanRepository:   ILoanRepository,    // interface from domain
    private readonly creditBureau:     ICreditBureauPort,  // interface from domain
    private readonly eventPublisher:   IEventPublisher,    // interface from domain
  ) {}
  // No import of TypeOrmLoanRepository, CibilService, or KafkaPublisher anywhere here
}
```

**3. Lint rules and architectural fitness functions:**
```typescript
// Using eslint-plugin-import with path rules, or dependency-cruiser:
// .dependency-cruiser.js — forbid domain from importing infrastructure
{
  forbidden: [{
    name: "no-domain-to-infrastructure",
    from: { path: "src/domain" },
    to:   { path: "src/infrastructure" },
  }, {
    name: "no-application-to-infrastructure",
    from: { path: "src/application" },
    to:   { path: "src/infrastructure" },
  }],
}
```

**4. Module boundary enforcement in NestJS:**
```typescript
// Each layer is a NestJS module; exports control what crosses boundaries
@Module({
  imports:   [],                            // Domain module imports nothing
  providers: [LoanEligibilityService],
  exports:   [LoanEligibilityService],      // Only domain services exported
})
export class DomainModule {}
```

**Q5. How does Onion Architecture relate to Clean Architecture and Hexagonal Architecture (Ports and Adapters)?**
A: All three are expressions of the same core idea — separate the domain from infrastructure via inward-pointing dependencies and interface inversion — but they use different metaphors and emphasise different aspects:

| Dimension              | Hexagonal (Ports & Adapters)                              | Onion Architecture                                         | Clean Architecture                                             |
|------------------------|-----------------------------------------------------------|------------------------------------------------------------|----------------------------------------------------------------|
| Metaphor               | A hexagon with ports on the edges                         | Concentric rings like an onion                             | Concentric circles with explicit layer names                   |
| Primary concern        | Driving vs. driven actors; port types                     | Domain purity; layer count and naming                      | Use case centricity; the flow of control                       |
| Layer count            | 2 conceptual: application core + adapters                 | 3–4: domain model, domain services, application, infra     | 4: entities, use cases, interface adapters, frameworks & drivers |
| Port concept           | Explicit: driving ports (in), driven ports (out)          | Implicit: interfaces in domain/application layer           | Implicit: part of "interface adapters" ring                    |
| Use case layer         | Part of the application core                              | Separate "application services" ring                       | Explicit "use cases" ring — the most important layer           |
| Original author        | Alistair Cockburn (2005)                                  | Jeffrey Palermo (2008)                                     | Robert C. Martin / Uncle Bob (2012)                            |
| Common in              | Domain-driven design, microservices                       | .NET, Java enterprise, NestJS backends                     | Mobile, embedded, any language                                 |

In practice, a NestJS backend built with "Onion Architecture" will look almost identical to one built with "Clean Architecture" or "Hexagonal Architecture." The naming convention and the precise number of rings differ; the Dependency Rule is the same in all three. At 5 YOE, being able to articulate the shared principle (DIP + interface boundaries + inward dependency) is more important than memorising which ring name belongs to which author.

**Q7. Show a rich domain entity that encapsulates business rules with no infrastructure dependencies.**
A:

```typescript
// src/domain/entities/loan.entity.ts

import { LoanId }          from "../value-objects/loan-id.value-object";
import { CustomerId }      from "../value-objects/customer-id.value-object";
import { Money }           from "../value-objects/money.value-object";
import { InterestRate }    from "../value-objects/interest-rate.value-object";
import { LoanApprovedEvent }  from "../events/loan-approved.event";
import { EmiRepaidEvent }     from "../events/emi-repaid.event";
import { LoanPreclosedEvent } from "../events/loan-preclosed.event";
import { InsufficientFundsException } from "../exceptions/insufficient-funds.exception";
import { LoanAlreadyClosedException } from "../exceptions/loan-already-closed.exception";

export type LoanStatus = "PENDING" | "APPROVED" | "DISBURSED" | "ACTIVE" | "CLOSED" | "PRECLOSED" | "REJECTED";

export class Loan {
  private readonly _domainEvents: object[] = [];

  private constructor(
    private readonly _id:             LoanId,
    private readonly _customerId:     CustomerId,
    private          _status:         LoanStatus,
    private readonly _principal:      Money,
    private readonly _interestRate:   InterestRate,
    private readonly _tenureMonths:   number,
    private          _emisPaid:       number,
    private          _outstandingPrincipal: Money,
    private readonly _createdAt:      Date,
    private          _updatedAt:      Date,
  ) {}

  // ── Factory method — enforces creation invariants ─────────────────────────

  static create(params: {
    id:            LoanId;
    customerId:    CustomerId;
    principal:     Money;
    interestRate:  InterestRate;
    tenureMonths:  number;
  }): Loan {
    if (params.tenureMonths < 3 || params.tenureMonths > 360) {
      throw new Error("Tenure must be between 3 and 360 months");
    }
    if (params.principal.isLessThan(Money.ofRupees(10_000))) {
      throw new Error("Minimum loan amount is ₹10,000");
    }

    const now = new Date();
    const loan = new Loan(
      params.id, params.customerId, "PENDING",
      params.principal, params.interestRate, params.tenureMonths,
      0, params.principal, now, now,
    );

    return loan;
  }

  // ── Reconstitution — rebuild from persistence without re-running invariants

  static reconstitute(params: {
    id:                   LoanId;
    customerId:           CustomerId;
    status:               LoanStatus;
    principal:            Money;
    interestRate:         InterestRate;
    tenureMonths:         number;
    emisPaid:             number;
    outstandingPrincipal: Money;
    createdAt:            Date;
    updatedAt:            Date;
  }): Loan {
    return new Loan(
      params.id, params.customerId, params.status,
      params.principal, params.interestRate, params.tenureMonths,
      params.emisPaid, params.outstandingPrincipal,
      params.createdAt, params.updatedAt,
    );
  }

  // ── Business methods — all business rules live here ───────────────────────

  approve(): void {
    if (this._status !== "PENDING") {
      throw new Error(`Cannot approve a loan in status ${this._status}`);
    }
    this._status    = "APPROVED";
    this._updatedAt = new Date();
    this._domainEvents.push(new LoanApprovedEvent(this._id, this._customerId, this._principal));
  }

  disburse(): void {
    if (this._status !== "APPROVED") {
      throw new Error(`Cannot disburse a loan in status ${this._status}`);
    }
    this._status    = "DISBURSED";
    this._updatedAt = new Date();
  }

  activate(): void {
    if (this._status !== "DISBURSED") {
      throw new Error(`Cannot activate a loan in status ${this._status}`);
    }
    this._status    = "ACTIVE";
    this._updatedAt = new Date();
  }

  repayEmi(emiAmount: Money): void {
    if (this._status !== "ACTIVE") {
      throw new LoanAlreadyClosedException(this._id);
    }
    if (emiAmount.isLessThan(this.calculateCurrentEmi())) {
      throw new InsufficientFundsException(
        `EMI amount ${emiAmount.display()} is less than required ${this.calculateCurrentEmi().display()}`
      );
    }

    // Principal component of this EMI
    const interestComponent  = this._outstandingPrincipal.multiply(this._interestRate.monthly());
    const principalComponent = emiAmount.subtract(interestComponent);

    this._outstandingPrincipal = this._outstandingPrincipal.subtract(principalComponent);
    this._emisPaid++;
    this._updatedAt = new Date();

    this._domainEvents.push(new EmiRepaidEvent(
      this._id, this._customerId, emiAmount, this._outstandingPrincipal, this._emisPaid,
    ));

    // Auto-close when fully repaid
    if (this._outstandingPrincipal.isZero() || this._emisPaid >= this._tenureMonths) {
      this._status = "CLOSED";
    }
  }

  preclose(payoffAmount: Money): void {
    if (this._status !== "ACTIVE") {
      throw new LoanAlreadyClosedException(this._id);
    }

    // Payoff must cover outstanding + prepayment penalty (5%)
    const penaltyAmount  = this._outstandingPrincipal.multiply(0.05);
    const minimumPayoff  = this._outstandingPrincipal.add(penaltyAmount);

    if (payoffAmount.isLessThan(minimumPayoff)) {
      throw new Error(
        `Payoff amount ${payoffAmount.display()} insufficient. Minimum: ${minimumPayoff.display()}`
      );
    }

    this._outstandingPrincipal = Money.zero(this._principal.currency);
    this._status    = "PRECLOSED";
    this._updatedAt = new Date();

    this._domainEvents.push(new LoanPreclosedEvent(this._id, this._customerId, payoffAmount));
  }

  // ── Pure computation — no side effects ────────────────────────────────────

  calculateCurrentEmi(): Money {
    const r          = this._interestRate.monthly();
    const n          = this._tenureMonths;
    const p          = this._principal.amountInPaise;
    const emiInPaise = r === 0
      ? p / n
      : (p * r * Math.pow(1 + r, n)) / (Math.pow(1 + r, n) - 1);
    return Money.ofPaise(Math.round(emiInPaise), this._principal.currency);
  }

  isOverdue(asOf: Date): boolean {
    // Domain rule: overdue if ACTIVE and last EMI was more than 30 days ago
    // Date is injected — no `new Date()` inside the entity
    return this._status === "ACTIVE" && this._emisPaid < this.expectedEmisByDate(asOf);
  }

  private expectedEmisByDate(asOf: Date): number {
    const monthsActive = (asOf.getTime() - this._createdAt.getTime()) / (1000 * 60 * 60 * 24 * 30);
    return Math.floor(monthsActive);
  }

  // ── Accessors ──────────────────────────────────────────────────────────────

  get id():                   LoanId   { return this._id; }
  get customerId():            CustomerId { return this._customerId; }
  get status():               LoanStatus { return this._status; }
  get principal():            Money    { return this._principal; }
  get outstandingPrincipal(): Money    { return this._outstandingPrincipal; }
  get emisPaid():             number   { return this._emisPaid; }
  get tenureMonths():         number   { return this._tenureMonths; }
  get interestRate():         InterestRate { return this._interestRate; }

  // ── Domain events ──────────────────────────────────────────────────────────

  pullDomainEvents(): object[] {
    const events = [...this._domainEvents];
    this._domainEvents.length = 0;   // clear after pull
    return events;
  }
}
```

**Q8. Show a value object that enforces its own invariants.**
A:

```typescript
// src/domain/value-objects/money.value-object.ts

export class Money {
  private constructor(
    readonly amountInPaise: number,
    readonly currency:      "INR" | "USD",
  ) {
    if (!Number.isInteger(amountInPaise)) {
      throw new Error(`Money amount must be an integer (paise), got: ${amountInPaise}`);
    }
    if (amountInPaise < 0) {
      throw new Error(`Money amount cannot be negative: ${amountInPaise}`);
    }
    Object.freeze(this);
  }

  static ofPaise(paise: number, currency: "INR" | "USD" = "INR"): Money {
    return new Money(paise, currency);
  }

  static ofRupees(rupees: number, currency: "INR" | "USD" = "INR"): Money {
    return new Money(Math.round(rupees * 100), currency);
  }

  static zero(currency: "INR" | "USD" = "INR"): Money {
    return new Money(0, currency);
  }

  add(other: Money): Money {
    this.assertSameCurrency(other);
    return new Money(this.amountInPaise + other.amountInPaise, this.currency);
  }

  subtract(other: Money): Money {
    this.assertSameCurrency(other);
    if (other.amountInPaise > this.amountInPaise) {
      throw new Error(`Cannot subtract ${other.display()} from ${this.display()}`);
    }
    return new Money(this.amountInPaise - other.amountInPaise, this.currency);
  }

  multiply(factor: number): Money {
    return new Money(Math.round(this.amountInPaise * factor), this.currency);
  }

  isLessThan(other: Money): boolean {
    this.assertSameCurrency(other);
    return this.amountInPaise < other.amountInPaise;
  }

  isGreaterThan(other: Money): boolean {
    this.assertSameCurrency(other);
    return this.amountInPaise > other.amountInPaise;
  }

  isZero(): boolean { return this.amountInPaise === 0; }

  equals(other: Money): boolean {
    return this.amountInPaise === other.amountInPaise && this.currency === other.currency;
  }

  display(): string {
    const symbol = this.currency === "INR" ? "₹" : "$";
    return `${symbol}${(this.amountInPaise / 100).toLocaleString("en-IN")}`;
  }

  private assertSameCurrency(other: Money): void {
    if (this.currency !== other.currency) {
      throw new Error(`Currency mismatch: ${this.currency} vs ${other.currency}`);
    }
  }
}
```

**Q9. Show a complete application use case that orchestrates the domain without touching infrastructure directly.**
A:

```typescript
// src/application/use-cases/apply-for-loan/apply-for-loan.use-case.ts

import { Loan }               from "../../../domain/entities/loan.entity";
import { LoanId }             from "../../../domain/value-objects/loan-id.value-object";
import { CustomerId }         from "../../../domain/value-objects/customer-id.value-object";
import { Money }              from "../../../domain/value-objects/money.value-object";
import { InterestRate }       from "../../../domain/value-objects/interest-rate.value-object";
import { ILoanRepository }    from "../../../domain/repositories/loan-repository.interface";
import { ICreditBureauPort }  from "../../../domain/ports/credit-bureau.port";
import { IEventPublisher }    from "../../../domain/ports/event-publisher.port";
import { LoanEligibilityService } from "../../../domain/services/loan-eligibility.service";
import { ApplyForLoanCommand }    from "./apply-for-loan.command";
import { ApplyForLoanResult }     from "./apply-for-loan.result";
import { InsufficientEligibilityException } from "../../../domain/exceptions/insufficient-eligibility.exception";

export class ApplyForLoanUseCase {
  constructor(
    // All dependencies are interfaces — no concrete infrastructure class imported
    private readonly loanRepository:      ILoanRepository,
    private readonly creditBureau:        ICreditBureauPort,
    private readonly eventPublisher:      IEventPublisher,
    private readonly eligibilityService:  LoanEligibilityService,
  ) {}

  async execute(command: ApplyForLoanCommand): Promise<ApplyForLoanResult> {
    const customerId = CustomerId.of(command.customerId);

    // 1. Guard: check for existing active loans (domain rule via repository interface)
    const activeLoans = await this.loanRepository.findActiveByCustomer(customerId);
    if (activeLoans.length >= 2) {
      throw new Error("Customer already has 2 active loans — cannot apply for more");
    }

    // 2. Fetch credit report via port (no knowledge of CIBIL vs Experian vs CRIF)
    const creditReport = await this.creditBureau.pullReport(
      command.panNumber,
      command.bureauConsent,
    );

    // 3. Domain service computes eligibility (pure domain logic)
    const requested = Money.ofRupees(command.requestedAmountInRupees);
    const eligibility = this.eligibilityService.compute({
      creditScore:     creditReport.score,
      monthlyIncome:   Money.ofRupees(command.monthlyIncomeInRupees),
      existingEmiLoad: Money.ofRupees(command.existingEmiLoadInRupees),
      requestedAmount: requested,
      tenureMonths:    command.tenureMonths,
    });

    if (!eligibility.isEligible) {
      throw new InsufficientEligibilityException(eligibility.rejectionReason!);
    }

    // 4. Create domain entity — business rules enforced in the entity
    const loan = Loan.create({
      id:           LoanId.generate(),
      customerId,
      principal:    eligibility.sanctionedAmount,
      interestRate: InterestRate.ofAnnual(eligibility.offeredRate),
      tenureMonths: command.tenureMonths,
    });

    // 5. Persist via repository interface
    await this.loanRepository.save(loan);

    // 6. Publish domain events via publisher interface
    const events = loan.pullDomainEvents();
    await Promise.all(events.map(event => this.eventPublisher.publish(event)));

    // 7. Return application-layer result DTO (not domain entity — no leaking internals)
    return {
      loanId:               loan.id.value,
      sanctionedAmountText: loan.principal.display(),
      emiText:              loan.calculateCurrentEmi().display(),
      interestRateText:     `${eligibility.offeredRate * 100}% p.a.`,
      tenureMonths:         command.tenureMonths,
      status:               loan.status,
    };
  }
}
```

```typescript
// src/infrastructure/persistence/typeorm/repositories/typeorm-loan.repository.ts

import { Injectable }         from "@nestjs/common";
import { InjectRepository }   from "@nestjs/typeorm";
import { Repository }         from "typeorm";
import { ILoanRepository }    from "../../../../domain/repositories/loan-repository.interface";
import { Loan }               from "../../../../domain/entities/loan.entity";
import { LoanId }             from "../../../../domain/value-objects/loan-id.value-object";
import { CustomerId }         from "../../../../domain/value-objects/customer-id.value-object";
import { LoanOrmEntity }      from "../entities/loan.orm-entity";
import { LoanOrmMapper }      from "../mappers/loan.orm-mapper";

@Injectable()
export class TypeOrmLoanRepository implements ILoanRepository {
  constructor(
    @InjectRepository(LoanOrmEntity)
    private readonly ormRepo: Repository<LoanOrmEntity>,
    private readonly mapper:  LoanOrmMapper,
  ) {}

  async findById(loanId: LoanId): Promise<Loan | null> {
    const ormEntity = await this.ormRepo.findOne({ where: { id: loanId.value } });
    if (!ormEntity) return null;
    return this.mapper.toDomain(ormEntity);   // ORM entity → domain entity
  }

  async save(loan: Loan): Promise<void> {
    const ormEntity = this.mapper.toOrm(loan);  // domain entity → ORM entity
    await this.ormRepo.save(ormEntity);
  }

  async findActiveByCustomer(customerId: CustomerId): Promise<Loan[]> {
    const ormEntities = await this.ormRepo.find({
```

## Section 4: Domain-Driven Design Integration

**Q13. How does Onion Architecture relate to Domain-Driven Design (DDD), and how do they reinforce each other?**
A: Onion Architecture is the structural implementation strategy that gives DDD's tactical patterns a place to live safely. They are not the same thing but are deeply complementary:

- **DDD's Bounded Contexts** map to Onion's application scope — each bounded context gets its own onion (its own domain, application, and infrastructure rings).
- **DDD's Entities and Aggregates** live in Onion's innermost domain ring — they have rich behaviour, enforce invariants, and are isolated from infrastructure.
- **DDD's Value Objects** live in the domain ring — `Money`, `PanNumber`, `InterestRate` — immutable, self-validating, identity-free.
- **DDD's Domain Services** live in Onion's domain service ring — pure logic that spans multiple aggregates.
- **DDD's Application Services** map exactly to Onion's application use cases — they orchestrate domain objects to fulfil a use case.
- **DDD's Repositories** are defined as interfaces in the domain ring (what Onion Architecture calls "ports") and implemented in the infrastructure ring.
- **DDD's Domain Events** are created in the domain ring, collected by aggregates, and published by the application layer via an `IEventPublisher` port.
- **DDD's Anti-Corruption Layer (ACL)** maps to adapters in Onion's infrastructure ring — they translate between external service models (CIBIL's API response) and the domain's own model (`CreditReport`).

Without Onion Architecture (or a similar structure), DDD's tactical patterns become aspirational — entities accumulate `@Column()` annotations, repositories import ORMs directly, and the domain gradually ceases to be the centre of the system.

## Section 5: Pitfalls & Anti-patterns

**Q15. What is the "anemic domain model" anti-pattern, and how does Onion Architecture prevent it?**
A: An anemic domain model is one where domain entities are data bags (plain classes with only getters and setters) and all business logic lives in service classes outside the entity. It's the most common anti-pattern in architectures that don't enforce domain purity:

```typescript
// ❌ Anemic domain — entity is a data bag
class Loan {
  id:             string;
  status:         string;
  principalPaise: number;
  emisPaid:       number;
  // No methods — just data
}

// ❌ Logic scattered in a "service" that knows too much
class LoanService {
  async repayEmi(loanId: string, amountPaise: number): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);

    // Business logic here — fragile, duplicated, hard to test without DB
    if (loan.status !== "ACTIVE") throw new Error("...");
    const interestComponent  = loan.principalPaise * 0.015;
    const principalComponent = amountPaise - interestComponent;
    loan.principalPaise -= principalComponent;
    loan.emisPaid++;
    if (loan.principalPaise <= 0) loan.status = "CLOSED";

    await this.loanRepo.save(loan);
  }
}
```

Onion Architecture prevents this by: (a) establishing the domain ring where entities *must* have behaviour to be useful, (b) making it structurally awkward to put business logic in the application layer (which should be a thin orchestrator), and (c) making the domain ring dependency-free — so there's no temptation to make entities depend on services that are themselves coupled to infrastructure. When entity methods can be tested in isolation (no DB, no network), developers are incentivised to put logic there.

**Q16. What is the "infrastructure leaking into the domain" anti-pattern, and how does it manifest?**
A: The most insidious violation — infrastructure concerns seep into the domain ring, coupling business rules to technical choices:

```typescript

import { Entity, Column, PrimaryColumn } from "typeorm";  // ← infrastructure import

  id: string;

  @Column("bigint")
  principalInPaise: number;    // Now switching ORMs = editing the domain entity
}

// ❌ Domain service calling external API directly
export class LoanEligibilityService {
  async computeEligibility(pan: string): Promise<Eligibility> {
    const score = await fetch(`https://api.cibil.com/score?pan=${pan}`);  // ← HTTP call in domain
    // ...
  }
}

// ❌ Domain entity using environment variables
export class InterestCalculationService {
  private readonly baseRate = parseFloat(process.env.BASE_INTEREST_RATE!);  // ← env var in domain
}

// ✅ Correct — domain interface, infrastructure implements it

  pullReport(pan: string, consent: boolean): Promise<CreditReport>;
}
```

Detection: any `import` in a domain file that points to a path outside the domain folder, or to an `npm` package that is an infrastructure concern (`typeorm`, `axios`, `@nestjs/common`, `redis`, `kafka-node`).

**Q17. What is the "use case bloat" anti-pattern, and how do you avoid it?**
A: Use case bloat occurs when application-layer use cases accumulate business logic that belongs in the domain:

```typescript
// ❌ Use case doing domain work
class ApplyForLoanUseCase {
  async execute(command: ApplyForLoanCommand): Promise<void> {
    // Business logic in use case — wrong layer
    const r   = command.annualRate / 12;
    const n   = command.tenureMonths;
    const emi = (command.principal * r * Math.pow(1 + r, n)) / (Math.pow(1 + r, n) - 1);

    if (emi / command.monthlyIncome > 0.5) throw new Error("EMI exceeds 50% of income");

    const cibilScore = await this.creditBureau.pullReport(command.pan, command.consent);
    if (cibilScore.score < 700) throw new Error("CIBIL score too low");

    // More business rules inline ...
  }
}
```

The use case should only orchestrate; business rules should live in domain entities, domain services, or value objects. Fix: push the EMI calculation into `Loan.calculateEmi()`, the eligibility threshold into `LoanEligibilityService.compute()`. The use case becomes a thin coordinator:

```typescript
// ✅ Thin use case — orchestrates, does not compute
class ApplyForLoanUseCase {
  async execute(command: ApplyForLoanCommand): Promise<void> {
    const creditReport = await this.creditBureau.pullReport(command.pan, command.consent);
    const eligibility  = this.eligibilityService.compute({ creditReport, ...command });
    if (!eligibility.isEligible) throw new InsufficientEligibilityException(eligibility.reason);
    const loan = Loan.create({ ...eligibility.terms });
    await this.loanRepository.save(loan);
  }
}
```

**Q18. How do you handle cross-cutting concerns (logging, metrics, transactions) without polluting the use case or domain layers?**
A: Cross-cutting concerns belong in the infrastructure layer, applied transparently via decorators, interceptors, or middleware — the use case and domain never know they exist:

```typescript
// ─── Transactional decorator — applied in the infrastructure wiring ───────────

function Transactional() {
  return function (target: any, key: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    descriptor.value = async function (...args: any[]) {
      return dataSource.transaction(async (manager) => {
        // Swap the repository for a transactional one within this call
        return original.apply(this, args);
      });
    };
  };
}

// ─── NestJS interceptor for logging and metrics ───────────────────────────────

@Injectable()
class UseCaseLoggingInterceptor implements NestInterceptor {
  constructor(private readonly metrics: MetricsService) {}

  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const start = Date.now();
    const handlerName = context.getHandler().name;

    return next.handle().pipe(
      tap(() => {
        this.metrics.recordUseCaseDuration(handlerName, Date.now() - start, "success");
      }),
      catchError(err => {
        this.metrics.recordUseCaseDuration(handlerName, Date.now() - start, "error");
        throw err;
      }),
    );
  }
}

// ─── Applied at the controller level — use case is untouched ─────────────────

@Controller("loans")
@UseInterceptors(UseCaseLoggingInterceptor)
class LoanController {
  constructor(private readonly applyForLoan: ApplyForLoanUseCase) {}

  @Post("apply")
  async apply(@Body() dto: ApplyForLoanRequestDto) {
    return this.applyForLoan.execute(dto);
    // Logging and metrics happen in the interceptor — use case has no idea
  }
}
```

**Q19. How do you test the domain layer in complete isolation — no mocks, no frameworks, no DI container?**

```typescript
});
```

These tests run in milliseconds. They test the only thing that matters at this layer: business rules.

**Q20. "You're designing a fintech platform from scratch — loan origination, EMI collection, KYC, and notifications. How do you apply Onion Architecture across these bounded contexts?"**

**Q21. "A team member says that Onion Architecture adds too much boilerplate — separate ORM entities, mappers, interface tokens — for no real benefit in a CRUD microservice. How do you respond?"**
A: The argument is partially right and should be engaged honestly:

> "For a pure CRUD service with no business rules — a microservice that just proxies between HTTP and a database — the overhead of a full Onion is not worth it. If `POST /loan-products` creates a record and `GET /loan-products/:id` fetches it, with no validation beyond data types, the domain ring is empty and the architecture adds cost without value. In that case, a simple controller → service → TypeORM repository is correct.
>
> But in a loan origination service — where a loan has a lifecycle of 7 statuses, where EMI repayment involves complex amortisation, where eligibility rules change by product type and credit score, where the same business logic must be exercised by an HTTP controller, a Kafka consumer, and a cron job — the boilerplate pays for itself in three concrete ways.
>
> First, testing speed. Every business rule in a rich domain entity can be tested in milliseconds with no database. Finding and fixing an eligibility rule bug in a 30-millisecond test loop is categorically faster than debugging through an integration test that needs a running Postgres.
>
> Second, infrastructure freedom. When we switched from TypeORM to Prisma last year, the domain and application layers were untouched — we rewrote the infrastructure ring over two days. With a coupled architecture, that would have been a three-week refactor touching hundreds of files.
>
> Third, reasoning about correctness. When the business rule 'a customer cannot have more than 2 active loans' lives in one place — the use case — and is tested directly, I can read that rule in plain English. When it's embedded in a TypeORM query inside a service that also handles HTTP parsing, I have to understand three concerns simultaneously to verify it's correct.
>
> The overhead is real. The question is whether the domain is complex enough to justify it. In our loan service, it is. In a product catalogue service, it probably isn't."

**Q22. "The data team needs direct read access to the loan database for analytics. How do you handle this without compromising the domain model?"**
A: Read models and analytics access are a separate concern from the write model — Onion Architecture's domain model is the write-side concern; reads can bypass it entirely:

```typescript
// ─── Read model — bypasses domain entity, talks directly to DB ───────────────

// src/loan-context/infrastructure/read-models/loan-analytics.query.ts

@Injectable()
class LoanAnalyticsQuery {
  constructor(private readonly dataSource: DataSource) {}

  // Direct SQL — no domain entity, no mapper, no business rules
  async getLoanDisbursementSummary(fromDate: Date, toDate: Date): Promise<DisbursementSummaryRow[]> {
    return this.dataSource.query(`
      SELECT
        product_code,
        DATE_TRUNC('month', disbursed_at) AS month,
        COUNT(*)                          AS loan_count,
        SUM(principal_in_paise) / 100     AS total_disbursed_rupees,
        AVG(interest_rate)                AS avg_interest_rate
      FROM loans
      WHERE disbursed_at BETWEEN $1 AND $2
        AND status IN ('DISBURSED', 'ACTIVE', 'CLOSED')
      GROUP BY product_code, month
      ORDER BY month DESC
    `, [fromDate, toDate]);
  }
}
```

For the data team's direct access:
- **Read replicas**: provision a read-only PostgreSQL replica. The data team connects directly — they never touch the write model.
- **CQRS read side**: for complex reporting, maintain a separate read-optimised store (denormalised views, Elasticsearch, Redshift) fed by Kafka events from the write side. The domain model emits events; the read side subscribes and builds materialized views.
- **Row-level access control**: the replica's schema is identical but access-controlled via PostgreSQL roles — the data team has `SELECT` only, never `INSERT`/`UPDATE`/`DELETE`.

The Onion Architecture's domain model is never exposed to the data team — they consume the projection of domain events, not the domain itself.

**Q23. "How does Onion Architecture handle a scenario where the same business logic needs to run in three places: an HTTP endpoint, a Kafka consumer, and a nightly cron job?"**
A: This is the exact problem Onion Architecture is designed to solve. The business logic lives in the application use case — a plain TypeScript class. Three infrastructure adapters invoke the same use case:

```typescript
// ─── Use case — defined once, no framework dependency ────────────────────────

class CollectEmiUseCase {
  constructor(
    private readonly loanRepo:    ILoanRepository,
    private readonly nachGateway: INachMandatePort,
    private readonly publisher:   IEventPublisher,
  ) {}

  async execute(command: CollectEmiCommand): Promise<CollectEmiResult> {
    const loan = await this.loanRepo.findById(LoanId.of(command.loanId));
    if (!loan) throw new NotFoundException(`Loan ${command.loanId} not found`);

    loan.repayEmi(Money.ofPaise(command.amountInPaise));   // domain logic
    await this.loanRepo.save(loan);

    const events = loan.pullDomainEvents();
    await Promise.all(events.map(e => this.publisher.publish(e)));

    return { success: true, outstandingPrincipal: loan.outstandingPrincipal.display() };
  }
}

// ─── HTTP adapter — invokes use case from HTTP context ────────────────────────

@Controller("loans/:id/repay")
class LoanController {
  constructor(private readonly collectEmi: CollectEmiUseCase) {}

  @Post()
  async repay(@Param("id") loanId: string, @Body() dto: RepayEmiDto) {
    return this.collectEmi.execute({ loanId, amountInPaise: dto.amountInPaise });
  }
}

// ─── Kafka adapter — invokes same use case from event context ─────────────────

@EventPattern("nach-mandate-debited")
class NachDebitKafkaConsumer {
  constructor(private readonly collectEmi: CollectEmiUseCase) {}

  async handle(@Payload() event: NachDebitedEvent): Promise<void> {
    await this.collectEmi.execute({
      loanId:        event.loanId,
      amountInPaise: event.amountInPaise,
    });
  }
}

// ─── Cron adapter — invokes same use case from scheduled context ──────────────

@Injectable()
class EmiCollectionCron {
  constructor(
    private readonly collectEmi:   CollectEmiUseCase,
    private readonly dueLoanQuery: DueEmiLoanQuery,
  ) {}

  @Cron("0 9 1 * *")   // 9am on 1st of every month
  async collectDueEmis(): Promise<void> {
    const dueLoans = await this.dueLoanQuery.findDueToday();
    const results  = await Promise.allSettled(
      dueLoans.map(loan => this.collectEmi.execute({
        loanId:        loan.id,
        amountInPaise: loan.emiInPaise,
      }))
    );
    // Log results, alert on failures
  }
}
```

The `CollectEmiUseCase` is tested once — it doesn't matter whether the caller is an HTTP request, a Kafka event, or a cron trigger. The three adapters are thin; their only job is translating from their respective contexts into the command the use case expects.

**Q24. "Your team is inheriting a legacy NestJS codebase where controllers call TypeORM repositories directly, entities have @Column() decorators, and services mix HTTP logic with business rules. How do you migrate incrementally to Onion Architecture?"**
A: Incremental migration — the "strangler fig" approach — replaces the legacy structure one use case at a time without a big-bang rewrite:

**Phase 1 — Define the target structure without moving code:**
Create the folder structure (`domain/`, `application/`, `infrastructure/`) alongside the existing code. Set up `dependency-cruiser` rules that flag violations but don't break the build yet.

**Phase 2 — Extract value objects for the most painful duplication:**
```typescript
// Legacy: amount validation scattered in 15 services
if (amount < 0 || !Number.isInteger(amount)) throw ...

// Extract: one Money value object — all validation in one place
class Money { /* ... */ }
// Gradually replace raw number usage — no migration of services needed yet
```

**Phase 3 — Extract domain entities one aggregate at a time:**
Start with the most complex aggregate (`Loan`). Create a domain entity with business methods. Keep the ORM entity (`@Column()`) separate. Add a mapper between them:
```typescript
// Old: LoanEntity has @Column and business methods mixed
// New: Loan (domain) ← LoanOrmMapper → LoanOrmEntity (@Column decorators)
```

**Phase 4 — Extract use cases from controllers and services:**
Pick the most-tested flow. Extract its logic into an `ApplyForLoanUseCase`. The controller becomes a thin HTTP adapter. The existing repository stays in place initially — the use case depends on `ILoanRepository` and the existing TypeORM service temporarily implements it:
```typescript
// Temporary adapter: wraps the legacy service as an ILoanRepository
class LegacyLoanRepositoryAdapter implements ILoanRepository {
  constructor(private readonly legacyService: LoanService) {}
  async findById(id: LoanId): Promise<Loan | null> {
    const raw = await this.legacyService.findLoanById(id.value);
    return raw ? LoanOrmMapper.toDomain(raw) : null;
  }
}
```

**Phase 5 — Replace the adapter with a proper infrastructure implementation:**
Once the use case is working with the adapter, replace `LegacyLoanRepositoryAdapter` with `TypeOrmLoanRepository` and delete the adapter.

**Phase 6 — Turn on the linting rules:**
Enable `dependency-cruiser` as a build-breaking check. The legacy violations are now visible as explicit suppressions — each suppression is a tracked item to fix.

Each phase is independently deployable. The system never breaks; the architectural improvement accumulates use case by use case.

**Q25. "How do you explain the value of Onion Architecture to a CTO who is asking why the team is taking longer to build features compared to a flat CRUD architecture?"**
A: A concrete, outcome-focused explanation grounded in measurable outcomes:

> "You're right that Onion Architecture has upfront costs — more files, more interfaces, more mapping code. For a pure CRUD service, it's probably not worth it. But for our loan origination and EMI collection system, here's what we're getting for that cost.
>
> First, our unit test suite runs in 8 seconds and covers every business rule — all the eligibility logic, EMI calculations, prepayment penalties, overdraft rules. Before the refactor, testing any of those required a live database and took 4 minutes. When we change an eligibility rule, we know in 8 seconds if we broke anything. That speed compounds over every sprint.
>
> Second, when we migrated from TypeORM to Prisma three months ago — a change I'd normally budget two weeks for — it took two engineers two days. The domain and application layers were completely untouched because they only reference interfaces. We just swapped the infrastructure implementations.
>
> Third, the EMI collection use case now runs identically from three places: the HTTP endpoint for manual retriggers, the Kafka consumer for NACH debit confirmations, and the cron job for scheduled collection. We have one set of tests for one set of business rules. Before, we had three separate implementations that diverged and produced three different bugs over six months.
>
> The slower feeling on features is real for the first few weeks of adoption on a new context. After that, the test speed and the infrastructure independence make features faster to ship with more confidence. The cost is front-loaded; the benefit compounds. For a domain as regulated and complex as ours, that trade-off is clearly worth it."

**Tip for the Interview:** At the 5 YOE level, Onion Architecture questions surface as system design problems — "design a loan origination service," "how do you structure a NestJS backend for a fintech product," or "how do you ensure the business rules are testable without a database?" The answers that land do three things: (1) articulate the Dependency Rule precisely — not just "separate concerns" but "source code dependencies always point inward, enforced by import discipline and lint rules"; (2) demonstrate a concrete layer breakdown with real TypeScript examples — a rich domain entity with business methods, a thin use case that orchestrates without computing, and an infrastructure adapter that implements an interface defined in the domain; and (3) make the testability argument with numbers — "the domain tests run in 8 seconds with no infrastructure," "swapping the ORM took two days because the domain layer had zero ORM imports." In fintech specifically, the regulatory traceability angle reinforces the architecture: when an auditor asks "show me every place the eligibility rule is applied," the answer in Onion Architecture is one class in one file — not a grep across 40 services.
