# Enterprise & Architectural Patterns: Domain-Driven Design (DDD) Basics — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Domain-Driven Design, and what problem does it solve?**
A: Domain-Driven Design (DDD) is an approach to software development that places the **business domain at the centre of all design decisions**. It was introduced by Eric Evans in his 2003 book and addresses the core problem of complex software: a growing disconnect between the code and the business it models, leading to systems that are hard to change, hard to explain to stakeholders, and gradually diverging from the actual business rules they were meant to encode.

DDD solves this through two complementary ideas:
- **Strategic design** — how to decompose a large, complex domain into manageable parts (Bounded Contexts, Context Maps, Ubiquitous Language) that align with the organisation's team and ownership structure.
- **Tactical design** — how to model the internals of each part using building blocks (Entities, Value Objects, Aggregates, Repositories, Domain Services, Domain Events) that keep business logic in the domain model, not scattered across services and controllers.

The central claim: if the code and the domain expert speak the same language, and the code structure mirrors the domain structure, the system will naturally adapt as the business evolves.

**Q2. What is Ubiquitous Language, and why is it the most important DDD concept?**
A: Ubiquitous Language is a shared, precise vocabulary developed between **developers and domain experts**, used consistently in conversations, documentation, and — critically — in the code itself. Variable names, class names, method names, and event names all use the domain's own terms.

It's the most important concept because every other DDD building block depends on it. If your domain expert says "sanction" and your code says "approve," you have a translation layer in every conversation and every piece of code — a constant source of misunderstanding and bugs.

```typescript
// ❌ Technical vocabulary — doesn't match domain expert's mental model
class LoanRecord { // Domain expert says "Loan Application"
  updateApprovalFlag(flag: boolean): void {} // Domain expert says "sanction" or "reject"
  setDisbursalTimestamp(ts: Date): void {}   // Domain expert says "disbursement date"
}

// ✅ Ubiquitous Language — code reads like the domain expert speaks
class LoanApplication {
  sanction(sanctionedBy: Officer, conditions: SanctionCondition[]): void {}
  reject(reason: RejectionReason): void {}
  disburse(disbursedOn: Date, paymentReference: string): void {}
}
```

In a lending platform, the Ubiquitous Language includes terms like: sanction, disbursement, EMI, moratorium, DPD (Days Past Due), NPA, NACH mandate, UMRN, bureau pull, CIBIL score, LTV, co-applicant, guarantor, pre-closure, foreclosure, write-off. These exact terms belong in your class names, method names, event names, and database column names — not "approve," "payout," "installment," or "payment_default."

**Q3. What is a Bounded Context, and why does it matter architecturally?**
A: A Bounded Context is an explicit boundary within which a particular domain model applies — and outside which the model may differ or be irrelevant. It defines the scope of a Ubiquitous Language: the same term may mean different things in different Bounded Contexts, and that's acceptable as long as each context is internally consistent.

In a lending platform, you might have these Bounded Contexts:
- **Loan Origination** — `LoanApplication`, `Applicant`, `BureauReport`, `SanctionLetter`. "Customer" here is an *Applicant* seeking a loan.
- **Collections** — `DelinquentLoan`, `EmiDue`, `DpdBucket`, `CollectionAction`. "Customer" here is a *Borrower* who owes money.
- **KYC** — `VerificationCase`, `Document`, `KycStatus`. "Customer" is an *Identity* to be verified.
- **Accounting/Ledger** — `LedgerEntry`, `Account`, `JournalEntry`. "Loan" is a set of *Debit/Credit* entries.
- **Regulatory Reporting** — `PslClassification`, `NpaAsset`, `CrilcEntry`. "Loan" is a *Reporting Obligation*.

A `Loan` means something different in each context — different fields, different behaviour, different lifecycle. If you try to build one `Loan` class that serves all five contexts, you get an object with 80 fields, most of which are irrelevant in any given context. Bounded Contexts let you have five smaller, focused `Loan` representations, each correct for its context.

**Q4. What is the difference between an Entity and a Value Object?**
A: The distinction is about **identity**:

- **Entity** — has a unique identity that persists over time and across state changes. Two entities are the same if they have the same ID, regardless of their current attribute values. Identity is the thing that makes it "this particular loan" or "this particular applicant."
- **Value Object** — has no identity; is defined entirely by its attribute values. Two value objects are equal if all their attributes are equal. Value objects are immutable — you don't change a value object, you replace it with a new one.

```typescript
// Entity — identity matters; same loan even if amount changes
class Loan {
  constructor(
    private readonly id: LoanId,       // identity — what makes it "this" loan
    private amount: Money,
    private status: LoanStatus,
    private applicantId: ApplicantId,
  ) {}

  equals(other: Loan): boolean {
    return this.id.equals(other.id);   // identity-based equality
  }
}

// Value Object — no identity; equality is by value
class Money {
  constructor(
    private readonly amount: number,
    private readonly currency: 'INR' | 'USD',
  ) {}

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new CurrencyMismatchError();
    return new Money(this.amount + other.amount, this.currency); // returns new instance
  }

  // No setters — immutable; replace rather than modify
}

class InterestRate {
  constructor(private readonly basisPoints: number) {
    if (basisPoints < 0 || basisPoints > 10000) throw new InvalidRateError(basisPoints);
  }

  toPercent(): number { return this.basisPoints / 100; }
  equals(other: InterestRate): boolean { return this.basisPoints === other.basisPoints; }
}
```

Good candidates for Value Objects in a lending domain: `Money`, `InterestRate`, `PanNumber`, `IfscCode`, `LoanTenor`, `Address`, `DateRange`, `LtvRatio`, `BureauScore`, `EmiAmount`. Every one of these has no independent identity — they're fully described by their value.

**Q5. What is an Aggregate, and what is the Aggregate Root?**
A: An Aggregate is a **cluster of domain objects (entities and value objects) that are treated as a single unit** for the purpose of data changes. Every aggregate has one special entity called the **Aggregate Root** — the only object in the aggregate that external code may hold a reference to or modify directly. All access to other objects within the aggregate must go through the root.

The aggregate enforces **consistency boundaries** — invariants that must hold across all objects within the aggregate are enforced by the root. The root also controls all lifecycle transitions.

```typescript
// LoanApplication is the Aggregate Root
// CoApplicant, SanctionCondition, EmiSchedule are part of the aggregate
class LoanApplication {
  private readonly id: LoanApplicationId;
  private status: ApplicationStatus;
  private primaryApplicant: Applicant;          // entity within aggregate
  private coApplicant: CoApplicant | null;      // entity within aggregate
  private conditions: SanctionCondition[];      // value objects within aggregate
  private readonly domainEvents: DomainEvent[] = [];

  // External code never directly modifies coApplicant —
  // it always goes through the root's method
  addCoApplicant(coApplicant: CoApplicant): void {
    if (this.status !== ApplicationStatus.DRAFT) {
      throw new InvalidOperationException('Cannot add co-applicant after submission');
    }
    if (this.coApplicant) {
      throw new InvalidOperationException('Co-applicant already exists');
    }
    this.coApplicant = coApplicant;
  }

  sanction(conditions: SanctionCondition[], officer: Officer): void {
    if (this.status !== ApplicationStatus.UNDER_REVIEW) {
      throw new InvalidStatusTransitionException(this.status, ApplicationStatus.SANCTIONED);
    }
    // Aggregate root enforces the invariant: sanctioning requires conditions
    if (conditions.length === 0) {
      throw new DomainException('Sanction must specify at least one condition');
    }
    this.status = ApplicationStatus.SANCTIONED;
    this.conditions = conditions;

    // Domain event raised on the root
    this.domainEvents.push(new LoanApplicationSanctionedEvent(this.id, officer.id, conditions));
  }

  reject(reason: RejectionReason, officer: Officer): void {
    if (![ApplicationStatus.UNDER_REVIEW, ApplicationStatus.DRAFT].includes(this.status)) {
      throw new InvalidStatusTransitionException(this.status, ApplicationStatus.REJECTED);
    }
    this.status = ApplicationStatus.REJECTED;
    this.domainEvents.push(new LoanApplicationRejectedEvent(this.id, reason, officer.id));
  }

  pullAndClearEvents(): DomainEvent[] {
    const events = [...this.domainEvents];
    this.domainEvents.length = 0;
    return events;
  }
}
```

## Section 2: Tactical DDD Building Blocks

**Q6. What is a Domain Service, and when should you use it instead of putting logic on an Entity?**
A: A Domain Service encapsulates **domain logic that doesn't naturally belong on a single entity or value object** — typically logic that involves multiple aggregates or requires coordination between domain concepts that don't have a single "home."

The test for using a Domain Service: if you find yourself asking "which entity owns this method?" and the answer is genuinely ambiguous because the operation spans multiple domain objects, the logic belongs in a Domain Service.

```typescript
// Domain Service — credit eligibility involves both the Applicant and the BureauReport
// It doesn't belong on LoanApplication alone, nor on BureauReport alone
class CreditEligibilityDomainService {
  assessEligibility(
    application: LoanApplication,
    bureauReport: BureauReport,
    product: LoanProduct,
  ): EligibilityAssessment {
    const ltvRatio = LtvRatio.compute(application.requestedAmount, application.propertyValue);
    const foir = FoirRatio.compute(application.proposedEmi, application.monthlyIncome);

    const breaches: EligibilityBreach[] = [];

    if (bureauReport.score.isBelow(product.minimumBureauScore)) {
      breaches.push(new EligibilityBreach('BUREAU_SCORE', bureauReport.score, product.minimumBureauScore));
    }
    if (ltvRatio.exceeds(product.maximumLtv)) {
      breaches.push(new EligibilityBreach('LTV', ltvRatio, product.maximumLtv));
    }
    if (foir.exceeds(product.maximumFoir)) {
      breaches.push(new EligibilityBreach('FOIR', foir, product.maximumFoir));
    }
    if (bureauReport.hasOverdueAccounts()) {
      breaches.push(new EligibilityBreach('OVERDUE_ACCOUNTS', bureauReport.overdueAccountCount, 0));
    }

    return breaches.length === 0
      ? EligibilityAssessment.eligible()
      : EligibilityAssessment.ineligible(breaches);
  }
}
```

Don't confuse Domain Services with Application Services — a Domain Service contains pure domain logic (no database calls, no HTTP calls, no NestJS injection of infrastructure); an Application Service orchestrates domain objects and infrastructure.

**Q7. What is a Repository in DDD, and how does it differ from a DAO (Data Access Object)?**
A: A DDD Repository provides **the illusion of an in-memory collection of aggregates** — you `find`, `save`, and `remove` aggregate roots as if they were in a collection, without caring about the underlying storage. One repository per aggregate root.

The critical difference from a DAO:
- **DAO** — a thin wrapper over database operations; often exposes `INSERT`, `SELECT`, `UPDATE` semantics; tied to a database table; returns rows or ORMs that look like rows.
- **Repository** — speaks in domain terms; returns and accepts aggregate roots; abstracts *all* persistence concerns; defined by an interface in the domain layer, implemented in the infrastructure layer.

```typescript
// Domain layer — defines the interface (port)
// No Prisma, no TypeORM, no SQL here — pure domain concepts
interface ILoanApplicationRepository {
  findById(id: LoanApplicationId): Promise<LoanApplication | null>;
  findByApplicantPan(pan: PanNumber): Promise<LoanApplication[]>;
  findPendingReview(): Promise<LoanApplication[]>;
  save(application: LoanApplication): Promise<void>;   // works for both create and update
  remove(application: LoanApplication): Promise<void>;
}

// Infrastructure layer — implements the port using Prisma
@Injectable()
export class PrismaLoanApplicationRepository implements ILoanApplicationRepository {
  constructor(private readonly prisma: PrismaService) {}

  async findById(id: LoanApplicationId): Promise<LoanApplication | null> {
    const record = await this.prisma.loanApplication.findUnique({
      where: { id: id.value },
      include: { coApplicant: true, conditions: true },
    });
    return record ? LoanApplicationMapper.toDomain(record) : null;
  }

  async save(application: LoanApplication): Promise<void> {
    const data = LoanApplicationMapper.toPersistence(application);
    await this.prisma.loanApplication.upsert({
      where: { id: data.id },
      create: data,
      update: data,
    });
  }

  async findByApplicantPan(pan: PanNumber): Promise<LoanApplication[]> {
    const records = await this.prisma.loanApplication.findMany({
      where: { applicantPan: pan.value },
      include: { coApplicant: true, conditions: true },
    });
    return records.map(LoanApplicationMapper.toDomain);
  }

  async findPendingReview(): Promise<LoanApplication[]> {
    const records = await this.prisma.loanApplication.findMany({
      where: { status: 'UNDER_REVIEW' },
    });
    return records.map(LoanApplicationMapper.toDomain);
  }

  async remove(application: LoanApplication): Promise<void> {
    await this.prisma.loanApplication.delete({ where: { id: application.id.value } });
  }
}
```

**Q8. What are Domain Events, and how do they enable loose coupling between Bounded Contexts?**
A: Domain Events are immutable records of **something significant that happened in the domain** — past tense, named after the business occurrence, not the technical operation. They're the primary mechanism for communication between Bounded Contexts without direct coupling.

```typescript
// Domain events — named in past tense, contain just enough data for consumers
class LoanApplicationSubmittedEvent {
  readonly occurredAt: Date = new Date();
  constructor(
    public readonly applicationId: string,
    public readonly applicantPan: string,
    public readonly requestedAmount: number,
    public readonly productCode: string,
  ) {}
}

class LoanSanctionedEvent {
  readonly occurredAt: Date = new Date();
  constructor(
    public readonly applicationId: string,
    public readonly applicantId: string,
    public readonly sanctionedAmount: number,
    public readonly sanctionedBy: string,
    public readonly conditions: string[],
  ) {}
}

class EmiDefaultedEvent {
  readonly occurredAt: Date = new Date();
  constructor(
    public readonly loanId: string,
    public readonly applicantId: string,
    public readonly emiAmount: number,
    public readonly dueDate: Date,
    public readonly daysPastDue: number,
    public readonly failureCode: string,
  ) {}
}
```

```typescript
// Application service — publishes events after persisting the aggregate
@Injectable()
export class LoanSanctionApplicationService {
  async execute(command: SanctionLoanCommand): Promise<void> {
    const application = await this.loanApplicationRepo.findById(
      new LoanApplicationId(command.applicationId),
    );
    if (!application) throw new LoanApplicationNotFoundException(command.applicationId);

    const officer = await this.officerRepo.findById(new OfficerId(command.officerId));
    application.sanction(command.conditions.map(SanctionCondition.from), officer);

    await this.loanApplicationRepo.save(application);

    // Publish domain events collected on the aggregate
    for (const event of application.pullAndClearEvents()) {
      await this.eventBus.publish(event);
    }
  }
}

// Handlers in OTHER Bounded Contexts consume the event — no direct coupling
// In the NACH Bounded Context:
@EventHandler(LoanSanctionedEvent)
class InitiateNachMandateOnSanction {
  async handle(event: LoanSanctionedEvent): Promise<void> {
    await this.nachService.initiateMandateRegistration(event.applicationId, event.applicantId);
  }
}

// In the KYC Bounded Context:
@EventHandler(LoanSanctionedEvent)
class TriggerReKycCheckOnSanction {
  async handle(event: LoanSanctionedEvent): Promise<void> {
    await this.kycService.scheduleReKycIfRequired(event.applicantId);
  }
}
```

The `LoanSanctionApplicationService` knows nothing about NACH or KYC — it just records what happened. Each bounded context reacts independently.

**Q9. What is a Context Map, and what integration patterns does DDD define between Bounded Contexts?**
A: A Context Map is a diagram (or documented understanding) of how Bounded Contexts relate to each other — which team owns which context, how data flows between them, and what the integration pattern is at each boundary.

DDD defines several inter-context integration patterns:

- **Shared Kernel** — two contexts share a subset of the model. Changes to the shared part require coordination between teams. High coupling — use sparingly. Example: `Money` value object shared between Origination and Accounting.
- **Customer/Supplier** — one context (supplier) produces data consumed by another (customer). Supplier controls the API; customer adapts. Example: KYC context is the supplier; Origination is the customer — KYC status flows from KYC to Origination.
- **Conformist** — the downstream context conforms to the upstream's model without negotiation. Common when integrating with a powerful external system (RBI reporting format, CIBIL bureau API). Example: your Regulatory Reporting context conforms to RBI's XBRL schema.
- **Anticorruption Layer (ACL)** — the downstream context translates the upstream's model into its own terms using an adapter. Prevents the upstream's concepts from polluting the downstream's domain model. Example: CibilBureauAdapter translates CIBIL's raw response into your domain's `BureauReport`.
- **Open Host Service** — the upstream context publishes a well-defined API (REST, events, GraphQL) that any downstream can consume. Example: the User/KYC context publishes a verified-identity API consumed by Origination, Collections, and Reporting.
- **Published Language** — a well-documented shared data format for integration (JSON schema, Protobuf, Avro). Example: domain events published to Kafka using Avro schemas that all consuming services know.

**Q10. What is an Application Service in DDD, and what should it never contain?**
A: An Application Service is the entry point to a use case — it orchestrates the domain model to accomplish one business operation. It's thin by design: it should read like a checklist of steps, delegating all decisions to domain objects.

```typescript
// ✅ Correct Application Service — thin, orchestrating only
@Injectable()
export class ApplyForLoanApplicationService {
  constructor(
    private readonly loanApplicationRepo: ILoanApplicationRepository,
    private readonly applicantRepo: IApplicantRepository,
    private readonly bureauService: IBureauService,        // domain service port
    private readonly eligibilityDomainService: CreditEligibilityDomainService,
    private readonly eventBus: IEventBus,
  ) {}

  async execute(command: ApplyForLoanCommand): Promise<LoanApplicationId> {
    // 1. Fetch / reconstruct domain objects
    const applicant = await this.applicantRepo.findByPan(new PanNumber(command.pan));
    if (!applicant) throw new ApplicantNotFoundException(command.pan);

    const product = LoanProduct.fromCode(command.productCode);

    // 2. Fetch external data needed for domain decisions
    const bureauReport = await this.bureauService.fetchReport(applicant.pan);

    // 3. Domain logic — delegated entirely to domain objects/services
    const eligibility = this.eligibilityDomainService.assessEligibility(
      LoanApplication.draft(applicant, product, command.requestedAmount),
      bureauReport,
      product,
    );

    if (!eligibility.isEligible()) {
      throw new IneligibleApplicantException(eligibility.breaches);
    }

    // 4. Create the aggregate
    const application = LoanApplication.submit(applicant, product, command.requestedAmount, bureauReport);

    // 5. Persist
    await this.loanApplicationRepo.save(application);

    // 6. Publish domain events
    for (const event of application.pullAndClearEvents()) {
      await this.eventBus.publish(event);
    }

    return application.id;
  }
}
```

What an Application Service must **never** contain:
- Business rules (`if (score < 700)`) — belongs in domain objects or domain services.
- Database queries directly (no `prisma.loan.findMany(...)`) — goes through repositories.
- HTTP response formatting — belongs in controllers.
- Decision logic about which path to take based on domain state — belongs in aggregate methods.

## Section 3: DDD in a Fintech/Lending Platform

**Q11. What does a well-modelled `LoanApplication` aggregate look like in a lending platform?**
A: A fully modelled aggregate enforces all invariants internally and only allows valid state transitions:

```typescript
class LoanApplication {
  private constructor(
    private readonly _id: LoanApplicationId,
    private _status: ApplicationStatus,
    private readonly _applicant: Applicant,
    private _coApplicant: CoApplicant | null,
    private readonly _product: LoanProduct,
    private _requestedAmount: Money,
    private _bureauScore: BureauScore,
    private _conditions: SanctionCondition[],
    private _sanctionedAmount: Money | null,
    private readonly _submittedAt: Date,
    private readonly _domainEvents: DomainEvent[],
  ) {}

  // Factory method — enforces creation invariants
  static submit(
    applicant: Applicant,
    product: LoanProduct,
    requestedAmount: Money,
    bureauReport: BureauReport,
  ): LoanApplication {
    if (requestedAmount.isGreaterThan(product.maximumAmount)) {
      throw new DomainException(`Requested ₹${requestedAmount} exceeds product max ₹${product.maximumAmount}`);
    }
    const app = new LoanApplication(
      LoanApplicationId.generate(),
      ApplicationStatus.SUBMITTED,
      applicant,
      null,
      product,
      requestedAmount,
      bureauReport.score,
      [],
      null,
      new Date(),
      [],
    );
    app._domainEvents.push(new LoanApplicationSubmittedEvent(app._id.value, applicant.pan.value, requestedAmount.amount));
    return app;
  }

  // State transition — enforces preconditions and raises event
  sendForReview(reviewedBy: Officer): void {
    if (this._status !== ApplicationStatus.SUBMITTED) {
      throw new InvalidStatusTransitionException(this._status, ApplicationStatus.UNDER_REVIEW);
    }
    this._status = ApplicationStatus.UNDER_REVIEW;
    this._domainEvents.push(new LoanApplicationSentForReviewEvent(this._id.value, reviewedBy.id.value));
  }

  sanction(sanctionedAmount: Money, conditions: SanctionCondition[], officer: Officer): void {
    if (this._status !== ApplicationStatus.UNDER_REVIEW) {
      throw new InvalidStatusTransitionException(this._status, ApplicationStatus.SANCTIONED);
    }
    // Invariant: sanctioned amount cannot exceed requested amount
    if (sanctionedAmount.isGreaterThan(this._requestedAmount)) {
      throw new DomainException('Sanctioned amount cannot exceed requested amount');
    }
    // Invariant: must have conditions
    if (conditions.length === 0) {
      throw new DomainException('Sanction requires at least one condition');
    }
    this._status = ApplicationStatus.SANCTIONED;
    this._sanctionedAmount = sanctionedAmount;
    this._conditions = conditions;
    this._domainEvents.push(
      new LoanSanctionedEvent(this._id.value, this._applicant.id.value, sanctionedAmount.amount, officer.id.value),
    );
  }

  reject(reason: RejectionReason, officer: Officer): void {
    const rejectableStatuses = [ApplicationStatus.SUBMITTED, ApplicationStatus.UNDER_REVIEW];
    if (!rejectableStatuses.includes(this._status)) {
      throw new InvalidStatusTransitionException(this._status, ApplicationStatus.REJECTED);
    }
    this._status = ApplicationStatus.REJECTED;
    this._domainEvents.push(
      new LoanApplicationRejectedEvent(this._id.value, reason, officer.id.value),
    );
  }

  // Read-only accessors — no setters; state changes only through domain methods
  get id(): LoanApplicationId { return this._id; }
  get status(): ApplicationStatus { return this._status; }
  get bureauScore(): BureauScore { return this._bureauScore; }
  pullAndClearEvents(): DomainEvent[] {
    const events = [...this._domainEvents];
    this._domainEvents.length = 0;
    return events;
  }
}
```

**Q12. How do you identify Aggregate boundaries in a lending domain? What are the rules?**
A: Aggregate boundary design is one of DDD's hardest problems. The rules:

**Rule 1 — Small aggregates.** Start small — one aggregate root plus the minimum entities/value objects needed to enforce invariants together. Large aggregates cause contention, lock conflicts, and performance problems.

**Rule 2 — Aggregates reference each other by identity only.** `LoanApplication` doesn't hold a reference to the `Applicant` object — it holds an `ApplicantId`. If it needs applicant data, the application service fetches both separately.

```typescript
// ❌ Aggregate holding a reference to another aggregate
class LoanApplication {
  private applicant: Applicant; // wrong — creates a merged super-aggregate
}

// ✅ Aggregate referencing by identity
class LoanApplication {
  private applicantId: ApplicantId; // correct — separate aggregates
}
```

**Rule 3 — Enforce invariants within a single aggregate transactionally.** If invariant X requires that A and B are consistent with each other, A and B belong in the same aggregate — they're updated in one transaction. If the consistency can be eventual (updated by a domain event asynchronously), they can be in separate aggregates.

**Rule 4 — Design aggregates for the command side, not the query side.** Aggregates are optimised for write consistency; complex reads (dashboards, reports) should use separate read models (CQRS), not load the full aggregate graph.

**Practical boundaries for a lending platform:**

| Aggregate Root         | Contains                                                         | Does NOT contain              |
|------------------------|------------------------------------------------------------------|-------------------------------|
| `LoanApplication`      | `CoApplicant`, `SanctionCondition`, application-level events     | `Applicant` identity data     |
| `ActiveLoan`           | `EmiSchedule`, `EmiPayment`, `MandateDetails`                   | Bureau report, original application |
| `NachMandate`          | `MandatePresentation`, `DebitAttempt`                            | Loan data                     |
| `Applicant`            | `KycStatus`, `Address`, `IncomeDetail`                           | Loan history                  |
| `CollectionCase`       | `CollectionAction`, `DpdHistory`                                 | Loan origination details      |

**Q13. How do you model the EMI collection lifecycle as a DDD aggregate?**
A:

```typescript
class ActiveLoan {
  private constructor(
    private readonly _id: ActiveLoanId,
    private _status: LoanStatus,
    private readonly _principal: Money,
    private _outstandingPrincipal: Money,
    private readonly _interestRate: InterestRate,
    private readonly _emiSchedule: EmiSchedule,      // value object — full schedule
    private _emiPayments: EmiPayment[],               // entity within aggregate
    private readonly _mandateUrn: MandateUrn,
    private readonly _domainEvents: DomainEvent[],
  ) {}

  // Records a successful EMI collection
  recordEmiCollection(
    emiMonth: EmiMonth,
    amount: Money,
    collectionRef: string,
    collectedOn: Date,
  ): void {
    const scheduledEmi = this._emiSchedule.findEmi(emiMonth);
    if (!scheduledEmi) throw new DomainException(`No EMI scheduled for ${emiMonth}`);

    // Invariant: cannot collect already-paid EMI
    const alreadyPaid = this._emiPayments.find(p => p.emiMonth.equals(emiMonth));
    if (alreadyPaid) throw new DomainException(`EMI for ${emiMonth} already collected`);

    // Invariant: amount must match scheduled EMI (partial payments handled separately)
    if (!amount.equals(scheduledEmi.amount)) {
      throw new DomainException(`Expected ₹${scheduledEmi.amount}, received ₹${amount}`);
    }

    this._emiPayments.push(EmiPayment.create(emiMonth, amount, collectionRef, collectedOn));
    this._outstandingPrincipal = this._outstandingPrincipal.subtract(scheduledEmi.principalComponent);

    if (this._outstandingPrincipal.isZero()) {
      this._status = LoanStatus.CLOSED;
      this._domainEvents.push(new LoanClosedEvent(this._id.value, collectedOn));
    }

    this._domainEvents.push(
      new EmiCollectedEvent(this._id.value, emiMonth.toString(), amount.amount, collectionRef),
    );
  }

  // Records a debit failure
  recordEmiFailure(emiMonth: EmiMonth, failureCode: NachFailureCode, attemptedOn: Date): void {
    const daysPastDue = differenceInDays(attemptedOn, this._emiSchedule.findEmi(emiMonth)!.dueDate);
    this._domainEvents.push(
      new EmiDefaultedEvent(this._id.value, emiMonth.toString(), failureCode.value, daysPastDue),
    );
  }
}
```

**Q14. How do you handle the tension between DDD aggregates and database performance?**
A: This is the most common real-world DDD challenge. Aggregates are modelled for domain integrity — but loading a full aggregate (with all EMI payments, conditions, events) for every operation is expensive. Several patterns manage this:

**Pattern 1 — Lazy loading via repository.** Load only what's needed for the specific operation. Not all operations on `ActiveLoan` need the full EMI payment history.

**Pattern 2 — CQRS (Command Query Responsibility Segregation).** The aggregate is the "write model" — only used for commands (state-changing operations). Read operations use a separate "read model" — denormalised views, projections, or direct SQL queries optimised for the query. This completely bypasses the aggregate for reads.

```typescript
// Write side — uses full aggregate
async collectEmi(command: CollectEmiCommand): Promise<void> {
  const loan = await this.activeLoanRepo.findById(new ActiveLoanId(command.loanId));
  loan.recordEmiCollection(/* ... */);
  await this.activeLoanRepo.save(loan);
}

// Read side — uses an optimised read model, no aggregate loaded
async getLoanDashboard(loanId: string): Promise<LoanDashboardDto> {
  // Direct DB query — no aggregate, no domain logic
  return this.prisma.$queryRaw`
    SELECT l.id, l.outstanding_principal, l.status,
           COUNT(p.id) as payments_made, SUM(p.amount) as total_paid
    FROM active_loans l
    LEFT JOIN emi_payments p ON p.loan_id = l.id
    WHERE l.id = ${loanId}
    GROUP BY l.id, l.outstanding_principal, l.status
  `;
}
```

**Pattern 3 — Snapshots.** For aggregates with long event histories (a loan with 120 EMI payments), store a snapshot of the aggregate state periodically. Rebuild from the latest snapshot + subsequent events rather than replaying all history.

**Q16. How do you implement a Value Object in TypeScript that's used as a strongly typed identifier?**
A: Strongly typed identifiers prevent accidentally passing a `LoanApplicationId` where a `ApplicantId` is expected — a common bug in systems with many UUID-typed IDs:

```typescript
// Base VO for IDs — generic to share the equality/validation logic
abstract class EntityId {
  protected constructor(protected readonly _value: string) {
    if (!_value || _value.trim().length === 0) {
      throw new DomainException(`${this.constructor.name} cannot be empty`);
    }
  }

  get value(): string { return this._value; }

  equals(other: EntityId): boolean {
    return this.constructor === other.constructor && this._value === other._value;
  }

  toString(): string { return this._value; }
}

class LoanApplicationId extends EntityId {
  static generate(): LoanApplicationId {
    return new LoanApplicationId(crypto.randomUUID());
  }

  static from(value: string): LoanApplicationId {
    return new LoanApplicationId(value);
  }
}

class ApplicantId extends EntityId {
  static from(value: string): ApplicantId {
    return new ApplicantId(value);
  }
}

// TypeScript now prevents mixing up IDs
function findApplication(id: LoanApplicationId): Promise<LoanApplication | null> { /* ... */ }

const applicantId = ApplicantId.from('abc-123');
findApplication(applicantId); // ← TypeScript ERROR at compile time
                               // Argument of type 'ApplicantId' is not assignable
                               // to parameter of type 'LoanApplicationId'
```

```typescript
// Domain-meaningful value objects with validation and behaviour
class PanNumber {
  private static readonly PAN_REGEX = /^[A-Z]{5}[0-9]{4}[A-Z]{1}$/;

  private constructor(private readonly _value: string) {}

  static from(value: string): PanNumber {
    const normalised = value.trim().toUpperCase();
    if (!PanNumber.PAN_REGEX.test(normalised)) {
      throw new DomainException(`Invalid PAN format: ${value}`);
    }
    return new PanNumber(normalised);
  }

  get value(): string { return this._value; }
  get masked(): string { return `${this._value.slice(0, 5)}****${this._value.slice(-1)}`; }
  equals(other: PanNumber): boolean { return this._value === other._value; }
}

class IfscCode {
  private static readonly IFSC_REGEX = /^[A-Z]{4}0[A-Z0-9]{6}$/;

  static from(value: string): IfscCode { /* similar validation */ }
  get bankCode(): string { return this._value.slice(0, 4); } // HDFC, SBIN, etc.
  get branchCode(): string { return this._value.slice(5); }
}
```

## Section 5: Anti-patterns & Common Pitfalls

**Q18. What are the most common DDD anti-patterns in a fintech codebase?**
A:

**Anti-pattern 1 — Anemic Domain Model:** Entities are data bags; all logic is in service classes. The code says `loanService.canApplicantPrepay(loan)` instead of `loan.canPrepay()`. Business rules are scattered, not cohesive on the entity they govern.

**Anti-pattern 2 — Ignoring Bounded Contexts:** One monolithic `Loan` object trying to serve origination, collections, accounting, and regulatory reporting. It has 60 fields, half of which are null in any given context, and changing it for one context breaks all others.

**Anti-pattern 3 — God Application Service:** Application services that contain business logic — complex conditionals, calculation formulas, multi-step domain decisions — rather than delegating to domain objects. The application service should read as a workflow, not a rule book.

**Anti-pattern 4 — Repository that returns rows:** A "repository" that returns Prisma entities (`PrismaLoan`) or plain JSON objects rather than domain aggregates. The service layer then operates on database rows, blurring the layers.

**Anti-pattern 5 — Missing Ubiquitous Language:** Code uses technical terms (`record`, `entry`, `process`, `update`, `flag`) instead of domain terms (`sanction`, `disburse`, `foreclose`, `NPA`, `DPD`). Domain experts can't read the code; developers can't understand the domain.

**Anti-pattern 6 — Aggregate too large:** A `LoanApplication` that includes `Applicant`, their full document history, all bureau reports, all officer comments, the full EMI schedule, and every payment ever made. Loading this for a simple status check is expensive and fragile.

**Q19. When should you NOT apply DDD?**
A: DDD adds real complexity — sophisticated domain modelling, aggregate design, repository interfaces, domain events, context mapping. The investment only pays off in specific conditions. Do NOT apply DDD when:

- The domain is **CRUD-heavy with minimal business logic** — a simple loan product catalogue or a reference data store doesn't need aggregates and domain events; active record or a simple service + repository is fine.
- The team is **small and the system is early-stage** — DDD's structure takes time to establish. For a 2-person team building an MVP, the overhead of proper DDD is counterproductive.
- The **domain is well-understood and stable** — DDD's value compounds when the domain evolves. If the business rules haven't changed in three years, the complexity of DDD may not be justified.
- You're building a **read-heavy reporting or analytics system** — DDD aggregates optimise for write consistency; reporting systems need denormalised, query-optimised data access, not rich domain models.

The practical approach: start with a clean Layered Architecture with good naming (Ubiquitous Language) and clear layer separation. Introduce DDD tactical patterns (aggregates, value objects, domain events) as complexity grows in specific bounded contexts. Apply full DDD where the domain is richest — typically loan origination, underwriting, and collections in a lending platform.

## Section 6: Scenario / Design Questions

**Q20. "Your codebase has `LoanService.updateLoan(id, data)` called from five different places with different partial `data` objects. Some callers set status, some update amounts, some add conditions. What's wrong and how do you fix it with DDD?"**
A: `updateLoan(id, data)` is the classic anemic service smell — it's a generic CRUD operation masquerading as a domain operation. Every caller is bypassing the domain model's invariants:

- A caller that sets `status = 'SANCTIONED'` without checking preconditions bypasses the state machine.
- A caller that sets `amount = newAmount` doesn't know whether the amount can be changed at this status.
- No domain events are raised — consumers (NACH, notification) never find out what changed.

**Fix: replace one generic update with explicit domain operations:**

```typescript
// ❌ Generic CRUD — no domain semantics, no invariants, no events
await loanService.updateLoan(id, { status: 'SANCTIONED', sanctionedAmount: 4500000 });

// ✅ Explicit domain operations — each enforces its own invariants
// Caller 1 — sanction use case
await sanctionLoanService.execute(new SanctionLoanCommand(id, sanctionedAmount, conditions, officerId));

// Caller 2 — reject use case
await rejectLoanService.execute(new RejectLoanCommand(id, reason, officerId));

// Caller 3 — send for review
await sendForReviewService.execute(new SendForReviewCommand(id, reviewerId));
```

Each command maps to one aggregate method, one invariant check, one domain event. The aggregate's `sanction()`, `reject()`, and `sendForReview()` methods enforce the rules and can't be bypassed.

**Q21. "Design the DDD model for a co-lending product where two lenders (your NBFC and a partner bank) co-fund each loan in a fixed ratio. How do you represent this as aggregates and domain events?"**
A:

```typescript
// Value Object — co-lending ratio; immutable; validates sum = 100%
class CoLendingRatio {
  constructor(
    public readonly nbfcPercent: number,
    public readonly partnerPercent: number,
  ) {
    if (nbfcPercent + partnerPercent !== 100) {
      throw new DomainException('Co-lending ratio must sum to 100%');
    }
    if (nbfcPercent < 20 || nbfcPercent > 80) {
      throw new DomainException('RBI co-lending: NBFC share must be 20–80%');
    }
  }

  nbfcAmount(total: Money): Money { return total.percent(this.nbfcPercent); }
  partnerAmount(total: Money): Money { return total.percent(this.partnerPercent); }
}

// Aggregate Root — CoLendingArrangement governs the co-lending agreement
class CoLendingLoan {
  private constructor(
    private readonly _id: CoLendingLoanId,
    private _status: CoLendingStatus,
    private readonly _baseLoanId: ActiveLoanId,   // reference by ID — separate aggregate
    private readonly _partnerBankId: PartnerBankId,
    private readonly _ratio: CoLendingRatio,
    private readonly _totalAmount: Money,
    private _nbfcDisbursed: boolean,
    private _partnerDisbursed: boolean,
    private readonly _domainEvents: DomainEvent[],
  ) {}

  // Both parties must disburse before co-lending loan is active
  recordNbfcDisbursement(reference: string, disbursedAt: Date): void {
    if (this._nbfcDisbursed) throw new DomainException('NBFC already disbursed');
    this._nbfcDisbursed = true;
    this._domainEvents.push(
      new NbfcDisbursedEvent(this._id.value, this._ratio.nbfcAmount(this._totalAmount).amount, reference),
    );
    this.checkAndActivate(disbursedAt);
  }

  recordPartnerDisbursement(reference: string, disbursedAt: Date): void {
    if (this._partnerDisbursed) throw new DomainException('Partner already disbursed');
    this._partnerDisbursed = true;
    this._domainEvents.push(
      new PartnerBankDisbursedEvent(this._id.value, this._ratio.partnerAmount(this._totalAmount).amount, reference),
    );
    this.checkAndActivate(disbursedAt);
  }

  private checkAndActivate(activatedAt: Date): void {
    // Invariant: both parties must disburse before loan becomes ACTIVE
    if (this._nbfcDisbursed && this._partnerDisbursed) {
      this._status = CoLendingStatus.ACTIVE;
      this._domainEvents.push(new CoLendingLoanActivatedEvent(this._id.value, activatedAt));
    }
  }
}

// Domain events trigger downstream reactions:
// CoLendingLoanActivatedEvent → partner bank notification (via ACL to partner bank's API)
// CoLendingLoanActivatedEvent → regulatory reporting (co-lending return to RBI)
// NbfcDisbursedEvent → ledger debit entry in our accounting context
// PartnerBankDisbursedEvent → reconciliation record in our accounting context
```

**Q22. "Your team is debating whether the EMI schedule should be inside the `ActiveLoan` aggregate or a separate aggregate. How do you decide?"**
A: Apply the aggregate boundary rules:

**Arguments for EMI schedule INSIDE `ActiveLoan`:**
- The EMI schedule is meaningless without the loan — it has no independent identity or lifecycle.
- Invariants span both: "a payment can only be recorded if an EMI is scheduled for that month" requires checking the schedule when recording a payment. This invariant can only be enforced atomically if they're in the same aggregate.
- The schedule never changes independently of the loan (moratorium, restructuring all happen on the loan, changing the schedule as a consequence).

**Arguments for EMI schedule OUTSIDE `ActiveLoan`:**
- Schedules can be large (120 rows for a 10-year loan) — loading all 120 EMI records to collect one EMI is expensive.
- If the schedule is queried frequently for display (customer app shows upcoming EMIs), loading the full `ActiveLoan` aggregate for reads is overkill.

**Decision:** Keep the schedule **inside** the `ActiveLoan` aggregate for write operations (the invariant argument wins for the command side). For read operations (show upcoming EMIs, display schedule), use CQRS — a separate read model or direct DB query that doesn't go through the aggregate at all.

```typescript
// Command side — aggregate enforces invariant
class ActiveLoan {
  recordEmiCollection(emiMonth: EmiMonth, amount: Money): void {
    const scheduled = this._emiSchedule.findEmi(emiMonth); // schedule is inside aggregate
    if (!scheduled) throw new DomainException('No EMI scheduled for this month');
    // ... rest of invariant enforcement
  }
}

// Query side — direct DB query, no aggregate loaded
@Injectable()
export class EmiScheduleQueryService {
  async getUpcomingEmis(loanId: string, fromDate: Date): Promise<EmiScheduleDto[]> {
    return this.prisma.emiSchedule.findMany({
      where: { loanId, dueDate: { gte: fromDate } },
      orderBy: { dueDate: 'asc' },
      take: 6, // next 6 EMIs
    });
  }
}
```
