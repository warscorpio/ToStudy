# JavaScript / TypeScript (Enterprise & Architectural Patterns): Clean Architecture — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Clean Architecture?**
A: Clean Architecture is an architectural philosophy proposed by Robert C. Martin (Uncle Bob) in 2012 that organises a software system into **concentric layers**, each with a distinct responsibility, where **source-code dependencies point only inward** — toward the higher-level, more abstract layers — and never outward toward lower-level, more concrete layers. The innermost layers contain enterprise-wide business rules and are entirely independent of frameworks, databases, UI, and any external agency. The outermost layers contain the concrete implementations — web frameworks, ORMs, third-party SDKs — which are treated as interchangeable details.

The central insight is that **the architecture screams the domain, not the framework**. A well-structured Clean Architecture codebase should, by its folder structure and class names alone, communicate that it is an order management system or an inventory system — not that it is an Express app or a NestJS app. The framework is a delivery mechanism, not the architecture.

Clean Architecture synthesises and reconciles several earlier architectural patterns — Hexagonal Architecture (Ports & Adapters) by Alistair Cockburn, Onion Architecture by Jeffrey Palermo, and BCE (Boundary-Control-Entity) by Ivar Jacobson — all of which share the same fundamental rule: the dependency rule.

**Q2. What is the Dependency Rule, and why is it the single most important constraint in Clean Architecture?**
A: The Dependency Rule states: **source code dependencies must point only inward, toward higher-level policies.** Nothing in an inner circle may know anything about something in an outer circle — not a name, not a function, not a class, not a variable.

This is not merely about import direction in a linter sense — it is about *knowledge*. If a domain entity contains the string `"prisma"`, `"express"`, or `"@nestjs"` anywhere in its source, the Dependency Rule is violated, even if the import resolves correctly at compile time.

```
        ┌─────────────────────────────────────────┐
        │  Frameworks & Drivers (outermost)        │
        │  ┌───────────────────────────────────┐   │
        │  │  Interface Adapters               │   │
        │  │  ┌─────────────────────────────┐  │   │
        │  │  │  Application / Use Cases    │  │   │
        │  │  │  ┌───────────────────────┐  │  │   │
        │  │  │  │  Domain / Entities    │  │  │   │
        │  │  │  │  (innermost)          │  │  │   │
        │  │  │  └───────────────────────┘  │  │   │
        │  │  └─────────────────────────────┘  │   │
        │  └───────────────────────────────────┘   │
        └─────────────────────────────────────────┘

  Dependencies point INWARD only:
  Frameworks → Adapters → Use Cases → Entities
```

Why it matters:
- **Testability** — the inner layers (entities, use cases) have zero infrastructure dependencies, so they run in pure Node.js tests with no database, no HTTP server, no framework boilerplate.
- **Framework independence** — you can swap Express for Fastify, Prisma for TypeORM, or React for Vue without touching a single use case or entity.
- **Independent deployability** — inner layers can be extracted into separate packages and deployed independently.
- **Long-term maintainability** — the most volatile things (frameworks, libraries, UI) are at the outermost ring; the most stable things (business rules) are at the innermost ring. Volatility increases outward.

**Q3. What are the four layers of Clean Architecture, and what does each contain?**
A:

**Layer 1 — Entities (Domain Layer / Enterprise Business Rules)**
The innermost layer. Contains the highest-level business rules of the enterprise — rules that would be true regardless of whether this software existed, rules that a business analyst could explain without referencing any technology. Contains:
- Domain entities (`Order`, `User`, `Product`) — plain TypeScript classes or objects with business methods and invariants.
- Value objects (`Money`, `Email`, `OrderId`) — immutable, identity-less domain concepts.
- Domain events (`OrderPlaced`, `PaymentFailed`) — facts that happened in the domain.
- Domain errors (`InsufficientInventoryError`, `PaymentDeclinedError`).
- Repository interfaces — abstract contracts for data access (the interface lives here; the implementation lives in the outermost layer).

**Layer 2 — Use Cases (Application Layer / Application Business Rules)**
Orchestrates the flow of data to and from entities to achieve a specific application goal. Contains:
- Use case classes / interactors (`PlaceOrderUseCase`, `RegisterUserUseCase`).
- Application-level interfaces (ports): `EmailService`, `PaymentGateway`, `EventBus`.
- DTOs (Data Transfer Objects) — input and output shapes for use cases.
- Application services that coordinate multiple entities and ports.

**Layer 3 — Interface Adapters**
Converts data from the format convenient for use cases and entities to the format convenient for the external world (and vice versa). Contains:
- Controllers — receive HTTP/CLI input, call use cases, return responses.
- Presenters / View Models — format use case output for the UI or API response.
- Repository implementations that adapt domain repository interfaces to specific ORMs.
- Gateway implementations that adapt domain port interfaces to specific SDKs.

**Layer 4 — Frameworks & Drivers (Infrastructure Layer)**
The outermost layer. Concrete implementations of everything external. Contains:
- Web framework configuration (Express routes, NestJS modules, Fastify plugins).
- ORM setup (Prisma client, TypeORM data source configuration).
- Third-party SDK instantiation (Stripe, SendGrid, AWS SDK).
- Database drivers, message queue clients, file system utilities.
- Dependency injection container configuration (composition root).

**Q4. What is the difference between Clean Architecture, Hexagonal Architecture, and Onion Architecture?**
A: All three share the same core insight (dependency rule, framework independence, testability), but differ in vocabulary and emphasis:

| Aspect | Hexagonal (Ports & Adapters) | Onion | Clean Architecture |
|---|---|---|---|
| **Origin** | Alistair Cockburn, 2005 | Jeffrey Palermo, 2008 | Robert C. Martin, 2012 |
| **Vocabulary** | Ports (interfaces), Adapters (implementations), Application core | Domain Model, Domain Services, Application Services, Infrastructure | Entities, Use Cases, Interface Adapters, Frameworks |
| **Shape metaphor** | Hexagon with ports on each face | Concentric rings (onion layers) | Concentric circles |
| **Primary emphasis** | Symmetry — driving side (UI) and driven side (DB) use same port/adapter model | Domain model at center, infrastructure at outside | The Dependency Rule + Screaming Architecture |
| **Use case concept** | Implicit — the application core | Application Services layer | Explicit Use Case classes (Interactors) |

In practice, these patterns describe the same architecture with different names. At 5 YOE, knowing that they converge is more valuable than memorising their differences — and being able to say "our architecture follows the Dependency Rule, with the domain at the centre and infrastructure at the edges" covers all three.

**Q5. What does "screaming architecture" mean?**
A: Screaming Architecture is Martin's principle that the top-level structure of a codebase should declare its domain purpose loudly — it should "scream" what the system does, not what framework it uses. A project whose root folder contains `controllers/`, `models/`, `views/` screams "Rails application." A project whose root folder contains `orders/`, `inventory/`, `billing/`, `identity/` screams "e-commerce system."

```
// ✗ — Framework-screaming structure (tells you about the tech, not the domain)
src/
  controllers/
    orderController.ts
    userController.ts
  models/
    order.ts
    user.ts
  services/
    orderService.ts
  routes/
    index.ts

// ✓ — Domain-screaming structure (tells you about the business)
src/
  orders/
    domain/
      Order.ts
      OrderItem.ts
      OrderRepository.ts       // interface
    application/
      PlaceOrderUseCase.ts
      CancelOrderUseCase.ts
      GetOrderUseCase.ts
    infrastructure/
      PrismaOrderRepository.ts // implements OrderRepository
  payments/
    domain/
      PaymentGateway.ts        // interface / port
    application/
      ProcessPaymentUseCase.ts
    infrastructure/
      StripePaymentGateway.ts  // implements PaymentGateway
  identity/
    domain/
      User.ts
      UserRepository.ts
    application/
      RegisterUserUseCase.ts
      LoginUseCase.ts
    infrastructure/
      PrismaUserRepository.ts
  shared/
    domain/
      Money.ts
      Email.ts
      UniqueId.ts
  main.ts                      // composition root
```

## Section 2: Domain Layer — Entities and Value Objects

**Q6. How do you implement a domain entity in TypeScript that enforces its own invariants?**
A: Domain entities encapsulate business rules as methods and enforce invariants at construction time — they are never in an invalid state:
```ts
// Value Object — immutable, no identity, validated at creation
class Money {
  private constructor(
    public readonly amount:   number,
    public readonly currency: string
  ) {}

  static create(amount: number, currency: string): Money {
    if (amount < 0)         throw new DomainError("Money amount cannot be negative");
    if (!currency.match(/^[A-Z]{3}$/)) throw new DomainError("Invalid currency code");
    return new Money(amount, currency);
  }

  add(other: Money): Money {
    if (this.currency !== other.currency)
      throw new DomainError(`Cannot add ${this.currency} and ${other.currency}`);
    return Money.create(this.amount + other.amount, this.currency);
  }

  multiply(factor: number): Money {
    return Money.create(this.amount * factor, this.currency);
  }

  isGreaterThan(other: Money): boolean {
    if (this.currency !== other.currency) throw new DomainError("Currency mismatch");
    return this.amount > other.amount;
  }

  format(): string {
    return new Intl.NumberFormat("en-IN", {
      style: "currency", currency: this.currency
    }).format(this.amount);
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
}

// Domain Entity — has identity (id), enforces invariants, exposes domain behavior
class Order {
  private items:   OrderItem[] = [];
  private status:  OrderStatus = "PENDING";
  private events:  DomainEvent[] = [];

  private constructor(
    public readonly id:         OrderId,
    public readonly customerId: CustomerId,
    private readonly createdAt: Date
  ) {}

  // Factory method — enforces valid initial state
  static create(customerId: CustomerId): Order {
    const order = new Order(
      OrderId.generate(),
      customerId,
      new Date()
    );
    order.addEvent(new OrderCreatedEvent(order.id, customerId));
    return order;
  }

  // Reconstruct from persistence — bypasses factory invariants (already validated)
  static reconstitute(props: OrderProps): Order {
    const order = new Order(props.id, props.customerId, props.createdAt);
    order.items  = props.items;
    order.status = props.status;
    return order;
  }

  // Domain behavior — with invariants enforced
  addItem(product: Product, quantity: number): void {
    if (this.status !== "PENDING")
      throw new DomainError("Cannot modify a confirmed order");
    if (quantity <= 0)
      throw new DomainError("Quantity must be positive");
    if (quantity > product.stockLevel)
      throw new InsufficientInventoryError(product.id, quantity, product.stockLevel);

    const existing = this.items.find(i => i.productId.equals(product.id));
    if (existing) {
      existing.increaseQuantity(quantity);
    } else {
      this.items.push(OrderItem.create(product.id, product.price, quantity));
    }
  }

  confirm(): void {
    if (this.status !== "PENDING")
      throw new DomainError(`Cannot confirm order in ${this.status} status`);
    if (this.items.length === 0)
      throw new DomainError("Cannot confirm an empty order");

    this.status = "CONFIRMED";
    this.addEvent(new OrderConfirmedEvent(this.id, this.getTotal()));
  }

  cancel(reason: string): void {
    if (this.status === "DELIVERED")
      throw new DomainError("Cannot cancel a delivered order");
    if (this.status === "CANCELLED")
      throw new DomainError("Order already cancelled");

    this.status = "CANCELLED";
    this.addEvent(new OrderCancelledEvent(this.id, reason));
  }

  // Computed domain property
  getTotal(): Money {
    return this.items.reduce(
      (sum, item) => sum.add(item.getSubtotal()),
      Money.create(0, "INR")
    );
  }

  requiresManagerApproval(): boolean {
    return this.getTotal().isGreaterThan(Money.create(100_000, "INR")); // business rule
  }

  // Domain events — consumed by outer layers after persistence
  pullEvents(): DomainEvent[] {
    const events = [...this.events];
    this.events  = [];
    return events;
  }

  private addEvent(event: DomainEvent): void { this.events.push(event); }

  // Getters — expose read-only snapshots
  getStatus():  OrderStatus  { return this.status; }
  getItems():   OrderItem[]  { return [...this.items]; }
  getCreatedAt(): Date       { return this.createdAt; }
}
```

**Q7. How do you define repository interfaces in the domain layer — and why do they belong there?**
A: Repository interfaces belong in the domain layer because they define *what the domain needs* from persistence, not *how* persistence works. The domain owns the contract; infrastructure fulfils it:
```ts
// Domain layer — interface defines what the domain needs
// orders/domain/OrderRepository.ts
interface OrderRepository {
  findById(id: OrderId): Promise<Order | null>;
  findByCustomerId(customerId: CustomerId, filter?: OrderFilter): Promise<Order[]>;
  save(order: Order): Promise<void>;
  delete(id: OrderId): Promise<void>;
  nextId(): OrderId; // domain controls ID generation strategy
}

// Domain layer — interface for a domain service implemented outside
// payments/domain/PaymentGateway.ts
interface PaymentGateway {
  charge(amount: Money, token: PaymentToken): Promise<ChargeResult>;
  refund(chargeId: ChargeId, amount: Money): Promise<RefundResult>;
}

// Infrastructure layer — implements the domain's contract
// orders/infrastructure/PrismaOrderRepository.ts
class PrismaOrderRepository implements OrderRepository {
  constructor(private prisma: PrismaClient) {}

  async findById(id: OrderId): Promise<Order | null> {
    const record = await this.prisma.order.findUnique({
      where:   { id: id.value },
      include: { items: true },
    });
    return record ? OrderMapper.toDomain(record) : null;
  }

  async save(order: Order): Promise<void> {
    const data = OrderMapper.toPersistence(order);
    await this.prisma.order.upsert({
      where:  { id: data.id },
      update: data,
      create: data,
    });
    // Publish domain events after successful persistence
    const events = order.pullEvents();
    await Promise.all(events.map(e => this.eventBus.publish(e)));
  }

  nextId(): OrderId { return OrderId.generate(); }

  // ... findByCustomerId, delete
}
```
The domain interface points inward (no Prisma import). The infrastructure implementation points inward (imports from domain). This is the Dependency Inversion Principle applied at the architectural level — exactly what Clean Architecture requires.

## Section 3: Application Layer — Use Cases

**Q8. How do you implement a Use Case class, and what should it contain?**
A: A Use Case (also called Interactor) is a single-operation class that orchestrates domain entities and ports to fulfil one application goal. It contains application-level flow logic — coordination, not business rules:
```ts
// Use Case input/output DTOs — live in the application layer
interface PlaceOrderInput {
  customerId:    string;
  items:         Array<{ productId: string; quantity: number }>;
  paymentToken:  string;
  shippingAddress: AddressDto;
}

interface PlaceOrderOutput {
  orderId:           string;
  total:             string; // formatted
  estimatedDelivery: string;
  chargeId:          string;
}

// Use Case — orchestrates; owns application flow
class PlaceOrderUseCase {
  constructor(
    private readonly orders:    OrderRepository,
    private readonly products:  ProductRepository,
    private readonly inventory: InventoryService,
    private readonly payments:  PaymentGateway,
    private readonly shipping:  ShippingService,
    private readonly events:    EventBus
  ) {}

  async execute(input: PlaceOrderInput): Promise<PlaceOrderOutput> {
    // 1. Load entities
    const customer = await this.validateCustomer(input.customerId);
    const order    = Order.create(customer.id);

    // 2. Apply domain logic — entity enforces its own invariants
    for (const item of input.items) {
      const product = await this.products.findById(new ProductId(item.productId));
      if (!product) throw new NotFoundError(`Product ${item.productId}`);
      order.addItem(product, item.quantity); // domain entity validates
    }

    // 3. Application-level guard
    if (order.requiresManagerApproval()) {
      throw new ManagerApprovalRequiredError(order.getTotal());
    }

    // 4. Reserve inventory — compensable action
    const reservation = await this.inventory.reserve(order.getItems());

    // 5. Process payment
    let charge: ChargeResult;
    try {
      charge = await this.payments.charge(
        order.getTotal(),
        new PaymentToken(input.paymentToken)
      );
    } catch (err) {
      await this.inventory.release(reservation.id); // compensate
      throw err;
    }

    // 6. Confirm order — domain transition
    order.confirm();

    // 7. Persist
    await this.orders.save(order); // publishes domain events internally

    // 8. Schedule shipping (non-critical — don't fail order if this fails)
    const shipment = await this.shipping.schedule(order, input.shippingAddress)
      .catch(() => null);

    // 9. Return output DTO — formatted for the caller, not the domain
    return {
      orderId:           order.id.value,
      total:             order.getTotal().format(),
      estimatedDelivery: shipment?.estimatedDelivery ?? "3-5 business days",
      chargeId:          charge.id,
    };
  }

  private async validateCustomer(customerId: string): Promise<Customer> {
    const customer = await this.customerRepo.findById(new CustomerId(customerId));
    if (!customer)          throw new NotFoundError(`Customer ${customerId}`);
    if (customer.isBanned()) throw new CustomerBannedError(customerId);
    return customer;
  }
}
```

**Q9. What is the difference between domain logic and application logic, and how do you decide where a rule belongs?**
A: This boundary is one of the most important and most frequently blurred in real codebases:

**Domain logic** — rules that are inherently true about the business, regardless of which application or use case invokes them. They would still exist if you rewrote the system from scratch:
- An order cannot be confirmed if it has no items.
- Money cannot be negative.
- A product with zero stock cannot be added to an order.
- An order total over ₹1,00,000 requires manager approval (a firm business rule, not a UI concern).

**Application logic** — rules about *how a specific application orchestrates* the domain to achieve a use case. They are specific to the current system and could change without the business rules changing:
- When placing an order, reserve inventory *before* charging payment (sequencing).
- If payment fails, release the inventory reservation (compensation).
- After an order is confirmed, send a confirmation email (side effect coordination).
- The `PlaceOrder` use case requires manager approval over ₹1,00,000 — but the *rule itself* (`requiresManagerApproval()`) lives in the entity.

The practical test: *if you wrote a CLI tool and a web app that both use this system, would this rule apply to both?* If yes — domain logic (entity). If it's specific to the web app's flow — application logic (use case).

```ts
// Domain logic — on the entity, always enforced
class Order {
  confirm(): void {
    if (this.items.length === 0)
      throw new DomainError("Cannot confirm empty order"); // always true
  }
  requiresManagerApproval(): boolean {
    return this.getTotal().isGreaterThan(Money.create(100_000, "INR")); // business rule
  }
}

// Application logic — in the use case, specific to this flow
class PlaceOrderUseCase {
  async execute(input: PlaceOrderInput): Promise<PlaceOrderOutput> {
    // Application logic: check approval BEFORE reserving inventory
    if (order.requiresManagerApproval()) {
      throw new ManagerApprovalRequiredError(); // sequencing is app logic
    }
    await this.inventory.reserve(order.getItems()); // app logic: this step exists here
    // ... rest of the flow
  }
}
```

## Section 4: Interface Adapters and Infrastructure

**Q10. What is the role of the Interface Adapters layer, and what are Mappers?**
A: The Interface Adapters layer is the translation boundary — it converts data between the shape convenient for use cases/entities and the shape required by external systems (HTTP, databases, message queues). This layer contains no business logic; it only converts data:

```ts
// Controller — converts HTTP request to Use Case input DTO, converts output to HTTP response
// orders/adapters/OrderController.ts
class OrderController {
  constructor(private placeOrder: PlaceOrderUseCase) {}

  async handlePlaceOrder(req: Request, res: Response): Promise<void> {
    try {
      // Adapter: HTTP request → Use Case input DTO
      const input: PlaceOrderInput = {
        customerId:      req.user.id,           // from auth middleware
        items:           req.body.items,
        paymentToken:    req.body.paymentToken,
        shippingAddress: req.body.shippingAddress,
      };

      const output = await this.placeOrder.execute(input);

      // Adapter: Use Case output DTO → HTTP response
      res.status(201).json({
        success: true,
        data: {
          orderId:           output.orderId,
          total:             output.total,
          estimatedDelivery: output.estimatedDelivery,
        },
      });

    } catch (err) {
      // Adapter: domain errors → HTTP status codes
      if (err instanceof NotFoundError)              return void res.status(404).json({ error: err.message });
      if (err instanceof CustomerBannedError)        return void res.status(403).json({ error: err.message });
      if (err instanceof ManagerApprovalRequiredError) return void res.status(422).json({ error: err.message, requiresApproval: true });
      if (err instanceof PaymentDeclinedError)       return void res.status(402).json({ error: err.message });
      res.status(500).json({ error: "Internal server error" });
    }
  }
}

// Mapper — translates between domain entity and persistence record
// orders/infrastructure/OrderMapper.ts
class OrderMapper {
  // Persistence record → Domain entity
  static toDomain(record: OrderRecord & { items: OrderItemRecord[] }): Order {
    return Order.reconstitute({
      id:         new OrderId(record.id),
      customerId: new CustomerId(record.customerId),
      status:     record.status as OrderStatus,
      items:      record.items.map(OrderItemMapper.toDomain),
      createdAt:  record.createdAt,
    });
  }

  // Domain entity → Persistence record (no domain methods exposed to DB)
  static toPersistence(order: Order): OrderRecord {
    return {
      id:         order.id.value,
      customerId: order.customerId.value,
      status:     order.getStatus(),
      total:      order.getTotal().amount,
      currency:   order.getTotal().currency,
      createdAt:  order.getCreatedAt(),
      items:      order.getItems().map(OrderItemMapper.toPersistence),
    };
  }

  // Domain entity → API response DTO (for read-optimised endpoints)
  static toDto(order: Order): OrderDto {
    return {
      id:            order.id.value,
      status:        order.getStatus(),
      total:         order.getTotal().format(),
      itemCount:     order.getItems().length,
      createdAt:     order.getCreatedAt().toISOString(),
    };
  }
}
```

**Q11. How do you implement the composition root — the one place that knows about all concrete dependencies?**
A: The composition root is where all abstractions are wired to their concrete implementations. It is the only file in the application that imports from both the domain/application layer and the infrastructure layer simultaneously:
```ts
// main.ts — composition root, the only place with full visibility of all layers
import { PrismaClient }          from "@prisma/client";
import { createApp }             from "./infrastructure/express/createApp";

// Infrastructure — concrete implementations
import { PrismaOrderRepository }    from "./orders/infrastructure/PrismaOrderRepository";
import { PrismaProductRepository }  from "./products/infrastructure/PrismaProductRepository";
import { PrismaCustomerRepository } from "./identity/infrastructure/PrismaCustomerRepository";
import { StripePaymentGateway }     from "./payments/infrastructure/StripePaymentGateway";
import { ShipStationShippingService } from "./shipping/infrastructure/ShipStationShippingService";
import { RabbitMQEventBus }         from "./shared/infrastructure/RabbitMQEventBus";
import { RedisInventoryService }    from "./inventory/infrastructure/RedisInventoryService";

// Application — use cases (depend only on interfaces)
import { PlaceOrderUseCase }   from "./orders/application/PlaceOrderUseCase";
import { CancelOrderUseCase }  from "./orders/application/CancelOrderUseCase";
import { GetOrderUseCase }     from "./orders/application/GetOrderUseCase";
import { RegisterUserUseCase } from "./identity/application/RegisterUserUseCase";

// Interface Adapters
import { OrderController }     from "./orders/adapters/OrderController";
import { IdentityController }  from "./identity/adapters/IdentityController";

async function bootstrap(): Promise<void> {
  // Instantiate infrastructure
  const prisma    = new PrismaClient();
  const eventBus  = new RabbitMQEventBus(process.env.RABBITMQ_URL!);
  await eventBus.connect();

  // Wire repositories — concrete implementations of domain interfaces
  const orderRepo    = new PrismaOrderRepository(prisma, eventBus);
  const productRepo  = new PrismaProductRepository(prisma);
  const customerRepo = new PrismaCustomerRepository(prisma);

  // Wire ports — concrete implementations of application interfaces
  const payments   = new StripePaymentGateway(process.env.STRIPE_SECRET_KEY!);
  const shipping   = new ShipStationShippingService(process.env.SHIPSTATION_KEY!);
  const inventory  = new RedisInventoryService(process.env.REDIS_URL!);

  // Wire use cases — inject all dependencies
  const placeOrder  = new PlaceOrderUseCase(orderRepo, productRepo, inventory, payments, shipping, eventBus);
  const cancelOrder = new CancelOrderUseCase(orderRepo, inventory, payments, eventBus);
  const getOrder    = new GetOrderUseCase(orderRepo);
  const register    = new RegisterUserUseCase(customerRepo, eventBus);

  // Wire controllers — inject use cases
  const orderController    = new OrderController(placeOrder, cancelOrder, getOrder);
  const identityController = new IdentityController(register);

  // Wire Express routes — inject controllers
  const app = createApp({ orderController, identityController });

  const PORT = Number(process.env.PORT) || 3000;
  app.listen(PORT, () => console.log(`Server running on port ${PORT}`));

  // Graceful shutdown
  process.on("SIGTERM", async () => {
    await prisma.$disconnect();
    await eventBus.disconnect();
  });
}

bootstrap().catch(console.error);
```

## Section 5: Testing in Clean Architecture

**Q12. How does Clean Architecture enable each layer to be tested independently?**
A: Because each layer depends only on abstractions, each layer can be tested in complete isolation by replacing its dependencies with fakes:

```ts
// Domain layer — pure unit tests, zero infrastructure
describe("Order entity", () => {
  it("enforces invariant: cannot confirm empty order", () => {
    const order = Order.create(CustomerId.generate());
    expect(() => order.confirm()).toThrow(DomainError);
  });

  it("calculates total correctly across all items", () => {
    const order = Order.create(CustomerId.generate());
    order.addItem(fakeProduct({ price: Money.create(500, "INR") }), 3);
    order.addItem(fakeProduct({ price: Money.create(200, "INR") }), 2);
    expect(order.getTotal()).toEqual(Money.create(1900, "INR")); // 500×3 + 200×2
  });

  it("raises OrderConfirmedEvent when confirmed", () => {
    const order = Order.create(CustomerId.generate());
    order.addItem(fakeProduct(), 1);
    order.confirm();
    const events = order.pullEvents();
    expect(events).toContainEqual(expect.any(OrderConfirmedEvent));
  });
});

// Application layer — use case tests with fake repositories and ports
describe("PlaceOrderUseCase", () => {
  let useCase:     PlaceOrderUseCase;
  let orderRepo:   InMemoryOrderRepository;  // fake — no DB
  let productRepo: InMemoryProductRepository;
  let payments:    FakePaymentGateway;        // fake — no Stripe
  let inventory:   FakeInventoryService;
  let shipping:    FakeShippingService;
```

**Q13. What are "fake" implementations vs "mocks," and which does Clean Architecture favour for use case testing?**
A: The distinction matters significantly in Clean Architecture:

- **Mock** — a test double configured with expected calls (`jest.fn().mockResolvedValue(...)`). The test asserts that specific methods were called with specific arguments. Brittle — breaks when implementation details change even if behavior is correct.
- **Fake** — a working lightweight implementation of a domain interface (`InMemoryOrderRepository`). The test exercises the real behavior through the interface. Robust — tests behavior, not implementation.

Clean Architecture strongly favours **fakes** for use case tests because:
1. Fakes implement the same interface the domain defines — they validate that the interface contract is sufficient.
2. Fakes can be shared across many tests without coupling tests to implementation details.
3. Fakes accumulate state naturally (an in-memory repository grows as `save()` is called), enabling multi-step use case flows.

```ts
// Fake — a working in-memory implementation of the domain interface
class InMemoryOrderRepository implements OrderRepository {
  private store: Map<string, Order> = new Map();

  async findById(id: OrderId): Promise<Order | null> {
    return this.store.get(id.value) ?? null;
  }

  async findByCustomerId(customerId: CustomerId): Promise<Order[]> {
    return [...this.store.values()]
      .filter(o => o.customerId.equals(customerId));
  }

  async save(order: Order): Promise<void> {
    this.store.set(order.id.value, order);
  }

  async delete(id: OrderId): Promise<void> {
    this.store.delete(id.value);
  }

  nextId(): OrderId { return OrderId.generate(); }

  // Test helpers — not on the interface, only available in tests
  findAll(): Order[] { return [...this.store.values()]; }
  clear(): void      { this.store.clear(); }
  seed(order: Order): void { this.store.set(order.id.value, order); }
}
```

## Section 6: Common Pitfalls, Anti-Patterns & Real-World Considerations

**Q14. What is "Architecture Astronaut" risk, and when should you NOT use Clean Architecture?**
A: Architecture Astronautics is the trap of applying Clean Architecture — with its full ceremony of entities, use cases, repositories, mappers, ports, and adapters — to problems that don't need it. The overhead is real:

- A simple CRUD endpoint with no business logic doesn't benefit from an entity, a use case, a mapper, and a repository interface. It benefits from a thin controller calling a service calling an ORM.
- A startup's MVP where requirements change daily is harmed by a rigid layer structure that makes adding a field require edits in five places (entity, mapper, DTO, repository, test).

Clean Architecture earns its overhead when:
- The domain has genuine, complex, and evolving business rules.
- Multiple delivery mechanisms exist or are anticipated (REST API + GraphQL + CLI + message consumers).
- The system is expected to live and grow for years with many contributors.
- The infrastructure is genuinely likely to be swapped (e.g., migrating from one payment provider or database to another).

**Start lean, layer in the architecture as complexity demands it.** A `src/services/orderService.ts` that calls Prisma directly is perfectly correct for a new system. Extract the layers when the service's complexity warrants it — not on day one because the pattern says so.

**Q15. What is "anemic domain model," and why is it the most common Clean Architecture violation?**
A: An anemic domain model is one where entities are plain data containers (just properties, no methods) and all business logic lives in services. This superficially resembles Clean Architecture (there are entities, there are services) but violates it fundamentally — the entity has no behaviour, so domain invariants are enforced nowhere:

```ts
// Anemic Domain Model — entity is just a data bag
class Order {
  id:         string;
  customerId: string;
  status:     string;
  items:      OrderItem[];
  total:      number;
  // No methods — no invariants — no behaviour
}

// All logic in the service — which becomes a procedural script
class OrderService {
  confirm(order: Order): void {
    // Business rule scattered in a service, not on the entity
    if (order.items.length === 0) throw new Error("Empty order");
    order.status = "CONFIRMED"; // direct mutation — no encapsulation
  }

  cancel(order: Order): void {
    if (order.status === "DELIVERED") throw new Error("Cannot cancel");
    order.status = "CANCELLED";
  }

  // The service duplicates these checks everywhere they're needed
  requiresApproval(order: Order): boolean {
    return order.total > 100_000;
  }
}
```

The fix is to move domain logic back onto the entity where it belongs:
```ts
// Rich domain model — entity owns its invariants and behavior
class Order {
  private status: OrderStatus = "PENDING";
  private items:  OrderItem[] = [];

  confirm(): void {
    if (this.items.length === 0)
      throw new DomainError("Cannot confirm empty order"); // invariant on entity
    this.status = "CONFIRMED"; // controlled mutation through domain method
  }

  // Business rule lives on the entity — called anywhere it's needed
  requiresManagerApproval(): boolean {
    return this.getTotal().isGreaterThan(Money.create(100_000, "INR"));
  }
}
```

**Q16. What happens to Clean Architecture in a monorepo or microservices context?**
A: Clean Architecture scales naturally to both:

**Monorepo (multiple bounded contexts in one repo):**
```
packages/
  orders/           ← bounded context package
    src/
      domain/
      application/
      infrastructure/
    package.json
  payments/         ← separate bounded context package
    src/
      domain/
      application/
      infrastructure/
    package.json
  shared-kernel/    ← shared domain primitives (Money, UniqueId)
    src/
    package.json
  api-gateway/      ← composition root; imports from all context packages
    src/
      main.ts       ← only place with imports from all packages
    package.json
```

Each bounded context enforces its own Dependency Rule internally. The `api-gateway` is the composition root that wires them together. A change to the `payments` domain never compiles into `orders` — TypeScript's project references enforce the boundary at the package level.

**Microservices:**
Each microservice is a separate deployment of one bounded context. The Clean Architecture layers become:
- **Domain layer** — shared via a private npm package (the shared kernel), or duplicated intentionally per service.
- **Application layer** — the service's own use cases, not shared across services.
- **Interface Adapters** — the service's controllers, message consumers, gRPC handlers.
- **Infrastructure** — the service's own database, its own message queue connection.

Cross-service communication goes through the outermost layer via HTTP or messaging — never via domain layer imports. A microservice that imports another service's domain entity violates Clean Architecture (and microservice principles).

**Q17. How does Clean Architecture handle cross-cutting concerns like logging, tracing, and authentication?**
A: Cross-cutting concerns belong at the boundary — in the infrastructure layer for implementation, injected as abstractions into the application layer where needed:

```ts
// Domain layer — Logger interface (optional; many prefer to keep domain pure)
// shared/domain/Logger.ts
interface Logger {
  info(message: string, context?: object): void;
  warn(message: string, context?: object): void;
  error(message: string, error?: Error, context?: object): void;
}

// Application layer — use cases receive Logger through DI
class PlaceOrderUseCase {
  constructor(
    private readonly orders:  OrderRepository,
    private readonly payments: PaymentGateway,
    private readonly logger:  Logger  // injected abstraction
  ) {}

  async execute(input: PlaceOrderInput): Promise<PlaceOrderOutput> {
    this.logger.info("Placing order", { customerId: input.customerId });
    try {
      // ... use case logic
      this.logger.info("Order placed successfully", { orderId: order.id.value });
      return output;
    } catch (err) {
      this.logger.error("Order placement failed", err as Error, { customerId: input.customerId });
      throw err;
    }
  }
}

// Authentication — enforced in the Interface Adapters layer (middleware/guard), not use cases
// The use case receives a validated customerId — it doesn't do auth
// orders/adapters/middleware/authMiddleware.ts
const authMiddleware = (req: Request, res: Response, next: NextFunction) => {
  const token = req.headers.authorization?.split(" ")[1];
  if (!token) return res.status(401).json({ error: "Unauthorized" });
  try {
    req.user = jwtService.verify(token); // adapter: HTTP auth → user identity
    next();
  } catch { res.status(401).json({ error: "Invalid token" }); }
};

// Tracing — wraps use cases at the adapter level using Decorator pattern
class TracedPlaceOrderUseCase implements PlaceOrderUseCaseInterface {
  constructor(
    private inner:  PlaceOrderUseCase,
    private tracer: Tracer
  ) {}

  async execute(input: PlaceOrderInput): Promise<PlaceOrderOutput> {
    const span = this.tracer.startSpan("PlaceOrderUseCase.execute");
    span.setAttributes({ customerId: input.customerId });
    try {
      const result = await this.inner.execute(input);
      span.setStatus({ code: SpanStatusCode.OK });
      return result;
    } catch (err) {
      span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).message });
      throw err;
    } finally {
      span.end();
    }
  }
}

// Composition root — wraps use case with tracing transparently
const placeOrder = new TracedPlaceOrderUseCase(
  new PlaceOrderUseCase(orderRepo, payments, logger),
  tracer
);
```

## Section 7: Scenario / System Design Style Questions

**Q18. "A codebase has all its business logic in Express route handlers — 500-line files that call Prisma directly, format responses, validate input, and apply business rules all in one function. How do you migrate to Clean Architecture without stopping feature development?"**
A: Use the Strangler Fig pattern — introduce Clean Architecture alongside the existing code, migrating route by route:

**Phase 1 — Extract services (stop the bleeding):** Create service classes that move the business logic out of route handlers. The route handler becomes thin but still calls Prisma directly through the service.

**Phase 2 — Introduce domain entities:** Identify the core entities (`Order`, `User`) and move business rules from services onto the entities. Services become orchestrators.

**Phase 3 — Define repository interfaces:** Create interfaces in a `domain/` folder that describe what the services need from persistence. Rename the existing Prisma calls to implement these interfaces.

**Phase 4 — Extract use cases:** For each significant route handler, create a Use Case class. The route handler becomes a controller that maps HTTP → use case input → HTTP response.

**Phase 5 — Reorganise by domain:** Move files into the domain-screaming structure (`orders/`, `payments/`, `identity/`). Update imports. Enforce with ESLint `import/no-restricted-paths`.

```ts
// Before — 500-line route handler (current state)
app.post("/orders", async (req, res) => {
  const { customerId, items, paymentToken } = req.body;
  // validates input inline
  // queries prisma directly
  // calculates totals inline
  // calls stripe directly
  // sends confirmation email inline
  // formats response inline
});

// Phase 1 — thin handler, fat service (first migration step)
app.post("/orders", async (req, res) => {
  const result = await orderService.placeOrder(req.body); // extracted
  res.status(201).json(result);
});

// Phase 4 — clean controller delegating to use case (target state)
app.post("/orders", authMiddleware, async (req, res) => {
  const controller = new OrderController(placeOrderUseCase);
  await controller.handlePlaceOrder(req, res);
});
```

**Q19. "Your team is debating whether to use NestJS modules, decorators, and its DI container as the architectural backbone, or to keep NestJS only in the outermost layer and implement Clean Architecture manually. What's your recommendation?"**
A: This is a real and important architectural decision. The key question is: *how tightly does NestJS couple your domain and application layers to the framework?*

**If NestJS decorators (`@Injectable`, `@Module`) are on your use case classes and domain entities — that's a Clean Architecture violation.** Your use cases now depend on NestJS; you cannot run them in a non-NestJS context (CLI, test, Lambda) without the framework overhead.

The recommended approach — use NestJS as the framework layer only:
```ts
// ✗ — Use case coupled to NestJS via @Injectable
@Injectable() // NestJS decorator on application layer — violation
export class PlaceOrderUseCase {
  constructor(
    @InjectRepository(Order) private orderRepo: Repository<Order>, // TypeORM on domain ✗
  ) {}
}

// ✓ — Use case is a plain TypeScript class; NestJS wraps it at the outer layer
// application/PlaceOrderUseCase.ts — no NestJS imports
export class PlaceOrderUseCase {
  constructor(
    private readonly orders:   OrderRepository,   // domain interface
    private readonly payments: PaymentGateway
  ) {}
}

// infrastructure/nestjs/OrderModule.ts — NestJS knows about the use case, not vice versa
@Module({
  providers: [
    { provide: "OrderRepository", useClass: PrismaOrderRepository },
    { provide: "PaymentGateway",  useClass: StripePaymentGateway  },
    {
      provide:  PlaceOrderUseCase,
      useFactory: (repo: OrderRepository, payments: PaymentGateway) =>
        new PlaceOrderUseCase(repo, payments),  // plain class, no decorator
      inject:   ["OrderRepository", "PaymentGateway"],
    },
  ],
  controllers: [OrderController],
})
export class OrderModule {}
```

The practical trade-off: using NestJS's `@Injectable` on use cases reduces boilerplate significantly and works well for teams that will never leave NestJS. The purist approach preserves framework independence at the cost of more manual wiring. At 5 YOE, the right answer depends on the team, timeline, and real likelihood of framework migration — but knowing the trade-off is what the question is really asking.

**Q20. "How does Clean Architecture handle read-heavy operations — where the domain entity model is too expensive to load for list/reporting endpoints?"**
A: This is where **Command Query Responsibility Segregation (CQRS)** integrates naturally with Clean Architecture. Reads (queries) bypass the domain layer and go directly from the infrastructure to a read-optimised projection:

```ts
// Write side — full domain model enforces invariants
class PlaceOrderUseCase { /* loads full Order entity, enforces rules */ }

// Read side — bypasses domain model for performance
// Query goes directly from controller to read service to database
interface OrderSummaryQuery {
  customerId?: string;
  status?:     OrderStatus;
  dateFrom?:   Date;
  dateTo?:     Date;
  page:        number;
  pageSize:    number;
}

interface OrderSummaryDto {
  id:            string;
  status:        string;
  total:         string;
  customerName:  string;
  itemCount:     number;
  createdAt:     string;
}

// Read service — lives in the application layer but bypasses domain entities for reads
class OrderQueryService {
  constructor(private db: ReadDatabaseClient) {} // can be Prisma, a read replica, or Elasticsearch

  async listOrders(query: OrderSummaryQuery): Promise<PagedResult<OrderSummaryDto>> {
    // Direct SQL/ORM query — no Order entity loaded, no domain logic
    const rows = await this.db.$queryRaw<any[]>`
      SELECT
        o.id, o.status,
        (o.total / 100.0)::money::text AS total,
        c.name AS customer_name,
        COUNT(oi.id)::int AS item_count,
        o.created_at
      FROM orders o
      JOIN customers c ON c.id = o.customer_id
      JOIN order_items oi ON oi.order_id = o.id
      WHERE
        (${query.customerId} IS NULL OR o.customer_id = ${query.customerId})
        AND (${query.status} IS NULL OR o.status = ${query.status})
        AND (${query.dateFrom} IS NULL OR o.created_at >= ${query.dateFrom})
      GROUP BY o.id, c.name
      ORDER BY o.created_at DESC
      LIMIT ${query.pageSize} OFFSET ${(query.page - 1) * query.pageSize}
    `;

    return {
      items: rows.map(r => ({
        id:           r.id,
        status:       r.status,
        total:        r.total,
        customerName: r.customer_name,
        itemCount:    r.item_count,
        createdAt:    r.created_at.toISOString(),
      })),
      page:      query.page,
      pageSize:  query.pageSize,
      total:     await this.countOrders(query),
    };
  }
}

// Controller routes: POST /orders → PlaceOrderUseCase (write — full domain model)
//                    GET  /orders → OrderQueryService  (read — direct DB, no domain)
```

This hybrid — strict Clean Architecture on the write path, pragmatic direct reads on the query path — is the pattern used in production systems where list endpoints serve thousands of requests per second.

## Quick Comparison Table (good for a whiteboard summary)

| Layer | Contains | Depends on | Framework dependency | Test type |
|---|---|---|---|---|
| **Entities (Domain)** | Entities, value objects, domain events, repo interfaces, domain errors | Nothing — innermost | None | Pure unit tests |
| **Use Cases (Application)** | Use case classes, DTOs, port interfaces, application services | Domain layer only | None | Unit tests with fakes |
| **Interface Adapters** | Controllers, presenters, mappers, repo implementations | Use Cases + Domain | Minimal (route handlers) | Integration tests |
| **Frameworks & Infrastructure** | ORM config, SDK clients, DI container, HTTP server | All layers | Full | E2E + integration tests |

## Dependency Rule Violations — Quick Reference

| Symptom | Violation | Fix |
|---|---|---|
| Domain entity imports `PrismaClient` | Innermost layer knows outermost | Move Prisma to infrastructure; inject via interface |
| Use case imports `Express.Request` | Application layer knows HTTP framework | Controller maps HTTP → DTO; use case receives DTO only |
| Entity has `@Injectable()` decorator | Domain knows NestJS | Remove decorator; wire in NestJS module provider factory |
| Service calls `fetch` or `axios` directly | Application layer knows HTTP transport | Extract interface; inject HTTP client as port |
| Controller contains business rule (`if total > 100000`) | Adapter layer contains domain logic | Move rule to entity method |
| Mapper imports domain entity AND Prisma in same file | Adapter knows both domain and infra | Expected — mappers live in the adapter layer and translate between the two |
| Use case returns raw Prisma object | Application layer exposes infrastructure type | Map to DTO in use case output or in mapper |

---

**Tip for the interview:** At the 5 YOE level, "what is Clean Architecture" never comes as a definition — it surfaces as: why is this route handler impossible to unit test (business logic coupled to Express and Prisma), how would you structure a new service so we can swap the database later (Dependency Rule + repository interface), how do you handle list endpoints that don't need the full domain model (CQRS read path bypasses domain), or how do you add tracing without modifying every use case (Decorator pattern at the composition root). The sharp answer names the Dependency Rule as the single load-bearing constraint (not the layers themselves), immediately shows what it means in a real TypeScript file (domain entity has zero framework imports, use case has zero Prisma imports), discusses the anemic domain model as the most common violation (logic in services, not entities), and explains where to draw the pragmatic line (don't apply full ceremony to CRUD endpoints; apply it where business rules are genuinely complex and evolving). Knowing the CQRS read-path shortcut — "reads bypass the domain model and go straight to a query service" — is the production-system depth that lands at 5 YOE.
