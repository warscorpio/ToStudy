# JavaScript / TypeScript (Enterprise & Architectural Patterns): MVVM (Model-View-ViewModel) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is MVVM?**
A: MVVM (Model-View-ViewModel) is an architectural pattern that structures UI-driven applications into three distinct layers:

- **Model** — the domain data and business logic layer. It holds raw data, enforces business rules, performs validation, and communicates with external services (APIs, databases). The Model is completely unaware of how it is displayed. It does not import or reference any UI framework.
- **View** — the UI layer. It renders what the user sees and forwards user interactions (clicks, input, gestures) upward. In modern JavaScript, the View is typically declarative — a React component, an Angular template, a Vue SFC template. The View binds to the ViewModel and reflects its state; it contains no business logic.
- **ViewModel** — the mediator and state manager between Model and View. It exposes data in a shape the View can directly bind to (formatted strings, booleans for visibility, derived computations), handles user commands from the View, and delegates to the Model for business operations. The ViewModel has no reference to any View — it is entirely unaware of the DOM or UI framework.

The defining characteristic of MVVM is **data binding**: the View automatically reflects ViewModel state without the ViewModel explicitly calling into the View. This is what separates MVVM from MVP (where the Presenter explicitly updates the View) and MVC (where the Controller does not own display state).

**Q2. Where did MVVM originate, and why is it relevant in JavaScript?**
A: MVVM was introduced by John Gossman at Microsoft in 2005 for WPF (Windows Presentation Foundation) and Silverlight, where two-way data binding between XAML templates and C# ViewModels was a platform feature. The pattern became relevant in JavaScript as front-end frameworks evolved to support declarative, reactive data binding:

- **Knockout.js (2010)** — the first major JavaScript MVVM framework, with explicit `ko.observable()` bindings.
- **AngularJS (2010)** — popularised two-way binding with `ng-model` in JavaScript.
- **Vue.js (2014)** — explicitly described itself as an MVVM framework; `data()` is the ViewModel, the template is the View.
- **React (2013)** — doesn't self-describe as MVVM but implements the pattern: component state/props + hooks = ViewModel; JSX = View; the React component is the natural MVVM unit.
- **Angular (2016+)** — TypeScript-first, with explicit `@Component` (View + ViewModel) and `@Injectable` services (Model).

At 5 YOE, MVVM matters because it describes *why* React hooks, Vue composables, and Angular component classes are designed the way they are — and because violating the pattern (putting API calls in JSX, or business logic in a template) produces the anti-patterns every senior engineer is asked to review and fix.

**Q3. What is the single most important distinction between MVVM, MVC, and MVP?**
A: The distinguishing factor is **who updates the View** and **how**:

| Aspect | MVC | MVP | MVVM |
|---|---|---|---|
| **Controller/Presenter/ViewModel knows the View?** | Controller knows the View (loosely) | Presenter holds a reference to the View interface | ViewModel has NO reference to the View |
| **How View is updated** | Controller manipulates View directly or via Model notifications | Presenter explicitly calls View methods (`view.showError()`) | Data binding — View observes ViewModel state reactively |
| **Data flow** | Bidirectional, often loose | Presenter ↔ View through an interface | ViewModel → View (one-way reactive) or two-way binding |
| **Testability of Presenter/ViewModel** | Medium — Controller may depend on View | High — Presenter talks to a View interface (mockable) | Highest — ViewModel has no UI dependency at all |
| **Typical JS expression** | Express.js routes + template rendering | React class components with explicit `setState` calls | React hooks / Vue composables / Angular component classes |

The key MVVM insight: because the ViewModel does not know the View, it can be tested with pure JavaScript — no DOM, no rendering, no browser. This is MVVM's primary engineering benefit over MVC and MVP.

**Q4. What is data binding, and what are the two forms of it in MVVM?**
A: Data binding is the mechanism by which the View automatically reflects ViewModel state — and optionally, how user input in the View automatically updates the ViewModel — without either side calling the other explicitly.

- **One-way binding (ViewModel → View)** — ViewModel state changes cause the View to re-render. The View is a pure function of ViewModel state. Used in React's unidirectional data flow: `state` → JSX renders → DOM updates. Input changes do not automatically write back to state; the View must raise an event.

- **Two-way binding (ViewModel ↔ View)** — ViewModel state drives the View AND user input in the View automatically updates the ViewModel state. Classic form elements with Angular's `[(ngModel)]` or Vue's `v-model`. More convenient for forms; harder to debug because data can flow in both directions.

```ts
// One-way binding (React) — ViewModel state → View, View raises events back
function SearchInput({ value, onChange }: { value: string; onChange: (v: string) => void }) {
  return (
    <input
      value={value}           // ViewModel → View (one-way read)
      onChange={e => onChange(e.target.value)} // View → ViewModel via event
    />
  );
}

// Two-way binding (Vue v-model equivalent) — ViewModel ↔ View
// <input v-model="searchQuery" />
// Equivalent to: <input :value="searchQuery" @input="searchQuery = $event.target.value" />
```

**Q5. What does the ViewModel own, and what does it explicitly NOT own?**
A: Understanding this boundary is the core of MVVM architecture:

**ViewModel owns:**
- UI state — loading flags, error messages, selected items, pagination page number, sort direction.
- Derived / formatted data — `fullName` computed from `firstName + lastName`, `formattedPrice` from `price * quantity`, `isSubmitDisabled` from form validation state.
- Commands — methods the View calls for user actions: `onSearchChanged()`, `onSubmitClicked()`, `onPageChanged()`.
- Orchestration — calls Model methods and maps results to UI state.
- Validation logic for display — "is this field in error?" (not the same as domain validation in the Model).

**ViewModel does NOT own:**
- DOM references, CSS classes, or render logic.
- Raw business rules (e.g., "an order over ₹10,000 requires manager approval" — that's Model territory).
- Direct HTTP calls or database queries — those belong in services (the Model layer).
- Framework-specific rendering code — no JSX, no Angular templates, no Vue render functions.

## Section 2: Implementing MVVM in React

**Q6. How does the MVVM pattern map to React hooks — what is the ViewModel in React?**
A: In React, a custom hook is the natural ViewModel. The hook encapsulates all UI state and logic; the component (JSX) is the pure View:

```ts
// Model — domain service, no UI dependency
class ProductService {
  async searchProducts(query: string, filters: ProductFilters): Promise<Product[]> {
    const params = new URLSearchParams({ q: query, ...filters });
    const response = await fetch(`/api/products?${params}`);
    if (!response.ok) throw new Error(`Search failed: ${response.statusText}`);
    return response.json();
  }
}

// ViewModel — custom hook, no JSX, no DOM, fully testable
function useProductSearch(service: ProductService) {
  const [query,    setQuery]    = useState("");
  const [filters,  setFilters]  = useState<ProductFilters>({});
  const [products, setProducts] = useState<Product[]>([]);
  const [isLoading,setIsLoading]= useState(false);
  const [error,    setError]    = useState<string | null>(null);
  const [page,     setPage]     = useState(1);
  const PAGE_SIZE = 20;

  // Derived state — computed from raw ViewModel state
  const hasResults      = products.length > 0;
  const isEmpty         = !isLoading && !error && query.length > 0 && !hasResults;
  const paginatedItems  = products.slice((page - 1) * PAGE_SIZE, page * PAGE_SIZE);
  const totalPages      = Math.ceil(products.length / PAGE_SIZE);
  const canGoNext       = page < totalPages;
  const canGoPrev       = page > 1;

  // Commands — what the View calls for user actions
  const handleSearch = useCallback(async (newQuery: string) => {
    setQuery(newQuery);
    setPage(1);
    if (!newQuery.trim()) { setProducts([]); return; }

    setIsLoading(true);
    setError(null);
    try {
      const results = await service.searchProducts(newQuery, filters);
      setProducts(results);
    } catch (err) {
      setError(err instanceof Error ? err.message : "Search failed");
      setProducts([]);
    } finally {
      setIsLoading(false);
    }
  }, [service, filters]);

  const handleFilterChange = useCallback((newFilters: ProductFilters) => {
    setFilters(newFilters);
    if (query) handleSearch(query); // re-search with new filters
  }, [query, handleSearch]);

  const handlePageChange = useCallback((newPage: number) => {
    setPage(newPage);
    window.scrollTo(0, 0);
  }, []);

  // ViewModel exposes: state + derived values + commands — nothing else
  return {
    // State
    query, isLoading, error,
    // Derived
    hasResults, isEmpty, paginatedItems, totalPages, canGoNext, canGoPrev, page,
    // Commands
    handleSearch, handleFilterChange, handlePageChange,
  };
}

// View — pure JSX, zero logic, zero state, zero service calls
function ProductSearchPage() {
  const vm = useProductSearch(new ProductService());

  return (
    <div className="product-search">
      <SearchBar value={vm.query} onSearch={vm.handleSearch} disabled={vm.isLoading} />
      <FilterPanel onFilterChange={vm.handleFilterChange} />

      {vm.isLoading && <Spinner />}
      {vm.error    && <ErrorBanner message={vm.error} />}
      {vm.isEmpty  && <EmptyState query={vm.query} />}

      {vm.hasResults && (
        <>
          <ProductGrid products={vm.paginatedItems} />
          <Pagination
            currentPage={vm.page}
            totalPages={vm.totalPages}
            canGoNext={vm.canGoNext}
            canGoPrev={vm.canGoPrev}
            onPageChange={vm.handlePageChange}
          />
        </>
      )}
    </div>
  );
}
```

**Q7. How do you make the ViewModel independently testable without rendering the View?**
A: Because the ViewModel is a plain hook with no JSX or DOM dependency, it can be tested with `renderHook` from React Testing Library — or in a pure Node environment for framework-agnostic ViewModels:

```ts
import { renderHook, act } from "@testing-library/react";

describe("useProductSearch ViewModel", () => {
  let mockService: jest.Mocked<ProductService>;

  beforeEach(() => {
    mockService = {
      searchProducts: jest.fn(),
    } as unknown as jest.Mocked<ProductService>;
  });

  it("initialises with empty state", () => {
    const { result } = renderHook(() => useProductSearch(mockService));

    expect(result.current.query).toBe("");
    expect(result.current.products).toEqual([]);  // via paginatedItems
    expect(result.current.isLoading).toBe(false);
    expect(result.current.error).toBeNull();
    expect(result.current.hasResults).toBe(false);
  });

  it("sets loading true during search and false after", async () => {
    mockService.searchProducts.mockResolvedValue([fakeProduct]);
    const { result } = renderHook(() => useProductSearch(mockService));

    act(() => { result.current.handleSearch("laptop"); });
    expect(result.current.isLoading).toBe(true);

    await act(async () => { /* wait for promise */ });
    expect(result.current.isLoading).toBe(false);
  });

  it("exposes error message when search fails", async () => {
    mockService.searchProducts.mockRejectedValue(new Error("Network error"));
    const { result } = renderHook(() => useProductSearch(mockService));

    await act(async () => { result.current.handleSearch("laptop"); });

    expect(result.current.error).toBe("Network error");
    expect(result.current.hasResults).toBe(false);
  });

  it("computes isEmpty correctly when query returns no results", async () => {
    mockService.searchProducts.mockResolvedValue([]);
    const { result } = renderHook(() => useProductSearch(mockService));

    await act(async () => { result.current.handleSearch("xyzzy"); });

    expect(result.current.isEmpty).toBe(true);
    expect(result.current.hasResults).toBe(false);
    expect(result.current.error).toBeNull();
  });

  it("resets to page 1 on new search", async () => {
    mockService.searchProducts.mockResolvedValue(Array(50).fill(fakeProduct));
    const { result } = renderHook(() => useProductSearch(mockService));

    await act(async () => { result.current.handleSearch("laptop"); });
    act(() => result.current.handlePageChange(3));
    expect(result.current.page).toBe(3);

    await act(async () => { result.current.handleSearch("tablet"); });
    expect(result.current.page).toBe(1); // reset on new search
  });
});
```

**Q8. How do you implement a form with complex validation using MVVM in React?**
A:
```ts
// Model — domain validation rules (pure functions, no UI)
const UserRegistrationRules = {
  validateEmail: (email: string): string | null => {
    if (!email)               return "Email is required";
    if (!email.includes("@")) return "Invalid email format";
    return null;
  },
  validatePassword: (password: string): string | null => {
    if (password.length < 8)               return "Minimum 8 characters";
    if (!/[A-Z]/.test(password))           return "Must contain uppercase letter";
    if (!/[0-9]/.test(password))           return "Must contain a number";
    return null;
  },
  validatePasswordConfirm: (password: string, confirm: string): string | null => {
    if (password !== confirm) return "Passwords do not match";
    return null;
  },
};

type RegistrationFormState = {
  email:           string;
  password:        string;
  confirmPassword: string;
  name:            string;
};

// ViewModel — form state, validation state, submission command
function useRegistrationForm(authService: AuthService) {
  const [fields, setFields] = useState<RegistrationFormState>({
    email: "", password: "", confirmPassword: "", name: "",
  });
  const [touched, setTouched] = useState<Partial<Record<keyof RegistrationFormState, boolean>>>({});
  const [isSubmitting, setIsSubmitting] = useState(false);
  const [submitError,  setSubmitError]  = useState<string | null>(null);
  const [isSuccess,    setIsSuccess]    = useState(false);

  // Derived — validation errors computed from Model rules
  const errors = useMemo(() => ({
    email:           UserRegistrationRules.validateEmail(fields.email),
    password:        UserRegistrationRules.validatePassword(fields.password),
    confirmPassword: UserRegistrationRules.validatePasswordConfirm(
                       fields.password, fields.confirmPassword),
    name:            fields.name.trim() ? null : "Name is required",
  }), [fields]);

  // Derived — only show errors for touched fields (UX best practice)
  const visibleErrors = useMemo(() => ({
    email:           touched.email           ? errors.email           : null,
    password:        touched.password        ? errors.password        : null,
    confirmPassword: touched.confirmPassword ? errors.confirmPassword : null,
    name:            touched.name            ? errors.name            : null,
  }), [errors, touched]);

  // Derived — form-level state
  const isFormValid      = Object.values(errors).every(e => e === null);
  const isSubmitDisabled = !isFormValid || isSubmitting;

  // Commands
  const handleFieldChange = useCallback((field: keyof RegistrationFormState, value: string) => {
    setFields(prev => ({ ...prev, [field]: value }));
  }, []);

  const handleFieldBlur = useCallback((field: keyof RegistrationFormState) => {
    setTouched(prev => ({ ...prev, [field]: true }));
  }, []);

  const handleSubmit = useCallback(async () => {
    // Mark all fields touched on submit attempt
    setTouched({ email: true, password: true, confirmPassword: true, name: true });

    if (!isFormValid) return;

    setIsSubmitting(true);
    setSubmitError(null);
    try {
      await authService.register(fields);
      setIsSuccess(true);
    } catch (err) {
      setSubmitError(err instanceof Error ? err.message : "Registration failed");
    } finally {
      setIsSubmitting(false);
    }
  }, [fields, isFormValid, authService]);

  return {
    fields, visibleErrors, isFormValid,
    isSubmitting, isSubmitDisabled, submitError, isSuccess,
    handleFieldChange, handleFieldBlur, handleSubmit,
  };
}

// View — pure rendering, all logic delegated to ViewModel
function RegistrationForm() {
  const vm = useRegistrationForm(new AuthService());

  if (vm.isSuccess) return <SuccessBanner />;

  return (
    <form onSubmit={e => { e.preventDefault(); vm.handleSubmit(); }}>
      <TextField
        label="Full Name" value={vm.fields.name}
        error={vm.visibleErrors.name}
        onChange={v => vm.handleFieldChange("name", v)}
        onBlur={() => vm.handleFieldBlur("name")}
      />
      <TextField
        label="Email" type="email" value={vm.fields.email}
        error={vm.visibleErrors.email}
        onChange={v => vm.handleFieldChange("email", v)}
        onBlur={() => vm.handleFieldBlur("email")}
      />
      <TextField
        label="Password" type="password" value={vm.fields.password}
        error={vm.visibleErrors.password}
        onChange={v => vm.handleFieldChange("password", v)}
        onBlur={() => vm.handleFieldBlur("password")}
      />
      <TextField
        label="Confirm Password" type="password" value={vm.fields.confirmPassword}
        error={vm.visibleErrors.confirmPassword}
        onChange={v => vm.handleFieldChange("confirmPassword", v)}
        onBlur={() => vm.handleFieldBlur("confirmPassword")}
      />
      {vm.submitError && <ErrorMessage text={vm.submitError} />}
      <Button type="submit" disabled={vm.isSubmitDisabled} loading={vm.isSubmitting}>
        {vm.isSubmitting ? "Creating account..." : "Create Account"}
      </Button>
    </form>
  );
}
```

## Section 3: Implementing MVVM in Vue and Angular

**Q9. How does MVVM map to Vue 3 Composition API?**
A: Vue 3's Composition API is the most explicit MVVM expression in the JavaScript ecosystem — Vue's own documentation uses the MVVM vocabulary directly:

```ts
// Model — plain TypeScript service, no Vue dependency
class CartService {
  private items: CartItem[] = [];

  addItem(product: Product, quantity: number): void {
    const existing = this.items.find(i => i.productId === product.id);
    if (existing) { existing.quantity += quantity; }
    else { this.items.push({ productId: product.id, name: product.name,
                              price: product.price, quantity }); }
  }

  removeItem(productId: string): void {
    this.items = this.items.filter(i => i.productId !== productId);
  }

  getItems(): CartItem[] { return [...this.items]; }
  getTotal(): number { return this.items.reduce((sum, i) => sum + i.price * i.quantity, 0); }
}

// ViewModel — Vue composable (useCart), no template dependency
// composables/useCart.ts
import { ref, computed, readonly } from "vue";

export function useCart(service: CartService) {
  const items        = ref<CartItem[]>(service.getItems());
  const isCheckingOut = ref(false);
  const checkoutError = ref<string | null>(null);

  // Derived — computed properties the template binds to
  const total          = computed(() => service.getTotal());
  const itemCount      = computed(() => items.value.reduce((sum, i) => sum + i.quantity, 0));
  const isEmpty        = computed(() => items.value.length === 0);
  const formattedTotal = computed(() =>
    new Intl.NumberFormat("en-IN", { style: "currency", currency: "INR" }).format(total.value)
  );
  const canCheckout    = computed(() => !isEmpty.value && !isCheckingOut.value);

  // Commands — methods the template calls
  function addToCart(product: Product, quantity = 1): void {
    service.addItem(product, quantity);
    items.value = service.getItems(); // sync reactive state from model
  }

  function removeFromCart(productId: string): void {
    service.removeItem(productId);
    items.value = service.getItems();
  }

  async function checkout(paymentToken: string): Promise<void> {
    if (!canCheckout.value) return;
    isCheckingOut.value = true;
    checkoutError.value = null;
    try {
      await checkoutApi.process({ items: items.value, paymentToken });
      items.value = [];
    } catch (err) {
      checkoutError.value = err instanceof Error ? err.message : "Checkout failed";
    } finally {
      isCheckingOut.value = false;
    }
  }

  return {
    // Expose readonly state — View cannot mutate directly
    items:          readonly(items),
    isCheckingOut:  readonly(isCheckingOut),
    checkoutError:  readonly(checkoutError),
    // Computed
    total, itemCount, isEmpty, formattedTotal, canCheckout,
    // Commands
    addToCart, removeFromCart, checkout,
  };
}

// View — Vue SFC template, binds to ViewModel via useCart()
```

**Q10. How does MVVM map to Angular's component architecture?**
A: Angular makes MVVM most explicit — the framework's architecture prescribes the separation:

```ts
// Model — Angular Injectable service (the domain layer)
@Injectable({ providedIn: "root" })
export class OrderService {
  constructor(private http: HttpClient) {}

  getOrders(filter: OrderFilter): Observable<Order[]> {
    return this.http.get<Order[]>("/api/orders", { params: { ...filter } }).pipe(
      map(orders => orders.sort((a, b) =>
        new Date(b.createdAt).getTime() - new Date(a.createdAt).getTime()
      ))
    );
  }

  cancelOrder(orderId: string): Observable<void> {
    return this.http.delete<void>(`/api/orders/${orderId}`);
  }
}

// ViewModel — Angular Component class (the TS class, not the template)
@Component({
  selector:    "app-order-list",
  templateUrl: "./order-list.component.html",
  changeDetection: ChangeDetectionStrategy.OnPush, // only update on input/observable change
})
export class OrderListComponent implements OnInit, OnDestroy {
  // ViewModel state — exposed to template via binding
  orders$:      Observable<Order[]>;
  isLoading$:   BehaviorSubject<boolean>   = new BehaviorSubject(false);
  error$:       BehaviorSubject<string | null> = new BehaviorSubject<string | null>(null);
  filter:       OrderFilter = { status: "all", page: 1 };
  selectedIds:  Set<string> = new Set();

  // Derived — ViewModel computes display-ready values
  get hasSelection(): boolean  { return this.selectedIds.size > 0; }
  get selectionCount(): number { return this.selectedIds.size; }

  private destroy$ = new Subject<void>();

  constructor(private orderService: OrderService) {}

  ngOnInit(): void {
    this.loadOrders();
  }

  // Commands — template calls these on user interaction
  onFilterChange(filter: Partial<OrderFilter>): void {
    this.filter = { ...this.filter, ...filter, page: 1 };
    this.loadOrders();
  }

  onPageChange(page: number): void {
    this.filter = { ...this.filter, page };
    this.loadOrders();
  }

  onSelectOrder(orderId: string, selected: boolean): void {
    selected ? this.selectedIds.add(orderId) : this.selectedIds.delete(orderId);
    this.selectedIds = new Set(this.selectedIds); // trigger change detection
  }

  onCancelSelected(): void {
    const ids = [...this.selectedIds];
    forkJoin(ids.map(id => this.orderService.cancelOrder(id))).pipe(
      takeUntil(this.destroy$)
    ).subscribe({
      next:  () => { this.selectedIds.clear(); this.loadOrders(); },
      error: (err) => this.error$.next(err.message),
    });
  }

  private loadOrders(): void {
    this.isLoading$.next(true);
    this.error$.next(null);
    this.orders$ = this.orderService.getOrders(this.filter).pipe(
      tap({ error: (err) => {
        this.error$.next(err.message);
        this.isLoading$.next(false);
      }}),
      finalize(() => this.isLoading$.next(false)),
      takeUntil(this.destroy$)
    );
  }

  ngOnDestroy(): void { this.destroy$.next(); this.destroy$.complete(); }
}

/* View — Angular template binds to ViewModel properties
  order-list.component.html:

  <app-filter-bar [filter]="filter" (filterChange)="onFilterChange($event)"></app-filter-bar>

  <ng-container *ngIf="isLoading$ | async"><app-spinner /></ng-container>
  <app-error-banner *ngIf="error$ | async as err" [message]="err"></app-error-banner>

  <app-order-table
    [orders]="orders$ | async"
    [selectedIds]="selectedIds"
    (selectionChange)="onSelectOrder($event.id, $event.selected)"
  ></app-order-table>

  <button [disabled]="!hasSelection" (click)="onCancelSelected()">
    Cancel {{ selectionCount }} order(s)
  </button>

  <app-pagination [filter]="filter" (pageChange)="onPageChange($event)"></app-pagination>
*/
```

## Section 4: MVVM with State Management

**Q11. How does MVVM interact with global state management libraries like Redux or Zustand?**
A: In applications with a global state store, the architecture is layered — the store is part of the Model layer; the ViewModel selects, transforms, and exposes store state to the View:

```
View (React component / JSX)
    ↕ binds to
ViewModel (custom hook — selects + transforms store state, dispatches actions)
    ↕ reads/writes
Store (Redux / Zustand — global Model layer)
    ↕ calls
Services (API clients, domain logic — inner Model layer)
```

```ts
// Store (Zustand) — Model layer, holds domain state
interface OrderStore {
  orders:    Order[];
  isLoading: boolean;
  error:     string | null;
  filter:    OrderFilter;

  // Actions — Model-level operations
  fetchOrders:  (filter: OrderFilter) => Promise<void>;
  cancelOrder:  (id: string) => Promise<void>;
  setFilter:    (filter: Partial<OrderFilter>) => void;
}

const useOrderStore = create<OrderStore>((set, get) => ({
  orders: [], isLoading: false, error: null,
  filter: { status: "all", page: 1 },

  fetchOrders: async (filter) => {
    set({ isLoading: true, error: null });
    try {
      const orders = await orderApi.list(filter);
      set({ orders, isLoading: false });
    } catch (err) {
      set({ error: (err as Error).message, isLoading: false });
    }
  },
  cancelOrder: async (id) => {
    await orderApi.cancel(id);
    await get().fetchOrders(get().filter); // refresh
  },
  setFilter: (filter) => set(s => ({ filter: { ...s.filter, ...filter } })),
}));

// ViewModel — selects from store, adds display-specific logic
function useOrderListViewModel() {
  const { orders, isLoading, error, filter, fetchOrders, cancelOrder, setFilter }
    = useOrderStore();

  const [selectedIds, setSelectedIds] = useState<Set<string>>(new Set());

  // Derived — ViewModel adds display-ready data the store doesn't hold
  const isEmpty      = !isLoading && orders.length === 0;
  const hasSelection = selectedIds.size > 0;
  const totalAmount  = useMemo(() =>
    orders.reduce((sum, o) => sum + o.total, 0), [orders]
  );
  const formattedTotal = new Intl.NumberFormat("en-IN", {
    style: "currency", currency: "INR"
  }).format(totalAmount);

  // Commands
  const handleFilterChange = useCallback((partial: Partial<OrderFilter>) => {
    setFilter(partial);
    fetchOrders({ ...filter, ...partial });
  }, [filter, setFilter, fetchOrders]);

  const handleSelectOrder = useCallback((id: string, selected: boolean) => {
    setSelectedIds(prev => {
      const next = new Set(prev);
      selected ? next.add(id) : next.delete(id);
      return next;
    });
  }, []);

  const handleCancelSelected = useCallback(async () => {
    for (const id of selectedIds) await cancelOrder(id);
    setSelectedIds(new Set());
  }, [selectedIds, cancelOrder]);

  useEffect(() => { fetchOrders(filter); }, []); // initial load

  return {
    orders, isLoading, error, filter, isEmpty,
    hasSelection, selectedIds, formattedTotal,
    handleFilterChange, handleSelectOrder, handleCancelSelected,
  };
}
```

**Q12. How do you handle side effects in the ViewModel — such as navigation, analytics, and toasts — without coupling it to the View?**
A: Side effects that are not UI rendering belong in the ViewModel, but they should be injected as abstractions rather than imported as concrete implementations:

```ts
// Abstractions — injected into ViewModel, mockable in tests
interface NavigationService { navigate(path: string): void; }
interface ToastService      { show(message: string, type: "success" | "error"): void; }
interface AnalyticsService  { track(event: string, properties?: object): void; }

// ViewModel — side effects via injected services, not direct imports
function useOrderPlacement(
  orderService: OrderService,
  navigation:  NavigationService,
  toast:       ToastService,
  analytics:   AnalyticsService
) {
  const [isSubmitting, setIsSubmitting] = useState(false);

  const handlePlaceOrder = useCallback(async (dto: PlaceOrderDto) => {
    setIsSubmitting(true);
    try {
      const order = await orderService.place(dto);

      // Side effects — called through injected abstractions, not direct imports
      analytics.track("order_placed", { orderId: order.id, total: order.total });
      toast.show(`Order #${order.id} placed successfully!`, "success");
      navigation.navigate(`/orders/${order.id}/confirmation`);

    } catch (err) {
      const message = err instanceof Error ? err.message : "Order failed";
      toast.show(message, "error");
      analytics.track("order_failed", { error: message });
    } finally {
      setIsSubmitting(false);
    }
  }, [orderService, navigation, toast, analytics]);

  return { isSubmitting, handlePlaceOrder };
}

// In tests — inject mocks, verify side effects were called correctly
it("navigates to confirmation on success", async () => {
  const mockNav      = { navigate: jest.fn() };
  const mockToast    = { show: jest.fn() };
  const mockAnalytics = { track: jest.fn() };
  const mockService  = { place: jest.fn().mockResolvedValue({ id: "ORD-1", total: 1000 }) };

  const { result } = renderHook(() =>
    useOrderPlacement(mockService, mockNav, mockToast, mockAnalytics)
  );

  await act(async () => { result.current.handlePlaceOrder(orderDto); });

  expect(mockNav.navigate).toHaveBeenCalledWith("/orders/ORD-1/confirmation");
  expect(mockToast.show).toHaveBeenCalledWith(expect.stringContaining("ORD-1"), "success");
  expect(mockAnalytics.track).toHaveBeenCalledWith("order_placed", expect.any(Object));
});
```

## Section 5: MVVM Anti-Patterns and Pitfalls

**Q13. What are the most common MVVM violations in React codebases, and how do you fix them?**
A: Four patterns appear repeatedly in code reviews:

**Violation 1 — Business logic in the View (JSX)**
```tsx
// ✗ — price calculation and tax logic inside JSX
function OrderSummary({ items }: { items: OrderItem[] }) {
  const subtotal = items.reduce((sum, i) => sum + i.price * i.qty, 0);
  const tax      = subtotal * 0.18; // GST — business rule in the View!
  const total    = subtotal + tax;
  const discount = total > 10000 ? total * 0.05 : 0; // domain rule in JSX!

  return <div>Total: ₹{(total - discount).toFixed(2)}</div>;
}

// ✓ — business logic in ViewModel (hook), View only renders
function useOrderSummary(items: OrderItem[], pricingService: PricingService) {
  return useMemo(() => pricingService.calculate(items), [items, pricingService]);
  // pricingService.calculate() applies tax, discounts — domain logic in the Model
}

function OrderSummary({ items }: { items: OrderItem[] }) {
  const vm = useOrderSummary(items, pricingService);
  return <div>Total: {vm.formattedTotal}</div>; // pure rendering
}
```

**Violation 2 — API calls directly in the component body**
```tsx
// ✗ — API call in the component
function UserProfile({ userId }: { userId: string }) {
  const [user, setUser] = useState<User | null>(null);
  useEffect(() => {
    fetch(`/api/users/${userId}`).then(r => r.json()).then(setUser); // API in View! ✗
  }, [userId]);
  return <div>{user?.name}</div>;
}

// ✓ — API call in ViewModel hook
function useUserProfile(userId: string, userService: UserService) {
  const [user, setUser]         = useState<User | null>(null);
  const [isLoading, setLoading] = useState(true);
  const [error, setError]       = useState<string | null>(null);

  useEffect(() => {
    setLoading(true);
    userService.getById(userId)
      .then(setUser)
      .catch(e => setError(e.message))
      .finally(() => setLoading(false));
  }, [userId, userService]);

  return { user, isLoading, error, displayName: user?.name ?? "Unknown" };
}

function UserProfile({ userId }: { userId: string }) {
  const vm = useUserProfile(userId, userService);
  if (vm.isLoading) return <Spinner />;
  if (vm.error)     return <Error message={vm.error} />;
  return <div>{vm.displayName}</div>;
}
```

**Violation 3 — Raw domain objects passed directly to Views**
```tsx
// ✗ — View receives raw domain object and formats it inline
function OrderCard({ order }: { order: Order }) {
  return (
    <div>
      {/* View doing formatting — belongs in ViewModel */}
      <p>{new Date(order.createdAt).toLocaleDateString("en-IN")}</p>
      <p>₹{(order.total / 100).toFixed(2)}</p>
      <p>{order.status.replace(/_/g, " ").toLowerCase()}</p>
    </div>
  );
}

// ✓ — ViewModel formats; View renders strings
type OrderCardViewModel = {
  id: string; formattedDate: string;
  formattedTotal: string; statusLabel: string;
};

function toOrderCardVM(order: Order): OrderCardViewModel {
  return {
    id:            order.id,
    formattedDate: new Date(order.createdAt).toLocaleDateString("en-IN"),
    formattedTotal: new Intl.NumberFormat("en-IN", { style:"currency", currency:"INR" })
                      .format(order.total / 100),
    statusLabel:   order.status.replace(/_/g, " ").toLowerCase(),
  };
}

function OrderCard({ vm }: { vm: OrderCardViewModel }) {
  return (
    <div>
      <p>{vm.formattedDate}</p>
      <p>{vm.formattedTotal}</p>
      <p>{vm.statusLabel}</p>
    </div>
  );
}
```

**Violation 4 — God ViewModel (too many concerns in one hook)**
```ts
// ✗ — one hook handles search, filters, pagination, selection, bulk actions, AND export
function useProductPage() {
  // 200 lines of mixed concerns
}

// ✓ — composed smaller ViewModels, each with one responsibility
function useProductPage() {
  const search     = useProductSearch(productService);
  const filters    = useProductFilters();
  const pagination = usePagination(search.totalCount, 20);
  const selection  = useRowSelection(search.products);
  const bulkAction = useBulkActions(selection.selectedIds, productService);
  const exporter   = useProductExporter(search.products);

  return { search, filters, pagination, selection, bulkAction, exporter };
}
```

**Q14. What is "ViewModel bloat," and how does it relate to the Single Responsibility Principle?**
A: ViewModel bloat is the accumulation of too many concerns in a single ViewModel — the UI equivalent of the god class. It violates SRP because the ViewModel has multiple reasons to change: a new filter type, a new bulk action, a pagination style change, a new export format. All of these require editing the same 300-line hook.

Detection signals:
- The hook returns more than 15–20 values.
- Adding a feature requires reading the entire hook to understand safe edit points.
- Tests for one feature require setting up state for unrelated features.
- Different parts of the hook are used by different sections of the View.

Resolution — decompose by user story / screen section:
```ts
// Each composable ViewModel has one responsibility
const useProductSearch      = () => { /* search state + command */ };
const useProductFilters     = () => { /* filter state + commands */ };
const usePagination         = (total: number, pageSize: number) => { /* page state */ };
const useProductSelection   = (products: Product[]) => { /* selection state */ };
const useBulkDelete         = (selectedIds: Set<string>) => { /* delete command + state */ };

// Parent ViewModel — composes smaller ones, thin orchestration only
function useProductListPage() {
  const search   = useProductSearch();
  const filters  = useProductFilters();
  const paging   = usePagination(search.totalCount, 20);
  const select   = useProductSelection(search.results);
  const bulkDel  = useBulkDelete(select.selectedIds);

  // Wire cross-cutting concerns (reset page on filter change)
  useEffect(() => { paging.reset(); }, [filters.activeFilters]);
  useEffect(() => { select.clearAll(); }, [search.results]);

  return { search, filters, paging, select, bulkDel };
}
```

## Section 6: Scenario / System Design Style Questions

**Q15. "You're reviewing a React codebase where every component makes its own `fetch` calls and formats data inline. How do you migrate to MVVM incrementally?"**
A: Use the Strangler Fig approach — introduce the pattern alongside existing code, migrate screen by screen:

1. **Identify the worst violators** — prioritise screens with the most duplicated fetch logic or most business rules in JSX. Use code search for `useEffect` + `fetch` patterns.

2. **Extract services first (Model layer)** — create `UserService`, `OrderService`, etc. that wrap `fetch` calls. This step doesn't change the architecture yet — it just stops duplication:
```ts
// Before
useEffect(() => { fetch("/api/orders").then(r => r.json()).then(setOrders); }, []);

// After Step 1 — service extracted, component still has state management
const orderService = new OrderService();
useEffect(() => { orderService.getAll().then(setOrders); }, []);
```

3. **Extract ViewModels (custom hooks) one screen at a time** — move `useState`, `useEffect`, derived computations, and handlers from the component into a `use<ScreenName>` hook:
```ts
// After Step 2 — ViewModel hook extracted, component is now a pure View
function useOrderList() {
  const [orders, setOrders]     = useState<Order[]>([]);
  const [isLoading, setLoading] = useState(true);
  // ... all logic here
  return { orders: formattedOrders, isLoading, handleCancel };
}

function OrderList() {
  const vm = useOrderList(); // pure View — just renders
  return vm.isLoading ? <Spinner /> : <OrderTable orders={vm.orders} />;
}
```

4. **Add mapping functions for ViewModel shapes** — raw API responses become view-model objects with formatted strings, rather than raw domain objects being formatted inline in JSX.

5. **Enforce with ESLint rules** — add rules prohibiting `fetch` inside components, requiring that `useEffect` with I/O only appears in hooks in designated `viewmodels/` or `hooks/` directories.

**Q16. "Design the MVVM architecture for a real-time dashboard showing live order metrics. It must handle WebSocket updates, filter controls, and a summary panel."**
A:
```ts
// Model — domain service, WebSocket + REST
class OrderMetricsService {
  private ws: WebSocket | null = null;

  subscribeToLiveOrders(onUpdate: (order: Order) => void): () => void {
    this.ws = new WebSocket("wss://api.example.com/orders/stream");
    this.ws.onmessage = (e) => onUpdate(JSON.parse(e.data));
    return () => this.ws?.close(); // unsubscribe / cleanup
  }

  async getHistoricalMetrics(range: DateRange): Promise<OrderMetrics> {
    const res = await fetch(`/api/metrics?from=${range.from}&to=${range.to}`);
    return res.json();
  }
}

// ViewModel — composes live and historical data, exposes display-ready state

  useEffect(() => {
    const unsubscribe = service.subscribeToLiveOrders((order) => {

  }, [service]);

  useEffect(() => {
    setLoading(true);
    service.getHistoricalMetrics(filterToDateRange(filter))
      .then(setHistorical)
      .finally(() => setLoading(false));
  }, [filter, service]);

  // Derived — display-ready metrics
  const filteredLiveOrders = useMemo(() =>
    liveOrders.filter(o =>
      filter.status === "all" || o.status === filter.status
    ),
    [liveOrders, filter.status]
  );

  const summary = useMemo(() => {
    if (!historical) return null;
    return {

      revenueChange:   formatPercentChange(historical.revenueChangeVsPrev),
      isRevenueUp:     historical.revenueChangeVsPrev >= 0,
    };

  const liveOrderVMs = useMemo(() =>
    filteredLiveOrders.map(o => ({

    ? `Updated ${formatTimeAgo(lastUpdated)}`
    : "Waiting for updates...";

  // Commands
  const handleFilterChange = useCallback((partial: Partial<DashboardFilter>) => {
    setFilter(prev => ({ ...prev, ...partial }));
  }, []);

  return {
    summary, liveOrderVMs, isLoading, filter,
    lastUpdatedLabel, liveOrderCount: filteredLiveOrders.length,

  };
}
```

**Q17. "How does MVVM handle the case where two different Views need to share ViewModel state — for example, a cart badge in the header and a cart drawer in the sidebar?"**
A: Shared ViewModel state is lifted to a shared context or store — the ViewModel becomes a provider:
```tsx
// Approach 1 — React Context as a shared ViewModel provider
const CartContext = createContext<ReturnType<typeof useCartViewModel> | null>(null);

function CartProvider({ children }: { children: React.ReactNode }) {
  const vm = useCartViewModel(cartService); // ViewModel instantiated once
  return <CartContext.Provider value={vm}>{children}</CartContext.Provider>;
}

function useCart() {
  const ctx = useContext(CartContext);
  if (!ctx) throw new Error("useCart must be used within CartProvider");
  return ctx;
}

// Two Views — both read from the SAME ViewModel instance
function CartBadge() {
  const { itemCount } = useCart(); // reads shared ViewModel
  return <span className="badge">{itemCount}</span>;
}

function CartDrawer() {
  const { items, formattedTotal, handleRemove, handleCheckout } = useCart(); // same VM
  return (
    <aside>
      {items.map(item => (
        <CartItem key={item.id} item={item} onRemove={() => handleRemove(item.id)} />
      ))}
      <footer>
        <strong>{formattedTotal}</strong>
        <button onClick={handleCheckout}>Checkout</button>
      </footer>
    </aside>
  );
}

// App layout — CartProvider wraps both consumers
function AppLayout() {
  return (
    <CartProvider>
      <Header>
        <NavLinks />
        <CartBadge /> {/* reads shared ViewModel */}
      </Header>
      <Main>
        <CartDrawer /> {/* reads same shared ViewModel */}
        <ProductCatalog />
      </Main>
    </CartProvider>
  );
}
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Model | ViewModel | View |
|---|---|---|---|
| **Contains** | Domain data, business rules, API calls, validation | UI state, derived data, commands, formatting | Markup, layout, user interaction wiring |
| **Knows about** | Nothing UI-related | Model (calls services) | ViewModel only |
| **Known by** | ViewModel | View (via binding) | Nothing — it's the output |
| **Framework dependency** | None — pure TypeScript | Minimal — React hooks, Vue composables | Full — JSX, templates |
| **Testability** | Unit tests, integration tests | Unit tests with `renderHook` — no DOM needed | Component tests, E2E |
| **Changes when** | Business rules change | UI requirements change | Design / UX changes |
| **Examples** | `OrderService`, `UserService`, domain entities | `useOrderList`, `useCart`, `OrderListComponent` class | `<OrderList />`, Angular template |

## MVVM vs Related Patterns (at a glance)

| Pattern | Presenter/Controller knows View? | Data flow | Binding mechanism | Primary JS expression |
|---|---|---|---|---|
| **MVC** | Controller loosely knows View | Bidirectional | Manual or observer | Express + template engines |
| **MVP** | Presenter holds View interface reference | Bidirectional through interface | Presenter calls `view.method()` | Legacy Android, WinForms-style |
| **MVVM** | ViewModel has NO View reference | One-way (or two-way) via binding | Reactive data binding | React hooks, Vue composables, Angular components |
| **Flux / Redux** | No explicit P/VM — unidirectional | Strictly one-way | Store subscriptions | React + Redux, Zustand |
| **Clean Architecture** | Same as MVVM at UI layer; adds use case layer | Dependency rule — inward only | Same as MVVM | NestJS + React monorepo |

---

**Tip for the interview:** At the 5 YOE level, "what is MVVM" never arrives as a definition question — it surfaces as: why is this component so hard to test (business logic in JSX — put it in a hook), how would you architect a dashboard that mixes real-time data and historical metrics (ViewModel composes both sources, View renders derived state), how do you share cart state across two unrelated UI sections (ViewModel as a Context provider), or how do you migrate a legacy codebase full of fetch-in-component patterns (Strangler Fig — extract services first, then hooks). The sharp answer immediately names the three layers and their boundaries, explains the ViewModel's central role (formats data for display, has no DOM reference, fully testable in Node), demonstrates the mapping from a React hook or Vue composable to the pattern, and names at least one anti-pattern it prevents (raw domain objects in JSX, fetch in useEffect inside the component body). Connecting ViewModel testability to the absence of UI framework imports — "the hook has no JSX, so it runs in a pure Node test with no DOM" — is the depth that lands at 5 YOE.
