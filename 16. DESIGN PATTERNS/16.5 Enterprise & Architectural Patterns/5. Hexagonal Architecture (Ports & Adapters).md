# Enterprise & Architectural Patterns: Hexagonal Architecture (Ports & Adapters) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Hexagonal Architecture?**
A: Hexagonal Architecture (also called Ports and Adapters) is an architectural pattern introduced by Alistair Cockburn in 2005. Its core idea: isolate the application's domain and business logic at the center — the *hexagon* — and connect every external system (HTTP, database, Kafka, SMS, third-party APIs) through explicitly defined interfaces called *ports*, implemented by interchangeable *adapters*. Nothing inside the hexagon knows anything about the outside world.

The hexagon is a deliberate metaphor — not a technical shape, but a statement that the application has many sides and each side is a symmetric, swappable connection point. The shape has six sides to emphasize that no one side (HTTP, database) is more fundamental than any other. The application is equally indifferent to whether it's driven by an HTTP request, a Kafka message, a CLI command, or a test suite — and equally indifferent to whether it persists to PostgreSQL, MongoDB, or an in-memory store.

The GoF gang called it "Ports and Adapters" because: a **Port** is the interface the application defines (it controls this), and an **Adapter** is the implementation that bridges the port to a specific external technology (a plugin for that port).

**Q2. What problem does Hexagonal Architecture solve?**
A: It solves the *framework coupling* and *infrastructure leakage* problems that make large applications hard to test, hard to evolve, and hard to run in multiple contexts. Without it:

```ts
// WITHOUT Hexagonal — business logic coupled to infrastructure
@Injectable()
export class LoanService {
  constructor(
    // Coupled to TypeORM — can't test without a database
    @InjectRepository(LoanEntity)
    private readonly ormRepo: Repository<LoanEntity>,

    // Coupled to Axios — can't test without the credit bureau being up
    private readonly httpService: HttpService,

    // Coupled to NestJS EventEmitter — can't run outside NestJS
    private readonly eventEmitter: EventEmitter2,

    // Coupled to Razorpay SDK — can't test without API keys
    private readonly razorpay: Razorpay,
  ) {}

  async approveLoan(loanId: string, approverId: string): Promise<void> {
    // Business logic tangled with ORM specifics
    const entity = await this.ormRepo.findOne({
      where: { id: loanId },
      relations: ["user"],
    });
    if (!entity) throw new NotFoundException();

    // Business rule mixed with HTTP call
    const { data } = await this.httpService.get(`/credit/check/${entity.user_id}`).toPromise();
    if (data.score < 650) throw new UnprocessableEntityException("Credit score too low");

    // Business state change mixed with ORM mutation
    entity.status = "APPROVED";
    entity.approved_by = approverId;
    entity.approved_at = new Date();
    await this.ormRepo.save(entity);

    // Side effect coupled to specific SDK
    await this.razorpay.transfers.create({ /* ... */ });
  }
}
```

To test the approval logic, you need TypeORM, a real database, an HTTP server for credit checks, NestJS's event system, and Razorpay API keys. Changing from Razorpay to JusPay means modifying the service. Changing from PostgreSQL to MongoDB means rewriting the service. Running the same logic from a Kafka consumer requires duplicating it.

With Hexagonal Architecture, `LoanService` depends only on interfaces (ports) it defines. Tests inject fast in-memory implementations. Production injects real database and HTTP adapters. The business logic is identical in both cases.

**Q3. What is a Port and what is an Adapter?**
A:
- **Port** — an interface defined *by the application domain*, expressing what the application needs from the outside world or what the outside world needs from the application. Ports are owned by the domain; they speak the domain's language (domain objects as parameters, not DTOs or ORM entities). There are two kinds:
  - **Driving Port (Primary/Inbound)** — the interface through which external actors *drive* the application. Example: `LoanApplicationPort` with a method `approveLoan(loanId: string, approverId: string): Promise<Loan>`. REST controllers, Kafka consumers, and CLI tools all implement this by calling into the application through the driving port.
  - **Driven Port (Secondary/Outbound)** — the interface the application uses to *reach out* to external systems. Example: `LoanRepository`, `CreditBureauPort`, `PaymentGatewayPort`. The application defines these; infrastructure implements them.

- **Adapter** — a concrete implementation that connects a port to a specific external technology. Adapters are in the infrastructure layer; they know about HTTP, databases, SDKs, and message queues. They translate between the domain's language (domain objects) and the external system's language (HTTP responses, ORM entities, SDK calls).

```
External World          Application Hexagon          External World
(Driving Side)                                       (Driven Side)

HTTP Request  ──▶  [REST Adapter]  ──▶  [Driving Port]  ──▶  Domain Logic
Kafka Message ──▶  [Kafka Adapter] ──▶  [Driving Port]  ──▶  Domain Logic
CLI Command   ──▶  [CLI Adapter]   ──▶  [Driving Port]  ──▶  Domain Logic
Test Suite    ──▶  [Test Adapter]  ──▶  [Driving Port]  ──▶  Domain Logic

Domain Logic  ──▶  [Driven Port]   ──▶  [DB Adapter]    ──▶  PostgreSQL
Domain Logic  ──▶  [Driven Port]   ──▶  [HTTP Adapter]  ──▶  Credit Bureau
Domain Logic  ──▶  [Driven Port]   ──▶  [MQ Adapter]    ──▶  Kafka
Domain Logic  ──▶  [Driven Port]   ──▶  [Mock Adapter]  ──▶  (in tests)
```

**Q4. What is the Dependency Rule in Hexagonal Architecture?**
A: The Dependency Rule states that all dependencies must point *inward* — toward the domain. Nothing in the domain layer may import from the infrastructure layer or the application framework. The domain is the most stable layer; it changes only when business rules change. Infrastructure is the most volatile; it changes when technology choices change.

```
Infrastructure Layer (Adapters, ORM, HTTP clients, SDKs)
        │
        │  depends on
        ▼
Application Layer (Use cases, Command/Query handlers)
        │
        │  depends on
        ▼
Domain Layer (Entities, Value Objects, Domain Services, Port interfaces)
        │
        │  depends on NOTHING external
        ▼
       (nothing)
```

The domain layer is an island — no `import` statement in any domain file points to TypeORM, NestJS, Axios, Razorpay, or any other framework or library. Domain classes are plain TypeScript (or Java, Python, etc.) with no framework annotations. This is what makes them testable in isolation, runnable in any environment, and resilient to technology changes.

**Q5. How does Hexagonal Architecture differ from MVC and Layered Architecture?**
A:

| Aspect                    | MVC / Layered Architecture                          | Hexagonal Architecture                                      |
|---                        |---                                                  |---                                                          |
| Primary concern           | Separating presentation from logic from data        | Isolating business logic from ALL external systems          |
| Dependency direction      | Top-down: Controller → Service → Repository → DB    | Inward: everything → Domain (domain depends on nothing)     |
| Database role             | Foundational — the bottom of the stack              | Just another adapter — no more important than Kafka or HTTP |
| Test approach             | Mock the layer below (mock the repository)          | Mock the port (in-memory adapter implements the port)       |
| Framework coupling        | Framework often penetrates service layer            | Framework is entirely outside the hexagon                   |
| Multi-channel support     | Requires careful discipline to avoid fat controllers| Natural — each channel is just a driving adapter            |
| Changeability             | Swapping ORM requires updating service layer        | Swapping ORM means writing a new adapter — domain unchanged |
| Port concept              | Implicit (interfaces between layers)                | Explicit — named, defined by the domain, bidirectional      |

MVC separates *presentation* from *logic* from *data*. Hexagonal separates *business logic* from *everything else* — including HTTP, the database, message queues, and external services. MVC is a subset of Hexagonal: a REST controller is a driving adapter, a repository is a driven adapter.

```ts
// ─── DOMAIN LAYER ───────────────────────────────────────────────────────────

// Domain Entity — pure TypeScript, zero framework dependencies
// src/domain/entities/loan.entity.ts
export class Loan {
  private constructor(
    public readonly id: string,
    private _status: LoanStatus,
    public readonly amount: LoanAmount,
    public readonly userId: string,
    private _approvedBy?: string,
    private _approvedAt?: Date,
    public readonly createdAt: Date = new Date(),
  ) {}

  static create(props: CreateLoanProps): Loan {
    if (props.amount.value < 10_000) {
      throw new DomainError("Loan amount must be at least ₹10,000");
    }
    return new Loan(generateId(), LoanStatus.PENDING, props.amount, props.userId);
  }

  static reconstitute(props: LoanProps): Loan {
    return new Loan(
      props.id, props.status, props.amount,
      props.userId, props.approvedBy, props.approvedAt, props.createdAt
    );
  }

  get status(): LoanStatus { return this._status; }
  get approvedBy(): string | undefined { return this._approvedBy; }
  get approvedAt(): Date | undefined { return this._approvedAt; }

  approve(approverId: string): void {
    if (this._status !== LoanStatus.PENDING) {
      throw new InvalidLoanStateError(
        `Cannot approve a loan in status: ${this._status}`
      );
    }
    if (!approverId) throw new DomainError("Approver ID is required");
    this._status = LoanStatus.APPROVED;
    this._approvedBy = approverId;
    this._approvedAt = new Date();
  }

  requiresDualApproval(): boolean {
    return this.amount.value > 500_000;
  }
}

// Value Object
// src/domain/value-objects/loan-amount.vo.ts
export class LoanAmount {
  private constructor(public readonly value: number) {}

  static of(value: number): LoanAmount {
    if (value <= 0) throw new DomainError("Loan amount must be positive");
    if (!Number.isInteger(value)) throw new DomainError("Loan amount must be in whole rupees");
    return new LoanAmount(value);
  }

  format(): string {
    return `₹${this.value.toLocaleString("en-IN")}`;
  }
}

// Driven Port — defined by the domain, implemented by infrastructure
// src/domain/ports/outbound/loan-repository.port.ts
export interface LoanRepositoryPort {
  findById(id: string): Promise<Loan | null>;
  findByUserId(userId: string): Promise<Loan[]>;
  save(loan: Loan): Promise<void>;
  existsActiveLoanForUser(userId: string): Promise<boolean>;
}

// Driven Port — credit bureau abstraction
// src/domain/ports/outbound/credit-bureau.port.ts
export interface CreditBureauPort {
  getCreditScore(userId: string, pan: string): Promise<CreditScore>;
}

// Driven Port — payment gateway abstraction
// src/domain/ports/outbound/payment-gateway.port.ts
export interface PaymentGatewayPort {
  disburse(loanId: string, amount: LoanAmount, accountId: string): Promise<DisbursementResult>;
  refund(transactionId: string, amount: LoanAmount): Promise<RefundResult>;
}

// Driving Port — what the application exposes to the outside world
// src/domain/ports/inbound/loan-use-cases.port.ts
export interface LoanUseCasesPort {
  approveLoan(command: ApproveLoanCommand): Promise<Loan>;
  createLoan(command: CreateLoanCommand): Promise<Loan>;
  getLoan(loanId: string): Promise<Loan>;
}

// ─── APPLICATION LAYER ──────────────────────────────────────────────────────

// Use Case — orchestrates domain + driven ports
// src/application/use-cases/approve-loan.use-case.ts
@Injectable()
export class ApproveLoanUseCase {
  constructor(
    // Injected via tokens — depends on port interfaces, not concrete adapters
    @Inject(LOAN_REPOSITORY_PORT) private readonly loanRepo: LoanRepositoryPort,
    @Inject(CREDIT_BUREAU_PORT)   private readonly creditBureau: CreditBureauPort,
    @Inject(PAYMENT_GATEWAY_PORT) private readonly paymentGateway: PaymentGatewayPort,
  ) {}

  async execute(command: ApproveLoanCommand): Promise<Loan> {
    // Pure business orchestration — no ORM, no HTTP, no SDK
    const loan = await this.loanRepo.findById(command.loanId);
    if (!loan) throw new LoanNotFoundError(command.loanId);

    const credit = await this.creditBureau.getCreditScore(
      command.approverId, command.approverPan
    );
    if (credit.score < 650) {
      throw new CreditCheckFailedError(`Credit score ${credit.score} below threshold 650`);
    }

    loan.approve(command.approverId); // domain method enforces invariants
    await this.loanRepo.save(loan);

    return loan;
  }
}

// ─── INFRASTRUCTURE LAYER — DRIVEN ADAPTERS ────────────────────────────────

// TypeORM Adapter — implements the driven LoanRepositoryPort
// src/infrastructure/driven/persistence/typeorm-loan.repository.ts
@Injectable()
export class TypeOrmLoanRepository implements LoanRepositoryPort {
  constructor(
    @InjectRepository(LoanOrmEntity)
    private readonly ormRepo: Repository<LoanOrmEntity>,
  ) {}

  async findById(id: string): Promise<Loan | null> {
    const entity = await this.ormRepo.findOne({ where: { id } });
    return entity ? LoanMapper.toDomain(entity) : null;
  }

  async save(loan: Loan): Promise<void> {
    const entity = LoanMapper.toOrm(loan);
    await this.ormRepo.save(entity);
  }

  async findByUserId(userId: string): Promise<Loan[]> {
    const entities = await this.ormRepo.find({ where: { user_id: userId } });
    return entities.map(LoanMapper.toDomain);
  }

  async existsActiveLoanForUser(userId: string): Promise<boolean> {
    return this.ormRepo.exists({
      where: { user_id: userId, status: In(["PENDING", "APPROVED", "DISBURSED"]) }
    });
  }
}

// Experian HTTP Adapter — implements the driven CreditBureauPort
// src/infrastructure/driven/credit-bureau/experian-credit-bureau.adapter.ts
@Injectable()
export class ExperianCreditBureauAdapter implements CreditBureauPort {
  constructor(
    private readonly httpService: HttpService,
    private readonly config: ConfigService,
  ) {}

  async getCreditScore(userId: string, pan: string): Promise<CreditScore> {
    try {
      const { data } = await firstValueFrom(
        this.httpService.post(`${this.config.get("EXPERIAN_URL")}/score`, {
          pan,
          consent: true,
        }, {
          headers: { "X-API-Key": this.config.get("EXPERIAN_API_KEY") },
          timeout: 5000,
        })
      );
      return { score: data.score, bureau: "EXPERIAN", fetchedAt: new Date() };
    } catch (err) {
      if (axios.isAxiosError(err) && err.response?.status === 404) {
        throw new CreditProfileNotFoundError(pan);
      }
      throw new CreditBureauUnavailableError(`Experian unreachable: ${err.message}`);
    }
  }
}

// ─── INFRASTRUCTURE LAYER — DRIVING ADAPTERS ───────────────────────────────

// REST Adapter — driving adapter that translates HTTP → domain
// src/infrastructure/driving/http/loan.controller.ts
@Controller("loans")
@UseInterceptors(ClassSerializerInterceptor)
export class LoanController {
  constructor(
    // Depends on the USE CASE (driving port), not the use case implementation
    @Inject(APPROVE_LOAN_USE_CASE) private readonly approveLoan: ApproveLoanUseCase,
    @Inject(CREATE_LOAN_USE_CASE)  private readonly createLoan: CreateLoanUseCase,
  ) {}

  @Post(":id/approve")
  @UseGuards(JwtAuthGuard, RolesGuard)
  @Roles("RISK_MANAGER", "ADMIN")
  async approve(
    @Param("id", ParseUUIDPipe) loanId: string,
    @Body() dto: ApproveLoanHttpDto,
    @CurrentUser() user: AuthUser,
  ): Promise<LoanHttpResponseDto> {
    // Adapter's job: translate HTTP → domain command
    const command = new ApproveLoanCommand(loanId, user.id, user.pan);
    // Call through the driving port
    const loan = await this.approveLoan.execute(command);
    // Translate domain → HTTP response
    return LoanHttpResponseDto.fromDomain(loan);
  }
}

// Kafka Adapter — same use case, different driving adapter
// src/infrastructure/driving/kafka/loan-command.consumer.ts
@Injectable()
export class LoanCommandConsumer {
  constructor(
    @Inject(APPROVE_LOAN_USE_CASE) private readonly approveLoan: ApproveLoanUseCase,
  ) {}

  @EventPattern("loan-commands")
  async handleCommand(@Payload() msg: LoanCommandMessage): Promise<void> {
    if (msg.type === "APPROVE_LOAN") {
      // Adapter's job: translate Kafka message → domain command
      const command = new ApproveLoanCommand(msg.loanId, msg.approverId, msg.approverPan);
      await this.approveLoan.execute(command);
      // No response DTO — Kafka ack is the "view"
    }
  }
}
```

**Q7. How do you wire ports to adapters in NestJS using injection tokens?**
A: Ports are interfaces; NestJS needs tokens to resolve them. Use `Symbol` tokens to bind each port interface to its concrete adapter — this keeps the application layer decoupled from infrastructure:

```ts
// Port tokens — defined once, referenced everywhere
// src/domain/ports/port-tokens.ts
export const LOAN_REPOSITORY_PORT  = Symbol("LoanRepositoryPort");
export const CREDIT_BUREAU_PORT    = Symbol("CreditBureauPort");
export const PAYMENT_GATEWAY_PORT  = Symbol("PaymentGatewayPort");
export const APPROVE_LOAN_USE_CASE = Symbol("ApproveLoanUseCase");
export const CREATE_LOAN_USE_CASE  = Symbol("CreateLoanUseCase");

// Infrastructure Module — wires adapters to ports
// src/infrastructure/infrastructure.module.ts
@Module({
  imports: [
    TypeOrmModule.forFeature([LoanOrmEntity]),
    HttpModule,
  ],
  providers: [
    // Driven adapters — port → adapter binding
    {
      provide: LOAN_REPOSITORY_PORT,
      useClass: TypeOrmLoanRepository,
    },
    {
      provide: CREDIT_BUREAU_PORT,
      useFactory: (http: HttpService, config: ConfigService): CreditBureauPort => {
        // Factory allows environment-based adapter selection
        return config.get("USE_MOCK_CREDIT_BUREAU") === "true"
          ? new MockCreditBureauAdapter()
          : new ExperianCreditBureauAdapter(http, config);
      },
      inject: [HttpService, ConfigService],
    },
    {
      provide: PAYMENT_GATEWAY_PORT,
      useFactory: (config: ConfigService): PaymentGatewayPort => {
        const gateway = config.get("PAYMENT_GATEWAY");
        if (gateway === "razorpay") return new RazorpayAdapter(config);
        if (gateway === "juspay")   return new JusPayAdapter(config);
        throw new Error(`Unknown payment gateway: ${gateway}`);
      },
      inject: [ConfigService],
    },

    // Application use cases — depend only on port tokens
    {
      provide: APPROVE_LOAN_USE_CASE,
      useFactory: (
        repo: LoanRepositoryPort,
        credit: CreditBureauPort,
        payment: PaymentGatewayPort,
      ) => new ApproveLoanUseCase(repo, credit, payment),
      inject: [LOAN_REPOSITORY_PORT, CREDIT_BUREAU_PORT, PAYMENT_GATEWAY_PORT],
    },
  ],
  exports: [APPROVE_LOAN_USE_CASE, CREATE_LOAN_USE_CASE],
})
export class InfrastructureModule {}

// Application Module — imports infrastructure, owns controllers
// src/app.module.ts
@Module({
  imports: [InfrastructureModule],
  controllers: [LoanController, LoanCommandConsumer],
})
export class AppModule {}
```

**Q8. How do you write tests in Hexagonal Architecture?**
A: The primary benefit of Hexagonal Architecture is that the domain and application layers are tested with zero framework or infrastructure involvement — no NestJS, no TypeORM, no HTTP clients. In-memory adapters replace real infrastructure:

```ts
// In-memory adapter — implements driven port for tests
// src/domain/ports/outbound/test-doubles/in-memory-loan.repository.ts
export class InMemoryLoanRepository implements LoanRepositoryPort {
  public readonly store = new Map<string, Loan>();
  public saveCalls: Loan[] = []; // spy capability

  async findById(id: string): Promise<Loan | null> {
    return this.store.get(id) ?? null;
  }

  async save(loan: Loan): Promise<void> {
    this.store.set(loan.id, loan);
    this.saveCalls.push(loan);
  }

  async findByUserId(userId: string): Promise<Loan[]> {
    return [...this.store.values()].filter(l => l.userId === userId);
  }

  async existsActiveLoanForUser(userId: string): Promise<boolean> {
    return [...this.store.values()].some(
      l => l.userId === userId && ["PENDING", "APPROVED"].includes(l.status)
    );
  }

  // Test helper — seed data without going through use cases
  seed(loan: Loan): void {
    this.store.set(loan.id, loan);
  }
}

// In-memory credit bureau adapter
export class InMemoryCreditBureauAdapter implements CreditBureauPort {
  private scores = new Map<string, number>();

  setScore(userId: string, score: number): void {
    this.scores.set(userId, score);
  }

  async getCreditScore(userId: string): Promise<CreditScore> {
    const score = this.scores.get(userId) ?? 750; // default: passing score
    return { score, bureau: "TEST", fetchedAt: new Date() };
  }
}

// Use case test — zero framework, zero DB, zero HTTP
describe("ApproveLoanUseCase", () => {
  let useCase: ApproveLoanUseCase;
  let loanRepo: InMemoryLoanRepository;
  let creditBureau: InMemoryCreditBureauAdapter;
  let paymentGateway: jest.Mocked<PaymentGatewayPort>;

  beforeEach(() => {
    loanRepo = new InMemoryLoanRepository();
    creditBureau = new InMemoryCreditBureauAdapter();
    paymentGateway = { disburse: jest.fn(), refund: jest.fn() };
    useCase = new ApproveLoanUseCase(loanRepo, creditBureau, paymentGateway);
  });

  it("approves a pending loan when credit score is sufficient", async () => {
    const loan = Loan.create({ amount: LoanAmount.of(50_000), userId: "U1" });
    loanRepo.seed(loan);
    creditBureau.setScore("U1", 720);

    const result = await useCase.execute(
      new ApproveLoanCommand(loan.id, "approver-1", "ABCDE1234F")
    );

    expect(result.status).toBe(LoanStatus.APPROVED);
    expect(result.approvedBy).toBe("approver-1");
    expect(loanRepo.saveCalls).toHaveLength(1);
    expect(loanRepo.saveCalls[0].status).toBe(LoanStatus.APPROVED);
  });

  it("rejects when credit score is below threshold", async () => {
    const loan = Loan.create({ amount: LoanAmount.of(50_000), userId: "U1" });
    loanRepo.seed(loan);
    creditBureau.setScore("U1", 600); // below 650

    await expect(
      useCase.execute(new ApproveLoanCommand(loan.id, "approver-1", "ABCDE1234F"))
    ).rejects.toThrow(CreditCheckFailedError);

    expect(loanRepo.saveCalls).toHaveLength(0); // loan was not saved
  });

  it("rejects when loan does not exist", async () => {
    await expect(
      useCase.execute(new ApproveLoanCommand("nonexistent-id", "approver-1", "PAN"))
    ).rejects.toThrow(LoanNotFoundError);
  });

  it("enforces domain invariant — cannot approve already-approved loan", async () => {
    const loan = Loan.create({ amount: LoanAmount.of(50_000), userId: "U1" });
    loan.approve("first-approver");
    loanRepo.seed(loan);

    await expect(
      useCase.execute(new ApproveLoanCommand(loan.id, "second-approver", "PAN"))
    ).rejects.toThrow(InvalidLoanStateError);
  });
});
```

These tests run in milliseconds — no database connections, no HTTP servers, no test containers. The entire domain and application layer is covered by pure unit tests.

## Section 3: Ports in Depth

**Q9. What is the difference between a Driving Port and a Driven Port, and which direction does dependency flow?**
A: The naming refers to the direction of *initiation* — who drives whom:

**Driving Ports (Primary / Inbound):**
- Defined by the application, implemented by driving adapters.
- External actors call *into* the application through these.
- The application is *driven* by external actors via these ports.
- Dependency flows: Driving Adapter → Driving Port (interface) ← Use Case (implements).
- Wait — the adapter calls the use case, which means the adapter holds a reference to the use case. The use case IS the implementation of the driving port; the adapter calls through it. This is the one place where the adapter depends on the application.

**Driven Ports (Secondary / Outbound):**
- Defined by the application, implemented by driven adapters.
- The application calls *out* through these.
- The application *drives* external systems via these ports.
- Dependency flows: Use Case → Driven Port (interface) ← Driven Adapter (implements).
- The use case depends on the interface (which it defines); the adapter implements it. This is Dependency Inversion — the application defines what it needs; infrastructure provides it.

```
DRIVING SIDE                              DRIVEN SIDE
(Primary — "in")                          (Secondary — "out")

[HTTP Request]                              [PostgreSQL]
```

**Q10. How do you define a port that needs async initialization (e.g., a database connection pool)?**
A: The port interface defines the *capability* (what you can do), not the *lifecycle* (how it's set up). Initialization is the adapter's responsibility, managed by the DI container:

```ts
// Port — clean capability interface, no lifecycle concerns
export interface LoanRepositoryPort {
  findById(id: string): Promise<Loan | null>;
  save(loan: Loan): Promise<void>;
  findByUserId(userId: string): Promise<Loan[]>;
}

// Adapter — handles its own initialization via NestJS lifecycle hooks
@Injectable()
export class TypeOrmLoanRepository implements LoanRepositoryPort, OnModuleInit {
  private pool: Pool;

  async onModuleInit(): Promise<void> {
    // Initialization happens here — never in the port interface
    this.pool = new Pool({ connectionString: process.env.PG_URL });
    await this.pool.connect(); // warm up
  }

  async findById(id: string): Promise<Loan | null> {
    const { rows } = await this.pool.query("SELECT * FROM loans WHERE id = $1", [id]);
    return rows[0] ? LoanMapper.toDomain(rows[0]) : null;
  }
}
```

The domain layer never sees `OnModuleInit`, `Pool`, or any lifecycle concern. The port is a pure interface. The adapter owns its lifecycle.

**Q11. How do you design ports for event publishing — both domain events and integration events?**
A: Event publishing crosses the boundary from application to infrastructure. The driven port for events should be defined in terms the domain understands:

```ts
// Domain event — pure domain concept, no framework dependency
export class LoanApprovedDomainEvent {
  readonly occurredAt = new Date();
  constructor(
    public readonly loanId: string,
    public readonly userId: string,
    public readonly amount: number,
    public readonly approvedBy: string,
  ) {}
}

// Driven port — domain defines what events it needs to publish
// src/domain/ports/outbound/domain-event-publisher.port.ts
export interface DomainEventPublisherPort {
  publish(event: LoanApprovedDomainEvent): Promise<void>;
  publishAll(events: DomainEvent[]): Promise<void>;
}

// In-process adapter — uses NestJS EventEmitter2
@Injectable()
export class NestJsEventPublisherAdapter implements DomainEventPublisherPort {
  constructor(private readonly emitter: EventEmitter2) {}

  async publish(event: LoanApprovedDomainEvent): Promise<void> {
    this.emitter.emit(`${event.constructor.name}`, event);
  }

  async publishAll(events: DomainEvent[]): Promise<void> {
    await Promise.allSettled(events.map(e => this.publish(e as LoanApprovedDomainEvent)));
  }
}

// Kafka adapter — publishes to external bus
@Injectable()
export class KafkaDomainEventPublisherAdapter implements DomainEventPublisherPort {
  constructor(private readonly producer: KafkaProducerService) {}

  async publish(event: LoanApprovedDomainEvent): Promise<void> {
    await this.producer.send({
      topic: "loan-events",
      messages: [{
        key: event.loanId,

  }
}
```

## Section 4: Adapters in Depth

**Q12. How do you implement a Data Mapper inside a driven adapter?**
A: The Data Mapper is the critical component inside a persistence adapter — it translates between the domain's rich objects and the database's flat records, keeping the domain pure:

```ts
// ORM Entity — infrastructure concern only, never reaches domain layer
// src/infrastructure/driven/persistence/loan.orm-entity.ts
@Entity("loans")
export class LoanOrmEntity {
  @PrimaryColumn("uuid")     id: string;
  @Column()                  status: string;
  @Column({ type: "bigint" }) amount_paise: number; // stored in paise, not rupees
  @Column()                  user_id: string;
  @Column({ nullable: true }) approved_by: string | null;
  @Column({ nullable: true }) approved_at: Date | null;
  @CreateDateColumn()         created_at: Date;
  @UpdateDateColumn()         updated_at: Date;
}

// Data Mapper — the translation layer inside the adapter
// src/infrastructure/driven/persistence/loan.mapper.ts
export class LoanMapper {
  static toDomain(orm: LoanOrmEntity): Loan {
    return Loan.reconstitute({
      id: orm.id,
      status: orm.status as LoanStatus,
      amount: LoanAmount.of(orm.amount_paise / 100), // paise → rupees
      userId: orm.user_id,
      approvedBy: orm.approved_by ?? undefined,
      approvedAt: orm.approved_at ?? undefined,
      createdAt: orm.created_at,
    });
  }

  static toOrm(domain: Loan): Partial<LoanOrmEntity> {
    return {
      id: domain.id,
      status: domain.status,
      amount_paise: domain.amount.value * 100, // rupees → paise
      user_id: domain.userId,
      approved_by: domain.approvedBy ?? null,
      approved_at: domain.approvedAt ?? null,
    };
  }
}
```

The mapper is the only place where the ORM entity and the domain entity meet. The domain `Loan` class never has `@Column` decorators; the `LoanOrmEntity` class never has domain methods like `approve()`.

**Q13. How do you implement an HTTP adapter for an outbound driven port with proper error mapping?**
A: The adapter's job is to translate between the external system's language (HTTP status codes, API-specific error objects) and the domain's language (domain exceptions):

```ts
// Razorpay payment adapter — implements PaymentGatewayPort
// src/infrastructure/driven/payment/razorpay-payment.adapter.ts
@Injectable()
export class RazorpayPaymentAdapter implements PaymentGatewayPort {
  private readonly client: Razorpay;

  constructor(private readonly config: ConfigService) {
    this.client = new Razorpay({
      key_id: config.getOrThrow("RAZORPAY_KEY_ID"),
      key_secret: config.getOrThrow("RAZORPAY_KEY_SECRET"),
    });
  }

  async disburse(
    loanId: string,
    amount: LoanAmount,
    accountId: string,
  ): Promise<DisbursementResult> {
    try {
      const transfer = await this.client.transfers.create({
        account: accountId,
        amount: amount.value * 100, // Razorpay expects paise
        currency: "INR",
        notes: { loanId, source: "loan-disbursement" },
      });

      return {
        transactionId: transfer.id,
        amount: LoanAmount.of(transfer.amount / 100), // paise → rupees
        disbursedAt: new Date(transfer.created_at * 1000), // Unix → Date
        gatewayReference: transfer.id,
      };
    } catch (err) {
      // Translate Razorpay errors → domain exceptions
      if (err.error?.code === "BAD_REQUEST_ERROR") {
        throw new PaymentValidationError(`Invalid account: ${accountId}`);
      }
      if (err.error?.code === "GATEWAY_ERROR") {
        throw new PaymentGatewayError(`Razorpay gateway error: ${err.error.description}`);
      }
      throw new PaymentGatewayError(`Unexpected payment error: ${err.message}`);
    }
  }

  async refund(transactionId: string, amount: LoanAmount): Promise<RefundResult> {
    try {
      const refund = await this.client.payments.refund(transactionId, {
        amount: amount.value * 100,
      });
      return {
        refundId: refund.id,
        amount: LoanAmount.of(refund.amount / 100),
        refundedAt: new Date(),
      };
    } catch (err) {
      throw new PaymentGatewayError(`Refund failed: ${err.message}`);
    }
  }
}
```

The domain never knows about Razorpay error codes, paise conversion, or Unix timestamps. Those are the adapter's translation responsibilities. Swapping to JusPay means writing `JusPayPaymentAdapter implements PaymentGatewayPort` — the domain and use cases are untouched.

**Q14. How does the Anti-Corruption Layer (ACL) pattern relate to driven adapters?**
A: An Anti-Corruption Layer is a pattern from Domain-Driven Design that protects the domain model from the concepts and terminology of external systems. In Hexagonal Architecture, every driven adapter is an ACL — it translates external concepts into domain concepts, preventing "corruption" of the domain model by external systems' language:

```ts
// Without ACL — external Experian model leaks into domain
// WRONG — domain code imports and uses Experian's specific type
import { ExperianCreditReport } from "@experian/sdk"; // DON'T DO THIS in domain

export class ApproveLoanUseCase {
  async execute(command: ApproveLoanCommand): Promise<Loan> {
    // Domain is now coupled to Experian's data model — corruption
    const report: ExperianCreditReport = await this.experian.getReport(pan);
    if (report.crif_score.enquiries[0].score_value < 650) { /* ... */ }
  }
}

// WITH ACL (driven adapter) — domain only sees CreditScore (domain concept)
export class ExperianCreditBureauAdapter implements CreditBureauPort {
  async getCreditScore(userId: string, pan: string): Promise<CreditScore> {
    // External Experian model is contained INSIDE the adapter
    const report: ExperianCreditReport = await this.experianSdk.getReport({ pan });

    // ACL translation: Experian concepts → domain concepts
    return {
      score: report.crif_score.enquiries[0].score_value, // extract the relevant field
      bureau: "EXPERIAN",
      fetchedAt: new Date(report.generated_date),        // normalize date format
      riskBand: this.mapRiskBand(report.score_band),     // translate risk band taxonomy
    };
  }

  private mapRiskBand(experianBand: string): DomainRiskBand {
    const mapping: Record<string, DomainRiskBand> = {
      "EXCELLENT":  DomainRiskBand.LOW,
      "VERY_GOOD":  DomainRiskBand.LOW,
      "GOOD":       DomainRiskBand.MEDIUM,
      "FAIR":       DomainRiskBand.MEDIUM_HIGH,
      "POOR":       DomainRiskBand.HIGH,
      "VERY_POOR":  DomainRiskBand.VERY_HIGH,
    };
    return mapping[experianBand] ?? DomainRiskBand.UNKNOWN;
  }
}
```

The ACL principle: every concept from an external system that enters your domain must be translated into a domain concept at the adapter boundary. No external SDK types, response shapes, or error codes should ever appear in domain or application layer code.

## Section 5: Hexagonal vs. Related Architectures

**Q15. How does Hexagonal Architecture relate to Clean Architecture?**
A: Clean Architecture (Robert C. Martin, 2012) is a more detailed elaboration of the same core idea as Hexagonal Architecture. They share the same fundamental principle — the Dependency Rule (dependencies point inward) — but Clean Architecture names the layers more explicitly:

| Clean Architecture Layer | Hexagonal Architecture Equivalent        |
|---                       |---                                       |
| Entities                 | Domain Entities, Value Objects           |
| Use Cases                | Application Services, Use Cases          |
| Interface Adapters       | Driving Adapters (Controllers, Consumers)|
| Frameworks & Drivers     | Infrastructure (ORM, HTTP clients, SDKs) |
| Driven Adapters          | Driven Adapters (Repositories, Gateways) |

The practical difference: Hexagonal focuses on the *port and adapter* mechanism as the isolation boundary — the explicit interfaces and their implementations. Clean Architecture focuses on the *layer hierarchy* and dependency rule. In NestJS codebases, the two are typically combined: Hexagonal's port/adapter naming gives structure to Clean Architecture's layers.

**Q16. How does Hexagonal Architecture relate to Microservices?**
A: Hexagonal Architecture is the natural internal architecture for each microservice. The hexagon represents one service's domain; ports represent that service's API boundary:

- **Driving ports** become the service's API contract — REST endpoints, Kafka topics it consumes, gRPC methods it exposes.
- **Driven ports** represent the service's external dependencies — other services it calls (via HTTP client adapters, gRPC client adapters), databases it uses, message queues it publishes to.

The key insight: in a microservices system, every inter-service call is a driven port at the calling service and a driving port at the receiving service. The receiving service doesn't know (or care) whether it was called by a REST adapter, a Kafka consumer, or a gRPC service — because those are just driving adapters into its hexagon.

```ts
// Loan service's driven port — it depends on Credit Service
export interface CreditServicePort {
  checkEligibility(userId: string): Promise<EligibilityResult>;
}

// Adapter — calls Credit Service over HTTP
@Injectable()
export class CreditServiceHttpAdapter implements CreditServicePort {
  async checkEligibility(userId: string): Promise<EligibilityResult> {
    // HTTP call to the credit-service microservice
    const { data } = await this.http.get(`${CREDIT_SERVICE_URL}/eligibility/${userId}`);
    return { eligible: data.eligible, score: data.score };
  }
}

// Credit service's driving port — it is called by loan service
// The credit-service's REST controller is its driving adapter
// It doesn't know loan-service is calling it — just an HTTP request
@Controller("eligibility")
export class EligibilityController {
  @Get(":userId")
  async check(@Param("userId") userId: string): Promise<EligibilityResponseDto> {
    return this.checkEligibilityUseCase.execute(userId);
  }
}
```

## Section 6: Pitfalls & Anti-patterns

**Q17. What is "Leaky Abstraction" in Hexagonal Architecture and how do you prevent it?**
A: A leaky port abstraction is when the port interface exposes concepts from a specific technology rather than domain concepts. This defeats the purpose of the port — switching adapters would require changing the port (and thus the domain):

```ts
// LEAKY PORT — exposes TypeORM-specific QueryBuilder
export interface LoanRepositoryPort {
  findById(id: string): Promise<LoanOrmEntity>; // ❌ returns ORM entity — leaks TypeORM
  query(): SelectQueryBuilder<LoanOrmEntity>;    // ❌ exposes QueryBuilder — TypeORM-specific
  getManager(): EntityManager;                  // ❌ exposes EntityManager — TypeORM concept
}

// CLEAN PORT — speaks domain language only
export interface LoanRepositoryPort {
  findById(id: string): Promise<Loan | null>;           // ✅ returns domain Loan
  findByUserId(userId: string): Promise<Loan[]>;         // ✅ domain concept
  findByStatus(status: LoanStatus): Promise<Loan[]>;     // ✅ domain concept (LoanStatus)
  save(loan: Loan): Promise<void>;                       // ✅ domain entity
  existsActiveLoanForUser(userId: string): Promise<boolean>; // ✅ business query
}
```

Other leaky abstraction examples:
- Port returning `Observable<T>` (RxJS — NestJS-specific) instead of `Promise<T>`.
- Port accepting `Request` (Express/NestJS HTTP object) instead of a domain command.
- Port returning `HttpException` instead of a domain exception.
- Port methods named after database operations (`upsert`, `bulkInsert`) instead of domain operations (`save`, `saveAll`).

**Q18. What is "Port Explosion" and how do you manage it?**
A: Port Explosion happens when each infrastructure dependency gets its own port interface, resulting in dozens of tiny interfaces that are never reused and add complexity without benefit:

```ts
// EXPLOSION — one port per method
export interface FindLoanByIdPort { findById(id: string): Promise<Loan | null>; }
export interface SaveLoanPort { save(loan: Loan): Promise<void>; }
export interface FindLoansByUserPort { findByUserId(id: string): Promise<Loan[]>; }
export interface ExistsLoanPort { existsActive(userId: string): Promise<boolean>; }
// ... 20 more single-method ports
```

This is over-engineering — each adapter would implement 20 interfaces; each use case would inject 20 tokens. Group related operations into cohesive ports:

```ts
// COHESIVE — grouped by responsibility
export interface LoanRepositoryPort {       // read + write for loans
  findById(id: string): Promise<Loan | null>;
  findByUserId(userId: string): Promise<Loan[]>;
  save(loan: Loan): Promise<void>;
  existsActiveLoanForUser(userId: string): Promise<boolean>;
}

export interface CreditBureauPort {         // credit checking
  getCreditScore(userId: string, pan: string): Promise<CreditScore>;
}

export interface PaymentGatewayPort {       // payment operations
  disburse(loanId: string, amount: LoanAmount, accountId: string): Promise<DisbursementResult>;
  refund(transactionId: string, amount: LoanAmount): Promise<RefundResult>;
}
```

The Interface Segregation Principle (ISP) applies: don't split ports into single-method interfaces unless there's a genuine reason to have multiple implementations of each method independently. Split when different use cases have radically different dependency needs.

**Q19. What is "Hexagonal Purity Theater" and when is it over-engineering?**
A: Hexagonal Purity Theater is when the team rigidly applies all the structural rules (separate directories, explicit tokens, mappers for every entity) to a simple CRUD microservice where there is no meaningful domain logic and no realistic chance of swapping infrastructure:

```ts
// OVER-ENGINEERED for a simple CRUD service
// If the service is: create, read, update, delete user profiles
// with no business rules, no domain events, no complex invariants —
// a full hexagonal structure adds layers with zero return:

// Port
export interface UserProfileRepositoryPort {
  findById(id: string): Promise<UserProfile | null>;
  save(profile: UserProfile): Promise<void>;
}

// Domain entity — essentially the same as the ORM entity
export class UserProfile { /* name, email, phone — no behavior */ }

// Mapper — trivially copies fields
export class UserProfileMapper {
  static toDomain(orm: UserProfileOrmEntity): UserProfile { /* ... */ }
  static toOrm(domain: UserProfile): UserProfileOrmEntity { /* ... */ }
}
// ... all for a service that is just a SELECT/INSERT/UPDATE wrapper
```

Guidelines for when Hexagonal Architecture is worth the cost:
- **Apply fully** when: the service has genuine domain logic (approval workflows, BRE, financial calculations), multiple delivery mechanisms (REST + Kafka + gRPC), realistic adapter swapping plans (multiple payment gateways, multiple credit bureaus), or team size where domain isolation prevents cross-team coupling.
- **Apply partially** when: CRUD services where the repository interface alone (without the full mapper/domain-entity split) buys testability. Keep ports for driven dependencies; skip the mapper if domain and ORM entities are structurally identical.
- **Skip** when: tiny utilities, lambdas that run once, or prototypes where architecture investment is premature.

## Section 7: Scenario / System Design Style Questions

**Q20. "Your team is switching from PostgreSQL to MongoDB for the loan service. Walk me through what changes in a Hexagonal Architecture."**
A: This is the clearest demonstration of Hexagonal Architecture's value. With properly defined ports, the answer is: only the driven adapter changes.

```ts
// BEFORE — TypeORM PostgreSQL adapter
@Injectable()
export class TypeOrmLoanRepository implements LoanRepositoryPort {
  constructor(@InjectRepository(LoanOrmEntity) private readonly ormRepo: Repository<LoanOrmEntity>) {}

  async findById(id: string): Promise<Loan | null> {
    const entity = await this.ormRepo.findOne({ where: { id } });
    return entity ? LoanMapper.toDomain(entity) : null;
  }
  async save(loan: Loan): Promise<void> {
    await this.ormRepo.save(LoanMapper.toOrm(loan));
  }
}

// AFTER — Mongoose MongoDB adapter (same port interface, different implementation)
@Injectable()
export class MongooseLoanRepository implements LoanRepositoryPort {
  constructor(@InjectModel(LoanMongoDocument.name) private readonly model: Model<LoanMongoDocument>) {}

  async findById(id: string): Promise<Loan | null> {
    const doc = await this.model.findOne({ _id: id }).lean();
    return doc ? LoanMongoMapper.toDomain(doc) : null;
  }
  async save(loan: Loan): Promise<void> {
    await this.model.findOneAndUpdate(
      { _id: loan.id },
      LoanMongoMapper.toDocument(loan),
      { upsert: true }
    );
  }
}

// Module change — one line
@Module({
  providers: [
    {
      provide: LOAN_REPOSITORY_PORT,
      useClass: MongooseLoanRepository, // ← only this line changes
      // was: TypeOrmLoanRepository
    },
  ],
})
export class InfrastructureModule {}
```

What does NOT change:
- `Loan` domain entity — zero changes.
- `ApproveLoanUseCase` — zero changes.
- `LoanRepositoryPort` interface — zero changes.
- All use case tests — zero changes (they use `InMemoryLoanRepository`).
- All driving adapters (controllers, Kafka consumers) — zero changes.

What changes:
- The MongoDB adapter class (new file).
- The Mongoose data mapper (new file).
- One line in the module binding.

The entire migration is additive — no existing code is modified.

**Q21. "How would you structure a NACH payment processing service using Hexagonal Architecture?"**
A:
```ts
// Domain layer — NACH-specific domain model
export class NachMandate {
  private constructor(
    public readonly id: string,
    private _status: MandateStatus,
    public readonly userId: string,
    public readonly bankAccountId: string,
    public readonly maxAmount: LoanAmount,
    public readonly startDate: Date,
  ) {}

  activate(): void {
    if (this._status !== MandateStatus.PENDING) {
      throw new InvalidMandateStateError("Only pending mandates can be activated");
    }
    this._status = MandateStatus.ACTIVE;
  }

  canDebit(amount: LoanAmount): boolean {
    return this._status === MandateStatus.ACTIVE && amount.value <= this.maxAmount.value;
  }
}

// Driven ports — what NACH processing needs from outside
export interface NachMandateRepositoryPort {
  findById(id: string): Promise<NachMandate | null>;
  findActiveByUserId(userId: string): Promise<NachMandate | null>;
  save(mandate: NachMandate): Promise<void>;
}

export interface NachGatewayPort {
  registerMandate(userId: string, bankAccount: BankAccount): Promise<MandateRegistrationResult>;
  cancelMandate(mandateId: string): Promise<void>;
  debitMandate(mandateId: string, amount: LoanAmount, reference: string): Promise<DebitResult>;
}

export interface BankVerificationPort {
  verifyAccount(accountNumber: string, ifsc: string): Promise<AccountVerificationResult>;
}

// Application use cases
@Injectable()
export class RegisterNachMandateUseCase {
  constructor(
    @Inject(NACH_MANDATE_REPO)    private readonly mandateRepo: NachMandateRepositoryPort,
    @Inject(NACH_GATEWAY_PORT)    private readonly nachGateway: NachGatewayPort,
    @Inject(BANK_VERIFICATION)    private readonly bankVerifier: BankVerificationPort,
    @Inject(EVENT_PUBLISHER)      private readonly events: DomainEventPublisherPort,
  ) {}

  async execute(command: RegisterMandateCommand): Promise<NachMandate> {
    // Business rules in domain — pure, testable
    const existing = await this.mandateRepo.findActiveByUserId(command.userId);
    if (existing) throw new ActiveMandateExistsError(command.userId);

    const verification = await this.bankVerifier.verifyAccount(
      command.accountNumber, command.ifsc
    );
    if (!verification.valid) throw new InvalidBankAccountError(command.accountNumber);

    const registration = await this.nachGateway.registerMandate(
      command.userId,
      new BankAccount(command.accountNumber, command.ifsc, command.accountHolderName)
    );

    const mandate = NachMandate.create({
      userId: command.userId,
      bankAccountId: registration.mandateId,
      maxAmount: LoanAmount.of(command.maxAmountRupees),
      startDate: command.startDate,
    });

    await this.mandateRepo.save(mandate);
    await this.events.publish(new NachMandateRegisteredEvent(mandate.id, mandate.userId));
    return mandate;
  }
}
```

**Q22. "A team member argues that Hexagonal Architecture is just 'more abstraction for abstraction's sake' and that interfaces make the code harder to navigate. How do you respond?"**
A: The critique is valid for the wrong application of the pattern but not for the right one. Respond on three dimensions:

**Dimension 1 — The cost of abstraction is real but bounded:**
The cost is: one interface file per port, one adapter file per implementation, one mapper file per persistence adapter. In a service with 4 driven ports, that's ~12 extra files. The cost is linear and doesn't grow as the service grows.

**Dimension 2 — The benefit compounds over time:**
```ts
// Without ports — to add a third payment gateway, modify the service:
class LoanService {
  async disburse(): Promise<void> {
    if (gateway === "razorpay") { /* razorpay code */ }
    else if (gateway === "juspay") { /* juspay code */ }
    else if (gateway === "hdfc") { /* new HDFC code — must modify service */ }
  }
}

// With ports — add a new gateway by adding a new file, zero service changes:
class HdfcPaymentAdapter implements PaymentGatewayPort { /* ... */ }
// Register in module — done. Service untouched.
```

**Dimension 3 — "Harder to navigate" is an IDE problem, not an architecture problem:**
"Go to implementation" in any modern IDE resolves interfaces to their concrete implementations in one keystroke. The interface creates a *contract* that is navigated by intent (what the port promises) rather than implementation (how it happens) — this is more useful for understanding the system at a glance. A service that injects `PaymentGatewayPort` communicates its intent better than one that injects `RazorpayPaymentService`.

The honest counter: if a CRUD service has a single repository with zero chance of being swapped and no complex domain logic, the hexagonal structure adds real cost for minimal gain. Apply the pattern where it pays — complex domains, multiple delivery channels, realistically swappable adapters.

**Q23. "How do you handle database transactions in Hexagonal Architecture without leaking transaction management into the domain?"**
A: Transactions are an infrastructure concern — they should never appear in the domain or application layer. The driven port defines the *intent* (save multiple things atomically); the adapter implements it using database-specific transaction mechanics:

```ts
// Option 1 — Unit of Work pattern: port expresses atomicity
export interface UnitOfWorkPort {
  execute<T>(work: (repos: TransactionalRepos) => Promise<T>): Promise<T>;
}

interface TransactionalRepos {
  loans: LoanRepositoryPort;
  approvals: LoanApprovalRepositoryPort;
}

// Use case — expresses intent without knowing about transactions
@Injectable()
export class ApproveLoanUseCase {
  constructor(
    @Inject(UNIT_OF_WORK) private readonly uow: UnitOfWorkPort,
    @Inject(CREDIT_BUREAU) private readonly creditBureau: CreditBureauPort,
  ) {}

  async execute(command: ApproveLoanCommand): Promise<Loan> {
    const credit = await this.creditBureau.getCreditScore(command.approverId, command.approverPan);
    if (credit.score < 650) throw new CreditCheckFailedError(credit.score);

    return this.uow.execute(async ({ loans, approvals }) => {
      // All operations inside this callback are in one transaction
      const loan = await loans.findById(command.loanId);
      loan.approve(command.approverId);
      await loans.save(loan);
      await approvals.save(new LoanApproval(loan.id, command.approverId));
      return loan;
      // Transaction commits on return, rolls back on throw
    });
  }
}

// TypeORM Unit of Work adapter — transaction is here
@Injectable()
export class TypeOrmUnitOfWork implements UnitOfWorkPort {
  constructor(private readonly dataSource: DataSource) {}

  async execute<T>(work: (repos: TransactionalRepos) => Promise<T>): Promise<T> {
    return this.dataSource.transaction(async (manager) => {
      const repos: TransactionalRepos = {
        loans: new TypeOrmLoanRepository(manager.getRepository(LoanOrmEntity)),
        approvals: new TypeOrmApprovalRepository(manager.getRepository(ApprovalOrmEntity)),
      };
      return work(repos);
    });
  }
}
```

The domain expresses "do these things atomically"; the adapter decides that "atomically" means a PostgreSQL transaction. If the adapter switches to MongoDB multi-document transactions, the domain code is unchanged.

**Q24. "How does Hexagonal Architecture help when you need to run the same business logic in both an online (real-time API) and offline (batch processing) context?"**
A:
```ts
// Use case — context-agnostic business logic
@Injectable()
export class ProcessLoanRepaymentUseCase {
  constructor(
    @Inject(LOAN_REPO)       private readonly loanRepo: LoanRepositoryPort,
    @Inject(REPAYMENT_REPO)  private readonly repaymentRepo: RepaymentRepositoryPort,
    @Inject(PAYMENT_GATEWAY) private readonly paymentGateway: PaymentGatewayPort,
    @Inject(EVENT_PUBLISHER) private readonly events: DomainEventPublisherPort,
  ) {}

  async execute(command: ProcessRepaymentCommand): Promise<RepaymentResult> {
    const loan = await this.loanRepo.findById(command.loanId);
    const repayment = loan.processRepayment(command.amount, command.dueDate);
    const paymentResult = await this.paymentGateway.debit(
      loan.nachMandateId, command.amount, command.repaymentId
    );
    repayment.markSettled(paymentResult.transactionId);
    await this.repaymentRepo.save(repayment);
    await this.loanRepo.save(loan);
    await this.events.publish(new RepaymentProcessedEvent(repayment));
    return RepaymentResult.fromDomain(repayment);
  }
}

// Driving Adapter 1 — Online: REST API
// POST /repayments/:id/process → ProcessLoanRepaymentUseCase.execute()

// Driving Adapter 2 — Online: Kafka consumer for mandate debit results
// topic: "nach-debit-results" → ProcessLoanRepaymentUseCase.execute()

// Driving Adapter 3 — Offline: Batch processor (cron job)
@Injectable()
export class RepaymentBatchProcessor implements OnModuleInit {
  constructor(
    private readonly useCase: ProcessLoanRepaymentUseCase,
    private readonly dueDateRepo: DueDateRepositoryPort,
  ) {}

  @Cron("0 9 * * *") // 9 AM daily
  async processDueRepayments(): Promise<void> {
    const dueRepayments = await this.dueDateRepo.findDueToday();

    const results = await Promise.allSettled(
      dueRepayments.map(r =>
        this.useCase.execute(new ProcessRepaymentCommand(r.loanId, r.amount, r.dueDate, r.id))
      )
    );

    // Log failures — don't crash the batch on individual failures
    results.forEach((result, i) => {
      if (result.status === "rejected") {
        logger.error({ loanId: dueRepayments[i].loanId, error: result.reason });
      }
    });
  }
}
```

The business logic — process a repayment, update loan state, record payment, publish event — runs identically online and offline. The only difference is the driving adapter: a REST controller vs. a cron job. Both call the same use case.

**Q25. "How do you structure a NestJS module system to enforce Hexagonal Architecture boundaries at the module level — preventing infrastructure from leaking into the domain?"**
A: Use NestJS module boundaries and TypeScript path aliases together to make boundary violations a compile-time error:

```ts
// tsconfig.json — path aliases enforce import boundaries
{
  "compilerOptions": {
    "paths": {
      "@domain/*":          ["src/domain/*"],
      "@application/*":     ["src/application/*"],
      "@infrastructure/*":  ["src/infrastructure/*"]
    }
  }
}

// ESLint import/no-restricted-paths rule — architectural boundary enforcement
// .eslintrc.js
{
  rules: {
    "import/no-restricted-paths": ["error", {
      zones: [
        {
          // Domain may not import from application or infrastructure
          target: "./src/domain",
          from: ["./src/application", "./src/infrastructure"],
          message: "Domain layer must not depend on application or infrastructure layers",
        },
        {
          // Application may not import from infrastructure
          target: "./src/application",
          from: ["./src/infrastructure"],
          message: "Application layer must not depend on infrastructure layer",
        },
      ],
    }],
  },
}

// NestJS module structure — each layer is a module
@Module({
  // Domain module — no imports from infrastructure
  providers: [
    // Domain services only — pure business logic
    LoanApprovalDomainService,
    LoanEligibilityPolicy,
  ],
  exports: [
    // Export domain services AND port tokens (for use case injection)
    LoanApprovalDomainService,
    LoanEligibilityPolicy,
  ],
})
export class DomainModule {}

@Module({
  imports: [DomainModule], // Application depends on Domain
  providers: [
    ApproveLoanUseCase,
    CreateLoanUseCase,
    GetLoanUseCase,
  ],
  exports: [
    // Export use cases — these ARE the driving port implementations
    ApproveLoanUseCase,
    CreateLoanUseCase,
    GetLoanUseCase,
  ],
})
export class ApplicationModule {}

@Module({
  imports: [
    ApplicationModule,     // Infrastructure wires into Application
    TypeOrmModule.forFeature([LoanOrmEntity]),
    HttpModule,
  ],
  providers: [
    // Bind driven ports to their adapters
    { provide: LOAN_REPOSITORY_PORT, useClass: TypeOrmLoanRepository },
    { provide: CREDIT_BUREAU_PORT,   useClass: ExperianCreditBureauAdapter },
    { provide: PAYMENT_GATEWAY_PORT, useClass: RazorpayPaymentAdapter },
    { provide: DOMAIN_EVENT_PUBLISHER, useClass: KafkaDomainEventPublisherAdapter },
  ],
  // Driving adapters (controllers) declared here
})
export class InfrastructureModule {}

@Module({
  imports: [InfrastructureModule], // App module only imports infrastructure
  controllers: [LoanController],   // Controllers are in infrastructure — registered at top
})
export class AppModule {}
```

With this setup: if a domain class accidentally imports `TypeOrmLoanRepository`, ESLint raises an error. If an application use case accidentally imports `HttpModule`, ESLint raises an error. The architecture boundary is enforced by tooling, not just convention.

## Quick Comparison Table

| Aspect                    | Layered (MVC+S)                              | Hexagonal Architecture                              | Clean Architecture                                   |
|---                        |---                                           |---                                                  |---                                                   |
| Primary goal              | Separate presentation from logic from data   | Isolate domain from ALL external systems            | Strict layering with explicit dependency rule        |
| Database position         | Bottom of the stack — foundational           | Just another adapter — symmetrical with HTTP        | Frameworks & Drivers layer — outermost               |
| Port concept              | Implicit — interfaces between layers         | Explicit — named, defined by domain, bidirectional  | Interface Adapters layer maps between layers         |
| Dependency direction      | Top-down (presentation → data)               | Inward (everything → domain)                        | Inward (Dependency Rule — always toward Entities)    |
| Test approach             | Mock the layer below                         | In-memory adapters implement the port               | Same as Hexagonal — test inner rings independently   |
| Framework coupling        | Framework often in service layer             | Framework entirely outside the hexagon              | Framework in outermost ring — Entities untouched     |
| Multi-channel support     | Requires discipline                          | Natural — each channel is a driving adapter         | Natural — each channel is an Interface Adapter       |
| Adapter swapping          | Possible but requires service changes        | Change adapter file only — domain untouched         | Same as Hexagonal                                    |
| Complexity overhead       | Low — familiar structure                     | Medium — ports + adapters + mappers                 | High — many named layers, strict rules               |
| Best for                  | Simple to moderate CRUD APIs                 | Complex domains with multiple delivery channels     | Large teams, long-lived systems, strict DDD          |

---

**Tip for the interview:** At the 5 YOE level, Hexagonal Architecture questions don't arrive as "explain ports and adapters." They arrive as: "how would you change the payment gateway without touching business logic?", "how do you run the same repayment logic from both a REST API and a cron job?", "how do you test your domain logic without a database?", and "what's your database migration strategy?" The pattern is the answer to all four. The strongest answers demonstrate understanding of *why* — the Dependency Rule is what makes the domain testable, portable, and stable — and connect it to tools your stack already uses: NestJS injection tokens as the port binding mechanism, TypeScript interfaces as the port definitions, in-memory adapters as test doubles, and ESLint import rules as architectural enforcement. Have a concrete story: a service where you extracted the payment gateway behind a port and swapping from Razorpay to JusPay was three files and zero business logic changes — that's the answer that lands at 5 YOE.
