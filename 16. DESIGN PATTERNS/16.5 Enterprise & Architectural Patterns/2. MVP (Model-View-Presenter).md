# Enterprise & Architectural Patterns: MVP (Model-View-Presenter) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the MVP pattern?**
A: MVP (Model-View-Presenter) is an architectural pattern that separates a user interface into three distinct components: the **Model** (data, business logic, and domain rules), the **View** (the UI surface — what the user sees and interacts with), and the **Presenter** (the intermediary that drives the View and reacts to its events, while orchestrating the Model). The defining characteristic of MVP over its predecessor MVC is that the View is *passive* — it renders exactly what the Presenter tells it to and forwards every user interaction to the Presenter without making any decisions itself. The Presenter holds all presentation logic; the View holds none.

**Q2. What problem does MVP solve, and what breaks without it?**
A: MVP solves the *testability and separation problem* in UI-heavy applications. Without it, UI components typically embed business and presentation logic directly — a button's click handler fetches data, transforms it, validates it, and updates other UI elements, all in one place. This makes the logic:
- **Untestable without a running UI** — you cannot exercise a button's logic without simulating a click in a real or headless browser.
- **Tightly coupled to the rendering framework** — logic written inside a React component, Angular component, or Android Activity cannot be reused or moved.
- **Hard to reason about** — the same class handles rendering, event handling, data fetching, validation, and error display simultaneously.

MVP breaks this by extracting all of that logic into the Presenter, which has no dependency on the UI framework. The Presenter is a plain TypeScript / Java / Python class — it can be instantiated and exercised in a unit test with a mock View, with zero browser or DOM involvement.

**Q3. What are the three components of MVP and what are their precise responsibilities?**
A:

**Model:**
- Encapsulates domain data, business rules, and data access (repository calls, API calls, local storage).
- Has no knowledge of the View or the Presenter.
- Notifies interested parties (typically the Presenter) when its state changes — via callbacks, Observables, or events.
- In a well-designed system, the Model is the same regardless of whether the UI is a web form, a mobile screen, or a CLI.

**View:**
- Renders data and UI elements as instructed by the Presenter.
- Forwards every user interaction (button clicks, form input, scroll events) to the Presenter without interpreting them.
- Exposes a narrow interface (`IView`) through which the Presenter calls it — methods like `displayLoanAmount(amount: string)`, `showError(message: string)`, `setSubmitButtonEnabled(enabled: boolean)`.
- Contains zero conditional logic, zero data transformation, zero business rules. It is a pure rendering surface.
- In frontend MVP: the View is typically an Angular component, a React component with no state logic, or a plain HTML page with event listeners wired to the Presenter. In backend MVP variants: the View is a template renderer (Handlebars, Pug, Thymeleaf).

**Presenter:**
- Mediates between Model and View.
- Subscribes to View events and reacts to them by calling Model methods and then updating the View.
- Transforms raw domain data from the Model into View-appropriate display data (formatting amounts, computing labels, deriving display states).
- Holds all conditional presentation logic (`if loan is rejected, show rejection reason; else show approval amount`).
- Has no direct dependency on the UI framework — it talks to the View only through the `IView` interface.
- Is the primary target of unit tests — mock the View, mock the Model, test the Presenter in isolation.

**Q4. What is the key structural difference between MVP and MVC?**
A: The difference lies in who controls the View and where presentation logic lives:

| Dimension                   | MVC                                                                  | MVP                                                                     |
|-----------------------------|----------------------------------------------------------------------|-------------------------------------------------------------------------|
| View awareness of Model     | View often observes Model directly (Observer pattern)                | View never touches Model — all data flows through Presenter             |
| Who updates the View        | Controller triggers update; View reads from Model itself             | Presenter updates the View explicitly via interface calls               |
| Presentation logic location | Spread across Controller and View                                    | All in Presenter — View is passive                                      |
| View passivity              | View is active — it reads Model and decides what to render           | View is passive — it renders only what Presenter instructs              |
| Testability of UI logic     | Controller testable; View logic often requires browser / framework   | Presenter fully testable with a mock View; zero framework dependency    |
| Coupling                    | Controller coupled to View type (usually)                            | Presenter coupled only to IView interface — swappable Views             |
| Typical habitat             | Web frameworks (Rails, Django, ASP.NET MVC), server-rendered pages   | Rich client apps (Android, WinForms, Angular), component-heavy frontends |

**Q5. What are the two main variants of MVP — Passive View and Supervising Controller — and how do they differ?**
A: Both are sub-patterns within the MVP family, distinguished by how much logic the View retains:

**Passive View (strict MVP):**
- The View is completely dumb — it has no data-binding, no computed properties, no conditional rendering logic.
- Every piece of display state is explicitly pushed by the Presenter via individual method calls: `view.setUserName("Ravi")`, `view.setBalanceText("₹12,500")`, `view.showErrorBanner(true)`.
- Maximum testability: the Presenter test can verify exactly which View methods were called with which arguments.
- Higher ceremony: the View interface grows large as every display property becomes a method.

**Supervising Controller (relaxed MVP):**
- The View handles simple, mechanical data binding — binding a `user.name` property directly to a text field — without any logic.
- The Presenter handles all non-trivial logic: formatting, conditional display, multi-field derivations.
- Less ceremony: the Presenter doesn't have to push every single display value; simple bindings are automatic.
- Slightly reduced testability: the data-binding layer is harder to verify in unit tests without some form of binding inspection.

At 5 YOE, Passive View is the variant most interviewers mean when they say MVP. Supervising Controller blurs toward MVVM (which is essentially Supervising Controller with reactive two-way data binding as first-class infrastructure).

## Section 2: Structure & Implementation

**Q6. Walk through a canonical TypeScript MVP implementation for a loan application form.**
A:

```typescript
// ─── Model ────────────────────────────────────────────────────────────────────

interface LoanApplicationDto {
  applicantName:    string;
  panNumber:        string;
  requestedAmount:  number;   // in paise
  tenureMonths:     number;
}

interface LoanDecision {
  approved:               boolean;
  sanctionedAmountInPaise?: number;
  rejectionReason?:         string;
  emiInPaise?:              number;
}

class LoanApplicationModel {
  async submit(dto: LoanApplicationDto): Promise<LoanDecision> {
    const response = await fetch("/api/loans/apply", {
      method:  "POST",
      headers: { "Content-Type": "application/json" },
      body:    JSON.stringify(dto),
    });
    if (!response.ok) throw new Error(`API error: ${response.status}`);
    return response.json();
  }

  async fetchEligibility(pan: string): Promise<{ maxEligibleAmountInPaise: number }> {
    const response = await fetch(`/api/loans/eligibility?pan=${encodeURIComponent(pan)}`);
    if (!response.ok) throw new Error("Eligibility check failed");
    return response.json();
  }
}

// ─── View Interface (IView) — the contract the Presenter programs against ──────

interface ILoanApplicationView {
  // Display methods — Presenter pushes data
  setApplicantName(name: string): void;
  setMaxEligibleAmount(displayText: string): void;
  displayApprovalResult(emiText: string, sanctionedText: string): void;
  displayRejectionResult(reason: string): void;
  showLoadingSpinner(visible: boolean): void;
  showErrorMessage(message: string): void;
  clearErrorMessage(): void;
  setSubmitButtonEnabled(enabled: boolean): void;
  highlightField(fieldName: string, isError: boolean): void;

  // Event registration — Presenter subscribes to View events
  onSubmitClicked(handler: () => void): void;
  onPanChanged(handler: (pan: string) => void): void;
  onAmountChanged(handler: (amountText: string) => void): void;
  onTenureChanged(handler: (months: number) => void): void;
}

// ─── Presenter ────────────────────────────────────────────────────────────────

class LoanApplicationPresenter {
  private applicantName   = "";
  private pan             = "";
  private amountInPaise   = 0;
  private tenureMonths    = 0;
  private maxEligible     = 0;

  constructor(
    private readonly view:  ILoanApplicationView,
    private readonly model: LoanApplicationModel,
  ) {
    this.bindViewEvents();
  }

  // Called once after construction — wires View events to Presenter handlers
  private bindViewEvents(): void {
    this.view.onPanChanged(pan => this.handlePanChanged(pan));
    this.view.onAmountChanged(text => this.handleAmountChanged(text));
    this.view.onTenureChanged(months => this.handleTenureChanged(months));
    this.view.onSubmitClicked(() => this.handleSubmit());
  }

  // ── Event Handlers ──────────────────────────────────────────────────────────

  private async handlePanChanged(pan: string): Promise<void> {
    this.pan = pan.toUpperCase().trim();

    // Validate PAN format first
    if (!this.isValidPan(this.pan)) {
      this.view.highlightField("pan", true);
      this.view.showErrorMessage("Enter a valid 10-character PAN number");
      this.view.setSubmitButtonEnabled(false);
      return;
    }

    this.view.highlightField("pan", false);
    this.view.clearErrorMessage();

    // Fetch eligibility once PAN is valid
    try {
      this.view.showLoadingSpinner(true);
      const { maxEligibleAmountInPaise } = await this.model.fetchEligibility(this.pan);
      this.maxEligible = maxEligibleAmountInPaise;
      this.view.setMaxEligibleAmount(this.formatCurrency(maxEligibleAmountInPaise));
    } catch {
      this.view.showErrorMessage("Could not fetch eligibility — please try again");
    } finally {
      this.view.showLoadingSpinner(false);
    }

    this.validateAndToggleSubmit();
  }

  private handleAmountChanged(text: string): void {
    const parsed = parseFloat(text.replace(/[₹,]/g, ""));
    this.amountInPaise = isNaN(parsed) ? 0 : Math.round(parsed * 100);

    if (this.amountInPaise > this.maxEligible) {
      this.view.highlightField("amount", true);
      this.view.showErrorMessage(
        `Maximum eligible amount is ${this.formatCurrency(this.maxEligible)}`
      );
    } else {
      this.view.highlightField("amount", false);
      this.view.clearErrorMessage();
    }

    this.validateAndToggleSubmit();
  }

  private handleTenureChanged(months: number): void {
    this.tenureMonths = months;
    this.validateAndToggleSubmit();
  }

  private async handleSubmit(): Promise<void> {
    if (!this.isFormValid()) return;

    this.view.setSubmitButtonEnabled(false);
    this.view.showLoadingSpinner(true);
    this.view.clearErrorMessage();

    try {
      const decision = await this.model.submit({
        applicantName:   this.applicantName,
        panNumber:       this.pan,
        requestedAmount: this.amountInPaise,
        tenureMonths:    this.tenureMonths,
      });

      if (decision.approved && decision.sanctionedAmountInPaise && decision.emiInPaise) {
        this.view.displayApprovalResult(
          `Monthly EMI: ${this.formatCurrency(decision.emiInPaise)}`,
          `Sanctioned: ${this.formatCurrency(decision.sanctionedAmountInPaise)}`,
        );
      } else {
        this.view.displayRejectionResult(decision.rejectionReason ?? "Application not approved");
      }
    } catch (err: any) {
      this.view.showErrorMessage("Submission failed — please try again");
      this.view.setSubmitButtonEnabled(true);
    } finally {
      this.view.showLoadingSpinner(false);
    }
  }

  // ── Helpers ─────────────────────────────────────────────────────────────────

  private isValidPan(pan: string): boolean {
    return /^[A-Z]{5}[0-9]{4}[A-Z]$/.test(pan);
  }

  private isFormValid(): boolean {
    return (
      this.isValidPan(this.pan) &&
      this.amountInPaise > 0 &&
      this.amountInPaise <= this.maxEligible &&
      this.tenureMonths > 0
    );
  }

  private validateAndToggleSubmit(): void {
    this.view.setSubmitButtonEnabled(this.isFormValid());
  }

  private formatCurrency(paise: number): string {
    return `₹${(paise / 100).toLocaleString("en-IN")}`;
  }
}

// ─── Concrete View (e.g., a plain DOM implementation) ─────────────────────────

class LoanApplicationDomView implements ILoanApplicationView {
  private readonly submitBtn  = document.getElementById("submit-btn")  as HTMLButtonElement;
  private readonly panInput   = document.getElementById("pan-input")   as HTMLInputElement;
  private readonly amountInput = document.getElementById("amount-input") as HTMLInputElement;
  private readonly spinner    = document.getElementById("spinner")     as HTMLElement;
  private readonly errorBox   = document.getElementById("error-box")   as HTMLElement;
  private readonly resultBox  = document.getElementById("result-box")  as HTMLElement;
  private readonly eligText   = document.getElementById("eligible-amt") as HTMLElement;

  setApplicantName(name: string): void {
    (document.getElementById("applicant-name") as HTMLElement).textContent = name;
  }
  setMaxEligibleAmount(displayText: string): void { this.eligText.textContent = displayText; }
  displayApprovalResult(emiText: string, sanctionedText: string): void {
    this.resultBox.innerHTML = `<p class="success">${sanctionedText}</p><p>${emiText}</p>`;
  }
  displayRejectionResult(reason: string): void {
    this.resultBox.innerHTML = `<p class="rejected">Not Approved: ${reason}</p>`;
  }
  showLoadingSpinner(visible: boolean): void { this.spinner.style.display = visible ? "block" : "none"; }
  showErrorMessage(message: string): void { this.errorBox.textContent = message; this.errorBox.style.display = "block"; }
  clearErrorMessage(): void { this.errorBox.textContent = ""; this.errorBox.style.display = "none"; }
  setSubmitButtonEnabled(enabled: boolean): void { this.submitBtn.disabled = !enabled; }
  highlightField(fieldName: string, isError: boolean): void {
    const el = document.getElementById(`${fieldName}-input`);
    if (el) el.classList.toggle("error", isError);
  }

  onSubmitClicked(handler: () => void): void { this.submitBtn.addEventListener("click", handler); }
  onPanChanged(handler: (pan: string) => void): void {
    this.panInput.addEventListener("input", e => handler((e.target as HTMLInputElement).value));
  }
  onAmountChanged(handler: (text: string) => void): void {
    this.amountInput.addEventListener("input", e => handler((e.target as HTMLInputElement).value));
  }
  onTenureChanged(handler: (months: number) => void): void {
    document.getElementById("tenure-select")!.addEventListener("change", e =>
      handler(parseInt((e.target as HTMLSelectElement).value, 10))
    );
  }
}

// ─── Composition root ─────────────────────────────────────────────────────────

const view      = new LoanApplicationDomView();
const model     = new LoanApplicationModel();
const presenter = new LoanApplicationPresenter(view, model);
```

**Q7. How do you unit-test the Presenter in isolation with a mock View?**
A: Because the Presenter depends only on `ILoanApplicationView` (an interface) and `LoanApplicationModel`, both can be replaced with mocks in tests — zero DOM, zero browser, zero network:

```typescript
// ─── Mock View ────────────────────────────────────────────────────────────────

class MockLoanApplicationView implements ILoanApplicationView {
  // Recorded calls — test assertions inspect these
  calls: { method: string; args: unknown[] }[] = [];

  private record(method: string, ...args: unknown[]): void {
    this.calls.push({ method, args });
  }

  // Stored event handlers — tests trigger them directly
  private handlers: Record<string, Function> = {};

  setApplicantName(name: string): void              { this.record("setApplicantName", name); }
  setMaxEligibleAmount(text: string): void          { this.record("setMaxEligibleAmount", text); }
  displayApprovalResult(emi: string, amt: string):void { this.record("displayApprovalResult", emi, amt); }
  displayRejectionResult(reason: string): void      { this.record("displayRejectionResult", reason); }
  showLoadingSpinner(visible: boolean): void        { this.record("showLoadingSpinner", visible); }
  showErrorMessage(message: string): void           { this.record("showErrorMessage", message); }
  clearErrorMessage(): void                         { this.record("clearErrorMessage"); }
  setSubmitButtonEnabled(enabled: boolean): void    { this.record("setSubmitButtonEnabled", enabled); }
  highlightField(field: string, isError: boolean): void { this.record("highlightField", field, isError); }

  onSubmitClicked(handler: () => void): void        { this.handlers["submit"] = handler; }
  onPanChanged(handler: (pan: string) => void): void { this.handlers["pan"] = handler; }
  onAmountChanged(handler: (t: string) => void): void { this.handlers["amount"] = handler; }
  onTenureChanged(handler: (m: number) => void): void { this.handlers["tenure"] = handler; }

  // Test helpers — simulate user actions
  simulatePanInput(pan: string): void      { this.handlers["pan"]?.(pan); }
  simulateAmountInput(text: string): void  { this.handlers["amount"]?.(text); }
  simulateTenureSelect(months: number): void { this.handlers["tenure"]?.(months); }
  simulateSubmitClick(): void              { this.handlers["submit"]?.(); }

  // Assertion helpers
  wasCalledWith(method: string, ...args: unknown[]): boolean {
    return this.calls.some(
      c => c.method === method && JSON.stringify(c.args) === JSON.stringify(args)
    );
  }
  lastCallTo(method: string): unknown[] | undefined {
    return [...this.calls].reverse().find(c => c.method === method)?.args;
  }
}

// ─── Mock Model ───────────────────────────────────────────────────────────────

class MockLoanApplicationModel extends LoanApplicationModel {

  submissionResult: LoanDecision = { approved: true, sanctionedAmountInPaise: 500000, emiInPaise: 11000 };
  shouldThrow = false;

  async fetchEligibility(_pan: string) {
    if (this.shouldThrow) throw new Error("Network error");
    return this.eligibilityResult;
  }

  async submit(_dto: LoanApplicationDto): Promise<LoanDecision> {
    if (this.shouldThrow) throw new Error("Submission failed");
    return this.submissionResult;
  }
}

// ─── Tests ────────────────────────────────────────────────────────────────────

describe("LoanApplicationPresenter", () => {
  let view:      MockLoanApplicationView;
  let model:     MockLoanApplicationModel;
  let presenter: LoanApplicationPresenter;

  beforeEach(() => {
    view      = new MockLoanApplicationView();
    model     = new MockLoanApplicationModel();
    presenter = new LoanApplicationPresenter(view, model);
  });

  it("should disable submit button when PAN format is invalid", () => {
    view.simulatePanInput("INVALID");
    expect(view.wasCalledWith("setSubmitButtonEnabled", false)).toBe(true);
    expect(view.wasCalledWith("highlightField", "pan", true)).toBe(true);
  });

  it("should fetch eligibility and display max eligible amount when PAN is valid", async () => {
    model.eligibilityResult = { maxEligibleAmountInPaise: 2000000 };
    view.simulatePanInput("ABCDE1234F");
    await Promise.resolve();   // flush async handlePanChanged

    expect(view.wasCalledWith("setMaxEligibleAmount", "₹20,000")).toBe(true);
  });

  it("should enable submit button only when all fields are valid", () => {
    view.simulatePanInput("ABCDE1234F");
    view.simulateAmountInput("5000");
    view.simulateTenureSelect(12);

    const lastCall = view.lastCallTo("setSubmitButtonEnabled");
    expect(lastCall?.[0]).toBe(true);
  });

  it("should display approval result on successful submission", async () => {
    model.submissionResult = { approved: true, sanctionedAmountInPaise: 500000, emiInPaise: 11000 };
    view.simulatePanInput("ABCDE1234F");
    view.simulateAmountInput("5000");
    view.simulateTenureSelect(12);
    view.simulateSubmitClick();
    await Promise.resolve();

    expect(view.wasCalledWith("displayApprovalResult",
      "Monthly EMI: ₹110", "Sanctioned: ₹5,000")).toBe(true);
  });

  it("should display rejection reason when application is rejected", async () => {
    model.submissionResult = { approved: false, rejectionReason: "Low CIBIL score" };
    view.simulatePanInput("ABCDE1234F");
    view.simulateAmountInput("5000");
    view.simulateTenureSelect(12);
    view.simulateSubmitClick();
    await Promise.resolve();

    expect(view.wasCalledWith("displayRejectionResult", "Low CIBIL score")).toBe(true);
  });

  it("should show error and re-enable submit on network failure", async () => {
    model.shouldThrow = true;
    view.simulatePanInput("ABCDE1234F");
    view.simulateAmountInput("5000");
    view.simulateTenureSelect(12);
    view.simulateSubmitClick();
    await Promise.resolve();

    expect(view.wasCalledWith("showErrorMessage", "Submission failed — please try again")).toBe(true);
    expect(view.wasCalledWith("setSubmitButtonEnabled", true)).toBe(true);
  });
});
```

Zero DOM, zero network, zero framework — 6 meaningful tests, each running in under 1ms.

**Q8. How do you implement the View interface in a React component while maintaining the Passive View contract?**
A: In React, the Passive View contract means the component holds zero local state and zero presentation logic — it is a pure rendering surface driven entirely by the Presenter:

```typescript
// ─── React Passive View implementation ───────────────────────────────────────

interface LoanFormState {
  maxEligibleText:    string;
  submitEnabled:      boolean;
  spinnerVisible:     boolean;
  errorMessage:       string;
  panError:           boolean;
  amountError:        boolean;
  resultHtml:         string;
}

// The View is a React component but holds NO logic — only calls Presenter handlers
const LoanApplicationView: React.FC = () => {
  // Presenter is created once outside the component (or via context)
  const presenterRef = useRef<LoanApplicationPresenter | null>(null);

  // All display state is owned by the Presenter and pushed via these setters
  const [displayState, setDisplayState] = useState<LoanFormState>({
    maxEligibleText: "", submitEnabled: false, spinnerVisible: false,
    errorMessage: "", panError: false, amountError: false, resultHtml: "",
  });

  // ILoanApplicationView implementation as a ref-stable adapter
  const viewAdapter = useMemo<ILoanApplicationView>(() => ({
    setApplicantName: (_name) => {},
    setMaxEligibleAmount: (text) => setDisplayState(s => ({ ...s, maxEligibleText: text })),
    displayApprovalResult: (emi, amt) =>
      setDisplayState(s => ({ ...s, resultHtml: `<p>${amt}</p><p>${emi}</p>` })),
    displayRejectionResult: (reason) =>
      setDisplayState(s => ({ ...s, resultHtml: `<p class="rejected">${reason}</p>` })),
    showLoadingSpinner: (v) => setDisplayState(s => ({ ...s, spinnerVisible: v })),
    showErrorMessage: (msg) => setDisplayState(s => ({ ...s, errorMessage: msg })),
    clearErrorMessage: () => setDisplayState(s => ({ ...s, errorMessage: "" })),
    setSubmitButtonEnabled: (e) => setDisplayState(s => ({ ...s, submitEnabled: e })),
    highlightField: (field, isError) =>
      setDisplayState(s => ({
        ...s,
        panError:    field === "pan"    ? isError : s.panError,
        amountError: field === "amount" ? isError : s.amountError,
      })),
    // Event wiring — the adapter stores handlers; the JSX calls them
    onSubmitClicked:  (h) => { handlers.current.submit = h; },
    onPanChanged:     (h) => { handlers.current.pan = h; },
    onAmountChanged:  (h) => { handlers.current.amount = h; },
    onTenureChanged:  (h) => { handlers.current.tenure = h; },
  }), []);

  const handlers = useRef<Record<string, Function>>({});

  useEffect(() => {
    presenterRef.current = new LoanApplicationPresenter(viewAdapter, new LoanApplicationModel());
    // No cleanup needed unless Presenter holds subscriptions
  }, [viewAdapter]);

  // ─── Rendering — pure display, zero logic ──────────────────────────────────
  return (
    <div className="loan-form">
      {displayState.spinnerVisible && <div className="spinner" />}
      {displayState.errorMessage   && <div className="error-box">{displayState.errorMessage}</div>}

      <input
        id="pan-input"
        className={displayState.panError ? "error" : ""}
        placeholder="PAN Number"
        onChange={e => handlers.current.pan?.(e.target.value)}
      />

      <input
        id="amount-input"
        className={displayState.amountError ? "error" : ""}
        placeholder="Loan Amount"
        onChange={e => handlers.current.amount?.(e.target.value)}
      />

      {displayState.maxEligibleText &&
        <p>Max eligible: {displayState.maxEligibleText}</p>}

      <select onChange={e => handlers.current.tenure?.(parseInt(e.target.value, 10))}>
        <option value="">Select tenure</option>
        {[12, 24, 36, 48, 60].map(m => <option key={m} value={m}>{m} months</option>)}
      </select>

      <button
        disabled={!displayState.submitEnabled}
        onClick={() => handlers.current.submit?.()}
      >
        Apply
      </button>

      {displayState.resultHtml &&
        <div dangerouslySetInnerHTML={{ __html: displayState.resultHtml }} />}
    </div>
  );
};
```

The React component contains no `if/else` over business state, no data fetching, no validation — it maps `displayState` to JSX and wires DOM events to the Presenter's handlers.

**Q9. How does MVP handle navigation between screens — who decides when to navigate?**
A: Navigation is a Presenter concern — the View exposes a `navigateTo(screen)` method (or a specific `navigateToLoanStatus()` method) which the Presenter calls after the appropriate business event:

```typescript
interface ILoanApplicationView {
  // ... other methods
  navigateToLoanStatus(loanId: string): void;
  navigateToRejectionHelp(): void;
}

// In Presenter:
private async handleSubmit(): Promise<void> {
  const decision = await this.model.submit(dto);
  if (decision.approved) {
    // Presenter decides navigation target based on business outcome
    this.view.navigateToLoanStatus(decision.loanId!);
  } else {
    this.view.navigateToRejectionHelp();
  }
}

// In concrete View (React):
navigateToLoanStatus(loanId: string): void {
  // In React Router:
  router.push(`/loans/${loanId}/status`);
  // In Angular:
  this.router.navigate(["/loans", loanId, "status"]);
}
```

The Presenter knows *when* and *why* to navigate (business logic); the View knows *how* to navigate (framework API). This means navigation decisions are fully unit-testable — verify that `view.navigateToLoanStatus` was called with the correct loan ID.

**Q10. How should the Presenter handle its own lifecycle — initialization, data pre-loading, and cleanup?**
A:

```typescript
class LoanDashboardPresenter {
  private subscriptions: (() => void)[] = [];

  constructor(
    private readonly view:  ILoanDashboardView,
    private readonly model: LoanDashboardModel,
  ) {}

  // Called by the View/framework when the screen appears
  async onViewAttached(): Promise<void> {
    this.bindViewEvents();
    await this.loadInitialData();
  }

  // Called by the View/framework when the screen disappears or component unmounts
  onViewDetached(): void {
    this.subscriptions.forEach(unsub => unsub());
    this.subscriptions = [];
  }

  private bindViewEvents(): void {
    this.view.onRefreshRequested(() => this.loadInitialData());
    this.view.onLoanSelected(loanId => this.handleLoanSelected(loanId));
  }

  private async loadInitialData(): Promise<void> {
    this.view.showLoadingSpinner(true);
    try {
      const [loans, summary] = await Promise.all([
        this.model.fetchActiveLoans(),
        this.model.fetchPortfolioSummary(),
      ]);
      this.view.displayLoans(loans.map(l => this.mapToDisplayLoan(l)));
      this.view.displayPortfolioSummary({
        totalOutstanding: this.formatCurrency(summary.totalOutstandingInPaise),
        nextEmiDue:       this.formatDate(summary.nextEmiDueDate),
        overdueCount:     summary.overdueCount,
      });
    } catch {
      this.view.showErrorMessage("Failed to load dashboard — pull to refresh");
    } finally {
      this.view.showLoadingSpinner(false);
    }
  }

  // Subscribe to a real-time model observable — store cleanup callback
  private subscribeToLiveUpdates(): void {
    const unsub = this.model.onLoanStatusChanged(update => {
      this.view.updateLoanStatus(update.loanId, update.newStatus);
    });
    this.subscriptions.push(unsub);
  }

  private mapToDisplayLoan(loan: Loan): DisplayLoan {
    return {
      id:           loan.id,
      productName:  loan.productName,
      statusLabel:  this.statusToLabel(loan.status),
      statusColour: this.statusToColour(loan.status),
      emiText:      `₹${(loan.emiInPaise / 100).toLocaleString("en-IN")} / month`,
      dueText:      `Due: ${this.formatDate(loan.nextEmiDue)}`,
    };
  }

  private statusToLabel(status: LoanStatus): string {
    const labels: Record<LoanStatus, string> = {
      ACTIVE: "Active", OVERDUE: "Overdue", CLOSED: "Closed", PRECLOSED: "Pre-closed",
    };
    return labels[status] ?? status;
  }

  private statusToColour(status: LoanStatus): string {
    return status === "OVERDUE" ? "#D32F2F" : status === "ACTIVE" ? "#388E3C" : "#757575";
  }

  private formatCurrency(paise: number): string {
    return `₹${(paise / 100).toLocaleString("en-IN")}`;
  }

  private formatDate(date: Date): string {
    return new Intl.DateTimeFormat("en-IN", { day: "2-digit", month: "short", year: "numeric" }).format(date);
  }
}
```

The lifecycle hooks (`onViewAttached` / `onViewDetached`) are called by the framework glue code — in Angular as `ngOnInit` / `ngOnDestroy`, in React as `useEffect` setup/cleanup, in Android as `onResume` / `onPause`.

## Section 3: MVP vs. Related Patterns

**Q11. How does MVP differ from MVVM, and when do you choose one over the other?**
A:

| Dimension                | MVP (Passive View)                                          | MVVM                                                                  |
|--------------------------|-------------------------------------------------------------|-----------------------------------------------------------------------|
| View update mechanism    | Presenter explicitly calls View methods                     | ViewModel exposes observable properties; View binds to them           |
| Data flow direction      | Presenter → View (push, explicit)                           | ViewModel ↔ View (reactive, automatic via binding framework)          |
| View passivity           | Completely passive — no logic, no binding                   | Passive to logic but active in binding — handles data-binding itself  |
| Framework dependency     | Presenter has none — pure class                             | ViewModel has none — pure class with observables                      |
| Ceremony                 | High — every display state = one IView method               | Lower — binding replaces many explicit setter calls                   |
| Testability              | Verify method calls on mock View                            | Verify ViewModel property values — no mock View needed                |
| Best fit                 | Rich forms with complex conditional display logic           | Data-driven UIs with many fields that mirror model properties         |
| Typical platforms        | Android (legacy), WinForms, Angular (manual wiring)         | Angular (with two-way binding), Vue, React (with state observables)   |

Choose **MVP** when: your UI has complex conditional display logic (field A is shown only when B and C are in specific states), you need maximum testability of presentation decisions, or the UI framework doesn't offer a reactive binding system.

Choose **MVVM** when: your UI is primarily data-driven (display what's in the model, with minimal conditional logic), you're using a framework with first-class reactive binding (Angular, Vue, RxJS), or you want to reduce the ceremony of an explicit View interface.

**Q12. How does MVP differ from MVI (Model-View-Intent), and what problem does MVI solve that MVP doesn't?**
A: MVI is a unidirectional data flow pattern common in Kotlin/Android and some React architectures:
- **Intent** — user actions captured as immutable intent objects.
- **Model** — the single immutable state derived from intents.
- **View** — renders the state; zero logic.

| Dimension            | MVP                                                        | MVI                                                                   |
|----------------------|------------------------------------------------------------|-----------------------------------------------------------------------|
| Data flow            | Bidirectional: View → Presenter → View                     | Unidirectional: Intent → State → View → Intent                        |
| State management     | Presenter holds mutable state internally                   | Single immutable state atom; each action produces a new state         |
| Side effects         | Presenter manages side effects directly                    | Side effects modelled explicitly as state transitions                 |
| Time-travel debug    | Hard — Presenter state is mutable and implicit             | Easy — every state is a value; replay any sequence of intents         |
| Complexity           | Lower — familiar imperative model                          | Higher — requires understanding of reducers / state machines          |
| Predictability       | Good (well-structured MVP)                                 | Excellent — same intent sequence always produces same state           |

MVI solves the *state explosion* problem in complex UIs where many concurrent events can fire in any order and MVP's mutable Presenter state becomes hard to reason about. MVP is simpler and sufficient for most standard form-and-display UIs.

**Q13. Is MVP relevant in a backend NestJS context, and how does the concept translate?**
A: The strict UI-oriented MVP is primarily a frontend/rich-client pattern. In a NestJS backend, the concepts translate loosely:
- **Model** → Service layer + repositories (domain logic and data access).
- **View** → Response serializer / DTO transformer (what gets sent to the client — the "view" of the data).
- **Presenter** → Controller + DTO mapping layer (orchestrates the service call, maps the domain object to a response DTO, handles error-to-HTTP-status mapping).

```typescript
// NestJS "MVP" analogue:

// Model (Service)
@Injectable()
class LoanService {
  async getActiveLoan(loanId: string): Promise<Loan> {
    return this.loanRepo.findActiveById(loanId);
  }
}

// "Presenter" logic — controller + response mapping
@Controller("loans")
class LoanController {
  constructor(private readonly loanService: LoanService) {}

  @Get(":id")
  async getLoan(@Param("id") loanId: string): Promise<LoanResponseDto> {
    const loan = await this.loanService.getActiveLoan(loanId);
    // Presentation logic: formatting, conditional field inclusion
    return {
      id:           loan.id,
      status:       loan.status,
      emiAmount:    `₹${(loan.emiInPaise / 100).toLocaleString("en-IN")}`,
      nextDueDate:  loan.nextEmiDue?.toISOString() ?? null,
      isOverdue:    loan.status === "OVERDUE",
    };
  }
}

// "View" — the HTTP response / JSON serializer (implicit in NestJS)
```

The principle — separate data-shaping ("presentation") from domain logic — is valuable regardless of frontend or backend context. However, when backend engineers say "MVP," they almost always mean the UI pattern. The backend equivalent is more commonly called "presentation layer" or "response mapping," not MVP.

**Q14. Show how MVP structures a transaction history screen with filtering, pagination, and export.**

```typescript
// ─── Model ────────────────────────────────────────────────────────────────────

// ─── View Interface ───────────────────────────────────────────────────────────

interface DisplayTransaction {

interface ITransactionHistoryView {

  showExportProgress(visible: boolean): void;

  onFilterChanged(handler: (filter: TransactionFilter) => void): void;

// ─── Presenter ────────────────────────────────────────────────────────────────

class TransactionHistoryPresenter {
  private currentFilter: TransactionFilter = {
    fromDate: null, toDate: null, type: "ALL", minAmount: null, maxAmount: null,
  };
  private currentPage  = 1;
  private readonly pageSize = 20;

    private readonly view:      ITransactionHistoryView,
    private readonly model:     TransactionHistoryModel,

    this.bindViewEvents();

  async onViewAttached(): Promise<void> {
    await this.loadPage();
  }

  private bindViewEvents(): void {
    this.view.onFilterChanged(async (filter) => {
      this.currentFilter = filter;
      this.currentPage   = 1;   // reset to first page on filter change
      await this.loadPage();
    });

    this.view.onPageChanged(async (page) => {
      this.currentPage = page;
      await this.loadPage();
    });

    this.view.onExportRequested(() => this.handleExport());

    this.view.onRowClicked(txnId => {
      this.view.navigateToTransactionDetail(txnId);
    });

    this.view.showLoadingSpinner(true);

      const result = await this.model.fetchTransactions(
        this.accountId, this.currentFilter, this.currentPage, this.pageSize,

      if (result.items.length === 0) {
        this.view.showEmptyState("No transactions found for the selected filters");
        this.view.displayPagination(1, 1);
        return;
      }

      this.view.displayTransactions(result.items.map(t => this.mapToDisplayRow(t)));
      this.view.displayPagination(
        result.page,
        Math.ceil(result.totalCount / result.pageSize),
      );
    } catch {
      this.view.showErrorMessage("Failed to load transactions — please try again");
    } finally {
      this.view.showLoadingSpinner(false);
    }
  }

  private async handleExport(): Promise<void> {
    this.view.showExportProgress(true);
    try {
      const blob     = await this.model.exportToCsv(this.accountId, this.currentFilter);
      const filename = `transactions-${new Date().toISOString().slice(0, 10)}.csv`;
      this.view.triggerCsvDownload(blob, filename);
    } catch {
      this.view.showErrorMessage("Export failed — please try again");
    } finally {
      this.view.showExportProgress(false);
    }
  }

  // All display mapping — Presenter responsibility, not View's

    return {
      id:          t.id,
      dateText:    new Intl.DateTimeFormat("en-IN", {
        day: "2-digit", month: "short", year: "numeric",
        hour: "2-digit", minute: "2-digit",

      amountText:  `${t.type === "DEBIT" ? "−" : "+"}₹${(t.amountInPaise / 100).toLocaleString("en-IN")}`,
      typeLabel:   t.type === "DEBIT" ? "Debit" : "Credit",
      typeColour:  t.type === "DEBIT" ? "#D32F2F" : "#388E3C",
      description: t.description,
      statusBadge: this.statusToBadge(t.status),
      refNo:       t.referenceNo,
    };
  }

  private statusToBadge(status: Transaction["status"]): string {
    return { SUCCESS: "✓ Success", PENDING: "⏳ Pending", FAILED: "✗ Failed" }[status];
  }
}
```

**Q15. How does MVP handle real-time data updates — e.g., a live EMI payment status dashboard?**
A: The Model subscribes to a real-time source (WebSocket, Server-Sent Events, polling) and notifies the Presenter via a callback. The Presenter processes the update and pushes display-ready data to the View:

```typescript
class EmiDashboardModel {
  private ws: WebSocket | null = null;

  subscribeToEmiUpdates(
    customerId: string,
    onUpdate: (update: EmiStatusUpdate) => void,
  ): () => void {
    this.ws = new WebSocket(`wss://api.finapp.in/emi-updates/${customerId}`);
    this.ws.onmessage = (event) => {
      const update: EmiStatusUpdate = JSON.parse(event.data);
      onUpdate(update);
    };
    // Return unsubscribe function
    return () => { this.ws?.close(); this.ws = null; };
  }
}

class EmiDashboardPresenter {
  private unsubscribe: (() => void) | null = null;

  constructor(
    private readonly view:       IEmiDashboardView,
    private readonly model:      EmiDashboardModel,
    private readonly customerId: string,
  ) {}

  onViewAttached(): void {
    this.unsubscribe = this.model.subscribeToEmiUpdates(
      this.customerId,
      (update) => this.handleEmiUpdate(update),
    );
  }

  onViewDetached(): void {
    this.unsubscribe?.();
    this.unsubscribe = null;
  }

  private handleEmiUpdate(update: EmiStatusUpdate): void {
    // Presenter transforms domain event into display state
    this.view.updateEmiRow({
      loanId:      update.loanId,
      statusText:  update.status === "COLLECTED" ? "✓ Paid" : "⚠ Pending",
      statusColor: update.status === "COLLECTED" ? "#388E3C" : "#F57C00",
      amountText:  `₹${(update.amountInPaise / 100).toLocaleString("en-IN")}`,
      collectedAt: update.collectedAt
        ? new Intl.DateTimeFormat("en-IN").format(new Date(update.collectedAt))
        : "—",
    });

    if (update.status === "FAILED") {
      this.view.showToast(`EMI collection failed for Loan #${update.loanId.slice(-6)}`);
    }
  }
}
```

## Section 5: Pitfalls & Anti-patterns

**Q16. What is the "Passive View" violation — when the View starts making decisions?**
A: The most common MVP anti-pattern is logic creeping into the View:

```typescript
// ❌ View making decisions — Passive View violated
class LoanFormDomView implements ILoanApplicationView {
  displayLoanDecision(decision: LoanDecision): void {
    // View is deciding which UI branch to take — Presenter's job
    if (decision.approved) {
      this.resultBox.innerHTML = `<p class="success">Approved: ₹${decision.sanctionedAmount}</p>`;
    } else {
      this.resultBox.innerHTML = `<p class="rejected">Rejected: ${decision.rejectionReason}</p>`;
    }
  }

  // View formatting amounts — Presenter's job
  displayBalance(balanceInPaise: number): void {
    this.balanceEl.textContent = `₹${(balanceInPaise / 100).toLocaleString("en-IN")}`;
  }
}

// ✅ Passive View — View renders what it's told; Presenter decides what to tell it
interface ILoanApplicationView {
  displayApprovalResult(sanctionedText: string): void;
  displayRejectionResult(reason: string): void;
  setBalanceText(formattedText: string): void;   // pre-formatted by Presenter
}
```

The signal that the View is making decisions: conditionals (`if`, `switch`) in the View implementation, data transformation (currency formatting, date parsing) in the View, or the View calling Model methods directly.

**Q17. What is the "fat Presenter" anti-pattern, and how do you address it?**
A: The Presenter attracts responsibility from both sides — business logic from the Model and rendering detail from the View — and grows into an unmanageable class:

```typescript
// ❌ Fat Presenter — doing too much
class LoanPresenter {
  // Business logic that belongs in the Model:
  private calculateEmi(principal: number, rate: number, months: number): number {
    const r = rate / 12;
    return (principal * r * Math.pow(1 + r, months)) / (Math.pow(1 + r, months) - 1);
  }

  // Data access that belongs in the Model:
  private async fetchCibilScore(pan: string): Promise<number> {
    const res = await fetch(`/api/cibil?pan=${pan}`);
    return (await res.json()).score;
  }

  // Rendering detail that belongs in the View:
  private buildApprovalHtml(amount: number, emi: number): string {
    return `<div class="card success"><h2>₹${amount}</h2><p>EMI: ₹${emi}/month</p></div>`;
  }
}
```

**Fix:** Push business logic down to the Model/domain layer; push rendering HTML/templates back into the View. The Presenter should only:
1. Call Model methods.
2. Map domain objects to display objects (format strings, derive display booleans).
3. Call View methods with the display objects.

For very complex screens, split one large Presenter into smaller, focused ones — one per logical section of the screen — coordinated by a parent Presenter or a screen-level router.

**Q18. How do you prevent the IView interface from becoming too large?**
A: A Passive View interface grows with every display state property — a complex screen can accumulate 30–50 methods. Mitigations:

1. **Group related display state into a display object:**
```typescript
// ❌ 10 individual methods for one section
interface IBadView {
  setLoanId(id: string): void;
  setLoanStatus(status: string): void;
  setLoanStatusColour(colour: string): void;
  setEmiAmount(text: string): void;
  setEmiDueDate(text: string): void;
  setOutstandingBalance(text: string): void;
  setLoanProductName(name: string): void;
  setLoanTenure(text: string): void;
  setDisbursedDate(text: string): void;
  setClosureDate(text: string): void;
}

// ✅ One method with a display model object
interface ILoanDetailView {
  displayLoanSummary(summary: LoanSummaryDisplay): void;
  displayEmiSchedule(rows: EmiScheduleRow[]): void;
  displayRepaymentProgress(progress: RepaymentProgressDisplay): void;
}

interface LoanSummaryDisplay {
  loanId:           string;
  statusText:       string;
  statusColour:     string;
  productName:      string;
  emiText:          string;
  nextDueDateText:  string;
  outstandingText:  string;
  disbursedDateText: string;
}
```

2. **Apply interface segregation** — split one large `IView` into role-specific interfaces: `ILoanSummaryView`, `IEmiScheduleView`, `IRepaymentChartView`. The concrete View class implements all of them; each Presenter section depends only on its relevant sub-interface.

3. **Accept some Supervising Controller pragmatism** — for simple, mechanical property-to-field bindings (name → text field content), allow one-time binding setup rather than a method per property.

**Q19. How do you handle Presenter state that must survive configuration changes — e.g., device rotation in Android or tab switching in a SPA?**
A: The Presenter's in-memory state is lost on destruction. The state it must carry across lifecycle events must be explicitly persisted:

```typescript
// Presenter state that must survive: current filter, current page, loaded data
interface LoanDashboardPresenterState {
  filter:      TransactionFilter;
  currentPage: number;
  lastLoadedAt: string | null;
}

class LoanDashboardPresenter {
  private state: LoanDashboardPresenterState = {
    filter: defaultFilter(), currentPage: 1, lastLoadedAt: null,
  };

  // Called by framework to save state before destruction
  saveState(): LoanDashboardPresenterState {
    return { ...this.state };
  }

  // Called by framework to restore state after recreation
  restoreState(saved: LoanDashboardPresenterState): void {
    this.state = saved;
  }

  // In a SPA: store state in sessionStorage or URL query params
  private persistStateToUrl(): void {
    const params = new URLSearchParams({
      page:     String(this.state.currentPage),
      type:     this.state.filter.type,
      from:     this.state.filter.fromDate?.toISOString() ?? "",
    });
    history.replaceState(null, "", `?${params.toString()}`);
  }

  private restoreStateFromUrl(): void {
    const params = new URLSearchParams(window.location.search);
    this.state.currentPage        = parseInt(params.get("page") ?? "1", 10);
    this.state.filter.type        = (params.get("type") ?? "ALL") as TransactionFilter["type"];
    this.state.filter.fromDate    = params.get("from") ? new Date(params.get("from")!) : null;
  }
}
```

In a NestJS + Angular SPA: URL query parameters are the canonical persistence layer for Presenter state that must survive navigation — they're bookmark-able, shareable, and survive page refresh without additional infrastructure.

**Q20. What are the signs that a codebase would benefit from introducing MVP, and how do you migrate incrementally?**
A: Signs that MVP is needed:
- Component test coverage is near zero because tests require a running browser or framework.
- Bug reports say "the form shows the wrong error in certain state combinations" — complex conditional display logic buried in template files.
- The same display logic (amount formatting, status labels, validation) is duplicated across multiple components.
- A new rendering target (mobile app, different UI library) requires rewriting logic that "should" be shareable.

**Incremental migration strategy:**
1. **Identify the most logic-heavy component** — the one with the most conditional template logic, the most event handlers, the most test complaints.
2. **Extract the IView interface** — enumerate every display method and every event the component handles. This is the most design-intensive step.
3. **Create the Presenter** — move the existing component's logic into it, calling `this.view.*` instead of manipulating the DOM/template directly.
4. **Refactor the component** — turn it into a thin Passive View that implements IView.
5. **Write Presenter unit tests** — verify the business logic that used to be untestable.
6. **Repeat for the next component** — MVP adoption does not have to be all-or-nothing.

## Section 6: Scenario / System Design Style Questions

**Q21. "You are designing a loan EMI calculator screen in a fintech app. The screen has a principal slider, a tenure dropdown, an interest rate field (auto-fetched based on CIBIL score), and a results section showing EMI, total interest, and total payable. Multiple edge cases: maximum loan cap per product, minimum tenure enforcement, real-time recalculation on any input change. How do you structure this with MVP?"**
A:

```typescript
// ─── Model ────────────────────────────────────────────────────────────────────

class EmiCalculatorModel {
  calculateEmi(principalInPaise: number, annualRate: number, tenureMonths: number): EmiResult {
    const r   = annualRate / 12;
    const emi = r === 0
      ? principalInPaise / tenureMonths
      : (principalInPaise * r * Math.pow(1 + r, tenureMonths)) / (Math.pow(1 + r, tenureMonths) - 1);
    const totalPayable = Math.round(emi) * tenureMonths;
    return {
      emiInPaise:           Math.round(emi),
      totalInterestInPaise: totalPayable - principalInPaise,
      totalPayableInPaise:  totalPayable,
    };
  }

  async fetchPersonalisedRate(pan: string, productCode: string): Promise<number> {
    const res = await fetch(`/api/rates?pan=${pan}&product=${productCode}`);
    const { annualRate } = await res.json();
    return annualRate;
  }

  getProductConstraints(productCode: string): ProductConstraints {
    const constraints: Record<string, ProductConstraints> = {
      "PERSONAL_LOAN": { minAmountInPaise: 10000_00, maxAmountInPaise: 1500000_00, minTenure: 6,  maxTenure: 60  },
      "HOME_LOAN":     { minAmountInPaise: 500000_00, maxAmountInPaise: 10000000_00, minTenure: 12, maxTenure: 360 },
    };

}

  }

  async onViewAttached(): Promise<void> {
    await this.handleProductChanged(this.productCode);
  }

  private bindViewEvents(): void {
    this.view.onProductChanged(code => this.handleProductChanged(code));
    this.view.onPrincipalChanged(amount => this.handlePrincipalChanged(amount));
    this.view.onTenureChanged(months => this.handleTenureChanged(months));
  }

  private async handleProductChanged(code: string): Promise<void> {
    this.productCode  = code;
    this.constraints  = this.model.getProductConstraints(code);

    // Update slider range to reflect product constraints
    this.view.setSliderRange(
      this.constraints.minAmountInPaise,
      this.constraints.maxAmountInPaise,
      10000_00,  // ₹10,000 steps
    );

    // Update tenure options
    const tenureOptions = this.buildTenureOptions(this.constraints.minTenure, this.constraints.maxTenure);
    this.view.setTenureOptions(tenureOptions);
    this.tenureMonths = this.constraints.minTenure;

    // Fetch personalised rate for this product
    await this.fetchAndApplyRate();
  }

  private async fetchAndApplyRate(): Promise<void> {
    this.view.setInterestRateLoading(true);
    try {
      this.annualRate = await this.model.fetchPersonalisedRate(this.pan, this.productCode);
      this.view.setInterestRateText(`${(this.annualRate * 100).toFixed(2)}% p.a.`);
    } catch {
      this.view.showErrorMessage("Could not fetch your personalised rate");
    } finally {
      this.view.setInterestRateLoading(false);
      this.recalculate();
    }
  }

  private handlePrincipalChanged(amountInPaise: number): void {
    if (amountInPaise < this.constraints.minAmountInPaise) {
      this.view.showPrincipalError(
        `Minimum loan amount is ${this.formatCurrency(this.constraints.minAmountInPaise)}`
      );
      this.view.clearEmiResult();
      return;
    }
    if (amountInPaise > this.constraints.maxAmountInPaise) {
      this.view.showPrincipalError(
        `Maximum loan amount is ${this.formatCurrency(this.constraints.maxAmountInPaise)}`
      );
      this.view.clearEmiResult();
      return;
    }
    this.view.clearPrincipalError();
    this.principalInPaise = amountInPaise;
    this.recalculate();
  }

  private handleTenureChanged(months: number): void {
    this.tenureMonths = months;
    this.recalculate();
  }

  private recalculate(): void {
    if (this.principalInPaise <= 0 || this.tenureMonths <= 0) {
      this.view.clearEmiResult();
      return;
    }
    const result = this.model.calculateEmi(this.principalInPaise, this.annualRate, this.tenureMonths);
    this.view.displayEmiResult({
      emiText:           this.formatCurrency(result.emiInPaise) + " / month",
      totalInterestText: this.formatCurrency(result.totalInterestInPaise),
      totalPayableText:  this.formatCurrency(result.totalPayableInPaise),
      breakdownPercent:  Math.round((this.principalInPaise / result.totalPayableInPaise) * 100),
    });
  }

  private buildTenureOptions(min: number, max: number): { label: string; value: number }[] {
    const options = [];
    for (let m = min; m <= max; m += (max <= 60 ? 6 : 12)) {
      options.push({ label: m >= 12 ? `${m / 12} yr${m > 12 ? "s" : ""}` : `${m} mo`, value: m });
    }
    return options;
  }

  private formatCurrency(paise: number): string {
    return `₹${(paise / 100).toLocaleString("en-IN")}`;
  }
}
```

**Q22. "A junior engineer is writing an Angular component with 200 lines of TypeScript in the component class — API calls, data formatting, validation, navigation — and says 'it all works, why refactor?' How do you make the case for MVP?"**
A: A concrete, outcome-focused argument:

> "Let's look at the specific risks this creates for our team right now, not hypothetically.
>
> First, testing. That 200-line component cannot be exercised without compiling Angular, bootstrapping the module, and running a browser — either Karma in a headless Chrome or a Jest DOM emulator. Every test is 10× slower and 10× more brittle than it needs to be. With MVP, the Presenter is a plain TypeScript class — you instantiate it in a Jest test in one line, pass it a mock View, and test every business decision in milliseconds without a browser.
>
> Second, the next feature. When the product team asks us to add a React Native mobile version, or a simpler web view for low-bandwidth users, all that logic in the component class gets rewritten from scratch for each new surface. With MVP, the Presenter contains the logic once — we write a new View implementation for each surface, but the business rules, validations, and flow live in one place.
>
> Third, the current bug cycle. When QA files a bug saying 'when the user enters a PAN, then changes the product, the eligibility amount sometimes shows stale data', we have to trace through 200 lines of mixed rendering and logic to understand state. With a Presenter, the state machine is explicit and isolated — we test it directly and find the bug in minutes.
>
> The refactor is not about cleanliness. It is about making the next three months of feature development faster and less risky."

**Q23. "Your team is migrating a legacy server-rendered Handlebars application to a React SPA. Some pages are being migrated incrementally — some are React, some still server-rendered. How do you apply MVP to support both surfaces from the same Presenter?"**
A: The Presenter talks only to `IView` — swap the concrete View implementation per rendering surface:

```typescript
// Same Presenter — runs against either View implementation
const presenter = new LoanSummaryPresenter(view, model);

// ─── React SPA View ───────────────────────────────────────────────────────────

class ReactLoanSummaryView implements ILoanSummaryView {
  private setState: React.Dispatch<React.SetStateAction<LoanSummaryDisplayState>>;

  constructor(setState: React.Dispatch<React.SetStateAction<LoanSummaryDisplayState>>) {
    this.setState = setState;
  }

  displayLoanSummary(summary: LoanSummaryDisplay): void {
    this.setState(s => ({ ...s, summary }));
  }
  showErrorMessage(msg: string): void {
    this.setState(s => ({ ...s, error: msg }));
  }
  navigateToRepayment(loanId: string): void {
    window.__reactRouter.push(`/loans/${loanId}/repayment`);
  }
  // ... rest of ILoanSummaryView
}

// ─── Server-rendered (Express + Handlebars) View ──────────────────────────────

class HandlebarsLoanSummaryView implements ILoanSummaryView {
  constructor(
    private readonly res:  express.Response,
    private readonly req:  express.Request,
  ) {}

  displayLoanSummary(summary: LoanSummaryDisplay): void {
    // Accumulate data — render() finalises the response
    (this.res.locals as any).summary = summary;
  }
  showErrorMessage(msg: string): void {
    (this.res.locals as any).error = msg;
  }
  navigateToRepayment(loanId: string): void {
    this.res.redirect(`/loans/${loanId}/repayment`);
  }

  render(): void {
    this.res.render("loan-summary", this.res.locals);
  }
}

// ─── Express route: server-rendered path ─────────────────────────────────────

app.get("/loans/:id/summary", async (req, res) => {
  const view      = new HandlebarsLoanSummaryView(res, req);
  const model     = new LoanSummaryModel();
  const presenter = new LoanSummaryPresenter(view, model);
  await presenter.onViewAttached();
  view.render();   // flush Handlebars response
});
```

The same Presenter runs in both environments. During migration, pages can be switched from Handlebars to React one at a time — the Presenter is never touched.

**Q24. "How does MVP interact with a state management library like Redux or NgRx — do they conflict, or can they coexist?"**
A: They occupy different layers and can coexist cleanly:
- **Redux / NgRx** — manages the global application state store: normalized entities, fetched data, UI state shared across many components.
- **MVP Presenter** — manages the *local* presentation state for one screen: what's currently displayed on this screen, derived display values, which buttons are enabled.

The Presenter treats the Redux store as part of the Model layer — it subscribes to store selectors and dispatches actions, the same way it would call a service:

```typescript
class LoanDashboardPresenter {
  constructor(
    private readonly view:  ILoanDashboardView,
    private readonly store: Store<AppState>,   // NgRx store as "Model"
  ) {
    this.bindViewEvents();

    // Subscribe to store — Presenter maps store state to display state
    this.store.select(selectActiveLoans).subscribe(loans => {
      this.view.displayLoans(loans.map(l => this.mapToDisplayLoan(l)));
    });

    this.store.select(selectIsLoading).subscribe(loading => {
      this.view.showLoadingSpinner(loading);
    });
  }

  private handleRefreshRequested(): void {
    // Presenter dispatches action — store/effect handles the fetch
    this.store.dispatch(LoanActions.loadLoans());
  }
}
```

The Presenter adds value on top of the store: it maps store entities to display models (formatting, derived colours, labels), handles screen-local state not worth putting in the global store, and keeps the View completely decoupled from the store's shape. The store handles cross-screen state; the Presenter handles per-screen presentation.

**Q25. "How would you explain the MVP pattern to a backend engineer who has never written a frontend, using an analogy from the backend world they already know?"**
A: A domain-familiar explanation:

> "Think of it like our NestJS service layer architecture, but for UI.
>
> In our backend, the Controller is supposed to be thin — it parses the request, calls a Service, and serializes the response. The Service is where the business logic lives. We wouldn't put EMI calculation or CIBIL validation in the Controller — that would make it impossible to test without an HTTP client.
>
> In the frontend without MVP, the Angular component or React component plays the role of a controller that has absorbed all the service logic too — it's fetching data, validating inputs, formatting output, and deciding which UI state to show, all in one place. Testing it requires a full browser, the same way testing a fat Controller would require a full HTTP stack.
>
> MVP applies the same separation we already do on the backend. The View is the Controller — thin, dumb, just wires events and renders output. The Presenter is the Service — it has all the logic, talks to the Model (our repository / API layer), and tells the View exactly what to render. The Presenter is a plain TypeScript class, no framework dependency — you instantiate it in Jest the same way you'd test a NestJS Service with a mocked repository.
>
> The IView interface is equivalent to our repository interfaces on the backend — the Presenter depends on an abstraction, not on a specific DOM implementation. Swap the concrete View and the Presenter doesn't change — the same way swapping from a Postgres repository to an in-memory mock doesn't change our Service logic."

## Quick Reference Table

| Dimension                          | MVP (Passive View)                                                         |
|------------------------------------|----------------------------------------------------------------------------|
| Category                           | Enterprise & Architectural (UI)                                            |
| Intent                             | Separate UI into Model, View, Presenter; make View completely passive      |
| Key participants                   | Model (data + domain), View (passive rendering surface), Presenter (logic + mediator) |
| View's role                        | Render what Presenter instructs; forward all events to Presenter           |
| Presenter's role                   | React to View events; call Model; transform domain data to display data; update View |
| Model's role                       | Business logic, data access, domain rules; no knowledge of View or Presenter |
| View-Presenter coupling            | Through IView interface — Presenter never references a concrete View type  |
| Testability                        | Presenter fully unit-testable with mock View; zero DOM / framework needed  |
| Passive View vs. Supervising Controller | Passive: all display logic in Presenter. Supervising: simple bindings in View |
| Relationship to MVC                | View is passive (no Model access) vs. MVC where View reads Model directly  |
| Relationship to MVVM               | MVP: explicit push via method calls. MVVM: reactive binding via observables |
| Relationship to MVI                | MVP: bidirectional, mutable Presenter state. MVI: unidirectional, immutable |
| Navigation ownership               | Presenter decides when and why; View knows how (framework API)             |
| Lifecycle hooks                    | onViewAttached / onViewDetached — load data, bind events, clean up         |
| IView interface size               | Keep small — group display state into display model objects; apply ISP     |
| Common misuses                     | Logic in View, business logic in Presenter, fat Presenter, no IView interface |
| Fintech canonical examples         | Loan application form, EMI calculator, transaction history, KYC wizard     |
| Backend analogy                    | Controller (View) + Service (Presenter) + Repository (Model)               |
| SOLID alignment                    | SRP (each layer one responsibility), DIP (Presenter depends on IView abstraction), OCP (new View without changing Presenter) |

**Tip for the Interview:** At the 5 YOE level, MVP questions don't come as "name the three components" — they come as "your Angular component has 300 lines, 5 API calls, and zero unit tests — how do you fix this?" or "how do you structure a wizard with back-navigation and real-time validation?" The answers that land demonstrate three things: (1) you can articulate precisely *why* the View must be passive — not as a rule, but because it's the move that makes the Presenter unit-testable without a browser; (2) you know the practical contract — the IView interface, lifecycle hooks, the display model pattern for keeping the interface manageable; and (3) you can place MVP in context — how it relates to MVVM, when to choose one over the other, and how it coexists with state management libraries. In fintech specifically, the testability argument is the one that resonates most — every form-based flow (loan application, KYC, EMI calculator) has complex conditional logic that *must* be covered by fast, deterministic unit tests, and MVP is the architectural decision that makes that possible.
