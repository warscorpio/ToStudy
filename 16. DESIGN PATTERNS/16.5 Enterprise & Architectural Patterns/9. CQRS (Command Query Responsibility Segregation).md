# Enterprise & Architectural Patterns: CQRS (Command Query Responsibility Segregation) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is CQRS?**
A: CQRS (Command Query Responsibility Segregation) is an architectural pattern that **separates the model used to mutate state (commands) from the model used to read state (queries)**. In a traditional layered architecture, the same service and data model serves both writes and reads — CQRS splits them into two distinct stacks that can be developed, deployed, scaled, and optimised independently.

The core principle comes from Bertrand Meyer's **Command-Query Separation (CQS)** at the method level: a method should either change state (command, returns nothing) or return data (query, changes nothing) — never both. CQRS elevates this from method design to architectural design:

- **Command side** — handles state-changing operations (apply for loan, disburse, record EMI payment, sanction). Uses domain aggregates, enforces business rules, writes to the primary data store. Returns acknowledgement, not data.
- **Query side** — handles all read operations (get loan status, list EMIs, dashboard data). Uses denormalised read models optimised for each specific query. Returns data shapes tailored to the consumer.

**Q2. What problem does CQRS solve? When is it worth the complexity?**
A: CQRS solves the **impedance mismatch between write and read models** that emerges in complex domains:

- **Write models** are designed around consistency — domain aggregates with strict invariants, normalised data, transaction boundaries. They're optimised for correctness, not query performance.
- **Read models** are designed around query performance — denormalised, pre-joined, often shaped per consumer (mobile app vs ops dashboard vs regulatory report). No domain logic needed.

Trying to serve both needs from one model produces either an overly complex write model (polluted with query-optimisation concerns) or an overly slow read model (loading full aggregates for simple lookups).

CQRS is worth the complexity when:
- **Read and write workloads are disproportionate** — a loan platform may have 1 write per 100 reads (applicants check status constantly; loans are applied for once).
- **Read and write scaling requirements differ** — reads can be served from read replicas or caches; writes must go to the primary. Separate models enable separate scaling strategies.
- **Read shapes differ radically from write shapes** — the ops dashboard needs a denormalised view of loan + applicant + bureau + EMI schedule; the write model is a normalised aggregate.
- **Complex domain model** — full DDD aggregates used on the write side would be expensive to load for every read operation.

Do NOT apply CQRS when the domain is simple CRUD, the team is small, or read and write workloads are symmetric. It adds two codepaths for every operation.

**Q3. What is the difference between CQS (Command-Query Separation) and CQRS?**
A:

| Aspect          | CQS                                              | CQRS                                                    |
|-----------------|--------------------------------------------------|---------------------------------------------------------|
| Scope           | Method level — one class                         | Architecture level — two separate stacks                |
| Data model      | Same model for reads and writes                  | Separate read model and write model                     |
| Data store      | Same database                                    | May use separate databases / storage technologies       |
| Infrastructure  | Single service, single stack                     | Potentially separate services, separate scaling         |
| Complexity      | Low — just a naming/design discipline            | High — two stacks, synchronisation, eventual consistency |

CQS is a design principle every codebase should follow. CQRS is an architectural pattern for specific scalability and complexity problems. You can apply CQS without CQRS; CQRS implies CQS.

**Q4. What is a Command in CQRS? What should it contain?**
A: A Command is an **intent to change state** — a named, immutable object expressing what the system should do. It is not the state change itself; it is a request to perform one.

Design rules for commands:
- **Named in imperative form** — `ApplyForLoan`, `SanctionLoan`, `CollectEmi`, `RegisterNachMandate`. Not `UpdateLoan` or `SetStatus`.
- **Carries exactly the data needed** — no more, no less. The handler resolves any additional context (e.g., fetches the aggregate from the repository).
- **Immutable** — once created, the command is not modified. It's a value object.
- **Targets one aggregate** — commands are handled by one aggregate root. If a command spans multiple aggregates, it's a sign the boundaries are wrong or it should be decomposed.

```typescript
// Commands — immutable, intent-expressing
class ApplyForLoanCommand {
  constructor(
    public readonly applicantId: string,
    public readonly productCode: string,
    public readonly requestedAmount: number, // in paise
    public readonly tenorMonths: number,
    public readonly pan: string,
    public readonly correlationId: string,   // for idempotency / tracing
  ) {}
}

class SanctionLoanCommand {
  constructor(
    public readonly loanApplicationId: string,
    public readonly sanctionedAmount: number,
    public readonly conditions: string[],
    public readonly officerId: string,
    public readonly correlationId: string,
  ) {}
}

class CollectEmiCommand {
  constructor(
    public readonly loanId: string,
    public readonly emiMonth: string,        // 'YYYY-MM'
    public readonly amount: number,
    public readonly collectionReference: string,
    public readonly collectedOn: string,     // ISO date string
  ) {}
}
```

**Q5. What is a Query in CQRS? How does it differ from a command?**
A: A Query is a **request for data** — it must not change any state, and it returns a result shaped specifically for the caller's needs. Unlike commands (which target aggregates), queries target read models optimised for retrieval.

```typescript
// Queries — named as questions/lookups, return shaped DTOs
class GetLoanApplicationStatusQuery {
  constructor(
    public readonly loanApplicationId: string,
    public readonly requestedBy: string,   // for authorisation
  ) {}
}

class GetLoanDashboardQuery {
  constructor(
    public readonly applicantId: string,
    public readonly page: number,
    public readonly pageSize: number,
  ) {}
}

class GetEmiScheduleQuery {
  constructor(
    public readonly loanId: string,
    public readonly fromMonth: string,
    public readonly toMonth: string,
  ) {}
}

class GetPortfolioAtRiskReportQuery {
  constructor(
    public readonly dpd: number,            // minimum DPD threshold
    public readonly asOfDate: string,
    public readonly productCode?: string,   // optional filter
  ) {}
}
```

Queries return **read model DTOs** — flat, denormalised, pre-shaped for the consumer. The query result for `GetLoanDashboardQuery` might join loan + applicant + latest bureau + EMI status in one go. The command side's `LoanApplication` aggregate never appears in a query result.

## Section 2: Implementation Patterns

**Q6. What does a basic CQRS implementation look like in NestJS?**
A: The simplest CQRS split uses NestJS's `@nestjs/cqrs` package — a command bus and query bus decouple senders from handlers:

```typescript
// --- COMMAND SIDE ---

// Command handler — applies for a loan
@CommandHandler(ApplyForLoanCommand)
@Injectable()
export class ApplyForLoanCommandHandler
  implements ICommandHandler<ApplyForLoanCommand> {

  constructor(
    @Inject(LOAN_APPLICATION_REPOSITORY)
    private readonly loanAppRepo: ILoanApplicationRepository,
    private readonly bureauService: BureauService,
    private readonly eligibilityService: CreditEligibilityDomainService,
    private readonly eventBus: EventBus,
  ) {}

  async execute(command: ApplyForLoanCommand): Promise<string> {
    // 1. Fetch or create the aggregate
    const bureauReport = await this.bureauService.fetchReport(command.pan);

    // 2. Domain logic — on the aggregate
    const application = LoanApplication.submit(
      ApplicantId.from(command.applicantId),
      LoanProduct.fromCode(command.productCode),
      Money.inr(command.requestedAmount),
      bureauReport,
    );

    // 3. Persist
    await this.loanAppRepo.save(application);

    // 4. Publish domain events (which update read models)
    application.pullAndClearEvents().forEach(e => this.eventBus.publish(e));

    return application.id.value; // return new aggregate's ID
  }
}

// --- QUERY SIDE ---

// Query handler — no domain logic; reads from optimised read model
@QueryHandler(GetLoanApplicationStatusQuery)
@Injectable()
export class GetLoanApplicationStatusQueryHandler
  implements IQueryHandler<GetLoanApplicationStatusQuery> {

  constructor(private readonly prisma: PrismaService) {}

  async execute(query: GetLoanApplicationStatusQuery): Promise<LoanStatusDto> {
    // Direct DB query — no aggregate, no domain objects loaded
    const result = await this.prisma.loanApplicationReadModel.findUnique({
      where: { id: query.loanApplicationId },
      select: {
        id: true,
        status: true,
        requestedAmount: true,
        sanctionedAmount: true,
        applicantName: true,    // denormalised from applicant table
        productName: true,      // denormalised from product table
        submittedAt: true,
        lastUpdatedAt: true,
      },
    });

    if (!result) throw new LoanApplicationNotFoundException(query.loanApplicationId);
    return result as LoanStatusDto;
  }
}

// Controller — thin dispatcher
@Controller('loan-applications')
export class LoanApplicationController {
  constructor(
    private readonly commandBus: CommandBus,
    private readonly queryBus: QueryBus,
  ) {}

  @Post()
  async apply(@Body() dto: ApplyForLoanDto, @CurrentUser() user: User): Promise<{ id: string }> {
    const id = await this.commandBus.execute(
      new ApplyForLoanCommand(user.id, dto.productCode, dto.amount, dto.tenorMonths, dto.pan, uuid()),
    );
    return { id };
  }

  @Get(':id/status')
  async getStatus(@Param('id') id: string, @CurrentUser() user: User): Promise<LoanStatusDto> {
    return this.queryBus.execute(new GetLoanApplicationStatusQuery(id, user.id));
  }
}
```

**Q7. How do read models get populated and kept in sync with the write side?**
A: This is CQRS's central engineering problem. The write side mutates aggregates; the read side needs to reflect those changes. There are three main synchronisation strategies:

**Strategy 1 — Synchronous projection (within the same transaction):**
```typescript
// Command handler writes aggregate AND updates read model in one transaction
@CommandHandler(SanctionLoanCommand)
export class SanctionLoanCommandHandler implements ICommandHandler<SanctionLoanCommand> {
  async execute(command: SanctionLoanCommand): Promise<void> {
    await this.prisma.$transaction(async (tx) => {
      // Write side — update aggregate
      const raw = await tx.loanApplication.findUnique({ where: { id: command.loanApplicationId } });
      const application = LoanApplicationMapper.toDomain(raw);
      application.sanction(
        Money.inr(command.sanctionedAmount),
        command.conditions.map(SanctionCondition.from),
        Officer.from(command.officerId),
      );
      await tx.loanApplication.update({ where: { id: raw.id }, data: LoanApplicationMapper.toPersistence(application) });

      // Read model — updated in the same transaction (synchronous)
      await tx.loanApplicationReadModel.update({
        where: { id: command.loanApplicationId },
        data: {
          status: 'SANCTIONED',
          sanctionedAmount: command.sanctionedAmount,
          sanctionedBy: command.officerId,
          lastUpdatedAt: new Date(),
        },
      });
    });
  }
}
```

Pros: read model is always consistent. Cons: tight coupling between write and read model; both fail if one fails.

**Strategy 2 — Event-driven projection (asynchronous, eventually consistent):**
```typescript
// Command handler only updates the aggregate and publishes events
@CommandHandler(SanctionLoanCommand)
export class SanctionLoanCommandHandler implements ICommandHandler<SanctionLoanCommand> {
  async execute(command: SanctionLoanCommand): Promise<void> {
    const application = await this.loanAppRepo.findById(LoanApplicationId.from(command.loanApplicationId));
    application.sanction(/* ... */);
    await this.loanAppRepo.save(application);
    application.pullAndClearEvents().forEach(e => this.eventBus.publish(e));
    // ← Read model NOT updated here
  }
}

// Separate event handler — updates read model asynchronously
@EventsHandler(LoanSanctionedEvent)
export class LoanSanctionedReadModelProjector implements IEventHandler<LoanSanctionedEvent> {
  constructor(private readonly prisma: PrismaService) {}

  async handle(event: LoanSanctionedEvent): Promise<void> {
    await this.prisma.loanApplicationReadModel.update({
      where: { id: event.applicationId },
      data: {
        status: 'SANCTIONED',
        sanctionedAmount: event.sanctionedAmount,
        lastUpdatedAt: event.occurredAt,
      },
    });
  }
}
```

Pros: write and read models are fully decoupled; read model can be rebuilt by replaying events; different teams can own each side. Cons: **eventual consistency** — there's a window (milliseconds to seconds) where the read model lags behind the write model.

**Strategy 3 — Database read replica:**
```typescript
// Simplest form of CQRS — write to primary, read from replica
// No separate read model tables; PostgreSQL streaming replication keeps replica in sync

@QueryHandler(GetLoanDashboardQuery)
export class GetLoanDashboardQueryHandler implements IQueryHandler<GetLoanDashboardQuery> {
  constructor(
    @Inject('READ_REPLICA_PRISMA') private readonly readReplica: PrismaService,
  ) {}

  async execute(query: GetLoanDashboardQuery): Promise<LoanDashboardDto[]> {
    return this.readReplica.$queryRaw`
      SELECT la.id, la.status, la.requested_amount, la.sanctioned_amount,
             a.name AS applicant_name, p.name AS product_name
      FROM loan_applications la
      JOIN applicants a ON a.id = la.applicant_id
      JOIN loan_products p ON p.code = la.product_code
      WHERE la.applicant_id = ${query.applicantId}
      ORDER BY la.submitted_at DESC
      LIMIT ${query.pageSize} OFFSET ${(query.page - 1) * query.pageSize}
    `;
  }
}
```

This is the lightest CQRS implementation — no separate read model tables, just separate database connections.

**Q8. What is a Projection, and how do you build and rebuild one?**
A: A Projection is a read model built by processing a stream of domain events. Each event updates the projection's state — the projection is a materialised view of "what happened," shaped for read efficiency.

```typescript
// Projection table — denormalised, optimised for the query
// CREATE TABLE loan_portfolio_projection (
//   loan_id         UUID PRIMARY KEY,
//   applicant_name  TEXT NOT NULL,
//   applicant_pan   TEXT NOT NULL,
//   product_code    TEXT NOT NULL,
//   status          TEXT NOT NULL,
//   requested_amount BIGINT NOT NULL,     -- in paise
//   sanctioned_amount BIGINT,
//   bureau_score    INTEGER,
//   dpd             INTEGER DEFAULT 0,
//   outstanding_principal BIGINT,
//   last_emi_date   DATE,
//   is_npa          BOOLEAN DEFAULT FALSE,
//   last_updated_at TIMESTAMPTZ NOT NULL
// );

// Projector — listens to domain events, maintains the projection
@Injectable()
export class LoanPortfolioProjector {
  constructor(private readonly prisma: PrismaService) {}

  @OnEvent('LoanApplicationSubmittedEvent')
  async onSubmitted(event: LoanApplicationSubmittedEvent): Promise<void> {
    await this.prisma.loanPortfolioProjection.create({
      data: {
        loanId: event.applicationId,
        applicantName: event.applicantName,
        applicantPan: event.applicantPan,
        productCode: event.productCode,
        status: 'SUBMITTED',
        requestedAmount: event.requestedAmount,
        lastUpdatedAt: event.occurredAt,
      },
    });
  }

  @OnEvent('LoanSanctionedEvent')
  async onSanctioned(event: LoanSanctionedEvent): Promise<void> {
    await this.prisma.loanPortfolioProjection.update({
      where: { loanId: event.applicationId },
      data: {
        status: 'SANCTIONED',
        sanctionedAmount: event.sanctionedAmount,
        lastUpdatedAt: event.occurredAt,
      },
    });
  }

  @OnEvent('EmiCollectedEvent')
  async onEmiCollected(event: EmiCollectedEvent): Promise<void> {
    await this.prisma.loanPortfolioProjection.update({
      where: { loanId: event.loanId },
      data: {
        dpd: 0,    // EMI paid — reset DPD
        lastEmiDate: event.collectedOn,
        outstandingPrincipal: { decrement: event.principalComponent },
        lastUpdatedAt: event.occurredAt,
      },
    });
  }

  @OnEvent('EmiDefaultedEvent')
  async onDefaulted(event: EmiDefaultedEvent): Promise<void> {
    await this.prisma.loanPortfolioProjection.update({
      where: { loanId: event.loanId },
      data: {
        dpd: event.daysPastDue,
        isNpa: event.daysPastDue >= 90,
        lastUpdatedAt: event.occurredAt,
      },
    });
  }
}
```

**Rebuilding a projection** — replay all events from the beginning and re-apply them:
```typescript
@Injectable()
export class ProjectionRebuildService {
  async rebuildLoanPortfolioProjection(): Promise<void> {
    // Step 1 — clear the stale projection
    await this.prisma.loanPortfolioProjection.deleteMany();

    // Step 2 — replay all events in chronological order
    const events = await this.eventStore.findAll({ orderBy: 'occurredAt ASC' });

    for (const event of events) {
      await this.projector.handle(event); // same projector handles rebuild
    }
  }
}
```

The ability to rebuild projections is one of CQRS's most powerful features — you can add a new query requirement (a new projection shape), build the projector, replay all historical events, and have the read model populated with historical data without touching the write side.

## Section 3: CQRS in a Fintech/Lending Platform

**Q9. How does CQRS solve the "dashboard query problem" in a lending platform?**
A: The ops/risk dashboard needs aggregated data from multiple domains in one query — loan details, applicant info, bureau score, EMI status, DPD, NPA flag. In a non-CQRS system, this either requires multiple API calls (slow) or complex joins in the service layer (couples unrelated domains). CQRS solves it with a dedicated read model:

```typescript
// Read model — pre-joined, pre-aggregated, shaped for the dashboard
@QueryHandler(GetRiskDashboardQuery)
export class GetRiskDashboardQueryHandler implements IQueryHandler<GetRiskDashboardQuery> {
  constructor(private readonly prisma: PrismaService) {}

  async execute(query: GetRiskDashboardQuery): Promise<RiskDashboardDto> {
    // One query against a denormalised projection — sub-millisecond
    const [summary, atRisk, recentDefaults] = await Promise.all([
      this.prisma.$queryRaw<PortfolioSummary[]>`
        SELECT
          COUNT(*) AS total_loans,
          SUM(outstanding_principal) AS total_outstanding,
          SUM(CASE WHEN is_npa THEN outstanding_principal ELSE 0 END) AS npa_amount,
          AVG(bureau_score) AS avg_bureau_score
        FROM loan_portfolio_projection
        WHERE status = 'ACTIVE'
      `,

      this.prisma.$queryRaw<AtRiskLoan[]>`
        SELECT loan_id, applicant_name, dpd, outstanding_principal, product_code
        FROM loan_portfolio_projection
        WHERE dpd >= ${query.dpd} AND status = 'ACTIVE'
        ORDER BY dpd DESC
        LIMIT 50
      `,

      this.prisma.$queryRaw<RecentDefault[]>`
        SELECT loan_id, applicant_name, emi_amount, defaulted_on
        FROM emi_defaults_projection
        WHERE defaulted_on >= NOW() - INTERVAL '7 days'
        ORDER BY defaulted_on DESC
        LIMIT 20
      `,
    ]);

    return {
      summary: summary[0],
      atRiskLoans: atRisk,
      recentDefaults,
    };
  }
}
```

All three sub-queries hit dedicated projections — no ORM hydration overhead, no aggregate loading, no cross-domain service calls. The dashboard loads in under 50ms even for portfolios of 100,000 loans.

**Q10. How does CQRS work with the Loan Application lifecycle — tracking status across multiple state transitions?**
A: Each state transition is a command; the read model reflects the current status and history:

```typescript
// Commands — one per lifecycle event
// ApplyForLoanCommand → SUBMITTED
// SendForReviewCommand → UNDER_REVIEW
// RequestAdditionalDocsCommand → DOCS_PENDING
// SanctionLoanCommand → SANCTIONED
// DisburseLoanCommand → DISBURSED
// RejectLoanCommand → REJECTED

// Read model — loan application tracking view
// Populated by projecting domain events
interface LoanApplicationTrackingDto {
  id: string;
  currentStatus: string;
  applicantName: string;
  productCode: string;
  requestedAmount: number;
  sanctionedAmount: number | null;
  timeline: {
    status: string;
    changedAt: Date;
    changedBy: string;
    notes: string | null;
  }[];
  pendingActions: string[];   // computed from current status
}

// Query handler — reads from tracking projection (no aggregate loaded)
@QueryHandler(GetLoanApplicationTrackingQuery)
export class GetLoanApplicationTrackingQueryHandler
  implements IQueryHandler<GetLoanApplicationTrackingQuery> {

  async execute(query: GetLoanApplicationTrackingQuery): Promise<LoanApplicationTrackingDto> {
    const [header, timeline] = await Promise.all([
      this.prisma.loanApplicationSummaryProjection.findUnique({
        where: { id: query.applicationId },
      }),
      this.prisma.loanApplicationTimelineProjection.findMany({
        where: { applicationId: query.applicationId },
        orderBy: { occurredAt: 'asc' },
      }),
    ]);

    return {
      ...header,
      timeline,
      pendingActions: this.resolvePendingActions(header.currentStatus),
    };
  }

  private resolvePendingActions(status: string): string[] {
    const actions: Record<string, string[]> = {
      'SUBMITTED': ['SEND_FOR_REVIEW', 'REQUEST_DOCS'],
      'UNDER_REVIEW': ['SANCTION', 'REJECT', 'REQUEST_DOCS'],
      'DOCS_PENDING': ['REVIEW_DOCS'],
      'SANCTIONED': ['DISBURSE', 'LAPSE'],
      'DISBURSED': [],
      'REJECTED': [],
    };
    return actions[status] ?? [];
  }
}
```

**Q11. How do you implement idempotent command handling in a CQRS system?**
A: In distributed systems, commands can be retried (due to timeouts, network failures, message queue redelivery). Idempotency ensures that processing the same command twice has the same effect as processing it once — critical for financial operations:

```typescript
// Command carries a correlationId / idempotency key
class CollectEmiCommand {
  constructor(
    public readonly loanId: string,
    public readonly emiMonth: string,
    public readonly amount: number,
    public readonly nachReference: string,
    public readonly idempotencyKey: string, // typically: UMRN + date + attempt number
  ) {}
}

// Command handler — checks idempotency before processing
@CommandHandler(CollectEmiCommand)
export class CollectEmiCommandHandler implements ICommandHandler<CollectEmiCommand> {
  async execute(command: CollectEmiCommand): Promise<void> {
    // Check if this command was already processed
    const existing = await this.idempotencyStore.find(command.idempotencyKey);
    if (existing) {
      // Already processed — return the stored result without re-processing
      return existing.result;
    }

    // Process normally
    const loan = await this.activeLoanRepo.findById(ActiveLoanId.from(command.loanId));
    loan.recordEmiCollection(
      EmiMonth.from(command.emiMonth),
      Money.inr(command.amount),
      command.nachReference,
      new Date(command.collectedOn),
    );
    await this.activeLoanRepo.save(loan);

    // Store the result for future duplicate checks (TTL: 24 hours)
    await this.idempotencyStore.save(command.idempotencyKey, { processed: true }, { ttlHours: 24 });

    loan.pullAndClearEvents().forEach(e => this.eventBus.publish(e));
  }
}
```

For database-backed idempotency, use a unique constraint on the idempotency key:
```sql
CREATE TABLE processed_commands (
  idempotency_key TEXT PRIMARY KEY,
  command_type    TEXT NOT NULL,
  processed_at    TIMESTAMPTZ NOT NULL,
  expires_at      TIMESTAMPTZ NOT NULL
);
```

**Q12. How do you handle the "read your own writes" problem in an eventually consistent CQRS system?**
A: When a user submits a command and immediately queries for the result, the read model may not yet reflect the change (projection lag). This is the "read your own writes" problem. Several strategies:

**Strategy 1 — Return the result from the command:**
```typescript
// Command handler returns enough for the UI to optimistically update
@CommandHandler(ApplyForLoanCommand)
export class ApplyForLoanCommandHandler implements ICommandHandler<ApplyForLoanCommand> {
  async execute(command: ApplyForLoanCommand): Promise<{ id: string; status: string }> {
    const application = LoanApplication.submit(/* ... */);
    await this.loanAppRepo.save(application);
    // ... publish events
    return { id: application.id.value, status: 'SUBMITTED' }; // client uses this directly
  }
}
```

**Strategy 2 — Version-based consistency check:**
```typescript
// Client sends the version it expects to see; query handler waits if needed
@QueryHandler(GetLoanApplicationStatusQuery)
export class GetLoanApplicationStatusQueryHandler {
  async execute(query: GetLoanApplicationStatusQuery): Promise<LoanStatusDto> {
    // Poll until projection catches up or timeout
    const maxAttempts = 5;
    for (let i = 0; i < maxAttempts; i++) {
      const result = await this.prisma.loanApplicationReadModel.findUnique({
        where: { id: query.applicationId },
      });
      if (result && result.version >= query.expectedVersion) {
        return result as LoanStatusDto;
      }
      await sleep(50 * (i + 1)); // 50ms, 100ms, 150ms, 200ms, 250ms
    }
    throw new ProjectionLagException('Read model not yet caught up');
  }
}
```

**Strategy 3 — Read from the write store for the immediate post-command query:**
```typescript
// Special query that reads from the primary (write) store when freshness is required
@QueryHandler(GetLoanApplicationStatusQuery)
export class GetLoanApplicationStatusQueryHandler {
  async execute(query: GetLoanApplicationStatusQuery): Promise<LoanStatusDto> {
    if (query.requiresFreshData) {
      // Read from write store — consistent but bypasses read model optimisations
      return this.getFromWriteStore(query.applicationId);
    }
    // Default — read from optimised read model
    return this.getFromReadModel(query.applicationId);
  }
}
```

**Q13. How do you implement a NACH debit failure notification system using CQRS + event projections?**
A:

```typescript
// COMMAND SIDE — records the failure on the aggregate
@CommandHandler(RecordNachDebitFailureCommand)
export class RecordNachDebitFailureCommandHandler implements ICommandHandler<RecordNachDebitFailureCommand> {
  async execute(command: RecordNachDebitFailureCommand): Promise<void> {
    const loan = await this.activeLoanRepo.findById(ActiveLoanId.from(command.loanId));
    loan.recordEmiFailure(
      EmiMonth.from(command.emiMonth),
      NachFailureCode.from(command.failureCode),
      new Date(command.attemptedOn),
    );
    await this.activeLoanRepo.save(loan);
    loan.pullAndClearEvents().forEach(e => this.eventBus.publish(e));
  }
}

// PROJECTIONS — three separate read models updated by the same event
@EventsHandler(EmiDefaultedEvent)
export class EmiDefaultedEventProjectors implements IEventHandler<EmiDefaultedEvent> {
  constructor(private readonly prisma: PrismaService) {}

  async handle(event: EmiDefaultedEvent): Promise<void> {
    await Promise.all([
      // 1. Update portfolio risk projection (for ops dashboard)
      this.prisma.loanPortfolioProjection.update({
        where: { loanId: event.loanId },
        data: { dpd: event.daysPastDue, isNpa: event.daysPastDue >= 90 },
      }),

      // 2. Update collections queue projection (for collections team)
      this.prisma.collectionsQueueProjection.upsert({
        where: { loanId: event.loanId },
        create: {
          loanId: event.loanId,
          dpd: event.daysPastDue,
          failureCode: event.failureCode,
          lastAttemptedOn: event.attemptedOn,
          nextRetryAt: this.computeNextRetry(event.failureCode),
          assignedAgent: null,
        },
        update: {
          dpd: event.daysPastDue,
          failureCode: event.failureCode,
          lastAttemptedOn: event.attemptedOn,
          nextRetryAt: this.computeNextRetry(event.failureCode),
        },
      }),

      // 3. Update customer notification projection (for customer-facing app)
      this.prisma.customerNotificationProjection.create({
        data: {
          applicantId: event.applicantId,
          type: 'EMI_FAILURE',
          loanId: event.loanId,

          message: this.buildNotificationMessage(event.failureCode),
          createdAt: event.occurredAt,
          readAt: null,
        },
      }),
    ]);
  }
}
```

## Section 4: CQRS + Event Sourcing

**Q14. How does CQRS relate to Event Sourcing, and are they the same?**
A: They're frequently used together but are independent patterns:

- **CQRS** — separates the write model (command stack) from the read model (query stack). The write model can use any persistence strategy — traditional relational tables, NoSQL documents, or event sourcing.
- **Event Sourcing (ES)** — persists the *sequence of domain events* as the source of truth, rather than the current state. The current state is derived by replaying events. ES naturally produces an event log that CQRS projectors can consume.

CQRS without Event Sourcing: the write model uses a traditional database (current state); the read model uses projections updated by domain events published at write time. This is the most common setup.

Event Sourcing without CQRS: you store events as the source of truth, but you load the full event history every time you need to read state — expensive and uncommon in practice.

CQRS + Event Sourcing: the write side stores events; the read side builds projections from those events. This gives you a full audit trail, the ability to rebuild any projection from scratch, and time-travel queries.

```typescript
// Event store — the source of truth in ES+CQRS
interface IEventStore {
  append(streamId: string, events: DomainEvent[], expectedVersion: number): Promise<void>;
  load(streamId: string, fromVersion?: number): Promise<StoredEvent[]>;
  loadAll(fromPosition?: number): Promise<StoredEvent[]>; // for rebuilding projections
}

// Aggregate rebuilt from events — not loaded from a state table
class ActiveLoan {
  private _version = 0;

  static reconstituteFromEvents(events: StoredEvent[]): ActiveLoan {
    const loan = new ActiveLoan();
    for (const event of events) {
      loan.apply(event.payload);
      loan._version = event.version;
    }
    return loan;
  }

  private apply(event: DomainEvent): void {
    if (event instanceof EmiCollectedEvent) {
      this._outstandingPrincipal -= event.principalComponent;
      this._emiPayments.push(/* ... */);
    } else if (event instanceof EmiDefaultedEvent) {
      this._dpd = event.daysPastDue;
    }
    // ... other event handlers
  }
}
```

**Q15. What are the trade-offs of using Event Sourcing with CQRS in a fintech context?**
A:

| Aspect                      | CQRS without ES                                    | CQRS + Event Sourcing                                      |
|-----------------------------|----------------------------------------------------|------------------------------------------------------------|
| Write persistence           | Current state in relational DB                     | Append-only event log                                      |
| Audit trail                 | Separate audit table or CDC                        | Built-in — every change is an event                       |
| Projection rebuild          | Possible if events are published and stored        | Always possible — events are the source of truth          |
| Read model lag              | Same as without ES                                 | Same — projectors are async                               |
| Aggregate load              | Read current state — O(1)                          | Replay events — O(n) events; mitigated by snapshots       |
| Regulatory compliance       | External audit trail required                      | Full audit trail native to the system                     |
| Query for past state        | Hard — need time-travel queries or audit tables    | Easy — replay events up to any point in time             |
| Operational complexity      | Moderate                                           | High — event schema evolution, snapshot management        |

For a lending platform: a full ES+CQRS system is valuable for the `ActiveLoan` aggregate (every EMI payment, prepayment, rate change is a business event worth auditing) but overkill for reference data (loan products, bank IFSCs). Apply ES selectively to aggregates where the full history matters.

## Section 5: Anti-patterns and Pitfalls

**Q16. What are the most common CQRS mistakes in a NestJS fintech codebase?**
A:

**Mistake 1 — Queries that change state:**
```typescript
// ❌ Query side mutating state — violates CQS and makes projections stale
@QueryHandler(GetAndMarkAsReadNotificationsQuery)
export class GetAndMarkAsReadHandler {
  async execute(query: GetAndMarkAsReadNotificationsQuery) {
    const notifications = await this.prisma.notification.findMany(/* ... */);
    // This is a COMMAND operation inside a query handler
    await this.prisma.notification.updateMany({ data: { readAt: new Date() } });
    return notifications;
  }
}

// ✅ Fix — separate query and command
// GET /notifications → GetNotificationsQuery (reads only)
// PATCH /notifications/mark-read → MarkNotificationsReadCommand (writes only)
```

**Mistake 2 — Commands returning rich domain objects:**
```typescript
// ❌ Command returns the full updated domain object — now the command side is also a read side
@CommandHandler(SanctionLoanCommand)
export class SanctionLoanHandler {
  async execute(command: SanctionLoanCommand): Promise<LoanApplicationDto> { // ← anti-pattern
    const app = await this.repo.findById(/* ... */);
    app.sanction(/* ... */);
    await this.repo.save(app);
    return LoanApplicationDto.from(app); // command doing a read
  }
}

// ✅ Fix — command returns minimal acknowledgement
async execute(command: SanctionLoanCommand): Promise<void> {
  // ... no return value, or just the ID
}
// Client queries for the updated state via a separate GET request
```

**Mistake 3 — One giant projection table for all reads:**
```typescript
// ❌ One monolithic read model serving all consumers
// loan_read_model has 50 columns, most NULL for any given query
// Now every projector touches the same table, causing lock contention

// ✅ Fix — one projection table per consumer / per query pattern
// loan_portfolio_projection → ops risk dashboard
// loan_application_tracking_projection → applicant status tracking
// collections_queue_projection → collections team
// customer_loan_summary_projection → customer mobile app
```

**Mistake 4 — Skipping the command/query bus for "simple" operations:**
```typescript
// ❌ Mixing direct service calls with bus dispatch — inconsistent architecture
@Controller('loans')
export class LoanController {
  async applyForLoan(@Body() dto) {
    return this.commandBus.execute(new ApplyForLoanCommand(/* ... */)); // ✅ uses bus
  }

  async getStatus(@Param('id') id) {
    return this.loanService.getStatus(id); // ❌ bypasses query bus — inconsistent
  }
}
```

**Mistake 5 — Not handling projection failures gracefully:**
```typescript
// ❌ Projector failure loses the read model update silently
@EventsHandler(LoanSanctionedEvent)
export class LoanSanctionedProjector {
  async handle(event: LoanSanctionedEvent): Promise<void> {
    await this.prisma.loanApplicationReadModel.update(/* ... */);
    // If this fails, the read model is stale — no retry, no alerting
  }
}

// ✅ Fix — projectors should be idempotent and retryable
// Use a message queue (SQS, RabbitMQ) for event delivery with dead-letter queues
// Make projections idempotent: upsert instead of update; version-gate updates
```

**Q17. How do you handle eventual consistency in a customer-facing API that uses CQRS?**
A: Eventual consistency requires explicit design decisions at the API level:

```typescript
// Communicate consistency guarantees explicitly in API contracts
// POST /loan-applications → 202 Accepted (not 201 Created)
// The resource may not be immediately queryable

@Post('loan-applications')
@HttpCode(HttpStatus.ACCEPTED)
async applyForLoan(@Body() dto: ApplyForLoanDto): Promise<AcceptedResponseDto> {
  const id = await this.commandBus.execute(new ApplyForLoanCommand(/* ... */));
  return {
    accepted: true,
    applicationId: id,
    // Tell the client where to poll and what to expect
    statusUrl: `/loan-applications/${id}/status`,
    message: 'Your application has been received. Status will be available within a few seconds.',
    retryAfterSeconds: 2,
  };
}

// Frontend pattern — poll with exponential backoff after a command
async function submitAndPoll(dto: LoanApplicationDto) {
  const { applicationId, retryAfterSeconds } = await api.post('/loan-applications', dto);

  for (let attempt = 0; attempt < 5; attempt++) {
    await sleep(retryAfterSeconds * 1000 * 2 ** attempt);
    const status = await api.get(`/loan-applications/${applicationId}/status`);
    if (status.status !== 'SUBMITTED') return status; // projection has caught up
  }
  // Fallback — show optimistic UI while waiting
}
```

## Section 6: Scenario / System Design Questions

**Q18. "Your loan portfolio dashboard is slow — it takes 4 seconds to load for a portfolio of 50,000 loans because the service is joining loans, applicants, bureau reports, EMI schedules, and payment history in real time. How do you fix this with CQRS?"**
A: The dashboard query is the archetypal CQRS use case — a complex multi-domain read that has nothing to do with write consistency:

**Step 1 — Identify the query shape** (interview with ops/risk team):
- Total portfolio stats (count, outstanding, NPA %)
- At-risk loans (DPD ≥ 30)
- Recent delinquencies (last 7 days)
- Product breakdown (HL vs PL vs MSME)

**Step 2 — Design a dedicated projection:**
```sql
CREATE TABLE risk_dashboard_projection (
  as_of_date        DATE NOT NULL,
  total_loans       INTEGER,
  total_outstanding BIGINT,   -- in paise
  npa_count         INTEGER,
  npa_amount        BIGINT,
  dpd_30_count      INTEGER,
  dpd_60_count      INTEGER,
  dpd_90_count      INTEGER,
  avg_bureau_score  DECIMAL(5,1),
  hl_outstanding    BIGINT,
  pl_outstanding    BIGINT,
  msme_outstanding  BIGINT,
  PRIMARY KEY (as_of_date)
);
```

**Step 3 — Build the projector:**
Update the projection on every relevant event (`EmiCollectedEvent`, `EmiDefaultedEvent`, `LoanDisbursedEvent`, `LoanClosedEvent`). Or, for a daily snapshot, run a nightly aggregation job.

**Step 4 — Query the projection:**
```typescript
@QueryHandler(GetRiskDashboardQuery)
export class GetRiskDashboardQueryHandler {
  async execute(query: GetRiskDashboardQuery): Promise<RiskDashboardDto> {
    // Sub-millisecond — single row lookup
    const snapshot = await this.prisma.riskDashboardProjection.findUnique({
      where: { asOfDate: query.asOfDate ?? new Date() },
    });
    return snapshot as RiskDashboardDto;
  }
}
```

Dashboard load time: 4 seconds → under 10 milliseconds.

**Q19. "Your team needs to add a new report — all loans where the NACH mandate was registered but the first EMI was never collected (potential orphan mandates). The data exists in the system but spans two bounded contexts (NACH and Collections). How do you build this without coupling the two contexts?"**
A: Build a cross-context projection by subscribing to events from both contexts:

```typescript
// New projection table — doesn't belong to either bounded context
// CREATE TABLE orphan_mandate_projection (
//   loan_id          UUID PRIMARY KEY,
//   mandate_urn      TEXT NOT NULL,
//   mandate_registered_at TIMESTAMPTZ NOT NULL,
//   first_emi_due_date DATE NOT NULL,
//   first_emi_collected BOOLEAN DEFAULT FALSE
// );

// Projector — subscribes to events from two bounded contexts
@Injectable()
export class OrphanMandateProjector {
  @OnEvent('NachMandateRegisteredEvent') // from NACH bounded context
  async onMandateRegistered(event: NachMandateRegisteredEvent): Promise<void> {
    await this.prisma.orphanMandateProjection.create({
      data: {
        loanId: event.loanId,
        mandateUrn: event.umrn,
        mandateRegisteredAt: event.registeredAt,
        firstEmiDueDate: event.firstEmiDueDate,
        firstEmiCollected: false,
      },
    });
  }

  @OnEvent('EmiCollectedEvent') // from Collections bounded context
  async onEmiCollected(event: EmiCollectedEvent): Promise<void> {
    const record = await this.prisma.orphanMandateProjection.findUnique({
      where: { loanId: event.loanId },
    });
    // Mark first EMI as collected if this is the first payment
    if (record && !record.firstEmiCollected) {
      await this.prisma.orphanMandateProjection.update({
        where: { loanId: event.loanId },
        data: { firstEmiCollected: true },
      });
    }
  }
}

// Query — reads the cross-context projection without coupling the contexts
@QueryHandler(GetOrphanMandatesQuery)
export class GetOrphanMandatesQueryHandler {
  async execute(query: GetOrphanMandatesQuery): Promise<OrphanMandateDto[]> {
    return this.prisma.orphanMandateProjection.findMany({
      where: {
        firstEmiCollected: false,
        firstEmiDueDate: { lt: new Date() }, // first EMI is past due
      },
      orderBy: { firstEmiDueDate: 'asc' },
    });
  }
}
```

The NACH bounded context doesn't know about Collections; the Collections context doesn't know about NACH. They publish events independently; the projector (in a reporting/ops context) assembles the cross-context view. This is CQRS enabling cross-context queries without coupling.

**Q20. "A regulatory audit finds that you have no complete audit trail for loan status changes — only the current state. The auditor wants to know every status transition, who triggered it, and when. How do you add this using CQRS without changing your existing write model?"**
A: Add a new projection that captures every command outcome — without touching the aggregate or write-side code:

```typescript
// New projector — subscribes to all loan lifecycle events
// (these events already exist; nothing changes on the write side)
@Injectable()
export class LoanAuditTrailProjector {
  private readonly eventToAuditEntry: Record<string, (e: DomainEvent) => AuditEntry> = {
    'LoanApplicationSubmittedEvent': (e: LoanApplicationSubmittedEvent) => ({
      loanId: e.applicationId, statusBefore: null, statusAfter: 'SUBMITTED',
      triggeredBy: e.applicantId, triggeredAt: e.occurredAt, notes: null,
    }),
    'LoanApplicationSentForReviewEvent': (e: LoanApplicationSentForReviewEvent) => ({
      loanId: e.applicationId, statusBefore: 'SUBMITTED', statusAfter: 'UNDER_REVIEW',
      triggeredBy: e.reviewedBy, triggeredAt: e.occurredAt, notes: null,
    }),
    'LoanSanctionedEvent': (e: LoanSanctionedEvent) => ({
      loanId: e.applicationId, statusBefore: 'UNDER_REVIEW', statusAfter: 'SANCTIONED',
      triggeredBy: e.sanctionedBy, triggeredAt: e.occurredAt,
      notes: `Sanctioned amount: ₹${e.sanctionedAmount / 100}`,
    }),
    'LoanApplicationRejectedEvent': (e: LoanApplicationRejectedEvent) => ({
      loanId: e.applicationId, statusBefore: null, statusAfter: 'REJECTED',
      triggeredBy: e.rejectedBy, triggeredAt: e.occurredAt, notes: e.reason,
    }),
  };

  async handle(event: DomainEvent): Promise<void> {
    const builder = this.eventToAuditEntry[event.constructor.name];
    if (!builder) return; // event not relevant to audit trail

    await this.prisma.loanAuditTrail.create({ data: builder(event) });
  }
}

// Rebuild historical audit trail by replaying all existing events
// — gives the auditor complete history back to day one
await this.projectionRebuildService.rebuild('LoanAuditTrailProjection');
```

The write model is completely untouched. The audit trail is built by projecting existing events. Historical data is recovered by replaying events already in the system. The auditor gets a complete, verifiable trail — with no changes to any business logic.

## Quick Reference: CQRS Checklist

| Signal                                                                            | Decision                                                                   |
|-----------------------------------------------------------------------------------|----------------------------------------------------------------------------|
| Dashboard query joins 5+ tables and takes 2–4 seconds                            | CQRS — dedicated projection shaped for the dashboard                       |
| Read and write workloads differ 10:1 or more                                     | CQRS — separate scaling for read replicas vs write primary                 |
| Same domain model serves ops dashboard, customer app, and regulatory reporting    | CQRS — one projection per consumer; each optimised independently           |
| Need complete audit trail but only current state is stored                        | Add an audit trail projector; replay existing events to backfill           |
| Two bounded contexts need a cross-context report without direct coupling          | Cross-context projection subscribing to events from both                   |
| Immediate read of just-written data is required                                   | Return minimal result from command + poll; or read-your-writes strategy     |
| Command returns a large DTO                                                       | Split — command returns ID/ack; client queries separately                  |
| Projector fails silently                                                          | Route events through queue (SQS/RabbitMQ) with DLQ; make projections idempotent |
| System is simple CRUD with no dashboard complexity                                | Skip CQRS — plain service layer is sufficient                              |
| Team < 5 engineers, early-stage product                                           | Skip CQRS — complexity not justified yet; refactor in when needed          |

---

**Tip for the interview:** At the 5 YOE level, CQRS questions come disguised as performance problems ("our dashboard is slow") or data problems ("we need historical state but only store current"). The answer that lands at the senior level starts with *the problem* — reads and writes have different optimisation needs — then names the pattern, distinguishes the command bus from the query bus, and explains projections with a concrete example from the lending domain (EMI default updating three different projections simultaneously: portfolio risk, collections queue, customer notifications). The senior differentiator is understanding the trade-offs: you can name when CQRS is overkill (simple CRUD), you know that eventual consistency requires explicit API design (202 Accepted, not 201 Created), and you can explain how to rebuild a projection from events — which turns what looks like a data migration nightmare into a simple event replay. If you've actually shipped a CQRS system, have the specific projections you built ready to describe: that specificity — "we had four projections for the ops dashboard, the customer app, collections, and RBI regulatory reporting, all fed from the same domain events" — is what separates a pattern description from evidence of having used it.
