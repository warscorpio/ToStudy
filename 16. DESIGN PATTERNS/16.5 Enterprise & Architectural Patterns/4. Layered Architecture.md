# Enterprise & Architectural Patterns: Layered Architecture — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Layered Architecture?**
A: Layered Architecture (also called N-Tier Architecture) is an architectural pattern that organises a system into **horizontal layers**, where each layer has a distinct responsibility and communicates only with the layer directly beneath it. Each layer is a logical grouping of components that serve a common abstraction level — presentation, business logic, data access, and so on. The fundamental rule: **upper layers depend on lower layers; lower layers never depend on upper layers**.

The canonical four-layer breakdown:
- **Presentation Layer** — handles user interaction or API entry points; formats input/output; no business logic.
- **Business Logic (Service/Application) Layer** — orchestrates use cases; applies domain rules; coordinates between domain and infrastructure.
- **Persistence (Data Access) Layer** — abstracts data storage; translates between domain objects and database rows; all DB queries live here.
- **Database Layer** — the actual data store (PostgreSQL, Redis, etc.); not application code, but modelled as a layer because all access must go through the persistence layer.

**Q2. What problem does Layered Architecture solve?**
A: Layered Architecture solves three fundamental problems in medium-to-large backend systems:

- **Separation of concerns** — each layer has one reason to change. HTTP response shaping changes don't touch business rules; database schema migrations don't ripple into controllers.
- **Controlled dependency direction** — without enforced layers, any component can depend on any other, creating a dependency tangle where a change anywhere breaks everything. Layers give you a predictable, one-way dependency graph.
- **Replaceability** — because each layer is isolated behind an interface, you can swap implementations independently. Switching from REST to gRPC should only touch the presentation layer; switching from PostgreSQL to CockroachDB should only touch the persistence layer.

**Q3. What is the "strict layering" vs "relaxed layering" distinction?**
A: The difference is whether layers can be skipped:

- **Strict layering** — a request must pass through every layer in sequence. Presentation always calls Service; Service always calls Repository; Repository always calls DB. No layer may call a non-adjacent layer. This maximises isolation but adds overhead for simple read-through operations.
- **Relaxed (open) layering** — layers may be skipped when appropriate. A presentation layer component may directly query the persistence layer for a simple read-only lookup without going through the full service layer. Trades isolation for simplicity and performance.

In practice, most fintech backends use **relaxed layering**: the service layer is mandatory for write operations (business rules must be enforced), but simple reference data reads (fetching a list of loan products, getting a bank's IFSC details) may go directly from controller to repository.

**Q4. What is the cardinal sin of Layered Architecture, and what does it look like in practice?**
A: The cardinal sin is a **layer boundary violation** — a lower layer depending on or knowing about a higher layer. The most common violation: the persistence layer importing from the service layer, or business logic directly embedded in a controller.

```typescript
// ❌ Violation 1 — Business logic in the presentation layer
@Post('/loans/apply')
async applyForLoan(@Body() dto: CreateLoanDto) {
  // This belongs in LoanService, not the controller
  if (dto.monthlyIncome < 25000) {
    throw new BadRequestException('Income too low');
  }
  if (dto.cibilScore < 700) {
    throw new BadRequestException('Score too low');
  }
  await this.db.query('INSERT INTO loans ...'); // Also hitting DB directly from controller
}

// ❌ Violation 2 — Repository knows about HTTP (presentation concerns)
class LoanRepository {
  async findAll(req: Request): Promise<Loan[]> { // HTTP Request object in the data layer!
    const page = req.query.page;  // pagination from HTTP leaking into persistence
    return this.db.query(`SELECT * FROM loans LIMIT 10 OFFSET ${page * 10}`);
  }
}

// ❌ Violation 3 — Service layer directly returns HTTP response objects
class LoanService {
  async applyForLoan(dto: CreateLoanDto): Promise<Response> { // HTTP Response in service layer!
    return new Response(JSON.stringify({ status: 'approved' }), { status: 201 });
  }
}
```

**Q5. How does Layered Architecture relate to NestJS's module structure?**
A: NestJS's architecture maps directly to the Layered Architecture pattern — the framework enforces the structure through its conventions:

| NestJS construct    | Layered Architecture equivalent    |
|---------------------|------------------------------------|
| `@Controller`       | Presentation Layer                 |
| `@Injectable` Service | Business Logic / Application Layer |
| Repository class    | Persistence Layer                  |
| `PrismaService` / `TypeORM` entities | Persistence + DB Layer |
| `@Module`           | Encapsulates one slice of all layers |

NestJS's DI system enforces the dependency direction: controllers inject services; services inject repositories; repositories inject the ORM/query client. The framework makes it structurally easy to respect layer boundaries, though it doesn't prevent violations — discipline and code review do.

## Section 2: Layer Responsibilities in Detail

**Q6. What are the exact responsibilities of the Presentation Layer in a NestJS REST API?**
A: The Presentation Layer (controllers + DTOs + pipes + guards in NestJS) is responsible for:

- **Request parsing** — extracting data from HTTP request (path params, query params, body, headers).
- **Input validation and transformation** — using `class-validator`, `class-transformer`, `ValidationPipe` to ensure input shape is correct before it reaches the service.
- **Authentication and authorisation** — guards check JWTs, roles, permissions at the HTTP boundary.
- **Response formatting** — shaping the service's domain output into the HTTP response (status codes, response DTOs, serialisation).
- **Error translation** — catching domain exceptions and translating to appropriate HTTP status codes.

What the Presentation Layer must **not** do:
- Apply business rules (income thresholds, LTV limits, bureau score cuts) — that's the service layer.
- Query the database — that's the repository layer.
- Hold any state between requests.

```typescript
// ✅ Clean presentation layer — orchestrates, delegates, formats
@Post('/loans/apply')
@UseGuards(JwtAuthGuard)
@HttpCode(HttpStatus.CREATED)
async applyForLoan(
  @Body() dto: CreateLoanApplicationDto, // validated by ValidationPipe
  @CurrentUser() user: AuthenticatedUser,
): Promise<LoanApplicationResponseDto> {
  const result = await this.loanApplicationService.apply(dto, user.id);
  return LoanApplicationResponseDto.fromDomain(result); // response shaping here
}
```

**Q7. What are the exact responsibilities of the Business Logic (Service) Layer?**
A: The Service Layer is the application's decision-making core:

- **Orchestrating use cases** — coordinates multiple domain operations and infrastructure calls to fulfil a business use case (e.g., "apply for a loan" = validate eligibility + pull bureau + compute offer + persist + notify).
- **Enforcing business rules** — income thresholds, LTV ratios, bureau score requirements, product eligibility rules. These must not live anywhere else.
- **Transaction boundaries** — decides what constitutes an atomic operation; coordinates the unit of work.
- **Domain event publishing** — emits events when significant domain transitions occur (LoanApproved, EmiCollected, MandateRegistered).
- **Cross-cutting coordination** — calls bureau APIs, payment gateways, notification services — all orchestrated here, not in controllers or repositories.

```typescript
// ✅ Clean service layer — business logic, orchestration, no HTTP awareness
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly eligibilityService: LoanEligibilityService,
    private readonly bureauService: BureauService,
    private readonly loanRepository: LoanRepository,
    private readonly notificationService: NotificationService,
  ) {}

  async apply(dto: CreateLoanApplicationDto, applicantId: string): Promise<LoanApplication> {
    // Business rule enforcement — lives here
    await this.eligibilityService.assertEligible(dto);

    // External service coordination — lives here
    const bureauReport = await this.bureauService.fetchCreditReport(dto.pan);

    // Persistence — delegated to repository
    const loan = await this.loanRepository.create({
      ...dto,
      applicantId,
      bureauScore: bureauReport.score,
      status: 'PENDING',
    });

    // Side effects — coordinated here
    await this.notificationService.sendApplicationReceived(loan);

    return loan; // returns domain object, not HTTP response
  }
}
```

**Q8. What are the exact responsibilities of the Persistence (Repository) Layer?**
A: The Repository Layer is the anti-corruption layer between your domain model and the database:

- **Abstracting the data store** — the service layer calls `loanRepository.findById(id)`, not `prisma.loan.findUnique(...)`. If you switch from Prisma to TypeORM or a raw pg client, only the repository changes.
- **Translating between domain objects and database representations** — ORM entities may have different shapes than domain objects; the repository handles the mapping.
- **Encapsulating all queries** — no SQL or ORM query methods should appear outside the repository. Centralising queries makes them easier to optimise, test, and secure.
- **Pagination, filtering, sorting abstractions** — expressed in domain terms (`findByStatus('APPROVED', { page: 1, limit: 20 })`), not HTTP query string terms.

```typescript
// ✅ Clean repository layer — database-facing, domain-returning
@Injectable()
export class LoanRepository {
  constructor(private readonly prisma: PrismaService) {}

  async findById(id: string): Promise<Loan | null> {
    const record = await this.prisma.loan.findUnique({ where: { id } });
    return record ? this.toDomain(record) : null;
  }

  async findByApplicantAndStatus(
    applicantId: string,
    status: LoanStatus,
  ): Promise<Loan[]> {
    const records = await this.prisma.loan.findMany({
      where: { applicantId, status },
      orderBy: { createdAt: 'desc' },
    });
    return records.map(this.toDomain);
  }

  async create(data: CreateLoanData): Promise<Loan> {
    const record = await this.prisma.loan.create({ data: this.toPersistence(data) });
    return this.toDomain(record);
  }

  // Mapping methods — the translation responsibility
  private toDomain(record: PrismaLoan): Loan {
    return new Loan(record.id, record.applicantId, record.amount, record.status as LoanStatus);
  }

  private toPersistence(loan: CreateLoanData): Prisma.LoanCreateInput {
    return {
      applicantId: loan.applicantId,
      amount: loan.amount,
      status: loan.status,
      bureauScore: loan.bureauScore,
    };
  }
}
```

**Q9. What is the DTO (Data Transfer Object) pattern, and how does it enforce layer boundaries?**
A: DTOs are plain objects used to transfer data between layers — crucially, each layer pair has its own DTO shape, preventing the leakage of one layer's representation into another:

```typescript
// Layer 1 (Presentation) → Layer 2 (Service)
// What the controller receives from the client and passes to the service
export class CreateLoanApplicationDto {
  @IsString() @IsNotEmpty() applicantId: string;
  @IsString() @IsPan() pan: string;
  @IsNumber() @Min(10000) requestedAmount: number;
  @IsString() productCode: string;
}

// Layer 2 (Service) internal domain object — not exposed to HTTP
export class LoanApplication {
  constructor(
    public readonly id: string,
    public readonly applicantId: string,
    public readonly amount: number,
    public readonly status: LoanStatus,
    public readonly bureauScore: number,
    public readonly createdAt: Date,
  ) {}
}

// Layer 2 (Service) → Layer 1 (Presentation)
// What the controller sends back to the client — may omit internal fields
export class LoanApplicationResponseDto {
  @Expose() id: string;
  @Expose() status: string;
  @Expose() requestedAmount: number;
  @Expose() @Transform(({ value }) => value?.toISOString()) createdAt: string;

  static fromDomain(loan: LoanApplication): LoanApplicationResponseDto {
    return plainToInstance(LoanApplicationResponseDto, loan, { excludeExtraneousValues: true });
  }
}

// Layer 2 (Service) → Layer 3 (Repository)
// Internal persistence shape — maps to DB schema
export interface CreateLoanData {
  applicantId: string;
  amount: number;
  status: LoanStatus;
  bureauScore: number;
  productCode: string;
}
```

Each DTO is owned by the boundary where it flows. The client never sees `bureauScore`; the repository never sees HTTP response fields. Adding a new response field doesn't touch the domain object or the DB schema.

## Section 3: Layered Architecture in a NestJS/TypeScript Fintech Context

**Q10. What does a well-structured directory layout look like for a NestJS lending platform using Layered Architecture?**
A:

```
src/
  loan/
    loan.module.ts
    presentation/
      controllers/
        loan-application.controller.ts    # Presentation layer
        loan-status.controller.ts
      dto/
        create-loan-application.dto.ts    # Input DTOs
        loan-application-response.dto.ts  # Output DTOs
      guards/
        loan-ownership.guard.ts
    application/                          # Business logic layer
      services/
        loan-application.service.ts
        loan-eligibility.service.ts
        loan-disbursement.service.ts
      events/
        loan-approved.event.ts
    domain/                               # Core domain objects
      loan.entity.ts
      loan-status.enum.ts
      loan.repository.interface.ts        # Port (interface) — dependency inversion
    infrastructure/                       # Persistence layer
      repositories/
        prisma-loan.repository.ts         # Implements loan.repository.interface.ts
      mappers/
        loan.mapper.ts                    # toDomain() / toPersistence()
      persistence/
        loan.schema.prisma               # or TypeORM entity
  bureau/
    ...same structure...
  nach/
    ...same structure...
  notification/
    ...same structure...
  shared/
    database/
      prisma.service.ts
    auth/
      jwt.strategy.ts
    exceptions/
      domain-exception.filter.ts
```

The `domain/` folder is the most important signal — it contains the repository *interface*, not the implementation. The service layer depends on the interface (`LoanRepository` interface); the infrastructure layer provides the implementation (`PrismaLoanRepository`). This is the Dependency Inversion Principle applied within Layered Architecture.

**Q11. How do you handle cross-layer transaction management without violating layer boundaries?**
A: Transactions must span multiple repository calls coordinated by the service layer — the service declares *what* is atomic, but the transaction mechanism is an infrastructure concern. Use the Unit of Work pattern or pass a transaction context:

```typescript
// Option A — Prisma interactive transactions (most common in NestJS/Prisma)
@Injectable()
export class LoanDisbursementService {
  constructor(private readonly prisma: PrismaService) {}

  async disburse(loanId: string, bankDetails: BankDetails): Promise<void> {
    await this.prisma.$transaction(async (tx) => {
      // All operations inside tx are atomic
      const loan = await this.loanRepo.findById(loanId, tx);   // tx passed as context
      if (loan.status !== 'SANCTIONED') throw new InvalidLoanStatusException(loanId);

      await this.loanRepo.updateStatus(loanId, 'DISBURSEMENT_INITIATED', tx);
      await this.disbursementRepo.create({ loanId, amount: loan.amount, bankDetails }, tx);
      await this.ledgerRepo.recordDebit({ loanId, amount: loan.amount }, tx);
    });
    // Post-transaction side effects (notification) happen AFTER commit
    await this.notificationService.sendDisbursementInitiated(loanId);
  }
}

// Repository accepts optional transaction context
@Injectable()
export class LoanRepository implements ILoanRepository {
  constructor(private readonly prisma: PrismaService) {}

  async updateStatus(
    id: string,
    status: LoanStatus,
    tx?: Prisma.TransactionClient, // optional — defaults to the root client
  ): Promise<void> {
    const client = tx ?? this.prisma;
    await client.loan.update({ where: { id }, data: { status } });
  }
}
```

The transaction boundary is declared in the service (the business decision — "disbursement is atomic"), while the mechanics are in the infrastructure layer. The repository is neutral — it accepts either the root client or a transaction client.

**Q12. How do you implement cross-cutting concerns (logging, metrics, audit) without polluting service layer code?**
A: Cross-cutting concerns are added at layer boundaries using NestJS Interceptors (Decorator pattern) and middleware — not embedded in service methods:

```typescript
// Audit logging interceptor — wraps all loan write operations at the presentation boundary
@Injectable()
export class LoanAuditInterceptor implements NestInterceptor {
  constructor(private readonly auditLog: AuditLogService) {}

  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const request = context.switchToHttp().getRequest();
    const { method, url, user, body } = request;

    return next.handle().pipe(
      tap((responseBody) => {
        this.auditLog.record({
          actor: user?.id,
          action: `${method} ${url}`,
          resourceId: responseBody?.id,
          timestamp: new Date(),
          ipAddress: request.ip,
        });
      }),
    );
  }
}

// Performance metrics — wraps service layer calls
@Injectable()
export class MetricsInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const start = Date.now();
    const endpoint = context.switchToHttp().getRequest().url;

    return next.handle().pipe(
      tap(() => this.metrics.record(`http.latency.${endpoint}`, Date.now() - start)),
      catchError(err => {
        this.metrics.increment(`http.errors.${endpoint}`);
        return throwError(() => err);
      }),
    );
  }
}
```

Service methods stay clean — they implement business logic, not logging boilerplate. The interceptors add the cross-cutting behaviour transparently at the HTTP layer boundary.

**Q13. How do you handle domain exceptions across layers — ensuring HTTP status codes don't leak into the service layer?**
A: Define domain exceptions in the business logic layer; translate them to HTTP at the presentation boundary using NestJS Exception Filters:

```typescript
// Domain exceptions — live in the application/domain layer, no HTTP awareness
export class LoanNotFoundException extends Error {
  constructor(loanId: string) {
    super(`Loan ${loanId} not found`);
    this.name = 'LoanNotFoundException';
  }
}

export class IneligibleApplicantException extends Error {
  constructor(public readonly reasons: string[]) {
    super(`Applicant is ineligible: ${reasons.join(', ')}`);
    this.name = 'IneligibleApplicantException';
  }
}

export class InsufficientBureauScoreException extends Error {
  constructor(public readonly score: number, public readonly minimum: number) {
    super(`Bureau score ${score} is below minimum ${minimum}`);
    this.name = 'InsufficientBureauScoreException';
  }
}

// Exception filter — presentation layer concern: translate domain → HTTP
@Catch()
@Injectable()
export class DomainExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost): void {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();

    if (exception instanceof LoanNotFoundException) {
      return response.status(404).json({ error: exception.message });
    }
    if (exception instanceof IneligibleApplicantException) {
      return response.status(422).json({
        error: 'Applicant not eligible',
        reasons: exception.reasons,
      });
    }
    if (exception instanceof InsufficientBureauScoreException) {
      return response.status(422).json({
        error: 'Insufficient credit score',
        score: exception.score,
        required: exception.minimum,
      });
    }
    // Fallthrough — unexpected errors
    response.status(500).json({ error: 'Internal server error' });
  }
}
```

The service layer throws domain exceptions; the filter (at the presentation layer boundary) translates them to HTTP. Adding a new endpoint that uses `LoanNotFoundException` automatically gets the correct 404 response — the translation is centralised.

**Q14. How does Layered Architecture interact with event-driven patterns in a lending platform?**
A: Domain events decouple service layer operations from their side effects without violating layer boundaries. The service publishes events; event handlers (in separate modules) consume them — each handler is itself a layered slice:

```typescript
// Service layer — publishes domain events, doesn't care who listens
@Injectable()
export class LoanApprovalService {
  constructor(
    private readonly loanRepository: ILoanRepository,
    private readonly eventEmitter: EventEmitter2,
  ) {}

  async approveLoan(loanId: string, approvedBy: string): Promise<void> {
    const loan = await this.loanRepository.findById(loanId);
    if (!loan) throw new LoanNotFoundException(loanId);

    await this.loanRepository.updateStatus(loanId, 'APPROVED');

    // Publish event — service doesn't know what happens next
    this.eventEmitter.emit('loan.approved', new LoanApprovedEvent(loanId, loan.applicantId, loan.amount));
  }
}

// Event handlers — each in its own layer-respecting slice
@Injectable()
export class LoanApprovedNotificationHandler {
  @OnEvent('loan.approved')
  async handle(event: LoanApprovedEvent): Promise<void> {
    // This handler has its own presentation/service/repo stack if needed
    await this.notificationService.sendApprovalNotification(event.applicantId, event.loanId);
  }
}

@Injectable()
export class LoanApprovedNachSetupHandler {
  @OnEvent('loan.approved')
  async handle(event: LoanApprovedEvent): Promise<void> {
    await this.nachService.initiateMandate(event.loanId);
  }
}
```

The approval service has no dependency on notification or NACH — it just announces what happened. Adding a new side effect (e.g., credit bureau update on approval) means adding a new event handler — zero changes to `LoanApprovalService`.

## Section 4: Common Violations and How to Fix Them

**Q15. What are the most common Layered Architecture violations in a NestJS fintech codebase, and how do you fix them?**
A:

**Violation 1 — Fat Controller (business logic in the presentation layer):**
```typescript
// ❌ Business logic in controller
@Post('/loans/:id/approve')
async approveLoan(@Param('id') id: string, @Body() body: ApproveDto) {
  const loan = await this.prisma.loan.findUnique({ where: { id } });
  if (loan.status !== 'PENDING_APPROVAL') throw new BadRequestException('...');
  if (loan.amount > 10_000_000 && body.approverRole !== 'CREDIT_COMMITTEE') {
    throw new ForbiddenException('Amount requires credit committee approval');
  }
  await this.prisma.loan.update({ where: { id }, data: { status: 'APPROVED' } });
}

// ✅ Fix — move to service; controller just routes
@Post('/loans/:id/approve')
async approveLoan(@Param('id') id: string, @Body() dto: ApproveDto, @CurrentUser() user: User) {
  await this.loanApprovalService.approve(id, user);
  return { message: 'Loan approved' };
}
```

**Violation 2 — Smart Repository (business logic in the persistence layer):**
```typescript
// ❌ Business rule in repository
class LoanRepository {
  async findEligibleLoans(applicantId: string): Promise<Loan[]> {
    // This is a business rule — which loans are "eligible" — not a query concern
    const loans = await this.prisma.loan.findMany({ where: { applicantId } });
    return loans.filter(l => l.cibilScore > 700 && l.income > 25000 && l.status === 'PENDING');
  }
}

// ✅ Fix — repository queries; service filters by business rules
class LoanRepository {
  async findByApplicant(applicantId: string): Promise<Loan[]> {
    return this.prisma.loan.findMany({ where: { applicantId } });
  }
}

class LoanEligibilityService {
  async findEligibleLoans(applicantId: string): Promise<Loan[]> {
    const loans = await this.loanRepo.findByApplicant(applicantId);
    return loans.filter(l => this.isEligible(l)); // business rule in service
  }
}
```

**Violation 3 — ORM Entity Leaking Across All Layers:**
```typescript
// ❌ Prisma/TypeORM entity used directly in controller response
@Get('/loans/:id')
async getLoan(@Param('id') id: string): Promise<PrismaLoan> { // Prisma type in response!
  return this.prisma.loan.findUnique({ where: { id } }); // DB call from controller
}

// ✅ Fix — map to response DTO at the presentation boundary
@Get('/loans/:id')
async getLoan(@Param('id') id: string): Promise<LoanResponseDto> {
  const loan = await this.loanService.findById(id); // domain object from service
  return LoanResponseDto.fromDomain(loan);          // DTO at boundary
}
```

**Violation 4 — Circular Dependencies Between Layers:**
```typescript
// ❌ Service imports from controller (lower layer depends on upper layer)
import { LoanController } from '../presentation/loan.controller'; // ← wrong direction

@Injectable()
export class LoanService {
  constructor(private readonly controller: LoanController) {} // circular disaster
}
```

NestJS will detect circular module dependencies at startup. The fix is always to extract the shared concern into a lower layer or a shared module that both layers import.

**Q16. What is the "Anemic Domain Model" anti-pattern, and how does Layered Architecture contribute to it?**
A: An Anemic Domain Model is one where domain objects (entities) are pure data containers with no behaviour — they have getters/setters but no domain logic. The business logic lives entirely in service classes, leaving entities as "dumb" data bags. Layered Architecture, when applied naïvely, encourages this: services do everything, entities do nothing.

```typescript
// ❌ Anemic — Loan entity is just a data bag
class Loan {
  id: string;
  status: LoanStatus;
  amount: number;
  // No behaviour — just data
}

// All business rules in the service — not where they belong
class LoanService {
  canRepay(loan: Loan, amount: number): boolean {
    return loan.status === 'ACTIVE' && amount <= loan.outstandingPrincipal;
  }
  canPrepay(loan: Loan): boolean {
    return loan.tenorCompletedMonths > 12 && loan.status === 'ACTIVE';
  }
}

// ✅ Rich domain model — loan knows its own rules
class Loan {
  constructor(
    public readonly id: string,
    private status: LoanStatus,
    private amount: number,
    private outstandingPrincipal: number,
    private tenorCompletedMonths: number,
  ) {}

  canRepay(repaymentAmount: number): boolean {
    return this.status === 'ACTIVE' && repaymentAmount <= this.outstandingPrincipal;
  }

  canPrepay(): boolean {
    return this.tenorCompletedMonths > 12 && this.status === 'ACTIVE';
  }

  approve(): void {
    if (this.status !== 'PENDING') throw new InvalidStatusTransitionException(this.status, 'APPROVED');
    this.status = 'APPROVED';
  }
}
```

The service layer then orchestrates, not decides: `loan.approve()` — the decision is in the entity; the service coordinates the persistence and notification.

## Section 5: Layered Architecture vs Related Architectures

**Q17. How does Layered Architecture compare to Hexagonal Architecture (Ports and Adapters)?**
A:

| Aspect                        | Layered Architecture                                | Hexagonal Architecture                              |
|-------------------------------|-----------------------------------------------------|-----------------------------------------------------|
| Dependency direction          | Top-down — upper layers depend on lower             | Inward — all dependencies point toward the domain   |
| Domain isolation              | Partial — domain may still depend on persistence    | Complete — domain has zero infrastructure dependencies |
| Testability of domain         | Requires mocking DB/service                         | Domain testable with no mocks at all                |
| Primary distinction           | Horizontal layers                                   | Inside (domain) vs outside (ports/adapters)         |
| Infrastructure coupling       | Service layer may know about Prisma types           | Domain never knows about Prisma, HTTP, or any infra |
| Suitable for                  | Most CRUD-heavy backends                            | Complex domain logic, high testability requirements |

Hexagonal Architecture is Layered Architecture with a stricter rule: **the domain layer has zero knowledge of any infrastructure** (no Prisma types, no HTTP types, no AWS SDK types). It depends on interfaces (ports); infrastructure provides implementations (adapters). This is achievable in NestJS by placing repository interfaces in the domain layer and implementations in an `infrastructure/` folder.

**Q18. When does Layered Architecture break down, and what architectural patterns complement or replace it?**
A: Layered Architecture breaks down in four scenarios:

- **High query complexity** — when reads need data from many layers simultaneously (e.g., a loan dashboard aggregating loans, payments, bureau data, NACH status), passing data up through every layer adds latency and complexity. **CQRS** (Command Query Responsibility Segregation) solves this: reads bypass the full service stack and query read models or denormalised views directly.
- **High throughput, async workflows** — synchronous request/response through all layers doesn't fit long-running processes (loan underwriting, NACH registration, disbursement). **Event-driven architecture with message queues** (AWS SQS, Kafka) handles these better — each async step is its own layered service.
- **Many independent business capabilities** — a single layered monolith with 20 domains (loan, KYC, collections, reporting, nach, bureau, notification...) becomes hard to deploy and scale independently. **Microservices** (each a self-contained layered application) solve deployment independence.
- **Very complex domain logic** — when business rules are so intricate that the service layer becomes a transaction script of hundreds of lines, the domain model needs to be richer (Domain-Driven Design with aggregates, value objects, domain events). **DDD within Layered or Hexagonal Architecture** enriches the domain layer without abandoning the layered structure.

**Q19. What is the difference between the Layered Architecture's "service layer" and an "application service" in Domain-Driven Design?**
A: The terms are related but DDD is more precise:

- **Layered Architecture service layer** — a catch-all layer for "not controller, not repository." In practice it often mixes orchestration logic, domain rules, and infrastructure coordination in the same class. No formal distinction between what types of logic belong here.
- **DDD Application Service** — specifically for *orchestration only*. It coordinates domain objects (aggregates), repositories, and external services to fulfil a use case. It has **no business rules of its own** — those live in domain objects (entities, value objects, domain services). An application service should be thin.

```typescript
// DDD-style application service — pure orchestration, no business logic
@Injectable()
export class ApplyForLoanApplicationService {
  async execute(command: ApplyForLoanCommand): Promise<void> {
    // Fetch domain object
    const applicant = await this.applicantRepo.findById(command.applicantId);
    if (!applicant) throw new ApplicantNotFoundException(command.applicantId);

    // Business rules live in the domain object, not here
    const loanApplication = LoanApplication.create(command, applicant); // factory on domain object

    // Persist via repository
    await this.loanApplicationRepo.save(loanApplication);

    // Publish domain event (already on loanApplication from .create())
    this.eventPublisher.publishAll(loanApplication.domainEvents);
  }
}
```

The `LoanApplication.create()` factory method *in the domain object* enforces all business rules (eligibility, amount limits, product rules). The application service just orchestrates — fetch, create, save, publish.

## Section 6: Scenario / System Design Questions

**Q20. "Your team's NestJS codebase has grown to 40,000 lines. A junior developer reports that changing the EMI calculation formula requires touching the controller, the service, and the repository. What's wrong and how do you fix it?"**
A: This is a layer boundary violation — the EMI calculation formula (a business rule) has leaked into multiple layers. Root cause analysis:

1. **Controller** — probably contains input validation that enforces EMI-related constraints (should be in service or domain).
2. **Service** — correctly contains EMI calculation, but also contains SQL for fetching the loan, mixing persistence with business logic.
3. **Repository** — probably contains an EMI-specific query (`findLoansWithEmiDue`) that encodes what "EMI due" means — a business concept — in query logic.

Fix in three steps:

```typescript
// Step 1 — extract EMI calculation to a domain service or value object
class EmiCalculator {
  static compute(principal: number, ratePercent: number, tenorMonths: number): EmiSchedule {
    const monthlyRate = ratePercent / 12 / 100;
    const emi = (principal * monthlyRate * (1 + monthlyRate) ** tenorMonths)
              / ((1 + monthlyRate) ** tenorMonths - 1);
    return { emi, schedule: buildSchedule(principal, monthlyRate, tenorMonths, emi) };
  }
}

// Step 2 — clean the repository: query by data, not by business meaning
class LoanRepository {
  async findActiveLoansWithDueDate(dueDate: Date): Promise<Loan[]> {
    return this.prisma.loan.findMany({
      where: { status: 'ACTIVE', nextEmiDate: { lte: dueDate } },
    }).then(rs => rs.map(this.toDomain));
  }
}

// Step 3 — service coordinates: uses EmiCalculator, calls repository cleanly
class EmiCollectionService {
  async collectDueEmis(): Promise<void> {
    const dueLoans = await this.loanRepo.findActiveLoansWithDueDate(new Date());
    for (const loan of dueLoans) {
      const schedule = EmiCalculator.compute(loan.principal, loan.rate, loan.tenor);
      await this.collectEmi(loan, schedule.emi);
    }
  }
}
```

Now changing the EMI formula touches exactly one place: `EmiCalculator`. Repository and controller are untouched.

**Q21. "Design the layered architecture for a new NACH debit retry system. When a debit fails, the system must retry based on failure code, notify the customer, and update the loan's delinquency status. Show the layer boundaries."**
A:

```typescript
// PRESENTATION LAYER — webhook endpoint that receives NACH callback from NPCI
@Post('/webhooks/nach/callback')
@UseGuards(NachWebhookSignatureGuard) // validates NPCI signature
async handleNachCallback(@Body() rawPayload: unknown): Promise<void> {
  const callback = this.nachCallbackAdapter.parse(rawPayload); // adapter translates NPCI → domain
  await this.nachCallbackService.process(callback);            // delegates to service
  // Returns 200 — NPCI needs acknowledgment
}

// APPLICATION SERVICE LAYER — orchestrates the business workflow
@Injectable()
export class NachCallbackService {
  async process(callback: NachDebitCallback): Promise<void> {
    const loan = await this.loanRepo.findByMandateUrn(callback.umrn);
    if (!loan) throw new LoanNotFoundException(`No loan for UMRN ${callback.umrn}`);

    if (callback.status === 'SUCCESS') {
      // Business rule enforcement — EMI credited
      await this.loanRepo.markEmiCollected(loan.id, callback.amount, callback.date);
      await this.notificationService.sendEmiSuccess(loan.applicantId, callback.amount);

    } else {
      // Business rule — classify failure and decide retry
      const retryPolicy = this.retryPolicyFactory.for(callback.failureCode);
      const schedule = retryPolicy.getSchedule(loan);

      await this.loanRepo.recordEmiFailure(loan.id, callback.failureCode);
      await this.delinquencyService.updateStatus(loan.id); // may move loan to DPD bucket

      if (schedule.shouldRetry) {
        await this.nachRetryQueue.schedule(loan.id, schedule.retryAt);
      }
      await this.notificationService.sendEmiFailure(loan.applicantId, callback.failureCode, schedule);
    }
  }
}

// PERSISTENCE LAYER — no business logic; just data access
@Injectable()
export class LoanRepository {
  async findByMandateUrn(umrn: string): Promise<Loan | null> { /* ... */ }
  async markEmiCollected(loanId: string, amount: number, date: Date): Promise<void> { /* ... */ }
  async recordEmiFailure(loanId: string, failureCode: string): Promise<void> { /* ... */ }
}
```

Layer responsibilities are clean:
- Presentation: parse NPCI callback, verify signature, return 200.
- Service: orchestrate the business response — what should happen when a debit fails?
- Domain: `retryPolicy.getSchedule()` — the business rule about when to retry.
- Repository: persist the outcome — no awareness of what NPCI is or why the EMI failed.

**Q22. "A code review reveals that your `LoanService` file is 1,200 lines long. It handles application, eligibility, underwriting, disbursement, collection, and reporting. How do you restructure this using Layered Architecture principles?"**
A: A 1,200-line service is a God Class — it has accumulated multiple responsibilities. The fix is vertical slicing within the existing layers:

```typescript
// Split by use case / bounded context — each is its own service
// loan/application/
//   services/
//     loan-application.service.ts       (apply, withdraw)
//     loan-eligibility.service.ts       (assess, prequalify)
//     loan-underwriting.service.ts      (underwrite, decline, approve)
//     loan-disbursement.service.ts      (initiate, confirm, reverse)
//     loan-collection.service.ts        (collectEmi, handleFailure, scheduleRetry)
//     loan-reporting.service.ts         (generateStatement, exportPortfolio)

// Each service has its own narrow interface and injected dependencies
@Injectable()
export class LoanApplicationService {
  // Depends on: LoanRepository, BureauService, NotificationService
  // Methods: apply(), withdraw(), getStatus()
}

@Injectable()
export class LoanUnderwritingService {
  // Depends on: LoanRepository, EligibilityService, RiskScoringService
  // Methods: underwrite(), approve(), decline()
}

@Injectable()
export class LoanDisbursementService {
  // Depends on: LoanRepository, PaymentGatewayService, LedgerService
  // Methods: initiateDisbursement(), confirmDisbursement()
}
```

Each service is now testable in isolation, has a clear set of dependencies, and has one team of business stakeholders who own it (Originations team owns `LoanApplicationService`; Collections team owns `LoanCollectionService`). The 1,200 lines become six files of 150–200 lines each — each well within the cognitive limit for a single reading session.

## Quick Reference: Layered Architecture Checklist

| Signal                                                                      | Diagnosis & Fix                                                                    |
|-----------------------------------------------------------------------------|------------------------------------------------------------------------------------|
| Controller contains `if` statements with business rules                     | Fat Controller — move rules to service layer                                       |
| Repository method name describes a business concept (`findEligibleLoans`)   | Smart Repository — query on data; filter in service                                |
| Service method returns `HttpException` or imports from `@nestjs/common`     | Layer bleed — service should throw domain exceptions; filter translates at boundary |
| Prisma/TypeORM entity type used in controller method signature              | ORM leaking upward — map to DTO at the presentation boundary                       |
| Domain objects are pure data bags with no methods                           | Anemic Domain Model — move business rules onto the entity                          |
| Changing one business rule requires editing 3+ files in different layers    | Cross-layer concern — extract to domain service or value object                    |
| Service file exceeds ~300 lines                                             | God Service — split by use case into focused service classes                       |
| Two services import each other (circular)                                   | Missing abstraction — extract shared concern to a lower layer or shared module     |
| Repository method accepts `Request` object                                  | Presentation concern leaking down — use domain parameters only in repositories     |
| Unit testing a service requires spinning up a full NestJS app               | Missing interface / DI abstraction — inject via interface, mock in tests            |

**Tip for the interview:** At the 5 YOE level, Layered Architecture questions rarely start with "define Layered Architecture." They come disguised as system design questions ("how would you structure a loan origination service?"), code review scenarios ("what's wrong with this controller?"), or refactoring questions ("this service has 1,200 lines — what do you do?"). The answer that lands at the senior level names the layers explicitly, gives the boundary responsibility for each layer, explains the dependency rule (upper depends on lower; never reverse), and has a concrete story about a violation you found and fixed — a fat controller, a leaking ORM entity, a repository encoding business logic. The architectural nuance that separates 5 YOE from 3 YOE: knowing that Layered Architecture encourages the Anemic Domain Model and understanding how a rich domain model corrects it while staying within the layered structure, and knowing when Layered Architecture's limitations (complex queries, async workflows, deployment independence) point toward CQRS, event-driven architecture, or microservices.
