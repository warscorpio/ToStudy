# JavaScript / TypeScript (Design Patterns — SOLID Principles): Coupling vs Cohesion — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is coupling?**
A: Coupling is the degree to which one module, class, or function *depends on* or *knows about* the internals of another. High coupling means a change in one place forces changes in many others — the modules are entangled. Low coupling means modules interact through narrow, stable contracts and are ignorant of each other's implementation details. Coupling is not binary — it exists on a spectrum from tight (worst) to loose (best). The goal is not zero coupling (an isolated module does nothing useful) but *minimal, intentional* coupling through well-defined interfaces.

**Q2. What is cohesion?**
A: Cohesion is the degree to which the elements *inside* a single module, class, or function belong together — how focused and unified its purpose is. High cohesion means everything inside the unit serves a single, well-defined responsibility. Low cohesion means the unit is a grab-bag of unrelated concerns that happen to live in the same file or class. Cohesion is an internal quality; coupling is a relationship quality between units.

**Q3. What is the canonical relationship between coupling and cohesion?**
A: They are inversely related in practice and jointly optimised by the same design decisions:
- **High cohesion → low coupling.** A class that does one thing well has a small, stable interface. Small, stable interfaces are easy for others to depend on without knowing internals — so external coupling is naturally low.
- **Low cohesion → high coupling.** A class that does many unrelated things grows a large, unstable interface. Callers must know more about it to use it, and changes inside it ripple outward.

The design mantra is: **maximise cohesion, minimise coupling.** These are not competing goals — they pull in the same direction. A well-designed system has tightly focused modules loosely connected through narrow contracts.

**Q4. Why do both concepts matter at the 5 YOE level — aren't they just theory?**
A: They're the root diagnosis behind the majority of real architectural problems:
- "Why does changing the database schema require touching the UI layer?" — accidental coupling across layers.
- "Why is this 2,000-line service impossible to unit test?" — low cohesion; the service has too many concerns, so testing one path drags in unrelated setup.
- "Why does every new feature require touching the same three files?" — a low-cohesion module is acting as a global coordination point; it's coupled to everything because it knows about everything.
- "Why did the Stripe migration take six weeks?" — payment logic was coupled directly into order processing, user management, and reporting.

At 5 YOE, you're expected to diagnose these from symptoms, name the root cause, and propose a concrete restructuring — not just define the terms.

**Q5. What is the classic formulation of good design in terms of these two concepts?**
A: Larry Constantine and Edward Yourdon (in *Structured Design*, 1979) established the foundational principle: **"Modules should be strongly cohesive and loosely coupled."** This predates OOP and applies equally to functions, classes, microservices, and React components. Every major design principle — SRP, DIP, ISP, Law of Demeter, Hexagonal Architecture — is a specific application of this general goal.

## Section 2: Types of Coupling

**Q6. What are the main types of coupling, ordered from tightest to loosest?**
A: Structured Design identified a coupling spectrum. Tightest (worst) to loosest (best):

| Level | Name | Description |
|---|---|---|
| 1 (worst) | **Content coupling** | Module A directly reads or writes the internal data of module B (accesses private fields, patches prototype) |
| 2 | **Common coupling** | Two modules share global mutable state (a global variable, a singleton, `window.x`) |
| 3 | **Control coupling** | A calls B and passes a flag/mode that controls B's internal logic (`doWork(true)` means "also log") |
| 4 | **Stamp coupling** | A passes a whole data structure to B, but B only uses part of it — B knows more about A's data shape than needed |
| 5 | **Data coupling** | A passes only the data B needs, through parameters — B knows nothing about A's internal shape |
| 6 (best) | **Message coupling** | Modules interact only via message passing / events — no direct method calls, no shared types |

In practice: aim for data or message coupling; avoid content and common coupling entirely; be alert for control and stamp coupling.

**Q7. What does content coupling look like in JavaScript, and how do you fix it?**
A: Content coupling means one module reaches into another's private implementation:
```ts
// Content coupling — module B (test or another class) accesses private internals
class UserService {
  private cache: Map<string, User> = new Map();

  async getUser(id: string): Promise<User> {
    if (this.cache.has(id)) return this.cache.get(id)!;
    const user = await this.db.find(id);
    this.cache.set(id, user);
    return user;
  }
}

// Content coupling — external code mutates private state directly
(userService as any).cache.set("1", fakeUser); // ✗ — accesses private cache

// Fix — expose a controlled seam (test helper method or injectable cache)
class UserService {
  constructor(private cache: UserCache, private db: UserRepository) {}
  // tests inject a fake UserCache — no private access needed
}
```
Monkey-patching prototypes (`Array.prototype.myMethod = ...`) and reaching into `_private` fields (JavaScript convention) are the most common JavaScript-specific content coupling patterns.

**Q8. What does common coupling look like, and why is it particularly dangerous in Node.js?**
A: Common coupling is shared mutable global state — both modules read and write the same variable:
```ts
// Common coupling — global mutable config object shared across modules
// config.ts
export const config = {
  dbUrl: "postgres://localhost/dev",
  featureFlags: { newCheckout: false }
};

// orderService.ts
import { config } from "./config";
config.featureFlags.newCheckout = true; // mutates shared global ✗

// paymentService.ts
import { config } from "./config";
if (config.featureFlags.newCheckout) { /* ... */ } // reads same object — order-dependent
```
In Node.js this is especially dangerous because the module cache means the same object instance is shared across *every* `require`/`import` in the process. In tests, a mutation in one test bleeds into the next — classic test-suite flakiness. Fix: make config immutable (`Object.freeze`), use dependency injection to pass config, or use a pure function that reads from environment variables each time.

**Q9. What does control coupling look like, and how do you eliminate it?**
A: Control coupling is passing a flag that dictates another module's *internal behaviour*:
```ts
// Control coupling — caller controls callee's internal logic via a flag
function processOrder(order: Order, sendEmail: boolean, logToAudit: boolean): void {
  // ... process ...
  if (sendEmail)   emailService.send(order);    // caller controls this branch
  if (logToAudit)  auditLog.write(order);        // caller controls this branch
}

// Callers must know the internals to set flags correctly
processOrder(order, true, false);  // what do these booleans mean? ✗
```
Fix — separate concerns; let callers compose the behaviour they need:
```ts
// Each concern is its own focused function
function processOrder(order: Order): ProcessedOrder { /* core logic only */ }
function notifyByEmail(order: ProcessedOrder): void { emailService.send(order); }
function auditOrder(order: ProcessedOrder): void    { auditLog.write(order); }

// Caller composes what it needs — explicit, readable
const processed = processOrder(order);
notifyByEmail(processed);
auditOrder(processed);
```

**Q10. What does stamp coupling look like in TypeScript, and how does it relate to ISP?**
A: Stamp coupling is passing a large data structure when only a few fields are needed — the receiver knows too much about the sender's shape:
```ts
// Stamp coupling — formatGreeting only uses name, but receives the entire User
interface User {
  id: string; name: string; email: string;
  address: Address; paymentMethods: PaymentMethod[];
  orderHistory: Order[]; preferences: UserPreferences;
}

function formatGreeting(user: User): string {
  return `Hello, ${user.name}!`; // only uses .name — knows entire User shape ✗
}

// Fix — pass only what's needed (data coupling)
function formatGreeting(name: string): string {
  return `Hello, ${name}!`;
}

// OR — narrow the type (ISP applied to data)
interface Nameable { name: string; }
function formatGreeting(entity: Nameable): string {
  return `Hello, ${entity.name}!`;
}
```
Stamp coupling and ISP violations are two faces of the same problem: a consumer knows more about a type than it needs to. TypeScript's structural typing makes the fix natural — narrow the parameter type to the minimal shape the function actually uses.

## Section 3: Types of Cohesion

**Q11. What are the main types of cohesion, ordered from lowest to highest?**
A: Constantine and Yourdon identified seven levels of cohesion. Lowest (worst) to highest (best):

| Level | Name | Description | Example |
|---|---|---|---|
| 1 (worst) | **Coincidental** | Elements grouped by accident — no meaningful relationship | `utils.ts` with unrelated helper functions |
| 2 | **Logical** | Elements grouped because they do "similar" things (all I/O, all math) but serve different purposes | `helpers.ts` with `formatDate`, `hashPassword`, `parseCsv` |
| 3 | **Temporal** | Elements grouped because they run at the same time (startup, teardown) | `init()` that connects DB, loads config, starts server |
| 4 | **Procedural** | Elements grouped because they execute in sequence to achieve a task | A function that reads a file, parses it, then logs the result |
| 5 | **Communicational** | Elements operate on the same data | Functions that all operate on the same `User` object |
| 6 | **Sequential** | Output of one element is input to the next — a pipeline | `parse → validate → transform → persist` |
| 7 (best) | **Functional** | All elements contribute to a single, well-defined task | `calculateOrderTotal(order): number` |

In practice: aim for functional or sequential cohesion. Be alert when a module feels "logical" or "temporal" — those are the most common low-cohesion patterns in real codebases.

**Q12. What does coincidental cohesion look like, and how do you refactor it?**
A: Coincidental cohesion is the `utils.ts` / `helpers.ts` anti-pattern — a file where things ended up together purely by convenience:
```ts
// utils.ts — coincidental cohesion (the junk drawer)
export function formatDate(date: Date): string { /* ... */ }
export function hashPassword(plain: string): Promise<string> { /* ... */ }
export function parseCsv(raw: string): Record<string, string>[] { /* ... */ }
export function retry<T>(fn: () => Promise<T>, times: number): Promise<T> { /* ... */ }
export function slugify(text: string): string { /* ... */ }
export function calculateTax(amount: number, rate: number): number { /* ... */ }
```
These functions share nothing except that they were small and had no other home. Refactor by grouping by *actual domain purpose*:
```
src/
  formatting/
    date.ts      → formatDate, parseDate
    text.ts      → slugify, truncate
  security/
    password.ts  → hashPassword, verifyPassword
  data/
    csv.ts       → parseCsv, writeCsv
  async/
    retry.ts     → retry, withTimeout
  finance/
    tax.ts       → calculateTax, applyDiscount
```
Each module now has functional or communicational cohesion — everything inside serves a single domain purpose.

**Q13. What does temporal cohesion look like, and why is it a warning sign?**
A: Temporal cohesion groups things that happen at the same time — typically application startup or shutdown — regardless of whether they're conceptually related:
```ts
// Temporal cohesion — startup function bundles unrelated concerns
async function initialise() {
  await connectDatabase(config.dbUrl);        // infrastructure
  loadFeatureFlags(config.flags);             // configuration
  startMetricsServer(config.metricsPort);     // observability
  scheduleBackgroundJobs(jobConfig);          // scheduling
  warmUpCache(cacheConfig);                   // caching
  registerShutdownHandlers();                 // lifecycle
}
```
None of these things are conceptually related — they're co-located only because they run at startup. Problems: testing one concern requires running all of them; changing the metrics setup risks breaking the DB connection order; the function grows without bound as the app grows.

Fix — each concern becomes an independently initialised module; `main.ts` orchestrates them explicitly:
```ts
// Each concern is independently cohesive
const db     = await DatabaseConnection.connect(config.dbUrl);
const flags  = FeatureFlags.load(config.flags);
const metrics = MetricsServer.start(config.metricsPort);
const jobs   = JobScheduler.start(jobConfig, db);
const cache  = CacheWarmer.warm(cacheConfig, db);
process.on("SIGTERM", () => Promise.all([db.close(), metrics.stop(), jobs.stop()]));
```

**Q14. What is functional cohesion, and what does it look like in a TypeScript service?**
A: Functional cohesion is the gold standard — every piece of code in the unit contributes to a single, well-named operation. The test: can you describe what this module does in one sentence without using "and"?
```ts
// Low functional cohesion — OrderService does too many things
class OrderService {
  placeOrder(dto: PlaceOrderDto) { /* ... */ }
  cancelOrder(id: string) { /* ... */ }
  generateInvoice(id: string) { /* ... */ }  // ← billing concern
  sendOrderConfirmation(id: string) { /* ... */ }  // ← notification concern
  exportOrdersToCSV(filter: OrderFilter) { /* ... */ }  // ← reporting concern
  calculateShipping(order: Order) { /* ... */ }
  applyDiscount(order: Order, code: string) { /* ... */ }
  trackDelivery(orderId: string) { /* ... */ }  // ← logistics concern
}
// Description: "manages orders AND billing AND notifications AND reporting AND logistics" ✗

// High functional cohesion — each class has one job
class OrderService        { placeOrder(); cancelOrder(); }             // order lifecycle
class InvoiceService      { generateInvoice(); emailInvoice(); }       // billing
class OrderNotifier       { sendConfirmation(); sendCancellation(); }   // notifications
class OrderReportExporter { exportToCSV(); exportToExcel(); }          // reporting
class ShippingCalculator  { calculate(); applyDiscount(); }            // shipping
class DeliveryTracker     { track(); updateStatus(); }                 // logistics
// Each: "does one thing" ✓
```

## Section 4: Coupling, Cohesion, and SOLID

**Q15. How does the Single Responsibility Principle (SRP) relate to cohesion?**
A: SRP is the object-oriented expression of high cohesion. Martin's definition — "a class should have only one reason to change" — is a cohesion test: if a class would need to change because of a billing policy change *and* a notification template change *and* a report format change, it has three reasons to change — three concerns mixed together — low cohesion. Refactoring toward SRP is refactoring toward high cohesion. The difference in language: cohesion describes the *internal quality* of the module; SRP describes the *external forces* that could change it. They measure the same property from different angles.

**Q16. How does the Dependency Inversion Principle (DIP) relate to coupling?**
A: DIP is the primary tool for reducing coupling between layers. Without DIP, the high-level business layer directly imports low-level infrastructure — tight coupling: a database schema change forces business logic changes. With DIP, both layers depend on an abstraction (interface) — the coupling is reduced to data coupling through a stable contract. The interface itself is the only shared surface: if the interface doesn't change, neither layer needs to know about the other's changes. DIP doesn't eliminate coupling — it relocates it to the most stable point in the system (the abstraction), making the coupling intentional and manageable.

**Q17. How does the Interface Segregation Principle (ISP) reduce coupling?**
A: ISP reduces stamp coupling and reduces the *surface area* of coupling. A fat interface forces a consumer to be coupled to methods it never calls — any change to those methods (signature, semantics, removal) affects the consumer even though it doesn't use them. Narrow, role-specific interfaces mean the consumer is coupled only to the methods it actually uses. The practical impact: fewer recompilations in TypeScript, fewer mock stubs in tests, and more resilience to unrelated changes in the implementing class.

**Q18. How does the Law of Demeter (LoD) relate to coupling?**
A: The Law of Demeter ("talk only to your immediate friends") is a coupling-reduction rule: a method should call methods only on its direct dependencies, not on objects *returned* by those dependencies — no chaining:
```ts
// LoD violation — chained access creates coupling to three layers deep
class OrderController {
  getShippingCity(orderId: string): string {
    return this.orderService
      .getOrder(orderId)       // returns Order
      .getCustomer()           // returns Customer — controller now knows Customer exists
      .getAddress()            // returns Address — controller now knows Address exists
      .getCity();              // returns string — controller traverses three objects
  }
}
// OrderController is coupled to Order, Customer, AND Address — stamp coupling at the object graph level

// LoD compliant — controller asks for what it needs; Order encapsulates the traversal
class Order {
  getShippingCity(): string {
    return this.customer.getAddress().getCity(); // Order knows about Customer — correct
  }
}

class OrderController {
  getShippingCity(orderId: string): string {
    return this.orderService.getOrder(orderId).getShippingCity(); // coupled only to Order ✓
  }
}
```
Each LoD violation increases the number of things a module is coupled to. The fix is to push the traversal into the object that owns the data.

**Q19. How do coupling and cohesion apply to microservices architecture?**
A: The same principles apply at the service level:
- **Cohesion at service level** — a microservice should encapsulate a single bounded context (Orders, Payments, Inventory). If a service must change whenever the pricing model changes *and* whenever the delivery algorithm changes, it has low cohesion — it owns two domains.
- **Coupling at service level** — services coupled through synchronous REST calls to each other's internals are tightly coupled: a downstream service's schema change breaks all callers. Loose coupling is achieved via:
  - **Published interfaces** (versioned API contracts) — data coupling through a stable schema.
  - **Asynchronous events** (Kafka, RabbitMQ) — message coupling; the producer doesn't know who's listening.
  - **Anti-corruption layers** — a translation boundary that insulates a service from changes in another's internal model.

The pattern: high cohesion within a service (owns its domain completely), low coupling between services (interacts only through published, versioned contracts or events).

## Section 5: Measuring and Detecting Problems

**Q20. What are the practical code smells that signal low cohesion?**
A: Recognisable symptoms in a real codebase:

- **The "and" description test** — if you describe the class as "handles X *and* Y *and* Z," it has low cohesion.
- **Utility/helper/common/shared files** — `utils.ts`, `helpers.ts`, `common.ts` are almost always coincidental or logical cohesion junk drawers.
- **God class / God service** — a class with 20+ methods, 500+ lines, dependencies on 8+ collaborators.
- **Unrelated test fixtures** — a test file that requires setting up a database, a mailer, and a payment gateway to test a discount calculation. The class under test has too many concerns.
- **Divergent change** — the class changes for multiple unrelated reasons across different sprints (SRP violation = low cohesion).
- **Shotgun surgery inverse** — when you *do* need to change one thing, you only change one file but that file has 30 unrelated functions in it (the module is the coupling point).

**Q21. What are the practical code smells that signal high coupling?**
A: Recognisable symptoms:

- **Shotgun surgery** — one logical change requires edits to 8 different files. The change is scattered because the modules are coupled.
- **Ripple effect** — changing a database column name requires changes in the repository, the service, the DTO, the controller, and the frontend type. Coupling with no abstraction barrier.
- **Impossible unit tests** — testing `OrderService` requires a real database, a real mailer, and a real payment gateway. The service is coupled to concrete infrastructure.
- **Import fan-out** — a module imports from 15 other modules. High import count is a coupling proxy metric.
- **Circular imports** — `A` imports `B` imports `A`. Two modules are so entangled they can't exist without each other — maximum coupling.
- **Temporal coupling** — two functions must be called in a specific order but nothing enforces it: `init()` must be called before `process()`, and if you forget, it silently fails.
- **Flag parameters** — `doWork(order, true, false, "admin")` — the caller controls the callee's internals through flags. Control coupling made visible.

**Q22. How do you measure coupling and cohesion quantitatively in a TypeScript project?**
A: Several proxy metrics are available:

| Metric | What it measures | Tools |
|---|---|---|
| **Afferent coupling (Ca)** | How many modules depend *on* this module — its "responsibility load" | `dependency-cruiser`, `madge` |
| **Efferent coupling (Ce)** | How many modules *this* module depends on — its "knowledge load" | `dependency-cruiser`, `madge` |
| **Instability (I = Ce / Ca+Ce)** | 0 = maximally stable (depended on, depends on nothing); 1 = maximally unstable | Derived from Ca/Ce |
| **Lines of code per file** | Proxy for cohesion — very large files often have low cohesion | ESLint `max-lines` rule |
| **Number of methods per class** | Proxy for cohesion — god classes have many unrelated methods | ESLint `max-methods` rule |
| **Cyclomatic complexity** | Proxy for coupling within a function — many branches often mean many concerns | `complexity-report`, ESLint |
| **Import count** | Proxy for efferent coupling | `eslint-plugin-import` |
| **Circular dependency count** | Direct coupling measure | `madge --circular`, `dependency-cruiser` |

No metric replaces code review judgment, but these catch systemic drift and can be enforced in CI.

## Section 6: Scenario / System Design Style Questions

**Q23. "A PR adds a `UserService` that handles registration, login, profile updates, password reset, avatar upload, email verification, session management, and admin user search. You're reviewing it. What do you say?"**
A: This is a low-cohesion god service. Walk through the diagnosis and restructuring:

Diagnosis: the service has at least five distinct reasons to change — authentication policy, profile management rules, password security requirements, file storage decisions, and admin tooling. Any of these changing requires touching `UserService`, risking unintended regressions in the others.

Proposed split by cohesion:
```ts
class AuthService        { register(); login(); logout(); refreshToken(); }   // authentication
class ProfileService     { updateProfile(); getProfile(); deleteAccount(); }  // profile management
class PasswordService    { resetPassword(); changePassword(); verifyEmail(); } // credential management
class AvatarService      { uploadAvatar(); deleteAvatar(); getAvatarUrl(); }  // file handling
class SessionService     { createSession(); invalidateSession(); listSessions(); } // session lifecycle
class UserAdminService   { searchUsers(); banUser(); impersonate(); }         // admin tooling
```
Each service now has one reason to change. `AuthService` doesn't need to know that avatar storage moved from S3 to Cloudinary. `PasswordService` doesn't need to know that admin search switched from SQL to Elasticsearch. Dependencies between them are via interfaces — not direct imports of concrete classes.

**Q24. "The team reports that every time shipping rates change, engineers must update code in `OrderService`, `CheckoutController`, `InvoiceService`, and `ReportingService`. What is the underlying problem and how do you fix it?"**
A: This is a classic **shotgun surgery** symptom — the symptom of high coupling. The shipping rate logic is scattered across four modules instead of being encapsulated in one. Each module is directly coupled to the shipping rate calculation logic (or its data), so all four break when that logic changes.

Root cause: shipping rate calculation is a *domain concept* with no single home — it has low cohesion at the system level.

Fix — extract a cohesive `ShippingCalculator` module that *owns* all shipping rate logic:
```ts
// Single source of truth — high cohesion
class ShippingCalculator {
  constructor(private rateProvider: ShippingRateProvider) {}

  calculate(order: Order, destination: Address): Money {
    const rate = this.rateProvider.getRate(order.weight, destination.zone);
    return rate.multiply(order.weight);
  }

  applyDiscount(shipping: Money, code: PromoCode): Money { /* ... */ }
}

// All four callers now depend on ShippingCalculator — low coupling through a stable interface
// Shipping rate change → update ShippingCalculator only → all callers unaffected
```
The coupling didn't disappear — `OrderService`, `CheckoutController`, `InvoiceService`, and `ReportingService` all still depend on shipping logic. But now they're coupled to *one stable abstraction* (`ShippingCalculator`), not to *scattered implementation details*. A rate change touches one file, not four.

**Q25. "A Node.js application has a `database.ts` module that exports a singleton `db` object. Every service imports and uses it directly. What are the coupling and cohesion problems, and how do you fix them?"**
A: Multiple problems layered together:

Coupling problems:
- **Common coupling** — every service shares the same global `db` singleton instance. A mutation on the connection (changing isolation level, closing the connection in a test) affects every service.
- **Content coupling risk** — services may query the DB directly rather than through a repository, knowing table schema and SQL details they shouldn't.
- **Tight coupling to the database technology** — every service imports from `database.ts` (which presumably uses a specific driver). Swapping from `pg` to Prisma means touching every service.

Cohesion problem:
- `database.ts` as a global singleton has no cohesive domain responsibility — it's a shared infrastructure object leaking into the domain layer.

Fix — three layers:
```ts
// Layer 1 — infrastructure: database connection (one place)
// database.ts stays, but is only imported by repositories

// Layer 2 — repository interfaces in domain (DIP): own the abstraction
interface OrderRepository { findById(id: string): Promise<Order | null>; save(order: Order): Promise<void>; }

// Layer 3 — concrete repositories (infrastructure): know about the db
class PrismaOrderRepository implements OrderRepository {
  constructor(private db: PrismaClient) {} // db injected — not imported globally
  async findById(id: string) { return this.db.order.findUnique({ where: { id } }); }
  async save(order: Order)   { return this.db.order.upsert({ /* ... */ }); }
}

// Services depend on the interface — not the db singleton
class OrderService {
  constructor(private repo: OrderRepository) {} // ← no db import here
}

// Composition root — the only place that imports the db singleton
const db          = new PrismaClient();
const orderRepo   = new PrismaOrderRepository(db);
const orderService = new OrderService(orderRepo);
```
Now: only `PrismaOrderRepository` knows about `db` (low coupling throughout the domain layer). Each repository has high cohesion (all its methods operate on the same domain entity). Tests inject a fake `OrderRepository` — no real DB needed.

**Q26. "You're designing a new feature: users can receive notifications via email, SMS, or push. A teammate proposes a single `NotificationService` with `sendEmail()`, `sendSMS()`, `sendPush()`, `getEmailTemplate()`, `getSMSTemplate()`, `getPushTemplate()`, `trackEmailOpen()`, `trackSMSDelivery()`, `trackPushClick()`, and `getUserPreferences()`. Evaluate this design."**
A: Evaluate along both dimensions:

**Cohesion analysis:** The service conflates at least four concerns:
- *Sending* (email, SMS, push) — transport concern
- *Templating* (email templates, SMS templates, push templates) — content concern
- *Tracking* (opens, delivery, clicks) — analytics concern
- *User preferences* — user domain concern

Description test: "manages notification sending *and* template retrieval *and* delivery tracking *and* user preference management" — four *ands*. Low cohesion.

**Coupling consequence:** Any class that imports `NotificationService` to send an email is now coupled to SMS delivery tracking, push templating, and user preference logic it never uses. A change to the tracking implementation forces recompilation of every email sender.

Proposed redesign:
```ts
// Functionally cohesive units
interface NotificationChannel  { send(recipient: Recipient, message: Message): Promise<void>; }
interface TemplateEngine       { render(templateId: string, vars: Record<string, string>): Message; }
interface DeliveryTracker      { track(event: DeliveryEvent): Promise<void>; }
interface NotificationPrefs    { getPreferences(userId: string): Promise<ChannelPreferences>; }

class EmailChannel      implements NotificationChannel { /* sendgrid */ }
class SMSChannel        implements NotificationChannel { /* twilio   */ }
class PushChannel       implements NotificationChannel { /* fcm      */ }

class HandlebarsEngine  implements TemplateEngine  { /* ... */ }
class SegmentTracker    implements DeliveryTracker { /* ... */ }
class UserPrefService   implements NotificationPrefs { /* ... */ }

// Orchestrator — composes the pieces, stays thin
class NotificationOrchestrator {
  constructor(
    private channels: Map<ChannelType, NotificationChannel>,
    private templates: TemplateEngine,
    private tracker:   DeliveryTracker,
    private prefs:     NotificationPrefs
  ) {}

  async notify(userId: string, templateId: string): Promise<void> {
    const userPrefs = await this.prefs.getPreferences(userId);
    const message   = this.templates.render(templateId, { userId });
    const channel   = this.channels.get(userPrefs.preferredChannel)!;
    await channel.send({ userId }, message);
    await this.tracker.track({ userId, channel: userPrefs.preferredChannel });
  }
}
```
Each interface is cohesive (one job). Adding a WhatsApp channel is a new `WhatsAppChannel` class — nothing else changes. Tracking implementation can be swapped (Segment → Mixpanel) without touching any channel or template code.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Coupling | Cohesion |
|---|---|---|
| **Definition** | Degree of dependency *between* modules | Degree of focus *within* a module |
| **Scope** | External — a relationship quality | Internal — a module quality |
| **Goal** | Minimise (loose coupling) | Maximise (high cohesion) |
| **Worst form** | Content coupling (access internals) | Coincidental cohesion (junk drawer) |
| **Best form** | Message coupling (events only) | Functional cohesion (single job) |
| **Primary symptom** | Shotgun surgery, ripple effects, impossible unit tests | God class, "and" description, divergent change |
| **SOLID lever** | DIP (depend on abstractions), ISP (narrow interfaces) | SRP (one reason to change) |
| **Architectural lever** | Hexagonal Architecture, event-driven design | Bounded contexts, microservice boundaries |
| **Testing signal** | Test requires many real collaborators | Test requires complex unrelated setup |
| **Measurement proxy** | Afferent/efferent coupling, circular dep count | Lines per file, methods per class, import count |

## Coupling Types Quick Reference

| Type | Signal phrase | Fix |
|---|---|---|
| **Content** | `(obj as any)._private`, prototype patching | Expose a proper API; use injectable seams |
| **Common** | Shared global/singleton mutation | Freeze config; use DI to pass state |
| **Control** | Boolean flags, mode strings as parameters | Split into separate functions per concern |
| **Stamp** | Passing whole object when only one field needed | Pass only needed fields; narrow the type |
| **Data** | Passing only needed data via parameters | ✅ Target state |
| **Message** | Event bus, pub/sub, no direct method calls | ✅ Ideal for cross-bounded-context communication |

---

## Cohesion Types Quick Reference

| Type | Signal phrase | Fix |
|---|---|---|
| **Coincidental** | `utils.ts`, `helpers.ts`, "miscellaneous" | Group by domain purpose; split into focused modules |
| **Logical** | "all formatters", "all validators" (different purposes) | Separate by what they operate on, not what kind they are |
| **Temporal** | "everything that runs at startup" | Extract each concern; orchestrate explicitly in `main.ts` |
| **Procedural** | Sequential steps with no shared data | Often fine; watch for unrelated steps creeping in |
| **Communicational** | All operate on the same data structure | ✅ Good — encapsulate the data with its operations |
| **Sequential** | Output of one feeds input of next | ✅ Good — pipeline / chain of responsibility |
| **Functional** | Single, well-named operation — no "and" | ✅ Target state |

**Tip for the interview:** At the 5 YOE level, "what is coupling and cohesion" will never be asked in isolation — it surfaces as: why does changing one thing break five files (high coupling), why is this service impossible to test (low cohesion or high coupling to infrastructure), how would you split this 2,000-line service (low cohesion — apply SRP), or how do you design the notification system (both — high cohesion per channel, low coupling between orchestrator and transport). The sharp answer diagnoses the *type* of coupling or the *level* of cohesion ("this is control coupling — the flag parameter is controlling internal branching"), proposes the specific fix ("extract the branching into two separate functions and let the caller compose them"), and names the SOLID principle or pattern that formalises it ("this is ISP applied to data — pass only the fields the function needs"). Naming the specific type, not just the general concept, is what separates a 5 YOE answer from a junior one.
