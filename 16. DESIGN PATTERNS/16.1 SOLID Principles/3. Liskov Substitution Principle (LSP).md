# Design Patterns (SOLID Principles): Liskov Substitution Principle (LSP) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Liskov Substitution Principle?**
A: LSP, introduced by Barbara Liskov in 1987, states that if `S` is a subtype of `T`, then objects of type `T` in a program may be replaced with objects of type `S` without altering the correctness of that program. In practical terms: a subclass must be usable wherever its parent class is expected, without surprising the caller. The caller should not need to know or care whether it's dealing with the base type or a derived type.

**Q2. How does LSP relate to the other SOLID principles?**
A: LSP is the behavioural contract enforcer of SOLID:
- **SRP** defines what a class does.
- **OCP** says classes should be open to extension (typically via subclassing or composition) — LSP ensures that extension through subclassing is *safe*.
- **ISP** ensures interfaces are lean; LSP ensures implementations honour those lean contracts.
- **DIP** makes high-level code depend on abstractions; LSP ensures substituting the concrete implementation of that abstraction doesn't break the high-level code.

Without LSP, OCP-based extension via inheritance becomes a liability — you can extend freely but callers silently break.

**Q3. What does "behavioural subtyping" mean, and why is it stronger than type-system subtyping?**
A: Type-system subtyping (what TypeScript, Java, etc. enforce) guarantees *structural* compatibility — the subclass has at least all the methods and properties of the parent, with compatible signatures. Behavioural subtyping (what LSP demands) is stricter: the subclass must also uphold the *semantics* of the parent — its invariants, pre/postconditions, and side-effect expectations. A class can satisfy a TypeScript `extends` or `implements` check and still violate LSP if it overrides a method in a way that changes observable behaviour.

**Q4. What are the three formal conditions LSP imposes on a subtype?**
A: Based on Liskov and Wing's formal definition:
1. **Precondition rule** — a subtype method may not strengthen preconditions (must accept at least as broad a range of inputs as the parent).
2. **Postcondition rule** — a subtype method may not weaken postconditions (must guarantee at least as strong a result as the parent).
3. **Invariant rule** — class invariants maintained by the parent must be maintained by the subtype.

Additionally: the **history constraint** — subtypes should not introduce mutations that the parent's type made impossible (e.g., a mutable subtype of an immutable parent).

**Q5. Give the canonical "Rectangle–Square" example of an LSP violation and explain what goes wrong.**
A: The classic example:

```typescript
class Rectangle {
  constructor(protected width: number, protected height: number) {}

  setWidth(w: number)  { this.width = w; }
  setHeight(h: number) { this.height = h; }
  area(): number       { return this.width * this.height; }
}

class Square extends Rectangle {
  // A square must keep width === height
  setWidth(w: number)  { this.width = w; this.height = w; }  // also sets height
  setHeight(h: number) { this.height = h; this.width = h; }  // also sets width
}

function stretchWidth(r: Rectangle): void {
  r.setWidth(10);
  r.setHeight(5);
  // Caller expects area = 10 * 5 = 50
  console.log(r.area()); // Rectangle → 50 ✅  |  Square → 25 ❌
}

const sq = new Square(4, 4);
stretchWidth(sq); // Postcondition violated — area is 25, not 50
```

`Square` violates LSP because `setWidth` and `setHeight` are no longer independent, breaking the Rectangle postcondition that `width` and `height` can be set independently. The caller's assumption is silently invalidated.

## Section 2: Identifying LSP Violations

**Q6. What are the common code smells that indicate an LSP violation?**
A: Key signals:
- **`instanceof` or type-checking in caller code** — `if (shape instanceof Square) { ... }` means the caller cannot treat the types uniformly.
- **Overridden methods that throw `UnsupportedOperationException` / `Error`** — the subtype can't honour the parent's contract for a method, so it just explodes.
- **Overridden methods that do nothing (no-op)** — the subtype "fulfils" the signature but provides no actual behaviour.
- **Weakened postconditions** — the parent guarantees a non-null return; the child can return `null`.
- **Strengthened preconditions** — the parent accepts any number; the child throws if the number is negative.
- **Broken invariants** — the parent guarantees a sorted collection; the child allows unsorted insertions.

**Q7. How does throwing `NotImplementedError` (or equivalent) in a subclass method violate LSP?**
A: A caller relying on the base class contract expects every method to execute without throwing a contract-violation error. If a subclass throws `NotImplementedError` for a method defined on the parent, any code passing that subclass where the parent is expected will crash at runtime. The subtype is no longer substitutable — it's a structurally compatible but behaviourally incompatible type. This pattern usually signals that inheritance is the wrong tool; composition or a narrower interface is the correct fix.

```typescript
class PaymentProcessor {
  refund(transactionId: string): Promise<void> {
    // ... default refund logic
  }
}

class CryptoPaymentProcessor extends PaymentProcessor {
  refund(_transactionId: string): Promise<void> {
    throw new Error("Crypto payments are non-refundable"); // LSP violation ❌
  }
}

// Caller is now broken:
async function processRefund(processor: PaymentProcessor, txId: string) {
  await processor.refund(txId); // crashes at runtime for CryptoPaymentProcessor
}
```

**Q8. How does strengthening a precondition in a subclass violate LSP?**
A: The parent's contract declares what inputs are valid. Callers are coded to that contract — they won't guard against conditions the parent never required. If the subclass adds restrictions:

```typescript
class Validator {
  validate(amount: number): boolean {
    return amount >= 0; // Parent accepts any non-negative number
  }
}

class StrictValidator extends Validator {
  validate(amount: number): boolean {
    if (amount > 1_000_000) throw new RangeError("Amount too large"); // Strengthened precondition ❌
    return amount >= 0;
  }
}
```

Code written against `Validator` will never guard for the `> 1_000_000` case — it was never required. When `StrictValidator` is substituted, calls with large amounts throw unexpectedly.

**Q9. Can LSP be violated without changing a method signature at all?**
A: Yes — and this is what makes LSP subtler than type-system checks. The violation is purely behavioural. Examples:
- A `save()` method that the parent guarantees persists to a database is overridden in a subclass to log to stdout instead (different side effect).
- A `getItems()` that the parent guarantees returns items in insertion order is overridden to return them sorted.
- A subclass overrides `calculateFee()` to return a negative value when the parent's contract guarantees a non-negative result.

None of these change the TypeScript signature, so the compiler won't catch them. Only runtime behaviour and well-written contract tests reveal them.

## Section 3: Fixing LSP Violations

**Q10. How do you fix an LSP violation — what are the standard remedies?**
A: Four main approaches:

1. **Flatten / remove the inheritance** — if `Square` can't be substituted for `Rectangle`, they should not share an inheritance hierarchy. Use a common interface or abstract type that captures only what they truly share (`Shape` with `area()`).
2. **Favour composition over inheritance** — instead of `Square extends Rectangle`, `Square` holds an internal geometry object and exposes only what it actually supports.
3. **Split the interface (ISP)** — extract a narrower interface that the subtype *can* honour; callers that need the full contract use the fuller interface, callers that don't use the narrower one.
4. **Make the parent abstract / push responsibilities down** — define behaviour in concrete subtypes rather than providing a default in the parent that some subtypes must override to no-op.

**Q11. Show how to refactor the Rectangle–Square example to honour LSP.**
A: The correct fix is to stop modelling Square as a subtype of Rectangle and instead use a shared abstraction:

```typescript
interface Shape {
  area(): number;
  perimeter(): number;
}

class Rectangle implements Shape {
  constructor(private width: number, private height: number) {}
  area(): number      { return this.width * this.height; }
  perimeter(): number { return 2 * (this.width + this.height); }
}

class Square implements Shape {
  constructor(private side: number) {}
  area(): number      { return this.side * this.side; }
  perimeter(): number { return 4 * this.side; }
}

// Caller works with Shape — LSP honoured for the Shape contract ✅
function printShapeInfo(shape: Shape): void {
  console.log(`Area: ${shape.area()}, Perimeter: ${shape.perimeter()}`);
}
```

Neither class has mutable setters, so there's no postcondition to violate. Each correctly substitutes for `Shape`.

**Q12. How does the Interface Segregation Principle help you avoid LSP violations proactively?**
A: LSP violations often arise when an interface (or base class) is too broad — it defines methods that some implementors simply cannot or should not honour. ISP says: split that interface into smaller, focused ones. When each interface captures exactly the capability a group of implementors can genuinely provide, there's no temptation to throw `NotImplementedError` or no-op an inherited method. Every implementor only signs up for contracts it can keep.

```typescript
// Too broad — forces LSP violation on read-only stores ❌
interface PaymentStore {
  read(id: string): Payment;
  write(payment: Payment): void;
  delete(id: string): void;
}

// ISP-split — each subtype honours its own contract ✅
interface ReadableStore  { read(id: string): Payment; }
interface WritableStore  { write(payment: Payment): void; }
interface DeletableStore { delete(id: string): void; }

class ArchiveStore implements ReadableStore { /* only reads — no fake write/delete */ }
class LiveStore implements ReadableStore, WritableStore, DeletableStore { /* full contract */ }
```

## Section 4: LSP in TypeScript & Node.js Fintech Context

**Q13. How does TypeScript's structural typing interact with LSP?**
A: TypeScript uses structural (duck) typing — if an object has the required shape, it's assignable to that type. This makes LSP violations *easier* to introduce because TypeScript only checks structure, not semantics. A class can satisfy `implements PaymentGateway` and still violate LSP behaviourally (e.g., its `charge()` method returns amounts in a different currency without saying so). TypeScript is a necessary but not sufficient condition for LSP compliance. Behavioural contracts must be enforced through tests and documentation, not just type signatures.

**Q14. Show a real-world LSP violation in a payment gateway abstraction common in Indian fintech.**
A: A common pattern in payment integrations (Razorpay, PayU, Cashfree):

```typescript
abstract class PaymentGateway {
  // Contract: resolves with a transaction ID string; never rejects for business-rule failures
  // (only for network errors). Returns null if payment was declined.
  abstract charge(orderId: string, amountInPaise: number): Promise<string | null>;

  abstract refund(transactionId: string, amountInPaise: number): Promise<void>;
}

// ❌ LSP Violation — RazorpayGateway throws on decline instead of returning null
class RazorpayGateway extends PaymentGateway {
  async charge(orderId: string, amountInPaise: number): Promise<string | null> {
    const res = await razorpayClient.orders.create({ amount: amountInPaise });
    if (res.status === "declined") throw new Error("Payment declined"); // ❌ Parent returns null
    return res.id;
  }

  async refund(transactionId: string, amountInPaise: number): Promise<void> {
    await razorpayClient.payments.refund(transactionId, { amount: amountInPaise });
  }
}

// ❌ LSP Violation — CashfreeGateway throws NotImplemented for refund
class CashfreeGateway extends PaymentGateway {
  async charge(orderId: string, amountInPaise: number): Promise<string | null> {
    const res = await cashfreeClient.createOrder({ orderId, orderAmount: amountInPaise / 100 });
    return res.cfOrderId ?? null;
  }

  async refund(_transactionId: string, _amountInPaise: number): Promise<void> {
    throw new Error("Refunds not supported via Cashfree SDK — use dashboard"); // ❌ NotImplemented
  }
}
```

```typescript
// ✅ LSP-compliant fix: narrower interfaces so each gateway only contracts what it can deliver

interface ChargingGateway {
  charge(orderId: string, amountInPaise: number): Promise<string | null>;
}

interface RefundableGateway extends ChargingGateway {
  refund(transactionId: string, amountInPaise: number): Promise<void>;
}

class RazorpayGateway implements RefundableGateway {
  async charge(orderId: string, amountInPaise: number): Promise<string | null> {
    try {
      const res = await razorpayClient.orders.create({ amount: amountInPaise });
      return res.id;
    } catch (err: any) {
      if (err.statusCode === 402) return null; // declined → null, honouring contract ✅
      throw err;
    }
  }

  async refund(transactionId: string, amountInPaise: number): Promise<void> {
    await razorpayClient.payments.refund(transactionId, { amount: amountInPaise });
  }
}

class CashfreeGateway implements ChargingGateway { // Only signs up for charge ✅
  async charge(orderId: string, amountInPaise: number): Promise<string | null> {
    const res = await cashfreeClient.createOrder({ orderId, orderAmount: amountInPaise / 100 });
    return res.cfOrderId ?? null;
  }
}
```

**Q15. How does LSP apply to repository patterns in a Node.js/PostgreSQL backend?**
A: Repository abstractions are a classic LSP surface — a `UserRepository` interface is consumed by services, and concrete implementations (Postgres, Redis cache, in-memory mock for tests) must all honour the same contract:

```typescript
interface UserRepository {
  findById(userId: string): Promise<User | null>;
  // Contract: never throws for "not found" — returns null
  // Contract: always returns a fully-hydrated User (all fields populated)
  save(user: User): Promise<void>;
  // Contract: durable write — after this resolves, data survives a process restart
}

// ✅ PostgresUserRepository — honours both contracts
class PostgresUserRepository implements UserRepository {
  async findById(userId: string): Promise<User | null> {
    const row = await db.query("SELECT * FROM users WHERE id = $1", [userId]);
    return row.rows[0] ? mapRowToUser(row.rows[0]) : null;
  }

  async save(user: User): Promise<void> {
    await db.query(
      "INSERT INTO users (id, name, email) VALUES ($1, $2, $3) ON CONFLICT (id) DO UPDATE SET name=$2, email=$3",
      [user.id, user.name, user.email]
    );
  }
}

// ❌ LSP Violation — InMemoryUserRepository weakens the durability postcondition
class InMemoryUserRepository implements UserRepository {
  private store = new Map<string, User>();

  async findById(userId: string): Promise<User | null> {
    return this.store.get(userId) ?? null;
  }

  async save(user: User): Promise<void> {
    this.store.set(user.id, user); // Not durable — violates postcondition for production use ❌
  }
}
```

In practice, the in-memory implementation is *intentionally* non-durable for tests — the solution is to make the durability expectation explicit in the interface documentation, and ensure the in-memory repo is only used in test/mock contexts where that weakened postcondition is acceptable by contract.

**Q16. How does LSP apply to NestJS injectable services when swapping implementations via DI?**
A: NestJS's dependency injection is the exact mechanism that makes LSP observable at runtime — you register a provider by token (usually an abstract class or interface symbol), and any concrete class can be substituted. If a substituted class violates LSP, the module that depends on the token breaks at runtime in subtle ways:

```typescript
// Abstract base — defines the contract
abstract class NotificationService {
  // Contract: resolves after notification is dispatched; never rejects for "user not found"
  abstract send(userId: string, message: string): Promise<void>;
}

// ✅ EmailNotificationService — honours contract
@Injectable()
class EmailNotificationService extends NotificationService {
  async send(userId: string, message: string): Promise<void> {
    const user = await this.userRepo.findById(userId);
    if (!user) return; // gracefully handles missing user ✅
    await this.mailer.sendMail({ to: user.email, text: message });
  }
}

// ❌ SmsNotificationService — violates contract by throwing on missing user
@Injectable()
class SmsNotificationService extends NotificationService {
  async send(userId: string, message: string): Promise<void> {
    const user = await this.userRepo.findById(userId);
    if (!user) throw new NotFoundException(`User ${userId} not found`); // ❌ Strengthened precondition
    await this.smsProvider.send(user.phone, message);
  }
}

// Module can swap implementations — LSP violation in SMS breaks all callers
@Module({
  providers: [{ provide: NotificationService, useClass: SmsNotificationService }],
})
export class NotificationModule {}
```

## Section 5: Testing for LSP

**Q17. What is the "substitutability test," and how do you apply it during code review?**
A: The substitutability test asks: *"Can I replace every usage of the base type with this subtype and have all existing tests pass?"* Operationally:
1. Write a shared test suite (sometimes called a "contract test") against the base type's interface.
2. Run that same test suite against every concrete subtype.
3. If any test fails for a subtype, you have an LSP violation.

This is the strongest form of LSP verification because it catches behavioural divergence that type checks miss. Libraries like Jest make it easy to parameterize the same `describe` block over multiple concrete implementations.

**Q18. Write a contract test suite that verifies LSP across multiple payment gateway implementations.**
A: 

```typescript
// contract-tests/payment-gateway.contract.ts
import { PaymentGateway } from "../interfaces/payment-gateway";

export function runPaymentGatewayContractTests(
  label: string,
  factory: () => PaymentGateway
): void {
  describe(`PaymentGateway contract — ${label}`, () => {
    let gateway: PaymentGateway;

    beforeEach(() => { gateway = factory(); });

    it("should return a string transaction ID on successful charge", async () => {
      const txId = await gateway.charge("order_123", 50000); // ₹500 in paise
      expect(typeof txId).toBe("string");
      expect(txId!.length).toBeGreaterThan(0);
    });

    it("should return null (not throw) when payment is declined", async () => {
      // Use a magic "declined" order ID recognised by test doubles
      const txId = await gateway.charge("order_decline_test", 50000);
      expect(txId).toBeNull(); // Must not throw — contract says null on decline
    });

    it("should resolve refund without throwing for a valid transaction", async () => {
      const txId = await gateway.charge("order_refund_test", 10000);
      await expect(gateway.refund(txId!, 10000)).resolves.toBeUndefined();
    });
  });
}

// Usage in concrete test files:
// razorpay-gateway.test.ts
import { runPaymentGatewayContractTests } from "./payment-gateway.contract";
import { RazorpayGateway } from "../gateways/razorpay-gateway";

runPaymentGatewayContractTests("RazorpayGateway", () => new RazorpayGateway(mockRazorpayClient));
```

Any implementation that fails these shared tests is an LSP violator.

**Q19. How do you use TypeScript's `satisfies` operator or `implements` to catch some LSP-adjacent issues at compile time?**
A: TypeScript's `implements` ensures structural compatibility — methods exist with compatible signatures. The `satisfies` operator (TS 4.9+) lets you verify a value matches a type without widening it. Neither catches behavioural LSP violations, but both help enforce the structural baseline:

```typescript
interface KYCProvider {
  verify(panNumber: string): Promise<KYCResult>;
  // Contract: panNumber is exactly 10 chars, uppercase
}

class MockKYCProvider implements KYCProvider { // TS enforces the method exists ✅
  async verify(panNumber: string): Promise<KYCResult> {
    if (panNumber.length !== 10) throw new Error("Invalid PAN"); // Strengthened precondition ❌ — TS won't catch this
    return { verified: true, name: "Test User" };
  }
}

// satisfies: useful for object literals checked against an interface
const testProviders = {
  mock: new MockKYCProvider(),
  sandbox: new SandboxKYCProvider(),
} satisfies Record<string, KYCProvider>; // Ensures structural fit for all entries
```

## Section 6: Scenario / System Design Style Questions

**Q20. "You're onboarding a new payment gateway (Juspay) alongside existing Razorpay and PayU integrations. How do you ensure LSP is maintained?"**
A: Structured approach:
1. **Define (or audit) the gateway interface contract** — document not just signatures but behavioural guarantees: what `charge()` returns on decline vs. network error, what `refund()` guarantees about idempotency, whether `getStatus()` is eventually consistent or strongly consistent.
2. **Run the existing contract test suite against the Juspay adapter** before it ships. Any failing test reveals an LSP violation before production traffic hits it.
3. **Identify contract gaps in the Juspay API** (e.g., Juspay might use a different decline code structure). Fix at the adapter layer — wrap Juspay's response into the common contract shape rather than leaking Juspay-specific behaviour up to callers.
4. **Use narrower interfaces** if Juspay genuinely can't fulfil part of the contract (e.g., no webhook-based refund status). Callers that need refund status should depend on a `RefundTrackingGateway` interface, not the base `PaymentGateway`.

**Q21. "A senior engineer on your team argues that `Square extends Rectangle` is fine because your codebase never calls `setWidth`/`setHeight` together. How do you respond?"**
A: This is a fragile contract argument — correctness shouldn't depend on callers' current usage patterns. Counter-points:
- The base class contract implicitly allows independent mutation of `width` and `height`. Future callers — new features, a new engineer, a test — may reasonably use that contract without knowing about `Square`. The violation is latent, not absent.
- LSP violations tend to surface at the worst possible moment: when the codebase evolves and a new caller exercises the contract path that was "never used before."
- The fix costs very little: a shared `Shape` interface with `area()` / `perimeter()`, and two independent concrete classes. No inheritance required, no ongoing cognitive burden.
- The `isinstance` check or `if (shape instanceof Square)` workaround that inevitably follows the original design is a permanent maintenance tax, not a one-time fix.

**Q22. "In a high-throughput UPI transaction processing system, you have a `TransactionLogger` base class. A new subclass `AsyncTransactionLogger` buffers writes and flushes every 5 seconds. Does this violate LSP?"**
A: It depends on what the base class contract guarantees:
- If `TransactionLogger.log()` contract says *"entry is durable immediately after this call returns"*, then `AsyncTransactionLogger` violates LSP — the postcondition of durability is weakened.
- If the contract says *"entry will be persisted eventually"*, there's no violation — the buffered behaviour is within contract.

For UPI systems under RBI's audit-trail requirements, immediate durability is usually a regulatory constraint, not just a code design preference. `AsyncTransactionLogger` must either: (a) not substitute for the synchronous logger (use a distinct type), or (b) make `log()` await the flush, defeating the buffering purpose. The right design is to make `AsyncTransactionLogger` a distinct type and inject it only in contexts (e.g., metrics, debug logs) where eventual consistency is explicitly acceptable.

**Q23. "A junior dev on your team is building an NACH mandate processing system. They create `NachMandate extends BaseMandate` but `NachMandate.cancel()` throws `"NACH mandates require 30-day notice via NPCI portal"`. How do you guide them?"**
A: This is a textbook LSP violation via `NotImplementedError`-equivalent. Guidance:
1. **Explain the violation** — any service that calls `.cancel()` on a `BaseMandate` will crash at runtime when it encounters an `NachMandate`. NACH-specific behaviour should not be a runtime surprise to the caller.
2. **Ask what `cancel()` actually means on the base type** — if cancellation is a first-class operation that all mandate types must support, then NACH's 30-day-notice process should still be representable as a resolution (e.g., the method schedules a deferred cancellation and resolves with a `CancellationScheduled` status rather than throwing).
3. **If cancellation is truly unsupported**, the fix is ISP: extract a `CancellableMandateType` interface that only `DirectDebitMandate` implements, and `NachMandate` does not. Callers that need cancellation accept `CancellableMandateType`, not `BaseMandate`.
4. **Regulatory context**: under NPCI guidelines, NACH mandate cancellation does have a defined flow (form submission, 30-day notice). The domain behaviour is real — it should be modelled as a state/status, not as a thrown exception.

**Q24. "How would you explain an LSP violation to a non-technical stakeholder (e.g., a fintech product manager) without using OOP jargon?"**
A: Try an analogy:

> "Imagine we have a standardised payment terminal in all our merchant stores. It accepts any card — debit, credit, prepaid. Now imagine we roll out a new 'premium' terminal that randomly refuses prepaid cards without any error message — it just freezes. Every store procedure, every cashier training, was written assuming the terminal handles all cards. The new terminal looks identical and fits the same socket, but it silently breaks the rules. That's what an LSP violation is in code — a new component that looks like it follows the rules but breaks assumptions downstream, causing failures that are hard to trace because nothing looks wrong on the surface."

**Q25. "You're designing a loan origination system that supports personal loans, home loans, and BNPL. What LSP considerations guide your `LoanProduct` abstraction?"**
A: Key design decisions informed by LSP:

```typescript
interface LoanProduct {
  // Contract: returns EMI amount in paise; never negative; throws only for invalid inputs
  calculateEMI(principal: number, tenureMonths: number): number;

  // Contract: resolves with updated loan; never rejects for business-rule reasons (returns Result type)
  disburse(loanId: string): Promise<DisburseResult>;

  // Contract: returns regulatory filing requirements per RBI guidelines
  getComplianceRequirements(): ComplianceRequirement[];
}
```

Considerations:
- **BNPL products** may not have an EMI in the traditional amortisation sense — if `calculateEMI()` is meaningless for BNPL, either the interface is too broad (use ISP to extract an `EMICapableLoan` sub-interface) or BNPL must return a meaningful equivalent (e.g., single-instalment "EMI").
- **Home loans** require CERSAI registration — `getComplianceRequirements()` must return that requirement; the base contract guarantees this call works, so all subtypes must return an array (empty if none, never throw).
- **Disbursal** for home loans triggers a NACH mandate setup; for BNPL it might be instant wallet credit. Both resolve with a `DisburseResult` — the caller doesn't need to know the mechanism. This is LSP-safe.
- **Avoid throwing inside `disburse()`** for expected business failures (e.g., CIBIL score too low) — return a `DisburseResult` with a failure status. Throwing breaks the postcondition that callers are coded against.

## Quick Reference Table

| LSP Concept                       | Violation Example                                           | Fix                                                      |
|-----------------------------------|-------------------------------------------------------------|----------------------------------------------------------|
| Strengthened precondition         | Subclass `validate()` throws for inputs parent allowed      | Remove extra guard; or use a narrower interface          |
| Weakened postcondition            | Subclass `charge()` throws on decline; parent returns null  | Catch and map to null at adapter boundary                |
| Broken invariant                  | Immutable parent; mutable subclass adds a setter            | Do not inherit; use composition or separate types        |
| `NotImplementedError` override    | `CashfreeGateway.refund()` throws always                    | Extract `RefundableGateway` interface; don't implement   |
| No-op override                    | `log()` override silently does nothing                      | Remove from base; use optional capability interface      |
| `instanceof` check in caller      | `if (mandate instanceof NachMandate)` in service            | Make all subtypes honour contract; remove type check     |
| Behavioural change, same sig      | Subclass `getItems()` changes sort order                    | Document contract explicitly; write contract tests       |
| Module-singleton LSP              | Repository mock weakens durability guarantee for production | Scope mock strictly to test DI context; document limits  |

**Tip for the Interview:** At the 5 YOE level, interviewers won't ask "what is LSP?" — they'll hand you a class hierarchy with a subtle bug and ask why the service occasionally returns wrong data, or they'll ask you to design a payment abstraction that works across three gateways. LSP violations show up as runtime surprises in those scenarios. The answers that land are ones that: (a) spot the violation by looking at whether a caller would need to type-check or catch unexpected exceptions, (b) fix it with ISP-split interfaces rather than adding more `if` branches, and (c) reach for contract tests as the enforcement mechanism. In fintech specifically, connect LSP to reliability — an LSP violation in a payment gateway adapter is not a design smell, it's a production incident waiting to happen.
