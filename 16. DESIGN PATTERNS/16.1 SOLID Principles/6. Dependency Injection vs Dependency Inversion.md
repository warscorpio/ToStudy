# JavaScript / TypeScript (Design Patterns — SOLID Principles): Dependency Injection vs Dependency Inversion — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals — Clearing Up the Confusion

**Q1. What is the single most important distinction between Dependency Injection and Dependency Inversion?**
A: One is a *technique*; the other is a *principle*:
- **Dependency Injection (DI)** — a *technique* for supplying an object's collaborators from the outside rather than having it construct them internally. It answers the question: *how does an object get its dependencies?*
- **Dependency Inversion Principle (DIP)** — a *design principle* (the D in SOLID) about which direction the source-code dependency arrow should point. It answers the question: *what should the dependency be — a concrete class or an abstraction?*

They are frequently confused because DI is the most common *mechanism* used to satisfy DIP. But they are independent: you can use DI without DIP (inject a concrete class), and you can satisfy DIP without DI (via a service locator, though that's discouraged). Understanding both independently — and then understanding how they compose — is what separates a senior engineer's answer from a junior one.

**Q2. Give a one-sentence definition of each.**
A:
- **Dependency Injection:** *"Don't create your dependencies — receive them."*
- **Dependency Inversion Principle:** *"Don't depend on concrete implementations — depend on abstractions, and make the concrete implementations depend on those abstractions too."*

**Q3. Can you have DI without DIP? Show a code example.**
A: Yes. DI is just the *delivery mechanism* — what gets delivered can still be a concrete class:
```ts
// DI without DIP — dependency is injected, but it's a concrete class, not an abstraction
class MySQLOrderRepository {
  save(order: Order): Promise<void> { /* MySQL logic */ }
}

class OrderService {
  constructor(private repo: MySQLOrderRepository) {} // injected ✓ — but concrete ✗
  async placeOrder(dto: PlaceOrderDto) {
    const order = Order.create(dto);
    await this.repo.save(order);
  }
}

// Composition root
const svc = new OrderService(new MySQLOrderRepository()); // DI: supplied externally
```
`OrderService` no longer constructs `MySQLOrderRepository` itself — that's DI. But it still depends on the *concrete* `MySQLOrderRepository` class — that violates DIP. Swapping to `PostgresOrderRepository` still requires changing `OrderService`'s constructor type.

**Q4. Can you have DIP without DI? Show a code example.**
A: Yes, though it's uncommon and usually inferior. A Service Locator satisfies DIP (depends on an abstraction) but doesn't use DI:
```ts
interface OrderRepository { save(order: Order): Promise<void>; }

// DIP without DI — depends on abstraction (✓ DIP), but pulls it from a global registry (✗ DI)
class OrderService {
  private repo: OrderRepository;

  constructor() {
    // Pulling the dependency — not receiving it
    this.repo = ServiceLocator.resolve<OrderRepository>("OrderRepository");
  }

  async placeOrder(dto: PlaceOrderDto) {
    const order = Order.create(dto);
    await this.repo.save(order);
  }
}
```
DIP is satisfied — `OrderService` depends on `OrderRepository` (the abstraction), not `MySQLOrderRepository` (the concrete). But DI is not used — `OrderService` reaches into a global locator instead of receiving its dependency. The dependency is still hidden, making the class harder to test and its contract opaque. This is why DI (especially constructor injection) is the preferred mechanism to *deliver* DIP.

**Q5. What does it look like when both DI and DIP are applied together correctly?**
A: This is the target state — DI as the *mechanism*, DIP as the *principle* it enforces:
```ts
// Abstraction — owned by the domain layer (DIP: high-level owns the contract)
interface OrderRepository {
  save(order: Order): Promise<void>;
  findById(id: string): Promise<Order | null>;
}

// High-level module depends only on the abstraction (DIP ✓)
class OrderService {
  constructor(private repo: OrderRepository) {} // injected from outside (DI ✓)

  async placeOrder(dto: PlaceOrderDto): Promise<Order> {
    const order = Order.create(dto);
    await this.repo.save(order);
    return order;
  }
}

// Low-level detail implements the abstraction (DIP ✓)
class MySQLOrderRepository implements OrderRepository {
  async save(order: Order)              { /* MySQL */ }
  async findById(id: string)            { /* MySQL */ }
}

// Composition root — the only place that knows about concretions
const svc = new OrderService(new MySQLOrderRepository()); // DI ✓
```
DI answers *how*: the repo is passed in through the constructor. DIP answers *what*: the repo is an `OrderRepository` interface, not `MySQLOrderRepository`. Together they make `OrderService` testable, swappable, and decoupled from infrastructure.

## Section 2: Dependency Injection In Depth

**Q6. What are the three forms of Dependency Injection? When do you use each?**
A:

| Form | Syntax | When to use |
|---|---|---|
| **Constructor injection** | `constructor(private dep: Dep)` | Default choice — dependencies required for the object to function; makes deps explicit and enforces completeness at construction time |
| **Setter injection** | `setDep(dep: Dep): void` | Truly optional dependencies that have a sensible default; object is valid without them |
| **Method/parameter injection** | `doWork(dep: Dep): void` | One-off dependency needed only for a single operation; common in functional-style code |

Constructor injection is overwhelmingly preferred in TypeScript/JavaScript because it makes the dependency contract visible at a glance, integrates cleanly with IoC containers, and prevents partial-state bugs (no object exists with a missing required dep).

**Q7. What is constructor over-injection, and what does it signal?**
A: Constructor over-injection is when a class's constructor accepts so many injected dependencies (typically 5+) that it becomes unwieldy:
```ts
class OrderService {
  constructor(
    private orderRepo:      OrderRepository,
    private userRepo:       UserRepository,
    private inventoryRepo:  InventoryRepository,
    private paymentGateway: PaymentGateway,
    private emailService:   EmailService,
    private smsService:     SMSService,
    private auditLogger:    AuditLogger,
    private eventBus:       EventBus,
  ) {}
}
```
This is a design smell — the class is violating the Single Responsibility Principle. It has too many concerns. The fix is not to reduce injections (which would violate DIP) but to split the class into smaller, focused services, each with fewer dependencies. Constructor over-injection is a *diagnostic tool*: it reveals that the class needs to be decomposed.

**Q8. What is the difference between DI done manually ("poor man's DI") and using an IoC container?**
A:
- **Manual DI ("poor man's DI")** — you wire dependencies yourself at the composition root using plain `new` calls. Simple, zero-framework, transparent.
- **IoC container** — a framework (InversifyJS, TSyringe, NestJS DI) that reads metadata (decorators, tokens) and automatically instantiates and injects dependencies.

```ts
// Manual DI — composition root
const emailService    = new SendGridEmailService(apiKey);
const orderRepo       = new MySQLOrderRepository(dbConnection);
const orderService    = new OrderService(orderRepo, emailService);
const orderController = new OrderController(orderService);

// IoC container — composition root
container.bind<EmailService>("EmailService").to(SendGridEmailService);
container.bind<OrderRepository>("OrderRepository").to(MySQLOrderRepository);
container.bind(OrderService).toSelf();
const orderService = container.get(OrderService); // auto-wired
```
Manual DI is excellent for small-to-medium projects — no magic, easy to debug, no decorators needed. IoC containers earn their complexity in large projects with deep dependency trees, where manual wiring becomes error-prone and repetitive. The DIP principle is the same regardless of which mechanism is used.

**Q9. What is a "composition root," and why must there be exactly one?**
A: The composition root is the single location in an application where all concrete implementations are instantiated and wired together. It's where DI happens. The rule "exactly one" matters because:
- If composition happens in multiple places, concrete classes leak into non-root modules, coupling business logic to infrastructure choices.
- The composition root is the *only* place that imports `MySQLOrderRepository`, `SendGridEmailService`, etc. Everything else imports only interfaces.
- In tests, you have a *test composition root* — a separate wiring that substitutes fakes for real implementations.

Typical composition root locations:
- **Node/Express:** `src/main.ts` or `src/app.ts`
- **NestJS:** `AppModule` providers array
- **InversifyJS:** `container.ts`
- **React app:** top-level `App.tsx` or a context provider

**Q10. How does DI work in a functional programming style, where classes aren't used?**
A: DI in functional code is just *function parameter passing* — higher-order functions that accept their dependencies as arguments:
```ts
// Functional DI — dependencies passed as parameters (no classes needed)
type SaveOrder = (order: Order) => Promise<void>;
type SendConfirmation = (order: Order) => Promise<void>;

// High-level function — depends on function-shaped abstractions (DIP ✓)
const placeOrder = (
  saveOrder: SaveOrder,            // injected ✓
  sendConfirmation: SendConfirmation // injected ✓
) => async (dto: PlaceOrderDto): Promise<Order> => {
  const order = Order.create(dto);
  await saveOrder(order);
  await sendConfirmation(order);
  return order;
};

// Composition root — wire real implementations
const placeOrderHandler = placeOrder(
  mysqlSaveOrder,
  sendgridSendConfirmation
);

// Test — wire fakes
const placeOrderTest = placeOrder(
  jest.fn().mockResolvedValue(undefined),
  jest.fn().mockResolvedValue(undefined)
);
```
DIP applies equally here — `placeOrder` depends on the *shape* of functions (`SaveOrder`, `SendConfirmation`), not on concrete implementations. The abstraction is a function type instead of an interface, but the principle is identical.

## Section 3: Dependency Inversion Principle In Depth

**Q11. What does "inversion" actually mean — what is being inverted?**
A: The *direction of the source-code dependency*, not the runtime flow of control. In a naive layered design, high-level code imports low-level code:
```
BusinessLogic  →  imports  →  Infrastructure (concrete)
```
After DIP, the import direction at the implementation level is flipped. The infrastructure depends on the domain's interface:
```
BusinessLogic  →  depends on  →  IRepository (abstraction, owned by domain)
Infrastructure →  implements  →  IRepository (depends on domain's abstraction)
```
Runtime flow of control is unchanged — `BusinessLogic` still *calls* the repository. But at the source-code level, `Infrastructure` now has an import dependency on `Domain` (to know what interface to implement), not the other way around. That's the inversion.

**Q12. Where should the interface (abstraction) live in the codebase — domain or infrastructure?**
A: Always in the **domain/application layer** — the high-level module that *uses* the dependency. This is where the inversion physically manifests in the file system:

```
src/
  domain/
    ports/
      OrderRepository.ts    ← interface lives HERE (domain owns it)
    OrderService.ts          ← imports from ports/
  infrastructure/
    MySQLOrderRepository.ts  ← imports from domain/ports/ to implement
    SendGridEmailService.ts  ← imports from domain/ports/ to implement
  composition-root/
    container.ts             ← only place that imports infrastructure
```

If the interface lived in `infrastructure/`, `OrderService` would have to import from `infrastructure/` — the dependency arrow still points downward. The interface must live where the *consumer* lives so the *implementor* depends *up* toward the consumer's contract.

**Q13. How does DIP relate to the "Stable Dependencies Principle"?**
A: The Stable Dependencies Principle (SDP) states that a module should only depend on modules that are *more stable* than itself. DIP and SDP reinforce each other:
- Interfaces (abstractions) are **stable** — they change rarely because they're defined by the consumer's need, not the implementor's capability.
- Concrete classes are **unstable** — they change frequently as implementation details evolve (library upgrades, schema changes, API changes).

DIP says "depend on abstractions" — which, by SDP, means depending on the most stable things in the system. A business rule depending on a MySQL query is depending on something very unstable. A business rule depending on an `OrderRepository` interface is depending on something very stable. DIP naturally guides you toward the SDP-compliant dependency direction.

**Q14. How does DIP enable the Open/Closed Principle (OCP)?**
A: DIP is the mechanism that makes OCP achievable. OCP says a module should be open for extension but closed for modification. Without DIP, extension requires editing the high-level module (because it knows about concretions). With DIP, extension means adding a new implementation of an existing abstraction — the high-level module never changes:
```ts
// DIP in place — NotificationService depends on abstraction
interface NotificationChannel { send(msg: Message): Promise<void>; }

class NotificationService {
  constructor(private channels: NotificationChannel[]) {}
  async notify(msg: Message) {
    await Promise.all(this.channels.map(c => c.send(msg)));
  }
}

// OCP: adding SMS support = new class, zero changes to NotificationService
class SMSChannel implements NotificationChannel {
  async send(msg: Message) { /* Twilio */ }
}

// Composition root — extend by adding, not modifying
const notifier = new NotificationService([
  new EmailChannel(),
  new SMSChannel(),    // new — NotificationService untouched
]);
```

## Section 4: How They Work Together — and Where They Diverge

**Q15. Summarise the relationship between DI and DIP in one mental model.**
A: Think of DIP as the *architectural blueprint* and DI as the *construction crew*:
- **DIP (blueprint)** says: "The domain layer should have an interface here. Infrastructure implements it. The domain never imports infrastructure."
- **DI (construction crew)** says: "At startup, we'll take the concrete infrastructure object and hand it to the domain object through its constructor."

DIP defines *what the wiring should look like in code*. DI defines *how the wiring is physically assembled at runtime*. You need both: DIP without DI means you follow the right abstraction rules but still have to pull dependencies yourself (Service Locator). DI without DIP means you efficiently deliver dependencies but they're still concrete — you've solved the construction problem without solving the coupling problem.

**Q16. How do DI and DIP interact in a testing workflow?**
A: They interact at every stage of the test lifecycle:

| Stage | DIP's role | DI's role |
|---|---|---|
| **Design** | Interface defined by domain — test knows the contract to fake | Constructor parameter declares what the test must supply |
| **Arrange** | Fake implements the interface — type-checked by TypeScript | Fake is passed via constructor — no global state to set up |
| **Act** | Subject under test calls through the interface — no real I/O | Subject receives the fake — no `new ConcreteClass()` inside |
| **Assert** | Interface methods are what we spy on — focused assertions | Spy is on the injected fake — nothing else to mock |

Without DIP, there's no interface to implement a fake against — you're stuck monkey-patching, intercepting module imports, or running against real infrastructure. Without DI, there's no injection point — you can't swap the real implementation for the fake without modifying the class.

**Q17. Is it possible to follow DIP without TypeScript interfaces — e.g., using abstract classes?**
A: Yes. Abstract classes are a valid abstraction mechanism and in some cases preferable:
```ts
// DIP via abstract class instead of interface
abstract class OrderRepository {
  abstract save(order: Order): Promise<void>;
  abstract findById(id: string): Promise<Order | null>;

  // Can include shared logic — interfaces can't
  async saveAll(orders: Order[]): Promise<void> {
    await Promise.all(orders.map(o => this.save(o)));
  }
}

class MySQLOrderRepository extends OrderRepository {
  async save(order: Order) { /* ... */ }
  async findById(id: string) { /* ... */ }
}
```
Trade-offs vs interfaces:
- Abstract classes **can contain shared implementation** — useful when multiple concrete implementations share logic.
- Abstract classes **use a nominal type relationship** — the subclass must explicitly `extend` the abstract class.
- A class can `implement` multiple interfaces but can only `extend` one abstract class — interfaces are more composable.
- For pure contracts with no shared behaviour, `interface` is idiomatic TypeScript. For contracts with shared defaults, `abstract class` is appropriate.

**Q18. What role does DI play in avoiding circular dependencies — and how does DIP help?**
A: Circular imports (`A → B → A`) are a common source of runtime `undefined` bugs in Node.js and TypeScript. DI and DIP together eliminate most of them:
- **DIP** breaks the cycle at the design level — if `UserService` depends on `IEmailService` (interface in domain) and `EmailService` implements `IEmailService`, there's no reason `EmailService` needs to import `UserService`. The cycle never forms.
- **DI** breaks it at the construction level — objects are assembled at the composition root, which imports all concrete classes in one place. The circular import at the module level disappears because no business module imports another concrete business module.

If you find a circular import in a DI-based codebase, it's almost always a sign that a class should be split, an interface should be extracted, or an event-driven decoupling (publishing a domain event instead of calling a service directly) should replace the direct call.

## Section 5: Pitfalls & Anti-Patterns

**Q19. What is the Service Locator anti-pattern, and how does it compare to proper DI?**
A: A Service Locator is a global registry that objects query to find their own dependencies — the object reaches *out* rather than having dependencies pushed *in*:

```ts
// Service Locator — pulls deps from a global registry
class OrderService {
  placeOrder(dto: PlaceOrderDto) {
    const repo   = ServiceLocator.get<OrderRepository>("OrderRepository");
    const mailer = ServiceLocator.get<EmailService>("EmailService");
    // ...
  }
}

// Constructor DI — deps pushed in from outside
class OrderService {
  constructor(
    private repo:   OrderRepository,
    private mailer: EmailService
  ) {}
}
```

| Aspect | Service Locator | Constructor DI |
|---|---|---|
| Dependencies visible? | No — hidden inside method bodies | Yes — declared in constructor signature |
| Testable without setup? | No — must pre-populate global registry | Yes — pass fakes directly |
| Coupled to locator? | Yes — always imports `ServiceLocator` | No |
| DIP satisfied? | Partially — abstractions used, but pulled | Fully — abstractions pushed in |
| Refactor safety? | Low — grep for hidden `get()` calls | High — constructor is the contract |

**Q20. What is "temporal coupling" in DI, and which injection style causes it?**
A: Temporal coupling occurs when an object is valid at construction time but incomplete until a setter is called — the order of operations matters:
```ts
// Setter injection creates temporal coupling
class ReportService {
  private repo: ReportRepository; // undefined until setRepo is called!

  setRepo(repo: ReportRepository) { this.repo = repo; }

  generate(): Report {
    return this.repo.fetch(); // runtime error if setRepo wasn't called first
  }
}

const svc = new ReportService();
// Forgot to call svc.setRepo(...)
svc.generate(); // 💥 TypeError: Cannot read properties of undefined
```
Constructor injection eliminates temporal coupling — if `repo` is a required constructor parameter, TypeScript enforces it at compile time. The object is either fully constructed or doesn't exist. Setter injection should be reserved for *genuinely optional* dependencies.

**Q21. What is "dependency over-exposure" and how does it relate to DIP?**
A: Dependency over-exposure happens when a class accepts a broad, fat dependency through DI (satisfying the mechanical DI requirement) but the interface it depends on exposes far more than the class needs — a DIP + ISP (Interface Segregation Principle) violation:
```ts
// Over-exposed dependency — OrderService only calls save(), but depends on all 8 methods
interface IOrderRepository {
  save(order: Order): Promise<void>;
  findById(id: string): Promise<Order | null>;
  findAll(): Promise<Order[]>;
  delete(id: string): Promise<void>;
  bulkDelete(ids: string[]): Promise<void>;
  count(): Promise<number>;
  paginate(opts: PageOptions): Promise<Page<Order>>;
  exportCsv(): Promise<Buffer>;
}

class OrderService {
  constructor(private repo: IOrderRepository) {} // DI ✓, but interface too fat
  async placeOrder(dto: PlaceOrderDto) {
    await this.repo.save(order); // uses only this one method
  }
}
```
Fix: apply ISP alongside DIP — narrow the injected interface to what the class actually uses:
```ts
interface OrderSaver { save(order: Order): Promise<void>; }

class OrderService {
  constructor(private repo: OrderSaver) {} // DI ✓, DIP ✓, ISP ✓
}
```

## Section 6: Scenario / System Design Style Questions

**Q22. "A teammate says: 'We're already using constructor injection everywhere, so we're following DIP.' How do you respond?"**
A: Acknowledge the good practice, then clarify the gap:
> "Constructor injection is a great start — it makes dependencies explicit and testable. But DI and DIP are two different things. DI tells us *how* to supply dependencies (through the constructor). DIP tells us *what* those dependencies should be — abstractions, not concretions. If we're injecting concrete classes like `MySQLOrderRepository` directly, we're using DI but not DIP. The constructor signature should reference an `OrderRepository` *interface*, not the concrete MySQL class. That way, swapping to Postgres or using an in-memory fake in tests requires zero changes to `OrderService`."

Then show the diff: constructor typed to `MySQLOrderRepository` → typed to `OrderRepository` interface. One line change; huge architectural shift.

**Q23. "You're setting up a new Node.js service from scratch. A junior dev asks: should we use InversifyJS or just wire things manually? How do you decide?"**
A: Frame the decision around scale and complexity, not preference:

| Factor | Manual DI ("Poor Man's DI") | IoC Container (InversifyJS / TSyringe) |
|---|---|---|
| Project size | Small to medium | Large, many modules |
| Dependency depth | Shallow (2–3 levels) | Deep (5+ levels of nesting) |
| Team familiarity | Works for all skill levels | Requires learning decorators and container API |
| Debuggability | Fully transparent — trace with eyes | Magic wiring — harder to debug misconfiguration |
| Boilerplate | More manual `new` calls | Less — container resolves automatically |
| Testing | Easy — just pass fakes manually | Easy — rebind in test container |

**Start with manual DI.** Add a container only when you have enough services that manual wiring becomes a maintenance problem — typically 10+ injectable services with non-trivial dependency trees. The DIP principles are *identical* in both cases; the container is just automation. Don't add framework complexity before you need it.

**Q24. "You're reviewing a PR where a developer added a React context that stores a concrete API service instance and shares it globally. Is this DI? Is this DIP? What would you change?"**
A: Evaluate both dimensions:
```tsx
// PR — concrete service in context
const ApiContext = React.createContext(new UserApiService()); // concrete ✗

function ProfilePage() {
  const api = useContext(ApiContext); // receives it — DI ✓ (sort of)
  api.fetchUser(id);
}
```
- **Is it DI?** Partially — components receive the dependency via context rather than constructing it, which is the *spirit* of DI. But the context is initialised with a concrete `new UserApiService()` at the top level.
- **Is it DIP?** No — `ProfilePage` depends on `UserApiService` (concrete). There's no abstraction. Testing `ProfilePage` in isolation requires a real `UserApiService` or module-level mocking.

What to change:
```tsx
// Define the abstraction
interface UserService { fetchUser(id: string): Promise<User>; }

// Context typed to the interface — DIP ✓
const UserServiceContext = React.createContext<UserService | null>(null);

// Provider at composition root — only place that knows about the concrete class
function App() {
  return (
    <UserServiceContext.Provider value={new UserApiService()}>
      <ProfilePage />
    </UserServiceContext.Provider>
  );
}

// Test — provide a fake
render(
  <UserServiceContext.Provider value={{ fetchUser: async () => fakeUser }}>
    <ProfilePage />
  </UserServiceContext.Provider>
);
```
Now `ProfilePage` depends on a `UserService` interface — DI (via context) and DIP (via interface) are both satisfied.

**Q25. "A monolith's `PaymentService` directly imports three different payment SDKs (Stripe, PayPal, Braintree) and switches between them with an if-else on a config flag. What's wrong, and how do you fix it using both DI and DIP?"**
A: Multiple violations compounded:
1. `PaymentService` imports three concrete SDKs — depends on three low-level details simultaneously.
2. The config flag branching is a runtime conditional that belongs at the composition root, not inside business logic.
3. Adding a fourth provider requires editing `PaymentService` — OCP violation, caused by the DIP violation.

Fix — apply Strategy pattern via DIP + DI:
```ts
// DIP: single abstraction for all payment providers
interface PaymentGateway {
  charge(amount: Money, token: string): Promise<ChargeResult>;
  refund(chargeId: string, amount: Money): Promise<RefundResult>;
}

// Three concrete implementations — each imports only its own SDK
class StripeGateway    implements PaymentGateway { /* Stripe SDK */ }
class PayPalGateway    implements PaymentGateway { /* PayPal SDK */ }
class BraintreeGateway implements PaymentGateway { /* Braintree SDK */ }

// PaymentService — knows nothing about any SDK
class PaymentService {
  constructor(private gateway: PaymentGateway) {} // DI ✓, DIP ✓

  async processPayment(amount: Money, token: string): Promise<ChargeResult> {
    return this.gateway.charge(amount, token);
  }
}

// Composition root — the one place that reads config and picks a concrete
function buildPaymentGateway(config: Config): PaymentGateway {
  switch (config.paymentProvider) {
    case "stripe":    return new StripeGateway(config.stripeKey);
    case "paypal":    return new PayPalGateway(config.paypalKey);
    case "braintree": return new BraintreeGateway(config.braintreeKey);
    default: throw new Error(`Unknown payment provider: ${config.paymentProvider}`);
  }
}

const paymentService = new PaymentService(buildPaymentGateway(config));
```
Adding a fourth provider is a new class + one `case` in the composition root. `PaymentService` is never touched — OCP achieved via DIP + DI.

## Master Comparison Table

| Dimension | Dependency Injection (DI) | Dependency Inversion Principle (DIP) |
|---|---|---|
| **Type** | Technique / pattern | Design principle (SOLID) |
| **Question answered** | *How* does an object get its dependencies? | *What* should dependencies be — abstractions or concretions? |
| **Enforced by** | Constructor / setter / method signatures; IoC containers | Interfaces / abstract types; file structure (interface in domain) |
| **Can exist without the other?** | Yes — inject a concrete class | Yes — Service Locator resolves an abstraction |
| **Primary benefit** | Removes construction responsibility from the class | Decouples high-level logic from low-level details |
| **Testing benefit** | Injection point exists to swap in fakes | Interface exists to implement fakes against |
| **Violation symptom** | `new ConcreteClass()` inside a business method | Business class imports from infrastructure layer |
| **Fix** | Pass dependency via constructor / context / parameter | Extract interface; move it to domain layer; implement in infrastructure |
| **Framework examples** | InversifyJS, TSyringe, NestJS DI, React Context | Manifests in file structure, not a framework |
| **Relation to IoC** | DI is the most common IoC mechanism | DIP tells IoC *what types* to wire — abstractions |
| **Over-application risk** | Constructor over-injection (class has too many deps) | Interface-for-everything with no real second implementor |

## Decision Flowchart (whiteboard-friendly)

```
A class needs a collaborator
          │
          ▼
Is the collaborator constructed inside the class?
    Yes → Apply DI: move construction outside (constructor param / context)
    No  → DI already in place
          │
          ▼
Is the injected type a concrete class?
    Yes → Apply DIP: extract interface; retype the constructor param to the interface
    No  → DIP already in place
          │
          ▼
Does the interface live in the infrastructure layer?
    Yes → Move it to domain/application layer (true inversion)
    No  → ✅ Both DI and DIP correctly applied
          │
          ▼
Is the interface broader than what the class uses?
    Yes → Apply ISP: narrow the interface to only what the class needs
    No  → ✅ Done
```

**Tip for the interview:** At the 5 YOE level this distinction comes up in three disguises: "why can't we unit-test this service without a real database" (missing DI or DIP or both), "we added a new payment provider and had to change five files" (missing DIP — no abstraction, so extension requires modification), and "our test suite pre-populates a global service locator and tests interfere with each other" (DI violated — hidden global state instead of injected deps). The sharp answer names the two concepts separately, explains why both are needed, and traces the specific violation in the code to its root cause — either missing injection point (DI problem) or missing abstraction (DIP problem) or both. That precision is what lands at 5 YOE.
