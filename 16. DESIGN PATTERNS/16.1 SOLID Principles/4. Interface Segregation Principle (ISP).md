# JavaScript / TypeScript (Design Patterns — SOLID Principles): Interface Segregation Principle (ISP) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Interface Segregation Principle (ISP)?**
A: ISP is the "I" in SOLID, originally stated by Robert C. Martin as: *"Clients should not be forced to depend on methods they do not use."* In practical terms, it means that a large, fat interface should be broken into smaller, focused interfaces (called role interfaces) so that implementing classes only need to know about the methods that are actually relevant to them. If a class is forced to implement methods it doesn't need, that's a signal the interface is doing too much.

**Q2. Why does ISP exist — what problem was it designed to solve?**
A: Before ISP, object-oriented design often produced "fat" or "god" interfaces — single interfaces that bundled every conceivable operation for a concept. Any class that needed just one behaviour was still forced to implement (or stub out) all of them. This created several problems:
- **Tight coupling** — a change to any method on the fat interface forced every implementor to recompile/re-verify, even if the change was irrelevant to them.
- **Meaningless implementations** — classes that didn't support a method had to throw `NotImplementedError` or return dummy values, making the contract deceptive.
- **Reduced reusability** — a class designed for one role dragged in unrelated responsibilities, making it harder to use in other contexts.
ISP fixes this by making interfaces cohesive and minimal, so a client depends only on what it actually uses.

**Q3. How does ISP relate to the other SOLID principles?**
A:
- **SRP (Single Responsibility)** — ISP is SRP applied to interfaces rather than classes. A fat interface is often a symptom that a class has too many responsibilities too.
- **LSP (Liskov Substitution)** — Fat interfaces often cause LSP violations: an implementor forced to provide a method it can't support meaningfully will throw or return nonsense, breaking substitutability. Segregated interfaces prevent this.
- **DIP (Dependency Inversion)** — ISP and DIP work together: DIP says depend on abstractions; ISP says those abstractions should be narrow. A client that depends on a narrow interface is both inverted (doesn't depend on the concrete) and segregated (doesn't depend on irrelevant methods).
- **OCP (Open/Closed)** — Narrow interfaces are easier to extend without modification, since adding a new role interface doesn't touch existing ones.

**Q4. What is a "fat interface," and what does a violation look like in JavaScript/TypeScript?**
A: A fat interface is one that groups unrelated or partially related methods, forcing implementors to deal with methods outside their concern. Classic violation in TypeScript:
```ts
interface Worker {
  work(): void;
  eat(): void;
  sleep(): void;
  attendMeeting(): void;
  writeReport(): void;
}

class Robot implements Worker {
  work() { /* fine */ }
  eat()  { throw new Error("Robots don't eat"); }    // forced, meaningless
  sleep(){ throw new Error("Robots don't sleep"); }  // forced, meaningless
  attendMeeting() { /* maybe */ }
  writeReport()   { /* maybe */ }
}
```
`Robot` is forced to implement `eat` and `sleep` — methods that have no meaning for it. This is the ISP violation.

**Q5. What does a well-segregated version of that interface look like?**
A: Split by role — each interface represents one coherent capability:
```ts
interface Workable    { work(): void; }
interface Eatable     { eat(): void; }
interface Sleepable   { sleep(): void; }
interface Reportable  { writeReport(): void; }
interface Meetable    { attendMeeting(): void; }

class Robot implements Workable, Meetable, Reportable {
  work()        { /* ✓ */ }
  attendMeeting(){ /* ✓ */ }
  writeReport() { /* ✓ */ }
  // eat and sleep never appear — Robot doesn't know they exist
}

class HumanWorker implements Workable, Eatable, Sleepable, Meetable, Reportable {
  work()        { /* ✓ */ }
  eat()         { /* ✓ */ }
  sleep()       { /* ✓ */ }
  attendMeeting(){ /* ✓ */ }
  writeReport() { /* ✓ */ }
}
```
Now each class implements exactly the interfaces relevant to it — no throwing, no stubs.

## Section 2: ISP in JavaScript (Structural Typing & Duck Typing)

**Q6. JavaScript doesn't have interfaces. Does ISP still apply?**
A: Yes — and in some ways it applies more naturally. JavaScript uses **duck typing**: if an object has the right shape (the right methods/properties), it satisfies the contract. ISP in plain JS manifests as: don't design functions or systems that demand an object with 10 methods when they only use 3. The violation and fix look like this:
```js
// Violation — caller forces a "fat" object contract
function processDocument(handler) {
  handler.parse();
  handler.validate();
  handler.serialize();   // <-- processDocument only calls parse & validate!
  handler.archive();     // <-- never called here
}

// Fix — narrow the dependency to what's actually used
function processDocument(handler) {
  handler.parse();
  handler.validate();
  // serialize and archive are someone else's concern
}
```
The "interface" is implicit (the object's shape), but the principle is identical: depend only on what you use.

**Q7. How does TypeScript's structural type system interact with ISP?**
A: TypeScript is structurally typed, not nominally typed — a type is compatible with an interface as long as it has the required shape, regardless of whether it explicitly declares `implements`. This makes ISP almost automatic for consumers: a function typed to accept `{ parse(): void; validate(): void }` naturally excludes unrelated methods from its contract. The risk is on the producer side — if you design a class or object literal with 15 methods, callers who type their parameter broadly will implicitly depend on all of them. Explicit narrow interfaces make the segregation visible and enforced:
```ts
interface Parser    { parse(raw: string): Document; }
interface Validator { validate(doc: Document): boolean; }

// This function depends ONLY on Parser — can't accidentally use Validator methods
function ingest(parser: Parser, raw: string): Document {
  return parser.parse(raw);
}
```

**Q8. What are "role interfaces," and how do they differ from "header interfaces"?**
A:
- **Header interface** — a 1:1 interface extracted from a concrete class, listing every method the class has. Often generated by IDEs ("Extract Interface"). Violates ISP because it mirrors the class's full surface area rather than a client's specific need.
- **Role interface** — a minimal interface defined from the *client's* perspective: what does *this* caller need from *any* collaborator? Clients drive the interface shape, not the implementor.

```ts
// Header interface (bad) — mirrors the concrete class
interface IUserService {
  getById(id: string): User;
  create(dto: CreateUserDto): User;
  update(id: string, dto: UpdateUserDto): User;
  delete(id: string): void;
  sendWelcomeEmail(user: User): void;
  generateReport(): Report;
}

// Role interfaces (good) — one per client need
interface UserReader   { getById(id: string): User; }
interface UserWriter   { create(dto: CreateUserDto): User; update(id: string, dto: UpdateUserDto): User; }
interface UserDeleter  { delete(id: string): void; }
interface EmailSender  { sendWelcomeEmail(user: User): void; }
interface ReportSource { generateReport(): Report; }
```

**Q9. Can a single class implement multiple segregated interfaces?**
A: Yes — and that's the intended pattern. ISP doesn't say "small classes"; it says "small interfaces." A concrete class may be rich in functionality and implement many role interfaces. The benefit is that clients depend on individual role interfaces, not the full class, so they're decoupled from methods they don't use:
```ts
class UserService implements UserReader, UserWriter, UserDeleter, EmailSender, ReportSource {
  getById(id: string) { /* ... */ }
  create(dto: CreateUserDto) { /* ... */ }
  update(id: string, dto: UpdateUserDto) { /* ... */ }
  delete(id: string) { /* ... */ }
  sendWelcomeEmail(user: User) { /* ... */ }
  generateReport() { /* ... */ }
}

// AuthGuard only needs to read users — depends on the narrow interface
class AuthGuard {
  constructor(private users: UserReader) {}
  // can't accidentally call delete() or sendWelcomeEmail()
}
```

## Section 3: Patterns, Techniques & Real-World Application

**Q10. How do you apply ISP to React component props?**
A: A React component that accepts a large "god object" as a prop is an ISP violation — it couples the component to data it doesn't use, makes testing harder (you must construct the whole object), and breaks when unrelated fields change. Apply ISP by typing props to only the fields the component actually renders:
```tsx
// Violation — component depends on entire User object
interface Props { user: User; }
const Avatar: React.FC<Props> = ({ user }) => <img src={user.avatarUrl} alt={user.name} />;

// Fix — depend only on what Avatar actually uses
interface AvatarProps { avatarUrl: string; name: string; }
const Avatar: React.FC<AvatarProps> = ({ avatarUrl, name }) => <img src={avatarUrl} alt={name} />;
```
Now `Avatar` can be passed any object with `avatarUrl` and `name` — a `User`, a `Teammate`, a `Contact` — without coupling to the full type.

**Q11. How does ISP apply to REST API / service layer design?**
A: When a service class grows to handle all operations for a domain entity, downstream callers (controllers, other services) often depend on the whole service even if they only call one or two methods. Apply ISP by defining read/write/admin interfaces:
```ts
interface OrderReader  { getOrder(id: string): Order; listOrders(filter: OrderFilter): Order[]; }
interface OrderWriter  { createOrder(dto: CreateOrderDto): Order; updateOrder(id: string, dto: UpdateOrderDto): Order; }
interface OrderCanceller { cancelOrder(id: string): void; }

class OrderService implements OrderReader, OrderWriter, OrderCanceller { /* ... */ }

// Reporting service only needs to read — inject the narrow interface
class SalesReportService {
  constructor(private orders: OrderReader) {}
}
```

**Q12. What is interface composition, and how does it relate to ISP?**
A: Interface composition (also called interface intersection in TypeScript) is the practice of combining narrow interfaces to build richer ones when needed, rather than starting with a fat interface and trying to break it down later. This is the natural ISP workflow:
```ts
// Atomic role interfaces
interface Readable<T>  { read(id: string): T; }
interface Writable<T>  { write(item: T): void; }
interface Deletable    { delete(id: string): void; }

// Composed interfaces for specific contexts
type ReadWritable<T>   = Readable<T> & Writable<T>;
type FullRepository<T> = Readable<T> & Writable<T> & Deletable;

// A cache might only implement Readable & Writable, not Deletable
class InMemoryCache<T> implements ReadWritable<T> { /* ... */ }
```

**Q13. How does ISP interact with the Repository pattern?**
A: The Repository pattern often grows fat — a single `UserRepository` interface with `findById`, `findAll`, `findByEmail`, `save`, `update`, `delete`, `bulkDelete`, `count`, `paginate`... A read-heavy consumer (e.g., a read model in CQRS) shouldn't depend on write methods it never calls. Segregate:
```ts
interface UserReadRepository {
  findById(id: string): Promise<User | null>;
  findByEmail(email: string): Promise<User | null>;
  paginate(opts: PaginationOptions): Promise<Page<User>>;
}

interface UserWriteRepository {
  save(user: User): Promise<void>;
  update(user: User): Promise<void>;
  delete(id: string): Promise<void>;
}

class PrismaUserRepository implements UserReadRepository, UserWriteRepository { /* ... */ }

// Query handler only gets the read side — can't accidentally call save()
class GetUserQueryHandler {
  constructor(private repo: UserReadRepository) {}
}
```

**Q14. How does ISP apply to event emitters or pub/sub systems in Node.js?**
A: An `EventEmitter`-based system can violate ISP if consumers are passed the full emitter and could listen to (or emit) any event. Segregate by exposing typed, role-specific interfaces:
```ts
interface OrderEventPublisher { emit(event: "order:created" | "order:cancelled", payload: OrderEvent): void; }
interface OrderEventSubscriber { on(event: "order:created" | "order:cancelled", handler: (p: OrderEvent) => void): void; }

// An analytics listener gets only the subscriber interface — can't accidentally emit
class AnalyticsListener {
  constructor(private events: OrderEventSubscriber) {
    this.events.on("order:created", this.track.bind(this));
  }
  private track(payload: OrderEvent) { /* ... */ }
}
```

## Section 4: Pitfalls, Anti-Patterns & Misapplications

**Q15. Can you over-apply ISP? What does that look like?**
A: Yes. Taken too far, ISP produces one-method interfaces for everything, resulting in an explosion of tiny types that are tedious to manage, hard to discover, and provide little semantic grouping. The signal that you've gone too far:
- Every method on a class has its own interface with no real client driving the split.
- You're creating interfaces preemptively, before any second client exists to justify the split.
- The interfaces have no meaningful name beyond "Thing that has methodX."

ISP is a client-driven principle — split interfaces when a *real* client needs a narrower contract. Don't split speculatively. YAGNI applies here: if there's only one consumer of an interface, one interface is fine.

**Q16. What is the difference between ISP and the Facade pattern?**
A: They solve related but distinct problems:
- **ISP** — a design principle about how to *define* interfaces: keep them narrow and role-specific so clients don't depend on what they don't use.
- **Facade** — a structural pattern about how to *simplify access* to a complex subsystem: provide one simple entry point that hides complexity behind it. A Facade may itself implement an ISP-compliant interface, but the Facade is about simplification, not segregation.

In practice, a Facade often helps *clients* not need to know the full interface of a complex system — a complementary, not competing, concern.

**Q17. How is ISP different from the Adapter pattern?**
A: Again, complementary:
- **ISP** — a principle that says interfaces should match the client's need.
- **Adapter** — a pattern that *retrofits* an existing class to satisfy an interface it wasn't designed for, bridging a mismatch in shape.

If a third-party library has a fat interface and you only need a narrow slice of it, you can write an Adapter that wraps it and exposes an ISP-compliant interface to your code:
```ts
// Third-party has 12 methods; you only need one
interface DocumentParser { parse(raw: string): Document; }

class ThirdPartyParserAdapter implements DocumentParser {
  constructor(private lib: ThirdPartyParserLib) {}
  parse(raw: string): Document {
    return this.lib.fullParse(raw, { strict: true, format: "json" });
  }
}
```

**Q18. What happens when ISP is violated in a large TypeScript codebase at scale?**
A: At scale, ISP violations compound into systemic problems:
- **Cascade recompilation** — TypeScript's language server and build tools must re-check every file that imports a fat interface whenever any part of it changes, slowing CI.
- **Circular dependency risk** — fat interfaces often pull in types from unrelated domains, creating import cycles that are hard to untangle.
- **Test doubles become enormous** — mocking a 15-method interface for a test that only exercises 2 paths means 13 no-op stubs, making tests verbose and fragile.
- **Cognitive load** — developers reading a function signature that accepts a fat interface can't tell which methods matter — they have to read the implementation.

**Q19. How do you refactor a fat interface without breaking existing consumers?**
A: Incrementally, using the Strangler Fig approach:
1. **Identify roles** — audit which methods each consumer actually calls. Group by consumer need.
2. **Extract narrow interfaces** — define the new role interfaces (additive; don't remove anything yet).
3. **Update the concrete class** — add `implements NarrowInterfaceA, NarrowInterfaceB` alongside the existing fat interface.
4. **Migrate consumers one by one** — update each consumer's parameter type from `FatInterface` to the appropriate role interface. Tests will catch regressions.
5. **Deprecate and eventually remove the fat interface** — once no consumer depends on it, delete it.

This avoids a big-bang rewrite and keeps the codebase functional throughout.

## Section 5: Testing & Dependency Injection

**Q20. How does ISP improve testability?**
A: Narrow interfaces make test doubles (mocks, stubs, fakes) trivial to write. Compare:
```ts
// Fat interface — mock needs 10 no-op stubs just to satisfy the type
const mockService: IFatUserService = {
  getById: jest.fn(),
  create: jest.fn(),
  update: jest.fn(),
  delete: jest.fn(),
  sendWelcomeEmail: jest.fn(),
  generateReport: jest.fn(),
  lock: jest.fn(),
  unlock: jest.fn(),
  audit: jest.fn(),
  exportCsv: jest.fn(),
};

// Narrow interface — mock only needs what the unit under test actually uses
const mockReader: UserReader = { getById: jest.fn().mockResolvedValue(fakeUser) };
```
The narrow mock is self-documenting: looking at the test, you instantly know the subject only reads users.

**Q21. How does ISP relate to Dependency Injection containers?**
A: DI containers (InversifyJS, TSyringe, NestJS's built-in) resolve dependencies by token, usually keyed to an interface. If you register a fat interface, every consumer that injects it gets the whole concrete class — including methods it'll never call. Registering narrow role interfaces means each consumer gets a binding scoped to exactly its need, and you can swap implementations per role independently:
```ts
container.bind<UserReader>("UserReader").to(PrismaUserRepository);
container.bind<UserWriter>("UserWriter").to(PrismaUserRepository);
// In tests, swap only the reader without touching the writer binding
container.rebind<UserReader>("UserReader").to(InMemoryUserRepository);
```

## Section 6: Scenario / System Design Style Questions

**Q22. "A junior dev created a single `IStorageService` interface with `upload`, `download`, `delete`, `listFiles`, `generatePresignedUrl`, `setMetadata`, `getMetadata`, and `createBucket`. You're reviewing the PR. What do you say?"**
A: Several concerns:
- The interface bundles at least three distinct roles: **file I/O** (`upload`, `download`, `delete`, `listFiles`), **URL generation** (`generatePresignedUrl`), **metadata management** (`setMetadata`, `getMetadata`), and **bucket administration** (`createBucket`).
- A consumer like a file-upload handler only needs `upload` and `generatePresignedUrl` — it shouldn't know `createBucket` exists.
- Any change to the bucket-admin surface (adding `deleteBucket`) forces every consumer of `IStorageService` to update their mock, even consumers that never use bucket ops.
- Suggested split: `FileUploader`, `FileDownloader`, `FileDeleter`, `PresignedUrlGenerator`, `MetadataManager`, `BucketManager`. Let concrete classes like `S3StorageService` implement all of them; consumers depend only on the role they need.

**Q23. "Your team is building a plugin system where third parties implement a `Plugin` interface. The interface has grown to 20 methods over 18 months. Plugin authors are complaining it's hard to implement. How do you fix this?"**
A: Classic ISP failure in a plugin API:
1. **Audit which methods are actually required vs optional** — often only 3–5 methods are genuinely required; the rest were added for specific host needs.
2. **Introduce lifecycle interfaces** — split by plugin lifecycle phase: `PluginInitializer` (`init`, `teardown`), `CommandHandler` (`registerCommands`), `EventListener` (`onEvent`), `UIContributor` (`contributePanel`), etc.
3. **Use mixin/composition** — plugin authors implement only the interfaces relevant to their plugin's capabilities.
4. **Provide base class with no-op defaults** — a `BasePlugin` abstract class can implement all interfaces with no-op defaults, letting authors override only what they care about (similar to how Java's `MouseAdapter` works). This is a pragmatic complement to ISP in plugin APIs.
5. **Version the API carefully** — removing methods from a public interface is a breaking change; use deprecation cycles.

**Q24. "You're designing a permissions system. An `Authorizer` interface has `canRead`, `canWrite`, `canDelete`, `canAdmin`. A logging middleware only checks `canRead`. Is this an ISP violation, and how would you fix it?"**
A: Yes — `LoggingMiddleware` is forced to depend on `canWrite`, `canDelete`, and `canAdmin` even though it only calls `canRead`. If the `Authorizer` interface gains a new method (say, `canExport`), the logging middleware's test double must be updated for no reason.
Fix:
```ts
interface ReadAuthorizer  { canRead(resource: string, user: User): boolean; }
interface WriteAuthorizer { canWrite(resource: string, user: User): boolean; }
interface DeleteAuthorizer{ canDelete(resource: string, user: User): boolean; }
interface AdminAuthorizer { canAdmin(resource: string, user: User): boolean; }

// Full authorizer composes all roles
type Authorizer = ReadAuthorizer & WriteAuthorizer & DeleteAuthorizer & AdminAuthorizer;

// LoggingMiddleware depends only on reading
class LoggingMiddleware {
  constructor(private auth: ReadAuthorizer) {}
}
```

**Q25. "A microservice's gRPC contract (proto) defines a single `UserService` with 15 RPCs. Each downstream service uses 2–3 of them. Is this an ISP problem? What do you do about it?"**
A: Yes — it's the same principle at the API boundary level. Each consumer is coupled to the full proto contract; a change to any RPC (even one it never calls) can trigger client regeneration and redeployment. Options:
- **Split the proto** — define separate `UserReadService`, `UserWriteService`, `UserAdminService` proto services. Each downstream service imports only the proto it needs.
- **API Gateway / BFF** — a Backend-for-Frontend can expose narrow contracts to each consumer while the upstream service remains fat (trades code coupling for network coupling, acceptable in some architectures).
- **Proto composition** — gRPC allows a service to span multiple `.proto` files; keep RPCs grouped by role interface in separate files even within one service definition.
In practice, splitting a live gRPC contract requires versioning (v1 → v2) or a migration period where both the old fat service and new narrow services coexist.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect                          | Fat Interface (ISP Violation)                  | Segregated Role Interfaces (ISP Compliant)       |
|---                              |---                                             |---                                               |
| Consumer coupling               | Coupled to all methods, used or not            | Coupled only to methods it actually uses         |
| Test double complexity          | Must stub every method                         | Stub only what the test exercises                |
| Change impact                   | Any method change affects all consumers        | Change ripples only to consumers of that role    |
| Implementor burden              | Must implement irrelevant methods (throws/stubs)| Implements only relevant methods                |
| Discoverability                 | Hard — which methods matter for my use case?   | Clear — role name tells you exactly              |
| Reuse potential                 | Low — drags in unrelated contract              | High — narrow interfaces compose freely          |
| Over-application risk           | N/A                                            | One-method-per-interface explosion if not careful|

## ISP vs Related Principles (at a glance)

| Principle | Focus                          | Relationship to ISP                                      |
|---        |---                             |---                                                       |
| **SRP**   | Class responsibilities         | ISP is SRP applied to interfaces                         |
| **LSP**   | Substitutability               | Fat interfaces cause LSP violations; ISP prevents them   |
| **OCP**   | Extension without modification | Narrow interfaces are easier to extend via new roles     |
| **DIP**   | Depend on abstractions         | ISP ensures those abstractions are minimal and role-based|
| **Facade**| Simplify complex subsystems    | Complementary — Facade may expose an ISP-compliant surface|
| **Adapter**| Bridge shape mismatches       | Use Adapter to wrap a fat third-party into a narrow ISP interface|

**Tip for the interview:** At the 5 YOE level, "what is ISP" won't come up in isolation — it surfaces as: why is this interface hard to mock in tests, why does changing one service force 12 other files to recompile, why is this plugin API painful to implement, or how would you structure a repository layer in a CQRS system. Know the fat-interface → role-interface refactor cold, be able to connect ISP to testability and DI container design, and have a real story about narrowing a large interface to ease testing or decouple a module — that's the level of answer that lands at 5 YOE.
