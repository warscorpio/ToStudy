# JavaScript / TypeScript (Design Patterns — SOLID Principles): Composition over Inheritance — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does "composition over inheritance" mean?**
A: It is a design principle — originating from the Gang of Four's *Design Patterns* (1994) — that recommends favouring object composition as the primary mechanism for code reuse and behaviour assembly, rather than class inheritance hierarchies. In plain terms: instead of building a subclass that *is-a* specialisation of a parent, build an object that *has-a* set of collaborating components that supply its behaviour. The principle does not say "never use inheritance" — it says "reach for composition first, and use inheritance only when the relationship is genuinely *is-a* and stable."

**Q2. What is the core problem with inheritance that composition solves?**
A: Inheritance creates **tight compile-time coupling** between a subclass and its parent. Several problems flow from this:
- **Fragile Base Class Problem** — a change to the parent class can silently break every subclass, even ones that never needed the changed method.
- **Inflexible hierarchy** — a class can only inherit from one parent (in most languages, including TypeScript's single-inheritance class model), so the hierarchy must be chosen upfront and is expensive to change later.
- **Inherited bloat** — subclasses inherit all parent methods, including ones they don't need, violating ISP at the structural level.
- **Encapsulation breach** — subclasses often need to know how the parent works internally to override correctly (white-box reuse), not just what its public contract is.

Composition solves all of these: components are loosely coupled, swappable at runtime, independently testable, and combined freely without hierarchy constraints.

**Q3. What is the difference between "is-a" and "has-a" relationships, and why does it matter?**
A: These are the two candidate relationships that inheritance and composition model respectively:
- **Is-a (inheritance):** `Dog is-a Animal`, `SavingsAccount is-a Account`. The subtype genuinely extends the contract of the supertype — everywhere you use `Animal`, a `Dog` can substitute (Liskov Substitution Principle). This is when inheritance is correct.
- **Has-a (composition):** `Car has-a Engine`, `OrderService has-a PaymentGateway`. The object *uses* or *delegates to* a collaborator to get behaviour. This covers the majority of real-world design needs.

The test: ask "would I ever substitute a `Dog` where an `Animal` is expected?" If yes — inheritance may be appropriate. Ask "does `Dog` *use* a `Tail` for behaviour?" — that's composition. Developers overuse inheritance because it feels like a shortcut to code reuse, not because the *is-a* relationship genuinely holds.

**Q4. What does "composition" mean concretely in JavaScript/TypeScript?**
A: An object holds references to other objects (its components) and delegates behaviour to them, rather than inheriting it. Composition takes several concrete forms:

```ts
// Form 1 — constructor injection (most common)
class OrderService {
  constructor(
    private payment: PaymentGateway,   // composed in
    private mailer:  EmailService       // composed in
  ) {}

  async placeOrder(dto: PlaceOrderDto) {
    const order = Order.create(dto);
    await this.payment.charge(order.total, dto.paymentToken);
    await this.mailer.sendConfirmation(order);
    return order;
  }
}

// Form 2 — object literal / mixin assembly (functional style)
const withLogging = (target: object) => ({
  ...target,
  log(msg: string) { console.log(`[${new Date().toISOString()}] ${msg}`); }
});

// Form 3 — React composition (components wrapping components)
const AuthenticatedPage = ({ children }: { children: React.ReactNode }) => (
  <AuthGuard>
    <Layout>{children}</Layout>
  </AuthGuard>
);
```

In every form, behaviour is assembled by *combining* objects, not by *extending* a class.

**Q5. Why does JavaScript's prototype chain make "composition over inheritance" especially relevant?**
A: JavaScript's class syntax (`class Foo extends Bar`) is syntactic sugar over prototype-chain delegation — it's still single-inheritance, still creates the same tight coupling, and still suffers the same fragile base class problems as classical OOP. But JavaScript also has first-class functions, object spread, and closures, which make composition *dramatically easier* to express than in Java or C#:
```js
// Behaviour as plain functions — compose freely, no class needed
const canEat   = (state) => ({ eat:   () => console.log(`${state.name} eats`)   });
const canSleep = (state) => ({ sleep: () => console.log(`${state.name} sleeps`) });
const canWork  = (state) => ({ work:  () => console.log(`${state.name} works`)  });

// Compose a Human from behaviours
const createHuman = (name) => {
  const state = { name };
  return Object.assign({}, canEat(state), canSleep(state), canWork(state));
};

// Compose a Robot from only the behaviours it needs
const createRobot = (name) => {
  const state = { name };
  return Object.assign({}, canWork(state)); // no eat, no sleep
};
```
No inheritance hierarchy. No `Robot extends Worker`. No forced `eat()` stub. Each behaviour is an independent, testable unit. JavaScript's flexibility makes composition the natural grain of the language.

## Section 2: Inheritance — When It Works and When It Doesn't

**Q6. When is inheritance the right choice?**
A: Inheritance is appropriate when all three conditions hold simultaneously:
1. **True is-a relationship** — the subclass genuinely specialises the supertype; every instance of the subclass is also a valid instance of the supertype, and LSP is satisfied.
2. **Stable hierarchy** — the relationship won't change; restructuring a deep hierarchy is extremely costly.
3. **Intentional extension points** — the parent was explicitly designed to be extended (template method pattern, abstract classes with well-defined hooks), not just reused for convenience.

Classic valid uses in a JavaScript/TypeScript codebase:
- `HttpException extends Error` — all HTTP errors genuinely *are* errors, `Error`'s properties are always relevant.
- `AdminUser extends User` — if `AdminUser` truly is a `User` with additional capability and your system must substitute one for the other.
- `React.Component` — the base class is explicitly designed as an extension point with lifecycle hooks.

**Q7. What is the Fragile Base Class Problem? Show it in TypeScript.**
A: The parent class is modified in a reasonable way, and a subclass that didn't know about the implementation detail breaks silently:
```ts
class EventEmitter {
  private listeners: Function[] = [];

  on(handler: Function) {
    this.listeners.push(handler);
  }

  emit(event: string) {
    this.listeners.forEach(l => l(event));
  }
}

class LoggingEmitter extends EventEmitter {
  private count = 0;

  // Overrides on() to count registrations
  on(handler: Function) {
    this.count++;
    super.on(handler); // delegates to parent
  }
}

// Parent is "improved" — on() now calls addListener() internally
class EventEmitter {
  private listeners: Function[] = [];

  addListener(handler: Function) {
    this.listeners.push(handler);
  }

  on(handler: Function) {
    this.addListener(handler); // refactored internals
    this.emit("listenerAdded");
  }

  emit(event: string) {
    this.listeners.forEach(l => l(event));
  }
}

// LoggingEmitter.on() now double-counts — once via override, once via emit("listenerAdded")
// triggering on() again in some setups — a silent, hard-to-trace bug
```
The subclass depended on a parent *implementation detail* (that `on()` directly pushed to `listeners`). When the parent was refactored (legitimately), the subclass broke. With composition, `LoggingEmitter` would *hold* an `EventEmitter` instance and wrap its methods — no access to internals, no fragility.

**Q8. What is the "inheritance for code reuse" anti-pattern?**
A: Using inheritance purely to avoid duplicating code, without a genuine *is-a* relationship — the most common misuse:
```ts
// Anti-pattern — Timestamp mixin via inheritance
class HasTimestamps {
  createdAt: Date = new Date();
  updatedAt: Date = new Date();
  touch() { this.updatedAt = new Date(); }
}

// Order is-a HasTimestamps? No. Order *has* timestamps.
class Order extends HasTimestamps {
  constructor(public id: string, public total: number) { super(); }
}

// User is-a HasTimestamps? No. User *has* timestamps.
class User extends HasTimestamps {
  constructor(public id: string, public email: string) { super(); }
}
```
Problems: `Order` and `User` can never extend anything else (single inheritance consumed). `HasTimestamps` is exposed in the public interface of `Order` even though it's a cross-cutting utility. The hierarchy is semantically wrong.

Fix — compose timestamps in:
```ts
interface Timestamps { createdAt: Date; updatedAt: Date; touch(): void; }

const createTimestamps = (): Timestamps => {
  let updatedAt = new Date();
  return {
    createdAt: new Date(),
    get updatedAt() { return updatedAt; },
    touch() { updatedAt = new Date(); }
  };
};

class Order {
  readonly timestamps = createTimestamps();
  constructor(public id: string, public total: number) {}
}
```

## Section 3: Composition Patterns in Practice

**Q9. What is the Mixin pattern, and how does it implement composition in TypeScript?**
A: A mixin is a function that takes a base class and returns an extended version of it — or, in the functional style, an object that contributes a set of methods. TypeScript supports both:
```ts
// TypeScript class mixin — augments a base class without a fixed hierarchy
type Constructor<T = {}> = new (...args: any[]) => T;

function Serializable<TBase extends Constructor>(Base: TBase) {
  return class extends Base {
    serialize(): string { return JSON.stringify(this); }
    static deserialize(data: string) { return JSON.parse(data); }
  };
}

function Validatable<TBase extends Constructor>(Base: TBase) {
  return class extends Base {
    validate(): boolean { return true; } // override in concrete class
  };
}

class BaseModel { constructor(public id: string) {} }

// Compose behaviours onto BaseModel without a deep hierarchy
class Order extends Serializable(Validatable(BaseModel)) {
  constructor(id: string, public total: number) { super(id); }
  validate() { return this.total > 0; }
}

const order = new Order("1", 100);
order.serialize();  // ✓
order.validate();   // ✓
```
Class mixins use inheritance mechanics under the hood, but the *design intent* is compositional — behaviours are independent units plugged in rather than a rigid parent–child relationship.

**Q10. How does the Strategy pattern implement composition over inheritance?**
A: Strategy replaces a subclass hierarchy (where each subclass overrides a method to provide a different algorithm) with a composed object that holds the algorithm as a replaceable dependency:
```ts
// Inheritance approach — fragile hierarchy, hard to combine strategies
class Sorter { sort(data: number[]): number[] { return data; } }
class BubbleSorter extends Sorter { sort(data: number[]) { /* bubble */ return data; } }
class QuickSorter  extends Sorter { sort(data: number[]) { /* quick  */ return data; } }

// Composition / Strategy approach — algorithm injected, swappable at runtime
interface SortStrategy { sort(data: number[]): number[]; }

const bubbleSort: SortStrategy = { sort: (data) => { /* bubble */ return data; } };
const quickSort:  SortStrategy = { sort: (data) => { /* quick  */ return data; } };

class DataProcessor {
  constructor(private strategy: SortStrategy) {}

  process(data: number[]): number[] {
    return this.strategy.sort(data);
  }

  setStrategy(strategy: SortStrategy) { this.strategy = strategy; } // swap at runtime
}

const processor = new DataProcessor(quickSort);
processor.process([3, 1, 2]);

// Switch strategy without touching DataProcessor
processor.setStrategy(bubbleSort);
```
Adding a merge sort requires zero changes to `DataProcessor` — open for extension (new `SortStrategy` implementation), closed for modification.

**Q11. How does the Decorator pattern use composition instead of inheritance to extend behaviour?**
A: The Decorator pattern wraps an object in another object that shares its interface, adding behaviour before or after delegating to the wrapped instance — all without subclassing:
```ts
interface Logger {
  log(message: string): void;
}

class ConsoleLogger implements Logger {
  log(message: string) { console.log(message); }
}

// Decorator — composes Logger, adds timestamp without extending ConsoleLogger
class TimestampLogger implements Logger {
  constructor(private inner: Logger) {}
  log(message: string) {
    this.inner.log(`[${new Date().toISOString()}] ${message}`);
  }
}

// Decorator — composes Logger, adds log level
class LevelLogger implements Logger {
  constructor(private inner: Logger, private level: string) {}
  log(message: string) {
    this.inner.log(`[${this.level}] ${message}`);
  }
}

// Stack decorators freely — no inheritance hierarchy
const logger = new LevelLogger(new TimestampLogger(new ConsoleLogger()), "ERROR");
logger.log("Something broke");
// → [ERROR] [2026-01-15T10:00:00.000Z] Something broke
```
Adding a `JsonLogger` or `FileLogger` decorator requires zero changes to any existing class. Inheritance would require a new branch in a growing tree; composition adds a new leaf that plugs in anywhere.

**Q12. How does composition over inheritance apply to React component design?**
A: React was explicitly designed around composition. The React team deprecated the mixin API early and instead built composition primitives:

```tsx
// Inheritance — wrong grain for React (rare, reserved for error boundaries)
class EnhancedButton extends Button { /* fighting React's model */ }

// Composition patterns in React:

// 1. Children prop — content injection
const Card = ({ children, title }: { children: React.ReactNode; title: string }) => (
  <div className="card">
    <h2>{title}</h2>
    {children}
  </div>
);

// 2. Render props — behaviour injection
const MouseTracker = ({ render }: { render: (pos: { x: number; y: number }) => React.ReactNode }) => {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return <div onMouseMove={e => setPos({ x: e.clientX, y: e.clientY })}>{render(pos)}</div>;
};

// 3. Higher-Order Components — wrapper composition
const withAuth = <P extends object>(Component: React.ComponentType<P>) =>
  (props: P) => isAuthenticated() ? <Component {...props} /> : <Redirect to="/login" />;

// 4. Custom hooks — logic composition (the modern idiomatic approach)
const useMousePosition = () => {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  useEffect(() => {
    const handler = (e: MouseEvent) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener("mousemove", handler);
    return () => window.removeEventListener("mousemove", handler);
  }, []);
  return pos;
};

// Compose hooks — no class hierarchy, no mixins
const Dashboard = () => {
  const pos    = useMousePosition();   // composed in
  const user   = useCurrentUser();     // composed in
  const theme  = useTheme();           // composed in
  return <div style={{ color: theme.primary }}>{user.name} at {pos.x},{pos.y}</div>;
};
```

**Q13. How does composition over inheritance apply to the Repository and Service layer patterns?**
A: A service with many responsibilities should compose specialised collaborators rather than extend a base service class:
```ts
// Inheritance anti-pattern — behaviour reuse via base class
class BaseService {
  protected logger: Logger;
  protected eventBus: EventBus;
  protected cache: Cache;
  constructor() {
    this.logger   = new ConsoleLogger();  // hardcoded ✗
    this.eventBus = new RabbitMQBus();    // hardcoded ✗
    this.cache    = new RedisCache();     // hardcoded ✗
  }
}
class OrderService extends BaseService { /* inherits all three whether it needs them or not */ }
class UserService  extends BaseService { /* same */ }

// Composition — each service receives only what it needs
class OrderService {
  constructor(
    private repo:     OrderRepository,
    private payment:  PaymentGateway,
    private logger:   Logger,
    private eventBus: EventBus
  ) {}
  // no cache — because OrderService doesn't need it; not forced to have it
}

class UserService {
  constructor(
    private repo:   UserRepository,
    private cache:  Cache,
    private mailer: EmailService
  ) {}
  // no eventBus — because UserService doesn't need it
}
```
Each service is independently testable with minimal fakes. No service is burdened with dependencies it doesn't use.

## Section 4: Advanced Composition Techniques

**Q14. What is "functional composition," and how does it relate to this principle?**
A: Functional composition is the practice of building complex behaviour by combining small, single-purpose functions — the functional programming equivalent of object composition:
```ts
// Small, single-purpose functions
const trim      = (s: string) => s.trim();
const lowercase = (s: string) => s.toLowerCase();
const removeSpaces = (s: string) => s.replace(/\s+/g, "-");

// Manual composition
const slugify = (s: string) => removeSpaces(lowercase(trim(s)));

// Generic compose utility — right-to-left
const compose = <T>(...fns: Array<(x: T) => T>) =>
  (x: T): T => fns.reduceRight((acc, fn) => fn(acc), x);

// Generic pipe utility — left-to-right (more readable)
const pipe = <T>(...fns: Array<(x: T) => T>) =>
  (x: T): T => fns.reduce((acc, fn) => fn(acc), x);

const slugify2 = pipe(trim, lowercase, removeSpaces);

slugify2("  Hello World  "); // "hello-world"
```
Each function is independently testable, reusable, and composable in any order. No class, no inheritance. Adding `encodeURIComponent` to the pipeline is one argument to `pipe` — no class modification.

**Q15. What are "traits" or "protocol composition" in TypeScript, and how do they differ from inheritance?**
A: TypeScript supports interface intersection (`&`) to compose types — often called "traits" informally. Unlike inheritance, type intersections are purely structural and don't create a runtime hierarchy:
```ts
// Traits via interface intersection
interface Printable  { print(): void; }
interface Exportable { export(format: string): Buffer; }
interface Auditable  { auditLog(): AuditEntry[]; }

// A type that composes all three traits — no class hierarchy
type PrintableExportableReport = Printable & Exportable & Auditable;

// Concrete implementation satisfies all three by shape — no extends chain
class SalesReport implements Printable, Exportable, Auditable {
  print()                    { /* ... */ }
  export(format: string)     { /* ... */ return Buffer.from(""); }
  auditLog(): AuditEntry[]   { /* ... */ return []; }
}

// A function that accepts any object satisfying a composed trait
function archiveReport(report: Exportable & Auditable): void {
  const data  = report.export("pdf");
  const trail = report.auditLog();
  // store data and trail
}

// Works — SalesReport satisfies both
archiveReport(new SalesReport());
```
You can add, remove, or rearrange traits without touching the class hierarchy. Adding a `Schedulable` trait to `archiveReport`'s parameter type requires no changes to `SalesReport` — it either has `schedule()` or it doesn't.

**Q16. How does composition over inheritance apply to error handling design?**
A: A common inheritance misuse is a deep error hierarchy. Composition flattens it:
```ts
// Inheritance — deep error hierarchy, fragile
class AppError    extends Error {}
class HttpError   extends AppError { constructor(public status: number, msg: string) { super(msg); } }
class NotFoundError extends HttpError { constructor(msg: string) { super(404, msg); } }
class AuthError    extends HttpError { constructor(msg: string) { super(401, msg); } }
// Adding ValidationError that is BOTH an HttpError AND has field details requires multiple inheritance — impossible

// Composition — errors as data
interface AppError {
  message:   string;
  code:      string;
  httpStatus?: number;
  fields?:   Record<string, string>;  // for validation errors
  cause?:    unknown;
}

// Factory functions compose the error shape needed
const notFoundError = (resource: string): AppError => ({
  message:   `${resource} not found`,
  code:      "NOT_FOUND",
  httpStatus: 404,
});

const validationError = (fields: Record<string, string>): AppError => ({
  message:   "Validation failed",
  code:      "VALIDATION_ERROR",
  httpStatus: 422,
  fields,
});

// A "validation error that is also an auth error" is just an object — no hierarchy conflict
const composedError: AppError = {
  message:   "Unauthorized and invalid",
  code:      "AUTH_VALIDATION",
  httpStatus: 401,
  fields:    { token: "expired" },
};
```

## Section 5: Pitfalls, Anti-Patterns & Misapplications

**Q17. What is the "yo-yo problem," and how does deep inheritance cause it?**
A: The yo-yo problem (also called the yo-yo effect) occurs in deep inheritance hierarchies where understanding a method's behaviour requires bouncing up and down the inheritance chain — from subclass to parent to grandparent and back:
```
UserService
  └── AuthenticatedService
        └── CachedService
              └── LoggingService
                    └── BaseService
```
To understand what `UserService.findUser()` does, a developer must trace: does `UserService` override it? Does `AuthenticatedService`? Does `CachedService` intercept it via `super`? The call chain is a yo-yo through five levels. With composition, `UserService`'s behaviour is flat — its collaborators are listed in its constructor and their behaviour is independently readable.

**Q18. When is "composition over inheritance" the wrong advice?**
A: The principle is a guideline, not a law. Inheritance is correct when:
- **Framework extension points** — `class MyMigration extends Migration`, `class AppController extends Controller`. The framework author designed the base class as an explicit extension point with documented hooks.
- **Genuine taxonomic hierarchies** — `ElectricCar extends Car extends Vehicle` when the domain model genuinely has this structure and LSP holds throughout.
- **Sharing state with access control** — protected fields in a parent class give subclasses access to internal state in a controlled way that composition cannot replicate without exposing that state publicly.
- **Polymorphism via type identity** — `instanceof` checks (though usually a smell) and `catch (e: HttpError)` blocks need a real class hierarchy to function.

The pragmatic rule: use inheritance when a framework or language feature demands it, or when LSP holds cleanly. Otherwise, compose.

**Q19. What is "composition hell," and how do you avoid it?**
A: Composition hell is when an object is assembled from so many small, granular components that the wiring becomes incomprehensible — the compositional equivalent of constructor over-injection:
```ts
// Composition hell — too many fine-grained pieces with no semantic grouping
const orderService = new OrderService(
  new PrismaOrderRepository(db),
  new StripePaymentGateway(stripeKey),
  new SendGridEmailService(sgKey),
  new TwilioSMSService(twilioKey),
  new RedisCache(redisClient),
  new RabbitMQEventBus(rabbitConn),
  new WinstonLogger(logConfig),
  new DatadogMetrics(ddKey),
  new CircuitBreaker(cbConfig),
  new RetryPolicy(retryConfig),
);
```
Mitigations:
- **Group related components into façades** — `NotificationService` composes `EmailService + SMSService`; inject `NotificationService` instead of both.
- **Use an IoC container** — automatic resolution hides the wiring complexity.
- **Apply the Single Responsibility Principle** — if wiring is this complex, the class has too many responsibilities and needs to be split.
- **Factory / builder functions** — encapsulate the assembly in a named function: `buildOrderService(config): OrderService`.

**Q20. How does composition over inheritance interact with TypeScript's type system?**
A: TypeScript's structural typing and generics make composition elegant and type-safe:
- **Intersection types (`&`)** compose contracts: `type Admin = User & { adminLevel: number }`.
- **Generics with constraints** let composed pieces remain type-safe without inheritance: `function withLogging<T extends { name: string }>(target: T): T & Loggable`.
- **Conditional types and mapped types** let you compose type transformations: `Partial<T>`, `Readonly<T>`, `Pick<T, K>`.
- **Discriminated unions** compose variant types without class hierarchies: `type Shape = Circle | Square | Triangle`.

```ts
// Discriminated union — composed variant without inheritance
type Circle   = { kind: "circle";   radius: number };
type Square   = { kind: "square";   side: number };
type Triangle = { kind: "triangle"; base: number; height: number };
type Shape    = Circle | Square | Triangle;

const area = (shape: Shape): number => {
  switch (shape.kind) {
    case "circle":   return Math.PI * shape.radius ** 2;
    case "square":   return shape.side ** 2;
    case "triangle": return 0.5 * shape.base * shape.height;
  }
};
// Adding Rectangle = one new type union member + one new case. No base class touched.
```

## Section 6: Scenario / System Design Style Questions

**Q21. "A junior dev modelled the permission system as: `User extends BaseUser`, `AdminUser extends User`, `SuperAdminUser extends AdminUser`. You're reviewing this PR. What do you say?"**
A: Several concerns to raise:

1. **Hierarchy inflexibility** — what happens when a user needs to be both an `AdminUser` for one team and a regular `User` for another? The inheritance hierarchy can't express this; composition can: a `User` *has* a set of `Role` objects, each with their own permissions.
2. **LSP risk** — is every `AdminUser` truly substitutable for `User` in every context? If `AdminUser.delete()` does something a plain `User.delete()` doesn't, callers treating it as a `User` get unexpected behaviour.
3. **Behavioural coupling** — a bug fix in `BaseUser` silently affects `AdminUser` and `SuperAdminUser`. In a permission system, that's a security risk.
4. **Suggested redesign**:
```ts
interface Permission { name: string; check(context: AuthContext): boolean; }

class User {
  constructor(
    public id: string,
    public email: string,
    private roles: Role[]  // composed — a User *has* roles
  ) {}

  can(permission: string, context: AuthContext): boolean {
    return this.roles.some(r => r.hasPermission(permission, context));
  }
}

class Role {
  constructor(public name: string, private permissions: Permission[]) {}
  hasPermission(name: string, context: AuthContext): boolean {
    return this.permissions.some(p => p.name === name && p.check(context));
  }
}

// Assigning admin is a data operation, not a type change
const adminUser = new User("1", "admin@co.com", [adminRole, userRole]);
```
Adding a new role type is a new `Role` instance — zero class changes.

**Q22. "A codebase has `PdfExporter extends BaseExporter`, `CsvExporter extends BaseExporter`, `ExcelExporter extends BaseExporter`. `BaseExporter` has grown to 400 lines and now every new export format requires overriding 6 methods. How do you refactor this?"**
A: Classic fragile base class + inheritance-for-reuse problem. Refactor in phases:

1. **Identify what varies** — the format-specific serialisation logic varies; the common pipeline (fetch data → transform → write output → notify) does not.
2. **Extract the pipeline as a composition** — use the Template Method pattern *or* replace it with explicit composition:
```ts
// What varies — each format provides its own serialiser
interface DataSerializer {
  serialize(data: ExportData): Buffer;
  mimeType(): string;
  fileExtension(): string;
}

// Concrete serialisers — small, focused, independently testable
class PdfSerializer  implements DataSerializer { /* ... */ }
class CsvSerializer  implements DataSerializer { /* ... */ }
class ExcelSerializer implements DataSerializer { /* ... */ }

// Pipeline — composed, not inherited
class Exporter {
  constructor(
    private dataSource: DataSource,
    private serializer: DataSerializer,
    private storage:    StorageService,
    private notifier:   NotificationService
  ) {}

  async export(query: ExportQuery): Promise<ExportResult> {
    const data   = await this.dataSource.fetch(query);
    const buffer = this.serializer.serialize(data);
    const url    = await this.storage.upload(buffer, this.serializer.fileExtension());
    await this.notifier.notify(url);
    return { url, mimeType: this.serializer.mimeType() };
  }
}

// Composition root — assemble per format
const pdfExporter   = new Exporter(dbSource, new PdfSerializer(),   s3, emailNotifier);
const csvExporter   = new Exporter(dbSource, new CsvSerializer(),   s3, emailNotifier);
const excelExporter = new Exporter(dbSource, new ExcelSerializer(), s3, emailNotifier);
```
Adding a new format is a new `DataSerializer` class — `Exporter`, `StorageService`, and `NotificationService` are untouched.

**Q23. "Your team is building a game with character classes: Warrior, Mage, Rogue. A junior dev proposes `Warrior extends Character`, `Mage extends Character`, `Rogue extends Character`. Then the product asks for a `WarriorMage` hybrid. How do you redesign with composition?"**
A: The hybrid class is the canonical argument against rigid inheritance hierarchies in game design:
```ts
// Abilities as independent composable units
interface Ability { use(context: CombatContext): AbilityResult; }

const swordAttack: Ability = {
  use: ({ target }) => ({ damage: 50, type: "physical", target })
};
const fireball: Ability = {
  use: ({ target }) => ({ damage: 80, type: "magical",  target })
};
const stealth: Ability = {
  use: ({ target }) => ({ damage: 30, type: "physical", stealth: true, target })
};

// Stats as composable data
interface StatBlock { health: number; mana: number; strength: number; intelligence: number; }

// Character assembled from abilities + stats — no hierarchy
class Character {
  constructor(
    public name:     string,
    public stats:    StatBlock,
    public abilities: Ability[]
  ) {}

  useAbility(index: number, context: CombatContext): AbilityResult {
    return this.abilities[index].use(context);
  }
}

// Composition root — mix and match freely
const warrior     = new Character("Thor",  warriorStats,  [swordAttack]);
const mage        = new Character("Merlin", mageStats,    [fireball]);
const warriorMage = new Character("Gandalf", hybridStats, [swordAttack, fireball]); // trivial
const rogue       = new Character("Bilbo",  rogueStats,  [stealth, swordAttack]);
```
No inheritance tree. Adding a `poisonDagger` ability is a new `Ability` object — no class changes. The `WarriorMage` is assembled in one line at the composition root.

**Q24. "You're architecting a plugin system where third-party developers extend your application. Should you offer base classes to extend, or interfaces to implement? What are the trade-offs?"**
A: Both have legitimate roles, but the defaults should differ:

| | Base class (inheritance) | Interface (composition) |
|---|---|---|
| **Coupling** | Plugin author coupled to your base class internals | Plugin author coupled only to the contract |
| **Versioning** | Adding a method to the base class is a breaking change for all plugins | Adding a method to an interface can be managed with optional methods or versioned interfaces |
| **Defaults** | Can provide default implementations — reduces boilerplate | No defaults (unless using abstract class or providing a helper factory) |
| **Flexibility** | Plugin can only extend one base class | Plugin can implement multiple interfaces and compose freely |
| **Discoverability** | Base class documents the extension points visually | Interface requires reading docs to know what's possible |

**Recommended pattern** — offer both: an interface for the contract (required), plus an optional abstract base class that provides sensible no-op defaults for optional methods (like Java's `MouseAdapter`). Plugin authors who want full control implement the interface; those who want convenience extend the base class. The system always depends on the *interface*, never the base class:
```ts
interface Plugin {
  name: string;
  init(context: PluginContext): void;
  onEvent?(event: AppEvent): void;   // optional
  teardown?(): void;                 // optional
}

// Convenience base — not required, just helpful
abstract class BasePlugin implements Plugin {
  abstract name: string;
  abstract init(context: PluginContext): void;
  onEvent(_event: AppEvent)  { /* no-op default */ }
  teardown()                 { /* no-op default */ }
}
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Inheritance | Composition |
|---|---|---|
| Relationship modelled | is-a | has-a / uses-a |
| Coupling | Tight — compile-time, structural | Loose — through interfaces / function shapes |
| Code reuse mechanism | Inheriting parent methods | Delegating to collaborator objects |
| Flexibility | Low — hierarchy fixed at design time | High — components swappable at runtime |
| Encapsulation | Weak — subclasses see protected internals | Strong — collaborator is a black box |
| Testability | Lower — must test with real parent | Higher — inject fakes per component |
| Multiple behaviours | Hard — single-inheritance constraint | Easy — compose as many components as needed |
| Change impact | High — parent change ripples to all subclasses | Low — change isolated to the component |
| TypeScript expression | `class A extends B` | Constructor injection, mixins, intersection types, HOFs |
| When to prefer | Framework hooks, true is-a, LSP holds | Default for everything else |

## Composition Patterns at a Glance

| Pattern | Composition mechanism | Problem solved |
|---|---|---|
| **Strategy** | Inject interchangeable algorithm object | Replace if-else / subclass-per-algorithm |
| **Decorator** | Wrap object in same-interface wrapper | Add behaviour without modifying the wrapped class |
| **Mixin** | Augment class with behaviour functions | Share cross-cutting behaviour without a hierarchy |
| **Higher-Order Function** | Wrap function in another function | Add behaviour (logging, auth, retry) to functions |
| **Custom Hook (React)** | Compose stateful logic via hook functions | Share stateful behaviour across components |
| **Higher-Order Component** | Wrap component in a component | Cross-cutting UI concerns (auth, theming, error boundary) |
| **Factory / Builder** | Assemble object graph at composition root | Complex wiring without coupling call sites to concretions |
| **Discriminated Union** | Compose variant types as a union | Model variants without class hierarchy |

**Tip for the interview:** At the 5 YOE level, "composition over inheritance" never arrives as a definition question — it surfaces as: why is this `BaseService` with 400 lines a problem, how would you design a permission system that doesn't break when roles are combined, why is this React HOC chain hard to test, or how do you add a new export format without touching existing code. The sharp answer names the specific inheritance failure (fragile base class, yo-yo problem, single-inheritance constraint), proposes a concrete composition alternative (Strategy, Decorator, hook composition, factory assembly), and traces exactly how the new design handles the change that broke the old one. That concreteness — "here's the old code, here's where it fails, here's the composed replacement" — is what lands at 5 YOE.
