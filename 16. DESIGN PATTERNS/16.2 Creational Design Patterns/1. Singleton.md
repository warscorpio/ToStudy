# Creational Design Patterns: Singleton — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Singleton pattern?**
A: Singleton is a creational design pattern that ensures a class has **exactly one instance** for the lifetime of the application and provides a **global access point** to that instance. It solves two problems simultaneously: controlling instantiation (only one object is ever created) and providing centralized access (any part of the codebase can reach it without passing the object around). The canonical implementation lazily creates the instance on first access and returns the same object on every subsequent call.

**Q2. What are the two core guarantees a Singleton must provide?**
A:
- **Single instance** — no matter how many times the class is "constructed," only one object exists in memory. All callers share the same state.
- **Global access point** — the instance is reachable through a static method or property (e.g., `getInstance()`) without the caller needing a reference passed to it explicitly.

Both are required. A class that's only ever instantiated once by convention — but could be instantiated again — is not a Singleton. A class with a global variable that holds one instance — but allows constructing more — is not a Singleton either.

**Q3. When should you reach for a Singleton?**
A: Singleton is appropriate when:
- A resource is **expensive to create** and should be shared — database connection pools, HTTP client pools, thread pools.
- There must be **exactly one coordinator** for a shared resource — a config registry, a logging manager, an in-process event bus.
- **State must be centralized** — a feature-flag store, an in-memory cache, a rate-limiter counter.

It is *not* appropriate when the "one instance" requirement is just a convenience or assumption — using Singleton there creates hidden coupling and testing pain without a genuine architectural need.

**Q4. How does Singleton differ from a global variable?**
A: They're related but not equivalent:

| Aspect                      | Global Variable                     | Singleton                              |
|-----------------------------|--------------------------------------|----------------------------------------|
| Instantiation control       | None — value set externally          | Controlled internally by the class     |
| Lazy initialization         | Rarely                               | Typically yes — created on first access |
| Encapsulation               | None — any code can reassign it      | Class controls access via `getInstance()` |
| Interface / subclassability | No                                   | Can implement an interface, be subclassed |
| Testability                 | Hard to swap                         | Slightly better — can use interface + DI |

A global variable is just a variable. A Singleton is a class that *governs* its own instantiation — the pattern adds structure and intent around what is effectively a managed global.

**Q5. What is lazy vs. eager initialization in a Singleton, and when does it matter?**
A: 
- **Eager initialization** — the instance is created when the class is loaded, regardless of whether it's ever used. Simple and thread-safe in languages where class loading is atomic, but wastes resources if the instance is never needed.
- **Lazy initialization** — the instance is created on first access. Saves resources but requires care in multithreaded environments to prevent race conditions where two threads simultaneously see `null` and each create an instance.

In a Node.js context (single-threaded event loop), lazy initialization is naturally safe — there's no race between threads. In Java or C++ (true multithreading), lazy Singletons need double-checked locking or other synchronization.

## Section 2: Implementation Patterns

**Q6. What does a basic TypeScript Singleton implementation look like?**
A: The classic pattern:

```typescript
class ConfigManager {
  private static instance: ConfigManager | null = null;
  private config: Record<string, string> = {};

  // Private constructor — prevents external `new ConfigManager()`
  private constructor() {
    this.config = this.loadFromEnv();
  }

  static getInstance(): ConfigManager {
    if (!ConfigManager.instance) {
      ConfigManager.instance = new ConfigManager();
    }
    return ConfigManager.instance;
  }

  get(key: string): string | undefined {
    return this.config[key];
  }

  private loadFromEnv(): Record<string, string> {
    return {
      DB_HOST: process.env.DB_HOST ?? 'localhost',
      DB_PORT: process.env.DB_PORT ?? '5432',
    };
  }
}

// Usage
const config = ConfigManager.getInstance();
console.log(config.get('DB_HOST')); // 'localhost'

// Same instance — no second object created
const config2 = ConfigManager.getInstance();
console.log(config === config2); // true
```

The `private constructor` is the critical guard — TypeScript enforces at compile time that no external code can call `new ConfigManager()`.

**Q7. How do ES modules give you a "free" Singleton in Node.js?**
A: Node's CommonJS and ES module systems cache the result of a `require()` / `import` after the first load. Every subsequent import of the same module returns the exact same module object from the cache — no re-execution. This means a module-level exported instance is already a Singleton:

```typescript
// db-pool.ts — module-level Singleton via ES module caching
import { Pool } from 'pg';

const pool = new Pool({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT),
  database: process.env.DB_NAME,
  max: 10,
});

export default pool;
```

```typescript
// loan.service.ts
import pool from './db-pool'; // always the same Pool instance

// credit-bureau.service.ts
import pool from './db-pool'; // same object — no second Pool created
```

This is idiomatic Node.js for singletons. The module itself is the `getInstance()` mechanism. No class, no static method needed. This pattern is widely used for database pools, HTTP client instances, and logger objects.

**Q8. How does NestJS handle Singleton scope, and what is the default injection scope?**
A: In NestJS, every provider registered in a module is a **Singleton by default** — the DI container creates one instance per module and reuses it for the entire application lifetime. This is the `DEFAULT` (singleton) scope:

```typescript
// Explicitly singleton (same as default — no decorator needed)
@Injectable({ scope: Scope.DEFAULT })
export class CreditBureauService {
  // One instance shared across all controllers and services that inject it
}
```

NestJS also provides two non-singleton scopes:
- **`Scope.REQUEST`** — a new instance per incoming HTTP request. Useful when the service needs to hold per-request context (e.g., tenant ID, user ID from JWT).
- **`Scope.TRANSIENT`** — a new instance every time it is injected. Rare; useful for stateful utilities that must not share state between consumers.

Understanding this distinction matters in interviews: NestJS's DI system *is* the Singleton management layer — you rarely implement the classic Singleton pattern by hand in a NestJS app.

**Q9. What are the pitfalls of request-scoped vs singleton-scoped providers in NestJS?**
A: A critical subtlety — scope bubbles upward:

```typescript
@Injectable({ scope: Scope.REQUEST })
export class TenantContextService {
  tenantId: string;
}

// If LoanService injects TenantContextService,
// LoanService is FORCED to become REQUEST-scoped too.
// This cascades up the dependency tree.
@Injectable()
export class LoanService {
  constructor(private readonly tenant: TenantContextService) {}
  // NestJS will make this REQUEST-scoped implicitly
}
```

The footgun: a singleton service (e.g., a cached `RateLimiterService`) that accidentally depends on a request-scoped provider gets re-instantiated per request, destroying the singleton guarantee. Always audit scope when adding dependencies, especially in high-throughput fintech services where singleton services hold shared state (rate limiter counters, connection pools).

**Q10. How do you implement a thread-safe Singleton in environments with true parallelism (Java/Go comparison)?**
A: In Node.js this isn't a concern (single-threaded), but it's a common interview follow-up. In Java the double-checked locking pattern is the standard approach:

```java
// Java — double-checked locking
public class ConnectionPool {
  private static volatile ConnectionPool instance;

  private ConnectionPool() {}

  public static ConnectionPool getInstance() {
    if (instance == null) {                    // First check (no lock)
      synchronized (ConnectionPool.class) {
        if (instance == null) {                // Second check (with lock)
          instance = new ConnectionPool();
        }
      }
    }
    return instance;
  }
}
```

The `volatile` keyword prevents CPU instruction reordering. The outer null-check avoids acquiring the lock on every call (performance). The inner null-check prevents a second thread that was waiting on the lock from creating a second instance once it enters. In Node.js, none of this is necessary — the event loop serializes all JavaScript execution.

## Section 3: Singleton in Real-World Fintech Contexts

**Q11. What real components in a lending platform are naturally Singleton-scoped?**
A: In a NestJS/TypeScript lending backend, these are canonical Singleton candidates:

| Component                         | Why Singleton                                                                 |
|-----------------------------------|-------------------------------------------------------------------------------|
| PostgreSQL connection pool (`pg.Pool`) | Creating a pool per request exhausts DB connections; one pool, shared globally |
| Redis client (`ioredis`)          | One persistent TCP connection, multiplexed across all callers                 |
| CIBIL/Experian HTTP client        | Connection pooling, retry config, circuit breaker state — shared              |
| `ConfigService` (NestJS built-in) | One source of truth for environment config across all services                |
| Logger (`winston`, `pino`)        | Log transport streams, formatters, and file handles are expensive to open per-instance |
| Feature flag client               | Polls remote config; one polling loop, shared flag state                      |
| `JwtService`                      | Stateless utility — no need for multiple instances; NestJS makes it singleton by default |
| AWS SDK clients (`S3Client`, etc.)| Credential caching and connection reuse happen at the client level            |

**Q12. How does Singleton interact with connection pool management for PostgreSQL in a high-throughput loan processing system?**
A: The `pg.Pool` is the textbook Singleton use case. Creating a new pool per request would:
- Open up to `N` connections per request (where `N` is pool `max`), exhausting Postgres's `max_connections` limit instantly under load.
- Incur TCP handshake + TLS overhead on every request.
- Leak connections when requests complete and pools aren't explicitly destroyed.

The correct pattern — one pool for the process lifetime:

```typescript
// database.module.ts — pool registered as a singleton provider
@Module({
  providers: [
    {
      provide: 'PG_POOL',
      useFactory: () =>
        new Pool({
          host: process.env.DB_HOST,
          database: process.env.DB_NAME,
          max: 20,                   // shared across all requests
          idleTimeoutMillis: 30000,
          connectionTimeoutMillis: 2000,
        }),
    },
  ],
  exports: ['PG_POOL'],
})
export class DatabaseModule {}
```

```typescript
// loan.repository.ts — injects the shared pool
@Injectable()
export class LoanRepository {
  constructor(@Inject('PG_POOL') private readonly pool: Pool) {}

  async findById(id: string): Promise<Loan> {
    const { rows } = await this.pool.query(
      'SELECT * FROM loans WHERE id = $1',
      [id],
    );
    return rows[0];
  }
}
```

All repositories share the same 20-connection pool. Postgres sees 20 connections from the service, not 20 × number-of-requests.

**Q13. How would you use the Singleton pattern to implement an in-process rate limiter for CIBIL API calls?**
A: Bureau APIs like CIBIL typically have per-second or per-minute rate limits. A Singleton rate limiter maintains a shared counter:

```typescript
@Injectable() // Singleton by default in NestJS
export class CibilRateLimiterService {
  private readonly maxCallsPerMinute = 100;
  private callTimestamps: number[] = [];

  canCall(): boolean {
    const now = Date.now();
    const oneMinuteAgo = now - 60_000;

    // Evict timestamps older than 1 minute
    this.callTimestamps = this.callTimestamps.filter(ts => ts > oneMinuteAgo);

    if (this.callTimestamps.length >= this.maxCallsPerMinute) {
      return false;
    }

    this.callTimestamps.push(now);
    return true;
  }
}

@Injectable()
export class CreditBureauService {
  constructor(
    private readonly rateLimiter: CibilRateLimiterService,
    private readonly httpClient: HttpService,
  ) {}

  async fetchReport(pan: string): Promise<BureauReport> {
    if (!this.rateLimiter.canCall()) {
      throw new TooManyRequestsException('CIBIL rate limit reached');
    }
    return this.httpClient.axiosRef.get(`/report/${pan}`).then(r => r.data);
  }
}
```

Because `CibilRateLimiterService` is a NestJS singleton, `callTimestamps` is shared across all concurrent requests. If it were request-scoped, every request would start with an empty counter and the rate limit would be meaningless.

**Q14. How do you handle Singleton state in a multi-instance (horizontally scaled) deployment?**
A: This is a critical production concern often missed in interviews. In-process Singletons only guarantee one instance *per Node.js process*. On AWS ECS, Kubernetes, or any horizontally scaled deployment, you have multiple processes — each with its own Singleton instance and its own copy of the state.

```
Pod 1: CibilRateLimiterService.callTimestamps = [t1, t2, t3...]  // 50 calls
Pod 2: CibilRateLimiterService.callTimestamps = [t1, t2, t3...]  // 50 calls
Total calls to CIBIL API: 100 — but each pod thinks it's only made 50
```

Solutions:
- **Externalize shared state to Redis** — use `ioredis` to store and atomically increment rate-limit counters with TTL. The Redis client itself is a Singleton, but the state it holds is distributed.
- **Sticky sessions** — route all requests for a given tenant/loan to the same pod (viable but operationally fragile).
- **Centralized rate-limiting service** — a dedicated microservice or API gateway layer (AWS API Gateway throttling, Kong, Nginx rate-limit module).

```typescript
// Distributed rate limiter via Redis Singleton
@Injectable()
export class DistributedRateLimiterService {
  constructor(@InjectRedis() private readonly redis: Redis) {}

  async canCall(key: string, limit: number, windowSeconds: number): Promise<boolean> {
    const count = await this.redis.incr(key);
    if (count === 1) await this.redis.expire(key, windowSeconds);
    return count <= limit;
  }
}
```

## Section 4: Testing Singletons

**Q15. Why are Singletons notoriously hard to unit test, and how do you mitigate it?**
A: The root problem: Singleton state **persists across tests**. If `ConfigManager.getInstance()` is called in test A and mutates config, test B sees that mutated state — producing order-dependent, flaky tests.

Three mitigation strategies:

**1. Reset method (for test environments only):**
```typescript
class ConfigManager {
  private static instance: ConfigManager | null = null;

  static getInstance(): ConfigManager {
    if (!ConfigManager.instance) {
      ConfigManager.instance = new ConfigManager();
    }
    return ConfigManager.instance;
  }

  // Only used in tests — resets the singleton for a clean slate
  static reset(): void {
    ConfigManager.instance = null;
  }
}

// In tests
afterEach(() => ConfigManager.reset());
```

**2. Dependency injection (preferred) — never reference the Singleton directly:**
```typescript
// Instead of calling ConfigManager.getInstance() inside a service,
// inject it as a dependency — then swap it in tests

@Injectable()
export class LoanService {
  constructor(private readonly config: ConfigService) {} // injected, not getInstance()
}

// In test
const module = await Test.createTestingModule({
  providers: [
    LoanService,
    { provide: ConfigService, useValue: { get: jest.fn().mockReturnValue('test-value') } },
  ],
}).compile();
```

**3. Interface + implementation — mock the interface, not the Singleton:**
```typescript
interface IConfigService {
  get(key: string): string;
}

@Injectable()
class ConfigService implements IConfigService { ... }

// Tests inject a mock implementation of IConfigService
// The Singleton implementation never enters the test
```

NestJS's DI system makes option 2 and 3 natural — the framework's `Test.createTestingModule` is designed for exactly this.

**Q16. How do you test a NestJS service that depends on a Singleton-scoped provider?**
A: Replace the provider with a mock in the test module — NestJS DI handles the wiring:

```typescript
describe('CreditBureauService', () => {
  let service: CreditBureauService;
  let rateLimiter: jest.Mocked<CibilRateLimiterService>;

  beforeEach(async () => {
    const mockRateLimiter = {
      canCall: jest.fn().mockReturnValue(true),
    };

    const module = await Test.createTestingModule({
      providers: [
        CreditBureauService,
        { provide: CibilRateLimiterService, useValue: mockRateLimiter },
        { provide: HttpService, useValue: { axiosRef: { get: jest.fn() } } },
      ],
    }).compile();

    service = module.get(CreditBureauService);
    rateLimiter = module.get(CibilRateLimiterService);
  });

  it('should throw when rate limit is exceeded', async () => {
    rateLimiter.canCall.mockReturnValue(false);
    await expect(service.fetchReport('ABCDE1234F')).rejects.toThrow(TooManyRequestsException);
  });
});
```

The key insight: you're not testing the Singleton *pattern* — you're testing the *behavior* of `CreditBureauService`. NestJS DI means you inject a mock and the real Singleton never participates in the unit test.

## Section 5: Anti-patterns & Alternatives

**Q17. What are the primary criticisms of the Singleton pattern?**
A: Singleton is sometimes called an anti-pattern because:
- **Hidden global state** — any part of the codebase can access and mutate the Singleton, creating invisible coupling. Function signatures lie: `processLoan(dto)` may secretly read `ConfigManager.getInstance()` inside.
- **Tight coupling** — code that calls `ConfigManager.getInstance()` directly is coupled to the concrete class, making it hard to substitute a different implementation (e.g., a test config, an env-specific config).
- **Violated SRP** — the class manages both its primary responsibility *and* its own lifecycle/instantiation — two reasons to change.
- **Testing pain** — as discussed, shared mutable state bleeds across tests unless carefully reset.
- **Multi-instance environments** — the "single instance" guarantee breaks the moment you scale horizontally, which is the default in cloud-native deployments.

**Q18. What is the relationship between Singleton and the Dependency Inversion Principle? How does DI fix Singleton's problems?**
A: Singleton violates Dependency Inversion by making consumers reach *up* to a static class:

```typescript
// ❌ Violates DIP — LoanService depends on the concrete ConfigManager Singleton
class LoanService {
  applyForLoan(dto: LoanApplicationDto) {
    const maxAmount = ConfigManager.getInstance().get('MAX_LOAN_AMOUNT');
    // ...
  }
}
```

DI inverts this — dependencies are *pushed in* rather than *pulled out*:

```typescript
// ✅ DIP-compliant — LoanService depends on an abstraction, not the concrete Singleton
@Injectable()
class LoanService {
  constructor(private readonly config: ConfigService) {}

  applyForLoan(dto: LoanApplicationDto) {
    const maxAmount = this.config.get('MAX_LOAN_AMOUNT');
    // ...
  }
}
```

The DI container (NestJS) still creates one instance of `ConfigService` — it's still effectively a Singleton. But `LoanService` doesn't know or care about that. It depends on an interface, not a static accessor. This preserves testability and replaceability while retaining the memory/performance benefits of a single shared instance.

**Q19. When should you prefer a simple module-level export over a class-based Singleton?**
A: When the "singleton" is stateless or its state is entirely initialized at startup and never mutated:

```typescript
// ✅ Module-level export — simpler, cleaner, same guarantee
// logger.ts
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  transport: { target: 'pino-pretty' },
});
```

```typescript
// Use anywhere — same logger instance via module cache
import { logger } from './logger';
logger.info({ loanId }, 'Loan created');
```

Reserve the class-based Singleton for cases where:
- The instance needs lazy initialization (resource not available at module load time).
- The class has methods that mutate instance state (rate limiter counters, cache entries).
- You need to implement an interface for substitutability / testability.

## Section 6: Scenario / System Design Style Questions

**Q20. "You notice your NACH debit service is hitting the NPCI API way over the rate limit even though you have a `RateLimiterService`. How would you investigate?"**
A: Classic multi-instance Singleton failure. Investigation steps:
1. Check deployment config — how many pods/containers is the service running? If > 1, each has its own in-process `RateLimiterService` with its own counters.
2. Confirm the rate limiter is truly Singleton-scoped in NestJS (not accidentally `Scope.REQUEST` or `Scope.TRANSIENT`).
3. Check if there are multiple NestJS applications in the same repo sharing the same `RateLimiterService` class (monorepo scenario).
4. **Fix**: migrate the counter to Redis with atomic `INCR` + `EXPIRE`. The Redis client itself is a Singleton per process; the counter state is externalized and shared across all pods.
5. Optionally add API Gateway-level throttling (AWS API Gateway, Kong) as a hard backstop independent of application code.

**Q21. "A junior developer proposes using a Singleton to share the authenticated user's ID across service calls within a single request. How do you respond?"**
A: This is a well-known anti-pattern — using a Singleton as a request context store. The problems:
- In Node.js, the event loop interleaves multiple concurrent requests. A Singleton `userId` field is overwritten by whichever request runs last — leading to one user's request being processed with another user's identity (a serious security bug in a fintech context).
- The Singleton has no awareness of request boundaries; it can't know when to reset its state.

Correct alternatives:
- **`AsyncLocalStorage` (Node.js built-in)** — provides per-async-call storage that follows the async execution chain of a single request without leaking across concurrent ones. Use for request-scoped context like `userId`, `tenantId`, `correlationId`.
- **NestJS `REQUEST`-scoped provider** — inject an `ExecutionContext` or a custom `RequestContextService` with `Scope.REQUEST`. NestJS creates a fresh instance per request and disposes it when the request completes.

```typescript
// ✅ AsyncLocalStorage — correct way to share per-request context
import { AsyncLocalStorage } from 'async_hooks';

export const requestContext = new AsyncLocalStorage<{ userId: string; tenantId: string }>();

// Middleware — sets context at request entry
app.use((req, res, next) => {
  requestContext.run({ userId: req.user.id, tenantId: req.headers['x-tenant-id'] }, next);
});

// Anywhere in the async call chain — safe, per-request
const ctx = requestContext.getStore(); // { userId: '...', tenantId: '...' }
```

**Q22. "Design the connection management layer for a Node.js service that calls PostgreSQL, Redis, and the CIBIL bureau API. How do you structure these as Singletons?"**
A: Three distinct Singleton types — each justified differently:

```typescript
// 1. PostgreSQL — managed by pg.Pool (connection pooling is the reason)
@Module({
  providers: [{
    provide: 'PG_POOL',
    useFactory: () => new Pool({ max: 20, /* ... */ }),
  }],
  exports: ['PG_POOL'],
})
export class DatabaseModule {}

// 2. Redis — ioredis manages its own connection internally; one client = one connection
@Module({
  providers: [{
    provide: 'REDIS_CLIENT',
    useFactory: () => new Redis({ host: process.env.REDIS_HOST, lazyConnect: true }),
  }],
  exports: ['REDIS_CLIENT'],
})
export class CacheModule {}

// 3. CIBIL HTTP client — Singleton for connection reuse + shared circuit-breaker state
@Module({
  providers: [{
    provide: 'CIBIL_HTTP_CLIENT',
    useFactory: () => axios.create({
      baseURL: process.env.CIBIL_BASE_URL,
      timeout: 5000,
      httpAgent: new http.Agent({ keepAlive: true }),   // TCP connection reuse
      httpsAgent: new https.Agent({ keepAlive: true }), // TLS session reuse
    }),
  }],
  exports: ['CIBIL_HTTP_CLIENT'],
})
export class BureauModule {}
```

All three are registered as NestJS module providers — the DI container manages their singleton lifecycle, handles graceful shutdown, and makes them available for injection without any `getInstance()` ceremony.

## Quick Reference: Singleton Decision Checklist

| Question                                                              | If Yes → Singleton Candidate | If No → Reconsider      |
|-----------------------------------------------------------------------|-------------------------------|--------------------------|
| Is instantiation expensive (connection pools, network clients)?       | ✅ Strong candidate           |                          |
| Must exactly one coordinator exist (rate limiter, cache manager)?     | ✅ Strong candidate           |                          |
| Does the state need to be shared across concurrent requests?          | ✅ But externalize to Redis if multi-pod |                 |
| Is it a per-request concern (user context, tenant ID)?                |                               | ❌ Use AsyncLocalStorage or REQUEST scope |
| Is it stateless (can be re-created cheaply)?                         |                               | ❌ Use transient or factory |
| Will this service scale horizontally (multiple pods)?                 | ⚠️ External state store needed | Local Singleton is fine for ephemeral state |
| Can you inject it via DI instead of calling `getInstance()` directly? | ✅ Always prefer DI           | ❌ Static access = hidden coupling |

---

**Tip for the interview:** At the 5 YOE level, "implement a Singleton" is a throwaway question — the real depth is in *why and when*. Interviewers want to hear you distinguish between in-process Singletons (fine for one pod) and distributed state (Redis for multi-pod), explain why NestJS's default `Scope.DEFAULT` *is* the Singleton pattern done right with DI, and articulate the testing problems Singleton causes along with how DI and interface-based injection solve them. The senior differentiator is knowing that `AsyncLocalStorage` replaces the naïve "singleton as request context" anti-pattern — a mistake with real security consequences in a multi-tenant fintech system.
