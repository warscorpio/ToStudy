# Design Patterns — Structural: Dependency Injection & IoC Containers — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Dependency Injection?**
A: Dependency Injection (DI) is a technique where an object receives its dependencies from an external source rather than creating them itself. Instead of a class calling `new DatabaseService()` internally, the `DatabaseService` is *provided* (injected) to the class by whoever constructs it. The class declares what it needs; something else decides how to fulfill that need. DI is the practical application of the Dependency Inversion Principle (the D in SOLID): high-level modules should not depend on low-level modules — both should depend on abstractions.

**Q2. What problem does Dependency Injection solve?**
A: It solves the problem of *tight coupling* between a class and the concrete implementations it uses. When a class calls `new PaymentService()` internally, three things happen:
- It is permanently bound to `PaymentService` — you cannot swap it without editing the class.
- Testing becomes hard — you can't inject a mock without patching module internals.
- The class violates SRP — it now has two responsibilities: *doing its job* and *constructing its tools*.

DI separates those concerns: the class declares a dependency on a `PaymentService` abstraction; the construction and wiring happens outside the class. The result is code that is loosely coupled, easy to test (swap real implementations for mocks at injection time), and easy to extend (swap one implementation for another without touching the class).

**Q3. What is Inversion of Control (IoC)?**
A: Inversion of Control is the broader principle that the *control flow* of a program should be inverted from the traditional model. Traditionally, your code calls a library; with IoC, a framework calls your code. DI is one *specific form* of IoC — the control that's inverted is *object creation and wiring*. Instead of a class controlling how its dependencies are instantiated, that control is inverted to an external container or caller.

The Hollywood Principle captures it: *"Don't call us, we'll call you."* Your class doesn't reach out to create or find its dependencies — the framework reaches in and provides them.

**Q4. What is an IoC Container?**
A: An IoC Container (also called a DI Container) is a framework component that automates Dependency Injection at scale. Instead of manually wiring every dependency by hand, you register your classes and their dependencies with the container; the container resolves the full dependency graph and instantiates everything in the right order. Key responsibilities of a container:
- **Registration** — record which class satisfies which interface/token.
- **Resolution** — when asked for a type, recursively resolve all its dependencies and construct the object.
- **Lifetime management** — decide whether to create a new instance every time (transient), once per request (scoped), or once for the process lifetime (singleton).
- **Circular dependency detection** — identify and report when A depends on B which depends on A.

In Node.js/TypeScript: NestJS's built-in container, `tsyringe`, `inversify`. In Java: Spring, Guice. In .NET: built-in `Microsoft.Extensions.DependencyInjection`.

**Q5. What are the three types of Dependency Injection?**
A:
- **Constructor Injection** — dependencies are passed as constructor parameters. The class cannot be instantiated without them; dependencies are guaranteed to be present and immutable after construction. This is the preferred style — it makes dependencies explicit and supports immutability.
  ```ts
  class LoanService {
    constructor(
      private readonly repo: LoanRepository,
      private readonly notifier: NotificationService,
    ) {}
  }
  ```
- **Setter/Property Injection** — dependencies are set via setter methods or public properties after construction. Useful for optional dependencies or when constructor injection creates circular dependency issues. Riskier — the object is in an incomplete state between construction and injection.
  ```ts
  class LoanService {
    setRepository(repo: LoanRepository) { this.repo = repo; }
  }
  ```
- **Interface/Method Injection** — the dependency is passed as a method parameter at the call site, not stored on the object. Useful for dependencies that vary per-call rather than per-instance.
  ```ts
  class LoanService {
    processLoan(loan: Loan, gateway: PaymentGateway): Promise<void> { /* ... */ }
  }
  ```

Constructor injection is the default recommendation. Setter injection is an escape hatch. Method injection is appropriate when the dependency is operation-scoped, not object-scoped.

## Section 2: DI Without a Container (Manual Wiring)

**Q6. What does manual Dependency Injection look like, and when is it sufficient?**
A: Manual DI (also called "poor man's DI") means wiring dependencies by hand at the composition root — the entry point of the application:

```ts
// Interfaces — stable abstractions
interface LoanRepository {
  findById(id: string): Promise<Loan | null>;
  save(loan: Loan): Promise<void>;
}

interface NotificationService {
  send(userId: string, message: string): Promise<void>;
}

// Concrete implementations
class PostgresLoanRepository implements LoanRepository {
  constructor(private readonly pool: Pool) {}
  async findById(id: string) { /* pg query */ }
  async save(loan: Loan) { /* pg upsert */ }
}

class SmsNotificationService implements NotificationService {
  constructor(private readonly smsClient: SmsClient) {}
  async send(userId: string, message: string) { /* SMS API call */ }
}

// Consumer — depends on abstractions only
class LoanApprovalService {
  constructor(
    private readonly repo: LoanRepository,
    private readonly notifier: NotificationService,
  ) {}

  async approveLoan(loanId: string): Promise<void> {
    const loan = await this.repo.findById(loanId);
    loan.approve();
    await this.repo.save(loan);
    await this.notifier.send(loan.userId, "Your loan has been approved.");
  }
}

// Composition root — app entry point wires everything
const pool = new Pool({ connectionString: process.env.PG_URL });
const repo = new PostgresLoanRepository(pool);
const notifier = new SmsNotificationService(new SmsClient(process.env.SMS_KEY));
const loanService = new LoanApprovalService(repo, notifier);
```
Manual DI is sufficient for small services with shallow dependency graphs. It becomes painful when graphs are deep (A depends on B depends on C depends on D...) — you end up constructing leaf dependencies first and passing them up manually through every layer. This is where a container earns its keep.

**Q7. What is the "composition root" and why does its placement matter?**
A: The composition root is the single place in the application where the entire dependency graph is assembled. Ideally it's as close to the application entry point as possible (`main.ts`, `app.ts`, `bootstrap()`). Its placement matters because:
- **Dependencies should be resolved once** — constructing the graph at startup surfaces misconfiguration early (missing env vars, unreachable DBs) rather than failing mid-request.
- **It's the only place `new` for infrastructure types belongs** — any `new ConcreteService()` inside a business logic class is a DI violation; it belongs only in the composition root or factory.
- **Testing** — in tests, you have a *test composition root* that wires mock implementations in place of real ones. The business logic classes never change.

In NestJS, the composition root is the module system (`AppModule` + `bootstrapNestApplication`). In a plain Express app, it's `index.ts` / `server.ts`.

**Q8. How does DI make unit testing dramatically easier?**
A: DI is the primary enabler of true unit testing because it makes substitution trivial. Without DI:

```ts
// Untestable — hardcoded dependency
class LoanApprovalService {
  private repo = new PostgresLoanRepository(); // can't swap in a test

  async approveLoan(loanId: string) { /* ... */ }
}
```

With DI:
```ts
// Fully testable
class LoanApprovalService {
  constructor(private readonly repo: LoanRepository) {} // inject the abstraction
}

// In tests — inject a mock, no DB needed
describe("LoanApprovalService", () => {
  it("approves a valid loan", async () => {
    const mockRepo: LoanRepository = {
      findById: jest.fn().mockResolvedValue(new Loan({ id: "1", status: "pending" })),
      save: jest.fn().mockResolvedValue(undefined),
    };
    const service = new LoanApprovalService(mockRepo);
    await service.approveLoan("1");
    expect(mockRepo.save).toHaveBeenCalledWith(expect.objectContaining({ status: "approved" }));
  });
});
```
No database, no network, no flakiness. The test is fast, deterministic, and isolated to exactly the logic under test.

## Section 3: DI in NestJS

**Q9. How does NestJS's DI container work?**
A: NestJS uses a module-scoped IoC container built on top of TypeScript decorators and `reflect-metadata`. The lifecycle:

1. **Registration** — `@Injectable()` marks a class as a provider. It is declared in a module's `providers` array.
2. **Token binding** — NestJS uses the class itself as the injection token by default; custom tokens use `@Inject('TOKEN_NAME')`.
3. **Resolution** — when a controller or provider declares a constructor parameter, NestJS reads its TypeScript type via `reflect-metadata`, finds the registered provider for that type, and injects it.
4. **Lifetime management** — providers default to singleton scope per module. `Scope.REQUEST` creates a new instance per HTTP request; `Scope.TRANSIENT` creates a new instance per injection.

```ts
// Provider
@Injectable()
export class LoanRepository {
  constructor(private readonly dataSource: DataSource) {}
  async findById(id: string): Promise<Loan | null> { /* ... */ }
}

// Module — registers providers and their dependencies
@Module({
  imports: [TypeOrmModule.forFeature([Loan])],
  providers: [LoanRepository, LoanApprovalService],
  controllers: [LoanController],
})
export class LoanModule {}

// Consumer — NestJS injects LoanRepository automatically
@Injectable()
export class LoanApprovalService {
  constructor(private readonly repo: LoanRepository) {}
}
```

**Q10. What are the different provider types in NestJS?**
A: NestJS supports five provider syntaxes, each for a different wiring scenario:

```ts
@Module({
  providers: [
    // 1. Shorthand — class is both token and implementation
    LoanService,

    // 2. useClass — explicit class binding (useful for swapping implementations)
    { provide: LoanRepository, useClass: PostgresLoanRepository },

    // 3. useValue — inject a literal value, config object, or mock
    { provide: CONFIG_TOKEN, useValue: { maxLoanAmount: 500_000 } },

    // 4. useFactory — runtime logic to determine which instance to provide
    {
      provide: PAYMENT_GATEWAY,
      useFactory: (config: ConfigService): PaymentGateway => {
        return config.get("GATEWAY") === "razorpay"
          ? new RazorpayGateway(config)
          : new JusPayGateway(config);
      },
      inject: [ConfigService],
    },

    // 5. useExisting — alias one token to another already-registered provider
    { provide: LEGACY_LOAN_SERVICE, useExisting: LoanService },
  ],
})
export class LoanModule {}
```
`useFactory` is Factory Method pattern inside the DI container. `useClass` is the standard swap for testing (replace `PostgresLoanRepository` with `InMemoryLoanRepository` in the test module).

**Q11. What is the difference between singleton, request, and transient scope in NestJS?**
A:

| Scope        | Instance lifetime                        | Use when                                                                 |
|---           |---                                       |---                                                                       |
| `DEFAULT` (Singleton) | One instance per module, shared across all requests | Stateless services, repositories, config — the vast majority of providers |
| `REQUEST`    | One instance per HTTP request; destroyed after response | Services that carry per-request state (current user, request ID, tenant context) |
| `TRANSIENT`  | New instance every time it is injected   | Stateful helpers that must not be shared between injections              |

`REQUEST` scope has a significant cost: NestJS must re-instantiate the provider *and every provider that depends on it* for each request — it propagates upward through the dependency tree. Use it only when the per-request isolation is genuinely required (e.g., a `CurrentUserService` that holds the authenticated user from the JWT). For user context in most cases, prefer storing it in `AsyncLocalStorage` (request-scoped store without DI scope overhead) and injecting a stateless service that reads from it.

**Q12. How do you inject a dependency using a custom token (non-class token) in NestJS?**
A: When the injection token is not a class (string literal, Symbol, or interface token), use `@Inject()`:

```ts
// Define the token — use a Symbol to avoid string collision
export const PAYMENT_CONFIG = Symbol("PAYMENT_CONFIG");

export interface PaymentConfig {
  razorpayKey: string;
  jusPayMerchantId: string;
  timeoutMs: number;
}

// Register with useValue or useFactory
@Module({
  providers: [
    {
      provide: PAYMENT_CONFIG,
      useFactory: (config: ConfigService): PaymentConfig => ({
        razorpayKey: config.getOrThrow("RAZORPAY_KEY"),
        jusPayMerchantId: config.getOrThrow("JUSPAY_MERCHANT_ID"),
        timeoutMs: config.get("PAYMENT_TIMEOUT_MS", 5000),
      }),
      inject: [ConfigService],
    },
  ],
  exports: [PAYMENT_CONFIG],
})
export class PaymentConfigModule {}

// Inject with @Inject(TOKEN)
@Injectable()
export class RazorpayGateway {
  constructor(
    @Inject(PAYMENT_CONFIG) private readonly config: PaymentConfig,
  ) {}

  async initiatePayment(amount: number, orderId: string): Promise<string> {
    // uses this.config.razorpayKey
  }
}
```
Using `Symbol` tokens (rather than strings) eliminates the risk of token name collisions across modules.

**Q13. What is a circular dependency in NestJS DI, and how do you resolve it?**
A: A circular dependency occurs when Module A imports Module B, and Module B imports Module A — or when Provider A depends on Provider B and B depends on A. NestJS will throw: *"A circular dependency has been detected."*

**For providers** — use `forwardRef()`:
```ts
@Injectable()
export class LoanService {
  constructor(
    // forwardRef defers resolution until both classes are initialized
    @Inject(forwardRef(() => RepaymentService))
    private readonly repaymentService: RepaymentService,
  ) {}
}

@Injectable()
export class RepaymentService {
  constructor(
    @Inject(forwardRef(() => LoanService))
    private readonly loanService: LoanService,
  ) {}
}
```

**For modules** — use `forwardRef()` in both `imports` arrays:
```ts
@Module({ imports: [forwardRef(() => RepaymentModule)] })
export class LoanModule {}

@Module({ imports: [forwardRef(() => LoanModule)] })
export class RepaymentModule {}
```

`forwardRef` is a workaround, not a solution. A circular dependency is almost always a design smell — it means two classes are too tightly coupled and likely violating SRP. The real fix is to extract the shared logic into a third service that both depend on, breaking the cycle structurally.

**Q14. How do you use DI for feature flagging or environment-specific implementations in NestJS?**
A:
```ts
// Abstraction
export abstract class EmailService {
  abstract send(to: string, subject: string, body: string): Promise<void>;
}

// Implementations
@Injectable()
export class SendGridEmailService extends EmailService {
  async send(to: string, subject: string, body: string) {
    // real SendGrid API call
  }
}

@Injectable()
export class NoOpEmailService extends EmailService {
  async send(to: string, subject: string, body: string) {
    console.log(`[NoOp] Email to ${to}: ${subject}`); // dev/test stub
  }
}

// Module swaps implementation based on environment
@Module({
  providers: [
    {
      provide: EmailService,
      useClass: process.env.NODE_ENV === "production"
        ? SendGridEmailService
        : NoOpEmailService,
    },
  ],
  exports: [EmailService],
})
export class EmailModule {}
```
`LoanApprovalService` injects `EmailService` — it never knows whether it's talking to SendGrid or a no-op stub. Switching environments is a module config change, not a code change.

## Section 4: DI Patterns & Advanced Concepts

**Q15. What is the difference between DI and a Service Locator, and why does it matter?**
A: Both patterns decouple a class from concrete implementations, but they differ fundamentally in *where* the coupling is resolved:

- **Service Locator** — the class holds a reference to a central registry and calls it to fetch dependencies: `const repo = ServiceLocator.get("LoanRepository")`. The class still *controls* dependency resolution; it just delegates to a registry instead of `new`.
- **Dependency Injection** — the class *declares* its dependencies (constructor parameters); an external entity fulfills them. The class has zero knowledge of how or where they come from.

Why it matters:
- **Service Locator hides dependencies** — a class's constructor signature doesn't reveal what it needs; you must read the implementation to discover its dependencies.
- **Service Locator is hard to test** — you must configure the global registry before every test; with DI, you just pass different constructor arguments.
- **DI makes dependencies explicit** — the constructor signature *is* the dependency contract. This is the expressiveness advantage.

The GoF community and Martin Fowler both consider Service Locator an anti-pattern in modern code — it's a form of global state disguised as a pattern.

**Q16. How does DI interact with the Repository pattern?**
A: DI and Repository are natural companions — DI is the *delivery mechanism*, Repository is the *abstraction*:

```ts
// Repository interface — the abstraction
export interface LoanRepository {
  findById(id: string): Promise<Loan | null>;
  findByUserId(userId: string): Promise<Loan[]>;
  save(loan: Loan): Promise<void>;
  delete(id: string): Promise<void>;
}

// Concrete implementation — database-specific
@Injectable()
export class TypeOrmLoanRepository implements LoanRepository {
  constructor(
    @InjectRepository(LoanEntity)
    private readonly ormRepo: Repository<LoanEntity>,
  ) {}

  async findById(id: string): Promise<Loan | null> {
    const entity = await this.ormRepo.findOne({ where: { id } });
    return entity ? LoanMapper.toDomain(entity) : null;
  }
  // ...
}

// Service depends on the interface, not the TypeORM class
@Injectable()
export class LoanApprovalService {
  constructor(
    @Inject("LOAN_REPOSITORY") // or use the interface as token
    private readonly loanRepo: LoanRepository,
  ) {}
}
```
In tests, inject an `InMemoryLoanRepository implements LoanRepository` — no database, microsecond-speed, fully deterministic.

**Q17. What is the Decorator pattern's relationship with DI in NestJS?**
A: NestJS uses TypeScript decorators as the *metadata* mechanism for DI — they aren't the Decorator *pattern* (structural wrapping), but they play a related role. However, the Decorator *pattern* also integrates cleanly with DI: you can inject a decorated version of a service transparently:

```ts
// Base service
@Injectable()
export class LoanRepository implements ILoanRepository { /* ... */ }

// Decorator — wraps and extends without modifying
@Injectable()
export class CachedLoanRepository implements ILoanRepository {
  constructor(
    @Inject("BASE_LOAN_REPO") private readonly inner: ILoanRepository,
    private readonly cache: CacheService,
  ) {}

  async findById(id: string): Promise<Loan | null> {
    const cached = await this.cache.get(`loan:${id}`);
    if (cached) return cached;
    const loan = await this.inner.findById(id);
    if (loan) await this.cache.set(`loan:${id}`, loan, 60);
    return loan;
  }
}

// Wire the decorator chain in the module
@Module({
  providers: [
    { provide: "BASE_LOAN_REPO", useClass: LoanRepository },
    { provide: ILoanRepository, useClass: CachedLoanRepository },
  ],
})
export class LoanModule {}
```
Consumers inject `ILoanRepository` and get the cached version without knowing it. Adding or removing the cache layer is a module wiring change — zero changes to business logic.

**Q18. How does `AsyncLocalStorage` complement DI for request-scoped context?**
A: `REQUEST` scope in NestJS (Q11) has performance overhead — it re-instantiates the entire dependency subtree per request. `AsyncLocalStorage` (Node.js built-in) is a more efficient alternative for propagating request context without DI scope:

```ts
// Singleton service — created once, reads from async context
@Injectable()
export class RequestContextService {
  private static storage = new AsyncLocalStorage<Map<string, unknown>>();

  static run<T>(store: Map<string, unknown>, fn: () => T): T {
    return this.storage.run(store, fn);
  }

  get<T>(key: string): T | undefined {
    return this.storage.getStore()?.get(key) as T;
  }

  set(key: string, value: unknown): void {
    this.storage.getStore()?.set(key, value);
  }
}

// Middleware — initializes the context store per request
@Injectable()
export class RequestContextMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void {
    const store = new Map<string, unknown>();
    store.set("userId", req.user?.id);
    store.set("requestId", req.headers["x-request-id"]);
    RequestContextService.run(store, next);
  }
}

// Any singleton service can now read request context
@Injectable()
export class LoanAuditService {
  constructor(private readonly ctx: RequestContextService) {}

  async log(action: string): Promise<void> {
    const userId = this.ctx.get<string>("userId");
    const requestId = this.ctx.get<string>("requestId");
    // write audit log with userId + requestId
  }
}
```
`LoanAuditService` is a singleton — no DI scope overhead — but it reads per-request data correctly because `AsyncLocalStorage` is bound to the async execution context of each request.

## Section 5: Pitfalls & Anti-patterns

**Q19. What are the most common DI mistakes in NestJS applications?**
A:
- **Injecting concrete classes instead of abstractions** — `constructor(private repo: PostgresLoanRepository)` instead of `constructor(private repo: LoanRepository)`. This defeats the purpose of DI — you can't swap implementations or mock in tests.
- **Forgetting to export a provider** — a provider declared in `ModuleA.providers` is not visible to `ModuleB` unless `ModuleA` adds it to `exports`. The error ("Nest can't resolve dependencies") is cryptic until you know this rule.
- **Overusing `REQUEST` scope** — cascades through the dependency tree and creates a new object graph per request. Significant performance cost for large graphs; use `AsyncLocalStorage` instead for context propagation.
- **Circular imports between modules** — distinct from circular *provider* dependencies (Q13); module circular imports arise from over-splitting or cross-cutting concerns not extracted into a shared module.
- **God modules** — stuffing every provider into `AppModule`. Breaks encapsulation; make each feature a self-contained module with its own providers, imports, and exports.
- **Not using `ConfigModule` / `ConfigService`** — reading `process.env` directly inside providers means you can't validate config at startup, mock values in tests, or use typed config objects.

**Q20. What is "constructor over-injection" and what does it signal?**
A: Constructor over-injection is when a class's constructor has too many parameters — typically 5 or more injected dependencies:

```ts
// Smell — too many dependencies
@Injectable()
export class LoanApprovalService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly userRepo: UserRepository,
    private readonly creditService: CreditService,
    private readonly notificationService: NotificationService,
    private readonly auditService: AuditService,
    private readonly configService: ConfigService,
    private readonly eventEmitter: EventEmitter2,
    private readonly paymentGateway: PaymentGateway,
  ) {}
}
```
This is not a DI problem — it's an SRP violation made *visible* by DI. The class is doing too many things. DI acts as a design feedback mechanism: if your constructor is painful to write and read, the class has too many responsibilities. Refactor: extract `LoanEligibilityChecker`, `LoanNotificationOrchestrator`, `LoanAuditLogger` — each with 2–3 dependencies — and inject those higher-level services instead.

**Q21. What is the "service locator in disguise" anti-pattern in NestJS, and how do you spot it?**
A: This happens when a provider injects the NestJS `ModuleRef` (or `Injector` in other frameworks) and uses it to resolve dependencies imperatively:

```ts
// ANTI-PATTERN — service locator in disguise
@Injectable()
export class LoanService {
  constructor(private moduleRef: ModuleRef) {}

  async process(type: string): Promise<void> {
    // Fetching a dependency dynamically — hides what this class actually needs
    const gateway = await this.moduleRef.resolve(PaymentGateway);
    await gateway.charge(100);
  }
}
```
This hides `PaymentGateway` as a dependency — it's not in the constructor, so it's invisible to callers and test authors. `ModuleRef` is legitimate for dynamic module contexts (plugin systems, lazy-loaded modules, getting providers whose type is only known at runtime), but using it as a routine dependency-fetching mechanism is the Service Locator anti-pattern.

**Q22. How should you handle optional dependencies in DI?**
A: Two approaches:
- **NestJS `@Optional()` decorator** — marks a constructor parameter as optional; if no provider is registered, `undefined` is injected instead of throwing:
  ```ts
  @Injectable()
  export class LoanService {
    constructor(
      private readonly repo: LoanRepository,
      @Optional() private readonly featureFlags?: FeatureFlagService,
    ) {}

    async processLoan(loanId: string) {
      const useNewFlow = this.featureFlags?.isEnabled("new-loan-flow") ?? false;
      // ...
    }
  }
  ```
- **Null object pattern** — always inject a dependency, but register a no-op implementation by default. Preferred over `@Optional()` because callers don't need null checks:
  ```ts
  @Injectable()
  export class NoOpFeatureFlagService implements FeatureFlagService {
    isEnabled(_flag: string): boolean { return false; } // safe default
  }
  // Register NoOpFeatureFlagService as the default; override in production module
  ```

## Section 6: Scenario / System Design Style Questions

**Q23. "Your NestJS service throws 'Nest can't resolve dependencies of LoanService (?). Please make sure that the argument LoanRepository at index [0] is available in the LoanModule context.' How do you debug this?"**
A: This is the most common NestJS DI error. Systematic resolution:

1. **Check `LoanModule.providers`** — is `LoanRepository` declared there? If not, add it.
2. **Check if it comes from another module** — if `LoanRepository` is declared in `DatabaseModule`, is `DatabaseModule` in `LoanModule.imports`? Is `LoanRepository` in `DatabaseModule.exports`? Both must be true.
3. **Check for typos in the token** — if using string or Symbol tokens with `@Inject()`, the token in `@Inject(TOKEN)` must exactly match the `provide:` value in the module.
4. **Check for circular module imports** — if `LoanModule` imports `DatabaseModule` and `DatabaseModule` imports `LoanModule`, you have a circular module dependency. Use `forwardRef()` or restructure.
5. **Check `@Injectable()` decorator** — `LoanRepository` must be decorated with `@Injectable()` for NestJS to manage it.
6. **Enable verbose DI logging** — temporarily set `{ logger: ['verbose'] }` in `NestFactory.create()` to see the full dependency resolution trace.

**Q24. "You're building a multi-gateway payment system. Today it's Razorpay; tomorrow JusPay, then HDFC. How do you use DI to make the gateway swappable without changing business logic?"**
A:
```ts
// Step 1 — Stable abstraction
export interface PaymentGateway {
  initiate(amount: number, orderId: string, metadata: PaymentMetadata): Promise<PaymentIntent>;
  verify(transactionId: string): Promise<PaymentStatus>;
  refund(transactionId: string, amount: number): Promise<RefundResult>;
}

export const PAYMENT_GATEWAY = Symbol("PAYMENT_GATEWAY");

// Step 2 — Concrete implementations, each independently deployable
@Injectable()
export class RazorpayGateway implements PaymentGateway { /* ... */ }

@Injectable()
export class JusPayGateway implements PaymentGateway { /* ... */ }

@Injectable()
export class HdfcGateway implements PaymentGateway { /* ... */ }

// Step 3 — Factory-driven DI binding
@Module({
  providers: [
    RazorpayGateway,
    JusPayGateway,
    HdfcGateway,
    {
      provide: PAYMENT_GATEWAY,
      useFactory: (config: ConfigService, razorpay: RazorpayGateway, juspay: JusPayGateway, hdfc: HdfcGateway): PaymentGateway => {
        const gateway = config.getOrThrow<string>("ACTIVE_PAYMENT_GATEWAY");
        const map: Record<string, PaymentGateway> = { razorpay, juspay, hdfc };
        if (!map[gateway]) throw new Error(`Unknown gateway: ${gateway}`);
        return map[gateway];
      },
      inject: [ConfigService, RazorpayGateway, JusPayGateway, HdfcGateway],
    },
  ],
  exports: [PAYMENT_GATEWAY],
})
export class PaymentModule {}

// Step 4 — Business logic depends on the abstraction only
@Injectable()
export class LoanDisbursementService {
  constructor(
    @Inject(PAYMENT_GATEWAY) private readonly gateway: PaymentGateway,
    private readonly loanRepo: LoanRepository,
  ) {}

  async disburse(loanId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);
    const intent = await this.gateway.initiate(loan.amount, loanId, { type: "disbursement" });
    loan.markDisbursed(intent.transactionId);
    await this.loanRepo.save(loan);
  }
}
```
Switching gateways is a config change (`ACTIVE_PAYMENT_GATEWAY=hdfc`). `LoanDisbursementService` is unchanged, its tests use a `MockPaymentGateway`, and each concrete gateway is independently unit-testable.

**Q25. "A team member says, 'We don't need DI — we can just use module-level singletons (export const loanService = new LoanService()). It's simpler.' How do you respond?"**
A: Module-level singletons work — until three problems compound:

**1. Testing becomes module-patching hell:**
```ts
// Their approach
export const loanService = new LoanService(new PostgresLoanRepository());

// In tests — must mock module internals
jest.mock("../repositories/loan.repository"); // brittle, affects all tests in the file
```
With DI, tests just pass a different constructor argument — no module patching, no global state shared between tests.

**2. Hidden dependencies and initialization order:**
Module-level singletons initialize at import time. If `loanService.ts` imports `config.ts` which reads `process.env.PG_URL`, and that env var isn't set when the test runner imports the module, you get a silent misconfiguration. A DI container surfaces this at startup — fail-fast, explicit error message, clear stack trace.

**3. No environment-specific swapping:**
```ts
// Their approach — hardcoded forever
export const emailService = new SendGridEmailService(process.env.SENDGRID_KEY!);
// In dev/test — real emails go out, or you must conditionally set env vars
```
With DI, you register `NoOpEmailService` in `test.module.ts` — zero env setup, zero real emails, zero coupling between test and infrastructure.

The singleton *lifetime* is correct — most services should be singletons. But the *construction* and *wiring* should go through DI. The answer isn't "DI vs. singletons" — it's "DI-managed singletons vs. unmanaged module-level singletons." The former gives you testability, configurability, and lifecycle management; the latter gives you none of those.

## Quick Comparison Table

| Aspect                   | Manual DI (Composition Root)          | IoC Container (NestJS)                         | Service Locator (Anti-pattern)             |
|---                       |---                                    |---                                             |---                                         |
| Wiring location          | Explicit, in entry point              | Automatic, via decorators + module config      | Implicit, inside each class                |
| Dependency visibility    | Fully visible in constructor          | Fully visible in constructor                   | Hidden inside method bodies                |
| Testability              | High — pass mocks to constructor      | High — replace providers in test module        | Low — must configure global registry       |
| Boilerplate              | High for deep graphs                  | Low — container resolves graph                 | Low (but wrong tradeoff)                   |
| Circular dep detection   | Manual / runtime crash                | Startup-time error with clear message          | Runtime crash, hard to trace               |
| Lifetime management      | Manual                                | Singleton / Request / Transient per provider   | Typically global singleton only            |
| Best for                 | Small services, scripts, CLIs         | Large NestJS applications, microservices       | Never — use DI instead                     |
| Swap implementation      | Edit composition root                 | Change `useClass` / `useFactory` in module     | Edit registry — hidden from callers        |
| Config validation        | Manual at startup                     | `ConfigModule` validates at bootstrap          | Typically deferred to first use            |

**Tip for the interview:** At the 5 YOE level, DI questions rarely arrive as pure theory — they show up in architecture discussions ("how would you make this testable?"), code reviews ("why is this hard to mock?"), and incident post-mortems ("why did this break when we changed the DB layer?"). The strongest answers connect DI to *concrete pain you've felt*: a `jest.mock()` nightmare that DI would have eliminated, a `REQUEST` scope performance problem you debugged, a NestJS "can't resolve dependencies" error you traced. Know the NestJS provider types cold (`useClass`, `useFactory`, `useValue`, `useExisting`), understand why circular dependencies are a design smell and not just a NestJS quirk, and be ready to explain why module-level singletons are not the same as DI-managed singletons — that's the level of nuance that lands at 5 YOE.
