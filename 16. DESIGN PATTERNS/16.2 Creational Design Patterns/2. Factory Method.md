# Design Patterns — Creational: Factory Method — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Factory Method pattern?**
A: Factory Method is a creational design pattern that defines an interface for creating an object, but lets subclasses (or implementing classes) decide which concrete class to instantiate. Instead of calling `new ConcreteClass()` directly in your code, you call a factory method — a method whose job is to produce an object. The creator class calls its own factory method and works with the result through an abstraction, never knowing the concrete type it received. The Gang of Four (GoF) definition: *"Define an interface for creating an object, but let subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses."*

**Q2. What problem does Factory Method solve?**
A: It decouples the code that *uses* an object from the code that *creates* it. When you write `new PaymentGateway()` inline, you've hardcoded a dependency on a specific class — changing the implementation means hunting down every `new` call. Factory Method moves that `new` call into one dedicated place (the factory method), and the consuming code depends only on the abstraction the factory returns. This makes it easy to swap implementations, extend with new types, and test by injecting a different factory that returns a mock or stub.

**Q3. What are the four participants in the Factory Method pattern?**
A:
- **Product** — the interface or abstract class that all created objects implement (e.g., `PaymentProvider`).
- **ConcreteProduct** — a specific implementation of `Product` (e.g., `RazorpayProvider`, `JusPayProvider`).
- **Creator** — the class that declares the factory method, which returns a `Product`. It may also contain core business logic that calls the factory method.
- **ConcreteCreator** — overrides the factory method to return a specific `ConcreteProduct`.

**Q4. What is the difference between a "factory method" (lowercase) and the Factory Method *pattern* (GoF)?**
A: A factory method (lowercase) is just any method whose purpose is to create and return an object — a helper, a static utility, a constructor wrapper. The Factory Method *pattern* is a specific structural arrangement: a creator class with a method that subclasses override to control which product gets instantiated, combined with a product abstraction so the creator never depends on a concrete type. In interviews, people often use the terms interchangeably — it's worth clarifying which one you're discussing. A `static createFromConfig(config)` utility is a factory method; the full GoF pattern involves a class hierarchy on both the creator and product sides.

**Q5. How does Factory Method relate to the Open/Closed Principle?**
A: Factory Method is one of the primary mechanisms for achieving OCP in object creation. The creator class is *closed* — it never needs to change when a new product type is added. A new product means a new `ConcreteProduct` class and a new `ConcreteCreator` subclass — both additions, no modifications to existing code. The consuming logic (in the creator's business methods) stays stable because it works through the `Product` interface, not a concrete type. OCP is the *goal*; Factory Method is one *tool* to reach it for the object-creation concern.

## Section 2: Structure & Variants

**Q6. What does a canonical Factory Method implementation look like in TypeScript?**
A:
```ts
// Product interface
interface PaymentProvider {
  initiatePayment(amount: number, orderId: string): Promise<string>;
  verifyPayment(transactionId: string): Promise<boolean>;
}

// Concrete Products
class RazorpayProvider implements PaymentProvider {
  async initiatePayment(amount: number, orderId: string) {
    // Razorpay-specific API call
    return `rzp_txn_${orderId}`;
  }
  async verifyPayment(transactionId: string) {
    return true; // Razorpay verify logic
  }
}

class JusPayProvider implements PaymentProvider {
  async initiatePayment(amount: number, orderId: string) {
    return `juspay_txn_${orderId}`;
  }
  async verifyPayment(transactionId: string) {
    return true; // JusPay verify logic
  }
}

// Creator — declares the factory method
abstract class PaymentProcessor {
  // Factory Method — subclasses override this
  protected abstract createProvider(): PaymentProvider;

  // Core business logic — uses the product via abstraction
  async processPayment(amount: number, orderId: string): Promise<string> {
    const provider = this.createProvider();           // delegates creation
    const txnId = await provider.initiatePayment(amount, orderId);
    console.log(`Payment initiated: ${txnId}`);
    return txnId;
  }
}

// Concrete Creators
class RazorpayProcessor extends PaymentProcessor {
  protected createProvider(): PaymentProvider {
    return new RazorpayProvider();
  }
}

class JusPayProcessor extends PaymentProcessor {
  protected createProvider(): PaymentProvider {
    return new JusPayProvider();
  }
}

// Usage
const processor: PaymentProcessor = new RazorpayProcessor();
processor.processPayment(5000, "order_001");
```

**Q7. What is the "static factory method" variant, and how does it differ from the GoF pattern?**
A: A static factory method is a `static` class method that creates and returns an instance — it replaces or supplements the constructor:

```ts
class PaymentProvider {
  private constructor(private readonly gateway: string) {}

  static forGateway(gateway: string): PaymentProvider {
    if (gateway === "razorpay") return new PaymentProvider("razorpay");
    if (gateway === "juspay")   return new PaymentProvider("juspay");
    throw new Error(`Unknown gateway: ${gateway}`);
  }
}

const provider = PaymentProvider.forGateway("razorpay");
```
It differs from the GoF pattern in that there's no class hierarchy or subclassing — the "factory" logic lives in one static method with branching, not in an overridable method that subclasses specialize. Static factory methods are simpler, more common in practice, and often all you need. The GoF pattern is heavier but more extensible — you add new concrete creators without editing existing code. Josh Bloch's *Effective Java* popularized static factory methods as a first-class construction pattern.

**Q8. What is a "parameterized factory method"?**
A: Instead of subclassing to vary the product, the factory method accepts a parameter that determines what to create:

```ts
abstract class NotificationFactory {
  createChannel(type: "email" | "sms" | "push"): NotificationChannel {
    switch (type) {
      case "email": return new EmailChannel();
      case "sms":   return new SMSChannel();
      case "push":  return new PushChannel();
    }
  }
}
```
It's simpler than maintaining a subclass per product, but less extensible — adding a new channel type still requires editing the switch. Combine with a registry (Q13) to get the best of both worlds: parameterized lookup without a growing `switch`.

**Q9. How do you implement Factory Method in languages without abstract classes or inheritance (e.g., Go, plain JavaScript)?**
A: In Go, Factory Method is expressed as a function that returns an interface:

```go
type PaymentProvider interface {
  InitiatePayment(amount int, orderID string) (string, error)
  VerifyPayment(txnID string) (bool, error)
}

// Factory function — the "method" is a standalone function
func NewPaymentProvider(gateway string) (PaymentProvider, error) {
  switch gateway {
  case "razorpay":
    return &RazorpayProvider{}, nil
  case "juspay":
    return &JusPayProvider{}, nil
  default:
    return nil, fmt.Errorf("unknown gateway: %s", gateway)
  }
}
```
In JavaScript (no types), you return objects that conform to an implied interface — often via a registry map of constructor functions. The spirit of the pattern — *delegate creation, return through abstraction* — is preserved even without class hierarchies.

**Q10. When does the Factory Method naturally evolve into the Abstract Factory pattern?**
A: Factory Method creates *one product*. When your system needs to create *families of related products* that must be used together, and you want to ensure consistency within a family, you graduate to Abstract Factory. Example: a UI toolkit where `WindowsFactory` produces `WindowsButton` + `WindowsDialog` + `WindowsScrollbar` — all visually consistent — while `MacFactory` produces the Mac equivalents. Abstract Factory is essentially a *collection* of factory methods. The progression: you start with one Factory Method for `PaymentProvider`, then realize you also need a coordinated `WebhookHandler` and `ReconciliationReport` per gateway — and suddenly you have an Abstract Factory of payment gateway components.

## Section 3: Factory Method vs. Related Patterns

**Q11. Factory Method vs. Simple Factory — what's the distinction?**
A: Simple Factory (not a GoF pattern — a common idiom) is a standalone class or function with a `create(type)` method that uses `if/else` or `switch` to return the right instance:

```ts
class PaymentProviderFactory {
  static create(type: string): PaymentProvider {
    if (type === "razorpay") return new RazorpayProvider();
    if (type === "juspay")   return new JusPayProvider();
    throw new Error("Unknown provider");
  }
}
```
Simple Factory centralizes creation but is **closed for extension** — you must edit it for every new type. Factory Method replaces that `if/else` with polymorphism — new types mean new subclasses, not edits to existing code. Simple Factory is easier to write and often sufficient; Factory Method is more extensible but heavier. In practice: start with Simple Factory, refactor to Factory Method when the `if/else` starts to grow.

**Q12. Factory Method vs. Abstract Factory — one-line distinction?**
A: Factory Method creates **one product** via subclass override; Abstract Factory creates **a family of related products** via an interface of multiple factory methods.

| Aspect               | Factory Method                     | Abstract Factory                            |
|---                   |---                                  |---                                          |
| Products created     | One                                 | Family of related products                  |
| Extension mechanism  | Subclass the creator                | Implement the factory interface             |
| Complexity           | Lower                               | Higher                                      |
| Use when             | One object type varies              | Multiple related objects must be consistent |

**Q13. How does a Factory Registry combine with Factory Method to eliminate `switch` statements?**
A: A registry maps type keys to factory functions, making the creation logic fully data-driven and OCP-compliant — new types are *registered*, not coded into a conditional:

```ts
type ProviderFactory = () => PaymentProvider;

class PaymentProviderRegistry {
  private static registry = new Map<string, ProviderFactory>();

  static register(key: string, factory: ProviderFactory): void {
    this.registry.set(key, factory);
  }

  static create(key: string): PaymentProvider {
    const factory = this.registry.get(key);
    if (!factory) throw new Error(`No provider registered for: ${key}`);
    return factory();
  }
}

// Register at startup
PaymentProviderRegistry.register("razorpay", () => new RazorpayProvider());
PaymentProviderRegistry.register("juspay",   () => new JusPayProvider());

// Adding HDFC — zero edits to existing code
PaymentProviderRegistry.register("hdfc", () => new HdfcProvider());

// Usage
const provider = PaymentProviderRegistry.create("razorpay");
```
This is especially powerful in a NestJS or DI-container context where providers register themselves at module load time.

**Q14. How does Factory Method relate to Dependency Injection?**
A: They solve overlapping problems from different angles. Factory Method puts the creation decision inside a method you override. DI externalizes creation entirely — the container creates objects and injects them. In practice:
- Use **Factory Method** when the creator class needs to control *how* an object is created, or when the type is determined at runtime (per-request, per-config).
- Use **DI** when the object is created once per scope (singleton, request scope) and wired up at startup.
- They're often combined: a DI container injects a *factory* (the factory method pattern), which the consuming class calls at runtime to produce instances on demand — common in NestJS with `FactoryProvider`.

## Section 4: OCP, Testing & Real-World Usage

**Q15. How does Factory Method make unit testing easier?**
A: By centralizing and abstracting creation, Factory Method gives you a single seam to substitute test doubles. Instead of mocking `new RazorpayProvider()` everywhere (which requires patching module internals), you inject a `TestPaymentProcessor` that overrides `createProvider()` to return a mock:

```ts
class TestPaymentProcessor extends PaymentProcessor {
  protected createProvider(): PaymentProvider {
    return {
      initiatePayment: jest.fn().mockResolvedValue("mock_txn_123"),
      verifyPayment: jest.fn().mockResolvedValue(true),
    };
  }
}

// Test uses TestPaymentProcessor — no real HTTP calls, no mocking internals
const processor = new TestPaymentProcessor();
await processor.processPayment(5000, "order_001");
```
The business logic in `processPayment` is tested in complete isolation from the real payment gateway.

**Q16. What are the signs that you need a Factory Method in an existing codebase?**
A: Watch for these smells:
- **Scattered `new ConcreteClass()`** — the same concrete class instantiated across many files; changing the class means touching all of them.
- **Type-checking before creation** — `if (config.gateway === "razorpay") { const p = new RazorpayProvider(); ... }` repeated in multiple places.
- **Constructor doing too much** — a constructor that fetches config, sets up connections, or has side effects; a factory method can handle pre-creation logic cleanly.
- **Difficulty stubbing in tests** — if you're patching module exports or using `jest.mock()` for a constructor, a factory method gives you a proper injection point.
- **Platform/environment variation** — same interface, different implementation per environment (browser vs Node, prod vs test, region-specific provider).

**Q17. How does Factory Method work in a NestJS application?**
A: NestJS's DI system supports Factory Providers natively — the `useFactory` option is a direct expression of the Factory Method pattern at the container level:

```ts
@Module({
  providers: [
    {
      provide: PAYMENT_PROVIDER,
      useFactory: (configService: ConfigService): PaymentProvider => {
        const gateway = configService.get<string>("PAYMENT_GATEWAY");
        switch (gateway) {
          case "razorpay": return new RazorpayProvider(configService);
          case "juspay":   return new JusPayProvider(configService);
          default: throw new Error(`Unsupported gateway: ${gateway}`);
        }
      },
      inject: [ConfigService],
    },
  ],
})
export class PaymentModule {}
```
The factory function receives injected dependencies and returns the right `PaymentProvider` implementation. Consumers inject `PAYMENT_PROVIDER` and never know which concrete class they got. Switching gateways is a config change, not a code change.

**Q18. Can Factory Method be used for creating database connections or repository instances?**
A: Yes — it's a natural fit. A `RepositoryFactory` can return different repository implementations based on environment or context:

```ts
interface UserRepository {
  findById(id: string): Promise<User | null>;
  save(user: User): Promise<void>;
}

abstract class RepositoryFactory {
  abstract createUserRepository(): UserRepository;
}

class PostgresRepositoryFactory extends RepositoryFactory {
  createUserRepository(): UserRepository {
    return new PostgresUserRepository(pgPool);
  }
}

class InMemoryRepositoryFactory extends RepositoryFactory {
  createUserRepository(): UserRepository {
    return new InMemoryUserRepository();  // used in tests
  }
}
```
Integration tests use `InMemoryRepositoryFactory` — fast, no DB required. Staging and production use `PostgresRepositoryFactory`. The application code never changes between environments.

## Section 5: Pitfalls & Anti-patterns

**Q19. What are the common misuses of Factory Method?**
A:
- **Using it for single, never-varying types** — if there will only ever be one `ConcreteProduct`, a factory method adds indirection without benefit. YAGNI applies.
- **Putting business logic in the factory** — the factory method's job is *creation*, not orchestration. If your `createProvider()` is fetching data, running validations, or emitting events, those responsibilities belong elsewhere.
- **Returning `any` / losing the abstraction** — if the return type isn't the `Product` interface but a concrete class, callers get coupled to the implementation and the whole pattern breaks down.
- **Overcomplicating with too many subclasses** — if you have 12 concrete creators each with trivial differences, a parameterized factory or registry (Q13) is simpler and more maintainable.
- **Confusing factory method with constructor** — the factory method should be a *separate, named method*, not the constructor itself. A constructor that decides between implementations based on a flag is an anti-pattern (constructors should be simple).

**Q20. What is the "Product Proliferation" problem in Factory Method?**
A: As the number of product types grows, you get an equivalent growth in concrete creator subclasses — one per product. For N products, you have N ConcreteCreators. If products also vary along a second axis (e.g., both by type *and* by region), you get an N×M explosion of subclasses. This is the point where Factory Method should be refactored into Abstract Factory (if families are the concern) or a Registry (if simple parameterization suffices). Recognizing this explosion early prevents a maintenance nightmare.

**Q21. How do you handle errors and fallback logic inside a factory method?**
A: The factory method is the right place to centralize creation-time validation and fallback:

```ts
protected createProvider(): PaymentProvider {
  const gateway = this.config.get("PAYMENT_GATEWAY");

  if (!gateway) {
    console.warn("No gateway configured — falling back to MockProvider");
    return new MockPaymentProvider();
  }

  const factory = providerRegistry.get(gateway);
  if (!factory) {
    throw new ConfigurationError(`Unsupported payment gateway: ${gateway}`);
  }

  return factory(this.config);
}
```
Keep the error handling *in* the factory method — don't spread it across call sites. If every consumer has to handle a `null` return or catch a creation exception, the factory is leaking its complexity outward.

## Section 6: Scenario / System Design Style Questions

**Q22. "Your team is integrating a 4th payment gateway (HDFC) into a fintech platform. The existing code has `if (gateway === "razorpay") ... else if (gateway === "juspay") ...` in three separate service files. What do you do?"**
A: This is the exact problem Factory Method solves. Step-by-step:
1. Define a `PaymentProvider` interface capturing the contract all gateways share: `initiatePayment`, `verifyPayment`, `refund`.
2. Wrap each existing gateway's code into its own class implementing `PaymentProvider` — `RazorpayProvider`, `JusPayProvider`, etc.
3. Create a `PaymentProviderFactory` (or registry) that maps gateway keys to provider instances.
4. Replace every `if/else` chain in the three service files with a single `factory.create(gateway)` call.
5. Add `HdfcProvider` and register it — zero changes to the three service files.
6. Each provider class is independently unit-testable. The factory has one integration test per provider key.

**Q23. "You're designing a Document Export feature that needs to support PDF, Excel, and CSV today, with more formats coming. How do you structure this with Factory Method?"**
A:
```ts
interface DocumentExporter {
  export(data: ReportData): Buffer;
  mimeType(): string;
  fileExtension(): string;
}

class PdfExporter implements DocumentExporter { /* ... */ }
class ExcelExporter implements DocumentExporter { /* ... */ }
class CsvExporter implements DocumentExporter { /* ... */ }

class ExporterFactory {
  private static registry = new Map<string, () => DocumentExporter>([
    ["pdf",   () => new PdfExporter()],
    ["excel", () => new ExcelExporter()],
    ["csv",   () => new CsvExporter()],
  ]);

  static create(format: string): DocumentExporter {
    const factory = this.registry.get(format);
    if (!factory) throw new Error(`Unsupported format: ${format}`);
    return factory();
  }

  static register(format: string, factory: () => DocumentExporter): void {
    this.registry.set(format, factory);
  }
}

// Controller
async exportReport(format: string, data: ReportData): Promise<Response> {
  const exporter = ExporterFactory.create(format);
  const buffer = exporter.export(data);
  return new Response(buffer, { headers: { "Content-Type": exporter.mimeType() } });
}
```
When "XML" or "JSON" is requested next quarter: one new class + one `register()` call. The controller, the factory, and existing exporters stay untouched.

**Q24. "Your notification service sends messages through email today. The product roadmap says SMS next sprint, WhatsApp the sprint after. How do you future-proof the design?"**
A: Apply Factory Method from day one — even with a single channel:

```ts
interface NotificationChannel {
  send(to: string, message: string): Promise<void>;
}

class EmailChannel implements NotificationChannel { /* ... */ }

abstract class NotificationService {
  protected abstract createChannel(type: string): NotificationChannel;

  async notify(userId: string, type: string, message: string): Promise<void> {
    const user = await this.loadUser(userId);
    const channel = this.createChannel(type);
    await channel.send(user.contact, message);
  }
}
```
When SMS arrives: add `SMSChannel`, add `SmsNotificationService extends NotificationService`. The base class logic — loading the user, calling `notify` — never changes. In practice with DI (NestJS): use a registry-based factory provider and register channels at module startup. The business logic service never sees a concrete channel class.

**Q25. "A junior dev on your team asks: 'Why not just use `new` everywhere and pass a flag to the constructor to handle variations?' How do you explain why Factory Method is better?"**
A: Three concrete problems with flag-based constructors:

```ts
// ANTI-PATTERN
const provider = new PaymentProvider("razorpay"); // what does this flag do?
```

1. **Readability** — `new PaymentProvider("razorpay")` is ambiguous. Is "razorpay" a config key? A mode? A region? A named factory (`RazorpayProvider`, `JusPayProvider`) communicates intent clearly.
2. **SRP violation** — a class that behaves differently based on a constructor flag has multiple personalities. It handles Razorpay AND JusPay AND the if/else logic to switch between them. These are separate responsibilities.
3. **OCP violation** — adding a 5th gateway means editing the constructor's `switch` (or adding another `if`), re-testing the entire class, and risking regressions for all existing gateways. With Factory Method: new class, register it, done.
4. **Testing** — you can't easily substitute a mock in a test if the class decides its own implementation internally. A factory gives you an injection point.

The constructor is for *initializing one type of thing well*. The factory method is for *deciding which thing to create*. Keep those concerns separate.

## Quick Comparison Table

| Aspect                    | Simple Factory (Idiom)             | Factory Method (GoF)                         | Abstract Factory (GoF)                       |
|---                        |---                                  |---                                           |---                                           |
| GoF pattern?              | No — common idiom                  | Yes                                          | Yes                                          |
| Extension mechanism       | Edit the `switch`/`if`             | Add a new ConcreteCreator subclass           | Add a new ConcreteFactory implementation     |
| OCP compliant?            | No (editing required)              | Yes                                          | Yes                                          |
| Products created          | One                                | One                                          | Family of related products                   |
| Complexity                | Low                                | Medium                                       | High                                         |
| Best for                  | Few types, unlikely to grow        | One object type that varies                  | Multiple coordinated objects that vary together |
| Testing                   | Mock module exports                | Subclass the creator in test                 | Inject a test factory implementation         |
| NestJS equivalent         | `if/else` in service               | `useFactory` provider                        | Module that exports a family of providers    |
| Common real-world use     | Config-based provider selection    | Per-request/per-env object creation          | Multi-tenant, multi-region product families  |

---

**Tip for the interview:** At the 5 YOE level, Factory Method rarely shows up as an isolated theory question — it surfaces in system design discussions about payment integrations, multi-provider systems, or extensible pipelines. The strongest answers connect the pattern to real cost: *"We had a growing `if/else` across five service files and every new payment gateway meant a risky multi-file edit — we centralized creation into a factory, each provider became its own class, and the last two gateway additions were zero-risk."* Also know the spectrum — Simple Factory → Factory Method → Abstract Factory — and be able to justify which level of complexity the problem actually needs. Defaulting to the heaviest pattern is as much a red flag as not knowing any pattern at all.
