# Design Patterns (Creational): Abstract Factory — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Abstract Factory pattern?**
A: Abstract Factory is a creational design pattern that provides an interface for creating *families* of related or dependent objects without specifying their concrete classes. It encapsulates a group of individual factories that share a common theme — the client code works only with the abstract factory and abstract product interfaces, never with concrete types directly. The key distinction from other creational patterns: it creates *multiple* related objects that are designed to work together, not a single object in isolation.

**Q2. What problem does Abstract Factory solve? When does it become necessary?**
A: It solves the problem of *product family consistency* — ensuring that a set of related objects (e.g., a button, a checkbox, and a dialog) always come from the same "family" and are compatible with each other. It becomes necessary when:
- The system must be independent of how its products are created, composed, and represented.
- The system must be configured with one of multiple families of products.
- A family of related product objects is designed to be used together and you need to enforce that constraint.
- You want to reveal the interfaces of a product library, not their implementations.

Without Abstract Factory, you end up with scattered `if/else` or `switch` blocks that check which family to use — duplicated in every place a product is created.

**Q3. What are the five participants in the Abstract Factory pattern?**
A: The GoF (Gang of Four) define five roles:
1. **AbstractFactory** — declares the interface for operations that create abstract product objects (e.g., `createButton()`, `createCheckbox()`).
2. **ConcreteFactory** — implements the creation operations to produce concrete product objects for a specific family (e.g., `WindowsFactory`, `MacFactory`).
3. **AbstractProduct** — declares an interface for a type of product object (e.g., `Button`, `Checkbox`).
4. **ConcreteProduct** — defines a product object to be created by the corresponding concrete factory; implements the `AbstractProduct` interface (e.g., `WindowsButton`, `MacCheckbox`).
5. **Client** — uses only the interfaces declared by `AbstractFactory` and `AbstractProduct`; never refers to concrete classes.

**Q4. How does Abstract Factory differ from Factory Method?**
A: They're related but distinct:

| Dimension             | Factory Method                                             | Abstract Factory                                              |
|-----------------------|------------------------------------------------------------|---------------------------------------------------------------|
| Creates               | One product                                                | A *family* of related products                                |
| Structure             | Single method in a class; subclasses override it           | Separate factory object with multiple creation methods        |
| Primary use           | Letting subclasses decide which class to instantiate       | Ensuring product families are used together consistently      |
| Extension             | Extend by subclassing and overriding the factory method    | Extend by creating a new concrete factory class               |
| Coupling              | Creator class coupled to one product hierarchy             | Client decoupled from all product hierarchies via factory     |

In practice, Abstract Factory often uses Factory Methods internally — each creation method on the factory can itself be a Factory Method.

**Q5. How does Abstract Factory relate to the other SOLID / GoF principles?**
A: It's a direct application of several:
- **OCP** — adding a new product family means adding a new `ConcreteFactory` class, not modifying existing ones.
- **DIP** — the client depends on `AbstractFactory` and `AbstractProduct` abstractions, not on concrete implementations.
- **ISP** — if the abstract factory interface grows too large (too many `create*()` methods), it should be split, keeping each factory focused.
- **Single Responsibility** — each `ConcreteFactory` is responsible for creating one consistent product family.

## Section 2: Structure & Implementation

**Q6. Walk through a canonical TypeScript implementation of Abstract Factory.**
A:

```typescript
// ─── Abstract Products ────────────────────────────────────────────────────────

interface Button {
  render(): void;
  onClick(handler: () => void): void;
}

interface Checkbox {
  render(): void;
  toggle(): void;
}

// ─── Concrete Products — Windows family ───────────────────────────────────────

class WindowsButton implements Button {
  render(): void { console.log("Rendering Windows-style button"); }
  onClick(handler: () => void): void { handler(); }
}

class WindowsCheckbox implements Checkbox {
  private checked = false;
  render(): void  { console.log(`Rendering Windows checkbox [${this.checked ? "x" : " "}]`); }
  toggle(): void  { this.checked = !this.checked; }
}

// ─── Concrete Products — Mac family ───────────────────────────────────────────

class MacButton implements Button {
  render(): void { console.log("Rendering macOS-style button"); }
  onClick(handler: () => void): void { handler(); }
}

class MacCheckbox implements Checkbox {
  private checked = false;
  render(): void  { console.log(`Rendering macOS checkbox [${this.checked ? "✓" : "○"}]`); }
  toggle(): void  { this.checked = !this.checked; }
}

// ─── Abstract Factory ─────────────────────────────────────────────────────────

interface UIFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}

// ─── Concrete Factories ───────────────────────────────────────────────────────

class WindowsFactory implements UIFactory {
  createButton(): Button     { return new WindowsButton(); }
  createCheckbox(): Checkbox { return new WindowsCheckbox(); }
}

class MacFactory implements UIFactory {
  createButton(): Button     { return new MacButton(); }
  createCheckbox(): Checkbox { return new MacCheckbox(); }
}

// ─── Client ───────────────────────────────────────────────────────────────────

class Application {
  private button: Button;
  private checkbox: Checkbox;

  constructor(factory: UIFactory) {
    // Client never mentions WindowsButton, MacCheckbox, etc.
    this.button   = factory.createButton();
    this.checkbox = factory.createCheckbox();
  }

  render(): void {
    this.button.render();
    this.checkbox.render();
  }
}

// ─── Composition root ─────────────────────────────────────────────────────────

const os = process.platform === "win32" ? "windows" : "mac";
const factory: UIFactory = os === "windows" ? new WindowsFactory() : new MacFactory();
const app = new Application(factory);
app.render();
```

The client (`Application`) is fully decoupled — swap `WindowsFactory` for `MacFactory` and every product automatically comes from the correct family.

**Q7. How is the concrete factory typically selected at the composition root?**
A: The choice of which `ConcreteFactory` to instantiate is pushed as far toward the entry point of the application as possible — the "composition root" in DI terminology. Common mechanisms:
- **Environment variable / config** — `process.env.PAYMENT_PROVIDER === "razorpay"` → instantiate `RazorpayFactory`.
- **Dependency injection container** — NestJS `@Module` providers map an abstract token to a concrete factory; the rest of the app never sees the concrete class.
- **Command-line argument or feature flag** — useful during gradual rollouts (e.g., Razorpay in prod, Juspay in beta).

The key invariant: *only one place* in the codebase names the concrete factory. Everything else works through the abstract interface.

**Q8. What is the "product family consistency" guarantee, and how does the pattern enforce it?**
A: The guarantee is that all products created in a session or context come from the same family and are guaranteed to be compatible with each other. Abstract Factory enforces this because the client receives *one* factory object and calls all its `create*()` methods from that single instance. There is no way for the client to accidentally mix a `RazorpayPaymentClient` with a `JuspayWebhookValidator` — they come from separate factories and can only be mixed if the client explicitly holds two factory references (which itself becomes visible and reviewable).

**Q9. How do you handle adding a new product type (e.g., a `Dialog`) to an existing Abstract Factory?**
A: This is the main weakness of the pattern — adding a new product type requires:
1. Adding `createDialog(): Dialog` to the `UIFactory` interface.
2. Implementing `createDialog()` in **every** existing `ConcreteFactory` (`WindowsFactory`, `MacFactory`, etc.).
3. Creating the concrete `Dialog` products for each family.

This is an OCP violation against the factory interface itself — changing the interface forces changes on all implementors. Mitigations:
- Provide a **default implementation** in the abstract factory (if using an abstract class instead of interface) so existing factories don't break immediately.
- Use a **registry / plugin approach** — factories register their product creators by key, so new products don't require changing the factory interface.
- Accept the trade-off — product families are relatively stable in most domains; the consistency guarantee is worth the extension cost.

## Section 3: Abstract Factory vs. Related Patterns

**Q10. When would you choose Abstract Factory over Builder?**
A: Builder is for constructing a single *complex* object step by step, where the construction process varies but the object itself has many optional or sequential parts. Abstract Factory is for creating *multiple related objects* that belong to the same family.

Choose **Abstract Factory** when:
- You have product families and need consistency across them.
- Objects are created in one step (no complex assembly sequence).

Choose **Builder** when:
- You need to construct one complex object through a multi-step process.
- The same construction process should produce different representations.

In practice, a `ReportBuilder` that assembles a report with headers, body, charts, and footers is Builder territory. A `ReportComponentFactory` that creates the right flavour of `Header`, `Chart`, and `Footer` for "PDF" vs "HTML" families is Abstract Factory territory. They can coexist — the builder uses a factory to get the right components.

**Q11. When would you choose Abstract Factory over a Service Locator?**
A: A Service Locator is a global registry that any code can pull dependencies from — it hides dependencies and makes them invisible in constructors, making code hard to test and reason about. Abstract Factory makes the dependency on the factory *explicit* via constructor injection — you can see, swap, and mock it. At 5 YOE, the answer is: prefer Abstract Factory (injected) over Service Locator (pulled). The locator is a known anti-pattern in most modern DI-based architectures; the factory is the testable alternative.

**Q12. How does Prototype pattern relate to Abstract Factory?**
A: Abstract Factory classes can be implemented using the Prototype pattern — instead of subclassing the factory for each product family, the factory is initialized with a prototypical instance of each product, and it creates new products by cloning those prototypes. This is useful when the number of product families is large or determined at runtime (e.g., loaded from configuration). It reduces the need for a new `ConcreteFactory` subclass per family:

```typescript
class PrototypeUIFactory implements UIFactory {
  constructor(
    private buttonPrototype: Button,
    private checkboxPrototype: Checkbox
  ) {}

  createButton(): Button     { return Object.create(this.buttonPrototype); }
  createCheckbox(): Checkbox { return Object.create(this.checkboxPrototype); }
}
```

## Section 4: Abstract Factory in Node.js / TypeScript / Fintech Context

**Q13. Show a real-world Abstract Factory implementation for a multi-provider payment system (Razorpay, Juspay, Cashfree).**
A: A payment processing system typically needs a consistent *family* of objects per provider: a payment client, a webhook validator, and a refund handler. Abstract Factory is the natural fit:

```typescript
// ─── Abstract Products ────────────────────────────────────────────────────────

interface PaymentClient {
  createOrder(amountInPaise: number, currency: string): Promise<{ orderId: string }>;
  capturePayment(paymentId: string): Promise<void>;
}

interface WebhookValidator {
  validate(payload: Buffer, signature: string, secret: string): boolean;
}

interface RefundHandler {
  initiateRefund(transactionId: string, amountInPaise: number): Promise<{ refundId: string }>;
  getRefundStatus(refundId: string): Promise<"pending" | "processed" | "failed">;
}

// ─── Abstract Factory ─────────────────────────────────────────────────────────

interface PaymentGatewayFactory {
  createPaymentClient(): PaymentClient;
  createWebhookValidator(): WebhookValidator;
  createRefundHandler(): RefundHandler;
}

// ─── Razorpay Family ──────────────────────────────────────────────────────────

class RazorpayClient implements PaymentClient {
  async createOrder(amountInPaise: number, currency: string) {
    const order = await razorpaySDK.orders.create({ amount: amountInPaise, currency });
    return { orderId: order.id };
  }
  async capturePayment(paymentId: string) {
    await razorpaySDK.payments.capture(paymentId);
  }
}

class RazorpayWebhookValidator implements WebhookValidator {
  validate(payload: Buffer, signature: string, secret: string): boolean {
    const expected = crypto
      .createHmac("sha256", secret)
      .update(payload)
      .digest("hex");
    return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature));
  }
}

class RazorpayRefundHandler implements RefundHandler {
  async initiateRefund(transactionId: string, amountInPaise: number) {
    const refund = await razorpaySDK.payments.refund(transactionId, { amount: amountInPaise });
    return { refundId: refund.id };
  }
  async getRefundStatus(refundId: string) {
    const refund = await razorpaySDK.refunds.fetch(refundId);
    return refund.status as "pending" | "processed" | "failed";
  }
}

class RazorpayGatewayFactory implements PaymentGatewayFactory {
  createPaymentClient(): PaymentClient       { return new RazorpayClient(); }
  createWebhookValidator(): WebhookValidator { return new RazorpayWebhookValidator(); }
  createRefundHandler(): RefundHandler       { return new RazorpayRefundHandler(); }
}

// ─── Juspay Family (similarly structured) ────────────────────────────────────

class JuspayGatewayFactory implements PaymentGatewayFactory {
  createPaymentClient(): PaymentClient       { return new JuspayClient(); }
  createWebhookValidator(): WebhookValidator { return new JuspayWebhookValidator(); }
  createRefundHandler(): RefundHandler       { return new JuspayRefundHandler(); }
}

// ─── Client (NestJS service) ──────────────────────────────────────────────────

@Injectable()
class PaymentOrchestrationService {
  private readonly client: PaymentClient;
  private readonly validator: WebhookValidator;
  private readonly refundHandler: RefundHandler;

  constructor(@Inject(PAYMENT_GATEWAY_FACTORY) factory: PaymentGatewayFactory) {
    // Always a consistent family — no risk of mixing Razorpay client with Juspay validator
    this.client        = factory.createPaymentClient();
    this.validator     = factory.createWebhookValidator();
    this.refundHandler = factory.createRefundHandler();
  }

  async processOrder(amountInPaise: number): Promise<string> {
    const { orderId } = await this.client.createOrder(amountInPaise, "INR");
    return orderId;
  }

  async handleWebhook(payload: Buffer, signature: string, secret: string): Promise<boolean> {
    return this.validator.validate(payload, signature, secret);
  }
}
```

**Q14. How do you wire an Abstract Factory in NestJS with dependency injection?**
A:

```typescript
// ─── Token ────────────────────────────────────────────────────────────────────
export const PAYMENT_GATEWAY_FACTORY = Symbol("PAYMENT_GATEWAY_FACTORY");

// ─── Dynamic factory selection ────────────────────────────────────────────────
const gatewayFactoryProvider: Provider = {
  provide: PAYMENT_GATEWAY_FACTORY,
  useFactory: (configService: ConfigService): PaymentGatewayFactory => {
    const provider = configService.get<string>("PAYMENT_PROVIDER");
    switch (provider) {
      case "razorpay": return new RazorpayGatewayFactory();
      case "juspay":   return new JuspayGatewayFactory();
      case "cashfree": return new CashfreeGatewayFactory();
      default: throw new Error(`Unknown payment provider: ${provider}`);
    }
  },
  inject: [ConfigService],
};

@Module({
  providers: [gatewayFactoryProvider, PaymentOrchestrationService],
  exports: [PaymentOrchestrationService],
})
export class PaymentModule {}
```

The entire module — every service that injects `PAYMENT_GATEWAY_FACTORY` — automatically uses the correct product family. Switching providers in production is a single environment variable change; no service code changes.

**Q15. Show how Abstract Factory enables clean unit testing by injecting a mock factory.**
A:

```typescript
// ─── Mock family ──────────────────────────────────────────────────────────────

class MockPaymentClient implements PaymentClient {
  async createOrder(amountInPaise: number, currency: string) {
    return { orderId: `mock_order_${amountInPaise}` };
  }
  async capturePayment(_paymentId: string): Promise<void> {}
}

class MockWebhookValidator implements WebhookValidator {
  validate(_payload: Buffer, _signature: string, _secret: string): boolean {
    return true; // Always valid in tests
  }
}

class MockRefundHandler implements RefundHandler {
  async initiateRefund(transactionId: string, _amountInPaise: number) {
    return { refundId: `mock_refund_${transactionId}` };
  }
  async getRefundStatus(_refundId: string): Promise<"processed"> {
    return "processed";
  }
}

class MockPaymentGatewayFactory implements PaymentGatewayFactory {
  createPaymentClient(): PaymentClient       { return new MockPaymentClient(); }
  createWebhookValidator(): WebhookValidator { return new MockWebhookValidator(); }
  createRefundHandler(): RefundHandler       { return new MockRefundHandler(); }
}

// ─── Test ─────────────────────────────────────────────────────────────────────

describe("PaymentOrchestrationService", () => {
  let service: PaymentOrchestrationService;

  beforeEach(() => {
    service = new PaymentOrchestrationService(new MockPaymentGatewayFactory());
  });

  it("should return a mock order ID on processOrder()", async () => {
    const orderId = await service.processOrder(50000);
    expect(orderId).toBe("mock_order_50000");
  });

  it("should return true for any webhook via mock validator", async () => {
    const valid = await service.handleWebhook(Buffer.from("payload"), "sig", "secret");
    expect(valid).toBe(true);
  });
});
```

No `jest.mock()`, no module mocking, no monkey-patching — the factory seam makes the entire product family swappable in one line.

**Q16. How would you use Abstract Factory to manage multi-tenant notification channels (email, SMS, WhatsApp) per client in a B2B SaaS fintech platform?**
A: In a multi-tenant system (e.g., different clients using different notification providers), each tenant's configuration maps to a `NotificationFactory`:

```typescript
interface EmailSender    { send(to: string, subject: string, body: string): Promise<void>; }
interface SmsSender      { send(to: string, message: string): Promise<void>; }
interface WhatsAppSender { send(to: string, templateId: string, vars: Record<string, string>): Promise<void>; }

interface NotificationFactory {
  createEmailSender(): EmailSender;
  createSmsSender(): SmsSender;
  createWhatsAppSender(): WhatsAppSender;
}

// Per-tenant factory registry
class NotificationFactoryRegistry {
  private factories = new Map<string, NotificationFactory>();

  register(tenantId: string, factory: NotificationFactory): void {
    this.factories.set(tenantId, factory);
  }

  forTenant(tenantId: string): NotificationFactory {
    const factory = this.factories.get(tenantId);
    if (!factory) throw new Error(`No notification factory registered for tenant: ${tenantId}`);
    return factory;
  }
}

// Tenant A uses SendGrid + Twilio + Meta WhatsApp
class TenantANotificationFactory implements NotificationFactory {
  createEmailSender(): EmailSender       { return new SendGridEmailSender(); }
  createSmsSender(): SmsSender           { return new TwilioSmsSender(); }
  createWhatsAppSender(): WhatsAppSender { return new MetaWhatsAppSender(); }
}

// Tenant B uses SES + MSG91 + Interakt
class TenantBNotificationFactory implements NotificationFactory {
  createEmailSender(): EmailSender       { return new SESEmailSender(); }
  createSmsSender(): SmsSender           { return new MSG91SmsSender(); }
  createWhatsAppSender(): WhatsAppSender { return new InteraktWhatsAppSender(); }
}
```

The `NotificationOrchestrationService` accepts a `NotificationFactory` and is entirely agnostic of the underlying providers — the tenant's factory is resolved at the request boundary and injected, ensuring full family consistency per tenant.

## Section 5: Pitfalls & Anti-patterns

**Q17. What is the "god factory" anti-pattern, and how do you avoid it?**
A: A god factory is an Abstract Factory that has grown to include `create*()` methods for dozens of unrelated products — it starts as a `UIFactory` and gradually accumulates `createLogger()`, `createCache()`, `createPaymentClient()`, and so on. Problems:
- Every `ConcreteFactory` must implement all methods, most of which are irrelevant to its domain.
- Adding a new product type forces changes to every `ConcreteFactory` in the codebase.
- The factory becomes a dumping ground that violates SRP.

Fix: decompose into multiple focused factories, each covering one cohesive product family. A `UIComponentFactory` and a `InfrastructureFactory` should be separate, injected independently into the clients that need them.

**Q18. When is Abstract Factory overkill?**
A: Abstract Factory adds real complexity — multiple interfaces, multiple classes per family, a factory selection mechanism. It's overkill when:
- You have only **one** implementation now and no clear reason to expect others. YAGNI applies.
- The "family" contains only **one product** — Factory Method is simpler and sufficient.
- Products in the "family" don't actually need to be used together — they're independent, not a cohesive family.
- The product types are **highly stable** and change only by adding new instances of existing types — a simple registry or map may suffice.

Start with a plain factory function. Reach for Abstract Factory when you genuinely have multiple product families that must be kept consistent.

**Q19. How does a concrete factory become an accidental singleton, and why does it matter?**
A: In NestJS (and most DI containers), providers are singletons by default — the container creates one instance of the factory and reuses it for every injection. This is usually fine for stateless factories. It becomes a problem when:
- The factory holds **mutable state** (e.g., a connection pool it creates products around) — multiple consumers share that state inadvertently.
- The factory needs to be **request-scoped** (e.g., a multi-tenant system where the factory is resolved per-tenant per-request).

Fix: in NestJS, use `scope: Scope.REQUEST` on the factory provider when the factory's identity or state must be per-request. Or keep factories stateless (preferred) — all state should be in the products they create, not in the factory itself.

**Q20. What happens to Abstract Factory when product families need to be loaded dynamically (e.g., from a plugin system)?**
A: The static class hierarchy breaks down when families are determined at runtime (e.g., loaded from `npm` packages, database config, or feature flags). The solution is a **registry-based factory**:

```typescript
type ProductCreators = {
  createPaymentClient: () => PaymentClient;
  createWebhookValidator: () => WebhookValidator;
  createRefundHandler: () => RefundHandler;
};

class DynamicPaymentGatewayFactory implements PaymentGatewayFactory {
  private registry = new Map<string, ProductCreators>();

  register(name: string, creators: ProductCreators): void {
    this.registry.set(name, creators);
  }

  private get(provider: string): ProductCreators {
    const creators = this.registry.get(provider);
    if (!creators) throw new Error(`Payment provider not registered: ${provider}`);
    return creators;
  }

  createPaymentClient(provider: string): PaymentClient {
    return this.get(provider).createPaymentClient();
  }
  createWebhookValidator(provider: string): WebhookValidator {
    return this.get(provider).createWebhookValidator();
  }
  createRefundHandler(provider: string): RefundHandler {
    return this.get(provider).createRefundHandler();
  }
}

// Plugin registration (e.g., from a dynamically loaded module)
dynamicFactory.register("razorpay", {
  createPaymentClient:       () => new RazorpayClient(),
  createWebhookValidator:    () => new RazorpayWebhookValidator(),
  createRefundHandler:       () => new RazorpayRefundHandler(),
});
```

This preserves the family-consistency guarantee while supporting runtime extensibility.

## Section 6: Scenario / System Design Style Questions

**Q21. "Your fintech platform currently supports Razorpay. The product team wants to A/B test Juspay for UPI payments. How do you use Abstract Factory to implement this without changing any payment logic?"**
A: Structured approach:
1. **Audit existing payment code** — identify every place a Razorpay-specific class is instantiated directly. These are the seams to replace.
2. **Extract abstract product interfaces** — `PaymentClient`, `WebhookValidator`, `RefundHandler` — from the Razorpay implementations, ensuring they capture the behavioural contract (return types, error handling semantics), not just the method signatures.
3. **Wrap existing Razorpay classes** into a `RazorpayGatewayFactory` with zero change to their internals.
4. **Build `JuspayGatewayFactory`** implementing the same abstract products. Write contract tests (see Q18 in the LSP doc) against both.
5. **At the composition root** (NestJS module provider), use a feature-flag service to select the factory:
   ```typescript
   useFactory: (flags: FeatureFlagService): PaymentGatewayFactory =>
     flags.isEnabled("juspay-upi-beta") ? new JuspayGatewayFactory() : new RazorpayGatewayFactory()
   ```
6. **Zero change** to `PaymentOrchestrationService` or any controller — they consume the abstract factory token and are fully isolated from the provider switch.

**Q22. "A junior engineer proposes putting all payment provider logic in one big PaymentService with `if (provider === 'razorpay')` blocks throughout. What's your counter-proposal and why?"**
A: The `if` block approach fails in several concrete ways as the codebase grows:
- Every new provider means adding another branch to **every** `if` block — in every method, in every service.
- The `if` logic is duplicated across `charge()`, `refund()`, `validateWebhook()`, `getStatus()` — O(methods × providers) branching points.
- Testing one provider path requires stubbing the entire service, not just the relevant implementation.
- Onboarding a provider becomes an archaeology exercise — "find all the `if (provider === ...)` blocks."

The counter-proposal is Abstract Factory: one `PaymentGatewayFactory` interface, one `ConcreteFactory` per provider, all selection logic in **one place** at the composition root. Adding a new provider means adding one factory class and one branch in the composition root — not hunting through every service method. The `PaymentService` itself never changes.

**Q23. "You're designing a reporting system that generates PDF, Excel, and HTML reports. Each format needs its own Header, Body, Footer, and Chart renderers. How do you apply Abstract Factory?"**

**Q24. "How would you handle the case where a new payment gateway only supports UPI but not card payments — it can't implement the full PaymentGatewayFactory interface?"**
A: This is an ISP / LSP problem surfaced by the Abstract Factory — the factory interface is too broad for some implementors. Three approaches:

1. **Split the factory interface** — separate `UpiPaymentFactory` from `CardPaymentFactory`; gateways implement only what they support. Callers that need both compose them explicitly.
   ```typescript
   interface UpiPaymentFactory  { createUpiClient(): UpiClient; createUpiWebhookValidator(): WebhookValidator; }
   interface CardPaymentFactory { createCardClient(): CardClient; createCardWebhookValidator(): WebhookValidator; }
   // JuspayUpiFactory implements UpiPaymentFactory only
   ```

2. **Use optional product creation with capability flags**:
   ```typescript
   interface PaymentGatewayFactory {
     supportsCards(): boolean;
     supportsUpi(): boolean;
     createPaymentClient(): PaymentClient;   // throws if capability not supported
   }
   ```
   The orchestration service checks capabilities before calling `createPaymentClient()`.

3. **Null Object pattern** — return a `NoOpCardClient` for gateways that don't support cards. The no-op returns a "not supported" result rather than throwing, and the orchestration layer handles it gracefully.

Option 1 (ISP split) is generally cleanest — it removes the violation rather than papering over it.

**Q25. "In a microservices architecture, each service has its own database. How does Abstract Factory help when writing integration tests that need to run against both a real PostgreSQL database and an in-memory store?"**
A: The repository layer is a natural Abstract Factory surface:

```typescript
interface RepositoryFactory {
  createUserRepository(): UserRepository;
  createTransactionRepository(): TransactionRepository;
  createMandateRepository(): MandateRepository;
}

class PostgresRepositoryFactory implements RepositoryFactory {
  constructor(private db: Pool) {}
  createUserRepository(): UserRepository               { return new PostgresUserRepository(this.db); }
  createTransactionRepository(): TransactionRepository { return new PostgresTransactionRepository(this.db); }
  createMandateRepository(): MandateRepository         { return new PostgresMandateRepository(this.db); }
}

class InMemoryRepositoryFactory implements RepositoryFactory {
  createUserRepository(): UserRepository               { return new InMemoryUserRepository(); }
  createTransactionRepository(): TransactionRepository { return new InMemoryTransactionRepository(); }
  createMandateRepository(): MandateRepository         { return new InMemoryMandateRepository(); }
}
```

In unit and fast integration tests: inject `InMemoryRepositoryFactory` — no DB setup, no teardown, millisecond execution. In full integration / contract tests against a Dockerised PostgreSQL: inject `PostgresRepositoryFactory`. The application services, business logic, and orchestration layer are identical in both cases — no conditional logic, no `process.env.NODE_ENV === "test"` scattered through the codebase.

## Quick Reference Table

| Dimension                           | Abstract Factory                                                      |
|-------------------------------------|-----------------------------------------------------------------------|
| Intent                              | Create families of related objects without specifying concrete classes |
| Key participants                    | AbstractFactory, ConcreteFactory, AbstractProduct, ConcreteProduct, Client |
| Number of products created          | Multiple (a whole family per factory)                                 |
| Extension mechanism                 | Add a new ConcreteFactory class                                       |
| Extension cost                      | New family → 1 new factory; new product *type* → change all factories |
| Primary benefit                     | Guarantees product family consistency                                 |
| Primary trade-off                   | Hard to add new product types without changing the factory interface  |
| Testing benefit                     | Entire product family swappable via a mock factory                   |
| Relationship to DIP                 | Client depends on abstractions (factory interface + product interfaces) |
| Relationship to OCP                 | Open to new families; closed for modification                         |
| Common misuse                       | God factory with unrelated products; use when only one family exists  |
| Distinction from Factory Method     | Creates a family vs. a single product; factory is a separate object   |
| Distinction from Builder            | Creates related objects in one step vs. one complex object step-by-step |

**Tip for the Interview:** At the 5 YOE level, Abstract Factory questions won't be "draw the UML" — they'll be "you're adding a third payment gateway, walk me through the design" or "why does your test suite require a real database?" The answers that land demonstrate that you know *when* to reach for the pattern (multiple consistent families, not just one thing to swap), *where* to put the selection logic (composition root / DI module, nowhere else), and *how* it enables testing (mock factory = entire product family replaced in one line). In fintech specifically, the payment gateway abstraction is the canonical example — knowing it cold, with real provider names and real API nuances, is what separates a pattern-reciter from someone who's actually applied it.
