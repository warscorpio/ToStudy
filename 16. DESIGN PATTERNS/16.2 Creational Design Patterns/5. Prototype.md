# Creational Design Patterns: Prototype — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Prototype pattern?**
A: Prototype is a creational design pattern that creates new objects by **cloning an existing object** — the "prototype" — rather than constructing a new one from scratch via `new`. The original object acts as a template; copies inherit its structure and state, which the caller can then modify as needed. The core idea: when object creation is expensive or complex, clone a pre-built instance instead of repeating the construction process.

The two defining operations:
- **Shallow clone** — copies the object's own primitive fields; nested objects are still referenced (shared), not duplicated.
- **Deep clone** — recursively copies nested objects too; the clone is entirely independent of the original.

**Q2. What problem does the Prototype pattern solve?**
A: Three concrete problems:

- **Expensive construction** — some objects are costly to initialize (DB queries, API calls, heavy computation). Clone a ready-made instance instead of re-running initialization every time.
- **Complex setup** — an object requires dozens of configuration steps to reach a valid state. Cloning from a pre-configured prototype avoids repeating all those steps and the chance of misconfiguring them.
- **Runtime-determined types** — when you don't know at compile time which concrete class to instantiate, you can keep a registry of prototypes and clone the right one at runtime without `if`/`switch` over types.

**Q3. What is the difference between the Prototype pattern and simply calling `new` on a class?**
A:

| Aspect                      | `new` Construction                                  | Prototype Clone                                        |
|-----------------------------|------------------------------------------------------|--------------------------------------------------------|
| Starting state              | Always starts from zero / default values             | Starts from the prototype's current state              |
| Construction cost           | Pays full initialization cost every time             | Pays only the cost of copying (often cheaper)          |
| Knowledge of concrete type  | Caller must know the exact class to instantiate      | Caller only needs a reference to the prototype object  |
| Configuration               | Caller must supply all parameters again              | Caller only overrides what differs from the prototype  |
| Subclass proliferation      | Often leads to many subclasses for slight variations | Variations handled by different prototypes, fewer classes |

**Q4. How does JavaScript's prototype chain relate to the Prototype design pattern?**
A: They share the name and philosophical ancestry but are distinct concepts:

- **JavaScript's prototype chain** is a *language mechanism* — every object has an internal `[[Prototype]]` link to another object. Property lookups traverse this chain. It's how `Object.create()`, `class` inheritance, and `__proto__` work at the engine level.
- **Prototype design pattern** is a *design-level concept* — it describes the practice of cloning objects to create new ones, independent of how the language implements inheritance.

In JavaScript, the prototype pattern is often implemented *using* the prototype chain (e.g., `Object.create(existingObject)`) — so the two concepts intersect in practice. But a Prototype pattern implementation in Java or C++ uses that language's copy mechanism, with no "prototype chain" involved at all.

**Q5. What is a prototype registry?**
A: A prototype registry (also called a prototype manager) is a centralized store that maps names or keys to pre-configured prototype objects. Instead of creating prototypes ad hoc, consumers ask the registry for the right prototype by name and clone it:

```typescript
class PrototypeRegistry {
  private store = new Map<string, Cloneable>();

  register(key: string, prototype: Cloneable): void {
    this.store.set(key, prototype);
  }

  clone(key: string): Cloneable {
    const proto = this.store.get(key);
    if (!proto) throw new Error(`No prototype registered for key: ${key}`);
    return proto.clone();
  }
}
```

The registry decouples consumers from concrete prototype classes — they request by key, not by type. This is particularly useful when the set of available prototypes is dynamic (loaded from config, toggled by feature flags, or varied per tenant).

## Section 2: Shallow vs. Deep Clone

**Q6. What is the difference between a shallow clone and a deep clone? Why does it matter?**
A: The distinction is how nested (reference) types are handled:

```typescript
const original = {
  loanId: 'L001',
  amount: 500000,
  applicant: { name: 'Arjun', pan: 'ABCDE1234F' }, // nested object
  tags: ['home-loan', 'salaried'],                  // nested array
};

// --- Shallow clone ---
const shallow = { ...original };
// shallow.loanId → 'L001'           (primitive — independent copy ✅)
// shallow.applicant === original.applicant  (same reference ⚠️)
// shallow.tags === original.tags            (same reference ⚠️)

shallow.applicant.name = 'Priya'; // mutates original.applicant.name too!
shallow.tags.push('co-applicant'); // mutates original.tags too!

// --- Deep clone ---
const deep = structuredClone(original);
// deep.applicant !== original.applicant     (independent copy ✅)
// deep.tags !== original.tags               (independent copy ✅)

deep.applicant.name = 'Priya'; // original.applicant.name still 'Arjun' ✅
```

**Why it matters in practice:** A shallow clone is fine when nested properties are treated as immutable (you always replace them, never mutate in place). When nested objects are mutated after cloning, a shallow clone produces unexpected shared-state bugs. In a fintech context this is serious — two loan objects sharing the same `applicant` reference means updating one loan's applicant inadvertently changes another loan's applicant.

**Q7. What are the main ways to shallow-clone an object in JavaScript/TypeScript?**
A:

```typescript
const original = { id: 'L001', amount: 500000, meta: { source: 'web' } };

// 1. Spread operator — most common, idiomatic
const c1 = { ...original };

// 2. Object.assign — equivalent; useful when merging into an existing target
const c2 = Object.assign({}, original);

// 3. Array spread (for arrays)
const arr = [1, 2, { nested: true }];
const c3 = [...arr];

// 4. Array.from (for arrays / iterables)
const c4 = Array.from(arr);

// 5. Object.create — creates a new object with `original` as its [[Prototype]];
//    own properties are NOT copied — this is prototype-chain delegation, not a clone
const c5 = Object.create(original); // ⚠️ Not a true copy — different semantics
```

**Q8. What are the main ways to deep-clone in JavaScript/TypeScript? What are the trade-offs?**
A:

```typescript
// 1. structuredClone (Node.js ≥ 17, modern browsers) — PREFERRED
//    Handles: nested objects, arrays, Date, Map, Set, ArrayBuffer
//    Does NOT handle: functions, class instances (loses prototype), undefined values in some cases
const deep1 = structuredClone(original);

// 2. JSON round-trip — simple but lossy
//    Loses: Date (becomes string), undefined, functions, Map/Set, circular refs (throws)
const deep2 = JSON.parse(JSON.stringify(original));

// 3. Lodash _.cloneDeep — handles most cases including class instances
import _ from 'lodash';
const deep3 = _.cloneDeep(original);

// 4. Custom clone() method on the class — most control, used in classic Prototype pattern
class LoanTemplate {
  constructor(
    public amount: number,
    public tenor: number,
    public applicant: ApplicantInfo,
  ) {}

  clone(): LoanTemplate {
    return new LoanTemplate(
      this.amount,
      this.tenor,
      { ...this.applicant }, // explicit control over nested clone depth
    );
  }
}
```

| Method              | Handles Dates | Handles Maps/Sets | Handles Classes | Circular Refs | Performance |
|---------------------|---------------|-------------------|-----------------|---------------|-------------|
| `structuredClone`   | ✅            | ✅                | ⚠️ (loses methods) | ✅          | Fast        |
| `JSON` round-trip   | ❌            | ❌                | ❌              | ❌            | Moderate    |
| `_.cloneDeep`       | ✅            | ✅                | ✅              | ✅            | Slower      |
| Custom `clone()`    | ✅ (manual)   | ✅ (manual)       | ✅              | ✅ (manual)  | Fastest     |

**Q9. How do you implement a `clone()` method on a TypeScript class while preserving the class type?**
A: The key is returning `this` type or the concrete class, not a plain object:

```typescript
class LoanOffer {
  constructor(
    public productCode: string,
    public interestRate: number,
    public maxTenorMonths: number,
    public processingFeePercent: number,
    public features: string[],
  ) {}

  clone(): LoanOffer {
    return new LoanOffer(
      this.productCode,
      this.interestRate,
      this.maxTenorMonths,
      this.processingFeePercent,
      [...this.features], // deep copy the array
    );
  }

  withRate(rate: number): LoanOffer {
    const c = this.clone();
    c.interestRate = rate;
    return c;
  }

  withTenor(months: number): LoanOffer {
    const c = this.clone();
    c.maxTenorMonths = months;
    return c;
  }
}

// Usage — builder-style cloning
const baseOffer = new LoanOffer('HL-STD', 8.5, 240, 1.0, ['insurance', 'top-up']);
const premiumOffer = baseOffer.withRate(7.9).withTenor(300);
// baseOffer is unchanged; premiumOffer is an independent variant
```

The `withRate` / `withTenor` pattern is immutable-style API design: every method returns a new clone rather than mutating in place — safe to share, easy to test.

## Section 3: Prototype Pattern in Real-World Fintech Contexts

**Q10. How would you use the Prototype pattern for loan product templates in an Indian lending platform?**
A: Loan products (home loan, personal loan, MSME loan, LAP) share a large set of base parameters — interest rate bands, LTV ratios, tenor ranges, fee structures, eligible bureau score ranges — with small per-product variations. Creating each from scratch is repetitive and error-prone. Prototype solves this cleanly:

```typescript
interface LoanProductPrototype {
  clone(): LoanProductPrototype;
}

class LoanProduct implements LoanProductPrototype {
  constructor(
    public code: string,
    public minAmount: number,
    public maxAmount: number,
    public interestRate: number,
    public maxTenorMonths: number,
    public ltv: number,              // Loan-to-Value ratio
    public minCibilScore: number,
    public processingFee: number,
    public eligibleSegments: string[],
    public mandatoryDocs: string[],
  ) {}

  clone(): LoanProduct {
    return new LoanProduct(
      this.code,
      this.minAmount,
      this.maxAmount,
      this.interestRate,
      this.maxTenorMonths,
      this.ltv,
      this.minCibilScore,
      this.processingFee,
      [...this.eligibleSegments],
      [...this.mandatoryDocs],
    );
  }
}

// Base prototype — standard home loan
const standardHomeLoan = new LoanProduct(
  'HL-STD', 500000, 10000000, 8.5, 240, 80,
  700, 1.0, ['salaried', 'self-employed'],
  ['pan', 'aadhaar', 'income-proof', 'property-docs'],
);

// Affordable housing variant — clone and tweak
const affordableHomeLoan = standardHomeLoan.clone();
affordableHomeLoan.code = 'HL-AFF';
affordableHomeLoan.maxAmount = 3500000;         // PMAY limit
affordableHomeLoan.interestRate = 6.5;          // subsidized rate
affordableHomeLoan.minCibilScore = 650;         // relaxed for affordable segment
affordableHomeLoan.eligibleSegments = ['ews', 'lig'];

// NRI variant — clone and tweak
const nriHomeLoan = standardHomeLoan.clone();
nriHomeLoan.code = 'HL-NRI';
nriHomeLoan.ltv = 75;                           // lower LTV for NRI
nriHomeLoan.mandatoryDocs.push('pio-card', 'nre-account-statement');
```

Each variant is independent — modifying `affordableHomeLoan` doesn't affect `standardHomeLoan`. Adding a new product variant takes seconds: clone, override the three or four differing fields.

**Q11. How does Prototype apply to KYC workflow configuration across different customer segments?**
A: Different customer segments (retail salaried, retail self-employed, MSME, NRI) go through KYC workflows that are largely the same but differ in a handful of document requirements and verification steps. Prototype avoids duplicating the full workflow definition per segment:

```typescript
class KycWorkflow {
  requiredDocs: string[];
  verificationSteps: string[];
  allowVideoKyc: boolean;
  bureauChecks: string[];
  pepScreening: boolean;

  constructor(config: Partial<KycWorkflow> = {}) {
    this.requiredDocs = config.requiredDocs ?? [];
    this.verificationSteps = config.verificationSteps ?? [];
    this.allowVideoKyc = config.allowVideoKyc ?? false;
    this.bureauChecks = config.bureauChecks ?? [];
    this.pepScreening = config.pepScreening ?? false;
  }

  clone(): KycWorkflow {
    return new KycWorkflow({
      requiredDocs: [...this.requiredDocs],
      verificationSteps: [...this.verificationSteps],
      allowVideoKyc: this.allowVideoKyc,
      bureauChecks: [...this.bureauChecks],
      pepScreening: this.pepScreening,
    });
  }
}

// Base workflow
const baseKyc = new KycWorkflow({
  requiredDocs: ['pan', 'aadhaar'],
  verificationSteps: ['ocr', 'face-match', 'liveness'],
  allowVideoKyc: true,
  bureauChecks: ['cibil'],
  pepScreening: false,
});

// NRI variant — stricter
const nriKyc = baseKyc.clone();
nriKyc.requiredDocs.push('passport', 'visa', 'nre-account-statement');
nriKyc.bureauChecks.push('experian');
nriKyc.pepScreening = true;         // FEMA/PMLA requirement

// MSME variant
const msmeKyc = baseKyc.clone();
msmeKyc.requiredDocs.push('gstin', 'udyam-certificate', 'itr-2yr');
msmeKyc.verificationSteps.push('gstin-validation', 'bank-statement-analysis');
```

When RBI updates base KYC norms (e.g., Aadhaar OTP now mandatory), you update `baseKyc` once — then re-derive variants from it.

**Q12. How does Prototype help with generating test fixtures and mock loan applications in a NestJS test suite?**
A: Test suites for loan origination systems need many slightly different loan application objects (different amounts, stages, statuses, applicant profiles). Building each from scratch in every test is verbose and brittle. A prototype-based fixture factory solves this:

```typescript
// test/fixtures/loan-application.fixture.ts

const baseLoanApplication: CreateLoanApplicationDto = {
  applicantId: 'APL-001',
  productCode: 'HL-STD',
  requestedAmount: 5000000,
  tenorMonths: 180,
  purpose: 'purchase',
  employmentType: 'salaried',
  monthlyIncome: 150000,
  pan: 'ABCDE1234F',
  coApplicant: null,
};

export function loanApplicationFixture(
  overrides: Partial<CreateLoanApplicationDto> = {},
): CreateLoanApplicationDto {
  return {
    ...structuredClone(baseLoanApplication), // deep clone — nested objects safe
    ...overrides,
  };
}

// Usage in tests
describe('LoanEligibilityService', () => {
  it('should reject income below threshold', () => {
    const dto = loanApplicationFixture({ monthlyIncome: 10000 });
    expect(() => service.assess(dto)).toThrow(BadRequestException);
  });

  it('should allow co-applicant to boost eligibility', () => {
    const dto = loanApplicationFixture({
      monthlyIncome: 40000,
      coApplicant: { name: 'Meena', income: 60000, pan: 'XYZAB5678G' },
    });
    expect(() => service.assess(dto)).not.toThrow();
  });
});
```

Each test gets an independent clone — no shared mutation between tests, no `beforeEach` reset ceremony, and the intent of each test is immediately obvious from the single override.

**Q13. How would you use a prototype registry for NACH mandate templates across different banks?**
A: Different banks (HDFC, SBI, ICICI, Axis) have slightly different NACH mandate field requirements and presentation formats but share a large common structure. A registry holds a pre-configured template per bank:

```typescript
interface NachMandateTemplate {
  bankIfsc: string;
  accountType: 'savings' | 'current';
  maxAmount: number;
  frequency: 'monthly' | 'quarterly';
  sponsorCode: string;
  utilityCode: string;
  clone(): NachMandateTemplate;
}

class NachTemplateRegistry {
  private templates = new Map<string, NachMandateTemplate>();

  register(bankCode: string, template: NachMandateTemplate): void {
    this.templates.set(bankCode, template);
  }

  forBank(bankCode: string): NachMandateTemplate {
    const template = this.templates.get(bankCode);
    if (!template) throw new Error(`No NACH template for bank: ${bankCode}`);
    return template.clone(); // always return a clone — callers customize freely
  }
}

// Setup (at app bootstrap)
const registry = new NachTemplateRegistry();
registry.register('HDFC', hdfcMandateTemplate);
registry.register('SBI', sbiMandateTemplate);
registry.register('ICICI', iciciMandateTemplate);

// At loan disbursement — clone and fill per-loan fields
const mandate = registry.forBank(loan.bankCode);
mandate.maxAmount = loan.emiAmount * 1.1; // 10% buffer per NPCI guideline
mandate.accountType = loan.accountType;
await nachService.register(mandate);
```

Adding a new bank requires only registering a new template — no conditional logic in `nachService`.

## Section 4: Prototype vs. Other Creational Patterns

**Q14. When should you choose Prototype over Factory Method or Builder?**
A:

| Scenario                                                             | Best Pattern       |
|----------------------------------------------------------------------|--------------------|
| Object creation is expensive; you want to skip re-initialization     | **Prototype**      |
| You need many slight variations of a pre-configured base object      | **Prototype**      |
| You don't know which concrete class to instantiate at compile time   | **Prototype**      |
| Construction steps are complex but the starting state is always default | **Builder**     |
| You want to encapsulate which subclass gets created                  | **Factory Method** |
| You need to construct fundamentally different objects via the same interface | **Abstract Factory** |

A practical heuristic: if your first instinct is "I'll copy this existing object and change two fields," that's Prototype. If it's "I'll call `new X()` but I don't know what X is yet," that's Factory. If it's "I'll wire together 15 optional fields in a specific order," that's Builder.

**Q15. How do Prototype and Builder work together?**
A: They complement each other naturally. Builder constructs the initial prototype through a deliberate, validated setup process. Prototype then clones that validated instance for rapid variations:

```typescript
// Builder constructs the initial, fully validated prototype
const baseOffer = new LoanOfferBuilder()
  .setProduct('HL-STD')
  .setInterestRate(8.5)
  .setMaxTenor(240)
  .setLtv(80)
  .setMinCibilScore(700)
  .build(); // validates all fields, throws if invalid

// Prototype clones for cheap, fast variation
const floatingRateOffer = baseOffer.clone();
floatingRateOffer.interestRate = 8.0;
floatingRateOffer.rateType = 'floating';

const balanceTransferOffer = baseOffer.clone();
balanceTransferOffer.processingFee = 0;
balanceTransferOffer.features.push('bt-topup');
```

Builder pays the full construction + validation cost once. Prototype amortizes that cost across all variants.

**Q16. How does Prototype relate to the concept of immutability and immutable data patterns in TypeScript?**
A: Prototype and immutability are natural partners. The standard immutable update pattern — "don't mutate; return a new copy with the change" — is Prototype applied functionally:

```typescript
// Immutable Prototype pattern with readonly — "clone-on-write"
class ImmutableLoanState {
  constructor(
    readonly loanId: string,
    readonly status: LoanStatus,
    readonly amount: number,
    readonly disbursedAt: Date | null,
  ) {}

  withStatus(status: LoanStatus): ImmutableLoanState {
    return new ImmutableLoanState(this.loanId, status, this.amount, this.disbursedAt);
  }

  withDisbursement(date: Date): ImmutableLoanState {
    return new ImmutableLoanState(this.loanId, this.status, this.amount, date);
  }
}

const pending = new ImmutableLoanState('L001', 'PENDING', 500000, null);
const approved = pending.withStatus('APPROVED');
const disbursed = approved.withDisbursement(new Date());

// pending, approved, disbursed are all distinct objects — full audit trail
console.log(pending.status);   // 'PENDING'
console.log(approved.status);  // 'APPROVED'
console.log(disbursed.status); // 'APPROVED'
```

This pattern is safe for event-sourcing — every state transition produces a new object that can be stored as an event without reference aliasing issues.

## Section 5: Pitfalls & Edge Cases

**Q17. What are the main pitfalls when implementing the Prototype pattern?**
A:

- **Shallow copy bugs** — the most common mistake. Cloning a loan object that has a nested `applicant` object with spread (`{ ...loan }`) means both the original and clone share the same `applicant` reference. Mutations to one affect the other silently.
- **Circular references** — if an object contains a reference back to itself or to a parent that references the child, naive recursive deep cloning will loop infinitely. `structuredClone` and `_.cloneDeep` handle this; `JSON.parse(JSON.stringify(...))` throws.
- **Lost prototype chain / class methods** — `structuredClone` and `JSON` round-trip produce plain objects (`{}`) — they lose the class's `prototype`, meaning methods defined on the class are gone. Use a custom `clone()` method or `_.cloneDeep` when you need the result to be an actual class instance.
- **Cloning stateful resources** — never clone objects that hold OS-level resources (file handles, database connections, open sockets). Cloning a `pg.Pool` instance doesn't duplicate the connection pool — it duplicates the object wrapper while both instances point at the same underlying connections, or none at all.
- **Mutable default prototype** — if a prototype object is shared and mutable (no `clone()` called before modification), callers who modify it corrupt the template for all future clones. Always enforce clone-before-mutate discipline, ideally by making the `clone()` method the only way to obtain an instance from the registry.

**Q18. How do you handle cloning of class instances that contain `Date`, `Map`, or `Set` fields?**
A: Each requires explicit handling in a custom `clone()` method:

```typescript
class LoanAuditEntry {
  constructor(
    public loanId: string,
    public createdAt: Date,                      // Date
    public tagSet: Set<string>,                  // Set
    public metaMap: Map<string, string>,         // Map
    public history: { status: string; at: Date }[], // nested array of objects with Dates
  ) {}

  clone(): LoanAuditEntry {
    return new LoanAuditEntry(
      this.loanId,
      new Date(this.createdAt.getTime()),        // Date — construct from timestamp
      new Set(this.tagSet),                      // Set — constructor accepts iterable
      new Map(this.metaMap),                     // Map — constructor accepts iterable of entries
      this.history.map(h => ({                   // nested objects — map to new objects
        status: h.status,
        at: new Date(h.at.getTime()),
      })),
    );
  }
}
```

Alternatively, `structuredClone` handles `Date`, `Set`, and `Map` natively — but produces a plain object, losing the class methods. For domain objects that need their methods, a custom `clone()` is the right answer.

**Q19. What happens to `private` fields when cloning TypeScript class instances with `structuredClone` or spread?**
A: TypeScript `private` is a **compile-time-only** enforcement — it doesn't exist at runtime. At runtime, "private" fields are ordinary JavaScript object properties. This means:

```typescript
class LoanConfig {
  public productCode: string;
  private secretKey: string; // compile-time private only

  constructor(code: string, key: string) {
    this.productCode = code;
    this.secretKey = key;
  }
}

const original = new LoanConfig('HL-STD', 'secret-123');
const spread = { ...original };
console.log((spread as any).secretKey); // 'secret-123' — copied despite "private"

const structured = structuredClone(original);
console.log((structured as any).secretKey); // 'secret-123' — also copied
```

For true runtime encapsulation of sensitive fields that must never be cloned, use **JavaScript private fields** (the `#` syntax — a language-level feature, not TypeScript-only):

```typescript
class LoanConfig {
  public productCode: string;
  #internalToken: string; // true JS private — not enumerable, not cloneable

  constructor(code: string, token: string) {
    this.productCode = code;
    this.#internalToken = token;
  }

  clone(): LoanConfig {
    // Explicitly control whether #internalToken is carried over
    return new LoanConfig(this.productCode, this.#internalToken);
  }
}

const c = structuredClone(new LoanConfig('HL-STD', 'token'));
// c.#internalToken is undefined — structuredClone cannot access JS private fields
```

## Section 6: Scenario / System Design Style Questions

**Q20. "Your team is building a loan offer generation engine. Each customer gets a personalized offer based on a base product, but with tweaks for their credit score band, income segment, and regional adjustments. How would you use Prototype here?"**
A: Build a two-tier prototype system — base product prototypes in a registry, then segment-adjusted prototypes cloned and customized per customer:

```typescript
// Tier 1 — product-level prototypes in registry
const offerRegistry = new LoanOfferRegistry();
offerRegistry.register('HL-STD', standardHomeLoanPrototype);
offerRegistry.register('PL-STD', standardPersonalLoanPrototype);

// Tier 2 — at offer generation time, clone and apply segment adjustments
async function generateOffer(
  customer: Customer,
  productCode: string,
): Promise<LoanOffer> {
  const baseOffer = offerRegistry.clone(productCode); // Prototype clone

  // Apply credit score band adjustment
  if (customer.cibilScore >= 750) {
    baseOffer.interestRate -= 0.5;
    baseOffer.processingFee -= 0.25;
  } else if (customer.cibilScore < 650) {
    baseOffer.interestRate += 1.5;
    baseOffer.maxAmount *= 0.8;
  }

  // Apply income segment adjustment
  if (customer.segment === 'premium') {
    baseOffer.features.push('dedicated-rm', 'doorstep-service');
  }

  // Regional adjustment (e.g., lower stamp duty states)
  if (LOWER_STAMP_DUTY_STATES.includes(customer.state)) {
    baseOffer.estimatedStampDuty *= 0.5;
  }

  return baseOffer;
}
```

The product team maintains base prototypes (product managers update rates centrally). The personalization engine clones and adjusts without touching the registry's master prototypes. Each customer gets an isolated `LoanOffer` object — no cross-customer contamination.

**Q21. "You have a large NestJS test suite for the underwriting engine. Tests are slow because each test builds a complete `LoanApplication` object with related entities (applicant, co-applicant, income docs, property docs) from scratch using TypeORM factories. How would you apply Prototype to speed this up?"**
A: Replace per-test factory construction with prototype cloning:

```typescript
// test/prototypes/underwriting.prototypes.ts
// Built once — expensive factory calls happen here only
export async function buildUnderwritingPrototypes(dataSource: DataSource) {
  const applicant = await dataSource.getRepository(Applicant).save({
    name: 'Test Applicant', pan: 'ABCDE1234F', cibilScore: 720, income: 120000,
  });
  const property = await dataSource.getRepository(Property).save({
    address: '123 Test Street', valuation: 5000000, type: 'residential',
  });
  const baseLoan = await dataSource.getRepository(Loan).save({
    applicantId: applicant.id, amount: 4000000, productCode: 'HL-STD',
    propertyId: property.id, status: 'PENDING',
  });

  return { baseLoan, applicant, property }; // the prototypes
}

// In test suite
describe('UnderwritingEngine', () => {
  let protos: Awaited<ReturnType<typeof buildUnderwritingPrototypes>>;

  beforeAll(async () => {
    protos = await buildUnderwritingPrototypes(dataSource); // once for the suite
  });

  it('should approve a standard eligible loan', async () => {
    // Clone — structuredClone loses DB entity metadata, so use plain object spread
    const loan = { ...protos.baseLoan, id: uuid() }; // new ID so DB insert doesn't conflict
    await loanRepo.save(loan);
    const result = await engine.evaluate(loan.id);
    expect(result.decision).toBe('APPROVED');
  });

  it('should reject when LTV exceeds limit', async () => {
    const loan = { ...protos.baseLoan, id: uuid(), amount: 4800000 }; // >80% LTV
    await loanRepo.save(loan);
    const result = await engine.evaluate(loan.id);
    expect(result.decision).toBe('REJECTED');
  });
});
```

DB writes happen once per suite in `beforeAll`; each test clones the prototype in-memory and inserts only the delta. Suite runtime drops from O(tests × construction cost) to O(1 construction + tests × clone cost).

**Q22. "A junior developer on your team copied a loan product object with `const newProduct = existingProduct` to create a 'variant' product. What's wrong and how do you fix it?"**
A: `const newProduct = existingProduct` is not a copy — it's an alias. Both variables point to the same object in memory:

```typescript
const existingProduct = { code: 'HL-STD', rate: 8.5, maxAmount: 10000000 };
const newProduct = existingProduct; // ❌ alias, not a copy

newProduct.code = 'HL-AFF';
newProduct.rate = 6.5;

console.log(existingProduct.code); // 'HL-AFF' — existingProduct was mutated!
console.log(existingProduct.rate); // 6.5 — corruption of the original
```

The fix depends on depth of nesting:

```typescript
// Flat object — spread is sufficient
const newProduct = { ...existingProduct, code: 'HL-AFF', rate: 6.5 };

// Nested objects — structuredClone or custom clone()
const newProduct = structuredClone(existingProduct);
newProduct.code = 'HL-AFF';
newProduct.rate = 6.5;

// Class instance with methods — custom clone()
const newProduct = existingProduct.clone();
newProduct.code = 'HL-AFF';
newProduct.rate = 6.5;
```

In code review, the signal to look for is any mutation of a variable that was assigned from another object without a spread, `clone()`, or `structuredClone`. Lint rules (`no-param-reassign`, immutability ESLint plugins) can catch some of these automatically.

## Quick Reference: Prototype Implementation Checklist

| Concern                                     | Decision                                                                              |
|---------------------------------------------|--------------------------------------------------------------------------------------|
| Does the object have nested reference types? | Use deep clone (`structuredClone`, `_.cloneDeep`, or custom `clone()`)              |
| Is the object a class instance (needs methods)? | Use custom `clone()` — `structuredClone` loses the prototype chain               |
| Does it contain `Date`, `Map`, or `Set`?    | `structuredClone` (native support) or explicit construction in `clone()`             |
| Does it contain circular references?         | `structuredClone` or `_.cloneDeep` — never `JSON.parse/stringify`                   |
| Are there many variants of a base object?   | Use a prototype registry — key → prototype, clone on retrieval                       |
| Is performance critical?                    | Prefer custom `clone()` — most control, lowest overhead                              |
| Is immutability required?                   | Combine `readonly` fields with `withX()` clone-returning methods                    |
| Is it in a test fixture context?            | `structuredClone(base)` + spread overrides — simplest, no class needed              |

---

**Tip for the interview:** At the 5 YOE level, Prototype won't come up as a pure pattern question — it surfaces in disguise: "how do you manage your test fixtures," "how do you handle loan product variants without duplicating configuration," "what went wrong when your team's shallow copy shared state across objects." The shallow-vs-deep clone distinction is the first thing to demonstrate — get that wrong and the interviewer knows you haven't used it in production. Then show you know where the pattern breaks: `structuredClone` drops class methods, in-process Prototype state doesn't survive horizontal scaling, and aliasing (`=`) is not cloning. The senior differentiator is connecting Prototype to immutability — showing you use clone-returning `withX()` methods to build audit-safe, test-friendly, event-sourceable state transitions in a fintech context where loan state history is non-negotiable.
