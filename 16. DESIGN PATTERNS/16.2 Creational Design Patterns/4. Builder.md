# JavaScript / TypeScript (Design Patterns — Creational): Builder Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Builder pattern?**
A: The Builder pattern is a creational design pattern that separates the *construction* of a complex object from its *representation*, allowing the same construction process to produce different representations. Instead of a constructor with many parameters — or a single factory call that must accept every possible configuration — the Builder provides a step-by-step API where each step configures one aspect of the object being built, and a terminal `build()` call assembles and returns the final product.

The pattern solves a specific construction problem: when an object requires many configuration options, some mandatory, some optional, some with interdependencies, expressing all of that in a single constructor call becomes unreadable, error-prone, and impossible to validate incrementally.

**Q2. What problem does the Builder pattern solve that a plain constructor or object literal cannot?**
A: Three concrete problems:

- **Telescoping constructor anti-pattern** — constructors with many parameters become unreadable and force callers to pass `undefined` or `null` for options they don't need:
```ts
// Telescoping constructor — unreadable, fragile, unscalable
const query = new QueryBuilder(
  "users",      // table
  ["id","name"],// columns
  null,         // no join
  "age > 18",   // where
  null,         // no group by
  "name ASC",   // order
  10,           // limit
  0,            // offset
  false,        // no cache
  true          // include deleted
);
// What does `false` mean here? What does `null` in position 3 mean? ✗
```

- **Invalid intermediate states** — an object literal can be passed around in a partially initialised state before all required fields are set. A Builder enforces a complete, validated object is only produced at `build()` time.

- **Immutability** — once `build()` returns the product, it can be a frozen, immutable object. The builder holds the mutable state; the product is clean.

**Q3. What are the four participants in the classic Builder pattern?**
A:
- **Builder (interface/abstract)** — declares the step-by-step construction interface (`setTable()`, `setWhere()`, `setLimit()`, etc.).
- **ConcreteBuilder** — implements the Builder interface, accumulates state across steps, and produces the final product via `build()`.
- **Director** — an optional orchestrator that knows a specific sequence of Builder steps to produce a particular configuration. It encapsulates construction *recipes*. In many JavaScript implementations, the Director is omitted and callers drive the Builder directly.
- **Product** — the complex object being constructed. It is returned by the ConcreteBuilder's `build()` method, typically as an immutable snapshot.

**Q4. What is the difference between the Builder pattern and a factory function or factory method?**
A: The distinction is about *process vs single call*:

| Aspect | Factory Function / Method | Builder |
|---|---|---|
| Construction style | Single call — all config at once | Multi-step — config accumulated across calls |
| Use case | Simple objects, few parameters | Complex objects, many optional/conditional params |
| Intermediate state | None — object created atomically | Builder holds mutable state; product created at `build()` |
| Validation | At factory call time | Can be incremental (per step) and final (at `build()`) |
| Reuse | Call factory again with new args | Reuse or reset builder; step sequence is repeatable |
| Director pattern | N/A | Director can encode named construction sequences |

Use a factory when the object is simple and fully specified in one call. Use a Builder when construction is a *process* — when there are many steps, optional branches, or the caller needs to make decisions between steps.

**Q5. What are the two main styles of Builder in JavaScript/TypeScript codebases?**
A: **Classic (stateful) Builder** and **Fluent (method-chaining) Builder**:
```ts
// Classic Builder — each setter mutates internal state, returns void
const builder = new QueryBuilder();
builder.setTable("users");
builder.setWhere("age > 18");
builder.setLimit(10);
const query = builder.build();

// Fluent Builder — each setter returns `this`, enabling chaining
const query = new QueryBuilder()
  .table("users")
  .where("age > 18")
  .limit(10)
  .build();
```
The fluent style is overwhelmingly preferred in JavaScript/TypeScript because it reads like a declarative configuration block, reduces temporary variable noise, and is immediately recognisable. Both styles are the Builder pattern — the difference is purely in the return type of each setter (`void` vs `this`).

## Section 2: Implementing the Builder Pattern in TypeScript

**Q6. How do you implement a fluent Builder with full TypeScript type safety?**
A: A minimal, production-quality example using an HTTP request builder:
```ts
// Product — immutable once built
interface HttpRequest {
  readonly url:     string;
  readonly method:  "GET" | "POST" | "PUT" | "DELETE" | "PATCH";
  readonly headers: Readonly<Record<string, string>>;
  readonly body:    unknown;
  readonly timeout: number;
}

// Builder — accumulates state, returns `this` for chaining
class HttpRequestBuilder {
  private _url:     string = "";
  private _method:  HttpRequest["method"] = "GET";
  private _headers: Record<string, string> = {};
  private _body:    unknown = undefined;
  private _timeout: number = 5000;

  url(url: string): this {
    this._url = url;
    return this;
  }

  method(method: HttpRequest["method"]): this {
    this._method = method;
    return this;
  }

  header(key: string, value: string): this {
    this._headers[key] = value;
    return this;
  }

  body(body: unknown): this {
    this._body = body;
    return this;
  }

  timeout(ms: number): this {
    this._timeout = ms;
    return this;
  }

  build(): HttpRequest {
    if (!this._url) throw new Error("HttpRequest requires a URL");
    return Object.freeze({
      url:     this._url,
      method:  this._method,
      headers: Object.freeze({ ...this._headers }),
      body:    this._body,
      timeout: this._timeout,
    });
  }
}

// Usage
const request = new HttpRequestBuilder()
  .url("https://api.example.com/orders")
  .method("POST")
  .header("Content-Type", "application/json")
  .header("Authorization", `Bearer ${token}`)
  .body({ items: [{ id: "1", qty: 2 }] })
  .timeout(3000)
  .build();
```

**Q7. How do you enforce mandatory fields at compile time rather than at runtime in a TypeScript Builder?**
A: Use the **Step Builder** pattern (also called a Staged Builder) — the Builder's type changes at each step, and the `build()` method only becomes available once all required steps have been called:
```ts
// Each stage is a distinct interface — build() only on the final stage
interface NeedsUrl  { url(url: string): NeedsMethod; }
interface NeedsMethod {
  method(m: HttpRequest["method"]): OptionalSteps;
}
interface OptionalSteps {
  header(key: string, value: string): OptionalSteps;
  body(body: unknown): OptionalSteps;
  timeout(ms: number): OptionalSteps;
  build(): HttpRequest;  // ← only available after url + method
}

class HttpRequestBuilder implements NeedsUrl, NeedsMethod, OptionalSteps {
  private _url    = "";
  private _method: HttpRequest["method"] = "GET";
  private _headers: Record<string, string> = {};
  private _body:    unknown;
  private _timeout  = 5000;

  static create(): NeedsUrl { return new HttpRequestBuilder(); }

  url(url: string): NeedsMethod         { this._url = url;       return this; }
  method(m: HttpRequest["method"]): OptionalSteps { this._method = m; return this; }
  header(k: string, v: string): OptionalSteps { this._headers[k] = v; return this; }
  body(b: unknown): OptionalSteps        { this._body = b;        return this; }
  timeout(ms: number): OptionalSteps     { this._timeout = ms;    return this; }

  build(): HttpRequest {
    return Object.freeze({
      url: this._url, method: this._method,
      headers: Object.freeze({...this._headers}),
      body: this._body, timeout: this._timeout,
    });
  }
}

// Compile-time enforcement — build() is not available until url() and method() are called
const req = HttpRequestBuilder
  .create()
  .url("https://api.example.com")   // returns NeedsMethod
  .method("GET")                    // returns OptionalSteps
  .timeout(3000)                    // returns OptionalSteps
  .build();                         // ✓ — only reachable after mandatory steps

// This fails at compile time — build() doesn't exist on NeedsMethod
// HttpRequestBuilder.create().url("...").build(); // ✗ TypeScript error
```

**Q8. How do you implement a Builder that supports resetting or cloning state for building multiple similar objects?**
A: Two approaches — `reset()` for reuse, or `clone()` for building variations from a base:
```ts
class QueryBuilder {
  private table_:   string  = "";
  private where_:   string  = "";
  private orderBy_: string  = "";
  private limit_:   number  = 100;
  private offset_:  number  = 0;

  table(t: string):   this { this.table_ = t;   return this; }
  where(w: string):   this { this.where_ = w;   return this; }
  orderBy(o: string): this { this.orderBy_ = o; return this; }
  limit(n: number):   this { this.limit_ = n;   return this; }
  offset(n: number):  this { this.offset_ = n;  return this; }

  // Reset — return builder to initial state for reuse
  reset(): this {
    this.table_ = ""; this.where_ = "";
    this.orderBy_ = ""; this.limit_ = 100; this.offset_ = 0;
    return this;
  }

  // Clone — snapshot current state; mutate clone without affecting original
  clone(): QueryBuilder {
    const copy = new QueryBuilder();
    copy.table_ = this.table_; copy.where_ = this.where_;
    copy.orderBy_ = this.orderBy_; copy.limit_ = this.limit_;
    copy.offset_ = this.offset_;
    return copy;
  }

  build(): Query {
    if (!this.table_) throw new Error("table is required");
    return { table: this.table_, where: this.where_,
             orderBy: this.orderBy_, limit: this.limit_, offset: this.offset_ };
  }
}

// Base query for a screen — clone to produce page variants
const base = new QueryBuilder().table("orders").where("status = 'active'").orderBy("createdAt DESC");
const page1 = base.clone().limit(20).offset(0).build();
const page2 = base.clone().limit(20).offset(20).build();
```

**Q9. How does a Director fit into the pattern, and when is it useful?**
A: A Director encapsulates a named construction *recipe* — a fixed sequence of builder steps that produces a specific, known configuration. It's useful when the same complex object is constructed in multiple places with the same configuration:
```ts
// Without Director — construction recipe duplicated at every call site
const devRequest = new HttpRequestBuilder()
  .url("http://localhost:3000/api")
  .method("GET")
  .header("X-Debug", "true")
  .timeout(30000)
  .build();

// With Director — recipe is named and centralised
class HttpRequestDirector {
  constructor(private builder: HttpRequestBuilder) {}

  buildDevRequest(path: string): HttpRequest {
    return this.builder
      .url(`http://localhost:3000${path}`)
      .method("GET")
      .header("X-Debug", "true")
      .timeout(30000)
      .build();
  }

  buildProdRequest(path: string, token: string): HttpRequest {
    return this.builder
      .url(`https://api.example.com${path}`)
      .method("GET")
      .header("Authorization", `Bearer ${token}`)
      .header("Accept", "application/json")
      .timeout(5000)
      .build();
  }
}

const director = new HttpRequestDirector(new HttpRequestBuilder());
const req = director.buildDevRequest("/orders");
```
Directors are most valuable in codebases that build the same complex objects repeatedly from different call sites. In many JavaScript codebases, static factory methods on the Builder itself serve the same purpose with less boilerplate.

## Section 3: Real-World Applications

**Q10. How is the Builder pattern used in query building (SQL / ORM / Elasticsearch)?**
A: Query builders are the canonical real-world Builder application. Knex.js, TypeORM's `QueryBuilder`, Prisma's fluent API, and Elasticsearch's body builder all implement this pattern:
```ts
// TypeORM QueryBuilder — classic Builder in a production ORM
const orders = await dataSource
  .getRepository(Order)
  .createQueryBuilder("order")
  .innerJoinAndSelect("order.customer", "customer")
  .where("order.status = :status", { status: "active" })
  .andWhere("customer.country = :country", { country: "IN" })
  .orderBy("order.createdAt", "DESC")
  .limit(20)
  .offset(0)
  .getMany();

// Custom SQL QueryBuilder implementation
class SqlQueryBuilder {
  private parts: {
    table:   string;
    joins:   string[];
    wheres:  string[];
    params:  unknown[];
    orderBy: string;
    limit_:  number;
    offset_: number;
  } = { table: "", joins: [], wheres: [], params: [], orderBy: "", limit_: 100, offset_: 0 };

  from(table: string): this         { this.parts.table = table; return this; }
  join(clause: string): this         { this.parts.joins.push(clause); return this; }
  where(clause: string, ...params: unknown[]): this {
    this.parts.wheres.push(clause);
    this.parts.params.push(...params);
    return this;
  }
  orderBy(col: string, dir: "ASC"|"DESC" = "ASC"): this {
    this.parts.orderBy = `${col} ${dir}`; return this;
  }
  limit(n: number):  this { this.parts.limit_  = n; return this; }
  offset(n: number): this { this.parts.offset_ = n; return this; }

  build(): { sql: string; params: unknown[] } {
    if (!this.parts.table) throw new Error("FROM clause required");
    const joins   = this.parts.joins.join(" ");
    const wheres  = this.parts.wheres.length
      ? `WHERE ${this.parts.wheres.join(" AND ")}`
      : "";
    const orderBy = this.parts.orderBy ? `ORDER BY ${this.parts.orderBy}` : "";
    const sql = [
      `SELECT * FROM ${this.parts.table}`,
      joins, wheres, orderBy,
      `LIMIT ${this.parts.limit_} OFFSET ${this.parts.offset_}`
    ].filter(Boolean).join(" ");
    return { sql, params: this.parts.params };
  }
}
```

**Q11. How does the Builder pattern apply to form validation schemas (Zod, Yup)?**
A: Schema libraries implement the Builder pattern — each method call configures a validation rule and returns the schema object (the builder), and the schema itself is the product:
```ts
import { z } from "zod";

// Zod — fluent builder for validation schemas
const CreateUserSchema = z.object({
  name:     z.string().min(2).max(100).trim(),
  email:    z.string().email().toLowerCase(),
  age:      z.number().int().min(18).max(120).optional(),
  role:     z.enum(["admin", "user", "guest"]).default("user"),
  password: z.string()
    .min(8)
    .regex(/[A-Z]/, "Must contain uppercase")
    .regex(/[0-9]/, "Must contain a number"),
});

type CreateUserDto = z.infer<typeof CreateUserSchema>;

// The schema IS the product — immutable, reusable, composable
const AdminSchema = CreateUserSchema.extend({
  adminCode: z.string().uuid(),
});
```
Each `.min()`, `.max()`, `.regex()` call returns a new schema (immutable builder step), and the final schema object is the product. This is the immutable variant of the Builder — rather than mutating internal state, each step returns a new builder instance.

**Q12. How does the Builder pattern apply to test data builders (the "Test Data Builder" pattern)?**
A: Test data builders are one of the most valuable Builder applications — they construct complex domain objects with sensible defaults for tests, allowing each test to override only the fields relevant to what it's testing:
```ts
// Test Data Builder — sensible defaults, override only what the test cares about
class OrderBuilder {
  private props: Order = {
    id:         "order-1",
    customerId: "customer-1",
    status:     "pending",
    items:      [{ productId: "prod-1", qty: 1, price: 100 }],
    total:      100,
    createdAt:  new Date("2026-01-01"),
    shippingAddress: {
      line1: "123 Main St", city: "Mumbai", country: "IN", postcode: "400001"
    },
  };

  withId(id: string):             this { this.props.id = id;               return this; }
  withStatus(s: Order["status"]): this { this.props.status = s;            return this; }
  withTotal(t: number):           this { this.props.total = t;             return this; }
  withCustomerId(id: string):     this { this.props.customerId = id;       return this; }
  withItems(items: OrderItem[]):  this { this.props.items = items;         return this; }
  withCreatedAt(d: Date):         this { this.props.createdAt = d;         return this; }

  build(): Order { return { ...this.props }; }

  // Named factory shortcuts for common test scenarios
  static pending():   OrderBuilder { return new OrderBuilder(); }
  static completed(): OrderBuilder { return new OrderBuilder().withStatus("completed"); }
  static cancelled(): OrderBuilder { return new OrderBuilder().withStatus("cancelled"); }
}

// Tests are now expressive — each test configures only what it cares about
describe("refund eligibility", () => {
  it("allows refund within 30 days of completion", () => {
    const order = OrderBuilder.completed()
      .withCreatedAt(new Date("2026-07-01"))
      .build();
    expect(isRefundEligible(order)).toBe(true);
  });

  it("denies refund after 30 days", () => {
    const order = OrderBuilder.completed()
      .withCreatedAt(new Date("2026-01-01"))
      .build();
    expect(isRefundEligible(order)).toBe(false);
  });
});
```
Without the builder, each test would either construct a full `Order` object (noisy, masks what the test is actually about) or use `as unknown as Order` casts (unsafe, breaks on schema changes).

**Q13. How does the Builder pattern apply to building configuration objects for services or frameworks?**
A: Complex service configuration is a classic Builder use case — think NestJS module builders, Express router builders, or custom service config:
```ts
// Service configuration builder — step-by-step assembly of complex config
class ServerConfigBuilder {
  private config: ServerConfig = {
    port:        3000,
    host:        "0.0.0.0",
    cors:        { enabled: false, origins: [] },
    rateLimit:   { enabled: false, max: 100, windowMs: 60000 },
    compression: false,
    logging:     { level: "info", format: "json" },
    tls:         null,
  };

  port(p: number):                    this { this.config.port = p;              return this; }
  host(h: string):                    this { this.config.host = h;              return this; }
  enableCors(origins: string[]):       this {
    this.config.cors = { enabled: true, origins };                              return this;
  }
  enableRateLimit(max: number, windowMs: number): this {
    this.config.rateLimit = { enabled: true, max, windowMs };                  return this;
  }
  enableCompression():                 this { this.config.compression = true;   return this; }
  logLevel(level: "debug"|"info"|"warn"|"error"): this {
    this.config.logging.level = level;                                          return this;
  }
  enableTLS(certPath: string, keyPath: string): this {
    this.config.tls = { certPath, keyPath };                                    return this;
  }

  build(): Readonly<ServerConfig> {
    if (this.config.tls && this.config.port === 3000) {
      // Cross-field validation — only possible in build()
      throw new Error("TLS should not use the default dev port 3000");
    }
    return Object.freeze({ ...this.config });
  }
}

// Production configuration — readable, self-documenting
const prodConfig = new ServerConfigBuilder()
  .port(443)
  .host("0.0.0.0")
  .enableCors(["https://app.example.com"])
  .enableRateLimit(500, 60000)
  .enableCompression()
  .logLevel("warn")
  .enableTLS("/certs/cert.pem", "/certs/key.pem")
  .build();
```

**Q14. How does the Builder pattern appear in React (component props builders, `renderProps`, testing with `@testing-library`)?**
A: In React, the Builder pattern manifests in several forms:
```tsx

const { getByRole } = render(<LoginForm />);
```

## Section 4: Variants and Related Patterns

**Q15. What is the difference between the Builder pattern and the Fluent Interface pattern?**
A: They frequently co-occur but are distinct:
- **Fluent Interface** is a *style* — an API design where methods return `this` (or the next object in a chain) to enable method chaining. It's a syntactic technique.
- **Builder pattern** is a *structural pattern* — it separates construction from representation, accumulates state across steps, and produces a distinct product at the end.

A Builder often *uses* a fluent interface (method chaining via `return this`), but a fluent interface is not always a Builder. jQuery's `$("selector").addClass("foo").hide()` is a fluent interface but not a Builder — there's no complex product being assembled and no `build()` step. TypeORM's `QueryBuilder` is both — it's fluent *and* produces a distinct query product via `getMany()` or `getRawMany()`.

**Q16. What is the immutable Builder variant, and when do you use it?**
A: The immutable Builder returns a *new builder instance* on each step rather than mutating `this`. Each step is side-effect-free, making the Builder itself composable and sharable as a base:
```ts
// Immutable Builder — each step returns a new instance
class ImmutableQueryBuilder {
  private constructor(private readonly state: QueryState = defaultQueryState) {}

  static create(): ImmutableQueryBuilder { return new ImmutableQueryBuilder(); }

  table(t: string): ImmutableQueryBuilder {
    return new ImmutableQueryBuilder({ ...this.state, table: t });
  }

  where(w: string): ImmutableQueryBuilder {
    return new ImmutableQueryBuilder({
      ...this.state,
      wheres: [...this.state.wheres, w]
    });
  }

  limit(n: number): ImmutableQueryBuilder {
    return new ImmutableQueryBuilder({ ...this.state, limit: n });
  }

  build(): Query {
    return { ...this.state };
  }
}

// Base query shared safely — no mutation risk
const activeOrders = ImmutableQueryBuilder.create()
  .table("orders")
  .where("status = 'active'");

// Both derived queries start from the same base — no interference
const page1 = activeOrders.limit(20).build();
const page2 = activeOrders.where("country = 'IN'").limit(20).build();
```
Use the immutable variant when builders are shared across threads/contexts (unlikely in single-threaded JS but relevant for configuration objects), stored and reused as templates, or when functional programming immutability is a team convention.

**Q17. What is the relationship between Builder and the Factory Method / Abstract Factory patterns?**
A: They are complementary creational patterns with different scopes:
- **Factory Method / Abstract Factory** — creates objects in a *single call*, abstracting over *which* concrete type is created. Focus: what type to create.
- **Builder** — creates objects through a *sequence of steps*, abstracting over *how* to configure the type. Focus: how to construct.

They compose naturally: a Factory can *return* a configured Builder (producing the right builder type for a context), or a Director can *use* a Factory to select the right ConcreteBuilder for a given environment:
```ts
// Factory returns the right Builder for the environment
function createRequestBuilder(env: "dev" | "prod"): HttpRequestBuilder {
  if (env === "dev") {
    return new HttpRequestBuilder()
      .url("http://localhost:3000")
      .header("X-Debug", "true")
      .timeout(30000);
  }
  return new HttpRequestBuilder()
    .url("https://api.example.com")
    .timeout(5000);
}

// Caller continues building on the pre-configured base
const request = createRequestBuilder("dev")
  .method("POST")
  .body({ test: true })
  .build();
```

**Q18. How does the Builder pattern relate to the Object Mother pattern in testing?**
A: Both create test fixtures, but they serve different roles:
- **Object Mother** — a class with static factory methods that return pre-built, named fixture objects for common test scenarios (`OrderMother.pendingOrder()`, `UserMother.adminUser()`). Simple, no configuration — you get a fixed object.
- **Test Data Builder** — a Builder with defaults, allowing fine-grained customisation per test. You start from defaults and override only what matters for the current test scenario.

They are complementary and often combined: Object Mother methods delegate to a Builder internally, giving callers both a quick path (Mother static method) and a customisation path (Builder API):
```ts
class OrderMother {
  // Quick path — fixed, named scenarios
  static pending():   Order { return new OrderBuilder().build(); }
  static completed(): Order { return new OrderBuilder().withStatus("completed").build(); }

  // Customisation path — full Builder access
  static builder(): OrderBuilder { return new OrderBuilder(); }
}

// Quick — test doesn't care about order details
const order = OrderMother.pending();

// Custom — test cares about a specific total
const highValueOrder = OrderMother.builder().withTotal(10000).withStatus("completed").build();
```

## Section 5: Pitfalls and Anti-Patterns

**Q19. What are the signs that you're misusing the Builder pattern?**
A: Several indicators:

- **Builder for simple objects** — if an object has two or three fields, a plain object literal or a factory function is cleaner. Builder overhead (a whole class, a `build()` call) is unjustified for `{ x: 1, y: 2 }`.
- **Mandatory step omission with no enforcement** — a Builder where `build()` silently produces an invalid object because a required step was skipped. Always validate at `build()` time or use the Step Builder to enforce steps at compile time.
- **Mutable product** — `build()` returns a reference to the builder's internal mutable state object rather than a copy or frozen snapshot. Callers can mutate the "built" object, defeating the pattern.
- **Chaining that doesn't build** — method chaining that modifies and returns the *same* domain object rather than building a *new* product. This is a fluent interface on the product, not a Builder.
- **Director with a single recipe** — if the Director only ever calls one fixed sequence, it's just a factory function in disguise. Directors earn their place when they encode multiple distinct named recipes.

**Q20. What is the "incomplete build" problem, and how do you guard against it?**
A: The incomplete build problem is when a caller forgets to call `build()` and instead uses the Builder object itself as if it were the product:
```ts
// Incomplete build — forgot .build(), using the Builder as the product
const query = new QueryBuilder().table("users").where("active = true");
// query is a QueryBuilder, not a Query — type error deferred to runtime

// Guard 1 — TypeScript types: Builder and Product are distinct types
// The caller's type annotation catches this immediately
const query: Query = new QueryBuilder().table("users").build(); // ✓

// Guard 2 — Step Builder: build() only available as the terminal step
// Callers can't "forget" build() because the type forces them to call it

// Guard 3 — Symbol.toPrimitive / toString override on Builder
// Makes accidental use of Builder-as-value produce a clear error
class QueryBuilder {
  [Symbol.toPrimitive]() {
    throw new Error("QueryBuilder must be terminated with .build()");
  }
}
```

**Q21. How does mutable shared builder state cause bugs, and how do you prevent it?**
A: When a Builder instance is shared between call sites (accidentally or intentionally), steps from one call site bleed into another's product:
```ts
// Shared builder state bug — one builder instance, two callers
const sharedBuilder = new QueryBuilder().table("orders");

// Site A — adds a where clause
const q1 = sharedBuilder.where("status = 'active'").build();

// Site B — unaware that sharedBuilder now has the where clause from Site A
const q2 = sharedBuilder.limit(10).build();
// q2 unexpectedly includes "WHERE status = 'active'" — state leaked ✗

// Prevention — three options:
// 1. Never share builder instances — create a new one per product
const q1 = new QueryBuilder().table("orders").where("status = 'active'").build();
const q2 = new QueryBuilder().table("orders").limit(10).build();

// 2. Call reset() between builds
sharedBuilder.reset();
const q2 = sharedBuilder.table("orders").limit(10).build();

// 3. Use the immutable Builder — each step returns a new instance
const base = ImmutableQueryBuilder.create().table("orders");
const q1   = base.where("status = 'active'").build(); // base unaffected
const q2   = base.limit(10).build();                  // base still clean
```

**Q22. "A REST API client SDK has a single `fetch(url, method, headers, body, timeout, retries, cacheKey, onProgress, auth)` function with 9 parameters. How do you refactor this with a Builder?"**
A: Nine positional parameters is the telescoping constructor problem at the function level. The Builder transformation:
```ts
// Before — 9-parameter function call
await fetch(
  "https://api.example.com/orders",
  "POST",
  { "Content-Type": "application/json" },
  body,
  5000,
  3,
  null,
  null,
  { type: "bearer", token }
);

// After — expressive, self-documenting, validated Builder
class ApiRequestBuilder {
  private _url     = "";
  private _method: Method = "GET";
  private _headers: Record<string, string> = {};
  private _body:    unknown;
  private _timeout = 5000;
  private _retries = 0;
  private _cacheKey: string | null = null;
  private _onProgress: ((pct: number) => void) | null = null;
  private _auth: AuthConfig | null = null;

  url(u: string):                        this { this._url = u;            return this; }
  method(m: Method):                     this { this._method = m;         return this; }
  header(k: string, v: string):          this { this._headers[k] = v;    return this; }
  jsonBody(body: unknown):               this {
    this._body = body;
    this._headers["Content-Type"] = "application/json";
    return this;
  }
  timeout(ms: number):                   this { this._timeout = ms;       return this; }
  retries(n: number):                    this { this._retries = n;        return this; }
  cache(key: string):                    this { this._cacheKey = key;     return this; }
  onProgress(fn: (pct: number) => void): this { this._onProgress = fn;   return this; }
  bearerAuth(token: string):             this {
    this._auth = { type: "bearer", token };                               return this;
  }

  async send(): Promise<ApiResponse> {
    if (!this._url) throw new Error("URL is required");
    return executeFetch({
      url: this._url, method: this._method, headers: this._headers,
      body: this._body, timeout: this._timeout, retries: this._retries,
      cacheKey: this._cacheKey, onProgress: this._onProgress, auth: this._auth,
    });
  }
}

// Readable, parameter-order-independent, self-documenting
await new ApiRequestBuilder()
  .url("https://api.example.com/orders")
  .method("POST")
  .bearerAuth(token)
  .jsonBody(body)
  .timeout(5000)
  .retries(3)
  .send();
```

**Q23. "Your team writes a lot of integration tests that each build a full `User` object with 15 fields. Tests are brittle because every schema change breaks dozens of test files. How does the Test Data Builder pattern fix this?"**
A: The root problem is that tests are coupled to the full `User` schema — every test constructs the whole object, so every schema change ripples to every test. The Test Data Builder centralises construction and provides sensible defaults:
```ts
// Before — every test constructs a full User: brittle, coupled to schema
const user: User = {
  id: "u1", name: "Alice", email: "alice@test.com",
  role: "user", createdAt: new Date(), updatedAt: new Date(),
  isVerified: true, isActive: true, plan: "free",
  preferences: { notifications: true, theme: "light" },
  address: { line1: "123 St", city: "Delhi", country: "IN", postcode: "110001" },
  paymentMethodId: null, lastLoginAt: new Date(),
  twoFactorEnabled: false
};
// Adding a new required field → update every single test ✗

// After — Test Data Builder with defaults: tests override only what they care about
class UserBuilder {
  private props: User = {
    id: "user-1", name: "Alice Test", email: "alice@test.com",
    role: "user", createdAt: new Date("2026-01-01"), updatedAt: new Date("2026-01-01"),
    isVerified: true, isActive: true, plan: "free",
    preferences: { notifications: true, theme: "light" },
    address: { line1: "1 Test St", city: "Delhi", country: "IN", postcode: "110001" },
    paymentMethodId: null, lastLoginAt: new Date("2026-01-01"),
    twoFactorEnabled: false,
  };

  withId(id: string):                    this { this.props.id = id;                    return this; }
  withRole(role: User["role"]):          this { this.props.role = role;                return this; }
  withPlan(plan: User["plan"]):          this { this.props.plan = plan;                return this; }
  withEmail(email: string):              this { this.props.email = email;              return this; }
  verified(v = true):                    this { this.props.isVerified = v;             return this; }
  active(v = true):                      this { this.props.isActive = v;               return this; }
  withTwoFactor():                       this { this.props.twoFactorEnabled = true;    return this; }
  build(): User { return { ...this.props }; }
}

// Adding a new field to User? Update the Builder defaults once — all tests unaffected
// Tests express exactly what they're testing and nothing more:
it("blocks login for unverified users", () => {
  const user = new UserBuilder().verified(false).build();
  expect(canLogin(user)).toBe(false);
});

it("allows admin access for admin role", () => {
  const user = new UserBuilder().withRole("admin").build();
  expect(hasAdminAccess(user)).toBe(true);
});
```
Schema changes now require one update: the builder's default. All tests that don't care about the new field continue to pass without any changes.

**Q24. "You're building a report generation system where reports have different sections — summary, charts, tables, appendices — and not all reports have all sections. How would you design this with a Builder?"**
A: Report generation is the classic "complex object with many optional parts" use case:
```ts
// Report Product — immutable once built
interface Report {
  readonly title:      string;
  readonly generatedAt: Date;
  readonly summary?:   SummarySection;
  readonly charts:     ChartSection[];
  readonly tables:     TableSection[];
  readonly appendices: AppendixSection[];
  readonly metadata:   ReportMetadata;
}

class ReportBuilder {
  private title_     = "Untitled Report";
  private summary_:  SummarySection | undefined;
  private charts_:   ChartSection[]   = [];
  private tables_:   TableSection[]   = [];
  private appendices_: AppendixSection[] = [];
  private metadata_: ReportMetadata = { format: "pdf", locale: "en-IN", pageSize: "A4" };

  title(t: string): this { this.title_ = t; return this; }

  withSummary(text: string, highlights: string[]): this {
    this.summary_ = { text, highlights };
    return this;
  }

  addChart(type: ChartType, data: ChartData, caption: string): this {
    this.charts_.push({ type, data, caption });
    return this;
  }

  addTable(headers: string[], rows: string[][], caption: string): this {
    this.tables_.push({ headers, rows, caption });
    return this;
  }

  addAppendix(title: string, content: string): this {
    this.appendices_.push({ title, content });
    return this;
  }

  format(f: "pdf" | "xlsx" | "html"): this { this.metadata_.format = f; return this; }
  locale(l: string): this { this.metadata_.locale = l;   return this; }

  build(): Report {
    if (!this.title_) throw new Error("Report title is required");
    if (this.charts_.length === 0 && this.tables_.length === 0 && !this.summary_) {
      throw new Error("Report must have at least one section");
    }
    return Object.freeze({
      title:       this.title_,
      generatedAt: new Date(),
      summary:     this.summary_,
      charts:      [...this.charts_],
      tables:      [...this.tables_],
      appendices:  [...this.appendices_],
      metadata:    Object.freeze({ ...this.metadata_ }),
    });
  }
}

// Director — named report recipes
class ReportDirector {
  static buildMonthlySalesReport(data: SalesData): Report {
    return new ReportBuilder()
      .title(`Sales Report — ${data.month}`)
      .withSummary(data.executiveSummary, data.highlights)
      .addChart("bar",  data.revenueByWeek,    "Weekly Revenue")
      .addChart("pie",  data.revenueByProduct, "Revenue by Product")
      .addTable(data.topCustomers.headers, data.topCustomers.rows, "Top 10 Customers")
      .addAppendix("Methodology", data.methodology)
      .format("pdf")
      .build();
  }

  static buildInventorySnapshot(data: InventoryData): Report {
    return new ReportBuilder()
      .title("Inventory Snapshot")
      .addTable(data.stockLevels.headers, data.stockLevels.rows, "Current Stock Levels")
      .addChart("bar", data.lowStockItems, "Low Stock Alert")
      .format("xlsx")
      .build();
  }
}
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Plain Constructor / Object Literal | Factory Function | Builder Pattern |
|---|---|---|---|
| **Parameter count** | Any — gets unreadable past 4–5 | Any — same readability limit | Unlimited — each step is named |
| **Optional params** | `undefined` / overloads — messy | Default args — limited | Named methods — clean, self-documenting |
| **Validation** | At construction time only | At call time only | Per step + final at `build()` |
| **Mandatory fields** | Enforced by TypeScript types | Enforced by TypeScript types | Enforced at `build()` or by Step Builder |
| **Immutable product** | Requires `Object.freeze` manually | Requires `Object.freeze` manually | Natural — builder holds state; `build()` returns frozen copy |
| **Reuse / variation** | New call with new args | New call with new args | `clone()` or base builder + overrides |
| **Readability** | Low past 4 params | Moderate | High — step names document intent |
| **Overhead** | None | Minimal | Extra class + API surface |
| **Best for** | Simple objects | Simple objects with type variance | Complex objects with many optional steps |

## Builder Pattern Variants at a Glance

| Variant | Key characteristic | Best used for |
|---|---|---|
| **Classic (stateful)** | Setters return `void`; explicit variable needed | Simple cases; Java-style OOP codebases |
| **Fluent (method chaining)** | Setters return `this` | Most JavaScript/TypeScript codebases |
| **Step Builder (staged)** | Each step returns a different interface type; `build()` only on final stage | Mandatory field enforcement at compile time |
| **Immutable Builder** | Each step returns a new Builder instance | Functional codebases; shared base builders |
| **Test Data Builder** | Sensible defaults; `with*` overrides per field | Test fixture construction |
| **Director + Builder** | Director encodes named construction recipes | Multiple known configurations of the same product |

**Tip for the interview:** At the 5 YOE level, "what is the Builder pattern" won't come up as a definition question — it surfaces as: how do you handle a constructor with 10 parameters, how do you make test fixtures maintainable when the schema changes, how would you design a query API for a reporting system, or how do you enforce that a complex object is always constructed in a valid state. The sharp answer names the specific problem (telescoping constructor, invalid intermediate state, scattered test fixture construction), proposes the Builder as the solution, shows the fluent API, mentions `build()`-time validation, and connects it to a real-world example they've used — a query builder, a test data builder, a Zod schema, or a configuration builder. If pushed on TypeScript specifics, the Step Builder's staged interface types (where `build()` only becomes available after mandatory steps) demonstrates depth that lands at 5 YOE.
