# Dependency Injection with NestJS — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Dependency Injection, and why does NestJS make it central to its design?**
A: Dependency Injection (DI) is a design pattern in which a class receives its dependencies from an external source rather than constructing them itself. Instead of `new BureauService()` inside a loan service, the DI container creates `BureauService` and *injects* it into `LoanApplicationService`.

NestJS makes DI central because it solves three structural problems that grow with codebase size:

- **Tight coupling** — without DI, `LoanApplicationService` knows about `BureauService`'s constructor, its dependencies, and how to wire them. Change `BureauService`'s constructor and you must touch every class that creates it.
- **Untestable code** — without DI, you cannot substitute a mock `BureauService` in unit tests. The real implementation — network calls and all — runs in every test.
- **Manual lifecycle management** — without DI, every class manages whether its dependency is a singleton or a new instance. NestJS's IoC container handles this automatically and consistently.

NestJS's DI is inspired by Angular and built on top of its own IoC container — not `reflect-metadata` alone, but a full hierarchical injector with module scoping, request-scoped providers, and circular dependency handling.

**Q2. What are the core building blocks of NestJS's DI system?**
A:

| Building Block | Role |
|---|---|
| **Provider** | Any class, value, or factory registered in the DI container via `@Injectable()` or explicit token |
| **Injector** | The NestJS IoC container — creates, stores, and resolves providers |
| **Token** | The key used to look up a provider — typically the class itself, a string, or a `Symbol` |
| **Module** | The unit of DI scope — declares which providers exist and which are exported to other modules |
| **`@Injectable()`** | Decorator that marks a class as a provider eligible for injection |
| **`@Inject(token)`** | Used when the token is not a class (string, Symbol, `InjectionToken`) |

The lifecycle:
1. `@Module` registers providers with the container
2. Container resolves the dependency graph (detects circular deps at startup)
3. Container instantiates providers in dependency order
4. Instances are injected via constructor parameters into dependent classes

**Q3. What is the difference between a Provider, a Service, and an Injectable in NestJS?**
A: These are related but distinct:

- **`@Injectable()`** — a TypeScript decorator that emits metadata enabling NestJS to reflect a class's constructor parameter types. It marks the class as *eligible* to be managed by the DI container. Every service, repository, guard, interceptor, and pipe that participates in DI needs this decorator.
- **Provider** — the registration descriptor in a `@Module`. A provider maps a *token* to a *value factory*. The simplest provider is just a class (`providers: [LoanService]`), but providers can also be value providers, factory providers, or aliased providers.
- **Service** — a naming convention, not a NestJS concept. `LoanApplicationService` is a service *by name* because it lives in the service layer. NestJS doesn't distinguish "service" from "repository" — both are providers. The name is a team convention that maps to CSR layer responsibilities.

```typescript
// All three are @Injectable() — NestJS treats them identically at the DI level
@Injectable() export class LoanApplicationService {}   // "service"
@Injectable() export class LoanRepository {}           // "repository"
@Injectable() export class JwtAuthGuard implements CanActivate {}  // "guard"
@Injectable() export class LoggingInterceptor implements NestInterceptor {} // "interceptor"
```

**Q4. How does NestJS resolve constructor dependencies automatically?**
A: NestJS uses `reflect-metadata` to read the type information emitted by TypeScript's `emitDecoratorMetadata` compiler option. When you write:

```typescript
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly loanRepository: LoanRepository,
    private readonly bureauService: BureauService,
  ) {}
}
```

TypeScript emits metadata: `design:paramtypes → [LoanRepository, BureauService]`. NestJS reads this at module initialisation, looks up the container for providers registered under those class tokens, and injects the resolved instances into the constructor.

This is why `tsconfig.json` must have:
```json
{
  "compilerOptions": {
    "emitDecoratorMetadata": true,
    "experimentalDecorators": true
  }
}
```

Without `emitDecoratorMetadata`, the type information is erased at compile time and NestJS cannot resolve constructor parameters — you'd get a runtime error or `undefined` injections.

**Q5. What is a NestJS Module and how does it scope the DI container?**
A: A `@Module` is the unit of encapsulation. Each module has its own scoped container — providers declared in one module are *not* available in another unless explicitly exported.

```typescript
@Module({
  imports: [TypeOrmModule.forFeature([LoanEntity]), BureauModule],
  controllers: [LoanApplicationController],
  providers: [
    LoanApplicationService,   // available only within LoanModule
    LoanRepository,           // available only within LoanModule
  ],
  exports: [LoanApplicationService],  // now available to any module that imports LoanModule
})
export class LoanModule {}
```

Rules of module scoping:
- A provider is visible only within the module that declares it.
- To share a provider, `exports` must list it, and the consuming module must `imports` the declaring module.
- `@Global()` makes a module's exports available everywhere without explicit import — use sparingly (config, logging, event emitter).

```typescript
@Global()
@Module({
  providers: [ConfigService, LoggerService],
  exports: [ConfigService, LoggerService],
})
export class CoreModule {}
```

## Section 2: Provider Types in Depth

**Q6. What are the four provider types in NestJS and when do you use each?**
A:

**1. Class Provider (most common)**
```typescript
// Shorthand — token = class itself
providers: [LoanApplicationService]

// Explicit longhand (same result)
providers: [{ provide: LoanApplicationService, useClass: LoanApplicationService }]
```
Use for: every service, repository, guard, interceptor — the default for anything `@Injectable()`.

**2. Value Provider**
```typescript
providers: [
  { provide: 'APP_CONFIG', useValue: { maxLoanAmount: 10_000_000_00, minBureauScore: 650 } },
  { provide: 'RAZORPAY_KEY', useValue: process.env.RAZORPAY_KEY },
]

// Inject with @Inject
@Injectable()
export class LoanApplicationService {
  constructor(
    @Inject('APP_CONFIG') private readonly config: AppConfig,
  ) {}
}
```
Use for: constants, configuration objects, third-party SDK instances already constructed outside NestJS.

**3. Factory Provider**
```typescript
providers: [
  {
    provide: 'NACH_CLIENT',
    useFactory: (config: ConfigService, logger: LoggerService) => {
      const client = new NachApiClient({
        endpoint: config.get('NACH_ENDPOINT'),
        apiKey:   config.get('NACH_API_KEY'),
        timeout:  config.get<number>('NACH_TIMEOUT_MS'),
      });
      logger.log('NACH client initialised');
      return client;
    },
    inject: [ConfigService, LoggerService], // declared dependencies for the factory
  },
]
```
Use for: providers that require async construction, conditional setup, or non-NestJS SDK instances that need configuration values.

**4. Alias Provider (`useExisting`)**
```typescript
providers: [
  PrismaLoanRepository,
  { provide: ILoanRepository, useExisting: PrismaLoanRepository },
]
```
Use for: dependency inversion — the service depends on `ILoanRepository` (the interface token), but the container serves `PrismaLoanRepository`. Swap to `MongoLoanRepository` for tests without touching the service.

**Q7. What is an Injection Token and when do you use `Symbol` vs `string` vs class as a token?**
A: An injection token is the key the DI container uses to register and look up a provider. The choice of token type matters:

```typescript
// String token — works but collision-prone in large codebases
providers: [{ provide: 'LOAN_REPOSITORY', useClass: PrismaLoanRepository }]
@Inject('LOAN_REPOSITORY') private readonly repo: ILoanRepository

// Symbol token — unique, collision-free, no magic strings
export const LOAN_REPOSITORY = Symbol('ILoanRepository');
providers: [{ provide: LOAN_REPOSITORY, useClass: PrismaLoanRepository }]
@Inject(LOAN_REPOSITORY) private readonly repo: ILoanRepository

// Class token — simplest; works when no interface abstraction is needed
providers: [LoanApplicationService]
constructor(private readonly loanService: LoanApplicationService) {} // no @Inject needed

// InjectionToken (NestJS) — adds type safety to the token
import { InjectionToken } from '@nestjs/common';
export const LOAN_REPO_TOKEN = new InjectionToken<ILoanRepository>('ILoanRepository');
```

**Guidance:**
- **Class token** — default for all concrete providers. Cleanest; no `@Inject` needed.
- **Symbol token** — for interface abstractions (DIP pattern), config values, and any provider where you want type safety without a concrete class as the token.
- **String token** — avoid in new code; acceptable in small projects but collides easily and provides no type safety.

**Q8. How does the `useFactory` provider handle asynchronous initialisation?**
A: Some providers need async setup — database connections, feature flag fetches, remote config pulls. NestJS supports async factories natively:

```typescript
@Module({
  providers: [
    {
      provide: 'REDIS_CLIENT',
      useFactory: async (config: ConfigService): Promise<Redis> => {
        const client = new Redis({
          host:     config.get('REDIS_HOST'),
          port:     config.get<number>('REDIS_PORT'),
          password: config.get('REDIS_PASSWORD'),
          db:       config.get<number>('REDIS_DB', 0),
        });

        // Wait until connection is established before declaring the app ready
        await new Promise<void>((resolve, reject) => {
          client.once('ready', resolve);
          client.once('error', reject);
        });

        return client;
      },
      inject: [ConfigService],
    },
  ],
})
export class RedisModule {}
```

For module-level async setup (database connections, remote config), use `forRootAsync`:

```typescript
@Module({
  imports: [
    TypeOrmModule.forRootAsync({
      imports: [ConfigModule],
      useFactory: async (config: ConfigService): Promise<TypeOrmModuleOptions> => ({
        type:        'postgres',
        host:        config.get('DB_HOST'),
        port:        config.get<number>('DB_PORT'),
        username:    config.get('DB_USER'),
        password:    config.get('DB_PASSWORD'),
        database:    config.get('DB_NAME'),
        entities:    [LoanEntity, ApplicantEntity, MandateEntity],
        synchronize: false,     // never true in production
        ssl:         config.get<boolean>('DB_SSL', false),
      }),
      inject: [ConfigService],
    }),
  ],
})
export class DatabaseModule {}
```

NestJS waits for all async factories to resolve before completing the application bootstrap — a failed async factory throws during startup, preventing a partially-initialised app from accepting requests.

## Section 3: Provider Scopes

**Q9. What are the three provider scopes in NestJS and how do they affect memory and performance?**
A: Provider scope controls how many instances of a provider the container creates:

```typescript
import { Injectable, Scope } from '@nestjs/common';

@Injectable({ scope: Scope.DEFAULT })   // singleton — one instance, shared by all
@Injectable({ scope: Scope.REQUEST })   // new instance per HTTP request
@Injectable({ scope: Scope.TRANSIENT }) // new instance per injection point
```

**Singleton (DEFAULT)** — created once, shared across the entire application lifetime.
- Memory: 1 instance
- Use for: everything — services, repositories, guards. The default and correct choice for 95% of providers.

**Request-scoped** — created fresh for every HTTP request, destroyed after the response.
- Memory: N instances (one per concurrent request)
- Use for: providers that must hold request-specific state — current user context, request correlation ID, per-request transaction client.

```typescript
// Request-scoped provider — holds request-specific data
@Injectable({ scope: Scope.REQUEST })
export class RequestContext {
  private correlationId: string;
  private authenticatedUser: AuthenticatedUser;

  setCorrelationId(id: string): void { this.correlationId = id; }
  getCorrelationId(): string          { return this.correlationId; }
  setUser(user: AuthenticatedUser): void { this.authenticatedUser = user; }
  getUser(): AuthenticatedUser           { return this.authenticatedUser; }
}

// Inject into service — service automatically becomes request-scoped too (scope bubbles up)
@Injectable()
export class AuditService {
  constructor(private readonly requestContext: RequestContext) {}

  async log(action: string): Promise<void> {
    await this.auditRepo.insert({
      action,
      userId:        this.requestContext.getUser().id,
      correlationId: this.requestContext.getCorrelationId(),
      timestamp:     new Date(),
    });
  }
}
```

**Transient** — new instance at every injection point; no sharing.
- Memory: M instances (one per injection site)
- Use for: stateful utilities that must not share state between consumers (e.g., a builder pattern object, a per-consumer logger instance with different prefixes).

```typescript
@Injectable({ scope: Scope.TRANSIENT })
export class LoanLogger {
  private context: string;

  setContext(ctx: string): this { this.context = ctx; return this; }
  log(msg: string): void { console.log(`[${this.context}] ${msg}`); }
}
```

**Performance implication:** request-scoped providers cause the entire injection chain above them to be instantiated per request — *scope bubbles up*. If a singleton service injects a request-scoped provider, NestJS forces the singleton to become request-scoped at runtime. This has real performance cost; prefer the `REQUEST` injection token for accessing request data in singletons instead:

```typescript
import { REQUEST } from '@nestjs/core';
import { Request } from 'express';

@Injectable()  // stays singleton
export class AuditService {
  constructor(@Inject(REQUEST) private readonly request: Request) {}
  // Works in request-scoped contexts; use REQUEST token to avoid scope bubbling
}
```

**Q10. How do you share a single provider instance across multiple modules without making it global?**
A: Export from the owning module and import that module wherever the provider is needed:

```typescript
// BureauModule owns BureauService
@Module({
  providers: [BureauService, CibilAdapter, ExperianAdapter],
  exports: [BureauService],  // only BureauService is shared; adapters stay internal
})
export class BureauModule {}

// LoanModule and UnderwritingModule both import BureauModule
@Module({
  imports: [BureauModule],   // ← imports the module, not the service directly
  providers: [LoanApplicationService],
})
export class LoanModule {}

@Module({
  imports: [BureauModule],   // same BureauService instance (singleton) is reused
  providers: [UnderwritingService],
})
export class UnderwritingModule {}
```

NestJS reuses the same singleton instance across all modules that import `BureauModule`. The container does not create a second `BureauService` — it returns the cached singleton from the first module that initialised it.

## Section 4: Dependency Inversion and Interfaces

**Q11. How do you implement the Dependency Inversion Principle with NestJS DI?**
A: DIP says high-level modules (services) should depend on abstractions, not concretions. In NestJS, this means the service depends on an *interface token*, while the module binds the concrete implementation:

```typescript
// Step 1 — Define the interface (no NestJS imports)
export interface IBureauService {
  fetchCreditReport(pan: string): Promise<BureauReport>;
  fetchBankStatement(accountNumber: string, months: number): Promise<BankStatement>;
}

// Step 2 — Define the injection token (Symbol = no string collision)
export const BUREAU_SERVICE = Symbol('IBureauService');

// Step 3 — Implement the interface
@Injectable()
export class CibilBureauAdapter implements IBureauService {
  constructor(
    private readonly httpClient: HttpService,
    private readonly config: ConfigService,
  ) {}

  async fetchCreditReport(pan: string): Promise<BureauReport> {
    const { data } = await this.httpClient.axiosRef.get(
      `${this.config.get('CIBIL_BASE_URL')}/report/${pan}`,
      { headers: { Authorization: `Bearer ${this.config.get('CIBIL_API_KEY')}` } },
    );
    return this.toDomain(data);
  }

  async fetchBankStatement(accountNumber: string, months: number): Promise<BankStatement> {
    // ...Account Aggregator integration
  }

  private toDomain(raw: any): BureauReport {
    return { score: raw.cibilScore, overdueAccounts: raw.overdueCount, /* ... */ };
  }
}

// Step 4 — Bind in module
@Module({
  providers: [
    { provide: BUREAU_SERVICE, useClass: CibilBureauAdapter },
  ],
  exports: [{ provide: BUREAU_SERVICE, useClass: CibilBureauAdapter }],
})
export class BureauModule {}

// Step 5 — Service depends on the abstraction
@Injectable()
export class LoanApplicationService {
  constructor(
    @Inject(BUREAU_SERVICE) private readonly bureauService: IBureauService,
  ) {}

  async apply(dto: CreateLoanApplicationDto, applicantId: string): Promise<LoanApplication> {
    const report = await this.bureauService.fetchCreditReport(dto.pan);
    if (report.score < 650) throw new IneligibleApplicantException([`Score ${report.score} below minimum`]);
    // ...
  }
}
```

Now swapping from CIBIL to Experian is a **one-line module change** — the service is untouched:

```typescript
// Swap implementation — service code unchanged
{ provide: BUREAU_SERVICE, useClass: ExperianBureauAdapter }

// Swap for tests — in-memory fake; no HTTP calls
{ provide: BUREAU_SERVICE, useValue: new InMemoryBureauAdapter([{ pan: 'ABCDE1234F', score: 720 }]) }
```

**Q12. How do you handle circular dependencies in NestJS?**
A: Circular dependencies occur when Module A imports Module B, and Module B imports Module A — or when Service A depends on Service B and vice versa. NestJS detects these at startup and throws a clear error.

**Fix 1 — Forward reference (`forwardRef`)** for genuine circular provider dependencies:

```typescript
// LoanService needs NotificationService
// NotificationService needs LoanService (to fetch loan details for email content)
@Injectable()
export class LoanApplicationService {
  constructor(
    @Inject(forwardRef(() => NotificationService))
    private readonly notificationService: NotificationService,
  ) {}
}

@Injectable()
export class NotificationService {
  constructor(
    @Inject(forwardRef(() => LoanApplicationService))
    private readonly loanService: LoanApplicationService,
  ) {}
}

// In modules too
@Module({
  imports: [forwardRef(() => NotificationModule)],
  providers: [LoanApplicationService],
})
export class LoanModule {}
```

**Fix 2 (preferred) — Eliminate the circular dependency by extracting shared logic:**

```typescript
// ❌ LoanService ↔ NotificationService circular
// Root cause: NotificationService is fetching loan details itself

// ✅ Fix: caller (LoanService) passes the data the notification needs
@Injectable()
export class NotificationService {
  // Does NOT inject LoanService — receives data it needs as parameters
  async sendSanctionLetter(applicantEmail: string, loanSummary: LoanSummaryDto): Promise<void> {
    // ... send email with loanSummary already available
  }
}

// LoanService fetches the data and passes it — no circular dependency
@Injectable()
export class LoanApplicationService {
  async sanction(loanId: string, dto: SanctionLoanDto): Promise<LoanApplication> {
    const loan = await this.loanRepo.findById(loanId);
    // ... sanction logic
    await this.notificationService.sendSanctionLetter(loan.applicantEmail, toSummary(loan));
    return loan;
  }
}
```

`forwardRef` is a **last resort**, not a design pattern. Every `forwardRef` in a codebase is a design smell indicating that two classes know too much about each other. The fix is almost always to push shared behaviour into a third class or pass data instead of calling back.

## Section 5: Testing with DI

**Q13. How does NestJS DI make unit testing cleaner compared to manual instantiation?**
A: Without DI, testing `LoanApplicationService` requires knowing and constructing all its transitive dependencies — a fragile pyramid. With DI, you swap any dependency with a mock:

```typescript
// ❌ Without DI — brittle; breaks every time a dependency's constructor changes
const bureauAdapter   = new CibilBureauAdapter(new HttpService(...), new ConfigService(...));
const loanRepo        = new PrismaLoanRepository(new PrismaService(...));
const eligibility     = new LoanEligibilityService(new BRE(...));
const notifications   = new NotificationService(new SesClient(...), new SmsClient(...));
const service         = new LoanApplicationService(loanRepo, bureauAdapter, eligibility, notifications);

// ✅ With NestJS DI — mock only what you need; container wires the rest
describe('LoanApplicationService', () => {
  let service: LoanApplicationService;
  let mockBureauService: jest.Mocked<IBureauService>;
  let mockLoanRepo: jest.Mocked<ILoanRepository>;

  beforeEach(async () => {
    mockBureauService = { fetchCreditReport: jest.fn(), fetchBankStatement: jest.fn() };
    mockLoanRepo      = { create: jest.fn(), findById: jest.fn(), updateStatus: jest.fn(), findByApplicant: jest.fn() };

    const module = await Test.createTestingModule({
      providers: [
        LoanApplicationService,
        { provide: BUREAU_SERVICE,   useValue: mockBureauService },
        { provide: LOAN_REPOSITORY,  useValue: mockLoanRepo },
        { provide: LoanEligibilityService, useValue: { assess: jest.fn().mockResolvedValue({ eligible: true, reasons: [] }) } },
        { provide: NotificationService,    useValue: { sendApplicationReceived: jest.fn() } },
        { provide: EventEmitter2,          useValue: { emit: jest.fn() } },
      ],
    }).compile();

    service = module.get(LoanApplicationService);
  });

  it('should reject applicant when bureau score is below 650', async () => {
    mockBureauService.fetchCreditReport.mockResolvedValue({ score: 580, overdueAccounts: 2 } as any);

    await expect(service.apply(validDto, 'USR-001')).rejects.toThrow(IneligibleApplicantException);
    expect(mockLoanRepo.create).not.toHaveBeenCalled();
  });

  it('should create loan when all checks pass', async () => {
    mockBureauService.fetchCreditReport.mockResolvedValue({ score: 720, overdueAccounts: 0 } as any);
    mockLoanRepo.create.mockResolvedValue({ id: 'LOAN-001', status: LoanStatus.PENDING } as any);

    const result = await service.apply(validDto, 'USR-001');

    expect(result.id).toBe('LOAN-001');
    expect(mockLoanRepo.create).toHaveBeenCalledTimes(1);
  });
});
```

**Q14. How do you override a provider for a specific test without changing the module?**
A: Use `overrideProvider` in `Test.createTestingModule`:

```typescript
// Override a specific provider in an otherwise fully-wired integration test
const module = await Test.createTestingModule({
  imports: [LoanModule],  // real module — most providers are real
})
  .overrideProvider(BUREAU_SERVICE)
  .useValue({ fetchCreditReport: jest.fn().mockResolvedValue({ score: 750 }) })
  .overrideProvider(NotificationService)
  .useValue({ sendApplicationReceived: jest.fn(), sendSanctionLetter: jest.fn() })
  .compile();

// Now LoanApplicationService uses the real repository + mocked bureau + mocked notifications
// — a useful middle ground between pure unit tests and full integration tests
```

This pattern is valuable for testing service logic against a real database (Testcontainers) while mocking expensive or non-deterministic external calls (bureau, payment gateway, SMS provider).

## Section 6: Advanced Patterns

**Q15. How do you implement a dynamic module in NestJS for a reusable integration (e.g., Razorpay, JusPay)?**
A: Dynamic modules allow configuration-time customisation — the consuming module passes options that the provider factory uses:

```typescript
// JusPayModule — configurable payment gateway integration

interface JusPayModuleOptions {
  apiKey:      string;
  merchantId:  string;
  environment: 'sandbox' | 'production';
}

export const JUSPAY_OPTIONS  = Symbol('JUSPAY_OPTIONS');
export const JUSPAY_CLIENT   = Symbol('JUSPAY_CLIENT');

@Module({})
export class JusPayModule {
  // Sync registration
  static forRoot(options: JusPayModuleOptions): DynamicModule {
    return {
      module:   JusPayModule,
      providers: [
        { provide: JUSPAY_OPTIONS, useValue: options },
        {
          provide:    JUSPAY_CLIENT,
          useFactory: (opts: JusPayModuleOptions) => new JusPayClient(opts),
          inject:     [JUSPAY_OPTIONS],
        },
        JusPayService,
      ],
      exports: [JusPayService],
    };
  }

  // Async registration — options come from ConfigService
  static forRootAsync(options: {
    imports?: any[];
    useFactory: (...args: any[]) => Promise<JusPayModuleOptions> | JusPayModuleOptions;
    inject?: any[];
  }): DynamicModule {
    return {
      module:  JusPayModule,
      imports: options.imports ?? [],
      providers: [
        {
          provide:    JUSPAY_OPTIONS,
          useFactory: options.useFactory,
          inject:     options.inject ?? [],
        },
        {
          provide:    JUSPAY_CLIENT,
          useFactory: (opts: JusPayModuleOptions) => new JusPayClient(opts),
          inject:     [JUSPAY_OPTIONS],
        },
        JusPayService,
      ],
      exports: [JusPayService],
    };
  }
}

// Consumer — async registration pulling from ConfigService
@Module({
  imports: [
    JusPayModule.forRootAsync({
      imports:    [ConfigModule],
      useFactory: (config: ConfigService): JusPayModuleOptions => ({
        apiKey:      config.get('JUSPAY_API_KEY')!,
        merchantId:  config.get('JUSPAY_MERCHANT_ID')!,
        environment: config.get<'sandbox' | 'production'>('JUSPAY_ENV', 'sandbox'),
      }),
      inject: [ConfigService],
    }),
  ],
})
export class PaymentModule {}
```

**Q16. How do you implement a multi-provider pattern — e.g., multiple SMS vendors with a fallback chain?**
A: Use a factory provider that composes multiple implementations behind a single interface:

```typescript
export interface ISmsProvider {
  send(to: string, message: string): Promise<SmsResult>;
}

export const SMS_PROVIDER = Symbol('ISmsProvider');

@Injectable()
export class TwilioSmsAdapter implements ISmsProvider { /* ... */ }

@Injectable()
export class Msg91SmsAdapter implements ISmsProvider { /* ... */ }

// Fallback chain — try Twilio first, fall back to Msg91
@Injectable()
export class FallbackSmsService implements ISmsProvider {
  constructor(
    @Inject('TWILIO_SMS') private readonly twilio: ISmsProvider,
    @Inject('MSG91_SMS')  private readonly msg91: ISmsProvider,
    private readonly logger: Logger,
  ) {}

  async send(to: string, message: string): Promise<SmsResult> {
    try {
      return await this.twilio.send(to, message);
    } catch (err) {
      this.logger.warn(`Twilio failed (${err.message}), falling back to Msg91`);
      return this.msg91.send(to, message);
    }
  }
}

@Module({
  providers: [
    { provide: 'TWILIO_SMS', useClass: TwilioSmsAdapter },
    { provide: 'MSG91_SMS',  useClass: Msg91SmsAdapter },
    FallbackSmsService,
    { provide: SMS_PROVIDER, useExisting: FallbackSmsService },
  ],
  exports: [{ provide: SMS_PROVIDER, useExisting: FallbackSmsService }],
})
export class SmsModule {}
```

**Q17. How do you lazily load a provider that is expensive to initialise and not always needed?**
A: Use NestJS's `LazyModuleLoader` for providers that should only be instantiated on first use — e.g., a PDF generation service or a bulk-report exporter that is called rarely:

```typescript
import { LazyModuleLoader } from '@nestjs/core';

@Injectable()
export class LoanReportService {
  constructor(private readonly lazyLoader: LazyModuleLoader) {}

  async exportPortfolio(filters: PortfolioFilters): Promise<Buffer> {
    // PdfExportModule is loaded only when exportPortfolio is called — not at startup
    const { PdfExportModule, PdfExportService } = await import('./pdf-export.module');
    const moduleRef = await this.lazyLoader.load(() => PdfExportModule);
    const pdfService = moduleRef.get<PdfExportService>(PdfExportService);

    return pdfService.generatePortfolioReport(filters);
  }
}
```

Use lazy loading sparingly — it trades startup cost for first-call latency and makes the dependency graph less transparent. Prefer it only for heavy, rarely-used providers (bulk exports, ML model inference).

## Section 7: Common Anti-Patterns and Pitfalls

**Q18. What are the most common DI mistakes in NestJS fintech codebases?**
A:

**Anti-pattern 1 — Instantiating dependencies with `new` inside a class:**
```typescript
// ❌ Bypasses DI entirely — untestable, singleton not reused
@Injectable()
export class LoanApplicationService {
  private readonly bureauService = new CibilBureauAdapter(); // wrong
  private readonly logger = new Logger(); // wrong — use NestJS Logger via DI
}

// ✅ Let the container inject
@Injectable()
export class LoanApplicationService {
  constructor(
    @Inject(BUREAU_SERVICE) private readonly bureauService: IBureauService,
    private readonly logger: Logger,
  ) {}
}
```

**Anti-pattern 2 — Importing a Service directly from another module without going through module exports:**
```typescript
// ❌ Importing the concrete class into a different module's provider list
@Module({
  providers: [
    LoanApplicationService,
    BureauService, // ← wrong — LoanModule is re-declaring BureauService from BureauModule
  ],
})
export class LoanModule {}

// ✅ Import the module that owns and exports it
@Module({
  imports: [BureauModule], // ← BureauModule exports BureauService; now available in LoanModule
  providers: [LoanApplicationService],
})
export class LoanModule {}
```

**Anti-pattern 3 — Using `@Global()` for domain services:**
```typescript
// ❌ Making domain-specific services global — pollutes the entire container
@Global()
@Module({
  providers: [LoanApplicationService, LoanRepository, BureauService],
  exports:   [LoanApplicationService, LoanRepository, BureauService],
})
export class LoanModule {}

// ✅ @Global() is appropriate only for cross-cutting infrastructure
@Global()
@Module({
  providers: [ConfigService, LoggerService, EventEmitter2, PrismaService],
  exports:   [ConfigService, LoggerService, EventEmitter2, PrismaService],
})
export class CoreModule {}
```

**Anti-pattern 4 — Overusing request-scoped providers:**
```typescript
// ❌ Making a repository request-scoped when it doesn't hold request state
@Injectable({ scope: Scope.REQUEST }) // wrong — repo is stateless; singleton is correct
export class LoanRepository { /* ... */ }

// ✅ Repository is stateless — singleton is always correct for repositories
@Injectable() // scope: Scope.DEFAULT
export class LoanRepository { /* ... */ }
```

**Anti-pattern 5 — Ignoring the `inject` array in factory providers:**
```typescript
// ❌ Factory parameter has no matching inject entry — will be undefined at runtime
{
  provide: 'NACH_CLIENT',
  useFactory: (config: ConfigService) => new NachApiClient(config.get('NACH_KEY')),
  // inject: [ConfigService] ← missing; config is undefined at runtime
}

// ✅ Every factory parameter must appear in inject in the same order
{
  provide: 'NACH_CLIENT',
  useFactory: (config: ConfigService) => new NachApiClient(config.get('NACH_KEY')),
  inject: [ConfigService],
}
```

**Q19. How do you debug a `Nest can't resolve dependencies` error?**
A: This is the most common DI error — it means the container cannot find a provider for an injection token. Systematic debugging:

```
Nest can't resolve dependencies of the LoanApplicationService (?).
Please make sure that the argument BUREAU_SERVICE at index [0]
is available in the LoanModule context.
```

**Checklist:**
1. **Is the provider declared?** The `BUREAU_SERVICE` token must be in `providers` of the module that owns it — or in a module that `LoanModule` imports.
2. **Is it exported?** If `BureauService` is in `BureauModule`, does `BureauModule` list it in `exports`?
3. **Is the module imported?** Does `LoanModule` import `BureauModule`?
4. **Is the token correct?** If using a Symbol, ensure you're importing the same Symbol reference — not re-declaring it.
5. **Is `@Injectable()` present?** The class must have `@Injectable()` to be managed by the DI container.
6. **Is `emitDecoratorMetadata: true` in `tsconfig.json`?** Without it, constructor parameter types are not emitted.

```typescript
// Diagnostic — log the full module graph
// Temporarily enable NestJS debug logging
const app = await NestFactory.create(AppModule, { logger: ['verbose'] });
// Startup logs show the full resolution order — spot what's missing
```

## Section 8: Scenario / System Design Questions

**Q20. "Your team wants to add Razorpay as a second payment gateway alongside JusPay, with a feature flag that routes traffic. Where does this go in the DI system?"**
A: The routing logic belongs in a facade provider — the DI system provides both implementations; the facade decides which to use at runtime:

```typescript
export const PAYMENT_GATEWAY = Symbol('IPaymentGateway');

export interface IPaymentGateway {
  initiatePayment(order: PaymentOrder): Promise<PaymentResult>;
  verifyWebhook(payload: any, signature: string): boolean;
}

@Injectable()
export class JusPayGateway implements IPaymentGateway { /* ... */ }

@Injectable()
export class RazorpayGateway implements IPaymentGateway { /* ... */ }

// Facade — injected by name; routes by feature flag
@Injectable()
export class PaymentGatewayFacade implements IPaymentGateway {
  constructor(
    @Inject('JUSPAY_GW')   private readonly jusPay: IPaymentGateway,
    @Inject('RAZORPAY_GW') private readonly razorpay: IPaymentGateway,
    private readonly featureFlags: FeatureFlagService,
  ) {}

  async initiatePayment(order: PaymentOrder): Promise<PaymentResult> {
    const gateway = await this.featureFlags.isEnabled('USE_RAZORPAY', order.customerId)
      ? this.razorpay
      : this.jusPay;
    return gateway.initiatePayment(order);
  }

  verifyWebhook(payload: any, sig: string): boolean {
    // Try both — webhook might come from either gateway
    return this.jusPay.verifyWebhook(payload, sig) || this.razorpay.verifyWebhook(payload, sig);
  }
}

@Module({
  providers: [
    { provide: 'JUSPAY_GW',   useClass: JusPayGateway },
    { provide: 'RAZORPAY_GW', useClass: RazorpayGateway },
    PaymentGatewayFacade,
    { provide: PAYMENT_GATEWAY, useExisting: PaymentGatewayFacade },
  ],
  exports: [{ provide: PAYMENT_GATEWAY, useExisting: PaymentGatewayFacade }],
})
export class PaymentModule {}

// LoanDisbursementService — unaware of which gateway is active
@Injectable()
export class LoanDisbursementService {
  constructor(
    @Inject(PAYMENT_GATEWAY) private readonly payment: IPaymentGateway,
  ) {}
}
```

Adding a third gateway later — Stripe, BillDesk — requires adding a new `@Injectable()` class and registering it in `PaymentModule`. `LoanDisbursementService` is never touched.

**Q21. "You're asked to add per-request correlation ID tracking to every log line across all services. How do you do this with NestJS DI without adding correlationId as a parameter to every service method?"**
A: Use a request-scoped `RequestContext` provider populated by middleware, injected wherever needed:

```typescript
// 1. Request-scoped context holder
@Injectable({ scope: Scope.REQUEST })
export class RequestContext {
  private data: Map<string, unknown> = new Map();

  set<T>(key: string, value: T): void { this.data.set(key, value); }
  get<T>(key: string): T | undefined   { return this.data.get(key) as T; }

  get correlationId(): string  { return this.get<string>('correlationId') ?? 'UNKNOWN'; }
  get authenticatedUserId(): string { return this.get<string>('userId') ?? 'ANONYMOUS'; }
}

// 2. Middleware — populates RequestContext for every request
@Injectable()
export class CorrelationMiddleware implements NestMiddleware {
  constructor(private readonly requestContext: RequestContext) {}

  use(req: Request, res: Response, next: NextFunction): void {
    const correlationId = (req.headers['x-correlation-id'] as string) ?? uuid();
    this.requestContext.set('correlationId', correlationId);
    res.setHeader('x-correlation-id', correlationId);
    next();
  }
}

// 3. Logger service — automatically includes correlationId in every log
@Injectable()
export class AppLogger {
  private readonly logger = new Logger();

  constructor(private readonly requestContext: RequestContext) {}

  log(context: string, message: string, meta?: Record<string, unknown>): void {
    this.logger.log({
      message,
      correlationId: this.requestContext.correlationId,
      userId:        this.requestContext.authenticatedUserId,
      ...meta,
    }, context);
  }
}

// 4. Any service injects AppLogger — gets correlationId automatically
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly logger: AppLogger,  // no correlationId param needed
  ) {}

  async apply(dto: CreateLoanApplicationDto, userId: string): Promise<LoanApplication> {
    this.logger.log('LoanApplicationService', 'Creating loan application', { userId });
    const loan = await this.loanRepo.create({ /* ... */ });
    this.logger.log('LoanApplicationService', 'Loan application created', { loanId: loan.id });
    return loan;
  }
}
```

The `RequestContext` is request-scoped — each HTTP request gets its own instance. Services that inject `AppLogger` (which injects `RequestContext`) automatically become request-scoped via scope bubbling — or you use the `REQUEST` token injection to keep them singleton. Either way, every log line across every service carries the correlation ID without any method signature changes.

## Quick Reference: NestJS DI Cheat Sheet

| Scenario | Pattern |
|---|---|
| Standard service/repository | `@Injectable()` + class token |
| Abstraction / interface | Symbol token + `useClass` + `@Inject(TOKEN)` |
| Configuration values | `useValue` or `useFactory` + `inject: [ConfigService]` |
| SDK / third-party client | `useFactory` async, `inject: [ConfigService]` |
| Swap impl for tests | `overrideProvider().useValue(mock)` |
| Shared across modules | `exports: [Provider]` + `imports: [OwningModule]` |
| App-wide infrastructure | `@Global()` on `CoreModule` — use sparingly |
| Per-request state | `scope: Scope.REQUEST` — RequestContext pattern |
| Fallback / strategy pattern | Named tokens (`'TWILIO_SMS'`) + facade `@Injectable` |
| Configurable library module | `DynamicModule` with `forRoot` / `forRootAsync` |
| Circular dependency | `forwardRef(() => Class)` — last resort; extract instead |
| Lazy heavy providers | `LazyModuleLoader` — rare; only for truly heavy infrequent deps |

---

**Tip for the interview:** At the 5 YOE level, DI questions surface as code review tasks ("why is this provider undefined at runtime?"), design questions ("how do you swap the SMS vendor without changing every service?"), or debugging scenarios ("your factory provider is receiving undefined — what's wrong?"). The differentiating answer is demonstrating *why* the DI container exists — not just "it injects dependencies" but "it decouples construction from use, enabling scope management, testability, and runtime polymorphism." In a fintech codebase, the patterns that land are the Symbol-token DIP setup for external integrations (bureau, payment gateways), the `RequestContext` pattern for audit correlation, and the `forRootAsync` pattern for config-driven third-party clients. The senior signal is knowing where `@Global()` is appropriate (cross-cutting infrastructure only), why `forwardRef` is a smell, and why request-scoped providers have a real performance cost in high-throughput lending APIs.
