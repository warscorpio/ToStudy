# JavaScript / TypeScript (Node.js & Backend Design Patterns): Circuit Breaker Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Circuit Breaker pattern?**
A: The Circuit Breaker pattern, popularised by Michael Nygard in *Release It!* (2007) and named by Martin Fowler, is a **fault-tolerance and resilience pattern** that prevents an application from repeatedly attempting an operation that is likely to fail, thereby allowing it to recover gracefully rather than cascading failures across the system. It is named after the electrical circuit breaker that automatically interrupts a circuit when it detects a fault — protecting downstream components from damage.

In software, a circuit breaker wraps a potentially failing operation (an HTTP call to a downstream service, a database query, an external API call) in a proxy object that monitors for failures. When failures exceed a configured threshold, the breaker "opens" — subsequent calls are immediately rejected without attempting the operation, giving the failing system time to recover. After a configured timeout, the breaker allows a limited number of trial calls through ("half-open"). If those succeed, the breaker closes and normal operation resumes. If they fail, the breaker opens again.

The circuit breaker is the primary tool for implementing **fail-fast** behaviour — a system that detects a failing dependency and rejects calls immediately rather than waiting for timeouts that consume threads, connections, and user patience.

**Q2. What specific failure scenarios does the Circuit Breaker pattern address?**
A: Without a circuit breaker, a slow or failing downstream service causes a cascade of failures:

```
User Request
    ↓
Service A (waits 30s for timeout)
    ↓ 30-second timeout
Service B ← FAILING (database overloaded, network partition, deployment in progress)

Effect without circuit breaker:
- Every request to Service A blocks for 30 seconds
- Thread pool / connection pool of Service A exhausted
- Service A itself starts failing with 503 / timeout errors
- Services upstream of A also start failing
- One failing B takes down the entire request chain ✗
```

Specific problems addressed:

**Cascading failure** — a single slow dependency brings down the entire call chain because all threads block waiting for timeouts.

**Resource exhaustion** — thread pools, connection pools, and memory fill up with requests that are all waiting on a dependency that cannot respond. New requests have no resources available.

**Slow recovery** — without a circuit breaker, even after the failing service recovers, it gets immediately hammered by the backlog of retried requests, preventing recovery.

**Thundering herd on recovery** — when a service comes back up, every circuit breaker simultaneously sends traffic, overwhelming the recovering service before it can stabilise.

**Q3. What are the three states of a Circuit Breaker, and what triggers each transition?**
A:

```
                   failure threshold exceeded
    ┌─────────┐ ──────────────────────────────► ┌──────────┐
    │  CLOSED │                                  │   OPEN   │
    │ (normal)│ ◄────────────────────────────── │(rejecting)│
    └─────────┘        reset timeout expires     └──────────┘
         ▲                    │ reset timeout expires
         │                    ▼
         │             ┌─────────────┐
         │             │  HALF-OPEN  │
         └─────────────│  (probing)  │
       probe succeeds  └─────────────┘
                            │ probe fails
                            ▼
                       (back to OPEN)
```

**CLOSED (normal operation):**
- All calls pass through to the dependency.
- Failures are counted within a sliding time window or by count.
- When failure count/rate exceeds the threshold (e.g., 5 failures in 10 seconds, or 50% failure rate), transitions to **OPEN**.
- Success calls reset or reduce the failure counter.

**OPEN (fail-fast):**
- All calls are immediately rejected with a `CircuitOpenError` (or return a fallback) — no attempt is made to call the dependency.
- A reset timeout timer runs (e.g., 30 seconds).
- When the timer expires, transitions to **HALF-OPEN**.

**HALF-OPEN (probing):**
- A limited number of trial calls (e.g., 1–3) are allowed through to the dependency.
- If all trial calls succeed → transitions back to **CLOSED**.
- If any trial call fails → transitions back to **OPEN** (reset timer restarts).
- Calls that arrive while probes are in flight are rejected (treated as if OPEN).

**Q4. What is the difference between a Circuit Breaker and a Retry pattern?**
A: They are complementary — but they address opposite failure scenarios and must be ordered carefully when combined:

| Aspect | Retry | Circuit Breaker |
|---|---|---|
| **Addresses** | Transient, short-lived failures (momentary network blip) | Persistent failures (service down, overloaded) |
| **Behaviour** | Retries the operation N times with backoff | Stops attempting the operation entirely |
| **Effect on load** | Increases load on the failing service | Reduces load on the failing service |
| **Failure detection** | Per-call — doesn't track history | Across calls — tracks cumulative failure rate |
| **Recovery time** | Immediate retries after each failure | Waits for reset timeout before probing |
| **When to use** | Idempotent operations, transient errors, few retries | Repeated failures, non-idempotent ops, slow recovery |

**Combined correctly** — Retry wraps the individual call attempt; Circuit Breaker wraps the overall operation. Retry tries a few times for transient errors; if failures persist and breach the Circuit Breaker threshold, the breaker opens and stops retrying entirely:

```ts
// Correct layering: Circuit Breaker (outer) → Retry (inner) → actual call
const result = await circuitBreaker.execute(async () =>
  retry(
    () => paymentApi.charge(amount, token),  // inner: retry 3 times for transient errors
    { attempts: 3, delay: 100 }
  )
);

// If all retries fail, that failure is counted by the circuit breaker
// When failures accumulate, breaker opens — stops even trying to retry
```

**Never** place Circuit Breaker inside Retry (breaker wrapping retries) — each retry attempt would look like a separate circuit breaker call, defeating the purpose of retry backoff.

**Q5. What is the difference between a Circuit Breaker and a Bulkhead pattern?**
A: Both are resilience patterns from *Release It!*, but they prevent different failure modes:

- **Circuit Breaker** — prevents calling a failing dependency; responds to *detected failure* by stopping calls.
- **Bulkhead** — partitions resources (thread pools, connection pools, semaphores) into isolated compartments so that a slow dependency consuming all resources of one compartment cannot starve other operations. Responds to *resource exhaustion* by isolating it.

They compose naturally: a Bulkhead limits how many concurrent calls can be in-flight to a dependency; a Circuit Breaker stops calls entirely when that dependency is failing. Together they prevent both resource exhaustion (Bulkhead) and cascading failure (Circuit Breaker):

```ts
// Bulkhead: max 10 concurrent calls to PaymentService at any time
const paymentBulkhead = new Semaphore(10);

// Circuit Breaker: stop calling if PaymentService fails too often
const paymentBreaker = new CircuitBreaker(paymentApi.charge);

// Combined: acquire semaphore slot, then go through circuit breaker
async function chargePayment(amount: number, token: string): Promise<ChargeResult> {
  return paymentBulkhead.runExclusive(async () =>  // Bulkhead: limit concurrency
    paymentBreaker.execute(() =>                   // Circuit Breaker: stop on failures
      paymentApi.charge(amount, token)
    )
  );
}
```

## Section 2: Implementing the Circuit Breaker in TypeScript

**Q6. Show a complete, production-quality Circuit Breaker implementation from scratch.**
A:
```ts
// Configuration
interface CircuitBreakerConfig {
  failureThreshold:   number;  // failures to open (count-based)
  successThreshold:   number;  // successes to close from half-open
  timeout:            number;  // ms before transitioning OPEN → HALF-OPEN
  halfOpenMaxCalls:   number;  // max probe calls in HALF-OPEN state
  volumeThreshold?:   number;  // min calls before opening (avoids opening on first failure)
  errorFilter?:       (err: unknown) => boolean; // which errors count as failures
}

type CircuitState = "CLOSED" | "OPEN" | "HALF_OPEN";

interface CircuitBreakerStats {
  state:          CircuitState;
  failures:       number;
  successes:      number;
  totalCalls:     number;
  lastFailureAt:  Date | null;
  lastStateChange: Date;
  nextAttemptAt:  Date | null; // only when OPEN
}

class CircuitBreakerOpenError extends Error {
  constructor(public readonly breakerName: string, public readonly nextAttemptAt: Date) {
    super(`Circuit breaker "${breakerName}" is OPEN. Next attempt at ${nextAttemptAt.toISOString()}`);
    this.name = "CircuitBreakerOpenError";
  }
}

class CircuitBreaker {
  private state:             CircuitState = "CLOSED";
  private failureCount:      number       = 0;
  private successCount:      number       = 0;
  private halfOpenCallCount: number       = 0;
  private totalCalls:        number       = 0;
  private lastFailureAt:     Date | null  = null;
  private lastStateChange:   Date         = new Date();
  private openedAt:          Date | null  = null;

  // Event listeners for observability
  private listeners: Map<string, Array<(...args: unknown[]) => void>> = new Map();

  constructor(
    private readonly name:   string,
    private readonly config: CircuitBreakerConfig
  ) {}

  async execute<T>(operation: () => Promise<T>, fallback?: () => Promise<T>): Promise<T> {
    this.totalCalls++;

    switch (this.state) {
      case "OPEN":
        return this.handleOpen(fallback);

      case "HALF_OPEN":
        return this.handleHalfOpen(operation, fallback);

      case "CLOSED":
        return this.handleClosed(operation, fallback);
    }
  }

  // ── State handlers ──────────────────────────────────────────────────────

  private async handleOpen<T>(fallback?: () => Promise<T>): Promise<T> {
    const nextAttemptAt = new Date(this.openedAt!.getTime() + this.config.timeout);

    if (Date.now() >= nextAttemptAt.getTime()) {
      // Timeout expired — transition to HALF_OPEN and probe
      this.transitionTo("HALF_OPEN");
      return this.execute(fallback ? fallback : () => Promise.reject(
        new CircuitBreakerOpenError(this.name, nextAttemptAt)
      ));
    }

    this.emit("rejected", { state: this.state, nextAttemptAt });

    if (fallback) return fallback();
    throw new CircuitBreakerOpenError(this.name, nextAttemptAt);
  }

  private async handleHalfOpen<T>(
    operation: () => Promise<T>,
    fallback?:  () => Promise<T>
  ): Promise<T> {
    if (this.halfOpenCallCount >= this.config.halfOpenMaxCalls) {
      // Too many probes in-flight — reject until probes resolve
      if (fallback) return fallback();
      throw new CircuitBreakerOpenError(
        this.name,
        new Date(Date.now() + this.config.timeout)
      );
    }

    this.halfOpenCallCount++;
    try {
      const result = await this.callWithTracking(operation);
      this.onSuccess();
      return result;
    } catch (err) {
      this.onFailure(err);
      if (fallback) return fallback();
      throw err;
    }
  }

  private async handleClosed<T>(
    operation: () => Promise<T>,
    fallback?:  () => Promise<T>
  ): Promise<T> {
    try {
      const result = await this.callWithTracking(operation);
      this.onSuccess();
      return result;
    } catch (err) {
      this.onFailure(err);
      if (fallback) return fallback();
      throw err;
    }
  }

  // ── Core tracking ───────────────────────────────────────────────────────

  private async callWithTracking<T>(operation: () => Promise<T>): Promise<T> {
    const start = Date.now();
    try {
      const result = await operation();
      this.emit("success", { durationMs: Date.now() - start });
      return result;
    } catch (err) {
      this.emit("failure", { error: err, durationMs: Date.now() - start });
      throw err;
    }
  }

  private onSuccess(): void {
    this.successCount++;

    if (this.state === "HALF_OPEN") {
      if (this.successCount >= this.config.successThreshold) {
        this.transitionTo("CLOSED");
      }
    }
    // In CLOSED state, successes don't affect failure count (count-based)
    // For rate-based, successes would be counted in the window
  }

  private onFailure(err: unknown): void {
    // Honour the error filter — some errors (e.g., 404) should not count as failures
    if (this.config.errorFilter && !this.config.errorFilter(err)) return;

    this.failureCount++;
    this.lastFailureAt = new Date();

    if (this.state === "HALF_OPEN") {
      this.transitionTo("OPEN"); // any probe failure re-opens
      return;
    }

    if (this.state === "CLOSED") {
      const meetsVolume = !this.config.volumeThreshold ||
                          this.totalCalls >= this.config.volumeThreshold;

      if (meetsVolume && this.failureCount >= this.config.failureThreshold) {
        this.transitionTo("OPEN");
      }
    }
  }

  private transitionTo(next: CircuitState): void {
    const prev = this.state;
    this.state = next;
    this.lastStateChange = new Date();

    // Reset counters on transition
    if (next === "OPEN") {
      this.openedAt          = new Date();
      this.halfOpenCallCount = 0;
      this.successCount      = 0;
    }
    if (next === "CLOSED") {
      this.failureCount      = 0;
      this.successCount      = 0;
      this.halfOpenCallCount = 0;
      this.openedAt          = null;
    }
    if (next === "HALF_OPEN") {
      this.halfOpenCallCount = 0;
      this.successCount      = 0;
    }

    this.emit("stateChange", { from: prev, to: next, at: this.lastStateChange });
  }

  // ── Observability ───────────────────────────────────────────────────────

  on(event: string, handler: (...args: unknown[]) => void): this {
    if (!this.listeners.has(event)) this.listeners.set(event, []);
    this.listeners.get(event)!.push(handler);
    return this;
  }

  private emit(event: string, data: object): void {
    this.listeners.get(event)?.forEach(h => h({ breakerName: this.name, ...data }));
  }

  getStats(): CircuitBreakerStats {
    const nextAttemptAt = this.openedAt
      ? new Date(this.openedAt.getTime() + this.config.timeout)
      : null;

    return {
      state:          this.state,
      failures:       this.failureCount,
      successes:      this.successCount,
      totalCalls:     this.totalCalls,
      lastFailureAt:  this.lastFailureAt,
      lastStateChange: this.lastStateChange,
      nextAttemptAt,
    };
  }

  // Manual controls — for admin endpoints and testing
  forceOpen():   void { this.transitionTo("OPEN"); }
  forceClose():  void { this.transitionTo("CLOSED"); }
  reset():       void { this.transitionTo("CLOSED"); this.totalCalls = 0; }
}

// Usage
const paymentBreaker = new CircuitBreaker("payment-service", {
  failureThreshold: 5,           // open after 5 consecutive failures
  successThreshold: 2,           // close after 2 consecutive successes in half-open
  timeout:          30_000,      // wait 30s before probing
  halfOpenMaxCalls: 1,           // one probe at a time
  volumeThreshold:  10,          // need at least 10 calls before opening
  errorFilter: (err) =>          // only count 5xx errors, not 4xx
    !(err instanceof HttpError && err.status < 500),
});

// Observability hooks
paymentBreaker
  .on("stateChange", (e) => logger.warn("Circuit breaker state changed", e))
  .on("rejected",    (e) => metrics.increment("circuit_breaker.rejected", { breaker: e.breakerName }))
  .on("failure",     (e) => metrics.increment("circuit_breaker.failure",  { breaker: e.breakerName }));

// With fallback
const result = await paymentBreaker.execute(
  () => paymentApi.charge(amount, token),
  () => Promise.resolve({ id: "pending", status: "queued" }) // fallback response
);
```

**Q7. How do you implement a sliding-window circuit breaker — one that tracks failure rate over time rather than just counting consecutive failures?**
A: Count-based breakers are fragile — a burst of failures followed by a long pause resets the counter, and slow failure rates (e.g., 50% of calls failing) may never trigger the threshold. A time-window or call-window breaker is more robust:

```ts
// Sliding window — tracks outcomes in a circular buffer over the last N calls or N seconds
class SlidingWindowCircuitBreaker {
  private window:     Array<{ success: boolean; timestamp: number }> = [];
  private state:      CircuitState = "CLOSED";
  private openedAt:   number | null = null;

  constructor(
    private readonly name:   string,
    private readonly config: {
      windowType:          "count" | "time";
      windowSize:          number;  // N calls (count) or N milliseconds (time)
      failureRateThreshold: number; // percentage, e.g. 50 = 50%
      minimumCalls:        number;  // min calls in window before opening
      slowCallDurationMs:  number;  // calls slower than this count as failures
      slowCallRateThreshold: number; // % of slow calls to also trigger opening
      timeout:             number;  // OPEN → HALF-OPEN wait ms
      successThreshold:    number;  // probes needed to close
    }
  ) {}

  async execute<T>(operation: () => Promise<T>): Promise<T> {
    this.pruneWindow();

    if (this.state === "OPEN") {
      if (Date.now() - this.openedAt! >= this.config.timeout) {
        this.state    = "HALF_OPEN";
        this.openedAt = null;
      } else {
        throw new CircuitBreakerOpenError(this.name,
          new Date(this.openedAt! + this.config.timeout));
      }
    }

    const start = Date.now();
    try {
      const result = await operation();
      const durationMs = Date.now() - start;
      const isSlow = durationMs >= this.config.slowCallDurationMs;

      this.recordOutcome(isSlow ? false : true); // slow calls count as failures
      this.evaluateWindow();
      return result;
    } catch (err) {
      this.recordOutcome(false);
      this.evaluateWindow();
      throw err;
    }
  }

  private recordOutcome(success: boolean): void {
    this.window.push({ success, timestamp: Date.now() });
  }

  private pruneWindow(): void {
    if (this.config.windowType === "time") {
      const cutoff = Date.now() - this.config.windowSize;
      this.window   = this.window.filter(e => e.timestamp >= cutoff);
    } else {
      // count window — keep only last N calls
      if (this.window.length > this.config.windowSize) {
        this.window = this.window.slice(-this.config.windowSize);
      }
    }
  }

  private evaluateWindow(): void {
    if (this.window.length < this.config.minimumCalls) return;

    const failures     = this.window.filter(e => !e.success).length;
    const failureRate  = (failures / this.window.length) * 100;

    if (failureRate >= this.config.failureRateThreshold && this.state === "CLOSED") {
      this.state    = "OPEN";
      this.openedAt = Date.now();
    }
    if (this.state === "HALF_OPEN") {
      const recentSuccesses = this.window.slice(-this.config.successThreshold)
        .every(e => e.success);
      if (recentSuccesses) this.state = "CLOSED";
    }
  }
}

// Configured for rate-based opening
const apiBreaker = new SlidingWindowCircuitBreaker("external-api", {
  windowType:            "count",
  windowSize:            100,     // last 100 calls
  failureRateThreshold:  50,      // open if ≥50% fail
  minimumCalls:          20,      // need at least 20 calls in window
  slowCallDurationMs:    3_000,   // calls over 3s count as failures
  slowCallRateThreshold: 80,      // open if ≥80% are slow
  timeout:               60_000,  // wait 60s before probing
  successThreshold:      5,       // 5 consecutive probes to close
});
```

**Q8. How do you use the `opossum` library — the most widely used Circuit Breaker for Node.js?**
A: `opossum` wraps any async function and provides state management, events, metrics, and fallback support out of the box:

```ts
import CircuitBreaker from "opossum";

// The function to protect — any async operation
async function callPaymentService(amount: number, token: string): Promise<ChargeResult> {
  const response = await fetch("https://api.payment.com/charge", {
    method:  "POST",
    headers: { "Content-Type": "application/json" },
    body:    JSON.stringify({ amount, token }),
    signal:  AbortSignal.timeout(5000), // 5-second timeout on the fetch itself
  });
  if (!response.ok) throw new Error(`Payment API error: ${response.status}`);
  return response.json();
}

// Wrap with circuit breaker
const paymentBreaker = new CircuitBreaker(callPaymentService, {
  timeout:              5000,  // if function takes longer than 5s, trigger failure
  errorThresholdPercentage: 50, // open when ≥50% of calls fail
  resetTimeout:         30000, // wait 30s before entering half-open
  volumeThreshold:      10,    // min calls before opening
  rollingCountTimeout:  10000, // 10s sliding window
  rollingCountBuckets:  10,    // 10 buckets of 1s each within the window

  // Only count specific errors as failures
  errorFilter: (err: Error) => {
    // Don't count 4xx (client errors) as circuit breaker failures
    if (err.message.includes("400") || err.message.includes("404")) return false;
    return true;
  },
});

// Fallback — called when circuit is open OR when the call itself fails
paymentBreaker.fallback(async (amount: number, _token: string) => {
  // Queue for async processing, return pending status
  await paymentQueue.enqueue({ amount, queuedAt: new Date() });
  return { id: `pending-${Date.now()}`, status: "queued", amount };
});

// Observability — hook into state changes and metrics
paymentBreaker.on("open",     () => {
  logger.warn("Payment circuit breaker OPENED");
  metrics.gauge("circuit_breaker.state", 1, { breaker: "payment" }); // 1 = open
  alerting.trigger("circuit_breaker_opened", { service: "payment" });
});
paymentBreaker.on("halfOpen", () => logger.info("Payment circuit breaker HALF-OPEN — probing"));
paymentBreaker.on("close",    () => {
  logger.info("Payment circuit breaker CLOSED — service recovered");
  metrics.gauge("circuit_breaker.state", 0, { breaker: "payment" }); // 0 = closed
});
paymentBreaker.on("fallback", (result) =>
  logger.warn("Payment circuit breaker used fallback", { result })
);
paymentBreaker.on("timeout",  () =>
  metrics.increment("circuit_breaker.timeout", { breaker: "payment" })
);
paymentBreaker.on("reject",   () =>
  metrics.increment("circuit_breaker.rejected", { breaker: "payment" })
);

// Usage — call through the breaker, not the raw function
async function chargeCustomer(customerId: string, amount: number, token: string) {
  try {
    return await paymentBreaker.fire(amount, token); // args forwarded to callPaymentService
  } catch (err) {
    if (err.code === "EOPENBREAKER") {
      throw new ServiceUnavailableError("Payment service temporarily unavailable");
    }
    throw err;
  }
}

// Stats endpoint — expose breaker health for monitoring
app.get("/health/circuit-breakers", (req, res) => {
  res.json({
    payment: {
      state:    paymentBreaker.opened ? "OPEN" : paymentBreaker.halfOpen ? "HALF_OPEN" : "CLOSED",
      stats:    paymentBreaker.stats,
      enabled:  paymentBreaker.enabled,
    }
  });
});
```

## Section 3: Real-World Applications

**Q9. How do you apply the Circuit Breaker pattern to an HTTP microservice client in a Node.js backend?**
A:
```ts
// HTTP client wrapper with circuit breaker per downstream service
class ResilientHttpClient {
  private breakers = new Map<string, CircuitBreaker>();

  constructor(
    private readonly logger:  Logger,
    private readonly metrics: MetricsClient
  ) {}

  private getBreakerFor(serviceName: string): CircuitBreaker {
    if (!this.breakers.has(serviceName)) {
      const breaker = new CircuitBreaker(`http-${serviceName}`, {
        failureThreshold:  5,
        successThreshold:  2,
        timeout:           30_000,
        halfOpenMaxCalls:  1,
        volumeThreshold:   5,
        errorFilter: (err) => {
          // 4xx are client errors — don't count them (they're our fault, not the service's)
          if (err instanceof HttpError && err.status >= 400 && err.status < 500) return false;
          return true;
        },
      });

      breaker
        .on("stateChange", (e) => {
          this.logger.warn("HTTP circuit breaker state change", e);
          this.metrics.gauge("http.circuit_breaker.state",
            e.to === "OPEN" ? 1 : 0,
            { service: serviceName }
          );
        })
        .on("rejected", () =>
          this.metrics.increment("http.circuit_breaker.rejected", { service: serviceName })
        );

      this.breakers.set(serviceName, breaker);
    }
    return this.breakers.get(serviceName)!;
  }

  async get<T>(serviceName: string, url: string, options?: RequestInit): Promise<T> {
    const breaker = this.getBreakerFor(serviceName);
    return breaker.execute(async () => {
      const controller = new AbortController();
      const timeoutId  = setTimeout(() => controller.abort(), 10_000); // 10s request timeout
      try {
        const response = await fetch(url, { ...options, signal: controller.signal });
        if (!response.ok) throw new HttpError(response.status, await response.text());
        return response.json() as T;
      } finally {
        clearTimeout(timeoutId);
      }
    });
  }

  async post<T>(serviceName: string, url: string, body: unknown): Promise<T> {
    const breaker = this.getBreakerFor(serviceName);
    return breaker.execute(() =>
      fetch(url, {
        method:  "POST",
        headers: { "Content-Type": "application/json" },
        body:    JSON.stringify(body),
        signal:  AbortSignal.timeout(10_000),
      }).then(async res => {
        if (!res.ok) throw new HttpError(res.status, await res.text());
        return res.json() as T;
      })
    );
  }

  getStats(): Record<string, CircuitBreakerStats> {
    const stats: Record<string, CircuitBreakerStats> = {};
    this.breakers.forEach((breaker, name) => { stats[name] = breaker.getStats(); });
    return stats;
  }
}

// Usage across the service layer
class OrderService {
  constructor(private http: ResilientHttpClient) {}

  async getProductDetails(productId: string): Promise<Product> {
    return this.http.get<Product>(
      "product-service",                            // breaker per service
      `https://products.internal/api/products/${productId}`
    );
  }

  async reserveInventory(items: OrderItem[]): Promise<Reservation> {
    return this.http.post<Reservation>(
      "inventory-service",
      "https://inventory.internal/api/reservations",
      { items }
    );
  }
}
```

**Q10. How does the Circuit Breaker pattern apply to database connections?**
A: Database connections are a common circuit breaker target — a slow or unresponsive DB should fail-fast rather than exhausting the connection pool:

```ts
// Database client with circuit breaker
class ResilientDatabaseClient {
  private breaker: CircuitBreaker;
  private pool:    Pool;

  constructor(config: DbConfig) {
    this.pool = new Pool({
      connectionString: config.url,
      max:              config.maxConnections ?? 20,
      idleTimeoutMillis: 30_000,
      connectionTimeoutMillis: 5_000,
    });

    this.breaker = new CircuitBreaker("database", {
      failureThreshold:  3,
      successThreshold:  1,
      timeout:           10_000, // try DB again after 10s
      halfOpenMaxCalls:  1,
      errorFilter: (err) => {
        // Don't open for constraint violations or not-found — those are expected errors
        if (err instanceof DatabaseConstraintError) return false;
        if (err instanceof DatabaseNotFoundError)   return false;
        return true; // count connection errors, timeouts, etc.
      },
    });

    this.breaker.on("open", () => {
      logger.error("Database circuit breaker OPENED — refusing queries");
      // Alert on-call engineer
    });
    this.breaker.on("close", () => {
      logger.info("Database circuit breaker CLOSED — queries resuming");
    });
  }

  async query<T>(sql: string, params?: unknown[]): Promise<T[]> {
    return this.breaker.execute(async () => {
      const client = await this.pool.connect();
      try {
        const { rows } = await client.query(sql, params);
        return rows as T[];
      } finally {
        client.release();
      }
    });
  }

  async transaction<T>(work: (client: PoolClient) => Promise<T>): Promise<T> {
    return this.breaker.execute(async () => {
      const client = await this.pool.connect();
      try {
        await client.query("BEGIN");
        const result = await work(client);
        await client.query("COMMIT");
        return result;
      } catch (err) {
        await client.query("ROLLBACK");
        throw err;
      } finally {
        client.release();
      }
    });
  }

  async healthCheck(): Promise<{ healthy: boolean; state: string; latencyMs: number }> {
    const start = Date.now();
    try {
      await this.query("SELECT 1");
      return { healthy: true, state: this.breaker.getStats().state, latencyMs: Date.now() - start };
    } catch {
      return { healthy: false, state: this.breaker.getStats().state, latencyMs: Date.now() - start };
    }
  }
}
```

**Q11. How do you apply Circuit Breakers to a message queue consumer — where the "dependency" is a downstream processing step, not an external service?**
A:
```ts
// Message queue consumer with circuit breaker around the processing step
class ResilientOrderConsumer {
  private processingBreaker: CircuitBreaker;

  constructor(
    private queue:        MessageQueue,
    private orderService: OrderService,
    private logger:       Logger
  ) {
    this.processingBreaker = new CircuitBreaker("order-processing", {
      failureThreshold: 3,
      successThreshold: 1,
      timeout:          60_000,  // wait 60s — give DB/services time to recover
      halfOpenMaxCalls: 1,
    });

    this.processingBreaker.on("open", async () => {
      this.logger.error("Order processing circuit breaker OPENED — pausing consumption");
      await this.queue.pause(); // stop pulling messages when processing is failing
    });

    this.processingBreaker.on("halfOpen", async () => {
      this.logger.info("Order processing circuit breaker HALF-OPEN — resuming with caution");
      await this.queue.resume(); // allow one message through to probe
    });

    this.processingBreaker.on("close", async () => {
      this.logger.info("Order processing circuit breaker CLOSED — full consumption resumed");
      await this.queue.resume();
    });
  }

  async processMessage(message: QueueMessage<OrderEvent>): Promise<void> {
    try {
      await this.processingBreaker.execute(async () => {
        await this.orderService.processOrderEvent(message.body);
        await message.ack();
      });
    } catch (err) {
      if (err instanceof CircuitBreakerOpenError) {
        // Circuit is open — nack without retry count increment
        // Message will be requeued when we resume consuming
        await message.nack({ requeue: true });
        return;
      }

      // Processing failed — send to DLQ after max retries
      if (message.attempts >= 3) {
        await message.deadLetter();
        this.logger.error("Message sent to DLQ after max retries", {
          messageId: message.id, error: err
        });
      } else {
        await message.nack({ requeue: true, delay: 5000 * message.attempts });
      }
    }
  }
}
```

## Section 4: Fallback Strategies

**Q12. What are the main fallback strategies when a circuit breaker is open, and how do you choose between them?**
A: The fallback strategy is as important as the circuit breaker itself — it determines what the caller experiences when the dependency is unavailable:

**Strategy 1 — Return cached / stale data:**
```ts
class ProductService {
  private cache = new Map<string, { data: Product; cachedAt: number }>();

  async getProduct(id: string): Promise<Product> {
    return this.breaker.execute(
      () => this.productApi.get(id),
      async () => {
        // Fallback: return cached version (even if stale)
        const cached = this.cache.get(id);
        if (cached) {
          logger.warn("Returning stale cached product", { id, ageMs: Date.now() - cached.cachedAt });
          return { ...cached.data, _stale: true };
        }
        throw new ServiceUnavailableError("Product service unavailable and no cache");
      }
    );
  }
}
```

**Strategy 2 — Return a safe default:**
```ts
async function getPersonalisedRecommendations(userId: string): Promise<Product[]> {
  return recommenderBreaker.execute(
    () => recommenderApi.getForUser(userId),
    () => {
      // Fallback: return pre-computed "popular items" — always available
      logger.info("Recommender unavailable — returning popular items", { userId });
      return popularItemsCache.get(); // static fallback, always works
    }
  );
}
```

**Strategy 3 — Queue for async processing (write operations):**
```ts
async function sendNotification(notification: Notification): Promise<void> {
  return notificationBreaker.execute(
    () => notificationApi.send(notification),
    async () => {
      // Fallback: enqueue for later delivery — don't lose the notification
      await outboxQueue.enqueue({ type: "NOTIFICATION", payload: notification });
      logger.warn("Notification service unavailable — queued for retry", { notificationId: notification.id });
    }
  );
}
```

**Strategy 4 — Graceful degradation (partial response):**
```ts
async function getOrderDetails(orderId: string): Promise<OrderDetails> {
  const [order, enrichment] = await Promise.allSettled([
    orderRepo.findById(orderId),      // critical — no fallback
    enrichmentBreaker.execute(         // non-critical — degrade gracefully
      () => enrichmentService.getOrderEnrichment(orderId),
      () => null                        // fallback: null → UI shows less detail
    ),
  ]);

  if (order.status === "rejected") throw new NotFoundError(orderId);

  return {
    ...order.value,
    enrichment: enrichment.status === "fulfilled" ? enrichment.value : null,
    // UI handles null enrichment — shows basic order info without recommendations
  };
}
```

**Strategy 5 — Fail fast with meaningful error:**
```ts
async function processPayment(dto: PaymentDto): Promise<ChargeResult> {
  return paymentBreaker.execute(
    () => stripeClient.charge(dto),
    () => {
      // Fallback: explicit failure — payment cannot be degraded
      throw new ServiceUnavailableError(
        "Payment processing is temporarily unavailable. Please try again in a few minutes.",
        { retryAfterMs: 30_000 }
      );
    }
  );
}
```

**Choosing a strategy:**

| Operation type | Recommended fallback |
|---|---|
| Read — non-critical enrichment | Stale cache or safe default |
| Read — critical data | Fail fast with meaningful error |
| Write — idempotent (notifications) | Queue for async retry (outbox) |
| Write — non-idempotent (payments) | Fail fast — cannot safely queue or default |
| Personalisation | Generic / popular items default |
| Configuration | Last-known-good config from local cache |

```ts
    return breaker;

  forceClose(name: string): void { this.breakers.get(name)?.forceClose(); }

      const breaker = this.breakers.get(name);

  }
```

## Section 7: Scenario / System Design Style Questions

**Q17. "Your payment service is calling Stripe. During peak load, Stripe slows down and your Node.js thread pool fills up with waiting requests, making the entire app unresponsive. Walk through how a circuit breaker fixes this."**
A: Walk through the failure cascade first, then the fix:

**Without circuit breaker — cascade:**
```
T=0:  Stripe starts responding slowly (5-second delays)
T=10: 100 requests queued, each waiting 5s → Node.js event loop backing up
T=20: Connection pool exhausted — DB queries also timing out (connections held by stuck requests)
T=30: Health checks failing — load balancer removes instance
T=40: Remaining instances absorb traffic — they also get overwhelmed
T=50: Full outage — entire checkout flow down
```

**With circuit breaker — contained failure:**
```
T=0:  Stripe starts responding slowly
T=5:  5 failures recorded (threshold reached) → circuit breaker OPENS
T=5+: All subsequent payment calls immediately get CircuitBreakerOpenError (microseconds)
      Fallback: payments queued in outbox for async retry
      Event loop is NOT blocked — fast rejection, no waiting
T=5+: DB, health checks, other services continue working normally
T=35: Reset timeout expires → circuit breaker enters HALF_OPEN
T=35: One probe call sent to Stripe
T=36: Probe succeeds → breaker CLOSES → normal traffic resumes
      Queued payments processed from outbox

Result: ~30-second degradation (queued payments) vs full outage ✓
```

**Q18. "A teammate suggests wrapping every service call in a circuit breaker. What concerns do you raise?"**
A: Challenge the blanket application — circuit breakers have costs and misuse scenarios:

**1. Not all errors should open a circuit breaker:**
```ts
// ✗ — Circuit breaker on a local DB call with a 404 error filter missing
// 404s (e.g., user not found) are not symptoms of a failing service — they are expected
// Without errorFilter, a flood of "user not found" would open the breaker
const userBreaker = new CircuitBreaker("user-repo", { failureThreshold: 5 });
// Every "user not found" counts as a failure → breaker opens on valid traffic ✗

// ✓ — Filter out expected, non-infrastructure errors
const userBreaker = new CircuitBreaker("user-repo", {
  failureThreshold: 5,
  errorFilter: (err) => !(err instanceof NotFoundError || err instanceof ValidationError),
});
```

**2. Internal services on the same host don't need circuit breakers:**
Circuit breakers are for calls that cross a network boundary. An in-process function call or a call to a sidecar on localhost doesn't need one — the failure mode is fundamentally different (no network timeout, no connection pool exhaustion).

**3. Idempotency must be verified before adding a breaker:**
If the operation being protected is not idempotent, a circuit breaker that opens during a request in-flight leaves the system in an unknown state. Ensure fallbacks account for this.

**4. Configuration requires domain knowledge:**
Threshold, timeout, and half-open probe counts must be tuned per dependency — a payment service needs conservative settings (low threshold, long timeout, few probes); a recommendation service can be more aggressive. Generic defaults produce either false positives (opens too easily) or miss real failures (opens too late).

**5. The fallback must be designed first:**
A circuit breaker without a meaningful fallback just changes the error type from "service timeout" to "circuit open." The fallback strategy (cache, queue, default, fail-fast) must be designed before adding the breaker.

```ts
  halfOpenMaxCalls: 3,
});
// Fallback: OUTBOX QUEUE — store email in DB, retry when SendGrid recovers
// User experience: email delayed, not lost; no user-facing error

// Checkout service — orchestrates with appropriate error handling per dependency
class CheckoutService {
  async checkout(dto: CheckoutDto): Promise<CheckoutResult> {
    // 1. Inventory — fail fast on breaker open or stock error
    const reservation = await inventoryBreaker.execute(
      () => this.inventory.reserve(dto.items)
      // No fallback — cannot proceed without stock confirmation
    );

    // 2. Payment — queue if Stripe is down
    const payment = await paymentBreaker.execute(
      () => this.payments.charge(dto.total, dto.paymentToken),
      async () => {
        const pendingId = await this.paymentOutbox.enqueue(dto);
        return { id: pendingId, status: "pending" };
      }
    );

    // 3. Shipping — use default if service is down
    const shippingRate = await shippingBreaker.execute(
      () => this.shipping.getRate(dto.shippingAddress, dto.items),
      () => Promise.resolve({ rate: DEFAULT_SHIPPING_RATE, carrier: "standard" })
    );

    const order = await this.orders.save({ ...dto, reservation, payment, shippingRate });

    // 4. Email — queue if SendGrid is down (never fail the checkout for email)
    await emailBreaker.execute(
      () => this.email.sendConfirmation(dto.customerEmail, order),
      () => this.emailOutbox.enqueue({ to: dto.customerEmail, orderId: order.id })
    ).catch(err => logger.error("Email fallback also failed", { orderId: order.id, err }));

    return { orderId: order.id, status: payment.status };
  }
}
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | No resilience | Retry only | Circuit Breaker only | Circuit Breaker + Retry |
|---|---|---|---|---|
| **Transient failure (momentary blip)** | Fails | Handles ✓ | Fails (counts toward threshold) | Handles ✓ |
| **Persistent failure (service down)** | Times out | Retries × N, still times out | Fails fast ✓ | Fails fast ✓ |
| **Resource exhaustion on failure** | Yes — threads block | Worse — N× more threads block | No — immediate rejection ✓ | No ✓ |
| **Recovery detection** | Manual | Manual | Automatic (half-open probe) ✓ | Automatic ✓ |
| **Load on failing service** | Full × timeout waits | N× worse | Zero during OPEN ✓ | Zero during OPEN ✓ |
| **Thundering herd on recovery** | Yes | Yes | Controlled (half-open max calls) ✓ | Controlled ✓ |
| **Fallback support** | No | No | Yes — on open or failure | Yes |
| **Observability** | None | Limited | Rich — state changes, metrics | Rich ✓ |

## Circuit Breaker Anti-Patterns at a Glance

| Anti-pattern | Description | Fix |
|---|---|---|
| **No error filter** | 4xx (client) errors counted as service failures — opens on valid traffic | Add `errorFilter` to exclude expected non-infrastructure errors |
| **Missing fallback** | Breaker open = changed error type, no degradation | Design fallback (cache, queue, default) before adding breaker |
| **Shared breaker across operations** | One breaker for all calls to a service — a failing read opens writes | Separate breakers per operation type or per criticality level |
| **Retry inside Circuit Breaker** | Retries counted as separate breaker calls — misses failure accumulation | Circuit Breaker (outer) → Retry (inner) |
| **Too-aggressive threshold** | Opens on first few errors during normal traffic spikes | Add `volumeThreshold`; use rate-based not count-based |
| **Too-lenient threshold** | Breaker opens too late — damage already done | Tune per service SLA; measure P99 latency to set slow-call thresholds |
| **No observability** | Breaker opens silently — engineers discover via user complaints | Emit metrics and structured logs on every state change; alert on OPEN |
| **No admin control** | Breaker stuck open during incident — no manual override | Expose `/admin/circuit-breakers/:name/close` with auth |
| **Non-idempotent fallback** | Queue write operations in fallback without idempotency key | Always include idempotency key; dedup in the queue consumer |
| **Circuit breaker on local calls** | Wrapping in-process or sidecar calls — no network failure mode | Only wrap cross-network calls with circuit breakers |

**Tip for the interview:** At the 5 YOE level, "what is the Circuit Breaker pattern" surfaces as: how do you prevent one slow downstream service from taking down your entire Node.js app, how do you design checkout to degrade gracefully when Stripe is having an incident, how do you combine retry with circuit breaker without amplifying load on a failing service, or how do you know when your circuit breaker is open in production. The sharp answer immediately names the three states (CLOSED/OPEN/HALF-OPEN) and the transition triggers, explains the cascade failure problem with a concrete before/after scenario (threads blocking vs fail-fast), distinguishes which errors should and should not count toward the threshold (4xx vs 5xx), designs a fallback per dependency criticality (fail-fast for payments, stale cache for product details, queue for notifications), and addresses observability (what metrics, what alerts). Explaining the layering of Circuit Breaker (outer) over Retry (inner) — "retry handles transient blips, circuit breaker handles persistent failures, and you need both ordered correctly to avoid amplifying load on a recovering service" — is the depth that lands at 5 YOE.
