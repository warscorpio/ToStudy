# Middleware Pattern in NestJS — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Middleware in NestJS and what problem does it solve?**
A: Middleware in NestJS is a function that executes in the request pipeline *before* the route handler. It has access to the `Request` object, the `Response` object, and the `next()` function that passes control to the next middleware or the route handler.

Middleware solves the **cross-cutting concern problem** — behaviour that must apply consistently across many routes without being duplicated in every controller or service:

- **Logging** — every request should be logged with method, URL, latency, and correlation ID. Without middleware, you'd add this to every controller method.
- **Authentication pre-processing** — extract and attach the JWT payload to the request before any route handler runs, so downstream guards and decorators can read it.
- **Rate limiting** — count and throttle inbound requests before they reach the application layer.
- **Request transformation** — normalise incoming payloads (strip null fields, normalise phone numbers to E.164, convert currency strings to paise integers) before validation runs.
- **Correlation ID injection** — generate or propagate a `X-Correlation-ID` header on every request so logs across services can be traced.

NestJS middleware is conceptually identical to Express middleware — NestJS runs on Express (or Fastify) under the hood, and `NestMiddleware` produces a function compatible with Express's `app.use()`. This means every existing Express middleware library works in NestJS out of the box.

**Q2. What is the execution order of the NestJS request pipeline and where does middleware fit?**
A: The full pipeline, in order:

```
Incoming HTTP Request
        │
        ▼
1. Middleware          ← execute first; can short-circuit the request
        │
        ▼
2. Guards              ← authorisation; can reject before the handler
        │
        ▼
3. Interceptors (pre)  ← wrap the handler; execute before and after
        │
        ▼
4. Pipes               ← transform and validate DTOs
        │
        ▼
5. Route Handler       ← controller method executes
        │
        ▼
6. Interceptors (post) ← execute after handler; can transform response
        │
        ▼
7. Exception Filters   ← catch and translate errors to HTTP responses
        │
        ▼
Outgoing HTTP Response
```

**Middleware vs Guards vs Interceptors — the practical distinction:**

| Concern | Where it belongs | Why |
|---|---|---|
| Attach correlation ID to request | Middleware | Runs before everything; no DI context needed |
| JWT authentication (verify token) | Guard | Has access to `ExecutionContext`; can inspect route metadata |
| Role-based authorisation | Guard | Needs `Reflector` to read `@Roles()` metadata |
| Request/response logging | Middleware or Interceptor | Middleware for raw HTTP timing; Interceptor for business-layer latency |
| Input transformation (DTO normalisation) | Pipe | Has access to `ArgumentMetadata`; runs just before the handler |
| Response envelope wrapping | Interceptor | Wraps the handler's return value |
| Error → HTTP translation | Exception Filter | Last line of defence |

**Q3. How do you create a NestJS Middleware class?**
A: Implement the `NestMiddleware` interface and decorate with `@Injectable()`:

```typescript
import { Injectable, NestMiddleware } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';
import { v4 as uuid } from 'uuid';

@Injectable()
export class CorrelationIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void {
    // Use the incoming header if present (from API gateway or upstream service)
    // otherwise generate a fresh UUID for this request
    const correlationId =
      (req.headers['x-correlation-id'] as string) ?? uuid();

    req.headers['x-correlation-id'] = correlationId; // attach to request
    res.setHeader('x-correlation-id', correlationId); // echo back in response

    next(); // pass control to the next middleware or route handler
  }
}
```

Three rules for NestJS middleware:
1. **`@Injectable()`** — required so the DI container can inject dependencies into it.
2. **Implements `NestMiddleware`** — enforces the `use(req, res, next)` signature.
3. **Must call `next()`** — unless intentionally short-circuiting (e.g., sending a 429 Too Many Requests). Forgetting `next()` hangs the request forever.

**Q4. How is middleware registered in NestJS and why is it different from Guards/Pipes/Interceptors?**
A: Middleware is registered in a module's `configure()` method via `MiddlewareConsumer` — not in `@Module()` metadata. This is because middleware applies to **routes** (URL patterns), while guards/pipes/interceptors apply to **handlers** (class/method decorators).

```typescript
import { Module, NestModule, MiddlewareConsumer, RequestMethod } from '@nestjs/common';

@Module({
  imports:     [LoanModule, NachModule, KycModule],
  controllers: [],
  providers:   [],
})
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer): void {
    consumer
      .apply(CorrelationIdMiddleware, RequestLoggingMiddleware) // applied in order
      .forRoutes('*');                                          // all routes
  }
}
```

Route-specific registration:

```typescript
configure(consumer: MiddlewareConsumer): void {
  // Apply to all routes globally
  consumer
    .apply(CorrelationIdMiddleware)
    .forRoutes('*');

  // Apply only to loan routes, all methods
  consumer
    .apply(RequestLoggingMiddleware)
    .forRoutes('loan-applications');

  // Apply only to specific method + route
  consumer
    .apply(RateLimitMiddleware)
    .forRoutes({ path: 'loan-applications', method: RequestMethod.POST });

  // Apply to everything EXCEPT health check
  consumer
    .apply(AuthTokenMiddleware)
    .exclude(
      { path: 'health',   method: RequestMethod.GET },
      { path: 'metrics',  method: RequestMethod.GET },
    )
    .forRoutes('*');

  // Apply using a controller class (route prefix auto-resolved)
  consumer
    .apply(AuditLogMiddleware)
    .forRoutes(LoanApplicationController, NachController);
}
```

The key difference from guards/interceptors: middleware is registered **globally by URL pattern** at the module level. Guards and interceptors are applied **locally by class/method decorator** or via `APP_GUARD` / `APP_INTERCEPTOR` global providers. This makes middleware the right tool when you need blanket coverage across URL patterns regardless of which controller handles them.

## Section 2: Core Middleware Patterns

**Q5. How do you implement a Request Logging Middleware with structured logging and latency tracking?**
A:

```typescript
import { Injectable, NestMiddleware } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';
import { AppLogger } from '../core/logger/app-logger.service';

@Injectable()
export class RequestLoggingMiddleware implements NestMiddleware {
  constructor(private readonly logger: AppLogger) {}

  use(req: Request, res: Response, next: NextFunction): void {
    const startTime     = Date.now();
    const correlationId = req.headers['x-correlation-id'] as string;
    const { method, originalUrl, ip } = req;

    // Log on request arrival
    this.logger.log('HTTP', `→ ${method} ${originalUrl}`, {
      correlationId,
      ip,
      userAgent: req.headers['user-agent'],
    });

    // Hook into response finish — fires after the response is sent
    res.on('finish', () => {
      const latencyMs    = Date.now() - startTime;
      const { statusCode } = res;
      const level = statusCode >= 500 ? 'error' : statusCode >= 400 ? 'warn' : 'log';

      this.logger[level]('HTTP', `← ${method} ${originalUrl} ${statusCode} (${latencyMs}ms)`, {
        correlationId,
        statusCode,
        latencyMs,
        contentLength: res.get('content-length'),
      });
    });

    next();
  }
}
```

Key points:
- `res.on('finish')` fires *after* the response is sent — this is where you capture response status and latency. Do not read response body here; it's already sent.
- Structured logging (JSON object as the third argument) makes logs queryable in Elasticsearch or CloudWatch.
- Use `correlationId` from the request header — `CorrelationIdMiddleware` must run before this one (middleware order is registration order).

**Q6. How do you implement a Correlation ID + Request Context Middleware that propagates context through the entire request lifecycle?**
A:

```typescript
// core/context/request-context.ts
import { Injectable, Scope } from '@nestjs/common';

@Injectable({ scope: Scope.REQUEST })
export class RequestContext {
  correlationId!: string;
  tenantId!:      string;
  userId?:        string;
  startTime!:     number;

  // Any service that injects RequestContext gets the per-request values
}

// core/middleware/request-context.middleware.ts
@Injectable()
export class RequestContextMiddleware implements NestMiddleware {
  constructor(private readonly requestContext: RequestContext) {}

  use(req: Request, res: Response, next: NextFunction): void {
    this.requestContext.correlationId =
      (req.headers['x-correlation-id'] as string) ?? uuid();
    this.requestContext.tenantId =
      (req.headers['x-tenant-id'] as string) ?? 'default';
    this.requestContext.startTime = Date.now();

    // Echo back so callers can trace their request
    res.setHeader('x-correlation-id', this.requestContext.correlationId);
    res.setHeader('x-tenant-id',      this.requestContext.tenantId);

    next();
  }
}

// Any service now gets context without receiving it as a method parameter
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly loanRepo:       LoanRepository,
    private readonly requestContext: RequestContext,
    private readonly logger:         AppLogger,
  ) {}

  async apply(dto: CreateLoanApplicationDto): Promise<LoanApplication> {
    this.logger.log('LoanApplicationService', 'Applying for loan', {
      correlationId: this.requestContext.correlationId,  // automatically available
      tenantId:      this.requestContext.tenantId,
    });
    // ...
  }
}
```

Register both in order in the module:

```typescript
configure(consumer: MiddlewareConsumer): void {
  consumer
    .apply(
      RequestContextMiddleware,  // 1. populate RequestContext
      RequestLoggingMiddleware,  // 2. log with correlationId already in context
    )
    .forRoutes('*');
}
```

**Q7. How do you implement a Rate Limiting Middleware using Redis for distributed rate limiting?**
A: In-memory rate limiting breaks in multi-instance deployments — each instance has its own counter. Redis-backed rate limiting shares state across all instances:

```typescript
import { Injectable, NestMiddleware } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';
import { Redis } from 'ioredis';
import { Inject } from '@nestjs/common';

@Injectable()
export class RateLimitMiddleware implements NestMiddleware {
  private readonly WINDOW_SECONDS = 60;   // 1-minute sliding window
  private readonly MAX_REQUESTS   = 100;  // 100 requests per minute per IP

  constructor(@Inject('REDIS_CLIENT') private readonly redis: Redis) {}

  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    // Key per IP + route family — prevents one IP from exhausting the loan apply endpoint
    const identifier = `rate_limit:${req.ip}:${this.routeFamily(req.originalUrl)}`;

    const pipeline = this.redis.pipeline();
    pipeline.incr(identifier);
    pipeline.expire(identifier, this.WINDOW_SECONDS);

    const [[incrErr, count]] = await pipeline.exec() as any;

    if (incrErr) {
      // Redis error — fail open (allow request); log the error
      console.error('Rate limit Redis error — failing open', incrErr);
      return next();
    }

    const remaining = Math.max(0, this.MAX_REQUESTS - (count as number));
    res.setHeader('X-RateLimit-Limit',     this.MAX_REQUESTS);
    res.setHeader('X-RateLimit-Remaining', remaining);
    res.setHeader('X-RateLimit-Reset',     Math.floor(Date.now() / 1000) + this.WINDOW_SECONDS);

    if ((count as number) > this.MAX_REQUESTS) {
      res.status(429).json({
        statusCode: 429,
        error:      'Too Many Requests',
        message:    `Rate limit exceeded. Try again in ${this.WINDOW_SECONDS} seconds.`,
        retryAfter: this.WINDOW_SECONDS,
      });
      return; // do NOT call next()
    }

    next();
  }

  private routeFamily(url: string): string {
    // Normalise URLs — /loan-applications/UUID/sanction → /loan-applications/:id/sanction
    return url.replace(/[0-9a-f-]{36}/gi, ':id').replace(/\?.*$/, '');
  }
}
```

For a fintech lending API, apply tighter limits to write operations:

```typescript
configure(consumer: MiddlewareConsumer): void {
  // Strict limit on loan application creation — prevent abuse
  consumer
    .apply(RateLimitMiddleware)
    .forRoutes({ path: 'loan-applications', method: RequestMethod.POST });

  // Looser limit on reads
  consumer
    .apply(RateLimitMiddleware)
    .forRoutes({ path: 'loan-applications', method: RequestMethod.GET });
}
```

**Q8. How do you implement a Body Sanitisation Middleware to normalise incoming payloads in a fintech context?**
A: Sanitisation middleware runs before `ValidationPipe` — it normalises input that is structurally valid but formatted inconsistently:

```typescript
@Injectable()
export class PayloadSanitisationMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void {
    if (req.body && typeof req.body === 'object') {
      req.body = this.sanitise(req.body);
    }
    next();
  }

  private sanitise(body: Record<string, any>): Record<string, any> {
    const sanitised: Record<string, any> = {};

    for (const [key, value] of Object.entries(body)) {
      if (value === null || value === undefined) continue; // strip null / undefined

      if (typeof value === 'string') {
        sanitised[key] = this.sanitiseString(key, value.trim());
      } else if (typeof value === 'object' && !Array.isArray(value)) {
        sanitised[key] = this.sanitise(value); // recurse for nested objects
      } else {
        sanitised[key] = value;
      }
    }

    return sanitised;
  }

  private sanitiseString(key: string, value: string): string {
    // Normalise PAN — ABCDE1234F or abcde1234f → ABCDE1234F
    if (key === 'pan') return value.toUpperCase();

    // Normalise phone numbers to E.164 — 09876543210, +919876543210, 9876543210 → +919876543210
    if (key === 'phone' || key === 'mobile') return this.normalisePhone(value);

    // Strip any leading/trailing whitespace from IFSC codes
    if (key === 'ifscCode') return value.toUpperCase().trim();

    return value;
  }

  private normalisePhone(phone: string): string {
    const digits = phone.replace(/\D/g, ''); // strip non-digits
    if (digits.length === 10) return `+91${digits}`;
    if (digits.length === 12 && digits.startsWith('91')) return `+${digits}`;
    return phone; // return as-is if unrecognised format — let ValidationPipe reject it
  }
}
```

Sanitisation vs Validation — the distinction:
- **Sanitisation** (middleware): "normalise the input into a canonical form." PAN `abcde1234f` → `ABCDE1234F`. No rejection.
- **Validation** (pipe): "is this input acceptable?" `ABCDE1234X` → reject with `400 Bad Request`.

Sanitisation runs first so validation operates on normalised input, reducing false rejections from formatting differences.

## Section 3: Functional Middleware

**Q9. What is functional middleware and when should you prefer it over class-based middleware?**
A: Functional middleware is a plain function with the `(req, res, next)` signature — no class, no `@Injectable()`, no DI. It is the correct choice when the middleware has no dependencies to inject:

```typescript
// Functional middleware — simple, zero overhead, no DI needed
import { Request, Response, NextFunction } from 'express';

export function RequestIdMiddleware(
  req: Request,
  res: Response,
  next: NextFunction,
): void {
  req.headers['x-request-id'] = req.headers['x-request-id'] ?? uuid();
  next();
}

// SecurityHeadersMiddleware — sets OWASP-recommended security headers
export function SecurityHeadersMiddleware(
  req: Request,
  res: Response,
  next: NextFunction,
): void {
  res.setHeader('X-Content-Type-Options',    'nosniff');
  res.setHeader('X-Frame-Options',           'DENY');
  res.setHeader('X-XSS-Protection',          '1; mode=block');
  res.setHeader('Strict-Transport-Security', 'max-age=31536000; includeSubDomains');
  res.setHeader('Referrer-Policy',           'strict-origin-when-cross-origin');
  res.removeHeader('X-Powered-By');          // hide Express fingerprint
  next();
}

// Registration — same MiddlewareConsumer API
configure(consumer: MiddlewareConsumer): void {
  consumer
    .apply(SecurityHeadersMiddleware, RequestIdMiddleware)
    .forRoutes('*');
}
```

**Decision guide:**

| Use functional middleware | Use class-based middleware |
|---|---|
| No external dependencies needed | Needs DI (Logger, Redis, ConfigService) |
| Pure transformation (headers, ID generation) | Needs to query a database or external service |
| Maximum performance (no class instantiation overhead) | Needs request-scoped state via injected providers |
| Wrapping existing Express middleware libraries | Complex logic that benefits from private methods |

**Q10. How do you use third-party Express middleware in NestJS?**
A: Since NestJS runs on Express, any Express-compatible middleware can be applied via `app.use()` in `main.ts` or via `MiddlewareConsumer` in a module:

```typescript
// main.ts — apply third-party middleware at the Express level
import * as helmet from 'helmet';
import * as compression from 'compression';
import * as cookieParser from 'cookie-parser';
import * as morgan from 'morgan';

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create(AppModule);

  // Security headers (more comprehensive than manual SecurityHeadersMiddleware)
  app.use(helmet({
    contentSecurityPolicy: {
      directives: {
        defaultSrc:  ["'self'"],
        scriptSrc:   ["'self'"],
        styleSrc:    ["'self'", "'unsafe-inline'"],
        imgSrc:      ["'self'", 'data:', 'https:'],
      },
    },
  }));

  // Gzip compression — reduce payload size
  app.use(compression());

  // Cookie parsing — needed for cookie-based sessions or CSRF tokens
  app.use(cookieParser(process.env.COOKIE_SECRET));

  // HTTP access log (dev only — replace with structured logger in production)
  if (process.env.NODE_ENV !== 'production') {
    app.use(morgan('dev'));
  }

  await app.listen(3000);
}
```

For middleware that needs NestJS DI (e.g., a third-party rate limiter that needs `ConfigService`), wrap it in a class-based `NestMiddleware`:

```typescript
@Injectable()
export class ThrottlerExpressMiddleware implements NestMiddleware {
  private readonly limiter: ReturnType<typeof rateLimit>;

  constructor(private readonly config: ConfigService) {
    // Construct the express-rate-limit instance here — config is now available
    this.limiter = rateLimit({
      windowMs: config.get<number>('THROTTLE_WINDOW_MS', 60_000),
      max:      config.get<number>('THROTTLE_MAX_REQUESTS', 100),
      message:  { statusCode: 429, error: 'Too Many Requests' },
    });
  }

  use(req: Request, res: Response, next: NextFunction): void {
    this.limiter(req, res, next);
  }
}
```

## Section 4: Middleware vs Other Pipeline Stages

**Q11. When should you use Middleware vs a Guard for authentication and authorisation?**
A: Authentication (verifying *who* the caller is) and authorisation (verifying *what* they can do) are related but distinct — and belong in different pipeline stages:

**Middleware for authentication pre-processing:**
```typescript
// Extract and attach the decoded JWT payload to the request
// — does NOT reject; just prepares data for the Guard
@Injectable()
export class AuthTokenMiddleware implements NestMiddleware {
  constructor(private readonly jwtService: JwtService) {}

  use(req: Request, res: Response, next: NextFunction): void {
    const authHeader = req.headers['authorization'];
    if (!authHeader?.startsWith('Bearer ')) {
      return next(); // no token — let the Guard decide whether to reject
    }

    try {
      const token   = authHeader.split(' ')[1];
      const payload = this.jwtService.verify(token); // throws if invalid
      req['user']   = payload;                        // attach to request
    } catch {
      // Expired or malformed token — don't reject here; let the Guard handle it
      // This allows public routes to work without a valid token
    }

    next();
  }
}

// Guard for authorisation — uses the user attached by middleware
@Injectable()
export class JwtAuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest<Request>();
    const user    = request['user'];

    if (!user) {
      throw new UnauthorizedException('Authentication required');
    }

    return true; // token is valid; pass to role-based guard or route handler
  }
}

// Role Guard — reads @Roles() decorator metadata; impossible in middleware
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.getAllAndOverride<Role[]>('roles', [
      context.getHandler(),
      context.getClass(),
    ]);
    if (!requiredRoles) return true; // no @Roles() decorator — route is role-agnostic

    const { user } = context.switchToHttp().getRequest();
    return requiredRoles.some(role => user?.roles?.includes(role));
  }
}
```

**The split:**
- **Middleware** — extract and decode the token; attach user to `req`. Runs globally for all routes. Does not read route metadata.
- **Guard** — check `req.user` exists (authentication) and has the required roles (authorisation). Has access to `ExecutionContext` and `Reflector` — can read `@Roles()`, `@Public()`, and other custom decorators on the route.

Guards cannot do what middleware does: run before the route is matched. Middleware cannot do what guards do: read metadata from the `@Roles()` decorator on the specific handler being invoked.

**Q12. When should you use Middleware vs an Interceptor for logging?**
A:

| Scenario | Use Middleware | Use Interceptor |
|---|---|---|
| Raw HTTP access log (method, URL, status, latency) | ✅ | — |
| Log the parsed DTO (after Pipes run) | — | ✅ |
| Latency including Pipe + Guard overhead | ✅ | — |
| Business operation audit log (who approved which loan) | — | ✅ |
| Attach request metadata before any NestJS processing | ✅ | — |
| Modify the response body before sending | — | ✅ |

```typescript
// Middleware — raw HTTP timing; fires before Guards/Pipes
@Injectable()
export class HttpTimingMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void {
    const start = process.hrtime.bigint();
    res.on('finish', () => {
      const ns = Number(process.hrtime.bigint() - start);
      res.setHeader('X-Response-Time', `${(ns / 1_000_000).toFixed(2)}ms`);
    });
    next();
  }
}

// Interceptor — business-layer latency; fires after Guards/Pipes
@Injectable()
export class AuditInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const request      = context.switchToHttp().getRequest();
    const handlerName  = context.getHandler().name;
    const controllerName = context.getClass().name;
    const start        = Date.now();

    return next.handle().pipe(
      tap(() => {
        // Handler succeeded — audit the operation
        this.auditService.log({
          action:      `${controllerName}.${handlerName}`,
          userId:      request.user?.id,
          latencyMs:   Date.now() - start,
          correlationId: request.headers['x-correlation-id'],
        });
      }),
      catchError(err => {
        // Handler threw — audit the failure
        this.auditService.logFailure({ /* ... */ });
        throw err;
      }),
    );
  }
}
```

The rule: use middleware for concerns that belong at the **HTTP transport layer** (timing, headers, raw body logging). Use interceptors for concerns that belong at the **application layer** (business audit trails, response shaping, retry logic).

## Section 5: Advanced Patterns

**Q13. How do you implement a Tenant Resolution Middleware for a multi-tenant NBFC lending platform?**
A:

```typescript
export interface TenantConfig {
  tenantId:      string;
  tenantName:    string;
  bureauProvider: 'CIBIL' | 'EXPERIAN';
  maxLoanAmount: number;
  minBureauScore: number;
}

@Injectable()
export class TenantResolutionMiddleware implements NestMiddleware {
  constructor(
    private readonly tenantConfigService: TenantConfigService,
    private readonly requestContext:      RequestContext,
    private readonly logger:              AppLogger,
  ) {}

  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    const tenantId = this.extractTenantId(req);

    if (!tenantId) {
      res.status(400).json({
        statusCode: 400,
        error:      'Bad Request',
        message:    'Missing x-tenant-id header',
      });
      return;
    }

    const config = await this.tenantConfigService.getConfig(tenantId);

    if (!config) {
      res.status(401).json({
        statusCode: 401,
        error:      'Unauthorized',
        message:    `Unknown tenant: ${tenantId}`,
      });
      return;
    }

    // Attach to RequestContext — available in all downstream services
    this.requestContext.tenantId     = config.tenantId;
    this.requestContext.tenantConfig = config;

    this.logger.log('TenantResolutionMiddleware', `Tenant resolved: ${config.tenantName}`, {
      tenantId:      config.tenantId,
      correlationId: this.requestContext.correlationId,
    });

    next();
  }

  private extractTenantId(req: Request): string | undefined {
    // Strategy 1: header (API-to-API, preferred)
    if (req.headers['x-tenant-id']) return req.headers['x-tenant-id'] as string;

    // Strategy 2: subdomain (NBFC-A.lending-platform.com)
    const host = req.hostname;
    const match = host.match(/^([a-z0-9-]+)\.lending-platform\.com$/);
    if (match) return match[1];

    // Strategy 3: API key prefix (NBFCA_sk_live_...)
    const apiKey = req.headers['x-api-key'] as string;
    if (apiKey) return apiKey.split('_')[0];

    return undefined;
  }
}
```

**Q14. How do you implement a CSRF Protection Middleware for a web-facing lending portal?**
A:

```typescript
import { doubleCsrf } from 'csrf-csrf';

@Injectable()
export class CsrfMiddleware implements NestMiddleware {
  private readonly doubleCsrfProtection: ReturnType<typeof doubleCsrf>['doubleCsrfProtection'];

  constructor(private readonly config: ConfigService) {
    const { doubleCsrfProtection } = doubleCsrf({
      getSecret:      () => this.config.get('CSRF_SECRET')!,
      cookieName:     '__Host-psifi.x-csrf-token',
      cookieOptions:  { secure: true, sameSite: 'strict', httpOnly: true },
      size:           64,
      getTokenFromRequest: (req) => req.headers['x-csrf-token'] as string,
    });
    this.doubleCsrfProtection = doubleCsrfProtection;
  }

  use(req: Request, res: Response, next: NextFunction): void {
    // Skip CSRF for API-to-API routes authenticated via API key or service JWT
    const isApiClient = req.headers['x-api-key'] || req.headers['x-service-token'];
    if (isApiClient) return next();

    // Apply double-submit cookie pattern for browser-originated requests
    this.doubleCsrfProtection(req, res, next);
  }
}
```

## Section 7: Common Anti-Patterns and Pitfalls

**Q18. What are the most common Middleware mistakes in a NestJS fintech codebase?**
A:

**Anti-pattern 1 — Forgetting to call `next()` in a non-terminating middleware:**
```typescript
// ❌ Request hangs forever — client receives no response
@Injectable()
export class LoggingMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void {
    console.log(`${req.method} ${req.url}`);
    // next() is missing — every request hangs after logging
  }
}

// ✅ Always call next() unless you're sending a response
use(req: Request, res: Response, next: NextFunction): void {
  console.log(`${req.method} ${req.url}`);
  next(); // ← required
}
```

**Anti-pattern 2 — Putting business logic in middleware:**
```typescript
// ❌ Middleware checking loan application limits — business logic in the wrong layer
@Injectable()
export class LoanLimitMiddleware implements NestMiddleware {
  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    const activeLoans = await this.loanRepo.countActiveByApplicant(req.body.applicantId);
    if (activeLoans >= 2) {
      res.status(422).json({ message: 'Maximum active loans reached' });
      return;
    }
    next();
  }
}
// This belongs in LoanApplicationService.apply() — middleware cannot access DTOs,
// cannot throw domain exceptions, and cannot participate in transactions

// ✅ Middleware handles cross-cutting infrastructure; business rules stay in services
```

**Anti-pattern 3 — Using middleware for authorisation instead of Guards:**
```typescript
// ❌ Middleware trying to check roles — cannot read @Roles() decorator metadata
@Injectable()
export class RoleCheckMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void {
    // There is no way to know which roles a route requires here
    // Middleware has no access to ExecutionContext or Reflector
    if (!req['user']?.roles?.includes('CREDIT_MANAGER')) {
      res.status(403).json({ message: 'Forbidden' });
      return;
    }
    next();
  }
}

// ✅ Role checking belongs in a Guard
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}
  canActivate(ctx: ExecutionContext): boolean {
    const requiredRoles = this.reflector.getAllAndOverride<Role[]>('roles', [
      ctx.getHandler(), ctx.getClass(),
    ]);
    return requiredRoles?.some(r => ctx.switchToHttp().getRequest().user?.roles?.includes(r)) ?? true;
  }
}
```

**Anti-pattern 4 — Registering middleware in the wrong module:**
```typescript
// ❌ Registering global middleware in a feature module — it only applies within that module's routes
// Feature modules don't control the global route registration
@Module({ /* ... */ })
export class LoanModule implements NestModule {
  configure(consumer: MiddlewareConsumer): void {
    consumer
      .apply(CorrelationIdMiddleware)
      .forRoutes('*'); // '*' here means all routes in LoanModule — not truly global
  }
}

// ✅ Global middleware belongs in AppModule
@Module({ imports: [LoanModule, NachModule] })
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer): void {
    consumer
      .apply(CorrelationIdMiddleware)
      .forRoutes('*'); // truly global — AppModule sees all routes
  }
}
```

**Anti-pattern 5 — Async middleware without error handling:**
```typescript
// ❌ Unhandled promise rejection crashes the process
@Injectable()
export class TenantMiddleware implements NestMiddleware {
  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    const config = await this.tenantService.getConfig(req.headers['x-tenant-id'] as string);
    // If getConfig() throws, the error is an unhandled rejection — process may crash
    req['tenantConfig'] = config;
    next();
  }
}

// ✅ Wrap async middleware in try/catch — pass errors to next()
async use(req: Request, res: Response, next: NextFunction): Promise<void> {
  try {
    const config = await this.tenantService.getConfig(req.headers['x-tenant-id'] as string);
    req['tenantConfig'] = config;
    next();
  } catch (err) {
    next(err); // passes error to Express error handler → NestJS Exception Filter
  }
}
```

**Q19. "Design the middleware stack for a lending API that serves both mobile app clients and internal microservices. The requirements are: request tracing, rate limiting (stricter for external), authentication pre-processing, payload sanitisation, and security headers."**

  private readonly externalLimits = { window: 60, max: 60  }; // 60 req/min for mobile
  private readonly internalLimits = { window: 60, max: 6000 }; // 6000 req/min for services

  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    const limits = req['callerType'] === 'INTERNAL'
      ? this.internalLimits
      : this.externalLimits;

// AppModule — registration order is execution order
configure(consumer: MiddlewareConsumer): void {
  consumer

**Q20. "Your audit team requires that every API request to the loan servicing platform is logged with: caller identity, request payload (PII-masked), response status, latency, and correlation ID — for RBI CERT-In compliance. Where does this live and how do you implement it?"**
A: Split across middleware and interceptor — each handles what it can access:

```typescript
// Middleware — captures raw HTTP metadata; runs before everything
@Injectable()
export class AuditIngressMiddleware implements NestMiddleware {
  constructor(
    private readonly auditStore: AuditStore,
    private readonly requestContext: RequestContext,
  ) {}

  use(req: Request, res: Response, next: NextFunction): void {
    // Store audit record stub — will be completed by the interceptor
    this.requestContext.auditId = uuid();

    const maskedBody = this.maskPii(req.body);

    this.auditStore.startRecord({
      auditId:       this.requestContext.auditId,
      correlationId: this.requestContext.correlationId,
      method:        req.method,
      path:          req.originalUrl,
      ip:            req.ip,
      userAgent:     req.headers['user-agent'],
      body:          maskedBody,   // PII masked before storage
      timestamp:     new Date(),
    });

    next();
  }

  private maskPii(body: any): any {
    if (!body || typeof body !== 'object') return body;
    const masked = { ...body };

    // Mask PAN — ABCDE1234F → ABCXX1234F
    if (masked.pan) masked.pan = masked.pan.replace(/^(.{3})(.{2})/, '$1XX');

    // Mask bank account — keep last 4 digits
    if (masked.accountNumber) {
      masked.accountNumber = '****' + masked.accountNumber.slice(-4);
    }

    // Mask Aadhaar — keep last 4 digits
    if (masked.aadhaar) {
      masked.aadhaar = '****-****-' + masked.aadhaar.slice(-4);
    }

    return masked;
  }
}

// Interceptor — completes the audit record with response outcome and latency
@Injectable()
export class AuditEgressInterceptor implements NestInterceptor {
  constructor(
    private readonly auditStore: AuditStore,
    private readonly requestContext: RequestContext,
  ) {}

  intercept(ctx: ExecutionContext, next: CallHandler): Observable<any> {
    const start = Date.now();

    return next.handle().pipe(
      tap((responseBody) => {
        this.auditStore.completeRecord(this.requestContext.auditId, {
          statusCode: ctx.switchToHttp().getResponse().statusCode,
          latencyMs:  Date.now() - start,
          userId:     this.requestContext.userId,
          outcome:    'SUCCESS',
        });
      }),
      catchError((err) => {
        this.auditStore.completeRecord(this.requestContext.auditId, {
          statusCode: err.status ?? 500,
          latencyMs:  Date.now() - start,
          userId:     this.requestContext.userId,
          outcome:    'FAILURE',
          error:      err.message,
        });
        throw err;
      }),
    );
  }
}
```

The audit record is opened by middleware (with request payload) and closed by the interceptor (with response status and latency). The `auditId` in `RequestContext` links them. PII masking happens in middleware — the sensitive data never reaches the audit store unmasked, satisfying CERT-In data handling requirements.

## Quick Reference: Middleware Pattern Cheat Sheet

```
MIDDLEWARE PATTERN — QUICK REFERENCE
──────────────────────────────────────

PIPELINE POSITION
  Middleware → Guards → Interceptors (pre) → Pipes → Handler
            → Interceptors (post) → Exception Filters

WHAT MIDDLEWARE CAN DO
  ✅ Access req, res, next
  ✅ Modify request headers and body before Guards/Pipes see them
  ✅ Short-circuit the pipeline (send response, skip next())
  ✅ Attach data to req (correlationId, tenantConfig, decoded token stub)
  ✅ Inject NestJS providers (Logger, Redis, ConfigService)
  ✅ Wrap Express middleware libraries

WHAT MIDDLEWARE CANNOT DO
  ❌ Read @Roles(), @Public() or other handler metadata (use Guard + Reflector)
  ❌ Access the parsed DTO (Pipes haven't run yet)
  ❌ Modify the response body after the handler (use Interceptor)
  ❌ Throw NestJS HttpException and have it auto-handled (use next(err))

REGISTRATION
  // In AppModule.configure() — route-pattern based
  consumer.apply(MiddlewareA, MiddlewareB).forRoutes('*');
  consumer.apply(RateLimit).forRoutes({ path: 'loan-applications', method: POST });
  consumer.apply(Auth).exclude({ path: 'health', method: GET }).forRoutes('*');
  consumer.apply(Audit).forRoutes(LoanController, NachController);

CLASS VS FUNCTIONAL
  Class middleware  → needs DI (Logger, Redis, ConfigService)
  Functional        → no dependencies; pure transformation/header ops

RECOMMENDED MIDDLEWARE STACK ORDER
  1. SecurityHeadersMiddleware    — headers on every response
  2. RequestContextMiddleware     — correlationId, tenantId, startTime
  3. RequestLoggingMiddleware     — log ingress (correlationId available)
  4. CallerTypeMiddleware         — internal vs external classification
  5. RateLimitMiddleware          — throttle before processing
  6. AuthTokenMiddleware          — extract + attach JWT payload (Guard validates)
  7. PayloadSanitisationMiddleware — normalise PAN, phone, IFSC before Pipes

ASYNC MIDDLEWARE
  async use(req, res, next): Promise<void> {
    try { /* async work */; next(); }
    catch(err) { next(err); } // always pass errors to next(err)
  }

FINTECH USE CASES
  → CorrelationId propagation (X-Correlation-ID for CERT-In audit)
  → Tenant resolution (NBFC partner identification via header/subdomain)
  → Distributed rate limiting (Redis; stricter for external callers)
  → PII masking (PAN, Aadhaar, account number before audit log storage)
  → Payload normalisation (PAN uppercase, E.164 phone, IFSC trim)
  → Security headers (Helmet; hide X-Powered-By; HSTS)
  → CSRF protection (double-submit cookie for browser-originated requests)

MIDDLEWARE vs GUARD vs INTERCEPTOR
  Cross-cutting HTTP concern, pre-route → Middleware
  Auth / role check, reads @Roles()    → Guard
  Business audit, response transform   → Interceptor
```
